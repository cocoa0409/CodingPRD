# Electrical Contractor Prefabrication & Model Coordination API — Product Requirements Document

## 1. Introduction

An electrical contractor's profitability on a large commercial job is decided long before the first conduit is strapped to a deck. Quantities have to be pulled off a coordinated building model, work packages have to be released to a prefabrication shop early enough to beat vendor lead times, fabricated content has to land in the right laydown slot and be hoisted during an agreed window, and the field crew that sets it has to be staffed against a labor agreement that caps the apprentice-to-journeyman mix. Coordination with the mechanical, plumbing and sprinkler trades on the same work front constrains all of it. When a design change lands after content has already been fabricated, the rework, the change-order pricing and the ship-date consequences ripple back through every one of those decisions.

This document specifies a single REST service, mounted under the `/prefab` prefix, that models that operating loop end to end: project and model registration, quantity takeoff, rack layout, work-package release to the shop, shop fabrication of discrete components, jobsite delivery logistics, field installation, crew-day labor reporting with jurisdiction compliance, procurement releases against vendor lead times, and design revisions with their rework and change-order pricing.

The service is an immediate-consistency system with optimistic concurrency on its four decision points, a server-side logical clock that drives every deadline, hoisting window and schedule-slippage evaluation, and a set of derived project-level rollups (posture, installed percentage, craft-hours credit, idle capacity) that are recomputed rather than stored by hand. Everything the contractor looks at — is this package releasable, is this crew legal, is this revision worth approving — is a derived answer over registered facts, and this document is the specification for how those answers are computed.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two headers: `X-User-ID` and `X-User-Role`. A request missing either header, or carrying a role that is not one of the eight declared roles, is rejected with `ERR_UNAUTHORIZED` (HTTP 401). A request whose role is declared but is not permitted for the requested operation is rejected with `ERR_FORBIDDEN` (HTTP 403). These two checks are performed before any business rule is evaluated.

The eight roles, spelled exactly as they must appear in the `X-User-Role` header, are `PlatformAdmin`, `ProjectManager`, `ModelCoordinator`, `ShopForeman`, `LogisticsCoordinator`, `ProcurementLead`, `GeneralForeman`, and `InstallForeman`. Each role holds a set of exclusive operations that no other role may perform, plus a set of shared read operations; §4 states the authorized role list for every endpoint.

All eight roles are opaque operators: when `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity, and the server does not compare it to any entity's `id`. The same holds for `ProjectManager`, `ModelCoordinator`, `ShopForeman`, `LogisticsCoordinator`, `ProcurementLead`, `GeneralForeman` and `InstallForeman` — in every case the identifier is an opaque operator identity. It is recorded where a workflow explicitly names a person (for example `receiving_user_id` on a procurement release, which holds the operator who will acknowledge receipt, and `foreman_id` on a crew day, which the reporting foreman supplies as a real worker id), but role identity itself is never used for ownership comparison.

Obvious division of labor: `PlatformAdmin` owns reference data, the posture ladder and the logical clock. `ProjectManager` owns the schedule, work-package release decisions, revision submission and approval, rework disposition, and the re-drafting of a rejected revision. `ModelCoordinator` owns model versions, extraction lines and rack layouts. `ShopForeman` owns shop production status, component fabrication, and rework execution. `LogisticsCoordinator` owns staging, loading, dispatch, unload and delivery. `ProcurementLead` owns material releases from creation through receipt. `GeneralForeman` owns roster dispatch, crew days, activity status and the written installation sequence agreement. `InstallForeman` owns setting delivered prefab content in the field.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept `limit` and `offset` query parameters. `limit` defaults to 10, accepts a minimum of 1 and a maximum of 100, and `offset` defaults to 0 and accepts values of 0 or greater. An omitted `limit` or `offset` behaves exactly as the defaults above; a value outside the permitted range is rejected rather than silently clamped.

Lists are ordered by `created_at` ascending unless a workflow explicitly states another ordering. Paginated responses report `limit`, `offset`, `total_count` and `has_more` in the `meta` object; `total_count` is the number of resources matching the filter before pagination is applied, and `has_more` is true when further resources remain after the returned page. Every list endpoint that supports filtering does so by the foreign-key style query parameters named in §4 — for example the model, project, rack, activity, revision or component identifier that the caller wants the children of.

### 2.4. Resource Identity, Versioning and Mutation Semantics

Every persisted resource in this service — a project, a worker, a labor-agreement rate row, a trade activity, a crew day, a compliance-ledger row, a model version, a takeoff line, an assembly, a rack, a work package, a fabricated component, a revision, a rework job or a material release — carries the same four structural properties. Every one of the fifteen resource types uses the common field set; there are no exceptions in this service.

The `id` is a server-minted UUID with no type prefix or other decoration. The `created_at` and `updated_at` values are ISO 8601 UTC timestamps carrying three fractional digits, and `created_at` never changes after creation. A resource's `version` is a non-negative integer that starts at its initial value and is incremented by exactly one each time the resource is mutated through a documented operation; a mutation that is rejected leaves the version untouched. `updated_at` is refreshed whenever the resource is mutated.

Not every field on a resource is supplied by the caller. Some are captured at registration because they describe a fact about the world (a `project_code`, a `worker_code`, a `rack_code`), others are stamped by the server because they record when something happened (a `coordinated_at_iso`, an `actual_start_iso`, a `release_to_shop_iso`, a `restriction_since_iso`, a `locked_release_iso`, a `takeoff_hash`), and a third group — the largest — are computed rollups that the server derives and re-derives rather than accepts. A request that supplies a computed field has that value ignored; the derived value always wins. §3 describes, per resource, which is which.

Mutating operations are idempotent in the sense that they are state-guarded rather than overwrite-style: a transition that requires a specific from-state fails with `ERR_INVALID_PREFAB_TRANSITION` (HTTP 409) if the resource is not in it, and a resource in a terminal condition for that dimension cannot be moved out of it. The service never applies a partial mutation: if any precondition of an operation fails, no field of the target resource, and no cascaded field of any related resource, is changed. A creation whose validation refuses it stores no row for the resource it would have created — the refusal is a pure no-op on the resource set, so nothing half-built is left behind for a later read to find.

### 2.5. The Logical Clock

Schedule evaluation in this service does not read the host's wall clock. The service maintains a single logical clock that starts at exactly `2026-09-01T00:00:00Z` when the process starts, and the clock never falls back to wall-clock time before the clock-setting operation has been called. An administrative capability lets a caller advance or rewind the logical clock by supplying the target instant in `to_iso8601`; after that call, every subsequent deadline test, hoisting-window derivation, slippage evaluation and staleness computation reads the new instant.

Every server-stamped timestamp in this document is stamped from the logical clock, not from wall time: `coordinated_at_iso` when a model version leaves `DRAFT`, `actual_start_iso` when a trade activity enters `ACTIVE`, `release_to_shop_iso` when a work package is released, `restriction_since_iso` when a procurement release enters `RESTRICTED`, and `locked_release_iso` when a release date is frozen. Registering a worker also stamps a safety-verification expiry, computed as the logical clock instant plus 90 days. Tests drive the clock deliberately, so any implementation that reads wall time for these values will diverge from the specification.

### 2.6. Optimistic Concurrency on the Four Decision Points

Four write operations in this service are gated by an optimistic-concurrency check, because each of them is a decision that other writers can invalidate. Each such request must carry the stated expected-version field as a non-optional input, and the field must equal the current `version` of the named parent resource. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412). Endpoints not covered here do not accept a version field at all.

Releasing a work package carries `expected_prefab_order_version`, the client's last observed `version` of that work package. If another writer has already advanced the order — a prior release, a shop-status change, or a rework cascade triggered by an approved revision — the release is rejected with `ERR_STALE_VERSION` (HTTP 412) and the client's view of the order is not acted upon any further.

Declaring a procurement release to the vendor carries `expected_project_version`, the client's last observed `version` of the owning project. Between the client's read and the declaration the project's posture may have moved to `HOLD` or `FROZEN` or its rollups may have shifted, so a mismatch rejects the declaration with `ERR_STALE_VERSION` (HTTP 412).

Acknowledging a foreman's crew-day report carries `expected_crew_day_version`, the client's last observed `version` of that crew-day row. Another writer may already have acknowledged the same report, in which case the hours the client acted on are no longer current and the acknowledgment is rejected with `ERR_STALE_VERSION` (HTTP 412).

Approving a revision carries `expected_model_version_version`, the client's last observed `version` of the model version the revision targets. The model version may already have been superseded by an earlier approved revision, so a mismatch rejects the approval with `ERR_STALE_VERSION` (HTTP 412).

The staleness test is a pure value comparison: it rejects a request whose supplied expected version does not equal the parent's current version. It is evaluated before any business rule of the operation, and it is not a lock, a lease or a queue — nothing about the check depends on requests overlapping in time.

### 2.7. Numeric Precision and Rounding

Money in this service is held in whole cents as an integer-valued number, and craft hours are held as a number. Unless a computation says otherwise, the rounding method is round half up — a value exactly halfway between two representable results rounds away from zero — and the number of decimal places is as follows. Derived project rollups that carry a percentage or a ratio — `slippage_pct`, `installed_pct`, and the productivity percentage produced by the productivity-actuals computation — are stated to four decimal places. The apprentice ratio caps `apprentice_ratio_max`, `ratio_limit` and `wait_ratio_limit`, and the labor-hour measures that feed the field-credit ledger, are stated to two decimal places. `journey_ring_claim_hours` and `craft_hours_credit` are stated to two decimal places, as are the per-line craft hours produced by the conduit-craft-hours and conduit-run-impact computations. Whole-cent monetary values — `labor_cost_cents`, `adjusted_value_cents`, `total_cents`, `gross_payroll_cents`, `adjusted_payroll_cents`, `pipeline_value_cents`, `completed_value_cents`, `approved_change_value_cents`, `idle_capacity_cents`, `craft_hours_balance`, and both variants of the revision cost impact — are stated to zero decimal places, that is, as whole cents. Hoisting windows and procurement timings are stated in whole days, each offset rounded up to the next whole day.

Where a computation sums per-item values, each item is rounded before the sum is taken, so that per-item rounding never accumulates past the total. This is stated explicitly for the gross payroll reconciliation, whose per-crew-day amounts are rounded to whole cents before they are added into the ledger row's totals, and for the craft-hours balance, whose terms are each rounded before the sum so that its two compensating terms cancel exactly.

### 2.8. The Order in Which Validations Are Evaluated

Because most operations in this service are guarded by several rules at once, two clients can send the same broken request and receive different errors depending on which rule fires first. The evaluation order is therefore part of the contract, and it is fixed:

First, authentication: the headers must be present and the role must be one of the eight declared roles (`ERR_UNAUTHORIZED`, HTTP 401). Second, authorization: the role must be permitted for the operation (`ERR_FORBIDDEN`, HTTP 403). Third, existence of the explicitly named entities, in this order — the project named in the path or body (`ERR_PROJECT_NOT_FOUND`, HTTP 404), then the model version named in the path or body (`ERR_MODEL_VERSION_NOT_FOUND`, HTTP 404), then the work package named in the path (`ERR_PREFAB_ORDER_NOT_FOUND`, HTTP 404), then every other referenced entity id, meaning a worker, trade activity, crew day, rack, takeoff line, foreman or revision-impact reference (`ERR_REFERENCED_ENTITY_NOT_FOUND`, HTTP 404), and finally the resolution of each entry of a revision's `impact_keys` to a declared artifact (`ERR_AFFECTED_REF_NOT_FOUND`, HTTP 404).

Fourth, and still before any business rule runs, the optimistic-concurrency test on the supplied expected version (`ERR_STALE_VERSION`, HTTP 412). Fifth, the from-state test: the target resource must be in the state its transaction requires, across the `fabricate_status`, `deliver_status`, `shipment_status`, component `install_status`, `ReworkJob.status`, `Revision.status`, `TradeActivity.status`, `MaterialRelease.status` and `ModelVersion.status` dimensions (`ERR_INVALID_PREFAB_TRANSITION`, HTTP 409). Only after all of those pass are the business rules evaluated.

The business rules themselves carry an order too, and where they overlap on the same operation the earlier one in this list wins. First, the two release-gate rules: an active engineering hold surfaces as `ERR_ENGINEERING_HOLD_ACTIVE` (HTTP 409) before a material hold, which surfaces as `ERR_MATERIAL_HOLD_ACTIVE` (HTTP 409). Then the written installation sequence agreement (`ERR_INSTALL_SEQUENCE_VIOLATION`, HTTP 409), then the apprentice ratio cap (`ERR_APPRENTICE_RATIO_EXCEEDED`, HTTP 409), then the hoisting-window conflict test (`ERR_HOISTING_WINDOW_CONFLICT`, HTTP 409), then the laydown-slot availability test (`ERR_LAYDOWN_SLOT_UNAVAILABLE`, HTTP 409), then the jurisdiction dispatch band test (`ERR_JURISDICTION_DISPATCH_BAND`, HTTP 422), then the takeoff duplicate-hash test (`ERR_DUPLICATE_TAKEOFF_LINE`, HTTP 409), then the apprentice-period consistency test (`ERR_APPRENTICE_PERIOD_INVALID`, HTTP 422), then the model-quantity-resolution test (`ERR_MODEL_QUANTITY_UNRESOLVED`, HTTP 409), then the conduit-type test (`ERR_CONDUIT_TYPE_NOT_PERMITTED`, HTTP 422), then the rack capacity test (`ERR_RACK_CAPACITY_EXCEEDED`, HTTP 409), then the label-code test (`ERR_LABEL_CODE_MISSING`, HTTP 422), then the non-empty impact-set test (`ERR_REVISION_IMPACT_REQUIRED`, HTTP 422), then the supersession test (`ERR_MODEL_SUPERSEDED`, HTTP 409), then the craft-hours ceiling test (`ERR_CRAFT_HOURS_EXCEEDED`, HTTP 409), then the service-lifecycle test (`ERR_SERVICE_LIFECYCLE_INVALID`, HTTP 422), then the qualification-code length test (`ERR_SHIFT_BAND_TOO_LONG`, HTTP 422), then the blocked safety-gate test (`ERR_REVISION_SAFETY_BLOCKED`, HTTP 409), then the material-release deadline test (`ERR_MATERIAL_RELEASE_DEADLINE`, HTTP 409), then the lapsed-fabrication-window test (`ERR_FABRICATION_WINDOW_LAPSED`, HTTP 409), and finally the already-frozen-window test (`ERR_WINDOW_ALREADY_FROZEN`, HTTP 409).

The ordering matters in practice. An approval attempted against a release whose safety gate is `BLOCKED` and whose impact set is empty returns the impact-set error; a release attempted against an order that is both on engineering hold and awaiting an undeclared commodity returns the engineering-hold error.

### 2.9. Hierarchical Addressability and Reference Resolution

Resources in this service are addressed in their own right, not only as children. A rack lives inside a model version and is reached by its own identifier; a takeoff line is reached by its own identifier; a fabricated component is reached by its own identifier even though it belongs to a work package, which in turn belongs to a project. Where a path names more than one resource — as in a work-package release, a component fabrication, a component install or an activity status change — the server validates the named resources from left to right and reports the first that fails, using the existence rules of §2.8.

Relationships are expressed by reference rather than by containment in the payload. A trade activity names the project it belongs to through its `project_id`, the rate row it is priced with through its `rate_id`, the revision that produced its rework through its `revision_id`, and the activity whose permit unblocks it through its `permit_id` — the last of which is a self-referential link between two activities, forming the installation-sequence chain. A fabricated component names its work package through `prefab_order_id`, the rack it is installed on through `rack_id`, the extracted line it satisfies through `takeoff_line_id`, and the component that gates it through `predecessor_component_id`, again self-referential. A model version names its lineage predecessor through `model_id`, which points at another model version. A revision names both the version it was raised against (`model_version_id`) and the successor version it produces (`revised_version_id`). Every one of these references must resolve to an existing resource of the stated kind, or the operation fails with `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404) as set out in §2.8.

Reads are bidirectional. Each list endpoint exposes the reverse-reachability direction of the same relationships: a caller can list the crew days reported by a given foreman, or filtered by a given worker; the trade activities of a given revision, rate row or permitting activity; the components assigned to a given rack or satisfying a given takeoff line; the rework jobs of a given component or revision; the compliance-ledger rows priced at a given rate row. This is the mechanism by which a consumer reconstructs the graph without embedding child collections in parent payloads.

### 2.10. Derived Quantities, Recomputes and Conserved Balances

Most of what a project manager looks at is derived, and the service treats six of those derivations as system-wide principles rather than as one-off report calculations. Their full formulas live in §3 where they belong to the workflow that triggers them; this subsection states the properties that hold everywhere.

First, recomputation is triggered by mutation, not by read. Project posture, the pipeline and completed value balances, installed percentage, craft-hours credit, fabrication-locked, external-gate-open and apprentice-breach flags are all recomputed as side effects of the operations that change their inputs, and they may additionally be recomputed on demand. A caller never has to recompute them manually for them to be correct.

Second, several of these balances are conserved across a forward action paired with its compensating action. The craft-hours balance `craft_hours_balance` is unchanged when a fabricated work package is reverted to planned, and unchanged by a load-then-unload cycle, provided the same content is re-credited to the pipeline balance. The field-credit balance is likewise unchanged when a loaded component is set in the field, because credited hours are a labor measure rather than a value measure. The released-quantity ledger `released_quantity` is unchanged by material receipt, because receipt moves quantity between pipeline buckets rather than into them. These are invariants, not coincidences: tests assert them.

Third, an empty or zero-denominator input has a defined answer rather than an error. A project with no non-`COMPLETE` activity has `slippage_pct` of zero and posture `ON_TRACK`. A project whose total installed and pipeline value is zero has an `installed_pct` of zero. A project with `man_hours_total` of zero has an idle-capacity cost of zero. A worker with no credited crew days has zero ring hours.

Fourth, quantities that are stated as a percentage are stored as a fraction between zero and one, not as a number out of one hundred — `shop_utilization_pct`, `prefab_share_pct`, `installed_pct`, `slippage_pct`, `burden_pct`, `submitted_markup_pct` and `prefab_share_pct` are all fractions. The ladder thresholds expressed in this document as percentages are comparisons against those fractions.

Fifth, a superseded or scrapped input contributes zero rather than negative. A takeoff line that has been marked superseded contributes nothing to its model version's zone quantity total, and a component with install status `SCRAPPED` is counted in neither the pipeline balance nor the completed balance while still being counted in the man-hour totals used for the release credit.

Sixth, reference data is versioned by effective date. A labor-agreement rate row takes effect on its `effective_from_iso`; the row that governs a piece of work is the latest row for the relevant jurisdiction whose effective date is at or before the work date, so a later-dated row never governs earlier work even when it was entered first.

### 2.11. Capacity and Conflict Guards

Three physical-world guards run across the service and each is enforced at more than one operation.

A rack may not be overloaded. The rack's `reserved_streams_and_phase_cf` value is the sum of `quantity` over the components bound to that rack whose install status is one of `PLANNED`, `FABRICATED`, `LOADED`, `REWORK` or `SCRAPPED`; components in `SET` and components with no rack binding are excluded. The check passes when that sum is at most 95 percent of the rack's `value_capacity_cf`. The comparison is inclusive at the boundary — a rack sitting exactly at 95 percent passes, and a hundredth of a cubic foot above it fails with `ERR_RACK_CAPACITY_EXCEEDED` (HTTP 409). The same guard runs when a component is created and when a rework job is resolved by scrapping.

A laydown slot may not be double-booked. A slot at an index between 1 and the project's `laydown_slots` counts as free when the window from the release instant inclusive to the delivery instant exclusive of every other non-terminal work package on the project is excluded. If no such slot survives that exclusion the release fails with `ERR_LAYDOWN_SLOT_UNAVAILABLE` (HTTP 409); the assigned index is recorded on the order as `laydown_slot_index`.

A hoisting window may not overlap. A proposed window — the half-open interval from `hoisting_start_iso` inclusive to `hoisting_end_iso` exclusive — must not overlap any already-frozen window booked under the same `hoisting_window_id`, and no more than one non-terminal work package of the same project may carry the same `hoisting_start_iso` date. A violation fails with `ERR_HOISTING_WINDOW_CONFLICT` (HTTP 409), both when a work package is created and when it is released.

## 3. Business Logic & Workflows

### 3.1. The Coordinated Model, Its Extraction Set and Its Rack Layout

Everything downstream of a design decision begins with a coordinated building model. A `ModelCoordinator` registers a building model revision letter and points it at the version it succeeds using `model_id`, forming a self-referential lineage chain across successive letters; the `revision_letter` is unique within that lineage. A newly registered version is `DRAFT`, its `zone_quantity_total` starts at zero and its `empty_takeoff` flag starts true. Coordinating the version — the act of freezing it as the model everyone will take quantities from — requires that the version's extraction set is not empty: `zone_quantity_total` must be at least 1 and `empty_takeoff` must be false, otherwise the request is refused with `ERR_MODEL_QUANTITY_UNRESOLVED` (HTTP 409), and this same rule blocks a revision from being approved against a version whose quantities do not resolve. A successful coordination moves the version to `COORDINATED` and stamps `coordinated_at_iso` from the logical clock. `COORDINATED` versions may still receive further extraction lines; the extraction set can be re-driven without reopening `DRAFT`.

Quantities are extracted one line at a time. Each line names the version it came from in `model_version_id`, the install zone in `zone_code`, the assembly definition in `assembly_code`, the installation method in `conduit_run_type`, the model's own conduit token in `conduit_run_type_code`, the extracted `quantity` in the assembly's unit of measure, and the fraction of that quantity the shop will supply rather than the field cut in `prefab_share_pct`. The accepted `conduit_run_type` values are `MC_CABLE`, `EMT_OVERHEAD`, `EMT_EMBEDDED`, `RIGID_RACK`, `OVERHEAD_RACK`, `UNDERGROUND_DUCTBANK` and `ALUMINUM_RACEWAY`. Extraction stamps a content hash — `takeoff_hash`, a digest over the version, zone, assembly and quantity — and that hash is the line's duplicate key: extracting the same content twice against the same `model_version_id`, or coordinating a version whose set repeats a hash, is refused with `ERR_DUPLICATE_TAKEOFF_LINE` (HTTP 409). A line must carry a positive `quantity`, and a re-extraction that would drive the owning version's zone quantity total below 1 is refused with `ERR_MODEL_QUANTITY_UNRESOLVED` and leaves both totals unchanged. An extracted line is live at the `EXTRACTED` stage of its own lifecycle, and becomes `SUPERSEDED` only when an approved revision names its hash — the two stages are mutually exclusive, and a superseded line is retained for audit rather than deleted.

The conduit token is checked against the assembly it is claimed to belong to. Every assembly publishes the conduit code tokens it was engineered for in `ideal_conduit_type_codes`, and a line's `conduit_run_type_code` must be a member of that array for its `assembly_code`; a code outside the array, or an installation method outside the permitted set above, is refused with `ERR_CONDUIT_TYPE_NOT_PERMITTED` (HTTP 422).

Two derived totals belong to the version rather than to any line: `zone_quantity_total` is the sum of the quantity of every non-superseded line extracted from that version, and `assembly_quantity_total` is the same content grouped by `assembly_code`. Both are recomputed whenever a line is added or superseded. A line that a later approved revision names is marked superseded: it stops contributing to `zone_quantity_total` and stops being billed, but the row itself is retained so the audit trail of what was taken off survives — and if its content was already installed, that content reappears as tied shipment hours rather than vanishing (see §3.7).

Assemblies are the catalog that turns quantity into hours. An assembly is identified by a unique `assembly_code` and belongs to a prefab family recorded in `assembly_kind` — `RACK`, `BRANCH_TRUNK`, `PANEL_FEEDER`, `DEVICE_STRAP` or `SWITCHGEAR_SECTION`. Its `unit_of_measure` is either `LINEAR_FEET` or `EACH`, and linear-footage families such as `RACK` and `BRANCH_TRUNK` use `LINEAR_FEET` while count-based families such as `DEVICE_STRAP` use `EACH`. The labor content of an assembly is described three ways, because the shop and the field pay differently for the same unit depending on how much the shop did: `prefab_hours_per_unit` is the shop hours to build one unit and is the minimum achievable craft content for that assembly, `field_hours_per_unit` is what one unit costs the field when it arrives pristine as a single piece, and `supported_field_hours_per_unit` is what it costs when it arrives cut, labeled and kitted but unassembled. When a unit arrives not merely supported but rigged and spotted on the deck, the field effort is further multiplied by `field_productivity_factor`. Assemblies also carry the commercial side of the unit: `material_price_cents` is the list material price per unit, `core_charge_cents` is the core charge billed on each unit, and `recycled_credit_cents` is the credit earned when a unit's core comes back. Finally, `is_switchgear` marks the long-lead switchgear family whose vendor lead times force early procurement release decisions. The map `conduit_labor_factors` holds one multiplier per conduit run type and is the mechanism by which the same assembly costs different craft hours depending on how it is run.

Craft hours for an extracted line are computed combinatorially at extraction time, and are recomputed on read of the takeoff lines for a version. The line's per-unit shop content is the assembly's `prefab_hours_per_unit` when the line's `conduit_run_type_code` is one of the assembly's `ideal_conduit_type_codes`, and is otherwise the assembly's `prefab_hours_per_unit` multiplied by a supported derate factor of 1.0 — that factor is one, so the supported case and the ideal case currently produce the same per-unit content, but the derate is a distinct multiplicative step and must be applied as one. The base hours for the line are that per-unit value multiplied by the line's `quantity`. The base is then multiplied by the run factor the assembly's `conduit_labor_factors` map holds for the line's `conduit_run_type`, and by a chain penalty: 1.2 when the line is consumed by a component whose `chain_mode` is `CHAIN_DEPENDENT`, and 1.0 when it is consumed by a `PARALLEL_FABRICATION` component or is not yet consumed at all. Conduit craft hours are stated to two decimal places, rounded half up, with each per-unit value rounded before it is multiplied by the quantity and the product rounded again per line. Lines that have been marked superseded contribute zero craft hours, because their content was re-taken against the successor model version.

A second, tiered view of the same labor — conduit run impact — applies a depth multiplier on top. The run factor is read from the assembly's `conduit_labor_factors` for the line's `conduit_run_type`, exactly as above. The depth multiplier is taken from a three-row ladder whose first matching row wins: run depths of at most 1 take a multiplier of 1.0, run depths of at most 3 take 1.15, and anything deeper takes 1.35. The billed hours for the line are its `quantity` multiplied by the assembly's `prefab_hours_per_unit`, multiplied by the run factor, multiplied by the depth multiplier, stated to two decimal places rounded half up with the depth multiplier applied before the per-line rounding. For a line that has been superseded the billed hours are exactly zero, and the value is accounted for elsewhere: `tied_shipment_hours` becomes the sum of the crafted hours of the superseded line's components that are already `SET`, and `shipment_tied_flag` is true precisely when `tied_shipment_hours` is greater than zero.

Racks are laid out inside a version before work packages are taken off it. A rack belongs to a `model_version_id` and carries a `rack_code` unique within that version, the install `zone_code` it serves, its top-of-rack elevation in feet as `top_elevation_ft`, a `rack_hoist_date` from which its hoisting reservation window starts, and the maximum cubic feet of rack structure and support material it may carry in `value_capacity_cf`. Two behavior flags matter downstream: `direct_assignment` is true when a move-back request may be assigned straight to this rack without a preceding hold, and `ordering_strength_rule` — either `HOLD_WINDOW` or `RELEASE_WINDOW` — decides how the rack's reservation window extends. The rack's derived occupancy is `reserved_streams_and_phase_cf`, the aggregate occupancy described in §2.11: it is the sum of `quantity` across components bound to the rack whose `install_status` is `PLANNED`, `FABRICATED`, `LOADED`, `REWORK` or `SCRAPPED`, and it must stay at or below 95 percent of `value_capacity_cf`, with equality passing. A rack that would exceed that mark on a component creation or a scrapping resolution is refused with `ERR_RACK_CAPACITY_EXCEEDED` (HTTP 409). The value is stated to four decimal places, rounded half up, and is re-derived after every rework-job transition and every component install-status change.

### 3.2. The Jobsite, Its Energization Anchor and the Five-Tier Posture Ladder

A job is registered once, before any work package exists, and the registration record is the anchor for every date in the system. The `project_code` is the contractor's job number and is unique across all projects; `project_name` is the jobsite name; `jurisdiction_key` names the labor agreement that governs the site and is the key that joins to the rate rows described in §3.5. Most importantly, `power_on_iso` is the energization date, and it is the literal anchor for every lead-time and hoisting derivation in this document — no derived value ever feeds back into it. The registration also fixes the site's physical and policy constraints: `laydown_slots` is the number of laydown yard slots, each non-terminal work package holding one; `safety_program_required` is true when the site operates a written safety program and gates the safety certification rules; `material_gate_commodities` is the array of commodities whose procurement releases gate this project's shop releases, so that an order whose gate commodity has not yet been declared cannot be released; `shop_utilization_pct` is the shop load stated as a fraction of capacity and drives the capacity ladder used in hoisting derivation; `total_quantity` is the total engineered quantity for the project and `released_quantity` is the cumulative quantity already released to procurement, starting at zero; `float_band_low_pct` is the low edge of the schedule float band, below which the recovery multiplier is preferred, and `achieved_flow_margin_pct` is the achieved flow margin credited against that low edge.

Two further registration fields exist for completeness of the schedule record but do not participate in any derivation defined here: `cumulative_narrative_count`, a running count of narrative counts of record which excludes insignificant documents and starts at zero, and `insignificant_narrative_count`, the count of documents of record that are insignificant and therefore excluded from the cumulative count, also starting at zero. The `credit_policy` input selects which of the two crew-day credit variants the field-credit computation uses; it is either `FIRST_ACCEPTED` or `HIGHEST_TOTAL`, and when omitted it defaults to `FIRST_ACCEPTED`. Its effect is described in §3.6. Registration also carries the project's planned contract value for reference purposes in `planned_value_cents`, a recorded figure that no derivation defined in this document consumes.

The project's posture is the single derived value the rest of the system keys off, and it is computed by a five-tier ladder over schedule slippage. Slippage starts from the project's critical path. The critical path span is the sum of `planned_duration_days` over the project's trade activities whose status is not `COMPLETE`. The critical path shortfall is the sum, over those same activities, of the number of whole days by which the logical clock has passed the activity's planned finish — that is, the logical clock instant minus the activity's `planned_start_iso` minus its `planned_duration_days`, evaluated in days and floored at zero so an on-time or early activity contributes nothing. The `slippage_pct` is the absolute value of the shortfall divided by the span, stated to four decimal places rounded half up; when the span is zero — a project with no non-`COMPLETE` activity, or none at all — `slippage_pct` is exactly zero and the posture is `ON_TRACK`. Activities in status `COMPLETE` are excluded from both the span and the shortfall, so completing work shortens the span as well as removing itself from the shortfall.

The ladder is then walked descending, and each tier uses a less-than-or-equal test, so a value exactly on a boundary belongs to the lower tier. When `slippage_pct` is at most `SLIP_RELEASE_AT` the posture is `ON_TRACK`. When it is at most `SLIP_RECOVERY_AT` the posture is `RELEASE_PENDING`. When it is at most `SLIP_HOLD_AT` the posture is `RECOVERY_MODE`. When it is at most `SLIP_FREEZE_AT` the posture is `HOLD`. Otherwise the posture is `FROZEN`. The thresholds are supplied per project as the `posture_thresholds` object keyed by `SLIP_RELEASE_AT`, `SLIP_RECOVERY_AT`, `SLIP_HOLD_AT` and `SLIP_FREEZE_AT`; their canonical values are two percent, five percent, ten percent and fifteen percent respectively, evaluated in that descending order. The ladder may never be waived: it may not be unset or relaxed below `SLIP_FREEZE_AT` for a project whose `shop_utilization_pct` is at or above 0.85, so a highly loaded shop always retains its freeze tier.

Recomputing posture is an administrative act that also propagates. A posture recompute against a project whose `slippage_pct` is at most `SLIP_RELEASE_AT` and whose `shop_utilization_pct` is below 1.00 keeps the project at `ON_TRACK`. Every recompute re-derives `project_posture` through the ladder above and also recomputes `apprentice_breach_flag` — true exactly when at least one compliance-ledger row of the project carries `excess_apprentice_hours` greater than zero — and `fabricated_revision_active`, which is true while the project has a revision that affects fabricated content and has not reached any of the terminal members `APPROVED`, `REJECTED` or `SUPERSEDED`.

Each landing tier carries its own propagation to the project's work packages. A recompute that lands the project at `RELEASE_PENDING` recomputes `releasable_status` on every non-terminal work package of the project; for each such package whose `rework_order_count` is greater than zero the recomputation writes `ENGINEERING_HOLD`; and `fabrication_locked` is then recomputed from the resulting gate values. Landing at `RECOVERY_MODE` recomputes `craft_hours_credit` on every non-terminal work package, adds overtime hours to the crew rows of the next work front — appending to each affected ledger row's `overtime_hours` — re-derives `apprentice_hours`, `journeyman_hours` and `excess_apprentice_hours` on every affected compliance-ledger row with overtime counted at 1.5 for apprentices and 1.0 for journeymen, and drives `DISALLOWED` the status of any trade activity whose crew carries excess apprentice hours. Landing at `HOLD` recomputes hoisting windows for the non-terminal work packages, re-derives each affected package's `releasable_status` with the release gate closed on packages whose windows shifted, and recomputes `fabrication_locked`. Landing at `FROZEN` forces `releasable_status` to `ENGINEERING_HOLD` on every non-terminal work package, suppresses the rack binding of every `PLANNED` component of those packages so that each contributes zero to `pipeline_value_cents`, and re-derives `material_release_timing` for every material release of the project; no new release may be declared while the project is `FROZEN`.

Recovering from a worse tier is symmetric. Moving from `RELEASE_PENDING` back to `ON_TRACK` (when slippage falls to at most `SLIP_RELEASE_AT`) recomputes `releasable_status` on every non-terminal work package — an engineering hold is still applied wherever `rework_order_count` is greater than zero — and recomputes `fabrication_locked`. Moving from `RECOVERY_MODE` back to `RELEASE_PENDING` (slippage at most `SLIP_RECOVERY_AT` but above `SLIP_RELEASE_AT`) recomputes `releasable_status` on every non-terminal work package. Moving from `HOLD` back to `RECOVERY_MODE` (slippage at most `SLIP_HOLD_AT` but above `SLIP_RECOVERY_AT`) recomputes hoisting windows for the non-terminal work packages. Moving from `FROZEN` back to `RECOVERY_MODE` requires the same slippage band plus one further condition — the project must have no work package whose `shipment_status` is `IN_TRANSIT` or `LOCKED` — after which `releasable_status` and the hoisting windows are recomputed for the non-terminal packages. Each of these moves is a full posture recompute, so `apprentice_breach_flag` and `fabricated_revision_active` are re-derived alongside them.

The project also carries a second, independent state dimension for the external coordination gate, `delivery_gate`, whose initial value is `OPEN`. The gate closes by system event rather than by a caller: when a dependency band gate result for an external trade becomes blocked, and the project has a trade activity whose `activity_kind` is one of `MECHANICAL_ROUGH`, `PLUMBING_ROUGH`, `SPRINKLER_MAIN` or `DRYWALL_CLOSEOUT` in a status among `PLANNED`, `PERMITTED`, `ACTIVE` or `DISALLOWED`, the gate moves to `BLOCKED`; `external_gate_open` is then recomputed to false, `releasable_status` is recomputed on every non-terminal work package and `fabrication_locked` is recomputed. The gate reopens, again by system event, when the blocking external trade activity reaches `COMPLETE`, at which point `external_gate_open` is recomputed to true.

Beyond posture, the project exposes a set of derived rollups that other workflows maintain. `pipeline_value_cents` is the pipeline balance over components not yet set, `completed_value_cents` is the same balance over components whose install status is `SET`, `installed_pct` is the completed value divided by the sum of the two balances stated to four decimals rounded half up and is zero when that sum is zero, `man_hours_total` is the sum of crafted hours over every component of the project, `effective_flow_pct` is the installed work volume divided by the total work volume with the installed figure expressed as a whole percent before the division, `apprentice_ratio_max` is the project-wide apprentice ratio cap taken as the smaller of the jurisdiction cap and the next front band default, `approved_change_value_cents` is the sum of the negotiated change-order variant over the project's approved revisions, and `craft_hours_credit`, `craft_hours_balance` and `idle_capacity_cents` are the commercial rollups described in §3.8.

### 3.3. Work Packages, Their Three State Dimensions and the Release Gate

A work package is a body of prefabricated content taken off one coordinated model version and delivered to one zone on one deck at one time. Creating one requires the owning `project_id`, the `model_version_id` it was taken off, the distribution `stage_code` — `FIRST_STAGE`, `SECOND_STAGE` or `TRIM_OUT` — the install `zone_code`, the `transport_kind` (either `FLATBED` or `MIXED_LOAD`, which drives travel and unload days applied to the delivery deadline), the `hoisting_window_id` the package is booked against, the just-in-time arrival deadline `required_on_site_iso`, the earliest it may be spotted on the deck `installation_window_start_iso`, the number of units in the package `fabricate_quantity`, and the shop-load basis `shop_utilisation_basis_pct` recorded when the order was taken, which is snapshotted at release. Creation is refused, with no row written and `ERR_ENGINEERING_HOLD_ACTIVE` returned, when the project already carries a revision that names an artifact of the package's assemblies.

A work package has three independent state dimensions, and they progress separately. The shop dimension is `fabricate_status`, starting at `PLANNED` and moving through `RELEASED`, `IN_FABRICATION` and `FABRICATED` to the terminal `CANCELLED`. The delivery dimension is `deliver_status`, starting at `AWAITING` and moving through `STAGED`, `LOADED`, `IN_TRANSIT`, back to `LOADED` on loss recovery, to the terminal `DELIVERED`. The transport-booking dimension is `shipment_status`, starting at `PENDING` and moving through `RESERVED`, `STAGED`, `LOADED`, `IN_TRANSIT` to the terminal members `DELIVERED` and `LOST`, with `LOCKED` available as the held condition. All three dimensions are independent: advancing the delivery dimension does not advance the shop dimension, and each transition names only its own dimension's target.

Whether a package is releasable is a derived value, `releasable_status`, recomputed rather than set. Its precedence is fixed. An engineering hold wins: `ENGINEERING_HOLD` is written when the project's `fabricated_revision_active` is true and a revision names an artifact of this package's assembly set, or when the package's own `rework_order_count` is greater than zero. Absent that, a material hold is second: `MATERIAL_HOLD` is written when a member of the project's `material_gate_commodities` has no procurement release in the declared-for-procurement state. Absent both, the posture-dependent values apply: `PERMITTED` is written when the posture is `RELEASE_PENDING`, `ALLOWED` when the posture is `ON_TRACK` and every gate passes, and `READY` otherwise. The five members are `ENGINEERING_HOLD`, `MATERIAL_HOLD`, `READY`, `PERMITTED` and `ALLOWED`, and a release is accepted for any of the last three.

Releasing a package to the shop is the ProjectManager's decision, and it is the point at which most of the package's derived dates are fixed. The request carries `expected_prefab_order_version` and is subject to the staleness rule of §2.6. The package must be in `PLANNED` on the shop dimension, must carry a `releasable_status` among `READY`, `PERMITTED` and `ALLOWED`, and the project's posture must be `ON_TRACK`, `RELEASE_PENDING` or `RECOVERY_MODE` — `HOLD` and `FROZEN` both block release. Three further guards apply: the derived window's start must not already be before the logical clock at the release instant, or the release fails with `ERR_FABRICATION_WINDOW_LAPSED` (HTTP 409); the package's hoisting window must not already have been frozen by a prior release-to-shop record, or the release fails with `ERR_WINDOW_ALREADY_FROZEN` (HTTP 409), because the window is derived exactly once; and an engineering hold or a material hold on the package fails the release with `ERR_ENGINEERING_HOLD_ACTIVE` or `ERR_MATERIAL_HOLD_ACTIVE` respectively, with the engineering hold firing first as set out in §2.8. The hoisting-window conflict test and the laydown-slot test of §2.11 also apply here.

A successful release does a great deal at once. The package's `fabricate_status` becomes `RELEASED` and its version increments by one. `release_to_shop_iso` is stamped from the logical clock, and it becomes the baseline for rework and revision crediting. `laydown_slot_index` is assigned as the lowest free slot index between 1 and the project's `laydown_slots`, chosen by ascending release instant with ties broken by ascending id. The hoisting window is derived and then frozen: `hoisting_duration_days`, `hoisting_start_iso` and `hoisting_end_iso` are written and thereafter immutable while the package stays at `RELEASED` or later. `fabrication_utilisation_pct` is recomputed. `material_release_timing` is recomputed for every procurement release whose commodity appears in this package's components, and `locked_release_iso` is frozen on those releases. Finally the owning project's pipeline balance is recomputed.

The hoisting window derivation is worth stating in full, because it is the derivation the whole delivery schedule hangs on. For the package's `stage_code`, a fixed stage window supplies a clash-slot count and a trade count: `FIRST_STAGE` carries four clash slots and two trades, `SECOND_STAGE` carries three clash slots and one trade, and `TRIM_OUT` carries two clash slots and no trades. A chain depth is then counted as the number of the package's components that name a `predecessor_component_id` whose predecessor's `install_status` is not `SET`. A productivity penalty of zero applies when the project's `installed_pct` is at least 0.40, and one otherwise — the threshold is the install productivity floor. A capacity multiplier is taken from a three-row shop capacity ladder by first matching row: a multiplier of 1.0 when `shop_utilization_pct` is at most 0.85, 1.2 when it is at most 1.00, and 1.5 for any higher load. The base day count is the sum of the clash slots, the trade count, the chain depth and the productivity penalty, multiplied by that capacity multiplier and rounded up to a whole number of days. The length `hoisting_duration_days` is that base clamped to the inclusive range from 1 to 10 days. The window's start `hoisting_start_iso` is the project's `power_on_iso` shifted earlier by the base day count plus the package's `assembly_count` multiplied by a rack staging duration factor of 3 and rounded up to whole days; the window's end `hoisting_end_iso` is the start shifted later by `hoisting_duration_days`. Every term is rounded up to whole days before the capacity multiplier is applied, and the window is derived only for packages whose `fabricate_status` is one of `PLANNED`, `RELEASED`, `IN_FABRICATION` or `FABRICATED`. The chain depth counts only components whose predecessor is not yet `SET`, so setting predecessor content shortens later windows.

A released package is advanced through the shop by the ShopForeman. Moving `RELEASED` to `IN_FABRICATION` requires the package to be in `RELEASED`, after which every component of the package whose consuming commodity release is declared is marked available for fabrication in the shop queue. Moving `IN_FABRICATION` to `FABRICATED` requires the package to be in `IN_FABRICATION` and to carry at least one component — `assembly_count` greater than zero — and on entry `crafted_hours_credit` is recomputed for the package's released components and the project's pipeline balance is recomputed. Both steps set the package's `fabricate_status`.

Reversal of a release is allowed only before anything has shipped. Reverting a `FABRICATED` package back to `PLANNED` requires `deliver_status` to be `AWAITING`, and it releases the laydown slot back to the free pool, clears `hoisting_start_iso`, `hoisting_end_iso` and `release_to_shop_iso` to null, reverts every component of the package whose `install_status` is `FABRICATED` back to `PLANNED`, recomputes those components' `crafted_hours_credit` to zero, and recomputes `pipeline_value_cents` through the pipeline balance. The compensating invariant is that the project's `craft_hours_balance` is unchanged by this revert, because the credit is re-credited to the pipeline balance. A package can also be cancelled outright, but only from `PLANNED` on the shop dimension with `deliver_status` still `AWAITING`; cancellation moves it to the terminal `CANCELLED`, clears `rack_id` on every component whose install status is `PLANNED` or `FABRICATED` and sets those components to `SCRAPPED`, recomputes `reserved_streams_and_phase_cf` for every affected rack, and recomputes the project's pipeline value.

The delivery dimension belongs to the LogisticsCoordinator. Staging requires the package to be `FABRICATED` on the shop dimension and moves `deliver_status` from `AWAITING` to `STAGED`. Loading requires `deliver_status` `STAGED`, a `shipment_status` among `PENDING`, `RESERVED` or `STAGED`, and the package's `required_on_site_iso` to fall inside its frozen hoisting window; success moves `deliver_status` and `shipment_status` both to `LOADED`, cascades every `FABRICATED` component of the package to `LOADED`, recomputes those components' `prefab_value_cents`, and recomputes the project's pipeline value, `installed_pct` and posture. Unloading a `LOADED` package reverses all of it: `deliver_status` returns to `AWAITING` and `shipment_status` to `STAGED`, the package's `LOADED` components revert to `FABRICATED`, the pipeline balance is recomputed, and — the compensating invariant — `craft_hours_balance` is unchanged by the load-then-unload cycle.

Dispatch is either an explicit move or a system event on the required dispatch date. Moving `LOADED` to `IN_TRANSIT` requires `deliver_status` `LOADED` and the logical clock to be at or after the package's `planned_delivery_iso`; the move sets `deliver_status` and `shipment_status` both to `IN_TRANSIT`. Delivery requires `deliver_status` `IN_TRANSIT` and sets both to `DELIVERED`; on delivery the package's `fabricate_quantity` is decremented by the delivered quantity and the package is marked deleted from the shop queue, the released allocation is restated through the project's `installed_pct`, `completed_value_cents` is recomputed through the pipeline balance, and the posture is recomputed through the ladder. Loss recovery covers the case where a shipment goes missing: from `IN_TRANSIT` with `shipment_status` `LOST`, the package returns to `LOADED` — clearing the loss so the content can be re-shipped — with `rework_order_count` recomputed and a re-shipping rework job opened for the lost content, the pipeline value recomputed and the posture recomputed.

The package's remaining derived fields tie the schedule to the money. `planned_delivery_iso` is the `required_on_site_iso` moved earlier by the vendor lead time, the travel time and the unload time in days, using the travel and unload lags of the commodity's appliance profile described in §3.9. `rework_order_count` is the number of rework jobs whose `prefab_component_id` belongs to this package, and it is the field the release gate reads. `assembly_count` is the number of the package's components, and `crafted_hours_total` is the sum of their crafted hours. `crafted_hours_credit` is the release-weighted share of that total credited before the release instant. `rework_hours` is the hours charged to shop rework, reset at the release instant. `fabrication_utilisation_pct` is zero when the package's material release has not been declared and is otherwise equal to the `shop_utilisation_basis_pct` snapshotted at release. `hoisting_start_iso`, `hoisting_end_iso` and `release_to_shop_iso` are computed rather than supplied, and the first two are frozen once the package is released.

### 3.4. Fabricated Components, Chain Dependencies and Field Installation

Components are the discrete units a work package is actually built from, and they are created by the ShopForeman against a package. A component names its owning package in `prefab_order_id`, the rack it will be installed on in `rack_id`, the extracted line it satisfies in `takeoff_line_id`, the component that gates it in `predecessor_component_id`, its assembly identity in `assembly_code`, its `quantity` in the assembly's unit of measure, and two chain fields: `chain_mode`, either `CHAIN_DEPENDENT` or `PARALLEL_FABRICATION`, and `chain_dependency_link`, the business key of the chain dependency it participates in. A newly created component starts at `PLANNED` on its install dimension, and its creation computes `crafted_hours` as its `quantity` multiplied by the assembly's `prefab_hours_per_unit` — the minimum achievable craft content for that component — and re-runs the rack capacity check on the bound rack.

The install dimension is a single state machine over `install_status` with members `PLANNED`, `FABRICATED`, `LOADED`, `SET`, `REWORK` and `SCRAPPED`, starting at `PLANNED` and terminating at `SET`. A component is fabricated by the ShopForeman, which requires the owning package to be in `IN_FABRICATION` on the shop dimension, the owning package's `releasable_status` not to be `ENGINEERING_HOLD`, and the chain to be satisfied: either the component names no predecessor at all, or the predecessor's `install_status` is `SET`, or the component's own `chain_mode` is `PARALLEL_FABRICATION`. On success the component becomes `FABRICATED`, `crafted_hours_credit` is recomputed for it, and the project's pipeline balance is recomputed.

Loading is not a component-driven action but a consequence of the package: when the owning package's `deliver_status` becomes `LOADED`, each of its `FABRICATED` components becomes `LOADED`, provided the component's rack capacity check still passes at load time; `contractual_credit_cents` — the credited value of the component including its `core_charge_cents` and any recycled credit earned against `recycled_credit_cents` — is recomputed, and the project's pipeline balance is recomputed. Setting a component in the field is the InstallForeman's action, and it requires the component to be `LOADED`, the project's posture not to be `FROZEN`, and the component's zone to have no pending disallowed predecessor activity under the written installation sequence agreement described in §3.5. Setting the component moves it to the terminal `SET`, recomputes `completed_value_cents` through the pipeline balance, recomputes `effective_flow_pct` and `installed_pct`, and recomputes the posture through the ladder. The field credit balance is unchanged by this transition, because credited hours are a labor measure rather than a value measure.

A component's value is expressed in three related fields. `crafted_hours` is its `quantity` multiplied by the assembly's `prefab_hours_per_unit`. `prefab_value_cents` is its crafted hours multiplied by the journeyman hourly rate for the project's jurisdiction and by one plus that rate's burden fraction. `contractual_credit_cents` is the credited value including core and recycled credits as described above.

Two of the six install members are reachable through rework rather than through the normal progression, and both are described with the revision workflow in §3.7: a `FABRICATED` component whose assembly is named by an approved revision moves to `REWORK`, and a component in `REWORK` may be scrapped to `SCRAPPED`, which returns its rack capacity and removes it from the pipeline balance.

### 3.5. Trade Activities, the Installation Sequence Agreement and Crew Days

Coordination with other trades is expressed as a written installation sequence agreement, and it is modelled as a set of trade activities. Each activity names its `project_id`, a `trade_key` identifying the trade — electrical activities use the trade key `ELECTRICAL` — an `activity_kind` from `ELECTRICAL_INSTALL`, `MECHANICAL_ROUGH`, `PLUMBING_ROUGH`, `SPRINKLER_MAIN` or `DRYWALL_CLOSEOUT`, the `work_front_code` it occupies, the `bay_code` or corridor within that work front, its `planned_start_iso` and `planned_duration_days`, and its `written_sequence_index` in the agreement, which is monotonically increasing. Activities also carry their pricing row in `rate_id`, the revision whose rework produced them in `revision_id` (null for originally planned activities), and the activity whose permit unblocks them in `permit_id`, which is a reference to another activity and forms the installation-sequence chain between activities. Registration starts an activity at `PLANNED` and recomputes the owning project's posture.

The activity state machine runs `PLANNED` to `PERMITTED`, `PERMITTED` to `ACTIVE`, `ACTIVE` to `COMPLETE` as its terminal member, and — across the ratio dimension described in §3.6 — `ACTIVE` to `DISALLOWED` and back. Admission to `PERMITTED` requires that the activity's permitting activity is either unspecified or itself `COMPLETE`, and additionally that no lower-indexed activity of another trade blocks the bay: no activity with a lower `written_sequence_index`, the same `work_front_code` and a non-overlapping `bay_code` may hold a status among `PLANNED`, `PERMITTED`, `ACTIVE` or `DISALLOWED` while carrying an `activity_kind` among `MECHANICAL_ROUGH`, `PLUMBING_ROUGH`, `SPRINKLER_MAIN` or `DRYWALL_CLOSEOUT`. A blocked request is refused with `ERR_INSTALL_SEQUENCE_VIOLATION` (HTTP 409). The same rule guards activity registration and component field installation, so a component cannot be set in a zone whose bay is still held by another trade.

Moving an activity to `ACTIVE` requires it to be `PERMITTED` and requires every crew member dispatched to it to hold a `home_jurisdiction_key` equal to the project's `jurisdiction_key`. On entry, `actual_start_iso` is stamped from the logical clock and the activity's `craft_hours_credit` — its pro-rated field credit for the work front — is recomputed. An activity advances, suspends or completes by having its `status` set; when an activity carries rework produced by a design revision, its `rework_trade_value_cents` holds the rework value computed for it under the memo variant of the revision cost impact described in §3.7. An activity reaches its terminal `COMPLETE` only when it is `ACTIVE` and no crew member assigned to it carries `excess_apprentice_hours` greater than zero. Completion recomputes the project's productivity actuals, then recomputes `slippage_pct`, the critical span and the shortfall without this activity's duration, and finally recomputes the posture through the ladder — so finishing an activity can improve the project's tier.

The suspension branch is driven by the ratio rule rather than by a caller's preference. An `ACTIVE` activity moves to `DISALLOWED` when at least one crew member on it carries a compliance-ledger row with `excess_apprentice_hours` greater than zero; the activity's `suspension_reason` is stamped with the apprenticeship ratio breach, the owning project's `apprentice_breach_flag` is recomputed to true, and the posture is recomputed through the ladder. The activity resumes when every crew member assigned to it has `excess_apprentice_hours` equal to zero — which happens when later crew-day acknowledgments bring the ratio back inside the cap — at which point the activity returns to `ACTIVE`, its `suspension_reason` is cleared to null, and the project's `apprentice_breach_flag` and posture are recomputed. A disallowed activity contributes its duration to the critical path span and its overdue days to the shortfall exactly as a planned one does.

A crew day is a foreman's report of one worker's day on one activity, and it is the input to every labor computation in the system. It names its `project_id`, the `worker_id` whose day is reported, the reporting `foreman_id`, the `trade_activity_id` worked on, and the `work_date_iso`, which is unique per worker and project. It carries `regular_hours` in straight-time quarter-hour increments and `overtime_hours`, a submission order in `report_sequence`, and an `acknowledge_mode` of either `RELEASE` or `FINAL`, which is required on every creation. Creation also derives two classification-dependent fields: `apprentice_hours` is the regular hours plus one and a half times the overtime hours when the worker is an apprentice and zero otherwise, and `journeyman_hours` is the regular hours plus the overtime hours when the worker is a journeyman, foreman or general foreman and zero otherwise. Registration applies the project's credit policy to the day's candidate reports, as described in §3.6.

Worker registration itself is guarded on two points that the crew-day path repeats. A worker's `qualification_state_code` may be at most 40 characters and is rejected with `ERR_SHIFT_BAND_TOO_LONG` (HTTP 422) if longer. A worker's `apprentice_period` must be a member of the range 1 to 5 exactly when the worker's `classification` is `APPRENTICE`, and must be null for every other classification; a violation is refused with `ERR_APPRENTICE_PERIOD_INVALID` (HTTP 422). Both worker registration and crew-day reporting enforce a jurisdiction dispatch rule as well: every worker dispatched to the project's next work front must hold a `home_jurisdiction_key` equal to the project's `jurisdiction_key` and an `apprentice_period` inside the band recorded for that worker, with an unknown band refused with `ERR_JURISDICTION_DISPATCH_BAND` (HTTP 422).

The registration record for a worker carries the identifying and measurement fields the roster summary reports. `worker_code` is the worker's badge number and is unique; `full_name` is the worker's name; `classification` is the labor classification that drives jurisdiction rates; and `home_jurisdiction_key` is the jurisdiction the worker is dispatched from. A worker also supplies two certified-progress figures and one verification pair: `percent_complete_certified` is the certified percent complete for the worker's own release, `percent_complete_verified` is the verified percent complete for recipients that view the worker's release, `safety_verified_status` is the safety verification outcome and is `VERIFIED`, `UNVERIFIED` or `EXPIRED`, defaulting to `UNVERIFIED`, and `safety_verification_code` is the code shown when the worker's own safety verification is inspected, which is only accepted once a second fact has been supplied alongside it. One field is derived rather than supplied: `shift_band_delta`, the worker's shift band delta, is set from the `qualification_state_code` by the release-gate derivation and defaults to 0. Registration also stamps the worker's safety verification expiry as the logical clock instant plus 90 days and initializes `journey_ring_claim_hours` to 0.

While the crew-day row is created by the GeneralForeman as a report, it is not credited until it is acknowledged. Acknowledging a report carries `expected_crew_day_version` and `acknowledge_mode` and is subject to the staleness rule of §2.6: if another writer has already acknowledged that same report, the acknowledgment is refused with `ERR_STALE_VERSION` (HTTP 412). A successful acknowledgment re-applies the credit policy for the day, re-prices the row through the gross payroll reconciliation of §3.6, re-resolves the ratio limits, recomputes the compliance-ledger row's `apprentice_hours`, `journeyman_hours`, `excess_apprentice_hours` and `adjustment_delta_hours` from the activity's non-voided crew-day rows, and re-derives those same activity totals on every other compliance-ledger row of that activity, increments the crew-day version by one, and cascades: an activity whose crew now carries excess apprentice hours moves to `DISALLOWED`, and the project's productivity actuals are recomputed. The row's `guilt_added` flag marks the single acknowledged row whose credited hours count toward the field credit ledger, and `adjusted_value_cents` — the row re-priced at the guilt-added rate — may differ from `labor_cost_cents` on the identical row.

### 3.6. Labor Agreement Rates, the Apprentice Ratio Cap and Payroll

Jurisdiction compliance is grounded in a rate table that a `PlatformAdmin` maintains. A rate row names the `jurisdiction_key` the agreement belongs to, the `classification` it covers — `APPRENTICE`, `JOURNEYMAN`, `FOREMAN` or `GENERAL_FOREMAN` — and, for apprentice rows only, the `apprentice_period` between 1 and 5 that the rate applies to. It carries the straight-time `hourly_rate_cents`, the payroll `burden_pct` applied on top of that rate, a first agreement cap in `apprentice_ratio_max`, a second valid cap in `wait_ratio_max`, and the `effective_from_iso` date the row takes effect. Registering a rate row re-evaluates the ratio limits for every project in that jurisdiction, because a new agreement can change the cap a site is working under.

The cap a piece of work is governed by resolves in two steps. First the governing row is found: the latest rate row for the project's `jurisdiction_key` whose `effective_from_iso` is at or before the crew day's `work_date_iso`, ordered by effective date descending with ties broken by creation time ascending, so a row that takes effect later never governs earlier work. When such a row exists, `ratio_limit` is that row's `apprentice_ratio_max` and `wait_ratio_limit` is that row's `wait_ratio_max`. When no row governs the date, both limits fall back to tier defaults keyed by the apprentice's ring band: for apprentices in periods 1 and 2 the default is 1.0, and for periods 3, 4 and 5 the default is 0.5 for both the apprentice ratio and the wait ratio. The project-wide cap `apprentice_ratio_max` is the smaller of the resolved `ratio_limit` and `wait_ratio_limit`, so the tighter of the two agreement constraints always wins. Both limits and the cap are stated to two decimal places, rounded half up.

The compliance ledger is where cumulative jurisdiction hours live, one row per project and worker and activity and rate row. A ledger row records its `jurisdiction_key`, the `classification` in force at the time of the work, its `regular_hours` and `overtime_hours`, the weighted average `pay_rate_cents` and `burden_pct` applied to it, and the `projected_ratio` the ledger expects after the pending crew change. Its cumulative hours are held in `apprentice_hours` — cumulative regular apprentice hours plus one and a half times the cumulative overtime apprentice hours on the activity — and `journeyman_hours` — cumulative journeyman and foreman hours with overtime counted at 1.0. Those two totals belong to the activity rather than to the single worker the row names: they are summed over every crew-day row booked to that project and activity, whichever worker reported it, so each ledger row of an activity carries the same cumulative hours and a crew-day acknowledgment re-derives that activity's totals on all of its ledger rows together. Its `excess_apprentice_hours` is the apprentice hours carried in excess of the resolved `ratio_limit` multiplied by the journeyman hours, and that figure is what drives activity suspension. Its `adjustment_delta_hours` is the signed sum of the compliance corrections applied to the row, and the row carries a conservation requirement: the row's `apprentice_hours` must equal its original apprentice hours plus `adjustment_delta_hours` at all times. The original figure is the baseline the row opens with: a newly opened row is seeded with its `original_apprentice_hours` set to the apprentice hours it has just accumulated and an `adjustment_delta_hours` of zero, and each later recompute writes the signed difference between the current cumulative apprentice hours and that baseline, so the identity holds from the row's first computation onward. The row's money fields are `total_cents`, `ledger_credit_cents`, `certified_hours`, `gross_payroll_cents` and `adjusted_payroll_cents`, described below.

The apprentice ratio cap itself may never be waived. When a crew day is reported or acknowledged, or when a new rate row is registered, the apprentice hours implied by the project's non-voided crew-day rows are summed per project and per classification, and this row's apprentice hours are added to that sum; if the total would exceed the ratio limit multiplied by the project's journeyman hours, the request is refused with `ERR_APPRENTICE_RATIO_EXCEEDED` (HTTP 409). This guard is project-wide — every crew day of the project counts toward its totals, whatever activity it was reported against — and it is therefore a different total from the activity-scoped cumulative hours a compliance-ledger row carries. The rule guards crew-day reporting, crew-day acknowledgment and rate-row registration alike — a new agreement row that would render existing site staffing illegal is refused rather than silently accepted. There is no override parameter and no role that can bypass it.

Which of several reports for the same worker on the same day earns the field credit is decided by the project's `credit_policy`, and the mechanism is the field credit policy. The candidates are the crew-day rows for the same project, worker and work date with a `report_sequence` of at least 1 — so a report sequence of zero is not a candidate. When the policy is `FIRST_ACCEPTED`, the winning row is the one with the smallest `report_sequence`, ties broken by the earliest `created_at`. When the policy is `HIGHEST_TOTAL`, the winning row is the one with the largest sum of its regular hours plus one and a half times its overtime hours, ties broken by the smaller `report_sequence`. Exactly one row per project, worker and work date is marked `accepted_for_credit` true — the winner — and that row's `credited_hours` is its regular hours plus one and a half times its overtime hours; every non-winning row for that key has `credited_hours` of zero and `accepted_for_credit` false, and is retained rather than deleted. The amounts are stated to two decimal places, rounded half up. The two policies therefore disagree in a specific way: under `FIRST_ACCEPTED` the earliest report wins even when a later report claims more hours, whereas under `HIGHEST_TOTAL` a mid-day re-report with more hours flips the winner. The default policy is `FIRST_ACCEPTED`, and the same winning-report rule governs the field credit ledger and the productivity actuals.

Two payroll figures are produced for every crew day. The straight-time value `labor_cost_cents` is the sum of the crew day's regular hours plus one and a half times its overtime hours, multiplied by the hourly rate resolved for that crew day's own worker, multiplied by one plus that worker's burden fraction, stated in whole cents with round half up. The guilt-added value `adjusted_value_cents` applies the identical arithmetic but resolves the rate against the journeyman row of the project's jurisdiction instead of the worker's own row, which is why the two figures can differ on the identical row. The ledger row aggregates them by different scopes: `total_cents` is the sum of `labor_cost_cents` over the row's accepted crew days only, `gross_payroll_cents` is the same sum over all of the row's crew days including those not accepted for credit, and `adjusted_payroll_cents` is the sum of `adjusted_value_cents` over the row's crew days. Each crew day is rounded to whole cents before the sum, so per-day rounding never accumulates beyond the sum.

The upgrade projection is a read-time computation over the same ledger. A worker's `journey_ring_claim_hours` is the sum of `credited_hours` over the worker's crew days that are accepted for credit, stated to two decimal places rounded half up; rows not accepted for credit contribute nothing. `upgrade_eligible` is true precisely when the worker's `journey_ring_claim_hours` is greater than 8,000 hours — the hours required by the applicable contract — and a completed upgrade resets `journey_ring_claim_hours` to zero. The worker also carries `credited_field_hours`, the sum of `credited_hours` across the worker's accepted crew-day rows, and it is this figure rather than the ring hours that the field productivity measures consume.

### 3.7. Design Revisions, Their Rework Loop and Their Two Cost Memos

A design revision is how a change to the coordinated model reaches the shop and the field. The `ProjectManager` raises one against a model version, and the request is heavy because the revision record is also the pricing worksheet. It names the owning `project_id`, the `model_version_id` raised against, and the successor version the change produces in `revised_version_id`; it carries a `revision_kind` of `DESIGN_CHANGE`, `RFI_RESPONSE`, `CLASH_RESOLUTION` or `OWNER_DIRECTIVE`; and it lists the affected artifacts in `impact_keys`, each of which must resolve to a declared artifact — a takeoff line's `takeoff_hash`, a component code, or a rack's `rack_code`. The status starts at `DRAFT`, and the server assigns a sequential `revision_number` within the project.

The commercial fields are supplied with the revision and are what both cost variants are computed from. `maintenance_hours`, `buffer_before_hours` and `momentum_before_hours` describe the maintenance window the rework sits inside; `base_service_hours`, `paid_service_hours` and `billed_service_hours` describe the craft content of the affected scope and how much of it has already been paid and billed; `percent_complete_mode` selects which percent complete is reported and is either `FLOW` or `WEIGHT`, defaulting to `FLOW`; `label_percent_complete` is the percent complete printed on the physical label, and `label_codes` are the codes printed on that label, with `fabricated_content_codes` naming the subset that marks fabricated content. `shop_parts_value_cents` and `shop_parts_quantity` describe the shop-fabricated parts tied to the revision, and `revision_quantity` the quantity affected. `impact_qualified_hours` is the qualified hours found by the revision search, including lines already fabricated; `effort_hours` is the hours the revision consumed before the shop closed it. The two rates are `kludge_rate_per_hour_cents` — the expedited shop rate — and `negotiated_rate_per_hour_cents` — the agreed change-order rate — and `submitted_markup_pct` is the markup applied on the negotiated rate for direct costs. `direct_shop_cost_cents` is the direct shop cost the revision incurred before approval. `replacement_lifecycle_percent` and `prior_lifecycle_percent` describe the lifecycle of the replacement content and of the content being replaced, and `qualified_lifecycle_percent` is the lifecycle percent of the fabricated content produced as a byproduct of the revision, zero when there is none. `proposed_waiver` is true when a waiver request is submitted alongside the revision, and `label_percentage` is the percent printed on the label when the revision carries fabricated content, null when it does not.

Three verification gates are attached to the revision and default to their open values. `safety_gate_status` is the external safety review outcome and is `OPEN`, `BLOCKED`, `LOCKED` or `PASSED`, defaulting to `OPEN`. `label_verified_status` records verification of the revision label and is `VERIFIED` or `UNVERIFIED`, defaulting to `UNVERIFIED`. `safety_verified_status` records verification of the revision safety record, also `VERIFIED` or `UNVERIFIED`, defaulting to `UNVERIFIED`.

Submission is the step that puts the rest of the project on notice. A revision can be submitted only from `DRAFT`, only when its `revised_version_id` names a model version whose zone quantity total is at least 1, and only when every entry of its `impact_keys` resolves to a declared artifact of its affected kind; an entry that does not resolve is refused with `ERR_AFFECTED_REF_NOT_FOUND` (HTTP 404). An empty impact set is refused with `ERR_REVISION_IMPACT_REQUIRED` (HTTP 422) at both submission and approval. A revision whose `label_codes` contain a fabricated-content code but which carries no positive `label_percentage` is refused with `ERR_LABEL_CODE_MISSING` (HTTP 422), and a revision whose `replacement_lifecycle_percent` is below its `prior_lifecycle_percent` — a replacement younger than the content it replaces — is refused with `ERR_SERVICE_LIFECYCLE_INVALID` (HTTP 422). A revision targeting a model version that is already `SUPERSEDED`, or one that another approved revision already targets, is refused with `ERR_MODEL_SUPERSEDED` (HTTP 409). On success the revision becomes `SUBMITTED`, its `engineering_hold` is recomputed to true, and three cascades run: every material release consuming an affected assembly's commodity is set to `RESTRICTED`, `material_release_timing` is recomputed for those releases, and `releasable_status` is recomputed to `ENGINEERING_HOLD` on every work package holding an affected component. `engineering_hold` is true while the revision's status is not a member of the set `APPROVED`, `REJECTED`, `SUPERSEDED`.

Whether a revision affects fabricated content is derived rather than declared: `affects_fabricated_content` is true when the revision's label codes include one of its `fabricated_content_codes` and its label percentage is greater than zero.

Approval is the decision that supersedes the model version and queues the rework, and it carries `expected_model_version_version` and is subject to the staleness rule of §2.6. It requires the revision to be `SUBMITTED`, requires that no other approved revision already targets the same `model_version_id`, and requires the revision's safety gate not to be `BLOCKED` — a blocked safety gate can never be approved and is refused with `ERR_REVISION_SAFETY_BLOCKED` (HTTP 409). The revision's adjusted flow hours constrain the scope: the sum of `tied_shipment_hours` and `revised_trade_hours` may not exceed the revision's `adjusted_flow_hours`, and a scope that does is refused with `ERR_CRAFT_HOURS_EXCEEDED` (HTTP 409); that ceiling also guards the rework-job status path. On success the revision becomes `APPROVED`, its version increments by one, its `engineering_hold` is recomputed to false, and `approved_change_value_cents` is computed from the negotiated change-order variant described below. Four cascades then run: the target model version becomes `SUPERSEDED` and its version increments by one while its `coordinated_at_iso` is left unchanged because history is immutable; each naming impact is expanded to the components it reaches — a takeoff-hash impact reaches every component extracted against that line, a rack-code impact reaches every component bound to that rack, and a component-code impact reaches that component itself — and each component so reached is queued for rework: a `FABRICATED` one moves to `REWORK` and gets an open rework job, a `SCRAPPED` one gets a deferred job instead, and a component in any other install status keeps that status while an open rework job is created for it; the owning packages' `rework_order_count` and `releasable_status` are recomputed; and the project's posture is recomputed through the ladder.

A revision can also be refused. A `SUBMITTED` revision whose approval carries a written `resolution` is moved to `REJECTED` — the `resolution` field is required for a rejection — its `engineering_hold` is recomputed to false, every material release that this revision restricted returns to `RELEASED`, and for every work package holding an affected component `releasable_status` is recomputed under the §3.3 precedence rather than reset to a fixed value — on an `ON_TRACK` project the gate lifts to `ALLOWED`, not to `READY` — with any engineering hold that still applies continuing to win. The rejected revision is not dead: it can be re-drafted, returning it from `REJECTED` to `DRAFT` provided the re-draft carries a revised `impact_keys` array, at which point its `impact_values` are cleared and recomputed on the next submission. This is a genuine cycle — a revision may be re-drafted and resubmitted any number of times without a new revision row being created — and the same is true of the material release it restricted, which can be restricted again by a later revision.

The revision cost impact computation produces two values for each named impact, and the difference between them is deliberate. For every entry of `impact_keys` the revision is priced once, and an impact whose component has already been scrapped is still priced — its rework job is simply opened deferred rather than open. The engineering hours for the impact are the revision's `impact_qualified_hours` multiplied by its `revision_quantity` and divided by a revision scope divisor of four, stated to two decimal places rounded half up. The memo rework ceiling is then the smaller of those engineering hours multiplied by the kludge rate and the revision's `direct_shop_cost_cents`; it uses the kludge rate of 8,500 cents per hour, it is capped by `direct_shop_cost_cents`, it never adds markup and it is never rounded. The negotiated change-order value is the engineering hours multiplied by the negotiated rate of 7,800 cents per hour, multiplied by one plus the submitted markup fraction of 0.18, stated in whole cents rounded half up; it is not capped by `direct_shop_cost_cents`, so it can exceed the memo value. Both values are written per impact into `impact_values`, one entry per impact key, the memo value as `rework_value_cents` and the change-order value as `negotiated_value_cents`. The revision's own `approved_change_value_cents` is the sum of the negotiated values while the revision's status is `APPROVED`, and zero otherwise; the project's `approved_change_value_cents` is the sum of that figure over its approved revisions. The memo variant is what internal shop planning and the queued rework job use, and the negotiated variant is what is submitted to the owner — they legitimately disagree on the same engineering hours.

Rework is where the revision meets the shop. A work package's `rework_hours` are the affected quantity multiplied by the assembly's `prefab_hours_per_unit`; when the affected set is empty the figure is zero and no job row is created at all. A rework job names its `project_id`, the `prefab_component_id` sent back to the shop, the `revision_id` that created it, an `impact_key` that must be a member of that revision's `impact_keys`, a `reason_code` such as `DESIGN_REVISION`, and a question-and-option pair: `reason_question_code` is presented to the shop when the job is opened and `reason_option_code` is the option the shop selects, which must be admissible for the question asked. Two confirmation fields describe how the job is confirmed: `confirmation_mode` is the mode requested and is either `SHOP_CONFIRMATION` or `FIELD_CONFIRMATION`, while `confirmation_mode_effective` is the mode actually applied and may additionally carry the conversion or extension modes — `CONVERSION` or `EXTENSION` — when the applied mode differs from the one requested. `scheduled_start_iso` is the scheduled start date, and the job's status starts at `OPEN`.

The rework job state machine moves `OPEN` to `IN_PROGRESS` and then either to the terminal `CLOSED` or, on a scrapping resolution, to the terminal `RECUT_DEFERRED`. Entering `IN_PROGRESS` requires the job to be `OPEN` and requires its `reason_option_code` to be admissible for its `reason_question_code`. Closing from `IN_PROGRESS` requires the job to be `IN_PROGRESS` and its `rework_hours` to be greater than zero; on close the owning component returns to `FABRICATED` and the package's `rework_order_count` is recomputed. A job with zero rework hours closes straight from `OPEN` — the no-op job is retained for audit even though it changes nothing but the component's return to `FABRICATED`. A scrapping resolution sets the job's `status` to `RECUT_DEFERRED` and may carry its own `resolution` text; it sets the owning component to `SCRAPPED` and recomputes the rack capacity check for the owning rack. The cycle closes back on itself in the other direction too: a `CLOSED` job whose owning component is `FABRICATED` may be reopened by the ProjectManager, returning the job to `IN_PROGRESS`, returning the component to `REWORK`, and recomputing the owning package's `rework_order_count` and `releasable_status` — this is why a rework job and its component can oscillate, and why the package's release gate must be recomputed on every step of the loop.

A component awaiting rework holds the package back. When a `FABRICATED` component whose assembly is named by an impact of an approved revision moves to `REWORK`, the owning package's `rework_order_count` recomputes, its `releasable_status` recomputes — `ENGINEERING_HOLD` is written when the project posture is `ON_TRACK` or `RELEASE_PENDING` and `rework_order_count` is greater than zero — and the project's `fabrication_locked` and `fabricated_revision_active` are recomputed. The rework loop can also be entered explicitly rather than through an approval, by a shop return that creates the job directly and moves the component to `REWORK`.

Three further derived fields on the revision connect it to the delivery plan. `tied_shipment_hours` is the craft hours tied to the committed content of the superseded lines — that is, the components whose install status is `FABRICATED`, `LOADED` or `SET` — and `shipment_tied_flag` is true when any such content exists. `revised_trade_hours` is the craft hours implied for the revised scope. `equipment_value_delta_cents` is the revision's `shop_parts_value_cents` minus its `shop_parts_quantity` multiplied by the current shop parts basis. The revision also carries `required_actions`, the ordered action identifiers it requires, and the flow-hour fields `base_flow_hours`, `peak_multiplier` and `adjusted_flow_hours`, where `adjusted_flow_hours` is the flow hours after the peak multiplier and any shift-band delta, together with `excess_flow_hours`, which is `adjusted_flow_hours` minus the rework hours allowed inside the rework window.

### 3.8. The Commercial Rollups the Contractor Watches

Four project-level figures turn the physical state of the job into money, and all four are recomputed rather than entered. They are what a project manager and a shop manager actually look at, and each has a precise definition that must survive re-derivation.

The pipeline and completion balances are computed together. For each component of the project, a job-scope blend factor of 1.0 is applied, and the component's `crafted_hours` is its `quantity` multiplied by its assembly's `prefab_hours_per_unit` and by that blend factor. The component's `prefab_value_cents` is those crafted hours multiplied by the hourly rate resolved for the project's jurisdiction at the `JOURNEYMAN` classification, multiplied by one plus that rate's burden fraction. The project's `pipeline_value_cents` is the sum of `prefab_value_cents` over the components whose install status is `PLANNED`, `FABRICATED`, `LOADED` or `REWORK`; `completed_value_cents` is the same sum over the components whose install status is `SET`. Components whose install status is `SCRAPPED` are counted in neither balance, and a component whose order was cancelled contributes zero along with its rack assignment. The installed percentage is `completed_value_cents` divided by the sum of the two balances, stated to four decimal places rounded half up, and is exactly zero when that sum is zero. The man-hour total `man_hours_total` is the sum of `crafted_hours` over every component of the project, including scrapped ones. The effective flow percentage is the project's installed work volume divided by its total work volume, with the installed figure expressed as a whole percent before the division: the man-hour total is multiplied by a factor that is 11 when `installed_pct` is at least 0.40 and 16 otherwise, the product is rounded to a whole number, and that is divided by the man-hour total or by one, whichever is greater. The value balances are whole cents and the percentages are four decimals, both rounded half up.

Two distinct credit computations share the word "credit", and they are not the same figure. The craft-hours credit is a release credit and falls as the released quantity rises. The expected released hours are the project's `man_hours_total` multiplied by the ratio of `released_quantity` to `total_quantity` — a project whose total quantity is zero has expected released hours of zero. The discrete released hours are the sum of `crafted_hours` over the components released so far, and the shortfall is the expected figure minus the discrete figure, floored at zero. The project's `craft_hours_credit` is `man_hours_total` minus the expected released hours, floored at zero, so the credit decreases as the released quantity increases and never goes negative. An order's own `craft_hours_credit` is its `crafted_hours_total` multiplied by one minus whether the order has a non-null `release_to_shop_iso` — that is, an order that has been released carries no further release credit. Both figures are stated to two decimal places rounded half up. The two views disagree for identical data by exactly the shortfall: the pro-rated release credit measures the release against the project rollup, while the discrete credit measures it against the order's own component list and reports the shortfall separately. Component rows counted here are those whose install status is not `SCRAPPED`.

The craft-hours balance is a conserved quantity — money already committed to shop and field craft on this project — and it is defined so that a forward action paired with its compensating action leaves it unchanged. Its labor base is the project's `man_hours_total` multiplied by the journeyman hourly rate for the project's jurisdiction, rounded to whole cents. Its material base is the sum of `crafted_hours` over the project's components, multiplied by the same journeyman rate, rounded to whole cents. The released labor figure and the reinstated labor figure are each the project's `released_quantity` multiplied by that same journeyman rate and rounded to whole cents. The project's `craft_hours_balance` is the labor base plus the material base. Reverting a fabricated order moves the released labor figure out of the released balance and the reinstated figure back in, and because both are the same expression over the same released quantity the net movement is exactly zero. The scope of the balance is labor plus material, it is stated in whole cents rounded half up, and every term is rounded before the sum so the two compensating terms cancel exactly. Component rows whose install status is `SCRAPPED` are excluded, and `released_quantity` is read at the release instant and again at the revert instant.

Idle capacity prices the capacity the job is carrying but not using. A weight is taken from a three-row idle weight ladder by first matching row: a multiplier of 0.85 when `shop_utilization_pct` is at most 0.70, 0.75 when it is at most 0.85, and 0.60 for any higher load — so a busier shop carries a smaller idle-capacity write-off per hour. The project's `idle_capacity_cents` is its `man_hours_total` multiplied by the journeyman hourly rate for the project's jurisdiction, multiplied by that weight multiplier, multiplied by one minus the project's `installed_pct`, stated in whole cents rounded half up; a project with a man-hour total of zero has an idle-capacity figure of zero. This value is recomputed on every read of the project's summary and on every posture recompute.

Productivity actuals measure whether the prefabricated content actually saved field labor. Earned hours are the sum of `crafted_hours` over the project's components whose install status is `SET`. Actual hours are the sum of `credited_hours` over the project's crew days whose activity's status is `COMPLETE`. The productivity percentage is earned hours divided by actual hours, stated to four decimal places rounded half up, and is exactly zero when actual hours are zero. Only crew days accepted for credit participate — disallowed apprentice hours are already absent from the figure because such rows carry zero credited hours — and the figure is recomputed whenever an activity reaches `COMPLETE` or a crew day is acknowledged.

### 3.9. Procurement Releases, Lead Times and the Material Gate

Long-lead material is what forces a job's schedule to be decided early, and the procurement release is where that decision is recorded. A `ProcurementLead` creates a release naming its `project_id`, the `model_version_id` the quantities were taken from, the `vendor_key`, the `material_commodity` — one of `MC_CABLE`, `EMT_CONDUIT`, `RIGID_CONDUIT`, `STRUT`, `FITTINGS`, `SWITCHGEAR`, `WIRE` or `BOX` — the `quantity` in vendor units, the `unit_price_cents`, the vendor's quoted `lead_time_days`, the `service_priority` (either `SECOND_DAY` or `NEXT_DAY`), the `commitment_mode` (either `PLANNED` or `CONFIRMED`), the date it must be issued to the vendor `planned_release_iso`, and the operator who will acknowledge receipt `receiving_user_id`. A switchgear release is special: its quoted lead time must be at least 90 days, because switchgear is the commodity that drives the earliest release decisions on the job. A new release starts at `PLANNED` on its procurement dimension, and its timing is computed immediately, with the release gate recomputed on every work package that consumes the commodity.

The procurement dimension has five members: `PLANNED`, `RELEASED`, `SHIPPED`, `RECEIVED` and `RESTRICTED`, starting at `PLANNED` and terminating at `RECEIVED`. A release advances one step at a time. A release is declared to the vendor by a `ProcurementLead` carrying `expected_project_version` and a `target_status`, and the associativity rule of §2.6 applies — a project version that has advanced since the client last observed it fails the declaration with `ERR_STALE_VERSION` (HTTP 412). Declaring requires the release to be `PLANNED`, its `commitment_mode` to be either `PLANNED` or `CONFIRMED`, and the declare instant to be on or before its `planned_release_iso`; declaring after that date is refused with `ERR_MATERIAL_RELEASE_DEADLINE` (HTTP 409), and the rejected response exposes `num_days_late`, the number of whole days by which the clock has passed the planned release date floored at zero. On success the release becomes `RELEASED`, its `declared_for_procurement` flag recomputes to true, its timing is recomputed with `locked_release_iso` frozen when a shop release has already occurred, and two cascades run: `releasable_status` is recomputed on every work package holding a component of that commodity, and the project's `fabrication_locked` is recomputed.

Vendor shipment and receipt continue the same path. A release moves from `RELEASED` to `SHIPPED` when the vendor acknowledges shipment, and from `SHIPPED` to `RECEIVED` when the material is received, provided the receiving instant is strictly after the release's `locked_release_iso`. Receipt recomputes `releasable_status` on every work package holding a component of that commodity out of `MATERIAL_HOLD` and under the §3.3 precedence — `ALLOWED` on an `ON_TRACK` project, `PERMITTED` on a `RELEASE_PENDING` one, `READY` otherwise — recomputes the project's `fabrication_locked`, and leaves the released-quantity ledger `released_quantity` unchanged — the compensating invariant, because receipt moves quantity between pipeline buckets rather than into them.

A revision can restrict a release, and the restriction lifts when the revision is refused. Registering a revision whose named artifacts belong to an assembly whose components consume a release's commodity sets that release to `RESTRICTED` and stamps `restriction_since_iso`; its timing is recomputed. The release returns to `RELEASED` when the blocking revision reaches `REJECTED`, at which point `restriction_since_iso` is cleared to null. This is a cycle rather than a one-way door: a later revision can restrict the same release again, and a restricted-then-released release is a normal sequence on a job with repeated design changes.

The timing derivation is pinned so that the circular-looking dependency between release dates and shop release dates is well defined, and the evaluation order matters. First, the anchor is the project's literal `power_on_iso` and never a value derived from a planned release date. Second, `locked_release_iso` freezes at the earliest affected shop release. Third, the optimistic-concurrency field `expected_project_version` gates the declaration before any of this runs. With that order in place, the required-on-site date is the project's `power_on_iso` moved earlier by the travel days of the commodity's appliance profile — two days for `SWITCHGEAR` and one day for each of `MC_CABLE`, `EMT_CONDUIT`, `RIGID_CONDUIT`, `STRUT`, `FITTINGS`, `WIRE` and `BOX`. The planned delivery date is that required-on-site date moved earlier by the release's lead time plus the commodity's unload days — two unload days for `SWITCHGEAR` and one for each of the others. The planned release date is the planned delivery date moved earlier by a default shop turnaround of two days. The locked release date is the earlier of the planned release date and the earliest `release_to_shop_iso` among the project's work packages. Every offset is applied as a day shift and rounded up to a whole day. The row's `priced_hours` is its `quantity` multiplied by its `lead_time_days` and drives the release ladder. Releases already `RECEIVED` are excluded from re-derivation.

The release's money fields complete the record. `list_value_cents` is the assembly-basis material price multiplied by the release quantity. `ship_cost_cents` is the transport cost for the release. `value_cents` is the release value after ship cost, material value and any recycled credit. `declared_for_procurement` is true when the status is `RELEASED`, `SHIPPED` or `RECEIVED`, and it is this flag — not the status name alone — that the material gate consults. `restriction_since_iso` carries the timestamp the release entered `RESTRICTED` and is null otherwise.

The material gate is how a release decision constrains the shop. A work package whose gate commodity is a member of the owning project's `material_gate_commodities` cannot be released while that commodity has no release in the declared-for-procurement state; the package's `releasable_status` reads `MATERIAL_HOLD` and the release is refused with `ERR_MATERIAL_HOLD_ACTIVE` (HTTP 409). The hold lifts as soon as the commodity's release is declared, at which point the affected packages' `releasable_status` recomputes out of `MATERIAL_HOLD` under the §3.3 precedence — `ALLOWED` on an `ON_TRACK` project, `PERMITTED` on a `RELEASE_PENDING` one, `READY` otherwise — and a gate commodity that is still undeclared keeps its hold. Because the engineering-hold rule precedes the material-hold rule — see §2.8 — a package that is both on engineering hold and awaiting a commodity reports the engineering hold.

## 4. Endpoint Definitions

All endpoints are mounted under the `/prefab` prefix. A request that creates a new resource returns HTTP 201 with the created resource in the `data` field; a request that modifies an existing resource returns HTTP 200 with the updated resource in the `data` field.
