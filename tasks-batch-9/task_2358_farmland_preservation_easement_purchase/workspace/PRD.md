# Farmland Preservation Easement Purchase API — Product Requirements Document

## 1. Introduction

Agricultural land preservation programs buy development rights rather than land. A county or state agency opens a competitive funding round, invites farm owners to offer a conservation easement over their fields, ranks the offers on soil quality, parcel size, contiguity to already-preserved ground and development pressure, has the easement appraised as the spread between what the land is worth unrestricted and what it is worth once farming is the only permitted future, negotiates a price, assembles the money from federal, state and local appropriations that each carry their own share caps and matching requirements, clears title, obtains mortgage subordination and a boundary survey, records the deed, and then monitors the protected acreage every year for the rest of time.

The operational pain this API addresses is that none of those steps is independent. A neighbour's easement recorded mid-round changes a parcel's contiguity and therefore its rank. A landowner's counter-offer changes the total program cost and therefore invalidates a funding plan that was already assembled. One acceptance can exhaust a federal appropriation and silently strand three other applications that had reserved against the same headroom. A single impervious-coverage violation discovered on an annual site visit must freeze every amendment already under review. Staff today reconcile these interactions by hand, in spreadsheets, and the reconciliations drift.

This document specifies the service that makes those interactions explicit and enforced. It defines fourteen resource types, the parallel state dimensions each one carries, the ten deterministic calculations that produce every score, valuation, fee, allocation and deadline in the system, and the sixty error conditions that must be reported rather than absorbed. Every temporal rule — intake windows, offer expiries, obligation windows, cure deadlines, monitoring projections — reads a server-held logical clock rather than wall time, so that a program's entire multi-year lifecycle can be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request except the clock-setting operation described in §2.5 must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user is acting. If either header is absent, or if `X-User-Role` is not one of the six role names below spelled exactly, the request is rejected with `ERR_UNAUTHENTICATED` (401). If the headers are well formed but the named role is not authorised for the endpoint per the table in §4, the request is rejected with `ERR_FORBIDDEN_ROLE` (403).

The six roles are `ProgramAdmin`, `Landowner`, `AcquisitionOfficer`, `AppraisalReviewer`, `Appraiser` and `StewardshipMonitor`.

- `ProgramAdmin` is the program authority. It configures programs, funding rounds and funding sources; maintains parcel attributes; assembles funding plans; reviews and waives closing requirements; records easements; cancels closings; and drafts, submits, decides, reinstates and rescinds amendments.
- `Landowner` is the applicant. It registers parcels, files applications, counters offers, accepts standing offers and withdraws.
- `AcquisitionOfficer` is the negotiator. It engages appraisers, issues offers, accepts standing counters and submits closing-requirement packages.
- `AppraisalReviewer` independently certifies or rejects a submitted appraisal.
- `Appraiser` is the engaged valuation professional who submits the unrestricted and restricted values.
- `StewardshipMonitor` is stewardship staff: it schedules, completes and cancels monitoring visits, opens violations, accepts cure plans and verifies cures.

Identity semantics differ by role, and the difference matters for every ownership check. When `X-User-Role` is `Landowner`, `X-User-ID` is the `id` of the acting `Landowner` record; ownership checks on any resource that references a landowner compare that resource's landowner foreign key to `X-User-ID`. Concretely, registering a parcel requires `X-User-ID` to equal the `landowner_id` in the body; filing an application requires `X-User-ID` to equal both the body `landowner_id` and the `landowner_id` recorded on the referenced parcel; and countering, accepting or withdrawing requires `X-User-ID` to equal the application's `landowner_id`. A mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (403).

When `X-User-Role` is any of `ProgramAdmin`, `AcquisitionOfficer`, `AppraisalReviewer`, `Appraiser` or `StewardshipMonitor`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared to any row's `id`. The server does record these identifiers where a transition writes them — `offer_issued_by_user_id` on an application, `engaged_by_user_id` and `certified_by_user_id` on an appraisal, `submitted_by_user_id` and `reviewed_by_user_id` on a closing requirement, and `actor_role` together with `actor_user_id` on every negotiation-log entry — and it compares them to one another for the segregation-of-duties gates in §2.9. The `Appraiser` role is the one opaque role that also carries an ownership gate: an appraisal submission requires `X-User-ID` to equal the `appraiser_user_id` nominated on that appraisal when it was engaged, and a mismatch is likewise `ERR_NOT_RESOURCE_OWNER`. There is no persisted appraiser entity.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two query parameters. `limit` caps the number of records returned; it defaults to 10, may be no smaller than 1 and no larger than 100. `offset` is the number of records to skip; it defaults to 0 and may not be negative. A `limit` outside its permitted range, or a negative `offset`, is a request-shape violation and is rejected with `ERR_INVALID_REQUEST` (422). Each list response reports `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope.

The default ordering for a list is `created_at` ascending. Several collections override that default because their natural reading order is not chronological:

- `GET /funding-rounds` returns newest first, ordered by `created_at` descending and then `id` ascending.
- `GET /parcels` is ordered by `created_at` ascending and then `id` ascending.
- `GET /applications` is ordered by `rank_position` ascending with unranked rows (those whose `rank_position` is null) placed last, then by `created_at` ascending.
- `GET /funding-sources` is ordered by `priority_order` ascending and then `created_at` ascending.
- `GET /funding-commitments` is ordered by `sweep_order` ascending and then `created_at` ascending.
- `GET /easements` is ordered by `recorded_on` ascending and then `created_at` ascending.
- `GET /easements/{id}/monitoring-visits` is ordered by `window_start` ascending and then `created_at` ascending.
- `GET /easements/{id}/violations` is ordered by `opened_on` ascending and then `created_at` ascending.

Filters available on the list endpoints are all optional and all exact-match. Funding rounds filter on `program_id` and `status`. Parcels filter on `landowner_id`, `status` and `county`. Applications filter on `funding_round_id`, `parcel_id`, `landowner_id`, `status`, `closing_status` and `funding_plan_status`. The negotiation log filters on `kind`. An application's closing requirements filter on `status` and `requirement_type`. Appraisal lists filter on `status`. Funding sources filter on `program_id`, `level` and `status`. Funding commitments filter on `application_id`, `funding_source_id` and `status`. Easements filter on `parcel_id`, `application_id`, `status`, `compliance_status` and `stewardship_status`. An easement's monitoring visits filter on `status`; its violations filter on `status` and `violation_type`; its amendments filter on `status` and `amendment_type`. The per-visit violation list filters on `status`.

### 2.4. Record Identity and the Immutable Negotiation Log

Every resource carries an `id`: a server-minted UUID with no type prefix. Every resource also carries a `created_at` timestamp, an ISO 8601 UTC instant with three fractional digits.

Thirteen of the fourteen resource types additionally carry `updated_at` — an ISO 8601 UTC instant refreshed on every mutation — and `version`, an integer that starts at 1 on creation and increments by exactly one on every mutation of that row, including mutations caused by a cascade the client did not request directly. Recomputing a derived counter or rollup is a mutation: when acceptance recomputes a funding source's ledger, or when a monitoring completion re-projects an easement's due date, the affected row's `updated_at` and `version` both move.

The single exception is the negotiation log. A `NegotiationRound` is append-only and immutable once written; it carries `id` and `created_at` only, and both `updated_at` and `version` are absent from it entirely.

### 2.5. The Logical Clock and the Time-Driven Sweep

The server holds a logical UTC clock, and every window, expiry, deadline and projection rule in this specification reads that clock rather than real wall-clock time. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z` and must never fall back to wall-clock time. `POST /_clock/set_current_utc` moves the clock to the supplied `current_utc` instant and returns both `current_utc` and `previous_utc`; it is the one endpoint exempt from the authentication headers of §2.1, and it performs no state transitions of its own.

Time does not, by itself, change any record. Every consequence of the clock advancing is realised by an explicit operational sweep — `POST /stewardship-sweeps` — which is idempotent with respect to the current clock reading and reports what it did through the counters `swept_easement_count`, `due_count`, `delinquent_count`, `cleared_to_compliant_count`, `terminated_easement_count`, `lapsed_offer_count`, `escalated_violation_count`, `expired_source_count` and `closed_round_count`. Each individual sweep effect is described in the workflow it belongs to in §3.

### 2.6. Numeric Domains, Money and Rounding

Every monetary amount in this system is an integer count of cents; there are no fractional-cent values anywhere in storage or in a response body. Acreage, weights, percentages and scores are decimal numbers. Wherever a value is rounded, the method is round half up unless the text explicitly says the value is floored (truncated toward zero for the non-negative quantities in this domain) or ceilinged.

Scores and acreage rollups are carried to exactly 2 decimal places, rounded half up: `soil_quality_score`, `development_pressure_score` and `composite_score` all live on the closed range from 0.00 to 100.00, and `total_preserved_acres` is a 2-decimal acreage rollup. Program weights carry exactly 2 decimals. A bargain-sale `donation_pct` may carry up to 4 decimals.

Different calculations deliberately round in different directions and at different granularities — the preliminary valuation floors to whole thousands of dollars while the certified valuation rounds half up to whole hundreds, the funding waterfall floors each source's share independently before summing, and the installment schedule floors the annual payment and pushes every residue onto the final payment. Each of those rules is stated in full where the calculation is described in §3, and reusing one calculation's rounding rule for another is incorrect.

Request bodies are validated against their declared numeric domains before any business rule runs, and a violation is `ERR_INVALID_REQUEST` (422). The domains are: `acres` strictly positive; `prime_soil_acres` and `statewide_important_soil_acres` non-negative with their sum no greater than `acres`; every field whose name ends in `_cents` non-negative; `donation_pct` at least 0 and strictly less than 1; `installment_years` between 2 and 10 inclusive; every fractional share field strictly above 0 and no greater than 1; `limit` between 1 and 100; `offset` non-negative; and every timestamp a valid ISO 8601 UTC instant. A body that is not a JSON object, omits a required field, carries an unknown field, uses the wrong type for a field, or names an enum member that does not exist is likewise `ERR_INVALID_REQUEST`.

### 2.7. Optimistic Concurrency Control on Parent Versions

Four write operations require the client to declare which version of a parent record it was looking at. In each case the field is mandatory, not optional, and the value must equal the parent row's current `version` at the moment the write is processed. If the parent's `version` has advanced since the client last read it, the write is rejected and nothing is mutated.

- `POST /applications/{id}/offers` requires `expected_application_version` matching the target `Application`'s current `version`. A mismatch is rejected with `ERR_STALE_APPLICATION_VERSION` (412). This gate is load-bearing precisely because a fresh offer is a legitimate operation from the same observed state — it supersedes the standing offer and rewrites `structure`, `donation_pct` and every derived cost field — so nothing in the state machine would otherwise reject a writer whose view predates an intervening offer, counter, certification or funding-plan assembly.
- `POST /applications/{id}/funding-plan` requires `expected_application_version` matching the target `Application`'s current `version`. A mismatch is rejected with `ERR_STALE_APPLICATION_VERSION` (412). Re-assembling a plan is also a legitimate repeat operation, so only the stale view distinguishes a writer whose `total_program_cost_cents` basis has since been rewritten by an offer or a counter.
- `POST /easements/{id}/amendments` requires `expected_easement_version` matching the target `Easement`'s current `version`. A mismatch is rejected with `ERR_STALE_EASEMENT_VERSION` (412). A new draft legitimately rescinds any prior draft on the same easement, so this gate is what rejects a drafter whose view predates an intervening approval, rescission, monitoring completion or violation.
- `PATCH /parcels/{id}` requires `expected_parcel_version` matching the target `Parcel`'s current `version`. A mismatch is rejected with `ERR_STALE_PARCEL_VERSION` (412). Re-patching the same attributes is legitimate — contiguity grows every time a neighbouring easement is recorded, and appraisers revise valuations — so only this gate rejects an editor whose view predates an intervening patch or an application or closing cascade that moved `status`.

No other endpoint accepts a version field. Supplying one where it is not defined is an unknown field and therefore `ERR_INVALID_REQUEST`.

### 2.8. Cascade Discipline Across the Preservation Graph

The records in this system form a graph rather than a tree, and several of them carry more than one state dimension at once. An `Application` carries three independent dimensions: `status` tracks acquisition and negotiation, `closing_status` is a pure function of that application's closing-requirement children together with its funding dimension, and `funding_plan_status` is a pure function of its funding-commitment children. An `Easement` likewise carries three: `status` is the deed dimension, `stewardship_status` is the monitoring dimension, and `compliance_status` is the violation dimension. These dimensions advance independently — a monitoring completion resets only the stewardship dimension and never touches compliance, and a compliant easement and a violating easement both traverse the monitoring edges on the same sweep.

Because the dimensions are derived, the server is expected to move parent rows without an explicit client request against them. Every such automatic move is a real mutation of the affected row and increments that row's `version` and refreshes its `updated_at`. Where an operation touches several rows, every touched row's `version` moves, not only the one named in the URL. The specific cascades — commitment obligation chains, source threshold flips, requirement bubble-ups, amendment suspensions, parcel status returns and program acreage rollups — are enumerated in the workflows of §3, and an implementation that performs the primary effect but skips a secondary one is incorrect.

Two conservation invariants must hold at all times and are the reason several cascades come in compensating pairs. First, for every funding source, `authorized_cents` must always equal `available_cents` plus `committed_cents` exactly; releasing an obligated commitment therefore recomputes both sides. Second, for every easement, `residential_rights_retained` plus `residential_rights_extinguished` must always equal the parcel's `baseline_dwelling_rights`; approving a rights-relocation amendment and rescinding it are exact inverses.

### 2.9. Segregation of Duties

Two review gates compare opaque operator identifiers and reject self-review, and they are evaluated as authorisation checks with HTTP 403 rather than as state conflicts.

An appraisal review must be performed by a user who is neither the officer who engaged the appraisal nor the appraiser who submitted it: `X-User-ID` must differ from both `engaged_by_user_id` and `appraiser_user_id` on that appraisal, otherwise the review is rejected with `ERR_APPRAISAL_REVIEW_SOD`. A closing-requirement review must be performed by a user other than the one who last submitted that requirement: `X-User-ID` must differ from `submitted_by_user_id`, otherwise the review is rejected with `ERR_CLOSING_REVIEW_SOD`. Because the same `ProgramAdmin` population both submits and reviews nothing in this domain, the practical effect of the second gate is that an `AcquisitionOfficer` who submits a package cannot also be the identifier that accepts it.

### 2.10. Path Resolution for Nested Resources

When a path contains an identifier, that identifier must resolve to an existing row of the endpoint's own entity type before any body parsing or business rule runs. Where a path is nested, identifiers are resolved strictly left to right and the response reports the first identifier that fails, using the not-found code belonging to that identifier's entity: `ERR_PROGRAM_NOT_FOUND`, `ERR_ROUND_NOT_FOUND`, `ERR_LANDOWNER_NOT_FOUND`, `ERR_PARCEL_NOT_FOUND`, `ERR_APPLICATION_NOT_FOUND`, `ERR_APPRAISAL_NOT_FOUND`, `ERR_SOURCE_NOT_FOUND`, `ERR_COMMITMENT_NOT_FOUND`, `ERR_REQUIREMENT_NOT_FOUND`, `ERR_EASEMENT_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_VIOLATION_NOT_FOUND` or `ERR_AMENDMENT_NOT_FOUND`, each with HTTP 404.

Foreign keys supplied inside a request body are resolved the same way and with the same codes, one step later in the ladder: a `program_id` that names no program yields `ERR_PROGRAM_NOT_FOUND`, and likewise for `funding_round_id`, `parcel_id`, `landowner_id`, `easement_id` and `monitoring_visit_id`. Body-level foreign-key resolution applies to funding-round creation, parcel registration, application filing, funding-source creation, monitoring-visit scheduling and violation opening.

### 2.11. Validation Precedence

When more than one rule would reject a request, the rule earliest in the following ladder wins and its error is the one reported. The ladder is global; it is not re-derived per endpoint.

1. `X-User-ID` present — `ERR_UNAUTHENTICATED`.
2. `X-User-Role` present and one of the six declared roles — `ERR_UNAUTHENTICATED`.
3. The role is permitted for the endpoint — `ERR_FORBIDDEN_ROLE`.
4. Every path identifier resolves — the entity-specific not-found code.
5. Every body foreign key resolves — the entity-specific not-found code.
6. Request shape, types, enum members, string lengths and numeric domains — `ERR_INVALID_REQUEST`, or `ERR_WEIGHTS_NOT_NORMALIZED` for the program-weight sum.
7. Ownership — `ERR_NOT_RESOURCE_OWNER`.
8. Optimistic concurrency — the stale-version code for the parent entity.
9. The subject row is in a state from which the requested transition exists — the state code for that entity and dimension.
10. Segregation of duties — `ERR_APPRAISAL_REVIEW_SOD` or `ERR_CLOSING_REVIEW_SOD`.
11. Stewardship hold and compliance posture — `ERR_EASEMENT_NOT_COMPLIANT`.
12. Temporal windows, in this order: round intake and ranking windows (`ERR_ROUND_WINDOW_CLOSED`), then appraisal engagement conflicts (`ERR_APPRAISAL_ENGAGEMENT_CONFLICT`), then monitoring window overlaps (`ERR_MONITORING_WINDOW_OVERLAP`).
13. Negotiation bounds — `ERR_NEGOTIATION_ROUNDS_EXHAUSTED` and `ERR_COUNTER_NOT_HIGHER`.
14. Parcel eligibility — `ERR_PARCEL_NOT_ELIGIBLE`.
15. The remaining business constraints, all at one rung: `ERR_SURVEY_ACREAGE_MISMATCH`, `ERR_LIENHOLDER_REQUIRED`, `ERR_TITLE_EXCEPTIONS_OUTSTANDING`, `ERR_REQUIREMENT_NOT_WAIVABLE`, `ERR_RESIDENTIAL_RIGHTS_OVERDRAWN`, `ERR_IMPERVIOUS_ALLOWANCE_EXCEEDED`, `ERR_NO_NET_CONSERVATION_BENEFIT` and `ERR_NO_SCORED_APPLICATIONS`.
16. Referential scope — `ERR_VISIT_EASEMENT_MISMATCH`, `ERR_REQUIREMENT_SCOPE_MISMATCH` and `ERR_EASEMENT_SCOPE_MISMATCH`.
17. The requested-price ceiling — `ERR_REQUESTED_PRICE_ABOVE_PRELIMINARY_CEILING`.
18. The certified-value ceiling on offers and counters — `ERR_OFFER_EXCEEDS_CERTIFIED_VALUE`.
19. Funding-plan completeness at acceptance (`ERR_FUNDING_PLAN_INCOMPLETE`) and funding-plan staleness at closing (`ERR_FUNDING_PLAN_STALE`).
20. Waterfall coverage and its share tests: `ERR_FUNDING_SHORTFALL`, then `ERR_FEDERAL_SHARE_EXCEEDED`, then `ERR_LOCAL_MATCH_SHORTFALL`, then `ERR_MATCH_RATIO_UNSATISFIED`.
21. Source capacity — `ERR_SOURCE_WINDOW_CAPACITY_EXCEEDED`.

Note in particular that concurrency sits above the state check: an offer carrying a stale `expected_application_version` against an application that is also in the wrong state reports the stale-version error, not the state error.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Program, Its Rounds and Its Appropriations

A `PreservationProgram` is the configuration root, and a `ProgramAdmin` creates it with a `name` of 1 to 200 characters together with the four ranking weights and the seven policy parameters that govern everything downstream. The weights — `soil_weight`, `size_weight`, `contiguity_weight` and `pressure_weight` — each lie between 0 and 1 inclusive, carry exactly 2 decimals, and must together sum to exactly 1.00; any other sum is rejected with `ERR_WEIGHTS_NOT_NORMALIZED` (422). `min_composite_score` is the inclusive ranking cut-off and lives between 0.00 and 100.00 with a default of 60.00. `max_negotiation_rounds` bounds how many program offer rounds one application may receive and lies between 1 and 10, defaulting to 3. `local_match_min_pct` (default 0.25) is the minimum local share of a funding plan and `federal_max_share_pct` (default 0.50) the maximum federal share, each between 0 and 1. `impervious_allowance_pct` is the fraction of protected acreage that may ever be covered by buildings and pavement; it lies between 0 and 0.25 and defaults to 0.02. `amendment_policy` is either `STRICT` or `CONDITIONAL` and defaults to `STRICT`. These eleven inputs are all required.

Three further parameters are optional on creation and fall back to program-wide defaults when omitted. `monitoring_interval_days` is the gap from one monitoring anchor to the next due date; it lies between 30 and 1095 days and defaults to a full year of 365 days. `monitoring_grace_days` is the forgiveness period after a due date before an easement is treated as delinquent; it lies between 0 and 365 days and defaults to 30. `appraisal_engagement_buffer_days` is the buffer padded symmetrically onto both ends of an appraisal engagement for conflict detection; it lies between 0 and 30 days and defaults to 3. A new program opens with `status` set to `ACTIVE` — the enumeration is `ACTIVE` and `CLOSED` — and with `total_preserved_acres` at 0. That rollup is the sum of `protected_acres` over every easement whose `status` is `RECORDED` or `AMENDED` that is reachable through this program's funding rounds, carried to 2 decimals and rounded half up, and it is recomputed whenever an easement is recorded or terminated.

A `FundingRound` is created against a program by supplying that program's identifier as `program_id`, a `round_label` of 1 to 80 characters, an intake window given by `opens_on` and `closes_on` where `closes_on` must be strictly later than `opens_on`, and a `pool_cents` acquisition pool that must be strictly positive and serves as the round's advertised budget. The round `status` enumeration is `DRAFT`, `OPEN`, `SELECTED` and `CLOSED`. A new round begins in `DRAFT` with `score_basis` and `ranked_at` both null and with `application_count` and `selected_count` at 0. Those two counters are derived: `application_count` counts every application on the round regardless of status, whereas `selected_count` counts only those applications whose `status` is not `RECEIVED`, `NOT_SELECTED` or `WITHDRAWN`.

Opening a round moves it `DRAFT → OPEN`, and three conditions must hold: the round is in `DRAFT`, the parent program's `status` is `ACTIVE`, and at least one funding source exists on that same program with `status` of `ACTIVE`. A round that is not in `DRAFT`, or whose program or appropriations do not satisfy those conditions, is rejected with `ERR_INVALID_ROUND_STATE` (409). The full round lifecycle is `DRAFT → OPEN → SELECTED → CLOSED`, with `CLOSED` terminal; the last edge is reached only by the time-driven sweep, which moves a round `SELECTED → CLOSED` once no application on it remains outside the terminal set `NOT_SELECTED`, `CLOSED_RECORDED`, `WITHDRAWN` and `LAPSED`.

A `FundingSource` is an appropriation authorised on a program. It carries `program_id`, a `source_name` of 1 to 160 characters, a `level` of `FEDERAL`, `STATE` or `LOCAL`, a strictly positive `authorized_cents` authority, an obligation window given by `obligation_window_start` and `obligation_window_end` where the end must be strictly later than the start, a `max_share_pct` strictly above 0 and no greater than 1 that guides how much of any one application's cost this source will carry, and a `priority_order` of at least 1 that fixes its place in the sweep — lower values are swept first. Three inputs are optional: `requires_match` defaults to false, `match_ratio` defaults to 0 and must be 0 whenever `requires_match` is false, and `fully_obligated_threshold_pct` defaults to 0.95 and must be strictly above 0 and no greater than 1.

A source's ledger is four derived amounts plus its authority. `committed_cents` is the sum of `amount_cents` over its commitments whose status is `OBLIGATED` or `DISBURSED`. `reserved_cents` is the same sum over commitments in `RESERVED`. `disbursed_cents` is the same sum over commitments in `DISBURSED`. `available_cents` is `authorized_cents` less `committed_cents` — reserved commitments are deliberately not netted out, which is why two competing plans may reserve against the same headroom and the loser lapses when the winner is accepted. A new source opens `ACTIVE` with all three sums at 0 and `available_cents` equal to `authorized_cents`, and with `suspension_reason` null. The status enumeration is `ACTIVE`, `FULLY_OBLIGATED`, `EXPIRED` and `SUSPENDED`, with `EXPIRED` terminal.

Two of those transitions are automatic and form a compensating pair. When a commitment reaches `OBLIGATED` and the source's `committed_cents` has reached or passed the floor of `authorized_cents` multiplied by `fully_obligated_threshold_pct`, the source flips `ACTIVE → FULLY_OBLIGATED`, every commitment against it still in `RESERVED` flips `RESERVED → LAPSED` with `lapse_reason` recorded as `SOURCE_FULLY_OBLIGATED`, and its `version` increments. When a commitment is released and `committed_cents` falls back strictly below that same floor, the source flips `FULLY_OBLIGATED → ACTIVE` and its `version` increments — but commitments already lapsed are never revived, because lapse is deliberately irreversible.

A `ProgramAdmin` may also suspend a source from either `ACTIVE` or `FULLY_OBLIGATED` by supplying a `reason`, which is stored as `suspension_reason`. Suspension flips the source to `SUSPENDED`, lapses every `RESERVED` commitment against it with `lapse_reason` `SOURCE_SUSPENDED`, flips each affected application's `funding_plan_status` from `FUNDED` to `UNDERFUNDED`, and increments the source's `version`. Suspending a source that is already `EXPIRED` or `SUSPENDED` is rejected with `ERR_INVALID_SOURCE_STATE`. Separately, the sweep expires a source from either `ACTIVE` or `FULLY_OBLIGATED` once the logical clock passes strictly beyond its `obligation_window_end`, lapsing its `RESERVED` commitments with `lapse_reason` `SOURCE_EXPIRED` and flipping their applications `FUNDED → UNDERFUNDED`.

### 3.2. Parcels: Registration, Scoring and Attribute Maintenance

A `Landowner` record is registered by a `ProgramAdmin` with a `legal_name` of 1 to 160 characters, a `mailing_state` of exactly two uppercase letters, and `tax_id_last4`, exactly four digits used on bargain-sale substantiation. The record opens with `status` `ACTIVE`; the enumeration is `ACTIVE` and `SUSPENDED`, and only an `ACTIVE` landowner may file an application. The identifier minted for the landowner is what that person subsequently presents as `X-User-ID`.

A parcel is registered either by its own landowner or by a `ProgramAdmin` on that landowner's behalf. The payload names the owner as `landowner_id` and describes the land: `county` (1 to 80 characters), `acres` (strictly positive, 2 decimals), `prime_soil_acres` and `statewide_important_soil_acres` (each non-negative with 2 decimals, and `prime_soil_acres` plus `statewide_important_soil_acres` may not exceed `acres`), `contiguous_preserved_acres` (non-negative, 2 decimals, the acreage of already-preserved land sharing a boundary), `road_frontage_feet` (a non-negative whole number of linear feet of public road frontage), `sewer_available` (whether public sewer reaches the parcel boundary), `zoning_min_lot_acres` (strictly positive, 2 decimals, the minimum lot size under current zoning), `baseline_dwelling_rights` (a non-negative count of residential building rights existing before any easement), `unrestricted_value_cents` (strictly positive) and `restricted_value_cents` (non-negative and strictly less than `unrestricted_value_cents`). `mortgage_lienholder_name` is optional and defaults to null; a parcel with a lienholder named here will require a mortgage subordination before it can close. A new parcel opens with `status` `ELIGIBLE`, and the enumeration is `ELIGIBLE`, `UNDER_APPLICATION`, `ENCUMBERED` and `WITHDRAWN`.

Registration immediately computes two scores. `soil_quality_score` credits prime farmland soil at full weight and soil of statewide importance at 60 percent of that weight. Divide `prime_soil_acres` by `acres` to obtain the prime share and `statewide_important_soil_acres` by `acres` to obtain the important share; add the prime share to the important share multiplied by the important-soil weight of 0.60; clamp the result to a maximum of 1; multiply by 100; and round half up to 2 decimals. The clamp is applied before rounding, so a parcel that is entirely prime and important soils scores exactly 100.00 and never more.

`development_pressure_score` sums three point awards and caps the total. Road frontage earns 3 points for each whole 100-foot unit of `road_frontage_feet`, discarding any fractional remainder rather than pro-rating it, and the frontage award is capped at 30 points — so 640 feet earns six whole units and therefore 18 points, while 150 feet earns one unit and therefore 3. Public sewer availability earns a flat 25 points when `sewer_available` is true and nothing when it is false. Zoning earns 45 points when `zoning_min_lot_acres` is strictly below 1.0 acre, otherwise 35 points when it is strictly below 3.0 acres, otherwise 20 points when it is strictly below 10.0 acres, otherwise 5 points. Those tiers are left-closed and right-open at every boundary: a minimum lot size of exactly 1.0 acre earns 35 rather than 45, exactly 3.0 acres earns 20, and exactly 10.0 acres earns 5. The three awards are added, the sum is capped at 100, and the capped figure is rounded half up to 2 decimals.

A `ProgramAdmin` maintains a parcel's mutable attributes over time, because contiguity grows as neighbouring easements are recorded and valuations get revised. The update carries the mandatory `expected_parcel_version` described in §2.7 plus any subset of `contiguous_preserved_acres`, `road_frontage_feet`, `sewer_available`, `zoning_min_lot_acres`, `unrestricted_value_cents`, `restricted_value_cents` and `mortgage_lienholder_name`. Both scores are recomputed from the post-update attribute values and the parcel's `version` increments. Crucially, the update is not retroactive: it never rewrites any application's `contiguity_acres_at_receipt`, and it never rewrites a `composite_score` that has already been assigned.

### 3.3. Filing an Application and Ranking the Round

An `Application` is the junction where a round, a parcel and a landowner meet. The landowner files it by naming `funding_round_id`, `parcel_id`, `landowner_id` and a strictly positive `requested_price_cents`, and five gates must clear. The round's `status` must be `OPEN` and the logical clock must lie within the intake window inclusive of both endpoints — at or after `opens_on` and at or before `closes_on` — otherwise the filing is rejected with `ERR_ROUND_WINDOW_CLOSED`. The parcel's `status` must be `ELIGIBLE` and its `restricted_value_cents` must be strictly below its `unrestricted_value_cents`, otherwise `ERR_PARCEL_NOT_ELIGIBLE`. The parcel's recorded `landowner_id` must equal the body's `landowner_id`, and `X-User-ID` must equal it too, otherwise `ERR_NOT_RESOURCE_OWNER`. The landowner's own `status` must be `ACTIVE`.

The fifth gate needs a number the server computes on the spot. The **preliminary easement value** is the assessor-proxy estimate of what the development rights are worth, and it is deliberately conservative so the program is never bound by an unappraised figure. Subtract the parcel's `restricted_value_cents` from its `unrestricted_value_cents` to get the gross spread; take 90 percent of that spread; then floor the result down to a whole multiple of 100,000 cents, that is, down to the nearest thousand dollars. The result is stamped onto the application as `preliminary_easement_value_cents`. The landowner's `requested_price_cents` may not exceed that figure multiplied by 1.10 and rounded half up — a ten percent ask above the assessor proxy — and a higher request is rejected with `ERR_REQUESTED_PRICE_ABOVE_PRELIMINARY_CEILING`.

Filing then freezes one thing and moves three others. `contiguity_acres_at_receipt` is stamped with the parcel's `contiguous_preserved_acres` as it stands at that instant, and that snapshot is never updated afterwards. The application opens with `status` `RECEIVED`, `closing_status` `NOT_APPLICABLE`, `funding_plan_status` `UNFUNDED` and `negotiation_round_count` at 0. The parcel moves `ELIGIBLE → UNDER_APPLICATION` and its `version` increments. The round's `application_count` is recomputed and its `version` increments.

The acquisition dimension of an application runs over the enumeration `RECEIVED`, `RANKED`, `NOT_SELECTED`, `OFFER_ISSUED`, `COUNTERED`, `ACCEPTED`, `CLOSED_RECORDED`, `WITHDRAWN` and `LAPSED`, of which `NOT_SELECTED`, `CLOSED_RECORDED`, `WITHDRAWN` and `LAPSED` are terminal.

Ranking is a single-shot checkpoint run by a `ProgramAdmin` once the intake window has closed. It requires the round to be `OPEN` — a second attempt therefore fails with `ERR_INVALID_ROUND_STATE` — requires the logical clock to be strictly past `closes_on`, failing which the answer is `ERR_ROUND_WINDOW_CLOSED`, and requires at least one application on the round still in `RECEIVED`, failing which the answer is `ERR_NO_SCORED_APPLICATIONS`. The caller nominates a `score_basis` of either `RECEIPT_BASIS` or `ROUND_CLOSE_BASIS`.

The **composite score** blends four components under the program's weights. The soil component is the parcel's `soil_quality_score` unchanged. The size component is 100 multiplied by the lesser of 1 and the parcel's `acres` divided by 200 — so a parcel of 200 acres or larger earns the full 100 and a 160-acre parcel earns 80. The contiguity component is 100 multiplied by the lesser of 1 and the contiguity acreage divided by the parcel's `acres`. The pressure component is the parcel's `development_pressure_score` unchanged. Multiply each component by its matching program weight, add the four products, and round that single sum half up to 2 decimals. Each component is carried at full precision through the multiplication; rounding the components individually before the weighted sum is the wrong variant and drifts.

Which contiguity acreage feeds the third component is exactly what `score_basis` selects, and the two variants can differ by many points on identical stored data. Under `RECEIPT_BASIS` the component reads the application's frozen `contiguity_acres_at_receipt`. Under `ROUND_CLOSE_BASIS` it reads the parcel's live `contiguous_preserved_acres` as it stands at the moment of the ranking call, which will have moved upward for any parcel whose neighbour was preserved during the round. The chosen basis is recorded on the round as `score_basis`.

Scoring is confined to applications on the round whose `status` is `RECEIVED`. Applications already in `RANKED`, `NOT_SELECTED`, `OFFER_ISSUED`, `COUNTERED`, `ACCEPTED`, `CLOSED_RECORDED`, `WITHDRAWN` or `LAPSED` are excluded from the pass entirely and keep whatever `composite_score` and `rank_position` they already had. Each scored application has its `composite_score` written, and the set is then partitioned at the program's `min_composite_score` inclusively: a score at or above the cut-off moves the application `RECEIVED → RANKED`, while a score strictly below it moves the application `RECEIVED → NOT_SELECTED`. Ranked applications receive a 1-based `rank_position` assigned over the ranked subset ordered by `composite_score` descending and then `created_at` ascending; applications that were not selected keep `rank_position` null. Because a not-selected application releases its land, each such parcel returns `UNDER_APPLICATION → ELIGIBLE` with its `version` incremented. Every touched application's `version` increments. The round finally records `ranked_at` as the logical-clock instant, recomputes `selected_count`, moves `OPEN → SELECTED`, and increments its own `version`. The call reports `ranked_count`, `selected_count`, `not_selected_count` and the list of `ranked_application_ids`.

### 3.4. Appraisal: Engagement, Submission and Certification

Before any money can be offered, an `AcquisitionOfficer` engages a valuation professional against the application. The engagement names an `appraiser_user_id` of 1 to 64 characters — the opaque identifier that person will present as `X-User-ID` — an `appraiser_firm` of 1 to 160 characters, an engagement interval given by `engagement_start` and `engagement_end` where the end must be at or after the start, and a `method` of either `PAIRED_SALES` or `INCOME_CAPITALIZATION`. The application must be in `RECEIVED`, `RANKED`, `OFFER_ISSUED` or `COUNTERED`, and any other state is rejected with `ERR_INVALID_APPLICATION_STATE`.

Engagements on the same application must not conflict, and the conflict test is a closed-interval comparison widened symmetrically by the program's `appraisal_engagement_buffer_days`. Two engagements conflict when the new engagement's start falls at or before the existing engagement's end extended forward by the buffer, and simultaneously the existing engagement's start falls at or before the new engagement's end extended forward by the buffer. Only appraisals whose `status` is `ASSIGNED`, `SUBMITTED` or `CERTIFIED` occupy an interval; a `REJECTED` appraisal blocks nothing. A conflict is rejected with `ERR_APPRAISAL_ENGAGEMENT_CONFLICT`.

A new appraisal opens in `ASSIGNED` with `basis` fixed at the only value that enumeration admits, `CERTIFIED_APPRAISAL_BASIS`, with `submission_count` at 0, with `engaged_by_user_id` set to the engaging officer's `X-User-ID`, and with `unrestricted_value_cents`, `restricted_value_cents`, `easement_value_cents`, `certified_by_user_id` and `review_note` all null. The lifecycle enumeration is `ASSIGNED`, `SUBMITTED`, `CERTIFIED` and `REJECTED`, and `CERTIFIED` is terminal.

The engaged `Appraiser` submits from either `ASSIGNED` or `REJECTED`, moving the appraisal to `SUBMITTED`; any other starting state is `ERR_INVALID_APPRAISAL_STATE`. The submission carries `unrestricted_value_cents`, which must be strictly positive, and `restricted_value_cents`, which must be non-negative and strictly less than the unrestricted figure. `X-User-ID` must match the `appraiser_user_id` nominated at engagement, else `ERR_NOT_RESOURCE_OWNER`.

The **certified easement value** derives from the appraiser's two figures and rounds quite differently from the preliminary figure. Subtract `restricted_value_cents` from `unrestricted_value_cents` to obtain the gross spread. Independently compute a ceiling of 1,200,000 cents — twelve thousand dollars — per acre, multiplied by the parcel's `acres`. Take the lesser of the gross spread and that ceiling. Divide by 10,000 cents, round half up to a whole number, and multiply back by 10,000: in other words, round half up to the nearest hundred dollars. There is no haircut on this basis, and the result is written to the appraisal's `easement_value_cents`. Submission also increments `submission_count`, which counts every entry into `SUBMITTED` including every resubmission after a rejection, clears any `review_note`, and increments the appraisal's `version`.

An `AppraisalReviewer` then decides, supplying a `decision` of `CERTIFY` or `REJECT` together with an optional `review_note` that becomes mandatory on rejection. The appraisal must be in `SUBMITTED`, and the segregation-of-duties gate of §2.9 applies. On `CERTIFY` the appraisal moves `SUBMITTED → CERTIFIED`, `certified_by_user_id` records the reviewer's `X-User-ID`, and — the cross-entity effect that unlocks negotiation — the parent application's `certified_easement_value_cents` is set to the appraisal's `easement_value_cents` and the application's `version` increments. On `REJECT` the appraisal moves `SUBMITTED → REJECTED`, the `review_note` is stored, and `easement_value_cents` is cleared back to null. Either way the appraisal's `version` increments. The revision cycle `SUBMITTED → REJECTED → SUBMITTED` may repeat without bound.

### 3.5. Negotiation: Offers, Counters, Structures and the Cost Build-Up

Negotiation is a bounded cycle between the program and the landowner, and every event in it is written to an append-only log. A `NegotiationRound` records the `application_id` it belongs to, a `round_index` of at least 1 identifying the 1-based offer round it belongs to, a `kind` of `OFFER`, `COUNTER`, `ACCEPTANCE`, `EXPIRATION` or `WITHDRAWAL`, an `amount_cents` that is null on `EXPIRATION` and `WITHDRAWAL` entries, an `offer_expires_on` populated only on `OFFER` entries, the `actor_role` and `actor_user_id` of whoever produced the event, and a `rationale` note carried across from a counter payload and null otherwise.

An `AcquisitionOfficer` issues an offer from either `RANKED` or `COUNTERED`, moving the application to `OFFER_ISSUED`; any other state yields `ERR_INVALID_APPLICATION_STATE`. The payload carries the mandatory `expected_application_version` of §2.7, an `offer_cents` amount, a `structure`, an `offer_expires_on` instant that must be strictly later than the logical clock, and optionally `donation_pct` and `installment_years`. The `structure` enumeration is `FULL_PURCHASE`, `BARGAIN_SALE` and `INSTALLMENT`, and it is null on an application that has never been offered. `donation_pct` is the bargain-sale donation fraction of certified value, at least 0 and strictly below 1 with at most 4 decimals; it must be 0 for any structure other than `BARGAIN_SALE`. `installment_years` is the number of annual installments, between 2 and 10 inclusive; it must be absent for any structure other than `INSTALLMENT`. Violations of either coupling rule are request-shape failures.

Two ceilings bound the offer. A `CERTIFIED` appraisal must already exist on the application, and `offer_cents` may not exceed the application's `certified_easement_value_cents`; either failure is reported as `ERR_OFFER_EXCEEDS_CERTIFIED_VALUE`. Separately, the application's `negotiation_round_count` — the number of `OFFER` entries in its log — must be strictly below the program's `max_negotiation_rounds`, and an attempt to exceed the bound is rejected with `ERR_NEGOTIATION_ROUNDS_EXHAUSTED`.

A successful offer appends an `OFFER` entry whose `round_index` is one more than the current `negotiation_round_count` and whose `amount_cents` is the offer amount, recomputes `negotiation_round_count` from the log, and writes `structure`, `donation_pct`, `installment_years`, `current_offer_cents`, `current_offer_expires_on`, `proposed_price_cents` (also the offer amount) and `offer_issued_by_user_id` (the issuing officer's `X-User-ID`). It then rebuilds the entire cost stack described below and increments the application's `version`.

The **cost build-up** turns a negotiated amount into what the program must actually fund, and its step order is normative. First, the donation: multiply the negotiated amount by `donation_pct` and round half up to whole cents, giving `donation_cents`, which is 0 whenever `donation_pct` is 0. Second, subtract `donation_cents` from the negotiated amount to obtain `bargain_sale_price_cents` — the cash portion the program pays. Third, select the administrative fee rate on that pre-fee cash portion: a rate of 0.030 — three percent — when `bargain_sale_price_cents` is strictly below 25,000,000 cents, otherwise a rate of 0.020 when it is strictly below 75,000,000 cents, otherwise a rate of 0.015. Fourth, multiply `bargain_sale_price_cents` by the selected rate and round half up to whole cents, giving `admin_fee_cents`. Fifth, add `bargain_sale_price_cents` and `admin_fee_cents` to obtain `total_program_cost_cents`. The tier is chosen on the pre-fee cash portion and never on the total; choosing it on the total is the natural-looking wrong variant and produces a different fee whenever the total crosses a tier boundary that the pre-fee price does not. There are exactly two rounding steps, in the stated order: donation first, administrative fee second.

When and only when `structure` is `INSTALLMENT`, three further fields are derived. Divide `total_program_cost_cents` by `installment_years` and floor to whole cents; that floored figure is `first_installment_cents` and is also what each of the early years pays. `final_installment_cents` is `total_program_cost_cents` less the floored annual figure multiplied by one fewer than `installment_years`, so that the early payments plus the final payment reconstitute the total exactly and every rounding residue lands on the last year. `installment_interest_total_cents` uses the average-outstanding-balance shortcut: multiply `total_program_cost_cents` by an annual rate of 0.0275, multiply by one fewer than `installment_years`, divide by 2, and round half up once at the end. For every other structure these three fields are null, and an offer that changes the structure away from `INSTALLMENT` nulls all three.

The landowner answers an offer with a counter, which requires the application to be in `OFFER_ISSUED` and `X-User-ID` to equal the application's `landowner_id`. The payload carries `counter_cents` and an optional `rationale`. The counter must be strictly greater than the application's `current_offer_cents` and must arrive at or before `current_offer_expires_on`; failing either, the answer is `ERR_COUNTER_NOT_HIGHER`. It may not exceed `certified_easement_value_cents`, and a higher counter is `ERR_OFFER_EXCEEDS_CERTIFIED_VALUE`. A successful counter appends a `COUNTER` entry carrying the `round_index` of the offer it answers, sets both `last_counter_cents` and `proposed_price_cents` to the counter amount, and moves the application `OFFER_ISSUED → COUNTERED`. The cost build-up is re-run against the counter amount, rewriting `donation_cents`, `bargain_sale_price_cents`, `admin_fee_cents` and `total_program_cost_cents`. Because the program cost has moved while the snapshot in `funded_cost_cents` has not, any assembled plan is now stale and `funding_plan_status` flips `FUNDED → UNDERFUNDED`; an application whose `funding_plan_status` is still `UNFUNDED` is left alone. The application's `version` increments.

The cycle `COUNTERED → OFFER_ISSUED → COUNTERED` may repeat until `negotiation_round_count` reaches the program's `max_negotiation_rounds`. A re-issued offer from `COUNTERED` runs exactly the same side-effect set as an offer from `RANKED`: a new `OFFER` entry is appended and every derived cost field is rewritten from the new offer amount. Note that `proposed_price_cents` always tracks the most recent `OFFER` or `COUNTER` entry, read in `created_at` ascending then `round_index` ascending order with the last such entry winning, whereas `current_offer_cents` tracks only the most recent `OFFER` and `last_counter_cents` only the most recent `COUNTER`.

A landowner may withdraw from `RECEIVED`, `RANKED`, `OFFER_ISSUED` or `COUNTERED` by supplying a `withdrawal_reason`, provided `X-User-ID` matches the application's `landowner_id`. Withdrawal appends a `WITHDRAWAL` entry with a null amount, stores the reason, and moves the application to `WITHDRAWN`. Every funding commitment on the application whose status is `RESERVED` or `OBLIGATED` flips to `RELEASED` with `lapse_reason` `APPLICATION_WITHDRAWN`, and `funding_plan_status` becomes `RELEASED`. Each touched source's `committed_cents`, `reserved_cents` and `available_cents` are recomputed and its `version` increments, and any source whose `committed_cents` has fallen back below the floor of `authorized_cents` times `fully_obligated_threshold_pct` returns `FULLY_OBLIGATED → ACTIVE`. The parcel returns `UNDER_APPLICATION → ELIGIBLE` with its `version` incremented, and the application's `version` increments.

An unanswered offer eventually dies of its own accord. On a sweep, any application still in `OFFER_ISSUED` whose `current_offer_expires_on` now lies strictly in the past appends an `EXPIRATION` entry with a null amount and moves `OFFER_ISSUED → LAPSED`. Its `RESERVED` commitments flip to `RELEASED` with `lapse_reason` `APPLICATION_LAPSED`, `funding_plan_status` becomes `RELEASED`, the parcel returns `UNDER_APPLICATION → ELIGIBLE`, and the application's `version` increments.

### 3.6. Funding Assembly: The Waterfall and Its Share Tests

Assembling the money is a `ProgramAdmin` operation on an application in `RANKED`, `OFFER_ISSUED` or `COUNTERED` whose `total_program_cost_cents` is already populated — that is, an offer must have been issued. It carries the mandatory `expected_application_version` of §2.7 plus a `target_closing_date`, the instant against which each source's obligation window is tested. The funding dimension runs over `UNFUNDED`, `FUNDED`, `UNDERFUNDED`, `OBLIGATED`, `DISBURSED` and `RELEASED`, of which `DISBURSED` and `RELEASED` are terminal; assembly is admissible from `UNFUNDED`, `FUNDED` or `UNDERFUNDED`, and re-assembly from `FUNDED` or `UNDERFUNDED` is a legitimate supersede rather than an error.

Eligibility for the sweep is narrow. A source participates only when it belongs to the same program as the application's round, its `status` is exactly `ACTIVE`, and its obligation window contains the supplied `target_closing_date` inclusively — that is, `obligation_window_start` is at or before the target date and `obligation_window_end` is at or after it. Sources that are `SUSPENDED`, `EXPIRED` or `FULLY_OBLIGATED` are skipped entirely even when their `available_cents` is large, and a source whose window does not contain the target date is skipped as well. Eligible sources are swept in `priority_order` ascending, ties broken by `created_at` ascending, and each source's 1-based position in that sweep is what gets recorded as `sweep_order` on any commitment it produces.

The sweep walks the eligible sources with a running remainder that starts at `total_program_cost_cents`. At each source, compute a share cap by multiplying the target total by that source's `max_share_pct` and flooring to whole cents. The source's take is the smallest of three quantities: the remaining amount still to be covered, that floored share cap, and the source's `available_cents`. Where the take is strictly positive, a commitment is created for exactly that `amount_cents`, and the take is subtracted from the remainder. Each source's share cap is floored independently and the caps are only summed afterwards; summing un-floored shares and flooring once is the wrong variant and diverges whenever more than one share has a fractional part.

Because per-source flooring can leave the summed caps a few cents short of the target, a remainder rule closes the gap, and that rule is `LAST_NON_ZERO_TAKE`. If a remainder survives the walk and at least one source took a non-zero amount, the last source with a non-zero take absorbs an extra amount equal to the smaller of the surviving remainder and that source's still-unused headroom (its `available_cents` less what it has already taken). The extra is added to that source's take, recorded on the commitment as `absorbed_remainder_cents`, and subtracted from the remainder. `absorbed_remainder_cents` is 0 on every other commitment. The absorbing source's own `max_share_pct` is deliberately not re-checked against the absorbed remainder; only the program-level federal ceiling still binds. If any remainder still survives, the whole assembly fails with `ERR_FUNDING_SHORTFALL` and nothing is written.

Four post-conditions are then checked against the assembled set, each with its own error. Let the federal total be the sum of takes from sources whose `level` is `FEDERAL`, the local total the sum from sources whose `level` is `LOCAL`, and the non-federal total the target less the federal total. The federal total may not exceed the target multiplied by the program's `federal_max_share_pct` and floored, otherwise `ERR_FEDERAL_SHARE_EXCEEDED`. The local total must be at least the target multiplied by the program's `local_match_min_pct` and rounded up to the next whole cent, otherwise `ERR_LOCAL_MATCH_SHORTFALL`. For every swept source whose `requires_match` is true, the non-federal total must be at least the federal total multiplied by that source's `match_ratio` and rounded half up, otherwise `ERR_MATCH_RATIO_UNSATISFIED`. And no source may be committed beyond its `available_cents`, nor may a source's `OBLIGATED` plus `DISBURSED` total ever exceed its `authorized_cents`, otherwise `ERR_SOURCE_WINDOW_CAPACITY_EXCEEDED` — a test that binds both at assembly time and again at acceptance.

On success, any commitment already standing on the application in `RESERVED` is first flipped to `RELEASED` with `lapse_reason` `PLAN_SUPERSEDED` before the new sweep's commitments are written; this is what makes repeat assembly safe. Each new `FundingCommitment` records its `application_id`, its `funding_source_id`, its strictly positive `amount_cents`, its `sweep_order`, its `absorbed_remainder_cents`, and a frozen copy of the source's obligation window as `window_start` and `window_end` for later capacity reasoning. It opens with `status` `RESERVED` and a null `lapse_reason`; the commitment enumeration is `RESERVED`, `OBLIGATED`, `DISBURSED`, `LAPSED` and `RELEASED`, of which the last three are terminal. The application's `funded_cost_cents` is snapshotted from `total_program_cost_cents`, `funding_plan_status` becomes `FUNDED`, each touched source's `reserved_cents` is recomputed with its `version` incremented, and the application's `version` increments. The call reports `application_id`, `funded_cost_cents`, `commitment_count`, `federal_total_cents`, `local_total_cents`, `state_total_cents`, `remainder_absorbed_cents` and the list of `commitment_ids`.

A plan can decay without anyone touching it. Whenever the reserved commitments on a `FUNDED` application no longer sum to its `total_program_cost_cents` — because a source reached its obligation threshold, was suspended, or expired, or because a counter moved the cost — the application flips `FUNDED → UNDERFUNDED` and its `version` increments. Re-assembly from `UNDERFUNDED` returns it to `FUNDED` with a fresh commitment set.

### 3.7. Acceptance, Pre-Closing Requirements and Recording the Deed

Acceptance is the branch join of the negotiation machine: it is reachable from two different states, by two different roles, locking two different prices, and it takes no request body at all. A `Landowner` accepts from `OFFER_ISSUED`, which requires `X-User-ID` to equal the application's `landowner_id` and requires the logical clock to be at or before `current_offer_expires_on`; the price locked into `agreed_price_cents` is `current_offer_cents`. An `AcquisitionOfficer` accepts from `COUNTERED`; the price locked into `agreed_price_cents` is `last_counter_cents`. Both branches require `funding_plan_status` to be exactly `FUNDED` and `funded_cost_cents` to equal `total_program_cost_cents`, and a plan that fails either test is rejected with `ERR_FUNDING_PLAN_INCOMPLETE`. Both branches also re-verify that the price being locked does not exceed `certified_easement_value_cents`, reporting `ERR_OFFER_EXCEEDS_CERTIFIED_VALUE` if it does.

The cascade that follows is the longest in the system, and every link is required. An `ACCEPTANCE` entry is appended to the negotiation log carrying the agreed price as its `amount_cents`, and the application moves to `ACCEPTED`. Every funding commitment on the application in `RESERVED` flips `RESERVED → OBLIGATED`, and `funding_plan_status` moves `FUNDED → OBLIGATED`. Each parent source has `committed_cents`, `reserved_cents` and `available_cents` recomputed and its `version` incremented. Any source whose `committed_cents` has now reached the floor of `authorized_cents` times `fully_obligated_threshold_pct` flips `ACTIVE → FULLY_OBLIGATED`; that flip lapses every remaining `RESERVED` commitment held against that source by *other* applications, with `lapse_reason` `SOURCE_FULLY_OBLIGATED`; and each of those other applications consequently flips `FUNDED → UNDERFUNDED` with its own `version` incremented. This is the intended serialisation point between competing plans that reserved against the same un-netted headroom.

Acceptance also opens the pre-closing file. Two closing requirements are always created — one of `requirement_type` `TITLE_COMMITMENT` and one of `BOUNDARY_SURVEY` — plus a third of `MORTGAGE_SUBORDINATION` if and only if the parcel's `mortgage_lienholder_name` is non-null, in which case that lienholder's name is copied onto the requirement as `lienholder_name`. The application's `closing_status` moves `NOT_APPLICABLE → PENDING_REQUIREMENTS`, `requirement_total` and `requirement_satisfied_count` are recomputed, and the application's `version` increments. The closing dimension runs over `NOT_APPLICABLE`, `PENDING_REQUIREMENTS`, `BLOCKED`, `CLEARED`, `CLOSED` and `CANCELLED`, with `CLOSED` and `CANCELLED` terminal, and it evolves entirely independently of the acquisition dimension once the application is `ACCEPTED`.

Each `ClosingRequirement` opens in `OUTSTANDING` with `submitted_by_user_id`, `reviewed_by_user_id`, `deficiency_note` and `waiver_reason` all null; its enumeration is `OUTSTANDING`, `SUBMITTED`, `SATISFIED`, `DEFICIENT` and `WAIVED`, with `WAIVED` terminal. An `AcquisitionOfficer` submits a requirement from `OUTSTANDING`, from `DEFICIENT` after a rejection, or even from `SATISFIED` when fresh work supersedes accepted work — though a resubmission of a `SATISFIED` requirement is only admissible while the application's `closing_status` is not yet `CLOSED`. Submitting a requirement that is already `SUBMITTED` or has been `WAIVED` is rejected with `ERR_INVALID_REQUIREMENT_STATE`. In all cases the application's `closing_status` must be `PENDING_REQUIREMENTS`, `BLOCKED` or `CLEARED`, and any other closing posture is `ERR_INVALID_CLOSING_STATE`. The payload is polymorphic and each field is mandatory for its own type and forbidden for the others. A `MORTGAGE_SUBORDINATION` submission must carry a `lienholder_name` equal to the parcel's `mortgage_lienholder_name`, and any submission of another type that carries `lienholder_name` at all is rejected — both failures report `ERR_LIENHOLDER_REQUIRED`. A `BOUNDARY_SURVEY` submission must carry `surveyed_acres`, strictly positive with 2 decimals, whose absolute difference from the parcel's `acres` is at most 0.50 acres; a larger discrepancy is `ERR_SURVEY_ACREAGE_MISMATCH`, and a submission of another type may not carry `surveyed_acres`. `exception_count` is a non-negative count of title exceptions defaulting to 0 and is only ever read for a `TITLE_COMMITMENT`.

A submission sets the requirement to `SUBMITTED`, records `submitted_by_user_id` as the submitting officer's `X-User-ID`, clears any `deficiency_note`, recomputes the application's `requirement_satisfied_count`, and increments the requirement's `version`. Because the requirement has left `DEFICIENT`, the application's `closing_status` may bubble `BLOCKED → PENDING_REQUIREMENTS` once no requirement on the application remains `DEFICIENT`; and because it may have left `SATISFIED`, the satisfied count can fall below the total and bubble `CLEARED → PENDING_REQUIREMENTS`.

A `ProgramAdmin` reviews a requirement with a `decision` of `ACCEPT` or `REJECT` plus an optional `deficiency_note` that becomes mandatory on rejection, subject to the segregation-of-duties gate of §2.9. The requirement must be in `SUBMITTED`, and reviewing one that is `OUTSTANDING`, `SATISFIED`, `DEFICIENT` or `WAIVED` is rejected with `ERR_INVALID_REQUIREMENT_STATE`. The requirement must belong to the application under which it is being acted upon, else `ERR_REQUIREMENT_SCOPE_MISMATCH`. Accepting a `TITLE_COMMITMENT` while its `exception_count` is greater than 0 is rejected with `ERR_TITLE_EXCEPTIONS_OUTSTANDING`. On `ACCEPT` the requirement moves `SUBMITTED → SATISFIED`, `reviewed_by_user_id` records the reviewer, and `requirement_satisfied_count` is recomputed. On `REJECT` the requirement moves `SUBMITTED → DEFICIENT`, stores the `deficiency_note`, records `reviewed_by_user_id`, and bubbles the application's `closing_status` `PENDING_REQUIREMENTS → BLOCKED`. Either way the requirement's `version` increments.

A survey — and only a survey — can be waived. A `ProgramAdmin` waives a requirement from `OUTSTANDING` or `DEFICIENT` — from any other status the waiver is `ERR_INVALID_REQUIREMENT_STATE` — by supplying a `waiver_reason`, and a waiver attempted on any `requirement_type` other than `BOUNDARY_SURVEY` is rejected with `ERR_REQUIREMENT_NOT_WAIVABLE`: title work and mortgage subordination are never waived. The requirement moves to `WAIVED`, the reason is stored, `requirement_satisfied_count` is recomputed — that counter counts requirements in `SATISFIED` *or* `WAIVED`, which is why a waiver can complete the file — and the requirement's `version` increments. A waiver from `DEFICIENT` can bubble the application through `BLOCKED → PENDING_REQUIREMENTS → CLEARED` in one step.

Clearance is a pure function of the children plus the funding dimension: the application's `closing_status` bubbles `PENDING_REQUIREMENTS → CLEARED` exactly when `requirement_total` is greater than 0, `requirement_satisfied_count` equals `requirement_total`, and `funding_plan_status` is `OBLIGATED`. Each such bubble increments the application's `version`.

Recording the deed is the `ProgramAdmin`'s final acquisition act and creates the `Easement`. It requires the application's `status` to be `ACCEPTED` and its `closing_status` to be `CLEARED` — anything else is `ERR_INVALID_CLOSING_STATE` — and it requires `funding_plan_status` to be `OBLIGATED`, so a plan whose commitments have lapsed or been released must be re-assembled first or the closing is rejected with `ERR_FUNDING_PLAN_STALE`. The payload carries `recorded_on`, which must be at or before the logical clock and may never be in the future; `protected_acres`, strictly positive with 2 decimals, which must equal the `surveyed_acres` of the application's accepted `BOUNDARY_SURVEY` requirement, or the parcel's `acres` when that requirement was waived, failing which the answer is `ERR_REQUIREMENT_SCOPE_MISMATCH`; `residential_rights_retained`, the count of building rights the landowner keeps, which must lie between 0 and the parcel's `baseline_dwelling_rights` inclusive, failing which the answer is `ERR_RESIDENTIAL_RIGHTS_OVERDRAWN`; `subdivision_permitted`, a flag defaulting to false; and `permitted_uses`, a non-empty array of distinct members drawn from `CROP_PRODUCTION`, `LIVESTOCK`, `DAIRY`, `ORCHARD`, `FARM_STAND`, `AGRITOURISM` and `FORESTRY`. The new easement's `parcel_id` must equal the application's `parcel_id`, else `ERR_EASEMENT_SCOPE_MISMATCH`.

The easement is created with `status` `RECORDED`, `stewardship_status` `MONITORING_CURRENT`, `compliance_status` `COMPLIANT`, `stewardship_hold` false and `impervious_used_sqft` at 0. Its `impervious_allowance_sqft` is derived by multiplying `protected_acres` by 43,560 square feet per acre and then by the program's `impervious_allowance_pct`, flooring the product to whole square feet. Its `residential_rights_extinguished` is the parcel's `baseline_dwelling_rights` less `residential_rights_retained`, so that the two always sum to the baseline. Its `next_monitoring_due_on` is projected from an anchor of `recorded_on` as described in §3.8. The application moves `ACCEPTED → CLOSED_RECORDED` and `closing_status` moves `CLEARED → CLOSED`. Every funding commitment in `OBLIGATED` flips `OBLIGATED → DISBURSED` and `funding_plan_status` moves `OBLIGATED → DISBURSED`; each touched source has `disbursed_cents` recomputed with its `version` incremented, while `committed_cents` and `available_cents` are deliberately unchanged, because a disbursed commitment still counts as committed. The parcel moves `UNDER_APPLICATION → ENCUMBERED` with its `version` incremented. The program's `total_preserved_acres` is recomputed and its `version` increments. The application's `version` increments.

A closing can instead be abandoned. A `ProgramAdmin` cancels from `closing_status` `PENDING_REQUIREMENTS`, `BLOCKED` or `CLEARED`, on an application whose `status` is `ACCEPTED`, by supplying a `reason`. `closing_status` becomes `CANCELLED`. Every commitment in `RESERVED` or `OBLIGATED` flips to `RELEASED` with `lapse_reason` `CLOSING_CANCELLED` and `funding_plan_status` becomes `RELEASED`; each touched source has its ledger recomputed so that `authorized_cents` still equals `available_cents` plus `committed_cents` exactly, with its `version` incremented, and any source whose `committed_cents` has fallen back below the obligation floor returns `FULLY_OBLIGATED → ACTIVE`. Every requirement still in `OUTSTANDING`, `SUBMITTED` or `DEFICIENT` becomes `WAIVED` with `waiver_reason` `CLOSING_CANCELLED`. The application itself moves `ACCEPTED → WITHDRAWN` with `withdrawal_reason` `CLOSING_CANCELLED`, the parcel returns `UNDER_APPLICATION → ELIGIBLE` with its `version` incremented, and the application's `version` increments. Cancelling a closing that is already `CLOSED` or `CANCELLED` is `ERR_INVALID_CLOSING_STATE`.

### 3.8. Stewardship: Monitoring, Impervious Coverage and Violation Resolution

Once recorded, an easement is stewarded indefinitely, and its three dimensions must be reasoned about separately. The deed dimension runs `RECORDED`, `AMENDED` and `TERMINATED`, with `TERMINATED` terminal. The monitoring dimension runs `MONITORING_CURRENT`, `MONITORING_DUE` and `MONITORING_DELINQUENT`. The compliance dimension runs `COMPLIANT`, `VIOLATION_OPEN`, `VIOLATION_CURED` and `VIOLATION_ESCALATED`. Alongside these, `stewardship_hold` is a boolean that is true exactly while some violation on the easement is in `OPEN`, `CURE_PLAN_ACCEPTED` or `ESCALATED`, and it is the flag that blocks new stewardship and amendment work. `open_violation_count` counts violations in those same three statuses, `pending_amendment_count` counts amendments in `UNDER_REVIEW`, and `amendment_count` counts amendments in `APPROVED`.

The **monitoring projection** works from an anchor: the easement's `last_monitored_on` when that is set, otherwise its `recorded_on`. `next_monitoring_due_on` is that anchor advanced by the program's `monitoring_interval_days` in whole days, with no timezone conversion. The posture is then read off the logical clock with both boundaries half-open: the easement is `MONITORING_CURRENT` while the clock is strictly before `next_monitoring_due_on`; it is `MONITORING_DUE` from the due instant itself up to but not including the due instant advanced by `monitoring_grace_days`; and it is `MONITORING_DELINQUENT` from that grace boundary onward. The due date itself is already due rather than current, and the grace boundary itself is already delinquent rather than due. Only easements in `RECORDED` or `AMENDED` are ever re-projected — a `TERMINATED` easement keeps whatever `stewardship_status` it last held — and only a `COMPLETED` monitoring visit ever moves the anchor, never a `SCHEDULED` or `CANCELLED` one. The sweep advances `MONITORING_CURRENT → MONITORING_DUE` and then `MONITORING_DUE → MONITORING_DELINQUENT` as the clock crosses those boundaries, incrementing the easement's `version` at each step, and it does so independently of compliance: a compliant easement and one with an open violation both traverse those edges on the same sweep.

New impervious coverage is metered against the allowance. A `ProgramAdmin` or `StewardshipMonitor` records it by supplying `added_impervious_sqft` and a `description` of the work; the requested amount is added to `impervious_used_sqft` only when the result stays within `impervious_allowance_sqft`, and the easement's `version` increments. A request that would push `impervious_used_sqft` above the allowance is rejected outright with `ERR_IMPERVIOUS_ALLOWANCE_EXCEEDED` and nothing is recorded.

A `StewardshipMonitor` schedules a site visit by naming the `easement_id` and a half-open window given by `window_start` inclusive and `window_end` exclusive, where the end must be strictly later than the start. The easement must be in `RECORDED` or `AMENDED`, else `ERR_INVALID_EASEMENT_STATE`, and its `stewardship_hold` must be false, else `ERR_EASEMENT_NOT_COMPLIANT` — an easement under hold accepts no new monitoring work. The visit must also belong to the program that recorded the easement, else `ERR_EASEMENT_SCOPE_MISMATCH`. Windows of visits on the same easement may not overlap, and because the window is half-open the test is that the new window's start falls strictly before an existing window's end while that existing window's start falls strictly before the new window's end; back-to-back visits touching at a single instant are therefore allowed. Only visits whose `status` is `SCHEDULED` occupy a window — `COMPLETED` and `CANCELLED` visits never block — and an overlap is rejected with `ERR_MONITORING_WINDOW_OVERLAP`. A new visit opens in `SCHEDULED` with `completed_at`, `observed_impervious_sqft`, `finding` and `cancellation_reason` all null and with an optional `notes` field defaulting to null; the enumeration is `SCHEDULED`, `COMPLETED` and `CANCELLED`, with the last two terminal.

Completing a visit requires it to be `SCHEDULED` and the logical clock to be at or after its `window_start`; a completion attempted early, or against a visit that is not scheduled, is `ERR_INVALID_VISIT_STATE`. The monitor supplies a non-negative `observed_impervious_sqft` and optional `notes`. The visit moves `SCHEDULED → COMPLETED` with `completed_at` set to the logical clock, and its `finding` is decided by a strict comparison: `CONFIRMED_VIOLATION` when `observed_impervious_sqft` is strictly greater than the easement's `impervious_allowance_sqft`, and `NO_ISSUE` otherwise. An observation exactly equal to the allowance is compliant; using a non-strict comparison here is the off-by-one wrong variant. Completion then resets the stewardship dimension only: `last_monitored_on` becomes the completion instant, `next_monitoring_due_on` is re-projected from that new anchor, and `stewardship_status` returns to `MONITORING_CURRENT` whether it was `MONITORING_DUE` or `MONITORING_DELINQUENT`. Compliance is decided separately by the finding.

On a `CONFIRMED_VIOLATION`, completion opens a violation automatically: a `Violation` is created against the easement, attributed to this visit through `monitoring_visit_id`, with `violation_type` `IMPERVIOUS_EXCEEDANCE`, with `excess_sqft` equal to the observed coverage less the allowance, and with `status` `OPEN`. That in turn flips the easement's `compliance_status` `COMPLIANT → VIOLATION_OPEN`, sets `stewardship_hold` to true, and recomputes `open_violation_count`; and because the hold is now on, every amendment on that easement in `UNDER_REVIEW` flips `UNDER_REVIEW → SUSPENDED` with `suspended_reason` `VIOLATION_OPEN` and `pending_amendment_count` is recomputed downward. Both the visit's and the easement's `version` increment. A scheduled visit may instead be cancelled with a `reason`, which is stored as `cancellation_reason`; the visit moves `SCHEDULED → CANCELLED`, its window is vacated for overlap purposes, and its `version` increments.

Violations may also be opened directly by a `StewardshipMonitor` or `ProgramAdmin` for the breaches a site visit does not measure numerically. The payload names the `easement_id` and a `violation_type` of `IMPERVIOUS_EXCEEDANCE`, `UNAUTHORIZED_SUBDIVISION`, `PROHIBITED_USE` or `EXCESS_DWELLING`, optionally an `excess_sqft` defaulting to 0, optionally a `monitoring_visit_id` attributing it to a visit, and optionally `notes`. The easement must be in `RECORDED` or `AMENDED`. When a `monitoring_visit_id` is supplied, that visit's own `easement_id` must equal the body's `easement_id`, else `ERR_VISIT_EASEMENT_MISMATCH`. An `IMPERVIOUS_EXCEEDANCE` opened this way must carry an `excess_sqft` strictly greater than 0. Opening a violation runs the same compliance cascade as an automatic one: `COMPLIANT → VIOLATION_OPEN`, `stewardship_hold` true, `open_violation_count` recomputed, `UNDER_REVIEW` amendments suspended with `suspended_reason` `VIOLATION_OPEN` and `pending_amendment_count` recomputed downward, and the easement's `version` incremented.

**Severity and the cure clock** are set once, at opening. The violation's `severity` — the enumeration is `MINOR` and `MAJOR` — is `MAJOR` when its `excess_sqft` is strictly greater than 2,000 square feet and `MINOR` otherwise, so an excess of exactly 2,000 is `MINOR` while 2,001 is `MAJOR`. `opened_on` is the logical clock at creation. A `MINOR` violation is given 180 days to cure and a `MAJOR` one only 90, and `cure_deadline_on` is `opened_on` advanced by that whole number of days. Because every non-impervious violation type carries an `excess_sqft` of 0, those types always open as `MINOR` with the 180-day clock. Deadlines are evaluated inclusively: a cure recorded exactly at `cure_deadline_on` is on time.

The resolution lifecycle runs `OPEN`, `CURE_PLAN_ACCEPTED`, `CURED` and `ESCALATED`, with `CURED` terminal. A monitor accepts a landowner's cure plan only from `OPEN`, supplying a `cure_plan_note`, and only while the logical clock is at or before `cure_deadline_on`; the violation moves `OPEN → CURE_PLAN_ACCEPTED`, the note is stored, and its `version` increments. A cure plan attempted on a violation that is `CURE_PLAN_ACCEPTED`, `ESCALATED` or `CURED` is `ERR_INVALID_VIOLATION_STATE`.

Cure verification is admissible from two states and closes the loop. From `CURE_PLAN_ACCEPTED` it additionally requires the clock to be at or before `cure_deadline_on`; from `ESCALATED` it carries no deadline test at all, because an escalated violation can still be remediated. The monitor may supply an optional `verification_note`. The violation moves to `CURED` with `cured_on` set to the logical clock. When the cured violation's `violation_type` is `IMPERVIOUS_EXCEEDANCE`, the easement's `impervious_used_sqft` is clamped back down to the lesser of its current value and `impervious_allowance_sqft`. `open_violation_count` is recomputed, and once it reaches 0 the easement's `compliance_status` moves to `VIOLATION_CURED` from either `VIOLATION_OPEN` or `VIOLATION_ESCALATED` and `stewardship_hold` returns to false. Both the violation's and the easement's `version` increment.

Time drives the two escalation edges. On a sweep, a violation in `OPEN` or `CURE_PLAN_ACCEPTED` whose `cure_deadline_on` now lies strictly in the past moves to `ESCALATED` with `escalated_on` set to the logical clock, and the easement's `compliance_status` moves `VIOLATION_OPEN → VIOLATION_ESCALATED` while `stewardship_hold` stays true. Conversely, the sweep closes the compliance cycle `COMPLIANT → VIOLATION_OPEN → VIOLATION_CURED → COMPLIANT`: an easement in `VIOLATION_CURED` with `open_violation_count` at 0 returns to `COMPLIANT` once the logical clock reaches or passes the latest `cured_on` among its violations advanced by 90 days with no new violation opened in the meantime. And where remediation never comes, the sweep terminates the easement: an easement whose `compliance_status` is `VIOLATION_ESCALATED` moves to `TERMINATED` once the clock reaches or passes the earliest `escalated_on` among its escalated violations advanced by 730 days. Termination returns the parcel `ENCUMBERED → ELIGIBLE` with its `version` incremented, recomputes the program's `total_preserved_acres`, and increments the easement's `version`.

### 3.9. Amending an Easement and Reversing an Amendment Exactly

Amendments are the controlled escape valve on a perpetual restriction, and the program's `amendment_policy` decides how forgiving that valve is. A `ProgramAdmin` drafts one against an easement in `RECORDED` or `AMENDED`, carrying the mandatory `expected_easement_version` of §2.7, an `amendment_type` of `IMPERVIOUS_INCREASE`, `BOUNDARY_ADJUSTMENT` or `RESIDENTIAL_RIGHT_RELOCATION`, and a non-negative `net_conservation_benefit_cents` giving the appraised conservation benefit of the change. Two type-specific fields complete the payload and each is mandatory for its own type and forbidden for the others. An `IMPERVIOUS_INCREASE` must carry `requested_impervious_sqft`, strictly positive and strictly greater than the easement's current `impervious_allowance_sqft`; a request that is not strictly greater is rejected with `ERR_IMPERVIOUS_ALLOWANCE_EXCEEDED`. A `RESIDENTIAL_RIGHT_RELOCATION` must carry a strictly negative `residential_rights_delta` whose addition to the easement's `residential_rights_retained` leaves a result of at least 0; a delta that would drive retained rights below zero is rejected with `ERR_RESIDENTIAL_RIGHTS_OVERDRAWN`. For every other type `residential_rights_delta` must be 0 or absent, and it defaults to 0.

Drafting first rescinds: every amendment already on that easement whose `status` is `DRAFT` flips `DRAFT → RESCINDED` with `rescission_reason` `SUPERSEDED_BY_NEWER_DRAFT` and its `version` increments. The new amendment is then created in `DRAFT` with `applied_rights_delta` at 0, `applied_impervious_sqft` null, and `suspended_reason`, `decision_reason` and `rescission_reason` all null. The easement's `version` increments. The amendment lifecycle is `DRAFT`, `UNDER_REVIEW`, `SUSPENDED`, `APPROVED`, `REJECTED` and `RESCINDED`, of which `REJECTED` and `RESCINDED` are terminal.

Submitting a draft for review moves it `DRAFT → UNDER_REVIEW` and is where the compliance gate bites. The amendment must be in `DRAFT`, and submitting one that is already `UNDER_REVIEW`, `SUSPENDED`, `APPROVED`, `REJECTED` or `RESCINDED` is rejected with `ERR_INVALID_AMENDMENT_STATE`. The easement's `stewardship_hold` must be false, and its `compliance_status` must be admissible under the program's policy: a `STRICT` program requires `compliance_status` to be exactly `COMPLIANT`, while a `CONDITIONAL` program also admits `VIOLATION_CURED`. Any other posture is rejected with `ERR_EASEMENT_NOT_COMPLIANT`. A successful submission recomputes the easement's `pending_amendment_count` and increments both the easement's and the amendment's `version`.

An amendment under review is fragile. As described in §3.8, a violation reaching `OPEN` on the easement flips every `UNDER_REVIEW` amendment `UNDER_REVIEW → SUSPENDED` with `suspended_reason` `VIOLATION_OPEN` and drives `pending_amendment_count` downward, each suspended amendment's `version` incrementing. Returning a suspended amendment to review moves it `SUSPENDED → UNDER_REVIEW`, clears `suspended_reason`, recomputes `pending_amendment_count` upward and increments the easement's and the amendment's `version` — but it applies the same compliance gate as submission, requiring `stewardship_hold` to be false and `compliance_status` to be `COMPLIANT` under a `STRICT` policy or either `COMPLIANT` or `VIOLATION_CURED` under a `CONDITIONAL` one. Since a freshly cured easement sits in `VIOLATION_CURED`, only a `CONDITIONAL` program can reinstate immediately; a `STRICT` program must wait for the sweep to return the easement to `COMPLIANT` ninety days after the cure. Reinstating an amendment that is not `SUSPENDED` is `ERR_INVALID_AMENDMENT_STATE`.

Deciding an amendment requires it to be `UNDER_REVIEW` — any other status is `ERR_INVALID_AMENDMENT_STATE`, so a `SUSPENDED` amendment must be reinstated before it can be decided — and requires the easement's `stewardship_hold` to be false, and the decision carries a `decision` of `APPROVE` or `REJECT` plus an optional `reason` that becomes mandatory on rejection and is stored as `decision_reason`. Approval additionally requires `net_conservation_benefit_cents` to be strictly greater than 0 — a zero-benefit amendment may be drafted and submitted but can never be approved — and subdivision rights are never granted by amendment at all; either attempt is rejected with `ERR_NO_NET_CONSERVATION_BENEFIT`.

On approval the amendment moves `UNDER_REVIEW → APPROVED`, the easement's deed dimension flips to `AMENDED` from either `RECORDED` or `AMENDED`, and `amendment_count` is recomputed. The type then decides what is rewritten. For an `IMPERVIOUS_INCREASE`, the easement's `impervious_allowance_sqft` is set to the amendment's `requested_impervious_sqft` and `applied_impervious_sqft` records the same value, so the reversal has an exact record of what it changed. For a `RESIDENTIAL_RIGHT_RELOCATION`, the signed `residential_rights_delta` is added to `residential_rights_retained` and subtracted from `residential_rights_extinguished`; since the delta is negative, retained rights fall and extinguished rights rise by the same magnitude, so their sum still equals the parcel's `baseline_dwelling_rights`, and `applied_rights_delta` records the delta that was applied. A `BOUNDARY_ADJUSTMENT` rewrites neither field. `pending_amendment_count` is recomputed and both the easement's and the amendment's `version` increment. On rejection the amendment moves `UNDER_REVIEW → REJECTED` with `decision_reason` stored, `pending_amendment_count` is recomputed, and the easement's and amendment's `version` increment.

Rescission is the exact inverse of approval and is available only from `APPROVED`, with a mandatory `reason` stored as `rescission_reason`. Where `applied_impervious_sqft` is non-null, the easement's `impervious_allowance_sqft` is not merely decremented but re-derived from first principles: `protected_acres` multiplied by 43,560 square feet per acre and then by the program's `impervious_allowance_pct`, floored to whole square feet. Where `applied_rights_delta` is non-zero, `applied_rights_delta` is subtracted from `residential_rights_retained` and added to `residential_rights_extinguished`, restoring the exact pre-approval pair and again conserving the baseline total. Both `applied_rights_delta` and `applied_impervious_sqft` are then cleared, to 0 and null respectively. `amendment_count` is recomputed, and when it reaches 0 the easement's deed dimension returns `AMENDED → RECORDED`. Both `version` counters increment. Rescinding an amendment that is not `APPROVED` is `ERR_INVALID_AMENDMENT_STATE`.
