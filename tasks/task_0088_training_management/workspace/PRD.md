# Training Management API — Product Requirements Document

## 1. Introduction

The Training Management API governs the entire enterprise learning lifecycle for a workforce of internal trainees and the instructors — both employees and contracted experts — who deliver their courses. From the moment a course designer drafts a new offering through the publication review chain, into the scheduling of classroom or virtual sessions, the eligibility-gated enrollment of trainees, the multi-channel verification of attendance, post-session examinations and surveys, and ultimately the accrual of credits against cycle-based job-role requirements, every transition must be coordinated under a single consistent rulebook.

Several intertwined concerns motivate the design. Course content changes over time and existing sessions must remain pinned to the exact version their participants were promised. Cancellations carry both operational and financial consequences depending on how close to the start instant they occur. Charged courses demand managerial approval, certificate templates, and shorter waitlists. Credits accumulate against rolling cycles and missing the required floor must surface as a timely warning rather than a year-end surprise. Synchronization with external HR, instant-messaging, and learning-content-platform systems is asynchronous but auditable. The API encodes these requirements as a coherent set of resources, state machines, and validation rules — described in the sections that follow — so that an implementer building against this specification can faithfully reproduce the operational semantics expected by every role that touches the system.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

All interactions with the API must be authenticated through a set of mandatory HTTP headers. Each request must include `X-User-ID` to identify the acting user and `X-User-Role` to specify their operational capacity. The only exception is the public certificate-verification endpoint described in §3 and listed in §4, which serves anonymous traffic. If either header is missing or empty on any other endpoint, the request is rejected with `ERR_AUTH_REQUIRED`. If the supplied `X-User-Role` is not one of the recognized role names, the request is rejected with `ERR_FORBIDDEN_ROLE`; the same error is returned when a role attempts an operation outside its permitted set.

The system recognizes four authenticated roles: `TrainingAdmin`, `CourseDesigner`, `DepartmentManager`, and `Trainee`.

When `X-User-Role` is `Trainee`, `X-User-ID` is the `id` of the acting `Trainee` row. Any ownership-scoped operation — self-enrolling, cancelling one's own enrollment, checking in for one's own session, taking exams, submitting evaluations, renewing one's certificate, and listing one's own enrollments, credit pools, certificates, or `Trainee` record — compares the resource's `trainee_id` (or, for `Trainee` reads, the resource's own `id`) to `X-User-ID`. When `X-User-Role` is `TrainingAdmin`, `CourseDesigner`, or `DepartmentManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example, as the `actor_id` on an `AuditLog` row written by a transition the role performed) but does not compare it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

For endpoints that return lists of resources, pagination is controlled via query parameters. The `limit` parameter specifies the maximum number of items to return. If not provided, it defaults to 10, with a minimum of 1 and a maximum of 100. The `offset` parameter specifies the number of items to skip and defaults to 0, with a minimum of 0. Any list request with `limit` or `offset` outside these bounds is rejected with `ERR_INVALID_PAGINATION`.

Unless otherwise specified, all list endpoints return resources sorted by their creation timestamp in ascending order.

Paginated and non-paginated list-based responses include the following fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. Common Resource Properties

Most primary resources in the system — `CourseCategory`, `Course`, `Instructor`, `Session`, `Classroom`, `OnlineRoom`, `Enrollment`, `Trainee`, `CreditPool`, `CertificateTemplate`, and `Certificate` — include a standard set of system-managed fields:

- `id` (string): a unique, server-minted identifier formatted as a UUID. The identifier carries no type prefix; it is the bare UUID itself.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits indicating when the resource was first created.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits indicating when the resource was last modified. This field advances on every mutation, including server-driven state transitions, ledger-style recomputations of derived fields, and waitlist-position shifts.
- `version` (integer): a server-managed integer that increments by one with every mutation to the resource. It supports optimistic concurrency control as described in §2.5.

A second class of resources is immutable, semi-derived, or append-only: `CourseVersion`, `InstructorAvailability`, `CheckIn`, `ExamAttempt`, `EvaluationSurvey`, `CreditAdjustment`, `SyncEvent`, and `AuditLog`. These rows still receive an `id` (UUID) and a `created_at` timestamp, but they expose neither `updated_at` nor `version`; mutations targeted at them are not part of the API surface.

### 2.5. Optimistic Concurrency Control

Endpoints that update an existing resource (the `PATCH` operations on categories, courses, instructors, and similar entities) accept an optional `version` field in their request body. When the client supplies a `version`, the server compares it to the current row; if the values differ, the write is rejected with `ERR_VERSION_CONFLICT`. When the `version` field is omitted from the body, the server processes the mutation without the optimistic-locking check. Successful mutations always increment `version` by one and refresh `updated_at`, regardless of whether the request carried a `version`. The same `ERR_VERSION_CONFLICT` is also the outcome of the credit-pool race described in §2.11: when two `CreditAdjustment` rows are applied to the same pool concurrently, the loser of the compare-and-set on `credit_pool.version` receives this error and must retry, while the eventually accumulated balance reflects the exact arithmetic sum of every applied delta.

### 2.6. Hierarchical Consistency and Side Effects

State transitions across this domain are rarely isolated. Publishing a course mints a fresh course-version snapshot and supersedes any prior published version. Completing a session walks every confirmed enrollment, computes attendance verdicts, awards credits, recalculates the credit-pool aggregate, and — where the course carries an eligible certificate template — issues certificates. Cancelling a session cascades down to every non-terminal enrollment, releases instructor blocks, and may mark a cancellation fee. Each such side effect is itself a mutation: the affected resource's `updated_at` advances and its `version` increments. When a confirmed enrollment is cancelled and a waitlist promotion fires, both the freshly-promoted row and the session's counters bump their versions; downstream `waitlist_position` reshuffles on other waitlisted rows likewise refresh `updated_at` and bump `version` on each row touched.

### 2.7. Nested Resource Retrieval

For endpoints whose URL contains multiple resource identifiers (such as session-scoped check-ins or course-scoped version listings), the system validates each identifier in left-to-right order. The first identifier that fails to resolve to an existing row terminates the request immediately with `ERR_RESOURCE_NOT_FOUND`, even when subsequent segments are also invalid. The same error covers the case of a missing identifier on any single-segment retrieval. Foreign-key identifiers carried inside a request body are not part of the URL hierarchy; failures to resolve them produce `ERR_REFERENCE_NOT_FOUND` instead.

### 2.8. Precision, Rounding, and Boundary Conventions

The system computes three distinct numeric quantities with three distinct precision rules. Credits awarded per enrollment, credit-pool accumulations, and course `credit_value` are stored with one fractional digit and rounded using the round-half-up method when intermediate arithmetic produces more precision. Instructor fees, exam scores, and evaluation aggregates are stored with two fractional digits, also rounded half-up. Time fractions and credit fractions used in the shortfall-warning trigger are evaluated at full floating-point precision before comparison against their respective thresholds.

Time-interval comparisons throughout the system follow the half-open convention `[start, end)`: the start instant is inclusive and the end instant is exclusive. Pass/fail thresholds and shortfall triggers are inclusive on one side and exclusive on the other in a manner spelled out where each rule is described.

### 2.9. Validation Ordering

When multiple validations could fire for a single request, they are evaluated in priority order so that authentication and existence problems surface before business semantics: the absence of `X-User-ID`/`X-User-Role` first (returning `ERR_AUTH_REQUIRED`), then the role membership check (`ERR_FORBIDDEN_ROLE`), then path-identifier existence (`ERR_RESOURCE_NOT_FOUND`), then body foreign-key existence (`ERR_REFERENCE_NOT_FOUND`), then state-machine preconditions (`ERR_INVALID_STATE`, plus state-machine-aware specializations such as `ERR_COURSE_NOT_ON_SHELF` when a session is being created against a non-on-shelf course), then business-safety checks (instructor blacklist, expertise mismatch), then business-referential eligibility (trainee prerequisites, job level, status), then time-bound conflicts (classroom overlap, online-room aggregate-capacity, instructor availability, enrollment deadline), then the remaining business constraints (capacity vs. waitlist, duplicate enrollment, certificate-template presence on charged-course publish, prerequisite-cycle detection, category-cycle detection, check-in coherence, exam completeness, renewal-window legality, non-negative accumulated credits), and finally pagination range and the OCC version check on `PATCH`. The priority ordering ensures, for example, that a missing certificate template on a charged course publish (priority 16) cannot mask an earlier state error (priority 5), and that a stale `version` (priority 24) does not preempt a permission rejection.

### 2.10. Time-Gated State Advancement

Several state transitions are driven not by an explicit client action but by the passage of time: the enrollment deadline closes enrollment, the start instant begins the session, the certificate renewal window opens an expiring-soon state, and the certificate expiry instant retires the certificate. To make these transitions testable and deterministic, the system exposes two administrative capabilities. A clock-advance capability accepts a single body field `now` — an ISO 8601 instant — and sets the server's logical clock to that value; the new clock then governs every subsequent comparison against `enrollment_deadline`, `start_at`, `end_at`, `expires_at`, and renewal windows. A sweep capability evaluates every time-gated transition against the current clock and applies them in bulk: any `ENROLLMENT_OPEN` session whose deadline has passed advances to `ENROLLMENT_CLOSED`; any `ENROLLMENT_CLOSED` session whose start instant has arrived advances to `IN_PROGRESS`; any `VALID` certificate within its renewal window advances to `EXPIRING_SOON` (emitting a reminder synchronization event); any `EXPIRING_SOON` or `VALID` certificate whose expiry instant has passed advances to `EXPIRED`; and the credit-pool warning evaluation described in §2.11 runs for every pool.

### 2.11. Credit Pools, Warnings, and Shortfall Detection

Every trainee may hold one or more credit pools, each scoped to a cycle. A pool's `cycle_kind` is either `ANNUAL` (a one-year window) or `BIENNIAL` (a two-year window); `cycle_end` is computed at creation as one year past `cycle_start` for an annual cycle, or two years past it for a biennial cycle, and is exclusive — credits earned for sessions whose start instant equals `cycle_end` belong to the next pool. The pool's `required_credits` floor is fixed at creation according to the trainee's job-role policy. The pool's `accumulated_credits` is a derived aggregate: the sum of every `final_credit` from completed and failed enrollments belonging to this trainee whose session start instant falls within the half-open window `[cycle_start, cycle_end)`, plus the algebraic sum of every `delta` from credit adjustments on this pool. Both aggregates recompute on enrollment status transitions into completion-or-failure and on every credit-adjustment creation.

The system raises a single, debounced shortfall warning per pool. The warning fires only when both conditions hold simultaneously: the fraction of the cycle's time remaining (computed as the cycle-end instant minus the current clock, divided by the cycle's full span) is at or below one quarter, and the fraction of credits already earned (accumulated divided by required) is strictly less than one half. Once the warning fires, the pool's `shortfall_warning_emitted` flag flips to true and the system emits a synchronization event of type `credit.shortfall_warning` originating from the `IM` source-system; the same pool will not emit a second warning while its flag remains true. The two thresholds are intentionally asymmetric: the time comparison is inclusive at one quarter, while the credit comparison is strictly less than one half.

### 2.12. Course-Version Pinning

When a session is created, the system snapshots a pointer to the course's currently published version — specifically the `CourseVersion` whose `version_no` equals the course's `current_version_no` and whose `status` is `PUBLISHED` — into the session's `pinned_course_version_id`. This pointer is immutable for the life of the session. Subsequent publishes of the course (which create new course-version rows and supersede the prior published row) do not retroactively change the pinned version for any existing session, and credit-award calculations during session completion read the snapshotted `credit_value`, `duration_hours`, `objective`, `outline`, `prerequisite_course_ids`, and `tags` from the pinned version rather than from the current course row. Instructor pricing — `hourly_rate` and `travel_cost` — is likewise read from the snapshot frozen at session creation, not from the current instructor record.

## 3. Business Logic & Workflows

### 3.1. The Course Catalog: Categories, Versions, and the Publication Workflow

The catalog is organized into a hierarchy of categories. Each `CourseCategory` is identified by a display `name` (between 1 and 80 characters, unique among siblings sharing the same parent) and an optional `parent_id` linking to another category. Root categories have a null `parent_id`. The system maintains a computed `depth` field — zero for roots and recomputed when a category is reparented — and refuses any reparenting that would either introduce a cycle through the `parent_id` chain or push `depth` past 4 (so a category tree may have at most five levels in total); such attempts are rejected with `ERR_CATEGORY_CYCLE`. Each category also carries a denormalized `course_count`: the number of `Course` rows whose `category_id` equals this category's `id`, regardless of the course's status. This count is refreshed whenever a course is created, deleted, or moved between categories, and whenever a category is reparented in a way that affects its course set.

A `Course` is the catalog primitive. Course authoring begins with a `CourseDesigner` who supplies a stable human-readable `code` — matching the pattern of two-to-six uppercase letters, a hyphen, and three-to-five digits, and globally unique — together with a `title` (1 to 200 characters), the parent `category_id`, the free-text `objective` and `outline` (the outline accepts markdown), a nominal `duration_hours` between 0.5 and 40.0 with one fractional digit, and the base `credit_value` between 0 and 20.0 with one fractional digit. Optionally the designer supplies an array of `prerequisite_course_ids` (at most five entries, with no cycles through the prerequisite graph reachable within five hops) and a `tags` array of free-form lowercase strings (each tag between 2 and 32 characters drawn from lowercase letters, digits, and hyphens, with at most ten tags overall). The `is_charged` flag defaults to false; setting it to true marks a course that requires managerial approval at enrollment time and demands a certificate template before publication. The course begins life with `status` equal to `DRAFT` and `current_version_no` equal to zero.

A draft course can be edited freely by a `CourseDesigner` or by a `TrainingAdmin`. Edit operations accept any subset of `title`, `objective`, `outline`, `duration_hours`, `prerequisite_course_ids`, `tags`, `credit_value`, `is_charged`, and the optional `version` for optimistic locking; the course `code` is immutable after creation. A prerequisite set that would form a cycle through any chain of length at most five is rejected with `ERR_PREREQUISITE_CYCLE`, both at creation and at edit time.

Once the designer is satisfied, submitting the course for review transitions it from `DRAFT` to `PENDING_REVIEW`. The submission requires that `objective` is non-empty, that `outline` is non-empty, and that `credit_value` is strictly greater than zero. A `TrainingAdmin` then either rejects the submission, returning the course from `PENDING_REVIEW` to `DRAFT`, or publishes it, transitioning it from `PENDING_REVIEW` to `ON_SHELF`. The publish action carries three indivisible side effects: a new `CourseVersion` row is minted whose `version_no` equals one plus the largest existing `version_no` for the course, whose `status` is `PUBLISHED`, and whose `snapshot` freezes the current values of `objective`, `outline`, `duration_hours`, `prerequisite_course_ids`, `tags`, and `credit_value`; the parent course's `current_version_no` is updated to point at the new version; and if a prior `CourseVersion` with `status` equal to `PUBLISHED` existed, that row is transitioned to `SUPERSEDED` as a parallel state-machine step. The new version's `published_at` is stamped at the moment of publication. Charged courses (those with `is_charged` true) cannot be published unless at least one `CertificateTemplate` exists for them; an attempt to do so is rejected with `ERR_CERT_TEMPLATE_MISSING`. When two publish operations race on the same course and both attempt to mint a fresh version, the system serializes the monotonic increment on `current_version_no` and the loser receives `ERR_COURSE_VERSION_RACE`; this guarantees that two new versions cannot share the same `version_no`.

A published course can be taken `OFF_SHELF` by a `TrainingAdmin`, which has no effect on sessions already in `SCHEDULED` or `ENROLLMENT_OPEN` (each continues with its own `pinned_course_version_id`) but blocks creation of new sessions referencing this course. Republishing — from `OFF_SHELF` back to `ON_SHELF` — is also a publish call; it succeeds only when a `CourseVersion` with `status` equal to `PUBLISHED` already exists for the course, and it simply unblocks new session creation rather than minting a new version. Finally, an `OFF_SHELF` course can be archived to `ARCHIVED` when no session referencing it remains in any state other than `COMPLETED` or `CANCELLED`; the `ARCHIVED` state is terminal and renders the course read-only for any further session-creation or enrollment reference.

Course rows are never themselves audited — only `ENROLLMENT` and `CREDIT_POOL` subjects appear in the audit log, as described in §3.7.

### 3.2. Instructors, Their Schedules, and Roster Status

An `Instructor` carries an internal-versus-external distinction in `instructor_type` (one of `INTERNAL` or `EXTERNAL`), a display `full_name`, a list of `expertise_tags` (lowercase strings used to match against course tags), a list of `qualifications` (free-form certificate names), a `hourly_rate` and a `travel_cost`, both non-negative decimals with two fractional digits, and a derived `avg_evaluation_score` averaged across the `EvaluationSurvey.aggregate_score` values of every survey submitted for that instructor's completed sessions (null when no completed evaluations exist). Internal instructors must have an `hourly_rate` of zero and a `travel_cost` of zero — internal time is tracked but never paid out. External instructors carry positive rates and a flat per-session travel cost.

An instructor's roster `status` begins as `ACTIVE` and may move to `BLACKLISTED` or `RETIRED`. Blacklisting requires a non-empty `blacklist_reason`; reinstating returns the instructor to `ACTIVE` and may be performed by a `TrainingAdmin`. A blacklisted or retired instructor cannot be assigned to a session: any session creation or update that tries to do so is rejected with `ERR_INSTRUCTOR_BLACKLISTED`. Additionally, the instructor's `expertise_tags` must overlap with the course's `tags` by at least one entry; otherwise the assignment is rejected with `ERR_INSTRUCTOR_EXPERTISE_MISMATCH`.

An instructor's availability calendar is built from `InstructorAvailability` rows. Each row carries an `instructor_id`, a `start_at` (inclusive) and an `end_at` (strictly after `start_at`, exclusive), and a `kind` of either `AVAILABLE` or `BLOCKED`. For a session to be scheduled against an instructor, at least one `AVAILABLE` window must fully cover the session's `[start_at, end_at)` interval, and no `BLOCKED` window may overlap that interval at all. Failure on either side returns `ERR_INSTRUCTOR_UNAVAILABLE`.

### 3.3. Classrooms, Online Rooms, and Session Scheduling

A `Classroom` is a physical seat resource defined by a unique `name`, a `capacity` of at least one seat, a roster `status` of one of `ACTIVE`, `MAINTENANCE`, or `RETIRED`, and a `setup_buffer_minutes` (default 30, between 0 and 240 inclusive) representing the minimum gap that must elapse after one session in this classroom before another may start. An `OnlineRoom` is the virtual analogue: it carries a `platform` (such as `zoom` or `teams`), a static `join_url`, a `max_participants` cap of at least one, and a `status` of `ACTIVE` or `RETIRED`.

A `Session` is a single scheduled offering of a course. The creator — a `TrainingAdmin` — supplies the parent `course_id`, the `instructor_id`, a delivery `mode` of `ONSITE`, `ONLINE`, or `HYBRID`, optionally a `classroom_id`, optionally an `online_room_id`, the `start_at` (inclusive) and `end_at` (strictly after `start_at`, exclusive), the integer `capacity` between 1 and 500, an optional `waitlist_capacity` (default 10, between 0 and 100 inclusive), and the `enrollment_deadline` instant — which must fall strictly before `start_at`. The room assignment must match the delivery mode: an `ONSITE` session requires a `classroom_id` and forbids an `online_room_id`; an `ONLINE` session requires an `online_room_id` and forbids a `classroom_id`; a `HYBRID` session requires both. The `end_at` must equal `start_at` plus the course's `duration_hours` to within a one-minute tolerance.

The session is created in `status` `SCHEDULED`, and four side effects fire at creation: the parent course must be `ON_SHELF` or the request fails with `ERR_COURSE_NOT_ON_SHELF`; the session's `pinned_course_version_id` is set to the `CourseVersion.id` whose `version_no` equals the course's `current_version_no` (and that version's snapshot, including `credit_value`, `duration_hours`, `objective`, `outline`, `prerequisite_course_ids`, and `tags`, is frozen for the life of the session); the counters `enrolled_count` and `waitlist_count` start at zero; and `cancellation_fee_charged` starts at false.

Three resource-conflict rules guard the creation step and any subsequent update of `start_at`, `end_at`, `classroom_id`, `online_room_id`, or `instructor_id`. The classroom non-overlap rule is the strictest: for a given `classroom_id`, no other session whose `status` is not `CANCELLED` may have a time interval that overlaps the candidate's interval extended by the classroom's `setup_buffer_minutes` on its end side. Concretely, treat each existing session as occupying the half-open window from its `start_at` to its `end_at` plus `setup_buffer_minutes`, and treat the candidate the same way; if these two windows share any positive duration of overlap, the request is rejected with `ERR_CLASSROOM_CONFLICT`. The online-room rule is gentler: multiple sessions may share the same `online_room_id` in overlapping windows provided that the sum of their `capacity` values at any single point in time does not exceed the online room's `max_participants`. Time intervals are half-open `[start_at, end_at)` and no setup buffer applies to online rooms; a violation returns `ERR_ONLINE_ROOM_CAPACITY_EXCEEDED`. The instructor availability rule is described in §3.2 and reuses the half-open interval convention.

A `TrainingAdmin` opens enrollment with the open-enrollment action, transitioning the session from `SCHEDULED` to `ENROLLMENT_OPEN`. The transition requires that the parent course is currently `ON_SHELF` (a cross-entity dependency between session and course) and that the current clock is strictly before `enrollment_deadline`. From this point the session is visible to trainees searching the catalog and is open for self-enrollment or assigned enrollment per §3.4.

As the clock advances, the sweep capability drives two further transitions automatically. When the current time reaches or passes `enrollment_deadline`, an `ENROLLMENT_OPEN` session moves to `ENROLLMENT_CLOSED`; from that moment on, any attempt to create an enrollment for this session is rejected with `ERR_ENROLLMENT_DEADLINE_PASSED`. When the current time reaches or passes `start_at`, an `ENROLLMENT_CLOSED` session moves to `IN_PROGRESS`, at which point the check-in endpoints become active for the duration of the session.

Completing a session is the heart of the system's cascade machinery and is described in §3.5. A session may also be cancelled by a `TrainingAdmin` from any non-terminal state. Cancellation triggers a uniform cascade: every `Enrollment` belonging to this session whose `status` is currently `PENDING_APPROVAL`, `CONFIRMED`, or `WAITLISTED` is transitioned to `CANCELLED`; the corresponding `InstructorAvailability` blocks for this session are released so the instructor's calendar reclaims the slot; and if the moment of cancellation is at or past `start_at` minus 48 hours, the session's `cancellation_fee_charged` is set to true, with the fee determined by the calculation in §3.6. A session cancelled while already `IN_PROGRESS` always has `cancellation_fee_charged` set to true because that state implies the start instant has already passed. Cancellation racing with a completion attempt is serialized at the level of `session.status`: exactly one of the two operations succeeds, and the loser receives `ERR_INVALID_SESSION_STATE`.

### 3.4. Trainee Enrollment, Eligibility, and the Waitlist

A `Trainee` carries an `employee_no` unique to the HR system, a display `full_name`, a `department` code, a `job_level` integer between 1 and 15 inclusive, and a `status` of `ACTIVE`, `ON_LEAVE`, or `OFFBOARDED`. Only `ACTIVE` trainees are eligible to enroll in a session; the eligibility check also requires that the trainee's `job_level` meets or exceeds the course's minimum (defaulting to 1 when the course imposes no explicit floor), and that every entry in the course's `prerequisite_course_ids` corresponds to a prior `Enrollment` of the same trainee whose `status` is `COMPLETED` or `FAILED` and whose `final_credit` is strictly positive. Any one of these checks failing returns `ERR_PREREQUISITE_NOT_MET`.

Creating an `Enrollment` requires a `session_id`, a `trainee_id`, and an enrollment `mode` of either `SELF` or `ASSIGNED`. A `Trainee` may create only `SELF` enrollments and only when `trainee_id` equals `X-User-ID`; a `DepartmentManager` may create either `SELF` or `ASSIGNED` enrollments on behalf of trainees in their department. At the moment of creation, the session must already be `ENROLLMENT_OPEN` and the current clock must be strictly before `enrollment_deadline`, or the request is rejected with `ERR_ENROLLMENT_DEADLINE_PASSED`. The same trainee cannot hold two non-`CANCELLED` enrollments for the same session — a second attempt returns `ERR_DUPLICATE_ENROLLMENT`. If the session is already at capacity (its `enrolled_count` equals `capacity`) and its `waitlist_count` equals `waitlist_capacity`, the request is rejected with `ERR_SESSION_AT_CAPACITY`.

The starting status for a newly created enrollment depends on the course and the session. For an uncharged course, when the session has open capacity (`enrolled_count` is strictly below `capacity`), the enrollment is auto-confirmed: it begins life in `CONFIRMED` directly and the session's `enrolled_count` is incremented by one. For a charged course, the enrollment begins life in `PENDING_APPROVAL` regardless of capacity and awaits an explicit approve or reject by a `DepartmentManager`. In either case, when the session is at capacity but has room on the waitlist (`waitlist_count` is strictly below `waitlist_capacity`), the enrollment is placed in `WAITLISTED` with a one-indexed `waitlist_position` equal to the new `waitlist_count` after increment.

Approval by a `DepartmentManager` advances a `PENDING_APPROVAL` enrollment to `CONFIRMED`. The transition requires that the session is `ENROLLMENT_OPEN`, that the session still has open capacity (`enrolled_count` is strictly below `capacity`), and that the trainee passes the eligibility checks above. On success the session's `enrolled_count` is incremented and an `AuditLog` row with `subject_kind` equal to `ENROLLMENT` is written. Rejection by a `DepartmentManager` advances a `PENDING_APPROVAL` enrollment to `CANCELLED`, also writing an audit row. Cancellation of a `CONFIRMED` enrollment by the trainee or by a manager requires that the current clock is strictly before the session's `start_at`; the operation decrements `enrolled_count` and writes an audit row.

The waitlist is FIFO by `waitlist_position`. When a `CONFIRMED` enrollment is cancelled and the waitlist is non-empty and the session is still `ENROLLMENT_OPEN` with the clock strictly before `enrollment_deadline`, the head of the waitlist — the row with the lowest `waitlist_position` — is promoted to `CONFIRMED` as a cascade hop: its status changes, the session's `waitlist_count` is decremented and its `enrolled_count` is incremented, and every remaining `WAITLISTED` row has its `waitlist_position` decreased by one to preserve the contiguous numbering. The cascade hop itself can race with an administrative promotion of a different row; serialization on `enrollment.status` ensures at most one waitlist row is promoted per freed seat, and the loser of the race remains `WAITLISTED` and receives `ERR_WAITLIST_PROMOTION_RACE`. When a `WAITLISTED` enrollment is cancelled directly, `waitlist_count` is decremented and `waitlist_position` is decreased by one for every row whose `waitlist_position` was higher than the cancelled row's.

When two enrollments race for the last open seat in a session, the system serializes the increment on `enrolled_count` using a compare-and-set against `session.version`: exactly one enrollment becomes `CONFIRMED`, and the loser is placed on the waitlist when waitlist capacity permits; if the waitlist is also full at that instant, the loser is rejected with `ERR_SESSION_AT_CAPACITY`.

### 3.5. Attendance, Examination, Evaluation, and Session Completion

A session in `IN_PROGRESS` accepts check-in submissions through three verification channels. A `CheckIn` row carries the parent `session_id`, the `enrollment_id` of the trainee checking in, a `channel` of `QR`, `FACE`, or `IP_RANGE`, a `source_value` whose semantics depend on the channel, and a server-stamped `checked_in_at` timestamp. When the channel is `QR`, the `source_value` must be a server-issued QR token; when the channel is `FACE`, the `source_value` must be a non-empty image reference; when the channel is `IP_RANGE`, the `source_value` must be an IPv4 dotted-quad falling inside either the 10.0.0.0/8 range or the 192.168.0.0/16 range. A mismatch on any of these — an invalid QR token, an IP outside the allowed CIDR blocks, or an empty image reference — is rejected with `ERR_CHECKIN_INVALID`. Periodic in-session sampling combines these check-ins into the enrollment's `attendance_status`, one of `NOT_RECORDED`, `PRESENT`, `ABSENT`, or `PARTIAL`.

After (or alongside) the session the trainee may submit answers to a post-session exam. Creating an `ExamAttempt` for a given `enrollment_id` populates the `questions` array from the course's question bank; each entry in `questions` carries a question identifier, a `weight`, the correct answer, and a slot for the trainee's given answer. The attempt's `total_weight` equals the sum of every question's weight. The submission step accepts a single body field `answers` and requires that this payload include an answer for every question in `questions` — any missing answer returns `ERR_INCOMPLETE_EXAM`. The `score` is computed by summing the weight of every question whose given answer matches the correct answer, dividing that sum by `total_weight`, multiplying by one hundred, and rounding the final result half-up to two decimal places; per-question contributions are not rounded separately because doing so would shift last-cent results. The `passed` flag is true when `score` is at or above 70 and false otherwise; the boundary is inclusive on the pass side, so 70.00 passes while 69.99 fails. The submission stamps `submitted_at` to the server clock.

A trainee may also submit an `EvaluationSurvey`, supplying the `enrollment_id` together with three integer scores in the range 1 to 5: `content_score`, `instructor_score`, and `logistics_score`. The `aggregate_score` is computed as the sum of `content_score` weighted at 0.4, `instructor_score` weighted at 0.3, and `logistics_score` weighted at 0.3, rounded half-up to two decimal places. The creation of an evaluation also triggers a recomputation of the relevant instructor's `avg_evaluation_score`, averaged across every survey whose enrollment belongs to one of that instructor's completed sessions.

The session's complete action, restricted to a `TrainingAdmin`, transitions the session from `IN_PROGRESS` to `COMPLETED` and requires that the current clock is at or past `end_at`. This single action drives a three-deep cascade. For every `Enrollment` whose `status` is `CONFIRMED` at the moment of completion, the system evaluates `attendance_status` from the accumulated `CheckIn` rows and finalizes it. If `attendance_status` is `PRESENT` or `PARTIAL`, the enrollment advances to `COMPLETED` unless the trainee took the exam and failed: a `PRESENT` or `PARTIAL` attendance combined with an `ExamAttempt` whose `passed` is false advances the enrollment to `FAILED` instead. If `attendance_status` is `ABSENT` (no qualifying check-in occurred), the enrollment advances to `NO_SHOW` and its `final_credit` remains zero.

The completion of each enrollment in turn triggers the credit-award calculation that writes `final_credit`, and the writing of `final_credit` in turn triggers a recomputation of the matching `CreditPool`'s `accumulated_credits` aggregate. The completion cascade also recomputes every involved instructor's `avg_evaluation_score`. Finally, for any course that carries a `CertificateTemplate`, a fresh `Certificate` is issued to a trainee whose enrollment status is now `COMPLETED` provided two conditions are met: when the template's `requires_attendance` is true the enrollment's `attendance_status` must be `PRESENT` (not merely `PARTIAL`), and when the template's `requires_exam_pass` is true the corresponding `ExamAttempt.passed` must be true. The new certificate starts in `status` `VALID`, with `issued_at` stamped at completion and `expires_at` computed as `issued_at` plus the template's `validity_months`.

### 3.6. Credit Calculation, Instructor Fees, and Their Interplay

The credit awarded for an enrollment is the product of the course's `credit_value` (read from the session's pinned snapshot, not from the current course row) and two factors. The attendance factor is 1.0 when `attendance_status` is `PRESENT`, 0.5 when it is `PARTIAL`, and 0.0 when it is `ABSENT`. The exam factor is 1.0 when an `ExamAttempt` exists with `passed` equal to true, 0.5 when an attempt exists with `passed` equal to false, and 0.0 when no attempt was made and `attendance_status` is not `ABSENT` (a no-show attendance produces a credit of zero regardless of exam state, while an unsubmitted exam combined with `PRESENT` or `PARTIAL` attendance is treated as a failed exam factor of zero).

The system records the result in two stages. The `provisional_credit`, written when attendance is recorded but the exam outcome is not yet final, equals `credit_value` multiplied by the attendance factor alone. The `final_credit`, written during the session-completion cascade when the exam outcome is decided, equals `credit_value` multiplied by both factors and overwrites `provisional_credit`. As a worked example, a `PARTIAL` attendance combined with a failed exam (and a course whose `credit_value` is four) yields a provisional of `4.0 × 0.5 = 2.0` and a final of `4.0 × 0.5 × 0.5 = 1.0` — the two stages produce different numbers, as designed. Both quantities are rounded half-up to one fractional digit to match the precision of `credit_value`.

The instructor fee is computed per session and is accessible on demand through an admin-only fee-inspection capability; it is also evaluated as the forward leg of the session-completion cascade and as the compensating leg of the session-cancellation cascade. The calculation pins evaluation order. First, the `effective_hours` is computed as `duration_hours` (from the pinned course version) multiplied by two, rounded up to the next whole number, then divided by two — equivalent to rounding `duration_hours` up to the next half-hour. Second, a tier multiplier is selected based on `effective_hours`: when `effective_hours` falls in the inclusive range from 0.5 to 2.0 the multiplier is 1.00; when it is strictly greater than 2.0 and at or below 5.0 the multiplier is 0.95; when it is strictly greater than 5.0 the multiplier is 0.90. Third, the `base_fee` is computed as `hourly_rate` (from the pinned snapshot frozen at session creation) multiplied by `effective_hours` multiplied by the tier multiplier, and the result is rounded half-up to two decimal places — the rounding is applied after the multiplication, not on each operand. Fourth, when the instructor's `instructor_type` is `EXTERNAL`, the total is the `base_fee` plus the instructor's `travel_cost` (added after the `base_fee` has already been rounded). When the `instructor_type` is `INTERNAL`, the total is zero regardless of the instructor's `hourly_rate` — internal time is tracked but not paid out. Finally, when the session is cancelled and `cancellation_fee_charged` is true, the same full total is still owed; the system makes no attempt to net the cancellation fee against future bookings, so the forward and compensating legs sum to zero drift only in the case where the cancellation occurred outside the 48-hour window.

The credit-pool aggregate is the sum of every applicable `final_credit` plus every applicable `delta`, as described in §2.11; it is order-independent (commutative addition) and is rounded half-up to one fractional digit. Recomputation runs on every enrollment status transition into `COMPLETED`, `FAILED`, `NO_SHOW`, or `CANCELLED`, and on every `CreditAdjustment` creation. A `CreditAdjustment` carries the `credit_pool_id` it targets, a signed `delta` (positive for grants, negative for revocations), a free-text `reason` (required), and an `actor_role` recorded by the system from the request's `X-User-Role`. The system rejects any adjustment whose `delta` would drive `accumulated_credits` below zero with `ERR_CREDIT_NEGATIVE`. Every credit-adjustment creation writes an `AuditLog` row with `subject_kind` equal to `CREDIT_POOL`.

### 3.7. Certification, Renewal, and External Verification

Each course may have at most one `CertificateTemplate`, identified by its `course_id` (which is unique on the template). The template carries an integer `validity_months` between 1 and 120, an integer `renewal_window_days` between 1 and 180 (default 30) representing how many days before `expires_at` a renewal is permitted, and two boolean flags `requires_attendance` and `requires_exam_pass` (each defaulting to true). Charged courses may not be published unless such a template exists, per §3.1.

A `Certificate` issued during the session-completion cascade (§3.5) records its `trainee_id`, the originating `certificate_template_id`, the `source_enrollment_id` that earned it, the `issued_at` and `expires_at` instants, a `status` that begins at `VALID`, and a `verification_code` — a unique opaque string used for external verification. As the clock advances, the sweep capability transitions the certificate through its remaining states. While the certificate is `VALID` and the difference between `expires_at` and the current clock falls at or below `renewal_window_days`, the sweep transitions it to `EXPIRING_SOON` and emits a `SyncEvent` with `event_type` equal to `cert.expiring_soon` and `source_system` equal to `IM` — a reminder routed to the instant-messaging integration. Once the current clock reaches or passes `expires_at`, the certificate transitions from `EXPIRING_SOON` to `EXPIRED`; a defensive direct path also exists from `VALID` to `EXPIRED` for cases where the renewal window was somehow never reached.

A `Trainee` may renew an `EXPIRING_SOON` certificate by supplying a `source_enrollment_id`. The renewal succeeds only when that enrollment belongs to the same trainee, completed the same course, and the corresponding session's `start_at` falls within the half-open window stretching from `expires_at` minus `renewal_window_days` (exclusive on the lower end) up to and including `expires_at` itself; a source enrollment outside this window is rejected with `ERR_RENEWAL_WINDOW_INVALID`. A successful renewal issues a new `Certificate` row whose `expires_at` is the old certificate's `expires_at` plus the template's `validity_months` — explicitly anchored to the previous expiry rather than to the current clock, so timely renewals add full validity periods rather than collapsing them. The old certificate transitions to `RENEWED` and is kept on file. A `TrainingAdmin` may revoke a certificate that is either `VALID` or `EXPIRING_SOON`, transitioning it to `REVOKED`; the action accepts an optional `reason` argument.

External parties verify a certificate through a public capability keyed by the certificate's `verification_code`. The verification endpoint is the only operation in the system that does not require `X-User-ID` and `X-User-Role`; it returns a minimal payload sufficient to confirm authenticity without exposing private trainee data.

### 3.8. External Synchronization, Audit Logging, and Operational Controls

Three external systems exchange data with the training platform: an HR system (`HR`) feeds employment changes, an instant-messaging system (`IM`) receives reminders and warnings, and a learning-content platform (`LCP`) feeds course-content updates. Inbound and outbound events are recorded as `SyncEvent` rows carrying a `source_system` of `HR`, `IM`, or `LCP`, an `event_type` string such as `employee.updated`, `message.delivery_failed`, `content.version_pulled`, `cert.expiring_soon`, or `credit.shortfall_warning`, an opaque `payload` object, a `processed_at` stamp recorded when the system applies the event (null while pending), and an `outcome` of `PENDING`, `APPLIED`, or `REJECTED`. An administrative emit capability is provided as a test driver so external integrations can be simulated end-to-end; when it accepts an `HR` `employee.updated` event it may mutate the matching `Trainee` row, when it accepts an `LCP` `content.version_pulled` event it may emit follow-on actions, and so on.

Audit logging is narrow and intentional. The system writes an `AuditLog` row whenever an `ENROLLMENT` or a `CREDIT_POOL` is mutated, capturing the `subject_kind` (one of `ENROLLMENT` or `CREDIT_POOL`), the `subject_id` (the id of the affected enrollment or credit pool), the `actor_role` (the `X-User-Role` at the moment of the action), the `actor_id` (the `X-User-ID` at the moment of the action), the `action` string (such as `enrollment.created`, `enrollment.approved`, or `credit.adjusted`), and JSON snapshots of the affected fields in `before` and `after`. The audit log is read-only via a list capability open to a `TrainingAdmin` and supports filtering by `subject_kind`, `subject_id`, and `action`.

The administrative clock-advance capability accepts a body field `now` and pins the server's logical clock to that ISO 8601 instant; thereafter every comparison against `enrollment_deadline`, `start_at`, `end_at`, `expires_at`, and the credit-pool cycle window uses the pinned clock. The administrative sweep capability runs the time-gated transitions and the warning-threshold evaluation described in §2.10 and §2.11. Both capabilities are restricted to `TrainingAdmin` and are intended as test drivers.

List endpoints expose a number of filter and search query parameters. Course listing accepts an optional `status` filter, a `category_id` filter, a single `tag` filter, and a free-text search query `q`. Session listing accepts `course_id`, `instructor_id`, `status`, and a date range bounded by `start_after` and `start_before`. Instructor listing accepts an `expertise_tag` filter and a `status` filter. Enrollment listing accepts `session_id`, `trainee_id`, and `status`. Credit-pool listing accepts `trainee_id` and `cycle_kind`. Certificate listing accepts `trainee_id` and `status`. Course-category listing accepts a `parent_id` filter. Audit-log listing accepts `subject_kind`, `subject_id`, and `action`. Every list endpoint additionally honours `limit` and `offset` per §2.3.
