# Software Release Management & Feature Flag Governance API — Product Requirements Document

## 1. Introduction

A release office sits between the engineers who write code and the customers who run it. Its job is unglamorous and unforgiving: decide what ships, decide when it ships, prove afterwards that the decision was made properly, and turn the whole thing off quickly when it goes wrong. Today that work is spread across a wiki page of cut dates, a spreadsheet of change approvals, a feature-flag console nobody prunes, a chat channel where rollbacks are argued about, and a quarterly scramble to reconstruct change-control evidence for auditors. This document specifies the API that replaces all of it with one governed system of record.

The system is organised around four intertwined disciplines. **Release cadence** gives every release a train, a cut date, a code-freeze lead time and a stabilization window, and refuses to let more releases stabilize concurrently than the train can absorb. **Change control** classifies every proposed change by risk, routes it through the approval lanes that its risk class demands, enforces segregation of duties so that no engineer can wave their own work through, and charges each approved change against a per-release risk budget. **Progressive delivery** reserves deployment windows on environments, ingests automated health samples, runs canary analysis against explicit abort criteria, and walks feature flags up an exposure ladder one soaked rung at a time. **Compliance evidence** assembles, waives and seals a change-control packet that regulated environments require before a release may be declared shipped.

Two engineering constraints shape the specification throughout. First, every collection sits at the API root — there is no shared URL prefix — and relationships are expressed by identifier fields in request payloads rather than by deep nesting. Second, time is a server-owned **logical clock**, never the host's wall clock, so that freeze deadlines, soak durations, blackout intervals, flag expiries and incident-linkage windows are all deterministic and reproducible. Every rule in this document that says "the current instant" means that logical clock.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold for every endpoint: authentication, envelope shape, pagination, time, precision, concurrency, and the order in which the server rejects a bad request.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they are acting. Six roles exist, and the header value must match one of these spellings exactly: `PlatformAdmin`, `ReleaseManager`, `Engineer`, `ChangeApprover`, `ComplianceOfficer`, and `SRE`. A request missing either header, carrying a blank value in either, or naming a role outside those six is rejected with `ERR_UNAUTHENTICATED` (401). A well-authenticated request whose role is not listed for the target endpoint in §4 is rejected with `ERR_ROLE_NOT_PERMITTED` (403).

The six roles divide the release office by duty. `PlatformAdmin` owns environment registration and the logical clock, and may also ingest health samples, but never touches change control. `ReleaseManager` owns trains, releases, code freeze, cutting, declaring a release shipped, and release notes, but may neither author, approve nor deploy a change. `Engineer` authors, submits, merges and withdraws changes, declares dependency edges and flag guards, and owns the feature-flag inventory including its rollout ladders. `ChangeApprover` records `TECHNICAL` and `CAB` decisions only. `ComplianceOfficer` records `COMPLIANCE` decisions, grants freeze exceptions, assembles, waives and seals evidence packets, and runs the stale-flag cleanup sweep. `SRE` reserves and drives deployment windows, ingests health samples, runs canary analysis, rolls deployments back, and decides incidents. Pausing a flag is shared between `Engineer` and `SRE`; reporting an incident is shared between `SRE` and `Engineer`; ingesting a health sample is shared between `SRE` and `PlatformAdmin`; the approvals endpoint is shared between `ChangeApprover` and `ComplianceOfficer` with disjoint lanes. Every read endpoint in §4 is open to all six roles.

For all six roles — `PlatformAdmin`, `ReleaseManager`, `Engineer`, `ChangeApprover`, `ComplianceOfficer` and `SRE` — `X-User-ID` is an **opaque operator identifier** that is not the `id` of any persisted resource, and the server never compares it against any entity's `id`. What the server does instead is record it and compare it against opaque user-id fields it has stored earlier. When an `Engineer` authors a change, the header value is frozen onto that change as `author_user_id`; when an `Engineer` creates a flag, it is recorded as `created_by_user_id`; when an approval is recorded, it is stamped as `approver_user_id`; when an incident is reported, it is stamped as `reporter_user_id`; when a packet is sealed, it is stamped as `sealed_by_user_id`; and when an evidence item is waived, it is stored as `waived_by_user_id` inside the waiver entry. Accountability for a flag is *declared*, not inferred: the flag's `owner_user_id` is supplied by the creating `Engineer` as an ordinary non-empty input string, and may name a different person than `created_by_user_id`.

Two ownership comparisons follow from this, and both yield `ERR_NOT_RESOURCE_OWNER` (403) when they fail. Flag operations — planning a rollout step, starting a soak, applying a soaked step, resuming a paused flag, and archiving a flag — require `X-User-ID` to equal the flag's `owner_user_id`. Change operations — submitting, merging and withdrawing — require `X-User-ID` to equal the change's `author_user_id`. Note the deliberate asymmetry: pausing a flag carries **no** ownership check at all, because an incident responder must be able to hit the kill switch on someone else's flag.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits; alone among the instants the API emits it is read from the host's wall clock rather than from the logical clock of §2.4, so it neither reflects nor is affected by the logical clock's position.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Inventory Filters

List endpoints are paginated by two query parameters. `limit` caps the number of items returned; when omitted it defaults to 10, its minimum accepted value is 1 and its maximum is 100. `offset` skips that many items from the front of the result set; when omitted it defaults to 0, and negative values are not accepted. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (400). Unless a rule below says otherwise, every list endpoint returns its items sorted by `created_at` in ascending order, ties broken by the order in which the records were created — a tie-break that decides most listings in practice, because the logical clock only moves when a client moves it. List responses include `limit`, `offset`, `total_count` and `has_more` in the envelope's `meta` object; `total_count` counts the items that survive the filters described below before the page window is applied, and `has_more` is true exactly when `offset` plus the number of items actually returned is less than `total_count`.

Beyond pagination, the read surface offers narrow server-side filters, each matching the named field exactly. A filter value outside the field's declared set is never a malformed request: it is compared verbatim and simply matches nothing. Releases of a train may be filtered by `phase`. Change requests of a release may be filtered by `state`. Dependency edges of a change accept a `direction` selector, which is `OUTGOING` when the change appears as the `from_change_id` of the edge and `INCOMING` when it appears as the `to_change_id`; omitting the parameter — or supplying any value other than `INCOMING`, unrecognised values included — means `OUTGOING`. Approvals of a change may be filtered by `kind`. The flag inventory may be filtered by `state`, by `cleanup_state` and by `owner_user_id`, in any combination. Rollout steps may be filtered by `feature_flag_id`, by `deployment_id` and by `state`. Deployments may be filtered by `release_id`, by `environment_id` and by `delivery_state`. Health samples of a deployment may be filtered by `cohort`. Release-notes documents of a release may be filtered by `audience`. Evidence packets of a release may be filtered by `state`. Incidents may be filtered by `release_train_id`, by `linked_release_id`, by `linked_deployment_id` and by `state`.

### 2.4. The Logical Clock

Time is a first-class, writable piece of server state. On startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never advances on its own and never falls back to the host's wall-clock time. A `PlatformAdmin` repositions it by supplying a `to_iso8601` instant; the response reports the resulting clock as `current_utc`. Moving the clock is inert with respect to business state: no freeze is cascaded, no soak is completed, no staleness debt is recomputed and no counter is refreshed merely because the clock moved. Derived values change only when an operation that recomputes them is invoked. Every timestamp the server stamps — `created_at`, `updated_at`, `frozen_at`, `released_at`, `rolled_back_at`, `merged_at`, `soak_started_at`, `applied_at`, `archived_at`, `last_sweep_at`, `completed_at`, `decided_at`, `generated_at`, `published_at` and `sealed_at` — is read from this clock.

Rendering of instants is uniform across the whole API. Setting `api_request_timestamp` aside, whose format §2.2 already pins, every instant that appears in a response body — the stamped values just listed, the instants a client supplied that the server stores and echoes back (`cut_at`, `expires_at`, `window_start_at`, `window_end_at`, `observed_at`, `detected_at`, `blackout_start_at`, `blackout_end_at`), the instants the server derives from them (`freeze_at`, `stabilization_end_at`), and the clock's own `current_utc` — is written as an ISO 8601 timestamp with exactly three fractional digits and a trailing `Z`, converted to UTC first and truncated to millisecond precision when the supplied value carried a non-UTC offset or finer-than-millisecond digits. A timestamp field that holds no value is rendered as null.

### 2.5. Common Resource Properties and Immutable Records

Governed resources — release trains, environments, releases, change requests, feature flags, rollout steps, deployments, incidents, release-notes documents and evidence packets — carry a standard system-managed quartet:

- `id` (string): a server-minted UUID with no type prefix.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, taken from the logical clock at creation.
- `updated_at` (string): an ISO 8601 UTC timestamp, refreshed on every mutation of the resource, including mutations the server performs on its own as a cascade rather than at a client's direct request.
- `version` (integer): a counter that is 1 on creation and increases by one on every mutation of the resource, including cascaded mutations and recomputations of derived fields.

Five record types are append-only audit rows rather than governed resources, and they are deliberately thinner: dependency edges, approvals, change-to-flag links, canary evaluations and health samples carry only `id` and `created_at`. For those five, **both `updated_at` and `version` are absent** from the resource entirely — they are never written, never returned, and never accepted.

### 2.6. Point Scales, Percentages and Rounding

The system keeps four integer point scales and one fractional one, and the difference matters. Change risk scores, release readiness scores, flag staleness debt, and an evidence packet's `base_index` are all **integer** point quantities with no fractional arithmetic anywhere in their derivation; each has an explicit floor of 0 and a ceiling of 100. Where a scale is banded into tiers, every band boundary is inclusive on its lower bound and exclusive on its upper bound unless a rule states otherwise.

Fractional quantities appear in exactly three places, and all three round **half up**. A canary evaluation rounds each health sample's error rate to one decimal place before weighting, then rounds the request-weighted aggregate and the weighted health score to two decimal places. An evidence packet's waiver credit is summed first and then rounded half up to two decimal places. A rollout step's `target_pct` is compared against the ladder ceiling at two-decimal precision. Percentage fields (`target_pct`, `current_exposure_pct`, `previous_exposure_pct`, `canary_pct`, `abort_error_rate_pct`, `error_rate_pct_rounded`) are plain numbers on a 0-to-100 scale, not fractions of one. Rendering follows the value: a computed fractional quantity whose rounded result happens to be integral is written as a plain integer rather than with trailing zeros — a `weighted_health_score` of 88.00 renders as `88` and an `error_rate_pct_rounded` of 0.00 renders as `0` — while a percentage the client supplied is stored and echoed in exactly the numeric form it arrived in.

### 2.7. Optimistic Concurrency on Flags and Releases

Exactly two write operations take an expected-version input, and each protects a derivation that would be silently wrong if the writer's view of the parent were out of date.

Planning a new rung on a feature flag's rollout ladder requires `expected_feature_flag_version` in the request body. It is **not optional**. Its value must equal the target flag's current `version`. If any other writer has advanced that flag's `version` since the client last read the flag, the create is rejected with `ERR_STALE_FLAG_VERSION` (412) and no step is created. The protection is meaningful because the ladder ceiling is derived from the flag's exposure as it stands at creation time — a writer holding a stale view of the flag would plan a rung against an obsolete ceiling. Planning does not supersede anything: a still-`PLANNED` rung is left exactly as it is, and the new step simply takes the next `step_index` behind it.

Assembling a compliance evidence packet for a release requires `expected_release_version` in the request body, likewise non-optional, and likewise required to equal the target release's current `version`. A mismatch is rejected with `ERR_STALE_RELEASE_VERSION` (412). A new packet supersedes the release's prior draft packet, and its `base_index` is computed from the release's approval, freeze and deployment facts, so sealing evidence from a stale view of the release would attest to a state that no longer exists.

No other endpoint accepts a version field of any kind, and no other endpoint performs a version check.

### 2.8. The Rejection Ladder

When a request violates more than one rule, the outcome is not ambiguous. The server evaluates the checks below in **strict ascending rank order**, stops at the first one that fails, returns that check's error, and applies **no side effect whatsoever** — no counter moves, no state changes, no timestamp is stamped. The ranking is global: a rank-8 state conflict always wins over a rank-30 freeze violation on the very same request, and a rank-7 stale version always wins over a rank-10 ownership failure.

1. Both authentication headers are present and non-blank and the role is one of the six declared names — otherwise `ERR_UNAUTHENTICATED` (401). All endpoints.
2. The acting role appears in the endpoint's authorized-role list in §4 — otherwise `ERR_ROLE_NOT_PERMITTED` (403). All endpoints.
3. Request-body shape: every required input is present, every value has the declared type, every enum value is a member of its declared set, and every numeric constraint holds — `cadence_days` at least 1, `target_pct` greater than 0 and at most 100, `window_end_at` strictly after `window_start_at`, `deploy_window_end_hour_utc` strictly greater than `deploy_window_start_hour_utc`, `error_count` no greater than `request_count`, `limit` between 1 and 100 inclusive, and `offset` at least 0. Otherwise `ERR_INVALID_REQUEST` (400). All endpoints. Three conventions complete this rank: an absent or empty request body is read as an empty JSON object, so an operation with no required inputs accepts a body-less POST while one with required inputs reports the first missing input; an explicit `null` for an optional input is treated exactly as if the field had been omitted, so the documented default applies, whereas an explicit `null` for a required input is a missing input; and any field the operation does not declare is ignored rather than rejected.
4. Every identifier in the URL path resolves to an existing resource, checked left to right, reporting the first failure: `ERR_RELEASE_TRAIN_NOT_FOUND`, `ERR_RELEASE_NOT_FOUND`, `ERR_CHANGE_REQUEST_NOT_FOUND`, `ERR_FEATURE_FLAG_NOT_FOUND`, `ERR_ROLLOUT_STEP_NOT_FOUND`, `ERR_DEPLOYMENT_NOT_FOUND`, or `ERR_RESOURCE_NOT_FOUND` for environments, incidents, release-notes documents and evidence packets (all 404). All endpoints.
5. Every foreign key supplied in the request body resolves: `environment_id` reports `ERR_RESOURCE_NOT_FOUND`, `release_train_id` reports `ERR_RELEASE_TRAIN_NOT_FOUND`, `feature_flag_id` reports `ERR_FEATURE_FLAG_NOT_FOUND`, `deployment_id` reports `ERR_DEPLOYMENT_NOT_FOUND`, and `to_change_id` reports `ERR_CHANGE_REQUEST_NOT_FOUND` (all 404). This rank guards exactly five operations: reserving a deployment window, reporting an incident, creating a flag link, declaring a dependency edge, and planning a rollout step.
6. Scoped uniqueness: a feature flag's `key` must be unique across the whole inventory, and a collision is `ERR_FLAG_KEY_DUPLICATE` (409); a release's `version_label` must be unique within its train, and a collision is `ERR_VERSION_LABEL_DUPLICATE` (409). An environment `name` must also be globally unique, but a collision there is treated as a malformed request and reported as `ERR_INVALID_REQUEST` (400) — `ERR_FLAG_KEY_DUPLICATE` is never used for environments. This rank guards flag creation and release creation.
7. Optimistic concurrency per §2.7: `expected_feature_flag_version` must equal the flag's `version` (`ERR_STALE_FLAG_VERSION`, 412) and `expected_release_version` must equal the release's `version` (`ERR_STALE_RELEASE_VERSION`, 412). This rank guards rollout-step planning and evidence-packet assembly.
8. The resource named in the path is in a state that permits the requested transition, reported as `ERR_RELEASE_PHASE_INVALID`, `ERR_CHANGE_STATE_INVALID`, `ERR_FLAG_STATE_INVALID`, `ERR_STEP_STATE_INVALID`, `ERR_DEPLOYMENT_STATE_INVALID`, `ERR_PACKET_STATE_INVALID`, `ERR_NOTE_ALREADY_PUBLISHED` or `ERR_INCIDENT_ALREADY_DECIDED` (all 409), according to the type of the path target. This rank guards every state-transition operation.
9. State preconditions on an entity **other than** the path target: reserving or starting a deployment requires its release's `phase` to be one of `CUT`, `STABILIZING` or `RELEASED` (`ERR_RELEASE_PHASE_INVALID`); submitting a change requires its release's `phase` to be `OPEN` (`ERR_RELEASE_PHASE_INVALID`); starting a step's soak requires the flag's `state` to be `DRAFT` or `ACTIVE_ROLLING_OUT` (`ERR_FLAG_STATE_INVALID`) and then requires every change linked to the flag to be `DEPLOYED` (`ERR_CHANGE_STATE_INVALID`), in that order within the rank; applying a soaked step requires the flag's `state` to be `ACTIVE_ROLLING_OUT` (`ERR_FLAG_STATE_INVALID`). All 409. This rank guards exactly those five operations: deployment reservation, deployment start, change submit, soak start, and step apply.
10. Ownership per §2.1 — otherwise `ERR_NOT_RESOURCE_OWNER` (403). This rank guards rollout-step planning, soak start, step apply, flag resume, flag archive, change submit, change merge and change withdraw.
11. Segregation of duties on the approvals operation: the approver's `X-User-ID` must differ from the change's `author_user_id` in every lane, and a `CAB` approval must additionally come from a user id that has not already recorded the `TECHNICAL` approval on the same change — otherwise `ERR_SELF_APPROVAL_FORBIDDEN` (403).
12. Approval lane matches the acting role: `TECHNICAL` and `CAB` require `ChangeApprover`, `COMPLIANCE` requires `ComplianceOfficer` — otherwise `ERR_APPROVAL_ROLE_MISMATCH` (403).
13. A flag whose `cleanup_state` is `ENFORCED` may not be resumed, may not start a new soak, and may not receive a new rollout step until its staleness is cleared — otherwise `ERR_FLAG_CLEANUP_ENFORCED` (409). This rank guards exactly those three operations.
14. A change whose `risk_class` is `HIGH` or `CRITICAL` may only merge when its `rollback_plan` is non-null and `rollback_tested` is true — otherwise `ERR_ROLLBACK_PLAN_REQUIRED` (422).
15. A release whose completed production deployment sits on an environment with `requires_compliance_evidence` true may only be declared shipped when one of its evidence packets is `SEALED` — otherwise `ERR_EVIDENCE_PACKET_REQUIRED` (409). Note that this check sits **above** the readiness gate at rank 37: a regulated release that is both unready and unevidenced reports the missing packet.
16. An evidence packet may only be sealed when its `completeness_index` is at least 90 — otherwise `ERR_EVIDENCE_INCOMPLETE` (422).
17. A waiver may only be recorded when the packet's `base_index` is at least 50, and the supplied `item_code` must name an item that is currently unsatisfied and not already waived — otherwise `ERR_WAIVER_NOT_ALLOWED` (422).
18. Completion of a deployment respects verification per §3.7 — otherwise `ERR_CANARY_NOT_PASSING` (409).
19. A dependency edge may not close a cycle in the prerequisite graph, may not point a change at itself, and may not join changes belonging to different releases — otherwise `ERR_DEPENDENCY_CYCLE` (409).
20. Every prerequisite of a merging change must already be `MERGED` or `DEPLOYED` — otherwise `ERR_PREREQUISITE_NOT_MERGED` (409).
21. At most one rollout step per flag may be `SOAKING` — otherwise `ERR_STEP_ALREADY_SOAKING` (409).
22. The step starting its soak must be the flag's next rung, meaning its `step_index` equals the flag's `applied_step_count` plus one — otherwise `ERR_STEP_OUT_OF_ORDER` (409).
23. A planned rung's `target_pct` must respect the ladder geometry of §3.5 — otherwise `ERR_ROLLOUT_STEP_TOO_LARGE` (422).
24. A planned rung's `soak_minutes` must be at least the soak required for its `target_pct` — otherwise `ERR_SOAK_TOO_SHORT` (422).
25. A release-notes document with `entry_count` of 0 may not be published — otherwise `ERR_EMPTY_RELEASE_NOTES` (422).
26. An incident decision must be admissible per §3.8 — otherwise `ERR_NO_LINKED_RELEASE` (409).
27. The submitted approval `kind` must be one the change's current `risk_class` actually requires — otherwise `ERR_APPROVAL_KIND_NOT_REQUIRED` (422).
28. The same approval `kind` may not be recorded twice with decision `APPROVE` on one change — otherwise `ERR_DUPLICATE_APPROVAL_KIND` (409).
29. A release may only be cut once the logical clock has reached its `freeze_at`, inclusively — otherwise `ERR_CUT_BEFORE_FREEZE` (409).
30. A change may not merge once the logical clock has reached its release's `freeze_at`, nor while that release's `phase` is `FROZEN` or `CUT`, unless the release's `freeze_exception_approved` is true — otherwise `ERR_CODE_FREEZE_ACTIVE` (409).
31. Deployment window geometry per §3.7 — otherwise `ERR_DEPLOY_WINDOW_VIOLATION` (409). This rank guards both window reservation and deployment start.
32. The logical clock must not lie inside the environment's blackout interval — otherwise `ERR_BLACKOUT_ACTIVE` (409). This rank guards deployment start.
33. The requested window must not collide with another live deployment's occupied window on the same environment, cooldown buffer included — otherwise `ERR_DEPLOYMENT_WINDOW_CONFLICT` (409). This rank guards window reservation.
34. Cutting must not exceed the train's concurrent-stabilization capacity — otherwise `ERR_STABILIZATION_CAPACITY_EXCEEDED` (409).
35. A soaked step may only be applied once the logical clock has reached the end of its soak, inclusively — otherwise `ERR_SOAK_NOT_ELAPSED` (409).
36. Consuming risk budget must not push a release's `risk_budget_consumed_points` above its train's `risk_budget_points` — otherwise `ERR_RISK_BUDGET_EXCEEDED` (409). This rank guards recording an approval and submitting a change, and the same ceiling is re-checked when a change merges.
37. A release may only be declared shipped when its `readiness_score_attested` is at least 80, its `rollback_plan_confirmed` is true, and at least one of its deployments has reached `COMPLETED` on a production-tier environment — otherwise `ERR_RELEASE_NOT_READY` (409).

### 2.9. Path Resolution for Nested Resources

Where a path carries an identifier, that identifier is resolved before any body content is examined. Where a path carries more than one, resolution proceeds strictly left to right and the first unresolvable identifier decides the response, so a request for the change requests of a non-existent release reports `ERR_RELEASE_NOT_FOUND` and never reaches the child lookup. Because the topology is flat, most write operations address a single parent in the path and name their other participants by identifier in the body; body identifiers are resolved only after every path identifier has resolved, per the rank ordering in §2.8.

### 2.10. Cascade Discipline and Derived-Counter Reconciliation

A great deal of this system's behaviour is second-order: one client request mutates the addressed resource and then propagates through parents, children, junction rows and cross-aggregate references. Three principles govern all of it.

**Cascades are ordered, not simultaneous.** Where a workflow in §3 describes a cascade in numbered hops, the hops run in exactly that order, each hop reading the state that the previous hop left behind. Reordering hops produces different counters and is not an acceptable implementation.

**Every touched resource is a real mutation, and only a real change is a mutation.** When a cascade changes any field of a governed resource — a phase, a state, a counter, a recomputed score, a nulled or stamped timestamp — that resource's `updated_at` is refreshed and its `version` increases by one, exactly as if a client had written it directly. This holds for parents mutated by a child's transition and for children mutated by a parent's transition. The converse also holds: a recomputation or a re-write that leaves every field at the value it already had is not a mutation, so `updated_at` and `version` stay exactly as they were. And the unit of accounting is the hop, not the field — every field a single hop writes together advances that resource's `version` by exactly one, however many fields the hop touched, while two hops that each write the same resource advance it twice.

**Counters are reconciled by compensation, not by recomputation from scratch.** The release-level ledgers — `committed_change_count` and `risk_budget_consumed_points` — move up when a change enters `APPROVED` and move back down by the same amounts when that change leaves `APPROVED`, whether it leaves by withdrawal or by being blocked on a prerequisite. A change that has never been approved never contributes to, and never subtracts from, either quantity. `verified_change_count` and the readiness scores, by contrast, are always recomputed from the current change set rather than adjusted incrementally.

### 2.11. Interval Geometry

Intervals in this domain are deliberately not uniform, and getting the endpoints wrong is the most common way to get the wrong answer. The conventions are:

- A deployment's reserved window `[window_start_at, window_end_at)` is **half-open**: the start instant is inside the window, the end instant is not.
- Occupancy checking on an environment compares half-open windows, but each already-occupied window is first extended at its end by the environment's `cooldown_minutes`, so the occupied span is from that deployment's `window_start_at` up to but not including its `window_end_at` plus the cooldown.
- An environment's blackout span `[blackout_start_at, blackout_end_at]` is **closed**: both endpoints are inside the blackout.
- A release's stabilization span `[cut_at, stabilization_end_at]` is **closed** for capacity purposes, and two spans that merely touch at an endpoint count as intersecting.
- A canary analysis window `[window_start_at, window_end_at)` over health samples is **half-open** on the sample's `observed_at`.
- Threshold gates on the clock are inclusive: a release may be cut at exactly its `freeze_at`, and a step may be applied at exactly the instant its soak ends.
- The freeze comparison inside the attested readiness score is the one strict comparison in the system: a change merged strictly before `freeze_at` counts as landed on time, and a change merged at exactly `freeze_at` counts as late.

### 2.12. Segregation of Duties

Change control only means something if no single person can complete it alone, so three separations are enforced structurally rather than by convention. An author may not approve their own change: any approval whose `X-User-ID` matches the change's `author_user_id` is refused with `ERR_SELF_APPROVAL_FORBIDDEN`, in every lane. The change advisory board may not rubber-stamp its own technical review: a `CAB` approval recorded by the same user id that already recorded the `TECHNICAL` approval on that change draws the same `ERR_SELF_APPROVAL_FORBIDDEN`. And the lanes themselves are role-bound rather than negotiable: `TECHNICAL` and `CAB` decisions may only be recorded by a `ChangeApprover`, `COMPLIANCE` decisions only by a `ComplianceOfficer`, and a mismatch is `ERR_APPROVAL_ROLE_MISMATCH`. Separately, only a flag's declared owner may drive that flag's rollout ladder, which keeps exposure changes attributable to one accountable engineer.

## 3. Business Logic & Workflows

### 3.1. The Release Train and Its Freeze Cascade

A `ReleaseManager` establishes a **release train** as the cadence container for everything that follows. The train is created with a human-readable `name` that must be non-empty and at most 80 characters, a `cadence_days` figure describing the nominal spacing between cuts (at least 1), a `code_freeze_lead_hours` figure describing how long before a cut merging stops (zero or more), a `stabilization_hours` figure describing how long a release stabilizes after its cut (zero or more), and a `risk_budget_points` ceiling (zero or more) that every release riding this train must respect. One optional input, `max_concurrent_stabilizing`, states how many of the train's releases may have overlapping stabilization spans; it must be at least 1 and defaults to 1 when omitted. A newly created train has `phase` `ACTIVE`, a null `frozen_at`, and both of its computed counters at zero: `open_release_count`, which tracks how many of its releases are in `phase` `OPEN` or `FROZEN`, and `freeze_exception_count`, which tracks how many of its releases have had a freeze exception granted.

The train's `phase` is a two-state gate that cycles: `ACTIVE`, meaning changes may flow, and `FROZEN`, meaning code freeze has been cascaded down to every open release. A `ReleaseManager` moves between the two by supplying an `action` of either `FREEZE` or `UNFREEZE`. Freezing requires the train to currently be `ACTIVE` and requires `open_release_count` to be at least 1 — a train with no open releases has nothing to freeze. Unfreezing requires the train to currently be `FROZEN`. A wrongly directed request is refused with `ERR_RELEASE_PHASE_INVALID`.

The `ACTIVE → FROZEN` transition is the largest cascade in the system, and its **five hops run in exactly this order**. First, the train itself: `frozen_at` is stamped with the current logical-clock instant, `phase` becomes `FROZEN`, and the train's `version` increases by one. Second, every release on the train whose `phase` is `OPEN` moves to `phase` `FROZEN`, each such release taking a `version` increment of its own; `open_release_count` is *not* reduced, because a `FROZEN` release still counts as open. Third — and caused by the second hop — on each release that just became `FROZEN`, every change request whose `state` is `DRAFT`, `RISK_CLASSIFIED` or `CAB_REVIEW` moves to `state` `DEFERRED`. Fourth, caused by the third hop, each change that was just deferred has its dependents examined: for every dependency edge whose `to_change_id` is that newly deferred change, the dependent change named by the edge's `from_change_id` moves from `state` `APPROVED` to `state` `BLOCKED_BY_DEPENDENCY`. Fifth in the pinned order but caused by the fourth hop, each change that just left `APPROVED` gives back its ledger contribution: its release's `committed_change_count` drops by one and its `risk_score_final` is subtracted from that release's `risk_budget_consumed_points`. Finally, caused by hops three through five together, `readiness_score_projected` is recomputed on every release touched anywhere above. Stated as a sequence: freeze the releases, defer the in-flight changes, block the approved dependents, reconcile the counters, recompute readiness.

Unfreezing compensates that cascade rather than merely flipping the gate. The train's `phase` returns to `ACTIVE` and its `version` increases by one, while `frozen_at` is **retained** as the historical record of the most recent freeze rather than nulled. Every release on the train whose `phase` is `FROZEN` and whose `cut_at` is still strictly in the future relative to the current logical clock returns to `phase` `OPEN`; a frozen release whose cut date has already passed stays frozen. On each release that returned to `OPEN`, every change whose `state` is `DEFERRED` returns to `state` `RISK_CLASSIFIED`, undoing the third hop of the freeze. Also on those releases, every change whose `state` is `BLOCKED_BY_DEPENDENCY` returns to `state` `APPROVED` provided that none of its prerequisites is currently `DEFERRED`, `WITHDRAWN` or `REJECTED` — note that on this path the prerequisites need only be *un-abandoned*, not yet merged. Each such restoration re-increments its release's `committed_change_count` by one and re-adds its `risk_score_final` to `risk_budget_consumed_points`. `readiness_score_projected` is then recomputed on every release touched.

### 3.2. Opening and Cutting a Release

A `ReleaseManager` opens a **release** on a train by supplying just two values: a `version_label`, which must be non-empty and unique among the releases of that train, and a scheduled `cut_at` instant. Everything else is derived. The release records its train as `release_train_id`. Its `freeze_at` is the `cut_at` instant moved earlier by the train's `code_freeze_lead_hours`. Its `stabilization_end_at` is the `cut_at` instant moved later by the train's `stabilization_hours`, and serves as the closed upper bound of the release's stabilization span. The new release starts in `phase` `OPEN` with `readiness_score_projected` of 100, a null `readiness_score_attested`, `rollback_plan_confirmed` true, `evidence_packet_required` false, `freeze_exception_approved` false, null `released_at` and `rolled_back_at`, and all three ledger counters — `committed_change_count`, `verified_change_count` and `risk_budget_consumed_points` — at zero. Creation raises the train's `open_release_count` by one. A duplicate `version_label` on the same train is refused with `ERR_VERSION_LABEL_DUPLICATE`.

The release `phase` is a six-value lifecycle: `OPEN`, `FROZEN`, `CUT`, `STABILIZING`, `RELEASED` and the terminal `ROLLED_BACK`. `OPEN` and `FROZEN` cycle in both directions under train control, as §3.1 describes; the remaining moves are described here and in §3.7.

Cutting is the release's most consequential act, and a `ReleaseManager` may perform it from either `phase` `OPEN` or `phase` `FROZEN` — the two source phases are treated identically in both their preconditions and their effects. Three preconditions apply. The release must be in one of those two phases, or the request is refused with `ERR_RELEASE_PHASE_INVALID`. The logical clock must have reached the release's `freeze_at`, where reaching it exactly is sufficient; an earlier attempt is refused with `ERR_CUT_BEFORE_FREEZE`. And the train's stabilization capacity must accommodate one more stabilizing release: count the *other* releases on the same train whose `phase` is `CUT` or `STABILIZING` and whose closed span from `cut_at` to `stabilization_end_at` intersects this release's closed span — where two spans that merely touch at a single endpoint do intersect — add one for this release, and the total must not exceed the train's `max_concurrent_stabilizing`. Exceeding it is refused with `ERR_STABILIZATION_CAPACITY_EXCEEDED`.

The effects of a cut are also ordered. **First**, every change request on the release whose `state` is `DRAFT`, `RISK_CLASSIFIED` or `CAB_REVIEW` moves to `state` `DEFERRED` — this deferral is pinned to run *before* the attested score is computed, so those changes are counted in their post-deferral state. **Then** `readiness_score_attested` is computed and pinned; it is never recomputed for the remainder of the release's life. `readiness_score_projected` and `rollback_plan_confirmed` are then recomputed, `phase` becomes `CUT`, the train's `open_release_count` drops by one, and the release's `version` increases by one.

Two readiness figures live on every release, and they answer different questions. The **projected** figure, `readiness_score_projected`, is forward-looking: it assumes everything still alive will land. The **attested** figure, `readiness_score_attested`, is chronological: it judges what actually landed by the freeze deadline, and it is the number the final release gate consults. Both are built from the same three penalty terms, applied to a set of the release's change requests. Within a given set, the penalty is: four points for each change in the set whose `risk_class` is `HIGH` or `CRITICAL` and whose `rollback_tested` is false; plus five points for each change in the set whose `state` is `BLOCKED_BY_DEPENDENCY`; plus three points for each **distinct** feature flag that is linked through a change-to-flag link to any change in the set and whose `cleanup_state` is `OVERDUE` or `ENFORCED`. That last term counts flags, not links, so two links to the same stale flag cost three points in total, not six.

For the projected figure, the set comprises the release's change requests whose `state` is `RISK_CLASSIFIED`, `CAB_REVIEW`, `APPROVED`, `MERGED`, `DEPLOYED` or `BLOCKED_BY_DEPENDENCY`, and the score is 100 minus that set's penalty, floored at 0. Changes that are `DRAFT`, `DEFERRED`, `WITHDRAWN` or `REJECTED` never enter it, and merge timing is ignored entirely; unapproved-but-live work attracts no not-landed penalty at all. The projected figure is refreshed continuously — on every change-request state transition on the release, on every new dependency edge, on every new change-to-flag link, and whenever the cleanup sweep alters a linked flag's `cleanup_state` — from release creation onward, with no phase gate of any kind: a release that has already been cut, shipped or even rolled back still recomputes the figure whenever one of those triggers fires on it.

For the attested figure, the set is narrower: only the release's change requests whose `state` is `MERGED` or `DEPLOYED` **and** whose `merged_at` is strictly earlier than the release's `freeze_at`. Two extra penalties then apply, each worth six points per change. A **late** change is one whose `state` is `MERGED` or `DEPLOYED` but whose `merged_at` is at or after `freeze_at` — merging at exactly the freeze instant is late. An **unlanded** change is one whose `state` at cut time is `RISK_CLASSIFIED`, `CAB_REVIEW`, `APPROVED`, `BLOCKED_BY_DEPENDENCY` or `DEFERRED`; because the cut defers in-flight work first, most unlanded changes are counted as `DEFERRED`. The attested score is 100 minus the narrow set's penalty, minus six times the number of late changes, minus six times the number of unlanded changes, floored at 0. `WITHDRAWN`, `REJECTED` and `DRAFT` changes enter neither variant's set nor either count.

Code freeze can be overridden, but only by compliance. A `ComplianceOfficer` grants a **freeze exception** on a specific release by supplying a non-empty `justification` (which is recorded nowhere on the release); the release's `freeze_exception_approved` becomes true, its train's `freeze_exception_count` rises by one, and the release's `version` increases by one. A second grant on a release that already carries the exception is accepted but completely inert — nothing changes, so the count does not rise again and neither the release's `version` nor its `updated_at` moves. That single flag is what allows a merge to proceed past `freeze_at` or into a `FROZEN` or `CUT` release, and it is also what can satisfy the freeze-discipline evidence item described in §3.9.

### 3.3. Authoring and Classifying a Change

An `Engineer` authors a **change request** against a release. The payload carries a `title` (non-empty, at most 120 characters), a `summary_internal` (non-empty), the diff size as `lines_changed` (zero or more), the breadth of the change as `touched_subsystem_count` (zero or more), and a `declared_blast_radius` of `INTERNAL`, `SINGLE_TENANT` or `GLOBAL`. Five optional inputs round out the declaration: `summary_customer_facing`, the customer-facing copy, null when unwritten; `customer_facing`, the author's assertion that the change is visible to customers, defaulting to false; `has_schema_migration`, defaulting to false; `rollback_plan`, a prose plan that is null when none was supplied; and `rollback_tested`, defaulting to false, asserting that the plan was actually rehearsed. Authoring itself is unconstrained by the release's `phase`: a change request may be created against a release in any phase, including a `FROZEN`, `CUT` or even `ROLLED_BACK` one, because the phase gate bites at submission rather than at authoring. The change records its release as `release_id` and freezes the creating engineer's `X-User-ID` as `author_user_id` — a value that never changes afterwards. It begins in `state` `DRAFT` with `risk_score_preliminary`, `risk_score_final` and `risk_class` all null, `dependency_depth` at 0, all three approval counters (`approval_technical_count`, `approval_compliance_count`, `approval_cab_count`) at 0, `merged_at` null, and `deployment_verified` false.

The change lifecycle has ten states: `DRAFT`, `RISK_CLASSIFIED`, `CAB_REVIEW`, `APPROVED`, `MERGED`, `DEPLOYED`, `DEFERRED`, `BLOCKED_BY_DEPENDENCY`, and the two terminal states `WITHDRAWN` and `REJECTED`.

Submitting is the fork point of change control, and only the author may do it, only from `state` `DRAFT`, and only while the owning release's `phase` is `OPEN` — a submission against a release in any other phase is refused with `ERR_RELEASE_PHASE_INVALID`, and a submission of a non-`DRAFT` change with `ERR_CHANGE_STATE_INVALID`. Submission pins `risk_score_preliminary` and the `risk_class` tier derived from it, moves the change to `RISK_CLASSIFIED`, increments its `version`, and recomputes the release's `readiness_score_projected`. The server then **immediately** takes one of three branches according to `risk_class`, and the branches receive equal treatment:

- A `LOW` change auto-approves. It moves straight from `RISK_CLASSIFIED` to `APPROVED` with **no approval records created at all**, pins `risk_score_final`, raises its release's `committed_change_count` by one, adds its `risk_score_final` to that release's `risk_budget_consumed_points`, and triggers a recomputation of `readiness_score_projected`.
- A `CRITICAL` change moves from `RISK_CLASSIFIED` to `CAB_REVIEW` to await the change advisory board. **No risk budget is consumed at this point** — budget is charged only on entry to `APPROVED`.
- A `MEDIUM` or `HIGH` change stays in `RISK_CLASSIFIED` and collects its approvals there.

Because a `LOW` submission consumes budget in the same request, submission is itself subject to the risk-budget ceiling and can be refused with `ERR_RISK_BUDGET_EXCEEDED`.

The risk score itself is a weighted, capped, integer computation with a **pinned evaluation order**: accumulate the raw points first, then apply the credits, then clamp, and only then select the tier. The raw points are the sum of five terms. *Size points* are five points for each whole or partial hundred lines of diff — that is, `lines_changed` divided by 100 and rounded **up** to a whole number, multiplied by five — capped at 30, so a change of 600 lines or more contributes the full 30. *Spread points* are four points per subsystem in `touched_subsystem_count`, capped at 20, so five or more subsystems contribute the full 20. *Migration points* are 25 when `has_schema_migration` is true and 0 otherwise. *Blast points* come from the declared radius: 0 for `INTERNAL`, 10 for `SINGLE_TENANT`, 20 for `GLOBAL`. *Dependency points* are five points per level of prerequisite depth, capped at 15, so three or more levels contribute the full 15.

Two credits then reduce the raw total, and each contributes at most once. The **rollback credit** subtracts 10 points when `rollback_plan` is non-null and `rollback_tested` is true; it subtracts 5 points when `rollback_plan` is non-null but untested; and it subtracts nothing when no plan was supplied. The **flag credit** looks at the change's flag guards, considering only flags whose `state` is `DRAFT`, `ACTIVE_ROLLING_OUT` or `FULLY_ROLLED_OUT`: it subtracts 15 points if at least one qualifying guard has `guard_kind` `GATES_ENTIRE_CHANGE`, otherwise it subtracts 5 points if at least one qualifying guard has `guard_kind` `PARTIAL`, otherwise nothing. When several guards qualify, the **larger credit magnitude wins** — a change with both a whole-change guard and a partial guard receives 15, not 20. A guard whose flag is `PAUSED` or `ARCHIVED` earns no credit whatsoever.

The score is the raw total plus both credits, clamped into the range 0 through 100 inclusive. The tier follows: `LOW` below 25, `MEDIUM` from 25 up to but not including 50, `HIGH` from 50 up to but not including 70, and `CRITICAL` at 70 and above. A score of exactly 50 is `HIGH`, and a score of exactly 70 is `CRITICAL`.

The same computation runs twice with one deliberate difference in its input. The **preliminary** run happens once at submission and is never recomputed; it treats prerequisite depth as **unconditionally zero**, because dependency edges are considered unknown at submit time, and it reads flag guards as they exist at submission. Its output is `risk_score_preliminary`, and `risk_class` is the tier of that value — so the tier a change is routed by is always the preliminary tier. The **final** run happens once on entry into `state` `APPROVED`, whichever of the three approval paths got the change there, and is likewise never recomputed afterwards; it uses the change's `dependency_depth` as it stands at approval. Consequently every dependency edge added after submission raises the final score by five points per level of depth, up to the 15-point cap, and a guard flag that has since been paused or archived silently withdraws its credit. Its output is `risk_score_final`, and that is the value charged against the release's risk budget.

Guarding a change with a flag is a separate, explicit act: an `Engineer` supplies a `feature_flag_id` together with a `guard_kind` of `GATES_ENTIRE_CHANGE` or `PARTIAL`, creating a change-to-flag link that records the pair as `change_request_id` and `feature_flag_id`. Creating a link recomputes the release's `readiness_score_projected`, and it also removes the flag's orphan penalty at that flag's next staleness evaluation, as §3.6 explains. Links are many-to-many, and nothing else gates the act: neither the change's `state` nor the flag's `state` or `cleanup_state` is checked, so a link may be declared against a `DEPLOYED` change or an `ARCHIVED` flag, and the very same change-and-flag pair may be linked more than once, each request appending another link row. One change may be guarded by several flags, and one flag may guard several changes.

### 3.4. Prerequisite Graphs, Approval Lanes, Merging and Withdrawal

Changes rarely land independently. An `Engineer` declares that one change must land after another by creating a **dependency edge**: the addressed change becomes the edge's `from_change_id`, the supplied `to_change_id` names the prerequisite that must land first, and an optional `note` records the rationale (null when omitted). Three structural rules apply, and all three report `ERR_DEPENDENCY_CYCLE`: the edge may not point a change at itself, the edge may not close a cycle anywhere in the prerequisite graph, and both endpoints must belong to the same release. On success, the dependent change's `dependency_depth` is recomputed as the length of the **longest** prerequisite chain reachable from it through dependency edges — zero when it has no prerequisites at all — and the release's `readiness_score_projected` is recomputed. Because `dependency_depth` feeds the final risk score, adding prerequisites after submission makes a change more expensive to approve without changing the lane it was routed into.

Approval is recorded one lane at a time. An approval names the change as `change_request_id`, carries a `kind` of `TECHNICAL`, `COMPLIANCE` or `CAB`, a `decision` of `APPROVE` or `REJECT`, and an optional reviewer `comment` (null when omitted). Three values are stamped by the server rather than supplied: `approver_user_id`, taken from `X-User-ID`; `pinned_risk_score`, a snapshot of the change's `risk_score_preliminary` at the instant the approval was recorded; and `pinned_change_version`, a snapshot of the change's `version` at that same instant. Approvals may only be recorded while the change's `state` is `RISK_CLASSIFIED` or `CAB_REVIEW`; anything else is `ERR_CHANGE_STATE_INVALID`.

Which lanes a change needs is decided entirely by its `risk_class`. A `LOW` change requires **no** lanes, which is why it auto-approves at submission. A `MEDIUM` change requires only `TECHNICAL`. A `HIGH` change requires `TECHNICAL` and `COMPLIANCE`. A `CRITICAL` change requires `TECHNICAL`, `COMPLIANCE` and `CAB`. Submitting a lane the change's class does not require — a `CAB` decision on a `MEDIUM` change, for instance — is refused with `ERR_APPROVAL_KIND_NOT_REQUIRED`, and recording the same lane a second time with decision `APPROVE` is refused with `ERR_DUPLICATE_APPROVAL_KIND`. Each accepted `APPROVE` raises exactly one of the change's three counters: `approval_technical_count`, `approval_compliance_count` or `approval_cab_count`.

Approval is a join, not a single gate, and the join condition depends on where the change is waiting. A change waiting in `RISK_CLASSIFIED` reaches `APPROVED` when either its `risk_class` is `MEDIUM` and `approval_technical_count` is at least 1, or its `risk_class` is `HIGH` and `approval_technical_count` is at least 1 **and** `approval_compliance_count` is at least 1. A change waiting in `CAB_REVIEW` reaches `APPROVED` when `approval_technical_count`, `approval_compliance_count` and `approval_cab_count` are each at least 1. Both joins have identical effects: `risk_score_final` is computed and pinned, the release's `committed_change_count` rises by one, `risk_score_final` is added to the release's `risk_budget_consumed_points`, and `readiness_score_projected` is recomputed. If that addition would push `risk_budget_consumed_points` above the train's `risk_budget_points`, the whole approval is refused with `ERR_RISK_BUDGET_EXCEEDED` and nothing is recorded.

A single `REJECT` ends the change. From either `RISK_CLASSIFIED` or `CAB_REVIEW` — and the two source states behave identically — a decision of `REJECT` moves the change to the terminal `state` `REJECTED` and recomputes the release's `readiness_score_projected`. No budget is released, because a rejected change never entered `APPROVED` and therefore never consumed any.

Merging is the author's act, permitted only from `state` `APPROVED` and only by the user whose id matches `author_user_id`. Six further conditions must hold, and they are checked in the ladder order of §2.8. If the change's `risk_class` is `HIGH` or `CRITICAL`, its `rollback_plan` must be non-null and its `rollback_tested` must be true, or the merge is refused with `ERR_ROLLBACK_PLAN_REQUIRED`. Every dependency edge whose `from_change_id` is this change must point to a prerequisite whose `state` is `MERGED` or `DEPLOYED`, or the merge is refused with `ERR_PREREQUISITE_NOT_MERGED`. The freeze gate must be open: the release's `phase` must be `OPEN`, or the release's `freeze_exception_approved` must be true while its `phase` is `FROZEN` or `CUT`; and the logical clock must still be strictly before the release's `freeze_at`, unless `freeze_exception_approved` is true. A merge that violates either half of the freeze gate is refused with `ERR_CODE_FREEZE_ACTIVE`. Finally the release's `risk_budget_consumed_points` must still be within the train's `risk_budget_points`, or the merge is refused with `ERR_RISK_BUDGET_EXCEEDED`.

A successful merge sets `state` to `MERGED`, stamps `merged_at` from the logical clock, and increments the change's `version`. It then unblocks dependents, and it does so **before** the release's derived fields are refreshed: every change on the release whose `state` is `BLOCKED_BY_DEPENDENCY` and whose **full** prerequisite set is now `MERGED` or `DEPLOYED` returns to `state` `APPROVED`, re-incrementing its release's `committed_change_count` by one and re-adding its `risk_score_final` to `risk_budget_consumed_points`. Only afterwards does the merge recompute the release's `rollback_plan_confirmed` — a boolean that is true exactly when every change on the release whose `state` is `MERGED` or `DEPLOYED` and whose `risk_class` is `HIGH` or `CRITICAL` has a non-null `rollback_plan` and `rollback_tested` true — together with `readiness_score_projected` in a single further mutation of the release, so that the projected score already reflects the dependents that were just unblocked and no longer carries their blocked-dependency penalty.

Withdrawal is the compensating exit, available to the author from six states — `DRAFT`, `RISK_CLASSIFIED`, `CAB_REVIEW`, `APPROVED`, `BLOCKED_BY_DEPENDENCY` and `DEFERRED` — and refused with `ERR_CHANGE_STATE_INVALID` from anywhere else. An optional `reason` may accompany it; it must be a string when present, but it is not stored on the change and appears in no response. The change moves to the terminal `state` `WITHDRAWN` and its `version` increases by one, and the release's `readiness_score_projected` is recomputed. Withdrawing from `state` `APPROVED` does strictly more: the release's `committed_change_count` drops by one and the change's `risk_score_final` is subtracted from `risk_budget_consumed_points`, restoring both quantities to exactly their pre-approval values; and every change whose `state` is `APPROVED` and which depends on the withdrawn change moves to `state` `BLOCKED_BY_DEPENDENCY`, each such dependent applying its own counter decrements in turn. Withdrawing from a state that never consumed budget — `DRAFT`, `RISK_CLASSIFIED`, `CAB_REVIEW`, `DEFERRED` — moves no counters, because there is nothing to compensate.

`BLOCKED_BY_DEPENDENCY` is therefore reachable from `APPROVED` by two routes — the train freeze cascade of §3.1 and the withdrawal of a prerequisite — and it is escaped by two routes: a prerequisite reaching `MERGED`, which requires the entire prerequisite set to be `MERGED` or `DEPLOYED`, or the train unfreezing, which requires only that no prerequisite is `DEFERRED`, `WITHDRAWN` or `REJECTED`. Both escapes restore the release counters identically.

### 3.5. The Feature Flag Inventory and Its Rollout Ladder

An `Engineer` registers a **feature flag** with a `key` that must be non-empty and unique across the entire inventory (a collision is `ERR_FLAG_KEY_DUPLICATE`), a non-empty `owner_user_id` naming the person accountable for retiring it, and an `expires_at` instant that is the contractual removal deadline. One optional input, `permanent`, defaults to false; setting it true marks the flag as an operational kill switch that is exempt from staleness debt and from cleanup enforcement forever. The server stamps `created_by_user_id` from `X-User-ID`. A new flag has `state` `DRAFT`, `cleanup_state` `COMPLIANT`, `current_exposure_pct` 0, `applied_step_count` 0, `kill_switch_engaged` false, `stale_debt_points` 0, and null `last_sweep_at` and `archived_at`.

Every flag carries **two independent state dimensions on the same record**. The rollout dimension, `state`, takes the values `DRAFT`, `ACTIVE_ROLLING_OUT`, `PAUSED`, `FULLY_ROLLED_OUT` and the terminal `ARCHIVED`. The hygiene dimension, `cleanup_state`, takes the values `COMPLIANT`, `WARNING`, `OVERDUE` and `ENFORCED` and evolves entirely separately, as §3.6 describes. The hygiene dimension is written only by the staleness computation and by archival, and it never blocks the rollout dimension except through the three operations named at rank 13 of the rejection ladder.

Exposure advances one rung at a time through **rollout steps**. Planning a rung is a create operation by the flag's owner that supplies a `target_pct`, a `soak_minutes` duration as a whole number of minutes that is zero or more, the mandatory `expected_feature_flag_version` of §2.7, and an optional `deployment_id` naming the canary deployment whose health will gate the rung (null for an ungated rung). Planning constrains the flag's rollout `state` not at all — only the cleanup enforcement of rank 13 can bar it — so a rung may be planned while the flag is `DRAFT`, `ACTIVE_ROLLING_OUT`, `PAUSED`, `FULLY_ROLLED_OUT` or even `ARCHIVED`. The step records its flag as `feature_flag_id`, begins in `state` `PLANNED` with null `previous_exposure_pct`, `soak_started_at` and `applied_at`, and receives a `step_index`: the count of that flag's steps whose `state` is anything other than `VOIDED`, plus one. Because voided rungs are excluded from that count, voiding a planned rung makes its index available again. Planning also increments the flag's `version` by one, which is precisely why the next plan must re-read the flag first.

The ladder geometry caps how far one rung may reach. Let the flag's `current_exposure_pct` be its exposure before this rung — 0 while `applied_step_count` is 0. The highest admissible `target_pct` is the smaller of 100 and the larger of 5 and three times the current exposure. A valid `target_pct` is therefore strictly greater than the current exposure and no greater than that ceiling; the floor is exclusive, the ceiling inclusive, and both comparisons are made at two-decimal precision. A violation is refused with `ERR_ROLLOUT_STEP_TOO_LARGE`. In plain terms, the first rung may reach at most 5 percent, a flag sitting at 5 percent may triple to at most 15, one at 15 may reach at most 45, and one at 45 may go straight to 100 because triple would exceed the cap. The required soak scales with the rung's ambition: a `target_pct` of 10 or less requires at least half an hour of soak, a `target_pct` above 10 and at most 50 requires at least a full hour, and a `target_pct` above 50 requires at least two hours. Supplying fewer minutes than required is refused with `ERR_SOAK_TOO_SHORT`.

A step's own lifecycle is `PLANNED`, `SOAKING`, and then one of the three terminal outcomes `APPLIED`, `ABORTED` and `VOIDED`. Starting a soak is the flag owner's act on a `PLANNED` step, and it carries the longest precondition list in the system — checked in exactly this order, which is the rank order of §2.8. The step must be `PLANNED` (`ERR_STEP_STATE_INVALID`); the flag's `state` must be `DRAFT` or `ACTIVE_ROLLING_OUT` (`ERR_FLAG_STATE_INVALID`); every change linked to the flag through a change-to-flag link must be in `state` `DEPLOYED` (`ERR_CHANGE_STATE_INVALID`); the caller must be the flag's owner (`ERR_NOT_RESOURCE_OWNER`) — so both of those cross-entity state checks outrank ownership; the flag's `cleanup_state` must not be `ENFORCED` (`ERR_FLAG_CLEANUP_ENFORCED`); no other step of the same flag may already be `SOAKING` (`ERR_STEP_ALREADY_SOAKING`); the step's `step_index` must equal the flag's `applied_step_count` plus one (`ERR_STEP_OUT_OF_ORDER`); and if the step names a `deployment_id`, that deployment's `delivery_state` must be `IN_PROGRESS` or `CANARY_SOAK` (`ERR_DEPLOYMENT_STATE_INVALID`), a check that comes last of all. On success the step becomes `SOAKING`, `soak_started_at` is stamped from the logical clock, `previous_exposure_pct` captures the flag's `current_exposure_pct` as it stands at that instant so that an abort can restore it verbatim, and the step's `version` increases by one. When the flag was still `DRAFT`, this is also the moment it becomes `ACTIVE_ROLLING_OUT`, with its own `version` increment.

Applying a soaked rung is likewise the owner's act, and its checks run in rank order too. The step must be `SOAKING` (`ERR_STEP_STATE_INVALID`), the flag's `state` must be `ACTIVE_ROLLING_OUT` (`ERR_FLAG_STATE_INVALID`) — again ahead of ownership — the caller must own the flag (`ERR_NOT_RESOURCE_OWNER`), and the logical clock must have reached `soak_started_at` advanced by `soak_minutes` — reaching that instant exactly is sufficient, and an earlier attempt is refused with `ERR_SOAK_NOT_ELAPSED`. If the step names a `deployment_id`, that deployment's `verification_state` must be `PASSING`, and an unhealthy or unevaluated canary is refused with `ERR_DEPLOYMENT_STATE_INVALID`. Application sets the step's `state` to `APPLIED`, stamps `applied_at`, increments the step's `version`, sets the flag's `current_exposure_pct` to the step's `target_pct`, raises the flag's `applied_step_count` by one, and recomputes the flag's `stale_debt_points` **and** its `cleanup_state` from the §3.6 evaluation — reading the flag as this application has just left it, and stamping no `last_sweep_at`. All of those flag fields are written together as one mutation, so the flag's `version` rises by exactly one. This single-flag re-evaluation only relabels: it never pauses the flag, never touches its steps, and never recomputes any release's readiness, however the `cleanup_state` moves. When the applied rung's `target_pct` is exactly 100, the flag additionally moves from `ACTIVE_ROLLING_OUT` to `FULLY_ROLLED_OUT` and its `current_exposure_pct` is set to the integer 100.

Pausing is the kill switch, and it is available to both an `Engineer` and an `SRE` — no ownership check applies, so an incident responder may pause a flag they do not own. It is permitted only from `state` `ACTIVE_ROLLING_OUT` (`ERR_FLAG_STATE_INVALID`), accepts an optional `reason` that must be a string when present but is not persisted anywhere, and sets `state` to `PAUSED` with a `version` increment. Two things a manual pause deliberately does **not** do: it leaves `kill_switch_engaged` unchanged, because that flag is reserved to mark pauses the *system* forced; and it leaves `current_exposure_pct` untouched, because pausing stops further advancement rather than retracting the traffic already exposed. Only a step abort restores exposure. When the same `ACTIVE_ROLLING_OUT → PAUSED` transition is instead forced by a system event — a canary abort, a release rollback, or cleanup enforcement — `kill_switch_engaged` is set to true.

Resuming closes the rollout cycle back to `ACTIVE_ROLLING_OUT`. It requires the flag to be `PAUSED` (`ERR_FLAG_STATE_INVALID`), the caller to be the flag's `owner_user_id` (`ERR_NOT_RESOURCE_OWNER`), and the flag's `cleanup_state` to be anything other than `ENFORCED` (`ERR_FLAG_CLEANUP_ENFORCED`). Resuming clears `kill_switch_engaged` back to false and increments the flag's `version`.

Archiving is permanent removal, and the owner may perform it from either `state` `FULLY_ROLLED_OUT` or `state` `PAUSED` — the two source states share identical preconditions and identical effects. Beyond ownership and those two source states, every change linked to the flag must have reached `state` `DEPLOYED`, `WITHDRAWN` or `REJECTED`, so that no live change is left unguarded; a linked change in any other state is refused with `ERR_CHANGE_STATE_INVALID`. Archival sets `state` to `ARCHIVED`, stamps `archived_at`, resets `cleanup_state` to `COMPLIANT` and `stale_debt_points` to 0, voids every one of the flag's steps that is still `PLANNED`, and increments the flag's `version`. It touches nothing else on the flag or its ladder: `kill_switch_engaged` and `current_exposure_pct` are left exactly as archival found them, and a step that is still `SOAKING` stays `SOAKING` rather than being aborted, so no exposure is restored.

### 3.6. Staleness Debt and Cleanup Enforcement

Flag inventories rot quietly, so the release office runs an explicit hygiene checkpoint. A `ComplianceOfficer` triggers a **cleanup sweep**, which re-evaluates staleness for every flag whose `state` is not `ARCHIVED`, and the same evaluation also runs for a single flag whenever one of its rungs is applied.

The evaluation is an integer debt with three components. A flag that is `permanent`, or whose `state` is `ARCHIVED`, has `stale_debt_points` of 0 and `cleanup_state` `COMPLIANT`, unconditionally — no further terms apply. Otherwise: the flag accrues **three points for every whole day the flag is past its deadline**, computed as the elapsed time from `expires_at` to the current logical-clock instant expressed in whole 86400-second days with any partial day discarded, and zero when the clock has not yet passed `expires_at`. It accrues a further **20 points** when the flag is `PAUSED` while its `current_exposure_pct` is greater than zero — a half-rolled-out flag nobody is driving is the worst kind of debt. It accrues a further **15 points** when the flag is an orphan, meaning it has no change-to-flag links at all. The three components are summed and then capped at 100, and the result is written to `stale_debt_points`.

The hygiene tier is then selected from that debt, and the ladder is evaluated in order with **inclusive** thresholds. A debt of 60 points or more is `ENFORCED`. Otherwise a debt of 30 points or more is `OVERDUE`. Otherwise any debt greater than zero is `WARNING`. Otherwise, even at zero debt, the flag is still `WARNING` when its `expires_at` is within seven days of the current logical clock — that is, when `expires_at` minus the current instant is at most 604800 seconds, a condition that is also satisfied when the deadline has already slipped past by less than a full day. Only a flag that clears all four tests is `COMPLIANT`. Exactly 60 points is `ENFORCED` and exactly 30 points is `OVERDUE`.

The sweep does more than relabel. On every flag it evaluates, it rewrites `stale_debt_points` and `cleanup_state` and stamps `last_sweep_at` with the current logical-clock instant — and `last_sweep_at` is only ever written by a sweep, never by the single-flag re-evaluation that a step application performs. Then it enforces: a flag that has newly become `ENFORCED` and whose `state` is `ACTIVE_ROLLING_OUT` is moved to `PAUSED` with `kill_switch_engaged` set to true; on each such flag, every step whose `state` is `PLANNED` becomes `VOIDED`, and every step whose `state` is `SOAKING` becomes `ABORTED` with the flag's `current_exposure_pct` restored to that step's `previous_exposure_pct`. Finally, `readiness_score_projected` is recomputed on every release that has a change linked to an affected flag, because a flag entering `OVERDUE` or `ENFORCED` costs its linked releases three readiness points. An **affected** flag means one this sweep genuinely altered — its `stale_debt_points`, `cleanup_state` or `last_sweep_at` actually moved, or the sweep paused it — so a sweep repeated at an unchanged logical-clock instant, which rewrites nothing, recomputes no release at all.

The sweep reports what it did as a summary object rather than a resource: `evaluated_count` flags examined, `warning_count`, `overdue_count` and `enforced_count` flags in each of those tiers after the rewrite, `paused_flag_count` flags forced to `PAUSED`, `voided_step_count` steps voided, and `aborted_step_count` steps aborted.

Enforcement is a wall, not a fine. While a flag's `cleanup_state` is `ENFORCED`, three operations are refused with `ERR_FLAG_CLEANUP_ENFORCED`: resuming the flag, starting a soak on any of its steps, and planning a new rung. The only ways out are to clear the debt — by linking the flag to a change, by fully rolling it out, or by moving the flag's deadline — or to archive the flag, which resets its hygiene dimension outright.

### 3.7. Environments, Deployment Windows and Canary Delivery

A `PlatformAdmin` registers each **environment** the release office deploys into. An environment has a globally unique non-empty `name` (a duplicate is reported as `ERR_INVALID_REQUEST`), a `tier` of `DEV`, `STAGING` or `PROD`, and a daily permitted deployment window expressed in whole UTC hours: `deploy_window_start_hour_utc` is the inclusive first hour and must be between 0 and 23, while `deploy_window_end_hour_utc` is the exclusive bound and must be between 1 and 24 and strictly greater than the start hour. Four optional inputs complete it: `cooldown_minutes`, the mandatory quiet buffer appended after every occupied window on this environment, defaulting to 30; `blackout_start_at` and `blackout_end_at`, the inclusive endpoints of a change-blackout span, both null when no blackout is configured — and a blackout is in force only when **both** endpoints are present, so an environment carrying just one of them behaves exactly like one carrying neither; and `requires_compliance_evidence`, defaulting to false, whose true value marks the environment as **regulated** and makes a sealed evidence packet a precondition of shipping any release deployed there. A new environment starts with `active_deployment_count` 0 — the number of its deployments whose `delivery_state` is `IN_PROGRESS` or `CANARY_SOAK` — and a null `last_deployment_end_at`, which tracks the `window_end_at` of the most recently created deployment on this environment whose `delivery_state` is neither `ABORTED` nor `ROLLED_BACK`. That field is a lagging record rather than a live one: it is recomputed **only** when a deployment on the environment completes or is rolled back. Reserving a window leaves it untouched — it stays null until the environment's first completion — and so does a canary abort, which therefore leaves behind the value the last completion wrote.

An `SRE` reserves a **deployment** window for a release that has already been cut. The reservation supplies the target `environment_id`, the window's inclusive `window_start_at` and exclusive `window_end_at` (which must be strictly later), a `strategy` of `CANARY`, `ALL_AT_ONCE` or `BLUE_GREEN`, and the two abort criteria `abort_error_rate_pct`, any number greater than zero, and `abort_latency_p95_ms`, a whole number of milliseconds of at least 1. Two optional inputs are `canary_pct`, the share of traffic on the canary fleet, greater than 0 and at most 100 and defaulting to 5; and `min_sample_count`, the minimum canary request volume below which analysis is inconclusive, zero or more and defaulting to 20. The deployment records its `release_id`, begins with `delivery_state` `SCHEDULED`, `verification_state` `PENDING`, `health_score` 0, and null `completed_at` and `rolled_back_at`, and triggers a recomputation of the release's `evidence_packet_required` — a boolean that is true exactly when at least one deployment of the release targets an environment whose `requires_compliance_evidence` is true.

Reservation enforces three temporal rules on top of the release's phase requirement. The **window geometry** rule requires the reserved span to fall on a single UTC date, with the `window_start_at` hour at or after the environment's `deploy_window_start_hour_utc` and `window_end_at` no later than that same date at `deploy_window_end_hour_utc`; a window that straddles midnight or reaches outside the permitted hours is refused with `ERR_DEPLOY_WINDOW_VIOLATION`. The **occupancy** rule compares the requested half-open span against every other deployment on the same environment whose `delivery_state` is neither `ABORTED` nor `ROLLED_BACK`, each of those spans extended at the end by the environment's `cooldown_minutes`; any intersection is refused with `ERR_DEPLOYMENT_WINDOW_CONFLICT`. And the release must be in `phase` `CUT`, `STABILIZING` or `RELEASED`, or the reservation is refused with `ERR_RELEASE_PHASE_INVALID`.

The deployment carries **two parallel state dimensions that advance independently on the same record**. The delivery dimension, `delivery_state`, runs `SCHEDULED`, `IN_PROGRESS`, `CANARY_SOAK`, `COMPLETED`, and the terminal `ABORTED` and `ROLLED_BACK`. The verification dimension, `verification_state`, runs `PENDING`, `PASSING`, `FAILING`, `INCONCLUSIVE` and `WAIVED`. Neither dimension's value constrains the other's transitions except where a rule below says so explicitly.

Starting a deployment is an `SRE` act on a `SCHEDULED` deployment. Its release must be in `phase` `CUT`, `STABILIZING` or `RELEASED` (`ERR_RELEASE_PHASE_INVALID`); the logical clock must lie at or after `window_start_at` and strictly before `window_end_at` (`ERR_DEPLOY_WINDOW_VIOLATION`); and the clock must not lie inside the environment's closed blackout span from `blackout_start_at` to `blackout_end_at` (`ERR_BLACKOUT_ACTIVE`). Starting sets `delivery_state` to `IN_PROGRESS`, increments the deployment's `version`, raises the environment's `active_deployment_count` by one, and bubbles up: a release still in `phase` `CUT` moves to `phase` `STABILIZING` with its own `version` increment. This is the only way a release enters stabilization.

Health data arrives as individual **health samples**, ingested by an `SRE` or a `PlatformAdmin`. Each sample records its `deployment_id`, an `observed_at` instant used for window membership, a `cohort` of `CANARY` or `BASELINE`, a `request_count` of at least 1, an `error_count` of at least 0 and no greater than `request_count`, and the sample's `latency_p95_ms` as a whole number of milliseconds, zero or more. Ingestion imposes no precondition on the deployment: a sample is accepted whatever the deployment's `delivery_state`, `SCHEDULED`, `COMPLETED`, `ABORTED` and `ROLLED_BACK` included. The **first** `CANARY`-cohort sample ingested for a deployment whose `strategy` is `CANARY` and whose `delivery_state` is `IN_PROGRESS` moves that deployment to `delivery_state` `CANARY_SOAK`. Samples for non-canary strategies, and `BASELINE` samples, never cause that transition.

**Canary analysis** is run explicitly by an `SRE` over a chosen half-open observation window, supplied as `window_start_at` and `window_end_at` with the end strictly after the start, and produces a canary evaluation record. Like ingestion, it has no delivery-state precondition and no strategy precondition — an evaluation may be run against a deployment in any `delivery_state` and on any `strategy`. It considers only that deployment's health samples whose `cohort` is `CANARY` and whose `observed_at` is at or after the window start and strictly before the window end; `BASELINE` samples are excluded from every term, `sample_count` included. Rows are processed in ascending `observed_at`, breaking ties by ascending `created_at`; the order does not change the result but is pinned for reproducibility. The evaluation's `sample_count` is the sum of `request_count` over those rows.

If `sample_count` is strictly below the deployment's `min_sample_count`, the analysis stops there: `verdict` is `INCONCLUSIVE`, `abort_triggered` is false, and `error_rate_pct_rounded`, `latency_p95_ms` and `weighted_health_score` are all recorded as 0. A `min_sample_count` of 0 therefore never yields `INCONCLUSIVE`: with no qualifying rows at all the analysis proceeds on an empty set, treats the error rate and the latency as 0, and lands on `verdict` `PASS` with `weighted_health_score` 100. Otherwise the analysis proceeds in three pinned steps. **First**, each row's own error rate is computed as its `error_count` divided by its `request_count`, expressed as a percentage, and **rounded half up to one decimal place** — this rounding happens per row, before any weighting. **Second**, `error_rate_pct_rounded` is the request-weighted mean of those already-rounded per-row rates: multiply each row's rounded rate by that row's `request_count`, sum the products, divide by `sample_count`, and round the quotient half up to two decimal places. Summing raw error counts over raw request counts and rounding once at the end is a different algorithm and yields a different number; it is not what this specification requires. The evaluation's `latency_p95_ms` is the **maximum** `latency_p95_ms` across the qualifying rows, and 0 when there are no rows. **Third**, two components are formed at full precision and only the final score is rounded: the error component is 100 minus sixty times the ratio of `error_rate_pct_rounded` to the deployment's `abort_error_rate_pct`, floored at 0; the latency component is 100 minus forty times the ratio of the evaluation's `latency_p95_ms` to the deployment's `abort_latency_p95_ms`, also floored at 0. The `weighted_health_score` is six tenths of the error component plus four tenths of the latency component, rounded half up to two decimal places.

The abort criteria are then applied with **inclusive** comparisons: `abort_triggered` is true when `error_rate_pct_rounded` is at or above the deployment's `abort_error_rate_pct`, or when the evaluation's `latency_p95_ms` is at or above the deployment's `abort_latency_p95_ms`. The `verdict` is `FAIL` when `abort_triggered` is true and `PASS` otherwise. The deployment's `verification_state` is then written from the verdict — `PASSING` for `PASS`, `FAILING` for `FAIL`, `INCONCLUSIVE` for `INCONCLUSIVE` — and its `health_score` is set to the evaluation's `weighted_health_score`, so `health_score` always mirrors the latest-created evaluation and stays 0 until the first one runs.

An abort is a four-hop cascade, and it fires from `delivery_state` `IN_PROGRESS` and from `CANARY_SOAK` and from nowhere else: when an `abort_triggered` verdict lands on a deployment in any other `delivery_state` — `SCHEDULED`, `COMPLETED`, `ABORTED` or `ROLLED_BACK` — the evaluation is still recorded and the deployment's `verification_state` and `health_score` are still written, but not one hop of the cascade below runs. **Hop one**: the deployment's `delivery_state` becomes `ABORTED` and its `verification_state` becomes `FAILING`, its `version` increases by one, and the environment's `active_deployment_count` drops by one. **Hop two**, caused by hop one: every rollout step whose `deployment_id` is this deployment and whose `state` is `SOAKING` becomes `ABORTED`, and its flag's `current_exposure_pct` is restored to that step's `previous_exposure_pct` while the flag's `applied_step_count` stays unchanged. **Hop three**, caused by hop two: each such flag whose `state` is `ACTIVE_ROLLING_OUT` moves to `PAUSED` with `kill_switch_engaged` set to true. **Hop four**, caused by hop three: every change linked to those flags whose `state` is `DEPLOYED` has its `deployment_verified` set to false, and each affected release's `verified_change_count` is recomputed.

Completing a deployment is permitted from `delivery_state` `IN_PROGRESS` or `CANARY_SOAK`, and both source states behave identically. Verification governs whether completion is allowed. A deployment whose `strategy` is `CANARY` may only complete while its `verification_state` is `PASSING` or `WAIVED`. A deployment on any other strategy may complete while its `verification_state` is `PENDING`, `PASSING` or `WAIVED` — so a `FAILING` or `INCONCLUSIVE` verification blocks completion regardless of strategy. Either violation is refused with `ERR_CANARY_NOT_PASSING`. The optional `waive_verification` input offers a narrow escape: setting it true is honoured **only** when the deployment's `verification_state` is currently `INCONCLUSIVE` **and** the target environment's `tier` is not `PROD`, and it moves `verification_state` to `WAIVED`. A waiver requested on a production tier, or from any state other than `INCONCLUSIVE`, is likewise refused with `ERR_CANARY_NOT_PASSING`. A successful completion sets `delivery_state` to `COMPLETED`, stamps `completed_at`, increments the deployment's `version`, lowers the environment's `active_deployment_count` by one, recomputes the environment's `last_deployment_end_at`, and recomputes the release's `evidence_packet_required`.

Rolling a deployment back is permitted only from `delivery_state` `COMPLETED`, and it may be requested directly by an `SRE` with an optional `reason` — a string when present, stored nowhere — or forced by an incident decision as §3.8 describes. The first hop sets `delivery_state` to `ROLLED_BACK`, stamps `rolled_back_at`, increments the deployment's `version`, and recomputes the environment's `last_deployment_end_at`. The second hop, caused by the first, rolls the release back when its `phase` is `STABILIZING` or `RELEASED` — and that release rollback runs its own cascade, described in §3.8.

### 3.8. Incidents, Rollback Cascades and Forward Fixes

An `SRE` or an `Engineer` reports an **incident** with a `title`, a `severity` of `SEV1`, `SEV2`, `SEV3` or `SEV4`, a `detected_at` detection instant, and the `release_train_id` of the train whose recent releases are suspects. The reporter's `X-User-ID` is stamped as `reporter_user_id`, the incident starts in `state` `OPEN` with a null `decision` and a null `decided_at`, and the server immediately computes the linkage — once, at creation, and never again.

Linkage is chronological. The candidate releases are those on the incident's train whose `phase` is `CUT`, `STABILIZING` or `RELEASED`, whose `cut_at` is at or before the incident's `detected_at`, and where the elapsed time from `cut_at` to `detected_at` is no more than 72 hours. Both of those interval bounds are inclusive, and releases whose `phase` is `ROLLED_BACK`, `OPEN` or `FROZEN` are never candidates. The candidates are ranked by `cut_at` descending — most recently cut first — with ties broken by `created_at` ascending, and the first ranked candidate becomes the incident's `linked_release_id`. When no release qualifies, `linked_release_id` is null. The deployment is then chosen from that selected release only: among its deployments whose `delivery_state` is `COMPLETED`, rank by `window_start_at` descending with ties broken by `created_at` ascending, and take the first as `linked_deployment_id`; when the selected release has no completed deployment, or when no release was selected at all, `linked_deployment_id` is null. Ranking and tie-breaking use those timestamps only — resource identifiers never participate in the ordering.

The release office then records a **decision** on an `OPEN` incident, which moves it to the terminal `state` `DECIDED`, stamps `decided_at`, and increments its `version`. A second attempt on an already-decided incident is refused with `ERR_INCIDENT_ALREADY_DECIDED`. Three decisions exist and their admissibility differs. A `ROLLBACK` decision requires the incident to have a non-null `linked_release_id` whose release is in `phase` `STABILIZING` or `RELEASED`, and a non-null `linked_deployment_id` whose deployment is in `delivery_state` `COMPLETED`. A `NO_ACTION` decision requires the `severity` to be `SEV3` or `SEV4` — the release office may not simply walk away from a `SEV1` or `SEV2`. A `FORWARD_FIX` decision has no additional requirement and leaves the release and all of its deployments completely untouched, on the understanding that the fix will ride a later release. An inadmissible `ROLLBACK` or `NO_ACTION` is refused with `ERR_NO_LINKED_RELEASE`.

A `ROLLBACK` decision fires the deepest cascade in the system, and its hops are pinned. Hop one takes the linked deployment from `delivery_state` `COMPLETED` to `ROLLED_BACK`, exactly as a directly requested deployment rollback would. Hop two, caused by hop one, takes the release from `phase` `STABILIZING` or `RELEASED` to the terminal `phase` `ROLLED_BACK`, stamping `rolled_back_at` and incrementing the release's `version`. Hop three, caused by hop two, walks the release's changes out through their flag guards: every feature flag reachable through a change-to-flag link from a change of this release whose flag `state` is `ACTIVE_ROLLING_OUT` moves to `PAUSED` with `kill_switch_engaged` set to true. Hop four, caused by hop three, cleans up each just-paused flag's ladder: every step whose `state` is `PLANNED` becomes `VOIDED`, and every step whose `state` is `SOAKING` becomes `ABORTED` with the flag's `current_exposure_pct` restored to that step's `previous_exposure_pct`. Alongside those hops, every change of the rolled-back release whose `state` is `DEPLOYED` **keeps** `state` `DEPLOYED` but has its `deployment_verified` set back to false, and the release's `verified_change_count` is recomputed to 0. The release-rollback effects are identical whether the release was `STABILIZING` or `RELEASED` when the rollback arrived.

### 3.9. Release Notes, Evidence Packets and the Final Release Gate

A `ReleaseManager` generates a **release-notes document** for a release by naming an `audience` of `CUSTOMER` or `INTERNAL`; generation is available at any point in the release's life and creates a document recording its `release_id` in `state` `DRAFT` with `generated_at` stamped from the logical clock and `published_at` null. Generation selects its content immediately. The candidate set is the release's change requests whose `state` is `MERGED` or `DEPLOYED` and whose `merged_at` is at or before the release's `cut_at` — an inclusive upper bound. Changes that are `DEFERRED`, `WITHDRAWN`, `REJECTED`, `APPROVED` or `BLOCKED_BY_DEPENDENCY` are excluded from the candidate set entirely, and therefore never appear in the exclusion count either. For an `INTERNAL` audience, every candidate is included. For a `CUSTOMER` audience, a candidate is included only when its `customer_facing` is true **and** its `summary_customer_facing` is both non-null and not the empty string — an author who ticked the customer-facing box but never wrote the copy does not make the customer notes. The included changes are ordered by `merged_at` ascending with ties broken by `created_at` ascending, never by identifier, and their identifiers are recorded in that order as `included_change_ids`. `entry_count` is the number of included changes, and `excluded_change_count` is the number of candidates minus `entry_count`.

Publication requires the document to be in `state` `DRAFT`, or it is refused with `ERR_NOTE_ALREADY_PUBLISHED`; requires `entry_count` to be at least 1, or it is refused with `ERR_EMPTY_RELEASE_NOTES` — generating an empty document is legal, publishing one is not; and requires the release's `phase` to be `CUT`, `STABILIZING` or `RELEASED`, or it is refused with `ERR_RELEASE_PHASE_INVALID`. Publication sets `state` to `PUBLISHED`, stamps `published_at`, increments the document's `version`, and has one cross-entity effect that is easy to miss: every `DRAFT` evidence packet belonging to the same release recomputes its `base_index`, its `waiver_credit_points` and its `completeness_index`, because published customer notes are themselves an evidence item.

A `ComplianceOfficer` assembles a **compliance evidence packet** for a release, supplying only the `expected_release_version` of §2.7. The packet records its `release_id`, begins in `state` `DRAFT`, and computes its indices immediately; creating it moves any prior `DRAFT` packet of the same release to the terminal `state` `SUPERSEDED` with that packet's own `version` increment, and increments the release's `version` by one. The packet starts with `waiver_credit_points` 0, `waiver_count` 0, an empty `waivers` array, and null `sealed_at` and `sealed_by_user_id`.

Completeness is assessed against six weighted evidence items, each satisfied or not by facts about the packet's release. The item codes are exactly these:

- `approvals_complete`, weight 25 — satisfied when every change of the release whose `state` is `MERGED` or `DEPLOYED` has, for each lane its own `risk_class` requires, at least one approval in that lane with `decision` `APPROVE`. A release whose merged changes are all `LOW` satisfies this trivially, since `LOW` requires no lane.
- `rollback_plans`, weight 20 — satisfied when every change of the release whose `state` is `MERGED` or `DEPLOYED` and whose `risk_class` is `HIGH` or `CRITICAL` has a non-null `rollback_plan` and `rollback_tested` true.
- `canary_pass`, weight 15 — satisfied when at least one deployment of the release on an environment whose `tier` is `PROD` has `verification_state` `PASSING`.
- `freeze_discipline`, weight 15 — satisfied when every change of the release whose `state` is `MERGED` or `DEPLOYED` has a `merged_at` strictly earlier than the release's `freeze_at`, or, alternatively, when the release's `freeze_exception_approved` is true.
- `flag_hygiene`, weight 15 — satisfied when no feature flag reachable through a change-to-flag link from any `MERGED` or `DEPLOYED` change of the release has a `cleanup_state` of `OVERDUE` or `ENFORCED`.
- `release_notes`, weight 10 — satisfied when at least one release-notes document of the release has `audience` `CUSTOMER` and `state` `PUBLISHED`.

Changes that are `DRAFT`, `RISK_CLASSIFIED`, `WITHDRAWN` or otherwise not merged never affect any item.

The index is then built in three pinned steps. **Step one** computes `base_index` as the sum of the weights of the satisfied items, **excluding waivers entirely**; it is an integer between 0 and 100. **Step two** selects the waiver credit cap from that `base_index`, and this is the subtle part: the cap is 15 when `base_index` is at least 85, 10 when it is at least 70, 5 when it is at least 50, and 0 otherwise. The tier is keyed on `base_index` and **not** on the running total — re-selecting the tier after adding credit is the wrong reading and produces a larger index. **Step three** computes the credit and clamps: sum, over every entry in `waivers`, half of that item's weight; round the sum half up to two decimal places; then take the smaller of that raw credit and the cap, and record the result as `waiver_credit_points`. The `completeness_index` is the smaller of 100 and `base_index` plus `waiver_credit_points`. Alongside them, `missing_items` lists the item codes that are neither satisfied nor waived, always in the canonical order the six items are listed above rather than in any order of discovery, and `waiver_count` is the number of entries in `waivers`, which appear in the order they were recorded.

Waiving an item is how a compliance officer accepts a documented gap. The packet must be in `state` `DRAFT`, or the request is refused with `ERR_PACKET_STATE_INVALID`. The request supplies an `item_code` naming one of the six items and a non-empty `justification`, and three conditions must all hold, tested in this order, or the waiver is refused with `ERR_WAIVER_NOT_ALLOWED`: the packet's `base_index` must be at least 50, so that the cap tier is greater than zero and a waiver could actually earn credit; the named item must currently be unsatisfied; and it must not already have been waived. "Currently" means as the packet last recorded it, not as the release stands this instant: both the `base_index` the waiver is judged and capped against and the per-item satisfaction it consults are the figures the packet computed when it was assembled, refreshed only by the recomputation a release-notes publication triggers. Release facts that have moved since — a change merged, a canary turned `PASSING` — do not re-satisfy an item or lift the `base_index` until one of those recomputations runs, and a waiver never recomputes `base_index` itself. A successful waiver appends an entry to `waivers` containing that `item_code`, the supplied `justification`, and `waived_by_user_id` taken from `X-User-ID`, then recomputes `waiver_count`, `waiver_credit_points`, `completeness_index` and `missing_items` — always re-selecting the cap tier from `base_index`.

Sealing freezes the evidence. The packet must be in `state` `DRAFT` (`ERR_PACKET_STATE_INVALID`) and its `completeness_index` must be at least 90, or sealing is refused with `ERR_EVIDENCE_INCOMPLETE`. A sealed packet moves to the terminal `state` `SEALED`, stamps `sealed_at` from the logical clock and `sealed_by_user_id` from `X-User-ID`, and increments its `version`.

The release's final gate pulls all of these threads together. A `ReleaseManager` declares a release shipped only from `phase` `STABILIZING`; any other phase is refused with `ERR_RELEASE_PHASE_INVALID`. Four substantive conditions then apply, and their order matters. The release must have at least one deployment whose `delivery_state` is `COMPLETED` on an environment whose `tier` is `PROD`. If that production environment's `requires_compliance_evidence` is true, the release must also have an evidence packet in `state` `SEALED`, and a missing seal is refused with `ERR_EVIDENCE_PACKET_REQUIRED` — a check that sits above the readiness gate, so a regulated release that is both unevidenced and unready reports the missing packet rather than the low score. The release's `readiness_score_attested` must be at least 80, and its `rollback_plan_confirmed` must be true; a failure of either of those, or the absence of a completed production deployment, is refused with `ERR_RELEASE_NOT_READY`.

Shipping sets `phase` to `RELEASED`, stamps `released_at` from the logical clock, and increments the release's `version`. It then promotes the work: every change on the release whose `state` is `MERGED` moves to `state` `DEPLOYED` with `deployment_verified` set to true, and `verified_change_count` is recomputed as the count of the release's changes whose `deployment_verified` is true. Those promotions are exactly what a later rollback undoes — the changes stay `DEPLOYED`, but their `deployment_verified` reverts to false and `verified_change_count` falls back to 0.

## 4. Endpoint Definitions

Operations that bring a new resource into existence — registering an environment, opening a release, authoring a change request, declaring a dependency edge or a flag link, recording an approval, creating a flag, planning a rollout step, reserving a deployment window, ingesting a health sample, running a canary evaluation, reporting an incident, generating release notes, or assembling an evidence packet — return `201 Created`. Operations that modify an existing resource, including every state transition, every cascade trigger, the cleanup sweep, waiving an evidence item, sealing a packet, and repositioning the logical clock, return `200 OK`. Every path below is mounted at the API root; there is no shared prefix. The request and response bodies are not repeated here — they are defined by the workflow narratives in §3.
