# Grill Seasonal Ops API — Product Requirements Document

## 1. Introduction

Grill retail is a clock-driven business. Demand concentrates violently into a spring selling window, which means production must be built through the winter, committed to retail channels before the first warm weekend, and cleared aggressively once the season turns. Wrapped into that core seasonal loop are three long-lived obligations that outlast any single season: assembly services performed by third-party technicians at retail stores and in customers' homes, warranty coverage that differs by component and can run a full decade on burners, and a parts-support promise that extends years past the discontinuation of a model. Connected grills add a fourth thread — app pairing and firmware stewardship — that begins at the point of sale and feeds registration data back into the warranty pipeline.

This document specifies the Grill Seasonal Ops API, the system of record for that entire operating cycle. It governs the season itself as a first-class lifecycle (planning, winter build, channel allocation, in-season selling, clearance, model transition), the inventory lots built against a season, the allocation offers channels compete for under credit and capacity limits, the sales that consume those allocations, the assembly jobs scheduled against sales, the warranty claims adjudicated against registered sales, the parts catalog with its supersession chains and restock-driven backorder filling, and the connected devices consumers pair to their grills. Every rule below — every threshold, every boundary, every rounding step — is normative.

The API is mounted under `/grillops`. All time-dependent behavior in the system is driven by a server-side logical clock, not wall-clock time; this is what makes seasonal posture, coverage expiry, and quality windows deterministic. Section 2 defines the system-wide contracts (envelope, pagination, roles, validation order). Section 3 walks the business workflows in narrative form and is where the detailed rules live. Section 4 is the endpoint index and Section 5 the error catalogue; both are deliberately summary-level and must be read together with Section 3.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

All interactions with the API must be authenticated through a set of mandatory HTTP headers. Each request must include `X-User-ID` to identify the acting user and `X-User-Role` to specify their operational capacity. The system recognizes five distinct roles: `PlannerAdmin`, `ChannelRep`, `Assembler`, `ServiceAgent`, and `AppUser`. A request missing either header, or carrying an `X-User-Role` value outside these five declared roles, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401).

Access to specific operations is restricted by role, and for action-style endpoints the restriction runs down to the individual action. An attempt to perform an operation outside the caller's designated role — or an action the role is not permitted for on that endpoint — is rejected with `ERR_UNAUTHORIZED_ROLE` (HTTP 403). The action-level permissions are: `PlannerAdmin` may revise an allocation offer but may never accept, decline, or release one; a `ChannelRep` may never revise an offer; an `Assembler` may only start and complete jobs; an `AppUser` may only call device endpoints.

The five roles divide into two identity kinds. When `X-User-Role` is `ChannelRep`, `X-User-ID` is the `id` of the acting `ChannelAccount`; ownership checks on any resource that references a channel compare the resource's channel foreign key to `X-User-ID`. When `X-User-Role` is `Assembler`, `X-User-ID` is the `id` of the acting `Assembler`; ownership checks on a job compare the job's assigned-assembler field to `X-User-ID`, and an assembler reading their own record is resolved the same way. When `X-User-Role` is `PlannerAdmin`, `ServiceAgent`, or `AppUser`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but does not compare it to any entity's `id`. An entity-backed caller acting on a resource owned by a different account — a `ChannelRep` touching another channel's allocation or sale, an `Assembler` starting a job assigned to someone else — is rejected with `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

For endpoints that return lists of resources, pagination is controlled via query parameters. The `limit` parameter specifies the maximum number of items to return. If not provided, it defaults to 10, with a minimum of 1 and a maximum of 100. The `offset` parameter specifies the number of items to skip and defaults to 0.

Unless otherwise specified, all list endpoints return resources sorted by their creation timestamp in ascending order.

Paginated and non-paginated list-based responses include the following fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. The Logical Clock

A single server-side logical clock is the sole source of "now" for the entire system. At startup the clock reads exactly `2026-09-01T00:00:00Z`; the server must never fall back to wall-clock time under any circumstance. Every timestamp the system stamps on its own — a sale's `sold_at`, a claim's `claim_date`, a denial's `denied_at`, a registration's `registered_at`, an offer's `offered_at`, a discontinuation's `discontinued_at`, and every entry appended to an assembler's no-show and completion histories — is taken from this logical clock.

A `PlannerAdmin`-only test-driving capability advances the clock: the caller supplies a `to_iso8601` instant and receives the clock's new value as `current_utc`. Clock-dependent derived state — coverage determinations, quality windows, obligation windows, markdown tiers — is recomputed lazily from the clock on the next read after an advance, so a clock move is immediately visible everywhere it matters.

### 2.5. Common Resource Properties

All twelve resources in this system — Season, GrillModel, ChannelAccount, InventoryLot, Allocation, Assembler, AssemblyJob, Sale, WarrantyClaim, PartSku, PartsOrder, and ConnectedDevice — carry the same standard set of system-managed fields:

- **`id` (string):** A unique, system-generated identifier for the resource, formatted as a UUID with no type prefix.
- **`created_at` (string):** An ISO 8601 timestamp in UTC with three fractional digits (e.g., `2026-09-01T08:15:00.123Z`) indicating when the resource was first created.
- **`updated_at` (string):** An ISO 8601 UTC timestamp with three fractional digits indicating when the resource was last modified. This field is refreshed upon any change to the resource's properties.
- **`version` (integer):** A system-managed integer that increments by exactly 1 on every modification to the resource, including modifications caused by cascades, automatic transitions, and recomputation-driven state flips.

Recomputations described anywhere in this document — lot availability flips, exposure refreshes, quality-score updates — are mutations of the entity they land on: each one refreshes `updated_at` and increments `version` on that entity, and each is visible in the response of the request that triggered it.

### 2.6. Money, Rates, and Rounding Conventions

Every monetary amount in the system is an integer number of cents — prices, fees, costs, credit limits, settlements. Every proportional rate is expressed in basis points, where 10000 basis points equal exactly 100 percent; a subsidy of 2000 basis points therefore means 20 percent. Where a calculation produces a non-integer cent or unit value, the rounding rule is stated alongside the calculation and is part of the contract: "round half up" means the commercial rounding where a fraction of one half or greater rounds away from zero, and "floor" means truncation toward negative infinity. Two calculations in this system pin an ordering of rounding steps — the assembly fee and the clearance price — and in both cases rounding each component before summation is mandatory; summing first and rounding once produces different cent values and is non-compliant. Channel attach rates are the one non-integer quantity exposed by the API: they are stored at exactly 4 decimal places, rounded half up.

### 2.7. Optimistic Concurrency Control

Exactly two write operations in this API carry an optimistic-concurrency field, and both reject a stale caller with `ERR_STALE_VERSION` (HTTP 412):

1. **Creating an allocation offer** requires the request to carry `expected_season_version`, the `version` of the target Season as the client last observed it. Because every allocation offer created against a season increments that season's `version` by 1, an earlier offer for the same season-channel-model tuple that has just legitimately superseded a prior offer advances the season's version, and any other planner still holding the pre-supersede version is working from a stale allocation book. If `expected_season_version` does not equal the season's current `version`, the create is rejected with `ERR_STALE_VERSION` (HTTP 412).
2. **Responding to an allocation offer** requires the request to carry `expected_allocation_version`, the `version` of the Allocation as the client last observed it. A `PlannerAdmin` revision legitimately re-offers the same allocation with a new unit count while it remains `OFFERED`, and that revision bumps the allocation's `version`; an acceptance carrying the pre-revision version must not bind the channel to stale terms. If `expected_allocation_version` does not equal the allocation's current `version`, the respond call is rejected with `ERR_STALE_VERSION` (HTTP 412).

Both fields are non-optional on their respective endpoints. No other endpoint in the system accepts a version field; optimistic concurrency applies nowhere else.

### 2.8. Nested Resource Retrieval and Existence Checking

Several resources are addressed beneath a parent — lots beneath a season or a model, claims and devices beneath a sale. When an endpoint path contains multiple resource identifiers, the system validates the existence of each identifier in strict left-to-right order and rejects the request immediately with the 404 code of the first identifier that does not resolve: `ERR_SEASON_NOT_FOUND` for a season, `ERR_MODEL_NOT_FOUND` for a model, `ERR_ALLOCATION_NOT_FOUND` for an allocation, `ERR_ASSEMBLER_NOT_FOUND` for an assembler, `ERR_JOB_NOT_FOUND` for an assembly job, `ERR_SALE_NOT_FOUND` for a sale, `ERR_CLAIM_NOT_FOUND` for a warranty claim, `ERR_PART_NOT_FOUND` for a part, `ERR_PARTS_ORDER_NOT_FOUND` for a parts order, and `ERR_DEVICE_NOT_FOUND` for a connected device. Identifiers carried in a request body are resolved with the same discipline: a `channel_account_id` that names no existing channel yields `ERR_CHANNEL_NOT_FOUND`, and likewise for any other body-carried reference. A request to list lots beneath a non-existent season therefore fails as `ERR_SEASON_NOT_FOUND` before any lot-level logic runs.

### 2.9. The Validation Ladder

Every request is evaluated against a fixed ladder of check categories. When a single request violates several rules at once, the category with the lowest priority number wins and alone determines the response; later violations are masked until the earlier one is fixed. The ladder, from first to last:

1. **Authentication.** The `X-User-ID` and `X-User-Role` headers must be present and the role must be one of the five declared roles, else `ERR_UNAUTHENTICATED` (401).
2. **Role authorization.** The acting role must be listed for the endpoint and, on action endpoints, permitted for the specific action requested, else `ERR_UNAUTHORIZED_ROLE` (403).
3. **Existence.** Path-template identifiers resolve to existing entities, validated left to right, else the per-entity 404 code of §2.8.
4. **Entity-backed ownership.** A `ChannelRep`'s `X-User-ID` must equal the target's channel for allocation respond and view, sale create and transition; an `Assembler`'s `X-User-ID` must equal the job's assigned assembler for start and complete, or the assembler record being viewed, else `ERR_FORBIDDEN_OWNERSHIP` (403).
5. **State gates.** The target entity must be in a state from which the requested transition exists — posture gates, terminal lockdowns, and invalid-from transitions — else the specific 409 code: `ERR_INVALID_STATE`, `ERR_SEASON_POSTURE_FORBIDDEN`, `ERR_ALLOCATION_NOT_ACTIONABLE`, `ERR_JOB_NOT_SCHEDULABLE`, `ERR_CLAIM_NOT_ADJUDICATABLE`, `ERR_SALE_NOT_REGISTERED`, `ERR_SALE_RETURNED`, `ERR_DEVICE_NOT_PAIRED`, or `ERR_DEVICE_ALREADY_PAIRED`.
6. **Body well-formedness.** Required fields present, enums valid, date orderings respected (the season's five milestone dates in strict ascending order; `window_end` after `window_start`), serial list length equal to quantity, a supersession successor in the same chain at a higher position, an out-of-coverage approval carrying a justification, a settlement carrying actual labor — else `ERR_VALIDATION` (400).
7. **Referenced-entity state and compatibility.** The assigned assembler is certified (`ERR_ASSEMBLER_NOT_CERTIFIED`, 409); the model is sellable (`ERR_MODEL_NOT_SELLABLE`, 409); an active allocation exists for the sale's tuple (`ERR_NO_ACTIVE_ALLOCATION`, 409); the part is not obsolete or unfulfillably superseded (`ERR_PART_UNAVAILABLE`, 409); the part fits the sale's model (`ERR_PART_INCOMPATIBLE`, 422).
8. **Interval and deadline rules.** Season in-season intervals must not overlap (`ERR_SEASON_OVERLAP`, 409); same-sale job windows must not overlap (`ERR_ASSEMBLY_WINDOW_CONFLICT`, 409); an assembler's padded schedule must not conflict (`ERR_ASSEMBLER_BUFFER_CONFLICT`, 409); a free parts order must fall within the model's support obligation (`ERR_PARTS_OBLIGATION_EXPIRED`, 422); a claim reopen must fall inside its window (`ERR_REOPEN_WINDOW_EXPIRED`, 409).
9. **Capacity, uniqueness, and quota.** Lot capacity on allocation writes (`ERR_ALLOCATION_CAPACITY_EXCEEDED`, 409); serial uniqueness (`ERR_DUPLICATE_SERIAL`, 409); assembler concurrency cap (`ERR_MAX_CONCURRENT_JOBS`, 409); one paired device per sale (`ERR_DEVICE_ALREADY_PAIRED`, 409); and chain-position uniqueness within a supersession chain, which is reported as `ERR_VALIDATION` (400).
10. **Fiscal limits, always last.** The channel credit check on allocation create and revise (`ERR_CREDIT_LIMIT_EXCEEDED`, 422) and the goodwill cap on claim approval (`ERR_GOODWILL_CAP_EXCEEDED`, 422).

Because fiscal checks sit at the bottom of the ladder, a request that is simultaneously over credit and malformed will surface the malformed body first; an approval that is simultaneously over the goodwill cap and out of state will surface the state error first.

### 2.10. Derived State and Immediate Consistency

Many fields in this system are computed rather than written: a lot's `units_available` and `units_consumed`, a channel's `outstanding_exposure_cents`, `accessory_attach_rate`, and `fuel_attach_rate`, an assembler's `active_job_count`, `official_quality_bp`, and `provisional_quality_bp`, a sale's `unit_price_cents` and attach flags, a claim's `coverage_determination` and settlement figures, a parts order's `resolved_part_id`, `free_of_charge`, and `total_cost_cents`. The consistency model is immediate: every mutation triggered by a request — including cascades into other entities — is applied and visible within that same request's response. A sale that consumes the last unit of an allocation returns a response in which the allocation is already `CONSUMED`; a no-show that trips the suspension threshold returns a response in which the assembler is already `SUSPENDED` and the cascade-unassigned jobs are already back to `REQUESTED`.

## 3. Business Logic & Workflows

### 3.1. The Season and Its Posture Ladder

Everything in the operating year hangs off a **Season**. A `PlannerAdmin` opens one by supplying a unique `name` (for example "Grilling Season 2026"), the calendar `year` it sells into, five milestone datetimes — `build_start` when the winter build window opens, `allocation_open` when channel allocation opens, `in_season_start` when the spring peak opens, `clearance_start` when end-of-season clearance opens, and `season_end` when the season closes — plus `demand_forecast_units`, the total forecast demand across all models. The five milestones must be strictly ascending: `build_start` before `allocation_open` before `in_season_start` before `clearance_start` before `season_end`; any other ordering is `ERR_VALIDATION`. One further calendar rule is global: the closed interval from `in_season_start` through `season_end` — both endpoints inclusive — must be strictly disjoint from the same interval of every other Season, and touching endpoints count as a conflict. A new season whose in-season interval so much as kisses a neighbor's is rejected with `ERR_SEASON_OVERLAP`.

A season is born in `PLANNING` posture and walks a one-directional ladder: `PLANNING → BUILD → ALLOCATION → IN_SEASON → CLEARANCE → TRANSITIONED → CLOSED`. A `PlannerAdmin` advances it one step at a time by naming the desired `target_status`, which must be exactly the next rung — asking to skip from `BUILD` straight to `IN_SEASON`, or to advance a `CLOSED` season, is rejected with `ERR_INVALID_STATE`. Each successful advance increments the season's `version` by 1. Two of the steps carry calendar guards measured against the logical clock: entering `IN_SEASON` requires the clock to have reached the season's `in_season_start`, and entering `CLEARANCE` requires the clock to have reached `clearance_start`; entering `TRANSITIONED` requires the clock to be at or past `season_end`. Entering `ALLOCATION` from `BUILD` requires instead that at least one inventory lot exist for the season, and its side effect activates the build: every lot of the season still `BUILDING` flips to `AVAILABLE`. The two late-season advances carry heavy cascades of their own — the clearance waterfall and the model-transition sweep — detailed in §3.4 and §3.2 respectively.

Posture is a gate, not a suggestion. Inventory lots can only be created while the season is `PLANNING` or `BUILD`; allocation offers can only be written while the season is `ALLOCATION`; sales can only be recorded while the season is `IN_SEASON` or `CLEARANCE`. Attempting any of these against a season in the wrong posture is rejected with `ERR_SEASON_POSTURE_FORBIDDEN`.

### 3.2. Grill Models and the Long Parts Obligation

A **GrillModel** is the sellable product: a unique `model_code` such as "GX-100", a `model_family` naming the product family shared across model years, a `model_year`, a list `base_price_cents`, and a `demand_share_bp` — the model's share of the season's demand forecast in basis points, between 0 and 10000. The family-and-year pair is a naming convention rather than a foreign key: next-year model transition matches a model to the member of the same `model_family` whose `model_year` is exactly one higher. Models also carry the warranty schedule that claims will later be judged against: `burner_coverage_years` defaulting to 10 years, `grate_coverage_years` defaulting to 5 years, `electronics_coverage_years` defaulting to 3 years, and `other_coverage_years` defaulting to 2 years, each measured from the sale date. Alongside them sits `parts_support_years`, defaulting to 7 years — the parts-availability obligation that survives discontinuation — and `current_firmware_version`, defaulting to "1.0.0", the firmware stamped onto newly paired connected devices.

A model is born `ACTIVE` and lives through `ACTIVE → CLEARANCE_ELIGIBLE → DISCONTINUED → PARTS_ONLY → RETIRED`, driven by `PlannerAdmin` lifecycle actions naming an `action`. Marking clearance-eligible moves `ACTIVE → CLEARANCE_ELIGIBLE`. Discontinuing moves either `ACTIVE` or `CLEARANCE_ELIGIBLE` to `DISCONTINUED`, stamping `discontinued_at` with the logical clock and computing `support_obligation_until` as `discontinued_at` plus the model's `parts_support_years` years; while a model has never been discontinued, both fields stay null. The parts-only rung is guarded by that obligation: marking parts-only requires the logical clock to be strictly later than `support_obligation_until` — the obligation must have fully expired — and attempting it earlier is `ERR_INVALID_STATE`. Retirement from `PARTS_ONLY` to `RETIRED` is unguarded. Every lifecycle action increments the model's `version` by 1.

Discontinuation also arrives by cascade. When a season advances `CLEARANCE → TRANSITIONED`, every model with at least one inventory lot in that season is discontinued in the same request — `discontinued_at` stamped, `support_obligation_until` computed exactly as above — before the season's lots and allocations are swept (§3.4). Sellability follows the lifecycle: a sale may only be recorded against a model that is `ACTIVE` or `CLEARANCE_ELIGIBLE`, and an allocation offer may only target an `ACTIVE` model; anything else is `ERR_MODEL_NOT_SELLABLE`.

### 3.3. Building Inventory and Sizing the Build

Against each season, a `PlannerAdmin` plans production as **InventoryLot** records, created beneath the season while it is `PLANNING` or `BUILD`. A lot names the `model_id` being built, a planned `build_week` label such as "2026-W06", and the `units_built` produced into it. The lot's `season_id` comes from the season it is created under. Lots are born `BUILDING` and flip to `AVAILABLE` when the season advances into `ALLOCATION`; thereafter availability bookkeeping drives two automatic flips — when `units_available` reaches 0 after an allocation create or revise, the lot becomes `DEPLETED`, and when a release, decline, expiry, or supersede recapture lifts `units_available` back above 0, it returns to `AVAILABLE`. When the season finally transitions out of clearance, every lot of the season — whether `AVAILABLE` or `DEPLETED` — is swept to the terminal `CLOSEOUT`.

Availability is a pure derivation. A lot's `units_available` equals its `units_built`, minus the sum of `allocated_units` over all allocations of the same season and model in `OFFERED`, `ACCEPTED`, `PARTIALLY_CONSUMED`, or `CONSUMED`, minus the sum of `committed_units` over allocations of the same season and model in `RELEASED`, `EXPIRED`, or `SUPERSEDED`. Its `units_consumed` is the sum of `committed_units` over all allocations of the same season and model regardless of state, starting from 0. Both are recomputed on every allocation-affecting event.

Each lot also carries two build-sizing recommendations, computed at creation. The forward-looking figure, `recommended_build_forward_units`, projects from history: take the Season with the greatest `year` strictly below this season's `year`, sum `units_consumed` over all of that prior season's lots, and if no such prior season exists, fall back to this season's `demand_forecast_units`; multiply that base by the growth multiplier of 11000 basis points — that is, 110 percent of the base, a 10 percent growth assumption — then by the model's `demand_share_bp` share, and floor to a whole unit. Concretely, the recommendation is the floor of the base times 11000 divided by 10000, times `demand_share_bp` divided by 10000. The chronological figure, `recommended_build_actual_units`, annualizes observed sell-through once the season is live: while the season is `IN_SEASON` or `CLEARANCE`, count the complete 7-day weeks elapsed between `in_season_start` and the logical clock, floor that to a whole number, and never let it drop below 1; the recommendation is then the floor of the lot's `units_consumed` multiplied by 26 — the length of the in-season annualization window in weeks — divided by those elapsed weeks. Before the season reaches `IN_SEASON`, `recommended_build_actual_units` is null. The actual variant is recomputed on every consumption change while the season is `IN_SEASON` or `CLEARANCE`, so the two variants routinely disagree: the forward figure ignores the current season's run-rate entirely, and the actual figure ignores the prior season.

### 3.4. Channels, Allocation Offers, and the Clearance Waterfall

Retail reach is modeled as **ChannelAccount** records created by a `PlannerAdmin`: a partner `name`, a `channel_type` of `HOME_CENTER`, `SPECIALTY_DEALER`, or `DIRECT`, an optional `service_tier` of `STANDARD` or `PREMIUM` (defaulting to `STANDARD`), an `allocation_priority` used as the redistribution rank in the clearance waterfall, and a `credit_limit_cents` capping the channel's outstanding allocation exposure. The channel's assembly-fee subsidy is derived, never written: a `HOME_CENTER` carries a `subsidy_bp` of 2000 (a 20 percent subsidy), a `SPECIALTY_DEALER` carries 1000 (10 percent), and a `DIRECT` channel carries 0. A channel's `outstanding_exposure_cents` is likewise derived as the sum, over that channel's allocations in `ACCEPTED` or `PARTIALLY_CONSUMED`, of each allocation's uncommitted remainder — `allocated_units` minus `committed_units` — multiplied by the model's `base_price_cents`. The channel's attach rates are defined with the sales that feed them in §3.5.

Once a season stands in `ALLOCATION`, a `PlannerAdmin` offers units to channels by creating an **Allocation** naming `season_id`, `channel_account_id`, `model_id`, and `allocated_units`. The season must be in `ALLOCATION` posture (`ERR_SEASON_POSTURE_FORBIDDEN` otherwise), the model must be `ACTIVE` (`ERR_MODEL_NOT_SELLABLE` otherwise), and the request must carry `expected_season_version` per §2.7. Two guards then apply, capacity before credit per the ladder. Capacity: after any same-tuple supersession recapture described below, the offered `allocated_units` — reckoned against the sum of the lot's active allocations — must not exceed the lot's `units_available`; an exact fit passes, and one unit over is `ERR_ALLOCATION_CAPACITY_EXCEEDED`. Credit: the channel's `outstanding_exposure_cents` plus the new offer's `allocated_units` times the model's `base_price_cents` must not exceed `credit_limit_cents`; equality passes, one cent over is `ERR_CREDIT_LIMIT_EXCEEDED`. At most one allocation per (season, channel, model) tuple may be live — `OFFERED`, `ACCEPTED`, `PARTIALLY_CONSUMED`, or `CONSUMED` — so creating a second offer for a tuple that already has a live one supersedes the first: the old allocation goes to `SUPERSEDED`, its `allocated_units` collapses to its `committed_units` (zero for a never-accepted offer), and the freed units return to lot availability before the new offer's capacity check runs. A successful create stamps `offered_at` from the logical clock, sets the allocation `OFFERED` with `committed_units` at 0, and — critically for the OCC rule of §2.7 — increments the season's `version` by 1.

The channel answers through the respond operation, which always carries `expected_allocation_version` (§2.7). Each action has its own valid-from states — accept, decline, and revise belong to `OFFERED`, release belongs to `ACCEPTED` and `PARTIALLY_CONSUMED` — and any action attempted on an allocation in a state that does not offer it, such as accepting a `DECLINED`, `RELEASED`, `EXPIRED`, `SUPERSEDED`, or `CONSUMED` allocation, is `ERR_ALLOCATION_NOT_ACTIONABLE`. An **accept** by the owning `ChannelRep` — their `X-User-ID` must equal the allocation's `channel_account_id` — moves `OFFERED → ACCEPTED` and recomputes the channel's exposure. A **decline** moves `OFFERED → DECLINED`, zeroes `allocated_units`, returns the offered units to the lot's `units_available` (which may flip a `DEPLETED` lot back to `AVAILABLE`), and recomputes exposure. A **revise** is the `PlannerAdmin`'s re-offer: it supplies a new `allocated_units`, recaptures the current offer first, then re-runs the capacity and credit checks against the refreshed numbers, and rewrites the offer in place (`OFFERED → OFFERED`) — this version bump is exactly what makes a concurrently held acceptance go stale. A **release** by the owning channel moves `ACCEPTED` or `PARTIALLY_CONSUMED → RELEASED`, collapsing `allocated_units` to `committed_units` so the unconsumed remainder returns to the lot. Every respond increments the allocation's `version` by 1.

Sales consume allocations (the mechanics are in §3.5). The first sale against an `ACCEPTED` allocation moves it to `PARTIALLY_CONSUMED`, adding the sale's quantity to `committed_units`; when cumulative `committed_units` reaches `allocated_units` — whether in one step or gradually — the allocation becomes `CONSUMED`. A return pushes back: decrementing `committed_units` below `allocated_units` reopens a `CONSUMED` allocation to `PARTIALLY_CONSUMED`, and a return against a `PARTIALLY_CONSUMED` allocation simply reduces `committed_units`. Each consumption event recomputes the lot's `units_consumed` and the channel's exposure, and increments the allocation's `version`.

Two season advances sweep allocations. Entering `CLEARANCE` expires every offer of the season still `OFFERED`: such an allocation goes to `EXPIRED` with `allocated_units` zeroed (its `committed_units` is 0 by construction), returning the offered units to lot availability. Entering `TRANSITIONED` expires everything still live — `OFFERED`, `ACCEPTED`, and `PARTIALLY_CONSUMED` allocations all go to `EXPIRED` with `allocated_units` collapsed to `committed_units` and the remainder returned to the lot.

The advance into `CLEARANCE` additionally runs the **allocation waterfall**, which recaptures underperforming commitments and redistributes them to channels that are actually selling. Its evaluation order is pinned. Step one snapshots every allocation of the season in `ACCEPTED` or `PARTIALLY_CONSUMED` and computes each one's consumption rate as the floor of 10000 times `committed_units` divided by `allocated_units`; these rates are frozen on this pre-release snapshot and never recomputed during the run. Step two releases the laggards: any allocation whose rate falls strictly below 5000 basis points — under 50 percent consumed — gives up its unconsumed remainder: `allocated_units` collapses to `committed_units`, the allocation becomes `RELEASED`, and the released units flow back into the lot's `units_available` and accumulate into a redistribution pool. Step three ranks the survivors — allocations still `ACCEPTED` or `PARTIALLY_CONSUMED` with a rate of at least 5000 basis points — by their channel's `allocation_priority`, highest first, breaking ties by the channel's `created_at` in ascending order, never by identifier. Step four deals the pool out in that order: each candidate absorbs a share equal to the smaller of two figures — the floor of the original pool times 4000 divided by 10000 (that is, 40 percent of the pool as it stood when redistribution began) and whatever units remain in the pool at that moment — adding the share to its `allocated_units`, deducting it from the lot's `units_available`, and draining the pool accordingly, continuing while units remain. Step five leaves any remainder in the lot's `units_available`.

### 3.5. Selling Season: Sales, Clearance Pricing, and Attach Rates

A **Sale** is recorded by the selling channel itself: the acting `ChannelRep`'s `X-User-ID` must equal the `channel_account_id` on the payload, else `ERR_FORBIDDEN_OWNERSHIP`. The payload names `season_id`, `model_id`, `channel_account_id`, the `quantity` of units in the transaction, and optionally `serials`, `accessories`, and a `proof_of_purchase_token`. The season must be `IN_SEASON` or `CLEARANCE` (`ERR_SEASON_POSTURE_FORBIDDEN`), the model `ACTIVE` or `CLEARANCE_ELIGIBLE` (`ERR_MODEL_NOT_SELLABLE`), and an active allocation — `ACCEPTED` or `PARTIALLY_CONSUMED` — must exist for the (season, channel, model) tuple, else `ERR_NO_ACTIVE_ALLOCATION`. When `serials` is present its length must equal `quantity` (`ERR_VALIDATION`), and every serial must be globally unique across all sales, else `ERR_DUPLICATE_SERIAL`. The `accessories` array carries attach items, each an object with a `sku`, an `accessory_type` of `COVER`, `TOOLS`, `FUEL`, or `OTHER`, and a `unit_price_cents`; from it the system derives `accessory_count` (the length of the array, defaulting to 0) and three booleans — `has_cover`, `has_tools`, and `has_fuel` — each true when at least one accessory of that type is present. Creation stamps `sold_at` from the logical clock; that timestamp anchors all warranty coverage arithmetic later.

Registration can happen at the moment of sale. When a `proof_of_purchase_token` is supplied at creation, the sale is born `REGISTERED` with `registered_at` stamped; otherwise it is born `SOLD`. A later registration — the sale-registration transition carrying a `proof_of_purchase_token`, driven by the owning `ChannelRep` — moves `SOLD → REGISTERED` and stamps `registered_at` then. Device pairing also registers a sale as a side effect, synthesizing the token "APP-PAIR" when none exists (§3.9).

Pricing is computed, never taken from the client: any `unit_price_cents` a caller sends is ignored. While the season is `IN_SEASON`, the unit price is simply the model's `base_price_cents` — no markdown, no subsidy. Once the season is `CLEARANCE`, the clearance engine prices each unit through a pinned pipeline. First, the engine computes how many complete 7-day weeks have elapsed between the season's `clearance_start` and the sale's `sold_at`, flooring the day count divided by 7. The markdown tier follows from that week index: weeks 0 through 2 take a 15 percent markdown; weeks 3 and 4 — the second tier begins at week index 3 — take 30 percent; week 5 and beyond — the third tier begins at week index 5 — take 50 percent. Second, the engine measures the lot's coverage ratio: the floor of 10000 times the (season, model) lot's `units_available` divided by its `units_built` — with a denominator of zero treated as 1 so the ratio is defined even for an empty build. Coverage of 6000 basis points or more — 60 percent of the build still unsold — signals overstock and adds 10 percentage points to the markdown; coverage of 2000 basis points or less — 20 percent or less remaining — signals understock and subtracts 5 percentage points as relief; anything between adjusts by 0. Both boundaries are inclusive. Third, the adjusted markdown is clamped to lie between 0 and a hard ceiling of 70 percent. Fourth, the markdown is applied: the after-markdown price is the model's `base_price_cents` times (100 minus the markdown percent) divided by 100, rounded half up to integer cents. Fifth and finally, the selling channel's subsidy is applied to that rounded figure — multiplying by (10000 minus the channel's `subsidy_bp`) and dividing by 10000, again rounded half up — yielding the `unit_price_cents` stored on the sale. The two round-half-up steps are pinned in exactly this order; rounding once at the end produces different cent values and is non-compliant. The identical cart priced in week 2 and week 5 of clearance can therefore differ twice over — once from the tier jump and once from a coverage adjustment that flipped in between.

Returns unwind a sale. A return moves `SOLD → RETURNED` or `REGISTERED → RETURNED`; the sale-transition surface is shared between the owning `ChannelRep` (whose `X-User-ID` must equal the sale's `channel_account_id`) and `ServiceAgent` operators, who are not ownership-scoped. Returning an already `RETURNED` sale is `ERR_SALE_RETURNED`. Four things happen together: the live allocation for the (season, channel, model) tuple — `ACCEPTED`, `PARTIALLY_CONSUMED`, or `CONSUMED` — has its `committed_units` reduced by the returned `quantity`, and a `CONSUMED` allocation that drops below `allocated_units` reopens to `PARTIALLY_CONSUMED`; the lot's `units_consumed` is recomputed; the channel's exposure and attach rates are recomputed; and every warranty claim of this sale still in flight — `SUBMITTED`, `UNDER_REVIEW`, `INFO_REQUESTED`, `ESCALATED`, or `REOPENED` — is force-denied, moving to `DENIED` with `denied_at` stamped from the logical clock. Claims already `APPROVED` or `SETTLED` are untouched.

Attach rates summarize a channel's selling behavior and are recomputed on every sale creation and every return for that channel. The denominator counts the channel's sales in `SOLD` or `REGISTERED` — `RETURNED` sales are excluded from both numerator and denominator. The `accessory_attach_rate` is the count of those sales with `accessory_count` of at least 1, divided by the denominator, rounded half up to 4 decimal places. The `fuel_attach_rate` uses the same denominator with a numerator counting sales where `has_fuel` is true, also at 4 decimal places. When the denominator is empty, both rates are exactly 0.0000 — an empty channel reports zeros rather than an error.

### 3.6. Assembly Programs: Fees, Scheduling, and Assembler Standing

Assembly labor comes from third-party **Assembler** companies, registered by a `PlannerAdmin` with a `name`, an optional `certification_level` of `BASIC`, `CERTIFIED_PRO`, or `MASTER` (defaulting to `BASIC`), the `service_regions` they cover as an array of region codes, and an optional `max_concurrent_jobs` cap (defaulting to 4) on jobs they may hold in `SCHEDULED` or `IN_PROGRESS` at once. An assembler is born `APPLIED` and moves through `CERTIFIED`, `SUSPENDED`, and the terminal `DECERTIFIED`. Certification — `APPLIED → CERTIFIED` — is a `PlannerAdmin` action. Suspension — `CERTIFIED → SUSPENDED` — may be invoked by a `ServiceAgent` or `PlannerAdmin`, and also fires automatically as described below. Reinstatement — `SUSPENDED → CERTIFIED` — is a `PlannerAdmin` certification action guarded by the assembler's rolling quality: it requires `provisional_quality_bp` of at least 7000, so an assembler whose recent record is still poor cannot be waved back in. Decertification — from either `CERTIFIED` or `SUSPENDED` — is a `PlannerAdmin` action guarded by the lifetime record: it requires `official_quality_bp` of 4000 or less, so only a genuinely degraded assembler can be pushed out. An attempt that fails either guard is rejected. Every status action increments the assembler's `version` by 1.

Two quality scores are recomputed on every completion and every no-show. The lifetime score, `official_quality_bp`, starts from a perfect 10000 basis points and subtracts 1200 basis points per lifetime no-show, floored at 0 — every no-show counts forever, and completions earn no credit; this is the figure the decertify guard reads. The rolling score, `provisional_quality_bp`, looks only at the last 90 days measured back from the logical clock — events exactly 90 days old are included in the window — and starts from 10000, subtracts 1200 basis points per no-show inside that window, adds a 25-basis-point completion bonus per completion inside the window, and clamps the result into the 0-to-10000 range; this is the figure the reinstatement guard reads. The two scores are fed by two append-only histories, `no_show_history` and `completion_history`, which record the logical-clock timestamp of each event, alongside the lifetime counters `no_show_count` and `jobs_completed` and the live `active_job_count`. The same event history therefore yields two different standings: a veteran with three ancient no-shows sits at 6400 official but can hold a spotless 10000 provisional.

An **AssemblyJob** is requested against a sale by a `ChannelRep` or a `ServiceAgent`, naming the `sale_id`, a `job_type` of `RETAIL_ASSEMBLY` or `IN_HOME`, and — for in-home work — an optional one-way `distance_mi` defaulting to 0. The job is born `REQUESTED` with no assigned assembler and null `window_start`/`window_end`; scheduling happens later at assignment. Its `fee_cents`, however, is priced immediately at creation through the fee engine. The base component is 7999 cents for every job. In-home work adds a flat 5005-cent surcharge, plus travel: the miles beyond the 15 included miles — `distance_mi` minus 15, never below zero — at 149 cents per mile. Retail-assembly jobs carry neither component: surcharge and travel are both zero. The selling channel's `subsidy_bp` then discounts the job, and the rounding order is load-bearing: each of the three components is individually multiplied by (10000 minus the subsidy) and divided by 10000, rounded half up to integer cents, and the three rounded figures are summed to form `fee_cents`. Summing first and rounding once is explicitly non-compliant — the per-component rounding is what makes a direct-channel in-home job price differently from the same job sold through a home center.

Assignment is a `ServiceAgent` action that supplies the `assembler_id`, `window_start`, and `window_end`, and it runs from either `REQUESTED` (first scheduling) or `NO_SHOW` (rescheduling); assigning a job in any other state is `ERR_JOB_NOT_SCHEDULABLE`. Five checks then guard the booking, and when several fail at once the ladder of §2.9 decides which error surfaces — a malformed window (`window_end` not strictly after `window_start`, `ERR_VALIDATION`) precedes the certification check, which precedes the two overlap checks, which precede the capacity check. The five: the named assembler must exist and be `CERTIFIED`, else `ERR_ASSEMBLER_NOT_CERTIFIED`; the window must be well-formed; no other active job — `SCHEDULED` or `IN_PROGRESS` — on the same sale may overlap the requested window under a half-open overlap test where a window ending exactly when another begins is allowed, else `ERR_ASSEMBLY_WINDOW_CONFLICT`; no active job of the same assembler may overlap, except that a new `IN_HOME` job is first padded by 45 minutes on both sides of its window — the travel buffer — before the same half-open test, while `RETAIL_ASSEMBLY` jobs are never padded, else `ERR_ASSEMBLER_BUFFER_CONFLICT`; and the assembler's `active_job_count` must be strictly below `max_concurrent_jobs`, so a booking that would bring the count to the cap is refused with `ERR_MAX_CONCURRENT_JOBS`. A successful assignment stores the `assembler_id` and both windows and adds 1 to the assembler's `active_job_count`.

From there the assigned assembler drives execution: starting moves `SCHEDULED → IN_PROGRESS` and completing moves `IN_PROGRESS → COMPLETED`, and both require the acting `Assembler`'s `X-User-ID` to equal the job's `assembler_id`, else `ERR_FORBIDDEN_OWNERSHIP` (attempting either from the wrong state is `ERR_JOB_NOT_SCHEDULABLE`). Completion subtracts 1 from `active_job_count`, adds 1 to `jobs_completed`, appends the logical clock to `completion_history`, and recomputes both quality scores. A `ServiceAgent` may cancel a job from `REQUESTED` or `SCHEDULED` — the latter also subtracting 1 from the assignee's `active_job_count` — moving it to the terminal `CANCELLED`.

The no-show path is where the lifecycle bites. When a `ServiceAgent` marks a `SCHEDULED` job as a no-show, three hops unfold in order within the same request. First the assembler's counters move: `no_show_count` gains 1, the logical clock is appended to `no_show_history`, `active_job_count` loses 1, and both quality scores are recomputed. Second, if `no_show_count` has reached the suspension threshold of 3 lifetime no-shows, the assembler auto-transitions `CERTIFIED → SUSPENDED`. Third, that suspension cascades: every other `SCHEDULED` job of the assembler returns to `REQUESTED` with its `assembler_id` cleared and its windows nulled — while jobs already `IN_PROGRESS` are deliberately not touched. The no-showed job itself keeps its `assembler_id` for audit; only its status changes to `NO_SHOW`, from which a later reassignment reschedules it under the same five checks. A manual suspension by an operator carries the same cascade of scheduled jobs back to `REQUESTED`. Decertification is harsher: decertifying a `CERTIFIED` assembler not only unassigns their scheduled jobs but cancels their in-progress work outright, moving every `IN_PROGRESS` job to `CANCELLED`; decertifying from `SUSPENDED` needs no cascade, because suspension has already cleared the schedule.

### 3.7. Warranty Claims: Coverage, Adjudication, and Settlement

A **WarrantyClaim** is filed by a `ServiceAgent` against a sale, and registration is the gate: filing against a sale still `SOLD` is rejected with `ERR_SALE_NOT_REGISTERED`, and filing against a `RETURNED` sale with `ERR_SALE_RETURNED`. The filing names the `sale_id`, the failed `component` — one of `BURNER`, `GRATE`, `ELECTRONICS`, or `OTHER` — a free-text `failure_description`, and optionally a `serial_number`, which must be a member of the sale's `serials` list whenever that list is non-empty (a mismatch is `ERR_VALIDATION`). A claim is born `SUBMITTED` with `goodwill` false; creation stamps `claim_date` from the logical clock and immediately computes and stores the `coverage_determination`, which never changes afterward.

Coverage is per component and anchored to the sale. The coverage window runs from the sale's `sold_at` for the model's per-component term — `burner_coverage_years`, `grate_coverage_years`, `electronics_coverage_years`, or `other_coverage_years` according to the claimed component, defaulting to 10, 5, 3, and 2 years respectively. A claim whose `claim_date` falls on or before the expiry day is `IN_COVERAGE` — the exact expiry day still counts. A claim falling after expiry but on or before 90 days past it is `GOODWILL_ELIGIBLE`. Anything later is `OUT_OF_COVERAGE`. Comparisons are at day granularity.

Adjudication is a `ServiceAgent` workflow over an eight-state loop. Reviewing moves `SUBMITTED → UNDER_REVIEW`, and likewise `REOPENED → UNDER_REVIEW`. Requesting information moves `UNDER_REVIEW → INFO_REQUESTED`, and submitting it returns `INFO_REQUESTED → UNDER_REVIEW`. Escalating moves `UNDER_REVIEW → ESCALATED`. Denying moves either `UNDER_REVIEW` or `ESCALATED → DENIED`, stamping `denied_at` from the logical clock — and recall from §3.5 that a returned sale force-denies claims in any of these in-flight states. A denied claim may be reopened — `DENIED → REOPENED` — only while the logical clock remains within 30 days of `denied_at`; once that reopen window has elapsed the attempt is `ERR_REOPEN_WINDOW_EXPIRED`. Any adjudication action attempted from a state that does not offer it — settling before approval, reopening a settled claim — is `ERR_CLAIM_NOT_ADJUDICATABLE`.

Approval is where money enters, and it comes in two strengths. Approving from `UNDER_REVIEW` first computes the provisional settlement — the catalog part cost plus the fixed labor allowance for the claimed component: a burner claim schedules 3200 cents of parts and 4500 cents of labor, a grate claim 2400 and 4500, an electronics claim 4800 and 7500, and any other component 1500 and 2500. From `UNDER_REVIEW`, that provisional figure must not exceed the goodwill cap of 10000 cents, else the approval is rejected with `ERR_GOODWILL_CAP_EXCEEDED` and the claim must be escalated first; note that an electronics claim's provisional settlement is 12300 cents, which sits above the cap, so electronics claims can never be approved directly from review. Approving from `ESCALATED` bypasses the cap entirely. Coverage interacts with approval as well: approving an `OUT_OF_COVERAGE` claim requires a non-empty `goodwill_justification` — omitting it is `ERR_VALIDATION` — and sets the claim's `goodwill` flag to true; approving while the determination is `GOODWILL_ELIGIBLE` also sets `goodwill` to true, with no justification demanded. A successful approval from either state stores the computed `provisional_settlement_cents` and lands the claim in `APPROVED`.

Settlement finalizes the money. Settling an `APPROVED` claim requires the caller to supply `actual_labor_cents` — omitting it is `ERR_VALIDATION` — and does three things atomically. First, it auto-creates a parts order for the claim: quantity 1, with `fulfillment_type` `WARRANTY` when the claim is `IN_COVERAGE` and `GOODWILL` otherwise, the claim reference stamped onto the order's `warranty_claim_id`. The part for that order is chosen by a deterministic selector over the catalog: eligible candidates share the claim's `component`, list the sale's model code among their `compatible_model_codes`, sit in `AVAILABLE` or `LOW_STOCK`, and hold at least 1 unit of `stock_quantity`; candidates rank by `unit_cost_cents` ascending, ties broken by `created_at` ascending — never by identifier. When the eligible pool is empty, no order is created, `settlement_parts_order_id` stays null, and the schedule's catalog part cost stands in as the actual part cost; otherwise the order's resolved cost is used and `settlement_parts_order_id` records it. Second, the final settlement is computed: `final_settlement_cents` is that actual part cost plus the supplied `actual_labor_cents`, and `settlement_delta_cents` is the final figure minus the stored provisional — so the same claim data settles at a different figure than it was approved at whenever real part costs or real labor diverge from the schedule. Third, the claim moves to the terminal `SETTLED`. Claims of a sale are listed through the sale's claims view, which doubles as the claim read surface and accepts an optional `status` filter.

### 3.8. The Parts Catalog, Supersession Chains, and Fulfilment

Parts support is a years-long obligation, and the catalog is built to survive product churn. A `PlannerAdmin` creates a **PartSku** with a unique `part_number` such as "BRN-4500-A", the `component` it serves (`BURNER`, `GRATE`, `ELECTRONICS`, or `OTHER`), a non-empty `compatible_model_codes` array naming the model codes the part fits, a `supersession_chain_id` grouping parts that replace one another over time, a `chain_position` giving the part's place in that chain — unique within its chain, so a duplicate position is `ERR_VALIDATION` — a catalog `unit_cost_cents`, and an opening `stock_quantity` defaulting to 0. The chain is a plain attribute, not a foreign key: parts sharing a `supersession_chain_id` form an ordered sequence in which each part's successor is the chain member with the next higher `chain_position`.

Stock level derives status automatically. A part with more than 10 units on hand — the low-stock threshold — is `AVAILABLE`; at 10 units or fewer but above zero it is `LOW_STOCK`; at exactly zero it is `EXHAUSTED`. These flips fire on every stock movement, including creation with low or zero opening stock, and each flips the part's `version` up by 1. A restock action carrying a `quantity` of at least 1 (anything less is `ERR_VALIDATION`) adds to `stock_quantity`; a restocked part lands `AVAILABLE` when the resulting stock exceeds 10, and `LOW_STOCK` otherwise — restocking an exhausted part by fewer than 11 units therefore leaves it `LOW_STOCK`, not `AVAILABLE`. Restocking also drains the backorder queue: every `BACKORDERED` parts order resolved to this part is allocated in `created_at` ascending order — ties broken by the order's `seq_no`, never by identifier — each one moving to `ALLOCATED` with its quantity deducted from stock, until either the stock or the backorders run out. A part may also be explicitly marked exhausted. Supersession is operator-driven from `AVAILABLE`, `LOW_STOCK`, or `EXHAUSTED`: the caller names a `successor_part_id` which must exist, share the part's `supersession_chain_id`, and hold a strictly higher `chain_position`, else `ERR_VALIDATION`; the part then moves to `SUPERSEDED`. Only a superseded part can be marked obsolete, moving `SUPERSEDED → OBSOLETE`, the terminal state. Both `PlannerAdmin` and `ServiceAgent` may drive these part transitions.

A **PartsOrder** is placed by a `ServiceAgent` against a sale — the `sale_id` anchors both the compatibility check and the obligation window — naming the requested `part_id`, the `quantity`, and a `fulfillment_type` of `WARRANTY`, `GOODWILL`, or `PAID`, plus an optional `warranty_claim_id` that is informational only, not a foreign key. Warranty and goodwill orders are free of charge — `free_of_charge` is true exactly when the fulfillment type is `WARRANTY` or `GOODWILL` — and free orders respect the model's parts obligation: the logical clock must be at or before the model's `support_obligation_until`, else the order is rejected with `ERR_PARTS_OBLIGATION_EXPIRED`. Compatibility is checked too: the requested part's `compatible_model_codes` must contain the sale's model code, else `ERR_PART_INCOMPATIBLE`. Each order is stamped with a `seq_no`, a per-entity monotonic insertion counter starting at 1 that serves as the deterministic tie-break after `created_at` in the backorder fill order — identifiers are never used for ordering.

Resolution happens synchronously inside the create, walking the supersession chain in `chain_position` order. The requested part is the first candidate: if it is `AVAILABLE` or `LOW_STOCK` with `stock_quantity` at least the requested `quantity`, it wins — `resolved_part_id` is set, stock is decremented by the quantity (which may flip the part `AVAILABLE → LOW_STOCK → EXHAUSTED`), `total_cost_cents` is computed as the resolved part's `unit_cost_cents` times the quantity at resolution time, and the order is born `ALLOCATED`. If a candidate is `OBSOLETE`, the walk fails outright with `ERR_PART_UNAVAILABLE`. Otherwise the walk advances to the chain member with the next higher `chain_position` and repeats. When the chain is exhausted, the outcome depends on the requested part: if the requested part is `EXHAUSTED`, the order is born `BACKORDERED` with `resolved_part_id` equal to the requested part, waiting for a restock to fill it; if the requested part was `SUPERSEDED` with no fulfiller downstream, the create fails with `ERR_PART_UNAVAILABLE`. A `BACKORDERED` order later flips to `ALLOCATED` through the restock fill described above.

From `ALLOCATED`, a `ServiceAgent` ships the order (`ALLOCATED → SHIPPED`) and later marks it delivered (`SHIPPED → DELIVERED`, terminal). Cancellation is possible from `REQUESTED`, `BACKORDERED`, or `ALLOCATED`; cancelling an allocated order is compensating — the resolved part's `stock_quantity` is credited back by the order's quantity, which may lift an `EXHAUSTED` or `LOW_STOCK` part back up the stock ladder.

### 3.9. Connected Grills: Pairing and Firmware

The consumer-facing thread begins when an `AppUser` pairs a grill: the pairing call names the `sale_id` and the consumer's `app_account_id`, and creates a **ConnectedDevice** in `PAIRED` with a server-issued `pairing_token` returned at creation. The device's `firmware_version` is initialized from the grill model's `current_firmware_version` at pairing time. Pairing doubles as registration: if the sale is still `SOLD`, it moves to `REGISTERED` in the same request with `registered_at` stamped and the `proof_of_purchase_token` synthesized as "APP-PAIR" — a sale already registered is left as is. A sale supports at most one device in `PAIRED` or `UPDATING`; pairing over an existing live device is `ERR_DEVICE_ALREADY_PAIRED`.

Firmware stewardship is a synchronous two-step disguised as one. An update action by the `AppUser` carries a `target_version`, which must be present and different from the device's current `firmware_version`, else `ERR_VALIDATION`, and the device must currently be `PAIRED`, else `ERR_DEVICE_NOT_PAIRED`. The device passes `PAIRED → UPDATING → PAIRED` within the single request — the update applies synchronously — emerging with `firmware_version` rewritten to the `target_version` and its `version` incremented by 1. Unpairing moves `PAIRED → UNPAIRED`, the terminal state. The devices of a sale are listed through the sale's device view, which lists only the sale's live device — one in `PAIRED` or `UPDATING` — and so returns zero or one entries: once the device is unpaired it no longer appears, and a sale whose only device is `UNPAIRED` yields an empty view. The view is visible to `ServiceAgent`, `AppUser`, `ChannelRep`, and `PlannerAdmin` callers alike.
