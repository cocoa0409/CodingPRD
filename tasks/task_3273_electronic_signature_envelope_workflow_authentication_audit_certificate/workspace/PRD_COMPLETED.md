# Esign Envelope Workflow API — Product Requirements Document

## 1. Introduction

The Esign Envelope Workflow API gives sending organizations a single programmatic surface for turning a set of documents into a legally defensible electronic signature transaction and for proving, afterwards, exactly what happened to it. An organization assembles an envelope out of documents and recipients, places signing fields on specific pages, dispatches the envelope through a routing order, watches each recipient authenticate and act, and finally seals the finished transaction behind a tamper-evident hash chain that records every event with a server-stamped timestamp. The same API carries the commercial and custodial concerns that surround that transaction: credit consumption for each send, itemized fee quoting, retention schedules that vary by jurisdiction, legal holds, and purge.

The hard part of the domain is not the happy path but the assurance around it. Recipients are not equally trustworthy, so each one carries an authentication level — a delivered email link, a shared access code, knowledge-based questions, or verification of an identity document — and the risk implied by the envelope's authentication posture feeds back into what the remaining recipients are required to prove. Senders change their minds: envelopes are declined by a recipient, voided by the sender, left to lapse past an expiry instant, or placed under a legal hold that freezes them against every destructive operation. Every one of those paths has to leave the audit trail intact and internally consistent.

The system is also a multi-tenant one. Accounts are the billing and ownership boundary, retention schedules are keyed to an account's jurisdiction, and the operator role exists separately to administer credits, retention policy, legal holds and the logical clock. This document specifies the entities, state machines, calculations, validation precedence and endpoints that together make those guarantees testable.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

Every request must be authenticated by two HTTP headers. `X-User-Role` names the operational capacity in which the caller is acting, and `X-User-ID` identifies the acting party. The system recognizes exactly three roles, spelled precisely as follows: `PlatformAdmin`, `Account`, and `Recipient`. A request whose `X-User-Role` is absent, empty, or set to anything other than one of those three spellings is rejected with `ERR_UNAUTHENTICATED` (HTTP 401), and the same code applies when the header names an entity-backed role but `X-User-ID` is absent or empty. A well-formed request that nonetheless asks for an operation its role may not perform is rejected separately with `ERR_FORBIDDEN` (HTTP 403).

The identity semantics behind `X-User-ID` differ per role and matter for every ownership check in the system. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it, for example as the actor of an administrative action, but never compares it to any entity's `id`. When `X-User-Role` is `Account`, `X-User-ID` is the `id` of the acting `Account`, and ownership checks compare the resource's account-valued field — a `sender_account_id` on an envelope, an `owning_account_id` on a template, an `account_id` on a bulk send batch — against `X-User-ID`. When `X-User-Role` is `Recipient`, `X-User-ID` is the `id` of the acting `Recipient`, and a recipient may act only on the recipient row it names.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

For endpoints that return lists of resources, pagination is controlled via query parameters. The `limit` parameter specifies the maximum number of items to return. If not provided, it defaults to 10, with a minimum of 1 and a maximum of 100; a supplied `limit` outside that range is clamped to the nearest bound rather than refused. The `offset` parameter specifies the number of items to skip and defaults to 0; a negative `offset` is treated as 0. A `limit` or `offset` that cannot be parsed as an integer falls back to its default rather than raising an error.

Unless otherwise specified, all list endpoints return resources sorted by their creation timestamp in ascending order; where resources share a `created_at` instant, which happens whenever the logical clock did not advance between their creations, they are returned in the order in which they were created, so the listing is deterministic.

Paginated and non-paginated list-based responses include the following fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count`, and `has_more`.

List endpoints additionally accept filter query parameters alongside `limit` and `offset`; a filter that is omitted does not constrain the result set. Available filters include `scope` for retention policies, `owning_account_id` and `status` for templates, `sender_account_id`, `retention_policy_id` and `status` for envelopes, `envelope_id` and `status` for recipients, `recipient_id`, `envelope_id` and `status` for signing sessions, `envelope_id`, `envelope_document_id` and `recipient_id` for field placements, `envelope_id`, `recipient_id` and `event_type` for audit events, and `account_id`, `template_id` and `status` for bulk send batches.

### 2.4. Envelope Ownership, Account Scoping and Segregation of Duties

An `Envelope` is owned by the `Account` recorded in its `sender_account_id`, and a `Template` is owned by the `Account` named in its `owning_account_id`. Ownership is the tenancy boundary of the whole system: an envelope's retention schedule is resolved through its owning account's `state_code`, and credits are debited from the owning account's `credit_balance`. When a caller presents the `Account` role, the acting account is the entity whose `id` equals `X-User-ID`, and the envelopes it may act upon are those whose `sender_account_id` matches that identifier.

The system enforces segregation of duties at the moment an envelope is sealed. The account that triggers sealing must not be the identity that acted as any recipient of that same envelope — the rule fires when the sealing identity matches a recipient of the envelope that has either authenticated (`auth_status` `AUTHENTICATED`) or signed (a non-null `signed_at`), not only one that did both. When the sealing identity is also such a recipient identity for the envelope, the seal is refused with `ERR_SOD_VIOLATION` (HTTP 403) and the envelope is left untouched. This prevents a sender from both performing the ceremony on a recipient's behalf and attesting to its integrity. The comparison is made only for an `Account`-role caller, since it is the `X-User-ID` of that role that names a recipient identity.

### 2.5. Common Resource Properties, Versioning and the Logical Clock

Most persisted resources in the system — `Envelope`, `Recipient`, `SigningSession`, `FieldPlacement`, `EnvelopeDocument`, `Template`, `Account`, `RetentionPolicy` and `BulkSendBatch` — carry a standard set of system-managed fields:

- `id` (string): a unique, server-minted identifier for the resource, formatted as a UUID with no type prefix.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the resource was created.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the resource was last modified; it is refreshed on any change to the resource, including changes caused by a cascade rather than by a direct request.
- `version` (integer): a server-managed counter that is incremented by one on every modification to the resource. It is the basis for the optimistic concurrency control described in §2.8.

One entity is deliberately thinner. An `AuditEvent` is append-only and immutable, so it carries only `id` and `created_at` — it has neither an `updated_at` field nor a `version` field, and no operation may modify a stored event.

All time-sensitive rules in this system are evaluated against a server-owned logical clock rather than the wall clock. The logical clock starts, on server startup, at exactly `2026-09-01T00:00:00Z` and never falls back to real time. An administrative capability, available only to `PlatformAdmin`, advances the logical clock to a supplied instant given as `to_iso8601`, and every subsequent temporal rule — envelope expiry, reminder cooldown, retention eligibility — reads that value.

### 2.6. Envelope Lifecycle Integrity and Cascade Propagation

The `Envelope` is the aggregate at the centre of the system, and its lifecycle status governs every resource beneath it. An envelope begins in `CREATED`, advances through `SENT` and `DELIVERED`, and reaches one of four terminal states: `COMPLETED`, `DECLINED`, `VOIDED` or `EXPIRED`. Once terminal, an envelope is immutable: any operation that requires mutability and targets a terminal envelope is rejected with `ERR_ENVELOPE_TERMINAL` (HTTP 409). An operation whose envelope is simply in the wrong non-terminal state for the transition it requests is rejected instead with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409).

Child resources are reconciled to the envelope's decision rather than left dangling, and each reconciliation is itself a mutation that refreshes the parent's `updated_at` and increments its `version`. When an in-flight envelope is voided, every recipient still in `WAITING`, `SENT`, `DELIVERED` or `SIGNING` moves to `VOIDED`, and every open signing session belonging to one of those recipients moves to `EXPIRED`. When an envelope expires, the same in-flight recipients move to `EXPIRED` and open sessions move to `EXPIRED`. When a recipient declines and the decline bubbles up, the envelope takes the `DECLINED` status and every other recipient that was still in `WAITING`, `SENT`, `DELIVERED` or `SIGNING` moves to `VOIDED`, while open sessions move to `DECLINED`. In every one of these cascades, a recipient moves only when its *status* is one of the named in-flight statuses: a recipient whose `status` is already terminal is never rewritten, while a recipient whose `status` is still in-flight moves even where its `auth_status` has already settled (for example, an in-flight recipient whose `auth_status` is `AUTHENTICATED` is moved by the cascade).

Two independent dimensions live on a `Recipient`. Its `status` tracks the workflow position — `WAITING`, `SENT`, `DELIVERED`, `SIGNING`, and the terminal `SIGNED`, `APPROVED`, `DECLINED`, `VOIDED`, `EXPIRED` — while its `auth_status` tracks the parallel authentication dimension, `PENDING`, `AUTHENTICATED` or `FAILED`. Authentication gates the workflow transitions; it does not replace them, and a change in one dimension never silently rewrites the other.

### 2.7. Nested Resource Addressing and Validation Precedence

Envelope-scoped resources are addressed through a nested path whose leading identifier is the envelope and whose trailing identifier is the child. The system resolves such a path strictly left to right and rejects the request at the first identifier that does not resolve, before any business rule is evaluated: a missing envelope yields `ERR_ENVELOPE_NOT_FOUND` (HTTP 404), a missing recipient yields `ERR_RECIPIENT_NOT_FOUND` (HTTP 404), a document that is not part of the addressed envelope yields `ERR_DOCUMENT_NOT_FOUND` (HTTP 404), an unresolvable sending or owning account yields `ERR_ACCOUNT_NOT_FOUND` (HTTP 404), an unresolvable template yields `ERR_TEMPLATE_NOT_FOUND` (HTTP 404), and an unresolvable retention policy yields `ERR_RETENTION_POLICY_NOT_FOUND` (HTTP 404). The single path identifier used by every nested route is `id`.

Two refinements follow from that addressing shape. A field placement is created through its envelope's `/fields` collection, and its body's `envelope_document_id` is resolved against existence first — an identifier that matches no document at all yields `ERR_DOCUMENT_NOT_FOUND` (HTTP 404) — whereas a body `recipient_id` that matches no recipient at all is refused by the referential-integrity guard with `ERR_RECIPIENT_ENVELOPE_MISMATCH` (HTTP 422) rather than a 404. The flat routes that address a resource by its own `id` with no leading envelope segment — reading or updating one field placement, and reading one signing session or one audit event — resolve the owning envelope from the stored child, and an `id` that matches nothing at all is refused with `ERR_INVALID_REQUEST` (HTTP 400).

Beyond existence, the system applies its validation rules in a fixed ascending priority order, and the first rule that fails determines the response — later rules are not evaluated and cannot mask an earlier failure. The ladder runs as follows. Authentication headers are checked first (priority 1 and 2, `ERR_UNAUTHENTICATED`, HTTP 401), then the acting role's permission on the operation (priority 3, `ERR_FORBIDDEN`, HTTP 403). Segregation of duties is evaluated next (priority 4, `ERR_SOD_VIOLATION`, HTTP 403). The existence checks follow immediately (priorities 5 through 10, the six `404` codes listed above). State guards come next: envelope mutability against terminal status (priority 11, `ERR_ENVELOPE_TERMINAL`, HTTP 409), the legal-hold freeze (priority 12, `ERR_LEGAL_HOLD_FROZEN`, HTTP 409), the transition's permitted from-set including the completion requirement that every signer and approver already be finished (priority 13, `ERR_INVALID_ENVELOPE_STATE`, HTTP 409), recipient actionability (priority 14, `ERR_RECIPIENT_TERMINAL`, HTTP 409) and the presence of an open signing session (priority 15, `ERR_SESSION_CLOSED`, HTTP 409).

The assurance and consent guards occupy the middle of the ladder: the level-escalation rule (priority 16, `ERR_AUTH_LEVEL_TOO_LOW`, HTTP 422), the authentication-satisfied rule (priority 17, `ERR_AUTH_REQUIRED`, HTTP 422), the knowledge-based-question attempt cap (priority 18, `ERR_AUTH_MAX_ATTEMPTS`, HTTP 422), the consent requirement (priority 19, `ERR_CONSENT_REQUIRED`, HTTP 422) and the access-code match (priority 20, `ERR_INVALID_ACCESS_CODE`, HTTP 401). Temporal guards follow — routing release (priority 21, `ERR_ROUTING_NOT_RELEASED`, HTTP 422), the envelope expiry instant (priority 22, `ERR_ENVELOPE_EXPIRED`, HTTP 409) and retention eligibility (priority 23, `ERR_RETENTION_NOT_EXPIRED`, HTTP 409). Structural constraints then apply, in this order: field completeness (priority 24, `ERR_FIELD_REQUIRED`, HTTP 422), recipient email/routing-order uniqueness (priority 25, `ERR_DUPLICATE_RECIPIENT`, HTTP 409), the contiguous routing-order set (priority 26, `ERR_ROUTING_ORDER_GAP`, HTTP 422), template publication (priority 27, `ERR_TEMPLATE_NOT_PUBLISHED`, HTTP 422), template-name uniqueness (priority 28, `ERR_DUPLICATE_TEMPLATE_NAME`, HTTP 409), recipient-to-envelope referential integrity (priority 29, `ERR_RECIPIENT_ENVELOPE_MISMATCH`, HTTP 422), document-to-envelope referential integrity (priority 30, `ERR_DOCUMENT_ENVELOPE_MISMATCH`, HTTP 422) and credit sufficiency (priority 31, `ERR_INSUFFICIENT_CREDIT`, HTTP 402). Bulk-row validity applies at priority 32 (`ERR_BULK_ROW_INVALID`, HTTP 422) and the stale-version guard at priority 33 (`ERR_STALE_VERSION`, HTTP 412). The reminder cooldown is checked at priority 35 (`ERR_REMINDER_COOLDOWN`, HTTP 409).

One rule sits outside that numeric run and acts as the last-resort shape check: priority 34 rejects a request whose required body fields are missing or whose enum-valued field carries a member outside its declared set, with `ERR_INVALID_REQUEST` (HTTP 400). It is the fallback applied after the operation-specific rules have been considered, so a request that is both malformed and, say, credit-short surfaces the more specific failure.

Two operations deliberately reorder two rungs of the ladder so that the more specific failure is the one surfaced. On purge, the retention-window-versus-hold-window overlap freeze (priority 12, `ERR_LEGAL_HOLD_FROZEN`, HTTP 409) is evaluated ahead of the retention-eligibility gate (priority 23, `ERR_RETENTION_NOT_EXPIRED`, HTTP 409), so an envelope whose retention window still overlaps an active hold reports the freeze rather than the unexpired retention term even before its purge-eligible instant arrives. On sealing, segregation of duties (priority 4, `ERR_SOD_VIOLATION`, HTTP 403) is evaluated ahead of the acting role's ownership permission (priority 3, `ERR_FORBIDDEN`, HTTP 403), so an `Account` caller whose identity is also a recipient of the target envelope surfaces the segregation refusal rather than the ownership refusal.

### 2.8. Optimistic Concurrency on Terminal Envelope Writes

Four operations on an envelope are made against a snapshot the client previously read, and each of them therefore requires the client to supply the envelope version it observed. Voiding an in-flight envelope, declaring an in-flight envelope expired, sealing a fully-signed envelope, and purging an expired envelope each take a non-optional `expected_envelope_version` input carrying the client's last-observed `version` of the target envelope. If that value does not equal the envelope's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412) and the envelope is not modified. This is a stale-view rejection, not a race arbiter: the server simply refuses to apply a write whose snapshot no longer describes the envelope, because a cascade such as a recipient decline bubbling up, an administrative completion, a legal-hold toggle or a retention-policy edit may have advanced the version after the client read it. No endpoint other than these four takes a version input.

### 2.9. Credit Ledger and Fee Arithmetic

Every account holds a spendable integer balance in `credit_balance`, initialized to 1000 for a new account. Sending an envelope debits that balance, and compensating a void credits it back; operators may also apply signed adjustments. The amount debited by a send is the envelope's credit spend consumption, computed in whole credit units as follows. First, the page overage is derived: the envelope's total page count, taken as the sum of the `page_count` of every document belonging to the envelope whose `is_certificate` is false, is reduced by the account's `page_allowance` and any negative excess is treated as zero; that excess is then divided by ten and rounded up to a whole number of page blocks. Second, the recipient overage is derived: the count of the envelope's recipients whose role is `SIGNER` or `APPROVER` is reduced by five and any negative excess is treated as zero. Third, the base unit count is one plus the page-block count plus the recipient overage. Fourth, the base count is multiplied by a tier multiplier — one for `STANDARD`, eight tenths for `PRO`, five tenths for `ENTERPRISE` — and that product is rounded up to a whole number of credit units. Fifth, if the account's `status` is `SUSPENDED`, the result is doubled. The consumption is always an integer number of credit units; the ceiling is applied to the tier multiplication, and the doubling is applied after the ceiling.

A spend estimate may be computed before an envelope is dispatched; it is an internal figure rather than a declared response field. That estimate follows exactly the same arithmetic except that it must not include the suspended-account doubling — the estimate is computed as though the account were `ACTIVE` — so for a suspended account the estimate is half the amount that will actually be debited.

Fee quoting is a separate, document-level concern with its own precision rules. The per-document page fee is computed by walking the envelope's non-certificate documents in ascending `created_at` order and, where two documents share a `created_at`, in ascending `name` order, and, where two documents share both `created_at` and `name`, in the order in which they were created; for each document computing its own chargeable block count as the number of ten-page blocks in its `page_count` — the page count divided by ten, rounded up — less the account's free block count, floored at zero. The free block count is derived once from the account's `page_allowance` by dividing it by ten and rounding down, and it is applied to every document independently. Each document's chargeable block count is multiplied by the per-document rate of 12.335, and that product is rounded half up to exactly two decimal places before it is added to the running total. The rounding happens per document, before summing; the summed fee is never rounded a second time, and rounding the aggregate once instead would produce a different figure.

The envelope fee quote is built from the page fee in a pinned evaluation order. The page component is the per-document page fee described above. The subtotal is a base charge of 1500.00 plus that page component. The discount is the subtotal multiplied by a discount rate, rounded half up to two decimal places. The total fee is the subtotal minus the discount. The discount rate is determined by the envelope's total page count — again the sum of `page_count` over non-certificate documents — as a flat tier: for fewer than 100 pages the rate is zero; for 100 pages up to and including 500 it is 0.02; for more than 500 pages up to and including 2000 it is 0.03; and for more than 2000 pages it is 0.04. The tier rate is applied flatly to the whole subtotal, never marginally to the pages crossing each boundary. All monetary values in the quote are rounded to two decimal places using the round-half-up method, and the discount is rounded once, after the subtotal has been formed.

### 2.10. Authentication Assurance and Identity Risk Scoring

Each recipient carries an authentication level, `auth_level`, one of `EMAIL_ACCESS`, `ACCESS_CODE`, `KBA` or `ID_DOCUMENT`, defaulting to `EMAIL_ACCESS`. The level drives an identity risk score that is recomputed at authentication events and again, finally, when the recipient signs. The score begins from a base that depends on the level: ten for `EMAIL_ACCESS`, thirty for `ACCESS_CODE`, fifty-five for `KBA` and eighty for `ID_DOCUMENT`. To that base, five points are added for each recorded knowledge-based-question failure on the recipient. If the recipient has been identity-verified, a further fifteen points are added.

Two variants of the score exist and they are not interchangeable. The provisional score, written to a recipient's `auth_risk_score`, is recomputed for every recipient of an envelope whenever any authentication event occurs; it is the raw total clamped into the range from zero to one hundred, and it takes no account of the envelope's other recipients. The final score, written to a recipient's `auth_risk_score_final` at the moment that recipient signs and never recomputed afterwards, is the raw total plus a peer-consensus term, clamped only at the upper bound of one hundred and never below zero at the lower end. The peer-consensus term is ten points for each other recipient of the same envelope whose `auth_status` is `AUTHENTICATED` and whose `auth_level` is `ACCESS_CODE`, `KBA` or `ID_DOCUMENT` — that is, any level at or above `ACCESS_CODE`. The provisional variant never includes that peer term, which is why the same recipient can read a lower provisional score than final score. Scores are always integers.

### 2.11. Retention, Legal Hold and Tamper-Evident Sealing

Retention eligibility is an interval computation. The retention window is anchored on the envelope's `sent_at` when that instant exists, and on its `created_at` otherwise. The number of retention years is taken from the governing `RetentionPolicy` when that policy's `scope` is `GLOBAL` — the policy's own `retention_years` value is used verbatim — but when the policy's `scope` is `ACCOUNT` the year count is resolved from a jurisdiction schedule keyed on the owning account's `state_code`: California carries seven years, Illinois five, Texas ten, and any state outside the schedule falls back to the three-year default. The purge-eligible instant is the anchor advanced by that many calendar years, then advanced again by the policy's `purge_grace_days` calendar days; it is a datetime fixed at `00:00:00Z` on the computed day, and the arithmetic is calendar arithmetic rather than a fixed number of seconds. The retention window is the closed-open interval from the anchor up to but not including the purge-eligible instant.

Against that window sits the legal-hold window. When the envelope's `legal_hold` is false the hold window is empty and blocks nothing. When the hold is active the hold window is the closed-open interval from `legal_hold_started_at` up to but not including `legal_hold_until`, and a hold with no supplied `legal_hold_until` is treated as open-ended, extending to positive infinity. Purging is blocked exactly when the retention window and the hold window overlap. The boundaries are adjacent rather than overlapping: a hold that starts exactly at the purge-eligible instant does not block, and a hold that lapses exactly at the purge-eligible instant does not block either, but a hold that starts one second before the purge-eligible instant does block.

The resolved retention term of an envelope is not frozen at dispatch unless pinning was requested; by default the eligibility check re-resolves the live policy on each run, so editing a `RetentionPolicy`'s `retention_years` changes the already-computed purge-eligible instant for every envelope governed by that policy. When an envelope is pinned to its resolved term at send time, it seals that resolved year count into its own record and keeps it permanently, and later policy edits no longer move its eligibility instant.

Integrity of a completed transaction rests on two hash structures. At sealing, a `seal_hash` is computed as the SHA-256 digest over the envelope's ordered document hash list joined by the pipe character, taking the `document_hash` of each of the envelope's documents in order — in creation order, with documents sharing a `created_at` instant ordered by the order in which they were created. The audit chain is a separate structure maintained per envelope: each `AuditEvent` carries a `prev_hash` equal to the `event_hash` of the event immediately before it in the chain, and an `event_hash` computed as the SHA-256 digest of the concatenation, joined by pipe characters, of the event's `sequence_number` rendered as a decimal string, the event's `event_type`, the event's `event_at` rendered in ISO 8601 form, and the previous hash — which is the empty string for the first event, whose `prev_hash` is null. A certificate hash is the SHA-256 digest over the ordered `event_hash` chain joined by the pipe character. Hashes are hexadecimal digest strings of sixty-four characters. When an existing chain is read back for verification, the system replays the computation from the stored fields and rejects the read if any stored `event_hash` disagrees with the recomputed value.

## 3. Business Logic & Workflows

### 3.1. Account Provisioning and Envelope Assembly

The sending organization is established as an `Account`. An operator creates one by supplying a display `name` and a `state_code` naming the United States jurisdiction the organization operates in, together with an optional `tier` and an optional `page_allowance`. A new account opens in `ACTIVE` status with a `credit_balance` of 1000 credit units, a `tier` of `STANDARD` and a `page_allowance` of 25 pages. The `state_code` is not decorative: as §2.11 describes, it selects the retention schedule that governs every envelope the account sends, so an account in Illinois retains for a shorter period than one in Texas by default. Operators administer the account afterwards by applying a credit adjustment of `delta_units` — which may be negative — accompanied by a human-readable `reason`, and by moving the account among `ACTIVE`, `SUSPENDED` and `CLOSED` with a `status` change. Both adjustments increment the account's `version`, and suspending an account has an immediate commercial consequence, since a suspended account pays double for every envelope it sends.

An envelope is drafted by its owning account. The creation payload names the `sender_account_id` and supplies a `subject` and a `retention_policy_id`; when the envelope is generated from reusable material it also carries a `template_id`. Three optional inputs shape its behaviour: `routing_mode`, which defaults to `SEQUENTIAL` and may be set to `PARALLEL`; `expires_after_days`, the calendar-day lifetime that defaults to 120; and `sender_visible_window_days`, the business-day window that defaults to 30. Both windows accept a value of at least 1 and at most 365. A freshly created envelope holds the `CREATED` status with `legal_hold` false and `sent_at`, `expires_at`, `sender_visible_expires_at`, `seal_hash`, `certificate_hash`, `audit_certificate_id`, `purged_at`, `decline_reason` and `void_reason` all unset; the system immediately appends the envelope's first audit entry, an `ENVELOPE_CREATED` event at sequence number 1.

Content is then assembled into the draft. Adding a document, adding a recipient and placing a field are each permitted only while the envelope is still `CREATED` and not under an active legal hold: assembly attempted on a terminal envelope is refused with `ERR_ENVELOPE_TERMINAL` (HTTP 409), on an active hold with `ERR_LEGAL_HOLD_FROZEN` (HTTP 409), and on a non-terminal envelope in any other state with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409). Documents are added one at a time with a file `name` and a `page_count` of at least one; the server stamps each with a `document_hash`, the SHA-256 digest of the assembled bytes, leaves `is_certificate` false, records a `DOCUMENT_HASHED` audit event and advances the envelope's version. Recipients are added with a `role` — `SIGNER`, `APPROVER` or `COPY` — and an `email`, optionally with a `routing_order` (at least 1, defaulting to 1), an `auth_level` (defaulting to `EMAIL_ACCESS`), an `access_code` for access-code challenges and a `consent_accepted` flag. A new recipient enters `WAITING` with `auth_status` `PENDING`, `kba_fail_count` zero, `identity_verified` false and `reminder_count` zero; a recipient created with `consent_accepted` already true has its `consent_accepted_at` stamped at creation. Two recipients of the same envelope may not share an `email` at the same `routing_order`; such an attempt is refused with `ERR_DUPLICATE_RECIPIENT` (HTTP 409). A recipient's `access_code` is a shared secret used only for challenge matching and is never returned in any response body.

Fields are the last piece of assembly. Each field placement names the `envelope_document_id` it sits on and the `recipient_id` responsible for it, and declares a `field_type` drawn from `SIGNATURE`, `INITIAL`, `DATE`, `TEXT` or `CHECKBOX`, a `page_number` of at least one, and an optional `tab_order` defaulting to 1. A field is `required` by default and its `value` is unset until the recipient supplies it; a `SIGNATURE` field is always required and always counts toward completion. Two referential guards protect placement: supplying a `recipient_id` that does not belong to the envelope in the path is refused with `ERR_RECIPIENT_ENVELOPE_MISMATCH` (HTTP 422), and supplying an `envelope_document_id` that does not belong to that envelope is refused with `ERR_DOCUMENT_ENVELOPE_MISMATCH` (HTTP 422). An envelope document identifier that resolves to nothing at all is refused earlier with `ERR_DOCUMENT_NOT_FOUND` (HTTP 404). Listings of an envelope's documents, of its field placements — filterable by `envelope_id`, `envelope_document_id` and `recipient_id` — and of its recipients — filterable by `envelope_id` and `status` — let a sender audit what has been assembled before dispatch.

### 3.2. Sending the Envelope and the Credit Debit

Dispatching an envelope moves it from `CREATED` to `SENT`, and it is a tightly gated transition. The envelope must still be in `CREATED`; it must not be under a legal hold; at least one document with a `page_count` of at least one must belong to it; at least one recipient whose role is `SIGNER` or `APPROVER` must belong to it; and every field placement on the envelope must point at a document that actually belongs to that envelope. A terminal envelope is refused with `ERR_ENVELOPE_TERMINAL` (HTTP 409) and an envelope in any other wrong state with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409); an active legal hold freezes the send with `ERR_LEGAL_HOLD_FROZEN` (HTTP 409).

Two commercial and structural guards sit alongside those. A sequential envelope's signer and approver recipients must occupy a contiguous run of routing positions: the set of `routing_order` values among recipients whose role is `SIGNER` or `APPROVER` must equal the full set from one up to the largest value present, with no gap; a gap is refused with `ERR_ROUTING_ORDER_GAP` (HTTP 422). A parallel envelope is exempt from that continuity requirement. Separately, the owning account must be able to pay: if its `credit_balance` is below the envelope's credit spend consumption as described in §2.9, the send is refused with `ERR_INSUFFICIENT_CREDIT` (HTTP 402).

A successful send stamps `sent_at` with the logical clock instant, then computes `expires_at` as `sent_at` advanced by `expires_after_days` calendar days and pinned to `23:59:59Z`, and `sender_visible_expires_at` as `sent_at` advanced by `sender_visible_window_days` business days — skipping Saturday and Sunday — and likewise pinned to `23:59:59Z`. The account is debited: `credit_balance` decreases by the computed credit consumption and the account's `version` advances. Every recipient at routing order 1 moves to `SENT` with `auth_status` `PENDING`, the provisional identity risk scores for the whole envelope are recomputed, a `SENT` audit event is appended, and the envelope's `version` advances by one.

### 3.3. Routing Release and Signing Sessions

Routing controls when a recipient is allowed to act. In a `SEQUENTIAL` envelope a recipient is released only when every recipient of the envelope whose role is `SIGNER` or `APPROVER` and whose `routing_order` is lower has already reached a terminal-attempted recipient status — `SIGNED`, `APPROVED`, `DECLINED` or `VOIDED`. In a `PARALLEL` envelope every recipient is released the moment the envelope is in flight. A recipient that acts before its position has been released is refused with `ERR_ROUTING_NOT_RELEASED` (HTTP 422), and the same guard protects the act of opening a session.

A recipient opens a signing session by submitting `consent_to_electronic_records`, the explicit consent flag for electronic records. The new session enters `OPEN`, its `opened_at` is stamped from the logical clock, its `consent_captured_at` is stamped from the logical clock only when consent was actually given, and when consent is given the recipient's own `consent_accepted` flag is set true and `consent_accepted_at` is stamped; opening a session also advances the recipient from its in-flight status — `WAITING`, `SENT` or `DELIVERED` — to `SIGNING`. The system appends a `SESSION_OPENED` audit event and, when consent was given, a `CONSENT_ACCEPTED` event as well. Opening a session additionally requires that the envelope be in `SENT` or `DELIVERED`, that the recipient's `auth_status` not be `FAILED` (such a recipient is refused with `ERR_AUTH_REQUIRED`, HTTP 422), that the recipient not already hold an open session (refused with `ERR_RECIPIENT_TERMINAL`, HTTP 409) and that the recipient's `status` still be one of `WAITING`, `SENT` or `DELIVERED` (otherwise refused with `ERR_RECIPIENT_TERMINAL`, HTTP 409). Sessions can be listed and filtered by `recipient_id`, `envelope_id` or `status`, which gives a sender visibility into which recipients have begun the ceremony and which have not.

### 3.4. Authentication and Identity Assurance

A recipient completes its authentication challenge by submitting a `method` drawn from `EMAIL_ACCESS`, `ACCESS_CODE`, `KBA` or `ID_DOCUMENT`, and depending on that method, an `access_code`, a `kba_answers_correct` verdict, or an `identity_document_verified` verdict. An `EMAIL_ACCESS` challenge always succeeds; an `ACCESS_CODE` challenge succeeds when the supplied code matches; a `KBA` challenge succeeds on a true `kba_answers_correct` verdict; and an `ID_DOCUMENT` challenge succeeds on a true `identity_document_verified` verdict. The challenge is available only while the envelope is in `SENT` or `DELIVERED`, an envelope in any other state being refused with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409); a missing `method` or one outside the declared set is refused with `ERR_INVALID_REQUEST` (HTTP 400). On success the recipient's `auth_status` becomes `AUTHENTICATED`; on failure it becomes `FAILED`. Knowledge-based-question failures are counted on the recipient: only when the submitted method is a knowledge-based challenge does a failure increment `kba_fail_count`. A successful identity-document verification sets `identity_verified` true. The provisional identity risk score is recomputed for every recipient of the envelope immediately afterwards, following §2.10, and an `AUTH_SUCCEEDED` or `AUTH_FAILED` audit event records the outcome.

Three guards constrain this step. A knowledge-based challenge attempted after the recipient has already accumulated three failures is refused with `ERR_AUTH_MAX_ATTEMPTS` (HTTP 422) — the cap is reached at a count of three, so a recipient with two prior failures may still make one more attempt. An `access_code` that does not match the recipient's stored `access_code` is refused with `ERR_INVALID_ACCESS_CODE` (HTTP 401), though that refusal is not raised until the failed attempt has been recorded on the parallel auth dimension — the recipient's `auth_status` is set to `FAILED` and an `AUTH_FAILED` audit event is appended, with the provisional identity risk scores recomputed, before the challenge is turned away. And if the logical clock has reached or passed the envelope's `expires_at`, the challenge is refused with `ERR_ENVELOPE_EXPIRED` (HTTP 409).

Authentication then gatekeeps signing itself. When a recipient whose level is `ACCESS_CODE`, `KBA` or `ID_DOCUMENT` attempts to sign, its `auth_status` must be `AUTHENTICATED`; when the recipient's level is `EMAIL_ACCESS` and the delivered email link is its only credential, either `AUTHENTICATED` or still-`PENDING` is accepted. A recipient that has not met its own requirement is refused with `ERR_AUTH_REQUIRED` (HTTP 422). The envelope's collective risk posture can raise the bar further: if the highest provisional identity risk score among the *other* recipients of the same envelope whose `auth_status` is `AUTHENTICATED` is at least 60, the acting recipient's `auth_level` must be at least `KBA`; if that maximum is at least 80, the acting recipient's `auth_level` must be `ID_DOCUMENT`. A recipient whose level falls below the required bar is refused with `ERR_AUTH_LEVEL_TOO_LOW` (HTTP 422). This is what makes authentication a two-way street on a high-risk envelope: one heavily scrutinised recipient raises the requirement for everyone else.

### 3.5. Signing, Approval and Decline

Signing completes a recipient's participation. The act is available only while the envelope is in `SENT` or `DELIVERED`. The acting recipient must be in `SIGNING`, hold an open signing session, satisfy its authentication requirements as §3.4 describes, have released its routing position, have given consent to electronic records either on the recipient row or on the signing session, and hold a value in every required field placement assigned to it. These gates are evaluated in the §2.7 ascending priority order, so the first that fails determines the response: a recipient already in a terminal recipient status is refused with `ERR_RECIPIENT_TERMINAL` (HTTP 409); a recipient with no open session is refused with `ERR_SESSION_CLOSED` (HTTP 409); a recipient whose level falls below the bar its peers impose is refused with `ERR_AUTH_LEVEL_TOO_LOW` (HTTP 422); a recipient that has not met its own authentication requirement is refused with `ERR_AUTH_REQUIRED` (HTTP 422); consent that has not been captured is refused with `ERR_CONSENT_REQUIRED` (HTTP 422); an unreleased routing position is refused with `ERR_ROUTING_NOT_RELEASED` (HTTP 422); an envelope whose `expires_at` has passed refuses the action with `ERR_ENVELOPE_EXPIRED` (HTTP 409); and a required field or a signature field still left null is refused with `ERR_FIELD_REQUIRED` (HTTP 422).

On success the recipient's outcome depends on its role. A `SIGNER` moves to `SIGNED`; an `APPROVER` moves to `APPROVED`. In both cases `signed_at` is stamped from the logical clock, and the two branches are specified identically — the approver path differs only in the destination status, in the recorded `RECIPIENT_APPROVED` audit event type, and in the fact that an approver holds no required-field obligations of its own. The signing recipient's `auth_risk_score_final` is sealed at this moment by the final variant of §2.10 and is never recomputed. The session the recipient signed from moves from `OPEN` to `COMPLETED`, a `FIELD_COMPLETED` audit event records the field work, and — the important side effect — the next routing group is released: every recipient of the envelope at the next-higher `routing_order` whose status is still `WAITING` moves to `SENT` with `auth_status` `PENDING`. The recipient's own outcome event — `RECIPIENT_SIGNED` for a signer, `RECIPIENT_APPROVED` for an approver — is appended last, after the `FIELD_COMPLETED` event and after the release of the next routing group. Signing itself leaves the envelope's own status untouched; the envelope advances to `COMPLETED` only when the sender issues a separate sealing action, described in §3.6.

Declining is the signer's refusal path and it is asymmetric: only a recipient whose role is `SIGNER` may decline. The acting recipient must be in `SIGNING` at the recipient level, and at the envelope level the envelope must be in `SENT` or `DELIVERED`, must not be under a legal hold, and the acting recipient's status must be one of `DELIVERED`, `AUTHENTICATED` or `SIGNING`. A decline carries a `decline_reason`. It moves the recipient to `DECLINED` and bubbles up: the owning envelope takes the `DECLINED` status with the supplied `decline_reason` captured on it, every other recipient still in `WAITING`, `SENT`, `DELIVERED` or `SIGNING` is moved to `VOIDED`, every open signing session belonging to a recipient of that envelope moves to `DECLINED`, a `RECIPIENT_DECLINED` audit event is appended, and the envelope's `version` advances. Declining is therefore terminal for the envelope as a whole, not merely for the one recipient.

Field values are recorded independently of the signing act. A recipient or its sender may supply or update a field's `value`; when a field transitions from null to a non-null value the system appends a `FIELD_COMPLETED` audit event. This lets a signer fill in date, text and checkbox answers tab by tab — in `tab_order` sequence within the signing flow — before finally committing the signature.

### 3.6. Sealing, the Audit Certificate and the Event Chain

Sealing is the sender's attestation that the envelope is finished. It is available only when the envelope is in `DELIVERED` and every recipient of the envelope whose role is `SIGNER` or `APPROVER` has already reached `SIGNED` or `APPROVED`; an envelope that does not meet that completeness condition is refused with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409). Every required field placement on the envelope — and every `SIGNATURE` placement, which is always required — must hold a value, or the attempt is refused with `ERR_FIELD_REQUIRED` (HTTP 422). The envelope must not be under a legal hold, or the attempt is refused with `ERR_LEGAL_HOLD_FROZEN` (HTTP 409). The sealing account must not be an identity that acted as a recipient of the same envelope, or the attempt is refused with `ERR_SOD_VIOLATION` (HTTP 403), as §2.4 sets out. A terminal envelope is refused with `ERR_ENVELOPE_TERMINAL` (HTTP 409), and the sealing request must carry the envelope's observed `expected_envelope_version`, a mismatch yielding `ERR_STALE_VERSION` (HTTP 412).

A successful seal is the system's richest single side effect. The envelope's status becomes `COMPLETED` and `is_sealed` becomes true. The `seal_hash` is computed over the envelope's ordered document hash list as §2.11 describes. A synthetic document is created inside the envelope to hold the certificate — its `name` is `AuditCertificate.pdf` and its `is_certificate` flag is true — and the envelope's `audit_certificate_id` is set to that document's identifier. Two audit events are appended in order, a `SEALED` event and then a `CERTIFICATE_GENERATED` event, and the `certificate_hash` is then computed over the ordered audit event hash chain, again per §2.11, so the stored value covers the whole chain including those two events. If the envelope was created from a template, that template's `times_used` counter is incremented. Finally the envelope's `version` advances by one.

Reading the audit certificate returns the `certificate_hash`, the `seal_hash` and an `event_count`, recomputing the chain on every read — the returned `certificate_hash` is therefore derived from the events as they stand at read time rather than echoed from the value stamped at seal time. The read doubles as a verification: the system replays the chain from the stored event fields — sequence number, type, timestamp and predecessor hash, in ascending `sequence_number` order starting from 1, with the chain contiguous — and rejects the read if any stored `event_hash` disagrees with the recomputed value. Audit events can also be browsed as a list, filtered by `envelope_id`, `recipient_id` or `event_type`, and each event exposes its `sequence_number`, `event_type`, the acting `recipient_id` when the event is recipient-scoped, its `event_at`, its `prev_hash`, its `event_hash` and a human-readable `detail`. Because an `AuditEvent` is immutable and carries no version, the chain is the envelope's permanent record of every delivery, authentication, consent, field, signature, decline, seal, void, expiry, reminder and purge that ever touched it.

### 3.7. Delivery Feed, Reminders, Expiry and Voiding

After a send, the delivery feed advances the envelope's delivery state. The sender or an operator submits a `feed_event`; `DELIVERED` is the only feed event the system declares, and any other value is refused with `ERR_INVALID_REQUEST` (HTTP 400). When that event is `DELIVERED`, an envelope in `SENT` advances to `DELIVERED`, every recipient still at routing order 1 whose `status` is `SENT` advances to `DELIVERED`, a `DELIVERED` audit event is appended, and the envelope's version advances. The feed is also frozen by an active legal hold (`ERR_LEGAL_HOLD_FROZEN`, HTTP 409) and an envelope that is not in `SENT` — whether terminal or merely not yet sent — is refused with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409), a terminal envelope therefore surfacing as the state error rather than `ERR_ENVELOPE_TERMINAL`. This stands in for the email provider's delivery callback and is what makes a recipient's link live.

While an envelope is in flight, the sender may nudge its stragglers. Sending reminders targets every recipient whose status is `SENT`, `DELIVERED` or `SIGNING`: each such recipient's `reminder_count` is incremented and its `last_reminder_at` is stamped from the logical clock, and a `REMINDER_SENT` audit event is recorded per recipient. The cooldown is evaluated for every target before any of them is mutated, so a fan-out in which any single target is still inside its cooldown is refused atomically with `ERR_REMINDER_COOLDOWN` (HTTP 409) and no target is reminded. Reminders are rate-limited per recipient by a closed-open cooldown window running from that recipient's `last_reminder_at` up to but not including `last_reminder_at` plus twenty-four hours: a reminder requested while the logical clock falls inside that window is refused with `ERR_REMINDER_COOLDOWN` (HTTP 409). A recipient that has never been reminded, whose `last_reminder_at` is null, is always eligible. An envelope that has already reached a terminal status refuses the reminder with `ERR_ENVELOPE_TERMINAL` (HTTP 409).

Expiry ends an in-flight envelope that has run out of time. The envelope must be in `SENT` or `DELIVERED`, must not be under a legal hold, and the logical clock must have reached or passed the envelope's `expires_at`; the request must carry the observed `expected_envelope_version`. An envelope whose clock has not yet reached `expires_at` is refused with `ERR_INVALID_ENVELOPE_STATE` (HTTP 409). On success the envelope takes the `EXPIRED` status, every recipient still in `WAITING`, `SENT`, `DELIVERED` or `SIGNING` moves to `EXPIRED`, every open signing session belonging to those recipients moves to `EXPIRED`, an `EXPIRED` audit event is appended, and the envelope's `version` advances.

Voiding is the sender's deliberate cancellation. It is available while the envelope is in `SENT` or `DELIVERED` and not under a legal hold, and it requires the observed `expected_envelope_version`. The payload carries a `void_reason` and an optional `refund_credit` flag. On success the envelope takes the `VOIDED` status with the `void_reason` captured, every recipient still in `WAITING`, `SENT`, `DELIVERED` or `SIGNING` moves to `VOIDED`, every open session belonging to those recipients moves to `EXPIRED`, and a `VOIDED` audit event is appended. When `refund_credit` is true the owning account is compensated: its `credit_balance` is increased by the envelope's credit spend consumption and the account's `version` advances. That compensating credit is accounted before the `VOIDED` audit event is appended. An envelope that has already reached a terminal status is refused with `ERR_ENVELOPE_TERMINAL` (HTTP 409), and a void whose snapshot is out of date is refused with `ERR_STALE_VERSION` (HTTP 412).

### 3.8. Templates and Bulk Send

A template is reusable envelope material owned by an account. It is created with an `owning_account_id`, a `name`, a `page_count` of at least one and a `role_slot_count` of at least one, and optionally a `default_routing_mode` and a `default_auth_level` that downstream envelopes and recipients will inherit, defaulting when omitted to `SEQUENTIAL` and `EMAIL_ACCESS` respectively. A new template opens in `DRAFT` status with `times_used` at zero. Template names must be unique within the owning account: a duplicate `name` for the same `owning_account_id` is refused with `ERR_DUPLICATE_TEMPLATE_NAME` (HTTP 409). A draft template is made usable by publishing it, which requires both a `page_count` and a `role_slot_count` of at least one and moves it from `DRAFT` to `PUBLISHED`; a published template may later be archived, moving it to the `ARCHIVED` terminal status. Either transition attempted from a status it does not accept — publishing a template that is not `DRAFT`, or archiving one that is not `PUBLISHED` — is refused with `ERR_TEMPLATE_NOT_PUBLISHED` (HTTP 422). Both transitions advance the template's version. Templates can be listed and filtered by `owning_account_id` or `status`.

Instantiation turns a published template into a concrete envelope. The caller supplies the `sender_account_id`, the `retention_policy_id`, the envelope's `subject` and the `recipients` that fill the template's role slots; the recipients must be supplied as a non-empty list, and a recipient that omits an `auth_level` inherits the template's `default_auth_level`. As with direct envelope creation, the acting account must own the `sender_account_id` it names. The resulting envelope opens in `CREATED` with its `routing_mode` inherited from the template's `default_routing_mode`, one recipient is created per supplied role slot, and the template's `times_used` counter is incremented. Only a `PUBLISHED` template may be instantiated; any other status is refused with `ERR_TEMPLATE_NOT_PUBLISHED` (HTTP 422). The instantiation also inherits the envelope's contiguous routing-order requirement, so a sequential set of recipients with a gap in its routing positions is refused with `ERR_ROUTING_ORDER_GAP` (HTTP 422). Unresolvable references surface as `ERR_ACCOUNT_NOT_FOUND`, `ERR_RETENTION_POLICY_NOT_FOUND` or `ERR_TEMPLATE_NOT_FOUND` (all HTTP 404).

Bulk send applies a template across many rows. A batch is created with an `account_id`, a `template_id` and a `total_rows` count of at least one, and opens in `CREATED` status with `succeeded_count` and `failed_count` both zero. Processing the batch against its submitted `rows` has deliberate partial-success semantics rather than all-or-nothing behaviour. A batch may be processed only once: an already-processed batch is refused with `ERR_INVALID_REQUEST` (HTTP 400), and an empty `rows` list is refused with `ERR_BULK_ROW_INVALID` (HTTP 422). A row is defined by a resolvable `email`, which the row may present either as its own `email` field or through the role slots it carries; a row that lacks a resolvable `email` or that does not carry the role slots the template declares is rejected with `ERR_BULK_ROW_INVALID` (HTTP 422). Each row either produces a valid envelope or is rejected: the template must still be `PUBLISHED` or the process is refused with `ERR_TEMPLATE_NOT_PUBLISHED` (HTTP 422), and the account's credit must cover the work or the process is refused with `ERR_INSUFFICIENT_CREDIT` (HTTP 402). The per-row work each accepted row represents is the same credit spend consumption a single direct send would incur for that envelope, checked against the account's balance as the batch proceeds. A row that carries no `retention_policy_id` is given the earliest-created retention policy, or is rejected when no policy exists. When every row succeeds the batch closes as `COMPLETED` with `succeeded_count` equal to `total_rows` and `failed_count` zero. When some rows succeed and some are rejected, the batch closes as `PARTIAL` with `succeeded_count` set to the number of rows that produced an envelope and `failed_count` set to the number rejected. When every row is rejected the batch closes as `FAILED` with `succeeded_count` zero and `failed_count` equal to `total_rows`. Batches can be listed and filtered by `account_id`, `template_id` or `status`.

### 3.9. Retention, Purge and Legal Hold

Retention policy is created by an operator with a `name`, a `scope`, a `retention_years` count between 1 and 50, a `purge_mode` and an optional `purge_grace_days` of zero or more. The `scope` decides how the retention term is resolved: a `GLOBAL` policy applies its own `retention_years` uniformly to every envelope it governs, whereas an `ACCOUNT` policy defers to the jurisdiction schedule keyed on the owning account's `state_code`. The `purge_mode` decides what purging actually removes — `ANONYMIZE_METADATA` leaves the envelope's documents, including the certificate, in place while keeping the audit chain intact, and `DELETE_ALL` deletes the certificate document outright. Policies can be listed and filtered by `scope`, and edited to change `retention_years`, `purge_mode` or `purge_grace_days`; each edit advances the policy's version. Because eligibility is re-resolved from the live policy on each read rather than stored on the envelope, a policy edit needs no per-envelope rewrite to change the computed purge-eligible instant of the envelopes it governs, which moves as soon as the policy itself changes.

Purging is the destructive end of the retention lifecycle, and it is guarded on both sides. The logical clock must have reached or passed the envelope's computed purge-eligible instant, following the interval arithmetic of §2.11; a purge attempted before that instant is refused with `ERR_RETENTION_NOT_EXPIRED` (HTTP 409). The envelope must not be frozen by an overlapping legal hold, or the purge is refused with `ERR_LEGAL_HOLD_FROZEN` (HTTP 409); as §2.7 records, that freeze is evaluated ahead of the retention gate. The request must carry the observed `expected_envelope_version`, and a stale snapshot is refused with `ERR_STALE_VERSION` (HTTP 412). On success the envelope's `purged_at` is stamped from the logical clock, the certificate document is deleted when the governing policy's `purge_mode` is `DELETE_ALL` and retained when it is `ANONYMIZE_METADATA`, a `PURGED` audit event is appended, and the envelope's version advances.

A legal hold is the freeze that overrides all of the above. An operator applies or releases it by submitting the `legal_hold` flag together with an optional `hold_until` instant. Applying a hold stamps `legal_hold_started_at` from the logical clock and sets `legal_hold_until` to the supplied instant, where a null `hold_until` means the hold is open-ended and never lapses on its own. Releasing the hold clears both `legal_hold_until` and `legal_hold_started_at`. Either way the envelope's version advances. While a hold is active in the interval terms described in §2.11, sending, voiding, sealing, expiring and purging the envelope are all frozen and refused with `ERR_LEGAL_HOLD_FROZEN` (HTTP 409) — the hold is the single strongest protection in the system and no destructive or status-advancing operation may proceed through it.
