# LED Display Manufacturing API — Product Requirements Document

## 1. Introduction

A large-format LED display is never a catalogue purchase. Every stadium ribbon board, roadside billboard and retail video wall is specified from a product family, engineered against a specific mounting structure, built cabinet by cabinet from individually tested and colour-calibrated modules, soaked in a burn-in chamber, QA-signed, shipped, mounted, calibrated again on site by a licensed crew, and then carried for years under a service contract that promises response times, spare modules and a brightness-degradation warranty. Today that chain lives in a plant ERP for manufacturing, a spreadsheet for structural drawings, a scheduling whiteboard for the burn-in chambers, and a field-service inbox for warranty claims. Nothing reconciles: a cabinet can be QA-signed by the same operator who calibrated its modules, a crew can be dispatched to a wall that was never fully mounted, and a warranty credit can be computed twice with two different answers.

This document specifies a single backend service that owns the whole chain. The service is deliberately opinionated about two things. First, **quality gates are arithmetic, not opinion**: dead-pixel density, colour-bin assignment, cabinet uniformity, structural load capacity, control-system bandwidth headroom, warranty credit — each is a pinned formula with a pinned rounding order, so two operators reading the same measurements always get the same verdict. Second, **state is the only permission**: a module cannot be installed before it is calibrated, a cabinet cannot be mounted before engineering approves the drawing, a crew cannot sign off before every cabinet is mounted, and a warranty case cannot be fulfilled before it is assessed.

The service also treats failure as a first-class path. A failed burn-in does not merely mark a run: it quarantines the cabinet, blocks the parent project, and releases every commissioning crew booked against that project so the plant does not send a truck to a wall that cannot be commissioned. Recovery is explicit and manual — the offending modules are pulled, the cabinet re-enters assembly, and the production ladder is re-walked from there. Engineering readers should expect no implicit repair anywhere in this specification: the system validates, rejects, and cascades, but it never quietly fixes a number the caller supplied.

## 2. Global Specifications & System-Wide Principles

### 2.1. Plant Personnel and Role-Based Access Control

Every request to the service carries two headers. `X-User-ID` identifies the acting user or crew, and `X-User-Role` names the role under which they act. If either header is absent or present but empty, or if `X-User-Role` is not one of the seven role names defined below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well formed but the named role is not permitted to invoke the target operation — the authorized roles for every operation are listed in §4 — the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The seven roles are `PlantAdmin`, `DesignEngineer`, `StructuralReviewer`, `ProductionOperator`, `QAEngineer`, `FieldEngineer` and `ServiceManager`. A `PlantAdmin` seeds the catalogue — display models, burn-in chambers and commissioning crews — and drives the service's logical clock; it has no reach into engineering, production, QA or service workflows. A `DesignEngineer` specifies projects and submits structural drawing revisions. A `StructuralReviewer` independently approves or rejects those revisions. A `ProductionOperator` registers, pixel-tests and colour-calibrates modules, plans cabinets, and installs or removes modules. A `QAEngineer` schedules and adjudicates burn-in runs and QA-signs cabinets. A `FieldEngineer` acts on site: mounting cabinets, arriving, calibrating and signing off commissioning visits. A `ServiceManager` sells service contracts, manages the spare pool, and runs warranty cases end to end. Every read operation is open to all seven roles.

Six of the seven roles are **opaque identities**. When `X-User-Role` is `PlantAdmin`, `DesignEngineer`, `StructuralReviewer`, `ProductionOperator`, `QAEngineer` or `ServiceManager`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to an entity's `id`. The server does record it where a workflow demands accountability — as `submitted_by_user_id` and `reviewed_by_user_id` on a drawing revision, as `calibrated_by_user_id` on a module, as `qa_approved_by_user_id` on a cabinet, and as `completed_by_user_id` on a burn-in run — and those recorded values are what the segregation-of-duties rules in §2.9 compare against each other.

`FieldEngineer` is the one **entity-backed identity**. When `X-User-Role` is `FieldEngineer`, `X-User-ID` is the `id` of the acting `CommissioningCrew`; ownership checks on a commissioning visit compare the visit's `commissioning_crew_id` to `X-User-ID`, and a mismatch is rejected with `ERR_CREW_NOT_ASSIGNED` (HTTP 403). This applies to all three crew actions on a visit — recording arrival, recording on-site calibration, and signing the installation over to the customer. Cabinet mounting is also a `FieldEngineer` action, but it is not scoped to a crew booking: any `FieldEngineer` may mount a QA-passed cabinet.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly 20 alphanumeric characters (upper- or lower-case letters and digits).
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the host's real wall clock rather than from the logical factory clock of §2.4.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be below 1, and may not exceed 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A `limit` outside the 1-to-100 range, or a negative `offset`, is a malformed request and is rejected with `ERR_VALIDATION_FAILED` (HTTP 400).

Unless a list endpoint's own narrative says otherwise, results are ordered by `created_at` ascending — oldest record first — with ties on an identical `created_at` broken by the order in which the records were written, earliest write first, so the ordering is always total and stable. Every list response carries the four pagination fields inside `meta`: `limit` and `offset` echo the effective values used for the page, `total_count` reports how many records matched the filters before the page window was applied, and `has_more` is true exactly when records remain beyond the current window. Single-resource reads carry neither of the four.

List endpoints also expose filters, and those filters are the only reverse-reachability channel for foreign keys the server writes on the caller's behalf. Modules can be listed by `display_model_id`, `cabinet_id`, `replaces_module_id`, `reserved_service_contract_id`, `module_state` and `color_bin`. Service cases can be listed by `service_contract_id`, `cabinet_id`, `faulty_module_id`, `resolved_faulty_module_id`, `replacement_module_id`, `case_type` and `case_state`. Projects accept `display_model_id`, `install_environment`, `engineering_state` and `production_state`. Drawing revisions accept `project_id` and `revision_state`; cabinets accept `project_id` and `cabinet_state`; burn-in runs accept `cabinet_id`, `burn_in_chamber_id` and `run_state`; commissioning visits accept `project_id`, `commissioning_crew_id` and `visit_state`; service contracts accept `project_id` and `contract_state`; display models accept `environmental_rating`; and commissioning crews accept `region_code` and `certification_level`. Every filter is optional, and supplying several narrows the result set by all of them at once. A filter is matched by exact equality against the stored field; an id- or code-valued filter supplied as an empty string is treated as though it had been omitted, while an enum-valued filter — every `..._state`, `case_type`, `color_bin`, `install_environment`, `environmental_rating` and `certification_level` filter — is screened against its own vocabulary at rung 3, so an empty or unrecognised enum value is refused with `ERR_VALIDATION_FAILED` rather than ignored; and an id-valued filter naming a record that does not exist is not an error but simply matches nothing.

### 2.4. Record Identity, Timestamps and the Logical Factory Clock

Every persisted record carries a server-minted `id`, which is a UUID string with no type prefix; clients never choose an `id`. Every record also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written. All eleven record types in this system — display models, burn-in chambers, commissioning crews, projects, drawing revisions, cabinets, modules, burn-in runs, commissioning visits, service contracts and service cases — additionally carry `updated_at`, refreshed to the moment of the most recent mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that record. Both `created_at` and `updated_at` are stamped from the host's real wall clock, not from the logical factory clock described below. There is no record type in this system that omits `updated_at` or `version`.

Time in this system is a **logical clock**, not wall-clock time. The clock's startup default is exactly `2026-08-01T00:00:00Z`, rendered at the standing millisecond precision as `2026-08-01T00:00:00.000Z`, and until it is moved the clock reads exactly that value; it never falls back to the host's real time. A `PlantAdmin` may move the clock to an absolute instant by supplying `to_iso8601`, and the service answers with the new `current_utc`. Every datetime a client supplies anywhere in this system — `to_iso8601`, `window_start`, `window_end` — is accepted in any parseable ISO 8601 form, including one carrying a numeric UTC offset instead of `Z` and one carrying no zone designator at all, which is read as UTC; it is then normalised to UTC and stored and echoed with exactly three fractional digits, so a value supplied with more or fewer fractional digits is truncated or padded to milliseconds rather than refused. A string that is not a parseable instant is rejected with `ERR_VALIDATION_FAILED`. Every temporal comparison in this document — burn-in window elapsement, commissioning window currency, service-case response deadlines, warranty age — reads that logical clock, and the fields `reported_at`, `arrived_at`, `signed_off_at` and `warranty_start_at` are all stamped from it. Instants are compared at millisecond resolution.

### 2.5. Measurement Precision and Rounding Discipline

Every rounding operation in this system is **round half up**: a value exactly at the midpoint rounds away from zero. Rounding targets differ by quantity and are stated with each formula, but the standing conventions are these. Areas in square metres are carried to 4 decimal places. Recommended viewing distances are carried to 1 decimal place. Structural loads in kilograms per square metre are carried to 2 decimal places. Dead-pixel densities in parts per million, degradation percentages, uniformity scores, data-load percentages and discount fractions are carried to 2 decimal places. Brightness-spread percentages inside the uniformity calculation are carried to 4 decimal places and chroma spreads to 6, before the score itself is rounded to 2. Chroma coordinates are supplied and compared at 4 decimal places. Money is always an integer count of cents; there are no fractional cents anywhere in the system. Every rounded quantity is emitted in the response as a bare JSON number, never as a quoted string, and a JSON number carries no trailing zeros: a figure rounded to 2 decimal places renders as `0.0` rather than `0.00` and as `12.5` rather than `12.50`, and one whose rounded value is a whole number renders without any fractional part at all. The pinned decimal-place count constrains the value that must be reached, not the width at which it is printed.

Where a formula rounds more than once, the **order of rounding is pinned in the formula's own narrative and is never the implementer's choice**. Two places in particular are load-bearing: the hardware contract value rounds each per-cabinet line to whole cents before multiplying by the cabinet count, and the annual service fee selects its volume-discount tier from the pre-discount subtotal exactly once. Getting either order wrong produces a number that differs from the specification by a few cents on small walls and by material amounts on large ones.

Several quantities deliberately do **not** round. Where a formula divides to produce an intermediate mean, that mean is carried at full precision into the next step. Where a formula takes a ceiling or a floor, that is an exact integer operation, not a rounding step, and its direction is stated explicitly.

### 2.6. Version Stamping and Stale-Read Rejection

Two record types are shared write targets: a `Cabinet`, which several operators populate slot by slot, and a `ServiceContract`, whose spare pool is drawn down and refilled. Writes against these two parents are guarded by optimistic concurrency control on the parent's `version`.

Three operations require `expected_cabinet_version` as a mandatory input field carrying the client's last observed `version` of the target cabinet: installing a module into a cabinet slot, removing an installed module from a cabinet, and fulfilling an approved warranty case by swapping a module. If the supplied value does not equal the cabinet's current `version`, the request is rejected with `ERR_STALE_CABINET_VERSION` (HTTP 412) and nothing is persisted. Slot assignment is the reason this matters: a writer holding a stale view of `occupied_slot_indexes` would otherwise hand out a slot that has already been filled, and a writer holding a stale view of the cabinet's dead-pixel totals would place a warranty replacement against superseded geometry.

Two operations require `expected_service_contract_version` as a mandatory input field carrying the client's last observed `version` of the target contract: reserving a spare module against the contract, and releasing a reserved spare back to free stock. A mismatch with the contract's current `version` is rejected with `ERR_STALE_CONTRACT_VERSION` (HTTP 412). A reservation legitimately supersedes the prior composition of the spare pool, so a writer acting on a stale `spare_reserved_count` would over-reserve or under-reserve against the contracted `spare_required_count`.

No other operation in this system takes a version field. Version fields are not optional on the five operations that declare them: omitting `expected_cabinet_version` or `expected_service_contract_version` is a malformed request, rejected with `ERR_VALIDATION_FAILED` (HTTP 400), not a concurrency failure.

### 2.7. The Screening Ladder: One Rejection, Strictly Ordered

Requests are screened in a fixed order, and the **first** rule that a request violates decides the response. Screening stops there: no later rule is consulted, no partial write is kept, and nothing at all is persisted. This ordering is observable and it matters, because a single bad request frequently violates several rules at once — a caller with the wrong role and a nonexistent id gets the authorization failure, not the not-found failure.

The ladder runs from authentication, through authorization, request shape, existence, ownership, optimistic concurrency and state preconditions, then segregation of duties, then structural safety, then temporal and resource conflicts, then referential coherence, then business constraints, and finally fiscal limits. Safety deliberately outranks scheduling: a structurally unsound wall must be refused before the factory starts arguing about chamber slots. In full, the rungs are:

1. Both authentication headers are present and `X-User-Role` is one of the seven declared roles — otherwise `ERR_UNAUTHENTICATED`. Applies to every operation.
2. The authenticated role is permitted to invoke the target operation — otherwise `ERR_UNAUTHORIZED`. Applies to every operation.
3. The request body and query shape are well formed: required fields present, JSON types correct, enum members recognised, numeric ranges honoured, any `window_end` strictly later than its `window_start`, `limit` within 1 to 100, and `offset` not negative — otherwise `ERR_VALIDATION_FAILED`. Applies to every operation. Four conventions make this rung precise. A field explicitly supplied as JSON `null` is treated exactly as though it had been omitted, so a required field sent as `null` is a missing field and an optional one sent as `null` falls back to its default. A field the operation does not declare is ignored rather than rejected, except where a narrative explicitly demands a field be omitted. Where an integer is required, an integer-valued JSON number such as `5.0` is accepted while a fractional one is refused, and a JSON boolean is never accepted for a numeric field. And a request body that is absent or blank is read as an empty object regardless of `Content-Type`, which is why the no-body operations succeed with no payload, while a body that is present but is not parseable JSON, or parses to something other than a JSON object, is refused with `ERR_VALIDATION_FAILED`.
4. Every referenced catalogue record exists. Path-templated ids are resolved **left to right** and the first unresolved id decides the answer. For the three catalogue parents — a `display_model_id`, a `burn_in_chamber_id` or a `commissioning_crew_id` — a missing target yields `ERR_REFERENCE_NOT_FOUND`. This rung guards project creation, module registration, burn-in scheduling, visit booking, and the three single-record catalogue reads.
5. A referenced `project_id`, whether in a path or a body, resolves to a project — otherwise `ERR_PROJECT_NOT_FOUND`. This rung guards single-project reads, drawing-revision submission, cabinet planning, visit booking and contract sale.
6. A referenced `drawing_revision_id` resolves — otherwise `ERR_REVISION_NOT_FOUND`. This rung guards the single-revision read and revision review.
7. A referenced `cabinet_id`, in path or body, resolves — otherwise `ERR_CABINET_NOT_FOUND`. This rung guards the single-cabinet read, module installation, module removal, QA approval, mounting, burn-in scheduling and service-case opening.
8. A referenced `module_id`, in path or body, resolves — otherwise `ERR_MODULE_NOT_FOUND`. This rung guards the single-module read, pixel testing, factory calibration, module installation, module removal, spare reservation, spare release, service-case opening and case fulfilment. On module installation the path cabinet is resolved before the body module, so a request naming a nonexistent cabinet **and** a nonexistent module reports the cabinet.
9. A referenced `burn_in_run_id` resolves — otherwise `ERR_RUN_NOT_FOUND`. This rung guards the single-run read, run completion and run abortion.
10. A referenced `commissioning_visit_id` resolves — otherwise `ERR_VISIT_NOT_FOUND`. This rung guards the single-visit read, arrival, on-site calibration and sign-off.
11. A referenced `service_contract_id`, in path or body, resolves — otherwise `ERR_CONTRACT_NOT_FOUND`. This rung guards the single-contract read, spare reservation, spare release and service-case opening.
12. A referenced `service_case_id` resolves — otherwise `ERR_CASE_NOT_FOUND`. This rung guards the single-case read, response, assessment and fulfilment.
13. A `FieldEngineer` acting on a commissioning visit presents an `X-User-ID` equal to that visit's `commissioning_crew_id` — otherwise `ERR_CREW_NOT_ASSIGNED`. This rung guards arrival, on-site calibration and sign-off.
14. `expected_cabinet_version` equals the cabinet's current `version` — otherwise `ERR_STALE_CABINET_VERSION`. This rung guards module installation, module removal and case fulfilment.
15. `expected_service_contract_version` equals the contract's current `version` — otherwise `ERR_STALE_CONTRACT_VERSION`. This rung guards spare reservation and spare release.
16. The revision under review is still in `SUBMITTED` — otherwise `ERR_INVALID_REVISION_STATE`.
17. A project whose `engineering_state` is already `APPROVED` accepts no further revision submission — otherwise `ERR_ENGINEERING_ALREADY_APPROVED`.
18. A project's `engineering_state` is `APPROVED` before any module may be installed into one of its cabinets or any of its cabinets mounted — otherwise `ERR_ENGINEERING_NOT_APPROVED`.
19. The module's `module_state` permits the operation: `MANUFACTURED` or `REWORK` for pixel testing, `PIXEL_TESTED` or `REWORK` for factory calibration, `CALIBRATED` for installation and for spare reservation, `INSTALLED` for removal — otherwise `ERR_INVALID_MODULE_STATE`.
20. The cabinet's `cabinet_state` permits the operation: `PLANNED` or `IN_ASSEMBLY` for installation; `IN_ASSEMBLY`, `POPULATED` or `QUARANTINED` for removal; `POPULATED` for burn-in scheduling; `BURN_IN_PASSED` for QA approval; `QA_PASSED` for mounting — otherwise `ERR_INVALID_CABINET_STATE`.
21. The run is still `SCHEDULED` when completed or aborted — otherwise `ERR_INVALID_RUN_STATE`.
22. The visit's `visit_state` permits the operation: `SCHEDULED` for arrival, `ON_SITE` for on-site calibration, `CALIBRATED` for sign-off — otherwise `ERR_INVALID_VISIT_STATE`.
23. The case's `case_state` permits the operation: `OPEN` for response, `RESPONDED` for assessment, `APPROVED` for fulfilment — otherwise `ERR_INVALID_CASE_STATE`.
24. The governing contract's `contract_state` is `ACTIVE` — otherwise `ERR_CONTRACT_NOT_ACTIVE`. This rung guards case opening, response, assessment and fulfilment, so a contract still `PENDING` or already `SUSPENDED` freezes the entire warranty pipeline.
25. The project's `production_state` is `INSTALLED`, meaning every cabinet of the project is `MOUNTED`, before a crew may go on site or sign off — otherwise `ERR_CABINETS_NOT_MOUNTED`.
26. Segregation of duties holds: the reviewing `X-User-ID` differs from the revision's `submitted_by_user_id`, and the QA-approving `X-User-ID` is not the `calibrated_by_user_id` of any module currently installed in the cabinet — otherwise `ERR_SEGREGATION_OF_DUTIES`. This rung guards revision review and cabinet QA approval.
27. The revision's `wind_load_kph` meets the environment floor — otherwise `ERR_WIND_LOAD_INSUFFICIENT`.
28. The revision's `structural_load_kg_per_sqm` meets the model's `required_load_kg_per_sqm` — otherwise `ERR_STRUCTURAL_CAPACITY_INSUFFICIENT`.
29. The project's `min_viewing_distance_m` meets the model's `recommended_min_viewing_distance_m` — otherwise `ERR_VIEWING_DISTANCE_TOO_SHORT`.
30. A `ROADSIDE` project declares some redundancy — otherwise `ERR_REDUNDANCY_REQUIRED_FOR_ROADSIDE`.
31. The run's `drive_pct` is within both the model's and the chamber's safe ceiling — otherwise `ERR_DRIVE_LEVEL_UNSAFE`.
32. The soak window is long enough for the model — otherwise `ERR_BURN_IN_DURATION_TOO_SHORT`.
33. The logical clock has reached the run's `window_end` before the run is completed — otherwise `ERR_BURN_IN_WINDOW_NOT_ELAPSED`.
34. The logical clock lies inside the visit's booked window when the crew records arrival — otherwise `ERR_VISIT_WINDOW_NOT_CURRENT`.
35. The chamber has enough free slots across the candidate occupancy interval — otherwise `ERR_CHAMBER_CAPACITY_EXCEEDED`.
36. The crew holds no live visit overlapping the requested window — otherwise `ERR_CREW_DOUBLE_BOOKED`.
37. The crew's `region_code` equals the project's `site_region_code` — otherwise `ERR_CREW_REGION_MISMATCH`.
38. The module's `display_model_id` equals the display model pinned by the cabinet's project — otherwise `ERR_MODULE_MODEL_MISMATCH`.
39. On case opening, the named cabinet belongs to the contract's project and the nominated faulty module is installed in that cabinet — otherwise `ERR_MODULE_GRID_MISMATCH`.
40. No revision of the project is still `SUBMITTED` when a new one is submitted — otherwise `ERR_OPEN_REVISION_EXISTS`.
41. The project has no existing service contract when one is sold — otherwise `ERR_CONTRACT_ALREADY_EXISTS`.
42. The cabinet's grid position is free and inside the declared grid — otherwise `ERR_CABINET_POSITION_TAKEN`.
43. The module's `serial_no` is not already in use — otherwise `ERR_MODULE_SERIAL_DUPLICATE`.
44. The requested `slot_index` is within the model's slot range and not already occupied — otherwise `ERR_CABINET_SLOT_OCCUPIED`.
45. The module being installed into production is not held as a contracted spare — otherwise `ERR_MODULE_RESERVED_AS_SPARE`.
46. The calibration chroma error is inside the reworkable band — otherwise `ERR_CHROMA_OUT_OF_TOLERANCE`.
47. A case carries the measurement its `case_type` demands — otherwise `ERR_MEASUREMENT_REQUIRED`.
48. A brightness-degradation approval has a positive shortfall — otherwise `ERR_DEGRADATION_WITHIN_ALLOWANCE`.
49. The case's cabinet still holds at least one installed module at assessment — otherwise `ERR_NO_REPLACEABLE_MODULE`.
50. The nominated module is reserved to this contract — otherwise `ERR_SPARE_NOT_RESERVED`. This rung guards case fulfilment and spare release.
51. The replacement module's colour bin is close enough to the outgoing module's — otherwise `ERR_COLOR_BIN_MISMATCH`.
52. The eligibility-filtered spare pool is non-empty — otherwise `ERR_NO_ELIGIBLE_SPARE_MODULE`. This rung guards spare reservation and case fulfilment.
53. The project's control-system headroom is sufficient — otherwise `ERR_DATA_LOAD_EXCEEDS_CAPACITY`.
54. The contract's `spare_pct_bp` meets the tier minimum — otherwise `ERR_SPARE_PCT_BELOW_MINIMUM`.

Rungs 27 through 54 each have a single natural home in the workflow narratives of §3, and the thresholds, comparison directions and boundary behaviours they enforce are specified there rather than here.

### 2.8. Two Independent Project Dimensions and Cascade Propagation

A project does not have "a status". It carries two independent state dimensions on the same record, and neither constrains the other's vocabulary. `engineering_state` tracks the structural drawing package and moves through `DRAFT`, `UNDER_REVIEW`, `REJECTED` and `APPROVED`, starting at `DRAFT`; `APPROVED` is terminal for that dimension. `production_state` tracks the factory and the field and moves through `NOT_STARTED`, `IN_ASSEMBLY`, `QA_COMPLETE`, `INSTALLED`, `COMMISSIONED` and `BLOCKED`, starting at `NOT_STARTED`; it has no terminal state, because a commissioned wall can still be blocked by a late quality failure. A third computed dimension, `service_posture`, is either `NORMAL` or `AT_RISK`, starts at `NORMAL`, and reads `AT_RISK` for exactly as long as some service contract of the project is `SUSPENDED`.

Project-level counters are **derived, never client-supplied**. `qa_passed_cabinet_count` counts the project's cabinets whose `cabinet_state` is `QA_PASSED` or `MOUNTED`; `mounted_cabinet_count` counts those that are `MOUNTED`; and `quarantined_cabinet_count` counts those that are `QUARANTINED`. Each is recomputed as part of the cabinet transition that could change it, and the parent's `production_state` is then re-derived from the recomputed counters — this is the bubble-up direction of the hierarchy. `BurnInChamber.reserved_slot_total` and `scheduled_run_count`, and `CommissioningCrew.scheduled_visit_count`, are derived in the same way from the runs and visits that reference them.

Cascades run downward from the same writes. Any operation that mutates a record refreshes that record's `updated_at` and increments its `version` by 1, and this holds for every record a cascade touches, not only the record the caller named: when a module installation lifts a cabinet out of `PLANNED` and a project out of `NOT_STARTED`, the module, the cabinet and the project each take a version increment. Two chains in this system run four hops deep and are specified in full in §3.6 and §3.9: a failing burn-in result quarantines the cabinet, blocks the project, and aborts the project's live commissioning visits; a warranty fulfilment returns one module, installs another, draws down the contract's spare pool, and can suspend the contract and flip the project's `service_posture`.

### 2.9. Segregation of Duties on the Factory Floor

Two independence rules are enforced by comparing recorded operator identifiers, and both surface as `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The first is straightforward: the `X-User-ID` reviewing a drawing revision must differ from the `submitted_by_user_id` recorded when that revision was submitted, so a `DesignEngineer` who also holds `StructuralReviewer` credentials cannot wave their own drawing through.

The second reaches across entities. When a cabinet is QA-approved, the approving `X-User-ID` is compared against the `calibrated_by_user_id` of **every** module currently installed in that cabinet, and a match on any one of them refuses the approval. The comparison is against the modules installed at the moment of approval, so removing an offending module and installing a different one legitimately unblocks the same approver. The identifier recorded on the successful approval is `qa_approved_by_user_id`.

### 2.10. Two Deliberately Different Reservation Geometries

The plant reserves two scarce resources on a timeline, and their interval semantics differ on purpose; implementers should not unify them.

Burn-in chamber occupancy is **closed at both ends and buffered**. A run's occupancy runs from its `window_start` through `occupied_until`, where `occupied_until` is the run's `window_end` advanced by the chamber's `turnaround_minutes` — the mandatory cool-down before the slots free up. Two occupancy intervals collide when each one's start is at or before the other's end, so runs that merely touch at a single instant **do** collide. Occupancy is an aggregate slot budget rather than exclusive possession: several runs may legally share the chamber at once as long as the sum of their `slots_required` fits within the chamber's `slot_capacity`.

Commissioning crew occupancy is **half-open and exclusive**. A visit occupies its crew from `window_start` up to but not including `window_end`. Two windows collide when each one's start is strictly before the other's end, so a visit beginning at exactly the previous visit's `window_end` is legal while one beginning a millisecond earlier is refused. A crew has capacity for one visit at a time: a single overlap is enough to reject the booking.

## 3. Business Logic & Workflows

### 3.1. Seeding the Plant: Product Families, Chambers and Crews

Nothing can be built until a `PlantAdmin` has described what the plant makes. Registering an LED product family captures its catalogue `name` (1 to 80 characters) and the three headline specifications a customer shops on: `pixel_pitch_mm`, the centre-to-centre LED spacing in millimetres, which must be greater than zero and carry at most 2 decimal places; `rated_brightness_nits`, the nameplate peak brightness in candela per square metre, which must be at least 500 and which later serves as the 100% baseline of the degradation warranty; and `environmental_rating`, the ingress protection class of the finished cabinet, which is one of `IP65_FRONT_IP54_REAR`, `IP65_FULL` or `IP43_INDOOR`.

Geometry is declared twice over — once for the module, once for the cabinet — and the two declarations must agree. A module is described by `module_width_mm`, `module_height_mm`, `module_pixel_cols` and `module_pixel_rows`; a cabinet by `cabinet_width_mm`, `cabinet_height_mm`, `modules_per_cabinet` and `cabinet_weight_kg`. All of these must be greater than zero, and the four millimetre dimensions, the two pixel counts and `modules_per_cabinet` are whole numbers — a fractional millimetre or pixel count is refused with `ERR_VALIDATION_FAILED` — while `cabinet_weight_kg` is an unrestricted positive decimal. The cabinet dimensions must be exact whole multiples of the module dimensions, and `modules_per_cabinet` must equal the number of module columns that fit across a cabinet multiplied by the number of module rows that fit up it — that is, the cabinet width divided by the module width, multiplied by the cabinet height divided by the module height, with both divisions coming out exact. **Geometry is validated, never repaired**: a declared slot count that contradicts the dimensions, or a division that leaves a remainder, is rejected with `ERR_VALIDATION_FAILED` and no product family is created. Slot indexes for a cabinet of this family run from 1 up to `modules_per_cabinet` inclusive.

The commercial and quality thresholds complete the record. `price_per_sqm_cents` is the list price per square metre of active display area in whole cents and must be at least 1. `dead_pixel_ppm_limit` is the highest cabinet-level dead-pixel density, in parts per million, that burn-in will accept; it must be zero or greater with at most 2 decimal places. `module_dead_pixel_max` and `module_cluster_max` govern the single-module pixel test: the first is the greatest number of dead pixels tolerated on one module and defaults to **3** when the caller omits it, the second is the largest adjacent dead-pixel cluster tolerated and defaults to **1**; both must be zero or greater. `reference_color_x` and `reference_color_y` are the target CIE 1931 chromaticity coordinates for factory colour calibration, each strictly between 0 and 1 and expressed to 4 decimal places. `burn_in_hours_required` is the minimum soak duration in whole hours and must be at least 1. `max_drive_pct` is the highest safe drive level during that soak, as a percentage of full drive, between 1 and 100 inclusive.

From those inputs the service derives six values at registration time and stores them on the family. `module_area_sqm` is the module width multiplied by the module height, converted from square millimetres to square metres by dividing by one million, rounded to 4 decimal places; `cabinet_area_sqm` is the same computation on the cabinet dimensions, likewise rounded to 4 decimal places. `module_pixel_count` is the module's pixel columns multiplied by its pixel rows, and `cabinet_pixel_count` is `modules_per_cabinet` multiplied by that module pixel count — the denominator of every dead-pixel density in the system. `recommended_min_viewing_distance_m` follows the industry rule of thumb of one metre of viewing distance for each millimetre of pixel pitch: it is the pixel pitch in millimetres multiplied by a factor of 1.0 metre per millimetre, rounded to 1 decimal place. Finally `required_load_kg_per_sqm` is the cabinet's dry weight divided by its active area — that is, divided by `cabinet_area_sqm` as it has just been rounded to 4 decimal places, not by the unrounded product of the cabinet dimensions — rounded to 2 decimal places; this is the structural floor that every drawing revision for a wall of this family must clear.

Burn-in chambers are registered separately. A chamber carries a floor-level `name` of 1 to 60 characters, a `slot_capacity` of at least 1 cabinet slot it can energise at one instant, a `turnaround_minutes` cool-down of zero or more minutes appended to every run's window before its slots free up, and a `certified_max_drive_pct` between 1 and 100 that is the highest drive level the chamber itself is certified to sustain. A new chamber starts with `reserved_slot_total` and `scheduled_run_count` both at 0; both are maintained by the service as runs are scheduled, completed, failed and aborted, and both are visible on a chamber read so a `QAEngineer` can see live reservation pressure before scheduling.

Commissioning crews are the field-side counterpart, and they double as identities. A crew carries a `name` of 1 to 60 characters, a `region_code` of 2 to 8 uppercase characters naming the region it is licensed to work in — every one of those characters must be an uppercase letter, so a code carrying a digit, a hyphen, a space or any lowercase letter is refused with `ERR_VALIDATION_FAILED` — and a `certification_level` of `L1`, `L2` or `L3`. Its `scheduled_visit_count` starts at 0 and counts the crew's visits that are `SCHEDULED`, `ON_SITE` or `CALIBRATED` — the live bookings, as distinct from those already signed off or aborted. The `id` returned when a crew is registered is precisely the `X-User-ID` a `FieldEngineer` authenticates with, which is what makes crew-scoped ownership checks possible at all.

One further `PlantAdmin` capability exists purely so that time-dependent behaviour can be driven deterministically: an administrative operation moves the service's logical clock to an absolute instant supplied as `to_iso8601` and answers with the resulting `current_utc`. Because burn-in elapsement, commissioning windows, service-case deadlines and warranty ages are all read from that clock, exercising this system end to end means advancing it deliberately rather than waiting.

### 3.2. Specifying a Wall: Sizing, Environment, Redundancy and Price

A `DesignEngineer` opens the engagement by creating a project. The commercial and siting inputs are `customer_name` (1 to 120 characters), `install_environment` — one of `STADIUM`, `ROADSIDE` or `RETAIL` — and `site_region_code`, 2 to 8 uppercase characters naming where the wall will be installed, held to the same uppercase-letters-only rule as a crew's `region_code` in §3.1. The project pins exactly one product family through `display_model_id`, and that pin fixes the geometry, the price per square metre and every quality threshold for the whole life of the project; later edits to the family do not retroactively move a project's numbers. Wall size comes from `cabinet_grid_cols` and `cabinet_grid_rows`, each between 1 and 40 inclusive, and the audience geometry from `min_viewing_distance_m`, the closest distance at which people will stand as surveyed on site, which must be greater than zero and carries 1 decimal place. `target_brightness_nits` is the brightness the customer contracted for, at least 100, and is the figure on-site calibration is later measured against.

The control-system design is declared on the same request. `redundancy_mode` is one of `NONE`, `HOT_BACKUP`, `DUAL_LINK` or `RING`, and it does double duty: it derates usable port capacity and it adds a price surcharge. `output_port_count` (1 to 64) and `port_bandwidth_mbps` (at least 1 Mbps) describe the processor feeding the wall, `color_depth_bits` is 8, 10 or 12 bits per colour channel, `refresh_rate_hz` is between 24 and 240 inclusive, and `player_count` is the number of content players between 1 and 16, each contributing 2500 Mbps of throughput.

Three sizing figures fall out immediately: `cabinet_count` is the grid columns multiplied by the grid rows; `module_count` is that cabinet count multiplied by the family's `modules_per_cabinet`; and `total_area_sqm` is the cabinet count multiplied by the family's `cabinet_area_sqm`, rounded to 4 decimal places.

Before any of that is persisted, two siting rules are checked. The surveyed `min_viewing_distance_m` must be at least the family's `recommended_min_viewing_distance_m`, compared at 1 decimal place; exact equality passes, and anything closer is refused with `ERR_VIEWING_DISTANCE_TOO_SHORT` because the audience would see the pixel grid. And a `ROADSIDE` wall must carry some control-system redundancy: declaring `install_environment` as `ROADSIDE` together with a `redundancy_mode` of `NONE` is refused with `ERR_REDUNDANCY_REQUIRED_FOR_ROADSIDE`. Stadium and retail walls may run without redundancy.

**Hardware price.** `contract_amount_cents` is the hardware contract value, and its rounding order is pinned. Start from the exact per-cabinet list value: the family's `cabinet_area_sqm` multiplied by its `price_per_sqm_cents`, carried at full precision. Then build a single surcharge multiplier as 1 plus the environment surcharge plus the redundancy surcharge. The environment surcharge is 12% for `STADIUM`, 18% for `ROADSIDE` and 5% for `RETAIL`. The redundancy surcharge is nothing for `NONE`, 6% for `HOT_BACKUP`, 9% for `DUAL_LINK` and 14% for `RING`. Multiply the exact per-cabinet list value by that multiplier and **round the per-cabinet line to whole cents first**; only then multiply the rounded line by `cabinet_count` to obtain `contract_amount_cents`. Summing exact per-cabinet amounts and rounding once at the end is a different — and wrong — number.

**Control-system headroom.** The same request evaluates whether the declared processor and players can actually drive the wall. Total pixels are `cabinet_count` multiplied by the family's `cabinet_pixel_count`. `required_data_mbps` is the total pixel count multiplied by `color_depth_bits`, multiplied by 3 for the three colour channels, multiplied by `refresh_rate_hz`, divided by one million to convert bits per second into Mbps, and then **rounded up to the next whole Mbps**. Port capacity is `output_port_count` multiplied by `port_bandwidth_mbps` multiplied by the redundancy derate factor — 1.0 for `NONE`, 0.5 for `HOT_BACKUP`, 0.5 for `DUAL_LINK` and 0.75 for `RING` — and then **rounded down to a whole Mbps**. Player capacity is `player_count` multiplied by 2500 Mbps. `effective_capacity_mbps` is the smaller of the floored port capacity and the player capacity. `data_load_pct` is `required_data_mbps` divided by `effective_capacity_mbps`, multiplied by 100, rounded to 2 decimal places. Should the derate floor the port capacity all the way to zero — a single 1 Mbps port on a `HOT_BACKUP` design does exactly that — `effective_capacity_mbps` is 0, no division is attempted, no percentage is computed, and the project is refused with `ERR_DATA_LOAD_EXCEEDS_CAPACITY`, because a control system with no usable capacity can never drive the wall. A load of more than 100.00 percent is refused with `ERR_DATA_LOAD_EXCEEDS_CAPACITY`; a load of exactly 100.00 percent is accepted, because a wall that saturates its links precisely is a legitimate — if tight — design.

A newly created project starts with `engineering_state` at `DRAFT`, `production_state` at `NOT_STARTED` and `service_posture` at `NORMAL`, with `approved_revision_number` unset and every derived cabinet counter at zero. Reading a project back returns both state dimensions, all three cabinet counters, both price and bandwidth derivations, and the service posture, which is why the project read is the natural progress view for every role in the plant.

### 3.3. Structural Engineering: Submission, Independent Review and the Rejection Loop

No module may be installed and no cabinet mounted until the wall's structural package has been approved, and approval is a two-person process. A `DesignEngineer` submits a drawing revision against a project by naming the `project_id` and certifying four things about the mounting design: `structural_load_kg_per_sqm`, the load-bearing capacity the drawing certifies, greater than zero and carried to 2 decimal places; `wind_load_kph`, the wind speed the structure is rated for, zero or greater; `mounting_type`, one of `WALL`, `FREESTANDING`, `ROOF` or `GANTRY`; and `service_access_side`, either `FRONT` or `REAR`, recording from which side modules can be reached once the wall is up.

Submission is only open while the project's `engineering_state` is `DRAFT` or `REJECTED`. The service assigns `revision_number` as the count of revisions already existing for that project plus 1, so the first submission is revision 1 and each subsequent attempt increments the counter. It snapshots the family's current `required_load_kg_per_sqm` onto the revision's own `required_load_kg_per_sqm` field, freezing the bar the drawing was judged against, records `submitted_by_user_id` as the submitting `X-User-ID`, sets `revision_state` to `SUBMITTED`, and moves the project's `engineering_state` from `DRAFT` or `REJECTED` to `UNDER_REVIEW`, taking a version increment and a fresh `updated_at` on the project as well as on the new revision.

Four rejections guard that submission, **and they are evaluated in this order**. First, a project whose `engineering_state` has already reached `APPROVED` accepts nothing further: the submission is refused with `ERR_ENGINEERING_ALREADY_APPROVED`. Second, the wind rating is checked against a floor set by where the wall will stand — at least 160 kph for a `STADIUM` wall, at least 200 kph for a `ROADSIDE` wall, and at least 100 kph for a `RETAIL` wall — with anything below the floor refused as `ERR_WIND_LOAD_INSUFFICIENT`. Third, the certified `structural_load_kg_per_sqm` must be at least the snapshotted `required_load_kg_per_sqm`, compared at 2 decimal places, with exact equality passing and anything less refused as `ERR_STRUCTURAL_CAPACITY_INSUFFICIENT`. Only fourth does the service check that no other revision of the project is still `SUBMITTED`, refusing a concurrent submission with `ERR_OPEN_REVISION_EXISTS`. That ordering is deliberate and observable: a structurally inadequate drawing submitted while another revision is still open reports the safety failure, not the queueing failure, because the plant would rather hear that the steel is undersized.

A `StructuralReviewer` then decides the revision by supplying a `decision` of either `APPROVE` or `REJECT`, with an optional `reason`. The revision must still be `SUBMITTED` — reviewing a revision that is already `APPROVED` or `REJECTED` is refused with `ERR_INVALID_REVISION_STATE` — and that state check is evaluated **before** the independence check, so a second review attempt by the original submitter reports the state failure rather than the segregation failure. The reviewer's `X-User-ID` must differ from the revision's `submitted_by_user_id`, or the decision is refused with `ERR_SEGREGATION_OF_DUTIES`. Either decision records `reviewed_by_user_id` as the deciding `X-User-ID` and returns the updated revision. Only the `decision` field itself is screened at rung 3: the `REJECT` branch's demand for a `reason` is evaluated after the state and independence checks, on that branch alone, so a `REJECT` that omits its `reason` against a revision that is no longer `SUBMITTED` reports `ERR_INVALID_REVISION_STATE` rather than `ERR_VALIDATION_FAILED`, and a `reason` volunteered alongside `APPROVE` is accepted and discarded rather than stored.

The two branches diverge in what they write. `APPROVE` moves the revision `SUBMITTED → APPROVED`, moves the project's `engineering_state` `UNDER_REVIEW → APPROVED`, and copies the revision's `revision_number` into the project's `approved_revision_number` — the single field that tells the factory which drawing the wall is being built to. `REJECT` moves the revision `SUBMITTED → REJECTED`, requires the `reason` to be present and between 1 and 240 characters (a missing or empty reason is refused with `ERR_VALIDATION_FAILED`), stores it as the revision's `rejection_reason`, moves the project's `engineering_state` `UNDER_REVIEW → REJECTED`, and leaves `approved_revision_number` unset. Both branches increment the revision's `version` and the project's `version` by 1.

Rejection reopens the loop rather than ending it: from `REJECTED` the design engineer may submit a further revision, which moves the project back to `UNDER_REVIEW` with the next `revision_number`. That cycle — `UNDER_REVIEW → REJECTED → UNDER_REVIEW` — may repeat without bound, and `revision_number` is effectively its loop counter. `APPROVED`, by contrast, is terminal for the engineering dimension.

### 3.4. Module Manufacturing: Pixel Testing, Colour Calibration and the Rework Allowance

Every LED module enters the system when a `ProductionOperator` registers it against a product family, naming the `display_model_id` it belongs to and its factory `serial_no` of 1 to 40 characters. Serials are globally unique across all modules; reusing one is refused with `ERR_MODULE_SERIAL_DUPLICATE`. A fresh module starts in `module_state` `MANUFACTURED` with `rework_cycles` at 0, no measurements recorded, and no placement — its `cabinet_id`, `slot_index`, `replaces_module_id` and `reserved_service_contract_id` are all unset, and `dead_pixel_count`, `max_cluster_size` and `color_bin` are all null until the relevant test runs.

**Pixel testing.** An operator records a dead-pixel test by supplying `dead_pixel_count` and `max_cluster_size`, the largest run of adjacent dead pixels found; both are mandatory whole numbers of zero or greater, and a missing, fractional or negative value is refused with `ERR_VALIDATION_FAILED`. The operation is available while the module is `MANUFACTURED` or `REWORK`; in any other state it is refused with `ERR_INVALID_MODULE_STATE`. Both measurements are stored on the module as the results of the most recent test regardless of outcome. The test passes when the reported dead-pixel count is at most the family's `module_dead_pixel_max` **and** the reported cluster size is at most the family's `module_cluster_max`; a passing test advances the module `MANUFACTURED → PIXEL_TESTED`, or `REWORK → PIXEL_TESTED` when it is a retest after rework, and in the retest case it does so **without touching `rework_cycles`**.

A test fails when either the dead-pixel count exceeds `module_dead_pixel_max` or the cluster size exceeds `module_cluster_max`. Failure runs the rework accounting, which is uniform wherever it applies: the candidate cycle count is the module's current `rework_cycles` plus 1, that value is **always** written back to `rework_cycles`, and then the module lands in `REWORK` if the candidate count is within the plant's allowance of **two** rework cycles, or in `SCRAPPED` if the candidate count exceeds it. In practice a module gets two failures and dies on the third. A failing test from `MANUFACTURED` therefore yields `MANUFACTURED → REWORK` on the first two failures and `MANUFACTURED → SCRAPPED` on a failure that exhausts the allowance; a failing retest yields the `REWORK → REWORK` self-loop while the allowance holds and `REWORK → SCRAPPED` once it is spent. The counter is monotonic: passing a retest never decrements it, so a module that reworked twice and then passed remains one failure away from scrap for the rest of its life. `SCRAPPED` is terminal.

**Factory colour calibration.** Calibration is recorded with three measurements — `measured_brightness_nits`, `measured_color_x` and `measured_color_y` — and is available while the module is `PIXEL_TESTED` or `REWORK`, with any other state refused as `ERR_INVALID_MODULE_STATE`. The service computes the module's chroma error as the larger of two absolute differences: the gap between `measured_color_x` and the family's `reference_color_x`, and the gap between `measured_color_y` and the family's `reference_color_y`. All three measurements are mandatory: `measured_brightness_nits` is a whole number of zero or greater, and each measured coordinate lies strictly between 0 and 1, with a value outside those bounds refused as `ERR_VALIDATION_FAILED`. Coordinates are supplied and compared at 4 decimal places, and one carrying more than 4 decimal places is refused the same way.

That single chroma error is read against a three-band tolerance ladder. A chroma error greater than 0.020 means the panel is not reworkable at all: the request is refused with `ERR_CHROMA_OUT_OF_TOLERANCE`, **no measurement is stored, `rework_cycles` is untouched and the module does not change state**. A chroma error greater than 0.008 but no greater than 0.020 lands in the rework band: the three measurements are stored, `color_bin` stays null, and the rework accounting above runs — so the module goes `PIXEL_TESTED → REWORK` (or `REWORK → REWORK`) while the two-cycle allowance holds, and `PIXEL_TESTED → SCRAPPED` (or `REWORK → SCRAPPED`) once the incremented count exceeds it. A chroma error of 0.008 or less calibrates the module: the measurements are stored, the module moves `PIXEL_TESTED → CALIBRATED` — or `REWORK → CALIBRATED` when the in-tolerance calibration is recorded directly against a reworked module, which needs no fresh pixel test first — and the acting `X-User-ID` is recorded as `calibrated_by_user_id` — the field that later blocks that same identity from QA-approving any cabinet holding this module.

A calibrated module is also **binned**, and the bin letter uses a stricter inner threshold than the calibrate-or-rework split, so a module can legitimately calibrate and still land in the weaker letter band. The letter is `A` when the chroma error is at most 0.003 and `B` otherwise. The digit is `1` when `measured_brightness_nits` is at least 96 percent of the family's `rated_brightness_nits`, that floor being rounded **up** to a whole number of nits, and `2` otherwise. The two characters concatenate into `color_bin`, which is therefore one of `A1`, `A2`, `B1` or `B2`, and the service also stores `color_bin_rank` as the bin's ordinal for later replacement matching: `A1` ranks 0, `A2` ranks 1, `B1` ranks 2 and `B2` ranks 3. Both fields stay null until the module reaches `CALIBRATED`. Reading a module back exposes its test results, its bin, its placement and its `rework_cycles`; listing modules by `module_state` or `color_bin` is how a production planner finds stock of a given quality.

### 3.5. Cabinet Assembly: Slots, Dead-Pixel Density and As-Built Uniformity

A wall is assembled cabinet by cabinet, and each cabinet is first planned into a position. A `ProductionOperator` plans one by naming the `project_id` and the 1-based `grid_row` and `grid_col` it will occupy. The position must lie inside the project's declared grid — the row no greater than `cabinet_grid_rows`, the column no greater than `cabinet_grid_cols` — and no other cabinet of that project may already hold it; a duplicate position and a position past the far edge of the grid are both refused with `ERR_CABINET_POSITION_TAKEN`. A row or column below 1 is a different matter: it fails the shape screen of rung 3 first and is refused with `ERR_VALIDATION_FAILED`. A planned cabinet begins in `cabinet_state` `PLANNED` with `installed_module_count` at 0, an empty `occupied_slot_indexes` list, `total_dead_pixel_count` at 0, `dead_pixel_ppm` at 0.00, an empty `baseline_module_ids` list, and both `as_built_uniformity_score` and `baseline_uniformity_score` null.

**Installing a module.** An operator populates a cabinet by naming the `module_id` to install, the `slot_index` it goes into, and `expected_cabinet_version`. The response returns the updated module rather than the cabinet. Six conditions guard the install and, as always, the first violated one decides: the supplied `expected_cabinet_version` must match the cabinet's current `version` (`ERR_STALE_CABINET_VERSION`); the owning project's `engineering_state` must be `APPROVED` (`ERR_ENGINEERING_NOT_APPROVED`); the module must be in `CALIBRATED` (`ERR_INVALID_MODULE_STATE`); the cabinet must be in `PLANNED` or `IN_ASSEMBLY` (`ERR_INVALID_CABINET_STATE`); the module's `display_model_id` must equal the display model pinned by the cabinet's project (`ERR_MODULE_MODEL_MISMATCH`); the requested `slot_index`, already screened at rung 3 as an integer of at least 1 so that a zero or negative slot is an `ERR_VALIDATION_FAILED` rather than a slot conflict, must not exceed the family's `modules_per_cabinet` and must not already appear in the cabinet's `occupied_slot_indexes` (`ERR_CABINET_SLOT_OCCUPIED`); and finally the module must not be held as a contracted spare, meaning its `reserved_service_contract_id` must be unset (`ERR_MODULE_RESERVED_AS_SPARE`). That last ordering matters in a busy plant: an operator who grabs a reserved spare and aims it at an occupied slot is told about the slot, not about the reservation.

A successful install writes the cabinet's id into the module's `cabinet_id`, stores the `slot_index`, and moves the module `CALIBRATED → INSTALLED`. On the cabinet side it recomputes `installed_module_count`, rebuilds `occupied_slot_indexes` as the ascending sorted list of slot indexes held by modules currently `INSTALLED` there, and refreshes `total_dead_pixel_count`, `dead_pixel_ppm` and `as_built_uniformity_score`. The first module installed in a cabinet moves it `PLANNED → IN_ASSEMBLY`, and the install that brings `installed_module_count` up to the family's `modules_per_cabinet` moves it `IN_ASSEMBLY → POPULATED`. Both transitions are evaluated on the same install, so on a family holding a single module per cabinet the first install carries the cabinet straight from `PLANNED` to `POPULATED` under one version increment. The very first install anywhere on the project also moves the project's `production_state` `NOT_STARTED → IN_ASSEMBLY`. Every record the install touches — the module, the cabinet, and the project when its dimension moved — takes a `version` increment of 1 and a refreshed `updated_at`.

**Removing a module.** Removal is the compensating action and takes the `module_id` plus `expected_cabinet_version`, again answering with the updated module. The module must currently be `INSTALLED` and its `cabinet_id` must be the cabinet being operated on, or the request is refused with `ERR_INVALID_MODULE_STATE`; the cabinet must be in `IN_ASSEMBLY`, `POPULATED` or `QUARANTINED`, or the request is refused with `ERR_INVALID_CABINET_STATE`; and the version must match, or the request is refused with `ERR_STALE_CABINET_VERSION`. Removal clears the module's `cabinet_id` and `slot_index` and returns it to `CALIBRATED`, freeing the slot for reuse, then recomputes the same five cabinet aggregates. An install followed by a removal of the same module must leave `installed_module_count` and `occupied_slot_indexes` exactly as they were before the pair.

Removal also walks the cabinet's own state backwards, and the three cases are distinct. From `POPULATED` a removal necessarily returns the cabinet to `IN_ASSEMBLY`, because a populated cabinet is by definition full and one fewer module cannot still be full. From `IN_ASSEMBLY` a removal keeps the cabinet in `IN_ASSEMBLY` — a self-loop that holds **even when `installed_module_count` falls back to 0**; a cabinet never returns to `PLANNED` once assembly has begun. And from `QUARANTINED` a removal moves the cabinet `QUARANTINED → IN_ASSEMBLY`, which is how a quarantined cabinet re-enters production; that path is what unblocks the parent project, as §3.6 describes.

**Dead-pixel density.** A cabinet's `total_dead_pixel_count` is the sum of `dead_pixel_count` over the modules whose `cabinet_id` is this cabinet **and** whose `module_state` is `INSTALLED` — modules that have been returned or scrapped are excluded even where they retain a `cabinet_id` for traceability — plus the `new_dead_pixel_count` of the cabinet's most recent burn-in run whose `run_state` is `PASSED` or `FAILED`, taking the last such run in ascending `created_at` order, and adding nothing when no such run exists. Aborted runs contribute nothing. `dead_pixel_ppm` is then that total divided by the family's `cabinet_pixel_count`, multiplied by one million to express it in parts per million, rounded to 2 decimal places. This is the figure burn-in compares against the family's `dead_pixel_ppm_limit`, and it is recomputed on every module install, every module removal, every burn-in completion and every warranty module swap.

**As-built uniformity.** Colour and brightness consistency across a cabinet is scored on a 100-point scale, and the same scoring procedure is used twice in this system over two different module sets. Over whichever set applies, take the mean of the modules' `measured_brightness_nits` — carried at full precision, not rounded — and compute the brightness spread as the highest measured brightness minus the lowest, divided by that mean, multiplied by 100, rounded to 4 decimal places. Compute the chroma spread as the range of `measured_color_x` across the set (its maximum minus its minimum) plus the range of `measured_color_y`, rounded to 6 decimal places. The score is then 100, less 1.5 times the brightness spread percentage, less 2000 times the chroma spread, rounded to 2 decimal places and floored at 0.00 so that a badly mismatched cabinet never scores negative. The score requires at least **two** modules in the set; with fewer than two it is null, and it is likewise null when the mean measured brightness of the set works out to zero, since no spread can be expressed against a zero mean and no division is attempted.

The `as_built_uniformity_score` applies that procedure to the modules **currently** holding `module_state` `INSTALLED` in the cabinet, and is refreshed on every install, every removal and every warranty swap. It is therefore a live figure, and it is null until the cabinet holds two installed modules. Reading a cabinet exposes it alongside `baseline_uniformity_score`, `dead_pixel_ppm`, `total_dead_pixel_count`, `installed_module_count`, `occupied_slot_indexes` and `qa_approved_by_user_id`; the gap between the two uniformity figures is the observable degradation a QA report cites, and §3.6 explains where the baseline comes from.

### 3.6. Burn-In: Chamber Booking, the Frozen QA Baseline and the Quarantine Cascade

A fully populated cabinet is soaked before anyone signs for it. A `QAEngineer` schedules the soak by naming the `cabinet_id` and the `burn_in_chamber_id`, the `window_start` and `window_end` of the soak as ISO 8601 UTC instants with three fractional digits, the `slots_required` the run consumes (a whole number of at least 1, with no upper bound of its own, so asking for more slots than the chamber owns is a capacity refusal rather than a shape refusal), the `drive_pct` used during the soak (a whole number from 1 to 100), and `ambient_c`, the chamber ambient temperature in Celsius, between -20 and 70 inclusive and accepted as a decimal rather than restricted to whole degrees. The window must be non-empty — a `window_end` at or before `window_start` is refused as `ERR_VALIDATION_FAILED`.

Four business rules guard scheduling, in this order. The cabinet must be `POPULATED`, since a partly built wall panel is not worth chamber time (`ERR_INVALID_CABINET_STATE`). The requested `drive_pct` must not exceed **either** the family's `max_drive_pct` **or** the chamber's `certified_max_drive_pct` — that is, it must be at most the smaller of the two — and exceeding either ceiling is refused as `ERR_DRIVE_LEVEL_UNSAFE`. The window must be at least as long as the family's `burn_in_hours_required` in whole hours, with a window of exactly that length passing and anything shorter refused as `ERR_BURN_IN_DURATION_TOO_SHORT`. Only then is chamber capacity consulted. Safety before scheduling is the standing principle: an unsafe drive level is reported even when the chamber is also full.

Capacity uses the closed, turnaround-buffered geometry of §2.10. The new run's occupancy is computed as `occupied_until`, the requested `window_end` advanced by the chamber's `turnaround_minutes`, and the candidate interval runs from `window_start` through that instant with **both ends inclusive**. Every existing run of the same chamber whose `run_state` is still `SCHEDULED` is examined over its own closed interval from its `window_start` through its `occupied_until`; runs that have already reached `PASSED`, `FAILED` or `ABORTED` have released their slots and are ignored. The candidate's `slots_required` plus the `slots_required` of every overlapping scheduled run is the concurrent slot demand, and if that sum exceeds the chamber's `slot_capacity` the booking is refused with `ERR_CHAMBER_CAPACITY_EXCEEDED`. Because capacity is an aggregate budget, two runs may legally share a chamber whenever their slot sums fit; because the intervals are closed, a run that starts at the exact instant a previous run's turnaround ends still collides with it.

A successful booking creates the run in `run_state` `SCHEDULED`, stores its `occupied_until`, leaves `new_dead_pixel_count`, `measured_brightness_nits`, `measured_uniformity_pct`, `cabinet_dead_pixel_ppm`, `abort_reason` and `completed_by_user_id` all null, adds the run's `slots_required` to the chamber's `reserved_slot_total` and 1 to its `scheduled_run_count`, and moves the cabinet `POPULATED → BURN_IN` with a version increment. Because the chamber's reservation totals moved, the chamber record itself also takes a version increment and a fresh `updated_at`, and so it does on the completion and abortion writes that release those slots again.

**Completing a run.** After the soak, the `QAEngineer` reports three figures, all three mandatory: `new_dead_pixel_count`, the additional dead pixels the soak revealed, a whole number of zero or greater; `measured_brightness_nits`, the cabinet brightness at completion, likewise a whole number of zero or greater; and `measured_uniformity_pct`, the chamber-measured uniformity percentage, a decimal of zero or greater carrying no upper bound, so a reading above 100 is stored as supplied rather than refused. The run must still be `SCHEDULED` (`ERR_INVALID_RUN_STATE`), and the logical clock must have reached the run's `window_end`, with the clock exactly at `window_end` counting as elapsed and anything earlier refused as `ERR_BURN_IN_WINDOW_NOT_ELAPSED`. Either outcome stores the three measurements, records `completed_by_user_id` as the acting `X-User-ID`, recomputes the cabinet's dead-pixel density with the new count folded in, and snapshots that figure onto the run as `cabinet_dead_pixel_ppm`, rounded to 2 decimal places, and releases the chamber: the run's `slots_required` is subtracted from the chamber's `reserved_slot_total` and 1 from its `scheduled_run_count`.

The verdict is a single conjunction of three acceptance floors. The run **passes** when the cabinet's recomputed dead-pixel density is at most the family's `dead_pixel_ppm_limit`, **and** `measured_brightness_nits` is at least 4800 nits, **and** `measured_uniformity_pct` is at least 92.00 percent. It **fails** when the density exceeds the limit, or the brightness falls below 4800 nits, or the uniformity falls below 92.00 percent. Each comparison treats exact equality with the floor as acceptable.

A pass moves the run `SCHEDULED → PASSED` and the cabinet `BURN_IN → BURN_IN_PASSED`, and it does one thing nothing else in the system does: it **freezes the QA baseline**. The uniformity procedure of §3.5 is evaluated once, at that instant, over the modules then holding `module_state` `INSTALLED` in the cabinet, and the result is written to `baseline_uniformity_score` while the participating module ids — ordered ascending by their `created_at` — are written to `baseline_module_ids`. That input set is frozen: later installs, removals and warranty swaps recompute `as_built_uniformity_score` but never move the baseline. After a warranty swap the two figures legitimately diverge over identical stored data, and their difference is the degradation the QA report cites.

A failure is where this system's deepest cascade runs, and all four hops land in a single write. First, the run moves `SCHEDULED → FAILED` with its measurements stored. Second, the cabinet moves `BURN_IN → QUARANTINED` and its `baseline_uniformity_score` is left null and its `baseline_module_ids` left as the empty list it was planned with — a failed cabinet never acquires a baseline. Third, the project's `quarantined_cabinet_count` is recomputed, and with at least one quarantined cabinet the project's `production_state` becomes `BLOCKED`; this happens from `IN_ASSEMBLY`, from `QA_COMPLETE`, from `INSTALLED` and even from `COMMISSIONED`, so a late quality failure can pull an already-handed-over wall back into a blocked state. A project that already stands in `BLOCKED` when a second of its cabinets fails is left alone by hops three and four: it takes no further version increment and no visit is aborted a second time. Fourth, every commissioning visit of that project whose `visit_state` is `SCHEDULED`, `ON_SITE` or `CALIBRATED` is moved to `ABORTED` with `abort_reason` set to the exact string `PROJECT_BLOCKED`, and each such abort decrements the crew's `scheduled_visit_count`, releasing the window for another booking. The plant would rather free a crew than send a truck to a wall it cannot commission.

**Aborting a run.** A scheduled run may be abandoned before its verdict by supplying a `reason`, which is mandatory and must be at least 1 character long but carries no upper length bound. The run must still be `SCHEDULED`, or the request is refused with `ERR_INVALID_RUN_STATE`. The abort moves the run `SCHEDULED → ABORTED`, stores the supplied text as `abort_reason`, records `completed_by_user_id`, and moves the cabinet `BURN_IN → POPULATED` so it can be rescheduled. Abortion is the exact compensating action for scheduling: the chamber's `reserved_slot_total` returns to its pre-schedule value and `scheduled_run_count` drops by 1. An aborted run contributes no dead pixels to its cabinet and never freezes a baseline. All three of `PASSED`, `FAILED` and `ABORTED` are terminal for a run.

**Recovery from quarantine.** A blocked project is unblocked from the shop floor, not from an override. Removing modules from the quarantined cabinet moves it `QUARANTINED → IN_ASSEMBLY`, and once the project's recomputed `quarantined_cabinet_count` reaches 0 the project moves `BLOCKED → IN_ASSEMBLY`. From there the ladder is re-walked from scratch: the cabinet is repopulated, soaked again, QA-approved again, mounted again. Aborted commissioning visits are **not** resurrected by recovery — a fresh visit must be booked.

### 3.7. QA Sign-Off, Structural Mounting and On-Site Commissioning

QA approval is the plant's release gate and is available only on a cabinet that has passed its soak: a `QAEngineer` approves a cabinet in `BURN_IN_PASSED`, and any other `cabinet_state` is refused with `ERR_INVALID_CABINET_STATE`. The approval carries no request body. Independence is enforced here as described in §2.9 — the approving `X-User-ID` must not be the `calibrated_by_user_id` of any module currently `INSTALLED` in that cabinet, on pain of `ERR_SEGREGATION_OF_DUTIES`. Note what is **not** required: the cabinet's `as_built_uniformity_score` need not equal its frozen `baseline_uniformity_score`. Both are simply reported, and it is the approver's judgement, not an automatic gate, that reconciles them.

Approval records `qa_approved_by_user_id` and moves the cabinet `BURN_IN_PASSED → QA_PASSED`. The project's `qa_passed_cabinet_count` — the count of its cabinets whose `cabinet_state` is `QA_PASSED` or `MOUNTED` — is then recomputed, and when that count equals the project's `cabinet_count` while `quarantined_cabinet_count` stands at 0, the project's `production_state` rises `IN_ASSEMBLY → QA_COMPLETE`. Both the cabinet and the project take a version increment.

Mounting moves the wall to site. A `FieldEngineer` records the structural mounting of a cabinet that is in `QA_PASSED` — any other state is refused with `ERR_INVALID_CABINET_STATE` — on a project whose `engineering_state` is still `APPROVED`, refused otherwise with `ERR_ENGINEERING_NOT_APPROVED`. Mounting takes no request body, moves the cabinet `QA_PASSED → MOUNTED`, which is terminal for the cabinet lifecycle, and recomputes the project's `mounted_cabinet_count`. When every cabinet of the project is mounted — that is, when the recomputed count equals `cabinet_count` — the project rises `QA_COMPLETE → INSTALLED`. The project takes a version increment and a fresh `updated_at` on every successful mount, whether or not that mount moved its `production_state`.

**Booking a crew.** A commissioning visit may be booked by either a `PlantAdmin` or a `FieldEngineer`, naming the `project_id`, the `commissioning_crew_id`, and the half-open `window_start` and `window_end` of the on-site window as ISO 8601 UTC instants with three fractional digits; `window_end` must be strictly later than `window_start`. Two rules guard the booking and their order is worth internalising because it is not the intuitive one: the **overlap check runs first**, so a crew that already holds a `SCHEDULED`, `ON_SITE` or `CALIBRATED` visit whose half-open window overlaps the requested one is refused with `ERR_CREW_DOUBLE_BOOKED` per §2.10, and only afterwards is licensing checked, where a crew whose `region_code` differs from the project's `site_region_code` is refused with `ERR_CREW_REGION_MISMATCH`. A booking that survives both is created with `visit_state` `SCHEDULED`, its `measured_brightness_nits`, `measured_uniformity_pct`, `arrived_at`, `signed_off_at` and `abort_reason` all null, and the crew's `scheduled_visit_count` rises by 1 — the crew record taking a version increment and a fresh `updated_at` with it, as it does again when sign-off or an abort releases the booking. Visits that have reached `SIGNED_OFF` or `ABORTED` have released the crew and never block a new booking.

**Arrival.** The booked crew — and only that crew, per the ownership rule of §2.1 — records arrival on site. The visit must be `SCHEDULED` (`ERR_INVALID_VISIT_STATE`); the project's `production_state` must be `INSTALLED`, meaning every cabinet is mounted, or the crew is turned away with `ERR_CABINETS_NOT_MOUNTED`; and the logical clock must lie inside the half-open window, at or after `window_start` and strictly before `window_end`, with a clock reading exactly at `window_end` counting as outside and refused with `ERR_VISIT_WINDOW_NOT_CURRENT`. Those three checks are evaluated in exactly that order, so a crew arriving out of window at a wall that is not fully mounted hears about the mounting first. Arrival stamps `arrived_at` from the logical clock and moves the visit `SCHEDULED → ON_SITE`.

**On-site calibration.** Once on site, the crew records the two acceptance measurements taken after structural mounting: `measured_brightness_nits`, a mandatory whole number of zero or greater, and `measured_uniformity_pct`, a mandatory decimal of zero or greater with no upper bound. The visit must be `ON_SITE`, or the request is refused with `ERR_INVALID_VISIT_STATE`. On-site floors are laxer than chamber floors because a mounted wall is measured through glass, dust and daylight: the measured brightness must be at least 95 percent of the project's contracted `target_brightness_nits`, with that floor rounded **up** to a whole number of nits, and the measured uniformity must be at least 90.00 percent. A measurement below either floor is an out-of-range value and is refused with `ERR_VALIDATION_FAILED`; exact equality with either floor passes. Unlike the shape checks of rung 3, however, the two floors are project-relative and are therefore evaluated **after** the ownership and `ON_SITE` state checks and in the order stated — brightness first, then uniformity — so a below-floor measurement offered against a visit that is not `ON_SITE` reports `ERR_INVALID_VISIT_STATE`, and a payload below both floors reports the brightness failure. On-site calibration is also the one crew action that does not re-check the project's `production_state`. A successful calibration stores both measurements on the visit and moves it `ON_SITE → CALIBRATED`.

**Sign-off.** Sign-off is the commercial handover and the second four-hop cascade in this system. The visit must be `CALIBRATED` (`ERR_INVALID_VISIT_STATE`), the acting crew must be the booked crew, and the project must still be in `production_state` `INSTALLED` (`ERR_CABINETS_NOT_MOUNTED`). The write then stamps `signed_off_at` from the logical clock and moves the visit `CALIBRATED → SIGNED_OFF`; moves the project `INSTALLED → COMMISSIONED`; activates the warranty by moving **every** service contract of that project whose `contract_state` is `PENDING` to `ACTIVE`, setting each one's `warranty_start_at` to the same `signed_off_at` instant and incrementing each contract's `version`; and decrements the crew's `scheduled_visit_count`, releasing the crew. `SIGNED_OFF` and `ABORTED` are the two terminal visit states, and an aborted visit records why in its `abort_reason`.

### 3.8. Service Contracts and the Spare Module Pool

A `ServiceManager` sells at most one service contract per project. The sale names the `project_id`, a `tier` of `BRONZE`, `SILVER` or `GOLD`, a `spare_pct_bp` holding expressed in basis points of the project's `module_count` (0 to 5000, so anything from nothing up to half the wall), and a `term_months` of between 12 and 120 whole months. Two rules guard the sale, in this order: a project that already carries a contract is refused with `ERR_CONTRACT_ALREADY_EXISTS`, and only then is the tier's spare floor checked — `spare_pct_bp` must be at least 100 basis points for `BRONZE`, 200 for `SILVER` and 300 for `GOLD`, with anything below refused as `ERR_SPARE_PCT_BELOW_MINIMUM`.

The tier fixes the on-site commitment. `response_hours` is derived, never supplied: two full days, that is 48 hours, for `BRONZE`; one full day, that is 24 hours, for `SILVER`; and 8 hours for `GOLD`. The spare obligation is `spare_required_count`, computed as the project's `module_count` multiplied by `spare_pct_bp`, divided by 10000, and **rounded up** to a whole module — a 3% holding on a 700-module wall obliges 21 modules, and a holding that works out to a fraction obliges the next whole module. That figure is computed from the project's `module_count` as it stands at contract creation and is **not** re-derived when cabinets change later.

**Annual fee.** The fee has three stages and their order is pinned. First, `gross_fee_cents` is the project's `total_area_sqm` multiplied by the tier's per-square-metre rate — 120000 cents for `BRONZE`, 190000 cents for `SILVER`, 268000 cents for `GOLD` — rounded half up to whole cents. Second, the spare carrying charge is `spare_required_count` multiplied by 4500 cents per held module, and `subtotal_fee_cents` is `gross_fee_cents` plus that carrying charge. Third — and this is the step implementers get wrong — the volume discount tier is selected **from `subtotal_fee_cents`, exactly once**: `volume_discount_pct` is 0.00 when the subtotal is below 2000000 cents, 0.04 when it is below 5000000 cents, 0.07 when it is below 10000000 cents, and 0.10 otherwise. The discount amount is the subtotal multiplied by that fraction, rounded half up to whole cents, and `annual_fee_cents` is `subtotal_fee_cents` minus that rounded discount. The tier is never re-evaluated against the post-discount fee, even when the discount pushes the fee back below the boundary it just crossed.

A new contract is created in `contract_state` `PENDING` with `spare_reserved_count` at 0, `sla_breach_count` at 0 and `warranty_start_at` null. It becomes `ACTIVE` only through commissioning sign-off (§3.7), which is also what stamps `warranty_start_at` — the zero point of the brightness-degradation warranty. Nothing in the warranty pipeline works before that: opening, responding to, assessing or fulfilling a case against a contract that is still `PENDING` is refused with `ERR_CONTRACT_NOT_ACTIVE`.

**Reserving a spare.** A `ServiceManager` holds stock against the contract by reserving `CALIBRATED` modules, supplying `expected_service_contract_version` and, optionally, the specific `module_id` to hold; the response is the reserved module. A named module must be in `CALIBRATED`, or the request is refused with `ERR_INVALID_MODULE_STATE`, and that state is the **only** property a named module is screened on: the display-model match and the free-stock condition below govern the server's automatic pick alone, so naming a `CALIBRATED` module of another family, or one already reserved to a different contract, is accepted and simply re-points the reservation to this contract. When `module_id` is omitted the server picks, and its choice is deterministic. Eligible candidates are modules whose `module_state` is `CALIBRATED`, whose `display_model_id` matches the display model pinned by the contract's project, and whose `reserved_service_contract_id` is unset — modules that are `MANUFACTURED`, `PIXEL_TESTED`, in `REWORK`, `INSTALLED`, `RETURNED` or `SCRAPPED` are never candidates. Candidates are ordered by `color_bin_rank` **descending**, so the weakest bins are reserved first and `A1` stock is held back for production installs; ties are broken by `measured_brightness_nits` **ascending**, and any remaining tie by `created_at` ascending. If the eligible pool is empty the reservation is refused with `ERR_NO_ELIGIBLE_SPARE_MODULE`.

A reservation writes the contract's id into the module's `reserved_service_contract_id` and raises `spare_reserved_count`, which is always the count of modules whose `reserved_service_contract_id` is this contract **and** whose `module_state` is `CALIBRATED`. If the contract was `SUSPENDED` and the reservation brings `spare_reserved_count` up to at least `spare_required_count` while `sla_breach_count` is still below 2, the contract moves `SUSPENDED → ACTIVE`, and the project's `service_posture` returns to `NORMAL` provided no other contract of that project is still `SUSPENDED`. Both the contract and the module take a version increment.

**Releasing a spare.** The compensating action returns a held module to free stock, and here the `module_id` is mandatory alongside `expected_service_contract_version`. The named module must currently be reserved to this very contract, or the release is refused with `ERR_SPARE_NOT_RESERVED`. The release clears the module's `reserved_service_contract_id` and lowers `spare_reserved_count` by 1, and if that drops the pool below `spare_required_count` the contract moves `ACTIVE → SUSPENDED` and the project's `service_posture` becomes `AT_RISK`, the project taking a version increment and a fresh `updated_at` on that flip. Both records take a version increment, and the contract takes its increment on every reservation and every release whether or not `contract_state` actually moved.

The contract therefore cycles: `ACTIVE → SUSPENDED → ACTIVE` may repeat without bound as the spare pool is drained and refilled. `sla_breach_count`, however, only ever grows, and reactivation requires it to be below 2 — so a contract that has breached twice is pinned in `SUSPENDED` permanently no matter how many spares are reserved against it.

### 3.9. Warranty Cases: Deadlines, Two Assessment Bases and Colour-Matched Fulfilment

A field problem enters the system as a service case, raised by a `ServiceManager` against an `ACTIVE` contract. The case names the `service_contract_id`, the affected `cabinet_id`, a `case_type` of either `MODULE_FAULT` or `BRIGHTNESS_DEGRADATION`, a `severity` of `CRITICAL`, `MAJOR` or `MINOR`, and a free-text `symptom` of up to 240 characters, which is a mandatory field but may legitimately be the empty string. Three rules guard case creation in this order: the contract must be `ACTIVE` (`ERR_CONTRACT_NOT_ACTIVE`); then the named cabinet must belong to the contract's project **and**, when a faulty module is nominated, that module must be installed in that very cabinet, with either violation refused as `ERR_MODULE_GRID_MISMATCH`; then the payload must match the case type.

Payload symmetry between the two case types is strict. A `MODULE_FAULT` case **requires** `faulty_module_id`, the caller-nominated failed module, and must **omit** `measured_brightness_nits`. A `BRIGHTNESS_DEGRADATION` case **requires** `measured_brightness_nits`, the field brightness measurement, which must be zero or greater, and must **omit** `faulty_module_id` — a degradation claim is about the whole panel, and which module gets swapped is the server's decision, not the caller's. Supplying the field the type forbids is a shape violation screened at rung 3 and refused with `ERR_VALIDATION_FAILED`, ahead of every existence, state and coherence check; a payload that merely omits the measurement its type demands survives rung 3 and is refused later with `ERR_MEASUREMENT_REQUIRED`.

Creation stamps `reported_at` from the logical clock, sets `case_state` to `OPEN` with `response_breached` false and `responded_at` together with every assessment and fulfilment field — `elapsed_warranty_months`, `allowed_degradation_pct`, `degradation_pct`, `shortfall_pct`, `assessment_basis`, `credit_cents`, `denial_reason`, `resolved_faulty_module_id` and `replacement_module_id` — left null, and computes `response_deadline_at` as `reported_at` advanced by the contract's `response_hours` multiplied by a severity multiplier: half the contracted hours for `CRITICAL`, the full contracted hours for `MAJOR`, and double for `MINOR`. A `CRITICAL` case on a `GOLD` contract is therefore due in four hours; a `MINOR` case on a `BRONZE` contract has four days.

**Responding.** Recording the on-site response takes no request body. The case must be `OPEN` (`ERR_INVALID_CASE_STATE`) and the contract `ACTIVE` (`ERR_CONTRACT_NOT_ACTIVE`). The write stamps `responded_at` from the logical clock, moves the case `OPEN → RESPONDED`, and sets `response_breached` to true only when `responded_at` is **strictly later** than `response_deadline_at` — a response landing at exactly the deadline instant is on time. A breach raises the contract's `sla_breach_count` by 1 and takes a version increment on the contract, and when that counter reaches 2 the contract moves `ACTIVE → SUSPENDED` and the project's `service_posture` becomes `AT_RISK` — the project taking a version increment on that flip — which, per §3.8, freezes every remaining case on that contract. An on-time response writes only the case: the contract is left entirely untouched, its `version` unchanged.

**Assessing.** The `ServiceManager` decides the case with a `decision` of `APPROVE` or `DENY`, accompanied — as the branch it takes requires — by an `assessment_basis` or a `denial_reason`. The case must be `RESPONDED` and the contract `ACTIVE`. Only `decision` itself, and `assessment_basis` when it is supplied, are screened at rung 3; the `DENY` branch's demand for a `denial_reason` and the degradation branch's demand for an `assessment_basis` are evaluated on their own branch **after** the state and contract checks, so an otherwise malformed branch payload aimed at a case that is not `RESPONDED` reports `ERR_INVALID_CASE_STATE` rather than `ERR_VALIDATION_FAILED`. The two branches write disjoint sets of fields, and each is specified in full below.

A `DENY` requires `denial_reason` to be present and between 1 and 240 characters, stores it, sets `credit_cents` to 0, leaves `assessment_basis` null, leaves both `resolved_faulty_module_id` and `replacement_module_id` null, and moves the case `RESPONDED → DENIED`, which is terminal. Nothing is pinned and no module moves.

An `APPROVE` on a `BRIGHTNESS_DEGRADATION` case first quantifies the claim against the guaranteed degradation curve. `elapsed_warranty_months` is the age of the warranty at the moment the case was reported, measured as the whole seconds between the contract's `warranty_start_at` and the case's `reported_at` — clamped to zero should the logical clock have been wound back so that `reported_at` precedes `warranty_start_at` — divided by 86400 and floored to whole days, then divided by 30 and floored again to whole 30-day warranty months. `allowed_degradation_pct` is the brightness loss the warranty concedes by then: 50 percent — the guaranteed total loss over the warranty's five-year, 60-month term — multiplied by `elapsed_warranty_months`, divided by 60, rounded to 2 decimal places. `degradation_pct` is the panel's actual loss: the family's `rated_brightness_nits` minus the reported `measured_brightness_nits`, divided by that same `rated_brightness_nits`, multiplied by 100, rounded to 2 decimal places. `shortfall_pct` is how far the panel has fallen below the curve: the difference of actual loss less allowed loss, rounded to 2 decimal places, and floored at 0.00 so it is never negative. A `shortfall_pct` of exactly 0.00 means the panel is still inside the guaranteed curve and is not compensable: the approval is refused with `ERR_DEGRADATION_WITHIN_ALLOWANCE`. Only after that does the service check that the case's cabinet still holds at least one module with `module_state` `INSTALLED`, refusing an empty cabinet with `ERR_NO_REPLACEABLE_MODULE`.

`credit_cents` then follows the `assessment_basis` the assessor chose, which is mandatory on this branch: an `APPROVE` of a `BRIGHTNESS_DEGRADATION` case that supplies no `assessment_basis` is refused with `ERR_VALIDATION_FAILED`, and that demand is evaluated only **after** the shortfall and replaceable-module refusals above, so a basis-less approval of a claim still inside the guaranteed curve reports `ERR_DEGRADATION_WITHIN_ALLOWANCE`. The two bases are genuinely different theories of compensation over identical stored data. Both start from `cabinet_value_cents`, the family's `cabinet_area_sqm` multiplied by its `price_per_sqm_cents`, rounded half up to whole cents — the bare cabinet value, carrying none of the environment or redundancy surcharges from §3.2. Under `PRO_RATA_REMAINING_TERM` the credit is `cabinet_value_cents` multiplied by the months of warranty still to run — 60 less `elapsed_warranty_months` — divided by 60, rounded half up to whole cents as the last step; that remaining-term count is not floored at zero, so a case reported after the 60-month term has run out yields a negative `credit_cents`. This basis ignores the size of the shortfall entirely and pays only for lost warranty life. Under `SHORTFALL_SEVERITY` the credit is `cabinet_value_cents` multiplied by the lesser of two fractions: `shortfall_pct` divided by 100 and then multiplied by 2.5, or the hard cap of 0.6; the product is rounded half up to whole cents as the last step. This basis ignores remaining term entirely and pays only for how far below the curve the panel has fallen, never more than 60 percent of cabinet value. An early-life low-severity case and a late-life high-severity case invert their ordering between the two bases, which is exactly why the basis is an explicit input rather than a derived value.

Approval also pins which module will be swapped, writing it to `resolved_faulty_module_id`. For a `MODULE_FAULT` case that is simply the `faulty_module_id` the caller nominated, and such a case skips the degradation arithmetic entirely: `elapsed_warranty_months`, `allowed_degradation_pct`, `degradation_pct` and `shortfall_pct` all stay null and `credit_cents` is 0 whatever basis was supplied — though a basis that *was* supplied is still stored verbatim as the case's `assessment_basis`, and left null when none was. The `ERR_NO_REPLACEABLE_MODULE` check applies to a `MODULE_FAULT` approval too, so a nominated module removed from its cabinet between opening and assessment leaves an empty cabinet and refuses the approval. For a `BRIGHTNESS_DEGRADATION` case the server selects it: among the modules whose `cabinet_id` is the case's cabinet and whose `module_state` is `INSTALLED` — returned modules from earlier swaps are excluded even though they retain a `cabinet_id` — it takes the one with the lowest `measured_brightness_nits`, because the dimmest panel is what the degradation claim is about, breaking ties by `created_at` ascending. An empty candidate set is the `ERR_NO_REPLACEABLE_MODULE` case above. Either way the case moves `RESPONDED → APPROVED`.

**Fulfilling.** The swap itself takes `expected_cabinet_version` and, optionally, the `replacement_module_id` to install. The case must be `APPROVED` (`ERR_INVALID_CASE_STATE`), the contract `ACTIVE`, and the cabinet version current (`ERR_STALE_CABINET_VERSION`). A nominated replacement must be reserved to this very contract — its `reserved_service_contract_id` equal to the case's `service_contract_id` — or the request is refused with `ERR_SPARE_NOT_RESERVED`; and its `color_bin_rank` must be within 1 of the outgoing module's `color_bin_rank`, so that an `A2` panel may be replaced by an `A1`, `A2` or `B1` module but never by a `B2`, with a wider gap refused as `ERR_COLOR_BIN_MISMATCH`. Those two are the only properties a nominated replacement is screened on — its `module_state` and its display model are not re-checked, because the `CALIBRATED`-and-matching-model filters below govern the server's automatic pick alone. When `replacement_module_id` is omitted the server picks from the modules that are `CALIBRATED`, match the project's pinned display model, are reserved to this contract, and sit within that colour-bin tolerance of the outgoing module; candidates are ordered by the absolute colour-bin rank gap **ascending** — closest colour match first — then by `measured_brightness_nits` **descending**, then by `created_at` ascending, and an empty pool is refused with `ERR_NO_ELIGIBLE_SPARE_MODULE`.

Fulfilment is the second four-hop cascade and it answers with the updated case. First, `replacement_module_id` is recorded and the case moves `APPROVED → FULFILLED`, which is terminal. Second, the module pinned as `resolved_faulty_module_id` moves `INSTALLED → RETURNED` and gives up its `slot_index` while **retaining** its `cabinet_id` for traceability, and the replacement module moves `CALIBRATED → INSTALLED` into that vacated `slot_index`, with `replaces_module_id` set to the outgoing module's id — the self-referential chain that lets an auditor walk a slot's whole replacement history — and its `reserved_service_contract_id` cleared, since a module in service is no longer a spare. Third, the contract's `spare_reserved_count` drops by 1, and when that leaves the pool below `spare_required_count` the contract moves `ACTIVE → SUSPENDED`. Fourth, that suspension sets the project's `service_posture` to `AT_RISK`. Along the way the cabinet's `total_dead_pixel_count`, `dead_pixel_ppm` and `as_built_uniformity_score` are recomputed over its new module set while `baseline_uniformity_score` and `baseline_module_ids` are left exactly as burn-in froze them, and version increments land on the cabinet, the case, both modules and the contract — the contract taking its increment on every fulfilment whether or not the drawdown suspended it, and the project taking one as well on the flip to `AT_RISK`.
