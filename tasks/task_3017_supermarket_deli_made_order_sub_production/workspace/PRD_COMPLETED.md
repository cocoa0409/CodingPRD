# Supermarket Deli and Made-to-Order Sub Production API - Product Requirements Document

## 1. Introduction

A supermarket deli counter is a perishable-goods business wearing a service-counter costume. Every pound of sliced turkey loaded onto the hot bar or into the cold case starts a countdown, and the difference between a profitable case yield and a write-off is measured in minutes of hold time rather than days of shelf life. The Deli and Made-to-Order Sub Production API exists to make that countdown legible and enforceable: it plans a day's production, occupies the slicers that do the work, holds each finished batch inside its pull-and-hold window, and forces every pound that expires to travel the mandated markdown-before-discard path before it becomes a recorded liability. The store itself carries a derived posture, and that posture is the single gate through which fresh work is admitted.

The same counter also runs a live queue. A customer orders a sub at the counter, from a phone, or through the digital app, and expects a ticket number and a promised time; behind the glass, someone has to decide which stations are staffed, which bread rolls are actually on hand, and whether the case can cover the weight the ticket implies. Weekly featured-sub promotions bend that demand upward in a predictable wave, and the wave has to be met with bread orders placed before the promotion week even begins.

Layered on top of both is a food-safety regime that is deliberately intrusive. Slicers require certified operators and sanitation cycles that are due on a cut count or a clock, allergen changeover has to be cleared between incompatible products, and waste can only be verified by someone who is neither the producer nor the person who applied the markdown. This document specifies the API that serves all three concerns at once, with the store as the aggregate root that owns batches, slicers, tickets, price files, promotions, platters, associates, certifications and waste records.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID` identifies the acting user, and `X-User-Role` names their operational capacity. A request that omits either header, or that names a role the installation does not recognize, is rejected with `ERR_UNAUTHENTICATED`. A request whose role is recognized but is not listed as an authorized role for the addressed operation is rejected with `ERR_UNAUTHORIZED`.

The system recognizes five roles. `PlatformAdmin` is a chain-level operator with override power over every store; when `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it where an operation carries an operator field, but it never compares it to any entity's `id`. `DeliManager`, `DeliClerk` and `BakeryCoordinator` are entity-backed: when `X-User-Role` is one of these, `X-User-ID` is the `id` of an acting `Associate` row, and ownership checks on any resource that references an `Associate` compare the resource's foreign-key field to `X-User-ID`. Only the two operations that read the acting associate — completing a sub ticket and confirming a catering order — ever resolve `X-User-ID` against the `Associate` table; they treat an identifier that names no row as an associate with an empty `allergy_set` and no certifications, so a self-consistent call from an entity-backed role is never rejected merely because the header names no persisted row. Because certification, allergy and segregation checks all read the acting `Associate`, a manager who works a shift as `DeliClerk` is evaluated against the same certification and allergen rules as a front-line clerk. `ScaleOperator`, like `PlatformAdmin`, is opaque: `X-User-ID` is an opaque operator identifier not tied to any persisted entity, recorded on scale and label operations but never compared to an entity `id`.

The acting role determines permissions only and need not equal the associate's `primary_role`. Role assignment is therefore a permission question, not an identity question: a store manager holding a manager's certifications may legitimately act as `DeliClerk` for a shift, and the certification and segregation checks follow the `Associate` named by `X-User-ID`. A platform-admin capability exists to replace the permission list attached to a role for the installation; it accepts a `role` and the replacement `permissions`, and the acting role's entry becomes the authoritative permission set for authorization checks. Replacing a role's permissions with a set that omits an operation is the supported way to force that role's denial path, and the response reports how many roles currently hold a non-empty permission list. The operations a replacement list may name are derived from the request rather than declared as literal paths: a state-transition call is named by its transition's action verb, a collection read or write by the resource noun together with the method's own verb (`read`, `create`, `update`), and a collection write additionally by `ticket`. An entry of `*`, or an entry ending in `*` that the request path begins with, grants the call outright. Only a role whose replacement entry is present is filtered this way — an empty list therefore omits every operation and denies each call — while a role with no replacement entry is not filtered at all.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` parameter that caps the number of items returned. When omitted it defaults to 10; the accepted range is 1 to 100 inclusive, and a value outside that range is a malformed request. The `offset` parameter skips a number of items from the front of the result set and defaults to 0. Every list endpoint in this API supports both parameters, and list responses additionally expose entity-specific filters described in §4.

Unless a specific list endpoint states otherwise, results are returned sorted by the resource's creation timestamp in ascending order, so the oldest resource appears first. The `meta` object of every paginated response carries four fields: `limit`, `offset`, `total_count` and `has_more`.

Two list endpoints in this API are explicitly ordered rather than creation-ordered: the store sub-queue ordering is defined in §3.4, and the sub-ticket list is ordered by its per-store `creation_sequence`. Both orderings are described where the workflow they serve is described.

### 2.4. Common Resource Properties

Every store-scoped resource in this API carries the same four system-managed fields. The `id` field is a server-minted UUID string with no type prefix; the identifier `store_id` is never a component of it. The `created_at` field is an ISO 8601 UTC timestamp carrying three fractional digits, recording when the row first appeared. The `updated_at` field shares that format and is refreshed on every mutation, including mutations the server performs automatically rather than in response to a client request. The `version` field is an integer that begins at 1 on creation and is incremented by exactly one on each mutation.

Derived fields are mutated fields. Recomputing `case_on_hand_lbs`, `posture`, `posture_reason`, `active_price_file_id`, `targeted_promo_id`, `covered_allergen_set`, `available_bread_units`, `certified_slicer_operator_count`, `verified_waste_liability_cents` or `pending_waste_verification_count` on a `Store` is a mutation of that store: `updated_at` is refreshed and `version` is incremented. The same holds for the derived counters on `ProductionBatch`, `SubTicket`, `Associate`, `SlicerAsset`, `BreadSupplyOrder` and `WasteRecord`. All fourteen entities in this API declare the common field set, so no entity omits `updated_at` or `version`; the only read-only quantities are derived ones, which clients may read but never supply.

### 2.5. Postal Address of the Logical Clock

The server never reads wall-clock time. The logical clock starts at the fixed instant `2026-09-01T00:00:00.000Z` and advances only when a caller instructs it to, through a platform-admin-only capability that accepts the instant to move to. Every deadline, expiry, markdown window, pickup window, sanitation occupancy and promised-time computation in this API is evaluated against that clock and against nothing else. The capability accepts the instant to move to as `current_utc`; there is no way to advance the clock partially, the value supplied is normalised to the canonical three-fractional-digit UTC form and it is that normalised instant the operation echoes back, and the server supplies no fallback to real time when `current_utc` is absent from a request. Because there is no wall-clock read anywhere, the `api_request_timestamp` of every response envelope is the logical clock instant itself. A test or operations harness that wants to move a batch past its hold window, or to walk a promotion into its week, advances the clock and then re-reads the affected resources.

Every interval this API defines is half-open. A hold window is the half-open span running from the instant a batch went on line up to, but not including, the instant its hold expires; the expiry instant itself is already outside the window. Pickup windows, price-file effective intervals, certification validity intervals, slicer occupancy intervals and markdown windows all follow the same convention: the lower bound is inclusive and the upper bound is exclusive. Where a rule below says "closed", it means the logical clock has reached or passed the exclusive upper bound.

### 2.6. Store Posture as the Admission Gate

A `Store` carries a derived `posture` drawn from three values: `OPEN`, `RESTRICTED` and `HALT`. Posture is not set directly by clients; it is computed from the store's own counters and flags, and it is recomputed on any change to the store's protection index, `certified_slicer_operator_count`, `case_on_hand_lbs`, `active_price_file_id` or `haccp_safety_flag`. Alongside `posture` the store exposes `posture_reason`, an enum token naming the single predicate that produced the current posture.

The predicates are evaluated in a fixed order, and the first one that fires decides both the posture and the reason token. If the store's `certified_slicer_operator_count` is zero, or if its `haccp_safety_flag` is true, the posture is `HALT` with reason `CERTIFICATION_TRIGGERED`. Otherwise, if the operator-controlled `posture_gate_flag` is true, the posture is `HALT` with reason `POSTURE_GATE_TRIGGERED`. Otherwise, if the store's `case_on_hand_lbs` exceeds its `deli_case_capacity_lbs`, or its protection index is at or below 30, or its `active_price_file_id` is null, the posture is `RESTRICTED`, with reason `INVENTORY_TRIGGERED` when the case is over capacity, `REVOCATION_TRIGGERED` when the protection index is at or below 30, and `NO_ACTIVE_PRICE_FILE` when no price file resolves. When none of those predicates fires, the posture is `OPEN` with reason `OK`. The protection-index boundary is inclusive on the restrictive side: a store at exactly 30 is `RESTRICTED`, and a store at 31 is `OPEN`.

Three postures, three different admission rules. A store in `HALT` accepts no fresh work at all: creating a sub ticket or a production batch is rejected with `ERR_POSTURE_HALT`. A store in `RESTRICTED` blocks new production batches — creation is rejected with `ERR_POSTURE_RESTRICTED` and starting a batch is likewise refused — but it deliberately does not block sub-ticket creation, so the counter can keep taking orders while the case is over capacity. A store in `OPEN` admits everything its other rules allow.

### 2.7. Protection and Diffusion Indices

The protection index is the store's single composite safety-and-fiscal health number, and it is the input to the `REVOCATION_TRIGGERED` posture predicate and to the `HALT` transition out of `HALT`. It begins at a base value of 100. Three counted sets subtract from it: each `Associate` in the store whose `status` is ACTIVE but who holds no `Certification` of type `SLICER_OPERATION` with `status` ACTIVE and an `expires_at` strictly after the logical clock subtracts 12; each `WasteRecord` in the store sitting in `DRAFT`, `MARKED_DOWN` or `DISCARDED` subtracts 6; each `SlicerAsset` in the store whose `sanitation_status` is `NEEDS_SANITATION` subtracts 4. The subtraction result is then clamped at a floor of zero, so the protection index is never negative. Certifications in `EXPIRED`, `REVOKED` or `RENEWED` contribute nothing to the counted set, and slicers in `CLEAN`, `IN_USE` or `SANITIZING` contribute nothing.

The diffusion index is derived from the clamped protection index: it is 100 minus the protection index, which means it can never be negative but is capped at 100. The clamp is applied before the diffusion index is derived, so a store whose raw subtraction would have driven the protection index below zero reports a protection index of 0 and a diffusion index of 100. Both numbers are integer-valued and are surfaced on the store's posture report.

### 2.8. Certified Staffing and the Certification Ledger

Certifications are the store's staffing credentials, and they gate slicer operation, allergen management and platter planning independently of an associate's `primary_role`. A `Certification` carries a `cert_type` of `SLICER_OPERATION`, `FOOD_HANDLING` or `ALLERGEN_MANAGEMENT`, an inclusive `issued_at`, an exclusive `expires_at`, and a status of `ACTIVE`, `EXPIRED`, `REVOKED` or `RENEWED`. An optional `deli_item_id` narrows the certification's allergen scope to a single catalog item; a null scope means the certification is store-wide.

The store's `certified_slicer_operator_count` counts associates in that store who hold at least one `SLICER_OPERATION` certification that is ACTIVE and whose `expires_at` is strictly after the logical clock. Expiry is not something a client does. When the logical clock reaches a certification's `expires_at`, the certification moves from `ACTIVE` to `EXPIRED` on the next production-day sweep, which recomputes the associate's `active_certification_count` and the store's `certified_slicer_operator_count` and then recomputes posture. That recomputation is the mechanism by which a lapse in staffing becomes a `HALT`: if the count reaches zero, the store halts.

Renewal is forward-only. Renewing an `EXPIRED` certification does not revive the lapsed row; it creates a successor `Certification` with `status` ACTIVE and a later `expires_at`, while the lapsed row takes `status` RENEWED. Reopening that successor recomputes its validity window from the logical clock and returns it to ACTIVE. Revoking an `ACTIVE` certification moves it to `REVOKED`, and revocation is constrained by a self-dealing rule: the `revoked_by_manager_id` supplied with the request must differ from the certification's `associate_id`, because a manager cannot revoke their own credential. Revocation recomputes the store's certified-slicer-operator count and induces the `HALT` transition whenever that count reaches zero.

Every `Certification` carries a derived `grace_reminder` flag, true when an ACTIVE certification expires within 72 hours of the logical clock. Associates additionally expose `active_certification_count`, the number of their certifications that are ACTIVE with an `expires_at` strictly after the logical clock, and `assigned_slicer_id`, the identifier of the `SlicerAsset` currently assigned to them, null when none is.

### 2.9. Precision, Rounding and Monetary Representation

Monetary quantities in this API are integer cents. No monetary field is a decimal string and no monetary field is a float; `unit_cost_cents`, `retail_price_per_lb_cents`, `discard_value_cents`, `handling_fee_cents`, `total_liability_cents`, `markdown_cents`, `deposit_cents`, `quote_total_cents`, `line_total_cents`, `total_price_cents`, `unit_price_cents`, `case_yield_cost_provisional_cents`, `case_yield_cost_final_cents` and `verified_waste_liability_cents` are all integers.

Where a calculation instructs rounding, it is round half up, and the scaffold pins where in the computation that rounding happens. The general rule is that each declared output is rounded once, at the point the calculation names, and component terms are not rounded in advance of it. Two calculations deliberately deviate by pinning per-step rounding: the sub-ticket line total rounds each line to whole cents before summing, and the waste-liability calculation rounds at its first and third steps. §3 names the rounding point for each calculation individually; where a calculation does not name one, no rounding is applied.

Weights are pounds and are decimal numbers, not integers; `net_weight_lbs`, `produced_lbs`, `planned_lbs`, `discard_lbs`, `markdown_sold_lbs` and `weight_lbs` all carry fractional pounds. Durations are whole minutes and are integers.

### 2.10. Optimistic Concurrency Control on Three Writes

Three write operations in this API require the client to present its last observed version of a parent resource, and they are the only operations that accept a version field. Starting a production batch requires `expected_store_version`, compared against the target store's current `version`. Verifying a waste record requires `expected_batch_version`, compared against the `version` of the `ProductionBatch` the record is drawn from. Confirming a bread supply order requires `expected_promotion_version`, compared against the `version` of the `Promotion` the order references. Each of these three fields is non-optional: a request that omits the relevant field is malformed, and there is no version-free path through these three operations.

In all three cases, the rule is stale-version rejection. If the supplied expected version does not match the parent's current `version` at the moment the request is evaluated, the write is rejected with `ERR_STALE_VERSION` and HTTP status 412, and no part of the operation takes effect. Each of the three parents is mutated by ordinary, legitimate work — starting a batch claims a slicer and recomputes the store's case weight, verification settles the batch's final case yield cost, and confirmation recomputes a promotion's required bread units — so a client that has not re-read the parent since its last observation is holding a superseded view, and the API refuses to act on it. A client that has advanced the parent's version through its own intervening legitimate operation must re-read before writing again.

No other endpoint in this API accepts a version field. In particular, catalog-item updates and slicer updates each carry an `expected_item_version` and an `expected_slicer_version` respectively, and those two fields are the only other version-bearing inputs in the API; they follow the same stale-version rule against their own parent. Every remaining modification endpoint is version-free and is guarded only by state and business rules.

### 2.11. Failure Order and Validation Priority

When a request could be rejected for several reasons at once, the API evaluates its checks in a fixed order and reports the first failure only. The order is a contract, not an implementation detail: it decides which of several plausible error identifiers a client sees, and tests exercise it deliberately.

Authentication comes first, then authorization, then existence. A missing or unrecognized header pair yields `ERR_UNAUTHENTICATED` before any resource is looked at, an unauthorized role yields `ERR_UNAUTHORIZED` before any business rule fires, and a missing store yields `ERR_STORE_NOT_FOUND` before the child addressed under it is examined. Existence of the addressed resource under that store follows, with `ERR_NOT_FOUND` for `id`-addressed resources and `ERR_DELI_ITEM_UNAVAILABLE` for catalog items that do not exist or are `DISCONTINUED`. The state-shape check comes next: an operation requested against a resource that is not in the state the operation requires yields `ERR_INVALID_STATE`.

Business safety checks then run before fiscal ones, with one deliberate inversion. The store-wide safety gates — the pickup-window freeze, the HACCP hold flag and the `HALT` posture gate — are evaluated ahead of all resource-level checks, so a halted store reports `ERR_HACCP_HOLD` or `ERR_POSTURE_HALT` rather than a slicer-specific complaint. The unverified-waste backlog check sits below those gates but above the resource-level checks it accompanies; on the batch-start path it fires before the slicer sanitation checks, so a store with three or more unverified waste records reports `ERR_UNVERIFIED_WASTE_BACKLOG` rather than `ERR_SLICER_NOT_SANITIZED`. The `RESTRICTED` posture gate applies to batch creation only, at a priority below the backlog check, and never to sub-ticket creation.

The full ordered check list, from the earliest check to the last, is: header presence and known role; role authorization; store existence and store/child scope agreement; resource existence; required state; the half-open pickup-window lockout; the `haccp_safety_flag` hold; `HALT` posture; the unverified-waste backlog; `RESTRICTED` posture on batch creation; associate certification; allergen changeover; slicer interval conflict; slicer sanitization state; a required `slicer_id`; certified staff at ticketing; a clean slicer for a slicer-required line; allergy coverage at completion; case-weight sufficiency; price-file currency; label currency; bread availability; pickup-window closure; catering lead time; pickup-bucket capacity; price-file overlap; price-file in-use; the promotion-withdrawal gate; the markdown-before-discard sequence; the half-open markdown window; segregation of duties; the non-empty ticket; sanitation-cycle dueness; cycle completion; the reopen limit; the label weight bound; the duplicate-request replay check; the OCC stale-version check; the completed-ticket slip basis; the slip lock; the queue-depth gate; and finally catalog-item availability for the ticket's lines. Each of these checks, its condition and its error identifier is described where the workflow it guards is described.

Two ordering notes matter in practice. The duplicate-request replay check on catering orders runs above the deeper state checks, so a replayed `request_id` surfaces as `ERR_DUPLICATE_REQUEST` and never as a state error. And the batch-start path additionally checks that the store's `posture` is `OPEN` as part of the transition preconditions rather than as a standalone gate, so starting a batch in a `RESTRICTED` store reports the posture rejection rather than a slicer complaint.

### 2.12. Hierarchical Consistency and Cascade Semantics

Every path that carries more than one identifier is validated left to right, and the first identifier that fails decides the error the caller sees. Where a store identifier appears in the path, the store must exist — a missing store reports `ERR_STORE_NOT_FOUND` — before the child addressed under it is examined at all. Where a resource identifier follows, that resource must exist and must belong to the store in scope; a resource that exists but sits under a different store is reported not as a permission problem but as `ERR_NOT_FOUND`, because scope disagreement is treated as non-existence. The same left-to-right discipline applies to the reverse-lookup reads nested under a catalog item, an associate or a certification, where the parent identifier is resolved first.

Most resources in this API are store-scoped and supply their store as a body field or a query filter rather than as a path segment, which is why the flat collections in §4 carry the store as `store_id` rather than nesting under a store path. A catalog item and a promotion are the two chain-level resources that carry no store identifier at all: both are chain-wide master data, and a store's relationship to them is derived rather than declared — a store's targeted promotion is resolved by week and its covered allergen set is derived from the items it produces.

Cascades in this system flow downward and are never reversed in place. When a store enters `HALT`, every non-terminal sub ticket in that store moves to `ABANDONED`, each abandoned ticket releases the bread units it was reserving from the store's bread supply orders, and each affected promotion is pushed to `DEGRADED` when its units-short count reaches zero. When an associate is suspended, the same cascade runs one level deeper: every certification the associate holds is revoked, the store's certified-slicer-operator count is recomputed, the store's `HALT` transition fires if that count reaches zero, and then the ticket, bread-reserve and promotion cascade runs as described. When a price file is superseded, every ISSUED label written against it is voided, and every sub ticket whose label was voided moves to `REMADE` — the reverse direction of the ordinary label life, expressed as a forward transition to a remake state rather than a reversion of the issued label.

Every one of these cascades counts as a mutation of each affected row. The server refreshes `updated_at` and increments `version` on every row it touches, including rows the client never named in its request.

## 3. Business Logic & Workflows

### 3.1. Planning the Production Day

The deli day begins with a catalog and a plan. The store itself is provisioned first, with a chain-unique `store_number` and a display `name` as its human identity and three physical capacity figures that drive the rest of the day: `deli_case_capacity_lbs` sets the refrigerated case capacity that decides the `INVENTORY_TRIGGERED` posture predicate, `hot_bar_capacity_lbs` sets the hot bar's holding capacity, and `sub_station_count` records how many made-to-order sub stations are staffed. A new store is provisioned at `posture` `OPEN` and `posture_reason` `OK`, with `case_on_hand_lbs` at 0, its `ops_run_index` production-day counter at 0, and its `version` at 1.

A `DeliItem` is the catalog row that defines what can be produced: its `sku` and `name` identify it, its `category` places it in one of `HOT_BAR`, `COLD_CUT`, `ROTISSERIE`, `SUB`, `BREAD` or `CATERING_PLATTER`, its `unit_cost_cents` and `retail_price_per_lb_cents` carry its economics in integer cents, and its `case_life_minutes` and `markdown_window_minutes` define how long a batch of it may sit and how long before expiry it may be marked down. Its `allergen_flags` list is a subset of `MILK`, `WHEAT`, `SOY`, `EGG`, `FISH` or `SESAME` and may be empty. Its `slicer_required` flag says whether producing it must occupy a slicer. A platter item contributes `servings_per_platter` servings per unit, defaulting to 12. A sub item names the `bread_deli_item_id` it is served on, and that referenced row must itself carry `category` `BREAD`; non-sub items leave the field null. Items carry a `status` of `ACTIVE` or `DISCONTINUED`, and a referenced item that is missing or discontinued blocks the ticket or batch that named it with `ERR_DELI_ITEM_UNAVAILABLE`. Item economics and case life may be revised later, and every revision recomputes any derived store field that reads the item. Reading the catalog back is a filtered operation: a caller may narrow the listing to a single `category`, to the subs built on one parent through the `bread_deli_item_id` filter, or to the withdrawn rows by setting `include_discontinued`, since discontinued items are suppressed from the listing by default.

A `ProductionBatch` is a planned run against one item in one store. It is created with a `batch_code` that is unique within its store, a `planned_lbs` weight that must be positive, and the `produced_by_associate_id` of the associate who will run it; it may optionally name a `slicer_id`, a `rework_of_batch_id`, and a `temperature_breach` flag defaulting to false; the producer named by `produced_by_associate_id` and any named `slicer_id` or `rework_of_batch_id` must belong to the same store as the batch, and a mismatch is reported as `ERR_NOT_FOUND`. The hold window a batch will occupy is only well formed when the item's `case_life_minutes` is strictly greater than its `markdown_window_minutes`: an item whose case life is less than or equal to its markdown window would open a window before the batch existed, and a batch planned against such an item is refused with `ERR_BATCH_WINDOW_INVALID`. Two state dimensions run in parallel on a batch and never cross-update each other. The `production_status` dimension reads `PLANNED`, `IN_PRODUCTION` or `ON_LINE`. The `hold_status` dimension reads `HOLDING`, `MARKED_DOWN` or `DISCARDED`. A fresh batch starts at `PLANNED` on the first dimension and `HOLDING` on the second, with `produced_lbs` at 0.

Planning a batch is gated by the store. A store in `RESTRICTED` refuses the creation with `ERR_POSTURE_RESTRICTED`, and a store in `HALT` refuses it with `ERR_POSTURE_HALT`. Separately, a store already carrying three or more waste records awaiting verification refuses new batches and refuses to start existing ones with `ERR_UNVERIFIED_WASTE_BACKLOG`: the fiscal backlog is allowed to apply brake pressure to a production line that is not keeping current on its paperwork. Every line's `deli_item_id` must name an existing ACTIVE item; a discontinued item is refused with `ERR_DELI_ITEM_UNAVAILABLE`.

Starting a planned batch is where the slicer enters the story. The transition from `PLANNED` to `IN_PRODUCTION`. Starting a planned batch advances a batch from `PLANNED` to `IN_PRODUCTION` and is refused with `ERR_INVALID_STATE` unless the batch is currently `PLANNED`. Beyond that, the operation must present the store's last observed `version` as `expected_store_version`, and a mismatch rejects the whole start with `ERR_STALE_VERSION` at HTTP 412, because the start claims a slicer and recomputes the case weight and therefore supersedes the store state the client was holding. For an item whose `slicer_required` flag is true, a `slicer_id` must be named or the request fails with `ERR_SLICER_REQUIRED`; the named `produced_by_associate_id` must hold a `SLICER_OPERATION` certification that is ACTIVE with an `expires_at` strictly after the logical clock, or the start is refused with `ERR_ASSOCIATE_NOT_CERTIFIED`; the slicer's `sanitation_status` must be `CLEAN` — or `NEEDS_SANITATION` with a sanitation cycle already due — because a slicer still `SANITIZING` cannot be claimed, and either failure yields `ERR_SLICER_NOT_SANITIZED`; the slicer's allergen profile must not introduce any allergen absent from the item's own declared set, or the start is refused with `ERR_ALLERGEN_CHANGEOVER_REQUIRED`; and the slicer must not already be committed anywhere in the half-open interval running from the logical clock to the clock plus the item's `case_life_minutes`, where the commitment set is the asset's non-aborted sanitation cycles together with every batch currently `IN_PRODUCTION` on that asset, or the start is refused with `ERR_SLICER_WINDOW_CONFLICT`. A successful start sets the slicer's `sanitation_status` to `IN_USE`, records the batch's item on the slicer as its `assigned_deli_item_id`, recomputes the store's `case_on_hand_lbs`, recomputes `posture`, and increments the store's `version` by one.

Because the start path is heavily checked, its ordering matters. The store-level gates run before the slicer-level ones, and within the slicer-level group the certification check, the allergen changeover check, the interval conflict check and the sanitization check run in that order.

Completing a batch advances it from `IN_PRODUCTION` to `ON_LINE` and accepts a `produced_lbs` figure, which must be greater than zero — a zero or negative weight is rejected with `ERR_INVALID_REQUEST`. On success the batch's `produced_at` is stamped from the logical clock and its `hold_expires_at` is computed as the produced instant plus the item's `case_life_minutes`. Three fields are recomputed at this moment: `case_yield_cost_provisional_cents` and `case_yield_cost_final_cents`, both from the dual-variant case-yield calculation described in §3.3 — both carrying the same pounds-based figure at this instant, because no waste record for the batch has yet reached `VERIFIED` and the final variant's two further terms are therefore both zero — and the store's `case_on_hand_lbs`. The slicer is left needing attention: its `sanitation_status` moves to `NEEDS_SANITATION`, its `last_sliced_deli_item_id` records the item just sliced, and its `cuts_since_sanitation` counter is incremented by the produced weight in pounds divided by five, rounded up to a whole number of cuts. Completing also clears the slicer's `assigned_deli_item_id`. The store's `version` is incremented.

Completion is also where allergen changeover has its teeth. If the completed batch's item carries an allergen set different from the set of the item the slicer last sliced, the changeover requirement makes every queued ticket in that allergen set un-buildable, each such ticket moves to `BREAD_HOLD`, and each affected promotion is pushed to `DEGRADED` when its units-short count reaches zero. The changeover is cleared by the sanitation workflow described in §3.6, not by the completion itself.

Marking a batch down moves it from `HOLDING` to `MARKED_DOWN` on the hold dimension and is only legal while the batch is `ON_LINE` on the production dimension and the logical clock falls inside the batch's markdown window. That window is half-open and runs from the hold expiry minus the item's `markdown_window_minutes` up to, but not including, the hold expiry; a markdown requested before the window opens or at or after the hold expiry fails with `ERR_MARKDOWN_WINDOW_CLOSED`. Two further rules apply. First, a batch that already has a waste record in `DRAFT` or `MARKED_DOWN` cannot be marked down again — the attempt fails with `ERR_WASTE_SEQUENCE_VIOLATION`, because opening a second concurrent waste record for one batch would fork the liability ledger. Second, the `recorded_by_associate_id`, which is optional and recorded on the synthesized record as its `markdown_by_associate_id`, must differ from the batch's `produced_by_associate_id`; the same person cannot both produce the batch and mark it down, and a violation reports `ERR_SEGREGATION_OF_DUTIES`. A successful markdown also synthesizes a `DRAFT` waste record against the batch, carrying the `HOLD_EXPIRED` reason and the recorded marker, accumulates `markdown_sold_lbs` and `markdown_cents` on the batch and recomputes the store's posture.

Rework is forward-only. Reworking a batch is legal only when that batch's `hold_status` is already `DISCARDED`; any other state yields `ERR_INVALID_STATE`, and the `rework_of_batch_id` supplied must reference a batch whose `hold_status` is `DISCARDED`. The operation does not revive the discarded row. It creates a successor `ProductionBatch` whose `rework_of_batch_id` names the discarded predecessor, whose `production_status` starts at `PLANNED`, and whose `hold_status` starts at `HOLDING`; the request supplies the successor's own `batch_code`, `planned_lbs`, `produced_by_associate_id` and optional `slicer_id`, each subject to the same store-scope and uniqueness rules as a fresh batch. The discarded row keeps its `DISCARDED` status forever, which means the rework loop is an induced cycle running from a batch through its waste record and back to a new batch, never a state reversal.

The production day itself is closed by a store-level sweep. Incrementing the store's `ops_run_index` production-day counter by one and stamping the current logical clock as the store's `logical_clock_at_last_run` are the two bookkeeping effects; the substantive ones are that every batch whose `hold_status` is `HOLDING` or `MARKED_DOWN` and whose half-open hold window has closed moves to `DISCARDED`, every certification whose `expires_at` has passed moves to `EXPIRED`, every bread supply order eligible for closeout moves to `RECONCILED`, and the store's posture, posture reason and derived counters are recomputed and its version incremented. The same sweep is also available chain-wide, where it advances the run index for every store in scope; supplying a store filter narrows it to one store, and omitting the filter applies it to the whole chain. The chain-wide form returns the array of the stores it swept. A batch that already has a verified waste record is left alone by the sweep; its hold dimension simply self-loops at `DISCARDED` as a no-op.

### 3.2. Slicer Custody, Sanitation and Allergen Changeover

A `SlicerAsset` is a `Store`-scoped piece of equipment with a cyclic sanitation life. It carries a store-unique `asset_tag`, an optional `assigned_deli_item_id` recording the item it is currently reserved for, an optional `last_sliced_deli_item_id` recording what it actually last sliced, and an optional `assigned_operator_id` naming the associate certified to operate it. Its `sanitation_cycle_limit` is the cut count at which a routine cycle becomes mandatory and defaults to 25. Its `sanitation_status` cycles through `CLEAN`, `IN_USE`, `NEEDS_SANITATION` and `SANITIZING`; its derived `cuts_since_sanitation` is a monotone cut counter reset only by a completed cycle; its derived `in_use_minutes` is a whole-minute counter that is zeroed by a completed cycle and not otherwise advanced, so an asset read back between sanitation events reports zero; its `last_sanitized_at` records the instant the asset last entered `CLEAN`, which for a freshly registered asset is the registration instant itself; and its derived `open_sanitation_cycle_id` names the single open `SanitationCycle` on the asset, or null when none is open.

Occupying a slicer happens through a batch start and moves the asset from `CLEAN` to `IN_USE`. That transition requires the asset to be `CLEAN` at the moment of the claim, and it requires the asset's `assigned_operator_id` to reference an associate holding a non-expired `SLICER_OPERATION` certification. While a slicer is being sanitized it cannot be claimed a second time. Completing a batch moves the asset from `IN_USE` to `NEEDS_SANITATION`, adds the batch's cut count to `cuts_since_sanitation`, adds the batch's slicing minutes to `in_use_minutes`, and records the item just sliced as `last_sliced_deli_item_id`.

A sanitation cycle is opened on a slicer whose `sanitation_status` is `NEEDS_SANITATION`, `CLEAN` or `SANITIZING`, in one of three `cycle_type` values, and each type has its own dueness rule. A `ROUTINE` cycle is due when the slicer's `cuts_since_sanitation` is greater than or equal to its `sanitation_cycle_limit` — the threshold is inclusive, so a slicer sitting at exactly its limit is due. A `TIMED` cycle is due when the slicer's `in_use_minutes` is greater than or equal to three times its `sanitation_cycle_limit`. An `ALLERGEN_CHANGEOVER` cycle is always permitted when allergen sets diverge, and it carries its own precondition instead of a threshold: the `allergen_cleared_from_item_id` supplied must be non-null, and that item's `allergen_flags` must be a proper subset of the `allergen_flags` belonging to the slicer's `last_sliced_deli_item_id`. Requesting a routine or timed cycle before it is due fails with `ERR_SANITATION_CYCLE_NOT_DUE`, and requesting any cycle type other than `ALLERGEN_CHANGEOVER` when the next batch's item allergen set diverges from what the slicer last sliced fails with `ERR_ALLERGEN_CHANGEOVER_REQUIRED` as well. A slicer may hold at most one open cycle at a time: opening a second cycle while one is open fails with `ERR_SLICER_WINDOW_CONFLICT`.

Opening a cycle creates a `SanitationCycle` in status `OPEN`, records the store and the slicer it belongs to, stamps its `started_at` from the logical clock, moves the slicer's `sanitation_status` to `SANITIZING`, and commits the asset for the half-open interval running from the clock to the clock plus the cycle's `cycle_minutes`, which defaults to 10 and must be at least 1. The `buffer_minutes` field, defaulting to 5 and never negative, records a quarantine buffer appended to that interval before the asset may re-enter `IN_USE`, and is recorded on the cycle without changing the cycle's own `cycle_minutes`. A cycle optionally names the `production_batch_id` whose completion forced it and the `allergen_cleared_from_item_id` whose residue it clears; the `verified_by_associate_id` is supplied at completion rather than at opening.

Completing an open cycle is refused with `ERR_CYCLE_NOT_COMPLETE` until the logical clock has reached the cycle's `started_at` plus its `cycle_minutes`. For an `ALLERGEN_CHANGEOVER` cycle the `verified_by_associate_id` supplied at completion must hold an `ALLERGEN_MANAGEMENT` certification that is ACTIVE; without it the completion fails with `ERR_ASSOCIATE_NOT_CERTIFIED`. A successful completion moves the cycle to `COMPLETE` and stamps its `completed_at`, moves the slicer's `sanitation_status` back to `CLEAN`, resets both `cuts_since_sanitation` and `in_use_minutes` to zero, stamps `last_sanitized_at`, and recomputes certification counters.

An open cycle may also be aborted by a manager-level caller supplying a `reason`, which moves it to `ABORTED`, clears the slicer's `open_sanitation_cycle_id`, and returns the slicer to `NEEDS_SANITATION` without any counter reset — an aborted cycle earns no credit, so the asset still needs the work. A completed cycle may be reopened, which is a manager-level reversal of a sanitation claim: the manager asserts the cycle's evidence is invalid, the cycle's status moves to `ABORTED` with its reopen count incremented, the slicer returns to `NEEDS_SANITATION`, and critically `cuts_since_sanitation` is not reset. Reopening requires the slicer to currently be `CLEAN`; anything else yields `ERR_INVALID_STATE`. A slicer may be reopened at most twice per production day, the third attempt fails with `ERR_REOPEN_LIMIT_EXCEEDED`, and the reopen request carries an optional `reason` that is recorded but whose vocabulary is not constrained. Because the aborted cycle keeps its `ABORTED` status permanently, a second attempt is made by opening a fresh cycle on the same slicer rather than by reviving the aborted one; the fresh cycle's opening is permitted only when the previous attempt is `ABORTED` and no other cycle on that slicer is open. A slicer whose most recent cycle is `ABORTED` and which is sitting at `NEEDS_SANITATION` therefore admits a fresh routine or timed cycle without re-testing that cycle type's dueness threshold — the aborted attempt's own consumption of the threshold is not re-charged — while the at-most-one-open-cycle rule continues to apply unchanged.

### 3.3. Case Yield Cost and the Waste Liability Ledger

Two cost figures ride on every batch, and they are the same calculation asked under two different conditions. The first is a pounds-based cost built from four components. The batch's produced weight in pounds multiplied by the item's `unit_cost_cents` gives the raw product cost. To that is added a retail labor load of 45 cents, but only when the batch's `production_status` is `ON_LINE` — a batch still in production carries no labor load. When the batch has a slicer, a slicer fee is added: the slicer's `cuts_since_sanitation` divided by 20, rounded down to a whole number of fee units, multiplied by 6 cents per unit. When the batch has no slicer, no slicer fee is added. That subtotal is the batch's pounds-based cost.

The provisional figure, `case_yield_cost_provisional_cents`, is the subtotal reduced by a waste-recovery credit: 0.70 multiplied by the batch's `discard_lbs` multiplied by the item's `unit_cost_cents`, subtracted from the subtotal, with the whole result rounded half up to two decimal places. It is reported while no verified waste record exists for the batch, and it deliberately excludes both the handling fee and the net markdown recovery.

The final figure, `case_yield_cost_final_cents`, is reported once at least one waste record for the batch has reached `VERIFIED`, and it adds two further terms to the same base — the base being the pounds-based subtotal less the recovery credit already reported as the batch's `case_yield_cost_provisional_cents`, and not a base re-derived from any `discard_lbs` that verification itself recomputes. The first addition is the sum of `handling_fee_cents` over every waste record for this batch that has reached `VERIFIED`, rounded half up to two decimal places. The second addition is 0.50 multiplied by the item's `retail_price_per_lb_cents` multiplied by the batch's `markdown_sold_lbs`, representing the net markdown recovery. The whole of the final figure is rounded half up to two decimal places, and the rounding is applied once to each output rather than per component. Records that have been `DISCARDED` but not yet verified contribute nothing to the final variant, which is why verification is the moment the final cost settles.

Waste itself follows a strict forward sequence: `DRAFT`, then `MARKED_DOWN`, then `DISCARDED`, then `VERIFIED`. A `WasteRecord` is opened against a `ProductionBatch` with the `production_batch_id` it is drawn from, the `markdown_by_associate_id` who will apply the markdown, and a `reason` drawn from `HOLD_EXPIRED`, `TEMPERATURE_BREACH`, `ALLERGEN_CONTAMINATION`, `QUALITY` or `UNCLAIMED_PLATTER`. Opening a record places it in `DRAFT` and recomputes the store's pending-verification count. A record may also be synthesized in `DRAFT` as a side effect of marking a batch down. Opening a second concurrent record against a batch that already holds one in `DRAFT` or `MARKED_DOWN` is refused with `ERR_MARKDOWN_REQUIRED_BEFORE_DISCARD`, because a second open record for one batch is not a state the sequence can represent.

Recording the markdown leg moves the record from `DRAFT` to `MARKED_DOWN` and is available only when the parent batch's `hold_status` is already `MARKED_DOWN`; otherwise the request fails with `ERR_MARKDOWN_REQUIRED_BEFORE_DISCARD`. It follows the same half-open markdown window as the batch-level markdown, failing with `ERR_MARKDOWN_WINDOW_CLOSED` outside it, and it carries the same segregation rule — the `markdown_by_associate_id` must differ from the batch's `produced_by_associate_id`, or the request fails with `ERR_SEGREGATION_OF_DUTIES`. A successful markdown records `markdown_sold_lbs` and `markdown_cents` on the record, stamps its `markdown_recorded_at` from the logical clock, and recomputes those same two fields on the parent batch.

Discarding is the step that converts pounds into liability, and it has two legal origins with different preconditions. A record may be discarded directly from `DRAFT` when the parent batch's `hold_status` is `HOLDING` and either the item's `markdown_window_minutes` is zero or the half-open markdown window has already closed at the logical clock; if the markdown window is still open at that moment the direct discard is refused with `ERR_MARKDOWN_REQUIRED_BEFORE_DISCARD`, because a discardable batch must first have been offered at markdown price. A record may also be discarded from `MARKED_DOWN`, in which case the parent batch's `hold_status` must be either `HOLDING` or `MARKED_DOWN`; any other state yields `ERR_INVALID_STATE`, and this is precisely because a batch already discarded cannot be marked down, that being the reverse of the mandated sequence. The discard request supplies a `discard_lbs` figure, which must be greater than zero.

Discard computes the liability in a pinned evaluation order, because the tier base reads a value the calculation itself produces for earlier records and the ordering is what removes the circularity. First, `discard_value_cents` is the discarded pounds multiplied by the item's `unit_cost_cents`, rounded half up to whole cents. Second, a prior-liability base is accumulated over every other waste record in the same store whose creation instant is strictly before this record's creation instant — records sharing the identical creation instant are excluded — and whose status is `VERIFIED` or one of `DISCARDED` and `MARKED_DOWN`; records whose `reason` is `UNCLAIMED_PLATTER` are excluded from this accumulation entirely.

Third, a discounted base is computed as 0.70 multiplied by `discard_value_cents`, plus 0.30 multiplied by that prior-liability base, rounded half up to whole cents. Fourth, the `handling_fee_cents` is chosen from that discounted base by a three-tier band. A discounted base below 5000 cents takes a fee of 0 cents. A discounted base at or above 5000 cents and below 15000 cents takes a fee of 250 cents. A discounted base at or above 15000 cents takes a fee of 600 cents. No rounding is applied at the fourth step. Fifth, `total_liability_cents` is `discard_value_cents` plus `handling_fee_cents`, with no rounding, and the record's `discarded_at` is stamped from the logical clock. A separate `markdown_cents` figure is computed as `markdown_sold_lbs` multiplied by the item's `retail_price_per_lb_cents`, rounded half up to whole cents. All of this is recomputed whenever a discard happens, and the parent batch's `hold_status` moves to `DISCARDED` as a direct consequence.

Verification closes the loop and is where the three-person rule lives. Verifying requires the `verifier_associate_id` supplied to differ both from the batch's `produced_by_associate_id` and from the record's `markdown_by_associate_id`; a verifier who was either the producer or the marker-down fails with `ERR_SEGREGATION_OF_DUTIES`. The `verified_by_certification_id` must additionally reference a `FOOD_HANDLING` certification that is ACTIVE and belongs to the stated verifier, or the request fails with `ERR_ASSOCIATE_NOT_CERTIFIED`. Because the verification settles the batch's final case yield cost — a value the client may have been quoting — the request must carry `expected_batch_version` matching the batch's current `version`, and a mismatch is rejected with `ERR_STALE_VERSION` at 412.

A successful verification moves the record to `VERIFIED`, recomputes the parent batch's `discard_lbs` and its `case_yield_cost_final_cents`, recomputes the store's waste-liability fields and its pending-verification count, and increments the store's verified-liability total. Unverifying returns a verified record to `DISCARDED` under review and decrements the store's verified-liability total; it clears the record's verifier and certification references, and it does not sit on the verified row, so a re-verification travels back through `DISCARDED` rather than restoring the old verified state in place. A record that never reached a verified discard may be voided instead, from `DRAFT` only when no discard has yet been recorded and from `MARKED_DOWN` freely, taking it to `VOIDED` and recomputing the store's pending-verification count.

Two store-level aggregations read the ledger. The store's total waste liability sums `total_liability_cents` over every waste record in the store whose status is `DISCARDED` or `VERIFIED`, whose creation instant is strictly before the logical clock — records created at exactly the clock instant are excluded — and whose `reason` is not `UNCLAIMED_PLATTER`. The store's `verified_waste_liability_cents` is the same sum restricted to records whose status is `VERIFIED`. Records in `DRAFT` or `VOIDED` contribute nothing to either figure. The exclusion of unclaimed-platter rows is what keeps a cancelled catering order from inflating the deli's waste liability, and the strict creation-instant bound is what keeps a record from counting toward liability in the same instant it was created.

Catering waste enters this ledger from one direction only. Cancelling a catered platter after it has been marked ready synthesizes an unclaimed-platter waste record against the platter's batch; because that record's `reason` is `UNCLAIMED_PLATTER`, it is excluded from both store-level liability sums by construction. The liability is real, but it is not deli waste liability, and the API says so structurally rather than by a special case.

### 3.4. The Digital Sub Queue, Ticketing and Promised Times

A `SubTicket` is a made-to-order sub order taken at the counter, through the digital app, or by phone, and it is the store's most active resource. It is created against a store with the `deli_item_id` being ordered, the `bread_deli_item_id` it is served on, and an `order_channel` of `IN_STORE`, `DIGITAL` or `PHONE`. Digital orders may carry a `placed_by_customer_ref`, an opaque app reference that is never an entity identifier. The ticket's `lines` array is the substance of the order: an ordered array of objects each carrying a `deli_item_id` and a `half_lb_units` count, where the array position is the client-supplied `line_sequence_number` order. A ticket must carry at least one line and every line's `half_lb_units` must be at least 1; an empty ticket is rejected with `ERR_EMPTY_CART`. A ticket with zero lines is refused at creation, and a ticket that survives creation has a derived `weight_lbs` equal to the sum over its lines of `half_lb_units` multiplied by 0.5.

A fresh ticket starts on two parallel dimensions. Its fulfillment dimension reads `QUEUED`, `TICKETED`, `IN_PROGRESS`, `COMPLETED`, `PICKED_UP`, `REMADE` or `ABANDONED`, and its bread dimension reads `QUEUED` or `BREAD_HOLD`. Creation places the ticket at `QUEUED` on both, and assigns a per-store `creation_sequence` and a customer-facing `ticket_number` equal to it, monotonically increasing within the store. That `creation_sequence` is the tie-break for every ordering the API performs over tickets.

Ticketing is the act of committing the store to the order, and it moves the fulfillment dimension from `QUEUED` to `TICKETED`. It is refused when the store's `posture` is `HALT`, with `ERR_POSTURE_RESTRICTED`; note that `RESTRICTED` posture does not block ticketing, only `HALT` does. It is refused when the store's `certified_slicer_operator_count` is below 1, with `ERR_NO_CERTIFIED_STAFF`, because there is nobody eligible to slice for it. It is refused when any line names an item whose `slicer_required` flag is true and the store has no `CLEAN` slicer at all, with `ERR_NO_CLEAN_SLICER`. It is refused while the ticket's bread dimension sits at `BREAD_HOLD`, with `ERR_BREAD_UNAVAILABLE`. And it is refused when the store's eligible queue already holds eight or more gate-eligible tickets, with `ERR_QUEUE_DEPTH_BREACH` — the gate counts only tickets already at `TICKETED` or `IN_PROGRESS`, so a store with a deep backlog of unticketed orders can still only hold eight live ones. A successful ticketing assigns the `promised_at` instant, described below, and recomputes the queue position of every non-terminal ticket in the store.

Between `TICKETED` and `IN_PROGRESS` the ticket moves when the assigned station begins the build, which happens automatically once the ticket's item prerequisites hold — in particular a `CLEAN` slicer for slicer-required lines. The slicer used enters `IN_USE` at that point. Because a ticket in `QUEUED` still reserves nothing, a ticket in that state whose item prerequisites already hold is not yet advanced by this rule; the transition from `TICKETED` to `IN_PROGRESS` is applied when the ticket is subsequently read or completed, and a completion presented against a `TICKETED` ticket therefore advances it to `IN_PROGRESS` before the completion is evaluated rather than refusing it as a state error.

The promised time is the store's public commitment and it is computed from the work the ticket implies. Preparation minutes are the sum of two terms. The first is 12 minutes multiplied by the number of distinct production batches the ticket's lines require. The second is the ticket's `weight_lbs` divided by 0.5, rounded up to a whole number of half-pound units, multiplied by 1 minute per half-pound unit. So a ticket needing two batches and weighing 2.5 pounds takes 24 minutes for the batches plus 5 minutes for the weight, or 29 minutes. The `promised_at` instant is the logical clock at the moment of ticketing plus those preparation minutes. `lateness_minutes` is derived once the ticket completes: it is the number of whole minutes by which `completed_at` exceeds `promised_at`, floored to a whole minute and clamped at a minimum of zero, so an early completion records zero rather than a negative figure.

Lateness then feeds two store-level rules that guard the promise's credibility. The first is the completed-ticket slip basis: every ticket the store already holds at `COMPLETED` or `PICKED_UP` contributes its `lateness_minutes`, and the basis is the greatest figure among them; the store's newest completed lateness is that same figure. The identifier `ERR_NO_COMPLETED_TICKET_YET` is declared in §5 for the closed-basis condition, but no completion is refused with it — the basis being closed is expressed through the bound the slip lock applies, not through a refusal of its own. On a store's first completion the check passes vacuously, because the set of prior completions is empty and the store's newest completed lateness reads as zero. The second is the slip lock: once any ticket in the store has completed late by some number of minutes, every later completion in that store must land within that same number of minutes of its own `promised_at`, and a violation is refused with `ERR_SLIP_LOCK_VIOLATED`. The bound is the current basis, so it moves only as later completions raise it; a store whose basis is still zero admits a completion at any lateness and lets that late completion set the basis. Taken together, the two rules mean a store is allowed exactly one late completion, and the grace it grants is the grace it must then keep.

Completing a ticket moves it from `IN_PROGRESS` to `COMPLETED` and is the ticket's pricing moment. The request supplies a `net_weight_lbs` figure that will be printed on the label, and that figure is subject to the same scale lock as a standalone label: a weight that is zero, negative or above 10 pounds is refused with `ERR_LABEL_WEIGHT_EXCEEDED` before any of the completion checks below run. Completion is refused with `ERR_PRICE_FILE_STALE` when the store's `active_price_file_id` is null or when the resolved file's interval does not contain the logical clock. It is refused with `ERR_BREAD_UNAVAILABLE` when the ticket's bread dimension is not `QUEUED`. It is refused with `ERR_SHELF_OUT` when the store's `case_on_hand_lbs` cannot cover every line's required weight, evaluated per line as half the ticket's per-line poundage. And it is refused with `ERR_ALLERGY_HOLD_ACTIVE` when the completing associate's `allergy_set` is not a superset of every line's `allergen_flags`; this is the allergen-coverage rule, evaluated against the acting `Associate` rather than against any store-level set, which is why a clerk cleared only for `MILK` and `WHEAT` cannot complete a ticket whose lines carry `SESAME`. The rule reads the acting associate only when the acting role is one of the three entity-backed roles; an opaque acting role such as `ScaleOperator` carries no `allergy_set` and is therefore not screened by it.

A successful completion stamps `completed_at`, recomputes `lateness_minutes`, recomputes the ticket's `line_total_cents`, and synthesizes a `Label` with `subject_type` `SUB_TICKET` and status `ISSUED`, storing its identifier on the ticket as `label_id` and resolving the store's ACTIVE price file onto the label as its `price_file_id`. The label carries the `net_weight_lbs` from the request, a `unit_price_cents` resolved from the completed build's own line items — the `retail_price_per_lb_cents` of the item named by the ticket's first line, so a SUB ticket whose top-level catalog row is the sub shell still prices from its sliced contents — and a derived `total_price_cents` equal to the net weight in pounds multiplied by the unit price, rounded half up to a whole cent. The resolved price file's `synced_scale_count` is recomputed, and the queue positions of the store's remaining eligible tickets are recomputed.

The ticket's own price is a separate calculation from the label's, and it has a different rounding discipline. The promotion uplift applied to the ticket is the `forecast_uplift_pct` of the store's targeted promotion when the store has one, and zero otherwise. The per-pound price is the `retail_price_per_lb_cents` of the item the line's entries name, so two lines naming different items are priced independently of the ticket's own top-level item; the ACTIVE price file gates freshness but does not supply the price. The computation walks each distinct `line_sequence_number` present in the ticket's lines. For each such line, the line's poundage is the sum of `half_lb_units` over every entry sharing that line number, multiplied by 0.5. The line's cost is that poundage multiplied by the per-pound price, rounded half up to zero decimal places — that is, to a whole cent. The line's promotional discount is that whole-cent line cost multiplied by the promotion uplift, again rounded half up to a whole cent. The line's total is the line cost minus the line discount. The ticket's `line_total_cents` is then the plain integer sum of the line totals. The rounding order here is pinned deliberately: each line is rounded to cents before the sum, and summing first and rounding afterwards would diverge by up to one cent per additional line.

Picking a ticket up moves it from `COMPLETED` to `PICKED_UP` and is refused with `ERR_INVALID_STATE` unless the ticket is currently `COMPLETED`, and refused with `ERR_LABEL_STALE` when the label issued for the ticket is no longer `ISSUED` — a voided label forces the ticket through a remake first rather than allowing a stale label to leave the counter. Abandoning a ticket moves it from `QUEUED` to `ABANDONED` and is refused with `ERR_INVALID_STATE` unless the ticket is currently `QUEUED`. Both terminal states release nothing further on their own, but abandonment releases the ticket's bread reserve as described in §3.5, and both recompute queue positions.

The derived queue is the store's live workload view. A ticket is gate-eligible when its fulfillment status is `TICKETED` or `IN_PROGRESS` and its bread status is `QUEUED` simultaneously. The eligible set is ranked by `promised_at` ascending, with `creation_sequence` ascending as the tie-break. A ticket's `queue_position` is its one-based rank in that ordering, or zero when it is not gate-eligible; tickets at `QUEUED`, `COMPLETED`, `PICKED_UP`, `REMADE` or `ABANDONED` all carry position zero, and so does any ticket whose bread dimension is `BREAD_HOLD`. The store's queue depth is the count of gate-eligible tickets, and it reads zero for an empty eligible set. The queue read returns the ranked tickets under an `ordered` key along with `queue_depth` and the ordered total, and it applies the ordinary `limit`/`offset` window to that ordered set while reporting the same ordered total as its count. A ticket awaiting a bread delivery is therefore invisible to the queue even though it is ticketed, which is intended: the counter should not see promises it cannot currently keep.

Remakes handle the case where a completed ticket's label is invalidated. When a label issued for a ticket is voided, the ticket's fulfillment dimension moves from `COMPLETED` to `REMADE`. This increments its `remake_count` by one, and the ticket returns to `QUEUED` through a fresh fulfillment cycle on the same row rather than as a new ticket. The remake carries its original `ticket_number` forward, so the customer's number does not change. A `REMADE` ticket must then be requeued explicitly, and only from `REMADE`; any other status yields `ERR_INVALID_STATE`, and the requeue re-enters the queue without issuing a new ticket number.

### 3.5. Weekly Promotions and the Bread Supply Chain

A weekly featured-sub promotion is a `Promotion` row that names the featured `deli_item_id`, a `promo_code` unique across the chain, a half-open promotional week running from an inclusive `week_start_date` to an exclusive `week_end_date`, a `forecast_uplift_pct` between 0 and 2 inclusive, and a `trailing_baseline_units` figure recording the featured sub's sales over the trailing 14-day window. It begins in `SCHEDULED` and can reach `ACTIVE`, `DEGRADED`, `SETTLED` or `CANCELLED`.

Activating a promotion requires the logical clock to fall inside its half-open week; activating outside it yields `ERR_INVALID_STATE`. Activation recomputes the promotion's `required_bread_units` under the provisional forecast described below and recomputes the store's `targeted_promo_id`. That store field names the ACTIVE promotion whose half-open week contains the logical clock, ranked by `week_start_date` ascending and then by creation instant ascending, and it is null when no promotion is ACTIVE. The field matters beyond bookkeeping: it is the uplift source for every sub ticket priced in that store, as described in §3.4.

Bread demand is a forecasting chain with two variants that differ in exactly one input. Under both variants the baseline is the promotion's `trailing_baseline_units`. The raw uplift is the promotion's `forecast_uplift_pct` under the provisional variant, and the smaller of that figure and a cap of 0.35 under the settled variant. Forecast units are the baseline multiplied by one plus the raw uplift, rounded half up to a whole number of units. Bread units are the forecast units plus the forecast units multiplied by a bread waste factor of 0.12, also rounded half up to a whole number. Finally, `required_bread_units` is the bread units divided by 12 units per case, rounded up to the next whole case, then multiplied back by 12 — so the figure is always a whole number of cases. Only the promotion's own baseline and uplift enter this calculation; no ticket or order data does, and promotions in `CANCELLED` are excluded from it. The provisional variant, written to `required_bread_units`, applies the full uplift and therefore over-orders bread for a promotion whose uplift sits above the settlement cap. The settled variant, written to `settled_bread_units` at settlement, caps the uplift at 0.35 first, so identical input data yields a smaller bread demand.

The promotion's `required_bread_units` is provisional while the week is live; `settled_bread_units` starts at zero and is stamped only at settlement. Between the two, the promotion's state responds to bread coverage. A promotion moves from `ACTIVE` to `DEGRADED` when its coverage shortfall is greater than half its `required_bread_units`. It stays ACTIVE for pricing purposes while DEGRADED — the featured price still applies — but the degradation is the store's signal that the bread commitment is in trouble. It returns to ACTIVE when the shortfall falls back to zero, which happens either on a bread confirmation or automatically when bread reserves are released by a ticket's abandonment, completion or pickup. Settlement requires the logical clock to have reached the promotion's `week_end_date`, and it requires that no bread supply order referencing the promotion sits in `SUBMITTED` or `CONFIRMED` — a promotion cannot settle while its bread commitments are still open. On settlement the promotion moves to `SETTLED` and `settled_bread_units` takes the settled variant of the demand calculation. A settled promotion may be reopened for revision, which clears `settled_bread_units` and recomputes `required_bread_units` provisionally, returning it to `ACTIVE`; it settles again permanently the second time. A promotion may be cancelled from `ACTIVE` or from `SETTLED`, and only when no bread supply order with status `SUBMITTED`, `CONFIRMED` or `DELIVERED` references it; the cancellation takes the promotion to `CANCELLED` and moves every bread supply order referencing it to `RECONCILED`.

Bread orders are the commitments that meet the forecast. A `BreadSupplyOrder` is created against a store with the `bread_deli_item_id` being ordered, the `promotion_id` whose forecast drives it, and a `committed_units` figure the bakery coordinator is willing to commit. It begins in `DRAFT` with its `required_units` copied from the promotion's provisional forecast, its `delivered_units` at zero, its `shortfall_units` recomputed, and a computed `submit_by_at` instant equal to the promotion's `week_start_date` minus 48 hours. Its `reserved_units` tracks the rolls this store's tickets are currently holding for that bread item, and its `unreserved_required_units` is `committed_units` minus `reserved_units`, clamped at a minimum of zero; `shortfall_units` is `required_units` minus `committed_units`, also clamped at a minimum of zero.

Submitting moves the order from `DRAFT` to `SUBMITTED`, copies `required_units` from the promotion's provisional forecast, and is refused with `ERR_LEAD_TIME_VIOLATED` if the logical clock has already reached `submit_by_at` — the 48-hour lead time is a hard wall, not a preference. It is also refused with `ERR_INVALID_STATE` when the promotion's provisional forecast leaves `required_units` at zero, because there is nothing to order. Confirming moves the order from `SUBMITTED` to `CONFIRMED` and requires `committed_units` to be at least eight tenths of `required_units`; a commit below that fraction is refused with `ERR_INVALID_STATE`. Confirmation recomputes `shortfall_units`, and if that figure is greater than zero the referenced promotion is pushed to `DEGRADED`. Confirmation is also one of the three OCC-guarded writes: it must carry `expected_promotion_version`, and a mismatch is rejected with `ERR_STALE_VERSION` at 412, because the confirmation recomputes the promotion's forecast and therefore supersedes the figure the client was holding.

Delivering moves the order from `CONFIRMED` to `DELIVERED`, recording the `delivered_units` figure supplied. When `delivered_units` is less than nine tenths of `required_units`, the order's post-delivery status is `SHORT` rather than `DELIVERED`, and the referenced promotion is pushed to `DEGRADED` by that shortfall. Delivery is also the release event for held tickets: every ticket in `BREAD_HOLD` whose bread item was delivered returns to `QUEUED` on its bread dimension, and the bread units those tickets reserve push each affected promotion to `DEGRADED` when its units-short count reaches zero. A delivery that is rejected at receiving may be reopened by a manager-level caller supplying a `reason`, which returns the order from `DELIVERED` to `SUBMITTED` for a second bakery commitment rather than reverting the delivered row, clearing its `delivered_units`; a `SHORT` order may likewise be reopened to `SUBMITTED`. Closeout moves eligible orders to `RECONCILED`, which is the order's terminal state: a `DELIVERED` order whose promotion week has passed with no open order remaining, or a `SHORT` order whose promotion has already reached `SETTLED` or `CANCELLED`.

Bread coverage is computed continuously, and its central figure is the units short. Reserved units are the number of tickets in the store, for this order's bread item, whose fulfillment status is `TICKETED` or `IN_PROGRESS`. The units-short figure is `required_units` minus `committed_units`, clamped at a minimum of zero, plus `reserved_units` minus `committed_units`, also clamped at a minimum of zero. The promotion is `DEGRADED` exactly when the units-short figure is greater than zero and back to `ACTIVE` when it is exactly zero. Tickets in `QUEUED`, `COMPLETED`, `PICKED_UP`, `REMADE` or `ABANDONED` reserve nothing — a completed ticket has already consumed its roll, and an abandoned or unmade one has not yet asked for it. The store's derived `available_bread_units` is the sum of `committed_units` over its delivered bread supply orders minus the units already reserved by tickets held on bread.

A ticket's bread dimension is the customer-visible face of this machinery. A ticket moves from `QUEUED` to `BREAD_HOLD` on its bread dimension automatically when a completed batch's item carries an allergen set diverging from the set the slicer last sliced, which is the allergen-changeover hold described in §3.1. Held tickets reserve no bread units, which is why a hold immediately improves the store's coverage picture. The dimension returns to `QUEUED` when a bread delivery covers the ticket's bread item.

### 3.6. Weight-Based Labeling and the Scale Price File

Every printed price in the deli rides on a `ScalePriceFile`. A price file is created for a store with a `file_label` unique within that store, a half-open effective interval running from an inclusive `effective_from` to an exclusive `effective_to`, and an `item_price_count` recording how many item prices it carries. It begins in `PENDING`, can move to `ACTIVE`, and from `ACTIVE` to `SUPERSEDED` when a successor takes over; it records an `activated_at` instant and a derived `synced_scale_count` counting the labels written against it, meaning those still at status `ISSUED`, so a label voided by a supersession retires its contribution to the counter.

A `Label` is the printed weight-and-price artifact. It carries the store that issued it, an optional `sub_ticket_id` when it was issued for a ticket and null for batch or platter labels, a derived `price_file_id` recording the ACTIVE file it resolved, a `subject_type` of `SUB_TICKET`, `PRODUCTION_BATCH` or `CATERING_PLATTER`, a polymorphic `subject_ref_id` naming the labelled subject — the entity named by `subject_type` — a `net_weight_lbs` that must be greater than zero, a `unit_price_cents` that the issuing operation supplies or resolves — a standalone label takes the figure from its own request, while a label issued as part of a workflow resolves it from the labelled subject's catalog `retail_price_per_lb_cents` — and a derived `total_price_cents` equal to the net weight multiplied by the unit price, rounded half up to a whole cent, and a `printed_at` instant — all three of `unit_price_cents`, `total_price_cents` and `printed_at`, along with the store and subject fields, are server-computed at issue time rather than echoed from the request. It records a status of `ISSUED` or `VOIDED`. A standalone label request supplies the weight and the unit price directly, and its `subject_type` must be one of the three declared values; an unrecognized value is a malformed request. It is refused with `ERR_LABEL_WEIGHT_EXCEEDED` when the weight is zero, negative, or above 10 pounds, and with `ERR_PRICE_FILE_STALE` when the store has no active price file at the logical clock; a negative unit price is likewise a malformed request. That weight bound is the scale-lock limit.

Resolving which file is active is a ranking problem rather than a lookup. The candidate set is every price file belonging to the store whose status is `ACTIVE` and whose half-open interval contains the logical clock, with `effective_from` inclusive and `effective_to` exclusive. Candidates are ranked by their `effective_from` descending, so the most recently started interval wins, and ties are broken by `activated_at` descending and then by creation instant ascending. The first element of that sort is the winner and is recorded on the store as `active_price_file_id`. When the candidate set is empty the store's `active_price_file_id` is null, every label-generating call returns `ERR_PRICE_FILE_STALE` at status 409, and the store's posture reason becomes `NO_ACTIVE_PRICE_FILE`, which as described in §2.6 drives the store to `RESTRICTED`. Price files in `PENDING` or `SUPERSEDED` are excluded from the candidate set entirely, even if their interval would otherwise contain the clock.

Activating a `PENDING` file moves it to `ACTIVE`, stamps `activated_at` from the logical clock, and supersedes the incumbent. The overlap rule is the gate: the requested file must not overlap an already-ACTIVE file for the same store on half-open intervals, or the activation is refused with `ERR_PRICE_FILE_OVERLAP`. Two shapes are exceptions. A re-price shape is permitted, where the new file's `effective_from` is strictly later than the incumbent's while its `effective_to` is identical — a mid-window re-price legitimately supersedes the incumbent. And abutting intervals are always permitted, meaning a new file whose `effective_from` equals the incumbent's `effective_to` is fine because the half-open intervals do not overlap. Superseding cascades: the previously ACTIVE file moves to `SUPERSEDED`, every `ISSUED` label written against it moves to `VOIDED`, every sub ticket whose label was voided moves to `REMADE`, the store's `active_price_file_id` is recomputed and the store's `version` is incremented. A completion or a standalone label issued in the same moment as a supersession is caught by the same cascade, which is the intended serialization point between pricing and printing. A completion that issues a fresh label against the just-superseded file is the case where the two directions meet: the cascade has already voided the older labels and forced their tickets to `REMADE`, while the newly issued label stands and is counted against the superseded file.

Withdrawing an `ACTIVE` file returns it to `PENDING` rather than to a dead end, and it is guarded twice. It is refused with `ERR_PRICE_FILE_IN_USE` when any `ISSUED` label references the file. It is refused with `ERR_PROMO_STATE_BLOCKS_FILE_WITHDRAWAL` when the associated promotion has not first been moved to `CANCELLED`. Reactivating a `SUPERSEDED` file also returns it through `PENDING` and then immediately into `ACTIVE` via the ordinary activation edge: this is permitted only when no price file is ACTIVE and containing the logical clock — the currently ACTIVE file is expired relative to the clock — and the returning file's effective interval contains the clock. That edge runs in full on reactivation, so any file still `ACTIVE` for the store is superseded by it, its `ISSUED` labels are voided, and the tickets carrying those labels move to `REMADE`, exactly as on a fresh activation. A superseded file re-enters rotation through `PENDING`, never by reverting the superseded row in place.

### 3.7. Catering Platters, Pickup Windows and Bucket Capacity

Catering is the deli's planned-volume business, and it takes a different shape from the walk-up counter. A `CateringOrder` names the `platter_deli_item_id` being ordered — a catalog item in category `CATERING_PLATTER` — the `certified_planner_associate_id` accountable for the build, a `customer_name`, a `platter_count` of at least 1, a `headcount` of at least 1, a `lead_time_hours` of at least 0, an inclusive `pickup_window_start` and an exclusive `pickup_window_end`, and a `deposit_cents` figure taken at confirmation. The pickup window must be strictly longer than zero and no longer than two hours past its start. An order may also name a `parent_order_id` when it was split off from a larger order. Orders begin in `INQUIRY` and can reach `CONFIRMED`, `IN_PRODUCTION`, `READY`, `PICKED_UP` or `CANCELLED`. Each creation request also carries a `request_id`.

That `request_id` is a replay guard. It must be unique across the store, and a repeated `request_id` is treated as a replayed request rather than a new order, rejected with `ERR_DUPLICATE_REQUEST`. The ordering of this check is deliberate and is stated in §2.11: the replay check fires ahead of the deeper state checks, so a replayed request never surfaces as a state error. Because the check is scoped to the store, a `request_id` reused against a different store is a new order.

Confirming an order moves it from `INQUIRY` to `CONFIRMED` and is the moment the order's capacity is claimed and its quote recomputed. Four conditions gate it, and the planner-certification test runs first among them. The `certified_planner_associate_id` must hold an ACTIVE `FOOD_HANDLING` certification, or the confirmation is refused with `ERR_ASSOCIATE_NOT_CERTIFIED`. The `lead_time_hours` must be at least 24 unless an ACTIVE `FOOD_HANDLING` certification is held — the floor is waived both when the planner holds one and when the acting caller is an entity-backed role whose own associate holds one; a violation yields `ERR_LEAD_TIME_VIOLATED`. The logical clock plus the order's `lead_time_hours` must not exceed the `pickup_window_start`, or the confirmation is refused with `ERR_LEAD_TIME_VIOLATED`. And the order must not push its pickup bucket past its aggregate capacity, or the confirmation is refused with `ERR_PICKUP_CAPACITY_EXCEEDED`. The store must also be `OPEN`; a store in any other posture is refused with `ERR_POSTURE_RESTRICTED`, which is the token this store-level gate reports even when the posture is `HALT`. On success the order is assigned its `pickup_bucket_key`, the bucket's headcount accumulator increases, and the quote is recomputed.

The bucketing is where the catering rules get their teeth, and it works on a bucketed key rather than on the raw window. The order's `pickup_bucket_key` is computed by subtracting a 10-minute pre-window staging buffer from the `pickup_window_start` and then truncating the result to the quarter hour. It is that key, and not the raw pickup window, that decides which aggregate bucket the order occupies. The bucket's capacity rule is aggregate rather than per-order: the sum of `headcount` over every catering order sharing one bucket key must stay within a bucket headcount limit of 40. An individual order can therefore pass every check in isolation and still be refused because of the company it keeps in its bucket. This is the classic aggregate-validation shape, and the rule is deliberately enforced on the confirm and revise paths rather than on creation.

Revising a confirmed order returns it to `INQUIRY` for re-confirmation and accepts an optional revised `platter_count`, `headcount`, `pickup_window_start` or `pickup_window_end`. It is available only before the order reaches `IN_PRODUCTION`. The bucket headcount accumulator increases on revision, and the quote is recomputed. A confirmed order that has not yet entered production may also be cancelled, which decreases the bucket accumulator; an inquiry may be cancelled freely with no accumulator effect.

The production sequence runs `CONFIRMED` to `IN_PRODUCTION` to `READY` to `PICKED_UP`. Starting production has no preconditions beyond the state pair. Marking an order ready requires the logical clock to have reached `pickup_window_start` minus two hours, and requires the store to have an ACTIVE price file at the clock, without which it is refused with `ERR_PRICE_FILE_STALE`; a clock more than two hours before the window is refused with `ERR_INVALID_STATE`. On success it synthesizes a `Label` with `subject_type` `CATERING_PLATTER` whose `net_weight_lbs` records the ordered item's `servings_per_platter` and whose unit price is that item's `retail_price_per_lb_cents`. Picking up requires the logical clock to sit strictly inside the half-open pickup window; a pickup requested at or after `pickup_window_end` is refused with `ERR_PICKUP_WINDOW_MISSED`, and the pickup decreases the bucket accumulator. Cancellation is available from `IN_PRODUCTION` and from `READY` for a manager-level caller, and a cancellation from `READY` additionally synthesizes an unclaimed-platter waste record against the platter's batch, which as described in §3.3 is excluded from the store's waste liability by virtue of its reason token. A cancellation from `IN_PRODUCTION` or `READY` is refused with `ERR_UNAUTHORIZED` for an acting role other than `DeliManager` or `PlatformAdmin`. The request may carry a free-text `reason`, which is recorded but whose vocabulary is not constrained: no cancellation is refused for the shape of its reason, and its absence is not a malformation.

A missed pickup window has a store-wide consequence that outlives the order. While a catering order sits past its `pickup_window_end` but short of `PICKED_UP`, the store is under a half-open pickup-window lockout, and that lockout blocks four operations: creating a sub ticket, ticketing a sub ticket, creating a production batch, and completing a production batch. All four are refused with `ERR_HACCP_WINDOW_FREEZE`. The freeze lifts when the order is finally picked up or cancelled. The effect is a FIFO brake: the store's fresh deli work stops until the stale catering commitment is resolved.

The quote itself is a tiered computation whose evaluation order is pinned. The per-platter base rate is chosen from the unadjusted `platter_count`: 1800 cents when the count is below 3, 1650 cents when the count is at least 3 and at most 6, and 1500 cents when the count exceeds 6. Note that the tier boundaries are inclusive on the middle band at both ends. The certified-planner adjustment is a rate of negative five percent when the order's `lead_time_hours` is below 24 and the `certified_planner_associate_id` holds an ACTIVE `FOOD_HANDLING` certification, and zero percent otherwise. The base total is the `platter_count` multiplied by the chosen per-platter rate. The service fee is the base total multiplied by the adjustment rate, rounded half up to a whole cent — and this is the only rounding in the whole computation. The rush fee is 2600 cents when `lead_time_hours` is below 24, and zero otherwise; note that the rush fee and the certified-planner discount are independent, so a fast order handled by a certified planner takes both the discount and the rush charge. Finally, `quote_total_cents` is the base total plus the service fee plus the rush fee, and `servings_per_platter` on the ordered item supplies the per-platter serving count used elsewhere.

A separate deposit flow exists alongside the quote. A platform-admin capability simulates an external payment outcome for a catering deposit, taking the `catering_order_id` and an `outcome`, and records the simulated result without moving any state. It exists so that the deposit surface can be exercised without an external payment provider.

### 3.8. Associate Lifecycle, Suspension and Store Halt

An `Associate` is the store's staff row: a store-unique `employee_number`, a `full_name`, a `primary_role` of `DELI_CLERK`, `DELI_MANAGER` or `BAKERY_COORDINATOR`, a status of `ACTIVE` or `SUSPENDED`, and an `allergy_set` naming the allergens that associate is cleared to handle, drawn from the same six-allergen vocabulary as catalog items and defaulting to empty. The `allergy_set` is not decoration: it is the coverage list checked when the associate completes a sub ticket, and a clerk cannot ticket or complete a product whose allergen set is not a subset of what their own set covers. Alongside those fields the associate exposes the derived `active_certification_count` and `assigned_slicer_id` described in §2.8.

Suspending an associate is the store's most consequential single action, and it is the deepest cascade in the system. The suspension request carries a `reason` drawn from `CERTIFICATION_EXPIRED`, `SAFETY_VIOLATION` or `TRANSFER`. The associate moves to `SUSPENDED`. Every certification they hold moves to `REVOKED`. The store's `certified_slicer_operator_count` is recomputed, and if that count has reached zero the store's `HALT` transition fires. Every non-terminal sub ticket in the store then moves to `ABANDONED`, each abandoned ticket releases the bread units it was reserving, and each affected promotion is pushed to `DEGRADED` when its units-short count reaches zero. Four cascade levels in one request, and every row touched along the way has its version incremented. Suspension is also what makes the `HALT` state reachable in ordinary operation: a store whose last certified slicer operator is suspended halts, and the halt takes the store's entire ticket book with it.

Reinstating a suspended associate returns them to `ACTIVE` and recomputes the store's certified-slicer-operator count, which can move the store from `HALT` back toward `RESTRICTED` or `OPEN`. The reinstatement path expects the associate to present a renewed `SLICER_OPERATION` certification before it is used, which is why reinstatement and certification renewal are naturally paired operations.

The store's `HALT` state is entered from `RESTRICTED` and left only when its predicates clear. Entering `HALT` happens automatically when the store's posture reason computes as `CERTIFICATION_TRIGGERED` — that is, when the certified-slicer-operator count has reached zero or `haccp_safety_flag` has been set true. The entry cascades as described above. Leaving `HALT` for `RESTRICTED` happens automatically once at least one associate in the store holds an `ACTIVE` `SLICER_OPERATION` certification whose `expires_at` is strictly after the logical clock, at which point the store's reason token recomputes to `REVOCATION_TRIGGERED` or `INVENTORY_TRIGGERED` depending on which of the remaining predicates still fires. `HALT` is the store's only terminal state, though the transition back out exists and is exercised in practice by reinstating a suspended associate or issuing a fresh certification.

The `RESTRICTED` state is entered automatically from `OPEN` whenever the store's posture reason computes as `INVENTORY_TRIGGERED`, `REVOCATION_TRIGGERED` or `NO_ACTIVE_PRICE_FILE`. Its entry records the predicate token on `posture_reason` and blocks new production-batch creation with `ERR_POSTURE_RESTRICTED` until the store returns to `OPEN`. It returns to `OPEN` once the store's case weight is back within its `deli_case_capacity_lbs`, an ACTIVE scale price file exists, and at least one associate holds an ACTIVE `SLICER_OPERATION` certification — the conjunction that the posture calculation reports as reason `OK`.

Finally, an operator-controlled gate exists for forcing the halt posture without touching certification or sanitation state. Setting a store's `posture_gate_flag` to true forces `posture` to `HALT` with reason `POSTURE_GATE_TRIGGERED`, and the gate request carries the store's identifier and the flag value. When the flag is set true, every non-terminal sub ticket in the store moves to `ABANDONED` and each abandoned ticket releases its bread reserve, exactly as the certification-induced halt does. Clearing the flag recomputes posture and the store's version. This is the supported way to put a store into `HALT` from a clean state, and it is the only posture predicate an operator can flip directly.

## 4. Endpoint Definitions

Operations that create a new stand-alone resource or add a distinct resource to a collection return `201 Created`. Operations that modify an existing resource — including state transitions, internal recomputations and derived-field refreshes — return `200 OK`. The logical clock, role-permission and payment-simulation utilities under the platform namespace also return `200 OK`, as does the chain-wide production-day sweep even though it mutates many stores. No endpoint in this API returns `204`: an operation with nothing to say still returns the standard envelope with an empty data object. Error responses return the status declared in §5 and carry the standard error envelope.
