# Event Ticketing Selfserve API — Product Requirements Document

## 1. Introduction

Independent promoters, conference organisers and club bookers have historically been squeezed between two bad options: spreadsheet-and-cash-box ticketing that collapses the moment a show sells out, or enterprise box-office software that assumes a full-time operations team. This document specifies the backend for a self-serve ticketing and registration platform that closes that gap. An organiser registers, describes a venue-bound event, publishes ticket tiers, and immediately has a working sales channel — with inventory holds, promotional codes, reserved seating, gate scanning, refunds, ticket transfers, a waitlist, and organiser payouts all handled by the platform rather than by the organiser.

Three tensions shape nearly every rule below. The first is **inventory truth**: a ticket tier's remaining capacity is not a stored counter that anyone may edit, but a derived quantity that must reconcile issued admissions, live checkout holds, and outstanding waitlist offers at the instant of the request. The second is **money that flows in two directions**. Buyers pay face value plus (or inclusive of) a platform fee; organisers are credited a gross figure that depends on who was declared to bear that fee; refunds later claw money back from the organiser and, depending on the refund variant selected, either do or do not return the platform's own fee. The third is **settlement risk**. Because organisers are paid before every refund window has closed, the platform withholds a rolling reserve sized by the organiser's measured reliability, and releases it only after the event has aged out.

The API is mounted under `/api`, with a single test-driving control surface mounted at `/_clock`. Everything in this specification is expressed in terms of a server-side logical clock rather than wall-clock time, so that time-dependent behaviour — hold expiry, promotional windows, check-in windows, transfer and waitlist offer time-to-live, refund windows, reserve maturity — is deterministic and reproducible.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two headers. `X-User-Role` names the acting role; `X-User-ID` names the acting principal. Exactly six roles are recognised, and their spellings are fixed: `Organizer`, `Buyer`, `GateStaff`, `FinanceOfficer`, `PlatformAdmin`, and `Anonymous`. A request whose `X-User-Role` header is missing, or whose value is not one of those six strings, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); the same rejection applies when `X-User-ID` is missing for any role other than `Anonymous`, which alone requires no `X-User-ID`. Once authenticated, if the acting role is not among the roles the target endpoint permits, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Two of the six roles are backed by persisted entities. When `X-User-Role` is `Organizer`, `X-User-ID` is the `id` of the acting `Organizer` record; ownership checks on any resource that references an `Organizer` compare the resource's foreign-key field to `X-User-ID`. Because an event names its owning organiser, and tiers, seat blocks, promotional codes, orders, admissions and refund requests all resolve upward to exactly one event, an `Organizer` acting on any of those resources must match the organiser reached by that upward walk. When `X-User-Role` is `Buyer`, `X-User-ID` is the `id` of the acting `Buyer` record; ownership checks compare `X-User-ID` against the purchasing buyer recorded on an order, the waiting buyer recorded on a waitlist entry, or the current holder recorded on an admission, whichever the endpoint operates on. An ownership failure on any organiser-scoped or buyer-scoped endpoint — mutating or read — is also reported as `ERR_UNAUTHORIZED` (HTTP 403). The single-resource reads that carry this check are the order, order line, admission, promotional code, transfer offer, waitlist entry, refund request, payout and event-report reads; the organiser, venue and buyer reads carry no ownership check at all, and no collection-listing endpoint is scoped by the acting principal — a list returns every matching record regardless of who owns it.

The remaining four roles are opaque. When `X-User-Role` is `GateStaff`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as `scanned_by_user_id` on the scan record a gate operator produces, but never compares it to any entity's `id`. When `X-User-Role` is `FinanceOfficer`, `X-User-ID` is likewise an opaque operator identifier; the server records it as `approved_by_user_id` and `released_by_user_id` on payouts, and compares those two recorded values against each other for segregation of duties, but never against any entity's `id`. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier that the server does not persist on any entity. When `X-User-Role` is `Anonymous`, there is no identity at all: the value is neither required nor recorded, and no ownership check can succeed or fail on it, so `Anonymous` is confined to public browsing and buyer self-registration.

Role boundaries carry real business meaning rather than being mere access lists. A `PlatformAdmin` provisions organisers and venues and drives the logical clock, but holds no approval power over money: it can neither approve a refund nor release a payout. An `Organizer` decides whether a refund is legitimate but cannot settle it. A `FinanceOfficer` settles refunds and administers payouts and the rolling reserve but cannot originate or approve a refund request on the organiser's behalf. `GateStaff` operates the door and nothing else.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection-returning endpoint accepts two optional query parameters. `limit` defaults to 10 when omitted, may be no smaller than 1, and may be no larger than 100. `offset` defaults to 0 and may be no smaller than 0. A value outside those bounds is a request-shape failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400), as is a value that cannot be parsed as an integer at all.

Results are ordered by `created_at` ascending unless a specific workflow states otherwise. The `meta` block of a list response carries `limit`, `offset`, `total_count` — the number of records matching the filters before the window is applied — and `has_more`, which is true exactly when records remain beyond the current window.

### 2.4. Common Resource Properties

Every persisted resource carries a server-minted `id`. Identifiers are UUID strings with no type prefix: a ticket tier's `id` and a payout's `id` are indistinguishable by shape, and clients must never parse meaning out of one. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits, recording the instant of creation as read from the logical clock.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp in the same format, and `version`, an integer that begins at 1 when the resource is created and increases by exactly 1 on every mutation of that resource. Any operation that changes a resource refreshes its `updated_at` to the current logical-clock instant and advances its `version`, including mutations that arrive as a downstream consequence of an operation on some other resource. One class of downstream write is deliberately excluded: when an `Event`'s four reporting roll-ups `gross_cents`, `refunds_cents`, `issued_count` and `checked_in_count` are refreshed as a consequence of a payment, a scan, an undone check-in, a void or a refund settlement, the event's `updated_at` and `version` are left exactly as they were — only the lifecycle transitions of §3.2, tier creation and tier edits, and order creation advance an event's `version`.

One entity is deliberately leaner. The scan record produced by a gate operator is an append-only audit fact: it carries `id` and `created_at` only. It has no `updated_at` and no `version`, because it is never modified after it is written. `Organizer`, `Venue`, `Buyer`, `Event`, `TicketType`, `SeatBlock`, `PromoCode`, `Order`, `OrderItem`, `Attendee`, `RefundRequest`, `TransferRequest`, `WaitlistEntry` and `Payout` all carry the full set.

### 2.5. The Logical Clock and Lazy Expiry

The platform reads the current instant — referred to throughout as the current time — from a server-side logical clock, never from wall-clock time. Before the clock has been set, it reads exactly `2026-07-01T00:00:00Z`. A `PlatformAdmin` may move it to any ISO 8601 UTC instant by supplying `to_iso8601`; the response reports the resulting `current_utc`. Moving the clock mutates no entity and fires no background work.

That last point is a load-bearing design decision. **Nothing in this system expires on a timer.** Every deadline — a checkout hold, a promotional window, a check-in window, a transfer offer, a waitlist offer, a refund window, a reserve maturity date — is evaluated lazily, at the moment the next business call reads it. An expired checkout hold remains stored as a held order until something looks at it; a stale waitlist offer remains `OFFERED` until the next sweep on that tier walks past it and retires it. Implementers must therefore compare stored deadlines against the clock at request time rather than relying on any scheduled process.

### 2.6. Money, Rounding and Cent Arithmetic

All monetary amounts are integers denominated in cents. There are no fractional cents anywhere in the system, and no amount is ever stored or returned as a decimal currency value. Wherever a computation produces a fractional intermediate — a percentage of a face value, a prorated share of a discount, a reserve rate applied to a basis — the result is rounded half up to a whole number of cents, meaning a value ending in exactly one half cent rounds away from zero to the next cent.

Rounding placement is not incidental; it is part of the contract. Each calculation below states exactly how many times rounding occurs and at which step, and an implementation that rounds a different number of times, or at a different step, will produce different totals on mixed-price orders even when every input matches. The single non-cent quantity in the system is the check-in rate reported by the organiser report, which is a number carried to exactly four decimal places and likewise rounded half up.

### 2.7. Optimistic Concurrency

Two write paths depend on state the client has already read and rendered, and both guard against acting on a stale view.

A `POST /api/orders` request must carry `expected_event_version` as a required input field, holding the `version` of the target `Event` as the client last observed it. If that value does not equal the event's current `version`, the create is rejected with `ERR_STALE_EVENT_VERSION` (HTTP 412). This matters because an event's `version` advances on every tier creation, every tier reprice or resize, every lifecycle transition, every prior order creation, and every waitlist claim — so a mismatch is proof that the tier lineup, pricing, or remaining inventory the client rendered on its checkout page is no longer what the server holds.

A `POST /api/payouts` request must carry `expected_organizer_version` as a required input field, holding the `version` of the target `Organizer` as the client last observed it. If that value does not equal the organiser's current `version`, the create is rejected with `ERR_STALE_ORGANIZER_VERSION` (HTTP 412). An organiser's `version` advances on every paid order and every settled refund, each of which changes the amounts a newly created payout would compute; the check exists so that a finance operator cannot open a settlement against figures that have already moved beneath them.

No other endpoint accepts a version field. Endpoints not named above neither require nor honour an expected-version input.

### 2.8. Validation Precedence

When a single request could fail several checks at once, the checks run in a fixed order and the first failure is the one reported. The order is:

1. **Authentication** — headers present and the role recognised, else `ERR_UNAUTHENTICATED`.
2. **Role authorisation** — the acting role appears in the endpoint's permitted list, else `ERR_UNAUTHORIZED`.
3. **Request shape** — required fields present, types correct, enum members drawn from the declared sets, integers inside their declared ranges, else `ERR_INVALID_REQUEST`.
4. **Existence** — every entity named in the path or body resolves, each with its own not-found code, evaluated in this internal order: organiser, venue, buyer, event, ticket tier, seat block, promotional code, order, order line, admission, refund request, transfer request, waitlist entry, payout, scan record.
5. **Ownership** — the acting principal owns the resource, else `ERR_UNAUTHORIZED`.
6. **State** — the entity is in a status from which the requested operation is declared.
7. **Temporal** — the operation falls inside its declared time window.
8. **Referential** — cross-entity parentage matches.
9. **Safety** — void, already-checked-in and segregation-of-duties guards.
10. **Structural constraints** — seat occupancy, seat range, per-buyer ticket limits, uniqueness.
11. **Fiscal constraints** — capacity, promotional eligibility, refund ceilings, payout eligibility.
12. **Optimistic concurrency** — the expected-version guard, which is evaluated last.

Within a path, parameters are validated left to right: a nested read whose parent does not resolve reports the parent's not-found code before the child is ever looked up.

### 2.9. Inventory Truth: Sold, Held and Available

A ticket tier's remaining capacity is derived on every read and on every write that consumes it, never trusted as an editable counter. The sold quantity for a tier is the number of admissions on that tier whose status is `ISSUED`, `CHECKED_IN` or `TRANSFERRED`. The held quantity for a tier is the sum of two things: the quantities on order lines belonging to orders whose fulfilment status is `HELD` and whose hold deadline is still in the future, plus the requested quantities of waitlist entries on that tier whose status is `OFFERED` and whose offer deadline is still in the future. The available quantity is the tier's total inventory minus the sold quantity minus the held quantity.

Two boundaries follow from that definition and are enforced everywhere capacity is consumed. A request for a given number of tickets requires the available quantity to be at least that number — equality is sufficient. When the available quantity is exactly zero, the tier is sold out and the request is rejected with `ERR_SOLD_OUT`; when the available quantity is greater than zero but strictly less than the requested number, the request is rejected with `ERR_INSUFFICIENT_CAPACITY`. Voided admissions and expired holds contribute to neither the sold nor the held quantity, so releasing a hold or voiding an admission genuinely returns capacity to the pool. When one order names the same tier on several lines, the number tested against that tier's available quantity is the sum of those lines' quantities, evaluated once per distinct tier.

## 3. Business Logic & Workflows

### 3.1. Provisioning the Marketplace

Before anything can be sold, the platform operator seeds two kinds of counterparty. An organiser account is registered with a `display_name`, the public-facing promoter name shown to buyers, and a `contact_email` used for billing and correspondence. Two lifetime money counters are opened at zero on that record and never edited directly: `lifetime_gross_cents` accumulates the organiser-credited amount of every order that reaches paid status across every event the organiser owns, and `lifetime_refunds_cents` accumulates the organiser-charged amount of every refund that reaches settlement across the same events. A venue is registered with a `name`, a `city`, and a `seated_capacity` giving the physical headcount the room can hold, which must be at least 1.

Buyers arrive through a different door. Buyer self-registration is open to the unauthenticated public as well as to platform operators, and takes an `email` and a `display_name`. The email address is the buyer's unique handle across the whole platform; a second registration reusing an address already on file — compared as an exact, case-sensitive string — is rejected with `ERR_DUPLICATE_PROMO_CODE`, the shared uniqueness-violation code. Reading an organiser, a venue or a buyer that does not resolve yields `ERR_ORGANIZER_NOT_FOUND`, `ERR_VENUE_NOT_FOUND` or `ERR_BUYER_NOT_FOUND` respectively.

### 3.2. Bringing an Event to Market

An organiser opens an event by naming the owning `organizer_id`, the `venue_id` it will occupy, a `title`, and the `starts_at` and `ends_at` instants that bound it. Two optional declarations are made at the same moment and are difficult to reverse in practice, so they deserve care. `fee_mode` decides who bears the platform fee and takes either `PASS_ON` — the default when omitted — or `ABSORB`. `refund_policy` decides the default refund variant for the event and takes either `FEE_RETAINED` — the default when omitted — or `FEE_INCLUDED`. The acting `Organizer` must itself be the named `organizer_id`, and a mismatch is rejected with `ERR_UNAUTHORIZED` once both the organiser and the venue have been resolved. The event is created in `DRAFT` status with `version` 1, and its four reporting roll-ups `gross_cents`, `refunds_cents`, `issued_count` and `checked_in_count` all start at zero.

Two temporal guards apply at creation. First, `starts_at` must be strictly after the current time and `ends_at` must be strictly after `starts_at`; a violation of either is rejected with `ERR_EVENT_START_IN_PAST`. Second, a venue cannot host two overlapping shows, and the platform reserves ninety minutes of turnaround after every event for load-out and reset. Concretely, the new event claims the half-open interval that begins at its `starts_at` and ends ninety minutes after its `ends_at`; if that interval intersects the identically-constructed interval of any other event on the same `venue_id` whose status is anything other than `CANCELLED`, the create is rejected with `ERR_VENUE_DOUBLE_BOOKED`. Because both intervals are half-open at their upper end, a new event whose `starts_at` falls exactly ninety minutes after an existing event's `ends_at` is accepted — the boundary instant belongs to the newcomer.

Publishing carries the event from `DRAFT` to `ONSALE`. It is permitted only while the event is in `DRAFT`, only when at least one ticket tier already exists on the event, and only while `starts_at` remains strictly in the future; a publish attempted from any other status, or with no tier declared, is rejected with `ERR_INVALID_EVENT_TRANSITION`, while a start instant that has already passed yields `ERR_EVENT_START_IN_PAST`. Publishing increments the event's `version` by 1.

Sales can be suspended and resumed without limit. Pausing takes an event from `ONSALE` to `PAUSED` and requires the event to be `ONSALE`; resuming takes it from `PAUSED` back to `ONSALE`, requires the event to be `PAUSED`, and re-checks that `starts_at` is still strictly in the future, rejecting with `ERR_EVENT_START_IN_PAST` if the show has since begun. Both increment `version` by 1. The `ONSALE → PAUSED → ONSALE` cycle may repeat without bound. Pausing deliberately does **not** disturb checkouts already in flight: orders sitting in `HELD` fulfilment keep their existing hold deadline untouched, so a buyer mid-checkout is not punished for an organiser's administrative pause.

Closing sales is the harder stop. It is permitted from either `ONSALE` or `PAUSED`, lands the event in `SALES_CLOSED`, and increments `version` by 1. It also sweeps the floor: every order on the event still in `HELD` fulfilment is moved to `EXPIRED` fulfilment and its held seats are given back, decrementing the affected seat blocks' occupied-seat counts by the number of seats released and recomputing each affected tier's held quantity. An event that has ended may then be completed, moving `SALES_CLOSED → COMPLETED`. Completion requires the event to be in `SALES_CLOSED` — otherwise `ERR_INVALID_EVENT_TRANSITION` — and requires that `ends_at` is at or before the current time, so an attempt to complete a show that has not yet finished is rejected with `ERR_EVENT_NOT_ENDED`. Completion increments `version` by 1 and recomputes and freezes the four reporting roll-ups `gross_cents`, `refunds_cents`, `issued_count` and `checked_in_count`.

Cancellation is available from `DRAFT`, `ONSALE`, `PAUSED` or `SALES_CLOSED`, accepts an optional `reason`, and is described in full in §3.8, because from `ONSALE` onward it is really a money operation wearing a lifecycle operation's clothes. `COMPLETED` and `CANCELLED` are terminal: no transition leaves either, and any attempt reports `ERR_INVALID_EVENT_TRANSITION`. Events may be listed with optional `organizer_id`, `venue_id` and `status` filters alongside the usual `limit` and `offset`, and read individually — both are open to every role including `Anonymous`, since the sales page is public. An event named in a path or body that does not resolve yields `ERR_EVENT_NOT_FOUND`.

### 3.3. Tiers, Seat Blocks and Promotional Codes

A ticket tier is declared against an `event_id` with a `name` such as General or VIP, a `tier_rank` giving its ordinal position where 1 is the lowest tier and higher integers rank above it, a `price_cents` face value of at least 0, and a `quantity_total` of at least 1 giving the tier's sellable inventory. An optional `seating_mode` chooses between `GA` — the default when omitted — and `RESERVED`. A tier may be declared against an event in any lifecycle status; the event's `status` is not consulted, only its ownership. Creating a tier increments the owning event's `version` by 1. The tier's derived `sold_count` and `held_count` are exposed on reads and follow the definitions in §2.9 exactly; the available count derived from `quantity_total` minus those two is likewise reported on a tier read, under both the field names `available` and `available_count`, which always carry the same value. Tiers may be listed with optional `event_id` and `seating_mode` filters. A tier that does not resolve yields `ERR_TICKET_TYPE_NOT_FOUND`.

Tiers can be repriced and resized after the fact by supplying `price_cents`, `quantity_total`, or both. Both fields are optional and the event's status is not checked, so an edit is accepted at any point in the event's life and an edit supplying neither field is accepted too — and still advances both versions. Such an edit increments both the tier's own `version` and the owning event's `version` by 1 — the latter is why a checkout page rendered before a reprice will fail the expected-event-version guard described in §2.7. Crucially, repricing is never retroactive: every order already created keeps the unit price it snapshotted at creation, and no existing order's money is recomputed by a later tier edit.

Reserved tiers need physical geography, supplied as seat blocks. A block names the `ticket_type_id` of the reserved tier it belongs to, a `row_label` that must be unique within that tier, and an inclusive numeric range from `seat_from` to `seat_to`. Both endpoints of the range are at least 1 and `seat_to` must be greater than or equal to `seat_from`; a block that inverts its range is rejected with `ERR_SEAT_RANGE_INVALID`, and a `row_label` already present on the same tier is rejected with `ERR_DUPLICATE_PROMO_CODE`. Of those two the duplicate-label check is the one that runs first, so a block that both repeats a row label and inverts its range reports `ERR_DUPLICATE_PROMO_CODE`. The named tier's `seating_mode` is not checked: a block may be declared against a `GA` tier just as against a `RESERVED` one. The block's `seats_total` is derived as `seat_to` minus `seat_from` plus one, and its `seats_taken` opens at zero. Thereafter `seats_taken` counts the seat numbers in the block currently occupied — occupied either by an admission whose status is `ISSUED`, `CHECKED_IN` or `TRANSFERRED`, or reserved by an order line belonging to an order whose fulfilment status is `HELD` and whose hold deadline is still in the future. Blocks may be listed filtered by `ticket_type_id`; an unresolvable block yields `ERR_SEAT_BLOCK_NOT_FOUND`.

Promotional codes are scoped to exactly one event. A code declares its `event_id`, the `code` string buyers will type — unique per event, with a collision rejected as `ERR_DUPLICATE_PROMO_CODE` — a `kind` of either `PERCENT` or `FIXED`, a `max_uses` of at least 1, and the `valid_from` and `valid_until` instants bounding its redemption window. A `PERCENT` code expresses its discount in `percent_bp`, basis points between 0 and 10000 inclusive where 1000 means ten percent; a `FIXED` code expresses it in `amount_cents`, a non-negative flat sum. Both fields default to 0 when omitted, so the field carrying the discount for the chosen `kind` must be supplied. The two window instants are never compared against each other at creation, so an inverted window is accepted and simply never opens. The code's `uses_count` starts at zero and counts the orders that currently hold it, described precisely in §3.4. Codes may be listed with optional `event_id` and `code` filters and read individually; a code that cannot be resolved yields `ERR_PROMO_CODE_NOT_FOUND`. Both listing and reading promotional codes are restricted to the owning `Organizer` and `PlatformAdmin` — buyers see the effect of a code, never its budget.

### 3.4. Checkout: Composing an Order, the Fee Ladder and the Discount

A buyer composes a purchase by naming the `event_id` being bought into, their own `buyer_id`, an `items` array describing one or more lines, an optional `promo_code` string, and the `expected_event_version` guard of §2.7. Each entry of `items` becomes one order line and carries a `ticket_type_id`, a `quantity` of at least 1, an optional `seat_block_id` and an optional `seat_numbers` array. Selling is only open while the event is `ONSALE`; an order attempted against an event in any other status is rejected with `ERR_EVENT_NOT_ONSALE`. Every tier named must belong to the same event as the order, every seat block named must belong to the tier named on the same line, and a promotional code named must be scoped to the same event; any of those parentage failures is reported as `ERR_PROMO_EVENT_MISMATCH`.

Creating the order opens a live hold. The `hold_expires_at` deadline is set to fifteen minutes after the current time, and the hold is live for as long as the current time is strictly before that instant. While it is live, the order's reserved seats count toward each affected seat block's `seats_taken` and each affected tier's `held_count`, which is exactly how a half-finished checkout keeps a competing buyer out. The order opens with `payment_status` of `PENDING` and `fulfillment_status` of `HELD`. Every line snapshots the tier's face value into `unit_price_cents` at this moment; that snapshot, not the tier's current price, governs every later money computation on the order.

The platform fee is computed per ticket, and the order of operations is pinned. For each line, take the face value snapshotted into `unit_price_cents` and choose a rate from a three-rung ladder: a face value of 25 dollars or less — that is, at most 2500 cents — uses a rate of 2.0 percent; a face value above that but no more than 100 dollars, meaning at most 10000 cents, uses 3.7 percent; anything above 10000 cents uses 5.0 percent. Multiply the face value by the chosen rate, round that product half up to a whole cent, then add a flat component of 179 cents. Clamp the result upward to a floor of 99 cents and downward to a ceiling of 2500 cents — that is, take the larger of the computed amount and 99, then take the smaller of that and 2500. The clamped figure is the line's `per_ticket_fee_cents`.

Line and order aggregation then follow mechanically, and the pinned rounding order matters more than it appears. The line's `line_face_cents` is `unit_price_cents` multiplied by `quantity`; the line's `line_fee_cents` is the **already rounded** `per_ticket_fee_cents` multiplied by `quantity`. The order's `subtotal_cents` is the sum of `line_face_cents` across every line, and its `fee_total_cents` is the sum of `line_fee_cents` across every line. The alternative arrangement — summing face values across the order, applying the rate once, rounding once, and adding the flat component afterwards — is explicitly not the rule here, and yields a different cent total on any order mixing tiers at different prices. Round once per ticket, then multiply, then sum.

Discounting runs after the order's subtotal is known and before the fee-mode variant is chosen. When a `promo_code` string is supplied, it is resolved by code string across every event, preferring the code scoped to the order's own event when one exists and otherwise taking the earliest-created match elsewhere; only a string matching no code anywhere is rejected with `ERR_PROMO_CODE_NOT_FOUND`, while a string that resolves solely to a code on some other event survives resolution and fails later on the parentage gate. Four gates then apply, and they fire in the precedence of §2.8 rather than in the order they read here. First, as a temporal check, the current time must fall at or after `valid_from` and strictly before `valid_until`, otherwise `ERR_PROMO_WINDOW_CLOSED` — this gate is evaluated ahead of every referential, seat, limit and capacity check on the whole checkout. Next, as a referential check, the code's `event_id` must equal the order's `event_id`, otherwise `ERR_PROMO_EVENT_MISMATCH`. Last, among the fiscal constraints and after capacity has been cleared, the order's `subtotal_cents` must be at least 50 dollars — 5000 cents, an inclusive floor, so a subtotal of exactly 5000 cents qualifies — otherwise the request is rejected with `ERR_PROMO_NOT_APPLICABLE`, and then the code's `uses_count` must be strictly less than its `max_uses`, otherwise `ERR_PROMO_EXHAUSTED`.

The discount itself is the smallest of three candidates. The first candidate is the code's raw entitlement: for a `PERCENT` code, the order's `subtotal_cents` multiplied by `percent_bp` and divided by 10000, rounded half up to a whole cent; for a `FIXED` code, simply its `amount_cents`. The second candidate is a platform-wide ceiling of thirty percent of the order's `subtotal_cents`, again rounded half up to a whole cent — no promotion, however generous its declaration, may discount an order by more than that share. The third candidate is `subtotal_cents` itself, so a discount can never exceed the goods. The smallest of those three becomes the order's `discount_cents`, and the resolved code's identifier is recorded on the order as `promo_code_id`, which stays null when no code was applied. Applying a code advances that code's `uses_count`, which counts precisely the orders naming it whose fulfilment status is `HELD`, `ISSUED`, `CHECKED_IN_PARTIAL` or `CHECKED_IN_FULL`.

One consequence of the pinned evaluation order deserves stating outright, because it looks circular. Fees are computed from **undiscounted** face values and are never recomputed once the discount is known, even though under a pass-on fee mode the buyer's total is assembled as subtotal minus discount plus fee, which makes the fee look as though it ought to track the total. It does not. The sequence is: per-ticket fee from face value, then subtotal, then discount from subtotal, then the buyer and organiser totals. Nothing propagates backwards.

The two totals depend on the event's `fee_mode`. Under `PASS_ON`, the buyer bears the fee: `buyer_total_cents` is `subtotal_cents` minus `discount_cents` plus `fee_total_cents`, and `organizer_gross_cents` is `subtotal_cents` minus `discount_cents`. Under `ABSORB`, the organiser bears it: `buyer_total_cents` is `subtotal_cents` minus `discount_cents`, and `organizer_gross_cents` is `subtotal_cents` minus `discount_cents` minus `fee_total_cents`. The order's `refunded_cents` opens at zero and its `paid_at` opens as null. Creating the order increments the owning event's `version` by 1.

Reserved seating adds its own arithmetic. For a line on a `RESERVED` tier, `seat_block_id` is required and `seat_numbers` must list exactly as many seat numbers as the line's `quantity`; for a line on a `GA` tier, `seat_block_id` must be null and `seat_numbers` must be empty. Every requested seat number must fall inside the block's inclusive range from `seat_from` to `seat_to`. Any of those shape failures is rejected with `ERR_SEAT_RANGE_INVALID`. Each requested seat must additionally be free at the current time: a seat is occupied when an admission with status `ISSUED`, `CHECKED_IN` or `TRANSFERRED` holds it, or when an order line of an order in `HELD` fulfilment holds it across the half-open interval running from that order's `created_at` up to but not including its `hold_expires_at`. A request landing at exactly the held order's `hold_expires_at` therefore finds the seat free. A collision is rejected with `ERR_SEAT_UNAVAILABLE`, and so is a seat named twice across two different lines of the very same order, because the occupancy pass runs over the whole request before the shape pass does; a single line that repeats a seat number inside its own `seat_numbers` array is instead caught by the shape pass and reported as `ERR_SEAT_RANGE_INVALID`.

A final ceiling protects the room from scalping. No buyer may hold more than ten live tickets for a single event. The count sums the `quantity` of every order line across that buyer's orders on the event whose fulfilment status is `HELD`, `ISSUED`, `CHECKED_IN_PARTIAL` or `CHECKED_IN_FULL`, plus the quantity now being requested; if that total would exceed ten, the request is rejected with `ERR_TICKET_LIMIT_EXCEEDED`.

When several of these guards could fire on one checkout, they resolve in the precedence of §2.8: the event-state gate first, then the promotional redemption window, then referential parentage, then seat occupancy and seat-range shape, then the per-buyer ticket limit, then the uniqueness family, then capacity — sold-out before insufficient-capacity — then the promotional gates in the order eligibility floor, redemption budget, and finally the expected-event-version guard last of all.

Orders can be read individually and listed with optional `event_id`, `buyer_id`, `promo_code_id`, `payment_status` and `fulfillment_status` filters; an order that does not resolve yields `ERR_ORDER_NOT_FOUND`. Order lines are readable individually and listable with optional `order_id`, `ticket_type_id` and `seat_block_id` filters, exposing the `order_id` of the owning order alongside the fee breakdown; a line that does not resolve yields `ERR_ORDER_ITEM_NOT_FOUND`.

### 3.5. Payment, Admissions and the Door

Paying carries an order's payment dimension from `PENDING` to `PAID` and, on the very same call, its fulfilment dimension from `HELD` to `ISSUED`. Four preconditions guard it, and they are evaluated in this order: the order's event must still be `ONSALE`, else `ERR_EVENT_NOT_ONSALE`; then the order's `payment_status` must be `PENDING` and its `fulfillment_status` must be `HELD` — a violation of either is `ERR_ORDER_NOT_HELD`; then the current time must be strictly before `hold_expires_at`, else `ERR_HOLD_EXPIRED`. A payment attempted against a lapsed hold on an event that has since left `ONSALE` therefore reports the event's state, not the expired hold.

The consequences fan out. `paid_at` is stamped with the current time. One admission is minted per ticket across every line — a reserved line mints one admission for each entry in its `seat_numbers`, a general-admission line mints as many as its `quantity` — each opening in `ISSUED` status. Each minted admission records the `order_id` and `order_item_id` that produced it, the `ticket_type_id` of the tier, the `event_id` it admits to, the `buyer_id` of its current holder, the `holder_email` copied from that buyer's `email`, and for reserved admissions the `seat_block_id` and the specific `seat_number` occupied, both of which stay null for general admission. Its `checked_in_at` opens as null. Each affected tier's `sold_count` rises and its `held_count` is recomputed; the seat blocks' `seats_taken` figures are unchanged, because the very same seat numbers simply move from held occupancy to issued occupancy. The organiser's `lifetime_gross_cents` rises by the order's `organizer_gross_cents` and the organiser's `version` rises by 1. The event's `gross_cents` and `issued_count` are recomputed, without disturbing the event's own `version` or `updated_at` as §2.4 describes; its `refunds_cents` and `checked_in_count` are left alone. The order's own `version` rises by 1, once, regardless of how many admissions were minted.

A buyer — or the organiser — may instead abandon the checkout, taking fulfilment from `HELD` to `EXPIRED`. That is permitted only while `fulfillment_status` is `HELD` and `payment_status` is `PENDING`, else `ERR_ORDER_NOT_HELD`. Releasing gives every reserved seat back, decrementing each affected block's `seats_taken` by the number of seat numbers the corresponding line held, recomputes the affected tiers' `held_count`, and — when the order carried a `promo_code_id` — hands the redemption back by decrementing that code's `uses_count` by 1. The order's `version` rises by 1. Both `EXPIRED` and `VOIDED` fulfilment are terminal for an order.

At the door, a gate operator scans an admission by submitting the `attendee_id`, the `event_id` of the gate performing the scan, and a `gate_code` identifying the specific gate. An accepted scan requires the admission to be in `ISSUED` or `TRANSFERRED` status — a transferred admission is scannable in exactly the way an issued one is — requires the admission's own `event_id` to equal the scan's `event_id`, requires the event to be in `ONSALE`, `PAUSED` or `SALES_CLOSED` — any other status is rejected with `ERR_EVENT_NOT_ONSALE`, and that gate is evaluated before both the check-in window and the event-mismatch check, so the window a scan is measured against is always the gate's event rather than the admission's — and requires the current time to fall inside the check-in window. That window opens two hours before the event's `starts_at` and closes one hour after its `ends_at`, and both bounds are inclusive, so a scan landing exactly on either boundary instant is accepted. A scan outside it is rejected with `ERR_CHECKIN_WINDOW_CLOSED`. A scan of an admission that has been voided is rejected with `ERR_TICKET_VOIDED`; a second scan of an admission already in `CHECKED_IN` is rejected with `ERR_ALREADY_CHECKED_IN`; a mismatch between the admission's event and the gate's event is rejected with `ERR_ATTENDEE_EVENT_MISMATCH`.

An accepted scan moves the admission from `ISSUED` — or from `TRANSFERRED` — to `CHECKED_IN`, stamps its `checked_in_at` with the current time, and writes an immutable scan record capturing `attendee_id`, `event_id`, `gate_code`, the `scanned_at` instant, and the `scanned_by_user_id` of the operator who performed it. The event's `checked_in_count` is recomputed. The owning order's fulfilment status is then re-derived by the system rather than set by hand: an order moves from `ISSUED` to `CHECKED_IN_PARTIAL` when at least one of its admissions is `CHECKED_IN` while at least one remains `ISSUED`, and from `CHECKED_IN_PARTIAL` to `CHECKED_IN_FULL` when every one of its non-voided admissions is `CHECKED_IN`. Each such re-derivation increments the order's `version` by 1, and only when the derived target actually differs from the order's stored fulfilment. Re-derivation touches only orders already sitting in `ISSUED`, `CHECKED_IN_PARTIAL` or `CHECKED_IN_FULL` — an order in `HELD`, `EXPIRED` or `VOIDED` is left alone — it ignores `VOIDED` admissions entirely when counting, and it makes no change at all when every admission of the order has been voided. Scan records may be read individually — an unresolvable one yields `ERR_SCAN_NOT_FOUND` — and listed with optional `attendee_id` and `event_id` filters.

Mistakes at the gate are reversible. Undoing a check-in returns an admission from `CHECKED_IN` to `ISSUED` and is permitted only from `CHECKED_IN`, else `ERR_ATTENDEE_NOT_ISSUED`. `GateStaff` may undo any admission, since that role is opaque and owns nothing; an `Organizer` may undo only on an event it owns. It clears `checked_in_at` back to null, recomputes the event's `checked_in_count`, and re-derives the owning order's fulfilment in the opposite direction: from `CHECKED_IN_FULL` back to `CHECKED_IN_PARTIAL` when, after the undo, at least one admission is `ISSUED` and at least one remains `CHECKED_IN`, and from `CHECKED_IN_PARTIAL` back to `ISSUED` when, after the undo, no admission of that order is `CHECKED_IN` any longer. Each such re-derivation increments the order's `version` by 1. The full fulfilment cycle `ISSUED → CHECKED_IN_PARTIAL → CHECKED_IN_FULL → CHECKED_IN_PARTIAL → ISSUED` may repeat without bound, as may the admission's own `ISSUED → CHECKED_IN → ISSUED` cycle.

Voiding is the organiser's blunt instrument, and it is one-way. An admission in `ISSUED`, `CHECKED_IN` or `TRANSFERRED` status may be voided with an optional `reason`, provided its event is not yet `COMPLETED`; an attempt once the event is `COMPLETED` is rejected with `ERR_INVALID_EVENT_TRANSITION`, and that check runs before the already-voided guard, so voiding twice on a completed event reports the event rather than the ticket. Any of the three source states produces identical consequences: the tier's `sold_count` falls by 1, and when the admission carried a non-null `seat_block_id` the block's `seats_taken` also falls by 1, returning that exact seat to the pool; `checked_in_at` is cleared back to null; the event's `issued_count` and `checked_in_count` are both recomputed. Voiding deliberately does **not** re-derive the owning order's `fulfillment_status`, so an order whose only checked-in admission is voided keeps whatever fulfilment it already held. `VOIDED` is terminal for an admission, and a further void attempt is rejected with `ERR_TICKET_VOIDED`. Admissions are readable individually — `ERR_ATTENDEE_NOT_FOUND` when unresolvable — and listable with optional `order_id`, `order_item_id`, `ticket_type_id`, `event_id`, `buyer_id`, `seat_block_id` and `status` filters.

### 3.6. Passing a Ticket On: Transfers

Plans change, and a holder who cannot attend should be able to hand the seat to a friend rather than seek a refund. A transfer offer is opened by the current holder naming the `attendee_id` of the admission and the `to_email` address the offer is aimed at. The offer is created in `DRAFT` status, records `from_buyer_id` as the holder at the moment of creation, and leaves `to_buyer_id` null, `offer_expires_at` null and `resend_count` at zero. An offer may not be opened against an admission that has been voided — that is `ERR_TICKET_VOIDED` — nor against one outside `ISSUED` or `TRANSFERRED` status, which is `ERR_ATTENDEE_NOT_ISSUED`. The event's own status is not consulted when an offer is merely opened; only sending it is gated on the event.

Sending the offer moves it from `DRAFT` to `SENT`. Sending is permitted only while the offer is in `DRAFT` or `DECLINED`, only while the underlying admission is in `ISSUED` or `TRANSFERRED`, and only while the event is in `ONSALE`, `PAUSED` or `SALES_CLOSED`. It sets `offer_expires_at` to seventy-two hours after the current time. A wrong source status is rejected with `ERR_INVALID_TRANSFER_STATE`; an event outside those three statuses is rejected with `ERR_EVENT_NOT_ONSALE`; and the caller must be either the admission's current holder or the buyer recorded as `from_buyer_id` — any other buyer is rejected with `ERR_UNAUTHORIZED`.

The recipient decides. Accepting takes the offer from `SENT` to `ACCEPTED` and requires the offer to be in `SENT`, the current time to be strictly before `offer_expires_at`, and the accepting buyer's `email` to equal the offer's `to_email`. The accepting buyer is supplied as `to_buyer_id` on the call and is recorded on the offer under the same name. The linked admission then moves to `TRANSFERRED`: its `buyer_id` becomes the accepting buyer, its `holder_email` becomes that buyer's email, and it remains scannable exactly as an `ISSUED` admission is. Declining takes the offer from `SENT` to `DECLINED`, likewise identifies the responding buyer with `to_buyer_id` and likewise requires that buyer's `email` to equal `to_email`, and clears `offer_expires_at` back to null. Accepting, by contrast, leaves `offer_expires_at` standing rather than clearing it, and re-checks neither the event's status nor the admission's. On either call the responding buyer must resolve — `ERR_BUYER_NOT_FOUND` when it does not — and a responding buyer whose `email` does not equal the offer's `to_email` is rejected with `ERR_UNAUTHORIZED` (HTTP 403), a check that precedes the source-status check. `ACCEPTED` is terminal.

A declined offer is not dead. Sending it again returns it from `DECLINED` to `SENT`, sets a fresh `offer_expires_at` seventy-two hours ahead of the current time, and increments `resend_count` by 1 — that counter records precisely how many times an offer has re-entered `SENT` after a decline. The `SENT → DECLINED → SENT` cycle may repeat without bound.

Expiry is evaluated lazily and destructively. An accept or a decline attempted at or after `offer_expires_at` finds the offer in `SENT` but past its deadline: the offer is moved to `EXPIRED` and the triggering call is itself rejected with `ERR_TRANSFER_TTL_EXPIRED`. `EXPIRED` is terminal, so a lapsed offer cannot be revived — the holder must open a new one. Transfer offers are readable individually, yielding `ERR_TRANSFER_REQUEST_NOT_FOUND` when unresolvable, and listable with optional `attendee_id`, `from_buyer_id`, `to_buyer_id` and `status` filters.

### 3.7. Overflow Demand: The Waitlist

A waitlist exists to capture demand that arrives after inventory is gone, and the platform is strict about that premise: a buyer may only join the queue for a tier that is *exactly* exhausted. Joining names the `ticket_type_id`, the joining `buyer_id`, and a `requested_quantity` between 1 and 10 inclusive. If the tier's available quantity is greater than zero at that moment, the request is rejected with `ERR_CAPACITY_AVAILABLE` — the buyer should simply buy. The event's own status is not consulted when joining — only the tier's availability is. The entry is created in `WAITING` status with `claimed_order_id`, `offered_at` and `offer_expires_at` all null.

Capacity is handed back to the queue by an organiser-run sweep on a tier, and the sweep does two things in a fixed order. First it retires stale offers: every entry on the tier in `OFFERED` status whose `offer_expires_at` is at or before the current time is moved to `EXPIRED`, and the tier's `held_count` is decremented by that entry's `requested_quantity`. Only after those releases have landed does the sweep compute the tier's now-current available quantity and begin offering. Candidates are the entries still in `WAITING`, ranked by `created_at` ascending and tie-broken by `requested_quantity` ascending, and each candidate is offered only if its `requested_quantity` is less than or equal to the sweep's remaining capacity — a candidate too large for what remains is skipped rather than partially served, and a smaller candidate behind it may still be reached. Offering an entry moves it `WAITING → OFFERED`, sets `offered_at` to the current time and `offer_expires_at` to twenty-four hours later, and increases the tier's `held_count` by the entry's `requested_quantity`, which is what stops the offered inventory from being bought out from under the queue. The sweep reports the `ticket_type_id` it ran on, the `expired_entry_ids` it retired, the `offered_entry_ids` it served, the `offered_count` of entries offered, and the `remaining_available` capacity left over.

Claiming converts an offer into a real checkout. It moves the entry `OFFERED → CLAIMED` and requires the entry to be in `OFFERED` — else `ERR_INVALID_WAITLIST_STATE` — the current time to be strictly before `offer_expires_at` — else `ERR_WAITLIST_OFFER_EXPIRED` — and the event to be `ONSALE`, else `ERR_EVENT_NOT_ONSALE`. It creates an order for the waiting buyer carrying a single general-admission line on the waited tier with `quantity` equal to the entry's `requested_quantity`, opened in `HELD` fulfilment and `PENDING` payment exactly like any other checkout, and records that order's identifier on the entry as `claimed_order_id`. The event's `version` is incremented by 1. The claim is still subject to the capacity boundaries of §2.9 and to the ten-ticket-per-buyer-per-event ceiling, so it can be rejected with `ERR_SOLD_OUT`, `ERR_INSUFFICIENT_CAPACITY` or `ERR_TICKET_LIMIT_EXCEEDED`. Those checks fire in the order event status, entry status, offer expiry, per-buyer ceiling, then capacity; and the availability the claim is measured against excludes the claiming entry's own offered hold, so an offer sized exactly to the inventory it is holding always fits. Every offer expiry on this path is evaluated against the entry's stored `offer_expires_at`, and an entry in `OFFERED` whose deadline is null is treated as expired. `CLAIMED` is terminal.

A buyer whose offer lapsed is not sent to the back of the queue. Requeuing returns an entry from `EXPIRED` to `WAITING`, requires the entry to be in `EXPIRED` — checked first, else `ERR_INVALID_WAITLIST_STATE` — and then the event to be in `ONSALE` or `PAUSED`, any other status being rejected with `ERR_EVENT_NOT_ONSALE`, and clears both `offered_at` and `offer_expires_at` back to null. The restored entry re-enters the candidate pool ranked by its **original** `created_at`, not by the instant of the requeue — seniority in the queue survives a missed offer. The `WAITING → OFFERED → EXPIRED → WAITING` cycle may repeat without bound. Waitlist entries are readable individually, yielding `ERR_WAITLIST_ENTRY_NOT_FOUND` when unresolvable, and listable with optional `ticket_type_id`, `buyer_id`, `claimed_order_id` and `status` filters.

### 3.8. Unwinding Money: Refunds and Event Cancellation

A refund request is opened by either the buyer or the organiser against a paid order, naming the `order_id`, a non-empty `item_refunds` array, a free-text `reason` that is required though it may be the empty string, and an optional `policy`. Each entry of `item_refunds` names an `order_item_id` and the `quantity` of tickets on that line to be refunded; a line named that does not resolve yields `ERR_ORDER_ITEM_NOT_FOUND`, and so does a line that resolves but belongs to some other order. The `policy` chooses the calculation variant and accepts `FEE_RETAINED` or `FEE_INCLUDED`; when omitted it defaults to the `refund_policy` declared on the order's event. The request is created in `REQUESTED` status with `settled_at` null.

Three gates guard the opening. The order's `payment_status` must be `PAID`, `REFUND_PENDING` or `PARTIALLY_REFUNDED`, else `ERR_ORDER_NOT_PAID`. The refund window must be open: the current time must be strictly before thirty days after the order's `paid_at`, **and** strictly before the event's `starts_at` — a refund cannot be opened once the show has begun, however recent the purchase. A failure of either condition is `ERR_REFUND_WINDOW_CLOSED`, as is an order carrying a null `paid_at`, which has no window to be inside. And the quantities must fit: for each entry of `item_refunds`, its `quantity` may not exceed the owning line's `quantity` minus the quantity already covered by settled refund requests on that same line, else `ERR_REFUND_EXCEEDS_ORDER`.

Approval by the owning organiser moves the request `REQUESTED → APPROVED` and requires the request to be in `REQUESTED` — else `ERR_INVALID_REFUND_STATE` — and the order's `payment_status` to still be `PAID`, `REFUND_PENDING` or `PARTIALLY_REFUNDED`. Approval is where the money is computed, from the request's own stored `policy` and the event's `fee_mode` as it stands at that moment. Start by summing, over the entries of `item_refunds`, the owning line's `unit_price_cents` multiplied by that entry's `quantity`; call that the refunded face. Sum likewise the owning line's `per_ticket_fee_cents` multiplied by that entry's `quantity`; call that the refunded fee. Then prorate the order's discount: take the order's `discount_cents`, multiply by the refunded face, divide by the order's `subtotal_cents`, and round that single result half up to a whole cent — this is the only rounding step in the whole refund calculation.

The two policies then diverge, and each is stated in full. Under `FEE_RETAINED`, `refund_amount_cents` is the refunded face minus the prorated discount, `platform_retained_cents` is the whole refunded fee, and `organizer_charged_cents` is the refunded face minus the prorated discount. Under `FEE_INCLUDED`, `refund_amount_cents` is the refunded face minus the prorated discount plus the refunded fee, `platform_retained_cents` is 0, and `organizer_charged_cents` is the refunded face minus the prorated discount plus the refunded fee. The practical difference under a pass-on event is that a `FEE_INCLUDED` refund returns strictly more to the buyer than a `FEE_RETAINED` refund would for identical inputs, because the platform hands its own fee back.

An event on `ABSORB` fee mode shifts that picture, because the buyer never paid the fee in the first place. There, `refund_amount_cents` is the refunded face minus the prorated discount under **both** policies. The two policies differ only in the other two figures: `platform_retained_cents` is the refunded fee under `FEE_RETAINED` and 0 under `FEE_INCLUDED`, while `organizer_charged_cents` is the refunded face minus the prorated discount under `FEE_RETAINED`, and that same value minus the refunded fee under `FEE_INCLUDED` — the platform hands the fee back to the organiser rather than to the buyer.

Rejection is the other branch out of `REQUESTED`. It moves the request `REQUESTED → REJECTED`, accepts an optional `reason`, requires the request to be in `REQUESTED`, and sets `refund_amount_cents`, `platform_retained_cents` and `organizer_charged_cents` all to 0. `REJECTED` is terminal.

Settlement is reserved for the finance desk and is where the cascade fires. It moves an `APPROVED` request to `SETTLED` — any other source status is `ERR_INVALID_REFUND_STATE` — and runs four hops in order. The first hop sets the request's status to `SETTLED` and stamps `settled_at` with the current time. The second hop, caused by the first, increases the order's `refunded_cents` by the request's `refund_amount_cents` and advances the order's payment dimension: when the accumulated `refunded_cents` now equals the order's `buyer_total_cents` **exactly** the order becomes `REFUNDED`, and on any other total — including one that overshoots the buyer total — it becomes `PARTIALLY_REFUNDED`; an order that reaches `REFUNDED` from `PAID` additionally has its `fulfillment_status` set to `VOIDED`, and an order sitting in `REFUND_PENDING` likewise reaches `REFUNDED` only on the settlement that brings `refunded_cents` up to `buyer_total_cents` exactly. The same hop voids the admissions named by `item_refunds` — for each entry, the first `quantity` of that line's still-live admissions taken in `created_at` order — releasing their seats by decrementing the relevant seat blocks' `seats_taken` and the relevant tiers' `sold_count`, and increases the organiser's `lifetime_refunds_cents` by the request's `organizer_charged_cents` while incrementing that organiser's `version` by 1. The third hop, caused by the order's refund figures moving, finds the payout whose `event_id` matches the order's event and whose status is `ACCRUING` or `ELIGIBLE`, and recomputes its `gross_cents`, `refunds_cents`, `platform_fee_cents`, `reserve_basis_cents`, `reserve_cents` and `net_amount_cents` using its frozen `reliability_score_snapshot`. The fourth hop, caused by that recompute, sets that payout's status to `ON_HOLD` whenever the recomputed `net_amount_cents` is below zero — a clawback that exceeds the accrual freezes the settlement rather than paying out a negative sum. Nothing in the cascade refreshes the *event's* own `gross_cents` or `refunds_cents` roll-ups; those two stay where the last completion left them until the event is completed again. Refund requests are readable individually — `ERR_REFUND_REQUEST_NOT_FOUND` when unresolvable — and listable with optional `order_id` and `status` filters.

Cancelling an event is the same unwinding performed wholesale, and it is a five-hop cascade. The first hop sets the event's `status` to `CANCELLED` and increments its `version` by 1. The second hop, caused by the first, sweeps the event's orders: every order whose `fulfillment_status` is `HELD`, `ISSUED`, `CHECKED_IN_PARTIAL` or `CHECKED_IN_FULL` is set to `VOIDED` fulfilment, and every such order whose `payment_status` is `PAID` is additionally set to `REFUND_PENDING`. The third hop, caused by those orders being voided, sets every admission belonging to them whose status is `ISSUED` or `CHECKED_IN` to `VOIDED`. The fourth hop, caused by those admissions being voided, gives the inventory back: for each voided admission carrying a non-null `seat_block_id`, the block's `seats_taken` falls by 1 and the tier's `sold_count` falls by 1. The fifth hop, caused by the orders entering `REFUND_PENDING`, opens the money return: for each such order a refund request is created already in `APPROVED` status with `policy` of `FEE_INCLUDED`, with `item_refunds` covering every line of that order at its full remaining quantity, and with `refund_amount_cents`, `platform_retained_cents` and `organizer_charged_cents` computed by the refund calculation above, with `settled_at` null and with `reason` set to the fixed string `Event cancelled`. Separately, every waitlist entry in `WAITING` or `OFFERED` status on any tier of the cancelled event is set to `EXPIRED`. Cancelling from `DRAFT` performs only the first hop and the waitlist expiry, since there is nothing sold to unwind; cancelling from `ONSALE`, `PAUSED` or `SALES_CLOSED` runs the identical five-hop cascade in each case.

### 3.9. Settlement: Reliability, Payouts, the Rolling Reserve and Reporting

Before any money leaves the platform, the organiser is scored. The reliability score is a weighted blend over the organiser's *qualifying* events — those the organiser owns whose status is `COMPLETED` or `CANCELLED`. For each qualifying event, three ingredients are formed. Its refund rate is its `refunds_cents` divided by its `gross_cents`, or zero when `gross_cents` is zero. Its check-in rate is its `checked_in_count` divided by its `issued_count`, or zero when `issued_count` is zero. Its cancellation flag is 1 when the event's status is `CANCELLED` and 0 otherwise. The event's score is 100 multiplied by the sum of three weighted terms: 0.45 times one minus the refund rate, plus 0.35 times the check-in rate, plus 0.20 times one minus the cancellation flag. The organiser's score is the arithmetic mean of the event scores across the variant's input set, rounded half up exactly once to a whole integer between 0 and 100. When the organiser has no qualifying events at all, the score is 75 by default rather than computed.

Two variants exist over the same formula, selected by an optional `variant` query parameter on the reliability read. `LIFETIME` — the default when the parameter is omitted — averages over every qualifying event. `TRAILING` averages over only the two most recently ended qualifying events, ordered by `ends_at` descending and tie-broken by `created_at` descending, which is why an organiser with one bad recent event scores strictly lower on `TRAILING` than on `LIFETIME`. The read reports `organizer_id`, the `variant` applied, the resulting `score`, and the `events_counted` that fed the mean — zero when the default 75 was used. A `variant` that is neither of those two strings is rejected with `ERR_INVALID_REQUEST`; the rounded mean is finally clamped into the 0–100 range; and the read carries no ownership check, so any permitted role may read any organiser's score.

A payout is opened by a finance officer naming the `organizer_id` to be paid, the `event_id` being settled, and the `expected_organizer_version` guard of §2.7. The event's sales must already be finished — its status must be `SALES_CLOSED` or `COMPLETED` — and an attempt at any earlier status is rejected with `ERR_INVALID_EVENT_TRANSITION`. The payout opens in `ACCRUING` status, freezes `reliability_score_snapshot` from the organiser's `TRAILING` reliability score at that instant, sets `reserve_release_at` to ninety days after the event's `ends_at`, opens `reserve_released_cents` at zero with `approved_by_user_id` and `released_by_user_id` both null, increments the organiser's `version` by 1, and computes the settlement chain. Three latitudes are left open here on purpose: the named `event_id` is not required to belong to the named `organizer_id`, nothing prevents a second payout being opened against an event that already has one, and the `expected_organizer_version` guard — despite §2.8 placing optimistic concurrency last — is evaluated on this endpoint immediately after the event-status check, so a stale version against a still-selling event reports `ERR_INVALID_EVENT_TRANSITION`.

That chain runs in seven pinned steps with no back-propagation. Step one sets `gross_cents` to the sum of `organizer_gross_cents` across the orders on the payout's event whose `payment_status` is `PAID`, `REFUND_PENDING`, `PARTIALLY_REFUNDED` or `REFUNDED` — orders still pending payment or expired without payment contribute nothing. Step two sets `refunds_cents` to the sum of `organizer_charged_cents` across the settled refund requests on orders of the same event. Step three sets `platform_fee_cents`: on an event whose `fee_mode` is `ABSORB` it is the sum of `fee_total_cents` over the same orders as step one, and on any other event it is 0, because a pass-on event has already collected its fee from the buyer. Step four sets `reserve_basis_cents` to `gross_cents` minus `refunds_cents` minus `platform_fee_cents`. Step five selects `reserve_rate` from the frozen `reliability_score_snapshot` on a four-rung ladder: a snapshot of at least 90 withholds nothing at all, a rate of 0.00; at least 70 but below 90 withholds 0.05; at least 50 but below 70 withholds 0.10; and anything below 50 withholds 0.20. Step six sets `reserve_cents` to the greater of zero and the reserve rate multiplied by `reserve_basis_cents`, rounded half up to a whole cent — the only rounding in the chain. Step seven sets `net_amount_cents` to `reserve_basis_cents` minus `reserve_cents`. The rate chosen in step five is itself exposed on the payout as `reserve_rate`, a fractional number rather than a cent amount, alongside the six cent figures the chain produces.

The apparent circularity in that chain is resolved deliberately: the reserve rate depends on a reliability score that is itself derived from the same refund data feeding step two. The cycle is broken by freezing `reliability_score_snapshot` at payout creation and never recomputing it. Later settled refunds move steps two, four, six and seven, but step five is immovable for the life of the payout.

Marking a payout eligible moves it `ACCRUING → ELIGIBLE` and recomputes the whole seven-step chain. Three preconditions apply beyond the source status: the event must be `COMPLETED` and the recomputed `net_amount_cents` must be at least zero, a failure of either being `ERR_PAYOUT_NOT_ELIGIBLE`; and no refund request on any order of the event may still be sitting in `REQUESTED` or `APPROVED`, a failure being `ERR_PAYOUT_PENDING_REFUNDS`. Those three preconditions are themselves ordered: source status first, then the event-completed and non-negative-net pair, then the pending-refund sweep, and the recomputed chain is written back onto the payout only when all three pass. A payout in `ACCRUING` or `ELIGIBLE` may be frozen to `ON_HOLD` with an optional `reason`, which freezes both approval and release and recomputes nothing; the settlement cascade of §3.8 drives the same transition automatically when a recompute pushes `net_amount_cents` below zero. Resuming returns a payout from `ON_HOLD` to `ELIGIBLE`, requires `net_amount_cents` to be at least zero — else `ERR_PAYOUT_NOT_ELIGIBLE` — and recomputes the full chain. The `ELIGIBLE → ON_HOLD → ELIGIBLE` cycle may repeat without bound. A wrong source status on any payout transition is reported as `ERR_INVALID_PAYOUT_STATE`.

Approval moves an `ELIGIBLE` payout to `APPROVED`, requires the payout's already-stored `net_amount_cents` to be at least zero — approval recomputes no part of the chain, and a negative figure is rejected with `ERR_PAYOUT_NOT_ELIGIBLE` — and records the acting operator's identifier as `approved_by_user_id`. Release moves an `APPROVED` payout to `RELEASED` and records the acting operator as `released_by_user_id` — but only if that operator differs from the one recorded in `approved_by_user_id`. One person may not both approve and release the same payout; an attempt is rejected with `ERR_SOD_SAME_ACTOR` (HTTP 403). `RELEASED` is terminal.

The withheld reserve is paid out separately and only once it has matured. Releasing the reserve requires the current time to be at or after `reserve_release_at` — the ninety-day mark past the event's end — and an earlier attempt is rejected with `ERR_RESERVE_NOT_MATURED`. The release sets `reserve_released_cents` equal to `reserve_cents`. Maturity is the only gate on it: the reserve release is permitted from any payout status, does not itself move that status, and may be repeated, each call simply re-copying the current `reserve_cents` and advancing the payout's `version`. Payouts are readable individually, yielding `ERR_PAYOUT_NOT_FOUND` when unresolvable, and listable with optional `organizer_id`, `event_id` and `status` filters.

Finally, organisers get a reporting roll-up on any of their events, and only on their own: an `Organizer` asking after an event it does not own is rejected with `ERR_UNAUTHORIZED`. It reports the `event_id`; a `tickets_sold_count` counting the event's admissions in `ISSUED`, `CHECKED_IN` or `TRANSFERRED` status; a `checked_in_count` counting those in `CHECKED_IN`; a `voided_count` counting those in `VOIDED`; the event's `gross_cents` and `refunds_cents` as stored; a `net_to_organizer_cents` equal to `gross_cents` minus `refunds_cents`; a `check_in_rate` equal to `checked_in_count` divided by `tickets_sold_count`, expressed as a number with exactly four decimal places rounded half up, and reported as zero when `tickets_sold_count` is zero; and a `waitlist_depth` counting the waitlist entries still in `WAITING` across every tier of the event.
