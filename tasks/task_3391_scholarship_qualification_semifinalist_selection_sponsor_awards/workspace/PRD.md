# Merit Scholarship Awards API — Product Requirements Document

## 1. Introduction

Every year, a national scholarship program must turn a vast field of preliminary examination results into a defensible, auditable roster of semifinalists, finalists, and ultimately scholarship recipients — while honoring state-by-state fairness, sponsor-imposed eligibility criteria, and strict publicity embargoes. This document specifies the Merit Scholarship Awards API, the system of record for that pipeline. It administers a competition cycle from initial configuration through entry intake, examination scoring, semifinalist selection, finalist review, award matching, disbursement, and renewal verification.

The program's funding model is tripartite. A fixed number of single-payment national awards is funded directly by the program in each cycle. Corporate sponsors fund awards — typically reserved for the children of their employees — through per-cycle agreements that carry their own eligibility criteria, award amounts, and funding pools. College institutions fund renewable multi-year awards for finalists who name the institution as their first choice. Because money, reputations, and regulatory exposure are all at stake, every deadline, embargo, and scheduled payment in this system is evaluated against a controllable logical clock rather than wall-clock time, and every mutating workflow is guarded by explicit posture, ownership, and optimistic-concurrency checks.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

All requests must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the principal's role. A request missing either header, or presenting a role the system does not declare, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other check runs — even before path identifiers are resolved. A request whose role is declared but not listed for the target endpoint is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

Five roles exist, spelled exactly as follows:

- `ProgramAdmin` — the national program operator: runs cycles, scoring, selection, finalist review, award matching, disbursement release, renewal decisions, notification release, and the logical clock. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any entity's `id`.
- `SchoolOfficial` — an official of a registered school, who endorses finalist applications of that school's students only. When `X-User-Role` is `SchoolOfficial`, `X-User-ID` is the `id` of the acting `School`; ownership checks on endorsement compare the student's `school_id` against `X-User-ID`, and a mismatch is rejected with `ERR_ENDORSEMENT_SCHOOL_MISMATCH` (HTTP 403).
- `Student` — an entrant or scholarship recipient acting only on their own records. When `X-User-Role` is `Student`, `X-User-ID` is the `id` of the acting `Student`; ownership checks on any resource that references a `Student` compare the resource's `student_id` field to `X-User-ID`, and a mismatch is rejected with `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403).
- `SponsorAdmin` — administrator of one corporate sponsor, defining and amending that sponsor's agreements while the program administers the awards themselves. When `X-User-Role` is `SponsorAdmin`, `X-User-ID` is the `id` of the acting `CorporateSponsor`; it is compared to an agreement's `sponsor_id` or to the sponsor identifier in the request path, and a mismatch is rejected with `ERR_FORBIDDEN_OWNERSHIP`.
- `CollegeAdmin` — administrator of one college institution, submitting renewal verifications for awards funded by that institution; decisions on those verifications belong to the program (segregation of duties). When `X-User-Role` is `CollegeAdmin`, `X-User-ID` is the `id` of the acting `CollegeInstitution`; it is compared to an award's `college_id`. When an award's `college_id` is null — national or corporate awards — any `CollegeAdmin` passes this ownership check and instead hits the renewability state gate described in §3.8.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two optional query parameters: `limit` (default 10, minimum 1, maximum 100) and `offset` (default 0). List responses carry the pagination fields `limit`, `offset`, `total_count`, and `has_more` in the `meta` object. Unless an endpoint states otherwise, list results are sorted by `created_at` in ascending order. Three endpoints override the default sort: a cycle's state allocations are returned sorted by `state_code` ascending, an award's disbursements sorted by `term_index` ascending, and a student's notifications sorted by `sequence_number` ascending.

### 2.4. Resource Identity, Timestamps, and Versioning

Every persisted resource carries a server-minted `id`: a UUID with no type prefix. Most resources additionally carry `created_at` and `updated_at` timestamps — ISO 8601 UTC with three fractional digits — and an integer `version` that starts at 1 on creation and increments by exactly 1 on every mutation of that resource. `created_at` and `updated_at` are audit metadata only; they must never drive a business decision. The single exception to the full common-field set is `School`, which carries only `id` and `created_at` — both `updated_at` and `version` are absent from schools.

### 2.5. The Logical Clock

The system maintains a logical clock that is the sole source of "now" for every deadline, embargo, scheduled date, and sweep; wall-clock time is never consulted for business decisions. Before any operator intervention, the logical clock starts at exactly 2026-09-01T00:00:00Z. A `ProgramAdmin` advances it through an admin-only clock-setting capability that takes a `to_iso8601` instant. The clock is monotonic: setting it to an instant less than or equal to the current value is rejected with `ERR_CLOCK_REGRESSION` (HTTP 422). A successful advance performs two side effects and nothing else — it sweeps every still-`OFFERED` award whose `acceptance_deadline` has passed to `EXPIRED` (running the full release cascade of §3.8), and it re-evaluates the cycle-completion bubble-up of §3.8. The clock never releases notifications and never releases disbursements; both are manual actions. The capability returns the new `current_utc` together with the `expired_offer_ids` of the offers swept by that advance.

### 2.6. Monetary Representation, Precision, and Rounding

All monetary amounts are integer cents — `award_amount_cents`, `pool_total_cents`, `amount_cents`, and the pool ledger fields are exact integers with no fractional part, and all pool arithmetic is exact integer arithmetic. Where division is unavoidable, the system rounds half up: apportionment quotas are stored to 4 decimal places rounded half up, provisional slot counts are whole-slot roundings (half up) of those quotas, and per-term disbursement amounts are rounded half up for every term except the final one, which absorbs the remainder so the schedule sums exactly to the award's `amount_cents` (§3.8). The selection index and all threshold comparisons are exact integer arithmetic over integers.

### 2.7. Optimistic Concurrency Control

Two write operations are guarded by optimistic concurrency control; endpoints not listed here do not take a version field.

- Amending a sponsor agreement requires the request to carry `expected_sponsor_agreement_version`, holding the agreement's `version` as the client last observed it. If the agreement's current `version` has advanced since that read — for example because another amendment already superseded the agreement under the sponsor's administration of its own awards, or a matching or pool cascade mutated it — the amendment is rejected with `ERR_STALE_VERSION` (HTTP 412), preventing the client from overwriting an agreement state it has not observed.
- Reviewing a finalist application requires the request to carry `expected_finalist_application_version`, holding the application's `version` as the reviewer last observed it. If the application's `version` has advanced since that read — a school endorsement or a resubmission landing after the reviewer's read — the review is rejected with `ERR_STALE_VERSION` (HTTP 412), so no decision rests on stale requirement state.

### 2.8. Validation Order and Error Precedence

When several checks could reject the same request, the server evaluates them in a fixed priority order so that the surfaced error is deterministic:

1. Authentication first — `ERR_UNAUTHENTICATED` — before anything else, even when the path identifier does not exist.
2. Role authorization — `ERR_FORBIDDEN_ROLE` when the declared role is not listed for the endpoint.
3. Ownership — `ERR_FORBIDDEN_OWNERSHIP` for student-, sponsor-, and college-backed identity mismatches; `ERR_ENDORSEMENT_SCHOOL_MISMATCH` for school endorsement mismatches.
4. Existence — path identifiers resolve left to right and a missing one yields `ERR_NOT_FOUND` (HTTP 404); identifiers referenced in the request body (`student_id`, `cycle_id`, `entry_id`, `school_id`, `first_choice_college_id`, `parent_sponsor_id`) must exist, and a missing referenced identifier yields `ERR_INVALID_REQUEST` (HTTP 400) rather than 404.
5. Optimistic concurrency — `ERR_STALE_VERSION` on the two OCC-guarded writes of §2.7.
6. State gates — the cycle posture gates `ERR_CYCLE_NOT_ACCEPTING_ENTRIES`, `ERR_CYCLE_NOT_CLOSED_FOR_SCORING`, `ERR_CYCLE_POSTURE_INVALID`, `ERR_UNSCORED_ENTRIES_REMAIN`, `ERR_PENDING_APPLICATIONS_REMAIN`, and `ERR_MATCHING_ALREADY_RUN`, and the entity state preconditions `ERR_INVALID_STATE`, `ERR_AWARD_NOT_OFFERED`, `ERR_DISBURSEMENT_HELD`, and `ERR_NOT_RENEWABLE`.
7. Business constraints — duplicates and uniqueness (`ERR_DUPLICATE_ENTRY`, and the duplicate-application rejection as `ERR_INVALID_REQUEST`), entry eligibility (`ERR_ENTRY_INELIGIBLE`), semifinalist standing (`ERR_ENTRY_NOT_SEMIFINALIST`, evaluated before the duplicate-application check), finalist requirements (`ERR_APPLICATION_INCOMPLETE`, `ERR_CONFIRMING_SCORE_BELOW_FLOOR`), renewal sequencing (`ERR_RENEWAL_ALREADY_EXISTS`) and renewal criteria (`ERR_RENEWAL_CRITERIA_UNMET`), and notification sequencing (`ERR_NOTIFICATION_SEQUENCE_VIOLATION`).
8. Temporal rules — `ERR_APPLICATION_WINDOW_CLOSED`, `ERR_AGREEMENT_WINDOW_OVERLAP`, `ERR_DISBURSEMENT_NOT_DUE`, `ERR_NOTIFICATION_EMBARGOED`, `ERR_PUBLICITY_WINDOW_TOO_EARLY`, and `ERR_CLOCK_REGRESSION`.
9. The fiscal guard — `ERR_POOL_BELOW_COMMITTED` on agreement amendment.
10. Field-shape validation last — missing required fields, invalid enum members, out-of-range numbers (section scores 8–38, GPA 0.0–4.0, confirming index 48–228, monetary amounts greater than 0), and unordered dates (start strictly before end): all `ERR_INVALID_REQUEST` (HTTP 400), checked last so domain errors surface first.

### 2.9. Path Resolution and Nested Resource Retrieval

Nested URLs resolve their path parameters left to right: the cycle, school, student, entry, application, sponsor, agreement, college, award, disbursement, renewal, or notification identifier nearest the root is validated first, and the first identifier that fails to resolve produces `ERR_NOT_FOUND` (HTTP 404) before any state or business check runs. A child resource is reachable only through its own parent chain; an identifier that exists but belongs to a different parent is treated as not found on that path.

## 3. Business Logic & Workflows

### 3.1. Competition Cycles: Configuration and Posture Progression

A competition cycle is the aggregate root of everything the program does for one scholarship year. A `ProgramAdmin` creates one with a human label (`name`, for example "2028 Competition"), the `target_graduation_year` entrants must declare, the `total_semifinalist_slots` to be apportioned across states (at least 1), the national bucket configuration — `national_award_slots` (zero or more; a value of 0 disables the national bucket entirely) and `national_award_amount_cents` per recipient (greater than 0) — the `confirming_floor` (the minimum confirming-examination selection index required for finalist confirmation, an integer from 48 to 228 inclusive), the `application_deadline`, and four per-notice-type embargo instants: `semifinalist_embargo_until`, `finalist_embargo_until`, `award_embargo_until`, and `public_embargo_until`. The same creation call carries `state_populations`, and one `StateAllocation` child is created per entry in it — recording the state's `state_code`, its projected `graduating_population` (zero or more), and its owning `cycle_id`, starting in `PENDING` status. The count of states with a population greater than zero may not exceed `total_semifinalist_slots`, so the guaranteed minimum slot per populated state remains fundable at final apportionment. A new cycle starts in `SETUP` posture with `matching_run` false and `version` 1.

Posture is destiny here: the cycle's `status` gates every child workflow, and each posture change is an explicit `ProgramAdmin` action. Opening entries moves `SETUP` → `ENTRY_OPEN`; attempted from any other posture it is `ERR_INVALID_STATE`. Closing entries moves `ENTRY_OPEN` → `ENTRY_CLOSED` — again `ERR_INVALID_STATE` from any other posture — and triggers the provisional apportionment of §3.2. Running semifinalist selection moves `ENTRY_CLOSED` → `SEMIFINALISTS_SELECTED` (§3.4). Publishing finalists moves `SEMIFINALISTS_SELECTED` → `FINALISTS_SELECTED` (§3.5). Award matching is a self-transition: the posture stays `FINALISTS_SELECTED` while `matching_run` flips to true, and it may run exactly once per cycle — a second attempt is rejected with `ERR_MATCHING_ALREADY_RUN` (HTTP 409). Finally, once matching has run and no award of the cycle remains live and no disbursement remains pending, the cycle bubbles up to `AWARDS_COMPLETED` on its own, as §3.8 details. Every posture transition increments the cycle's `version` by 1.

### 3.2. Apportioning Semifinalist Slots to the States

Closing entries is the moment the cycle learns its provisional shape. For every `StateAllocation` of the cycle the server computes `quota_raw`: the cycle's `total_semifinalist_slots` multiplied by that state's `graduating_population` and divided by the sum of `graduating_population` across all of the cycle's states — an exact rational quotient, stored rounded half up to 4 decimal places. The provisional variant of the allocation then sets each state's `slots_provisional` to its `quota_raw` rounded half up to a whole slot and flips the allocation `PENDING` → `PROVISIONAL`, incrementing the allocation's `version`. The provisional sum across states may exceed or fall short of `total_semifinalist_slots`; it drives no selection decisions and is informational until the final run.

Semifinalist selection computes the final variant — the only allocation that selects students. Each state's base is, when its `graduating_population` is greater than zero, the larger of the minimum state guarantee `MIN_STATE_SLOTS` (exactly 1) and its `quota_raw` rounded down to a whole slot; states with zero population take a base of 0. The remainder — `total_semifinalist_slots` minus the sum of the bases — is then distributed one seat at a time, each seat going to the state with the largest fractional remainder (the portion of `quota_raw` below its whole-slot floor); ties break toward the state with the larger `graduating_population` first, then toward the lexicographically smaller `state_code`. The resulting `slots_final` per state sums to exactly `total_semifinalist_slots`, and an individual state may receive fewer slots than its provisional figure suggested. The run flips every allocation `PROVISIONAL` → `FINAL`, computes each state's `threshold_selection_index` and `selected_count` as §3.4 describes, and increments each allocation's `version`.

### 3.3. Schools, Students, and Examination Entries

Before any entry exists, the program registers the actors on the student's side. A `ProgramAdmin` registers each `School` with its official `name`, a program-assigned `school_code` that is unique across all schools, and the `state_code` where the school is located. A `ProgramAdmin` likewise registers each `Student` with a `full_name`, the `school_id` of the school attended (which later routes endorsement), the `state_code` of attendance (which later drives semifinalist allocation), the declared `graduation_year`, a `citizenship_status` of `US_CITIZEN`, `US_NATIONAL`, `LAWFUL_PERMANENT_RESIDENT`, or `OTHER`, an `enrollment_status` of `ENROLLED_FULL_TIME`, `ENROLLED_PART_TIME`, or `NOT_ENROLLED`, and an optional `parent_sponsor_id` naming the corporate sponsor employing a parent — null when not applicable, and later the driver of employee-children award eligibility. The student roster can be listed with optional filters on `school_id`, `parent_sponsor_id`, and `state_code`.

With the cycle in `ENTRY_OPEN` posture, a `Student` creates their own `Entry` for the preliminary examination: the acting student's `X-User-ID` must equal the payload's `student_id`, or the request is `ERR_FORBIDDEN_OWNERSHIP`. The payload names the `cycle_id` entered and the `exam_year_of_hs` in which the examination was taken — `SECOND_YEAR` or `THIRD_YEAR`. Four entry requirements apply, each failed requirement a rejection with `ERR_ENTRY_INELIGIBLE` (HTTP 422): the student's `citizenship_status` must not be `OTHER`; the `enrollment_status` must be `ENROLLED_FULL_TIME` or `ENROLLED_PART_TIME` (a `NOT_ENROLLED` student is ineligible); the student's `graduation_year` must equal the cycle's `target_graduation_year`; and the examination must have been taken in `THIRD_YEAR`. One entry per student per cycle is a hard rule — a second entry for the same student in the same cycle is `ERR_DUPLICATE_ENTRY` (HTTP 409). Entries may be created only while the cycle is `ENTRY_OPEN`; creation in any other posture yields `ERR_CYCLE_NOT_ACCEPTING_ENTRIES` (HTTP 409). A new entry starts in `SUBMITTED` with `reading_score`, `writing_score`, `math_score`, `selection_index`, and `scored_at` all null, and the entry roster can be listed with optional filters on `cycle_id`, `student_id`, and `status`.

### 3.4. Scoring and Semifinalist Selection

Scoring begins only after the entry window closes: the entry's cycle must be in `ENTRY_CLOSED` posture, or the attempt is `ERR_CYCLE_NOT_CLOSED_FOR_SCORING` (HTTP 409). A `ProgramAdmin` records the three preliminary-examination section scores — `reading_score`, `writing_score`, and `math_score`, each an integer from 8 to 38 inclusive — on an entry that is still `SUBMITTED`; scoring an entry in any other status is `ERR_INVALID_STATE`. The server then computes the entry's `selection_index` as the sum of the three section scores multiplied by the section weight 2, giving an exact integer in the range 48 to 228. Any client-supplied `selection_index` value is ignored — the server always recomputes. The logical-clock instant of scoring is stamped into `scored_at`, the entry moves `SUBMITTED` → `SCORED`, and the entry's `version` increments.

The selection run refuses to fire while any entry of the cycle is still `SUBMITTED` — the rejection is `ERR_UNSCORED_ENTRIES_REMAIN` (HTTP 409). Once it fires, each state's allocation is finalized per §3.2, and the threshold calculation then runs state by state. The candidates in a state are the cycle's `SCORED` entries whose student's `state_code` equals that state. Candidates rank by `selection_index` descending, ties broken by `math_score` descending, then `reading_score` descending, then `created_at` ascending — never by `id`. With n candidates and k the smaller of `slots_final` and n: a state with zero candidates takes a null `threshold_selection_index` and selects nobody; otherwise `threshold_selection_index` is the `selection_index` of the k-th ranked candidate. Every candidate whose `selection_index` is at least the threshold flips `SCORED` → `SELECTED_SEMIFINALIST` — the boundary is inclusive, so a tie at the threshold selects more than `slots_final` candidates and a state's `selected_count` may exceed its `slots_final` — while every candidate below the threshold flips `SCORED` → `NOT_SELECTED`. Each selection increments the allocation's `selected_count` by 1, and each newly selected student's entry spawns a `SEMIFINALIST_NOTICE` notification (sequence 1, embargoed until the cycle's `semifinalist_embargo_until`). The cycle moves to `SEMIFINALISTS_SELECTED`, and the run reports `selected_total` and `states_finalized` to the caller.

### 3.5. The Finalist Application: Endorsement, Submission, Review, and Correction

Semifinalist standing qualifies a student to pursue finalist status — it does not confer it; the student must apply. Once the cycle reaches `SEMIFINALISTS_SELECTED` — application creation in any other posture is `ERR_CYCLE_POSTURE_INVALID` (HTTP 409) — a `Student` creates a `FinalistApplication` for one of their own entries, with `X-User-ID` equal to the entry's student or `ERR_FORBIDDEN_OWNERSHIP`. The entry must be `SELECTED_SEMIFINALIST`: creating an application for an entry that never made semifinalist is `ERR_ENTRY_NOT_SEMIFINALIST` (HTTP 409), and that standing check is evaluated before the duplicate-application check; a second application for the same entry is `ERR_INVALID_REQUEST` (HTTP 400) — at most one application per entry, ever. Creation must also happen while the logical clock is at or before the cycle's `application_deadline`; later attempts are `ERR_APPLICATION_WINDOW_CLOSED` (HTTP 422). The application records the `entry_id`, an optional `first_choice_college_id` (null means no college preference declared, and this field later drives college-sponsored matching), the academic record — `gpa_scaled` on a 0.0 to 4.0 scale and `course_rigor` of `STANDARD`, `ADVANCED`, or `MOST_RIGOROUS` — and a self-reported `confirming_selection_index` from 48 to 228 inclusive. The `student_id` is denormalized from the entry at creation, `endorsement_status` starts `PENDING`, `endorsed_by_school_id` stays null until endorsement, and the application starts `IN_PROGRESS` with no `submitted_at`. The applications roster can be listed with optional filters on `entry_id`, `student_id`, `first_choice_college_id`, `endorsed_by_school_id`, and `status`.

Endorsement comes from the student's school. A `SchoolOfficial` endorses an application whose student's `school_id` equals the official's `X-User-ID` — any other pairing is `ERR_ENDORSEMENT_SCHOOL_MISMATCH` (HTTP 403) — and only while the application is `IN_PROGRESS`. Endorsement is a self-transition on the status axis: the `status` stays `IN_PROGRESS` while `endorsement_status` flips to `ENDORSED` and `endorsed_by_school_id` records the acting official's `X-User-ID`. Endorsement fires exactly once per application: because endorsement is pinned to the pre-submission `IN_PROGRESS` status and an endorsed-but-unsubmitted application is already `ENDORSED`, a repeat endorsement is rejected with `ERR_INVALID_STATE` (HTTP 409), as is endorsing an application in any other status.

Submission moves the application `IN_PROGRESS` → `UNDER_REVIEW` — and, after a return, `RETURNED_FOR_CORRECTION` → `UNDER_REVIEW`; this correction cycle may repeat without bound while the cycle stays `SEMIFINALISTS_SELECTED`. Only the owning student submits (`X-User-ID` equal to the application's `student_id`, else `ERR_FORBIDDEN_OWNERSHIP`). Four further gates apply: the cycle must be `SEMIFINALISTS_SELECTED` (else `ERR_CYCLE_POSTURE_INVALID`); the logical clock must be at or before the `application_deadline` (else `ERR_APPLICATION_WINDOW_CLOSED`); `endorsement_status` must be `ENDORSED` (else `ERR_APPLICATION_INCOMPLETE`, HTTP 422); and `confirming_selection_index` must be at least the cycle's `confirming_floor` (else `ERR_CONFIRMING_SCORE_BELOW_FLOOR`, HTTP 422). Each successful submit stamps `submitted_at` from the logical clock — `submitted_at` later serves as the final selector tie-break in matching, never `id` — clears `return_reason` to null, and increments the application's `version`.

Review is a `ProgramAdmin` decision on an `UNDER_REVIEW` application, OCC-guarded by `expected_finalist_application_version` per §2.7, with the request's `decision` field choosing among three outcomes. Reviewing an application not in `UNDER_REVIEW` is `ERR_INVALID_STATE`. A `decision` of `CONFIRM` additionally requires `endorsement_status` `ENDORSED` (else `ERR_APPLICATION_INCOMPLETE`), a `confirming_selection_index` at or above the cycle's `confirming_floor` (else `ERR_CONFIRMING_SCORE_BELOW_FLOOR`), and the cycle still in `SEMIFINALISTS_SELECTED` (else `ERR_CYCLE_POSTURE_INVALID`); it moves the application `UNDER_REVIEW` → `FINALIST_CONFIRMED`. A `decision` of `RETURN` requires a non-empty `return_reason` in the payload (else `ERR_INVALID_REQUEST`, HTTP 400); it moves the application `UNDER_REVIEW` → `RETURNED_FOR_CORRECTION` and records the payload value in `return_reason` for the student. A `decision` of `DENY` moves the application `UNDER_REVIEW` → `DENIED`, terminal. Every successful review increments the application's `version`.

Publishing finalists refuses to fire while any application of the cycle's entries is `UNDER_REVIEW` or `RETURNED_FOR_CORRECTION` — the rejection is `ERR_PENDING_APPLICATIONS_REMAIN` (HTTP 409) — which makes the `RETURNED_FOR_CORRECTION` → `DENIED` cascade edge unreachable by construction; that edge is declared only so the deny-from-returned policy is explicit. What publishing does: every application still `IN_PROGRESS` flips to `DENIED` (auto-denial at the deadline of the process), every `FINALIST_CONFIRMED` application spawns a `FINALIST_NOTICE` notification (sequence 2, embargoed until the cycle's `finalist_embargo_until`), and the cycle moves `SEMIFINALISTS_SELECTED` → `FINALISTS_SELECTED` with its `version` incremented.

### 3.6. Funding Configurations: Corporate Agreements and College Sponsorships

Corporate participation begins when a `ProgramAdmin` registers a `CorporateSponsor` with its `legal_name` and a unique, program-assigned `sponsor_code`. Thereafter the sponsor administers its own agreements. A `SponsorAdmin` creates a `SponsorAgreement` under their own sponsor — the acting sponsor's `X-User-ID` must equal the sponsor named in the request path, else `ERR_FORBIDDEN_OWNERSHIP` — naming the `cycle_id` whose finalists the agreement funds, the per-award `award_amount_cents` (greater than 0), the `max_awards` the agreement may grant (at least 1), the `pool_total_cents` funding pool (at least `award_amount_cents`), and the effective window from `effective_start_date` to `effective_end_date` — a half-open interval that includes the start date and excludes the end date, with the end strictly after the start. Two eligibility criteria ride on the agreement: `employee_children_only` (default true) restricts eligibility to students whose `parent_sponsor_id` equals the agreement's `sponsor_id`, and `min_selection_index` (null by default, meaning no extra floor) imposes a minimum entry `selection_index`. A new agreement is `ACTIVE`, its `supersedes_agreement_id` is null, and its four ledger fields — `pool_committed_cents`, `pool_paid_cents`, `pool_available_reserved_cents`, and `pool_available_cash_cents` — start at their computed defaults. The agreements roster can be listed with optional filters on `sponsor_id`, `cycle_id`, `supersedes_agreement_id`, and `status`.

Effective windows of the same sponsor for the same cycle must not overlap. Because windows are half-open, adjacency — one agreement's end date equal to another's start date — is allowed, and the agreement being superseded by an amendment is excluded from the check. A violation is `ERR_AGREEMENT_WINDOW_OVERLAP` (HTTP 409), and on amendment this temporal check runs before the pool-floor check. Amendment replaces rather than edits: the sponsor amends its own agreement (the same ownership rule, `X-User-ID` against the agreement's `sponsor_id`) while it is `ACTIVE` or `EXHAUSTED` — amending a `SUPERSEDED` or `CLOSED` agreement is `ERR_INVALID_STATE` — carrying `expected_sponsor_agreement_version` per §2.7 plus any of the amendable fields (`award_amount_cents`, `max_awards`, `pool_total_cents`, `effective_start_date`, `effective_end_date`, `employee_children_only`, `min_selection_index`); unchanged fields are copied. A successful amendment creates a new `ACTIVE` agreement whose `supersedes_agreement_id` points at the old one and whose `pool_committed_cents` and `pool_paid_cents` start at 0 — obligations already incurred stay on the old agreement — while the old agreement flips to `SUPERSEDED` with a version bump. Amendment may not set `pool_total_cents` below the agreement's current `pool_committed_cents` plus `pool_paid_cents`: obligations are preserved across amendment, and a violating payload is rejected with `ERR_POOL_BELOW_COMMITTED` (HTTP 422).

College institutions are registered by a `ProgramAdmin` with a `legal_name`, a unique `college_code`, and the sponsorship configuration: `award_amount_cents` per academic year (greater than 0), `renewable_years_total` (at least 2), `terms_per_year` (at least 1), a `pool_total_cents` of at least `award_amount_cents` multiplied by `renewable_years_total`, and `max_awards` concurrently funded (at least 1). An institution is `ACTIVE` while it can fund offers.

Both kinds of funding pool keep the same double ledger, recomputed on every mutation of the pool's awards or disbursements. The reservation ledger `pool_committed_cents` sums, over the pool's awards in a live recipient state (`OFFERED`, `ACCEPTED`, `ENROLLED`, or `RENEWED`), each award's `amount_cents` minus that award's already-`RELEASED` disbursement amounts. The cash ledger `pool_paid_cents` sums all `RELEASED` disbursement amounts the pool has funded. Two availability figures derive from these: `pool_available_reserved_cents` is `pool_total_cents` minus `pool_committed_cents` minus `pool_paid_cents`, and `pool_available_cash_cents` is `pool_total_cents` minus `pool_paid_cents`. Every gate in the system — matching capacity, exhaustion evaluation, promotion capacity — uses the reservation variant only; the cash variant is reported for reconciliation and must never gate anything.

Exhaustion and recovery are automatic, driven by the pool cascade. A sponsor agreement flips `ACTIVE` → `EXHAUSTED` after any award creation or pool release touching it whenever its `pool_available_reserved_cents` falls below its `award_amount_cents` or its granted award count reaches `max_awards`; it flips back `EXHAUSTED` → `ACTIVE` when a decline, expiry, or lapse release raises `pool_available_reserved_cents` to at least `award_amount_cents` while the granted count is below `max_awards` — and that recovery flip triggers waitlist promotion for the agreement's candidate pool (§3.7). A college institution follows the same loop with its own unit of account: exhaustion when `pool_available_reserved_cents` falls below `award_amount_cents` multiplied by `renewable_years_total` or the funded award count reaches `max_awards`, recovery when a release restores that capacity, again triggering promotion for the institution's first-choice candidate pool. Agreements — but never institutions — also reach a terminal `CLOSED` when their cycle completes, whether from `ACTIVE` or `EXHAUSTED`; institutional pools span cycles and are not closed.

### 3.7. Award Matching and Waitlist Promotion

Once finalists are published, a `ProgramAdmin` runs the award-matching waterfall — exactly once per cycle, only in `FINALISTS_SELECTED` posture (any other posture is `ERR_CYCLE_POSTURE_INVALID`), with a repeat attempt rejected as `ERR_MATCHING_ALREADY_RUN`. Candidates are the cycle's `FINALIST_CONFIRMED` applications with no existing award; one award per finalist per cycle is a hard rule. The waterfall visits buckets in a fixed order: first the national bucket, then the corporate bucket — each `ACTIVE` `SponsorAgreement` of the cycle in `created_at` ascending order — then the college bucket, each `ACTIVE` `CollegeInstitution` in `created_at` ascending order. Within every bucket the selector ranks candidates identically: `selection_index_snapshot` (the entry's `selection_index`, snapshotted onto the award at matching time) descending, then `confirming_selection_index` descending, then `submitted_at` ascending — never by `id`. A candidate granted in an earlier bucket is removed from all later buckets in the same run, and a bucket with no eligible candidates is skipped silently, without error.

Each bucket grants differently. The national bucket grants to the top candidates, at most the cycle's `national_award_slots` of them; each grant's `amount_cents` is the cycle's `national_award_amount_cents`, with `terms_total` 1 and `renewable_years_total` 1 — a single-payment award. A corporate agreement grants to candidates eligible for it: either `employee_children_only` is false or the student's `parent_sponsor_id` equals the agreement's `sponsor_id`, and either `min_selection_index` is null or the entry's `selection_index` is at least that floor. Each agreement grants at most the smaller of its remaining award headroom (`max_awards` minus awards already granted under it) and its remaining capacity in award units (`pool_available_reserved_cents` divided by `award_amount_cents`, rounded down); each corporate award's `amount_cents` is the agreement's per-award amount, again with `terms_total` 1 and `renewable_years_total` 1. A college institution is a candidate's bucket exactly when the application's `first_choice_college_id` names that institution; it grants at most the smaller of `max_awards` minus granted and `pool_available_reserved_cents` divided by the full per-award obligation (`award_amount_cents` multiplied by `renewable_years_total`), rounded down; each college award's `amount_cents` is that full obligation, its `renewable_years_total` is the institution's own, and its `terms_total` is `renewable_years_total` multiplied by `terms_per_year`. Every grant debits its pool at offer time: `pool_committed_cents` grows by the award's `amount_cents` — a reservation, not yet a payment.

Every created award records the `cycle_id`, the `application_id` it was matched from, and the `student_id` denormalized from the application, and is assigned a `category` of `NATIONAL_SINGLE`, `CORPORATE_SPONSORED`, or `COLLEGE_SPONSORED` by the bucket that granted it — a corporate award records its funding `agreement_id` and a null `college_id`, a college award records its `college_id` and a null `agreement_id`, and a national award carries neither. Each award starts `OFFERED` on the recipient dimension and `PLEDGED` on the funding dimension, with `years_renewed` at 0, `offered_logical_at` stamped from the logical clock, and `acceptance_deadline` computed 30 days after `offered_logical_at`. Two notifications queue per award, both `EMBARGOED`: an `AWARD_OFFER` (sequence 3, embargoed until the cycle's `award_embargo_until`) and a `PUBLIC_ANNOUNCEMENT` (sequence 4, embargoed until the cycle's `public_embargo_until`). The run sets the cycle's `matching_run` to true, increments the cycle's `version`, and reports `awards_created`, `national_granted`, `corporate_granted`, and `college_granted` to the caller. The awards roster can be listed with optional filters on `cycle_id`, `application_id`, `student_id`, `agreement_id`, `college_id`, `category`, and `recipient_status`.

Waitlist promotion reuses the same selector outside the matching run. Whenever a pool's `EXHAUSTED` → `ACTIVE` flip (§3.6) — caused by a decline, an expiry sweep, or a lapse release — frees capacity, promotion runs for that one pool: the freed sponsor agreement, the freed institution, or the cycle's national slot count, for which capacity returns when the live national count (awards in `OFFERED`, `ACCEPTED`, `ENROLLED`, or `RENEWED`) drops below `national_award_slots`. Eligible candidates are the cycle's un-awarded `FINALIST_CONFIRMED` applications satisfying the pool's own criteria — none for the national bucket; the agreement's `employee_children_only` and `min_selection_index` for corporate; `first_choice_college_id` equality for college — ranked by the same snapshot-confirming-submitted ordering. Promotion grants exactly one award per iteration to the top-ranked candidate when capacity allows — for corporate and college pools, `pool_available_reserved_cents` must cover at least one full award unit — then re-evaluates the pool status and repeats while capacity and candidates remain; an empty candidate set is a no-op and the pool simply stays `ACTIVE`. A promoted award is created `OFFERED` and `PLEDGED` with `offered_logical_at` from the logical clock and queues its own `AWARD_OFFER` and `PUBLIC_ANNOUNCEMENT` notifications under the cycle's embargo values.

### 3.8. The Award Lifecycle: Acceptance, Decline, Disbursement, and Renewal

An offer is live for exactly 30 days of logical time: `acceptance_deadline` is `offered_logical_at` plus the 30-day acceptance window, and an offer not accepted by that instant is swept to `EXPIRED` on the next clock advance. Only the recipient may act — `X-User-ID` equal to the award's `student_id`, else `ERR_FORBIDDEN_OWNERSHIP` — and only while the award is `OFFERED`: accepting or declining an award in any other recipient state (already accepted, already declined, expired-swept, or lapsed) is `ERR_AWARD_NOT_OFFERED` (HTTP 409). Because the sweep runs on clock advance, an expired offer hits this state gate first rather than any deadline error.

Acceptance moves the recipient `OFFERED` → `ACCEPTED` and the funding dimension `PLEDGED` → `COMMITTED`, and it generates the disbursement schedule: one `Disbursement` row per term, each recording its owning `award_id` and its 1-based `term_index`. Numbering terms 1 through `terms_total`, with T0 the logical-clock date at acceptance: term i takes a `scheduled_date` of T0 plus (i − 1) times 180 days. Each non-final term's `amount_cents` is the award's `amount_cents` divided by `terms_total`, rounded half up; the final term absorbs the remainder, taking the award's `amount_cents` minus the sum of all prior terms. This rounding order is pinned — round each non-final term first, then let the final term absorb the remainder; rounding every term would let the schedule drift from the award total, and summing-then-splitting is likewise forbidden. Each term's `academic_year_index` is its `term_index` divided by the funding configuration's `terms_per_year`, rounded up (for single-payment awards `terms_per_year` is 1, so every term belongs to year 1). Year-1 terms are created `SCHEDULED` — payable once due — while terms of year 2 and beyond are created `HELD` pending that year's renewal, and `released_logical_at` stays null until payment.

Decline and expiry share one four-link release cascade: decline moves the recipient `OFFERED` → `DECLINED`, expiry moves the recipient `OFFERED` → `EXPIRED`, and in both cases the award's `funding_status` goes to `RELEASED_BACK`. Link one releases the reservation: a corporate or college pool's `pool_committed_cents` drops by the award's `amount_cents`, while for the national bucket the cycle's live national count decreases by 1. Link two re-evaluates the freed pool's capacity, flipping an `EXHAUSTED` agreement or institution back to `ACTIVE` when capacity returns (national capacity returns when the live count drops below `national_award_slots`). Link three runs waitlist promotion for that pool (§3.7), creating the next eligible finalist's `OFFERED` award when one exists. Link four queues the promoted award's own `AWARD_OFFER` and `PUBLIC_ANNOUNCEMENT` notifications, `EMBARGOED`. Meanwhile the declined-or-expired award's own unreleased `AWARD_OFFER` and `PUBLIC_ANNOUNCEMENT` notifications flip `EMBARGOED` → `SUPERSEDED`. Decline is the recipient's explicit act; expiry is the clock sweep's, firing when the logical clock advances past `acceptance_deadline` while the award is still `OFFERED`. Both increment the award's `version`.

Releasing a disbursement is a `ProgramAdmin` action with three preconditions: the disbursement must be `SCHEDULED` — a `HELD` one is rejected `ERR_DISBURSEMENT_HELD` (HTTP 409) and a terminal one (`RELEASED` or `CANCELLED`) is `ERR_INVALID_STATE`; the logical clock must be at or past its `scheduled_date`, else `ERR_DISBURSEMENT_NOT_DUE` (HTTP 422); and the award's recipient state must be `ACCEPTED`, `ENROLLED`, or `RENEWED`, else `ERR_INVALID_STATE`. A release stamps `released_logical_at` from the logical clock, moves money in the funding pool's ledger — `pool_committed_cents` down by the term's `amount_cents`, `pool_paid_cents` up by the same amount — and re-evaluates the award's funding dimension: `COMMITTED` → `PARTIALLY_DISBURSED` while released terms remain fewer than `terms_total`, and on to `FULLY_DISBURSED` when the last non-`CANCELLED` term releases. The first successful release on an award also flips its recipient `ACCEPTED` → `ENROLLED`, and reaching `FULLY_DISBURSED` flips a recipient in `ACCEPTED`, `ENROLLED`, or `RENEWED` to `COMPLETED`.

College-sponsored awards renew yearly behind a segregation of duties: the institution reports, the program decides, and neither can perform the other's step. A `CollegeAdmin` submits a renewal verification for an award their institution funds — `X-User-ID` must equal the award's `college_id`, else `ERR_FORBIDDEN_OWNERSHIP`; on a national or corporate award, whose `college_id` is null, any `CollegeAdmin` passes this ownership check and hits the renewability gate instead. Renewability requires the award's `renewable_years_total` to be at least 2, else `ERR_NOT_RENEWABLE` (HTTP 409); the award's recipient state must be `ENROLLED` or `RENEWED`, else `ERR_INVALID_STATE`; and exactly one verification may exist per academic year — the submitted `academic_year_index` must lie between 2 and the award's `renewable_years_total` and must be the immediately next unverified year, else `ERR_RENEWAL_ALREADY_EXISTS` (HTTP 409). The report carries `reported_enrollment` (`FULL_TIME`, `HALF_TIME`, or `NOT_ENROLLED`) and `reported_gpa` (0.0 to 4.0), is created `SUBMITTED`, and records the acting administrator in `submitted_by_college_id` — informational only; the authoritative linkage runs from the verification's `award_id` through the award to its `college_id`.

A `ProgramAdmin` decides a verification that is `SUBMITTED` — deciding a decided one is `ERR_INVALID_STATE` — stamping `decided_logical_at` from the logical clock. A `decision` of `APPROVE` requires `reported_enrollment` of `FULL_TIME` and a `reported_gpa` of at least 2.5; anything short is `ERR_RENEWAL_CRITERIA_UNMET` (HTTP 422). Approval moves the verification `SUBMITTED` → `APPROVED` and cascades into the award: the recipient moves `ENROLLED` → `RENEWED` — or, for later years, stays `RENEWED` — `years_renewed` grows by 1, and that year's `HELD` disbursements flip `HELD` → `SCHEDULED`. A `decision` of `REJECT` moves the verification `SUBMITTED` → `REJECTED` and lapses the award: the recipient moves from `ENROLLED` or `RENEWED` to `LAPSED`; every remaining `SCHEDULED` or `HELD` disbursement flips to `CANCELLED`; the funding pool's `pool_committed_cents` drops by the outstanding (not-`RELEASED`, not-`CANCELLED`) amount; the pool re-evaluates its status, and an `EXHAUSTED` → `ACTIVE` flip there runs waitlist promotion, creating a new `OFFERED` award and queueing its notifications; and the award's `funding_status` goes to `RELEASED_BACK`.

The cycle watches all of this. After every award recipient-status change, every disbursement status change, and every clock sweep, the completion bubble-up re-evaluates: when the cycle's `matching_run` is true, no award of the cycle remains in `OFFERED`, `ACCEPTED`, `ENROLLED`, or `RENEWED`, and no disbursement of the cycle's awards remains `SCHEDULED` or `HELD`, the cycle moves `FINALISTS_SELECTED` → `AWARDS_COMPLETED`, every `ACTIVE` or `EXHAUSTED` `SponsorAgreement` of the cycle flips to `CLOSED`, and the cycle's `version` increments.

### 3.9. Notifications, Embargoes, and the Publicity Gap

Every stage notice is a `Notification` row bound to a recipient student, with a per-student release order pinned by `sequence_number`: `SEMIFINALIST_NOTICE` is 1, `FINALIST_NOTICE` is 2, `AWARD_OFFER` is 3, and `PUBLIC_ANNOUNCEMENT` is 4. Each notification records the `student_id` of its recipient, the `cycle_id` it belongs to (informational — authoritative cycle reachability runs from the student through the entry to the cycle), and its `notice_type`, and it copies its `embargo_until` from the cycle's per-type embargo field at creation: `semifinalist_embargo_until`, `finalist_embargo_until`, `award_embargo_until`, or `public_embargo_until` respectively. Every notification starts `EMBARGOED`, with `released_logical_at` null until release.

Release is manual-only: a `ProgramAdmin` releases a notification, and the clock never auto-releases one. Three gates guard every release, plus a fourth for publicity. The notification must be `EMBARGOED` — re-releasing a `RELEASED` notification, or releasing a `SUPERSEDED` one, is `ERR_INVALID_STATE`. Every notification of the same student with a lower `sequence_number` must already be `RELEASED`, else `ERR_NOTIFICATION_SEQUENCE_VIOLATION` (HTTP 409). The logical clock must be at or past the notification's `embargo_until`, else `ERR_NOTIFICATION_EMBARGOED` (HTTP 422). And for a `PUBLIC_ANNOUNCEMENT` specifically, the logical clock must additionally be at least 2 days past the most recent `released_logical_at` among the cycle's `RELEASED` `AWARD_OFFER` notifications — the publicity gap — else `ERR_PUBLICITY_WINDOW_TOO_EARLY` (HTTP 422). A successful release stamps `released_logical_at` from the logical clock and increments the notification's `version`.

Withdrawal supersedes publicity: when the underlying award becomes `DECLINED` or is swept `EXPIRED` before release, that award's `AWARD_OFFER` and `PUBLIC_ANNOUNCEMENT` notifications flip `EMBARGOED` → `SUPERSEDED` as part of the release cascade of §3.8. A student's notification list — readable with optional filters on `status` and `notice_type` — always returns rows in `sequence_number` ascending order, so the release order is visible at a glance.
