# House Jewelry Credit & Lifetime Service Plan Administration API — Product Requirements Document

## 1. Introduction

A jewelry chain sells high-ticket, emotionally significant items at a counter, and almost everything that happens after the sale is a promise about money or about a stone. This API is the back office for both. It covers the private-label credit application a sales associate takes across the counter — instant decisioning, tier pricing out of a risk registry, and the down-payment the store must collect before a line is opened — together with the deferred-interest promotional financing the customer signs at the same moment, the payoff-by-date clock that decides whether that interest is forgiven or capitalized, and the quarterly installment billing that follows.

Running alongside the money is a second, longer-lived obligation. A lifetime diamond-and-service plan is registered against a purchase and a specific stone, and it stays valid only while the customer keeps bringing the piece in for inspection. Missed inspections lapse the plan; lapsed plans stop paying for repairs; and a customer who lapses repeatedly has their credit posture downgraded. Repairs themselves move through a bench-shop network with vendor routing, pinned loss-liability at intake, turnaround commitments the store can be forced to compensate for, and appraisals that feed both insurance replacement and the trade-up console where an old purchase's ticket value is credited toward a new one.

The commercial goal is that no counter decision, bench routing, inspection miss, commission revision, or statement generation can put the store's balance sheet, the customer's credit posture, or a registered stone in an inconsistent state. That is why the rules in this document are frequently coupled: a single default on a deferred-interest plan cascades through the customer's account status, their pending applications, and their inspection-bearing registrations before the tier is recomputed; a single trade-up credits a prior ticket, retires the prior plan, and opens a fresh registration. Implementers should read the calculation and cascade rules as ordering-sensitive, not as independent guard clauses.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting user and `X-User-Role` names their operational capacity. Six roles are recognized, spelled exactly as follows: `ChainAdmin`, `StoreManager`, `CreditAnalyst`, `SalesAssociate`, `CustomerService`, and `Customer`. A request that omits either header, or whose `X-User-Role` does not name one of those six, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401).

Authorization is a separate, later check. Each operation belongs to a set of permitted roles; a role that attempts an operation outside its permitted set — including a role attempting another role's exclusive capability — is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Five of the six roles carry an opaque operator identity. When `X-User-Role` is `ChainAdmin`, `StoreManager`, `CreditAnalyst`, `SalesAssociate`, or `CustomerService`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it on the resources it writes, but it does not compare it to any entity's `id`, and it never makes an ownership decision on the basis of it — for example, a `CustomerService` operator closing a customer file does so by naming the customer in the request, not by possessing a matching identifier.

The `Customer` role is the exception, and it is backed by an entity. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Customer`; ownership checks on any resource that references a `Customer` compare the resource's customer foreign-key field (the resource's `customer_id`) to `X-User-ID`. A `Customer` acting on a credit application, a custom commission, or a statement that names a different customer is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). This check is enforced on accepting a countered offer, declining a countered offer, requesting a CAD revision, approving a CAD document, and cancelling an own commission.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps how many items are returned; when omitted it defaults to 10, and it may be set no lower than 1 and no higher than 100. `offset` skips that many items from the front of the result and defaults to 0. Unless a rule elsewhere in this document says otherwise, list endpoints return resources sorted by creation timestamp (`created_at`) in ascending order.

List responses carry `limit`, `offset`, `total_count`, and `has_more` inside the response envelope's `meta` object, in addition to `api_request_id` and `api_request_timestamp`.

### 2.4. The Risk Registry and Counter Credit Pricing

Before any numeric or business check runs on a counter credit decision, the chain's risk registry must be able to price the requested line. Registry rows are keyed by `registry_key` and `credit_tier`. A row is either state-scoped (`registry_type` of `STATE`, where `registry_key` equals a two-letter state code) or the chain-wide fallback (`registry_type` of `GLOBAL`, where `registry_key` equals the `all_states_key` sentinel (the sentinel acts as the registry type named by the `REGISTRY_TYPE_GLOBAL` row), whose default value is the literal string `*`, the constant `ALL_STATES_KEY`). `registry_key` is unique; a state row's key equals the store's `state_code`, and the global row's key equals `all_states_key`. `base_limit_cents` is the standalone ceiling the row grants and `min_down_payment_pct` is the down-payment percentage the row requires. `min_ticket_cents` is the lowest requested limit for which the row may be selected at all, defaulting to 0.

Pricing a line proceeds in a fixed sequence. First the applicant's policy tier is derived from the requested limit alone: the tier is `TIER_3` when `requested_limit_cents` is at least 1,000,000 cents (10,000 dollars); otherwise `TIER_2` when `requested_limit_cents` is at least 500,000 cents (5,000 dollars); otherwise `TIER_1` when `requested_limit_cents` is at least 200,000 cents (2,000 dollars); and otherwise `TIER_1` as well, because a request below the registry floor still resolves against a `TIER_1` row. Second, income acts as a downgrade, never an upgrade: if `declared_annual_income_cents` was supplied and is below 2,500,000 cents (25,000 dollars), the policy tier is forced down to `TIER_1` regardless of the requested amount. The two thresholds are named `TIER_3_REQUEST_THRESHOLD_CENTS`, `TIER_2_REQUEST_THRESHOLD_CENTS`, and `TIER_1_REQUEST_THRESHOLD_CENTS`, and the income floor is `INCOME_DOWNGRADE_THRESHOLD_CENTS`.

Third, the candidate set is every registry row whose `credit_tier` equals the policy tier just derived and whose `min_ticket_cents` is at most `requested_limit_cents`. Among those candidates the state-scoped rows — those whose `registry_key` equals the customer's `state_code` — are preferred: if any exists, the winning row is the one with the largest `min_ticket_cents`, breaking ties by the most recent creation (`created_at`). If no state-scoped candidate exists, the winning row is chosen by the same rule from the candidates whose `registry_key` equals their own `all_states_key`, and the response's `decision_rule_id` then names that global row instead of a state row. These two readings are the `STATE_ROW_WINS` and `GLOBAL_FALLBACK_ROW` variants: a state row binds even when the global row would have been more generous. If no row resolves at all, the decision is refused with `ERR_REGISTRY_ROW_MISSING` (HTTP 422).

The granted ceiling is the lesser of the winning row's `base_limit_cents` and the requested amount: `approved_limit_cents` is the smaller of `base_limit_cents` and `requested_limit_cents`. A requested amount above the standalone limit implied by the customer's `credit_tier` is refused with `ERR_CREDIT_LIMIT_EXCEEDED` (HTTP 422).

The down-payment floor is derived from the winning row's percentage and the sale it would fund, rounded away from zero to the next whole cent: `min_down_payment_required_cents` is `min_down_payment_pct` multiplied by `requested_purchase_amount_cents`, rounded up to a whole cent. `down_payment_shortfall_cents` is `min_down_payment_required_cents` minus `down_payment_cents`, floored at 0 — that is, the amount by which the tendered down payment falls short, or 0 when it does not. A declared down payment below the formula-derived minimum for the decisioned tier is refused with `ERR_DOWN_PAYMENT_REQUIRED` (HTTP 422). Worked reference: a Texas row with `min_ticket_cents` of 200,000, `base_limit_cents` of 300,000, and `min_down_payment_pct` of 0.10, against a requested limit of 300,000 and a purchase amount of 300,000 with 30,000 tendered, yields `approved_limit_cents` of 300,000, a required minimum of 30,000, and a shortfall of 0; the same inputs with a purchase amount of 300,001 yield a required minimum of 30,001 and a shortfall of 1; and with a purchase amount of 300,050 they yield 30,050 required against 30,000 tendered, a shortfall of 5.

At intake, `minimum_down_payment_cents` is the floor supply guard on the application row: intake refuses any application whose `down_payment_cents` is below it. It defaults to 0, so an application that supplies no floor is not gated by this guard.

### 2.5. Deferred-Interest Plan Economics

A promotional plan is opened against a purchase under one of three enumerated codes: `PROMO_12_6M`, `PROMO_18_6M`, or `PROMO_24_12M`. The code determines three derived terms at creation. `PROMO_12_6M` grants `deferred_months` of 6, a `simplicity_months` window of 12, and a `deferral_basis_points` rate of 1200. `PROMO_18_6M` grants 6 deferred months, an 18-month window, and 1500 basis points. `PROMO_24_12M` grants 12 deferred months, a 24-month window, and 1600 basis points. The annual percentage rate applied to the deferral accrual is `promotional_apr_pct`, and the constants that carry it are `APR_PROMO_12_6M` at 26.99, `APR_PROMO_18_6M` at 27.99, and `APR_PROMO_24_12M` at 28.99.

The financed principal is `principal_cents`: the financed purchase's `net_amount_cents`, plus that purchase's `protection_fee_cents` when the purchase carries a bundle, and nothing when it does not. The principal and the protection fee are read once at creation and are never re-read from the purchase afterwards. The quarterly installment schedule divides the principal by the number of quarters in the simplicity window, where a quarter is 3 months (`MONTHS_PER_QUARTER`): `installment_quarter_cents` is `principal_cents` divided by `simplicity_months` divided by 3, rounded half up to a whole cent. `installment_amount_cents` equals `installment_quarter_cents`; the installment does not reduce the plan principal, it is the amount the customer is billed. The merchant's deferral fee is `merchant_deferral_fee_cents`, computed as `principal_cents` multiplied by `deferral_basis_points` and divided by 10,000, rounded half up to a whole cent. The constants naming the codes' rates are `DEFERRAL_BPS_PROMO_12_6M`, `DEFERRAL_BPS_PROMO_18_6M`, and `DEFERRAL_BPS_PROMO_24_12M`. Worked reference: `PROMO_12_6M` on a 450,000 cent net amount with no bundle gives a principal of 450,000, a quarterly installment of 112,500 (450,000 over 4 quarters), and a merchant deferral fee of 54,000. `PROMO_24_12M` on the same amount gives a quarterly installment of 56,250 (450,000 over 8 quarters) and a merchant deferral fee of 72,000.

Two readings of the deferral fee exist. Under `HEADLINE_DEFERRAL_BPS` the fee uses the chosen code's single headline rate; under `MARGINAL_DEFERRAL_BPS` a plan that straddles the 18-month boundary prices months 13 through 18 at 1500 basis points and builds the fee tier by tier. For `PROMO_12_6M` the two readings coincide.

Deferred interest accrues on a forward-looking basis. `deferred_interest_accrued_cents` is 0 whenever the plan's `plan_status` is `CAPITALIZED`, because the interest has by then been absorbed into the principal. Otherwise it is `principal_cents` multiplied by `promotional_apr_pct`, divided by 100, multiplied by the whole number of days elapsed since the plan was created, and divided by 365 (`DAYS_PER_YEAR`), rounded half up to a whole cent. Only plans in `ACCRUING` status accrue: `PAID`, `CAPITALIZED`, `DEFAULTED`, and `VOIDED` plans contribute 0, which is the `VESTED_ZERO` reading against the `PROVISIONAL_ACCRUING` reading for an `ACCRUING` plan. Worked reference: a 450,000 cent principal at 26.99 percent over 196 days accrues 65,220 cents; over 120 days, 39,930 cents; over 200 days, 66,551 cents.

The plan's contractual balance is `final_settlement_amount_cents`. While the plan is `ACCRUING` it is `principal_cents` plus `deferred_interest_accrued_cents`. Once the plan is `CAPITALIZED` it is the principal alone. `total_paid_cents` accumulates every payment applied to the plan, whether an installment or a lump-sum payoff.

### 2.6. Lifetime Plan Registration Terms and State Compliance

A lifetime plan registration is governed by a protection bundle: `bundle_code` (unique), `display_name`, `bundle_status` (`CURRENT` or `RETIRED`), `lifetime_plan_fee_cents`, `stone_limit_labor_cents`, `stone_limit_parts_cents`, `inspection_interval_days` (default 180) and `inspection_cure_days` (default 30). A `RETIRED` bundle may not be attached to new registrations, though it continues to govern registrations already written under it — this is the state in which the `GROSS_RESERVE` liability posture becomes available (§2.7).

A registration also takes `plan_term_months`, the contracted term, which must not exceed the maximum the governing state permits. State terms live in the lifetime-plan regulation table, keyed by a unique `state_code`: `max_plan_term_months`, `inspection_required_months` (0 meaning the state imposes no inspection mandate), `max_inspection_gap_days` (default 0), `lapse_cure_days`, and `replacement_plus_pct` — the share of the chain's replacement invoice a store may absorb before the 25 percent cap applies, entered as either 0.75 or 1.0.

Origination carries a hard prerequisite. The governing regulation row for the store's state must exist before any state or business rule is evaluated on a purchase completion, a registration, or a credit decision; if it does not, the request is refused with `ERR_REGULATION_TERMS_VIOLATION` (HTTP 422). This check holds the highest position of the compliance layer precisely so that a missing regulation surfaces as itself rather than being masked by a later check. Where the row exists but the plan's `plan_term_months` exceeds `max_plan_term_months`, the request is refused with the same `ERR_REGULATION_TERMS_VIOLATION` code at HTTP 422, and the catalogue also declares `ERR_PLAN_TERM_EXCEEDS_REGULATION` (HTTP 422) for the specific term-overrun condition — both identifiers describe refusals of a lifetime-plan term the state does not allow.

Where no regulation row exists for a store's state, a registration in `PENDING_INSPECTION` may be voided rather than defaulted; the resulting `coverage_status` is `VOID`, which is terminal. This is why the void capability is restricted to a chain-level administrator.

When a state's `inspection_required_months` is greater than 0, the registration must be scheduled for inspection; a registration that is not is refused with `ERR_REGULATION_TERMS_VIOLATION` (HTTP 422).

### 2.7. Bench Liability, Routing and Turnaround Commitments

Repair intake pins a loss liability once and never recomputes it. The computation reads the intake repair's `declared_parts_cents` and `declared_labor_cents`, the governing bundle's `stone_limit_labor_cents` and `stone_limit_parts_cents`, the optional `declared_loss_liability_cents` supplied on the intake payload, and whether the pinned registration's coverage is currently valid.

The chain's default posture is the `NET_RESERVE` reading. A warranty reserve is taken on parts first: the reserve is `declared_parts_cents` multiplied by `WARRANTY_RESERVE_PCT` (0.07), rounded half up. Covered parts are `declared_parts_cents` minus that reserve. Insurance-funded labor is the smaller of `declared_labor_cents` and the remaining labor headroom, where the headroom is `stone_limit_labor_cents` minus covered parts, floored at 0. The store-absorbed liability is then the parts-and-labor value above the labor limit, plus the reserve, plus the declared loss liability: that is, the greater of 0 and (`covered` plus `declared_labor_cents` minus `stone_limit_labor_cents`), plus the reserve, plus `declared_loss_liability_cents`. `LOSS_LIABILITY_DEFAULT_CENTS` is 0, so an intake that supplies no `declared_loss_liability_cents` contributes nothing to that final term.

The alternative `GROSS_RESERVE` reading applies when the covered plan was retired mid-term, so that above-limit value is reserved too. There the reserve is taken on parts plus labor — the sum multiplied by `WARRANTY_RESERVE_PCT`, rounded half up — and the liability is the greater of 0 and (`declared_parts_cents` plus `declared_labor_cents` minus `stone_limit_labor_cents`), plus that larger reserve, plus the declared loss liability. On the shared worked example the two readings diverge: `declared_parts_cents` of 40,000, `declared_labor_cents` of 15,000, `stone_limit_labor_cents` of 25,000, `stone_limit_parts_cents` of 60,000, and `declared_loss_liability_cents` of 5,000 on a valid plan give a `NET_RESERVE` store-absorbed liability of 35,000 cents (reserve 2,800; covered parts 37,200; insurance labor 0; then 37,200 plus 15,000 minus 25,000, plus 2,800, plus 5,000) and a `GROSS_RESERVE` liability of 38,850 cents (reserve 3,850; 55,000 minus 25,000, plus 3,850, plus 5,000) — a 3,850 cent divergence for identical inputs.

The parts split is evaluated before any reserve term. `insurance_parts_cents` is the smaller of covered parts and `stone_limit_parts_cents`. `customer_parts_cents` is `declared_parts_cents` minus `insurance_parts_cents`. `customer_labor_cents` is the greater of 0 and (`declared_labor_cents` minus insurance-funded labor). `store_absorbed_cents` equals the store-absorbed liability. On the worked example above, `insurance_parts_cents` is 37,200, `customer_parts_cents` is 2,800, and `customer_labor_cents` is 15,000.

The final step is the coverage gate. Whether the plan is valid is `is_valid_plan`, which is true only when the pinned registration's `coverage_status` is `ACTIVE`. When it is not true, `customer_parts_cents` is increased by `insurance_parts_cents` and `insurance_parts_cents` is reset to 0 — the customer carries the whole parts cost and the diamond component absorbs nothing. This gate is what makes a lapsed or otherwise non-`ACTIVE` plan bill at full price. The repair's stored `reserve_cents` is the reserve term computed in the chosen variant.

Routing is deterministic from the failure class. When the repair is not a rush, `vendor_shop_code` comes from a fixed routing table (`ROUTE_TABLE`): `STONE_LOSS` routes to `MALCA`, `SETTING` and `PRONG` route to `JEWELCRAFT`, and `RESIZE` and `OTHER` route to `MASTERMELT`. When `vendor_is_rush` is true, the routing is the constant `RUSH_SHOP_CODE` — `CONRUSH` — irrespective of failure class. The bench shop must exist in the shop directory with `vendor_status` of `ACTIVE`; otherwise routing is refused with `ERR_VENDOR_MISSING` (HTTP 422), and a rush routing additionally requires the rush shop to hold a signed alliance agreement, failing which the request is refused with `ERR_VENDOR_AGREEMENT_REQUIRED` (HTTP 422). The shop directory keys each shop by a unique `shop_code`, which is the value stored on the repair as `vendor_shop_code`, and carries `shop_name`, `base_turnaround_days` seeded from the alliance agreement, an optional `rush_surcharge_cents` defaulting to 0, and a computed `open_repair_count` counting the repairs at that shop currently in `ROUTED`, `IN_REPAIR`, or `QC_REVIEW`.

Turnaround is measured in whole calendar days from the intake instant, and the datetime arithmetic is inclusive of the accepted instant. The shop's `base_turnaround_days` fixes `promised_delivery_at` as the accepted instant plus that many days — the `QUOTED_TURNAROUND` reading. When at least one deadline hold has been applied, the commitment becomes the accepted instant plus the base turnaround plus every applied extension, still bounded by the 1.5 multiplier — the `ADJUSTED_TURNAROUND` reading. The ceiling for any single extension request is the accepted instant plus `base_turnaround_days` multiplied by `CEILING_MULTIPLIER` (1.5). Worked reference: a `SETTING` failure that is not a rush routes to `JEWELCRAFT`; with a base turnaround of 7 days the promise lands at the accepted instant plus 7 days and the ceiling is 10.5 days; an applied hold asking for the accepted instant plus 10 days sets the extension to 3 days and stands; a hold asking for the accepted instant plus 11 days is refused because 11 exceeds 10.5.

Breach compensation is tiered on the number of whole overdue days, floored at 0. When the repair is verified, or when an extension request is refused, the overdue count is the delivery instant — or the current instant if delivery has not happened — minus `promised_delivery_at`, in whole days, never below 0. Zero overdue days produces no compensation. One to five overdue days inclusive compensates `loss_liability_cents` multiplied by `PARTIAL_BREACH_PCT` (0.05), rounded half up. Six to fifteen overdue days inclusive compensates the loss liability multiplied by `MAJOR_BREACH_PCT` (0.15), rounded half up. Sixteen or more overdue days compensates the loss liability multiplied by `FULL_BREACH_PCT` (0.25), rounded half up. The compensation is then clipped to the store's remaining credit capacity: it is the lesser of itself and `available_credit_capacity_cents` (`UNBOUND_COMPENSATION` when capacity is ample, `CAPACITY_BOUND_COMPENSATION` when it is not, in which case the store's conserved capacity drains to exactly 0). Worked reference on a 35,000 cent liability: 5 overdue days gives 1,750 cents, 6 overdue days gives 5,250 cents, 16 overdue days gives 8,750 cents, and delivery exactly at the promised instant gives 0. A refused extension records `imposed_breach_adjustment_cents` using `BREACH_COMPENSATION_PCT` (0.05) applied to the pinned loss liability, rounded half up, recorded as a store credit owed to the customer.

### 2.8. Trade-Up and Commission Economics

A trade-up credits a prior purchase's ticket toward a new one. The origin purchase's `base_price_cents` and any `trade_up_credit_cents` it already carries are read; a bonus is added to the origin ticket at `TRADE_UP_BONUS_PCT` (0.10), rounded half up, giving a credited base of the origin ticket plus that bonus. The credit itself is `TRADE_UP_CREDIT_PCT` (0.85) of the credited base, rounded half up — this single rounding over the combined base is the `SINGLE_ROUND` reading, and it is the authoritative value that lands in `trade_up_credit_cents`. The alternative `PER_COMPONENT_ROUND` reading rounds each component separately — the origin ticket at 85 percent, and the rounded bonus at 85 percent — and sums them; it exists because the credit may alternatively be posted to the ledger as two component credits. On the shared worked example the two differ by exactly one cent and the single rounding governs: an origin ticket of 450,018 with an existing credit of 10,050 gives a bonus of 1,005, a credited base of 451,023, and a `SINGLE_ROUND` credit of 383,370 (against 383,369 under per-component rounding). With no existing credit the two readings coincide: an origin ticket of 450,018 gives a credit of 382,515.

`trade_up_floor_cents` is twice the origin purchase's `base_price_cents`. The floor is a hard gate: a new ticket that does not reach it is refused with `ERR_TRADE_UP_FLOOR_NOT_MET` (HTTP 422), and the constant carrying the multiplier is `TRADE_UP_CREDIT_CAP_MULTIPLIER` (2).

The amount actually due at the counter is `net_amount_cents`, computed as `base_price_cents` minus the credited `trade_up_credit_cents`, floored at 0. The credit is also capped at twice the origin ticket when an origin is named. When no origin is named, no credit is applied at all even if a `trade_up_credit_cents` value was supplied on creation: the stored `trade_up_credit_cents` is recomputed, never accepted from the payload. This is the `NO_ORIGIN` reading against `WITH_ORIGIN`. `protection_fee_cents` is the attached bundle's `lifetime_plan_fee_cents`, or 0 when the purchase carries no bundle; on the trade-up preview the sum of `net_amount_cents` and `protection_fee_cents` is reported as `balance_due_cents`. Worked reference: a 900,100 cent ticket against a 450,018 cent origin gives a cap of 900,036, a credit of 383,370 (which is below the cap), a net amount of 516,730, and — with no bundle — a balance due of 516,730; attaching a bundle whose lifetime fee is 19,900 raises the balance due to 536,630. A 900,100 cent ticket with no origin gives a credit of 0, a net amount of 900,100, and a balance due of 900,100. A 900,035 cent ticket against the same origin misses the 900,036 floor by one cent: completion is refused with `ERR_TRADE_UP_FLOOR_NOT_MET` even though the credit would still compute to 383,370.

A trade-up credit may only be stamped on the purchase that leads its console. A purchase that already names an `origin_purchase_id`, or that has already reached `TRADE_UP_APPLIED`, is a dependent and cannot itself be credited; an attempt to stamp a credit on such a purchase is refused with `ERR_TRADE_UP_GUARDIAN_REFERENCE` (HTTP 409).

A custom commission stamps a non-refundable deposit at submission and holds it immutable thereafter. `deposit_cents` is `estimate_amount_cents` multiplied by `deposit_pct`, rounded half up, and it is read from the order row afterwards rather than recomputed from the current estimate. `deposit_pct` defaults to 0.30 and must fall within the closed band of 0.30 (`DEPOSIT_PCT_MIN`) to 0.50 (`DEPOSIT_PCT_MAX`); a percentage below 0.30 is refused with `ERR_INSUFFICIENT_DEPOSIT` (HTTP 422), because the stamped deposit must cover the shop's release requirement.

The forfeitable portion depends on the commission's stage. The `non_refundable_deposit_cents` is the full `deposit_cents` when `design_status` is `COMPLETED`; it is 0 when `design_status` is `DEPOSIT_PAID`, `CAD_REVISION`, or `CAD_APPROVED`; and it is the full `deposit_cents` when `design_status` is `IN_PRODUCTION` or `CANCELLED`. `refundable_deposit_cents` is `deposit_cents` minus `non_refundable_deposit_cents`.

On cancellation, `cancellation_fee_cents` is 0 while `design_status` has not reached `IN_PRODUCTION`. Once `design_status` is `CANCELLED` the fee is the greater of the two candidates: when `revision_count` has reached 3 or more the fee is the costs incurred, and otherwise it is the whole deposit. Costs incurred are `deposit_cents` plus `revision_fee_cents` minus `material_recovery_cents` — the material value recovered from the abandoned build. If the cancellation fee exceeds the deposit, the excess is billed to the customer as `customer_balance_due_cents` (the `COST_BEARING_FORFEIT` reading); otherwise the difference is returned to the customer as `customer_refund_cents` (the `DEPOSIT_BOUNDED_FORFEIT` reading). Worked reference: a 250,000 cent estimate at a 0.40 percentage stamps a 100,000 cent deposit; cancelling out of `CAD_REVISION` with one revision gives no forfeit, a 100,000 cent refund, and no cancellation fee; cancelling out of `IN_PRODUCTION` with three revisions and 20,000 cents of material recovery gives costs incurred of 82,500 cents (100,000 plus a 7,500 cent revision fee, less 20,000), a cancellation fee of 82,500, and a customer refund of 17,500.

### 2.9. Replacement Appraisal Valuation and Insurance Coordination

An appraisal issued from a repair file is valued from the customer's own exposure on that repair, not from the ticket. The base is the repair's pinned `customer_parts_cents` plus its pinned `customer_labor_cents`. When the repair's `repair_status` is `UNREPAIRABLE`, the base is multiplied by `APPRAISAL_MULTIPLIER_UNREPAIRABLE` (1.04) — the unrepairable uplift; otherwise it is multiplied by `APPRAISAL_MULTIPLIER_DEFAULT` (1.00), which leaves it unchanged. The result of that step is rounded half up to a whole cent. A lab-grown stone is then discounted: when the diamond's `stone_kind` is `LAB_GROWN`, the value is multiplied by `LAB_GROWN_FACTOR` (0.65) and rounded half up again. The final figure is `appraised_value_cents`. Worked reference: parts of 2,800 and labor of 15,000 give a base of 17,800; an unrepairable natural stone appraises at 18,512; the default multiplier would leave the same inputs at 17,800; and an unrepairable lab-grown stone appraises at 12,033. This is the `UNREPAIRABLE_MULTIPLIER` reading against `DEFAULT_MULTIPLIER`; the two differ by 712 cents on identical inputs. A third reading, `ORIGIN_TRACEABILITY`, changes no value at all: when the diamond's `origin_registry` is non-null, `traceability_document_url` is populated from that origin document, and it is null when the origin registry is null.

Insurance replacement is coordinated on the registration. Only a `REPLACEMENT`-kind appraisal may be circulated to an insurer; a repair file that carries no issued replacement appraisal cannot support the advice and the request is refused with `ERR_APPRAISAL_REQUIRED` (HTTP 422). Circulating the advice increases the registration's `replacement_claims_used`; a registration whose count is already 1 cannot support a second advice and is refused with `ERR_CLAIM_ALREADY_USED` (HTTP 409). The store's share of the chain's replacement invoice is governed by the state regulation's `replacement_plus_pct` — the share the store may absorb before the `INSURANCE_REPLACEMENT_CAP_PCT` (0.25) applies. Under the first claim the store pays the full invoice and the insurer reimburses `INSURANCE_REPLACEMENT_PCT` (0.75) of it, with the remainder absorbed. On a second claim the store pays at most 25 percent of the invoice, rounded half up. Worked reference for a Texas registration (a `replacement_plus_pct` of 1.0) against an 850,000 cent replacement invoice with no prior claim: the store pays 850,000, the insurer reimburses 212,500, and the store absorbs 637,500; with `replacement_claims_used` already at 1 the store pays 212,500, the insurer reimburses 212,500, and the store absorbs 0.

### 2.10. Customer Credit Posture and Its Recomputation Order

A customer carries a single credit posture: `account_status` (`NO_FILE`, `OPEN`, `SUSPENDED`, or `CLOSED`, starting at `NO_FILE`), `credit_tier` (`NO_FILE`, `TIER_1`, `TIER_2`, or `TIER_3`, starting at `NO_FILE`), `standalone_credit_limit_cents` (starting at 0), `revolving_utilization_bps` (starting at 0), `lifetime_purchase_cents` (starting at 0), `outstanding_balance_cents` (starting at 0), and `lost_inspection_streak` (starting at 0).

`revolving_utilization_bps` expresses the latest balance against the standalone limit in basis points, and is 0 when the limit is 0. `lifetime_purchase_cents` is the sum of `base_price_cents` over the customer's purchases that have reached `COMPLETED` or `TRADE_UP_APPLIED`. `outstanding_balance_cents` is the sum of `adjustment_cents` over the customer's payoff-ledger entries, plus, for every promotional plan that is not yet `PAID`, the `installment_amount_cents` of its current open quarter. `lost_inspection_streak` counts consecutive missed inspections across the customer's registrations and is recomputed whenever any registration enters `LAPSED`.

The tier is recomputed by a weighted score whenever a promotional plan changes status, whenever a registration lapses, and when a suspended account is reinstated. The score is built from three components. The utilization band is 2 when the utilization expressed in basis points reaches `UTIL_VIOLATION_BPS` (8000); otherwise 1 when it reaches `UTIL_WATCH_BPS` (5000); otherwise 0 — including the case where utilization is above 0 but below 5,000 basis points, which also scores 0. The utilization in basis points is the customer's outstanding balance multiplied by 10,000 and divided by the standalone credit limit (the limit treated as at least 1), rounded to a whole basis point. The active-plan component is the number of the customer's promotional plans in `ACCRUING`. The streak component is the customer's `lost_inspection_streak`, capped at `STREAK_COMPONENT_CAP` (3). The raw score is twice the utilization band, plus the active-plan count, plus the streak component.

The tier then follows from that raw score with one override that outranks it. If the customer has any promotional plan in `DEFAULTED`, the tier is `NO_FILE` regardless of the score. Otherwise a raw score of 3 or more gives `TIER_1`; a raw score of exactly 2 gives `TIER_2`; and any lower score gives `TIER_3`. Worked reference: an outstanding balance of 300,000 against a limit of 300,000 gives 10,000 basis points and band 2; with one active plan and a streak of 0 the raw score is 5 and the tier is `TIER_1`; with the streak raised to 1 before evaluation the raw score is 6 and the tier remains `TIER_1`. A balance of 150,000 against a limit of 300,000 gives 5,000 basis points and band 1; with no active plans and a streak of 0 the raw score is 2 and the tier is `TIER_2`; with a streak of 1 the raw score is 3 and the tier becomes `TIER_1`.

Ordering is load-bearing here. When the recomputation is the final step of a lapse cascade, the streak increment produced by that very lapse is included, so the evaluation runs on the post-increment streak — the `STREAK_APPLIED_AFTER_INCREMENT` reading. When the recomputation runs as a step of a payoff or plan-status cascade, the pre-event streak is used — the `STREAK_APPLIED_BEFORE_INCREMENT` reading — and the same customer can therefore read `TIER_2` in the plan cascade and `TIER_1` in the lapse cascade. Implementers must not hoist the tier computation above the streak increment.

Interactions with the customer that recompute the posture take effect in their own places and are described in §3.

### 2.11. Statement Balances and Payment Allocation

A billing statement carries `statement_period` (a label such as `2026-09`, unique per customer), `bucket_totals_cents`, `min_payment_due_cents`, `statement_balance_cents`, and a `statement_status` of `OPEN` or `CLOSED`, starting at `OPEN`.

Payment allocation runs a waterfall across three buckets, filled in a fixed priority order: `PROMOTIONAL` first, then `STANDARD_RETAIL`, then `NEW_ACCOUNT`. Each bucket's capacity is the corresponding customer balance — `promotional_balance_cents`, `retail_balance_cents`, and `new_account_balance_cents` respectively. The payment fills the first bucket to the lesser of the remaining payment and that bucket's capacity, subtracts what it took, and moves to the next bucket until the payment is exhausted. The last bucket absorbs whatever remainder is left. If any payment remains once all three buckets are full, the statement is refused with `ERR_STATEMENT_OVERPAYMENT` (HTTP 422) — the payment may not exceed the sum of the three bucket balances. This is the `CASCADING_OVERFLOW` reading; the `FIRST_BUCKET_ABSORBS` reading is simply the case where the payment is smaller than the promotional balance, so the whole payment lands in `PROMOTIONAL` and the other buckets are untouched. The allocated amounts are reported in `bucket_totals_cents`. The waterfall's own restatement of the same figures names the third bucket `NEW_ACCOUNT` where the reporting key inside `bucket_totals_cents` is `RETAIL`; the two labels denote the same bucket. Worked reference with balances of 140,000 promotional, 60,000 retail, and 90,000 new-account: a 90,000 cent payment allocates 90,000 to `PROMOTIONAL`; a 200,000 cent payment allocates 140,000 to `PROMOTIONAL` and 60,000 to `STANDARD_RETAIL`; a 250,000 cent payment additionally allocates 50,000 to `NEW_ACCOUNT`; and a 300,000 cent payment exceeds the 290,000 cent total capacity and is refused.

`min_payment_due_cents` is the greater of the `MIN_FLOOR_CENTS` floor (5,000 cents) and the sum, over the buckets that received an allocation, of that allocation multiplied by its `min_base_pct`, each rounded half up. The `min_base_pct` applied to a bucket is `MIN_BASE_PCT_HIGH` (0.02) when the bucket's balance reaches `HIGH_BALANCE_THRESHOLD_CENTS` (200,000 cents) and `MIN_BASE_PCT_LOW` (0.01) otherwise, so the floor of 5,000 cents governs small statements.

`statement_balance_cents` is the statement rollup. Line items on the statement each carry an `amount_cents`, a `billable_pct`, and a `line_status`; only lines whose `line_status` is `BILLABLE` participate, and `PAID` and `DISPUTED` lines are excluded before anything else runs. Under the `SUM_THEN_TIER` reading, each billable line's amount is multiplied by its `billable_pct` and rounded half up, the results are summed into a subtotal, a tier fee percentage is selected from that aggregate — 0.03 (`TIER_FEE_PCT_HIGH`) when the subtotal reaches `TIER_BOUNDARY_HIGH_CENTS` (500,000 cents), otherwise 0.02 (`TIER_FEE_PCT_MID`) when it reaches `TIER_BOUNDARY_MID_CENTS` (200,000 cents), otherwise 0.01 (`TIER_FEE_PCT_LOW`) — and the balance is the subtotal multiplied by one plus that percentage, rounded half up. Under the `PER_LINE_TIER` reading, each line selects its own tier from its own rounded amount and is individually uplifted by one plus its own percentage, rounded half up, and the balanced lines are then summed. The rounding order is the discriminator between the two. Worked reference with two billable lines of 250,000 and 260,000 cents at a `billable_pct` of 1.0: `SUM_THEN_TIER` gives a subtotal of 510,000, a 0.03 tier, and a balance of 525,300; `PER_LINE_TIER` gives 255,000 for the first line, 267,800 for the second, and a balance of 522,800 — a 2,500 cent divergence for identical inputs.

### 2.12. Common Resource Properties

Resources created with the full common field set carry four system-managed properties. `id` is a unique, server-minted identifier formatted as a UUID with no type prefix and no enclosing braces. `created_at` is an ISO 8601 timestamp in UTC with exactly three fractional digits (for example `2025-05-24T10:30:00.123Z`) recording when the resource was first written. `updated_at` records when the resource was last modified and is refreshed by every mutation, including mutations performed by a cascade rather than by a direct request. `version` is an integer that starts at 1 and increments by one on every modification to the resource; it is the quantity optimistic concurrency control is asserted against (§2.13).

Two resources in this system are deliberately outside that convention. A payoff ledger entry and a repair hold are immutable records of a single event: they carry only `id` and `created_at`, and neither `updated_at` nor `version` exists on them. Those two entities must not be given the common field set, and no endpoint may assert a version against them.

Nested and computed collections are re-derived rather than stored: a store's `available_credit_capacity_cents`, `store_absorbed_total_cents`, `open_repair_liability_cents`, and `open_inspection_count`; a vendor shop's `open_repair_count`; and a customer's `credit_tier`, `standalone_credit_limit_cents`, `revolving_utilization_bps`, `lifetime_purchase_cents`, `outstanding_balance_cents`, and `lost_inspection_streak` are all quantities maintained in step with the events described in §3.

### 2.13. Optimistic Concurrency Control

Three write operations require the client to assert the version of the parent resource it last observed, and reject the write when that assertion no longer holds.

Creating a financing plan against a purchase requires `expected_purchase_version` in the request body, carrying the client's last observed `version` of the target purchase. If the purchase's current `version` differs, the create is rejected with `ERR_STALE_VERSION` (HTTP 412); a second financing code is a legitimate product for the same purchase, so the state preconditions alone would not have prevented a write the client had not observed.

Logging an inspection visit against a registration requires `expected_registration_version`, carrying the client's last observed `version` of the target registration. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412); a second visit log for a different instant is legitimate under the product semantics, so the visit's own state does not cover the case.

Applying a payoff against a promotional plan requires `expected_plan_version`, carrying the client's last observed `version` of the target plan. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).

Reinstating a defaulted plan likewise requires `expected_plan_version`, and a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).

No other endpoint takes a version field. In particular, appending a ledger entry directly requires `expected_plan_version` as well, since it mutates the plan and must not be applied against a plan state the client has not observed.

### 2.14. Validation Priority Ladder

When a single request violates more than one rule, the lowest-numbered priority wins and its error identifier is the one returned. Priority is global across the request, not per category. The ladder is ordered as follows, and the ordering is normative — in particular the compliance prerequisite at priority 6 is evaluated before any state or business rule, and the frozen-credit hazard at priority 8 outranks every data-validity and fiscal check later in the ladder.

Priority 1 is authentication: `X-User-Role` and `X-User-ID` must be present and `X-User-Role` must name a declared role, else `ERR_UNAUTHENTICATED` (401). Priority 2 is authorization: the acting role must be permitted for the operation, and a role performing another role's exclusive operation is refused with `ERR_UNAUTHORIZED` (403). Priority 3 is existence: the path resource must exist, and on a flat entity the foreign-key fields named in the input are resolved left to right in the order the endpoint's input list declares them; a failure is `ERR_RESOURCE_NOT_FOUND` (404). Priority 4 is state: the target resource must be in a state from which the requested transition is declared, else `ERR_INVALID_STATE` (409). Priority 5 is the optimistic concurrency assertion, `ERR_STALE_VERSION` (412), on the four write operations named in §2.13. Priority 6 is the regulation prerequisite — the governing regulation row for the store's state must exist before state and business rules run — `ERR_REGULATION_TERMS_VIOLATION` (422). Priority 7 is the term and inspection-scheduling compliance check, also `ERR_REGULATION_TERMS_VIOLATION` (422). Priority 8 is the frozen-credit hazard: credit is frozen while any promotional plan of the customer is `DEFAULTED`, giving `ERR_CREDIT_FROZEN` (422), and this outranks every data-validity and fiscal check on the same request. Priority 9 is the account posture requirement that the account carrying the obligation be `OPEN`, giving `ERR_ACCOUNT_NOT_OPEN` (422). Priority 10 is the certified-metal requirement, `ERR_RING_METAL_NOT_CERTIFIED` (422), checked before any coupling underwriting runs. Priority 11 is the origin-document requirement for a natural centre stone over 1.00 carat, `ERR_ORIGIN_DOCUMENT_MISSING` (422). Priority 12 is resource ownership, `ERR_NOT_RESOURCE_OWNER` (403). Priority 13 is the validity-window check, `ERR_WINDOW_EXPIRED` (422). Priority 14 is the extension ceiling, `ERR_HOLD_PROMISE_CEILING` (422). Priority 15 is the retroactive visit check, `ERR_EXTENSION_WINDOW_EXPIRED` (422). Priority 16 is the requirement that a pinned registration still cover the stone under repair, `ERR_PLAN_TERMS_UNSATISFIED` (422). Priority 17 is the requirement that the plan be non-lapsed at intake, `ERR_PLAN_TERMS_UNSATISFIED` (422). Priority 18 is the one-live-plan-per-purchase rule, `ERR_PLAN_ALREADY_EXISTS` (409). Priority 19 is registry resolvability, `ERR_REGISTRY_ROW_MISSING` (422). Priority 20 is the standalone credit ceiling, `ERR_CREDIT_LIMIT_EXCEEDED` (422). Priority 21 is store credit capacity, `ERR_STORE_CREDIT_CAPACITY_EXCEEDED` (422). Priority 22 is the down-payment minimum, `ERR_DOWN_PAYMENT_REQUIRED` (422). Priority 23 is the payoff minimum, `ERR_INSUFFICIENT_PAYOFF` (422). Priority 24 is the trade-up floor, `ERR_TRADE_UP_FLOOR_NOT_MET` (422). Priority 25 is statement overpayment, `ERR_STATEMENT_OVERPAYMENT` (422). Priority 26 is the trade-up guardian rule, `ERR_TRADE_UP_GUARDIAN_REFERENCE` (409). Priority 27 is code uniqueness across stones, bundles, and shops, `ERR_DUPLICATE_STONE_CODE` (409). Priority 28 is the terminal-registration guard, `ERR_REGISTRATION_TERMINATED` (409). Priority 29 is the commission deposit percentage floor, `ERR_INSUFFICIENT_DEPOSIT` (422). Priority 30 is the five-revision ceiling, `ERR_REVISION_LIMIT_REACHED` (409). Priority 31 is the rush alliance agreement, `ERR_VENDOR_AGREEMENT_REQUIRED` (422). Priority 32 is the appraisal prerequisite for an insurance advice, `ERR_APPRAISAL_REQUIRED` (422). Priority 33 is the active-obligations guard on closing a customer file, `ERR_CUSTOMER_ACTIVE_OBLIGATIONS` (409).

Two malformed-input conditions sit outside the ladder and are reported as themselves: a request body that misses a required field, carries an unknown field, or carries a field of the wrong type is refused with `ERR_INVALID_REQUEST` (400); and a declared enum field receiving a value outside its constraint set, or a numeric field outside its declared range, is refused with `ERR_VALIDATION_FAILED` (422).

### 2.15. Nested Resource Retrieval

When a request path contains more than one resource identifier, the identifiers are resolved in strict left-to-right order and the request is rejected at the first one that does not resolve, with `ERR_RESOURCE_NOT_FOUND` (404) and no partial processing. The sub-resource reads under a parent — a store's repairs, credit applications, registrations, inspection visits, or purchases; a vendor shop's repairs; a customer's applications, plans, registrations, diamonds, purchases, commissions, or statements; a repair's appraisals or holds; a plan's payoff ledger entries; a registration's inspection visits or repairs; a purchase's plans, registrations, or derivative trade-up purchases; a diamond's registrations; a bundle's registrations — all follow this order, and a construction or modification operation validates the containing parent's existence and status before any child check.

### 2.16. Cascade and Hierarchy Consistency

State changes propagate. When a child event changes a quantity a parent carries, the parent is reconciled without a separate client request, and each such reconciliation is an ordinary mutation that increments the parent's `version` and refreshes its `updated_at` where the entity carries those fields.

Store-level quantities are recomputed at the end of every repair state transition: `open_repair_liability_cents` sums `loss_liability_cents` across the store's repairs currently in `INTAKE`, `ROUTED`, `IN_REPAIR`, or `QC_REVIEW`. `store_absorbed_total_cents` sums `store_absorbed_cents` across the store's repairs currently in `INTAKE`, `ROUTED`, `IN_REPAIR`, `QC_REVIEW`, or `COMPLETED`. `open_inspection_count` counts the store's registrations whose `coverage_status` is `PENDING_INSPECTION` or `REMINDER_ISSUED`, and is recomputed on every registration transition. `available_credit_capacity_cents` is `credit_capacity_cents` minus `store_absorbed_total_cents` minus the outstanding customer credit, floored at 0 — it is the quantity that drains as the store absorbs cost, and it is this drain that the capacity-bound compensation and the store suspension rule both read. A store also carries `store_code` (unique), `name`, `state_code`, `credit_enabled` (default true), `store_status` (default `OPEN`, one of `OPEN`, `ACTIVE`, `SUSPENDED`), `credit_capacity_cents`, and `store_hold_days` (default 30, the days a completed repair is held before it is abandoned).

The logical clock is a system-wide precondition for every deadline rule. Before any call it reads the fixed startup default `2026-09-01T00:00:00Z` and never falls back to real wall-clock time. An administrative test-driving capability moves it to a supplied `to_iso8601` instant and reports the resulting `current_utc`. Every temporal comparison in §3 — validity windows, simplicity windows, cure deadlines, pickup deadlines, overhaul overdue counts — is evaluated against this logical instant, not against the host clock.
## 3. Business Logic & Workflows

### 3.1. The Counter Credit Conversation

The chain's relationship with a cardholder begins at a sales counter. A `SalesAssociate` or a `CustomerService` operator opens the customer file with a `full_name`, an `email`, and the customer's `state_code` of residence — the state code matters later because it selects the risk-registry row that prices any line the customer asks for. A `phone` number is optional and defaults to null. Email is a unique contact key: a second customer file carrying an email already held by another customer is refused with `ERR_DUPLICATE_EMAIL` (HTTP 409). A newly created customer carries `account_status` of `NO_FILE` and `credit_tier` of `NO_FILE`, an `outstanding_balance_cents` of 0, and no `standalone_credit_limit_cents` at all, so nothing can be financed against the file until a decision opens it.

Credit is taken at the counter through a credit application. A `SalesAssociate` or `CustomerService` operator submits the applicant's `customer_id` and the `store_id` at which the application is taken, the `requested_limit_cents` the customer is asking for, the `requested_purchase_amount_cents` of the pending sale the line would fund, an optional `down_payment_cents` of cash tendered with the request (defaulting to 0), and an optional `declared_annual_income_cents` (defaulting to null, meaning the applicant declared nothing). Intake runs the chain's counter credit pricing — `credit_limit_registry_pricing` — immediately and stamps the resulting `policy_tier` on the row, sets `decision_status` to `PENDING`, and sets `expires_at` to the creation instant plus the chain's declared validity period in hours (`DECISION_VALIDITY_HOURS`). Nothing about the customer's own credit posture changes at intake; the application is a proposal and binds only itself.

The store matters. Credit runs only where a store has been opened and activated, and a store declares whether the counter credit program is offered at all through `credit_enabled`, which defaults to true. A store is opened by a chain-level administrator with a unique `store_code`, a display `name`, its `state_code`, a `credit_capacity_cents` ceiling, and a `store_hold_days` window (default 30) that will later govern abandoned repairs; its `store_status` starts at `OPEN`, and it must be moved to `ACTIVE` before it may sell credit.

Decisioning is the `CreditAnalyst`'s exclusive ground. The analyst supplies a `decision`, one of `APPROVE_FULL`, `APPROVE_COUNTERED`, or `DECLINE`, against an application that is still `PENDING`. A full approval requires that the current logical instant is at or before the application's `expires_at`, that a registry row resolves for the applicant's state and the application's `policy_tier` with a `min_ticket_cents` no greater than the requested limit (falling back to the global row), and that the store's `store_status` is `ACTIVE`. When it succeeds, the granted tier `decision_tier` equals the application's `policy_tier`; `approved_limit_cents` takes the selected row's `base_limit_cents`; `min_down_payment_required_cents` is the selected row's percentage applied to the requested purchase amount and rounded up to a whole cent; `down_payment_shortfall_cents` is the amount by which the tendered down payment falls short of that minimum, floored at 0; and `decision_rule_id` names the winning registry row. The customer's posture then moves in the same operation: `credit_tier` is set to the granted tier, `account_status` becomes `OPEN` if it had been `NO_FILE`, `standalone_credit_limit_cents` is set to the granted limit, and `revolving_utilization_bps` is recomputed from the agreed-for utilization band. The application's `version` increments by one and its `updated_at` is refreshed.

A counteroffer is deliberately narrower. An `APPROVE_COUNTERED` decision requires the application to be `PENDING`, the instant to be at or before `expires_at`, and a `TIER_1` registry row to resolve for the applicant's state at a `min_ticket_cents` no greater than the requested limit. It sets `decision_tier` to `TIER_1` and `approved_limit_cents` to that row's `base_limit_cents`, recomputes `min_down_payment_required_cents` at the `TIER_1` percentage, and recomputes the shortfall against it — but it changes nothing on the customer file. The counteroffer binds only the application row until the customer accepts. A flat `DECLINE` needs only that the application be `PENDING`; the resulting `decision_status` of `DECLINED` is terminal, and the customer file is untouched, so an applicant whose only application was declined remains at `NO_FILE`.

Accepting or declining a counteroffer is the cardholder's own act, and it is the one place in this system where the acting identity is a persisted entity. The `Customer` role carries `X-User-ID` equal to the acting customer's `id`, and the operator-level ownership check compares the application's `customer_id` to that identifier. Accepting requires the application to be `COUNTERED` and the instant to be at or before `expires_at`; it moves `decision_status` to `APPROVED` and then applies the customer-side effects of a full approval — `credit_tier` of `TIER_1`, `account_status` to `OPEN` if it was `NO_FILE`, `standalone_credit_limit_cents` set to `approved_limit_cents`, `revolving_utilization_bps` recomputed — and increments the application's `version`. Declining the counteroffer moves `decision_status` to `DECLINED` and leaves every customer field exactly as it was, `account_status` included, and does not consult the validity window at all.

A validity sweep, run by a `CreditAnalyst`, retires applications nobody acted on. Every application still `PENDING` and every application `COUNTERED` at an instant strictly after its `expires_at` is set to `EXPIRED`, which is terminal alongside `DECLINED`. The sweep reports `expired_count` and `expired_application_ids`. Acting on an application outside its window is refused with `ERR_WINDOW_EXPIRED` (HTTP 422), and that refusal is what the sweep exists to make unnecessary.

### 3.2. Promotional Financing: Opening, Capitalizing and Paying Off

A purchase ticket is opened by a `SalesAssociate` with the buyer's `customer_id`, the selling `store_id`, the `base_price_cents` of the new item before any credit, and optionally a centre `diamond_id`, a protection `bundle_id`, and an `origin_purchase_id` if the sale is a trade-up. The ticket starts in `PENDING`, and its `protection_fee_cents` is the attached bundle's `lifetime_plan_fee_cents` when a bundle was taken and 0 otherwise. The ticket's own `trade_up_credit_cents` is recomputed rather than accepted, so a value supplied at creation cannot be used to inflate the credit (§2.8).

Financing is then attached by a `SalesAssociate` or a `CustomerService` operator. Opening a plan requires the cardholder's `customer_id`, the `purchase_id` being financed, the `plan_code` chosen at the counter, and — because a second financing code is a perfectly legitimate product for the same ticket — the client's last observed `expected_purchase_version`. The plan is priced immediately by `promo_plan_tiering`, which derives `promotional_apr_pct`, `deferred_months`, `simplicity_months`, `deferral_basis_points`, `principal_cents`, `installment_quarter_cents`, `installment_amount_cents`, and `merchant_deferral_fee_cents` as described in §2.5. The plan starts in `ACCRUING` with `deferred_interest_accrued_cents` of 0, `total_paid_cents` of 0, `paid_at` null, and `deferred_interest_accrued_cents`-free `simplicity_expires_at` set to the creation instant plus `simplicity_months`. The financed ticket's `purchase_status` moves from `PENDING` to `FINANCED` — the transition requires the ticket's `customer_id` to equal the plan's — and the ticket's `version` increments by one. Only one live plan may reference a ticket: a second non-terminal plan naming the same `purchase_id` is refused with `ERR_PLAN_ALREADY_EXISTS` (HTTP 409). A customer who already carries a defaulted plan cannot open new financing at all; the frozen-credit hazard described in §3.7 refuses it with `ERR_CREDIT_FROZEN` (HTTP 422).

Capitalization is the event the promo clock is designed around, and it belongs to a `CreditAnalyst` running a scheduled sweep. Any plan still `ACCRUING` when the current instant is strictly after `simplicity_expires_at` has its deferred interest converted into principal. The sweep appends a payoff-ledger entry whose `entry_kind` is `CAPITALIZATION` and whose `direction` is `INCREASE`, with `amount_cents` equal to the interest that had accrued and `adjustment_cents` equal to the positive of that amount. The plan's `principal_cents` is increased by the accrued interest, `deferred_interest_accrued_cents` falls back to 0, `final_settlement_amount_cents` becomes the new principal, `plan_status` becomes `CAPITALIZED`, and `merchant_deferral_fee_cents` is zeroed because capitalization cancels the merchant's deferral credit. The plan's `version` increments by one, and the cardholder's `outstanding_balance_cents` and utilization band are recomputed. The sweep reports `capitalized_count` and `capitalized_plan_ids`.

Paying off inside the window is the outcome the customer wants, and it takes the `CustomerService` or `SalesAssociate` desk. A payoff on an `ACCRUING` plan requires the current instant to be at or before `simplicity_expires_at`, requires the submitted `amount_cents` to be at least the plan's `principal_cents` plus its `deferred_interest_accrued_cents`, and requires the client's `expected_plan_version` to match the plan's current `version`. The payment appends a ledger entry whose `entry_kind` is `LUMPSUM_PAYOFF`, whose `direction` is `DECREASE`, whose `amount_cents` is the submitted amount, whose `adjustment_cents` is the negative of that amount, and whose `reference_bucket` is `PROMOTIONAL`; its `entry_sequence` is one past the plan's previous maximum. The amount is added to `total_paid_cents`; `plan_status` becomes `PAID` and `paid_at` is stamped with the current instant; `deferred_interest_accrued_cents` and `final_settlement_amount_cents` both fall to 0, which is the forgiveness the promo promised; and `merchant_deferral_fee_cents` is zeroed, refunding the merchant's deferral fee. The plan's `version` increments by one and the cardholder's `outstanding_balance_cents`, utilization band, and recomputed tier all follow. A payoff below the settlement amount is refused with `ERR_INSUFFICIENT_PAYOFF` (HTTP 422), a payoff outside the window with `ERR_WINDOW_EXPIRED` (HTTP 422), and a payoff carrying a version the plan has already moved past with `ERR_STALE_VERSION` (HTTP 412). Paying off a `CAPITALIZED` plan is the same operation with a simpler bar — the amount must reach `principal_cents` and there is no window to satisfy — and it too appends a `LUMPSUM_PAYOFF` entry, sets `paid_at`, clears the settlement amount, and recomputes the cardholder's balance and tier.

Voiding is for plans that never took a cent. A `CustomerService` operator may cancel an `ACCRUING` plan only when `total_paid_cents` is exactly 0 and no ledger entry of any kind exists for it; the plan moves to `VOIDED`, which is terminal, and `merchant_deferral_fee_cents` and `deferred_interest_accrued_cents` are both zeroed. The financed ticket walks back from `FINANCED` to `PENDING`, and the cardholder's outstanding balance and tier are recomputed.

Reinstating a defaulted plan is an analyst action. It requires `plan_status` of `DEFAULTED`, the account status to be `SUSPENDED`, and the client's `expected_plan_version`. The plan returns to `ACCRUING` — the cycle `DEFAULTED` to `ACCRUING` and back is permitted — its `simplicity_expires_at` is reset to the current instant plus `simplicity_months` so the deferral clock restarts, and its `version` increments. The cardholder's `account_status` returns to `OPEN`, their `credit_tier` is recomputed, and their `standalone_credit_limit_cents` is restored from the `base_limit_cents` of the registry row named by the `decision_rule_id` of their most recent approved application.

Ledger entries can also be appended directly, by a `CustomerService` operator or a `CreditAnalyst`, against the plan's `plan_id` with an `entry_kind`, a `direction`, an `amount_cents`, an `adjustment_cents`, an optional `reference_bucket`, and the client's `expected_plan_version`. Such an append takes the next `entry_sequence` after the plan's current maximum, stamps its `projected_total_cents` from the payoff-ledger projection described below, adjusts `total_paid_cents` for a `DECREASE` entry, and increments the plan's `version` by one.

The payoff-ledger projection reads a plan's full entry history in chronological order — ordered by `recorded_at` ascending, with `entry_sequence` ascending as the tie-break, and used only as a tie-break, never as a business input. Two readings of the projected balance exist. The base reading, which is artifact-independent, starts from `principal_cents`, adds the plan's running deferral accrual, adds the `amount_cents` of every entry whose `direction` is `INCREASE`, and subtracts the `amount_cents` of every entry whose `direction` is `DECREASE`. The reference-bucket reading instead looks only at entries whose `reference_bucket` is `PROMOTIONAL`, the bucket constant `PROMOTIONAL_BUCKET`. If no such entry exists, it falls back to the base reading exactly. If one does, the first such entry's `amount_cents` is taken as the `invariant` — the amount the customer promised to pay — and the `drift` is the sum of the `amount_cents` of all `DECREASE` entries among the `PROMOTIONAL` entries, minus that `invariant`; the projected total is the `invariant` plus the `drift`. The practical difference is that a payment booked to a bucket other than `PROMOTIONAL` never moves the promotional payoff figure, while it does move the artifact-independent figure. Worked reference: a 450,000 cent principal at 26.99 percent accruing 65,220 cents over 196 days projects 515,220 cents under both readings when no entries exist; after a 50,000 cent `PROMOTIONAL`-referenced payoff the base reading gives 465,220 and the reference reading gives 465,220 plus a drift of 0, so the two still agree; after a second 50,000 cent payoff misdirected to `RETAIL` the base reading falls to 415,220 while the reference reading stays at 465,220.

### 3.3. Registering a Lifetime Plan and Keeping It Valid

A lifetime diamond-and-service plan is registered at the counter by a `SalesAssociate` or a `StoreManager` against the `customer_id`, the covered `purchase_id`, the specific `diamond_id`, the `store_id` of record, the governing `bundle_id`, and a `plan_term_months`. The registration starts in `PENDING_INSPECTION` with `is_valid` false; `registered_at` is the current instant; `inspection_due_at` is that instant plus the bundle's `inspection_interval_days`; `cure_expires_at` is that due instant plus the lapse cure window, which is the governing state regulation's `lapse_cure_days` when a regulation row is registered for the store's state and the bundle's `inspection_cure_days` otherwise; `last_inspection_at` and `next_inspection_at` are null until the first inspection is claimed; `missed_inspection_count`, `renewal_count`, and `replacement_claims_used` start at 0. The store's `open_inspection_count` is recomputed at once, because a registration in `PENDING_INSPECTION` counts against it.

Registration conversion has a compliance gate in front of it. If no regulation row exists for the store's `state_code`, the registration cannot be originated and the attempt is refused with `ERR_REGULATION_TERMS_VIOLATION` (HTTP 422), the same refusal that fires when the requested `plan_term_months` exceeds the state's `max_plan_term_months` or when a state with a nonzero `inspection_required_months` would leave the plan unscheduled. A natural centre stone heavier than 1.00 carat needs its `origin_registry` document on file, and a registration naming such a stone without one is refused with `ERR_ORIGIN_DOCUMENT_MISSING` (HTTP 422). A customer account that is not open cannot carry a new registration: the posture requirement refuses it with `ERR_ACCOUNT_NOT_OPEN` (HTTP 422).

Reminder scheduling is driven by elapsed whole days since `registered_at`. For a registration on cycle `cycle_index`, where the first cycle is `FIRST_CYCLE_INDEX` (1) and the index advances each time an inspection is claimed, the reminder window opens at `registered_at` plus the bundle's `inspection_interval_days` multiplied by the cycle index, less the reminder lead of 14 days (`REMINDER_LEAD_DAYS`), and closes at `registered_at` plus the interval multiplied by the cycle index plus the bundle's `inspection_cure_days`. The number of reminder visits the schedule calls for is 1 when the elapsed whole days have reached the window-open instant but not yet the interval boundary, 1 again when they fall between the interval and the cure deadline inclusive, and 0 both before the window opens and after the cure deadline passes — so the window closes inclusively. Worked reference for a registration dated 2026-03-05 with a 180-day interval and a 30-day cure: 143 elapsed days spawn no visit; 166 days spawn exactly one; 180 days spawn one; 210 days still spawn one; and 211 days spawn none, because at that point the registration is to be lapsed rather than reminded. These two readings are the `EARLY_CYCLE` and `OPEN_WINDOW` variants.

A `StoreManager` drives the reminder sweep. A registration in `PENDING_INSPECTION` whose due instant is within 14 days of the current instant, and whose bundle is still `CURRENT`, moves to `REMINDER_ISSUED` and spawns an inspection visit for the registration and its store with `result` of `SCHEDULED`, `inspection_status` of `SCHEDULED`, and a `scheduled_for_at` equal to the due instant; the registration's `version` increments. A registration already `ACTIVE` or in `GRACE_PERIOD` whose `next_inspection_at` minus 14 days has been reached behaves the same way, spawning a visit scheduled at `next_inspection_at`; the `ACTIVE` path also increments the store's `open_inspection_count`. The cycle `ACTIVE` to `REMINDER_ISSUED` and back to `ACTIVE` or `GRACE_PERIOD` is permitted and is the normal rhythm of a kept-up plan. A registration in `RENEWED` also returns to `PENDING_INSPECTION` on this sweep, with `is_valid` false and a fresh scheduled visit for its due instant. The sweep reports `reminded_count` and `reminded_registration_ids`.

The store visit itself is logged by a `StoreManager` either against the registration with a `visit_at` and a `result`, or as a standing visit record with a `registration_id`, a `store_id`, a `visit_at`, a `result` of `SCHEDULED`, `CLAIMED`, or `NO_SHOW`, an optional `scheduled_for_at`, and the client's last observed `expected_registration_version`. A visit logged earlier than the registration's current `inspection_due_at` is rejected with `ERR_EXTENSION_WINDOW_EXPIRED` (HTTP 422) — retroactive back-dating beyond one cycle is not allowed. Logging a visit against a registration whose `version` has moved past what the client observed is rejected with `ERR_STALE_VERSION` (HTTP 412).

The registration-scoped visit log is the operation that advances coverage, and it has two outcomes. A visit claimed at or before the registration's `inspection_due_at` is timely: the registration's `coverage_status` becomes `ACTIVE` and `is_valid` becomes true. A visit claimed strictly after `inspection_due_at` but at or before `cure_expires_at` is late but cured: `coverage_status` becomes `GRACE_PERIOD`, and `is_valid` is true there as well — a cured gap is not a miss. Both paths share the same housekeeping: `last_inspection_at` is set to the visit instant, `next_inspection_at` is set to that instant plus the bundle's `inspection_interval_days`, `inspection_due_at` is set equal to `next_inspection_at`, and `cure_expires_at` is set to `next_inspection_at` plus the lapse cure window (the state's value when a regulation row is registered, the bundle's otherwise). The claimed visit itself takes `inspection_status` of `CLAIMED`, `claimed_at` of the current instant, and `result` of `CLAIMED`. On the timely path only, every other visit of that registration still in `SCHEDULED` becomes `NO_SHOW`, the store's `open_inspection_count` decrements by one, and the cardholder's `lost_inspection_streak` resets to 0, because a claimed inspection resets the consecutive-miss counter; the registration's `version` increments. On the cured path the streak is deliberately left unchanged and the other scheduled visits are left alone. Attempting either against a registration already in a terminal `coverage_status` of `TERMINATED` or `VOID` is refused with `ERR_REGISTRATION_TERMINATED` (HTTP 409), and a visit falling outside the cure window is refused with `ERR_WINDOW_EXPIRED` (HTTP 422).

The two visit-record actions are narrower. Marking a scheduled visit claimed requires `inspection_status` of `SCHEDULED` and a registration currently in `PENDING_INSPECTION`, `REMINDER_ISSUED`, or `GRACE_PERIOD`; the record becomes `CLAIMED` with `claimed_at` supplied or stamped, and the registration advances to `ACTIVE` or `GRACE_PERIOD` exactly as above depending on whether the visit instant fell at or before the due instant. Marking a visit as a no-show requires `inspection_status` of `SCHEDULED` and a current instant strictly after the visit's `scheduled_for_at`; the record becomes `NO_SHOW`, which is terminal, and the registration's coverage is left untouched — the lapse decision belongs to the sweep.

Lapsing is a `CreditAnalyst` sweep and it is where the plan's cost moves onto the customer. Any registration still in `PENDING_INSPECTION` or `REMINDER_ISSUED` at an instant strictly after its `cure_expires_at` becomes `LAPSED` with `is_valid` false; `missed_inspection_count` increments by one; every visit of the registration still in `SCHEDULED` becomes `NO_SHOW`; the store's `open_inspection_count` decrements by one; and the cardholder's `lost_inspection_streak` increments by one, after which the tier is recomputed on the post-increment streak. The sweep reports `lapsed_count` and `lapsed_registration_ids`. Whatever has already been declared for repairs pinned to the registration is left alone: a repair still in `INTAKE`, `ROUTED`, or `IN_REPAIR` keeps the `loss_liability_cents` that was pinned at its intake, because a lapse never recomputes an already-declared liability.

Renewing a lapsed plan is a `StoreManager` decision. It requires `coverage_status` of `LAPSED`, a customer `account_status` of `OPEN` or `NO_FILE`, and — when the customer's `credit_tier` is `TIER_1` — fewer than two prior renewals. The registration's `renewal_count` increments, `coverage_status` becomes `RENEWED`, `registered_at` is reset to the current instant so the inspection clock restarts, `inspection_due_at` becomes that instant plus the bundle interval, `cure_expires_at` becomes the new due instant plus the cure window, the cardholder's `lost_inspection_streak` resets to 0, and the registration's `version` increments. A renewal does not by itself restore coverage: the registration sits in `RENEWED`, with `is_valid` false, until the reminder sweep returns it to `PENDING_INSPECTION`.

Termination ends a plan on demand. A `StoreManager` or a `CustomerService` operator may terminate a registration currently in `PENDING_INSPECTION`, `REMINDER_ISSUED`, `ACTIVE`, or `GRACE_PERIOD`, provided no repair referencing it is in `INTAKE`, `ROUTED`, `IN_REPAIR`, or `QC_REVIEW`. The result is `TERMINATED`, with `is_valid` false, every scheduled visit of the registration marked `NO_SHOW`, and the store's `open_inspection_count` decremented. A separate path terminates the covered registration automatically when the covered purchase is traded up (§3.5). Voiding is narrower still and belongs to a chain-level administrator: a registration in `PENDING_INSPECTION` may be voided only when no regulation row exists for the store's state, producing the terminal `VOID` status and decrementing the store's open inspection count.

One derived property governs everything downstream: `is_valid` is true only while `coverage_status` is `ACTIVE`, and it is the gate that decides whether a new repair's liability is split with the diamond component or billed wholly to the customer.

### 3.4. Repairs at the Bench

A repair enters the system at a store counter. A `StoreManager` or a `SalesAssociate` intakes it with the `customer_id` who brought the item in, the `store_id` of intake, the `diamond_id` of the stone under repair, the `registration_id` of the governing lifetime plan as pinned at that instant, the `failure_class` (one of `STONE_LOSS`, `SETTING`, `PRONG`, `RESIZE`, or `OTHER`), the `declared_parts_cents` and `declared_labor_cents` quoted by the bench, an optional `vendor_is_rush` flag defaulting to false, and an optional `declared_loss_liability_cents`. Intake pins two things that are never recomputed: `accepted_at`, the intake instant from which every turnaround deadline is measured, and `loss_liability_cents`, the result of `repair_loss_liability` evaluated against the coverage as it stood at that moment. The repair starts in `INTAKE`, and the store's `open_repair_liability_cents` is recomputed straight away.

Intake refuses several things. A registration already `TERMINATED` or `VOID` cannot be named, and neither can one whose terms no longer cover the stone under repair — both are `ERR_PLAN_TERMS_UNSATISFIED` (HTTP 422). A registration that has already `LAPSED` routes the repair to full-price billing and is likewise refused at intake with `ERR_PLAN_TERMS_UNSATISFIED` (HTTP 422). A store whose available credit capacity cannot cover the obligation being booked refuses the intake with `ERR_STORE_CREDIT_CAPACITY_EXCEEDED` (HTTP 422), and a natural centre stone over 1.00 carat arriving without an `origin_registry` document is refused with `ERR_ORIGIN_DOCUMENT_MISSING` (HTTP 422).

Stones have their own custody ledger, and it is not cosmetic. A stone is registered with a unique `stone_code`, a `stone_kind` of `NATURAL` or `LAB_GROWN`, its `carat` weight, and an optional `origin_registry` naming the Kimberley-process or lab registry it is filed with. Its `owner_customer_id` is set when the owning purchase completes, and its `custody_status` tracks physical control: `IN_CASE` at the counter, `IN_VAULT` in store stock, `AT_VENDOR` at a bench, and `WITHDRAWN` when it leaves the chain's custody for good. A duplicate `stone_code` — and likewise a duplicate bundle or shop code — is refused with `ERR_DUPLICATE_STONE_CODE` (HTTP 409).

Routing a repair is a `StoreManager` action and it freezes the customer-facing promise. Routing requires the repair to be in `INTAKE` and the shop named by the routing rule to exist with a `vendor_status` of `ACTIVE`; a missing or retired shop is refused with `ERR_VENDOR_MISSING` (HTTP 422), and a rush routing whose shop holds no signed alliance agreement is refused with `ERR_VENDOR_AGREEMENT_REQUIRED` (HTTP 422). On success the repair's `vendor_shop_code` is stamped with the routing result, `promised_delivery_at` is stamped as the intake instant plus that shop's `base_turnaround_days`, `repair_status` becomes `ROUTED`, the stone's `custody_status` becomes `AT_VENDOR`, the store's open repair liability is recomputed, and the repair's `version` increments. A `StoreManager` also records the stone's arrival at the bench, which requires `ROUTED` and a custody of `AT_VENDOR` and moves the repair to `IN_REPAIR`; submitting the finished piece for quality review requires `IN_REPAIR` and a custody of `AT_VENDOR`, moves the repair to `QC_REVIEW`, and returns the stone to `IN_VAULT`.

Verification closes a successful repair and is where several obligations land at once. It requires `QC_REVIEW` and, critically, that the store's `available_credit_capacity_cents` can cover the repair's `loss_liability_cents` — capacity is checked before the liability is booked, not after. On success the repair becomes `COMPLETED`, its `pickup_deadline_at` is stamped as the current instant plus the store's `store_hold_days`, and the stone returns to `IN_CASE`. A replacement appraisal is then issued out of the repair file at the value described in §2.9, its traceability URL taken from the stone's `origin_registry`. A purchase is opened against the appraised value — `base_price_cents` equal to the appraisal's `appraised_value_cents`, starting in `PENDING`, with its own `trade_up_credit_cents` set to the lesser of the repair's `loss_liability_cents` and the appraised value. The lifetime registration that covered the damaged diamond becomes `TERMINATED`. The store's `open_inspection_count` decrements and its `open_repair_liability_cents` is recomputed. The repair records the issued appraisal in `stored_appraisal_id` and increments its `version`. If the promised delivery instant has already passed at verification, the breach compensation described in §2.7 is evaluated and recorded as a store credit owed to the customer.

A loss can also be declared rather than repaired. A `StoreManager` may declare a stone-loss repair unrepairable from `QC_REVIEW`, from `ROUTED`, or from `IN_REPAIR`, provided the failure class is `STONE_LOSS`; the repair becomes `UNREPAIRABLE`, the stone's custody becomes `WITHDRAWN`, and a replacement appraisal is issued at the unrepairable multiplier. Declaring a verified loss is available only from `QC_REVIEW` and only while the stone's custody is `AT_VENDOR` or `IN_VAULT`; the repair becomes `VERIFIED_LOSS`, custody becomes `WITHDRAWN`, an appraisal is issued, the store's liability is recomputed, and — explicitly — the `loss_liability_cents` declared at intake is not recomputed here. `COMPLETED`, `UNREPAIRABLE`, `VERIFIED_LOSS`, and `ABANDONED` are the terminal repair states.

Deadline extensions are recorded as holds. Each hold is a record of a single evaluation, and its evaluation state is `EVALUATING`, which resolves to either `APPLIED` or `REJECTED` and never persists beyond that. A `StoreManager` requests one against a repair in `ROUTED` or `IN_REPAIR` by naming the `repair_id` and the `extended_promised_delivery_at` the customer is asking for. If the requested instant does not push the promise past the accepted instant plus 1.5 times the shop's base turnaround, the hold is `APPLIED`: the hold's `deadline_adjusted` flag is true, its `extension_days` is the whole-day difference between the requested instant and the promise it replaces, the repair's `promised_delivery_at` takes the requested instant, and the repair's `version` increments. If it does push past that ceiling, the hold is `REJECTED`, `deadline_adjusted` is false, the original promise stands untouched, and the hold records an `imposed_breach_adjustment_cents` computed from the repair's pinned loss liability at 5 percent and recorded as a store credit owed to the customer. Either way the hold carries a `recorded_at` instant and only the two identifiers `id` and `created_at` beyond that, since a hold is an immutable event record. A request past the ceiling is refused with `ERR_HOLD_PROMISE_CEILING` (HTTP 422).

Repairs no one collects are swept by a `CustomerService` operator. A repair in `COMPLETED` whose `pickup_deadline_at` is strictly before the current instant becomes `ABANDONED`, the store takes constructive custody of the stone with a `custody_status` of `IN_VAULT`, and the store's open repair liability is recomputed. The sweep reports `abandoned_count` and `abandoned_repair_ids`.

The store's own posture is driven by the same numbers. A store in `OPEN` moves to `ACTIVE` on activation, which requires at least one registry row available on its state code or the global fallback. A store in `ACTIVE` is suspended by a chain-level administrator when its `open_repair_liability_cents` has outrun its `available_credit_capacity_cents`; suspension sets `store_status` to `SUSPENDED`, declines every pending credit application taken at that store, and blocks all further repair intake at that store with `ERR_STORE_CREDIT_CAPACITY_EXCEEDED` (HTTP 422). A suspended store returns to `ACTIVE` once its liability is back inside its capacity. Every one of these transitions increments the store's `version`.

### 3.5. Appraisals, Insurance Replacement and the Trade-Up Console

Appraisals are issued out of a repair file by a `StoreManager` or a `CustomerService` operator, naming the `repair_id`, the `customer_id` the appraisal is to name, an `appraisal_kind` of `INSURANCE` or `REPLACEMENT`, and an optional `insurance_schedule_ref`. The issued row carries the `appraised_value_cents` computed by `replacement_appraised_value`, a `traceability_document_url` populated from the stone's `origin_registry` when that registry is non-null and left null otherwise, an `appraisal_status` of `ISSUED`, and a `circulated_at` equal to the issuance instant. Issuing a newer replacement appraisal for a repair file supersedes the older one: when another replacement appraisal already exists for the same `repair_id`, the earlier row's `appraisal_status` becomes `SUPERSEDED`, and only `SUPERSEDED` is terminal for an appraisal.

Insurance coordination is the aftercare desk's job. Circulating a replacement appraisal to the insurer requires the appraisal to be of kind `REPLACEMENT` and the registration covering the stone to have `replacement_claims_used` below 1; a repair carrying no issued replacement appraisal cannot support the advice and is refused with `ERR_APPRAISAL_REQUIRED` (HTTP 422), and a second advice against a registration that has already used its claim is refused with `ERR_CLAIM_ALREADY_USED` (HTTP 409). The circulation moves `appraisal_status` to `CIRCULATED`, takes the mandatory `insurance_schedule_ref`, and increments the registration's `replacement_claims_used`. The store's exposure on the replacement invoice follows the state regulation's `replacement_plus_pct` and the 25 percent cap described in §2.9, and the store's open inspection count is not affected either way.

The trade-up console is where an old ticket becomes money toward a new one. A purchase ticket carries its own `trade_up_credit_cents`, a `trade_up_floor_cents` of twice its own ticket, and a `net_amount_cents` reflecting whatever credit it took (§2.8). A `CustomerService` operator or a `StoreManager` may stamp an additional credit onto a purchase by naming an `additional_credit_cents`; the amount is added to the purchase's `trade_up_credit_cents` and the purchase's `version` increments. Only the leader of a console may be credited: a purchase already naming an `origin_purchase_id`, or one already `TRADE_UP_APPLIED`, is a dependent and stamping a credit on it is refused with `ERR_TRADE_UP_GUARDIAN_REFERENCE` (HTTP 409). A `SalesAssociate` or a `StoreManager` can also preview what completing a ticket would produce, reading `trade_up_credit_cents`, `trade_up_floor_cents`, `net_amount_cents`, and `balance_due_cents` for a prospective `origin_purchase_id` without changing anything.

Completing a purchase is the `SalesAssociate`'s act and it has five preconditions. The ticket must be in `PENDING` or `FINANCED`; the customer's `account_status` must be `OPEN`; the customer must hold an approved credit application whose `approved_limit_cents` reaches the ticket's `net_amount_cents`; the customer's `outstanding_balance_cents` plus that net amount must not exceed their `standalone_credit_limit_cents`; and, when the ticket names an `origin_purchase_id`, its `base_price_cents` must reach twice the origin ticket, failing which the completion is refused with `ERR_TRADE_UP_FLOOR_NOT_MET` (HTTP 422). On success the completion runs a fixed sequence. The ticket's `purchase_status` becomes `COMPLETED` and its `completed_at` is stamped. The customer's `outstanding_balance_cents` is increased by the net amount and their `lifetime_purchase_cents` by the ticket's `base_price_cents`. Every stone attached to the ticket takes the customer as `owner_customer_id` and returns to `IN_CASE`. When the ticket names an origin, that origin ticket becomes `TRADE_UP_APPLIED` and, if it carried a live promotional plan, that plan becomes `PAID` with a ledger entry of kind `TRADE_UP_CREDIT` — one of the ledger's entry kinds alongside `INSTALLMENT`, `LUMPSUM_PAYOFF`, and `CAPITALIZATION` — with direction `DECREASE` and an `amount_cents` equal to the trade-up credit. When the origin ticket carries a live lifetime registration, that registration becomes `TERMINATED` and exactly one fresh registration for the new stone starts at `PENDING_INSPECTION`; when the origin carries no registration, none is created. Finally the customer's outstanding balance and tier are recomputed and the store's open inspection count is recomputed, because the retirement of the old plan and the opening of the new one must leave that population unchanged. The ticket's `version` increments.

A surrendered stone also moves in custody. When a completed trade-up names an origin purchase that transferred a particular stone, that stone's `custody_status` becomes `IN_VAULT`, returning it to chain stock rather than to the customer.

### 3.6. Custom Commissions: Deposits, Revisions and Cancellation

A bespoke commission is opened by a `SalesAssociate` or a `StoreManager` with the commissioning `customer_id`, the `store_id` of record, the quoted `estimate_amount_cents`, and an optional `deposit_pct`. The deposit is stamped at submission by `custom_design_deposit_and_forfeit`: `deposit_cents` is the estimate multiplied by `deposit_pct` and rounded half up, and it is never recomputed afterwards, so a later change to the estimate does not move it. The order starts in `DEPOSIT_PAID`. A `deposit_pct` below 0.30 is refused with `ERR_INSUFFICIENT_DEPOSIT` (HTTP 422), the same code that covers a recomputed deposit too small to cover the shop's release requirement; an alloy outside the certified production metal list is refused with `ERR_RING_METAL_NOT_CERTIFIED` (HTTP 422) before any underwriting runs; and a commission naming a natural centre stone over 1.00 carat without its `origin_registry` document is refused with `ERR_ORIGIN_DOCUMENT_MISSING` (HTTP 422).

Revisions belong to the customer, acting on their own commission. Requesting a CAD revision requires the design to be in `DEPOSIT_PAID` or `CAD_REVISION` and the `revision_count` to be below 5; a sixth request is refused with `ERR_REVISION_LIMIT_REACHED` (HTTP 409). Each accepted request increments `revision_count`. The first two revisions are free — the free limit is `FREE_REVISION_LIMIT`, which is 2 — so `free_revisions_used` increments and `revision_fee_cents` is left alone — and from the third onward an additional 2,500 cents (`CAD_REVISION_FEE_CENTS`) is added to `revision_fee_cents`. The design moves to `CAD_REVISION` and the order's `version` increments. Approving the CAD document is likewise the customer's act: from `CAD_REVISION` the design becomes `CAD_APPROVED`, `approved_at` is stamped, and `non_refundable_deposit_cents` takes the full `deposit_cents`, locking the money as forfeitable.

Releasing to the workshop is a `StoreManager` step. From `CAD_APPROVED` the design becomes `IN_PRODUCTION`, with `non_refundable_deposit_cents` held at the full deposit and `refundable_deposit_cents` at 0, and the customer's account must be `OPEN` or the release is refused with `ERR_ACCOUNT_NOT_OPEN` (HTTP 422). A recall is also the manager's, and it carries the `variance_pct` by which the shop's revised quote moved; when that variance exceeds ten percent of the estimate the design reverts out of production, and if the customer declines the variance it settles all the way back to `DEPOSIT_PAID`. The cycle `CAD_APPROVED` to `IN_PRODUCTION` to `CAD_APPROVED` to `DEPOSIT_PAID` is permitted, and the recall clears `non_refundable_deposit_cents` while restoring `refundable_deposit_cents` to the full deposit. The order's `version` increments.

Completion is the manager's last step and it needs credit behind it. From `IN_PRODUCTION`, the commission completes only when the customer holds an approved credit application whose `approved_limit_cents` reaches the estimate plus the accumulated `revision_fee_cents`; a shortfall is refused with `ERR_CREDIT_LIMIT_EXCEEDED` (HTTP 422). On success the design becomes `COMPLETED`, the deposit is held whole and nothing is refundable, and a purchase ticket is opened for the customer at the estimate plus the revision fees, starting in `PENDING` with a `trade_up_credit_cents` of 0. The order's `version` increments.

Cancellation is available to the customer on their own commission and to a `StoreManager`, and its financial consequence depends on how far the build had gone. From `DEPOSIT_PAID`, `CAD_REVISION`, or `CAD_APPROVED` — that is, whenever the design has not reached `IN_PRODUCTION` or `COMPLETED` — the commission cancels with a `cancellation_fee_cents` of 0, `non_refundable_deposit_cents` of 0, and the whole deposit returned as `refundable_deposit_cents`; the cancellation out of `DEPOSIT_PAID` additionally appends a ledger entry of kind `TRADE_UP_CREDIT` and direction `DECREASE` against the plan financing that order, when such a plan exists, in the amount of the refundable deposit. From `IN_PRODUCTION` the commission still cancels, but the deposit is held: `non_refundable_deposit_cents` becomes the full `deposit_cents`, `refundable_deposit_cents` becomes 0, and `cancellation_fee_cents` becomes the result of `non_refundable_deposit_forfeit`. `CANCELLED` and `COMPLETED` are both terminal.

The forfeit arithmetic is where the customer's exposure is settled. Costs incurred, `costs_incurred_cents`, are the deposit plus the accumulated `revision_fee_cents` minus whatever `material_recovery_cents` the chain recovers from the abandoned build. The cancellation fee is the greater of two candidates: when the order's `revision_count` has reached 3 or more, the fee is those costs incurred; otherwise it is the whole deposit. When the fee exceeds the deposit the difference is billed to the customer as `customer_balance_due_cents` — the cost-bearing case — and otherwise the difference is returned as `customer_refund_cents`, the deposit-bounded case.

### 3.7. Default, Suspension and the Customer's Credit Posture

A deferred-interest plan that nobody pays off or capitalizes declares itself by defaulting, and one analyst sweep handles the whole consequence chain. The default sweep acts on any plan whose status is `ACCRUING` or `CAPITALIZED` when the current instant is strictly more than 90 days past that plan's `simplicity_expires_at` and `total_paid_cents` is still below `principal_cents`. Six hops follow, in this order, and the order is normative.

The first hop sets `plan_status` to `DEFAULTED`. The second suspends the cardholder: `account_status` becomes `SUSPENDED`, `credit_tier` is forced to `NO_FILE`, `standalone_credit_limit_cents` is zeroed, and `revolving_utilization_bps` is pinned at 10000. The third declines every credit application the customer still holds in `PENDING` or `COUNTERED`. The fourth lapses every lifetime registration the customer holds in `PENDING_INSPECTION`, incrementing each one's `missed_inspection_count`. The fifth recomputes the customer's `lost_inspection_streak`, which counts the registrations that have entered `LAPSED`. The sixth re-runs `credit_tier_from_plan_mix_and_inspection_streak`, and this is the point that pins the evaluation order: the streak mutation from hops four and five happens before the tier is recomputed, so the downgrade reflects the new misses rather than the posture from before the default. The sweep reports `defaulted_count`, `defaulted_plan_ids`, and `suspended_customer_ids`.

While any plan of a customer sits in `DEFAULTED`, credit is frozen across the chain for that customer. Completing a purchase, opening a promotional plan, opening a custom commission, and releasing a commission to production are all refused with `ERR_CREDIT_FROZEN` (HTTP 422), and this hazard check is deliberately placed above every data-validity and fiscal check that would otherwise fire on the same request, so a frozen account surfaces as frozen rather than as a limit problem. The account posture requirement is the next layer down: any obligation carried by an account that is not `OPEN` is refused with `ERR_ACCOUNT_NOT_OPEN` (HTTP 422), which is the check a suspended customer meets first once their plans have been reinstated.

Lifting the suspension is a `CreditAnalyst` action against the customer file. It requires `account_status` of `SUSPENDED` and that no plan of the customer remains in `DEFAULTED`. On success `account_status` returns to `OPEN`, `standalone_credit_limit_cents` is restored from the registry row named by the customer's most recent approved application, and the tier is recomputed by the plan-mix-and-streak rule — using the pre-event streak, since this recomputation runs in the plan-status family rather than the lapse family. The plan-level reinstatement described in §3.2 restores the same limit and reopens the account from the plan's side, and the two paths must agree on the restored ceiling.

A customer file can be closed, by a `CustomerService` operator, only when nothing is left outstanding. Closing requires an `outstanding_balance_cents` of exactly 0, no repair of that customer in `INTAKE`, `ROUTED`, `IN_REPAIR`, `QC_REVIEW`, or `COMPLETED`, and no registration of that customer in `PENDING_INSPECTION`, `REMINDER_ISSUED`, `GRACE_PERIOD`, or `RENEWED`. Anything else is refused with `ERR_CUSTOMER_ACTIVE_OBLIGATIONS` (HTTP 409). The resulting `CLOSED` status is terminal, and closing cascades: every registration of that customer in `ACTIVE` becomes `TERMINATED`, every one of their applications still in `PENDING` becomes `DECLINED`, and the open inspection count is recomputed for each store affected. Note that the tiers a customer can be in are exactly `NO_FILE`, `TIER_1`, `TIER_2`, and `TIER_3`, and that a customer whose plan mix and inspection history drive them to `TIER_3` is not thereby refused credit — the tier is a pricing input and a limit input, not a gate.

### 3.8. Statements, Credit Buckets and the Monthly Close

A billing statement is generated by a `CreditAnalyst` or a `CustomerService` operator with the cardholder's `customer_id`, a `statement_period` label unique per customer, the statement's `lines`, and an optional `payment_cents` to allocate. Each line carries its own `amount_cents`, its `billable_pct`, and a `line_status`; only lines whose status is `BILLABLE` are counted, and lines already `PAID` or `DISPUTED` are dropped before any arithmetic runs.

When a payment is supplied it is applied by `payment_allocation_waterfall` across the three credit buckets in their fixed priority order — `PROMOTIONAL`, then `STANDARD_RETAIL`, then `NEW_ACCOUNT` — each bucket capped by the corresponding customer balance, with any residual cascading to the next bucket until the payment is exhausted. The allocation is reported in `bucket_totals_cents`. A payment may be directed at any of the three allocation buckets — `PROMOTIONAL`, `CUSTOM_DESIGN`, or `RETAIL` — and payments directed at a bucket other than `PROMOTIONAL` never move a plan's promotional payoff figure (§3.2). A payment larger than the sum of the three balances has nowhere to go and the whole statement is refused with `ERR_STATEMENT_OVERPAYMENT` (HTTP 422) rather than silently truncating. The statement's `min_payment_due_cents` is then computed from the allocated buckets, subject to the 5,000 cent floor described in §2.11, so a small statement still bills the floor.

The statement balance itself comes from `statement_balance_rollup` over the billable lines. The storage form is an object keyed by the three buckets and the numeric fields are integers in cents; the statement's `statement_balance_cents` is the rollup result, and `statement_status` starts at `OPEN`. Closing a statement is the `CustomerService` desk's action: it requires the statement to be `OPEN` and its `statement_balance_cents` to be at least 0, and it produces the terminal `CLOSED` status with the statement's `version` incremented by one.
