# Sponsored Internship Placement API — Product Requirements Document

## 1. Introduction

The Sponsored Internship Placement API is the system of record for a workforce-development program that recruits young adults from low-income households, trains them, and places them into paid internships hosted by corporate employer partners. It covers the whole arc of a participant's journey: application intake, an eligibility decision against age, education and household-income criteria, enrollment into a learning-and-development cohort, progression through technical training measured by attendance-driven contract points, matching to a sponsoring employer, an interview cycle, an offer and acceptance, a stipend-paying internship, and finally graduation with follow-up outcome tracking. Every one of those stages is a first-class resource with its own lifecycle, and the API is expected to keep the stages consistent with one another rather than treating them as independent records.

The commercial half of the system is just as load-bearing as the programmatic half. Employer partners sign placement agreements that commit supervisor hours, a number of intern slots and a fee tier; each accepted intern generates a placement fee derived from the agreement's frozen tier, the committed supervision hours and the length of the placement window. That fee becomes an invoice, the invoice becomes a receivable, and the receivable's ageing directly governs what the partner is allowed to do next — an overdue invoice places the partner's account on credit hold, and a sufficiently aged one suspends it outright. Stipends run in parallel: participants are paid per period, with deductions driven by attendance shortfalls and recorded behavior incidents, and the points earned from those periods gate advancement from training into the internship phase.

Because the program's rules are time-sensitive — eligibility is judged at decision time, invoices age against a clock, interview slots are booked against agreement windows, and stipend periods must not overlap — the API does not read the wall clock. It maintains a logical clock that the operator sets explicitly, and every deadline, window and interval in this document is evaluated against that clock. Requests are validated in a fixed priority order so that a request that violates several rules at once always fails on the same one, and writes against a partner's billing state are guarded by an optimistic-concurrency check so that a client acting on a stale view of that partner is rejected rather than allowed to overwrite it. The API is served at the server root; there is no path prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Identity and Access Control

Every request must carry the acting user's identity in two headers: `X-User-ID` and `X-User-Role`. The system recognizes exactly four roles: `Anonymous`, `ProgramStaff`, `Partner` and `Student`. A request whose `X-User-Role` header is absent or names a role outside that set, or whose `X-User-ID` header is absent, is rejected with `ERR_UNAUTHORIZED` at HTTP 401. The single exception is student registration, which is the one operation an `Anonymous` caller may perform without credentials; every other endpoint in this document requires both headers.

The role names map to identities as follows. When `X-User-Role` is `Anonymous`, `X-User-ID` is an opaque identifier not tied to any persisted entity, and the caller may only submit a program application. When `X-User-Role` is `ProgramStaff`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it, but never compares it to any entity's `id`. When `X-User-Role` is `Partner`, `X-User-ID` is the `id` of the acting `Partner`; ownership checks on any resource that references a partner — an `Agreement`, an `InternshipPlacement` under one of that partner's agreements, a `SatisfactionRecord` for such a placement, or an `Invoice` — compare the resource's `partner_id` to `X-User-ID`. When `X-User-Role` is `Student`, `X-User-ID` is the `id` of the acting `Student`; ownership checks on any resource that references a student — an enrollment, an offer acceptance, a stipend statement, an outcome checkpoint or a credit grant — compare the resource's `student_id` to `X-User-ID`.

Role permissions are enumerated per endpoint in §4, which is the authoritative matrix. A caller whose role is valid but who is not among the roles authorized for an operation is rejected with `ERR_UNAUTHORIZED` at HTTP 401. A caller whose role is authorized for the operation but whose `X-User-ID` does not match the owning foreign key on the specific row being acted upon is rejected with `ERR_NOT_OWNER` at HTTP 403 — this is the row-level check that separates, for example, one partner's interview outcome from another's.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

List endpoints accept a `limit` query parameter giving the maximum number of items to return — it defaults to 10, and must be between 1 and 100 inclusive — and an `offset` query parameter giving the number of leading items to skip, which defaults to 0. The `meta` object of any list response carries `limit`, `offset`, `total_count` and `has_more`.

Unless a specific endpoint says otherwise, list endpoints return resources sorted by `created_at` in ascending order. Three list endpoints deviate deliberately: interview rounds are returned in `round_number` order, satisfaction records are returned newest first, and a student's outcome checkpoints are returned in ascending `interval_months` order.

### 2.4. Common Resource Properties

Every top-level resource in this API — `Partner`, `Student`, `Cohort`, `Agreement`, `InternshipPlacement`, `InterviewRound`, `StipendStatement`, `SatisfactionRecord`, `OutcomeCheckpoint`, `Invoice` and `CreditGrant` — carries the same four system-managed properties. The `id` is a server-minted UUID with no type prefix, so an `id` alone never reveals which resource kind it belongs to. The `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the row was created. The `updated_at` is an ISO 8601 UTC timestamp with three fractional digits refreshed on every mutation of the row. The `version` is an integer that starts at its initial value and increments by one on every mutation.

All eleven resources are fully mutable and therefore all eleven expose both `updated_at` and `version`; none of them omits either field. Recomputation of a derived field — a partner's billing totals, a cohort's `awarded_points`, a placement's `satisfaction_score`, a student's `lifetime_contract_points` — counts as a mutation of the owning row and refreshes its `updated_at` and increments its `version` exactly like a client-supplied field change does. A single client request that cascades into several rows therefore advances the `version` of each row it touches, not just the row named in the path.

### 2.5. Request Evaluation Order

A request frequently violates more than one rule at once. To keep rejection deterministic, the server evaluates the following checks in this fixed order and reports only the first failure; a later check never masks an earlier one.

1. **Authentication — role.** `X-User-Role` must be present and name one of the four declared roles. Otherwise `ERR_UNAUTHORIZED` (401). Applies to every endpoint except anonymous student registration.
2. **Authentication — identity.** `X-User-ID` must be present, and for the entity-backed roles it must resolve to an existing instance of the backing entity. Otherwise `ERR_UNAUTHORIZED` (401). Applies to every endpoint except anonymous student registration.
3. **Path resource existence.** Every path resource must exist, validated left to right along the path, so the first missing identifier in the chain is the one reported. Otherwise `ERR_NOT_FOUND` (404). Applies to every endpoint carrying a path identifier.
4. **Body foreign-key resolution.** Every foreign key supplied in the request body — `cohort_id`, `partner_id`, `agreement_id`, `student_id`, `placement_id` — must resolve to an existing row. Otherwise `ERR_NOT_FOUND` (404). Applies to cohort enrollment, agreement drafting, placement matching, stipend statement creation, satisfaction record submission, invoice issuance, credit grant registration and checkpoint recording.
5. **Request well-formedness.** Required fields must be present; enum fields must carry a declared member; `hours_expected` must be greater than zero; `credit_hours` must be greater than zero; `period_end` must be at least 7 days after `period_start`; an agreement's `end_date` must be at least 28 days after its `start_date`; the three satisfaction ratings must lie within 0.00 to 5.00; and a checkpoint recorded as `EMPLOYED` must carry a positive `hourly_wage_cents`. Otherwise `ERR_INVALID_REQUEST` (422). Applies to every endpoint with a request body.
6. **Transition admissibility.** The target row must be in a non-terminal state that admits the requested transition; this check reports a row whose current state simply has no transition for the requested action. Otherwise `ERR_INVALID_STATE` (409). Applies to every action endpoint.
7. **Terminal guard.** The target row must not already sit in a terminal state, in which case the request is reported here rather than as an inadmissible transition. The terminal states are `INELIGIBLE` for a student, `PAID` and `VOID` for a stipend statement, `PAID` and `VOID` for an invoice, `GRANTED` and `VOID` for a credit grant, and `TERMINATED` for an internship placement. Otherwise `ERR_ALREADY_TERMINAL` (409). Applies to every action endpoint.
8. **Row ownership.** An entity-backed actor's `X-User-ID` must equal the owning foreign key on the target row — a `Student` acting on their own enrollment, offer acceptance or checkpoint recording, and a `Partner` acting on the interview outcomes and satisfaction records of its own agreements' placements. Otherwise `ERR_NOT_OWNER` (403). Applies to offer acceptance, cohort enrollment, checkpoint recording, interview outcome recording and satisfaction record submission.
9. **Parent aggregate state.** The parent aggregate must be in the state the transition requires — an `ACTIVE` agreement for interview scheduling and offers, an `ACTIVE` or `FULFILLED` agreement for offer acceptance, a `PLANNED` or `ACTIVE` cohort for enrollment, and a placement at `ACCEPTED` or `ACTIVE` for an internship-phase stipend statement. Otherwise `ERR_PARENT_STATE_CONFLICT` (409). Applies to interview scheduling, offers, offer acceptance, cohort enrollment and stipend statement creation.
10. **Age gate.** The student must be at least 18 and at most 24 years old at the logical-clock date, the full band being set out in §2.11. Otherwise `ERR_AGE_INELIGIBLE` (422). Applies to eligibility decisions and cohort enrollment.
11. **Education gate.** The student's `education_status` must be one of `NO_DIPLOMA`, `HS_DIPLOMA`, `SOME_COLLEGE` or `ASSOCIATE`. Otherwise `ERR_EDUCATION_INELIGIBLE` (422). Applies to eligibility decisions and cohort enrollment.
12. **Income gate.** The student's `household_income_cents` must be at or below the income ceiling. Otherwise `ERR_INCOME_INELIGIBLE` (422). Applies to eligibility decisions and cohort enrollment.
13. **Match eligibility.** The placement's student must be eligible for matching — enrolled with `current_phase` at `INTERNSHIP`, or at `current_phase` `COMPLETED`. Otherwise `ERR_NOT_ELIGIBLE_FOR_MATCH` (409). Applies to placement matching.
14. **Fee tier agreement.** The agreement's negotiated `fee_tier` must match the partner's current `fee_tier`. Otherwise `ERR_FEE_TIER_MISMATCH` (409). Applies to agreement activation.
15. **Credit hold.** The partner's `credit_hold` must be false. Otherwise `ERR_PARTNER_CREDIT_HOLD` (402). Applies to agreement activation.
16. **Partner standing.** The partner's `status` must be `ACTIVE`. Otherwise `ERR_PARTNER_SUSPENDED` (402). Applies to agreement activation, placement matching and offer extension.
17. **Partner past due.** The partner must hold no invoice at status `OVERDUE` whose `due_date` is strictly before the logical-clock date minus 14 days. Otherwise `ERR_PARTNER_PAST_DUE` (402). Applies to offer extension.
18. **Partner credit limit.** The partner's `outstanding_balance_cents` plus the new invoice's total must not exceed the partner credit ceiling. Otherwise `ERR_PARTNER_CREDIT_LIMIT` (402). Applies to invoice issuance.
19. **Placement window.** The accepted placement window must lie inside the sponsoring agreement's window and `hours_per_week` must be at least 20. Otherwise `ERR_PLACEMENT_WINDOW_INVALID` (409). Applies to offer acceptance.
20. **Payment amount.** `amount_paid_cents` must equal the invoice's `total_amount_cents`. Otherwise `ERR_PAYMENT_AMOUNT_MISMATCH` (422). Applies to invoice payment.
21. **Capacity.** The resource's capacity must not be exhausted — `enrolled_count` below `capacity` for enrollment, and a placement count below `slot_count` for matching. Otherwise `ERR_CAPACITY_EXCEEDED` (409). Applies to cohort enrollment and placement matching.
22. **Single active placement.** The student must hold no other placement at state `ACCEPTED` or `ACTIVE`. Otherwise `ERR_STUDENT_ALREADY_PLACED` (409). Applies to offer acceptance and placement matching.
23. **Interview slot conflict.** The proposed interview slot must not overlap an existing interview round booked with the same `supervisor_name`. Otherwise `ERR_INTERVIEW_SLOT_CONFLICT` (409). Applies to interview scheduling.
24. **Stipend period overlap.** The stipend period must not overlap an existing statement of the same student and phase whose `status` is `PENDING` or `PAID`. Otherwise `ERR_STIPEND_PERIOD_OVERLAP` (409). Applies to stipend statement creation.
25. **Interview rounds exhausted.** The placement must not have already used all of its allowed interview rounds. Otherwise `ERR_INTERVIEW_ROUNDS_EXHAUSTED` (409). Applies to interview scheduling.
26. **Duplicate email.** No other student may already carry the same `email`. Otherwise `ERR_DUPLICATE_EMAIL` (409). Applies to student registration.
27. **Stale partner version.** The request's `expected_partner_version` must equal the partner's current `version`. Otherwise `ERR_STALE_VERSION` (412). Applies to invoice issuance and agreement activation.

### 2.6. The Logical Clock

The server never reads the wall clock. It starts with a logical clock fixed at `2026-09-01T00:00:00Z` and stays there until an operator moves it. A `ProgramStaff` operator may advance or set it to any instant by supplying a `to_iso8601` value to the clock-setting capability; from that moment every later deadline, window and interval check in this document is evaluated against the new logical time. Setting the clock backwards is not a supported workflow and no rule in this document depends on it.

The clock matters most for ageing. An invoice turns `OVERDUE` once the logical-clock date passes its `due_date`, and that evaluation runs both when the clock advances and again whenever the invoice itself or its partner is read, so a read can never observe an invoice as `ISSUED` after its due date has already passed on the logical clock. The clock also stamps `submitted_at` on satisfaction records, `recorded_at` on outcome checkpoints and `paid_on` on invoice payments, and it fixes the reference date for the age gate, the cohort graduation-date deadline, the credit-grant 365-day limit and the 14- and 30-day partner-delinquency thresholds.

### 2.7. Monetary Values, Ratios and Rounding

All monetary amounts in this API are integers in cents — `household_income_cents`, `placement_fee_cents`, `gross_amount_cents`, `attendance_deduction_cents`, `behavior_deduction_cents`, `net_amount_cents`, `total_stipend_paid_cents`, `total_amount_cents`, `amount_paid_cents`, `outstanding_balance_cents`, `billed_cents`, `collected_cents`, `hourly_wage_cents` and `tuition_credit_cents` alike. No monetary field is ever returned as a decimal number or a string.

Every rounding step anywhere in this API uses round-half-up. Rate and ratio fields are the exception to the integer rule and are held at fixed scale: `attendance_ratio`, `on_time_payment_ratio` and `collection_ratio` are stored and returned to exactly 4 decimal places, while `placement_quality_score`, `composite_score` and a placement's `satisfaction_score` are stored and returned to exactly 2 decimal places on a 0.00-to-5.00 scale. Where a formula in §3 performs several rounding steps, each step is rounded independently at the precision stated for that step, in the order given.

### 2.8. Optimistic Concurrency Control on Partner Writes

Two write operations are guarded by an optimistic-concurrency check, and both of them are guarded against the `Partner` row: issuing an invoice and activating an agreement. Each of those two requests must carry `expected_partner_version`, the `version` of the target partner that the client last observed. If the partner's `version` has advanced past the value carried in the request, the server rejects the write with `ERR_STALE_VERSION` at HTTP 412, because the fee tier, credit hold, outstanding balance and standing that the client based its request on may no longer be the ones the server holds. No other endpoint in this API accepts a version field, and no other resource is protected this way — an endpoint not named above must ignore or reject any version-carrying input rather than honoring it.

### 2.9. Nested Resource Retrieval and Referential Integrity

Several endpoints address a resource through the resource that owns it, and the server validates such a chain strictly from left to right: for a request that names a parent and then a child, the parent is resolved first and the request fails at the first identifier in the chain that does not resolve, with `ERR_NOT_FOUND` at HTTP 404. This applies to the agreement lists nested under a partner, the student and interview lists nested under a cohort and a placement, the stipend statement, checkpoint and credit grant lists nested under a student, and the satisfaction record list nested under a placement. The same rule governs body-supplied references: a `cohort_id`, `partner_id`, `agreement_id`, `student_id` or `placement_id` that names no row is a `ERR_NOT_FOUND` (404) and is checked before any business rule about the referenced row's state is evaluated.

### 2.10. Partner Ledger Reconciliation

A partner row carries a running picture of its receivables that is recomputed from its invoices whenever one of them changes status or is read. The `outstanding_balance_cents` is the sum of `total_amount_cents` over the partner's invoices at status `ISSUED` or `OVERDUE`; `billed_cents` adds to that sum the `total_amount_cents` of its `PAID` invoices; `collected_cents` is the sum of `amount_paid_cents` over its `PAID` invoices; and `collection_ratio` is `collected_cents` divided by `billed_cents` to 4 decimal places, round half up, or 0.0000 when `billed_cents` is 0. The `oldest_open_due_date` is the earliest `due_date` among the `ISSUED` and `OVERDUE` invoices, and is null when the partner has none open. A `VOID` invoice enters none of these aggregates. The `on_time_payment_ratio` is the sum of paid invoice amounts divided by the sum of issued invoice amounts for the partner, held between 0.0000 and 1.0000.

Two derived flags follow from the same data. The `credit_hold` flag is true exactly when the partner carries an invoice at status `OVERDUE` whose `due_date` is strictly before the logical-clock date; it is cleared as soon as that condition stops holding, which happens when the invoice is paid or voided. The partner's `status` is driven to `SUSPENDED` when the partner carries an invoice at status `OVERDUE` whose `due_date` is strictly more than 30 days before the logical-clock date, and returns to `ACTIVE` once no such invoice remains. The partner's `placement_quality_score` is the most recent submitted satisfaction composite for that partner, on the same 0.00-to-5.00 scale, and starts at 0.00 before any record is submitted. A `SUSPENDED` partner may not activate new agreements, be matched to new placements or receive new offers; `INACTIVE` is a terminal partner standing that no automatic rule in this document produces, and an `ACTIVE` partner is the only one that admits new agreement activation.

### 2.11. Program Eligibility Gates

Three gates decide whether an applicant qualifies for the program, and they are evaluated both when a selection decision is recorded and again when the student attempts to enroll. The age gate requires the applicant to be at least 18 and at most 24 years old at the logical-clock date. The education gate requires the applicant's `education_status` to be one of `NO_DIPLOMA`, `HS_DIPLOMA`, `SOME_COLLEGE` or `ASSOCIATE` — a `BACHELOR_OR_HIGHER` applicant is refused. The income gate requires `household_income_cents` to be at or below 4,500,000 cents, that is, an annual household income of at most $45,000. A failing gate reports its own error — `ERR_AGE_INELIGIBLE`, `ERR_EDUCATION_INELIGIBLE` or `ERR_INCOME_INELIGIBLE`, each at HTTP 422 — and, on a selection decision, leaves the applicant exactly where they were so the decision can be retried once the record is corrected.
## 3. Business Logic & Workflows

### 3.1. Applicant Intake and the Selection Decision

An applicant enters the program through an anonymous registration that carries `full_name`, `email`, `date_of_birth`, `education_status` and `household_income_cents`. Registration is the only operation that requires no credentials, and it is refused with `ERR_DUPLICATE_EMAIL` (409) when another student already holds the same `email`. A newly registered applicant starts with `application_state` at `APPLIED`, `current_phase` null because no phase has begun, `roster_status` `ON_TRACK`, `total_stipend_paid_cents` 0, `lifetime_contract_points` 0 and `conversion_streak` 0. Nothing else in the system may reference the student yet — no cohort assignment, no placement, no stipend statement.

A `ProgramStaff` operator records the selection outcome by supplying a `decision` and an optional `reason`. This decision is the only way a student leaves `APPLIED`. A `decision` of `ELIGIBLE` requires all three eligibility gates from §2.11 to hold at once: the applicant must be at least 18 and at most 24 years old on the logical-clock date, must hold one of the four qualifying education statuses, and must report a household income at or below the ceiling. When they hold, the student moves `APPLIED → ELIGIBLE` and waits for a cohort assignment. When any of them fails, the request is rejected with that gate's own error — `ERR_AGE_INELIGIBLE`, `ERR_EDUCATION_INELIGIBLE` or `ERR_INCOME_INELIGIBLE`, each at 422 — and the student stays at `APPLIED`, so the record can be corrected and decided again. A `decision` of `INELIGIBLE` requires no gate at all: it moves the student `APPLIED → INELIGIBLE`, which is the student machine's only terminal state, and from that point no enrollment, cohort assignment or stipend statement may ever be created for that student. Any later attempt to act on that student is refused with `ERR_ALREADY_TERMINAL` (409).

### 3.2. Cohort Enrollment and the Learning & Development Phase

Cohorts are created before students are placed into them. A cohort is defined by a `program_code` naming the career track it trains for — `SOFTWARE`, `DATA`, `CYBER` or `IT_SUPPORT` — a `location_code` naming the training site, a `start_date`, and an optional `capacity` that defaults to 24 and caps the number of enrolled students. The system writes the cohort's `graduation_date` at creation as the `start_date` plus 180 days, and that derived date is never recomputed afterwards. A new cohort starts at `status` `PLANNED` with `enrolled_count` 0 and `awarded_points` 0.

Enrollment is requested with a `cohort_id` and the student's `track_code`, which is the career track supplied with the enrollment request and must equal the target cohort's `program_code`. Enrollment is permitted only while the cohort is at `PLANNED` or `ACTIVE`; a cohort that has reached `COMPLETED` refuses it with `ERR_PARENT_STATE_CONFLICT` (409). It is also permitted only while the logical-clock date is on or before the cohort's `graduation_date`; once that date has passed on the logical clock, enrollment is likewise refused with `ERR_PARENT_STATE_CONFLICT` (409). The cohort must have a free seat — when `enrolled_count` has already reached `capacity`, the request is rejected with `ERR_CAPACITY_EXCEEDED` (409). The three eligibility gates from §2.11 are re-evaluated here too, so a student who has aged past 24 or whose recorded income has moved since the decision cannot slip into a cohort. When everything passes, the student moves `ELIGIBLE → ENROLLED`, `current_phase` becomes `L_AND_D`, the cohort's `enrolled_count` increments by 1, and a cohort that was `PLANNED` becomes `ACTIVE`.

The learning-and-development phase is measured in contract points. A student's `lifetime_contract_points` is a running total of the `contract_points_earned` awarded across that student's L&D cohorts, incremented each time an L&D stipend statement is paid (§3.5). Reaching 12 points while the student has at least one statement at status `PAID` for phase `L_AND_D` and a `roster_status` other than `DISMISSED` advances `current_phase` from `L_AND_D` to `INTERNSHIP`; this is a system-driven move on the student's own row and needs no separate request. The student's `roster_status` tracks standing within the cohort and takes one of `ON_TRACK`, `PROBATION` or `DISMISSED`, with the moves into `PROBATION` and `DISMISSED` driven by stipend payment (§3.5). A cohort's own `status` becomes `COMPLETED` once every enrolled student of that cohort has a `current_phase` of `INTERNSHIP` or `COMPLETED`.

Cohorts also carry a cohort-level point award, `awarded_points`, recomputed whenever one of the cohort's students pays a stipend statement. The recomputation sums `contract_points_earned` over the stipend statements at status `PAID` whose `phase` is `L_AND_D` and whose student is enrolled in this cohort, producing a raw `total_points`. The cohort's level is read from that raw total: level 3 when `total_points` is at least 20, otherwise level 2 when `total_points` is at least 10, otherwise level 1. The base award is `total_points` divided by 3, rounded half up to a whole number of points. The final `awarded_points` is that base award plus the level multiplied by 100 bonus points. The level must always be read from the raw `total_points` and never from the base award or from the already-bonused `awarded_points`, which would make the value self-referential.

### 3.3. Corporate Partner Onboarding and Agreement Activation

An employer partner is registered with a `legal_name`, an `industry` drawn from `TECH`, `FINANCE`, `HEALTHCARE`, `RETAIL` or `LOGISTICS`, and a `billing_email` used for invoice delivery, plus an optional `fee_tier` that defaults to `TIER_C`. A new partner starts at `status` `ACTIVE` with `placement_quality_score` 0.00, `on_time_payment_ratio` 0.0000, `credit_hold` false, every billing total — `outstanding_balance_cents`, `billed_cents` and `collected_cents` — at 0, `collection_ratio` 0.0000 and `oldest_open_due_date` null.

A placement agreement is drafted with a `partner_id` naming the sponsoring employer, a written `project_scope`, a commitment of `supervision_hours_per_week`, a `slot_count` of interns the partner will host, a negotiated `fee_tier`, and a `start_date` and `end_date` bounding the placement window. The window must be at least 28 days long — an `end_date` less than 28 days after the `start_date` is a `ERR_INVALID_REQUEST` (422) — and the agreement starts at `status` `DRAFT`.

Activation is the point at which an agreement becomes usable, and it is one of the two operations guarded by the partner optimistic-concurrency check described in §2.8: the request must carry `expected_partner_version`, and a partner whose `version` has advanced past that value is rejected with `ERR_STALE_VERSION` (412). Beyond that guard, activation enforces five conditions. The supervision commitment must be real: `supervision_hours_per_week` must be at least 10. The agreement must commit at least one slot: `slot_count` must be at least 1. The window must be at least 28 days, checked again at activation even though it was checked at drafting. The partner must be in good standing — a `status` of `SUSPENDED` or `INACTIVE` is rejected with `ERR_PARTNER_SUSPENDED` (402), and a partner whose `credit_hold` is true is rejected with `ERR_PARTNER_CREDIT_HOLD` (402). And the agreement's negotiated `fee_tier` must match the partner's current `fee_tier`, because billing always reads the agreement-level tier and never the partner's; a mismatch is rejected with `ERR_FEE_TIER_MISMATCH` (409). When all five hold, the agreement moves `DRAFT → ACTIVE`, its `fee_tier` is frozen at that instant from `Partner.fee_tier` and is never re-read from the partner afterwards, and the partner's `version` increments by 1 so that any client holding the pre-activation view is now stale.

An active agreement has a second lifecycle driven by its placements. When the count of its placements at `ACCEPTED`, `ACTIVE` or `COMPLETED` reaches `slot_count`, the agreement moves `ACTIVE → FULFILLED` and no new placement may be matched to it. Should that count later drop below `slot_count` because a placement was terminated, the agreement returns `FULFILLED → ACTIVE` and accepts new matches again.

### 3.4. Matching, Interviews and the Offer Cycle

Matching pairs one student with one sponsoring agreement and consumes a slot. The request supplies an `agreement_id`, a `student_id` and an optional `max_interview_rounds` that defaults to 3 and caps how many interview rounds the placement may run. Before the placement is created the server checks that the student is eligible for matching — `application_state` at `ENROLLED` with `current_phase` at `INTERNSHIP`, or `current_phase` at `COMPLETED`; anything else is `ERR_NOT_ELIGIBLE_FOR_MATCH` (409). It checks that the partner behind the agreement is `ACTIVE`, rejecting a suspended one with `ERR_PARTNER_SUSPENDED` (402). It checks that the agreement still has a free slot: when the count of its placements at `ACCEPTED`, `ACTIVE` or `COMPLETED` has already reached `slot_count`, the request is rejected with `ERR_CAPACITY_EXCEEDED` (409). And it checks that the student holds no other placement at `ACCEPTED` or `ACTIVE`, rejecting with `ERR_STUDENT_ALREADY_PLACED` (409). A successful match creates a placement at `state` `MATCHED` with `interview_attempt` 0, its `project_scope` copied from the sponsoring agreement, and its `supervisor_name` copied from the sponsoring agreement's partner's `legal_name`; the placement's `placement_fee_cents`, `outcome` and `satisfaction_score` stay unset at this point.

Interview scheduling is requested against the placement with a `scheduled_for` instant, an optional `duration_minutes` that defaults to 45 and must be at least 30 minutes, and a `supervisor_name` naming the interviewing supervisor. The placement must currently be `MATCHED`, or be `INTERVIEWED` with its latest round's `outcome` at `FAILED` and rounds remaining; any other state is `ERR_INVALID_STATE` (409). The sponsoring agreement must be `ACTIVE`, and `scheduled_for` must fall inside that agreement's window, from its `start_date` through its `end_date` inclusive. Two further checks apply. A placement that has already used all of its allowed interview rounds cannot be booked again: once `interview_attempt` has reached `max_interview_rounds` the ordinary case is a placement that failed its final allowed round and has returned to `MATCHED`, and there the refusal is `ERR_INTERVIEW_ROUNDS_EXHAUSTED` (409). A placement still sitting at `INTERVIEWED` is stopped one step earlier by the state check and reported as `ERR_INVALID_STATE` (409), because the `INTERVIEWED → INTERVIEW_SCHEDULED` transition itself requires rounds to remain. Finally, the proposed slot must not overlap an existing interview round booked with the same `supervisor_name`, which is `ERR_INTERVIEW_SLOT_CONFLICT` (409); two rounds conflict when the intervals running from each round's `scheduled_for` for its `duration_minutes` share any instant, regardless of which placement they belong to. A successful scheduling creates an interview round whose `outcome` starts at `PENDING`, whose `round_number` is the placement's current `interview_attempt` plus 1, and whose `feedback` is empty; the placement moves `MATCHED → INTERVIEW_SCHEDULED`, or `INTERVIEWED → INTERVIEW_SCHEDULED` on a retry after a failed round.

The interviewing partner records the round's result by supplying an `outcome` of `PASSED` or `FAILED` and an optional `feedback`. The round must still be at `PENDING`, and the placement must not be beyond its allowed rounds. Recording the outcome sets the round's `outcome` to the recorded value and increments the placement's `interview_attempt` by 1. A `PASSED` round moves the placement `INTERVIEW_SCHEDULED → INTERVIEWED`. A `FAILED` round moves it `INTERVIEW_SCHEDULED → INTERVIEWED` while rounds remain, but when that failure falls on the final allowed round — that is, when the incremented `interview_attempt` has reached `max_interview_rounds` — the placement instead moves `INTERVIEW_SCHEDULED → MATCHED` and returns to the matching pool, retaining its `student_id` and `agreement_id` so it can be re-interviewed or terminated. The partner recording an outcome must own the placement's agreement, or the request is rejected with `ERR_NOT_OWNER` (403).

An offer is extended once the placement's latest interview round has `outcome` `PASSED` and the sponsoring agreement is still `ACTIVE`. Two fiscal checks gate the offer: the partner must not be `SUSPENDED` (`ERR_PARTNER_SUSPENDED`, 402), and the partner must not carry an invoice at status `OVERDUE` whose `due_date` is strictly more than 14 days before the logical-clock date (`ERR_PARTNER_PAST_DUE`, 402). Extending the offer moves the placement `INTERVIEWED → OFFERED` and computes and stores `placement_fee_cents` from the sponsoring agreement's window and frozen tier, using the fee calculation in §3.7.

Acceptance is the student's action, and the acting `X-User-ID` must equal the placement's `student_id` or the request fails with `ERR_NOT_OWNER` (403). The student supplies a concrete `start_date` and `end_date` and an optional `hours_per_week` that defaults to 20. The two dates must span at least 28 days; the sponsoring agreement must be `ACTIVE` or `FULFILLED`; the student must hold no other placement at `ACCEPTED` or `ACTIVE` (`ERR_STUDENT_ALREADY_PLACED`, 409); and the accepted window must lie inside the agreement's window with `hours_per_week` at least 20, a violation of which is `ERR_PLACEMENT_WINDOW_INVALID` (409). On success the placement moves `OFFERED → ACCEPTED` and `placement_fee_cents` is recomputed against the accepted `start_date` and `end_date` rather than the agreement's window, because the actual placement length now governs the fee. The sponsoring agreement moves to `FULFILLED` at the same moment if this acceptance brings its `ACCEPTED`, `ACTIVE` or `COMPLETED` placement count to `slot_count`. Finally, if the logical-clock date is already on or after the accepted `start_date` and the agreement is `ACTIVE` or `FULFILLED`, the placement advances `ACCEPTED → ACTIVE` within the same request, so a back-dated acceptance lands in a running internship immediately.

Termination is available from every non-terminal placement state — `MATCHED`, `INTERVIEW_SCHEDULED`, `INTERVIEWED`, `OFFERED`, `ACCEPTED` and `ACTIVE` each move to `TERMINATED` — and takes an optional `reason`. Termination is how a slot is released: when the sponsoring agreement is `FULFILLED` and the termination drops its `ACCEPTED`, `ACTIVE` or `COMPLETED` count below `slot_count`, the agreement returns to `ACTIVE`. `TERMINATED` is terminal for the placement and no further action may move it; a request against an already-terminated placement is refused with `ERR_ALREADY_TERMINAL` (409).
### 3.5. Stipend Administration

A stipend statement pays one student for one period in one phase. Creation supplies a `student_id`, a `phase` of `L_AND_D` or `INTERNSHIP`, a `period_start` and `period_end`, the `hours_attended` and the `hours_expected` for the period, and an optional `behavior_incidents` count that defaults to 0. Both period dates are inclusive days and the period must span at least 7 days. `hours_expected` must be greater than zero. An internship-phase statement additionally requires the student to be holding a placement at `ACCEPTED` or `ACTIVE`, because an internship stipend cannot be paid for a placement that is not running; otherwise the request is refused with `ERR_PARENT_STATE_CONFLICT` (409). The period must not overlap an existing statement of the same student and phase whose `status` is `PENDING` or `PAID` — two inclusive periods overlap when they share at least one calendar day — and a violation is `ERR_STIPEND_PERIOD_OVERLAP` (409). Every amount on the statement is computed at creation, never later, and the statement starts at `status` `PENDING`.

For an `L_AND_D` statement the system works through the following steps in this exact order. First, the number of weeks is the number of days from `period_start` to `period_end` divided by 7, rounded half up to a whole number, and never less than 1. Second, `gross_amount_cents` is that week count multiplied by 17,500 cents, that is, $175 for each week of the period. Third, `attendance_ratio` is `hours_attended` divided by `hours_expected`, rounded half up to 4 decimal places. Fourth, the absence ratio is 1 minus `attendance_ratio`. Fifth, `attendance_deduction_cents` is `gross_amount_cents` multiplied by the absence ratio and divided by 10, rounded half up to a whole cent — so the deduction is strictly proportional to the absence ratio, and an absence ratio of exactly 0.1000 on a 35,000-cent period deducts 350 cents rather than a flat tenth of the gross. Sixth, `behavior_deduction_cents` is 5,000 cents when `behavior_incidents` is 3 or more, and 0 otherwise. Seventh, `net_amount_cents` is `gross_amount_cents` minus both deductions, floored at zero. Eighth, `contract_points_earned` is 3 points, plus 2 additional points when `attendance_ratio` is at least 0.95.

For an `INTERNSHIP` statement the order is different because the pay is hourly and capped. First, the week count is derived exactly as above. Second, the weekly hours are `hours_expected` divided by the week count, rounded half up to a whole number. Third, the billable hours are the week count multiplied by the smaller of the weekly hours and 25 — the weekly cap — so a 60-hour expectation over a 14-day period bills 50 hours rather than 60. Fourth, `gross_amount_cents` is the billable hours multiplied by 1,650 cents, that is, $16.50 per hour. Fifth, `attendance_ratio` is computed as before, to 4 decimal places round half up. Sixth, the total deduction is the sum of three parts: `gross_amount_cents` multiplied by 1 minus `attendance_ratio`, rounded half up; plus 15,000 cents when `attendance_ratio` is below 0.60; plus 7,500 cents when `behavior_incidents` is 3 or more. Seventh, `net_amount_cents` is `gross_amount_cents` minus that total deduction, floored at zero. Eighth, `contract_points_earned` is 6 points, plus 3 additional points when `attendance_ratio` is at least 0.95. The three deduction parts land in `attendance_deduction_cents` and `behavior_deduction_cents` as appropriate for reporting, but `net_amount_cents` is what the student is actually paid.

Paying a statement is a `ProgramStaff` action that moves it `PENDING → PAID`. Payment credits the student's `total_stipend_paid_cents` with the statement's `net_amount_cents` and adds the statement's `contract_points_earned` to `lifetime_contract_points`. It also re-evaluates the student's standing in the cohort: when the statement's `attendance_ratio` is below 0.50, `roster_status` becomes `DISMISSED`; when `attendance_ratio` is at or above 0.50 and the student's `lifetime_contract_points` is still below 12 after this payment, `roster_status` becomes `PROBATION`. If the payment brings `lifetime_contract_points` to 12 or more while the student's `roster_status` is not `DISMISSED`, the student's `current_phase` advances `L_AND_D → INTERNSHIP` in the same operation. Every payment also recomputes the `awarded_points` of the cohort the student is enrolled in, using the cohort award calculation in §3.2. A statement that has already reached `PAID` cannot be paid again — a second attempt is refused with `ERR_ALREADY_TERMINAL` (409).

A mis-issued statement is corrected by voiding it, a `ProgramStaff` action taking an optional `reason` that moves it `PENDING → VOID`. A voided statement stops contributing to every student total and to the cohort's `awarded_points`; `PAID` and `VOID` are both terminal for a statement, so a paid statement cannot be voided and a voided one cannot be paid, each attempt being refused with `ERR_ALREADY_TERMINAL` (409).

### 3.6. Partner Satisfaction and Placement Completion

The hosting partner rates a placement by submitting a `placement_id` together with a `supervisor_rating`, a `project_rating` and a `communication_rating`, each on the 0.00-to-5.00 scale; a rating outside that band is a `ERR_INVALID_REQUEST` (422), and a partner rating a placement outside its own agreements is refused with `ERR_NOT_OWNER` (403). The `composite_score` is built in a fixed order that rounds each weighted term before summing. The supervisor term is `supervisor_rating` multiplied by 0.50, rounded half up to 2 decimal places. The project term is `project_rating` multiplied by 0.30, rounded half up to 2 decimal places. The communication term is `communication_rating` multiplied by 0.20, rounded half up to 2 decimal places. The weighted total is the sum of those three already-rounded terms, itself rounded half up to 2 decimal places. The composite is then that weighted total multiplied by 5, divided by 4, minus 1, rounded half up to 2 decimal places, and finally clamped into the range 0.00 to 5.00. Rounding each term before summing is mandatory — summing the unrounded terms first produces different values. `submitted_at` is stamped from the logical clock at submission. The resulting composite is mirrored in two places: the placement's `satisfaction_score` is set to it, and the partner's `placement_quality_score` is set to it, so the partner row always carries the most recently submitted composite across all of its placements.

A placement that has been running is closed by recording a completion with an `outcome` of `CONVERTED` or `NOT_CONVERTED`. Only a placement at `ACTIVE` may complete, and completion requires two conditions: the logical-clock date must be on or after the placement's `end_date`, and the placement must carry at least one satisfaction record — a placement the partner never rated cannot be closed. The completion moves the placement `ACTIVE → COMPLETED`. Its effects are broad. The student's `conversion_streak` increments by 1 when the outcome is `CONVERTED` and resets to 0 when it is `NOT_CONVERTED`. When the outcome is `CONVERTED`, the `converted_to_hire` flag is set to true on every satisfaction record of this placement. The placement's `satisfaction_score` is set to the composite of its latest satisfaction record. The sponsoring agreement moves to `FULFILLED` if this completion brings its `ACCEPTED`, `ACTIVE` or `COMPLETED` placement count to `slot_count`. And if the completion leaves the student with no placement still in a non-terminal state while at least one placement is `COMPLETED`, the student graduates: `current_phase` advances `INTERNSHIP → COMPLETED`, `graduation_at` is stamped with the logical clock, and three outcome checkpoints are created as described in §3.8.

### 3.7. Placement Fee Billing and Partner Receivables

Every accepted placement carries a `placement_fee_cents`, the amount its sponsoring partner owes for hosting that intern. The fee is built in five steps, in this order. First, the supervision credit is the smaller of two amounts: the agreement's `supervision_hours_per_week` multiplied by 2,500 cents, that is, $25 for each committed supervision hour per week, and a ceiling of 50,000 cents, that is, $500. Second, the base amount is 200,000 cents — a flat $2,000 — plus that supervision credit. Third, the tiered amount is the base amount multiplied by the multiplier for the agreement's frozen `fee_tier`: 1.25 for `TIER_A`, 1.10 for `TIER_B` and 1.00 for `TIER_C`, rounded half up to a whole cent. Fourth, the duration factor is the number of days from the window start to the window end, divided by the 180 days of a scheduled placement. Fifth, `placement_fee_cents` is the tiered amount multiplied by the duration factor, rounded half up to a whole cent. The window used depends on when the fee is computed: at offer time it is the sponsoring agreement's own `start_date` through `end_date`, and at acceptance time it is the placement's accepted `start_date` through `end_date` supplied in the request, so a placement shorter or longer than the agreement's nominal window is billed in proportion to its real length. The fee is strictly proportional to the window length — it is not a two-step proration that pays the full tiered amount for any window of 168 days or more and half of it below that.

Billing begins when a `ProgramStaff` operator issues an invoice against a partner for a placement, supplying the `partner_id`, the `placement_id` and a `due_date`, and carrying the `expected_partner_version` guard described in §2.8. The invoice's `total_amount_cents` is copied from the placement's `placement_fee_cents` at issuance, `amount_paid_cents` starts at 0, `paid_on` starts null, and the `status` starts `ISSUED`. Before the invoice is written, the partner's `outstanding_balance_cents` plus the new invoice's total must not exceed the partner credit ceiling of 750,000 cents, that is, $7,500; exceeding it is `ERR_PARTNER_CREDIT_LIMIT` (402). Issuing the invoice recomputes the partner's `outstanding_balance_cents`, `billed_cents` and `oldest_open_due_date` from the invoice set, and increments the partner's `version` by 1.

An invoice ages on the logical clock. Once the logical-clock date passes an `ISSUED` invoice's `due_date`, the invoice moves `ISSUED → OVERDUE`; that evaluation runs when the clock advances and again whenever the invoice or its partner is read, so a stale `ISSUED` reading is never served past its due date. The move to `OVERDUE` recomputes the partner's `outstanding_balance_cents`, `billed_cents` and `oldest_open_due_date`, sets the partner's `credit_hold` to true, and suspends the partner outright — `status` becomes `SUSPENDED` — when that invoice's `due_date` is strictly more than 30 days before the logical-clock date. A suspended partner cannot activate agreements, be matched to placements or receive offers, and a partner on credit hold cannot activate agreements at all.

Payment is recorded against an invoice with an `amount_paid_cents` and a `paid_on` date, and the amount must match the invoice's `total_amount_cents` exactly, since this API records full payment only; a mismatch is `ERR_PAYMENT_AMOUNT_MISMATCH` (422). An `ISSUED` or `OVERDUE` invoice moves to `PAID`, `paid_on` is recorded, and the partner's `on_time_payment_ratio`, `collected_cents`, `collection_ratio` and `outstanding_balance_cents` are all recomputed. The partner's `credit_hold` is cleared once no other invoice of that partner remains `OVERDUE`, and the partner's `status` returns to `ACTIVE` once no invoice remains `OVERDUE` by more than 30 days. An unpaid invoice can also be voided by a `ProgramStaff` operator with an optional `reason`; an `ISSUED` or `OVERDUE` invoice moves to `VOID`, and the partner's `outstanding_balance_cents`, `billed_cents` and `oldest_open_due_date` are recomputed with the voided invoice excluded from every aggregate. `PAID` and `VOID` are both terminal for an invoice — neither can be paid, voided or aged further, and any such attempt is refused with `ERR_ALREADY_TERMINAL` (409).

The partner's receivable picture is not maintained incrementally but derived from the invoice set on every change and on every read, using the definitions in §2.10. `outstanding_balance_cents` is the sum of `total_amount_cents` over the partner's `ISSUED` and `OVERDUE` invoices; `billed_cents` adds the `total_amount_cents` of its `PAID` invoices to that; `collected_cents` is the sum of `amount_paid_cents` over its `PAID` invoices; `collection_ratio` is `collected_cents` divided by `billed_cents` to 4 decimal places round half up, or 0.0000 when `billed_cents` is 0; and `oldest_open_due_date` is the earliest `due_date` among the `ISSUED` and `OVERDUE` invoices, or null when there are none. Because every one of these is a sum or a minimum, the result does not depend on the order in which the invoices were processed.

### 3.8. Graduation, College Credit and Outcome Tracking

Graduation is the moment a student's `current_phase` reaches `COMPLETED` and `graduation_at` is stamped, which happens automatically when a placement completion leaves the student with no non-terminal placement and at least one `COMPLETED` placement (§3.6). At that moment the system creates three outcome checkpoints for the student, one at each `interval_months` value of 3, 6 and 12, and writes each one's `due_date` as `graduation_at` advanced by that many calendar months. Each checkpoint starts with `employment_status` at `UNKNOWN` and no wage recorded.

A graduate records the survey result on a checkpoint by supplying an `employment_status` of `UNKNOWN`, `EMPLOYED`, `UNEMPLOYED` or `ENROLLED_EDUCATION`, an optional `hourly_wage_cents`, and an optional `recorded_at`. A checkpoint recorded as `EMPLOYED` must carry a positive `hourly_wage_cents`; omitting it is a `ERR_INVALID_REQUEST` (422). When `recorded_at` is omitted, the server stamps it from the logical clock. Only the student the checkpoint belongs to may record it, and any other actor is refused with `ERR_NOT_OWNER` (403). Checkpoints are the program's long-run evidence: they capture whether the graduate is working and at what wage at three, six and twelve months after graduation.

College credit runs alongside the placement record. A `ProgramStaff` operator registers a grant with a `student_id`, the `college_partner_name` of the higher-education institution granting it, and a `credit_hours` value that must be greater than zero. The grant starts at `status` `PENDING` and its own `tuition_credit_cents` is computed at creation as the smaller of `credit_hours` multiplied by 12,500 cents — $125 per credit hour — and a per-grant cap of 500,000 cents, that is, $5,000. A grant is then advanced by a `ProgramStaff` operator who supplies a `status` of `GRANTED` or `VOID` and an optional `reason`. Advancing a grant to `GRANTED` requires the student's `current_phase` to be `INTERNSHIP` or `COMPLETED` and the logical-clock date to be on or before the student's `graduation_at` plus 365 days; a grant that fails either condition is refused with `ERR_PARENT_STATE_CONFLICT` (409). Advancing it to `VOID` carries no such condition. `GRANTED` and `VOID` are both terminal, and any further attempt to move the grant is refused with `ERR_ALREADY_TERMINAL` (409).

The student's total tuition credit is an aggregate over the grants that still count. The included set is the student's grants at status `PENDING` or `GRANTED`; a `VOID` grant contributes nothing. Each included grant contributes its per-grant value — `credit_hours` multiplied by 12,500 cents, capped at 500,000 cents, the cap being applied to each grant individually before any summing, so two grants of 48 credit hours each contribute 500,000 cents apiece rather than 1,200,000 cents between them. Those per-grant values are summed into a subtotal, and a graduation bonus of 50,000 cents is added when the student's `current_phase` is `COMPLETED`, giving the total tuition credit for the student.
