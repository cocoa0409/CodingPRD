# Payroll Employment Verification Exchange API — Product Requirements Document

## 1. Introduction

Lenders, social-service agencies, background screeners, landlords and insurers all need the same thing at the moment of decision: a trustworthy statement of what a person earns and whether they still work where they said they do. Today that statement arrives by fax, by pay stub, or by a call to a payroll clerk, and it arrives too late to matter. This document specifies the Payroll Employment Verification Exchange — a data exchange in which employers contribute payroll files, workers control who may look at them, and requesting parties receive an instant, machine-readable verification anchored in a specific pay period.

The exchange is a compliance and audit system first and a data-delivery system second. Every verification must be traceable to a captured consumer authorization with a declared permissible purpose, a purchasable product tier whose depth the requesting party is entitled to receive, and an employer feed that is demonstrably current. When any of those anchors fails — the authorization lapsed, the purpose does not match, the employer filed a data freeze, the feed stalled, the record moved out of currency — the request must be declined with a machine-readable reason rather than answered with data of unknown quality. Verification admissions therefore ride on a strict precedence order, and refusals are as much a part of the product as approvals.

Contributors are paid for the records they supply, requesting parties prepay for the verifications they consume, and workers are entitled to see their own file and to dispute it when it is wrong. That means the exchange also carries a settlement ledger with conserved quantities, a dispute cycle with employer response deadlines, a disclosure path that reconstructs a worker's file from the same records the verification path draws on, and a currency-monitoring loop that watches each contributor's feed cadence and escalates when pay periods go missing. Only three roles do productive work here — the employer who contributes and answers for its data, the worker who consents and disputes, and the requesting party who looks — with a platform operator role that onboards all three and drives the exchange's logical clock.

## 2. Global Specifications & System-Wide Principles

### 2.1. Identity, Roles and Ownership Boundaries

Every request carries two headers. `X-User-ID` names the acting principal and `X-User-Role` names the role it acts under; when `X-User-Role` is absent, when `X-User-ID` is absent, or when the role is not one of the four declared roles, the request fails with `ERR_UNAUTHENTICATED` (HTTP 401). A role that is present and recognized but not listed on the addressed operation's role set fails with `ERR_UNAUTHORIZED` (HTTP 403). The complete role enumeration is `PlatformAdmin`, `Employer`, `CoveredWorker` and `Verifier`; these spellings are exact and case-sensitive.

Ownership is what turns `X-User-ID` from a label into an access-control decision. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it, but it is never compared to any entity's `id`, so a platform operator may act on any row. When `X-User-Role` is `Employer`, `X-User-ID` is the `id` of the acting `Employer`, and every ownership check on a resource that references an employer — a `RecordLayout`, a `PayrollFeedBatch`, an `EmploymentRecord`, a `CompensationAccrual`, a freeze filing — compares that resource's employer foreign key to `X-User-ID`. When `X-User-Role` is `CoveredWorker`, `X-User-ID` is the `id` of the acting `CoveredWorker`, and ownership checks compare `covered_worker_id` on the addressed resource to `X-User-ID`. When `X-User-Role` is `Verifier`, `X-User-ID` is the `id` of the acting `Verifier`, and ownership checks compare `verifier_id` to `X-User-ID`. An entity-backed role acting on a row owned by a different entity of the same type is rejected with `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403).

Role scoping is not uniform across the surface. Contributor onboarding, worker registration, requesting-party registration, product administration, accrual and settlement administration, currency-review administration, escrow adjustment and logical-clock control are reserved to `PlatformAdmin`. Contributor-side layout, batch, record-retention, dispute-notice, dispute-response and freeze operations are reserved to the acting `Employer`. Authorization capture, opt-out and opt-in, disclosure request and generation, dispute filing and reopening, corrected-span reconfirmation, request permitting and request reconsent are reserved to the acting `CoveredWorker`. Request permitting is shared between `CoveredWorker` and `PlatformAdmin`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept a page size in `limit` and a start position in `offset`. The default `limit` is 10, its minimum is 1 and its maximum is 100; a selection outside that range falls outside the contract this document fixes. The default `offset` is 0. The four pagination fields — `limit`, `offset`, `total_count` and `has_more` — appear in the response `meta` for list endpoints; `total_count` reports the number of resources matching the filters before the page is cut, and `has_more` reports whether further rows exist beyond the returned page. Lists are ordered by `created_at` ascending unless the operation is described otherwise; in particular the disclosure file's embedded record list follows its own explicit ordering described in §3.6, and the settlement waterfall's accrual ordering is pinned in §3.7.

### 2.4. Canonical Resource Properties, Precision and Rounding

Every persisted resource carries an `id` minted by the server as a UUID with no type prefix and no embedded entity name; foreign keys in request bodies and responses are those raw UUIDs. Every persisted resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits, and `updated_at`, which is refreshed whenever the row is mutated. Every persisted resource carries an integer `version` that starts at 1 and increments by exactly 1 on every mutation, including mutations caused by cascades rather than by a direct client call.

The single exception is `VerificationResponse`, which is declared without common fields: it carries only `id` and `created_at`, and it has neither `updated_at` nor `version`. No operation takes or returns an `expected_..._version` for a response row, and a response row is never mutated in place — the reversal path deletes it.

Money is always carried in integer cents. Where a monetary or scored result requires rounding, the exchange rounds half up — a half-cent or half-point is resolved upward — and rounds once at the point named in the rule that produced it, never by successive re-rounding of an intermediate. The per-record annualization rule rounds each record individually before any batch-level aggregation, so batch totals are plain sums of already-rounded figures rather than a single rounding of a summed total. Score values that are integer-valued are rounded half up once, after their weighted sum has been formed. Counts, month depths and day counts are exact integers and are never rounded.

### 2.5. Consumer Authorization as the Permission Root

Nothing in the exchange resolves a worker's employment data without a live `ConsumerAuthorization` behind it. An authorization binds a `covered_worker_id` to a `verifier_id` under one `permitted_purpose`, and it carries the `granted_at` instant at which it was captured, an `expires_at` that is `granted_at` advanced by 365 days and frozen at grant time, and a `revoked_at` that stays null while the authorization is live. Its `status` is `CAPTURED` at creation and moves to `REVOKED` when the worker opts out. Its `permitted_purpose` is one of `PUBLIC_BENEFIT_DETERMINATION`, `MORTGAGE_CREDIT_DECISION`, `EMPLOYMENT_SCREENING`, `TENANT_SCREENING` or `INSURANCE_UNDERWRITING`, and it must equal both the requesting party's declared purpose and the purpose the request asserts; the two mandatory overlaps of the 365-day grant and of the reconsent interval are pinned in §3.1 and §2.13 respectively.

A worker whose consent record has advanced since the client last read it cannot have a new authorization captured against it: the capture must supply `expected_covered_worker_version`, the caller's last observed `version` of the `CoveredWorker` row, and a value that no longer equals the row's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412). This is a staleness rejection, not an overlap rejection — a worker may legitimately hold several live authorizations for different requesting parties, so a second capture is not wrong in itself; the only defect the check catches is that `consent_status` and `opt_out` were read from a superseded view of the row.

### 2.6. Verification Product Tiers and Depth Constraints

A `VerificationProduct` is the purchasable unit of verification depth. Its `product_code` is a stable identifier unique across all products, its `tier` is one of `EMPLOYMENT_ONLY`, `EMPLOYMENT_INCOME` or `FULL_INCOME_HISTORY`, its `requesting_class` is one of `SOCIAL_SERVICE`, `MORTGAGE`, `BACKGROUND`, `TENANT` or `INSURANCE`, its `base_fee_cents` is the per-transaction list price, its `history_months_included` is one of exactly 0, 12 or 24, and `includes_employment_status` declares whether the tier renders the employment status and tenure dimensions. Its `active` flag defaults to true and an inactive product refuses new submissions. `rendered_field_set` is projected at product creation and lists, sorted lexicographically ascending, the canonical field names the tier renders.

A requesting party may only buy depth its class entitles it to. `Verifier.verifier_class` maps to a product class — `DEPARTMENT_OF_SOCIAL_SERVICES` and `GOVERNMENT_AGENCY` map to `SOCIAL_SERVICE`, `MORTGAGE_LENDER` maps to `MORTGAGE`, `BACKGROUND_CHECKER` maps to `BACKGROUND`, `LANDLORD` maps to `TENANT`, and `INSURER` maps to `INSURANCE` — and the requested product's `requesting_class` must equal that mapped class. A class mismatch, or a product whose `active` flag is false, fails with `ERR_PRODUCT_NOT_PERMITTED_FOR_CLASS` (HTTP 403). One uniqueness discipline runs across the whole exchange, and it is the reason several otherwise unrelated registrations share a failure mode: a contributor's `fein` is unique across all contributors, a batch's (`employer_id`, `batch_sequence`) pair is unique for its contributor, a product's `product_code` is unique across all products, and an accrual's (`employer_id`, `transaction_ref`) pair is unique for its contributor — any repeat is rejected with `ERR_DUPLICATE_RESOURCE` (HTTP 409).

### 2.7. The Employer Data Freeze and Its Cascade

An employer can withdraw its whole book from the exchange. `freeze_state` begins at `NONE`; filing a freeze moves it to `REQUESTED` and records the `freeze_reason_code` — one of `EMPLOYER_DIRECTIVE`, `REGULATORY_HOLD` or `DATA_QUALITY_INVESTIGATION` — together with a `freeze_requested_at` stamp, while the filing must carry a submitted `reason_code` and may only be made by the employer that owns the row. A second filing against an employer already in `REQUESTED` activates the freeze; filing against an employer already `ACTIVE` is rejected with `ERR_ACTIVE_FREEZE_BLOCK` (HTTP 409). Once `ACTIVE`, the freeze propagates outward in ordered hops: the employer's `EmploymentRecord` rows move to `FROZEN` and record the employer version they observed, every `VerificationRequest` of that employer sitting in `PERMITTED` or `VALIDATED` is declined with `EMPLOYER_FROZEN` and its fee released, and each `SIGNED` attestation belonging to a declined request is invalidated. While `ACTIVE`, the employer keeps the last feed status it derived and its records stay frozen — the ordinary feed-currency derivation is suppressed. The instant a record freezes, it records in `frozen_by_employer_version` the employer version that stood immediately before the freeze cascade's own version increment, so the row remembers exactly which view of the employer it froze against.

Releasing or lapsing the freeze runs the same cascade in reverse by moving frozen records to `STALE` and clearing the recorded employer version; lapsed and released employers can be frozen again, returning `freeze_state` to `NONE`. A `REGULATORY_HOLD` freeze cannot be released until the hold is withdrawn — an attempted release raises `ERR_REGULATORY_HOLD_IRRELEASABLE` (HTTP 409) — and a lapse requires that the employer carry no open disputes and no request sitting in `PERMITTED`.

### 2.8. Lifecycle Enumerations in Play

Every state string in the exchange is exact and uppercase. A `RecordLayout`'s `status` is `DRAFT`, `VERIFIED` or `SUPERSEDED`. A `PayrollFeedBatch`'s `validation_state` is `RECEIVED`, `VALIDATED` or `REJECTED`. A `CompensationAccrual`'s `cycle_state` is `ACCRUED`, `WAIVED` or `PAID` and never reaches a terminal state. A `DataCurrencyReview`'s `review_state` is `PENDING`, `SCORED`, `ESCALATED` or `CLEARED`. A `ConsumerDisclosure`'s own `disclosure_state` is `REQUESTED`, `GENERATED` or `SUPERSEDED`, while the separate `disclosure_state` field on `CoveredWorker` is `NEVER_DISCLOSED`, `CURRENT` or `STALE`. A `VerificationAttestation`'s `attestation_state` is `PENDING`, `SIGNED`, `SUPERSEDED` or `INVALIDATED`, and the purpose it records in `attested_purpose` is one of the five permissible purposes below. An `EmploymentRecord` carries two independent dimensions that never share a transition: `record_state` runs through `PENDING_VERIFICATION`, `VERIFIED`, `DISPUTED`, `CORRECTED` and `IMMUTABLE`, and `currency_state` runs through `CURRENT`, `STALE` and `FROZEN`. A `RecordDispute`'s `dispute_state` runs through `FILED`, `AWAITING_EMPLOYER`, `NOTICE_SENT`, `EMPLOYER_RESPONDED`, `ESCALATED`, `RESOLVED_CORRECTED`, `RESOLVED_UPHELD` and `CLOSED`. A `VerificationRequest`'s `request_state` runs through `SUBMITTED`, `PENDING_AUTH`, `PERMITTED`, `VALIDATED`, `RESPONDED`, `DECLINED` and `REVERSED_RECONSENT_REQUIRED`. An employer's `review_state` is `NONE`, `PENDING`, `SCORED`, `ESCALATED` or `CLEARED`; its `feed_status` is `CURRENT`, `DELAYED` or `STALLED` and is a derived dimension, not a transition target. A `Verifier`'s `entitlement_status` is `UNVERIFIED`, `PENDING_REVIEW`, `AUTHORIZED` or `RESTRICTED`, and its `posture` is `NORMAL` or `RESTRICTED`, starting at `RESTRICTED` and permitting verification work only when `NORMAL`. A `CoveredWorker`'s `consent_status` is `PROVIDED` or `REVOKED`. A `VerificationRequest.decline_reason` is one of `NO_AUTHORIZATION`, `AUTHORIZATION_EXPIRED`, `PURPOSE_MISMATCH`, `WORKER_OPT_OUT`, `EMPLOYER_FROZEN`, `RECORD_STALE_INSUFFICIENT_HISTORY`, `ESCROW_INSUFFICIENT` or `VERIFIER_RESTRICTED`.

Terminal states are hard stops. A `VerificationRequest` that has reached `RESPONDED`, `DECLINED` or `REVERSED_RECONSENT_REQUIRED`, a `RecordLayout` that is `SUPERSEDED`, a `PayrollFeedBatch` that is `VALIDATED` or `REJECTED`, a `RecordDispute` that is `CLOSED`, a `DataCurrencyReview` that is `CLEARED`, and a `VerificationAttestation` that is `SUPERSEDED` or `INVALIDATED` may not be driven further by an action that assumes they are live; the attempt fails with `ERR_ALREADY_TERMINAL` (HTTP 409). A `CompensationAccrual` has no terminal state and may be voided back to `ACCRUED` repeatedly, subject to the grace windows of §3.7. An action addressed at a resource that is not in any state from which that action is defined fails with `ERR_INVALID_STATE` (HTTP 409), and reopening or responding to a `CLOSED` dispute fails with `ERR_DISPUTE_TERMINAL` (HTTP 409).

### 2.9. Stale-View Rejection on Contributor and Worker Writes

Two write operations are version-guarded because the client must decide against a row it has actually observed. Capturing a `ConsumerAuthorization` requires `expected_covered_worker_version` matching the target `CoveredWorker`'s current `version`, and filing a `RecordDispute` requires `expected_employment_record_version` matching the disputed `EmploymentRecord`'s current `version`. In both cases a supplied value that does not equal the parent row's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412). The filing check is not a duplicate-dispute check: a worker may legitimately file a fresh dispute over a span that was disputed and corrected before, and the only defect rejected is that the `claimed_field` values and the span's `currency_state` were read from a superseded view of the row. No other operation in the exchange accepts a client-supplied expected-version field, and no other endpoint rejects on version mismatch.

### 2.10. The Precedence Order for Verification Admission

An operation that resolves or materializes a worker's employment data must pass a gauntlet of checks, and the order in which they run is part of the contract because a request can fail several of them at once. The order is:

1. Authentication first: a missing or unrecognized `X-User-Role` or a missing `X-User-ID` yields `ERR_UNAUTHENTICATED` (HTTP 401).
2. Role authorization next: a role the operation does not list yields `ERR_UNAUTHORIZED` (HTTP 403).
3. Ownership next: an entity-backed role acting on another entity's row yields `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403).
4. Existence next, validated left to right through the path: a path-addressed resource that does not exist yields `ERR_NOT_FOUND` (HTTP 404); a body-supplied foreign key that does not resolve yields `ERR_REFERENCE_NOT_FOUND` (HTTP 404) after the path check passes.
5. State admissibility next: a resource in a state from which the action is undefined yields `ERR_INVALID_STATE` (HTTP 409), and a resource already terminal yields `ERR_ALREADY_TERMINAL` (HTTP 409).
6. Verifier posture next: a requesting party whose `posture` is not `NORMAL` blocks any operation that consumes a worker's data on its behalf — submitting a request, permitting a request, validating currency and building a response — all with `ERR_VERIFIER_RESTRICTED` (HTTP 403). A requesting party whose `entitlement_status` is not `AUTHORIZED` is refused the same way and with the same identifier.
7. Worker opt-out next, at the same tier and with equal force: an operation that resolves or materializes a worker's data — permitting, validating currency or building a response — is refused with `ERR_WORKER_OPT_OUT` (HTTP 403) when `opt_out` is true or `consent_status` is `REVOKED`. The request-submission step is not refused here; a submitted request whose worker has opted out is declined and is recorded under `WORKER_OPT_OUT` through the decline path of §3.2.
8. Permissible purpose next: the purpose must be present and consistent across the authorization's `permitted_purpose`, the request's `permissible_purpose_asserted` and the requesting party's `permitted_purpose`; the presented authorization must be `CAPTURED`; and its `expires_at` must be on or after the current instant, so an authorization expiring exactly now is still admissible. The purpose comparison runs before the expiry comparison, and both run before any data-availability check. Any failure here yields `ERR_PERMISSIBLE_PURPOSE_UNAVAILABLE` (HTTP 403). This binding governs submission, permitting, currency validation and response construction, and is the step that declines a request whose authorization has lapsed with `AUTHORIZATION_EXPIRED` or whose purpose diverges with `PURPOSE_MISMATCH`, leaving a request with no live authorization at all to be declined with `NO_AUTHORIZATION`.
9. Product class match next: a requesting party whose class does not map to the product's `requesting_class`, or a product that is inactive, yields `ERR_PRODUCT_NOT_PERMITTED_FOR_CLASS` (HTTP 403). This gate closes submission and permitting but not currency validation or response construction.
10. Freeze, then feed, then match, then escrow: the selected employer's `freeze_state` must be `NONE`, its `feed_status` must not be `STALLED`, `employer_match_selection` must have produced at least one candidate employer, and the requesting party's `escrow_balance_cents` must be on or above the fee this transaction would post. These yield, in order, `ERR_EMPLOYER_FROZEN` (HTTP 403), `ERR_EMPLOYER_FEED_STALLED` (HTTP 422), `ERR_NO_EMPLOYER_MATCH` (HTTP 422) and `ERR_ESCROW_INSUFFICIENT` (HTTP 402). The escrow comparison is inclusive: a balance exactly equal to the fee is sufficient and leaves the balance at exactly zero.

Three structural operations enforce their own single checks outside this ordering. A `RecordLayout` promoted to `VERIFIED` must have zero unmapped canonical fields and a `column_map` covering every canonical field; an incomplete mapping yields `ERR_LAYOUT_MAPPING_INCOMPLETE` (HTTP 422). A batch validated while its `record_layout_id` references a layout that is not `VERIFIED` yields `ERR_BATCH_LAYOUT_NOT_VERIFIED` (HTTP 422), and a batch whose `pay_period_end_date` is not strictly after the employer's `last_feed_received_date` yields `ERR_FEED_NOT_MONOTONIC` (HTTP 422). A batch that declares more records than the 50000-record ceiling, or that carries an attached record whose `separation_date` precedes its `hire_date`, yields `ERR_BATCH_RECORD_COUNT_EXCEEDED` (HTTP 422).

### 2.11. Interval Guards, Window Separation and Temporal Bounds

Two admission guards protect windowed obligations, and they are deliberately asymmetric. A new `ConsumerAuthorization` for the same `covered_worker_id`, `verifier_id` and `permitted_purpose` is rejected with `ERR_AUTHORIZATION_OVERLAP` (HTTP 409) when an existing authorization for that triple is `CAPTURED` and its half-open interval from `granted_at` up to but not including `expires_at` already covers the current instant; because the interval is half-open, an authorization whose `expires_at` is exactly the current instant does not occupy it, so a grant landing on the expiry instant is admitted. A new `DataCurrencyReview` for an employer is rejected with `ERR_REVIEW_WINDOW_OVERLAP` (HTTP 409) when any existing review for that employer is `PENDING`, `SCORED` or `ESCALATED` and its closed window — `review_period_end` minus `window_days` through `review_period_end` inclusive — is separated from the new window by fewer than 3 days of gap. Here a gap of exactly 3 days is admitted while a zero-day gap is rejected: the opposite adjacency semantics to the authorization guard, and the reason the two must not be implemented with shared code.

Temporal bounds elsewhere are inclusive where the rule says "on or before". An employer resolution or notice on a dispute must arrive no later than `response_due_date`; a resolution landing exactly on the due date is accepted and one landing the next day is rejected with `ERR_DISPUTE_RESPONSE_WINDOW_EXPIRED` (HTTP 422). A reopened dispute must be reopened within 14 days of `resolved_at`, and a `PAID` accrual may only be voided within 30 days of its `updated_at`. At most one `VerificationResponse` row may exist per `VerificationRequest`; a second materialization attempt against a request that already carries a response row is rejected with `ERR_RESPONSE_ALREADY_MATERIALIZED` (HTTP 409). A disclosure file may only be generated while the worker's `disclosure_state` is `NEVER_DISCLOSED` or `STALE`; regenerating while it is `CURRENT` is rejected with `ERR_DISCLOSURE_ALREADY_CURRENT` (HTTP 409). A settlement that names an outcome other than `WAIVED` or `PAID`, or that covers no accrual in `ACCRUED` state, yields `ERR_SETTLEMENT_OUTCOME_INVALID` (HTTP 422), and a compensating adjustment that would drive a settled counter below zero yields `ERR_COUNTER_FLOOR_VIOLATION` (HTTP 409).

### 2.12. The Logical Clock

The exchange runs on a logical clock, not on wall-clock time. Until the clock is set it reads exactly 2026-09-01T00:00:00Z, and it never reads real wall-clock time. A platform operator sets it with a `to_iso8601` instant; setting the clock re-evaluates every employer's `feed_status` and runs the dispute escalation sweep against the new instant, so an instant placed far enough in the future can stall feeds and escalate disputes as a side effect of the set itself. A companion test-driving capability advances the clock to the first instant after a named batch's expiry, taking a `payroll_feed_batch_id`, and re-evaluates the owning employer's currency. Every derivation in this document that speaks of "the current instant", "now", or a day count between a stamp and the present reads that logical clock.

### 2.13. Reconsent Intervals and the Consent Loop

A request that cannot proceed on the authority it holds does not die; it goes back around the consent loop. A `PERMITTED` request may be returned to `SUBMITTED` by the worker — clearing its `resolved_product_tier` and its `consumer_authorization_id` — but only once at least 7 days have elapsed since its `submitted_at` and only while the worker's `opt_out` is false. A request in `PENDING_AUTH` reaches `PERMITTED` when a `CAPTURED` authorization for the worker, requesting party and asserted purpose exists, has not expired, the worker's `opt_out` is false and the requesting party's `entitlement_status` is `AUTHORIZED`; a request that is still `SUBMITTED` when such an authorization already exists reaches `PERMITTED` directly, without passing through `PENDING_AUTH`, on the same conditions. A request in `REVERSED_RECONSENT_REQUIRED` returns to `SUBMITTED` — clearing its `decline_reason` — when a `CAPTURED` authorization for the worker and requesting party exists and the worker has not opted out. Submission itself is automatic: when no `CAPTURED` authorization exists for the worker, requesting party and asserted purpose at submission time, the request advances from `SUBMITTED` to `PENDING_AUTH` on the spot.

### 2.14. Nested Path Addressing

Path parameters are validated left to right, so a request naming a parent and a child resolves the parent first: if the parent does not exist the failure is `ERR_NOT_FOUND` (HTTP 404) regardless of whether the child would have resolved. The unfreeze filing is also the only operation that carries an `outcome` field, whose value is either the release that clears the freeze or the lapse that ends it. The exchange's deeply addressed operations are the employer freeze and unfreeze filings, the layout verify step, the batch record, reject, and validate steps, the record reconfirm and retain steps, the worker opt-out and opt-in steps, the request permit, currency-validation and reconsent steps, the disclosure generate step, the dispute notice, respond and reopen steps, the settlement void step, the currency-review escalate and rescore steps, the requesting-party accredit, authorize and escrow-adjustment steps, and the response and attestation reads. A resource reachable under one parent is not reachable under another: a batch's reject step addressed with an id belonging to a different employer's batch fails the ownership check before any state check runs.

## 3. Business Logic & Workflows

### 3.1. Contributor Onboarding, Layout Mapping and the Feed Calendar

A payroll contributor enters the exchange when a platform operator onboards it with its `legal_name` and its nine-digit `fein`, tagged with an `employer_type` of `PRIVATE`, `NON_PROFIT`, `STAFFING_AGENCY` or `GOVERNMENT` and a declared `payroll_frequency` of `WEEKLY`, `BIWEEKLY`, `SEMIMONTHLY` or `MONTHLY`. That cadence is not decoration: it drives both the pay-period bucketing of contributed income and the staleness arithmetic that decides, later and elsewhere, whether the contributor's feed is still trustworthy. Onboarding initializes `feed_status` to `CURRENT`, `freeze_state` to `NONE`, `review_state` to `NONE`, `last_feed_received_date` to null, `missing_periods` and `currency_score` to 0, `total_records_contributed` to 0, `dispute_open_count` to 0, `compensation_earned_cents` to 0 and `counted_verification_records` to 0. A repeated `fein` is refused with `ERR_DUPLICATE_RESOURCE` (HTTP 409), and the contributor's `employer_type` is drawn from `PRIVATE`, `NON_PROFIT`, `STAFFING_AGENCY` and `GOVERNMENT`.

The contributor then declares how its payroll file is shaped. Registering a record layout supplies the owning `employer_id`, a monotonic `layout_version` of at least 1, a `column_map` that maps the contributor's own column names onto canonical field names, and a `fiscal_year_start_month` between 1 and 12 that anchors fiscal bucketing. The canonical vocabulary is fixed: `worker_ssn_last4`, `worker_date_of_birth`, `hire_date`, `employment_status`, `pay_rate` and `pay_rate_basis`. Each registration recomputes the layout's two diagnostics — `validation_error_count`, the number of required canonical entries absent from the map, and `missing_canonical_fields`, the sorted list of those absent names, empty when the map is complete. A layout begins life as `DRAFT`, its `verified_at` null, and it may be revised any number of times while `DRAFT`; each revision replaces the `column_map` wholesale, recomputes the diagnostics, and leaves `verified_at` alone. Conventional layouts in this domain map a single contributor column to each canonical name, so a map that leaves any of the six canonical names uncovered is incomplete and its `missing_canonical_fields` is non-empty. A `column_map` that maps a contributor column onto something outside the canonical vocabulary simply leaves the corresponding canonical entries absent, and they show up in `missing_canonical_fields` by their canonical names. A layout with any absent canonical field cannot be promoted: the verify step requires `validation_error_count` of zero and a complete map, and otherwise fails with `ERR_LAYOUT_MAPPING_INCOMPLETE` (HTTP 422). On success it moves to `VERIFIED` and stamps `verified_at` with the current instant. A `VERIFIED` layout may be reverted to `DRAFT` by a further map revision — clearing `verified_at` and recomputing the diagnostics — but only while no batch referencing it is still `RECEIVED`, because an in-flight batch cannot have its mapping yanked out from under it.

Registering a new layout does more than create a row: it supersedes the contributor's pinned predecessor. The predecessor is deterministic and not fuzzy — among the layouts whose `employer_id` equals the new layout's `employer_id`, it is the one with the greatest `layout_version` strictly less than the new layout's `layout_version`, and ties are broken by `created_at` ascending; a layout's own `id` never participates in the selection. When a predecessor exists, its `status` becomes `SUPERSEDED` and it is terminal. The new layout's `layout_version` must be strictly greater than its predecessor's; a version that is not strictly greater is refused. A layout that falls into `SUPERSEDED` takes no further revisions and no further verification.

### 3.2. Authorization Capture, Opt-Out and the Worker's Control of Their File

Workers, not employers, decide who may look. A worker is registered by a platform operator with a `full_name`, the last four digits of the SSN in `ssn_last4` — exactly four digits, used to match contributor rows to the worker — and a `date_of_birth`; registration stamps the row's `version` at 1. registration initializes `consent_status` to `PROVIDED`, `opt_out` to false, `disclosure_state` to `NEVER_DISCLOSED`, and the counters `open_dispute_count` and `corrected_record_count` to 0.

To let a requesting party verify them, the worker captures a `ConsumerAuthorization` naming the `verifier_id`, the `permitted_purpose`, and carrying `expected_covered_worker_version`. The purpose the worker authorizes must equal both the requesting party's declared purpose and the purpose the request later asserts, and a grant whose window touches an existing live grant for the same triple by half-open interval semantics is refused with `ERR_AUTHORIZATION_OVERLAP` (HTTP 409) as described in §2.11. Capturing an authorization bumps the worker's `version`.

Worker-level opt-out is the blunt instrument. Setting opt-out flips `consent_status` to `REVOKED` and `opt_out` to true, revokes every live authorization, declines every request still in `SUBMITTED`, `PENDING_AUTH`, `PERMITTED` or `VALIDATED` with `WORKER_OPT_OUT`, reverses every request already `RESPONDED` into `REVERSED_RECONSENT_REQUIRED` (also stamped `WORKER_OPT_OUT`), invalidates the `SIGNED` attestations of every affected request, and releases the counted records through the compensation invariant of §3.9. Opt-out is per-worker: it blocks every future verification for that worker regardless of employer. Opting back in flips `consent_status` to `PROVIDED` and `opt_out` to false, restoring eligibility but not reinstating any authorization that was already revoked.

### 3.3. Payroll Batch Ingestion and the Currency Sweep

A contributor submits a payroll batch keyed to a pay period with its `employer_id`, the `record_layout_id` of the verified layout the batch was mapped with, a contributor-assigned `batch_sequence` that must be unique for that employer, the `pay_period_end_date` the batch covers, and a declared `record_count` of at least 1. The batch opens in `RECEIVED` with `accepted_record_count` and `rejected_record_count` at 0, `gross_amount_cents` at 0 and `received_at` stamped from the logical clock. Batches in `RECEIVED` or `REJECTED` never advance the employer's currency data. Because a batch's own layout must be settled before its payload can be trusted, a batch validated while its `record_layout_id` points at a layout that is not `VERIFIED` fails with `ERR_BATCH_LAYOUT_NOT_VERIFIED` (HTTP 422).

Before validation the contributor declares how many of the batch's declared entries were unparseable under the layout. A record-entry declaration sets `rejected_record_count` to the submitted `rejected_entries` and recomputes `accepted_record_count` as `record_count` minus `rejected_record_count`; the contributor is compensated on the accepted figure, not the declared one. A second declaration path rejects the batch outright, moving it to `REJECTED` and freezing every attached record's `currency_state`; `REJECTED` is terminal for the batch.

Validation is the sole transition that advances feed currency. It requires that the batch belongs to the acting employer, that its layout is `VERIFIED`, that `rejected_record_count` is 0, that `record_count` does not exceed the 50000-record ceiling, and that `pay_period_end_date` is strictly after the employer's current `last_feed_received_date`; a batch whose pay period is not strictly later fails with `ERR_FEED_NOT_MONOTONIC` (HTTP 422), and one carrying a `record_count` above the ceiling or an attached record whose `separation_date` precedes its `hire_date` fails with `ERR_BATCH_RECORD_COUNT_EXCEEDED` (HTTP 422). On success the batch becomes `VALIDATED` — terminal — and a single transition drives a long list of consequences: `last_feed_received_date` advances to the later of its current value and the batch's `pay_period_end_date`; every attached record is set to `record_state` `VERIFIED` and `currency_state` `CURRENT`, which is what closes both the pending-verification hop and the stale-feed hop for those rows; the employer's `feed_status` is derived to `CURRENT`; the annualization rule of §3.4 runs per attached record and `gross_amount_cents` becomes the sum of the per-record results; the employer's `total_records_contributed` grows by `accepted_record_count`; and the contributor's pricing rule of §3.7 runs against the batch's declared `record_count` and appends a `CompensationAccrual` for the employer.

Currency moves on its own schedule, driven by the staleness arithmetic of §3.8. When an employer's derived `feed_status` moves to `DELAYED` or `STALLED`, every one of its `CURRENT` records is staled. When the feed returns to `CURRENT` — which happens through a fresh validated batch — records in `STALE` are restored to `CURRENT` by that same validation. A freeze overrides this entirely: a record in `CURRENT` or `STALE` moves to `FROZEN` when its employer's `freeze_state` reaches `ACTIVE`, and returns to `STALE` when the freeze is released or lapses. The two dimensions are genuinely independent — a record can be `VERIFIED` and `STALE`, or `DISPUTED` and `FROZEN` — and no transition ever moves both at once.

### 3.4. Employment Records and Annualized Income

An employment span is attached to a received batch with its `employer_id`, `covered_worker_id`, the `payroll_feed_batch_id` that produced it, an `employment_status` of `ACTIVE`, `LEAVE_OF_ABSENCE`, `FURLOUGH`, `TERMINATED` or `RETIRED`, a `hire_date`, an optional `separation_date` that stays null while the span is open, a non-negative `pay_rate_cents`, a `pay_rate_basis` of `HOURLY`, `WEEKLY`, `BIWEEKLY`, `SEMIMONTHLY`, `MONTHLY` or `ANNUAL`, an optional `standard_hours_per_week` that only means anything when the basis is `HOURLY`, and a `final_pay_period_income_cents` that is 0 for open spans. Each write appends the span's `annualized_income_cents` and `tenure_months`.

The annualization rule converts the reported rate into a yearly figure and is recomputed on every record mutation — when a batch reaches `VALIDATED`, when a dispute resolves with a correction, and when a corrected span is reconfirmed. It first fixes the effective weekly hours: the reported `standard_hours_per_week`, or 40 when that field is absent, whichever is smaller, but never more than 60 hours a week. A contributor that reports 45 hours therefore annualizes on 45, one that reports 72 annualizes on 60, and one that reports nothing annualizes on 40. The normalized annual figure is then produced from `pay_rate_cents` according to the basis: for an hourly basis it is the rate multiplied by the effective weekly hours and then multiplied by 52 weeks; for a weekly basis it is the rate multiplied by 52; for a biweekly basis the rate multiplied by 26; for a semimonthly basis the rate multiplied by 24; for a monthly basis the rate multiplied by 12; and for an annual basis the rate stands as it is. That normalized figure is rounded half up to the nearest whole cent and stored as `annualized_income_cents`. The rounding happens per record and before any aggregation: a batch's `gross_amount_cents` is the plain sum of the already-rounded per-record values, and summing the raw values first and rounding once would produce a different figure whenever a record carries a fractional cent.

One variant applies to the final, partial pay period of a separated worker. When the span's `employment_status` is `TERMINATED`, its `separation_date` is present, and its `final_pay_period_income_cents` is greater than zero, the annual figure is not the standing rate. Instead the standing normalized rate is pro-rated to the pay periods actually worked by multiplying it by one less than the number of periods per year and dividing by the number of periods per year, and the final partial period's income is then added to that prorated amount; the result is rounded half up once. The number of periods per year comes from the employer's declared `payroll_frequency` — 52 for weekly, 26 for biweekly, 24 for semimonthly and 12 for monthly — so a monthly contributor whose standing normalized rate is 5200000 cents and whose final period income is 180000 cents annualizes to 4946667 cents rather than 5200000. A `TERMINATED` span with a zero final-period income, or an open span, takes the standing-rate branch unchanged.

Tenure is the companion measure: `tenure_months` counts completed whole months from `hire_date` to `separation_date`, or from `hire_date` to the current clock date while the span has no separation. A span that is its worker's most recent employment is what a verifier will see as the current employer once the match rule of §3.5 has run.

A settled span can be retained as `IMMUTABLE`, which freezes its source values against further recomputation: an immutable record still exposes the `annualized_income_cents` and `tenure_months` it stored, but no later rule recomputes them, and it is excluded from the depth counts and match candidacy of §3.5. Retention is barred while the span carries a dispute in `AWAITING_EMPLOYER`, `NOTICE_SENT`, `EMPLOYER_RESPONDED` or `ESCALATED`, and barred while its `currency_state` is `FROZEN`. Retaining a span has a disclosure side effect: every generated disclosure of that worker is superseded and its held-record count grows by one, because a retained span can no longer be re-derived into a fresh file.

### 3.5. Permissible-Purpose Verification from Submission to Response

A requesting party is registered by a platform operator with a `legal_name`, a `verifier_class` of `DEPARTMENT_OF_SOCIAL_SERVICES`, `MORTGAGE_LENDER`, `BACKGROUND_CHECKER`, `LANDLORD` or `INSURER`, a declared `permitted_purpose`, and an optional `escrow_balance_cents` that defaults to zero. A new requesting party starts with `entitlement_status` `UNVERIFIED` and `posture` `RESTRICTED`, so it cannot verify anything yet; moving it into accreditation review sets `entitlement_status` to `PENDING_REVIEW`, and authorizing it sets `entitlement_status` to `AUTHORIZED` and restores `posture` to `NORMAL`. Posture is not a free flag — it is derived from the risk score, and authorizing recomputes that score, so a party whose risk score has not fallen below the restriction threshold stays restricted even after it is authorized. Prepaid budget is topped up or drawn down through an `amount_cents` adjustment applied to `escrow_balance_cents`. A requesting party's `transaction_count` counts the requests it has taken to `VALIDATED` or `RESPONDED`, and its `negative_escalation_count` is the risk score produced by §3.8.

Submission begins the request lifecycle. A requesting party submits a request naming its `verifier_id`, the `covered_worker_id` it wishes to verify, the `product_id` it wishes to buy, and the `permissible_purpose_asserted` it claims. The request opens in `SUBMITTED` with `decline_reason` and `resolved_product_tier` null, `records_matched_count` and `fee_charged_cents` at 0, `responded_at` null and the rendered sets empty. Submission is subject to the posture, purpose and class gates of §2.10, and its purpose assertion must match both the authorization it will rely on and the requesting party's own declared purpose. Where no `CAPTURED` authorization yet exists for the worker, requesting party and asserted purpose, the request advances immediately from `SUBMITTED` to `PENDING_AUTH` and waits there for the worker.

Permitting is the worker's act. A permitted request must present the `consumer_authorization_id` it relies on, and on success it moves to `PERMITTED` with its `resolved_product_tier` snapshotted by the tier rule below and its `version` bumped. A request that was parked in `PENDING_AUTH` and one that was still `SUBMITTED` when a valid authorization already existed both reach `PERMITTED` by this route; the only difference is that the `SUBMITTED` case never had to pass through `PENDING_AUTH`. Aiming a permit at a request that is not in `SUBMITTED` or `PENDING_AUTH` fails the state check with `ERR_INVALID_STATE` (HTTP 409), and a request that has already reached one of its terminal states fails with `ERR_ALREADY_TERMINAL` (HTTP 409). Purpose binding governs: a permit whose presented authorization has lapsed fails with `ERR_PERMISSIBLE_PURPOSE_UNAVAILABLE` (HTTP 403) and is recorded with the reason `AUTHORIZATION_EXPIRED`, and one whose purposes diverge fails the same way with `PURPOSE_MISMATCH`.

Everything the worker sees as "the current employer" is chosen, not assumed. The requesting party's request is resolved against the worker's records by a match rule that ranks candidates and picks one. A candidate is any record for that worker whose `record_state` is `PENDING_VERIFICATION`, `VERIFIED` or `CORRECTED` — spans that are `DISPUTED` or `IMMUTABLE` are out, and so are spans in `FROZEN` currency — and whose employer's `freeze_state` is `NONE`. Candidates are ranked by `hire_date` descending first, so the most recent employment leads; ties are broken by an employment-status rank ascending, where `ACTIVE` ranks 0, `LEAVE_OF_ABSENCE` ranks 1, `FURLOUGH` ranks 2, `TERMINATED` ranks 3 and `RETIRED` ranks 4; and remaining ties are broken by `created_at` ascending. If `hire_date`, the status rank and `created_at` all tie, the record belonging to the employer whose batch carries the smaller `batch_sequence` wins. An employer's `id` is never consulted in this ranking — it identifies the employer but never orders it — and when the candidate pool is empty the request is declined with `ERR_NO_EMPLOYER_MATCH` (HTTP 422) rather than being answered with an empty result.

Depth is constrained by what the requesting party bought and by what the worker's history can support. The tier rule runs when a request reaches `PERMITTED` — and again on every read of a permitted request — and compares the product's nominal depth with the history actually available. Available history is the count of complete calendar months from the earliest `hire_date` among the selected employer's records in `PENDING_VERIFICATION`, `VERIFIED` or `CORRECTED` currency-`CURRENT` or `STALE` state up to the current clock date; records that are `DISPUTED`, `IMMUTABLE` or `FROZEN` are excluded from that count and cannot support a deeper tier. When the product's nominal history depth does not exceed the available months, the tier the requesting party asked for is the tier that resolves. When the nominal depth exceeds what is available, the resolution floors rather than fails: a request that can show at least 12 available months resolves to `EMPLOYMENT_INCOME` even if `FULL_INCOME_HISTORY` was purchased, and anything less resolves to `EMPLOYMENT_ONLY`. The floor is deliberate — an over-deep purchase is answered at the depth the data can support rather than declined for insufficient history.

Once a request is permitted, the requesting party checks whether the resolved data is current enough to answer instantly. Currency validation requires that the request is `PERMITTED`, that the selected employer's `feed_status` is `CURRENT`, and that every resolved record is in `CURRENT` currency; a stalled employer fails with `ERR_EMPLOYER_FEED_STALLED` (HTTP 422). On success the request moves to `VALIDATED`, `records_matched_count` is set to the number of resolved records, and the requesting party's `transaction_count` grows by one. The validation is not a one-way door. If any resolved record later moves out of `CURRENT` — a stale feed, a freeze — the request falls back from `VALIDATED` to `PERMITTED`, resets `records_matched_count` to 0, and decrements `transaction_count` by one so the count reflects only live validations. A request whose selected employer's records have all gone `FROZEN` under an `ACTIVE` freeze is not merely unvalidated: it is declined with `EMPLOYER_FROZEN`, and one whose records have gone stale without a freeze is declined with `RECORD_STALE_INSUFFICIENT_HISTORY`. Both declines release the fee and invalidate any signed attestation the request carried.

Building the response is the payoff and the most consequential single operation in the exchange. A response may be built from a request in `SUBMITTED` or from one in `VALIDATED`, and it requires a `verification_request_id`. It is admitted only when the requesting party's posture is `NORMAL`, the worker has not opted out, the selected employer's `freeze_state` is `NONE`, its `feed_status` is not `STALLED`, and the requesting party's escrow covers the fee this transaction would post. On success a great many things happen together. The request moves to `RESPONDED` and stamps `responded_at` from the logical clock. The resolved tier is recomputed and `current_employer_id` is set by the match rule; `current_employment_status` and `current_tenure_months` are set from the selected employer's selected record. The rendered field set is projected by the rule below and the income history is materialized at the resolved tier's depth. A `VerificationResponse` row is created carrying the same `product_tier`, `rendered_fields`, `employment_status`, `tenure_months`, `income_history`, `active_employment_found` and `employer_feed_status`, and the fee rule below posts `fee_charged_cents` against the requesting party's escrow. A `VerificationAttestation` is created already `SIGNED`, stamped at `signed_at` with the current logical-clock instant, and recording in `attested_purpose` the purpose the requesting party attested to. The employer's counted-verification-record figure is recomputed as specified in §3.9. The requesting party's `transaction_count` grows by one unless the request had already been counted at `VALIDATED`. The response payload's `active_employment_found` is true when the response includes an open span whose status is `ACTIVE`, `LEAVE_OF_ABSENCE` or `FURLOUGH`, and `employer_feed_status` records the contributing employer's feed status at the moment of materialization.

The rendered field set is determined by the tier and is always sorted lexicographically ascending. Four names are always present regardless of tier: the employer's legal name, `hire_date`, the employer feed status and the record match count. When the tier includes employment status, the employment status and tenure dimensions join the set. When the tier's nominal history depth is greater than zero, the income history joins it. When that nominal depth is at least 12 months, the pay rate and its basis join the set. When the nominal depth is at least 24 months, the separation date and the final-pay-period income join it. The income history itself is a list of monthly buckets ordered by bucket month descending: an employment-only tier carries none, an employment-and-income tier carries the smaller of 12 and the available months, and a full-history tier carries the smaller of 24 and the available months. A downgraded tier therefore renders fewer buckets than its nominal depth — a full-history request resolved over 14 available months renders 14 buckets, while the same tier resolved over 30 available months renders its nominal 24. Fields that belong to a record in `DISPUTED` state are omitted from the rendered set entirely, even though the tier would otherwise include them.

### 3.6. Consumer Disclosure and the Dispute Cycle

A worker is entitled to see the file the exchange has built about them. A disclosure request names the `covered_worker_id` whose file is wanted and opens a `ConsumerDisclosure` in `REQUESTED` with `file_contents` null, `included_record_count` and `held_record_count` at 0 and `requested_at` stamped from the logical clock. Generation materializes the file, but only while the worker's `disclosure_state` is `NEVER_DISCLOSED` or `STALE`; a regeneration attempt while the file is `CURRENT` is refused with `ERR_DISCLOSURE_ALREADY_CURRENT` (HTTP 409), because a current file is by definition one the worker has already been served. On success the disclosure moves to `GENERATED`, `file_contents` is populated, the worker's `disclosure_state` becomes `CURRENT`, and both the disclosure row and the worker row advance their versions.

Assembly is inclusive where a verifier's view is not. The file's included set is the worker's spans whose `record_state` is `PENDING_VERIFICATION`, `VERIFIED` or `DISPUTED`, whose `updated_at` falls within the 3650-day disclosure window ending at the current instant, and whose `currency_state` is not `FROZEN`. Every one of the worker's spans that fails any of those conditions is held instead — an immutable span is held unless its last update falls inside the window, and a frozen span is always held regardless of its age — and the file reports the two populations as `included_record_count` and `held_record_count`. Inside the file, records are ordered by `hire_date` descending and then by `created_at` ascending, and each carries a provenance block recording the employer's legal name, the employer's feed status and the employer's last feed received date. A spanning row that has been corrected surfaces only its corrected values; the values that preceded the correction are never written into the file.

Disputes are the worker's remedy when a span is wrong. Filing a dispute names the `employment_record_id` in question, the filing `covered_worker_id`, a `claimed_field` of `EMPLOYMENT_STATUS`, `HIRE_DATE`, `SEPARATION_DATE`, `PAY_RATE` or `TENURE`, the `claimed_correct_value` the worker asserts, and `expected_employment_record_version`. Filing is permitted only when the worker owns the span's `covered_worker_id`, the span's employer has `freeze_state` `NONE`, and the span's `currency_state` is not `FROZEN`; aim it at a frozen span and the freeze guard of §2.10 refuses it with `ERR_EMPLOYER_FROZEN` (HTTP 403). A successful filing moves the span to `DISPUTED`, increments the worker's `open_dispute_count` and the employer's `dispute_open_count`, and creates a `RecordDispute` that reaches `AWAITING_EMPLOYER` on the spot and stamps a `response_due_date` 45 days after the `filed_at` instant. That due date is frozen at filing and is not extended by anything except the employer's single permitted extension, recorded as `deadline_extended`.

The employer is then on a clock. It records notice of the dispute, which moves the dispute to `NOTICE_SENT` and stamps `notice_sent_at`. It may acknowledge the dispute while the response window is still open, moving the dispute to `EMPLOYER_RESPONDED`. Acknowledgement is not a resolution and buys no time: an acknowledged dispute whose `response_due_date` passes without resolution is swept into `ESCALATED`, and that escalation is not a private matter between the employer and one worker. Escalating a dispute drives the employer's `feed_status` to `DELAYED`, stales every one of the employer's records that was `CURRENT`, and recomputes the risk score of every requesting party holding a `RESPONDED` request against that employer — the employer's failure contaminates the verifiers. The cascade runs in ordered hops from the dispute, through the employer's feed status, to the records, and finally to the risk scores. A notice or a resolution that arrives strictly after `response_due_date` is refused with `ERR_DISPUTE_RESPONSE_WINDOW_EXPIRED` (HTTP 422), and a resolution landing exactly on the due date is accepted.

Resolving takes one of two forms, and both require that the acting employer owns the disputed record and that the response arrives no later than the due date. Upholding the recorded value moves the dispute to `RESOLVED_UPHELD`, stamps `resolved_at`, and returns the span to `VERIFIED` without changing any of its values. Correcting it moves the dispute to `RESOLVED_CORRECTED`, stamps `resolved_at`, and changes the span: the span's `record_state` becomes `CORRECTED` and its annualized income is recomputed. The field that changes is the one the worker named, overwritten from `claimed_correct_value` — with one asymmetry that matters: a claim against `TENURE` does not write a tenure figure at all, it updates `standard_hours_per_week` instead, because tenure is derived rather than stored. A non-resolving response that merely acknowledges the dispute moves it to its acknowledged state and is the only response form that leaves the span untouched. The employer's response supplies a `resolution` field, and its value selects which of the three response forms is taken; the same field is what the worker supplies when reopening a resolved dispute, where the only admissible value is the reopening one. A correction also increments the worker's `corrected_record_count`, and both resolution forms decrement the worker's `open_dispute_count` and the employer's `dispute_open_count`. A correction carries a further obligation: for every request against this employer that was previously declined with `RECORD_STALE_INSUFFICIENT_HISTORY`, a fresh `VerificationAttestation` is created in `PENDING` state, because the correction may have restored the history those requests lacked.

A corrected span does not stay corrected. The worker may reconfirm it, returning it to `VERIFIED` and decrementing `corrected_record_count`, provided the worker owns it, its employer's `freeze_state` is `NONE`, and it carries no dispute in `AWAITING_EMPLOYER`, `NOTICE_SENT`, `EMPLOYER_RESPONDED` or `ESCALATED`. An upheld dispute is likewise not final: within 14 days of `resolved_at` the worker may reopen it, which returns the dispute to `NOTICE_SENT` and increments both open-dispute counters again. After those 14 days elapse, a resolved dispute — corrected or upheld — is swept to `CLOSED`, which is terminal; reopening or responding to a closed dispute is refused with `ERR_DISPUTE_TERMINAL` (HTTP 409). The cycle therefore runs dispute, notice, response, resolution, and either a reopen back into the notice stage or a closure that ends it, with the 14-day grace period being the only thing standing between a resolution and finality.

### 3.7. Contributor Compensation, Pricing and Settlement

Contributors are paid for the records they actually deliver, at a rate that depends on how much they deliver. A `CompensationAccrual` names the `employer_id` that earned it, the `pay_period_end_date` it is keyed to, a `transaction_ref` that is unique for that employer, and the `records_count` it covers, which must be at least 1; it opens in `ACCRUED` with `adjusted_cents` and the settled figures at 0. The rate is selected by the tiered pricing rule, which reads the declared `record_count` of the batch that reached `VALIDATED` — batches that are `RECEIVED` or `REJECTED` never produce an accrual, so their counts are excluded. A batch declaring at least 10000 records earns 8 cents per record, one declaring fewer than 10000 but at least 1000 earns 10 cents, and one declaring fewer than 1000 earns 12 cents. The accrual's `unit_rate_cents` is that per-record rate and `gross_accrued_cents` is the declared `records_count` multiplied by it, computed exactly with no rounding step. The same rule also prices an accrual recorded directly against a contributor transaction, setting its unit rate and gross amount from its own `records_count` on the same thresholds.

One alternative pricing mode exists for settlement. When a settlement is posted with `apply_blended_rate` true, the whole count is priced at a single blended average rate instead of the marginal rate, where the blended rate is the sum of the tier amounts the count straddles divided by the sum of the tier counts, rounded half up. A 15000-record accrual therefore settles at 15000 records times 9 cents — 135000 cents — under the blended variant, against 132000 cents under the marginal base variant, the difference being that the marginal reading charges 10000 records at 8 cents, 4000 at 10 cents and 1000 at 12 cents while the blended reading averages the three bands across the whole figure.

Settlement draws down prepaid budgets against accrued obligations in a pinned order. Posting a settlement supplies the `employer_id`, a `settlement_period_end`, a `settlement_budget_cents` and a `waiver_budget_cents`. The eligible set is the employer's accruals still in `ACCRUED` whose `pay_period_end_date` is on or before the settlement period end; accruals already `WAIVED` or `PAID` are excluded, so re-posting cannot double-charge. Eligible accruals are walked in a pinned sequence — by `pay_period_end_date` ascending, then `created_at` ascending, then `transaction_ref` ascending — and each is offered to the buckets in the pinned order `BUCKET_BASE`, `BUCKET_ADJUSTMENT`, `BUCKET_WAIVER`. The paid budget fills `BUCKET_BASE` first; an accrual whose `gross_accrued_cents` is covered by what remains in the paid bucket moves to `PAID` with `paid_cents` set to its full gross amount and that amount subtracted from the remaining paid capacity. Only when the paid bucket cannot cover the accrual in full is the waiver bucket consulted: an accrual whose gross is covered by what remains in `BUCKET_WAIVER` moves to `WAIVED` with `waived_cents` set to its full gross amount and that amount subtracted from the remaining waiver capacity. An accrual that neither bucket can cover in full stays `ACCRUED` and the walk moves on to the next accrual in order. Every settlement is all-or-nothing per accrual: no accrual is ever partially settled, and a bucket's residual capacity is not carried forward beyond the settlement that spent it. An employer holding 7000 cents of paid budget against a single 9000-cent accrual therefore settles nothing at all, while the same accrual against a 9000-cent paid budget settles fully and leaves the budget at exactly 0.

The settlement reports its outcome as a `settlement_id`, an `accrual_count`, a `settled_gross_cents` equal to the gross accrued amounts of every accrual it moved to `PAID` or `WAIVED`, and a `settled_net_cents` equal to the gross amounts of the `PAID` accruals alone — the difference is what the waiver bucket absorbed. Wavier and payment both add to the employer's settled total: `compensation_earned_cents` is the sum of `waived_cents` over the employer's `WAIVED` accruals plus the sum of `paid_cents` over its `PAID` accruals. An accrual still `ACCRUED` contributes nothing to that total.

Voiding is the compensating act. A void must cover accruals and names a settlement; the `WAIVED` accruals it covers return to `ACCRUED` unconditionally, while a `PAID` accrual returns to `ACCRUED` only when the void lands within 30 days of that accrual's `updated_at`, so a stale payment is not reversible indefinitely. A void releases exactly the settled figures it had added — `waived_cents` or `paid_cents` is reset to 0 — and decrements the employer's `compensation_earned_cents` by the released amount, reporting a `settlement_id`, an `accrual_count` and a `reverted_cents`. A settlement that names an outcome other than `WAIVED` or `PAID`, or that covers no accrual in `ACCRUED` state, is refused with `ERR_SETTLEMENT_OUTCOME_INVALID` (HTTP 422).

### 3.8. Feed Currency, Score Escalation and Verifier Risk Contagion

An employer's feed status is derived, never set, and it is derived from a single comparison. The staleness measure is the whole number of days between the employer's most recent validated feed date and the current instant, counted by whole-day floor division of the elapsed seconds; when no batch has ever validated, the employer's own creation instant stands in for the missing feed date. The declared cadence sets the tolerance: 7 days for a weekly contributor, 14 for biweekly, 15 for semimonthly and 30 for monthly. Equality stays in the lower band, so an employer is `CURRENT` while its staleness is no greater than one cadence interval, `DELAYED` while staleness is greater than one interval and no greater than three intervals, and `STALLED` once staleness exceeds three intervals. An `ACTIVE` freeze suppresses the whole derivation: the employer keeps the last status it derived and its records stay frozen.

The currency score is a weighted composite of four signals. Coverage is the number of distinct validated pay periods in the window divided by the expected number of pay periods, with the denominator floored at 1 so an expected count of zero never divides by zero. Recency contributes in full when the employer's feed status is `CURRENT`, half when it is `DELAYED` and nothing when it is `STALLED`. Responsiveness contributes in full when the employer answered every one of its disputes within the response due date and a quarter otherwise. Decay subtracts for age: the whole number of days, by floor division, between the most recent validated feed date in the window and the current instant, again falling back to the employer's creation instant when there is no feed date. The raw score weights coverage at 250, recency at 200 and responsiveness at 150, and subtracts 3 for each day of decay; the score is that raw figure rounded half up once and clamped between 0 and 600.

Opening a currency review for a contributor takes an `employer_id`, a `review_period_end`, a `window_days` of at least 1, the `last_feed_date_in_window`, the `distinct_pay_periods_in_window` and the `expected_periods`, and it scores immediately rather than waiting: a review moves from `PENDING` to `SCORED` at once, provided the window covers at least one day and the expected period count is at least 1. Scoring computes `missing_periods` as the number of expected pay periods the window would have produced beyond the distinct validated periods actually present, never below zero, and computes the currency score; it then writes the employer's `review_state`, `review_period_end`, `missing_periods` and `currency_score`, re-derives the employer's feed status, and advances the employer's version. Review windows are subject to the 3-day separation guard of §2.11, which is the opposite adjacency rule from the authorization guard.

Escalation is permitted only when the score is at or above 300 — the comparison is inclusive, so a score of exactly 300 escalates. Escalating a scored review also requires that the review period end has already arrived, and it is a cascading act: the review moves to `ESCALATED`, the employer's feed status is driven to `STALLED`, every `CURRENT` record of that employer is staled, and every request of that employer sitting in `PERMITTED` or `VALIDATED` is returned to `SUBMITTED` with its resolved tier cleared. That last hop is caused by the records going stale, not by the review transition directly — the cascade runs review, then feed status, then records, then requests. Escalation also recomputes the risk score of every requesting party holding any request against that employer. Rescoring a review returns it to `SCORED` and recomputes the score, but only while the employer's feed status is `CURRENT` or `DELAYED`; a review closes as `CLEARED` when a rescore finds the employer's feed status back at `CURRENT` and its missing period count at 0.

Requesting parties absorb the consequences of the employers they query. A verifier's risk score is a running total over the escalation events attributed to it, processed in ascending `created_at` order — `created_at` ascending is also the tie-break, and a verifier's own `id` is never consulted for ordering. The three event kinds carry different base penalties: a dispute that reached `ESCALATED` carries 25, a feed stall that reached `ESCALATED` carries 40, and a response reversal carries 30. Each event in sequence is compounded by multiplying its base penalty by 1.5 raised to the event's zero-based position in that verifier's ordered list, rounded half up, so the first attributed event is charged exactly its base penalty and each later one is charged more; the compounded figure is added to the running total, which is clamped between 0 and 1000. The final running total is the verifier's `negative_escalation_count`, and its `posture` is `RESTRICTED` when that total is at or above 100 and `NORMAL` otherwise. Escalation events are charged to a verifier when a dispute against an employer it holds a `RESPONDED` request with escalates, when a currency review escalates for any employer it has a request against, and when one of its own responses is reversed. Because posture gates every data-consuming operation in §2.10, a verifier that accumulates enough attributed failures stops being able to verify at all until its score falls or an operator authorizes it afresh.

### 3.9. Compensating Invariants and Conserved Counters

Two quantities in the exchange are conserved, and the rules that maintain them are the place where forward actions are undone exactly. The first is the counted verification record. An employer's `counted_verification_records` is the sum of `records_matched_count` across its requests that are currently `RESPONDED`, restricted to requests whose `current_employer_id` is that employer. Requests in `SUBMITTED`, `PENDING_AUTH`, `PERMITTED`, `VALIDATED`, `DECLINED` or `REVERSED_RECONSENT_REQUIRED` contribute nothing, which is precisely what makes a reversal exactly compensating: a request that added its matched count when it reached `RESPONDED` releases exactly the same count when its reversal takes it out of `RESPONDED`, so an employer's counter returns to its pre-verification value with no drift. The counter is clamped at zero and never goes negative; an adjustment that would drive it — or the settled compensation total — below zero is refused with `ERR_COUNTER_FLOOR_VIOLATION` (HTTP 409), because a negative value can only mean the same release was applied twice.

The second conserved quantity is settled cents. An employer's `compensation_earned_cents` is the sum of the waived amounts on its `WAIVED` accruals plus the sum of the paid amounts on its `PAID` accruals, and voiding a settlement must leave the total exactly where it stood before the settlement posted. The invariant is an equality, not an approximation: the tolerance is pinned at zero, so there is no rounding drift to excuse. An employer whose settled total was 0 before a 26000-cent settlement therefore reads exactly 0 again after that settlement is voided, and a partial or over-eager release is as much a defect as an under-release.

Both invariants are maintained through the reversal and opt-out paths described in §3.2 and §3.5, which run the counter recomputation for every affected employer rather than adjusting a stored figure incrementally. Recomputing from the live `RESPONDED` population and from the live `WAIVED` and `PAID` population is what makes the compensating actions exact: the counter is not decremented from memory of what it once was, it is re-derived from the rows that currently justify it.
