# QDRO Processing API — Product Requirements Document

## 1. Introduction

A retirement plan administrator receives domestic relations orders that purport to divide a participant's account balance between the participant and a former spouse or dependent. Before any money moves, the administrator must decide whether the paper in front of it is a *qualified* domestic relations order: whether it adopts the plan's model language, whether the assignment formula is one the plan will honour, whether the marital period and the alternate payee are identified well enough to act on, and whether the order asks for anything the plan simply cannot provide. That determination is a fiduciary act with a statutory clock attached — funds must be segregated the moment a draft is received, the review must complete inside the plan's stated review period, and the segregation cannot outlive its eighteen-month window.

This document specifies the API that carries a QDRO from intake through to the alternate payee's last distribution and its 1099-R reporting line. The system is deliberately built as a compliance-audit ledger rather than a workflow queue: every determination is guarded by an ordered set of checks whose *first* violation decides the response, every money figure is derived from the underlying money sources rather than stored as a loose total, and every reversal is recorded as a compensating entry rather than an edit. Two structurally different products live inside the same case model — a **separate interest** award, which carves principal out of the participant's account into a standing payee account, and a **shared payment** award, which leaves principal alone and hands the payee a slice of each periodic benefit payment. Identical case data yields two entirely different money shapes depending on which of these approaches the order proposes, and the plan's own procedures decide which are even permissible.

Time in this system is explicit, not ambient. Every deadline, expiry, tax-year boundary and age comparison reads a server-side **logical clock** that an operator sets directly; nothing in this API consults wall-clock time. Readers implementing this specification should treat the logical clock as the single temporal authority and the plan's three window lengths — review, resubmission and segregation — as the only sources of deadline arithmetic.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API carries two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the capacity in which the caller acts. If either header is absent, or if `X-User-Role` is not exactly one of the five declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well formed but the presented role is not among the roles authorised for the endpoint being called (see the Authorized Role(s) column in §4), the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The five roles are `PlanAdministrator`, `QdroAnalyst`, `Participant`, `AlternatePayee`, and `Attorney`.

A `PlanAdministrator` is the plan's fiduciary operator. It registers plans and moves their procedures through publication, enrols participants, opens plan accounts, records money sources and valuations, makes the qualification and denial determinations, releases holds, voids distributions, revokes attorney authorizations, drives the logical clock, and runs the segregation sweep. It deliberately cannot issue deficiency notices and cannot send manual correspondence. When `X-User-Role` is `PlanAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any entity's `id`.

A `QdroAnalyst` is the reviewer. It reads draft orders against the plan's written procedures, issues rejection notices enumerating specific deficiencies, and sends manual correspondence to participants, payees and counsel. It cannot qualify or deny an order — the determination belongs to the administrator. When `X-User-Role` is `QdroAnalyst`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The server does record it: when an analyst issues a rejection notice, that analyst's `X-User-ID` is written to the draft order's `reviewed_by_user_id`. That recorded value is compared only against a later qualifier's `X-User-ID`, never against any entity's `id`.

When `X-User-Role` is `Participant`, `X-User-ID` is the `id` of the acting `Participant`; ownership checks on any resource that references a `Participant` compare the resource's participant reference to `X-User-ID`. Concretely, a participant reaching a case compares against that case's `participant_id`; a participant reaching a draft order resolves the draft order's case first and then compares that case's `participant_id`; a participant reaching a plan account compares against the account's `participant_id`.

When `X-User-Role` is `AlternatePayee`, `X-User-ID` is the `id` of the acting `AlternatePayeeAccount`. The role therefore only exists once an order has been qualified and a payee account has been established. A payee reaching a payee account compares `X-User-ID` to the account `id` named in the path; a payee reaching a distribution resolves that distribution's `alternate_payee_account_id` and compares it to `X-User-ID`.

When `X-User-Role` is `Attorney`, `X-User-ID` is the `id` of the acting `AttorneyAuthorization`. That single value pins both the case the attorney may touch and the side represented: an attorney reaching any resource resolves the case behind it and requires that the authorization identified by `X-User-ID` carry that same `qdro_case_id`.

Whenever an entity-backed role — `Participant`, `AlternatePayee`, or `Attorney` — presents an `X-User-ID` that does not match the resource it is acting on, the request is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). An acting `Attorney` faces one further gate: the authorization whose `id` is the presented `X-User-ID` must be in `ACTIVE` status, and the logical clock must fall inside the authorization's operative window — on or after `effective_from` (interpreted as that calendar date at midnight UTC) and at or before `expires_at`. When a draft order is submitted by an acting `Attorney` and the body carries an `attorney_authorization_id`, that value must equal the acting attorney's `X-User-ID`. Any of these failures is rejected with `ERR_ATTORNEY_NOT_AUTHORIZED` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a list endpoint's description in §4 names a different ordering, results are sorted by `created_at` ascending. Several collections in this domain are ordered by a domain-meaningful instant instead, with `created_at` ascending as the tie-breaker; those orderings are stated where the collection is discussed and again in §4.

For every list response, the `meta` object carries the four pagination fields `limit`, `offset`, `total_count`, and `has_more`. `total_count` is the number of rows matching the request's filters before the page window is applied, and `has_more` is true exactly when rows remain beyond the current window. Single-resource responses omit all four.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every persisted resource carries a server-minted `id` — a UUID string with no type prefix — and a `created_at` timestamp in ISO 8601 UTC form with three fractional digits. Clients never supply either.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation of that row, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation. `Plan`, `Participant`, `PlanAccount`, `MoneySource`, `QdroCase`, `DraftOrder`, `DeficiencyNotice`, `SegregationHold`, `AttorneyAuthorization`, `AlternatePayeeAccount`, and `Distribution` all carry both fields. Three resources are append-only records of something that happened and therefore carry only `id` and `created_at` — for `ValuationSnapshot`, `TaxReport`, and `Communication`, both `updated_at` and `version` are absent from the resource entirely. Nothing in this API ever updates or deletes a row of those three types.

The logical clock is the system's only clock. It is set by an administrator to an arbitrary UTC instant supplied as `current_utc`, and the response reports both the newly applied `current_utc` and the `previous_utc` it replaced. Setting the clock mutates no entity; the next time-gated operation or sweep simply observes the new instant. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real wall-clock time. Every deadline, expiry, tax-year determination and age comparison described in this document reads this clock.

The domain instants a resource takes from this clock — namely a draft order's `received_at` and `review_deadline_at`, a segregation hold's `placed_at` and `expires_at`, a deficiency notice's `issued_at` and `resubmission_deadline_at`, an attorney authorization's `revoked_at`, an alternate payee account's `established_at`, a distribution's `issued_at` and `voided_at`, a communication's `sent_at`, and a tax report line's `written_at` — are rendered at the clock instant's own precision: with no fractional part at all when the clock's microsecond component is zero, and with three fractional digits otherwise. Whole-day arithmetic carries that precision along with the time of day, so a deadline computed from the clock renders the same way the clock does. Only `created_at`, `updated_at` and `api_request_timestamp` always carry three fractional digits. The clock-setting response echoes the supplied `current_utc` verbatim and reports as `previous_utc` the string the clock previously read.

### 2.5. Money, Basis Points and Rounding Discipline

All monetary amounts in this API are integer cents. All proportional quantities — assigned shares, plan ceilings, earnings growth, withholding rates — are integer **basis points**, where 10000 basis points is 100 percent. There are no decimal fractions anywhere in the contract: the two-decimal precision of a dollar figure is expressed by the cent being the unit, and the four-decimal precision of a percentage is expressed by the basis point being the unit.

Rounding is never left to the implementer's discretion, and the two rounding modes in use are not interchangeable. Where this document says an amount is **rounded down**, the mathematical quotient is truncated toward zero to a whole number of cents or basis points. Where it says an amount is **rounded half up**, the quotient is rounded to the nearest whole unit, with an exact half rounding away from zero. Aggregations of already-integer values — the derived balances on a plan account, the net position of a tax-report ledger — involve no rounding at all and are exact integer sums.

Three places in this specification pin the *order* of rounding rather than only its mode, because rounding an aggregate is not the same as summing rounded parts. The earnings adjustment rounds each money source's share and only then sums; the per-source allocation rounds every source except the last and lets the last absorb the remainder; and the distribution settlement rounds withholding before the administrative fee tier is selected. Each is stated in full where its workflow is described, and an implementation that reorders the steps produces figures that differ by whole cents from the contract.

### 2.6. Path Resolution and Nested Resource Retrieval

Every path parameter in this API is named `{id}`, and each one resolves against the entity that owns the collection segment immediately preceding it: an `{id}` under `/plans` is a `Plan`, under `/participants` a `Participant`, under `/plan-accounts` a `PlanAccount`, under `/qdro-cases` a `QdroCase`, under `/draft-orders` a `DraftOrder`, under `/segregation-holds` a `SegregationHold`, under `/alternate-payee-accounts` an `AlternatePayeeAccount`, under `/distributions` a `Distribution`, under `/attorney-authorizations` an `AttorneyAuthorization`, and under `/tax-reports` a `TaxReport`.

Path parameters are validated left to right, and existence is checked before any field of the request body is inspected. A path `{id}` that does not resolve yields the not-found error belonging to that entity type: `ERR_PLAN_NOT_FOUND`, `ERR_PARTICIPANT_NOT_FOUND`, `ERR_PLAN_ACCOUNT_NOT_FOUND`, `ERR_QDRO_CASE_NOT_FOUND`, `ERR_DRAFT_ORDER_NOT_FOUND`, `ERR_SEGREGATION_HOLD_NOT_FOUND`, `ERR_AP_ACCOUNT_NOT_FOUND`, `ERR_DISTRIBUTION_NOT_FOUND`, `ERR_AUTHORIZATION_NOT_FOUND`, or `ERR_TAX_REPORT_NOT_FOUND`, each with HTTP 404.

Foreign keys supplied inside a request body are resolved with the same errors and the same status. A `plan_id` that does not resolve when enrolling a participant yields `ERR_PLAN_NOT_FOUND`; a `participant_id` that does not resolve when opening a case yields `ERR_PARTICIPANT_NOT_FOUND`; a `qdro_case_id` that does not resolve when a draft order is received yields `ERR_QDRO_CASE_NOT_FOUND`; and an `attorney_authorization_id` that does not resolve on that same submission yields `ERR_AUTHORIZATION_NOT_FOUND`. One further case is worth naming: several operations reach the *operative* plan account for a case by resolving the case's `participant_id` and then the single plan account whose `participant_id` matches it. When no such account has been opened, `ERR_PLAN_ACCOUNT_NOT_FOUND` is the answer.

### 2.7. Optimistic Concurrency on Case and Payee-Account Writes

Two write operations in this API are legitimately repeatable against the same parent, which means their guard cannot be a state precondition — it has to be a version check. Both use optimistic concurrency against the parent resource's `version`.

A `POST /draft-orders` request must carry `expected_case_version`, a non-optional integer field holding the `QdroCase.version` the client last observed. Receiving a second draft order on a case is legitimate product behaviour — the later draft supersedes the earlier one and rewrites the case's operative terms and hold amount — so the server cannot distinguish an intentional supersede from an accidental one on state alone. If `expected_case_version` does not equal the target case's current `version`, the receipt is rejected with `ERR_STALE_CASE_VERSION` (HTTP 412), preventing the client from overwriting terms it has not observed.

A `POST /alternate-payee-accounts/{id}/distributions` request must carry `expected_ap_account_version`, a non-optional integer field holding the `AlternatePayeeAccount.version` the client last observed. Partial distributions are legitimate and repeatable, so a further sequential request against an `ESTABLISHED` account with sufficient balance would itself succeed; only the stale version the client carries distinguishes it. If `expected_ap_account_version` does not equal the target payee account's current `version`, the distribution is rejected with `ERR_STALE_AP_ACCOUNT_VERSION` (HTTP 412).

No other endpoint in this API accepts a version field. Both version checks are evaluated *after* the target resource's own state check, so a stale version presented against a `CLOSED` payee account reports the closure rather than the staleness.

### 2.8. Validation Precedence

Requests are evaluated against an ordered ladder of checks. The **first** violated rung decides the response, and no later rung can override it. This ordering is part of the contract: two independently invalid requests that differ only in which rung they trip must produce different error identifiers, and a request that is invalid on several rungs at once must report the earliest one. The ladder, from first evaluated to last:

1. **Authentication.** Both headers present and `X-User-Role` one of the five declared roles — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorisation.** The presented role appears among the called endpoint's authorised roles — otherwise `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint.
3. **Request shape.** Every non-optional input field is present; every enum-typed field carries a declared literal; every integer field whose name ends in `_cents`, `_bps`, or `_days` is zero or greater; calendar dates are ISO 8601 calendar dates and datetimes are ISO 8601 UTC instants; when both are supplied, `marital_period_start` is strictly earlier than `marital_period_end`; and `assigned_percentage_bps` and its proposed counterpart do not exceed 10000. Any violation is `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
4. **Path existence.** Each `{id}` resolves per §2.6 — otherwise the matching not-found error (404). Applies to every endpoint that has a path parameter.
5. **Body foreign-key existence.** `plan_id`, `participant_id`, `qdro_case_id`, and `attorney_authorization_id` resolve where supplied — otherwise the matching not-found error (404). Applies to participant enrolment, case opening, and draft-order receipt.
6. **Resource ownership.** An entity-backed role's `X-User-ID` matches the resource reached — otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to every endpoint whose authorised roles include `Participant`, `AlternatePayee`, or `Attorney`.
7. **Attorney standing.** An acting attorney's authorization is `ACTIVE` and inside its window, and a supplied `attorney_authorization_id` matches the acting attorney — otherwise `ERR_ATTORNEY_NOT_AUTHORIZED` (403). Applies to every endpoint whose authorised roles include `Attorney`.
8. **Segregation of duties.** On a qualification determination, `X-User-ID` differs from the draft order's `reviewed_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to the qualification determination only.
9. **Target state.** The target resource's own state admits the operation, at HTTP 409: issuing a rejection notice and qualifying both require the draft order to be `UNDER_REVIEW` (`ERR_DRAFT_ORDER_NOT_UNDER_REVIEW`); resubmitting requires it to be `DEFICIENT` (`ERR_DRAFT_ORDER_NOT_DEFICIENT`); denying requires it to be either `UNDER_REVIEW` or `DEFICIENT`; releasing requires the hold to be `HELD` (`ERR_HOLD_NOT_HELD`); issuing a distribution requires the payee account to be `ESTABLISHED` (`ERR_AP_ACCOUNT_CLOSED`); voiding requires the distribution to be `ISSUED` (`ERR_DISTRIBUTION_ALREADY_VOIDED`) and its payee account to be `ESTABLISHED` (`ERR_AP_ACCOUNT_CLOSED`); revoking requires the authorization to be `ACTIVE` (`ERR_AUTHORIZATION_NOT_ACTIVE`); and a procedures-status change requires the requested pair of current and target statuses to be a declared plan transition (`ERR_PROCEDURE_STATUS_TRANSITION_INVALID`). Applies to the nine state-driving operations: the plan procedures-status change, rejection-notice issuance, resubmission, qualification, denial, hold release, distribution issuance, distribution void, and authorization revocation.
10. **Optimistic concurrency.** `expected_case_version` matches on draft-order receipt (`ERR_STALE_CASE_VERSION`) and `expected_ap_account_version` matches on distribution issuance (`ERR_STALE_AP_ACCOUNT_VERSION`), both HTTP 412. Applies to those two endpoints.
11. **Disclosure scope.** A manual communication's `disclosure_level` does not exceed the addressee's entitlement — otherwise `ERR_DISCLOSURE_SCOPE_EXCEEDED` (403). Applies to manual case correspondence only.
12. **Procedures in force.** The plan's `procedures_status` is `PUBLISHED` — otherwise `ERR_PLAN_PROCEDURES_NOT_PUBLISHED` (409). Applies to the qualification determination only.
13. **Windows still open,** all HTTP 409: resubmission requires the logical clock at or before the resubmission deadline of the highest-`notice_sequence` rejection notice (`ERR_RESUBMISSION_WINDOW_CLOSED`); resubmission and qualification both require the case's segregation hold to be `HELD` with the logical clock at or before its `expires_at` (`ERR_SEGREGATION_WINDOW_EXPIRED`); a void requires the logical clock's calendar year to equal the distribution's `tax_year` (`ERR_VOID_ACROSS_TAX_YEARS`). Applies to resubmission, qualification, and distribution void.
14. **Revision cap.** On resubmission, the draft order's `revision_number` is strictly less than the plan's `max_revisions` — otherwise `ERR_MAX_REVISIONS_EXCEEDED` (409). This rung sits deliberately *after* the window rung, so a resubmission that is both late and over the cap reports the closed window, not the cap. Applies to resubmission only.
15. **Marital-period exclusivity.** A new case's marital period does not overlap another live case's on the same participant — otherwise `ERR_MARITAL_PERIOD_OVERLAP` (409). Applies to case opening only.
16. **Cross-entity readiness.** The facts the operation asserts about neighbouring rows hold. Qualification requires an empty deficiency set (`ERR_QUALIFICATION_DEFICIENCIES_PRESENT`, 409), a valuation snapshot on the operative account matching the case's `valuation_date` (`ERR_VALUATION_SNAPSHOT_MISSING`, 422), and an approach consistent with the participant's payment posture (`ERR_APPROACH_NOT_PERMITTED`, 422). Rejection-notice issuance requires a non-empty deficiency set (`ERR_NO_DEFICIENCIES_TO_REPORT`, 409). Denial requires the supplied `denial_reason` to match the observable facts (`ERR_DENIAL_NOT_PERMITTED`, 409). Hold release requires the hold's case to have reached `DENIED` review status (`ERR_CASE_NOT_DENIED`, 409). Resubmission, rejection-notice issuance, hold release, and manual correspondence all require the case to have the draft order the operation presupposes (`ERR_NO_ACTIVE_DRAFT_ORDER`, 409). Correspondence addressed to counsel requires a matching `ACTIVE` authorization on the case (`ERR_ATTORNEY_NOT_AUTHORIZED`, 403). Applies to six endpoints: qualification, rejection-notice issuance, denial, resubmission, hold release, and manual case correspondence.
17. **Uniqueness and conditional shape,** at HTTP 409 or 422: a participant may hold at most one plan account (`ERR_PLAN_ACCOUNT_ALREADY_EXISTS`, 409); a money source's `source_code` is unique within its account (`ERR_MONEY_SOURCE_DUPLICATE`, 409); a valuation snapshot's `as_of_date` is unique within its account (`ERR_SNAPSHOT_DUPLICATE`, 409); a `DIRECT_ROLLOVER` election requires `rollover_institution` (`ERR_ROLLOVER_INSTITUTION_REQUIRED`, 422); a distribution from a `SHARED_PAYMENT` payee account requires `gross_amount_cents` to equal `per_period_amount_cents` exactly (`ERR_SHARED_PAYMENT_AMOUNT_MISMATCH`, 422); and on draft-order receipt and resubmission the computed gross assigned amount must be greater than zero (`ERR_ASSIGNED_AMOUNT_ZERO`, 422). Applies to six endpoints: plan-account opening, money-source creation, valuation-snapshot creation, draft-order receipt, resubmission, and distribution issuance.
18. **Money capacity, checked last,** both HTTP 409: on draft-order receipt and on resubmission the aggregate segregation exposure on the plan account must fit inside the vested balance (`ERR_HOLD_CAPACITY_EXCEEDED`); on distribution issuance the requested gross must fit inside the funding pool (`ERR_INSUFFICIENT_DISTRIBUTABLE_BALANCE`). Applies to draft-order receipt, resubmission, and distribution issuance.

### 2.9. Derived Balances and Ledger Reconciliation

A plan account never stores a loose total. Five of its figures are derived, and all five are recomputed together — on account creation, on every money-source creation, on every change to the status of a segregation hold touching the account, and on every qualification, hold release, distribution or void that moves a money source:

- `vested_balance_cents` is the sum of `balance_cents` over every money source belonging to the account, with no filter of any kind.
- `assignable_base_cents` is the sum of `balance_cents` over only those money sources of the account whose `is_assignable` is true.
- `after_tax_basis_cents` is the sum of `basis_cents` over only those money sources of the account whose `is_assignable` is true.
- `held_amount_cents` is the sum of `hold_amount_cents` over the segregation holds on the account whose `status` is `HELD`; holds in `CONVERTED`, `RELEASED`, or `EXPIRED` contribute zero.
- `available_balance_cents` is `vested_balance_cents` reduced by `held_amount_cents`.

All five are exact integer sums with no rounding. Money sources have no lifecycle of their own, so no status filter applies to them; segregation holds do, which is why only `HELD` holds depress the available balance. On a freshly opened account with no money sources and no holds, all five figures are zero. The available balance can only go negative if a hold outlives a debit of the underlying sources, a situation the capacity rung of §2.8 exists to prevent.

The **assignable base** deserves separate emphasis because three different calculations read it: the sizing of an assignment, the per-source allocation that debits the account, and the aggregate-exposure capacity check. A loan receivable is seeded as non-assignable, so whenever a loan exists on an account the assignable base is strictly smaller than the vested balance, and an order can never reach the loan bucket.

An alternate payee account's totals are reconciled the same way. `total_distributed_gross_cents` is the sum of `gross_amount_cents` over that account's distributions whose `status` is `ISSUED`; a `VOIDED` row contributes zero, which is exactly what makes a void a true compensation rather than a fresh debit. For a `SEPARATE_INTEREST` payee account, `balance_cents` is the balance established at qualification reduced by the sum of `gross_amount_cents` over the `ISSUED` distributions, and `after_tax_basis_cents` is the basis established at qualification reduced by the sum of `basis_recovery_cents` over the `ISSUED` distributions. Both are recomputed from the `ISSUED` set rather than adjusted incrementally, so repeated issue-and-void cycles cannot drift. Both figures are recomputed on every distribution issuance and on every void.

### 2.10. Cascades, Versions and the Two State Dimensions of a Case

Several operations in this system mutate more than one row. Whenever they do, every touched row's `updated_at` is refreshed and — for the eleven resource types that carry it — its `version` increments by one. The cascade descriptions in §3 name the version increments that matter to clients explicitly, because those increments are what a subsequent optimistic-concurrency check will compare against. In particular, almost every write on the review track increments the owning case's `version`, which means a client holding a case version from before a rejection notice, a resubmission, a denial, a hold release, or a sweep-driven lapse is stale for the purpose of receiving a new draft order.

A QDRO case carries **two independent state dimensions on the same row**. `review_status` is the review track, moving through `INTAKE`, `UNDER_REVIEW`, `DEFICIENT`, and terminating in either `QUALIFIED` or `DENIED`. `segregation_status` is the custody track, moving from `NONE` through `HELD` and terminating in `CONVERTED`, `RELEASED_TO_PARTICIPANT`, or `LAPSED`. Neither dimension gates the other's progress except where this document says so: a case may sit at `review_status` `DEFICIENT` with `segregation_status` `HELD`, or at `review_status` `UNDER_REVIEW` with `segregation_status` `LAPSED`. Both dimensions start at their initial values when the case is opened and are only ever advanced by the server.

Reverse-reachability list endpoints are the *only* discovery channel for rows this system creates by cascade rather than by client request. A segregation hold, an alternate payee account, a corrective tax-report line, and a cascade-appended communication are never returned by the operation that created them; a client finds them by listing the collection that owns them. §4 marks each such list.

### 2.11. Disclosure Discipline and Attorney Interaction

Correspondence carries a `disclosure_level` of either `LIMITED` or `FULL`, and `FULL` outranks `LIMITED`. What a given addressee is entitled to receive depends on who they are.

For correspondence addressed to counsel — `recipient_type` of `PARTICIPANT_ATTORNEY` or `AP_ATTORNEY` — the server resolves the authorization on the case whose `represents` matches the addressed side: `PARTICIPANT_ATTORNEY` resolves the authorization representing `PARTICIPANT`, and `AP_ATTORNEY` resolves the one representing `ALTERNATE_PAYEE`. That resolution happens **regardless of the authorization's status**, and if the request asks for `disclosure_level` `FULL` while the resolved authorization's `disclosure_scope` is `LIMITED`, the request is rejected with `ERR_DISCLOSURE_SCOPE_EXCEEDED` (HTTP 403). Because the disclosure rung precedes the cross-entity readiness rung, an over-scoped request addressed to a *revoked* attorney reports the scope violation rather than `ERR_ATTORNEY_NOT_AUTHORIZED`; the authorization must be `ACTIVE` only once the scope itself is acceptable.

For correspondence addressed to the payee — `recipient_type` of `ALTERNATE_PAYEE` — `disclosure_level` `FULL` is rejected with `ERR_DISCLOSURE_SCOPE_EXCEEDED` unless the case has reached `review_status` `QUALIFIED`. Before qualification the payee is entitled only to `LIMITED` detail. Correspondence addressed to `PARTICIPANT` carries no disclosure ceiling.

An attorney's reach over the case is bounded in three ways at once: by the case named in the authorization, by the `disclosure_scope` recorded on it, and by time. The authorization is operative from `effective_from` until `expires_at`, and revocation ends it immediately — after revocation no correspondence may cite the authorization and an attorney acting under it is rejected with `ERR_ATTORNEY_NOT_AUTHORIZED`.

### 2.12. Segregation of Duties

The reviewer and the determiner must be different people. When an analyst issues a rejection notice on a draft order, that analyst's `X-User-ID` is written to the draft order's `reviewed_by_user_id`. When a qualification determination is later attempted on that same draft order, the acting administrator's `X-User-ID` must differ from the recorded `reviewed_by_user_id`; if they are equal the determination is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

This memory is deliberately durable. A resubmission returns the draft order to review but does **not** clear `reviewed_by_user_id`, so the bar survives the entire revision cycle: an analyst who rejected revision 1 can never qualify revision 3 of the same draft order. The field is null until the first rejection notice is issued, which is why a faultless draft order that was never rejected can be qualified by anyone holding the administrator role.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Plan and Its Written QDRO Procedures

A `PlanAdministrator` registers a retirement plan together with the written procedures that will govern every order received against it. Registration captures the sponsor-facing `plan_name` (one to 120 characters, not blank), the `plan_type` — only `DEFINED_CONTRIBUTION` account-balance designs are in scope for this administrator — and the `model_language_version` tag of the model QDRO language packet the plan publishes to counsel (one to 32 characters). Two array fields state what the plan will accept: `acceptable_formula_codes`, a non-empty duplicate-free list drawn from `PERCENTAGE_OF_ACCOUNT`, `FLAT_DOLLAR`, and `COVERTURE_FRACTION`, and `allowed_approaches`, a non-empty duplicate-free list drawn from `SEPARATE_INTEREST` and `SHARED_PAYMENT`. The plan also elects an `earnings_adjustment_method` of either `PERIOD_END` or `PRO_RATA_DAILY`, which decides how growth between the valuation date and the segregation date is credited; there is no default, so the election is mandatory at registration.

Four optional switches carry defaults that most plans keep. `requires_model_language` defaults to true, meaning a draft that does not adopt the model packet verbatim is deficient. `permits_benefit_not_otherwise_available` defaults to false and is statutorily always false; it exists as configuration purely so the prohibited-provision check has an explicit gate to read. `max_assignable_pct_bps` defaults to 5000 basis points — half the assignable base — and may be set anywhere from 1 to 10000. `max_assignable_amount_cents` defaults to 100000000 cents, one million dollars, and must be at least 1.

Three window lengths, each expressed in whole days, define the plan's clocks. `review_period_days` is the time from receipt of a draft to the administrator's review deadline and defaults to 45 days, within an accepted range of 1 to 365. `resubmission_window_days` is the time from issuance of a rejection notice within which a corrected draft may be resubmitted, defaulting to 60 days inside the same 1-to-365 range. `segregation_period_days` is how long a segregation hold survives from placement; its default of 548 days is the eighteen-month statutory window, and it may be set anywhere from 1 to 1095 days. A fourth cap, `max_revisions`, bounds how many revisions of a draft order the plan will look at before a final denial; it defaults to 3 and accepts 1 through 10.

Every plan is registered with `procedures_status` set to `DRAFT` and `participant_count` initialised to 0. That count is not a stored tally the client maintains — it is the number of participant rows whose `plan_id` names this plan, with no status filter of any kind, so terminated and retired participants count exactly as active ones do.

Procedures move through their own small lifecycle, driven by a `to_status` supplied by the administrator. From `DRAFT` the procedures may be published, advancing `procedures_status` to `PUBLISHED`; publication additionally requires that both `acceptable_formula_codes` and `allowed_approaches` are non-empty, because published procedures with nothing declared as acceptable would qualify nothing. A published plan may pull its procedures back for amendment, moving `PUBLISHED` to `AMENDMENT_PENDING`, and may re-publish them, moving `AMENDMENT_PENDING` back to `PUBLISHED`. That pair is a genuine cycle a plan may traverse repeatedly. Each of the three transitions increments the plan's `version` by one. No other movement exists: `DRAFT` to `AMENDMENT_PENDING` is not a declared transition, and neither is any movement *into* `DRAFT`; both are rejected with `ERR_PROCEDURE_STATUS_TRANSITION_INVALID`.

While procedures sit in `AMENDMENT_PENDING`, in-flight orders are untouched — drafts continue to be received, reviewed, rejected and denied exactly as before — but no qualification determination may be signed, because determinations require procedures actually in force. The same is true of a plan still in `DRAFT`. A determination attempted in either situation is refused with `ERR_PLAN_PROCEDURES_NOT_PUBLISHED`, even when the draft order itself is entirely faultless.

### 3.2. The Participant's Account Picture

Enrolment records the participant's `full_name` (one to 120 characters, not blank), the `ssn_last4` used to match incoming orders (exactly four ASCII digits), the `date_of_birth` and the `participation_start_date`, both ISO 8601 calendar dates. The participation start date is the denominator of every coverture fraction the plan will ever compute for this person, and it may not be later than the logical clock's calendar date at the time of enrolment. `employment_status` is one of `ACTIVE`, `TERMINATED`, or `RETIRED` and defaults to `ACTIVE`. `benefit_commenced` defaults to false and is the single most consequential flag on the row: it decides which division approach is even possible later, because a participant not yet in pay status can only be divided by separate interest, while a participant already in pay status can only be divided by shared payment. Enrolling a participant recomputes the plan's `participant_count` and increments the plan's `version` by one. Participants are listed under their plan, optionally narrowed by `employment_status`.

Each participant may hold at most one plan account. Opening it accepts an optional `monthly_payment_cents`, the current periodic benefit payment in cents, which defaults to 0 and must not be negative; the figure is only meaningful once `benefit_commenced` is true and it is the base from which a shared-payment slice is computed. A freshly opened account has all five of its derived balances at 0. Attempting to open a second account for the same participant is refused with `ERR_PLAN_ACCOUNT_ALREADY_EXISTS`. The account is discoverable both directly and through the list of the participant's accounts, which returns an array of length 0 or 1.

The account's substance lives in its **money sources** — the contribution buckets that together make up the balance. Each source records the `plan_account_id` it belongs to, a `source_code` drawn from `AFTER_TAX`, `EMPLOYER_MATCH`, `LOAN_RECEIVABLE`, `PRE_TAX_DEFERRAL`, and `ROTH`, a `balance_cents` that must not be negative, an optional `basis_cents` recording the after-tax non-taxable basis inside the bucket (defaulting to 0, never negative, and never greater than that bucket's own `balance_cents`), and an optional `is_assignable` flag defaulting to true. A bucket a domestic relations order may not reach — the loan receivable being the standing example — is created with `is_assignable` false, which keeps it inside the vested balance while excluding it from the assignable base. A `source_code` may appear at most once per account; a repeat is refused with `ERR_MONEY_SOURCE_DUPLICATE`. Adding a source recomputes all five derived balances on the parent account and increments that account's `version` by one. The account's sources are listed in `source_code` ASCII-ascending order, which is deliberately the same order the allocation waterfall uses.

Valuations are recorded separately and are immutable. A snapshot names the `plan_account_id`, an `as_of_date` calendar date, the total `balance_cents` recorded at that date (never negative), and a `source` of `TRUSTEE_STATEMENT`, `RECORDKEEPER_FEED`, or `MANUAL_ADJUSTMENT`. An account may hold at most one snapshot per `as_of_date`; a repeat is refused with `ERR_SNAPSHOT_DUPLICATE`. Recording a snapshot changes no derived field anywhere — a snapshot is valuation history, not a balance mutation. Snapshots are listed in `as_of_date` ascending order with `created_at` ascending as the tie-breaker, and the list may be narrowed to a single `as_of_date`. Two snapshots matter later: the one whose `as_of_date` exactly equals a case's valuation date is the earnings baseline, and the earliest snapshot on or after the segregation date is the earnings endpoint.

### 3.3. Opening a Case, Authorizing Counsel, and Case Correspondence

A case is opened by a `PlanAdministrator` or a `QdroAnalyst` against a `participant_id`, and it fixes three things that the order itself cannot later move: the alternate payee's identity, the marital accrual window, and the valuation date. `alternate_payee_name` is the payee's legal name as stated in the order (one to 120 characters, not blank). `alternate_payee_dob` is the payee's date of birth; it is optional at intake but drives the 1099-R distribution code much later, and leaving it absent has consequences at review time. `alternate_payee_address_on_file` defaults to false, and a false value likewise surfaces as a deficiency when the draft is examined. `marital_period_start` is the inclusive first day of the marital accrual window; `marital_period_end` is optional, defaults to null, and when supplied must be strictly later than the start. `valuation_date` is the order's valuation date, and a valuation snapshot bearing exactly that `as_of_date` must exist on the operative plan account before any determination can be signed.

The marital window is treated as **half-open**: the start day is inside the window and the end day is outside it. Two cases on the same participant may not carry overlapping windows unless the earlier one has been denied — formally, a new case's window must not overlap the half-open window of any other case on the same participant whose `review_status` is anything other than `DENIED`. Sharing only an endpoint is not an overlap, so a case whose window ends 2027-01-01 and a case whose window starts 2027-01-01 coexist happily. A null `marital_period_end` is treated as unbounded forward and therefore overlaps every window that starts later. A violation is refused with `ERR_MARITAL_PERIOD_OVERLAP`.

A newly opened case starts at `review_status` `INTAKE` and `segregation_status` `NONE`, and all five of its operative order terms — `approach`, `formula_code`, `assigned_percentage_bps`, `assigned_flat_amount_cents`, and `shared_payment_end_date` — are null, because nothing has been proposed yet. Those five are system-maintained: they are copied from the most recent non-`SUPERSEDED` draft order on the case and are never supplied by a client. Cases may be listed under their participant and narrowed by `review_status`, by `segregation_status`, or by both.

Counsel for either side is recorded as an authorization on the case. The record names which party the attorney acts for through `represents`, either `PARTICIPANT` or `ALTERNATE_PAYEE`, together with `attorney_name` (one to 120 characters, not blank), `attorney_bar_number` (one to 32 characters, not blank), and `attorney_email`, an address of one to 200 characters that must contain an at-sign and to which authorized correspondence is directed. `disclosure_scope` is either `LIMITED` or `FULL` and caps what may ever be sent to that attorney. The operative window runs from `effective_from`, a calendar date, until `expires_at`, an ISO 8601 UTC instant that must be strictly after midnight UTC on `effective_from`. Authorizations are created with `status` `ACTIVE` and `revoked_at` null, and recording one increments the case's `version` by one. The `id` of the resulting authorization is precisely the `X-User-ID` an acting `Attorney` presents on every later request. The case's authorizations may be listed and narrowed by `represents`, by `status`, or by both.

Revocation is an administrator act and moves the authorization from `ACTIVE` to `REVOKED`, stamping `revoked_at` with the logical clock and incrementing the authorization's own `version` by one. A revocation attempted on an authorization that is already `REVOKED` is refused with `ERR_AUTHORIZATION_NOT_ACTIVE`. After revocation the attorney can neither act on the case nor be addressed by correspondence.

Correspondence is an append-only journal on the case. Every entry records the `recipient_type` it was addressed to — `PARTICIPANT`, `ALTERNATE_PAYEE`, `PARTICIPANT_ATTORNEY`, or `AP_ATTORNEY` — a `template_code` drawn from `RECEIPT_ACKNOWLEDGMENT`, `DEFICIENCY_NOTICE`, `DETERMINATION_QUALIFIED`, `DETERMINATION_DENIED`, `SEGREGATION_LAPSE_NOTICE`, `RELEASE_NOTICE`, and `DISTRIBUTION_CONFIRMATION`, a `disclosure_level` of `LIMITED` or `FULL`, and a `sent_at` instant taken from the logical clock. An `origin` field distinguishes the two ways an entry comes into being: entries appended by a cascade carry `SYSTEM`, and entries a `QdroAnalyst` composes by hand carry `MANUAL`. For an entry addressed to counsel, `attorney_email` is copied as a value — not held as a reference — from the authorization resolved for that side under the rules of §2.11; for entries addressed to the participant or the payee, `attorney_email` is null. Correspondence is listed in `sent_at` ascending order with `created_at` ascending as the tie-breaker, which reproduces exactly the order cascades appended entries, and the list may be narrowed by `recipient_type`, by `template_code`, or by `origin`.

Manual correspondence is available only to a `QdroAnalyst`, and it presupposes that something has actually happened on the case. A determination letter composed against a case still sitting at `review_status` `INTAKE`, with no draft order ever received, is refused with `ERR_NO_ACTIVE_DRAFT_ORDER`. Correspondence addressed to counsel additionally requires a matching `ACTIVE` authorization on the case for the side addressed, failing which the request is refused with `ERR_ATTORNEY_NOT_AUTHORIZED`.

### 3.4. Receipt of a Draft Order, Assignment Sizing, and Hold Placement

Receipt is the moment the plan's money stops being freely available. Contrary to a common assumption, the segregation hold is placed **on receipt of a draft**, not at qualification: the assignable amount is computed from the draft's own terms, the aggregate exposure on the account is checked, and a hold is created with the plan's eighteen-month expiry. A draft order may be lodged by a `PlanAdministrator`, a `QdroAnalyst`, the `Participant` whose account is at stake, or an `Attorney` acting under an authorization on the case.

The submission names its `qdro_case_id`, the `expected_case_version` described in §2.7, and a `document_reference` pointing into the imaging system (one to 64 characters, not blank). Its substantive terms are `uses_model_language`, a required boolean asserting that the draft adopts the plan's model packet verbatim; `proposed_approach`, either `SEPARATE_INTEREST` or `SHARED_PAYMENT`; `proposed_formula_code`, one of `PERCENTAGE_OF_ACCOUNT`, `FLAT_DOLLAR`, or `COVERTURE_FRACTION`; and an optional `provisions` array defaulting to an empty list, whose members are drawn from `ASSIGNS_BENEFITS_ALREADY_ASSIGNED`, `BENEFIT_NOT_OTHERWISE_AVAILABLE`, `LUMP_SUM_ELECTION`, `REQUIRES_INCREASED_TOTAL_BENEFIT`, `REQUIRES_QJSA_FOR_AP_SPOUSE`, and `SURVIVOR_ANNUITY_FOR_AP`, without duplicates. Which numeric term is required depends on the formula: `proposed_percentage_bps` — null by default, otherwise from 1 to 10000 — is required unless the formula is `FLAT_DOLLAR`, and `proposed_flat_amount_cents` — null by default, otherwise at least 1 — is required precisely when the formula is `FLAT_DOLLAR`. A `SHARED_PAYMENT` proposal must additionally carry `proposed_shared_payment_end_date`, the last calendar date on which the payee shares periodic payments, which must be strictly later than the logical clock's calendar date at receipt. When an `Attorney` lodges the draft, `attorney_authorization_id` names the authorization relied on and must equal the acting attorney's `X-User-ID`; when the participant or the administrator lodges it, the field is null.

The received row is stamped with `revision_number` 1, `status` `UNDER_REVIEW`, a `received_at` taken from the logical clock, a freshly computed `deficiency_codes` set, and a null `reviewed_by_user_id` and `denial_reason`. Its `review_deadline_at` is `received_at` advanced by the plan's `review_period_days` whole days. If this is the first draft on the case, the case moves `INTAKE → UNDER_REVIEW` on the review track and `NONE → HELD` on the custody track, a segregation hold is created, and a single correspondence entry addressed to the `PARTICIPANT` with template `RECEIPT_ACKNOWLEDGMENT`, `disclosure_level` `LIMITED`, and `origin` `SYSTEM` is appended. The case's `version` increments by one.

A second receipt on the same case is legitimate and is how a wholly rewritten order reaches the plan. Any existing draft order on the case that is still `UNDER_REVIEW` or `DEFICIENT` moves to `SUPERSEDED`, and every rejection notice on that superseded row that was still `ISSUED` moves to `EXPIRED`. No correspondence entry is appended on account of the superseded row itself. If the case was sitting at `review_status` `DEFICIENT`, the superseding receipt returns it to `UNDER_REVIEW`; the case's five operative terms are overwritten from the new draft in either event. The existing hold is **not** re-placed: `placed_at` and therefore `expires_at` survive from the first receipt, and only `hold_amount_cents` is recomputed from the new terms, after which the account's derived balances are recomputed.

A segregation hold records the `qdro_case_id` whose receipt triggered it and the `plan_account_id` whose funds are held, both set by the server; a client never creates one. Its `hold_amount_cents` is the gross assigned amount computed below. `placed_at` is the logical clock at the first receipt on the case and is never reset by a supersede or a resubmission, so the eighteen-month clock runs from first receipt across the entire revision cycle. `expires_at` is `placed_at` advanced by the plan's `segregation_period_days` whole days. `valuation_date` is copied from the case and forms the left edge of the earnings window. `segregation_date` is null while the hold is `HELD`, `RELEASED`, or `EXPIRED`, and both `earnings_growth_bps` and `earnings_adjustment_cents` sit at 0 until conversion. Holds are discoverable only by listing them — narrowed by `plan_account_id`, by `qdro_case_id`, or by `status` — in `placed_at` ascending order with `created_at` ascending as the tie-breaker, which is also the order the sweep processes them in.

Whole-day arithmetic on UTC instants carries the time-of-day component unchanged, and every expiry predicate in this system is **strictly greater than**, never greater-than-or-equal. A hold placed at 2026-09-01T00:00:00Z under the default 548-day window expires at 2028-03-02T00:00:00Z; the sweep leaves it `HELD` at exactly 2028-03-02T00:00:00Z and only expires it at 2028-03-02T00:00:01Z or later. The same discipline governs rejection notices: a notice issued 2026-09-15 with a 60-day window carries a resubmission deadline of 2026-11-14, and a resubmission arriving at exactly 2026-11-14T00:00:00Z is accepted.

Sizing the assignment is the arithmetic heart of receipt, and it is recomputed identically on every resubmission, on the projection read, and again at qualification when the payee account is funded. It begins from the account's assignable base — the sum of the assignable money sources' balances, as defined in §2.9 — and then branches on the case's operative `formula_code`.

- Under `PERCENTAGE_OF_ACCOUNT`, the raw amount is the assignable base multiplied by the operative `assigned_percentage_bps` and divided by 10000, rounded **down** to whole cents.
- Under `FLAT_DOLLAR`, the raw amount is simply the operative `assigned_flat_amount_cents`.
- Under `COVERTURE_FRACTION`, a coverture share is computed first and then applied to the assigned percentage. The effective share in basis points is the coverture share multiplied by the operative `assigned_percentage_bps` and divided by 10000, rounded down to a whole basis point; the raw amount is then the assignable base multiplied by that effective share and divided by 10000, again rounded down to whole cents.

The **coverture share** measures how much of the participant's benefit accrued inside the marriage. Its numerator is the number of whole calendar days in the marital window, counted half-open from `marital_period_start` up to but not including `marital_period_end` — so a marital period ending on the participation anniversary contributes exactly that many days, not one more. Its denominator is the number of whole calendar days from the participant's `participation_start_date` to the case's `valuation_date`. When that denominator is zero or negative, the coverture share is 0 basis points. Otherwise the share is 10000 multiplied by the numerator, divided by the denominator, and rounded **half up** to a whole basis point. The result is then capped at 10000, because a marital period longer than the period of participation cannot represent more than the whole account. The formula requires `marital_period_end`; a case that never supplied one cannot be priced this way, and the review step below turns that into a named deficiency.

Two statutory ceilings are then applied, and both are applied — the tighter one wins. The **percentage ceiling** is the same assignable base multiplied by the plan's `max_assignable_pct_bps` and divided by 10000, rounded down to whole cents. The **amount ceiling** is the plan's `max_assignable_amount_cents` taken as-is. The gross assigned amount is the smallest of the raw amount, the percentage ceiling, and the amount ceiling, and it is floored at zero so it can never be negative. Note the consequence for flat-dollar orders: a flat assignment above half the assignable base is silently trimmed to the percentage ceiling rather than being rejected. Note also that division is rounded **down** at every step of this calculation and never half up, and that because the ceiling is recomputed from the very same base, two plans with identical `assigned_percentage_bps` produce different amounts whenever their ceilings differ.

If the gross assigned amount comes out as exactly 0 — a zero percentage, a zero flat amount, an empty assignable base, or a coverture share that rounds to nothing — the receipt is refused with `ERR_ASSIGNED_AMOUNT_ZERO`, and the same refusal applies to a resubmission that would produce a zero.

Before the hold amount is written, the plan account's **aggregate exposure** is tested. The candidate hold for this case is added to the sum of `hold_amount_cents` over every *other* segregation hold on the same plan account whose `status` is `HELD` — this case's own hold is excluded, so a resubmission that changes the amount replaces its old exposure rather than double-counting it, and holds in `CONVERTED`, `RELEASED`, or `EXPIRED` are excluded entirely, which is how an expired hold frees capacity for the next order. If that total is **strictly greater** than the account's `vested_balance_cents`, the request is refused with `ERR_HOLD_CAPACITY_EXCEEDED`; exposure exactly equal to the vested balance is permitted. The check is collective, not per-order: on an account with a vested balance of 1000000 cents, two holds of 400000 cents each individually satisfy a 50-percent per-order ceiling and together total 800000, but a third hold of 300000 cents would bring the total to 1100000 and is refused.

### 3.5. Pricing an Assignment Before It Is Committed

Counsel and the plan both need to see the money before anybody signs anything, so the case exposes a purely computed read that mutates nothing. It reports `assignable_base_cents` and `gross_assigned_amount_cents` exactly as §3.4 defines them, an `effective_approach` string naming which of the two approaches was priced, the earnings pair `earnings_growth_bps` and `earnings_adjustment_cents`, the two mutually exclusive money shapes `separate_interest_balance_cents` and `shared_payment_per_period_cents`, an `after_tax_basis_carryover_cents` figure, and `valuation_snapshot_count`, the number of valuation snapshots on the operative plan account. By default the read prices the case's own operative `approach`; an optional `approach` input overrides it, which lets a caller price the road not taken. Before variant selection the projection is a skeleton in which the two earnings figures, the separate-interest balance, and the shared-payment periodic amount are all 0; the selected variant fills in the ones that apply and leaves the others at 0.

Under the **separate interest** variant — the shape available when the participant's `benefit_commenced` is false — the payee receives a carved-out principal balance that is immediately distributable, and the participant's money sources are permanently debited. `earnings_growth_bps` and `earnings_adjustment_cents` are computed as described below, `separate_interest_balance_cents` is the gross assigned amount increased by the earnings adjustment, and `shared_payment_per_period_cents` is 0.

Under the **shared payment** variant — the shape available when the participant's `benefit_commenced` is true and the plan account's `monthly_payment_cents` is greater than 0 — nothing is segregated as principal, so no interval earnings accrue at all: `earnings_growth_bps`, `earnings_adjustment_cents`, and `separate_interest_balance_cents` are all 0. Instead `shared_payment_per_period_cents` is the plan account's `monthly_payment_cents` multiplied by the case's operative `assigned_percentage_bps` and divided by 10000, rounded **down** to whole cents. The payee then receives a slice of each periodic payment as it is made, principal stays with the participant, and the hold is released rather than converted. The divergence is stark on identical case data: with a `monthly_payment_cents` of 320000 and an `assigned_percentage_bps` of 4000, the shared-payment shape reports 128000 per period and a balance of 0, while the separate-interest shape reports a per-period amount of 0 and a balance equal to the gross assigned amount plus earnings.

**Allocating the assignment across money sources.** Whenever the assignment has to touch actual buckets — to debit the participant at conversion, and as the input to the earnings arithmetic — the gross assigned amount is spread across the account's assignable money sources in `source_code` ASCII-ascending order, which for the assignable codes means `AFTER_TAX`, then `EMPLOYER_MATCH`, then `PRE_TAX_DEFERRAL`, then `ROTH`; a non-assignable loan bucket takes part in nothing. The ordering is by `source_code` and never by `id`. For every source except the last in that order, its share is the gross assigned amount multiplied by that source's `balance_cents`, divided by the assignable base, and rounded **half up** to whole cents. The final source in the order receives the gross assigned amount reduced by the sum of all the shares already assigned, so it absorbs whatever rounding residue remains and the shares sum to the gross assigned amount with zero drift. Because the residue always lands on the highest `source_code`, changing an account's source mix changes which bucket eats it.

**Earnings between the valuation date and the segregation date.** Growth is measured from two valuation snapshots on the operative plan account. The baseline snapshot is the one whose `as_of_date` exactly equals the case's `valuation_date`; a snapshot one day off does not qualify, and if none exists the determination is refused with `ERR_VALUATION_SNAPSHOT_MISSING`. The endpoint snapshot is chosen from the snapshots whose `as_of_date` falls on or after the segregation date — the logical clock's calendar date at conversion, or the clock's current date when the projection is being read — taking the **earliest** such `as_of_date`, with `created_at` ascending as the tie-breaker and never the `id`. When that candidate set is empty, the endpoint snapshot is taken to be the baseline snapshot itself, which drives the whole calculation to 0. Snapshots falling strictly between the valuation date and the segregation date are ignored entirely.

The period growth is then 10000 multiplied by the difference between the endpoint snapshot's `balance_cents` and the baseline's, divided by the baseline's `balance_cents`, rounded **half up** to a whole basis point; it is 0 when the baseline balance is 0, and it is negative when the account lost value. The plan's `earnings_adjustment_method` decides what happens next. Under `PERIOD_END` the growth is credited verbatim — the whole valuation-to-valuation move goes to the segregated amount regardless of how much of the interval elapsed before segregation. Under `PRO_RATA_DAILY` only the elapsed fraction is credited: the span is the number of whole days from the baseline snapshot's `as_of_date` to the endpoint snapshot's `as_of_date`, the elapsed portion is the number of whole days from the baseline snapshot's `as_of_date` to the segregation date, and the credited growth is the period growth multiplied by the elapsed days, divided by the span days, rounded half up to a whole basis point; when the span is zero or negative the credited growth is 0. Whenever the elapsed portion is shorter than the span, `PRO_RATA_DAILY` yields a strictly smaller magnitude than `PERIOD_END`. Both methods collapse to 0 basis points when no post-segregation snapshot exists, because the endpoint then equals the baseline.

The earnings **amount** is derived from the allocation vector, and the order of operations is pinned: each source's earnings are the share allocated to that source multiplied by the credited growth in basis points, divided by 10000, rounded **half up** to whole cents — and only then are the per-source figures summed to give `earnings_adjustment_cents`. This is deliberately *not* the same as rounding the aggregate once. With shares of 40000, 596050, and 963950 cents and a credited growth of 300 basis points, the per-source figures are 1200, 17882, and 28919 cents, summing to 48001, whereas rounding the aggregate first would give 48000. The one-cent divergence is the observable contract; summing before rounding is wrong. The adjustment covers exactly the interval between the valuation date and the segregation date; it is 0 for a shared-payment case, because no principal is segregated, and 0 whenever no post-segregation snapshot exists.

**Basis carried to the payee.** After-tax basis follows the principal it belongs to. Walking the same assignable sources in the same `source_code` ascending order, each source with a non-zero `balance_cents` contributes its `basis_cents` multiplied by that source's allocated share, divided by that source's `balance_cents`, rounded **down** to whole cents; sources with a zero balance are skipped and sources with a zero `basis_cents` — an employer match or a pre-tax deferral bucket — contribute nothing. The contributions are summed to give the carryover. Rounding down per source is deliberate: the payee can never inherit more after-tax basis than was actually assigned. The earnings adjustment carries no basis at all. For a shared-payment case the carryover is 0.

### 3.6. Deficiency Review, Rejection Notices, and the Resubmission Cycle

Reviewing a draft order against the plan's procedures produces a set of **deficiency codes**, recomputed fresh at four moments: when a draft is received, when it is resubmitted, when a rejection notice is issued on it, and again when a qualification is attempted. The codes are held on the draft order's `deficiency_codes` array, which the client never supplies. Eight codes exist, and each is raised by exactly one condition:

- `MISSING_MODEL_LANGUAGE` — the plan's `requires_model_language` is true and the draft's `uses_model_language` is false.
- `FORMULA_NOT_ACCEPTABLE` — the draft's `proposed_formula_code` is not among the plan's `acceptable_formula_codes`.
- `MARITAL_PERIOD_UNDEFINED` — the case's `marital_period_end` is null **and** the draft's `proposed_formula_code` is `COVERTURE_FRACTION`. The code is conditional on the formula: a percentage-of-account draft on a case with no marital end date is perfectly qualifiable, while the same case with a coverture draft is deficient.
- `AP_IDENTIFICATION_INCOMPLETE` — the case's `alternate_payee_dob` is null **or** its `alternate_payee_address_on_file` is false.
- `PROHIBITED_BENEFIT_NOT_AVAILABLE` — the draft's `provisions` contain `BENEFIT_NOT_OTHERWISE_AVAILABLE` while the plan's `permits_benefit_not_otherwise_available` is false.
- `PROHIBITED_INCREASED_BENEFIT` — the draft's `provisions` contain `REQUIRES_INCREASED_TOTAL_BENEFIT`.
- `PROHIBITED_ALREADY_ASSIGNED` — the draft's `provisions` contain `ASSIGNS_BENEFITS_ALREADY_ASSIGNED`.
- `PROHIBITED_FORM_NOT_OFFERED` — the draft's `provisions` contain `SURVIVOR_ANNUITY_FOR_AP` **or** `REQUIRES_QJSA_FOR_AP_SPOUSE`, because a defined-contribution plan offers no annuity form at all.

The codes are a set, then sorted ASCII ascending for determinism. One prohibited provision raises at most one code, and the two annuity-form provisions collapse into the single `PROHIBITED_FORM_NOT_OFFERED`, so a draft carrying both yields one code, not two. `LUMP_SUM_ELECTION` is explicitly benign on a defined-contribution plan and contributes no code whatever.

Issuing a rejection notice is the exclusive act of a `QdroAnalyst`, and it takes only an optional `reviewer_notes` free-text explanation (null by default, otherwise one to 2000 characters). The draft order must be `UNDER_REVIEW`, its recomputed code set must be non-empty — an empty set is refused with `ERR_NO_DEFICIENCIES_TO_REPORT` — and the case's segregation hold must still be `HELD` with the logical clock at or before its `expires_at`. The notice records its `draft_order_id`, a `notice_sequence` equal to the count of notices already on that draft order plus one, a snapshot of the recomputed `deficiency_codes` sorted ASCII ascending, an `issued_at` taken from the logical clock, a `resubmission_deadline_at` equal to `issued_at` advanced by the plan's `resubmission_window_days` whole days, and `status` `ISSUED`. Notices are listed under their draft order in `notice_sequence` ascending order and may be narrowed by `status`; that list is the only channel through which a client discovers notices a cascade expired.

Issuance cascades. The draft order moves `UNDER_REVIEW → DEFICIENT` and its `reviewed_by_user_id` is set to the issuing analyst's `X-User-ID`, planting the segregation-of-duties marker of §2.12. The case moves `UNDER_REVIEW → DEFICIENT` on its review track, its `version` increments by one, and two correspondence entries are appended **in this order**: first one addressed to `PARTICIPANT` with template `DEFICIENCY_NOTICE`, `disclosure_level` `FULL`, and `origin` `SYSTEM`; then one addressed to `ALTERNATE_PAYEE` with the same template, `disclosure_level` `LIMITED`, and `origin` `SYSTEM`. The payee's level is `LIMITED` because the case has not reached `QUALIFIED`.

Resubmission is how a corrected order gets back in front of the reviewer, and it is performed **in place** on the same draft order row rather than by lodging a new one. A `PlanAdministrator`, the `Participant`, or an authorized `Attorney` may resubmit — the analyst who issued the notice may not. The submission carries the same substantive terms as an original receipt: `document_reference`, `uses_model_language`, `proposed_approach`, `proposed_formula_code`, and optionally `provisions`, `proposed_percentage_bps`, `proposed_flat_amount_cents`, and `proposed_shared_payment_end_date`. It carries no version field, because it is not a create.

Four gates guard it, and their relative order is stated in §2.8: the draft order must be `DEFICIENT` (otherwise `ERR_DRAFT_ORDER_NOT_DEFICIENT`); the notice with the highest `notice_sequence` on that draft must still be `ISSUED` and the logical clock must be at or before its `resubmission_deadline_at` (otherwise `ERR_RESUBMISSION_WINDOW_CLOSED`); the case's segregation hold must still be `HELD` with the clock at or before its `expires_at` (otherwise `ERR_SEGREGATION_WINDOW_EXPIRED`); and the draft's `revision_number` must be strictly less than the plan's `max_revisions` (otherwise `ERR_MAX_REVISIONS_EXCEEDED`). Because the window gate is evaluated before the revision cap, a submission that is both late and over the cap reports the closed window.

A successful resubmission overwrites `uses_model_language`, `provisions`, `proposed_approach`, `proposed_formula_code`, `proposed_percentage_bps`, `proposed_flat_amount_cents`, and `proposed_shared_payment_end_date` with the newly submitted values, increases `revision_number` by one, recomputes `deficiency_codes`, and resets `review_deadline_at` to the logical clock advanced by the plan's `review_period_days`. `received_at` is deliberately **not** reset, and neither is the hold's `placed_at` or `expires_at` — the eighteen-month segregation window is not restarted by a revision. The highest-sequence notice moves `ISSUED → CURED`. The draft order moves `DEFICIENT → UNDER_REVIEW` while `reviewed_by_user_id` is retained. The case's five operative terms are refreshed from the resubmitted values and, because those terms changed, the `HELD` hold's `hold_amount_cents` is recomputed and the plan account's derived balances are recomputed with it. The case moves `DEFICIENT → UNDER_REVIEW` and its `version` increments by one. This `UNDER_REVIEW → DEFICIENT → UNDER_REVIEW` loop is the non-linear shape of the draft-order lifecycle, and a case may traverse it up to one time fewer than the plan's `max_revisions`.

Draft orders are listed in `received_at` ascending order with `created_at` ascending as the tie-breaker, and the list may be narrowed by `qdro_case_id`, by `attorney_authorization_id`, or by `status`.

### 3.7. The Qualification Determination and the Segregation-to-Payee Cascade

Qualification is reserved to a `PlanAdministrator` and takes no request body at all — everything it needs is already on the case, the draft, the plan, and the account. It is nonetheless the most heavily guarded operation in the system. Seven conditions must hold, and §2.8 fixes the order in which their failures are reported: the draft order must be `UNDER_REVIEW` (otherwise `ERR_DRAFT_ORDER_NOT_UNDER_REVIEW`); the acting `X-User-ID` must differ from the draft's `reviewed_by_user_id` (otherwise `ERR_SEGREGATION_OF_DUTIES`); the plan's `procedures_status` must be `PUBLISHED` (otherwise `ERR_PLAN_PROCEDURES_NOT_PUBLISHED`); the case's segregation hold must still be `HELD` with the logical clock at or before its `expires_at` (otherwise `ERR_SEGREGATION_WINDOW_EXPIRED`); the recomputed `deficiency_codes` set must be empty (otherwise `ERR_QUALIFICATION_DEFICIENCIES_PRESENT`); a valuation snapshot whose `as_of_date` equals the case's `valuation_date` must exist on the operative plan account (otherwise `ERR_VALUATION_SNAPSHOT_MISSING`); and the case's operative `approach` must be one the plan lists in `allowed_approaches` *and* must match the participant's payment posture — a `SHARED_PAYMENT` case requires `benefit_commenced` true with `monthly_payment_cents` greater than 0, and a `SEPARATE_INTEREST` case requires `benefit_commenced` false (otherwise `ERR_APPROACH_NOT_PERMITTED`).

A determination that survives all seven fires a seven-level cascade in a fixed order, and each level exists *because* of the one before it.

**Level 1.** The draft order moves `UNDER_REVIEW → QUALIFIED`.

**Level 2.** Because the draft qualified, the case's `review_status` moves `UNDER_REVIEW → QUALIFIED`. That terminates the review track.

**Level 3.** Because the case reached `QUALIFIED`, its segregation hold leaves `HELD`, and which way it leaves depends entirely on the approach. For a `SEPARATE_INTEREST` case the hold moves `HELD → CONVERTED`, and three fields are stamped on the way out: `segregation_date` becomes the logical clock's calendar date, `earnings_growth_bps` becomes the credited growth computed in §3.5, and `earnings_adjustment_cents` becomes the per-source-rounded earnings amount. For a `SHARED_PAYMENT` case the hold moves `HELD → RELEASED` instead: `segregation_date` stays null and both `earnings_growth_bps` and `earnings_adjustment_cents` stay at 0, because nothing was ever carved out to earn anything. Either way the hold stops contributing to the account's `held_amount_cents`.

**Level 4.** Because the hold left `HELD`, an alternate payee account is established on the case. Its `qdro_case_id` is set by the server — a client never creates one of these — and the funding plan account is the one whose `participant_id` matches the case's `participant_id`. `payment_mode` is copied from the case's operative `approach`, `established_at` is the logical clock, and `status` is `ESTABLISHED`. For `SEPARATE_INTEREST`, `balance_cents` is the hold's `hold_amount_cents` increased by its `earnings_adjustment_cents`, `after_tax_basis_cents` is the basis carryover computed in §3.5, `per_period_amount_cents` is 0, and `shared_payment_end_date` is null. For `SHARED_PAYMENT`, `balance_cents` and `after_tax_basis_cents` are both fixed at 0 — payments will be drawn from the participant's own account, not from a carved-out pot — `per_period_amount_cents` is the shared-payment periodic amount from §3.5, and `shared_payment_end_date` is copied from the case. `total_distributed_gross_cents` starts at 0 in both shapes. The account is discoverable only by listing the case's payee accounts, which returns an array of length 0 or 1.

**Level 5.** Because the payee account was funded, the participant's side is debited — but only in the separate-interest shape. Each assignable money source, in `source_code` ascending order, has its `balance_cents` debited by the sum of its allocated share and its own per-source earnings figure, both from §3.5, and — because after-tax basis follows the principal it belongs to — its `basis_cents` debited by that same source's own contribution to the basis carryover of §3.5, computed from the balance and basis the source carried before the debit. The basis that leaves the participant's buckets is therefore exactly the basis the payee account is credited with. Because money source balances and bases changed, the account's `vested_balance_cents`, `assignable_base_cents`, and `after_tax_basis_cents` are recomputed; and because the hold left `HELD`, `held_amount_cents` drops to 0 and `available_balance_cents` is recomputed with it. In the shared-payment shape no money source is debited at all — the only balance movement is `held_amount_cents` dropping to 0 as the hold is released, restoring `available_balance_cents` to the vested balance.

**Level 6.** Because the payee account was established, the case's `segregation_status` moves `HELD → CONVERTED` for a separate-interest case, or `HELD → RELEASED_TO_PARTICIPANT` for a shared-payment case. Two correspondence entries are then appended **in this order**: one addressed to `PARTICIPANT` with template `DETERMINATION_QUALIFIED`, `disclosure_level` `FULL`, `origin` `SYSTEM`; then one addressed to `ALTERNATE_PAYEE` with the same template, `disclosure_level` `FULL`, `origin` `SYSTEM`. The payee's level is `FULL` here — unlike on a rejection notice — precisely because the case's `review_status` is already `QUALIFIED` at the moment the entry is appended.

**Level 7.** The case's `version` increments by one.

### 3.8. Denial, Hold Release, and the Segregation Sweep

Denial is the other terminal outcome, and it is also reserved to a `PlanAdministrator`. It takes a single `denial_reason`, and the reason must match the observable facts rather than merely being a plausible label. `ORDER_NOT_QUALIFIABLE` is available only from an `UNDER_REVIEW` draft order whose recomputed deficiency set is non-empty. `MAX_REVISIONS_EXCEEDED` is available only from a `DEFICIENT` draft order whose `revision_number` has reached or passed the plan's `max_revisions`. `RESUBMISSION_WINDOW_CLOSED` is available only from a `DEFICIENT` draft order whose highest-`notice_sequence` rejection notice has a `resubmission_deadline_at` strictly earlier than the logical clock. `SEGREGATION_LAPSED` is a system-only reason and may never be supplied by a human caller at all. Any other combination — a faultless `UNDER_REVIEW` draft offered as `ORDER_NOT_QUALIFIABLE`, a revision count below the cap offered as `MAX_REVISIONS_EXCEEDED`, an open window offered as `RESUBMISSION_WINDOW_CLOSED` — is refused with `ERR_DENIAL_NOT_PERMITTED`.

A denial moves the draft order to `DENIED` with the supplied `denial_reason` stored, expires any rejection notice on that draft that was still `ISSUED`, moves the case's `review_status` to `DENIED`, increments the case's `version` by one, and appends two correspondence entries **in this order**: one addressed to `PARTICIPANT` with template `DETERMINATION_DENIED`, `disclosure_level` `FULL`, `origin` `SYSTEM`; then one addressed to `ALTERNATE_PAYEE` with the same template, `disclosure_level` `LIMITED`, `origin` `SYSTEM`. One thing the denial deliberately does *not* do is let the money go: the segregation hold stays `HELD` and the account's `available_balance_cents` stays depressed. Restoring the funds is a separate, explicit second act.

That second act is the release, again an administrator operation, and it is permitted only while the hold is still `HELD` (otherwise `ERR_HOLD_NOT_HELD`) and only once the hold's case has actually reached `review_status` `DENIED` (otherwise `ERR_CASE_NOT_DENIED`) — funds cannot go back to the participant while an order is still live. Release moves the hold `HELD → RELEASED`, recomputes the account's derived balances so that `held_amount_cents` drops and `available_balance_cents` is fully restored to `vested_balance_cents`, moves the case's `segregation_status` to `RELEASED_TO_PARTICIPANT`, increments the case's `version` by one, and appends two correspondence entries **in this order**: one addressed to `PARTICIPANT` with template `RELEASE_NOTICE`, `disclosure_level` `FULL`, `origin` `SYSTEM`; then one addressed to `ALTERNATE_PAYEE` with the same template, `disclosure_level` `LIMITED`, `origin` `SYSTEM`.

When nobody acts, time acts instead. An administrator-only sweep capability walks the whole system in three pinned phases and reports what it did: an `evaluated_count`, plus the identifier lists `expired_hold_ids`, `lapsed_case_ids`, `denied_draft_order_ids`, `expired_notice_ids`, and `closed_ap_account_ids`.

**Phase 1 — lapsed segregation.** Every hold in `HELD` status whose `expires_at` is strictly earlier than the logical clock is processed, in `placed_at` ascending order with `created_at` ascending as the tie-breaker. Each one cascades six levels. The hold moves `HELD → EXPIRED`. Because it left `HELD`, the plan account's derived balances are recomputed so `held_amount_cents` drops and `available_balance_cents` is restored. Because the segregation lapsed, the case's `segregation_status` moves `HELD → LAPSED`. Because the case can no longer be qualified, the case's non-terminal draft order — one sitting at `UNDER_REVIEW` or `DEFICIENT` — moves to `DENIED` with `denial_reason` `SEGREGATION_LAPSED`, and every rejection notice on it that was still `ISSUED` moves to `EXPIRED`. Because the draft was denied, the case's `review_status` moves to `DENIED` from whichever of `UNDER_REVIEW` or `DEFICIENT` it held, and two correspondence entries are appended **in this order**: one addressed to `PARTICIPANT` with template `SEGREGATION_LAPSE_NOTICE`, `disclosure_level` `FULL`, `origin` `SYSTEM`; then one addressed to `ALTERNATE_PAYEE` with the same template, `disclosure_level` `LIMITED`, `origin` `SYSTEM`. Finally the case's `version` increments by one. Note that a lapse is the one path by which the custody track and the review track both terminate without a single human act.

**Phase 2 — expired resubmission windows.** Every rejection notice in `ISSUED` status whose `resubmission_deadline_at` is strictly earlier than the logical clock moves `ISSUED → EXPIRED`, processed in `issued_at` ascending order. This phase touches nothing else: the draft order stays `DEFICIENT`. Expiry of the window alone does not deny an order — only an explicit denial carrying `RESUBMISSION_WINDOW_CLOSED` does that.

**Phase 3 — exhausted shared-payment streams.** Every alternate payee account in `ESTABLISHED` status whose `payment_mode` is `SHARED_PAYMENT` and whose `shared_payment_end_date` is strictly earlier than the logical clock's calendar date moves `ESTABLISHED → CLOSED`, and each such account's `version` increments by one. Separate-interest accounts are untouched by this phase; they close by a different route, described in §3.9.

Sweeps are idempotent with respect to a fixed clock: a second run at the same instant finds nothing left to do, because every row it would act on has already left the status the phase selects for.

### 3.9. Alternate Payee Distributions, Tax Reporting, and Corrections

Once an account exists, the alternate payee — or a `PlanAdministrator` acting for them — may elect a distribution. The request carries the `expected_ap_account_version` of §2.7, an `election` of either `CASH` or `DIRECT_ROLLOVER`, a `gross_amount_cents` of at least 1, and, for a rollover, a `rollover_institution` naming the receiving IRA or plan trustee (one to 120 characters). A cash election carries no `rollover_institution`; a rollover election without one is refused with `ERR_ROLLOVER_INSTITUTION_REQUIRED`. On a `SHARED_PAYMENT` payee account the requested `gross_amount_cents` must equal that account's `per_period_amount_cents` **exactly** — a periodic slice is not negotiable — and any other figure is refused with `ERR_SHARED_PAYMENT_AMOUNT_MISMATCH`. The account must be `ESTABLISHED`; a request against a `CLOSED` account is refused with `ERR_AP_ACCOUNT_CLOSED`.

Which pool funds the payment depends on the account's `payment_mode`, and this single branch propagates through the whole settlement. For a `SEPARATE_INTEREST` account the basis pool is the payee account's own `after_tax_basis_cents` and the balance pool is its own `balance_cents`. For a `SHARED_PAYMENT` account the payee account holds no principal, so the participant's plan account funds each slice: the basis pool is the plan account's `after_tax_basis_cents` and the balance pool is its `assignable_base_cents`. Capacity is checked against the pool the payee can actually draw on: for a separate-interest account the requested gross may not exceed the payee account's `balance_cents`, and for a shared-payment account it may not exceed the participant's `available_balance_cents`. Either overdraft is refused with `ERR_INSUFFICIENT_DISTRIBUTABLE_BALANCE`.

Settlement then runs as seven pinned steps, and every derived field on the distribution row is a product of exactly one of them.

1. **Basis recovery.** `basis_recovery_cents` is the basis pool multiplied by `gross_amount_cents`, divided by the balance pool, rounded **down** to whole cents; it is 0 when the balance pool is 0, and it is then capped so that it never exceeds the basis pool itself.
2. **Taxable portion.** `taxable_amount_cents` is `gross_amount_cents` reduced by `basis_recovery_cents`.
3. **Mandatory federal withholding.** For a `DIRECT_ROLLOVER`, `federal_withheld_cents` is always 0 no matter how large the taxable amount. For a `CASH` election, withholding applies only once `taxable_amount_cents` reaches at least 20000 cents, at which point `federal_withheld_cents` is `taxable_amount_cents` multiplied by 2000 basis points — twenty percent — divided by 10000 and rounded **half up** to whole cents; below that floor it is 0. The threshold is on the **taxable** amount and not on the gross: with no basis at all, a gross of 20000 withholds 4000 while a gross of 19999 withholds nothing.
4. **Intermediate net.** `net_before_fee_cents` is `gross_amount_cents` reduced by `federal_withheld_cents`.
5. **Administrative fee.** The tier is keyed on `net_before_fee_cents` and never on the gross or on the final net. A `net_before_fee_cents` below 100000 cents draws an `admin_fee_cents` of 2500; from 100000 up to and including 999999 cents it draws 5000; at 1000000 cents or above it draws 7500.
6. **Final net.** `net_amount_cents` is `net_before_fee_cents` reduced by `admin_fee_cents`.
7. **Reporting code and year.** `distribution_code` is the 1099-R box 7 code. A `DIRECT_ROLLOVER` is always `CODE_G`, and the payee's age is irrelevant to it. A `CASH` election is `CODE_2` when the logical clock's calendar date falls strictly before the payee's fifty-nine-and-a-half birthday — the case's `alternate_payee_dob` advanced by 59 years and then a further 6 calendar months — and `CODE_7` on or after it. `tax_year` is the logical clock's calendar year.

Because the fee tier keys on the net after withholding, the election alone can change the fee on an identical gross. Take a gross of 1050000 cents whose basis recovery leaves a taxable amount of 1034710 cents: the cash election withholds 206942, lands at a `net_before_fee_cents` of 843058, and draws the middle fee of 5000; the direct rollover of the very same gross withholds nothing, lands at a `net_before_fee_cents` of 1050000, and draws the top fee of 7500. Keying the tier on the gross instead of the intermediate net is wrong.

The issued row carries `issued_at` from the logical clock, a null `voided_at`, and `status` `ISSUED`. Issuance then reconciles the account totals of §2.9, and for a `SHARED_PAYMENT` account it additionally debits the participant's assignable money sources by spreading the gross amount across them with the same allocation waterfall described in §3.5, after which the plan account's derived balances are recomputed. A reporting line is appended, and the payee account's `version` increments by one. When a `SEPARATE_INTEREST` account's `balance_cents` reaches exactly 0 after the debit, the account moves `ESTABLISHED → CLOSED`: no further distribution and no void is accepted against it, and a void attempted afterwards is refused with `ERR_AP_ACCOUNT_CLOSED`. Distributions are listed under their payee account in `issued_at` ascending order with `created_at` ascending as the tie-breaker, narrowable by `status` or by `tax_year`.

Tax reporting is an append-only ledger, never an editable record. Each reporting line records the `distribution_id` it reports, a denormalised `alternate_payee_account_id` used for net-position aggregation, a `correction_of_tax_report_id` that is null on an original line, a `form_code` of `FORM_1099R`, the three signed money figures `reportable_gross_cents`, `reportable_taxable_cents`, and `federal_withheld_cents`, a `distribution_code` and `tax_year` copied from the distribution as it stood when the line was written, and a `written_at` instant from the logical clock. Lines carry no `updated_at` and no `version`, and nothing in this API ever updates or deletes one. An original line copies the distribution's gross, taxable amount, and withholding as positive figures. Lines are listed in `written_at` ascending order with `created_at` ascending as the tie-breaker, narrowable by `distribution_id`, by `alternate_payee_account_id`, by `correction_of_tax_report_id`, or by `tax_year`; that list is the only channel through which a client discovers a cascade-appended corrective line.

A payee account's net reported position for a given year is the sum of `reportable_gross_cents`, the sum of `reportable_taxable_cents`, and the sum of `federal_withheld_cents` over every line whose `alternate_payee_account_id` is that account and whose `tax_year` is that year — original and corrective lines alike, since correction is expressed by sign rather than by deletion.

Voiding a distribution issued in error is an administrator act, and it is a **compensation, not an edit**. It is permitted only while the distribution is `ISSUED` (otherwise `ERR_DISTRIBUTION_ALREADY_VOIDED`), only while its payee account is `ESTABLISHED` (otherwise `ERR_AP_ACCOUNT_CLOSED`), and only while the logical clock's calendar year still equals the distribution's `tax_year` (otherwise `ERR_VOID_ACROSS_TAX_YEARS`). That last restriction exists because the corrective line inherits the **original** `tax_year` rather than the year of the void: a corrective line stamped with a stale year could never be reconciled against the year it was filed in.

A void cascades four levels. The distribution moves `ISSUED → VOIDED` and its `voided_at` is stamped with the logical clock. Because the payment is undone, the funding side is restored: for a `SEPARATE_INTEREST` account the payee account's `balance_cents` is increased by the distribution's `gross_amount_cents` and its `after_tax_basis_cents` is increased by the distribution's `basis_recovery_cents`; for a `SHARED_PAYMENT` account each participant money source that the original distribution debited is credited back its allocated share and the plan account's `vested_balance_cents`, `assignable_base_cents`, `after_tax_basis_cents`, and `available_balance_cents` are recomputed. The payee account's `total_distributed_gross_cents` is then recomputed from the `ISSUED` set alone, so the voided row contributes 0. Because the reported amounts no longer reflect a payment, a corrective reporting line is appended whose `reportable_gross_cents`, `reportable_taxable_cents`, and `federal_withheld_cents` are the negations of the original line's, whose `distribution_code` and `tax_year` are copied from the original, and whose `correction_of_tax_report_id` is the original line's `id`. Finally the payee account's `version` increments by one. After an issue followed by a void, all three of the account's net figures for that year are 0 while the ledger holds two rows, never zero rows — the history of the mistake is part of the record.

## 4. Endpoint Definitions

All endpoints are mounted at the API root. An operation that brings a new resource into existence answers with HTTP 201 and the created resource in `data`; an operation that modifies or transitions an existing resource, and every read, answers with HTTP 200. State-driving operations return the resource whose state they moved — a qualification, a denial and a resubmission all return the draft order, a release returns the hold, a void returns the distribution, and a procedures-status change returns the plan. Rows created by cascade are never returned by the operation that caused them; the list endpoints marked below are their only discovery channel.
