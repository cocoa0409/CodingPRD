# Rideshare Rental Program API — Product Requirements Document

## 1. Introduction

The Rideshare Rental Program API is the operational backbone of a vehicle-rental programme offered to rideshare and delivery drivers. A driver who does not own a qualifying car can be admitted to the programme, matched with a programme-owned unit from a designated fleet, and billed a recurring weekly rental that bundles insurance, a maintenance allowance and a mileage provision. The programme is deliberately protective of the driver's earning capacity: when a unit is taken out of service for repair, a like-for-like loaner is issued so that the driver's platform work is not interrupted, and when a driver falls behind on a weekly renewal the programme escalates through graduated compliance postures rather than terminating the arrangement outright.

The API therefore has to reconcile three concerns that pull in different directions: **eligibility and compliance**, which decide who may hold a unit at all; **fleet stewardship**, which keeps units assigned, serviced, recovered and fairly sized against regional demand; and **weekly money**, which meters each rental week, applies platform activity credits, collects tenders and accrues the equity that can eventually convert a rental into a purchase. Every one of those concerns is expressed as an explicit state machine, so the API is addressed primarily through named state transitions rather than free-form updates.

A note on the shape of this document. The global rules in §2 apply to every caller and every resource; they are stated once and are not repeated per endpoint. The business narratives in §3 describe *how the programme behaves* as a sequence of operational stories, and they intentionally carry the thresholds, defaults and cascade effects inline with the prose rather than in a consolidated specification block. The endpoint catalogue in §4 gives only method, path, purpose and authorised callers — the request and response payloads must be reconstructed from the §2 and §3 narratives.

## 2. Global Specifications & System-Wide Principles

### 2.1. Caller Identity and Role Segregation

Every request must carry two HTTP headers. `X-User-ID` identifies the acting principal and `X-User-Role` states the operational capacity in which that principal is acting. A request whose `X-User-Role` header is absent or carries a value outside the five recognised roles is rejected with `ERR_UNAUTHENTICATED` (HTTP 401), and the same code covers a request whose `X-User-ID` header is absent or cannot be resolved to a live principal. A request that is properly authenticated but attempts an operation the caller's role does not hold is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The five roles are `Driver`, `FleetOpsAgent`, `ComplianceOfficer`, `PlatformAdmin` and `SupportAgent`. They are deliberately segregated: `ComplianceOfficer` decides enrolment outcomes and declares delinquency but holds no fleet dispatch authority; `FleetOpsAgent` owns the fleet surface — admitting units, assigning and swapping them, reporting service events and executing recovery — but cannot decide who is admitted to the programme; `PlatformAdmin` configures the programme, prices buyouts, waives charges and controls the logical clock, but neither decides enrolment outcomes nor dispatches units; `SupportAgent` is read-mostly and collects weekly payments; `Driver` is the renters' own role.

Identity resolution depends on the role. When `X-User-Role` is `Driver`, `X-User-ID` is the `id` of the acting `Driver`, so it must name a driver that actually exists, or the request is rejected as unauthenticated with `ERR_UNAUTHENTICATED` (HTTP 401); ownership checks on any resource that references a `Driver` compare the resource's foreign-key field to `X-User-ID`. When `X-User-Role` is `FleetOpsAgent`, `ComplianceOfficer`, `PlatformAdmin` or `SupportAgent`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity — the server may record it on rows it writes but does not compare it to any entity's `id`. It is recorded as `operator_id` on every row an operation creates, and it is never exposed in a response payload.

The four operations that are ownership-checked — withdrawal from the programme by the driver, and the three driver-facing purchase-option actions of electing, funding escrow and withdrawing an option — admit the owning driver, and are otherwise rejected with `ERR_UNAUTHORIZED` (HTTP 403). Every other operation is gated purely by role membership.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

List-returning endpoints accept two query parameters. `limit` caps the number of items in the page; when omitted it defaults to 10, and the server enforces a floor of 1 and a ceiling of 100. `offset` skips a number of items from the front of the result set and defaults to 0. Neither is a rejection: a `limit` outside the permitted span is clamped into it rather than refused, a negative `offset` is read as 0, and a value that is not a whole number at all is rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a request says otherwise, list results are ordered by creation timestamp in ascending order. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more` alongside the request identifiers, so a caller can walk a result set without a second count query.

### 2.4. Common Resource Properties

Every top-level resource in this API — `Driver`, `DriverEnrollment`, `ProgramVehicle`, `RentalAgreement`, `RentalWeek`, `MaintenanceEvent`, `RentalPayment`, `PurchaseOption`, `PlatformIntegration` and `FleetFact` — carries the same four system-managed properties:

- `id` (string): a server-minted UUID, unique across the resource type, with no type prefix and no embedded semantics. Identifiers are opaque strings of this one form everywhere in the API — there is no separately typed or prefixed identifier shape.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording the last mutation of the row.
- `version` (integer): a monotonically increasing integer that advances by exactly one on every mutation of the row. A row is stamped at version 1 as it is written, so an operation that creates a row and then mutates it again within the same request — opening a weekly period being the clearest case, since the period is created and carried into `OPEN` before the call returns — hands the row back already advanced past that first value.

All ten resource types are fully versioned; none of them is immutable after creation, so `updated_at` and `version` are present on every one of them. For a resource whose natural key is supplied rather than minted — the unit's identification number, the driver's contact email, the driver's platform identity, a region's code — uniqueness is enforced on the submitted value, and a second submission of an already-held value is rejected as malformed rather than as a conflict. A derived field is a mutation like any other: recomputing a computed property on an `RentalAgreement`, on a `RentalWeek`, on a `ProgramVehicle` or on a `PurchaseOption` refreshes that row's `updated_at` and increments its `version`, even when the caller asked for an operation on a different resource in the same family. This matters because the version counters are the substrate for the concurrency guards described in §2.6.

### 2.5. Integer-Cents Money and Rounding Policy

All monetary amounts in this API are integer cents. There are no floating-point dollars anywhere in the contract, and no monetary field is ever returned as a string or with a decimal point. Fees, premiums, allowances, caps, tender amounts, equity credits and escrow balances are all counts of whole cents.

Rounding is therefore the exception rather than the rule, and where it happens it is always the same convention: **round half up** to the nearest whole cent, away from zero. Only four places in the system round at all — the mileage overage on a weekly renewal, the equity share applied to settled periods, the recurring escrow amount derived from that equity share, and the downtime divisor that converts a loaner-covered service window into whole hours — and the last of those rounds to a whole number of hours rather than to cents. Where the mileage overage is taken on a figure that could otherwise go negative, the excess is read as 0 before it is priced, and the equity share and the escrow amount are each clamped at 0 rather than left below it. Every other arithmetic step is exact integer arithmetic, including the two floor divisions inside the platform activity credit, the equity share's own integer division, and the basis-point utilization of a region. Where a computation floors, it floors in the order written, and any cap or floor-clamp is applied after the arithmetic that precedes it.

### 2.6. Version Guards on Agreement and Unit Writes

Three writes in this API are guarded by an optimistic-concurrency check, because each of them reasons about a parent aggregate whose derived figures may have moved since the caller last read it.

Opening a new weekly rental period requires an `expected_agreement_version` field in the request body carrying the caller's last-observed `version` of the target `RentalAgreement`. Electing a purchase option likewise requires `expected_agreement_version` for the agreement behind the option. Reporting a maintenance event requires `expected_vehicle_version` carrying the caller's last-observed `version` of the target `ProgramVehicle`.

In each case the supplied value is compared against the parent row's current `version` at the moment the request is served. A mismatch means another writer has advanced that row since the caller last observed it, and the request is rejected rather than applied: the two agreement-guarded writes fail with `ERR_STALE_AGREEMENT_VERSION` (HTTP 412) and the unit-guarded write fails with `ERR_STALE_VEHICLE_VERSION` (HTTP 412). These fields are mandatory, not optional — there is no "skip the check" mode; a request that omits one, or supplies one that cannot be read as an integer, is rejected with the same stale-version code as a mismatch. Conversely, endpoints that do not appear in this list must not accept a version field at all, and a request that supplies one is an undeclared field and is rejected as malformed. The list is exhaustive: no operation outside these three is version-guarded, including an escrow funding step, which recomputes the agreement's derived figures and advances the agreement's `version` without itself being guarded by one.

### 2.7. The Ordered Validation Sequence

A request is evaluated against a fixed, ordered sequence of guards, and the **first** guard that fails determines the error the caller sees. Order matters here for more than tidiness: a caller who is both unauthenticated and pointing at a non-existent resource should be told about the authentication failure, and a caller who is pointing at a resource that is both frozen and in the wrong state should be told about the freeze. The sequence is:

1. **Role header.** `X-User-Role` must be present and must name one of the five recognised roles. Failure is `ERR_UNAUTHENTICATED` (HTTP 401).
2. **Identity header.** `X-User-ID` must be present for every role, and for `Driver` it must resolve to the `id` of an existing `Driver`. Failure is `ERR_UNAUTHENTICATED` (HTTP 401).
3. **Payload schema.** The body must supply every required field and must not carry any undeclared field. Failure is `ERR_INVALID_REQUEST` (HTTP 400).
4. **Ownership.** For the four ownership-checked operations, the acting `X-User-ID` must own the target resource, or the role must carry override authority. Failure is `ERR_UNAUTHORIZED` (HTTP 403).
5. **Path existence.** The resource addressed by the path must exist. Failure is `ERR_NOT_FOUND` (HTTP 404). This guard also covers the request that is not addressable at all: a path matching no declared route, and a declared path addressed with a method the catalogue does not give it, are both reported as a missing resource with `ERR_NOT_FOUND` (HTTP 404) rather than as a method error.
6. **Referential existence.** Every foreign key in the request body must name an existing row of the referenced resource. Failure is `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404).
7. **State admissibility.** The target resource must be in a state from which the requested operation is declared. Failure is `ERR_INVALID_STATE` (HTTP 409).
8. **Posture freeze.** The agreement's `compliance_posture` must not be `FROZEN`. Failure is `ERR_AGREEMENT_FROZEN` (HTTP 409).
9. **Posture openness.** The purchase stream requires the agreement's `compliance_posture` to be exactly `OPEN`, which is stricter than the not-frozen gate above. Failure is `ERR_POSTURE_NOT_OPEN` (HTTP 409).
10. **Enrolment currency.** The enrolment named by the agreement must be `ACTIVE`. Failure is `ERR_ENROLLMENT_NOT_ACTIVE` (HTTP 409).
11. **Driving record.** The driver's `driving_record_points` must be at most 6 at the instant the enrolment is evaluated. Failure is `ERR_DRIVING_RECORD_INELIGIBLE` (HTTP 422).
12. **Driver standing for dispatch.** The driver's `eligibility_status` must be `ELIGIBLE` before a unit is submitted to the platform, because the platform will not dispatch work to a unit held by a driver who is not in good standing. Failure is `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422).
13. **Activity floor.** The driver's platform activity score must be at least the programme activity floor, which is 50 points and which the organisation's platform configuration delivers as `app_ride_enabled`. Failure is `ERR_PLATFORM_ACTIVITY_INSUFFICIENT` (HTTP 422).
14. **Licence class.** The driver's `license_class` must be `FOR_HIRE` or `COMMERCIAL` before a unit is assigned or submitted for platform qualification. Failure is `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422).
15. **Single-unit rule.** The driver must not already hold a `ProgramVehicle` in `ASSIGNED` status. Failure is `ERR_DRIVER_VEHICLE_CONFLICT` (HTTP 409).
16. **Unit availability.** The named unit must be `AVAILABLE`. Failure is `ERR_VEHICLE_NOT_AVAILABLE` (HTTP 409).
17. **Model qualification.** The unit's `vehicle_class` must be permitted for the activity the platform requires of it, so a unit that only qualifies for delivery activity may not be assigned to a ride-only agreement. Failure is `ERR_MODEL_NOT_QUALIFIED` (HTTP 409).
18. **Week ordinal.** The operation must not leave two `RentalWeek` rows of the same agreement sharing one `week_number`. Failure is `ERR_WEEK_OVERLAP` (HTTP 409).
19. **Term bound.** The weekly period that would be opened, running from the logical clock instant for seven days, must not extend past the agreement's `period_end`. Failure is `ERR_WEEK_OUTSIDE_AGREEMENT_TERM` (HTTP 422).
20. **Occupancy overlap.** The requested rental interval must not collide with an existing occupancy interval on the same unit. Intervals are half-open: a new interval that starts exactly at an existing interval's `period_end` does not collide. Failure is `ERR_VEHICLE_INTERVAL_OVERLAP` (HTTP 409).
21. **Recovery quiet period.** A maintenance event may not be reported against a unit whose recovery interval is still open — that interval runs from the instant the unit entered `RECOVERY` through 24 hours after it last returned to `AVAILABLE`. Failure is `ERR_MAINTENANCE_WINDOW_CONFLICT` (HTTP 409).
22. **Grace lapse.** The logical clock must be at or past the week's `grace_deadline` before the week may be declared delinquent. Failure is `ERR_GRACE_NOT_LAPSED` (HTTP 422).
23. **Purchase cleanliness.** The purchase election is blocked while any week of the agreement is `DELINQUENT`. Failure is `ERR_PURCHASE_BLOCKED_BY_DELINQUENCY` (HTTP 409).
24. **Escrow completeness.** The option's `escrow_weeks_funded` must have reached its `escrow_weeks_required`. Failure is `ERR_ESCROW_INCOMPLETE` (HTTP 422).
25. **Tender sufficiency.** On a tender that is neither a partial tender nor a retry of a failed tender, the tendered amount plus the applied platform credit must be at least the week's `amount_due_cents`. Failure is `ERR_PAYMENT_BELOW_AMOUNT_DUE` (HTTP 402).
26. **Recovery closure.** The agreement's recovered-week set must still be open, so recovery has not already been executed. Failure is `ERR_RECOVERY_ALREADY_CLOSED` (HTTP 409).
27. **Agreement version.** `expected_agreement_version` must match the agreement's `version`. Failure is `ERR_STALE_AGREEMENT_VERSION` (HTTP 412).
28. **Unit version.** `expected_vehicle_version` must match the unit's `version`. Failure is `ERR_STALE_VEHICLE_VERSION` (HTTP 412).

The scope of each guard is fixed, and the scope is as binding as the condition itself. Guards 1 through 7 are universal: they apply to every call, and guards 5 and 6 in particular apply to every path-addressed call and to every call whose body carries a foreign key. The freeze gate, guard 8, bars six operations — opening a weekly period, settling a week, reporting a maintenance event, issuing a loaner, completing an agreement, and electing a purchase option — and on that sixth operation it is evaluated ahead of guard 9, so a frozen agreement presented for an election is reported as the freeze rather than as an openness failure. The openness gate, guard 9, bars exactly two — offering a purchase option and electing one. The enrolment-currency gate, guard 10, bars activation only. The driving-record ceiling, guard 11, bars enrolment only. The dispatch-standing gate, guard 12, bars the platform-qualification submission only. The activity floor, guard 13, bars enrolment and the platform-qualification submission. The licence-class gate, guard 14, bars agreement creation, agreement activation and the platform-qualification submission. The single-unit gate, guard 15, bars agreement creation and agreement activation. The availability gate, guard 16, bars agreement creation, agreement activation and a vehicle swap. The model-qualification gate, guard 17, bars agreement creation, a vehicle swap and the platform-qualification submission. The week-ordinal gate, guard 18, bars opening a weekly period and a vehicle swap. The term-bound gate, guard 19, bars opening a weekly period only. The occupancy-overlap gate, guard 20, bars agreement creation and a vehicle swap. The recovery quiet-period gate, guard 21, bars reporting a maintenance event only. The grace-lapse gate, guard 22, bars declaring a week delinquent only. The purchase-cleanliness gate, guard 23, bars electing a purchase option only. The escrow-completeness gate, guard 24, bars completing a purchase option only. The tender-sufficiency gate, guard 25, bars tendering a weekly payment and retrying a failed tender. The recovery-closure gate, guard 26, bars executing vehicle recovery only. The agreement-version gate, guard 27, bars opening a weekly period and electing a purchase option. And the unit-version gate, guard 28, bars reporting a maintenance event only.

The numbered sequence gives the order in which the guards are declared, and it is the order a caller may rely on with only these stated exceptions, each of which a caller can observe. On opening a weekly period, on settling a week and on completing an agreement the freeze gate (8) is evaluated ahead of the state gate (7), so an agreement that is both frozen and in an inadmissible lifecycle state is reported as the freeze. On executing a recovery the recovery-closure gate (26) is evaluated ahead of the state gate (7), so a replay of an already-executed recovery is reported as a closed recovered-week set rather than as an inadmissible state. And on the platform-qualification submission the dispatch-standing gate (12) is evaluated last of that path's guards, after the activity floor (13), the licence class (14) and the model qualification (17) — so a driver who is both out of standing and below the floor is told about the floor, and a unit whose class is permitted for neither activity is told about its class rather than about the driver.

### 2.8. The Assigned-Fleet-Units Invariant

The programme maintains a single count of units it is responsible for: a unit is either held by a driver, parked in the available pool, or parked in the recovery pool, and never two of those at once. Servicing a unit threatens that count, because a unit in `MAINTENANCE` is nominally still assigned to its driver while contributing nothing to that driver's earning capacity. The programme therefore treats a loaner as a *substitute* for the unit under repair rather than as an additional assignment: issuing a loaner flips the loaner from `AVAILABLE` to `ASSIGNED` and stamps the agreement's driver onto it, so the number of assigned units across the fleet is conserved even though the driver now nominally controls two units. It follows that the single-unit rule of §3.3 must read the driver's holding as exclusive of loaners — a unit currently on loan to the driver is a substitute for their own unit rather than a second assignment, so it is not itself a holding. Completing the service event performs the compensating action — the loaner is released back to `AVAILABLE` with its driver reference cleared, and the original unit, restamped to `ASSIGNED`, resumes the assignment.

The invariant is enforced by refusal, not by substitution. If no conforming unit exists to serve as a loaner, the loaner step is simply unavailable and the request is rejected with `ERR_LOANER_UNAVAILABLE` (HTTP 409); the programme never fabricates a unit, never promotes a non-conforming unit, and never quietly leaves the driver without cover.

### 2.9. The Logical Clock

Time in this API is not wall-clock time. The server reads a **logical clock** whose initial value is `2026-09-01T00:00:00Z`, and every timestamp the programme stamps — a weekly period boundary, a payment deadline, a verification instant, a loaner deadline — is derived from that clock. The server never falls back to the host's real time, so a test run is reproducible regardless of when it executes.

Only an administrator may move the clock, by supplying a destination instant as `to_iso8601`; the call returns the new clock value as `current_utc`. Advancing the clock is not a passive bookkeeping operation: every time-gated transition whose deadline the new instant reaches is applied as part of that call. Advancing the clock past a week's `payment_deadline` therefore moves that week into grace without any further request from a caller. That is the one transition the advance carries: a week standing in `DUE` whose `payment_status` is not `SETTLED`, and whose `payment_deadline` the new instant has reached, becomes `GRACE`. A week in any other status is left where it is — a week already collected, waived or recovered does not move, and a week whose `payment_status` is already `SETTLED` does not move either, since there is nothing left to be in grace about. The other deadlines the programme stamps — a week's `grace_deadline`, a loaner's `loaner_deadline` — are read by the operations that consult them rather than crossed by the advance itself, so a lapsed grace period still has to be declared delinquent deliberately, and the clock moving does not by itself close a loaner.

### 2.10. Path Resolution for Nested Lookups

Resources in this API are addressed by their own `id`, and several paths carry a single identifier in the position the catalogue calls `{id}`. Where a path carries more than one identifier — for example a sub-collection scoped by its owner — the identifiers are resolved in a strict left-to-right order, and the request is rejected at the *first* identifier that does not correspond to an existing row. The error reported in that case is `ERR_NOT_FOUND` (HTTP 404) for the missing segment, and the caller learns nothing about whether the deeper segments would have resolved. This left-to-right discipline, combined with the ordering in §2.7 (existence before state), means a caller can rely on a definite consequence: a request that names a non-existent parent is rejected for the parent, not for a deeper cause. It is worth noting what the discipline does not cover: a resource whose own existence is checked only as part of resolving its place in a hierarchy is still reported with the same `ERR_NOT_FOUND` (HTTP 404), and a body-supplied reference is reported under the referential-existence guard with `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404) instead — the two 404 codes differ only in whether the missing identifier arrived in the path or in the body.

## 3. Business Logic & Workflows

### 3.1. Programme Enrolment and Eligibility Determination

Every relationship in the programme begins with a **driver record**. When a `PlatformAdmin` registers a driver, the payload carries the driver's legal name as `full_name`, a contact email as `email`, the external rideshare-platform identity used for activity verification as `platform_driver_id`, the driver's latest platform activity score as `platform_activity_score`, accumulated driving-record points as `driving_record_points`, the licence class presented at enrolment as `license_class`, and the programme tier at admission as `program_driver_tier`. The `email` is unique across drivers under a case-insensitive comparison, so two registrations differing only in letter case are the same registration, and the address must take the shape of one local part, an `@`, and one dotted domain with no spaces anywhere. The `platform_driver_id` must be formatted as the literal prefix `PLT-` followed by eight alphanumerics, and it too is unique across drivers; both a malformed address and a re-used `email` or `platform_driver_id` — the latter matched case-sensitively — are rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400), never as a conflict. The `platform_activity_score` is a whole number from 0 through 100 inclusive; `driving_record_points` is a whole number from 0 through 12 inclusive; `license_class` is exactly one of `STANDARD`, `FOR_HIRE` or `COMMERCIAL`; and `program_driver_tier` is exactly one of `TIER_1`, `TIER_2` or `TIER_3`, with the driver's `program_driver_tier` recorded on the row exactly as submitted. A newly registered driver starts with `eligibility_status` of `PENDING`.

The derived `eligibility_status` is recomputed by the eligibility-score calculation, whose only possible values are `PENDING`, `ELIGIBLE`, `INELIGIBLE` and `SUSPENDED`. Freshly entered drivers sit at `PENDING`; drivers admitted to the programme sit at `ELIGIBLE`; drivers whose application was refused, or who left the programme and hold no other active enrolment, sit at `INELIGIBLE`; and drivers whose agreement has been frozen sit at `SUSPENDED`. The derivation reads the driver's enrolments in a fixed order of precedence: any `SUSPENDED` enrolment yields `SUSPENDED`; otherwise any `ACTIVE` enrolment yields `ELIGIBLE`; otherwise, where the driver holds enrolments and every one of them is `WITHDRAWN`, the posture is `INELIGIBLE`; otherwise any `REJECTED` enrolment yields `INELIGIBLE`; and a driver holding no enrolment, or holding only an enrolment still at `PENDING_VERIFICATION`, sits at `PENDING`. This precedence, and not the enrolment that happens to be newest, is what the posture reflects when a driver holds several enrolments.

**Enrolling a driver.** Enrolment is the work of a `ComplianceOfficer`, who names the driver as `driver_id` and requests a tier as `program_tier`. The server captures the driver's current `platform_activity_score` as `activity_snapshot` and their `driving_record_points` as `record_snapshot`, then runs the eligibility-score calculation against the driver to produce `eligibility_score`, a composite score in the range 0 through 100, and records `eligibility_decision`. The enrolment itself opens with `enrollment_status` at `PENDING_VERIFICATION`, and — importantly — enrolment is the one operation where the raw licence class is *not* consulted; the driving record is what gates it. Recording an enrolment does not itself admit the driver: their `eligibility_status` is left at `PENDING` until the enrolment is verified, so the decision recorded at evaluation time is a reading held on the enrolment rather than a change of standing. A driver whose accumulated record points exceed 6 at the instant of evaluation is refused outright with `ERR_DRIVING_RECORD_INELIGIBLE` (HTTP 422), and a driver whose platform activity score sits below the programme's activity floor of 50 points is refused with `ERR_PLATFORM_ACTIVITY_INSUFFICIENT` (HTTP 422). Note that `program_driver_tier` accepted on a driver record and `program_tier` requested on an enrolment are separate inputs: the enrolment's requested tier is the one the evaluation reasons about, and it is the value that is eventually written back onto the driver when the enrolment is verified.

The composite score starts at 100 and is reduced according to the driver's accumulated driving-record points, in three bands. At 3 points or fewer, the deduction is 5 points per point on the record. Between 4 and 6 points inclusive, the deduction is a flat 15 points for the first tier plus 10 points for each point above 3. Above 6 points, the deduction is a flat 15 points plus a flat 30 points plus 20 points for each point above 6. The result is then clamped so it never falls below zero. Only after that floor is applied does the escalation bonus get considered: if the floored score is 40 or less *and* the driver's platform activity score is at least 90, 15 points are added back. The score is then clamped so it never exceeds 100. The two clamps are not interchangeable — the lower clamp runs before the bonus and the upper clamp after it — which is why a driver with 4 record points and an activity score of 95 ends at 75, since the bonus requires the floored score to be 40 or below and that driver floors at 75. A driver with 8 record points and an activity score of 90 ends at 30: the first two bands contribute 45 points of deduction, the third band adds 40 more, the floor leaves 15, and the bonus lifts it to 30.

The `eligibility_decision` follows directly from the finished `eligibility_score` and the activity reading. An application is `APPROVED` when the score is at least 60 and the activity score is at least 70. It is `DEFERRED` when the score is at least 60 but the activity score falls short of 70 — the driver is welcome but not yet at the activity level the programme wants. It is `DENIED` when the score itself falls below 60.

**Verifying an enrolment.** Verification is a separate, deliberate step taken by a `ComplianceOfficer`, and the decision recorded at evaluation time is what drives it. It is available only while `enrollment_status` is `PENDING_VERIFICATION`; against any other state the operation is unavailable and is rejected as an inadmissible state with `ERR_INVALID_STATE` (HTTP 409). An `APPROVED` enrolment moves `enrollment_status` from `PENDING_VERIFICATION` to `ACTIVE`, the driver's `eligibility_status` moves from `PENDING` to `ELIGIBLE`, and `verified_at` is stamped with the logical clock instant. A `DEFERRED` enrolment is admitted on exactly the same terms as an approved one — the driver is welcome, the enrolment reaches `ACTIVE` with `verified_at` stamped, and the driver's `eligibility_status` moves to `ELIGIBLE` — because deferral speaks only to the driver's activity reading sitting below the level the programme prefers, not to their admissibility. A `DENIED` enrolment moves `enrollment_status` from `PENDING_VERIFICATION` to `REJECTED` and pushes the driver's `eligibility_status` from `PENDING` to `INELIGIBLE`.

**Re-evaluation.** A refused enrolment is not a dead end. A `ComplianceOfficer` may re-evaluate it — an operation available only while `enrollment_status` is `REJECTED`, and rejected with `ERR_INVALID_STATE` (HTTP 409) from any other state — which returns `enrollment_status` from `REJECTED` to `PENDING_VERIFICATION`, returns the driver's `eligibility_status` to `PENDING`, refreshes `activity_snapshot` and `record_snapshot` from the driver's *current* `platform_activity_score` and `driving_record_points`, and reruns the eligibility-score calculation into `eligibility_score` so a driver who has cleaned up their record or lifted their activity since the refusal gets a fresh decision. This is an explicitly cyclic edge in the enrolment lifecycle: refused, re-evaluated, re-evaluated again, until either the driver is admitted or the enrolment is abandoned.

**Withdrawal.** A driver leaving the programme, or a `ComplianceOfficer` withdrawing an active or suspended enrolment on the driver's behalf, is refused while any agreement of that enrolment still holds occupancy. Occupancy-holding agreement states are `ACTIVE`, `RENEWAL_DUE`, `DELINQUENT`, `RECOVERY_PENDING` and `PURCHASE_PENDING`; an agreement in any other state — `DRAFT`, `RECOVERED`, `COMPLETED`, `PURCHASED` — does not block withdrawal. When the withdrawal succeeds `enrollment_status` reaches `WITHDRAWN`, which is its only terminal state, and if the driver holds no other `ACTIVE` enrolment their posture is forced to `INELIGIBLE`. Withdrawal is one of the four ownership-checked operations: a driver may withdraw only their own enrolment, an attempt on another driver's being rejected with `ERR_UNAUTHORIZED` (HTTP 403), while a `ComplianceOfficer` carries override authority and may withdraw any enrolment. The operation is available only while `enrollment_status` is `ACTIVE` or `SUSPENDED`; against any other state it is unavailable and is rejected with `ERR_INVALID_STATE` (HTTP 409).

### 3.2. Standing Data Changes and the Platform Activity Credit

Drivers' circumstances move, and the API exposes two ways to record that. A `PlatformAdmin` or `ComplianceOfficer` may post a new `platform_activity_score`, or post fresh `driving_record_points`, and in both cases the effect ripples further than the driver row. The eligibility-score calculation is rerun for every non-terminal enrolment belonging to that driver — an enrolment is non-terminal unless it has reached `WITHDRAWN`, and a withdrawn enrolment keeps its recorded snapshots and decision untouched — and the driver's derived eligibility posture is refreshed afterwards from the precedence stated in §3.1. This is also a quiet guard against stale admissions: a driver admitted at an activity score of 80 who later drifts down to 40 has their posture recomputed on the spot, without waiting for anyone to re-evaluate the enrolment explicitly.

A driver's computed summary read the driver's standing together with their current holding. `outstanding_balance_cents` is the sum of `amount_due_cents` across every week of every agreement the driver holds whose `week_status` is not one of the terminal `PAID`, `WAIVED` or `RECOVERED` — so a week still in `DRAFT`, metering or deferral counts toward the balance alongside one in `DUE`, `GRACE` or `DELINQUENT`. `active_enrollment_id` is the driver's earliest-enrolled `ACTIVE` enrolment, or empty when there is none; `assigned_vehicle_id` is the unit currently stamped with the driver's `assigned_driver_id` at `ASSIGNED` status, or empty when there is none; and `open_week_number` is the `current_week_number` of the driver's most recently created occupancy-holding agreement, or 0 when the driver holds none.

The same activity reading feeds the **platform activity credit**, the mechanism by which the programme gives a driver a weekly rebate against their rental in proportion to how much platform work they have been doing. The credit is computed against the credit bands and the driver's programme tier, and it is expressed in whole cents.

The band arithmetic is marginal and cumulative. A driver whose activity score is below the programme floor of 50 points earns nothing at all. A driver at 50 points through 74 points earns 10 cents for each point from 50 up to and including their score — so the band credits a point sitting exactly at 50, and a score of 60 yields 110 cents. A driver at 75 points or above earns the full 50-to-74 band, which is 25 qualifying points at 10 cents each for 250 cents, plus 10 cents multiplied by *three halves* for each point from 75 up to and including their score, with the multiplication floored to a whole number of cents as it is applied. A score of exactly 75 therefore adds one point's worth of the escalated band for 15 cents, bringing the running total to 265 cents, and a score of 100 adds the full 26-point escalated band for 390 cents, bringing the raw total to 640 cents. A driver on `TIER_3` receives a further benefit: once the band sum is complete, the whole of it is multiplied by *five quarters* and floored, applied exactly once and applied after — never before — the band sum is finished. Finally the result is capped at 600 cents. So the driver scoring 100 has their 640 cents trimmed to the 600-cent cap, and a `TIER_3` driver at 60 points has their 110 cents lifted to 137 cents.

Two distinct readings of that credit must not be confused. The **platform credit** is a statement about the driver's activity level: it is the figure the band arithmetic produces, and it is the figure the weekly renewal always carries — re-read from the driver's current activity level wherever the provisional charge is computed, which is at the moment a week is opened and again whenever mileage is recorded against a week still `OPEN`, so the credit on a week in flight tracks the driver's standing, while the credit a settled week was billed with is left exactly as it stood. The **renewal credit** is a statement about money actually collected: it counts only the payments whose `payment_outcome` is `SUCCEEDED` and that were applied to a week which has since reached the terminal `PAID`, `RECOVERED` or `WAIVED` status, each such payment contributing its `coverage_cents` — so a week that was only partially tendered contributes just the coverage allocated to it and a payment recorded against a week still short of a terminal status contributes nothing at all, while a week that was waived contributes nothing because no payment ever settled it. The renewal credit is reported to the driver on the agreement summary alongside `outstanding_delinquent_weeks`, `escrow_balance_cents` and the agreement's `current_week_number`, `agreement_status`, `compliance_posture`, `total_billed_cents`, `total_waived_cents` and `equity_credit_cents` — the last two reads, of equity and escrow, being live recomputations off the agreement's settled weeks rather than whatever was last written onto an option row — and it is *never* written back into `platform_credit_cents`. That field always holds the activity-based figure.

### 3.3. Fleet Intake, Model Qualification and Assignment of a Unit

The fleet side of the programme begins with **admitting a unit**. A `FleetOpsAgent` registers a programme vehicle with its identification number as `vin`, its model designation as `model_name`, its model year as `model_year`, its programme class as `vehicle_class`, its current odometer reading as `odometer_miles`, and the region it is allocated to as `region_code`. `vin` is exactly 17 characters and is unique across the fleet. `model_year` must fall between 2018 and 2027 inclusive. `odometer_miles` must be zero or greater, and it is expected to be monotonically non-decreasing — the only way it may go backwards is through an explicit compensation. `region_code` is a two-letter uppercase code. `vehicle_class` is exactly one of `STANDARD`, `XL`, `LUXURY` or `DELIVERY_VAN`, and that single field determines which kinds of platform work the unit may serve: it is the sole input to the derived `qualifies_ride` and `qualifies_delivery` flags that the qualification check later reads. Admission is the moment `baseline_odometer_miles` is pinned: it is stamped from the `odometer_miles` supplied at intake, and it exists so that mileage invariants can reconcile later even after the unit has been swapped, serviced and reassigned. A newly admitted unit sits with `vehicle_status` at `AVAILABLE`, and `assigned_driver_id` is empty.

The derived `vehicle_status` takes exactly one of five values: `AVAILABLE`, `ASSIGNED`, `MAINTENANCE`, `RECOVERY` or `RETIRED`. A unit moves to `ASSIGNED` when an agreement takes it, to `MAINTENANCE` when it is taken out of service for repair, to `RECOVERY` when its agreement is frozen or being escalated, and to `RETIRED` when it is bought out and leaves the rental fleet permanently. `assigned_driver_id` holds the driver currently holding the unit, or nothing when the unit is unassigned.

**Qualification for platform activity.** Before a unit can carry platform work, it is submitted for a qualification check by a `ComplianceOfficer`, naming the agreement it serves as `agreement_id` and the unit itself as `vehicle_id`. The recorded `integration_result` is derived purely from `vehicle_class`, and its evaluation order is pinned so the answer is deterministic. `ride_qualified` is true when the class is `STANDARD`, `XL` or `LUXURY` — three classes. `delivery_qualified` is true when the class is `STANDARD`, `XL` or `DELIVERY_VAN` — also three classes. `model_restriction_hit` is set whenever the unit fails either of those two predicates. The verdict itself is then assigned in this order: a unit that passes both predicates is `QUALIFIED`; a unit that fails both is `REJECTED_MODEL`; a unit that passes delivery but fails ride is `REJECTED_RIDE`; and a unit that passes ride but fails delivery is `REJECTED_DELIVERY`. The ordering matters because a class that fails both predicates must be reported as the model restriction rather than as either of the single-activity rejections, and because `LUXURY` and `DELIVERY_VAN` are each one-sided — a `LUXURY` unit will never qualify for delivery work and a `DELIVERY_VAN` unit will never qualify for ride work, so both land on a single-activity rejection rather than on the model verdict. The check records `integration_result`, `ride_qualified`, `delivery_qualified`, `model_restriction_hit` and `checked_at`; a `ComplianceOfficer` may re-run a recorded check, which recomputes `integration_result`, `ride_qualified`, `delivery_qualified` and `model_restriction_hit` from the unit's current class and restamps `checked_at` from the logical clock, leaving the agreement and unit the check names untouched.

Three conditions gate the submission itself, and the unit's class is settled before any of the driver conditions is reached. The unit must be permitted for platform activity at all — a class that serves neither ride nor delivery work is refused with `ERR_MODEL_NOT_QUALIFIED` (HTTP 409) — and, because the requirement this submission is presented against is a ride requirement, a unit that does not qualify for ride work is refused with `ERR_MODEL_NOT_QUALIFIED` (HTTP 409) as well, so even a class that qualifies for delivery alone never reaches a recorded check and its always-one-sided verdict is reported as a refusal rather than as the recorded `REJECTED_RIDE`. Only then is the driver consulted: their platform activity score must be at least the activity floor of 50 points, or the request is rejected with `ERR_PLATFORM_ACTIVITY_INSUFFICIENT` (HTTP 422); their licence class must be `FOR_HIRE` or `COMMERCIAL`, or the request is rejected with `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422); and the driver behind the unit must be in `ELIGIBLE` standing, because the platform will not dispatch work to a unit held by a driver who is not, or the request is rejected with `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422).

**Creating the rental agreement.** A `FleetOpsAgent` creates an agreement by naming the authorising enrolment as `enrollment_id`, the driver who will hold it as `driver_id`, the unit being assigned as `vehicle_id`, the recurring weekly rate as `weekly_rate_cents`, the weekly insurance premium as `insurance_premium_cents`, the mileage provisions, and the contractual period as `period_start` and `period_end`. `weekly_rate_cents` and `insurance_premium_cents` are both whole cents and neither may be negative. The mileage provision has two shapes. If `unlimited_mileage` is false the agreement is metered: it carries `mileage_cap_miles` as its included weekly mileage and the driver pays for anything beyond it. If `unlimited_mileage` is true that cap is not applicable and the weekly rate already covers all mileage; the flag defaults to false, so an omitted flag means the metered shape and `mileage_cap_miles` is the operative provision. `maintenance_allowance_miles` — the mileage credited against wear, and the pool that absorbs damage liability later — is a non-negative whole number of miles. Both period bounds are supplied by the caller and must be ISO 8601 instants, with `period_end` falling strictly after `period_start`; a bound that cannot be read as an instant, or an interval that does not run forwards, is rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400), as is a mileage provision that is not a whole number, a negative rate or premium, or a metered agreement offered without a `mileage_cap_miles`, since the flag defaults to false and an omitted cap therefore leaves a metered agreement without its operative provision. Together the two bounds define the occupancy interval the agreement reserves on the unit. The named enrolment, driver and unit must each exist, or the request is rejected with `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404).

An agreement opens with `agreement_status` at `DRAFT` and `compliance_posture` at `OPEN`. Its derived counters begin at zero: `current_week_number` is 0, `total_billed_cents` is 0 and `total_waived_cents` is 0. A `DRAFT` agreement is not yet live — it holds no unit and bills nothing. Creation is itself gated: the driver may not already hold a unit in `ASSIGNED` status, or the request is rejected with `ERR_DRIVER_VEHICLE_CONFLICT` (HTTP 409) — a unit that is currently out on loan to that driver being a substitute rather than a second holding, so it does not count against the rule — the named unit must be `AVAILABLE`, or the request is rejected with `ERR_VEHICLE_NOT_AVAILABLE` (HTTP 409); the unit's class must be permitted for the activity the agreement will require, or the request is rejected with `ERR_MODEL_NOT_QUALIFIED` (HTTP 409); the requested interval must not collide with an existing occupancy interval on that unit, or the request is rejected with `ERR_VEHICLE_INTERVAL_OVERLAP` (HTTP 409); and the driver's licence class must be `FOR_HIRE` or `COMMERCIAL`, or the request is rejected with `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422).

**Activation.** Moving an agreement from `DRAFT` to `ACTIVE` is what actually puts a unit on the road, and it is reserved to a `FleetOpsAgent`. Three things must be true first: the authorising enrolment's `enrollment_status` must be `ACTIVE`, or the request is rejected with `ERR_ENROLLMENT_NOT_ACTIVE` (HTTP 409); the driver's `eligibility_status` must be `ELIGIBLE`, or the request is rejected with `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422); and the named unit's `vehicle_status` must still be `AVAILABLE`, or the request is rejected with `ERR_VEHICLE_NOT_AVAILABLE` (HTTP 409). The driver must also still be free of any other assigned unit, or the request is rejected with `ERR_DRIVER_VEHICLE_CONFLICT` (HTTP 409), and their licence class must still be `FOR_HIRE` or `COMMERCIAL`, or the request is rejected with `ERR_DRIVER_NOT_ELIGIBLE` (HTTP 422). On success `vehicle_status` is flipped from `AVAILABLE` to `ASSIGNED`, `assigned_driver_id` is stamped with the driver, `baseline_odometer_miles` is restamped to the unit's current `odometer_miles` so the new rental term starts from a clean mileage origin, `compliance_posture` is set to `OPEN`, and `current_week_number` is reset to 0. Activation is where a re-let unit's mileage ledger is cut over, which is precisely why the baseline is repinned here rather than left at the fleet-intake value.

**Swapping units.** A `FleetOpsAgent` may move an agreement onto a different unit by naming `new_vehicle_id`. The swap respects the same restrictions as assignment: the replacement's `vehicle_status` must be `AVAILABLE`, or the request is rejected with `ERR_VEHICLE_NOT_AVAILABLE` (HTTP 409); its class must be permitted for the agreement's required activity, or the request is rejected with `ERR_MODEL_NOT_QUALIFIED` (HTTP 409); the interval it would occupy must not collide with another occupancy interval, or the request is rejected with `ERR_VEHICLE_INTERVAL_OVERLAP` (HTTP 409); and the swap must not leave two weeks of the agreement sharing one `week_number`, or the request is rejected with `ERR_WEEK_OVERLAP` (HTTP 409) — that ordinal check being taken ahead of the overlap check that follows it, so an agreement whose weeks already collide is told about the ordinal. On success the outgoing unit's `vehicle_status` is released to `AVAILABLE`, the incoming unit is set to `ASSIGNED` with `assigned_driver_id` stamped onto it, and the incoming unit's `baseline_odometer_miles` is restamped — again, because the mileage ledger follows the unit rather than the driver.

### 3.4. The Rental Term, Occupancy and the Weekly Period

An agreement's contractual bounds are its agreed `period_start` and `period_end`, and the interval they describe is the **occupancy interval** reserved on the unit. Occupancy intervals are half-open on both bounds: a new interval that begins exactly at another interval's `period_end` does not collide with it, while one that begins strictly before that instant does. This is what allows the same unit to be re-let back-to-back without an artificial gap, and it is also the rule behind the `ERR_VEHICLE_INTERVAL_OVERLAP` rejection that guards agreement creation and swaps.

Inside that term, the programme meters and bills in **weekly rental periods**, and each period is its own row. A period records the agreement it belongs to as `agreement_id`, the unit the mileage accrued against as `vehicle_id`, its own ordinal as `week_number`, its own `period_start` and `period_end`, and the miles recorded for it as `miles_driven` — a non-negative whole number defaulting to 0 when nothing has been reported yet. It then carries the money broken out into components: `base_charge_cents`, `insurance_charge_cents`, `mileage_overage_cents`, `damage_charge_cents` and `platform_credit_cents`, and finally `amount_due_cents`. The net amount and the recorded mileage both begin at 0 until the period is metered. The period also carries the two deadlines that govern its collections — `payment_deadline`, the instant payment becomes due, and `grace_deadline`, the instant the grace period lapses — and two independent lifecycle dimensions: `week_status` and `payment_status`.

`week_status` takes exactly one of `SCHEDULED`, `OPEN`, `DUE`, `PAID`, `GRACE`, `DELINQUENT`, `DEFERRED`, `RECOVERED` or `WAIVED`, and a period begins life at `SCHEDULED`. Its terminal values are `PAID`, `RECOVERED` and `WAIVED`; every other value in the set is still in flight. `payment_status` takes exactly one of `UNPAID`, `PARTIAL`, `SETTLED` or `FAILED` and starts at `UNPAID`. These two dimensions evolve independently on the very same row, and conflating them is a mistake the contract explicitly forbids: a period can be `GRACE` in status while `UNPAID` in payment, or `DELINQUENT` in status while `FAILED` in payment, and the transitions of one dimension never imply the transitions of the other.

**Opening the next period.** A `FleetOpsAgent` opens the next weekly period by naming the agreement and supplying `expected_agreement_version` carrying their last-observed version of that agreement — this is the guard described in §2.6, and a stale value is rejected with `ERR_STALE_AGREEMENT_VERSION` (HTTP 412) before anything else about the request is considered. The agreement must be in `ACTIVE` or `RENEWAL_DUE`; it must not be `FROZEN` in posture, or the request is rejected with `ERR_AGREEMENT_FROZEN` (HTTP 409); and the seven-day period that would be opened, running from the logical clock instant, must not extend past the agreement's `period_end`, or the request is rejected with `ERR_WEEK_OUTSIDE_AGREEMENT_TERM` (HTTP 422). The operation must also not leave two periods of the agreement sharing one ordinal, or the request is rejected with `ERR_WEEK_OVERLAP` (HTTP 409).

On success a period is created and, within the same request, walks straight from `SCHEDULED` to `OPEN` without the caller doing anything further — the opening is the one place that transition happens implicitly, and the call responds with the newly created period and a `201 Created`. The new period's `week_number` is one greater than the agreement's `current_week_number`, and the agreement's counter is advanced to match. Its start instant is the logical clock instant and its end instant is exactly seven days later. The provisional renewal charge is computed at this moment — that is, before any miles are known — and `agreement_status` is moved to `RENEWAL_DUE`. The agreement's `version` advances by one as part of the operation, and the new period leaves `payment_status` at `UNPAID` with both `payment_deadline` and `grace_deadline` still empty, since those two are stamped only when the week is settled.

There is a subtlety worth stating plainly: opening the next period is *not* blocked by an unsettled prior period. An agreement already in `RENEWAL_DUE` may have another period opened against it, and doing so leaves the agreement in `RENEWAL_DUE` while still creating and opening the new period, advancing the ordinal, incrementing the version, and computing the provisional charge. A driver who is behind on one week can therefore keep renting into the following week — which is exactly what makes the delinquency and recovery machinery in §3.8 necessary rather than redundant.

### 3.5. Metering and Settling a Week

A week's money is computed twice, and the two computations are two variants of the same rule rather than two rules. The evaluation order is pinned and must be followed literally: base first, then insurance, then mile overage, then damage, then platform credit, and finally the net amount owed.

In the **provisional variant**, the week enters `OPEN` while the mile cycle is still open. `base_charge_cents` is the agreement's `weekly_rate_cents` and `insurance_charge_cents` is the agreement's `insurance_premium_cents`, both carried across unchanged. Because no mileage has been closed, `mileage_overage_cents` is 0 and `damage_charge_cents` is 0, so `amount_due_cents` is simply the weekly rate plus the premium minus `platform_credit_cents`.

Mileage is recorded against the open week by a `FleetOpsAgent` or a `ComplianceOfficer`, either from the platform trip feed or from a manual submission, by supplying `miles_driven` as a non-negative whole number — anything else being rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400). Recording mileage updates `miles_driven` and recomputes the renewal charge — still in the provisional variant, while the week remains `OPEN`, so the charge stays the flat rate-and-premium figure until the mile cycle closes. The recorded figure is what settlement will eventually price. The write is admitted against a week in any status; where the week is no longer `OPEN` the recorded figure is stored but no charge is recomputed, because the mile cycle has already closed and the billed figures stand.

In the **final variant**, a `ComplianceOfficer` settles the week, closing the mile cycle and billing it. Settlement requires that `week_status` is `OPEN`; that the agreement's `compliance_posture` is not `FROZEN`, or the request is rejected with `ERR_AGREEMENT_FROZEN` (HTTP 409); and that the mile cycle for the week is closed. The final computation writes all four money components at once. `base_charge_cents` is again the agreement's `weekly_rate_cents`, and `insurance_charge_cents` is again `insurance_premium_cents`. `mileage_overage_cents` is zero when `unlimited_mileage` is true; otherwise the programme takes the `miles_driven` actually recorded beyond the agreement's `mileage_cap_miles` — counting only the excess, and treating a week driven entirely within the allowance as having no excess at all — and multiplies that excess by the programme's overage rate of 25 cents per mile, rounding half up to a whole cent. `platform_credit_cents` is the activity credit described in §3.2, and it is not recomputed away by settlement: the amount the week was provisionally carrying stands, even if the driver's activity reading has since moved. `damage_charge_cents` carries the settled damage liability computed by the damage apportionment described in §3.7. `amount_due_cents` is the base plus the insurance plus the mile overage plus the damage, minus the platform credit.

The order in which the final variant is assembled is itself fixed: the base, insurance and mileage-overage figures are written first, the platform credit is read for the week, and only then is the damage liability apportioned into `damage_charge_cents` from the agreement's `DAMAGE_REPAIR` events that name this week — after which the net amount owed is finally struck. Nothing is billed until the net figure is written, and the settlement is one mutation of the week.

Because the final variant brings in mileage and damage that the provisional variant does not, a settled week always yields an amount owed strictly greater than the figure the week showed while provisionally open, whenever the driver exceeded their included mileage or any damage liability was settled onto the week. When the driver stayed within the allowance and no damage was apportioned, the two figures coincide.

Settlement also stamps the two collection deadlines. `payment_deadline` is the week's own `period_end`. `grace_deadline` is the payment deadline plus 72 hours. `week_status` then moves from `OPEN` to `DUE`, which is the signal that the amount owed is now a live receivable.

### 3.6. Collection, Partial Tenders and Failed Tenders

Once a week is `DUE`, a `SupportAgent` or a `PlatformAdmin` collects against it. A tender carries the amount being offered as `amount_cents` and the outcome the collection channel reported as `payment_outcome`, and it may optionally carry the caller's expectation of the outstanding amount as `expected_amount_due_cents`; that expectation is accepted and carried through the request but is never compared against the week's figure, so a stale expectation is not by itself a reason to refuse a tender — the sufficiency rule stated below is what governs. Every tender attempt is recorded as its own payment row against the agreement as `agreement_id` and the week as `week_id`, with `amount_cents` tendered, the `coverage_cents` allocated to the week's amount due, the `platform_credit_cents` allocated to platform activity credit, the reported `payment_outcome`, and `collected_at`, the instant the attempt was recorded. Coverage and platform credit are both written as 0 on a tender that does not settle the week — including one that only partially covers it — and are filled in only where the attempt actually clears the outstanding balance, the platform credit then taking the week's own `platform_credit_cents`. Every tender attempt therefore leaves an audit trail whether it succeeded or not.

`payment_status` moves independently of `week_status`. A tender carries `amount_cents` as a non-negative whole number and `payment_outcome` as exactly `SUCCEEDED` or `FAILED`, anything else being rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400), and the week itself must stand in `DUE`, `GRACE` or `DELINQUENT` before any successful tender is accepted, a week in any other state being rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409). When `amount_cents` is positive and strictly less than the outstanding amount owed — and the tender is an explicitly partial one, which is a first tender presented against a week whose `payment_status` is still `UNPAID` — `payment_status` becomes `PARTIAL`, `amount_due_cents` is reduced by the tendered amount — the remainder is still genuinely owed — and `coverage_cents` is recomputed so the ledger still reconciles against the reduced balance. A short tender on a week that has already been part-tendered is not a fresh partial tender; it is refused with `ERR_PAYMENT_BELOW_AMOUNT_DUE` (HTTP 402), and `amount_due_cents` carries the outstanding balance that remains after the reduction. When enough has been tendered to cover the outstanding amount, `payment_status` becomes `SETTLED` and, if `week_status` was still `DUE`, `GRACE` or `DELINQUENT`, it also becomes `PAID`. A successful settlement credits the agreement's cumulative billed total by the week's amount owed and triggers a recompute of the purchase equity credit described in §3.9.

A tender reported as failed is handled as its own case rather than as a short payment. When the channel reports `payment_outcome` as `FAILED` against a week whose `payment_status` is `UNPAID` or `PARTIAL`, `payment_status` becomes `FAILED`; against any other payment status the attempt is rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409), as it is also against a tender whose `payment_outcome` is neither `SUCCEEDED` nor `FAILED`. Recovery from that state is a distinct operation: a `SupportAgent` or `PlatformAdmin` retries collection on the week, supplying a fresh amount and outcome, and only a week whose `payment_status` is `FAILED` may be retried — any other state being rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409). A retry therefore never creates a partial state: a retry tender that falls short of the outstanding amount records the new attempt and returns the week to `UNPAID` with the balance still fully owed, while a retry tender that covers the outstanding amount takes the week to `SETTLED` directly. A retry that is itself reported as failed leaves both the payment status and the balance as they stood. Both paths write a new payment row. This is a deliberately cyclic edge — a week may fail, retry, fail again, and retry again — and the week's status is untouched by the payment dimension throughout.

The rule that separates a short payment from an underpayment is worth stating precisely, because it is one of the places where the API is easiest to get wrong. On a tender that is **neither** a partial tender **nor** a retry of a failed tender, the tendered amount must be at least the week's outstanding amount owed; otherwise the request is rejected with `ERR_PAYMENT_BELOW_AMOUNT_DUE` (HTTP 402). The comparison is drawn against `amount_due_cents` as it then stands, which already carries the platform credit as a deduction — a tender body supplies no credit figure of its own, so the credit is never added a second time at this gate. In other words, a first attempt that does not cover the bill is refused outright, while an explicitly partial tender and a retry are both legitimate paths that leave the balance outstanding.

Finally, a `PlatformAdmin` may waive a week's amount due outright. Waiver is available while the week stands in `DUE`, `GRACE` or `DELINQUENT`, but not while a purchase option on the agreement is in the `ELECTED` state — a driver who has committed to buying the unit cannot have a rental week erased underneath the equity that has accrued on it, and the attempt is rejected as an inadmissible state with `ERR_INVALID_STATE` (HTTP 409). A waived week moves to `WAIVED`, which is terminal, and the agreement's cumulative waived total rises by that week's amount owed. Because the equity credit is computed from paid amounts *net of* waived amounts, a waiver does not simply remove a bill — it also suppresses the equity that week would otherwise have earned, and it triggers both a delinquency-count recompute and an equity-credit recompute.

### 3.7. Service Events, Loaner Cover and Damage Liability

When a unit needs work, a `FleetOpsAgent` reports a **service event** against the agreement the unit was rented under as `agreement_id` and the unit itself as `vehicle_id`. The report describes the nature of the work as `event_type`, the odometer reading when the unit entered service as `odometer_at_service`, the expected downtime in hours as `downtime_hours`, and — for damage work only — `damage_liability_cents`, the amount of liability being apportioned to the driver. `event_type` is exactly one of `SCHEDULED_SERVICE`, `UNSCHEDULED_REPAIR` or `DAMAGE_REPAIR`. `odometer_at_service` and `downtime_hours` are both non-negative whole numbers, the downtime defaulting to 0 when omitted, and `damage_liability_cents` likewise defaults to 0. Because a reading is the unit's state and not merely the caller's claim, a reported reading above the unit's current `odometer_miles` advances that odometer to the reported figure — the record is what carries a reading forward, and the only way the odometer moves backwards is the explicit rebasing that activation and a swap perform. Reporting an event takes the unit out of both ride and delivery availability: `vehicle_status` becomes `MAINTENANCE`, from `ASSIGNED` when it was on rent or from `AVAILABLE` when it was sitting in the pool, and `assigned_driver_id` on the unit is cleared.

This write is guarded. The request must carry `expected_vehicle_version` holding the caller's last-observed version of the unit, and a stale value is rejected with `ERR_STALE_VEHICLE_VERSION` (HTTP 412) — the reason the guard exists is that a stale view of a unit would take the wrong unit out of service. The agreement behind the event must not be `FROZEN` in posture, or the request is rejected with `ERR_AGREEMENT_FROZEN` (HTTP 409). And the unit must not still be inside a recovery interval: a maintenance event may not be reported against a unit whose recovery interval is open, where that interval runs from the instant the unit entered `RECOVERY` through 24 hours after it last returned to `AVAILABLE`. Reporting against a unit still inside that window is rejected with `ERR_MAINTENANCE_WINDOW_CONFLICT` (HTTP 409), because a unit that has just come back from recovery has not yet been cleared for service.

A reported event opens with `event_status` at `REPORTED`, which is where a `FleetOpsAgent` begins work on it by moving it to `IN_PROGRESS`; that step requires `event_status` to be `REPORTED` and `vehicle_status` to actually be `MAINTENANCE`, or the request is rejected as an inadmissible state with `ERR_INVALID_STATE` (HTTP 409).

**Zero-downtime work.** When the expected downtime is 0 hours, the event can be completed directly from `REPORTED` without ever entering `IN_PROGRESS`, because there is no window to cover. Completion in this path requires the downtime to be exactly 0, moves `event_status` to `COMPLETED`, records `maintenance_allowance_applied_miles` as 0, returns `vehicle_status` from `MAINTENANCE` to `ASSIGNED`, and recomputes the damage apportionment into `damage_charge_cents` on the agreement's open week. No loaner is ever issued on this path.

**Short work with no cover needed.** When the expected downtime is greater than 0 but no greater than 24 hours, completion is taken from `IN_PROGRESS`. `event_status` reaches `COMPLETED`, `vehicle_status` returns from `MAINTENANCE` to `ASSIGNED`, `earnings_interruption_hours` is recorded as the full `downtime_hours`, and `maintenance_allowance_applied_miles` is the smaller of `downtime_hours` and the agreement's `maintenance_allowance_miles` — the downtime is charged hour for hour against the allowance, without any divisor. The damage apportionment is recomputed into `damage_charge_cents` on the agreement's open week as before. The protected-hours figure here is a straight statement of the downtime, because the driver did not actually lose the working time.

**Long work with loaner cover.** When the expected downtime exceeds 24 hours, the service window is long enough to interrupt the driver's platform earnings, and the driver becomes entitled to a loaner. Issuing one is a distinct step a `FleetOpsAgent` takes against an event already in `IN_PROGRESS`, and it is gated in several ways: `event_status` must be `IN_PROGRESS`; `downtime_hours` must exceed 24; the agreement's `compliance_posture` must not be `FROZEN`, or the request is rejected with `ERR_AGREEMENT_FROZEN` (HTTP 409); and a conforming loaner must exist in the candidate pool. That pool is defined tightly — it is every unit whose `region_code` matches the region of the agreement's assigned unit, whose `vehicle_class` matches the class of the agreement's assigned unit, whose `vehicle_status` is `AVAILABLE`, and whose `id` is not that of the very unit under repair. From that pool the programme takes the unit with the smallest `odometer_miles`; if several tie on `odometer_miles`, the earliest `created_at` wins, and ties beyond that are broken by row order in the underlying store rather than by `id`. When the pool is empty the step is simply unavailable and the request is rejected with `ERR_LOANER_UNAVAILABLE` (HTTP 409) — the programme will not fabricate a substitute, promote a non-conforming unit, or quietly leave the driver uncovered.

On success the chosen unit is stamped onto the event as `loaner_vehicle_id`, `loaner_deadline` is set to the logical clock instant plus the event's `downtime_hours`, `event_status` moves from `IN_PROGRESS` to `LOANER_ISSUED`, the loaner's `vehicle_status` is flipped from `AVAILABLE` to `ASSIGNED` with `assigned_driver_id` stamped onto it, and `earnings_interruption_hours` is recorded as 0 — because the driver has been covered and so loses nothing. Issuing a loaner is a substitution rather than a fresh rental term, so unlike activation and a swap it does not repin the loaner's `baseline_odometer_miles`; the mileage ledger is cut over only when the agreement takes a unit as its own. This assignment of the loaner is the forward half of the invariant described in §2.8: the loaner substitutes for the unit under repair so the count of assigned units is conserved.

Completing a loaner-backed event is the compensating half. It requires `event_status` to be `LOANER_ISSUED` with `loaner_vehicle_id` set, and on success `event_status` reaches `COMPLETED`, the loaner's `vehicle_status` is released back to `AVAILABLE` with its `assigned_driver_id` cleared, the original unit's `vehicle_status` returns from `MAINTENANCE` to `ASSIGNED` with `assigned_driver_id` restamped from the agreement's `driver_id`, `earnings_interruption_hours` is recorded as 0, and `maintenance_allowance_applied_miles` is the smaller of `downtime_hours` divided by 8 rounded half up to a whole number of hours, and the agreement's `maintenance_allowance_miles`. That divisor reflects the fact that a loaner already absorbed the driver's working hours, so only the unit's own wear is charged against the allowance. The damage apportionment is recomputed into `damage_charge_cents` on the open week once more.

**How damage liability is shared.** The damage apportionment applies only to service events whose `event_type` is `DAMAGE_REPAIR`, whose `event_status` has reached `COMPLETED`, and which name the agreement's current open week; events of the other two types, events not yet completed, and completed events naming a week that is no longer open are all outside its scope. The `damage_liability_cents` reported on the event is apportioned in a strict two-bucket waterfall: the allowance bucket is filled first and takes whatever it can, and only the remainder is exposed to the driver. Concretely, for each in-scope event taken on its own, the allowance applied is the smaller of `damage_liability_cents` and the agreement's `maintenance_allowance_miles` multiplied by the damage allowance rate of 2 cents per mile; that allowance absorbs its share and is subtracted from the reported liability, and the allowance is drawn afresh for every event rather than being consumed once per agreement. Whatever remains is then charged to the driver, but only up to the driver-damage cap of 50,000 cents — that cap too being applied to each event, after the allowance has been taken — and the charged amounts are summed into `damage_charge_cents` on the open week. The apportionment writes that field to the total of every in-scope event, so it replaces rather than accumulates and is recomputed into a fresh total on each completion.

The waterfall order is load-bearing and is not symmetric with the cap. A liability of 30,000 cents reported against an agreement carrying 200 allowance miles is reduced by 400 cents of allowance first, leaving the driver charged 29,600 cents; the identical 30,000 cents reported against an agreement with no allowance miles leaves the driver charged the full 30,000 cents. Because the apportionment is recomputed into `damage_charge_cents` on every completion, the week's damage portion always reflects the settled state of every in-scope damage event for that week rather than accumulating stale charges.

### 3.8. Compliance Postures, Delinquency and Recovery

An agreement carries a **compliance posture** alongside its lifecycle status, and the posture is what gates the riskier operations. It takes exactly one of three values: `OPEN`, `RESTRICTED` or `FROZEN`, and a newly created agreement begins with `compliance_posture` at `OPEN`. The posture is derived, not set by callers, and it is driven by a single integer — the count of the agreement's weeks whose `week_status` is `DELINQUENT`, taken across all of the agreement's weeks regardless of `payment_status`. A count of 0 yields `OPEN`; a count of exactly 1 yields `RESTRICTED`; a count of 2 or more yields `FROZEN`. The count is recomputed from the full set of weeks at the end of any transition that changes a week's status — never incremented or decremented incrementally — and the posture transitions are then applied from the recomputed value.

The posture machine moves in both directions. An agreement at `OPEN` whose delinquent count rises from 0 to 1 moves to `RESTRICTED`. One at `RESTRICTED` whose count falls back to 0 returns to `OPEN`, and one at `RESTRICTED` whose count reaches 2 moves to `FROZEN`. One at `FROZEN` whose count drops back to 1 returns to `RESTRICTED`. Posture is therefore a continuous reading of the agreement's payment health rather than a one-way ratchet. Leaving `FROZEN` is itself an event with co-effects, and it does not matter whether the posture lands at `RESTRICTED` or at `OPEN`: the unit comes back out of the recovery pool to `ASSIGNED` with the agreement's driver restamped onto it, and the driver's `SUSPENDED` standing — and any enrolment the freeze suspended — is restored from `SUSPENDED` to the live state, the restoration being withheld while any other agreement of that driver is still `FROZEN`. A partial cure, in other words, gives the driver their unit and their standing back while the posture stays `RESTRICTED` until the last week is settled; a full cure in addition closes the delinquency out entirely.

**Declaring a week delinquent.** When a week's payment deadline has passed without settlement, the clock advance described in §2.9 moves the week from `DUE` to `GRACE`; this happens as a consequence of advancing the clock, not as a separate call. Grace buys 72 hours. Declaring the week delinquent is a deliberate step taken by a `ComplianceOfficer` after that grace has lapsed: the week must be in `GRACE` — a week in any other status being rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409) — and the logical clock must be at or past its grace deadline, or the request is rejected with `ERR_GRACE_NOT_LAPSED` (HTTP 422). The grace-lapse gate is read after the state gate, so a week that is not in grace is told about its state rather than about the clock. On success `week_status` moves to `DELINQUENT`, `payment_status` is forced to `FAILED`, the agreement's delinquent count is recomputed, `compliance_posture` transitions are applied from that count, and `agreement_status` is pushed to `DELINQUENT`.

This single declaration is the first hop of the deepest cascade in the programme. Declaring the week delinquent bumps the count, and when that bump takes the count to 2 `compliance_posture` reaches `FROZEN`, which fans out in three directions at once: `agreement_status` is set to `DELINQUENT`; the driver's `eligibility_status` is moved from `ELIGIBLE` to `SUSPENDED`; and the unit's `vehicle_status` is moved from `ASSIGNED` to `RECOVERY`. The driver's suspension then triggers the enrolment's own `enrollment_status` transition from `ACTIVE` to `SUSPENDED`, which is the final hop of the cascade. The unit's move to `RECOVERY` is a direct co-effect of the posture change rather than a chained hop — it does not wait on anything downstream. So a single delinquent week that lifts the count to 2 can carry a driver from good standing to suspension and a unit from the road to the recovery pool without anyone issuing a second request. Each hop is applied only where its own precondition holds, so a driver already standing outside `ELIGIBLE`, or an enrolment no longer `ACTIVE`, is left as it was rather than restamped; and the unit's entry into the recovery pool opens the recovery interval at that instant, so the quiet period described in §3.7 begins the moment the freeze lands.

A `ComplianceOfficer` may also **reopen** a delinquent week administratively, which puts it back into metering rather than writing it off. Reopening requires `week_status` to be `DELINQUENT`, `compliance_posture` to be exactly `RESTRICTED`, and `eligibility_status` to be `ELIGIBLE` — in other words, it is available in the narrow window where the agreement has been flagged but not yet frozen, and it is unavailable precisely when the situation has escalated past that point or when the driver is already suspended. A reopened week's `week_status` returns to `OPEN` with `payment_status` reset to `UNPAID`, and both deadlines are freshly stamped: `payment_deadline` moves to seven days from the logical clock instant and `grace_deadline` to 72 hours after that. The delinquent count is recomputed and the posture transitions reapplied, so reopening a week genuinely relieves the posture rather than merely masking it. This is an explicitly cyclic edge — a week may lapse, be declared delinquent, and be reopened back into metering.

**Curing delinquency by payment.** A delinquent week is not written off by default; it can be paid. A `SupportAgent`- or `PlatformAdmin`-initiated tender against a week whose `week_status` is `DELINQUENT` covers the outstanding amount when `amount_cents` is at least `amount_due_cents` — the platform credit is already netted into that figure rather than added to the tender; on success `week_status` moves to `PAID` with `payment_status` at `SETTLED`, and the agreement's `total_billed_cents` is credited by the week's `amount_due_cents` as it stood at settlement, the delinquent count is recomputed, `compliance_posture` transitions are reapplied, and `equity_credit_cents` is recomputed. Paying one delinquent week of two therefore drops a frozen agreement back to `RESTRICTED` and restores the driver to `ELIGIBLE` standing, and paying the second drops it back to `OPEN`.

**Escalation and recovery.** When the situation does not cure, a `FleetOpsAgent` escalates the agreement into recovery. Escalation requires `agreement_status` to be `DELINQUENT`, `compliance_posture` to be `FROZEN`, and the delinquent count to be at least 2 — the same conditions that produce a freeze, so escalation is only available once the freeze has actually landed, and each condition that fails is reported as an inadmissible state with `ERR_INVALID_STATE` (HTTP 409). On success `agreement_status` moves from `DELINQUENT` to `RECOVERY_PENDING`, and if no agreement of the enrolment still holds occupancy — occupancy-holding states being `ACTIVE`, `RENEWAL_DUE`, `DELINQUENT`, `RECOVERY_PENDING` and `PURCHASE_PENDING` — `enrollment_status` is moved to `WITHDRAWN`, every other enrolment status being left alone. `vehicle_status` stays at `RECOVERY` throughout the escalation; it is not returned to the pool until the recovery itself is executed.

Executing the recovery is the final fleet step. It requires `agreement_status` to be `RECOVERY_PENDING` and `vehicle_status` to actually be `RECOVERY`, and — because recovery can only be executed once — the agreement's recovered-week set must still be open, or the request is rejected with `ERR_RECOVERY_ALREADY_CLOSED` (HTTP 409). The recovered-week set is inspected ahead of the lifecycle state, so a replay of a recovery that has already been executed is reported as a closed recovered-week set rather than as an inadmissible state. On success `vehicle_status` returns from `RECOVERY` to `AVAILABLE` with `assigned_driver_id` cleared, every week whose `week_status` is `DELINQUENT` is moved to `RECOVERED`, and `agreement_status` becomes `RECOVERED` — one of its three terminal values. The unit then enters a quiet period: its recovery interval stays open for 24 hours past this instant, and no maintenance event may be reported against it during that window, which is exactly the `ERR_MAINTENANCE_WINDOW_CONFLICT` guard described in §3.7. Closing the recovered-week set also drops the delinquent count, so the posture reading falls back with it and any freeze the recovery has just relieved is unwound in the same step.

Recovery is not, however, a point of no return. A frozen agreement that has been escalated to `RECOVERY_PENDING` can be pulled back by a full cure: a tender against the delinquent weeks that cures *every* one of them returns `agreement_status` to `ACTIVE` from `RECOVERY_PENDING`. When that cure drives the delinquent count to 0, `compliance_posture` returns to `OPEN`, `vehicle_status` is brought back from `RECOVERY` to `ASSIGNED` with `assigned_driver_id` restamped, and the driver's `eligibility_status` is lifted from `SUSPENDED` back to `ELIGIBLE`. A driver who clears the whole arrears therefore gets both their unit and their standing back without the agreement having to be torn up. Curing only some of the weeks leaves the agreement in `RECOVERY_PENDING` but has the same release effect on the unit and the driver, because leaving `FROZEN` — whether to `RESTRICTED` or to `OPEN` — is what returns the unit to the road; the recovery itself then cannot be executed, because by that point the unit is on the road rather than in the pool, and escalation cannot be taken again while the posture is no longer `FROZEN`. A partially cured agreement therefore sits in `RECOVERY_PENDING` until the remaining weeks are paid or reopened, which is why a completed recovery is only ever taken against a set of weeks that are still all delinquent.

**Reinstatement.** Where the driver's posture has been suspended by a freeze rather than by a withdrawal, a `ComplianceOfficer` may reinstate them. Reinstatement requires that no agreement held by that driver has `compliance_posture` at `FROZEN`, and that `enrollment_status` is `SUSPENDED` — a request against an enrolment in any other status being rejected as an inadmissible state with `ERR_INVALID_STATE` (HTTP 409). On success `enrollment_status` returns from `SUSPENDED` to `ACTIVE` and the driver's `eligibility_status` returns from `SUSPENDED` to `ELIGIBLE`, a driver already standing outside `SUSPENDED` being left as they are. The precondition is deliberately framed on the posture rather than on the agreement status, so a driver cannot be reinstated while any agreement of theirs is still frozen, regardless of how far along the recovery path that agreement has travelled.

**Closing an agreement normally.** A `FleetOpsAgent` closes an active agreement by completing it. Completion requires that no week of the agreement has `week_status` in `DUE`, `GRACE` or `DELINQUENT` — the agreement cannot be walked away from with money outstanding and uncollected — and that no purchase option on the agreement has `option_status` at `ELECTED`, since a driver mid-purchase cannot have the underlying rental terminated; either condition failing is reported as an inadmissible state with `ERR_INVALID_STATE` (HTTP 409). `compliance_posture` must not be `FROZEN`, or the request is rejected with `ERR_AGREEMENT_FROZEN` (HTTP 409), and that gate is read before the lifecycle-state gate, so a frozen agreement that is also not `ACTIVE` is told about the freeze. On success `vehicle_status` returns from `ASSIGNED` to `AVAILABLE` with `assigned_driver_id` cleared and the unit becomes available again at that instant, and `agreement_status` becomes `COMPLETED`, another of its terminal values.

### 3.9. Accruing Equity: Escrow, Election and the Path to Ownership

The programme's exit ramp for a driver who wants to keep the car is the **purchase option**. A `PlatformAdmin` offers one against an agreement by naming the agreement as `agreement_id`, the driver entitled to elect it as `driver_id`, the fixed buyout price quoted by the programme as `purchase_price_cents`, and the number of weekly escrow periods that must be funded before the option can be completed as `escrow_weeks_required`. `purchase_price_cents` is a non-negative whole number of cents, and `escrow_weeks_required` must be at least 1. An offered option sits with `option_status` at `OFFERED`, and its option lifecycle takes exactly one of five values: `OFFERED`, `ELECTED`, `ESCROW_FUNDED`, `COMPLETED` or `WITHDRAWN`. Offering is gated on the agreement's posture being exactly `OPEN`; an agreement merely `RESTRICTED` is not good enough, and the attempt is rejected with `ERR_POSTURE_NOT_OPEN` (HTTP 409). Both the agreement and the driver the option names must exist, or the request is rejected with `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404). On offer, `equity_credit_cents` is computed for the first time and written onto the option, `escrow_required_cents` is derived from it, and `escrow_balance_cents` and `escrow_weeks_funded` both begin at 0. `elected_at` is empty until the driver actually elects.

**How the equity credit accrues.** The credit is a share of the money the driver has actually paid, net of anything the programme gave away. It is computed from the agreement's weeks whose `week_status` is `PAID` and its weeks whose `week_status` is `WAIVED` — a week that has been `RECOVERED` contributes nothing, since recovery writes the money off rather than collecting it — each such week contributing its own `amount_due_cents` as that figure then stands: for a settled week, the amount it was settled for, and for a waived week, the amount waived. The programme sums the `amount_due_cents` across the paid weeks, sums the `amount_due_cents` across the waived weeks, and subtracts the waived total from the paid total to obtain a subtotal. The driver's equity share is one tenth of that subtotal, taken with integer division so any remainder below a whole cent is discarded. That gross figure is then converted through the programme's cent divisor of 100 — multiplied by 100, divided by that same divisor with round-half-up to the nearest whole cent — and multiplied by the whole-cent factor obtained by dividing that divisor by 100, which is 1. Finally the credit is clamped so it can never fall below zero, which matters only in the theoretical case where waivers exceed payments on the agreement.

Because the credit is recomputed whenever a week reaches `PAID` and whenever a week is waived, and because waivers suppress it while settlements lift it, the credit is a live reading rather than a once-and-for-all figure. Two settled weeks of 39,000 cents and 30,100 cents with nothing waived produce a subtotal of 69,100 cents and therefore a credit of 6,910 cents.

**How the recurring escrow amount is derived.** `escrow_required_cents` is `purchase_price_cents` with the current `equity_credit_cents` subtracted from it, divided by `escrow_weeks_required`, rounded half up to a whole cent. The schedule therefore depends on the equity credit rather than on the price alone, and because the credit is recomputed as the driver continues to pay rent, re-running the schedule after a later credit recompute changes the recurring amount even though the quoted buyout price has not moved at all.

**Election.** A `Driver` elects the option, and the request must carry `expected_agreement_version` holding their last-observed version of the agreement behind the option — a stale value is rejected with `ERR_STALE_AGREEMENT_VERSION` (HTTP 412). Election requires `option_status` to be `OFFERED`, the agreement's `compliance_posture` to be exactly `OPEN` (otherwise `ERR_POSTURE_NOT_OPEN`, HTTP 409), the agreement's delinquent count to be 0, and `PurchaseOption.agreement_id` to actually name that agreement. A frozen agreement is reported as the freeze rather than as an openness failure, so that gate is read first; and the agreement must be live — `ACTIVE` or `RENEWAL_DUE`, a live agreement being either one — with any other lifecycle status rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409). Election is additionally blocked whenever any week of the agreement has `week_status` at `DELINQUENT`, and that attempt is rejected with `ERR_PURCHASE_BLOCKED_BY_DELINQUENCY` (HTTP 409) — a driver who is behind on rent cannot start buying the car. On success `option_status` moves from `OFFERED` to `ELECTED` with `elected_at` stamped, `agreement_status` moves to `PURCHASE_PENDING`, and every week of the agreement still at `OPEN` is moved to `DEFERRED`, at which point the maintenance of the deferred week is charged at escrow rates rather than at ordinary rental rates. The escrow schedule is recomputed and the agreement's version advances by one.

**Funding escrow.** The driver funds the option one weekly period at a time. Each funding step requires `option_status` to be `ELECTED` or `ESCROW_FUNDED` and `escrow_weeks_funded` to still be below `escrow_weeks_required`, a step taken after the required weeks are already covered being rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409); `escrow_weeks_funded` is incremented by one and `escrow_balance_cents` rises by the `escrow_required_cents` then standing on the option. `option_status` lands at `ESCROW_FUNDED` after a funding step, and it stays there: a further funding step is permitted from that state, but it leaves the option at `ESCROW_FUNDED` once more rather than returning it to `ELECTED`, so `ELECTED` is the state an option is in before any week has been funded and `ESCROW_FUNDED` is where it remains from the first funded week onwards. Every funding step also recomputes `equity_credit_cents`, which re-derives `escrow_required_cents` from the freshly computed credit, and advances the agreement's `version` by one, so the escrow requirement charged on the next step may itself have moved.

**Withdrawal.** A `Driver` may withdraw an option whose `option_status` is `OFFERED`, `ELECTED` or `ESCROW_FUNDED`, moving it to `WITHDRAWN`, which is terminal; an attempt from `COMPLETED` or `WITHDRAWN` is rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409). Withdrawal reverses everything the election did: the deferred week returns to `OPEN` with fresh deadlines — `payment_deadline` seven days from the logical clock instant and `grace_deadline` 72 hours after that — and `agreement_status` returns from `PURCHASE_PENDING` to `ACTIVE`. An option withdrawn before it was ever elected never deferred a week, so there is nothing to re-open and no agreement status to reverse. This is the exact mirror of the election deferral, and it is why a driver who changes their mind is not left holding a frozen week.

**Completion.** A `PlatformAdmin` completes the purchase once the option is funded, and the operation is available from `ELECTED` or `ESCROW_FUNDED`, any other option state being rejected as inadmissible with `ERR_INVALID_STATE` (HTTP 409). Completion requires `escrow_weeks_funded` to have reached `escrow_weeks_required` — otherwise the request is rejected with `ERR_ESCROW_INCOMPLETE` (HTTP 422) — and requires `escrow_balance_cents` plus `equity_credit_cents` to cover `purchase_price_cents`, a shortfall being rejected with the same `ERR_ESCROW_INCOMPLETE` (HTTP 422). On success `option_status` reaches `COMPLETED`, `vehicle_status` is moved from `ASSIGNED` to `RETIRED` and the unit leaves the rental fleet permanently with `assigned_driver_id` cleared, and `agreement_status` becomes `PURCHASED`, its final terminal value.

Election, funding and withdrawal are three of the four ownership-checked operations, so a driver may act only on their own option and an attempt on someone else's is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

### 3.10. Regional Fleet Sizing and Utilization

The last piece of the programme is knowing whether each region has the right number of cars. A `PlatformAdmin` declares a **regional fleet fact** by naming a two-letter uppercase `region_code` — unique across facts, so a second declaration for an already-declared region is rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400) rather than as a conflict — and stating `demand_units`, the driver demand for that region expressed in vehicle units as a non-negative whole number; a code that is not two uppercase letters, or a demand that is not a non-negative whole number, is likewise rejected as malformed with `ERR_INVALID_REQUEST` (HTTP 400). The fact is a derived reading of live fleet state; declaring it computes a provisional reading immediately and responds with the created fact, and a `PlatformAdmin` or `FleetOpsAgent` can recompute it at will, each recompute refreshing the fact row's `updated_at` and advancing its `version`.

Recomputation walks the region's units. Units whose `vehicle_status` is `ASSIGNED` are counted once each and form the assigned-unit figure, and a loaner currently stamped onto a driver's agreement is one of those assigned units like any other. The region's `active_agreements_count` is recorded as that same assigned-unit figure — the programme treats the two as identical by construction, because a unit is assigned exactly while an occupancy-holding agreement holds it, and occupancy-holding means `agreement_status` at `ACTIVE`, `RENEWAL_DUE`, `DELINQUENT`, `RECOVERY_PENDING` or `PURCHASE_PENDING`. `available_fleet_count` is then every unit whose `vehicle_status` is `AVAILABLE` **or** `RECOVERY` — a unit sitting in the recovery pool is still programme fleet and still counts toward supply, even though it is not currently lettable. The denominator of the utilization measure is the sum of the assigned units and the available fleet count, and because the two sets are disjoint by construction each unit is counted exactly once.

`utilization_bps` is expressed in basis points, with floor division: it is the assigned units multiplied by 10,000 and divided by that denominator, truncated to a whole number, and it is reported as 0 in the degenerate case where the denominator is itself 0. The measure is bounded between 0 and 20,000 inclusive. `sizing_deficit_units` is the region's `demand_units` minus that same denominator, and it is a signed figure: a positive value means the region is short of cars against demand, and a negative value — one this API only produces when `demand_units` itself is below the fleet count, since a region admitted with no demand declared sits at exactly zero — means the region has more supply than demand calls for. A unit held by a driver is neither parked in the available pool nor available to be let, so it does not by itself count as supply: only the assigned-and-available denominator enters the subtraction, which is why a region whose demand exactly matches its assigned units plus its parked units balances at zero rather than reporting spare capacity against the rented cars.

The region's fleet posture follows the sign of that deficit, with a balance point of exactly zero. A recomputation leaving `sizing_deficit_units` positive puts `fleet_fact_status` at `UNDER_SUPPLIED`; one leaving it negative puts it at `OVER_SUPPLIED`; and one leaving it at exactly zero returns it to `BALANCED`. The posture set is exactly `BALANCED`, `UNDER_SUPPLIED` and `OVER_SUPPLIED`, and every recompute re-derives the posture from the freshly computed figures rather than nudging it. The sign convention is worth holding onto, because the two readings of supply disagree in a way that is easy to invert: with three units assigned and one available in a region whose demand is three units, the deficit basis reports an under-supply of two while the counted-unit basis would report a surplus of one, so the same fleet state can look short or over-supplied depending on which side of the subtraction is taken as the reference — and this API takes demand as the reference, so the deficit of two is the answer that governs.

## 4. Endpoint Definitions

Operations that bring a new, stand-alone resource into existence — a driver, an enrolment, a fleet unit, an agreement, a weekly period, a service event, a purchase option, a qualification check or a regional fleet fact — respond with `201 Created`. Operations that modify an existing resource, that drive it through a state transition, or that record a payment against it respond with `200 OK`; the sole exception is the collection of a weekly payment, which is the creation of a new payment row and therefore responds with `201 Created`, and that holds for a retried collection just as it does for a first tender. Collection reads respond with `200 OK`. Every write returns the affected resource in `data`; the transition operations that act on a week return the week, those that act on an agreement return the agreement, those that act on an option return the option, a completed service event returns the event, and re-running a qualification check returns the check. The error envelope of §2.2 applies to every failure, so a rejection carries the same `meta` shape as a success and never a partial resource body.
