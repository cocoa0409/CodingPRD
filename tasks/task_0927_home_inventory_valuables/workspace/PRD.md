# Home Inventory & Valuables Vault API — Product Requirements Document

## 1. Introduction

Households accumulate value faster than they document it. A wedding ring, a restored guitar, a grandmother's oil painting and a four-year-old refrigerator all sit in the same house, but only one of them will ever be photographed before a fire, and almost none of them will have a receipt when the adjuster asks. The Home Inventory & Valuables Vault exists to close that gap: it walks a household room by room, captures each object with photographs and serial plates, attaches declared values and credentialed appraisals, reconciles the result against the household's insurance policy, and freezes the whole picture into a documentation package that a carrier will accept after a loss.

The service is built around three ideas that shape every rule in this document. First, **evidence is a tier, not a checkbox** — an item's usefulness in a claim depends on exactly what has been uploaded for it, and that tier moves down as easily as it moves up when an owner deletes a photograph. Second, **valuations compete** — a declared value, a depreciated actual-cash-value and a certified appraisal can all exist for the same object, and a fixed precedence order decides which one the household, the carrier and the estate executor all see. Third, **posture gates sit above ordinary business rules** — a lapsed subscription makes the whole vault read-only, an overdue annual refresh attestation blocks package generation and new share links, and an open loss claim freezes the affected items outright. These three gates pre-empt the ordinary state machines rather than being pre-empted by them, and the priority ladder in §2.8 makes that ordering normative.

Beyond insurance, the same catalogue serves estate and downsizing work: an executor allocates every unit of every catalogued item to an heir or to a sale, donation or discard pile, the service scores how fairly the result divides across heirs under two different valuation conventions, and the homeowner — never the executor — approves it. Everything the household chooses to expose outside the vault leaves through a time-boxed, redaction-scoped share link with a hard redemption cap. The API is mounted under `/vault`, with a single administrative clock endpoint outside that mount.

## 2. Global Specifications & System-Wide Principles

### 2.1. Members, Roles and Access Control

Every request to the service carries two headers. `X-User-ID` identifies the caller and `X-User-Role` names the capacity the caller is acting in. A request that omits `X-User-Role`, or whose `X-User-Role` is not one of the eight role names below, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); the same error is returned when `X-User-ID` is missing or empty for any role other than `Anonymous`. When the headers are well-formed but the named role does not appear in the called endpoint's authorised-role list in §4, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The eight roles are `Anonymous`, `Homeowner`, `HouseholdMember`, `Appraiser`, `InsuranceAgent`, `ClaimsAdjuster`, `EstateExecutor` and `PlatformAdmin`.

Three of these roles are backed by a `Member` row. When `X-User-Role` is `Homeowner`, `X-User-ID` is the `id` of the acting `Member`; ownership checks on any resource that references a `Household` compare the acting member's `household_id` to the target resource's `household_id`. The same identity rule applies when `X-User-Role` is `HouseholdMember` and when it is `EstateExecutor`. When `X-User-Role` is `Appraiser`, `X-User-ID` is the `id` of the acting `Appraiser` row, and ownership checks compare it to the target `Appraisal`'s `appraiser_id`. The remaining four roles carry opaque identities: when `X-User-Role` is `Anonymous`, `InsuranceAgent`, `ClaimsAdjuster` or `PlatformAdmin`, `X-User-ID` is an operator identifier that is not tied to any persisted entity; the server may record it (for example as `declared_by_member_id` or `approved_by_member_id` where a transition writes it) but never compares it to any entity's `id` for those four roles. `Anonymous` in addition needs no `X-User-ID` at all.

Household scoping is enforced as a single check. For `Homeowner`, `HouseholdMember` and `EstateExecutor`, the acting `Member`'s `household_id` must equal the target resource's `household_id`; for `Appraiser`, `X-User-ID` must equal the target `Appraisal`'s `appraiser_id`. Operations reserved to the homeowner additionally require the acting member's `member_role` to be `OWNER`, and operations reserved to the executor require the acting member's `member_role` to be `EXECUTOR` **and** `X-User-ID` to equal the target `EstatePlan`'s `executor_member_id`. Any of these failures produces `ERR_HOUSEHOLD_SCOPE_VIOLATION` (HTTP 403).

Two segregation-of-duties bars run through the role model and are stated in full in §3.4 and §3.8: an `Appraiser` whose `linked_member_id` names the member who declared an item's value may not appraise that item, and the member named as `executor_member_id` on an estate plan may not approve it. Both produce `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Ordering and Filtering

Every list endpoint accepts `limit` and `offset`. `limit` defaults to 10, has a minimum of 1 and a maximum of 100; `offset` defaults to 0 and has a minimum of 0. Both are reported back in `meta` together with `total_count` (the number of rows matching the filters before the page window is applied) and `has_more` (true when rows remain after the current window).

**Global ordering rule.** Every list endpoint returns rows ordered by `created_at` ascending. When two rows carry the same `created_at`, the tie is broken by **creation order**: the row created by the earlier API request comes first. Creation order is a total order the server observes directly from the append order of each collection; it is never approximated by comparing `id` values, which are random UUIDs and are forbidden from every business decision, including ordering, tie-breaking and selection. Because `created_at` is stamped from the logical clock described in §2.5, every row created between two clock advances shares the same `created_at` down to the millisecond, and the creation-order tie-break is what makes those pages deterministic. The same ordering rule and the same tie-break govern every ordered computation in this document — the waterfall in §3.5, the per-line snapshot in §3.6, the deductible allocation in §3.7 and the heir ordering in §3.8.

**Filters.** The filter parameters accepted by each list endpoint are named in the workflow narratives of §3 and repeated in §4. A filter whose value is a well-formed string that simply matches no row — including a value outside the declared member set of the field being filtered on, such as an unknown `status`, `lifecycle_state`, `evidence_tier`, `valuation_state`, `member_role`, `asset_kind`, `disposition`, `scope_kind`, `refresh_state`, `write_gate_state`, `category` or `stale` value — returns an empty page: HTTP 200, an empty `data` array, `total_count` of 0 and `has_more` false. List filters never produce `ERR_INVALID_ENUM` and never produce `ERR_INVALID_REQUEST`. The single exception is the `basis` query parameter of the coverage-gap read, which is a computation selector rather than a filter: a `basis` outside `SCHEDULED_FIRST` and `BLANKET_FIRST` is rejected with `ERR_INVALID_ENUM` (HTTP 422). Omitting `basis` selects `SCHEDULED_FIRST`.

### 2.4. Common Resource Properties

Fourteen of the seventeen persisted resource types — `Member`, `Household`, `Subscription`, `Room`, `Item`, `Appraiser`, `Appraisal`, `Policy`, `DocumentationPackage`, `LossClaim`, `ClaimLine`, `EstatePlan`, `Allocation` and `ShareGrant` — carry the full set of system-managed fields:

- `id` (string): a server-minted UUID with no type prefix.
- `created_at` (string): an ISO 8601 UTC instant recording when the row was created.
- `updated_at` (string): an ISO 8601 UTC instant refreshed on every mutation of the row.
- `version` (integer): starts at 1 when the row is created and increments by exactly 1 each time the row is mutated.

The remaining three types are lighter. `Asset`, `CategorySchedule` and `PackageLine` carry only `id` and `created_at`: they have **no** `updated_at` field and **no** `version` field, and nothing in this document may be read as bumping a version on them. Soft-deleting an asset, or flipping a package line's `stale` flag, therefore changes those rows without any version to observe — the observable version movement lands on the owning `Item` or `DocumentationPackage` instead.

**The one-bump rule.** Within a single API request, a row whose persisted state actually changes has its `version` incremented exactly once, no matter how many separate fields change or how many cascade hops touch it. A row that a request creates starts at `version` 1 and is not additionally "bumped" by the same request. A roll-up parent whose derived counters are recomputed but land on the values they already held is not mutated and does not bump. §2.9 renders this as an exhaustive per-operation ledger.

### 2.5. The Logical Clock and Timestamp Rendering

The service runs on a logical clock, never on wall-clock time. Before the first clock-setting call the clock reads exactly `2026-05-01T00:00:00Z`, and it must not fall back to the host's real time under any circumstance. Every deadline, band boundary, expiry, depreciation age and window comparison in this document is evaluated against this logical clock, and every server-stamped instant is taken from it. An administrative capability reserved to `PlatformAdmin` advances the clock to a supplied `to_iso8601` instant; its response reports `current_utc` together with four counters — `subscriptions_repostured`, `share_grants_expired`, `appraisals_expired` and `packages_expired` — described in §2.7.

**Rendering rules, which admit no exceptions:**

1. Every **server-written** instant is rendered as an ISO 8601 UTC string with exactly three fractional digits and a trailing `Z` — for example `2026-05-01T00:00:00.000Z`. This covers `created_at` and `updated_at` on every row, and it covers every server-stamped or server-derived `*_at` field: `period_start_at`, `period_end_at`, `past_due_since_at`, `last_attested_at`, `refresh_due_at`, `certified_at`, `valid_until_at`, `generated_at`, `delivered_at`, the package's computed `expires_at`, `submitted_at`, `proposed_at`, `approved_at` and `executed_at`. A row created before any clock advance therefore carries `created_at` of `2026-05-01T00:00:00.000Z`.
2. A **derived** instant inherits the three-digit rendering of rule 1 even when it is computed from a caller-supplied input. The package's `expires_at`, computed as `generated_at` plus 180 days, and an appraisal's `valid_until_at`, computed as `certified_at` plus 1095 days, are both server-written and both carry three fractional digits.
3. Every **caller-supplied** instant is echoed back byte-for-byte as the caller supplied it, with no reformatting, no digit padding and no truncation. This covers `acquired_at`, `captured_at`, `inspection_start_at`, `inspection_end_at`, `effective_from`, `loss_date`, and a share grant's `starts_at` and `expires_at`. If a client writes `2026-06-01T00:00:00Z`, that exact string is what every later read returns.
4. The clock endpoint's `current_utc` reproduces the operator-supplied `to_iso8601` string verbatim, exactly as rule 3 governs caller-supplied instants. The rows the clock advance stamps afterwards still follow rule 1.
5. All instant comparisons are **semantic**: two strings that denote the same instant compare equal regardless of how many fractional digits either carries. The difference between `2026-06-01T00:00:00Z` and `2026-06-01T00:00:00.000Z` is a rendering difference only and never changes the outcome of a band test, a window test or an expiry test.

### 2.6. Money, Quantities and Rounding

Every monetary field in the service is an integer number of cents; there are no fractional cents anywhere, and no monetary value is ever returned as a string or as a decimal number. Wherever a calculation produces a non-integer intermediate, the result is converted to cents with **round half up** — a value ending in exactly one half cent rounds away from zero to the larger magnitude. The single non-monetary rounded quantity in the system is `balance_spread_pct` on an estate plan, which is a number rounded half up to two decimal places.

Rounding **order** is pinned per calculation and is never a matter of taste. §3.6 pins per-line rounding before summation for documentation packages; §3.7 pins per-line rounding for gross values and for pro-rata deductible shares with a single anchor line absorbing the remainder; §3.4 pins a single rounding at the very end of the actual-cash-value curve. Where a rounding order is pinned, applying the arithmetic in any other order is a defect even when the difference is one cent.

Percentages configured on a category — `annual_depreciation_pct` and `salvage_floor_pct` — and the two policy-level percentages `FAIR_DIVISION_TOLERANCE_PCT` (5.0) and `SELL_DISPOSITION_COST_PCT` (12.0) are decimal numbers and preserve their input precision. The remaining three disposition cost percentages are all zero: `DONATE_DISPOSITION_COST_PCT` is 0.0, `DISCARD_DISPOSITION_COST_PCT` is 0.0 and `KEEP_DISPOSITION_COST_PCT` is 0.0, which is why only sale proceeds are ever reduced by a disposition cost.

Item quantities are bounded: `MIN_ITEM_QUANTITY` is 1 and `MAX_ITEM_QUANTITY` is 999, so an item's `quantity` must be at least 1 and at most 999. An allocation's `quantity` must be at least `MIN_ALLOCATION_QUANTITY`, which is 1. A claim line's `claimed_quantity` must be at least 1 and at most the claimed item's `quantity`.

### 2.7. The Three Posture Gates and When Posture Is Recomputed

A household carries a derived posture in `write_gate_state`, which is one of `OPEN`, `RESTRICTED` or `READ_ONLY`. It is never set by any endpoint directly. It is computed from the household's single `Subscription` row by a fixed rule: a household with no subscription row is `OPEN`; a household whose subscription `status` is `LAPSED` or `CLOSED` is `READ_ONLY`; otherwise a household whose subscription `refresh_state` is `OVERDUE` is `RESTRICTED`; otherwise the household is `OPEN`. The precedence is strict — `READ_ONLY` outranks `RESTRICTED`, which outranks `OPEN` — so a lapsed household that is also refresh-overdue reports `READ_ONLY`, and the read-only rung fires before the restricted rung.

**Gate 1 — the global write gate.** While a household is `READ_ONLY`, every mutating endpoint under `/vault` is rejected with `ERR_VAULT_READ_ONLY` (HTTP 403) at ladder rung 10, except for the endpoints on the exclusion list below, which remain callable:

- `POST /vault/subscriptions/{subscription_id}/billing-event`
- `POST /vault/subscriptions/{subscription_id}/reinstate`
- `POST /vault/subscriptions/{subscription_id}/attest-refresh`
- `POST /vault/claims`
- `POST /vault/claims/{claim_id}/lines`
- `POST /vault/claims/{claim_id}/submit`
- `POST /vault/claims/{claim_id}/withdraw`
- `POST /vault/claim-lines/{claim_line_id}/adjudicate`
- `POST /vault/claim-lines/{claim_line_id}/appeal`
- `POST /vault/claims/{claim_id}/settle`
- `POST /vault/share-grants/{share_grant_id}/revoke`
- `POST /_clock/set_current_utc`
- every `GET` under `/vault`

The intent is deliberate: a household that stops paying keeps the ability to run a loss claim to completion on the evidence it has already banked, to revoke a share link, and to pay and come back — but it may not add inventory, upload evidence, declare values, schedule coverage, request appraisals, generate or deliver packages, run an estate plan, or issue new share links. Rung 10 pre-empts rungs 11 through 38 for the endpoints it governs.

**Gate 2 — the restricted gate.** While a household is `RESTRICTED` — that is, its subscription `refresh_state` is `OVERDUE` and its `status` is neither `LAPSED` nor `CLOSED` — exactly two endpoints are blocked with `ERR_REFRESH_OVERDUE` (HTTP 403) at ladder rung 11:

- `POST /vault/packages/{package_id}/generate`
- `POST /vault/share-grants`

Every other write passes. A restricted household can still catalogue items, upload assets, declare values, schedule coverage, request appraisals, open and run claims, and build estate plans; it simply may not mint fresh evidence packages or fresh share links until someone attests the annual refresh. Rung 11 pre-empts rungs 12 through 38 on those two endpoints and has no effect on any other endpoint.

**Gate 3 — the records freeze.** An `Item` whose `lifecycle_state` is `FROZEN` is under an open loss claim. Nine endpoints refuse to touch such an item with `ERR_ITEM_FROZEN` (HTTP 409) at ladder rung 12: item patch, asset delete, asset upload, value declaration, scheduling, unscheduling, replacement, appraisal request and appraisal certification. Rung 12 pre-empts rungs 13 through 38 — in particular it pre-empts both ordinary state rungs, so certifying an appraisal whose item is frozen surfaces `ERR_ITEM_FROZEN` and never `ERR_INVALID_STATE`. The household-level mirror of this gate is `records_freeze_active`, which is true exactly while at least one loss claim on the household sits in `OPEN`, `SUBMITTED`, `UNDER_REVIEW` or `SUPPLEMENT_REQUESTED`.

**Posture recomputation order.** Posture is recomputed at exactly two hooks and nowhere else.

- **Hook H1** runs at the end of a successful clock advance, over the whole store, in this fixed order: recompute `refresh_state` on every `Subscription` from the bands in §3.2; then recompute `write_gate_state` on every owning `Household`; then move every `ShareGrant` whose status is `ACTIVE` to `EXPIRED` when the new clock instant is at or after its `expires_at`; then move every `Appraisal` whose status is `CERTIFIED` to `EXPIRED` when the new instant is at or after its `valid_until_at`; then move every `DocumentationPackage` whose status is `GENERATED` or `DELIVERED` to `EXPIRED` when the new instant is at or after its `expires_at`. The response's four counters report the number of rows each of the last four steps actually changed: `subscriptions_repostured` counts subscriptions whose `refresh_state` moved, `share_grants_expired` counts grants moved to `EXPIRED`, `appraisals_expired` counts appraisals moved to `EXPIRED`, and `packages_expired` counts packages moved to `EXPIRED`.
- **Hook H2** runs as the very first step of evaluating any request under `/vault`, before ladder rung 1 is considered, and only for the household or households reachable from the request path or body: recompute that household's `Subscription.refresh_state`, then that `Household.write_gate_state`. H2 is a read-modify-write — when a value actually changes it persists the change and bumps the affected `Subscription.version` and `Household.version` accordingly.

Within any single request the order is always: subscription refresh band first, household write gate second, ladder rung 1 third.

Expressed as transitions, the household posture axis moves in exactly six ways, all of them driven by those two hooks and none of them by a dedicated endpoint. `OPEN → RESTRICTED` fires when the subscription's `refresh_state` becomes `OVERDUE` while its `status` is neither `LAPSED` nor `CLOSED`. `RESTRICTED → OPEN` fires after an attestation returns `refresh_state` to `CURRENT`, `DUE` or `GRACE` while `status` is neither `LAPSED` nor `CLOSED`. `OPEN → READ_ONLY` and `RESTRICTED → READ_ONLY` both fire when `status` becomes `LAPSED` or `CLOSED`. `READ_ONLY → OPEN` fires after a reinstatement that leaves `status` `ACTIVE` and `refresh_state` anything other than `OVERDUE`, and `READ_ONLY → RESTRICTED` fires after a reinstatement that leaves `status` `ACTIVE` while `refresh_state` is `OVERDUE`. Each of the six bumps the household's `version` by one.

### 2.8. The Validation Priority Ladder

Every request is evaluated against one ordered ladder of 38 rungs. The rungs are checked strictly in ascending order, and the **first** rung whose condition fires produces the response; no later rung is evaluated. Two rungs never share a number, so a request that violates several rules has exactly one defined error — the one belonging to the lowest-numbered rung it violates. Rungs whose scopes are disjoint can never both fire on one request; where scopes overlap, the numbering below is the tie-break.

The three posture rungs — 10, 11 and 12 — sit deliberately **above** the two ordinary state rungs 13 and 14. A lapsed vault, a restricted vault and a records freeze each pre-empt the ordinary state machine rather than being pre-empted by it.

1. **`ERR_UNAUTHENTICATED` (401)** — `X-User-Role` is missing or names no declared role, or `X-User-ID` is missing or empty for any role other than `Anonymous`. Applies to every endpoint.
2. **`ERR_UNAUTHORIZED` (403)** — the supplied `X-User-Role` does not appear in the called endpoint's authorised-role list. Applies to every endpoint.
3. **`ERR_INVALID_REQUEST` (400)** — a required body field is missing, a JSON type does not match, a required array is empty, or a datetime field does not parse as ISO 8601 UTC. This rung also owns four specific malformed-payload cases and one uniqueness case: `inspection_end_at` at or before `inspection_start_at`; a share grant's `expires_at` at or before its `starts_at`; a `byte_size` below 1; an `access_cap` below 1; and a `Member.email` that duplicates an existing member's email. Applies to every write endpoint.
4. **`ERR_INVALID_ENUM` (422)** — a value outside the declared member set of an enum-valued field. This rung is a **closed iff-list**. Exactly these fields route here: `Member.member_role`, `Subscription.tier`, `Item.category`, `Asset.asset_kind`, `CategorySchedule.category`, `CategorySchedule.appraisal_scope`, each member of `Appraiser.scope_categories`, `Appraisal.void_reason`, `LossClaim.peril`, `LossClaim.settlement_basis`, `LossClaim.deductible_mode`, `ClaimLine.denial_reason`, `EstatePlan.valuation_mode`, `Allocation.disposition`, `ShareGrant.scope_kind`, `ShareGrant.redaction_level`, the billing event's `outcome`, the adjudication's `decision`, the tier change's `proration_mode`, and the coverage-gap read's `basis`. **No other field routes to `ERR_INVALID_ENUM`** — every other validation failure routes to `ERR_INVALID_REQUEST` at rung 3 — and none of the twenty fields listed here ever routes to `ERR_INVALID_REQUEST` for a bad member value. Applies to every write endpoint plus the coverage-gap read.
5. **`ERR_HOUSEHOLD_NOT_FOUND` (404)** — an id in the request **path** does not resolve. Path ids are validated left to right, so the leftmost unresolvable segment decides the error. An unresolvable household id produces `ERR_HOUSEHOLD_NOT_FOUND`; an unresolvable item id produces `ERR_ITEM_NOT_FOUND`; every other unresolvable path resource — member, room, subscription, policy, package, package line, appraiser, appraisal, claim, claim line, estate plan, allocation, share grant, asset — produces `ERR_REFERENCE_NOT_FOUND`. Applies to every endpoint with a path id.
6. **`ERR_REFERENCE_NOT_FOUND` (404)** — a foreign key supplied in the request **body** does not resolve: `household_id`, `room_id`, `item_id`, `policy_id`, `package_id`, `appraiser_id`, `heir_member_id`, `executor_member_id`, `scope_room_id`, `scope_package_id`, `scope_claim_id`, or any element of `affected_room_ids`. An unresolvable `household_id` in the body produces `ERR_HOUSEHOLD_NOT_FOUND` instead. Applies to every write endpoint that accepts a foreign key in its body.
7. **`ERR_SHARE_TOKEN_UNKNOWN` (404)** — the `{share_token}` path segment matches no share grant at all. Applies to the share-link redemption endpoint only. This is deliberately distinct from rung 9: "no grant exists" is a 404, "a grant exists but is unusable" is a 403.
8. **`ERR_HOUSEHOLD_SCOPE_VIOLATION` (403)** — the household-scoping and role-standing check described in §2.1. Applies to every `/vault` endpoint acted on by a role whose identity is backed by an entity.
9. **`ERR_SHARE_GRANT_INACTIVE` (403)** — the resolved share grant is not usable: its `status` is not `ACTIVE`, or the current instant is before `starts_at`, or at or after `expires_at`, or `access_count` has already reached `access_cap`. A `REVOKED`, `EXPIRED`, `EXHAUSTED` or `VOIDED_BY_SCOPE` grant fails here. Applies to the share-link redemption endpoint only.
10. **`ERR_VAULT_READ_ONLY` (403)** — the global write gate of §2.7: the household is `READ_ONLY` and the endpoint is a mutating `/vault` endpoint that is not on the exclusion list.
11. **`ERR_REFRESH_OVERDUE` (403)** — the restricted gate of §2.7: the household is `RESTRICTED` and the endpoint is package generation or share-grant creation.
12. **`ERR_ITEM_FROZEN` (409)** — the records freeze of §2.7: the target item, or the item behind the target appraisal or allocation, has `lifecycle_state` `FROZEN`. Applies to `PATCH /vault/items/{item_id}`, `DELETE /vault/assets/{asset_id}`, `POST /vault/items/{item_id}/assets`, `POST /vault/items/{item_id}/declare-value`, `POST /vault/items/{item_id}/schedule`, `POST /vault/items/{item_id}/unschedule`, `POST /vault/items/{item_id}/replace`, `POST /vault/appraisals` and `POST /vault/appraisals/{appraisal_id}/certify`.
13. **`ERR_ALREADY_TERMINAL` (409)** — the target entity already sits in a terminal state of the axis the request would move. Applies to every state-transition endpoint.
14. **`ERR_INVALID_STATE` (409)** — the target entity's current state is not a declared origin state for the requested transition, or a cross-entity precondition of that transition fails. Worked examples: submitting a claim whose documentation package is neither `GENERATED` nor `DELIVERED`; certifying before `inspection_end_at`; certifying while the appraiser's `status` is `SUSPENDED`; opening a claim against a package that is neither `GENERATED` nor `DELIVERED`, or whose `policy_id` differs from the claim's; creating a second live estate plan for a household that already holds one in `DRAFT`, `PROPOSED` or `APPROVED`; changing tier to the tier already held; and delivering a package at or after its `expires_at`. Applies to every state-transition endpoint.
15. **`ERR_APPRAISER_SCOPE_MISMATCH` (422)** — the appraiser's `scope_categories` array does not contain the `appraisal_scope` of the `CategorySchedule` governing the target item's `category`. Applies to appraisal requests.
16. **`ERR_SEGREGATION_OF_DUTIES` (403)** — either (a) on an appraisal request, the appraiser's `linked_member_id` equals the target item's `declared_by_member_id`, or (b) on an estate plan approval, `X-User-ID` equals the plan's `executor_member_id`. Applies to appraisal requests and estate plan approvals.
17. **`ERR_APPRAISAL_WINDOW_CONFLICT` (409)** — the appraisal inspection hold overlap of §3.4. Applies to appraisal requests.
18. **`ERR_SHARE_WINDOW_OVERLAP` (409)** — the share window overlap of §3.9. Applies to share-grant creation.
19. **`ERR_SHARE_WINDOW_TOO_LONG` (422)** — the requested share window is longer than `SHARE_MAX_DURATION_DAYS`, which is 90 days. Applies to share-grant creation.
20. **`ERR_EVIDENCE_TIER_INSUFFICIENT` (422)** — the item's `evidence_tier` ranks below `CLAIM_MIN_EVIDENCE_TIER`, which is `PHOTO_SERIAL` (rank 2). Applies to claim-line creation.
21. **`ERR_APPRAISAL_REQUIRED` (422)** — the item's `valuation_state` is `APPRAISAL_REQUIRED`. Applies to claim-line creation and to item scheduling.
22. **`ERR_SERIAL_REQUIRED` (422)** — the `CategorySchedule` for the submitted `category` has `serial_required` true and the submitted `serial_number` is null or empty. Applies to item creation, item patch and item replacement.
23. **`ERR_DUPLICATE_SERIAL` (409)** — another item in the same household already carries this `serial_number` and its `lifecycle_state` is `DRAFT`, `CATALOGED` or `FROZEN`. Applies to item creation, item patch and item replacement.
24. **`ERR_INVALID_QUANTITY` (422)** — an item `quantity` outside 1 through 999 inclusive, an allocation `quantity` below 1, or a `claimed_quantity` outside 1 through the item's `quantity` inclusive. Applies to item creation, item patch, item replacement, allocation creation and claim-line creation.
25. **`ERR_ALLOCATION_OVER_QUANTITY` (409)** — the requested allocation `quantity` added to the item's current `allocated_quantity` under this plan would exceed the item's `quantity`. Applies to allocation creation.
26. **`ERR_ITEM_NOT_DISPOSABLE` (409)** — the item being allocated is not dispositionable: its `lifecycle_state` is `FROZEN`, or an appraisal on it sits in status `REQUESTED`. Applies to allocation creation.
27. **`ERR_PLAN_NOT_FULLY_ALLOCATED` (422)** — the plan's `unallocated_item_count` is greater than zero at propose time. Applies to plan proposal.
28. **`ERR_PLAN_UNBALANCED` (409)** — the plan's `balanced` flag is false and the approval request did not set `override_unbalanced` to true. Applies to plan approval.
29. **`ERR_DUPLICATE_CLAIM_LINE` (409)** — a claim line for this claim and this `item_id` already exists. Applies to claim-line creation.
30. **`ERR_APPEAL_LIMIT_REACHED` (409)** — the line's `appeal_count` has already reached `MAX_APPEALS_PER_LINE`, which is 2. Applies to claim-line appeal.
31. **`ERR_PACKAGE_EMPTY` (422)** — the eligible item set for package generation is empty. Applies to package generation.
32. **`ERR_QUOTA_EXCEEDED` (402)** — a storage quota of the household's current tier would be breached by this create. Applies to item creation, asset upload and item replacement.
33. **`ERR_DOWNGRADE_BLOCKED_BY_USAGE` (409)** — the target tier's `max_items`, `max_assets` or `max_asset_bytes` is strictly less than the household's current usage. Applies to tier change and to reinstatement.
34. **`ERR_NO_APPRAISAL_CREDITS` (402)** — the subscription's `appraisal_credits_remaining` is zero. Applies to appraisal requests.
35. **`ERR_PACKAGE_QUOTA_EXCEEDED` (402)** — `packages_used_this_period` has reached or passed the tier's `included_packages_per_period`. Applies to package generation.
36. **`ERR_ALLOWANCE_EXCEEDED` (409)** — the requested `scheduled_value_cents` is strictly greater than the policy's `scheduled_remaining_cents`. A request for exactly the remaining amount succeeds. Applies to item scheduling.
37. **`ERR_ALLOWANCE_BELOW_CONSUMED` (409)** — a policy patch would set `scheduled_allowance_cents` strictly below the policy's current `scheduled_consumed_cents`. Applies to the policy patch.
38. **Optimistic concurrency, evaluated last** — the supplied expected-version field does not match its parent's current `version`. Routes to `ERR_STALE_POLICY_VERSION`, `ERR_STALE_SUBSCRIPTION_VERSION`, `ERR_STALE_HOUSEHOLD_VERSION` or `ERR_STALE_PLAN_VERSION` (all HTTP 412) according to §2.10. Applies to item scheduling, tier change, package generation and allocation creation.

### 2.9. The Version-Bump Ledger

A row that the operation creates enters at `version` 1 and is not listed as bumped. A parent counter that is recomputed to the value it already held is not a mutation and does not bump. Recomputing a derived valuation in place — for example refreshing an item's `acv_value_cents` because the clock moved — does not bump a version unless a transition listed here says it does.

### 2.10. Optimistic Concurrency Control

Four write endpoints require the caller to declare which version of a parent row it believed it was writing against. In each case the field is a **required** body field, not an optional one, and a mismatch with the parent's current `version` is rejected at ladder rung 38. Endpoints not named here take no expected-version field at all.

- **Item scheduling** requires `expected_policy_version`, carrying the client's last observed `version` of the target `Policy`. If another writer has advanced that policy's version since the client read it, the scheduling request is rejected with `ERR_STALE_POLICY_VERSION` (HTTP 412). The reason is the allowance ledger: another rider may already have consumed part of the same `scheduled_allowance_cents` pool, so the client's view of `scheduled_remaining_cents` no longer exists and its request is sized against a number that is gone.
- **Tier change** requires `expected_subscription_version`, carrying the client's last observed `version` of the `Subscription`. A mismatch is rejected with `ERR_STALE_SUBSCRIPTION_VERSION` (HTTP 412). Proration is priced from `period_start_at` and `monthly_fee_cents`, both of which an earlier billing event or tier change may already have rewritten, so a stale version means the client priced the change against a superseded period.
- **Package generation** requires `expected_household_version`, carrying the client's last observed `version` of the `Household`. A mismatch is rejected with `ERR_STALE_HOUSEHOLD_VERSION` (HTTP 412). Generation freezes a snapshot of the household and supersedes the prior delivered package, so a client working from a stale household version would freeze a picture that no longer exists.
- **Allocation creation** requires `expected_estate_plan_version`, carrying the client's last observed `version` of the `EstatePlan`. A mismatch is rejected with `ERR_STALE_PLAN_VERSION` (HTTP 412). Every allocation consumes units out of the plan-wide conservation budget, so a writer holding a stale plan version is sizing its `quantity` against an unallocated remainder another allocation already claimed.

Note the interaction with hook H2 of §2.7: because H2 can itself bump `Household.version` when a posture value changes, a client that read a household before its subscription drifted into a new refresh band must re-read before generating a package.

### 2.12. Conservation Invariants

Three quantities in this system are conserved. Each has a forward operation, a compensating operation, and an invariant that must hold after any round trip of the two.

**Invariant 1 — scheduled allowance cents on a policy.** A policy's `scheduled_consumed_cents` always equals the sum of `scheduled_value_cents` over the items whose `coverage_mode` is `SCHEDULED` and whose `scheduled_policy_id` names that policy, and its `scheduled_remaining_cents` always equals `scheduled_allowance_cents` minus `scheduled_consumed_cents`. Scheduling an item is the forward step; unscheduling it is the compensating step, and it releases exactly the amount that item consumed — never a recomputed or approximate amount. After a schedule-then-unschedule round trip on the same item both figures return to their exact pre-schedule values, including when other items were scheduled in between. Items that leave for `REPLACED` or `DISPOSED` release their allowance as part of those transitions and never linger in the sum.

**Invariant 2 — the count of frozen item records.** A household's `frozen_item_count` always equals the number of its items whose `lifecycle_state` is `FROZEN`; every such item carries a non-null `frozen_by_claim_id` pointing at a loss claim whose status is `OPEN`, `SUBMITTED`, `UNDER_REVIEW` or `SUPPLEMENT_REQUESTED`; and `records_freeze_active` is true exactly when `frozen_item_count` is greater than zero. Opening a claim is the forward step; withdrawing it is the compensating step, and it unfreezes exactly the items whose `frozen_by_claim_id` names that claim — not every frozen item of the household — so a second claim's freeze survives the first claim's withdrawal untouched. After an open-then-withdraw round trip both `frozen_item_count` and `records_freeze_active` return to their exact pre-claim values.

**Invariant 3 — allocated units of an item.** For every `CATALOGED` item of a plan's household, `allocated_quantity` equals the sum of `quantity` over that item's allocations under the plan, and never exceeds the item's own `quantity`; the plan's `unallocated_item_count` equals the number of such items whose `allocated_quantity` is strictly less than their `quantity`. Creating an allocation is the forward step, deleting it the compensating one, and after a create-then-delete round trip both `allocated_quantity` and `unallocated_item_count` return to their exact prior values. Only `CATALOGED` items are inside this scope: `DRAFT`, `FROZEN`, `REPLACED` and `DISPOSED` items are outside it, which is precisely why a claim freeze forces a proposed plan back to `DRAFT` rather than silently shrinking the count.

## 3. Business Logic & Workflows

### 3.1. Households, Members and the People Who Act on Them

A person enters the platform as a **Member**, identified by an `email` that must be unique across the whole platform — a second registration with an email that already exists is rejected with `ERR_INVALID_REQUEST` — and a `full_name`. Registration accepts two optional fields, `member_role` and `household_id`. Omitting `household_id` self-registers an unattached person, and in that case `member_role` is set to `OWNER`; supplying `household_id` attaches the person to an existing household, and in that case `member_role` falls back to `LIMITED`. The declared default on the field itself is `LIMITED`; the `OWNER` value comes from the self-registration path. A caller may name the role explicitly, in which case the value must be one of `OWNER`, `LIMITED`, `EXECUTOR` or `HEIR`. Attaching a member to an existing household is a homeowner's act; self-registration is the one write an `Anonymous` caller may perform.

An unattached owner then creates the **Household** itself, supplying a `name` and an `address_label` — the free-text location label that later appears on documentation packages. Creating the household writes the new household's id onto the acting member's `household_id` and forces that member's `member_role` to `OWNER`, and the household's `write_gate_state` initialises to `OPEN`.

Everything else on a household is derived and is never written directly. `item_count` counts the household's items whose `lifecycle_state` is `DRAFT`, `CATALOGED` or `FROZEN`. `asset_count` counts evidence blobs with `status` `STORED` across all of the household's items, and `asset_bytes_used` sums their `byte_size`. `frozen_item_count` counts items in `FROZEN`, and `records_freeze_active` mirrors whether that count is above zero. `active_share_count` counts share grants whose `status` is `ACTIVE`. `total_effective_value_cents` sums `effective_value_cents` over the household's items whose `lifecycle_state` is `CATALOGED` or `FROZEN` — draft, replaced and disposed items contribute nothing.

Members are readable individually and as a filtered list, where `household_id` and `member_role` narrow the result and provide the reverse lookup from a household to its people. Households are readable individually by everyone with a stake in them, while the platform-wide household list, filterable by `write_gate_state`, is reserved to `PlatformAdmin`.

### 3.2. The Subscription: Two Clocks Running Side by Side

A household holds at most one **Subscription**, opened by the homeowner with a `household_id` and a `tier`. It opens in `status` `TRIAL` and `refresh_state` `CURRENT`, with `period_start_at` set to the current logical instant, `period_end_at` set to `period_start_at` plus the 30-day billing period, `refresh_due_at` set to `created_at` plus the 365-day refresh interval, `appraisal_credits_remaining` set to the tier's included credit allowance, `packages_used_this_period` at 0, `monthly_fee_cents` copied from the tier table and `last_proration_charge_cents` at 0.

The three tiers are fixed configuration. `BASIC` costs 900 cents a month and allows 50 items, 200 stored assets, 2,000,000,000 stored bytes, 1 household, 0 included appraisal credits and 1 documentation package per period; its tier rank is 1. `PLUS` costs 2,900 cents a month and allows 500 items, 2,000 assets, 20,000,000,000 bytes, 2 households, 2 included appraisal credits and 4 packages per period; its tier rank is 2. `ESTATE` costs 7,900 cents a month and allows 5,000 items, 20,000 assets, 200,000,000,000 bytes, 5 households, 6 included appraisal credits and 12 packages per period; its tier rank is 3. The household allowance on each tier records how many households the plan is sold for; every quota that this service enforces — items, assets, bytes, credits and packages — is enforced per household against the tier the household's own subscription holds.

**The billing axis.** A `PlatformAdmin` drives `status` by posting a billing event whose `outcome` is one of `PAYMENT_SUCCEEDED`, `PAYMENT_FAILED`, `LAPSE` or `CLOSE`.

- From `TRIAL`, a `PAYMENT_SUCCEEDED` outcome moves the subscription `TRIAL → ACTIVE`. It resets `period_start_at` to the current instant, recomputes `period_end_at` as 30 days later, reassigns `appraisal_credits_remaining` to the tier's included credits and resets `packages_used_this_period` to 0. The household's `write_gate_state` is recomputed.
- From `TRIAL`, a `LAPSE` outcome moves `TRIAL → LAPSED`, but only once the clock has reached or passed the subscription's `created_at` plus the 14-day trial length; before that the transition's precondition fails. Lapsing sets the household's `write_gate_state` to `READ_ONLY`, and every share grant on the household whose `status` is `ACTIVE` **and** whose `redaction_level` is `FULL` moves to `VOIDED_BY_SCOPE` with `voided_reason` `SUBSCRIPTION_LAPSED`; grants at `VALUES_HIDDEN` or `SERIALS_HIDDEN` are left alone. `active_share_count` drops by one for each grant voided.
- From `ACTIVE`, a `PAYMENT_FAILED` outcome moves `ACTIVE → PAST_DUE` and stamps `past_due_since_at` with the current instant. A past-due household keeps **full** write access — `write_gate_state` does not change.
- From `PAST_DUE`, a `PAYMENT_SUCCEEDED` outcome moves `PAST_DUE → ACTIVE`, clears `past_due_since_at` to null, resets `period_start_at` to now with `period_end_at` recomputed, reassigns `appraisal_credits_remaining` to the tier's included credits — an assignment, so an unused balance is discarded and never rolls over — and resets `packages_used_this_period` to 0.
- From `PAST_DUE`, a `LAPSE` outcome moves `PAST_DUE → LAPSED`, but only once the clock has reached or passed `past_due_since_at` plus the 10-day past-due grace. This is a four-hop cascade. Hop 1 sets `status` to `LAPSED`. Hop 2, caused by hop 1, sets the household's `write_gate_state` to `READ_ONLY` — the global write gate. Hop 3, caused by hop 2, moves every share grant on that household with `status` `ACTIVE` and `redaction_level` `FULL` to `VOIDED_BY_SCOPE` with `voided_reason` `SUBSCRIPTION_LAPSED`; grants at the two partial redaction levels do not fire this hop. Hop 4, caused by hop 3, recomputes `active_share_count` as the count of grants still `ACTIVE`.
- From `LAPSED`, a `CLOSE` outcome moves `LAPSED → CLOSED`, and the household's `write_gate_state` stays `READ_ONLY` permanently. `CLOSED` is terminal: every further billing event on that subscription is rejected with `ERR_ALREADY_TERMINAL`.

Reinstatement is the homeowner's own path back. It moves `LAPSED → ACTIVE` and is allowed only while the household's usage still fits the tier it holds — its `item_count` at most the tier's item allowance, its `asset_count` at most the asset allowance and its `asset_bytes_used` at most the byte allowance. When any of the three is exceeded the request is refused with `ERR_DOWNGRADE_BLOCKED_BY_USAGE`. Reinstatement clears `past_due_since_at`, resets `period_start_at` to now with `period_end_at` recomputed, reassigns `appraisal_credits_remaining` and zeroes `packages_used_this_period`. The household then becomes `RESTRICTED` if its `refresh_state` is `OVERDUE` and `OPEN` otherwise. Share grants voided with reason `SUBSCRIPTION_LAPSED` are **not** restored — `VOIDED_BY_SCOPE` is terminal.

**The refresh axis.** Running on the very same subscription row, and entirely independently of the billing axis, is `refresh_state`: a past-due subscription can be refresh-`CURRENT`, and an active subscription can be refresh-`OVERDUE`. The axis is a set of bands measured from `refresh_due_at`, which is `last_attested_at` — or, before the first attestation, `created_at` — plus the 365-day refresh interval. While the clock is before `refresh_due_at` the state is `CURRENT`. From `refresh_due_at` up to but not including 15 days after it, the state is `DUE`. From 15 days after `refresh_due_at` up to but not including 30 days after it, the state is `GRACE`. At 30 days after `refresh_due_at` and beyond, the state is `OVERDUE`. Every band boundary is inclusive on its lower edge and exclusive on its upper edge. These bands are evaluated only by the two posture hooks of §2.7, and each band change bumps the subscription's `version` by one. A single clock jump that crosses several boundaries at once collapses `CURRENT → DUE → GRACE → OVERDUE` in one recomputation: the terminal band wins and exactly one version increment is applied. Reaching `OVERDUE` is what sets the household to `RESTRICTED`, provided the billing axis is neither `LAPSED` nor `CLOSED`.

Attesting the refresh is the homeowner's act and is legal from every band, including `CURRENT`, where it is an early attestation that simply pushes the window forward — that self-loop is what makes this axis cyclic. An attestation may carry an optional `attestation_note`. It requires only that `status` is not `CLOSED`. It stamps `last_attested_at` with the current instant, recomputes `refresh_due_at` as 365 days after that instant, and returns `refresh_state` to `CURRENT` — the four legal moves being `DUE → CURRENT`, `GRACE → CURRENT`, `OVERDUE → CURRENT` and the `CURRENT → CURRENT` self-loop of an early attestation. From `OVERDUE` it additionally returns the household's `write_gate_state` to `OPEN`, unless `status` is `LAPSED`, in which case the household stays `READ_ONLY`. Attestation is on the write-gate exclusion list, so a lapsed household may still attest.

**Changing tier.** A homeowner may change `tier`, supplying the new `tier`, the required `expected_subscription_version` and an optional `proration_mode`. Changing to the tier the subscription already holds is rejected with `ERR_INVALID_STATE`. Changing to a tier whose item, asset or byte allowance is strictly below the household's current usage is rejected with `ERR_DOWNGRADE_BLOCKED_BY_USAGE`. Otherwise the proration runs. The old fee is the monthly fee of the tier held before the change; the new fee is the monthly fee of the requested tier. Elapsed days are the whole days from `period_start_at` to the current instant, rounded down and then clamped to the range from 0 to 30; remaining days are 30 minus that clamped figure. Under the `DAILY` mode — the default when `proration_mode` is omitted — the credit is the old fee multiplied by remaining days divided by 30, rounded half up to whole cents, the charge is the new fee multiplied by remaining days divided by 30, rounded half up to whole cents, and `last_proration_charge_cents` is the charge minus the credit, which may be negative. Under the `WHOLE_PERIOD` mode, `last_proration_charge_cents` is simply the new fee minus the old fee, with no proration at all; the two modes differ by the fee delta multiplied by elapsed days divided by 30. Either way the credit and the charge are rounded **separately** before being subtracted. Both modes then set `tier` to the requested tier, set `monthly_fee_cents` to the new fee, and clip `appraisal_credits_remaining` down to the new tier's included credits — taking the smaller of the current balance and the new allowance, so a downgrade never grows a balance and an upgrade never grants credits mid-period. A tier change does **not** reset `period_start_at`.

**Quota arithmetic.** Three usage figures drive every quota decision: item usage is the count of the household's items in `DRAFT`, `CATALOGED` or `FROZEN`; asset usage is the count of its evidence blobs with `status` `STORED`; and byte usage is the sum of `byte_size` over those same stored blobs. Replaced, disposed and soft-deleted rows are excluded from all three, which is why a replacement is quota-neutral only after the predecessor leaves the counted set. At create time the check is prospective: an item create is refused when item usage plus one would exceed the tier's item allowance, and an asset upload is refused when asset usage plus one would exceed the asset allowance or when byte usage plus the new `byte_size` would exceed the byte allowance — all with `ERR_QUOTA_EXCEEDED`. At downgrade time the check is retrospective and uses the same three comparisons against the target tier's allowances, and reinstatement runs those comparisons against the tier the subscription already holds.

### 3.3. The Room-by-Room Walkthrough: Rooms, Items and Evidence

A household is divided into **Rooms**, each created with a `household_id`, a `name` such as "Primary Bedroom", and a `floor_label` that orders the walkthrough by level. A room carries its own derived `item_count`, counting the room's items in `DRAFT`, `CATALOGED` or `FROZEN`.

**Items.** An item is created with a `household_id`, a `room_id` naming a room of that same household, a `name`, a `category`, an `acquired_at` instant, and optionally a `quantity`, a `serial_number`, a `purchase_price_cents` and a `replacement_cost_cents`. The ten categories are `JEWELRY`, `FINE_ART`, `ELECTRONICS`, `FURNITURE`, `APPLIANCE`, `COLLECTIBLE`, `MUSICAL_INSTRUMENT`, `FIREARM`, `WATCH` and `GENERAL`, and the submitted category must match an existing category schedule. `quantity` defaults to 1 and must be between 1 and 999 inclusive. A new item lands in `lifecycle_state` `DRAFT` with `evidence_tier` `NONE`, `valuation_state` `UNVALUED`, `effective_value_cents` 0, `effective_value_basis` `NONE`, `coverage_mode` `BLANKET`, `scheduled_policy_id` null, `scheduled_value_cents` 0, `declared_value_cents` 0, `declared_by_member_id` null, `replaces_item_id` null, `serial_chain_intact` true, `allocated_quantity` 0 and `frozen_by_claim_id` null; its `acv_value_cents` is computed immediately against the current clock. Creating an item raises both the household's and the room's `item_count`.

Serial numbers carry two rules. When the category schedule governing the submitted `category` has `serial_required` true and no `serial_number` is supplied, the request fails with `ERR_SERIAL_REQUIRED`. And a `serial_number` must be unique within the household among items whose `lifecycle_state` is `DRAFT`, `CATALOGED` or `FROZEN`; a collision fails with `ERR_DUPLICATE_SERIAL`. Rows in `REPLACED` or `DISPOSED` sit outside that uniqueness scope, which is exactly what lets a replacement reuse its predecessor's serial. Both rules are enforced on item creation, on the item patch, and on item replacement.

A `Homeowner` or a `HouseholdMember` may patch an item's `name`, `room_id`, `serial_number`, `purchase_price_cents`, `replacement_cost_cents` and `quantity`. A patch that changes `serial_number` re-derives the evidence tier first and then the effective value; any other patch re-derives the effective value only.

**Evidence assets.** Evidence is uploaded one blob at a time against an item, each carrying an `asset_kind`, a `byte_size` of at least 1, a `checksum` supplied by the client and a `captured_at` instant recording when the photograph or scan was taken. The five kinds are `PHOTO`, `SERIAL_PLATE`, `RECEIPT`, `PROVENANCE_DOC` and `APPRAISAL_PDF`. An asset lives in `status` `STORED` until it is soft-deleted, at which point its `status` becomes `DELETED`; deleted assets leave the household's `asset_count` and `asset_bytes_used` and stop contributing to any evidence computation, but the row itself remains readable.

**The evidence tier.** An item's `evidence_tier` is recomputed wholesale — never incrementally — at the end of every asset upload, every asset deletion, and every item patch that changes `serial_number`. Three predicates drive it. The photo predicate holds when the item has at least one stored asset of kind `PHOTO`. The serial predicate holds when the item has at least one stored asset of kind `SERIAL_PLATE` **or** its `serial_number` is not null. The document predicate holds when the item has at least one stored asset of kind `RECEIPT` or `PROVENANCE_DOC`. The tier is `DOCUMENTED` when all three hold; otherwise `PHOTO_SERIAL` when the photo and serial predicates hold; otherwise `PHOTO_ONLY` when the photo predicate holds; otherwise `NONE`. An `APPRAISAL_PDF` asset counts toward the storage quotas but participates in none of the three predicates and therefore never raises the tier. The four tiers form an ordinal ladder used by every comparison in this document: `NONE` ranks 0, `PHOTO_ONLY` ranks 1, `PHOTO_SERIAL` ranks 2 and `DOCUMENTED` ranks 3. Claim lines demand at least `PHOTO_SERIAL`; package generation demands at least `PHOTO_ONLY`.

Because the tier is recomputed wholesale, **any** pair of old and new tiers that the recomputation produces is legal, including multi-step jumps. The canonical upgrades are four. Uploading the first `PHOTO` to an item that has no other stored asset and no `serial_number` moves it `NONE → PHOTO_ONLY`; the household's `asset_count` and `asset_bytes_used` rise. Uploading a `SERIAL_PLATE` to an item that already has a stored `PHOTO`, or patching a `serial_number` onto it, moves it `PHOTO_ONLY → PHOTO_SERIAL` and makes it eligible for a claim line. Uploading a `RECEIPT` or a `PROVENANCE_DOC` to an item already at `PHOTO_SERIAL` moves it `PHOTO_SERIAL → DOCUMENTED`. And uploading the first `PHOTO` to an item that already carries a non-null `serial_number` jumps straight from `NONE → PHOTO_SERIAL`.

The canonical downgrades are three, and they are where the consequences live. Deleting the last stored `RECEIPT` or `PROVENANCE_DOC` moves the item `DOCUMENTED → PHOTO_SERIAL` and lowers `asset_count` and `asset_bytes_used`. Deleting the last stored `PHOTO`, leaving none behind, moves the item `PHOTO_ONLY → NONE` and excludes it from every future package generation, because it now sits below the package minimum. And deleting the last stored `SERIAL_PLATE` from an item whose `serial_number` is null moves it `PHOTO_SERIAL → PHOTO_ONLY` — the four-hop evidence-downgrade cascade. Hop 1 sets the asset's `status` to `DELETED`. Hop 2, caused by hop 1, recomputes the item's `evidence_tier` downward to `PHOTO_ONLY`. Hop 3, caused by hop 2, moves every claim line on this item that is still in status `PENDING` to `DENIED` with `denial_reason` `EVIDENCE_INSUFFICIENT`, because `PHOTO_ONLY` now ranks below the claim minimum; its `net_settlement_cents` is forced to 0. Hop 4, caused by hop 3, recomputes each affected claim's `denied_line_count`, and where that count now equals the claim's `line_count` and the claim sits in `UNDER_REVIEW`, the claim itself moves `UNDER_REVIEW → DENIED`. Hop 3 fires only for lines in `PENDING`: lines already `APPROVED`, `DENIED` or `APPEALED` are untouched, and if the item has no pending lines the cascade stops after hop 2. Deleting evidence is a homeowner-only act, and it is refused outright with `ERR_ITEM_FROZEN` while the item is frozen by a claim.

**The draft-to-catalogued gate.** An item moves `DRAFT → CATALOGED` automatically, never by a dedicated call. The predicate is evaluated at the end of every asset upload and every value declaration, and it holds when the item's `evidence_tier` is anything other than `NONE` **and** its `declared_value_cents` is strictly greater than zero — whichever of the two calls completes the pair is the one that flips the item. Neither the household's nor the room's `item_count` moves, because draft items were already counted; the household's `total_effective_value_cents` is recomputed, because a catalogued item now contributes.

**Replacement.** When a homeowner replaces an item — after a repair, an upgrade or a re-photograph — they submit a `name`, an `acquired_at`, and optionally a `serial_number`, a `purchase_price_cents`, a `replacement_cost_cents` and a `quantity`. The predecessor must be `CATALOGED` and must not be frozen by a claim. A new item row is created in `DRAFT` with `replaces_item_id` pointing at the predecessor and inheriting the predecessor's `household_id`, `room_id` and `category`. The new row's `serial_chain_intact` is true when the submitted `serial_number` equals the predecessor's `serial_number` and false otherwise — a broken provenance chain is recorded, not rejected. The predecessor moves `CATALOGED → REPLACED`, and if it was individually scheduled its allowance is released: the policy's `scheduled_consumed_cents` falls by exactly the amount that item consumed, `scheduled_remaining_cents` is recomputed, and the predecessor's `coverage_mode` returns to `BLANKET` with `scheduled_policy_id` null and `scheduled_value_cents` 0. Once the predecessor is `REPLACED` its `serial_number` is free for reuse. Replacement is subject to the storage quota, so a household at its item ceiling cannot replace until it has room.

Items are readable individually and as a list filtered by `household_id`, `room_id`, `declared_by_member_id`, `scheduled_policy_id`, `replaces_item_id`, `frozen_by_claim_id`, `evidence_tier`, `lifecycle_state` and `valuation_state`. Assets are readable individually and as a list filtered by `item_id`, `status` and `asset_kind`.

### 3.4. Valuation: Declared, Depreciated and Certified

**Category schedules.** A `PlatformAdmin` configures one **CategorySchedule** per item category, and the row is the depreciation and coverage configuration for that whole category. It carries the `category` it governs, a `useful_life_months` figure recorded for documentation, an `annual_depreciation_pct` straight-line rate, a `salvage_floor_pct` below which depreciation may never push the value, a `blanket_sublimit_cents` ceiling shared by every unscheduled item in that category, an `appraisal_scope` naming the credential scope required to certify items in the category, and an optional `serial_required` flag that defaults to false. The eight appraisal scopes are `JEWELRY`, `FINE_ART`, `ELECTRONICS`, `COLLECTIBLE`, `MUSICAL_INSTRUMENT`, `FIREARM`, `WATCH` and `GENERAL` — note that `FURNITURE` and `APPLIANCE` are item categories but not credential scopes, so a schedule for either must nominate one of the eight scopes above.

**Declared value.** A `Homeowner` or `HouseholdMember` records what the household believes an object is worth by submitting a `declared_value_cents`. The call writes that figure, stamps `declared_by_member_id` with the caller's `X-User-ID` — the input to the segregation-of-duties bar below — re-runs the valuation resolution, and may complete the draft-to-catalogued gate.

**Actual cash value.** The depreciated value of an item is computed from its `purchase_price_cents`, its `acquired_at`, the category schedule for its `category`, and an as-of instant. When `purchase_price_cents` is null, or when no category schedule exists for the item's category, the actual-cash-value regime is unavailable and the result is 0. Otherwise: elapsed days are the whole days from `acquired_at` to the as-of instant, rounded down; the age in months is those elapsed days divided by 30 and rounded down, never below zero, so a month here is a flat 30 days rather than a calendar month; the depreciated percentage is the category's `annual_depreciation_pct` divided by 12 and multiplied by the age in months, capped at 100; the raw amount is `purchase_price_cents` multiplied by one minus the depreciated percentage divided by one hundred; the salvage floor is `purchase_price_cents` multiplied by `salvage_floor_pct` divided by one hundred; and the result is the larger of the raw amount and the salvage floor, rounded half up to whole cents **once**, at the very end. No intermediate is rounded.

That single curve is evaluated at three different as-of instants, and the three answers differ. In the **current-clock** variant the as-of instant is the logical clock's current instant; this is what writes `acv_value_cents` and what feeds the effective-value resolution on every ordinary read or write. In the **loss-date** variant the as-of instant is the claim's `loss_date`, used when computing a claim line's gross value on an `ACV`-basis claim; because the loss date precedes the clock, the age in months is smaller and the value is strictly higher for any item whose depreciation has not yet reached its salvage floor — identical item data, two different numbers. In the **snapshot** variant the as-of instant is the package's `generated_at`, pinned into the package line and never recomputed afterwards.

**Which value wins.** An item's `effective_value_cents` and `effective_value_basis` come from a strict precedence order in which the first matching regime wins. The **appraisal** regime is considered first: the candidates are the item's appraisals whose `status` is `CERTIFIED` and whose `valid_until_at` is strictly after the current instant. If any candidate exists, the winner is the one with the greatest `certified_at`, with ties broken by the earlier `created_at` and then by creation order; `effective_value_cents` becomes that appraisal's `appraised_value_cents`, `effective_value_basis` becomes `APPRAISAL`, and `valuation_state` becomes `CERTIFIED`. Failing that, the **actual-cash-value** regime applies when `purchase_price_cents` is not null and a category schedule exists for the item's category: `effective_value_cents` becomes the current-clock actual cash value and `effective_value_basis` becomes `ACV`. Failing that, the **declared** regime applies when `declared_value_cents` is strictly greater than zero: `effective_value_cents` becomes `declared_value_cents` and `effective_value_basis` becomes `DECLARED`. Failing all three, the value is 0 with basis `NONE`.

For every non-appraisal outcome the `valuation_state` is decided afterwards, in this order: when `declared_value_cents` is at or above 1,000,000 cents — the appraisal-required threshold — the state is `APPRAISAL_REQUIRED`, regardless of which of the two remaining regimes supplied the number; otherwise, when the basis is `ACV` or `DECLARED`, the state is `DECLARED_ONLY`; otherwise it is `UNVALUED`. The resolution is re-run whenever an item's assets, declared value, serial number or appraisals change, and at the end of every clock advance. Note the trap: an item that owns a valid certified appraisal reports `CERTIFIED` even when its declared value is above the threshold, and it drops to `APPRAISAL_REQUIRED` the moment that appraisal is voided or expires.

**Appraisers.** A `PlatformAdmin` registers an **Appraiser** with a `display_name`, a `credential_id` unique across appraisers, a non-empty `scope_categories` array drawn from the eight appraisal scopes, and an optional `linked_member_id`. A non-null `linked_member_id` marks this appraiser as also being a household member, and that is what activates the segregation-of-duties bar. An appraiser opens in `status` `ACTIVE` and may be suspended by the admin to `SUSPENDED`, after which any certification attempt fails with `ERR_INVALID_STATE`.

**Requesting an appraisal.** A homeowner requests an appraisal with an `item_id`, an `appraiser_id`, an `inspection_start_at` and an `inspection_end_at` that must be strictly after the start. The new row opens in `status` `REQUESTED` with `requested_by_member_id` stamped from `X-User-ID`, `appraised_value_cents` null, `certified_at` null, `valid_until_at` null and `void_reason` null. Four checks guard it, in ladder order. The appraiser's `scope_categories` must contain the `appraisal_scope` of the category schedule governing the item's `category`, or the request fails with `ERR_APPRAISER_SCOPE_MISMATCH`. The appraiser's `linked_member_id` must not equal the item's `declared_by_member_id` — the party who declared a value may not be the party who certifies it — or the request fails with `ERR_SEGREGATION_OF_DUTIES`. The requested inspection window must not collide with an existing hold: taking the new window as a **closed** interval from `inspection_start_at` to `inspection_end_at` and widening it by 24 hours on **both** sides, it must not intersect the un-widened closed interval of any other appraisal on the same item whose `status` is `REQUESTED` or `CERTIFIED`; touching endpoints count as intersecting, and a collision fails with `ERR_APPRAISAL_WINDOW_CONFLICT`. Finally the subscription must have at least one credit: `appraisal_credits_remaining` is decremented by one and the appraisal's `credit_consumed` is set true, or, when the balance is already zero, the request fails with `ERR_NO_APPRAISAL_CREDITS`. A `BASIC` household has zero included credits, so its very first appraisal request is refused. Requesting an appraisal against an item frozen by a claim is refused earlier still, with `ERR_ITEM_FROZEN`.

**Certification.** The appraiser — and only the appraiser named on the row — certifies by submitting an `appraised_value_cents`. The appraisal must be in `REQUESTED`, the caller's `X-User-ID` must equal `appraiser_id`, the appraiser's own `status` must be `ACTIVE`, and the clock must have reached or passed `inspection_end_at`; certifying early or while suspended fails with `ERR_INVALID_STATE`. If the item is frozen the attempt fails at the records-freeze rung with `ERR_ITEM_FROZEN`, never with `ERR_INVALID_STATE`. Certification moves the appraisal `REQUESTED → CERTIFIED` in a four-hop cascade. Hop 1 writes `appraised_value_cents`, stamps `certified_at` with the current instant, and sets `valid_until_at` to 1,095 days after `certified_at`. Hop 2, caused by hop 1, re-runs the valuation resolution on the item so that `effective_value_cents` and `effective_value_basis` move to the certified figure and `APPRAISAL`, and `valuation_state` becomes `CERTIFIED`. Hop 3, caused by hop 2, recomputes the household's `total_effective_value_cents`. Hop 4, also caused by hop 2, recomputes `total_effective_value_cents` and `coverage_gap_cents` on **every** policy of the item's household, under the scheduled-first waterfall variant.

**Expiry.** A certified appraisal moves `CERTIFIED → EXPIRED` when the clock reaches or passes its `valid_until_at`. This is evaluated by the clock-advance hook and again as the first step of package generation. The item's `effective_value_basis` then falls back to `ACV` or `DECLARED` under the ordinary precedence, and when the item's `declared_value_cents` is at or above the 1,000,000-cent threshold its `valuation_state` becomes `APPRAISAL_REQUIRED`, which excludes it from package generation and refuses it for new claim lines.

**Voiding, and the deepest cascade in the system.** A `PlatformAdmin` voids an appraisal with a `void_reason` of `APPRAISER_WITHDRAWN`, `SCOPE_REVOKED` or `VALUE_DISPUTED`. From `REQUESTED`, voiding is the shallow `REQUESTED → VOIDED` move: the reason is written, the item's appraisal hold is released so its inspection window is free for a new request, and if `credit_consumed` was true the credit is **not** refunded — entitlements never roll back. From `CERTIFIED`, voiding is the `CERTIFIED → VOIDED` move and runs a five-hop cascade. Hop 1 sets `status` to `VOIDED` and writes `void_reason`. Hop 2, caused by hop 1, strips the appraisal basis from the item: `effective_value_cents`, `effective_value_basis` and `valuation_state` are all recomputed by the ordinary precedence, so the item falls back to `ACV`, to `DECLARED`, or to `APPRAISAL_REQUIRED` when its declared value is at or above the threshold. Hop 3, caused by hop 2, recomputes `total_effective_value_cents` and `coverage_gap_cents` on every policy of the item's household — this hop does **not** require the item to have been scheduled. Hop 4, caused by hop 3, moves every documentation package with one of those policy ids whose `status` is `GENERATED` to `EXPIRED`, **unconditionally**: the trigger is that hop 3 executed at all, not whether the recomputed `coverage_gap_cents` actually changed; packages in `DELIVERED`, `DRAFT` or already-terminal statuses are not moved by this hop. In the same hop, every package line — in any package, whatever its status — that references the affected item has its `stale` flag set to true, and the owning package's `stale_line_count` is recomputed. Hop 5, caused by hop 4, sets `settlement_hold` to true on every claim line still in `PENDING` whose claim's `package_id` is one of the packages hop 4 just expired, and recomputes `blocked_line_count` on each of those claims. A claim line already `APPROVED`, `DENIED` or `APPEALED` is not put on hold, and a pending line whose claim rests on a package that hop 4 did not expire is untouched. The credit consumed at request time is never refunded on this path either.

Appraisals are readable individually and as a list filtered by `item_id`, `appraiser_id`, `requested_by_member_id` and `status`; appraisers are readable individually and as a list filtered by `linked_member_id` and `status`; the category configuration table is readable as a list filtered by `category`.

### 3.5. Insurance Coverage: Policies, the Scheduling Ledger and the Coverage Gap

A household registers its **Policy** with a `household_id`, a `carrier_name`, a `policy_number`, a `deductible_cents` applied per claim, a `scheduled_allowance_cents` — the total value the carrier permits to be individually scheduled — and an `effective_from` inception instant. A new policy opens with `scheduled_consumed_cents` at 0, `scheduled_remaining_cents` equal to the full `scheduled_allowance_cents`, and `coverage_gap_cents` and `total_effective_value_cents` at 0. Both a `Homeowner` and an `InsuranceAgent` may register a policy; only the `InsuranceAgent` may afterwards patch its `carrier_name`, `deductible_cents` or `scheduled_allowance_cents`. A patch that would set `scheduled_allowance_cents` strictly below the policy's current `scheduled_consumed_cents` is refused with `ERR_ALLOWANCE_BELOW_CONSUMED` — individually every existing rider is fine, but collectively they no longer fit. Any accepted patch recomputes `scheduled_remaining_cents` and `coverage_gap_cents`.

Note the difference between the two "total effective value" figures the system reports. A **household**'s `total_effective_value_cents` sums `effective_value_cents` over its `CATALOGED` and `FROZEN` items with no evidence condition at all. A **policy**'s `total_effective_value_cents` sums the same field over the same lifecycle states but only for items whose `evidence_tier` is something other than `NONE`, because an item with no evidence is not something a carrier will underwrite. The two figures are expected to differ whenever a catalogued item has lost its last photograph.

**Scheduling an item.** A homeowner individually schedules a high-value item onto a policy by submitting the `policy_id`, the `scheduled_value_cents` this item should occupy, and the required `expected_policy_version`. An item whose `valuation_state` is `APPRAISAL_REQUIRED` cannot be scheduled and is refused with `ERR_APPRAISAL_REQUIRED`; an item frozen by a claim is refused earlier with `ERR_ITEM_FROZEN`. The requested amount must not exceed the policy's `scheduled_remaining_cents`: a request strictly greater is refused with `ERR_ALLOWANCE_EXCEEDED`, while a request for exactly the remaining amount succeeds and drives `scheduled_remaining_cents` to precisely 0. On success the item's `coverage_mode` becomes `SCHEDULED`, its `scheduled_policy_id` names the policy and its `scheduled_value_cents` records the amount; the policy's `scheduled_consumed_cents` rises by that amount, `scheduled_remaining_cents` falls by the same amount, and `coverage_gap_cents` is recomputed.

Unscheduling is the exact compensating action: the policy's `scheduled_consumed_cents` falls by the exact amount **that item** consumed and `scheduled_remaining_cents` rises by the same amount, while the item returns to `coverage_mode` `BLANKET` with `scheduled_policy_id` null and `scheduled_value_cents` 0. The round trip is lossless even when other items were scheduled in between, as §2.12 requires. The same release runs automatically when a scheduled item is replaced or disposed of.

**The coverage gap.** The gap read answers a single question — how much of the household's catalogued value the policy does not actually cover — and it can answer it two ways. The candidate set for both variants is every item of the policy's household whose `lifecycle_state` is `CATALOGED` or `FROZEN` and whose `evidence_tier` is not `NONE`, processed in `created_at` ascending order with the creation-order tie-break. Draft, replaced and disposed items are excluded, as are items with no evidence at all. Each candidate's value is its `effective_value_cents`.

Under the **`SCHEDULED_FIRST`** variant — the default, and the only variant ever written back to `Policy.coverage_gap_cents` — the scheduling allowance is spent first. Starting with the allowance pool set to the policy's `scheduled_allowance_cents`, each candidate in creation order that is `SCHEDULED` on **this** policy takes the smallest of three numbers: its own `scheduled_value_cents`, its effective value, and whatever remains in the allowance pool; that amount becomes its covered figure and leaves the pool. Every other candidate takes zero at this stage. Each candidate's residual is its effective value minus what it has been covered for so far. Then, with a fresh sublimit pool per category set to that category's `blanket_sublimit_cents`, each candidate in creation order takes the smaller of its residual and the remaining sublimit of its own category, adds it to its covered figure and removes it from that category's pool.

Under the **`BLANKET_FIRST`** variant the order is reversed. With a sublimit pool per category set to that category's `blanket_sublimit_cents`, each candidate in creation order takes the smaller of its effective value and its category's remaining sublimit as its covered figure, removing that amount from the category pool, and its residual is its effective value minus that amount. Then, with the allowance pool set to `scheduled_allowance_cents`, each candidate in creation order that is `SCHEDULED` on this policy takes the smallest of its residual, its `scheduled_value_cents` and the remaining allowance, adds it to its covered figure and removes it from the allowance pool. The two variants report different gaps for identical data whenever a scheduled item shares a category with unscheduled items and the sublimit binds, because under `BLANKET_FIRST` the early unscheduled items exhaust the sublimit the scheduled item would otherwise have fallen back on.

Both variants finish with the same tail. `total_value_cents` is the sum of the candidates' effective values, `total_covered_cents` is the sum of their covered figures, `coverage_gap_cents` is the first minus the second, and `item_count` is the number of candidates. `schedule_required_unscheduled_count` counts the candidates whose effective value is at or above the 500,000-cent scheduling threshold **and** whose `coverage_mode` is still `BLANKET` — an object that valuable which is not individually scheduled is only ever covered up to its category's shared sublimit, and this counter is the headline warning a documentation package is meant to surface. Every figure here is already whole cents, so no rounding is applied anywhere in the waterfall. The `SCHEDULED_FIRST` result is written back to `Policy.coverage_gap_cents` whenever an item's effective value, `coverage_mode` or `scheduled_value_cents` changes.

Policies are readable individually and as a list filtered by `household_id`.

### 3.6. Documentation Packages: Freezing the Evidence

A **DocumentationPackage** is the artefact a household hands to its carrier. The homeowner opens one with a `household_id` and a `policy_id`, and it starts in `status` `DRAFT` with `generated_at`, `delivered_at`, `expires_at`, `recipient_ref` and `superseded_by_package_id` all null, `line_count`, `stale_line_count` and all three snapshot totals at 0.

**Generation.** Generating — the `DRAFT → GENERATED` move — is the moment the package stops being a query and becomes a record. The request carries the required `expected_household_version`. Before anything else the service expires any certified appraisal whose `valid_until_at` the clock has reached, so a package can never be built on an appraisal that has just lapsed. The package must be in `DRAFT`; the household must be `OPEN`, since a `RESTRICTED` household is refused with `ERR_REFRESH_OVERDUE` and a `READ_ONLY` one with `ERR_VAULT_READ_ONLY`; `packages_used_this_period` must still be below the tier's included package allowance, or the request is refused with `ERR_PACKAGE_QUOTA_EXCEEDED`; and at least one eligible item must exist, or the request is refused with `ERR_PACKAGE_EMPTY`.

An item is **eligible** when all three of these hold: its `lifecycle_state` is `CATALOGED` or `FROZEN`; its `evidence_tier` ranks at or above `PHOTO_ONLY`; and its `valuation_state` is not `APPRAISAL_REQUIRED`. The eligible set is processed in `created_at` ascending order with the creation-order tie-break, and one immutable **PackageLine** is written per eligible item.

Each line's `snapshot_effective_value_cents` is the item's exact, unrounded effective value evaluated with an as-of instant of the package's `generated_at` — for an actual-cash-value item that is the larger of the depreciated amount and the salvage floor taken before any rounding, and for appraisal-basis and declared-basis items the figure is already a whole number of cents — and that exact value is then rounded half up **per line**. Each line's `snapshot_covered_cents` is the covered figure that item receives from the `SCHEDULED_FIRST` waterfall of §3.5 restricted to the eligible set. The remaining snapshot fields copy the item verbatim at that instant: `snapshot_name` from `name`, `snapshot_category` from `category`, `snapshot_evidence_tier` from `evidence_tier`, `snapshot_effective_value_basis` from `effective_value_basis` and `snapshot_coverage_mode` from `coverage_mode`. Every line starts with `stale` false.

The rounding order is pinned and is **not** interchangeable: round every line first, then sum the rounded lines. `snapshot_total_effective_cents` is the sum of the lines' `snapshot_effective_value_cents`, `snapshot_total_covered_cents` is the sum of their `snapshot_covered_cents`, `snapshot_coverage_gap_cents` is the first total minus the second, and `line_count` is the size of the eligible set. Summing the exact unrounded values and rounding the total once is explicitly forbidden; the two orders can differ by up to half a cent per line. Three items each with an exact value of 189,990.5 cents produce 569,973 under the pinned order and 569,972 under the forbidden one.

Generation also stamps `generated_at` with the current instant and sets `expires_at` to 180 days later, and then runs a four-hop cascade. Hop 1 creates the lines and freezes the totals as described. Hop 2, caused by hop 1, moves any prior documentation package for the **same** `policy_id` whose `status` is `DELIVERED` along `DELIVERED → SUPERSEDED`, writing `superseded_by_package_id` with the new package's id; a prior package still in `GENERATED` or `DRAFT` is not superseded, and neither is a package for a different policy. Hop 3, caused by hop 2, moves every share grant with `status` `ACTIVE` whose `scope_package_id` names that superseded package to `VOIDED_BY_SCOPE` with `voided_reason` `SCOPE_SUPERSEDED`. Hop 4, caused by hop 3, recomputes the household's `active_share_count`. Where hop 2 finds no delivered predecessor, hops 3 and 4 do not fire at all. Finally `packages_used_this_period` rises by one.

**Immutability.** From `GENERATED` onward the package body is frozen. No snapshot total, no line and no line field is ever recomputed — delivering the package does not recompute them, and neither does any later change to the underlying items. Exactly two fields keep moving after generation: `stale_line_count`, and `superseded_by_package_id`. A line's `stale` flag is set true when the item behind it has since diverged from the snapshot — that is, when the item's current `effective_value_basis` or `effective_value_cents` no longer matches the values frozen into that line — and the owning package's `stale_line_count` is the count of its lines whose `stale` flag is true.

**Delivery.** The homeowner or the insurance agent delivers a `GENERATED` package to a `recipient_ref` — an opaque agent email or portal id. Delivery is legal only while the clock is strictly before the package's `expires_at`; at or after it the attempt is refused with `ERR_INVALID_STATE`. Delivery stamps `delivered_at` and moves the package `GENERATED → DELIVERED`.

**Expiry.** A package reaches `EXPIRED` down two paths. The clock-advance hook moves a package `GENERATED → EXPIRED` or `DELIVERED → EXPIRED` once the clock reaches or passes its `expires_at`. The appraisal-void cascade of §3.4 moves a package `GENERATED → EXPIRED` unconditionally when hop 3 of that cascade touched a policy the package documents. However a package expires, two consequences follow: every claim line still in `PENDING` under a claim whose `package_id` names that package has its `settlement_hold` set to true and each such claim's `blocked_line_count` is recomputed, and every share grant with `status` `ACTIVE` whose `scope_package_id` names that package moves to `VOIDED_BY_SCOPE` with `voided_reason` `SCOPE_SUPERSEDED`. `SUPERSEDED` and `EXPIRED` are both terminal for a package.

Packages are readable individually and as a list filtered by `household_id`, `policy_id`, `superseded_by_package_id` and `status`; package lines are readable individually and as a list filtered by `package_id`, `item_id` and `stale`.

### 3.7. Post-Loss Claim Support

**Opening a claim.** After a fire, a burglary or a burst pipe, the homeowner opens a **LossClaim** against a frozen evidence package. The payload carries a `household_id`, the `package_id` of the package the claim is built on, a `policy_id` that must equal that package's own `policy_id`, a `loss_date`, a `peril` of `FIRE`, `THEFT`, `WATER`, `STORM` or `OTHER`, a `settlement_basis` of `ACV` or `RCV`, a non-empty `affected_room_ids` array whose every element is a room of that household, and an optional `deductible_mode` of `PRO_RATA` or `HIGHEST_VALUE_FIRST` that defaults to `PRO_RATA`. A package that is neither `GENERATED` nor `DELIVERED`, or a `policy_id` that does not match the package's, is refused with `ERR_INVALID_STATE`. Claim opening is on the write-gate exclusion list, so even a lapsed household may run a claim to completion.

Opening a claim runs the records-freeze cascade. Every item of the household whose `lifecycle_state` is `CATALOGED` **and** whose `room_id` appears in `affected_room_ids` moves `CATALOGED → FROZEN` with `frozen_by_claim_id` set to the new claim's id; the household's `frozen_item_count` rises by the number frozen, `records_freeze_active` becomes true, and the claim's own `frozen_item_count` records exactly how many rows it froze. Items in `DRAFT` in an affected room are **not** frozen and remain fully editable during the claim; items in unaffected rooms are likewise untouched. In addition, any estate plan in `PROPOSED` that holds an allocation on one of the newly frozen items is pushed back to `DRAFT` and those allocations get `blocked` set to true.

**Claim lines.** A per-item settlement line carries an `item_id` and a `claimed_quantity` between 1 and the item's `quantity` inclusive. The item's `evidence_tier` must rank at or above `PHOTO_SERIAL`, or the line is refused with `ERR_EVIDENCE_TIER_INSUFFICIENT`; an item whose `valuation_state` is `APPRAISAL_REQUIRED` is refused with `ERR_APPRAISAL_REQUIRED`; and at most one line may exist per item per claim, a second attempt being refused with `ERR_DUPLICATE_CLAIM_LINE`. Crucially, the claimed item does **not** have to sit in one of the claim's `affected_room_ids`: only items in those rooms are records-frozen, so an item claimed from outside them stays editable and its evidence can still be deleted — which is exactly how the evidence-downgrade cascade of §3.3 comes to deny a line mid-claim. A new line opens in `status` `PENDING` with `gross_value_cents`, `capped_value_cents`, `deductible_share_cents`, `net_settlement_cents` and `appeal_count` all 0, `settlement_hold` and `basis_downgraded` false, and `denial_reason` null. The claim's `line_count` rises.

A line also records whether the ground beneath it moved: `basis_downgraded` is set true when the item's `effective_value_basis` falls away from `APPRAISAL` — through a void or an expiry — after that line was created.

**Submission and the settlement arithmetic.** The homeowner submits a claim that is `OPEN` and has at least one line, and whose package is still `GENERATED` or `DELIVERED`; otherwise the submission is refused with `ERR_INVALID_STATE`. Submission stamps `submitted_at`, moves the claim `OPEN → SUBMITTED`, and runs the settlement allocation across every line. The apparent circularity — the sublimit clipping needs the gross values, the deductible needs the clipped values, and the reported total needs both — is resolved by a **pinned evaluation order**: all of step 1 runs, then all of step 2, then all of step 3. No step may look ahead at a later step's output.

*Step 1, gross.* For each line, take the claimed item's own `quantity` as the divisor. When the claim's `settlement_basis` is `ACV`, the unit value is the item's actual cash value evaluated with an as-of instant of the claim's `loss_date`, divided by that quantity. When the basis is `RCV`, the unit value is the item's `replacement_cost_cents` divided by that quantity. The line's `gross_value_cents` is the unit value multiplied by `claimed_quantity`, rounded half up to whole cents.

*Step 2, capping.* Each category starts with a sublimit pool equal to its `blanket_sublimit_cents`. Lines are processed in `created_at` ascending order with the creation-order tie-break. For a line whose item has `coverage_mode` `SCHEDULED` **and** whose `scheduled_policy_id` is the claim's `policy_id`, the cap is that item's `scheduled_value_cents`, and the shared category pool is left untouched. For every other line the cap is whatever remains in its item's category pool, and that pool is then reduced by the smaller of the line's `gross_value_cents` and the cap. Either way the line's `capped_value_cents` is the smaller of its `gross_value_cents` and its cap.

*Step 3, the deductible.* The scope at submission is every line of the claim; at settlement it is only the lines in status `APPROVED`. The base is the sum of `capped_value_cents` over the lines in scope. When the base is zero, every line's `deductible_share_cents` is zero. Under the `PRO_RATA` mode, every line in scope **except the anchor** takes a share of the policy's `deductible_cents` proportional to its capped value — the deductible multiplied by that line's `capped_value_cents` divided by the base, rounded half up to whole cents. The anchor is the line in scope with the greatest `capped_value_cents`, with ties broken by the earlier `created_at` and then creation order, and the anchor's share is the smaller of the policy's `deductible_cents` and the base, minus the sum of all the other shares — so the shares always add up exactly, with the anchor absorbing the rounding remainder. Under the `HIGHEST_VALUE_FIRST` mode there is no anchor: with a running remainder starting at the policy's `deductible_cents`, lines are taken in descending `capped_value_cents` order with ties broken by the earlier `created_at` and then creation order, and each line's share is the smaller of the running remainder and its own capped value, with the remainder reduced by that share. Under the first mode a small line still loses part of its settlement; under the second the largest line absorbs the whole deductible and the small lines settle in full.

*Steps 4 and 5.* Each line's `net_settlement_cents` is its `capped_value_cents` minus its `deductible_share_cents`, floored at zero. The claim's `total_settlement_cents` is the sum of `net_settlement_cents` over the lines in scope whose `status` is `APPROVED` — which is zero at submission, because every line is still `PENDING` at that moment.

**Adjudication and the appeal loop.** A `ClaimsAdjuster` adjudicates one line at a time with a `decision` of `APPROVE` or `DENY` and, on a denial, a `denial_reason` of `EVIDENCE_INSUFFICIENT`, `NOT_COVERED`, `VALUE_DISPUTED` or `DUPLICATE`. Approving a line — `PENDING → APPROVED` or `APPEALED → APPROVED` — requires its `settlement_hold` to be false, and, on the `PENDING → APPROVED` path, requires the owning claim to be `SUBMITTED` or `UNDER_REVIEW`; the claim's `approved_line_count` is then recomputed. Denying a line — `PENDING → DENIED` or `APPEALED → DENIED` — writes the `denial_reason`, forces `net_settlement_cents` to 0 and recomputes `denied_line_count`. The first adjudication under a claim bubbles it `SUBMITTED → UNDER_REVIEW`. When every line of the claim is denied — `denied_line_count` equal to `line_count` — the claim itself auto-transitions `UNDER_REVIEW → DENIED`, its `total_settlement_cents` is forced to 0, every item it froze returns `FROZEN → CATALOGED`, and the household's `frozen_item_count` falls by exactly the claim's `frozen_item_count`.

`APPROVED` is terminal for a line, but `DENIED` deliberately is not. The homeowner may appeal a denied line, optionally with an `appeal_note`, while the line's `appeal_count` is below the limit of 2 and the claim sits in `UNDER_REVIEW` or `SUPPLEMENT_REQUESTED`; at the limit the appeal is refused with `ERR_APPEAL_LIMIT_REACHED`. An appeal moves the line `DENIED → APPEALED`, raises `appeal_count` by one, clears `denial_reason` back to null, and bubbles the claim `UNDER_REVIEW → SUPPLEMENT_REQUESTED`. Adjudicating an appealed line sends it to `APPROVED` or back to `DENIED`, and once no line under the claim remains `APPEALED` the claim returns `SUPPLEMENT_REQUESTED → UNDER_REVIEW`. That is the cycle, and the per-line appeal limit is what bounds it.

**Settlement.** The adjuster settles a claim that is `UNDER_REVIEW`, has no line left in `PENDING` or `APPEALED`, has a `blocked_line_count` of 0 — a single line on settlement hold is enough to stop the whole claim — and has at least one `APPROVED` line. Settlement re-runs the deductible allocation of step 3 over the approved subset only, writes `total_settlement_cents` as the sum of the approved lines' `net_settlement_cents`, moves the claim `UNDER_REVIEW → SETTLED`, returns every item this claim froze `FROZEN → CATALOGED` with `frozen_by_claim_id` cleared to null, lowers the household's `frozen_item_count` by exactly the claim's `frozen_item_count` and recomputes `records_freeze_active`.

**Withdrawal.** The homeowner may withdraw a claim along `OPEN → WITHDRAWN`, `SUBMITTED → WITHDRAWN` or `UNDER_REVIEW → WITHDRAWN`, optionally supplying a `withdraw_reason`, and all three paths carry identical compensating effects: every item whose `frozen_by_claim_id` names this claim returns to `CATALOGED` with that pointer cleared, the household's `frozen_item_count` falls by exactly this claim's `frozen_item_count` — restoring its pre-claim value and leaving any second claim's freeze intact — and every share grant with `status` `ACTIVE` whose `scope_claim_id` names this claim moves to `VOIDED_BY_SCOPE` with `voided_reason` `SCOPE_DELETED`. `SETTLED`, `DENIED` and `WITHDRAWN` are the three terminal claim states.

Claims are readable individually and as a list filtered by `household_id`, `package_id`, `policy_id` and `status`; claim lines are readable individually and as a list filtered by `claim_id`, `item_id` and `status`.

### 3.8. Estate and Downsizing Dispositions

**The plan.** A homeowner opens an **EstatePlan** with a `household_id`, an `executor_member_id` naming the member who will act as executor, and an optional `valuation_mode` of `GROSS` or `NET` that defaults to `GROSS`. A household may hold at most one live plan — one whose `status` is `DRAFT`, `PROPOSED` or `APPROVED` — so that an item's `allocated_quantity` is unambiguous; a second attempt is refused with `ERR_INVALID_STATE`. The new plan opens in `DRAFT` with `proposed_at`, `approved_at`, `executed_at`, `approved_by_member_id` and `balance_spread_pct` all null, `balanced` false, `heir_count` 0, and `unallocated_item_count` initialised to the number of `CATALOGED` items in the household.

**Allocations.** The executor allocates units of items by submitting an `item_id`, a `disposition` of `KEEP`, `SELL`, `DONATE` or `DISCARD`, a `quantity` of at least 1, the required `expected_estate_plan_version` and, for a `KEEP` allocation only, a `heir_member_id`. A `heir_member_id` is required when the disposition is `KEEP` and must be null for `SELL`, `DONATE` and `DISCARD`, because sale proceeds are pooled rather than attributed to any one person. The allocation's `allocated_value_cents` is fixed at creation as the item's `effective_value_cents` multiplied by this allocation's `quantity`, divided by the item's own `quantity`, rounded half up to whole cents. Its `blocked` flag starts false and is set true when the allocated item is later frozen by a claim, which is what pushes a proposed plan back to `DRAFT`.

Two guards protect the conservation invariant. The requested `quantity` added to the item's current `allocated_quantity` must not exceed the item's `quantity`, or the request is refused with `ERR_ALLOCATION_OVER_QUANTITY`. And the item must be dispositionable: an item whose `lifecycle_state` is `FROZEN`, or which carries an appraisal in status `REQUESTED`, is refused with `ERR_ITEM_NOT_DISPOSABLE`. An item's `allocated_quantity` sums the `quantity` of its allocations under plans in `DRAFT`, `PROPOSED` or `APPROVED`; executed plans drop out of that sum because their items are already `DISPOSED`.

Deleting an allocation is the compensating action: the item's `allocated_quantity` falls by exactly that row's `quantity` and the plan's `unallocated_item_count` is recomputed. When the plan was `PROPOSED`, the deletion also drives it `PROPOSED → DRAFT`, setting `balance_spread_pct` back to null and `balanced` back to false while leaving `proposed_at` at its previous value. That is the revision loop.

**Proposing, and the fair-division score.** The executor proposes the plan. Proposal is the `DRAFT → PROPOSED` move, and it is legal again from `PROPOSED` as the `PROPOSED → PROPOSED` self-loop — a re-proposal that may supply a different `valuation_mode` to rescore the very same allocations. It requires `unallocated_item_count` to be exactly 0, meaning every unit of every `CATALOGED` item is allocated, or it is refused with `ERR_PLAN_NOT_FULLY_ALLOCATED`; and it requires that no allocation under the plan carries `blocked` true, or it is refused with `ERR_INVALID_STATE`. Proposal stamps `proposed_at` with the current instant and runs the fair-division balance.

The heirs are exactly the distinct non-null `heir_member_id` values under the plan — which only `KEEP` allocations carry — ordered by the heir member's `created_at` ascending with the creation-order tie-break; their number is the plan's `heir_count`. When there are no heirs at all, `balance_spread_pct` is 0.0, `balanced` is true, and the computation stops there. Otherwise each heir's kept value is the sum of `allocated_value_cents` over the `KEEP` allocations naming them, and the sale pool is the sum of `allocated_value_cents` over all `SELL` allocations; `DONATE` and `DISCARD` allocations contribute nothing to anybody. Under the `GROSS` mode the distributable pool is the sale pool untouched. Under the `NET` mode the distributable pool is the sale pool multiplied by one minus the 12 percent sale disposition cost divided by one hundred, rounded half up to whole cents. The per-heir share is the distributable pool divided by the heir count, rounded **down** to a whole cent, and the remainder — the distributable pool minus that share multiplied by the heir count, a figure at least zero and less than the heir count — is distributed one cent each to the first heirs in that same creation order. Each heir's total is their kept value plus their share. The mean is the sum of the heir totals divided by the heir count. When the mean is zero, `balance_spread_pct` is 0.0; otherwise it is the greatest heir total minus the smallest heir total, divided by the mean, multiplied by 100, rounded half up to two decimal places. `balanced` is true exactly when `balance_spread_pct` is at or below the 5.0 percent fair-division tolerance. Because the `NET` mode lowers every heir's total by the same aggregate amount, it lowers the mean while leaving the gap between the largest and smallest totals unchanged: the spread is strictly larger under `NET`, and a plan can be balanced under `GROSS` and unbalanced under `NET` on identical allocations.

**Approval.** Approval belongs to the homeowner and to nobody else. The plan must be `PROPOSED`; the caller's `X-User-ID` must not equal the plan's `executor_member_id`, because the executor may never approve their own plan, and a violation is refused with `ERR_SEGREGATION_OF_DUTIES`; and the plan's `balanced` flag must be true unless the request sets `override_unbalanced` to true, an unbalanced plan without that override being refused with `ERR_PLAN_UNBALANCED`. Approval moves the plan `PROPOSED → APPROVED`, stamps `approved_at` and writes `approved_by_member_id` from `X-User-ID`.

**Execution.** The executor executes an `APPROVED` plan, provided no allocation under it carries `blocked` true. Execution is a four-hop cascade. Hop 1 moves the plan `APPROVED → EXECUTED` and stamps `executed_at`. Hop 2, caused by hop 1, moves every item whose `SELL`, `DONATE` and `DISCARD` allocations together cover its **full** `quantity` from `CATALOGED → DISPOSED`; an item that is wholly or partly kept by an heir is not disposed of, and neither is one whose disposition allocations cover only part of its quantity. Hop 3, caused by hop 2, releases the allowance of each disposed item that was `SCHEDULED`: the policy's `scheduled_consumed_cents` falls by exactly that item's `scheduled_value_cents` and `scheduled_remaining_cents` is recomputed. Hop 4, caused by hop 3, recomputes the policy's `coverage_gap_cents` and the household's `item_count` and `total_effective_value_cents`. `EXECUTED` is terminal.

Estate plans are readable individually and as a list filtered by `household_id`, `executor_member_id`, `approved_by_member_id` and `status`; allocations are readable individually and as a list filtered by `estate_plan_id`, `item_id`, `heir_member_id` and `disposition`.

### 3.9. Secure Sharing and Redacted Redemption

**Issuing a link.** A homeowner issues a **ShareGrant** by naming a `household_id`, a `scope_kind` of `HOUSEHOLD`, `ROOM`, `PACKAGE` or `CLAIM`, a `recipient_ref` identifying the person the link is for, a `redaction_level` of `VALUES_HIDDEN`, `SERIALS_HIDDEN` or `FULL`, a `starts_at`, an `expires_at`, and optionally an `access_cap` that defaults to 10. The scope pointer must match the scope kind exactly: `scope_room_id` is required when `scope_kind` is `ROOM` and must be null otherwise, `scope_package_id` is required when it is `PACKAGE` and must be null otherwise, and `scope_claim_id` is required when it is `CLAIM` and must be null otherwise; a mismatch is a malformed payload and is refused with `ERR_INVALID_REQUEST`, as are an `expires_at` at or before `starts_at` and an `access_cap` below 1. The grant window is half-open: it includes `starts_at` and excludes `expires_at`.

Two temporal guards then apply, in this order. First, the window must not collide with another live link to the same person: a new grant is refused with `ERR_SHARE_WINDOW_OVERLAP` when another share grant with `status` `ACTIVE` shares the same `household_id` and `recipient_ref` pair and its half-open window intersects the new one's. Because both windows are half-open, exact adjacency — a new `starts_at` equal to an existing `expires_at` — does not intersect and is allowed. There is no buffer of any kind on this check, in deliberate contrast with the appraisal hold of §3.4, which is a closed interval widened by 24 hours on both sides. Second, the window's length, `expires_at` minus `starts_at`, must not be strictly greater than the 90-day maximum share duration, or the request is refused with `ERR_SHARE_WINDOW_TOO_LONG`; a window of exactly 90 days is accepted. Issuing a link is one of the two operations a `RESTRICTED` household cannot perform.

On success the server mints an opaque `share_token`, the grant opens in `status` `ACTIVE` with `access_count` 0 and `voided_reason` null, and the household's `active_share_count` rises.

**Redeeming a link.** Redemption is done by anyone holding the token — an `Anonymous` caller, an `InsuranceAgent` or a `ClaimsAdjuster` — and is addressed by the token itself rather than by the grant's id. A token that matches no grant at all yields `ERR_SHARE_TOKEN_UNKNOWN` (404); a token that matches a grant which is not usable yields `ERR_SHARE_GRANT_INACTIVE` (403). A grant is usable only when its `status` is `ACTIVE`, the current instant is at or after `starts_at` and strictly before `expires_at`, and `access_count` is still below `access_cap`. That two-error split is deliberate: a recipient with no grant at all is distinguishable from one whose grant has died.

The rows the recipient sees depend on `scope_kind`. A `HOUSEHOLD` grant returns every item of the grant's household whose `lifecycle_state` is `CATALOGED` or `FROZEN`, in `created_at` ascending order. A `ROOM` grant returns that same set restricted to the room named by `scope_room_id`. A `PACKAGE` grant returns one row per package line of the package named by `scope_package_id`, in package-line `created_at` order, carrying the **snapshot** values and never the items' live values. A `CLAIM` grant returns one row per claim line of the claim named by `scope_claim_id`, in claim-line `created_at` order. Rows are always drawn from the household named on the grant, and a grant can never surface another household's rows.

Redaction is then applied over those rows. Under `VALUES_HIDDEN` every field whose name ends in `_cents` is omitted from every row **and** from the envelope's `total_effective_value_cents`, while `serial_number` remains visible. Under `SERIALS_HIDDEN` `serial_number` is omitted from every row while the `_cents` fields remain. Under `FULL` nothing is omitted. The response reports the grant's own `share_grant_id`, `scope_kind`, `redaction_level`, `access_count`, `access_cap`, the `household_name` and the `rows` themselves.

Metering is applied **before** the response is rendered: `access_count` rises by one on every successful redemption, so the body carries the post-increment value. When that post-increment count equals `access_cap` the grant transitions `ACTIVE → EXHAUSTED` and the household's `active_share_count` falls — but **this** redemption still succeeds and returns its rows in full. Only the next attempt fails, with `ERR_SHARE_GRANT_INACTIVE`.

**The four ways a link dies.** A grant leaves `ACTIVE` down four distinct branches, each with its own observable footprint. The homeowner may revoke it, moving it `ACTIVE → REVOKED`; revocation is on the write-gate exclusion list, so it works even in a read-only vault, and it lowers `active_share_count`. The clock-advance hook moves it `ACTIVE → EXPIRED` once the clock reaches or passes its `expires_at`, likewise lowering `active_share_count`. The redemption meter moves it `ACTIVE → EXHAUSTED` as described above. And four separate cascades move it `ACTIVE → VOIDED_BY_SCOPE`, each writing a different `voided_reason`: `SCOPE_SUPERSEDED` when the package it is scoped to is superseded by a newer generation or expires, `SCOPE_DELETED` when the claim it is scoped to is withdrawn, and `SUBSCRIPTION_LAPSED` when the household's subscription lapses while the grant's `redaction_level` is `FULL`. All four are terminal, and none of them is reversible — reinstating a lapsed subscription does not bring a voided grant back. In every branch the household's `active_share_count` is lowered by one per grant that leaves `ACTIVE`.

Share grants are readable individually and as a list filtered by `household_id`, `scope_room_id`, `scope_package_id`, `scope_claim_id` and `status`, both reserved to the homeowner and the platform administrator.

## 4. Endpoint Definitions

Operations that create a new, stand-alone resource — a member, a household, a subscription, a room, an item, an evidence asset, a category schedule, an appraiser, an appraisal, a policy, a documentation package, a claim, a claim line, an estate plan, an allocation, a share grant, or the replacement item produced by a replacement — return `201 Created`. Every other operation, including every state transition, every patch, the soft delete of an evidence asset, the delete of an allocation, and every read, returns `200 OK`. Errors carry the HTTP status listed against their error id in §5.
