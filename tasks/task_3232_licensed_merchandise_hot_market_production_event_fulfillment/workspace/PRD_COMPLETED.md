# Licensed Merchandise Hot Market Production and Event Fulfillment API — Product Requirements Document

## 1. Introduction

A championship is decided at 11:47 p.m. and the first celebratory jersey must be on a truck by 3:00 a.m. That single sentence is the operating reality this API exists to serve. The platform coordinates league, team and player licensing rights; the approval of artwork against those rights; the manufacture of championship, milestone and athlete-transaction merchandise inside the hours immediately following an event outcome; the placement of on-demand print and embroidery capacity close to where demand will land; the movement of a single shared inventory pool through venue retail, event pop-ups and e-commerce; and the settlement of the royalty and minimum-guarantee money that flows back to each rights holder.

The economics of the hot market are adversarial in a way ordinary retail is not. Because the outcome is unknown at production time, the business pre-produces both possible outcomes and then destroys or donates the losing side's goods, so the system must carry two parallel production runs per event, commit exactly one of them, and dispose of the other with a defensible audit trail. Royalty ledgers must stay exact to the cent across deliveries, returns, distress disposals and early minimum-guarantee settlements, and a rights holder's contractual floor must never be quietly crossed. Around the venues themselves, counterfeit goods surface within minutes of a win, and brand-protection investigators need a valuation of that exposure that is reproducible from evidence rather than estimated.

This document specifies the API surface that implements all of the above: the rights-holder register, the design approval workflow and its revocation cascade, the parallel-hold production pair, print layering and press operations, capacity windows and rush delivery commitments, the fulfillment lifecycle from planning through pick, ship, deliver, return and distress, the royalty accrual and minimum-guarantee settlement ledger, and counterfeit enforcement. It is a specification for engineers, so it fixes field names, state values, error identifiers, arithmetic and ordering rules precisely; where a rule is arithmetic, the exact sequence of operations is normative, because the cent-level outcome depends on that sequence.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting operator and `X-User-Role` states the operational capacity that operator is acting in. A request that omits either header, or presents one in a form the server cannot parse, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose `X-User-Role` is well-formed but is not permitted for the operation being attempted is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The system recognises eight roles, spelled exactly as follows: `PlatformAdmin`, `LicensingOps`, `DesignOps`, `ProductionPlanner`, `PrintOperator`, `FulfillmentCoordinator`, `EnforcementAgent` and `AuditOnly`.

`PlatformAdmin` is the benchmark administrator: it owns the logical clock and the licensor register, and when `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity — the server records it on the operations it performs but never compares it to any entity's `id`. `DesignOps` (the design studio that authors licensed designs and resubmits rejected ones), `ProductionPlanner` (the hot-market planner), `PrintOperator` (the press and embroidery operator), `FulfillmentCoordinator` (the venue, pop-up and e-commerce fulfilment operator), `EnforcementAgent` (the brand-protection investigator) and `AuditOnly` (the read-only reviewer) are likewise opaque identities: `X-User-ID` is an operator identifier that the server does not compare to any persisted entity's `id`.

`LicensingOps` is the one entity-backed role. When `X-User-Role` is `LicensingOps`, `X-User-ID` is the `id` of the acting `Licensor`; ownership checks on any resource that references a `Licensor` compare the resource's `licensor_id` field to `X-User-ID`. Concretely, a `LicensingOps` caller may record a licensor decision only on a design whose `licensor_id` equals its own identifier and may settle only the licensor it identifies; acting on any other rights holder is rejected with `ERR_LICENSOR_MISMATCH` (HTTP 403).

Role exclusivity follows the same matrix. Registering a rights holder and advancing the clock belong to `PlatformAdmin` alone. `LicensingOps` exclusively records the licensor decision on a design, applies a minimum-guarantee settlement and reverses the latest one. `DesignOps` exclusively creates designs and resubmits rejected ones. `ProductionPlanner` exclusively opens runs, authors layers against them and retires them. `PrintOperator` exclusively prints units and records lost units. `FulfillmentCoordinator` exclusively registers capacity windows, reserves units from them, and places, picks, ships, delivers, returns and distresses demand. `EnforcementAgent` exclusively logs and adjudicates counterfeit findings. `AuditOnly` holds no exclusive operation whatsoever and can serve no request that mutates state.

Segregation of duties is enforced as a distinct authorization rule, not merely as a role matrix. The acting `X-User-ID` that recorded the licensor decision on a design may not afterwards be the acting `X-User-ID` that commits a production run using that design, nor the one that settles that licensor's minimum guarantee. Violations are rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). This rule guards three operations: creating a production run, authoring layers against a run (which is what commits it), and applying a minimum-guarantee settlement.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept `limit` and `offset` as query parameters. `limit` is the maximum number of resources returned in one page; when omitted it defaults to 10, and a supplied value must be at least 1 and at most 100 — values outside that band are a request-shape failure. `offset` is the number of resources to skip before the page begins and defaults to 0 when omitted. Every list response reports `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope.

Lists are ordered by the resource's `created_at` instant, ascending, unless a rule elsewhere in this document pins a different key for a specific computation. That global ordering is what makes the "earliest-created run" and "first run for a team and trigger" rules elsewhere in this document deterministic.

### 2.4. Rights-Holder Ledgers and the Guarantee Recovery Rail

Each `Licensor` is registered once, by a `PlatformAdmin`, with its display `name`, its `league_code` (for example `NBL`, `NBLM` or `NBLW`), the contractual per-unit rate `royalty_rate_pct` expressed as a decimal fraction between 0 and 1 inclusive, and its contractual `minimum_guarantee_cents`, which must be zero or greater. The `currency` field carries the ISO currency code and defaults to `USD` when the caller does not supply one. At registration the ledger triple is written to zero: `accrued_royalty_cents`, `guarantee_recovery_block_cents` and `accrued_unsettled_cents` all begin at 0. The rights projects the licensor holds are not supplied by the caller: a rights holder registered this way is recorded as holding a project that covers every trigger type and every garment SKU this API recognises, so the rights-project clearance of §3.1 and §3.2 is satisfied for that licensor without any further registration step and `ERR_LICENSOR_PROJECT_NOT_FOUND` can never fire against a licensor registered through `POST /licensors`.

The licensor's ledger is governed by one invariant, checked at every observable point: `accrued_unsettled_cents` equals the greater of zero and the difference between `accrued_royalty_cents` and `guarantee_recovery_block_cents`. Whenever any operation touches the ledger, the unsettled figure is recomputed from the other two rather than adjusted independently, so the triple can never drift out of that relation.

`accrued_royalty_cents` is the running sum of the `accrued_cents` carried by the licensor's current royalty accrual rows. An accrual whose `basis` is `RUSH_or_STANDARD` contributes only while it holds the licensor's current `version_seq`; a row that has been replaced by a later rush-or-standard accrual on the same licensor-and-version pair is flagged `superseded` and contributes nothing. Rows whose `basis` is `STANDARD`, `EVENT_shortfall` or `shortfall` contribute their full `accrued_cents`. Accruals abandoned by a retired original version of a run are excluded as well, so a run that has been superseded does not double-count its royalty.

`guarantee_recovery_block_cents` is the sum of `guarantee_shortfall_cents` over this licensor's `APPROVED` early settlements. It is the floor value used when a settlement is reversed: reversal returns the licensor's accrued royalty to the exact figure captured at approval and removes exactly the shortfall that was added, which is what makes apply-then-reverse a zero-drift round trip.

### 2.5. Common Resource Properties and Mutation Semantics

Every top-level resource in this API — `Licensor`, `Design`, `ProductionOrder`, `PrintLayer`, `PrintCapacity`, `PrintReservation`, `FulfillmentOrder`, `Shipment`, `RoyaltyAccrual`, `MinimumGuaranteeSettlement` and `CounterfeitReport` — carries the same four system-managed properties:

- `id` is a server-minted universally unique identifier. It is a bare UUID string with no type prefix, no resource-name prefix and no separator.
- `created_at` is an ISO 8601 UTC timestamp with exactly three fractional digits, stamped when the resource is first created (for example `2026-09-01T00:00:00.000Z`).
- `updated_at` is an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the resource.
- `version` is an integer that starts at its initial value when the resource is created and is incremented by exactly 1 on every mutation of that resource. Cascade-driven mutations increment the version of every resource they touch, so `version` is a faithful count of writes to that resource and is the value clients capture for optimistic concurrency control.

Because `version` is the anchor for optimistic concurrency control, any operation that changes a resource as a side effect of acting on a different resource — a design rejection retiring every run that uses the design, a failed print rescal-ing a run's open orders, a retirement cascading into layers and orders — must increment the version of each affected resource and refresh its `updated_at`. Clients that captured a version before a cascade will find it stale afterwards, which is the intended serialization point described in §2.8.

### 2.6. The Logical Clock, Event Windows and Terminal Lockdown

All deadlines, reopen windows, window classifications and rush service levels in this API are evaluated against a logical clock, never against wall-clock time. The server's startup default is the instant `2026-09-01T00:00:00Z`: before any clock-setting call the clock reads exactly that instant, and it never falls back to the host's real time. A `PlatformAdmin` advances or rewinds the clock by supplying the `current_utc` instant it should read from then on; because the clock can move backwards as well as forwards, every temporal rule in this document is written as a comparison against the clock, not as an elapsed-duration accumulator.

The window that governs hot-market production is the run's event window: it opens at `ProductionOrder.committed_at` and closes 48 hours later. Printing into the window, and reopening a committed run back from `PRINTING` to `COMMITTED`, are both permitted only while the logical clock reads at or before that instant; a request that arrives after it is rejected with `ERR_EVENT_WINDOW_CLOSED` (HTTP 409). Reopening the run restarts the window, because the reopen re-stamps `committed_at`, and a second failed print may therefore revert the run a second time.

Six state values are terminal and are locked down absolutely: `DELIVERED`, `RETURNED` and `DISTRESSED` on a `FulfillmentOrder`, `RETIRED_DESTROYED` and `RETIRED_DONATED` on a `ProductionOrder`, and `REVERSED` on a `MinimumGuaranteeSettlement`. No operation in this API leaves a resource in one of those states. An attempt to act on a locked-down resource is rejected with `ERR_INVALID_STATE` (HTTP 409) — every state-transition operation enforces this.

### 2.7. Monetary Precision and Rounding Discipline

All money in this API is carried in integer cents. Fields whose names end in `_cents` — `minimum_guarantee_cents`, `accrued_royalty_cents`, `guarantee_recovery_block_cents`, `accrued_unsettled_cents`, `unit_cost_cents`, `hold_allocation_cents`, `committed_inventory_cents`, `write_down_inventory_cents`, `requested_wholesale_cents`, `realized_wholesale_cents`, `gross_wholesale_cents`, `settled_cents`, `accrued_cents`, `max_recoverable_early_cents`, `reserved_cents`, `snapped_accrued_cents`, `guarantee_shortfall_cents`, `royalty_leakage_cents`, `penalty_cents` and `total_exposure_cents` — are integers, and the arithmetic that produces them must be performed in decimal arithmetic before conversion, never in binary floating point.

Where a computation produces a fractional cent, the value is rounded half up to two decimal places at the point the rule names, and never later; the licensor ledger's three quantities — `accrued_royalty_cents`, `guarantee_recovery_block_cents` and `accrued_unsettled_cents` — are the exception that carries those two decimal places itself, because their specification reference figures (168.76 and 843.75) are themselves fractional. Three specific rounding sequences are normative and are set out in full in §3: royalty accruals round each order's royalty and its designer premium to the cent before summing the rows rather than rounding the sum once; the wholesale total rounds each term and adds the terms in a pinned order rather than rounding a single combined sum; and the settlement reports a fractional shortfall rounded half up. The reason these sequences are load-bearing can be seen directly: two delivered orders of 1250 cents each on a garment whose royalty rate is 0.06 and whose designer premium is 0.125 produce, when each row is rounded first, a per-row value of 75 cents of royalty plus 9.38 cents of premium, and a ledger total of 168.76 cents; rounding the unrounded total once instead produces 168.75 cents. Both figures are defensible arithmetic, only one is the specification, and the difference is the whole point of pinning the order.

Quantities, unit counts and version numbers are always integers, and no rounding is applied to them. Percentage and factor fields — `royalty_rate_pct`, `win_probability_pct`, `royalty_rate_pct`-derived rates, and the recovery and markup factors used by the write-down rule — are fractions between 0 and 1 or small decimal multipliers, and they are inputs to arithmetic rather than money.

### 2.8. Optimistic Concurrency Control

Every request whose body carries a field named `expected_..._version` is an optimistic-concurrency write. The field carries the client's last-observed value of the parent entity's `version`, it is a non-optional input on those operations, and the server compares it to the parent entity's current `version`. If the two differ the write is rejected with `ERR_STALE_VERSION` (HTTP 412), because some other writer — another operator's pick on the same order, a cascade triggered by the referenced run's print layers, a royalty accrual, a production retirement or an enforcement confirmation — has already advanced that parent's version since the client last read it. The client is then expected to re-read the parent and retry against the fresh version.

Two operations are designated concurrency-controlled writes of record. A pick of units from a run's shared pool must carry `expected_production_order_version`, the client's last-observed `version` of the `ProductionOrder` the order draws from; a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412), because committing a pick against a view of the run that another writer has already advanced would move units out of a pool whose composition the client has not observed. A minimum-guarantee settlement must carry `expected_licensor_version`, the client's last-observed `version` of the `Licensor`; a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412), because settling against a stale ledger would reserve an amount the rights holder no longer holds.

The same version-comparison guard applies to the other version-bearing writes in this specification: resubmitting a rejected design and recording a licensor decision both carry `expected_design_version` compared against the `Design`'s current `version`; authoring layers against a run carries `expected_production_order_version` compared against the `ProductionOrder`'s current `version`; and reversing the latest early settlement carries `expected_licensor_version` compared against the `Licensor`'s current `version`. In every one of those cases a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).

### 2.9. Capacity Windows and the Reservation Ordering Rule

A print-capacity window is registered against a market by its `city_code` (for example `ATL` or `PHI`), the `print_type` capability it offers, its `window_start` and `window_end` instants, the total `capacity_qty` it can print and the `rush_sla_hours` it commits for rush work drawn from it. The window is half-open: `window_start` is a closed end and `window_end` is an open end, so adjacent windows are non-overlapping — a window ending at an instant and one starting at that same instant do not overlap. A window whose `window_end` is not strictly after its `window_start`, whose `capacity_qty` is not strictly positive, or whose `rush_sla_hours` is not strictly positive is a request-shape failure. A new window starts with `reserved_qty` at 0 and `available_qty` equal to its `capacity_qty`.

A `PrintCapacity` supports the `BASE`, `EMBROIDER` and `HEAT_PRESS` capabilities. Pennant goods run on the `BASE` capability, which is why no separate pennant capacity is registered.

Reservations against a window accumulate and are ordered by their `reserved_at` stamp, and that order is the deterministic processing key whenever several reservations compete for one window: the reservation stamped earlier keeps its units, the later one is evaluated against what remains, and the outcome never depends on the order the requests happened to arrive in at the socket. A tie on the `reserved_at` stamp is broken by ascending reservation quantity and never by a random, generated or time-derived field. A window's `reserved_qty` is the sum of the `quantity` of its `HELD` reservations processed in that order, and `available_qty` is its `capacity_qty` less its `reserved_qty`.

A reservation stays in `HELD` for the life of its window; it is never released, expired or cancelled. Consequently a reservation that cannot fit inside the window it names is rejected rather than downgraded: when the requested `quantity` exceeds the window's remaining `available_qty`, the request fails with `ERR_CAPACITY_EXCEEDED` (HTTP 409). The one exception is the reclaim rail: a reservation aimed at a window whose `window_end` already precedes the logical clock is re-pointed at the next window honouring the same `city_code` and `print_type`, and no quantity is released from the closed window — the reclaimed units are counted once and only once, never twice.

### 2.10. Validation Precedence

Every mutating request is evaluated against an ordered ladder of checks, and the first check that fails determines the response. The order matters for the client's diagnosis, and it is therefore normative rather than incidental: an operator who supplies an unparseable body learns that the body was unparseable even if they also lack the role, and an operator who lacks the role learns that before learning that a referenced resource was missing.

Request shape is checked first, at the highest precedence, and a failure is reported as `ERR_INVALID_REQUEST` (HTTP 400). This rung covers a missing or mistyped body field, an enum member that is not one of the permitted values, a numeric field that must be strictly positive supplied as zero or negative, a capacity window whose `window_end` is not after its `window_start`, a `limit` outside the permitted band, and a distress or return that elects the `DONATE` destruction mode without supplying a `donation_recipient_code`.

Authentication is checked second: absent or malformed `X-User-Role` or `X-User-ID` headers yield `ERR_UNAUTHENTICATED` (HTTP 401).

Authorization is checked third, as three rules occupying one rung: the role must be permitted for the operation, otherwise `ERR_FORBIDDEN_ROLE` (HTTP 403); the segregation-of-duties rule of §2.1 must hold, otherwise `ERR_SEGREGATION_OF_DUTIES` (HTTP 403); and a `LicensingOps` caller must be acting on the licensor its identifier names, otherwise `ERR_LICENSOR_MISMATCH` (HTTP 403).

Existence is checked fourth: a path identifier that resolves to nothing yields `ERR_NOT_FOUND` (HTTP 404), and the specific reference checks yield `ERR_LICENSOR_NOT_FOUND`, `ERR_DESIGN_NOT_FOUND`, `ERR_PRODUCTION_ORDER_NOT_FOUND` or `ERR_FULFILLMENT_ORDER_NOT_FOUND`, each HTTP 404, according to which reference failed.

State eligibility is checked fifth. A resource that is not in a state permitting the requested transition — including any attempt to leave a locked-down terminal state — yields `ERR_INVALID_STATE` (HTTP 409); picking units and then shipping them out of a run that is no longer `COMMITTED` or `PRINTING` is likewise `ERR_INVALID_STATE` (HTTP 409); and a commit attempted on a run that has already left `PARALLEL_HOLD` without an intervening revert yields `ERR_ALREADY_COMMITTED` (HTTP 409).

Optimistic concurrency is checked sixth, exactly as §2.8 describes, yielding `ERR_STALE_VERSION` (HTTP 412).

Rights clearance is checked seventh: a run or layer that needs an approved design but finds one that is not `APPROVED` fails with `ERR_DESIGN_NOT_APPROVED` (HTTP 422), and a run whose licensor holds no recorded rights project covering the run's requested `trigger_type` or `garment_sku` fails with `ERR_LICENSOR_PROJECT_NOT_FOUND` (HTTP 422).

Temporal commitments are checked eighth: a reservation no window can satisfy under the rush service level, a rush shipment that breaches its commitment, or a run with no rush delivery points that is not punctual fails with `ERR_RUSH_COMMITMENT_BREACH` (HTTP 422); and a print arriving after the event window has closed fails with `ERR_EVENT_WINDOW_CLOSED` (HTTP 409).

Commit sequencing is checked ninth: when a run with the same `team_code` and `trigger_type` has already committed, only the earliest-created run of the pair may commit, and the later one fails with `ERR_PRODUCTION_ALREADY_COMMITTED` (HTTP 409).

Capacity aggregates are checked tenth: exceeding a run's printable pool with picked, destroyed, donated or returned units, exceeding a window's remaining units with a reservation, or returning more than was shipped, all yield `ERR_CAPACITY_EXCEEDED` (HTTP 409); a pick exceeding the available units of its reference pool yields `ERR_INVENTORY_INSUFFICIENT` (HTTP 409); and a pick attempted when every picked unit of the run has already been shipped or distressed yields `ERR_LOT_EXHAUSTED` (HTTP 409).

The licensor ledger is checked eleventh: a settlement with no unsettled accrual, or a reserve larger than the unsettled amount, yields `ERR_NO_ACCRUED_ROYALTY` (HTTP 422); and a settlement that would carry the accrued royalty below the minimum guarantee while `accept_guarantee_breach` is false yields `ERR_GUARANTEE_FLOOR_BREACH` (HTTP 422) with the exact shortfall carried in the message.

The remaining business-integrity checks occupy the twelfth and last rungs: a settlement that would reserve zero and leave all three ledger quantities unchanged yields `ERR_SETTLEMENT_NOOP` (HTTP 422); a counterfeit confirmation whose `suspect_quantity` exceeds `unit_count`, or whose confirmed `suspect_quantity` is zero, yields `ERR_COUNTERFEIT_OVERCOUNT` (HTTP 422); a confirmation attempted on a listing whose `online_listing_id` does not begin with the `VERIFIED-` prefix yields `ERR_LISTING_UNVERIFIED` (HTTP 422); a pick whose `pick_remark` repeats a remark already recorded on that order yields `ERR_PICK_REMARK_REUSED` (HTTP 409); a layer whose print type is out of sequence or whose pennant flag forbids it yields `ERR_PRINT_TYPECAST_MISMATCH` (HTTP 422); and a print that would exceed the layer's authorized `quantity` yields `ERR_PRINT_QUANTITY_EXCEEDED` (HTTP 422). Finally, a hot-market allocation that falls below its own floor and alignment requirement yields `ERR_UNBALANCED_ALLOCATION` (HTTP 422), with the required value reported in the message.

### 2.11. Nested Resource Retrieval

Requests that address a resource through more than one identifier in the URL resolve those identifiers left to right. The server validates each identifier in path order and rejects the request at the first one that does not correspond to an existing resource, so a request for layers under a run identifier that does not exist fails on the run rather than on the layer. The rejection for a missing resource is `ERR_NOT_FOUND` (HTTP 404) where the resource is addressed by its own bare path identifier and carries no reference-specific code — a design read by path, a print layer, a capacity window, a counterfeit report, a royalty accrual — and one of the reference-specific codes of §2.10 where it does: `ERR_LICENSOR_NOT_FOUND` for a licensor, `ERR_DESIGN_NOT_FOUND` for a design named as a reference in a request body, and `ERR_PRODUCTION_ORDER_NOT_FOUND` or `ERR_FULFILLMENT_ORDER_NOT_FOUND` for a production run or a fulfillment order, whether it is named in a request body or addressed by its own path identifier. Parent existence always takes precedence over any check on the child, so an operation can never be judged against a context that does not exist.

## 3. Business Logic & Workflows

### 3.1. Licence Clearance: Authoring, Rejection, Resubmission and Revocation

A design cannot be printed, layered or produced until its licensor has cleared it, and the whole clearance cycle is therefore the gate in front of every other workflow in this document.

A `DesignOps` studio authors a design by naming the rights holder it belongs to through `licensor_id`, the team whose marks appear on it through `team_code`, the player whose marks appear on it through `player_code` — which is supplied only when the artwork carries an individual player's marks and is null for team-only artwork — the garment that will carry the print through `garment_sku`, and a human-readable `design_name`. The `garment_sku` must be one of `JERSEY`, `TRACTOR`, `DUFFEL`, `CAP`, `MINI` or `PENNANT`. A newly authored design is written in `PENDING_LICENSOR_APPROVAL` with `approved_version` null and `rejection_reason` null; the `approved_version` property stays null for the whole of the design's unapproved life and is populated only at the moment of approval.

Approval and rejection are both recorded by a `LicensingOps` operator, and both are decision calls the rights holder's operator records against the design. The operator supplies `decision`, its last-observed `expected_design_version`, and — for a rejection only — the `rejection_reason`. Recording `decision` as `APPROVE` requires the design to be in `PENDING_LICENSOR_APPROVAL`; it moves `approval_state` to `APPROVED` and pins `approved_version` to the design's `version` as it stands after that call's increment. That pinned figure is the anchor every production run pins in turn, which is why it is captured at the increment rather than before it. `APPROVED` is the state the production workflow requires, and it is not reachable again once left: a resubmission is accepted only from `APPROVAL_REJECTED`, so an approved design cannot be returned to review. Recording `decision` as `REJECT` requires `rejection_reason` to be present and non-empty and is refused only once the design has already been rejected — a pending design and an approved design both admit a rejection, because rejection is the revocation rail acting on cleared artwork. It moves `approval_state` to `APPROVAL_REJECTED` and stores the supplied reason on `rejection_reason`. Either decision increments `Design.version` by exactly 1.

Rejection is not merely a design-level event, because goods already scheduled against the design may bear marks the licensor has just refused. A rejection therefore cascades, and the cascade is normative in its scope and depth. Every production run whose `design_id` is this design is moved to `RETIRED_DESTROYED` with `retire_reason` set to `ASSORTMENT_CHANGED`, `retired_at` stamped, and the run's own version advanced by 1. Within each such run, every print layer is moved to `PRINT_FAILED` with `committed_qty` forced to 0 even where units had already been printed, and that layer-level failure in turn rescales the run's open fulfillment demand exactly as the press-failure cascade of §3.3 does. The cascade therefore reaches three levels deep — design, run, layer and the demand hanging off the layer — and each level it touches has its version advanced and its `updated_at` refreshed. The retired run's `write_down_inventory_cents` is also recomputed from its `destroyed_units` by the demand-collapse write-down rule of §3.7, so goods already booked as lost against the withdrawn artwork carry their charge.

The channel is deliberately not one-way. A rejected design is recoverable: the studio may revise it and resubmit, supplying its `expected_design_version`. Resubmission requires `APPROVAL_REJECTED` and moves the design back to `PENDING_LICENSOR_APPROVAL` with `rejection_reason` cleared to null, ready for a fresh licensor decision, and increments `Design.version` by exactly 1. Because the machine has this single-step revert, `APPROVAL_REJECTED` is not a terminal state and a design may cycle between rejection and resubmission as many times as the artwork requires before it is finally `APPROVED`.

### 3.2. The Parallel-Hold Pair and Hot-Market Capacity Commitment

The defining business fact of this domain is that the winning side is unknown at production time, so the `ProductionPlanner` opens two production runs for one event — one for each possible outcome — and both begin life in `PARALLEL_HOLD`. A `ProductionOrder` is opened by a `ProductionPlanner` with the rights holder it produces under in `licensor_id`, the cleared artwork in `design_id`, the team in `team_code`, the reason the run exists in `trigger_type`, and the quantity and economics of the run in `expected_demand_qty`, which must be strictly positive, and `unit_cost_cents`, which must also be strictly positive. The `trigger_type` is one of `CHAMPIONSHIP_WIN`, `MILESTONE`, `ATHLETE_TRANSACTION` or `STANDARD`. The outcome the run is printed for is declared in `event_outcome`, one of `WIN_FAVORED_TEAM`, `WIN_UNDERDOG_TEAM` or `NO_OUTCOME`, and defaults to `NO_OUTCOME` when the planner does not declare one — which is the normal state for a milestone or athlete-transaction run that is not bound to a deciding match. The planner may also supply `win_probability_pct`, a fraction between 0 and 1 inclusive that defaults to 0.5, and `outcome_at`, the instant the deciding event is scheduled to resolve, which defaults to null. The flag `pennants_included` records whether pennant layers count toward the run's sellable units and defaults to true.

Creation writes the run's whole initial surface. `status` is `PARALLEL_HOLD`; `retired_design_version` is pinned to the design's current `approved_version`, which is what will later let the system detect that a run is printing artwork the licensor has since changed; `observed_current_design_version` is set to the design's current `version`; `hold_allocation_cents` holds the parallel-hold inventory value this run contributes, computed as the run's `unit_cost_cents` multiplied by the run's `capacity_commitment_units` for a hot-market trigger and by its `expected_demand_qty` for a `STANDARD` run — never less than one unit's cost — and the two outcome runs of one event share the same pool of capital between them; `layer_ids` starts empty and later lists the ids of the run's print layers in submission order; `base_units_printed`, `accessory_units_printed`, `committed_inventory_cents`, `rush_delivery_points`, `write_down_inventory_cents`, `destroyed_units` and `donated_units` all start at 0; and `committed_at`, `retired_at` and `retire_reason` all start null. Creating the run also requires that the referenced licensor exists and that the referenced design exists with an `APPROVED` clearance, and that the licensor holds a recorded rights project covering the run's requested `trigger_type` and `garment_sku`; structural existence is judged before the run is scored, so a dangling reference is reported as a missing resource rather than as an allocation failure.

The committed capital for the run is computed at creation by the hot-market capacity commitment rule, and the rule has two variants whose divergence is the entire point of the rule. Its inputs are the projected demand `expected_demand_qty`, the outcome probability `win_probability_pct`, the landed unit cost `unit_cost_cents`, the `trigger_type`, and the whole number of hours from the logical clock to the run's `outcome_at` — a value that is zero or negative once the outcome instant has passed, and a fixed default of 24 hours when the caller declared no `outcome_at` at all, so an unscheduled run is capitalised as unhurried. The written output is `capacity_commitment_units`, and the evaluation order is pinned: the demand tier first, then the probability, then the hour factor, then, for the superseding variant only, the tier residual.

Tier selection is inclusive at each lower edge, and the tier a run lands in is recorded as one of three exact values: `MAJOR_MARKET`, `REGIONAL` or `LOCAL`. A projected demand of at least 100000 units places the run in `MAJOR_MARKET`. Below that, a projected demand of at least 25000 units places it in `REGIONAL`. Anything lower places it in `LOCAL`. The probability is then floored: the working value is the greater of the supplied `win_probability_pct` and 0.05, so a run the planner believes will not happen is still capitalised as though it had a one-in-twenty chance.

The hour band scales the commitment by how close the outcome is, and it too is inclusive at each lower edge. When more than 6 hours remain, the hour factor is 1.0 and the run is treated as unhurried. When 6 hours or fewer remain but more than 1 hour remains, the factor is 1.5. When an hour or less remains — or the outcome instant has already passed and the remaining hours are zero or negative — the factor is 2.0, the same-hour rush rate. This is the compression that makes hot-market capitalisation behave differently from ordinary production planning: the same demand committed inside the final hour is capitalised at double the unhurried rate.

The variant is then selected by precedence between two runs for the same team and trigger. The first run created for a given `team_code` and `trigger_type` pair is the provisional variant, and it multiplies before rounding: its commitment is the projected demand times the floored probability times the hour factor, rounded up to the next whole unit. The second and every later run created for that same pair is the committed-final variant, and it drops the hour factor entirely — the demand is multiplied by the floored probability, rounded down to the whole unit, and then the tier residual is added: 25 units for a `LOCAL` run, 50 units for a `REGIONAL` run, and no residual at all for a `MAJOR_MARKET` run. Whichever variant applies, the result is then floored a final time at half of the demand-times-probability figure rounded up, so a run can never carry a commitment below that floor. That final floor — half of the demand-times-probability figure rounded up — is the run's allocation floor, and the alignment the run additionally requires is its tier residual: for a `MAJOR_MARKET` run the alignment is zero, for a `REGIONAL` run it is 50 units and for a `LOCAL` run it is 25 units. The comparison is made on identical inputs, and it diverges sharply: a `LOCAL` run with 1000 units of projected demand, a quarter probability and two hours to the outcome writes 375 units as the provisional first run of its pair, and would write 275 units as a later committed-final run of the same pair, because the provisional run is multiplied by the 1.5 hour factor while the later run trades that multiplier for a flat 25-unit residual. The commitment is written once and is never recomputed from a value it has already written, so the rule terminates in a single pass rather than iterating toward a fixed point.

The ordering of the runs in that pair is itself deterministic: runs are ordered by their `created_at` instant, and a tie on `created_at` is broken by ascending `ProductionOrder.id` order of creation, never by any random or generated field. The same ordering governs the sequencing rule that later decides which of two same-team, same-trigger runs is permitted to commit. If the run's allocation cannot be balanced — where the computed allocation falls below its own floor and the alignment it requires — the creation is rejected with `ERR_UNBALANCED_ALLOCATION` (HTTP 422), and the message reports the value the run would have needed. That check sits on the last rung of the precedence ladder of §2.10, so a run whose body is malformed, whose caller is unauthenticated or unpermitted, whose licensor or design is missing, whose design is uncleared, or whose licensor holds no matching rights project is reported for that earlier failure instead.

### 3.3. Authoring Layers and Committing the Winning Outcome

Committing an outcome happens through layering, not through a purpose-built commit call. A `ProductionPlanner` authors print layers against a held run, supplying its last-observed `expected_production_order_version` along with the `layers` it wants created, and the call both appends those layers and, by default, commits the run.

Each layer names the run it belongs to through `production_order_id`, the artwork it will print through `design_id`, the press operation it requires through `print_type`, and the number of units it is authorised for through `quantity`, which must be strictly positive. The layer's `design_id` may be left out of the submitted body, in which case the layer inherits the run's own pinned artwork; a `design_id` that is present but not a string is a request-shape failure like any other mistyped field. The `print_type` is one of `BASE`, `EMBROIDER`, `HEAT_PRESS` or `PENNANT`. A new layer is written with its `layer_state` in `PENDING_PRINT` and with `printed_qty`, `committed_qty` and `failed_qty` all at 0 and `design_version_checked` null. Layers may only be authored while the run is in `PARALLEL_HOLD`; a run that has already left that state and has not since been reverted cannot accept a commit request at all, and such a request is rejected with `ERR_ALREADY_COMMITTED` (HTTP 409).

Two sequencing rules guard the layer set itself, and both are reported as `ERR_PRINT_TYPECAST_MISMATCH` (HTTP 422). First, a `BASE` layer must be committed before any `EMBROIDER` or `HEAT_PRESS` layer on the same run: a request that presents a non-base operation before its run's base layer has been committed is refused. Second, a `PENNANT` layer may only be requested on a run whose `pennants_included` flag is true; a pennant layer on a run that has declared pennants excluded from its sellable units is refused with the same code. The same code also carries a third, unrelated ground of refusal that belongs to rights clearance rather than to sequencing: when the run's pinned design version — the `retired_design_version` captured when the run was created — differs from the design's current approved version, the layering is refused, because the artwork being produced is no longer the artwork the licensor cleared. And layering cannot proceed against artwork that is not cleared at all: a design in `PENDING_LICENSOR_APPROVAL` or `APPROVAL_REJECTED` fails the request with `ERR_DESIGN_NOT_APPROVED` (HTTP 422).

The commit itself is serialised by the outcome pair. When any run sharing the same `team_code` and `trigger_type` has already committed, only the earliest-created run of that group remains eligible to commit, and a commit request on any later-created run of the group is rejected with `ERR_PRODUCTION_ALREADY_COMMITTED` (HTTP 409). This is the mechanism that guarantees exactly one outcome run of a parallel-hold pair advances while the other is disposed of, and it is why the ordering rule of §3.2 had to be deterministic down to the tie-break.

Whether the call commits the run depends on `destroy_mode`, and the asymmetry is intentional. When `destroy_mode` is omitted, or is supplied as `DESTROY` or as `DONATE`, the run is committed: `status` moves from `PARALLEL_HOLD` to `COMMITTED` and `committed_at` is stamped. Committing acquires cycle eligibility for the run, because the `committed_at` stamp is what makes it the favoured cycle of its `team_code`. The run's `committed_inventory_cents` is recomputed and its `hold_allocation_cents` is released to 0, because the capital that was held against an unknown outcome is now capitalised against a known one — the recomputed figure is the run's `unit_cost_cents` multiplied by its `capacity_commitment_units` plus the units its layer set credits, where a layer credits the lesser of its authorised `quantity` and its `committed_qty`, a layer still awaiting its first print credits its full authorised `quantity`, and an all-failed layer credits nothing; a `STANDARD` run instead capitalises its `unit_cost_cents` over the total authorised quantity of its layers. In every case the figure is never less than one unit's cost. Any write-down previously booked against the run is unset: `write_down_inventory_cents` is recomputed at the run's `unit_cost_cents`. Print capacity is relicensed for the now-committed run, in the sense that every supported market and press capability window still holding at least its `rush_sla_hours` of remaining time becomes re-eligible to carry this run's reservations. The run's `base_units_printed` and `accessory_units_printed` are recomputed from the run's layer set — the first summing over layers whose `print_type` is `BASE`, the second over layers whose `print_type` is `EMBROIDER`, `HEAT_PRESS` or `PENNANT` — and the newly created layer ids are appended to `layer_ids` in submission order. Each layer contributes its `committed_qty`, capped at the quantity it was authorised for, except that a layer still awaiting its first print (`PENDING_PRINT`) is credited at its full authorised `quantity`, because a layer that has been committed but not yet printed is part of the committed layer set the run holds. The previously written `capacity_commitment_units` is left exactly as it was computed at creation and is not rewritten on commit.

When `destroy_mode` is supplied as `SHORTFALL`, the run is not committed at all: it stays in `PARALLEL_HOLD`, and the call's effect stops at appending the submitted layers, recomputing the printed-unit totals from them and appending their ids to `layer_ids` in submission order. That is the rail that lets a planner stage artwork against a run before the outcome is known, which is precisely what pre-production for both possible outcomes requires.

Every committing path advances three versions. The run's own `version` is incremented by 1, the `Design`'s `version` is incremented by 1, and the `Licensor`'s `version` is incremented by 1 with its `accrued_unsettled_cents` recomputed from the ledger invariant of §2.4. All three increments refresh the corresponding `updated_at` stamps, so a client holding any of the three versions from before the commit will find it stale on its next version-bearing write, as §2.8 anticipates.

### 3.4. Press Operations, Print Failures and the Reopen Rail

Printing is where a committed outcome becomes sellable units, and it is also where the run can be pushed backwards, so both directions of the machine matter.

A `PrintOperator` prints units on a layer by supplying the `printed_qty` to add. The print is accepted only while the layer's running total would remain within the units the layer was authorised for: a print that would carry `printed_qty` above the layer's `quantity` is rejected with `ERR_PRINT_QUANTITY_EXCEEDED` (HTTP 422). If the parent run is in `PRINTING`, the clock must read at or before the run's `committed_at` plus 48 hours; a print arriving after that instant is rejected with `ERR_EVENT_WINDOW_CLOSED` (HTTP 409). A pennant layer on a run whose `pennants_included` flag is false, and a non-base layer presented before its run's base layer has been committed, are both refused with `ERR_PRINT_TYPECAST_MISMATCH` (HTTP 422). The parent run must be in `COMMITTED` or `PRINTING`.

A successful print adds the supplied `printed_qty` to the layer's running `printed_qty`, recomputes the layer's `committed_qty` as its `printed_qty` less its `failed_qty`, advances the layer to `PRINTED` and refreshes `design_version_checked` with the `Design`'s `version` observed at that moment. A first print may be recorded on a layer that is still in `PENDING_PRINT`, and it carries that layer straight to `PRINTED` like any other print, so the layer's contribution is its printed units from then on rather than its authorised quantity. The layer's own machine is accumulating rather than one-shot: a further print on a layer already in `PRINTED` keeps it in `PRINTED` and simply increases `printed_qty` and `committed_qty` again while refreshing `design_version_checked` afresh, so a layer carries the sum of all its successful attempts. The print cascades upward: the parent run's `base_units_printed` or `accessory_units_printed` is recomputed from the committed layers according to the layer's `print_type`, and the run moves from `COMMITTED` to `PRINTING`. The `Design`'s `version` is incremented by 1 on every print.

Lost units are recorded separately, by a `PrintOperator` supplying the `failed_qty` to add. Recording a failure on a layer that has already been printed is a printing mutation and is governed by the run's event window exactly as a print is; recording one on a layer still in `PENDING_PRINT` recognises no printed goods and is not gated by the window. On a layer still in `PENDING_PRINT`, recording a failure adds the supplied figure to `failed_qty`, recomputes `committed_qty` as `printed_qty` less `failed_qty` with any negative result floored at 0, moves the layer to `PRINT_FAILED` and refreshes `design_version_checked` with the design's `version` observed at that moment.

On a layer already in `PRINTED`, a recorded failure is far more consequential, because units that were counted as sellable have just become unsellable, and the effect propagates two hops outward. The layer's `failed_qty` is increased by the supplied figure and `committed_qty` is recomputed as `printed_qty` less `failed_qty`. The parent run's `base_units_printed` or `accessory_units_printed` is then recomputed downward so that the failed layer's contribution is removed. From there the effect reaches demand: for each of the run's open fulfillment orders, the order's `requested_wholesale_cents` is scaled by the layer's committed quantity divided by the layer's authorised `quantity`, and any order whose recomputed total falls to zero or below is moved to `DISTRESSED` with `distress_reason` recorded as `DEMAND_COLLAPSE`. That is the chain — a press defect, then a thinner printable pool, then demand that no longer has goods behind it — and it is why a failed print is never a local event in this system.

The reopen rail runs the other way, from `PRINTING` back to `COMMITTED`, and it is triggered by the arithmetic of the failure rather than by an explicit request. When a recorded failure drives the print reducer's result — the layer's `printed_qty` less its `failed_qty` — to exactly zero, meaning the layer's `failed_qty` has caught up with or passed its `printed_qty`, the run reopens: its `status` returns to `COMMITTED` and `committed_at` is re-stamped, which restarts the event window from the new stamp. This is permitted only while the clock still reads at or before the pre-existing `committed_at` plus 48 hours; an attempt to reopen after that instant is rejected with `ERR_EVENT_WINDOW_CLOSED` (HTTP 409). The reopen also zeroes the run's `write_down_inventory_cents`, because no version of the run is sellable at that point, and it recomputes the run's open fulfillment orders against the reduced printable pool — any order whose recomputed `requested_wholesale_cents` drops below zero is set to `DISTRESSED`, and the scaling projects the layer's realised units forward so that a layer whose reducer has fallen to zero scales the run's open demand to zero rather than leaving it untouched. Because the reopen re-stamps `committed_at` and returns the run to a committable state, it is genuinely cyclic: the reopened run may be layered again, and a second failed print reverts it a second time within the freshly opened window.

A third way into `PRINT_FAILED` exists and it is not operator-driven at all. When the parent run is retired, every layer of that run that is not already `PRINT_FAILED` — printed or not, since the whole layer set leaves the sellable pool — is moved to `PRINT_FAILED` with `committed_qty` forced to 0 even though any `printed_qty` already recorded remains above zero, because the units that exist physically are no longer sellable. Where goods had been printed and the run is destroyed rather than donated, `design_version_checked` is set to the run's `retired_design_version` rather than to the design's current version, deliberately preserving the version the goods were actually printed at for the audit trail. The write-down is recomputed from the quantity the run actually lost rather than from the failed layers, and the order-level charge is skipped whenever it is strictly less than the write-down already standing on the run, because the greater charge remains the recorded position.

Capacity is held against windows rather than against runs. A `FulfillmentCoordinator` registers a window by naming its market through `city_code`, its capability through `print_type`, its `window_start` and `window_end`, its total `capacity_qty` and the `rush_sla_hours` it commits, and the new window opens with `reserved_qty` at 0 and `available_qty` equal to its `capacity_qty`. Units are then held by reserving against a window, supplying the window through `print_capacity_id`, the units through `quantity`, the instant the goods must be printable by through `needed_by`, and optionally `rush_flag`, which defaults to false. A reservation is created with its `reservation_state` in `HELD`, stamped with `reserved_at`, and immediately adds its `quantity` to the window's `reserved_qty` with `available_qty` recomputed. The supplied `needed_by` instant is carried back exactly as the client sent it rather than being reformatted to the server's canonical timestamp shape, so the round trip is byte-identical. A reservation that exceeds the window's remaining `available_qty` is refused with `ERR_CAPACITY_EXCEEDED` (HTTP 409) under the ordering rule of §2.9, and a reservation that no window can start early enough to serve under the rush service level is refused with `ERR_RUSH_COMMITMENT_BREACH` (HTTP 422).

The run's rush delivery commitment is derived from the reservations held against it and is written to `ProductionOrder.rush_delivery_points`. It is written at run creation from whatever reservations are already held — zero when none are — and recomputed whenever a reservation is placed and on every re-evaluation of a printing run's delivery commitment. The rule walks every reservation that is still in `HELD` and held against a window matching a print capability the run's authored layers require — a `PENNANT` layer riding the `BASE` capability — and classifies each by the slack between its window's `window_start` and the instant it must be printable by: when that span is 24 hours or fewer the reservation is a rush reservation and its units join the rush total; when the span is longer the reservation is a standard one and its units join the standard total — the 24-hour boundary belongs to rush, and 72 hours is the standard window length the classification is calibrated against. The run's commitment is then nine tenths of the rush units plus one tenth of the standard units, rounded half up to two decimal places, and the commitment floor for the run is half of that figure rounded up to a whole unit. If the run's rush delivery points come out at zero while the floor it needs is above zero, the run is not punctual and the request is rejected with `ERR_RUSH_COMMITMENT_BREACH` (HTTP 422), with the message carrying the commitment floor in units. That check guards both the reservation call and the run's own commit — a run with no punctual reservation behind it cannot be committed, and committing such a run is refused on the same code as the reservation that failed to make it punctual; a run that is committed without having acquired a punctual reservation of its own is nevertheless credited with the points its reservations earn. The weighting is what makes the rush rail worth using: a run holding one rush window of 100 units and one standard window of 50 units writes 95 points, because nine tenths of 100 is 90 and one tenth of 50 is 5. An unweighted projection of the same reservations would ignore the rush-and-standard split, slope the whole held quantity at one half and write a smaller figure — that unweighted form is the non-default variant and is not what this ledger records. Overflow follows the processing order of §2.9 strictly: any reserved quantity that runs beyond a window's remaining capacity is still counted at its own class rate and is not made available to a later run competing for the same window; the later reservation is processed after the earlier one by ascending `reserved_at`, with a tie broken by ascending reservation quantity and never by any random or generated field.

### 3.5. The Shared Inventory Pool: Placing Demand and Picking It

Venue retail, event pop-ups and e-commerce are three faces of one pool. When a `FulfillmentCoordinator` places demand, it names the run the goods will come out of through `production_order_id`, the route to market through `channel` — one of `VENUE_RETAIL`, `EVENT_POPUP` or `ECOM` — the venue or e-commerce destination through `destination_code`, and the units wanted through `quantity`, which must be strictly positive. The optional `rush_flag` declares that the order carries a rush shipping commitment and defaults to false. The optional `donation_recipient_code` names the nonprofit recipient and defaults to null. The optional `pick_remark` carries an operator note forward for the pick and defaults to null. A new order is written in `PLANNED` with `picked_qty`, `shipped_qty`, `returned_qty`, `destroyed_qty`, `donated_qty`, `realized_wholesale_cents`, `write_down_inventory_cents` and `requested_wholesale_cents` set by the quote below, and with `distress_reason` null.

Because the three channels draw on one pool, the quote is computed from the channel rather than from the destination: a venue-retail unit is quoted at 12 cents, an event-pop-up unit at 9 cents and an e-commerce unit at 5 cents. A rush order adds a 2-cent surcharge per unit on top. An order carrying a `donation_recipient_code` adds a flat 100 cents. The result is written to `requested_wholesale_cents`, and the arithmetic order is pinned rather than incidental: the per-unit channel term is computed and rounded half up to the cent first, then the per-unit rush surcharge term is computed, then the flat donation term is added, and the three are added together in that order. Rounding a single combined sum once instead would produce a different cent whenever the channel term is fractional, and it is not what this field records. Two reference values are worth carrying: 250 units of venue retail with no rush and no donation is quoted at 3000 cents, and 250 units of e-commerce is quoted at 1250 cents. Nothing is quoted at all for a run that is still in `PARALLEL_HOLD` — demand is placed against a committed outcome, not against a held possibility.

This request-time quote is deliberately a grosser figure than what the order will eventually recognize. The quote includes the rush surcharge and the donation flat, because at request time the operator is being told what the whole arrangement is worth; the settled recognition, applied later at delivery, return or distress, drops those surcharges and recognizes only the units that actually moved. The two variants therefore read differently for identical orders, and the request-time figure is the larger of the two.

Picking is the act that removes units from the pool, and it is the system's most heavily guarded operation because it is the point at which a channel's demand becomes a physical claim on the same scarce goods every other channel wants. A `FulfillmentCoordinator` picks by supplying its last-observed `expected_production_order_version`, the units it wants through `quantity`, and a `pick_remark`. The order picks only from `PLANNED`. Four conditions are evaluated in the pinned order of §2.10, and the response identifies the first that failed.

The state check comes first: an order that is not `PLANNED` is rejected with `ERR_INVALID_STATE` (HTTP 409) once its terminal lockdown is considered.

The optimistic-concurrency check then compares `expected_production_order_version` against the referenced run's current `version` and rejects a mismatch with `ERR_STALE_VERSION` (HTTP 412). This is the first of the two designated concurrency-controlled writes of record: the run's version is advanced by further picks on the same order, by cascades from the run's print layers, and by the run's own retirement, so a pick carrying a version observed before any of those events is refused and the client is expected to re-read the run and retry.

The quantity is then judged against two different pools. The `quantity` must not exceed the available units of the reference pool, which is the order's own requested `quantity`; the run's earliest shipment ordered by its `committed_at` stamp — the designated deterministic key when shipments cannot be separated by an exact stamp ordering — resolves to that same figure, so the reference pool does not shrink as legs are picked. A pick that exceeds it is rejected with `ERR_INVENTORY_INSUFFICIENT` (HTTP 409). Separately, the aggregate view must hold: the run's picked units counted across all channels — venue retail, pop-up and e-commerce together — must not, when added to this pick, exceed the run's printable pool, which is the run's `committed_inventory_cents` divided by its `unit_cost_cents`; a pick that would breach that ceiling is rejected with `ERR_CAPACITY_EXCEEDED` (HTTP 409). When every picked unit of the run has already been shipped or distressed, leaving nothing behind it to pick from, the pick is rejected with `ERR_LOT_EXHAUSTED` (HTTP 409).

Finally the remark is checked for uniqueness: `pick_remark` must differ from every remark already recorded on any prior pick of the same order, and a repeat is rejected with `ERR_PICK_REMARK_REUSED` (HTTP 409). This is what stops an operator from re-recording a pick under a note that has already been used, and it is why the third attempt to pick under an unchanged note fails even when quantity and version are both fine.

A successful pick adds its `quantity` to the order's `picked_qty`, moves `status` to `PICKED`, and increments the referenced run's `version` by exactly 1, refreshing the run's `updated_at`. Picking is accumulating rather than one-shot: a further pick on an order already in `PICKED` keeps it in `PICKED`, increases `picked_qty` again, and is subject to the same remark-uniqueness rule, so an operator picking in several passes must write a distinct note each time.

### 3.6. Shipping, Delivery and the Rush Commitment

Units leave the pool by shipment, and a shipment is both a physical commitment and a promise about time. A `FulfillmentCoordinator` ships picked units by supplying the units through `quantity`, the transport through `carrier` — one of `RUSH_AIR` or `GROUND` — and the hours promised through `sla_hours`, which must be strictly positive. The shipment itself is created in `IN_TRANSIT` with its `committed_at` stamped, which is also the deterministic processing key used when shipments cannot be separated by an exact stamp ordering.

Shipping requires the order to be in `PICKED`, requires the shipped `quantity` not to exceed the order's `picked_qty` less its `shipped_qty` so that nothing is shipped that was never picked, and requires the referenced run to still be in `COMMITTED` or `PRINTING`. A run that has been retired blocks the shipment outright: shipping against a retired run is rejected with `ERR_INVALID_STATE` (HTTP 409), because the goods the pick was made against are no longer a sellable pool.

Two commitment rules protect the rush promise, and both are reported as `ERR_RUSH_COMMITMENT_BREACH` (HTTP 422). Electing the `RUSH_AIR` carrier on an order whose `rush_flag` is false is refused, because air carriage is a commitment the order never declared. And a shipment whose `sla_hours` exceeds 24 hours is refused when the order carries `rush_flag` true and its `destination_code` is a venue or event-pop-up code, because a rush commitment to a venue that takes longer than a day to serve is not a rush commitment at all; a ground shipment to a destination with more slack is not caught by this rule.

A successful shipment adds its `quantity` to the order's `shipped_qty`, creates a `Shipment` record carrying the order through `fulfillment_order_id`, and moves the order's `status` to `SHIPPED` when the whole picked quantity has been shipped — a partial shipment leaves the order in `PICKED`, which is what makes the partial rail possible. Shipping again for the remaining picked quantity leaves the order in `SHIPPED`, creates a second `Shipment`, and appends a partial-shipment line to the run's settling ledger, so a multi-leg dispatch is visible as a sequence rather than as a single event. A shipment does not reprice the order: `requested_wholesale_cents` is left exactly at the value the request-time quote of §3.5 wrote, and it is only the delivery, return and distress rails of §3.6 and §3.7 that replace it.

Delivery closes the shipment leg. Confirm delivery only from `SHIPPED`; an order that has not shipped cannot be delivered, and the attempt is rejected with `ERR_INVALID_STATE` (HTTP 409). The order moves to `DELIVERED`, which is terminal, and every one of its `Shipment` records moves to `DELIVERED` with its `delivered_at` stamped — a shipment's `shipment_state` is otherwise `IN_TRANSIT` and its `delivered_at` is null while it is in transit. Recognizing delivery sets the order's `realized_wholesale_cents` equal to its `requested_wholesale_cents`, which is the first of the post-event rails that replaces the request-time recognition rather than adding to it, and it increments the `Licensor`'s `version` by 1 with `accrued_royalty_cents` recomputed from the delivered units per §3.8. `DELIVERED` is one of the six locked-down terminal states, so nothing in this API moves an order out of it afterwards.

### 3.7. Returns, Distress and Retiring the Losing Side

The event window ends and the music stops. Three disposal rails clean up the goods that did not sell, and they differ in who ends up with the merchandise and what is recovered.

Accepting unsold units back is a `FulfillmentCoordinator` action against a `return_quantity`, with an optional `destroy_mode`. It is permitted from `PLANNED`, whatever the order's pick history and whatever the run's status, and from `SHIPPED`, and the one bound on the request is that the `return_quantity` must not exceed the order's shipped quantity — a return larger than what went out is rejected with `ERR_CAPACITY_EXCEEDED` (HTTP 409). A return also participates in the run's aggregate ceiling, alongside picked, destroyed and donated units.

The order moves to `RETURNED`, which is terminal, and its `returned_qty` is increased by the `return_quantity`. Recovery is recognized as the request-time wholesale total less the returned units valued at the run's `unit_cost_cents`, floored at zero and rounded half up: that difference is written to `realized_wholesale_cents`, and whatever is not recovered is simply lost — this is the rail that replaces the recognition rather than adding to it, so the order ends up worth strictly less than it was quoted at. In either case the returned units raise the run's destroyed quantity by the `return_quantity` while the order's `donated_qty` is left untouched, and the entry path is what distinguishes the ledger line rather than the damage state: a return taken from `SHIPPED` appends a `units_damaged_destroyed` line, and a return taken from `PLANNED` appends a `units_destroyed_damaged` line instead. The two entry paths therefore leave different ledger lines even though they land the same terminal state and the same recovery arithmetic.

Distress is the rail for demand that has collapsed or goods that cannot be sold, and it is called explicitly by a `FulfillmentCoordinator` against a `distress_reason` — one of `LOSING_OUTCOME`, `DEMAND_COLLAPSE` or `DAMAGED_ON_SITE` — with an optional `destroy_mode` and an optional `donation_recipient_code`. It is permitted from `PLANNED`, and on the `DESTROY` branch the order's `destroyed_qty` is set to its full `quantity`, its `donated_qty` is left at 0, and its `requested_wholesale_cents` is rewritten to the units valued at the destroy penalty rate of 4 cents per unit. On the `DONATE` branch the order's `donated_qty` is set to its full `quantity`, its `destroyed_qty` is left at 0, and its `requested_wholesale_cents` is rewritten at the donate penalty rate, which is zero, so a donated order's requested total is zero. Both branches set `realized_wholesale_cents` to 0 and both move the order to `DISTRESSED`, which is terminal, with `distress_reason` recorded as supplied. Electing the `DONATE` branch without also supplying a `donation_recipient_code` is a request-shape failure reported as `ERR_INVALID_REQUEST` (HTTP 400), because a donation without a named recipient is not a donation. A distress also refuses to take the run past its ceiling: when the distressed units would carry the run's picked, destroyed, donated and returned total beyond its printable pool, the request is rejected with `ERR_CAPACITY_EXCEEDED` (HTTP 409). Every distress increments the `Licensor`'s `version` by 1 and recomputes the licensor's royalty settlement so that the distressed units stop accruing exposition royalty — distressed goods never accrue a royalty, which is the rule §3.8 depends on.

Distress also arrives on its own, without an operator, as the far end of the press-failure cascade described in §3.4: an order that is rescaled to a wholesale total of zero or below by a layer failure is moved to `DISTRESSED` with `distress_reason` `DEMAND_COLLAPSE`. An order that had already been picked when that happens is counted at its already-picked units as its destroyed quantity and has its `requested_wholesale_cents` recomputed downward by the committed-over-authorised scaling; the operational consequence is that units an operator physically picked can end up distressed without anyone calling distress, and the resulting state is terminal.

Retiring the run is the `ProductionPlanner` act that ends the losing outcome, and it is taken against a `retire_reason` — one of `OUTCOME_COMMITTED`, `LOSING_OUTCOME`, `ASSORTMENT_CHANGED` or `DEMAND_COLLAPSE` — with an optional `destroy_mode`. Retirement is permitted from `PARALLEL_HOLD`, from `COMMITTED` and from `PRINTING`. From `COMMITTED` or `PRINTING` with `destroy_mode` `DONATE` the run moves to `RETIRED_DONATED`; with `destroy_mode` `DESTROY` it moves to `RETIRED_DESTROYED`; and a retirement taken from `PARALLEL_HOLD` always lands in `RETIRED_DESTROYED`, which is why the losing side of a pair that never committed is destroyed rather than donated by default. Whichever branch applies, `retired_at` is stamped and the run's `retire_reason` records what ended it. Whichever branch applies, too, the run's entire print layer set is moved to `PRINT_FAILED` with `committed_qty` forced to 0, whether or not the layers had already been printed. Both `RETIRED_DESTROYED` and `RETIRED_DONATED` are terminal and neither can be left.

The two committed branches differ in what happens to the goods already sitting against the run. On the donation branch, every fulfillment order of the run that is still open — one that has not already reached the terminal `DELIVERED`, `RETURNED` or `DISTRESSED` state — has its `donated_qty` set to its full `quantity`, its `destroyed_qty` set to 0, its `requested_wholesale_cents` rewritten on the donate weighting with no penalty, its `realized_wholesale_cents` set to 0, and its `status` moved to `DISTRESSED` with `distress_reason` recorded as `DEMAND_COLLAPSE`. On the destruction branch, every such order of the run has its `destroyed_qty` set to its full `quantity`, its `donated_qty` set to 0, its `requested_wholesale_cents` rewritten on the destroy weighting with the penalty rate applied, its `realized_wholesale_cents` set to 0, and its `status` likewise moved to `DISTRESSED` with `distress_reason` `DEMAND_COLLAPSE`. A retirement requested without a `destroy_mode` takes the destruction path, so an omitted mode disposes of the goods as destroyed rather than donated on the committed branches too. Both branches increment the `Design`'s `version` by 1; a donation leaves `Design.approved_version` untouched rather than clearing it, and the destruction branch additionally carries the write-down value into the licensor's destroyed-unit ledger line while the donation branch reduces the licensor's `accrued_royalty_cents` by the destroyed-or-donated share instead. The donation branch therefore touches the licensor's accrued royalty directly, and the destruction branch touches its destroyed-unit line and the run's own write-down.

Retirement from `PARALLEL_HOLD` is the lightest branch and does not touch the design at all: the run moves to `RETIRED_DESTROYED` with `retired_at` stamped and `hold_allocation_cents` released, and every print layer is moved to `PRINT_FAILED` with `committed_qty` forced to 0, which then scales that run's open fulfillment orders down to zero and marks any order that is still open as `DISTRESSED`.

Retirement from `PRINTING` is the heaviest branch, because printed goods are already in the room. The run moves to `RETIRED_DESTROYED` with `retired_at` stamped and every printed layer is moved to `PRINT_FAILED` with `committed_qty` forced to 0. When this branch destroys rather than donates, each failed layer's `design_version_checked` is set to the run's `retired_design_version` — the version the goods were printed at — rather than to the design's current version; on the donation branch the freshly observed design version is recorded instead. Its distinguishing rule is skip-if-lesser: the write-down that a printed-then-failed layer would otherwise apply is skipped whenever it is strictly less than the write-down already standing on that run, because the greater write-down remains as the recorded position and re-booking a smaller figure would understate the loss. This branch increments the `Design`'s `version` by 1 and the `Licensor`'s `version` by 1, and it recomputes the run's `write_down_inventory_cents` by the rule below.

That write-down is computed on two independent targets, and the run is booked at the greater of the two on each target separately. The run's own target is `write_down_inventory_cents` for a retired run: the quantity the run actually lost — its destroyed units and its donated units as `destroyed_units` and `donated_units` record them — multiplied by the run's `unit_cost_cents`, multiplied by the share of cost that cannot be recovered. That recovery share depends on how the run came to exist rather than on how it ended: a `STANDARD` run recovers 0.6 of cost, so it writes down the remaining 0.4; a `CHAMPIONSHIP_WIN`, `MILESTONE` or `ATHLETE_TRANSACTION` run — the hot-market triggers — recovers nothing at all, so it writes down the full cost. The two variants diverge by a factor of 2.5, which is the same factor the post-event markup uses and is not a coincidence: 100 destroyed units at a 900-cent unit cost write down 36000 cents on a standard run and 90000 cents on a championship run. The second target is an individual order's `write_down_inventory_cents`, booked when the order is still sitting in `PLANNED` as the event window closes: the order's `quantity` multiplied by the run's `unit_cost_cents`, multiplied by the post-event markup of 2.5 — the punitive figure that reflects goods priced for an event that no longer exists. That run-level figure is recomputed from those two ledgers when the run is retired, replacing whatever value the run carried before rather than being accumulated on top of the units the run had printed. The greater figure is retained on each target, so an order-level write-down strictly smaller than the run-level write-down already booked is skipped rather than layered on top of it. The rule also tracks what the run discharged: the total of `realized_wholesale_cents` over the run's orders that reached `DELIVERED` or `RETURNED`, accumulated in creation order. That discharged figure is tracked for the run's audit and is not subtracted from the write-down: the run's own target is recomputed from the run's lost units alone, so a retired run's `write_down_inventory_cents` is never reduced by what its delivered or returned orders realized. Orders that never left `PLANNED` contribute nothing to the discharged figure, because they never realized anything to discharge against. The write-down is expressed to two decimal places with half-up rounding. The window length of 48 hours governs this whole rail, exactly as it governs printing and reopening in §3.4: after the event window closes the disposal arithmetic is the only remaining treatment for the goods.

### 3.8. Royalty Accruals

Royalty is earned when goods are recognized, not when they are printed, and it is earned per order rather than per run. The accrual walks every fulfillment order of the licensor's production runs whose status is `DELIVERED` or `RETURNED`, processed in `created_at` order with ties broken by `created_at` alone — the order's `quantity` is deliberately not a sort key, so the sequence is never reordered by size. Orders in `PLANNED`, `PICKED`, `SHIPPED` or `DISTRESSED` contribute nothing at all, and a `DISTRESSED` order never accrues a royalty on any path: distressed goods are destroyed or donated, and destroyed or donated goods do not earn.

For each contributing order, the gross is the order's `realized_wholesale_cents`, and the rate is selected by the garment the artwork was printed on, read from `Design.garment_sku`: a `JERSEY` earns 0.08 of gross per unit value, a `TRACTOR` 0.02, a `DUFFEL` 0.04, a `CAP` 0.06, a `MINI` 0.06 and a `PENNANT` nothing at all — pennants are a promotional giveaway as far as royalty is concerned. The row's royalty is the gross multiplied by that rate, rounded half up to the cent. A designer premium of 0.125 is then applied to the row's royalty, rounded half up to the cent, and the row's total is the royalty plus the premium. The licensor's `accrued_royalty_cents` is the sum of those row totals, and the total is not rounded again after summing.

The rounding sequence is the substance of the rule and it is pinned: each row is rounded to the cent before the rows are summed, and the sum is then taken as it stands. Rounding the unrounded rows once at the end instead yields a different cent, and the divergence is easy to see. Two delivered orders of 1250 cents each on a cap design, at a 0.06 rate and a 0.125 premium, give per-row values of 75 cents of royalty and 9.38 cents of premium — 75 plus 9.375 rounded half up — for a row total of 84.38 cents, and a two-row ledger of 168.76 cents. Rounding the combined unrounded figure once instead gives 168.75 cents. The per-row sequence is the specification; the single-rounding variant is the projectable but non-default form, and it reads a cent higher than the actual ledger whenever a licensor has two or more accrual rows, which is exactly the kind of discrepancy the pinned order exists to prevent.

Each accrual row also carries the machinery that lets the accrual be reconciled as a ledger. A row's `basis` records which rule produced it and is written as `RUSH_or_STANDARD` from the moment the row is created — every row this rail writes carries that basis, so a row is never read with a null or a nested-shortfall basis. Rush-or-standard accruals on a given licensor carry a `version_seq` counter of 1, 2, 3 and upward in `created_at` order; when a later rush-or-standard accrual on the same licensor is written, every earlier rush-or-standard row of that licensor is flagged `superseded` and its `accrued_cents` is driven to 0 so it contributes nothing to the licensor's running total, which is what keeps the ledger from double-counting a version that was restated. A row's `accrual_state` stays `ACCRUED` and its `settled_cents` stays 0 for the life of the ledger, because the settlement rail of §3.9 settles against the licensor's ledger triple and never marks the accrual rows themselves as paid. Its `incurred_at` records the instant the royalty-bearing activity occurred. Accrual rows are append-mostly and are read back by their `basis`, their `version_seq` and their `accrual_state`.

### 3.9. Minimum-Guarantee Settlement and Its Compensating Reversal

A rights holder's contract carries a floor as well as a rate, and settlement is how the floor is honoured early. A `LicensingOps` operator applies a settlement by supplying its last-observed `expected_licensor_version`, the amount it wants to reserve through `reserved_cents`, and the `accept_guarantee_breach` flag. The operator may only settle the licensor its `X-User-ID` names, and only where that operator did not itself record the licensor decision on the design being produced under that rights holder — the segregation-of-duties rule of §2.1 refuses the attempt with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) otherwise.

The ledger the settlement works against is the three-part figure of §2.4: the accrued royalty `accrued_royalty_cents`, the guarantee recovery block `guarantee_recovery_block_cents` and the unsettled amount `accrued_unsettled_cents`, all three starting at 0 for a newly registered licensor and related at every observable point by the invariant that the unsettled amount is the greater of zero and the accrued royalty less the recovery block. The waterfall that keeps that relation is applied in a fixed sequence and is never re-entered: reset, then earn, then drop, then floor, then cap, then unsettled. The cap is applied last, and it matters: when the recovery block would exceed 12500 cents, the excess is not blocked at all — the block is capped at 12500 and the excess is folded back into the licensor's accrued royalty instead, so a licensor whose guaranteed shortfall runs beyond the cap keeps the excess as recoverable royalty rather than having it blocked away. That capped form is the actual ledger; an uncapped projection of the same exposure would block the full shortfall and leave a smaller unsettled figure, and it is not what this ledger records.

Applying a settlement has preconditions and a pinned arithmetic order. The licensor must have a strictly positive unsettled amount, and the reserved amount must not exceed it; a settlement attempted with no unsettled accrual at all, or with a reserve larger than the unsettled amount, is rejected with `ERR_NO_ACCRUED_ROYALTY` (HTTP 422). The settlement also carries the version guard of §2.8: the supplied `expected_licensor_version` must equal the licensor's current `version`, and a stale value is rejected with `ERR_STALE_VERSION` (HTTP 412), because any royalty accrual, production retirement or enforcement confirmation that landed since the client read the licensor has advanced that version, and settling against it would reserve an amount the licensor no longer holds. This is the second of the two designated concurrency-controlled writes of record, alongside the pick of §3.5. Both are checked at the same rung of the ladder of §2.10, after state eligibility and before rights clearance, so a settlement against a licensor that does not exist is reported as a missing resource rather than as a stale version.

The arithmetic then proceeds in order. The accrued royalty after the reserve is the greater of zero and the accrued royalty less the reserved amount. If that post-settlement figure is below the contract's `minimum_guarantee_cents` while `accept_guarantee_breach` is false, the request is rejected with `ERR_GUARANTEE_FLOOR_BREACH` (HTTP 422) and the message carries the exact shortfall — the greater of zero and the guarantee less the post-settlement figure — so the operator can see precisely how deep the breach would run rather than being told only that one would occur. With the breach accepted, the recorded figures are written in this order: `snapped_accrued_cents` takes the licensor's accrued royalty as it stood before the settlement, `guarantee_shortfall_cents` takes the shortfall just computed, `max_recoverable_early_cents` takes the unsettled amount as it stood before the application, then the licensor's accrued royalty is reduced by the reserved amount, the recovery block is increased by the shortfall, the unsettled amount is recomputed from the invariant, and the settlement's `licensor_version` records the licensor's `version` immediately after the application — which is the anchor the client captures for its next version-bearing write against that ledger. The licensor's `version` is incremented by 1.

The distinction between the two reference figures is worth stating plainly because both are in play. With an accrued royalty of 843.75 cents, a guarantee of 2000 cents, a reserve of 100 cents and the breach accepted, the post-settlement accrued figure is 743.75, the shortfall is 1256.25, the snapped figure is 843.75 and the recoverable figure is 843.75, so the licensor's accrued royalty becomes 743.75, its recovery block becomes 1256.25 and its unsettled amount recomputes to 0. The same inputs with the breach refused are rejected with `ERR_GUARANTEE_FLOOR_BREACH` (HTTP 422) carrying 1256.25 in the message and the ledger is left untouched.

The settlement machine has one further guard on repeated application: a settlement that would reserve nothing while leaving the accrued royalty, the recovery block and the unsettled amount all unchanged moves no royalty at all and is rejected with `ERR_SETTLEMENT_NOOP` (HTTP 422) rather than being recorded as an empty event. A settlement must move at least one ledger quantity to be worth recording.

Reversal is the compensating rail, and it is what makes early settlement a reversible commercial instrument rather than a one-way write. A settlement is created by the application in `PENDING` and moves to `APPROVED` as the application's side effect, so an applied settlement is read as `APPROVED`. Reversal is permitted only where an approved settlement exists to reverse — an attempt with none is rejected with `ERR_INVALID_STATE` (HTTP 409) — and it carries the same version guard, `expected_licensor_version` compared against the licensor's current `version` with a mismatch rejected as `ERR_STALE_VERSION` (HTTP 412). The settlement moves from `APPROVED` to `REVERSED`, which is terminal, and the ledger is restored exactly: the licensor's accrued royalty is set back to the settlement's `snapped_accrued_cents`, the recovery block is reduced by the settlement's recorded `guarantee_shortfall_cents`, and the unsettled amount is recomputed from the invariant. The licensor's `version` is incremented by 1. Because the reversal restores exactly the captured figure and removes exactly the amount that was added, applying a settlement and then reversing it returns the three ledger quantities to precisely the values observed before the application, with no drift — the reference round trip above ends at an accrued royalty of 843.75, a recovery block of 0 and an unsettled amount of 843.75, which is where it started. When the reversal clause is elected, no counterfeit report of that licensor is revalued by the reversal: a report's leakage, penalty and total exposure are recomputed only by a confirmation call, so the exposure that stands on a report is whatever the report's own last adjudication wrote and the reversal leaves it untouched.

### 3.10. Counterfeit Enforcement and Exposure Valuation

Counterfeit goods appear around venues within minutes of a win, and the brand-protection function needs a valuation of the harm that any two investigators would compute identically from the same evidence. An `EnforcementAgent` opens a report by naming the rights holder through `licensor_id`, where the goods were found through `venue_code`, the marketplace listing through `online_listing_id`, the total units observed through `unit_count`, which must be strictly positive, the units already believed counterfeit through `suspect_quantity`, which defaults to 0, and the detection instant through `detected_at`. A new report is written with its `report_status` in `OPEN` and `infringement_confirmed` null, `suspect_quantity` at 0 unless supplied, `royalty_leakage_cents`, `penalty_cents` and `total_exposure_cents` all at 0.

Adjudicating the report is a confirmation call carrying `infringement_confirmed` and `suspect_quantity`. Two integrity checks guard a confirmation, and both are reported as `ERR_COUNTERFEIT_OVERCOUNT` (HTTP 422): the `suspect_quantity` may not exceed the report's `unit_count`, since more units cannot be counterfeit than were observed, and a confirmed infringement may not carry a `suspect_quantity` of zero, since a confirmation of nothing is not a finding. A third check sits alongside them: the report's `online_listing_id` must not begin with the `VERIFIED-` prefix, because enforcement may not confirm a violation against a listing that has already been verified — the attempt is rejected with `ERR_LISTING_UNVERIFIED` (HTTP 422).

Confirmation is asymmetric, and the asymmetry is deliberate. When `infringement_confirmed` is true, the report moves from `OPEN` to `ENFORCED` and the exposure is computed on the confirmed quantity: the leaked royalty is the confirmed unit count multiplied by 1450 cents of exposure valuation per unit, multiplied by 0.6 as the share of gross that royalty represents, multiplied by the licensor's `royalty_rate_pct`, rounded half up to the cent. The deterrence penalty is the leaked royalty multiplied by 2.5, rounded half up to the cent. The total exposure is the leaked royalty plus the penalty, and a confirmed finding whose total falls below 500 cents is raised to 500 cents, so trivial confirmations still carry a deterrent floor. The report's `unit_count` is never an input to this arithmetic — it is only the bound the integrity check enforces above. A confirmation on 200 units against a licensor whose `royalty_rate_pct` is 0.08 computes a leaked royalty of 13920 cents, a penalty of 34800 cents and a total exposure of 48720 cents. Every confirmation increments the `Licensor`'s `version` by 1 and surfaces the exposure on that licensor's enforcement ledger.

When `infringement_confirmed` is false the report writes a total exposure of 0 and stays in `OPEN`, and it is left open deliberately so that it may be enforced again after further evidence arrives. Because that same `suspect_quantity` would have produced a substantial total under a true confirmation, the confirmation flag alone is what separates the two outcomes, and the differing totals for identical quantities are the point of the rule. A report already in `ENFORCED` may be re-enforced with a larger confirmed quantity: the leaked royalty, the penalty and the total exposure are all recomputed on the newly confirmed quantity, and the report stays `ENFORCED`, so `ENFORCED` loops back to itself and accumulates as the evidence grows. A cleared report is likewise not terminal, which is why the `OPEN` state is the one that carries a self-loop back to itself on every unconfirmed adjudication.

### 3.11. Advancing the Logical Clock

Every temporal rule in this document — the 48-hour event window, the rush and same-hour bands of the hot-market commitment, the 24-hour rush delivery boundary, the rush service level a window must satisfy — is evaluated against the logical clock rather than against wall-clock time, and the test-driving capability that moves it belongs to a `PlatformAdmin` alone. Calling it supplies `current_utc`, the instant the clock should read from then on, and the clock takes that value whether it moves forward or backward, because the capability must support replaying a scenario as well as running one forward. The response carries no resource body.

The clock's starting position is part of the contract: the server boots with the clock reading exactly `2026-09-01T00:00:00Z`, and until a clock-setting call is made the clock reads that instant rather than the host's real time. Any deadline, reopen window, rush service level or window classification evaluated before the first clock-setting call is therefore evaluated against that fixed instant, which is what makes a freshly started server's behaviour reproducible rather than dependent on when it happened to start.

## 4. Endpoint Definitions

Every operation below is mounted at the path shown, and every one of them requires both `X-User-ID` and `X-User-Role` headers. Operations that create a new stand-alone resource or add a new distinct resource to a collection — registering a licensor, opening a production run, registering a capacity window, opening a reservation, placing channel demand, opening a shipment for a picked order, logging a counterfeit report, and applying a minimum-guarantee settlement — return `201 Created` with the created resource in the response body. Operations that modify an existing resource, including adding a layer collection to a run, recording a licensor decision, resubmitting a design, printing or recording a print failure on a layer, retiring a run, picking, delivering, returning, distressing, adjudicating a counterfeit report and reversing a settlement, return `200 OK` with the updated resource in the response body. Read operations return `200 OK`. The clock-setting capability returns `200 OK` with no resource payload.
