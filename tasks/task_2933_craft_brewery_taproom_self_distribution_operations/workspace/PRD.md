# Craft Brewery Taproom & Self-Distribution API — Product Requirements Document

## 1. Introduction

A regional craft brewery lives inside three regulatory perimeters at once. The federal government decides whether the brewery may sell anything at all, and whether each recipe and each label has cleared review. Each state decides whether the brewery may deliver its own beer inside that state's borders, how many barrels it may deliver per calendar year, and what happens the moment a wholesaler is appointed. And the tax authorities want a periodic return that splits every barrel removed from the premises into the portion poured across the bar and the portion loaded onto a truck. Today those three perimeters live in three unrelated spreadsheets, and the cellar log that would reconcile them lives on a clipboard by the brite tanks.

This document specifies the API that replaces all of it. The service is a single system of record spanning the brewer's notice, brand approvals, cellar vessels and brew scheduling, the packaging line, the physical keg float, taproom pour metering, growler and crowler sanitation, state distribution licences, wholesaler appointments and their franchise consequences, distribution orders with their full landed cost, excise determination and filing, and off-site event permits. Every collection is mounted at the API root — there are no nested collection paths — and child records carry their parent's identifier in the request body rather than in the URL.

Two design commitments run through everything that follows. First, **barrels are conserved**: every barrel that leaves a fermenter is accounted for in exactly one place at any instant, and every operation that reserves, ships, releases or voids inventory moves that barrel between accounts rather than creating or destroying it. Second, **nobody signs both sides of a control**: the user who proposes a wholesaler appointment may not approve it, the user who prepares an excise return may not file it, and the bartender who fills a growler may not be the person who attests its sanitation reading. Readers implementing this specification should treat both commitments as invariants that the test suite will probe directly.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across every endpoint. Where a rule here and a workflow narrative in §3 describe the same behaviour from different angles, they reinforce one another; they never conflict.

### 2.1. User and Role-Based Access Control

Every request — reads included — must carry two headers: `X-User-ID`, naming the acting user, and `X-User-Role`, naming the capacity that user is acting in. If either header is absent, is supplied as an empty string, is blank, or if `X-User-Role` names anything other than one of the five roles below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A header supplied as an empty string counts as absent.

The system recognises exactly five roles, spelled here as they must appear in `X-User-Role`:

- `BreweryAdmin` — the owner-operator. Stands up the premises record, the keg float, and the commercial surface: distribution orders, appointment proposals, and excise return drafts. Never approves its own paperwork.
- `ComplianceOfficer` — holder of the regulatory file. Makes TTB submissions, registers state licences, approves the appointments a `BreweryAdmin` proposed, files the returns a `BreweryAdmin` prepared, and drives the event-permit application. Cannot propose an appointment or prepare a return, so it can never sit on both sides of a control.
- `CellarOperator` — runs the brewhouse, the packaging line and the keg float. Owns every production transition from scheduling a brew through filling, deploying and returning kegs. Holds no commercial or regulatory authority whatsoever.
- `TaproomStaff` — works the bar. Records pours, growler and crowler fills with their sanitation attestation, and taps or returns kegs at the bar. Cannot brew, package, or touch a licence.
- `StateRegulator` — the external authority. Decides the brewer's notice, TTB formula and label filings, and off-site event permits. Deliberately holds no operational write on production, inventory, orders or excise returns; it only ever answers applications.

Once the headers are accepted, the role named by `X-User-Role` must appear in the acting endpoint's authorised-role list, which §4 tabulates. A role that is not listed is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). This check runs before the request body is inspected at all, so a forbidden role submitting a malformed body still receives the 403 rather than a schema error. All five roles may read every list and single-resource retrieval endpoint, and all five may drive the logical clock.

Identity in this system is **opaque for every one of the five roles**. When `X-User-Role` is `BreweryAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a workflow demands an audit stamp — as `proposed_by_user_id` on an appointment, or as `prepared_by_user_id` on an excise return — but never compares it to any entity's `id`. The same holds for `ComplianceOfficer`, whose `X-User-ID` is recorded as `approved_by_user_id` on an approved appointment and as `filed_by_user_id` on a filed return; for `CellarOperator`, whose `X-User-ID` is recorded as `certified_by_user_id` on a completed packaging run; for `TaproomStaff`, whose `X-User-ID` is recorded as `poured_by_user_id` on each pour; and for `StateRegulator`, whose identifier is not persisted on any row at all. Because no role is entity-backed, there is no resource-ownership check anywhere in this API: `X-User-ID` is compared only against other recorded user-id stamps, and only where a segregation-of-duties rule says so.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two pagination query parameters. `limit` is the maximum number of rows to return; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` is the number of rows to skip before the first returned row; it defaults to 0 and may not be negative. Both must be integers. A `limit` outside the range from 1 through 100 inclusive, or a negative `offset`, or either value supplied as a non-integer, is a schema failure reported as `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint says otherwise, list results are sorted by `created_at` in ascending order — oldest row first.

The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of rows matching the request's filters before pagination is applied; `has_more` is true when rows matching the filters remain beyond the returned window.

### 2.4. Resource Identity, Timestamps and the Version Counter

Every persisted resource carries a server-minted `id`: a UUID string with no type prefix of any kind. Clients never supply an `id`.

Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written. Resources that can be modified additionally carry `updated_at`, in the same format, refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row. The brewery singleton, beers, tanks, batches, packaging runs, keg assets, state licences, distributor appointments, distribution orders, excise reports and event permits all carry the full quartet.

Taproom pours are the single exception. A pour is an append-only event record: **it carries only `id` and `created_at`. It has no `updated_at` field and no `version` field at all**, because nothing in this system ever modifies a pour after it is written.

A "mutation" for versioning purposes includes recomputation of derived fields. When a packaging run completes and the owning batch's `packaged_bbl` and `remaining_bbl` shift as a result, the batch has been mutated: its `updated_at` refreshes and its `version` increments, even though the client addressed the run rather than the batch. The same holds for every cascade described in §2.9 — each row that a cascade touches has its own `updated_at` refreshed and its own `version` incremented by 1.

### 2.5. The Logical Clock

Nothing in this system reads wall-clock time. Every deadline, expiry, occupation interval, reporting window, tap instant and removal instant is evaluated against a server-held **logical clock**. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to the host's real time.

An operator of any of the five roles may advance or reset the clock by supplying a `current_utc` instant to the clock-setting capability; the response echoes the new `current_utc`. Setting the clock does not itself mutate any entity, but a forward move has a deferred consequence: state licences are re-evaluated for expiry lazily, on the next request that reads them (see §3.6).

All datetime fields, in requests and in responses, are ISO 8601 UTC instants. A datetime string that cannot be parsed as an ISO 8601 UTC instant is a schema failure (`ERR_INVALID_REQUEST`). Wherever a pair of instants delimits an interval, the later bound must be strictly after the earlier one: `brew_end_utc` strictly after `brew_start_utc`, `expires_at_utc` strictly after `effective_from_utc`, `period_end_utc` strictly after `period_start_utc`, and `event_end_utc` strictly after `event_start_utc`. A reversed or equal pair is likewise `ERR_INVALID_REQUEST`.

### 2.6. Barrels, Ounces, Cents and Rounding

Three units of measure circulate through this system, and the conversions between them are fixed.

- **Barrels** (`bbl`) are the regulatory unit of removal. Barrel quantities in the production and excise ledgers — `actual_yield_bbl`, `packaged_bbl`, `remaining_bbl`, `total_loss_bbl`, `bbl_removed`, `allocated_bbl`, `shipped_bbl`, `available_bbl`, `loss_share_bbl`, `carry_in_taproom_bbl`, `carry_in_distribution_bbl`, `taproom_bbl_ytd`, `distribution_bbl_ytd`, `total_bbl_ytd`, `carry_in_barrels_ytd`, `barrels_shipped_ytd`, `taproom_bbl`, `distribution_bbl` and `total_taxable_bbl` — carry **three decimal places, rounded half up**. Barrel quantities that describe intent or capacity rather than a booked removal — `capacity_bbl`, `planned_volume_bbl`, `annual_barrel_cap`, `bbl_requested` and `requested_bbl` — carry **two decimal places**. A submitted number with more decimal places than its field permits is `ERR_INVALID_REQUEST`.
- **Fluid ounces** (`oz`) are the taproom unit. One barrel is exactly **3,968 fluid ounces**, and one US gallon is exactly **128 fluid ounces**. Ounce quantities — `filled_volume_oz`, `remaining_volume_oz`, `poured_volume_oz`, `returned_volume_oz`, `depletion_variance_oz` and `keg_shrinkage_oz` — carry **two decimal places, rounded half up**.
- **Cents** are the money unit; there are no fractional cents anywhere. `price_per_bbl_cents`, `price_cents`, `product_cents`, `freight_cents`, `franchise_fee_cents`, `landed_cost_cents`, `federal_tax_cents`, `state_tax_cents` and `total_tax_due_cents` are all whole-cent integers.

Wherever this document says a value is rounded, the method is **round half up** — a value exactly halfway between two representable results rounds away from zero. Several calculations round **more than once**, at intermediate steps, before summing; where that happens §3 pins the exact step order, and the pinned order is the only correct one. Rounding the final exact product instead of rounding each component independently produces a different answer and is wrong.

### 2.7. Optimistic Concurrency on Parent Records

Two create operations in this system stake a claim on a parent record whose own state the claim depends on. Both are guarded by an optimistic-concurrency check on the parent's `version`.

**Planning a packaging run.** A request to create a packaging run must carry `expected_batch_version` as a required, non-optional field holding the `version` of the target batch as the client last observed it. If `expected_batch_version` does not equal that batch's current `version`, the request is rejected with `ERR_STALE_BATCH_VERSION` (HTTP 412). The rule exists because a newly planned run legitimately claims part of the batch's remaining barrels; without the check, a client working from a stale view of the batch would plan against volume another run has already claimed. Creating the run itself increments the batch's `version` by 1, so a second create replayed from the same observed version is rejected.

**Proposing a wholesaler appointment.** A request to create a distributor appointment must carry `expected_state_license_version` as a required, non-optional field holding the `version` of the target state licence as the client last observed it. If it does not equal that licence's current `version`, the request is rejected with `ERR_STALE_LICENSE_VERSION` (HTTP 412). A newer proposal legitimately supersedes the territory scope a prior proposal staked out, so without the version check a client working from a stale licence view would appoint a wholesaler over a scope that has already moved.

Both checks are evaluated **after** existence resolution, so a request naming a batch or licence that does not exist receives the 404 rather than the 412. No other endpoint in this API accepts a version field: any endpoint not named in the two paragraphs above takes no `expected_*_version` input, and supplying one is not part of its contract.

### 2.8. The Rejection Ladder: Order of Evaluation

When a single request violates more than one rule, the answer the client receives is fully determined: the system evaluates checks in the fixed order below and reports the **first** violation it finds, stopping there. This ordering is part of the contract, not an implementation detail — a request that is both submitted by a forbidden role and carries a malformed body must answer `ERR_FORBIDDEN_ROLE`, not `ERR_INVALID_REQUEST`.

The ladder, from first-evaluated to last:

1. **Header authentication** — both `X-User-ID` and `X-User-Role` present, non-blank, and `X-User-Role` naming one of the five declared roles. Otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorisation** — the acting role appears in the endpoint's authorised list. Otherwise `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint, and is evaluated before the body is inspected.
3. **Request and query schema** — `ERR_INVALID_REQUEST` (400). Covers unknown enum values, numeric range violations, excess decimal places, missing required fields, datetime strings that will not parse as ISO 8601 UTC instants, the pagination guards from §2.3, and the interval-ordering guards from §2.5. Conditional requirements belong here too: a pour whose `container_type` is `CROWLER_32OZ` or `GROWLER_64OZ` makes `container_sanitized`, `sanitizer_ppm`, `contact_time_seconds`, `attested_by_user_id` and `label_fields` all required, while a pour into any of the three draft container types must **not** carry any of them — supplying a growler field on a draft pour is a schema failure. Applies to every write endpoint and to every list endpoint that accepts `limit` and `offset`.
4. **Path-parameter existence** — resources named by URL path variables are resolved **left to right**, and the first identifier that resolves to nothing produces its own entity-specific 404. The vocabulary is `ERR_BREWERY_NOT_FOUND`, `ERR_BEER_NOT_FOUND`, `ERR_TANK_NOT_FOUND`, `ERR_BATCH_NOT_FOUND`, `ERR_PACKAGING_RUN_NOT_FOUND`, `ERR_KEG_ASSET_NOT_FOUND`, `ERR_TAPROOM_POUR_NOT_FOUND`, `ERR_STATE_LICENSE_NOT_FOUND`, `ERR_APPOINTMENT_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_REPORT_NOT_FOUND` and `ERR_EVENT_PERMIT_NOT_FOUND`. Applies to every endpoint with a path parameter. `ERR_BREWERY_NOT_FOUND` additionally answers any operation that needs the brewery singleton when no brewery row has been created at all.
5. **Body foreign-key existence** — identifiers carried in the request body are resolved next, using the same entity-specific 404 vocabulary. The guarded references are a batch's `beer_id` and `tank_id`; a packaging run's `batch_id`; a keg fill's `packaging_run_id`; a pour's `keg_asset_id`; an appointment's `state_license_id` and `appointed_beer_id`; an order's `beer_id` and `state_license_id`; an excise return's `amends_report_id`; an event permit's `featured_beer_id`; and a keg movement's `event_permit_id`. Applies to batch creation, packaging-run creation, keg fill, pour recording, appointment proposal, order submission, excise-return drafting and event-permit drafting.
6. **Business-code uniqueness** — `ERR_DUPLICATE_CODE` (409) when the submitted human-authored code already exists. The unique codes are a beer's `name`, a tank's `code`, a batch's `batch_code`, a packaging run's `run_code`, a keg's `keg_serial`, a distribution order's `order_code` and a state licence's `state_code`. Applies to beer registration, tank registration, batch scheduling, packaging-run creation, keg registration, state-licence registration and order submission.
7. **Brewery singleton uniqueness** — at most one brewery row may ever exist; a second attempt to create it is refused with `ERR_BREWERY_ALREADY_EXISTS` (409).
8. **Optimistic concurrency** — the two checks of §2.7: `expected_batch_version` against the batch's `version` (`ERR_STALE_BATCH_VERSION`, 412) and `expected_state_license_version` against the licence's `version` (`ERR_STALE_LICENSE_VERSION`, 412). Because this rung sits below rungs 4 and 5, a bad identifier still yields a 404.
9. **Transition legality** — the target resource must currently be in a state from which the requested transition is declared. Terminal states reject every trigger through this rung. Each entity has its own code: `ERR_NOTICE_TRANSITION_INVALID` for a brewer's-notice action the current `notice_status` does not permit; `ERR_FILING_TRANSITION_INVALID` for a formula or label filing, or a decision on one, that the current `registration_state` or `label_state` does not permit; `ERR_TANK_TRANSITION_INVALID`; `ERR_BATCH_TRANSITION_INVALID`; `ERR_RUN_TRANSITION_INVALID`; `ERR_KEG_TRANSITION_INVALID`; `ERR_ORDER_TRANSITION_INVALID`; `ERR_ORDER_NOT_ALLOCATED` specifically for a shipment attempted on an order whose `state` is not `ALLOCATED`; `ERR_APPOINTMENT_TRANSITION_INVALID`; `ERR_REPORT_TRANSITION_INVALID`; and `ERR_PERMIT_TRANSITION_INVALID`. All are HTTP 409. Applies to every action endpoint that drives a state machine.
10. **Brewer's-notice gating** — `ERR_NOTICE_NOT_ACTIVE` (409) when the brewery's `notice_status` is anything other than `ACTIVE`. `PENDING_NOTICE`, `SUSPENDED` and `REVOKED` all fail here. This gate guards **eight** operations: batch start, packaging-run completion, every keg movement, pour recording, order submission, order allocation, order shipment, and event-permit submission.
11. **Other cross-entity state gates** — `ERR_TANK_NOT_IDLE` (409) when a batch start targets a tank whose `status` is `OCCUPIED`, `DIRTY` or `OUT_OF_SERVICE`; `ERR_BATCH_NOT_CONDITIONING` (409) when a packaging run is created against, or completed against, a batch that is not `CONDITIONING`; `ERR_KEG_NOT_TAPPED` (409) when a pour is recorded against a keg whose `state` is not `TAPPED`; `ERR_RUN_NOT_COMPLETED` (409) when a keg fill cites a run that is still `PLANNED` or already `VOIDED`; `ERR_LICENSE_NOT_ACTIVE` (409) when an order is submitted, allocated or shipped under a licence whose `status` is `SUSPENDED` or `EXPIRED`. This rung guards batch start, packaging-run completion, pour recording, keg fill, order submission, order allocation and order shipment.
12. **Federal approval prerequisites on the beer** — `ERR_FORMULA_NOT_APPROVED` (422) when the beer's `registration_state` is neither `FORMULA_APPROVED` nor `FORMULA_EXEMPT` on any sale path, meaning a taproom pour, a keg tap, a keg deployment, or an order submission. `ERR_LABEL_NOT_APPROVED` (422) when `label_state` is anything other than `COLA_APPROVED` on a **distribution** path, meaning order submission or a distribution deployment of a keg — a certificate of label approval is never required for a taproom draft pour and this code is never raised for one. `ERR_EVENT_PERMIT_NOT_APPROVED` (422) when an event deployment names a beer with no approved event permit covering the current logical instant. This rung guards pour recording, keg movements and order submission.
13. **Tank occupation scheduling** — `ERR_TANK_SCHEDULE_CONFLICT` (409) on batch scheduling; see §3.2 for the buffer arithmetic.
14. **Licence validity window** — `ERR_LICENSE_NOT_YET_EFFECTIVE` (409) when the logical clock is earlier than the licence's `effective_from_utc`; `ERR_LICENSE_EXPIRED` (409) when the logical clock has reached or passed the licence's `expires_at_utc`. Because that bound is exclusive, an instant exactly equal to `expires_at_utc` is already lapsed. This rung guards order submission, order allocation, order shipment and appointment proposal.
15. **Excise period closure** — `ERR_PERIOD_NOT_CLOSED` (422) when a return is filed while the logical clock is still earlier than `period_end_utc`.
16. **Statutory termination notice** — `ERR_TERMINATION_NOTICE_NOT_ELAPSED` (409) when a termination finalisation arrives before `termination_effective_utc`.
17. **Off-site concurrency ceiling** — `ERR_OFFSITE_EVENT_CAPACITY_EXCEEDED` (409) on an approval decision; see §3.9.
18. **Sanitation standard** — `ERR_SANITATION_BELOW_STANDARD` (422) when the sanitation verdict computes to a failure. This guards growler and crowler fills, keg washes, and tank clean-in-place cycles. A failing verdict is never persisted.
19. **Growler label completeness** — `ERR_GROWLER_LABEL_INCOMPLETE` (422) when a growler or crowler fill's `label_fields` is missing or has a blank member. This is deliberately **below** the sanitation check, so a fill that is both under-sanitised and unlabelled reports `ERR_SANITATION_BELOW_STANDARD`.
20. **Segregation of duties** — `ERR_SEGREGATION_OF_DUTIES` (409) when an appointment's approver equals its proposer, when an excise return's filer equals its preparer, or when a growler or crowler fill's `attested_by_user_id` equals the pouring user. This rung guards appointment approval, excise filing and pour recording.
21. **Territory rule** — `ERR_TERRITORY_NOT_LICENSED` (422) when an order's `ship_to_state_code` differs from the referenced licence's `state_code`, or when an event permit's `venue_state_code` has no state licence at all. Guards order submission and event-permit drafting.
22. **Wholesaler requirement** — `ERR_WHOLESALER_APPOINTMENT_REQUIRED` (422) on order submission into a licence whose `license_type` is `WHOLESALER_ONLY` with no live appointment covering the beer.
23. **Appointment scope exclusivity** — `ERR_DUPLICATE_APPOINTMENT_SCOPE` (409) on appointment approval that would leave two live appointments covering the same licence with overlapping brand scope.
24. **Good cause** — `ERR_GOOD_CAUSE_REQUIRED` (422) when a termination request in a franchise state omits `good_cause_code`.
25. **Excise period integrity** — `ERR_PERIOD_ALREADY_FILED` (409) when a non-amending return is filed for a period another filed return already covers; `ERR_AMENDMENT_TARGET_NOT_FILED` (422) when `amends_report_id` points at a return whose `state` is `DRAFT` or `SUPERSEDED` rather than `FILED`.
26. **Volume and container constraints** — `ERR_TANK_CAPACITY_EXCEEDED` (422), `ERR_UNITS_EXCEED_BATCH_VOLUME` (422), `ERR_KEG_SIZE_MISMATCH` (422), `ERR_RUN_UNITS_EXHAUSTED` (409), `ERR_POUR_EXCEEDS_KEG_VOLUME` (422) and `ERR_RETURN_EXCEEDS_FILL` (422). This rung guards batch scheduling, yield recording, packaging-run completion, keg fill, pour recording and keg movements; §3 states each threshold at the workflow it guards.
27. **Void and dump guards** — `ERR_RUN_HAS_ALLOCATIONS` (409) when voiding a completed run whose `allocated_bbl`, `shipped_bbl` or `kegs_filled_count` is non-zero; `ERR_BATCH_HAS_PLANNED_RUNS` (409) when dumping a conditioning batch that still has a run in `PLANNED`.
28. **Self-distribution annual ceiling** — `ERR_SELF_DISTRIBUTION_CAP_EXCEEDED` (422) at shipment; see §3.7.
29. **Off-site annual barrel ceiling** — `ERR_EVENT_BARREL_CAP_EXCEEDED` (422) at event-permit submission; see §3.9.

Two consequences of this ladder deserve emphasis. Because transition legality (rung 9) sits above the notice gate (rung 10), an operation attempted from a state that does not declare it reports its entity's transition error even when the brewer's notice is also inactive. And because the notice gate sits above the beer-approval prerequisites (rung 12), a pour of an unapproved beer while the notice is suspended reports `ERR_NOTICE_NOT_ACTIVE`, not `ERR_FORMULA_NOT_APPROVED`.

### 2.9. Cascade Discipline and the Conservation of Packaged Barrels

Several transitions in this system reach beyond the row the client addressed. Where they do, the cascade is **transitive**: each hop is caused by the previous hop's mutation, not by the original request, and every hop must complete before the response is returned. Consistency is immediate; there is no deferred or eventual settlement anywhere.

Three cascades run to depth three, and they are the deepest reach in the system:

- **Suspending or revoking the brewer's notice.** Hop 1 moves every state licence in `ACTIVE` to `SUSPENDED`. Hop 2, caused by hop 1, rejects each distribution order citing a just-suspended licence whose `state` is `SUBMITTED` or `ALLOCATED`. Hop 3, caused by hop 2, releases the allocation of every order that was in `ALLOCATED` when hop 2 rejected it, returning barrels to the packaging runs those allocations cited.
- **Revoking a certificate of label approval.** Hop 1 rejects every distribution order for that beer whose `state` is `SUBMITTED` or `ALLOCATED`. Hop 2, caused by hop 1, releases each rejected order's allocation lines back to the cited runs.
- **Returning the last outstanding keg of a run.** Hop 1 books the returning keg's volumes and variance. Hop 2, caused by hop 1, decrements the owning run's `kegs_outstanding_count`. Hop 3, caused by hop 2, reconciles the run when that count reaches zero.

Underneath all of it sits the **conservation law for packaged barrels**. For any packaging run, at every instant, `bbl_removed` equals the sum of `available_bbl`, `allocated_bbl` and `shipped_bbl`. Reserving inventory for an order moves barrels from available to allocated; shipping moves them from allocated to shipped; releasing a reservation — because the order was cancelled from `ALLOCATED`, or because a cascade rejected it — moves them back from allocated to available. `bbl_removed` itself changes only when the run completes (rising from zero) or is voided (falling to zero). A companion law holds one level up on the batch: once a yield has been recorded, `actual_yield_bbl` equals `packaged_bbl` plus `remaining_bbl`, and voiding a completed run compensates both sides of that equation so it continues to hold.

### 2.10. Flat Collections, Reverse Reachability and Filters

Every collection in this API sits at the root of the URL space. There is no owning aggregate in the path and no nested collection: a packaging run is not addressed beneath its batch, and a pour is not addressed beneath its keg. Children instead carry their parent's identifier as a field in the request body, and the relationship is traversed in reverse through filtered list endpoints.

Because a path may still carry an identifier — a single-resource read, or an action on one row — the left-to-right resolution rule of §2.8 rung 4 applies wherever more than one path variable appears, and applies to the single variable otherwise. For a filing decision, the beer identified in the path is resolved before the filing type named after it is interpreted.

The filters available on each list, all optional and all combinable with `limit` and `offset`, are the reverse-reachability surface of the data model:

- Beers may be filtered by `registration_state` or `label_state`, the two independent approval dimensions.
- Tanks may be filtered by `status` or `tank_type`.
- Batches may be filtered by `beer_id`, `tank_id` or `state` — this is how a beer's or a vessel's batches are found.
- Packaging runs may be filtered by `batch_id`, `state`, `destination` or `reconciliation_state`.
- Keg assets may be filtered by `packaging_run_id`, `filled_beer_id`, `state` or `deployment_channel`.
- Taproom pours may be filtered by `keg_asset_id` or `container_type`.
- State licences may be filtered by `status`, `license_type` or `franchise_state`.
- Distributor appointments may be filtered by `state_license_id`, `appointed_beer_id` or `state`.
- Distribution orders may be filtered by `beer_id`, `state_license_id`, `appointment_id`, `state` or `channel`.
- Excise reports may be filtered by `amends_report_id` — the self-reference that finds the amendment of a return — or by `state` or `taproom_basis`.
- Event permits may be filtered by `featured_beer_id`, `venue_state_code`, `state` or `permit_type`.

A filter value that is not a member of the underlying enumeration is a schema failure (`ERR_INVALID_REQUEST`), not an empty result set.

## 3. Business Logic & Workflows

### 3.1. Federal Prerequisites: The Brewer's Notice and the Two Brand Approval Dimensions

Before anything else exists, a `BreweryAdmin` stands up the **brewery singleton** — the premises record that carries the federal brewer's notice. Creation takes the brewery's registered `legal_name` (between 1 and 120 characters), its `home_state_code` (exactly two uppercase letters, the USPS code of the state where the premises sit), and the `ttb_brewers_notice_number` exactly as filed (between 1 and 32 characters). Exactly one brewery row may ever exist; a second creation attempt is refused with `ERR_BREWERY_ALREADY_EXISTS`. The new row is minted with `notice_status` of `PENDING_NOTICE`, a null `notice_effective_utc`, a null `suspension_reason`, and both `carry_in_taproom_bbl` and `carry_in_distribution_bbl` at 0.000. Nothing is sellable in that condition.

Only a `StateRegulator` may move the notice, and it does so by naming an `action`. `ACTIVATE` takes `PENDING_NOTICE` to `ACTIVE`, and is legal only from `PENDING_NOTICE`; it stamps `notice_effective_utc` with the current logical clock, clears `suspension_reason`, re-derives `taproom_sellable` and `distribution_sellable` on every beer, and increments the brewery's `version` by 1. `SUSPEND` takes `ACTIVE` to `SUSPENDED` and requires a `reason` that is present and non-blank, which is stored as `suspension_reason`. `REINSTATE` takes `SUSPENDED` back to `ACTIVE`, re-stamping `notice_effective_utc` from the logical clock and clearing `suspension_reason`. `REVOKE` takes `SUSPENDED` to `REVOKED` and likewise requires a non-blank `reason`, stored as `suspension_reason`; `REVOKED` is terminal, and once reached no notice action of any kind is legal again. An action that the current `notice_status` does not declare — `REVOKE` straight from `ACTIVE`, `ACTIVATE` on an already-active notice, anything at all from `REVOKED` — is refused with `ERR_NOTICE_TRANSITION_INVALID`.

The `ACTIVE → SUSPENDED` move is the most consequential write in the system, because it triggers the three-hop cascade of §2.9 in full. First, every state licence whose `status` is `ACTIVE` moves to `SUSPENDED`. Second — caused by that licence change, not by the notice change — every distribution order citing a licence that just moved, and whose own `state` is `SUBMITTED` or `ALLOCATED`, moves to `REJECTED` with `rejection_reason` set to `NOTICE_SUSPENDED`. Third — caused by those rejections — every order that had been in `ALLOCATED` releases each entry of its `allocation_lines`: the cited packaging run's `allocated_bbl` falls by that entry's barrel figure while its `available_bbl` rises by the same amount, and the order's own `allocation_lines` becomes an empty list with `allocated_bbl` returning to 0.000. Alongside all of that, every beer's `taproom_sellable` and `distribution_sellable` become false. Each row touched anywhere in hops one through three has its `updated_at` refreshed and its `version` incremented by 1 — the brewery, each licence, each order and each packaging run.

`SUSPENDED → REVOKED` carries a similar but blunter consequence: every state licence, whatever its current `status`, moves to `SUSPENDED`, and no sale operation of any kind is permitted thereafter. Reinstatement is deliberately asymmetric with suspension. `SUSPENDED → ACTIVE` returns to `ACTIVE` only those licences whose `status` is `SUSPENDED` **and** whose `expires_at_utc` is strictly later than the current logical clock; a licence that lapsed during the suspension stays suspended. Orders that were rejected during the suspension are **never revived** — `REJECTED` is terminal, and the brewery must submit fresh orders.

Two carry-in figures exist so that fiscal boundaries can be exercised without months of history. A `ComplianceOfficer` may record pre-go-live barrels already removed this calendar year by supplying `carry_in_taproom_bbl` and `carry_in_distribution_bbl`, each at least 0 with three decimal places; the call overwrites both fields outright rather than accumulating. From them the brewery's three read-only aggregates are derived: `taproom_bbl_ytd` is `carry_in_taproom_bbl` plus the sum of `taproom_bbl` over every excise report whose `state` is `FILED` (reports in `SUPERSEDED` are excluded, as are drafts); `distribution_bbl_ytd` is `carry_in_distribution_bbl` plus the sum of `distribution_bbl` over the same filed set; and `total_bbl_ytd` is the sum of those two. Recording a carry-in adjustment shifts the opening tier position of every excise return computed afterwards, and increments the brewery's `version`. The brewery row also exposes `franchise_locked_state_codes`: the list of `state_code` values, sorted ascending, of every state licence that has at least one distributor appointment whose `state` is `ACTIVE`.

A brand is registered as a **beer** by either a `BreweryAdmin` or a `ComplianceOfficer`. Registration takes the brand `name` (1 to 80 characters, unique across all beers), a `style` descriptor for the label (1 to 40 characters), `abv_pct` — the alcohol-by-volume percentage, at least 0.5 and at most 20.0, carrying one decimal place — and `price_per_bbl_cents`, the wholesale price of a barrel in whole cents, at least 1. An optional `requires_formula` flag defaults to true and means the recipe uses non-traditional ingredients and therefore needs TTB formula approval. The flag decides the beer's opening position on the first of its two approval dimensions: when `requires_formula` is true the beer is minted with `registration_state` of `DRAFT`, and when it is false the beer is minted directly in `FORMULA_EXEMPT` and the formula machine never runs for it at all. Either way `label_state` is minted as `NO_LABEL`, `cola_id` and `label_fields` are null, and both sellability flags are false until the notice is active.

Those two dimensions — `registration_state` over the values `DRAFT`, `FORMULA_PENDING`, `FORMULA_APPROVED` and `FORMULA_EXEMPT`, and `label_state` over `NO_LABEL`, `COLA_PENDING`, `COLA_APPROVED` and `COLA_REVOKED` — live on the same beer row and advance **independently**. Advancing one never touches the other. A beer may therefore hold `COLA_APPROVED` while its formula sits back in `DRAFT`, and that combination is legal, not a data error.

A `ComplianceOfficer` opens a filing by naming a `filing_type`. A `FORMULA` filing is legal only when `registration_state` is `DRAFT` and `requires_formula` is true, and requires an `ingredient_list` that is present and non-empty; it advances `registration_state` from `DRAFT` to `FORMULA_PENDING`, leaves `label_state` untouched, and increments the beer's `version` by 1. A `LABEL` filing is legal when `label_state` is either `NO_LABEL` or `COLA_REVOKED`, and requires `label_fields` carrying non-blank `brand_name`, `abv_statement`, `net_contents` and `health_warning`; it advances `label_state` to `COLA_PENDING`, stores the submitted `label_fields` on the beer, leaves `registration_state` untouched, and increments `version` by 1. When the filing is a re-filing after a revocation — that is, from `COLA_REVOKED` — it additionally clears the stale `cola_id`. A filing attempted from a state that does not declare it is refused with `ERR_FILING_TRANSITION_INVALID`.

Only a `StateRegulator` answers a pending filing, supplying a `decision` and, where relevant, a `cola_id` or an explanatory `note`. On the formula dimension, a `decision` of `APPROVED` moves `FORMULA_PENDING → FORMULA_APPROVED` and re-derives both sellability flags; `REJECTED` moves `FORMULA_PENDING → DRAFT`, leaving `label_state` untouched. On the label dimension, `APPROVED` moves `COLA_PENDING → COLA_APPROVED` and requires a `cola_id` that is present and non-blank, which is stored on the beer, after which `distribution_sellable` is re-derived; `REJECTED` moves `COLA_PENDING → NO_LABEL` and clears `label_fields`; and `REVOKED` moves `COLA_APPROVED → COLA_REVOKED`. Every one of those decisions increments the beer's `version` by 1, and a decision on a dimension that is not pending — or a revocation of a certificate that was never approved — is refused with `ERR_FILING_TRANSITION_INVALID`.

Revocation is the label dimension's cascade. `COLA_APPROVED → COLA_REVOKED` drops `distribution_sellable` to false while leaving `taproom_sellable` exactly as it was, then reaches out two hops: first every distribution order for that beer whose `state` is `SUBMITTED` or `ALLOCATED` moves to `REJECTED` with `rejection_reason` of `LABEL_REVOKED`, and then — caused by those rejections — every allocation entry of each just-rejected order is released, decrementing the cited run's `allocated_bbl` and incrementing its `available_bbl` by that entry's barrel figure. The beer's `version` increments by 1, and so does the `version` of every other row the cascade touched.

The two derived sellability flags are the single gate every sale path consults. `taproom_sellable` is true exactly when the brewery's `notice_status` is `ACTIVE` **and** the beer's `registration_state` is either `FORMULA_APPROVED` or `FORMULA_EXEMPT`; a certificate of label approval is emphatically **not** required to pour draft beer across the bar. `distribution_sellable` is true exactly when the brewery's `notice_status` is `ACTIVE`, the beer's `registration_state` is `FORMULA_APPROVED` or `FORMULA_EXEMPT`, **and** its `label_state` is `COLA_APPROVED`. Any sale path against a beer failing the formula half of that test reports `ERR_FORMULA_NOT_APPROVED`; a distribution path against a beer failing only the label half reports `ERR_LABEL_NOT_APPROVED`.

### 3.2. Cellar Vessels, Brew Scheduling and the Batch Lifecycle

A cellar vessel — a **tank** — is registered by a `BreweryAdmin` or a `CellarOperator` with a `code` (1 to 16 characters, unique across the cellar), a `tank_type` of either `FERMENTER` or `BRITE`, and a `capacity_bbl` giving the maximum working volume in barrels, strictly greater than zero and carrying two decimal places. A new vessel opens with `status` of `IDLE`, a `cip_cycle_count` of 0, a null `last_cip_utc`, and a null `occupying_batch_id`.

Vessels cycle through four states: `IDLE`, `OCCUPIED`, `DIRTY` and `OUT_OF_SERVICE`. A `CellarOperator` drives three of the transitions by naming a service `action`. `CIP` — clean-in-place — is legal only from `DIRTY` and returns the vessel to `IDLE`, stamping `last_cip_utc` with the current logical clock and incrementing `cip_cycle_count` by 1. `TAKE_OUT_OF_SERVICE` is legal only from `IDLE` and moves the vessel to `OUT_OF_SERVICE`; `RETURN_TO_SERVICE` is legal only from `OUT_OF_SERVICE` and returns it to `IDLE`. Each of the three increments the tank's `version` by 1. A service action the current `status` does not declare — a clean-in-place on an idle vessel, a return-to-service on a dirty one — is refused with `ERR_TANK_TRANSITION_INVALID`. The fourth transition, `OCCUPIED → DIRTY`, is never client-driven: the system performs it when the occupying batch reaches `PACKAGED` or `DUMPED`, clearing `occupying_batch_id` and incrementing the tank's `version`.

A clean-in-place cycle is only accepted if the chemistry was right, and the same sanitation standard governs every wash in this system. The operator submits a measured `sanitizer_ppm` — the sanitiser concentration in parts per million, an integer — and a `contact_time_seconds`, the integer number of seconds the solution was in contact with the surface. The reading **passes** when the concentration is at least 150 ppm and at most 400 ppm, both bounds inclusive, **and** the contact time is at least 60 seconds, likewise inclusive. Anything else fails: 150 ppm passes while 149 fails, 400 ppm passes — over-concentration is a rinse hazard, not a bonus — while 401 fails, and 60 seconds passes while 59 fails. A failing reading is never recorded anywhere. The request is aborted with `ERR_SANITATION_BELOW_STANDARD` and no clean-in-place cycle is booked at all: `last_cip_utc` is not moved, `cip_cycle_count` is not incremented, and the vessel stays `DIRTY`. A blank or absent reading is a different matter entirely — that is a schema failure reported as `ERR_INVALID_REQUEST`, not a failed verdict.

Scheduling a brew creates a **batch**, and only a `CellarOperator` may do it. The payload names the `beer_id` of the brand to be produced and the `tank_id` of the vessel to be reserved, plus a `batch_code` (1 to 24 characters, unique), a `planned_volume_bbl` the cellar intends to brew (strictly greater than zero, two decimal places), and the two instants `brew_start_utc` and `brew_end_utc` that delimit the occupation interval — inclusive at the start, exclusive at the end, with the end strictly after the start. An optional `loss_basis`, defaulting to `PRO_RATA` and otherwise `LAST_RUN_ABSORBS`, is chosen at scheduling time and decides how brewhouse-to-package loss is distributed when the batch eventually closes. A batch opens in `state` `SCHEDULED` with a null `actual_yield_bbl`, a `packaged_bbl` of 0.000, a null `total_loss_bbl` and a null `dumped_reason`. Its `remaining_bbl` is derived as the batch's yield figure minus `packaged_bbl`, where the yield figure is `actual_yield_bbl` once one has been measured and `planned_volume_bbl` until then — so a fresh batch reports `remaining_bbl` equal to its `planned_volume_bbl`. A `planned_volume_bbl` above the referenced vessel's `capacity_bbl` is refused with `ERR_TANK_CAPACITY_EXCEEDED`.

Vessels cannot be double-booked, and a mandatory turnaround separates consecutive occupations so the cellar has time to clean. The buffer is **twelve hours**, applied to the requested batch's own interval on both sides. Concretely: for the batch being scheduled, take the window that begins twelve hours before its `brew_start_utc` and ends twelve hours after its `brew_end_utc`, treating that window as inclusive at its start and exclusive at its end. No other batch on the same vessel whose `state` is `SCHEDULED`, `BREWING` or `CONDITIONING` may have its own half-open interval, from its `brew_start_utc` inclusive to its `brew_end_utc` exclusive, overlap that window. A conflict is refused with `ERR_TANK_SCHEDULE_CONFLICT`. Because both intervals are half-open, two occupations separated by a gap of exactly twelve hours do **not** overlap and are legal; a gap of eleven hours and fifty-nine minutes is not. Batches already in `PACKAGED` or `DUMPED` are dead and never conflict with anything.

Starting the brew advances the batch `SCHEDULED → BREWING`, and it is the point at which the reservation becomes a real occupation. The transition demands three things: the batch is in `SCHEDULED`, the brewery's `notice_status` is `ACTIVE` (otherwise `ERR_NOTICE_NOT_ACTIVE`), and the referenced vessel's `status` is exactly `IDLE` (otherwise `ERR_TANK_NOT_IDLE` — a `DIRTY` vessel must pass a clean-in-place cycle first, and an `OUT_OF_SERVICE` one must be returned to service). Across the two rows, the vessel moves `IDLE → OCCUPIED` with its `occupying_batch_id` set to the starting batch, and both the batch's `version` and the tank's `version` increment by 1. That back-reference is a convenience mirror of the batch's own `tank_id`, and it is null whenever the vessel's `status` is anything other than `OCCUPIED`.

When fermentation is done the operator records the measured yield, advancing `BREWING → CONDITIONING`. The payload carries `actual_yield_bbl`, which must be strictly greater than zero, must not exceed the occupied vessel's `capacity_bbl` — a yield above capacity is `ERR_TANK_CAPACITY_EXCEEDED` — and carries three decimal places. Storing it re-derives `remaining_bbl` as `actual_yield_bbl` minus `packaged_bbl`, and increments the batch's `version` by 1. From `CONDITIONING`, the batch closes to `PACKAGED` only by system action, when a completing packaging run drains it to the closing remainder (see §3.3); `PACKAGED` is terminal.

A batch can also be written off. Dumping requires a `reason` that is present and non-blank, stored as `dumped_reason`, and is declared from three states, each with its own consequence. From `SCHEDULED` the vessel is untouched, because this batch never occupied it — the reservation simply evaporates. From `BREWING` the occupying vessel moves `OCCUPIED → DIRTY`. From `CONDITIONING` the vessel likewise moves `OCCUPIED → DIRTY`, and because a yield had already been measured the batch's `total_loss_bbl` is set to `actual_yield_bbl` minus `packaged_bbl`; a dump from `CONDITIONING` is additionally refused with `ERR_BATCH_HAS_PLANNED_RUNS` while any packaging run of the batch is still in `PLANNED`, since an unclosed run would otherwise be orphaned. Each dump increments the batch's `version` by 1, plus the vessel's `version` where the vessel moved. `DUMPED` is terminal, and any of start, condition or dump attempted from a state that does not declare it — including anything at all from `PACKAGED` or `DUMPED` — is refused with `ERR_BATCH_TRANSITION_INVALID`.

### 3.3. Packaging Runs, the Barrel Ledger and Loss Allocation

A **packaging run** is the line's plan to pull a stated number of containers off a conditioning batch. A `CellarOperator` creates one by naming the `batch_id` it will draw down, a `run_code` (1 to 24 characters, unique across all runs), a `package_type`, a `destination`, a `units_planned` count of at least 1, and the `expected_batch_version` demanded by §2.7. The `package_type` is one of `HALF_BBL_KEG`, `QUARTER_BBL_KEG` or `CAN_CASE_24`, and the `destination` is either `TAPROOM` or `DISTRIBUTION` — a single decision at planning time that determines, permanently, whether the resulting inventory may ever be drawn on by a distribution order. The batch must be in `CONDITIONING`; a run created against a batch in any other state is refused with `ERR_BATCH_NOT_CONDITIONING`.

Each container type has a fixed barrel content. A `HALF_BBL_KEG` holds 0.500 barrels, a `QUARTER_BBL_KEG` holds 0.250 barrels, and a `CAN_CASE_24` — a twenty-four pack of twelve-ounce cans, which is 288 fluid ounces against the 3,968 fluid ounces in a barrel — is taken to hold 0.073 barrels, that ratio rounded to three decimal places. These three figures are used identically by the completion arithmetic, by the keg-size match test, and by the volume guard.

A fresh run opens in `state` `PLANNED` with `reconciliation_state` of `NOT_APPLICABLE`, a null `units_produced`, a null `removed_at_utc`, a null `voided_at_utc`, a null `certified_by_user_id`, a null `keg_shrinkage_oz`, a null `loss_share_bbl`, a `kegs_filled_count` of 0, and every barrel figure — `bbl_removed`, `allocated_bbl`, `shipped_bbl` and `available_bbl` — at 0.000. **No barrels move at creation time.** Creation nevertheless increments the owning batch's `version` by 1, because the run has staked a claim on the batch's remaining volume; that increment is exactly what makes a second create replayed from the same observed version fail the stale-batch check.

Certifying the run is what actually removes beer from the batch. The operator supplies `units_produced`, the count actually filled, which must be at least 1. The run must be in `PLANNED` (otherwise `ERR_RUN_TRANSITION_INVALID`), the owning batch must still be in `CONDITIONING` (otherwise `ERR_BATCH_NOT_CONDITIONING`), and the brewery's `notice_status` must be `ACTIVE` (otherwise `ERR_NOTICE_NOT_ACTIVE`). The barrels the run removes, `bbl_removed`, are `units_produced` multiplied by the barrel content of the run's `package_type`, rounded half up to three decimal places, and that figure may not exceed the batch's current `remaining_bbl`; a request that would remove more than the batch has left is refused with `ERR_UNITS_EXCEED_BATCH_VOLUME`. On success the run advances `PLANNED → COMPLETED`, `available_bbl` becomes equal to `bbl_removed`, `removed_at_utc` is stamped with the current logical clock — this instant is the tax-determination instant for those barrels — and `certified_by_user_id` records the acting `X-User-ID`. In the same operation the batch's ledger moves in lockstep: `packaged_bbl` rises by `bbl_removed` and `remaining_bbl` falls by the same amount. Both the run's `version` and the batch's `version` increment by 1.

Completion can close the batch. **When the resulting `remaining_bbl` is one barrel or less — at most 1.000, the comparison inclusive so exactly 1.000 closes the batch — the batch auto-transitions `CONDITIONING → PACKAGED` in the same request.** Closure sets the batch's `total_loss_bbl` to `actual_yield_bbl` minus `packaged_bbl`, moves the occupying vessel `OCCUPIED → DIRTY` with its `occupying_batch_id` cleared, and runs the loss allocation described next, writing a `loss_share_bbl` onto every completed run of the batch. The batch's `version`, the vessel's `version` and every touched run's `version` each increment by 1.

**Loss allocation** distributes the brewhouse-to-package shortfall across the runs that actually packaged beer, and the batch's `loss_basis` chosen at scheduling time selects between two genuinely different distributions of the same number. The input set is only those packaging runs of the closing batch whose `state` is `COMPLETED`, ordered by their `created_at` ascending — never by identifier. Runs still in `PLANNED` are not yet charged anything, and runs in `VOIDED` are excluded from the set and have their `loss_share_bbl` cleared to null. The total to distribute is the batch's `actual_yield_bbl` minus its `packaged_bbl`, rounded half up to three decimal places. If there are no completed runs at all, or if that total is zero or negative, every completed run's `loss_share_bbl` is set to 0.000 and nothing further happens.

Under a `loss_basis` of `PRO_RATA`, each completed run first takes a proportional share: the total loss multiplied by that run's `bbl_removed`, divided by the batch's `packaged_bbl`, with **each run's share rounded half up to three decimal places independently** before anything is summed. Because independent rounding rarely reproduces the total, the arithmetic then closes the gap: the remainder is the total loss minus the sum of the already-rounded shares, itself rounded half up to three decimal places, and if that remainder is anything other than zero it is assigned **in full to exactly one run — never spread across several**. The receiving run is the one with the largest `bbl_removed`; if several tie on `bbl_removed`, the tie is broken in favour of the **earliest** `created_at`. That run's `loss_share_bbl` becomes its rounded share plus the entire remainder, rounded half up to three decimal places. Worked through: a batch with an `actual_yield_bbl` of 16.000 packaged by three runs of 5.000 barrels each has a total loss of 1.000 barrels; each raw share is one barrel times five barrels divided by fifteen barrels, which is 0.333 after independent rounding; the three rounded shares sum to 0.999; the 0.001 remainder goes to the earliest-created run because all three tie on `bbl_removed`; and the result is 0.334, 0.333, 0.333.

Under a `loss_basis` of `LAST_RUN_ABSORBS`, every completed run except one is set to 0.000 and the **final run by `created_at` ascending** absorbs the entire total loss as its `loss_share_bbl`. The same three-run batch therefore yields 0.000, 0.000 and 1.000 — identical inputs, a completely different distribution. In both variants the invariant is exact: the sum of `loss_share_bbl` across the completed runs equals the total loss to the last thousandth of a barrel.

Voiding a run is declared from two states and behaves very differently from each. From `PLANNED` there is nothing to undo — `bbl_removed` is still 0.000 — so the void simply stamps `voided_at_utc` with the current logical clock, moves the run to `VOIDED`, and increments the run's `version` by 1; no ledger figure anywhere moves. From `COMPLETED` the void is a full compensation, and it is guarded: it is refused with `ERR_RUN_HAS_ALLOCATIONS` if the run's `allocated_bbl` is non-zero, or its `shipped_bbl` is non-zero, or its `kegs_filled_count` is non-zero, because beer that has already been reserved, shipped or racked into kegs cannot be un-removed. When the guard passes, the batch's `packaged_bbl` falls by the run's `bbl_removed` and its `remaining_bbl` rises by the same amount, restoring the batch identity that `actual_yield_bbl` equals `packaged_bbl` plus `remaining_bbl`; the run's `bbl_removed` and `available_bbl` are reset to 0.000, its `units_produced` is set back to null, and `voided_at_utc` is stamped. If the batch had already auto-closed to `PACKAGED`, it **stays** `PACKAGED` — the closure is not undone — but its `total_loss_bbl` is recomputed, the voided run's own `loss_share_bbl` is cleared, and the loss allocation is re-run under the batch's `loss_basis` over the surviving completed runs. Both the run's `version` and the batch's `version` increment by 1. `VOIDED` is terminal: a void attempted on a run already in `VOIDED`, like a completion attempted on a run that is not `PLANNED`, is refused with `ERR_RUN_TRANSITION_INVALID`.

The four barrel figures on a run are the conserved ledger of §2.9 in concrete terms, and three of them are derived rather than stored. `allocated_bbl` is the sum of the barrel entries in the `allocation_lines` of every distribution order in `ALLOCATED` that cites this run; `shipped_bbl` is the same sum over orders in `SHIPPED`; and `available_bbl` is `bbl_removed` less `allocated_bbl` less `shipped_bbl`. A void sets `bbl_removed` back to 0.000, which is precisely why it may not run while either of the other two is non-zero.

Two further counters track the keg float against the run. `kegs_filled_count` is the number of keg assets ever filled from this run since it completed, and `kegs_outstanding_count` is the number of keg assets whose `packaging_run_id` is this run and whose `state` is `FILLED`, `TAPPED` or `DEPLOYED` — the kegs still out in the world. Together they drive the run's second, parallel state dimension, `reconciliation_state`. It stays `NOT_APPLICABLE` for a run whose `package_type` is `CAN_CASE_24`, since cases are never racked into kegs. For a run whose `package_type` is `HALF_BBL_KEG` or `QUARTER_BBL_KEG` it moves `NOT_APPLICABLE → OPEN` on the first keg fill, with `kegs_filled_count` and `kegs_outstanding_count` each rising by 1 and the run's `version` incrementing by 1. It then moves `OPEN → RECONCILED` — by system action, never by a client request — at the instant `kegs_outstanding_count` reaches zero after a returning keg is booked, provided `kegs_filled_count` is at least 1. Reconciliation writes `keg_shrinkage_oz` as the sum of `depletion_variance_oz` over every keg asset filled from this run, rounded half up to two decimal places, and increments the run's `version` by 1. `RECONCILED` is terminal on that dimension.

### 3.4. The Keg Float: Cleaning, Filling, Deployment and Return

Physical kegs are tracked individually as **keg assets**, because a brewery's float is capital equipment and because the difference between what a keg was filled with and what comes back is the brewery's clearest shrinkage signal. A `BreweryAdmin` or a `CellarOperator` registers one with its etched `keg_serial` (1 to 24 characters, unique across the float) and its nominal `size_bbl`, which must be either 0.5 or 0.25 — there is no third size. A new keg opens in `state` `EMPTY_DIRTY` with a `cycle_count` of 0, a null `last_cleaned_utc`, a null `packaging_run_id`, a null `filled_beer_id`, a null `returned_volume_oz`, a null `depletion_variance_oz`, a null `tapped_at_utc`, a null `deployment_channel`, a `shrinkage_flagged` of false, and `filled_volume_oz`, `remaining_volume_oz` and `poured_volume_oz` all at 0.

A keg circulates through six states: `EMPTY_DIRTY`, `CLEANED`, `FILLED`, `TAPPED`, `DEPLOYED` and `DECOMMISSIONED`. Any clean, fill or movement that the keg's current `state` does not declare — including anything at all attempted from `DECOMMISSIONED`, which is terminal — is refused with `ERR_KEG_TRANSITION_INVALID`.

Washing a keg is legal only from `EMPTY_DIRTY` and moves it to `CLEANED`. A `CellarOperator` submits the same two sanitation readings the cellar uses on its vessels, `sanitizer_ppm` and `contact_time_seconds`, and the same standard applies unchanged: the concentration must be at least 150 and at most 400 parts per million with both bounds inclusive, and the contact time must be at least 60 seconds. Anything outside that band aborts the request with `ERR_SANITATION_BELOW_STANDARD` and **no wash is recorded** — the keg stays `EMPTY_DIRTY` and `last_cleaned_utc` is not moved. A passing wash stamps `last_cleaned_utc` with the current logical clock and wipes the keg's history of its previous contents: `packaging_run_id`, `filled_beer_id`, `returned_volume_oz` and `depletion_variance_oz` are all cleared to null and `shrinkage_flagged` returns to false. The keg's `version` increments by 1.

Filling is legal only from `CLEANED` and moves the keg to `FILLED`. The `CellarOperator` names the `packaging_run_id` the beer comes from, and three conditions gate the fill. The cited run's `state` must be `COMPLETED` — a run still in `PLANNED` has no beer yet and a run in `VOIDED` never will, and either is refused with `ERR_RUN_NOT_COMPLETED`. The barrel content of the run's `package_type` must equal this keg's `size_bbl` exactly, so a half-barrel keg may only be filled from a `HALF_BBL_KEG` run and a quarter-barrel keg only from a `QUARTER_BBL_KEG` run; any mismatch, including every attempt to rack a keg from a `CAN_CASE_24` run, is refused with `ERR_KEG_SIZE_MISMATCH`. And the run must have containers left to give: its `kegs_filled_count` must be strictly less than its `units_produced`, otherwise the fill is refused with `ERR_RUN_UNITS_EXHAUSTED`. On success the keg's `packaging_run_id` is set, its `filled_beer_id` is resolved by following the run to its batch and the batch to its beer, its `filled_volume_oz` is set to `size_bbl` multiplied by the 3,968 fluid ounces in a barrel — 1984.00 ounces for a half barrel, 992.00 for a quarter — its `remaining_volume_oz` is set equal to `filled_volume_oz`, and its `poured_volume_oz` is reset to 0. On the run's side, `reconciliation_state` moves `NOT_APPLICABLE → OPEN` if this is the first fill, and `kegs_filled_count` and `kegs_outstanding_count` each rise by 1. Both the keg's `version` and the run's `version` increment by 1.

Everything a filled keg subsequently does is expressed as a **movement**, driven by a `movement_type` of `TAP`, `DEPLOY_DISTRIBUTION`, `DEPLOY_EVENT`, `RETURN` or `DECOMMISSION`. Both `CellarOperator` and `TaproomStaff` may record any of the five, though in practice tapping and returning are the bar's everyday moves and deployment is the cellar's. Every movement requires the brewery's `notice_status` to be `ACTIVE`; a suspended or pending notice refuses the movement with `ERR_NOTICE_NOT_ACTIVE`.

A `TAP` movement is legal only from `FILLED` and moves the keg to `TAPPED`. Beyond the notice, it demands that the filled beer's `taproom_sellable` be true — the formula dimension must be settled, though no certificate of label approval is needed to pour draft. The movement stamps `tapped_at_utc` with the current logical clock and sets `deployment_channel` to `TAPROOM`. That instant matters well beyond the cellar: it is the whole-keg tax-determination instant, and it is exactly what the whole-keg excise basis of §3.8 counts.

A `DEPLOY_DISTRIBUTION` movement is also legal only from `FILLED`, and moves the keg to `DEPLOYED` with `deployment_channel` set to `DISTRIBUTION`. It demands that the filled beer's `distribution_sellable` be true, so a beer whose `label_state` is not `COLA_APPROVED` cannot leave the premises on a truck and the attempt is refused with `ERR_LABEL_NOT_APPROVED`. A `DEPLOY_EVENT` movement is its sibling: likewise legal only from `FILLED`, likewise moving the keg to `DEPLOYED`, but with `deployment_channel` set to `EVENT`, and gated on a different authority — the filled beer must be the featured brand of an event permit whose `state` is `APPROVED` and whose event window covers the current logical instant, identified by the optional `event_permit_id` carried with the movement. A deployment to an event with no such permit is refused with `ERR_EVENT_PERMIT_NOT_APPROVED`. Both deploy movements increment the keg's `version` by 1.

Bringing a keg back is the system's deepest single-request cascade. A `RETURN` movement is declared from both `TAPPED` and `DEPLOYED`, moves the keg to `EMPTY_DIRTY`, and behaves identically from either. It requires `returned_volume_gal`, the volume of beer physically left in the keg expressed in US gallons, present and at least 0; converted at 128 fluid ounces to the gallon, it may not exceed the keg's `filled_volume_oz`, and a return claiming more beer came back than went in is refused with `ERR_RETURN_EXCEEDS_FILL`. The first hop books the volumes on the keg itself: `returned_volume_oz` becomes `returned_volume_gal` multiplied by 128, rounded half up to two decimal places; `depletion_variance_oz` becomes `returned_volume_oz` minus the keg's expected remainder, where the expected remainder is `filled_volume_oz` minus `poured_volume_oz` — the same quantity the keg reports as `remaining_volume_oz` — again rounded half up to two decimal places; and `cycle_count` rises by 1. A **negative** `depletion_variance_oz` means less beer came back than the pour log predicted, which is shrinkage. The keg is flagged when the variance is large in either direction: the tolerance is two percent of `filled_volume_oz`, rounded half up to two decimal places, and `shrinkage_flagged` becomes true when the absolute value of `depletion_variance_oz` is **strictly greater** than that tolerance. For a half-barrel keg filled with 1984.00 ounces the tolerance is 39.68 ounces, so a variance of exactly −39.68 ounces is **not** flagged while −39.69 ounces is.

The second hop follows from the first: the owning run's `kegs_outstanding_count` falls by 1, since this keg is no longer out in the world. The third hop follows from the second: when that count reaches zero and the run's `kegs_filled_count` is at least 1, the run's `reconciliation_state` moves `OPEN → RECONCILED` and its `keg_shrinkage_oz` is written as the sum of `depletion_variance_oz` over every keg asset still linked to the run — including the kegs whose own variance sat comfortably inside tolerance — rounded half up to two decimal places. Both the keg's `version` and the run's `version` increment by 1. Note the interaction with washing: a keg's `poured_volume_oz` counts only the pours recorded since its **current** fill, so a keg that has been washed and refilled starts its variance arithmetic from zero, but the run-level roll-up is taken at reconciliation time while the links are still intact.

Finally, a `DECOMMISSION` movement is legal only from `EMPTY_DIRTY` and retires the keg permanently to `DECOMMISSIONED`, incrementing its `version` by 1. Nothing brings it back.

### 3.5. The Taproom Bar: Pours, Growlers and Crowlers

Every glass served across the bar is recorded as a **taproom pour** by a member of `TaproomStaff`. Pours are an append-only event log: as §2.4 notes, a pour carries only an `id` and a `created_at`, has no `updated_at` and no `version`, and is never modified or deleted once written. The payload names the `keg_asset_id` being drawn from, the `container_type`, and the `price_cents` charged, an integer of at least 0 — a zero-price staff sample is a legitimate pour and still counts for tax.

The `container_type` fixes the volume; clients never supply it. A `SAMPLE_4OZ` pour is 4 ounces, a `HALF_PINT_8OZ` is 8, a `PINT_16OZ` is 16, a `CROWLER_32OZ` is 32 and a `GROWLER_64OZ` is 64, and the chosen figure is stored as the pour's `volume_oz`. The server also stamps `poured_at_utc` from the current logical clock — the metered tax-determination instant — and `poured_by_user_id` from the acting `X-User-ID`.

Four conditions gate every pour regardless of container. The brewery's `notice_status` must be `ACTIVE`, or the pour is refused with `ERR_NOTICE_NOT_ACTIVE`. The cited keg's `state` must be exactly `TAPPED`; a keg that is merely `FILLED`, or has already been returned to `EMPTY_DIRTY`, or was deployed out of the building, cannot be poured from, and the attempt is refused with `ERR_KEG_NOT_TAPPED`. The beer in the keg must satisfy `taproom_sellable`, so an unapproved formula is refused with `ERR_FORMULA_NOT_APPROVED` — but a missing or revoked certificate of label approval is **never** an obstacle to a draft pour and `ERR_LABEL_NOT_APPROVED` is never raised here. And the pour must fit: the container's ounce figure may not exceed the keg's current `remaining_volume_oz`, so a 64-ounce growler cannot be pulled from a keg with 50 ounces left, and the attempt is refused with `ERR_POUR_EXCEEDS_KEG_VOLUME`. A successful pour raises the keg's `poured_volume_oz` by the poured ounces and lowers its `remaining_volume_oz` by the same amount, and the pour immediately joins the metered taxable base of any reporting period whose window contains its `poured_at_utc`.

Growlers and crowlers are pours too, but they are also **packaged beer handed to a consumer in a container the brewery did not sanitise itself**, which is why they carry a heavier evidentiary burden. Whenever `container_type` is `CROWLER_32OZ` or `GROWLER_64OZ`, five additional fields are required: `container_sanitized`, the boolean attestation that the vessel was sanitised before filling; `sanitizer_ppm` and `contact_time_seconds`, the measured reading; `attested_by_user_id`, the identifier of the second person who witnessed that reading; and `label_fields`, the label content that must accompany the sealed container. Conversely, when `container_type` is `SAMPLE_4OZ`, `HALF_PINT_8OZ` or `PINT_16OZ`, **none of those five fields may be supplied at all** — offering a `sanitizer_ppm` on a pint is a schema failure reported as `ERR_INVALID_REQUEST`, exactly as omitting it on a growler is.

The sanitation reading on a growler or crowler is judged by the same standard as a tank clean-in-place or a keg wash: the concentration must be at least 150 and at most 400 parts per million, both bounds inclusive, and the contact time must be at least 60 seconds. A passing reading persists the pour's `sanitation_verdict` as `PASS`. A failing reading aborts the request with `ERR_SANITATION_BELOW_STANDARD` and **no pour row is written at all**; the value `FAIL` is never persisted anywhere, so the only two values `sanitation_verdict` ever holds are `PASS` and — for the three draft container types, where the sanitation calculation does not run at all — `NOT_REQUIRED`, which is also its default.

Two further checks apply to sealed containers, and their **relative order is fixed**. The label check runs strictly **after** the sanitation check: `label_fields` must be present and must carry non-blank values for every one of `brand_name`, `abv_statement`, `net_contents`, `health_warning` and `fill_date`, and a missing or blank member is refused with `ERR_GROWLER_LABEL_INCOMPLETE`. Because sanitation is evaluated first, a fill that is both under-sanitised **and** unlabelled reports `ERR_SANITATION_BELOW_STANDARD`, never the label error. Separately, the attestation must be genuinely second-person: `attested_by_user_id` may not equal the acting `X-User-ID` recorded as `poured_by_user_id`, and a bartender attesting their own reading is refused with `ERR_SEGREGATION_OF_DUTIES`. Note the difference in shape between the label content on a beer and the label content on a growler: the beer-level filing requires `brand_name`, `abv_statement`, `net_contents` and `health_warning`, while the growler fill requires those four **plus** `fill_date`, because a consumer's container carries a freshness date the brand label does not.

### 3.6. State Licences, Wholesaler Appointments and the Franchise Trap

Self-distribution is a privilege granted state by state, and each grant is recorded as a **state licence** by a `ComplianceOfficer`. Registration takes the `state_code` the licence covers (exactly two uppercase letters, unique — one licence per state, and a second registration for the same state is refused with `ERR_DUPLICATE_CODE`), a `license_type` of either `SELF_DISTRIBUTION` or `WHOLESALER_ONLY`, an `annual_barrel_cap` giving the maximum barrels the brewery may self-distribute into that state per calendar year (at least 0, two decimal places), a `franchise_state` boolean that is true when the state grants statutory franchise protection to appointed wholesalers, and the validity window `effective_from_utc` (inclusive) and `expires_at_utc` (exclusive, and strictly after the start). An optional `termination_notice_days` gives the statutory notice period in days between a termination request and its effective instant; it **defaults to 90** when omitted and must be at least 0 and at most 365. A new licence opens with `status` of `ACTIVE` and a `carry_in_barrels_ytd` of 0.000.

Two figures on the licence are derived. `barrels_shipped_ytd` is `carry_in_barrels_ytd` plus the sum of `allocated_bbl` over every distribution order under this licence whose `state` is `SHIPPED` — orders that were rejected, cancelled or are merely allocated contribute nothing. `active_appointment_count` is the number of distributor appointments under this licence whose `state` is either `ACTIVE` or `TERMINATION_REQUESTED`; an appointment whose termination has been requested but not yet finalised still counts, because it is still live. As with the brewery, a `ComplianceOfficer` may seed history by supplying `carry_in_barrels_ytd`, the barrels already self-distributed into that state this calendar year; the call overwrites the field, re-derives `barrels_shipped_ytd`, moves the effective distance to `annual_barrel_cap`, and increments the licence's `version` by 1.

A licence's `status` takes three values — `ACTIVE`, `SUSPENDED` and `EXPIRED` — and **no client ever sets it directly**. `ACTIVE → SUSPENDED` happens as hop one of the notice cascade of §3.1, when the brewer's notice moves `ACTIVE → SUSPENDED` or `SUSPENDED → REVOKED`; suspension then cascades onward to that licence's `SUBMITTED` and `ALLOCATED` orders, which are rejected with `rejection_reason` `NOTICE_SUSPENDED`, and thence to the allocations those orders held. `SUSPENDED → ACTIVE` happens when the notice is reinstated, and only for a licence whose `expires_at_utc` is strictly later than the current logical clock. `ACTIVE → EXPIRED` is **lazy**: the system re-evaluates expiry on any request that reads the licence, and when the logical clock has reached or passed `expires_at_utc` the licence moves to `EXPIRED`, at which point every distribution order citing it whose `state` is `SUBMITTED` or `ALLOCATED` moves to `REJECTED` with `rejection_reason` `LICENSE_NOT_ACTIVE`, and each released allocation entry decrements the cited run's `allocated_bbl` while incrementing its `available_bbl`. Each of the three transitions increments the licence's `version` by 1, plus the `version` of every row the accompanying cascade touched. `EXPIRED` is terminal — a lapsed licence is never revived, only replaced.

Commercially, the licence exposes three separate failure modes and they must not be conflated. A licence whose `status` is `SUSPENDED` or `EXPIRED` refuses order submission, allocation and shipment with `ERR_LICENSE_NOT_ACTIVE`. A licence whose window has not opened — the logical clock is earlier than `effective_from_utc` — refuses order submission, allocation, shipment and appointment proposal with `ERR_LICENSE_NOT_YET_EFFECTIVE`. And a licence whose window has closed — the logical clock has reached or passed the exclusive `expires_at_utc`, so an instant exactly equal to `expires_at_utc` already counts as lapsed — refuses the same four operations with `ERR_LICENSE_EXPIRED`.

Appointing a wholesaler is the single most irreversible commercial decision in this domain, which is why it is split across two users. A `BreweryAdmin` **proposes** a **distributor appointment** by naming the `state_license_id` of the territory, the wholesaler's `distributor_name` (1 to 120 characters), and the `expected_state_license_version` demanded by §2.7. The proposal may optionally name an `appointed_beer_id`, and that single choice sets the appointment's derived `brand_scope`: when `appointed_beer_id` is present the scope is `SINGLE_BRAND` and covers only that brand, and when it is absent — null — the scope is `ALL_BRANDS` and covers every brand the brewery makes. A proposal may also carry `good_cause_code` at creation, though that field only becomes meaningful at termination. The new appointment opens in `state` `PROPOSED` with `proposed_by_user_id` recording the acting `X-User-ID`, a null `approved_by_user_id`, and null `activated_at_utc`, `termination_requested_at_utc`, `termination_effective_utc` and `terminated_at_utc`. Critically, **a proposal in `PROPOSED` does not yet bar self-distribution of anything** — it is a piece of paper, not a commitment.

Approval is where the trap closes, and only a `ComplianceOfficer` may spring it. The appointment must be in `PROPOSED`; the acting `X-User-ID` must differ from `proposed_by_user_id`, or the approval is refused with `ERR_SEGREGATION_OF_DUTIES`; the referenced licence's `status` must be `ACTIVE`; and no other appointment under the same `state_license_id` whose `state` is `ACTIVE` or `TERMINATION_REQUESTED` may have an overlapping brand scope, or the approval is refused with `ERR_DUPLICATE_APPOINTMENT_SCOPE`. Overlap is defined precisely: an `ALL_BRANDS` scope overlaps every other scope, including any `SINGLE_BRAND` scope; two `SINGLE_BRAND` scopes overlap only when their `appointed_beer_id` values are the same brand. On success the appointment moves `PROPOSED → ACTIVE`, `approved_by_user_id` records the approving `X-User-ID`, `activated_at_utc` is stamped from the logical clock, the licence's `active_appointment_count` rises by 1, and the licence's `state_code` joins the brewery's ascending `franchise_locked_state_codes` list. Approval also cascades: every distribution order whose `channel` is `SELF_DISTRIBUTED`, whose `state` is `SUBMITTED` or `ALLOCATED`, that cites the same `state_license_id`, and whose beer falls inside this appointment's scope, moves to `REJECTED` with `rejection_reason` `APPOINTMENT_ACTIVATED`; and each released allocation entry decrements the cited run's `allocated_bbl` while incrementing its `available_bbl` by that entry's barrel figure. The appointment's `version`, the licence's `version` and the `version` of every row the cascade touched each increment by 1.

Getting out of an appointment is a three-phase workflow, driven by a `ComplianceOfficer` supplying a `phase` of `REQUEST`, `WITHDRAW` or `FINALIZE`. A `REQUEST` is legal only from `ACTIVE` and moves the appointment to `TERMINATION_REQUESTED`. In a franchise state — the licence's `franchise_state` is true — the request must carry a `good_cause_code`, one of `NONPAYMENT`, `BREACH_OF_CONTRACT`, `LOSS_OF_LICENSE` or `VOLUNTARY_MUTUAL`; omitting it is refused with `ERR_GOOD_CAUSE_REQUIRED`. The request stamps `termination_requested_at_utc` from the logical clock and computes `termination_effective_utc`: in a franchise state it is the request instant advanced by the licence's `termination_notice_days` number of days, and in a non-franchise state it is simply equal to the request instant, so a non-franchise termination may be finalised immediately. Self-distribution of the appointed scope **stays barred** throughout `TERMINATION_REQUESTED` — requesting termination buys nothing until it completes.

A `WITHDRAW` is legal only from `TERMINATION_REQUESTED` and returns the appointment to `ACTIVE`, clearing `termination_requested_at_utc`, `termination_effective_utc` and `good_cause_code`. A `FINALIZE` is likewise legal only from `TERMINATION_REQUESTED` and moves the appointment to `TERMINATED`, but only once the logical clock has reached or passed `termination_effective_utc`; arriving early is refused with `ERR_TERMINATION_NOTICE_NOT_ELAPSED`. Finalisation stamps `terminated_at_utc`, decrements the licence's `active_appointment_count` by 1, removes the licence's `state_code` from the brewery's `franchise_locked_state_codes` unless another live appointment still holds that state, and restores the brewery's freedom to self-distribute the previously appointed scope. Every phase increments the appointment's `version` by 1, and finalisation additionally increments the licence's `version`. `TERMINATED` is terminal, and an approval attempted on an appointment that is not `PROPOSED`, or a termination phase the current state does not declare, is refused with `ERR_APPOINTMENT_TRANSITION_INVALID`.

### 3.7. Distribution Orders: Channel, Landed Cost, Allocation and Removal

A **distribution order** is the commercial instrument that moves packaged beer off the premises, and a `BreweryAdmin` owns its whole life. Submission names the `beer_id` of the brand being shipped, the `state_license_id` of the licence the shipment moves under, an `order_code` (1 to 24 characters, unique across all orders), the `bbl_requested` in barrels (strictly greater than zero, two decimal places), the destination `ship_to_state_code` (exactly two uppercase letters), a `distance_miles` one-way freight distance as a non-negative integer, and the `requested_ship_utc` instant at which removal is wanted. The order opens in `state` `SUBMITTED` with an empty `allocation_lines` list, an `allocated_bbl` of 0.000, and null `rejection_reason`, `cancel_reason` and `shipped_at_utc`.

Submission is the most heavily gated write in the system. The brewery's `notice_status` must be `ACTIVE`. The licence's `status` must be `ACTIVE` and the logical clock must sit inside its validity window, so a licence that has not yet opened or has already lapsed refuses the order. The beer's `distribution_sellable` must be true, which means both that its `registration_state` is `FORMULA_APPROVED` or `FORMULA_EXEMPT` and that its `label_state` is `COLA_APPROVED` — an unapproved formula reports `ERR_FORMULA_NOT_APPROVED` and a missing certificate reports `ERR_LABEL_NOT_APPROVED`. The territory rule applies without exception: `ship_to_state_code` must equal the referenced licence's `state_code`, and any mismatch is refused with `ERR_TERRITORY_NOT_LICENSED` — the brewery may not ship into Ohio on a Michigan licence, however convenient the truck route.

The order's `channel` is **derived, never supplied**. When a distributor appointment that is live — meaning its `state` is `ACTIVE` or `TERMINATION_REQUESTED`, since self-distribution stays barred right through the notice period — covers the pairing of this `state_license_id` and this `beer_id`, then `channel` becomes `WHOLESALER` and the order's `appointment_id` is stamped with that appointment. An appointment covers a beer when its `brand_scope` is `ALL_BRANDS`, or when its `brand_scope` is `SINGLE_BRAND` and its `appointed_beer_id` is this beer. Otherwise `channel` becomes `SELF_DISTRIBUTED` and `appointment_id` stays null. Note carefully that a live appointment does **not** reject the order — it reroutes it, and that rerouting is what pulls the wholesaler's statutory margin into the cost. The mirror-image case is the one that fails: a licence whose `license_type` is `WHOLESALER_ONLY` with **no** live appointment covering the beer cannot be shipped into at all, because the brewery holds no self-distribution privilege there and has no wholesaler to hand the beer to. That order is refused with `ERR_WHOLESALER_APPOINTMENT_REQUIRED`.

The full **landed cost** is computed at submission, before any state or ledger effect, and frozen onto the order. Its step order is pinned, each step consumes the rounded output of the step before it, and every rounding is half up to whole cents.

1. **Product value.** `product_cents` is `bbl_requested` multiplied by the referenced beer's `price_per_bbl_cents`, rounded to whole cents. The price is read at creation time; a later change to the beer's `price_per_bbl_cents` never restates a stored order.
2. **Raw freight.** Freight has two legs, each rounded to whole cents **independently** before they are added: a distance leg of the `distance_miles` multiplied by 30 cents per mile, and a volume leg of `bbl_requested` multiplied by 1,200 cents per barrel — twelve dollars a barrel. Their sum is the raw freight.
3. **Volume discount tier.** The freight discount percentage is chosen from the **rounded** `product_cents` of step 1, never from the un-rounded product. A `product_cents` of at least 400,000 cents (four thousand dollars) earns 30 percent; failing that, at least 200,000 cents earns 20 percent; failing that, at least 100,000 cents earns 10 percent; below that the discount is nothing. Tier selection is inclusive at each boundary: a product value of exactly 200,000 cents takes the 20 percent tier, while 199,999 cents takes the 10 percent tier.
4. **Discounted freight.** The discount amount is the raw freight multiplied by the chosen percentage, **rounded on its own** to whole cents, and `freight_cents` is the raw freight minus that rounded discount amount.
5. **Franchise fee.** On the `WHOLESALER` channel only, `franchise_fee_cents` is 3 percent of the subtotal — where the subtotal is `product_cents` plus the **discounted** `freight_cents` of step 4, not the raw freight — rounded to whole cents. On the `SELF_DISTRIBUTED` channel `franchise_fee_cents` is 0.
6. **Total.** `landed_cost_cents` is `product_cents` plus `freight_cents` plus `franchise_fee_cents`.

Applying the discount to un-rounded freight, or the franchise fee to an un-discounted subtotal, produces a different total. The order above is the only correct one.

Reserving inventory is a fork, not a simple transition, and it is the reason a single endpoint can answer 200 OK with a rejected order rather than an error body. Allocation is legal only from `SUBMITTED`, and requires the brewery's `notice_status` and the licence's `status` both to be `ACTIVE`. The **candidate pool** is assembled first: every packaging run whose `state` is `COMPLETED`, whose `destination` is `DISTRIBUTION`, whose `available_bbl` is strictly greater than zero, and whose owning batch produced the order's beer. Runs destined for the taproom are **never** drawn from, however much idle stock is sitting there; runs still in `PLANNED` hold no inventory yet; and runs in `VOIDED` have an `available_bbl` of 0.000. The pool is then sorted **oldest stock first**: by `removed_at_utc` ascending, with `created_at` ascending as the tie-break for two runs certified at the same logical instant. The row identifier is never consulted, and because a different order over the same pool produces different `allocation_lines`, the sort is directly observable.

If the summed `available_bbl` across the whole candidate pool is less than the order's `bbl_requested` — and the empty-pool case is the same branch as the merely-short case — the order takes the rejection fork: it moves `SUBMITTED → REJECTED` with `rejection_reason` set to `INSUFFICIENT_INVENTORY`, its `allocation_lines` stays an empty list and its `allocated_bbl` stays 0.000, **not one barrel is reserved and no packaging run is touched at all**, and only the order's own `version` increments by 1. This is the all-or-nothing rule, and the response is still a 200 OK carrying the rejected order.

When the pool can cover the request, the order takes the allocation fork and the waterfall draws down. Walking the sorted pool in order, each run contributes the smaller of its own `available_bbl` and the barrels still outstanding; that contribution is appended to `allocation_lines` as an entry naming the run's `packaging_run_id` and the `bbl` taken, rounded half up to three decimal places; the run's `allocated_bbl` rises by that amount so its `available_bbl` falls by the same amount; and the outstanding figure is reduced by the contribution, rounded half up to three decimal places. The walk stops as soon as nothing remains outstanding. The resulting `allocation_lines` is stored **in draw-down order**, the order's `allocated_bbl` is set to its `bbl_requested`, and the order moves `SUBMITTED → ALLOCATED`. The order's `version` and every cited run's `version` increment by 1.

Removal is the fiscal moment. Shipment is legal only from `ALLOCATED`; attempted from any other state it is refused with `ERR_ORDER_NOT_ALLOCATED`. It requires the brewery's `notice_status` and the licence's `status` to be `ACTIVE`, and on the `SELF_DISTRIBUTED` channel it enforces the annual ceiling: the licence's `barrels_shipped_ytd` plus this order's `allocated_bbl` must be **at most** the licence's `annual_barrel_cap`. The comparison is inclusive, so landing exactly on the cap is permitted and the very next barrel is not; a breach is refused with `ERR_SELF_DISTRIBUTION_CAP_EXCEEDED`. Orders on the `WHOLESALER` channel are not subject to the cap at all, because the barrels are the wholesaler's problem once handed over. On success the order moves `ALLOCATED → SHIPPED` and `shipped_at_utc` is stamped from the logical clock — the distribution tax-determination instant that decides which reporting period the barrels land in. Each cited run moves that line's barrels from `allocated_bbl` to `shipped_bbl`, leaving `available_bbl` **unchanged**, since those barrels were already spoken for. The licence's `barrels_shipped_ytd` rises by the order's `allocated_bbl`. The order's `version`, the licence's `version` and every cited run's `version` increment by 1.

Cancellation is declared from two states and requires a `reason` that is present and non-blank, stored as `cancel_reason`. From `SUBMITTED` there is nothing to unwind and no ledger figure moves. From `ALLOCATED` it is a full compensation: every entry of `allocation_lines` is released, so each cited run's `allocated_bbl` falls and its `available_bbl` rises by that entry's barrels, leaving the run's `bbl_removed` still equal to the sum of its `available_bbl`, `allocated_bbl` and `shipped_bbl`; the order's `allocation_lines` becomes an empty list and its `allocated_bbl` returns to 0.000. Either way the order moves to `CANCELLED`, and the order's `version` plus every cited run's `version` increment by 1.

`SHIPPED`, `REJECTED` and `CANCELLED` are all terminal: an allocation or cancellation attempted from any of them is refused with `ERR_ORDER_TRANSITION_INVALID`. Rejection can also arrive without any client asking, from four different cascades, and the `rejection_reason` records which one: `NOTICE_SUSPENDED` when the brewer's notice was suspended or revoked, `LICENSE_NOT_ACTIVE` when the governing licence was suspended or lazily expired, `LABEL_REVOKED` when the beer's certificate of label approval was revoked, `APPOINTMENT_ACTIVATED` when a wholesaler appointment closed over a self-distributed order's scope, and `INSUFFICIENT_INVENTORY` for the allocation fork above. A system rejection from `SUBMITTED` touches no run because nothing was reserved; a system rejection from `ALLOCATED` releases every allocation entry back to the cited runs, decrementing `allocated_bbl` and incrementing `available_bbl`, and increments the `version` of the order and of every cited run.

### 3.8. Excise Determination: Two Bases, Two Tiers, and Amendment

An **excise report** is the periodic return that tells the tax authorities how many barrels the brewery removed and what it owes. A `BreweryAdmin` prepares the draft, naming the `period_start_utc` (inclusive), the `period_end_utc` (exclusive, and strictly after the start), the `taproom_basis` the return uses, and optionally an `amends_report_id` pointing at the previously filed return this one supersedes — null for an original return. The draft opens in `state` `DRAFT` with `prepared_by_user_id` recording the acting `X-User-ID`, a null `filed_by_user_id` and a null `filed_at_utc`. Every barrel and tax figure is computed at draft time and recomputed at filing time, where it is frozen.

The most consequential input is `taproom_basis`, because the two permitted values determine tax on the same underlying reality in ways that genuinely disagree. Both variants read the **same** window: inclusive at `period_start_utc`, exclusive at `period_end_utc`.

Under a `taproom_basis` of `METERED_POUR`, the brewery is taxed only on what it actually served. `taproom_bbl` is the sum of `volume_oz` over every taproom pour whose `poured_at_utc` falls inside the window, regardless of `container_type` — a four-ounce sample counts for exactly its four ounces and a growler for its sixty-four — divided by the 3,968 fluid ounces in a barrel, rounded half up to three decimal places. Beer still sitting in a tapped keg, and beer lost to foam or line cleaning, is untaxed until somebody pours it. Because pours are append-only, no row ever leaves the set once written.

Under a `taproom_basis` of `WHOLE_KEG_REMOVAL`, tax is determined on the whole container at the moment it is tapped, and pours are ignored entirely. `taproom_bbl` is the sum of `size_bbl` over every keg asset whose `deployment_channel` is `TAPROOM`, whose `tapped_at_utc` is not null, and whose `tapped_at_utc` falls inside the window, rounded half up to three decimal places. Kegs deployed to distribution or to an event are excluded, and a keg tapped **before** `period_start_utc` is excluded even though it is still pouring inside the window. The divergence is not marginal: a half-barrel keg tapped inside the window from which three sixteen-ounce pints were pulled yields forty-eight ounces divided by 3,968, which is 0.012 barrels on the metered basis, against the keg's full 0.500 barrels on the whole-keg basis — a gap of 0.488 barrels on identical data.

The distribution half of the return needs no basis election. `distribution_bbl` is the sum of `allocated_bbl` over every distribution order whose `state` is `SHIPPED` and whose `shipped_at_utc` falls inside the same window, inclusive at the start and exclusive at the end, carried to three decimal places. `total_taxable_bbl` is `taproom_bbl` plus `distribution_bbl`.

The return's opening tier position is `ytd_bbl_before_period`: the brewery's `carry_in_taproom_bbl` plus its `carry_in_distribution_bbl`, plus the sum of `total_taxable_bbl` over every excise report whose `state` is `FILED` and whose `period_end_utc` is at or before this return's `period_start_utc`. Returns in `SUPERSEDED` never contribute, and neither do drafts — which has the deliberate consequence that an amending return sees exactly the same `ytd_bbl_before_period` its superseded original saw.

Taxes are then computed in two independent components, and **each component is rounded to whole cents on its own before anything is summed**, so the total is never the rounding of one exact product.

The **federal** component is tiered, modelling the reduced small-brewer rate that applies up to an annual limit. The period's total barrels, `total_bbl`, are `taproom_bbl` plus `distribution_bbl` rounded half up to three decimal places. The barrels that fall in the reduced tier are the smaller of `total_bbl` and the headroom left in the annual limit, where the headroom is 60,000 barrels minus `ytd_bbl_before_period` — and if that headroom is negative, the reduced-tier barrels are zero rather than a negative number, because the year's earlier barrels consume the reduced tier **before** this period's do. The remaining barrels, `total_bbl` minus the reduced-tier barrels rounded half up to three decimal places, fall in the standard tier. `federal_tax_cents` is then the reduced-tier barrels multiplied by 350 cents per barrel, rounded half up to whole cents, **plus** the standard-tier barrels multiplied by 1,600 cents per barrel, likewise rounded half up to whole cents on its own.

The **state** component splits by channel, because beer sold on premises attracts the higher rate. The raw state amount is `taproom_bbl` multiplied by 1,085 cents per barrel, rounded half up to whole cents, plus `distribution_bbl` multiplied by 870 cents per barrel, again rounded half up to whole cents independently. A small-brewer credit then applies conditionally: when `ytd_bbl_before_period` plus `total_bbl` is at most 15,000 barrels — the comparison inclusive — `state_tax_cents` is half the raw state amount, that is the raw amount multiplied by the complement of a fifty-percent credit, rounded half up to whole cents; when the sum exceeds 15,000 barrels the credit is lost entirely and `state_tax_cents` is the raw state amount unchanged. Finally, `total_tax_due_cents` is `federal_tax_cents` plus `state_tax_cents`.

Filing is a `ComplianceOfficer` act and is legal only from `DRAFT`; attempted on a return whose `state` is `FILED` or `SUPERSEDED` it is refused with `ERR_REPORT_TRANSITION_INVALID`. Four further conditions apply. The acting `X-User-ID` must differ from `prepared_by_user_id`, or the filing is refused with `ERR_SEGREGATION_OF_DUTIES`. The period must have closed: the logical clock must have reached or passed `period_end_utc`, and an early filing is refused with `ERR_PERIOD_NOT_CLOSED`. When `amends_report_id` is null, no other return in `FILED` may already cover the same pairing of `period_start_utc` and `period_end_utc`, and a duplicate is refused with `ERR_PERIOD_ALREADY_FILED`. When `amends_report_id` is non-null, the target return's `state` must be `FILED`; a target sitting in `DRAFT` or already in `SUPERSEDED` is refused with `ERR_AMENDMENT_TARGET_NOT_FILED`.

On success the return moves `DRAFT → FILED`. Every barrel and tax field — `taproom_bbl`, `distribution_bbl`, `total_taxable_bbl`, `ytd_bbl_before_period`, `federal_tax_cents`, `state_tax_cents` and `total_tax_due_cents` — is recomputed **at filing time** from the data as it then stands and frozen at those values. `filed_by_user_id` records the filing `X-User-ID` and `filed_at_utc` is stamped from the logical clock. The brewery's `taproom_bbl_ytd` and `distribution_bbl_ytd` absorb this return's barrels. And when the return amends another, that target moves `FILED → SUPERSEDED` in the same request, its barrels and taxes stop counting toward the brewery's year-to-date aggregates, and its own `version` increments by 1 alongside the amending return's. `SUPERSEDED` is terminal.

### 3.9. Off-Site Events, Festivals and Farmers' Markets

Pouring beer away from the licensed premises needs its own authorisation, and an **event permit** is the application for it. A `ComplianceOfficer` drafts one naming the `featured_beer_id` of the brand to be poured, the public `event_name` (1 to 120 characters), the `permit_type` — one of `FESTIVAL`, `OFF_SITE_TASTING` or `FARMERS_MARKET` — the `venue_state_code` of the venue's state (exactly two uppercase letters), the event window `event_start_utc` and `event_end_utc` (both inclusive, with the end strictly after the start), and the `requested_bbl` the brewery intends to pour there (strictly greater than zero, two decimal places). The venue's state must be licensed at all: if no state licence exists for that `venue_state_code`, the draft is refused with `ERR_TERRITORY_NOT_LICENSED`. A new permit opens in `state` `DRAFT` with a `submission_count` of 0, a null `info_request_note`, a null `denial_reason` and a null `decided_at_utc`.

Submission is declared from two states, `DRAFT` and `INFO_REQUESTED`, and both lead to `SUBMITTED`. It requires the brewery's `notice_status` to be `ACTIVE` and the featured beer's `taproom_sellable` to be true — a festival pour is a taproom-style pour and needs no certificate of label approval. Every submission increments `submission_count` by 1 and clears any `info_request_note`, so the counter records how many times the regulator has been asked, including re-submissions after an information request. Submission also enforces an **aggregate annual ceiling per state** that no single permit can breach on its own: the sum of `requested_bbl` over every event permit in the same `venue_state_code` whose `state` is `SUBMITTED` or `APPROVED`, **plus** this permit's own `requested_bbl`, must be at most 25.00 barrels. Ten permits of three barrels each are individually unremarkable and collectively over the line; the eventual breach is refused with `ERR_EVENT_BARREL_CAP_EXCEEDED`. Each submission increments the permit's `version` by 1.

Only a `StateRegulator` answers, supplying a `decision` and, for two of the three outcomes, a `note`. A `decision` of `INFO_REQUESTED` is legal only from `SUBMITTED`, moves the permit to `INFO_REQUESTED`, and requires a `note` that is present and non-blank, stored as `info_request_note`; the permit is then re-openable by another submission, which is what makes this the system's only true application loop. A `decision` of `DENIED` is likewise legal only from `SUBMITTED`, requires a present and non-blank `note` stored as `denial_reason`, stamps `decided_at_utc` from the logical clock, and moves the permit to `DENIED`. A `decision` of `APPROVED` is legal only from `SUBMITTED`, stamps `decided_at_utc`, and moves the permit to `APPROVED`. Every decision increments the permit's `version` by 1, and a submission or decision from a state that does not declare it — including anything at all from the terminal `APPROVED` or `DENIED` — is refused with `ERR_PERMIT_TRANSITION_INVALID`.

Approval carries a concurrency ceiling of its own, and it is where this domain's interval arithmetic differs deliberately from the cellar's. The regulator will not have more than **two** approved off-site events running at once in the same state. Concretely, count the permits already in `APPROVED` whose `venue_state_code` matches this one and whose event window intersects this permit's window, treating both windows as **closed intervals** — inclusive at `event_start_utc` and inclusive at `event_end_utc`. If that count has already reached two, the approval is refused with `ERR_OFFSITE_EVENT_CAPACITY_EXCEEDED`; approval proceeds only while the count is strictly below two. Because these intervals are closed, two events that merely touch at an endpoint — one ending at the exact instant the other begins — **do** intersect and do count against each other. That is the opposite of the half-open tank occupation intervals of §3.2, where touching intervals do not conflict, and the difference is intentional.

Once a permit reaches `APPROVED`, it unlocks exactly one downstream capability: filled kegs of the featured beer may be moved out of the cellar on the event channel, as §3.4 describes, with the movement naming that permit's identifier as its `event_permit_id`. A deployment to an event with no approved permit covering the beer at the current logical instant is refused with `ERR_EVENT_PERMIT_NOT_APPROVED`.

## 5. Error Code Catalogue

Every failure the API can produce is one of the sixty-four identifiers below, returned in the `error_id` field of the error envelope described in §2.2 with the HTTP status shown. When a single request violates more than one rule, the identifier returned is the one belonging to the earliest rung of the rejection ladder in §2.8, and evaluation stops there.

| Error ID | HTTP Status Code |
