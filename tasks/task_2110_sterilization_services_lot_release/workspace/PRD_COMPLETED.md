# Sterilization Services & Lot Release API — Product Requirements Document

## 1. Introduction

Contract sterilization is a business whose deliverable is evidence. A medical-device manufacturer ships pallets of finished goods to a service provider; the provider exposes them to ethylene oxide, gamma radiation or an electron beam; and what the manufacturer receives back is not merely treated product but a defensible assertion — supported by a validated cycle recipe, dosimeter readings, biological indicators, residual-gas assays and a current dose qualification — that the goods meet their sterility assurance level and may be distributed. This document specifies the API for the plant record system that assembles that assertion. It governs reference data (customer accounts, product families, air permits, chambers and recipes), the physical workflow (scheduling a cycle, building a load map, placing indicators, running the dwell, reading out dosimetry, degassing ethylene-oxide loads), and the quality decisions that terminate a lot's life in the facility (release, rejection, scrapping, recall and re-sterilization).

Four groups of people share this record, and they deliberately do not trust one another's signatures. The regulatory administrator owns reference data and the audit calendar. The plant-floor operator builds load maps and drives chambers. The metrology analyst reads indicators and closes dosimetry review. The quality release officer, and only the quality release officer, converts a quarantined lot into a released lot — and may not be the same person who ran the cycle or closed its dosimetry. Superimposed on this human choreography are two hard capacity ceilings that the plant cannot exceed: a chamber can hold only so many pallets and can only be occupied by one cycle at a time, and an annual air permit caps both the post-abatement ethylene-oxide mass the site may emit and the number of ethylene-oxide dwells that may overlap under that permit.

The API is mounted under `/sterilization`. Every arithmetic rule in it is deterministic and pinned: rounding happens at a stated step and nowhere else, thresholds are inclusive or exclusive by explicit statement, and evaluation order is fixed wherever two rules could both fire. Every deadline is measured against a server-side logical clock rather than wall time, so that aeration windows and audit intervals are reproducible. Where a single operation touches more than one record — and in this domain it usually does — the full cascade is specified, because a lot's disposition is only as trustworthy as the weakest propagation rule behind it.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contract: authentication, response shape, pagination, audit fields, arithmetic precision, concurrency control, the order in which a request is screened, and the consistency guarantees that hold across the batch record.

### 2.1. Operator Identity and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. Five roles exist, spelled exactly as follows: `RegulatoryAdmin`, `CustomerRep`, `CycleOperator`, `DosimetryAnalyst` and `QualityReleaseOfficer`. If either header is absent, or if `X-User-Role` is not one of those five strings, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well formed but the role is not among those authorised for the requested operation — the authorised roles for every operation are listed in the endpoint table of §4 — the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

When `X-User-Role` is `CustomerRep`, `X-User-ID` is the `id` of the acting `Customer`; ownership checks on any resource that references a `Customer` compare the resource's `customer_id` to `X-User-ID`. Six operations are scoped this way: reading a customer, listing that customer's products, reading a product, creating a lot, reading a lot, and reporting an adverse event against a lot. In each of them, a `CustomerRep` whose `X-User-ID` differs from the `customer_id` of the addressed customer, of the product's owning customer, or of the lot's owning customer is rejected with `ERR_CUSTOMER_SCOPE_VIOLATION` (HTTP 403).

When `X-User-Role` is `RegulatoryAdmin`, `CycleOperator`, `DosimetryAnalyst` or `QualityReleaseOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands attribution — as `operator_user_id` on a `Cycle` when a `CycleOperator` starts it, as `dosimetry_closed_by_user_id` on a `Cycle` when a `DosimetryAnalyst` closes its dosimetry, as `read_by_user_id` on an `Indicator` when a reading is taken, as `released_by_user_id` on a `Lot` when a `QualityReleaseOfficer` releases it, and as `reported_by_user_id` on an `AdverseEvent` — but it never compares that value to any entity's `id`. All four opaque roles draw from the same identifier space, which is what makes the segregation-of-duties comparison in §2.10 meaningful.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints; `total_count` counts every row matching the filters before the page window is applied, and `has_more` is true exactly when `offset` plus the number of rows in this page is still less than `total_count`.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection endpoints are paginated through two query parameters. `limit` sets the maximum number of rows returned; it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` sets how many rows are skipped before the page begins and defaults to 0. Both are screened as payload schema at step 3 of the order in §2.7 — ahead of any path identifier — so a non-integer value, a `limit` outside 1 to 100 or a negative `offset` is refused with `ERR_VALIDATION` even when the collection's own path segment names a resource that does not exist. Unless a specific endpoint states otherwise, every list is sorted by `created_at` in ascending order, so that a plant record reads chronologically; because the logical clock stands still between administrative moves, many rows share an instant, and rows carrying the same `created_at` are ordered by the sequence in which the server persisted them, earliest first. That same instant-then-insertion-sequence order is what every "ascending `created_at` order" instruction elsewhere in this document means. The `meta` object of every list response carries `limit`, `offset`, `total_count` and `has_more`.

Several collections also accept domain filters alongside `limit` and `offset`. The customer list accepts `status`. The customer-scoped product list, the permit-scoped chamber list, the audit history of a qualification, the aeration records of a lot, the adverse events of a lot and the indicators of a load-map slot accept pagination only. The qualification list accepts `product_id`, `recipe_id` and `status`. The lot list accepts `customer_id`, `product_id`, `parent_lot_id`, `status` and `residual_status`, the last of which filters on the lot's second, independent state dimension. The cycle list accepts `chamber_id`, `recipe_id` and `status`. The load-position list accepts `cycle_id` and `lot_id`. Every one of these filters is matched as an exact string against the stored field and is not itself validated against the enumeration it draws from, so a filter value that is not a recognised member is accepted and simply selects no rows.

### 2.4. Record Identity, the Audit Trail, and the Facility Clock

Every resource the API mints carries an `id`: a server-generated UUID with no type prefix and no client control over its value. Alongside it, every resource carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was persisted. All resources except one also carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every persisted change to the row, and `version`, an integer that begins at 1 when the row is created and increases by exactly one on every persisted mutation of that row. The single exception is the `DoseAudit`: a dose audit is an immutable laboratory record, so it carries only `id` and `created_at` — it has no `updated_at` field and no `version` field at all.

A mutation for these purposes includes changes the client did not directly request. When a load-position write recomputes `load_density_g_per_cm3` on its cycle, when a cycle start debits `consumed_kg_ytd` on a permit, or when a cascade clears `schedulable` on a lot the caller never named, each affected row has its `updated_at` refreshed and its `version` incremented in its own right.

Time in this system is logical, not wall-clock. The server holds a single logical clock whose startup value is exactly `2026-08-01T00:00:00Z`; before any client sets it, every read of "now" returns that instant, and the server never falls back to real time. A `RegulatoryAdmin` may move the clock through an administrative test-driving capability that accepts a single field, `to_iso8601`, carrying the instant the clock should read from that point on; the call answers `200 OK` with an empty `data` object rather than returning any resource, and the clock may be moved backwards as freely as forwards. Every timestamp the server stamps and every deadline comparison it makes — aeration target ends, audit due dates, release instants, indicator read instants — reads this clock.

### 2.5. Precision in Dose, Density, Mass, Time and Money

Numbers in this domain are not interchangeable, and each family has its own precision rule. All rounding, wherever it appears below, is **round half up**, and it is applied exactly at the step named and at no other step.

- **Load density** is carried to 4 decimal places in grams per cubic centimetre. A single rounding step is applied to the final quotient; the mass and volume accumulations that feed it are never rounded.
- **Absorbed dose** — `delivered_dose_kgy`, `max_observed_dose_kgy`, `cumulative_dose_kgy` and `release_dose_kgy` — is carried to 2 decimal places in kilogray. Conformance comparisons are made against the already-rounded 2-decimal values, not against unrounded intermediates.
- **Ethylene-oxide mass** — `abated_eto_kg` on a cycle and `consumed_kg_ytd` on a permit — is carried to 3 decimal places in kilograms.
- **Money** — `emission_fee_usd` on a cycle and `total_emission_fee_usd` on a permit — is carried to 2 decimal places in US dollars.
- **Aeration duration** is a whole number of hours. The ceiling function is applied once, to the complete product of base hours and all applicable multipliers, never to intermediate factors.
- **Residual concentrations** in parts per million are compared exactly as supplied; no rounding is applied to `eto_residual_ppm` or `ech_residual_ppm` before comparison against the product's limits.
- **Instants** used in scheduling overlap tests are compared to the second. The `created_at` ordering used to rank a lot's load positions is compared at millisecond resolution — three fractional digits.
- **Audit intervals** are computed in whole days added to the UTC instant of `performed_at`.

All numeric values are returned in JSON as numbers, not strings.

### 2.6. Load-Map and Lot-File Concurrency Control

Two write operations in this system are legitimate to repeat — a second load position on the same cycle and a second adverse event on the same lot would each succeed on their own merits — and therefore cannot be protected by any state precondition. Both are protected instead by an optimistic stale-version check against the parent record.

Creating a load position on a cycle — the write served by `POST /sterilization/cycles/{id}/load-positions` — requires `expected_cycle_version` in the request body. The field is not optional; it carries the `version` of the parent `Cycle` as the client last observed it. If that value does not equal the cycle's current `version`, the request is rejected with `ERR_STALE_CYCLE_VERSION` (HTTP 412), because a client working from an earlier read is reasoning about a load map and a `load_density_g_per_cm3` that no longer exist. The cycle's `version` advances on every load-map write, on the readiness sign-off, and on every cascade-driven position removal, so any of those events invalidates a client's cached handle. Each `LoadPosition` records `cycle_version_after`, a snapshot of the parent cycle's `version` immediately after that position was persisted; it is the handle a client uses for the next load-map write.

Reporting an adverse event against a lot — the write served by `POST /sterilization/lots/{id}/adverse-events` — requires `expected_lot_version` in the request body, again not optional, carrying the `version` of the parent `Lot` as the client last observed it. A mismatch with the lot's current `version` is rejected with `ERR_STALE_LOT_VERSION` (HTTP 412), which tells the reporter that the lot's disposition, `quarantine_reason` or residual posture moved underneath their read. Each `AdverseEvent` records `lot_version_after`, a snapshot of the subject lot's `version` immediately after the event was persisted, and creating the event itself increments the lot's `version` by one.

No other endpoint in this API accepts a version field, and no other endpoint performs a stale-version check.

### 2.7. Order of Screening: How a Request Is Rejected

Requests are screened in a strictly ascending order of checks, and the **first** check that fails determines the error returned. This ordering is part of the contract: a request that violates three rules must surface the earliest one. The order is as follows.

1. **Authentication.** Both headers present and `X-User-Role` one of the five declared roles, otherwise `ERR_UNAUTHENTICATED`.
2. **Role authorisation.** The caller's role appears in the operation's authorised list, otherwise `ERR_FORBIDDEN_ROLE`.
3. **Payload schema.** On every write, required fields are present, types are correct, enum members are recognised and numeric ranges hold — `pallet_count` at least 1, `positives` between 0 and `samples_tested` inclusive, `samples_tested` exactly 100, `abatement_efficiency_pct` between 0 and 100 inclusive, `scheduled_end_at` strictly later than `scheduled_start_at`, `position_index` at least 1 and no greater than the `pallet_capacity` of the chamber behind the cycle named in the path, `eto_residual_ppm` and `ech_residual_ppm` both zero or greater, and on an indicator reading exactly one of `measured_dose_kgy` or `bi_result` supplied and matching the indicator's `indicator_type`, with `spore_population` required for a `BIOLOGICAL` indicator and forbidden for a `DOSIMETER`. Violations yield `ERR_VALIDATION` (HTTP 400). Three of these checks — the `position_index` ceiling, the indicator reading's type match and the `MIN_DOSE` placement rule of §3.5 — need a record the URL names in order to be evaluated at all. Each of them consults that record without resolving it: if the identifier matches nothing the check is simply skipped, so the request falls through to step 4 and is answered with that resource's own 404 rather than with `ERR_VALIDATION`.
4. **Path identifiers.** Every identifier in the URL is resolved left to right, and each resource type raises its own 404: `ERR_CUSTOMER_NOT_FOUND` for a customer segment, `ERR_PRODUCT_NOT_FOUND` for a product, `ERR_PERMIT_NOT_FOUND` for an emission permit, `ERR_CHAMBER_NOT_FOUND` for a chamber, `ERR_RECIPE_NOT_FOUND` for a cycle recipe, `ERR_QUALIFICATION_NOT_FOUND` for a qualification, `ERR_LOT_NOT_FOUND` for a lot, `ERR_CYCLE_NOT_FOUND` for a cycle, `ERR_LOAD_POSITION_NOT_FOUND` for a load position, `ERR_INDICATOR_NOT_FOUND` for an indicator, `ERR_AERATION_RECORD_NOT_FOUND` for an aeration record and `ERR_ADVERSE_EVENT_NOT_FOUND` for an adverse event. On a nested path the outer segment is resolved before the inner one: deleting a load-map slot resolves the cycle first and only then the `position_id` segment, and a slot that exists but belongs to a different cycle than the one named in the path is itself reported as `ERR_LOAD_POSITION_NOT_FOUND`.
5. **Body foreign keys.** Every foreign key supplied in a request body must resolve, each raising its own 404: `customer_id` raises `ERR_CUSTOMER_NOT_FOUND`, `product_id` raises `ERR_PRODUCT_NOT_FOUND`, `permit_id` raises `ERR_PERMIT_NOT_FOUND`, `recipe_id` raises `ERR_RECIPE_NOT_FOUND`, `chamber_id` raises `ERR_CHAMBER_NOT_FOUND` and `lot_id` raises `ERR_LOT_NOT_FOUND`. This applies when creating a product, a permit, a chamber, a qualification, a lot, a cycle or a load position. Where one body carries two unresolvable keys, they are resolved in exactly the order just listed, so a cycle created against a missing recipe and a missing chamber reports `ERR_RECIPE_NOT_FOUND`, and a lot created against a missing customer and a missing product reports `ERR_CUSTOMER_NOT_FOUND`.
6. **Code uniqueness.** `account_code`, `permit_code`, `chamber_code`, `recipe_code`, `cycle_code` and `serial_code` are unique across the whole facility; `product_code` and `lot_code` are unique within their owning `customer_id`. A collision yields `ERR_DUPLICATE_CODE` (HTTP 409) and is checked when creating a customer, a product, an emission permit, a chamber, a cycle recipe, a lot, a cycle or an indicator.
7. **Customer scoping.** The `CustomerRep` ownership rule of §2.1, yielding `ERR_CUSTOMER_SCOPE_VIOLATION`.
8. **Declared transition.** The target resource is in a state from which the requested transition exists. Specific states raise specific errors: starting a cycle that is not `READY` yields `ERR_CYCLE_NOT_READY`; recording a residual test against an aeration record already in `PASSED` or `EXHAUSTED` yields `ERR_RETEST_LIMIT_EXHAUSTED`; recording a reading against an already-`READ` indicator whose cycle is not in `DOSE_DEVIATION` yields `ERR_INDICATOR_ALREADY_READ`; attempting release on a lot that is not in `QUARANTINE`, or whose `residual_status` is `RESIDUAL_FAIL`, or that has no governing cycle, yields `ERR_LOT_NOT_RELEASABLE`. Everything else yields `ERR_INVALID_STATE` (HTTP 409). One deliberate exception exists at this step: the readiness sign-off admits both `PLANNED` and `LOADING` here, so that the empty-load-map check further down the order stays reachable.
9. **Recipe approval.** A cycle may only be scheduled against a recipe whose `status` is `APPROVED`, otherwise `ERR_RECIPE_NOT_APPROVED` (HTTP 409).
10. **Lot schedulability.** A load position may only be created for a lot whose `schedulable` flag is true, otherwise `ERR_LOT_NOT_SCHEDULABLE` (HTTP 409).
11. **Stale parent version.** The optimistic checks of §2.6 — `expected_cycle_version` against the cycle's `version` yielding `ERR_STALE_CYCLE_VERSION`, and `expected_lot_version` against the lot's `version` yielding `ERR_STALE_LOT_VERSION`.
12. **Biological indicator positivity.** On release, no `BIOLOGICAL` indicator on the governing cycle may have `bi_result` equal to `POSITIVE`, otherwise `ERR_BI_POSITIVE_BLOCKS_RELEASE` (HTTP 409).
13. **Cycle conformance.** On release, the governing cycle's `status` must be `DOSE_CONFORMING`, otherwise `ERR_CYCLE_DEVIATION_BLOCKS_RELEASE` (HTTP 409).
14. **Current qualification.** A `ProductQualification` for the product-and-recipe pair must exist with `status` either `QUALIFIED` or `CONDITIONAL`, otherwise `ERR_QUALIFICATION_NOT_CURRENT` (HTTP 409). This check guards both load-position creation and release. A qualification whose `next_audit_due_at` has been reached is first moved lazily to `AUDIT_DUE` and therefore fails here.
15. **Chamber availability.** A chamber must have `status` `AVAILABLE` to start a cycle, and must not be `DECOMMISSIONED` to have a cycle scheduled in it; otherwise `ERR_CHAMBER_UNAVAILABLE` (HTTP 409).
16. **Permit standing.** The `EmissionPermit` backing the chamber must have `status` `ACTIVE` at cycle start, otherwise `ERR_PERMIT_NOT_ACTIVE` (HTTP 409).
17. **Segregation of duties.** The release rule of §2.10, yielding `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).
18. **Modality coherence.** A recipe's `modality` must equal the chamber's `modality` when a cycle is scheduled, and the chamber's `modality` must be a member of the lot owner's `contracted_modalities` when a load position is created; otherwise `ERR_MODALITY_MISMATCH` (HTTP 422).
19. **Chamber occupancy.** The buffer-extended occupancy interval of a newly scheduled cycle must not intersect that of any non-terminal cycle in the same chamber, otherwise `ERR_CHAMBER_WINDOW_CONFLICT` (HTTP 409).
20. **Permit concurrency.** The number of overlapping non-terminal ethylene-oxide dwells under the same permit must remain below the permit's cap, otherwise `ERR_PERMIT_CONCURRENCY_EXCEEDED` (HTTP 409).
21. **Residual timing.** A residual test may not be recorded before the logical clock reaches the aeration record's `target_end_at`, and a lot may not be released while its `residual_status` is `PENDING_AERATION` or `AERATING`; either violation yields `ERR_AERATION_INCOMPLETE` (HTTP 409).
22. **Aeration applicability.** An aeration record may only be opened for a lot whose `residual_status` is `PENDING_AERATION`; every other value of that field — `NOT_APPLICABLE`, because the lot has no degassing obligation at all, and equally `AERATING`, `RESIDUAL_PASS` and `RESIDUAL_FAIL`, because the obligation is already open or already settled — yields `ERR_AERATION_NOT_APPLICABLE` (HTTP 422) rather than `ERR_INVALID_STATE`.
23. **Non-empty load map.** The readiness sign-off requires at least one load position on the cycle, otherwise `ERR_LOAD_MAP_EMPTY` (HTTP 422).
24. **Indicator placement.** The readiness sign-off requires the cycle's indicator counts to meet the recipe's minima, otherwise `ERR_INDICATOR_PLACEMENT_INCOMPLETE` (HTTP 422).
25. **Density band.** The readiness sign-off requires the cycle's `load_density_g_per_cm3` to fall inside the recipe's validated band, otherwise `ERR_LOAD_DENSITY_OUT_OF_BAND` (HTTP 422).
26. **Capacity.** A load position may not push the cycle's `loaded_pallet_count` past the chamber's `pallet_capacity`, and its `pallet_count` may not exceed the lot's `available_pallet_count`; either violation yields `ERR_CHAMBER_CAPACITY_EXCEEDED` (HTTP 422).
27. **Slot uniqueness.** No other load position on the same cycle may already occupy the requested `position_index`, otherwise `ERR_DUPLICATE_POSITION_INDEX` (HTTP 409).
28. **Parametric eligibility.** A `PARAMETRIC` release requires the governing recipe's `required_biological_indicators` to be 0, otherwise `ERR_PARAMETRIC_NOT_PERMITTED` (HTTP 422).
29. **Incubation completeness.** A `DOSIMETRIC` release requires every `BIOLOGICAL` indicator on the governing cycle to have `reading_status` equal to `READ`, otherwise `ERR_BI_INCUBATION_PENDING` (HTTP 409).
30. **Cumulative dose headroom.** A load position requires the lot's `cumulative_dose_kgy` plus the recipe's `target_dose_kgy`, rounded half up to 2 decimal places, to be no greater than the product's `max_cumulative_dose_kgy`; otherwise `ERR_CUMULATIVE_DOSE_EXCEEDED` (HTTP 422).
31. **Dosimetry completeness.** Closing dosimetry requires every indicator on the cycle to have `reading_status` equal to `READ` and the variant-selected dosimeter subset to be non-empty, otherwise `ERR_DOSIMETRY_INCOMPLETE` (HTTP 422).
32. **Permit allowance.** Starting an ethylene-oxide cycle whose charge would push the permit's consumption strictly past its `annual_allowance_kg` is rejected with `ERR_PERMIT_ALLOWANCE_EXCEEDED` (HTTP 402); landing exactly on the allowance is accepted.
33. **Customer standing.** The lot's owning customer must have `status` `ACTIVE` both when a lot is received and when it is released, otherwise `ERR_CUSTOMER_SUSPENDED` (HTTP 402).

### 2.8. Batch-Record Consistency and Cascading Reversal

The batch record is hierarchical — a permit owns chambers, a chamber owns cycles, a cycle owns load positions, a load position owns indicators, a lot owns aeration records and adverse events — and consistency across that hierarchy is maintained by the server, not by the client. Removing a load-map slot is never a single-row operation: the parent cycle's `loaded_pallet_count` and `load_density_g_per_cm3` are recomputed, the referenced lot's `staged_pallet_count` and `available_pallet_count` are corrected, and the parent cycle may itself be walked backwards from `READY` to `LOADING`, or from `LOADING` to `PLANNED`, because the criteria that justified its previous state no longer hold. Aborting a cycle removes every one of its slots in ascending `created_at` order and applies each of those corrections in turn.

Two cascades in this system run deeper than one hop, and each hop is caused by the hop before it rather than by the original request. A dosimetry close that finds a deviation triggers a four-hop cascade that reaches from the cycle through its lots to their qualifications and finally back to unrelated cycles that happen to be holding lots of the same product; that cascade is specified in §3.6. A re-sterilization disposition triggers a three-hop cascade that recalls a released lot, mints a successor lot, and re-evaluates the product's qualifications against the successor's inherited dose burden; that cascade is specified in §3.9. Every row touched at any hop of either cascade has its `updated_at` refreshed and its `version` incremented in its own right.

### 2.9. Conserved Quantities

Two quantities in this system are conserved, meaning that every forward action has an exact compensating action and no drift may accumulate across a forward/compensating pair.

The first is the discrete pallet count. For every lot, `staged_pallet_count` plus `available_pallet_count` always equals `total_pallet_count`, and `staged_pallet_count` always equals the sum of `pallet_count` over every load position that references that lot. For every cycle, `loaded_pallet_count` always equals the sum of `pallet_count` over every load position on that cycle. Creating a load position is the forward action and deleting one is the compensating action, but both equalities must also hold after cascade-driven removals and after the bulk removals performed by an abort. `available_pallet_count` must never be negative.

The second is post-abatement ethylene-oxide mass. For every permit, `consumed_kg_ytd` always equals the sum of `abated_eto_kg` over every cycle in a chamber under that permit whose `status` is not `CANCELLED`, rounded half up to 3 decimal places; and `total_emission_fee_usd` always equals the sum of `emission_fee_usd` over that same cycle set, rounded half up to 2 decimal places. Starting a cycle is the forward action and aborting a running cycle is the compensating action. The abort credits back exactly the values stored on the cycle rather than recomputing them, so that a start-and-abort pair leaves the permit ledger bit-for-bit where it began even if the fee tier boundary would have been crossed differently in the meantime.

### 2.10. Segregation of Duties in Release Decisions

A lot is released by a `QualityReleaseOfficer`, and the officer's `X-User-ID` must differ from both `operator_user_id` and `dosimetry_closed_by_user_id` on the lot's governing cycle. Because all four opaque roles draw identifiers from one space, the same human acting first as `CycleOperator` and later as `QualityReleaseOfficer` is detectable and is refused: the release is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The rule is symmetric — matching either stamped identity is disqualifying — and it applies to no operation other than release.

## 3. Business Logic & Workflows

The subsections below follow the physical path of goods through the facility: reference data is established first, then capacity is commissioned, then recipes are validated and products are qualified against them, then lots arrive, are loaded, irradiated or gassed, measured, degassed, and finally released or dispositioned.

### 3.1. Accounts, Product Families, and Contracted Modalities

Everything in the plant record hangs off a **Customer** — the device manufacturer contracting for sterilization services. A `RegulatoryAdmin` registers one with a legal `name`, a short `account_code` of between 1 and 32 characters that must be unique across all customers as an exact, case-sensitive string, and a `contracted_modalities` list. That list must be non-empty, may contain no duplicates, and each member must be one of `ETO`, `GAMMA` or `EBEAM`; it is the commercial fence that decides which chambers may ever hold this customer's goods. A customer also carries a `status`, supplied optionally at registration and defaulting to `ACTIVE`, whose only other value is `SUSPENDED`. The administrator may move an account between those two values at any time — and may equally re-assert the value the account already holds, which is accepted rather than refused and, because no field on the row changes, advances neither `updated_at` nor `version` — and a `SUSPENDED` account may neither receive new lots into the facility nor have any of its lots released — both attempts are refused with `ERR_CUSTOMER_SUSPENDED`.

Each customer record also exposes `open_lot_count`, a server-maintained integer that starts at 0 and reflects how many of that customer's lots are still live in the facility: it counts the lots whose `status` is none of `RELEASED`, `REJECTED`, `SCRAPPED` or `RECALLED`. It is recomputed whenever any of that customer's lots changes `status`, rising by one when a lot is received and falling by one when a lot is released, rejected on residual grounds, or scrapped out of quarantine. The recomputation is always a fresh count over that customer's lots rather than an increment applied to the stored figure, and it refreshes the customer's `updated_at` and advances its `version` only when the freshly counted value actually differs from the one already stored — a lot movement that leaves the open set unchanged therefore leaves the customer row untouched.

Under a customer sit **Products** — families of finished goods that behave identically under sterilization. A product is registered with its owning `customer_id`, a `product_code` of 1 to 32 characters that must be unique within that customer, and the physical and toxicological constants that drive the rest of the system. `pallet_mass_kg` is the mass of one shipping pallet of the product in kilograms and must be greater than zero; `pallet_volume_m3` is the displaced volume of that pallet in cubic metres and must likewise be greater than zero. These two feed the aggregate load-density computation described in §3.4. `max_allowed_dose_kgy` is the per-cycle absorbed dose ceiling the product tolerates, in kilogray, and must be greater than zero; `max_cumulative_dose_kgy` is the lifetime ceiling across every sterilization pass one physical lot may ever receive, also greater than zero. `eto_residual_limit_ppm` and `ech_residual_limit_ppm` are the maximum permitted ethylene-oxide and ethylene-chlorohydrin residual concentrations in parts per million and may be zero or greater. `requires_aeration` is a boolean defaulting to true; when it is true and the goods are processed in an ethylene-oxide chamber, lots of that product acquire a degassing obligation the moment their cycle completes. Finally a product carries a `status`, optional at creation and defaulting to `ACTIVE`, whose only other value is `DISCONTINUED`.

### 3.2. Air Permits, Chamber Capacity, and the Emission Rate Schedule

Ethylene-oxide processing is permitted, not merely equipped. An **EmissionPermit** is created by a `RegulatoryAdmin` with a regulator-issued `permit_code` of 1 to 32 characters unique across the facility, a `permit_year` of 2000 or later identifying the calendar year the allowance applies to, an `annual_allowance_kg` greater than zero expressing the post-abatement ethylene-oxide mass the site may emit that year, and a `max_concurrent_eto_cycles` of at least one, capping how many ethylene-oxide dwells may be in progress at once beneath this permit across every chamber it backs. The permit opens with `consumed_kg_ytd` and `total_emission_fee_usd` both at 0 and `status` `ACTIVE`.

The permit's `status` moves on four declared transitions. `ACTIVE → SUSPENDED` happens automatically the moment a cycle start leaves `consumed_kg_ytd` at or above `annual_allowance_kg`, and can also be commanded by a `RegulatoryAdmin`; while `SUSPENDED`, further cycle starts under this permit are refused with `ERR_PERMIT_NOT_ACTIVE`. `SUSPENDED → ACTIVE` happens automatically when an abort credits mass back and leaves `consumed_kg_ytd` strictly below `annual_allowance_kg`; the server keeps no record of why a permit was suspended, so that credit restores an administratively suspended permit on exactly the same terms as an auto-suspended one. The administrator may also command the move; either way, starts become possible again. `ACTIVE → EXPIRED` and `SUSPENDED → EXPIRED` are both commanded by a `RegulatoryAdmin` and are permanent — there is no transition out of `EXPIRED`, and an `EXPIRED` permit blocks cycle starts with the same `ERR_PERMIT_NOT_ACTIVE`. Those four ordered pairs are the whole of the permit's commandable surface: a status request naming any other pair — a re-assertion of the status the permit already holds included — is refused with `ERR_INVALID_STATE`.

A **Chamber** is commissioned under exactly one permit, identified by `permit_id`, and carries a `chamber_code` of 1 to 32 characters unique across the facility, a `modality` of `ETO`, `GAMMA` or `EBEAM`, a `pallet_capacity` of at least one pallet, a `turnaround_minutes` value of zero or more expressing the purge and cooldown buffer that must follow every dwell, and an `abatement_efficiency_pct` between 0 and 100 inclusive describing how much of the raw ethylene-oxide charge the chamber's abatement train destroys. A chamber opens `AVAILABLE`. A `RegulatoryAdmin` may move it `AVAILABLE → MAINTENANCE` and back `MAINTENANCE → AVAILABLE`; a chamber in `MAINTENANCE` cannot have a cycle started in it, which surfaces as `ERR_CHAMBER_UNAVAILABLE`. The administrator may also retire it, `AVAILABLE → DECOMMISSIONED` or `MAINTENANCE → DECOMMISSIONED`; `DECOMMISSIONED` is terminal and additionally blocks scheduling any new cycle into that chamber, again with `ERR_CHAMBER_UNAVAILABLE`. The chamber's four ordered pairs are likewise exhaustive, and a status request naming any other pair — again including a re-assertion of the chamber's current status — is refused with `ERR_INVALID_STATE`.

Emissions are charged on a three-band rate schedule indexed by the permit's post-charge year-to-date consumption. When that figure is at most 50.000 kilograms, the rate is 12.00 US dollars per abated kilogram. When it is above 50.000 and at most 200.000 kilograms, the rate is 18.50 dollars per abated kilogram. Above 200.000 kilograms the rate is 27.00 dollars per abated kilogram. The band is always selected from the consumption figure that *includes* the charge being priced, never from the pre-charge figure; §3.5 pins the exact order in which the two are computed. Gamma and electron-beam chambers never consume the allowance and never accrue a fee.

### 3.3. Validated Recipes and VDmax Product Qualification

A **CycleRecipe** is the validated process description a cycle runs against. A `RegulatoryAdmin` drafts one with a `recipe_code` of 1 to 32 characters unique across the facility and a `modality` of `ETO`, `GAMMA` or `EBEAM` that must match the modality of any chamber the recipe is ever run in. The recipe declares the load-density band it was validated for through `density_min_g_per_cm3`, which must be greater than zero and is the **inclusive** lower edge, and `density_max_g_per_cm3`, which must be strictly greater than the minimum and is the **exclusive** upper edge — a load sitting exactly on the maximum is out of band. It declares three dose figures: `target_dose_kgy`, the nominal dose the recipe aims to deliver and the figure used when checking lifetime dose headroom at load time; `min_dose_kgy`, the inclusive floor a cycle's delivered dose must reach, so that a cycle landing exactly on it conforms; and `max_dose_kgy`, the ceiling on the highest single reading, which must be strictly greater than `min_dose_kgy` and which is only breached when a reading strictly exceeds it. All three must be greater than zero. The `dose_basis` field, either `ROUTINE_MEAN` or `MIN_ZONE`, selects which of the two delivered-dose formulations of §3.6 the recipe is released against.

The recipe also fixes the degassing baseline and the indicator census. `aeration_base_hours` is a whole number of zero or more hours of degassing before density derating is applied. `required_min_zone_dosimeters`, `required_routine_dosimeters` and `required_biological_indicators` are each zero or greater and state the minimum count of each kind of indicator that must be present on a load map before it may be signed off as ready. A recipe whose `required_biological_indicators` is exactly 0 is, by that fact alone, qualified for parametric release. Recipes open in `status` `DRAFT`; only a `RegulatoryAdmin` may advance one `DRAFT → APPROVED`, and only an `APPROVED` recipe may back a cycle — scheduling against a draft is refused with `ERR_RECIPE_NOT_APPROVED`.

Approval of the recipe is not enough to run a customer's goods through it. Each product must additionally hold a current **ProductQualification** binding that specific product to that specific recipe. The administrator opens one with `product_id`, `recipe_id`, a dose-setting `method` of `VDMAX_15`, `VDMAX_25` or `METHOD_1`, a `verification_dose_kgy` greater than zero at which the periodic audit is irradiated, and a `sal_exponent` of at least 1 giving the negative base-ten logarithm of the sterility assurance level, so that a value of 6 denotes one chance in a million. A new qualification is born in `status` `PENDING` with `audit_interval_days` at 90, `consecutive_conditional_count` at 0, and both `last_audit_at` and `next_audit_due_at` null. `PENDING` is not a usable state: load positions and releases both require a qualification in `QUALIFIED` or `CONDITIONAL`, and anything else — missing, `PENDING`, `AUDIT_DUE`, `SUSPENDED` or `REVOKED` — is refused with `ERR_QUALIFICATION_NOT_CURRENT`. Nothing stops several qualifications from binding the same product-and-recipe pair, and no uniqueness rule is enforced on that pair. Where more than one exists, the lapse test below is applied to all of them first and the earliest-created one then standing in `QUALIFIED` or `CONDITIONAL` is the one that satisfies the check; the deviation cascade of §3.6, by contrast, moves every qualification binding the pair rather than only that one.

Qualifications become usable, and stay usable, only through the **dose audit**. A `RegulatoryAdmin` records one by supplying `performed_at`, the instant the audit sample set was irradiated and tested; `samples_tested`, which the VDmax method fixes at exactly 100 so that any other value is refused as a schema violation; `positives`, the number of positive sterility tests, which must lie between 0 and `samples_tested` inclusive; and `verification_dose_kgy_applied`, the dose actually applied to the samples, which must be greater than zero. The audit is a permanent laboratory record: it stores its own `qualification_id`, the computed `outcome`, its own `next_audit_due_at`, and `qualification_status_after`, a snapshot of the parent qualification's `status` immediately after the audit was applied, which is one of `QUALIFIED`, `CONDITIONAL`, `SUSPENDED` or `REVOKED`.

The verdict is decided by the count of positives alone. Zero positives is a `PASS` and buys an interval of 90 days. Exactly one positive is a `CONDITIONAL_PASS` and buys only 30 days. Two or more positives is a `FAIL` and buys nothing — the interval is 0. Where the outcome is not `FAIL`, the audit's `next_audit_due_at` is `performed_at` advanced by the interval in whole days; where the outcome is `FAIL`, `next_audit_due_at` is null. The parent qualification is then updated in lockstep: its `audit_interval_days` becomes the selected interval, its `last_audit_at` becomes `performed_at`, and its `next_audit_due_at` becomes the audit's. A `PASS` sets `consecutive_conditional_count` back to 0 and the qualification's `status` to `QUALIFIED`. A `CONDITIONAL_PASS` increases `consecutive_conditional_count` by one and then looks at the new count: below 2 the qualification becomes `CONDITIONAL`; at 2 or above it becomes `REVOKED`, with `next_audit_due_at` forced to null. That forcing reaches the qualification's own field only — the immutable audit row still records its `next_audit_due_at` as `performed_at` advanced by the 30-day conditional interval, and the qualification's `audit_interval_days` still becomes 30 — so the two rows deliberately disagree after a revoking audit. A `FAIL` resets `consecutive_conditional_count` to 0 and sets the qualification to `SUSPENDED` with `next_audit_due_at` null.

Read as a state machine, the qualification therefore admits fourteen declared transitions, none of which may be attempted against a `REVOKED` qualification — `REVOKED` is terminal. From `PENDING` an audit drives `PENDING → QUALIFIED` on a `PASS` (setting `last_audit_at` to the supplied `performed_at`, `audit_interval_days` to 90, `next_audit_due_at` to 90 days later and `consecutive_conditional_count` to 0), `PENDING → CONDITIONAL` on a `CONDITIONAL_PASS` (interval 30 days, `consecutive_conditional_count` raised by one), and `PENDING → SUSPENDED` on a `FAIL` (interval 0, `next_audit_due_at` null, count reset to 0). A qualification already in service lapses on the calendar: `QUALIFIED → AUDIT_DUE` and `CONDITIONAL → AUDIT_DUE` both fire when the logical clock reaches `next_audit_due_at`, evaluated lazily at the moment the qualification is consulted as a precondition — which is to say during load-position creation and during release, and at no other time, so that merely reading or listing a qualification whose due date has passed still reports the stale `QUALIFIED` or `CONDITIONAL` value until one of those two operations touches it — and both are also driven by the deviation cascade of §3.6; in either case load-position creation for that product-and-recipe pair is thereafter blocked with `ERR_QUALIFICATION_NOT_CURRENT`. A lapsed qualification is repaired by the next audit: `AUDIT_DUE → QUALIFIED` on a `PASS` (count back to 0, next due 90 days after `performed_at`), `AUDIT_DUE → CONDITIONAL` on a `CONDITIONAL_PASS` provided the count after increment is still below 2 (next due 30 days after `performed_at`), and `AUDIT_DUE → SUSPENDED` on a `FAIL` with `next_audit_due_at` null. A conditional qualification behaves symmetrically: `CONDITIONAL → QUALIFIED` on a `PASS` clears the count to 0 and sets the next due date 90 days out; `CONDITIONAL → SUSPENDED` on a `FAIL` nulls the next due date, and the same transition is also reached by the re-sterilization cascade of §3.9; and `CONDITIONAL → REVOKED` fires when a `CONDITIONAL_PASS` pushes `consecutive_conditional_count` to 2 or more — reachable from `CONDITIONAL` and from `AUDIT_DUE` alike — nulling `next_audit_due_at` and, as a further consequence, clearing `schedulable` on every lot of that product whose `status` is `RECEIVED` or `STAGED`. `QUALIFIED → SUSPENDED` is reached either by a `FAIL` audit or by the cumulative-dose re-evaluation of §3.9, and nulls `next_audit_due_at`. Requalification is possible out of suspension: `SUSPENDED → QUALIFIED` on a `PASS` (count 0, next due 90 days out) and `SUSPENDED → CONDITIONAL` on a `CONDITIONAL_PASS` whose post-increment count remains below 2 (next due 30 days out).

### 3.4. Receiving Lots and Scheduling Chamber Time

A `CustomerRep` books physical goods into the facility as a **Lot**, supplying the owning `customer_id`, the `product_id` identifying the product family, a `lot_code` of 1 to 32 characters that must be unique within that customer, and a `total_pallet_count` of at least one. The lot is born in `status` `RECEIVED` with `residual_status` `NOT_APPLICABLE`, `quarantine_reason` `NONE`, `staged_pallet_count` 0, `available_pallet_count` equal to `total_pallet_count`, `cumulative_dose_kgy` 0, `resterilization_count` 0, `schedulable` true, `release_mode` `NONE`, and `parent_lot_id`, `released_at`, `released_by_user_id` and `release_dose_kgy` all null — `parent_lot_id` is populated only on a successor minted by the re-sterilization pathway of §3.9. The owning customer's `open_lot_count` rises by one. A customer whose `status` is `SUSPENDED` may not book lots at all, and the attempt is refused with `ERR_CUSTOMER_SUSPENDED`.

A lot carries two independent state dimensions on one record, and the distinction matters. The primary dimension, `status`, walks `RECEIVED`, `STAGED`, `IN_PROCESS`, `PROCESSED`, `QUARANTINE` and then one of the four dispositions `RELEASED`, `REJECTED`, `SCRAPPED` or `RECALLED`; the last three are terminal. The second dimension, `residual_status`, tracks ethylene-oxide residual clearance through `NOT_APPLICABLE`, `PENDING_AERATION`, `AERATING` and the two terminal values `RESIDUAL_PASS` and `RESIDUAL_FAIL`. The residual dimension advances only on the degassing workflow of §3.8 and never on a cycle or release operation, so the two dimensions genuinely evolve independently. A third descriptive field, `quarantine_reason`, records why a lot is being held and takes one of `NONE`, `ROUTINE`, `DOSE_DEVIATION`, `BI_POSITIVE`, `RESIDUAL_FAIL` or `ADVERSE_EVENT`.

Chamber time is booked as a **Cycle** by a `CycleOperator`, who supplies the `chamber_id` of the chamber to occupy, the `recipe_id` of the approved recipe to run, a `cycle_code` of 1 to 32 characters unique across the facility, and the dwell window as `scheduled_start_at` and `scheduled_end_at`, the latter strictly later than the former. For ethylene-oxide work the operator also supplies `raw_eto_charge_kg`, the mass of gas to be charged into the chamber before abatement; it is optional, defaults to 0, may not be negative, and is ignored outright for gamma and electron-beam chambers. Ignored there means unused, not discarded: whatever figure the operator supplied is persisted on the cycle and echoed back in `raw_eto_charge_kg` regardless of modality, and it is simply never allowed to reach the emission arithmetic. The cycle opens in `status` `PLANNED` with `loaded_pallet_count` 0, `load_density_g_per_cm3` 0, `abated_eto_kg` 0, `emission_fee_usd` 0, `deviation_code` `NONE`, and `delivered_dose_kgy`, `max_observed_dose_kgy`, `operator_user_id` and `dosimetry_closed_by_user_id` all null. Its full state enumeration is `PLANNED`, `LOADING`, `READY`, `RUNNING`, `COMPLETED`, `DOSIMETRY_REVIEW`, and then either `DOSE_CONFORMING` or `DOSE_DEVIATION`, with `CANCELLED` reachable from the pre-dwell and dwell states; `DOSE_CONFORMING` and `CANCELLED` are terminal. Scheduling is refused if the chamber is `DECOMMISSIONED` (`ERR_CHAMBER_UNAVAILABLE`), if the recipe is still `DRAFT` (`ERR_RECIPE_NOT_APPROVED`), if the recipe's `modality` differs from the chamber's `modality` (`ERR_MODALITY_MISMATCH`), or if the `cycle_code` is already taken (`ERR_DUPLICATE_CODE`).

Two distinct temporal rules police the schedule, and they differ from one another in three respects — buffer, inclusivity and arity — so they must be implemented separately. At creation the server derives `occupancy_end_at` as `scheduled_end_at` advanced by the chamber's `turnaround_minutes`, which is the outer edge of the chamber's occupancy; that derived instant is persisted as a field of the cycle and returned with it, and it is never recomputed afterwards even if the chamber's `turnaround_minutes` were to change. **The chamber rule** is pairwise and exclusive: the new cycle's occupancy interval runs from `scheduled_start_at` up to but not including `occupancy_end_at`, and the request is refused with `ERR_CHAMBER_WINDOW_CONFLICT` if any other cycle in the same chamber whose `status` is none of `CANCELLED`, `DOSE_CONFORMING` or `DOSE_DEVIATION` has an occupancy interval that intersects it — that is, when the new cycle's start is strictly earlier than that cycle's occupancy end and that cycle's start is strictly earlier than the new cycle's occupancy end. Touching endpoints do not collide: a cycle beginning exactly at the instant another cycle's occupancy ends is accepted. **The permit rule** is aggregate, unbuffered and closed at both ends, and applies only when the chamber's `modality` is `ETO`. The server counts the cycles whose chamber sits under the same permit, whose chamber `modality` is also `ETO`, whose `status` is none of `CANCELLED`, `DOSE_CONFORMING` or `DOSE_DEVIATION`, and whose dwell interval from `scheduled_start_at` to `scheduled_end_at` inclusive touches or overlaps the new cycle's dwell interval — the new cycle's start at or before the other's end, and the other's start at or before the new cycle's end, so that merely touching dwells do count as concurrent. If that count is already equal to or greater than the permit's `max_concurrent_eto_cycles`, the request is refused with `ERR_PERMIT_CONCURRENCY_EXCEEDED`. Cycles that are `CANCELLED`, `DOSE_CONFORMING` or `DOSE_DEVIATION` release both the chamber and the permit slot.

### 3.5. Building the Load Map: Slots, Indicators, and Aggregate Density

A cycle without a load map sterilizes nothing. The `CycleOperator` builds the map one **LoadPosition** at a time, each request naming the `lot_id` of the lot to place, a `position_index` identifying the physical slot, which must be at least 1 and no greater than the chamber's `pallet_capacity` — both of those numeric bounds are payload-schema checks screened at step 3 of §2.7, so a breach of either is reported as `ERR_VALIDATION`, and the upper bound is evaluated by consulting the chamber behind the cycle named in the path, which means it is skipped altogether when that cycle identifier resolves to nothing and the request goes on to answer `ERR_CYCLE_NOT_FOUND` at step 4 — and which must not already be used by another position on the same cycle, a `zone` describing the slot's geometric dose exposure — one of `MIN_DOSE`, `MAX_DOSE`, `INTERIOR` or `EDGE` — a `pallet_count` of at least one pallet, and the `expected_cycle_version` handle described in §2.6.

Before the slot is written, eight conditions must hold, and they are evaluated in the screening order of §2.7 so that the earliest breach is the one reported. The cycle must be in `PLANNED`, `LOADING` or `READY`. The lot's `schedulable` flag must be true, failing which the write is refused with `ERR_LOT_NOT_SCHEDULABLE`. The supplied `expected_cycle_version` must equal the cycle's current `version`, failing which the write is refused with `ERR_STALE_CYCLE_VERSION`. A `ProductQualification` must exist for the lot's product and the cycle's recipe with `status` `QUALIFIED` or `CONDITIONAL`, failing which the write is refused with `ERR_QUALIFICATION_NOT_CURRENT`. The chamber's `modality` must appear in the owning customer's `contracted_modalities`, and a modality the customer never contracted for is refused with `ERR_MODALITY_MISMATCH`. The cycle's `loaded_pallet_count` plus the requested `pallet_count` must not exceed the chamber's `pallet_capacity`, and the requested `pallet_count` must not exceed the lot's `available_pallet_count`; either breach is refused with `ERR_CHAMBER_CAPACITY_EXCEEDED`. No existing position on the cycle may already hold the requested `position_index`, on pain of `ERR_DUPLICATE_POSITION_INDEX`. Finally the lot's lifetime dose headroom must survive the placement: the lot's `cumulative_dose_kgy` plus the recipe's `target_dose_kgy`, rounded half up to two decimal places, must be no greater than the product's `max_cumulative_dose_kgy`, and a breach is refused with `ERR_CUMULATIVE_DOSE_EXCEEDED`.

When the write succeeds, the slot is persisted with `cycle_version_after` set to the cycle's `version` as of that write; the cycle's `loaded_pallet_count` grows by the placed `pallet_count`; the cycle's `load_density_g_per_cm3` is recomputed from scratch; the lot's `staged_pallet_count` grows by the same `pallet_count` and its `available_pallet_count` is refreshed to `total_pallet_count` less `staged_pallet_count`; the lot moves `RECEIVED → STAGED`, or simply stays `STAGED` if it was already staged by an earlier slot, or — since the eight conditions above impose no gate at all on the lot's primary dimension — keeps whatever other `status` it happened to be carrying, untouched; and the cycle's `version` increases by one. The cycle's own state follows the map: the first position on a fresh cycle drives `PLANNED → LOADING`, every subsequent position holds it at `LOADING → LOADING`, and a position added to a cycle that had already been signed off drives `READY → LOADING`, deliberately unwinding the sign-off so that every readiness check must be re-run against the revised map. That `READY → LOADING → READY` round trip is a supported working pattern, not an error.

Removing a slot is the exact compensating action and is permitted while the cycle is in `PLANNED`, `LOADING` or `READY`. The position must belong to the cycle named in the path; a position that exists but hangs off a different cycle is reported as `ERR_LOAD_POSITION_NOT_FOUND`. The row is hard-deleted — there is no soft-delete or tombstone — and the same arithmetic runs in reverse: the cycle's `loaded_pallet_count` falls by the removed `pallet_count`, `load_density_g_per_cm3` is recomputed, the lot's `staged_pallet_count` falls and `available_pallet_count` is refreshed, and the lot walks `STAGED → RECEIVED` when it retains no load position on any cycle anywhere. A cycle that was `READY` and still retains at least one other position reverts to `LOADING`; a cycle already in `LOADING` that still retains at least one other position holds at `LOADING → LOADING`; and a cycle left with no positions at all lands in `PLANNED` in one move — from `LOADING` or straight from `READY`, whichever it was when the last slot went — with `loaded_pallet_count` at 0 and `load_density_g_per_cm3` at 0.0000. The cycle's `version` increases by one on every removal, which is precisely why a client holding an older `cycle_version_after` cannot blindly append.

The aggregate **load density** is the number the whole recipe-selection story turns on, and its evaluation order is pinned. Over every load position currently on the cycle — regardless of the status of the lot occupying it — the server accumulates a total mass in grams by multiplying each position's `pallet_count` by the `pallet_mass_kg` of the product behind that position's lot and then by one thousand to convert kilograms to grams, and accumulates a total volume in cubic centimetres by multiplying each position's `pallet_count` by that product's `pallet_volume_m3` and then by one million to convert cubic metres to cubic centimetres. Neither accumulation is rounded at any intermediate step. The total mass is then divided by the total volume exactly once, and that single quotient is rounded half up to four decimal places to give `load_density_g_per_cm3`. When the total volume is zero — a cycle with no positions left — the density is 0.0000. Rounding each position's own density to four places and averaging those per-position figures is explicitly **not** the rule, and produces a different answer for any load whose positions differ in volume. Positions removed by a deletion or by a cascade are excluded simply because their rows no longer exist.

Indicators are placed into individual slots rather than into the cycle as a whole. A `CycleOperator` places an **Indicator** in a load position by supplying `indicator_type`, either `DOSIMETER` or `BIOLOGICAL`; `placement_zone`, the dose zone the indicator is qualified to report on, one of `MIN_DOSE`, `MAX_DOSE` or `ROUTINE`; a `serial_code` of 1 to 32 characters unique across the facility, a collision being refused with `ERR_DUPLICATE_CODE`; and, for a biological indicator only, `spore_population`, the declared spore count, which must be present and at least 1 for a `BIOLOGICAL` indicator and must be omitted or null for a `DOSIMETER`. An indicator whose `placement_zone` is `MIN_DOSE` may only be placed in a slot whose `zone` is `MIN_DOSE`; a mismatched placement, like a malformed `spore_population`, is refused as a payload violation with `ERR_VALIDATION`. The persisted indicator records the slot it sits in as `load_position_id`. Every indicator is born with `reading_status` `UNREAD`, `bi_result` `PENDING`, and `measured_dose_kgy`, `read_at` and `read_by_user_id` all null. The `bi_result` field is meaningful only for biological indicators and its terminal values are `NEGATIVE` and `POSITIVE`.

Throughout all of this, the pallet arithmetic of §2.9 must balance after every single mutation — the load-map write, the deletion, the bulk removals performed by an abort, and the cascade-driven removals of §3.7 alike.

### 3.6. Readiness Sign-Off, the Dwell, and the Emission Debit

Signing a load map off as ready is the operator's assertion that the physical chamber matches the record. The sign-off is accepted while the cycle is in `LOADING`, and its state gate deliberately also admits a cycle still in `PLANNED` so that the emptiness check below stays reachable rather than being masked by a generic state rejection. Three checks then run, strictly in this order, and the first failure is the one reported. First, the cycle must hold at least one load position; a `PLANNED` cycle necessarily holds none, so it always fails here with `ERR_LOAD_MAP_EMPTY` and never reaches `READY`. Second, the indicator census must be satisfied: counted across every load position of the cycle, the number of `DOSIMETER` indicators whose `placement_zone` is `MIN_DOSE` must be at least the recipe's `required_min_zone_dosimeters`, the number of `DOSIMETER` indicators whose `placement_zone` is `ROUTINE` must be at least `required_routine_dosimeters`, and the number of `BIOLOGICAL` indicators must be at least `required_biological_indicators`; any shortfall is refused with `ERR_INDICATOR_PLACEMENT_INCOMPLETE`. Third, the cycle's `load_density_g_per_cm3` must sit inside the recipe's validated band — at or above `density_min_g_per_cm3` and strictly below `density_max_g_per_cm3` — with a density below the floor or at or above the ceiling refused as `ERR_LOAD_DENSITY_OUT_OF_BAND`. On success the cycle moves `LOADING → READY` and its `version` increases by one, which invalidates any load-map handle a client was holding.

Starting the cycle is the point at which the plant commits resources it cannot take back for free. The cycle must be `READY`, and a start attempted from any other state is refused specifically with `ERR_CYCLE_NOT_READY`. The chamber must be `AVAILABLE`; one in `MAINTENANCE` or `DECOMMISSIONED` is refused with `ERR_CHAMBER_UNAVAILABLE`. The permit behind the chamber must be `ACTIVE`; one that is `SUSPENDED` or `EXPIRED` is refused with `ERR_PERMIT_NOT_ACTIVE`.

For an ethylene-oxide chamber, the emission arithmetic then runs in a pinned six-step order, and the order matters because the fee depends on a rate which in turn depends on consumption that includes this very charge. **Step one** computes the abated mass: the cycle's `raw_eto_charge_kg` multiplied by the fraction of gas that survives abatement — one minus the chamber's `abatement_efficiency_pct` divided by one hundred — with the result rounded half up to three decimal places. **Step two** computes the prospective year-to-date figure: the permit's current `consumed_kg_ytd` plus that abated mass, again rounded half up to three decimal places. **Step three** is the allowance gate: if the prospective figure is strictly greater than the permit's `annual_allowance_kg` the start is refused with `ERR_PERMIT_ALLOWANCE_EXCEEDED`, while landing exactly on the allowance is accepted. **Step four** selects the rate from the three-band schedule of §3.2 using the *prospective* figure, not the pre-charge one — 12.00 dollars per kilogram at or below 50.000 kilograms, 18.50 dollars per kilogram above 50.000 and at or below 200.000, and 27.00 dollars per kilogram above 200.000. **Step five** computes `emission_fee_usd` as the abated mass multiplied by that rate, rounded half up to two decimal places. **Step six** commits: the permit's `consumed_kg_ytd` becomes the prospective figure, the permit's `total_emission_fee_usd` becomes its previous value plus the new fee rounded half up to two decimal places, and the cycle's `abated_eto_kg` records the abated mass. For gamma and electron-beam chambers, `raw_eto_charge_kg` is ignored entirely: `abated_eto_kg` is 0.000, `emission_fee_usd` is 0.00, and steps three through six are skipped — so the permit, which must still be `ACTIVE` for the start to proceed at all, is read but never written, and its `consumed_kg_ytd`, `total_emission_fee_usd`, `status`, `updated_at` and `version` all stand exactly where they were.

The rest of the start is bookkeeping with consequences. If the commit leaves `consumed_kg_ytd` at or above `annual_allowance_kg`, the permit moves `ACTIVE → SUSPENDED` on the spot, and every subsequent start beneath it is refused with `ERR_PERMIT_NOT_ACTIVE` until an abort or an administrator restores it. The caller's `X-User-ID` is stamped onto the cycle as `operator_user_id` — the first half of the segregation-of-duties pair. Every lot referenced by a load position of this cycle moves `STAGED → IN_PROCESS`. The cycle itself moves `READY → RUNNING`.

Completing the dwell is deliberately unconditional beyond the state gate: a `RUNNING` cycle moves `RUNNING → COMPLETED`, every lot on its load map moves `IN_PROCESS → PROCESSED`, and — for each such lot, only when the chamber's `modality` is `ETO` and the lot's product has `requires_aeration` set to true — the lot's second dimension opens with `NOT_APPLICABLE → PENDING_AERATION`, creating the degassing obligation of §3.8. Lots of gamma or electron-beam work, and lots of products that do not require aeration, stay at `NOT_APPLICABLE` forever and are releasable on the residual axis without any further step.

Aborting a cycle is available from `PLANNED`, `LOADING`, `READY` and `RUNNING`, and always requires a `reason` in the payload. From the three pre-dwell states the effect is purely structural: every load position on the cycle is hard-deleted in ascending `created_at` order, each referenced lot has its `staged_pallet_count` decremented and its `available_pallet_count` refreshed, every lot left with no load position anywhere walks `STAGED → RECEIVED`, the cycle's `loaded_pallet_count` returns to 0 with `load_density_g_per_cm3` at 0.0000, and the cycle lands in `CANCELLED` — `PLANNED → CANCELLED`, `LOADING → CANCELLED` or `READY → CANCELLED` as the case may be. From `RUNNING` the abort additionally performs the compensating half of the emission ledger, and it does so only for an ethylene-oxide chamber — a running gamma or electron-beam cycle has nothing to credit, so its permit row is not written at all, `updated_at` and `version` included. For an ethylene-oxide chamber the permit's `consumed_kg_ytd` becomes its current value less exactly the cycle's stored `abated_eto_kg`, rounded half up to three decimal places, and its `total_emission_fee_usd` becomes its current value less exactly the cycle's stored `emission_fee_usd`, rounded half up to two decimal places. Because the credit reverses the stored figures rather than recomputing them from the rate schedule, no drift can accumulate even if a tier boundary was crossed in between. If that credit leaves `consumed_kg_ytd` strictly below `annual_allowance_kg` and the permit is currently `SUSPENDED`, the permit walks `SUSPENDED → ACTIVE`. The cycle's own `abated_eto_kg` and `emission_fee_usd` are then zeroed, its positions removed on the same terms as above, and the lots it was processing walk `IN_PROCESS → RECEIVED` — back to the receiving dock, not to `STAGED`, because the abort has dissolved their load map. The cycle itself walks `RUNNING → CANCELLED`, which is terminal and which releases both the chamber occupancy and the permit concurrency slot for future scheduling.

### 3.7. Dosimetry Review, Delivered Dose, and the Deviation Cascade

Once the dwell is over, the metrology laboratory takes possession of the record. A `DosimetryAnalyst` records a reading against one indicator at a time, supplying exactly one of two mutually exclusive fields, and the one supplied must match the indicator's `indicator_type`: `measured_dose_kgy`, a positive dose in kilogray, is supplied for a `DOSIMETER` indicator, and `bi_result`, which must be `NEGATIVE` or `POSITIVE` and may never be `PENDING`, is supplied for a `BIOLOGICAL` indicator. Supplying both, neither, or the wrong one for the type is refused with `ERR_VALIDATION`. A successful reading sets the indicator's `reading_status` to `READ` and stamps `read_at` with the logical clock and `read_by_user_id` with the analyst's `X-User-ID`.

The very first reading recorded against a `COMPLETED` cycle carries that cycle `COMPLETED → DOSIMETRY_REVIEW`, which is a server-driven transition rather than a separate operator action. The cycle's state is never itself a precondition of a reading: a reading taken while the cycle sits in any other state — still `PLANNED`, `LOADING`, `READY` or `RUNNING`, already in `DOSIMETRY_REVIEW`, or already `DOSE_CONFORMING` — is accepted on the indicator's own terms and leaves the cycle's `status` exactly where it stood. Recording a reading against an indicator that is already `READ` is normally refused with `ERR_INDICATOR_ALREADY_READ` — with one deliberate exception. When the indicator's cycle is sitting in `DOSE_DEVIATION`, a re-read is the documented mechanism for correcting a mis-read instrument: the indicator's `measured_dose_kgy` or `bi_result` is overwritten, `read_at` and `read_by_user_id` are refreshed, the cycle's `deviation_code` returns to `NONE`, its `delivered_dose_kgy` and `max_observed_dose_kgy` are cleared back to null, and the cycle walks `DOSE_DEVIATION → DOSIMETRY_REVIEW` so that the close may be attempted again on corrected data. The `dosimetry_closed_by_user_id` stamped by the deviated close is deliberately *not* cleared alongside them, so the analyst who closed the deviation remains disqualified from releasing the lot even across the correction.

Closing dosimetry is the analyst's terminal act on a cycle and requires the cycle to be in `DOSIMETRY_REVIEW` with every indicator on it — dosimeters and biological indicators alike — at `reading_status` `READ`; any unread indicator refuses the close with `ERR_DOSIMETRY_INCOMPLETE`. The close computes two dose figures from the set of `DOSIMETER` indicators on the cycle's load positions whose `reading_status` is `READ`. Biological indicators contribute to neither figure. If that set is empty the close is refused with `ERR_DOSIMETRY_INCOMPLETE`. `max_observed_dose_kgy` is the largest `measured_dose_kgy` in that set, rounded half up to two decimal places.

`delivered_dose_kgy` is then computed by whichever of two variants the recipe's `dose_basis` selects, and the two can disagree sharply on identical instrument data. Under the **`ROUTINE_MEAN`** variant, the server takes the subset of those read dosimeters whose `placement_zone` is `ROUTINE`; if that subset is empty the close is refused with `ERR_DOSIMETRY_INCOMPLETE`; otherwise `delivered_dose_kgy` is the sum of their `measured_dose_kgy` values divided by the count of those readings, with the single quotient rounded half up to two decimal places. Under the **`MIN_ZONE`** variant, the server instead takes the subset of read dosimeters whose `placement_zone` is `MIN_DOSE`; if that subset is empty the close is again refused with `ERR_DOSIMETRY_INCOMPLETE`; otherwise `delivered_dose_kgy` is the smallest `measured_dose_kgy` among them, rounded half up to two decimal places. For any load whose minimum-zone readings sit below the routine mean, the `MIN_ZONE` variant yields a strictly smaller figure than `ROUTINE_MEAN` would on the same data, and can therefore flip a cycle that would otherwise conform into an underdose deviation.

The conformance verdict is then decided by three tests evaluated in a pinned order, where the **first matching test wins and the later tests are not evaluated at all** — an ordering that changes the recorded `deviation_code` for any load that breaches more than one condition. Before the tests run, the server derives a product-side dose ceiling: the smallest `max_allowed_dose_kgy` among the distinct products of the lots present in this cycle's load map. The first test asks whether any `BIOLOGICAL` indicator on the cycle has `bi_result` equal to `POSITIVE`; if one does, the verdict is a deviation with `deviation_code` `BI_POSITIVE`. The second test asks whether `delivered_dose_kgy` is strictly less than the recipe's `min_dose_kgy`, so that a cycle landing exactly on the floor conforms; if it is below, the verdict is a deviation with `deviation_code` `UNDERDOSE`. The third test asks whether `max_observed_dose_kgy` is strictly greater than the recipe's `max_dose_kgy`, or strictly greater than the product-side ceiling, so that a reading landing exactly on either limit conforms; if either is exceeded, the verdict is a deviation with `deviation_code` `OVERDOSE`. If none of the three fires, the verdict is conforming and `deviation_code` is `NONE`. All of these comparisons are made against the already-rounded two-decimal dose values.

On the conforming branch the cycle walks `DOSIMETRY_REVIEW → DOSE_CONFORMING`. The analyst's `X-User-ID` is stamped as `dosimetry_closed_by_user_id`, the second half of the segregation-of-duties pair. Every lot on the load map at `status` `PROCESSED` moves `PROCESSED → QUARANTINE` with `quarantine_reason` set to `ROUTINE`. Any lot on this cycle that is already in `QUARANTINE` carrying `quarantine_reason` of `DOSE_DEVIATION` or `BI_POSITIVE` — the residue of a previous deviated close on this same cycle that has since been corrected by re-reads — has its `quarantine_reason` reset to `ROUTINE` and its `schedulable` flag restored to true, compensating the earlier cascade. Finally the lifetime dose ledger is posted: taking the distinct lots referenced by this cycle's load positions, processed in ascending `created_at` order of their load positions and, where two positions share an instant, in ascending `position_index` order, each lot's `cumulative_dose_kgy` becomes its previous value plus the cycle's `delivered_dose_kgy`, rounded half up to two decimal places at each accumulation step. A lot occupying several slots of the same cycle is credited exactly once, because the distinct set of lots is used rather than the set of position rows.

On the deviating branch the cycle walks `DOSIMETRY_REVIEW → DOSE_DEVIATION` and a four-hop cascade fires, where each hop is caused by the hop before it rather than by the analyst's request. **Hop one** writes the dose figures, sets `deviation_code` to `BI_POSITIVE`, `UNDERDOSE` or `OVERDOSE` as the verdict decided, stamps `dosimetry_closed_by_user_id`, and lands the cycle in `DOSE_DEVIATION`. **Hop two**, caused by hop one, moves every lot of this cycle at `status` `PROCESSED` to `QUARANTINE`, with `quarantine_reason` set to `BI_POSITIVE` when the deviation code is `BI_POSITIVE` and to `DOSE_DEVIATION` otherwise, and clears each of those lots' `schedulable` flag to false. **Hop three**, caused by hop two, reaches the qualification file: for each lot quarantined in hop two, the `ProductQualification` binding that lot's product to this cycle's recipe, if its `status` is `QUALIFIED` or `CONDITIONAL`, is moved to `AUDIT_DUE` with `next_audit_due_at` set to the current logical-clock instant, so that the pair cannot be loaded again until a fresh dose audit clears it. **Hop four**, caused by hop three, reaches sideways into unrelated in-flight work: for every qualification pushed to `AUDIT_DUE` in hop three, every *other* lot of the same product whose `status` is `STAGED` has its `schedulable` flag cleared to false and walks `STAGED → RECEIVED`, and each of that lot's load positions on cycles whose `status` is `PLANNED`, `LOADING` or `READY` is hard-deleted in ascending `created_at` order — decrementing that cycle's `loaded_pallet_count`, recomputing its `load_density_g_per_cm3`, and reverting that cycle from `READY` to `LOADING`, or from `LOADING` to `PLANNED` when the removal leaves it with no positions at all. A deviating close deliberately does **not** touch any lot's `cumulative_dose_kgy`; only a conforming close posts dose to the lifetime ledger.

### 3.8. Aeration and Residual Clearance

Several rules need to know which cycle actually governs a lot, and the answer is always computed the same way. Among all load positions referencing that lot, the server ranks them by `created_at` descending — compared at millisecond resolution — and breaks ties by `position_index` ascending; the cycle behind the first row of that ranking is the lot's **governing cycle**. Identifier values are never used as an ordering key. A lot with no load positions at all has no governing cycle, which matters because an aborted cycle hard-deletes its positions: such a lot is refused a release with `ERR_LOT_NOT_RELEASABLE` and is refused an aeration record with `ERR_AERATION_NOT_APPLICABLE`.

Ethylene-oxide loads leave the chamber saturated with gas, and the goods cannot go anywhere until they have degassed. A `CycleOperator` opens an **AerationRecord** for a lot whose `residual_status` is `PENDING_AERATION`; the request carries no payload beyond the lot named in the path. A lot whose `residual_status` is anything other than `PENDING_AERATION` is refused with `ERR_AERATION_NOT_APPLICABLE`, and never with `ERR_INVALID_STATE`: `NOT_APPLICABLE` because the lot has no degassing obligation at all, and `AERATING`, `RESIDUAL_PASS` or `RESIDUAL_FAIL` because its obligation is already open or already settled. Opening the record moves the lot `PENDING_AERATION → AERATING` on the residual dimension and creates the record in `status` `IN_PROGRESS` with `retest_count` 0, `variant_applied` `STANDARD`, `aeration_start_at` set to the current logical-clock instant, and `last_failed_sample_at`, `last_eto_ppm` and `last_ech_ppm` all null. The record snapshots two inputs from the governing cycle at the moment it is opened and never re-reads them afterwards: `base_hours`, copied from the governing cycle's recipe `aeration_base_hours`, and `density_factor`, derived from the governing cycle's `load_density_g_per_cm3`.

The density derating uses three bands, both breakpoints lower-inclusive. A governing density below 0.1000 grams per cubic centimetre gives a `density_factor` of 1.00; a density at or above 0.1000 and below 0.2000 gives 1.25; a density at or above 0.2000 gives 1.60. A load sitting exactly on 0.1000 therefore takes 1.25, not 1.00. Under the **`STANDARD`** variant — which is what a freshly opened record with a `retest_count` of 0 always uses — `required_hours` is the product of `base_hours` and `density_factor`, rounded up to the next whole hour by a single ceiling applied to the complete product, and `target_end_at` is `aeration_start_at` advanced by that many hours.

`target_end_at` is the earliest instant at which the laboratory may sample. A `DosimetryAnalyst` records a residual test by supplying `eto_residual_ppm` and `ech_residual_ppm`, the measured ethylene-oxide and ethylene-chlorohydrin concentrations. If the record has already reached `PASSED` or `EXHAUSTED`, no further sample is accepted and the attempt is refused with `ERR_RETEST_LIMIT_EXHAUSTED`; that is the declared-transition test of §2.7 and it is therefore evaluated first. Only once the record is shown to still admit a sample is the timing tested: if the logical clock has not yet reached the record's `target_end_at`, the sample is refused with `ERR_AERATION_INCOMPLETE`. A settled record sampled early therefore reports the exhaustion, not the timing. Every accepted test records `last_eto_ppm` and `last_ech_ppm` on the record regardless of its verdict.

The verdict is a pass when `eto_residual_ppm` is at or below the product's `eto_residual_limit_ppm` **and** `ech_residual_ppm` is at or below the product's `ech_residual_limit_ppm`; both comparisons are inclusive, so a reading landing exactly on a limit passes. A pass carries the record `IN_PROGRESS → PASSED` or `RETEST_REQUIRED → PASSED`, and the lot `AERATING → RESIDUAL_PASS`, which is what makes the lot releasable on the residual axis. A failure is tolerated at most twice: the facility grants a retest budget of two failed samples per record. When a failure arrives and the incremented `retest_count` would still be at most two, the record moves `IN_PROGRESS → RETEST_REQUIRED` on the first such failure and self-loops `RETEST_REQUIRED → RETEST_REQUIRED` on the second; in both cases `retest_count` rises by one, `last_failed_sample_at` is stamped with the current logical-clock instant, `variant_applied` becomes `EXTENDED_RETEST`, and both `required_hours` and `target_end_at` are recomputed under that variant.

The **`EXTENDED_RETEST`** variant differs from `STANDARD` in two ways at once, so the two never agree on `target_end_at` once a failure has occurred. Its `required_hours` is the product of the snapshotted `base_hours`, the snapshotted `density_factor`, and a growth multiplier of one plus one half times the current `retest_count` — a single ceiling applied once to that complete product — so a first failure stretches the requirement by half again and a second failure doubles it. Its anchor is not `aeration_start_at` but `last_failed_sample_at`: `target_end_at` is the instant of the most recent failing sample advanced by the newly computed `required_hours`.

When a failure arrives that would push `retest_count` past two, the budget is exhausted. `retest_count` still rises by one, the record moves `RETEST_REQUIRED → EXHAUSTED`, and the failure propagates: the lot moves `AERATING → RESIDUAL_FAIL` on the residual dimension and simultaneously `QUARANTINE → REJECTED` on the primary dimension with `quarantine_reason` set to `RESIDUAL_FAIL`, and the owning customer's `open_lot_count` falls by one because the lot has left the open set for good. Two details of that final failure differ from the tolerated ones. First, no new deadline is computed: `variant_applied`, `required_hours` and `target_end_at` are left exactly as the previous failure set them and `last_failed_sample_at` is not restamped, because an exhausted record accepts no further sample. Second, only the residual half of the propagation is unconditional — the move to `REJECTED`, the `quarantine_reason` of `RESIDUAL_FAIL` and the fall in `open_lot_count` all require the lot to actually be sitting in `QUARANTINE` at that instant, and a lot that is not keeps its primary `status`, keeps its existing `quarantine_reason`, and leaves its customer's `open_lot_count` where it stood.

### 3.9. Quarantine, Release, and Adverse-Event Disposition

Quarantine is the default resting place of processed goods, and a `QualityReleaseOfficer` is the only role that can end it. Release requires a single payload field, `release_mode`, which must be either `PARAMETRIC` or `DOSIMETRIC`; the value `NONE` that a lot carries before release is never a legal request. The release gate is a chain of checks in a fixed order, and the first failure is what the caller sees.

The chain begins with the lot's own posture: the lot must be in `QUARANTINE`, must not carry a `residual_status` of `RESIDUAL_FAIL`, and must have a governing cycle at all, with any of those three failures reported as `ERR_LOT_NOT_RELEASABLE`. Next, no `BIOLOGICAL` indicator on the governing cycle may carry `bi_result` `POSITIVE` — a growth-positive indicator blocks release outright with `ERR_BI_POSITIVE_BLOCKS_RELEASE`, regardless of how favourable the dosimetry looks. Next, the governing cycle's `status` must be `DOSE_CONFORMING`; a cycle still under review, or one parked in `DOSE_DEVIATION`, blocks release with `ERR_CYCLE_DEVIATION_BLOCKS_RELEASE`. Next, the `ProductQualification` binding the lot's product to the governing cycle's recipe must be `QUALIFIED` or `CONDITIONAL`, failing which the release is refused with `ERR_QUALIFICATION_NOT_CURRENT`. Next comes the segregation-of-duties test of §2.10, refusing with `ERR_SEGREGATION_OF_DUTIES` when the officer's `X-User-ID` matches either the governing cycle's `operator_user_id` or its `dosimetry_closed_by_user_id`. Next, the residual axis must be settled: a lot whose `residual_status` is still `PENDING_AERATION` or `AERATING` is refused with `ERR_AERATION_INCOMPLETE`, while `NOT_APPLICABLE` and `RESIDUAL_PASS` both satisfy this gate. Next, the two release modes are checked against their own eligibility rules: a `PARAMETRIC` release is permitted only when the governing cycle's recipe has `required_biological_indicators` equal to 0, and is otherwise refused with `ERR_PARAMETRIC_NOT_PERMITTED`; a `DOSIMETRIC` release requires every `BIOLOGICAL` indicator on the governing cycle to have `reading_status` `READ`, and is otherwise refused with `ERR_BI_INCUBATION_PENDING`. Last, the owning customer must be `ACTIVE`, with a suspended account refused as `ERR_CUSTOMER_SUSPENDED`.

A release that survives that chain moves the lot `QUARANTINE → RELEASED` and stamps the certificate: `release_mode` records the pathway used, `released_at` records the current logical-clock instant, `released_by_user_id` records the officer's `X-User-ID`, and `release_dose_kgy` snapshots the governing cycle's `delivered_dose_kgy` so that the released record is immune to any later re-read of the cycle. `quarantine_reason` returns to `NONE`, and the owning customer's `open_lot_count` falls by one.

Goods in the field can still go wrong. An **AdverseEvent** may be reported against a lot by either a `CustomerRep` — subject to the customer scoping of §2.1 — or a `QualityReleaseOfficer`. The subject lot's `status` is not a precondition of the report: an event is accepted against a lot in any state whatever, from `RECEIVED` through `RELEASED` and the terminal dispositions alike, and beyond scoping the only gate is the `expected_lot_version` handle. The report carries an `event_type` of `STERILITY_COMPLAINT`, `RESIDUAL_EXCEEDANCE`, `FIELD_DOSE_DEVIATION` or `PACKAGING_BREACH`; a reporter-assigned `severity` of `LOW`, `MEDIUM`, `HIGH` or `CRITICAL`; a free-text `description` of between 1 and 500 characters; and the `expected_lot_version` handle of §2.6. The event is created in `status` `REPORTED` with `reported_by_user_id` set from the caller's `X-User-ID`, `lot_version_after` snapshotting the lot's `version` immediately after the write, and `disposition` null. If the subject lot is in `QUARANTINE`, its `quarantine_reason` is set to `ADVERSE_EVENT`. The lot's `version` increases by one, which is exactly what makes a second reporter's stale handle detectable.

Dispositioning a reported event is reserved to a `QualityReleaseOfficer` and takes one field, `disposition`, whose three values are `RESTERILIZE`, `SCRAP` and `DISMISS`. All three outcomes are terminal for the event, and all three require the event to still be in `REPORTED`. An event that has already been dispositioned, and a subject lot whose `status` does not admit the chosen disposition under the rules below, are both refused with `ERR_INVALID_STATE`.

`DISMISS` is the gentlest: the event moves `REPORTED → DISMISSED`, and if the lot is sitting in `QUARANTINE` carrying a `quarantine_reason` of `ADVERSE_EVENT`, that reason walks back to `ROUTINE`. Both halves of that condition are required — a quarantined lot held for any other reason, and a lot not in `QUARANTINE` at all, are left entirely untouched, `updated_at` and `version` included. The lot's `status` is untouched, so a dismissed complaint leaves a quarantined lot releasable on its original merits.

`SCRAP` is available when the subject lot is `RELEASED` or in `QUARANTINE`. The event moves `REPORTED → SCRAP_APPROVED`, the lot moves `QUARANTINE → SCRAPPED` or `RELEASED → SCRAPPED` as the case may be, and its `schedulable` flag is cleared to false so the physical goods can never re-enter a load map. The owning customer's `open_lot_count` falls by one only when the lot was in `QUARANTINE`; a lot that had already been released left the open set at release time and must not be double-counted.

`RESTERILIZE` is available only when the subject lot is `RELEASED`, and it fires a three-hop cascade. **Hop one** moves the event `REPORTED → RESTERILIZE_APPROVED` and records `disposition` as `RESTERILIZE`. **Hop two**, caused by hop one, moves the subject lot `RELEASED → RECALLED` with `quarantine_reason` set to `ADVERSE_EVENT`, and mints a successor lot in the same breath: the successor's `parent_lot_id` points at the subject, its `customer_id`, `product_id` and `total_pallet_count` are copied from the subject, its `lot_code` is the subject's `lot_code` followed by the literal characters `-R` and then the subject's `resterilization_count` increased by one, its `status` is `RECEIVED` with `staged_pallet_count` 0 and `available_pallet_count` equal to `total_pallet_count`, its `residual_status` is `NOT_APPLICABLE`, its `cumulative_dose_kgy` is inherited unchanged from the subject so that the physical goods carry their full dose history forward, its `resterilization_count` is the subject's increased by one, and its `schedulable` flag starts true. The customer's `open_lot_count` is unchanged across this hop: the recalled lot leaves the open set at the same moment the successor enters it. **Hop three**, caused by hop two, exists because the successor arrives carrying a non-zero dose burden. Every `ProductQualification` for the successor's product whose `status` is `QUALIFIED` or `CONDITIONAL` is re-evaluated in ascending `created_at` order, and for each one the server adds the successor's `cumulative_dose_kgy` to the `target_dose_kgy` of that qualification's recipe and rounds the sum half up to two decimal places; where that figure exceeds the product's `max_cumulative_dose_kgy`, the qualification moves to `SUSPENDED` with `next_audit_due_at` set to null and the successor's `schedulable` flag is cleared to false. A successor whose dose history leaves no headroom under any recipe therefore arrives pre-blocked, and a later load-position attempt against it is refused with `ERR_LOT_NOT_SCHEDULABLE`.

## 4. Endpoint Definitions

Operations that mint a new resource — registering a customer, a product, a permit, a chamber, a recipe, a qualification, a dose audit, a lot, a cycle, a load-map slot, an indicator or an aeration record — return `201 Created`. Removing a load-map slot returns `204 No Content` with no response body.
