# PRD Bench Unit Test Generator

Generate a **complete, rigorous Python unit test suite** that validates whether an API implementation
faithfully satisfies every requirement in a given PRD.

## Input

A single **working directory** containing:
- **`*.yaml`** — the scaffold (entities, state machines, calculations, validations, endpoints, errors, RBAC)
- **`*.md`** — the PRD document generated from that scaffold

The skill reads both files from this directory, then creates `test_helpers/` and `test_suite/`
as subdirectories under it. All generated code uses **relative imports** within this directory.

```
{working_dir}/                     # ← input directory (provided by user)
├── scaffold.yaml                  #    input: scaffold
├── prd.md                         #    input: PRD
├── test_helpers/                  #    output: generated by Stage 1
│   └── ...
└── test_suite/                    #    output: generated by Stage 2
    └── ...
```

See `references/example-test-patterns.md` for concrete Python code patterns.

## Responsibility Boundary

This skill generates **test code only**. It does not handle server lifecycle, test execution,
or result collection — those are the `prd-bench-local-runner` framework's job.

| Concern | Owner | Details |
|---|---|---|
| Server start/stop | `prd-bench-local-runner` | Spawn subprocess, poll readiness, SIGTERM on exit |
| Crash recovery | `prd-bench-local-runner` | Per-test liveness check via pytest plugin |
| `API_BASE_URL` injection | `prd-bench-local-runner` | Set as env var before pytest subprocess |
| `PYTHONPATH` setup | `prd-bench-local-runner` | Ensures `test_helpers` and framework are importable |
| Test execution | `prd-bench-local-runner` | Invokes `pytest` with JUnit XML output |
| Result collection | `prd-bench-local-runner` | Parses JUnit XML → structured JSON |
| **test_helpers/** | **this skill** | PRD-specific: types, api client, factories, assertions, fixtures |
| **test_suite/** | **this skill** | Claim-driven test files |

**The generated tests assume the server is already running and reachable at `API_BASE_URL`.**
They never start, stop, or health-check the server — that's the runner's guarantee.

### Framework API Quick Reference

**CRITICAL: Use these exact signatures. Do NOT guess parameters.**

```python
# --- Validators (from prd_bench_local_runner.testing) ---

validate_success(response, expected_status=200) -> dict
# Returns the data payload. Asserts status code and envelope structure.

validate_error(response, expected_error_id, expected_status=None) -> dict
# Returns error_data dict. If set_error_http_status_map() was called, HTTP status
# is auto-checked from the map (no need to pass expected_status explicitly).

validate_error_is_one_of(response, acceptable_error_ids: list) -> str
# For race condition tests where multiple error outcomes are valid.
# Returns the actual error_id string. Does NOT check HTTP status.

validate_paginated(response) -> tuple[list, dict]
# Returns (data_list, meta_dict). Takes ONLY the response — no status code argument.
# meta_dict contains: total_count, has_more, limit, offset.
# Usage: data, meta = validate_paginated(resp)

get_success_data(response) -> dict
# Lenient validator — accepts any 2xx status. Use in fixtures.py for setup calls.

# --- Error registration (NOT exported from top-level package) ---

from prd_bench_local_runner.testing.validators import set_error_http_status_map
set_error_http_status_map(mapping: dict) -> None
# Registers error_id → HTTP status mapping. Call once at import time in api_errors.py.

# --- Race condition utilities (from prd_bench_local_runner.testing) ---

run_race(*operations) -> list[Response]
# Takes VARARGS of zero-arg callables (NOT a list). Each callable returns Response.
# Usage: results = run_race(lambda: api.foo(...), lambda: api.bar(...))
# Returns list of Response objects in completion order (not submission order).

assert_race_outcome(results: list, expected_successes: int, expected_failures: int) -> dict
# Counts 2xx as successes, 4xx+ as failures. Returns {"successes": [...], "failures": [...]}.

assert_exactly_one_succeeds(result_a, result_b) -> dict
# Shortcut for assert_race_outcome([result_a, result_b], 1, 1).

assert_at_least_one_succeeds(*results) -> dict
# Asserts at least one result is 2xx.
```

## Testing Philosophy

The test suite answers: "Does the implementation correctly handle requirement X?" for every X
in the PRD. The organizing principle is **testable claims**, not code structure.

### Core Principles

1. **Claim Extraction** — Before writing any test, enumerate every testable claim the scaffold
   makes. A testable claim is any statement with a verifiable true/false answer against a
   running API. Every claim gets at least one test.

2. **Boundary Precision** — For every numeric threshold or inequality, test the exact boundary.
   "Exceeds X" → test X-1, X, X+1. The scaffold's `constants` and the PRD's wording together
   determine exact semantics.

3. **Side Effects as First-Class Citizens** — When the scaffold says a transition has side effects,
   every side effect is a testable claim.

4. **Error ID Specificity** — Assert the exact `error_id` string, not just the HTTP status code.

5. **Data Isolation** — Every test creates its own entities. No shared mutable state between tests.

6. **Domain Language** — Name files, classes, and functions using the PRD's domain terminology.

This stage generates **only PRD-specific code** — types, endpoint methods, entity assertions,

### 1.2 `api_client.py` — PRD-Specific Endpoint Methods

**Subclass** `GenericApiClient` from the framework. Only generate the endpoint methods
(one per row in Table 5). The base `_request()` method is inherited.

```python
"""API client: one method per endpoint from scaffold Table 5."""
from prd_bench_local_runner.testing import GenericApiClient

class ApiClient(GenericApiClient):
    # Generate one method per endpoint:
    def create_{entity}(self, payload, headers):
        return self._request("POST", "/{entities}", payload, headers)
    def get_{entity}(self, entity_id, headers):
        return self._request("GET", f"/{entities}/{entity_id}", headers=headers)
    def list_{entities}(self, headers, params=None):
        return self._request("GET", "/{entities}", headers=headers, params=params)
    def activate_{entity}(self, entity_id, headers):
        return self._request("POST", f"/{entities}/{entity_id}/activate", headers=headers)
    # ... etc

api_client = ApiClient()
```

### 1.4 `assertions.py` — PRD-Specific Entity Assertions

Generate `assert_{entity}(data)` for each entity using the framework's generic validators
(`is_valid_uuid`, `is_iso8601_timestamp`) internally. Also generate domain-specific invariant
checkers (e.g., `assert_plan_invariants`) using `assert_cost_precision` from the framework.

```python
"""Entity assertions and domain invariant checkers."""
import pytest
from prd_bench_local_runner.testing import (
    is_valid_uuid, is_iso8601_timestamp, assert_cost_precision,
)

def assert_{entity}(data: dict):
    assert is_valid_uuid(data.get("id", "")), "id must be valid UUID"
    assert is_iso8601_timestamp(data.get("created_at", "")), "created_at must be ISO 8601"
    assert isinstance(data["field_a"], str) and len(data["field_a"]) > 0
    assert data["status"] in ["STATE_A", "STATE_B", "STATE_C"]
    # ... all fields from Table 1

def assert_{parent}_invariants(data: dict):
    """Domain invariants that must hold after any operation."""
    assert data["cost_balance"] >= 0
    assert data["cost_balance"] <= data["total_budget"]
    assert_cost_precision(data["cost_balance"])
    assert data["safety_score"] >= 0
```

### 1.8 `fixtures.py` — Composite Setup Helpers

This is the **most important and most substantial** file in `test_helpers/`. It encapsulates
multi-step setup sequences so tests can focus on assertions, not plumbing. It is normal and
expected for this file to be large (500–1000+ lines for complex PRDs).

The reason fixtures matter so much: **most interesting test claims require the system to be
in a specific state that takes 5–15 API calls to reach.** A test for "bio-risk threshold at
6000 minutes" cannot just create one entity — it must create a plan, activate it, create a
rotation, create a resource with known cost, create a procedure spanning 5980 minutes, create
an assignment, approve it, schedule it, and THEN create the 100-minute procedure under test.
Without fixtures, every test would repeat this 9-step preamble.

#### How to identify which fixtures to generate

Walk through each test claim from Phase 2.1. For each claim, ask: "What state must the system
be in before I can test this?" Count the API calls needed to reach that state. If ≥3 claims
share the same multi-step preamble, extract it into a fixture.

#### Fixture tiers (generate all tiers that apply to this scaffold)

**Tier 1: State Progression** — for any entity with a state machine where the testable
state is not the initial state.

```python
def create_and_activate_{parent}(budget=250_000.00, name="Test Plan"):
    """Create parent + transition to ACTIVE. Returns activated entity."""

def create_entity_in_state(entity_type, target_state, **kwargs):
    """Walk the state machine to reach target_state. For parametrized tests."""
```

**Tier 2: Entity Hierarchy** — for any PRD with parent-child relationships where tests
need a pre-built hierarchy.

```python
def setup_{parent}_with_{child}_and_{resource}(**overrides):
    """Active parent + one child + one resource. Returns (parent, child, resource)."""

def setup_basic_scenario():
    """Active parent + child + resource + one procedure. Most common setup."""
```

**Tier 3: Full Lifecycle Shortcuts** — for any entity with multi-step lifecycles (create →
approve → schedule → etc.) where tests need the entity in a late lifecycle stage.

```python
def create_and_schedule_assignment(parent_id, proc_id, resource_id):
    """Create → approve → schedule. Returns scheduled assignment."""

def create_scheduled_assignment(parent_id, child_id, resource_id, proc_overrides=None):
    """Create procedure + assignment, walk through to SCHEDULED. Returns both."""
```

**Tier 4: Accumulation / Threshold Targeting** — for any calculation with thresholds or
accumulating values. These are critical because testing boundary precision requires the
system to be at an exact cumulative state.

```python
def setup_with_cumulative_usage(minutes_used, cost_per_minute=1.0):
    """
    Create a plan where a resource already has `minutes_used` of SCHEDULED time.
    Used for boundary tests: set minutes_used=THRESHOLD-20, then test at boundary.
    Internally: creates plan → activates → creates rotation → creates resource →
    creates one large procedure → assigns → approves → schedules.
    """

def setup_and_raise_score(target_score, plan_budget=200_000):
    """
    Create a plan and accumulate safety score to `target_score` by creating
    N bio-risk assignments. Each bio-risk assignment adds +50 to score.
    If score would breach 500, uses override_flag (+100 penalty).
    Internally: creates base procedure (5950 min) to enter bio-risk zone,
    then loops creating bio-risk procedures until target_score is reached.
    """

def create_bulk_scored_assignments(parent_id, child_id, resource_ids,
                                    target_score, **options):
    """Create N assignments until cumulative score reaches target. Returns assignments."""
```

**Tier 5: Finalization / Terminal State** — for any PRD with a finalization lifecycle.

```python
def setup_finalization_ready(num_assignments=3, budget=10_000):
    """
    Full setup through to FINAL_REVIEW_PENDING state:
    plan → activate → rotation → resource → N scheduled assignments →
    transition rotation to READY → initiate final review.
    Returns (plan, rotation, resource, assignments, procedures).
    """

def setup_finalized_plan(budget=1_000):
    """Full lifecycle through COMPLETED. For post-finalization lockdown tests."""
```

**Tier 6: Concurrency / Race Condition** — pre-configured setups that produce the exact
conditions needed for race tests.

```python
def setup_race_test_scenario(include_scheduled=True):
    """
    Setup plan with entities in states suitable for concurrent operations.
    Returns all entity IDs needed for race condition tests.
    """
```

#### Key design principle for fixtures

Every fixture should accept `**overrides` for the values that tests need to control. A
threshold test needs to control `minutes_used` and `cost_per_minute`. A budget test needs
to control `budget`. A certification test needs to control which certs exist. The fixture
provides sensible defaults for everything else.

Fixtures use `get_success_data()` (lenient validator) internally, not `validate_success()`,
so setup failures produce clear "Setup failed" errors instead of confusing assertion failures.

## Stage 2: Generate `test_suite/` (AFTER Stage 1 is complete)

**Stage 2 MUST NOT begin until Stage 1 is fully written to disk.** Before writing any test
file, read back the generated `test_helpers/` code to know the exact:
- `ApiClient` method names and signatures (from `api_client.py`)
- Fixture function signatures and return types (from `fixtures.py`)
- Exported names (from `__init__.py`)
- Error ID constants (from `api_errors.py`)
- Factory function names and parameters (from `factories.py`)
- Assertion function signatures (from `assertions.py`)

This eliminates the most common generation bug: test_suite guessing test_helpers' interface
instead of reading it. Tests import everything from `test_helpers` and focus purely on test logic.

### 2.0 `conftest.py` — Pytest Fixture Bridge

Thin file that exposes `test_helpers` as pytest fixtures. The runner handles `PYTHONPATH`
so `test_helpers` is importable without `sys.path` hacks.

```python
"""Pytest fixtures exposing test_helpers infrastructure."""
import pytest
from test_helpers import api_client, ApiClient, TEST_USERS

@pytest.fixture(scope="session")
def api() -> ApiClient:
    """Session-scoped API client. Server lifecycle managed by prd-bench-local-runner."""
    return api_client

# One fixture per role from TEST_USERS:
@pytest.fixture
def role_a_headers():
    return TEST_USERS["role_a_headers"]

# ... one per role
```

### 2.1 Extract Every Testable Claim

Walk through each scaffold table systematically. For every structural element, ask: "What can go
right? What can go wrong? What are the boundaries?" Record each answer as a testable claim.

See `references/claim-extraction-guide.md` for the comprehensive extraction tables covering
all entity topologies, state machine shapes, calculation algorithm types, validation patterns,
RBAC role models, and cross-cutting complexity layers.

### 2.2 Organize Claims into Test Files

Cluster claims into coherent test files:

1. **Group by testing concern, not scaffold table.** A state transition claim and its
   side-effect-on-ledger claim belong together in a "workflows" file.

2. **One file per concern with ≥5 tests.** Smaller concerns fold into the nearest related file.

3. **Name files in domain language.** Prefer `test_booking_conflicts.py` over `test_constraints.py`.

4. **Number for reading order** (`test_01_`, `test_02_`, ...) from simple to complex.

A Starter PRD might produce 3–4 test files. An Expert PRD might produce 10–15.

### 2.3 Generate Test Files

For each file, generate all test functions. Every test function must:
- Have a descriptive name using domain language: `test_{what}_{scenario}`
- Include a docstring citing the scaffold table and claim it validates
- Create its own entities via `test_helpers` factories and fixtures
- Assert the direct result AND every side effect via `test_helpers` assertion helpers

**Patterns to apply:**
- `@pytest.mark.parametrize` for families (invalid transitions, SQL payloads, missing fields, unauthorized roles)
- `pytest.approx(expected, abs=0.01)` for decimal precision
- `concurrent.futures.ThreadPoolExecutor` for concurrency tests
- `class TestXxx:` for grouping related tests within a file

See `references/example-test-patterns.md` §2.1–2.10 for concrete test patterns covering CRUD,
state machines, constraints, calculations, cascades, finalization, edge cases, security,
concurrency, and end-to-end integration.

## Generation Quality Rules

These rules apply regardless of generation approach. They address code quality issues that
cannot be caught by reading test_helpers code — they require understanding of the PRD itself.

### Field names are PRD-exact — never abbreviated

```python
# WRONG — abbreviated or guessed
product["price"]              # PRD says "base_price"
promo.get("value")            # PRD says "promo_value"
settlement["commission_amount"]  # PRD says "total_commission"

# RIGHT — exact PRD field names in both test_helpers AND test_suite
product["base_price"]
promo.get("promo_value")
settlement["total_commission"]
```

This applies to both layers: test_helpers (factories, assertions, api_client) and test_suite.

### Required vs optional fields follow the PRD

Before parametrizing `test_missing_required_field`, check each field in the PRD:
- `required: false` or has a `default` → optional, do NOT test as required
- All other `source: input` fields → required, test omission

## Code Style

- **pytest** (not `unittest.TestCase`). Module-level functions or `class TestXxx:` groupings.
- `pytest.fixture` for setup. Session-scoped for API client, function-scoped for data.
- Descriptive assertion messages: `assert x == y, f"Expected {y}, got {x} after {action}"`
- No mocking — tests hit the real API. These are integration-level PRD compliance tests.
- Each test is independent. No ordering dependencies.
- All imports from `test_helpers`, not inline infrastructure in test files.

## Completeness Check

After generating both layers, verify:

1. **Every error in Table 6** has at least one test that triggers it.
2. **Every state transition in Table 2** has a valid-path test and an invalid-from-wrong-state test.
3. **Every calculation in Table 3** has at least one boundary test.
4. **Every side effect in Table 2 and Table 5** has a test that verifies it was applied.
5. **Every RBAC exclusive operation** has a negative test (wrong role → ERR_UNAUTHORIZED).
6. **Every complexity layer** in `complexity_profile.complexity_layers` has dedicated test coverage.

If any gap is found, add the missing tests to the most appropriate test file.
