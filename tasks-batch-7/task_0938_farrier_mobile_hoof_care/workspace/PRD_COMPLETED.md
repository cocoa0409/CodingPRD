# Farrier & Mobile Hoof-Care API — Product Requirements Document

## 1. Introduction

Mobile hoof care is a business of small, repeating promises. A horse is trimmed or shod every six to eight weeks; a farrier drives a van full of steel, aluminium and composite shoes between yards; a barn opens its gate at a certain hour and closes it again; and an owner expects to be told, twice, before anyone turns up. When a horse goes lame the routine stops dead and a veterinarian's therapeutic prescription takes over the calendar. None of this is difficult in isolation. It becomes difficult because every one of those promises is metered — a van either has the pairs or it does not, a day either has the minutes or it does not, a certification either covers corrective work or it does not — and because the money follows the limb rather than the horse.

This document specifies the server that runs that business. The unit of work is not a visit but a **limb**: a single appointment decomposes into up to four service lines, one per hoof (`LF`, `RF`, `LH`, `RH`), and price, shoeing-unit load, chair minutes, stock draw and validation are all roll-ups over those lines rather than per-horse scalars. A route is metered in **two independent units** — shoeing units and minutes — and either meter alone is enough to refuse a horse. Cycle length has two competing sources, the horse's routine profile and a live therapeutic prescription, and the prescription wins unconditionally while it lives. A stop's trip fee attaches to the stop and is then split across the horses actually billed there, with a deterministic remainder rule so that the cents always add back up.

The specification is written for an implementer who has never seen the yard. Everything that a request may be refused for is stated, and stated in a fixed order of precedence, because in this domain two refusals are almost always simultaneously true and the caller needs the same answer every time. Five ordered write gates sit in front of every domain rule; four optimistic-concurrency checks sit in front of the gates; and a ladder of fifty-three rungs governs the whole. Read §2 for the contract, §3 for the business narrative, §4 for the HTTP surface and §5 for the error catalogue.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operators, Roles and Identity

Every request to this API — without exception, including read-only requests — must carry two headers: `X-User-ID` and `X-User-Role`. If either header is absent, or if `X-User-Role` carries a string that is not one of the six roles named below, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role does not appear in the authorized-role set of the endpoint being called, the request is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403). These two checks sit at the very top of the rejection ladder and run before anything else, including before the server looks up any resource id.

The six roles are peers rather than a hierarchy. They are, spelled exactly:

- **`PlatformAdmin`** — sets up the reference data: barns, farriers, shoe SKUs, rate cards, stock adjustments and the logical clock.
- **`Dispatcher`** — builds routes, places stops, attaches horses to stops and drives reminder delivery.
- **`Farrier`** — works the route: arrives, starts, completes and records no-shows.
- **`ClientUser`** — the horse owner: creates and retires horses, books and cancels visits, reports lameness and acknowledges reminders.
- **`Veterinarian`** — issues, activates, revokes and withdraws therapeutic prescriptions, and closes or reopens lameness cases.
- **`BillingClerk`** — handles deposits, payments and the invoice lifecycle.

Two of the six are **entity-backed**, and for those two `X-User-ID` is a real row id that ownership is compared against. When `X-User-Role` is `Farrier`, `X-User-ID` is the `id` of the acting `Farrier` row; ownership checks on any `Route`, `RouteStop` or `Appointment` compare the `farrier_id` of the governing route to `X-User-ID`. When `X-User-Role` is `ClientUser`, `X-User-ID` is the `id` of the acting `Client` row; ownership checks compare the resource's owning client — directly for a `Client`, through `client_id` for a `Horse`, through the horse for an `Appointment`, and through `client_id` for an `Invoice` — to `X-User-ID`. A mismatch is refused with `ERR_NOT_RESOURCE_OWNER` (HTTP 403), and this ownership rung sits immediately below the role check and above every existence check **wherever the identity to compare against is already in hand — the `{id}` of `GET /clients/{id}`, and the `client_id` supplied in a horse-creation body — the raw body value is compared as it stands, so a `ClientUser` creating a horse without a `client_id` at all, or with one that is not a string, is refused with `ERR_NOT_RESOURCE_OWNER` before the shape rung is ever reached. Everywhere else the owning identity can only be read off the resource itself, so that resource's existence rung runs first and a nonexistent id reports its own `*_NOT_FOUND` code rather than this one: `GET /horses/{id}` on an unknown id reports `ERR_HORSE_NOT_FOUND` even to a `ClientUser`, while `GET /clients/{id}` on an unknown id reports `ERR_NOT_RESOURCE_OWNER`. The rung is further confined to single-resource operations: no list endpoint narrows or refuses by ownership — `GET /horses`, `GET /appointments`, `GET /invoices`, `GET /reminders` and every other collection return every row matching the declared filters to any authorized role, so `ERR_NOT_RESOURCE_OWNER` is unreachable on them however §4.1 lists it. And the `Farrier` half of the rung is skipped whenever the resource has no governing route at all: a `Farrier` may read an `UNROUTED` appointment, or a service line of one, whoever it belongs to, because there is no `farrier_id` to compare.**

The remaining four roles are **opaque**. When `X-User-Role` is `PlatformAdmin`, `Dispatcher`, `Veterinarian` or `BillingClerk`, `X-User-ID` is an operator identifier that is not tied to any persisted entity; the server may record it but never compares it to any row's `id`, and `ERR_NOT_RESOURCE_OWNER` is therefore unreachable for those four roles.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources. "array" is carried by the list endpoints — the ones that also carry the four pagination keys. The one operation that returns several rows without being a list endpoint, the service-line addition of §3.5, returns `response_type` "object" with an array in `data` and a `meta` holding only `api_request_id` and `api_request_timestamp`.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Ordering and Filtering

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 (`DEFAULT_PAGE_LIMIT`), may not be smaller than 1 (`MIN_PAGE_LIMIT`) and may not be larger than 100 (`MAX_PAGE_LIMIT`); a value outside that closed range is refused with `ERR_VALUE_OUT_OF_RANGE` (HTTP 422). `offset` defaults to 0 and may not be negative; a negative offset is refused with the same code. Both are read from the query string, and the pagination rung applies to every list endpoint in the system.

For list responses the `meta` object carries `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of rows matching the filters **before** `limit` and `offset` are applied, and `has_more` is true exactly when the sum of `offset` and the number of rows actually returned is strictly less than `total_count`.

Ordering is uniform: every list endpoint returns its rows ordered by `created_at` ascending, and rows minted inside a single request tie-break in the order they were minted. The `id` field is never a sort key. Exactly one endpoint departs from this rule and says so in its own description — the per-horse limb listing, which always returns its four rows in the fixed anatomical order `LF`, `RF`, `LH`, `RH`.

Filters are exact-match and conjunctive: when a list endpoint declares an optional filter parameter, supplying it narrows the result set to rows whose corresponding field equals the supplied value, and supplying several narrows by all of them at once. The comparison is textual: the stored value is rendered as a string (a boolean as `true` or `false`, a null as no match at all) and compared byte for byte with the raw query-string value. Omitting a filter never narrows anything. A filter naming an id that matches no row is not an error — it simply yields an empty page with `total_count` zero — and neither is a filter carrying a value outside the enum it names: no filter ever routes to `ERR_INVALID_ENUM`, it simply matches nothing. `limit` and `offset` are validated rather than clamped, and a value that is not an integer at all is `ERR_VALUE_OUT_OF_RANGE` exactly as an out-of-band integer is. `total_count` counts the rows surviving the filters, so on the two listings that carry their own non-pagination filter — the per-horse limb listing's `limb` and the invoice-line listing's `line_kind` — the filter is applied to the fully ordered set before the page is cut and `total_count` reports the filtered size.
### 2.4. Common Resource Properties, Versioning and the Logical Clock

Every persisted resource carries a server-minted `id`: a UUID string with no type prefix and no embedded meaning. Clients never supply an `id`; a client-supplied `id` in a request body is ignored. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits and a trailing `Z`.

All but one entity additionally carry `updated_at` (same format as `created_at`, refreshed on every mutation of that row) and `version`, an integer that starts at 1 when the row is minted and increases by exactly 1 on every mutation of that row. The sole exception is `InvoiceLine`: an invoice line is immutable once written, so it carries only `id` and `created_at` — it has neither `updated_at` nor `version`, and an implementation must not emit those two keys on an invoice line.

`version` counts **mutations of the row**, not requests. A single request that touches a row twice — for example a completion that both moves an appointment to `COMPLETED` and then re-derives its billing axis — advances that row's `version` once per declared mutation step, and the side-effect lists throughout §3 name each increment individually. Concretely: a visit completion advances the appointment **twice** (the status step, then the `billing_status` step); so do a `LATE` cancellation, an `ONSITE` cancellation and a no-show; an `ADVANCE` cancellation advances it once, because it mints no invoice. The counterpart rule is that a row whose recomputed values do not actually move is **not** a mutated row and does not advance: a `Route` whose `committed_units`, `committed_minutes` and `stop_count` all come back unchanged from a recomputation keeps its `version`, and so does a `RouteStop` whose recomputed `service_minutes` and `end_minute` are unchanged. Attaching an appointment that carries no service lines therefore leaves both the route's and the stop's `version` exactly where they were, and the next attachment still passes the route version the caller already holds.

`created_at`, `updated_at` and `api_request_timestamp` are all minted from the logical clock below, never from the host clock, so every row written while the clock stands still shares one `created_at` to the millisecond and the mint-order tie-break of §2.3 is what separates them. Three renderings coexist and never mix. Server-minted instants are rendered `YYYY-MM-DDTHH:MM:SS.mmmZ` with exactly three fractional digits. A caller-supplied string is echoed **byte-verbatim** and never re-rendered — `POST /_clock/set_current_utc` returns in `current_utc` precisely the `to_iso8601` it was given, so an input of `2026-07-01T09:15:00.5Z` comes back as `2026-07-01T09:15:00.5Z`, and every caller-supplied date field (`scheduled_date`, `route_date`, `cert_expires_on`, `effective_from`, …) is stored and returned as received. A derived value renders in the style of the source it was derived from, and every derived value here is derived from an ISO calendar date, so `next_due_on`, `due_on`, `completed_on`, `issued_on`, `sent_on` and `last_serviced_on` all render as `YYYY-MM-DD`.

Time in this system is a **logical clock**, never the host's wall clock. Before any operator sets it, the clock reads exactly `2026-05-01T00:00:00Z` (`DEFAULT_CLOCK_UTC`), and it never falls back to real time. A `PlatformAdmin` moves it with a test-driving capability that takes a single field, `to_iso8601`, and returns an object rather than an entity: `current_utc` (the new clock value as an ISO 8601 string), `expired_prescription_ids` (the ids of prescriptions this move pushed into `EXPIRED`, ordered by their `created_at` ascending) and `restanding_client_ids` (the ids of clients whose `billing_standing` this move changed, ordered by their `created_at` ascending). Everywhere this document says "the logical clock date" it means the calendar date of that instant in UTC.

Date arithmetic is calendar arithmetic. "N weeks after date D" means D plus N times 7 (`DAYS_PER_WEEK`) calendar days. A difference in "lead days" between two ISO dates is the whole-calendar-day difference of the later minus the earlier, never a count of wall-clock hours. The weekday token of an ISO date is taken from the proleptic Gregorian calendar with `MON` at index 0 through `SUN` at index 6, so that 2026-05-04 is `MON`. A minute-of-day is an integer in the half-open range from 0 up to but not including 1440 (`MINUTES_PER_DAY`).

Nested paths are resolved strictly left to right. When a path names a parent and then a child, the parent's existence is checked and reported first; only if the parent resolves does the server look for the child; and only if the child resolves does any state or business rule run. A child that exists but belongs to a different parent is treated as not found for that path.

### 2.5. Money, Basis Points and Rounding Discipline

All money in this system is **integer cents**. No amount is ever stored or returned as a decimal fraction, and no response field carries a currency symbol.

Percentages are expressed in **basis points** against a denominator of 10000 (`BASIS_POINT_DENOMINATOR`). A rate of 1250 basis points is therefore 12.5 percent, a rate of 725 basis points is 7.25 percent, and a rate of 0 basis points contributes nothing. Wherever a basis-point rate is applied, the arithmetic is: multiply the base amount by the rate, divide by 10000, and round the exact rational result **half up** — that is, take the largest integer not greater than the value plus one half, for non-negative values. Half-up is the only rounding mode in this specification; no step ever truncates, rounds half-even, or rounds toward zero.

Rounding **order** is pinned and is not a free choice. Where a per-line amount is rounded, each line is rounded on its own and the rounded line amounts are then summed; summing the unrounded bases and rounding one combined figure is a different and incorrect answer. Where a whole-invoice amount is rounded, the rounding happens once at that step and the already-rounded result is carried forward without ever being re-rounded. §3.9 names, step by step, which figures are rounded per line and which are rounded on a total.

Two non-money quantities also round, and they round differently. Shoe pairs round **up**: a requirement of three shoes of one SKU is a requirement of two pairs, because shoes leave stock in left/right pairs of 2 (`SHOES_PER_PAIR`). Handling minutes under sedation round **half up** like money. Nothing else rounds at all — shoeing units, chair minutes per limb, travel minutes and route totals are integers by construction.

### 2.6. The Five Ordered Write Gates

Before any domain rule of a write endpoint is evaluated, up to five **gates** run in a fixed order. The first gate that fails decides the error, and no later gate — and no domain rule below them — is consulted. The gates are deliberately ordered so that the most fundamental refusal wins: a decertified farrier's dispatched route reports the farrier problem, not the route problem.

**Gate 1 — the farrier may work at all.** The `Farrier` that owns the `Route` in scope must have `status` `ACTIVE`, and that farrier's `cert_expires_on` must be on or after the logical clock date. The gate is really two rungs in sequence: an `INACTIVE` or `DECERTIFIED` farrier yields `ERR_FARRIER_INACTIVE` (HTTP 409), and only if the status is `ACTIVE` does the server look at the certificate, a lapsed one yielding `ERR_FARRIER_CERT_EXPIRED` (HTTP 409). Gate 1 guards twelve operations: route creation, route planning, route dispatch, stop insertion, stop reordering, appointment attachment, appointment detachment, stop arrival, stop completion, appointment start, appointment completion and no-show recording. For route creation the farrier in scope is the one named by `farrier_id` in the body; everywhere else it is the farrier of the route that owns the stop or appointment being acted on.

**Gate 2 — the route is still open.** `Route.status` must be `DRAFT` or `PLANNED`. A route that is `DISPATCHED`, `CLOSED` or `CANCELLED` no longer accepts structural change, and the refusal is `ERR_ROUTE_NOT_OPEN` (HTTP 409). Gate 2 guards exactly four operations: stop insertion, stop reordering, appointment attachment and appointment detachment. It deliberately sits **after** gate 1, so that a dispatched route belonging to a lapsed farrier reports the farrier codes rather than this one.

**Gate 3 — the client may be booked.** The `Client` that owns the horse in scope must have `billing_standing` `ACTIVE`, or `PREPAY_REQUIRED` together with a `deposit_balance_cents` of at least 10000 (`PREPAY_DEPOSIT_MIN_CENTS`). A `SUSPENDED` client never passes, whatever deposit is held. The refusal is `ERR_CLIENT_PREPAY_REQUIRED` (HTTP 402). Gate 3 guards exactly three operations: appointment creation, appointment attachment and warranty-revisit creation.

**Gate 4 — the horse is not on hold.** `Horse.hold_status` must be `CLEAR`; alternatively the horse may pass while on `HOLD` if every `ServiceLine` already on the appointment in scope has `service_type` `CORRECTIVE` under a prescription that is live and whose `limb_scope` covers that line's `limb`. The refusal is `ERR_HORSE_ON_HOLD` (HTTP 409). Gate 4 guards exactly four operations: appointment creation, appointment attachment, service-line addition and appointment start. A horse on lameness hold may still receive corrective work under a live prescription; routine trims are refused.

**Gate 5 — the appointment is in an eligible status.** `Appointment.status` must be inside the eligible set the endpoint declares, and the refusal is `ERR_APPOINTMENT_NOT_ELIGIBLE` (HTTP 409). Gate 5 guards eleven operations, with these eligible sets: service-line addition and service-line removal accept `UNROUTED`, `SCHEDULED` and `CONFIRMED`; attachment accepts only `UNROUTED`; detachment accepts `SCHEDULED` and `CONFIRMED`; start accepts `SCHEDULED` and `CONFIRMED`; completion accepts only `IN_PROGRESS`; cancellation accepts `UNROUTED`, `SCHEDULED` and `CONFIRMED`; no-show accepts `SCHEDULED` and `CONFIRMED`; warranty-revisit creation accepts only `COMPLETED` on the origin visit; reminder sending accepts `SCHEDULED` and `CONFIRMED` on the reminder's appointment; and reminder acknowledgement accepts `SCHEDULED` and `CONFIRMED` on the reminder's appointment. Gate 5 is last of the five, so a `BLOCKED` appointment sitting on a dispatched route reports `ERR_ROUTE_NOT_OPEN` rather than this code.

> **Gate 4 on a brand-new appointment.** Creating an appointment for a horse whose `hold_status` is `HOLD` is **refused** with `ERR_HORSE_ON_HOLD`. The escape clause is not satisfied vacuously by the empty service-line set of a freshly minted visit: with no corrective line yet named the booking is routine, and a horse on hold is not to be booked for routine work. The escape clause therefore only ever admits a horse that is already carrying lines — which is why gate 4 lets an attachment, a further line addition or a start through when every line already on the visit is `CORRECTIVE` under a prescription live on the appointment's `scheduled_date` whose `limb_scope` covers that line's `limb`. Warranty-revisit creation does **not** sit behind gate 4 at all: its gate list is gate 3 and gate 5 only, so a warranty revisit may be opened for a horse on hold.

> **Gate 5 on reminder acknowledgement.** The eligible set for reminder acknowledgement is `SCHEDULED` **and** `CONFIRMED`. Acknowledging while the appointment is already `CONFIRMED` succeeds and moves only the reminder, because the appointment transition of §3.8 is conditioned on the appointment being `SCHEDULED` and is simply skipped otherwise; a second acknowledgement — of the sibling reminder, say — is therefore not a refusal. `ERR_APPOINTMENT_NOT_ELIGIBLE` remains reachable on acknowledgement through a `BLOCKED`, `UNROUTED`, completed or cancelled appointment.

### 2.7. The Rejection Ladder — Full Priority Order

Every refusal in this system comes from one of fifty-three ordered rungs. When more than one rung would fire for a single request, the **lowest-numbered rung wins** and its code is returned; later rungs are not evaluated and their side conditions are irrelevant. The order below is the complete ladder, and it is the same for every endpoint — an endpoint simply skips rungs that do not apply to it.

**Rungs 1–3, authentication and ownership.** (1) Headers present and the role recognised, else `ERR_UNAUTHENTICATED`. (2) The role appears in this endpoint's authorized set, else `ERR_FORBIDDEN_ROLE`. (3) Ownership for the two entity-backed roles — a `ClientUser` may act only on its own `Client` and on the horses, appointments and invoices belonging to it, and a `Farrier` may act only on a route, stop or appointment whose governing route has `farrier_id` equal to `X-User-ID` — else `ERR_NOT_RESOURCE_OWNER`. Rung 3 applies to every **single-resource** endpoint whose authorized set includes `ClientUser` or `Farrier` and whose target actually resolves to an owner; it never applies to a list endpoint, and its `Farrier` half is inert on a resource with no governing route, exactly as §2.1 sets out.

**Rungs 4–20, existence.** These run in a fixed sequence, and they run **before** any payload-shape check, so a request that names a nonexistent id and also omits a required field reports the existence code. In order: (4) `Barn` — `ERR_BARN_NOT_FOUND`, on barn read, client creation, horse creation and stop insertion. (5) `Client` — `ERR_CLIENT_NOT_FOUND`, on client read, deposit posting, payment application and horse creation. (6) `Horse` — `ERR_HORSE_NOT_FOUND`, on horse read, horse patch, retire, reinstate, limb-state listing, appointment creation and lameness-case creation. (7) `Farrier` — `ERR_FARRIER_NOT_FOUND`, on farrier read, deactivate, reactivate, recertify and route creation. (8) `ShoeSku` — `ERR_SKU_NOT_FOUND`, on SKU read, service-line addition and transfer request. (9) `InventoryBucket` — `ERR_BUCKET_NOT_FOUND`, on bucket read, bucket adjustment and transfer request. (10) `StockTransfer` — `ERR_TRANSFER_NOT_FOUND`, on transfer read, dispatch, receive and abort. (11) `ShoeReservation` — `ERR_RESERVATION_NOT_FOUND`, on reservation read. (12) `RateCard` — `ERR_RATE_CARD_NOT_FOUND`, on card read, card activation and card creation naming a `supersedes_rate_card_id`. (13) `Route` — `ERR_ROUTE_NOT_FOUND`, on route read, plan, dispatch, close, cancel and stop insertion. (14) `RouteStop` — `ERR_ROUTE_STOP_NOT_FOUND`, on stop read, reorder, arrive, complete, attach and detach. (15) `Appointment` — `ERR_APPOINTMENT_NOT_FOUND`, on appointment read, service-line addition, start, complete, cancel, no-show, warranty-revisit, attach and detach; a detach naming an appointment that is not attached to that stop also reports this code. (16) `ServiceLine` — `ERR_SERVICE_LINE_NOT_FOUND`, on line read, line removal, and any id inside `performed_service_line_ids` at completion that is not a line of that appointment. (17) `LamenessCase` — `ERR_LAMENESS_CASE_NOT_FOUND`, on case read, resolve, reopen and prescription drafting. (18) `VetPrescription` — `ERR_PRESCRIPTION_NOT_FOUND`, on prescription read, activate, revoke and any `prescription_id` named on a service line. (19) `Invoice` — `ERR_INVOICE_NOT_FOUND`, on invoice read, invoice-line listing, issue and void. (20) `Reminder` — `ERR_REMINDER_NOT_FOUND`, on reminder read, send and acknowledge.

**Rungs 21–23, payload shape.** (21) Every field the endpoint declares as required is present and correctly typed; the `lines` array of a service-line addition is non-empty; and the declared field-combination rules hold — `sku_id` is present exactly when the `service_type` needs a shoe (`NEW_SHOES`, `CORRECTIVE`, `GLUE_ON`) and absent otherwise, `prescription_id` is present exactly when `service_type` is `CORRECTIVE` and absent otherwise, `with_pad` is false for `TRIM`, `RESET` and `GLUE_ON`, `limb_scope` and `served_weekdays` are non-empty and free of duplicates, and `warranty_reason` is present exactly when `visit_kind` is `WARRANTY_REVISIT`. Four further shape failures route here rather than anywhere else: a service line whose `limb_state_id` names no limb row, or names a limb row belonging to some other horse (there is no `LimbState` existence rung and no code for it); a `sku_code` that duplicates one already on file; a transfer whose `from_bucket_id` is not the `SHOP` bucket of the named SKU or whose `to_bucket_id` is not a `VAN` bucket of it; and a `lines` element that is not a JSON object. Any breach is `ERR_VALIDATION` (HTTP 400). This rung applies to every write endpoint. Inside the `lines` array the ladder outranks the index: **every** element is put through rung 21 in index order first, and only if all of them pass does **every** element go through rung 22 in index order, so an array whose first element carries an undeclared `service_type` and whose second omits a required `sku_id` reports `ERR_VALIDATION`, not `ERR_INVALID_ENUM`. (22) Every enum-valued field carries a declared member, else `ERR_INVALID_ENUM` (HTTP 422). **This routing list is exhaustive and closed:** `Barn.zone`, `ServiceLine.service_type`, `Appointment.visit_kind`, `Appointment.warranty_reason`, `Farrier.certification_level`, `ShoeSku.material`, `LimbState.limb`, the members of `VetPrescription.limb_scope`, the members of `Barn.served_weekdays`, the `reason` field of farrier deactivation, the `delivery_outcome` field of reminder sending and the `direction` field of stop reordering route here. No other field routes to `ERR_INVALID_ENUM`; a bad value in any other field is either a shape problem (rung 21) or a range problem (rung 23). Two members of that closed list are on it for completeness and are in fact **unreachable**: `Appointment.visit_kind` is never accepted as input by any endpoint, and `LimbState.limb` is a system field whose only caller-supplied appearance is the query filter of `GET /horses/{id}/limb-states`, and filters never route here. (23) Numeric and date ranges hold, else `ERR_VALUE_OUT_OF_RANGE` (HTTP 422) — `routine_cycle_weeks` between 6 and 8 inclusive, `prescribed_cycle_weeks` between 2 and 8 inclusive, `severity` between 1 and 5 inclusive, `quantity_pairs` between 1 and 40 inclusive, `amount_cents` strictly positive, `access_open_minute` strictly below `access_close_minute` with the open minute at least 0 and the close minute at most 1440, `planned_start_minute` at least 0 and strictly below 1440, `sequence_index` between 1 and the route's current `stop_count` plus one inclusive, the route's `stop_count` strictly below 8 before a stop is inserted, `expires_on` on or after `issued_on` and no more than 180 days after it, and the pagination `limit` between 1 and 100 inclusive. Five further bands route here: `opening_completed_visit_count` may not be negative, `price_cents_per_pair` may not be negative, `planned_start_minute` on a reorder obeys the same 0-to-below-1440 band as on an insertion, a `delta_pairs` that would drive a bucket's `on_hand_pairs` or `available_pairs` below zero is refused, and `offset` may not be negative. This rung applies to every write endpoint and to every list endpoint's pagination parameters.

**Rungs 24–27, optimistic concurrency.** (24) `expected_route_version` equals `Route.version` on attachment, else `ERR_STALE_ROUTE_VERSION` (HTTP 412). (25) `expected_appointment_version` equals `Appointment.version` on service-line addition, else `ERR_STALE_APPOINTMENT_VERSION` (HTTP 412). (26) `expected_lameness_case_version` equals `LamenessCase.version` on prescription activation, else `ERR_STALE_CASE_VERSION` (HTTP 412). (27) `expected_client_version` equals `Client.version` on payment application, else `ERR_STALE_CLIENT_VERSION` (HTTP 412). These four rungs sit **above** all five gates: a stale version is reported even when the farrier is inactive or the client is suspended, provided the payload itself was well formed.

**Rungs 28–33, the five gates.** (28) Gate 1a — `ERR_FARRIER_INACTIVE`. (29) Gate 1b — `ERR_FARRIER_CERT_EXPIRED`. (30) Gate 2 — `ERR_ROUTE_NOT_OPEN`. (31) Gate 3 — `ERR_CLIENT_PREPAY_REQUIRED`. (32) Gate 4 — `ERR_HORSE_ON_HOLD`. (33) Gate 5 — `ERR_APPOINTMENT_NOT_ELIGIBLE`. Their conditions and guard lists are in §2.6.

**Rung 34, every other state precondition.** The state precondition of the target transition must hold for every entity that is neither an `Appointment` (covered by gate 5) nor a `Route` in one of gate 2's four guarded operations. That covers `Horse.lifecycle_status`, `LamenessCase.status`, `VetPrescription.status`, `StockTransfer.status`, `RateCard.status`, `Invoice.status`, `Reminder.status` and `RouteStop.status`; it covers `Route.status` on planning, dispatching, closing and cancelling, none of which gate 2 guards; and by the same rule it covers `Farrier.status` on deactivation, reactivation and recertification and `ServiceLine.status` on line removal. The refusal is `ERR_INVALID_STATE` (HTTP 409) — a retired horse being retired again, a resolved case being resolved again, a `DRAFT` prescription being revoked, a `RECEIVED` transfer being dispatched, a `PAID` invoice being voided, an `ACKNOWLEDGED` reminder being sent, or a stop being arrived at out of sequence.

**Rungs 35–53, the domain rules.** (35) The route's farrier's certification level covers every service type on the appointment, else `ERR_CREDENTIAL_INSUFFICIENT` (HTTP 403); checked on attachment, start and completion. (36) A `CORRECTIVE` service line names a prescription live on the appointment's `scheduled_date`, else `ERR_NO_LIVE_PRESCRIPTION` (HTTP 422); on service-line addition. (37) That prescription's `limb_scope` contains the exact limb of the referenced limb row, else `ERR_LIMB_NOT_IN_PRESCRIPTION_SCOPE` (HTTP 422); on service-line addition. (38) A `RESET` line targets a limb whose `shoeing_state` is `SHOD`, `SHOD_WITH_PAD` or `GLUED`, else `ERR_RESET_REQUIRES_SHOD_LIMB` (HTTP 422); on service-line addition. (39) That limb's `consecutive_reset_count` is strictly below 1 (`MAX_CONSECUTIVE_RESETS`), else `ERR_RESET_LIMIT_REACHED` (HTTP 409); on service-line addition. (40) The appointment has no other `PLANNED` or `PERFORMED` line for the same limb, else `ERR_DUPLICATE_LIMB_LINE` (HTTP 409); on service-line addition. The set this is checked against grows as the array is walked, so two elements of one `lines` array naming the same limb collide with each other and the second reports this code. (41) A warranty revisit falls within 21 days of the origin visit's `completed_on`, inclusive, else `ERR_WARRANTY_WINDOW_EXPIRED` (HTTP 422); on warranty-revisit creation. (42) The stop's `barn_id` equals the horse's `barn_id`, else `ERR_BARN_MISMATCH` (HTTP 422); on attachment. (43) The weekday of the route's `route_date` is a member of the stop barn's `served_weekdays`, else `ERR_BARN_WEEKDAY_NOT_SERVED` (HTTP 422); on stop insertion. (44) The `route_date` is not a member of that barn's `blackout_dates`, else `ERR_BARN_BLACKOUT_DATE` (HTTP 422); on stop insertion. (45) The stop fits inside the barn's access window, else `ERR_OUTSIDE_ACCESS_WINDOW` (HTTP 422); on stop insertion, attachment and reorder. (46) Consecutive stops respect the travel buffer, else `ERR_STOP_TIME_CONFLICT` (HTTP 409); on stop insertion, reorder and attachment. Only the adjacent pairs that touch the stop or stops the request itself moves are policed — the new stop on an insertion, the two exchanged stops on a reorder, the receiving stop on an attachment — so a buffer violation already standing between two stops that the request does not touch never blocks the write. (47) A horse that requires sedation has an appointment carrying `vet_present` true, else `ERR_SEDATION_VET_REQUIRED` (HTTP 422); on appointment creation and attachment. (48) The reminder is not suppressed by a recently sent sibling, else `ERR_REMINDER_SUPPRESSED` (HTTP 409); on reminder sending. (49) Route unit capacity holds, else `ERR_ROUTE_UNIT_CAPACITY_EXCEEDED` (HTTP 409); on attachment, and on service-line addition to an appointment already attached to a stop. (50) Route minute capacity holds, else `ERR_ROUTE_MINUTE_CAPACITY_EXCEEDED` (HTTP 409); on stop insertion, on attachment, and on service-line addition to an already-attached appointment. (51) The van bucket holds enough pairs, else `ERR_VAN_STOCK_INSUFFICIENT` (HTTP 409); on attachment, and on service-line addition to an already-attached appointment. (52) The shop bucket holds enough pairs, else `ERR_SHOP_STOCK_INSUFFICIENT` (HTTP 409); on transfer dispatch. (53) An effective rate card exists for the service date, else `ERR_NO_EFFECTIVE_RATE_CARD` (HTTP 422); on attachment, appointment completion, appointment cancellation, no-show recording and stop completion. Fiscal checks run last, which is why a visit that is both unpriceable and over capacity reports the capacity code.

Three consequences of this ordering are worth stating outright, because they are the ones an implementation most often gets backwards. The **units meter is checked before the minutes meter**, so an attachment that would breach both reports `ERR_ROUTE_UNIT_CAPACITY_EXCEEDED`. The **credential check runs before every other domain rule of the attachment**, so an apprentice being handed a corrective visit reports `ERR_CREDENTIAL_INSUFFICIENT` rather than a stock or capacity code. And the **corrective-work rungs run in the order live-prescription, then limb-scope**, so a line naming an expired prescription whose scope also excludes the limb reports `ERR_NO_LIVE_PRESCRIPTION`.
### 2.8. Optimistic Concurrency on Parent Rows

Four write operations require the caller to prove that it is acting on a picture of a **parent** row that is still current. In each case the field is mandatory — omitting it is a rung-21 shape failure, not a concurrency failure — and it must carry the `version` the client last observed on that parent. If the parent's `version` has moved on since, the write is refused and nothing is written.

- Attaching an appointment to a stop requires `expected_route_version` matching the current `version` of the `Route` that owns the stop. A mismatch is `ERR_STALE_ROUTE_VERSION` (HTTP 412). Both of two competing attachments may be individually legitimate — the route may have capacity for either horse on its own — so no state precondition can separate them; only the stale version reveals that the capacity picture the caller reasoned about is out of date.
- Adding service lines requires `expected_appointment_version` matching the current `version` of the target `Appointment`. A mismatch is `ERR_STALE_APPOINTMENT_VERSION` (HTTP 412). Adding a second line for a different limb is perfectly valid on its own, so the appointment's status precondition cannot distinguish a caller who has seen the first line from one who has not; the version does.
- Activating a prescription requires `expected_lameness_case_version` matching the current `version` of the `LamenessCase` the prescription belongs to. A mismatch is `ERR_STALE_CASE_VERSION` (HTTP 412). Activation legitimately supersedes any sibling already `ACTIVE` on the same case, so a second activation is a valid product operation rather than an invalid-state error; the version check is what rejects an activation raised against a case whose prescription picture the veterinarian has not re-read.
- Applying a payment requires `expected_client_version` matching the current `version` of the `Client`. A mismatch is `ERR_STALE_CLIENT_VERSION` (HTTP 412). A second payment is always a valid operation, so no state precondition rejects it; the version check rejects a payment raised from a stale view of the client's outstanding balance.

No other endpoint takes a version field, and none may be invented. All four rungs sit above every gate and every domain rule, and below the payload-shape rungs.

### 2.9. Conservation Invariants

Seven identities must hold after **every** request, successful or refused. They are not merely descriptive; they are the arithmetic the rest of this document has to add up to.

1. **Trip-fee split.** For a stop whose `status` is `COMPLETED` and whose `billable_horse_count` is greater than zero, the sum of `trip_fee_share_cents` over the invoices of the appointments attached to that stop whose `status` is `COMPLETED`, `NO_SHOW` or `CANCELLED_ONSITE` equals that stop's `trip_fee_cents` exactly.
2. **Bucket balance.** For every inventory bucket, `on_hand_pairs` equals `available_pairs` plus `reserved_pairs`.
3. **System pairs.** For any one SKU, the sum of `on_hand_pairs` across all its buckets plus the sum of `quantity_pairs` over that SKU's transfers whose `status` is `IN_TRANSIT` is unchanged by transfer dispatch, receive and abort. In-transit stock is, in effect, a third bucket.
4. **Reserve/release round trip.** Attaching an appointment and then detaching the same appointment leaves the van bucket's `available_pairs` and `reserved_pairs` at exactly their pre-attachment values.
5. **Route capacity round trip.** Attaching an appointment and then detaching the same appointment leaves the route's `committed_units` and `committed_minutes` at exactly their pre-attachment values.
6. **Loyalty split.** On every invoice, `loyalty_discount_labor_cents` plus `loyalty_discount_product_cents` equals `loyalty_discount_cents` exactly.
7. **Invoice total.** On every invoice, `total_cents` equals `labor_net_cents` plus `taxable_product_base_cents` plus `trip_fee_share_cents` plus `fee_cents` plus `tax_cents`, and `balance_cents` equals `total_cents` minus `paid_cents`.

### 2.10. Chained Consequences

Four consequences in this system are **chains**, in the sense that each step is caused by the step before it rather than by the original request. They are named here so that §3 can refer to them, and §3 states each hop's own preconditions and effects; where §3 and this overview appear to differ in detail, §3's hop-by-hop account governs.

**The lameness chain** runs six deep from the reporting of a lameness case whose `severity` is at least 3. Hop 1: the case is created with `status` `OPEN` and `hold_applied` true. Hop 2: because the hold applied, the horse's `hold_status` becomes `HOLD`. Hop 3: because the horse went on hold, every appointment of that horse whose `status` is `SCHEDULED` or `CONFIRMED` becomes `BLOCKED` and its `route_stop_id` is cleared. Hop 4: because those appointments were detached, each of their `RESERVED` reservations becomes `RELEASED`. Hop 5: because a reservation was released, its bucket gains `available_pairs`, loses `reserved_pairs`, and has `replenishment_flag` recomputed. Hop 6: because that flag flipped from true to false, every transfer still `REQUESTED` into that bucket becomes `CANCELLED`. A parallel branch runs alongside hops 3 and 4: hop 3b, a stop that is still `PENDING` and is left with no attached appointment at all becomes `VOIDED` — a stop already `ARRIVED`, `COMPLETED` or `VOIDED` is never voided by this branch however empty it is left; hop 4b, because the stop was voided, the route's `committed_minutes` and `stop_count` fall, and a `PLANNED` route whose `committed_units` has fallen from a positive figure to zero reverts to `DRAFT` (a route already sitting at zero units does not re-enter `DRAFT`, since nothing fell).

**The completion chain** runs three deep. Hop 1: the appointment becomes `COMPLETED`. Hop 2: because the visit completed, every `RESERVED` reservation becomes `COMMITTED` and the van bucket's `on_hand_pairs` and `reserved_pairs` both fall. Hop 3: because those counters moved, the bucket's `replenishment_flag` is recomputed and may flip to true.

**The re-scheduling chain** also starts at completion and runs four deep. Hop 1: the horse's `last_completed_on` is set and its `next_due_on` is recomputed. Hop 2: because `next_due_on` moved, a successor appointment is minted at the snapped-forward date. Hop 3: because a successor appointment now exists, two reminder rows are minted `PENDING` against it. Hop 4: the completed appointment's `rate_card_id` is pinned and its invoice is minted `DRAFT` with its lines. The hop numbering here is causal, not chronological: hop 4's card is pinned with the appointment's own status step and its invoice is built before hops 1 to 3 run, which is what lets the invoice see the client's `completed_visit_count` already incremented. §3.7 gives the executed order.

**The expiry chain** runs five deep from a clock advance. Hop 1: the clock advances. Hop 2: because the new date is past its `expires_on`, an `ACTIVE` prescription becomes `EXPIRED`. Hop 3: because the prescription expired, the horse's `active_prescription_id` becomes null and its `next_due_on` reverts to the routine derivation. Hop 4: because no live prescription remains, every `PLANNED` `CORRECTIVE` service line on a non-terminal appointment of that horse becomes `REMOVED`. Hop 5: because lines were removed, the affected appointment's `service_units`, `service_minutes` and `estimated_total_cents` are recomputed, its stop's `service_minutes` and `end_minute` follow, and its route's committed totals follow those.

## 3. Business Logic & Workflows

### 3.1. Yards, Owners, Horses and Hooves

A `PlatformAdmin` seeds the world with **barns**. A barn is described by a `name`, a travel `zone` that is one of `A`, `B` or `C`, a set of `served_weekdays` drawn from `MON`, `TUE`, `WED`, `THU`, `FRI`, `SAT` and `SUN`, an `access_open_minute` and an `access_close_minute` bounding the hours the gate is unlocked, and an optional list of `blackout_dates` on which the yard is shut regardless of the weekday pattern. `served_weekdays` must be non-empty and free of duplicates, and so must every list of weekday tokens; `blackout_dates` defaults to the empty list when it is not supplied. The access window is a genuine half-day constraint rather than decoration — the open minute must be strictly less than the close minute, the open minute may not be negative, and the close minute may not exceed 1440.

Owners are **clients**. A client is created with a `display_name` and a `home_barn_id` naming the barn where that owner's horses normally live; two optional fields round out the record. `tax_exempt` defaults to false and selects which tax treatment the owner's invoices receive. `opening_completed_visit_count` defaults to 0 and exists because this business is migrating off a paper diary: whatever number is supplied is the starting value of the client's `completed_visit_count`, and every visit the system itself completes is added on top of it; a negative figure is refused with `ERR_VALUE_OUT_OF_RANGE`. `home_barn_id` must name an existing barn, but it is a filing detail only — every rule that needs a yard reads the horse's own `barn_id`, never the owner's home barn. Everything else on a client is derived and starts at a known value — `billing_standing` starts `ACTIVE`, `deposit_balance_cents` starts 0, `credit_balance_cents` starts 0 and `no_show_count_rolling` starts 0.

Horses belong to owners and live at barns, and those two need not agree: a horse carries both a `client_id` naming the paying owner and a `barn_id` naming where it is physically kept. It also carries a `name`, a `shoe_size_code` giving the nominal size its shoes are ordered in — a note for the yard, never compared by any rule against a `ShoeSku`'s `size_code`, so a line may name a SKU of any size — and a `routine_cycle_weeks` between 6 (`MIN_ROUTINE_CYCLE_WEEKS`) and 8 (`MAX_ROUTINE_CYCLE_WEEKS`) inclusive that says how often it is normally due. `requires_sedation` defaults to false; when true it changes the arithmetic of the visit in two separate places — the chair minutes and the labour price — and forces a veterinarian's attendance. Creating a horse mints four (`LIMB_COUNT_PER_HORSE`) `LimbState` rows in exactly the order `LF`, `RF`, `LH`, `RH`, each starting `BAREFOOT` with a null `current_sku_code`, a null `last_serviced_on` and a `consecutive_reset_count` of 0. The per-horse limb listing always returns those four rows in that same anatomical order, whatever the general ordering rule says elsewhere; it accepts an optional `limb` filter.

Two independent status axes ride on a horse and neither constrains the other. `lifecycle_status` starts `ACTIVE` and may be moved to `RETIRED` by the owner or an administrator, provided the horse has no appointment whose `status` is `SCHEDULED`, `CONFIRMED` or `IN_PROGRESS` — otherwise the retirement is refused with `ERR_INVALID_STATE`. `lifecycle_status` is consulted by nothing except these two transitions: it is not a gate and it is on no rung, so a `RETIRED` horse may still have a fresh appointment created for it, may still be attached to a stop, worked and billed, and may still take a lameness case. Retiring a horse nulls its `next_due_on`, cancels every `UNROUTED` appointment of that horse to `CANCELLED_ADVANCE` with a `cancellation_fee_cents` of 0, and increments the horse's `version` by 1. Reinstating moves `RETIRED` back to `ACTIVE`, leaves `next_due_on` null until the next completed visit recomputes it, and again increments `version` by 1; reinstating a horse that is already `ACTIVE` is refused with `ERR_INVALID_STATE`. The second axis, `hold_status`, starts `CLEAR` and is driven entirely by lameness — §3.6 owns it. A horse's `active_prescription_id`, `next_due_on` and `last_completed_on` are all derived and start null. Of those three, `next_due_on` is purely reportorial: no rule and no derivation ever reads it back — the successor visit of §3.8 is dated from a fresh run of the derivation rather than from the stored figure — whereas `active_prescription_id` and `last_completed_on` are both read by that derivation.

An owner or administrator may amend a horse in flight, supplying any of `routine_cycle_weeks`, `requires_sedation` and `shoe_size_code`; each supplied field replaces the stored one, omitted fields are left alone, and the horse's `version` increments by 1. Amending the routine cycle does not retroactively move an already-computed `next_due_on`; the new figure takes effect at the next recomputation.

### 3.2. The Bench: Farriers, Shoe SKUs and the Two Kinds of Bucket

A farrier is created with a `display_name`, a `certification_level` and a `cert_expires_on` date. The certification level is the single gate on what work that farrier may perform, and the mapping is exhaustive: an `APPRENTICE` may perform only `TRIM`; a `JOURNEYMAN` may perform `TRIM`, `RESET`, `NEW_SHOES` and `GLUE_ON`; and a `CERTIFIED_THERAPEUTIC` may perform all five, adding `CORRECTIVE`. Whenever an appointment carries a service type the route's farrier may not perform, the operation is refused with `ERR_CREDENTIAL_INSUFFICIENT`, and that refusal is checked at three distinct moments — when the horse is attached to a stop, when work on it starts, and when the visit is completed.

A farrier's `status` starts `ACTIVE` and has two distinct exits, chosen by a `reason` field on the stand-down operation. A `reason` of `VOLUNTARY` moves `ACTIVE` to `INACTIVE`; a `reason` of `CERT_EXPIRED` moves `ACTIVE` to `DECERTIFIED`. Both exits do the same collateral damage — every route of that farrier whose `status` is `DRAFT` or `PLANNED` moves to `CANCELLED`, which in turn voids that route's `PENDING` stops, detaches its appointments back to `UNROUTED` and releases their reservations — and both increment the farrier's `version` by 1. The two exits differ only in how they are cleared. Reactivation returns `INACTIVE` to `ACTIVE` and increments `version` by 1, and it is refused with `ERR_INVALID_STATE` for a farrier who is `DECERTIFIED` or already `ACTIVE`. Recertification is the only way out of `DECERTIFIED`: it accepts a fresh `certification_level` and `cert_expires_on`, requires that the supplied expiry be on or after the logical clock date, writes both values, sets `status` to `ACTIVE` and increments `version` by 1. A recertification aimed at a farrier who is not `DECERTIFIED`, or carrying an expiry already in the past, is refused with `ERR_INVALID_STATE`.

Shoes are catalogued as SKUs. A `ShoeSku` carries a `sku_code` that must be unique across all SKUs — a repeat is a shape failure, `ERR_VALIDATION`, and it is caught at rung 21, so a request that both repeats a code and names an undeclared `material` reports `ERR_VALIDATION` rather than `ERR_INVALID_ENUM` — a `size_code` that is recorded and never matched against anything, a `material` that is one of `STEEL`, `ALUMINUM` or `COMPOSITE`, and a `price_cents_per_pair` of at least 0, a negative figure being `ERR_VALUE_OUT_OF_RANGE` — because shoes are bought, held and sold in left/right pairs of 2 (`SHOES_PER_PAIR`), never singly.

Stock lives in **buckets**, and a bucket's `location_kind` is either `SHOP` or `VAN`. There is exactly one `SHOP` bucket per SKU, and its `farrier_id` is null; there is one `VAN` bucket per farrier per SKU, and its `farrier_id` names that farrier. Buckets are minted automatically and never by hand: creating a farrier mints one `VAN` bucket for each existing SKU, and creating a SKU mints its one `SHOP` bucket plus one `VAN` bucket per existing farrier. Every freshly minted bucket has `on_hand_pairs`, `available_pairs` and `reserved_pairs` all at 0 and, because the flag is recomputed on every write **including creation**, a `replenishment_flag` of true.

> **Which farriers get a van bucket for a new SKU.** Creating a shoe SKU mints one `VAN` bucket per **existing farrier row, whatever its status** — `ACTIVE`, `INACTIVE` and `DECERTIFIED` alike — so that a later reactivation or recertification finds its stock already in place rather than leaving that farrier permanently without a bucket for the SKU.

The replenishment flag is a two-state axis of its own — a bucket is either `REPLENISHMENT_FLAGGED`, meaning `replenishment_flag` is true, or `REPLENISHMENT_CLEAR`, meaning it is false — and every bucket begins life `REPLENISHMENT_FLAGGED`. The axis is a threshold, not a judgement: the flag is true exactly while `available_pairs` is less than or equal to 2 (`REORDER_POINT_PAIRS`). The comparison is inclusive, so a bucket holding exactly two available pairs **is** flagged and one holding three is not. Every write that changes `available_pairs` recomputes it: a reservation taken on attachment, a reservation resized or released by a service-line change, a reservation released on detachment, cancellation, no-show or the lameness chain, a reservation committed at completion, a transfer dispatched out of the shop, a transfer received into a van, a transfer aborted back into it, and the stock-take adjustment. Every one of those also records one mutation step on the bucket row, so a bucket's `version` advances once per counter movement even when the flag itself does not change. And the flag carries a consequence of its own — whenever it flips from true to false, every stock transfer still sitting in `REQUESTED` whose `to_bucket_id` is that bucket is moved to `CANCELLED` with no stock moving at all, each such transfer's `version` incrementing by 1. The reasoning is simply that the shortage which justified the transfer has gone away.

Stock moves between buckets in one direction only. A transfer is requested with a `sku_id`, a `from_bucket_id` that must be the `SHOP` bucket for that SKU, a `to_bucket_id` that must be a `VAN` bucket for the same SKU — either bucket being of the wrong kind, or belonging to a different SKU, is `ERR_VALIDATION` at rung 21, the two buckets' own existence having already been checked at rung 9 — and a `quantity_pairs` between 1 and 40 (`MAX_TRANSFER_PAIRS`) inclusive. It is minted `REQUESTED` and moves no stock. Dispatching it requires the shop bucket to hold at least `quantity_pairs` in `available_pairs` — otherwise `ERR_SHOP_STOCK_INSUFFICIENT` — and then lowers the shop bucket's `on_hand_pairs` and `available_pairs` by that quantity, recomputes the shop bucket's flag, moves the transfer to `IN_TRANSIT` and increments its `version` by 1. Receiving raises the van bucket's `on_hand_pairs` and `available_pairs` by the same quantity, recomputes the van bucket's flag, moves the transfer to `RECEIVED` and increments its `version` by 1. Aborting an `IN_TRANSIT` transfer returns the pairs to the shop bucket — `on_hand_pairs` and `available_pairs` both rise by the quantity — moves the transfer to `ABORTED` and increments its `version` by 1. Any of these three attempted from the wrong state is refused with `ERR_INVALID_STATE`, and once a transfer is `RECEIVED`, `CANCELLED` or `ABORTED` it is finished. While a transfer is `IN_TRANSIT` its pairs belong to no bucket at all, which is exactly why the third conservation invariant counts them separately.

A stock-take reconciles a bucket against reality. It takes a single `delta_pairs`, which may be positive or negative, adds it to both `on_hand_pairs` and `available_pairs`, recomputes the replenishment flag, and increments the bucket's `version` by 1. Because both counters move by the same amount, `reserved_pairs` is untouched and the bucket-balance invariant is preserved by construction.

> **Adjusting a bucket below zero.** A negative `delta_pairs` that would drive either `on_hand_pairs` or `available_pairs` below zero is **refused** with `ERR_VALUE_OUT_OF_RANGE`, and nothing is written: the resulting negative balance is treated as a range violation rather than as an unconditional stock-take. The test is on both counters independently and is made before any write, so an adjustment that would leave `on_hand_pairs` at 0 but `available_pairs` at −1 is refused just as firmly.

### 3.3. The Pricing Calendar: Rate Cards

Prices are not attributes of a service; they are attributes of a **rate card**, and which card applies is decided by the date the work is done rather than the date anyone is billed. A card carries a `label`, an `effective_from` date, an optional `supersedes_rate_card_id` naming the card it replaces (null for the very first card), five labour prices — `price_trim_cents`, `price_reset_cents`, `price_new_shoes_cents`, `price_corrective_cents` and `price_glue_on_cents`, one per service type, each the price of **one limb** — a `pad_price_cents` charged once for each limb whose line carries a pad, and three trip fees, `trip_fee_zone_a_cents`, `trip_fee_zone_b_cents` and `trip_fee_zone_c_cents`, one per barn zone.

A card is minted `DRAFT` and prices nothing. Activation moves `DRAFT` to `ACTIVE`, and if the card names a predecessor that predecessor must itself be `ACTIVE` at that moment — otherwise the activation is refused with `ERR_INVALID_STATE` — and the predecessor is moved to `SUPERSEDED`. Both cards' `version` increments by 1. Activating a card that is not `DRAFT` is likewise refused with `ERR_INVALID_STATE`.

Selection is chronological and deliberately admits superseded cards. Given a service date, the candidates are every card whose `status` is `ACTIVE` or `SUPERSEDED` and whose `effective_from` is on or before that date; `DRAFT` cards are never candidates. The candidates are ranked by `effective_from` descending and, where two share an `effective_from`, by `created_at` descending; the first is selected. A card whose `effective_from` equals the service date exactly **is** eligible. If the candidate list is empty the operation is refused with `ERR_NO_EFFECTIVE_RATE_CARD`.

The service date is never the invoice's `issued_on` and never the logical clock date. For a finalised visit it is the appointment's `completed_on`; for an estimate it is the appointment's `scheduled_date`. A card that takes effect between those two dates therefore changes the answer between the estimate and the bill, and that is intended rather than a defect. The remaining selections are: for an attachment, the appointment's `scheduled_date`; for a cancellation in any of the three tiers, and for a no-show, the appointment's `scheduled_date` — not the clock date on which the cancellation is raised; and for a stop's trip fee, the route's `route_date`. Every one of those five selections is mandatory and refuses with `ERR_NO_EFFECTIVE_RATE_CARD` when the candidate list is empty. The estimate is the single exception: it is a convenience figure, so when no card is effective on the `scheduled_date` the appointment's `estimated_total_cents` is simply written as 0 and the operation that triggered the refresh — a service-line addition or removal — succeeds regardless.
### 3.4. Building the Day: Routes, Stops and Two Meters That Both Say No

A `Dispatcher` opens a route for one farrier on one date, supplying `farrier_id` and `route_date`. The route is minted `DRAFT` with `committed_units` 0, `committed_minutes` 0 and `stop_count` 0. Because gate 1 guards route creation, a route cannot even be opened for a farrier who is `INACTIVE`, `DECERTIFIED` or whose `cert_expires_on` falls before the logical clock date.

The route lifecycle has five states. `DRAFT` moves to `PLANNED` once the route has at least one stop; a planning attempt on a route with no stops, or on a route that is not `DRAFT`, is refused with `ERR_INVALID_STATE`, and success increments the route's `version` by 1. `PLANNED` moves to `DISPATCHED` only when `committed_units` is at least 1 — a route of empty stops is not worth sending out — again with `ERR_INVALID_STATE` otherwise and a `version` increment on success. From the moment a route is `DISPATCHED`, stop insertion, stop reordering, attachment and detachment are all refused by gate 2 with `ERR_ROUTE_NOT_OPEN`. `DISPATCHED` moves to `CLOSED` once no stop on the route is `PENDING` or `ARRIVED`, with `ERR_INVALID_STATE` otherwise and a `version` increment on success. Cancellation is available from `DRAFT` and from `PLANNED` and from nowhere else: every `PENDING` stop moves to `VOIDED`, every attached appointment is detached and returns to `UNROUTED`, every `RESERVED` reservation belonging to those appointments moves to `RELEASED`, and the route's `version` increments by 1. Attempting to cancel a route that is `DISPATCHED`, `CLOSED` or already `CANCELLED` is refused with `ERR_INVALID_STATE` — note that cancellation, planning, dispatch and closing are **not** gate-2 operations, so their state failures surface as `ERR_INVALID_STATE` rather than `ERR_ROUTE_NOT_OPEN`.

There is one system-driven leg back up the chain: a `PLANNED` route whose `committed_units` has fallen to zero reverts to `DRAFT`, incrementing its `version` by 1. This happens when the last appointment leaves the route, and it is the reason the route lifecycle is not a one-way ratchet.

A stop is a barn visited once. Several horses standing at the same yard form **one** stop, not several. Inserting a stop supplies `barn_id`, `sequence_index` and `planned_start_minute`. The stop is minted `PENDING`, its `travel_minutes` is fixed from the barn's zone — 15 minutes for zone `A` (`STOP_TRAVEL_MINUTES_ZONE_A`), 30 for zone `B` (`STOP_TRAVEL_MINUTES_ZONE_B`) and 50 for zone `C` (`STOP_TRAVEL_MINUTES_ZONE_C`) — its `service_minutes` starts at 0, its `end_minute` is its `planned_start_minute` plus its `service_minutes`, its `trip_fee_cents` starts at 0 and its `billable_horse_count` starts at 0. The route's `committed_minutes` rises by the stop's `travel_minutes`, its `stop_count` rises by 1, and its `version` increments by 1. A route may hold at most 8 stops (`MAX_STOPS_PER_ROUTE`) — the eighth insertion succeeds and the ninth does not: the insertion is refused with `ERR_VALUE_OUT_OF_RANGE` when the route's `stop_count` has already reached 8, and likewise when `sequence_index` is below 1 or above the route's current `stop_count` plus one, which is what keeps the ordering contiguous. The `sequence_index` band is checked first and the 8-stop ceiling second, though both carry the same code. Note that `stop_count` counts only the route's non-`VOIDED` stops, so a voided stop frees its slot for a fresh insertion.

Four temporal rules police a stop, and they are checked in the ladder order given in §2.7. The weekday of the route's `route_date` must be one of the barn's `served_weekdays`, else `ERR_BARN_WEEKDAY_NOT_SERVED`. The `route_date` must not appear in the barn's `blackout_dates`, else `ERR_BARN_BLACKOUT_DATE`. The stop must sit **inside** the barn's access window: its `planned_start_minute` must be at least the barn's `access_open_minute`, and its `planned_start_minute` plus its `service_minutes` must be at most the barn's `access_close_minute`. The end boundary is inclusive, so a stop finishing exactly at closing time is accepted; anything else is `ERR_OUTSIDE_ACCESS_WINDOW`. And consecutive stops must respect the travel buffer: for two stops whose `sequence_index` values differ by exactly one, the later stop's `planned_start_minute` must be at least the earlier stop's `end_minute` plus the **later** stop's own `travel_minutes`. Equality is accepted; a start anywhere inside that buffer is `ERR_STOP_TIME_CONFLICT`. Both the access-window rule and the adjacency rule are re-evaluated whenever a stop's minutes change, which is why they guard attachment and reordering as well as insertion.

One planning constant is declared but deliberately unenforced. `ROUTE_DAY_START_MINUTE` is 480 — eight o'clock in the morning — and it describes when a farrier's day nominally begins. No rule in this specification compares a `planned_start_minute` against it, and no error code is defined for starting earlier; barn access windows are the only hard bound on when work may begin.

Reordering moves a stop one place earlier or later. It takes a `direction` of `EARLIER` or `LATER` together with a fresh `planned_start_minute`, exchanges this stop's `sequence_index` with that of the sibling it swaps past, writes the new start minute, and increments the route's `version` by 1. Because the swap changes where two stops sit in the day, the access-window rule and the adjacency rule are both re-checked, and a violation is refused with `ERR_OUTSIDE_ACCESS_WINDOW` or `ERR_STOP_TIME_CONFLICT` respectively. A reorder that would move the first stop earlier, or the last stop later, has no sibling to swap with and is refused with `ERR_INVALID_STATE`.

> **Stop insertion at an occupied index, and version bookkeeping on reorder.** Both are settled as follows. Inserting at an index already held **shifts the incumbents one place later**: every non-`VOIDED` stop whose `sequence_index` is at or above the requested index has it raised by one, and each such shifted incumbent advances its own `version` by 1; the new stop takes the requested index. Refusing instead would leave only `stop_count` plus one ever acceptable and strand the whole declared range. The adjacency and capacity checks are made against the shifted picture before anything is written. And on a reorder, **both exchanged stop rows each advance their own `version`** on top of the route increment the side-effect list names, because the general rule of §2.4 applies without qualification and both rows genuinely mutate — this stop's `sequence_index` and `planned_start_minute`, the sibling's `sequence_index`. The reorder rewrites only this stop's `end_minute`; the sibling keeps its own `planned_start_minute` and therefore its own `end_minute`, and neither route meter moves, so the route's `version` advances but its `committed_minutes`, `committed_units` and `stop_count` do not.

Route capacity is metered in **two independent units**, and either alone is enough to refuse a horse. `committed_units` is the sum of `service_units` over the appointments attached to any non-`VOIDED` stop of the route whose `status` is `SCHEDULED`, `CONFIRMED`, `IN_PROGRESS` or `COMPLETED`; appointments that are `BLOCKED`, `UNROUTED`, cancelled in any tier or `NO_SHOW` contribute nothing. `committed_minutes` is the sum of `travel_minutes` over the route's non-`VOIDED` stops plus the sum of `service_minutes` over those same qualifying appointments. A day may carry at most 44 shoeing units (`ROUTE_MAX_UNITS_PER_DAY`) and at most 480 minutes (`ROUTE_MAX_MINUTES_PER_DAY`). Both meters, and `stop_count` with them, are recomputed from scratch over the whole route whenever any of them could have moved — which is what makes the round-trip invariants of §2.9 hold to the minute — and the route row records a mutation step only when at least one of the three actually changes. A stop's own `service_minutes` is a different sum and deliberately so: it totals `service_minutes` over **every** appointment attached to the stop with no status filter at all, so an appointment that stays attached after an on-site cancellation or a no-show goes on lengthening its stop even though it has stopped contributing to the route's meters. `end_minute` is always `planned_start_minute` plus that total.

The check is forward-looking. The projected units are the route's current `committed_units` plus the delta the request would add, and the projected minutes are the current `committed_minutes` plus the minute delta. For a stop insertion the unit delta is 0 and the minute delta is the new stop's `travel_minutes`; for an attachment the unit delta is the appointment's `service_units` and the minute delta is its `service_minutes`. The comparison is strictly greater-than, so landing **exactly** on 44 units or exactly on 480 minutes is accepted and only exceeding the figure is refused. Units are checked first, with `ERR_ROUTE_UNIT_CAPACITY_EXCEEDED`; minutes second, with `ERR_ROUTE_MINUTE_CAPACITY_EXCEEDED`. A stop insertion can only ever breach the minute meter, since its unit delta is zero.

### 3.5. The Visit: Appointments and Per-Limb Service Lines

A visit begins life detached. A `Dispatcher` or the owning `ClientUser` creates an appointment with a `horse_id`, a `scheduled_date` and an optional `vet_present` that defaults to false. It is minted with `status` `UNROUTED` and `billing_status` `UNBILLED`; its `route_stop_id`, `origin_appointment_id`, `rate_card_id`, `warranty_reason`, `cycle_source` and `completed_on` are all null; its `visit_kind` is `ROUTINE`; and its `service_units`, `service_minutes`, `estimated_total_cents`, `cancellation_fee_cents` and `trip_fee_share_cents` all start at 0. Creation passes gate 3 and gate 4, and it also passes the sedation rule: if the horse's `requires_sedation` is true the appointment must carry `vet_present` true, else `ERR_SEDATION_VET_REQUIRED`.

The work itself is described **per limb**. Service lines are added in one atomic call carrying a non-empty `lines` array together with `expected_appointment_version`. Each element of the array names a `limb_state_id` — which identifies both the horse and the exact hoof — a `service_type`, and optionally a `sku_id`, a `prescription_id` and a `with_pad` flag that defaults to false. The `limb_state_id` must name an existing limb row **of this appointment's horse**; one that names no row, or a limb of some other horse, is `ERR_VALIDATION` rather than any not-found code, because no existence rung covers `LimbState`. The array is validated in index order and the first offending element's error is returned, but the ladder still outranks the index between rungs: rung 21 is applied to every element before rung 22 is applied to any, so a first element with an undeclared `service_type` alongside a second that omits a required `sku_id` reports `ERR_VALIDATION`. Rungs 36 to 40 are then applied element by element in index order, all five to one element before the next is looked at, so an earlier element's duplicate-limb refusal pre-empts a later element's missing-prescription refusal. On any failure **nothing at all is written**: no partial line set, no roll-up change, no reservation. On success the rows come back in exactly the order they were supplied, each with `status` `PLANNED`, `labor_cents` 0 and `limb` copied from the referenced limb row.

Which optional fields are required is a function of the service type and is checked at rung 21. `NEW_SHOES`, `CORRECTIVE` and `GLUE_ON` each consume a shoe and therefore require `sku_id`; `TRIM` and `RESET` consume none and must leave it null. Only `CORRECTIVE` requires `prescription_id`; every other type must leave it null. And a pad is only meaningful under a nailed-on shoe, so `with_pad` may be true only for `NEW_SHOES` and `CORRECTIVE` — a true value on a `TRIM`, a `RESET` or a `GLUE_ON` line is `ERR_VALIDATION`.

Five domain rungs then guard the line, in this order. A `CORRECTIVE` line's named prescription must be **live on the appointment's `scheduled_date`** — its `status` is `ACTIVE`, its `issued_on` is on or before that date and that date is on or before its `expires_on`, both bounds inclusive — else `ERR_NO_LIVE_PRESCRIPTION`. That prescription's `limb_scope` must contain the exact limb of the referenced limb row, else `ERR_LIMB_NOT_IN_PRESCRIPTION_SCOPE`. A `RESET` line reuses the shoe already on the hoof, so the limb's `shoeing_state` must be `SHOD`, `SHOD_WITH_PAD` or `GLUED`; a `RESET` on a `BAREFOOT` limb has nothing to reuse and is `ERR_RESET_REQUIRES_SHOD_LIMB`. That limb's `consecutive_reset_count` must be strictly below 1 (`MAX_CONSECUTIVE_RESETS`) — a limb may be reset once before the shoe must be replaced, and a second consecutive reset is `ERR_RESET_LIMIT_REACHED`. Finally, the appointment must not already carry another `PLANNED` or `PERFORMED` line for the same limb, else `ERR_DUPLICATE_LIMB_LINE`; four hooves means at most four live lines.

Two roll-ups are recomputed from scratch after every change to the line set, counting only lines whose `status` is `PLANNED` or `PERFORMED` — `REMOVED` and `OMITTED` lines contribute nothing. Minting an appointment is not itself such a change, so a brand-new appointment's roll-ups stay at 0 until its first service line arrives, with none of the handling term below folded in. `service_units` is the sum of a fixed per-limb load: 1 for a `TRIM` (`SERVICE_UNITS_TRIM`), 2 for a `RESET` (`SERVICE_UNITS_RESET`), 3 for `NEW_SHOES` (`SERVICE_UNITS_NEW_SHOES`), 5 for `CORRECTIVE` (`SERVICE_UNITS_CORRECTIVE`) and 4 for `GLUE_ON` (`SERVICE_UNITS_GLUE_ON`). `service_minutes` starts from the sum of the per-limb chair times — 8 minutes for a `TRIM` (`SERVICE_MINUTES_TRIM`), 14 for a `RESET` (`SERVICE_MINUTES_RESET`), 20 for `NEW_SHOES` (`SERVICE_MINUTES_NEW_SHOES`), 32 for `CORRECTIVE` (`SERVICE_MINUTES_CORRECTIVE`) and 26 for `GLUE_ON` (`SERVICE_MINUTES_GLUE_ON`) — and then adds handling. For a horse whose `requires_sedation` is false, handling is a flat 6 minutes (`HORSE_HANDLING_MINUTES`). For a horse that requires sedation, the handling term is multiplied by 15000 basis points (`SEDATION_HANDLING_MULTIPLIER_BP`), divided by 10000 and rounded half up, which turns 6 minutes into 9, and a further 15 minutes (`SEDATION_EXTRA_MINUTES`) of sedation time is added on top — 18 minutes more than the unsedated case in total.

Shoes are drawn in pairs. For each distinct `sku_id` referenced by the appointment's lines whose `status` is `PLANNED` or `PERFORMED` and whose `service_type` is `NEW_SHOES`, `CORRECTIVE` or `GLUE_ON`, count those lines and divide by 2 (`SHOES_PER_PAIR`), rounding **up**. Three shoes of one SKU therefore draw two pairs, and the odd shoe costs a whole extra pair.

Adding lines has consequences beyond the appointment. The appointment's `service_units` and `service_minutes` are recomputed; if the appointment is already attached to a stop, that stop's `service_minutes` and `end_minute` and the route's `committed_units` and `committed_minutes` are all recomputed and re-checked against both caps, and the reservation for each affected SKU is created or its `pairs` recomputed; the appointment's `estimated_total_cents` is refreshed by the estimate derivation of §3.9; and the appointment's `version` increments by 1.

> **A line added to an attached appointment that breaches a limit.** The same three rungs that guard attachment are applied, in the same order — `ERR_ROUTE_UNIT_CAPACITY_EXCEEDED`, then `ERR_ROUTE_MINUTE_CAPACITY_EXCEEDED`, then `ERR_VAN_STOCK_INSUFFICIENT` — and the addition is refused **atomically**: nothing is written, no line survives, no reservation moves and no meter changes. The check runs only when the appointment is genuinely on a stop, that is when it has a `route_stop_id` and its `status` is `SCHEDULED` or `CONFIRMED`; an `UNROUTED` visit is never capacity-checked, whatever it accumulates. The figures projected onto the route's current meters are the per-limb loads of the lines being added and nothing else — the sum of their `service_units` and the sum of their per-limb chair minutes — and the van test is the shortfall between the pairs each SKU would then require and the pairs the appointment already holds reserved for it.

> **Adding lines to a visit already under way.** Line **addition** takes the same eligible set as line removal, `UNROUTED`, `SCHEDULED` and `CONFIRMED`, exactly as gate 5 in §2.6 states it. `IN_PROGRESS` is not admitted: a farrier who has already started work cannot extend the visit and receives `ERR_APPOINTMENT_NOT_ELIGIBLE`.

Removing a line moves it from `PLANNED` to `REMOVED`. Only a `PLANNED` line can be removed; the appointment's `service_units` and `service_minutes` are recomputed, and if it is attached, the stop's `service_minutes` and the route's committed totals follow, and the reservation for the affected SKU has its `pairs` recomputed with any surplus pairs returning to the van bucket's `available_pairs`. The appointment's `version` increments by 1.

Attaching a horse to a stop is the busiest operation in the system. It supplies `appointment_id` and `expected_route_version`, and it moves the appointment from `UNROUTED` to `SCHEDULED`. Beyond the five gates and the stale-version rung it enforces that the stop's `barn_id` equals the horse's `barn_id` — several horses at one barn share the stop, and a horse kept elsewhere is `ERR_BARN_MISMATCH` — that the sedation rule holds, that the access window and the travel buffer still hold once the appointment's minutes join the stop, that the route's farrier is certified for every service type on the appointment, that both capacity meters still hold, that the farrier's van bucket has at least the required `pairs` for every SKU on the appointment (else `ERR_VAN_STOCK_INSUFFICIENT`), and that a rate card exists for the appointment's `scheduled_date` (else `ERR_NO_EFFECTIVE_RATE_CARD`).

On success: the appointment's `route_stop_id` is set to the stop; one reservation per distinct `sku_id` is created `RESERVED`, or an existing `RELEASED` reservation for that SKU is moved back to `RESERVED` with its `bucket_id` repointed at the new farrier's van bucket; in either case the bucket's `available_pairs` falls and its `reserved_pairs` rises by that reservation's `pairs`, and its `replenishment_flag` is recomputed; the route's `committed_units` and `committed_minutes` rise and the stop's `service_minutes` and `end_minute` rise; two reminder rows are minted `PENDING`, unconditionally and whatever reminders the appointment already carries; the appointment's `estimated_total_cents` is refreshed; the appointment's `version` increments by 1; and the route's `version` and the stop's `version` each increment by 1 **only if their recomputed figures actually moved**. Attaching an appointment that carries no service lines yet moves neither meter and no stop minute, so neither the route nor the stop records a mutation step and the `expected_route_version` the caller already holds is still current for the next attachment.

Detaching reverses all of it exactly. The appointment's `route_stop_id` is cleared and its `status` returns to `UNROUTED` from either `SCHEDULED` or `CONFIRMED`; every `RESERVED` reservation of the appointment moves to `RELEASED`, raising the bucket's `available_pairs` and lowering its `reserved_pairs` by the reservation's `pairs` with `on_hand_pairs` untouched, and recomputing the bucket's `replenishment_flag`; the route's `committed_units` and `committed_minutes` fall by exactly the amounts the attachment added; the appointment's `version` increments by 1; and the route's `version` increments by 1 on the same condition as on attachment, namely that one of its three recomputed figures moved. Detachment sits behind gate 1 and gate 2 only among the farrier and route gates, plus gate 5; gates 3 and 4 are not consulted, so a suspended owner or a horse that has gone on hold is no obstacle to freeing the slot. The exactness of this reversal is what the fourth and fifth conservation invariants assert.

Reservations therefore have a cyclic life. `RESERVED` becomes `COMMITTED` when the visit completes — `on_hand_pairs` and `reserved_pairs` both fall by `pairs` while `available_pairs` is untouched — and `COMMITTED` is final. `RESERVED` becomes `RELEASED` on detachment, on cancellation, on a no-show, on route cancellation and on the lameness chain's fourth hop. And `RELEASED` becomes `RESERVED` again when the same appointment is re-attached, provided the target van bucket has at least `pairs` available.
### 3.6. Lameness, Therapeutic Prescriptions and the Hold

Lameness is reported by the owner or by a veterinarian against a `horse_id`, carrying a `reported_on` date and a `severity` between 1 (`LAMENESS_MIN_SEVERITY`) and 5 (`LAMENESS_MAX_SEVERITY`) inclusive; anything outside that band is `ERR_VALUE_OUT_OF_RANGE`. The case is minted `OPEN`. Severity is what decides whether the yard's routine stops: a case whose `severity` is at least 3 (`LAMENESS_HOLD_SEVERITY_THRESHOLD`) has `hold_applied` set true and puts the horse's `hold_status` on `HOLD`, incrementing the horse's `version` by 1; a case of severity 1 or 2 is recorded with `hold_applied` false and changes nothing else at all. `reported_on` is recorded and never consulted again: it is the severity alone that decides the hold, and no window, no expiry and no ordering is keyed on the reported date. The horse's side of this is idempotent — a qualifying case raised against a horse whose `hold_status` is **already** `HOLD` is minted with `hold_applied` true, but the horse's row does not change, its `version` does not advance and the lameness chain is **not** re-run, so nothing is blocked, detached or released a second time.

A qualifying case starts the lameness chain described in §2.10, and each hop has its own guard. Appointments move to `BLOCKED` only from `SCHEDULED` or `CONFIRMED`; an appointment that is `UNROUTED`, `IN_PROGRESS`, already `BLOCKED`, completed, cancelled or `NO_SHOW` is left exactly as it is. Each blocked appointment has its `route_stop_id` cleared and its `version` incremented by 1, and the route's committed totals fall accordingly. Only reservations that are `RESERVED` are released; ones already `COMMITTED` or `RELEASED` are untouched. Only a stop that is still `PENDING` and is left with no attached appointment at all becomes `VOIDED`, and when it does the route's `committed_minutes` falls by that stop's `travel_minutes`, its `stop_count` falls by 1 and the stop's `version` increments by 1 — a stop whose recomputed minutes moved records that step even if it is not voided. Every route the chain reaches records exactly one mutation step, unconditionally, whether or not its meters actually moved; the same is true of every route the expiry chain reaches. Only a bucket whose `replenishment_flag` actually flips from true to false cancels inbound transfers, and only transfers still in `REQUESTED` are cancelled — a transfer already `IN_TRANSIT` keeps running.

Resolving a case closes it from either `OPEN` or `PRESCRIBED`, and the two legs differ. From `PRESCRIBED`, every prescription of that case whose `status` is `ACTIVE` moves to `REVOKED` with its own `version` incrementing by 1, the horse's `active_prescription_id` is nulled — but only when it actually pointed at one of the prescriptions just revoked — the horse's `hold_status` is recomputed and the case's `version` increments by 1. The horse's `version` advances only if one of those two horse fields really moved. Unlike the explicit revocation below, a resolve does **not** re-run the cycle derivation: the horse's `next_due_on` keeps whatever therapeutic figure it was last given until the next completion, activation, revocation or expiry recomputes it. From `OPEN` there is no prescription to revoke, so the resolve recomputes the horse's `hold_status` and increments the case's `version` by 1, and nothing else. Resolving a case that is already `RESOLVED` is refused with `ERR_INVALID_STATE`.

The hold clears only when nothing is holding it. After a resolve, the horse's `hold_status` becomes `CLEAR` exactly when no remaining case for that horse has `hold_applied` true **and** a `status` of `OPEN` or `PRESCRIBED`; one qualifying case still open keeps the horse on hold however many others are closed. When the hold does clear, every appointment of that horse whose `status` is `BLOCKED` returns to `UNROUTED` — note that it returns unattached, since the block already stripped its `route_stop_id`, and each such appointment's `version` increments by 1 — and the horse's `version` increments by 1.

Reopening moves a case from `RESOLVED` back to `OPEN` and recomputes the horse's `hold_status`; if the reopened case's `severity` is at least 3 the horse goes back on `HOLD` and its `version` increments by 1, and the case's `version` increments by 1 in every event. Reopening is deliberately **not** a re-run of the lameness chain: it does not block any appointment, does not detach anything, does not release any reservation and does not touch any bucket or transfer. The hold it re-imposes is felt only prospectively, through gate 4, on the next attempt to book, attach, add lines or start work. Reopening a case that is not `RESOLVED` is refused with `ERR_INVALID_STATE`.

A veterinarian drafts a therapeutic prescription against a case, supplying `lameness_case_id`, `issued_on`, `expires_on`, a non-empty duplicate-free `limb_scope` drawn from `LF`, `RF`, `LH` and `RH`, and a `prescribed_cycle_weeks` between 2 (`MIN_PRESCRIBED_CYCLE_WEEKS`) and 8 (`MAX_PRESCRIBED_CYCLE_WEEKS`) inclusive. The `expires_on` must be on or after `issued_on` and no more than 180 days (`PRESCRIPTION_MAX_DURATION_DAYS`) after it, else `ERR_VALUE_OUT_OF_RANGE`. The prescription copies `horse_id` from its case and is minted `DRAFT`, which authorises nothing.

Activation is the operation that makes it real, and it carries `expected_lameness_case_version`. It requires the prescription to be `DRAFT` and its `expires_on` to be on or after the logical clock date, else `ERR_INVALID_STATE`. On success: any sibling prescription of the **same case** whose `status` is `ACTIVE` moves to `SUPERSEDED`, its `version` incrementing by 1; the horse's `active_prescription_id` is set to this prescription; the horse's `next_due_on` is recomputed using the therapeutic cycle, but only when the horse's `last_completed_on` is already set, since there is no base date otherwise; the case moves from `OPEN` to `PRESCRIBED`, and a case already `PRESCRIBED` or `RESOLVED` keeps the status it has; and the prescription's `version` and the case's `version` each increment by 1. Superseding a sibling this way is a legitimate product operation rather than an error, which is precisely why the stale-case-version rung exists.

Withdrawal is the veterinarian's undo. Revoking moves an `ACTIVE` prescription to `REVOKED`, nulls the horse's `active_prescription_id` when it pointed at this prescription, recomputes the horse's `next_due_on` using the **routine** cycle again, and increments the prescription's `version` by 1 and the horse's `version` by 1 whenever either of those two horse fields actually moved. Revoking a prescription that is `DRAFT`, `EXPIRED`, `SUPERSEDED` or already `REVOKED` is refused with `ERR_INVALID_STATE`. Expiry is the same ending reached without anyone acting: when the logical clock advances past a live prescription's `expires_on`, that prescription becomes `EXPIRED` and the expiry chain of §2.10 runs — the horse's `active_prescription_id` is nulled and `next_due_on` reverts to the routine derivation, every `PLANNED` `CORRECTIVE` service line on a non-terminal appointment of that horse moves to `REMOVED`, and the affected appointments' `service_units` and `service_minutes` and their routes' committed totals are recomputed. "Non-terminal" here means an appointment whose `status` is not one of `COMPLETED`, `CANCELLED_ADVANCE`, `CANCELLED_LATE`, `CANCELLED_ONSITE` or `NO_SHOW`.

Liveness is checked against a date, and both bounds are inclusive: a prescription is live on a given date when its `status` is `ACTIVE`, its `issued_on` is on or before that date, and that date is on or before its `expires_on`. Coverage is set membership: a prescription covers a limb exactly when that limb is a member of its `limb_scope`.

### 3.7. Running the Route

The farrier's day proceeds stop by stop, in `sequence_index` order. Arriving moves a stop from `PENDING` to `ARRIVED`, and it requires the route to be `DISPATCHED` and every stop on the same route with a lower `sequence_index` to be already `COMPLETED` or `VOIDED`; an out-of-order arrival is refused with `ERR_INVALID_STATE`. Success increments the stop's `version` by 1.

Starting work on one horse moves that appointment from `SCHEDULED` or `CONFIRMED` to `IN_PROGRESS`, requires its stop to be `ARRIVED`, and increments the appointment's `version` by 1. The gates that guard it are the three §2.6 names in their own guard lists — gate 1, gate 4 and gate 5, in that order — so a horse that has gone on lameness hold since the route was built is refused here rather than silently worked on. Gate 2 and gate 3 are **not** consulted on a start: a dispatched route is exactly where a start belongs, and an owner who has fallen into prepayment since the visit was booked does not block work that is already on the road. The stop's `ARRIVED` precondition is rung 34, so it is reported before the credential check of rung 35.

Completing the visit is the largest single operation in this specification. It carries `performed_service_line_ids`, the ids of the lines actually carried out; every id must belong to this appointment and be `PLANNED`, else `ERR_SERVICE_LINE_NOT_FOUND`, and that existence rung is checked before the payload-shape rung, as §2.7 requires. The array may be **empty**: a visit at which nothing was done still completes, every `PLANNED` line simply becoming `OMITTED`. The appointment must be `IN_PROGRESS`. On success, in order: the listed lines move to `PERFORMED` and every other `PLANNED` line on the appointment moves to `OMITTED`, with `labor_cents` 0 and no effect on its limb whatsoever; each `PERFORMED` line computes its `labor_cents` and drives its limb's transition; every `RESERVED` reservation moves to `COMMITTED`, lowering the van bucket's `on_hand_pairs` and `reserved_pairs` by the reservation's `pairs` and leaving `available_pairs` alone, after which that bucket's `replenishment_flag` is recomputed and may flip to true; the appointment's `completed_on` is set to the logical clock date and its `rate_card_id` is pinned by selecting the effective card for that completion date; the appointment's `service_units` and `service_minutes` are then recomputed, the `OMITTED` lines having dropped out of the counted set while the `PERFORMED` ones remain in it, and its `estimated_total_cents` is left exactly as it stands; the owning client's `completed_visit_count` rises by 1 and the client's `version` increments by 1 — this **before** the invoice is built, which is what lets the loyalty tier of §3.9 see the count as it stands after this visit has been counted; an invoice is minted `DRAFT` with its lines and the appointment's `billing_status` moves from `UNBILLED` to `INVOICED`; the horse's `last_completed_on` is set to the completion date and its `next_due_on` recomputed, the horse's `version` incrementing by 1; a successor appointment is minted with two reminder rows of its own; and the appointment's `version` increments by 1 for the status step and again for the billing step, twice in all. Once all of that has run, the stop the visit is still attached to has its `service_minutes` and `end_minute` re-derived from the appointment's new figures, and the route's committed totals follow. The reservations commit whatever the lines did: a reservation raised for a SKU whose only line was `OMITTED` still moves to `COMMITTED` and still draws its pairs out of the van, and still prices as a `PRODUCT` line on the invoice.

Each performed line moves its limb according to what was done to it, and the resulting `shoeing_state` follows a single table. A `TRIM` always leaves the limb `BAREFOOT`, whatever it was before — including the ordinary barefoot trim, which is a self-loop from `BAREFOOT` back to `BAREFOOT` and a real event rather than a no-op — and it nulls `current_sku_code`. `NEW_SHOES` and `CORRECTIVE` leave the limb `SHOD`, or `SHOD_WITH_PAD` when the line's `with_pad` is true, and write the line's SKU code into `current_sku_code`; both are legal on a limb that is already `SHOD`, `SHOD_WITH_PAD` or `GLUED`, so pulling a glued shoe and nailing on a new one, or replacing a padded shoe with an unpadded one and thereby dropping the pad, are ordinary events. `GLUE_ON` leaves the limb `GLUED` and writes its SKU code into `current_sku_code`. A `RESET` reuses the shoe that is already there, so it leaves `shoeing_state` exactly as it found it — a self-loop on `SHOD`, on `SHOD_WITH_PAD` or on `GLUED` — and leaves `current_sku_code` unchanged.

The reset counter is the termination condition on those self-loops. A performed `RESET` increases the limb's `consecutive_reset_count` by 1; a performed `TRIM`, `NEW_SHOES`, `CORRECTIVE` or `GLUE_ON` resets it to 0. Since a line may only be added while that count is strictly below 1, a limb can be reset once and then must have a shoe replaced or be trimmed before it can be reset again. Every performed line, of every type, also sets its limb's `last_serviced_on` to the logical clock date, and every limb a performed line touches advances its own `version` by 1. Of the four fields this table writes, only `shoeing_state` and `consecutive_reset_count` are ever read back — by rungs 38 and 39 respectively. `current_sku_code` and `last_serviced_on` are recorded for the reader and consulted by no rule at all, so the SKU a limb currently wears never has to agree with the SKU a later line names.

A visit may end without work. Cancelling is available to the owner or the dispatcher from `UNROUTED`, `SCHEDULED` and `CONFIRMED`, and the tier is derived rather than chosen. Let the lead be the whole-calendar-day difference between the appointment's `scheduled_date` and the logical clock date. A lead of at least 3 days (`ADVANCE_CANCEL_MIN_LEAD_DAYS`) is the `ADVANCE` tier — exactly three days of notice still counts as advance notice, and two days does not. A lead of at least 1 day but less than 3 is the `LATE` tier. A lead of zero or negative is the `ONSITE` tier when the appointment is attached to a stop whose `status` is `ARRIVED`, and the `LATE` tier otherwise — including when the appointment is not attached at all.

Of the five gates only gate 5 guards a cancellation; the farrier gates, the route gate and the client gate are all silent, so a visit may be cancelled off a dispatched route, under an inactive farrier and for a suspended owner alike. Before the tier is derived, all three tiers select the rate card effective on the appointment's `scheduled_date` and refuse with `ERR_NO_EFFECTIVE_RATE_CARD` when there is none — the refusal lands even in the `ADVANCE` tier, which then makes no use of the card. The `LATE` and `ONSITE` tiers pin that card's id into the appointment's `rate_card_id`; the `ADVANCE` tier leaves `rate_card_id` exactly as it found it, null on a visit that was never completed, because it mints no invoice. The three tiers differ in every particular, and each is stated in full; where a tier mints an invoice the appointment's `version` advances twice, once for the cancellation step and once for the `billing_status` step, and where it does not it advances once. **`ADVANCE`** sets `cancellation_fee_cents` to 0, moves the appointment to `CANCELLED_ADVANCE`, detaches it from its stop and releases every `RESERVED` reservation with the route's committed totals falling accordingly, moves every `PENDING` and `SENT` reminder of the appointment to `FAILED`, mints **no** invoice at all, and increments the appointment's `version` by 1. **`LATE`** sets `cancellation_fee_cents` to 3500 (`LATE_CANCEL_FEE_CENTS`), moves the appointment to `CANCELLED_LATE`, detaches it and releases its reservations with the route's totals falling accordingly, mints a `DRAFT` invoice carrying only the cancellation-fee line, moves the appointment's `billing_status` to `INVOICED`, and increments the appointment's `version` by 1. **`ONSITE`** sets `cancellation_fee_cents` to 5500 (`ONSITE_CANCEL_FEE_CENTS`), moves the appointment to `CANCELLED_ONSITE`, **keeps it attached to the stop** so that it still bears a share of the trip fee when the stop closes out, releases every `RESERVED` reservation, mints a `DRAFT` invoice carrying the cancellation-fee line with the trip-fee line added later when the stop completes, moves `billing_status` to `INVOICED`, and increments the appointment's `version` by 1.

> **A detached visit cancelled at short notice.** An `UNROUTED` appointment cancelled with a lead of less than 3 days **follows the tier**: it moves to `CANCELLED_LATE` with the 3500-cent fee and a fee-only `DRAFT` invoice, exactly as an attached visit would. Refusing it would contradict gate 5, which explicitly admits `UNROUTED` for cancellation, and would strand such a visit with no exit at all, since the lead only shrinks. The `ONSITE` tier remains the only one that needs an attachment: a lead of zero or less on a visit that is not attached to an `ARRIVED` stop — including one attached to nothing — is `LATE`.

A no-show is recorded by the farrier standing at an `ARRIVED` stop, against an appointment that is `SCHEDULED` or `CONFIRMED`; gate 1 and gate 5 guard it, the stop's `ARRIVED` precondition is rung 34, and the rate card effective on the appointment's `scheduled_date` is then selected and **pinned into the appointment's `rate_card_id`**, `ERR_NO_EFFECTIVE_RATE_CARD` if there is none. It sets `cancellation_fee_cents` to 6500 (`NO_SHOW_FEE_CENTS`), moves the appointment to `NO_SHOW`, **keeps it attached** so that it too bears a trip-fee share, releases every `RESERVED` reservation, mints a `DRAFT` invoice carrying the no-show-fee line and moves `billing_status` to `INVOICED`, sets the appointment's `completed_on` to the logical clock date, recomputes the client's rolling no-show count and re-derives that client's `billing_standing`, and increments the client's `version` by 1 and the appointment's `version` by 2 — once for the no-show step and once for the billing step. The client's row records its mutation step whether or not the count or the standing actually moved.

Closing out a stop moves it from `ARRIVED` to `COMPLETED`, and it is refused with `ERR_INVALID_STATE` while any attached appointment is still `SCHEDULED`, `CONFIRMED` or `IN_PROGRESS` — every horse at the yard must have been worked, cancelled on site or marked absent first. Completion pins the stop's `trip_fee_cents` from the effective rate card for the route's `route_date` and the barn's `zone`, recomputes `billable_horse_count`, runs the trip-fee split of §3.9 across the billable appointments, and increments the stop's `version` by 1 — once for the whole operation, the split included. The card is selected before the status moves, so a route date with no effective card refuses with `ERR_NO_EFFECTIVE_RATE_CARD` even when the billable set is empty; and when the billable set is empty the stop still closes, with `trip_fee_cents` and `billable_horse_count` both left at 0 and no share written anywhere.

A warranty revisit is opened against a completed visit, by the owner or the dispatcher, supplying a `warranty_reason` of `SPRUNG_SHOE`, `LOST_SHOE` or `QUICK` together with a `scheduled_date`. The origin visit must have `status` `COMPLETED`, and the whole-day difference between the logical clock date and the origin's `completed_on` must be at least 0 and at most 21 days (`WARRANTY_WINDOW_DAYS`); the boundary is inclusive, so exactly twenty-one days later is still eligible and one day more is `ERR_WARRANTY_WINDOW_EXPIRED`. The new appointment is minted `UNROUTED` with `visit_kind` `WARRANTY_REVISIT`, the supplied `warranty_reason`, and `origin_appointment_id` pointing at the origin visit; like any other freshly minted appointment it carries no service lines yet, so its `service_units`, `service_minutes`, `estimated_total_cents`, `cancellation_fee_cents` and `trip_fee_share_cents` all start at 0. Its `cycle_source` is null, since no derivation produced it, and its `vet_present` is minted true exactly when the horse's `requires_sedation` is true at the moment the revisit is opened, so that it can be attached without further editing. Only gate 3 and gate 5 guard the operation — gate 4 does not, so a revisit may be opened for a horse on lameness hold. It is scheduled, routed, worked and billed exactly like any other visit, with one difference: its labour is free.
### 3.8. The Cycle, the Auto-Schedule and the Two Reminders

Hoof care repeats, and the interval has two competing sources. The horse's own `routine_cycle_weeks` is the ordinary answer. A live therapeutic prescription is the other, and while one lives it **overrides the routine cycle unconditionally** — even when its `prescribed_cycle_weeks` is not shorter than the routine figure. There is no "whichever is sooner" rule here; the clinical instruction simply wins.

The derivation takes a base date, which is the horse's `last_completed_on`. If the horse's `active_prescription_id` is not null, and that prescription's `status` is `ACTIVE`, and its `expires_on` is on or after the base date, then the cycle is that prescription's `prescribed_cycle_weeks` and the derivation is the therapeutic one; otherwise the cycle is the horse's `routine_cycle_weeks` and the derivation is the routine one. The horse's `next_due_on` is then the base date plus the cycle multiplied by 7 (`DAYS_PER_WEEK`) calendar days. Where the derivation produces an appointment, that appointment's `cycle_source` records which branch was taken — `THERAPEUTIC` or `ROUTINE` — and an appointment a human created by hand carries a null `cycle_source`. `cycle_source` and `origin_appointment_id` are both records of provenance and are consulted by no rule: the free labour of a warranty revisit is decided by its `visit_kind` alone, never by whether it names an origin, and no derivation reads a stored `cycle_source` back. The derivation is re-run on visit completion, on prescription activation, on prescription revocation and on prescription expiry; when the horse has no `last_completed_on` at all there is no base date and `next_due_on` stays null.

The raw due date is then **snapped forward** onto a day the barn will actually accept a farrier — the barn named by the horse's own `barn_id`, never the owner's `home_barn_id` and never the barn of the stop the completed visit sat at. Starting at an offset of 0 days and testing 1, 2 and then 3 (`SNAP_FORWARD_LOOKAHEAD_DAYS`) in turn, the first candidate date whose weekday is a member of the barn's `served_weekdays` and which does not appear in the barn's `blackout_dates` is taken. Because offset 0 is tested **first**, a raw due date that already lands on a served, non-blacked-out day is used unchanged. If all four candidates fail, the raw due date is used as it stands and the visit will need a human to place it.

Completing a visit therefore mints a successor: a new appointment for the same horse, `UNROUTED`, with `scheduled_date` set to the snapped-forward date and `cycle_source` set to the branch the derivation took; it too carries no service lines yet, so its `service_units`, `service_minutes`, `estimated_total_cents`, `cancellation_fee_cents` and `trip_fee_share_cents` all start at 0. Two reminder rows are minted against it, both `PENDING`, one at an `offset_days` of 7 (`REMINDER_OFFSET_DAYS_PRIMARY`) and one at an `offset_days` of 2 (`REMINDER_OFFSET_DAYS_SECONDARY`), each with a `due_on` equal to the appointment's `scheduled_date` minus its own `offset_days` and a null `sent_on`. The same pair of reminders is minted whenever an appointment is attached to a stop.

> **The successor visit's sedation flag.** The auto-minted successor carries `vet_present` **true** whenever the horse's `requires_sedation` is true, mirroring the sedation rung so that the successor can be attached without further edits; for any other horse it carries the ordinary default of false. The flag is read off the horse **at the moment the successor is minted**, that is at the completion of the previous visit, and it is a snapshot rather than a link: no endpoint can edit an appointment's `vet_present` afterwards, so a later `PATCH /horses/{id}` that sets `requires_sedation` true does **not** retro-fit the already-minted successor, which will then be refused at attachment by rung 47 with `ERR_SEDATION_VET_REQUIRED` until a human books a replacement visit carrying the flag. The same snapshot rule fixes the `vet_present` of a warranty revisit.

> **Reminders on an auto-minted successor that is later attached.** Both mintings happen, **unconditionally**: two rows when the successor is created and two more when it is attached to a stop, so an auto-minted visit that is later routed ends up with four reminder rows, two at each offset. No minting is ever skipped on the ground that the appointment already carries a pair, and a detach-then-reattach mints two more again.

Delivery is driven by the dispatcher, one reminder at a time, carrying a `delivery_outcome` of `DELIVERED` or `FAILED`. A `DELIVERED` outcome moves the reminder from `PENDING` — or from `FAILED`, since a failure may be retried — to `SENT` and sets its `sent_on` to the logical clock date. A `FAILED` outcome moves it from `PENDING` to `FAILED` and leaves `sent_on` null. Sending is only possible while the reminder's appointment has a `status` of `SCHEDULED` or `CONFIRMED`, and attempting to send a reminder that is already `SENT` or `ACKNOWLEDGED` is refused with `ERR_INVALID_STATE`. Each send increments the reminder's `version` by 1. A reminder's `due_on` and `offset_days` are recorded for the reader and gate nothing: a reminder may be sent, failed and retried at any clock date whatever, before its `due_on` or long after it.

Two reminders two days apart would be pestering, so delivery is suppressed by a recent sibling. A send **whose `delivery_outcome` is `DELIVERED`** is refused with `ERR_REMINDER_SUPPRESSED` when some **other** reminder of the same appointment has a `status` of `SENT` or `ACKNOWLEDGED`, a non-null `sent_on`, and a `sent_on` within 3 days (`REMINDER_SUPPRESSION_WINDOW_DAYS`) of the logical clock date in either direction. A `FAILED` outcome is never suppressed: recording a failure delivers nothing, so it is admitted whatever the siblings have done, and the suppression test is the last rung of the operation, below the reminder's own state precondition. The window is a closed interval on both sides: exactly three days apart is still suppressed, and four days apart is not.

> **Which code a send gets when the appointment is ineligible.** The **gate stays authoritative**. An appointment outside `SCHEDULED` and `CONFIRMED` — `BLOCKED`, `UNROUTED`, `IN_PROGRESS`, completed or cancelled — reports `ERR_APPOINTMENT_NOT_ELIGIBLE` at rung 33, and `ERR_REMINDER_SUPPRESSED` at rung 48 is reserved for the recently-sent-sibling case alone. The ladder is explicit that the lowest-numbered rung wins, and both codes stay reachable under this reading.

Acknowledgement is the owner's confirmation. It moves a `SENT` reminder to `ACKNOWLEDGED` and increments its `version` by 1; acknowledging a reminder that is `PENDING`, `FAILED` or already `ACKNOWLEDGED` is refused with `ERR_INVALID_STATE`. Its cross-entity effect is the point of the whole mechanism: when the reminder's appointment is `SCHEDULED` it moves to `CONFIRMED`, and that appointment's `version` increments by 1. `ACKNOWLEDGED` is where a reminder's life ends.

One further leg exists and it is system-driven: when a visit is cancelled in the `ADVANCE` tier, every reminder of that appointment that is `PENDING` or `SENT` moves to `FAILED`. No further send is possible afterwards, because the appointment has left the `SCHEDULED`/`CONFIRMED` set that sending requires.

### 3.9. Money: Pricing One Visit, Splitting One Stop, Settling One Client

Pricing runs twice over the life of a visit, and the two runs answer different questions.

The **estimate** is a forward look, refreshed into `estimated_total_cents` on every service-line change and on attachment. It prices the appointment's `PLANNED` lines off the rate card effective on the appointment's `scheduled_date`. It is the sum of the per-line labour amounts, plus for every SKU the required `pairs` multiplied by that SKU's `price_cents_per_pair`, plus the card's `pad_price_cents` multiplied by the number of `PLANNED` lines whose `with_pad` is true. It carries **no** trip-fee share, no discounts, no tax and no fees.

The **final** price is the invoice, built at completion off the rate card effective on the appointment's `completed_on`. A card that took effect between the scheduled date and the completion date changes the answer, and the invoice — not the estimate — is what the client owes.

**Labour, per line.** The base is the rate card price for that line's service type: `price_trim_cents` for a `TRIM`, `price_reset_cents` for a `RESET`, `price_new_shoes_cents` for `NEW_SHOES`, `price_corrective_cents` for `CORRECTIVE` and `price_glue_on_cents` for `GLUE_ON`. When the horse's `requires_sedation` is true, a surcharge of 1250 basis points (`SEDATION_LABOR_SURCHARGE_BP`) of that base is added — computed as the base multiplied by 1250, divided by 10000, and rounded half up **for this line alone**; when it is false the surcharge is 0. The line's `labor_cents` is the base plus that surcharge. One exception overrides everything above: on an appointment whose `visit_kind` is `WARRANTY_REVISIT`, `labor_cents` is forced to 0 for **every** line on the visit, while its product lines are still charged in full.

**Rounding order is pinned and is the commonest way to get this wrong.** Each line's sedation surcharge is rounded on its own, and the already-rounded line amounts are then summed into `labor_subtotal_cents`, counting only lines whose `status` is `PERFORMED`. Summing the base prices and rounding a single combined surcharge produces a different subtotal and is incorrect.

**Products.** `product_subtotal_cents` is the sum, over the appointment's reservations whose `status` is `COMMITTED`, of that reservation's `pairs` multiplied by its SKU's `price_cents_per_pair`, plus the rate card's `pad_price_cents` multiplied by the number of `PERFORMED` lines whose `with_pad` is true. Product amounts never carry a sedation surcharge.

The invoice is then assembled in a **pinned sequence**, because each step feeds the next and no intermediate value is ever re-rounded.

1. `labor_subtotal_cents`, as above.
2. `product_subtotal_cents`, as above.
3. `multi_horse_discount_cents`. When the appointment is attached to a stop whose `billable_horse_count` is at least 3 (`MULTI_HORSE_DISCOUNT_MIN_HORSES`), this is `labor_subtotal_cents` multiplied by 500 basis points (`MULTI_HORSE_DISCOUNT_BP`), divided by 10000 and rounded half up; otherwise it is 0. It applies to **labour only** — the product subtotal and the trip-fee share are untouched — and a visit that never reached a stop never qualifies. Because `billable_horse_count` is only computed when the stop closes out, this figure is 0 at the moment the invoice is first minted and takes its real value when the stop completion re-runs the build.
4. Labour after the multi-horse discount is `labor_subtotal_cents` minus `multi_horse_discount_cents`.
5. `loyalty_discount_cents`. The loyalty base is labour-after-multi-horse plus `product_subtotal_cents`. The rate is chosen from the client's `completed_visit_count` **as it stands after this visit has been counted**: at 30 visits or more (`LOYALTY_PREMIER_THRESHOLD_VISITS`) the rate is 600 basis points (`LOYALTY_PREMIER_BP`); at 12 visits or more (`LOYALTY_THRESHOLD_VISITS`) but fewer than 30 the rate is 300 basis points (`LOYALTY_STANDARD_BP`); below 12 the rate is 0. Both thresholds are inclusive. The discount is the loyalty base multiplied by the rate, divided by 10000, rounded half up. The premier tier is exactly double the standard tier on identical work.
6. The discount is split across the two legs it was computed over. When the loyalty base is 0, `loyalty_discount_product_cents` is 0. Otherwise it is `loyalty_discount_cents` multiplied by `product_subtotal_cents`, divided by the loyalty base, rounded half up. `loyalty_discount_labor_cents` is then `loyalty_discount_cents` minus `loyalty_discount_product_cents` — the product leg is the rounded one and the labour leg absorbs whatever remainder is left, which is what makes the loyalty-split invariant hold exactly.
7. `labor_net_cents` is labour-after-multi-horse minus `loyalty_discount_labor_cents`.
8. `taxable_product_base_cents` is `product_subtotal_cents` minus `loyalty_discount_product_cents`.
9. `tax_cents`. When the client's `tax_exempt` is false, it is `taxable_product_base_cents` multiplied by 725 basis points (`PRODUCT_TAX_RATE_BP`), divided by 10000, rounded half up. When `tax_exempt` is true, `tax_cents` is 0 while `taxable_product_base_cents` keeps the value computed at step 8, so the total falls by exactly the tax that would otherwise have been charged. Labour, the trip-fee share and cancellation or no-show fees are **always** untaxed: `LABOR_TAX_RATE_BP`, `TRIP_FEE_TAX_RATE_BP` and `FEE_TAX_RATE_BP` are all 0.
10. `trip_fee_share_cents`, which is 0 until the stop completes and is written by the split below.
11. `fee_cents`, which is the appointment's `cancellation_fee_cents`.
12. `total_cents` is `labor_net_cents` plus `taxable_product_base_cents` plus `trip_fee_share_cents` plus `fee_cents` plus `tax_cents`.
13. `balance_cents` is `total_cents` minus `paid_cents`.

The invoice's line rows record the same arithmetic in human-readable form. There is one `LABOR` line per `PERFORMED` service line, carrying that line's `limb` and `service_type`, a `quantity` of 1, a `unit_amount_cents` and an `amount_cents` both equal to the line's `labor_cents`. There is one `PRODUCT` line per `COMMITTED` reservation, carrying the SKU's `sku_code` as a plain string rather than a foreign key, a null `limb`, a `quantity` equal to the reservation's `pairs`, a `unit_amount_cents` equal to the SKU's `price_cents_per_pair` and the product of the two as `amount_cents`. There is one `PAD` line per `PERFORMED` line whose `with_pad` is true, carrying that line's `limb`, a `quantity` of 1 and the card's `pad_price_cents` as both `unit_amount_cents` and `amount_cents`. A `TRIP_FEE` line appears when a non-zero share is allocated, a `CANCELLATION_FEE` or `NO_SHOW_FEE` line when a non-zero fee is levied — `NO_SHOW_FEE` on a no-show and `CANCELLATION_FEE` on either fee-bearing cancellation tier — a `MULTI_HORSE_DISCOUNT` line and a `LOYALTY_DISCOUNT` line when those discounts are non-zero, and a `TAX` line when tax is non-zero. Discount lines carry a **negative** `amount_cents` and an equally negative `unit_amount_cents`; every other kind is positive. Only `PRODUCT` and `PAD` lines carry `taxable` true; every other kind carries `taxable` false. Every line carries a human-readable `description`, and every line has a `quantity` of 1 unless stated otherwise above; the fields a given kind does not use — `limb` on a `PRODUCT` line, `service_type` on anything but a `LABOR` line, `sku_code` on anything but a `PRODUCT` line — are null. The rows are emitted in a fixed order: every `LABOR` line in service-line order, then every `PRODUCT` line in reservation order, then every `PAD` line in service-line order, then `TRIP_FEE`, then the fee line, then `MULTI_HORSE_DISCOUNT`, then `LOYALTY_DISCOUNT`, then `TAX`. Invoice lines are immutable and therefore carry neither `updated_at` nor `version` — an implementation must not emit those two keys on one — but the *set* is not: every rebuild of an invoice discards all of its line rows and mints the whole set afresh, so the ids of an invoice's lines change when the stop closes out and the figures are recomputed. The invoice's own `version` advances once per rebuild that a caller can observe, and the rebuild that happens inside the trip-fee split records one such step.

**Splitting one stop's trip fee.** When a stop closes out, its `trip_fee_cents` is taken from the effective rate card for the route's `route_date`, choosing `trip_fee_zone_a_cents`, `trip_fee_zone_b_cents` or `trip_fee_zone_c_cents` according to the barn's `zone`. The billable set is the appointments attached to that stop whose `status` is `COMPLETED`, `NO_SHOW` or `CANCELLED_ONSITE`, ordered by `created_at` ascending; appointments cancelled in the `ADVANCE` or `LATE` tiers were detached and are therefore never billable. If the billable set is empty, the stop's `trip_fee_cents` is 0 and no share is written anywhere. Otherwise the stop's `trip_fee_cents` is the card's zone fee, its `billable_horse_count` is the size of the billable set, the base share is the fee divided by that count and rounded **down**, the remainder is the fee minus the base share multiplied by the count, and the **first** appointments in the sorted order — as many as the remainder — each receive one cent more than the base share while the rest receive the base share exactly. Each billable appointment receives its share in its own `trip_fee_share_cents`, advancing that appointment's `version` by 1, and its invoice receives the same figure and a `TRIP_FEE` line, each affected invoice then being rebuilt from step 1 with the new `billable_horse_count` in place and advancing its own `version` by 1. The rebuild re-reads the client's `completed_visit_count` and `tax_exempt` as they stand at that moment, so a loyalty threshold crossed by a sibling visit completed between the two events is felt here. A billable appointment that somehow carries no invoice — nothing in this specification produces one — simply keeps the share on the appointment row. The shares sum to the stop's fee to the cent, which is the first conservation invariant, and removing a horse from the billable set raises the surviving horses' shares.

> **Re-allocating after the stop has closed.** The split is a **one-shot at stop completion** and the shares written then are final. No later event recomputes it: the stop cannot close while any attached appointment is still workable, so every member of the billable set is already terminal — `COMPLETED`, `NO_SHOW` or `CANCELLED_ONSITE` — and none of them has any remaining transition that could take it out of the set. Voiding an invoice afterwards does not re-allocate, and neither does anything else.

**Issuing and voiding.** A `DRAFT` invoice is issued by the billing clerk, which moves it to `ISSUED` and sets its `issued_on` to the logical clock date, incrementing its `version` by 1. Voiding moves a `DRAFT` invoice, or an `ISSUED` invoice whose `paid_cents` is 0, to `VOID`, sets the appointment's `billing_status` to `VOIDED`, and increments the invoice's `version` by 1 and the appointment's `version` by 1. Voiding an invoice that is `PARTIALLY_PAID`, `PAID`, already `VOID`, or `ISSUED` with a non-zero `paid_cents` is refused with `ERR_INVALID_STATE`.

> **Issuing a cancelled visit's invoice.** "Or the appointment is unrouted" is a test of the **attachment**, not of the literal status token: any invoice whose appointment has a null `route_stop_id` may be issued, whatever that appointment's `status` reads. A `LATE`-cancellation invoice, whose appointment is detached but sits in `CANCELLED_LATE`, is therefore issuable; only an invoice whose appointment is still attached to a stop that has not reached `COMPLETED` is refused, with `ERR_INVALID_STATE`. The invoice's own `DRAFT` precondition is checked first, so an already-issued invoice reports `ERR_INVALID_STATE` on its own account.

**Settling.** A payment is applied by a waterfall over the client's outstanding invoices. It carries `amount_cents`, which must be strictly positive, together with `expected_client_version`. The targets are the client's invoices whose `status` is `ISSUED` or `PARTIALLY_PAID` and whose `balance_cents` is greater than zero, ordered by `issued_on` ascending and then, where those tie, by `created_at` ascending; `DRAFT` and `VOID` invoices are never targets. Working down that list, each invoice absorbs the smaller of the payment remaining and its own `balance_cents`: its `paid_cents` rises by that amount, its `balance_cents` falls by it, and its `status` becomes `PAID` when the balance reaches zero or `PARTIALLY_PAID` otherwise, each such invoice's `version` incrementing by 1. The oldest issued invoice is filled completely before the next is touched. When an invoice reaches `PAID`, its appointment's `billing_status` moves from `INVOICED` to `SETTLED` and that appointment's `version` increments by 1. Whatever remains after every target is full is added to the client's `credit_balance_cents`, and the client's `version` increments by 1 whether or not any invoice was actually touched. `credit_balance_cents` only ever accumulates: no later payment, deposit or invoice draws it down, and it is consulted by no gate and no derivation — `deposit_balance_cents`, which is a different counter, is the one gate 3 and the standing derivation read.

**Deposits and standing.** A deposit carries an `amount_cents` that must be strictly positive — a zero or negative figure is `ERR_VALUE_OUT_OF_RANGE`, and a missing or non-integer one is `ERR_VALIDATION`; it raises the client's `deposit_balance_cents` by that amount, re-derives the client's `billing_standing` and `no_show_count_rolling`, and increments the client's `version` by 1 whether or not either derived figure moved. A deposit is never refunded, drawn down or otherwise reduced by anything in this specification.

The rolling no-show count is the number of appointments belonging to that client's horses whose `status` is `NO_SHOW` and whose `completed_on` falls between the logical clock date minus 180 days (`NO_SHOW_ROLLING_WINDOW_DAYS`) and the logical clock date, **both bounds inclusive** — a strike whose `completed_on` equals the window's start date is still counted, one day older is not. That count is written to `no_show_count_rolling`. The stored figure is never itself an input: every re-derivation recounts the strikes from scratch against the clock of the moment and feeds that fresh number to the standing rule, so `no_show_count_rolling` is a report of the last recomputation rather than a running tally.

`billing_standing` is derived from it, and both thresholds are inclusive. A count of 5 or more (`NO_SHOW_SUSPEND_THRESHOLD`) gives `SUSPENDED`. A count of 3 or more (`NO_SHOW_PREPAY_THRESHOLD`) but fewer than 5, together with a `deposit_balance_cents` below 10000 (`PREPAY_DEPOSIT_MIN_CENTS`), gives `PREPAY_REQUIRED` — so the **third** strike inside the window is what tips a client into prepayment. Anything else gives `ACTIVE`. The derivation is re-run when a no-show is recorded, when a deposit is posted and whenever the logical clock moves.

The standing axis is a cycle, not a ratchet, and every leg is reachable. `ACTIVE` becomes `PREPAY_REQUIRED` when a recorded no-show pushes the rolling count to at least 3 while it is still below 5 and the deposit is below 10000 cents. `PREPAY_REQUIRED` becomes `ACTIVE` when a deposit lifts `deposit_balance_cents` to at least 10000 while the rolling count is still below 5, and it also becomes `ACTIVE` when a clock advance ages strikes out of the window until the rolling count falls below 3. `PREPAY_REQUIRED` becomes `SUSPENDED` when a recorded no-show pushes the rolling count to 5 or more. And `SUSPENDED` becomes `PREPAY_REQUIRED` when a clock advance ages strikes out until the rolling count is at least 3 but below 5. Every one of these legs increments the client's `version` by 1. A `SUSPENDED` client is refused at gate 3 whatever deposit is held; only time can bring it back.

Advancing the logical clock is thus a business event and not merely a test fixture. It expires every `ACTIVE` prescription whose `expires_on` falls strictly before the new date and runs the expiry chain for each, in `created_at` order, and it recomputes `no_show_count_rolling` and re-derives `billing_standing` for every client, in `created_at` order. A client whose row changed at all — the rolling count moved, or the standing moved, or both — records one mutation step; a client whose `billing_standing` did not move records that step all the same when only the count moved. The response reports both effects: `expired_prescription_ids` lists the prescriptions this move expired, and `restanding_client_ids` lists **only** the clients whose `billing_standing` this move changed, so a client whose count moved without crossing a threshold advances its `version` yet does not appear in the list. The clock accepts any parseable ISO 8601 instant, forward or backward — nothing forbids moving it into the past — and a value it cannot parse is `ERR_VALIDATION`.

### 4.1. Request and Response Index

This index names, for every operation, the fields it accepts, the shape it returns and the refusal codes reachable on it. A field written with a trailing question mark is optional; every other field is required. Precedence among the listed codes is always the §2.7 ladder order — the index does not restate it. One code is listed below more widely than it can actually fire: `ERR_NOT_RESOURCE_OWNER` appears against many list endpoints, but as §2.1 sets out no list endpoint applies the ownership rung, so on a list endpoint it is unreachable. Codes that arise only from a cascade or a recomputation the operation triggers are described in the §3 narrative that owns the operation rather than repeated here.

- **`POST /barns`** — HTTP 201 on success. Accepts `name`, `zone`, `served_weekdays`, `access_open_minute`, `access_close_minute`, `blackout_dates`?. Returns one `Barn`. Refusals: `ERR_UNAUTHENTICATED`, `ERR_FORBIDDEN_ROLE`, `ERR_VALIDATION`, `ERR_INVALID_ENUM`, `ERR_VALUE_OUT_OF_RANGE`.

- **`POST /reminders/{id}/send`** — HTTP 200 on success. Accepts `delivery_outcome`. Returns one `Reminder`. Refusals: `ERR_UNAUTHENTICATED`, `ERR_FORBIDDEN_ROLE`, `ERR_REMINDER_NOT_FOUND`, `ERR_VALIDATION`, `ERR_INVALID_ENUM`, `ERR_APPOINTMENT_NOT_ELIGIBLE`, `ERR_INVALID_STATE`, `ERR_REMINDER_SUPPRESSED`.
- **`POST /reminders/{id}/acknowledge`** — HTTP 200 on success. Accepts no body and no query parameters. Returns one `Reminder`. Refusals: `ERR_UNAUTHENTICATED`, `ERR_FORBIDDEN_ROLE`, `ERR_NOT_RESOURCE_OWNER`, `ERR_REMINDER_NOT_FOUND`, `ERR_APPOINTMENT_NOT_ELIGIBLE`, `ERR_INVALID_STATE`.
- **`POST /_clock/set_current_utc`** — HTTP 200 on success. Accepts `to_iso8601`. Returns an object carrying `current_utc`, `expired_prescription_ids` and `restanding_client_ids`. Refusals: `ERR_UNAUTHENTICATED`, `ERR_FORBIDDEN_ROLE`, `ERR_VALIDATION`.
