# Spice Sourcing Blend Private Label API — Product Requirements Document

## 1. Introduction

A global spice business lives or dies on two tensions that never fully resolve: agricultural variability and the promise of a consistent product. Every harvest year, every origin region, and every supplier delivers raw material whose flavor intensity, moisture, and safety profile differ from the last, while the retail shelf and the private-label customer expect an unchanging sensory specification at a contracted price. Around that core tension sit the operational realities of a modern flavor house: origin-specific sourcing relationships, laboratory screening for adulterants and contaminants, proprietary blend formulas whose true composition must never leak to the suppliers who provide the raw material, production lines shared between branded and private-label programs under strict allergen changeover and confidentiality controls, a category of hundreds of low-velocity items with long shelf lives, and the ever-present obligation to execute a precise, correctly scoped recall when something goes wrong.

This document specifies the API through which that business operates, mounted under the `/spice` path prefix. It covers supplier registration and raw-lot receiving; food-safety testing with per-analyte action levels and a strict segregation of duties between the analyst who posts a test and the manager who dispositions the lot; blend formula authoring with masked supplier-facing component codes; blend run sourcing with two lot-selection policies and a specification gate; production scheduling against weekly line-capacity pools with seasonal surge multipliers and computed allergen changeover classes; finished-batch shipping gated on shelf life and recall coverage; recall case management with two scope policies; and private-label agreements with year-to-date commitment tracking and dedicated capacity reservations. Eight roles share the surface, every mutation is immediately consistent, and a server-side logical clock — not wall-clock time — drives every date-sensitive calculation so the system is fully testable end to end.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role under which that user acts. If either header is missing, or if `X-User-Role` is not one of the declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the role is valid but is not listed among the roles authorized for the target endpoint, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). The role catalog is fixed and spelled exactly as follows: `PlatformAdmin`, `SupplyPlanner`, `QualityAnalyst`, `QualityManager`, `FlavorScientist`, `ProductionScheduler`, `RecallCoordinator`, and `SupplierRep`.

The roles partition the workflow by responsibility. A `PlatformAdmin` is the operations administrator: it owns the logical clock and production-line master data, and it is the only role that may set the clock or create a production line. A `SupplyPlanner` is the global sourcing planner: it registers suppliers, receives raw lots, and ships finished batches. A `QualityAnalyst` is the food-safety laboratory analyst who posts safety test results. A `QualityManager` is the quality disposition authority, deliberately segregated from test posting. A `FlavorScientist` owns blend formulation and blend runs, and is the only role that ever sees full formula composition — true spice codes and proportions. A `ProductionScheduler` owns production runs, capacity reservations, and private-label agreements. A `RecallCoordinator` opens, initiates, and closes recall cases. A `SupplierRep` is an external supplier representative with a deliberately narrow read surface.

Identity semantics differ by role. When `X-User-Role` is `SupplierRep`, `X-User-ID` is the `id` of the acting `Supplier`; ownership checks on any resource that references a `Supplier` compare the resource's foreign-key field to `X-User-ID`. Concretely, a `SupplierRep` may only read lots whose `supplier_id` equals `X-User-ID`, and anything touching another supplier's lot behaves as though that lot does not exist — a direct read of another supplier's lot fails with `ERR_NOT_FOUND` (HTTP 404), never with an authorization error, and list results are implicitly restricted to the caller's own lots. When `X-User-Role` is any of `PlatformAdmin`, `SupplyPlanner`, `QualityAnalyst`, `QualityManager`, `FlavorScientist`, `ProductionScheduler`, or `RecallCoordinator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — for example, as `analyst_user_id` on a safety test, where the posting workflow copies it — but does not compare it to any entity's `id`, except where a business rule explicitly references it, such as the segregation-of-duties check on lot disposition described in §3.2.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All list endpoints accept the optional query parameters `limit` and `offset`. The `limit` parameter defaults to 10, must be at least 1, and may not exceed 100; the `offset` parameter defaults to 0. List results are always sorted by `created_at` ascending. The `meta` object of a list response carries the pagination fields `limit`, `offset`, `total_count`, and `has_more`, where `total_count` is the full number of matching records and `has_more` indicates whether any records exist beyond the returned page. Malformed pagination parameters — a non-integer `limit` or `offset`, a `limit` below 1 or above 100, or a negative `offset` — are rejected with `ERR_INVALID_REQUEST` (HTTP 400), and the same rejection applies to a non-integer `crop_year` filter or an enum-valued list filter (`status`, `spice_code`, `brand_type`, `commercial_status`, `quality_status`) carrying a value outside its declared set.

### 2.4. Common Resource Properties

Every persisted resource carries a server-minted `id` — a UUID with no type prefix — assigned at creation and returned in every representation. Resources additionally carry `created_at` and `updated_at`, both ISO 8601 UTC timestamps rendered with three fractional digits, and an integer `version` that starts at exactly 1 when the resource is created and that the server increments by exactly 1 on every mutation of the resource; the current value is always returned in the resource representation. The sole exception to this common shape is the safety test record: a safety test is an append-only, immutable event carrying only `id` and `created_at`, with both `updated_at` and `version` absent from it, and once posted it is never modified. Newly created resources are returned with HTTP 201; reads, and actions that modify an existing resource — including state transitions — return HTTP 200.

### 2.5. The Logical Clock

The server maintains a logical clock that is the single source of "now" for the entire system. At server start, before any clock-setting call, the logical clock reads exactly 2026-09-01T00:00:00Z, and it never falls back to wall-clock time at any point. An administrator-only, test-driving capability sets the logical clock to a supplied instant: the request carries the target instant in the `to_iso8601` field, and the response reports the resulting clock value in the `current_utc` field. Setting the clock is absolute, not relative — the supplied value becomes the clock, replacing whatever value it previously held. Every date-sensitive calculation in the system reads this clock and nothing else: the `produced_at` timestamp stamped when a production run completes, the derived `best_by_date` of a finished batch, the remaining-shelf-life computation behind the shipping gate, and the ISO-8601 week numbering that determines which weekly capacity pool a production run or reservation consumes. Consequently, all downstream date arithmetic changes the moment the clock is set, with no caching of earlier values.

### 2.6. Decimal Arithmetic, Precision, and Rounding

All kilogram arithmetic in the system is exact decimal arithmetic carried to three decimal places, and all money arithmetic — expressed in integer cents — is exact decimal arithmetic as well; every rounding step uses round-half-up, and binary floating-point arithmetic is forbidden anywhere in a calculation. As a concrete consequence, multiplying 1.005 by 100 must yield exactly 100.5, which then rounds to exactly 101. Three deliberate exceptions to round-half-up exist, each pinned where it applies: the per-line single-lot allocation cap in blend sourcing is rounded down to three decimal places, the weekly line-capacity pool is rounded down to a whole kilogram, and the remaining-shelf-life computation floors the exact duration between `best_by_date` and the logical clock to whole days before converting to a percentage. Computed percentages that persist on a blend run — `residual_flavor_pct` and `blended_moisture_pct` — are rounded half-up to three decimal places. Kilogram quantities arriving as inputs — a received lot's `quantity_kg`, a blend run's `target_batch_kg`, and a production run's `quantity_kg` — are likewise rounded half-up to three decimal places at intake and stored at that precision. Cost rollups are integer cents, rounded half-up at each pinned step of the costing pipeline described in §3.4.

### 2.7. Optimistic Concurrency Control on Line Scheduling

Scheduling a production run is the one write in the system guarded by optimistic concurrency control. The scheduling request must carry `expected_line_version` — a non-optional input field holding the `version` of the target production line as the client last observed it. If the line's current `version` does not equal `expected_line_version` at the moment the request is evaluated, the schedule is rejected with `ERR_STALE_VERSION` (HTTP 412), preventing the client from scheduling against a stale view of the line — the canonical case being another writer having just scheduled a run on the same line, which legitimately consumed weekly pool capacity and possibly became the changeover predecessor. A successful scheduling increments the line's `version` by 1, so every scheduling invalidates previously observed versions. No endpoint other than production-run scheduling takes a version field. Separately, and for informational completeness, every commit attempt on a blend run — whether it succeeds or persists a failure — increments the blend run's own `version` by exactly 1, as detailed in §3.4.

### 2.8. Request Evaluation Pipeline

Every request is evaluated against the following checks in the stated order, and the first check that fails determines the response — later checks are not consulted. This ordering is observable behavior: when two checks could both reject a request, the one listed earlier produces the error.

1. Authentication: `X-User-Role` and `X-User-ID` are present and the role is one of the declared roles, else `ERR_UNAUTHENTICATED` (HTTP 401).
2. Authorization: the role is listed among the endpoint's authorized roles, else `ERR_UNAUTHORIZED` (HTTP 403). Entity-backed ownership for `SupplierRep` is enforced as invisibility at the existence step below, not here.
3. Request shape: required fields are present, types are valid, enum values fall within their declared sets, and unknown fields are rejected, else `ERR_INVALID_REQUEST` (HTTP 400).
4. Value ranges and cross-field semantics: `quantity_kg` greater than 0, `measured_value` at least 0, `crop_year` between 2000 and 2100 inclusive, `target_proportion_pct` greater than 0 and at most 100, `reserved_kg_per_week` greater than 0, `capacity_kg_per_shift` greater than 0, `annual_commitment_kg` greater than 0, `window_end` strictly after `window_start`, and `product_codes` non-empty, else `ERR_VALIDATION` (HTTP 422). The field-range rules stated alongside each resource in §3 — `flavor_intensity_units` greater than 0, `moisture_pct` between 0 and 100 inclusive, `cost_per_kg_cents` zero or greater, `target_flavor_units` greater than 0, `min_lot_flavor_units` zero or greater, and `supported_changeover_classes` non-empty and containing `NONE` — are enforced at this same step with `ERR_VALIDATION` (HTTP 422).
5. Existence: path ids and body foreign-key references — `supplier_id`, `formula_id`, `line_id`, `blend_run_id`, `private_label_agreement_id`, `agreement_id`, `suspect_lot_id`, `suspect_batch_id`, `supersedes_formula_id` — must resolve to existing entities, else `ERR_NOT_FOUND` (HTTP 404). A `SupplierRep` reading another supplier's lot lands here: the id is invisible and the outcome is `ERR_NOT_FOUND`.
6. Stale-version guard: on production-run scheduling only, `expected_line_version` must equal the line's current `version`, else `ERR_STALE_VERSION` (HTTP 412).
7. Generic state legality: the target entity must be in a legal from-state for the action — a blend run must be `DRAFT` to be committed and `DRAFT` or `COMMITTED` (and not referenced by any `COMPLETED` production run) to be voided; a formula must be `DRAFT` to receive lines or be activated; a production run must be `SCHEDULED` to be completed or cancelled; a batch's `commercial_status` must be `CREATED` to ship; a recall case must be `DRAFT` to be initiated and `INITIATED` to be closed — else `ERR_INVALID_STATE` (HTTP 409).
8. Lot terminal guard: posting a test or a disposition against a `REJECTED` or `DEPLETED` lot is rejected with `ERR_LOT_TERMINAL` (HTTP 409); for those two actions this lot-specific error is reported rather than the generic state error.
9. Segregation of duties: on lot disposition, no safety test on the lot may carry an `analyst_user_id` equal to the caller's `X-User-ID`, else `ERR_DISPOSITION_FORBIDDEN` (HTTP 403).
10. Changeover support: the computed `changeover_class_required` must be a member of the line's `supported_changeover_classes`, else `ERR_ALLERGEN_CHANGEOVER_INSUFFICIENT` (HTTP 409).
11. Shipping quality gate: the batch's `quality_status` must be `CLEAR` and no `INITIATED` recall case may cover the batch, else `ERR_BATCH_NOT_SHIPPABLE` (HTTP 409).
12. Failing-test gate: an accept disposition requires that the latest safety test of each test type on the lot — latest by `created_at` — is not a `FAIL`, else `ERR_LOT_HAS_FAILING_TEST` (HTTP 409).
13. Active-formula gate: blend-run creation, blend-run commit, and production-run scheduling each require the referenced formula to be `ACTIVE`, else `ERR_FORMULA_NOT_ACTIVE` (HTTP 409).
14. Committed-blend gate: production-run scheduling requires the referenced blend run to be `COMMITTED`, else `ERR_BLEND_RUN_NOT_COMMITTED` (HTTP 409).
15. Line window exclusivity: the half-open window from `window_start` to `window_end` must not intersect any non-`CANCELLED` run on the same line; adjacency — one run's `window_end` exactly equal to another's `window_start` — is allowed. Violations are `ERR_LINE_WINDOW_CONFLICT` (HTTP 409).
16. Shelf-life gate: shipping requires at least 75.0 percent of shelf life remaining at ship time, else `ERR_SHELF_LIFE_INSUFFICIENT` (HTTP 409); the exact computation and its passing boundary are defined in §3.6.
17. Test-suite gate: an accept disposition requires at least one recorded `PASS` safety test for each of `MICRO`, `ADULTERANT_SCREEN`, and `MOISTURE`, else `ERR_TEST_SUITE_INCOMPLETE` (HTTP 409).
18. Product-code uniqueness: a `product_code` already held by a `DRAFT` or `ACTIVE` formula is rejected with `ERR_DUPLICATE_PRODUCT_CODE` (HTTP 409) unless `supersedes_formula_id` chains the same `product_code`.
19. Proportion-sum gate: formula activation requires the sum of `target_proportion_pct` over the formula's lines to be within 0.01 of 100.0 — inclusive, so an absolute difference of exactly 0.01 passes — else `ERR_PROPORTION_SUM_INVALID` (HTTP 422); an empty formula sums to 0 and fails.
20. Agreement-required gate: scheduling a run whose formula's `brand_type` is `PRIVATE_LABEL` without `private_label_agreement_id` is rejected with `ERR_AGREEMENT_REQUIRED` (HTTP 422).
21. Agreement-scope gate: when `private_label_agreement_id` is supplied, the formula's `product_code` must be a member of the referenced agreement's `product_codes`, else `ERR_PRODUCT_NOT_IN_AGREEMENT` (HTTP 422).
22. Quantity-match gate: a production run's `quantity_kg` must equal the referenced blend run's `target_batch_kg`, else `ERR_QUANTITY_MISMATCH` (HTTP 422).
23. Formula-match gate: a production run's `formula_id` must equal the referenced blend run's `formula_id`, else `ERR_FORMULA_MISMATCH` (HTTP 422).
24. Recall-suspect gate: recall creation requires exactly one of `suspect_lot_id` or `suspect_batch_id` to be present, for every `trigger_type`, else `ERR_RECALL_SCOPE_INVALID` (HTTP 422).
25. Candidate-pool gate: blend commit aborts with `ERR_NO_QUALIFYING_LOTS` (HTTP 422) when any formula line's qualifying candidate pool is empty.
26. Allocatable-quantity gate: blend commit aborts with `ERR_INSUFFICIENT_LOT_QUANTITY` (HTTP 409) when a line's total max-allocatable kilograms — respecting the per-lot cap — fall below the needed kilograms.
27. Specification gate: blend commit rejects with `ERR_BLEND_OUT_OF_SPEC` (HTTP 422) when the absolute `residual_flavor_pct` exceeds the formula's `flavor_tolerance_pct` or the `blended_moisture_pct` exceeds the formula's `max_moisture_pct`.
28. Run-capacity gate: scheduling is rejected with `ERR_CAPACITY_EXCEEDED` (HTTP 409) when it would drive the line's weekly pool for the ISO week of `window_start` negative.
29. Reservation-capacity gate: reservation creation is rejected with `ERR_RESERVATION_OVER_COMMIT` (HTTP 409) when it would drive any intersected ISO week's pool negative.

### 2.9. Nested Resources and Path Validation

Two resources exist only in the context of a parent: safety tests belong to a raw lot, and formula lines belong to a blend formula. Their URLs nest accordingly — the lot's `id` appears in the path of every test operation, and the formula's `id` in the path of every line operation. Path parameters are validated strictly left to right: the parent `id` must resolve to an existing entity before the sub-resource is considered, and an unresolvable parent id is rejected with `ERR_NOT_FOUND` (HTTP 404) regardless of the rest of the request. The same left-to-right discipline applies to every parameterized endpoint in the system.

### 2.10. Recipe Confidentiality and the Masked Supplier View

Blend formulas are trade secrets, and the API enforces that secrecy structurally. Every formula line carries a system-assigned `masked_component_code`, a pseudonym built from the prefix `CMP-` followed by a letter assigned in creation order within the formula — the first line created is `CMP-A`, the second `CMP-B`, and so on. When a `SupplierRep` lists the lines of a formula, the response is the masked view: `spice_code` and `target_proportion_pct` are replaced by null, while `masked_component_code`, `allergen_profile`, `organic_required`, and `min_lot_flavor_units` remain visible — the allergen and qualification fields stay visible because suppliers need them for safe handling and lot qualification. A `FlavorScientist` listing the same lines sees every field, and no other role may list formula lines at all. A supplier's `knowledge_tier` — `MASKED_ONLY` by default, or `FULL` — records the contractual knowledge level of the supplier relationship: `MASKED_ONLY` suppliers only ever see masked component codes, never true spice codes or proportions, and the API serves the masked view to `SupplierRep` callers in all cases.

### 2.11. Quantity and Capacity Invariants

Two invariants hold at every instant, across every operation. The first is the raw-lot mass invariant: for every lot, `quantity_kg` always equals the sum of `quantity_remaining_kg`, `quantity_consumed_kg`, and `quantity_wasted_kg`. Receiving establishes the invariant with the full quantity in `quantity_remaining_kg`; blend-run commit moves kilograms from remaining to consumed; rejecting a lot moves all remaining kilograms into `quantity_wasted_kg`; voiding a committed blend run moves kilograms back from consumed to remaining. No operation creates or destroys mass. The second is the weekly capacity invariant: for every production line and every ISO week, the week's pool kilograms minus the kilograms scheduled or completed against it minus the kilograms reserved against it must remain greater than or equal to zero; any write that would drive this figure negative is rejected outright rather than queued. Both invariants are enforced atomically within the triggering request — every side effect of an operation lands in the same transaction, and the system is immediately consistent with no eventual-convergence window.

## 3. Business Logic & Workflows

### 3.1. Supplier Registration and Raw-Lot Receiving

Everything begins with the sourcing network. A `SupplyPlanner` registers each supplier with its legal `name`, its primary sourcing `origin_country` (free text, such as a two-letter country code), an optional `certifications` array, and an optional `knowledge_tier`. The `certifications` array defaults to empty when omitted, and each member must be one of `ORGANIC`, `KOSHER`, `HALAL`, or `NON_GMO`. The `knowledge_tier` is `MASKED_ONLY` or `FULL` and defaults to `MASKED_ONLY` when omitted, recording how much of the proprietary formula picture the supplier relationship is contractually allowed to see (§2.10).

Against a registered supplier, the same planner receives raw spice lots. Receiving a lot records the sourcing `supplier_id`, the `spice_code` (exactly one of `BLACK_PEPPER`, `PAPRIKA`, `CUMIN`, `OREGANO`, `GARLIC_POWDER`, or `CINNAMON`), an `origin_region` label such as Malabar or La Vera, the `crop_year` (an integer harvest year between 2000 and 2100 inclusive), the gross `quantity_kg` (greater than 0, at three-decimal precision), the lot's `flavor_intensity_units` (greater than 0 — a generic sensory scale per kilogram onto which measures such as ASTA color, piperine content, or volatile-oil content are mapped), the received `moisture_pct` (between 0 and 100 inclusive), the contract `cost_per_kg_cents` (an integer number of cents, zero or greater), the `allergen_profile` (exactly one of `NONE`, `CELERY`, `MUSTARD`, `SESAME`, or `GLUTEN`), and optionally `organic_certified` (defaulting to false). A freshly received lot starts in `RECEIVED` status, with `quantity_remaining_kg` initialized to the full `quantity_kg` and both `quantity_consumed_kg` and `quantity_wasted_kg` initialized to 0, establishing the mass invariant of §2.11. Lot listings support optional `supplier_id`, `status`, `spice_code`, and `crop_year` filters, and a `SupplierRep` browsing lots sees only lots whose `supplier_id` matches the caller's `X-User-ID`.

### 3.2. Laboratory Testing, Disposition, and the Segregation of Duties

A lot in `RECEIVED` cannot be blended, shipped against, or trusted until the laboratory speaks. A `QualityAnalyst` posts safety test results against a lot, each carrying a `test_type`, a `measured_value` (zero or greater), and a `lab_code` identifying the laboratory; the server copies the posting analyst's `X-User-ID` into `analyst_user_id`, computes the `result`, and links the record to the lot via `lot_id` taken from the URL path. Test records are immutable, append-only events, and the tests recorded on a lot can be listed back by authorized roles. Four test types exist, each with a fixed unit and a pinned action level. An `ADULTERANT_SCREEN` test — measured in parts per million against the lead action level — fails when `measured_value` is greater than or equal to 2.00, so a reading of exactly 2.00 is a `FAIL`. A `PESTICIDE` test, also in parts per million, fails when `measured_value` is greater than or equal to 0.10, so exactly 0.10 is a `FAIL`. A `MICRO` test, measured in colony-forming units per gram, fails only when `measured_value` is strictly greater than 100000 — a reading of exactly 100000 is a `PASS`. A `MOISTURE` test, measured in percent, fails only when `measured_value` is strictly greater than 12.0 — exactly 12.0 is a `PASS`. Anything not reaching its action level is a `PASS`.

Posting tests drives the lot's state machine automatically. The very first test recorded on a `RECEIVED` lot moves it to `IN_TEST`. A test posted while the lot is `QUARANTINED` — a retest — moves it back to `IN_TEST`. And the moment an `ADULTERANT_SCREEN` test computes `FAIL`, the lot is auto-quarantined: a lot in `IN_TEST` or even in `ACCEPTED` moves immediately to `QUARANTINED`, and the adulterant cascade of §3.7 fires within the same request. Tests posted while a lot is already `IN_TEST` or `ACCEPTED`, when they are not adulterant failures, leave the status unchanged; such a status-preserving post is not a mutation of the lot, so the lot's `version` and `updated_at` do not move. The retest rule and the adulterant rule compose within a single request: an `ADULTERANT_SCREEN` `FAIL` posted while the lot is `QUARANTINED` first moves it to `IN_TEST` as a retest, and the auto-quarantine rule then applies to that `IN_TEST` lot — the lot ends the request back in `QUARANTINED` and the adulterant cascade of §3.7 fires again (its batch-hold and case-creation effects deduplicating as §3.7 describes). Attempting to post a test against a `REJECTED` or `DEPLETED` lot is rejected with `ERR_LOT_TERMINAL` (HTTP 409).

Disposition authority rests with a `QualityManager`, who acts on a lot in `IN_TEST` or `QUARANTINED` by submitting an `action` with an optional `reason`; the `reason` is accepted with the request but is not persisted on the lot representation. Three actions exist. `QUARANTINE` moves an `IN_TEST` lot to `QUARANTINED`. `REJECT` moves an `IN_TEST` or `QUARANTINED` lot to `REJECTED` and writes the lot off: all of `quantity_remaining_kg` is added to `quantity_wasted_kg` and `quantity_remaining_kg` becomes 0, preserving the mass invariant. `ACCEPT` moves an `IN_TEST` or `QUARANTINED` lot to `ACCEPTED`, and is the most heavily gated action in the system. Every disposition — accept, quarantine, or reject — is subject to a hard segregation of duties: if any safety test on the lot carries an `analyst_user_id` equal to the dispositioning manager's `X-User-ID`, the action is rejected with `ERR_DISPOSITION_FORBIDDEN` (HTTP 403); the person who tested a lot may never disposition it. An accept then faces two further gates, evaluated after the segregation check and in this order: first, the latest safety test of each test type on the lot (latest by `created_at`) must not be a `FAIL`, else `ERR_LOT_HAS_FAILING_TEST` (HTTP 409); second, the lot must carry at least one recorded `PASS` for each member of the required suite — `MICRO`, `ADULTERANT_SCREEN`, and `MOISTURE` — else `ERR_TEST_SUITE_INCOMPLETE` (HTTP 409). Notably, `PESTICIDE` results inform the record but are not part of the required suite for acceptance. A successful accept additionally unwinds any outstanding adulterant-cascade artifacts naming the lot, as detailed in §3.7 — and because an exonerating retest moves an auto-quarantined lot back to `IN_TEST` before an accept can pass its gates, that unwinding is keyed to the cascade's artifacts, not to the lot sitting in `QUARANTINED` at the moment of acceptance. A disposition attempted against a lot that is not in a legal from-state for the requested action — such as a `RECEIVED` lot that has never been tested, or an `ACCEPTED` lot — is rejected with `ERR_INVALID_STATE` (HTTP 409), while a `REJECTED` or `DEPLETED` lot draws `ERR_LOT_TERMINAL` instead. A lot's lifecycle is cyclic by design: quarantine and retest may iterate any number of times before the terminal `REJECTED` state — or the consumption-driven `DEPLETED` state of §3.4 — closes it.

### 3.3. Proprietary Blend Formulation

A `FlavorScientist` authors blend formulas. Creating one records the finished `product_code`, a display `name`, the `brand_type` (`BRANDED` or `PRIVATE_LABEL`), and the sensory target `target_flavor_units` (greater than 0). Two specification bounds accompany the target, both optional: `flavor_tolerance_pct`, defaulting to 2.0, which is the allowed absolute residual percent around the target, and `max_moisture_pct`, defaulting to 10.0, the blend moisture ceiling. An optional `supersedes_formula_id` declares the formula a revision of an existing one; when supplied it must resolve to an existing formula carrying the same `product_code`, and the new formula's `revision` becomes the superseded formula's `revision` plus 1, whereas a fresh `product_code` starts at `revision` 1. Product codes are unique among formulas in `DRAFT` or `ACTIVE`: creating a formula whose `product_code` is already held by a `DRAFT` or `ACTIVE` formula is rejected with `ERR_DUPLICATE_PRODUCT_CODE` (HTTP 409) unless the new formula chains that same code through `supersedes_formula_id`. A superseding reference that cannot be resolved fails existence validation with `ERR_NOT_FOUND`, and one that points at a formula carrying a different `product_code` violates the create's cross-field semantics and fails with `ERR_VALIDATION` (HTTP 422). New formulas are born in `DRAFT`. Formula listings accept optional `status`, `brand_type`, `product_code`, and `supersedes_formula_id` filters.

Composition is added line by line, and only while the formula remains `DRAFT` — adding a line to an `ACTIVE` or `RETIRED` formula is rejected with `ERR_INVALID_STATE`. Each line names the true `spice_code`, the `target_proportion_pct` (greater than 0 and at most 100), the `allergen_profile`, an optional `organic_required` flag (default false — when true, only lots with `organic_certified` true may supply the line), and the qualification floor `min_lot_flavor_units` (zero or greater — candidate lots must carry `flavor_intensity_units` of at least this value). The server assigns each line its `masked_component_code` in creation order, per §2.10, and stamps the line's `formula_id` from the URL path. Only a `FlavorScientist` ever sees `spice_code` and `target_proportion_pct`; suppliers see the masked view.

Activation is the point of no return for composition. Activating a `DRAFT` formula requires the sum of its lines' `target_proportion_pct` to sit within 0.01 of the 100.0 target — inclusive, so a sum of 99.99 or 100.01 passes, while a formula with no lines at all sums to 0 and fails — else activation is rejected with `ERR_PROPORTION_SUM_INVALID` (HTTP 422). Successful activation flips the formula to `ACTIVE` and simultaneously retires every other `ACTIVE` formula carrying the same `product_code`: each such formula's status becomes `RETIRED` in the same request. This supersede cascade is how a revision chain takes over a product code, and it is the only transition into `RETIRED`, which is terminal. Only `ACTIVE` formulas may feed blend runs and production schedules (§3.4, §3.5).

### 3.4. Blend Run Sourcing, Specification Control, and Costing

With an active formula in hand, a `FlavorScientist` creates a blend run from a `formula_id` (which must reference an `ACTIVE` formula, else `ERR_FORMULA_NOT_ACTIVE`), a `selection_policy` — `COST_MIN` or `FIFO_AGE` — and a `target_batch_kg` (greater than 0). A new blend run is `DRAFT`, and its five computed fields — `selected_allocations`, `residual_flavor_pct`, `blended_moisture_pct`, `cost_total_cents`, and `spec_status` — are null until the first commit attempt. Blend-run listings accept optional `formula_id` and `status` filters.

Committing is where sourcing mathematics meets the lot inventory. The commit walks the formula's lines in line-creation order and, for each line, first derives the needed kilograms: `target_batch_kg` multiplied by the line's `target_proportion_pct` and divided by 100, rounded half-up to three decimal places. From the needed quantity it derives the per-line single-lot cap: 40.0 percent of the needed kilograms, rounded down to three decimal places — no single lot may supply more than that cap for the line. The line's candidate pool is then every raw lot that is in `ACCEPTED` status (lots in `RECEIVED`, `IN_TEST`, `QUARANTINED`, `REJECTED`, or `DEPLETED` are never selected), whose `spice_code` equals the line's, whose `flavor_intensity_units` are at least the line's `min_lot_flavor_units`, that satisfies the organic requirement (when `organic_required` is true the lot must have `organic_certified` true), and whose `quantity_remaining_kg` is greater than 0. If that pool is empty, the commit aborts with `ERR_NO_QUALIFYING_LOTS` (HTTP 422) and persists nothing. Otherwise the pool is ordered by the run's selection policy: under `COST_MIN`, ascending `cost_per_kg_cents` with ties broken by ascending `created_at`, so the cheapest lots are consumed first; under `FIFO_AGE`, ascending `crop_year` with the same `created_at` tie-break, so the oldest crop is consumed first. Given identical inventory, the two policies select genuinely different lot sets — and therefore produce a different `cost_total_cents` — whenever cost order and age order disagree. The commit then walks the ordered pool, allocating from each lot the minimum of three quantities — the line's remaining need, the lot's `quantity_remaining_kg`, and the per-line cap — recording each positive allocation as an entry carrying the source `lot_id`, the line's `spice_code`, and the `allocated_kg`, and stopping as soon as the remaining need reaches zero. If the walk ends with need still outstanding, the commit aborts with `ERR_INSUFFICIENT_LOT_QUANTITY` (HTTP 409) and persists nothing.

Once every line is fully allocated, the commit computes the blend's sensory and moisture outcome. The blended flavor is the allocation-weighted average of the lots' `flavor_intensity_units` — the sum over all allocations of `allocated_kg` times the sourcing lot's `flavor_intensity_units`, divided by the total allocated kilograms, in exact decimal arithmetic. The blended moisture is the same weighted average over the lots' `moisture_pct`. The persisted `residual_flavor_pct` is the difference between the blended flavor and the formula's `target_flavor_units`, divided by `target_flavor_units`, expressed as a percentage and rounded half-up to three decimal places; the persisted `blended_moisture_pct` is the weighted moisture rounded half-up to three decimal places. The run's `spec_status` is `WITHIN_SPEC` when the absolute value of `residual_flavor_pct` is less than or equal to the formula's `flavor_tolerance_pct` and `blended_moisture_pct` is less than or equal to the formula's `max_moisture_pct`; anything else is `OUT_OF_SPEC`, and an out-of-spec commit is rejected with `ERR_BLEND_OUT_OF_SPEC` (HTTP 422) — the computed fields persist, the status stays `DRAFT`, and no lot quantities change. The referenced formula must also still be `ACTIVE` at commit time, else `ERR_FORMULA_NOT_ACTIVE`.

Costing runs only after every line allocates, and its rounding order is pinned and non-negotiable. For each recorded allocation, in recording order, the allocation's `line_cost_cents` is `allocated_kg` multiplied by the lot's `cost_per_kg_cents`, rounded half-up to a whole cent — the rounding happens per allocation first. The subtotal is then the sum of those per-allocation cents. The production overhead is the subtotal multiplied by 3.5 percent, rounded half-up to a whole cent. The `cost_total_cents` is the subtotal plus the overhead. Rounding per allocation, then summing, then applying overhead is the only correct order; summing raw per-allocation products and rounding once at the end yields different cents and is wrong.

A successful commit — selection complete and `WITHIN_SPEC` — is atomic: for every allocation, the source lot's `quantity_remaining_kg` decreases by `allocated_kg` and its `quantity_consumed_kg` increases by the same amount; any lot whose `quantity_remaining_kg` reaches exactly 0 transitions from `ACCEPTED` to `DEPLETED`; the run's `selected_allocations` (ordered by formula-line creation order, then by policy order within each line), `residual_flavor_pct`, `blended_moisture_pct`, `cost_total_cents`, and `spec_status` are persisted; and the run's status becomes `COMMITTED`. Every commit attempt — success or persisted failure — increments the run's `version` by exactly 1. A failed commit leaves the run in `DRAFT` and touches no lot quantities: candidate-pool and insufficient-quantity failures abort before any computed field exists and persist nothing — not even a `version` increment, so the run's `version` moves only on a successful commit or on a persisted out-of-spec failure — while an out-of-spec failure persists the computed fields it reached. The scientist may adjust inputs and retry a failed commit any number of times.

Voiding is the compensating action, and its effect depends on the run's state. Voiding a `DRAFT` run simply moves it to `VOIDED` — nothing was consumed, so no lot quantities change. Voiding a `COMMITTED` run is permitted only while no production run referencing it has reached `COMPLETED` — otherwise the void is rejected with `ERR_INVALID_STATE` (HTTP 409) — and it reverses the consumption exactly: for every allocation, the lot's `quantity_consumed_kg` decreases by `allocated_kg` and its `quantity_remaining_kg` increases by the same amount, and any `DEPLETED` lot whose remaining quantity rises above 0 returns to `ACCEPTED`. `VOIDED` is terminal.

### 3.5. Production Scheduling, Changeover Control, and Weekly Capacity

The plant side starts with master data: a `PlatformAdmin` creates each production line with a `name`, a `capacity_kg_per_shift` (an integer greater than 0), and the `supported_changeover_classes` the line's sanitation program can execute — a non-empty array drawn from `NONE`, `DRY_CLEAN`, `WET_WASH`, and `FULL_SANITATION` (ascending severity) that must contain `NONE`. A line's `version` is the pivot of scheduling concurrency, per §2.7.

A `ProductionScheduler` schedules runs against a line. The request names the `line_id`, the `formula_id` (which must be `ACTIVE`, else `ERR_FORMULA_NOT_ACTIVE`), the `blend_run_id` (which must be `COMMITTED`, else `ERR_BLEND_RUN_NOT_COMMITTED`, and must belong to the same formula — a `formula_id` differing from the blend run's formula is rejected with `ERR_FORMULA_MISMATCH`, HTTP 422), the planned `quantity_kg` (which must equal the referenced blend run's `target_batch_kg` exactly, else `ERR_QUANTITY_MISMATCH`, HTTP 422), the half-open production window from `window_start` to `window_end` (both UTC ISO 8601; `window_end` must be strictly after `window_start`), optionally the `private_label_agreement_id`, and the optimistic-concurrency field `expected_line_version`. Two agreement rules govern private-label work: when the formula's `brand_type` is `PRIVATE_LABEL`, omitting `private_label_agreement_id` is rejected with `ERR_AGREEMENT_REQUIRED` (HTTP 422); and when an agreement is supplied, the formula's `product_code` must appear in that agreement's `product_codes`, else `ERR_PRODUCT_NOT_IN_AGREEMENT` (HTTP 422). For a `BRANDED` formula the agreement field stays null. Windows on a line are exclusive under half-open semantics: the new window must not intersect any non-`CANCELLED` run on the same line, though perfect adjacency — a neighbor whose `window_end` equals the new `window_start`, or whose `window_start` equals the new `window_end` — is allowed; a true overlap is rejected with `ERR_LINE_WINDOW_CONFLICT` (HTTP 409).

Every scheduled run also picks up two server-computed attributes at creation. The `predecessor_run_id` is the changeover predecessor: among runs on the same line that are not `CANCELLED` and whose `window_end` is less than or equal to the new run's `window_start`, the one with the greatest `window_end`, ties broken by earliest `created_at`; when no such run exists it is null. From the predecessor, the server computes `changeover_class_required`. When there is no predecessor, the class is `NONE`. When either the predecessor or the new run is a high-segregation private-label run — meaning its formula's `brand_type` is `PRIVATE_LABEL` and its agreement's `confidentiality_level` is `HIGH_SEGREGATION` — the class is `FULL_SANITATION`. Otherwise, let each run's allergen set be the distinct `allergen_profile` values of its formula's lines excluding `NONE`: if the predecessor's allergen set is not a subset of the new run's allergen set, allergen carryover is possible and the class is `WET_WASH`. If the sets are compatible but the new run's formula is fully organic — every line of its formula has `organic_required` true, with an empty formula counting as not organic — while the predecessor's formula is not fully organic, the non-organic-to-organic transition also demands `WET_WASH`. If the allergen sets are exactly equal, both runs share a `brand_type`, and — for `PRIVATE_LABEL` runs — both reference the same `private_label_agreement_id`, the class is `NONE`. In every remaining case the class is `DRY_CLEAN`. The computed class must then be a member of the line's `supported_changeover_classes`; a line that cannot execute the required sanitation rejects the schedule with `ERR_ALLERGEN_CHANGEOVER_INSUFFICIENT` (HTTP 409).

Capacity is pooled per line per ISO week. A line's weekly pool is its `capacity_kg_per_shift` multiplied by 5 shifts per week, multiplied by the week's surge multiplier, and floored to a whole kilogram: the surge multiplier is 1.25 for ISO weeks 44 through 52 inclusive — the holiday demand spike — and 1.0 for every other week, with ISO weeks counted Monday-start under ISO-8601. Against that pool stand the week's scheduled consumption — the summed `quantity_kg` of the line's runs in `SCHEDULED` or `COMPLETED` status whose `window_start` falls in that week, with `CANCELLED` runs consuming nothing — and the week's reservations described in §3.8. A new run consumes pool from exactly one week: the ISO week containing its `window_start`. If scheduling would push the week's balance below zero — pool minus scheduled minus reserved going negative — the request is rejected with `ERR_CAPACITY_EXCEEDED` (HTTP 409). Successful scheduling stamps the run `SCHEDULED`, persists `predecessor_run_id` and `changeover_class_required`, and increments the line's `version` by 1. Production-run listings accept optional `line_id`, `formula_id`, `blend_run_id`, `private_label_agreement_id`, and `status` filters.

### 3.6. Run Completion, Finished Goods, and the Shipping Gate

Completing a `SCHEDULED` run turns blend into stock. The completion marks the run `COMPLETED` and creates its finished batch in the same request: `production_run_id` points back at the run; `product_code` and `brand_type` are copied from the run's formula; `quantity_kg` is copied from the run; `produced_at` is the logical clock's value at completion; `shelf_life_days` is always 540; `best_by_date` is `produced_at` plus 540 days; both `produced_at` and `best_by_date` are rendered as ISO 8601 UTC timestamps with three fractional digits, in the same format as `created_at` and `updated_at`; `genealogy_lot_ids` is the distinct list of raw-lot ids drawn from the blend run's `selected_allocations`, in allocation order; and `unit_cost_cents` equals the blend run's `cost_total_cents` — exact equality holds because the run's quantity must equal the blend target. A batch is born with `commercial_status` `CREATED` and `quality_status` `CLEAR`. The completion response carries the updated production run (HTTP 200), per §2.4's rule for actions that modify an existing resource; the created batch is retrievable through the batch listing filtered by `production_run_id`. When the completed run carried a `private_label_agreement_id`, the same completion adds the run's `quantity_kg` into the agreement's `produced_ytd_kg` and recomputes `commitment_met` as true exactly when `produced_ytd_kg` is greater than or equal to `annual_commitment_kg` — a year-to-date total landing exactly on the commitment counts as met. Only `COMPLETED` runs count toward an agreement; `SCHEDULED` and `CANCELLED` runs contribute nothing. Cancelling a `SCHEDULED` run instead marks it `CANCELLED` and releases its weekly-pool consumption, restoring the capacity invariant for that week. Both completion and cancellation attempted on a run in any other state are rejected with `ERR_INVALID_STATE`.

A finished batch lives on two parallel and independent status dimensions. The commercial dimension runs from `CREATED` to `SHIPPED`; the quality dimension runs from `CLEAR` through `QUALITY_HOLD` to the terminal `RECALLED` or `WITHDRAWN`. Shipping — performed by a `SupplyPlanner` — is gated three ways: the batch's `commercial_status` must be `CREATED` (else `ERR_INVALID_STATE`); its `quality_status` must be `CLEAR` and no `INITIATED` recall case may list the batch among its `affected_batch_ids` (else `ERR_BATCH_NOT_SHIPPABLE`, HTTP 409); and at least 75.0 percent of shelf life must remain at ship time, else `ERR_SHELF_LIFE_INSUFFICIENT` (HTTP 409). The shelf-life computation floors the exact duration from the logical clock to `best_by_date` to whole days, divides by the 540-day shelf life, and expresses the result as a percentage; a batch with exactly 405 days remaining sits exactly at 75.0 percent and passes — at-threshold passes. A successful ship moves `commercial_status` to `SHIPPED`, which is terminal for the commercial dimension. Independently of shipping, a `QualityManager` may place a `CLEAR` batch on manual hold, optionally attaching a `note` — accepted with the request but not persisted on the batch representation: the batch's `quality_status` becomes `QUALITY_HOLD` with `quality_hold_cause` set to `MANUAL` and `quality_hold_lot_id` set to null. Batch listings accept optional `production_run_id`, `product_code`, `commercial_status`, and `quality_status` filters.

### 3.7. Recall Operations and the Adulterant Cascade

Recall readiness is engineered into the data model rather than bolted on. The trigger sits in the laboratory: the moment an `ADULTERANT_SCREEN` test computes `FAIL` on a lot in `IN_TEST` or `ACCEPTED`, the lot auto-quarantines (§3.2) and, within the same request, the cascade fires. Every finished batch whose `genealogy_lot_ids` contains that lot and whose `quality_status` is `CLEAR` moves to `QUALITY_HOLD`, with `quality_hold_cause` set to `LOT_QUARANTINE` and `quality_hold_lot_id` set to the quarantined lot's id. If at least one batch was held and no recall case in `DRAFT` or `INITIATED` already names that lot as its `suspect_lot_id`, the system auto-creates a recall case with `trigger_type` `LOT_SUSPECT`, the quarantined lot as its suspect, `scope_policy` `PROVISIONAL`, `source` `AUTO_QUARANTINE`, and status `DRAFT` — a standing draft awaiting a coordinator's decision.

Manual cases come from a `RecallCoordinator`, who opens a case with a `trigger_type` of `LOT_SUSPECT`, `BATCH_SUSPECT`, or `REGULATORY`, a `scope_policy` of `PROVISIONAL` or `FINAL`, and exactly one suspect reference — `suspect_lot_id` or `suspect_batch_id`; supplying both or neither, for any trigger type, is rejected with `ERR_RECALL_SCOPE_INVALID` (HTTP 422). A manually opened case starts in `DRAFT` with `source` `MANUAL`, `affected_batch_ids` an empty array, and `affected_quantity_kg` 0. Recall listings accept optional `status`, `suspect_lot_id`, and `suspect_batch_id` filters.

Scope is computed once, at initiation, and then frozen on the case. The base suspect set is the suspect lot alone when `suspect_lot_id` was given, or the suspect batch's `genealogy_lot_ids` when `suspect_batch_id` was given. Under the `FINAL` policy — the confirmed legal scope — the affected batches are exactly those whose `genealogy_lot_ids` intersect that base set. Under the `PROVISIONAL` policy — forward-looking cohort suspicion used while an investigation is open — the base set is first widened by a cohort: for each suspect lot, every raw lot in any status except `REJECTED` that shares the suspect's `supplier_id`, `spice_code`, and `crop_year` joins the suspect set, and the affected batches are those whose genealogy intersects the widened set. `PROVISIONAL` is therefore always a superset of `FINAL`, and the two diverge whenever a cohort lot reached a different batch. The frozen `affected_batch_ids` are sorted by batch `created_at` ascending, and `affected_quantity_kg` is their summed `quantity_kg` in exact decimal arithmetic. Initiation considers every finished batch regardless of either status dimension, an empty scope is legitimate — a case may initiate with an empty `affected_batch_ids` — and initiating a case not in `DRAFT` is rejected with `ERR_INVALID_STATE`. Upon initiation every affected batch whose `quality_status` is `CLEAR` moves to `QUALITY_HOLD`; a recall-driven hold does not set a cause, so `quality_hold_cause` remains `NONE` and `quality_hold_lot_id` remains null for those batches.

Closing an `INITIATED` case finalizes the commercial fate of everything in scope: each affected batch sitting in `QUALITY_HOLD` moves to `RECALLED` when its `brand_type` is `BRANDED`, or to `WITHDRAWN` when it is `PRIVATE_LABEL` — the retailer shelf pull. Closing changes only the quality status: the batches' `quality_hold_cause` and `quality_hold_lot_id` are left unchanged. Batches not on hold are untouched, and `RECALLED` and `WITHDRAWN` are terminal. One more path closes a case without any coordinator action: when the suspect lot of an auto-created `AUTO_QUARANTINE` case still in `DRAFT` is released via a successful accept disposition, the case auto-closes — its status becomes `CLOSED`, its `affected_batch_ids` empties, and its `affected_quantity_kg` returns to 0.

That release is the cascade's unwinding path, and it fires on any successful accept disposition of the lot (passing every gate of §3.2), whether the lot sits in `QUARANTINED` at that moment or has already been returned to `IN_TEST` by an exonerating retest — indeed, after an adulterant `FAIL` the retest path is the only reachable one, since the zero-FAIL accept gate rejects a direct accept while the latest `ADULTERANT_SCREEN` is still `FAIL`, and posting the retest moves the lot back to `IN_TEST` (§3.2). The unwind is therefore keyed to the cascade's artifacts rather than to the lot's status at acceptance: every finished batch still held specifically because of that lot — sitting in `QUALITY_HOLD` with `quality_hold_cause` `LOT_QUARANTINE` and `quality_hold_lot_id` equal to the released lot — and not covered by any `INITIATED` recall case returns to `CLEAR`, with `quality_hold_cause` reset to `NONE` and `quality_hold_lot_id` to null; a batch that a closed recall has already moved to `RECALLED` or `WITHDRAWN` is not held and stays put, those states being terminal. And every `DRAFT` recall case with `source` `AUTO_QUARANTINE` naming the released lot auto-closes as just described. An accept of a lot carrying no outstanding cascade artifacts — one that was never auto-quarantined, including a lot quarantined only by the manual `QUARANTINE` action — unwinds nothing, and a reject disposition never unwinds: cascade-created batch holds and recall cases survive the lot's rejection untouched. A batch simultaneously covered by an `INITIATED` recall does not clear on lot release — the recall, not the quarantine, then owns its fate.

### 3.8. Private-Label Agreements and Seasonal Capacity Reservations

Private-label and foodservice-industrial business runs on contracts. A `ProductionScheduler` creates an agreement with the customer's `retailer_name`, the `product_codes` the agreement covers (a non-empty array of strings — the custom-development scope under NDA), an optional `confidentiality_level` of `STANDARD` or `HIGH_SEGREGATION` (default `STANDARD`), the `annual_commitment_kg` (greater than 0), and an optional `development_nda_signed` flag (default false) recording execution of the custom-development NDA. Choosing `HIGH_SEGREGATION` has a concrete plant-floor consequence: any production run adjacent to a run for that agreement — immediately before it or after it — requires a `FULL_SANITATION` changeover, per the changeover rules of §3.5. An agreement is born with `produced_ytd_kg` 0 and `commitment_met` false; both advance only through run completions, per §3.6, with `commitment_met` becoming true exactly when the year-to-date total reaches `annual_commitment_kg`.

Reservations dedicate weekly line capacity to a program ahead of the scheduling horizon — the seasonal surge-planning instrument. Creating one names the `line_id`, an optional `agreement_id` (when null, the reservation holds capacity for the branded program rather than a private-label customer), a half-open window from `window_start` to `window_end`, and the `reserved_kg_per_week` (an integer greater than 0). A reservation consumes `reserved_kg_per_week` from every ISO week its window intersects — not from a single week — where intersection is measured against each week's Monday-to-Monday half-open span. If honoring the reservation would push any intersected week's pool below zero, the create is rejected with `ERR_RESERVATION_OVER_COMMIT` (HTTP 409); the reservation is all-or-nothing across its window. Reservation listings accept optional `line_id` and `agreement_id` filters.
