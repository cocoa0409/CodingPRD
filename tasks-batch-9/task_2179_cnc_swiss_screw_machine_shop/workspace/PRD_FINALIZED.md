# CNC Swiss Screw Machine Shop API — Product Requirements Document

## 1. Introduction

A Swiss screw machine shop sells spindle time and material conversion, not parts in isolation. A single sliding-headstock lathe can run a 40,000-piece order across three weeks, unattended overnight, from a bar of 316 stainless that was certified by a mill six months earlier — and the difference between a profitable run and a scrap loss is measured in microns of tool offset drift and tenths of a second of cycle time. The shop's back office today lives in three disconnected places: a quoting spreadsheet that guesses cycle times, a whiteboard that tracks which machine is down and why, and a stack of inspection sheets that nobody reconciles against the blanket purchase orders they are supposed to satisfy. This document specifies the API that replaces all three.

The system models the shop as a single, conserved economy. A customer's blanket purchase order commits a finite quantity of pieces; kanban releases draw that quantity down onto the floor; work orders hold it open while the spindle turns; short-closes and rejections return it. Bar stock behaves the same way in millimetres rather than pieces — length moves from available, to reserved, to consumed, and never appears or disappears. Layered over both ledgers is a compliance surface the shop's aerospace and medical customers demand: statistical process control sampling by print characteristic, gauge calibration and gauge repeatability-and-reproducibility linkage, and a hard segregation of duties between the operator who ran the job and the inspector who measured it. Nothing reaches the customer's account until that compliance surface says it may.

Two design consequences follow, and both shape the specification below. First, a work order carries **two independent state dimensions** — a production dimension and a quality dimension — that advance on their own schedules and are never collapsed into one status field. A job can be finished on the machine while its capability study is still open, and it can sit on a quality hold while the spindle has long since moved on. Second, because tool holds, machine outages, fulfilment credits and quote consumption all cascade across several entities from a single request, every write that could be authored against a stale view of a shared resource carries an explicit version expectation. Implementers should read §2 as the binding contract and §3 as the business narrative that determines the behaviour behind each endpoint in §4.

## 2. Global Specifications & System-Wide Principles

All business resources are mounted under the `/swiss-shop` prefix. One administrative capability, the logical clock, sits outside that prefix and is described in §2.4.

### 2.1. Shop Personnel, Headers and Role Authority

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the authority the caller is acting under. Four roles exist and their spellings are exact: `ShopPlanner`, `Machinist`, `Inspector`, and `QualityManager`. If either header is absent, or if `X-User-Role` is not one of those four strings, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not among the roles listed for the requested endpoint in §4, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). Authentication is checked before authorization, and both are checked before anything else about the request is examined.

A `ShopPlanner` owns the commercial and scheduling surface — registering masters, opening and pricing quotes, accepting them into blanket orders, cutting kanban releases, scheduling and cancelling work orders, defining secondary routing, and settling reclamation. When `X-User-Role` is `ShopPlanner`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may accept and log it but never compares it to any resource's `id`. The same holds for `QualityManager`, who owns the compliance surface — gauge registration, calibration and gauge R&R posting, bar lot certification, and the final quality disposition of a work order: `X-User-ID` for a `QualityManager` is likewise opaque and is never resolved against a stored row.

`Machinist` and `Inspector` are different. When `X-User-Role` is `Machinist`, `X-User-ID` is the `id` of the acting `Operator` record; the same is true when `X-User-Role` is `Inspector`. For both of these roles, the header must name an `Operator` that exists and whose `status` is `ACTIVE`; if it names no operator, or names one whose `status` is `INACTIVE`, the request is rejected with `ERR_OPERATOR_NOT_FOUND` (HTTP 404). Ownership and duty checks on any resource that references an operator compare the resource's operator field to `X-User-ID` directly: a `Machinist` starting a job becomes that job's `machinist_operator_id`, and an `Inspector` posting a measured subgroup becomes that subgroup's `inspector_operator_id`. The operator-existence check applies to starting machining, completing machining, posting a tool offset log, indexing a tool station, restoring a machine, posting an SPC subgroup, and advancing a routing step.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two optional query parameters. `limit` defaults to 10, has a minimum of 1 and a maximum of 100. `offset` defaults to 0 and has a minimum of 0. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Results are returned in ascending `created_at` order unless a subsection below states otherwise. List responses set `response_type` to `"array"` and populate four pagination fields inside `meta`: `limit` and `offset` echo the effective values used, `total_count` reports the number of rows matching the filter before the window was applied, and `has_more` is true when rows remain beyond the current window. Single-resource reads set `response_type` to `"object"` and omit the four pagination fields.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every stored resource is addressed by an `id`, which is a server-minted UUID carrying no type prefix and no client-supplied component. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written.

Most resources additionally carry `updated_at`, in the same ISO 8601 UTC format with three fractional digits, and `version`, an integer that begins at 1 on creation and increases by exactly one on every mutation of that row. `Operator`, `Machine`, `Part`, `Characteristic`, `Gauge`, `BarStockLot`, `Quote`, `BlanketPO`, `KanbanRelease`, `WorkOrder`, `ToolAssignment` and `RoutingStep` all carry the full quartet of `id`, `created_at`, `updated_at` and `version`. The single exception is `SpcSample`: a measured subgroup is an immutable observation, so it carries only `id` and `created_at` — it has no `updated_at` field and no `version` field at all, and neither key appears in its representation.

Time in this system is not wall-clock time. The server maintains a **logical clock** that every temporal comparison in this document reads from. Before the first time it is set, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time. An administrative capability, available to `ShopPlanner` and `QualityManager` alike, moves the clock: the request supplies the target instant as `to_iso8601` and the response reports the new setting as `current_utc`. Advancing the clock does not itself rewrite any stored row; it changes the answer that later lazy re-evaluations give, most visibly for gauge calibration windows, blanket-order expiry and quote validity.

### 2.5. Version Expectations on Shared-Resource Writes

Two write operations in this system draw on a resource that other writers are constantly moving, and both therefore require the client to declare the version it last observed.

Cutting a kanban release — a `POST /swiss-shop/kanban-releases` request — must carry `expected_blanket_po_version` as a non-optional field of the request body, holding the `version` the client last read from the `BlanketPO` named by `blanket_po_id`. If that value does not equal the blanket order's current `version`, the create is rejected with `ERR_STALE_PO_VERSION` (HTTP 412). The order's `remaining_qty`, `open_released_qty` and `status` are moved by earlier releases, by fulfilment credits, by rejections and by suspend and reinstate, so a release authored against an out-of-date view of the order would draw down a pool the client never actually saw.

Scheduling a work order — a `POST /swiss-shop/work-orders` request — must carry `expected_machine_version` as a non-optional field of the request body, holding the `version` the client last read from the `Machine` named by `machine_id`. If that value does not equal the machine's current `version`, the create is rejected with `ERR_STALE_MACHINE_VERSION` (HTTP 412), and it is rejected before any window arithmetic is attempted. Every accepted schedule, every start, every machining completion and every tool-hold cascade advances a machine's `version`, so a window authored against an out-of-date calendar is refused rather than evaluated.

No other endpoint accepts a version-expectation field. Requests to any endpoint outside those two must not be expected to supply one, and none is validated there.

### 2.6. Cents, Millimetres, Microns and Rounding Discipline

All money in this system is carried as whole cents in integer fields; no monetary value is ever stored or returned as a decimal currency amount. Wherever a monetary value is derived from a fractional intermediate, the conversion is **round half up** to zero decimal places — a value of exactly one half cent rounds away from zero to the next whole cent.

Where rounding happens matters as much as how it happens, and two calculations in §3 pin their rounding order explicitly: quote costing rounds each of its four cost components to a whole cent separately and then sums the four rounded integers, and reclamation settlement rounds each per-alloy scrap line to a whole cent separately and then sums the rounded lines. Summing unrounded intermediates and rounding once at the end is not the declared order in either case and will diverge by whole cents.

Non-monetary precision is stated per quantity. Chip mass in kilograms and coolant make-up in litres are held to 3 decimal places, round half up. Cumulative tool offset drift in microns is held to 3 decimal places, while the piece counter beside it is a whole count. A subgroup's mean and range are held to 4 decimal places, its within-subgroup sigma to 6 decimal places, and both capability indices to 3 decimal places — all round half up. Observed average cycle time is held to 1 decimal place, round half up. Bar length in millimetres is exact and is never rounded; only the count of whole bars drawn from a lot is rounded, and that is always a ceiling.

### 2.7. Two Conserved Ledgers

The shop runs on two invariants that must hold before and after every operation that touches them.

The **bar length ledger** governs each `BarStockLot`. The lot's `total_length_mm` is fixed at receipt and is immutable thereafter. At every instant, `available_length_mm` plus `reserved_length_mm` plus `consumed_length_mm` equals `total_length_mm` exactly. Length only ever moves between the three buckets; it is never created, destroyed or rounded on the move. Scheduling a work order moves length from available to reserved; completing machining moves the same length from reserved to consumed and leaves available untouched; cancelling moves it from reserved back to available and leaves consumed untouched.

The **committed quantity ledger** governs each `BlanketPO`. The order's `total_committed_qty` is fixed when the order is cut and is immutable thereafter. At every instant, `remaining_qty` plus `open_released_qty` plus `fulfilled_qty` equals `total_committed_qty` exactly. Pieces move between the three buckets in whole units with no rounding anywhere. In ledger terms, releases in `RELEASED` or `IN_PRODUCTION` status are exactly what `open_released_qty` counts; a `FULFILLED` release contributes its work order's good-piece count to `fulfilled_qty`; a `SHORT_CLOSED` release contributes nothing to either, having returned everything it held.

### 2.8. The Two Work-Order Dimensions and Cascade Semantics

A `WorkOrder` carries `machining_status` and `quality_status` as two independent enumerations on the same row. `machining_status` is the production dimension and takes one of `SCHEDULED`, `RUNNING`, `INTERRUPTED`, `MACHINING_COMPLETE` or `CANCELLED`, beginning at `SCHEDULED` and terminating at `MACHINING_COMPLETE` or `CANCELLED`. `quality_status` is the quality dimension and takes one of `PENDING_INSPECTION`, `IN_SPC`, `QUALITY_HOLD`, `ACCEPTED` or `REJECTED`, beginning at `PENDING_INSPECTION` and terminating at `ACCEPTED` or `REJECTED`. Neither dimension consults the other when it advances, with exactly one exception: the quality dimension may not reach `ACCEPTED` or `REJECTED` until the production dimension is already at `MACHINING_COMPLETE`. Completing machining leaves `quality_status` exactly as it was, and a quality transition leaves `machining_status` exactly as it was.

Several operations in §3 fire multi-hop cascades that mutate more than one entity in a single request. Every entity touched by a cascade has its `updated_at` refreshed, and every entity carrying `version` has that integer incremented by one for each mutation the cascade applies to it. Where the narrative names an explicit `version` increment on a sibling entity — a machine going down, a blanket order absorbing a fulfilment credit — that increment is part of the contract and is what a later stale-version check will compare against. The response body of any of these operations is the primary resource named in the URL path, not the cascade's collateral; clients observe the collateral by re-reading it.

### 2.9. Path Resolution and the Validation Ladder

Checks run in a fixed order, and the first failure is the one reported. Higher-priority checks mask lower ones entirely, which is why a request that violates several rules at once returns exactly one error.

The ladder is: header presence and role legality first, yielding `ERR_UNAUTHENTICATED`; then endpoint role authorization, yielding `ERR_FORBIDDEN_ROLE`; then request-body well-formedness, yielding `ERR_INVALID_REQUEST` — this covers missing required fields, wrong types, enum members outside their declared sets, numeric fields outside their declared bounds, a `scheduled_end_at` that is not strictly after `scheduled_start_at`, and out-of-range pagination. Next, every resource named in the URL path must exist, validated strictly left to right, so on a nested path the leftmost missing segment determines the reported code. Each resource family carries its own not-found code, all of them HTTP 404: `ERR_OPERATOR_NOT_FOUND` for an operator, `ERR_MACHINE_NOT_FOUND` for a machine, `ERR_PART_NOT_FOUND` for a part, `ERR_CHARACTERISTIC_NOT_FOUND` for a print characteristic, `ERR_GAUGE_NOT_FOUND` for a gauge, `ERR_BAR_LOT_NOT_FOUND` for a bar stock lot, `ERR_QUOTE_NOT_FOUND` for a quote, `ERR_BLANKET_PO_NOT_FOUND` for a blanket order, `ERR_RELEASE_NOT_FOUND` for a kanban release, `ERR_WORK_ORDER_NOT_FOUND` for a work order, `ERR_TOOL_ASSIGNMENT_NOT_FOUND` for a tool station, `ERR_SPC_SAMPLE_NOT_FOUND` for a measured subgroup, and `ERR_ROUTING_STEP_NOT_FOUND` for a routing step. The same codes are used when the identifier appears in the request body rather than the path — a `machine_id`, `part_id`, `characteristic_id`, `gauge_id`, `bar_lot_id`, `blanket_po_id`, `release_id`, `work_order_id` or `predecessor_step_id` naming nothing raises its family's code. Next, every foreign key named in the request body must exist, validated in the order the fields are declared on the owning entity — this applies to creating a characteristic, a quote, a kanban release, a tool assignment, a work order, an SPC subgroup and a routing step. Next, for `Machinist` and `Inspector` calls, `X-User-ID` must name an `ACTIVE` operator, yielding `ERR_OPERATOR_NOT_FOUND`.

Only then do the version expectations of §2.5 run, yielding `ERR_STALE_PO_VERSION` or `ERR_STALE_MACHINE_VERSION`. After those comes the generic state check: the target resource must be in a state from which the requested transition is declared, otherwise `ERR_INVALID_STATE` (HTTP 409). Everything below that point is domain-specific and is described in §3 beside the workflow it guards; the relative order among those domain checks is stated explicitly wherever more than one can fire on the same endpoint.

### 2.10. Segregation of Duties and Measurement Integrity

The shop's quality system rests on a single non-negotiable separation: the person who ran a job may not be the person who measures it. Concretely, the `Inspector` whose `X-User-ID` accompanies a subgroup post must differ from the `machinist_operator_id` recorded on the work order being measured; when they are the same operator, the post is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). A second separation is structural rather than per-request: only a `QualityManager` may certify bar stock, calibrate gauges or issue a final disposition, and a `QualityManager` never runs a spindle or posts a measurement.

Measurement integrity has a second leg — the instrument. A gauge may only be used when it is in service, which means both that its calibration window has not lapsed against the logical clock and that its most recent gauge R&R study came in at or below the acceptable percentage of tolerance. §3 describes how a gauge moves between `IN_SERVICE`, `CALIBRATION_DUE`, `GRR_FAILED` and `RETIRED`, and what happens to a subgroup posted against one that is not in service.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Shop: Operators, Machines, Parts and Print Characteristics

Before any commercial work can be scheduled, a `ShopPlanner` populates the shop's master file. Registering a shop-floor operator captures a `name` and a `badge_code`, the latter unique across every operator on file. Two further attributes are optional at registration: `certifications`, an array of certification codes drawn from `SWISS_SETUP`, `LIGHTS_OUT`, `CMM` and `DEBURR`, which defaults to an empty array when omitted; and `status`, which is either `ACTIVE` or `INACTIVE` and defaults to `ACTIVE`. The `LIGHTS_OUT` certification is the one with teeth — §3.6 explains where it gates a start.

Machines are registered with an `asset_tag`, unique across the shop floor, and a `max_bar_diameter_mm` that records the largest bar the guide bushing will accept, which must be greater than zero. A `model` designation may be supplied and defaults to `SWISS-20`; `lights_out_certified` may be supplied and defaults to false. Everything else on a machine is derived by the system rather than typed in. A newly registered machine has `status` `AVAILABLE` — the three legal values are `AVAILABLE`, `RUNNING` and `DOWN` — with `current_work_order_id` null, an empty `chip_accrual_by_alloy` map, `coolant_makeup_liters` at 0, `last_reclamation_credit_cents` null because nothing has ever been settled, and `lifetime_reclamation_credit_cents` at 0. `current_work_order_id` mirrors whichever work order is currently running on the machine and is null whenever none is; it is a live mirror, not a declared foreign key.

A part master carries what both the quoting engine and the floor need. `part_number` identifies it uniquely to the customer. `alloy_code` names the bar stock alloy and must be one of `303SS`, `316SS`, `C360`, `6061AL` or `12L14`. `bar_diameter_mm` and `cut_off_length_mm` describe the geometry — the diameter the part requires and the finished length consumed per piece before the parting kerf — and both must be greater than zero, as must `cycle_time_sec`, the engineered standard spindle seconds per piece. `setup_hours` records the standard setup charged once per quoted lot and may be zero or more. `material_cost_cents_per_meter` is the purchased bar cost in whole cents per metre at this diameter and alloy and may be zero or more. `finished_mass_g` is the mass of one finished piece in grams and must be greater than zero; it exists to close the chip mass balance described in §3.9. Three optional flags round out the record: `lights_out_eligible` and `secondary_required` both default to false, and `secondary_minutes_per_piece` defaults to 0 and may be zero or more. Two computed fields are seeded at creation and never typed in — `observed_avg_cycle_time_sec` starts null and `observed_accepted_qty` starts 0; §3.8 explains what fills them.

Every dimension the customer wants inspected becomes a **characteristic** hung off the part, created with a payload naming the `part_id` it belongs to. Each carries a `char_code`, the print balloon reference, unique within its part; a `nominal` print dimension in millimetres; and the two specification limits `usl` and `lsl`, where `usl` must be strictly greater than `lsl` and `lsl` strictly less than `usl`. `sample_freq_pieces` states how many ordered pieces one subgroup must cover and must be at least 1. `required_gauge_type` names the instrument family that must be used and is one of `MICROMETER`, `BORE_GAUGE`, `OPTICAL_COMPARATOR` or `CMM`. Two values may be omitted: `cpk_min`, the minimum short-term capability index a subgroup must reach to be dispositioned as acceptable, defaults to 1.33 and must be greater than zero; and `subgroup_size`, the number of measurements every subgroup for this characteristic must contain, defaults to 5 and must be either 3 or 5. Adding a characteristic to a part raises the required subgroup count for every future work order on that part. Characteristics may be listed across the shop or narrowed to a single part by supplying `part_id` as a filter.

Tooling is registered per station. A tool assignment names the `machine_id` it belongs to and a `station` number, at least 1 and unique within that machine, together with the `tool_code` currently loaded and `expected_life_pieces`, the pieces the tool is rated for between indexes, which must be at least 1. `drift_limit_um` — the absolute cumulative offset drift in microns at or beyond which the station must be held — may be supplied and defaults to 8 microns; it must be greater than zero. A newly loaded station opens `IN_SERVICE`, one of `IN_SERVICE`, `OFFSET_HOLD`, `LIFE_EXPIRED` and `RETIRED`, with `pieces_since_index`, `cumulative_drift_um` and `offset_log_count` all at 0. Loading a tool does **not** touch the machine's `version`. Stations may be listed for the whole shop or filtered to one machine by supplying `machine_id`.

Uniqueness is enforced on creation across the master file and rejected with `ERR_DUPLICATE_KEY` (HTTP 409): a repeated `part_number` on a part, `asset_tag` on a machine, `gauge_code` on a gauge, `heat_number` on a bar lot, `badge_code` on an operator, `char_code` within the same part, `station` within the same machine, or `sequence` within the same work order.

### 3.2. Bar Stock: Receipt, Certification and the Length Ledger

Bar stock arrives by heat. Receiving a lot records the mill `heat_number`, unique across all lots; the `alloy_code`, again one of `303SS`, `316SS`, `C360`, `6061AL` or `12L14`; the `bar_diameter_mm` and `bar_length_mm` of every bar in the lot, both greater than zero; `bars_received`, at least one; and `mass_kg_per_meter`, the mass of one metre of bar at this diameter and alloy in kilograms, greater than zero. An optional `feeder_slots` value declares how many work orders may have intersecting staging intervals on this lot's bar feeder; it defaults to 1 and must be at least 1.

Receipt seeds the ledger. `total_length_mm` is the number of bars received multiplied by the length of a single bar, and it is immutable for the life of the lot — it is the conserved total of §2.7. `available_length_mm` is set to the same figure, while `reserved_length_mm` and `consumed_length_mm` both start at 0. The lot opens in `status` `RECEIVED`; the four legal values are `RECEIVED`, `CERTIFIED`, `QUARANTINED` and `DEPLETED`. `certificate_number` starts null.

Certification is a `QualityManager` act and is the gate that makes material eligible to back production. Recording a `certificate_number` against a lot in `RECEIVED` moves it `RECEIVED → CERTIFIED` and stores the number. One sentinel value inverts the outcome: when the supplied `certificate_number` is exactly the literal string `QUARANTINE`, the lot moves `RECEIVED → QUARANTINED` instead, and a quarantined lot can never back a work order start for the rest of its life. Certification is only declared from `RECEIVED`; attempting it against a lot already `CERTIFIED`, `QUARANTINED` or `DEPLETED` is rejected with `ERR_INVALID_STATE`.

The lot's fourth state arrives on its own. When a machining completion drives both `available_length_mm` and `reserved_length_mm` to exactly 0, the system moves the lot `CERTIFIED → DEPLETED` and no further work order may reserve against it. Depletion is a consequence, never a request.

### 3.3. Quoting a Long Run

A quote opens in `DRAFT` with a payload naming the `part_id` being quoted, the `customer_code` it is addressed to, and the `lot_qty` in pieces, which must be at least 1. The customer may also ask for unattended running to be priced in, supplied as `requested_lights_out_hours`; this defaults to 0 and may be zero or more. A quote's `status` is one of `DRAFT`, `PRICED`, `ACCEPTED`, `CONSUMED` and `EXPIRED`. While a quote is `DRAFT` and unpriced, `costing_basis` is null and every computed pricing field — `cycle_time_used_sec`, `effective_qty`, `run_cost_cents`, `setup_cost_cents`, `secondary_cost_cents`, `material_cost_cents`, `quoted_lot_cost_cents` and `quoted_unit_price_cents` — is null. Quotes may be listed across the shop or narrowed to a single part by supplying `part_id` as a filter.

Pricing is a `ShopPlanner` act and moves the quote `DRAFT → PRICED`. It may also be re-run on an already-`PRICED` quote, in which case the quote stays `PRICED` and every pricing field is overwritten; the previous figures are not retained anywhere. The request carries exactly one field, `costing_basis`, which selects between the two costing variants and must be either `STANDARD_CYCLE` or `HISTORICAL_CYCLE`.

The pricing run proceeds in a fixed order. **First**, the quoted quantity is inflated by a two-percent scrap allowance and rounded up to a whole number of pieces: `effective_qty` is the lot quantity multiplied by one plus two hundredths, with any fractional piece rounded up. **Second**, the seconds per piece to be charged is selected by the costing basis and stored as `cycle_time_used_sec`. On the `STANDARD_CYCLE` basis it is the part's engineered `cycle_time_sec`. On the `HISTORICAL_CYCLE` basis it is the part's `observed_avg_cycle_time_sec` when that value is not null, and falls back to the engineered `cycle_time_sec` when it is null — a documented fallback, not an error. Because observed cycle time reflects real running that was interrupted and degraded by unattended hours, it is normally the longer of the two, so the same quote and part priced on the two bases produce different unit prices.

**Third**, total spindle hours are the effective quantity multiplied by the selected seconds per piece, divided by 3,600 seconds in an hour. This quotient is kept exact; it is not rounded at this step or any later one. **Fourth**, those hours are split between attended and unattended running. When the part is not `lights_out_eligible`, the unattended hours are zero regardless of what the customer asked for. Otherwise the unattended hours are the lesser of the `requested_lights_out_hours` and sixty hundredths of the total spindle hours — the shop will not price more than three fifths of any run as lights-out. The attended hours are the total spindle hours minus the unattended hours.

**Fifth**, four cost components are computed, and the rounding order here is pinned: each component is rounded half up to a whole cent on its own, and the four rounded integers are then summed. `run_cost_cents` is the attended hours multiplied by 9,500 cents per attended spindle hour, rounded half up to a whole cent, plus the unattended hours multiplied by 6,200 cents per lights-out spindle hour, rounded half up to a whole cent — the two hour buckets are rated and rounded separately and then added. `setup_cost_cents` is the part's `setup_hours` multiplied by 11,000 cents per setup hour, rounded half up. `secondary_cost_cents` is zero when the part does not have `secondary_required` set; when it does, it is the quoted lot quantity multiplied by the part's `secondary_minutes_per_piece`, divided by 60 minutes in an hour, multiplied by 7,400 cents per secondary hour, rounded half up. Note that secondary work is priced on the ordered lot quantity, not on the scrap-inflated effective quantity. `material_cost_cents` starts from the bar length the lot needs, which is the effective quantity multiplied by the sum of the part's `cut_off_length_mm` and a 2.0-millimetre part-off kerf, plus a flat 300 millimetres of setup scrap; that length in millimetres is divided by 1,000 to give metres, multiplied by the part's `material_cost_cents_per_meter`, multiplied by one plus eighteen hundredths for the material markup, and rounded half up.

`quoted_lot_cost_cents` is the sum of those four rounded integers. **Sixth and last**, `quoted_unit_price_cents` is the lot cost divided by the quoted `lot_qty` and then divided by one minus twenty-two hundredths — the shop's margin load — with a single half-up rounding to a whole cent applied at the end.

A priced quote is accepted by a `ShopPlanner`, which moves it `PRICED → ACCEPTED` and cuts the blanket purchase order described in §3.4. Acceptance is only declared from `PRICED`. Two temporal rules bound it. The `expires_on` instant supplied in the accept request must be strictly after the logical clock. And a quote is only good for 30 days from the moment it was raised: when acceptance is attempted while the logical clock stands at or after 30 days past the quote's `created_at`, the quote is moved to `EXPIRED` and the accept request itself is rejected with `ERR_INVALID_STATE`. A quote that has reached `EXPIRED` or `CONSUMED` cannot be accepted, priced or otherwise advanced.

### 3.4. The Blanket Order and the Kanban Signal

Accepting a quote cuts exactly one blanket purchase order, created in `status` `ACTIVE` — the four legal values being `ACTIVE`, `SUSPENDED`, `EXHAUSTED` and `EXPIRED`. The accept payload supplies the `customer_po_number`, the `total_committed_qty` the customer commits to over the life of the order, which must be at least 1 and is immutable thereafter, and the `expires_on` instant after which no further kanban release may be cut. The order records the `quote_id` it came from and copies the `part_id` from that quote; `suspension_reason` starts null.

Rebate selection happens once, at this moment, and its evaluation order is pinned. `list_unit_price_cents` is copied verbatim from the quote's `quoted_unit_price_cents`. `pre_rebate_total_cents` is that list unit price multiplied by the committed quantity, and it is from this **pre-rebate** extended total that the rebate tier is chosen. Below 500,000 cents the `rebate_pct` is zero. From 500,000 cents up to but not including 2,000,000 cents it is three hundredths. From 2,000,000 cents up to but not including 10,000,000 cents it is six hundredths. At 10,000,000 cents and above it is nine hundredths. Every tier boundary is inclusive on its lower edge and exclusive on its upper edge. The tier is never re-selected from the rebated figures, even when applying the rebate would drop the order into a lower tier. `net_unit_price_cents` is the list unit price multiplied by one minus the rebate fraction, rounded half up to a whole cent, and `committed_value_cents` is that net unit price multiplied by the committed quantity. Nothing outside the one accepted quote and the committed quantity in the accept body participates in this calculation.

The order's quantity ledger is seeded at the same moment: `remaining_qty` is set to the full `total_committed_qty`, while `open_released_qty` and `fulfilled_qty` both start at 0.

A `ShopPlanner` may suspend an `ACTIVE` order, supplying a `reason` that is stored as the order's `suspension_reason`; the order moves `ACTIVE → SUSPENDED` and its `version` is incremented by one. Suspension does not touch existing kanban releases in any way — work already on the floor runs to completion — it only blocks new ones. Reinstating moves the order `SUSPENDED → ACTIVE`, clears `suspension_reason` and increments `version` by one; reinstatement additionally requires that the logical clock is strictly before the order's `expires_on`. Orders may be listed and narrowed by supplying `quote_id` or `part_id` as filters.

Cutting a kanban release is how pieces reach the floor. The payload names the `blanket_po_id` being drawn against, the `qty` of pieces released, which must be at least 1, the customer dock date `due_at`, and the `expected_blanket_po_version` required by §2.5. Several gates guard the draw and they fire in this order: the named order must be in `ACTIVE` status, and a `SUSPENDED`, `EXHAUSTED` or `EXPIRED` order is rejected with `ERR_PO_NOT_ACTIVE` (HTTP 409); then the logical clock must be strictly before the order's `expires_on`, and when it stands at or after that instant the order is moved `ACTIVE → EXPIRED`, its `version` is incremented by one, and the release request that triggered the re-evaluation is rejected with `ERR_PO_EXPIRED` (HTTP 409); then the requested `qty` must not exceed the order's `remaining_qty`, and a larger request is rejected with `ERR_PO_QTY_EXCEEDED` (HTTP 409).

A release that clears those gates opens in `status` `RELEASED` — one of `RELEASED`, `IN_PRODUCTION`, `FULFILLED` and `SHORT_CLOSED` — with `fulfilled_qty` at 0 and `close_reason` null. The draw moves pieces on the ledger immediately: the released quantity is subtracted from the order's `remaining_qty` and added to its `open_released_qty`, and the order's `version` is incremented by one. Releases may be listed and narrowed by supplying `blanket_po_id` as a filter.

Short-closing is the compensating action, performed by a `ShopPlanner` with a `reason` that is recorded as the release's `close_reason`. It is declared from two states. From `RELEASED`, short-close is permitted only when no work order on the release has a `machining_status` of `RUNNING`, `INTERRUPTED` or `MACHINING_COMPLETE`. From `IN_PRODUCTION`, it is permitted only when every work order on the release has `machining_status` `CANCELLED`. In both cases the release moves to `SHORT_CLOSED`, its entire released quantity is subtracted from the order's `open_released_qty` and added back to its `remaining_qty` leaving `total_committed_qty` conserved, and the order's `version` is incremented by one. A short-closed release leaves `fulfilled_qty` at 0 and can never drive an order to exhaustion.

### 3.5. Scheduling a Work Order Onto the Floor

A work order is the unit of production. A `ShopPlanner` schedules one with a payload naming the `release_id` it satisfies, the `machine_id` it will run on, the `bar_lot_id` staged on that machine's feeder, the `qty_ordered` in pieces (at least 1), the occupancy window bounded by `scheduled_start_at` and `scheduled_end_at`, and the `expected_machine_version` required by §2.5. `lights_out_hours` — the portion of the window that will run unattended — is optional, defaults to 0 and may be zero or more. The `part_id` is not supplied; it is copied from the blanket order behind the named release. A new work order opens with `machining_status` `SCHEDULED` and `quality_status` `PENDING_INSPECTION`, with `machinist_operator_id` null, `actual_run_seconds` null, `qty_good` and `qty_scrap` at 0, `chip_kg` at 0 and `cancel_reason` null.

Scheduling is the most heavily guarded operation in the system, and the guards fire in a strict order so that exactly one code is reported. After the generic ladder of §2.9 has passed and the machine's version expectation has been satisfied, the checks run as follows.

The blanket order behind the release must be `ACTIVE`; otherwise `ERR_PO_NOT_ACTIVE`. Next comes material fit, in two steps. The lot's `bar_diameter_mm` must equal the part's `bar_diameter_mm` and must also be less than or equal to the machine's `max_bar_diameter_mm`; a failure of either half is `ERR_BAR_DIAMETER_MISMATCH` (HTTP 422). Then the lot's `alloy_code` must equal the part's `alloy_code`, failing which the request is rejected with `ERR_ALLOY_MISMATCH` (HTTP 422). Next, if `lights_out_hours` is greater than zero, both the part's `lights_out_eligible` flag and the machine's `lights_out_certified` flag must be true; if either is false, the request is rejected with `ERR_LIGHTS_OUT_NOT_PERMITTED` (HTTP 422).

The two occupancy checks come next, and they use deliberately different interval arithmetic. **Machine occupancy is evaluated first.** The candidate job occupies the half-open window running from its `scheduled_start_at` up to but not including its `scheduled_end_at`. Every existing work order on the same machine whose `machining_status` is anything other than `CANCELLED` occupies the half-open window from its own start up to but not including its own end plus a changeover buffer. That buffer is 45 minutes when the existing job's part and the candidate's part call for different bar diameters — the guide bushing and collets must be swapped — and is zero minutes when the two bar diameters are equal. The buffer is appended only to the earlier interval's end and is never prepended to the candidate's start. A conflict exists when the candidate's start falls strictly before the buffered end of an existing job and that existing job's start falls strictly before the candidate's end. Because the geometry is half-open, exact adjacency is legal: a candidate beginning at the very instant a buffered interval ends does not conflict. Existing jobs are examined in ascending `scheduled_start_at` order with ties broken by ascending `created_at`; cancelled jobs release their window immediately and never participate. A conflict is rejected with `ERR_MACHINE_WINDOW_CONFLICT` (HTTP 409).

**Bar-lot feeder occupancy is evaluated second**, and its rules are the mirror image. The candidate occupies the closed interval from its `scheduled_start_at` through its `scheduled_end_at` inclusive on the feeder of its bar lot. Every existing work order naming the same `bar_lot_id` whose `machining_status` is not `CANCELLED` occupies its own closed interval, with no buffer of any kind, and jobs on other lots never participate regardless of machine. The system counts how many of those existing intervals intersect the candidate's, where intersection means the candidate's start is at or before an existing job's end **and** that job's start is at or before the candidate's end. Because the geometry is closed, touching endpoints do collide — a candidate beginning at the exact instant an existing job ends is counted as overlapping, which is the opposite of the machine rule. Capacity is aggregate: the conflict fires when that count plus one exceeds the lot's `feeder_slots`, so on a lot declaring two slots the first intersecting job is admitted and only the second is refused. A conflict is rejected with `ERR_BAR_LOT_FEEDER_CONFLICT` (HTTP 409).

Two quantity gates close out the sequence. The candidate's `qty_ordered`, added to the `qty_ordered` of every non-cancelled sibling work order already on the same release, must not exceed the release's `qty`; exceeding it is `ERR_RELEASE_QTY_EXCEEDED` (HTTP 409). Finally the material must actually be on the rack, which requires the reservation arithmetic to be run.

That arithmetic works as follows. `required_length_mm` is the ordered quantity multiplied by the sum of the part's `cut_off_length_mm` and the 2.0-millimetre part-off kerf, plus a flat 300 millimetres of setup scrap. Because a bar cannot be fed to its very end, only the lot's `bar_length_mm` less a 150-millimetre remnant is usable from each bar. `bars_reserved` is therefore the required length divided by that usable length per bar, rounded **up** to the next whole bar — no fractional bar is ever taken off the rack. The work order's own `reserved_length_mm` is `bars_reserved` multiplied by the lot's full `bar_length_mm`, because whole bars leave the rack including the remnant that will never be cut. If that reserved length exceeds the lot's `available_length_mm`, the schedule is rejected with `ERR_BAR_STOCK_INSUFFICIENT` (HTTP 409).

When every gate passes, the reservation is booked: the reserved length is subtracted from the lot's `available_length_mm` and added to its `reserved_length_mm`, leaving the conserved total of §2.7 intact. The machine's `version` is incremented by one as part of the same operation — which is precisely why a second schedule authored against the version the client read before the first will be refused as stale. Work orders may be listed with any combination of `release_id`, `machine_id`, `bar_lot_id`, `part_id`, `machinist_operator_id` and `machining_status` as filters.

### 3.6. Running the Spindle and the Secondary Route

Starting a job is a `Machinist` act and drives `machining_status` `SCHEDULED → RUNNING`. The same action drives `INTERRUPTED → RUNNING`, which is the revision loop that makes the production dimension cyclic. Neither variant takes a request body; the acting operator is identified entirely by `X-User-ID`.

The preconditions differ slightly between the two entry points. Starting from `SCHEDULED` requires that the machine named by the work order is `AVAILABLE`, that the bar lot named by the work order is `CERTIFIED`, that no tool station on that machine sits in `OFFSET_HOLD` or `LIFE_EXPIRED`, that the operator behind `X-User-ID` exists and is `ACTIVE`, and — when the work order's `lights_out_hours` is greater than zero — that the operator's `certifications` array contains `LIGHTS_OUT`. Restarting from `INTERRUPTED` requires that the machine is `AVAILABLE`, that no tool station on it is held, and that the operator exists and is `ACTIVE`; the bar lot is not re-examined, because its material was reserved at schedule time. The rejection codes are, in evaluation order, `ERR_MACHINE_NOT_AVAILABLE` (HTTP 409) when the machine is `RUNNING` or `DOWN`, `ERR_BAR_LOT_NOT_CERTIFIED` (HTTP 409) when the lot is `RECEIVED`, `QUARANTINED` or `DEPLETED`, `ERR_TOOL_LIFE_EXPIRED` (HTTP 409) when any station on the machine is held, and `ERR_OPERATOR_NOT_CERTIFIED` (HTTP 403) when a lights-out job is started by an operator lacking the `LIGHTS_OUT` code.

A successful start writes `machinist_operator_id` from `X-User-ID` — on a restart it overwrites whatever operator was recorded before, so the last operator to touch the spindle is the one on the record. It sets the machine `AVAILABLE → RUNNING`, points the machine's `current_work_order_id` at this work order, and increments the machine's `version` by one. It moves the work order's kanban release `RELEASED → IN_PRODUCTION` when the release is still `RELEASED`; no quantity moves on the blanket order at this point, because the pieces were already shifted into `open_released_qty` when the release was cut. A restart out of `INTERRUPTED` carries one extra effect: every routing step on this work order sitting in `BLOCKED` is returned to `PENDING` and its `blocked_reason` is cleared.

Completing machining is likewise a `Machinist` act, declared only from `RUNNING`, and drives `machining_status` `RUNNING → MACHINING_COMPLETE`. The request reports `qty_good`, `qty_scrap` and `actual_run_seconds`, all of which are stored on the work order. The sum of good and scrap pieces must not exceed the work order's `qty_ordered`; a larger sum is rejected with `ERR_QTY_EXCEEDS_ORDERED` (HTTP 422). Completion then performs four things in one operation: it moves the work order's `reserved_length_mm` on the bar lot out of `reserved_length_mm` and into `consumed_length_mm`, leaving `available_length_mm` untouched; it drives the lot `CERTIFIED → DEPLETED` when both `available_length_mm` and `reserved_length_mm` have reached exactly 0; it computes the job's `chip_kg` and coolant make-up and accrues both onto the machine as described in §3.7; and it sets the machine `RUNNING → AVAILABLE`, clears `current_work_order_id` and increments the machine's `version` by one. The work order's `quality_status` is left exactly as it was — completion is a production event and says nothing about conformance.

Cancellation is a `ShopPlanner` act, declared from `SCHEDULED` and from `INTERRUPTED`, and carries a `reason` that is stored as the work order's `cancel_reason`. It drives `machining_status` to `CANCELLED`. The reserved bar length is returned from the lot's `reserved_length_mm` to its `available_length_mm`, leaving `consumed_length_mm` untouched so the length ledger stays conserved, and both the machine window and the bar-lot staging interval are released for reuse by later candidates. Every routing step on the cancelled work order that is `PENDING`, `BLOCKED` or `IN_PROGRESS` is moved to `BLOCKED` with `blocked_reason` recorded as `WORK_ORDER_CANCELLED`. When the cancelled work order happens to be the one the machine's `current_work_order_id` points at, the machine is released as well: its status is set to `AVAILABLE`, `current_work_order_id` is cleared, and its `version` is incremented by one.

Secondary work — deburr, wash and the rest — is modelled as a route of steps hung off the work order. A `ShopPlanner` adds a step naming the `work_order_id` it belongs to, its `sequence` position (at least 1 and unique within that work order), and the `operation`, which is one of `DEBURR`, `WASH`, `HEAT_TREAT`, `PLATING` or `INSPECTION_100PCT`. An optional `predecessor_step_id` names the step that must finish first; it defaults to null for the first step in a route. When a predecessor is supplied it must belong to the same work order and its `sequence` must be strictly lower than the new step's `sequence`; violating either condition is rejected with `ERR_PREDECESSOR_STEP_INVALID` (HTTP 422). A new step opens in `status` `PENDING`, one of `PENDING`, `IN_PROGRESS`, `COMPLETE` and `BLOCKED`, with `blocked_reason` null. Steps may be listed filtered by `work_order_id` or by `predecessor_step_id`.

A `Machinist` advances a step by naming the target in `to_status`. `PENDING → IN_PROGRESS` requires that the step's work order has already reached `machining_status` `MACHINING_COMPLETE` and, when `predecessor_step_id` is not null, that the predecessor step is `COMPLETE`. `IN_PROGRESS → COMPLETE` has no further precondition; completing a step unblocks nothing automatically, but successor steps become startable because their predecessor guard now passes. Steps also move without anyone asking: a `PENDING` step goes to `BLOCKED` when its work order moves to `INTERRUPTED` or to `CANCELLED`, an `IN_PROGRESS` step goes to `BLOCKED` when its work order is cancelled, and a `BLOCKED` step returns to `PENDING` — with `blocked_reason` cleared — when its work order moves `INTERRUPTED → RUNNING`. That return edge is what makes the routing step cyclic.

### 3.7. Tool Wear, the Machine-Down Chain, and Reclamation

Every so often during a run the `Machinist` logs what the tool has done and how far it has walked. The offset log carries `pieces_produced` and `measured_drift_um`, and posting one re-derives the station's wear state. The station's `pieces_since_index` is increased by the pieces produced, its `cumulative_drift_um` is increased by the measured drift — the accumulation is **signed**, so a positive correction followed by an equal negative correction returns the accumulator to zero — and its `offset_log_count` is increased by one.

The branch order is pinned: **life is evaluated first, drift second**. If, after the log has been applied, `pieces_since_index` is greater than or equal to the station's `expected_life_pieces`, the station moves `IN_SERVICE → LIFE_EXPIRED`. Otherwise, if the absolute value of `cumulative_drift_um` is greater than or equal to the station's `drift_limit_um`, the station moves `IN_SERVICE → OFFSET_HOLD`. Otherwise the station stays `IN_SERVICE`. Both comparisons include their boundary: a station that lands exactly on its rated life, or exactly on its drift limit, is held. A log that crosses both thresholds at once lands in `LIFE_EXPIRED`, because the life branch is tested first. Only the one station being logged and the single log being posted participate; logs written before the last index do not, because indexing zeroes both accumulators.

Either hold fires the same four-hop chain, and every hop must be applied. **Hop one** is the station itself reaching `OFFSET_HOLD` or `LIFE_EXPIRED`. **Hop two**, caused by that station being held, sends the station's machine to `DOWN` when the machine was `RUNNING` or `AVAILABLE`, and increments the machine's `version` by one. **Hop three**, caused by the machine reaching `DOWN`, moves the work order on that machine whose `machining_status` is `RUNNING` to `INTERRUPTED` and clears the machine's `current_work_order_id`; when no job was running, this hop and the next simply have nothing to act on. **Hop four**, caused by that work order reaching `INTERRUPTED`, moves every routing step of that work order that is `PENDING` to `BLOCKED` and records its `blocked_reason` as `UPSTREAM_MACHINE_DOWN`.

Indexing is how a held station comes back. The request may carry `new_tool_code`, which replaces the station's `tool_code` when supplied, and `retire`. Without `retire`, a station in `OFFSET_HOLD` or `LIFE_EXPIRED` returns to `IN_SERVICE` with `pieces_since_index`, `cumulative_drift_um` and `offset_log_count` all reset to 0 — the return edge that makes the tool station cyclic. When `retire` is supplied as true, a station in `OFFSET_HOLD` or `LIFE_EXPIRED` moves to `RETIRED` instead, permanently; any further offset log or index attempt against a `RETIRED` station is rejected with `ERR_INVALID_STATE`. Crucially, indexing does **not** bring the machine back — the machine is restored by its own separate action and by nothing else.

Restoring a machine is a `Machinist` act declared only from `DOWN`. It succeeds only when no tool station on that machine remains in `OFFSET_HOLD` or `LIFE_EXPIRED`; if one does, the restore is rejected with `ERR_TOOL_LIFE_EXPIRED`. A `RETIRED` station does not block a restore, because the guard inspects only the two held statuses — retiring a station is therefore a legitimate way to clear the path. A successful restore moves the machine `DOWN → AVAILABLE` and increments its `version` by one. Note that a machine can reach `DOWN` from two directions: from `RUNNING`, when a tool hold or a rejected inspection subgroup lands on a machine that is turning, in which case the running work order is carried to `INTERRUPTED`; and from `AVAILABLE`, when a tool hold lands on an idle machine, in which case no work order is affected because none is running. Either way the machine's `version` is incremented by one.

Machining completion is also where the shop's swarf and coolant bookkeeping happens. The consumed metres for the job are the work order's `reserved_length_mm` divided by 1,000. The job's `chip_kg` is those consumed metres multiplied by the bar lot's `mass_kg_per_meter`, minus the good-piece count multiplied by the part's `finished_mass_g` divided by 1,000 to convert grams to kilograms, with the result rounded half up to 3 decimal places. Scrapped pieces are deliberately not credited as finished mass, so the material in a scrapped piece stays in the chip bucket where the scrap dealer will find it. That chip mass is added to the machine's `chip_accrual_by_alloy` map under the part's `alloy_code` — the existing kilograms for that alloy, or zero if the alloy has no entry yet, plus the job's chip mass, rounded half up to 3 decimal places. In the same operation, the machine's `coolant_makeup_liters` is increased by the job's `actual_run_seconds` divided by 3,600 and multiplied by 0.35 litres of coolant make-up per machine hour, with the running total rounded half up to 3 decimal places. Work orders that have not reached `MACHINING_COMPLETE` contribute nothing to either bucket, because accrual is written only at completion.

Settlement is a `ShopPlanner` act against one machine, carrying a `collected_at` instant that records when the chip hopper was emptied. It turns the accrual into money, and its rounding order is pinned. The system walks the machine's `chip_accrual_by_alloy` entries in **ascending alloy code order by ASCII collation**, skipping any entry whose kilograms are exactly zero. Each line's credit is its kilograms multiplied by the scrap rate for that alloy — 118 cents per kilogram for `303SS`, 132 for `316SS`, 465 for `C360`, 87 for `6061AL` and 41 for `12L14` — rounded half up to a whole cent **on that line alone**. The chip credit is the sum of those rounded per-line integers; summing the unrounded lines and rounding once at the end is not the declared order and will differ by whole cents whenever the dropped fractions accumulate. Against that credit stands the coolant cost, which is the machine's `coolant_makeup_liters` multiplied by 420 cents per litre, rounded half up to a whole cent exactly once. The net reclamation credit is the chip credit minus the coolant cost, and no rounding is ever applied to that grand total.

The settlement then writes itself onto the machine: `last_reclamation_credit_cents` is set to the net credit — it may be negative when the coolant bill outruns the scrap value — `lifetime_reclamation_credit_cents` is increased by the same net credit, `chip_accrual_by_alloy` is emptied back to an empty map, `coolant_makeup_liters` is set to 0, and the machine's `version` is incremented by one. Because settlement zeroes both buckets, already-settled accrual can never be counted twice.

### 3.8. Gauges, Calibration Linkage and SPC Sampling

A `QualityManager` registers each measuring instrument with a `gauge_code` unique across the shop, a `gauge_type` drawn from `MICROMETER`, `BORE_GAUGE`, `OPTICAL_COMPARATOR` and `CMM`, the `calibrated_at` instant of its most recent successful calibration, the `calibration_due_at` instant at which that calibration lapses, and `grr_pct`, the gauge repeatability-and-reproducibility result expressed as a percentage of tolerance, which may be zero or more. `calibration_count` starts at 0. The gauge's opening `status` — one of `IN_SERVICE`, `CALIBRATION_DUE`, `GRR_FAILED` and `RETIRED` — is derived from what was registered: it is `IN_SERVICE` when `grr_pct` is at most 10 percent and `calibration_due_at` falls after the logical clock; it is `GRR_FAILED` when `grr_pct` is greater than 10 percent and at most 30 percent; and it is `RETIRED` when `grr_pct` is greater than 30 percent.

Calibration windows lapse on their own. Whenever a gauge is read, and whenever a subgroup post names it, the system re-evaluates lazily: a gauge that is `IN_SERVICE` and whose `calibration_due_at` is at or before the logical clock moves `IN_SERVICE → CALIBRATION_DUE`, and from that moment it no longer satisfies the in-service check that guards measurement.

Posting a calibration record is how a gauge comes back, and it is declared from `IN_SERVICE`, `CALIBRATION_DUE` and `GRR_FAILED` alike. The request supplies a fresh `calibrated_at`, a fresh `calibration_due_at` and the `grr_pct` from the new study; all three overwrite what was stored and `calibration_count` is increased by one on every post. The resulting state follows the posted study: when `grr_pct` is at most 10 percent and the posted `calibration_due_at` is strictly after the logical clock, the gauge returns to `IN_SERVICE` — the return edge that makes the gauge cyclic. When `grr_pct` is greater than 10 percent and at most 30 percent, the gauge lands in `GRR_FAILED` and stops satisfying the in-service check. When `grr_pct` is greater than 30 percent, the gauge is moved to `RETIRED` permanently, and any later calibration post against a `RETIRED` gauge is rejected with `ERR_INVALID_STATE`.

An `Inspector` posts a measured subgroup naming the `work_order_id` the pieces came from, the `characteristic_id` being measured, the `gauge_id` used, the `piece_index` — the ordinal piece number in the run at which the subgroup was pulled, at least 1 — and `measurements`, the array of individual measured values in millimetres. The subgroup's `inspector_operator_id` is taken from `X-User-ID`. A subgroup is an immutable observation: as noted in §2.4 it carries `id` and `created_at` but neither `updated_at` nor `version`.

Four domain checks guard the post, in this order. First the gauge must be `IN_SERVICE` after the lazy re-evaluation above; a gauge that is `CALIBRATION_DUE`, `GRR_FAILED` or `RETIRED` is rejected with `ERR_GAUGE_NOT_IN_SERVICE` (HTTP 409). Second comes the segregation of duties rule of §2.10, rejected with `ERR_SEGREGATION_OF_DUTIES`. Third, the length of the `measurements` array must equal the characteristic's `subgroup_size`; a mismatch is rejected with `ERR_SUBGROUP_SIZE_MISMATCH` (HTTP 422). Fourth, the characteristic's `part_id` must equal the work order's `part_id`, failing which the post is rejected with `ERR_CHARACTERISTIC_PART_MISMATCH` (HTTP 422); and last, the gauge's `gauge_type` must equal the characteristic's `required_gauge_type`, failing which it is rejected with `ERR_GAUGE_TYPE_MISMATCH` (HTTP 422).

An accepted post is scored immediately, against that one subgroup and nothing else — no sibling sample and no other work order participates. The subgroup's `mean` is the arithmetic mean of the measured values, rounded half up to 4 decimal places. Its `range` is the largest measured value minus the smallest, likewise rounded half up to 4 decimal places. `sigma_within` is the range divided by the bias-correction constant for the subgroup size — 1.693 when the characteristic's `subgroup_size` is 3, and 2.326 when it is 5 — rounded half up to 6 decimal places. `cpk_short_term` is then the lesser of two distances — the characteristic's `usl` minus the subgroup mean, and the subgroup mean minus the characteristic's `lsl` — divided by three times the within-subgroup sigma, rounded half up to 3 decimal places. `out_of_spec_count` is the number of individual measurements lying strictly below `lsl` or strictly above `usl`.

The subgroup's `disposition` follows from those two numbers. It is `REJECT` whenever `out_of_spec_count` is greater than zero, whatever the capability index says. When no measurement is out of spec, it is `MARGINAL` if `cpk_short_term` is strictly less than the characteristic's `cpk_min`, and `ACCEPT` if `cpk_short_term` is greater than or equal to `cpk_min` — the boundary is inclusive, so a subgroup landing exactly on the minimum is accepted.

The verdict then drives the work order's quality dimension. A subgroup dispositioned `ACCEPT` posted against a work order in `PENDING_INSPECTION` moves it `PENDING_INSPECTION → IN_SPC`, and nothing else in the system is touched — `machining_status` is left exactly as it was. A subgroup dispositioned `MARGINAL` or `REJECT` moves the work order `PENDING_INSPECTION → QUALITY_HOLD` if it was pending, or `IN_SPC → QUALITY_HOLD` if a study was already open. A `REJECT` disposition carries one additional cascade in both cases: the work order's machine is sent to `DOWN`, its `current_work_order_id` is cleared, and its `version` is incremented by one. A `MARGINAL` disposition does not touch the machine. When the work order is already in `QUALITY_HOLD`, the subgroup is still recorded and scored but no quality transition takes place. Subgroups may be listed filtered by `work_order_id`, `characteristic_id`, `gauge_id` or `inspector_operator_id`.

Alongside the per-subgroup index sits a second, stricter capability measure evaluated across every subgroup of one characteristic on one work order. The pooled readings are the concatenation of the `measurements` arrays of every subgroup naming that same work order and that same characteristic, taken in ascending `created_at` order with ties broken by ascending `piece_index`. Every such subgroup is pooled in regardless of its own `disposition` — `MARGINAL` and `REJECT` subgroups are counted, not filtered out — while subgroups belonging to any other work order are excluded even when they measure the same characteristic. The long-term mean is the arithmetic mean of the pooled readings. The overall sigma is the sample standard deviation of those pooled readings: the sum of the squared differences between each reading and the long-term mean, divided by one less than the number of pooled readings, then square-rooted. The long-term capability index is the lesser of the characteristic's `usl` minus the long-term mean and the long-term mean minus the characteristic's `lsl`, divided by three times that overall sigma, rounded half up to 3 decimal places. It is undefined — reported as null — whenever fewer than two readings have been pooled. Because the overall sigma counts drift between subgroups while the within-subgroup sigma cannot see it, the same measurement data yields a different number from the two variants; the per-subgroup verdict is judged on the short-term index and the acceptance gate of §3.9 is judged on the long-term one.

Sampling coverage is governed by frequency. For each characteristic of the work order's part, the required number of subgroups is the work order's `qty_ordered` divided by that characteristic's `sample_freq_pieces`, rounded **up** to a whole subgroup. The ceiling is applied per characteristic before anything is summed, never to a summed ratio. A computed read is available for any role that summarises this: it reports the work order's `work_order_id`, the `characteristic_count` of characteristics on the part, the `sample_count` of subgroups actually posted, the `required_sample_count` obtained by summing the per-characteristic requirements, the `out_of_spec_count` obtained by summing the out-of-spec tallies of every subgroup on the work order, `cpk_short_term_min` — the smallest short-term index among those subgroups, or null when no subgroup exists — and `ppk_long_term_min`, the smallest long-term index across the characteristics that have at least two subgroups, or null when no characteristic has two or more. An optional `characteristic_id` narrows the read to a single characteristic. When the part declares no characteristics at all, the characteristic and sample counts are 0, the required count is 0, coverage counts as complete, and both capability figures are null.

### 3.9. Disposition, the Fulfilment Chain and the Feedback Loop into Quoting

The final word on a job belongs to a `QualityManager`, who records a verdict carrying a `decision` of `ACCEPT`, `REJECT` or `RELEASE_HOLD` and an optional `note`.

`RELEASE_HOLD` is the lightest of the three and is declared only from `QUALITY_HOLD`, moving the work order `QUALITY_HOLD → IN_SPC`. The note is recorded on the work order and no sibling entity changes at all — this is the return edge that makes the quality dimension cyclic, and it is how a job that tripped a marginal subgroup gets a second chance once the process has been re-centred.

`ACCEPT` is declared only from `IN_SPC` and is the most heavily gated operation in the quality dimension. Its preconditions are, in order: the work order's `quality_status` must be `IN_SPC`; its `machining_status` must already be `MACHINING_COMPLETE`, because a job still turning cannot be signed off; every characteristic of the work order's part must have reached its required subgroup count as computed in §3.8, failing which the request is rejected with `ERR_SPC_SAMPLING_INCOMPLETE` (HTTP 409); and the long-term capability index of every characteristic with at least two pooled subgroups must be greater than or equal to 1.00, failing which the request is rejected with `ERR_CAPABILITY_BELOW_MINIMUM` (HTTP 409). Note the asymmetry between the two capability thresholds: a single subgroup is judged against the characteristic's own `cpk_min`, defaulting to 1.33, while the acceptance gate is judged against a long-term floor of 1.00 across pooled readings.

An accepted disposition sets `quality_status` to `ACCEPTED` and fires a four-hop fulfilment chain that every implementation must apply in full. **Hop one**: the work order's kanban release has its `fulfilled_qty` set to the work order's `qty_good` and moves `IN_PRODUCTION → FULFILLED`. **Hop two**, caused by that release reaching `FULFILLED`: on the release's blanket order, the release's `qty` is subtracted from `open_released_qty`, the work order's `qty_good` is added to the order's `fulfilled_qty`, the shortfall — the release quantity minus the good pieces — is added back to `remaining_qty`, and the order's `version` is incremented by one. The three buckets therefore still sum to `total_committed_qty`, with unproduced pieces returning to the pool rather than evaporating. **Hop three**, caused by that recomputation landing on both `remaining_qty` and `open_released_qty` at exactly 0: the blanket order moves `ACTIVE → EXHAUSTED`. **Hop four**, caused by the order reaching `EXHAUSTED`: the quote behind that order moves `ACCEPTED → CONSUMED`, and no further blanket order may ever be created from it.

`REJECT` is declared from `IN_SPC` and from `QUALITY_HOLD`, and in both cases requires that `machining_status` is already `MACHINING_COMPLETE`. It sets `quality_status` to `REJECTED` and moves the work order's kanban release `IN_PRODUCTION → SHORT_CLOSED` with `close_reason` recorded as `WORK_ORDER_REJECTED` and `fulfilled_qty` left at 0. On the release's blanket order, the release's `qty` is subtracted from `open_released_qty` and the same quantity is added back to `remaining_qty` — the whole release returns to the pool, none of it is credited as fulfilled — and the order's `version` is incremented by one. Because nothing lands in `fulfilled_qty`, a rejection can never drive an order to `EXHAUSTED` and never consumes the quote behind it.

Acceptance has one more consequence, and it closes the loop back to §3.3. The part's observed running figures are recomputed from every work order for that part whose `quality_status` is `ACCEPTED`. `observed_accepted_qty` becomes the sum of `qty_good` over that accepted set. When that sum is zero, `observed_avg_cycle_time_sec` is set to null; otherwise it is the sum of `actual_run_seconds` over the same accepted set divided by the accepted good-piece count, rounded half up to 1 decimal place. Jobs in `PENDING_INSPECTION`, `IN_SPC`, `QUALITY_HOLD` or `REJECTED` are excluded from both figures even when their `machining_status` is `MACHINING_COMPLETE` — which is exactly why a rejected disposition does **not** recompute them. The next quote priced on the historical basis for that part will therefore reflect the real, interrupted, lights-out-degraded seconds per piece rather than the engineered ideal.
