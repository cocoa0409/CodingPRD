# HNW Homeowners Underwriting API — Product Requirements Document

## 1. Introduction

High-net-worth personal lines underwriting is an appraisal-driven business: nothing may be bound until a credentialed human has stood on the property, and the moment the valuation goes stale or the wildfire exposure shifts, coverage that was already written must be revisited. This document specifies the API that supports that business for a carrier writing catastrophe-exposed dwellings through a licensed agency force. It governs the whole arc — registering the catastrophe zones and producing agencies, recording replacement-cost appraisals, scheduling jewelry, fine art, collections and wine against substantiating appraisal documents, imposing and verifying loss-prevention requirements, dispatching private wildfire defense during an active event, approving and binding policy enrollments, settling first-party losses, and deciding not to renew in zones where the carrier's exposure has become too concentrated.

Two pressures define the design. The first is regulatory: catastrophe-zone concentration is measured, banded and frozen, and a non-renewal in a concentrated zone follows a notice period that is read from the zone itself. The second is capital: every bind commits a reserve, and the replacement-cost valuation that reserve rests on is a moving target as appraisals are approved, superseded and re-opened across review cycles. The API therefore treats the dwelling's exposure values, the property's underwriting posture and the enrollment's bound limits as three separate, explicitly versioned things that must be reconciled at the moment of commitment rather than assumed to agree.

The scope below covers the full record set — dwellings, appraisals, appraisal documents, scheduled personal property, mitigation requirements, risk-consulting visits, defense dispatches, managed-risk letters, enrollments, claims and non-renewal notices — together with the reference configuration (risk zones, agencies and the logical clock) that the rest of the system reads. Authentication, response framing and pagination are specified first, because they are contract-level and identical across every resource; the business rules follow, deliberately distributed across the workflows that give them their meaning.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which it acts. A request missing either header, or naming a role the platform does not recognize, is refused with `ERR_UNAUTHENTICATED`; a request whose role is not among the roles the target operation admits is refused with `ERR_FORBIDDEN`. The one exception to the header requirement is the reference-clock operation, which is reachable by the operator role alone but is still screened for role membership. Note that an unrecognized role is a 401 while a recognized-but-unlisted role is a 403 — the two gates are distinct.

The platform recognizes seven role names, spelled exactly as follows: `Underwriter`, `AgencyProducer`, `ClaimsAdjuster`, `RiskConsultant`, `PlatformAdmin`, `ComplianceReporter`, and `Anonymous`. The `Underwriter` is the binding authority — posture derivation, appraisal approval and provision, enrollment approval and attachment, mitigation imposition and waiver, non-renewal issuance and vendor dispatch all sit with this role. The `AgencyProducer` is the agent-produced business role, acting on behalf of the agency of record. The `ClaimsAdjuster` handles first-party losses. The `RiskConsultant` performs the complimentary on-site visit and verifies completed mitigation work. The `PlatformAdmin` owns reference configuration and the logical clock. The `ComplianceReporter` is a non-writing regulatory audience; `Anonymous` exists only to exercise the authentication gate and holds no operations.

Identity binds differently for different roles. When `X-User-Role` is `AgencyProducer`, `X-User-ID` is the `id` of the acting `Agency`; every producer-scoped ownership check on any resource that references an `Agency` compares the resource's foreign-key field — `agency_id` on an `Enrollment`, for instance — to `X-User-ID`, and a mismatch is refused with `ERR_AGENCY_NOT_OF_RECORD`. For the other six roles — `Underwriter`, `ClaimsAdjuster`, `RiskConsultant`, `PlatformAdmin`, `ComplianceReporter` and `Anonymous` — `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record such an identifier where a scaffold rule calls for it — the `consultant_user_id` on a `RiskConsultation` and the `adjuster_user_id` on a `Claim` are both supplied by the caller — but it never compares an opaque identifier to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept a `limit` and an `offset`. `limit` caps the number of records returned, defaults to 10 when omitted, and must fall between a minimum of 1 and a maximum of 100. `offset` skips that many records and defaults to 0. Unless a resource-specific rule says otherwise, every list is returned in ascending order of the record's `created_at` timestamp. Responses to list operations carry the four pagination fields — `limit`, `offset`, `total_count` and `has_more` — inside the `meta` object of the standard envelope.

### 2.4. The Logical Clock and Temporal Determinism

The platform does not read the host wall clock. A logical clock is the single source of "now" for every currency, notice, lapse and dispatch-age rule, which makes those rules reproducible. At server startup the clock is pinned to 2026-09-01T00:00:00Z. The only way it moves is an operator-driven clock advance, which accepts the desired instant as `current_utc` and takes no other input. The clock never falls back to real time, and it is monotone in practice: the business rules below assume that advancing it is how a test scenario "waits".

Advancing the clock is not a passive bookkeeping act. On read, every field whose value is derived from elapsed time is recomputed — the `currency_months` of an `AppraisalDocument`, the `appraisal_currency_months` of a `ScheduledItem`, and the `notice_period_days` of a `NonRenewalNotice` are all refreshed from the new instant. Advancing the clock also fires each automatic, date-driven state transition whose threshold the advance has crossed, without any client request against the affected resource. Four temporal thresholds recur throughout the specification: an approved base appraisal remains within currency for 24 months and the property reverts to `PENDING_APPRAISAL` once none does; a scheduled consulting visit that is not completed within 7 days past its appointment becomes a no-show; a non-renewal may not be issued against a policy bound fewer than 60 days earlier; and each defense assignment occupies a 24-hour window on its zone.

### 2.5. Nested Resource Retrieval and Left-to-Right Resolution

When a request path carries more than one resource identifier — a `property_id` above an `id`, or a `dispatch_id` nested under a zone — the server resolves those identifiers strictly left to right and rejects the request with `ERR_NOT_FOUND` at the first one that does not correspond to a stored record. A request naming an `id` under a `property_id` that does not exist fails on the property before the child is ever looked up, and the same ordering applies to creation and modification operations, where the parent's existence takes precedence over any validation of the payload. A catastrophe-zone code that matches no zone resolves through the same `ERR_NOT_FOUND` path rather than a distinct error of its own.

### 2.6. Common Resource Properties

Resources created with the common field set carry four system-managed properties. `id` is a unique, server-minted identifier formatted as a UUID; it is opaque and carries no type prefix or domain segment. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording first persistence. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits refreshed on any change to the resource's own properties. `version` is a system-managed integer that increments with each modification, and it is the anchor for the concurrency rules in §2.8.

`RiskZone`, `Agency`, `Property`, `Appraisal`, `ScheduledItem`, `MitigationRequirement`, `RiskConsultation`, `WildfireDefenseDispatch`, `Enrollment`, `Claim` and `NonRenewalNotice` all carry the full set. Two records do not: an `AppraisalDocument` and a `ManagedRiskEvent` are created with `id` and `created_at` only, and therefore expose neither `updated_at` nor `version`; nothing in the specification keys a mutation or a concurrency check on either of them. A mutation to a derived field on a parent — recomputing a property's valuation, recomputing a zone's concentration ratio — is a mutation like any other: it refreshes `updated_at` and increments `version` on the record it changed.

### 2.7. Valuation Arithmetic and Monetary Precision

All monetary quantities in this system are integer cents, and the arithmetic that produces them is fixed rather than incidental. Replacement-cost accumulation is evaluated in a pinned order: each contributing appraisal's weight is established first, then each per-appraisal product is rounded half up to the cent, and only then are the rounded products summed. "Round each then sum" and "sum then round" diverge by cents once a re-opened appraisal is in the mix, so the order is part of the contract. Percentages are rounded half up to 2 decimal places and rounded exactly once, after the division, never before. Premiums are rounded half up to the cent at each step, and the ratio that scales them is rounded half up to 4 decimal places before it is used. Score values are whole integers rounded half up and computed once, at the end of their evaluation. Two thresholds are stated as ratios rather than amounts and must not be pre-rounded: the guarantee ratio compares appraised dwelling cost against current replacement cost at 1.50, and the extended-replacement factor scales a limit at 1.5.

### 2.8. Optimistic Concurrency Control on Property Writes

Two operations write against a `Property` and both are guarded, because both legitimately move the property's valuation inputs and therefore its `version`. An enrollment attachment — `POST /hnw/enrollments/{id}/attach` — must carry `expected_property_version` holding the property version the client last observed; if another writer has advanced the property's version since, the attachment is rejected with `ERR_STALE_VERSION` (HTTP 412), which is what stops a client from binding coverage against a valuation it has not seen. Re-running the ordered underwriting gate — `POST /hnw/properties/{id}/posture-eval` — carries the same `expected_property_version` guard and rejects a stale view with the same `ERR_STALE_VERSION` at HTTP 412, because the evaluation itself stamps `appraised_at` and may auto-impose a requirement, and a second evaluation built on superseded inputs would derive a posture from values that no longer hold. `expected_property_version` is a required field on both operations. No other endpoint in this API accepts a version field; in particular, attachment is the only enrollment write that is version-guarded, and the version it carries is always the property's, never the enrollment's own.

### 2.9. The Ordered Underwriting Gate

A property's fitness to be written is expressed as two separate enumerations. `base_posture` is the ordered gate derived purely from the property's own appraisal and mitigation state, and takes one of `PENDING_APPRAISAL`, `MITIGATION_REQUIRED`, `UNDERWRITABLE` or `DECLINED`; it is initialized to `PENDING_APPRAISAL` when the dwelling is registered. `posture` is the write-facing verdict and takes one of `WRITE_FROZEN`, `REFERRAL_REQUIRED` or `WRITE_ELIGIBLE`; it is initialized to `WRITE_FROZEN`, so a newly registered dwelling cannot be submitted until the gate has actually run.

The two are linked by a pinned precedence order, and the order matters because the conditions overlap. `DECLINED` or `PENDING_APPRAISAL` as the base posture yields `WRITE_FROZEN`, first and unconditionally. Only if the base posture survives that test does a zone freeze push the verdict to `WRITE_FROZEN`. Only then does a base posture of `MITIGATION_REQUIRED` yield `REFERRAL_REQUIRED`. Only then does unresolved wildland-urban-interface exposure yield `REFERRAL_REQUIRED` — that branch fires when the bound zone's `exposure_band` is `ELEVATED`, the zone's `wildland_urban_interface_band` is `WITHIN_WUI` or `ADJACENT_WUI`, and the property's `defense_in_progress` is false. Everything else is `WRITE_ELIGIBLE`. The agency concentration band never participates in a property's posture: an agency that has become over-concentrated in a zone does not, by itself, freeze or refer the dwellings it produced.

### 2.10. Catastrophe Concentration and Portfolio Freeze

Exposure concentration is measured at two scopes and only at a population of two or more active enrollments. The active population is every enrollment whose `status` is `SUBMITTED`, `REFERRED`, `APPROVED` or `ATTACHED` — terminal enrollments are excluded — and the currency of the measurement is each enrollment's property's `total_insured_value_cents`. When the portfolio holds fewer than two such enrollments the ratio is pinned to 0.0 and the band to `NORMAL`, even though a single active enrollment is by construction the entire book.

The zone-scope ratio is the zone's share of that exposure, rounded half up to 2 decimal places once: at or above 30.0 the zone band is `CRITICAL`, at or above 18.0 it is `ELEVATED`, and otherwise `NORMAL`. The zone ratio's denominator is the whole active book, so it is 100.0 for a book that lives entirely in one zone, however small that book is. A zone whose band is `CRITICAL` — and only then, and only with a population of at least two — sets `freeze_active`, and a frozen zone blocks attachment on every property bound to it. The agency-scope ratio narrows the numerator to the zone and agency intersection and divides it by that zone's own exposure rather than by the portfolio — so an agency holding every active enrollment of its zone reads 100.0 in that zone — and it is banded far more tightly: `CRITICAL` at or above 25.0 and `ELEVATED` at or above 15.0. An agency band is a ranking signal, not a gate — a `CRITICAL` agency never freezes a zone and never blocks an attachment. Recomputing concentration is a portfolio-wide act, since the denominator moves whenever an enrollment enters or leaves the active population; every recomputation re-derives the freeze flag and, where that flag flipped, the posture of every property in the affected zone.

### 2.11. Request Validation Priority Ladder

Where several checks could refuse the same request, their order is fixed, because the error a caller sees should be the most fundamental defect rather than an arbitrary one. Authentication is evaluated first (priority 1), then role membership (priority 2), then left-to-right resolution of path identifiers (priority 3). Payload-shape defects are caught alongside these: a required input field that is absent, an enumerated value that falls outside its declared set, or a numeric value that violates a declared bound is refused with `ERR_INVALID_REQUEST` before any business rule is consulted, which is why a request carrying both a malformed enumeration and a frozen property reports the malformed enumeration. Business-safety gates follow — the write-frozen gate (priority 4, ahead of the zone-freeze gate at priority 5 and the referral-posture gate at priority 6), because a frozen property is a more fundamental refusal than a referred one. Producer scoping (priority 7) precedes the state-validity check (priority 8), and both precede the stale-version guard (priority 9). The remaining checks are business-temporal and business-fiscal constraints, ordered so that a defect in the request's own arithmetic or its temporal basis surfaces ahead of the softer eligibility rules: mitigation lapse and notice period (priorities 10–11), then the aggregate scheduled-value cap and the coverage-ceiling and coverage-floor checks (priorities 12–14), then ground actionability, valuation staleness and the appraisal-document referential checks (priorities 15–18), then agency activity and enrollment-bound status (priorities 19–20), and finally the slot-conflict, dispatch-capacity, branch-capital, deductible and endorsement-compatibility checks (priorities 21–25). A caller that supplies a request failing two rules will therefore see the lower-numbered rule's error, not whichever check the implementation happened to run first.

## 3. Business Logic & Workflows

### 3.1. Appraisal Intake and the Valuation Ledger

Replacement-cost valuation begins when an underwriter records an appraisal against a dwelling. The payload names the `appraiser_name`, the `valuation_method` — one of `SITE_MEASURED`, `DESKTOP_ESTIMATE` or `DRIVE_BY` — the `appraised_on` date, the `dwelling_cost_cents`, an optional `contents_cost_cents` defaulting to 0, and the `valuation_confidence_pct`, which must be greater than zero and no greater than 100. The `dwelling_cost_cents` must be strictly positive. A `review_kind` may be supplied and defaults to `VALUATION_PROVISION`; the other admissible value is `FULL_APPRAISAL`, which distinguishes a full post-approval re-appraisal from a valuation-provision review. A new row is born in `PENDING_REVIEW` with `percent_complete` at 0.00, and nothing about the property's valuation moves yet.

Review and approval are the two halves of the sourcing cycle. Moving a `PENDING_REVIEW` appraisal into `REVIEWED` changes no valuation field. It is approval that converts a row into a contributing valuation: `percent_complete` becomes 1.00, and the property's `dwelling_replacement_cost_cents` and `contents_replacement_cost_cents` are recomputed by accumulating every contributing appraisal, followed by a recomputation of `total_insured_value_cents`. Not every reviewed row may be approved outright, however. An ordinary approval requires the row's `valuation_method` to be `SITE_MEASURED`; a row carrying any other method is refused with `ERR_APPRAISAL_METHOD_INVALID`. The second admissible path is the valuation provision: a reviewed row may be approved as a provision only when at least one prior appraisal on the same property already holds `APPROVED` or `SUPERSEDED` status and the highest such prior `dwelling_cost_cents` is at least 1.25 times the provision row's own `dwelling_cost_cents`. When no such baseline exists, or the baseline falls below that multiple, the provision is refused with `ERR_APPRAISAL_PROVISION_BASELINE`. A reviewed row can also be marked `SUPERSEDED` — which is how a desktop estimate or a drive-by is retired while still contributing at full weight — or `WITHDRAWN`, the latter being a producer action available only while no enrollment of the property is `APPROVED` or `ATTACHED`. Rejection is available from both `PENDING_REVIEW` and `REVIEWED`, may carry a free-text `reason`, and leaves the property's valuation untouched.

The valuation ledger itself is an accumulation with a pinned evaluation order. The contributing set is every appraisal of the property whose `status` is `APPROVED` or `SUPERSEDED`; rows in `PENDING_REVIEW`, `REVIEWED`, `REJECTED` or `WITHDRAWN` contribute nothing at all. For each contributing row the server multiplies the row's `dwelling_cost_cents` by that row's `percent_complete`, rounds the product half up to the cent, and adds the rounded products together to give `dwelling_replacement_cost_cents`; it does the same with `contents_cost_cents` to give `contents_replacement_cost_cents`. The `scheduled_valuation_cents` component is the sum of `attached_value_cents` over the property's scheduled items in status `APPROVED` or `ATTACHED`. `total_insured_value_cents` is the dwelling component plus the contents component plus the scheduled component. Loss-of-use coverage is never part of this sum, and never participates in any concentration or exposure measurement. This is the only place the per-appraisal rounding order bites: because a row carries weight 1.00 while `APPROVED` or `SUPERSEDED` and 0.00 otherwise, re-opening a row silently drops it out of the sum without deleting anything.

Two reversal paths keep the ledger honest. An underwriter may re-open an already approved appraisal for a fresh review cycle by naming the `appraisal_id`; the target row returns to `REVIEWED` with `percent_complete` reset to 0.00, and the property's dwelling and total insured value are recomputed so the row stops contributing immediately. The re-opened row is then recycled through review and approval rather than replaced, which is precisely why a provision can be re-derived from a superseded baseline. Re-opening is refused while any other appraisal of the same property sits in `PENDING_REVIEW` or `REVIEWED`, so the property never has two valuations in flight. Separately, the base appraisal currency lapses on its own: once the logical clock passes 24 months from the latest approved site-measured appraisal, and no approved appraisal remains within currency, the property reverts to `PENDING_APPRAISAL` — but the dwelling component continues to be computed from the stale approved rows rather than being zeroed, so the exposure figure survives the lapse even as the gate closes. A property that has reached `UNDERWRITABLE` cannot outlive the valuation that funded its gate: whenever its posture or its derived valuation fields are recomputed and it no longer rests on an approved appraisal produced by a site measurement that remains within currency — because the last contributing row was re-opened, or because its approved appraisals have aged out — its base posture falls back to `PENDING_APPRAISAL` on the same recomputation, closing the write-facing posture to `WRITE_FROZEN` as well and leaving the property's enrollments where they stand rather than returning a parked `REFERRED` row to the queue. The clock-driven lapse described just above is the case that does re-queue: a `SUBMITTED` enrollment of a property that reverts through that lapse is pushed to `REFERRED`.

### 3.2. Scheduled Personal Property and Appraisal-Document Currency

Jewelry, fine art, collections and wine are scheduled against a dwelling rather than folded into contents. A producer or underwriter schedules an item by naming the `item_type` — `JEWELRY`, `FINE_ART`, `COLLECTION` or `WINE` — the `declared_value_cents`, which must be strictly positive, and the `appraisal_doc_id` of the substantiating appraisal document. The item is born in `PENDING` with `attached_value_cents` at 0, and contributes nothing until it is approved. Appraisal documents are filed separately against the dwelling, each carrying an `item_class` — one of `JEWELRY`, `FINE_ART`, `COLLECTION`, `WINE` or `DWELLING` — an `appraiser_name`, an `appraisal_date` and an `appraised_value_cents` that must be strictly positive. Filing a document immediately computes its `currency_months` as the whole months from `appraisal_date` to the logical clock, derives its `currency_status` band as `CURRENT`, `AGING` or `EXPIRED`, and computes `expires_on` as the appraisal date advanced by 24 months and then rolled forward to the first day of the following month.

Approving a scheduled item is a five-part test, and every part must hold. The substantiating document must belong to the same property as the item. Its `item_class` must match the item's `item_type`. Its `currency_status` must be `CURRENT` or `AGING` — an `EXPIRED` document, or one whose `appraised_value_cents` falls below the item's `declared_value_cents`, is refused with `ERR_APPRAISAL_CURRENCY_EXPIRED`. A document that belongs to another property or mismatches the item class is refused with `ERR_APPRAISAL_DOC_MISMATCH`. And the aggregate test: the sum of `declared_value_cents` across the property's items already in status `APPROVED` or `ATTACHED`, counted together with the item under approval, must not exceed 60 percent of the property's `total_insured_value_cents`; a breach is refused with `ERR_SCHEDULED_VALUE_CAP`. Approval recomputes the item's `appraisal_currency_months` from the clock and then recomputes both `scheduled_valuation_cents` and `total_insured_value_cents` on the property. An item that is already `APPROVED` may instead be thrown back to `REJECTED` on the re-work branch, but only while its `appraisal_currency_months` has reached 24 — a stale approved item is not silently retained.

Currency decay is a live hazard, so two paths exist to deal with it without a full re-schedule. A producer may refresh an approved item by repointing it at a newer document: the item must have reached `appraisal_currency_months` of at least 24, and a replacement document of matching `item_class` must exist with `currency_status` `CURRENT` or `AGING`. The item's `appraisal_doc_id` is repointed, the currency months recomputed, the status reset to `PENDING`, and `attached_value_cents` zeroed because the row is no longer approved; both property-side aggregates are recomputed. Consumption is the other path: when the property's enrollment reaches `ATTACHED`, every approved scheduled item of that property transitions to `ATTACHED` automatically, and `attached_value_cents` becomes the item's `declared_value_cents` — which is what makes the scheduled component of `total_insured_value_cents` real. An attached item is detached back to `APPROVED` by an underwriter, optionally naming the `claim_id` of the closed claim, but only once that claim has already reached `SETTLED`, `PAID` or `REJECTED`; a detach before the claim closes is refused.

### 3.3. Mitigation Requirements and the Risk-Consulting Visit

A mitigation or loss-prevention requirement is how the carrier records that a dwelling must do something before it can be written. An underwriter or a risk consultant imposes one by naming the `requirement_code` — `DEFENSIBLE_SPACE`, `FIRE_RESISTANT_ROOF`, `EMBER_VENT_SCREEN`, `EXTERIOR_IRRIGATION` or `FULL_MITIGATION_PROGRAM` — the `band_awarded` it confers when satisfied, which is either `CLEARED` or `PARTIAL`, the `source` of the requirement, one of `UNDERWRITING`, `RISK_CONSULTANT` or `DEFENSE_FOLLOW_UP`, and a `due_on` date. The requirement is born `IMPOSED` with `verification_count` at 0 and `verified_on` null. Imposing a requirement recomputes the property's `base_posture` and, when the property was `UNDERWRITABLE`, moves it to `MITIGATION_REQUIRED` while pushing every `SUBMITTED` enrollment of that property to `REFERRED`. A requirement may be waived by an underwriter on a supplied `reason`, which sets it to `WAIVED` and recomputes the base posture.

Verification is the consultant's act and is a compare-and-set. The consultant supplies the `verified_band` observed in the field and, optionally, the `verification_count` last observed; a request carrying a count that no longer matches the stored one is refused rather than applying a second verification against a row the client has not re-read. Verification must take place no later than the requirement's `due_on` — a verification attempted after that date is refused with `ERR_MITIGATION_LAPSED`. On success the requirement becomes `VERIFIED` with `verified_on` stamped, `verification_count` is incremented by exactly one, and both the property's `mitigation_band` and its `base_posture` and `posture` are recomputed. The count is monotone: it is never decremented, so re-opening a verified requirement for re-inspection — an act that resets its status to `IMPOSED` and clears `verified_on` while leaving `verification_count` untouched and setting a fresh `due_on` — does not erase the history of how many times the work has been signed off. That history matters on the second pass: if the count reaches 2, a `ManagedRiskEvent` of `event_type` `REPEAT_INSPECTION_NOTICE` is recorded, unless a letter carrying the identical key already exists.

The property's `mitigation_band` summarizes the whole set and is read as an ordered cascade. If any verified requirement confers `CLEARED`, the band is `CLEARED`. Failing that, if any verified requirement confers `PARTIAL`, the band is `PARTIAL`. Failing that, if any requirement at all is `LAPSED` or `WAIVED`, the band is `FAILED`. Otherwise the band is `UNVERIFIED`. When the last open requirement of a property lapses on its due date, or is waived, the property's gate closes: its `posture` becomes `WRITE_FROZEN` and every `DRAFT` or `SUBMITTED` enrollment of that property is driven to `DECLINED`.

The complimentary risk-consulting visit is booked against a dwelling by naming the `consultant_user_id`, the `scheduled_for` instant and a `duration_minutes` that must be strictly positive. The booking is born `SCHEDULED` and is refused with `ERR_CONSULTATION_SLOT_CONFLICT` when it would overlap another non-cancelled consultation of the same consultant. The overlap test uses a half-open interval running from `scheduled_for` to `scheduled_for` plus `duration_minutes`: an appointment starting exactly at the instant a previous one ends is adjacent, not overlapping, and is therefore allowed. A scheduled visit may be completed by the consultant once the clock has reached `scheduled_for`, which stamps `completed_at`; it may be cancelled by a producer strictly before `scheduled_for`; and it becomes a `NO_SHOW` automatically once the clock passes `scheduled_for` by more than 7 days without completion. Completion is not always the end of the road: a visit that has been completed and that has already produced a report (`report_issued_at` not null) may be recycled into a fresh appointment, which returns it to `SCHEDULED` and clears both `completed_at` and `report_issued_at`. The report itself is issued in the same action that may impose its recommendation — the consultant supplies the `requirement_code`, `band_awarded` and `due_on`, the visit's `report_issued_at` is stamped, a requirement is created with `source` `RISK_CONSULTANT` and status `IMPOSED`, and the property's posture is recomputed and moved to `MITIGATION_REQUIRED` if it had been underwritable with nothing open. The action answers with the pair of identifiers it produced — the `consultation_id` and the `mitigation_requirement_id` of the requirement it just imposed.

### 3.4. Catastrophe Zone and Agency Configuration

The reference layer that everything else reads is configured by the platform operator. A catastrophe risk zone is registered by supplying its `zone_code`, which must be unique across all zones, its two-letter `state_code`, its `wildland_urban_interface_band` — `WITHIN_WUI`, `ADJACENT_WUI` or `OUTSIDE_WUI` — its design `sustained_wind_mph`, which must be at least zero, and its `mitigation_band_multiplier`, which must be strictly positive. Two further values may be supplied: the `mitigated_loss_multiplier`, the factor applied to base loss when a property is `CLEARED`, which defaults to 1.0, and the zone's `state_event`, which defaults to `NONE` and may be `NONE`, `WATCH` or `ACTIVE`. The zone's catastrophe severity band, `exposure_band`, is supplied at registration as one of `STANDARD`, `ELEVATED` or `EXTREME`, and it is this band that later feeds the risk score directly. The zone's computed fields — `concentration_ratio_pct`, `concentration_band` and `freeze_active` — are not accepted at registration; `freeze_active` defaults to false and is re-derived from the concentration band, being true only while the band is `CRITICAL`. Note that an agency writing into a zone never changes the zone's own `exposure_band`; only the zone's own definition does.

Setting the zone's event level is a separate act from registering it, and it has weight. Dropping a zone's `state_event` below `ACTIVE` cancels every defense dispatch in that zone that has reached vendor assignment, and recomputes `defense_in_progress` on every affected property. Recomputing concentration is likewise a deliberate action, covered in §2.10: it re-derives the zone ratio and band, re-derives the ratio and band of every agency with exposure in the zone, recomputes the posture of every property bound to a zone whose freeze flag changed, and pushes the `SUBMITTED` enrollments of any newly frozen property to `REFERRED`. A property in a zone whose freeze flag flips off has its posture re-derived on the same sweep — it sheds the freeze and may return to `WRITE_ELIGIBLE`, or resolve to whatever other posture its own appraisal and mitigation state warrants — but its `REFERRED` enrollments are not returned to the queue.

An agency is registered with a unique `agency_code`, a `legal_name`, its `state_code` of licensure, and a `delegated_authority_limit_cents` that must be at least zero — the maximum replacement cost the agency may bind without referral. Its `servicing_tier` defaults to `STANDARD` and may be `PREMIER`, `SELECT` or `STANDARD`; its `active` flag defaults to true. An agency's own `concentration_ratio_pct` and `concentration_band` are computed, never supplied, and reflect the share of the carrier's portfolio that this agency wrote for the zone in question. An operator may flip an agency's `active` flag at any time, and deactivating an agency blocks the two producer acts that depend on an active license: submitting an enrollment and recalling one.

### 3.5. The Underwriting Gate: Posture, Referral and Enrollment Intake

A dwelling is registered against a zone and a producing agency by supplying the `risk_zone_id`, the `agency_id`, the `address_line`, and an optional `grid_risk_block` defaulting to `UNGROUPED`. The grid block is an adjacency key: dwellings that share one are treated as co-exposed for exposure purposes. A newly registered property is born `PENDING_APPRAISAL` and `WRITE_FROZEN`, with its replacement-cost figures, `scheduled_valuation_cents` and `total_insured_value_cents` all at 0, and with `defense_in_progress` false. Nothing can be submitted against it until the gate has been run.

Running the gate is a version-guarded act and it is where the appraisal and mitigation strands finally meet. The evaluation requires `expected_property_version` to match the property's current `version` (§2.8), so a caller working from a stale view is refused with `ERR_STALE_VERSION` rather than allowed to derive a posture from superseded inputs. It then applies its tests in a fixed order, and that order is deliberate. A fully mitigated property whose valuation is nonetheless too thin must still fail closed: the guarantee-ratio test runs before the mitigation short-circuit, so the presence of `CLEARED` mitigation never rescues an under-insured appraisal. Concretely, the property passes to `UNDERWRITABLE` only when at least one appraisal holds `APPROVED` status, at least one approved appraisal was produced by a site measurement, and the latest approved appraisal satisfies the 1.50 guarantee ratio — meaning its appraised `dwelling_cost_cents` is at least 1.50 times the property's current `dwelling_replacement_cost_cents`. When the latest approved appraisal fails that ratio the property is driven to `DECLINED` instead, its posture set to `WRITE_FROZEN`, and every `DRAFT` or `SUBMITTED` enrollment of that property moved to `DECLINED` — which in turn launches the declined-enrollment cascade described in §3.9. On the passing path, `appraised_at` is stamped from the latest approved appraisal's `appraised_on`, and the posture is recomputed. One conditional side effect rides along: if no `CLEARED` mitigation exists, the zone's `exposure_band` is `EXTREME`, and the zone's `wildland_urban_interface_band` is `WITHIN_WUI` or `ADJACENT_WUI`, a `DEFENSIBLE_SPACE` requirement is auto-imposed with `band_awarded` `PARTIAL`, `source` `UNDERWRITING` and a `due_on` taken from the latest approved valuation's `appraised_on` — so an already-stale appraisal date makes the follow-up overdue the moment the clock next moves.

Two further automatic transitions close the loop between mitigation and the gate. Imposing a requirement as the explicit act of a workflow that names it — through the mitigation endpoint, from any of its sources, or through the report a consulting visit issues — moves an `UNDERWRITABLE` property to `MITIGATION_REQUIRED`, pushes its `SUBMITTED` enrollments to `REFERRED`, and increments the property's version. The follow-ups the platform imposes for itself — the defensive-space requirement a gate evaluation spawns, and the one a defense completion spawns — are recorded and recompute the property's mitigation band, but leave its base posture where it stands, with the write-facing posture still re-derived from the rest of the ladder. And the appraisal-lapse path in §3.1 moves an `UNDERWRITABLE` property back to `PENDING_APPRAISAL`, again pushing its `SUBMITTED` enrollments to `REFERRED`. A `DECLINED` property is terminal unless an underwriter reopens it at the branch of record. Reopening recomputes `base_posture` and `posture` from the property's current appraisal and mitigation state and increments its version, and in deriving that base posture the property falls back to `PENDING_APPRAISAL` while it holds no approved appraisal, while no approved appraisal was produced by a site measurement, or while none of its approved appraisals remains within currency; otherwise the derived posture is `MITIGATION_REQUIRED` if any requirement of the property is still `IMPOSED`, and `UNDERWRITABLE` when none is. Reopening is refused when the branch the property would inherit has a `mitigated_loss_multiplier` above 1.00 — that is, when the zone baseline has not been capitalised — with `ERR_BRANCH_CAPITAL_INSUFFICIENT`.

An enrollment is opened by a producer against a dwelling by naming the producing `agency_id` and the desired `dwelling_coverage_cents`, with optional `contents_coverage_cents`, `scheduled_coverage_cents` and `loss_of_use_coverage_cents` all defaulting to 0. The `dwelling_coverage_cents` must be strictly positive, and the rules that govern it are stated where they bite: the Coverage A limit must be at least 1.5 times the current replacement cost, and the eventual binding minimum is checked at attachment (§3.7). The enrollment is born `DRAFT` with `risk_score` at 0, `risk_tier` at `MANAGED`, `replacement_provision` at `NONE`, and reserves recomputed. It then travels a queue whose branches are enumerated in §4's table. Submission is the producer's act and is refused unless the acting agency is the agency of record, the agency is active (`ERR_AGENCY_INACTIVE` otherwise), and the property's posture is neither `WRITE_FROZEN` (`ERR_WRITE_FROZEN`) nor `REFERRAL_REQUIRED` (`ERR_POSTURE_REFERRAL_REQUIRED`). Referral is the underwriter's act and requires the property's posture to be `REFERRAL_REQUIRED` or `WRITE_ELIGIBLE`.

### 3.6. Wildfire Defense Dispatch

Private wildfire defense is dispatched only while a zone is in an active event. A producer or underwriter requests defense for a dwelling during such an event, which creates a dispatch request in `REQUESTED` and computes its `priority_rank` — the ordering key that decides who gets a vendor first. The rank is a single integer assembled from three components: a zone rank that is 1 when the property's `mitigation_band` is `PARTIAL` or `UNVERIFIED` and 2 otherwise, multiplied by one million; an expiring rank that is 0 when the property holds any `IMPOSED` requirement whose `due_on` falls within the next 14 days and 1 otherwise, multiplied by one thousand; and the whole-day age of the property measured from its `created_at` to the logical clock. Lower rank dispatches first, and because the zone rank is scaled by a million, an unmitigated property in a zone always outranks a `CLEARED` one regardless of how long it has waited. A `CLEARED` property is never excluded from the queue outright; it simply ranks last within its zone.

Polling the vendor network assigns exactly one queued request per poll, drawn from the zone being polled. The candidate pool is every dispatch in `REQUESTED` whose zone's `state_event` is `ACTIVE`, restricted to the polled zone, and excluding any zone already holding two or more assignments whose occupancy windows overlap — each assignment occupies the half-open window from `assigned_at` to `assigned_at` plus 24 hours. Within the pool the selection is ordered by zone rank ascending, then expiring rank ascending, then property age descending, and finally by `created_at` ascending; a property's `id` is never consulted as a tie-break, so two candidates identical on every prior key are separated by the order in which their properties were created and nothing else. A poll that would place a third overlapping assignment in the same zone is refused with `ERR_ZONE_DISPATCH_CAPACITY`, and a poll finding no eligible request at all — an empty pool — is refused with `ERR_NO_ELIGIBLE_VENDOR`.

Assignment moves the selected dispatch to `VENDOR_ASSIGNED`, sets its `vendor_ref` from the polled selection, stamps `assigned_at`, and recomputes `defense_in_progress` on the property to true. A producer acknowledges or releases the assignment by supplying the `risk_zone_id` and an optional `vendor_ref`: supplying a reference that matches the property's assigned vendor re-affirms the assignment, while supplying a null reference releases it, clearing `vendor_ref`, resetting `assigned_at` and returning the dispatch to `REQUESTED` so the next poll may select it again. Release is refused with `ERR_ZONE_EVENT_INACTIVE` when the zone's event has dropped below `ACTIVE`, and it is also refused when the zone's `concentration_band` is `CRITICAL`. The same refusal guards the initial request: a defense request raised against a zone whose event is not `ACTIVE` is rejected with `ERR_ZONE_EVENT_INACTIVE` rather than queued.

Two paths carry a dispatch forward without a release. An underwriter advances a dispatch one step at a time: from `VENDOR_ASSIGNED` to `ON_SITE`, and from `ON_SITE` to `COMPLETED`. Completion is not a mere bookkeeping event — it auto-imposes a `DEFENSIBLE_SPACE` requirement with `band_awarded` `CLEARED` and `source` `DEFENSE_FOLLOW_UP`, and if the property was underwritable with no defensible-space mitigation previously cleared, it moves to `MITIGATION_REQUIRED`; if that new requirement is verified as `CLEARED` within 14 days the property returns to `UNDERWRITABLE`. Separately, a dispatch still in `VENDOR_ASSIGNED` is cancelled automatically the moment its zone's event drops below `ACTIVE`; cancellation recomputes `defense_in_progress` to false and, if the property had an `APPROVED` enrollment whose `replacement_provision` was `GUARANTEED`, recomputes that enrollment's `guaranteed_replacement_limit_cents` down to the current dwelling replacement cost. A dispatch in `REQUESTED` is likewise cancelled when the property's enrollment is declined, which is the first hop of the cascade described in §3.9.

### 3.7. Binding, Reserves and Replacement Provisions

Approval is where an enrollment's numbers are fixed. It is available both from `SUBMITTED` and, for a referred enrollment, from `REFERRED` — the latter hop additionally requiring the property's posture to be `REFERRAL_REQUIRED` and its `base_posture` to be `UNDERWRITABLE`. An enrollment that has become `REFERRED` because the property froze or because its base posture left `UNDERWRITABLE` is parked: it may not be approved while the property is frozen, precisely because the referred-to-approved hop demands `REFERRAL_REQUIRED`. The approval computes and snapshots the enrollment's `risk_score` and derives its `risk_tier`, computes `required_dwelling_coverage_cents` as 1.5 times the current replacement cost, computes the premiums and the two limit fields, writes the `replacement_provision` snapshot, and writes the `valuation_fingerprint` recording the property's approved dwelling, contents and scheduled values at that instant.

The score that is snapshotted is a weighted integer computed once from three inputs, in a pinned order. The zone component contributes 0 points for a `STANDARD` band, 240 for `ELEVATED` and 420 for `EXTREME`. The mitigation credit, which is subtracted, is 420 for a `CLEARED` band, 250 for `PARTIAL`, 60 for `FAILED` and 0 for `UNVERIFIED`; the same two numbers also yield an intermediate adjustment — the zone points reduced by the mitigation credit, floored at zero. The agency component adds 0 for a `NORMAL` agency band, 70 for `ELEVATED` and 150 for `CRITICAL`. The base value is 300 plus the zone points plus the agency points minus the mitigation credit, and the published score is that base clamped into the range from 0 to 999 inclusive. The tier is derived from the score in a downward cascade: `REFER` at 700 or above, `SURCHARGE` at 450 or above, `REVIEW` at 200 or above, and `MANAGED` below 200. The underwriting summary of an enrollment breaks the arithmetic out into its parts, exposing `base_score`, `band_points`, `mitigation_credit` and `agency_points` alongside the resulting `risk_score` and `risk_tier`.

Two legitimately different integers come out of that same arithmetic, and both are reachable. The scored variant is the binding one whenever the property holds at least one verified mitigation conferring `CLEARED` or `PARTIAL`, and it subtracts the mitigation credit, so clearing a mitigation lowers the score by exactly the credit delta. The gross, unmitigated variant is a reporting-only view: it treats the mitigation credit as zero while leaving the zone points, agency points and base value unchanged, so it reports a score strictly greater than the scored variant by exactly the credit. That second figure is obtained by asking for the underwriting summary of an enrollment with a `view` of `gross`; the default `view` is the scored one, and neither variant ever overwrites the snapshotted `risk_score` — a read never mutates.

The replacement provision is decided by a threshold evaluation, and the extended branch is tested first. The extended replacement limit is always 1.5 times the current dwelling replacement cost, rounded half up. When the property's `mitigation_band` is `CLEARED`, the provision is `EXTENDED` and the guaranteed limit is the current dwelling replacement cost divided by 1.5 — exactly two thirds of the extended replacement limit. Otherwise, when a defense dispatch is in progress — meaning one exists in `VENDOR_ASSIGNED` or `ON_SITE` — the provision is `GUARANTEED` and the guaranteed limit is unlimited, represented as null. A property that is both design-cleared and under active defense therefore takes `EXTENDED`, never the larger guarantee. In every other case the provision is `NONE` and the guaranteed limit is pinned to the dwelling replacement cost. Because the extended test precedes the guaranteed one, a defense window that opened only after approval is still honoured: the provision is re-evaluated not just at approval but again at attachment.

The premium is tiered on the guarantee ratio rather than on the coverage amount. The ratio is the requested `dwelling_coverage_cents` divided by the current `dwelling_replacement_cost_cents`, rounded half up to four decimal places once, before any rate is applied; the two meaningful step points are 1.2500 and 1.5000. The base rate is 0.0021 times the requested dwelling coverage, rounded half up, and the extended-replacement premium is that base rate multiplied by the ratio and rounded half up. A floor of 12500 cents is then applied to the result of the multiplication — never inside it — and the higher of the two is the `extended_replacement_premium_cents`. The contents premium is 0.0009 times `contents_coverage_cents`, rounded half up, and `gross_premium_cents` is the extended-replacement premium plus that contents premium. The two fields move the other limits as well: `extended_replacement_limit_cents` is the Coverage A limit computed above, and `guaranteed_replacement_limit_cents` follows the provision rules just described.

Attachment is the binding act, and it is gated by five distinct checks whose order is fixed. The property must not be `WRITE_FROZEN` and, separately, the bound zone's `freeze_active` must be false (`ERR_RISK_ZONE_FROZEN`); these are different refusals, because a property can be unfrozen while its zone is frozen. The enrollment's `dwelling_coverage_cents` must be at least its `required_dwelling_coverage_cents` (`ERR_COVERAGE_BELOW_REQUIRED`). The enrollment's `valuation_fingerprint` must still equal the property's current approved dwelling, contents and scheduled values (`ERR_VALUATION_STALE`) — a valuation that moved after approval invalidates the bind. And the request must carry an `expected_property_version` matching the property's current version (`ERR_STALE_VERSION`, §2.8). On success the property's dwelling replacement cost is re-read and `required_dwelling_coverage_cents` recomputed, `stress_reserve_cents` and `committed_reserve_cents` are computed — both are the dwelling plus contents plus scheduled coverage, and the committed figure is zero whenever the enrollment is not yet non-terminal — `bound_at` is stamped, every approved scheduled item of the property transitions to `ATTACHED`, and the property's version is incremented because the attach writes the property's exposure ledger. That version bump is the reason a second attach still carrying the pre-attach version is stale.

Beyond subscribing coverage, an enrollment carries endorsements and can be unwound. An underwriter or producer attaches an endorsement by naming the `endorsement_code` and its `required_provision`; the endorsement is refused with `ERR_INCOMPATIBLE_ENDORSEMENT` when its required provision conflicts with the enrollment's snapshotted `replacement_provision`, and any replacement provision the endorsement would grant is granted at submission time and is therefore void once the enrollment is no longer bound. The result records the `endorsement_id`, the `enrollment_id` it was attached to, and a `void_on_recall` flag carrying that understanding. Recall is the producer-side unwind: it is available only while the enrollment is `APPROVED` and unbound, only to the agency of record, and only when that agency's `concentration_band` is `CRITICAL` and the agency is still active — and it resets `risk_score` to 0, `risk_tier` to `MANAGED`, `replacement_provision` to `NONE`, and clears `valuation_fingerprint`, so a re-approval re-snapshots the score. A referred enrollment may be returned to its producer for rework, which resets the same two score fields to 0 and `MANAGED` while retaining `required_dwelling_coverage_cents`. Withdrawal is available to the agency of record from `DRAFT` or `SUBMITTED` and recomputes `committed_reserve_cents` to 0. Decline is an underwriter act available from `DRAFT`, `SUBMITTED` and `REFERRED`, may carry a `reason`, recomputes `committed_reserve_cents` to 0, and launches the cascade in §3.9.

### 3.8. Claims, Cash Settlement and Specialty Restoration

A claim is reported against a bound policy by naming the `cause_of_loss` — `WILDFIRE`, `WIND`, `HALL`, `WATER`, `THEFT` or `OTHER` — the `loss_date`, the `reported_indemnity_cents` (which must be at least zero), an optional `adjuster_user_id` and an optional `adjuster_override` defaulting to false. The claim is born `REPORTED` with `reported_at` stamped, and all of its monetary fields — `settlement_amount_cents`, `deductible_applied_cents` and `limit_applied_cents` — at 0, with `cash_settlement_eligible` false. Review is the adjuster's first act and it is refused with `ERR_ENROLLMENT_NOT_BOUND` unless the parent enrollment is `ATTACHED`; the rationale is simple, in that an unattached policy has no coverage to draw on. Approval then requires that an adjuster has already been assigned to the claim.

Approval computes the cash settlement, and its evaluation order is fixed: the deductible is derived first, the ceiling second, and the settlement last. The deductible percentage depends on the cause: two percent for `WILDFIRE`; one percent for `WIND` and for `HALL`; and one-half of one percent for `WATER`, `THEFT` and `OTHER`. The raw deductible is that percentage applied to the enrollment's `dwelling_coverage_cents`, rounded half up. The applicable ceiling follows the enrollment's `replacement_provision`: it is unlimited when the provision is `GUARANTEED`, the extended replacement limit when the provision is `EXTENDED`, and the enrollment's `dwelling_coverage_cents` in every other case. A scarcity factor then applies — 1.20 when the adjuster has set `adjuster_override` for a specialty restoration vendor, and 1.0 otherwise. Critically, the reported indemnity is capped by the ceiling before the scarcity factor is applied, because that factor reflects the cost of specialty restoration and is not an extension of the limit; the capped figure is the reported indemnity when the ceiling is unlimited, and otherwise the lesser of the reported indemnity and the ceiling. The `settlement_amount_cents` is the capped figure multiplied by the scarcity factor, rounded half up, and `deductible_applied_cents` is the lesser of the raw deductible and that settlement value. `cash_settlement_eligible` is true exactly when the provision is `GUARANTEED`.

Two admissibility rules guard approval. The reported indemnity must not exceed the applicable replacement-cost limit — the check is skipped when the provision is `GUARANTEED` because that limit is unlimited, and when it fires it is refused with `ERR_COVERAGE_ABOVE_APPRAISAL`, whose condition is that the provision is `EXTENDED` or `NONE`. And the claim must be worth settling at all: a claim whose reported indemnity is at or below the deductible that would be applied is refused with `ERR_CLAIM_BELOW_DEDUCTIBLE`, so the payable line is drawn strictly above the deductible with nothing to settle at or beneath it. Note how the ceiling interacts with the provision: an extended-provision loss above Coverage A is payable up to the extended replacement limit, and only the excess over that limit is refused — whereas under a `NONE` provision the excess over Coverage A itself is refused, because Coverage A is the ceiling.

Settlement is the second act, and it too carries a cascade. It requires an approved claim whose `settlement_amount_cents` is strictly greater than zero; it computes `deductible_applied_cents`; and it transitions every scheduled item of the property that is in `ATTACHED` status back to `APPROVED` with `attached_value_cents` set to 0, after which the property's `scheduled_valuation_cents` and `total_insured_value_cents` are recomputed. This is the detach path of §3.2 reached from the claim side: the scheduled property is released because the loss that justified scheduling it has now been paid, not because anyone asked for a detach. A settled claim may be moved to `PAID`, a claim in `REPORTED` or `UNDER_REVIEW` may be denied with an optional `reason` and reach `DENIED`, and a claim still in `REPORTED` or `UNDER_REVIEW` is rejected automatically if its parent enrollment is declined, in which case its `settlement_amount_cents` is reset to 0.

### 3.9. Non-Renewal, Concentration Review and the Declined-Enrollment Cascade

A non-renewal decision begins as a notice raised against a bound enrollment by an underwriter, naming the `ground` and the `effective_on` date. The `ground` must be one of `CONCENTRATION_REVIEW`, `MITIGATION_FAILURE`, `APPRAISAL_LAPSE` or `NONPAYMENT`. The notice is born `PENDING` and immediately computes two fields: `required_notice_days`, read from the zone's band at issue time — 90 days when the zone band is `CRITICAL`, 60 when it is `ELEVATED`, and 45 otherwise; and `notice_period_days`, the whole days from `issued_on` to `effective_on`, counted exclusively of the issue date and inclusively of the effective date. Both are computed at birth while the notice is still `PENDING` and are re-derived at issuance: the notice period, the seal instant and the 60-day policy-age test are all measured against the date the notice was filed rather than a date re-stamped at issuance, so a notice filed and issued without any clock advance in between measures its window from its filing instant, and the seal instant is that filing date advanced by the required period. A third computed field, `delay_exempt`, is true exactly when the ground is `CONCENTRATION_REVIEW` and the zone band is `CRITICAL`.

Issuance is the regulated step and it clears four tests. The notice period must be strictly longer than the required period — a notice whose effective date falls exactly on the seal instant is insufficient, so equality fails; the seal instant itself is the filing date advanced by the required number of days. The policy must be old enough: the enrollment's `bound_at` must be at least 60 days before that same filing date. The parent enrollment must be `ATTACHED`. And the ground must be actionable against the property's actual state: a `MITIGATION_FAILURE` ground is refused unless the property's `mitigation_band` is `FAILED`, an `APPRAISAL_LAPSE` ground is refused unless no approved appraisal remains current, and a `CONCENTRATION_REVIEW` ground is refused unless the zone band is `CRITICAL` — all three refusals carrying `ERR_GROUND_NOT_ACTIONABLE`. A notice failing the notice-period test or the 60-day age test is refused with `ERR_NOTICE_PERIOD_INSUFFICIENT`, and a notice with a zero-day period is refused as well. When the ground is `CONCENTRATION_REVIEW` and the zone is `CRITICAL`, `delay_exempt` is true and the required-period test is skipped entirely, leaving only the 60-day minimum age to satisfy. Issuance stamps `issued_on`, computes `seal_at` as the filing date advanced by the required number of days, and sets the property's `non_renewal_ground_activated` flag to true when the ground is `CONCENTRATION_REVIEW`.

A `NonRenewalNotice` is resolved either by effect or by rescission. It becomes `EFFECTIVE` automatically once the clock passes `effective_on` — provided it was still `ISSUED` at the moment the clock crossed that date. Effect is not a private matter between the notice and the policy: the parent enrollment, identified by its `enrollment_id`, transitions from `ATTACHED` to `DECLINED`, its `committed_reserve_cents` is recomputed to 0, and the zone's concentration is re-evaluated against the now-smaller book. Rescission is available while the notice is `PENDING` or `ISSUED` and while the clock has not yet passed `effective_on`; it moves the notice to `RESCINDED` and resets the property's `non_renewal_ground_activated` flag to false. A rescission requested after the effective date is refused.

The declined-enrollment cascade is the deepest chain in the system, four hops long, and it is launched by any decline — whether an underwriter declined an enrollment directly from `DRAFT`, `SUBMITTED` or `REFERRED`, or whether a decline was forced by a failed guarantee ratio, an unresolved mitigation lapse, or a non-renewal becoming effective. In the first hop, every defense dispatch of the property that is still in `REQUESTED` transitions to `CANCELLED`, with `vendor_ref` cleared, `assigned_at` reset, and `defense_in_progress` recomputed to false. That cancellation is not locally contained, because a cancelled request returns insured value to the zone's exposure base, which sends the second hop across the whole book: concentration is recomputed for the dispatch's own zone and for every other zone, re-deriving `concentration_ratio_pct`, `concentration_band` and `freeze_active` everywhere, since the portfolio denominator itself has moved. In the third hop, every zone whose freeze flag changed pushes every property bound to it through a posture recomputation, flipping between `WRITE_FROZEN` and `WRITE_ELIGIBLE`. In the fourth and final hop, every property that became `WRITE_FROZEN` pushes its `SUBMITTED` enrollments to `REFERRED`, while every property released to `WRITE_ELIGIBLE` sheds its frozen posture and becomes writable again. A property that is released this way is not re-queued: a `REFERRED` enrollment that was parked by the freeze stays `REFERRED` until an underwriter returns it to draft or approves it. The declined enrollment itself recomputes `committed_reserve_cents` to 0, and any claim of that enrollment that is not yet terminal is rejected with `settlement_amount_cents` reset to 0.

One record class exists purely to document this cascade's human-facing output. A `ManagedRiskEvent` is a managed-risk letter recorded against a dwelling, carrying an `event_type` of `OVERDUE_WARNING` or `REPEAT_INSPECTION_NOTICE`, the `source_requirement_id` of the requirement that stands as its evidence, and a `sent_at` timestamp; its `body_summary` holds the rendered text. Each letter's identity is its `derived_key`, the immutable concatenation of the property, the source requirement and the event type — and that same key never opens a second letter. Two events in this specification produce one: a mitigation requirement that reaches its second verification opens a repeat-inspection notice, and a requirement that lapses on its due date is the event that emits the overdue-warning letter.
