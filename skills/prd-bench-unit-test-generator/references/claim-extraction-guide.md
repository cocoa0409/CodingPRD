## From Table 1 (Entities)

For **each entity**:

| Claim Type | What to extract | Example claim |
|---|---|---|
| Creation | Required input fields, success status | "POST with all required fields → 201 + all fields in response" |
| Retrieval | GET endpoint returns stored data | "GET /{id} returns matching entity" |
| Listing | List endpoint + pagination params | "GET / returns paginated list with total_count and has_more" |
| Not Found | Non-existent ID handling | "GET with non-existent UUID → ERR_X_NOT_FOUND (404)" |
| Required Fields | Each field with `source: input` and no default | "Missing field_x → ERR_INVALID_REQUEST" |
| Defaults | Fields with `default` values | "Omitting field_x → default value applied" |
| Computed Fields | Fields with `source: computed` | "Computed field_x calculated correctly, input value ignored" |
| System Fields | Fields with `source: system` | "id, created_at, updated_at generated by system, input ignored" |
| Type Constraints | Enum fields, numeric ranges | "Invalid enum value → error; start ≥ end → error" |
| Immutability | `common_fields: false` entities | "Immutable entity: no update endpoint, no version field" |
| Parent Relationships | `parent` field | "Entity requires valid parent; wrong parent → NOT_FOUND" |

For **entity topology** (`complexity_profile.entity_topology`):

| Topology | Extra claims to extract |
|---|---|
| `hierarchical` | Child creation requires parent in correct state; nested URL routing works |
| `flat` | Foreign key references validated; cross-reference integrity |
| `graph` | Many-to-many junction entities work; cycle-related constraints (if any) |
| `hybrid` | Cross-cutting associations validated across the hierarchy |

## From Table 2 (State Machines)

For **each state machine**, for **each transition**:

| Claim Type | What to extract |
|---|---|
| Valid Transition | Trigger → entity moves to target state |
| Precondition Enforcement | Each precondition violated → specific error |
| Side Effect Execution | Each side effect in the list is applied |
| Invalid Transitions | From each state, every trigger NOT in the transition list → error |
| Initial State | Newly created entity starts in `initial_state` |
| Terminal State Lockdown | From each `terminal_state`, no transitions are possible |
| Idempotency | Same trigger twice → error on second attempt |

For **state machine shape** (`complexity_profile.state_machine_shape`):

| Shape | Extra claims |
|---|---|
| `linear` | Transitions only go forward; no revert possible |
| `branching` | Fork paths each work; join point requires all branches complete (if applicable) |
| `cyclic` | Entity can loop back; loop count or termination condition respected |
| `parallel` | Independent state dimensions change independently; combined state correct |
| `compound` | Parent state auto-derived from children states; re-derived on child change |
| guarded transitions | Cross-entity preconditions: "A→B only if entity C in state X" |

For **side effect patterns** (inspect each transition's `side_effects`):

| Pattern | Claims to generate |
|---|---|
| Cascade down | Parent change → children change; only non-terminal children affected |
| Bubble up | When all children terminal → parent auto-transitions |
| Cross-entity | Entity A change → entity B adjusts; verify B's state and fields |
| Ledger sync | State change → ancestor's derived field updated; before/after reconcile |
| Compensation | Undo transition → all original side effects reversed; no drift |
| Conditional cascade | Side effect applied only when child is in specific state |

> **PRD-First**: The scaffold may list side effects at higher precision than the PRD. Test only what the PRD specifies — if the PRD is vague where the scaffold is precise, the test must not hard-code the scaffold's specifics.

## From Table 3 (Calculations)

For **each calculation rule**:

| Claim Type | What to extract |
|---|---|
| Correct Result | Known inputs → expected output (compute expected value from formula) |
| Input Set Filtering | Only entities in specified states are included |
| Constants Applied | Threshold/multiplier values from `constants` used correctly |
| Precision | Decimal places and rounding mode honored |

For **each algorithm type**, specific claims:

| Algorithm Type | Boundary / Edge Claims |
|---|---|
| `threshold` | Value at threshold-1, at threshold, at threshold+1; crossing threshold: split calculation |
| `forward_looking` | Includes pending + confirmed; re-evaluated when pending items change |
| `chronological` | Processing order matters; out-of-order creation → still correct chronological result |
| `aggregation` | Running total correct after add; correct after reversal; floor/ceiling honored |
| `tiered_pricing` | Each tier boundary tested; marginal vs average rate; cross-tier straddling |
| `interval_merge` | Overlapping intervals merged; adjacent intervals (gap=0); disjoint preserved |
| `topological` | DAG order respected; cycle detection (if applicable); disconnected components handled |
| `projection` | Event replay produces correct current state; late event handled correctly |
| `weighted_scoring` | Weights sum correctly; rounding accumulation doesn't drift; weight change re-scores |
| `decay_function` | Decay applied at correct intervals; reset events restart the curve |
| `waterfall_allocation` | First bucket fills before second; overflow handled; remainder allocation |
| `constraint_propagation` | Change propagates through chain; reaches fixed point; no infinite loop |

For **dual-variant calculations** (`variants` field):

| Claim Type | What to extract |
|---|---|
| Variant Divergence | Same data, two variants produce different results; test both and verify delta |
| Variant Selection | Correct variant applied in correct context (e.g., provisional at creation, final at confirmation) |
| Reconciliation | When variant switches (provisional → final), delta correctly applied to ledger |

## From Table 4 (Validations)

For **each validation rule**:

| Claim Type | What to extract |
|---|---|
| Violation → Error | Trigger the condition → correct error_id returned |
| Satisfaction → Pass | Condition not triggered → operation succeeds |
| Priority Ordering | Two rules violated → higher priority error returned |

For **validation patterns** (inspect the `category` and interaction between rules):

| Pattern | Claims to generate |
|---|---|
| Priority conflict | Violate rule at priority P and rule at priority P+N → expect P's error |
| Cross-entity validation | Validity depends on state of different entity → test both valid/invalid |
| Temporal validation | Operation valid now but creates future conflict → test detection |
| Aggregate validation | Each individual valid, but collective exceeds limit → test aggregate |
| Conditional validation | Rule applies only when entity has certain config/flag → test with/without |
| Cascading validation | Check A requires result of check B → ensure B runs first |

## From Table 5 (Endpoints)

For **each endpoint**, ensure every `side_effect` listed has a corresponding test. Also extract:

| Endpoint Pattern | Claims |
|---|---|
| Standard CRUD | Create/Read/Update/Delete each work with valid input |
| Action endpoint | State transition triggers correctly; preconditions enforced |
| Bulk action | Partial success/failure semantics; rollback-or-skip behavior |
| Cross-reference link | Both entities must exist; link creates correct association |
| Computed read | Derived data matches expected calculation |
| Conditional action | Action allowed only under specified conditions |

## From Table 6 (Errors)

Verify every error code is triggerable: for each error in the catalog, there must be at least one
test that causes it. Cross-check against your test list — if any error has no test, add one.

## From Table 7 (RBAC)

For **each role**:
- Can perform all `exclusive_operations` and `shared_operations`
- Cannot perform other roles' `exclusive_operations` → `ERR_UNAUTHORIZED`

For **role model patterns** (`complexity_profile.role_model`):

| Role Model | Extra claims |
|---|---|
| `approval_chain` | Each step requires correct role; skip a step → error; role at step N cannot do step N-1 |
| `peer_roles` | Role A cannot touch role B's resources; shared operations work for both |
| `hierarchical_override` | Higher role can do everything lower role can; lower cannot do higher's exclusive ops |
| `delegated_authority` | Delegation grant works; delegated permission expires/revocable; delegatee can act |
| Segregation of duties | Same user cannot do step A and step B (if `X-User-ID` tracked) |

> **PRD-First**: These role model claims apply only if the PRD describes the pattern. The scaffold's `role_model` is designer intent; the PRD's endpoint table is the implementation contract.

## From Cross-Cutting Complexity Layers

> **PRD-First**: Use these layers as a checklist to find PRD claims you might have missed, not as an independent requirements source. If the PRD is silent on a layer, skip it.

Inspect `complexity_profile.complexity_layers` and generate claims for each active layer that the PRD describes:

| Layer | Claims to generate |
|---|---|
| `optimistic_concurrency` | Stale version write → conflict error; correct version → success; version increments on every write. **Does NOT imply race-condition tests** — only generate race tests if the PRD explicitly defines concurrent-operation outcomes (e.g., "only one succeeds", uniqueness constraints on creation). |
| `cascading_side_effects` | N-level chain verified end-to-end; ordering sensitivity tested; partial failure handled |
| `dual_variant_calculation` | Both variants produce expected results; delta on switch is correct |
| `soft_delete` | Soft-deleted entity excluded from lists (default); included when filter specified; references still valid |
| `idempotency` | Same request with same idempotency key → same response; different key → new operation |
| `pagination_with_filtering` | Filter + sort + paginate interact correctly; cursor/offset consistency under mutation |
| `bulk_operations` | All succeed → success; some fail → partial response with per-item status; rollback if transactional |
| `scheduled_actions` | Scheduled action created; cancellable before execution; executes at correct time (if testable) |
| `multi_tenancy` | Tenant A cannot see/modify tenant B's resources; tenant-scoped uniqueness enforced |
| `rate_threshold_triggers` | Cumulative threshold tested at boundary; instantaneous threshold tested at boundary; reset works |
| `derived_field_reconciliation` | Derived field correct after create; correct after update; correct after delete of source |
| `conditional_feature_flags` | Behavior changes when flag toggled; default behavior when flag absent |

## From Consistency Model

| Model | Claims |
|---|---|
| `immediate` | All changes visible in same request's response |
| `eventual` | Denormalized fields may lag; re-read after delay shows correct value |
| `saga` | Multi-step workflow: if step N fails, steps 1..N-1 are compensated/rolled back |
