# Translation Collab API — Product Requirements Document

## 1. Introduction

The Translation Collab platform exists to coordinate large multilingual localization projects across a network of freelance translators, in-house reviewers, and final reviewers, while preserving a defensible audit trail of every state change, quotation, payout, and quality judgement. Project managers operating on behalf of client organizations enter the platform with a stack of source documents and a deadline; they leave it with a published, terminology-consistent, quality-scored deliverable and a payout ledger ready for downstream financial systems. The platform's value proposition lies less in any individual feature than in the way it stitches the workflow together: a forward-looking quotation that anchors price expectations, a translation-memory engine that prevents the same sentence from being paid for twice, a dispatch-and-acceptance protocol that absorbs translator rejections without manual rerouting, and a three-stage review pipeline whose rejections cascade back through parent state to make project readiness a derived rather than declared property.

Two pressures shape the design. The first is fiscal: a quote produced at draft time must be honoured even though the actual translator grades and quality outcomes are not yet known, so the platform separates the forward-looking *quotation* (which assumes a `SENIOR` baseline) from the chronological *final payout* (which reflects who actually did the work and how well). The second is temporal: most failures in translation workflows are timeouts — a translator who never accepts a dispatch, a reviewer who lets a stage deadline slip, a project that drifts past its hard deadline — so the platform binds every dispatch to an explicit accept window and every acceptance to an explicit stage deadline, and exposes a test-driving clock so these timeouts can be exercised deterministically. Around this core, the platform also operates a terminology library that gates publication, a rolling translator-rating engine that feeds back into dispatch selection, and an event fan-out to payment, IM, and storage systems so that publication is observable from outside.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID` identifies the acting principal, and `X-User-Role` declares which role the caller is asserting. If either header is missing or empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are present but the asserted role is not permitted to invoke the targeted endpoint per the role matrix in Section 4, the request is rejected with `ERR_FORBIDDEN` (HTTP 403).

The platform recognises exactly two roles:

- `ProjectManager` — the platform operator who creates clients, manages translators, dispatches assignments, manages terminology, advances the workflow through quote/activate/publish/cancel, and operates the test-driving clock. When `X-User-Role` is `ProjectManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it (for example, as `actor_id` on `AuditEntry` rows that record state transitions performed by a project manager) but does not compare it against any entity's `id`.
- `Translator` — an authenticated freelancer who may act in any of the three pipeline roles (`TRANSLATOR`, `REVIEWER`, `FINAL_REVIEWER`) depending on which `Assignment` covers the segment. When `X-User-Role` is `Translator`, `X-User-ID` is the `id` of the acting `Translator` record; ownership checks on any resource that references a `Translator` compare the resource's foreign-key field (such as `Assignment.translator_id` or `QualityScore.translator_id`) to `X-User-ID`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters: `limit` defaults to 10, must be an integer of at least 1, and may not exceed 100; `offset` defaults to 0 and must be a non-negative integer. Results are returned in `created_at` ascending order unless an endpoint explicitly states otherwise. The `meta` envelope for list responses includes `limit`, `offset`, `total_count` (the total number of rows that match the filter, ignoring pagination), and `has_more` (true when more rows exist beyond the current page).

### 2.4. Common Resource Properties and Resource Identity

Every resource exposes an `id` that is a server-minted UUID, returned as a plain hyphenated UUID string with no entity-type prefix. Mutable resources additionally expose `created_at` (the ISO 8601 UTC timestamp with three fractional digits at which the row was inserted), `updated_at` (the ISO 8601 UTC timestamp of the most recent mutation, equal to `created_at` immediately after insert), and `version` (a non-negative integer that starts at 1 and increases by exactly one each time the row is mutated). The entities that carry this full common field set are `Client`, `Translator`, `Project`, `Document`, `Segment`, `Assignment`, `TerminologyEntry`, and `QualityScore`. The remaining persisted entities — `ProjectTemplate`, `AuditEntry`, and `ExternalSyncRecord` — are immutable append-only rows; they carry only `id` and `created_at`, and both `updated_at` and `version` are absent from their representations.

### 2.5. Optimistic Concurrency Control

The three mutating update endpoints — updating a project profile in `DRAFT`, updating a client, and approving or resolving a terminology entry — accept an optional `version` field in the request body. When the field is supplied, the server checks that its value equals the current `version` of the targeted entity before applying the mutation; a mismatch fails the request with `ERR_VERSION_CONFLICT` (HTTP 409) and no change is persisted. When the field is omitted from the body, the version check is skipped and the mutation proceeds against whatever the current row holds. Every successful mutation increments `version` by exactly one and refreshes `updated_at` to the server clock at commit.

### 2.6. Path Resolution and Nested Resource Retrieval

Path parameters are resolved strictly left to right. A request such as one targeting a document or segment beneath a project must resolve the project identifier before resolving the descendant identifier, and a 404 with `ERR_NOT_FOUND` is returned the first time a path segment fails to resolve. The same rule applies to assignments that act on a segment, terminology mutations against a scope identifier, and quality scores against a segment: the parent must exist before the child is looked up, and reporting the wrong-level identifier as the cause is acceptable as long as the response carries `ERR_NOT_FOUND`.

### 2.7. State Transition Bookkeeping and Cascading Updates

Every state transition produced by a state machine in this document refreshes the `updated_at` of the transitioning entity, increments its `version`, and emits an `AuditEntry` whose `event` is `STATE_TRANSITION`. Cascading transitions — for example, when an `ACCEPTED` translator assignment drives the covered segments from `NEW` to `ASSIGNED`, when a `Project` cancellation forces every non-terminal `Segment` to `REJECTED`, or when a published project refreshes its translators' rolling and latest ratings — are part of the same write: each touched entity has its `version` bumped, its `updated_at` refreshed, and its own `AuditEntry` emitted. The `AuditEntry` rows themselves are never mutated; they carry `subject_type`, `subject_id`, `event`, `from_state`, `to_state`, `actor_role`, `actor_id`, and an event-specific `payload`. When a transition is initiated by the system rather than a human caller — for example, the time-based expiration of a pending assignment, or the bubble-up of a project's compound state — `actor_role` is the literal string `"system"` and `actor_id` may be null.

### 2.8. Monetary Precision, Repetition Percentages, and Rounding

All monetary amounts are stored and returned in integer cents (the fields `base_unit_price_cents`, `quoted_total_cents`, `final_payout_cents`, and `tax_amount_cents`, and the per-segment intermediates used in their derivation). All multipliers — repetition tiers, urgency tiers, translator-grade multipliers, and tax rates — are expressed in basis points: 10000 basis points means 1.00, 12500 means 1.25, 1300 means 13.00%, and the field `tax_rate_bps` on `Client` carries values in this unit. Whenever a calculation in this document divides by 10000, the result is rounded to the nearest integer cent using half-up rounding (a fractional 0.5 always rounds away from zero). When a value's natural precision is fractional rather than integer — `error_density`, `score`, `rolling_quality_score`, and `latest_quality_score` — the value is rounded to two decimal places, again half-up.

Percentages used as gates or thresholds (the repetition-rate gate, the translation-memory leverage thresholds) are evaluated against the exact ratio without intermediate rounding; the threshold check operates on the unrounded ratio. Repetition percentages and translation-memory leverage values that the platform returns on a segment (`tm_leverage_pct` on `Segment`) are integers in the range 0 to 100 inclusive.

### 2.9. Translation-Memory Leverage and Repetition Classification

Every `Segment` carries a `repetition_class` whose value is one of `NEW`, `FUZZY`, `EXACT_REPEAT`, or `TM_LEVERAGE`. The classification is produced when a `Document` is split and is the input to the project's monetary calculations: segments classified as `EXACT_REPEAT` are paid out at a small fraction of the new-segment unit price, segments classified as `TM_LEVERAGE` somewhat more, segments classified as `FUZZY` more again, and segments classified as `NEW` at the full unit price. The classification is per-project: segments in archived documents are excluded from the candidate pool, and the earliest-ordinal segment for a given normalized source string within a project always retains the `NEW` classification — only its later siblings can match against it.

### 2.10. Stage Time Limits and Acceptance Window

Two clock-bound deadlines govern translator workflow. When an `Assignment` is dispatched, `accept_deadline_at` is set to `dispatched_at` plus a fixed acceptance window of 48 hours. When the translator accepts, `stage_deadline_at` is set to `accepted_at` plus a role-specific stage limit: 72 hours for `TRANSLATOR`, 48 hours for `REVIEWER`, and 24 hours for `FINAL_REVIEWER`. Crossing `accept_deadline_at` while the assignment is still `PENDING` causes it to expire and a successor to be spawned to a different translator. Crossing `stage_deadline_at` while the assignment is `ACCEPTED` does not by itself terminate the assignment, but it makes the assignment reassign-eligible: a project manager can then force a reassignment that regresses the covered segments and dispatches the work to a new translator. Time-based effects do not advance on their own — the platform clock advances only via the test-driving `/_clock/advance` endpoint described in Section 4. After any clock advance, the system re-evaluates time-gated state machines automatically, but a project manager may also explicitly invoke `/_sweep/run` to force the same re-evaluation idempotently.

### 2.11. Workload, Eligibility, and Translator Selection

The platform caps each translator's open workload at 200 open segments — that is, `Translator.workload_segments_open` plus the size of any new package must not exceed 200, and any dispatch or acceptance that would breach the cap is rejected with `ERR_TRANSLATOR_OVERLOADED`. `workload_segments_open` is recomputed on every assignment acceptance, rejection, and segment terminal transition; for a given translator it equals the count of segments currently held by that translator in non-terminal segment states. A translator is eligible for dispatch only when `test_translation_passed` is true, when `availability_status` is `AVAILABLE`, when the project's `source_lang`/`target_lang` pair exactly appears in the translator's `language_pairs`, and when the project's `domain` is one of the translator's `domains`. Whenever a successor assignment must be spawned (because the previous translator rejected, let the assignment expire, or was reassigned), the platform ranks all eligible translators by descending `rolling_quality_score`, then ascending `workload_segments_open`, then ascending `id` lexicographically, and dispatches to the top of the ranked list. The translator whose action triggered the successor (the rejecter, the expirer, or the reassigned-out translator) is excluded from the candidate pool for that successor. When no eligible translator remains, the successor is not created and the caller receives `ERR_NO_ELIGIBLE_TRANSLATOR`.

### 2.12. Compound State and Parent-Child State Propagation

Project state is a compound function of its segments. When every segment of a project has reached one of `TRANSLATED`, `REVIEWED`, or `FINAL_APPROVED`, the project transitions automatically from `ACTIVE` to `ALL_TRANSLATED`. When every segment has reached one of `REVIEWED` or `FINAL_APPROVED`, the project transitions automatically from `ALL_TRANSLATED` to `ALL_REVIEWED`. The reverse holds: if a reviewer rejects a segment back to `NEW` while the project sits in `ALL_TRANSLATED`, the project demotes back to `ACTIVE`; if a final reviewer rejects a segment back to `TRANSLATED` while the project sits in `ALL_REVIEWED`, the project demotes back to `ALL_TRANSLATED`. The publishing transition from `ALL_REVIEWED` to `PUBLISHED` is explicit and requires every segment to be in `FINAL_APPROVED` at the instant of publish. Whenever a child transition causes a parent transition, both transitions are part of the same write — both entities have their `version` incremented and their `updated_at` refreshed, and both emit a separate `AuditEntry`.

### 2.13. Concurrency Serialization

Race conditions on a single entity are resolved by first-writer-wins on the contested attribute. Two translators attempting to accept the same `PENDING` assignment simultaneously serialize on the assignment's state transition: exactly one acceptance succeeds and the loser receives `ERR_ASSIGNMENT_ALREADY_TAKEN`. A reviewer's submission and a final reviewer's rejection landing on the same segment serialize on the segment's state: exactly one persists, and the loser receives `ERR_INVALID_SEGMENT_STATE`. A project publish and a final reviewer's segment rejection on the same project serialize on the project's state: if the rejection persists first, publish receives `ERR_PROJECT_NOT_READY`; if the publish persists first, the segment rejection receives `ERR_INVALID_SEGMENT_STATE`. Two simultaneous `finalize` calls on the same quality score serialize on the score's state: exactly one quality score finalizes, and the loser receives `ERR_QUALITY_SCORE_ALREADY_FINALIZED`. The terminology conflict case is different: when two `TerminologyEntry` rows are proposed in the same scope with identical `source_term` but different `target_term` within the same instant, both rows persist but both are marked `CONFLICT`, and the error identifier `ERR_TERMINOLOGY_CONFLICT` is the publish-time gate that surfaces this condition.

### 2.14. Validation Ordering

For any mutating request, validation runs in a fixed priority order so that the error returned is always the highest-priority failing condition. The order is: authentication (`ERR_UNAUTHENTICATED`) first; authorization (`ERR_FORBIDDEN`) second; path existence (`ERR_NOT_FOUND`) third; general state legality (`ERR_INVALID_STATE`) fourth; the segment-specific state check (`ERR_INVALID_SEGMENT_STATE`) fifth; the assignment-specific state check (`ERR_INVALID_ASSIGNMENT_STATE`) sixth; the test-translation gate (`ERR_TEST_TRANSLATION_REQUIRED`) seventh; the translator profile match (`ERR_TRANSLATOR_PROFILE_MISMATCH`) eighth; the acceptance-window check (`ERR_ACCEPT_WINDOW_EXPIRED`) ninth; the segment-not-already-assigned check (`ERR_SEGMENT_ALREADY_ASSIGNED`) tenth; the package-size cap (`ERR_PACKAGE_SIZE_EXCEEDED`) eleventh; the workload cap (`ERR_TRANSLATOR_OVERLOADED`) twelfth; the publish-time terminology gate (`ERR_TERMINOLOGY_CONFLICT`) thirteenth; the repetition-price gate (`ERR_REPETITION_PRICE_TOO_LOW`) fourteenth; the minimum unit price check (`ERR_INVALID_PRICE`) fifteenth; the deadline-in-future check (`ERR_DEADLINE_NOT_IN_FUTURE`) sixteenth; the same-source-target check (`ERR_SAME_SOURCE_TARGET`) seventeenth; the empty-project gate (`ERR_EMPTY_PROJECT`) eighteenth; optimistic concurrency (`ERR_VERSION_CONFLICT`) nineteenth; and generic request body schema validation (`ERR_VALIDATION_FAILED`) last. A request that simultaneously violates several conditions reports the lowest priority number — for example, a publish request whose role is unauthorised and whose project still has terminology conflicts reports `ERR_FORBIDDEN`, not `ERR_TERMINOLOGY_CONFLICT`.

## 3. Business Logic & Workflows

### 3.1. Onboarding Clients and Translators

A `ProjectManager` opens a project lifecycle by first registering the customer that will pay for it. Creating a client captures the client's legal `name`, a contact email used for downstream notifications (`contact_email`, validated for RFC 5322 syntactic form), the tax rate that will be applied to every payable line item the platform produces for the client (`tax_rate_bps`, an integer in basis points between 0 and 3000 inclusive), and the deferral window that turns a published payout into a payable one (`payment_cycle_days`, restricted to the set 0, 7, 15, 30, and 45). A newly created client's `status` defaults to `ACTIVE`; the terminal value `ARCHIVED` is reserved for filtering and is set out-of-band.

Registering a translator captures the translator's public `display_name`, the set of source/target language pairs the translator is qualified on (`language_pairs`, each entry an object with `source_lang` and `target_lang` ISO 639-1 codes, with the two codes required to differ within any single pair), the subject domains the translator works in (`domains`, drawn from `LEGAL`, `MEDICAL`, `TECH`, `MARKETING`, `MEDIA`, `FINANCE`, and `GENERAL`), and the translator's tier (`grade`, defaulting to `JUNIOR` and one of `JUNIOR`, `INTERMEDIATE`, `SENIOR`, `EXPERT`). Two computed reputational fields are initialised at 100.00 — `rolling_quality_score` and `latest_quality_score` — and updated whenever a quality score is finalized. The translator's `availability_status` (one of `AVAILABLE`, `BUSY`, `OFFLINE`, `SUSPENDED`) defaults to `AVAILABLE`, the open-workload counter `workload_segments_open` defaults to 0, and the test-translation gate `test_translation_passed` defaults to false. A separate operation by the project manager clears the test gate by setting `test_translation_passed` to true; a translator whose gate has not been cleared can still be the target of a dispatch, but cannot accept it.

### 3.2. Project Creation, Drafting, and the Quotation Round

When a project manager creates a project, they supply the owning `client_id`, a project `name`, the source and target language codes, the `domain`, the deadline beyond which the project must reach `PUBLISHED` (`deadline_at`), the pricing mode (`unit_pricing_mode`, one of `PER_WORD`, `PER_SEGMENT`, or `PER_FILE`), the unit price in integer cents (`base_unit_price_cents`, at least 1), an optional package size (`package_size_segments`, defaulting to 50, in the range 1 to 500), and an optional `template_id` referencing a `ProjectTemplate`. Where a template is supplied, the platform seeds `domain`, `unit_pricing_mode`, `base_unit_price_cents`, and `package_size_segments` from the template's matching defaults (`default_domain`, `default_unit_pricing_mode`, `default_base_unit_price_cents`, `default_package_size_segments`), but any explicit field on the request body overrides the template default. The platform refuses the creation with `ERR_DEADLINE_NOT_IN_FUTURE` when `deadline_at` is not strictly later than the current server time at creation, with `ERR_SAME_SOURCE_TARGET` when `source_lang` and `target_lang` are equal, with `ERR_INVALID_PRICE` when `base_unit_price_cents` is less than 1, and with `ERR_VALIDATION_FAILED` for any other body-schema or enum violation. Updates to a project in `DRAFT` are confined to `name`, `deadline_at`, `base_unit_price_cents`, and `package_size_segments`; the same field-level checks apply on update, and an OCC `version` may be supplied to guard against concurrent edits. On creation the project's `state` is `DRAFT`, the project's `word_count` is 0, and `quoted_total_cents`, `final_payout_cents`, `tax_amount_cents`, `payable_at`, and `urgency_tier` are unset; `urgency_tier` will be computed when the project is quoted and defaults to `STANDARD` if the field is read before the quote runs.

Source material enters the project as one or more documents. Uploading a document captures the original `filename`, the parsed `file_format` (one of `DOCX`, `PDF`, `PPTX`, `XLSX`, `SRT`), the segmentation rule that will be applied at split time (`split_mode`, either `SENTENCE` or `PARAGRAPH`), and the raw extracted text (`raw_text`). A newly uploaded document is in state `UPLOADED`; its segments are not materialised until the manager invokes the split operation. Splitting the document — permitted only while the parent project is in `DRAFT` — parses the raw text according to `split_mode`, creates one `Segment` per parsed unit with the original ordering recorded in `ordinal` (1-based and unique within `document_id`), captures the per-segment `source_text` and computes its `word_count` (which must be at least 1), and writes the denormalized `project_id` onto each segment for query convenience. The document transitions to `SPLIT`, and a project manager may archive a document — transitioning it to `ARCHIVED` — only while the parent project is in `DRAFT` or `CANCELLED`; archiving sets every child segment to `REJECTED` and recomputes both `Document.word_count` and `Project.word_count`.

Immediately after segments are created during a split, the platform runs repetition detection across the project's segment pool to decide each new segment's `repetition_class` and `tm_leverage_pct`. The candidate pool consists of every segment under the same project whose parent document is not `ARCHIVED`, including segments produced in earlier splits. For each newly created segment, the platform normalizes its source text by lowercasing and stripping punctuation, counts the pre-existing segments in the pool whose normalized source text exactly equals the new segment's normalized source text, and computes the highest fuzzy-similarity percentage between the new segment and any pre-existing segment in the pool (as an integer from 0 to 100). When the exact-match count is at least 1 and the fuzzy-match percentage is exactly 100, the segment is classified as `EXACT_REPEAT` with `tm_leverage_pct` set to 100. Otherwise, when the fuzzy percentage is at least 95, the segment is classified as `TM_LEVERAGE` with `tm_leverage_pct` equal to that percentage. Otherwise, when the fuzzy percentage is at least 75, the segment is classified as `FUZZY` with `tm_leverage_pct` equal to that percentage. Otherwise the segment is classified as `NEW` and `tm_leverage_pct` is 0. Segments are processed in ascending order of the pair (`document_id`, `ordinal`), so the earliest-indexed segment within the project for any given normalized text remains `NEW` and every subsequent match classifies against it; if two candidate matches achieve identical fuzzy percentages, the earlier (`document_id`, `ordinal`) wins.

When the project manager judges the source material complete, they request a quote, which is the gateway transition from `DRAFT` to `QUOTED`. The quote runs only when every document under the project is in `SPLIT` and the project's `word_count` is strictly greater than zero (otherwise `ERR_EMPTY_PROJECT`). Two computations fire as side effects of this transition. The first computes the project's `urgency_tier` from the hours remaining until the project's `deadline_at` measured against the platform clock at the moment of transition: when the remaining hours are strictly less than 48, the tier is `CRITICAL`; otherwise when the remaining hours are strictly less than 168, the tier is `RUSH`; otherwise the tier is `STANDARD`. The boundary is strict: a remaining-hours value of exactly 48 lands in `RUSH`, and a value of exactly 168 lands in `STANDARD`. The second computation produces `quoted_total_cents` by walking every segment under the project whose parent document is in `SPLIT`, in ascending (`document_id`, `ordinal`) order, and computing a per-segment contribution under the assumption that the eventual translator will be a `SENIOR`. For each segment, the unit quantity depends on `unit_pricing_mode`: under `PER_WORD` it is the segment's `word_count`; under `PER_SEGMENT` it is 1; under `PER_FILE` it is 1 only for the segment whose `ordinal` is 1 within its document and 0 otherwise. A repetition multiplier in basis points is selected from the segment's `repetition_class` (`NEW` is 10000, `FUZZY` is 6000, `TM_LEVERAGE` is 3000, `EXACT_REPEAT` is 1500). The base in cents is the product of `base_unit_price_cents` and the unit quantity; this is multiplied by the repetition multiplier and divided by 10000, rounded half-up to integer cents; the result is multiplied by the forward-looking grade multiplier of 10000 (the `SENIOR` assumption) and divided by 10000, rounded half-up to integer cents; the rounded per-segment contributions are summed to a subtotal; finally the subtotal is multiplied by the urgency multiplier (`STANDARD` is 10000, `RUSH` is 12500, `CRITICAL` is 15000) and divided by 10000, with one final half-up rounding to integer cents to produce `quoted_total_cents`. The rounding order is fixed: each per-segment contribution is rounded before the summation, the subtotal is summed without further rounding, and the urgency multiplication produces the only post-sum rounding.

The quotation gate also enforces a repetition-price guard. The project's repetition rate is the sum of `word_count` over segments classified `EXACT_REPEAT` divided by the project's `word_count`. When that ratio reaches or exceeds 75 percent (the boundary is inclusive: exactly 75.00 percent triggers the gate, 74.99 percent does not), the project's `base_unit_price_cents` must be at least the platform's minimum high-repetition price, otherwise the creation or update is rejected with `ERR_REPETITION_PRICE_TOO_LOW`. The same gate runs on project creation and project update, so an attempt to lower the unit price below the floor after a heavily repeated body of text has been split also fails fast.

### 3.3. Dispatching, Accepting, and Reassigning Translation Work

Once the project is in `QUOTED`, the project manager dispatches assignments. Each dispatch nominates one translator (`translator_id`), the pipeline role for the assignment (`role`, one of `TRANSLATOR`, `REVIEWER`, or `FINAL_REVIEWER`), and the segment package (`segment_ids`, an ordered, non-empty list of segments whose count must not exceed the project's `package_size_segments`). The platform checks that all listed segment ids belong to the project, that they are in the appropriate pre-state for the dispatched role, and that none is already covered by another non-terminal assignment for the same role; any violation surfaces as `ERR_SEGMENT_ALREADY_ASSIGNED`. The translator's profile is checked: the project's `source_lang` and `target_lang` pair must be present in the translator's `language_pairs` and the project's `domain` must be in the translator's `domains`, otherwise `ERR_TRANSLATOR_PROFILE_MISMATCH`. The workload cap also runs at dispatch — if accepting this package would push the translator over 200 open segments, `ERR_TRANSLATOR_OVERLOADED` is returned. On success the assignment is created in state `PENDING`, `dispatched_at` is set to the server clock, and `accept_deadline_at` is set to `dispatched_at` plus the 48-hour acceptance window; `stage_deadline_at` and `accepted_at` remain null until acceptance. The platform emits an `ExternalSyncRecord` whose `target_system` is `IM` and whose `trigger_event` is `ASSIGNMENT_DISPATCHED`. After at least one translator assignment exists for the project, the project manager can move the project from `QUOTED` to `ACTIVE`; this transition requires `quoted_total_cents` to be set and at least one `TRANSLATOR` assignment to exist, and it locks `unit_pricing_mode` and `base_unit_price_cents` against further modification.

A translator accepts a pending assignment they hold; the acceptance is rejected with `ERR_INVALID_ASSIGNMENT_STATE` if the assignment is not in `PENDING`, with `ERR_ACCEPT_WINDOW_EXPIRED` if the platform clock has reached or passed `accept_deadline_at`, with `ERR_TEST_TRANSLATION_REQUIRED` if `test_translation_passed` is still false, with `ERR_TRANSLATOR_PROFILE_MISMATCH` if the translator's profile no longer covers the project's language pair and domain (this check repeats at acceptance because the translator's profile may have changed between dispatch and acceptance), and with `ERR_TRANSLATOR_OVERLOADED` if accepting would push their open workload above the cap. The translator's `availability_status` must be one of `AVAILABLE` or `BUSY` for acceptance to succeed. On success the assignment transitions to `ACCEPTED`, `accepted_at` is set to the server clock, and `stage_deadline_at` is set to `accepted_at` plus the role's stage limit — 72 hours for `TRANSLATOR`, 48 hours for `REVIEWER`, and 24 hours for `FINAL_REVIEWER`. When the accepting role is `TRANSLATOR`, every covered segment whose state is `NEW` advances to `ASSIGNED` and the segment's `assignment_id` is set to the accepted assignment's id; the translator's `workload_segments_open` is recomputed.

A translator may also decline a pending assignment they hold (supplying a `reason`); declining is rejected by the same state and window checks. On decline, the assignment terminates as `REJECTED`, the covered segments remain in `NEW`, the platform emits an `ExternalSyncRecord` whose `target_system` is `IM` and whose `trigger_event` is `ASSIGNMENT_REJECTED`, and a successor assignment is immediately spawned to a different translator selected by the ranking described in §2.11; the rejecting translator is excluded from the candidate pool. If the candidate pool is empty, the successor is not created and the platform reports `ERR_NO_ELIGIBLE_TRANSLATOR`. The same successor-spawning logic fires automatically when the platform clock crosses `accept_deadline_at` while the assignment is still `PENDING`: the assignment transitions to `EXPIRED`, an `IM` `ExternalSyncRecord` with trigger `ASSIGNMENT_REJECTED` is emitted, and a successor is dispatched.

After acceptance, if a translator stalls past their `stage_deadline_at`, the project manager may force a reassignment by invoking the reassign action with a `reason`. Reassignment is allowed only when the assignment is in `ACCEPTED` and either the platform clock has passed `stage_deadline_at` or the project manager has supplied the reason value `'STALE'`. The assignment terminates as `REASSIGNED`, and for `TRANSLATOR`-role reassignments every covered segment is regressed back to `NEW` and its `assignment_id` is cleared. A successor assignment is then dispatched to a new translator by the same ranking, and an `ExternalSyncRecord` is emitted with `target_system` `IM` and `trigger_event` `STAGE_DEADLINE_BREACHED`. While time-gated state changes never advance on their own, the project manager has two test-driving capabilities — advancing the platform clock by a supplied `seconds` value and running an idempotent sweep that re-evaluates time-gated state machines — that drive pending-assignment expirations into the regime described above. The system also recomputes any assignment that has just satisfied its terminal precondition: when an `ACCEPTED` translator assignment's every covered segment has reached `TRANSLATED`, `REVIEWED`, or `FINAL_APPROVED` (depending on the assignment's `role`), the assignment transitions automatically to `COMPLETED`.

### 3.4. The Three-Stage Translation Pipeline

The translator who has accepted a `TRANSLATOR`-role assignment submits the translation of each covered segment by supplying `translated_text` (which must be non-empty); the segment transitions from `ASSIGNED` to `TRANSLATED`, the terminology-consistency check fires (creating `TerminologyEntry` rows in the `CONFLICT` state whenever the new submission's terms collide with existing approved or proposed terms in the project or client scope), the translator's `workload_segments_open` is recomputed, and the project re-evaluates its compound state for the `ACTIVE` to `ALL_TRANSLATED` transition described in §2.12. The submitter must be the assignee of the current `Assignment` with role `TRANSLATOR` covering the segment; any other caller is refused with `ERR_INVALID_SEGMENT_STATE` (because the segment is held by a different translator) or `ERR_FORBIDDEN` (because the role check fails first). A segment whose state is not `ASSIGNED` cannot be translated; that case yields `ERR_INVALID_SEGMENT_STATE`.

The translator who holds the `REVIEWER`-role assignment covering the segment submits review by supplying the revised text (`reviewed_text`, non-empty); the segment transitions from `TRANSLATED` to `REVIEWED` and the project re-evaluates `ALL_TRANSLATED` to `ALL_REVIEWED`. The translator who holds the `FINAL_REVIEWER`-role assignment performs final approval; the segment transitions from `REVIEWED` to `FINAL_APPROVED`, but only after every project-scoped `TerminologyEntry` that was marked `CONFLICT` has been resolved (otherwise the operation is refused by the segment state machine).

The pipeline cycles via two distinct rejection paths. A reviewer may reject a `TRANSLATED` segment by supplying a `reason`; the segment regresses to `NEW`, its `assignment_id` is cleared, the original translator's `workload_segments_open` is recomputed, and the project's compound state bubbles back down — if the project was in `ALL_TRANSLATED` it regresses to `ACTIVE`. A final reviewer may reject a `REVIEWED` segment by supplying a `reason` and, optionally, an `errors` array describing the defects spotted; the segment regresses to `TRANSLATED`, the project bubbles from `ALL_REVIEWED` back to `ALL_TRANSLATED` if it had been there, and when the rejection body includes `errors` the platform creates a `DRAFT` `QualityScore` recording those errors for the segment. Each `errors` element has a `category` drawn from `MISTRANSLATION`, `OMISSION`, `GRAMMAR`, `STYLE`, and `TERMINOLOGY`, a `severity` drawn from `MINOR`, `MAJOR`, and `CRITICAL`, and a positive integer `count`. The two rejection paths are sibling transitions out of the segment state machine and share the same `reason` requirement; the divergence is the destination state, the cascade target (clearing `assignment_id` for the reviewer-rejection branch, leaving it intact for the final-reviewer-rejection branch), and the side effect of optionally creating a quality-score draft on the final-reviewer-rejection branch.

### 3.5. Terminology Library Lifecycle

A terminology entry binds a `source_term` in a `source_lang` to a `target_term` in a `target_lang`, scoped either to a project or to a client. Creating an entry supplies `scope_type` (`PROJECT` or `CLIENT`), `scope_id` (the project or client identifier), the two language codes, the source term, and the target term; the entry is created in `PROPOSED`. The platform runs a conflict detector against existing entries in the same scope: when another entry with identical `scope_type`, `scope_id`, `source_lang`, `target_lang`, and `source_term` but a different `target_term` is already in `PROPOSED` or `APPROVED`, both rows transition to `CONFLICT` and an audit event is emitted. A project manager approves an entry only when no existing `APPROVED` row covers the same scope and term tuple; on approval the platform re-runs the terminology consistency check across the project's segments. Resolution of a conflict requires the body to include `loser_id` (the identifier of the other `CONFLICT` row to be archived); the platform archives the loser, transitions the winning entry to `APPROVED`, and re-runs the consistency check. A request to resolve that omits or mis-identifies the loser is refused with `ERR_TERMINOLOGY_RESOLVE_REQUIRES_LOSER`. Deleting an entry archives it; the operation is unconditional from `PROPOSED` but requires the parent project not to be `PUBLISHED` for entries in `APPROVED`. Publish itself enforces that no project-scoped entry remains in `CONFLICT` — if any does, the publish call fails with `ERR_TERMINOLOGY_CONFLICT`, and the same identifier is also the cause when two simultaneous proposals create the conflict in the first place.

### 3.6. Quality Scoring and Translator Rating

A `QualityScore` is created either explicitly by a translator or project manager submitting `segment_id` and an `errors` array, or implicitly as a `DRAFT` produced by a final reviewer's segment rejection that carried an `errors` array. The score's `translator_id` is denormalized at creation: it is the translator credited with submitting the `translated_text` on the underlying segment (the assignee of the most recently `COMPLETED` `TRANSLATOR`-role assignment that covered the segment in its terminal lineage). Finalization is a separate operation invoked by a `Translator` (specifically the final reviewer holding the relevant assignment, asserting the score's correctness) and requires the underlying segment to be in `FINAL_APPROVED`; the body must carry a non-empty `errors` array or the platform's zero-error flag is set explicitly. Two simultaneous finalize calls on the same quality score serialize on the score's `state`, with the loser receiving `ERR_QUALITY_SCORE_ALREADY_FINALIZED`. A project manager may instead void a `DRAFT` score, transitioning it to the terminal `VOIDED` state without affecting translator ratings.

Finalization fires three calculations in fixed order. The first computes `error_density`: every error element contributes its severity weight (`MINOR` is 1, `MAJOR` is 3, `CRITICAL` is 9) multiplied by its `count`, the contributions are summed to give the weighted error count, that total is multiplied by 1000 and divided by the segment's `word_count` (with a floor of 1 to avoid division by zero), and the result is rounded half-up to two decimal places. The second computes `score`: the platform subtracts the product of `error_density` and the penalty rate of 2.5 from 100, clamps the result into the closed interval from 0 to 100, and rounds half-up to two decimal places. A score of at least 90 is the platform's pass bar; scores strictly below 90 contribute to the project's quality deduction at publish time. The third refreshes the credited translator's reputational fields. `rolling_quality_score` is the arithmetic mean of every finalized quality score for the translator whose finalization timestamp lies within the last 90 days, rounded half-up to two decimal places; when the 90-day window contains no finalized scores, the value resets to 100.00. `latest_quality_score` is the score value of the single most recent finalized quality score for the translator (most recent by finalization timestamp, with the lexicographically smallest `id` as a deterministic tie-break for identical timestamps); when no finalized score exists for the translator, the value is 100.00. The two reputational fields share triggers — finalization of any score, and project publish — but their aggregation semantics differ: the rolling field averages across a window, the latest field snapshots one row, and they can disagree whenever the 90-day window holds two or more disagreeing scores.

### 3.7. Publishing, Payout, and Outbound Synchronization

Publishing is the project manager's final action and the chronological counterpart to the forward-looking quote. The publish call is permitted only when the project is in `ALL_REVIEWED`, every segment is `FINAL_APPROVED`, and every project-scoped `TerminologyEntry` is in `APPROVED` or `ARCHIVED` with none in `CONFLICT`; failures on these gates surface as `ERR_PROJECT_NOT_READY` (segments not all final) or `ERR_TERMINOLOGY_CONFLICT` (terminology not resolved). A publish call against a project whose word count is zero is rejected with `ERR_EMPTY_PROJECT` — the same gate that protects quotation also protects publish. On success the project transitions from `ALL_REVIEWED` to `PUBLISHED` and four computations fire.

The first is the chronological `final_payout`. It walks every `FINAL_APPROVED` segment in ascending (`document_id`, `ordinal`) order. For each segment the unit quantity is decided exactly as in the quote (the project's `unit_pricing_mode` selects between `word_count`, 1, or 1-iff-ordinal-1); the repetition multiplier in basis points is the same map (`NEW` is 10000, `FUZZY` is 6000, `TM_LEVERAGE` is 3000, `EXACT_REPEAT` is 1500); but the grade multiplier is now the actual translator's `grade`-keyed multiplier (`JUNIOR` is 8000, `INTERMEDIATE` is 10000, `SENIOR` is 12000, `EXPERT` is 14000) rather than the quote's flat `SENIOR` assumption. The base in cents is `base_unit_price_cents` times unit quantity; that base is multiplied by the repetition multiplier and divided by 10000, rounded half-up to integer cents; the rounded result is multiplied by the grade multiplier and divided by 10000, rounded half-up to integer cents. The per-segment rounded contributions are summed without further rounding to a subtotal, the subtotal is multiplied by the urgency multiplier matching the project's `urgency_tier` (`STANDARD` is 10000, `RUSH` is 12500, `CRITICAL` is 15000) and divided by 10000, with one half-up rounding to integer cents to produce the urgency-adjusted cents.

The second computation is the quality deduction, which is then subtracted from the urgency-adjusted cents. For every finalized quality score attached to a `FINAL_APPROVED` segment in the project, the platform computes the deduction percentage in basis points as the larger of zero and the product of the quality-bar deficit (90 minus the score) and the deduction rate of 50 basis points per point — so a score of 90 or above contributes nothing, a score of 80 contributes 500 basis points (5 percent), and a score of 50 contributes 2000 basis points (20 percent). The deduction applies to the segment's `graded_cents` from the final payout (the per-segment value after grade multiplication but before the urgency multiplication): the per-segment deduction in cents is `graded_cents` times the deduction-percentage basis points divided by 10000, rounded half-up. The per-segment deductions are summed to the total quality deduction in cents. A `FINAL_APPROVED` segment that has no finalized quality score contributes zero deduction. The project's `final_payout_cents` is the larger of zero and the urgency-adjusted cents minus the total quality deduction; the rounding order is fixed (per-segment first, then sum, then urgency, then quality-deduction subtraction).

The third computation is `tax_amount_cents`: the product of `final_payout_cents` and the client's `tax_rate_bps` divided by 10000, rounded half-up to integer cents. The fourth computes `payable_at` as the publish moment plus the client's `payment_cycle_days` measured in days of 24 hours each, and is the timestamp at which the payout is considered payable downstream.

Three downstream synchronizations follow. The platform creates three `ExternalSyncRecord` rows, one for each of `PAYMENT`, `STORAGE`, and `IM`, each with `trigger_event` `PROJECT_PUBLISHED` and a `payload` containing the published project's identifying and monetary fields. For every translator who acted as a `TRANSLATOR` on a `COMPLETED` assignment in the project, both `rolling_quality_score` and `latest_quality_score` are refreshed using the same rules described in §3.6. The publish operation, like every state transition, also writes an `AuditEntry` carrying `subject_type` of `Project`, the project's `subject_id`, the `event` `STATE_TRANSITION`, `from_state` `ALL_REVIEWED`, `to_state` `PUBLISHED`, and the operator's `actor_role` and `actor_id`.

### 3.8. Cancellation and Reversal Paths

A project manager may cancel a project at any time while it is in `DRAFT` or `ACTIVE`. In either case cancellation is permitted only when no assignment under the project is in state `ACCEPTED`; an `ACCEPTED` assignment must first be reassigned or allowed to complete. On cancellation from `DRAFT`, every segment is set to `REJECTED` and every assignment in state `PENDING` is set to `REJECTED`. On cancellation from `ACTIVE`, every non-terminal segment is set to `REJECTED`. Cancellation terminates the project at `CANCELLED`; no payout calculation runs and no `ExternalSyncRecord` rows are produced. Audit entries for the cancellation and every cascaded segment and assignment transition are emitted as usual.

### 3.9. Audit Trail and External Synchronization Records

Every state transition produces an `AuditEntry` whose `subject_type` is the entity that transitioned (one of `Segment`, `Assignment`, `Project`, or `QualityScore`), whose `subject_id` is that entity's `id`, whose `event` is `STATE_TRANSITION`, and whose `from_state` and `to_state` carry the pre- and post-transition states. Quality score finalizations additionally produce an `AuditEntry` with `event` `QUALITY_SCORED`, assignment expirations and rejections that spawn a successor produce an entry with `event` `REASSIGNED`, and every emission of an `ExternalSyncRecord` produces a companion `AuditEntry` with `event` `EXTERNAL_SYNC`. The `payload` captures event-specific structured data — for a `QUALITY_SCORED` event, the finalized score and per-category error counts; for a `REASSIGNED` event, the predecessor assignment id and the successor's translator; for an `EXTERNAL_SYNC` event, the target system and the trigger that produced the sync. `ExternalSyncRecord` rows are immutable fan-out markers carrying `project_id`, the downstream `target_system` (`PAYMENT`, `IM`, or `STORAGE`), the `trigger_event` (`PROJECT_PUBLISHED`, `PAYMENT_PAYABLE`, `ASSIGNMENT_DISPATCHED`, `ASSIGNMENT_REJECTED`, or `STAGE_DEADLINE_BREACHED`), and the `payload` pushed to the downstream system at sync time. Both audit and sync rows are queryable via list endpoints filtered by `subject_type`, `subject_id`, `project_id`, and `target_system` as appropriate.
