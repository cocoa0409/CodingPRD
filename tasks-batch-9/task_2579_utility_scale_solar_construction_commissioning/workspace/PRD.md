# Utility-Scale Solar EPC API — Product Requirements Document

## 1. Introduction

A utility-scale photovoltaic plant is not built as one project but as a dozen interlocking ones. Civil crews strip and grade acreage under a stormwater construction general permit that can be suspended without warning; procurement sequences module, tracker and inverter trucks into a laydown yard whose pallet positions are a finite, contested resource; foundation crews drive steel piles into geotechnical conditions that occasionally refuse them outright; electrical crews terminate string circuits into combiner boxes and measure insulation resistance, open-circuit voltage and polarity; a utility coordinator negotiates switching outages so the substation can be backfed and energized; a commissioning team proves nameplate capacity and performance ratio against contractual guarantees; and a labor compliance function maintains certified payroll so the project keeps its prevailing-wage and apprenticeship qualification for the tax credit that makes the whole financing model work. Each of these workstreams produces evidence that another workstream depends on, and today that evidence lives in spreadsheets, email threads and PDF transmittals.

This document specifies the backend service that replaces those spreadsheets with a single auditable system of record, mounted under the `/solar` URL prefix. The service's central obligation is not merely to store construction data but to compute — continuously and deterministically — whether the project has actually earned the milestone its contractor is claiming. Mechanical completion readiness is derived from every array block's two independent progress dimensions plus every grading area's civil acceptance; substantial completion is gated on an energized substation, a passed capacity test and a clean critical punch list; final acceptance is gated on a passed performance-ratio test, an empty punch list and a qualified tax-credit determination. When a single pile is refused or a single string circuit fails a retest, that derived readiness must collapse and take the outstanding milestone claim and every live commissioning test down with it, in one pass, in the same request.

Two further constraints shape the design. First, money is settled through a pinned waterfall: liquidated damages, retainage and punch-list holdback interact circularly enough that any reordering of the arithmetic produces a different number, so the evaluation order is part of the contract, not an implementation detail. Second, the project is a segregation-of-duties environment by regulation and by contract — the operator who posts payroll lines may not certify the week, the foreman who submits punch-list closure evidence may not decide it, and the manager who files a milestone claim may not certify it. The API enforces those separations at the header level rather than trusting client-side workflow.

## 2. Global Specifications & System-Wide Principles

### 2.1. Site Personnel and Role-Based Access Control

Every request to this API — including every read — must carry two headers. `X-User-ID` identifies the acting operator and `X-User-Role` declares the capacity in which that operator is acting. If either header is absent, or if `X-User-Role` carries a value that is not one of the eight roles below, the request is rejected with `ERR_UNAUTHENTICATED` and HTTP 401. If both headers are well-formed but the declared role is not authorized for the requested operation, the request is rejected with `ERR_FORBIDDEN_ROLE` and HTTP 403.

The eight recognized roles are:

- `EpcProjectManager` — the contractor-side owner of the project record. Creates projects and array blocks, accepts change orders, and files milestone claims. Files claims but never certifies them.
- `CivilSuperintendent` — runs grading, drainage and access-road work under the stormwater permit, and logs rain events, best-management-practice inspections, permit suspensions and permit reinstatements.
- `ProcurementCoordinator` — opens laydown yard zones, reserves pallet positions for inbound shipments, and receives or cancels those shipments.
- `InstallationForeman` — registers and drives piles, remediates piles, declares block mechanical completion, registers and wires string circuits, records string test results, and submits punch-list closure evidence. Submits closures but never decides them.
- `UtilityCoordinator` — creates the substation and interconnection facility record, advances its construction status, requests utility switching outages and records the utility's response.
- `CommissioningEngineer` — schedules capacity and performance-ratio tests, appends measurement intervals, and finalizes results.
- `OwnerEngineer` — the owner's representative. Accepts civil work, raises punch-list items, decides closure submissions, and certifies or rejects milestone claims. Decides but never submits.
- `LaborComplianceOfficer` — opens certified-payroll weeks, posts and voids labor entries, certifies weeks, and triggers labor-compliance runs that feed tax-credit qualification.

All eight roles are **opaque identities**. When `X-User-Role` is `EpcProjectManager`, `CivilSuperintendent`, `ProcurementCoordinator`, `InstallationForeman`, `UtilityCoordinator`, `CommissioningEngineer`, `OwnerEngineer` or `LaborComplianceOfficer`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it wherever a transition writes it — as `mc_claimed_by_user_id` on a project, as `submitted_by_user_id` and `decided_by_user_id` on a punch-list item, as `posted_by_user_id` on a labor entry, and as `certified_by_user_id` on a payroll week — and it compares recorded values to each other for the segregation-of-duties rules of §2.10, but it never compares `X-User-ID` to any entity's `id` and never treats it as a foreign key.

Read access is uniform: every GET endpoint in §4 is available to all eight roles. The logical-clock test-driving endpoint is likewise available to all eight roles. Every write endpoint is exclusive to the single role named in its §4 row, with no overlap between roles.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection endpoints accept two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific list endpoint states otherwise, results are ordered by `created_at` ascending. Three listings order differently because their domain demands it: payroll weeks of a project are returned in `week_start_date` ascending order, labor entries of a week are returned in `work_date` ascending order with `created_at` ascending as the tie-break, and measurement intervals of a commissioning test are returned in `created_at` ascending order (which is also the order in which they are replayed by the commissioning calculations).

For every list response, the `meta` object carries the four pagination fields `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of rows matching the request's filters *before* the page window is applied, and `has_more` is true exactly when rows matching the filters remain beyond the current window. Where a list endpoint also accepts domain filters — for example `project_id`, `yard_zone_id`, `status`, `component_type`, `severity`, `test_type`, `is_valid`, `is_apprentice`, `purpose`, `mechanical_status`, `electrical_status`, `mc_ready`, `grading_area_id`, `block_id`, `milestone_state` or `mc_readiness` — those filters combine conjunctively and are applied before pagination.

### 2.4. Resource Identity, Timestamps and Version Semantics

Every resource is addressed by an `id` that the server mints as a UUID. Identifiers carry no type prefix and no domain-flavoured encoding; a project id and a pile id are indistinguishable by shape. Clients never supply an `id`.

Most resources also carry three system-managed properties. `created_at` is an ISO 8601 UTC timestamp with three fractional digits, stamped from the logical clock at creation and never changed thereafter. `updated_at` is an ISO 8601 UTC timestamp in the same format, equal to `created_at` at creation and refreshed on every subsequent mutation. `version` is an integer that starts at 1 when the resource is persisted and increments by exactly 1 on every mutation of that resource, including mutations driven indirectly by a cascade originating in a different resource.

One resource is deliberately leaner. A measurement interval belonging to a commissioning test is immutable once appended: it carries only `id` and `created_at`. It has **no** `updated_at` field and **no** `version` field, and no operation in this specification mutates one after it is written.

### 2.5. The Logical Site Clock

Every timestamp the server stamps, every rain-blackout comparison, every best-management-practice currency check, every outage-window containment test and every delay-day count reads from a single logical UTC clock rather than from wall-clock time. Until it has been set explicitly, that clock reads `2026-08-01T00:00:00Z`. A test-driving capability, available to all eight roles, replaces the clock instant with a supplied `now` value; it modifies no business entity and bumps no resource's `version`.

### 2.6. Path Resolution Order and the Single-Project Boundary

Nested addresses are resolved strictly left to right. For a request addressed at a resource nested under a project, the project is resolved first — a missing project yields `ERR_PROJECT_NOT_FOUND` (HTTP 404) — and only then is the child segment resolved. Once every path segment resolves, foreign keys carried in the request body are resolved in their declaration order, so a body naming both a yard zone and something else fails on the first unresolvable reference rather than on an arbitrary one. Each entity kind has its own not-found code: `ERR_GRADING_AREA_NOT_FOUND`, `ERR_YARD_ZONE_NOT_FOUND`, `ERR_DELIVERY_NOT_FOUND`, `ERR_BLOCK_NOT_FOUND`, `ERR_PILE_NOT_FOUND`, `ERR_STRING_CIRCUIT_NOT_FOUND`, `ERR_SUBSTATION_NOT_FOUND`, `ERR_OUTAGE_WINDOW_NOT_FOUND`, `ERR_COMMISSIONING_TEST_NOT_FOUND`, `ERR_PUNCH_ITEM_NOT_FOUND`, `ERR_PAYROLL_WEEK_NOT_FOUND` and `ERR_LABOR_ENTRY_NOT_FOUND`, each returning HTTP 404. The grading-area code covers both grading-area-addressed endpoints and the `grading_area_id` supplied when a block is created; the block code covers both block-addressed endpoints and the optional `block_id` supplied when a punch-list item is raised.

Existence is not the same as belonging. Three references cross aggregate boundaries and each must stay inside a single project: the yard zone named by a delivery's `yard_zone_id` must have the same owning project as the delivery's `project_id`; the grading area named by a block's `grading_area_id` must belong to the project in whose path the block is created; and the block named by a punch-list item's `block_id` must belong to the project in whose path the item is raised. A reference that resolves to a real row belonging to a different project is rejected with `ERR_CROSS_PROJECT_REFERENCE` and HTTP 422 — never with a not-found code, because the resource does exist.

### 2.7. Validation Precedence

Many write operations can fail for several reasons at once, and the error a client receives must be predictable. The server therefore evaluates checks in a fixed global precedence order and returns the **first** failure it encounters, never a later one that happens to be easier to detect. The ladder, from highest precedence to lowest:

1. Header authentication — `ERR_UNAUTHENTICATED`.
2. Role authorization for the requested operation — `ERR_FORBIDDEN_ROLE`.
3. Request shape: required body fields present, enum values inside their declared sets, unknown fields rejected, and every numeric constraint honoured — hours strictly positive, pallet counts strictly positive, ordered unit counts strictly positive, capacities strictly positive, and percentages and fractions inside their declared ranges. Any violation is `ERR_INVALID_REQUEST`. The civil acceptance payload's compaction and drainage checks also report at this precedence, as described in §3.2.
4. Interval bound ordering: a laydown window's `laydown_window_start` must be strictly earlier than its `laydown_window_end`, an earthwork log's `work_start_at` strictly earlier than its `work_end_at`, and an outage request's `start_at` strictly earlier than its `end_at`. A non-strictly-ordered pair is `ERR_INVALID_WINDOW_BOUNDS` (HTTP 400). This applies to delivery creation, earthwork logging and outage requests.
5. Existence of path resources and then of body foreign keys, as described in §2.6.
6. The single-project boundary for cross-aggregate references — `ERR_CROSS_PROJECT_REFERENCE`. This applies to delivery creation, block creation and punch-list-item creation.
7. Optimistic concurrency on the parent resource — `ERR_STALE_YARD_ZONE_VERSION` on delivery creation and `ERR_STALE_PROJECT_VERSION` on commissioning-test creation (§2.8).
8. State-machine admissibility of the requested operation on the addressed resource: `ERR_GRADING_AREA_NOT_OPEN_FOR_WORK`, `ERR_DELIVERY_NOT_RESERVED`, `ERR_PILE_NOT_DRIVEABLE`, `ERR_PILE_NOT_REMEDIABLE`, `ERR_BLOCK_PILES_INCOMPLETE`, `ERR_CIRCUIT_STATE_INVALID`, `ERR_SUBSTATION_STEP_NOT_SEQUENTIAL`, `ERR_OUTAGE_WINDOW_ALREADY_ANSWERED`, `ERR_TEST_STATE_INVALID`, `ERR_PUNCH_ITEM_STATE_INVALID`, `ERR_PAYROLL_WEEK_LOCKED`, `ERR_LABOR_ENTRY_ALREADY_VOIDED` and `ERR_MILESTONE_OUT_OF_SEQUENCE`. Each is described with the workflow it guards in §3.
9. Segregation of duties — `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), covering punch-list closure decisions, payroll-week certification and milestone decisions (§2.10).
10. Prerequisite state on a *related* resource: the owning block's grading area must have been accepted before any pile of that block is driven or remediated (`ERR_GRADING_AREA_NOT_ACCEPTED`, HTTP 409); the owning block must be mechanically complete before a string circuit may be wired (`ERR_BLOCK_NOT_MECHANICALLY_COMPLETE`, HTTP 409); and a substation of the project must be energized before a commissioning test may be finalized and before substantial completion may be claimed (`ERR_SUBSTATION_NOT_ENERGIZED`, HTTP 422).
11. Stormwater permit currency: the grading area's `permit_status` must be `ACTIVE` and `bmp_deficiency_open` must be false. Otherwise `ERR_PERMIT_NOT_ACTIVE` (HTTP 422), on both earthwork logging and civil acceptance.
12. Post-rain blackout on earthwork logging — `ERR_RAIN_EVENT_BLACKOUT` (HTTP 422).
13. Best-management-practice inspection currency on earthwork logging — `ERR_BMP_INSPECTION_OVERDUE` (HTTP 422).
14. Earthwork window collision — `ERR_EARTHWORK_WINDOW_CONFLICT` (HTTP 409).
15. Outage window collision, including the switching buffer — `ERR_OUTAGE_WINDOW_CONFLICT` (HTTP 409).
16. Energization coverage: an approved backfeed window must contain the current instant — `ERR_NO_APPROVED_OUTAGE_WINDOW` (HTTP 422), on substation status advances.
17. Permitted disturbed acreage on earthwork logging — `ERR_DISTURBED_ACREAGE_EXCEEDED` (HTTP 422).
18. Laydown pallet capacity for the requested occupancy window on delivery creation — `ERR_YARD_WINDOW_CAPACITY_EXCEEDED` (HTTP 409).
19. Torque-tube survey tolerance on block mechanical completion — `ERR_TORQUE_TUBE_TOLERANCE_EXCEEDED` (HTTP 422).
20. Accepted-module availability on block mechanical completion — `ERR_INSUFFICIENT_ACCEPTED_MODULES` (HTTP 422).
21. Remediation effectiveness on a pile remediation — `ERR_REMEDIATION_STILL_OUT_OF_TOLERANCE` (HTTP 422).
22. At least one weather-valid interval on commissioning-test finalization — `ERR_NO_VALID_TEST_INTERVALS` (HTTP 422).
23. Project mechanical-completion readiness for a mechanical-completion claim and for its certification — `ERR_BLOCKS_NOT_MC_READY` (HTTP 422), on both milestone claims and milestone decisions.
24. Required commissioning test passed, for milestone claims — `ERR_REQUIRED_TEST_NOT_PASSED` (HTTP 422).
25. No open critical punch items, on substantial-completion claims and decisions — `ERR_OPEN_CRITICAL_PUNCH_ITEMS` (HTTP 422).
26. No open punch items at all, on final-acceptance claims and decisions — `ERR_OPEN_PUNCH_ITEMS` (HTTP 422).
27. Tax-credit qualification, on final-acceptance claims and decisions — `ERR_TAX_CREDIT_NOT_QUALIFIED` (HTTP 422).
28. Prevailing-wage floor at labor-entry post time when the project elects strict enforcement — `ERR_BELOW_PREVAILING_WAGE` (HTTP 422).
29. Cumulative change-order cap — `ERR_CHANGE_ORDER_CAP_EXCEEDED` (HTTP 422).

The practical consequence worth internalizing: a suspended permit surfaces as `ERR_PERMIT_NOT_ACTIVE` rather than being masked by a later acreage or window-collision failure, and a stale parent version surfaces as a concurrency rejection rather than as a state-machine rejection, even when both conditions hold in the same request.

### 2.8. Optimistic Concurrency on Contested Parents

Two write operations consume or supersede state that belongs to a parent resource, and both require the client to prove it is working from a current view of that parent.

Reserving pallet positions for an inbound shipment requires a non-optional `expected_yard_zone_version` field in the request body, carrying the client's last observed `version` of the target yard zone. If that value does not equal the yard zone's current `version` — because another writer has reserved, cancelled or rejected a shipment in that zone since the client read it — the reservation is rejected with `ERR_STALE_YARD_ZONE_VERSION` and HTTP 412. Pallet positions are a conserved quantity, and a reservation may only be admitted while the client's view of the zone's occupancy is current.

Scheduling a commissioning test requires a non-optional `expected_project_version` field carrying the client's last observed `version` of the target project. A mismatch with the project's current `version` is rejected with `ERR_STALE_PROJECT_VERSION` and HTTP 412. This write legitimately destroys commissioning history — it voids any earlier test of the same kind on that project — so it is only admitted when the client has observed the project as it stands.

No other endpoint in this specification takes a version field. Requests to endpoints outside these two carry no `expected_yard_zone_version`, no `expected_project_version` and no other expected-version input, and supplying one is an unknown field.

### 2.9. Precision, Rounding and Units

Wherever a computed value is rounded, the method is **round half up** — a value exactly on the midpoint rounds away from zero. The scales differ by quantity and are part of the contract:

- Money is whole cents. Every cents-denominated computed field — restitution, liquidated damages, retainage, holdback, settlement and release amounts — is rounded half up to a whole number of cents.
- Hour ledgers, acreage ledgers, percentage figures, capacity results in kilowatts and per-interval corrected power are carried to **2 decimal places**, rounded half up.
- Performance ratio and the string-test allowed-deviation figure are carried to **4 decimal places**, rounded half up. A delivery's damage ratio is likewise carried to 4 decimal places.
- Voltages are carried to 2 decimal places, insulation resistance to 1 decimal place, pile embedment in whole millimetres, plumb deviation to 1 decimal place, rainfall to 2 decimal places and compaction to 1 decimal place.
- Pallet positions, unit counts, pile counts, circuit counts, interval counts and delay days are integers with no rounding at all.
- Interval arithmetic on windows and buffers is in whole minutes, UTC; delay days and inspection intervals are in whole UTC calendar days.

Where a formula rounds more than once, **the order of rounding is part of the specification**, not a matter of taste. Two places in this system are especially sensitive and are spelled out where they are used: per-interval weather correction rounds each interval before the intervals are averaged and then rounds the average (§3.7), and prevailing-wage restitution rounds each labor entry to whole cents before the entries are summed (§3.8). Rounding the aggregate instead of the parts produces a different, incorrect number.

### 2.10. Segregation of Duties

Three decision points in this system must be taken by someone other than the person who created the thing being decided, and all three compare `X-User-ID` against a previously recorded operator identifier. A punch-list closure decision is refused when the deciding `X-User-ID` equals the item's `submitted_by_user_id`. A payroll-week certification is refused when the certifying `X-User-ID` matches the `posted_by_user_id` of any labor entry of that week that is still posted. A milestone decision is refused when the deciding `X-User-ID` equals the project's `mc_claimed_by_user_id`. In all three cases the rejection is `ERR_SEGREGATION_OF_DUTIES` with HTTP 403, and it is evaluated after state admissibility but before any of the domain-specific business gates.

### 2.11. Three Interval Conventions, Deliberately Different

This system reasons about three kinds of time windows, and they do **not** share semantics. Implementers should treat the differences as intentional.

Laydown occupancy windows are **half-open with aggregate capacity**. Two shipments overlap only when one's `laydown_window_start` is strictly earlier than the other's `laydown_window_end` *and* its `laydown_window_end` is strictly later than the other's `laydown_window_start`; windows that merely touch at an endpoint do not overlap. Overlap alone is not a conflict — many shipments may share a zone until their summed pallet demand exceeds the zone's capacity.

Utility outage windows are **closed with an exclusive switching buffer**. A feeder admits exactly one live window, and each window is padded on both sides by a switching buffer of two hours — 120 minutes — so touching windows collide, and so do windows separated by a gap of 120 minutes or less.

Earthwork occupancy windows are **closed with exclusive crew occupancy and no buffer**. Two windows collide when the candidate's start is at or before an existing window's end and the candidate's end is at or after that window's start, which means windows that merely touch at an instant do collide, but a one-minute gap is enough to clear.

### 2.12. Derived Readiness and Cascade Discipline

A great deal of this system's value lies in fields nobody writes directly. Counters, ledgers, readiness flags and settlement figures are recomputed from their inputs whenever those inputs change, and the recomputation is **immediate**: by the time a write returns, every derived field it affects — on the written resource, on its parent, and on the project — already reflects the new reality.

Cascades propagate in a single ordered pass, and the order is fixed: a pile or string-circuit outcome updates its array block's counters and state dimensions; the block's readiness flag is recomputed; the project's block counters and readiness are recomputed; and only then are the two readiness-loss consequences applied — automatic rejection of an outstanding mechanical-completion claim, and suspension of every live commissioning test. Each resource touched along that chain has its own `version` incremented by 1 and its `updated_at` refreshed. A resource whose derived values happen to come out unchanged is not re-versioned by the cascade.

Each write states, in §3, exactly which parents it bumps. As a rule of thumb, creating a child that changes a project-level rollup bumps the project — grading areas, blocks, punch-list items, commissioning tests and labor entries all do — whereas creating a child that changes nothing at the project level does not: registering a yard zone, a pile, a string circuit, an outage window or a payroll week leaves the project's `version` untouched.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Project and Managing Scope

An `EpcProjectManager` opens the system of record by creating a project. The payload establishes the identity and the commercial baseline in one shot: a `name`, the `utility_name` of the interconnecting utility, the nameplate `ac_capacity_kw` and the installed `dc_capacity_kw` (both strictly greater than zero), the base `contract_value_cents` (strictly positive), the `retainage_pct` fraction of the adjusted contract withheld until final acceptance (at least 0 and at most 0.10), the `ld_per_day_cents` liquidated-damages rate per calendar day of substantial-completion delay (zero or more), the `ld_cap_pct` ceiling on liquidated damages expressed as a fraction of the adjusted contract (at least 0 and at most 0.20), the contractual `sc_deadline_date` as a `YYYY-MM-DD` UTC calendar date, the `guaranteed_capacity_kw_ac` the capacity test must clear (strictly positive) and the `guaranteed_performance_ratio` the performance test must clear, given to four decimals and lying strictly between 0 and 1.

Three optional inputs are feature selectors that shape later compliance behaviour, and each has a default. `prevailing_wage_election` defaults to `REMEDIABLE`, which accepts an under-prevailing payroll line and accrues restitution against it; the alternative value `STRICT` refuses such a line outright at post time. `apprenticeship_basis` defaults to `PROJECT_AGGREGATE` and selects which of the two apprenticeship measurement variants a labor-compliance run applies; the alternative is `WEEKLY_WORST_CASE`. `apprenticeship_min_pct` defaults to 15.00 — a fifteen percent apprentice share of labor hours is the statutory floor most wage determinations impose — and may be set anywhere from 0 through 100 inclusive.

A newly persisted project has `version` 1 and every derived field at rest. Its `milestone_state` is `PRECONSTRUCTION`, its `mc_readiness` is `BLOCKED`, and its `tax_credit_status` is `UNDETERMINED` — the last of these meaning "no labor-compliance run has been performed yet", which is deliberately distinguishable from both `QUALIFIED` and `DISQUALIFIED`. The ledger fields `approved_change_order_cents`, `blocks_total`, `blocks_mc_ready_count`, `total_labor_hours`, `apprentice_labor_hours`, `apprentice_hours_pct`, `wage_restitution_owed_cents`, `wage_liquidated_damages_cents`, `open_punch_item_count`, `open_critical_punch_count`, `delay_days`, `ld_assessed_cents`, `retainage_held_cents`, `punchlist_holdback_cents`, `sc_payment_due_cents` and `final_payment_cents` all start at 0. `apprenticeship_basis_applied`, `mc_claimed_by_user_id` and `last_milestone_rejection_reason` all start null; the first records which basis the most recent labor-compliance run actually used, the second holds the operator identity behind an outstanding mechanical-completion claim, and the third holds the reason recorded by the most recent milestone rejection.

Scope grows through change orders, which only the `EpcProjectManager` may accept. Each carries an `amount_cents` and a `reason`. Acceptance is capped: the cumulative total of accepted change orders — the project's existing `approved_change_order_cents` plus the new `amount_cents` — may not exceed twenty percent of the **base** contract value, computed as `contract_value_cents` multiplied by 0.20 and rounded half up to whole cents. Note carefully that the cap is always measured against the base `contract_value_cents` and never against the already-adjusted value, so the cap does not creep upward as change orders accumulate. A request that would breach the cap is rejected with `ERR_CHANGE_ORDER_CAP_EXCEEDED` and the project is left untouched; one that clears it sets `approved_change_order_cents` to the new cumulative total and increments the project's `version` by 1. Change orders are inadmissible once the project has reached `FINAL_ACCEPTED`, where the attempt is rejected with `ERR_MILESTONE_OUT_OF_SEQUENCE`.

A dedicated computed read exposes the commercial position on one page, for any role. It returns `adjusted_contract_cents` — the base `contract_value_cents` plus `approved_change_order_cents` — together with `open_punch_item_count`, `open_critical_punch_count` and `tax_credit_status`, and all four of those are always live. It also returns seven money and timing figures that mirror what the settlement waterfall of §3.9 froze onto the project: `delay_days`, `ld_cap_cents`, `ld_assessed_cents`, `retainage_held_cents`, `punchlist_holdback_cents` and `sc_payment_due_cents` are 0 until substantial completion has been certified, and `final_payment_cents` is 0 until final acceptance has been certified. `ld_cap_cents` is the only one of the seven that is not stored on the project itself; it is the adjusted contract multiplied by `ld_cap_pct`, rounded half up to whole cents.

### 3.2. Civil Grading Under Stormwater Permit Coverage

Site civil work is organised into grading areas, each opened by the `CivilSuperintendent` under a named stormwater construction general permit. Creation takes an `area_code` unique within the project, the `permit_number` covering the area, a `disturbed_acreage_limit` strictly greater than zero, a `bmp_inspection_interval_days` of at least one day, and optionally an `access_road_meters` length of access road constructed under the area, which defaults to 0. The new area begins with `status` `PLANNED` and `permit_status` `ACTIVE`. The permit field takes one of `ACTIVE`, `SUSPENDED` or `TERMINATED`: suspension and reinstatement move coverage between the first two, while `TERMINATED` denotes coverage withdrawn outright and is not reachable through any operation in this specification. On creation its `earthwork_windows` list is empty, its `disturbed_acreage_current` is 0, its `bmp_deficiency_open` is false, and `rain_blackout_until`, `status_before_hold`, `compaction_test_pct` and `drainage_inspection_passed` are all null. `bmp_last_inspected_at` is stamped with the current logical-clock instant, which starts the inspection interval running from the moment the area is opened. Because a project's mechanical-completion readiness demands that *every* grading area be accepted, opening a fresh area immediately forces the project's `mc_readiness` to `BLOCKED` and increments the project's `version` by 1.

Physical work is recorded as earthwork logs. Each log declares an `activity_type` of `CLEARING`, `GRADING`, `DRAINAGE` or `ACCESS_ROAD`, the closed occupancy interval `work_start_at` through `work_end_at`, the `acreage_disturbed_delta` the activity newly disturbs, and optionally a `crew_ref`. A `CLEARING` log advances a `PLANNED` area to `CLEARED`; on an area already `CLEARED` or `GRADED` it is accepted and leaves the status where it was. A `GRADING` log requires the area to be `CLEARED` or `GRADED` and advances `CLEARED → GRADED`, leaving an already-`GRADED` area unchanged; attempting it on a `PLANNED` area is rejected with `ERR_GRADING_AREA_NOT_OPEN_FOR_WORK`. `DRAINAGE` and `ACCESS_ROAD` logs are accepted from `PLANNED`, `CLEARED` or `GRADED` and never change the status. An area on `HOLD`, and an area that has reached the terminal `ACCEPTED`, accept no earthwork logs at all, and the rejection is again `ERR_GRADING_AREA_NOT_OPEN_FOR_WORK`.

Every earthwork log runs a gauntlet of site-condition gates, and §2.7 fixes the order in which they fire. Permit currency comes first: an area whose `permit_status` is anything other than `ACTIVE`, or whose `bmp_deficiency_open` is true, refuses work with `ERR_PERMIT_NOT_ACTIVE`. Next comes the post-rain blackout: when `rain_blackout_until` is set and the proposed `work_start_at` falls strictly before it, work is refused with `ERR_RAIN_EVENT_BLACKOUT`; a null `rain_blackout_until` imposes no restriction, and a `work_start_at` exactly at the blackout boundary is permitted. Third is inspection currency: the proposed `work_start_at` may be no later than `bmp_last_inspected_at` advanced by `bmp_inspection_interval_days` whole days, and a later start is refused with `ERR_BMP_INSPECTION_OVERDUE`. Fourth, the candidate interval is checked against crew occupancy under the closed, unbuffered convention of §2.11: if the candidate's `work_start_at` is at or before the `work_end_at` of any record already in `earthwork_windows`, and the candidate's `work_end_at` is at or after that record's `work_start_at`, the log is refused with `ERR_EARTHWORK_WINDOW_CONFLICT`. Every record ever appended participates in this check; the list is append-only and is never pruned, so accepted history keeps constraining new work indefinitely. Fifth and last, the acreage ledger gate: the area's current `disturbed_acreage_current` plus the candidate's `acreage_disturbed_delta`, rounded half up to two decimal places, may not exceed the `disturbed_acreage_limit`; exceeding it is `ERR_DISTURBED_ACREAGE_EXCEEDED`.

Only after all five gates pass is the log persisted. The system appends a record of the `work_start_at`, `work_end_at`, `activity_type` and `acreage_disturbed_delta` to `earthwork_windows`, then recomputes `disturbed_acreage_current` as the sum of `acreage_disturbed_delta` across every appended record taken in `created_at` ascending order, rounded half up to two decimal places. The status advance described above is applied, `updated_at` is refreshed and the area's `version` increments by 1.

Site conditions themselves arrive as site events, also logged by the `CivilSuperintendent`. Every event names an `event_type` and the `occurred_at` instant, and may carry a free-text `note`. A `RAIN_EVENT` additionally carries `rainfall_inches`; if that figure is at least a quarter of an inch — 0.25 inches — the area's `rain_blackout_until` is set to `occurred_at` advanced by 48 hours, which is to say two full days of enforced dry-out. A rain event below the quarter-inch trigger is recorded but leaves `rain_blackout_until` exactly as it was, including leaving it null. A `BMP_INSPECTION` carries `deficiencies_found`; it sets `bmp_last_inspected_at` to `occurred_at` and sets `bmp_deficiency_open` to whatever `deficiencies_found` reported, so a clean inspection both restarts the interval clock and clears any deficiency the previous inspection had raised.

The remaining two event types drive the area's hold cycle. A `PERMIT_SUSPENSION` is admissible while the area is `PLANNED`, `CLEARED` or `GRADED` with `permit_status` `ACTIVE`; it captures the current status into `status_before_hold`, sets `status` to `HOLD` and `permit_status` to `SUSPENDED`, and — because a non-accepted area forces the project to `BLOCKED` — recomputes the project's `mc_readiness` and increments the project's `version` by 1 when that changes anything. Attempting a suspension on an area already on `HOLD` is rejected with `ERR_GRADING_AREA_NOT_OPEN_FOR_WORK`. A `PERMIT_REINSTATEMENT` runs the reverse: it requires `status` `HOLD`, `permit_status` `SUSPENDED` and `bmp_deficiency_open` false, and it restores `status` to whichever of `PLANNED`, `CLEARED` or `GRADED` was captured in `status_before_hold`, clears `status_before_hold` back to null, and returns `permit_status` to `ACTIVE`. Reinstatement while a deficiency is still open, or on an area that is not on hold, is rejected with `ERR_GRADING_AREA_NOT_OPEN_FOR_WORK`. Either event increments the grading area's `version` by 1.

Civil work ends with owner acceptance, which is the `OwnerEngineer`'s prerogative and drives `GRADED → ACCEPTED`. The acceptance payload carries the surveyed `compaction_test_pct` and the boolean `drainage_inspection_passed`, and both are stored on the area. Acceptance requires the area to be `GRADED` — any other status is `ERR_GRADING_AREA_NOT_OPEN_FOR_WORK` — and requires the permit to be `ACTIVE` with no open BMP deficiency, failing which it is `ERR_PERMIT_NOT_ACTIVE`. Beyond that, the compaction result must be at least 95.0 percent and `drainage_inspection_passed` must be true; a compaction figure below 95.0 or a drainage inspection that did not pass is refused with `ERR_INVALID_REQUEST`. Acceptance is terminal for the area: no further earthwork, suspension or reinstatement is admitted. It recomputes the project's `mc_readiness` — this is often the last piece of the readiness puzzle — and increments both the project's `version` and the area's `version` by 1.

### 3.3. Delivery Sequencing and Laydown Yard Occupancy

Material arrives faster than crews can install it, so the laydown yard is the project's real constraint. A `ProcurementCoordinator` divides it into zones, each created with a `zone_code` unique within the project and a `pallet_capacity` of at least one pallet position. A new zone starts with `reserved_pallets` at 0 and therefore `available_pallets` equal to its `pallet_capacity`; creating a zone changes nothing at project level and leaves the project's `version` alone.

Pallet positions behave as a conserved quantity. At every instant, a zone's `pallet_capacity` equals its `reserved_pallets` plus its `available_pallets`. `reserved_pallets` is the sum of `pallets` across every delivery pointing at that zone whose `status` is `RESERVED`, `ARRIVED` or `ACCEPTED`; deliveries that ended as `CANCELLED` or `REJECTED` are excluded and contribute nothing. `available_pallets` is simply the zone's `pallet_capacity` less `reserved_pallets`. The conservation property is strict rather than approximate: if a coordinator reserves a shipment and then cancels that same reservation, the zone's `reserved_pallets` returns to exactly the value it held before the reservation, with no pallet drift, while the zone's `version` has advanced by exactly 2 — once for the reservation and once for the release.

Reserving a shipment is the system's most heavily guarded create. The payload names the owning `project_id`, the `yard_zone_id` of the zone that will hold the pallets, the `component_type` being procured (`MODULE`, `TRACKER` or `INVERTER`), the `unit_qty` of ordered units — modules, tracker rows or inverters, depending on the component class — the `pallets` positions the shipment will occupy, the `planned_arrival_at` instant the truck is expected, the half-open occupancy window from `laydown_window_start` through `laydown_window_end`, and the `expected_yard_zone_version` demanded by §2.8. An `inspection_note` may be supplied at reservation time and left null otherwise. Both `unit_qty` and `pallets` must be strictly positive, and the occupancy window must be strictly ordered or the request fails with `ERR_INVALID_WINDOW_BOUNDS`. The named zone must belong to the same project as `project_id`, or the request fails with `ERR_CROSS_PROJECT_REFERENCE`.

The capacity check that follows is where the half-open convention earns its keep. The system collects every other delivery in the same zone whose `status` is `RESERVED`, `ARRIVED` or `ACCEPTED` and whose window genuinely overlaps the candidate's — that is, whose `laydown_window_start` is strictly earlier than the candidate's `laydown_window_end` and whose `laydown_window_end` is strictly later than the candidate's `laydown_window_start`. Shipments that merely abut the candidate, ending exactly when it begins, are not overlapping and are ignored. The `pallets` of the overlapping set are summed, the candidate's own `pallets` are added, and if that total exceeds the zone's `pallet_capacity` the reservation is refused with `ERR_YARD_WINDOW_CAPACITY_EXCEEDED`. This pairwise-overlap sum against the candidate is the pinned definition of occupancy: there is no interval splitting and no scan for a peak profile across sub-intervals. When the check passes, the delivery is persisted with `status` `RESERVED`, its `received_unit_qty`, `damaged_unit_qty`, `accepted_unit_qty`, `damage_ratio` and `cancel_reason` all null, and the zone's `reserved_pallets` and `available_pallets` are recomputed with the zone's `version` incremented by 1.

Receiving a truck is a two-step transition resolved inside a single request. The receipt payload carries the `received_unit_qty` actually counted off the truck, which must be greater than zero, the `damaged_unit_qty` found on inspection, which must be at least zero and no greater than `received_unit_qty`, and optionally an `inspection_note`. The delivery must still be `RESERVED`; anything else is `ERR_DELIVERY_NOT_RESERVED`. The system stores the two counts and the note, moves the delivery `RESERVED → ARRIVED`, and computes `damage_ratio` as `damaged_unit_qty` divided by `received_unit_qty`, rounded half up to four decimal places. It then immediately resolves the `ARRIVED` fork in the same request, and the two branches diverge sharply.

When `damage_ratio` is at most 0.05 — five percent damage or less — the delivery moves `ARRIVED → ACCEPTED`. Its `accepted_unit_qty` is set to `received_unit_qty` less `damaged_unit_qty`; the zone keeps this shipment's `pallets` inside `reserved_pallets`, because the material is now physically on hand; and for a `MODULE` shipment the accepted units become available to the module-availability ledger that gates block mechanical completion. When `damage_ratio` is strictly above 0.05, the delivery moves `ARRIVED → REJECTED` instead. Its `accepted_unit_qty` is set to 0, contributing nothing to module availability, and the reservation is released: the zone's `reserved_pallets` and `available_pallets` are recomputed with this delivery excluded and the zone's `version` is incremented by 1. Either way the delivery's own `version` increments by 1, and both `ACCEPTED` and `REJECTED` are terminal.

A reservation may also be abandoned before the truck arrives. Cancellation requires the delivery to still be `RESERVED` — otherwise `ERR_DELIVERY_NOT_RESERVED` — takes a mandatory `cancel_reason`, and is the compensating action of the pallet ledger: it moves the delivery `RESERVED → CANCELLED`, stores the reason, recomputes the zone's `reserved_pallets` and `available_pallets` with this delivery excluded, increments the zone's `version` by 1, and increments the delivery's own `version` by 1.

### 3.4. Foundations: Piles, Refusal and the Mechanical Dimension

The array is divided into blocks, and an `EpcProjectManager` creates each one inside a grading area of the same project. A block declares the `grading_area_id` it sits in, a `block_code` unique within the project, its own `dc_capacity_kw` strictly greater than zero, the `planned_pile_count` of piles that must be accepted before the block can be mechanically complete (at least one), and the `planned_string_count` of string circuits that must be tested before the block can be electrically complete (also at least one).

Each block carries **two independent progress dimensions**, and understanding their independence is essential. `mechanical_status` tracks foundations, racking and modules through the values `PLANNED`, `PILES_COMPLETE`, `MECH_COMPLETE` and `HOLD`. `electrical_status` tracks DC collection through `PLANNED`, `WIRED`, `TESTED` and `REWORK`. The two advance from entirely different operations and never constrain each other's values: a block may sit at `MECH_COMPLETE` while its electrical dimension is in `REWORK`, and it may sit at `TESTED` electrically while its mechanical dimension is on `HOLD`. They are joined at exactly one point — the derived boolean `mc_ready`, which is true if and only if `mechanical_status` is `MECH_COMPLETE` **and** `electrical_status` is `TESTED`, and false in every other combination.

A fresh block therefore starts with both dimensions at `PLANNED` and `mc_ready` false. Its five rollup counters — `piles_accepted_count`, `piles_refused_count`, `circuits_wired_count`, `circuits_tested_count` and `circuits_failed_count` — all start at 0, and `modules_installed_qty` and `max_torque_tube_deviation_mm` are both null until mechanical completion reports them. Creating the block increments the project's `blocks_total`, recomputes the project's `mc_readiness` (a brand-new block is not ready, so readiness cannot survive the addition) and increments the project's `version` by 1.

An `InstallationForeman` registers each planned pile location on the block with its `row_index` (the tracker row within the block, at least 1), its `position_index` (the pile position within that row, at least 1) and the geotechnical `design_embedment_mm` depth in whole millimetres, strictly greater than zero. A registered pile begins at `PLANNED` with `actual_embedment_mm`, `plumb_deviation_mm`, `blow_count`, `driven_at` and `remediation_method` all null, `refusal_flag` false and `remediated` false. Registering a pile touches no counter and bumps no parent version.

Driving a pile is only permitted once the civil work under it has been signed off: the grading area owning the pile's block must be `ACCEPTED`, and a drive attempted before that is refused with `ERR_GRADING_AREA_NOT_ACCEPTED`. The pile must also still be `PLANNED`; a second drive on the same pile is refused with `ERR_PILE_NOT_DRIVEABLE`. The drive-result payload reports the `actual_embedment_mm` achieved, the `plumb_deviation_mm` from vertical in millimetres to one decimal place, the `blow_count` of the drive, a boolean `refusal` stating whether the crew hit geotechnical refusal, and optionally the `driven_at` instant.

Disposition follows a rule in which the three measurements interact non-linearly, because the refusal flag *selects which embedment threshold applies* and the plumb check is then required on top of whichever threshold was selected. Two derived quantities set it up: the refusal-relief embedment floor is the pile's `design_embedment_mm` multiplied by 0.90 — ninety percent of design depth — and the plumb check passes when `plumb_deviation_mm` is at most 12.0 millimetres. When `refusal` is reported true, the crew is entitled to relief: if `actual_embedment_mm` is strictly below the ninety-percent floor the pile becomes `REFUSED`; otherwise, if the plumb check passes the pile becomes `ACCEPTED`; otherwise it becomes `OUT_OF_TOLERANCE`. When `refusal` is reported false, no relief applies: the pile becomes `ACCEPTED` only when `actual_embedment_mm` is at least the full `design_embedment_mm` *and* the plumb check passes, and becomes `OUT_OF_TOLERANCE` in every other case. Whatever the outcome, the measurements are stored, `refusal_flag` is set to what the request reported, `driven_at` is recorded and the pile's `version` increments by 1.

The three dispositions have three quite different consequences at block level. An `ACCEPTED` pile increments the block's `piles_accepted_count` and therefore increments the block's `version` by 1; when that count reaches the block's `planned_pile_count` and no pile of the block is `REFUSED`, the mechanical dimension additionally advances `PLANNED → PILES_COMPLETE` and the block's `mc_ready` is recomputed, staying false until the electrical dimension reaches `TESTED`. An `OUT_OF_TOLERANCE` pile triggers no block-level cascade whatsoever — it simply never counts toward `piles_accepted_count`, and the block's two status dimensions, its five counters and its `version` all stay exactly as they were. A `REFUSED` pile increments `piles_refused_count`, and because the block now contains at least one refused pile its `mechanical_status` is forced to `HOLD` from whichever of `PLANNED`, `PILES_COMPLETE` or `MECH_COMPLETE` it held; that is the second hop of the pile-refusal cascade.

The third and fourth hops follow from the hold. Moving to `HOLD` recomputes `mc_ready` to false, and when `mc_ready` had been true the project's `blocks_mc_ready_count` is decremented and the project's `mc_readiness` recomputed — the third hop. If that recomputation takes readiness out of `READY` while a mechanical-completion claim was outstanding, the claim is automatically withdrawn: the project's `milestone_state` reverts `MC_CLAIMED → PRECONSTRUCTION`, `last_milestone_rejection_reason` is set to `AUTO_MC_READINESS_LOST` and `mc_claimed_by_user_id` is cleared. In the same pass, every commissioning test of the project sitting at `SCHEDULED` or `IN_PROGRESS` is driven to `SUSPENDED` with `suspend_reason` set to `MC_READINESS_LOST`. Each entity touched — block, project, and each suspended test — has its own `version` incremented by 1.

Remediation is the way back. A pile that is `OUT_OF_TOLERANCE` or `REFUSED` may be remediated by the `InstallationForeman`, again only while the owning block's grading area is `ACCEPTED`; a pile in any other status is refused with `ERR_PILE_NOT_REMEDIABLE`. The payload names a `remediation_method` of `PREDRILL`, `SPLICE` or `RELOCATE` together with the post-remediation `actual_embedment_mm` and `plumb_deviation_mm`. The remediation path reuses the relief branch of the disposition rule regardless of how the pile got there: it is accepted only when the new `actual_embedment_mm` is at least ninety percent of `design_embedment_mm` *and* the new `plumb_deviation_mm` is at most 12.0 millimetres. If either condition fails, the request is rejected with `ERR_REMEDIATION_STILL_OUT_OF_TOLERANCE` and the pile keeps its previous status and its previous measurements. On success the pile moves to `ACCEPTED`, `remediated` is set to true, `remediation_method` and the new measurements are stored, `refusal_flag` is cleared to false, and the pile's `version` increments by 1.

An accepted remediation then re-derives the block's `piles_accepted_count` and `piles_refused_count`. A block on `HOLD` whose `piles_refused_count` returns to 0 leaves the hold, and where it lands depends on the pile arithmetic: if `piles_accepted_count` is at least `planned_pile_count` the mechanical dimension goes to `PILES_COMPLETE`, and if it is still short of the planned count the block returns to `PLANNED` instead. The block's `version` increments by 1, and the project's `mc_readiness` is recomputed with the project's `version` incremented by 1 when the recomputation changes it.

Declaring mechanical completion is the `InstallationForeman`'s final mechanical act on a block, and it drives `PILES_COMPLETE → MECH_COMPLETE`. It reports the `modules_installed_qty` mounted on the block and the surveyed worst-case `max_torque_tube_deviation_mm`. The block must be at `PILES_COMPLETE`; any other mechanical status, including `HOLD`, is refused with `ERR_BLOCK_PILES_INCOMPLETE`. The surveyed deviation may not exceed a torque-tube tolerance of 25.0 millimetres, and a wider deviation is refused with `ERR_TORQUE_TUBE_TOLERANCE_EXCEEDED`.

The remaining gate reconciles the field report against procurement reality, and it counts only material that genuinely arrived intact. The system sums `accepted_unit_qty` across every delivery of the block's project whose `component_type` is `MODULE` and whose `status` is `ACCEPTED`; deliveries still `RESERVED` or `ARRIVED`, and deliveries that ended `REJECTED` or `CANCELLED`, contribute nothing, and `TRACKER` and `INVERTER` deliveries are excluded from the sum entirely. It then sums `modules_installed_qty` across every *other* block of the same project whose `modules_installed_qty` is not null. If the reported `modules_installed_qty` exceeds the delivered total less the amount already installed elsewhere, the declaration is refused with `ERR_INSUFFICIENT_ACCEPTED_MODULES`. Equality is acceptable — a block may consume the last remaining module.

On success the two reported measurements are stored, `mechanical_status` becomes `MECH_COMPLETE`, and `mc_ready` is recomputed. When `mc_ready` flips to true the project's `blocks_mc_ready_count` is incremented and the project's `mc_readiness` recomputed, with the project's `version` incremented by 1 when either changes; the block's own `version` increments by 1 in every case.

### 3.5. DC Collection: Wiring, String Testing and the Electrical Dimension

String circuits are registered on a block by the `InstallationForeman` with a `circuit_code` unique within that block and the `modules_in_series` count wired in series along the string, which must be at least 1. A registered circuit starts at `PLANNED` with `combiner_position`, `insulation_resistance_mohm`, `measured_voc_v`, `expected_voc_v`, `polarity_ok`, `test_failure_reason` and `tested_at` all null. Registration bumps no counter and no parent version.

Terminating a string into its combiner box requires the mechanical work above it to be finished: the owning block must have `mechanical_status` `MECH_COMPLETE`, and wiring attempted before that is refused with `ERR_BLOCK_NOT_MECHANICALLY_COMPLETE`. The circuit must be `PLANNED`; wiring an already-wired or tested circuit is refused with `ERR_CIRCUIT_STATE_INVALID`. The payload carries the `combiner_position` — the combiner box terminal position the string lands on — which is stored as the circuit moves `PLANNED → WIRED`. The block's `circuits_wired_count`, which counts every circuit of the block whose status is `WIRED`, `TESTED` or `FAILED`, is then re-derived; when it reaches the block's `planned_string_count` with `circuits_failed_count` still at 0, the block's electrical dimension advances `PLANNED → WIRED`. Both the circuit's `version` and the block's `version` increment by 1.

Testing is where the electrical dimension is actually decided. A test result may be recorded on a circuit that is `WIRED`, `TESTED` or `FAILED` — retesting is explicitly permitted and unbounded — while a `PLANNED` circuit refuses the operation with `ERR_CIRCUIT_STATE_INVALID`. The payload carries the measured `insulation_resistance_mohm` in megaohms, the measured `measured_voc_v` open-circuit voltage in volts, the `ambient_c` ambient temperature at the moment of measurement, and the boolean `polarity_ok` from polarity verification.

Before comparing anything, the system computes the temperature-corrected voltage the string *should* produce. Each module contributes 49.50 volts of open-circuit voltage at standard test conditions, so the uncorrected expectation is `modules_in_series` multiplied by 49.50 volts. That figure is then scaled by a temperature factor equal to one plus the module voltage temperature coefficient of -0.0028 per degree Celsius multiplied by the difference between `ambient_c` and the 25 degree Celsius standard-test reference — meaning an ambient temperature above 25 °C lowers the expected voltage and one below 25 °C raises it. The product is rounded half up to two decimal places and stored as `expected_voc_v`. The tolerance band around it is `expected_voc_v` multiplied by 0.03 — three percent — rounded half up to four decimal places.

Three checks are then applied **in a pinned order, and the first one that fails names the failure cause**. First, if `insulation_resistance_mohm` is strictly below 40.0 megaohms, the test fails and `test_failure_reason` is `INSULATION`. Second, if the absolute difference between `measured_voc_v` and `expected_voc_v` is strictly greater than the three-percent tolerance band, the test fails and `test_failure_reason` is `VOC_DEVIATION`. Third, if `polarity_ok` is false, the test fails and `test_failure_reason` is `POLARITY`. If none of the three fires, the test passes. The order matters because a string can violate two or three conditions at once; a circuit with wet insulation *and* reversed polarity reports `INSULATION`, never `POLARITY`. The insulation figure at exactly 40.0 megaohms passes, and a deviation exactly equal to the tolerance band passes.

A passing test drives the circuit to `TESTED`, from `WIRED` or from `FAILED` alike. The measurements `insulation_resistance_mohm`, `measured_voc_v`, `expected_voc_v` and `polarity_ok` are stored along with `tested_at`, and `test_failure_reason` is cleared back to null. The block's `circuits_tested_count` — the number of its circuits at `TESTED` — is re-derived; when it reaches `planned_string_count` with `circuits_failed_count` at 0, the block's electrical dimension advances `WIRED → TESTED`, `mc_ready` is recomputed, and if `mc_ready` flips to true the project's `blocks_mc_ready_count` is incremented and its `mc_readiness` recomputed. The same landing applies to a clean retest out of rework: a `REWORK` block whose `circuits_failed_count` returns to 0 while `circuits_tested_count` is at least `planned_string_count` advances `REWORK → TESTED`, with the identical `mc_ready` and project-readiness recomputation. Circuit and block versions each increment by 1, and the project's version increments by 1 when its readiness figures change.

A failing test drives the circuit to `FAILED` — admissible from `WIRED`, from `TESTED` and from `FAILED` — storing the measurements and the `test_failure_reason` that the pinned order selected. Because the block now contains a failed circuit, its `electrical_status` is forced from `WIRED` or `TESTED` to `REWORK`; that is the second hop of the string-test-failure cascade. The third hop recomputes `mc_ready` to false and, when it had been true, decrements the project's `blocks_mc_ready_count` and recomputes `mc_readiness`. The fourth hop is the readiness-loss consequence set already described in §3.4: an outstanding mechanical-completion claim reverts `MC_CLAIMED → PRECONSTRUCTION` with `last_milestone_rejection_reason` set to `AUTO_MC_READINESS_LOST` and `mc_claimed_by_user_id` cleared, and every commissioning test of the project at `SCHEDULED` or `IN_PROGRESS` is driven to `SUSPENDED` with `suspend_reason` `MC_READINESS_LOST`. The cycle `WIRED → FAILED → TESTED → FAILED → TESTED` is unbounded, and each new result overwrites the stored measurements rather than accumulating them.

Project-level readiness itself is a single derived verdict, recomputed after every transition that changes a block's `mechanical_status`, a block's `electrical_status`, or a grading area's `status`. `blocks_total` is the number of blocks belonging to the project and `blocks_mc_ready_count` is the number of those blocks whose `mc_ready` is true. `mc_readiness` is `READY` when the project has at least one block, when `blocks_mc_ready_count` equals `blocks_total`, and when every grading area of the project has `status` `ACCEPTED`; in every other case it is `BLOCKED`. A project with no blocks at all is never `READY`, however clean its civil work. The evaluation order across the whole chain is fixed and single-pass: pile or string-circuit outcome, then block, then project, then the milestone auto-rejection and commissioning-test suspension consequences.

### 3.6. Medium-Voltage Collection, the Substation and Utility Coordination

The plant cannot export a watt until the interconnection facility is built and the utility agrees to close a switch. A `UtilityCoordinator` creates the facility record for a project with a `substation_code` unique within the project, the point-of-interconnection `interconnection_voltage_kv` in kilovolts (strictly greater than zero) and the `mv_collection_km` length of medium-voltage collection circuit in kilometres (zero or more). A new facility begins at `SITE_CIVIL` with `utility_witness_ref`, `energized_at` and `energizing_outage_window_id` all null, and its creation leaves the project's `version` untouched.

Construction proceeds through a strictly sequential ladder — `SITE_CIVIL → STEEL_ERECTED → EQUIPMENT_SET → BACKFEED_REQUESTED → ENERGIZED` — and each advance is a separate act by the `UtilityCoordinator` carrying the target `to_status` and a `utility_witness_ref` recording the utility's witness or evidence reference for that step. Steps may be neither skipped nor repeated: a `to_status` that is not the immediate successor of the facility's current `status` is refused with `ERR_SUBSTATION_STEP_NOT_SEQUENTIAL`. Every accepted advance overwrites `utility_witness_ref` with the value supplied and increments the facility's `version` by 1. The advance into `BACKFEED_REQUESTED` carries no gate beyond sequencing — the project's medium-voltage collection is represented by `mv_collection_km`, which is already constrained to be zero or more at creation, and nothing further is checked.

Energization is different. Before the facility may move `BACKFEED_REQUESTED → ENERGIZED`, an outage window belonging to that facility must be sitting at `APPROVED` with `purpose` `BACKFEED`, and the current logical-clock instant must fall inside that window's closed interval from `start_at` through `end_at` inclusive. If no such window covers the instant, the advance is refused with `ERR_NO_APPROVED_OUTAGE_WINDOW`. When one does, the facility's `status` becomes `ENERGIZED`, `energized_at` is stamped with the current logical-clock instant, `energizing_outage_window_id` records the `id` of the window that was consumed, and that window itself transitions `APPROVED → EXECUTED` with its own `version` incremented by 1 alongside the facility's. `ENERGIZED` is terminal for the facility. Which window was consumed can be recovered afterwards by listing the facility's outage windows and filtering for `EXECUTED`.

Outage windows are requested by the `UtilityCoordinator` well ahead of the work they cover. Every window is stored against the `substation_id` of the facility whose switching it covers. A request names the `start_at` and `end_at` bounds of the desired switching outage — strictly ordered, or the request is refused with `ERR_INVALID_WINDOW_BOUNDS` — and a `purpose` of `BACKFEED`, `SWITCHING` or `TIE_IN`. The request is persisted at `REQUESTED` with `utility_reference` and `responded_at` null, and it bumps no parent version.

Because the feeder can only be de-energized once at a time, and because switching itself takes crews and time on either side of the nominal window, the conflict rule is the strictest of the three interval conventions in this system. Every other window on the same facility whose `status` is `REQUESTED`, `APPROVED` or `EXECUTED` is examined; windows that were `DENIED` have released the feeder and are excluded from the comparison entirely. The candidate collides with such a window when the candidate's `start_at` is at or before that window's `end_at` advanced by the two-hour switching buffer of 120 minutes, and simultaneously the candidate's `end_at` advanced by the same 120-minute buffer is at or after that window's `start_at`. Because the intervals are closed and both sides are padded, two windows that merely touch collide, and so do two windows separated by a gap of 120 minutes or less; a gap strictly greater than 120 minutes clears. A collision is refused with `ERR_OUTAGE_WINDOW_CONFLICT`.

The utility's answer arrives as a single recorded response carrying a `decision` of either `APPROVE` or `DENY` together with the `utility_reference` switching-order reference the utility issued. The window must still be at `REQUESTED`; a second response on the same window is refused with `ERR_OUTAGE_WINDOW_ALREADY_ANSWERED`. Both decisions store `utility_reference` and stamp `responded_at`, and both increment the window's `version` by 1. `APPROVE` drives `REQUESTED → APPROVED`, making the window eligible to be consumed by energization. `DENY` drives `REQUESTED → DENIED`, which is terminal and which additionally frees the feeder: from that moment the window is excluded from the conflict comparison, so a request that had been blocked by it can be resubmitted and accepted.

### 3.7. Commissioning: Capacity and Performance-Ratio Verification

Commissioning proves two separate contractual guarantees, and a `CommissioningEngineer` schedules a test for each. The scheduling payload names the `project_id` under test, the `test_type` — `CAPACITY` for the nameplate demonstration or `PERFORMANCE_RATIO` for the efficiency demonstration — the `scheduled_at` planned start instant, and the `expected_project_version` that §2.8 demands. It may also carry a `correction_variant`, which defaults to `AS_MEASURED` and whose only other value is `WEATHER_CORRECTED`. That selector governs the capacity calculation only; on a `PERFORMANCE_RATIO` test it is ignored by the arithmetic entirely but is still stored and echoed back unchanged.

Scheduling a test is destructive by design, which is why it is version-guarded. When a new test is created, every earlier test of the *same* `test_type` on the *same* project whose `status` is `SCHEDULED`, `IN_PROGRESS`, `FAILED` or `SUSPENDED` is driven to `VOID`, with `void_reason` set to `SUPERSEDED_BY_NEW_TEST`, `superseded` set to true and each voided test's `version` incremented by 1. A test that already reached `PASSED` is *not* voided — passed results are the project's evidence and survive later testing — and a test of the other `test_type` is untouched. The new test is persisted at `SCHEDULED` with `interval_count` and `valid_interval_count` at 0, `reported_kw_ac`, `reported_performance_ratio`, `pass_threshold_kw_ac`, `finalized_at`, `suspend_reason` and `void_reason` all null, and `superseded` false. The project's `version` increments by 1.

Measurements are appended as immutable intervals, one per sampling period, each stored against the `commissioning_test_id` of the test it was appended to. Each carries the `sampled_at` instant, the plane-of-array `irradiance_w_m2` in watts per square metre, the metered `measured_kw_ac` power at the point of interconnection in kilowatts, the `ambient_c` ambient temperature in degrees Celsius and the `wind_m_s` wind speed in metres per second; irradiance, power and wind speed must all be zero or greater. Intervals may be appended while the test is `SCHEDULED` or `IN_PROGRESS`, and any other status refuses them with `ERR_TEST_STATE_INVALID`. The first interval appended to a `SCHEDULED` test moves it `SCHEDULED → IN_PROGRESS`. Every append increments `interval_count`, increments `valid_interval_count` when the sample is valid, and increments the test's `version` by 1. Intervals are replayed in `created_at` ascending order by every commissioning calculation, and — as §2.4 notes — an interval carries only `id` and `created_at`, with no `updated_at` and no `version`.

Validity is decided at append time by three weather filters that must all hold: `irradiance_w_m2` must be at least 600 watts per square metre, `wind_m_s` must be at most 8.0 metres per second, and `ambient_c` must lie between -10 and 45 degrees Celsius inclusive on both ends. The result is stored as `is_valid`. Also computed at append time is `corrected_kw_ac`, the interval's weather-corrected power, which is null whenever `is_valid` is false. For a valid interval it is derived in three steps: the cell temperature is the interval's `ambient_c` plus its `irradiance_w_m2` multiplied by a cell-temperature rise of 0.025 degrees Celsius per watt per square metre; the temperature factor is one plus the maximum-power temperature coefficient of -0.0035 per degree Celsius multiplied by the difference between that cell temperature and the 25 degree Celsius standard-test reference; and `corrected_kw_ac` is the interval's `measured_kw_ac` multiplied by the ratio of the 1000 watts per square metre reference irradiance to the interval's own `irradiance_w_m2`, then divided by that temperature factor, and finally rounded half up to two decimal places.

Finalization is the `CommissioningEngineer`'s closing act and requires three preconditions in the precedence order of §2.7. The test must be `IN_PROGRESS`, or the request is refused with `ERR_TEST_STATE_INVALID`. A substation of the project must be `ENERGIZED`, or the request is refused with `ERR_SUBSTATION_NOT_ENERGIZED` — nothing can be metered at the point of interconnection before the plant is connected to it. And at least one interval of the test must have cleared all three weather filters, or the request is refused with `ERR_NO_VALID_TEST_INTERVALS`. An optional `note` may accompany the request. On success `finalized_at` is stamped and the test's `version` increments by 1.

For a `CAPACITY` test the calculation runs over exactly the intervals whose three weather filters passed, taken in `created_at` ascending order; invalid samples are excluded from both the numerator and the denominator, so they neither drag the average down nor dilute it. The threshold is computed first: `pass_threshold_kw_ac` is the project's `guaranteed_capacity_kw_ac` multiplied by a pass ratio of 0.98 — ninety-eight percent of guarantee — rounded half up to two decimal places. Then each valid interval contributes one sample value, and which value it contributes is the whole point of the variant selector. Under `AS_MEASURED` an interval's sample value is its raw `measured_kw_ac`, with no correction applied at all; the interval's `corrected_kw_ac` is still stored for reference but plays no part in the result. Under `WEATHER_CORRECTED` an interval's sample value is its `corrected_kw_ac`, the per-interval figure already rounded to two decimal places when the interval was appended. **The rounding order is pinned**: correction and rounding happen per interval first, the rounded per-interval values are then summed and divided by the number of valid intervals, and that mean is rounded half up to two decimal places to give `reported_kw_ac`. Averaging raw values and rounding only once at the end is a different and incorrect computation. The same set of intervals can therefore yield a materially different `reported_kw_ac` under the two variants, and can flip the outcome. The test lands at `PASSED` when `reported_kw_ac` is at least `pass_threshold_kw_ac` and at `FAILED` when it falls short; equality passes.

For a `PERFORMANCE_RATIO` test the valid-interval filter is identical but the arithmetic is not, and no per-interval rounding occurs anywhere. The numerator is the sum of `measured_kw_ac` across the valid intervals. The denominator is the sum, across those same intervals, of the project's `dc_capacity_kw` multiplied by the interval's `irradiance_w_m2` and divided by the 1000 watts per square metre reference irradiance. `reported_performance_ratio` is the numerator divided by the denominator, rounded half up to four decimal places — one rounding, applied once to the ratio. The test lands at `PASSED` when `reported_performance_ratio` is at least the project's `guaranteed_performance_ratio` and at `FAILED` otherwise, again with equality passing. `correction_variant` has no effect here whatsoever: performance ratio is always computed from as-measured power against as-measured irradiance. `pass_threshold_kw_ac` and `reported_kw_ac` remain null on a `PERFORMANCE_RATIO` test, just as `reported_performance_ratio` remains null on a `CAPACITY` test.

One more path can end a test's life without any engineer touching it. As §3.4 and §3.5 describe, when a project's `mc_readiness` leaves `READY`, every test of that project at `SCHEDULED` or `IN_PROGRESS` is driven to `SUSPENDED` with `suspend_reason` `MC_READINESS_LOST`. A suspended test accepts no further intervals and cannot be finalized — both are refused with `ERR_TEST_STATE_INVALID` — and its only remaining fate is to be voided by a fresh test of the same `test_type`.

### 3.8. Certified Payroll, Prevailing Wage and Apprenticeship Qualification

The tax credit that underwrites the project's economics is conditional on labor practice, so payroll is a compliance artefact here rather than an accounting one. A `LaborComplianceOfficer` opens a certified-payroll week for a project by supplying its `week_start_date` — the Monday of the week in `YYYY-MM-DD` form, unique within the project. A new week starts at `OPEN` with `entry_count`, `total_hours`, `apprentice_hours`, `journeyworker_hours` and `apprentice_pct` all 0, and `certified_by_user_id` and `certified_at` null. Opening a week does not touch the project's `version`.

Each payroll line is posted into an open week by the same role, and is stored against the `payroll_week_id` of the week it was posted into. A line records the anonymized `worker_ref`, the wage-determination `classification` — one of `ELECTRICIAN`, `LABORER`, `OPERATOR` or `IRONWORKER` — a boolean `is_apprentice` marking a registered apprentice, the `hours` worked to two decimal places and strictly greater than zero, the base hourly `paid_rate_cents`, the hourly `fringe_rate_cents` benefit credit, the applicable `prevailing_rate_cents` total rate from the wage determination (all three rates in cents and none of them negative), and the `work_date` in `YYYY-MM-DD` form, which must fall inside the owning week; a date outside the week is refused with `ERR_INVALID_REQUEST`. The week must be `OPEN`; posting into a certified week is refused with `ERR_PAYROLL_WEEK_LOCKED`. The acting operator's `X-User-ID` is recorded on the line as `posted_by_user_id`, which is what makes the certification separation of §2.10 enforceable.

Two computed figures are derived per line. `shortfall_cents_per_hour` is the amount by which the line falls short of the wage determination each hour: the `prevailing_rate_cents` less the sum of `paid_rate_cents` and `fringe_rate_cents`, floored at zero so an over-scale line records no shortfall rather than a negative one. `restitution_cents` is that hourly shortfall multiplied by the line's `hours`, rounded half up to whole cents while the line remains `POSTED`; it becomes 0 once the line is voided.

Here the project's feature election bites. When `prevailing_wage_election` is `REMEDIABLE`, an under-prevailing line is accepted and its restitution simply accrues against the project. When `prevailing_wage_election` is `STRICT`, an under-prevailing line never enters the ledger at all: the post is refused with `ERR_BELOW_PREVAILING_WAGE` before persistence, on the grounds that the sum of `paid_rate_cents` and `fringe_rate_cents` must be at least `prevailing_rate_cents`. A line paying exactly the determination is admissible under both elections.

An accepted line is persisted at `POSTED` and immediately re-derives its week's hour ledger. `total_hours` is the sum of `hours` across the week's `POSTED` lines, `apprentice_hours` the same sum restricted to lines whose `is_apprentice` is true, and `journeyworker_hours` the same sum restricted to lines whose `is_apprentice` is false — each rounded half up to two decimal places. `apprentice_pct` is `apprentice_hours` divided by `total_hours`, multiplied by 100 and rounded half up to two decimal places, and is 0 whenever `total_hours` is 0. `entry_count` is the number of `POSTED` lines. The hour ledger is a conserved quantity: at every instant `apprentice_hours` plus `journeyworker_hours` equals `total_hours`. The week's `version` increments by 1, and the project's `total_labor_hours` and `apprentice_labor_hours` — the sums of the corresponding week figures across every week of the project, each rounded half up to two decimal places — are recomputed with the project's `version` incremented by 1.

Voiding is the compensating action, and it is exact. A void carries a `void_reason` and requires both that the line still be `POSTED` — an already-voided line is refused with `ERR_LABOR_ENTRY_ALREADY_VOIDED` — and that its owning week still be `OPEN`, failing which it is refused with `ERR_PAYROLL_WEEK_LOCKED`. The line moves `POSTED → VOIDED`, the reason is stored, and `restitution_cents` is zeroed. The week's `total_hours`, `apprentice_hours`, `journeyworker_hours`, `apprentice_pct` and `entry_count` are recomputed with the week's `version` incremented by 1, and the project's `total_labor_hours` and `apprentice_labor_hours` are recomputed with the project's `version` incremented by 1; the line's own `version` also increments by 1. The exactness matters: after a line is posted and then voided, all six of those ledger figures equal precisely the values they held before the post. Voided lines leave the ledger entirely and contribute nothing to any later computation.

Certification locks the week. It may carry an optional `note`. The week must be `OPEN` — certifying twice is refused with `ERR_PAYROLL_WEEK_LOCKED` — and it must contain at least one `POSTED` line, since an empty week certifies nothing; a week whose `entry_count` is 0 is refused with `ERR_INVALID_REQUEST`. Then the separation rule applies: the certifying `X-User-ID` must not match the `posted_by_user_id` of any `POSTED` line of that week, and a self-certification attempt is refused with `ERR_SEGREGATION_OF_DUTIES`. On success the week moves `OPEN → CERTIFIED`, `certified_by_user_id` records the certifying `X-User-ID`, `certified_at` is stamped from the logical clock, and the week's `version` increments by 1. A certified week is terminal and admits no further posts and no further voids.

Compliance is then evaluated by an explicit labor-compliance run, which the `LaborComplianceOfficer` triggers against the project and which may carry an optional `basis_override`. The run works over the `POSTED` lines of every payroll week of the project **regardless of whether those weeks are open or certified**; voided lines are excluded. The applied basis is the `basis_override` when one is supplied and the project's stored `apprenticeship_basis` otherwise, and whichever it is, the run records it in `apprenticeship_basis_applied`. Supplying `basis_override` changes only that one run — the project's own `apprenticeship_basis` is left exactly as it was.

The two bases measure the same hours very differently, and a project can qualify under one and fail under the other. Under `PROJECT_AGGREGATE`, the weeks of the project are taken in `week_start_date` ascending order and treated as one pool: `apprentice_hours_pct` is the sum of `hours` over all posted apprentice lines, divided by the sum of `hours` over all posted lines, multiplied by 100 and rounded half up to two decimal places — a single ratio across the whole job, in which a strong week can carry a weak one. Under `WEEKLY_WORST_CASE`, each week is measured on its own: the week's `apprentice_hours` divided by its `total_hours`, multiplied by 100 and rounded half up to two decimal places, and `apprentice_hours_pct` is the **smallest** of those per-week figures across the weeks whose `total_hours` is greater than zero. Weeks with no posted hours are excluded from that minimum entirely. Note that the rounding happens per week *before* the minimum is taken, which is one more reason the two bases can disagree on the same underlying lines. When no posted hours exist at all under the applied basis, `apprentice_hours_pct` is 0.

Apprenticeship qualification is then a single comparison: the run's `apprentice_hours_pct` must be **at least** the project's `apprenticeship_min_pct`, so a project landing exactly on its threshold qualifies.

The same run recomputes the wage position. Every `POSTED` line of the project, taken in `work_date` ascending order with `created_at` ascending as the tie-break, has its `shortfall_cents_per_hour` and `restitution_cents` re-derived exactly as described above. **The rounding order is pinned**: each line's restitution is rounded half up to whole cents *first*, and only then are the per-line amounts summed into the project's `wage_restitution_owed_cents`. Summing the unrounded products and rounding the total once produces a different figure and is wrong. From that total, `wage_liquidated_damages_cents` is the project's `wage_restitution_owed_cents` multiplied by 0.20 — a twenty percent uplift — rounded half up to whole cents.

Finally the run sets `tax_credit_status`. It is `QUALIFIED` when apprenticeship qualification holds *and* `wage_restitution_owed_cents` is exactly 0; in every other case it is `DISQUALIFIED`. A single cent of unpaid restitution disqualifies the project no matter how strong its apprentice ratio, and a fully-paid payroll with a thin apprentice share disqualifies it just as firmly. `UNDETERMINED` is reachable only before the first run and is never restored afterwards. The run stores `apprentice_hours_pct`, `apprenticeship_basis_applied`, `wage_restitution_owed_cents`, `wage_liquidated_damages_cents` and `tax_credit_status`, and increments the project's `version` by 1.

### 3.9. Punch List Closure, Milestone Administration and Settlement

Defects are raised by the `OwnerEngineer` as punch-list items against a project, each with a `title` describing the defect, a `category` naming the owning discipline (`MECHANICAL`, `ELECTRICAL`, `CIVIL` or `DOCUMENTATION`), a `severity` of `CRITICAL`, `MAJOR` or `MINOR`, and an `estimated_cost_cents` closure estimate of zero or more which later feeds the punch-list holdback. An item may optionally name the `block_id` of the block it belongs to; a balance-of-plant defect leaves it null, and a block that is named must belong to the same project. A new item starts at `OPEN` with `closure_evidence_ref`, `submitted_by_user_id` and `decided_by_user_id` null and `rejection_count` at 0. Raising it increments the project's `open_punch_item_count` and, when the severity is `CRITICAL`, also `open_critical_punch_count`, with the project's `version` incremented by 1.

The two project counters are derived from status, and their definition is deliberately inclusive: `open_punch_item_count` is the number of the project's items whose `status` is `OPEN` **or** `CLOSURE_SUBMITTED`, and `open_critical_punch_count` is the same count restricted to items whose `severity` is `CRITICAL`. An item awaiting an owner decision is therefore still open for milestone purposes; submitting evidence does not relieve the gate.

An `InstallationForeman` submits closure evidence on an `OPEN` item, supplying the `closure_evidence_ref`. The item moves `OPEN → CLOSURE_SUBMITTED`, the reference is stored, `submitted_by_user_id` records the submitting `X-User-ID`, and the item's `version` increments by 1. Submitting on an item that is not `OPEN` is refused with `ERR_PUNCH_ITEM_STATE_INVALID`, and because neither counter changes, the project's `version` is untouched.

The `OwnerEngineer` then decides the submission with a `decision` of `APPROVE`, `REJECT` or `WAIVE` and an optional `note`. The item must be at `CLOSURE_SUBMITTED`, or the decision is refused with `ERR_PUNCH_ITEM_STATE_INVALID`, and the deciding `X-User-ID` must differ from the item's `submitted_by_user_id`, or it is refused with `ERR_SEGREGATION_OF_DUTIES`. All three decisions store `decided_by_user_id` and increment the item's `version` by 1, and there the three diverge. `REJECT` sends the item back `CLOSURE_SUBMITTED → OPEN` and increments `rejection_count`; the two project counters are unaffected because the item was already counted as open, so the project's `version` does not move. This cycle — `OPEN → CLOSURE_SUBMITTED → OPEN` — is unbounded, and `rejection_count` is the running record of how many times the loop has been travelled. `APPROVE` drives `CLOSURE_SUBMITTED → CLOSED` and `WAIVE` drives `CLOSURE_SUBMITTED → WAIVED`; both are terminal, and both recompute the project's `open_punch_item_count` and `open_critical_punch_count` with the project's `version` incremented by 1. A waived item counts exactly as a closed one for every downstream gate.

Milestone administration runs as a two-party protocol across the project's `milestone_state`, which advances `PRECONSTRUCTION → MC_CLAIMED → MC_CERTIFIED → SC_CLAIMED → SC_CERTIFIED → FA_CLAIMED → FINAL_ACCEPTED`. Only the `EpcProjectManager` may file a claim, and every claim names a `milestone_kind` of `MECHANICAL_COMPLETION`, `SUBSTANTIAL_COMPLETION` or `FINAL_ACCEPTANCE`. Only the `OwnerEngineer` may decide one, supplying a `milestone_kind`, a `decision` of `CERTIFY` or `REJECT`, and an optional `reason`. A claim or decision that does not match the state the project is actually in — a substantial-completion claim while still in `PRECONSTRUCTION`, a decision when no claim is outstanding, a `milestone_kind` other than the one that was claimed — is refused with `ERR_MILESTONE_OUT_OF_SEQUENCE`. Every accepted claim and every accepted decision increments the project's `version` by 1.

A mechanical-completion claim requires `milestone_state` `PRECONSTRUCTION` and `mc_readiness` `READY`; a claim filed while readiness is `BLOCKED` is refused with `ERR_BLOCKS_NOT_MC_READY`. The accepted claim moves `PRECONSTRUCTION → MC_CLAIMED` and records the claiming `X-User-ID` in `mc_claimed_by_user_id`. Certifying it requires `milestone_state` `MC_CLAIMED`, requires that `mc_readiness` is *still* `READY` at decision time — readiness lost between claim and certification is refused with `ERR_BLOCKS_NOT_MC_READY` — and requires that the deciding `X-User-ID` differ from `mc_claimed_by_user_id`, failing which it is `ERR_SEGREGATION_OF_DUTIES`. Certification moves `MC_CLAIMED → MC_CERTIFIED` and clears `mc_claimed_by_user_id` back to null. Rejecting it moves `MC_CLAIMED → PRECONSTRUCTION`, stores the supplied `reason` into `last_milestone_rejection_reason`, and likewise clears `mc_claimed_by_user_id`; the same separation rule applies to a rejection as to a certification. The claim may then be re-filed once readiness is restored, and the cycle is unbounded. Separately — and without any owner action — an outstanding claim is withdrawn automatically when a pile refusal or a string-circuit failure takes `mc_readiness` out of `READY`, in which case `last_milestone_rejection_reason` is set to the sentinel `AUTO_MC_READINESS_LOST` rather than to any client-supplied text.

A substantial-completion claim requires `milestone_state` `MC_CERTIFIED` and three further conditions: a substation of the project must be `ENERGIZED`, or the claim is refused with `ERR_SUBSTATION_NOT_ENERGIZED`; a commissioning test of the project with `test_type` `CAPACITY` and `status` `PASSED` must exist, or it is refused with `ERR_REQUIRED_TEST_NOT_PASSED`; and `open_critical_punch_count` must be 0, or it is refused with `ERR_OPEN_CRITICAL_PUNCH_ITEMS`. Non-critical items may remain open at this stage. Certifying substantial completion requires `milestone_state` `SC_CLAIMED` and re-checks that `open_critical_punch_count` is still 0, again reporting `ERR_OPEN_CRITICAL_PUNCH_ITEMS`; it moves `SC_CLAIMED → SC_CERTIFIED` and runs the settlement waterfall below. Rejecting it moves `SC_CLAIMED → MC_CERTIFIED` and stores the supplied `reason` into `last_milestone_rejection_reason`.

The settlement waterfall is evaluated at the instant of substantial-completion certification, and its **seven steps run in exactly this order**. The circularity is only apparent: the liquidated-damages cap and the retainage both key off the adjusted contract value, and the punch-list holdback is capped by a retainage figure that has not been computed yet when the holdback's own raw amount is formed, so the sequence is fixed rather than inferable.

1. The adjusted contract value is the project's `contract_value_cents` plus its `approved_change_order_cents`.
2. The liquidated-damages ceiling is that adjusted contract value multiplied by `ld_cap_pct`, rounded half up to whole cents.
3. `delay_days` is the number of whole UTC calendar days from the project's `sc_deadline_date` to the calendar date of the current logical-clock instant, floored at 0 — an early or on-time certification records 0 rather than a negative figure.
4. `ld_assessed_cents` is the lesser of `delay_days` multiplied by `ld_per_day_cents`, and the ceiling from step 2.
5. `retainage_held_cents` is the adjusted contract value multiplied by `retainage_pct`, rounded half up to whole cents.
6. `punchlist_holdback_cents` is the lesser of two amounts: the sum of `estimated_cost_cents` across the project's punch-list items whose `status` is `OPEN` or `CLOSURE_SUBMITTED` at this instant, multiplied by a holdback multiplier of 1.5 — one and a half times the owner's estimate — and rounded half up to whole cents; and the `retainage_held_cents` from step 5. Items already `CLOSED` or `WAIVED` contribute nothing to that sum.
7. `sc_payment_due_cents` is the adjusted contract value less `retainage_held_cents`, less `ld_assessed_cents`, less `punchlist_holdback_cents`, floored at 0.

All six stored figures — `delay_days`, `ld_assessed_cents`, `retainage_held_cents`, `punchlist_holdback_cents`, `sc_payment_due_cents` and, through it, the project's commercial position — are frozen onto the project at that moment and are not recomputed by later punch-list activity.

A final-acceptance claim requires `milestone_state` `SC_CERTIFIED` and three conditions of its own: `open_punch_item_count` must be 0, so that no item remains `OPEN` or `CLOSURE_SUBMITTED`, or the claim is refused with `ERR_OPEN_PUNCH_ITEMS`; a commissioning test of the project with `test_type` `PERFORMANCE_RATIO` and `status` `PASSED` must exist, or it is refused with `ERR_REQUIRED_TEST_NOT_PASSED`; and `tax_credit_status` must be `QUALIFIED`, or it is refused with `ERR_TAX_CREDIT_NOT_QUALIFIED`. An `UNDETERMINED` status — a project on which no labor-compliance run has ever been performed — fails that gate exactly as a `DISQUALIFIED` one does. Certifying final acceptance requires `milestone_state` `FA_CLAIMED` and re-checks both that `open_punch_item_count` is still 0 and that `tax_credit_status` is still `QUALIFIED`, reporting `ERR_OPEN_PUNCH_ITEMS` and `ERR_TAX_CREDIT_NOT_QUALIFIED` respectively. It moves `FA_CLAIMED → FINAL_ACCEPTED`, which is terminal for the project. Rejecting it moves `FA_CLAIMED → SC_CERTIFIED` and stores the supplied `reason` into `last_milestone_rejection_reason`.

The final release is deliberately simple: `final_payment_cents` is the sum of the `retainage_held_cents` and `punchlist_holdback_cents` that the substantial-completion waterfall froze onto the project. Since no punch item may still be open at this point, the holdback that was withheld against unfinished work is released in full alongside the retainage. The arithmetic satisfies a money identity worth checking against any implementation, even though the identity itself is not stored anywhere: `sc_payment_due_cents` plus `final_payment_cents` equals the adjusted contract value less `ld_assessed_cents`. In other words, the only money the owner permanently keeps is the liquidated damages actually assessed.

## 4. Endpoint Definitions

Status codes follow one rule: an operation that brings a **new** resource into existence returns **201 Created**, while an operation that modifies an existing resource — including every state transition, every ledger recomputation and every settlement — returns **200 OK**.
