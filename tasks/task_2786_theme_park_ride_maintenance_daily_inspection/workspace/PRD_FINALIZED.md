# Theme Park Ride Maintenance API — Product Requirements Document

## 1. Introduction

A regional theme park opens its gates on the strength of a paper trail. Before the first guest boards, a technician must walk every attraction against a manufacturer-derived checklist, a second qualified pair of eyes must sign that walk off, and nothing that carries a live safety finding may dispatch. Around that daily ritual sits a much larger maintenance economy: nondestructive testing intervals counted in both ride cycles and calendar days, manufacturer bulletins and recalls that must be worked across every identical unit in the fleet, downtime events whose root cause has to be pinned to a specific component, parts that arrive late and park a repair indefinitely, operator certifications that expire silently, guest injuries that trigger a statutory notification clock, and an off-season overhaul programme that tears major components down to the shaft and rebuilds them in a shop bay with a finite number of slots.

Today the maintenance department reconciles all of this by hand across a checklist binder, a spreadsheet of bulletin compliance, a whiteboard of bay bookings and an email thread with the state ride inspector. The consequences are predictable: an attraction gets signed off while a safety-critical component is past its testing interval; a recall action is quietly deferred past its compliance deadline; the same person who recorded a finding is the person who signs it off; a parts commitment is released twice and the season budget drifts. The purpose of this API is to make each of those outcomes structurally impossible rather than merely discouraged.

This document specifies that service. It is a system of record for the maintenance department, and every business path is mounted under the `/park-ops` prefix. The design principle throughout is that guest-facing operability is never asserted by a human — it is **derived** from the current state of every child record an attraction owns, recomputed after every mutation, and refused loudly when any gate is closed.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that hold across every endpoint. Where §3 describes a workflow, this section describes the frame that workflow runs inside.

### 2.1. Operating Roles and Request Authentication

Every request — reads included — must carry two headers: `X-User-ID`, which identifies the acting staff member, and `X-User-Role`, which declares the capacity they are acting in. When either header is absent, blank, or when `X-User-Role` does not name one of the six roles below, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). When the role is recognised but is not listed among the authorised roles for the endpoint being called (see the table in §4), the request is refused with `ERR_UNAUTHORIZED` (HTTP 403).

The maintenance department recognises exactly six roles, spelled here as they must appear in the header:

- **`ParkOpsAdmin`** configures the system of record — attractions, components, checklist template revisions and their activation, bulletin publication, shop bays, and the logical park clock. A `ParkOpsAdmin` records no inspection outcomes and signs nothing off.
- **`MaintenanceManager`** owns money, parts and scheduling — bulletin acknowledgement and deferral, requisition commitment, backordering and cancellation, downtime closure and voiding, operator certification issuance, and off-season overhaul scheduling and phase advancement.
- **`MaintenanceTechnician`** performs the work — opening, reworking and submitting daily inspections, recording checklist outcomes, opening, diagnosing and resolving downtime events, raising and receiving part requisitions, and starting bulletin corrective work.
- **`QualifiedInspector`** holds the statutory sign-off authority — signing off or rejecting the pre-opening checklist, performing nondestructive testing, and verifying bulletin corrective work. A `QualifiedInspector` never records checklist outcomes.
- **`SafetyOfficer`** owns incident handling and the regulatory interface — filing incidents, placing the ride hold, opening the investigation, filing the regulator notification or closing the internal review, releasing the hold, and suspending operator certifications.
- **`RideOperator`** dispatches guests and logs ride cycles, and is otherwise read-only against every maintenance record.

Identity in this service is deliberately shallow. For all six roles — `ParkOpsAdmin`, `MaintenanceManager`, `MaintenanceTechnician`, `QualifiedInspector`, `SafetyOfficer` and `RideOperator` alike — `X-User-ID` is an opaque maintenance-department badge identifier and is never the `id` of a persisted entity. The server records that badge value on business rows wherever the scaffolded workflow calls for an audit stamp — `opened_by_user_id`, `recorded_by_user_ids` and `signed_off_by_user_id` on a daily inspection, `recorded_by_user_id` on an individual checklist result, `acknowledged_by_user_id` on a bulletin, `verified_by_user_id` on a fleet action, and `investigator_user_id` on an incident report — but it never compares `X-User-ID` to any entity's `id`, and no resource in this system is "owned" by its caller in an ownership-check sense. The one place a stored badge value is compared against a live caller is the segregation-of-duties rule at inspection sign-off, described in §3.3. Note also that `operator_user_id` on an operator certification is an opaque staff identifier supplied as ordinary input data — it identifies the ride operator being certified, not the authenticated caller.

Read access is uniform: all six roles may call every `GET` endpoint under `/park-ops`. Write access is narrow and is enumerated per endpoint in §4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Ordering and List Filters

List endpoints are paginated through two query parameters. `limit` caps the number of rows returned; when it is omitted it defaults to 10, and a supplied value must be at least 1 and at most 100. `offset` is the number of rows to skip before the page begins; when it is omitted it defaults to 0, and a supplied value must not be negative. A value outside either range is a malformed request and is refused with `ERR_INVALID_REQUEST`. Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` counts every row matching the filters before pagination is applied and `has_more` is true exactly when rows remain beyond the current page.

Unless stated otherwise, list results are ordered by `created_at` ascending. Several collections carry a domain-natural order instead, and those orders are normative:

- Attractions, components, fleet actions, part requisitions and shop bays: `created_at` ascending.
- Inspection template revisions: by `attraction_id`, then `revision` ascending.
- Checklist lines: by `sequence_no` ascending.
- Daily inspections: by `service_date` ascending, then `created_at` ascending.
- Inspection item results: by the `sequence_no` of the checklist line each result answers.
- Maintenance bulletins: by `issued_date` ascending, then `created_at` ascending.
- Downtime events: by `service_date` ascending, then `started_at` ascending.
- Operator certifications: by `effective_from` ascending.
- Overhaul work orders: by `window_start_date` ascending.

Because every entity in this system is a peer top-level collection rather than a nested child, each list endpoint also accepts equality filters named exactly after the fields they filter on, and those filters are the only way to reverse-enumerate a foreign key or to discover the identifier of a row the server created as a cascade. The attraction list accepts `park_area`, `operational_posture`, `model_code`, `manufacturer` and `active_template_id`. The component list accepts `attraction_id`, `criticality`, `ndt_status`, `component_type` and `condition_flag`. The template list accepts `attraction_id` and `status`. The checklist-line list accepts `template_id`, `component_id` and `severity_class`. The daily-inspection list accepts `attraction_id`, `template_id`, `service_date` and `status`. The inspection-item-result list accepts `inspection_id`, `checklist_item_id`, `outcome` and `severity_class`. The bulletin list accepts `manufacturer`, `model_code`, `severity`, `status` and `supersedes_bulletin_id`. The fleet-action list accepts `bulletin_id`, `attraction_id` and `status`. The downtime list accepts `attraction_id`, `failed_component_id`, `status`, `service_date`, `cause_category` and `auto_opened`. The requisition list accepts `attraction_id`, `downtime_event_id`, `bulletin_action_id` and `status`. The certification list accepts `attraction_id`, `operator_user_id` and `status`. The incident list accepts `attraction_id`, `status`, `injury_severity` and `notified_late`. The work-order list accepts `attraction_id`, `component_id`, `shop_bay_id`, `status` and `off_season`. Every one of these filters is optional, and several may be combined in one request.

### 2.4. The Logical Park Clock

Nothing in this service reads the wall clock. A single server-held **logical clock** supplies the value of "now" for every time-dependent derivation in the system: how many calendar days have elapsed since a component's last nondestructive test, whether an operator certification is inside its validity interval, whether a regulator notification was filed late, which UTC date a capacity-impact window defaults to, and which service date the operational posture derivation compares against. At process start the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time.

A `ParkOpsAdmin` moves the clock by calling `POST /_clock/set_current_utc` with a single field `to_iso8601` carrying the instant to move to. The response body reports the resulting instant as `current_utc`. This capability persists no business entity and moves no state machine on its own; it simply changes the instant that every subsequent derivation reads. That said, because derived values are recomputed on read, moving the clock forward can change a component's `ndt_status`, a certification's `status`, an incident's `notified_late` evaluation and an attraction's `operational_posture` the very next time any of them is read.

Timestamps supplied as input and timestamps returned in responses are ISO 8601 UTC with exactly three fractional-second digits, for example `2026-08-01T11:30:00.000Z`. Date-only fields — `service_date`, `effective_from_date`, `issued_date`, `compliance_deadline_date`, `deferred_until_date`, `needed_by_date`, `expected_availability_date`, `last_signed_off_service_date`, `window_start_date`, `window_end_date` and the `window_start_date` / `window_end_date` capacity-window bounds — are plain calendar dates in `YYYY-MM-DD` form. A malformed instant or date is refused with `ERR_INVALID_REQUEST`.

### 2.5. Record Identity, Audit Fields and Immutable Configuration Rows

Every resource this service persists carries an `id`, which is a server-minted UUID with no type prefix of any kind, and a `created_at`, which is the ISO 8601 UTC instant the row was created. Almost every resource additionally carries `updated_at`, the ISO 8601 UTC instant of the most recent mutation, and `version`, an integer that starts at 1 when the row is created and increments by exactly one on every mutation of that row. A mutation for this purpose includes changes to derived fields: when a checklist result is recorded and the parent inspection's counters move, the inspection's own `updated_at` refreshes and its `version` increments, because the inspection row genuinely changed.

There is exactly one exception. A **checklist line** is a configuration row that is immutable once written: it carries only `id` and `created_at`. It has no `updated_at`, no `version`, and no update endpoint. Nothing in the system ever mutates a checklist line after creation; a change to a checklist means authoring a new template revision.

### 2.6. The Validation Ladder

When a request violates more than one rule, exactly one error is returned, and which one is not a matter of implementation convenience. Checks are evaluated strictly in the ascending priority order below, and the first violated check supplies the response. This ladder is normative and is the single most consequential contract in this document.

1. **Authentication.** `X-User-Role` and `X-User-ID` are both present and non-blank — otherwise `ERR_UNAUTHENTICATED` (401).
2. **Authorisation.** `X-User-Role` names one of the six declared roles and that role appears among the target endpoint's authorised roles — otherwise `ERR_UNAUTHORIZED` (403).
3. **Path existence.** Every identifier embedded in the request path resolves to a live row, validated left to right. The error names the resource that was missing: `ERR_ATTRACTION_NOT_FOUND`, `ERR_COMPONENT_NOT_FOUND`, `ERR_TEMPLATE_NOT_FOUND`, `ERR_CHECKLIST_ITEM_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND`, `ERR_ITEM_RESULT_NOT_FOUND`, `ERR_BULLETIN_NOT_FOUND`, `ERR_BULLETIN_ACTION_NOT_FOUND`, `ERR_DOWNTIME_EVENT_NOT_FOUND`, `ERR_REQUISITION_NOT_FOUND`, `ERR_CERTIFICATION_NOT_FOUND`, `ERR_INCIDENT_NOT_FOUND`, `ERR_SHOP_BAY_NOT_FOUND` or `ERR_WORK_ORDER_NOT_FOUND`, each with HTTP 404.
4. **Body foreign-key existence.** Every foreign key supplied in the request body resolves to a live row, validated in the order the fields are declared for that endpoint in §4's companion narrative. The same 404 identifiers apply, drawn from `ERR_ATTRACTION_NOT_FOUND`, `ERR_COMPONENT_NOT_FOUND`, `ERR_TEMPLATE_NOT_FOUND`, `ERR_BULLETIN_NOT_FOUND`, `ERR_BULLETIN_ACTION_NOT_FOUND`, `ERR_DOWNTIME_EVENT_NOT_FOUND` and `ERR_SHOP_BAY_NOT_FOUND`.
5. **Request shape.** All required fields are present, enum values are recognised members of their declared sets, integers sit inside their declared ranges, dates and instants are well formed, `ended_at` is strictly later than `started_at`, `expires_at` is strictly later than `effective_from`, `window_end_date` is the same as or later than `window_start_date`, `compliance_deadline_date` is the same as or later than `issued_date`, `bulletin_ref` is unique across all bulletins, `sequence_no` does not repeat within its template, `supersedes_bulletin_id` does not name the bulletin being created, at most one of `downtime_event_id` and `bulletin_action_id` is supplied on a requisition, a supplied `downtime_event_id` or `bulletin_action_id` belongs to the same `attraction_id` as the requisition being created, and an `outcome` of `NA` is never recorded against a `SAFETY_CRITICAL` checklist line. Any violation yields `ERR_INVALID_REQUEST` (400).
6. **Stale-parent rejection.** The supplied `expected_attraction_version` or `expected_shop_bay_version` equals the current `version` of the named parent row — otherwise `ERR_STALE_ATTRACTION_VERSION` or `ERR_STALE_SHOP_BAY_VERSION` (412). See §2.7.
7. **Declared-transition check.** The target row is in a state from which the requested transition is declared. The error names the entity: `ERR_TEMPLATE_STATE_INVALID`, `ERR_INSPECTION_STATE_INVALID`, `ERR_BULLETIN_STATE_INVALID`, `ERR_ACTION_STATE_INVALID`, `ERR_DOWNTIME_STATE_INVALID`, `ERR_REQUISITION_STATE_INVALID`, `ERR_CERTIFICATION_STATE_INVALID`, `ERR_INCIDENT_STATE_INVALID` or `ERR_WORK_ORDER_STATE_INVALID`, each with HTTP 409. This priority level also carries one cross-entity gate: advancing an overhaul work order into `TEARDOWN` is refused with `ERR_INSPECTION_STATE_INVALID` when the attraction has a daily inspection for the current service date sitting in `PENDING_SIGN_OFF`.
8. `ERR_SAFETY_CRITICAL_ITEM_FAILED` (409) — sign-off is refused while the inspection's `blocking_item_count` is greater than zero.
9. `ERR_NDT_OVERDUE_SAFETY_CRITICAL` (409) — sign-off is refused while any component of the attraction whose `criticality` is `SAFETY_CRITICAL` derives an `ndt_status` of `OVERDUE`.
10. `ERR_REGULATORY_HOLD_ACTIVE` (409) — operations that would return an attraction to guest service are refused while the attraction's `regulatory_hold` is true. This guards exactly two operations: inspection sign-off, and logging ride cycles.
11. `ERR_SEGREGATION_OF_DUTIES` (403) — the signing `X-User-ID` must not already appear in the inspection's `recorded_by_user_ids`. Guards inspection sign-off only.
12. `ERR_COMPONENT_ATTRACTION_MISMATCH` (422) — a supplied component identifier names a component installed on a different attraction than the one the request targets. This guards three operations: creating an overhaul work order, diagnosing a downtime event, and appending a checklist line to a template.
13. `ERR_NO_ACTIVE_TEMPLATE` (409) — a daily inspection may only be opened for an attraction that has a template whose `status` is `ACTIVE`.
14. `ERR_PART_NOT_RECEIVED` (409) — verifying a fleet action requires its `required_part_received` to be true.
15. `ERR_NOTIFICATION_NOT_REQUIRED` (422) — regulator notification is only meaningful when the incident's `injury_severity` is `SERIOUS` or `FATAL`.
16. `ERR_REGULATOR_CLEARANCE_REQUIRED` (422) — clearing an incident that reached `REGULATOR_NOTIFIED` requires a non-empty `regulator_clearance_ref`.
17. `ERR_TEMPLATE_HAS_NO_ITEMS` (422) — a template may only be activated when its `item_count` is at least 1.
18. `ERR_ITEM_RESULTS_PENDING` (409) — submission is refused while `pending_item_count` is greater than zero.
19. `ERR_ESSENTIAL_FAIL_NOTE_REQUIRED` (422) — recording a `FAIL` on a line whose `severity_class` is `ESSENTIAL` requires a non-empty `note`.
20. `ERR_DUPLICATE_INSPECTION` (409) — at most one daily inspection may exist for any one pairing of `attraction_id` and `service_date`.
21. `ERR_DOWNTIME_ALREADY_OPEN` (409) — an attraction may hold at most one downtime event whose `status` is `OPEN`, `DIAGNOSED`, `AWAITING_PARTS` or `RESOLVED`.
22. `ERR_RECALL_NOT_DEFERRABLE` (409) — a fleet action belonging to a bulletin whose `severity` is `RECALL` may not be deferred.
23. `ERR_DOWNTIME_SPANS_SERVICE_DATES` (422) — the UTC calendar date of `ended_at` must equal the downtime event's pinned `service_date`.
24. `ERR_BAY_CAPACITY_CONFLICT` (409) — the buffered overhaul window must not land on a calendar day where the bay's existing work orders already occupy every concurrent slot. The arithmetic is spelled out in §3.9.
25. `ERR_CERTIFICATION_WINDOW_OVERLAP` (409) — a requested certification validity interval must not intersect an existing interval for the same operator on the same attraction for a positive duration. The interval semantics are spelled out in §3.7.
26. `ERR_PARTS_BUDGET_EXCEEDED` (402) — committing a requisition must not push the attraction's committed parts spend above its parts budget ceiling. Guards exactly two operations: reserving a requisition, and backordering one.

Two consequences of this ladder deserve emphasis. First, because the declared-transition check sits at priority 7 and the blocking-item gate at priority 8, an inspection that is not in `PENDING_SIGN_OFF` at all fails with `ERR_INSPECTION_STATE_INVALID` before `ERR_SAFETY_CRITICAL_ITEM_FAILED` is ever considered. Second, because the safety gates at priorities 8, 9, 10 and 11 are ordered among themselves, an inspection that simultaneously carries a blocking finding, an overdue safety-critical test, a regulatory hold and a self-signing caller reports `ERR_SAFETY_CRITICAL_ITEM_FAILED` — the blocking finding — and nothing else.

### 2.7. Stale-Parent Protection on Shared Records

Two write operations reach across into a record that other clients are also editing, and both require the client to prove it was looking at the current version of that shared parent. This is the system's only concurrency mechanism, and it is expressed purely as a stale-read check: the question is never whether two requests arrived close together, only whether the version the client echoed back still matches the version the server holds.

Activating an inspection template requires `expected_attraction_version` in the request body, carrying the `version` of the attraction as the client last read it. Activation legitimately retires whichever template revision is currently `ACTIVE` for that attraction, so a client working from a stale view of the attraction would silently supersede a revision it never saw. When `expected_attraction_version` does not equal the attraction's current `version`, the activation is refused with `ERR_STALE_ATTRACTION_VERSION` and HTTP 412. The write endpoint guarded by this rule is `POST /park-ops/inspection-templates/{id}/activate`.

Creating an overhaul work order requires `expected_shop_bay_version` in the request body, carrying the `version` of the shop bay as the client last read it. Another planner may have consumed a concurrent slot in that bay since the client read it, which invalidates the capacity arithmetic the client reasoned from. When `expected_shop_bay_version` does not equal the bay's current `version`, the booking is refused with `ERR_STALE_SHOP_BAY_VERSION` and HTTP 412. The write endpoint guarded by this rule is `POST /park-ops/overhaul-work-orders`.

Both fields are mandatory on their endpoints, not optional hints — omitting one is a request-shape failure at priority 5. No other endpoint in this service accepts a version field of any kind, and no other endpoint performs a stale-parent check.

### 2.8. Operational Posture: The Guest-Operations Gate

Every attraction carries an `operational_posture`, which is the single answer to "may this attraction carry guests right now". It is never set directly by any caller. It is derived, and it is recomputed at the end of every mutation that touches the attraction itself or any of its components, daily inspections, downtime events, incident reports or overhaul work orders, and it is re-derived after the logical clock moves. A recomputation that actually changes the posture is a genuine mutation of the attraction row in the sense of §2.5, so the attraction's own `updated_at` refreshes and its `version` increments by one even though no caller wrote the attraction directly and even when the row that triggered the recomputation was a child row — a newly opened downtime event, for instance, whether a technician opened it or the inspection cascade of §3.2 did. A recomputation that lands on the posture the attraction already held is not on its own such a mutation, and the re-derivation that follows a clock move advances neither `updated_at` nor `version`. Its value is one of `OPEN`, `CLOSED_PENDING_INSPECTION`, `DOWN`, `HOLD` or `OVERHAUL`, and a freshly registered attraction starts at `CLOSED_PENDING_INSPECTION`.

The derivation walks five clauses in this exact order and the first clause that matches wins:

1. `OVERHAUL` — if any overhaul work order of the attraction has a `status` of `TEARDOWN`, `INSPECTION` or `REBUILD`. This is the highest-precedence posture and outranks even a regulatory hold.
2. `HOLD` — if the attraction's `regulatory_hold` is true.
3. `DOWN` — if any of the following holds: the attraction has a downtime event whose `status` is `OPEN`, `DIAGNOSED`, `AWAITING_PARTS` or `RESOLVED`; or any component of the attraction whose `criticality` is `SAFETY_CRITICAL` derives an `ndt_status` of `OVERDUE`; or the attraction's daily inspection for the current service date has a `status` of `BLOCKED`.
4. `CLOSED_PENDING_INSPECTION` — if the attraction's `last_signed_off_service_date` is not the same as the logical clock's current UTC date.
5. `OPEN` — otherwise.

Note the asymmetry this precedence creates. A resolved-but-not-yet-closed downtime event still holds the attraction at `DOWN`, because `RESOLVED` is in the clause-3 set; only closing or voiding the event releases it. Conversely, a signed-off inspection alone does not open an attraction — it merely satisfies clause 4, and the attraction still reads `DOWN`, `HOLD` or `OVERHAUL` if any higher clause remains true.

### 2.9. Conserved Quantities: The Parts Budget and the Downtime Ledger

Two integer counters on the attraction are **conserved quantities**: they are defined as an aggregate over child rows, and every forward movement has an exactly compensating reverse movement, so that a forward-then-reverse pair restores the counter to its precise prior value for every row and in any order.

`parts_budget_committed_cents` is the sum, in whole cents, of `total_cost_cents` across every part requisition of that attraction whose `status` is `RESERVED`, `BACKORDERED` or `RECEIVED`. Requisitions in `REQUESTED` and `CANCELLED` are excluded. Reserving or backordering a requisition adds that requisition's `total_cost_cents` to the counter; cancelling a requisition that was `RESERVED` or `BACKORDERED` subtracts exactly that amount back out; cancelling one that was still `REQUESTED` moves the counter not at all, because nothing had been committed; and receiving a requisition moves the counter not at all either, because `RECEIVED` stays inside the committed set. The arithmetic is exact integer arithmetic on whole cents with no rounding anywhere.

`ytd_downtime_minutes` is the sum, in whole minutes, of `duration_minutes` across every downtime event of that attraction whose `status` is exactly `CLOSED`. Events in `OPEN`, `DIAGNOSED`, `AWAITING_PARTS`, `RESOLVED` and `VOIDED` are all excluded. Closing a resolved event adds its `duration_minutes` to the counter; voiding a closed event subtracts exactly the same number back out, returning the counter to its pre-close value. Resolving an event, by contrast, deliberately touches the counter not at all — the minute geometry is frozen at resolve time but the ledger only moves at close.

Two further counters are aggregates in the same spirit, recomputed rather than incrementally patched whenever their inputs move: `certified_operator_count` is the number of operator certifications of that attraction whose derived `status` is exactly `CERTIFIED` at the current logical clock instant, and `booked_order_count` on a shop bay is the number of overhaul work orders for that bay whose `status` is anything other than `RECOMMISSIONED`.

### 2.10. Numeric Precision and Rounding

Every rounding operation in this service is **round half up** — a value exactly on the midpoint rounds away from zero. Three precision regimes apply.

Money is whole cents throughout. `parts_budget_cents`, `parts_budget_committed_cents`, `unit_cost_cents`, `total_cost_cents`, `parts_subtotal_cents`, `base_total_cents`, `off_season_discount_cents`, `discounted_base_cents`, `expedite_fee_cents` and `estimated_total_cents` are all integers, and in the overhaul cost estimate every intermediate multiplication is rounded half up to a whole cent before the next step consumes it.

Capacity and score figures are decimal numbers carried to exactly 2 decimal places with round-half-up: `settled_guest_slots_lost`, `provisional_guest_slots_lost`, `divergence_guest_slots`, `fleet_aggregate_score`, `per_unit_max_score`, `divergence`, `escalation_factor` and `dispatch_readiness_index`. Where a formula names an intermediate that is explicitly described as unrounded, it stays unrounded inside the expression and only the stated output is rounded.

Minute and cycle counts are whole integers compared inclusively: `duration_minutes`, `peak_minutes`, `off_peak_minutes`, `ytd_downtime_minutes`, `mean_repair_minutes`, `cumulative_cycles`, `last_ndt_cycles`, `ndt_interval_cycles` and `ndt_interval_days`. Instants in this domain are always minute-aligned, so minute geometry never produces a fractional minute.

### 2.11. Cascades and Derived-Field Reconciliation

Many operations in this system move more than one row. When a technician records a single failing checklist line, the finding can propagate through four hops — the bound component's condition, the inspection's counters and status, the attraction's posture, and finally a newly opened downtime event. When a safety officer places a ride hold, the hold propagates through the attraction's `regulatory_hold`, its `operational_posture`, every certified operator's certification, and the attraction's `certified_operator_count`. Each hop is a genuine mutation of the row it touches: that row's `updated_at` refreshes and its `version` increments, exactly as if it had been written directly. Where a cascade creates a row, that row is created with its normal defaults and its own fresh `id`, `created_at` and `version`.

Cascades are also **compensating** wherever the domain has a reverse gesture. Clearing an incident undoes precisely the certifications that incident suspended and no others. Re-recording the last blocking checklist line as a pass walks the inspection back out of `BLOCKED`. Voiding a closed downtime event returns the minutes ledger to its exact pre-close value. What a compensating cascade never does is undo more than it did: clearing an incident does not reinstate a certification that some other incident suspended, and re-recording a blocking line as a pass does not close the downtime event that the original failure opened.

Every derived field described in this document is recomputed from its current inputs at the moment it is read, not cached from the moment it was written. Reading a single attraction re-derives every computed field on it against the current logical clock before the response is built; reading a component re-derives its `ndt_status` against the attraction's current cycle count and the clock; reading a certification re-derives its `status`.

## 3. Business Logic & Workflows

### 3.1. Establishing the Fleet: Attractions, Components and Checklist Revisions

A `ParkOpsAdmin` registers an attraction into the maintenance system of record by supplying its public `name`, the `park_area` it sits in — one of `FRONTIER`, `LAGOON`, `SKYLINE` or `KIDS_COVE` — the `manufacturer` that built it, the manufacturer's `model_code`, and its thrill classification `ride_class`, which is one of `KIDDIE`, `FAMILY`, `THRILL` or `WATER`. Three operating numbers come with it: `theoretical_hourly_capacity`, the number of guests the attraction carries per operating hour at design throughput, which must be at least 1; `min_operators_required`, the number of operators needed to dispatch, also at least 1; and `parts_budget_cents`, the season parts spending ceiling for this unit in whole cents, which must not be negative. A fourth number, `mean_repair_minutes`, is optional and represents the historical mean repair duration in whole minutes; when it is omitted it defaults to 120, and when supplied it must be at least 1. The `manufacturer` and `model_code` strings matter far beyond labelling: together they are the fleet-matching key that decides which units a manufacturer bulletin fans out to.

Registration leaves the attraction's derived state at a clean baseline. `operational_posture` initialises to `CLOSED_PENDING_INSPECTION`; `cumulative_cycles`, `parts_budget_committed_cents`, `ytd_downtime_minutes` and `certified_operator_count` all initialise to 0; `regulatory_hold` initialises to false; and `active_template_id` and `last_signed_off_service_date` both begin as null. None of those fields is ever writable by a caller — each is either an aggregate over child rows or a stamp the server sets during a workflow.

Ride cycles are the wear metric that drives half of the nondestructive-testing regime, and logging them is the one write operation a `RideOperator` shares with a `MaintenanceTechnician`. The caller supplies the `service_date` the cycles were run on and `cycles_added`, the count to add. The count is added to the attraction's `cumulative_cycles`, which is the only field this operation writes and the only writer that field has — there is no other route to advancing a component across its cycle interval. Every component of the attraction then has its `ndt_status` re-derived, and the attraction's `operational_posture` is recomputed, which means a component that crosses into `OVERDUE` on this very call can force the attraction to `DOWN` before the response is even built. While the attraction's `regulatory_hold` is true, cycle logging is refused with `ERR_REGULATORY_HOLD_ACTIVE` — a held ride does not accumulate wear because a held ride does not run.

Components are installed onto an attraction by a `ParkOpsAdmin`, who supplies the `attraction_id` the part sits on, the component's `name` as printed in the manufacturer manual, its `component_type` — one of `BRAKE`, `LIFT_CHAIN`, `RESTRAINT_ACTUATOR`, `GEARBOX`, `AXLE` or `CONTROL_PLC` — its safety classification `criticality`, which is one of `SAFETY_CRITICAL`, `ESSENTIAL` or `NON_CRITICAL`, and the manufacturer's two testing intervals: `ndt_interval_cycles` in ride cycles and `ndt_interval_days` in calendar days, each at least 1. Installation seeds the testing baselines rather than leaving them empty: `last_ndt_at` is set to the current logical clock instant, `last_ndt_cycles` is set to the attraction's `cumulative_cycles` as observed at that moment, `ndt_status` starts at `CURRENT`, `condition_flag` starts at `OK`, and `last_ndt_method` starts as null because no test has been run yet.

A component's `ndt_status` is derived, never stored by a caller, and it is recomputed after ride cycles are logged, after a nondestructive test is recorded, after the logical clock moves, and on every read of the component. Two elapsed metrics feed it. The cycles elapsed since the last test is the attraction's `cumulative_cycles` minus the component's `last_ndt_cycles`. The days elapsed since the last test is the whole number of complete 24-hour days between `last_ndt_at` and the current logical clock instant, discarding any part-day remainder. The component is **due by cycles** when the cycles elapsed is greater than or equal to `ndt_interval_cycles`, and **due by days** when the days elapsed is greater than or equal to `ndt_interval_days`. It is **overdue by cycles** when the cycles elapsed is greater than or equal to `ndt_interval_cycles` multiplied by a grace factor of 1.20 and rounded up to a whole number, and **overdue by days** when the days elapsed is greater than or equal to `ndt_interval_days` multiplied by that same 1.20 grace factor and rounded up to a whole number. If either overdue condition holds, `ndt_status` is `OVERDUE`; otherwise, if either due condition holds, it is `DUE`; otherwise it is `CURRENT`. Both comparisons are inclusive, so a cycles-elapsed figure exactly equal to `ndt_interval_cycles` is already `DUE` rather than still `CURRENT`.

Recording a nondestructive test is reserved to a `QualifiedInspector`, who supplies the `ndt_method` used — one of `MAGNETIC_PARTICLE`, `ULTRASONIC`, `DYE_PENETRANT`, `EDDY_CURRENT` or `VISUAL` — together with the `result`, which is either `PASS` or `FAIL`. The record resets both interval baselines at once: `last_ndt_method` becomes the supplied `ndt_method`, `last_ndt_at` becomes the current logical clock instant, and `last_ndt_cycles` becomes the attraction's `cumulative_cycles` as observed now, so `ndt_status` necessarily returns to `CURRENT`. The `result` decides the component's health flag: a `PASS` returns `condition_flag` to `OK`, while a `FAIL` sets it to `FAILED`. The attraction's `operational_posture` is recomputed afterwards, which is how a test that clears a previously overdue safety-critical component can release the attraction from `DOWN`.

The pre-opening checklist itself lives in versioned template revisions, also authored by a `ParkOpsAdmin`. Opening a revision takes the `attraction_id` it belongs to and an `effective_from_date`, the first service date on which a daily inspection may pin this revision. The server assigns the `revision` number itself: 1 for an attraction's first template, and otherwise the greatest existing `revision` for that attraction plus one. A new revision opens with `status` `DRAFT`, an `item_count` of 0 and a null `activated_at`.

Checklist lines are appended to a revision one at a time, and only while that revision is still `DRAFT` — appending to a revision that is `ACTIVE` or `SUPERSEDED` is refused with `ERR_TEMPLATE_STATE_INVALID`. Each line carries a `sequence_no` giving its walk order within the template, which must be at least 1 and must not repeat within that template; a non-empty `description` of the check the technician performs; a `severity_class` of `SAFETY_CRITICAL`, `ESSENTIAL` or `ADVISORY`; an optional `component_id` naming the component this line inspects; and an optional documentation flag `requires_photo`, which defaults to false when omitted and is carried onto the result row without being enforced by the API. A supplied `component_id` must name a component installed on the same attraction that owns the template, and one that belongs to a different attraction is refused with `ERR_COMPONENT_ATTRACTION_MISMATCH`. Appending a line sets the row's `template_id` from the revision being appended to and increments that revision's `item_count` by one. Checklist lines are the immutable configuration rows described in §2.5.

The `severity_class` on a line is what gives it teeth downstream, and the three levels behave very differently: a `SAFETY_CRITICAL` line that fails blocks the whole inspection, an `ESSENTIAL` line that fails demands a written note but still permits sign-off, and an `ADVISORY` line that fails is purely informational.

Activation is the moment a revision becomes the live checklist, and it is performed by a `ParkOpsAdmin`. The revision must still be `DRAFT` — activating one that is already `ACTIVE` or `SUPERSEDED` is refused with `ERR_TEMPLATE_STATE_INVALID` — and it must carry at least one checklist line, since activating an empty revision is refused with `ERR_TEMPLATE_HAS_NO_ITEMS`. The request must also carry `expected_attraction_version` matching the attraction's current `version`, per §2.7. When those gates pass, the revision moves `DRAFT` → `ACTIVE`, its `activated_at` is stamped with the current logical clock instant, whichever revision of that same attraction was previously `ACTIVE` — there is at most one — moves `ACTIVE` → `SUPERSEDED` and is no longer pointed at by the attraction, the attraction's `active_template_id` is repointed at the newly activated revision, the attraction's `version` increments by one, and the attraction's `operational_posture` is recomputed. `SUPERSEDED` is terminal for a template revision. Crucially, activation does not reach backwards: daily inspections that already pinned an earlier revision keep the revision they pinned.

### 3.2. The Pre-Opening Inspection Walk

A `MaintenanceTechnician` opens the day's inspection by naming the `attraction_id` and the `service_date` the walk covers. Three gates apply before anything is created. The attraction must have an `active_template_id` that is not null, since an attraction with no activated checklist cannot be inspected — that failure reports `ERR_NO_ACTIVE_TEMPLATE`. No inspection may already exist for that same combination of `attraction_id` and `service_date`, since exactly one pre-opening walk exists per attraction per operating date — a repeat reports `ERR_DUPLICATE_INSPECTION`. And the `service_date` must be the same as or later than the `effective_from_date` of the template revision about to be pinned.

Opening the inspection pins the checklist in place so that later template activations cannot retroactively change what was walked: `template_id` is set to the attraction's current `active_template_id` and `template_revision` is snapshotted from that revision's `revision` number, and neither is ever re-pointed afterwards. The server then fans out the checklist: one result row is created for every checklist line of the pinned revision, each starting with an `outcome` of `PENDING`, each carrying `inspection_id` pointing back at the inspection and `checklist_item_id` pointing at the line it answers, and each taking a snapshot of that line's `severity_class` into its own `severity_class` field so that later template edits cannot retro-change blocking semantics. The inspection's counters are initialised accordingly: `pending_item_count` is set to the pinned revision's `item_count`, while `blocking_item_count` and `essential_fail_count` both start at 0. The badge of the opening technician is stored in `opened_by_user_id`, and `recorded_by_user_ids` starts as an empty list. A freshly opened inspection has `status` `IN_PROGRESS`, and its `signed_off_by_user_id`, `signed_off_at` and `rejection_reason` are all null with `rework_round` at 0.

Because the fanned-out result rows are created by the server rather than by the client, their identifiers are not in the create response; the way to discover them is the result list filtered by `inspection_id`, as described in §2.3.

Walking the checklist means recording each result row's outcome, one row at a time, and only a `MaintenanceTechnician` may do it. The request carries the `outcome` being recorded — one of `PASS`, `FAIL` or `NA` — and an optional `note` holding the free-text finding. Recording sets the row's `recorded_by_user_id` to the acting badge and its `recorded_at` to the current logical clock instant, appends that badge to the parent inspection's `recorded_by_user_ids` if it is not already present, and recomputes the inspection's `pending_item_count`, `blocking_item_count` and `essential_fail_count`. A result row that is still `PENDING` carries a null `recorded_by_user_id` and a null `recorded_at`.

Results may be recorded, and re-recorded, only while the parent inspection is in an accepting state, and the accepting set differs by direction. Recording a `PENDING` row as `PASS`, `FAIL` or `NA` requires the parent inspection to be `IN_PROGRESS` or `BLOCKED`. Re-recording a `FAIL` row as `PASS` likewise requires the parent to be `IN_PROGRESS` or `BLOCKED`. Re-recording a `PASS` row as `FAIL`, however, is additionally permitted while the parent is `PENDING_SIGN_OFF`. Any attempt to record against an inspection that is `REJECTED` or `SIGNED_OFF`, or to record a `PASS` against a `PENDING_SIGN_OFF` inspection, is refused with `ERR_INSPECTION_STATE_INVALID`.

The three outcomes move the counters differently, and the differences are exact. Recording a `PENDING` row as `PASS` decrements `pending_item_count` by one. Recording a `PENDING` row as `NA` also decrements `pending_item_count` by one — but `NA` may never be recorded against a line whose `severity_class` is `SAFETY_CRITICAL`, because a safety-critical check can never be waived, and attempting it is a request-shape violation reported as `ERR_INVALID_REQUEST`. Recording a `PENDING` row as `FAIL` increments `essential_fail_count` by one when that row's `severity_class` is `ESSENTIAL`, and increments `blocking_item_count` by one when it is `SAFETY_CRITICAL`. A `FAIL` on a line whose `severity_class` is `ESSENTIAL` requires a non-empty `note`; omitting it is refused with `ERR_ESSENTIAL_FAIL_NOTE_REQUIRED`.

Re-recording is symmetric with recording, counter for counter. Re-recording a `FAIL` row as `PASS` sets `recorded_by_user_id` and `recorded_at` to the re-recording technician and instant, decrements `essential_fail_count` when that row's `severity_class` is `ESSENTIAL` and decrements `blocking_item_count` when it is `SAFETY_CRITICAL`, and leaves `pending_item_count` untouched, because a failed row was not a pending row. Re-recording a `PASS` row as `FAIL` moves the same two counters in the opposite direction — incrementing `essential_fail_count` for an `ESSENTIAL` line and `blocking_item_count` for a `SAFETY_CRITICAL` one — and it too demands a non-empty `note` when the line is `ESSENTIAL`, on pain of `ERR_ESSENTIAL_FAIL_NOTE_REQUIRED`.

A failing result does not stop at the result row. Consider a technician who records `FAIL` on a line bound to a specific component. **Hop one** of the cascade sets that component's `condition_flag` to `SUSPECT`, and this happens for any `FAIL` on any line whose `component_id` is non-null, regardless of `severity_class`. When the failing line's `severity_class` is `SAFETY_CRITICAL` and the parent inspection is `IN_PROGRESS`, three more hops follow. **Hop two** increments `blocking_item_count` and moves the inspection `IN_PROGRESS` → `BLOCKED`. **Hop three** recomputes the attraction's `operational_posture`, which now reads `DOWN` because clause 3 of §2.8 sees a blocked inspection for the current service date. **Hop four** opens a downtime event on the attraction automatically: the server creates one with `cause_category` `INSPECTION_FAIL`, `auto_opened` set to true, `started_at` set to the current logical clock instant and `status` `OPEN` — but only if the attraction does not already hold a downtime event whose `status` is `OPEN`, `DIAGNOSED`, `AWAITING_PARTS` or `RESOLVED`, in which case hop four is skipped and the existing event stands.

There is one important asymmetry in that cascade. A `PASS` → `FAIL` re-record against an inspection that is already `PENDING_SIGN_OFF` runs hop one and moves `blocking_item_count` and `essential_fail_count`, but it does **not** move the inspection's `status` — `PENDING_SIGN_OFF` has no declared edge into `BLOCKED`, so the inspection stays `PENDING_SIGN_OFF` while carrying a `blocking_item_count` greater than zero. This is the only route to a `PENDING_SIGN_OFF` inspection with a live blocking finding, and it is precisely why the blocking-item gate at ladder priority 8 rather than the declared-transition check at priority 7 is the operative refusal at sign-off.

The cycle also runs backwards. Re-recording the last remaining blocking line as `PASS` — that is, a re-record on a `SAFETY_CRITICAL` row whose current `outcome` is `FAIL`, against an inspection currently `BLOCKED`, where `blocking_item_count` would reach 0 as a result — decrements `blocking_item_count` to 0 and returns the inspection `BLOCKED` → `IN_PROGRESS`. The bound component's `condition_flag` is cleared back to `OK`, but only when no other failed result row still references that component. The attraction's `operational_posture` is recomputed, and here the domain is deliberately conservative: the downtime event that hop four opened is **not** closed automatically, so the attraction remains `DOWN` until a manager closes or voids that event.

### 3.3. Sign-Off, Rejection and the Rework Cycle

Submission is the technician's hand-off. A `MaintenanceTechnician` submits an inspection that is `IN_PROGRESS`, moving it `IN_PROGRESS` → `PENDING_SIGN_OFF`, and the operation touches no field on any other entity — only the inspection's own `updated_at` and `version` advance. Submission is refused while any line remains unanswered: a `pending_item_count` greater than zero yields `ERR_ITEM_RESULTS_PENDING`. Note that a blocked inspection cannot be submitted at all, because `BLOCKED` is not `IN_PROGRESS`; that attempt reports `ERR_INSPECTION_STATE_INVALID`.

Sign-off is the statutory act, reserved to a `QualifiedInspector`, and it is the most heavily gated operation in the service. The inspection must be `PENDING_SIGN_OFF`. Four further gates then apply, and they are evaluated in this order, so the first one that closes is the one the caller hears about:

1. The inspection's `blocking_item_count` must be zero. A live safety-critical failure yields `ERR_SAFETY_CRITICAL_ITEM_FAILED`.
2. No component of the attraction whose `criticality` is `SAFETY_CRITICAL` may derive an `ndt_status` of `OVERDUE`. One that does yields `ERR_NDT_OVERDUE_SAFETY_CRITICAL`. This gate reaches across into the component inventory and the logical clock — an inspection that was signable an hour of logical time ago can become unsignable purely because the clock advanced past a testing interval.
3. The attraction's `regulatory_hold` must be false. A live hold yields `ERR_REGULATORY_HOLD_ACTIVE`. This gate reaches across into the incident register, because `regulatory_hold` is true exactly while the attraction has an incident report in `RIDE_HELD`, `UNDER_INVESTIGATION` or `REGULATOR_NOTIFIED`.
4. The signing badge in `X-User-ID` must not appear anywhere in the inspection's `recorded_by_user_ids`. A signer who recorded any result on this walk is refused with `ERR_SEGREGATION_OF_DUTIES`. This is structural segregation of duties: whoever recorded a finding can never be the person who certifies it, no matter how many rework rounds intervene.

When all four gates pass, the inspection moves `PENDING_SIGN_OFF` → `SIGNED_OFF`, which is terminal. Its `signed_off_by_user_id` is stamped with the signing badge and its `signed_off_at` with the current logical clock instant. The attraction's `last_signed_off_service_date` is set to this inspection's `service_date`, and the attraction's `operational_posture` is recomputed — which is how an attraction leaves `CLOSED_PENDING_INSPECTION` for `OPEN`, provided nothing higher in the posture precedence still gates it.

Rejection is the same inspector's other option. Rejecting an inspection that is `PENDING_SIGN_OFF` moves it `PENDING_SIGN_OFF` → `REJECTED` and stores the supplied `rejection_reason`, which is retained across later reopens for audit purposes. The attraction's `operational_posture` is recomputed, and because the attraction now has no signed-off inspection for the service date it stays at `CLOSED_PENDING_INSPECTION` or lower.

Reopening closes the loop. A `MaintenanceTechnician` reopens an inspection that is `REJECTED`, moving it `REJECTED` → `IN_PROGRESS` and completing the cycle `IN_PROGRESS` → `PENDING_SIGN_OFF` → `REJECTED` → `IN_PROGRESS`. Reopening increments `rework_round` by one. Every result row of that inspection whose `outcome` is `FAIL` is reset to `PENDING` with its `recorded_by_user_id` and `recorded_at` cleared, and `pending_item_count`, `blocking_item_count` and `essential_fail_count` are then recomputed from the reset rows — so a reopened inspection with two prior failures returns with those two lines pending again and both fail counters back at zero. Passed and `NA` rows are left exactly as they were. What reopening deliberately does **not** clear is `recorded_by_user_ids`: the segregation-of-duties set survives every rework round, so a technician who recorded a finding in round zero is still barred from signing in round three.

### 3.4. Downtime Events, Root Cause and Capacity Impact

When an attraction stops carrying guests, a `MaintenanceTechnician` opens a downtime event against it, supplying the `attraction_id`, the `started_at` instant at which guest carriage stopped, and the reported `cause_category`, which is one of `MECHANICAL`, `ELECTRICAL`, `GUEST_ILLNESS`, `WEATHER`, `INSPECTION_FAIL` or `OPERATOR`. An attraction may hold only one live downtime event at a time: if it already has one whose `status` is `OPEN`, `DIAGNOSED`, `AWAITING_PARTS` or `RESOLVED`, the new report is refused with `ERR_DOWNTIME_ALREADY_OPEN`. A newly opened event starts at `status` `OPEN` with `auto_opened` false, and the server pins its `service_date` to the UTC calendar date of `started_at` — that pinned date, not the event's creation timestamp, is the bucketing key every capacity-impact window uses. Opening an event recomputes the attraction's `operational_posture` to `DOWN`. The four minute-and-capacity fields — `duration_minutes`, `peak_minutes`, `off_peak_minutes` and `settled_guest_slots_lost` — stay null until the event is resolved, along with `ended_at`, `root_cause_code`, `failed_component_id` and `void_reason`.

The same event shape is also created by the server as hop four of the inspection cascade described in §3.2; those rows are distinguishable by an `auto_opened` value of true and a `cause_category` of `INSPECTION_FAIL`, and because the server minted them their identifiers are discoverable only through the downtime list filtered by `attraction_id` or `auto_opened`.

Diagnosis is the root-cause step, again performed by a `MaintenanceTechnician`, and it moves an event `OPEN` → `DIAGNOSED`. The request carries a `root_cause_code` and an optional `failed_component_id` naming the component identified as root cause. Both are stored on the event. When a `failed_component_id` is supplied, that component's `condition_flag` becomes `FAILED` — a stronger statement than the `SUSPECT` flag an inspection failure raises. A supplied `failed_component_id` must name a component installed on the same attraction the event belongs to; one installed elsewhere is refused with `ERR_COMPONENT_ATTRACTION_MISMATCH`.

Waiting on a part is modelled as a cycle out of and back into `DIAGNOSED`, and no caller drives it directly. Backordering a requisition linked to a `DIAGNOSED` event moves that event `DIAGNOSED` → `AWAITING_PARTS`; the attraction's posture stays `DOWN` and the event is excluded from the settled capacity picture until it is eventually closed. Receiving that part, or cancelling the backordered requisition, moves the event `AWAITING_PARTS` → `DIAGNOSED` again, changing no other entity. That round trip may repeat any number of times.

Resolution freezes the arithmetic. A `MaintenanceTechnician` resolves an event that is `DIAGNOSED` by supplying the `ended_at` instant at which service resumed, moving the event `DIAGNOSED` → `RESOLVED`. An event sitting in `AWAITING_PARTS` must return to `DIAGNOSED` before resolution is permitted at all; attempting to resolve from `AWAITING_PARTS` reports `ERR_DOWNTIME_STATE_INVALID`. The supplied `ended_at` must be strictly later than `started_at`, and its UTC calendar date must equal the event's pinned `service_date` — a repair that spans midnight must be recorded as two events, and attempting to resolve across the date boundary is refused with `ERR_DOWNTIME_SPANS_SERVICE_DATES`. Resolution computes `duration_minutes`, `peak_minutes`, `off_peak_minutes` and `settled_guest_slots_lost`, and it deliberately does not touch the attraction's `ytd_downtime_minutes` — the minutes ledger moves only at close.

Closing is the manager's reporting sign-off. A `MaintenanceManager` closes an event that is `RESOLVED`, moving it `RESOLVED` → `CLOSED`, adding that event's `duration_minutes` to the attraction's `ytd_downtime_minutes`, and recomputing the attraction's `operational_posture` — which is the moment the attraction can finally leave `DOWN`, provided nothing else gates it. Voiding is the compensating gesture for an event logged in error: a `MaintenanceManager` voids an event that is `CLOSED`, moving it `CLOSED` → `VOIDED`, storing the supplied `void_reason`, subtracting exactly that same `duration_minutes` back out of `ytd_downtime_minutes` so the counter returns to its precise pre-close value, removing the event from the capacity-impact input set for both variants, and recomputing the attraction's posture. `VOIDED` is terminal.

**Capacity impact** is a computed read available to every role, and it reports what an attraction's downtime cost the park in guest-carrying slots across an inclusive service-date window. The caller may supply `window_start_date` and `window_end_date`; either that is omitted defaults to the logical clock's current UTC date, so the unparameterised call reports today. The response echoes the `attraction_id`, the `window_start_date` and `window_end_date` actually used, an `event_count`, and three figures: `settled_guest_slots_lost`, `provisional_guest_slots_lost` and `divergence_guest_slots`. Nothing is persisted by this read.

Both figures are computed from the *same* set of events, and that set is every downtime event of the attraction whose `service_date` falls inside the window with both bounds inclusive and whose `status` is `RESOLVED`, `CLOSED`, `OPEN`, `DIAGNOSED` or `AWAITING_PARTS`. Events whose `status` is `VOIDED` are excluded from both figures. `event_count` is the number of events in that set. Where the settled summation needs a deterministic order it processes events by `service_date` ascending, then `started_at` ascending, then `created_at` ascending; no identifier ever participates in that ordering.

The per-event geometry both figures share works like this. Each event's **occupancy interval** runs from its `started_at` up to but not including its `ended_at`. Each event's **peak window** runs from 11:00 UTC on its `service_date` up to but not including 17:00 UTC on that same date — a six-hour band across the middle of the operating day. The event's `peak_minutes` is the whole number of minutes in the intersection of its occupancy interval with its peak window; its `duration_minutes` is the whole number of minutes in its occupancy interval; and its `off_peak_minutes` is `duration_minutes` less `peak_minutes`. Its **weighted lost hours** are its `peak_minutes` divided by 60 and multiplied by the peak capacity weight of 1.00, plus its `off_peak_minutes` divided by 60 and multiplied by the off-peak capacity weight of 0.55 — off-peak downtime is charged at a little over half the guest-loss rate of peak downtime.

The **settled** figure is the books-closed number park operations reports after each event has been resolved, and it rounds per event before it sums. For one event, the settled loss is the attraction's `theoretical_hourly_capacity` multiplied by that event's weighted lost hours, rounded half up to 2 decimal places; that per-event value is exactly what is stamped onto the event's own `settled_guest_slots_lost` field at resolution. The window's `settled_guest_slots_lost` is then the sum of those already-rounded per-event values, rounded half up to 2 decimal places once more. The settled figure never projects: an event whose `ended_at` is still null — anything in `OPEN`, `DIAGNOSED` or `AWAITING_PARTS` — contributes zero to it.

The **provisional** figure is the forward-looking number a duty manager reads mid-day, and it differs from the settled figure in three specific ways. First, it aggregates the raw geometry before rounding: it sums `peak_minutes` across every event in the set and separately sums `off_peak_minutes` across every event in the set, then computes the attraction's `theoretical_hourly_capacity` multiplied by the quantity given by the summed peak minutes divided by 60 times the peak weight of 1.00 plus the summed off-peak minutes divided by 60 times the off-peak weight of 0.55, and rounds that whole product half up to 2 decimal places exactly once. Second, it applies a recovery credit: the rounded raw figure is multiplied by 0.85 — that is, one less the 15 percent recovery credit the park assumes it will claw back through re-rides and extended hours — and the product is rounded half up to 2 decimal places again to give `provisional_guest_slots_lost`. Third, it projects still-open downtime rather than ignoring it: for any event whose `status` is `OPEN`, `DIAGNOSED` or `AWAITING_PARTS` and whose `ended_at` is null, the provisional figure substitutes a projected end instant equal to that event's `started_at` plus the attraction's `mean_repair_minutes` in minutes, clamped so that the projected end never crosses midnight UTC at the end of the event's `service_date`.

`divergence_guest_slots` is the window's `settled_guest_slots_lost` less its `provisional_guest_slots_lost`, rounded half up to 2 decimal places; it may legitimately be negative when open events dominate the window. When the event set is empty, all three figures are 0.00.

### 3.5. Parts Requisitions and the Season Parts Budget

A `MaintenanceTechnician` raises a requisition by supplying the `attraction_id` whose budget it will commit against, the manufacturer's `part_number`, the `quantity` of units needed, which must be at least 1, the `unit_cost_cents` price per unit in whole cents, which must not be negative, and the `needed_by_date` on which the part must be on site. Two optional links express the reason for the part, and they are mutually exclusive: `downtime_event_id` attaches the requisition to a downtime repair, `bulletin_action_id` attaches it to a fleet corrective action, and a requisition may carry one of them or neither. Supplying both on the same request is refused with `ERR_INVALID_REQUEST`, and so is supplying a `downtime_event_id` or `bulletin_action_id` that belongs to a different attraction than the requisition's own `attraction_id`. Creation computes `total_cost_cents` as the `quantity` multiplied by the `unit_cost_cents`, in whole cents, and leaves the requisition at `status` `REQUESTED` with `expected_availability_date` and `cancel_reason` both null. Nothing is committed against the budget while a requisition is merely `REQUESTED`.

Commitment is the manager's decision, and it takes one of two forms with identical fiscal consequences. Reserving a requisition that is `REQUESTED` moves it `REQUESTED` → `RESERVED` and adds its `total_cost_cents` to the attraction's `parts_budget_committed_cents`. Backordering a requisition that is `REQUESTED` moves it `REQUESTED` → `BACKORDERED`, stores the vendor's promise date in `expected_availability_date`, and adds the same `total_cost_cents` to `parts_budget_committed_cents`. Both are refused under exactly the same fiscal ceiling: if the attraction's current `parts_budget_committed_cents` plus this requisition's `total_cost_cents` would come to more than the attraction's `parts_budget_cents`, the commitment is refused with `ERR_PARTS_BUDGET_EXCEEDED` and HTTP 402. Equality is permitted — a commitment that lands the committed total exactly on the ceiling succeeds. Backordering carries one cross-entity consequence that reserving does not: when the requisition names a `downtime_event_id` whose event is currently `DIAGNOSED`, that event moves `DIAGNOSED` → `AWAITING_PARTS`.

Receiving brings the part into the shop, and it is the technician's step rather than the manager's. A requisition that is `RESERVED` or `BACKORDERED` moves to `RECEIVED`, which is terminal. The committed budget does not change, because `RECEIVED` stays inside the committed set — this is the one status transition in the requisition lifecycle that moves money not at all despite crossing a boundary. Receiving has two cross-entity effects. When the requisition names a `bulletin_action_id`, that fleet action's `required_part_received` becomes true, which is what unlocks its verification. And when the requisition names a `downtime_event_id` whose event is currently `AWAITING_PARTS`, that event moves `AWAITING_PARTS` → `DIAGNOSED`, freeing the repair to be resolved.

Cancellation is the compensating leg, and it is deliberately status-sensitive so that it releases exactly what was committed and nothing more. A `MaintenanceManager` may cancel a requisition whose `status` is `REQUESTED`, `RESERVED` or `BACKORDERED`, supplying a `cancel_reason` that is stored on the row; cancelling one that is already `RECEIVED` or `CANCELLED` is refused with `ERR_REQUISITION_STATE_INVALID`, and `CANCELLED` is terminal. Cancelling a `REQUESTED` requisition changes no ledger at all, because nothing had been committed. Cancelling a `RESERVED` or `BACKORDERED` requisition subtracts exactly its `total_cost_cents` back out of the attraction's `parts_budget_committed_cents`, restoring the counter to its precise pre-commitment value. Cancelling a `BACKORDERED` requisition additionally returns a linked `AWAITING_PARTS` downtime event to `DIAGNOSED`, on the reasoning that a cancelled backorder is no longer a reason to wait.

### 3.6. Manufacturer Bulletins and Fleet-Wide Corrective Action

Manufacturers issue service bulletins and recalls against a model, not against an individual unit, so this service models a bulletin as a fleet-wide instrument that fans out into one action per matching unit. A `ParkOpsAdmin` publishes one by supplying the manufacturer's `bulletin_ref`, which must be non-empty and unique across every bulletin the park holds; the `manufacturer` that issued it; the affected `model_code`; the `severity`, which is one of `ADVISORY`, `MANDATORY` or `RECALL`; the `issued_date` the manufacturer released it; and the `compliance_deadline_date` by which every fleet action must be verified, which must be the same as or later than `issued_date`. An optional `supersedes_bulletin_id` names an earlier bulletin this one replaces, forming a self-referential chain; a bulletin may not name itself, and doing so is refused with `ERR_INVALID_REQUEST`. Publication leaves the bulletin at `status` `ISSUED` with `action_total_count` and `action_verified_count` both 0 and `acknowledged_at` and `acknowledged_by_user_id` both null. No fleet action exists yet — publication alone creates nothing downstream.

Naming an earlier bulletin in `supersedes_bulletin_id` retires it immediately. The named bulletin, if its `status` is `ISSUED` or `ACKNOWLEDGED`, moves to `SUPERSEDED`, which is terminal for a bulletin. Every fleet action belonging to that retired bulletin whose `status` is `PENDING`, `IN_WORK` or `DEFERRED` moves to `CANCELLED`, and the retired bulletin's `action_total_count` is then recomputed with those cancelled rows excluded — which, when every outstanding action was cancelled, drives that count to zero.

Acknowledgement is the `MaintenanceManager`'s act and the moment the fleet work is actually created. A bulletin that is `ISSUED` moves `ISSUED` → `ACKNOWLEDGED`; acknowledging one that is already `ACKNOWLEDGED`, `COMPLETED` or `SUPERSEDED` is refused with `ERR_BULLETIN_STATE_INVALID`. Acknowledgement stamps `acknowledged_at` with the current logical clock instant and `acknowledged_by_user_id` with the acting badge, and then fans out: the server creates one fleet action with `status` `PENDING` for **every** attraction whose `manufacturer` equals the bulletin's `manufacturer` and whose `model_code` equals the bulletin's `model_code` — both must match — creating them in order of the attractions' `created_at` ascending. Each created action carries `bulletin_id` pointing at the bulletin and `attraction_id` pointing at the fleet unit, with `deferral_reason`, `deferred_until_date`, `verified_by_user_id` and `verified_at` all null. The bulletin's `action_total_count` is set to the number of actions created and its `action_verified_count` to 0. Since these action rows are server-minted, their identifiers are found through the fleet-action list filtered by `bulletin_id` or `attraction_id`.

The `required_part_received` flag on a fleet action deserves its own sentence, because its default is counter-intuitive: it reads true when at least one part requisition naming this action has reached `RECEIVED`, **and also** when no part requisition references this action at all. An action that needs no parts is therefore ready to verify from the moment it is created, while an action with an outstanding requisition is not.

Working an action is a two-step affair split across two roles. A `MaintenanceTechnician` starts an action that is `PENDING`, moving it `PENDING` → `IN_WORK`; the start additionally requires the parent bulletin's `status` to be `ACKNOWLEDGED`, and a start against a non-`PENDING` action or a non-acknowledged parent is refused with `ERR_ACTION_STATE_INVALID`. Starting changes nothing on any other entity. A `QualifiedInspector` then verifies an action that is `IN_WORK`, moving it `IN_WORK` → `VERIFIED`, which is terminal. Verification requires the action's `required_part_received` to be true; otherwise it is refused with `ERR_PART_NOT_RECEIVED`. Verification stamps `verified_by_user_id` with the inspector's badge and `verified_at` with the current logical clock instant, and increments the parent bulletin's `action_verified_count` by one. When that increment makes `action_verified_count` equal `action_total_count` — and the parent has at least one non-cancelled action — the parent bulletin bubbles up `ACKNOWLEDGED` → `COMPLETED`, and no further action rows may be created for it.

Deferral is the `MaintenanceManager`'s escape valve and it is available only before work starts. An action that is `PENDING` moves `PENDING` → `DEFERRED` when the manager supplies a `deferral_reason` and a `deferred_until_date`; that date must be no later than the parent bulletin's `compliance_deadline_date`. Deferring an action that is `IN_WORK`, `VERIFIED`, `DEFERRED` or `CANCELLED` is refused with `ERR_ACTION_STATE_INVALID`. The hard rule sits on the parent's `severity`: an action whose parent bulletin has `severity` `RECALL` may never be deferred, and the attempt is refused with `ERR_RECALL_NOT_DEFERRABLE`. `ADVISORY` and `MANDATORY` actions may be deferred. Deferral has no ledger effect, but it does raise the bulletin's fleet-aggregate risk through the escalation factor described next, while leaving the per-unit maximum figure untouched.

**Fleet risk scoring** is a computed read on a bulletin, available to every role, and it reports two deliberately different numbers over the same set of actions. That set is every fleet action of the bulletin whose `status` is `PENDING`, `IN_WORK` or `DEFERRED`; actions in `VERIFIED` and `CANCELLED` are excluded from both figures. Actions are iterated in order of their attraction's `created_at` ascending. The response reports the `bulletin_id`, an `evaluated_action_count` giving the size of that set, a `deferred_action_count`, the `escalation_factor`, and the three score figures `fleet_aggregate_score`, `per_unit_max_score` and `divergence`. Nothing is persisted.

The overdue penalty is shared by every action of the bulletin. The days overdue is the whole number of days from the bulletin's `compliance_deadline_date` to the logical clock's current UTC date, discarding any part-day remainder and treated as zero whenever the deadline has not yet passed. The overdue points are then those days overdue multiplied by 1.5 points per day, capped at 30 points — which is to say the penalty stops growing after twenty days past deadline.

Each individual action's raw score is the product of three factors plus that shared overdue penalty. The severity base comes from the parent bulletin's `severity`: 10 for `ADVISORY`, 40 for `MANDATORY`, 70 for `RECALL`. The ride-class factor comes from the action's attraction's `ride_class`: 0.6 for `KIDDIE`, 0.8 for `FAMILY`, 1.0 for `WATER`, 1.2 for `THRILL`. The status factor comes from the action's own `status`: 1.0 for `PENDING`, 0.6 for `IN_WORK`, 1.4 for `DEFERRED` — deferring an action makes it more dangerous on paper, not less. The raw score is the severity base multiplied by the ride-class factor multiplied by the status factor, with the overdue points added afterwards. That raw score is then rounded half up to 2 decimal places and capped at a score ceiling of 100 to give the action's score.

The `escalation_factor` reflects how much of the fleet has been deferred: it is 1 plus 0.05 for each action in the evaluated set whose `status` is `DEFERRED`, so `deferred_action_count` deferrals give a factor of 1 plus five hundredths times that count. `fleet_aggregate_score` is the compliance-dashboard number the maintenance director reports, and it is built in two rounded steps: first the arithmetic mean of the per-action scores — their sum divided by the number of actions in the set — is rounded half up to 2 decimal places, then that rounded mean is multiplied by the `escalation_factor`, that product is rounded half up to 2 decimal places, and the result is capped at the ceiling of 100. `per_unit_max_score` is the number the safety committee uses to decide whether a single unit must be pulled: it is simply the greatest individual action score in the set, and it ignores the escalation factor entirely. `divergence` is `per_unit_max_score` less `fleet_aggregate_score`, rounded half up to 2 decimal places. When the evaluated set is empty, both scores are 0.00 and `divergence` is 0.00.

### 3.7. Ride Operator Certification and Dispatch Readiness

A `MaintenanceManager` certifies an operator on one attraction by supplying the `attraction_id`, the operator's opaque staff identifier `operator_user_id`, the inclusive interval start `effective_from`, the exclusive interval end `expires_at`, which must be strictly later than `effective_from`, and two practical results: `restraint_verification_score` and `dispatch_procedure_score`, each an integer from 0 through 100 inclusive. A new certification's `suspended_at` and `suspension_reason` both begin null.

Certification validity is a **half-open** interval — the instant `effective_from` is inside the interval and the instant `expires_at` is outside it — and for any one pairing of `attraction_id` and `operator_user_id` those intervals must be strictly pairwise exclusive with no buffer of any kind. A requested interval is refused with `ERR_CERTIFICATION_WINDOW_OVERLAP` when it intersects an existing certification's interval for the same operator on the same attraction for a positive duration. Exact adjacency is not an overlap and is accepted: a new certification whose `effective_from` equals an existing one's `expires_at`, or whose `expires_at` equals an existing one's `effective_from`, is perfectly legal. Certifications whose derived `status` has become `EXPIRED` still occupy their intervals for the purposes of this check — expiry is a fact about the clock, not a release of the slot.

A certification's `status` is derived at every read and every aggregation, and after every clock move, from four inputs in a pinned precedence order. If the current logical clock instant is at or after `expires_at`, the status is `EXPIRED` — and `EXPIRED` takes precedence over everything else, including suspension, so a suspended certification that reaches its expiry reads `EXPIRED` rather than `SUSPENDED`. Otherwise, if `suspended_at` is not null, the status is `SUSPENDED`. Otherwise, if the clock is still before `effective_from`, the status is `TRAINEE`, because a future-dated certification is not yet in force. Otherwise, if `restraint_verification_score` is at least 85 **and** `dispatch_procedure_score` is at least 80, the status is `CERTIFIED`. In every other case the status is `TRAINEE` — which is to say a failing score on either practical leaves the operator a trainee indefinitely rather than producing an error. `EXPIRED` is terminal.

Two consequences follow at creation time. A certification created with both scores at or above their thresholds and a validity interval that contains the current clock instant derives `CERTIFIED` immediately, and the attraction's `certified_operator_count` increments accordingly. A certification created with a failing score on either practical, or with a future `effective_from`, derives `TRAINEE`, and the attraction's `certified_operator_count` does not move.

Suspension is the `SafetyOfficer`'s tool. Suspending a certification whose derived `status` is `CERTIFIED` stores the supplied `suspension_reason` and stamps `suspended_at` with the current logical clock instant, moving the derived status `CERTIFIED` → `SUSPENDED` and causing the attraction's `certified_operator_count` to be recomputed downward. Attempting to suspend a certification whose derived status is `TRAINEE`, `SUSPENDED` or `EXPIRED` is refused with `ERR_CERTIFICATION_STATE_INVALID`. The same `CERTIFIED` → `SUSPENDED` movement is also driven by the server as part of the ride-hold cascade described in §3.8, in which case the stored `suspension_reason` is the literal string `RIDE_HOLD`. The reverse movement `SUSPENDED` → `CERTIFIED` is never available to a caller directly: it happens only when the incident report that suspended the certification is cleared, and only while the clock is still inside the certification's interval, at which point `suspended_at` and `suspension_reason` are cleared and `certified_operator_count` is recomputed upward. Separately, the movements `CERTIFIED` → `EXPIRED` and `SUSPENDED` → `EXPIRED` are not operations at all — they simply become true as the logical clock reaches `expires_at`, and the attraction's `certified_operator_count` excludes such a row from its next recomputation.

**Dispatch readiness** is a computed read on an attraction, available to every role, that answers whether the attraction is genuinely staffed and prepared to dispatch guests right now. The response reports the `attraction_id`, the attraction's current `operational_posture`, its `certified_operator_count`, a `mean_restraint_score`, an `essential_fail_count`, and the `dispatch_readiness_index` itself. Nothing is persisted.

The certified set feeding the index is every operator certification of the attraction whose derived `status` is exactly `CERTIFIED` at the current logical clock instant, and `certified_operator_count` is the size of that set. The `essential_fail_count` figure is read from a single inspection: the attraction's daily inspection with the greatest `service_date` among those whose `status` is `SIGNED_OFF`, breaking a tie on `created_at` ascending so the earliest row wins. When the attraction has no signed-off inspection at all, that count contributes nothing.

The index itself is computed as follows. If the attraction's `operational_posture` is anything other than `OPEN`, the `dispatch_readiness_index` is 0.00 — a closed, down, held or overhauled attraction has no dispatch readiness by definition. If the posture is `OPEN` but the certified set is empty, the index is likewise 0.00, and no division is attempted. Otherwise three quantities are combined. The **staffing ratio** is the `certified_operator_count` divided by the attraction's `min_operators_required`, capped at 1.0 so that surplus operators do not inflate the score. The **mean restraint score**, reported as `mean_restraint_score`, is the sum of `restraint_verification_score` across the certified set divided by the size of that set, and it stays an exact unrounded value inside the expression. The **restraint factor** is that mean restraint score less a floor of 60, divided by a span of 40, then clamped into the range 0.0 through 1.0 — a mean of 60 or below gives 0.0, a mean of 100 or above gives 1.0, and it also stays unrounded. The **penalty** is the `essential_fail_count` described above multiplied by 8 points per essential failure, capped at 40 points, so no more than five essential failures can ever count against the index. The index is then 100 multiplied by the staffing ratio, multiplied by the quantity given by a base weight of 0.40 plus a restraint weight of 0.60 times the restraint factor, less the penalty; that whole expression is rounded half up to 2 decimal places exactly once at the end, and the result is floored at 0.00 so the index is never negative.

### 3.8. Incidents, Ride Holds and the Regulatory Interface

A guest incident is filed by a `SafetyOfficer`, who supplies the `attraction_id` the incident occurred on, the `occurred_at` instant, the `injury_severity` — one of `NONE`, `MINOR`, `SERIOUS` or `FATAL` — the `guest_count_affected`, which must not be negative, and a non-empty `narrative` giving the first report. Filing branches immediately on severity, and the two branches are not variations of one another but genuinely different opening states.

An incident whose `injury_severity` is `SERIOUS` or `FATAL` opens directly at `status` `RIDE_HELD`. Its `regulator_notification_due_at` is set to its `occurred_at` plus the statutory notification window of 24 hours, and the full four-hop hold cascade described below runs at once. An incident whose `injury_severity` is `NONE` or `MINOR` opens at `status` `REPORTED`, its `regulator_notification_due_at` stays null, and no cascade runs at all — the ride keeps operating. In both branches `notified_late` starts false and `suspended_certification_count` starts at 0 unless the cascade ran, and `regulator_case_ref`, `notified_at`, `investigator_user_id`, `regulator_clearance_ref` and `cleared_at` all start null.

An incident that opened at `REPORTED` can be escalated later: a `SafetyOfficer` places the regulatory hold on it, moving it `REPORTED` → `RIDE_HELD`. That is the entry point for the hold cascade, and the cascade is identical whether it was triggered by escalation or by a `SERIOUS`/`FATAL` filing. **Hop one** sets the attraction's `regulatory_hold` to true. **Hop two** recomputes the attraction's `operational_posture`, which now reads `HOLD` because clause 2 of §2.8 matches — unless an overhaul is in progress, in which case `OVERHAUL` still outranks it. **Hop three** suspends the workforce: every operator certification of that attraction whose derived `status` is `CERTIFIED` moves to `SUSPENDED` with its `suspension_reason` set to `RIDE_HOLD` and its `suspended_at` stamped with the current logical clock instant, and the incident's `suspended_certification_count` records exactly how many certifications it suspended. **Hop four** recomputes the attraction's `certified_operator_count` downward to reflect those suspensions. Placing a hold on an incident that is not `REPORTED` is refused with `ERR_INCIDENT_STATE_INVALID`.

Investigation is the fork point. A `SafetyOfficer` opens the investigation on an incident that is `RIDE_HELD`, moving it `RIDE_HELD` → `UNDER_INVESTIGATION` and recording the acting badge in `investigator_user_id`. The attraction's `regulatory_hold` stays true throughout — investigating does not release anything. From `UNDER_INVESTIGATION` the incident takes exactly one of two branches, and the branch it takes determines what clearance later requires.

**Branch A — the regulator filing.** A `SafetyOfficer` files the statutory notification, supplying a `regulator_case_ref`, which moves the incident `UNDER_INVESTIGATION` → `REGULATOR_NOTIFIED`. The supplied `regulator_case_ref` is stored, `notified_at` is stamped with the current logical clock instant, and `notified_late` is set to true exactly when `notified_at` is strictly later than `regulator_notification_due_at` — filing precisely on the deadline instant is on time. This branch is only meaningful for a genuine reportable injury: attempting it on an incident whose `injury_severity` is `NONE` or `MINOR` is refused with `ERR_NOTIFICATION_NOT_REQUIRED`. Taking this branch adds a requirement to clearance, described below.

**Branch B — the internal review.** A `SafetyOfficer` closes the internal review without any regulator filing, which moves the incident `UNDER_INVESTIGATION` → `INTERNAL_REVIEW_CLOSED`. On this branch `regulator_case_ref` and `notified_at` both stay null and `notified_late` stays false; no regulator bookkeeping is created at all. Clearance from this branch requires no clearance reference.

Attempting either branch from any state other than `UNDER_INVESTIGATION` is refused with `ERR_INCIDENT_STATE_INVALID`.

The two branches join at clearance, which is where the hold is finally released. A `SafetyOfficer` clears an incident whose `status` is `REGULATOR_NOTIFIED` or `INTERNAL_REVIEW_CLOSED`, moving it to `CLEARED_TO_OPERATE`, which is terminal; clearing from any other state is refused with `ERR_INCIDENT_STATE_INVALID`. The two branches carry divergent entry preconditions at this join. An incident that took Branch A must supply a non-empty `regulator_clearance_ref`, which is stored on the row; omitting it, or supplying an empty one, is refused with `ERR_REGULATOR_CLEARANCE_REQUIRED`. An incident that took Branch B ignores `regulator_clearance_ref` entirely and may omit it.

Clearance stamps `cleared_at` with the current logical clock instant and then compensates the hold cascade, in the same shape on both branches. The attraction's `regulatory_hold` becomes false — but only when no other incident report of that attraction remains in `RIDE_HELD`, `UNDER_INVESTIGATION` or `REGULATOR_NOTIFIED`, so a second live incident keeps the hold in place. Every operator certification that **this** incident suspended returns `SUSPENDED` → `CERTIFIED`, with its `suspended_at` and `suspension_reason` cleared, and the attraction's `certified_operator_count` is recomputed upward; certifications suspended by some other incident, or suspended directly by a safety officer, are untouched. Finally the attraction's `operational_posture` is recomputed, which is how an attraction leaves `HOLD`.

### 3.9. Off-Season Overhaul Scheduling and Recommissioning

Major components do not get inspected in place at the end of the season — they get pulled, torn down, measured and rebuilt in a maintenance shop bay. A `ParkOpsAdmin` opens a bay with a `name` and a `concurrent_slot_capacity` giving how many overhaul work orders may occupy that bay on any single calendar day, which must be at least 1. A new bay begins at `version` 1 with a `booked_order_count` of 0. Reading a bay is how a planner obtains the `version` value they must echo back as `expected_shop_bay_version`.

A `MaintenanceManager` books an overhaul by supplying the `attraction_id` being overhauled, the `component_id` of the major component to be torn down and rebuilt, the `shop_bay_id` of the bay to be reserved, the `expected_shop_bay_version` required by §2.7, the inclusive occupancy window bounded by `window_start_date` and `window_end_date` — where the end must be the same as or later than the start — the quoted `parts_subtotal_cents` for the rebuild kit in whole cents, the quoted shop `labor_hours`, and an optional `expedite_requested` flag which defaults to false. Neither the parts subtotal nor the labor hours may be negative. The named `component_id` must be a component installed on the named `attraction_id`; one installed on a different attraction is refused with `ERR_COMPONENT_ATTRACTION_MISMATCH`. Three refusals therefore compete on this one operation, and per the ladder in §2.6 they resolve in this order: the stale-bay check first with `ERR_STALE_SHOP_BAY_VERSION`, then the component-installation check with `ERR_COMPONENT_ATTRACTION_MISMATCH`, then the bay-capacity check with `ERR_BAY_CAPACITY_CONFLICT`.

Bay occupancy is checked with a changeover buffer, because a bay needs a day either side to move iron in and out. The requested window is widened by one changeover day at each end, giving an expanded window that starts one day before `window_start_date` and ends one day after `window_end_date`, both endpoints inclusive. For every calendar day in that expanded window, the server counts the existing work orders booked into the same `shop_bay_id` whose `status` is anything other than `RECOMMISSIONED` and whose own **unwidened** inclusive window from their `window_start_date` through their `window_end_date` contains that day. If the count on any single day already equals or exceeds the bay's `concurrent_slot_capacity`, the booking is refused with `ERR_BAY_CAPACITY_CONFLICT`. Note the asymmetry deliberately built into this test: the requested window is buffered but the existing windows are not, so a new booking is pushed away from its neighbours by one day without existing bookings pushing away from each other retroactively.

Booking succeeds at `status` `SCHEDULED`, increments the bay's `booked_order_count` by one, and increments the bay's `version` by one — which is precisely why a second planner working from a stale read of the same bay will be turned away.

The cost estimate is stamped onto the work order at booking and is evaluated in a **pinned seven-step order**, because the expedite tier depends on the discounted base while the discount depends on the undiscounted base. No other evaluation order is sanctioned.

1. The labor cost is the `labor_hours` multiplied by the shop labor rate of 9,500 cents per hour — that is, 95 dollars an hour.
2. `base_total_cents` is the `parts_subtotal_cents` plus that labor cost.
3. `off_season` is true when **every** calendar date in the inclusive window from `window_start_date` through `window_end_date` falls inside the park's off-season span, which runs from the 1st of November in one year through the 28th of February in the next; equivalently, every date in the window has a month-and-day of November 1 or later, or of February 28 or earlier. When `off_season` is true, `off_season_discount_cents` is `base_total_cents` multiplied by the off-season discount of 6 percent, rounded half up to a whole cent; when `off_season` is false, `off_season_discount_cents` is 0.
4. `discounted_base_cents` is `base_total_cents` less `off_season_discount_cents`.
5. `expedite_pct` is selected from `discounted_base_cents` — **not** from `base_total_cents`. When `expedite_requested` is false, `expedite_pct` is 0. When it is true, `expedite_pct` is 0.12 if `discounted_base_cents` is below 5,000,000 cents (50,000 dollars), 0.08 if it is below 20,000,000 cents (200,000 dollars) but not below the first ceiling, and 0.05 otherwise. Small jobs pay the highest expedite rate; large ones pay the lowest.
6. `expedite_fee_cents` is `discounted_base_cents` multiplied by `expedite_pct`, rounded half up to a whole cent; it is 0 whenever `expedite_requested` is false.
7. `estimated_total_cents` is `discounted_base_cents` plus `expedite_fee_cents`.

Every intermediate multiplication is rounded half up to a whole cent before the next step consumes it, and no sibling work order participates in any of this arithmetic — the estimate is a function of the single order being created.

Overhaul progress is advanced one phase at a time by a `MaintenanceManager`, who names the phase being entered in `target_phase`. The pipeline is `SCHEDULED` → `TEARDOWN` → `INSPECTION` → `REBUILD` → `RECOMMISSIONED`, and `target_phase` must name the immediate successor of the order's current `status`. A `target_phase` that skips a phase, moves backwards, or is requested against an order already at `RECOMMISSIONED` is refused with `ERR_WORK_ORDER_STATE_INVALID`. `RECOMMISSIONED` is terminal.

Each step does something different. The `SCHEDULED` → `TEARDOWN` step recomputes the attraction's `operational_posture` to `OVERHAUL`, the highest-precedence posture in the system, and it carries one cross-entity gate: it is refused with `ERR_INSPECTION_STATE_INVALID` when the attraction has a daily inspection for the current service date sitting in `PENDING_SIGN_OFF`, since tearing a component out from under an inspector who is mid-decision is not permitted. The `TEARDOWN` → `INSPECTION` step deliberately leaves the component's `condition_flag` untouched — a torn-down component keeps whatever flag it carried in until it is recommissioned. The `INSPECTION` → `REBUILD` step changes nothing outside the work order. The `REBUILD` → `RECOMMISSIONED` step is the one that returns iron to service: it stamps `recommissioned_at` with the current logical clock instant, resets the component's `last_ndt_at` to that same instant and its `last_ndt_cycles` to the attraction's current `cumulative_cycles` so its `ndt_status` returns to `CURRENT`, returns the component's `condition_flag` to `OK`, decrements the bay's `booked_order_count`, and recomputes the attraction's `operational_posture`, which now leaves `OVERHAUL`.

## 4. API Endpoint Reference

Creation endpoints answer with HTTP 201; every other successful call answers with HTTP 200. Where a row lists "All roles", all six roles of §2.1 may call it. The behaviour of each endpoint — its inputs, its refusals and its side effects — is specified in §2 and §3; this section is the routing index only.
