# Lead Service Line Inventory & Replacement API — Product Requirements Document

## 1. Introduction

Drinking-water utilities are now required to know, address by address, what every service line is made of — on the utility side of the curb stop and on the customer side of it — and to retire every lead and galvanized-requiring-replacement line on a published schedule. In practice the knowledge arrives in fragments: a tap card from 1954, a predictive model fitted on installation-era housing stock, a crew that pothole-excavated the curb box last Tuesday, a laboratory result from a first-draw sample. Those fragments disagree with each other, they arrive out of order, and some of them are later retracted. The utility must nonetheless publish a single defensible number for how many lines are lead, how many are galvanized, how many are non-lead, and how many remain unknown — and then notify every affected customer within a fixed window of publishing.

This document specifies the Lead Service Line Inventory & Replacement API, the system of record for that program. It carries the full arc: registering a public water system and its regulatory deadline; accumulating material evidence and deriving a classification from whichever evidence currently governs; dispatching verification crews into shift-bounded appointment windows and absorbing the access barriers they hit; running statistically validated sampling strata; certifying and publishing an inventory under segregation of duties; fanning out and chasing customer notifications; prioritizing replacement work by material certainty, disadvantaged-community status and coordination with paving projects; negotiating customer-side consent and settling for a partial replacement when consent cannot be obtained; assembling money across state revolving funds, federal grants and rate revenue under per-source caps and equity floors; scheduling excavation around post-paving moratoria and street capacity; issuing post-replacement flushing guidance; and filing periodic compliance progress reports.

Two design commitments run through the whole specification and are worth stating up front. First, almost every stored number that matters is **derived**, not supplied: classifications, certainty scores, priority scores, funding ledgers, counters and postures are recomputed by the server from primitive facts, and clients never write them directly. Second, the program has a single system-wide brake — the water system's **program posture** — which the server recomputes after every material change and which can freeze or restrict replacement, funding and publication work without any operator asking it to. Engineers implementing this API should expect that a single write frequently produces a chain of four or five secondary mutations, and that the chain's ordering is normative rather than incidental. All resources described here are mounted under the `/lsl` path prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. If either header is absent — a header present but carrying an empty string counts as absent — or if `X-User-Role` is not one of the six role names below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). When the headers are well formed but the declared role is not among the roles authorized for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The six recognized roles are `ProgramAdministrator`, `InventoryAnalyst`, `ComplianceOfficer`, `FieldTechnician`, `CustomerRepresentative` and `ReplacementContractor`.

- A `ProgramAdministrator` is the utility's program owner. It registers water systems, verification crews, street projects and funding sources, opens replacement orders, commits funding plans, cancels orders, re-books appointments after an access barrier, and drives the logical clock.
- An `InventoryAnalyst` builds the material inventory from records and predictive modelling, records and retracts evidence, issues classification overrides, and drafts inventory publications. An analyst may never certify a publication it drafted.
- A `ComplianceOfficer` is the regulatory signatory. It advances the system inventory lifecycle, opens and manages sampling batches, runs statistical validation, certifies and publishes inventories, adjusts corrosion-control posture, and files progress reports.
- A `FieldTechnician` is a verification crew operating in the field: it arrives on site, records verified material, and reports access barriers.
- A `CustomerRepresentative` staffs the notification and consent desk: it delivers, records acknowledgement of, and returns customer notifications, and it canvasses customers for customer-side replacement consent.
- A `ReplacementContractor` is the construction contractor that schedules, starts and closes out excavations.

Identity semantics differ by role, and the difference is load-bearing. When `X-User-Role` is `FieldTechnician`, `X-User-ID` is the `id` of the acting `VerificationCrew` row; ownership checks on any resource that references a `VerificationCrew` compare that resource's crew foreign-key field to `X-User-ID`. Concretely, a technician may only act on a `VerificationAppointment` whose `crew_id` equals the caller's `X-User-ID`; a mismatch is rejected with `ERR_CREW_IDENTITY_MISMATCH` (HTTP 403). When `X-User-Role` is `ProgramAdministrator`, `InventoryAnalyst`, `ComplianceOfficer`, `CustomerRepresentative` or `ReplacementContractor`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — it stores the drafting analyst's identifier as `drafted_by_user_id` and the certifying officer's identifier as `certified_by_user_id` on an inventory publication — but it never compares such an identifier to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Filtering

Collection reads are paginated with two query parameters. `limit` is the maximum number of rows to return; it defaults to 10, may not be lower than 1, and may not exceed 100. `offset` is the number of rows to skip; it defaults to 0 and may not be negative. A `limit` outside the inclusive range 1 through 100, a negative `offset`, or a non-integer value for either, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

Unless a specific collection says otherwise, list results are ordered by the server's monotonic insertion sequence — the order in which the rows were first persisted — which agrees with `created_at` ascending except that rows sharing a `created_at` millisecond keep their insertion order rather than being re-sorted among themselves. Every list response carries `limit`, `offset`, `total_count` and `has_more` in the envelope's `meta` object; `total_count` counts the rows matching the filters before pagination is applied, and `has_more` is true when rows remain beyond the current page.

Each collection also accepts optional equality filters, all of them narrowing the result set. A filter is compared for exact string equality against the stored value, except for the three boolean filters — `retracted`, `disadvantaged_status` and `overdue` — which read `true` or `1` as true and `false` or `0` as false, case-insensitively. A filter value that matches nothing, whether an unrecognized enum spelling or an unparseable boolean, simply narrows the result set to zero rows; it is never a validation error:

- Water systems may be filtered by `inventory_status` and by `program_posture`.
- Service lines may be filtered by `water_system_id`, `street_project_id`, `classification`, `inventory_state`, `replacement_state` and `disadvantaged_status`.
- Evidence items may be filtered by `service_line_id`, `source_type`, `side`, `retracted` and `origin`.
- Verification crews may be filtered by `water_system_id` and `status`.
- Verification appointments may be filtered by `crew_id`, `service_line_id`, `state` and `method`.
- Sampling batches may be filtered by `water_system_id` and `state`.
- Inventory publications may be filtered by `water_system_id`, `state` and `basis`.
- Customer notifications may be filtered by `service_line_id`, `inventory_publication_id`, `state` and `overdue`.
- Replacement orders may be filtered by `service_line_id`, `street_project_id`, `fulfillment_state`, `consent_state` and `scope`.
- Street projects may be filtered by `water_system_id`.
- Funding sources may be filtered by `water_system_id`, `source_kind` and `status`.
- Progress reports may be filtered by `water_system_id` and `compliance_status`.

### 2.4. Resource Identity, Timestamps and Revision Counters

Water systems, service lines, evidence items, verification crews, verification appointments, sampling batches, inventory publications, customer notifications, replacement orders, street projects and funding sources all carry the same four system-managed properties:

- `id` — a server-minted UUID. It carries no type prefix and no embedded meaning; in particular, an evidence item's `id` is never an input to any ranking or tie-break rule.
- `created_at` — an ISO 8601 UTC timestamp with three fractional digits, stamped when the row is first persisted and never changed afterwards. These two row-bookkeeping stamps are read from the server's real wall-clock time at the moment the write happens, not from the logical clock of §2.5; where the logical clock feeds a row is always a named business field or comparison, never `created_at` or `updated_at`.
- `updated_at` — an ISO 8601 UTC timestamp in the same format and from the same wall-clock source, refreshed on every mutation of the row, including mutations the server performs on its own initiative as part of a cascade.
- `version` — an integer that starts at 1 on creation and increases by exactly 1 on every mutation of the row. A server-initiated recompute counts as a mutation: when a classification recompute rewrites a service line's derived fields, that line's `version` advances and its `updated_at` is refreshed just as if a client had written it. That applies to derived fields the server actually stores on the row; the aggregate counters, ledgers, postures and flags that §2.8 lists as evaluated at serialization time are not stored at all, so refreshing one of those is not a mutation and moves neither `updated_at` nor `version`.

Progress reports are the exception. A progress report is an append-only compliance artifact: it is computed once at filing time and is never updated, so it carries only `id` and `created_at`. It has neither an `updated_at` field nor a `version` field, and there is no endpoint that modifies one.

Two collections hold their detail rows as embedded arrays rather than as separately addressable resources. A sampling batch's `samples` array holds append-only objects shaped `{ sample_seq, service_line_id, lead_ppb, collected_at, sample_type, invalidated, invalidation_reason }`; `sample_seq` starts at 1 for the first accepted sample of the batch and increases by 1 for each subsequent accepted sample, `invalidated` starts false, and `invalidation_reason` starts null. A replacement order's `funding_allocations` array holds objects shaped `{ funding_source_id, allocated_cents, priority_rank, state }`, where the allocation's own `state` is `COMMITTED`, `DRAWN` or `RELEASED`. Embedded objects do not carry their own `id`, `created_at`, `updated_at` or `version`; they are part of the parent row, and mutating one advances the parent's `version`.

### 2.5. The Logical Clock

Every deadline, overdue determination, paving-coordination tier and completion-window comparison in this system reads a server-held **logical clock** rather than real wall-clock time. On startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it holds that value until a `ProgramAdministrator` moves it; the server never falls back to real time. The clock-setting capability accepts a single `to_iso8601` instant and responds with an object carrying `current_utc` (the clock's new value) and `previous_utc` (the value it held before the call). Movement is monotonic non-decreasing: a `to_iso8601` earlier than the clock's current value is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while a `to_iso8601` equal to the current value is accepted and leaves the clock where it is.

Moving the clock is not inert: `overdue` on every customer notification and `program_posture` on every water system both follow the new value immediately, because one clause of the posture rule compares the clock's calendar date against the water system's `compliance_deadline_date`. It follows it by re-derivation, though, not by rewriting. Both of those values are computed at serialization time per §2.8, so a clock move writes to no row whatsoever: no notification and no water system has its `updated_at` refreshed or its `version` advanced by the move, and the new determinations simply appear on the next read of each row. The response `data` carries exactly `current_utc` and `previous_utc` and nothing else, both in the three-fractional-digit ISO 8601 UTC form of §2.4, at HTTP 200.

### 2.6. Numeric Precision and Cent Arithmetic

Scores, percentages and credit values are stored to exactly 2 decimal places using the round-half-up method. This covers `certainty_score`, `replacement_priority_score`, `unknown_share_pct`, `disadvantaged_share_pct` on both funding sources and progress reports, `replacement_progress_pct`, `base_credit`, `total_credit`, `shortfall_credit` and the intermediate `pipe_volume_liters` term of the flushing calculation. One value is stored to 4 decimal places, again round-half-up: a sampling batch's `classification_confidence`. A batch's `percentile_90_ppb` is not rounded at all — it is the stored `lead_ppb` of a selected sample, reproduced verbatim.

All money in the system is expressed in whole cents as integers: `estimated_cost_cents`, `authorized_cents`, `available_cents`, `committed_cents`, `drawn_cents`, `disadvantaged_committed_cents`, `equity_shortfall_cents`, `allocated_total_cents` and each allocation's `allocated_cents`. There is no sub-cent state anywhere; apportionment rounds each source's share to whole cents individually and then reconciles the residue, as described in §3.7. Counters that measure time in minutes — `flushing_duration_minutes` — and integer tallies such as `mandated_annual_credit`, `deferral_allowance`, `required_sample_count` and `attempt_count` are whole numbers.

Where a rule rounds a fractional count upward, it does so with an exact ceiling: a value already at a whole number stays where it is, and any fraction above it advances to the next whole number.

### 2.7. Program Posture: The System-Wide Brake

Each water system carries a derived `program_posture` with three possible values — `OPEN`, `RESTRICTED` and `FROZEN` — that gates replacement, funding and publication work across the whole system. It is never written by a client. The server recomputes it at the end of every water-system counter refresh, every funding-source ledger refresh, every customer-notification state change, every `inventory_status` transition, and every logical-clock move.

The recompute walks the following clauses in order and returns the value of the **first** clause that matches:

1. If the water system's `inventory_status` is `DRAFT`, the posture is `FROZEN`.
2. Otherwise, if `unknown_count` is greater than zero and the logical clock's calendar date is strictly later than `compliance_deadline_date`, the posture is `FROZEN`.
3. Otherwise, if `inventory_status` is `AMENDMENT_PENDING`, the posture is `RESTRICTED`.
4. Otherwise, if `outstanding_notification_count` is greater than zero, the posture is `RESTRICTED`.
5. Otherwise, if at least one funding source of this water system has `status` equal to `ACTIVE` and an `equity_shortfall_cents` greater than zero, the posture is `RESTRICTED`.
6. Otherwise, if `unknown_share_pct` is strictly greater than 10.00, the posture is `RESTRICTED`. A share of exactly 10.00 does not restrict.
7. Otherwise, the posture is `OPEN`.

Three operations refuse to run while the posture is `FROZEN` and answer `ERR_PROGRAM_POSTURE_FROZEN` (HTTP 409): opening a replacement order, committing a funding plan, and drafting an inventory publication. One operation is stricter still and demands the posture be exactly `OPEN`: scheduling an excavation window. If the posture is anything other than `OPEN` at that moment, scheduling fails with `ERR_PROGRAM_POSTURE_RESTRICTED` (HTTP 409).

### 2.8. Derived Values and Cascade Ordering

No client ever writes a derived field. Materials, classifications, certainty and priority scores on a service line; every counter on a water system; every ledger figure on a funding source; the excavation counter on a street project; the appointment counter on a crew; `overdue` on a notification; and the entire body of a progress report are all computed by the server from primitive facts. They divide into two kinds, and the division decides whether a recompute is a mutation. The service line's own derived fields — `utility_side_material`, `customer_side_material`, `classification`, `certainty_basis`, `certainty_score`, `replacement_priority_score`, `disadvantaged_status`, `consent_barrier_flag` and its two state axes — together with a progress report's computed body, are persisted onto the row, so rewriting them is a mutation that refreshes `updated_at` and advances `version`. Every other value in that list is instead evaluated afresh each time the owning row is serialized and is never stored: `total_service_line_count`, `lead_count`, `grr_count`, `non_lead_count`, `unknown_count`, `unknown_share_pct`, `outstanding_notification_count` and `program_posture` on a water system; `committed_cents`, `drawn_cents`, `available_cents`, `disadvantaged_committed_cents`, `disadvantaged_share_pct` and `equity_shortfall_cents` on a funding source; `active_excavation_order_count` on a street project; `scheduled_appointment_count` on a crew; `overdue` on a notification; `required_sample_count` and `valid_sample_count` on a sampling batch; and `allocated_total_cents` on a replacement order. Because those are never stored, refreshing one mutates nothing at all — the owning row's `updated_at` and `version` stay exactly where they were, and every subsequent reader nonetheless sees the refreshed figure.

Recomputes chain, and the chain runs bottom-up in a fixed order. A write that touches evidence for one service line first re-selects that line's governing evidence per side, then rewrites `utility_side_material`, `customer_side_material`, `classification`, `disadvantaged_status` and `certainty_score`, then possibly moves the line's `inventory_state` across the classification axis, then rewrites `replacement_priority_score`, then possibly moves the line's `replacement_state` across the replacement axis. Only after the line has settled does the chain bubble up to the parent water system, refreshing `total_service_line_count`, `lead_count`, `grr_count`, `non_lead_count`, `unknown_count` and `unknown_share_pct`. Only after those counters have settled does the chain recompute `program_posture` from them — both of those steps being re-derivations rather than writes, so the amendment edge below is the one and only observable water-system mutation the chain performs. And only then — if the water system's `inventory_status` was `PUBLISHED` and the recompute actually changed at least one service line's `classification` to a different value than it held before — does the water system move to `AMENDMENT_PENDING`, which by clause 3 of §2.7 forces the posture to `RESTRICTED`. Computing the posture before the counters, or amending before the counters settle, produces observably different results and is incorrect.

Compensating operations must restore exactly what they undid. Returning a delivered notification must restore `outstanding_notification_count` to precisely its pre-delivery value; cancelling a funded order must restore each affected funding source's `available_cents` to precisely its pre-commit value. "Restore" here means arithmetic identity, not approximation.

### 2.9. Stale-Version Guards on Drafting and Overriding

Two write operations require the client to prove it is acting on data it has actually seen, and both use the parent row's `version` as the token of proof.

Drafting an inventory publication requires a non-optional `expected_water_system_version` field in the request body, carrying the client's last observed `version` of the target `WaterSystem`. If that value does not equal the water system's current `version`, the draft is rejected with `ERR_STALE_WATER_SYSTEM_VERSION` (HTTP 412). Nothing else blocks this write — a new draft legitimately supersedes and discards any prior `DRAFT` publication of the same water system, so no state precondition stands in its way. The version check is the only thing preventing an analyst from drafting a publication against counters they can no longer see.

Recording a classification override on a service line requires a non-optional `expected_service_line_version` field carrying the client's last observed `version` of the target `ServiceLine`. A mismatch against the line's current `version` is rejected with `ERR_STALE_SERVICE_LINE_VERSION` (HTTP 412). Again, no state precondition blocks the operation: an override deliberately supersedes the prior governing evidence on its side, so a second override on the same side is a legitimate product operation. The version check is what prevents an analyst from overriding a classification that was derived from evidence they never observed.

No other endpoint in this API takes a version field, and no other endpoint performs a version comparison. Endpoints not named above must not require, and must not reject on, any `expected_*_version` input.

### 2.10. Request Validation Order

When a single request could fail several ways, the server reports the failure from the earliest applicable rung of the following ladder. The ordering is normative: a request that violates two rules always reports the higher rung's error, never the lower one's.

1. **Authentication.** Both headers present and `X-User-Role` among the six declared roles, else `ERR_UNAUTHENTICATED` (401).
2. **Authorization.** The acting role appears in the called endpoint's authorized-role list, else `ERR_UNAUTHORIZED` (403).
3. **Schema.** Every non-optional input field of the endpoint is present and of the declared JSON type, else `ERR_INVALID_REQUEST` (400). A required field sent explicitly as `null` fails this rung exactly as an absent one does, while an optional field sent explicitly as `null` is treated as absent and takes its documented default. A field declared as a calendar date, an instant or an `HH:MM` clock time must also parse in that form to clear this rung, so a malformed date or instant is `ERR_INVALID_REQUEST` here and never `ERR_INVALID_DATE_RANGE` at rung 5. The declared per-field value constraints — minimums such as `authorized_cents` at least 1, maximums such as `cct_target_ph` at most 9.5, strict positivity such as `interior_diameter_mm`, and the non-emptiness of a required string or array — report `ERR_INVALID_REQUEST` (400) as well, but they are the one part of this rung evaluated *after* rung 4 rather than before it: a body carrying both an unrecognized enum spelling and an out-of-range number reports `ERR_INVALID_ENUM_VALUE`.
4. **Enumerations.** Every enum-typed input value is a member of that field's declared value set, else `ERR_INVALID_ENUM_VALUE` (422).
5. **Interval coherence.** Interval inputs are ordered correctly, else `ERR_INVALID_DATE_RANGE` (422). Specifically: `window_end_utc` must be strictly later than `window_start_utc`; `excavation_end_date` must be on or after `excavation_start_date`; `moratorium_end_date` must be on or after `moratorium_start_date`; `period_end_date` must be on or after `period_start_date`; and `shift_end_utc_time` must be strictly later than `shift_start_utc_time`. This rung guards appointment booking and appointment re-booking, replacement-order opening and excavation scheduling, street-project registration, progress-report filing, and crew registration.
6. **Pagination.** On collection reads, `limit` and `offset` are valid per §2.3, else `ERR_INVALID_PAGINATION` (400).
7. **Path resolution.** Every identifier segment in the URL resolves to a live row, checked left to right, so that the leftmost unresolvable segment determines the error. Each entity has its own not-found code: `ERR_WATER_SYSTEM_NOT_FOUND`, `ERR_SERVICE_LINE_NOT_FOUND`, `ERR_EVIDENCE_ITEM_NOT_FOUND`, `ERR_CREW_NOT_FOUND`, `ERR_APPOINTMENT_NOT_FOUND`, `ERR_SAMPLING_BATCH_NOT_FOUND`, `ERR_PUBLICATION_NOT_FOUND`, `ERR_NOTIFICATION_NOT_FOUND`, `ERR_REPLACEMENT_ORDER_NOT_FOUND`, `ERR_STREET_PROJECT_NOT_FOUND`, `ERR_FUNDING_SOURCE_NOT_FOUND` and `ERR_PROGRESS_REPORT_NOT_FOUND`, each returning HTTP 404.
8. **Foreign-key resolution.** Every foreign-key field in the request body resolves to a live row, checked in the order the fields appear in that endpoint's input list, reporting the same per-entity 404 codes.
9. **Crew identity.** For a `FieldTechnician` acting on an appointment, `X-User-ID` equals the appointment's `crew_id`, else `ERR_CREW_IDENTITY_MISMATCH` (403). This rung guards on-site arrival, appointment completion and access-barrier reporting.
10. **Segregation of duties.** The certifying officer's `X-User-ID` differs from the publication's `drafted_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES` (403).
11. **Stale-version guards.** The `expected_water_system_version` or `expected_service_line_version` check of §2.9, yielding HTTP 412.
12. **Consent resolution on funding.** Before the funding plan even looks at the order's work state, it requires the consent canvass to be settled: `consent_state` must be `GRANTED`, `DENIED` or `NO_RESPONSE` and `scope` must be non-null, else `ERR_CONSENT_NOT_RESOLVED` (409). This rung sits deliberately **above** the general work-state check on the next rung, so that an order still parked in `DRAFT` is told the real reason — consent is unresolved — rather than merely that its state is wrong.
13. **Declared-transition state checks.** The target row is in the `from:` state the requested transition declares, else the entity's own conflict code at HTTP 409: `ERR_INVENTORY_STATE_INVALID` for a water-system inventory advance, `ERR_APPOINTMENT_STATE_INVALID` for appointment arrival, completion, barrier reporting and re-booking, `ERR_BATCH_STATE_INVALID` for appending a sample, invalidating a sample, validating and reopening a batch, `ERR_PUBLICATION_STATE_INVALID` for certifying and publishing, `ERR_NOTIFICATION_STATE_INVALID` for delivering, acknowledging and returning a notification, and `ERR_ORDER_STATE_INVALID` for consent request, consent response, funding plan, schedule, start, complete and cancel — the last of which checks the relevant axis's declared `from:` state on each of the order's two independent axes.
14. **Line eligibility.** A replacement order may only be opened against a service line whose `replacement_state` is `ELIGIBLE` or `REPLACED_PARTIAL`, else `ERR_LINE_NOT_ELIGIBLE` (409).
15. **Evidence retraction idempotence.** A retraction target must have `retracted` currently false, else `ERR_EVIDENCE_ALREADY_RETRACTED` (409).
16. **Frozen posture.** The three posture-frozen refusals of §2.7, yielding `ERR_PROGRAM_POSTURE_FROZEN` (409).
17. **Restricted posture.** The scheduling-only requirement that the posture be exactly `OPEN`, yielding `ERR_PROGRAM_POSTURE_RESTRICTED` (409).
18. **Referential business gates.** `ERR_INVENTORY_NOT_PUBLISHED` (409) when a replacement order is opened before the inventory is published; `ERR_UNVALIDATED_SAMPLING_STRATUM` (409) when a publication is certified while the water system has no sampling batch at all or has any batch not yet validated; `ERR_CREW_INACTIVE` (409) when arrival is attempted with an inactive crew; `ERR_PINNED_SNAPSHOT_STALE` (409) when a certified publication's pinned notifiable count no longer matches reality.
19. **Safety gates.** `ERR_CCT_NOT_OPTIMIZED` (422) when excavation is scheduled during corrosion-control re-optimization; `ERR_NOTIFICATION_OVERDUE_BLOCK` (409) when certification is attempted while any notification of the water system is overdue.
20. **Uniqueness, membership and shape.** `ERR_DUPLICATE_PWSID`, `ERR_DUPLICATE_ADDRESS_LABEL` and `ERR_DUPLICATE_STRATUM_CODE` (all 409); `ERR_CREW_METHOD_NOT_CERTIFIED`, `ERR_CREW_OUTSIDE_SHIFT`, `ERR_EVIDENCE_SIDE_MISMATCH`, `ERR_REPLACED_SIDES_MISMATCH` and `ERR_SAMPLE_COUNT_INSUFFICIENT` (all 422); and `ERR_SAMPLE_NOT_FOUND` (404) when a supplied `sample_seq` matches no entry of the batch's `samples`.
21. **Temporal conflicts.** `ERR_CREW_WINDOW_CONFLICT` (409), `ERR_MORATORIUM_CONFLICT` (409), `ERR_COMPLIANCE_DEADLINE_PASSED` (409), `ERR_PERIOD_OVERLAP` (409) and `ERR_CLOCK_NOT_MONOTONIC` (422).
22. **Capacity conflicts.** `ERR_CREW_DAILY_CAPACITY_EXCEEDED` (409) and `ERR_EXCAVATION_CAPACITY_EXCEEDED` (409).
23. **Equity breach.** `ERR_EQUITY_REQUIREMENT_BREACH` (422) when a funding commit would leave an active source short of its equity requirement.
24. **Funding sufficiency.** `ERR_FUNDING_INSUFFICIENT` (402) when the candidate pool cannot cover the order's estimated cost. This is the last rung: an order that is both equity-breaching and underfunded reports the equity breach.

### 2.11. Segregation of Duties

Inventory certification is a two-person control. The `InventoryAnalyst` that drafts a publication has its `X-User-ID` recorded as `drafted_by_user_id`, and the `ComplianceOfficer` that later certifies it has its own `X-User-ID` recorded as `certified_by_user_id`. Those two identifiers must differ; if the certifying user id equals the drafting user id, certification fails with `ERR_SEGREGATION_OF_DUTIES`. The check compares user identifiers only — it does not compare roles, and it does not care whether the same human holds both roles in an external directory.

The crew binding of §2.1 is the mirror-image control on the field side: because a technician's `X-User-ID` *is* a crew row's `id`, a technician physically cannot drive another crew's appointment.

## 3. Business Logic & Workflows

### 3.1. Registering a Water System and Advancing Its Inventory Lifecycle

A `ProgramAdministrator` brings a utility into the program by registering a water system with its `pwsid` — the public water system identifier, which must be globally unique, a duplicate being refused with `ERR_DUPLICATE_PWSID` — a human-readable `system_name`, and the regulatory `compliance_deadline_date` (a calendar date in `YYYY-MM-DD` form) by which the count of unknown-material lines must reach zero. Four further inputs are optional at registration. `baseline_lead_and_grr_count` is the regulatory baseline tally of lead and galvanized lines that serves as the denominator of the mandated annual replacement rate; it defaults to 0 and may not be negative. `disadvantaged_tract_codes` is the list of census tract codes the state has designated disadvantaged, defaulting to the empty list. `funding_mode` selects which apportionment variant every replacement order of this system will use and defaults to `WATERFALL`, the alternative being `PRO_RATA`. And the corrosion-control trio — `cct_optimization_status`, defaulting to `NOT_REQUIRED` with `OPTIMIZED` and `PENDING_REOPTIMIZATION` as its other values; `cct_orthophosphate_mg_l`, the orthophosphate residual target in milligrams per litre, defaulting to null and constrained only to be not negative — the server does not couple it to `cct_optimization_status`, so a non-null residual is accepted and stored even while that status is `NOT_REQUIRED`; and `cct_target_ph`, defaulting to null and, when supplied, lying between 6.0 and 9.5 inclusive.

A freshly registered system starts with `inventory_status` at `DRAFT`, and because clause 1 of the posture rule fires on `DRAFT`, its `program_posture` is `FROZEN` from the very first moment. Its counters all start at zero: `total_service_line_count`, `lead_count`, `grr_count`, `non_lead_count`, `unknown_count` and `outstanding_notification_count` are integers starting at 0, and `unknown_share_pct` starts at 0.0. Those counters are pure aggregations over the system's service lines: `total_service_line_count` counts every service line of the system with no status filter whatsoever, and `lead_count`, `grr_count`, `non_lead_count` and `unknown_count` count the subsets whose `classification` is `LEAD`, `GRR`, `NON_LEAD` and `UNKNOWN` respectively. `unknown_share_pct` is 0.00 when the system has no service lines at all; otherwise it is one hundred times the unknown count divided by the total count, rounded half-up to two decimals. `outstanding_notification_count` counts the customer notifications belonging to this system's service lines whose `state` is `PENDING` or `RETURNED`.

The system's `inventory_status` follows four states — `DRAFT`, `VALIDATION_PENDING`, `PUBLISHED` and `AMENDMENT_PENDING` — and none of them is terminal. A `ComplianceOfficer` walks it out of `DRAFT` by supplying a `target_status` of `VALIDATION_PENDING`. That advance is permitted only when the system is currently in `DRAFT`, when it has at least one service line, and when no service line of the system is still sitting at `UNCLASSIFIED` on its classification axis; a request that does not describe a declared transition out of the current status is refused with `ERR_INVENTORY_STATE_INVALID`, and so are the empty-inventory and still-`UNCLASSIFIED` failures — all three conditions collapse onto that one code, whereas a `target_status` outside the four `inventory_status` names is caught earlier at rung 4 as `ERR_INVALID_ENUM_VALUE`. On success the server recomputes `program_posture` — leaving `DRAFT` lifts clause 1's freeze, though a later clause may still bite — and advances the water system's `version` by one.

The remaining three `inventory_status` edges are all server-driven and are described where they are triggered: `VALIDATION_PENDING → PUBLISHED` and `AMENDMENT_PENDING → PUBLISHED` fire as the second link of the publication fan-out in §3.5, and `PUBLISHED → AMENDMENT_PENDING` fires as the third link of any classification recompute in §3.2. That last pair forms the amendment cycle — a published inventory drops back to `AMENDMENT_PENDING` when a classification changes underneath it, and returns to `PUBLISHED` only when a newer publication publishes.

Two administrative levers adjust a registered system in place. A `ProgramAdministrator` may switch `funding_mode` between `WATERFALL` and `PRO_RATA`; the switch applies only to funding plans committed after the call, and `funding_allocations` rows already committed on existing orders are untouched. A `ComplianceOfficer` may update `cct_optimization_status` — the only non-optional field of that call — and, alongside it, `cct_orthophosphate_mg_l` and `cct_target_ph`, each of which is written only when its key is actually present in the request body: an omitted key leaves the stored value exactly as it stood, while a key present with an explicit `null` clears that value to null. The change recomputes `program_posture` and changes the corrosion-control multiplier that later replacement completions apply to their flushing guidance. Both levers advance the water system's `version` by one, and neither is gated on the posture or on any other precondition.

### 3.2. Inventorying Service Lines: Evidence, Governing Selection and Classification

An `InventoryAnalyst` adds a premise to the inventory by creating a service line under a `water_system_id`, with an `address_label` naming the service address and a `census_tract_code` naming the tract the premise sits in. The pair of water system and address label must be unique — a repeat is refused with `ERR_DUPLICATE_ADDRESS_LABEL`. Four inputs are optional: `street_project_id`, which links the premise into a paving project's coordination window and is null when absent; `serves_sensitive_population`, a boolean defaulting to false that is set true for schools, licensed child-care premises and dialysis facilities; `interior_diameter_mm`, the line's interior diameter in millimetres, defaulting to 19.0 and required to be strictly positive; and `total_length_m`, the combined utility-side plus customer-side length in metres, defaulting to 15.0 and likewise strictly positive. A fresh line is persisted with both side materials at `UNKNOWN`, `classification` at `UNKNOWN`, `certainty_basis` at `RECORDS_BASIS`, `certainty_score` and `replacement_priority_score` at 0.0, `consent_barrier_flag` false, and `disadvantaged_status` already evaluated against the parent system's `disadvantaged_tract_codes`; creation runs no classification recompute, so despite that `UNKNOWN` classification the replacement axis stays at `NOT_REQUIRED` and the line's `version` stays at 1. Creating a line refreshes the parent system's `total_service_line_count` and `unknown_share_pct`, and then its `program_posture`.

Each service line carries **two independent state axes**. The classification axis, `inventory_state`, starts at `UNCLASSIFIED` and moves among `CLASSIFIED_PROVISIONAL` and `CLASSIFIED_VERIFIED`. The replacement axis, `replacement_state`, starts at `NOT_REQUIRED` and moves among `ELIGIBLE`, `IN_PROGRAM`, `REPLACED_PARTIAL` and `REPLACED_FULL`. Neither axis is terminal and neither drives the other directly: a line may be `CLASSIFIED_PROVISIONAL` while already `IN_PROGRAM`, or `CLASSIFIED_VERIFIED` while still `NOT_REQUIRED`.

Material knowledge enters as **evidence items**. An `InventoryAnalyst` or a `FieldTechnician` records one by naming the `service_line_id`, the `source_type` from which the observation came, the `side` of the line it covers, the `observed_material` it found, and the `observed_at` instant in ISO 8601 UTC at which the observation was made; free-text `notes` are optional and default to null. `source_type` is one of `HISTORIC_RECORD`, `PREDICTIVE_MODEL`, `WATER_SAMPLING`, `VISUAL_INSPECTION` or `POTHOLE`. `side` is either `UTILITY` or `CUSTOMER`. `observed_material` is one of `LEAD`, `GRR`, `COPPER`, `PLASTIC` or `UNKNOWN`. A water-sampling observation may only describe the utility side; a `WATER_SAMPLING` item carrying `side` equal to `CUSTOMER` is refused with `ERR_EVIDENCE_SIDE_MISMATCH`, and the same code guards a completion cascade whose recorded side contradicts the side the appointment's method may legitimately observe.

Two properties of an evidence item are derived from its `source_type` alone and are fixed the moment it is created. Its `tier_rank` is 1 for `HISTORIC_RECORD`, 2 for `PREDICTIVE_MODEL`, 3 for `WATER_SAMPLING`, 4 for `VISUAL_INSPECTION` and 5 for `POTHOLE` — higher meaning more authoritative. Its `confidence_weight` is 0.40 for `HISTORIC_RECORD`, 0.55 for `PREDICTIVE_MODEL`, 0.70 for `WATER_SAMPLING`, 0.85 for `VISUAL_INSPECTION` and 1.00 for `POTHOLE`. Two further properties are set by the server: `origin`, which is `MANUAL` for an item created directly or by a classification override, `APPOINTMENT_CASCADE` for one synthesized by a completed verification appointment, and `REPLACEMENT_CASCADE` for one synthesized by a completed replacement; and `retracted`, a boolean starting false, paired with a `retraction_reason` starting null.

**Governing evidence.** For any given side of a line, exactly one evidence item governs, and it is chosen the same way every time. First an eligibility filter: the candidate pool is the evidence items of that line, for that side, whose `retracted` is false, and whose `source_type` is admissible under the line's active `certainty_basis`. Under `RECORDS_BASIS` only `HISTORIC_RECORD` and `PREDICTIVE_MODEL` are admissible; under `FIELD_BASIS` all five source types are. Then a ranking: the pool is ordered by `tier_rank` descending, so the highest tier wins; ties on tier are broken by `observed_at` descending, so the most recent observation wins; ties on both are broken by `created_at` descending, so the most recently recorded row wins — realized, exactly as in §2.3, as insertion sequence descending, so two items persisted inside the same millisecond still order deterministically by which was recorded second. The first row in that ordering governs. If the pool is empty, no evidence governs that side. An evidence item's `id` is never a ranking or tie-break input.

**Classification.** Whenever evidence is inserted — manually, by an override, by an appointment cascade or by a replacement cascade — whenever evidence is retracted, and whenever a line's `certainty_basis` flips, the server rewrites the line's derived material picture. `utility_side_material` becomes the `observed_material` of the governing utility-side item, or `UNKNOWN` when nothing governs that side; `customer_side_material` is derived the same way for the customer side. Both are drawn from `LEAD`, `GRR`, `COPPER`, `PLASTIC` and `UNKNOWN`, and both default to `UNKNOWN`. The line's `classification` is then the worst of the two sides, tested in a fixed order: if either side is `LEAD` the classification is `LEAD`; otherwise if either side is `GRR` it is `GRR`; otherwise if either side is `UNKNOWN` it is `UNKNOWN`; otherwise it is `NON_LEAD`. Note the third rung — an unknown side outranks a clean side, so a line with copper on the utility side and nothing at all on the customer side classifies as `UNKNOWN`, not `NON_LEAD`. In the same pass the server sets `disadvantaged_status` to true exactly when the line's `census_tract_code` is a member of the parent water system's `disadvantaged_tract_codes` list at that moment, and false otherwise.

**Certainty basis and the verification cycle.** A line's `certainty_basis` is `RECORDS_BASIS` while its `inventory_state` is `UNCLASSIFIED` or `CLASSIFIED_PROVISIONAL`, and `FIELD_BASIS` once its `inventory_state` is `CLASSIFIED_VERIFIED`. The test for leaving `UNCLASSIFIED` is simply whether the line currently holds at least one non-retracted evidence item, of any source type and on either side, so a line whose only item has since been retracted falls back to sitting at `UNCLASSIFIED`. The first non-retracted evidence item recorded for a line — or a first classification override — moves the line from `UNCLASSIFIED` to `CLASSIFIED_PROVISIONAL`, sets `certainty_basis` to `RECORDS_BASIS`, recomputes `disadvantaged_status`, both side materials, `classification`, `certainty_score` and `replacement_priority_score`, bubbles the water-system counters up, recomputes `program_posture` from the refreshed counters, and advances the line's `version` by one. Further evidence writes, retractions or overrides against an already-provisional line keep it at `CLASSIFIED_PROVISIONAL` — recomputing `classification` and `certainty_score` under `RECORDS_BASIS`, bubbling the counters and then the posture, and advancing `version` — for as long as the line does **not** hold both a utility-side and a customer-side non-retracted evidence item whose `source_type` is `VISUAL_INSPECTION` or `POTHOLE`. That `version` advance is unconditional: a recompute pass advances the line's `version` by one and refreshes its `updated_at` even when every derived value comes out identical to what it already held, and by a second increment on the same request when the replacement axis below also moves.

The moment that both-sides field-evidence condition does hold — immediately after any evidence insertion, whether manual, by override, or by an appointment cascade — the server moves the line from `CLASSIFIED_PROVISIONAL` to `CLASSIFIED_VERIFIED` on its own initiative. When the very write that lifts a line out of `UNCLASSIFIED` already satisfies the condition, the line makes both hops inside that one pass and lands directly on `CLASSIFIED_VERIFIED`. That transition sets `certainty_basis` to `FIELD_BASIS` and re-derives `utility_side_material`, `customer_side_material`, `classification` and `certainty_score` under the field variant: the very same evidence set now admits field observations into the pool, so a pothole or visual inspection outranks the records tier and supplies both the material and its higher weight. Under the records variant those field observations were excluded from *both* the material roll-up and the weight lookup, which is why an identical evidence set can yield a lower `certainty_score` and even a different `classification` depending on which basis is active. The transition also recomputes `replacement_priority_score`, because the verified bonus term switches on; bubbles the water-system counters up and recomputes `program_posture`; moves the water system from `PUBLISHED` to `AMENDMENT_PENDING` if it was published and this recompute changed the classification; and advances the line's `version` by one.

Retraction runs the cycle backwards. An `InventoryAnalyst` may retract an evidence item by supplying a `reason`; the server sets `retracted` to true, stores that text as `retraction_reason`, and re-derives the line's `classification` and `certainty_score`, because a retracted item is excluded from every governing-evidence pool from then on. Retracting an item whose `retracted` is already true is refused with `ERR_EVIDENCE_ALREADY_RETRACTED`. The call answers with the retracted evidence item itself; the service line it re-derived is not part of the response. If the retraction removes the last non-retracted `VISUAL_INSPECTION` or `POTHOLE` item on either side, so that the both-sides condition no longer holds, the server immediately moves the line from `CLASSIFIED_VERIFIED` back to `CLASSIFIED_PROVISIONAL`: `certainty_basis` returns to `RECORDS_BASIS`, `classification` and `certainty_score` are re-derived under the records variant so the records-basis value returns, `replacement_priority_score` is recomputed, the counters and posture are refreshed, the water system drops from `PUBLISHED` to `AMENDMENT_PENDING` if it was published and the classification moved, and the line's `version` advances by one. A retraction advances the evidence item's own `version` by one as well.

**Classification overrides.** An analyst who has definitive knowledge may assert a material directly. The override names the `side` it covers, the `asserted_material` it asserts, a `justification` recording why, and the `expected_service_line_version` guard of §2.9. The server implements it by inserting an evidence item at the top tier — `source_type` of `POTHOLE`, `origin` of `MANUAL`, `observed_at` set to the logical clock's current instant, and the supplied `justification` text stored verbatim as that item's `notes` — which by the ranking rule supersedes whatever previously governed that side. The call answers HTTP 200 with the recomputed `ServiceLine`, not with the evidence item it minted. It then recomputes `classification`, `certainty_score` and `replacement_priority_score`, may fire the `UNCLASSIFIED → CLASSIFIED_PROVISIONAL` or `CLASSIFIED_PROVISIONAL → CLASSIFIED_VERIFIED` transition, bubbles the water-system counters and then the posture, and advances the line's `version` by one.

**Certainty scoring.** A line's `certainty_score` runs from 0.00 to 100.00 and starts at 0.0. It is computed from exactly the two governing evidence items selected under the line's active basis; all other evidence is ignored. Each side contributes a certainty figure: zero when no item governs that side, zero when the governing item's `observed_material` is `UNKNOWN` — an unknown observation carries no certainty however authoritative its source — and otherwise the governing item's `confidence_weight`. The score then weights the two contributions unevenly, deliberately favouring the weaker side: one hundred multiplied by the sum of six tenths of the lower of the two side figures and four tenths of the higher of the two, rounded half-up to two decimal places. A line verified by potholing on both sides therefore reaches 100.00, while a line resting on a single historic record with nothing on the other side reaches 16.00.

**The replacement axis.** At the end of any classification recompute that lands the line's `classification` in `LEAD`, `GRR` or `UNKNOWN`, a line still sitting at `NOT_REQUIRED` moves to `ELIGIBLE`, its `replacement_priority_score` is recomputed, and its `version` advances by one. Symmetrically, a recompute that lands the classification at `NON_LEAD` moves a line sitting at `ELIGIBLE` back to `NOT_REQUIRED`, sets its `replacement_priority_score` to exactly 0.00, and advances its `version` by one. The remaining edges of this axis are driven by replacement orders and appear in §3.7.

### 3.3. Field Verification: Crews, Windows and Access Barriers

A `ProgramAdministrator` registers a verification crew under a `water_system_id` with a `crew_name`, a daily shift bounded by `shift_start_utc_time` and `shift_end_utc_time` — each a 24-hour `HH:MM` UTC clock time, the close strictly later than the open — a `daily_appointment_capacity` of at least 1, and a non-empty `certified_methods` list drawn from `VISUAL_INSPECTION`, `POTHOLE` and `WATER_SAMPLING`. A new crew's `status` is `ACTIVE`; the administrator may later flip it between `ACTIVE` and `INACTIVE`, which advances the crew's `version` by one. The crew also carries a derived `scheduled_appointment_count`, starting at 0, counting the appointments booked to it whose `state` is `SCHEDULED` or `ON_SITE`.

Booking a verification appointment is open to both a `ProgramAdministrator` and a `FieldTechnician`. The booking names the `service_line_id` to be verified, the `crew_id` to send, the `method` to perform — `VISUAL_INSPECTION`, `POTHOLE` or `WATER_SAMPLING` — and the crew occupation interval as `window_start_utc` (inclusive) and `window_end_utc` (exclusive, and strictly later than the start). The appointment is created with `state` equal to `SCHEDULED` and `attempt_count` equal to 1, and the crew's `scheduled_appointment_count` is refreshed.

Three gates guard a booking, and all three are re-applied identically when a parked appointment is re-booked into a new window. First, the requested `method` must be a member of the crew's `certified_methods`, else `ERR_CREW_METHOD_NOT_CERTIFIED`. Second, the window's UTC clock times must both fall inside the crew's shift, between `shift_start_utc_time` and `shift_end_utc_time` inclusive, and must sit on a single UTC calendar date; a window that escapes the shift or straddles midnight is refused with `ERR_CREW_OUTSIDE_SHIFT`. Third, the crew must not already be committed elsewhere at that time, and the collision test carries a travel buffer: measured against every other appointment of the same `crew_id` whose `state` is `SCHEDULED`, `ON_SITE` or `COMPLETED`, the booking is refused with `ERR_CREW_WINDOW_CONFLICT` when the new window's start is earlier than three quarters of an hour past the existing appointment's end **and** the new window's end is strictly later than the existing appointment's start. The buffer is applied to the existing appointment's end only, and the comparison at the new window's start is strict-less-than, so a new window beginning exactly 45 minutes after an existing one ends is accepted.

A fourth gate counts rather than compares. For the UTC calendar date on which the requested `window_start_utc` falls, the number of appointments of the same crew whose `state` is `SCHEDULED`, `ON_SITE` or `COMPLETED` and whose own `window_start_utc` falls on that same date must be strictly fewer than the crew's `daily_appointment_capacity`; a crew already holding its full day's load is refused with `ERR_CREW_DAILY_CAPACITY_EXCEEDED`. Note that completed appointments still consume both the overlap buffer and the daily quota — a crew's past work on a date does not free the date up.

An appointment's lifecycle spans five states — `SCHEDULED`, `ON_SITE`, `COMPLETED`, `NO_ACCESS` and `ABANDONED` — of which `COMPLETED` and `ABANDONED` are terminal. A `FieldTechnician` whose `X-User-ID` matches the appointment's `crew_id` moves it from `SCHEDULED` to `ON_SITE` on arrival, which additionally requires the assigned crew's `status` to be `ACTIVE`; arriving with an inactive crew is refused with `ERR_CREW_INACTIVE`. Arrival advances the appointment's `version` by one.

From `ON_SITE` the visit resolves one of two ways. **Completion** is the productive outcome: the technician records the `observed_side` — `UTILITY` or `CUSTOMER` — and the `observed_material` found, and the appointment moves to `COMPLETED`. That single write starts a four-link chain. The first link synthesizes an evidence item for the appointment's `service_line_id`, with `source_type` copied from the appointment's `method`, `side` copied from `observed_side`, `observed_material` copied from `observed_material`, `observed_at` set to the logical clock's current instant rather than to anything drawn from the appointment's window, `notes` left null, and `origin` set to `APPOINTMENT_CASCADE`; the new item's identifier is stored back onto the appointment as `emitted_evidence_item_id`, which is null until completion, as are the `observed_side` and `observed_material` the appointment echoes back, and as is `barrier_reason` until a barrier is reported. The second link runs that insertion through the service line's governing-evidence, `classification`, `certainty_score` and `replacement_priority_score` recompute, and may fire the line's `CLASSIFIED_PROVISIONAL → CLASSIFIED_VERIFIED` transition. The third link bubbles the change into the water system's `lead_count`, `grr_count`, `non_lead_count`, `unknown_count` and `unknown_share_pct` and recomputes `program_posture`. The fourth link moves the water system from `PUBLISHED` to `AMENDMENT_PENDING` when it was published and the classification actually changed, which by clause 3 of the posture rule forces `program_posture` to `RESTRICTED`. Completion also refreshes the crew's `scheduled_appointment_count` and advances the appointment's `version` by one.

**An access barrier** is the unproductive outcome, and it forks on how many attempts the crew has already spent. The technician supplies a `barrier_reason` drawn from `LOCKED_PREMISE`, `OCCUPANT_REFUSED`, `UTILITY_CONFLICT` and `WEATHER`. When the appointment's `attempt_count` is fewer than 3, the appointment is parked: it moves from `ON_SITE` to `NO_ACCESS`, the supplied reason is stored as `barrier_reason`, the crew's `scheduled_appointment_count` is refreshed, and `version` advances by one. When `attempt_count` has already reached 3, the same request instead terminates the appointment: it moves from `ON_SITE` to `ABANDONED`, and the supplied reason is stored as `barrier_reason`, the crew's `scheduled_appointment_count` is refreshed, and `version` advances by one exactly as in the parked case. The third exhausted attempt ends the pursuit rather than parking it again. On neither branch does the barrier report touch `attempt_count` — that counter only advances when the parked appointment is re-booked.

A parked appointment can be re-canvassed. A `ProgramAdministrator` re-books a `NO_ACCESS` appointment into a new `window_start_utc` and `window_end_utc`, which returns it to `SCHEDULED`, writes the new window onto the row, increases `attempt_count` by 1, refreshes the crew's `scheduled_appointment_count`, and advances `version` by one. The new window is subjected to the same shift, buffer-overlap and daily-capacity gates as an original booking. This closes the appointment cycle: `SCHEDULED → ON_SITE → NO_ACCESS → SCHEDULED`, with the third barrier report exiting the loop at `ABANDONED`.

### 3.4. Sampling Strata and Statistical Validation

Water sampling is organized by stratum. A `ComplianceOfficer` opens a sampling batch under a `water_system_id` with a `stratum_code` labelling the stratum — unique within the water system, a repeat being refused with `ERR_DUPLICATE_STRATUM_CODE` — and a `stratum_line_count` of at least 1 giving the stratum's population size. The batch opens with `state` equal to `OPEN`, `reopen_count` at 0, `rejection_reason` null, `valid_sample_count` at 0, `exceedance_count` at 0, `exceedance` false, and both `percentile_90_ppb` and `classification_confidence` null. Its `required_sample_count` is derived immediately: five per cent of the stratum population, rounded up to a whole line, but never fewer than 5 samples. A stratum of 40 lines therefore needs 5 samples, a stratum of 101 lines needs 6.

Samples are appended one at a time, by either a `FieldTechnician` or a `ComplianceOfficer`, to a batch that is still `OPEN`. Each append names the `service_line_id` sampled, the measured `lead_ppb` concentration — a number that may not be negative — the `collected_at` instant, and the `sample_type`, which is `FIRST_DRAW` or `FIFTH_LITER`. The server appends an entry to the batch's `samples` array with the next `sample_seq`, with `invalidated` false and `invalidation_reason` null, refreshes `valid_sample_count`, and advances the batch's `version` by one. It answers with the whole batch at HTTP 200, the appended entry visible inside its `samples` array rather than returned as a resource of its own; voiding a sample, validating and reopening all answer the same way. A `ComplianceOfficer` may later void a sample by naming its `sample_seq` and a `reason`; the server sets that entry's `invalidated` to true, stores the reason as its `invalidation_reason`, refreshes `valid_sample_count` and advances `version`. A `sample_seq` matching no entry of the array yields `ERR_SAMPLE_NOT_FOUND`. `valid_sample_count` is simply the number of entries whose `invalidated` is false.

Validation resolves the batch, and it is where the statistics live. Only entries with `invalidated` false participate — invalidated samples are excluded from the population count, from the percentile rank and from the exceedance tally alike. If the number of valid samples is strictly fewer than `required_sample_count`, validation is refused with `ERR_SAMPLE_COUNT_INSUFFICIENT`. Otherwise the valid samples are ordered by `lead_ppb` ascending with ties broken by `collected_at` ascending and any remaining tie broken by `sample_seq` ascending, and the ninetieth-percentile rank is computed by the one-based nearest-rank method: nine tenths of the valid-sample count, rounded up to a whole number. `percentile_90_ppb` is the `lead_ppb` of the sample occupying that rank in the ordering, reproduced exactly as stored. `exceedance` is true when `percentile_90_ppb` is strictly greater than the action level of 15.0 parts per billion — a ninetieth percentile of exactly 15.0 is **not** an exceedance. `exceedance_count` is the number of valid samples whose own `lead_ppb` is strictly greater than 15.0. And `classification_confidence` is one minus the exceedance count divided by the valid-sample count, rounded half-up to four decimal places.

The batch then resolves to one of two branches, both persisting `percentile_90_ppb`, `exceedance_count`, `exceedance` and `classification_confidence`, and both advancing the batch's `version` by one. When `classification_confidence` is at least 0.8000 — exactly 0.8000 validates — the batch moves from `OPEN` to `VALIDATED` and `rejection_reason` is left null. On that branch alone, and on that branch only when `exceedance` came out true, a second link fires: the parent water system's `cct_optimization_status` moves to `PENDING_REOPTIMIZATION`. That change has two consequences that reach well outside sampling, and they are the point of the whole coupling: while the system sits in `PENDING_REOPTIMIZATION`, every attempt to schedule an excavation window fails with `ERR_CCT_NOT_OPTIMIZED`, and every replacement completed in the meantime has its flushing guidance multiplied by one and a half. When `classification_confidence` is below 0.8000, the batch moves from `OPEN` to `REJECTED` instead, and `rejection_reason` is set to `CONFIDENCE_BELOW_FLOOR`. The rejected branch carries **no** corrosion-control side effect whatsoever; what it does carry is a blockage downstream, since a batch that is not `VALIDATED` keeps inventory certification for that water system failing with `ERR_UNVALIDATED_SAMPLING_STRATUM`.

A rejected batch can be reopened for another resample round. A `ComplianceOfficer` supplies a `reason`, the batch returns from `REJECTED` to `OPEN`, `reopen_count` increases by 1, and `percentile_90_ppb`, `classification_confidence` and `rejection_reason` are all cleared back to null while `exceedance` returns to false and `exceedance_count` returns to 0 — every statistic of the superseded round is discarded, so a reopened batch is indistinguishable from a freshly opened one. The batch's `version` advances by one. This is the resample cycle: `OPEN → REJECTED → OPEN`. Appending or invalidating a sample is only legal while the batch is `OPEN`, validation only from `OPEN`, and reopening only from `REJECTED`; anything else is `ERR_BATCH_STATE_INVALID`.

### 3.5. Publishing the Inventory and Notifying Customers

An `InventoryAnalyst` drafts an inventory publication for a `water_system_id`, declaring the `basis` under which the published counts were computed — `RECORDS` when they reflect the records variant, `FIELD_VERIFIED` when they reflect the field-verified variant — and a human-readable `reporting_period_label` such as `2026-H2`, alongside the `expected_water_system_version` guard of §2.9. The draft is created with `state` equal to `DRAFT` and `drafted_by_user_id` set to the caller's `X-User-ID`; any prior `DRAFT` publication of the same water system is discarded destructively — the row is removed from storage outright, so its identifier stops resolving and any later read of it answers `ERR_PUBLICATION_NOT_FOUND`, in deliberate contrast to the non-destructive supersede edge described below — and the water system's `version` advances by one. Drafting is refused while the system's posture is `FROZEN`. A publication's `state` walks `DRAFT`, `CERTIFIED`, `PUBLISHED` and the terminal `SUPERSEDED`; a request against a publication that is not in the declared origin state yields `ERR_PUBLICATION_STATE_INVALID`.

Certification is the `ComplianceOfficer`'s act and it is heavily gated. Beyond the publication being in `DRAFT` and the certifying user id differing from `drafted_by_user_id`, the water system must have at least one sampling batch and every one of its batches must be `VALIDATED`, else `ERR_UNVALIDATED_SAMPLING_STRATUM`; no customer notification belonging to the water system's service lines may currently be overdue, else `ERR_NOTIFICATION_OVERDUE_BLOCK`; and the logical clock's calendar date must be on or before the water system's `compliance_deadline_date`, else `ERR_COMPLIANCE_DEADLINE_PASSED`. When all of that holds, the publication moves to `CERTIFIED`, `certified_by_user_id` is set to the certifying `X-User-ID`, and the live water-system counters are frozen onto the publication as `pinned_lead_count`, `pinned_grr_count`, `pinned_unknown_count` and `pinned_non_lead_count` — all null before certification. `notifiable_line_count` is then set to the sum of the pinned lead, galvanized and unknown counts; it is the number of customer notifications the publish step will have to create. The publication's `version` advances by one.

Publishing is the officer's second act, and it re-validates the pin before it fans anything out. The publication must be `CERTIFIED`, and its `notifiable_line_count` must still equal the current number of service lines of that water system whose `classification` is `LEAD`, `GRR` or `UNKNOWN`; if the inventory has moved underneath the pin, publishing is refused with `ERR_PINNED_SNAPSHOT_STALE`. On success the publication moves from `CERTIFIED` to `PUBLISHED`, `published_at` is stamped with the logical clock's current instant, and `notification_due_at` is set to exactly thirty days after `published_at`. Then a three-link cascade runs. The first link creates exactly one customer notification in `state` `PENDING` for each service line of the water system whose `classification` is `LEAD`, `GRR` or `UNKNOWN`, walking those lines in their own insertion order so the notifications inherit that order, each carrying that line's `service_line_id`, this publication's identifier as `inventory_publication_id`, `notified_classification` copied from the line's classification at that moment, and `due_at` copied from the publication's `notification_due_at`. The second link recomputes the water system's `outstanding_notification_count` over the freshly created rows. The third link recomputes `program_posture`, which clause 4 forces to `RESTRICTED` for as long as any notification remains `PENDING` or `RETURNED`. Alongside the cascade, the water system's `inventory_status` moves to `PUBLISHED` — from `VALIDATION_PENDING` on a first publication, or from `AMENDMENT_PENDING` on a later one, the server simply writing `PUBLISHED` over whatever status it finds that is not `PUBLISHED` already — and its `version` advances by one on that write, while its `outstanding_notification_count` and `program_posture` re-derive on the next read. Should the status already read `PUBLISHED` when this publication publishes, there is nothing to write and the water system's `version` does not move at all.

A later publication supersedes an earlier one. When a publication of a water system reaches `PUBLISHED`, any other publication of the same water system that was in `PUBLISHED` moves to `SUPERSEDED` with `supersede_reason` set to `AMENDED_BY_NEWER_PUBLICATION`, and that superseded row's `version` advances by one. Superseding is deliberately not destructive downstream: the customer notifications created by the superseded publication keep their own `state` and are **not** cancelled. Both publications' identifiers remain resolvable, and the amendment cycle on the water system — `PUBLISHED → AMENDMENT_PENDING → PUBLISHED` — closes at this point.

**The notification chase.** A customer notification's `state` walks `PENDING`, `DELIVERED`, `RETURNED` and the terminal `ACKNOWLEDGED`; its `notified_classification` is one of `LEAD`, `GRR` or `UNKNOWN`, since only those lines are notifiable. It starts with `delivery_channel`, `delivered_at`, `acknowledged_at` and `return_reason` all null and `delivery_attempt_count` at 0, and it carries a derived `overdue` flag that is true exactly when the logical clock stands strictly later than the notification's `due_at` and its `state` is `PENDING` or `RETURNED` — a clock resting exactly on `due_at` is not yet overdue. A `CustomerRepresentative` records a successful delivery by supplying a `delivery_channel` — `MAIL`, `EMAIL` or `DOOR_HANGER` — and a `delivered_at` instant, which is stored verbatim as the client supplied it rather than re-formatted or replaced by the logical clock, as is `acknowledged_at` on acknowledgement; the notification moves to `DELIVERED`, `delivery_attempt_count` increases by 1, `return_reason` is cleared back to null, the water system's `outstanding_notification_count` is refreshed and its `program_posture` recomputed — the posture leaving `RESTRICTED` for `OPEN` once the counter reaches zero and no other clause applies — and the notification's `version` advances by one. Delivery is legal from `PENDING` and, on the redelivery leg, from `RETURNED`; anything else is `ERR_NOTIFICATION_STATE_INVALID`.

From `DELIVERED` the notification resolves two ways, and the two are symmetric obligations. Acknowledgement takes an `acknowledged_at` instant, moves the row to the terminal `ACKNOWLEDGED`, stores that instant, and advances `version` by one. A return takes a `return_reason` drawn from `ADDRESS_INVALID`, `REFUSED` and `VACANT`, moves the row from `DELIVERED` to `RETURNED`, stores that reason, clears `delivered_at` back to null, refreshes the water system's `outstanding_notification_count` — the row re-enters the outstanding set — and recomputes `program_posture`, which lands back on `RESTRICTED`; `version` advances by one. The return is the exact compensation for the delivery: it must restore `outstanding_notification_count` to precisely the value it held before that delivery. A returned notification can be delivered again, which closes the redelivery cycle `PENDING → DELIVERED → RETURNED → DELIVERED`, increases `delivery_attempt_count` again, and clears `return_reason` back to null.

### 3.6. Prioritizing Replacement Work

Every service line eligible for replacement carries a `replacement_priority_score` from 0.00 to 100.00, starting at 0.0, that the server recomputes on every classification recompute, on every `inventory_state` transition, and on every change to the line's `consent_barrier_flag`. Eleven steps produce it, and the step order is normative because a cap and a floor are applied at different points.

The first step converts material risk into points: 50.00 points for a `LEAD` line, 35.00 for a `GRR` line, 0.00 for a `NON_LEAD` line, and for an `UNKNOWN` line a sliding figure — forty multiplied by the quantity one minus one hundredth of the line's `certainty_score`, rounded half-up to two decimals — so an utterly uncharacterized unknown line earns the full 40.00 while an unknown line already carrying strong evidence earns proportionally less. The second step adds a certainty bonus of 15.00 points when the line's `inventory_state` is `CLASSIFIED_VERIFIED`, and nothing otherwise. The third step adds 25.00 equity points when the line's `disadvantaged_status` is true, and nothing otherwise.

The fourth step scores coordination with paving. The server takes the number of whole days from the logical clock's calendar date to the `paving_start_date` of the line's linked street project. When the line has no `street_project_id`, or when that day count is negative because paving has already begun, coordination contributes 0.00. Otherwise: 20.00 points when paving starts within three months, meaning ninety days or fewer; 12.00 points when it starts within a hundred and eighty days; 5.00 points when it starts within a full year, meaning three hundred and sixty-five days; and 0.00 beyond that. The fifth step adds 10.00 points when `serves_sensitive_population` is true.

The sixth step sums the five contributions into a raw total. The seventh caps that total, taking the lower of 100.00 and the raw figure, and separately never letting it fall below 0.00. The eighth step computes a barrier penalty of 8.00 points when the line's `consent_barrier_flag` is true and 0.00 otherwise; the ninth subtracts that penalty from the capped total and rounds half-up to two decimals. The tenth step establishes an equity floor of 65.00 — but only for a line whose `disadvantaged_status` is true **and** whose `classification` is `LEAD` or `GRR`; for every other line the floor is 0.00. The eleventh and last step takes the greater of the penalized figure and the floor, rounded half-up to two decimals, and stores it as `replacement_priority_score`. Because the cap is applied before the penalty and the floor after it, a disadvantaged galvanized line with no paving coordination and no sensitive population — 35.00 plus 25.00, or 60.00 raw — is lifted by the floor to 65.00 whether or not it carries a consent barrier.

The `consent_barrier_flag` itself is derived, not supplied: it is true exactly when the most recently created replacement order of that service line whose `fulfillment_state` is not `CANCELLED` has a `consent_state` of `DENIED` or `NO_RESPONSE`. Cancelled orders are skipped outright rather than merely outranked, so cancelling the order that raised the barrier hands the determination to the newest surviving order, or clears the flag altogether when no order survives. It is the mechanism by which a customer's refusal feeds back into the queue, and §3.7 describes when it flips.

**Street projects** supply the coordination input and two hard constraints. A `ProgramAdministrator` registers one under a `water_system_id` with a `project_name`, a post-paving cut moratorium bounded by `moratorium_start_date` and `moratorium_end_date` as inclusive calendar dates with the end on or after the start, and a `paving_start_date` that drives the coordination tier above. `max_concurrent_excavations` is optional, defaults to 1, and must be at least 1; it caps how many non-terminal excavation windows of this project may overlap on any single calendar date. The project also carries a derived `active_excavation_order_count`, starting at 0, counting the replacement orders linked to it whose `fulfillment_state` is `SCHEDULED` or `IN_PROGRESS`. Registering a project immediately re-derives the coordination tier of every service line already linked to it, advancing such a line's `version` only when its `replacement_priority_score` actually comes out different; because a line's `street_project_id` has to resolve at the moment the line is created, no line can already be linked to a project that does not yet exist, so in practice that pass finds nothing to re-tier.

**Funding sources** supply the money and its equity strings. A `ProgramAdministrator` authorizes one under a `water_system_id` with a `source_kind` of `STATE_REVOLVING_FUND`, `FEDERAL_GRANT` or `RATE_REVENUE`, an `authorized_cents` of at least 1 cent, and a `priority_rank` of at least 1 that governs both waterfall fill order and pro-rata remainder assignment, lower ranks going first. `max_share_pct` is optional, defaults to 100.0, must be greater than 0.0 and at most 100.0, and caps the percentage of any single order's estimated cost this source may fund. `equity_required_pct` is optional, defaults to 0.0, lies between 0.0 and 100.0 inclusive, and sets the minimum percentage of this source's committed-plus-drawn dollars that must sit on disadvantaged service lines. A new source starts with `status` `ACTIVE`, `committed_cents` and `drawn_cents` at 0, and `available_cents` equal to `authorized_cents`.

The ledger on a funding source is fully derived and holds a conservation identity: `available_cents` is always `authorized_cents` less `committed_cents` less `drawn_cents`. `committed_cents` sums the `allocated_cents` of every allocation row naming this source whose allocation `state` is `COMMITTED`; `drawn_cents` sums those whose allocation `state` is `DRAWN`. `disadvantaged_committed_cents` is the portion of committed plus drawn dollars whose order's service line has `disadvantaged_status` true. `disadvantaged_share_pct` is 0.00 when committed plus drawn is zero, and otherwise one hundred times `disadvantaged_committed_cents` divided by committed plus drawn, rounded half-up to two decimals. `equity_shortfall_cents` is the amount by which the source falls short of its own equity requirement: take committed plus drawn, multiply by `equity_required_pct`, divide by one hundred, round that product up to a whole cent, subtract `disadvantaged_committed_cents`, and clamp the result at zero so it is never negative. A `ProgramAdministrator` may move a source's `status` among `ACTIVE`, `SUSPENDED` and `CLOSED`; only `ACTIVE` sources enter the apportionment candidate pool, and only `ACTIVE` sources are scanned by clause 5 of the posture rule, so suspending a shortfall-carrying source lifts that restriction. A status change recomputes the water system's `program_posture` and advances the source's `version` by one.

### 3.7. Replacement Orders: Consent, Money, Excavation and Close-Out

A `ProgramAdministrator` opens a replacement order against a service line by naming its `service_line_id`, the total `estimated_cost_cents` to be apportioned across funding sources (at least 1 cent), and the intended excavation window as `excavation_start_date` and `excavation_end_date`, inclusive calendar dates with the end on or after the start. An optional `street_project_id` links the order to a paving project, in which case the excavation window will be checked against that project's moratorium and excavation capacity. Three gates guard the opening: the line's `replacement_state` must be `ELIGIBLE` or `REPLACED_PARTIAL`, else `ERR_LINE_NOT_ELIGIBLE`; the water system's `inventory_status` must be `PUBLISHED` or `AMENDMENT_PENDING`, because replacement may not precede publication, else `ERR_INVENTORY_NOT_PUBLISHED`; and the `program_posture` must not be `FROZEN`. The new order is created with `fulfillment_state` `DRAFT` and `consent_state` `NOT_REQUESTED`, and the service line moves to `IN_PROGRAM` — from `ELIGIBLE` on a first order, or from `REPLACED_PARTIAL` on a follow-up order covering the customer side of an already partially replaced line, closing that axis's cycle `IN_PROGRAM → REPLACED_PARTIAL → IN_PROGRAM`. The move is unconditional once the eligibility gate has passed: the server consults neither the line's `classification` nor which side the follow-up order intends to cover. Either way the line's `consent_barrier_flag` is re-derived, its `replacement_priority_score` recomputed, and its `version` advances by one.

Like a service line, a replacement order carries **two independent axes**. The work axis, `fulfillment_state`, walks `DRAFT`, `SCOPED`, `FUNDED`, `SCHEDULED`, `IN_PROGRESS` and the terminal `COMPLETED` and `CANCELLED`. The consent axis, `consent_state`, walks `NOT_REQUESTED`, `REQUESTED`, `GRANTED`, `DENIED` and `NO_RESPONSE`, of which `GRANTED` and `DENIED` are terminal and `NO_RESPONSE` is not. The consent axis advances while the work axis is still `DRAFT`, and the fork out of `DRAFT` consumes it.

**Canvassing consent.** A `CustomerRepresentative` requests consent for the customer-side portion, moving `consent_state` from `NOT_REQUESTED` to `REQUESTED` while `fulfillment_state` is still `DRAFT`, and advancing the order's `version` by one. The customer's answer arrives as a consent response carrying an `outcome` of `GRANTED`, `DENIED` or `NO_RESPONSE`, plus an optional `barrier_reason` that becomes mandatory on the two non-granting outcomes and is drawn from `COST`, `REFUSED`, `NO_CONTACT` and `ACCESS_DENIED`. A non-granting outcome arriving without one is `ERR_INVALID_REQUEST` (400), raised at rung 3 of §2.10 and therefore ahead of the order's own path resolution and state check. Either way the work axis forks from `DRAFT` to `SCOPED`, but the two branches are materially different.

On the **granting branch**, with `outcome` of `GRANTED`, the order's `scope` is set to `FULL` and its `consent_state` to `GRANTED`. The service line's `consent_barrier_flag` stays false and its `replacement_priority_score` is recomputed in place with no barrier penalty — but the line is not booked as mutated for that, so neither its `updated_at` nor its `version` moves. The order's `version` advances by one. This branch touches no other field of the service line.

On the **non-granting branch**, with `outcome` of `DENIED` or `NO_RESPONSE` and a `barrier_reason` present, the order's `scope` is set to `PARTIAL`, its `consent_state` to the supplied outcome, and its `consent_barrier_reason` to the supplied barrier reason. Two further links then fire. The first sets the service line's `consent_barrier_flag` to true, since this order is now the line's most recent one. The second recomputes the line's `replacement_priority_score`, subtracting the 8.00-point barrier penalty and then applying the disadvantaged equity floor — which is why a disadvantaged lead or galvanized line can absorb the penalty without its score moving at all. The order's `version` advances by one. Where the granting branch mutates no service-line field, this branch mutates two.

A `NO_RESPONSE` order can be re-canvassed, and only a `NO_RESPONSE` order can. A second consent request against an order whose `consent_state` is `NO_RESPONSE` and whose `fulfillment_state` is `SCOPED` returns `consent_state` to `REQUESTED` and walks the work axis back from `SCOPED` to `DRAFT`, clearing `scope` and `consent_barrier_reason` to null, setting the service line's `consent_barrier_flag` back to false and recomputing its `replacement_priority_score` without the barrier penalty, and advancing the order's `version` by one and the line's by one as well. This is the work axis's cycle `DRAFT → SCOPED → DRAFT`, and it is reachable only through the no-response outcome — a `GRANTED` or `DENIED` order has no such edge.

**Assembling funding.** A `ProgramAdministrator` commits a funding plan against a `SCOPED` order, moving it to `FUNDED`. The consent canvass must be resolved first, per rung 12 of §2.10; the water system's `program_posture` must not be `FROZEN`; the apportionment must cover the order's `estimated_cost_cents` in full; and no `ACTIVE` funding source of the water system may end the commit carrying an `equity_shortfall_cents` above zero, else `ERR_EQUITY_REQUIREMENT_BREACH`.

The candidate pool is pinned. It comprises the funding sources of the order's water system whose `status` is `ACTIVE` and whose `available_cents` is strictly greater than zero, ordered by `priority_rank` ascending with ties broken by `created_at` ascending. Suspended sources, closed sources and exhausted sources are excluded outright. If the pool is empty, the commit fails with `ERR_FUNDING_INSUFFICIENT` (HTTP 402). Which apportionment then runs depends on the water system's `funding_mode`, read at commit time and frozen onto the order as `funding_mode_applied`.

Under the **waterfall** variant, the sources are filled in candidate order. For each source the server first computes that source's cap as the order's total estimated cost multiplied by the source's `max_share_pct`, divided by one hundred, and truncated downward to a whole cent — note that the cap is computed against the order total, not against what remains. The amount allocated to that source is then the smallest of three quantities: the cost still remaining to be covered, the source's `available_cents`, and that cap. When the allocated amount is above zero, an allocation row is appended naming the source as `funding_source_id`, the amount as `allocated_cents`, the source's `priority_rank`, and an allocation `state` of `COMMITTED`; when it comes out at zero the source is omitted from `funding_allocations` entirely. The remaining cost is reduced by each allocation in turn. If any cost still remains after every candidate has been offered, the commit fails with `ERR_FUNDING_INSUFFICIENT`.

Under the **pro-rata** variant, the server first sums the `available_cents` of every candidate into a pool; if that pool is smaller than the order's total, the commit fails with `ERR_FUNDING_INSUFFICIENT` before anything is allocated. Otherwise every candidate receives a row, in the same candidate order, proportional to its own share of the pool: the order total multiplied by that source's `available_cents`, divided by the pool. Each source's share is rounded half-up to whole cents **individually and first** — the alternative approaches of summing exact shares and rounding the total once, or of rounding a running cumulative share, are explicitly not used. Only after every per-source share has been rounded does the server reconcile: the difference between the order total and the sum of the rounded allocations is added to the first row, which is the row of the lowest `priority_rank` source. That difference may be negative, in which case that row absorbs the reduction. Under pro-rata, `max_share_pct` is not applied at all. The same order cost against the same pool of sources therefore produces a different number of allocation rows and different per-source cents under the two variants.

The commit then writes its consequences. `funding_allocations` is populated with the `COMMITTED` rows, `funding_mode_applied` records which variant ran, and `allocated_total_cents` is set to the order's `estimated_cost_cents` — it is the sum of allocation amounts whose allocation `state` is `COMMITTED` or `DRAWN`. For every referenced funding source, `committed_cents` increases by that source's allocated amount, `available_cents` is re-derived as `authorized_cents` less `committed_cents` less `drawn_cents`, and `disadvantaged_committed_cents`, `disadvantaged_share_pct` and `equity_shortfall_cents` are recomputed. The water system's `program_posture` is then recomputed from the refreshed sources. The order's `version` advances by one.

**Scheduling and breaking ground.** A `ReplacementContractor` schedules a `FUNDED` order into a concrete window by supplying `excavation_start_date` and `excavation_end_date`, moving the order to `SCHEDULED`. Four gates apply. The water system's `program_posture` must be exactly `OPEN`. Its `cct_optimization_status` must not be `PENDING_REOPTIMIZATION` — excavation may not proceed while corrosion control is being re-optimized — else `ERR_CCT_NOT_OPTIMIZED`. The remaining two gates belong to the linked street project, and an order carrying no `street_project_id` clears both of them vacuously — only the posture and corrosion-control gates apply to such an order. The requested window must not intersect the linked street project's moratorium: with both windows treated as closed inclusive date ranges, the request is refused with `ERR_MORATORIUM_CONFLICT` when the excavation start falls on or before the moratorium end and the excavation end falls on or after the moratorium start. And street capacity must hold for **every** calendar date in the requested closed window: for each such date, the number of *other* replacement orders of the same `street_project_id` whose `fulfillment_state` is `SCHEDULED` or `IN_PROGRESS` and whose own closed excavation window includes that date must be strictly fewer than the project's `max_concurrent_excavations`, else `ERR_EXCAVATION_CAPACITY_EXCEEDED`. On success the supplied dates are written onto the order, the street project's `active_excavation_order_count` is refreshed, and the order's `version` advances by one. Breaking ground moves the order from `SCHEDULED` to `IN_PROGRESS`, refreshes `active_excavation_order_count` again, and advances `version` by one.

**Closing out.** The contractor completes an `IN_PROGRESS` order by supplying the `completed_at` instant and the `replaced_sides` array recording which portions were actually replaced. That array must match the order's `scope` exactly — both `UTILITY` and `CUSTOMER` for a `FULL` order, `UTILITY` alone for a `PARTIAL` one — else `ERR_REPLACED_SIDES_MISMATCH`. "Exactly" is tested both as a set and by length, so a repeated entry such as `["UTILITY", "UTILITY"]` against a `PARTIAL` order is refused too; the array must also be non-empty, a rung-3 failure, and every entry must be `UTILITY` or `CUSTOMER`, a rung-4 failure. Completion stamps `completed_at`, computes `flushing_duration_minutes`, and then runs a four-link financial chain. The first link flips every row of `funding_allocations` from `COMMITTED` to `DRAWN`. The second moves each affected funding source's money from one bucket to the other — `committed_cents` decreases by the allocated amount and `drawn_cents` increases by the same amount — which leaves `available_cents` unchanged, since the conservation identity subtracts both buckets. The third recomputes each affected source's `disadvantaged_share_pct` and `equity_shortfall_cents`. The fourth recomputes the water system's `program_posture`, which clause 5 drives to `RESTRICTED` if any active source now carries a non-zero `equity_shortfall_cents`. The street project's `active_excavation_order_count` is refreshed and the order's `version` advances by one.

Completion also settles the service line. A `FULL` order moves the line's `replacement_state` from `IN_PROGRAM` to `REPLACED_FULL`; a `PARTIAL` order moves it to `REPLACED_PARTIAL`. In both cases the server synthesizes exactly one evidence item per entry of `replaced_sides`, each with `source_type` `POTHOLE`, `side` equal to that entry, `observed_material` `COPPER`, `observed_at` equal to the order's `completed_at`, and `origin` `REPLACEMENT_CASCADE`; each insertion re-runs the line's classification and certainty recompute, which bubbles the water-system counters up and then recomputes `program_posture`. The two branches therefore diverge in their downstream effect: a full replacement lands field evidence on **both** sides, so the both-sides condition of §3.2 fires and the line reaches `CLASSIFIED_VERIFIED` with `classification` `NON_LEAD`; a partial replacement lands it on the utility side only, so the customer side keeps whatever previously governed it, the line stays `CLASSIFIED_PROVISIONAL` on `RECORDS_BASIS`, and its `classification` does not move off `LEAD`, `GRR` or `UNKNOWN`. Both `REPLACED_FULL` and `REPLACED_PARTIAL` are sticky: the `NON_LEAD` recompute does **not** drag `replacement_state` back to `NOT_REQUIRED`.

**Flushing guidance.** `flushing_duration_minutes` is null on a freshly opened order and stays null until completion writes it, as `completed_at`, `funding_mode_applied`, `scope` and `cancellation_reason` stay null until their own steps write them and `replaced_sides` stays an empty array. It is computed at completion in six steps from the replaced line's geometry, the order's scope, and the water system's corrosion-control posture at that moment. First the line's radius in metres is its `interior_diameter_mm` divided by two thousand. Second, the pipe volume in litres is pi — taken as 3.141592653589793 — multiplied by the square of that radius, multiplied by the line's `total_length_m`, multiplied by one thousand, and rounded half-up to two decimals. Third, the volume-driven flushing time is that litre figure multiplied by three complete pipe turnovers, divided by a flush rate of 20.0 litres per minute, and rounded up to a whole minute. Fourth, a partial replacement adds a fifteen-minute penalty, a full replacement adds nothing. Fifth, the corrosion-control multiplier is one and a half when the water system's `cct_optimization_status` is `PENDING_REOPTIMIZATION` and exactly one otherwise. Sixth and last, the stored value is a base half-hour of 30 minutes plus the volume minutes plus the partial penalty, that whole sum multiplied by the corrosion-control multiplier, and the product rounded up to a whole minute.

**Cancelling and compensating.** A `ProgramAdministrator` may cancel an order that has not yet broken ground — from `DRAFT`, from `SCOPED`, from `FUNDED` or from `SCHEDULED`, but never from `IN_PROGRESS` or from a terminal state, an attempt at which yields `ERR_ORDER_STATE_INVALID`. Every cancel takes a `reason`, stores it as `cancellation_reason`, moves the order to `CANCELLED`, returns the service line's `replacement_state` from `IN_PROGRAM` to `ELIGIBLE`, and advances both rows' `version` by one. What differs is the financial compensation. The consent-side compensation does not differ: every cancel, `DRAFT` included, re-derives the service line's `consent_barrier_flag`, recomputes its `replacement_priority_score` and advances the line's `version` — the recompute is unconditional rather than reserved for the `SCOPED` case, and it simply comes out unchanged when the cancelled order never raised a barrier. Cancelling from `DRAFT` needs no money returned, since none was ever committed, and cancelling from `SCOPED` likewise returns none; what the `SCOPED` case settles is the barrier, since the order that set it is gone. Cancelling from `FUNDED` runs the full financial reversal: every row of `funding_allocations` flips from `COMMITTED` to `RELEASED`; each referenced source's `committed_cents` decreases by that row's allocated amount and its `available_cents` is re-derived as `authorized_cents` less `committed_cents` less `drawn_cents`, which restores `available_cents` to exactly its pre-commit value; `disadvantaged_committed_cents`, `disadvantaged_share_pct` and `equity_shortfall_cents` are recomputed, and then the water system's `program_posture`; and the order's `allocated_total_cents` is set back to 0 — the `RELEASED` rows stay on `funding_allocations` for the record and are simply excluded from that derived total, which sums only `COMMITTED` and `DRAWN` rows. Cancelling from `SCHEDULED` runs that same financial reversal and additionally refreshes the street project's `active_excavation_order_count`.

### 3.8. Compliance Progress Reporting

A `ComplianceOfficer` files a progress report for a closed reporting period by naming the `water_system_id` and the inclusive period bounds `period_start_date` and `period_end_date`, the end on or after the start. The period may not intersect any period already filed for the same water system — the comparison treats both periods as closed inclusive ranges — else `ERR_PERIOD_OVERLAP`. Filing computes the entire report in one pass; the row is immutable thereafter and carries no `version`. Alongside that computed body the row records the three inputs it was filed with — `water_system_id`, `period_start_date` and `period_end_date` — and returns them with it.

The report's population is the replacement orders of that water system whose `fulfillment_state` is `COMPLETED` and whose `completed_at` calendar date falls inside the period, inclusive of both bounds. Cancelled and still-running orders are excluded entirely. `full_replacement_count` is the number of those orders whose `scope` is `FULL`; `partial_replacement_count` is the number whose `scope` is `PARTIAL`; and `disadvantaged_full_count` is the subset of the full ones whose service line has `disadvantaged_status` true.

Six steps then produce the credit picture, and the order matters because two of the values look circular but are not. The first step computes `base_credit` as the full-replacement count plus half the partial-replacement count, that half-weighted term rounded half-up to two decimals — a partial replacement earns half the credit of a full one. The second step computes the report's own `disadvantaged_share_pct` as one hundred multiplied by `disadvantaged_full_count`, divided by the greater of 1 and `full_replacement_count` so that an empty period never divides by zero, rounded half-up to two decimals; the `equity_tier` and its `equity_multiplier` are keyed on that share **and on nothing else** — never on `base_credit` and never on `total_credit`. A share of at least 60.00 is `TIER_A` with a multiplier of 1.20; at least 40.00 is `TIER_B` at 1.10; at least 20.00 is `TIER_C` at 1.00; anything below that is `TIER_D` at 0.90. The third step computes `total_credit` as `base_credit` multiplied by `equity_multiplier`, rounded half-up to two decimals.

The fourth step computes `mandated_annual_credit` as one tenth of the water system's `baseline_lead_and_grr_count`, rounded up to a whole credit — the regulator's ten-per-cent-a-year replacement rate expressed against the regulatory baseline. The fifth step reads `deferral_allowance` off the `total_credit` computed in step three: 3 when `total_credit` is at least 20, 2 when it is at least 10, and 1 otherwise. This step is evaluated exactly once, against the step-three `total_credit`; it is not re-derived from the total plus the allowance, and not from the shortfall. The sixth step computes `shortfall_credit` as the mandated annual credit less the deferral allowance less the total credit, clamped at zero so it never goes negative, rounded half-up to two decimals, and sets `compliance_status` to `ON_TRACK` when `shortfall_credit` is exactly zero and `BEHIND` otherwise.

The report also carries a simple physical-progress measure, evaluated at filing time over the whole inventory rather than over the period. `replaced_count` is the number of service lines of the water system whose `replacement_state` is `REPLACED_FULL` or `REPLACED_PARTIAL`. `baseline_denominator` is the sum of the water system's `lead_count`, `grr_count` and `unknown_count` plus that replaced count, so that non-lead lines which were never replaced contribute to neither the numerator nor the denominator. `replacement_progress_pct` is defined as exactly 100.00 when `baseline_denominator` is zero — the empty-universe case is a definition, never a division by zero — and otherwise one hundred times `replaced_count` divided by `baseline_denominator`, rounded half-up to two decimals.

## 4. Endpoint Definitions

Every resource collection is mounted directly beneath the `/lsl` prefix; parentage is carried in request bodies as foreign-key fields rather than in nested URL paths. Endpoints that mint a new top-level resource respond with HTTP 201 and the created resource in `data`; endpoints that modify, transition or read an existing resource respond with HTTP 200 and, in `data`, the row named by the last identifier segment of the path — so a classification override answers with the recomputed `ServiceLine` rather than the `EvidenceItem` it minted, a sample append or void answers with the whole `SamplingBatch` rather than the embedded sample, an appointment completion answers with the `VerificationAppointment` rather than the evidence item or service line it cascaded into, and an order transition answers with the `ReplacementOrder` rather than any funding source, street project or service line it touched. Those first two are also the only two exceptions to the 201 rule: minting an `EvidenceItem` through an override and minting an embedded sample both answer 200 with their parent row instead. The clock endpoint is not a resource at all and answers 200 with the bare `current_utc` / `previous_utc` object of §2.5. ## 5. Error Code Catalogue

The API uses a fixed vocabulary of error identifiers. Each identifier maps to exactly one HTTP status code regardless of which endpoint raises it; the conditions that raise each one are specified in §2 and §3, and the order in which competing conditions are reported is the ladder in §2.10.
