# Inpatient Psychiatric Admission API — Product Requirements Document

## 1. Introduction

A hospital behavioral health unit operates under two pressures that pull in opposite directions. Clinically, staff must move a person in crisis from an emergency evaluation into a safe bed quickly, with restraint used only as a last resort and only under continuous documented observation. Legally, every hour a patient is detained against their will is an hour that must be justified on the record: a signed statutory criterion, a physician certification landing inside a four-hour window, a petition filed before a court cutoff, a hearing with independent patient representation, and a written answer to any request for discharge. When those two pressures collide, the failure mode is not a clinical one — it is a rights violation that surfaces months later in an audit.

This document specifies the Inpatient Psychiatric Admission API, the system of record that reconciles both. It governs emergency evaluation and legal hold initiation with statutory time limits, hold extension petitions and court hearing scheduling with assigned patient representation, voluntary conversion and patient-initiated discharge requests against a running response clock, bed availability with gender and acuity mixing rules, restraint and seclusion authorization with monitoring and debriefing documentation, the contraband and safety search protocol at admission, medication consent, capacity determination with substitute decision makers, and discharge planning with guaranteed outpatient follow-up. All resources are mounted under the `/behavioral-health` namespace.

Two design commitments run through everything that follows. First, an admission carries **two independent state axes** — a legal axis describing why the patient may be held, and a placement axis describing where the patient physically is — and the two never move each other implicitly. Second, time is a first-class, server-controlled input: the system runs on a logical clock and applies statutory lapses only when an explicit compliance sweep is invoked, so that a deadline never passes silently in the middle of a request.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. Exactly five roles exist, spelled precisely as follows: `ComplianceOfficer`, `IntakeClinician`, `AttendingPsychiatrist`, `ChargeNurse`, and `PatientRightsAdvocate`. A request missing either header, or presenting an `X-User-Role` value outside this set of five, is rejected with `ERR_UNAUTHENTICATED` (401). A syntactically valid request whose acting role is not authorized for the target operation is rejected with `ERR_UNAUTHORIZED` (403). The same 403 code covers one role-scoped payload restriction: only an `AttendingPsychiatrist` may supply a `posture_override_reason` when placing an admission, so the same field submitted by a `ChargeNurse` is a permission failure rather than a schema failure.

When `X-User-Role` is `IntakeClinician`, `AttendingPsychiatrist`, `ChargeNurse`, or `PatientRightsAdvocate`, `X-User-ID` is the `id` of the acting `Clinician` row. Attribution and ownership checks on any resource that references a `Clinician` compare that resource's clinician foreign-key field to `X-User-ID`. Concretely, the server copies `X-User-ID` into `evaluating_clinician_id` on an evaluation, `initiated_by_clinician_id` and later `certifying_clinician_id` on a hold, `petitioning_clinician_id` on a petition, `admitting_clinician_id` and `search_performed_by_clinician_id` on an admission, `ordered_by_clinician_id` and later `face_to_face_clinician_id` on a restraint episode, `recorded_by_clinician_id` on each monitoring log entry, `determined_by_clinician_id` on a capacity determination, `prescribing_clinician_id` on a medication consent, and `recorded_by_clinician_id` and later `responding_clinician_id` on a discharge request. Every segregation-of-duties comparison described in §2.10 is a comparison between one of those stored fields and the current `X-User-ID`.

When `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The roster, inventory, logical-clock, sweep and court-disposition operations this role performs never write it onto a resource and never compare it to any entity's `id`; the server may log it, but no field stores it. A `ComplianceOfficer` therefore cannot satisfy any rule that requires the actor to be a specific `Clinician`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. The `limit` parameter caps the number of records returned; it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. The `offset` parameter skips records from the front of the result set; it defaults to 0 and its minimum accepted value is 0. A value outside those bounds is a schema failure and yields `ERR_INVALID_REQUEST`.

Unless a specific operation says otherwise, list results are sorted by `created_at` in ascending order. Every list response reports `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the size of the filtered set before pagination is applied and `has_more` indicates whether records remain beyond the current page.

Beyond `limit` and `offset`, each collection accepts equality filters on the identifier and status fields named in its §4 description. Evaluations may be filtered by `patient_id`, `evaluating_clinician_id` and `status`. Holds accept `patient_id`, `evaluation_id`, `predecessor_hold_id`, `initiated_by_clinician_id`, `certifying_clinician_id` and `status`. Petitions accept `hold_id`, `petitioning_clinician_id` and `status`; hearings accept `petition_id`, `advocate_clinician_id` and `status`. Admissions accept `patient_id`, `unit_id`, `bed_id`, `evaluation_id`, `admitting_clinician_id`, `search_performed_by_clinician_id`, `search_witness_clinician_id`, `legal_status` and `placement_status`. Restraint episodes accept `admission_id`, `ordered_by_clinician_id`, `face_to_face_clinician_id` and `status`. Capacity determinations accept `admission_id`, `determined_by_clinician_id` and `status`; medication consents accept `admission_id`, `capacity_determination_id`, `prescribing_clinician_id` and `status`; discharge requests accept `admission_id`, `recorded_by_clinician_id`, `responding_clinician_id` and `status`. The bed listing of a unit accepts `status` and `bed_type`.

### 2.4. The Logical Clock and the Statutory Compliance Sweep

Every timestamp the server writes, and every deadline comparison it performs, reads a server-held **logical clock** rather than the real wall clock. At process startup that clock holds exactly `2026-08-01T00:00:00Z`; until an operator moves it, all deadline arithmetic is anchored to that default. A `ComplianceOfficer` moves the clock by submitting a `to_iso8601` instant, and the response body reports the new value as `current_utc`. Moving the clock changes no entity state whatsoever — nothing expires, nothing transitions, no counter is recomputed.

Statutory lapses are applied only by an explicit compliance sweep, also restricted to a `ComplianceOfficer`, and always evaluated against the clock's current value. One sweep performs four families of expiry and reports how many records each family touched, as `expired_hold_count`, `expired_restraint_count`, `expired_discharge_request_count` and `expired_consent_count`: an `ACTIVE` hold whose release deadline has arrived moves to `EXPIRED` with its full cascade; a restraint episode still in `ORDERED` past its face-to-face deadline, or still in `ACTIVE` at or past its authorization end, moves to `EXPIRED_UNAUTHORIZED`; a `PENDING` discharge request past its response deadline moves to `EXPIRED_UNANSWERED`; and a `MedicationConsent` in `ACTIVE` status whose basis is `EMERGENCY_OVERRIDE` and whose `expires_at` has passed moves to `EXPIRED`. Because the sweep is the only expiry engine, an implementation must never lazily expire a record while serving an unrelated read or write.

### 2.5. Common Resource Properties

All thirteen persisted resource types — `Clinician`, `Unit`, `Bed`, `Patient`, `EmergencyEvaluation`, `HoldOrder`, `HoldPetition`, `CourtHearing`, `Admission`, `RestraintEpisode`, `CapacityDetermination`, `MedicationConsent` and `DischargeRequest` — carry the same four system-managed properties, with no exceptions and no type-specific omissions:

- `id` (string): a server-minted UUID. It carries no type prefix and clients never supply it.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, recording when the row was first written.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the row, including mutations of purely derived fields.
- `version` (integer): begins at 1 on creation and increments by exactly 1 on every mutation of the row.

Recomputing a derived counter counts as a mutation. When placing an admission changes a unit's occupancy figures, that unit's `updated_at` is refreshed and its `version` increments by one even though no client field on the unit was touched. The same holds for `Patient` when `active_hold_count` is recomputed, for `Clinician` when `booked_docket_minutes` is recomputed, and for `Bed` when its `status` flips as a side effect of a placement or a discharge.

Path identifiers are validated left to right. Where an endpoint nests one identifier under another — the bed listing of a unit is the only such path in this API — the parent `Unit` identifier is resolved first, and a request naming a unit that does not exist fails with `ERR_UNIT_NOT_FOUND` before any bed is examined. The same left-to-right discipline extends to the relationship between path and body: every path segment is resolved before any body-supplied foreign key, and body-supplied keys are resolved in the order the §4 description lists them.

### 2.6. Clocks, Calendars and Numeric Precision

Datetime values are millisecond-truncated ISO 8601 UTC with exactly three fractional digits. Any instant that a rolling rule pushes to the start of a court day lands exactly on `09:00:00.000Z`, and any instant pushed to the start of a business day lands exactly on `08:00:00.000Z`.

Two calendars are shared across the system. The **court calendar** treats a judicial day as any day that is not a Saturday, not a Sunday, and not one of the five recognized holidays — `2026-01-01`, `2026-07-03`, `2026-09-07`, `2026-11-26` and `2026-12-25` — and its window runs from 09:00:00 to 16:00:00 UTC. The **business calendar** uses the same weekend and holiday exclusions but runs from 08:00:00 to 17:00:00 UTC, which yields nine business hours per business day.

Counts, scores, durations in minutes, staffing quarter-hours and guarantee windows in days are all integers. The only fractional figures in the system are the two restraint monitoring compliance percentages, which are rounded half up to one decimal place. Integer division never happens implicitly: wherever a duration is converted into a number of required observations the quotient is rounded up to the next whole number, and wherever a duration is converted from an elapsed interval into whole minutes the remainder is discarded (rounded down).

### 2.7. Version Guards on Capacity-Consuming Writes

Two write operations consume state that other writers can move underneath them, and both are guarded by an optimistic concurrency check on a parent resource's `version`.

Placing an admission into a bed requires a non-optional `expected_unit_version` field carrying the client's last observed `version` of the target `Unit`. If that number does not equal the unit's current `version`, the placement is rejected with `ERR_STALE_UNIT_VERSION` (HTTP 412). Bed inventory edits, other placements and discharges all advance a unit's `version`, so a client working from an older read of the unit is refused rather than allowed to consume bed capacity it never observed. The unit read endpoint is the authoritative source of the value to send.

Recording a capacity determination requires a non-optional `expected_admission_version` field carrying the client's last observed `version` of the target `Admission`. A mismatch with the admission's current `version` is rejected with `ERR_STALE_ADMISSION_VERSION` (HTTP 412). Because a new determination supersedes the admission's prior `ACTIVE` one, the guard prevents a writer holding a stale view of the admission from silently displacing a determination it never saw.

No other endpoint accepts a version field. Requests to endpoints outside these two must not be rejected for omitting one, and an unrecognized version field elsewhere is simply not part of the contract.

### 2.8. Cascade Discipline

Several operations in this domain mutate more than one aggregate, and the cascades are chained: one link causes the next. The system applies every link of a chain within the same request, immediately and synchronously, and each link independently refreshes `updated_at` and increments `version` on the row it touches.

The chains that matter are named where they occur, but their shape is uniform. Closing a hold recomputes the patient's `active_hold_count`; if that leaves the patient with no `ACTIVE` hold, each of the patient's admissions still in `PENDING_PLACEMENT` or `PLACED` flips its legal axis from `INVOLUNTARY` to `VOLUNTARY`; because those admissions are now voluntary, any `PENDING` discharge request against them is answered in the patient's favour; and because a discharge request was granted, the admission's placement axis advances. Symmetrically, freeing a bed recomputes the owning unit's occupancy and availability counters, which may move the unit's `posture`, which may in turn promote a queued admission into the bed that just opened — and that promotion recomputes the unit's counters a second time within the same request.

Derived counters are always recomputed from the underlying rows rather than adjusted by a delta. `Unit.occupied_bed_count`, `Unit.raw_available_bed_count`, `Unit.licensed_placement_bed_count`, `Unit.effective_available_bed_count`, `Unit.active_seclusion_count`, `Unit.open_rights_violation_count`, `Patient.active_hold_count`, `Patient.is_minor`, `HoldPetition.continuance_count`, `Clinician.booked_docket_minutes` and `Admission.observation_staff_quarter_hours` are each defined by a query over their children, and that query is the definition of the field's value at all times.

### 2.9. Validation Precedence

Many operations are guarded by several checks at once, and which error a client sees is part of the contract. Checks are evaluated in the following fixed order, and the first failing check terminates the request. Authentication precedes authorization, authorization precedes schema validation, schema validation precedes existence resolution, existence resolution precedes version guards, version guards precede state checks, and state checks precede the clinical, temporal and capacity rules. Within each band the order below is authoritative.

1. `ERR_UNAUTHENTICATED` — on every endpoint: both context headers present and `X-User-Role` among the five declared roles.
2. `ERR_UNAUTHORIZED` — on every endpoint: the acting role is authorized for the operation, and `posture_override_reason` on placement is accepted only from an `AttendingPsychiatrist`.
3. `ERR_INVALID_REQUEST` — on every endpoint: required body fields present, enum members valid, integers within their declared bounds, hearing `duration_minutes` equal to either 30 or 60, `hold_type` equal to `EMERGENCY_72H` when a hold is initiated, and `requested_hold_type` equal to `EXTENSION_14D` when a petition is filed.
4. `ERR_PATIENT_NOT_FOUND` — the referenced `Patient` resolves; guards the patient read, evaluation creation, hold initiation and admission creation (the latter three through the body's `patient_id`).
5. `ERR_UNIT_NOT_FOUND` — the referenced `Unit` resolves; guards the unit read, the unit's bed listing, bed creation, admission creation and admission placement.
6. `ERR_EVALUATION_NOT_FOUND` — the referenced `EmergencyEvaluation` resolves; guards the evaluation read, evaluation signing, hold initiation and admission creation.
7. `ERR_ADMISSION_NOT_FOUND` — the referenced `Admission` resolves; guards the admission read, every admission action (safety search, placement, voluntary conversion, discharge planning, discharge), restraint ordering, capacity determination, medication consent and discharge-request creation.
8. `ERR_HOLD_NOT_FOUND` — the referenced `HoldOrder` resolves; guards the hold read, certification, rescission and petition filing.
9. `ERR_REFERENCED_RESOURCE_NOT_FOUND` — every remaining referenced identifier resolves, namely a `Clinician` cited as search witness or hearing advocate, a `Bed`, a `HoldPetition`, a `CourtHearing`, a `RestraintEpisode`, a `CapacityDetermination` or a `DischargeRequest`. These are resolved left to right, path segments before body fields.
10. `ERR_STALE_UNIT_VERSION` — `expected_unit_version` equals the unit's current `version`; on placement.
11. `ERR_STALE_ADMISSION_VERSION` — `expected_admission_version` equals the admission's current `version`; on capacity determination.
12. `ERR_EVALUATION_ALREADY_SIGNED` — the evaluation is still in `DRAFT`; on signing.
13. `ERR_EVALUATION_NOT_SIGNED` — the evaluation is in `SIGNED`; on hold initiation and admission creation.
14. `ERR_HOLD_NOT_PENDING_CERTIFICATION` — the hold is in `PENDING_CERTIFICATION`; on certification.
15. `ERR_HOLD_NOT_ACTIVE` — the hold is in the status the action needs: `ACTIVE` for petition filing and for voluntary conversion, and either `PENDING_CERTIFICATION` or `ACTIVE` for rescission.
16. `ERR_ADMISSION_NOT_PLACEABLE` — the admission's `placement_status` is `PENDING_PLACEMENT`; on placement.
17. `ERR_ADMISSION_NOT_DISCHARGEABLE` — the admission's `placement_status` is inside the set the action needs: either `PLACED` or `DISCHARGE_READY` for discharge, and either `PENDING_PLACEMENT` or `PLACED` for the safety search, discharge planning, voluntary conversion and discharge-request creation. All five operations report this same code.
18. `ERR_PETITION_NOT_OPEN` — the petition is in the status the action needs: either `FILED` or `CONTINUED` for hearing scheduling; `FILED`, `HEARING_SCHEDULED` or `CONTINUED` for withdrawal; and `HEARING_SCHEDULED` for outcome recording.
19. `ERR_HEARING_NOT_SCHEDULED` — the hearing is in `SCHEDULED`; on outcome recording.
20. `ERR_RESTRAINT_INVALID_STATE` — the episode is in the status the action needs: `ORDERED` for the face-to-face review, `ACTIVE` for release, either `ORDERED` or `ACTIVE` for appending a monitoring check, and `RELEASED` for debriefing.
21. `ERR_DISCHARGE_REQUEST_NOT_PENDING` — the request is in `PENDING`; on responding.
22. `ERR_SEGREGATION_OF_DUTIES` — the acting clinician differs from the counterpart the rule names; guards hold certification, the safety search and the restraint face-to-face review.
23. `ERR_CLINICAL_CRITERIA_NOT_MET` — the anchoring evaluation's `recommended_status` is `INVOLUNTARY_HOLD` for hold initiation, and is either `VOLUNTARY` or `INVOLUNTARY_HOLD` for admission creation.
24. `ERR_SAFETY_SEARCH_INCOMPLETE` — the admission's `safety_search_status` is `COMPLETED`; on placement.
25. `ERR_RESTRAINT_DURATION_EXCEEDS_LIMIT` — `ordered_duration_minutes` is within the age- and intervention-specific ceiling; on restraint ordering.
26. `ERR_SECLUSION_CAPACITY_EXCEEDED` — the unit's live seclusion occupancy is below its licensed seclusion room count; on ordering a seclusion episode.
27. `ERR_FACE_TO_FACE_WINDOW_CLOSED` — the clock is at or before the episode's `face_to_face_deadline_at`; on the face-to-face review.
28. `ERR_MONITORING_INCOMPLETE` — the episode's interval-grid compliance is exactly 100.0; on debriefing.
29. `ERR_OPEN_RESTRAINT_EPISODE` — no episode of the admission remains in `ORDERED`, `ACTIVE` or `RELEASED`; on discharge.
30. `ERR_CERTIFICATION_WINDOW_CLOSED` — the clock is at or before the hold's `certification_deadline_at`; on certification.
31. `ERR_PETITION_WINDOW_CLOSED` — the clock is at or before the hold's `petition_filing_deadline_at`; on petition filing.
32. `ERR_HEARING_SLOT_INVALID` — the requested docket slot falls on a judicial day, starts no earlier than 09:00:00, ends no later than 16:00:00, and starts strictly after the current clock; on hearing scheduling.
33. `ERR_HEARING_BEYOND_HOLD_EXPIRY` — the hearing's `scheduled_end_at` is at or before the hold's `release_deadline_at`; on hearing scheduling.
34. `ERR_ADVOCATE_DOCKET_CONFLICT` — the advocate's buffered docket does not collide with another of their `SCHEDULED` hearings; on hearing scheduling.
35. `ERR_ADVOCATE_NOT_QUALIFIED` — the nominated advocate's `staff_role` is `RIGHTS_ADVOCATE`; on hearing scheduling.
36. `ERR_CAPACITY_LACKING` — the admission has an `ACTIVE` capacity determination recording capacity as present; required for voluntary conversion and for a patient-consent medication basis.
37. `ERR_SURROGATE_REQUIRED` — the surrogate fields are supplied exactly when capacity is absent and omitted entirely when capacity is present; on capacity determination.
38. `ERR_SURROGATE_SCOPE_INSUFFICIENT` — a surrogate-consent basis cites an `ACTIVE` determination that records capacity as absent and grants a surrogate scope wide enough for medication; on medication consent.
39. `ERR_NO_ACTIVE_HOLD` — the patient has at least one `ACTIVE` hold; required for an involuntary admission, for denying a discharge request, and for an emergency medication override.
40. `ERR_PETITION_PENDING` — no petition for the hold is in `FILED`, `HEARING_SCHEDULED` or `CONTINUED`; guards petition filing and voluntary conversion.
41. `ERR_ACTIVE_HOLD_BLOCKS_DISCHARGE` — the admission's `legal_status` is `VOLUNTARY`; guards discharge and the granting of a discharge request.
42. `ERR_DUPLICATE_DISCHARGE_REQUEST` — no other discharge request for the admission is still `PENDING`; on discharge-request creation.
43. `ERR_CONTINUANCE_LIMIT_REACHED` — the petition's `continuance_count` is below 2; on recording a continued outcome.
44. `ERR_ROOM_COHORT_VIOLATION` — the target bed satisfies the unit's room cohort and minor cohort rules; on placement.
45. `ERR_BED_NOT_ELIGIBLE` — an explicitly named bed satisfies the eligibility rules; on placement.
46. `ERR_DISCHARGE_PLAN_INCOMPLETE` — the admission's `discharge_plan_status` is `APPOINTMENT_SECURED` and its `follow_up_appointment_at` is strictly after the current clock; on discharge.
47. `ERR_FOLLOW_UP_WINDOW_EXCEEDED` — the proposed appointment falls inside the guarantee window; on discharge planning.
48. `ERR_UNIT_POSTURE_BLOCKED` — the unit's posture admits the placement; on placement.
49. `ERR_NO_ELIGIBLE_BED` — automatic bed selection produced at least one candidate; on placement.

### 2.10. Segregation of Clinical Duties

Three decision pairs in this domain must be made by two different people, and in all three the violation surfaces as `ERR_SEGREGATION_OF_DUTIES`. A psychiatrist may not certify a hold they themselves initiated, so the certifying `X-User-ID` must differ from the hold's `initiated_by_clinician_id`. The independent witness of a contraband search must not be the person who performed it, so the body's `search_witness_clinician_id` must differ from the `search_performed_by_clinician_id` the server takes from the header. And the in-person review that authorizes continuation of a mechanical restraint or a seclusion must come from someone other than the clinician who ordered it, so for `MECHANICAL_RESTRAINT` and `SECLUSION` the reviewing `X-User-ID` must differ from `ordered_by_clinician_id`. The third rule has a deliberate exception: for a `PHYSICAL_HOLD`, the ordering clinician is permitted to perform their own face-to-face review.

### 2.11. Rights Violations as a First-Class Record

When the system detects that a statutory protection lapsed, it does not merely refuse a later action — it records the lapse. Three sweep-detected conditions set `rights_violation_flag` to true on the affected admission: a hold that expired while the patient was still physically placed, a restraint episode that ran without the required authorization, and a discharge request that went unanswered past its deadline. Each such flag immediately recomputes `open_rights_violation_count` on the owning unit, which is defined as the number of that unit's admissions carrying a true `rights_violation_flag` whose `placement_status` is anything other than `DISCHARGED`. The flag is never cleared by any operation in this specification.

## 3. Business Logic & Workflows

### 3.1. Staffing the Unit: Roster, Wards and Bed Inventory

A `ComplianceOfficer` builds the operational substrate before any patient arrives. Registering a staff member records their `full_name`, their `license_number` — which must be unique across all clinician rows — and their `staff_role`, one of `INTAKE_CLINICIAN`, `PSYCHIATRIST`, `CHARGE_NURSE` or `RIGHTS_ADVOCATE`. Note that `staff_role` is a credential class on the roster row and is independent of the `X-User-Role` header: the header decides what an actor may call, while `staff_role` decides whether that person is eligible to be *named* in a clinical role. Every new clinician starts with `booked_docket_minutes` at 0. That figure is not a free-form counter but a derived total: it always equals the sum of `duration_minutes` across every court hearing whose `advocate_clinician_id` is this clinician and whose `status` is `SCHEDULED`. Because it is derived, a hearing that leaves `SCHEDULED` for any reason reduces it again.

Creating a behavioral health unit records its `name`, its `seclusion_room_count` — a whole number of licensed seclusion rooms, which may be zero but never negative — and its `gender_mixing_policy`, one of `SEPARATE_BY_ROOM`, `SEPARATE_BY_WING` or `MIXED_ALLOWED`. A brand-new unit has no beds, so the availability computation described below produces a `posture` of `CLOSED` at the moment of creation. Every unit exposes `licensed_placement_bed_count`, `raw_available_bed_count`, `posture`, `effective_available_bed_count`, `occupied_bed_count`, `active_seclusion_count` and `open_rights_violation_count`, all derived, and its `version` is what a placement client must echo back.

Beds are added one at a time, each carrying its `unit_id`, a `room_number` label, a `wing_code` label, a `bed_label` that must be unique within its room on that unit, and a `bed_type` of `STANDARD`, `LIGATURE_RESISTANT_OBSERVATION` or `SECLUSION`. A new bed's `status` starts at `AVAILABLE` and thereafter takes one of `AVAILABLE`, `OCCUPIED`, `BLOCKED_CLEANING` or `OUT_OF_SERVICE`. A `ComplianceOfficer` or a `ChargeNurse` may change a bed's `status` directly — blocking it for cleaning, taking it out of service, or returning it to service — and the beds of a unit can be listed with optional filters on `status` and `bed_type`. Beds that share a `room_number` within a unit are roommates; beds that share a `wing_code` are wingmates.

**Availability and posture are computed in four pinned steps, and the order is not negotiable.** Step one counts inventory from bed statuses alone, and it considers only beds of type `STANDARD` or `LIGATURE_RESISTANT_OBSERVATION` — a `SECLUSION` bed is never counted and therefore can never influence posture. `licensed_placement_bed_count` is the number of such beds on the unit whose `status` is anything other than `OUT_OF_SERVICE`; `raw_available_bed_count` is the number of such beds whose `status` is exactly `AVAILABLE`. Step two derives `posture` from `raw_available_bed_count` and nothing else: first compute a restriction threshold equal to the greater of 1 and one fifth of `licensed_placement_bed_count` rounded down to a whole number; then the posture is `CLOSED` when `raw_available_bed_count` is zero, `RESTRICTED` when it is greater than zero but no greater than that threshold, and `OPEN` otherwise. Step three derives a safety reserve from the posture: one bed is held back when the posture is `RESTRICTED`, and none otherwise. Step four sets `effective_available_bed_count` to `raw_available_bed_count` minus the reserve, floored at zero.

The pinning matters because step four's subtraction depends on step three, which depends on step two — yet step two never re-reads step four. There is no fixed-point iteration and no second pass. The consequence must be preserved exactly: a unit with a `licensed_placement_bed_count` of 3 and a `raw_available_bed_count` of 1 has a threshold of 1, is therefore `RESTRICTED`, holds one bed in reserve, and reports an `effective_available_bed_count` of 0 — so an ordinary placement is refused even though a physically free bed exists.

This four-step recomputation runs on bed creation, on a bed status change, on an admission placement, on a system promotion, and on the bed release that follows a discharge; each run refreshes the unit's `updated_at` and increments its `version` by one. Whenever a recomputation moves `posture` from `CLOSED` to either `RESTRICTED` or `OPEN` — which happens exactly when `raw_available_bed_count` rises above zero — the queued-admission promotion described in §3.5 fires exactly once for that unit and promotes at most one waiting admission. A recomputation that drops `raw_available_bed_count` to zero sets `posture` to `CLOSED` and `effective_available_bed_count` to 0 and fires no promotion. A recomputation that moves `posture` from `OPEN` to `RESTRICTED` — that is, one that leaves `raw_available_bed_count` above zero but no greater than the threshold — also fires no promotion, because the posture never left `CLOSED`.

### 3.2. Intake: Patient Registration and the Emergency Evaluation

Registration of a patient records an `mrn` that must be unique across all patients, the patient's `legal_name`, their `age_years` as a whole number no less than 0 and no greater than 120, and a `gender_care_category` of `MALE`, `FEMALE` or `NONBINARY`. From the age the system derives `is_minor`, which is true exactly when `age_years` is below 18; minor status later both separates cohorts in rooms and lowers restraint duration ceilings. A patient's `active_hold_count` starts at 0 and is always the number of that patient's holds whose `status` is `ACTIVE`.

An `IntakeClinician` or an `AttendingPsychiatrist` then records an emergency psychiatric evaluation against a `patient_id`. The three statutory criteria are submitted as booleans: `danger_to_self`, `danger_to_others` and `grave_disability`. Alongside them the clinician records `capacity_present`, the intake screen for whether the patient presently has decisional capacity to consent to admission, and a `clinical_summary` narrative. The server stamps `evaluating_clinician_id` from the header and `evaluation_started_at` from the logical clock, and the evaluation's `status` begins at `DRAFT`.

Scoring happens at creation. First the system counts the patient's recent history into `prior_admission_count_30d`: the number of that patient's admissions whose `placement_status` is `PLACED`, `DISCHARGE_READY` or `DISCHARGED`, and whose `admitted_at` is at or after the instant 30 days before `evaluation_started_at` and strictly before `evaluation_started_at` itself. The lower bound of that window is inclusive and the upper bound is exclusive; admissions in `PENDING_PLACEMENT` or `CANCELLED` are excluded entirely, because neither represents a completed episode of care.

The `acuity_score` is then an integer sum of five contributions: 4 points when `danger_to_self` is true, 5 points when `danger_to_others` is true, 3 points when `grave_disability` is true, 2 points for each recent prior admission counted but crediting no more than three of them, and 3 points when `capacity_present` is false. The `acuity_tier` follows from the score with inclusive lower bounds: `HIGH` when the score is 12 or more, `MODERATE` when the score is at least 7 but below 12, and `LOW` for any lower score — so a score of exactly 12 is `HIGH` and a score of exactly 7 is `MODERATE`. Independently of the score, the `recommended_status` follows from the criteria: if none of the three statutory criteria is true it is `NO_ADMISSION`; if at least one is true and `capacity_present` is true it is `VOLUNTARY`; and if at least one is true while `capacity_present` is false it is `INVOLUNTARY_HOLD`.

Signing moves the evaluation `DRAFT → SIGNED`, which is terminal for this entity; a second attempt fails with `ERR_EVALUATION_ALREADY_SIGNED`. Signature stamps `signed_at` from the logical clock and freezes the record: `acuity_score`, `acuity_tier`, `prior_admission_count_30d` and `recommended_status` keep exactly the values computed at creation and are never recomputed at signature, however much the world has moved in between. `signed_at` is the statutory anchor every emergency hold clock is measured from, which is why nothing downstream may be built on a `DRAFT` evaluation — hold initiation and admission creation both reject one with `ERR_EVALUATION_NOT_SIGNED`.

### 3.3. Detention Authority: Initiating, Certifying and Closing a Hold

An emergency hold is initiated by an `IntakeClinician` or an `AttendingPsychiatrist` against a `patient_id` and a signed `evaluation_id`. The `hold_type` supplied on initiation must be `EMERGENCY_72H`; the other class, `EXTENSION_14D`, is never client-created and exists only as a system-created successor to a granted court petition, which is why an initiation naming it fails schema validation with `ERR_INVALID_REQUEST`. Initiation is permitted only when the anchoring evaluation's `recommended_status` is exactly `INVOLUNTARY_HOLD`; a `VOLUNTARY` or `NO_ADMISSION` recommendation is refused with `ERR_CLINICAL_CRITERIA_NOT_MET`. The server records `initiated_by_clinician_id` from the header, leaves `certifying_clinician_id`, `certified_at` and `closure_reason` null, leaves `predecessor_hold_id` null because an emergency hold has no predecessor, and sets `status` to `PENDING_CERTIFICATION`.

**Four instants are computed at initiation and never recomputed afterwards.** `statutory_hours` is 72 for an `EMERGENCY_72H` hold and 336 — fourteen days expressed in hours — for an `EXTENSION_14D` hold. `clock_started_at` is the statutory anchor and is emphatically *not* the hold row's own creation timestamp: for an `EMERGENCY_72H` hold it is the anchoring evaluation's `signed_at`, and for an `EXTENSION_14D` successor it is the predecessor hold's `release_deadline_at`. From that anchor, `certification_deadline_at` is the anchor plus 4 hours. The remaining two are a matched pair computed from the same anchor and the same offset but on two different calendars, and they routinely disagree.

The first variant, `release_deadline_at`, is pure wall-clock arithmetic: the anchor plus `statutory_hours` hours, with no rolling of any kind. Weekends and holidays are counted, so this instant may legitimately fall at two in the morning on a Sunday. It is the moment detention authority lapses and the moment the compliance sweep may expire the hold.

The second variant, `petition_filing_deadline_at`, starts from that same raw instant and then rolls it forward onto the court calendar until it lands inside a judicial-day court window. The roll is applied repeatedly: if the candidate's date is a Saturday, a Sunday or one of the recognized holidays, the candidate becomes the following day at `09:00:00.000Z` and the test restarts; otherwise, if the candidate's time of day is earlier than 09:00:00 it becomes that same date at `09:00:00.000Z` and the test restarts; otherwise, if its time of day is later than 16:00:00 it becomes the following day at `09:00:00.000Z` and the test restarts; when none of the three applies, that candidate is the filing deadline. The divergence between the two variants is the point: an anchor of `2026-09-03T14:30:00Z` on a 72-hour hold yields a `release_deadline_at` of `2026-09-06T14:30:00.000Z` — a Sunday — while the same inputs yield a `petition_filing_deadline_at` of `2026-09-08T09:00:00.000Z`, because Sunday rolls to Monday and Monday the 7th is a recognized holiday.

Certification is the act that converts an initiated hold into detention authority, and it is restricted to an `AttendingPsychiatrist` other than the initiator. A certification arriving from the initiating clinician is refused with `ERR_SEGREGATION_OF_DUTIES`; one arriving when the hold is not in `PENDING_CERTIFICATION` is refused with `ERR_HOLD_NOT_PENDING_CERTIFICATION`; and one arriving after `certification_deadline_at` — that is, when the clock is strictly past it — is refused with `ERR_CERTIFICATION_WINDOW_CLOSED`, while an arrival exactly at the deadline is accepted. A successful certification carries a `certification_note`, moves the hold `PENDING_CERTIFICATION → ACTIVE`, stamps `certified_at` and `certifying_clinician_id`, recomputes the patient's `active_hold_count` upward by one and increments `Patient.version` by one, and then reaches across into the admission aggregate: every admission of that patient whose `placement_status` is `PENDING_PLACEMENT` or `PLACED` has its `legal_status` set to `INVOLUNTARY` and its own `version` incremented by one. The placement axis of those admissions is untouched — the two axes move independently, always.

Rescission is the psychiatrist's own release of the hold and is accepted while the hold is in either `PENDING_CERTIFICATION` or `ACTIVE`; from any other status it fails with `ERR_HOLD_NOT_ACTIVE`. It carries a `rescind_reason`, which is stored verbatim as the hold's `closure_reason`, and moves the hold to `RESCINDED`. Rescinding a hold that was still `PENDING_CERTIFICATION` has no further consequence, because that hold never counted toward detention. Rescinding an `ACTIVE` hold starts a four-link chain: the patient's `active_hold_count` is recomputed and reaches 0 when no other `ACTIVE` hold remains; because the patient now has no `ACTIVE` hold, every admission of theirs in `PENDING_PLACEMENT` or `PLACED` flips `legal_status` from `INVOLUNTARY` to `VOLUNTARY`; because such an admission is now voluntary, every discharge request against it that is still `PENDING` flips to `GRANTED_DISCHARGE` with its `decision` set to `GRANT` and its `responding_clinician_id` set to the rescinding psychiatrist's `X-User-ID`; and because a discharge request was granted, that admission's `placement_status` advances `PLACED → DISCHARGE_READY`.

Voluntary conversion closes the hold from the admission side and is described in §3.5, but its effect on the hold belongs here: the patient's `ACTIVE` hold moves `ACTIVE → CONVERTED_VOLUNTARY`, its `closure_reason` is set to the supplied `conversion_note`, the patient's `active_hold_count` is recomputed with `Patient.version` incremented by one, and the admission's `legal_status` flips `INVOLUNTARY → VOLUNTARY` with `Admission.version` incremented by one. Conversion is refused with `ERR_HOLD_NOT_ACTIVE` unless the hold is `ACTIVE`, and refused with `ERR_PETITION_PENDING` when any petition for that hold is in `FILED`, `HEARING_SCHEDULED` or `CONTINUED` — a matter before the court may not be settled unilaterally at the bedside.

The remaining three terminal statuses are reached without a client asking for them. A granted extension petition moves the predecessor `ACTIVE → SUPERSEDED`; a denied one moves it `ACTIVE → DISCHARGED_BY_COURT` with `closure_reason` set to `COURT_DENIED_EXTENSION`; both are detailed in §3.4. The compliance sweep moves an `ACTIVE` hold to `EXPIRED` when the clock has reached or passed `release_deadline_at` **and** no petition for that hold is in `FILED`, `HEARING_SCHEDULED` or `CONTINUED` — an open petition holds the statutory clock open indefinitely. Expiry sets `closure_reason` to `STATUTORY_EXPIRY`, recomputes the patient's `active_hold_count` with `Patient.version` incremented by one, and flips every admission of that patient in `PENDING_PLACEMENT` or `PLACED` from `INVOLUNTARY` to `VOLUNTARY`. It carries one extra consequence the other closures do not: for any such admission whose `placement_status` is `PLACED`, the expiry also sets `rights_violation_flag` to true, because the patient remained physically detained after authority lapsed — and that in turn recomputes `open_rights_violation_count` on the owning unit.

### 3.4. Extension Petitions, the Advocate Docket and Court Disposition

An `AttendingPsychiatrist` who needs more time than the emergency window allows files a petition against a `hold_id`, supplying a `requested_hold_type` that must be `EXTENSION_14D` and a `petition_grounds` narrative. The server stamps `petitioning_clinician_id` from the header and `filed_at` from the logical clock, sets `status` to `FILED`, and starts `continuance_count` at 0. Filing requires the target hold to be `ACTIVE` — otherwise `ERR_HOLD_NOT_ACTIVE` — requires that no other petition for that hold is already in `FILED`, `HEARING_SCHEDULED` or `CONTINUED`, which is `ERR_PETITION_PENDING`, and must arrive at or before the hold's `petition_filing_deadline_at`; a later filing is refused with `ERR_PETITION_WINDOW_CLOSED`. A petition may be withdrawn by an `AttendingPsychiatrist` or a `PatientRightsAdvocate` with a `withdraw_reason` while it is in `FILED`, `HEARING_SCHEDULED` or `CONTINUED`.

Scheduling a hearing is performed by a `PatientRightsAdvocate` or a `ComplianceOfficer` and is the act that assigns patient representation. The request names the `petition_id`, the `advocate_clinician_id` who will represent the patient, a `scheduled_start_at` docket slot and a `duration_minutes` of exactly 30 or exactly 60 — any other length is `ERR_INVALID_REQUEST`. The server computes `scheduled_end_at` as `scheduled_start_at` plus that many minutes, creates the hearing with `status` `SCHEDULED`, `outcome` `PENDING` and a null `findings_note`, and advances the petition to `HEARING_SCHEDULED`. Scheduling is accepted from a petition in `FILED` or in `CONTINUED`; any other petition status is `ERR_PETITION_NOT_OPEN`.

Four scheduling constraints guard the slot itself, and they are evaluated in the order given in §2.9. The slot must be a genuine court slot: its date must be a judicial day, its start time no earlier than 09:00:00, its end time no later than 16:00:00, and its start strictly after the current clock — any breach is `ERR_HEARING_SLOT_INVALID`. The hearing must also conclude while detention authority still exists, so `scheduled_end_at` must be at or before the petition's hold's `release_deadline_at`, failing which the request is refused with `ERR_HEARING_BEYOND_HOLD_EXPIRY`. Next comes the advocate's own docket: for every existing hearing with the same `advocate_clinician_id` still in `SCHEDULED`, the new slot must not overlap that hearing once both are expanded by a 30-minute travel buffer. Concretely, a conflict exists when the new start minus 30 minutes falls before the existing end **and** the existing start falls before the new end plus 30 minutes; a conflict is reported as `ERR_ADVOCATE_DOCKET_CONFLICT`. The buffer boundary is exact: a gap of exactly 30 minutes between two hearings is permitted, while a gap of 29 minutes is not. Finally the nominated advocate must be credentialed for the job — their roster `staff_role` must be `RIGHTS_ADVOCATE`, and anyone else is refused with `ERR_ADVOCATE_NOT_QUALIFIED`. A successful scheduling recomputes that advocate's `booked_docket_minutes`, which rises by the new hearing's `duration_minutes`, and increments `Clinician.version` by one.

A `ComplianceOfficer` records the court's disposition against a `SCHEDULED` hearing, supplying an `outcome` and a `findings_note`. The hearing must be in `SCHEDULED` — otherwise `ERR_HEARING_NOT_SCHEDULED` — and its petition must be in `HEARING_SCHEDULED`, otherwise `ERR_PETITION_NOT_OPEN`. Three outcomes are recognized, and the three branches carry equal weight in this specification.

When the outcome is `GRANTED`, the hearing moves `SCHEDULED → HELD` with `outcome` recorded as `GRANTED`, and the petition moves `HEARING_SCHEDULED → GRANTED`. This requires the petition's hold to still be `ACTIVE`. That predecessor hold moves `ACTIVE → SUPERSEDED`, and the system creates a successor hold in the same request: `hold_type` `EXTENSION_14D`, `predecessor_hold_id` pointing at the predecessor, `patient_id` and `evaluation_id` copied from the predecessor, `status` set directly to `ACTIVE`, `certifying_clinician_id` set to the granted petition's `petitioning_clinician_id`, `clock_started_at` set to the predecessor's `release_deadline_at`, `statutory_hours` of 336, and both deadline variants plus `certification_deadline_at` recomputed from that new anchor exactly as §3.3 describes. Because the predecessor leaves `ACTIVE` while the successor enters it, the patient's `active_hold_count` nets out unchanged — but it is still recomputed and `Patient.version` still increments by one. The advocate's `booked_docket_minutes` is recomputed downward, since the hearing has left `SCHEDULED`, and `Clinician.version` increments by one.

When the outcome is `DENIED`, the hearing likewise moves `SCHEDULED → HELD` with `outcome` recorded as `DENIED`, and the petition moves `HEARING_SCHEDULED → DENIED`; this too requires the hold to still be `ACTIVE`. The hold moves `ACTIVE → DISCHARGED_BY_COURT` with `closure_reason` set to `COURT_DENIED_EXTENSION`, and the same chain that follows a rescission runs: the patient's `active_hold_count` is recomputed to 0, every admission of that patient in `PENDING_PLACEMENT` or `PLACED` flips `legal_status` to `VOLUNTARY`, every `PENDING` discharge request on those admissions flips to `GRANTED_DISCHARGE`, and each affected admission's `placement_status` advances `PLACED → DISCHARGE_READY`. The advocate's `booked_docket_minutes` is recomputed downward and `Clinician.version` increments by one.

When the outcome is `CONTINUED`, the matter is put over to another date. The hearing moves `SCHEDULED → CONTINUED` and the petition moves `HEARING_SCHEDULED → CONTINUED`, with `continuance_count` recomputed as the number of that petition's hearings now in `CONTINUED`. The advocate's `booked_docket_minutes` is recomputed downward because the hearing has left `SCHEDULED`, and `Clinician.version` increments by one. A continued petition can be scheduled again, which returns it `CONTINUED → HEARING_SCHEDULED` and creates a second hearing in `SCHEDULED` with the advocate's docket recomputed upward — this is the one cycle in the system, `HEARING_SCHEDULED → CONTINUED → HEARING_SCHEDULED`, and it is bounded: a continuance is permitted only while `continuance_count` is below 2, so the third attempt at a continuance on the same petition is refused with `ERR_CONTINUANCE_LIMIT_REACHED`. Note that no hold transition accompanies a continuance, and the open petition continues to hold the statutory clock open against the sweep.

Withdrawal has a shape that depends on what has already been scheduled, and both shapes must be honoured. Withdrawing a petition still in `FILED` simply moves it to `WITHDRAWN`; no hearing exists, so no docket minutes change. Withdrawing a petition in `HEARING_SCHEDULED` runs a three-link chain: the petition moves to `WITHDRAWN`; because the petition is withdrawn, every hearing of that petition still in `SCHEDULED` flips `SCHEDULED → VACATED`; and because those hearings have left `SCHEDULED`, the advocate's `booked_docket_minutes` is recomputed downward by the vacated `duration_minutes` and `Clinician.version` increments by one. Withdrawing a petition in `CONTINUED` moves it to `WITHDRAWN` and changes no docket minutes, because a petition in `CONTINUED` has no hearing left in `SCHEDULED`. `GRANTED`, `DENIED` and `WITHDRAWN` are all terminal for a petition, and `HELD`, `CONTINUED` and `VACATED` are all terminal for a hearing.

### 3.5. Admission, the Safety Search, and Getting the Patient into a Bed

Only an `IntakeClinician` may open an admission. The request names the `patient_id`, the signed `evaluation_id` authorizing the stay, the `unit_id` the patient is destined for, and a `requested_legal_status` that becomes the admission's initial `legal_status` on the legal axis — either `VOLUNTARY` or `INVOLUNTARY`. Requesting `INVOLUNTARY` requires that the patient already has at least one hold in `ACTIVE`; without one the request is refused with `ERR_NO_ACTIVE_HOLD`. The anchoring evaluation must be `SIGNED`, and its `recommended_status` must be either `VOLUNTARY` or `INVOLUNTARY_HOLD`; a `NO_ADMISSION` recommendation is refused with `ERR_CLINICAL_CRITERIA_NOT_MET`. On creation the server copies `acuity_tier` from the evaluation — that copy, not a fresh computation, is what drives bed-type fit and promotion ranking for the rest of the stay — stamps `admitted_at` from the logical clock and `admitting_clinician_id` from the header, and initializes the record: `placement_status` `PENDING_PLACEMENT` on the placement axis, `safety_search_status` `PENDING`, `discharge_plan_status` `NOT_STARTED`, `rights_violation_flag` false, `observation_staff_quarter_hours` 0, and `bed_id`, `placed_at`, `discharged_at`, `search_performed_by_clinician_id`, `capacity_present`, `follow_up_provider_name`, `follow_up_appointment_at`, `follow_up_guarantee_days`, `follow_up_guarantee_deadline_at` and `discharge_summary` all null.

Before any patient touches a bed, the contraband and safety search must be documented, and it is documented by two people. A `ChargeNurse` or an `IntakeClinician` records it with a `search_type` of `VISUAL`, `WANDED` or `FULL_BODY_WITH_CONSENT`, a `search_witness_clinician_id` naming the independent observer, a `search_items_secured_count` of belongings taken into safekeeping which defaults to 0, a `contraband_found` boolean which defaults to false, and an `outcome`. An `outcome` of `COMPLETED` sets `safety_search_status` to `COMPLETED`; an `outcome` of `REFUSED` sets it to `REFUSED`, which permanently blocks placement until a later successful search. Either way the server records `search_performed_by_clinician_id` from the header and increments `Admission.version` by one. The witness must be a different person from the performer, per §2.10. The search is accepted only while the admission's `placement_status` is `PENDING_PLACEMENT` or `PLACED`; from any other placement state it is refused with `ERR_ADMISSION_NOT_DISCHARGEABLE`.

Placement is performed by a `ChargeNurse` or an `AttendingPsychiatrist` and is where the largest number of constraints converge. The request restates the `unit_id`, carries the mandatory `expected_unit_version` described in §2.7, may name an explicit `bed_id`, and may carry a `posture_override_reason`. The admission must be in `PENDING_PLACEMENT`, or the request fails with `ERR_ADMISSION_NOT_PLACEABLE`, and its `safety_search_status` must be exactly `COMPLETED`, or the request fails with `ERR_SAFETY_SEARCH_INCOMPLETE`.

The unit's posture then gates the placement, and each posture behaves differently. A `CLOSED` unit accepts no ordinary placement at all. A `RESTRICTED` unit accepts one only when the request carries a `posture_override_reason` and the acting role is `AttendingPsychiatrist` and the admission's `acuity_tier` is exactly `HIGH` — that is the deliberate mechanism by which the reserved bed of a nearly full unit is spent on the sickest patient, and it works precisely because a `RESTRICTED` unit's `effective_available_bed_count` may well be 0 while a physically free bed exists. An `OPEN` unit accepts a placement only when its `effective_available_bed_count` is at least 1. Any of these three failures is reported as `ERR_UNIT_POSTURE_BLOCKED`. A `posture_override_reason` submitted by a `ChargeNurse` never reaches this rule; it is stopped earlier by `ERR_UNAUTHORIZED`.

**Bed eligibility** is assessed next. A bed is a candidate only when it belongs to the requested unit, its `status` is exactly `AVAILABLE`, its `bed_type` is `STANDARD` or `LIGATURE_RESISTANT_OBSERVATION` — a `SECLUSION` bed is never a placement destination — and, when the admission's `acuity_tier` is `HIGH`, its `bed_type` is specifically `LIGATURE_RESISTANT_OBSERVATION`. A bed must additionally satisfy two cohort rules. The room cohort rule reads the unit's `gender_mixing_policy`: under `MIXED_ALLOWED` it always passes; under `SEPARATE_BY_ROOM` every roommate — meaning every admission in `PLACED` whose bed sits in the same unit and the same `room_number` — must have a patient whose `gender_care_category` matches the incoming patient's; under `SEPARATE_BY_WING` the same equality must hold across every wingmate, meaning every `PLACED` admission whose bed shares the `wing_code`. The minor cohort rule applies under all three policies, including `MIXED_ALLOWED`: every roommate's patient must have the same `is_minor` value as the incoming patient, so minors and adults never share a room. A cohort failure is `ERR_ROOM_COHORT_VIOLATION`; an explicitly named `bed_id` that fails the unit, status or bed-type conditions is `ERR_BED_NOT_ELIGIBLE`.

When `bed_id` is omitted, the system chooses for itself from the candidate set, and the choice is a deterministic total order rather than a preference. First it fixes the exact-fit bed type for this admission: `LIGATURE_RESISTANT_OBSERVATION` when the `acuity_tier` is `HIGH` or `MODERATE`, and `STANDARD` when it is `LOW`. Candidates are then ranked on five keys, compared in order, with the smallest winning: the number of current roommates in the bed's room, so emptier rooms come first; then whether the bed's `bed_type` is the exact-fit type, with exact fits ahead of the rest; then the bed's `room_number` in ascending lexicographic order; then the bed's `bed_label` in ascending lexicographic order; and finally the bed's `created_at`, earliest first. Because `room_number` and `bed_label` are unique within a unit, the ranking is a total order and never needs a random tie-break — the identifiers of beds and admissions are never consulted, and `created_at` is the only common field the ordering ever falls back on. If the candidate set is empty for an explicit placement call, the request is refused with `ERR_NO_ELIGIBLE_BED`.

A successful placement sets `bed_id` to the selected bed, stamps `placed_at` from the logical clock, and advances the placement axis `PENDING_PLACEMENT → PLACED` while leaving `legal_status` exactly as it was. The chosen bed's `status` flips `AVAILABLE → OCCUPIED` with `Bed.version` incremented by one, and the unit's `occupied_bed_count`, `raw_available_bed_count`, `posture` and `effective_available_bed_count` are all recomputed with `Unit.version` incremented by one.

**Queued promotion** is the system's own placement path, and it is triggered by a unit's posture leaving `CLOSED` — after a discharge frees a bed, after a blocked bed returns to service, or after a new bed is created. The eligible queue for that unit is its admissions whose `placement_status` is `PENDING_PLACEMENT` and whose `safety_search_status` is `COMPLETED`; admissions with a `PENDING` or `REFUSED` search are excluded. The queue is ordered by acuity descending — treating `HIGH` as rank 3, `MODERATE` as rank 2 and `LOW` as rank 1 — then by `created_at` ascending so the longest-waiting patient wins among equals, and finally, when acuity rank and `created_at` are identical, by the patient's `mrn` in ascending order as the deterministic last resort. The first row of that ordering is the winner, and exactly one admission is promoted per posture transition out of `CLOSED`. An empty queue produces no promotion, no error and no change of posture. A promotion runs the same bed selection as an ordinary placement and is exempt from exactly two gates — the `effective_available_bed_count` requirement and the `RESTRICTED` safety reserve, on the reasoning that this patient is already in the facility's custody — but it is not exempt from bed eligibility, bed-type fit or the room and minor cohort rules. If bed selection yields no candidate for the winner, no promotion happens and the admission simply stays in `PENDING_PLACEMENT`. A promotion sets `bed_id`, stamps `placed_at`, moves the admission to `PLACED`, flips the bed `AVAILABLE → OCCUPIED`, and recomputes the unit's counters and posture a second time within the same request.

Voluntary conversion is the psychiatrist's route off the legal axis. It carries a `conversion_note`, requires the admission's `placement_status` to be `PENDING_PLACEMENT` or `PLACED`, requires the admission to have an `ACTIVE` capacity determination recording `capacity_present` as true — otherwise `ERR_CAPACITY_LACKING` — requires the hold to be `ACTIVE`, and requires no petition for that hold to be open. It flips `legal_status` `INVOLUNTARY → VOLUNTARY` and closes the hold as described in §3.3, and it never touches the placement axis. The mirror-image transition on the legal axis, `VOLUNTARY → INVOLUNTARY`, is only ever produced by a hold certification, and the reverse direction is also produced by hold rescission, statutory expiry and court denial; in every case the flip to `VOLUNTARY` presupposes that the patient has no remaining hold in `ACTIVE`.

### 3.6. Restraint and Seclusion: Order, Review, Monitoring, Release, Debrief

An `AttendingPsychiatrist` orders a restraint episode against an `admission_id`, naming an `intervention_type` of `PHYSICAL_HOLD`, `MECHANICAL_RESTRAINT` or `SECLUSION`, an `ordered_duration_minutes` greater than zero, and a `clinical_justification` documenting why less restrictive alternatives were insufficient. Duration ceilings depend on both the patient's age and the intervention: for an adult, 60 minutes for a `PHYSICAL_HOLD` and 240 minutes for either other type; for a patient whose `is_minor` is true, 30 minutes for a `PHYSICAL_HOLD` and 120 minutes for either other type. An order above its ceiling is refused with `ERR_RESTRAINT_DURATION_EXCEEDS_LIMIT`.

Seclusion is additionally capped by physical plant. Before a `SECLUSION` episode is created, the system counts the live seclusion load on the admission's unit: episodes whose `intervention_type` is `SECLUSION`, whose `status` is `ORDERED` or `ACTIVE`, whose `authorized_until_at` is strictly after the current clock, and whose admission sits on that unit. That count must be strictly below the unit's `seclusion_room_count`; otherwise the order is refused with `ERR_SECLUSION_CAPACITY_EXCEEDED`. The same query defines the unit's `active_seclusion_count`, which is recomputed with `Unit.version` incremented by one whenever a seclusion episode is created, released or expired.

On creation the server stamps `started_at` from the logical clock, records `ordered_by_clinician_id` from the header, sets `status` to `ORDERED`, and computes three derived values. `authorized_until_at` is `started_at` plus `ordered_duration_minutes`, and it is the right-open end of the episode's occupancy interval. `face_to_face_deadline_at` is `started_at` plus 60 minutes. And `monitoring_interval_minutes` is 5 for a `PHYSICAL_HOLD` and 15 for a `MECHANICAL_RESTRAINT` or a `SECLUSION` — the tighter cadence for the intervention where a clinician's hands are physically on the patient.

The in-person review is what authorizes continuation. Performed by an `AttendingPsychiatrist` with an `assessment_note`, it moves the episode `ORDERED → ACTIVE`, stamps `face_to_face_at` from the clock and `face_to_face_clinician_id` from the header. It must arrive at or before `face_to_face_deadline_at`; strictly later is `ERR_FACE_TO_FACE_WINDOW_CLOSED`. From any status other than `ORDERED` it is `ERR_RESTRAINT_INVALID_STATE`. For a `MECHANICAL_RESTRAINT` or a `SECLUSION` the reviewer must differ from the orderer; for a `PHYSICAL_HOLD` the same clinician may do both.

A `ChargeNurse` appends observations to the episode's `monitoring_check_log` while the episode is in `ORDERED` or `ACTIVE`; from any other status the append is `ERR_RESTRAINT_INVALID_STATE`. Each append names a `check_type` of `CIRCULATION`, `HYDRATION_OFFERED`, `TOILETING` or `VITALS` and may carry a free-text `note`. The log is append-only and each element records `recorded_at` from the logical clock, the `check_type`, `recorded_by_clinician_id` from the header, and the `note`. Because the log endpoint refuses episodes that are neither `ORDERED` nor `ACTIVE`, no entry can ever exist with a `recorded_at` at or after the moment of release.

Release is performed by a `ChargeNurse` or an `AttendingPsychiatrist` with a `release_note` and requires the episode to be `ACTIVE`. It moves the episode `ACTIVE → RELEASED`, stamps `released_at` from the logical clock, and computes the episode's compliance record. `actual_duration_minutes` is the elapsed interval from `started_at` to `released_at` expressed in whole minutes with any partial minute discarded. `required_check_count` is `actual_duration_minutes` divided by `monitoring_interval_minutes`, rounded up to the next whole number.

**Compliance is measured two ways, and only one of them gates anything.** The interval-grid measure divides the episode into `required_check_count` consecutive slots, where slot number k runs from `started_at` plus k minus one intervals, inclusive, up to `started_at` plus k intervals, exclusive. `grid_satisfied_slot_count` is the number of those slots holding at least one log entry whose `recorded_at` falls inside the slot, and `grid_compliance_pct` is 100 multiplied by `grid_satisfied_slot_count`, divided by `required_check_count`, rounded half up to one decimal place. Because at most one entry can ever credit a slot, checks clustered at the start of an episode leave later slots unsatisfied. The raw measure ignores slots entirely: `raw_compliance_pct` is 100 multiplied by the lesser of `required_check_count` and the number of entries in `monitoring_check_log`, divided by `required_check_count`, rounded half up to one decimal place. The two diverge routinely — a 30-minute mechanical restraint with checks logged at 3 and 7 minutes after the start records a `grid_compliance_pct` of 50.0 against a `raw_compliance_pct` of 100.0. When `required_check_count` is 0, both percentages are 100.0. `raw_compliance_pct` is published for quality dashboards and never gates a transition; `grid_compliance_pct` is the only figure a debriefing consults.

Release also recomputes the admission's observation staffing burden. `observation_staff_quarter_hours` is the sum, over every episode of that admission whose `status` is `RELEASED`, `DEBRIEFED` or `EXPIRED_UNAUTHORIZED`, of that episode's `actual_duration_minutes` divided by 15 and rounded up to the next whole number. Episodes still in `ORDERED` or `ACTIVE` have no `actual_duration_minutes` and contribute nothing. **The rounding order is pinned: the ceiling is taken per episode and the per-episode ceilings are then added.** Summing the raw minutes first and taking a single ceiling is wrong — two 20-minute episodes contribute two quarter-hours each, for a total of four, not the three that a single ceiling over 40 minutes would give. For auditability the episodes are traversed by `started_at` ascending and then by `created_at` ascending, though that order does not change the total. The recomputation increments `Admission.version` by one, and for a `SECLUSION` episode the unit's `active_seclusion_count` is recomputed with `Unit.version` incremented by one.

Debriefing closes the episode properly. Performed by an `AttendingPsychiatrist` or a `ChargeNurse` on an episode in `RELEASED`, it carries `patient_participated_in_debrief`, a `staff_participants_count` of at least 1, and a `debrief_note`; it moves the episode `RELEASED → DEBRIEFED` and stamps `debrief_completed_at` from the clock. It is permitted only when `grid_compliance_pct` is exactly 100.0 — every interval slot accounted for. Anything less, including an episode with no log entries at all, is refused with `ERR_MONITORING_INCOMPLETE`.

The sweep provides the punitive alternative ending, and its two branches diverge from the release path in ways that must be reproduced exactly. An episode still in `ORDERED` when the clock has moved strictly past `face_to_face_deadline_at` moves `ORDERED → EXPIRED_UNAUTHORIZED`: its `released_at` is set to the lapsed `face_to_face_deadline_at` rather than to the sweep instant, its `actual_duration_minutes` is 60, both compliance percentages are computed, the admission's `rights_violation_flag` is set true, the unit's `open_rights_violation_count` is recomputed, and the admission's `observation_staff_quarter_hours` is recomputed. An episode in `ACTIVE` when the clock has reached or passed `authorized_until_at` moves `ACTIVE → EXPIRED_UNAUTHORIZED`: its `released_at` is set to `authorized_until_at`, its `actual_duration_minutes` equals the full `ordered_duration_minutes`, both compliance percentages are computed, the `rights_violation_flag` and `open_rights_violation_count` are set and recomputed as above, `observation_staff_quarter_hours` is recomputed, and the unit's `active_seclusion_count` is recomputed. `EXPIRED_UNAUTHORIZED` is terminal and debriefing is never reachable from it — an episode that lapsed without authorization cannot be closed out as if it had been managed properly.

### 3.7. Capacity, Substitute Decision Makers and Medication Consent

Capacity to consent to psychotropic medication is a clinical determination that can change during a stay, so it is recorded as its own resource rather than a flag. An `AttendingPsychiatrist` records one against an `admission_id`, carrying the mandatory `expected_admission_version` of §2.7 and a `capacity_present` boolean. When `capacity_present` is false the body must also carry all three surrogate fields: a `surrogate_name`, a `surrogate_relationship` of `SPOUSE`, `PARENT`, `ADULT_CHILD` or `GUARDIAN`, and a `surrogate_authority_scope` of `NONE`, `MEDICATION_ONLY` or `FULL`. When `capacity_present` is true all three must be absent. Either asymmetry — missing surrogate fields on an incapacity finding, or surrogate fields supplied alongside a finding of capacity — is refused with `ERR_SURROGATE_REQUIRED`.

The server stamps `determined_by_clinician_id` from the header and `determined_at` from the logical clock, and sets `status` to `ACTIVE`. At most one determination per admission may be `ACTIVE`, so creating a new one moves any prior `ACTIVE` determination for that admission to `SUPERSEDED`. The new finding is mirrored onto the admission's own `capacity_present` field, which stays null until the first determination exists, and `Admission.version` increments by one.

Medication consent records the legal basis on which a psychotropic may be given. An `AttendingPsychiatrist` names the `admission_id`, the `medication_name`, and a `consent_basis` of `PATIENT_CONSENT`, `SURROGATE_CONSENT` or `EMERGENCY_OVERRIDE`; the server records `prescribing_clinician_id` from the header and sets `status` to `ACTIVE`. Each basis has its own precondition. `PATIENT_CONSENT` requires the admission to have an `ACTIVE` capacity determination whose `capacity_present` is true, and fails with `ERR_CAPACITY_LACKING` otherwise. `SURROGATE_CONSENT` requires a `capacity_determination_id` naming the determination that authorizes the surrogate, and that determination must be `ACTIVE`, must record `capacity_present` as false, and must grant a `surrogate_authority_scope` of either `MEDICATION_ONLY` or `FULL`; a determination that is `SUPERSEDED`, or records capacity as present, or grants a scope of `NONE`, is refused with `ERR_SURROGATE_SCOPE_INSUFFICIENT`. `EMERGENCY_OVERRIDE` requires the patient to have at least one hold in `ACTIVE`, requires the admission's `legal_status` to be `INVOLUNTARY`, and requires a non-empty `emergency_justification`; a failure of the hold condition is `ERR_NO_ACTIVE_HOLD`. The `capacity_determination_id` is supplied only for a surrogate basis and is null for the other two, and `emergency_justification` is supplied only for an emergency override and is null otherwise.

An emergency override is time-limited by design: its `expires_at` is set to the logical clock at creation plus 72 hours, and the compliance sweep moves any such consent from `ACTIVE` to `EXPIRED` once the clock has passed that instant. Consents on the other two bases carry a null `expires_at` and never expire.

### 3.8. Leaving: Discharge Requests, Follow-Up Guarantees and Physical Discharge

A patient or their guardian may ask to leave at any time, and the clock on answering that request starts immediately. A `ChargeNurse` or a `PatientRightsAdvocate` records the request against an `admission_id` with a `requested_by` value of `PATIENT` or `GUARDIAN`; the server stamps `requested_at` from the logical clock and `recorded_by_clinician_id` from the header, sets both `decision` and `status` to `PENDING`, and leaves `responding_clinician_id` and `response_note` null. Only one request per admission may be open at a time: a second recorded while one is still `PENDING` is refused with `ERR_DUPLICATE_DISCHARGE_REQUEST`. The admission must be in `PENDING_PLACEMENT` or `PLACED`.

The response deadline is 24 business hours from `requested_at`, measured on the business calendar of §2.6 — nine hours a day between 08:00:00 and 17:00:00 UTC, with Saturdays, Sundays and the recognized holidays skipped entirely. The budget is consumed day by day. Starting from `requested_at`, if the current candidate instant falls on a weekend day or a holiday, or is at or after that day's 17:00:00 close, the candidate moves to the next day at `08:00:00.000Z` and the test restarts; if the candidate falls before that day's 08:00:00 open, it moves up to the open. Whatever remains between the candidate and that day's close is the day's available time; if it covers the remaining budget, the deadline is the candidate plus the remaining budget and the computation ends; otherwise the available time is subtracted from the budget and the candidate moves to the next day at `08:00:00.000Z`. The result is stored as `response_deadline_at`. Worked through, a request recorded at `2026-09-03T15:00:00Z` yields `2026-09-09T12:00:00.000Z`: two hours on Thursday the 3rd, nine on Friday the 4th, the weekend skipped, Monday the 7th skipped as a holiday, nine on Tuesday the 8th, and the final four on Wednesday the 9th.

An `AttendingPsychiatrist` answers a `PENDING` request with a `decision` and a `response_note`, and the server records `responding_clinician_id` from the header. A `decision` of `GRANT` requires the admission's `legal_status` to be `VOLUNTARY`; granting release to a patient under an active hold is refused with `ERR_ACTIVE_HOLD_BLOCKS_DISCHARGE`. Granting moves the request `PENDING → GRANTED_DISCHARGE` and advances the admission's placement axis: an admission in `PLACED` becomes `DISCHARGE_READY` while keeping its bed `OCCUPIED` until the physical discharge, and an admission still in `PENDING_PLACEMENT` becomes `CANCELLED`, which changes no unit counter because no bed was ever held. A `decision` of `DENY` requires the opposite: the patient must have at least one hold in `ACTIVE`, or the denial is refused with `ERR_NO_ACTIVE_HOLD`. Denial moves the request `PENDING → DENIED_HOLD_INITIATED` and leaves the admission entirely untouched. A request that is neither granted nor denied by its `response_deadline_at` is swept to `EXPIRED_UNANSWERED`: that sets the admission's `rights_violation_flag` true and recomputes the unit's `open_rights_violation_count`, and — when the admission's `legal_status` is `VOLUNTARY` — additionally advances it `PLACED → DISCHARGE_READY`, or `PENDING_PLACEMENT → CANCELLED`. Silence is not a defence; an unanswered request is treated as granted for a voluntary patient and recorded as a rights violation either way.

Discharge planning is the guarantee that a patient does not leave into a vacuum. An `AttendingPsychiatrist` or a `ChargeNurse` submits a `follow_up_provider_name` and a `follow_up_appointment_at` while the admission is in `PENDING_PLACEMENT` or `PLACED`. The permitted lead time depends on how the patient was held and how sick they were: 7 days when the `legal_status` is `INVOLUNTARY` and the `acuity_tier` is `HIGH`, 10 days when the `legal_status` is `INVOLUNTARY` and the tier is `MODERATE` or `LOW`, and 14 days when the `legal_status` is `VOLUNTARY`. For a patient whose `is_minor` is true the window is tightened to the lesser of that base figure and 5 days — so a voluntary minor gets 5 days, not 14. The resulting figure is stored as `follow_up_guarantee_days`, and `follow_up_guarantee_deadline_at` is the logical clock **at plan submission** plus that many 24-hour days; the window is anchored to submission time and never to the later discharge instant. The plan is accepted only when `follow_up_appointment_at` is strictly after the current clock and at or before `follow_up_guarantee_deadline_at` — an appointment exactly at the deadline is accepted, one exactly at the current clock is not — and a violation of either bound is `ERR_FOLLOW_UP_WINDOW_EXCEEDED`. Acceptance moves `discharge_plan_status` `NOT_STARTED → APPOINTMENT_SECURED` and increments `Admission.version` by one.

Physical discharge is restricted to an `AttendingPsychiatrist` and carries a `discharge_summary` narrative. Four preconditions apply. The admission's `placement_status` must be `PLACED` or `DISCHARGE_READY`, or the request fails with `ERR_ADMISSION_NOT_DISCHARGEABLE`. Its `legal_status` must be `VOLUNTARY`, or the request fails with `ERR_ACTIVE_HOLD_BLOCKS_DISCHARGE`. Its `discharge_plan_status` must be `APPOINTMENT_SECURED` and its `follow_up_appointment_at` must still lie strictly in the future relative to the current clock, or the request fails with `ERR_DISCHARGE_PLAN_INCOMPLETE` — a secured appointment that has since gone stale is no guarantee at all. And no restraint episode of that admission may remain in `ORDERED`, `ACTIVE` or `RELEASED`; an episode released but never debriefed still blocks discharge, and the refusal is `ERR_OPEN_RESTRAINT_EPISODE`.

A successful discharge is the longest cascade in the system, and every link must fire in the same request. First, `placement_status` becomes `DISCHARGED` and `discharged_at` is stamped from the logical clock, while `bed_id` is deliberately retained on the record for audit rather than nulled. Second, because the admission has released its bed, that bed's `status` flips `OCCUPIED → AVAILABLE` and `Bed.version` increments by one. Third, because a bed became `AVAILABLE`, the unit's `occupied_bed_count`, `raw_available_bed_count`, `posture` and `effective_available_bed_count` are recomputed and `Unit.version` increments by one. Fourth — and only when that recomputation moved the unit's `posture` out of `CLOSED` — the queued-admission promotion of §3.5 selects a single winner, flips that admission `PENDING_PLACEMENT → PLACED`, flips its selected bed `AVAILABLE → OCCUPIED`, and recomputes the unit's counters and posture a second time. `DISCHARGED` and `CANCELLED` are the two terminal states of the placement axis.
