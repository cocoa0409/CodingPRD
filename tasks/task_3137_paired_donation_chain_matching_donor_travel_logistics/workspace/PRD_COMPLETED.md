# Paired Donation Chain Matching & Donor Travel Logistics API — Product Requirements Document

## 1. Introduction

This document specifies the Product Requirements for the National Kidney Registry's **Paired Donation Chain Matching & Donor Travel Logistics** API. The registry coordinates kidney paired donation at national scale: donors who are incompatible with their intended recipients enter a common pool, an algorithm constructs chains of cross-compatible transplants across multiple transplant centers, altruistic and bridge donors start new chains, and the resulting surgeries, organ shipments, and donor protection commitments are tracked end to end. Because a single chain can span half a dozen centers and a single late donor withdrawal can orphan several downstream recipients, the system places unusually strong emphasis on optimistic concurrency, hierarchical state propagation, and auditable side effects.

The audience for this document is the engineering team building the service. All endpoints are mounted under the `/nkr` prefix. The system maintains its own **logical clock** for test-driving and deadline evaluation: on server startup the logical clock reads exactly `2026-09-01T00:00:00Z`, does not fall back to wall-clock time, and advances only when an authorized caller invokes the clock-set capability. Time-dependent transitions (slot expiry, offer deadline expiry) are evaluated whenever the logical clock moves.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two authentication headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role under which the user acts. If `X-User-Role` is missing or not one of the recognized values, the server rejects the request with `ERR_UNAUTHENTICATED` (HTTP 401). If the role is recognized but is not authorized for the endpoint per the access rules below, the server rejects with `ERR_UNAUTHORIZED` (HTTP 403).

The system recognizes exactly four roles, spelled exactly as follows: `RegistryAdmin`, `MatchOperator`, `CenterCoordinator`, and `LogisticsCoordinator`.

- When `X-User-Role` is `RegistryAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it (for example as `adjudicator_user_id` on a `DonorProtectionClaim` when an adjudication transition is performed) but does not compare it to any entity's `id`.
- When `X-User-Role` is `MatchOperator`, `X-User-ID` is likewise an opaque operator identifier; it is not compared to any persisted entity's `id`.
- When `X-User-Role` is `LogisticsCoordinator`, `X-User-ID` is an opaque operator identifier with no entity binding.
- When `X-User-Role` is `CenterCoordinator`, `X-User-ID` is the `id` of the acting `TransplantCenter`; ownership checks on any resource that references a `TransplantCenter` compare the resource's relevant center foreign-key field (for example `home_center_id`, `recipient_center_id`, or `attributed_center_id`) to `X-User-ID`. A mismatch between the acting coordinator's center and the center owning the targeted resource is rejected with `ERR_CENTER_MISMATCH` (HTTP 403).

Role capabilities in brief: `RegistryAdmin` administers centers, adjudicates claims, reimburses travel, and finalizes outcome attribution. `MatchOperator` runs chain-construction batches, locks and schedules chains, releases reserved slots, and marks chain breaks reconstructed. `CenterCoordinator` registers donors, recipients, and pairs, performs medical transitions, submits crossmatch reviews, accepts or declines offers on behalf of the recipient center, opens surgery slots, files protection claims, reports outcomes, and files appeals. `LogisticsCoordinator` plans organ shipments and donor travel itineraries and advances their lifecycle states. All four roles may use read (list/get) endpoints across all resources. The clock-set capability is shared by `RegistryAdmin` and `MatchOperator` only.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept the query parameters `limit` and `offset`. `limit` defaults to 10, must be at least 1, and must not exceed 100. `offset` defaults to 0. Unless otherwise specified, list responses are sorted by `created_at` in ascending order, with `id` ascending as the tie-breaker. The `meta` envelope of a paginated list response carries `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. Common Resource Properties

Every top-level and nested resource in this system carries a standard set of system-managed fields:

- `id` — a server-minted UUID with no type prefix.
- `created_at` — an ISO 8601 UTC timestamp with three fractional digits, stamped at creation.
- `updated_at` — an ISO 8601 UTC timestamp refreshed on every mutation of the resource.
- `version` — an integer starting at 1 at creation and incremented by one on every mutation. Mutations that flow from cascading side effects (for example a chain break propagating `OFFER_FAILED` onto a downstream offer) each independently update the affected resource's `updated_at` and increment its `version`.

### 2.5. Nested Resource Retrieval and Validation Order

Endpoints whose paths contain multiple resource identifiers are validated strictly left-to-right: the server first verifies the leftmost path resource exists, then the next, and so on. The first missing identifier short-circuits the request with `ERR_NOT_FOUND` (HTTP 404). Body-referenced foreign keys (for example a `match_offer_id` supplied in a shipment-creation body) are likewise resolved to existing resources; a reference that does not resolve is rejected with `ERR_NOT_FOUND`. The path parameter names used across the API are stable and part of the contract: `center_id`, `donor_id`, `recipient_id`, `pair_id`, `run_id`, `chain_id`, `offer_id`, `review_id`, `slot_id`, `shipment_id`, `itinerary_id`, `policy_id`, `claim_id`, `outcome_id`, and `event_id`. The state-field names that drive the domain machines are likewise stable: `participation_status` on a center, `medical_status`, `surgery_state`, and `chain_participation_state` on donors and recipients, `pair_state` on a pair, `run_state` on a chain run, `chain_state` on a chain, `offer_state` on a match offer, `decision` on a `CrossmatchReview`, `slot_state` on a slot, `shipment_state` on a shipment, `itinerary_state` on an itinerary, `policy_state` on a policy, `claim_state` on a claim, `outcome_state` on an outcome, and `event_state` on a chain break event.

Validation across the system runs in a fixed priority order so that callers see deterministic failure surfaces. The ordering, from first-evaluated to last, is: (1) authentication of the role header; (2) authorization of the role against the endpoint; (3) existence of path-templated resources left-to-right; (4) existence of body-referenced foreign keys; (5) center suspension guards; (6) donor clearance guards; (7) recipient listing guards; (8) center-ownership segregation checks; (9) generic state-machine legality; (10) optimistic-concurrency version match; (11) review-deadline temporal checks; (12) slot lead-time checks; (13) itinerary flight-window checks; (14) slot overlap constraints; (15) pair incompatibility eligibility; (16) candidate pool size; (17) chain-lock mutability; (18) organ readiness; (19) cold-ischemia acceptance; (20) claim bucket headroom; (21) protection-policy existence; (22) organ arrival for transplant; (23) recipient commitment; (24) donor post-nephrectomy immutability; (25) center concurrency capacity; (26) claim segregation-of-duties; and (27) generic request shape. A request failing an earlier check never observes a later one's error.

### 2.6. Optimistic Concurrency Control

Four write endpoints require an optimistic-concurrency version field in the request body. A request that carries a stale value — one that does not equal the current `version` of the named parent entity — is rejected with `ERR_STALE_VERSION` (HTTP 412); a request that omits the field is accepted without a version check. The four guarded operations are:

- **Scheduling a chain** requires `expected_chain_version`, matched against the target `Chain`'s current `version`. If another writer has advanced the chain's version since the client last observed it — for example by locking, cascading an update, or completing a schedule — the schedule call is rejected.
- **Locking a chain** requires `expected_chain_version`, matched the same way against the `Chain`'s current `version`.
- **Suspending a transplant center** requires `expected_center_version`, matched against the `TransplantCenter`'s current `version`. If the center's version has advanced since the caller's last read — because of probate, reinstate, or a recomputed reputation — the suspend is rejected.
- **Executing a chain run** requires `expected_run_version`, matched against the `ChainRun`'s current `version`.

Endpoints not in this list do not accept a version field.

### 2.7. Precision, Monetary Values, and the Logical Clock

All monetary amounts are integer cents. Where a calculation produces a non-integer intermediate (the flight component of travel reimbursement multiplies miles by a cents-per-mile constant), the component is rounded half-up to the nearest cent before components are summed. Cold-ischemia duration in hours is reported with two decimal places, rounded half-up. Basis-point scores (match score, center reputation) are integers on the closed range 0 through 10000.

The logical clock is advanced only by an authorized caller supplying a target `to_iso8601` timestamp through the clock-set capability. Advancing the clock triggers the time-based transitions described throughout §3 — open or reserved slots whose `slot_end_utc` has passed move to `EXPIRED`, and offers whose `crossmatch_deadline_utc` or `center_accept_deadline_utc` has passed move to `OFFER_FAILED`.

### 2.8. Hierarchical Consistency and Cascading Side Effects

Many operations in this domain fan out: a donor withdrawal breaks a chain; a center suspension rolls back accepted offers; a chain-break event orphans downstream recipients and may mint a bridge donor. The principle is that when a parent-level event renders a child resource's state incoherent, the child is transitioned automatically by the system, with each such transition independently updating the child's `updated_at` and incrementing its `version`. Conversely, child-level completions (nephrectomy done, organ delivered, transplant completed) drive parent aggregates (chain `length_actual`, chain `completion_grade`) upward. The exact cascades are enumerated per workflow in §3.

### 2.9. Segregation of Duties on Claims

Claim adjudication is segregated from claim submission. The user recorded at submission time as the claim's submitter (via a `submitter_user_id` field captured from the request header at submit time) may not adjudicate the same claim: an attempt by the same `X-User-ID` to approve, partially approve, or deny is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

## 3. Business Logic & Workflows

### 3.1. Transplant Center Lifecycle and Participation Discipline

A `RegistryAdmin` provisions a transplant center by supplying its `center_code` (a unique national code such as `CA-SF-001`), its legal `name`, a three-letter UNOS-style `region_code`, a participation `tier` (one of `STANDARD`, `PREFERRED`, or `NATIONAL_HUB`), and a `max_concurrent_chains` integer bounding how many chains may be in `SCHEDULED` state at the center at any moment. New centers are born with `participation_status` equal to `ACTIVE` and with all computed counters — `failed_outcome_count`, `shipped_organ_count`, `probed_cold_ischemia_violations`, `reputation_score_bps`, and `active_chain_count` — initialized.

A center's `participation_status` moves among `ACTIVE`, `PROBATION`, and `SUSPENDED`. Probation is a disciplinary step applied by a `RegistryAdmin`: it is permitted only from `ACTIVE`, and only when at least one of two triggers holds — the center's `probed_cold_ischemia_violations` has reached the probation threshold `PROBATION_CIT_VIOLATIONS`, or its `failed_outcome_count` has reached the probation threshold `PROBATION_FAILURES`. Otherwise the transition is rejected with `ERR_CENTER_INVALID_STATE`. A center in `PROBATION` continues to schedule surgeries but cannot accept new match offers; in addition, every pending or crossmatch-passed offer at that center is logically flagged `stale_review` (a transient flag, not a stored field). Offer review and acceptance additionally require the center's `participation_status` to be exactly `ACTIVE` (see §3.4), so probation — like suspension — blocks them, surfacing `ERR_CENTER_SUSPENDED`. Reinstatement from `PROBATION` back to `ACTIVE` is permitted only while both thresholds are again below their respective limits — `probed_cold_ischemia_violations` strictly less than `PROBATION_CIT_VIOLATIONS` **and** `failed_outcome_count` strictly less than `PROBATION_FAILURES`.

Suspension is the hard sanction. A `RegistryAdmin` may suspend a center from either `ACTIVE` or `PROBATION`; any other starting state yields `ERR_CENTER_INVALID_STATE`. Because suspension cascades destructively, the call is OCC-guarded by `expected_center_version` (see §2.6). The suspension cascade does three things at once: every `RESERVED` surgery slot at the center moves to `RELEASED` (clearing `reserved_for_chain_id`, `reserved_for_offer_id`, and `simultaneous_group_id`); every offer at the center currently in `CENTER_ACCEPTED` rolls back to `CROSSMATCH_PASSED`, undoing the acceptance; and every offer at the center in `PENDING_CROSSMATCH` or `CROSSMATCH_PASSED` — including the just-rolled-back offers — moves to `OFFER_FAILED` with `offer_failure_reason` equal to `CHAIN_BREAK_PROPAGATION`, so no offer at the suspended center is left accepted. For these purposes an offer is "at the center" when either its `donor_center_id` or its `recipient_center_id` equals the center. Reinstatement from `SUSPENDED` back to `ACTIVE` is permitted only when no chain whose `chain_state` is `LOCKED`, `SCHEDULED`, or `EXECUTING` references the center — via its `starts_at_center_id` or via any of its offers' donor or recipient centers; otherwise the transition is rejected with `ERR_CENTER_INVALID_STATE`.

Center scheduling capacity is enforced separately: scheduling a chain is rejected with `ERR_CENTER_AT_CAPACITY` when any participating center's `active_chain_count` has already reached its `max_concurrent_chains`. The active-chain count is the number of distinct chains with at least one offer at that center in `SCHEDULED` state — with a chain additionally counted when its `starts_at_center_id` equals the center even if no offer references it — and it is recomputed on read and before the capacity check rather than maintained as a stored tally.

### 3.2. Donor and Recipient Registration, Pair Vetting, and Pool Entry

A `CenterCoordinator` at the donor's home center registers a donor with the center-issued `external_ref`, the donor's `home_center_id`, the `abo_type` (one of `A`, `B`, `AB`, or `O`), three comma-separated HLA loci `hla_a`, `hla_b`, and `hla_drb1` (each locus carrying two alleles such as `A02,A24`), an integer `kdri_score` on the Kidney Donor Risk Index range from 20 to 250 (lower is better), an integer `age_at_registration` which must be at least 18, and a `donor_kind` — `PAIRED` for a donor entering with a recipient, `ALTRUISTIC` for a non-directed chain starter, or `BRIDGE` for a donor holding a bridge credit. The donor's initial `medical_status` is `CLEARED`, initial `surgery_state` is `PRE_SURGERY`, and initial `chain_participation_state` is `POOL`. The donor's `protection_policy_id` is null until the nephrectomy completes, `priority_waitlist_status` begins at `NONE`, and the computed fields `traveled_distance_miles` and `complications_recorded` start at zero. A donor's `medical_status` may move through `CLEARED`, `ON_HOLD`, and the terminal values `WITHDRAWN` and `DECEASED`; `surgery_state` moves from `PRE_SURGERY` through `SURGERY_SCHEDULED` to either `NEPHRECTOMY_DONE` or `FAILED_PREOP`; `chain_participation_state` walks `POOL` → `PROPOSED` → `LOCKED` → `COMMITTED` and terminates at one of `COMPLETED`, `BROKEN`, or `WITHDRAWN`. The donor's `nephrectomy_completed_at_utc` field is null until the nephrectomy completes, when it is stamped with the donor's `updated_at` at that moment (it is the timestamp from which cold ischemia is measured).

Recipients are registered similarly, with `external_ref`, `home_center_id`, `abo_type`, a `cpra_percent` sensitization score from 0 to 100 (higher narrows the feasible donor pool), and an `unacceptable_antigens` array listing HLA antigens the recipient's antibodies will attack. The optional `paired_donor_id` records the donor the recipient entered with; it is null for non-paired entry. A new recipient is stamped with `listed_at_utc` at creation, has `medical_status` equal to `LISTED`, `chain_participation_state` equal to `POOL`, and `priority_boost_active` false. A recipient also carries the same three HLA locus fields (`hla_a`, `hla_b`, `hla_drb1`) used in match scoring; they are optional at registration and default to empty. The read-only `waiting_time_days` is recomputed on read as the whole days from `listed_at_utc` to the current logical clock, floored at zero (a clock set before `listed_at_utc` never yields a negative value), and `transplant_completed_at_utc` is stamped when the recipient reaches `TRANSPLANTED`. When a recipient registers whose `external_ref` matches an existing donor who has already completed nephrectomy and whose `priority_waitlist_status` is `ELIGIBLE`, that donor's `priority_waitlist_status` advances to `ENROLLED` and the new recipient's `priority_boost_active` is set true at creation.

The `CenterCoordinator` then registers the `DonorRecipientPair` itself, referencing the `donor_id`, `recipient_id`, and the vetting `registered_center_id`. Registering a pair also back-fills the recipient's `paired_donor_id` with the pair's donor when that field is still null. A pair begins in `pair_state` `REGISTERED` and is verified by a coordinator, which requires that the donor be `CLEARED` (otherwise `ERR_DONOR_NOT_CLEARED`) and the recipient be `LISTED` (otherwise `ERR_RECIPIENT_NOT_LISTED`); the pair itself must be in `REGISTERED` (otherwise `ERR_INVALID_STATE`). Verification moves the pair to `VERIFIED`. A verified pair is admitted to the national pool by the same coordinator role. Pool entry enforces genuine need: the donor and recipient must be ABO-cross-incompatible in the donation direction, or the donor must express at least one antigen in the recipient's `unacceptable_antigens` list, or — for a compatible-pair bypass — the request body must carry `compatible_pair_opt_in` set to true on a `PAIRED`-kind pair. If none of the three holds, pool entry is rejected with `ERR_PAIR_NOT_INCOMPATIBLE`. Successful entry moves the pair to `IN_POOL`, stamps `entered_pool_at_utc`, and confirms both participants' `chain_participation_state` as `POOL`.

A pair still in `VERIFIED` or `IN_POOL` may be dissolved by a `CenterCoordinator`; dissolution sets the pair to `DISSOLVED` and records the `dissolution_reason` supplied in the request body — one of `NONE`, `RECIPIENT_TRANSPLANTED`, `DONOR_WITHDRAWN`, `MEDICAL_DECLINE`, or `CHAIN_BROKEN`. Once a chain locks a pair, the pair may no longer be dissolved through this route. When a chain run selects a pair, the pair moves from `IN_POOL` to `IN_PROPOSED_CHAIN`; when the chain locks, the pair moves from `IN_PROPOSED_CHAIN` to `LOCKED`; recipient transplant completion moves it from `LOCKED` to `RELEASED` (with `dissolution_reason` equal to `RECIPIENT_TRANSPLANTED`), and a chain break moves it from `LOCKED` to `DISSOLVED` with `dissolution_reason` equal to `CHAIN_BROKEN`.

### 3.3. Chain Run Execution and Chain Construction

Chain matching proceeds in batches. A `MatchOperator` opens a `ChainRun` by supplying an operator-chosen `run_label` such as `weekly-batch-2026-W36`; the run is stamped with `started_at_utc`, starts in `run_state` `DRAFT` with `algorithm_version` null and `candidate_pool_size` and `proposed_chain_count` zeroed, and will be stamped with the server's `algorithm_version` at execution time (taken from the `CHAIN_ALGORITHM_VERSION` constant). A run moves from `DRAFT` to `EXECUTED`, then either to `PUBLISHED` or directly to `SUPERSEDED`; `PUBLISHED` may also be superseded, and `SUPERSEDED` is terminal.

Executing a run is the heavy operation and is OCC-guarded by `expected_run_version`. Execution requires that the run still be in `DRAFT` (otherwise `ERR_INVALID_STATE`) and that the candidate pool size — the number of `DonorRecipientPair` rows in `IN_POOL` — is at least `MIN_POOL_SIZE` of 2, otherwise `ERR_POOL_TOO_SMALL`. Execution runs the chain-construction algorithm and mints `Chain` rows in `PROPOSED` state with embedded `MatchOffer` rows in `PENDING_CROSSMATCH`, recording on the run the `candidate_pool_size` observed at execution and the resulting `proposed_chain_count`.

The chain-construction algorithm proceeds as follows. The candidate pool consists of every pair in `IN_POOL`, plus every `ALTRUISTIC` donor whose `medical_status` is `CLEARED` and whose `chain_participation_state` is `POOL`. Step 1 computes the match score (see §3.4) for every donor–recipient Cartesian pair where donor and recipient come from different pairs. Step 2 keeps only edges whose `match_score_bps` is strictly greater than zero, whose `unacceptable_antigen_hit` is false, and whose `abo_compatible` is true. Step 3 orders candidate starting donors: altruistic donors first in `created_at` ascending order, then bridge donors in `created_at` ascending order. Step 4 greedily extends each starting donor by picking the highest-scoring unused recipient, recursing from that recipient's paired donor, and stopping when no outgoing edge remains, when chain length reaches `MAX_CHAIN_LENGTH` of 6, or when the donor has no paired recipient (an altruistic donor terminates by donating to a recipient whose own paired donor would start a new chain — such continuation is deferred and not unrolled within the same run). Ties among equal-scoring recipients break by `listed_at_utc` ascending — the earliest-listed recipient wins — and any residual tie breaks by recipient `created_at` ascending. UUIDs are never used as tie-breakers. The run's execution increments the `ChainRun`'s `version` by one.

A run in `EXECUTED` may be published by a `MatchOperator`, moving it to `PUBLISHED`; publication leaves the proposed chains in place and sets each participating donor's and recipient's `chain_participation_state` to `PROPOSED`. Alternatively, an executed or published run may be superseded, which moves it to `SUPERSEDED` — but only while no child chain has reached `LOCKED` or any later state (`LOCKED`, `SCHEDULED`, `EXECUTING`, or `COMPLETED`; otherwise `ERR_CHAIN_LOCKED`). Supersession aborts every proposed or accepting chain (each chain in `PROPOSED` or `ACCEPTING` moves to `ABORTED`), fails every embedded offer still in `PENDING_CROSSMATCH`, `CROSSMATCH_PASSED`, or `CENTER_ACCEPTED` with `offer_failure_reason` equal to `CHAIN_BREAK_PROPAGATION`, reverts each participant's `chain_participation_state` from `PROPOSED` back to `POOL`, and returns each pair the run selected from `IN_PROPOSED_CHAIN` back to `IN_POOL`.

Each `Chain` row carries its `chain_run_id`, the `starter_donor_id` (the altruistic or bridge donor who opens the chain), the declared `length_target` (the count of recipient transplants the chain is targeting at proposal time), the `starts_at_center_id` where the first nephrectomy will happen, the `scheduled_date` once locked surgery dates are stamped, the `broken_at_index` recording the 1-based `position_index` of the offer where a break occurred (null unless the chain is `BROKEN`), the `completion_grade` (initially `PENDING`), and the computed `length_actual` counting offers that reached `TRANSPLANT_COMPLETED`. The chain's `chain_state` begins at `PROPOSED`, moves to `ACCEPTING` automatically when its parent run is published, and from there may be locked, scheduled, executed, and finally completed or broken.

### 3.4. Crossmatch Review and Center Acceptance

Each offer minted by a chain run begins in `PENDING_CROSSMATCH` and is reviewed by a `CenterCoordinator` at the offer's `recipient_center_id`. The submitted `CrossmatchReview` records the reviewer's center on its `reviewer_center_id` field, which must equal the offer's `recipient_center_id`. Review submission carries the reviewer's `virtual_result` (one of `NEGATIVE`, `WEAK_POSITIVE`, `STRONG_POSITIVE`, or `INDETERMINATE`), the raw `flow_cytometry_channel_shift` reading on a 0–1024 scale, the `dsa_mfi_max` donor-specific antibody reading on a 0–30000 scale, and free-text `review_notes`. The reviewer must be a coordinator of the recipient center (otherwise `ERR_CENTER_MISMATCH`), the recipient center's `participation_status` must be `ACTIVE` (otherwise `ERR_CENTER_SUSPENDED`), the donor's `medical_status` must be `CLEARED` (otherwise `ERR_DONOR_NOT_CLEARED`) and the recipient's `medical_status` must be `LISTED` (otherwise `ERR_RECIPIENT_NOT_LISTED`), the offer must still be in `PENDING_CROSSMATCH` (otherwise `ERR_INVALID_STATE`), and the logical clock must not have reached the offer's `crossmatch_deadline_utc` (otherwise `ERR_REVIEW_DEADLINE_PASSED`). The crossmatch deadline is computed at proposal time as `proposed_at_utc` plus `CROSSMATCH_REVIEW_HOURS`; the center-acceptance deadline is likewise `proposed_at_utc` plus `CENTER_ACCEPT_HOURS`.

The review's `decision` is computed by the system from `virtual_result` and `dsa_mfi_max` per the center's policy: a `NEGATIVE` result with `dsa_mfi_max` strictly below the `DSA_PASS_THRESHOLD` of 1000 yields `PASS`; a `NEGATIVE` result with `dsa_mfi_max` at or above 1000 yields `FAIL` (a silent DSA); a `WEAK_POSITIVE` result with `dsa_mfi_max` strictly below the `DSA_WEAK_THRESHOLD` of 3000 yields `PASS`; a `WEAK_POSITIVE` result at or above 3000 yields `FAIL`; any `STRONG_POSITIVE` yields `FAIL` regardless of MFI; and `INDETERMINATE` yields `FAIL` on conservative grounds. A `PASS` decision moves the offer from `PENDING_CROSSMATCH` to `CROSSMATCH_PASSED` and stamps `decided_at_utc` on the review; a `FAIL` moves it to `CROSSMATCH_FAILED` with `offer_failure_reason` equal to `CROSSMATCH_POSITIVE`. A failed offer cannot proceed; the chain-construction logic re-evaluates the chain, which moves to `ABORTED` if no replacement is found — concretely, when the failing offer's chain is still in `PROPOSED` or `ACCEPTING`, the chain is aborted immediately and every other offer of that chain still in `PENDING_CROSSMATCH` or `CROSSMATCH_PASSED` moves to `OFFER_FAILED` with `offer_failure_reason` equal to `CHAIN_BREAK_PROPAGATION`. Reviews whose submitted fields would violate center review policy are rejected with `ERR_REVIEW_POLICY_VIOLATION`.

With the offer in `CROSSMATCH_PASSED`, the recipient center's coordinator accepts it — moving the offer to `CENTER_ACCEPTED` and stamping `accepted_at_utc` — provided the recipient center's `participation_status` is `ACTIVE`, the donor center's `participation_status` is also `ACTIVE`, the logical clock has not reached `center_accept_deadline_utc`, and the acting coordinator's center matches `recipient_center_id`. Both center-state failures surface as `ERR_CENTER_SUSPENDED`; a deadline failure surfaces as `ERR_REVIEW_DEADLINE_PASSED`; a center mismatch surfaces as `ERR_CENTER_MISMATCH`. Declining is the sibling action: a coordinator at the recipient center moves the offer to `CENTER_DECLINED` — allowed only while the offer is in `CROSSMATCH_PASSED` (otherwise `ERR_INVALID_STATE`), with no center-status or deadline checks — which immediately finalizes the offer as `OFFER_FAILED` with `offer_failure_reason` equal to `CENTER_DECLINE`, and the chain may be reconstructed.

Every offer carries the computed match metadata produced at proposal time. `abo_compatible` is the Boolean result of ABO donation-direction compatibility — the `ABO_DONOR_MAP` rule fixes the donation direction: an `O` donor may give to any recipient; an `A` donor may give to `A` or `AB`; a `B` donor may give to `B` or `AB`; an `AB` donor may give only to `AB`. `unacceptable_antigen_hit` is true exactly when the donor's combined HLA antigen set (the union of the two alleles at each of the three loci) intersects the recipient's `unacceptable_antigens`. `hla_mismatch_count` counts, across the three loci, how many have zero shared alleles between donor and recipient — a value from 0 to 3 (a recipient whose HLA loci were never supplied therefore mismatches at all three). The composite `match_score_bps` is computed at proposal time as follows: the KDRI component is `10000` reduced by `10000` times the proportion of the donor's `kdri_score` along the range from `KDRI_MIN` 20 to `KDRI_MAX` 250 — computed as the integer `10000 - (kdri_score - 20) * 10000 / 230` — clamped to the closed range from 0 to 10000. The HLA penalty is `hla_mismatch_count` multiplied by `HLA_PENALTY_PER_LOCUS_BPS` of 500 basis points. The waiting-time bonus is the recipient's `waiting_time_days` multiplied by `WAIT_BONUS_PER_DAY_BPS` of 5, capped at `WAIT_BONUS_CAP_BPS` of 1500. The priority bonus is `PRIORITY_BOOST_BPS` of 2000 if the recipient's `priority_boost_active` is true, zero otherwise. The cPRA bonus is the recipient's `cpra_percent` multiplied by `CPRA_BONUS_PER_PCT_BPS` of 20 — high sensitization is rewarded, because matching a highly sensitized recipient is valuable. The raw score is the KDRI component, minus the HLA penalty, plus the waiting-time bonus, plus the priority bonus, plus the cPRA bonus. If the pair is ABO-incompatible, or if `unacceptable_antigen_hit` is true, the score is zero outright; otherwise the raw score is floored at 0 and capped at 10000 to produce `match_score_bps`.

An offer that is `CENTER_ACCEPTED` advances to `SCHEDULED` automatically when its parent chain moves from `LOCKED` to `SCHEDULED`. Subsequent system-driven transitions take the offer through `DONOR_SURGERY_DONE` (when the donor's nephrectomy completes), then `ORGAN_SHIPPED` (when the linked shipment reaches `DELIVERED`), and finally `TRANSPLANT_COMPLETED` (when the recipient's transplant completes). Any offer can be moved to `OFFER_FAILED` by the system from `PENDING_CROSSMATCH`, `CROSSMATCH_PASSED`, `CENTER_ACCEPTED`, or `SCHEDULED` — by chain break, donor withdrawal, recipient withdrawal, deadline expiry, or run supersession; deadline expiry via the logical clock uses `offer_failure_reason` equal to `CHAIN_BREAK_PROPAGATION`. `OFFER_FAILED` and `TRANSPLANT_COMPLETED` are terminal. Each offer's `donor_travel_required` flag is true exactly when `donor_center_id` differs from `recipient_center_id`, signaling that the donor must travel or the organ must be shipped. Offers that fail carry an `offer_failure_reason` of one of `NONE`, `CROSSMATCH_POSITIVE`, `CENTER_DECLINE`, `COLD_ISCHEMIA`, `DONOR_UNAVAILABLE`, or `CHAIN_BREAK_PROPAGATION`.

### 3.5. Surgery Scheduling and Slot Reservation

Centers open operating-room capacity by registering `SurgeryScheduleSlot` rows: a `CenterCoordinator` supplies the `center_id`, the `slot_start_utc` and `slot_end_utc` (start strictly before end, and the duration must be at least `SLOT_MIN_HOURS`), and the `room_kind` — `NEPHRECTOMY_OR`, `TRANSPLANT_OR`, or `BACK_OR` (a recovery or backup room). New slots begin in `slot_state` `OPEN`. Slot intervals at the same center must not overlap when both are `RESERVED` or `CONSUMED`; intervals are half-open — a slot whose start equals another slot's end is permitted. This constraint is enforced both at slot creation (creating a slot that would overlap an existing `RESERVED` or `CONSUMED` slot at the same center is rejected) and at chain-schedule time, where an overlapping reservation is rejected with `ERR_SLOT_OVERLAP`. A slot whose start precedes the logical clock plus the `MIN_SCHEDULE_LEAD_HOURS` lead time is rejected with `ERR_SLOT_TOO_SOON`. A slot not `OPEN` at reservation time is rejected with `ERR_SLOT_TAKEN`.

Locking a chain is the gate between acceptance and scheduling. A `MatchOperator` locks a chain only when the chain is in `ACCEPTING` (otherwise `ERR_INVALID_STATE`) and every offer in the chain has reached `CENTER_ACCEPTED` (otherwise `ERR_PENDING_OFFERS`). The call is OCC-guarded by `expected_chain_version`. A successful lock moves the chain from `ACCEPTING` to `LOCKED`, flips each participating donor's and recipient's `chain_participation_state` to `LOCKED`, and increments the chain's `version` by one.

Scheduling a locked chain atomically reserves every required slot: a `MatchOperator` supplies `expected_chain_version`, the `scheduled_date`, and a `slot_ids` array naming the slots to reserve. The operation requires the chain to be `LOCKED`; rejects the call when any participating center — every offer's donor and recipient center plus the chain's `starts_at_center_id` — is `SUSPENDED` with `ERR_CENTER_SUSPENDED`; requires every offer in the chain to have at least one slot reserved at both its donor center and its recipient center by the time the call completes (a request that cannot satisfy this is rejected with `ERR_INVALID_REQUEST`); and requires that no participating center has reached `max_concurrent_chains` (otherwise `ERR_CENTER_AT_CAPACITY`). When the supplied `slot_ids` number exactly two per offer, they are mapped positionally — the first slot of each pair at the offer's donor center, the second at its recipient center; otherwise slots are assigned greedily by matching center. Each slot reserved flips from `OPEN` to `RESERVED`, with `reserved_for_chain_id` and `reserved_for_offer_id` recorded, and a shared `simultaneous_group_id` assigned across all slots reserved for the chain so that simultaneous-burst reservations are traceable as one group. On success the chain moves to `SCHEDULED`, `scheduled_date` is stamped, every donor's `surgery_state` moves to `SURGERY_SCHEDULED`, every participant's `chain_participation_state` moves to `COMMITTED`, every offer moves from `CENTER_ACCEPTED` to `SCHEDULED`, and the chain's `version` increments.

A reserved slot may be released by a `MatchOperator`, moving it to `RELEASED`, provided the slot is `RESERVED` and the chain it serves is not yet `EXECUTING` or `COMPLETED` — otherwise the release is rejected with `ERR_CHAIN_LOCKED`. Release clears `reserved_for_chain_id`, `reserved_for_offer_id`, and `simultaneous_group_id`. Slots left `OPEN` past their `slot_end_utc` move to `EXPIRED` automatically as the logical clock advances, as do `RESERVED` slots whose chain never started — that is, whose reserved-for chain is missing or still in `PROPOSED`, `ACCEPTING`, or `LOCKED`. When the surgery actually happens — a donor nephrectomy completes or, for `TRANSPLANT_OR` slots, the transplant completes — the corresponding `RESERVED` slot moves to `CONSUMED` and `consumed_at_utc` is stamped.

Starting execution is the final gate: a `MatchOperator` begins execution on a `SCHEDULED` chain, moving it to `EXECUTING`, provided the first offer's donor has been prepared — that is, the donor at position one is in `SURGERY_SCHEDULED`. From `EXECUTING`, the chain reaches `COMPLETED` automatically once `length_actual` equals `length_target`, and its `completion_grade` becomes `FULL`. If instead a chain break event lands on a chain in `SCHEDULED` or `EXECUTING`, the chain moves to `BROKEN` and the grade becomes `BROKEN_PARTIAL`.

Chain grading is pinned down exactly: when a chain reaches `COMPLETED`, `completion_grade` is `FULL`. When a chain reaches `BROKEN` with `length_actual` equal to zero, `completion_grade` is `BROKEN_PARTIAL`. When a chain reaches `BROKEN` with `length_actual` greater than zero but strictly less than `length_target`, `completion_grade` is likewise `BROKEN_PARTIAL`. The unreachable-by-construction case of a `BROKEN` chain whose `length_actual` meets or exceeds `length_target` is still pinned: it would be graded `FULL` even on the `BROKEN` label. Before any terminal transition, `completion_grade` remains `PENDING`.

### 3.6. Surgery Execution, Organ Shipment, and Cold Ischemia

The donor's medical lifecycle runs in parallel with the chain. A `CenterCoordinator` may place a cleared donor on hold (moving `medical_status` from `CLEARED` to `ON_HOLD`, with any other starting state rejected `ERR_INVALID_STATE`); doing so fails any offer in `PENDING_CROSSMATCH`, `CROSSMATCH_PASSED`, or `CENTER_ACCEPTED` that references the donor, with `offer_failure_reason` equal to `DONOR_UNAVAILABLE`. Placing a donor on hold is forbidden once `surgery_state` is `NEPHRECTOMY_DONE` (`ERR_DONOR_POST_NEPHRECTOMY`). Release from hold returns the donor to `CLEARED`. A donor in `CLEARED` or `ON_HOLD` may be withdrawn — but only while `surgery_state` is not `NEPHRECTOMY_DONE`, otherwise `ERR_DONOR_POST_NEPHRECTOMY`. Withdrawal from a donor embedded in a chain in `LOCKED`, `SCHEDULED`, or `EXECUTING` emits a `ChainBreakEvent` and cascades the break; a donor in no such active chain simply fails any pending offers referencing them (per the hold rule). Withdrawal also dissolves every pair still in `VERIFIED`, `IN_POOL`, or `IN_PROPOSED_CHAIN` naming the donor, with `dissolution_reason` equal to `DONOR_WITHDRAWN`, and moves the donor's `chain_participation_state` to `BROKEN` when it was `COMMITTED`, or to `WITHDRAWN` otherwise (a donor already `COMPLETED` or `BROKEN` is untouched). Recording a donor deceased follows the same cascade; the only precondition is that the donor is not already `DECEASED`.

Completing the nephrectomy is the point of no return. A `CenterCoordinator` at the donor's `home_center_id` — verified by `ERR_CENTER_MISMATCH` — marks the donor's nephrectomy done, requiring that `surgery_state` is `SURGERY_SCHEDULED` (otherwise `ERR_INVALID_STATE`), that the donor's `medical_status` is `CLEARED` (otherwise `ERR_DONOR_NOT_CLEARED`), and that the donor's home center is not `SUSPENDED` (otherwise `ERR_CENTER_SUSPENDED`). The transition mints a `DonorProtectionPolicy` for the donor in `ACTIVE` state with standard caps (see §3.9), sets the donor's `chain_participation_state` to `COMPLETED`, advances the linked offer from `SCHEDULED` to `DONOR_SURGERY_DONE`, and makes any linked shipment eligible to depart — departure itself remains an explicit action. Completing the nephrectomy also moves every `NEPHRECTOMY_OR` slot at the donor's home center that is `RESERVED` for one of the donor's offers to `CONSUMED`, stamping `consumed_at_utc`. If the donor is `PAIRED` and the paired recipient is still in `POOL`, the recipient's state is unchanged by this transition. The donor's `priority_waitlist_status` moves from `NONE` to `ELIGIBLE` at this moment. Conversely, marking preop failed from either `PRE_SURGERY` or `SURGERY_SCHEDULED` moves the donor to `FAILED_PREOP` and emits a `ChainBreakEvent` with `trigger_kind` equal to `SURGERY_ABORTED` when the donor is embedded in an active (`LOCKED`, `SCHEDULED`, or `EXECUTING`) chain; otherwise it merely fails any pending offers referencing the donor per the hold rule.

Organ shipments are planned by a `LogisticsCoordinator` against an existing offer: the body names the `match_offer_id`, the `shipment_mode` (`COMMERCIAL_FLIGHT`, `CHARTER`, or `GROUND_COURIER`), the planned `scheduled_departure_utc` and `scheduled_arrival_utc`, and an optional `cold_ischemia_max_hours` override (defaulting to the `COLD_ISCHEMIA_MAX_HOURS` constant of 24, which may be tightened per chain). A shipment begins in `PLANNED` with `routing_sequence` equal to 0, and the system records the `origin_center_id` and `destination_center_id` from the linked offer. The shipment's `shipment_state` walks `PLANNED` → `DEPARTED` (optionally via `DELAYED` and `REROUTED`) and terminates at either `DELIVERED` or `CANCELLED`.

Departure requires the shipment to be `PLANNED`, the source offer to be in `DONOR_SURGERY_DONE` (otherwise `ERR_ORGAN_NOT_READY`), and the origin center to be `ACTIVE` (otherwise `ERR_CENTER_SUSPENDED`). Stamping `actual_departure_utc` moves the shipment to `DEPARTED`. A `DEPARTED` shipment may be flagged `DELAYED` with a `contingency_reason` of `WEATHER`, `MECHANICAL`, `ATC`, or `COURIER_BREAKDOWN` — any other reason is rejected with `ERR_INVALID_REQUEST`. From `DEPARTED` or `DELAYED`, the shipment may be rerouted, moving it to `REROUTED`, incrementing `routing_sequence` by one, and replacing `scheduled_arrival_utc` with the `new_scheduled_arrival_utc` supplied in the reroute call. Delivery is allowed from `DEPARTED`, `DELAYED`, or `REROUTED` — provided neither the origin nor the destination center is `SUSPENDED` (otherwise `ERR_CENTER_SUSPENDED`) — the server stamps `actual_arrival_utc` and computes `cold_ischemia_hours_actual` as the elapsed hours from the donor's `nephrectomy_completed_at_utc` timestamp (captured when `surgery_state` transitioned to `NEPHRECTOMY_DONE`) to actual arrival, rounded half-up to two decimal places. Every successful delivery also increments the origin center's `shipped_organ_count` by one and recomputes its `reputation_score_bps`, regardless of whether a cold-ischemia violation resulted. If `cold_ischemia_hours_actual` exceeds `cold_ischemia_max_hours`, the `cold_ischemia_violation` flag is set true: the destination center's `probed_cold_ischemia_violations` increments by one (and its `reputation_score_bps` is recomputed), the linked offer moves to `OFFER_FAILED` with `offer_failure_reason` equal to `COLD_ISCHEMIA`, a chain break cascade fires — a `ChainBreakEvent` with `trigger_kind` equal to `ORGAN_LOST_IN_TRANSIT` when the chain is in `SCHEDULED` or `EXECUTING` — and a subsequent transplant attempt on that offer is rejected with `ERR_COLD_ISCHEMIA_VIOLATION`. Otherwise the offer advances from `DONOR_SURGERY_DONE` to `ORGAN_SHIPPED`. Cancellation is permitted from `PLANNED`, `DEPARTED`, `DELAYED`, or `REROUTED`; if the organ has already departed, cancellation additionally emits a `ChainBreakEvent` with `trigger_kind` equal to `ORGAN_LOST_IN_TRANSIT` when the chain is in `SCHEDULED` or `EXECUTING`, and otherwise fails the linked offer with `offer_failure_reason` equal to `ORGAN_LOST_IN_TRANSIT`.

### 3.7. Transplant Completion and Outcome Reporting

Completing the recipient's transplant is the chain's productive endpoint. A `CenterCoordinator` marks the recipient transplanted only when five conditions hold — the acting coordinator's center must match the recipient's `home_center_id` (otherwise `ERR_CENTER_MISMATCH`), and the recipient's home center must not be `SUSPENDED` (otherwise `ERR_CENTER_SUSPENDED`): the recipient's `medical_status` is `LISTED` (otherwise `ERR_INVALID_STATE`); the recipient's `chain_participation_state` is `COMMITTED` (otherwise `ERR_RECIPIENT_NOT_COMMITTED`); an offer exists for this recipient in `ORGAN_SHIPPED` (otherwise `ERR_ORGAN_NOT_ARRIVED`); the linked shipment is `DELIVERED` (likewise `ERR_ORGAN_NOT_ARRIVED`); and the shipment's `cold_ischemia_violation` is false (otherwise `ERR_COLD_ISCHEMIA_VIOLATION`). On success, the offer moves to `TRANSPLANT_COMPLETED`, the recipient's `medical_status` becomes `TRANSPLANTED`, `transplant_completed_at_utc` is stamped, the recipient's `chain_participation_state` becomes `TRANSPLANTED`, the chain's `length_actual` increments by one, the chain's `completion_grade` is recomputed, the pair is released — `pair_state` becomes `RELEASED` with `dissolution_reason` equal to `RECIPIENT_TRANSPLANTED` — and every `TRANSPLANT_OR` slot reserved for the offer moves to `CONSUMED` with `consumed_at_utc` stamped.

Recipient medical transitions mirror the donor side. Placing a recipient on hold requires `LISTED` and fails any of the recipient's offers in `PENDING_CROSSMATCH`, `CROSSMATCH_PASSED`, or `CENTER_ACCEPTED` with `offer_failure_reason` equal to `DONOR_UNAVAILABLE` (the recipient-side application of the same reason). Release from hold returns the recipient to `LISTED`. Withdrawal from `LISTED` or `ON_HOLD` dissolves the pair with `dissolution_reason` equal to `MEDICAL_DECLINE`, as does recording the recipient deceased — this dissolution sweeps every pair for the recipient still in `REGISTERED`, `VERIFIED`, `IN_POOL`, or `IN_PROPOSED_CHAIN` — and both transitions also fail any of the recipient's offers in `PENDING_CROSSMATCH`, `CROSSMATCH_PASSED`, or `CENTER_ACCEPTED` with `offer_failure_reason` equal to `DONOR_UNAVAILABLE`; recipient `medical_status` terminates at `TRANSPLANTED`, `WITHDRAWN`, or `DECEASED`, and the recipient's `chain_participation_state` terminates at one of `TRANSPLANTED`, `ORPHANED`, or `WITHDRAWN` (a recipient already `TRANSPLANTED` keeps that participation state through withdrawal).

Outcomes are reported by a `CenterCoordinator` against a completed offer, supplying the `match_offer_id`, the `outcome_kind` — one of `SUCCESS`, `DELAYED_GRAFT_FUNCTION`, `PRIMARY_NON_FUNCTION`, `REJECTED_30D`, or `FAILED` — and the `followup_days` window (30, 90, 180, or 365). A new outcome begins in `REPORTED` with `reported_at_utc` stamped. A `RegistryAdmin` then attributes the outcome: `attributed_center_id` defaults to the recipient center of the offer but may be overridden by an `attributed_center_id` supplied in the attribution body, and if `outcome_kind` is `FAILED`, that center's `failed_outcome_count` increments by one and its `reputation_score_bps` is recomputed. Attribution moves the outcome from `REPORTED` to `ATTRIBUTED_TO_CENTER`. A `CenterCoordinator` of the attributed center — again verified by `ERR_CENTER_MISMATCH` — may appeal, moving the outcome to `APPEALED`. A `RegistryAdmin` resolves an appeal, moving the outcome to `FINAL`; the body may carry `new_attributed_center_id` to reattribute, and when a `FAILED` outcome's attribution changes, the previously attributed center's `failed_outcome_count` decrements, the newly attributed center's increments, and both centers' `reputation_score_bps` are recomputed. A `RegistryAdmin` may alternatively finalize directly from `ATTRIBUTED_TO_CENTER` without an appeal.

The reputation score is a basis-point value on the closed range 0 to 10000, recomputed whenever an outcome is attributed, an appeal reattributes a `FAILED` outcome, or a shipment's cold-ischemia violation lands. The score starts from `REPUTATION_BASE_BPS` of 10000, subtracts `REPUTATION_FAILURE_PENALTY_BPS` of 1500 per `FAILED` outcome attributed to the center up to a cumulative cap of `REPUTATION_FAILURE_CAP_BPS` of 4500, subtracts `REPUTATION_CIT_PENALTY_BPS` of 800 per probed cold-ischemia violation with no cap, adds `REPUTATION_SHIPMENT_BONUS_BPS` of 200 per successfully delivered shipment up to a cumulative cap of `REPUTATION_SHIPMENT_CAP_BPS` of 1000, and clamps the result to the closed range 0 to 10000. The `shipped_organ_count` used by that bonus counts shipments whose `origin_center_id` is the center — incremented on every delivery.

### 3.8. Chain Breaks, Orphaned Recipients, and Bridge Donors

A `ChainBreakEvent` is the audit record of a chain failure. It is created against a chain, naming the `broken_at_offer_id` whose donor became unavailable and a `trigger_kind` — one of `DONOR_MEDICAL_DECLINE`, `DONOR_WITHDRAWAL`, `DONOR_DECEASED`, `SURGERY_ABORTED`, or `ORGAN_LOST_IN_TRANSIT`. The event begins in `RECORDED` and immediately cascades: the broken offer itself moves to `OFFER_FAILED` with `offer_failure_reason` equal to `DONOR_UNAVAILABLE` (or `ORGAN_LOST_IN_TRANSIT` when that is the trigger). Then, walking the chain's offers in `position_index` ascending order, every offer whose position is strictly greater than the `broken_at_index` and whose state is not yet terminal is moved to `OFFER_FAILED` with `offer_failure_reason` equal to `CHAIN_BREAK_PROPAGATION`. Offers already at `TRANSPLANT_COMPLETED` are left untouched — a transplant that has already happened stands. The chain itself moves to `BROKEN`, its `broken_at_index` is stamped with the broken offer's `position_index`, and `completion_grade` becomes `BROKEN_PARTIAL` (or `FULL` in the unreachable case of §3.5). Each downstream recipient whose offer failed becomes an orphan: their `chain_participation_state` moves from `COMMITTED` to `ORPHANED`, and if their paired donor has already completed nephrectomy (donated on the orphan's behalf before the break), the orphan's `priority_boost_active` flag is set true. The event records `recipients_already_transplanted` — the count of the chain's offers already in `TRANSPLANT_COMPLETED` before the event — and `downstream_recipients_orphaned`. The cascade additionally releases every `RESERVED` slot reserved for the chain (clearing its reservation fields) and dissolves every pair still `LOCKED` into the chain with `dissolution_reason` equal to `CHAIN_BROKEN` (a `LOCKED` pair already carrying a different `dissolution_reason` is left untouched). Finally, if the broken donor's paired recipient was already transplanted before the break, the system mints a new bridge donor with `donor_kind` equal to `BRIDGE` and `home_center_id` equal to the broken donor's home center — inheriting the broken donor's blood type, HLA loci, KDRI score, and age — recording it as the event's `bridge_donor_id`; this donor holds the bridge credit that will start a future chain.

A cascaded event remains in `CASCADED` until a `MatchOperator` reconstructs it. Reconstruction requires the event to be in `CASCADED` (otherwise `ERR_INVALID_STATE`) and requires that a new chain run has been executed with the orphaned recipients in its candidate pool — concretely, that some chain run in `EXECUTED` or `PUBLISHED` exists whose `created_at` is at or after the event's `created_at` — otherwise the call is rejected with `ERR_RECONSTRUCTION_NOT_VIABLE`. Successful reconstruction moves the event to `RECONSTRUCTED`, after which the orphaned recipients may enter newly constructed chains.

### 3.9. Donor Protection Policy and Claims Adjudication

The moment a donor's nephrectomy completes, the system mints a `DonorProtectionPolicy` for that donor in `policy_state` `ACTIVE`. The policy's caps come from system constants: `covered_complication_max_cents` is the `COMPLICATION_COVER_CENTS` constant of 25000000 cents (250,000 dollars), and `covered_lost_wages_max_cents` is the `LOST_WAGES_COVER_CENTS` constant of 600000 cents (6,000 dollars). The policy tracks three paid buckets — `complications_paid_cents`, `lost_wages_paid_cents`, and `travel_reimbursed_cents` — each incremented as approved claims land in the corresponding kind. A `priority_kidney_claim_available` flag remains true while the policy is `ACTIVE` and the donor has not yet claimed a priority kidney slot.

A `CenterCoordinator` files a `DonorProtectionClaim` on behalf of the donor's policy by supplying the `claim_kind` — `COMPLICATION`, `LOST_WAGES`, `TRAVEL`, or `PRIORITY_KIDNEY` — and, for monetary kinds, a `requested_amount_cents` that must be strictly greater than zero. Filing requires the donor to have an active protection policy; if the donor's `protection_policy_id` is still null (pre-nephrectomy) or the policy is not active, the submission is rejected with `ERR_NO_PROTECTION_POLICY`. The claim begins in `SUBMITTED` with `submitted_at_utc` stamped, and the submitter's identity is captured from the request headers as `submitter_user_id` for segregation-of-duties enforcement.

A `RegistryAdmin` moves a submitted claim to `UNDER_REVIEW`, recording themselves as `adjudicator_user_id`. From `UNDER_REVIEW`, three resolutions are available, all guarded by segregation of duties — the adjudicator must differ from the recorded submitter, otherwise `ERR_SEGREGATION_OF_DUTIES`. **Approve** sets `approved_amount_cents` equal to `requested_amount_cents` and debits the matching policy bucket; for non-`PRIORITY_KIDNEY` claims the requested amount must fit within the bucket's remaining headroom — that is, the bucket cap minus the amount already paid from that bucket — otherwise the approval is rejected with `ERR_CLAIM_EXCEEDS_CAP`. **Partial approve** takes `approved_amount_cents` from the request body, which must be strictly greater than zero and strictly less than `requested_amount_cents` (otherwise `ERR_INVALID_REQUEST`); the policy bucket is debited by the approved amount. **Deny** moves the claim to `DENIED` and records the `denial_reason`. The headroom waterfall is exact: when the requested amount fits, the claim may be approved in full; when the remaining headroom is strictly between zero and the requested amount, the correct outcome is a partial approval at the headroom amount — the system does not auto-approve a full request that does not fit (the full approve is rejected with `ERR_CLAIM_EXCEEDS_CAP`, and the partial-approve endpoint enforces only the `0 < approved < requested` shape, so the caller must supply the headroom amount); when headroom is zero, the claim must be denied under `ERR_CLAIM_EXCEEDS_CAP`. Approving a `PRIORITY_KIDNEY` claim consumes the policy's one slot — `priority_kidney_claim_available` flips to false and `approved_amount_cents` is zero; approving when the slot is already consumed is rejected with `ERR_CLAIM_EXCEEDS_CAP`. The travel bucket has no aggregate cap within the policy, but each itinerary's auto-minted travel claim is approved at exactly its `estimated_cost_cents`. The priority-kidney bucket is boolean-like: one slot is available while `priority_kidney_claim_available` is true, and it is not monetary.

Payment is the final step: a `RegistryAdmin` pays an `APPROVED` or `PARTIALLY_APPROVED` claim, moving it to `PAID`. Bucket updates happen at approval time; payment itself does not double-count. `PAID` and `DENIED` are terminal. A claim that has been adjudicated carries `resolved_at_utc`, stamped when it reaches `APPROVED`, `PARTIALLY_APPROVED`, or `DENIED`. A policy whose buckets are drained transitions through `LAPSED` to `EXHAUSTED` as its coverage is consumed.

The donor's `priority_waitlist_status` begins at `NONE`, becomes `ELIGIBLE` once the donor has donated, and moves to `ENROLLED` when the donor later registers as a recipient (matched by `external_ref`, per §3.2) — at which point their `priority_boost_active` flag drives the priority bonus in match scoring (§3.4). The donor's `complications_recorded` counter tracks claims of kind `COMPLICATION`, incrementing by one each time a complication claim is approved or partially approved.

### 3.10. Donor Travel Logistics and Reimbursement

A `LogisticsCoordinator` drafts a `TravelItinerary` for a donor by supplying the `donor_id`, the three-letter IATA `origin_airport_code` and `destination_airport_code`, the planned `depart_utc` and `arrive_utc` (arrival strictly after departure), the `segment_miles` great-circle distance, and the `lodging_nights` count (0 through 7). The itinerary begins in `DRAFT`; its `itinerary_state` moves to `CONFIRMED` on confirmation and terminates at either `REIMBURSED` or `CANCELLED`; it carries an `estimated_cost_cents` of null and a `cancelled_reason` of `NONE` until confirmation or cancellation respectively. Confirmation moves it to `CONFIRMED` and computes `estimated_cost_cents` — the capped reimbursement estimate — using the travel reimbursement calculation; the donor's `traveled_distance_miles` is then recomputed as the sum of `segment_miles` over the donor's confirmed itineraries only.

The reimbursement estimate has two component formulas. For a non-altruistic donor, the flight component is `FLIGHT_CENTS_PER_MILE` of 50 cents per mile multiplied by `segment_miles`, rounded half-up to the nearest cent, and then capped at `FLIGHT_CAP_CENTS` of 80000. The lodging component is `lodging_nights` multiplied by `LODGING_PER_NIGHT_CENTS` of 15000, capped at `LODGING_CAP_CENTS` of 60000. The estimate is the flight component plus the lodging component plus a flat booking fee `FLAT_FEE_CENTS` of 2500. The flight component is rounded (then capped) before summing; the lodging component and flat fee are already integral — rounding is applied per component first, then components are summed, then the flat fee is added, and that order is mandatory. For an `ALTRUISTIC` donor, the structure is identical but with elevated caps and a mileage multiplier: the flight component multiplies the per-mile rate by `ALTRUISTIC_MILEAGE_MULTIPLIER` of 1.10 before the per-component rounding and caps at `FLIGHT_CAP_CENTS_ALTRUISTIC` of 95000, while the lodging cap is `LODGING_CAP_CENTS_ALTRUISTIC` of 75000; the per-night rate, the per-mile base rate, and the flat fee are unchanged. For identical inputs, the altruistic variant yields a strictly greater estimate whenever the multiplier or the elevated caps bind, and an equal estimate otherwise.

Cancellation of a confirmed itinerary is permitted only while the logical clock is strictly before `depart_utc` — at or after departure the attempt is rejected with `ERR_FLIGHT_ALREADY_DEPARTED` — and records a `cancelled_reason` of `NONE`, `CHAIN_BROKEN`, `DONOR_UNAVAILABLE`, or `SCHEDULE_MOVED`. Cancelling recomputes the donor's `traveled_distance_miles` to exclude the cancelled segment. Reimbursement is the mirror-image window: a `RegistryAdmin` reimburses a confirmed itinerary only once the logical clock has reached `arrive_utc` — an attempt before arrival is rejected with `ERR_FLIGHT_ALREADY_DEPARTED` as well — and only while the donor has an active protection policy, otherwise `ERR_NO_PROTECTION_POLICY`. Reimbursement moves the itinerary to `REIMBURSED`, auto-mints a `DonorProtectionClaim` with `claim_kind` equal to `TRAVEL`, `requested_amount_cents` equal to the itinerary's `estimated_cost_cents`, and `claim_state` equal to `APPROVED` — with `submitted_at_utc` and `resolved_at_utc` stamped at minting and both `submitter_user_id` and `adjudicator_user_id` null — and credits the policy's `travel_reimbursed_cents` by the same amount.
