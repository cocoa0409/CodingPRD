# Elite Field Purse Admin API — Product Requirements Document

## 1. Introduction

A major marathon is two races. One is run on the road on race morning; the other runs for a year beforehand, in the correspondence between an organizing committee and a few dozen licensed representation agents, over appearance fees, business-class seats, hotel nights and airport pickups. This document specifies the back-office system that governs that second race — the Elite Field & Prize Purse Administration API — from the moment an edition's qualifying standards and purse structure are drafted to the moment the last withholding remittance is booked and the purse is closed.

The committee's operating problem is that money is promised long before it is owed, and owed long before it is verifiable. An appearance guarantee is committed the instant an agent accepts terms, but the prize a runner earns cannot be known until times are verified, results are certified, ties are resolved, course-record claims are ratified or rejected by the sanctioning body, and anti-doping outcomes are returned by a laboratory the committee does not control. Meanwhile a single adverse analytical finding, arriving weeks after payment, has to unwind a chain of consequences that reaches from a race result back through a prize award, a course record, an invitation and the edition's own ledgers. The system therefore treats every monetary aggregate as a derived quantity that must reconcile exactly after every forward action and after every compensating action, and it treats the edition's posture as a gate that every child operation must pass.

Two further constraints shape the design. Negotiation is strictly alternating and adversarial: the committee side and the athlete side take turns, may never act on each other's behalf, and each new round supersedes the terms of the last — which makes the negotiation record the one place where a client working from stale data can silently destroy a term it never saw. And prize disbursement is subject to segregation of duties: the officer who approves an award may not be the officer who pays it. The specification below is written so that an engineer can implement all of this without needing to ask which of two readings was intended.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level behaviour that applies uniformly across the API: authentication, envelope shape, pagination, the logical clock, common resource properties, ledger invariants, concurrency protection and the fixed precedence in which validations are evaluated.

### 2.1. User and Role-Based Access Control

Every request — reads included — must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which they are acting. Six roles exist and their spelling is exact: `ElitesDirector`, `AthleteAgent`, `TechnicalOfficial`, `AntiDopingLiaison`, `SanctioningBody`, and `FinanceOfficer`. If either header is absent, or if `X-User-Role` is not one of those six strings, the request fails with `ERR_UNAUTHENTICATED`. If the headers are well formed but the declared role is not among the roles authorized for the endpoint being called (see the table in §4), the request fails with `ERR_ROLE_NOT_PERMITTED`.

The `ElitesDirector` is the organizing committee's elite field director: it configures editions, registers athletes and agents, recruits, negotiates from the committee side, runs the elite services (bibs, fluid tables, pacers) and triggers the operational sweep. A `TechnicalOfficial` is the chief referee and technical delegate: it verifies claimed qualifying times, opens the race, enters and certifies results, disqualifies for assistance or course violations, and lodges record ratification packages. The `AntiDopingLiaison` is the committee's anti-doping coordinator, scheduling tests inside declared athlete availability windows and collecting samples. The `SanctioningBody` is an external officer who returns laboratory outcomes and ratifies or rejects course-record claims. The `FinanceOfficer` maintains withholding profiles, generates the award set, approves and pays prizes, and settles the purse. The `AthleteAgent` is a licensed representation agent acting for the athlete: it submits qualifying performances and negotiates or responds from the athlete side.

Only one of the six roles is tied to a persisted entity. When `X-User-Role` is `AthleteAgent`, `X-User-ID` is the `id` of the acting `RepAgent`; ownership checks on any resource that references a `RepAgent` compare the resource's foreign-key field to `X-User-ID` — concretely, an invitation-scoped write by an `AthleteAgent` requires `X-User-ID` to equal that invitation's `agent_id`, and a mismatch is rejected with `ERR_NOT_INVITATION_AGENT`. The identifier returned when an agent is registered is therefore the value that agent authenticates with.

When `X-User-Role` is `ElitesDirector`, `TechnicalOfficial`, `AntiDopingLiaison`, `SanctioningBody`, or `FinanceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — as `negotiated_by_user_id` on an invitation when an `ElitesDirector` sends the first offer, and as `approved_by_user_id` and `paid_by_user_id` on a prize award when a `FinanceOfficer` approves or pays it — but it never compares such a value to any entity's `id`. Those recorded operator identifiers are compared only to each other, which is how segregation of duties is enforced on payment.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.4 rather than from real time, so it does not advance between requests unless an operator moves the clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- The status codes in §5 pair with the error identifiers on the endpoints of §4. A request that reaches no endpoint at all still answers in this envelope with `error_id` `ERR_INVALID_REQUEST`, but carries the transport's own status — 404 for an unrouted path and 405 for a method the path does not offer — rather than the 400 the catalogue lists.

### 2.3. Pagination

List-returning endpoints are paginated through two query parameters. `limit` caps the number of items returned; it defaults to 10, may not be smaller than 1 and may not be larger than 100. `offset` is the number of items to skip; it defaults to 0 and may not be negative. A `limit` outside the range of 1 through 100, a non-integer `limit` or `offset`, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST`. The same code rejects any enumerated filter query parameter — `status`, `category`, `gender`, `division`, `test_type`, `certification_status`, `record_claim_status`, `side`, `verification_status` — whose supplied value is not a declared member of that enum. Identifier-valued filters are matched literally and are never existence-checked: a filter naming an identifier that no row carries yields an empty page with `total_count` zero rather than a 404.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. The single documented exception is the negotiation history of an invitation, which is returned in ascending `round_number` — the same ordering, expressed in the sequence number the reader cares about.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the number of matching rows before the window is applied and `has_more` indicates whether rows remain beyond it.

### 2.4. The Logical Race Clock

Nothing in this system reads real wall-clock time. The server maintains a logical clock that begins at the fixed instant `2026-08-01T00:00:00Z` and changes only when an operator moves it, by supplying a target instant as `to_iso8601`. Every deadline comparison, availability-window comparison and race-day comparison in this document is evaluated against that logical clock, and every timestamp the server stamps on a resource — an offer's `offer_sent_at`, a recomputed `response_deadline_at`, a sample's `collected_at`, an award's `paid_at` — is the logical clock's current value. Moving the clock mutates no entity; it merely changes what subsequent requests observe.

Because deadlines are logical, they are also durable: an offer whose deadline has passed does not become `EXPIRED` on its own. It stays where it is until either the operational sweep visits it or the field is locked, at which point the expiry is recorded explicitly. A request that arrives after a deadline is rejected on the strength of the comparison, not on the strength of the invitation's stored status.

### 2.5. Common Resource Properties

Every persisted resource carries a server-minted `id`, formatted as a UUID with no type prefix, and a `created_at` timestamp expressed as an ISO 8601 UTC instant with three fractional digits (for example `2026-08-01T00:00:00.000Z`). Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, a system-managed integer that starts at 1 on creation and increases by one on every mutation — including mutations that only change derived fields such as an edition's committed or allocated cents.

`RaceEdition`, `PurseLine`, `DivisionStandard`, `Athlete`, `RepAgent`, `PerformanceRecord`, `Invitation`, `PacerAssignment`, `FluidStationSlot`, `DopingTest`, `RaceResult` and `PrizeAward` all carry the full set: `id`, `created_at`, `updated_at` and `version`. A `NegotiationRound` is the one exception. Rounds are append-only historical facts and are never edited, so a round carries only `id` and `created_at`; it has no `updated_at` field and no `version` field at all, and neither key appears in its representation.

### 2.6. Edition Posture as the Master Gate

Each `RaceEdition` moves through a linear posture pipeline whose values are `PLANNING`, `FIELD_OPEN`, `FIELD_LOCKED`, `RACED`, `RESULTS_CERTIFIED` and `PURSE_SETTLED`. A new edition begins in `PLANNING`, `PURSE_SETTLED` is terminal, and the `status` field is never writable by a client — it changes only through the edition transitions described in §3. Almost every child operation is gated on the posture of the edition that owns it, whether that edition is named directly in the request or reached transitively through an invitation or a result. When the posture does not permit the operation, the rejection is `ERR_EDITION_STATE_INVALID`.

The gating map is fixed. Opening the field requires `PLANNING`. Creating purse lines and division standards requires `PLANNING`. Creating invitations, sending offers, appending negotiation rounds and responding to terms all require `FIELD_OPEN`. Assigning a bib, reserving fluid-station positions, registering pacing arrangements and withdrawing an invitation are permitted while the edition is in either `FIELD_OPEN` or `FIELD_LOCKED`. Entering a race result and certifying one require `RACED`. Disqualifying a result is permitted while the edition is `RACED` or `RESULTS_CERTIFIED`. Computing the award set, approving an award and paying an award all require `RESULTS_CERTIFIED`. The operations the map does not name individually — scheduling a doping test, collecting a sample, adjudicating a laboratory outcome, lodging a record ratification package, deciding a record claim, and the operational sweep itself — are admitted from every posture except the terminal one, so for those the gate reduces to the settled-edition rule alone. Once the edition reaches `PURSE_SETTLED`, every mutation anywhere in its subtree is rejected.

### 2.7. Stale-Version Protection on Superseding Writes

Two operations in this system do not add information but replace it, and both are protected by optimistic concurrency control against the parent entity's `version`. No other endpoint accepts or requires a version field.

Appending a negotiation round to an invitation — the `POST /invitations/{id}/negotiation-rounds` operation of §4 — requires `expected_invitation_version` as a non-optional field of the request, carrying the client's last observed `version` of that `Invitation`. A round legitimately supersedes the previous package — `current_appearance_fee_cents`, `current_air_class`, `current_hotel_nights` and `current_ground_transport` are all replaced — so a writer holding a version older than the invitation's current one would overwrite terms it never read. When `expected_invitation_version` does not equal the invitation's current `version`, the append is rejected with `ERR_STALE_INVITATION_VERSION` and HTTP 412.

Recomputing an edition's award set — the `POST /race-editions/{id}/compute-awards` operation of §4 — requires `expected_race_edition_version` as a non-optional field of the request, carrying the client's last observed `version` of that `RaceEdition`. A recompute supersedes the whole award set — awards still in `COMPUTED` are voided and regenerated from the current result data — so a writer holding an older version would silently discard awards generated from newer results. When `expected_race_edition_version` does not equal the edition's current `version`, the recompute is rejected with `ERR_STALE_EDITION_VERSION` and HTTP 412.

### 2.8. Money, Basis Points and Rounding Discipline

All monetary quantities in this system are integer cents. There is no decimal money anywhere in the API, and no monetary value is ever returned as a fractional number. Rates are integers in basis points, so 3,000 basis points means thirty percent, and a rate is applied by multiplying an amount in cents by the rate and dividing by 10,000.

Three different rounding disciplines appear, and each is pinned to its use. Withholding rate multiplication rounds half up to whole cents. Prize pooling for a tied place divides after pooling and takes the floor of each share, distributing the leftover cents one at a time (see §3.8). The wheelchair bonus factor takes the floor after multiplication and never rounds half up. Where a formula nests a minimum or maximum inside an arithmetic expression, the nesting order stated in §3 is normative — for example hotel nights are capped before the nightly rate is multiplied, never after.

Distances behave similarly: pacing and fluid-station kilometre marks are carried to one decimal place, and table positions and bib numbers are integers. Times are always whole seconds, which means a tie in a race result is exact integer equality rather than a tolerance comparison.

### 2.9. The Appearance Budget and Prize Purse Ledgers

An edition owns two conserved pools of cents, and six of its fields are read-only projections that the server recomputes rather than accepts. `appearance_committed_cents` is the sum of `guaranteed_commitment_cents` over the invitations of that edition whose `status` is `ACCEPTED`, and `appearance_uncommitted_cents` is `appearance_budget_cents` less `appearance_committed_cents`. `purse_allocated_cents` is the sum of `gross_amount_cents` over the prize awards of that edition whose `status` is any of `COMPUTED`, `APPROVED`, `PAID` or `CLAWBACK_PENDING`, and `purse_unallocated_cents` is `total_purse_cents` less `purse_allocated_cents`. `bonus_pool_consumed_cents` is the sum of `gross_amount_cents` over that same set of awards restricted to those whose `category` is `TIME_BONUS` or `RECORD_BONUS`. `expired_offer_count` is a system counter, starting at zero, of invitations the server has auto-expired.

Two invariants must hold exactly after every forward action and after every compensating action, down to the last remainder cent distributed to break a tie. First, `appearance_budget_cents` equals `appearance_uncommitted_cents` plus the summed `guaranteed_commitment_cents` of the edition's `ACCEPTED` invitations. Second, `total_purse_cents` equals `purse_unallocated_cents` plus the summed `gross_amount_cents` of the edition's awards in `COMPUTED`, `APPROVED`, `PAID` or `CLAWBACK_PENDING`. The status filters are what make the invariants work: invitations in `WITHDRAWN`, `BREACHED`, `EXPIRED` or `DECLINED` contribute nothing to the appearance ledger, awards in `VOID` contribute nothing to the purse ledger, and awards in `CLAWBACK_PENDING` still do contribute, because the cash has already left the building and recovering it is a collections problem rather than an accounting one.

Every transition whose effects touch `appearance_committed_cents`, `purse_allocated_cents` or `bonus_pool_consumed_cents` recomputes the affected projections in the same operation, and the operational sweep recomputes all of them unconditionally as its final step.

### 2.10. Cascades, Path Resolution and Existence Checks

Several operations in this system mutate more than one entity, and the secondary effects are as normative as the primary one. An adverse laboratory outcome disqualifies results; a disqualification nulls places, rejects record claims, voids or flags awards, recomputes the owning edition's ledgers and can breach an invitation, which in turn releases a bib and a set of fluid-station reservations. Each entity the cascade touches has its `updated_at` refreshed and its `version` incremented, including the edition whose derived ledger fields moved. Cascades run to completion inside the request that triggered them; consistency is immediate and there is no deferred reconciliation.

When a request names identifiers, they are resolved in a fixed order: path identifiers first, left to right, and then the foreign-key fields in the request body in the order they appear in that endpoint's input list. The first identifier that does not resolve determines the error, and each entity type has its own code — `ERR_RACE_EDITION_NOT_FOUND`, `ERR_ATHLETE_NOT_FOUND`, `ERR_REP_AGENT_NOT_FOUND`, `ERR_PERFORMANCE_RECORD_NOT_FOUND`, `ERR_INVITATION_NOT_FOUND`, `ERR_DOPING_TEST_NOT_FOUND`, `ERR_RACE_RESULT_NOT_FOUND` and `ERR_PRIZE_AWARD_NOT_FOUND`, all HTTP 404. A request for the purse lines of a non-existent edition therefore fails on the edition before anything else is considered.

Because the entity graph is flat — peers linked by foreign keys carried in request bodies rather than nested creation paths — reverse navigation is provided by sub-resource listings hanging off the three hub entities and by filtered top-level lists. The purse lines, division standards and pacing arrangements of an edition are listed under that edition; the performance records of an athlete are listed under that athlete; the negotiation rounds and fluid-station reservations of an invitation are listed under that invitation. Invitations, doping tests, race results and prize awards each have a filtered top-level list that accepts every foreign key the entity carries, which is how a client reaches, say, all awards of one result.

### 2.11. Validation Precedence

When several rules could reject the same request, exactly one of them must win, and the order below is the order of evaluation. It is a strict precedence, not a suggestion: an earlier rule always surfaces in place of a later one it would have masked.

1. **Authentication.** Both headers present and `X-User-Role` one of the six declared roles, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Endpoint role permission.** The declared role appears in the called endpoint's authorized-role list in §4, else `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Existence.** Every referenced identifier resolves, path identifiers left to right first and then body foreign keys in input order, else the matching 404 code from §2.10. Applies to every endpoint.
4. **Request-body schema.** Required fields present; enum values are declared members; integers inside their declared ranges; `net_seconds` no greater than `gun_seconds`; `window_start_at` strictly earlier than `window_end_at`; `start_km` strictly less than `end_km`; `bib_range_end` not less than `bib_range_start`; the last table position occupied (`table_position` plus `bottle_count` minus one) not beyond 40; `station_km` one of the allowed station marks; a coherent combination of `category`, `division`, `place` and `threshold_seconds` on a purse line; a verification `decision` of `VERIFIED` accompanied by `official_seconds` and a `decision` of `REJECTED` accompanied by `rejection_reason`; `limit` within 1 through 100 and `offset` not negative. Otherwise `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
5. **Agent ownership.** When the acting role is `AthleteAgent` on an invitation-scoped write, `X-User-ID` must equal that invitation's `agent_id`, else `ERR_NOT_INVITATION_AGENT` (403). This guards exactly two operations: appending a negotiation round, and responding to terms.
6. **Edition posture.** The owning edition's `status` permits the operation, per the map in §2.6, else `ERR_EDITION_STATE_INVALID` (409). Applies to every mutating endpoint that references an edition directly or transitively.
7. **Configuration completeness.** Opening the field requires at least one `DivisionStandard` and at least one `OVERALL` purse line for that edition, else `ERR_EDITION_CONFIG_INCOMPLETE` (422). This guards the open-field operation only.
8. **Target entity state.** The target entity is in a state that permits the requested transition, else one of `ERR_INVALID_INVITATION_STATE`, `ERR_INVALID_AWARD_STATE`, `ERR_INVALID_RECORD_CLAIM_STATE`, `ERR_INVALID_DOPING_TEST_STATE`, `ERR_INVALID_PERFORMANCE_STATE`, `ERR_RESULT_NOT_CERTIFIED`, `ERR_RESULTS_NOT_ALL_ADJUDICATED` or `ERR_AWARDS_NOT_ALL_SETTLED` (409). Applies to every state-transition endpoint.
9. **Turn-taking.** Which side may act depends on the invitation's current state: from `OFFERED` only an `AthleteAgent` may act, from `COUNTERED` only an `ElitesDirector` may act. The rule governs both responding to terms and appending a negotiation round, and a violation is `ERR_ROLE_NOT_PERMITTED_FROM_STATE` (403).
10. **Stale version.** The supplied `expected_invitation_version` or `expected_race_edition_version` equals the parent's current `version`, else `ERR_STALE_INVITATION_VERSION` or `ERR_STALE_EDITION_VERSION` (412). This guards exactly two operations: appending a negotiation round, and recomputing the award set.
11. **Segregation of duties.** The `FinanceOfficer` paying an award must not be the operator recorded in `approved_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES` (403). This guards the pay operation only.
12. **Anti-doping and representation gates.** Bib assignment requires the athlete to be doping-compliant, else `ERR_ATHLETE_NOT_DOPING_COMPLIANT`; award approval requires an in-competition test cleared for that athlete in that edition, else `ERR_IN_COMPETITION_TEST_NOT_CLEARED`; a `SUSPENDED` representation agent may neither receive an offer nor negotiate nor respond, else `ERR_AGENT_SUSPENDED`. All three are 422. Between them these gates guard five operations: bib assignment, award approval, sending an offer, appending a negotiation round, and responding to terms.
13. **Clock-relative windows.** A negotiation round or a response must arrive at or before the invitation's `response_deadline_at`, else `ERR_OFFER_DEADLINE_PASSED`; a sample collection must fall inside the declared availability window, else `ERR_COLLECTION_WINDOW_INVALID`; marking the edition raced requires the logical clock to have reached the edition's `race_date` at midnight UTC, else `ERR_RACE_DATE_NOT_REACHED`. All three are 422, and together they guard four operations: appending a negotiation round, responding to terms, collecting a sample, and marking the edition raced.
14. **Occupancy, capacity and uniqueness.** The negotiation round cap, the qualifying standard's existence and satisfaction, bib pool availability and single-assignment, the fluid-table buffer, pacing overlap and the pacing distance ceiling, testing-window overlap and the testing frequency cap, one result per invitation, and the uniqueness keys on purse lines, division standards, agent licence codes and sample codes. The codes are `ERR_NEGOTIATION_ROUNDS_EXHAUSTED`, `ERR_QUALIFYING_STANDARD_MISSING`, `ERR_QUALIFYING_STANDARD_NOT_MET`, `ERR_BIB_POOL_EXHAUSTED`, `ERR_BIB_ALREADY_ASSIGNED`, `ERR_FLUID_SLOT_CONFLICT`, `ERR_PACING_RANGE_CONFLICT`, `ERR_PACING_BEYOND_LIMIT`, `ERR_TESTING_WINDOW_OVERLAP`, `ERR_TESTING_FREQUENCY_EXCEEDED`, `ERR_DUPLICATE_RESULT` and `ERR_CONFIG_DUPLICATE`. These are all 409 except `ERR_QUALIFYING_STANDARD_MISSING`, `ERR_QUALIFYING_STANDARD_NOT_MET`, `ERR_PACING_BEYOND_LIMIT` and `ERR_TESTING_FREQUENCY_EXCEEDED`, which are 422. The operations guarded are appending a negotiation round, sending an offer, assigning a bib, reserving a fluid-station slot, registering a pacing arrangement, scheduling a doping test, entering a race result, creating a purse line, creating a division standard, and registering a representation agent.
15. **Cross-entity coherence.** The pinned performance belongs to the invited athlete and to the invitation's division, else `ERR_PERFORMANCE_DIVISION_MISMATCH`; a record package may only be lodged for a non-`SUB_ELITE` result whose claim status is `CLAIMED` or `REJECTED`, else `ERR_RECORD_CLAIM_NOT_ELIGIBLE`; the invitation named on a result must belong to the same edition, be `ACCEPTED` and already hold a `bib_number`, else `ERR_INVITATION_EDITION_MISMATCH`. All three are 422, and they guard sending an offer, lodging a record package, and entering a race result.
16. **Money ceilings, checked last.** On acceptance, `appearance_uncommitted_cents` must be at least the invitation's guaranteed valuation, else `ERR_APPEARANCE_BUDGET_EXCEEDED`; on locking the field, the summed full-exposure valuation of `ACCEPTED` invitations must not exceed `appearance_budget_cents` plus `bonus_pool_cap_cents`, else `ERR_FIELD_LOCK_EXPOSURE_EXCEEDED`. Both are 422, and they guard responding to terms and locking the field.

Two interactions of this ordering deserve emphasis. Because turn-taking sits at priority 9 and stale-version checking at priority 10, an agent attempting to counter a `COUNTERED` invitation is refused for acting out of turn even if the version it holds is also stale. And because record-claim eligibility sits at priority 15 while generic target-state checking sits at priority 8, a record package lodged against a result whose claim status is `NONE` — meaning no claim was ever raised — surfaces as `ERR_RECORD_CLAIM_NOT_ELIGIBLE` and is deliberately not shadowed by the priority-8 state error, whereas a package lodged against a claim already `SUBMITTED` or already `RATIFIED` does fail earlier, at priority 8, with `ERR_INVALID_RECORD_CLAIM_STATE`.

## 3. Business Logic & Workflows

### 3.1. Standing Up an Edition

An `ElitesDirector` opens the year by creating a marathon edition, supplying a `name` for the edition, the host `city`, and the `race_date` as an ISO 8601 calendar date in year-month-day form. Race day is a date rather than an instant, and every window measured against it — the race-day gate, the qualifying lookback — is measured from midnight UTC at the start of that date. Three money figures are supplied at the same time: `appearance_budget_cents`, the total guaranteed pool for appearance fees, air travel and hotel; `total_purse_cents`, the total prize purse covering both place prizes and bonuses; and `bonus_pool_cap_cents`, the ceiling on aggregate time and record bonuses. None of the three may be negative. Four course records may also be supplied at creation — `course_record_male_seconds`, `course_record_female_seconds`, `course_record_wheelchair_male_seconds` and `course_record_wheelchair_female_seconds` — each a whole number of seconds, each defaulting to null, and a null meaning simply that no ratified record is on file for that key.

Four policy dials round out the edition, and each has a default that applies when the field is omitted. `offer_response_days` is how long an offer or a counter stays open before it goes stale; it defaults to 14 and must lie between 1 and 60 inclusive. `max_negotiation_rounds` is the per-side round allowance; it defaults to 3 and must lie between 1 and 6 inclusive, which means an invitation's total round tally may never reach twice that figure. `masters_min_age` is the minimum age in completed years, as at race day, that makes a runner a master; it defaults to 40 and must lie between 35 and 60 inclusive. A freshly created edition is in `PLANNING`, with `appearance_committed_cents` and `purse_allocated_cents` both at zero, `expired_offer_count` at zero, and `version` at 1.

While the edition is in `PLANNING` — and only then — the director builds out the purse structure. Each **purse line** names the edition it belongs to through `race_edition_id`, a `category` drawn from `OVERALL`, `DIVISION`, `MASTERS`, `TIME_BONUS` and `RECORD_BONUS`, a `gender` of either `MALE` or `FEMALE`, and an `amount_cents` that must be strictly greater than zero. Which of the remaining fields is meaningful depends on the category, and getting the combination wrong is a malformed request. A `division` of `ELITE`, `SUB_ELITE` or `WHEELCHAIR` is required on `DIVISION`, `TIME_BONUS` and `RECORD_BONUS` lines and must be null on `OVERALL` and `MASTERS` lines. A `place` between 1 and 20 inclusive is required on `OVERALL`, `DIVISION` and `MASTERS` lines and must be null on `TIME_BONUS` and `RECORD_BONUS` lines. A `threshold_seconds`, the qualifying time in whole seconds that a bonus tier pays out at and itself strictly greater than zero, is required on `TIME_BONUS` lines and must be null on every other category. No two purse lines of an edition may share the same combination of category, division, gender, place and threshold; a duplicate is refused with `ERR_CONFIG_DUPLICATE`.

Alongside the purse, the director configures one **division standard** per division and gender. A standard names its edition through `race_edition_id`, its `division` and its `gender`, and sets `max_qualifying_seconds`, the slowest verified time that still qualifies, as an inclusive upper bound greater than zero. `window_months` bounds how far back a qualifying performance may have been run; it defaults to 24 and must lie between 1 and 60 inclusive. `requires_chip_timing` defaults to true and, when true, means the qualifying performance must have been chip-timed. Each standard also owns that division's bib pool, from `bib_range_start` — an integer between 1 and 9999 inclusive — through `bib_range_end`, which must be at least 1 and may not be smaller than the start but carries no upper bound of its own. Only one standard may exist per edition, division and gender combination; a second is refused with `ERR_CONFIG_DUPLICATE`.

Opening the field is the `ElitesDirector`'s first posture change, moving the edition `PLANNING → FIELD_OPEN`, and it is admitted only when the edition already has at least one division standard and at least one purse line in the `OVERALL` category; otherwise it is refused with `ERR_EDITION_CONFIG_INCOMPLETE`. From that point the recruitment surface — creating invitations, sending offers, appending rounds, responding — becomes available, and conversely no further purse line or division standard may be created, because configuration is frozen for reading once the edition leaves `PLANNING`. Committee staff and finance may read an edition's purse structure at any time, filtering by `category` and by `gender`, and the qualifying standards and bib pools may be read filtered by `division` and `gender` — the latter listing is also open to agents, who need to know what time their runner has to have run.

### 3.2. Athletes, Agents and the Verification of Claimed Times

Registering an **athlete** requires a `full_name`, a `country_code` as an ISO 3166-1 alpha-3 nationality code, a `gender` of `MALE` or `FEMALE`, and a `birth_date` as an ISO 8601 calendar date, which is the sole input to the masters age determination. Country codes are stored exactly as supplied and are checked only for being non-empty strings; they are never validated against the ISO register, so the alpha-3 convention is documentary. The tax profile is optional at registration and consists of `tax_residency_country`, again an ISO 3166-1 alpha-3 code, which when omitted is filled in from `country_code`; `w8ben_on_file`, a flag that defaults to false and records whether a valid treaty certification form has been lodged; and `treaty_withholding_bps`, the treaty rate in basis points, defaulting to 0 and constrained to between 0 and 3,000 inclusive, which is consulted only when the certification form is on file. `whereabouts_filed` also defaults to false and records whether the athlete has filed anti-doping whereabouts and availability information. A system counter, `missed_test_count`, starts at zero and tracks how many of that athlete's tests have ended up missed. A `FinanceOfficer` may later revise the withholding profile — `tax_residency_country`, `w8ben_on_file` and `treaty_withholding_bps` are each independently updatable, every one of them optional in the request, and a key supplied as null counts as omitted and leaves the stored value alone — which increments the athlete's `version` on every accepted call, including one that supplies no field at all; awards already computed are deliberately not re-withheld by that edit, and the new profile takes effect only the next time the award set is regenerated.

A **representation agent** is registered with an `agency_name` and a `license_code` that must be unique across all agents, a duplicate being refused with `ERR_CONFIG_DUPLICATE`. `commission_bps` records the agent's commission in basis points for reporting purposes only — the system never applies it to any payment — and defaults to 1,500 within a permitted range of 0 to 3,000 inclusive. An agent's `status` may be supplied at registration as either `ACTIVE` or `SUSPENDED` and defaults to `ACTIVE` when omitted; a `SUSPENDED` agent may neither be offered an invitation nor negotiate nor respond, and any such attempt is refused with `ERR_AGENT_SUSPENDED`.

Qualifying proof enters the system as a **performance record**, which either the agent or the director may submit on an athlete's behalf. A submission carries `athlete_id`, the `race_name` where the performance was set, the `performance_date` as an ISO 8601 date, the claimed `performance_seconds` as a whole number of seconds greater than zero, the `division` the performance is being claimed against, a `sanctioning_ref` identifying the result in the sanctioning body's records, and an optional `chip_timed` flag defaulting to false. New records begin with `verification_status` at `SUBMITTED` and both `verified_seconds` and `rejection_reason` at null; `rejection_reason` is part of the record's representation and stays null unless and until a rejection fills it.

A `TechnicalOfficial` then adjudicates the claim, and this is where the system's most important piece of scepticism lives: the claimed time is never used for anything. Verification carries a `decision` of either `VERIFIED` or `REJECTED`. A `decision` of `VERIFIED` must be accompanied by `official_seconds` greater than zero; the record moves `SUBMITTED → VERIFIED` and `verified_seconds` is set to that official figure, which may differ from what was claimed and is the only value any qualifying comparison ever reads. A `decision` of `REJECTED` must be accompanied by a `rejection_reason`, which is stored; the record moves `SUBMITTED → REJECTED` and can never qualify an invitation again. Both target states are terminal, so a second verification attempt on an already-adjudicated record is refused with `ERR_INVALID_PERFORMANCE_STATE`. An athlete's submitted performances may be listed and filtered by `verification_status` and `division`.

### 3.3. Recruitment: The Offer and the Negotiation Cycle

An **invitation** is the negotiation vehicle, and it is created in `DRAFT` by an `ElitesDirector` naming five things: the `race_edition_id` being recruited for, the `athlete_id` being invited, the `agent_id` of the agent who represents that athlete for this deal, the `qualifying_performance_id` of the performance record pinned as the qualifying proof, and the `division` — `ELITE`, `SUB_ELITE` or `WHEELCHAIR` — the athlete is being invited into. A `DRAFT` invitation has `guaranteed_commitment_cents` at zero, `full_exposure_cents` at zero and `round_count` at zero, and its `current_appearance_fee_cents`, `current_air_class`, `current_hotel_nights`, `current_ground_transport`, `offer_sent_at`, `response_deadline_at`, `bib_number` and `negotiated_by_user_id` are all null. Invitations may be listed and filtered on `race_edition_id`, `athlete_id`, `agent_id`, `qualifying_performance_id`, `status` and `division`, which is how a client navigates from any of those entities back to the deals that reference it.

Sending the first offer moves the invitation `DRAFT → OFFERED` and requires the edition to be `FIELD_OPEN`, the invitation itself to stand in `DRAFT` — any other status is `ERR_INVALID_INVITATION_STATE`, surfacing ahead of the agent and qualifying gates — and the representing agent to be `ACTIVE`. It also runs the qualifying gate against exactly one performance record — the one pinned on the invitation. Other, faster performances by the same athlete are irrelevant. The pinned record must belong to the invited athlete and must have been claimed against the invitation's own division; either mismatch is `ERR_PERFORMANCE_DIVISION_MISMATCH`, and because that coherence test sits at priority 15 it is reached only once every qualifying check below has passed. It must be in `VERIFIED`. There must be a division standard for the combination of this edition, the invitation's division and the athlete's gender, and if there is none the offer is refused with `ERR_QUALIFYING_STANDARD_MISSING` — the standard's existence is tested before the record's own verification state, time, date window and timing technology, so a missing standard surfaces even when the pinned record would also have failed on its own merits. The record's `verified_seconds` must be no slower than that standard's `max_qualifying_seconds`, so a time exactly equal to the standard still qualifies. The `performance_date` must fall on or after the day obtained by subtracting the standard's `window_months` from the edition's `race_date`, and on or before the `race_date` itself; both endpoints are inclusive and the month subtraction keeps the same day of month, so with a two-year window a race dated the first of November 2026 accepts a performance run on the first of November 2024. Finally, if the standard requires chip timing, the record's `chip_timed` must be true. Every failure of the record's verification state, its time, its date window or its timing technology is reported as `ERR_QUALIFYING_STANDARD_NOT_MET`.

The offer itself carries the opening package: an `appearance_fee_cents` that may not be negative, an `air_class` of `ECONOMY`, `PREMIUM_ECONOMY` or `BUSINESS`, a `hotel_nights` count between 0 and 14 inclusive, a `ground_transport` boolean saying whether airport and ground transport is included, and an optional free-text `note`. Sending the offer writes the first **negotiation round**, with `side` set to `COMMITTEE` and `round_number` 1, mirrors the posted terms onto the invitation's four `current_` fields, stamps `offer_sent_at` from the logical clock, sets `response_deadline_at` to the logical clock plus the edition's `offer_response_days` days, records the acting operator in `negotiated_by_user_id`, and leaves the invitation in `OFFERED`. Although the offer brings that first round into existence, the operation is a transition on the invitation rather than a creation: it answers `200 OK` and its `data` is the updated invitation, not the round.

Thereafter the two sides alternate, and the alternation is enforced from the invitation's state rather than from any turn counter. From `OFFERED` only the `AthleteAgent` may append a round, which moves the invitation `OFFERED → COUNTERED`; from `COUNTERED` only the `ElitesDirector` may append one, which moves it `COUNTERED → OFFERED`. The cycle `OFFERED → COUNTERED → OFFERED` may repeat until the round allowance is used up. Acting from the wrong state is `ERR_ROLE_NOT_PERMITTED_FROM_STATE`, and appending a round from any status other than `OFFERED` or `COUNTERED` is `ERR_INVALID_INVITATION_STATE`. An appended round takes the same four term fields as the opening offer plus the optional `note`, and it additionally requires `expected_invitation_version` as described in §2.7. Each append requires the edition to still be `FIELD_OPEN`, requires the logical clock to be at or before `response_deadline_at` — a late arrival is `ERR_OFFER_DEADLINE_PASSED` — and requires the invitation's `round_count` to be strictly below twice the edition's `max_negotiation_rounds`; once the tally has reached that ceiling the append is refused with `ERR_NEGOTIATION_ROUNDS_EXHAUSTED`. When an agent appends, the ownership rule of priority 5 also applies and the acting operator must be the invitation's own agent. A successful append writes a round whose `round_number` is one more than the previous `round_count` and whose `side` is derived from the acting role, `COMMITTEE` for the director and `AGENT` for the agent; replaces all four `current_` term fields with the newly proposed ones; pushes `response_deadline_at` out to the logical clock plus `offer_response_days` days; increments the invitation's `version`; and flips the status to the opposite side of the cycle. The append answers `201 Created` and its `data` is the newly written round — `id`, `created_at`, `invitation_id`, `round_number`, `side`, the four term fields `appearance_fee_cents`, `air_class`, `hotel_nights` and `ground_transport`, and `note`, which is null when omitted — rather than the invitation the round moved. The `round_count` field is itself a read-only count of the rounds attached to the invitation. The full negotiation history of an invitation can be read in ascending `round_number` and filtered by `side`.

### 3.4. Acceptance, Refusal, Withdrawal and Locking the Field

Responding to terms carries a single field, `decision`, whose value is `ACCEPT` or `DECLINE`, and the same turn-taking rule governs it: from `OFFERED` the response comes from the `AthleteAgent` acting for the athlete, and from `COUNTERED` it comes from the `ElitesDirector` accepting or refusing the agent's counter. Either way the edition must still be `FIELD_OPEN`, the invitation must stand in `OFFERED` or `COUNTERED` — responding from any other status is `ERR_INVALID_INVITATION_STATE`, checked before the turn-taking rule — the agent must be `ACTIVE`, and the logical clock must be at or before `response_deadline_at`.

Acceptance is the moment money becomes real, and its price is the **guaranteed valuation** of the current package. That valuation is built from the invitation's four `current_` term fields. The air component is a flat allowance keyed to `current_air_class`: 120,000 cents for `ECONOMY`, 260,000 cents for `PREMIUM_ECONOMY`, and 540,000 cents for `BUSINESS`. The hotel component is 32,000 cents per night multiplied by the number of nights, where the number of nights used is the lesser of `current_hotel_nights` and the committee's ceiling of seven nights — the cap is applied to the night count before the nightly rate is multiplied, never to the product afterwards, so a fourteen-night package is valued at seven nights of hotel. The ground component is 18,000 cents when `current_ground_transport` is true and nothing when it is false. The guaranteed valuation is `current_appearance_fee_cents` plus the air component plus the hotel component plus the ground component, in integer cents, and it excludes every bonus exposure term.

Before the acceptance is admitted, the edition's `appearance_uncommitted_cents` must be at least that guaranteed valuation; if it is short, the acceptance is refused with `ERR_APPEARANCE_BUDGET_EXCEEDED`, and this fiscal ceiling is evaluated after every other check on the request. On success the invitation moves `OFFERED → ACCEPTED` or `COUNTERED → ACCEPTED`, the guaranteed valuation is frozen onto `guaranteed_commitment_cents`, the edition's `appearance_committed_cents` grows by that amount, `appearance_uncommitted_cents` is recomputed, and the edition's `version` is incremented alongside the invitation's. In every status other than `ACCEPTED`, `guaranteed_commitment_cents` reads as zero.

A `DECLINE` moves the invitation `OFFERED → DECLINED` or `COUNTERED → DECLINED`. `DECLINED` is terminal and no budget moves, because nothing was ever committed; the edition is therefore not touched at all and its `version` does not move. Either decision answers `200 OK` with the updated invitation.

Withdrawal is the committee's unilateral exit and is available to an `ElitesDirector` while the edition is in `FIELD_OPEN` or `FIELD_LOCKED`, optionally recording a `reason` — which is accepted and validated as a string but is not persisted on the invitation and appears nowhere in its representation. Only the four statuses `DRAFT`, `OFFERED`, `COUNTERED` and `ACCEPTED` may be withdrawn; from any other the request is refused with `ERR_INVALID_INVITATION_STATE`. From `DRAFT`, from `OFFERED` and from `COUNTERED` a withdrawal simply moves the invitation to `WITHDRAWN` with no budget movement, since `guaranteed_commitment_cents` was already zero, and the edition is not touched. From `ACCEPTED` it is a genuine compensating action, and it may not be taken once a race result exists for that invitation — that block is also `ERR_INVALID_INVITATION_STATE`. It reduces the edition's `appearance_committed_cents` by the invitation's `guaranteed_commitment_cents`, resets `guaranteed_commitment_cents` to zero and increments the edition's `version`, so that the appearance-budget invariant of §2.9 holds exactly again; it nulls `bib_number`, returning that bib to its division pool for immediate reuse; and it moves every fluid-station reservation belonging to the invitation from `RESERVED` to `RELEASED`. `WITHDRAWN` is terminal.

Locking the field is the `ElitesDirector`'s cut-off, moving the edition `FIELD_OPEN → FIELD_LOCKED`, and it is admitted only when at least one invitation of the edition is `ACCEPTED`; an edition with none is refused with `ERR_INVALID_INVITATION_STATE`, and that check runs before the exposure ceiling below. Its precondition introduces the second valuation variant, the **full exposure** of an accepted package, which is the guaranteed valuation plus two bonus exposure terms. The first is the time-bonus exposure: among the edition's `TIME_BONUS` purse lines whose `division` equals the invitation's division and whose `gender` equals the athlete's gender, take the largest `amount_cents`, or zero when no such line exists. The second is the record-bonus exposure. Each division maps to a record class — `ELITE` and `SUB_ELITE` both map to the open class, while `WHEELCHAIR` maps to the wheelchair class — and that class together with the athlete's gender selects one of the edition's four course-record fields: the open class selects `course_record_male_seconds` or `course_record_female_seconds`, and the wheelchair class selects `course_record_wheelchair_male_seconds` or `course_record_wheelchair_female_seconds`. The athlete is treated as a threat to that record when the selected record field is null, or when the `verified_seconds` of the pinned qualifying performance is at or below the value in that field. When the athlete is a threat, the record-bonus exposure is the `amount_cents` of the `RECORD_BONUS` purse line matching the invitation's division and the athlete's gender; otherwise it is zero. Full exposure is therefore always at least the guaranteed valuation, and strictly greater for any athlete with a matching bonus line. The lock is admitted only when the summed full exposure across all `ACCEPTED` invitations of the edition is no greater than `appearance_budget_cents` plus `bonus_pool_cap_cents`; over that ceiling it is refused with `ERR_FIELD_LOCK_EXPOSURE_EXCEEDED`.

When the lock succeeds it does three things. Visiting the `ACCEPTED` invitations in ascending `created_at`, it stamps each one's computed full exposure onto `full_exposure_cents` and increments that invitation's `version`. Visiting the invitations still in `DRAFT`, `OFFERED` or `COUNTERED` in ascending `created_at`, it moves each to `EXPIRED` — leaving `response_deadline_at` untouched, since the expiry is administrative rather than temporal — and increments the edition's `expired_offer_count` once per invitation so expired. Finally it sets the edition's `status` to `FIELD_LOCKED`. However many invitations the lock stamps or expires, the edition's own `version` moves exactly once for the whole operation. `EXPIRED` is terminal.

### 3.5. Elite Athlete Services: Bibs, Fluid Tables and Pacing

Bib assignment is a service operation on an `ACCEPTED` invitation, performed by an `ElitesDirector` while the edition is `FIELD_OPEN` or `FIELD_LOCKED`; attempting it against an invitation in any other status is `ERR_INVALID_INVITATION_STATE`, and attempting it against an invitation that already holds a `bib_number` is `ERR_BIB_ALREADY_ASSIGNED`. It is also the point at which the committee checks that the athlete is in good standing with the testing programme — and because that gate sits at priority 12 while the already-assigned check sits at priority 14, a non-compliant athlete whose invitation already carries a bib is refused with `ERR_ATHLETE_NOT_DOPING_COMPLIANT`. An athlete is **doping-compliant** for an edition when three things hold at once: `whereabouts_filed` is true; the number of that athlete's doping tests in `MISSED` whose `window_end_at` falls on or after the day 365 days before the edition's `race_date` is strictly fewer than two, so it is the second recent missed test that breaks compliance rather than the first; and no doping test exists for that athlete in that edition with status `ADVERSE`. The missed-test tally is counted across every edition the athlete has been tested under, while the adverse check looks only at tests belonging to this edition. A failure on any of the three is `ERR_ATHLETE_NOT_DOPING_COMPLIANT`. As a matter of programme record, an out-of-competition clearance is regarded as current for 90 days; that horizon is informational and gates nothing.

Once the athlete passes the gate, the bib is chosen deterministically rather than randomly. The eligible pool is every integer from `bib_range_start` through `bib_range_end` inclusive on the division standard matching this invitation's edition, division and the athlete's gender. From that pool the server excludes every bib currently held by an `ACCEPTED` invitation of the same edition — and only of the same edition. Bibs held by invitations that have gone `WITHDRAWN`, `BREACHED`, `EXPIRED` or `DECLINED` are not held at all and are immediately reusable. The lowest remaining number is written to `bib_number`; because bib numbers are distinct integers there is never a tie to break, and the selector consults no identifier of any kind. When nothing remains in the pool the request is refused with `ERR_BIB_POOL_EXHAUSTED`, and the same code answers the degenerate case in which no division standard exists at all for this edition, division and gender, since an absent standard offers an empty pool rather than a missing-configuration error.

Bottles are reserved by **fluid-station slot**, one reservation per station, naming the `invitation_id` of the accepted invitation the bottles belong to — the reservation endpoint imposes no status precondition of its own on that invitation, so the edition posture is the only gate it applies — the `station_km` at which they sit, the first `table_position` occupied — an integer between 1 and 40 inclusive — and a `bottle_count` between 1 and 3 inclusive giving how many adjacent positions the reservation takes. Stations exist only at the eight marks 5.0, 10.0, 15.0, 20.0, 25.0, 30.0, 35.0 and 40.0 kilometres; any other `station_km` is a malformed request, as is a reservation whose last position would fall beyond position 40. The server derives `occupied_from` as the first table position and `occupied_to` as the first position plus the bottle count less one, making a closed interval of integer positions, and sets `status` to `RESERVED`. Conflict is then tested against the `RESERVED` reservations at the same `station_km` whose owning invitations belong to the same edition; reservations in `RELEASED` never conflict, and reservations at a different station or in a different edition are irrelevant. The rule is not simple intersection: two reservations must leave at least one free position between them, so a new reservation conflicts with an existing one unless the earlier one's last position is at least two positions below the later one's first position. Positions 3 through 4 and positions 5 through 6 therefore conflict, because nothing free separates them, while positions 3 through 4 and positions 6 through 7 coexist, because position 5 stays free. A conflict is refused with `ERR_FLUID_SLOT_CONFLICT`. An invitation's reservations may be listed and filtered by `status` and `station_km`.

**Pacing arrangements** are registered per licensed pacer against an edition, naming the `race_edition_id`, the `pacer_license_code` that identifies the pacer and is the key against which range occupation is measured, the `pacer_name` for display, a `target_pace_seconds_per_km` between 120 and 400 inclusive, and the paced range as `start_km` — which may not be negative — and `end_km`, which must be strictly greater than the start. The range is half-open: it includes its start and excludes its end. `assistance_rule` records whether the pacer may hand fluids to the athlete, taking either `LEAD_ONLY` or `FLUIDS_ALLOWED` and defaulting to `LEAD_ONLY`. Pacing on this course stops at 32.0 kilometres, well short of the 42.195-kilometre race distance; an `end_km` exactly equal to 32.0 is admitted while anything beyond it is refused with `ERR_PACING_BEYOND_LIMIT`, and this ceiling is a business rule rather than a schema bound, tested before the overlap check so a range both too long and overlapping surfaces the ceiling. Two arrangements conflict only when they belong to the same edition and the same `pacer_license_code` and their half-open ranges genuinely overlap — that is, when the new range starts before the existing one ends and the existing one starts before the new one ends. There is no buffer, so abutting ranges are legal and one pacer may hold both 0 through 21.0 and 21.0 through 32.0. Arrangements of a different licence code never conflict. An overlap is refused with `ERR_PACING_RANGE_CONFLICT`. An edition's pacing arrangements may be listed, filtered by `pacer_license_code`.

### 3.6. Anti-Doping Coordination and the Disqualification Cascade

The `AntiDopingLiaison` schedules each **doping test** against an athlete availability window, supplying the `athlete_id` under test, the `race_edition_id` whose testing programme owns the test, a `test_type` of either `IN_COMPETITION` or `OUT_OF_COMPETITION`, the window as `window_start_at` and `window_end_at` — a closed datetime interval whose end must be strictly later than its start, each accepted with a `Z` suffix, an explicit offset or no zone at all (which is read as UTC) and each echoed back normalised to UTC in the canonical three-fractional-digit form — and a `sample_code` agreed with the sanctioning body that must be unique across all tests, a duplicate being `ERR_CONFIG_DUPLICATE`. A new test begins in `SCHEDULED` with `collected_at`, `collected_sample_ref` and `outcome_notes` all null.

Two independent capacity rules apply at scheduling time. The first is overlap: the requested closed window may not touch or overlap any window of the same athlete belonging to a test in `SCHEDULED` or `COLLECTED`. Touching counts as overlapping, so a window whose start equals another window's end conflicts, and the rejection is `ERR_TESTING_WINDOW_OVERLAP`. Tests already in `CLEARED`, `ADVERSE` or `MISSED` are ignored by this check. The second rule is a frequency cap that applies regardless of overlap: counting the athlete's tests in every status, including completed and missed ones, whose `window_start_at` falls within seven days either side of the requested start, the request is refused with `ERR_TESTING_FREQUENCY_EXCEEDED` once that count has reached two. A finished test therefore still consumes capacity. Both rules scan the athlete's tests across every edition, not merely the edition named on the request, and the seven-day span is inclusive at both ends, so a peer window starting exactly seven days away is counted. The three scheduling rejections are evaluated in a fixed order — window overlap first, then the frequency cap, then the `sample_code` uniqueness check — so a request that would trip more than one of them surfaces the earliest.

Collection moves a test `SCHEDULED → COLLECTED` and is admitted only when the logical clock sits at or after `window_start_at` and at or before `window_end_at`; outside that closed interval it is refused with `ERR_COLLECTION_WINDOW_INVALID`. The request supplies a `collected_sample_ref`, the chain-of-custody reference, which is stored alongside a `collected_at` taken from the logical clock. Attempting collection on a test that is not `SCHEDULED` is `ERR_INVALID_DOPING_TEST_STATE`.

The `SanctioningBody` then returns the laboratory result, supplying an `outcome` of either `CLEARED` or `ADVERSE` together with an optional `outcome_notes` that is stored as the body's note on the adjudication. Adjudication is admitted only from `COLLECTED`; from anywhere else it is `ERR_INVALID_DOPING_TEST_STATE`. An outcome of `CLEARED` moves the test `COLLECTED → CLEARED`, and for an `IN_COMPETITION` test that clearance is what unlocks prize approval for the athlete.

An outcome of `ADVERSE` moves the test `COLLECTED → ADVERSE` and starts a four-hop cascade that is the most consequential chain in the system. Because the test is `ADVERSE`, every race result sharing that test's athlete and edition whose `certification_status` is `PROVISIONAL` or `CERTIFIED` moves to `DISQUALIFIED` with `dq_reason` set to `ADVERSE_ANALYTICAL_FINDING`. Because each of those results is now disqualified, any record claim it held in `CLAIMED` or `SUBMITTED` moves to `REJECTED`, and its prize awards cascade exactly as described for a manual disqualification in §3.7 — awards in `COMPUTED` or `APPROVED` become `VOID`, awards in `PAID` become `CLAWBACK_PENDING`, the edition's ledger projections are recomputed and the edition's `version` is incremented. And because `ADVERSE_ANALYTICAL_FINDING` is one of the breach reasons, the invitation each disqualified result ran under moves `ACCEPTED → BREACHED` with all of that transition's own effects. The edition's `version` moves at most once for the whole adjudication, and only when the cascade actually shifted an award's status or breached an invitation: an `ADVERSE` outcome that disqualifies a result carrying neither awards nor an `ACCEPTED` invitation leaves the edition's `version` where it was.

Overdue tests are not resolved by adjudication but by the operational sweep of §3.9, which moves a `SCHEDULED` test past its window end to `MISSED`. `CLEARED`, `ADVERSE` and `MISSED` are all terminal. Doping tests may be read individually or listed and filtered on `athlete_id`, `race_edition_id`, `test_type` and `status`, which is the reverse-navigation channel for both of the entity's foreign keys.

### 3.7. Race Day, Results, Certification and Course Records

A `TechnicalOfficial` opens the race by moving the edition `FIELD_LOCKED → RACED`, which is admitted only once the logical clock has reached the edition's `race_date` at midnight UTC; before that instant it is refused with `ERR_RACE_DATE_NOT_REACHED`. From `RACED`, results may be entered.

A **race result** is entered against a bibbed invitation, naming the `race_edition_id` and the `invitation_id` and carrying two times: `gun_seconds`, the gun-to-finish time in whole seconds, and `net_seconds`, the chip time in whole seconds, both strictly positive and with the net time no greater than the gun time. The named invitation must belong to the same edition, must be `ACCEPTED` and must already hold a `bib_number`; any of those three failing is `ERR_INVITATION_EDITION_MISMATCH`. Only one result may exist per invitation, and a second is refused with `ERR_DUPLICATE_RESULT`. On creation the server copies `athlete_id` and `division` from the invitation rather than accepting them from the client, and derives `official_seconds` from the division: for `ELITE` and `SUB_ELITE` results the official time is the gun time, while for `WHEELCHAIR` results it is the net time. The result begins with `certification_status` at `PROVISIONAL` and `record_claim_status` at `NONE`, its `dq_reason` and `sanctioning_submission_ref` null, its three place fields null, its `tie_group_size` at 1 and its `is_masters` false.

Each result then evolves along two independent dimensions. The first is certification. A `TechnicalOfficial` moves a result `PROVISIONAL → CERTIFIED` while the edition is `RACED`; a result that is not `PROVISIONAL` cannot be certified and is refused with `ERR_RESULT_NOT_CERTIFIED`, the priority-8 target-state code this endpoint uses in place of any result-specific one. Certification alone assigns no places — the place fields stay null until the edition-level certification pass runs. Disqualification is available from `PROVISIONAL` or from `CERTIFIED` while the edition is `RACED` or `RESULTS_CERTIFIED` — a result already `DISQUALIFIED` is likewise refused with `ERR_RESULT_NOT_CERTIFIED` — and it carries a `dq_reason` drawn from `PACER_BEYOND_RANGE`, `UNAUTHORIZED_FLUID_HANDOFF`, `COURSE_CUTTING`, `ADVERSE_ANALYTICAL_FINDING` and `MISSED_TEST_THRESHOLD`. `DISQUALIFIED` is terminal, and a disqualified result is excluded from the input set of every calculation in the system — it does not consume a place and it does not enlarge any tie group.

Disqualifying a result from `PROVISIONAL` records the status and the reason and nothing more, since a provisional result held no places, no claim and no awards. Disqualifying a result from `CERTIFIED` runs the full cascade. `place_overall`, `place_division` and `place_masters` are nulled and `tie_group_size` returns to 1. Because the result is disqualified, a record claim in `CLAIMED` or `SUBMITTED` moves to `REJECTED` — the cross-dimension coupling between the two state dimensions. Because the result is disqualified, each of its prize awards in `COMPUTED` or `APPROVED` becomes `VOID` and each in `PAID` becomes `CLAWBACK_PENDING`. Because those awards changed status, the edition's `purse_allocated_cents`, `purse_unallocated_cents` and `bonus_pool_consumed_cents` are all recomputed and the edition's `version` is incremented exactly once — and only when at least one award actually moved or the invitation was actually breached, so a `CERTIFIED` result carrying no awards, disqualified for `MISSED_TEST_THRESHOLD`, leaves the edition's `version` alone — a `VOID` award leaves the allocated pool and its cents return to the unallocated pool, whereas a `CLAWBACK_PENDING` award stays inside the allocated pool and the unallocated pool does not grow. And when the `dq_reason` is one of the four breach reasons `PACER_BEYOND_RANGE`, `UNAUTHORIZED_FLUID_HANDOFF`, `COURSE_CUTTING` or `ADVERSE_ANALYTICAL_FINDING`, the invitation the runner ran under moves `ACCEPTED → BREACHED`. A breach is a compensating action in its own right: the edition's `appearance_committed_cents` is reduced by the invitation's `guaranteed_commitment_cents`, that field is then reset to zero, `bib_number` is nulled, and every fluid-station reservation of the invitation moves from `RESERVED` to `RELEASED`. `BREACHED` is terminal. A disqualification deliberately does not re-place the surviving results; re-placement happens only when the award set is explicitly recomputed.

Certifying the edition is the `TechnicalOfficial`'s pass over the whole result set, moving it `RACED → RESULTS_CERTIFIED`. It is admitted only when no result of the edition is still `PROVISIONAL` and at least one result is `CERTIFIED`; a still-provisional result or an empty certified set is refused with `ERR_RESULTS_NOT_ALL_ADJUDICATED`. The pass first assigns places and ties over the `CERTIFIED` results, using `official_seconds` throughout. Age is computed as the difference between the race year and the birth year, reduced by one when the race's month-and-day pair falls before the birth date's month-and-day pair, so a birthday landing exactly on race day counts as reached; `is_masters` is true when that age in completed years is at least the edition's `masters_min_age`. Three partitions are then formed among the certified results of the edition. The overall partition groups results by the athlete's gender and admits only divisions `ELITE` and `SUB_ELITE`. The division partition groups by division and the athlete's gender. The masters partition groups by the athlete's gender and admits only results whose division is `ELITE` and whose `is_masters` is true. Within a partition, a result's place is one more than the number of results in that partition strictly faster than it, which is standard competition ranking: two runners on the same official time share a place and the place after a shared pair is skipped. `place_overall` is the result's place in the overall partition for `ELITE` and `SUB_ELITE` results and null for `WHEELCHAIR` results. `place_division` is the result's place in the division partition and is always assigned. `place_masters` is the result's place in the masters partition when the result is `ELITE` and a master, and null otherwise. `tie_group_size` is the number of certified results sharing this result's `official_seconds` inside the partition that produced its overall place, or inside its division partition when it has no overall place, which is the wheelchair case. The pass writes these five fields — `is_masters`, the three places and `tie_group_size` — only where at least one of them actually differs from what the result already holds, so a result whose computed values are unchanged keeps its `updated_at` and its `version`, while one whose values move has both refreshed once.

The same pass raises course-record claims. For every `CERTIFIED` result whose division is not `SUB_ELITE`, the server looks up the edition's course record for that result's record class and the athlete's gender — the open class for `ELITE` results, the wheelchair class for `WHEELCHAIR` results, mapped onto the four course-record fields exactly as in §3.4. When that record field is null, or when the result's `official_seconds` is strictly faster than the value on file, the result's `record_claim_status` moves `NONE → CLAIMED`. Once the edition reaches `RESULTS_CERTIFIED`, award computation becomes available.

The second dimension of a result is its record claim, whose values are `NONE`, `CLAIMED`, `SUBMITTED`, `RATIFIED` and `REJECTED`. A `TechnicalOfficial` lodges the ratification package with the sanctioning body, supplying a `sanctioning_submission_ref`; this is admitted only for a result whose `certification_status` is `CERTIFIED`, whose division is not `SUB_ELITE`, and whose claim stands in `CLAIMED` or in `REJECTED` — a rejected package may be corrected and lodged again, moving `REJECTED → SUBMITTED`. A claim in `NONE` was never raised and is refused with `ERR_RECORD_CLAIM_NOT_ELIGIBLE`, while a claim already `SUBMITTED` or already `RATIFIED` is refused earlier with `ERR_INVALID_RECORD_CLAIM_STATE`, per the precedence note in §2.11. Those preconditions are evaluated in a fixed order at this endpoint. The claim-state check comes first, so a claim already `SUBMITTED` or already `RATIFIED` surfaces `ERR_INVALID_RECORD_CLAIM_STATE` whatever the result's certification status and division. A package lodged against a result whose `certification_status` is anything other than `CERTIFIED` — one still `PROVISIONAL`, or one already `DISQUALIFIED` — is then refused with `ERR_RESULT_NOT_CERTIFIED`, the priority-8 target-entity state error of §2.11, whatever that result's division and whether its claim stands in `NONE`, `CLAIMED` or `REJECTED`. Only a `CERTIFIED` result therefore reaches the priority-15 eligibility test, where a `SUB_ELITE` division or a claim in `NONE` is what surfaces `ERR_RECORD_CLAIM_NOT_ELIGIBLE`. Lodging stores the reference and moves the claim `CLAIMED → SUBMITTED`, and while any claim of an edition is `SUBMITTED` that edition cannot settle its purse.

The `SanctioningBody` closes the claim with a `decision` of `RATIFIED` or `REJECTED` and an optional `decision_note`, which is validated as a string but is not persisted and appears in no representation. Both require the claim to be `SUBMITTED`, and ratification additionally requires the result to still be `CERTIFIED`; otherwise the request is refused with `ERR_INVALID_RECORD_CLAIM_STATE`. A `REJECTED` decision moves the claim `SUBMITTED → REJECTED`, leaves the course record untouched, and changes nothing else — in particular the edition is not touched and its `version` does not move. A `RATIFIED` decision moves the claim `SUBMITTED → RATIFIED` and then cascades twice: because the claim is ratified, the edition's course-record field for that result's record class and gender is overwritten with the result's `official_seconds` and the edition's `version` is incremented; and because the edition's course record has changed, every other `CERTIFIED` result of the edition whose claim stands in `CLAIMED` and whose `official_seconds` is not strictly faster than the newly ratified figure moves `CLAIMED → REJECTED`. Results may be read individually or listed and filtered on `race_edition_id`, `athlete_id`, `invitation_id`, `division`, `certification_status` and `record_claim_status`.

### 3.8. The Prize Purse: Generation, Withholding, Approval and Settlement

Award generation is a `FinanceOfficer` operation on an edition in `RESULTS_CERTIFIED`, guarded by `expected_race_edition_version` as described in §2.7, and it is idempotent in intent rather than in effect: it regenerates the whole set from the current data. It proceeds in a fixed sequence of steps.

It begins by superseding: every existing prize award of the edition whose `status` is `COMPUTED` becomes `VOID`, while awards already in `APPROVED`, `PAID` or `CLAWBACK_PENDING` are left exactly as they are and their cents stay allocated against the purse. It then re-runs the place-and-tie assignment of §3.7 over the current `CERTIFIED` set, which is where a disqualification recorded since the last run finally re-places the survivors.

Place prizes are then paid in three categories, in the fixed order `OVERALL`, then `DIVISION`, then `MASTERS`. Within a category, the distinct places actually occupied are visited in ascending place order, and where several partitions of the same category occupy the same place the partitions are visited by ascending division name — with the null division of an `OVERALL` or `MASTERS` line sorting first — and then by ascending gender, so `FEMALE` precedes `MALE`. That is the order in which the awards of a run come into existence, and since they all share the run's single `created_at` it is also the order in which they list. For a place, the tied group is the certified results holding that place in that category's partition, and its size is the tie count. The pool for that group is the sum of `amount_cents` over the edition's purse lines of that category matching the group's partition — matching on gender, and additionally on division for `DIVISION` lines — whose `place` falls in the run of consecutive places starting at the shared place and extending for as many places as there are tied runners. A purse line that does not exist contributes nothing. The order of operations is pinned: pool the matching line amounts first, then divide the pool by the tie count and take the floor of the quotient as each runner's share, then compute the leftover as the pool less that share multiplied by the tie count — a value between zero and one less than the tie count — and hand one extra cent to each of the earliest tied results, ordering the tied group by the result's `created_at` ascending, until the leftover is exhausted. Rounding each purse line before pooling is wrong and will produce different cents. Each resulting award is created in `COMPUTED` with its `category`, its `place` set to the shared place, its `tie_share_count` set to the tie count — which is 1 when there was no tie — and its `gross_amount_cents` set to that runner's share. An award whose gross would be zero is not created at all. `MASTERS` purse lines pay only results whose division is `ELITE` and whose `is_masters` is true; `DIVISION` lines pay only the division named on the line; `OVERALL` lines ignore division entirely and cover the `ELITE` and `SUB_ELITE` results of the matching gender.

Bonuses are computed next, against the edition's `bonus_pool_cap_cents`, and the pool is consumed in a strict order that makes the cap a genuine race between athletes. The consumed figure starts as the summed `gross_amount_cents` of the surviving `TIME_BONUS` and `RECORD_BONUS` awards in `APPROVED`, `PAID` or `CLAWBACK_PENDING` — the bonuses kept from earlier runs. The certified results are then visited in ascending `official_seconds`, breaking ties by ascending result `created_at`. For each result, the time-bonus candidate is the largest `amount_cents` among the edition's `TIME_BONUS` purse lines whose `division` equals the result's division, whose `gender` equals the athlete's gender, and whose `threshold_seconds` the result's `official_seconds` does not exceed — the threshold is inclusive, so hitting it exactly earns the tier — or zero when no tier matches. Time bonuses are matched on exact division and gender; there is no wildcard. For a `WHEELCHAIR` result the time-bonus candidate is then scaled to 7,500 basis points of itself — three quarters — taking the floor of the product rather than rounding half up. The record-bonus candidate is the `amount_cents` of the `RECORD_BONUS` purse line matching the result's division and the athlete's gender, but only when the result's `record_claim_status` is `RATIFIED` at the instant generation runs; otherwise it is zero. The candidate paid is the greater of the two: a record bonus supersedes a time bonus, it never adds to it. The award's `category` is `RECORD_BONUS` when the record candidate is above zero and is at least as large as the time candidate, and `TIME_BONUS` in every other case. The headroom is the edition's `bonus_pool_cap_cents` less the consumed figure, floored at zero, and the amount actually paid is the lesser of the candidate and that headroom. When the paid amount is above zero an award is created in `COMPUTED` with that `category`, a null `place`, a `tie_share_count` of 1 and a `gross_amount_cents` equal to the paid amount, and the consumed figure grows by it. When the paid amount is zero — because no tier matched or because the pool is exhausted — no award is created at all.

Withholding is applied immediately after every gross amount in the run is fixed, per athlete, over that athlete's freshly generated awards in this edition. Awards voided by an earlier run are excluded. Which of three variants applies is decided by the athlete's profile, and the chosen variant is recorded on each award as `withholding_variant`. When the athlete's `tax_residency_country` is `USA`, the domestic case, the variant is `NONE`, `withholding_bps` is zero and `withholding_cents` is zero on every award. Otherwise, when `w8ben_on_file` is true, the variant is `PER_AWARD` and the rate is the athlete's `treaty_withholding_bps`; each award is then handled on its own, in ascending category order with `created_at` ascending as the tie-break, where category order runs `OVERALL`, `DIVISION`, `MASTERS`, `TIME_BONUS`, `RECORD_BONUS`. An award whose `gross_amount_cents` is below 60,000 cents is withheld nothing at all; otherwise its `withholding_cents` is the gross multiplied by the rate and divided by 10,000, rounded half up to whole cents. Rounding therefore happens once per award, and small awards escape withholding entirely.

When the athlete's residency is not domestic and `w8ben_on_file` is false, the variant is `AGGREGATED` and the rate is the statutory 3,000 basis points. Here the de-minimis test runs on the athlete's aggregate rather than award by award: the aggregate is the summed `gross_amount_cents` of the athlete's awards from this run, and when that aggregate is at or below 150,000 cents every award is withheld nothing. Above it, the total withheld is the aggregate multiplied by the statutory rate and divided by 10,000, rounded half up once, and that single total is then split across the awards pro rata by gross using largest-remainder allocation. Each award's exact share is the total multiplied by that award's gross and divided by the aggregate; each award provisionally receives the integer part of its exact share, truncated toward zero; the leftover is the total less the sum of those integer parts; and one extra cent goes to each of the first awards when the awards are ordered by the fractional part of their exact share descending, with the award's own `created_at` ascending as the tie-break, until the leftover is exhausted. The consequence is deliberate and visible: an award small enough to escape under `PER_AWARD` is still withheld on under `AGGREGATED`, so two athletes with identical grosses at an identical rate can owe different totals.

For every award, `net_amount_cents` is `gross_amount_cents` less `withholding_cents`, and `withholding_bps` is zero when the variant is `NONE` and the applicable rate otherwise — which means an award exempted by either de-minimis threshold still reports the rate that would have applied, with `withholding_cents` at zero. The run closes by recomputing the edition's `purse_allocated_cents`, `purse_unallocated_cents` and `bonus_pool_consumed_cents` and incrementing the edition's `version` exactly once, however many awards it voided or created. Generation answers `200 OK` and its `data` is the updated edition, not the award set; the awards themselves are then read through the filtered award list.

Approval is the first of two `FinanceOfficer` acts on an individual award and moves it `COMPUTED → APPROVED`. It requires the edition to be in `RESULTS_CERTIFIED`, requires the award itself to stand in `COMPUTED` — an award in any other status is refused with `ERR_INVALID_AWARD_STATE` before the result is even inspected — requires the award's result to be `CERTIFIED` — otherwise `ERR_RESULT_NOT_CERTIFIED` — and requires a doping test to exist for that result's athlete in that edition whose `test_type` is `IN_COMPETITION` and whose status is `CLEARED`; without that clearance the approval is refused with `ERR_IN_COMPETITION_TEST_NOT_CLEARED`. Approval records the acting operator in `approved_by_user_id`. Payment moves the award `APPROVED → PAID`, supplies a `payment_reference` which is stored, records the acting operator in `paid_by_user_id` and stamps `paid_at` from the logical clock. Payment may only be performed by a different operator than the one recorded in `approved_by_user_id`; the same identifier attempting both halves is refused with `ERR_SEGREGATION_OF_DUTIES`. The amount that leaves the treasury is `net_amount_cents`; the `withholding_cents` is remitted to the tax authority. Approving or paying an award that is not in the required state is refused with `ERR_INVALID_AWARD_STATE`. `VOID` and `CLAWBACK_PENDING` are both terminal award states. Awards may be read individually or listed and filtered on `race_edition_id`, `race_result_id`, `athlete_id`, `category` and `status`.

Settling the purse is the last act of the edition's life, performed by a `FinanceOfficer` and moving it `RESULTS_CERTIFIED → PURSE_SETTLED`. It is admitted only when every prize award of the edition stands in `PAID`, `VOID` or `CLAWBACK_PENDING` — an award still in `COMPUTED` or `APPROVED` blocks it with `ERR_AWARDS_NOT_ALL_SETTLED` — and only when no result of the edition still has a record claim in `SUBMITTED`, a block reported as `ERR_INVALID_RECORD_CLAIM_STATE`. The award sweep is evaluated first, so an edition failing both surfaces `ERR_AWARDS_NOT_ALL_SETTLED`. Settlement recomputes `purse_allocated_cents` and `purse_unallocated_cents` and sets the status to `PURSE_SETTLED`, which is terminal; every mutation in the edition's subtree is rejected thereafter.

### 3.9. The Ops-Run Checkpoint

Because deadlines are logical rather than real, someone has to walk the edition and apply them. That is the `ElitesDirector`'s operational sweep, which is available as a single checkpoint and runs three steps in order, each visiting its rows in ascending `created_at`. The checkpoint is admitted from every posture except `PURSE_SETTLED`, and it answers `200 OK` with the updated edition.

Step one expires overdue offers. Every invitation of the edition in `OFFERED` or in `COUNTERED` whose `response_deadline_at` lies strictly before the logical clock moves to `EXPIRED`, and the edition's `expired_offer_count` grows by one for each. An invitation still in `DRAFT` has no deadline and is untouched by this step; it is only the field lock that expires drafts.

Step two records missed tests. Every doping test of this edition in `SCHEDULED` whose `window_end_at` lies strictly before the logical clock moves to `MISSED` — the step is scoped to the swept edition's own testing programme and never reaches a test belonging to another edition — and for each one the athlete's `missed_test_count` is incremented and the athlete's `version` is incremented with it. This is the only path by which a test becomes missed, and it is what eventually trips the doping-compliance gate of §3.5.

Step three recomputes the edition's ledger projections in full — `appearance_committed_cents`, `appearance_uncommitted_cents`, `purse_allocated_cents`, `purse_unallocated_cents` and `bonus_pool_consumed_cents` — and re-evaluates doping compliance for the edition's athletes. Both are pure re-derivations: the five ledger figures are computed from the invitations and awards on every read of the edition, and the compliance re-evaluation persists no field of its own, so step three's only visible effect is the version bump. The sweep increments the edition's `version` once for the checkpoint.

## 4. Endpoint Definitions

Operations that bring a new resource into existence return `201 Created`: creating an edition, a purse line, a division standard, an athlete, a representation agent, a performance record, an invitation, a negotiation round, a fluid-station slot, a pacing arrangement, a doping test or a race result. Every other operation — posture changes on an edition, state transitions on a child resource, profile updates, the clock control and all reads — returns `200 OK`, and each such transition answers with the resource it transitioned, except that sending an offer answers with the invitation and every edition-level operation answers with the edition. The one operation whose `data` is not a persisted resource is the clock control, which takes a required `to_iso8601` and answers with the single key `current_utc` carrying the clock's new value in the same three-fractional-digit UTC form as every other timestamp. Error responses carry the status code listed in §5.
