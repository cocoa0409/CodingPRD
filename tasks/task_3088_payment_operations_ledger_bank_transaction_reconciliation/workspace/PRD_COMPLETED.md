# Payment Operations Ledger Reconciliation API — Product Requirements Document

## 1. Introduction

Payment operations teams live or die by whether the money they think they moved is the money the bank actually moved. This API exists to close that gap. It models payment initiation across four rails — the automated clearing house, wire, real-time payments and paper check — as a sequence of explicit, auditable state changes, and it books every one of those changes into a double-entry `Ledger` whose pending and posted balances are derived, never typed in by hand. The product's north star is agreement: at any instant an operator can ask a ledger what it believes and can ask a bank statement what the bank believes, and the reconciliation machinery exists to explain, quantify and finally eliminate every cent of difference between the two answers.

The second half of the problem is trust. Moving money is the highest-privilege operation the platform performs, so no single human is allowed to do it alone: one operator drafts a payment, a different operator releases it, and the allocation of these powers across eight distinct roles is a first-class requirement rather than an afterthought. Every mutating operation appends an immutable `AuditEvent` carrying a per-ledger monotonic `sequence_number`, so the complete history of a ledger can be replayed from its audit trail alone. Closed accounting periods are frozen: a posting whose business-effective instant falls inside a closed period is rejected outright, and no back-dated adjustment can silently rewrite a set of books that has already been reported.

This document specifies the complete external contract of that system — its resource model, its state machines, its arithmetic, its validation cascade, its access-control matrix and its error catalogue — in sufficient precision that an independent implementer can build a byte-compatible service without ever consulting an internal design document.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` names the capacity in which that user is acting. If either header is absent, or if `X-User-Role` names a role that the platform does not recognize, the request is refused with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER`, which is always reported with HTTP status 401. If both headers are present and valid but the caller's role does not appear in the authorized-role list for the endpoint being invoked, the request is refused with `ERR_FORBIDDEN_FOR_ROLE`, reported with HTTP status 403. No endpoint in this API is anonymous.

The platform defines exactly eight roles. `PlatformAdmin` provisions institutions, ledgers and calendars and holds no payment-release authority at all, which is a deliberate structural choice: release can therefore never be granted as a side effect of platform administration. `LedgerController` owns the books — it opens and closes periods, recomputes derived balances, voids posted entries, and is the only role permitted to certify a ledger as balanced. `PaymentInitiator` drafts payments and may never release one; the release endpoints do not list this role at all, and the `ReleaseRequest` it raises is the only route by which its own payment can reach the rails. `PaymentApprover` is the release authority and the only role that can make money move; it approves and dispatches payment orders and maintains counterparty posture. `PaymentOpsAnalyst` works the exceptions and the settlement pipeline but cannot approve, dispatch or close a period. `PaymentOpsApprover` is the senior operations approver: it waives aged exceptions and reassigns the queue, and it too possesses no payment-release authority, so an exception waiver can never be traded for a release. `CounterpartyUser` is the counterparty's own operator. `Auditor` is a read-only external reviewer that sees postings, exceptions, statements and the audit trail and can read nothing that would let it mutate state.

Role-to-identity binding is not uniform, and the difference matters for ownership checks. For `PlatformAdmin`, `LedgerController`, `PaymentInitiator`, `PaymentApprover`, `PaymentOpsAnalyst`, `PaymentOpsApprover` and `Auditor`, the `X-User-ID` value is an opaque operator identifier that is not tied to any persisted entity; the server may record it — for example as `initiator_user_id` or `approver_user_id` on a `PaymentOrder`, or as `actor_user_id` on an `AuditEvent` — but it never compares that value to any entity's `id`. For `CounterpartyUser` the identity is real: when `X-User-Role` is `CounterpartyUser`, `X-User-ID` must be the `id` of an existing `Counterparty`, and any ownership check on a resource that references a counterparty compares the resource's counterparty foreign-key field to `X-User-ID`.

Several endpoints are single-role by design, and for those the role check runs before any other check. An activation request on a counterparty relationship, an approval or a dispatch of a payment order, a period close, a posted-entry void and an exception waiver are all refused with `ERR_FORBIDDEN_FOR_ROLE` (HTTP 403) when presented by any other role, regardless of how valid the rest of the payload is. The distinction is observable: a `PaymentApprover` whose `X-User-ID` equals a payment order's `initiator_user_id` passes the role gate on approval and fails the later separateness check with `ERR_SELF_APPROVAL_FORBIDDEN`, whereas a `PaymentOpsAnalyst` calling the very same endpoint never reaches the separateness check and fails at the role gate with `ERR_FORBIDDEN_FOR_ROLE`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

---

### 2.3. Pagination

List endpoints accept a `limit` and an `offset`. The `limit` parameter caps how many items a single response may carry; it defaults to 10, its minimum admissible value is 1 and its maximum is 100. The `offset` parameter states how many leading items to skip and defaults to 0. Unless a subsection below says otherwise, every list endpoint returns its rows in `created_at` ascending order. Responses that are lists carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope.

### 2.4. The Chart of Accounts: Ledgers and Their Money

A `Ledger` is the unit of accounting. It is opened with a `name` and a `currency`, where the `currency` must be one of exactly `USD`, `EUR` or `GBP`; every amount booked into that ledger is denominated in that currency. The ledger's `status` begins at `OPEN` and can end at `CLOSED`. Two system-managed period fields describe where the books currently stand: `period_index` starts at 1 and counts the accounting period currently in progress, while `period_closed_through_index` starts at 0, where 0 means that no period has yet been closed at all. The instant at which the current period opened is `period_opened_utc`, which is the ledger's own creation instant for the first period and the preceding period's close instant thereafter; this value is the inclusive lower bound of `period_index`.

Four derived monetary fields live on the ledger. `pending_balance_cents` is the signed sum of `net_effect_cents` over every transaction in the ledger whose `settlement_status` is either `UNSETTLED` or `IN_SETTLEMENT`. `posted_balance_cents` is the signed sum of `net_effect_cents` over every transaction in the ledger whose `settlement_status` is exactly `SETTLED`, and it is the only balance eligible for reconciliation against a bank statement. `delivered_fee_transfers_cents` is a running total of the reverse-rail fee shares that have actually been delivered by resolved return legs, and `undeliverable_cents` is the residue parked when a leg's allocated share exceeded the settled fee cover available to it; those two fields are the two halves of one conserved quantity, described in §2.11.

All four derived balances are recomputed after every posting, every settlement decision and every recomputation, and the recomputation happens inside the same request that caused it, so the response to the mutating call already carries the new numbers. This is a derived-field reconciliation model, not an eventually-consistent one.

### 2.5. Common Resource Properties

Most resources in this API carry a standard quartet of server-managed fields. `id` is a unique, system-generated identifier formatted as a UUID with no type prefix and no embedded entity name. `created_at` is an ISO 8601 UTC timestamp with exactly three fractional digits recording when the row was first written. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits recording the last modification. `version` is an integer that increments by one on every modification to the resource and exists so that clients can participate in optimistic concurrency control.

The exception is `AuditEvent`, which is declared with `common_fields: false`. An audit event carries an `id` and a `created_at` and nothing else from the quartet: it has no `updated_at` field and it has no `version` field, because an audit event is immutable once appended and can never be modified, so neither a modification timestamp nor a mutation counter would ever advance. Implementers should not mint `updated_at` or `version` on an audit event and should not expect them in an audit-event response body.

### 2.6. Arithmetic, Signs and Precision

Amounts are integers in the smallest currency unit; every monetary field in this API is a whole number of cents and no rounding step is ever applied to a stored balance. Derived balances, fee totals, allocated shares and attributed fee components are all computed with integer arithmetic only — additions, subtractions and integer floor division. Where a formula divides at all, the quotient is truncated toward negative infinity by floor division and no fractional intermediate value is ever materialised, which is why a large wire fee can be computed without a decimal type.

The design decision that most often trips an implementer is that debit and credit entries are not separate books. A `Transaction` carries a `direction` of `DEBIT` or `CREDIT`, and a `net_effect_cents` that is the negative of `amount_cents` when the direction is `DEBIT` and the positive of `amount_cents` when the direction is `CREDIT`. Both derived ledger balances are signed sums of that single field over a single population, so an outbound credit leg depresses the pending balance by its amount and, once settled, moves into the posted book carrying the very same sign. No sign flip occurs at settlement.

### 2.7. Optimistic Concurrency Control

Some write paths require the caller to prove that it is acting on a version of a parent resource that it has actually observed. Those paths accept an `expected_..._version` field in the request body; the field is required on the statement-import path and is optional on every other guarded path, where a request that omits it is not refused on version grounds. Whenever a supplied value does not match the parent entity's current `version`, the entire request is rejected with `ERR_STALE_VERSION`, reported with HTTP status 412; a supplied value that is not an integer is refused as `ERR_INVALID_REQUEST` with HTTP status 400. The rule is a stale-version rejection rule and nothing more: it exists so that a client cannot act on a parent it has not observed. Endpoints that are not named below take no version field at all.

Importing a bank statement through the statement-import path requires `expected_bank_account_version` matching the current `version` of the `BankAccount` the statement belongs to; a writer whose view of that account's statement history has gone stale is rejected with `ERR_STALE_VERSION` and HTTP 412 rather than being allowed to supersede a revision it has never seen. Activating a counterparty relationship requires `expected_relationship_version` matching the current `version` of the `CounterpartyRelationship`; the rejection is again `ERR_STALE_VERSION` with HTTP 412, and the reason is that an intervening activation already consumed the counterparty-relationship slot for that institution pair, so a second activation would duplicate an account-sharing grant. Asking a ledger to recompute its derived balances requires `expected_ledger_version` matching the current `version` of the `Ledger`, because recomputation is only meaningful against the version the caller actually reconciled; a stale request is rejected with `ERR_STALE_VERSION` and HTTP 412 rather than being allowed to restore balances over postings the caller never saw.

Three further write paths carry a version field for reasons other than the three rules above: closing a period on a ledger carries `expected_ledger_version`, voiding a posted transaction carries `expected_ledger_version` because the void mutates the ledger's balances, and the statement reconcile and statement revise commands each carry an optional `expected_statement_version` carrying the caller's last-observed revision of the statement, honoured when supplied and skipped when omitted. Payment-order approval, dispatch, return and reverse each carry `expected_payment_order_version` carrying the caller's last-observed `version` of the order. For all of these the mismatch behaviour is uniform: the request is rejected with `ERR_STALE_VERSION` and HTTP 412. The same error identifier also covers the case in which a statement revision is proposed against a supplied `revision_number` that does not equal the statement's persisted `revision_number`; the `revision_number` field is optional on the revise command and is honoured only when supplied.

### 2.8. Access Control Across the Institution Graph

`LegalEntity` rows are the institutions of the platform. An institution is registered with a `legal_name` and a `short_code`, the latter being unique across all institutions. Its `entity_type` is either `PLATFORM` or `ORGANISATION` and defaults to `ORGANISATION`; a `PLATFORM` row books nothing itself, whereas an `ORGANISATION` row must name its `home_ledger_id`, the ledger in which that institution books its own payment operations. The `home_ledger_id` is required when `entity_type` is `ORGANISATION` and is recorded for a `PLATFORM` row only if it was supplied. Each institution also carries a `default_velocity_limit_cents`, the half-open upper bound applied to a payment order when no counterparty-specific limit row exists for that payee; it defaults to 5000000 cents. An institution may additionally be registered with an optional `timezone` naming one of `America/New_York`, `America/Chicago` or `Europe/London`. When present it is the first choice for the local timezone that anchors the ledger-side aging count and the period-close day boundary described in §3.8 and §3.9, ahead of any calendar cell published for the institution; cutoff resolution under §3.4 is unaffected and continues to read the timezone of the calendar cell it resolves against.

`Counterparty` rows are payees and payers. Each carries a `legal_entity_id` naming the institution that owns the payment relationship, a `display_name` used on instructions and statements, and an `external_ref` whose uniqueness scope is the owning institution rather than the whole platform. A counterparty also carries an optional `velocity_limit_cents`, which is a half-open upper bound for a single payout to that counterparty; when it is null the counterparty inherits its legal entity's `default_velocity_limit_cents`. Counterparty posture is a four-value enum: `status` is one of `ACTIVE`, `RESTRICTED`, `BLOCKED` or `CLOSED`, and it begins at `ACTIVE`.

`CounterpartyRelationship` rows join two institutions. Each row names a `legal_entity_id` on one side — the party that shares its account data — and a `partner_legal_entity_id` on the other; the two must differ, so a self-relationship is rejected. Each relationship declares a `purpose` of `ACCOUNT_SHARING`, `PAYMENT_RAIL_AGREEMENT` or `DISPUTE_CHANNEL`, and an `account_data_sharing` boolean defaulting to false. When `account_data_sharing` is true, the bank accounts owned by the `partner_legal_entity_id` side become readable by the `legal_entity_id` side. A relationship's `status` runs `PENDING` then `ACTIVE` then `SUSPENDED` then `TERMINATED`, beginning at `PENDING`. Once one relationship for a given institution pair is `ACTIVE`, a second cannot be: attempting to create a competing relationship on an already-active pair is rejected with `ERR_RELATIONSHIP_ALREADY_ACTIVE`, and an activation that would duplicate the grant is caught by the stale-version rule described in §2.7.

`BankAccount` rows are the real accounts money actually moves through. Each names its owning `legal_entity_id`, the `institution_name` of the holding bank, a `routing_number` which must be exactly nine digits satisfying the ABA weighted mod-10 checksum, and `account_number_last4` which must be exactly four digits. The `supported_rails` array is a non-empty subset of `ACH`, `WIRE`, `RTP` and `CHECK`, and a rail outside that set is rejected for any payment order that debits or credits the account. Bank account `status` is `OPEN` or `CLOSED` and starts at `OPEN`. Bank accounts also carry an `available_funds_cents` figure, which is what the check-rail sufficiency test and the settlement-pool health test are computed from.

`CounterpartyUser` identity is the one place where `X-User-ID` is compared against persisted data: the value must be an existing `Counterparty` id, and a `CounterpartyUser` reads only the payment orders addressed to its own counterparty, the release requests concerning that counterparty, and its own counterparty record.

### 2.9. Rail Cutoffs and the Banking Calendar

A `BankingCalendar` cell describes one institution's operating posture on one local date. Each cell names its `legal_entity_id`, the `calendar_date` it describes — at most one cell may exist per institution-and-date pair — a `timezone` which must be one of `America/New_York`, `America/Chicago` or `Europe/London`, and an `is_open` boolean. When `is_open` is false the institution does not process payments that date, and that fact outranks the weekday rule used by the business-day aging calculation, so a closed Monday is not counted as a business day. Each cell carries a `cutoffs` array of rail-and-time pairs: a rail that is absent from that array is simply not processed on that date and is therefore not a candidate when a payment order resolves its due moment. The cell also carries `allowed_rails`, the rails admissible on that date, which must be a non-empty subset of the rails named in `cutoffs`.

Resolution of an order's due moment is described in §3.4, where the four-calendar-day lookahead and the inclusive-at-cutoff comparison are stated in full.

### 2.10. Validation Cascade

The API evaluates a request against a fixed, ordered cascade of checks, and the ordering is part of the contract because more than one check can fail at once. First, the two context headers must be present and the role must be a declared role, else `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER`. Second, the caller's role must appear in the endpoint's authorized-role list, else `ERR_FORBIDDEN_FOR_ROLE`. Third, on the endpoints whose authorized-role list contains exactly one role, the caller's role must be that role before any further check runs, else `ERR_FORBIDDEN_FOR_ROLE`. Fourth, referenced resources must exist, and existence is validated left to right in the request-body order declared for the endpoint, with the ledger segment of a path validated before the resource segment beneath it. Each absent parent is reported as its own entity-specific not-found error rather than as a generic not-found, and every one of them carries HTTP status 404: a missing institution is reported as `ERR_LEGAL_ENTITY_NOT_FOUND`, a missing ledger as `ERR_LEDGER_NOT_FOUND`, a missing counterparty as `ERR_COUNTERPARTY_NOT_FOUND`, a missing real account as `ERR_BANK_ACCOUNT_NOT_FOUND`, a missing virtual account as `ERR_VIRTUAL_ACCOUNT_NOT_FOUND`, a missing statement as `ERR_BANK_STATEMENT_NOT_FOUND`, a missing payment order as `ERR_PAYMENT_ORDER_NOT_FOUND`, a missing ledger entry as `ERR_TRANSACTION_NOT_FOUND`, a missing exception as `ERR_EXCEPTION_NOT_FOUND`, and a missing release request as `ERR_RELEASE_REQUEST_NOT_FOUND`. Fifth comes the state gate, sixth the settlement-axis gate, and then the business checks in the order given in §3.10.

A malformed request — an unparseable body, a missing required field, a field of the wrong type, or a `return_reason` that is not one of `R01` through `R10` or `CHK_RETURNED` — is rejected with `ERR_INVALID_REQUEST` and HTTP 400. A request that targets a resource which exists but sits in a state from which the requested transition is not declared is rejected with `ERR_INVALID_TRANSITION` and HTTP 409. A request that is legal on a transaction's lifecycle axis but illegal on its settlement axis is rejected with `ERR_INVALID_SETTLEMENT_AXIS` and HTTP 409; voiding requires `settlement_status` to be `UNSETTLED`, and reversing a payment order requires `settlement_status` to be `SETTLED`. A request that tries to move a resource out of a terminal state is rejected with `ERR_ALREADY_TERMINAL` and HTTP 409.

### 2.11. Ledger Integrity, Fiscal Guardrails and the Logical Clock

The double-entry identity of a ledger is an invariant, not a report. Define booked debits as the sum of `amount_cents` over every transaction in the ledger whose `direction` is `DEBIT` and whose `lifecycle_status` is `PENDING` or `POSTED`, and booked credits as the same sum over every transaction whose `direction` is `CREDIT` and whose `lifecycle_status` is `PENDING` or `POSTED`. The invariant is that booked credits minus booked debits equals `posted_balance_cents` plus `pending_balance_cents`, to a tolerance of zero cents. Rows whose `lifecycle_status` is `VOID` or `REJECTED` are excluded from both sides of that identity, so voiding an entry removes its contribution from both sums in the same step and the identity survives the void intact.

A second invariant governs the reverse-rail fee pool. The ledger's `delivered_fee_transfers_cents` plus its `undeliverable_cents` must always equal 25 cents multiplied by the number of return legs that have been resolved on that ledger. The identity holds on the shortfall branch too, which is precisely why a shortfall must be parked in `undeliverable_cents` rather than dropped on the floor. Both invariants are re-derived from the raw rows whenever a ledger recomputation runs; a recomputation that cannot restore either of them reports `ERR_LEDGER_UNBALANCED` with HTTP 409 instead of quietly steering the derived balances toward a number that balances.

Three further guardrails protect the books. A manual posting that would drive `posted_balance_cents` below zero on a ledger whose institution has no overdraft facility is refused with `ERR_BALANCE_WOULD_GO_NEGATIVE` and HTTP 409. A payment order may not be released when its ledger's status is `CLOSED` or when the close pass is mid-flight; that rejection is `ERR_LEDGER_LOCKED` with HTTP 409. And a ledger recomputation that cannot restore either identity reports `ERR_LEDGER_UNBALANCED`, as stated above.

Finally, the system never reads the host clock. Temporal state is held by an injected logical clock whose startup default is exactly `2026-09-01T00:00:00Z`; the clock is set explicitly through an administrative capability that accepts a `to_iso8601` instant and returns the resulting `current_utc` together with the `previous_utc` value it replaced. The clock is strictly monotonic: a request to set it to an instant strictly earlier than the current logical clock is rejected with `ERR_CLOCK_NOT_MONOTONIC` and HTTP 409. Because every cutoff, aging and duplicate-window rule reads this injected value, a test can pin any temporal boundary exactly.

### 2.12. Audit Trail

Every mutating operation appends an `AuditEvent`. An audit event names the `ledger_id` it belongs to, the `actor_user_id` and `actor_role` of the caller that produced it, an `action` verb in dotted lowercase noun-dot-verb form such as `payment_order.created` or `bank_statement.reconciled`, a `target_entity_type` and `target_entity_id` naming what the event concerned, and a `details` object whose default value is the empty object `{}` and which conventionally carries fields such as `from_status`, `to_status` and `amount_cents`. The event's `sequence_number` is a monotonic per-ledger integer starting at 1, assigned in `created_at` ascending order with `sequence_number` ascending as the tie-break, and it is the stable deep-link identity of the event. A UUID `id` is never consulted for ordering or tie-breaking anywhere in this system.

## 3. Business Logic & Workflows

### 3.1. Opening a Ledger and Establishing the Books

A `PlatformAdmin` or a `LedgerController` opens an accounting ledger by supplying a `name` and a `currency` drawn from `USD`, `EUR` or `GBP`. The response carries every derived balance initialised to zero — `pending_balance_cents`, `posted_balance_cents`, `delivered_fee_transfers_cents` and `undeliverable_cents` all begin at 0 — with `period_index` sitting at 1, `period_opened_utc` set to the ledger's own creation instant, `period_closed_through_index` sitting at 0, and `status` at `OPEN`. An `AuditEvent` recording the action `ledger.opened` is appended in the same transaction.

The structure that a ledger books against is built in a specific order. Institutions are registered first: a `PlatformAdmin` supplies a `legal_name` and a `short_code` and may additionally supply a `home_ledger_id`, an `entity_type` and a `default_velocity_limit_cents`; the `entity_type` defaults to `ORGANISATION`, and an `ORGANISATION` row must name its `home_ledger_id` while a `PLATFORM` row may omit it. Bank accounts are registered next, by a `PaymentApprover`, a `LedgerController` or a `PlatformAdmin`, with the owning `legal_entity_id`, the holding bank's `institution_name`, a nine-digit `routing_number` passing the ABA mod-10 checksum, a four-digit `account_number_last4`, the `supported_rails` set and an optional `available_funds_cents`. Counterparties come next: a `PaymentInitiator`, a `PaymentApprover` or a `PlatformAdmin` supplies the owning `legal_entity_id`, a `display_name`, an `external_ref` and an optional `velocity_limit_cents`, and the counterparty is born at `ACTIVE`.

Business intent is then expressed as a `PaymentOrder`, and the platform is deliberately strict about which entity may express it. Only a `PaymentInitiator` may draft a payment order. The draft carries the `legal_entity_id` that is originating the payment, the `ledger_id` it books into, the `counterparty_id` that is the payee for an outbound order or the payer for an inbound one, the `source_account_id` that is debited for outbound orders and credited for inbound ones, the `rail`, the `direction`, and the gross `amount_cents`. The `direction` is `CREDIT` for an outbound payout and `DEBIT` for an inbound collection. The `rail` is one of `ACH`, `WIRE`, `RTP` or `CHECK` and must be present in the source account's `supported_rails`. The `direction` is `CREDIT` for an outbound payout and `DEBIT` for an inbound collection, and it may be paired with any of the four rails. The order is created in the `PENDING_APPROVAL` state with its settlement axis at `UNSETTLED`, its `initiator_user_id` taken from the caller's `X-User-ID`, and its `approver_user_id` left null.

Two optional fields shape how and when the payment will eventually move. `settlement_speed` is `STANDARD` or `SAME_DAY` and defaults to `STANDARD`; `SAME_DAY` is admissible only on the `ACH` rail and it changes both the cutoffs that apply and the fee schedule that will be charged. `requested_release_utc` names an optional future instant at which the payment should attempt release; when it is omitted, release is due at `cutoff_snapshot_utc`, which is the earliest candidate among the order's resolved `cutoffs`, and never at some unstated default. A `CHECK` order additionally requires a `payable_to_name`, and the `idempotency_key` field is mandatory on every draft.

An audit event recording the action `payment_order.created` is appended when the draft is accepted, and the order's `cutoffs` array — populated by the cutoff-resolution rule described in §3.4 — is returned in the create response.

### 3.2. Account Topology: Counterparties, Relationships and Virtual Accounts

Counterparty posture is maintained exclusively by a `PaymentApprover`. A counterparty moves from `ACTIVE` to `RESTRICTED` when a `PaymentApprover` restricts it — and the same posture change is also the compulsory cascade described in §3.5 when a draft is cancelled or a returned amount crosses a threshold. A counterparty may additionally be moved to `BLOCKED` from either `ACTIVE` or `RESTRICTED`, and from `BLOCKED` it can be moved back to `RESTRICTED` but never directly to `ACTIVE`. A `RESTRICTED` counterparty is restored to `ACTIVE` by a deliberate restore action. Closing a counterparty moves it to `CLOSED`, which is terminal, and it is permitted only when no payment order referencing that counterparty sits in a status other than `SETTLED`, `RETURNED`, `REVERSED` or `CANCELLED`; a counterparty that still has a live order cannot be closed and the attempt is refused with `ERR_COUNTERPARTY_NOT_SETTLED` and HTTP 409. Restricting, blocking, unblocking, restoring and closing each append their own audit action, being respectively `counterparty.restricted`, `counterparty.blocked`, `counterparty.unblocked`, `counterparty.restored` and `counterparty.closed`.

Institution-to-institution relationships are requested by a `PaymentApprover`, a `PaymentInitiator` or a `PlatformAdmin` and are born at `PENDING`. The request carries the `legal_entity_id` on one side, a `partner_legal_entity_id` on the other that must differ from it, a `purpose` of `ACCOUNT_SHARING`, `PAYMENT_RAIL_AGREEMENT` or `DISPUTE_CHANNEL`, and an optional `account_data_sharing` flag defaulting to false. Activation is reserved to a `PaymentApprover`, and it is gated on a condition that ties payment operations to account-sharing hygiene: every `UNMATCHED_DEPOSIT`-kind exception on the ledger of either side must already be `RESOLVED` or `WAIVED`, because an institution may not begin sharing account data while an unattributed deposit is still open; when the gate fails the activation is refused with `ERR_LEDGER_UNBALANCED` and HTTP 409, and the same condition and the same error guard a suspended relationship's return to `ACTIVE`. The error identifier `ERR_UNATTRIBUTED_DEPOSIT_OPEN` is declared with HTTP 409 in §5 but is not emitted by any path: every unattributed-deposit guard is the activation gate itself, which reports `ERR_LEDGER_UNBALANCED` for the cause, so the two identifiers do not split the condition between them. An `ACTIVE` relationship may be suspended, and a `SUSPENDED` one reactivated; terminating moves an `ACTIVE` relationship to `TERMINATED`, which is terminal. Activation also requires `expected_relationship_version` matching the relationship's current `version`, as §2.7 explains.

Inbound money is attributed through `VirtualAccount` rows carved out of a pooled real account. A `PaymentOpsAnalyst`, `PaymentApprover` or `PlatformAdmin` allocates one by supplying the `bank_account_id` of the pooled account, a `virtual_account_number` of ten to sixteen digits which is unique across all virtual accounts, and a `reference_code` of six to twelve uppercase alphanumeric characters that a payer can embed in a remittance field so that an unmatched deposit can be attributed without human intervention. A virtual account is born `OPEN` and a `PaymentOpsAnalyst` or `PlatformAdmin` may close it, after which it stops participating in deposit attribution entirely: a `CLOSED` virtual account is excluded from every branch of the attribution rule in §3.7.

### 3.3. The Settlement Rails: Fees, Speed and Cutoffs

Outbound money leaves through exactly one of four rails, and the fee the platform charges is a function of that rail, the order's `direction` and its `settlement_speed`. The base fee is 25 cents for a standard ACH order and 500 cents for a same-day ACH order. A real-time order's base fee is 75 cents plus 100 cents for every complete 1000000-cent tranche of `amount_cents`, the tranche count being obtained by integer floor division of the amount by 1000000. A wire's base fee is 500 cents plus 250 cents for every complete 1000000-cent tranche of `amount_cents`, again by integer floor division. A check's base fee is 350 cents when the order direction is `DEBIT` and 150 cents when it is `CREDIT`.

Two adjustments follow the base. First, a direction adjustment: when the direction is `CREDIT` and the rail is `ACH` or `RTP`, 25 cents are subtracted from the running total. Second, a rail cap applied after that adjustment: the total may not exceed 400 cents on `ACH`, 2500 cents on `WIRE`, or 250 cents on `RTP`, and `CHECK` has no cap at all. A floor is then applied last, so that the final `fee_total_cents` is the larger of the running total and 10 cents. The ordering is load-bearing: because the cap is applied after the direction adjustment and before the floor, a capped-then-floored fee can never fall below 10 cents, and a large `CREDIT` wire can never exceed 2500 cents.

Settlement speed is admissible only where the rail supports it. `SAME_DAY` is valid when the order's `rail` is `ACH` and nowhere else; drafting a payment order whose `settlement_speed` is `SAME_DAY` on the `WIRE`, `RTP` or `CHECK` rail is refused with `ERR_SETTLEMENT_SPEED_UNSUPPORTED` and HTTP status 422.

The fee is booked as a single ledger entry. At dispatch the platform emits exactly one `FEE` `Transaction` whose `net_effect_cents` is the negative of `fee_total_cents` — the whole fee in one entry, never a series. The operator-facing presentation may itemise that same total as a breakdown of wire milestone tranches, emitting one component of 500 cents plus 250 cents for every complete 1000000-cent tranche of the amount; the components sum to the identical total, so the ledger effect is the same while the reported line count is not. A fee leg created alongside a return is a flat 25 cents regardless of rail.

The rail-specific validation that guards dispatch is described in §3.5, and the rail-cutoff resolution that determines when an order becomes due is described in §3.4.

### 3.4. Cutoff Resolution and the Banking Calendar

Every payment order carries a `cutoffs` array and a `cutoff_snapshot_utc`, both computed at creation and both recomputed whenever a pending order's cutoffs are refreshed. The candidates are the banking calendar cells of the institution that owns the order's `source_account_id`, restricted to cells whose `calendar_date` falls between the local date of the order's opening instant and that date plus four calendar days inclusive, and further restricted to cells whose `allowed_rails` contains this order's `rail`. For each such candidate cell the eligible moment is the cell's `cutoff_local_time` when the order's opening local time is at or before that cutoff, and otherwise it is `cutoff_local_time` plus one day, which must itself fall on an open calendar cell. The due moment is the minimum eligible moment across all candidates, and `cutoff_snapshot_utc` is that due moment converted to UTC in the institution's timezone; the local timezone of a cell is the timezone the cell itself declares, falling back to `America/New_York` when the institution has published no cell at all. Each element of the order's `cutoffs` array reports the order's `rail`, the resolved cutoff instant under the key `cutoff_utc`, and a `calendar_code` for the cell it came from, so the array is a renderable list of rail-and-instant pairs rather than the raw cells. An order whose `requested_release_utc` is already past the due moment therefore belongs to the institution's next open cycle rather than the current one, which is why a Friday-evening order rolls forward to Monday instead of landing on a weekend date.

The comparison at the cutoff is inclusive: an order opened at exactly a cell's `cutoff_local_time` on an open day is admitted to that day's cycle. The reader should note the deliberate inversion with the velocity limit described in §3.5 — that comparison is strict — so a test written for one boundary commits the wrong operator for the other.

When no open calendar cell for the order's rail exists anywhere inside the four-day lookahead window, the draft cannot be created at all and is refused with `ERR_CALENDAR_HAS_NO_OPEN_CYCLE` and HTTP 409. Institutions manage their own calendars through cell publication: a `LedgerController`, `PlatformAdmin` or `PaymentApprover` publishes a cell carrying its `legal_entity_id`, `calendar_date`, `timezone`, `is_open` flag, `cutoffs` array and `allowed_rails` set, subject to the one-cell-per-institution-per-date rule and the rule that `allowed_rails` must be a non-empty subset of the rails named in `cutoffs`. Reading calendar cells is available to a `PaymentInitiator` as well, and cells can be filtered by `legal_entity_id`, a `from_date` and `to_date` range, and the `is_open` flag; the same date-range filtering is exposed for one institution's cells. Both calendar list endpoints depart from the §2.3 default ordering and return their cells in `calendar_date` ascending order, with the creation ordinal as the tie-break, because a calendar is read as a timeline rather than as a log.

### 3.5. The Payment Order Lifecycle: Release, Dispatch and Termination

A drafted order sits at `PENDING_APPROVAL` until a `PaymentApprover` releases it. Releasing an order is the highest-stakes call in the system and is therefore evaluated against a fixed, ordered set of checks rather than a shapeless pile of conditions. The order of evaluation is: the velocity and amount check first, then the counterparty-posture check, then the separateness check, and finally the ledger-availability check. Because the counterparty check precedes the separateness check, a counterparty that is not `ACTIVE` is reported as `ERR_COUNTERPARTY_BLOCKED` with HTTP 409 even when the approver would also fail the separateness rule; and because the separateness check is the last business check among the first three, `ERR_SELF_APPROVAL_FORBIDDEN` is reported only when no earlier business rule already rejected the release. It carries HTTP status 403.

The velocity check itself is a case of the effective-limit rule. The effective limit for an order is the counterparty's own `velocity_limit_cents` when that field is not null, and otherwise it is the counterparty's legal entity's `default_velocity_limit_cents`; where the platform supplies a fallback it is 5000000 cents. An order is admitted only when its `amount_cents` is strictly less than that effective limit, so an order whose amount exactly equals the limit is refused with `ERR_VELOCITY_LIMIT_EXCEEDED` and HTTP 409 while an order one cent below the limit is admitted, and an amount of zero or less is refused with the same error. This is the strict comparison whose inversion with the inclusive cutoff comparison was flagged in §3.4.

The counterparty check requires `Counterparty.status` to be exactly `ACTIVE`. The separateness check requires that the `X-User-ID` of the approving operator differ from the order's `initiator_user_id`; this is the regime's segregation-of-duties rule, and it is also why `PaymentInitiator` is absent from every release endpoint's authorized-role list — the draft's author simply has no standing to release it. The ledger-availability check refuses the release when the order's `ledger_id` names a ledger whose status is `CLOSED` or when the close pass is still running, reporting `ERR_LEDGER_LOCKED` with HTTP 409. The state gate precedes all of these: releasing an order that is not at `PENDING_APPROVAL` yields `ERR_INVALID_TRANSITION` with HTTP 409.

On success the order moves `PENDING_APPROVAL` → `APPROVED`, its `approver_user_id` is stamped with the caller's `X-User-ID`, and its `version` advances by one. Approval carries a withdrawal cascade that is easy to miss: because the approver has now consumed a release slot in the pool, every still-pending `ReleaseRequest` whose `initiator_user_id` equals that same approver is denied, and each such denial is surfaced as `ERR_APPROVAL_POOL_WITHDRAWN` with HTTP 409. An audit event recording `payment_order.approved` is appended, carrying the approver in its `details`.

A `ReleaseRequest` is the instrument by which a second operator can be asked to release a payment, and it is raised by a `PaymentInitiator` or a `PaymentApprover`. The request names the `payment_order_id` whose release is sought, the `counterparty_id` whose funds the request concerns, the `needed_by_utc` instant by which the requesting operator needs the release, and a free-text `reason` recorded for audit; its `initiator_user_id` is taken from the caller's `X-User-ID`, and the pool eligible to satisfy it is every `PaymentApprover` whose `X-User-ID` differs from that value. A request is born at `request_state` `PENDING` and moves to exactly one of `SATISFIED`, `DECLINED` or `DENIED`. It becomes `SATISFIED` as a cascade of the linked order settling, `DECLINED` as a cascade of the linked order being reversed, and `DENIED` as a cascade of the linked order being approved by an operator whose `X-User-ID` equals the request's own `initiator_user_id` — the withdrawal cascade described below. A `PaymentInitiator` or a `PaymentApprover` may also cancel a pending request directly, which sets its `request_state` to `DENIED` and appends an audit event recording `release_request.cancelled`. Raising a request appends an audit event recording `release_request.raised`. The queue of requests is readable by a `PlatformAdmin`, `LedgerController`, `PaymentOpsAnalyst`, `PaymentOpsApprover`, `PaymentApprover`, `PaymentInitiator`, `CounterpartyUser` and `Auditor`, filterable on `payment_order_id`, `counterparty_id` and `request_state`, and a `CounterpartyUser` reads only those requests concerning its own counterparty.

An `APPROVED` order is pushed onto its rail by a `PaymentApprover`. Dispatch is a genuine four-way fork. The `rail` recorded on the order selects exactly one of four destination states — `ACH_DISPATCHED`, `WIRE_DISPATCHED`, `RTP_DISPATCHED` or `CHECK_DISPATCHED` — and all four branches converge afterwards on the shared `IN_FLIGHT` state. The branches differ only in their validation and in which branch of the fee schedule is applied; every branch creates the same trio of consequences.

The validation on every branch is the same three-part rail test. The order's `rail` must be present in the source account's `supported_rails`; the source account must belong to the order's `legal_entity_id`; and a `CHECK` order must already carry a `payable_to_name`. Any of these failing yields `ERR_RAIL_ACCOUNT_UNSUPPORTED` with HTTP 422. A separate fiscal precondition then applies: the source account's forced settlement status must not be `FAILED`, and for the `CHECK` rail the source account's `available_funds_cents` must be at least the order amount plus its fee; breaching either is reported as `ERR_SETTLEMENT_POOL_INSUFFICIENT` with HTTP 409. Dispatch also refreshes the ledger-availability check, so `ERR_LEDGER_LOCKED` can surface here as well.

The three consequences shared by all four branches are identical, and it is worth stating them once for all four destinations. An `ORIGINATING` `Transaction` is created with `lifecycle_status` at `PENDING`, `settlement_status` at `UNSETTLED`, and a `net_effect_cents` that is the negative of `amount_cents` for a `CREDIT` order and the positive of `amount_cents` for a `DEBIT` order. A `FEE` `Transaction` is created with a `net_effect_cents` equal to the negative of the fee computed by that rail's branch of the fee schedule — the whole fee in one entry, as §3.3 sets out. The two legs of a dispatch are created in one step and are stamped with the same `value_effective_utc`, the logical clock instant of the dispatch itself, so the booking is dated to the moment the dispatch ran rather than to the order's creation or its due moment. A `ReleaseRequest` is created for the linked counterparty with its `request_state` at `PENDING`; it is stamped with the dispatching operator as its `initiator_user_id`, so the pool eligible to satisfy it is every `PaymentApprover` whose identity differs from the dispatcher's. The order's `settlement_status` then moves to `IN_SETTLEMENT`, the ledger's `pending_balance_cents` is recomputed, the ledger's `version` advances by one, the order's `version` advances by one, and an `AuditEvent` recording `payment_order.dispatched` is appended. So the `ACH` dispatch moves the order `APPROVED` → `ACH_DISPATCHED` and books the ACH credit branch of the fee schedule, the `WIRE` dispatch moves it `APPROVED` → `WIRE_DISPATCHED` and books the whole wire fee as one `FEE` entry with `net_effect_cents` equal to the negative of the wire total rather than as a tranche series, the `RTP` dispatch moves it `APPROVED` → `RTP_DISPATCHED` and books the real-time credit branch, and the `CHECK` dispatch moves it `APPROVED` → `CHECK_DISPATCHED` and books the check credit branch. Each of the four also creates its own `ORIGINATING` leg, its own `ReleaseRequest` at `PENDING`, and its own `IN_SETTLEMENT` settlement axis, with no branch treated more lightly than another.

From the rail-specific dispatched state the order joins the shared in-flight state. This join is a `PaymentOpsAnalyst` capability with no preconditions beyond the state gate: it accepts an order in any of `ACH_DISPATCHED`, `WIRE_DISPATCHED`, `RTP_DISPATCHED` or `CHECK_DISPATCHED` and moves it to `IN_FLIGHT`.

`IN_FLIGHT` has two exits, and both are worked by a `PaymentOpsAnalyst`. Settlement moves the order `IN_FLIGHT` → `SETTLED`, sets its settlement axis to `SETTLED`, and drags the order's own legs with it: every `ORIGINATING` and `FEE` transaction belonging to the order that is currently `IN_SETTLEMENT` moves to `SETTLED`. The linked `ReleaseRequest`, if it is still at `PENDING`, becomes `SATISFIED`. The ledger's `posted_balance_cents` is recomputed, the order's `version` advances, and an audit event recording `payment_order.settled` is appended. Settlement is additionally blocked when the order already carries a `return_reason`: settling an order that has been marked for return is refused with `ERR_INVALID_TRANSITION` and HTTP 409, as is settling an order that is not `IN_FLIGHT`.

Return is the other exit and it is the more intricate one. A `PaymentOpsAnalyst` returns an `IN_FLIGHT` order by supplying a `return_reason` that must be one of the ten ACH return codes `R01` through `R10` or the check-return code `CHK_RETURNED`; anything else is refused with `ERR_INVALID_REQUEST` and HTTP 400, and a return against an order that is not `IN_FLIGHT` is refused with `ERR_INVALID_TRANSITION` and HTTP 409. The order moves `IN_FLIGHT` → `RETURNED`, which is terminal for that order, and its `return_reason` is recorded. For every `ORIGINATING` or `FEE` leg of the order that is still `IN_SETTLEMENT`, a compensating `RETURN` `Transaction` is created in the same ledger with a `net_effect_cents` that is the negation of the leg's own `net_effect_cents`, a `lifecycle_status` of `POSTED` and a `settlement_status` of `UNSETTLED`; the compensating leg records the reversed leg in its `refunds_transaction_id`. Each such return leg is atomically paired with a `FEE` transaction booked at a flat 25 cents with direction `CREDIT`; the pair exists so that the reverse-rail fee invariant of §2.11 can be evaluated at all. The ledger's `pending_balance_cents` is recomputed, the order's `version` advances, and an `ExceptionItem` of kind `RETURN` is raised in status `OPEN` with `aging_bucket` `CURRENT` for the order's own `amount_cents`, so the item locks the order's gross rather than the sum of its legs.

Return carries one conditional cascade that reaches beyond the order. When the returned `amount_cents` is at or above 100000 cents, the linked counterparty is moved `ACTIVE` → `RESTRICTED`, and that posture change in turn suspends every one of its `ACTIVE` `ACCOUNT_SHARING` relationships — the same relationship cascade described in §3.2 and §3.9.

Reversal is reserved for an order that has actually reached `SETTLED`. A `PaymentOpsAnalyst` may reverse such an order only when its settlement axis is `SETTLED` and only when it reached that state at least once through a settlement action; an order that never settled cannot be reversed, and the attempt is refused with `ERR_INVALID_TRANSITION` and HTTP 409. This is also the settlement-axis gate of §2.10 in action: the state gate on the lifecycle axis precedes it, and the axis gate refuses a reverse whose order is not `SETTLED` with `ERR_INVALID_SETTLEMENT_AXIS` and HTTP 409. On success the order moves `SETTLED` → `REVERSED`, a `REVERSAL` `Transaction` is created already `POSTED` and already `SETTLED` with a `net_effect_cents` equal to the negative of the order's settled net, the ledger's `posted_balance_cents` is recomputed, the linked `ReleaseRequest` becomes `DECLINED`, the order's `version` advances, and an `ExceptionItem` of kind `REVERSAL` is raised in status `OPEN` with `aging_bucket` `CURRENT`, locking the order's own `amount_cents` as the `RETURN` item does.

An `IN_FLIGHT` order can also fail. A `PaymentOpsAnalyst` supplies a `failure_reason`, the order's settlement axis moves to `FAILED`, every one of its legs that is in `IN_SETTLEMENT` returns to `UNSETTLED` so that a later re-dispatch can settle it, and an `ExceptionItem` of kind `FAILED_PAYMENT` is raised in status `OPEN`, again locking the order's own `amount_cents`. A failed payment's exception resolves itself when its order eventually settles: a settle pass that finds an `OPEN`, `ASSIGNED` or `ESCALATED` `FAILED_PAYMENT` item naming that order moves it to `RESOLVED` and notes that the payment order settled, even though that settlement path is not the resolution endpoint described in §3.8 and does not itself advance the ledger's `version`.

The last exit belongs to the initiator. A `PaymentInitiator` may cancel an order that is still at `PENDING_APPROVAL`, and only when the caller's `X-User-ID` equals the order's `initiator_user_id`; violating that ownership requirement is reported as `ERR_FORBIDDEN_FOR_ROLE` with HTTP 403, and cancelling an order that has already left `PENDING_APPROVAL` is reported as `ERR_INVALID_TRANSITION` with HTTP 409. Once the order is in one of its four terminal statuses the attempt is reported as `ERR_ALREADY_TERMINAL` with HTTP 409. Cancellation is not a local edit: it moves the order to `CANCELLED`, moves the linked `Counterparty.status` to `RESTRICTED` so that the payee relationship is frozen pending operations review, and resets every still-`OPEN` `ExceptionItem` of kind `FAILED_PAYMENT` that names this order — restoring its status to `OPEN` and clearing its `assignee_user_id` to null — while leaving the item's `opened_utc` untouched, so its `aging_bucket` continues to be derived from the instant the exception was first raised rather than from the cancel.

No transition in this lifecycle is idempotent. Settling an order that is already `SETTLED`, returning one that is already `RETURNED`, dispatching one that has already been dispatched, or approving one that is no longer `PENDING_APPROVAL` all return `ERR_INVALID_TRANSITION` with HTTP 409. The four dispatch branches differ only in rail validation and in the fee branch they select, and all four converge on `IN_FLIGHT`, whose settlement and return exits are shared.

### 3.6. Double-Entry Postings and the Two Settlement Axes

The unit of accounting is the `Transaction`, and its most important property is that it carries two independent state dimensions on the same row. The lifecycle axis, `lifecycle_status`, runs `PENDING` → `POSTED` → `VOID`, with a `PENDING` → `REJECTED` branch; its terminal states are `VOID` and `REJECTED`. It moves only by an explicit settlement decision and never by the calendar. The settlement axis, `settlement_status`, runs `UNSETTLED` → `IN_SETTLEMENT` → `SETTLED` and is evaluated entirely independently of the lifecycle axis. Because the two dimensions are genuinely independent, a reversal of a not-yet-settled entry changes only one of them.

Every posting names its `ledger_id`, its `entry_type` — one of `ORIGINATING`, `RETURN`, `REVERSAL`, `FEE`, `ADJUSTMENT` or `DEPOSIT` — its `direction` of `DEBIT` or `CREDIT`, its `amount_cents` which must be strictly greater than zero, and its `value_effective_utc`, the business instant of the posting that is used for period assignment and statement-cycle filtering and which is deliberately distinct from `created_at`, the audit instant. A posting made for a payment order carries the order's id in `payment_order_id`; a posting booked by hand carries null there. Two self-referential foreign keys tie compensating entries to their targets: `reverses_transaction_id` names the post-settlement entry this row reverses and is required when `entry_type` is `REVERSAL` while it must be null for every other entry type; `refunds_transaction_id` names the unsettled entry this row cancels and is required when `entry_type` is `RETURN` while it must be null otherwise. The signed effect of the row is carried by `net_effect_cents`, which is the negative of `amount_cents` when the direction is `DEBIT` and the positive of `amount_cents` when the direction is `CREDIT`. `ADJUSTMENT` and `DEPOSIT` entries arise when operations books a correction or recognises an inbound deposit directly.

Manual postings, also known as adjustments, are booked by a `LedgerController` or a `PaymentOpsAnalyst` through a ledger-scoped entry point. Such an entry begins its life with `lifecycle_status` at `PENDING` and `settlement_status` at `UNSETTLED`, and books into `pending_balance_cents`. Because a manual posting changes the posted book's exposure as well, the ledger refuses it with `ERR_BALANCE_WOULD_GO_NEGATIVE` and HTTP 409 when it would drive `posted_balance_cents` below zero on a ledger whose institution has no overdraft facility; the guard is about withdrawing funds the ledger has actually settled, so it bites only when the posting would push an already-positive posted book negative — a ledger with nothing settled has no settled funds for the posting to withdraw, and the pending-only postings and the `ADJUSTMENT`/`REVERSAL` compensation pairs of this section therefore book freely. A manual posting whose `value_effective_utc` falls at or before the close instant of the ledger's `period_closed_through_index` is refused with `ERR_PERIOD_CLOSED` and HTTP 409. The ledger segment of the path is validated before the body's foreign keys, so a request naming a non-existent ledger reports `ERR_LEDGER_NOT_FOUND` rather than a missing counterparty.

Moving a `PENDING` entry to `POSTED` is a `PaymentOpsAnalyst` and `LedgerController` capability. It is refused with `ERR_INVALID_TRANSITION` and HTTP 409 when the entry is not `PENDING`, refused with `ERR_PERIOD_CLOSED` and HTTP 409 when the entry's `value_effective_utc` falls at or before the close instant of the ledger's `period_closed_through_index`, and refused with `ERR_INVALID_REQUEST` and HTTP 400 when the entry is a `RETURN` or a `REVERSAL` whose referenced counterpart entry does not exist in the same ledger. On success the row's `lifecycle_status` becomes `POSTED`, and both the ledger's `pending_balance_cents` and its `posted_balance_cents` are recomputed across both settlement partitions.

Rejecting a `PENDING` entry is the same pair of roles' capability and requires only that the row be `PENDING`. A reject moves the row to `REJECTED`, which is terminal; the row is retained on disk but excluded from every balance projection, and the ledger's `pending_balance_cents` is recomputed without it. A `POSTED` entry may instead be voided, and voiding is exclusive to a `LedgerController`. A void requires the row to be `POSTED`, requires its settlement axis to be `UNSETTLED` so that an already-settled entry cannot be erased, and carries one subtle prohibition: a `POSTED` transaction of `entry_type` `ORIGINATING` that entered the `POSTED` lifecycle through the reversal command must be voided through that same command and not through the ordinary void path, an attempt that is refused with `ERR_INVALID_TRANSITION`. A void sets the row's `lifecycle_status` to `VOID`, recomputes the ledger's `pending_balance_cents` with the row contributing zero, advances the ledger's `version`, and carries the `expected_ledger_version` field described in §2.7. Rejections and voids both append their own audit actions.

A manual entry whose `payment_order_id` is null may also be settled directly, bypassing the rail round trip entirely; a `PaymentOpsAnalyst` or `LedgerController` moves its settlement axis to `SETTLED`, which increments `posted_balance_cents` by its `net_effect_cents` and decrements `pending_balance_cents` by the same amount. Direct settlement is guarded on three grounds: a row that still carries a `payment_order_id` is refused with `ERR_INVALID_REQUEST` and HTTP 400, because the command is reserved for hand-booked entries; a row whose entry lifecycle is `VOID` or `REJECTED` is refused with `ERR_INVALID_TRANSITION` and HTTP 409; and a row whose settlement axis is already `SETTLED` is refused with `ERR_INVALID_TRANSITION` as well, because a settlement is not repeatable. Both the `PENDING` and the already-`POSTED` lifecycle are admissible for the settlement itself.

Both derived ledger balances are projections of the same transaction population. `pending_balance_cents` is the signed sum of `net_effect_cents` over every transaction of the ledger whose `settlement_status` is `UNSETTLED` or `IN_SETTLEMENT`; `posted_balance_cents` is the signed sum over every transaction whose `settlement_status` is exactly `SETTLED`. Rows whose `lifecycle_status` is `VOID` or `REJECTED` contribute zero to both sums. Debit and credit entries are peers in one population rather than separate books, so an unsettled outbound credit leg is already a negative contribution to the pending book and moves into the posted book carrying that same sign once it settles. No sign flip happens at settlement. The projection is refreshed inside the request that caused it, so the response to that request already carries the new balances.

The two consumer-facing variants of that projection are worth distinguishing. The provisional view is what an operator sees while payments are still in flight; it includes `UNSETTLED` and `IN_SETTLEMENT` rows, so a payment that has been dispatched but not yet settled already depresses the balance it reports. The final view is the book of record used for financial reporting; it includes only `SETTLED` rows, so the same ledger reports a materially different number before and after settlement of an identical population. Both variants are exposed as derived balances and period metadata, and both are available in aggregate through a ledger summary view. That view answers with the provisional variant unless the request carries a `settled` flag whose value is true, whether it arrives as a query parameter or in the request body, in which case it answers with the final variant; the summary response reports the `ledger_id`, the `provisional_pending_cents` figure, the `posted_balance_cents` figure, the `opened_exception_count` of exceptions still open on the ledger, and the current `period_index`. The same `posted_balance_cents` figure is also echoed as a `final_posted_cents` key, and the resolved `settled_variant` boolean is reported alongside it, so a caller can read which projection it received without re-deriving it.

The same population also carries the double-entry identity restated in §2.11. Booked credits less booked debits must equal `posted_balance_cents` plus `pending_balance_cents` with a tolerance of zero cents, and identity is maintained incrementally by the mutation handlers themselves on the ordinary path. A ledger recomputation re-derives the identity from the raw rows instead, and reports `ERR_LEDGER_UNBALANCED` with HTTP 409 rather than steering the derived balances when the identity does not hold.

Ledger inspection is broadly available. A ledger's own state, including both derived balances and the current period bounds, is readable by every role except `CounterpartyUser`. The transaction population is readable by a `PlatformAdmin`, `LedgerController`, `PaymentOpsAnalyst`, `PaymentOpsApprover` and `Auditor`, and is returned in `created_at` ascending order with a `created_at`-then-role tie-break so that the legs one dispatch creates appear as `ORIGINATING` before `FEE`. Filtering is available on the `ledger_id`, the `payment_order_id`, the `entry_type`, the `lifecycle_status` and the `settlement_status`, and separately on the polymorphic-owner filters `reverses_transaction_id` and `refunds_transaction_id`. An auditor can additionally ask for a projection of selected postings into their double-entry receipt pairs by supplying a `transaction_ids` list, which is the shape that a receipt-pair view exposes.

### 3.7. Bank Statements, Lines and Reconciliation

Reconciliation begins with a statement import. A `PaymentOpsAnalyst` or a `LedgerController` imports a `BankStatement` for one account and one cycle by supplying the `bank_account_id`, the bank's own `institution_ref`, the `cycle_date` that is the cutoff instant of the cycle, an `opening_balance_cents` and a `closing_balance_cents`, the `matching_algorithm` that this statement will be reconciled under, which defaults to the posted-net variant when the field is omitted, the mandatory `expected_bank_account_version`, and an optional `expected_statement_version`. The newly imported row is born in status `IMPORTED` with `revision_number` at 1 and `supersedes_statement_id` null, and the import increments the owning bank account's `version` by one. Its `institution_ref` must be unique within its `bank_account_id` for `revision_number` equal to 1, one statement may be imported per statement cycle, and `BankStatement` rows are in any case unique on the combination of `bank_account_id`, `institution_ref` and `revision_number`. A duplicate therefore surfaces as `ERR_LINE_ALREADY_MATCHED` with HTTP 409, and a body that carries an unsupported `matching_algorithm` value fails the enumeration check described in §3.10.

The statement's `status` then moves through a lifecycle with a loop in it. From `IMPORTED` a reconciliation run advances it to `RECONCILING`, and the reconciliation executes under the statement's effective algorithm. From `RECONCILING` the run falls through to one of two outcomes: when the recomputed `unmatched_amount_cents` is exactly zero the statement becomes `RECONCILED`, which is terminal, with `matched_posted_cents` pinned and `unmatched_amount_cents` at zero, and an audit event recording `bank_statement.reconciled` is appended; when `unmatched_amount_cents` is anything other than zero the statement becomes `DISCREPANCY` and an `ExceptionItem` of kind `STATEMENT_VARIANCE` is raised against it in status `OPEN` with `aging_bucket` `CURRENT`, with an audit event recording `bank_statement.discrepancy`. A caller who attempts to force a statement into `RECONCILED` while the variance is non-zero is refused with `ERR_STATEMENT_VARIANCE_UNRESOLVED` and HTTP 409.

The whole lifecycle has one global constraint: a statement's lines may only be appended while the statement is still `IMPORTED`. A line appended to a statement that has already left that state is refused with `ERR_STATEMENT_ONLY_MUTABLE_BEFORE_RECONCILE` and HTTP 409. A `PaymentOpsAnalyst` appends a line by supplying its `bank_reference`, the signed `amount_cents` where a positive value means the bank credited the account, the `direction` of `CREDIT` or `DEBIT`, the `effective_at` instant the bank considers the line effective, and an optional `embedded_reference_code` parsed out of the remittance field. The line is born with `match_state` at `UNMATCHED`, and an audit event recording `statement_line.added` is appended. A line's `match_state` is one of `UNMATCHED`, `MATCHED` or `IGNORED`: reconciliation sets it to `MATCHED` when the line is consumed by exactly one settled transaction, leaves it at `UNMATCHED` when no transaction could be paired with it, and `IGNORED` is available for lines an operator has deliberately taken out of the matching population. Line uniqueness is enforced on two axes at once: a `bank_reference` must be unique within its statement, and the triple of `bank_statement_id`, `amount_cents` and `effective_at` must be unique within the statement; either duplication is reported as `ERR_LINE_ALREADY_MATCHED` with HTTP 409.

When a discrepancy is to be corrected, the reconciliation revision loop takes over. A `PaymentOpsAnalyst` or a `LedgerController` creates the next revision of a statement that is in `DISCREPANCY`, supplying an optional `expected_statement_version`, an optional `revision_number`, a fresh `institution_ref`, a fresh `cycle_date`, an `opening_balance_cents` and a `closing_balance_cents`. The command is OCC-guarded in two ways. First, the `revision_number` the caller holds, when it supplies one, must equal the persisted `revision_number` of the predecessor, and a value that trails the persisted one is rejected with `ERR_STALE_VERSION` and HTTP 412 rather than being allowed to fork the bank's line set silently. Second, when `expected_statement_version` is supplied, it must match the predecessor's current `version`; otherwise it is skipped on the same terms as every other guarded path. A `DISCREPANCY` state is likewise required, and anything else is rejected with `ERR_INVALID_TRANSITION` and HTTP 409. On success the predecessor's status becomes `SUPERSEDED`, a new `BankStatement` row is created directly in status `REVISED` with `revision_number` equal to the predecessor's `revision_number` plus one and `supersedes_statement_id` set to the predecessor's id, and the predecessor's `STATEMENT_VARIANCE` exception is resolved with a resolution note recording that it was superseded by revision N plus one. The same command performs a second hop: deposit attribution is re-run over the predecessor's still-unmatched lines, and every line that still resolves to no destination raises an `UNMATCHED_DEPOSIT` exception whose `amount_cents` equals the line's amount. The predecessor's `version` advances by one, and a `REVISED` statement re-enters `RECONCILING` when a fresh reconciliation run is executed against it, incrementing its `version` again. Because the successor is born in `REVISED` and re-enters the loop, a statement may be revised any number of times before it stabilises at `RECONCILED`.

The arithmetic of the reconciliation itself is where the two algorithm variants diverge, and it is worth stating carefully. Lines are processed in `effective_at` ascending order with `bank_reference` ascending as the tie-break. For each line, the candidate set is every transaction in the account's ledger that is `SETTLED`, whose `value_effective_utc` is at or before the statement's `cycle_date`, and whose `created_at` is at or before the line's `effective_at`. A line is matched when exactly one candidate carries a `net_effect_cents` equal to the line's `amount_cents` and, when the statement is being reconciled under the settled-single variant, additionally carries a `value_effective_utc` equal to the line's `effective_at`. Under the posted-net variant the timestamp equality is not required, so a net-settled wire batch whose single bank line carries the batch net matches the sum of several internal legs and reconciles cleanly with `unmatched_amount_cents` at zero. Under the settled-single variant — required for accounts whose bank posts each item individually — the same statement over the same data does not match the batch net line at all, and instead leaves `unmatched_amount_cents` at minus 700000 cents, a 7000.00 gap, so the two algorithms genuinely contradict each other on identical inputs. Switching a statement from one variant to the other therefore changes the reconciled result without changing a single row of data.

An unmatched line is not automatically worthless. When a line fails to match but the candidate set does contain a transaction of equal amount that an earlier line has already consumed, the line is still recorded `UNMATCHED` but its amount is accumulated into an excess bucket, meaning it is an excess bank line. When it fails to match for any other reason, its amount is accumulated into the unattributed bucket, meaning it is a deposit the platform never attributed. Afterwards `matched_posted_cents` is the sum of `net_effect_cents` over the matched transactions, and `unmatched_amount_cents` is the sum of `net_effect_cents` over every settled transaction at or before the cycle date, minus `matched_posted_cents`, minus the excess bucket, plus the unattributed bucket. Because each settled transaction is consumed by at most one line — the first match in `effective_at` ascending order wins it — the matching is exact rather than greedy, and the amount equality test is exact rather than approximate.

The `matched_posted_cents` published on a statement is the sum of `net_effect_cents` over the transactions matched under that statement's own algorithm variant, and `unmatched_amount_cents` is the signed remainder the statement exposes for reconciliation, computed by the rule above. Line inspection is available to a `PlatformAdmin`, `LedgerController`, `PaymentOpsAnalyst`, `PaymentOpsApprover` and `Auditor`, with filtering on the `match_state`; lines are returned in `effective_at` ascending order with a `bank_reference` ascending tie-break, the same order in which the matching consumes them, and the lines of a statement revision are published only after a reconciliation run has written their `match_state`, since lines are appended only while the statement is `IMPORTED`. Statements themselves are listable with filtering on `bank_account_id`, `status` and the self-referential `supersedes_statement_id`, and a statement's own revision chain is listable oldest-first; the per-account statement list under §4 is the one exception to that revision order and returns its revisions newest first.

### 3.8. Deposit Attribution and the Exception Queue

An unmatched deposit becomes an exception, and the machinery that tries to attribute it before a human ever sees it runs on its own rules. A `StatementLine` that resolves to no destination raises an `ExceptionItem` of kind `UNMATCHED_DEPOSIT`. The attribution rule considers only `VirtualAccount` rows of that line's `BankAccount` whose status is `OPEN`, and only within the currently open statement cycle — that is, where the line's `effective_at` is at or before the statement's `cycle_date`. It then applies four branches in strict precedence, and the first branch that yields a virtual account wins. First, a reference match: the line's `embedded_reference_code` equals a virtual account's `reference_code`. Second, an account match: the line's `bank_reference` names a virtual account's `virtual_account_number`. Third, a sole-open fallback: exactly one virtual account of that bank account is `OPEN`. Fourth, none: no destination resolves at all. The precedence is strict, so the reference branch is tried before the account branch, which is tried before the sole-open branch, and the none branch applies only when no earlier branch succeeded.

When a destination resolves, two computed fields are reported on the exception. The attributed fee is keyed on the tier of the gross line amount, not on the attributed amount, so the fee can change discontinuously while the attributed amount does not. The fee branch reads as follows: when the gross is strictly below 100000 cents the attributed fee is zero; when the gross is at least 100000 cents but strictly below 1000000 cents the attributed fee is the larger of 100 cents and the gross multiplied by 10 and then integer-floor-divided by 1000; otherwise, when the gross is 1000000 cents or more, the attributed fee is the smaller of 5000 cents and the larger of 500 cents and the gross multiplied by 5 and then integer-floor-divided by 1000. The fee is then capped so that it never exceeds the gross itself. The `attributable_amount_cents` field is the gross minus that fee, computed after the fee so that the two always sum to the gross exactly and no cent is lost. This is precisely why computing the amount first and the fee as a residual would be wrong: the tier boundary would then depend on the already-rounded amount, which is a different number. Both `attributed_fee_cents` and `attributable_amount_cents` are reported on every raise and every reevaluation of an `UNMATCHED_DEPOSIT` item whether or not a destination resolved, so the split remains observable even while the deposit is still unattributed; both default to 0.

Every exception carries its own accounting metadata. `amount_cents` is the absolute amount locked behind the item and must be strictly greater than zero. `opened_utc` is the instant the exception was raised and is the origin of its aging clock. `closing_period_utc` is the close instant of the accounting period that was in effect when the item was opened, and the item must be resolved before the ledger's next close or it will draw `ERR_CLOSE_BLOCKED_BY_EXCEPTION`. `age_business_days` is the business-day distance from `opened_utc` to the logical clock, and `aging_bucket` is one of `CURRENT`, `AGING`, `ESCALATED` or `CRITICAL`, derived from that distance. The item's `kind` is one of `UNMATCHED_DEPOSIT`, `RETURN`, `REVERSAL`, `FAILED_PAYMENT` or `STATEMENT_VARIANCE`. Its `payment_order_id` and `bank_statement_id` are a polymorphic pair and are mutually exclusive: an `UNMATCHED_DEPOSIT` or `STATEMENT_VARIANCE` item names a bank statement in `bank_statement_id` and leaves `payment_order_id` null, whereas a payment-ordering item names an order in `payment_order_id` and leaves `bank_statement_id` null. `assignee_user_id` names the operations user the item is assigned to and is required before the item may be resolved or waived, and `resolution_note` is the free-text operator note captured on resolve or waive.

The aging arithmetic has two boundaries in it and both must be honoured. The ledger institution's timezone that anchors the counting is resolved from published data: the `LegalEntity` that owns the ledger has no declared timezone field in this contract, so the count is taken in the timezone of a published banking calendar cell associated with the ledger's institution, and `America/New_York` is the final fallback when no such cell exists. First, the count itself: define the open date as the calendar date of `opened_utc` in the ledger institution's timezone and the target date as the calendar date of the logical clock in the same timezone; `age_business_days` is then the number of calendar dates strictly after the open date and at or before the target date whose weekday is Monday through Friday and for which no banking calendar cell exists with that `calendar_date` and `is_open` false. The lower bound is strict: an item opened at 09:00 and re-evaluated at 23:59 the same business day reports zero, not one, and the endpoint days are not included. Second, the bucket ladder, which is applied in strict order and is inclusive at the top of every tier: an item whose `age_business_days` is at most 1 is `CURRENT`; at most 3 but more than 1 is `AGING`; at most 7 but more than 3 is `ESCALATED`; and anything above 7 is `CRITICAL`. So an item at exactly one business day is `CURRENT` and one at exactly seven is `ESCALATED`, while an item at eight is `CRITICAL`. The two boundaries therefore point in opposite directions — the age is exclusive at its lower bound and the tiers are inclusive at their ceilings — and an implementation that makes both inclusive, or both exclusive, fails one of the two boundary cases.

An exception's `status` runs `OPEN` → `ASSIGNED` → `RESOLVED`, with `ASSIGNED` → `ESCALATED` → `ASSIGNED` as a loop and `ASSIGNED` → `WAIVED` and `ESCALATED` → `WAIVED` as terminal exits. Assignment is performed by a `PaymentOpsAnalyst` or a `PaymentOpsApprover` and requires the item to be `OPEN`; the payload's `assignee_user_id` names the operator and the acting user owns the work. An `ASSIGNED` item can be returned to the unowned `OPEN` queue by unassigning, which also clears `assignee_user_id` to null. An assigned item can be escalated, and that action requires its `aging_bucket` to already be `AGING`, `ESCALATED` or `CRITICAL`; an item still sitting at `CURRENT` cannot be escalated and the attempt is refused with `ERR_EXCEPTION_NOT_AGED` and HTTP 409. An escalated item can be de-escalated back to `ASSIGNED`, and that action requires the bucket to be exactly `CURRENT`; attempting it on a still-aged item is refused with the same error identifier and status. The same `ERR_EXCEPTION_NOT_AGED` identifier and HTTP 409 also guard escalation and waiver on the grounds of age alone. An `OPEN` item can have its aging recomputed without any status change, and that recomputation re-runs the age and bucket rules against the current logical clock; for an `UNMATCHED_DEPOSIT` item the same reevaluation re-runs deposit attribution and closes the item if a destination has since become resolvable.

Resolution is the analyst's exit and it is doubly gated. A `PaymentOpsAnalyst` or a `PaymentOpsApprover` may resolve an item only when its status is `ASSIGNED`, only when its `assignee_user_id` is set and matches the caller's `X-User-ID`, and only once its `age_business_days` is at least 1. Failing the ownership test or the age test is reported as `ERR_EXCEPTION_NOT_ASSIGNED_TO_CALLER` with HTTP 409. A resolution records the caller's `resolution_note`, advances the ledger's `version`, and appends an audit event recording `exception_item.resolved`. Resolving an item of kind `RETURN` executes the reverse-rail fee transfer described in §3.9 for that leg, adding its allocated share to `delivered_fee_transfers_cents` and parking any shortfall in `undeliverable_cents`. Resolving an item of kind `UNMATCHED_DEPOSIT` re-runs deposit attribution and books an `ORIGINATING` leg for the `attributable_amount_cents` together with a `FEE` leg for the `attributed_fee_cents`.

Waiver is the senior approver's exit and it is available only to a `PaymentOpsApprover`. A waive requires the item's `aging_bucket` to be `AGING`, `ESCALATED` or `CRITICAL` — a `CURRENT` item cannot be waived, and the attempt is refused with `ERR_EXCEPTION_NOT_AGED` and HTTP 409 — and it requires the item's `opened_utc` to be at or after the close instant of the ledger's `period_closed_through_index`, because a closed period's exception may not be waived retroactively; breaching that is reported as `ERR_PERIOD_CLOSED` with HTTP 409. The action is reachable from both `ASSIGNED` and `ESCALATED`, records the caller's `resolution_note`, moves the item to `WAIVED`, and appends an audit event recording `exception_item.waived` and carrying the reason in its `details`.

The exception queue is readable by a `PlatformAdmin`, `LedgerController`, `PaymentOpsAnalyst`, `PaymentOpsApprover` and `Auditor`, and is returned in `opened_utc` ascending order with a `created_at` ascending tie-break, the created-at value itself standing in for the creation ordinal the queue rule uses. Filtering is available on `ledger_id`, `kind`, `status`, `aging_bucket`, `payment_order_id` and `bank_statement_id`; the `aging_bucket` filter compares against a bucket recomputed from the logical clock at read time rather than any stored value. Reading a single exception recomputes its aging bucket against the logical clock before answering, so a stale bucket is never served.

### 3.9. Settlement Pools, the Reverse-Rail Fee Allocation and Period Close

`SettlementPool` rows group bank accounts whose combined funds back a set of payments. A `LedgerController` or a `PlatformAdmin` creates one by naming its `ledger_id`, a pool `name`, a `member_bank_account_ids` array, and an optional `status` which begins at `ACTIVE` and may be `SUSPENDED`. Every account named in `member_bank_account_ids` must exist and be `OPEN`. The pool's `forced_settlement_status` is not stored from the payload; it is derived from the pool's members by the pool rule, which sums the `available_funds_cents` of every member account whose status is `OPEN` to obtain eligible funds and then assigns a forced status thus: `FAILED` when eligible funds are strictly below 1000000 cents, `DEGRADED` when eligible funds are at or below 5000000 cents, and `READY` otherwise. The two thresholds point in opposite directions at their boundaries, so exactly 1000000 cents is `DEGRADED` rather than `FAILED` while exactly 5000000 cents is still `DEGRADED` rather than `READY`. The derived status is recomputed on pool creation, on every membership change and on every explicit refresh, and a refresh by a `PaymentOpsAnalyst` or a `LedgerController` appends an audit event recording `settlement_pool.refreshed`. The same health is also exposed on a `BankAccount`: because one account may belong to several pools, an account's own `forced_settlement_status` reports the least healthy forced status among the pools that name it, and is null when the account is a member of no pool at all.

Membership itself is a first-class row. A `PoolMembership` names its `settlement_pool_id`, the `bank_account_id` of the member account, and a `weight_units` integer which defaults to 1 and must be strictly greater than zero; the weight is the relative share used when a pool-level remainder must be distributed across members in `created_at` ascending order. A `LedgerController` or `PlatformAdmin` adds a member and, separately, removes one; adding also records the account in the pool's `member_bank_account_ids` when it is not already there, exactly as the pool's initial creation records each of its members as a row, and removal deletes the membership row and returns the pool with its forced settlement status recomputed. Memberships are listable by pool or by bank account, and the members of a pool are listable on their own.

The reverse-rail fee machinery is the most intricate piece of arithmetic in the system, and it rests on one allocation primitive that must be implemented exactly as stated. Given a total to distribute across ordered buckets that carry weights, first compute the sum of all the weights. Then, for each bucket in weight order, compute that bucket's share as the total multiplied by the bucket's weight and then integer-floor-divided by the weight sum; every share is rounded down. Compute the remainder as the total minus the sum of the shares. Then distribute that remainder one cent at a time, cycling through the buckets in order — first bucket, second bucket, and so on to the last, then back to the first — until the remainder is exhausted. The bucket order is the order in which each bucket's backing entry was created, using `created_at` ascending with a `sequence` tie-break ascending, and a UUID `id` is never consulted for that ordering. The floor-then-cycle order is pinned and must not be replaced by a single round-half-up over the total, nor may the whole remainder be handed to the first bucket, because both alternatives produce a different per-bucket distribution for the same inputs. Under equal weights the first bucket may receive up to one cent more than the last while the total still sums exactly to the distributed amount; under unequal weights the same floor-then-cycle result is what must be reproduced, and a ceiling-divided or round-half-up share differs from it for the same total and weights.

That primitive is applied to the ledger's reverse-rail fee pool as follows. Consider each active return leg — a `RETURN` transaction whose `settlement_status` is `UNSETTLED` or `IN_SETTLEMENT` — ordered by `created_at` ascending with a `sequence` ascending tie-break. For a given leg, let the cover be the absolute value of the sum of `net_effect_cents` over the ledger's `SETTLED` `FEE` legs whose `value_effective_utc` is at or before that return leg's `value_effective_utc`. Let the total to distribute be 25 cents multiplied by the count of active return legs on the ledger. Let the leg's allocated share be the share assigned to it by the allocation primitive above applied over those legs with equal weights, so that the shares sum to that total exactly. Then, when the leg's cover is at or above its allocated share, the fee transferred for that leg is its allocated share; otherwise the fee transferred for that leg is zero. Delivered shares accumulate on the ledger's `delivered_fee_transfers_cents` and shortfalls on its `undeliverable_cents`. The conserved-quantity invariant that ties this together was stated in §2.11 and is restated here because it is the point of the whole construction: `delivered_fee_transfers_cents` plus `undeliverable_cents` must equal 25 cents multiplied by the number of resolved return legs on the ledger. The identity holds on the shortfall branch too, which is why the residue must be parked in `undeliverable_cents` rather than dropped. Concretely, a leg whose settled fee cover is at or above its allocated share contributes its full allocated share to `delivered_fee_transfers_cents` and zero to `undeliverable_cents`, whereas a leg whose cover is short contributes its cover to `delivered_fee_transfers_cents` and the difference between its allocated share and its cover to `undeliverable_cents`. Resolving a leg and then booking its compensating re-credit returns the pair of fields to their pre-resolution values.

The accounting period is advanced or terminated through a ledger-level command that only a `LedgerController` may issue. The command carries an `expected_ledger_version` and an optional `force_resolve_exceptions` flag. It first runs the business-day aging and bucket rules over every exception on the ledger. It then either advances or closes. When `period_index` is below 12 the period advances by one, `period_index` increases, and `period_opened_utc` is reset to the close instant of the period just ended, while `period_closed_through_index` is set to the index of the period that was just closed. When `period_index` is already exactly 12 the ledger's `status` becomes `CLOSED`, which is terminal, and `period_closed_through_index` is set to 12. In both cases the ledger's `version` advances by one and an audit event recording `ledger.period_closed` is appended. The close instant recorded for the period being closed is anchored at the end of the closing local date rather than at the instant the close command happened to run, so the closed-period boundary covers the whole of the closing date and a posting dated anywhere on it is refused. After the aging pass, if any exception on the ledger is still `OPEN`, `ASSIGNED` or `ESCALATED`, the command is refused with `ERR_CLOSE_BLOCKED_BY_EXCEPTION` and HTTP 409 — unless the caller supplied `force_resolve_exceptions` as true, in which case the close proceeds anyway and the unresolved items simply keep their status with their `closing_period_utc` pinned to the period being closed. Note the consequence of ordering: an item that the aging pass raises to `ESCALATED` during the very same close both blocks the close and yields `ERR_CLOSE_BLOCKED_BY_EXCEPTION` rather than any generic state error. Because period close mutates the ledger's own `status` and `period_closed_through_index`, it is also one of the ledger's concurrency-guarded writes.

Once a period is closed, the boundary is absolute for postings and for waivers alike. Any `Transaction` whose `value_effective_utc` falls at or before the close instant of `period_closed_through_index` is refused with `ERR_PERIOD_CLOSED` and HTTP 409, whether it is a directly booked manual entry or a transition that would post an existing `PENDING` row into the books. Likewise an `ExceptionItem` whose `opened_utc` falls before that close instant may not be waived, and the attempt is refused with `ERR_PERIOD_CLOSED`.

Two of the ledger's own destructive operations carry the version guard described in §2.7. Voiding a posted transaction requires `expected_ledger_version`, and recomputing a ledger's derived balances requires `expected_ledger_version` as well. Recomputing a ledger re-derives `pending_balance_cents` and `posted_balance_cents` under the projection rule of §3.6, re-verifies the double-entry identity and the reverse-rail fee invariant, raises `ERR_LEDGER_UNBALANCED` with HTTP 409 on failure, advances the ledger's `version`, and appends an audit event recording `ledger.recomputed`. It is available to a `LedgerController` and a `PlatformAdmin`.

### 3.10. Duplicate Prevention, the Validation Cascade and Test-Driving Capabilities

Two independent guards stop the same payment being drafted twice, and they have different scopes on purpose. The first is the caller's `idempotency_key`, which is mandatory on every draft. A create that carries a key already used by a payment order for the same `legal_entity_id` in a status other than `CANCELLED` or `REJECTED` is refused with `ERR_DUPLICATE_PAYMENT` and HTTP 409, while a retried create that repeats a key whose prior order was cancelled or rejected proceeds. The second guard is a content fingerprint that does not depend on the caller at all: the platform derives a duplicate signature as the SHA-256 digest over the concatenation of the order's `legal_entity_id`, its `counterparty_id`, its `rail`, its `direction` and its `amount_cents`, and a stored signature blocks a new create only while the logical clock has advanced no more than 600 seconds past the instant that signature was last seen. Two creates 600 seconds apart are blocked; two creates 601 seconds apart are not. The second guard is subordinate to the first: a stored signature is consulted only for a create whose `idempotency_key` has already been used, and it refuses the create only when the order that stored that key carries a different signature. A retried create that repeats the same key and the identical signature is therefore governed entirely by the first guard — refused when that prior order is live, and admitted when it was cancelled or rejected — and a create carrying a never-used key is always a new draft even when its content signature matches a sibling key's. The window is measured on the injected logical clock rather than wall-clock time, so a test can pin it exactly, and the manual transaction-booking path is exempt from this second guard entirely.

The rest of the cascading validation order is as follows. Existence checks run left to right in the request-body order declared for the endpoint, and where a path carries two segments the ledger segment is validated before the resource segment beneath it; each absent parent is reported as its own entity-specific not-found error rather than a generic one. The state gate then refuses any transition not declared from the resource's current state with `ERR_INVALID_TRANSITION` and HTTP 409. The settlement-axis gate then refuses any operation legal on the lifecycle axis but illegal on the settlement axis with `ERR_INVALID_SETTLEMENT_AXIS` and HTTP 409. The business checks follow in the order described across §3.5 and §3.6, with the velocity and amount check before the counterparty-posture check and the counterparty-posture check before the separateness check, so that a blocked counterparty is reported even when the approver would also fail the separateness rule and `ERR_SELF_APPROVAL_FORBIDDEN` is reached only when no earlier business rule has already rejected the release.

Three uniqueness constraints are checked independently and sit at the same priority as one another, which is significant: because they are independent, a payload that violates two of them reports only whichever one the implementation reaches first, and no ordering between them is promised. They are that a counterparty's `external_ref` must be unique within its owning `legal_entity_id`, that a virtual account's `reference_code` must be unique, and that a virtual account's `virtual_account_number` must be unique across all virtual accounts. Any of them being violated is reported as `ERR_DUPLICATE_REFERENCE_CODE` with HTTP 409.

Two test-driving capabilities exist so that rail and calendar behaviour can be exercised without waiting for real time. A `PlatformAdmin` or a `LedgerController` sets the logical clock by supplying a `to_iso8601` instant; the response carries the resulting `current_utc` and the `previous_utc` value it replaced, and a strictly backwards move is refused with `ERR_CLOCK_NOT_MONOTONIC` and HTTP 409 as §2.11 states. A `PlatformAdmin` or a `PaymentOpsAnalyst` drives the rail network's asynchronous settlement confirmation by supplying a `payment_order_id` and an `outcome`, optionally with a `return_reason`; the response carries the `payment_order_id` back, the `outcome`, and an `accepted` boolean stating whether the simulated outcome was accepted, which is true when the `outcome` is one of `SETTLED`, `RETURNED`, `FAILED`, `IN_FLIGHT` or `ACCEPTED` and false otherwise. The call records the outcome against the order without changing any order state or booking any ledger leg. Neither capability is a business operation and neither appends a business audit action.

Finally, the audit trail is readable and appendable on its own terms. Any of `PlatformAdmin`, `LedgerController`, `PaymentOpsAnalyst`, `PaymentOpsApprover`, `PaymentApprover` or `PaymentInitiator` may append an event directly by supplying the `ledger_id`, the `actor_user_id`, the `actor_role`, the `action`, a `target_entity_type`, a `target_entity_id` and optional `details`, and the append mints the event's `sequence_number` per the rule in §2.12. A `PlatformAdmin`, `LedgerController`, `Auditor` or `PaymentOpsApprover` may read the trail for a `ledger_id`, optionally filtered by `target_entity_type` and `target_entity_id`, or deep-link a single event by its per-ledger `sequenceNumber` together with the `ledger_id` it belongs to. The trail response is ordered by the event's `created_at` ascending with its `sequence_number` ascending as the tie-break, so it reads in the same order in which the per-ledger numbers were minted. A deep link that names no event under that `ledger_id` is refused with `ERR_INVALID_REQUEST` and HTTP 400, and a trail read that names no existing `ledger_id` is refused with `ERR_LEDGER_NOT_FOUND`; on both reads the `ledger_id` may be carried in the query string or in the request body.
