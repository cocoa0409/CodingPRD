# Freestanding Emergency Department Compliance API — Product Requirements Document

## 1. Introduction

A freestanding emergency department occupies an uncomfortable regulatory position. It looks to the arriving patient like an urgent care clinic, it bills like a hospital emergency room, and it holds no inpatient beds — so every patient who cannot go home must either be watched in an observation bay or moved to a receiving hospital under an agreement negotiated months earlier. Around that clinical reality sits a dense compliance perimeter: the facility must disclose its emergency facility fee and its network posture before care begins, it must never let a financial conversation delay a medical screening examination, it must attest to state-mandated signage, it must keep enough board-certified physician coverage on the schedule to match forecast arrival volume, and when an out-of-network claim is disputed it must exhaust open negotiation before a certified independent dispute resolution entity may set the number.

This document specifies the API that operates that perimeter. The system tracks facilities and their licensure posture, versioned patient-facing disclosure templates, payer contracts and their balance-billing regimes, physician coverage blocks and volume forecasts, receiving-hospital transfer agreements and ambulance memoranda of understanding, individual patient encounters carrying two independent state dimensions, on-site ancillary orders bounded by licensed scope, transfer orders that reserve ambulance units, claims that settle money down to the cent, and dispute cases that cycle through bounded negotiation rounds. Every compliance-relevant event — a disclosure refused, a screening started late, a transfer declined because of insurance — is appended to a per-facility compliance ledger, and the accumulated defect count feeds back into a derived facility posture that gates which child operations are still permitted.

Two design commitments run through the whole specification and should be read as non-negotiable. First, **money and hours are exact**: every settlement figure is a whole number of cents produced by a pinned evaluation order, and every coverage figure is a two-decimal hour count produced by a pinned rounding order — an implementation that rounds at a different step produces different numbers and is wrong. Second, **the clinical path is never gated on the financial path**: the medical screening examination may begin regardless of whether the patient has acknowledged, refused, or never answered the disclosure, and the specification deliberately gives the encounter two independent state dimensions so that no implementer is tempted to couple them.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint, including the two logical-clock endpoints, must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the role that operator is acting under. If either header is absent, or if `X-User-Role` is not one of the seven role names below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not among the roles authorised for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Authentication is checked before authorisation, and both are checked before anything else about the request is examined.

The seven roles are `FacilityAdministrator`, `ComplianceOfficer`, `RegistrationClerk`, `EmergencyPhysician`, `HospitalTransferCoordinator`, `PayerRepresentative`, and `IDREntity`.

None of the seven roles is backed by a persisted entity. In every case `X-User-ID` is an **opaque operator identifier**: the server never resolves it against any stored row's `id`, and no ownership check anywhere in this system compares a resource's foreign key to `X-User-ID`. What the server does instead is *record* the identifier on the resources whose control depends on who acted:

- When `X-User-Role` is `FacilityAdministrator`, `X-User-ID` is an opaque operator identifier; the server records it as `published_by_user_id` on a `DisclosureTemplate` at publication.
- When `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier; the server records it as `signage_attested_by_user_id` on the `Facility` when a signage attestation is filed, as `initiated_by_user_id` on a `DisputeCase`, and as `last_offer_by_user_id` on a `DisputeCase` when a facility offer is submitted.
- When `X-User-Role` is `RegistrationClerk`, `X-User-ID` is an opaque operator identifier; the server records it as `registered_by_user_id` on an `Encounter` at registration and as `disclosure_decided_by_user_id` when the patient's disclosure decision is recorded.
- When `X-User-Role` is `EmergencyPhysician`, `X-User-ID` is an opaque operator identifier; the server records it as `mse_physician_user_id` on an `Encounter` when the medical screening examination begins and as `certifying_physician_user_id` on a `TransferOrder`.
- When `X-User-Role` is `HospitalTransferCoordinator`, `X-User-ID` is an opaque operator identifier; the server may record it for audit purposes but never compares it to any entity's `id`, and no transfer-order field stores it.
- When `X-User-Role` is `PayerRepresentative`, `X-User-ID` is an opaque operator identifier; the server records it as `last_offer_by_user_id` on a `DisputeCase` when a payer counteroffer is posted.
- When `X-User-Role` is `IDREntity`, `X-User-ID` is an opaque operator identifier; the server may record it for audit purposes but never compares it to any entity's `id`.

Two of those recorded identifiers are load-bearing, because two controls in this system are **segregation-of-duties** controls rather than role controls: the operator who attests a facility's signage must differ from the operator who published that facility's currently published disclosure template, and the operator who records an emergent disclosure waiver must differ from the operator who registered that encounter. Both breaches are reported as `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Section 2.9 states these two controls precisely.

One further identifier deserves a warning because it looks like an actor reference and is not one. `clinician_user_id` on a coverage block is a free-form operator string in the range of 1 to 64 characters naming the clinician who staffs the block; it is never required to equal any entity's `id`, and it is never compared to `X-User-ID`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` defaults to 0 and may not be negative. A `limit` outside the range 1 through 100 inclusive, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

List results are ordered by `created_at` ascending unless the endpoint's own description in Section 3 pins a different order. The append-only compliance ledger is therefore returned oldest entry first, which is the same rule stated from the domain's point of view.

The `meta` block of a list response carries `limit` and `offset` as they were applied, `total_count` as the number of rows matching the filters before the window was applied, and `has_more` as a boolean that is true when rows remain beyond the current window.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries an `id` that is a server-minted UUID with no type prefix; clients never supply it. Twelve of the thirteen resource kinds — `Facility`, `DisclosureTemplate`, `PayerContract`, `PhysicianShift`, `VolumeForecast`, `Encounter`, `AncillaryOrder`, `TransferAgreement`, `AmbulanceMOU`, `TransferOrder`, `Claim` and `DisputeCase` — additionally carry `created_at` and `updated_at` as ISO 8601 UTC timestamps with three fractional digits, plus `version`, an integer that is 1 when the row is created and is incremented by exactly 1 on every mutation of that row. Whenever a specification below says a row's `version` is bumped, that row's `updated_at` is refreshed in the same operation.

The thirteenth kind is the exception and must be treated as such. A `ComplianceLedgerEntry` carries only `id` and `created_at`: it has **no** `updated_at` and **no** `version`, because the ledger is append-only and an entry is never modified after it is written.

All domain time in this system comes from a **logical clock**, not from wall-clock time. Before the clock has ever been set, it reads `2026-08-01T00:00:00Z`. A test-driving capability lets any of the seven roles set the clock to a supplied `current_utc` instant, and a companion read returns the clock's `current_utc` value. Setting the clock stamps no rows and increments no entity's `version`; it simply changes the instant that subsequent reads and writes observe. Because four status fields are derived rather than stored decisions — a payer contract's `status`, a transfer agreement's `status`, an ambulance memorandum's `status`, and a facility's `signage_attestation_status` when its attestation has aged out — moving the clock changes what those fields report on the next read or the next validation that consults them, with no separate sweep required.

### 2.5. Optimistic Concurrency on Facility and Encounter Writes

Three write endpoints are guarded by optimistic concurrency control, because each of them legitimately overwrites or supersedes state that a client may have read before someone else changed it. On those three endpoints the version field is a **required** input, not an optional one; omitting it is a malformed request. Every other endpoint in this system takes no version field at all, and supplying one is simply ignored data.

- `PATCH /facilities/{id}` requires `expected_facility_version`, carrying the client's last observed `version` of the target `Facility`. If that value does not equal the facility's current `version`, the update is rejected with `ERR_STALE_FACILITY_VERSION` (HTTP 412). Licensure and scope edits are last-writer-visible overwrites of the same fields, so the writer must prove its view of the facility is current.
- `POST /disclosure-templates/{id}/publish` requires `expected_facility_version`, carrying the client's last observed `version` of the `Facility` that owns the template. If that value does not equal the facility's current `version`, publication is rejected with `ERR_STALE_FACILITY_VERSION` (HTTP 412). Publication retires the facility's currently published template and rewrites `current_published_template_id`, so a publisher working from a stale view of the facility would silently retire a template it never saw.
- `POST /encounters/{id}/transfer-orders` requires `expected_encounter_version`, carrying the client's last observed `version` of the target `Encounter`. If that value does not equal the encounter's current `version`, the create is rejected with `ERR_STALE_ENCOUNTER_VERSION` (HTTP 412). A new order legitimately cancels an existing requested or accepted order on the same encounter and releases its ambulance unit, so the create must prove the caller saw the encounter's current version.

These are stale-version rejections, evaluated against stored state at the moment the request is processed. They are not about requests arriving close together in time; a client that read a facility yesterday and publishes today is stale in exactly the same way as one that read it a millisecond ago.

### 2.6. Validation Order

When a single request could fail several checks, the outcome is pinned: the checks are evaluated in the order below and the **first** failure is the one reported. Text order in Section 3 carries no ordering information — this ladder does. Steps 1 through 6 apply broadly; the remaining steps name the operations they guard.

1. **Authentication.** `X-User-Role` and `X-User-ID` must be present and `X-User-Role` must be one of the seven declared roles, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorisation.** The acting role must appear in the called endpoint's authorised-role list, else `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Request shape.** Required fields must be present, enum members must be declared values, integers must satisfy their declared minimums, `in_network_coinsurance_rate` must lie between 0 and 1 inclusive with at most four decimal places, `end_utc` must be strictly later than `start_utc`, `effective_end_date` must not be earlier than `effective_start_date`, `coverage_end_at` must be strictly later than `coverage_start_at`, `limit` must lie between 1 and 100 inclusive, `offset` must not be negative, every element of `historical_daily_volumes` must be at least 0, and an ancillary `code` must belong to the `category` stated alongside it. Any breach is `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
4. **Path existence, left to right.** Path-referenced resources must exist, and are resolved in the order they appear in the URL: the facility first, then the disclosure template, payer contract, physician shift, volume forecast, transfer agreement, ambulance memorandum, encounter, ancillary order, transfer order, claim, or dispute case named deeper in the path. A miss yields the not-found error for the segment that failed — `ERR_FACILITY_NOT_FOUND`, `ERR_DISCLOSURE_TEMPLATE_NOT_FOUND`, `ERR_PAYER_CONTRACT_NOT_FOUND`, `ERR_PHYSICIAN_SHIFT_NOT_FOUND`, `ERR_VOLUME_FORECAST_NOT_FOUND`, `ERR_TRANSFER_AGREEMENT_NOT_FOUND`, `ERR_AMBULANCE_MOU_NOT_FOUND`, `ERR_ENCOUNTER_NOT_FOUND`, `ERR_ANCILLARY_ORDER_NOT_FOUND`, `ERR_TRANSFER_ORDER_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, or `ERR_DISPUTE_CASE_NOT_FOUND` — each at HTTP 404. Applies to every endpoint with an id in its path.
5. **Body and query reference existence.** Resources referenced from the request body or query string must exist and must belong to the same facility as the path resource, checked in this declared field order: `transfer_agreement_id`, then `ambulance_mou_id`, then `payer_contract_id`, then `volume_forecast_id`, yielding `ERR_TRANSFER_AGREEMENT_NOT_FOUND`, `ERR_AMBULANCE_MOU_NOT_FOUND`, `ERR_PAYER_CONTRACT_NOT_FOUND`, or `ERR_VOLUME_FORECAST_NOT_FOUND` at HTTP 404. Applies to `POST /encounters/{id}/transfer-orders`, `POST /encounters/{id}/claims`, and `GET /facilities/{id}/coverage-summary`.
6. **Optimistic concurrency.** `expected_facility_version` must equal the facility's `version` and `expected_encounter_version` must equal the encounter's `version`, else `ERR_STALE_FACILITY_VERSION` or `ERR_STALE_ENCOUNTER_VERSION` at HTTP 412. Applies to `PATCH /facilities/{id}`, `POST /disclosure-templates/{id}/publish`, and `POST /encounters/{id}/transfer-orders`.
7. A template must be in `DRAFT` before it can be published, else `ERR_TEMPLATE_NOT_PUBLISHABLE` (409). Guards `POST /disclosure-templates/{id}/publish`.
8. An encounter's `disclosure_state` must be `DISCLOSURE_PRESENTED` before a disclosure decision is recorded, else `ERR_DISCLOSURE_DECISION_ALREADY_RECORDED` (409). Guards `POST /encounters/{id}/disclosure-decision`.
9. An encounter's `clinical_state` must be a declared source state for the requested clinical transition and must not be terminal, else `ERR_INVALID_ENCOUNTER_STATE` (409). This catches beginning screening from anything other than `ARRIVED`, completing screening from anything other than `MSE_IN_PROGRESS`, admitting to observation or discharging from `TRANSFER_PENDING`, `TRANSFERRED` or `DISCHARGED`, ordering a transfer from `ARRIVED`, `MSE_IN_PROGRESS`, `TRANSFERRED` or `DISCHARGED` (transfer ordering *is* permitted from `MSE_COMPLETE`, `OBSERVATION` and `TRANSFER_PENDING`, the last of these being the supersede path), and ordering an ancillary service on an encounter that has already reached `TRANSFERRED` or `DISCHARGED`. Guards `POST /encounters/{id}/begin-mse`, `POST /encounters/{id}/complete-mse`, `POST /encounters/{id}/observation`, `POST /encounters/{id}/discharge`, `POST /encounters/{id}/ancillary-orders`, and `POST /encounters/{id}/transfer-orders`.
10. The status of the acted-upon child must permit the requested transition: an ancillary order must be `ORDERED` before it is resolved (`ERR_INVALID_ANCILLARY_ORDER_STATE`), a transfer order's status must match the requested transition (`ERR_INVALID_TRANSFER_ORDER_STATE`), a claim's status must match (`ERR_INVALID_CLAIM_STATE`), and a dispute case's status must match (`ERR_INVALID_DISPUTE_STATE`) — all at HTTP 409. Guards `POST /ancillary-orders/{id}/resolve`, `POST /transfer-orders/{id}/accept`, `POST /transfer-orders/{id}/decline`, `POST /transfer-orders/{id}/complete`, `POST /claims/{id}/adjudicate`, `POST /encounters/{id}/claims`, `POST /claims/{id}/dispute-cases`, `POST /dispute-cases/{id}/offers`, `POST /dispute-cases/{id}/initiate-idr`, `POST /dispute-cases/{id}/award`, and `POST /dispute-cases/{id}/withdraw`.
11. Segregation of duties, as specified in Section 2.9, else `ERR_SEGREGATION_OF_DUTIES` (403). Guards `POST /facilities/{id}/signage-attestations` and the emergent-waiver form of `POST /encounters/{id}/disclosure-decision`.
12. The medical screening examination must be complete — `clinical_state` must be neither `ARRIVED` nor `MSE_IN_PROGRESS` — before an observation admission or a transfer order, else `ERR_MSE_NOT_COMPLETE` (409). Guards `POST /encounters/{id}/observation` and `POST /encounters/{id}/transfer-orders`.
13. `clinical_benefit_certified` must be true on a transfer order, else `ERR_TRANSFER_CERTIFICATION_REQUIRED` (422). Guards `POST /encounters/{id}/transfer-orders`.
14. An encounter whose `stabilization_status` is `UNSTABLE` may only be transferred under an agreement whose `accepts_unstable` is true using a memorandum whose `level_of_care` is `CRITICAL_CARE`, and may never be discharged; a breach is `ERR_STABILIZATION_REQUIRED` (422). Guards `POST /encounters/{id}/transfer-orders` and `POST /encounters/{id}/discharge`.
15. An emergent disclosure waiver requires `acuity_level` of at least 4, else `ERR_WAIVER_NOT_EMERGENT` (422). Guards the emergent-waiver form of `POST /encounters/{id}/disclosure-decision`.
16. The facility posture gate: a `SUSPENDED` posture blocks registration, observation admission and every ancillary order, and a `RESTRICTED` posture blocks an ancillary order whose `code` appears in the facility's `restricted_service_codes`; either way the rejection is `ERR_FACILITY_POSTURE_BLOCKED` (409). Guards `POST /facilities/{id}/encounters`, `POST /encounters/{id}/observation`, and `POST /encounters/{id}/ancillary-orders`.
17. Registration requires the facility to have a non-null `current_published_template_id` so a disclosure can be presented and pinned, else `ERR_NO_PUBLISHED_DISCLOSURE` (409). Guards `POST /facilities/{id}/encounters`.
18. `attested_elements` must cover every element required by the facility's `license_category` and every element listed in the currently published template's `required_signage_elements`, else `ERR_SIGNAGE_ELEMENTS_INCOMPLETE` (422). Guards `POST /facilities/{id}/signage-attestations`.
19. The ordered `code` must fall inside the facility's licensed scope, else `ERR_OUT_OF_SCOPE_SERVICE` (422). Guards `POST /encounters/{id}/ancillary-orders`.
20. A new transfer agreement must clear the window-separation rule against every existing agreement for the same facility, `destination_hospital_name` and `service_line`, else `ERR_AGREEMENT_WINDOW_CONFLICT` (409). Guards `POST /facilities/{id}/transfer-agreements`.
21. A new coverage block must not overlap another block of the same `clinician_user_id` at the same facility, else `ERR_CLINICIAN_DOUBLE_BOOKED` (409). Guards `POST /facilities/{id}/physician-shifts`.
22. The referenced transfer agreement must be `ACTIVE` at order creation and again at acceptance, else `ERR_AGREEMENT_NOT_ACTIVE` (422). Guards `POST /encounters/{id}/transfer-orders` and `POST /transfer-orders/{id}/accept`.
23. The order's `requested_at` must fall inside the memorandum's coverage window, else `ERR_MOU_WINDOW_NOT_COVERING` (422). Guards `POST /encounters/{id}/transfer-orders`.
24. The referenced payer contract must be `ACTIVE` at claim creation and again at adjudication, else `ERR_PAYER_CONTRACT_NOT_ACTIVE` (422). Guards `POST /encounters/{id}/claims` and `POST /claims/{id}/adjudicate`.
25. The agreement's `service_line` must equal the encounter's `presenting_service_line` and its `capability_tier` must meet the acuity's required tier, else `ERR_TRANSFER_CAPABILITY_INSUFFICIENT` (422). Guards `POST /encounters/{id}/transfer-orders`.
26. The memorandum's `level_of_care` must meet the acuity floor, else `ERR_MOU_LEVEL_INSUFFICIENT` (422). Guards `POST /encounters/{id}/transfer-orders`.
27. The claim's payer contract must have `idr_eligible` true before a dispute case is opened or independent dispute resolution is initiated, else `ERR_IDR_NOT_ELIGIBLE` (422). Guards `POST /claims/{id}/dispute-cases` and `POST /dispute-cases/{id}/initiate-idr`.
28. `observation_beds_occupied` must be strictly less than `observation_bed_count` before an observation admission, else `ERR_OBSERVATION_CAPACITY_EXCEEDED` (409). Guards `POST /encounters/{id}/observation`.
29. The referenced memorandum must have `units_available` of at least 1, else `ERR_AMBULANCE_CAPACITY_EXCEEDED` (409). Guards `POST /encounters/{id}/transfer-orders`.
30. The aggregate concurrent-coverage cap must hold, else `ERR_COVERAGE_CAPACITY_EXCEEDED` (409). Guards `POST /facilities/{id}/physician-shifts`.
31. A facility offer requires the dispute case's `round_index` to be strictly less than 3, else `ERR_NEGOTIATION_ROUNDS_EXHAUSTED` (409). Guards `POST /dispute-cases/{id}/offers`.
32. Initiating independent dispute resolution requires `round_index` of at least 3, else `ERR_NEGOTIATION_NOT_EXHAUSTED` (422). Guards `POST /dispute-cases/{id}/initiate-idr`.
33. `award_cents` must lie inside the inclusive band bounded by `last_offer_cents` and `last_counteroffer_cents`, else `ERR_AWARD_OUT_OF_RANGE` (422). Guards `POST /dispute-cases/{id}/award`.
34. `version_label` must be unique among the facility's templates, else `ERR_DUPLICATE_TEMPLATE_VERSION` (409). Guards `POST /facilities/{id}/disclosure-templates`.
35. At most one claim may exist per encounter and the encounter must have reached `TRANSFERRED` or `DISCHARGED`, else `ERR_CLAIM_ALREADY_EXISTS` (409). Guards `POST /encounters/{id}/claims`.

### 2.7. Money, Hours and Rounding Conventions

Every monetary field in this system is an integer number of **whole cents**. There are no fractional cents anywhere, and no field is ever expressed in dollars. Where a monetary result is produced by multiplying by a rate — an administrative surcharge percentage, a state benchmark percentage, a coinsurance rate — the product is rounded **half up** to the nearest whole cent.

*Where* that rounding happens is as important as the rounding mode, and it is pinned per calculation. The good-faith estimate rounds exactly once, when the administrative surcharge is computed. Claim settlement rounds **per line** twice — once when the allowed amount is allocated across billed lines and once when coinsurance is computed on each line — and never on an aggregate; summing first and rounding once produces a different cent total and is incorrect. Ancillary line charges involve no rounding at all, being an exact integer multiplication. Ambulance units and observation beds are integer counts with no rounding.

Hour figures — a coverage block's `duration_hours`, a forecast's required and scheduled hour totals, and the deficit between them — are decimal numbers carrying **two decimal places**, rounded half up. Coverage reconciliation rounds each contributing block's clipped hours to two decimals *before* summing, then rounds the sum to two decimals again. One figure in the forecast is not rounded but ceilinged: the required physician hours per day are raised to the next whole quarter hour before the statutory floor is applied, as Section 3.4 sets out.

### 2.8. Derived Facility Posture and the Compliance Ledger

Every facility carries a derived gate called `compliance_posture`, whose value is one of `OPEN`, `RESTRICTED`, or `SUSPENDED`. It is never set directly by a client. It is recomputed synchronously at the end of every facility-scoped mutation — facility creation, facility configuration update, a signage attestation, a template publication, and every side effect anywhere in the system that changes the facility's `open_compliance_defect_count` — and the recomputation is a fixed, first-match-wins ladder.

Before the ladder is consulted, signage aging is settled: if `signage_attestation_status` is `ATTESTED` and the logical clock has reached or passed `signage_expires_at`, the status is first rewritten to `LAPSED` so that the ladder sees the fresh value. Then, in order: if `license_status` is `SUSPENDED`, the posture is `SUSPENDED`; otherwise if `license_status` is `PROBATION`, the posture is `RESTRICTED`; otherwise if `signage_attestation_status` is anything other than `ATTESTED`, the posture is `RESTRICTED`; otherwise if `current_published_template_id` is null, the posture is `RESTRICTED`; otherwise if `open_compliance_defect_count` has reached 3 or more, the posture is `RESTRICTED`; otherwise the posture is `OPEN`. The defect threshold is inclusive — a count of exactly 3 restricts the facility, a count of 2 does not.

`restricted_service_codes` is derived from the posture in the same pass and is the list the ancillary-order gate consults. When the posture is `OPEN` the list is empty. When the posture is `RESTRICTED` the list is exactly `MRI` and `THROMBOLYTIC`. When the posture is `SUSPENDED` the list is all eleven ancillary codes: `XRAY`, `CT`, `ULTRASOUND`, `MRI`, `CBC`, `CHEMISTRY`, `TROPONIN`, `BLOOD_CULTURE`, `ANALGESIC`, `ANTIBIOTIC`, `THROMBOLYTIC`.

When — and only when — the recomputation produces a value different from the one the facility held before, three things follow. A ledger entry is appended with `event_type` `POSTURE_CHANGE`, `subject_type` `FACILITY`, `subject_id` set to the facility's own id, and `defect_counted` false; its `severity` is `INFO` when the new posture is `OPEN`, `MINOR` when the new posture is `RESTRICTED`, and `MAJOR` when the new posture is `SUSPENDED`. The facility's `version` is incremented by 1 and its `updated_at` refreshed. And on a change from `OPEN` to `RESTRICTED` specifically, a two-hop forecast cascade fires, described in Section 3.4.

The ledger itself is the facility's permanent compliance record and it is append-only: entries are written, never edited, never deleted. Each entry names the `facility_id` it is recorded against, an `event_type` drawn from `DISCLOSURE_PRESENTED`, `DISCLOSURE_ACKNOWLEDGED`, `DISCLOSURE_REFUSED`, `DISCLOSURE_DEFECT`, `EMERGENT_WAIVER_RECORDED`, `SCREENING_DELAY`, `TEMPLATE_PUBLISHED`, `SIGNAGE_ATTESTED`, `POSTURE_CHANGE`, `TRANSFER_DECLINED_FOR_INSURANCE`, `BALANCE_BILL_ISSUED`, `IDR_INITIATED`, `IDR_AWARDED`, and `IDR_AWARD_WITHDRAWN`; a `severity` of `INFO`, `MINOR`, `MAJOR`, or `CRITICAL`; a polymorphic subject given as a `subject_type` of `ENCOUNTER`, `TRANSFER_ORDER`, `CLAIM`, `FACILITY`, or `DISCLOSURE_TEMPLATE` together with a `subject_id` holding the id of a row of that kind (a deliberately untyped reference, resolved by reading `subject_type` first); a single-sentence machine-generated `detail`; a `recorded_at` holding the logical-clock instant at which the entry was appended; and a `defect_counted` boolean that is true exactly when appending this entry incremented the facility's `open_compliance_defect_count`.

Exactly four kinds of finding are defect-counted, and they are the four that can push a facility into `RESTRICTED`: a refused disclosure, a disclosure defect discovered at disposition, a late medical screening examination, and a transfer declined for insurance reasons. Every other event type is informational and leaves `open_compliance_defect_count` alone. The ledger read endpoint accepts optional `event_type` and `severity` filters alongside `limit` and `offset`.

### 2.9. Segregation of Duties

Two controls in this system split a single compliance act across two operators, and both are enforced by comparing `X-User-ID` against a stored operator identifier rather than by role.

The first governs signage. A `ComplianceOfficer` filing a signage attestation for a facility may not be the same operator who published that facility's currently published disclosure template — that is, the acting `X-User-ID` must differ from the `published_by_user_id` recorded on the template referenced by the facility's `current_published_template_id`. The point is that the person who wrote the fee and network language on the placard cannot also certify that the placard is up on the wall.

The second governs emergent waivers. A `RegistrationClerk` recording an emergent waiver on an encounter may not be the operator who registered that encounter — the acting `X-User-ID` must differ from the encounter's `registered_by_user_id`. Waiving the disclosure conversation entirely is the one disclosure outcome that requires nobody's signature but the clerk's, so a second pair of eyes is mandatory. Note that acknowledgement and refusal carry no such restriction: the registering clerk may record either of those.

Both breaches surface as `ERR_SEGREGATION_OF_DUTIES` at HTTP 403.

### 2.10. Conservation Invariants

Three ledger-style quantities in this system are strict derivations of other rows rather than independently maintained counters, and each carries a conservation invariant that must hold after every operation that touches it.

**Ambulance units.** For each memorandum, `units_reserved` equals the number of transfer orders referencing that memorandum whose status is `REQUESTED` or `ACCEPTED`; `units_available` equals `units_committed` minus `units_reserved`; and `saturation_state` is `SATURATED` when `units_available` is 0 and `AVAILABLE` otherwise. Declined, cancelled and completed orders hold no units. At the facility level, `ambulance_units_committed_total` is the sum of `units_committed` over the facility's memoranda whose `status` is `ACTIVE`, `ambulance_units_reserved_total` is the corresponding sum of `units_reserved`, and `transfer_capacity_state` is `AVAILABLE` when committed total minus reserved total is greater than 0 and `SATURATED` otherwise. Across a facility's `ACTIVE` memoranda, the sum of committed units always equals the sum of reserved units plus the sum of available units; and a reservation followed by its compensating release — a decline, a supersede cancellation, or a completion — must return the reserved sum to exactly the value it held before the reservation.

**Observation beds.** A facility's `observation_beds_occupied` always equals the number of that facility's encounters whose `observation_bed_held` is true, counted regardless of `clinical_state` — an encounter that entered observation and is now `TRANSFER_PENDING` still holds its bed. The count always satisfies the bounds of at least 0 and at most `observation_bed_count`, and an admission paired with its compensating release (a discharge, or a transfer completion) returns the count to its pre-admission value.

**Settlement money.** For every claim, at every moment after adjudication — including after an award is applied and again after an award is withdrawn — `billed_total_cents` equals `plan_paid_cents` plus `patient_responsibility_cents` plus `written_off_cents`. Separately, the per-line allowed allocations always sum to exactly `allowed_amount_cents`, which is what the residual-on-the-last-line rule in Section 3.9 exists to guarantee.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Facility: Licensure, Scope and Signage

A `FacilityAdministrator` brings a freestanding emergency department into the system by supplying its legal `name` (1 to 200 characters, not blank), the `state_code` of the state whose licensure and balance-billing regime applies (exactly two uppercase letters), the state licensure `license_category` — either `INDEPENDENT_FREESTANDING_ED` or `HOSPITAL_OUTPATIENT_DEPARTMENT_OFF_CAMPUS` — an optional `license_status` that defaults to `ACTIVE` and may otherwise be `PROBATION` or `SUSPENDED`, the licensed non-inpatient `observation_bed_count` (at least 0), the on-site `imaging_scope` and `lab_scope` arrays, the `pharmacy_scope_tier`, and `max_concurrent_physicians` (at least 1). `imaging_scope` is any subset, possibly empty, of `XRAY`, `CT`, `ULTRASOUND` and `MRI`; `lab_scope` is any subset, possibly empty, of `CBC`, `CHEMISTRY`, `TROPONIN` and `BLOOD_CULTURE`; `pharmacy_scope_tier` is either `EMERGENCY_ONLY`, which permits `ANALGESIC` and `ANTIBIOTIC`, or `EXTENDED`, which permits those two plus `THROMBOLYTIC`.

A newly created facility is deliberately not yet open for business. Its `signage_attestation_status` is `PENDING` with `signage_attested_at`, `signage_expires_at` and `signage_attested_by_user_id` all null; `observation_beds_occupied`, `open_compliance_defect_count` are 0 and `current_published_template_id` is null; `ambulance_units_committed_total` and `ambulance_units_reserved_total` are 0 with `transfer_capacity_state` reading `SATURATED`; `coverage_deficit_flag` is false; and `version` is 1. Because signage is `PENDING` and no template is published, the very first posture computation lands on `RESTRICTED` with `restricted_service_codes` holding `MRI` and `THROMBOLYTIC`. Creation is the one facility-scoped mutation that produces no `POSTURE_CHANGE` ledger entry, since `RESTRICTED` is where the posture starts rather than a change from a previous value.

Configuration changes arrive as a partial update carrying `expected_facility_version` plus any of `license_status`, `observation_bed_count`, `max_concurrent_physicians`, `imaging_scope`, `lab_scope` and `pharmacy_scope_tier`. Declared fields are replaced wholesale; omitted fields are left untouched. Afterwards the posture and `restricted_service_codes` are recomputed, a `POSTURE_CHANGE` entry is appended if the posture value actually moved, a posture drop to `RESTRICTED` or `SUSPENDED` cascades into the facility's `ACTIVE` volume forecast as described in Section 3.4, and the facility's `version` is incremented by 1.

Signage attestation is the `ComplianceOfficer`'s job and is the other half of the disclosure control. The attestation carries `attested_elements`, the set of patient-facing signage elements the officer certifies are physically posted, plus an optional `attestation_note`. The elements are drawn from `LICENSE_CATEGORY_SIGN`, `FEE_DISCLOSURE_SIGN`, `NETWORK_STATUS_SIGN` and `NOT_A_URGENT_CARE_SIGN`, and what the facility must show depends on how the state licenses it: an `INDEPENDENT_FREESTANDING_ED` must post all four, while a `HOSPITAL_OUTPATIENT_DEPARTMENT_OFF_CAMPUS` — which patients can reasonably read as part of a hospital — must post the first three and is not required to post the not-urgent-care placard. `attested_elements` must contain every element required by the category and, when the facility has a published template, every element in that template's `required_signage_elements` as well; anything less is rejected with `ERR_SIGNAGE_ELEMENTS_INCOMPLETE`. Extra elements beyond the required set are harmless.

An accepted attestation sets `signage_attestation_status` to `ATTESTED`, stamps `signage_attested_at` with the logical clock, computes `signage_expires_at` as that instant plus one year of validity (365 days), and records the acting operator as `signage_attested_by_user_id`. Any open signage-defect ledger finding is resolved and `open_compliance_defect_count` decremented once per resolved finding — a provision that has no effect in practice, because the ledger's event vocabulary contains no signage-defect member, so no entry can ever qualify and the counter is left as it stands. The attestation then appends a ledger entry with `event_type` `SIGNAGE_ATTESTED`, `severity` `INFO` and `defect_counted` false, recomputes the posture and `restricted_service_codes` with the same cascade behaviour as a configuration update, and increments the facility's `version` by 1. Attestations do not expire on a schedule of their own: the aging check runs at the start of each posture recomputation, so a facility whose attestation has passed `signage_expires_at` reads `LAPSED` and is pushed back to `RESTRICTED` the next time anything touches it.

The posture itself moves along six edges, all of them driven by the system rather than requested by a client. `RESTRICTED → OPEN` fires when `license_status` is `ACTIVE`, `signage_attestation_status` is `ATTESTED` with the logical clock still before `signage_expires_at`, `current_published_template_id` is not null, and `open_compliance_defect_count` is below 3; it empties `restricted_service_codes`, appends an `INFO`-severity `POSTURE_CHANGE` entry, and bumps the facility's `version` and `updated_at`. `OPEN → RESTRICTED` fires when `license_status` is not `SUSPENDED` and at least one of the following holds: `license_status` is `PROBATION`, `signage_attestation_status` is not `ATTESTED`, `current_published_template_id` is null, or `open_compliance_defect_count` has reached 3; it sets `restricted_service_codes` to `MRI` and `THROMBOLYTIC`, appends a `MINOR`-severity `POSTURE_CHANGE` entry, fires the forecast cascade, and bumps `version`. `OPEN → SUSPENDED` and `RESTRICTED → SUSPENDED` both fire when `license_status` becomes `SUSPENDED`; each sets `restricted_service_codes` to all eleven ancillary codes, appends a `MAJOR`-severity `POSTURE_CHANGE` entry, and bumps `version`. Recovery runs the same ladder in reverse: `SUSPENDED → RESTRICTED` fires when `license_status` is no longer `SUSPENDED` but at least one of the four restricting conditions still holds, restoring `restricted_service_codes` to `MRI` and `THROMBOLYTIC` with a `MINOR`-severity entry and a `version` bump, while `SUSPENDED → OPEN` fires when `license_status` is `ACTIVE`, signage is attested and unexpired, a template is published and the defect count is below 3, emptying `restricted_service_codes` with an `INFO`-severity entry and a `version` bump.

### 3.2. The Patient-Facing Disclosure: Drafting, Publication and Retirement

Before a single patient may be registered, the facility needs published disclosure language, because the fee the patient is quoted at the desk must come from a document the facility has formally adopted. A `FacilityAdministrator` drafts one by supplying a `version_label` of 1 to 40 characters, an optional `supersedes_version_label` naming the label this draft is meant to replace, the disclosed emergency `facility_fee_cents` (at least 0, billed once per encounter), the disclosed `observation_hourly_cents` (at least 0), a `network_status_statement` of `IN_NETWORK_WITH_SOME_PLANS`, `OUT_OF_NETWORK_ALL_PLANS` or `NETWORK_VARIES_BY_PLAN`, and the `required_signage_elements` its disclosure text depends on. Two of those fields are quieter than they look. `supersedes_version_label` is informational only — no referential check is performed against it, and a label that matches nothing is accepted. And `observation_hourly_cents` is disclosure text only: it is printed for the patient, and no calculation in this system ever bills it.

A draft is created with `status` `DRAFT`, `published_at` null and `published_by_user_id` null, and it has no effect whatsoever on the facility — neither `current_published_template_id` nor the posture moves. The `version_label` must be unique among that facility's templates, whatever their status; a collision is `ERR_DUPLICATE_TEMPLATE_VERSION`. Templates can be listed per facility with an optional `status` filter and read individually by administrators, compliance officers and registration clerks alike, since the clerk at the desk needs to see the language being presented.

Publication is where the disclosure becomes real, and it is the single most side-effect-heavy administrative act in the system. Only a `FacilityAdministrator` may publish, only a `DRAFT` template may be published (otherwise `ERR_TEMPLATE_NOT_PUBLISHABLE`), and the request must carry `expected_facility_version` matching the facility's current `version` (otherwise `ERR_STALE_FACILITY_VERSION` at HTTP 412, as Section 2.5 sets out). On success the template moves `DRAFT → PUBLISHED`, `published_at` is stamped with the logical clock and `published_by_user_id` with the acting operator. The facility's previously published template — there is at most one — moves `PUBLISHED → RETIRED` in the same operation, with its own `updated_at` refreshed and its own `version` incremented by 1. The facility's `current_published_template_id` is rewritten to the newly published template's id, a ledger entry with `event_type` `TEMPLATE_PUBLISHED` is appended, the facility's `version` is incremented by 1, and the posture is recomputed — which is frequently the moment a facility finally reaches `RESTRICTED → OPEN`, since publication removes the null-template restriction and a facility whose signage was already attested and whose defect count is below 3 now satisfies every condition.

Retirement is careful about history. Encounters that were registered while an older template was published keep their `pinned_disclosure_template_id` pointing at that older template forever; retiring it does not repoint anything and does not re-quote any patient. This version pinning is what lets a claim opened weeks later bill the fee the patient was actually shown.

### 3.3. Payer Relationships and Balance-Billing Regimes

Payer contracts can be recorded either by a `FacilityAdministrator` or by a `ComplianceOfficer`, and they carry the whole vocabulary the settlement engine needs: a `payer_name` of 1 to 120 characters, a `network_status` of `IN_NETWORK` or `OUT_OF_NETWORK`, the `qualifying_payment_amount_cents` the plan recognises for the emergency service bundle (at least 0), the `in_network_coinsurance_rate` applied to post-deductible allowed amounts (between 0 and 1 inclusive, at most four decimal places), the `in_network_deductible_remaining_cents` standing at adjudication time (at least 0), the `state_protection_regime` governing freestanding emergency departments under this contract — `FEDERAL_NSA_ONLY`, `STATE_PROTECTED_FSED` or `STATE_EXEMPT_FSED` — and an inclusive date window given as `effective_start_date` and `effective_end_date` in year-month-day form.

Neither of the contract's two derived fields is ever supplied by a client. `status` reads `ACTIVE` when the logical clock's date falls on or after `effective_start_date` and on or before `effective_end_date`, and `TERMINATED` otherwise; it is re-evaluated on every read and on every validation that consults it, so advancing the clock past a window silently terminates the contract with no sweep. `idr_eligible` is true exactly when `network_status` is `OUT_OF_NETWORK` **and** `state_protection_regime` is anything other than `STATE_EXEMPT_FSED`. In plain domain terms: an in-network claim has no dispute to resolve, and a state that exempts freestanding emergency departments from its balance-billing regime offers no independent dispute resolution to escalate into. A claim whose contract has `idr_eligible` false can be adjudicated but can never enter a dispute case; attempting either to open a dispute or to escalate one is `ERR_IDR_NOT_ELIGIBLE`.

Contracts can be listed per facility, filtered by `status` or by `network_status`, and read individually; the `PayerRepresentative` role has read access to contracts and facilities so a plan operator can see the terms it is adjudicating against.

### 3.4. Forecasting Volume and Reconciling Physician Coverage

Physician coverage minimums in this domain are forward-looking: the facility forecasts how many patients will walk in per day, converts that into required physician hours, and is then measured against the coverage blocks actually on the schedule. A `FacilityAdministrator` creates a forecast by supplying the `period_start_date` (inclusive, year-month-day), the `period_days` in the period (from 1 to 90), an ordered `historical_daily_volumes` array of prior daily encounter counts with the oldest element first (each element at least 0, at most 60 elements, possibly empty), and a `method` of either `TRAILING_MEAN` or `PEAK_ADJUSTED`.

The derivation runs as follows. The system first takes a trailing window: the most recent elements of `historical_daily_volumes`, preserving their order, up to a maximum of fourteen — that is, the last two weeks of history, or the whole array when it holds fourteen elements or fewer.

When `historical_daily_volumes` is empty, the forecast has no history to reason from and the **statutory floor alone** governs: `forecast_basis` is set to `FLOOR_ONLY`, `forecast_daily_volume` is 0.00, and `required_physician_hours_per_day` is set to the coverage floor of 12 hours per day — emphatically not 0, because a licensed emergency department must be staffed whether or not anyone predicted arrivals.

When history is present, `forecast_basis` is `HISTORY` and the window mean is computed as the sum of the window's elements divided by the number of elements in the window, rounded half up to two decimals. Under the `TRAILING_MEAN` variant, `forecast_daily_volume` is that window mean unchanged. Under the `PEAK_ADJUSTED` variant, `forecast_daily_volume` is sixty percent of the window's largest element plus forty percent of the window mean, that sum rounded half up to two decimals; for any window whose maximum exceeds its mean this yields a strictly larger volume, and therefore strictly more required hours, than the trailing mean does on identical input. The forecast volume is then converted to raw hours by dividing by a throughput of 1.5 patients per physician hour. Those raw hours are raised to the next whole quarter hour — multiply by four, take the ceiling, divide by four — and `required_physician_hours_per_day` is the larger of that quarter-hour figure and the 12-hour statutory floor. Three inputs therefore interact here: the forecast volume, the throughput constant, and the floor, and the floor wins whenever the computed figure falls below it.

Two totals follow. `required_physician_hours_total` is `required_physician_hours_per_day` multiplied by `period_days`, rounded half up to two decimals. `required_board_certified_hours_total` is that total multiplied by the board-certification minimum share of three quarters, rounded half up to two decimals — three of every four required physician hours must be covered by a clinician who is board certified in emergency medicine.

A new forecast is created with `status` `ACTIVE` and `escalated_by_posture` false, and every other `ACTIVE` forecast of the same facility becomes `SUPERSEDED` in the same operation, so a facility holds at most one active forecast at a time. Creation also runs the coverage reconciliation below to populate `scheduled_physician_hours` and `coverage_deficit_hours`, recomputes the facility's `coverage_deficit_flag`, and increments the facility's `version` by 1. Forecasts can be listed per facility with an optional `status` filter and read individually.

Coverage blocks are the other half of the picture. A block carries the `clinician_user_id` staffing it, a `role_type` of `PHYSICIAN` or `ADVANCED_PRACTICE_PROVIDER`, a `board_certified` boolean, and a half-open interval given as an inclusive `start_utc` and an exclusive `end_utc` that must be strictly later than the start. Its `duration_hours` is the elapsed time from `start_utc` to `end_utc` expressed in hours and rounded half up to two decimals. Only `PHYSICIAN` blocks matter for compliance: `ADVANCED_PRACTICE_PROVIDER` blocks are excluded from both coverage totals and from the concurrency cap, even though they are perfectly legitimate rows to record.

Two temporal rules guard block creation. First, no clinician may be double-booked: a new block may not overlap another block of the same `clinician_user_id` at the same facility under half-open interval semantics, which means a block starting at exactly the instant another one ends is accepted, while any genuine intersection is rejected with `ERR_CLINICIAN_DOUBLE_BOOKED`. Second, the facility's aggregate concurrency cap must hold: counting the new block itself, the number of `PHYSICIAN` blocks that overlap any single instant of the new block's half-open interval may not exceed `max_concurrent_physicians`, and a breach is `ERR_COVERAGE_CAPACITY_EXCEEDED`. Creating a block recomputes the active forecast's scheduled hours and deficit, recomputes `coverage_deficit_flag`, and increments the facility's `version` by 1. Blocks can be listed per facility with an optional `role_type` filter and read individually.

Reconciliation clips coverage to the forecast period. The period begins at `period_start_date` at midnight UTC and ends that many days later, the end being exclusive. Candidate blocks are those of the same facility with `role_type` `PHYSICIAN` whose `start_utc` falls before the period end and whose `end_utc` falls after the period start — the standard half-open overlap test — taken in `created_at` ascending order. For each candidate, the clipped span runs from the later of the block's `start_utc` and the period start to the earlier of the block's `end_utc` and the period end; that span in minutes is divided by 60 and rounded half up to two decimals to give the block's contribution. `scheduled_physician_hours` is the sum of those per-block contributions, rounded half up to two decimals again. `board_certified_hours` is the same sum restricted to blocks whose `board_certified` is true, likewise rounded half up to two decimals. `coverage_deficit_hours` is the shortfall of `required_physician_hours_total` against `scheduled_physician_hours`, rounded half up to two decimals, and floored at 0 so that over-coverage never produces a negative deficit. A facility is `coverage_compliant` only when `coverage_deficit_hours` is exactly 0 **and** `board_certified_hours` is at least `required_board_certified_hours_total` — surplus total hours do not excuse a board-certification shortfall. Finally, the facility's `coverage_deficit_flag` is set to true when `coverage_deficit_hours` is greater than 0 and false otherwise.

The reconciled picture is available as a computed read for administrators and compliance officers. It optionally accepts `volume_forecast_id` to reconcile against a specific forecast; when that parameter is omitted, the forecast selected is the facility's `ACTIVE` forecast ordered by `period_start_date` descending, ties broken by `created_at` ascending, taking the first — and when the facility has no `ACTIVE` forecast at all, the read fails with `ERR_VOLUME_FORECAST_NOT_FOUND`. The response reports `facility_id`, the facility's `compliance_posture`, the `selected_volume_forecast_id` actually used, the selected forecast's `forecast_basis` and its `forecast_method` (the value of the forecast's `method`), `required_physician_hours_per_day`, `required_physician_hours_total`, `required_board_certified_hours_total`, `scheduled_physician_hours`, `board_certified_hours`, `coverage_deficit_hours`, the `coverage_compliant` boolean, the facility's `coverage_deficit_flag`, `observation_bed_count`, `observation_beds_occupied`, and `ambulance_units_available`, that last figure being the facility's committed unit total less its reserved unit total.

One cascade deserves its own paragraph because it connects two apparently unrelated corners of the system. Whenever a facility's posture changes from `OPEN` to `RESTRICTED` — from any cause, whether a licensure downgrade, a lapsed attestation, or a third counted compliance defect — the facility is presumed to be under stress and its forecasting is escalated to the conservative variant. Every `ACTIVE` forecast of that facility whose `method` is `TRAILING_MEAN` has its `method` rewritten to `PEAK_ADJUSTED` and its `escalated_by_posture` set to true, and `forecast_daily_volume`, `required_physician_hours_per_day`, `required_physician_hours_total` and `required_board_certified_hours_total` are all recomputed under the peak-adjusted variant. Because those required hours have now risen, a second hop follows immediately: `scheduled_physician_hours` and `coverage_deficit_hours` are recomputed by the reconciliation above and the facility's `coverage_deficit_flag` is reset from the selected active forecast's deficit. A facility that was comfortably staffed against a trailing-mean requirement can therefore acquire a coverage deficit the instant a disclosure refusal is recorded at its registration desk, with no coverage-related request having been made at all.

### 3.5. Receiving-Hospital Agreements and Ambulance Commitments

Having no inpatient beds, a freestanding emergency department can only move a patient onward through pre-arranged relationships, and there are two of them: a transfer agreement with a receiving hospital, and a memorandum of understanding with an ambulance carrier. Both may be created by a `FacilityAdministrator`; transfer agreements may also be recorded by a `HospitalTransferCoordinator`, since the receiving side often drives the paperwork.

A transfer agreement names its `destination_hospital_name` (1 to 120 characters), the `service_line` the receiving hospital accepts — one of `GENERAL_MEDICAL`, `CARDIAC`, `STROKE`, `TRAUMA`, `PEDIATRIC` or `PSYCHIATRIC` — a `capability_tier` from 1 (basic) to 4 (comprehensive), an `accepts_unstable` boolean stating whether the hospital will take a patient whose stabilization finding is `UNSTABLE`, and an inclusive window of `effective_start_date` and `effective_end_date` where the end may not precede the start. Its `status` is derived from the logical clock's date against that inclusive window and is re-evaluated on every read and validation: `PENDING` while the clock date is before `effective_start_date`, `ACTIVE` while the clock date falls within the window inclusive of both endpoints, and `EXPIRED` once the clock date has passed `effective_end_date`.

Agreements for the same facility, the same `destination_hospital_name` and the same `service_line` must be kept genuinely apart in time, and the separation rule is stricter than mere non-overlap. Whatever the computed status of the existing agreement, a new agreement's inclusive date window must be separated from it by at least one clear calendar day in whichever direction the new window sits: either the new `effective_start_date` falls at least two days after the existing `effective_end_date`, or the new `effective_end_date` plus two days falls on or before the existing `effective_start_date`. Windows that overlap, windows that touch at a shared endpoint, and windows that are merely adjacent with no clear day between them are all rejected with `ERR_AGREEMENT_WINDOW_CONFLICT`. Agreements for a different hospital or a different service line are not compared at all. Recording an agreement mutates no facility field and does not increment the facility's `version` — an agreement is a standing arrangement, not a change to the facility's compliance posture or capacity. Agreements can be listed per facility filtered by `status` or `service_line`, and read individually, by administrators, compliance officers, physicians and transfer coordinators.

An ambulance memorandum names its `carrier_name` (1 to 120 characters), the highest `level_of_care` its committed units can provide — `BLS`, `ALS` or `CRITICAL_CARE` — a half-open coverage window given as an inclusive `coverage_start_at` and an exclusive `coverage_end_at` that must be strictly later, and the `units_committed` count for that window (at least 0). Four fields are derived and never supplied: `units_reserved` starts at 0, `units_available` starts equal to `units_committed`, `saturation_state` is `SATURATED` at creation when `units_committed` is 0 and `AVAILABLE` otherwise, and `status` is `ACTIVE` while the logical clock is before `coverage_end_at` and `EXPIRED` from that instant onward, re-evaluated on every read and validation. Recording a memorandum immediately recomputes the facility's `ambulance_units_committed_total`, `ambulance_units_reserved_total` and `transfer_capacity_state` per the unit ledger in Section 2.10, and increments the facility's `version` by 1. Memoranda can be listed per facility filtered by `status` or `saturation_state`, and read individually.

A memorandum committing zero units is legal to record and useless to transfer with: the availability check in Section 3.8 requires at least one available unit, and a commitment of 0 can never satisfy it.

### 3.6. Registration: the Good-Faith Estimate and the Patient's Decision

Registration is performed exclusively by a `RegistrationClerk` and is the moment the whole disclosure regime is exercised. The clerk supplies an opaque `patient_reference` of 1 to 64 characters, a triage `acuity_level` from 1 (least acute) to 5 (most acute), and the `presenting_service_line` the presentation belongs to, drawn from the same six-value vocabulary the transfer agreements use: `GENERAL_MEDICAL`, `CARDIAC`, `STROKE`, `TRAUMA`, `PEDIATRIC`, `PSYCHIATRIC`. The `acuity_level` is doing more work than triage: it selects the acuity allowance inside the good-faith estimate, it sets the minimum receiving-hospital capability tier and the minimum ambulance level of care for any later transfer, and it decides whether an emergent disclosure waiver is even available.

Two gates stand in front of registration. A facility whose `compliance_posture` is `SUSPENDED` may not register anyone at all, and the attempt is rejected with `ERR_FACILITY_POSTURE_BLOCKED`; a facility whose posture is `RESTRICTED` may still register patients freely, since restriction narrows the ancillary formulary rather than closing the door. And the facility must have a published disclosure to present: if `current_published_template_id` is null the attempt fails with `ERR_NO_PUBLISHED_DISCLOSURE`, because a patient cannot be quoted a fee that no adopted document states.

A successful registration writes a rich row. `pinned_disclosure_template_id` is set to the facility's `current_published_template_id` and never changes again for the life of the encounter, no matter how many later templates are published or retired. `clinical_state` starts at `ARRIVED` and `disclosure_state` at `DISCLOSURE_PRESENTED` — two independent dimensions on one row, each with its own transition rules. `arrival_at` is stamped with the logical clock and `registered_by_user_id` with the acting clerk. `mse_start_deadline_at` is computed as `arrival_at` plus half an hour (30 minutes), with `mse_timeliness` reading `PENDING` until screening actually begins. `stabilization_status` starts at `NOT_ASSESSED`. `observation_bed_held` is false, `observation_started_at` is null, and `declined_transfer_count` is 0. A ledger entry with `event_type` `DISCLOSURE_PRESENTED` is appended, informationally and without counting a defect. And `disclosed_estimate_cents` is computed as the patient's good-faith estimate.

That estimate is computed from exactly two inputs — the pinned template and the encounter's `acuity_level` — and from nothing else; no other row participates. The order of evaluation is pinned and matters enormously, because the administrative surcharge rate is selected from a tier table and the tier could plausibly be read either from the pre-surcharge subtotal or from the final total. It is read from the **pre-surcharge subtotal only**. First, the base subtotal is the template's `facility_fee_cents` plus the acuity allowance for the encounter's acuity level, where the allowance is 15000 cents at acuity 1, 35000 cents at acuity 2, 70000 cents at acuity 3, 130000 cents at acuity 4, and 220000 cents at acuity 5. Second, the surcharge rate is selected by comparing that base subtotal against two thresholds: a base subtotal below 100000 cents draws a rate of zero, a base subtotal from 100000 cents up to but not including 250000 cents draws five percent, and a base subtotal of 250000 cents or more draws nine percent. Third, the administrative surcharge is the base subtotal multiplied by the selected rate, rounded half up to whole cents — the single rounding step in this calculation. Fourth, `disclosed_estimate_cents` is the base subtotal plus that surcharge.

Consider the trap concretely. A template disclosing a facility fee of 115000 cents, presented to an acuity-4 patient, gives a base subtotal of 245000 cents, which sits in the five-percent band; the surcharge is 12250 cents and the disclosed estimate is 257250 cents. Note that 257250 is itself at or above the 250000-cent threshold — reading the tier from the total would select nine percent and quote 267050 cents, which is wrong.

The disclosure decision is recorded, again by a `RegistrationClerk`, as a `decision` of `ACKNOWLEDGED`, `REFUSED` or `EMERGENT_WAIVER`, with an optional `waiver_reason`. The decision may be recorded at any point before the encounter reaches a disposition and reads no clinical precondition whatsoever — a patient may acknowledge the disclosure while screening is already under way, and screening is never held up waiting for the answer. What the transition does require is that `disclosure_state` is still `DISCLOSURE_PRESENTED`; a second decision on the same encounter is rejected with `ERR_DISCLOSURE_DECISION_ALREADY_RECORDED`. In all three outcomes the acting operator is recorded as `disclosure_decided_by_user_id`, and the facility's `version` is incremented by 1 whenever the decision changes any facility-level field.

`DISCLOSURE_PRESENTED → DISCLOSURE_ACKNOWLEDGED` is the clean path: the patient has been told what the visit may cost and what the facility's network posture is. It appends an informational ledger entry with `event_type` `DISCLOSURE_ACKNOWLEDGED` and `defect_counted` false, and leaves the posture untouched.

`DISCLOSURE_PRESENTED → DISCLOSURE_WAIVED_EMERGENT` is the compliant escape hatch for patients too sick for a financial conversation, and it is fenced twice. The encounter's `acuity_level` must be at least 4, otherwise the request fails with `ERR_WAIVER_NOT_EMERGENT` — a waiver is a clinical judgement about urgency, not a convenience. And the acting operator must differ from the encounter's `registered_by_user_id`, otherwise the request fails with `ERR_SEGREGATION_OF_DUTIES`. A waiver appends an informational entry with `event_type` `EMERGENT_WAIVER_RECORDED` and `defect_counted` false; no defect is counted, because waiving the conversation for a critically ill patient is a compliant outcome, not a failure.

`DISCLOSURE_PRESENTED → DISCLOSURE_REFUSED` is where the compliance machinery bites, and it is worth following all five hops. The patient's refusal to acknowledge the disclosure is recorded, and then: a ledger entry with `event_type` `DISCLOSURE_REFUSED`, `severity` `MAJOR`, `subject_type` `ENCOUNTER`, `subject_id` set to the encounter's id and `defect_counted` true is appended, and the facility's `open_compliance_defect_count` is incremented by 1. Because that counter changed, the facility's posture is recomputed. If the counter has now reached 3 and `license_status` is `ACTIVE`, the posture moves `OPEN → RESTRICTED` and `restricted_service_codes` becomes `MRI` and `THROMBOLYTIC`. Because the posture became `RESTRICTED`, every `ACTIVE` volume forecast of the facility whose `method` is `TRAILING_MEAN` is rewritten to `PEAK_ADJUSTED` with `escalated_by_posture` set true and its required hours recomputed. And because those required hours changed, the facility's `coverage_deficit_flag` is recomputed from the selected forecast's `coverage_deficit_hours`. One front-desk refusal, in other words, can end with a facility losing its ability to order thrombolytics and simultaneously acquiring a physician-coverage deficit.

There is a fifth disclosure outcome that no client ever requests. `DISCLOSURE_PRESENTED → DISCLOSURE_DEFECT` is fired by the system at the moment a clinical disposition lands — when `clinical_state` reaches `TRANSFERRED` or `DISCHARGED` — while `disclosure_state` is still `DISCLOSURE_PRESENTED`. The patient left without the disclosure conversation ever being closed out, which is a compliance failure by the facility rather than a choice by the patient. It appends a ledger entry with `event_type` `DISCLOSURE_DEFECT`, `severity` `MAJOR`, `subject_type` `ENCOUNTER`, `subject_id` the encounter's id and `defect_counted` true, increments `open_compliance_defect_count` by 1, and runs the same posture recomputation cascade as a refusal. All four of `DISCLOSURE_ACKNOWLEDGED`, `DISCLOSURE_REFUSED`, `DISCLOSURE_WAIVED_EMERGENT` and `DISCLOSURE_DEFECT` are terminal for the disclosure dimension.

Encounters are readable individually and as a filtered list; the list accepts `facility_id`, `pinned_disclosure_template_id`, `clinical_state` and `disclosure_state` filters alongside pagination, which is how a compliance officer finds, for instance, every encounter still sitting in `DISCLOSURE_PRESENTED`.

### 3.7. Screening, Observation, Ancillary Orders and Discharge

The clinical dimension belongs to the `EmergencyPhysician`, and its first rule is a prohibition: no clinical transition anywhere in this system reads `disclosure_state` as a precondition. The medical screening examination may never be delayed by a financial disclosure step, which is precisely why the two dimensions are modelled separately.

Beginning the screening moves the encounter `ARRIVED → MSE_IN_PROGRESS`, accepts an optional `screening_note`, stamps `mse_started_at` with the logical clock, and records the acting physician as `mse_physician_user_id`. Timeliness is then judged against the deadline computed at registration: `mse_timeliness` becomes `ON_TIME` when `mse_started_at` is at or before `mse_start_deadline_at` and `LATE` when it is strictly after. The boundary is inclusive to the second — a start at exactly thirty minutes after `arrival_at` is `ON_TIME`, and one second later is `LATE`. A `LATE` result is a counted compliance defect: it appends a ledger entry with `event_type` `SCREENING_DELAY`, `severity` `MAJOR`, `subject_type` `ENCOUNTER`, `subject_id` the encounter's id and `defect_counted` true, increments the facility's `open_compliance_defect_count` by 1, and cascades into the posture recomputation — which will flip `OPEN → RESTRICTED` once the counter reaches 3, with the forecast escalation following behind it.

Completing the screening moves the encounter `MSE_IN_PROGRESS → MSE_COMPLETE`, stamps `mse_completed_at`, and requires the physician to record a `stabilization_status` of either `STABLE` or `UNSTABLE`. `NOT_ASSESSED` is the value the field holds before screening completes and is not an acceptable input here. Completion touches no facility field and mutates no counter.

From `MSE_COMPLETE` the encounter forks three ways: into observation, into a transfer, or out the door. Observation admission — the choice a facility with no inpatient beds makes when a patient needs watching but not admitting — accepts an optional `observation_plan_note` and requires four things: the encounter must be in `MSE_COMPLETE` (an attempt from `ARRIVED` or `MSE_IN_PROGRESS` is `ERR_MSE_NOT_COMPLETE`, and one from a terminal or transfer-pending state is `ERR_INVALID_ENCOUNTER_STATE`), `stabilization_status` must be anything other than `NOT_ASSESSED`, the facility's `compliance_posture` must not be `SUSPENDED` (otherwise `ERR_FACILITY_POSTURE_BLOCKED`), and `observation_beds_occupied` must be strictly below `observation_bed_count` (otherwise `ERR_OBSERVATION_CAPACITY_EXCEEDED`). On success the encounter moves `MSE_COMPLETE → OBSERVATION`, `observation_bed_held` becomes true, `observation_started_at` is stamped with the logical clock on first entry into observation, the facility's `observation_beds_occupied` is recomputed upward by one, and the facility's `version` is incremented by 1.

Discharge is available from two source states, `MSE_COMPLETE → DISCHARGED` and `OBSERVATION → DISCHARGED`, accepts an optional `discharge_instructions_ack`, and carries the system's hardest clinical prohibition: `stabilization_status` must be `STABLE`. An `UNSTABLE` patient may never be discharged, only transferred, and the attempt is rejected with `ERR_STABILIZATION_REQUIRED`. Discharging from observation sets `observation_bed_held` to false and recomputes `observation_beds_occupied` downward by one; discharging from `MSE_COMPLETE` releases nothing because nothing was held. Either way, if `disclosure_state` is still `DISCLOSURE_PRESENTED` at the moment of disposition, the disclosure-defect transition described in Section 3.6 fires with its ledger entry, its defect increment and its posture cascade. The facility's `version` is incremented by 1.

Ancillary services are ordered against the encounter by the treating physician with a `category` of `IMAGING`, `LABORATORY` or `PHARMACY`, a specific `code`, and a `quantity` of at least 1. The code must belong to the stated category — `IMAGING` covers `XRAY`, `CT`, `ULTRASOUND` and `MRI`; `LABORATORY` covers `CBC`, `CHEMISTRY`, `TROPONIN` and `BLOOD_CULTURE`; `PHARMACY` covers `ANALGESIC`, `ANTIBIOTIC` and `THROMBOLYTIC` — and a mismatch is a malformed request reported as `ERR_INVALID_REQUEST`. Two further gates then apply, in this order: the posture gate, where a `SUSPENDED` facility blocks every ancillary order and a `RESTRICTED` facility blocks any order whose `code` appears in `restricted_service_codes`, both reported as `ERR_FACILITY_POSTURE_BLOCKED`; and the licensed-scope gate, where an `IMAGING` code must appear in the facility's `imaging_scope`, a `LABORATORY` code must appear in its `lab_scope`, and a `PHARMACY` code must be permitted by its `pharmacy_scope_tier` — `EMERGENCY_ONLY` permitting `ANALGESIC` and `ANTIBIOTIC`, `EXTENDED` additionally permitting `THROMBOLYTIC` — with a breach reported as `ERR_OUT_OF_SCOPE_SERVICE`. Ordering on an encounter that has already reached `TRANSFERRED` or `DISCHARGED` is `ERR_INVALID_ENCOUNTER_STATE`.

Once those gates are cleared, the line is priced from a fixed schedule and no other row is read. `unit_charge_cents` is looked up by `code`: 12000 for `XRAY`, 49000 for `CT`, 24000 for `ULTRASOUND`, 145000 for `MRI`, 4500 for `CBC`, 6200 for `CHEMISTRY`, 15500 for `TROPONIN`, 11500 for `BLOOD_CULTURE`, 8500 for `ANALGESIC`, 7400 for `ANTIBIOTIC`, and 210000 for `THROMBOLYTIC`. `line_total_cents` is `unit_charge_cents` multiplied by `quantity` — an exact integer product with no rounding — and that relationship holds for every order in every status, for the life of the row. The order is created with `status` `ORDERED`, and creation has no billing effect yet.

Resolution fixes whether the line is money. The physician resolves an order with an `outcome` of `RESULTED` or `CANCELLED` plus an optional `result_note`, and the order must still be `ORDERED` (otherwise `ERR_INVALID_ANCILLARY_ORDER_STATE`). `ORDERED → RESULTED` makes the line billable: it will be summed into the claim's ancillary total when a claim is created. `ORDERED → CANCELLED` excludes the line permanently — a cancelled study is never billed even if it was performed in error. Both `RESULTED` and `CANCELLED` are terminal. Ancillary orders can be listed per encounter with optional `status` and `category` filters and read individually by physicians, compliance officers and administrators.

### 3.8. Ordering, Superseding and Closing a Transfer

When a patient needs more than the facility can provide, the treating physician orders a transfer. The order carries `expected_encounter_version` (the encounter-level concurrency token described in Section 2.5), the `transfer_agreement_id` of the receiving-hospital agreement that authorises the destination, the `ambulance_mou_id` of the memorandum whose unit will carry the patient, and `clinical_benefit_certified` — the physician's certification that the medical benefits of the transfer outweigh its risks. That certification must be true; a false value is rejected with `ERR_TRANSFER_CERTIFICATION_REQUIRED`, because an uncertified transfer out of an emergency department is exactly the transfer regulators care most about.

Creation is the most heavily validated operation in the system, and its checks fire in the order the ladder in Section 2.6 pins. After the referenced agreement and memorandum are resolved and the concurrency token is matched, the encounter must have completed screening — an attempt from `ARRIVED` or `MSE_IN_PROGRESS` is `ERR_MSE_NOT_COMPLETE`, while an attempt from `TRANSFERRED` or `DISCHARGED` is `ERR_INVALID_ENCOUNTER_STATE`; ordering is permitted from `MSE_COMPLETE`, from `OBSERVATION`, and from `TRANSFER_PENDING`. Certification is checked next. Then, for an encounter whose `stabilization_status` is `UNSTABLE`, the destination and the transport must both be capable of it: the agreement's `accepts_unstable` must be true and the memorandum's `level_of_care` must be `CRITICAL_CARE`, or the order is rejected with `ERR_STABILIZATION_REQUIRED`. The agreement's `status` must be `ACTIVE` on the logical clock's date, else `ERR_AGREEMENT_NOT_ACTIVE`. The order's `requested_at`, stamped from the logical clock, must fall inside the memorandum's half-open coverage window — at or after `coverage_start_at` and strictly before `coverage_end_at`, so an instant exactly equal to `coverage_end_at` is outside — else `ERR_MOU_WINDOW_NOT_COVERING`.

Two acuity-driven matching rules follow. The agreement's `service_line` must equal the encounter's `presenting_service_line`, and its `capability_tier` must be at least the tier the acuity demands: acuity 1 and acuity 2 both require tier 1, acuity 3 requires tier 2, acuity 4 requires tier 3, and acuity 5 requires tier 4. A wrong service line or an insufficient tier is `ERR_TRANSFER_CAPABILITY_INSUFFICIENT`. The memorandum's `level_of_care` must clear the acuity floor as well: acuity 4 requires `ALS` or `CRITICAL_CARE`, and acuity 5 requires `CRITICAL_CARE`; anything less is `ERR_MOU_LEVEL_INSUFFICIENT`. Acuity levels 1 through 3 impose no level-of-care floor, so `BLS` transport is acceptable for them. Last, the memorandum must actually have a unit to give: `units_available` must be at least 1, else `ERR_AMBULANCE_CAPACITY_EXCEEDED`.

A created order is `REQUESTED`, with `requested_at` stamped, `certifying_physician_user_id` set to the acting physician, and `reserved_unit_count` of 1. Its `round_index` is 1 plus the number of `DECLINED` orders already on that encounter, so the first attempt is round 1 and the order created after two declines is round 3. The encounter's `clinical_state` becomes `TRANSFER_PENDING` — arriving there as `MSE_COMPLETE → TRANSFER_PENDING` from a screened patient, as `OBSERVATION → TRANSFER_PENDING` from a patient already in a bed, or as `TRANSFER_PENDING → TRANSFER_PENDING` when a live order is being replaced — and the encounter's `version` is incremented by 1. The memorandum's `units_reserved`, `units_available` and `saturation_state` are recomputed, and so are the facility's `ambulance_units_reserved_total` and `transfer_capacity_state`, with the facility's `version` incremented by 1. One thing that deliberately does **not** change is the observation bed: `observation_bed_held` and the facility's `observation_beds_occupied` are untouched while a transfer is pending, because the patient is physically still lying in the observation bay until the ambulance leaves.

Superseding is the self-loop, and it is why the encounter carries a concurrency token. When a new order is created on an encounter already in `TRANSFER_PENDING`, the previous `REQUESTED` or `ACCEPTED` order on that encounter transitions to `CANCELLED` and releases its reserved ambulance unit — the memorandum's `units_reserved` drops by one and its availability, `saturation_state` and the facility's totals are all recomputed — while the new order is created `REQUESTED` with `reserved_unit_count` 1. The encounter stays in `TRANSFER_PENDING`, its `version` is incremented by 1, and `observation_bed_held` is unchanged by the supersede.

The receiving hospital's coordinator drives the order's remaining life. Acceptance moves it `REQUESTED → ACCEPTED`, accepts an optional `accepting_clinician_note`, and re-checks that the agreement's `status` is still `ACTIVE` at that moment — a window that expired between ordering and acceptance yields `ERR_AGREEMENT_NOT_ACTIVE`. Acceptance holds the ambulance unit: `units_reserved` is unchanged, because the unit is still committed to this patient. The encounter stays in `TRANSFER_PENDING`.

Declining moves the order `REQUESTED → DECLINED` and requires a `decline_reason` of `CAPACITY`, `CAPABILITY` or `INSURANCE`. Its consequences fan out. `reserved_unit_count` drops to 0; because the order has left the reserving statuses, the memorandum's `units_reserved` decreases by one and `units_available` is recomputed as `units_committed` less `units_reserved`; because availability is now above 0, that memorandum's `saturation_state` moves `SATURATED → AVAILABLE`; and because its availability changed, the facility's `ambulance_units_reserved_total` is recomputed and `transfer_capacity_state` moves `SATURATED → AVAILABLE`. The encounter's `declined_transfer_count` is incremented by 1 and its `clinical_state` returns along one of two paths: `TRANSFER_PENDING → OBSERVATION` when `observation_bed_held` is true, and `TRANSFER_PENDING → MSE_COMPLETE` when it is false. Only the encounter's newest transfer order drives that return path. Returning to observation performs **no** bed capacity re-check, because the bed was never released — this is the observation-versus-transfer cycle a facility without inpatient beds lives in, and a patient can go round it repeatedly. Both the encounter's and the facility's `version` are incremented by 1.

A decline whose `decline_reason` is `INSURANCE` is treated as the gravest finding this system records. It appends a ledger entry with `event_type` `TRANSFER_DECLINED_FOR_INSURANCE`, `severity` `CRITICAL`, `subject_type` `TRANSFER_ORDER`, `subject_id` set to the declined order's id and `defect_counted` true, increments the facility's `open_compliance_defect_count` by 1, and runs the full posture recomputation cascade including the forecast escalation. Declines for `CAPACITY` or `CAPABILITY` append no defect-counted entry and leave the posture alone.

Completion closes the encounter. It moves the order `ACCEPTED → COMPLETED`, accepts an optional `arrival_confirmation_note`, and sets `reserved_unit_count` to 0. The memorandum's unit is released with the same recomputation chain as a decline — `units_reserved`, `units_available`, `saturation_state`, the facility's `ambulance_units_reserved_total` and `transfer_capacity_state`. The encounter moves `TRANSFER_PENDING → TRANSFERRED`; if `observation_bed_held` was true it becomes false and the facility's `observation_beds_occupied` is recomputed downward by one; if `disclosure_state` is still `DISCLOSURE_PRESENTED` the disclosure-defect transition fires with its `MAJOR` ledger entry, its defect increment and its posture cascade. Both the encounter's and the facility's `version` are incremented by 1. `DECLINED`, `CANCELLED` and `COMPLETED` are all terminal for a transfer order. Orders are readable individually and as a list filtered by `encounter_id`, `transfer_agreement_id`, `ambulance_mou_id` or `status`.

### 3.9. Billing the Encounter: Settlement, Negotiation and Independent Dispute Resolution

Only a closed encounter can be billed. A `ComplianceOfficer` opens a claim against an encounter by naming the `payer_contract_id` the claim is billed under; the encounter must have reached `TRANSFERRED` or `DISCHARGED`, and an attempt before disposition is rejected with `ERR_INVALID_ENCOUNTER_STATE`. At most one claim may ever exist per encounter, and a second attempt is rejected with `ERR_CLAIM_ALREADY_EXISTS`. The referenced contract's `status` must be `ACTIVE` on the logical clock's date, else `ERR_PAYER_CONTRACT_NOT_ACTIVE`.

Claim creation freezes what is billed. `billed_facility_fee_cents` is copied from the `facility_fee_cents` of the template the encounter pinned at registration — not from whatever template happens to be published today. `billed_ancillary_cents` is the sum of `line_total_cents` over the encounter's ancillary orders whose `status` is `RESULTED`; `ORDERED` and `CANCELLED` lines contribute nothing. `billed_total_cents` is the sum of those two figures. The claim is created with `status` `DRAFT`, with `negotiation_rounds_used` 0, with all four `pre_award_allowed_cents`, `pre_award_plan_paid_cents`, `pre_award_patient_responsibility_cents` and `pre_award_written_off_cents` snapshots null, and with `allowed_amount_cents`, `plan_paid_cents`, `patient_responsibility_cents`, `balance_bill_amount_cents` and `written_off_cents` all unset until adjudication.

What creation *does* resolve, permanently, is `protection_variant` — which balance-billing regime this claim settles under. There are three, and the selection reads both the contract and the encounter's `disclosure_state`:

- `PROTECTED_NSA` applies when the contract's `network_status` is `IN_NETWORK`; or when `network_status` is `OUT_OF_NETWORK` with `state_protection_regime` `FEDERAL_NSA_ONLY`; or — as an override that outranks the regime entirely — whenever the encounter's `disclosure_state` is `DISCLOSURE_REFUSED` or `DISCLOSURE_DEFECT`, whatever the regime says. The rationale is that a facility which failed to close out the disclosure conversation cannot then rely on a state exemption to balance bill the patient.
- `PROTECTED_STATE` applies when `network_status` is `OUT_OF_NETWORK`, `state_protection_regime` is `STATE_PROTECTED_FSED`, and the encounter's `disclosure_state` is neither `DISCLOSURE_REFUSED` nor `DISCLOSURE_DEFECT`.
- `UNPROTECTED` applies when `network_status` is `OUT_OF_NETWORK`, `state_protection_regime` is `STATE_EXEMPT_FSED`, and the encounter's `disclosure_state` is `DISCLOSURE_ACKNOWLEDGED` or `DISCLOSURE_WAIVED_EMERGENT`.

Adjudication belongs to the `PayerRepresentative`, accepts an optional `adjudication_note`, requires the claim to be in `DRAFT` (otherwise `ERR_INVALID_CLAIM_STATE`), re-checks that the payer contract is still `ACTIVE` (otherwise `ERR_PAYER_CONTRACT_NOT_ACTIVE`), and moves the claim `DRAFT → ADJUDICATED`. The settlement it computes is a per-line waterfall, and every step's order is pinned.

**Step one — the ordered line set.** The facility-fee line always comes first, carrying `billed_facility_fee_cents`. Behind it come the encounter's `RESULTED` ancillary lines, each carrying its `line_total_cents`, ordered by the ancillary order's `created_at` ascending — never by id. The billed total across the set equals the claim's `billed_total_cents`.

**Step two — the allowed total.** Under `PROTECTED_STATE`, the allowed total is the larger of the contract's `qualifying_payment_amount_cents` and the billed total multiplied by the state benchmark of eighty percent, that product rounded half up to whole cents; the state benchmark can exceed the plan's qualifying payment amount, which is exactly why cost sharing, plan payment and write-off all differ from `PROTECTED_NSA` on otherwise identical inputs. Under both `PROTECTED_NSA` and `UNPROTECTED`, the allowed total is the contract's `qualifying_payment_amount_cents` unchanged.

**Step three — per-line allocation of the allowed total.** For every line except the last one in the ordered set, the line's allowed share is the allowed total multiplied by that line's billed amount divided by the billed total, rounded half up to whole cents. The last line in the set takes the residual: the allowed total less the sum of every earlier line's allocated share. That residual rule is what makes the per-line allocations sum to exactly `allowed_amount_cents` with no drift.

**Step four — the deductible waterfall.** The contract's `in_network_deductible_remaining_cents` is consumed across the lines in set order, facility fee first. Each line absorbs the smaller of the deductible still remaining and that line's allowed share, and the remaining deductible is reduced by what the line absorbed. A line reached after the deductible is exhausted absorbs nothing.

**Step five — coinsurance, rounded per line and then summed.** For each line, the coinsurance is that line's allowed share less the deductible it absorbed, multiplied by the contract's `in_network_coinsurance_rate`, rounded half up to whole cents. The coinsurance total is the sum of those per-line figures. This order is pinned: summing the post-deductible allowed amounts across lines and rounding once at the end produces a different cent total and is wrong. The patient's cost share is the sum of the deductible amounts absorbed across all lines plus the coinsurance total.

**Step six — variant-specific settlement.** Under `PROTECTED_NSA` and `PROTECTED_STATE`, `patient_responsibility_cents` is the cost share, `balance_bill_amount_cents` is 0, and `written_off_cents` is the billed total less the allowed total — the unallowed remainder is the facility's loss and may not be passed to the patient. Under `UNPROTECTED`, `patient_responsibility_cents` is the cost share **plus** the unallowed remainder, `balance_bill_amount_cents` is that same unallowed remainder, and `written_off_cents` is 0; for identical inputs the patient's obligation is therefore strictly larger than under either protected variant. In all three variants, `plan_paid_cents` is the allowed total less the cost share, and `allowed_amount_cents` is the allowed total. The money-conservation invariant of Section 2.10 must hold afterwards: `billed_total_cents` equals `plan_paid_cents` plus `patient_responsibility_cents` plus `written_off_cents`.

When adjudication leaves `balance_bill_amount_cents` above 0, a ledger entry with `event_type` `BALANCE_BILL_ISSUED`, `severity` `MINOR` and `defect_counted` false is appended — a balance bill is disclosed and tracked, not treated as a defect. Claims are readable individually, including their pre-award snapshots, and as a list filtered by `encounter_id`, `payer_contract_id` or `status`, by compliance officers, payer representatives, administrators and the dispute-resolution entity alike.

Disputing an adjudicated claim opens the negotiation cycle. A `ComplianceOfficer` opens a dispute case on a claim that is `ADJUDICATED` (otherwise `ERR_INVALID_CLAIM_STATE`) whose payer contract has `idr_eligible` true (otherwise `ERR_IDR_NOT_ELIGIBLE`), with an optional `dispute_note`. The case is created with `status` `OPEN_NEGOTIATION`, its `claim_id` naming the out-of-network claim under dispute, `round_index` 0, `initiated_by_user_id` set to the acting officer, and `last_offer_cents`, `last_counteroffer_cents`, `last_offer_by_user_id`, `idr_award_cents` and `awarded_at` all null; the claim moves `ADJUDICATED → NEGOTIATION` with `negotiation_rounds_used` 0. Cases can be listed per claim with an optional `status` filter and read individually.

Open negotiation is a genuine cycle, walked one round at a time by two different roles through the same offer-submission capability, with `offer_cents` carrying the amount and an optional `offer_note`. A `ComplianceOfficer` submitting a facility offer requires the case to be in `OPEN_NEGOTIATION` and its `round_index` to be strictly below the three-round bound; it writes `last_offer_cents` and `last_offer_by_user_id`, and moves the case `OPEN_NEGOTIATION → OFFER_PENDING` **without** changing `round_index`. A `PayerRepresentative` posting a counteroffer requires the case to be in `OFFER_PENDING`; it writes `last_counteroffer_cents` and `last_offer_by_user_id`, increments `round_index` by 1, mirrors that value onto the claim's `negotiation_rounds_used`, and returns the case `OFFER_PENDING → OPEN_NEGOTIATION`. A round, in other words, is closed by the payer's answer, not by the facility's offer. An offer submitted in the wrong status is `ERR_INVALID_DISPUTE_STATE`; a facility offer attempted when `round_index` has already reached 3 is `ERR_NEGOTIATION_ROUNDS_EXHAUSTED`.

The bound cuts both ways, and this is the pairing that trips implementations. The loop **must be exhausted** before independent dispute resolution may be initiated: escalation requires `round_index` to be at least 3, and an attempt with fewer completed rounds is rejected with `ERR_NEGOTIATION_NOT_EXHAUSTED`. Escalation is a `ComplianceOfficer` action naming the `certified_entity_name` that will decide the matter; it requires the case to be in `OPEN_NEGOTIATION` (otherwise `ERR_INVALID_DISPUTE_STATE`) and the contract to still be `idr_eligible` (otherwise `ERR_IDR_NOT_ELIGIBLE`). On success the case moves `OPEN_NEGOTIATION → IDR_INITIATED`, the claim moves `NEGOTIATION → IDR_PENDING` with `negotiation_rounds_used` set to the case's `round_index`, and a ledger entry with `event_type` `IDR_INITIATED` is appended.

The award is entered by the `IDREntity` as an `award_cents` figure with an optional `award_rationale`, against a case in `IDR_INITIATED` (otherwise `ERR_INVALID_DISPUTE_STATE`). The award is bounded by what the parties themselves last said: it must fall inside the inclusive band whose endpoints are `last_offer_cents` and `last_counteroffer_cents`, in whichever order those two happen to sit — the band runs from the smaller of the two to the larger of the two, and both endpoints are acceptable values. An award outside that band is `ERR_AWARD_OUT_OF_RANGE`. On acceptance the case moves `IDR_INITIATED → AWARDED`, `idr_award_cents` is set to the awarded figure, `awarded_at` is stamped with the logical clock, and a ledger entry with `event_type` `IDR_AWARDED`, `severity` `INFO`, `subject_type` `CLAIM`, `subject_id` the claim's id and `defect_counted` false is appended.

Applying the award to the claim is a snapshot-then-recompute. First the four current settlement figures are captured: `pre_award_allowed_cents` takes `allowed_amount_cents`, `pre_award_plan_paid_cents` takes `plan_paid_cents`, `pre_award_patient_responsibility_cents` takes `patient_responsibility_cents`, and `pre_award_written_off_cents` takes `written_off_cents`. Then the awarded figure becomes the allowed total and steps three through six of the settlement are re-run with it — same ordered line set, same deductible input, same `protection_variant` — producing new `allowed_amount_cents`, `plan_paid_cents`, `patient_responsibility_cents`, `balance_bill_amount_cents` and `written_off_cents`. The claim moves `IDR_PENDING → RESOLVED`. The money-conservation invariant holds again after the award.

Withdrawal exists because an award can be vacated, and it is a strict compensating action rather than a fresh calculation. The `IDREntity` withdraws an award on a case in `AWARDED` (otherwise `ERR_INVALID_DISPUTE_STATE`) with a `withdrawal_reason`. The case moves `AWARDED → WITHDRAWN`, which is terminal, and `idr_award_cents` and `awarded_at` are set back to null. On the claim, `allowed_amount_cents`, `plan_paid_cents`, `patient_responsibility_cents` and `written_off_cents` are restored from their corresponding `pre_award_*` snapshots — each field taking back exactly its pre-award value, with no recomputation and therefore no rounding drift — while `balance_bill_amount_cents` is recomputed as `billed_total_cents` less the restored `allowed_amount_cents` when `protection_variant` is `UNPROTECTED`, and 0 for both protected variants. All four `pre_award_*` fields are then cleared to null. The claim returns `RESOLVED → IDR_PENDING`, so a replacement award can be entered against a fresh dispute posture, and a ledger entry with `event_type` `IDR_AWARD_WITHDRAWN`, `severity` `MINOR`, `subject_type` `CLAIM` and `defect_counted` false is appended. After the withdrawal, `billed_total_cents` once again equals `plan_paid_cents` plus `patient_responsibility_cents` plus `written_off_cents`, and each of the four restored figures equals its pre-award value exactly.
