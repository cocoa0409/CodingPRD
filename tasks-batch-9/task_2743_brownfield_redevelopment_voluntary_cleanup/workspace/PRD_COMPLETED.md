# Brownfield Voluntary Cleanup API — Product Requirements Document

## 1. Introduction

Brownfield redevelopment stalls for a reason that has nothing to do with engineering: nobody will lend against a parcel whose environmental liability is unbounded. A developer can price excavation, groundwater treatment and a vapour barrier, but cannot price the possibility that a state agency reopens the file three years after construction. The Voluntary Cleanup Program (VCP) exists to convert that open-ended exposure into a documented, dated, transferable closure — and the back office described here is the system of record that makes the conversion auditable. It tracks a parcel from the first all-appropriate-inquiries desktop review, through phased field delineation and risk-based cleanup-goal derivation, into an approved remedial action plan with an insured cost cap, and out the other side as a no-further-action letter a lender is willing to rely on.

The programme's central difficulty is that every one of those artefacts depends on the state of the others, and the dependencies run in both directions. A risk-based cleanup goal may credit a vapour-mitigation system only if the remedy actually builds one. A bona fide prospective purchaser (BFPP) defence survives only while the redeveloper keeps certifying continuing obligations on schedule; let a defence-critical duty lapse and the defence is forfeited, which freezes the parcel and revokes a closure letter that a lender has already accepted, which in turn rescinds every grant awarded against the site. Conversely, a single failed operation-and-maintenance inspection on an engineered cap pushes a completion review back into implementation. The system must therefore treat the parcel's **cleanup posture** as a derived, always-current gate rather than a status somebody sets by hand, and it must propagate every consequence synchronously inside the request that triggered it.

This document specifies the API a reviewer, a redeveloper, a consultant, an insurer, a lender and a platform operator all share. Read §2 as the fixed contract — envelope shape, pagination, identity, rounding, posture semantics, concurrency and the order in which validations fire. Read §3 as the domain narrative: what each participant does, what the server derives on their behalf, and which rule refuses the request when the file is not in a state that supports it. §4 and §5 are indexes back into that narrative, not substitutes for it.

## 2. Global Specifications & System-Wide Principles

### 2.1. Programme Participants and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the capacity in which that principal acts. If either header is absent, empty or blank, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about the request is examined — including whether the URL resolves to a real resource. If both headers are present but the supplied `X-User-Role` is not among the roles listed for the target endpoint in §4, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). Two routing-level failures are settled before either header is looked at, because they are decided by URL dispatch rather than by any rule in this document: a URL that matches no route in the API at all answers `ERR_NOT_FOUND` (HTTP 404), and a routed URL invoked with a method that route does not support answers `ERR_METHOD_NOT_ALLOWED` (HTTP 405) — in both cases whether or not the identity headers were supplied. A trailing slash on any path is tolerated and dispatches to the same endpoint as the slashless form.

There are exactly six roles, spelled exactly as follows: `Redeveloper`, `EnvironmentalConsultant`, `Insurer`, `StateAgencyReviewer`, `Lender`, and `ProgramAdmin`.

Three of these roles are **entity-backed**: their `X-User-ID` is a real primary key in the party registry, and ownership checks compare persisted foreign keys against it.

- When `X-User-Role` is `Redeveloper`, `X-User-ID` is the `id` of the acting `Party` — a party whose `party_type` is `REDEVELOPER`. Ownership checks on any resource that references a `Party` in the owner slot compare that resource's site's `owner_party_id` to `X-User-ID`; a mismatch is `ERR_NOT_RESOURCE_OWNER` (HTTP 403).
- When `X-User-Role` is `EnvironmentalConsultant`, `X-User-ID` is the `id` of the acting `Party` with `party_type` `CONSULTANT`. Ownership checks on an assessment phase compare the phase's `consultant_party_id` to `X-User-ID`, and monitoring-result filing requires that the acting id resolve to a `CONSULTANT` party.
- When `X-User-Role` is `Insurer`, `X-User-ID` is the `id` of the acting `Party` with `party_type` `INSURER`. Ownership checks on a cost-cap policy compare the policy's `insurer_party_id` to `X-User-ID`.

The other three roles are **opaque**: their `X-User-ID` is an operator identifier that is not tied to any persisted entity, and the server never compares it to any entity's `id`.

- When `X-User-Role` is `StateAgencyReviewer`, `X-User-ID` is an opaque agency operator identifier, never a `Party` id. The server does record it — as `reviewed_by_user_id` on an assessment phase, `imposed_by_user_id` on a continuing obligation, `eligibility_decided_by_user_id` on an enrollment, `approved_by_user_id` on a remedial action plan, `decided_by_user_id` on a funding award, and `issued_by_user_id` on a no-further-action letter — and it drives the two segregation-of-duties rules described below.
- When `X-User-Role` is `Lender`, `X-User-ID` is an opaque lender or investor operator identifier. It is persisted as `accepted_by_lender_user_id` when a closure letter is accepted, but is never compared to any `Party` id.
- When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque platform operator identifier tied to no persisted entity at all. `ProgramAdmin` maintains the party registry and the accredited laboratory list and otherwise only reads.

Segregation of duties applies to the two agency actions where self-review would defeat the purpose of the control. The reviewer who voids a certification must not be the reviewer who imposed the duty in the first place: the acting `X-User-ID` must differ from the obligation's `imposed_by_user_id`. And the reviewer who issues — or re-issues — a site's closure letter must not be the reviewer who approved the remedy: the acting `X-User-ID` must differ from the approving plan's `approved_by_user_id`. Either collision is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

Read access is broad. All six roles may read the party registry and the site list; laboratory reads are open to `ProgramAdmin`, `StateAgencyReviewer`, `EnvironmentalConsultant` and `Redeveloper`; and the logical-clock endpoint is available to all six roles so that any participant can drive time forward in a test. Write access is narrow and role-exclusive; §4 is authoritative on which roles may invoke which endpoint.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty randomly chosen alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0. A `limit` or `offset` outside those bounds is a request-shape violation and yields `ERR_INVALID_REQUEST` (HTTP 422), as is a `limit` or `offset` that is not a base-ten integer, and as is any documented filter parameter supplied empty or carrying a value outside its enumeration; query parameters an endpoint does not document are ignored rather than rejected. On a list endpoint nested under a path identifier, that identifier is resolved before the pagination and filter parameters are inspected, so a malformed `limit` against a parcel that does not exist reports the parcel's 404.

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending. Because the logical clock only advances when a caller advances it, many rows legitimately share an identical `created_at`; such ties are broken by insertion order, the earlier-written row first, and the UUID `id` is never a decision input. Every list response populates four pagination fields inside `meta`: `limit` (the page size actually applied), `offset` (the starting position actually applied), `total_count` (the number of rows matching the filters before the page window is applied), and `has_more` (true when rows remain beyond the current window). Single-resource reads do not carry those four fields.

### 2.4. Resource Identity, Audit Fields and the Logical Clock

Every persisted resource carries an `id` that is a server-minted UUID with no type prefix and no client control. Clients never supply an `id`; supplying one has no effect. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recorded when the row is first written.

Most resources additionally carry `updated_at` — same format, refreshed on every mutation — and `version`, an integer that begins at 1 when the row is created and increments by exactly 1 on every mutation of that row, including mutations that arrive as cascades from a neighbouring aggregate rather than from a direct client request. The one exception is `ContaminantFinding`: an analytical finding is immutable once recorded, so it carries only `id` and `created_at`. It has no `updated_at`, no `version`, and no update endpoint. Every other entity in the system — `Party`, `Laboratory`, `Site`, `AssessmentPhase`, `CleanupGoal`, `LiabilityProtection`, `ContinuingObligation`, `VcpEnrollment`, `RemedialActionPlan`, `CostCapPolicy`, `SiteControl`, `FundingAward`, `NoFurtherActionLetter` and `MonitoringEvent` — carries all four common properties.

Time in this system is a **logical clock**, not wall-clock time. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to the host's real clock. An administrative capability sets it to a supplied `current_utc` instant; every participant role may invoke it, and it modifies no entity rows. The supplied instant may carry a trailing `Z`, an explicit UTC offset or no designator at all, and is normalised to UTC before it is stored; the call answers 200 with a `data` object holding the single key `current_utc`, echoing the string exactly as the caller supplied it rather than a re-formatted rendering. Every deadline, expiry, coverage window, certification window, staleness threshold and "as of" comparison in this specification reads the logical clock, so a test that has not moved the clock is reasoning about 1 August 2026.

### 2.5. Site Cleanup Posture: the Programme-Wide Gate

Each parcel carries a derived `cleanup_posture` that is one of `OPEN`, `RESTRICTED` or `FROZEN`. It is never set by a client; it is recomputed synchronously, inside the triggering request, every time a side effect changes either the site's `impaired_control_count` or its liability protection's `bfpp_status`. The derivation is evaluated top-down and the first matching condition wins: if a liability protection exists on the site and its `bfpp_status` is `FORFEITED`, the posture is `FROZEN`; otherwise, if `impaired_control_count` is greater than zero, the posture is `RESTRICTED`; otherwise the posture is `OPEN`. Forfeiture therefore dominates impairment — a parcel with both a forfeited defence and an impaired control is `FROZEN`, never `RESTRICTED` — and a site that has no liability protection row at all can never be `FROZEN`.

`impaired_control_count` is itself a derived count: the number of `SiteControl` rows on the site whose `status` is `IMPAIRED`. Controls in `PROPOSED`, `APPROVED`, `OPERATING` or `DECOMMISSIONED` do not contribute. The posture transitions follow directly: the parcel moves `OPEN → RESTRICTED` whenever that count rises from zero to a positive value while the defence is not forfeited, returns `RESTRICTED → OPEN` whenever the count falls back to zero while the defence is not forfeited, and moves `OPEN → FROZEN` or `RESTRICTED → FROZEN` the moment `bfpp_status` becomes `FORFEITED`. Because `FORFEITED` is absorbing — no transition anywhere in this specification restores it — `FROZEN` is absorbing as well.

Posture gates behaviour at two strengths. A `FROZEN` parcel refuses every mutating endpoint scoped to that site except for a closed set of seven operations, each of them either a compensating action, an adverse decision or a bookkeeping step the freeze has no reason to block: the compliance sweep, the void-certification compensating action, the logical-clock endpoint, a technical-branch decision of `REQUEST_REVISION` (§3.5), the public-comment close (§3.5), an eligibility decision of `REJECT` (§3.5), and an operation certification whose `condition` is `FAIL` (§3.7). Every other mutating operation scoped to the parcel is gated — a funding decision of `DENY` or `RESCIND` and the retirement of a control included — and the refusal is `ERR_SITE_FROZEN` (HTTP 409). A `RESTRICTED` parcel still permits ordinary work but refuses the four closure-critical operations that require the parcel to be fully `OPEN` — a completion request on an enrollment, issuance of a closure letter, lender acceptance of a closure letter, and a funding decision of `AWARD`. Those refusals carry `ERR_SITE_POSTURE_RESTRICTED` (HTTP 409). The distinction matters: an impaired control blocks closure even though the BFPP defence still stands.

### 2.6. Cascade Depth, Version Propagation and Conserved Quantities

Consistency in this system is immediate. When an operation touches more than one aggregate, every consequence lands inside the same request, and every row the cascade rewrites has its `updated_at` refreshed and its `version` incremented by 1. Cascades in this domain run several levels deep — a monitoring exceedance impairs a control, which restricts the parcel, which reverts a completion review, which revokes a closure letter, which rescinds every awarded grant — and the specification in §3 names each level explicitly. An implementation that stops at the first level will leave the file internally inconsistent.

Two quantities are conserved and may be relied on as invariants after any operation completes. First, on a liability protection, the sum of `current_weight`, `satisfied_weight`, `at_risk_weight` and `lapsed_weight` always equals `obligations_total_weight`. Second, in the funding assembly, the sum of every awarded application's `allocated_cents` plus the residual `unfunded_gap_cents` always equals the approved plan's `total_funding_need_cents`.

### 2.7. Path Resolution and Cross-Aggregate Coherence

URLs in this API are shallow — at most one path identifier followed by a sub-collection — but where a path carries an identifier, that identifier is resolved before anything in the body is examined, and where more than one identifier appears they are resolved strictly left to right. Each resource kind has its own not-found code so the caller can tell which segment failed: `ERR_SITE_NOT_FOUND`, `ERR_PHASE_NOT_FOUND`, `ERR_PROTECTION_NOT_FOUND`, `ERR_OBLIGATION_NOT_FOUND`, `ERR_ENROLLMENT_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_POLICY_NOT_FOUND`, `ERR_CONTROL_NOT_FOUND`, `ERR_AWARD_NOT_FOUND`, `ERR_LETTER_NOT_FOUND`, `ERR_EVENT_NOT_FOUND`, `ERR_GOAL_NOT_FOUND`, `ERR_FINDING_NOT_FOUND`, `ERR_PARTY_NOT_FOUND` and `ERR_LAB_NOT_FOUND`, each HTTP 404.

Foreign keys supplied in a request body are resolved after every path identifier, and among themselves in a fixed order: `site_id` first, then `vcp_enrollment_id`, then `remedial_action_plan_id`, then the party references (`owner_party_id`, `consultant_party_id`, `insurer_party_id`), then `laboratory_id`, then `cleanup_goal_id`, then `site_control_id`, and finally the assessment-phase references `aai_phase_id` and `basis_assessment_phase_id`. The first unresolvable reference determines the 404 code returned.

Because the entity graph is a directed acyclic graph rather than a tree, the server also enforces cross-aggregate coherence explicitly. A remedial action plan's `site_id` must equal its enrollment's `site_id`. A site control's `remedial_action_plan_id` must name a plan on the same site as the control. A monitoring event's `cleanup_goal_id` and `site_control_id` must both belong to the event's own site. A closure letter's `vcp_enrollment_id` must name an enrollment on the letter's own site. Any of these mismatches is `ERR_PLAN_SITE_MISMATCH` (HTTP 422).

### 2.8. Monetary Precision, Concentration Precision and Rounding

All money in this system is expressed in **integer cents**. There are no fractional cents anywhere in a request or a response, and every field whose name ends in `_cents` is an integer. Wherever a monetary intermediate is produced by multiplication, that intermediate is rounded to a whole number of cents at the step where this document says it is rounded — never earlier, never later. The rounding method is always **round half up**: a value exactly halfway between two candidates rounds away from zero.

The pinned-order discipline matters most in the remediation cost estimate, where each cost line is rounded to whole cents individually and only the rounded line values are summed. Summing the raw products and rounding once at the end produces a different total by whole cents and is wrong.

Two non-monetary quantities carry their own precision. A cleanup goal's `goal_ugl` is stored to 2 decimal places, round half up, and the rounding is applied exactly once — to the final selected value, not to the intermediates that produced it. A finding's `exceedance_factor` is likewise 2 decimal places, round half up. A liability protection's `compliance_pct` is stored to 4 decimal places, round half up. A cost-cap policy's `rate_applied` is stored to 3 decimal places, but the ratio the rate tier is selected from is compared **unrounded**, so a ratio that would round into a neighbouring tier still selects the tier its exact value falls in. A plan's `contingency_pct` is stored to 2 decimal places.

### 2.9. Version Pinning and Optimistic Concurrency Control

Two create operations in this system are guarded by optimistic concurrency control, because in both cases a second create is legitimate business behaviour — it supersedes an earlier artefact — so no state precondition can distinguish an intentional supersession from a client working off a stale view.

A `POST /remedial-action-plans` request must carry `expected_vcp_enrollment_version` as a required, non-optional field, holding the `version` of the target `VcpEnrollment` as the client last observed it. If that value does not equal the enrollment's current `version`, the create is rejected with `ERR_STALE_ENROLLMENT_VERSION` (HTTP 412). Filing a new plan legitimately supersedes any prior `DRAFT` or `REVISION_REQUESTED` plan on the same enrollment, so the stale enrollment version is the only signal that the client's picture of the enrollment — including which plan is current — is out of date.

A `POST /cost-cap-policies` request must carry `expected_remedial_action_plan_version` as a required, non-optional field, holding the `version` of the target `RemedialActionPlan` as the client last observed it. If that value does not equal the plan's current `version`, the quote is rejected with `ERR_STALE_PLAN_VERSION` (HTTP 412). A fresh quote legitimately supersedes the prior `QUOTED` policy on the same plan, so the stale plan version is what tells the server the underwriter priced against cost figures that a re-submit or an edit has since recomputed.

No other endpoint takes a version field. In particular, ordinary state-transition endpoints, edits and list reads accept no `expected_*_version` input, and supplying one has no effect.

A related but distinct mechanism operates on plan approval. When a plan is submitted, the server captures `pinned_cleanup_goal_versions`, a junction array with one entry per cleanup goal on the site, each entry recording a `cleanup_goal_id` and the `pinned_version` that goal's `version` held at submit time, ordered by the goal's `created_at` ascending. At approval every pin is re-validated against the goal's current `version`; any divergence is `ERR_PINNED_GOAL_VERSION_STALE` (HTTP 409). This is not an OCC input from the client — the client supplies nothing — it is a server-captured snapshot that makes goal re-derivation and plan approval mutually serialising.

### 2.10. Validation Precedence

Validations are evaluated in ascending priority order, and evaluation stops at the first violation: the first rule violated determines the response, and no later rule is even considered. Two requests that are each wrong in three ways therefore report only their earliest failure, and a test that expects a business error can be masked by an earlier structural one. The ordering, from earliest to latest, is:

1. **Header presence** — both auth headers present and non-blank, else `ERR_UNAUTHENTICATED`.
2. **Role authorisation** — the acting `X-User-Role` appears in the endpoint's role list, else `ERR_FORBIDDEN_ROLE`.
3. **Request shape** — every required field present, every type correct, every enum member recognised, every numeric range honoured, every date and datetime parseable, every conditional field pairing legal; else `ERR_INVALID_REQUEST`. An absent or empty request body is treated as an empty JSON object, so what gets reported is its missing required fields; a body that parses to anything other than a JSON object is itself `ERR_INVALID_REQUEST`. An explicit `null` counts exactly as an omission — fatal for a required field, and taking the documented default for an optional one — and body fields the endpoint does not document are ignored.
4. **Path existence** — every identifier in the URL resolves, left to right, else the resource-specific 404.
5. **Body reference existence** — every foreign key in the body resolves, in the order given in §2.7, else the resource-specific 404.
6. **Ownership** — the entity-backed role owns the resource it is acting on, else `ERR_NOT_RESOURCE_OWNER`.
7. **Segregation of duties** — the acting opaque reviewer is not the one barred from this action, else `ERR_SEGREGATION_OF_DUTIES`.
8. **Party typing** — a party referenced in a typed slot carries the required `party_type`, else `ERR_PARTY_TYPE_MISMATCH`.
9. **Uniqueness** — at most one liability protection per site, else `ERR_DUPLICATE_LIABILITY_PROTECTION`.
10. **Frozen-site gate** — the parcel is not `FROZEN`, else `ERR_SITE_FROZEN`.
11. **Open-posture gate** — for the four closure-critical operations, the parcel is `OPEN`, else `ERR_SITE_POSTURE_RESTRICTED`.
12. **State-machine precondition** — the target entity's current state permits the requested trigger, else the entity-specific state error.
13. **Fork-join gate** — the plan's two review branches are in the states the requested transition requires, else `ERR_JOIN_NOT_SATISFIED`.
14. **Optimistic concurrency** — the supplied expected parent version matches, else `ERR_STALE_ENROLLMENT_VERSION` or `ERR_STALE_PLAN_VERSION`.
15. **Safety and regulatory rules** (priorities 20 through 24) — delineation completeness, credited-control existence, controls-operating, closure-scope support and letter curability, and control-still-required, in that order.
16. **Temporal and resource-overlap rules** (priorities 25 through 29) — inquiry-versus-acquisition ordering, inquiry staleness, engineering-control coverage exclusivity, laboratory capacity, and the three certification/reporting windows, in that order.
17. **Cross-entity referential rules** (priorities 30 through 35) — Phase I approval, basis-phase eligibility, pinned goal versions, enrollment eligibility, completion prerequisites, and cross-aggregate coherence, in that order.
18. **Constraint-satisfaction rules** (priorities 36 through 42) — delineation prerequisite for enrollment, findings and goals prerequisites for submission, the two revision ceilings, funding documentation, the approved-plan bar on withdrawal, and plan editability, in that order.
19. **Fiscal rules** (priorities 50 through 52), evaluated last of all — attachment point, minimum limit, and funding-need/eligible-base determinacy.

Placing the safety family ahead of the referential and fiscal families is deliberate: a request that is simultaneously unsafe and unaffordable reports the safety failure, because the safety failure is the one the reviewer must act on. Placing the frozen-site gate ahead of every state-machine check is equally deliberate: a forfeited defence surfaces as `ERR_SITE_FROZEN` rather than being masked by whatever state the target child happens to be in.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Registry, the Parcel, and Taking Title

Before any environmental work can be recorded, the platform operator populates two registries. A `ProgramAdmin` registers each organisation that will participate, supplying its `legal_name` (1 to 160 characters, required), its `party_type`, its `state_code` (exactly two uppercase letters, the US state of registration) and, where applicable, its `licence_number`. `party_type` is one of `REDEVELOPER`, `CONSULTANT` or `INSURER`, and it determines whether the licence identifier is mandatory: a `CONSULTANT` or an `INSURER` must supply `licence_number` — at least one character long, with no upper length bound — while for a `REDEVELOPER` it is optional and defaults to null. The `id` returned by registration is the value that organisation's operators will send as `X-User-ID`. Parties can be listed with an optional `party_type` filter and retrieved individually.

The same operator maintains the accredited laboratory list. Each `Laboratory` carries a `lab_name` (1 to 120 characters), a `certification_code` (1 to 32 characters, the state accreditation code) and a `concurrent_capacity` between 1 and 10 inclusive — the maximum number of monitoring events whose analysis windows may overlap at that laboratory at any instant. Laboratories can be listed with an optional `certification_code` filter and retrieved individually.

A `Redeveloper` registers the brownfield parcel itself. The payload carries `owner_party_id` — which must resolve to a party whose `party_type` is `REDEVELOPER`, and which must equal the acting `X-User-ID`, since a redeveloper may only register sites it will own — plus `site_name` (1 to 160 characters), `county_code` (the regulator's county or district code for the parcel, 1 to 16 characters), `acreage` (strictly greater than zero, at most two decimal places), `intended_reuse`, and `planned_acquisition_date` as an ISO 8601 calendar date in `YYYY-MM-DD` form. `intended_reuse` is one of `RESIDENTIAL`, `RECREATIONAL`, `COMMERCIAL` or `INDUSTRIAL` and describes the post-redevelopment land use; it is the single most consequential input on the record, because it drives the exposure multiplier that sets every restricted-basis cleanup goal. An optional `institutional_control_committed` boolean defaults to false. If the referenced owner party is not a `REDEVELOPER`, registration is refused with `ERR_PARTY_TYPE_MISMATCH`.

A newly registered parcel starts in a known posture: `acquisition_status` is `UNDER_CONTRACT`, `acquisition_date` is null, `delineation_status` is `NONE`, `cleanup_posture` is `OPEN` and `impaired_control_count` is zero. The site list can be filtered by `owner_party_id` and by `cleanup_posture`, and an individual read exposes the three derived values alongside the inputs.

`institutional_control_committed` records that the redeveloper has committed in writing to record deed restrictions on the parcel. It is the prerequisite for any closure strategy that leans on institutional controls: the programme's design intent is that no restricted-basis cleanup goal is derived for a parcel whose commitment is still false, and the enforced gate on the flag is enrollment acceptance on the restricted-closure track, which is refused with `ERR_CONTROL_COMMITMENT_MISSING` while the flag is false.

Taking title is recorded separately from registration. The owning redeveloper reports the actual closing by supplying `acquisition_date`, which flips `acquisition_status` from `UNDER_CONTRACT` to `ACQUIRED` and stores the date. Any well-formed calendar date is accepted: the closing date is not required to fall on or after `planned_acquisition_date`, and it is not required to sit on or before the logical clock's current date. Only the owning redeveloper may record it, and only once — a second attempt on a parcel already `ACQUIRED` is refused with `ERR_SITE_ALREADY_ACQUIRED`. Recording title is not a bookkeeping no-op: it is one of the two conditions the BFPP defence needs, so the site's liability protection has its `bfpp_status` immediately recomputed (an inquiry already accepted as complete now yields `ESTABLISHED`) and both the protection's `version` and the site's `version` increment by 1.

While the parcel is still `UNDER_CONTRACT`, the acquisition **reference date** for all-appropriate-inquiries timing is `planned_acquisition_date`; once the parcel is `ACQUIRED`, the reference date is the actual `acquisition_date`. Every inquiry-timing rule in §3.4 reads whichever of the two applies.

### 3.2. Phased Site Assessment and Contaminant Delineation

Assessment proceeds in tiers, and each tier is one `AssessmentPhase` record opened by an `EnvironmentalConsultant`. The consultant supplies `site_id`, `consultant_party_id` (which must resolve to a `CONSULTANT` party — otherwise `ERR_PARTY_TYPE_MISMATCH`), a `phase_type` of `PHASE_I`, `PHASE_II` or `SUPPLEMENTAL`, the field-work window as `field_start_date` and `field_end_date` (both ISO 8601 dates, with `field_end_date` on or after `field_start_date`), and a `delineation_confidence` of `SCREENING`, `PARTIAL` or `FULL` recording how confident the consultant is that the plume boundary is closed. Two optional inputs complete the record. `aai_report_date` is the all-appropriate-inquiries report date: it is required when `phase_type` is `PHASE_I` and must be absent for any other tier, and it defaults to null. `delineation_complete` is a boolean, defaulting to false, by which the consultant asserts that every impacted media boundary has been closed; it is only meaningful for `PHASE_II` and `SUPPLEMENTAL` work. A third optional input, `supersedes_phase_id`, is a self-reference to the phase this one replaces — the mechanism by which `SUPPLEMENTAL` field work re-delineates a phase the agency rejected — and is null for an original phase. That reference need only resolve to an existing assessment phase, else `ERR_PHASE_NOT_FOUND`; the server does not additionally require the superseded phase to sit on the same parcel or to hold any particular `status`. A newly opened phase is in `DRAFT` with `review_round` zero, `findings_count` zero, `max_exceedance_factor` zero and `submitted_at`, `reviewed_by_user_id` and `review_comment` all null.

Analytical results are attached to a phase one finding at a time, and each one is immutable once written. A finding carries its parent `assessment_phase_id`, a `contaminant_code` (the analyte code, 1 to 24 uppercase characters — `TCE`, `PCE`, `LEAD` and the like), a `media` of `SOIL`, `GROUNDWATER` or `SOIL_VAPOR`, a `sample_location_code` naming the boring or well (`MW-3`, for example), a `max_concentration_ugl` of at least zero expressing the highest detected concentration in micrograms per litre (or micrograms per kilogram for soil, on the same numeric scale), the `screening_level_ugl` regulatory threshold for that analyte and media pair (strictly greater than zero), and an optional `delineated` boolean defaulting to false that asserts the lateral and vertical extent of this analyte is closed at this location. From those two concentrations the server derives `exceedance_factor`: the maximum concentration divided by the screening level, rounded half up to two decimal places. Recording a finding increments the phase's `findings_count` by 1, recomputes the phase's `max_exceedance_factor` as the largest `exceedance_factor` across all findings on the phase, and increments the phase's `version` by 1. Findings may only be added while the phase is in `DRAFT` or `REVISION_REQUESTED`; attaching one to a phase in any other state is `ERR_INVALID_PHASE_STATE`. Findings can be listed for a phase with an optional `media` filter, and read individually — but because the entity is immutable it carries neither `version` nor an update endpoint.

Submission for agency review is the consultant's act, and four conditions must hold. The parcel must not be `FROZEN`. The phase must carry at least one finding, so `findings_count` must be 1 or more — a phase with no findings is refused with `ERR_NO_FINDINGS`. A `PHASE_I` phase must have a non-null `aai_report_date`, else `ERR_INVALID_REQUEST`. And the acting `X-User-ID` must equal the phase's `consultant_party_id`. Submission sets `submitted_at` from the logical clock, increments `review_round` by 1, recomputes `max_exceedance_factor` from the phase's findings, and increments the phase's `version` by 1. The status movement is a two-step within one request: the phase advances `DRAFT → SUBMITTED` and then, automatically and in the same request, `SUBMITTED → UNDER_REVIEW`. No client ever observes a phase resting in `SUBMITTED` after the request completes; the automatic follow-on changes nothing but `status` and `updated_at`, and it too requires `findings_count` to be at least 1.

Agency review is a single decision endpoint taking a `decision` of `APPROVE` or `REQUEST_REVISION` plus an optional `review_comment` of 1 to 2000 characters, and it always records the deciding reviewer's opaque id as `reviewed_by_user_id`. The comment itself is a stored attribute of the phase: a `REQUEST_REVISION` decision writes the supplied `review_comment` onto the phase — null when the caller omits it — on either of the two landings that decision can take, while an `APPROVE` decision accepts the field and leaves the stored `review_comment` as it was. Approval requires that the parcel not be `FROZEN`, and it enforces the delineation-integrity rule: when the phase's `phase_type` is `PHASE_II` or `SUPPLEMENTAL` **and** its `delineation_complete` is true, every finding on that phase whose `exceedance_factor` is strictly greater than 1.0 must have `delineated` true. A phase claiming closed boundaries while an exceeding analyte remains open is refused with `ERR_MEDIA_NOT_DELINEATED`. Approval then cascades into the parcel's `delineation_status`: approving a `PHASE_I` phase moves it to `SCREENED` unless it is already `DELINEATED`, in which case it is left alone; approving a `PHASE_II` or `SUPPLEMENTAL` phase whose `delineation_complete` is true moves it to `DELINEATED`. Where `supersedes_phase_id` is set, the superseded phase keeps its own terminal status unchanged — history is preserved, never rewritten. The phase's `version` increments by 1, and the site's `version` increments by 1 as well whenever `delineation_status` actually changed. An approval reaches one level further, because §3.3's distinct-analyte count only sees findings that sit on `APPROVED` phases: every cleanup goal on the parcel has its `contaminant_count_in_media`, `goal_ugl` and `cumulative_cap_applied` recomputed and its attainment replay of §3.8 re-run inside the same request, and each goal whose derived figures actually changed has its `version` incremented by 1 while a goal that comes out identical is left untouched.

`REQUEST_REVISION` is where the revision cycle lives, and it is bounded. A revision may be requested while `review_round` is 2 or less, and the phase then moves `UNDER_REVIEW → REVISION_REQUESTED`, recording both `reviewed_by_user_id` and the `review_comment` and incrementing the phase's `version` by 1. From `REVISION_REQUESTED` the consultant may re-submit — again requiring an unfrozen parcel, at least one finding, and `review_round` of 2 or less — which closes the loop `REVISION_REQUESTED → SUBMITTED → UNDER_REVIEW → REVISION_REQUESTED` while incrementing `review_round`, recomputing `max_exceedance_factor` and bumping `version`. When a revision decision arrives on a phase whose `review_round` has reached 3, the phase is not returned for rework: it moves `UNDER_REVIEW → REJECTED` instead, recording `reviewed_by_user_id` and the `review_comment` and incrementing `version`. A fourth submit of that same phase is refused with `ERR_ASSESSMENT_REVISION_LIMIT`. On the submit endpoint that ceiling is evaluated **ahead of** the state precondition, notwithstanding the general ordering of §2.10: a phase whose `status` is `REJECTED`, and equally a phase whose `review_round` has already reached 3 in any status at all, reports `ERR_ASSESSMENT_REVISION_LIMIT` rather than `ERR_INVALID_PHASE_STATE`. `APPROVED` and `REJECTED` are both terminal, and a rejected phase can only be replaced by a new `SUPPLEMENTAL` phase whose `supersedes_phase_id` points back at it.

A revision request or a rejection on a `PHASE_I` phase reaches beyond the phase itself. When such a decision lands and the site has a liability protection record, that protection's `inquiry_state` becomes `AAI_DEFICIENT`, its `bfpp_status` is recomputed, and its `version` increments by 1. `AAI_DEFICIENT` is terminal within the inquiry dimension: the deficiency can only be cured by a superseding phase, and because no new protection record is created for the site, that protection can never reach `ESTABLISHED` again.

Phases can be listed with filters on `site_id`, `consultant_party_id`, `supersedes_phase_id`, `phase_type` and `status`, and read individually with `findings_count`, `max_exceedance_factor`, `reviewed_by_user_id` and `review_comment` exposed.

### 3.3. Deriving Risk-Based Cleanup Goals

A cleanup goal is the numeric target a single analyte in a single media must reach for the parcel to close. Either an `EnvironmentalConsultant` or the owning `Redeveloper` may derive one, supplying the `contaminant_code` the goal governs (1 to 24 characters; unlike a finding's analyte code it is not required to be uppercase), the `media` (`SOIL`, `GROUNDWATER` or `SOIL_VAPOR`), the `screening_level_ugl` used as the risk basis (strictly greater than zero), and the `basis`. Where `basis` is `RESTRICTED`, a `control_credit_type` naming the control whose exposure interruption is credited is required; where `basis` is `UNRESTRICTED`, `control_credit_type` must be absent and defaults to null. `control_credit_type` is one of `VAPOR_MITIGATION`, `ENGINEERED_CAP`, `GW_USE_RESTRICTION` or `DEED_RESTRICTION`. The triple of site, `contaminant_code` and `media` is unique: a repeat derivation for the same triple does not create a second row, it upserts the existing goal, recomputes `goal_ugl`, increments that goal's `version` by 1, and recomputes its `compliant_streak` and `attainment_status` against the newly derived target. The upsert answers **201 Created** exactly as a first derivation does, even though no new row came into existence; only `screening_level_ugl`, `basis` and `control_credit_type` are rewritten, the identifying `contaminant_code` and `media` being what selected the row.

The derivation runs in a pinned order, and rounding happens exactly once, at the very end.

**Step one — the exposure scenario.** When `basis` is `UNRESTRICTED`, the scenario is forced to residential regardless of what the parcel's `intended_reuse` says; when `basis` is `RESTRICTED`, the scenario is the parcel's `intended_reuse`. The scenario multiplier is 1.0 for a residential scenario, 2.5 for recreational, 3.5 for commercial and 8.0 for industrial. The scenario goal is the supplied `screening_level_ugl` multiplied by that scenario multiplier.

**Step two — the control credit.** A `RESTRICTED` goal multiplies the scenario goal by the credit factor of the control it names: 10.0 for `VAPOR_MITIGATION`, 4.0 for `ENGINEERED_CAP`, 6.0 for `GW_USE_RESTRICTION`, and 1.0 for `DEED_RESTRICTION` (a deed restriction alone interrupts no exposure pathway, so it earns no relief). An `UNRESTRICTED` goal takes no control credit at all — the credited value equals the scenario goal.

**Step three — media attenuation.** The credited value is divided by the media's attenuation divisor: 1.0 for `SOIL`, 1.0 for `GROUNDWATER`, and 0.03 for `SOIL_VAPOR`. Because the soil-vapour divisor is less than one, dividing by it raises the vapour target; this is the vapour-intrusion attenuation factor and it is applied as a division by 0.03, never as a multiplication.

**Step four — the cumulative risk budget.** The parcel carries a total risk budget of 500.0 micrograms per litre per media, and that budget is shared among the analytes actually driving risk in that media. The server counts `contaminant_count_in_media` as the number of **distinct** `contaminant_code` values that satisfy three conditions simultaneously: the finding's `media` equals this goal's media, the finding's `exceedance_factor` is strictly greater than 1.0, and the finding belongs to an assessment phase on this site whose `status` is `APPROVED`. Findings on phases in `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `REVISION_REQUESTED` or `REJECTED` are excluded entirely. Because the count is over distinct analyte codes, two wells reporting the same analyte count once. The cumulative cap is 500.0 divided by the greater of 1 and that distinct count — so a media with no qualifying analytes still divides by 1 rather than by zero.

**Step five — selection, floor and rounding.** The candidate target is the smaller of the attenuated value and the cumulative cap. The programme will not set a goal below the practical quantitation floor of 0.50 micrograms per litre, so the selected value is the larger of that floor and the candidate. That single selected value is then rounded half up to two decimal places and stored as `goal_ugl`. The boolean `cumulative_cap_applied` is set true exactly when the cumulative cap was strictly below the attenuated value **and** the cumulative cap was strictly above the practical quantitation floor — that is, when the shared risk budget, rather than the scenario-and-control arithmetic or the floor, is what actually determined the target. It defaults to false.

The two bases behave very differently in practice, and both deserve equal attention. An `UNRESTRICTED` goal pins the scenario multiplier at 1.0 and forgoes any control credit, so it produces the strictest of the two targets and needs no control to be built. A `RESTRICTED` goal uses the parcel's actual `intended_reuse` multiplier and then multiplies again by the control credit, which frequently pushes the arithmetic well above the shared risk budget — with the consequence that the cumulative cap, not the control credit, is what sets the number, and `cumulative_cap_applied` comes back true. A `RESTRICTED` goal also creates an obligation downstream: the remedy must actually build a control of the credited type, which §3.5 enforces at approval.

Newly derived goals begin with `attainment_status` `NOT_ATTAINED` and `compliant_streak` zero; both are driven exclusively by the monitoring replay described in §3.8. Goals can be listed for a parcel with optional `media` and `basis` filters, and read individually.

### 3.4. The Bona Fide Prospective Purchaser Defence and Its Continuing Obligations

The BFPP defence is the reason a redeveloper touches a contaminated parcel at all, and the system models it as a single record per parcel carrying **two independent state dimensions** plus a derived verdict. The owning `Redeveloper` opens the file by supplying only `site_id`; at most one such record may exist per parcel, and a second attempt is refused with `ERR_DUPLICATE_LIABILITY_PROTECTION` (HTTP 409). A freshly opened record has `inquiry_state` `AAI_PENDING`, `obligation_state` `OBLIGATIONS_NONE`, `bfpp_status` `NOT_ESTABLISHED`, all four weight buckets — `obligations_total_weight`, `current_weight`, `satisfied_weight`, `at_risk_weight` and `lapsed_weight` — at zero, `compliance_pct` at 1.0, and `aai_phase_id`, `aai_report_date` and `aai_expires_on` all null. The parcel's protection record can be listed from the site (a collection of zero or one element) or read directly.

**The inquiry dimension.** `inquiry_state` is one of `AAI_PENDING`, `AAI_COMPLETE`, `AAI_STALE` or `AAI_DEFICIENT`, and it tracks whether the all-appropriate-inquiries record is good. An `EnvironmentalConsultant` moves it forward by nominating a completed inquiry: the payload carries `aai_phase_id`, the identifier of the assessment phase being accepted as the AAI record, stored on the protection as a plain reference alongside the `aai_report_date` copied from that phase. Three conditions must all hold, and each has its own refusal. The nominated phase must be an assessment phase on **this protection's site** with `phase_type` `PHASE_I` and `status` `APPROVED`, else `ERR_PHASE_I_NOT_APPROVED`. The `aai_report_date` must fall on or before the acquisition reference date — the actual `acquisition_date` when the parcel is `ACQUIRED`, otherwise the `planned_acquisition_date` — because an inquiry completed after taking title cannot support the defence; a later date is `ERR_AAI_AFTER_ACQUISITION`. And the report must be recent: the number of days between the reference date and the `aai_report_date` must be at most 180, counted inclusively, so a report exactly 180 days old is accepted and one 181 days old is refused with `ERR_AAI_REPORT_STALE`. On acceptance the server stores `aai_phase_id` and `aai_report_date`, derives `aai_expires_on` as the `aai_report_date` advanced by 365 days, recomputes `bfpp_status`, and increments the protection's `version` by 1.

That transition serves two source states symmetrically. From `AAI_PENDING` it is the first completion; from `AAI_STALE` it is a cure, overwriting `aai_phase_id`, `aai_report_date` and `aai_expires_on` with the fresher inquiry, recomputing `bfpp_status` and incrementing `version` by 1 exactly as before. Staleness is therefore curable, and the inquiry dimension genuinely cycles. Deficiency is not curable on the same record: filing an inquiry completion against a protection whose `inquiry_state` is already `AAI_DEFICIENT` is refused with `ERR_INQUIRY_DEFICIENT` (HTTP 409). That same code answers a nomination filed against a protection whose `inquiry_state` is already `AAI_COMPLETE`, because the transition accepts no source state other than `AAI_PENDING` and `AAI_STALE`.

Staleness itself arrives from the ops-run checkpoint described in §3.9. A protection whose `inquiry_state` is `AAI_COMPLETE` moves to `AAI_STALE` when the sweep's `as_of_date` is strictly later than `aai_expires_on` **and** the parcel is still `UNDER_CONTRACT` — an inquiry that has aged past a year while the deal has not closed no longer supports the defence. The sweep recomputes `bfpp_status`, which becomes `NOT_ESTABLISHED`, and increments the protection's `version` by 1. Once title has been taken the expiry no longer bites, because the inquiry's job was to establish the buyer's diligence at the moment of purchase.

**The obligation dimension.** `obligation_state` is one of `OBLIGATIONS_NONE`, `CURRENT`, `AT_RISK` or `LAPSED`, and it is entirely derived from the continuing obligations hanging off the protection. A `StateAgencyReviewer` imposes each duty, supplying the `obligation_category`, a free-text `description` of 1 to 400 characters recorded in the enrollment file, the `due_date` on which the current certification period closes — any well-formed calendar date, the server not requiring it to sit on or after the logical clock's current date — and `recurrence_days` — at least 30, with no upper bound — being the number of days added to `due_date` each time a certification is accepted, which opens the next period. The five categories are `REASONABLE_STEPS`, `LAND_USE_RESTRICTION_COMPLIANCE`, `ACCESS_AND_COOPERATION`, `INSTITUTIONAL_CONTROL_MAINTENANCE` and `NOTIFICATION`. Two of them — `REASONABLE_STEPS` and `LAND_USE_RESTRICTION_COMPLIANCE` — are **defence-critical**: if either lapses, the defence is forfeited outright. A newly imposed duty is `CURRENT` with `certification_count` zero and both `certified_at` and `prior_due_date` null; its `liability_protection_id` is taken from the protection named in the path rather than from the request body, and the acting reviewer's opaque id is stored as `imposed_by_user_id` for the later segregation-of-duties check. Imposing a duty requires the parcel not be `FROZEN`, recomputes the weight buckets and `compliance_pct`, moves the protection's obligation dimension `OBLIGATIONS_NONE → CURRENT` on the first duty imposed — a later imposition does not force `CURRENT`, it simply re-reads the dimension from the recomputed figures by the order of precedence below, so a protection already carrying a lapsed defence-critical duty stays `LAPSED` — recomputes `bfpp_status` and increments the protection's `version` by 1. The duties on a protection can be listed with optional `status` and `obligation_category` filters, and read individually with their certification counters.

**The weighted compliance figure.** Each category carries a statutory weight: `REASONABLE_STEPS` weighs 5, `LAND_USE_RESTRICTION_COMPLIANCE` weighs 5, `INSTITUTIONAL_CONTROL_MAINTENANCE` weighs 4, `ACCESS_AND_COOPERATION` weighs 3, and `NOTIFICATION` weighs 3. `obligations_total_weight` is the sum of those weights over **every** duty on the protection, regardless of status — there is no soft delete, so a lapsed duty still sits in the denominator. `current_weight`, `satisfied_weight`, `at_risk_weight` and `lapsed_weight` are the sums of the weights of the duties whose `status` is respectively `CURRENT`, `SATISFIED`, `AT_RISK` and `LAPSED`, and by construction those four always add up to `obligations_total_weight`. The numerator of the compliance figure counts `current_weight` in full, `satisfied_weight` in full, half of `at_risk_weight`, and none of `lapsed_weight`. When `obligations_total_weight` is zero, `compliance_pct` is exactly 1.0; otherwise `compliance_pct` is that numerator divided by `obligations_total_weight`, rounded half up to four decimal places.

`obligation_state` is then read off in a fixed order of precedence. If `obligations_total_weight` is zero the dimension is `OBLIGATIONS_NONE`. Otherwise, if any duty with a defence-critical category has `status` `LAPSED`, the dimension is `LAPSED`. Otherwise, if `compliance_pct` is greater than or equal to 0.85 the dimension is `CURRENT` — the comparison is inclusive, so a `compliance_pct` of exactly 0.8500 stays `CURRENT`. Otherwise the dimension is `AT_RISK`.

**The derived verdict.** `bfpp_status` is one of `NOT_ESTABLISHED`, `ESTABLISHED` or `FORFEITED`, and it reads both dimensions plus the parcel's `acquisition_status` in a fixed order. If `obligation_state` is `LAPSED`, `bfpp_status` is `FORFEITED`. Otherwise, if `inquiry_state` is `AAI_COMPLETE` **and** `acquisition_status` is `ACQUIRED`, `bfpp_status` is `ESTABLISHED`. Otherwise it is `NOT_ESTABLISHED`. `FORFEITED` is absorbing: once written it is never recomputed away, which is why an unfinished inquiry is a recoverable setback while a lapsed defence-critical duty is not.

Crossing 0.85 downward is a warning, not a forfeiture. When a duty entering `AT_RISK` or `LAPSED` drives `compliance_pct` below 0.85 while no defence-critical duty has lapsed, the protection moves `CURRENT → AT_RISK`, its four buckets and `compliance_pct` are recomputed, `bfpp_status` stays `ESTABLISHED`, and `version` increments by 1. The reverse edge exists too: when a certification restores `compliance_pct` to 0.85 or above and no defence-critical duty has lapsed, the protection moves `AT_RISK → CURRENT`, recomputing the buckets and `compliance_pct` and incrementing `version` by 1. Forfeiture is the different story. When any duty in `REASONABLE_STEPS` or `LAND_USE_RESTRICTION_COMPLIANCE` enters `LAPSED`, the protection moves `CURRENT → LAPSED` (or `AT_RISK → LAPSED` from the warning state — both edges behave identically), `bfpp_status` becomes `FORFEITED`, the parcel's `cleanup_posture` becomes `FROZEN`, and both the protection's `version` and the site's `version` increment by 1. Because `FORFEITED` is absorbing, the obligation dimension never leaves `LAPSED` afterwards along any ordinary path; the single exception is the void-certification compensating action described below, which — where the lapsed defence-critical duty carries a certification to void — restores that duty and lets the dimension be recomputed to `CURRENT` or `AT_RISK` while `bfpp_status` stays `FORFEITED` and the parcel stays `FROZEN`.

**Certifying a period.** The owning `Redeveloper` certifies performance for the open period. Three conditions apply: the acting `X-User-ID` must equal the site's `owner_party_id`, the parcel must not be `FROZEN`, and the logical clock's current date must be on or before the duty's `due_date` — certifying after the period has closed is `ERR_CERTIFICATION_WINDOW_CLOSED`. Certification is available from `CURRENT` and from `AT_RISK`, and both source states produce the identical effect set: the current `due_date` is copied into `prior_due_date`, then `due_date` is advanced by `recurrence_days`; `certified_at` is set from the logical clock; `certification_count` increments by 1; the duty's `status` becomes `SATISFIED`; the protection's four weight buckets and `compliance_pct` are recomputed; and both the duty's `version` and the protection's `version` increment by 1. Certifying from `AT_RISK` carries the additional consequence that if the recomputed `compliance_pct` has returned to 0.85 or above, the protection's obligation dimension returns to `CURRENT`. Certifying a duty that is already `SATISFIED`, or one that has `LAPSED`, is refused with `ERR_INVALID_OBLIGATION_STATE`.

**Voiding a certification.** Because an accepted certification can turn out to have been filed on bad information, a compensating action exists — and it is one of the operations §2.5 permits even on a `FROZEN` parcel. A `StateAgencyReviewer` supplies a `void_reason` of 1 to 400 characters. The acting reviewer's `X-User-ID` must differ from the duty's `imposed_by_user_id`, and — tested after that segregation check, following §2.10 — the duty must have `certification_count` of at least 1, otherwise `ERR_INVALID_OBLIGATION_STATE`. The duty's own `status` is not a precondition: `CURRENT`, `AT_RISK`, `SATISFIED` and even `LAPSED` may all be voided so long as an accepted certification is there to void. The restoration is exact: `due_date` is restored verbatim from `prior_due_date`, `certified_at` is cleared, `prior_due_date` is set back to null, `certification_count` decrements by 1, and the protection's weight buckets and `compliance_pct` are recomputed to exactly the values they held before the certification was accepted. Only one period is remembered, so a second consecutive void on the same duty — reaching back past a certification whose `prior_due_date` the first void already cleared — still decrements `certification_count` and clears `certified_at`, but leaves `due_date` exactly where it stands. Both the duty's `version` and the protection's `version` increment by 1. Which state the duty lands in depends on how much of the restored period remains against the logical clock: if the restored `due_date` is more than 30 days in the future the duty returns to `CURRENT`; if it is between 0 and 30 days in the future inclusive — inside the grace window — the duty returns to `AT_RISK` instead, as does a restored `due_date` that has already passed, the void never landing a duty back in `LAPSED`. The restoration itself is identical in both cases; only the landing state and the resulting `compliance_pct` differ.

### 3.5. Enrollment in the Programme and the Remedial Action Plan

Enrollment is the redeveloper's formal request that the agency supervise the cleanup and, in exchange, issue closure at the end. The owning `Redeveloper` applies by supplying `site_id`, a `program_track`, and an `applicant_statement` of 1 to 600 characters narrating the intended reuse and the remedy concept. The track is either `UNRESTRICTED_CLOSURE`, which forbids the remedy from crediting any control, or `RESTRICTED_CLOSURE`, which permits engineering and institutional controls to carry part of the risk reduction. An application may only be filed once the parcel has at least been screened — `delineation_status` must not be `NONE`, meaning an approved `PHASE_I` phase exists — otherwise the application is refused with `ERR_DELINEATION_REQUIRED`. A new enrollment starts with `reverted_completion_count` at zero, `enrolled_on` null, `eligibility_decided_by_user_id` null and `completion_requested_at` null, and its status advances `APPLIED → ELIGIBILITY_REVIEW` automatically inside the creating request, changing nothing but `status` and `updated_at`, so no client observes an enrollment resting in `APPLIED`.

A `StateAgencyReviewer` then decides eligibility with a `decision` of `ENROLL` or `REJECT` plus an optional `decision_note` of 1 to 600 characters. Accepting the application requires three things: the parcel's liability protection must exist and its `inquiry_state` must be `AAI_COMPLETE` — a cross-entity guard refused with `ERR_ENROLLMENT_NOT_ELIGIBLE` when the protection is missing or the inquiry is anything other than complete; the parcel must not be `FROZEN`; and a `RESTRICTED_CLOSURE` track additionally requires the parcel's `institutional_control_committed` to be true, refused with `ERR_CONTROL_COMMITMENT_MISSING` when it is false. The inquiry guard is evaluated ahead of the track guard, so an application that fails both reports `ERR_ENROLLMENT_NOT_ELIGIBLE`. Acceptance moves the enrollment `ELIGIBILITY_REVIEW → ENROLLED`, sets `enrolled_on` from the logical clock's date, records `eligibility_decided_by_user_id`, and increments the enrollment's `version` by 1. Rejection has no preconditions at all: it moves the enrollment `ELIGIBILITY_REVIEW → REJECTED`, which is terminal, records `eligibility_decided_by_user_id`, and increments `version` by 1. Deciding eligibility a second time is `ERR_INVALID_ENROLLMENT_STATE`, as is any other trigger the current status does not permit — filing a plan against a terminal enrollment, requesting completion outside `IMPLEMENTATION`, or withdrawing an enrollment whose status is anything other than `ENROLLED`. Enrollments can be listed for a parcel with an optional `status` filter and read individually.

Withdrawal is the owner's exit, available only from `ENROLLED` and only while no plan on the enrollment has reached `APPROVED` — an attempt against an approved remedy is refused with `ERR_APPROVED_PLAN_EXISTS`. The two guards are ordered by §2.10, the state-machine precondition ahead of the approved-plan bar, and that ordering is observable: because approving a plan has already cascaded the enrollment `ENROLLED → REMEDY_APPROVED`, a withdrawal attempted after remedy approval reports `ERR_INVALID_ENROLLMENT_STATE` (HTTP 409), and `ERR_APPROVED_PLAN_EXISTS` (HTTP 409) is reached only by an enrollment still resting in `ENROLLED` that nonetheless carries an `APPROVED` plan. The owning redeveloper supplies a `withdrawal_reason` of 1 to 600 characters. Withdrawal cascades two levels: at the first level, every remedial action plan on this enrollment whose `status` is `DRAFT`, `SUBMITTED`, `UNDER_TECHNICAL_REVIEW`, `PUBLIC_COMMENT` or `REVISION_REQUESTED` becomes `WITHDRAWN` with its `version` incremented by 1; at the second level, every cost-cap policy on those plans whose `status` is `QUOTED` becomes `CANCELLED` with its `version` incremented by 1. The enrollment's own `version` increments by 1 as well. `WITHDRAWN` is terminal for the enrollment.

**Filing the plan.** An `EnvironmentalConsultant` files a remedial action plan against the enrollment. The payload names `vcp_enrollment_id` and, denormalised, the `site_id` — which must equal the enrollment's own site, or the request is refused with `ERR_PLAN_SITE_MISMATCH`. It carries a `remedy_narrative` of 1 to 600 characters describing the selected remedy, a `basis_assessment_phase_id` pointing at the approved delineation work that supports it — a reference that at filing time need only resolve to some existing assessment phase, its eligibility being tested at submission — `years_to_construction_start` as a whole number of years between approval and construction mobilisation (at least 0 and at most 10), the `cost_lines` array, and the concurrency field `expected_vcp_enrollment_version` described in §2.9. Each element of `cost_lines` is an object with four keys: a `cost_category` of `EXCAVATION_DISPOSAL`, `GW_TREATMENT`, `VAPOR_MITIGATION`, `MONITORING` or `OVERSIGHT`; a `media` of `SOIL`, `GROUNDWATER` or `SOIL_VAPOR`; a `quantity` strictly greater than zero; and a `unit_cost_cents` integer strictly greater than zero. The array must hold between 1 and 12 elements and its order is significant, because §3.6 evaluates the lines in array order. A newly filed plan sits in `DRAFT` with `technical_review_state` `NOT_STARTED`, `public_comment_state` `NOT_STARTED`, `revision_round` zero, `pinned_cleanup_goal_versions` an empty array, `approved_by_user_id` null and `approved_at` null. Filing immediately runs the design-basis estimate of §3.6, writing `direct_cost_cents`, `escalation_cents`, `contingency_pct`, `contingency_cents`, `oversight_cents` and `total_estimate_cents`, and setting `total_funding_need_cents` equal to `total_estimate_cents` — no insurance premium has been placed yet. Filing also increments the parent enrollment's `version` by 1.

Editing a filed plan is the consultant's privilege too, and it accepts any subset of `remedy_narrative`, `basis_assessment_phase_id`, `years_to_construction_start` and `cost_lines`, the empty subset included. It is permitted only while the plan's `status` is `DRAFT` or `REVISION_REQUESTED`; an edit against any other status is refused with `ERR_PLAN_NOT_EDITABLE` (HTTP 409). An accepted edit immediately re-runs the design-basis estimate over the new inputs, rewriting all seven cost figures including `total_funding_need_cents`, and increments the plan's `version` by 1. Outstanding `QUOTED` cost-cap policies are deliberately **not** re-priced by an edit — the underwriter's attachment point was set against the figures it was shown, and it is the bind-time attachment test in §3.6 that catches a plan that has drifted upward since the quote. Plans can be listed with filters on `vcp_enrollment_id`, `site_id` and `status`, and read individually with every cost figure, both branch dimensions and the goal pins exposed.

**Submission forks the review.** Submitting a plan requires four things: the parcel must not be `FROZEN`; the parent enrollment's `status` must be `ENROLLED`; the `basis_assessment_phase_id` must reference an assessment phase on the plan's own site whose `phase_type` is `PHASE_II` or `SUPPLEMENTAL`, whose `status` is `APPROVED` and whose `delineation_complete` is true, else `ERR_BASIS_PHASE_INELIGIBLE`; and at least one cleanup goal must exist on the site, else `ERR_NO_CLEANUP_GOALS`. Submission then does three things in one request. It forks the review into two independent branches, setting `technical_review_state` to `NOT_STARTED` and `public_comment_state` to `OPEN`. It captures `pinned_cleanup_goal_versions` — one entry per cleanup goal on the site, each holding that goal's `cleanup_goal_id` and its current `version` as `pinned_version`, the entries ordered by the goal's `created_at` ascending. And it recomputes every design-basis cost figure. The plan's `version` increments by 1, and the status advances `DRAFT → SUBMITTED` and then automatically `SUBMITTED → UNDER_TECHNICAL_REVIEW` in the same request, the automatic step requiring `public_comment_state` to be `OPEN` and touching nothing but `status` and `updated_at`.

**The technical branch.** A `StateAgencyReviewer` decides the technical branch with a `decision` of `PASS` or `REQUEST_REVISION` plus an optional `review_comment` of 1 to 2000 characters, which is validated but not persisted — the plan carries no review-comment attribute. A `PASS` requires the parcel not be `FROZEN` and requires that every cleanup goal on the site whose `basis` is `RESTRICTED` have a `goal_ugl` greater than or equal to that same goal's own stored `screening_level_ugl` — a restricted goal stricter than the underlying screening level signals an incoherent risk basis and the branch may not pass, the refusal carrying `ERR_INVALID_PLAN_STATE`. A passing decision sets `technical_review_state` to `PASSED`, moves the plan `UNDER_TECHNICAL_REVIEW → PUBLIC_COMMENT`, and increments the plan's `version` by 1. It touches **no** cost figure whatsoever; that asymmetry against the other branch is deliberate.

A `REQUEST_REVISION` decision on the technical branch is bounded: it may be issued only while `revision_round` is 1 or less, and a third revision request is refused with `ERR_PLAN_REVISION_LIMIT` (HTTP 409). Unlike a `PASS`, it is not gated on the parcel's posture at all — a revision may be requested even on a `FROZEN` parcel. When issued, the plan moves `UNDER_TECHNICAL_REVIEW → REVISION_REQUESTED`, `revision_round` increments by 1, `public_comment_state` resets to `NOT_STARTED` and `public_comment_count` resets to zero because the comment period is void, `pinned_cleanup_goal_versions` is cleared to an empty array, and every cost-cap policy on this plan whose `status` is `QUOTED` becomes `CANCELLED` with its `version` incremented by 1. The plan's own `version` increments by 1. From `REVISION_REQUESTED` the consultant may re-submit — requiring an unfrozen parcel, an `ENROLLED` enrollment, and `revision_round` of 2 or less — which re-forks the branches to `NOT_STARTED` and `OPEN`, re-pins `pinned_cleanup_goal_versions` from the goals' current versions, recomputes every design-basis cost figure, increments `version` by 1, and closes the loop `REVISION_REQUESTED → SUBMITTED → UNDER_TECHNICAL_REVIEW`.

**The public-participation branch.** The same reviewer role closes the comment period, supplying `public_comment_count` as the number of comments logged, an integer of zero or more. The plan's `status` must be `UNDER_TECHNICAL_REVIEW` or `PUBLIC_COMMENT`, else `ERR_INVALID_PLAN_STATE`, and that state test is settled first; only then does the branch test apply, which requires `public_comment_state` to be `OPEN` **and** `technical_review_state` to already be `PASSED`; closing the comment period before the technical branch has passed is refused with `ERR_JOIN_NOT_SATISFIED` (HTTP 409). Like the technical branch's revision request, this action is not gated on the parcel's posture. Closing stores `public_comment_count`, advances `public_comment_state` `OPEN → CLOSED`, and increments the plan's `version` by 1. The plan's `status` stays `PUBLIC_COMMENT` throughout — only the branch dimension moves — and, mirroring the technical branch's refusal to touch cost figures, this branch touches no technical field.

**The join.** Approval is the join point, and it enforces four conditions. The parcel must not be `FROZEN`. The join itself must be satisfied: `technical_review_state` must be `PASSED` and `public_comment_state` must be `CLOSED`, else `ERR_JOIN_NOT_SATISFIED`. For every cleanup goal on the site whose `basis` is `RESTRICTED`, this plan must carry a site control whose `control_type` equals that goal's `control_credit_type` and whose `status` is `PROPOSED`, `APPROVED` or `OPERATING` — a risk-based goal that credits a control the remedy does not build is refused with `ERR_CREDITED_CONTROL_MISSING`. And every entry of `pinned_cleanup_goal_versions` must still match the referenced goal's current `version`, else `ERR_PINNED_GOAL_VERSION_STALE`. Approval records `approved_by_user_id` and `approved_at`, then cascades: every site control on this plan whose `status` is `PROPOSED` becomes `APPROVED` with its `next_certification_due_on` recomputed and its `version` incremented by 1; the parent enrollment moves `ENROLLED → REMEDY_APPROVED` with its `version` incremented by 1; and every **other** remedial action plan on the same enrollment whose `status` is `DRAFT` or `REVISION_REQUESTED` becomes `WITHDRAWN` with its `version` incremented by 1. The approved plan's own `version` increments by 1. `APPROVED` and `WITHDRAWN` are the plan's terminal states, and reviewing a `DRAFT` plan, approving from any state other than `PUBLIC_COMMENT`, or submitting an `APPROVED` or `WITHDRAWN` plan are all refused with `ERR_INVALID_PLAN_STATE`.

**Completion and its reversal.** Once the remedy is built and operating, the owning `Redeveloper` asks the agency to review completion. Four conditions apply: the acting `X-User-ID` must equal the site's `owner_party_id`; the parcel's `cleanup_posture` must be `OPEN`; every cleanup goal on the site must have `attainment_status` `ATTAINED`, else `ERR_GOALS_NOT_ATTAINED`; and every site control on this enrollment's approved plan must have `status` `OPERATING`, else `ERR_CONTROLS_NOT_OPERATING` — a check skipped outright when the enrollment carries no `APPROVED` plan. Those last two are evaluated goals-first, notwithstanding §2.10's placement of the controls-operating rule in the safety family, so a request failing both reports `ERR_GOALS_NOT_ATTAINED`. The request sets `completion_requested_at` from the logical clock, moves the enrollment `IMPLEMENTATION → COMPLETION_REVIEW`, and increments `version` by 1. That state is not a commitment: completion review is reversible for as long as controls can fail. When a site control belonging to this enrollment's approved plan enters `IMPAIRED`, the enrollment is pushed back `COMPLETION_REVIEW → IMPLEMENTATION`, `reverted_completion_count` increments by 1, and `version` increments by 1. The enrollment reaches `IMPLEMENTATION` in the first place as a cascade from the first passing operation certification on a control belonging to this enrollment's plan, moving `REMEDY_APPROVED → IMPLEMENTATION` with `version` incremented by 1, and it reaches the terminal `CLOSED` state only as a cascade from the issuance of the parcel's closure letter, again incrementing `version` by 1.

### 3.6. Estimating the Remediation and Placing the Cost Cap

Two different parties need a number for the same remedy, and they are entitled to different numbers. The agency and the redeveloper want the **design-basis** estimate: what the remedy should cost on the schedule the plan actually proposes. The carrier writing the stop-loss cover wants the **underwriting-basis** estimate: what the remedy could cost on a pessimistic schedule with a floor under the contingency. Both estimates run the identical five-step arithmetic over the identical `cost_lines`; they differ in exactly two inputs, and the underwriting figure is therefore never smaller than the design figure for the same lines whenever the plan's `years_to_construction_start` is below five or its contingency tier sits below twenty-five percent.

**Step one — the direct cost, line by line.** The lines of `cost_lines` are evaluated **in array order**, and each is rounded to whole cents individually before any summing happens. A single line's cost is its `quantity` multiplied by its `unit_cost_cents` multiplied by the media factor for that line's `media` — 1.00 for `SOIL`, 1.35 for `GROUNDWATER` and 1.15 for `SOIL_VAPOR`, groundwater work carrying a thirty-five percent premium and vapour work fifteen percent — with that product rounded half up to a whole number of cents. `direct_cost_cents` is the sum of those already-rounded line values. Summing the raw products and rounding the total once at the end yields a different figure by whole cents and is not what this specification requires. Every element of `cost_lines` participates; there is no status filter, because cost lines are immutable inputs supplied when the plan is filed or edited.

**Step two — escalation to the construction date.** Escalation runs at 4.2 percent of the direct cost per year. The design basis escalates over the plan's own `years_to_construction_start`; the underwriting basis escalates over a fixed five years regardless of what the plan proposes. `escalation_cents` is the direct cost multiplied by 0.042 multiplied by the applicable number of years, rounded half up to whole cents. A design-basis plan mobilising immediately, with `years_to_construction_start` at zero, therefore carries no escalation at all, while the same plan's underwriting estimate carries five years of it.

**Step three — contingency, from the delineation confidence.** The contingency rate is read from the `delineation_confidence` of the **single** assessment phase named by the plan's `basis_assessment_phase_id` — never from any other phase on the parcel. A `SCREENING` confidence sets the base rate at 35 percent, `PARTIAL` at 20 percent, and `FULL` at 10 percent. A five-percentage-point adder is applied on top when that same basis phase's `max_exceedance_factor` is greater than or equal to 10.0, and no adder is applied when it is below 10.0 — a plume an order of magnitude above screening levels earns extra reserve. Under the design basis, `contingency_pct` is exactly that base rate plus the adder. Under the underwriting basis, `contingency_pct` is the larger of that same sum and a 25-percent floor. `contingency_cents` is the sum of `direct_cost_cents` and `escalation_cents`, multiplied by `contingency_pct`, rounded half up to whole cents.

**Step four — agency oversight, capped.** The subtotal is `direct_cost_cents` plus `escalation_cents` plus `contingency_cents`. Oversight runs at 6.5 percent of that subtotal, rounded half up to whole cents, but it is capped: `oversight_cents` is the smaller of that rounded figure and 4,000,000 cents (a hard ceiling of 40,000.00 in agency oversight, however large the remedy).

**Step five — the total.** The total is `direct_cost_cents` plus `escalation_cents` plus `contingency_cents` plus `oversight_cents`. Under the design basis that total is stored on the plan as `total_estimate_cents`; under the underwriting basis it is stored on the cost-cap policy as `underwriting_estimate_cents`. A plan's `total_funding_need_cents` is its `total_estimate_cents` plus the `premium_cents` of every cost-cap policy on that plan whose `status` is `BOUND` — quoted, superseded and cancelled policies contribute nothing.

**Quoting the cap.** An `Insurer` quotes a policy against a plan, supplying `remedial_action_plan_id`, `insurer_party_id` (which must resolve to a party whose `party_type` is `INSURER`, else `ERR_PARTY_TYPE_MISMATCH`, and which must equal the acting `X-User-ID`), a `policy_reference` of 1 to 64 characters carrying the carrier's own reference string, a `term_years` between 1 and 10 inclusive, and the concurrency field `expected_remedial_action_plan_version` from §2.9. The plan's own `status` is not a precondition of quoting — a quote may be struck against a plan in `DRAFT`, in either review branch, in `APPROVED` or even in `WITHDRAWN`; it is binding, not quoting, that demands an `APPROVED` plan. Quoting runs the underwriting-basis estimate over the plan's `cost_lines` and its basis assessment phase, then derives the placement in a strictly pinned order. This is the part of the system that looks circular and is not: a plan's `total_funding_need_cents` includes the premium, and the cap limit looks like a function of the funding need — but the limit and the premium are derived from the **pre-premium** `underwriting_estimate_cents` alone, and `total_funding_need_cents` is written afterwards, at bind, and never re-enters the pricing.

The attachment point is the underwriting estimate multiplied by 1.10, rounded half up to whole cents, and stored as `attachment_point_cents`; the ten percent above the estimate is the self-funded layer the insured wears before the cap responds, recorded as `buffer_layer_cents`, which is `attachment_point_cents` minus `underwriting_estimate_cents`. The cap limit starts as thirty percent of the underwriting estimate, rounded half up to whole cents, and is then rounded **up** to the next whole multiple of 10,000,000 cents — a 100,000.00 granularity, because carriers do not write odd limits; a value already exactly on a multiple stays where it is. That result is `limit_cents`. The rate ladder is then selected from the ratio of `limit_cents` to `underwriting_estimate_cents`, and that ratio is compared **unrounded**: a ratio of 0.35 or less selects a rate of 0.070, a ratio above 0.35 but no greater than 0.60 selects 0.055, and any larger ratio selects 0.045. The selected rate is stored as `rate_applied` to three decimal places. The base premium is `limit_cents` multiplied by `rate_applied`, rounded half up to whole cents; the broker fee adds three percent on top of that base, rounded half up; and `premium_cents` is the larger of that broker-loaded figure and a minimum premium of 2,500,000 cents (25,000.00), so a small remedy still pays the carrier's floor.

A quoted policy is created in `QUOTED` with `bound_at` null. Any prior policy on the same plan whose `status` is `QUOTED` becomes `SUPERSEDED` with its `version` incremented by 1 — a superseded quote's premium never enters the plan's funding need, since only bound premiums do. The plan's `version` increments by 1 as well, which is precisely why the next quote needs a refreshed `expected_remedial_action_plan_version`. Policies can be listed with filters on `remedial_action_plan_id`, `insurer_party_id` and `status`, and read individually with the full underwriting derivation exposed.

**Binding the cap.** Binding is the carrier's commitment, and it re-tests the quote against the world as it now stands. The acting `X-User-ID` must equal the policy's `insurer_party_id`; the parent plan's `status` must be `APPROVED`, else `ERR_INVALID_PLAN_STATE`; the policy's `attachment_point_cents` must be greater than or equal to the plan's current `total_estimate_cents` multiplied by 1.05 and rounded half up — the self-funded buffer must still sit at least five percent above the design estimate, and a plan edited upward after the quote was struck will fail this test with `ERR_ATTACHMENT_POINT_TOO_LOW`; and `limit_cents` must be at least 25,000,000 cents, since carriers do not bind a cap below a 250,000.00 limit, else `ERR_LIMIT_BELOW_MINIMUM`. Binding sets `bound_at` from the logical clock and the `status` to `BOUND`. It then cascades: at the first level the plan's `total_funding_need_cents` becomes its `total_estimate_cents` plus the `premium_cents` of every policy on that plan now standing in `BOUND`, this one included, with the plan's `version` incremented by 1; at the second level every funding award on the parcel whose `status` is `AWARDED` has its `allocated_cents` re-derived against the new, larger need by the waterfall of §3.9, each changed award having its `version` incremented by 1. The policy's own `version` increments by 1. Attempting to bind a policy that is not `QUOTED` — already `BOUND`, `SUPERSEDED` by a newer quote, or `CANCELLED` by a revision request or an enrollment withdrawal — is refused with `ERR_INVALID_POLICY_STATE`, a test settled ahead of the parent plan's own state check. `SUPERSEDED` and `CANCELLED` are terminal.

### 3.7. Engineering and Institutional Controls

A control is the physical or legal mechanism that keeps a residual contaminant away from a receptor, and it is what makes restricted closure possible. An `EnvironmentalConsultant` proposes one against a plan, supplying `site_id`, `remedial_action_plan_id` (which must name a plan on the same parcel, else `ERR_PLAN_SITE_MISMATCH`), a `control_type`, a `sub_area_code` of 1 to 32 characters naming the parcel sub-area the control covers (`BLDG-A-SLAB`, for instance), the closed inclusive coverage interval as `coverage_from` and `coverage_to` (both ISO 8601 dates, with `coverage_to` on or after `coverage_from`), and an `inspection_interval_days` between 30 and 730 inclusive giving the maximum number of days permitted between operation certifications.

`control_type` is one of `VAPOR_MITIGATION`, `ENGINEERED_CAP`, `GW_USE_RESTRICTION` or `DEED_RESTRICTION`, and from it the server derives `control_class`: `ENGINEERING` for `VAPOR_MITIGATION` and `ENGINEERED_CAP`, `INSTITUTIONAL` for `GW_USE_RESTRICTION` and `DEED_RESTRICTION`. The distinction is not cosmetic — only `ENGINEERING` controls are physical installations that occupy a sub-area, so only they are subject to the coverage-exclusivity rule below. A newly proposed control sits in `PROPOSED` with `impairment_count` zero, `last_certified_on` null, `impaired_since` null, and `next_certification_due_on` derived as `coverage_from` advanced by `inspection_interval_days`. The named plan's own `status` is not a precondition of proposing: a control may be filed against a plan in `DRAFT`, in either review branch, in `APPROVED` or in `WITHDRAWN` — but only the approval cascade of §3.5 ever lifts a control out of `PROPOSED`.

**Coverage exclusivity for engineering controls.** Two physical installations may not cover the same sub-area of the same parcel at overlapping times, and the programme insists on a **symmetric 30-day changeover buffer** between them so that a decommissioning and a replacement do not run into each other. When an `ENGINEERING` control is proposed, the server compares its requested closed inclusive interval against the interval of every existing control on the same `site_id` and the same `sub_area_code` whose `control_class` is `ENGINEERING` and whose `status` is `PROPOSED`, `APPROVED`, `OPERATING` or `IMPAIRED` — decommissioned controls are ignored. Two intervals conflict when the new `coverage_from` falls on or before the existing `coverage_to` advanced by 30 days **and** the existing `coverage_from` falls on or before the new `coverage_to` advanced by 30 days. Both halves of that test must hold for a conflict; a conflict is refused with `ERR_CONTROL_COVERAGE_CONFLICT` (HTTP 409). The practical consequence is that back-to-back coverage — where one interval starts the day after the other ends — is rejected, and a gap of 31 days is the first separation the rule accepts. `INSTITUTIONAL` controls are exempt from this rule entirely: a groundwater use restriction and a deed restriction can coexist over the same sub-area and the same dates.

Controls become `APPROVED` only as a cascade from the approval of the plan that specifies them, as described in §3.5, and that cascade also recomputes `next_certification_due_on` as `coverage_from` advanced by `inspection_interval_days`. Controls can be listed with filters on `site_id`, `remedial_action_plan_id`, `sub_area_code`, `status` and `control_class`, and read individually with their coverage interval and impairment counters.

**Operation-and-maintenance certification.** The owning `Redeveloper` files each periodic certification, supplying a `condition` of `PASS` or `FAIL` and the `certification_date` on which the inspection took place. The acting `X-User-ID` must equal the site's `owner_party_id`. For any passing certification the parcel must not be `FROZEN`, and the `certification_date` must fall inside the control's `coverage_from` to `coverage_to` interval, inclusive at both ends — a date outside it is refused with `ERR_CERTIFICATION_OUTSIDE_COVERAGE`. Certifying a control that is still `PROPOSED`, or one that has been `DECOMMISSIONED`, is refused with `ERR_INVALID_CONTROL_STATE`, and so is a `condition` of `FAIL` filed against a control that is merely `APPROVED` or already `IMPAIRED`, since only a control in service can fail. Those two state tests are settled ahead of the coverage-window test, per §2.10, so a `PROPOSED` control certified on a date outside its coverage interval reports `ERR_INVALID_CONTROL_STATE`.

A `PASS` serves three source states with a common core and three different tails. From `APPROVED` it brings the control into service, moving `APPROVED → OPERATING`. From `OPERATING` it is a routine re-certification, and the control stays `OPERATING` — the state pair `OPERATING → OPERATING` is a legitimate self-transition, not a no-op. From `IMPAIRED` it is a cure, moving `IMPAIRED → OPERATING`. In every case `last_certified_on` is set to the supplied `certification_date` and `next_certification_due_on` is recomputed as `last_certified_on` advanced by `inspection_interval_days`, and the control's `version` increments by 1. The first passing certification on a control belonging to a plan drives the parent enrollment `REMEDY_APPROVED → IMPLEMENTATION`. A pass arriving from `IMPAIRED` additionally clears `impaired_since`, decrements the parcel's `impaired_control_count`, and — when that count reaches zero and the parcel's `bfpp_status` is not `FORFEITED` — returns `cleanup_posture` to `OPEN`; the site's `version` increments by 1.

A `FAIL` is only meaningful on a control in service, and it moves `OPERATING → IMPAIRED`. It sets `impaired_since` to the logical clock's date and increments the control's `impairment_count` by 1. It then cascades: the parcel's `impaired_control_count` increments and its `cleanup_posture` becomes `RESTRICTED` unless the parcel is already `FROZEN`, in which case forfeiture continues to dominate; and, at the next level down, an enrollment sitting in `COMPLETION_REVIEW` whose approved plan owns this control is pushed back to `IMPLEMENTATION` with its `reverted_completion_count` incremented by 1. The control's `version`, the site's `version`, and — where the enrollment moved — the enrollment's `version` each increment by 1.

**Decommissioning.** A `StateAgencyReviewer` retires a control that is no longer needed, optionally supplying a `decommission_note`. Only an `OPERATING` control may be retired; any other status is `ERR_INVALID_CONTROL_STATE`. Two substantive conditions guard the action: every cleanup goal on the parcel whose `control_credit_type` equals this control's `control_type` must have `attainment_status` `ATTAINED`, and no closure letter on the parcel may be in `ACCEPTED_BY_LENDER` with a `requested_scope` of `RESTRICTED_WITH_CONTROLS`. Retiring a control that a lender is still relying on, or one whose credited goal has not yet been demonstrated, is refused with `ERR_CONTROL_STILL_REQUIRED`. Retirement sets the `status` to the terminal `DECOMMISSIONED` and increments the control's `version` by 1.

### 3.8. Long-Term Monitoring, Laboratory Capacity and Attainment

Demonstrating that a cleanup goal has actually been met takes years of quarterly results, and the system models each of those results as a `MonitoringEvent`. An `EnvironmentalConsultant` schedules one, supplying `site_id`, `laboratory_id` naming the accredited lab whose analysis window is being reserved, `cleanup_goal_id` naming the goal the result will be compared against, an `event_type`, a `monitoring_period_code` of 1 to 16 characters labelling the reporting period (`2027-Q1`, say), the `sample_date` on which the sample was or will be collected, and the reserved laboratory window as `window_start` and `window_end`, both ISO 8601 UTC datetimes with `window_end` strictly after `window_start`. The window is **half-open**: `window_start` is inclusive and `window_end` is exclusive. An optional `site_control_id` names the control whose performance this event verifies, and it may be null only for a `SAMPLING` event that is not tied to any control. `event_type` is `SAMPLING`, which produces a concentration result, or `CONTROL_INSPECTION`, which verifies control operation only. Both the referenced goal and the referenced control must belong to the event's own parcel, else `ERR_PLAN_SITE_MISMATCH`.

**Laboratory capacity.** A laboratory can only run so many analyses at once, and the check is an aggregate one — each existing reservation is individually legal, and it is their simultaneous count that fails. When an event is scheduled, the server counts the existing monitoring events on the same `laboratory_id` whose `status` is `SCHEDULED` or `REPORTED` and whose half-open window intersects the requested half-open window. Two half-open windows intersect when the new `window_start` is strictly before the existing `window_end` **and** the existing `window_start` is strictly before the new `window_end`; windows that merely touch — where one ends exactly when the next begins — do **not** conflict. If that count already equals or exceeds the laboratory's `concurrent_capacity`, the request is refused with `ERR_LAB_CAPACITY_EXCEEDED` (HTTP 409). A newly scheduled event sits in `SCHEDULED` with `result_status` `PENDING`, `result_value_ugl` null and `control_condition` null. Events can be listed with filters on `site_id`, `laboratory_id`, `cleanup_goal_id`, `site_control_id`, `event_type` and `status`, and read individually with the reported result and derived `result_status` exposed.

**Filing the result.** The consultant files the laboratory result or the inspection verdict, moving the event `SCHEDULED → REPORTED`. Three conditions apply. The acting `X-User-ID` must resolve to a party whose `party_type` is `CONSULTANT`, else `ERR_PARTY_TYPE_MISMATCH`. The logical clock must have reached `window_start` — filing before the reserved window has opened is refused with `ERR_RESULTS_BEFORE_WINDOW`. And the payload must match the event kind: a `SAMPLING` event requires `result_value_ugl`, the reported concentration in micrograms per litre and at least zero, while a `CONTROL_INSPECTION` event requires `control_condition`, the inspector's verdict of `PASS` or `FAIL`. Each kind ignores the other's field: `control_condition` is stored as null on a sampling event even when the caller supplies one, and `result_value_ugl` is left null on a control inspection even when one is offered. That payload pairing is the **last** of the three conditions evaluated, notwithstanding §2.10's placement of request shape at priority 3 — the party-type check, the already-`REPORTED` check and the window check all precede it, so an event whose window has not opened reports `ERR_RESULTS_BEFORE_WINDOW` even when its payload is incomplete as well. Filing results against an event that is already `REPORTED` is refused with `ERR_EVENT_ALREADY_REPORTED`. `REPORTED` is terminal.

On filing a `SAMPLING` event, `result_status` is derived: it becomes `COMPLIANT` when the reported `result_value_ugl` is less than or equal to the referenced goal's `goal_ugl` — the comparison is inclusive, so a result exactly equal to the goal is compliant — and `EXCEEDANCE` otherwise. A `CONTROL_INSPECTION` derives no result at all: its `result_status` stays `PENDING` permanently, its `result_value_ugl` stays null, and its verdict lives only in `control_condition`. The event's `version` increments by 1.

**The attainment replay.** The referenced goal's `compliant_streak` and `attainment_status` are then recomputed **from scratch**, by full chronological replay rather than by incrementing a counter. The server collects every monitoring event whose `cleanup_goal_id` is this goal, whose `event_type` is `SAMPLING` and whose `status` is `REPORTED` — control inspections and still-scheduled events are excluded — and orders them by `sample_date` ascending with `created_at` ascending and then insertion order as the tie-breaks; the UUID `id` is never a decision input. Walking that sequence from the beginning, a running count is incremented by 1 for each event whose `result_value_ugl` is less than or equal to the goal's `goal_ugl`, and reset to zero for each event that exceeds it. The final value of that running count is stored as `compliant_streak`, and `attainment_status` becomes `ATTAINED` when `compliant_streak` is at least 4 — four consecutive compliant sampling results — and `NOT_ATTAINED` otherwise. The replay runs on every filed event, a `CONTROL_INSPECTION` included, which simply contributes nothing to the sequence, and the goal row is rewritten unconditionally: the goal's `version` increments by 1 even when the replayed `compliant_streak` and `attainment_status` come out exactly as they were.

Replaying rather than incrementing has a consequence worth stating plainly. A late-arriving result — one reported today but sampled months ago — is inserted into the **middle** of the chronological sequence, not appended to the end. If it exceeds the goal, it resets the streak at that point, and every compliant result after it is re-counted from zero. A goal that had already reached `ATTAINED` can therefore fall back to `NOT_ATTAINED` when a stale exceedance finally arrives, and that is the intended behaviour. Re-deriving a goal has the same effect from the other direction: because a re-derivation changes `goal_ugl`, the upsert re-runs this replay against the new target.

**Exceedance as a control failure.** When a filed result comes back as `EXCEEDANCE`, the event's `site_control_id` is not null and that named control's own `status` is `OPERATING`, the exceedance is treated as evidence that the control is not performing, and the cascade runs four levels deep inside the same request. At the first level the event is stored and `result_status` derived. At the second, the goal's streak and attainment are replayed as above, and the named control moves `OPERATING → IMPAIRED`, setting `impaired_since` and incrementing its `impairment_count` by 1. At the third, the parcel's `impaired_control_count` increments and its `cleanup_posture` becomes `RESTRICTED` unless it is already `FROZEN`. At the fourth, an enrollment in `COMPLETION_REVIEW` is pushed back to `IMPLEMENTATION`, and every closure letter on the parcel whose `status` is `ISSUED` or `ACCEPTED_BY_LENDER` becomes `REVOKED` with its `revocation_reason` set to `CONTROL_FAILURE` — which in turn rescinds every funding award on the parcel whose `status` is `AWARDED`. The `version` of the event, the goal, the control, the site, the enrollment, each revoked letter and each rescinded award all increment by 1. Those three preconditions are strict. A control that is not `OPERATING` when the exceedance lands — one still `APPROVED`, one already `IMPAIRED`, one `DECOMMISSIONED` — is left exactly as it stands and the cascade stops after the goal replay, revoking no letter and rescinding no award. And a `CONTROL_INSPECTION` returning `control_condition` `FAIL` is not an exceedance at all: the verdict is recorded on the event and nothing else moves, because only a `SAMPLING` exceedance here and a failing operation-and-maintenance certification under §3.7 ever drive a control into `IMPAIRED`.

### 3.9. Funding Assembly, Closure, Revocation and the Ops-Run Checkpoint

**Assembling the money.** Brownfield cleanups are paid for by stacking public programmes, and the owning `Redeveloper` files one application per programme. Each application carries `site_id`, a `program_code` of 1 to 48 characters identifying the programme (`EPA-CLEANUP-GRANT`, `STATE-BROWNFIELD-CREDIT`), a `funding_kind` of `GRANT` or `TAX_CREDIT`, a `program_priority` between 1 and 99 inclusive that is the waterfall's order key, a `max_award_cents` ceiling strictly greater than zero, a `max_share_pct` strictly greater than zero and at most 1 giving the largest fraction of the eligible cost base the programme will cover, a `match_requirement_pct` between 0 and 1 inclusive giving the local match the redeveloper must contribute against whatever is allocated, and `eligible_cost_categories`, an array of 1 to 5 unique members drawn from `EXCAVATION_DISPOSAL`, `GW_TREATMENT`, `VAPOR_MITIGATION`, `MONITORING` and `OVERSIGHT`. An optional `eligibility_documents` array of zero to five elements, defaulting to empty, lists the document codes filed with the application, each one of `SITE_CONTROL_EVIDENCE`, `BFPP_CERTIFICATION`, `PHASE_II_REPORT`, `COST_ESTIMATE` and `MATCH_COMMITMENT`; unlike `eligible_cost_categories`, its elements are not required to be unique. Grants disburse cash and tax credits offset liability, but both obey the same waterfall. A new application sits in `APPLIED` with `allocated_cents` zero and `decided_by_user_id` null. Applications can be listed for a parcel or globally with filters on `site_id`, `funding_kind` and `status`, and read individually with their current `allocated_cents`.

A `StateAgencyReviewer` decides each application with a `decision` of `AWARD`, `DENY` or `RESCIND` plus an optional `decision_note`, always recording `decided_by_user_id`. An `AWARD` is documentation-gated and requires the parcel's `cleanup_posture` to be `OPEN`. The documentation requirement depends on the `funding_kind`, and the two branches are enumerated in full: a `GRANT` requires `eligibility_documents` to contain `SITE_CONTROL_EVIDENCE`, `PHASE_II_REPORT`, `COST_ESTIMATE` and `MATCH_COMMITMENT`; a `TAX_CREDIT` requires `BFPP_CERTIFICATION`, `PHASE_II_REPORT` and `COST_ESTIMATE`. Any code missing from the applicable set is refused with `ERR_MISSING_ELIGIBILITY_DOCUMENT`, and this check is evaluated only for an `AWARD` decision. The parcel must also carry a remedial action plan in `APPROVED`, since without one the funding need is undefined — refused with `ERR_FUNDING_NEED_UNDETERMINED` — and the approved plan must contain at least one cost line whose `cost_category` falls in this award's `eligible_cost_categories`, since otherwise the eligible base is zero and the programme has nothing to pay for; that is `ERR_NO_ELIGIBLE_COST_BASE`. An award moves `APPLIED → AWARDED` and re-derives the whole parcel's allocation; because the newly awarded application is written twice inside that one request — once for the status transition and once again by the waterfall that fills in its `allocated_cents` — its own `version` increments by 2 whenever the waterfall assigns it a non-zero allocation, and by 1 when the allocation comes out zero. A `DENY` has no precondition of its own beyond an `APPLIED` status and the frozen-site gate, which — unlike the enrollment file's `REJECT` — does apply to all three funding decisions: it moves `APPLIED → DENIED`, which is terminal, and `allocated_cents` stays zero. A `RESCIND` is a compensating action available only from `AWARDED`: it sets this award's `allocated_cents` to zero, moves it to the terminal `RESCINDED`, and re-derives the remaining awarded applications so the conserved total still holds. Awarding or denying an already decided application, or rescinding one that is not `AWARDED`, is refused with `ERR_INVALID_AWARD_STATE`. Every award whose `allocated_cents` changed has its `version` incremented by 1.

**The waterfall.** The allocation is a strict priority waterfall against a single need figure, and it is also exposed as a computed read on the parcel. The need is the `total_funding_need_cents` of the parcel's remedial action plan whose `status` is `APPROVED` — should more than one plan on the parcel be `APPROVED`, the earliest by `created_at` is the one read; when the parcel has no approved plan the need is zero. A running remainder starts at the need. The parcel's funding applications whose `status` is `AWARDED` are then visited in order of `program_priority` ascending, with `created_at` ascending and then insertion order as the tie-breaks — the UUID `id` is never a decision input, and applications in `APPLIED`, `DENIED` or `RESCINDED` are excluded entirely and carry `allocated_cents` zero. For each visited application the server computes an eligible base: the sum of the **per-line rounded** design-basis line values of the approved plan for exactly those lines whose `cost_category` appears in this application's `eligible_cost_categories`. Those are the same whole-cent line figures §3.6 produced, not freshly multiplied products. A share cap is that eligible base multiplied by the application's `max_share_pct`, rounded half up to whole cents. The application's `allocated_cents` is then the smallest of three quantities: its own `max_award_cents` ceiling, that share cap, and the running remainder. The remainder is reduced by the amount allocated before the next application is visited, so a later programme can only fill what earlier ones left behind.

When every awarded application has been visited, whatever remains of the running remainder is the parcel's `unfunded_gap_cents`, and `local_match_required_cents` is the sum, over each allocation, of that allocation's `allocated_cents` multiplied by that application's own `match_requirement_pct`, each product rounded half up to whole cents before summing. The invariant §2.6 promises holds by construction: the allocated amounts plus the unfunded gap always equal the need. The computed read exposes `site_id`, the `remedial_action_plan_id` of the approved plan, `total_funding_need_cents`, an `allocations` array whose entries each pair a `funding_award_id` with its `allocated_cents`, `unfunded_gap_cents` and `local_match_required_cents`. When the parcel has no awarded applications the `allocations` array is empty, `unfunded_gap_cents` equals the need, and `local_match_required_cents` is zero; when the parcel has no approved plan the need is zero and the allocation list is likewise empty.

**Drafting and issuing closure.** The owning `Redeveloper` drafts the closure request, supplying `site_id`, `vcp_enrollment_id` (which must name an enrollment on the same parcel, else `ERR_PLAN_SITE_MISMATCH`) and a `requested_scope` of `UNRESTRICTED` or `RESTRICTED_WITH_CONTROLS`. A draft letter sits in `DRAFT` with `reissue_count` zero, `controls_certified_count` zero, `issued_on` null, `issued_by_user_id` null, `accepted_by_lender_user_id` null, `lender_reference` null and `revocation_reason` null. The parent enrollment's own `status` is not a precondition of drafting — a request may be raised against an enrollment at any stage, the guard being issuance rather than drafting — and no uniqueness rule limits a parcel or an enrollment to a single letter. Letters can be listed with filters on `site_id`, `vcp_enrollment_id` and `status`, and read individually with their issuance, acceptance and revocation history.

Issuance is the agency's act and it is the most heavily guarded operation in the system. The parcel's `cleanup_posture` must be `OPEN`. The parent enrollment's `status` must be `COMPLETION_REVIEW`, else `ERR_INVALID_ENROLLMENT_STATE`. The enrollment's `APPROVED` plan must exist and every site control on it must have `status` `OPERATING`, else `ERR_CONTROLS_NOT_OPERATING`. The acting `X-User-ID` must differ from that plan's `approved_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES` — and on this endpoint the segregation test is evaluated **after** the enrollment-state and controls-operating tests rather than at §2.10's priority 7, because the plan whose approver it compares against is only reached through them, so the reviewer who approved the remedy still sees `ERR_CONTROLS_NOT_OPERATING` first while any control is out of service. And a `requested_scope` of `UNRESTRICTED` requires that every cleanup goal on the parcel have `basis` `UNRESTRICTED` — a parcel closing on the strength of a credited control cannot be granted unrestricted closure, and the attempt is refused with `ERR_UNRESTRICTED_SCOPE_NOT_SUPPORTED`. Issuance moves the letter `DRAFT → ISSUED`, sets `issued_on` from the logical clock's date, records `issued_by_user_id`, and stores `controls_certified_count` as the number of site controls on the parcel whose `status` is `OPERATING` at that instant. On a first issuance it cascades the parent enrollment `COMPLETION_REVIEW → CLOSED` with the enrollment's `version` incremented by 1. The letter's `version` increments by 1.

**Lender reliance.** A `Lender` records reliance on an issued letter, supplying a `lender_reference` of 1 to 64 characters that identifies the loan or investment file. Two conditions apply: the parcel's `cleanup_posture` must be `OPEN`, and the parcel's `bfpp_status` must be `ESTABLISHED` — a lender may not rely on closure for a parcel whose purchaser defence is not actually in place. A defence standing at `NOT_ESTABLISHED` or `FORFEITED`, and equally a parcel carrying no liability protection record at all, is refused with `ERR_LETTER_NOT_CURABLE` (HTTP 422), the same code the uncurable revocation of a letter earns. Acceptance stores `accepted_by_lender_user_id` from the acting `X-User-ID` along with `lender_reference`, moves the letter `ISSUED → ACCEPTED_BY_LENDER`, and increments its `version` by 1. Attempting acceptance on a letter that is still `DRAFT`, or one that has been `REVOKED`, is refused with `ERR_INVALID_LETTER_STATE`, as is issuing a letter that is already `ISSUED` or `ACCEPTED_BY_LENDER`.

**Revocation and cure.** Closure is not permanent if the facts that supported it stop being true. Two events revoke a letter, and both reach it from either `ISSUED` or `ACCEPTED_BY_LENDER` — the two source states behave identically. A `bfpp_status` becoming `FORFEITED` revokes the letter with `revocation_reason` `BFPP_FORFEITED`; a site control driven into `IMPAIRED` by a monitoring exceedance as described in §3.8 revokes it with `revocation_reason` `CONTROL_FAILURE`. Impairment revokes closure only along that monitoring path: a control that enters `IMPAIRED` through a failing operation-and-maintenance certification (§3.7) still restricts the parcel and still reverts a completion review, but leaves `ISSUED` and `ACCEPTED_BY_LENDER` letters — and therefore the parcel's awards — exactly as they stand. In either case the letter moves to `REVOKED`, its `version` increments by 1, and every funding award on the parcel whose `status` is `AWARDED` becomes `RESCINDED` with its `allocated_cents` set to zero, which re-derives the parcel's assembly and raises `unfunded_gap_cents` accordingly. Where the letter had been accepted, `accepted_by_lender_user_id` and `lender_reference` are **preserved as history** rather than cleared — the record of who relied on the letter survives its revocation.

Re-issuance closes the cycle `ISSUED → REVOKED → ISSUED`, and it is available only for the curable reason. A `StateAgencyReviewer` may re-issue when the parcel's `cleanup_posture` is `OPEN`, when the letter's `revocation_reason` is `CONTROL_FAILURE`, when every site control on the enrollment's approved plan has returned to `OPERATING`, when the acting `X-User-ID` differs from that plan's `approved_by_user_id`, and — a `requested_scope` of `UNRESTRICTED` being re-tested exactly as on a first issuance — when every cleanup goal on the parcel still has `basis` `UNRESTRICTED`. The parent enrollment's `status` is deliberately **not** re-tested on this path, since the first issuance already drove it to `CLOSED`. A revocation whose reason is `BFPP_FORFEITED` can never be re-issued — the forfeiture is absorbing and the attempt is refused with `ERR_LETTER_NOT_CURABLE`, a test settled ahead of the controls-operating test, so a letter revoked for forfeiture reports `ERR_LETTER_NOT_CURABLE` whatever state its controls are in. Re-issuance increments `reissue_count` by 1, refreshes `issued_on`, `issued_by_user_id` and `controls_certified_count`, clears `revocation_reason`, and increments the letter's `version` by 1. The lender's acceptance is **not** restored automatically: the letter returns to `ISSUED`, and reliance must be re-obtained. The letter entity has no terminal state at all — even `REVOKED` may be left behind.

**The ops-run checkpoint.** Deadlines do not enforce themselves in this system; a `StateAgencyReviewer` runs a compliance sweep that advances every overdue or nearly-overdue duty and stales every expired inquiry as of a supplied date. The sweep takes an `as_of_date` and an optional `site_id` to narrow it to one parcel — which must resolve when supplied, else `ERR_SITE_NOT_FOUND` — and it is one of the operations §2.5 permits even on a `FROZEN` parcel — indeed running it on frozen parcels is the point, since forfeiture is exactly what it detects.

Against each continuing obligation the sweep applies a small set of rules. A duty in `CURRENT` whose `due_date` is between 0 and 30 days after the `as_of_date` inclusive moves `CURRENT → AT_RISK`; a duty in `SATISFIED` whose next `due_date` falls in that same window likewise moves `SATISFIED → AT_RISK`, because the next certification period has opened and is already approaching its own deadline. A duty in either `CURRENT` or `AT_RISK` whose `due_date` is strictly earlier than the `as_of_date` moves to the terminal `LAPSED`; both edges behave identically. Each advanced duty has its `version` incremented by 1, and each touched protection has its four weight buckets and `compliance_pct` recomputed per §3.4 with its `version` incremented by 1. Where a lapsed duty's `obligation_category` is defence-critical, the cascade continues: the protection's `obligation_state` becomes `LAPSED`, its `bfpp_status` becomes `FORFEITED`, the parcel's `cleanup_posture` becomes `FROZEN`, every closure letter on the parcel in `ISSUED` or `ACCEPTED_BY_LENDER` becomes `REVOKED` with `revocation_reason` `BFPP_FORFEITED`, and every funding award on the parcel in `AWARDED` becomes `RESCINDED`. Every site whose `cleanup_posture` changed has its `version` incremented by 1.

The same run also handles inquiry freshness: a protection whose `inquiry_state` is `AAI_COMPLETE`, whose parcel is still `UNDER_CONTRACT`, and whose `aai_expires_on` is strictly earlier than the `as_of_date` moves `AAI_COMPLETE → AAI_STALE`, with `bfpp_status` recomputed to `NOT_ESTABLISHED` and the protection's `version` incremented by 1.

The sweep reports what it did rather than returning an entity. Its response echoes the `as_of_date` and carries six counters: `swept_obligation_count` for the duties this run actually advanced — a duty the sweep examined and left where it was does not count towards it — `at_risk_count` and `lapsed_count` for the two adverse landings, `stale_inquiry_count` for the inquiries expired, `forfeited_protection_count` for the defences lost, and `frozen_site_count` for the parcels frozen as a consequence.

## 4. API Endpoint Definitions

The API is a flat, multi-root surface: resource collections sit at the root of the URL space with no version or product prefix, and the deeper paths are used only where a child genuinely belongs to exactly one parent. Every path segment shown as `{id}` is the UUID `id` of the resource named by the preceding collection segment.

Status codes follow one rule. An endpoint that brings a new row into existence answers **201 Created**; every other successful call — reads, lists, state transitions, edits, computed reads, the logical-clock setter and the compliance sweep — answers **200 OK**. Transitions therefore return 200 even though they change the resource, and they return the full updated resource in `data`. The `POST` endpoints that answer 201 are exactly those that create a party, a laboratory, a parcel, a cleanup goal, an assessment phase, a contaminant finding, a liability protection, a continuing obligation, an enrollment, a remedial action plan, a cost-cap policy, a site control, a funding application, a closure letter and a monitoring event.

Every list endpoint honours `limit` and `offset` per §2.3 and returns its `meta` counters. Every endpoint validates authentication and role membership before anything else, per §2.10.

## 5. Error Codes

Every failed request answers with the standard error envelope of §2.2, carrying the `error_id` from the table below in `data` together with a human-readable `message`. The `error_id` is the contract; the `message` text is not. When several conditions are simultaneously unmet, the precedence rules of §2.10 decide which single `error_id` is returned — the first failing tier wins and no later tier is evaluated. Three further identifiers sit outside this catalogue because request routing rather than any rule in §2 or §3 produces them: `ERR_NOT_FOUND` (HTTP 404) for a URL matching no route at all, `ERR_METHOD_NOT_ALLOWED` (HTTP 405) for an unsupported method on a routed URL, and `ERR_INTERNAL` (HTTP 500) for an unexpected server fault.
