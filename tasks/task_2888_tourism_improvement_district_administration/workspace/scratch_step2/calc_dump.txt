- name: assessment_amount
  trigger: on POST /assessment-statements/{id}/filings and POST /assessment-statements/{id}/amendments (PROVISIONAL variant writes provisional_assessment_cents); on POST /assessment-statements/{id}/audit-certification
    action AUDIT and on POST /assessment-disputes/{id}/resolution outcome ADJUSTED (FINAL variant writes final_assessment_cents)
  algorithm: threshold
  formula: "# branch selected by AssessmentStatement.assessment_method_at_period_start\nif assessment_method_at_period_start == PCT_OF_ROOM_REVENUE:\n    revenue_component_cents = round_half_up(revenue_basis_cents\
    \ * ZONE_RATE[zone_basis] * CLASS_MULTIPLIER[class_basis])\n    floor_cents             = nights_basis * PER_NIGHT_FLOOR_CENTS\n    gross_cents             = max(revenue_component_cents, floor_cents)\n\
    elif assessment_method_at_period_start == PER_OCCUPIED_ROOM_NIGHT:\n    gross_cents = round_half_up(nights_basis * PER_NIGHT_RATE_CENTS * CLASS_MULTIPLIER[class_basis])\nelse:   # TIERED_BY_CLASSIFICATION\n\
    \    gross_cents = round_half_up(FLAT_FEE_CENTS[class_basis] * ZONE_FACTOR[zone_basis])\n\ncapped_cents     = min(gross_cents, PERIOD_CAP_CENTS)\nassessment_cents = max(capped_cents - adjustment_basis_cents,\
    \ 0)\n\n# exactly one rounding step per branch, applied before the max/min pair.\n# The max() floor test runs BEFORE the min() cap test; reversing the two\n# would let a floor above the cap escape the\
    \ cap.\n"
  input_set: one AssessmentStatement row; only statements whose owning LodgingBusiness.status == ASSESSABLE at generation time exist at all, so EXEMPT, OUTSIDE_BOUNDARY and CLOSED_OUT properties are never
    billed
  constants:
    ZONE_RATE:
      ZONE_CORE: 0.02
      ZONE_PERIMETER: 0.0125
      OUTSIDE: 0.0
    CLASS_MULTIPLIER:
      FULL_SERVICE: 1.0
      LIMITED_SERVICE: 0.85
      BOUTIQUE: 0.9
      SHORT_TERM_RENTAL: 1.15
    ZONE_FACTOR:
      ZONE_CORE: 1.0
      ZONE_PERIMETER: 0.625
      OUTSIDE: 0.0
    FLAT_FEE_CENTS:
      FULL_SERVICE: 500000
      LIMITED_SERVICE: 300000
      BOUTIQUE: 350000
      SHORT_TERM_RENTAL: 150000
    PER_NIGHT_FLOOR_CENTS: 150
    PER_NIGHT_RATE_CENTS: 300
    PERIOD_CAP_CENTS: 2500000
  precision: integer cents, round_half_up applied once per branch as written
  variants:
  - name: PROVISIONAL
    when: computed at filing and at every amendment, before any audit has run
    difference: zone_basis := the LodgingBusiness.boundary_zone read live at the moment of the call; class_basis := the LodgingBusiness.classification read live at the moment of the call; revenue_basis_cents
      := reported_gross_room_revenue_cents; nights_basis := reported_room_nights; adjustment_basis_cents := 0. Output lands in provisional_assessment_cents.
  - name: FINAL
    when: computed at audit and recomputed on every RESOLVED_ADJUSTED dispute
    difference: zone_basis := AssessmentStatement.zone_at_period_start; class_basis := AssessmentStatement.classification_at_period_start; revenue_basis_cents := audited_gross_room_revenue_cents when non-null
      else reported_gross_room_revenue_cents; nights_basis := audited_room_nights when non-null else reported_room_nights; adjustment_basis_cents := AssessmentStatement.granted_adjustment_cents. Output
      lands in final_assessment_cents. Because a mid-period classification or zone revision moves the live values away from the period-start snapshot, the two variants return different integers for byte-identical
      reported data.
- name: petition_support
  trigger: recomputed on POST /petition-drives/{id}/signatures, POST /petition-signatures/{id}/withdrawal, any cascade that disqualifies a signature, any POST /districts/{id}/boundary-revisions, any POST

    \n# ONE division, ONE rounding, at the very end. Per-business shares are never\n# rounded and then summed; that order would drift by up to n half-cents.\nweighted_support_pct  = 0.0000 if assessable_basis_snapshot_cents\
    \ == 0\n                        else round_half_up(signed_basis_cents / assessable_basis_snapshot_cents, 4)\nheadcount_support_pct = 0.0000 if assessable_count_snapshot == 0\n                      \
    \  else round_half_up(valid_signature_count / assessable_count_snapshot, 4)\n\nqualifies = (weighted_support_pct >= drive.required_weighted_pct)\n            AND (headcount_support_pct >= drive.required_headcount_pct)\n\
    # both comparisons are >= , so a support level exactly equal to the\n# threshold qualifies.\n"
  input_set: signatures filtered to status == VALID only; WITHDRAWN and DISQUALIFIED signatures contribute nothing to either numerator. The denominator is the assessable set as of the recompute instant,

    DEFAULT_RENEWAL_HEADCOUNT_THRESHOLD_PCT: 0.5
    MIN_PETITION_POOL: 3
    MIN_ASSESSABLE_ROOMS: 5
  precision: 4 decimal places, round_half_up, applied once after the single division
  variants:
  - name: REVENUE_WEIGHTED
    when: the binding test for FORMATION drives, where required_headcount_pct is snapshotted as 0.0000
    difference: numerator and denominator are revenue in cents, so a single large property can carry a drive on its own. Writes weighted_support_pct.
  - name: HEADCOUNT
    when: an additional binding test for RENEWAL drives, where required_headcount_pct is snapshotted from District.renewal_headcount_threshold_pct
    difference: numerator and denominator are unweighted counts of businesses, so property size is irrelevant. Writes headcount_support_pct. For a signature set dominated by one large property the two variants
      return materially different percentages from identical data, and a RENEWAL drive can pass the revenue test while failing the headcount test.

- name: delinquency_charges

- name: remittance_waterfall
  trigger: on POST /assessment-statements/{id}/remittances (forward) and on POST /assessment-statements/{id}/remittance-reversals (exact inverse)
  algorithm: waterfall_allocation
  formula: "remaining = amount_cents\n\n# Bucket order is fixed. A bucket is filled to its outstanding balance\n# before any cents reach the next bucket.\ninterest_outstanding  = statement.interest_cents\
    \  - statement.interest_paid_cents\napplied_to_interest   = min(remaining, max(interest_outstanding, 0))\nremaining            -= applied_to_interest\n\npenalty_outstanding   = statement.penalty_cents\
    \   - statement.penalty_paid_cents\napplied_to_penalty    = min(remaining, max(penalty_outstanding, 0))\nremaining            -= applied_to_penalty\n\nprincipal_outstanding = statement.effective_assessment_cents\
    \ - statement.principal_paid_cents\napplied_to_principal  = min(remaining, max(principal_outstanding, 0))\nremaining            -= applied_to_principal\n\napplied_to_credit     = remaining         \
    \ # overflow, never discarded\n\nstatement.interest_paid_cents  += applied_to_interest\nstatement.penalty_paid_cents   += applied_to_penalty\nstatement.principal_paid_cents += applied_to_principal\n\
    statement.credit_balance_cents += applied_to_credit\nDistrict.collected_to_date_cents += amount_cents\n\n# CONSERVED IDENTITY, checked after every forward and reverse call:\n#   District.collected_to_date_cents\
    \ ==\n#     sum over the district's statements of\n#       (interest_paid_cents + penalty_paid_cents\n#        + principal_paid_cents + credit_balance_cents)\n# A reversal subtracts exactly the four\
    \ per-bucket amounts recorded on the\n# Remittance row \u2014 it does NOT re-run the waterfall backwards \u2014 so the\n# identity holds no matter what order remittances and reversals arrive in.\n"
  input_set: the four buckets of exactly one AssessmentStatement plus the amount_cents of the one Remittance being applied or reversed; only Remittance rows with status == APPLIED contribute to the buckets
  constants:
    OVERPAYMENT_TOLERANCE_CENTS: 500000
  precision: integer cents; no rounding occurs anywhere in the waterfall, so it is exactly reversible
