# Employer Backup Care API — Product Requirements Document

## 1. Introduction

When a school closes without warning, a nanny calls in sick, or an ageing parent is discharged from hospital on a Tuesday morning, an employee's day of work is at risk. Employer-sponsored backup care exists to absorb exactly those shocks: the sponsoring employer pre-purchases a pool of entitlement days, the employee pays a modest copay, and a vetted network of childcare centres and in-home caregivers absorbs the demand at short notice. The Employer Backup Care API is the transactional system of record for that benefit. It holds the benefit design, the enrolled workforce and their eligible dependents, the supply-side provider network with its credentials and published capacity, and the reservations that bind demand to supply on a specific care date.

Two pressures shape the design. The first is that entitlement is a scarce, conserved quantity: every day a reservation holds must be released if the care never happens, and every day beyond the annual allowance must be billed back to the employer at a volume-discounted overage rate rather than silently absorbed. The second is that supply is safety-critical. A caregiver whose background check lapses must be pulled out of the matching pool the same night, and any care already confirmed against that caregiver must be handed back to the matching queue before the family shows up at a locked door. The API therefore treats every quantity-moving operation as an append-only ledger movement, and every credentialing or quality event as a cascade that can reach all the way down to an employee's remaining entitlement.

This document specifies the complete contract: the global response envelope and access-control model in Section 2, the domain workflows and the arithmetic behind them in Section 3, the endpoint surface in Section 4, and the error catalogue in Section 5. Every path in this API is mounted under the `/backup-care` prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. Caller Identity and the Five Peer Roles

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which that principal acts. A request whose `X-User-ID` is absent or does not resolve to a known role identity is rejected with `ERR_UNAUTHENTICATED` (401). A request whose declared role is not among the roles authorised for the target operation is rejected with `ERR_UNAUTHORIZED` (403). A request whose role *is* authorised for the operation but whose principal is reaching a row outside its own scope is rejected with `ERR_FORBIDDEN_SCOPE` (403) — the distinction matters, and the two codes are never interchangeable.

The system recognises exactly five roles, and none of them is a superset of another. They are `benefits_admin`, `network_admin`, `care_coordinator`, `provider_manager`, and `employee_user`. `benefits_admin` owns the demand side: employer accounts, benefit designs, employee enrolment and dependents. `network_admin` owns the supply side: provider onboarding, credentialing, network posture, invoice issuance and voiding, incident resolution, and the nightly maintenance sweep. `care_coordinator` owns the matching and delivery workflow. `provider_manager` operates a single provider's surface. `employee_user` operates a single employee's own surface.

Identity binds differently per role. When `X-User-Role` is `benefits_admin`, `network_admin`, or `care_coordinator`, the `X-User-ID` is an opaque operator identifier not tied to any persisted entity row. The server may record such an identifier — for instance as `reported_by_user_id` when an incident report is filed, or as `reviewed_by` when a report is taken under review — but it never compares it to any entity's `id`. When `X-User-Role` is `provider_manager`, `X-User-ID` is the `owner_user_id` of the acting `Provider`; ownership checks on any resource that references a provider compare that resource's provider reference (directly, or through a reservation's `matched_provider_id`) to the provider whose `owner_user_id` equals `X-User-ID`. When `X-User-Role` is `employee_user`, `X-User-ID` is the `user_id` of the acting `Employee`; ownership checks on any resource that references an employee compare the resource's employee reference to the `id` of that `Employee` row, and reads or writes aimed at a different employee's rows fail with `ERR_FORBIDDEN_SCOPE`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

List endpoints accept two query parameters. `limit` caps the number of rows returned; it defaults to 10, may be no smaller than 1, and may be no larger than 100. `offset` is the number of rows to skip and defaults to 0; the smallest accepted value is 0. A `limit` or `offset` outside those bounds, or of the wrong type, is a schema violation and yields `ERR_INVALID_REQUEST`.

Unless a specific endpoint states otherwise, list responses are ordered by `created_at` ascending. Four surfaces override that default and are called out where they appear in Section 3 and Section 4: an employer's benefit-plan listing orders by `effective_from` descending (newest design first); an employer's invoice listing orders by `period_start` descending; an offer listing orders by `rank_position` ascending within a generation batch; and the entitlement ledger orders by `effective_at` ascending and then, for entries sharing an instant, by `created_at` ascending, which is the pinned replay order for all ledger arithmetic.

Every list response carries `limit`, `offset`, `total_count`, and `has_more` inside the envelope's `meta` object.

### 2.4. The Logical Clock and Temporal Evaluation

Every temporal rule in this specification reads a single server-held logical clock rather than wall-clock time. On a cold start, and at any point at which it has never been explicitly set, the clock reads `2026-08-01T00:00:00Z`; any scenario that never sets it behaves as though that were the present instant. Any of the five roles may advance the clock by supplying a `current_utc` instant; the response reports the new `current_utc` alongside the `previous_utc` it replaced. The clock may only move forward — a target strictly earlier than the present value is rejected with `ERR_CLOCK_MOVES_BACKWARD`.

Advancing the clock does **not** by itself run the maintenance sweep and moves no lifecycle state. It does, however, change the answers every clock-relative derivation gives: credential expiry, the age-decay band applied to each substantiated incident, and every employee's eligibility derivation. Concretely, setting the clock recomputes `quality_score` and `lifetime_quality_score` on every provider and recomputes `eligibility_status` on every employee. Timestamp comparisons throughout the system are evaluated at whole-second resolution, and "date" comparisons — credential expiry, care dates, service dates, benefit-year buckets — are UTC calendar dates.

### 2.5. Record Identity, Timestamps and Versioning

Every resource carries an `id` that is a server-minted UUID with no type prefix, and a `created_at` timestamp rendered as an ISO 8601 UTC instant with three fractional digits. Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation that writes a stored field of that row. Derived figures are not stored at all: an employee's entitlement counters and `eligibility_status`, a plan's `enrolled_employee_count`, a provider's two score variants together with its substantiated-incident and completed-reservation counts, an employer's accrual and year-to-date billing totals, and a capacity block's occupancy counters are each evaluated afresh whenever the row is read. Wherever this document says that an operation *recomputes* one of those figures, that wording is a statement about what the next read of the row will report and not a mutation in its own right: such a recomputation refreshes neither `updated_at` nor `version` on the row whose figure it restates. Exactly one row is nevertheless re-stamped for a purely occupancy-driven reason, and it is called out immediately below.

Two record types are append-only and therefore carry neither field: a `UsageLedgerEntry` and an `InvoiceLine` expose only `id` and `created_at`, and have no `updated_at` and no `version`. Everything else — employers, benefit plans, employees, dependents, providers, credentials, capacity blocks, reservations, match offers, employer invoices and incident reports — carries the full set of four.

Version increments matter beyond bookkeeping, because two of them are load-bearing for the concurrency guards in the next subsection: amending an employer's commercial terms bumps that employer's `version`, and every confirmation, cancellation, completion, no-show or provider-withdrawal that touches a capacity block recomputes that block's occupancy counters and bumps its `version` by 1.

### 2.6. Stale-Version Guards on Employer and Capacity Writes

Two write paths are protected by optimistic concurrency control against the `version` of a *parent* record. Both are mandatory inputs, not optional hints, and no other endpoint in this API accepts a version field of any kind.

A benefit-plan creation request (`POST /backup-care/benefit-plans`) must carry `expected_employer_version` holding the client's last observed `version` of the target `Employer`. If that value differs from the employer's current `version`, the creation is rejected with `ERR_STALE_EMPLOYER_VERSION` (HTTP 412). The guard exists because activating a new plan legitimately retires the employer's incumbent `ACTIVE` design; a writer holding an outdated view of the employer's plan portfolio would otherwise supersede a design it never saw.

A care-confirmation request (`POST /backup-care/reservations/{id}/confirm`) must carry `expected_capacity_block_version` holding the client's last observed `version` of the `CapacityBlock` named by `capacity_block_id`. If that value differs from the block's current `version`, the confirmation is rejected with `ERR_STALE_CAPACITY_BLOCK_VERSION` (HTTP 412). Some other confirmation, cancellation, completion or no-show has already consumed or released seats on that block, so the caller's remaining-slot view is stale even in cases where a fresh read would still admit the reservation. The `version` field returned when reading a capacity block is precisely the value a confirming caller is expected to echo back.

### 2.7. Money, Days and Rounding Discipline

All money in this system is carried as an integer count of cents; no monetary field is ever a fractional value in a stored record or in a response body. Rate and quantity fields are decimals: `admin_fee_pct` is a decimal fraction with at most four decimal places, hour quantities and entitlement-day quantities are carried to two decimal places, ranking components and rank scores are carried to four decimal places, and the overage tier multiplier is exact to two decimals.

Wherever this document says a value is rounded, the method is always **round half up**: a value exactly halfway between two representable results rounds away from zero. Two operations are explicitly *not* rounding: the step that raises in-home hours to the next whole quarter hour is an exact ceiling, and the step that converts hours into whole entitlement days is likewise an exact ceiling. Incident age in days and the completed-reservation bonus step count are exact floors.

The order in which rounding and summation are applied is pinned and observable. Invoice arithmetic rounds every line independently to an integer cent amount and only then sums those integers; it never sums unrounded products and rounds once at the end. Two in-home copay lines of 4.25 hours at 605 cents per hour each therefore produce 2571 cents and 2571 cents for a subtotal of 5142 cents, not 5143. The administrative fee is likewise derived from the already-integer subtotal, never from an unrounded product sum.

### 2.8. Validation Precedence

When a single request violates more than one rule, exactly one error is returned, and which one is fully determined. Checks are grouped into ten bands, evaluated in the order below; within a band, the checks are evaluated in the order listed. The first violated check wins.

1. **Request shape.** Every field the endpoint marks required must be present and of the declared type, and no enum-valued field may carry a member outside its declared set — otherwise `ERR_INVALID_REQUEST`. Then: every `*_cents` field, plus `annual_use_limit_days`, `total_slots`, `max_concurrent_assignments` and any dependent count, must be an integer that is zero or greater, on benefit-plan creation, provider creation, capacity-block creation and employer creation (`ERR_INVALID_REQUEST`). Then `admin_fee_pct` must be a decimal between 0 and 0.5 inclusive with at most four decimal places, and `fiscal_year_start_month` must be an integer between 1 and 12 inclusive, on both employer creation and employer amendment (`ERR_INVALID_REQUEST`). Then `care_end_utc` must be strictly after `care_start_utc` and `end_time_utc` strictly after `start_time_utc`, on reservation creation and capacity-block creation respectively (`ERR_INVALID_WINDOW`); the 14-hour ceiling on a requested care window is *not* checked here, but in band 6 below. Then `period_end` must fall on or after `period_start`, on both the invoice sweep and the utilization report (`ERR_INVALID_PERIOD`). Then `dependent_ids` must be a non-empty array of distinct values on reservation creation (`ERR_INVALID_REQUEST`).
2. **Authentication and authorisation.** `X-User-ID` must be present and resolve to a known role identity (`ERR_UNAUTHENTICATED`); then the caller's role must be authorised for the endpoint (`ERR_UNAUTHORIZED`); then an `employee_user` caller must be acting within its own employee record, which is enforced on exactly seven surfaces — reading one reservation, creating a reservation, cancelling a reservation, reading an employee's entitlement projection, listing an employee's dependents, listing an employee's reservations and listing an employee's ledger entries (`ERR_FORBIDDEN_SCOPE`); then a `provider_manager` caller must be acting on a provider whose `owner_user_id` is its own `X-User-ID`, which is enforced on exactly five surfaces — publishing a capacity block, filing a credential, checking in a reservation, completing a reservation and reporting a no-show (`ERR_FORBIDDEN_SCOPE`); then the `X-User-ID` recorded in an incident report's `reported_by_user_id` may not be the `X-User-ID` resolving that report, which is enforced on both substantiation and dismissal (`ERR_SEGREGATION_OF_DUTIES`).
3. **Existence.** Path identifiers resolve first, strictly left to right, so the outermost identifier in a nested path is the one whose absence is reported; then body identifiers resolve — `employer_id`, `employee_id`, `benefit_plan_id`, each element of `dependent_ids`, `provider_id`, `capacity_block_id`, `match_offer_id` and `reservation_id` — on employee creation, benefit-plan creation, reservation creation, offer rejection, confirmation and incident filing. Each failure returns the not-found code of the entity that failed to resolve.
4. **Optimistic concurrency.** As soon as the parent record named by a stale-version-guarded write has resolved, its version guard is evaluated — before any state, temporal, referential, fiscal, constraint or safety check on that request.
5. **Lifecycle state.** The target entity's current state must permit the requested transition, yielding that entity's `..._STATE_INVALID` code; when the current state is a terminal state of that machine, the terminal code is returned instead and the transition-permitted check stands down. Then invoice-specific state: an invoice may be issued only while `DRAFT` and paid only while `ISSUED` (`ERR_INVOICE_STATE_INVALID`). Then a benefit plan may be attached to a new employee or a new reservation only while its `status` is `ACTIVE` (`ERR_PLAN_NOT_ACTIVE`). Then a plan may be activated only while its employer's `contract_status` is `ACTIVE` (`ERR_EMPLOYER_CONTRACT_INACTIVE`). Then a capacity block named at confirmation must have `block_status` of `OPEN` (`ERR_BLOCK_NOT_OPEN`). Then a provider amendment may carry `care_mode` or `market_code` only when the supplied value equals the stored value (`ERR_PROVIDER_FIELD_IMMUTABLE`). Then a plan amendment is permitted only while the plan is `DRAFT` (`ERR_PLAN_NOT_EDITABLE`).
6. **Clock- and window-relative checks.** In order: `care_start_utc` strictly after the clock at intake (`ERR_CARE_WINDOW_IN_PAST`); `care_start_utc` and `care_end_utc` on the same UTC calendar date, and then that same requested window spanning at most 14 hours — both of those failures report `ERR_CARE_WINDOW_SPANS_DAYS` (400); the selected offer still live against `offer_expires_at`, checked on both confirmation and offer rejection (`ERR_OFFER_EXPIRED`); the check-in window open (`ERR_CHECK_IN_TOO_EARLY`); the no-show window open (`ERR_NO_SHOW_TOO_EARLY`); the reported actual window well-formed (`ERR_INVALID_ACTUAL_WINDOW`); a capacity block's two endpoints on one UTC date (`ERR_BLOCK_DATE_MISMATCH`); the clock moving forward (`ERR_CLOCK_MOVES_BACKWARD`).
7. **Cross-entity linkage.** In order: every dependent named on a reservation belongs to that reservation's employee (`ERR_DEPENDENT_NOT_OWNED`); the plan named for an employee belongs to that employee's employer, on employee creation and on the employee amendment that moves a person onto another plan (`ERR_PLAN_EMPLOYER_MISMATCH`) — benefit-plan creation names no employee population and so never raises this code; the rejected offer belongs to the path reservation (`ERR_OFFER_RESERVATION_MISMATCH`); the capacity block named at confirmation belongs to the offered provider (`ERR_BLOCK_PROVIDER_MISMATCH`); an incident report's optional reservation reference names a reservation matched to the same provider (`ERR_INCIDENT_PROVIDER_MISMATCH`).
8. **Money and entitlement arithmetic.** In order: an invoice with no billable lines may not be issued (`ERR_INVOICE_EMPTY`); a payment must match the invoice total exactly (`ERR_PAYMENT_AMOUNT_MISMATCH`); a paid invoice may not be voided (`ERR_INVOICE_NOT_VOIDABLE`); a confirmation that would produce overage days while the employer forbids overage billing is refused (`ERR_OVERAGE_NOT_PERMITTED`); a new invoice period may not overlap an existing non-void period of the same employer (`ERR_INVOICE_PERIOD_OVERLAP`).
9. **Capacity, quota and uniqueness.** In order: centre-based seat capacity (`ERR_CAPACITY_EXHAUSTED`); reservation window containment inside the block (`ERR_WINDOW_OUTSIDE_BLOCK`); in-home caregiver concurrency after the travel buffer is applied (`ERR_CAREGIVER_WINDOW_CONFLICT`); one confirmed reservation per employee per care date (`ERR_DUPLICATE_CARE_DATE`); uniqueness keys (`ERR_DUPLICATE_KEY`); capacity-block overlap (`ERR_BLOCK_OVERLAP`); forward-only plan supersession (`ERR_ACTIVE_PLAN_EXISTS`).
10. **Credentialing and eligibility gates,** evaluated last of all. In order: the employee's `eligibility_status` (`ERR_EMPLOYEE_NOT_ELIGIBLE`); the dependent-count ceiling (`ERR_TOO_MANY_DEPENDENTS`); dependent eligibility (`ERR_DEPENDENT_NOT_ELIGIBLE`); the provider's credential set, which is checked on credential review, on any network-posture movement and on confirmation (`ERR_PROVIDER_NOT_CREDENTIALED`); the provider's network posture (`ERR_PROVIDER_NOT_IN_NETWORK`); same-day availability (`ERR_SAME_DAY_UNAVAILABLE`); the reinstatement score floor (`ERR_REINSTATE_SCORE_TOO_LOW`).

The uniqueness keys enforced under band 9 are: an `Employer` `name` unique across the whole system; an `employee_external_id` unique within one employer; a `user_id` unique across the whole system; a `plan_code` unique within one employer across plans whose `status` is `DRAFT` or `ACTIVE`; and at most one credential per `credential_type` per provider that is not `REVOKED`. The `Employer` `name` key is checked on employer creation and the `employee_external_id` and `user_id` keys on employee creation; the plan-code key is checked on benefit-plan creation, and the credential key on credential filing. Provider creation carries no uniqueness key of its own and therefore never returns `ERR_DUPLICATE_KEY`: two providers may freely share a `provider_name`, a `market_code` or an `owner_user_id`.

### 2.9. Two Independent State Dimensions on a Reservation

A reservation carries two lifecycle dimensions that advance independently and never read each other's current value. `fulfillment_status` tracks the sourcing and delivery of care and takes one of `INTAKE`, `MATCHING`, `OFFERED`, `CONFIRMED`, `IN_SERVICE`, `COMPLETED`, `CANCELLED`, `NO_SHOW`, or `UNFULFILLED`, starting at `INTAKE`. Its terminal states are `COMPLETED`, `CANCELLED` and `NO_SHOW`; `UNFULFILLED` is explicitly **not** terminal, because a coordinator may re-run matching and lift the reservation back to `OFFERED`.

`billing_status` tracks money movement and takes one of `NOT_BILLABLE`, `ACCRUED`, `INVOICED`, or `PAID`, starting at `NOT_BILLABLE`, with `PAID` as its only terminal state. Every billing transition is system-driven; no endpoint moves `billing_status` directly. The consequence is that the two dimensions genuinely decouple: a `COMPLETED` reservation may sit at `ACCRUED`, `INVOICED` or `PAID` without any further fulfillment movement, and a `CANCELLED` reservation may be `ACCRUED` (if the cancellation was late enough to draw a penalty) or remain `NOT_BILLABLE` (if it was not).

A `409` state error therefore names the dimension it guards. Attempting a transition the current `fulfillment_status` does not permit — confirming from `INTAKE`, checking in from `OFFERED`, completing from `CONFIRMED`, rejecting an offer from `MATCHING` — yields `ERR_RESERVATION_STATE_INVALID`, while any transition attempt on a reservation already in `COMPLETED`, `CANCELLED` or `NO_SHOW` yields `ERR_RESERVATION_TERMINAL`.

### 2.10. The Append-Only Entitlement Ledger and its Conservation Invariants

Every movement of entitlement days or penalty money is recorded as a `UsageLedgerEntry`, and those entries are never updated or deleted. Each entry names the `employee_id` whose entitlement it moves and the `reservation_id` that caused it, an `entry_type` drawn from `RESERVE`, `COMMIT`, `RELEASE`, `OVERAGE_ACCRUE`, `OVERAGE_REVERSE`, `NO_SHOW_CHARGE` and `LATE_CANCEL_CHARGE`, a signed `days_delta` (negative for a `RELEASE`, and zero on entries that move only money), a signed `cents_delta` (negative for an `OVERAGE_REVERSE`, and zero on entries that move only days), the `benefit_year_start` calendar date the entry is bucketed into, the `effective_at` clock reading at which it was appended, and a short machine-readable `memo` naming the transition that appended it.

Three invariants follow, and they hold after every forward transition and after every compensating transition that reverses it. First, for a given employee and benefit year, the sum of `days_delta` across all of that employee's entries in that year equals `entitlement_days_used` plus `entitlement_days_reserved`; a confirmation that reserves some number of days paired with its compensating cancellation, or paired with a provider-withdrawal that hands the reservation back to matching, leaves that sum exactly where it stood before the confirmation. Second, for a given capacity block, `reserved_slots` plus `committed_slots` equals the sum of `required_seats` over every reservation whose `matched_capacity_block_id` is that block and whose `fulfillment_status` is `CONFIRMED`, `IN_SERVICE`, `COMPLETED` or `NO_SHOW`; a confirmation paired with its cancellation or withdrawal returns that occupancy to its pre-confirmation value, and returns `block_status` from `FULL` to `OPEN`. Third, for a given employer and benefit year, the sum of `cents_delta` across the entries of all of that employer's employees is unaffected by invoicing: drafting or issuing an invoice only *reads* the ledger, and voiding an invoice deletes its lines without appending or removing any entry.

### 2.11. Benefit-Year Boundaries and Entitlement Resets

Entitlement is annual, and the year is the employer's, not the calendar's. Each employer declares a `fiscal_year_start_month` between 1 and 12, defaulting to January. Given the logical clock, the benefit year begins on the first day of that month in the clock's own year when the clock's month is at or after the declared month, and on the first day of that month in the previous year otherwise; `benefit_year_start` is that inclusive date, and `benefit_year_end` is the first day of the same month one year later, exclusive.

Ledger entries are bucketed by `benefit_year_start` at the moment they are appended, and every entitlement aggregate reads only the entries whose bucket equals the current benefit year. That single scoping rule is the entire reset mechanism: when the clock crosses into a new benefit year, last year's entries simply drop out of scope, restoring each employee's remaining allowance without any sweep, migration, or write of any kind.

## 3. Business Logic & Workflows

### 3.1. Sponsoring Employers and Their Benefit Designs

An employer account is registered with a legal `name` (non-empty, at most 200 characters, and globally unique) and an `industry_code` (non-empty, at most 16 characters) that is used for nothing except grouping in renewal analytics. Commercial terms follow, all optional at creation and all defaulted: `contract_status` is one of `ACTIVE`, `SUSPENDED` or `TERMINATED` and defaults to `ACTIVE`; `fiscal_year_start_month` defaults to 1; `invoicing_cycle` is `MONTHLY` or `QUARTERLY` and defaults to `MONTHLY`, recording the cadence agreed with the client but scheduling nothing on its own; `admin_fee_pct` defaults to 0.085, that is eight and a half percent; `overage_billing_enabled` defaults to true; and `adult_elder_extension_enabled` defaults to false. Two counters are derived rather than supplied. `accrued_overage_cents_current_period` is the sum of `cents_delta` over every ledger entry of type `OVERAGE_ACCRUE` minus the sum over every entry of type `OVERAGE_REVERSE`, taken across all of this employer's employees and restricted to entries whose `effective_at` falls inside the benefit year containing the logical clock; it is the figure the overage tier snapshot reads. `ytd_billed_cents` is the sum of `total_cents` over this employer's invoices whose `invoice_status` is `ISSUED` or `PAID`.

Amending an employer is a `benefits_admin` operation and may revise `contract_status`, `admin_fee_pct`, `invoicing_cycle`, `overage_billing_enabled`, `adult_elder_extension_enabled` and `fiscal_year_start_month`. Two consequences deserve attention. Moving `contract_status` away from `ACTIVE` immediately drives every one of that employer's employees to an `eligibility_status` of `INELIGIBLE` without touching any employee's `employment_status`. And the amendment bumps the employer's `version`, which invalidates any `expected_employer_version` a plan writer is still holding.

A benefit design is drafted as a `BenefitPlan` against an `employer_id`, with a `plan_code` and the full commercial shape of the benefit: `annual_use_limit_days`, the entitlement days each enrolled employee receives per benefit year, between 1 and 60 inclusive; `copay_center_cents_per_day`, the employee's copay per covered centre-based care day, between 0 and 100000 inclusive; `copay_in_home_cents_per_hour`, the employee's copay per covered in-home billable hour, in the same range; `in_home_min_billable_hours`, the floor applied to any in-home reservation, defaulting to 4, greater than 0, at most 12, and a whole multiple of a quarter hour; `eligible_dependent_types`, a non-empty duplicate-free subset of `CHILD` and `ADULT_ELDER`; `max_dependents_per_reservation`, defaulting to 3 and constrained between 1 and 6 inclusive; `overage_rate_center_cents_per_day` and `overage_rate_in_home_cents_per_hour`, the employer-billed rates before the tier multiplier, each between 0 and 500000 inclusive; `cancellation_window_hours`, the number of hours before the start of care up to and including which a cancellation is penalty-free, defaulting to 24 and constrained between 0 and 168 inclusive; `no_show_charge_cents`, the employer-billed charge for a missed confirmed reservation, between 0 and 200000 inclusive; and the validity window `effective_from` (inclusive) with an optional `effective_to` (exclusive, defaulting to null for an open-ended design). The `plan_code` must be unique within the employer across every plan whose `status` is `DRAFT` or `ACTIVE`; the companion `ERR_PLAN_EMPLOYER_MISMATCH` guard, which keeps a design and the workforce enrolled on it under one employer, is enforced when an employee is enrolled against the plan or later moved onto it rather than at drafting time. A new plan is born with `status` `DRAFT`, `superseded_by_plan_id` null and `enrolled_employee_count` zero, enrolls nobody and supersedes nothing.

A plan's `status` moves through `DRAFT`, `ACTIVE` and `SUPERSEDED`, with `SUPERSEDED` terminal. While the plan is `DRAFT` a `benefits_admin` may amend `annual_use_limit_days`, `copay_center_cents_per_day`, `copay_in_home_cents_per_hour`, `in_home_min_billable_hours`, `eligible_dependent_types`, `max_dependents_per_reservation`, `overage_rate_center_cents_per_day`, `overage_rate_in_home_cents_per_hour`, `cancellation_window_hours`, `no_show_charge_cents` and `effective_to`; each such amendment bumps the plan's `version`, so any reservation later taken against the plan pins the newer design. Once the plan is `ACTIVE` it is frozen: an amendment attempt returns `ERR_PLAN_NOT_EDITABLE`, and the only way to change terms is to activate a successor.

Activation moves `DRAFT` to `ACTIVE` and requires three things: the owning employer's `contract_status` is `ACTIVE` (otherwise `ERR_EMPLOYER_CONTRACT_INACTIVE`), the plan's `effective_from` is at or before the logical clock, and the plan's `effective_to` is either null or strictly after the logical clock (otherwise `ERR_PLAN_EFFECTIVE_WINDOW`). Activating a plan whose `status` is not `DRAFT` returns `ERR_BENEFITPLAN_STATE_INVALID`, and activating one already `SUPERSEDED` returns `ERR_BENEFITPLAN_TERMINAL`. Supersession only ever moves forward in effective-date order: if the employer already holds an `ACTIVE` plan whose `effective_from` is on or after the candidate's `effective_from`, activation is refused with `ERR_ACTIVE_PLAN_EXISTS`, because activating the candidate would leave a later-effective incumbent superseded by an earlier-effective design. When activation succeeds, at most one `ACTIVE` plan per employer survives: the incumbent moves `ACTIVE → SUPERSEDED` and its `superseded_by_plan_id` is set to the newly activated plan's identifier. Employees already enrolled keep their existing `benefit_plan_id` — supersession re-enrols nobody — with the practical effect that a new reservation for an employee still pointing at the superseded design is refused with `ERR_PLAN_NOT_ACTIVE`. Plan listings are filterable by `superseded_by_plan_id`, which is how the supersession chain is walked in reverse to find the design a given plan replaced.

### 3.2. Enrolling the Workforce and Registering Dependents

Enrolment is a `benefits_admin` act. An `Employee` is created against an `employer_id` and a `benefit_plan_id` that must be `ACTIVE` and must belong to that same employer, carrying an `employee_external_id` (the employer's payroll identifier, unique within the employer), a `user_id` (the globally unique, non-empty, at most 80 character identifier the person will present as `X-User-ID` when acting as an `employee_user`), an `email` that must contain an at-sign, a `full_name` of at most 200 non-empty characters, and an `employment_status` of `ACTIVE`, `LEAVE` or `TERMINATED` that defaults to `ACTIVE`. Creating an employee recomputes `enrolled_employee_count` on the named plan, which counts the employees pointing at that plan whose `employment_status` is `ACTIVE` or `LEAVE`. A later amendment may revise `employment_status`, `email`, or move the person to a different `ACTIVE` plan of the same employer via `benefit_plan_id`; that amendment recomputes `eligibility_status` and recomputes `enrolled_employee_count` on both the old and the new plan. Moving `employment_status` away from `ACTIVE` flips `eligibility_status` to `INELIGIBLE` but leaves already-confirmed care standing.

Four employee counters are derived, all scoped to the current benefit year. `entitlement_days_used` is the sum of `days_delta` over that employee's `COMMIT` entries. `entitlement_days_reserved` is the sum of `days_delta` over that employee's `RESERVE` and `RELEASE` entries taken together — which is why a release, carrying a negative delta, cancels the reservation it compensates. `no_show_strike_count` is the number of `NO_SHOW_CHARGE` entries. `eligibility_status` is derived in a strictly ordered three-way test: it is `INELIGIBLE` when the employee's `employment_status` is anything other than `ACTIVE` or the employer's `contract_status` is anything other than `ACTIVE`; failing that, it is `RESTRICTED` when `no_show_strike_count` has reached two or more strikes; otherwise it is `ELIGIBLE`.

The forward-looking entitlement projection an employee or an administrator reads exposes that arithmetic explicitly. It reports the `employee_id`, the `benefit_year_start` and `benefit_year_end` bounding the current year, the `days_limit` taken from the enrolled plan's `annual_use_limit_days`, the `days_used` and `days_reserved` sums described above, a `days_remaining` figure that is the allowance less both of those sums but never below zero, an `overage_days_projected` figure that is the amount by which those two sums together exceed the allowance and is likewise never below zero, the `no_show_strike_count`, and the `eligibility_status`. Because `days_remaining` subtracts still-reserved days as well as committed ones, a confirmed-but-not-yet-delivered reservation already reduces the remaining allowance. Day quantities in the projection are carried to two decimal places, rounded half up; the strike count is an integer.

Dependents hang off the employee. Each `Dependent` carries the `employee_id` it belongs to, a `full_name` of at most 200 non-empty characters, a `dependent_type` of either `CHILD` or `ADULT_ELDER` that selects the care track, a `date_of_birth` as an ISO 8601 calendar date, a `relationship` string of at most 40 non-empty characters such as SON, DAUGHTER, PARENT or SPOUSE, an optional free-text `care_notes` block that defaults to the empty string and is forwarded verbatim to the matched provider, and a `status` of `ACTIVE` or `INACTIVE` defaulting to `ACTIVE`. Either a `benefits_admin` or the employee themselves may register a dependent and may later amend `full_name`, `relationship`, `care_notes` or `status`. Setting `status` to `INACTIVE` bars the dependent from *new* reservations but never rewrites the frozen dependent list of an existing one. Dependent listings are filterable by `dependent_type` and `status`.

### 3.3. The Provider Network: Onboarding, Credentialing, Capacity and Posture

A `network_admin` onboards a provider with a `provider_name` of at most 200 non-empty characters, an `owner_user_id` (the at most 80 character, non-empty `X-User-ID` of the `provider_manager` entitled to act on this provider), a `care_mode` of either `CENTER_BASED` or `IN_HOME`, a `market_code` and a `postal_code` each of at most 16 non-empty characters, and three optional operational settings: `daily_capacity_slots`, defaulting to 0 and capped at 500, which is the seat count copied onto new centre-based capacity blocks when none is supplied; `max_concurrent_assignments`, defaulting to 1 and constrained between 1 and 10 inclusive, which bounds an in-home caregiver's overlapping workload; and `same_day_available`, defaulting to false. A provider's `care_mode` and `market_code` are immutable for its lifetime — an amendment may carry them only if the supplied value equals the stored value, and any attempted change is refused with `ERR_PROVIDER_FIELD_IMMUTABLE`, while `provider_name`, `postal_code`, `daily_capacity_slots`, `max_concurrent_assignments` and `same_day_available` remain freely amendable. Four provider figures are derived: `quality_score` and `lifetime_quality_score`, the two scoring variants described in Section 3.8, both starting at 100; `substantiated_incident_count`, the number of this provider's incident reports whose `incident_status` is `SUBSTANTIATED`; and `completed_reservation_count`, the number of reservations whose `matched_provider_id` is this provider and whose `fulfillment_status` is `COMPLETED`. A fifth, `last_status_reason_code`, records the reason code carried by the most recent network-posture movement and starts null.

Credentials are the gate into the network. A `Credential` names its `provider_id` and a `credential_type` of `LICENSE`, `BACKGROUND_CHECK`, `CPR` or `INSURANCE`, records the `issued_on` and `expires_on` ISO 8601 calendar dates (with `expires_on` strictly after `issued_on`), and captures a `verified_by` identifier of at most 80 non-empty characters for the operator who checked the document. Its `status` starts at `VALID` and may reach `EXPIRED` or `REVOKED`, both terminal, and `revoked_reason_code` starts null. A provider may hold at most one credential per `credential_type` that is not `REVOKED`; a second attempt returns `ERR_DUPLICATE_KEY`. Expiry is evaluated by comparing `expires_on` against the relevant date: strictly earlier than the logical clock's date means expired. **The required credential set** — the four types `LICENSE`, `BACKGROUND_CHECK`, `CPR` and `INSURANCE`, all of them — is what "fully credentialed" means throughout this document. Either a `network_admin` or the owning `provider_manager` may file a credential; only a `network_admin` may revoke one, supplying a `revoked_reason_code`. Revoking a credential that is already `EXPIRED` or `REVOKED` returns `ERR_CREDENTIAL_TERMINAL`. Credential listings are filterable by `credential_type` and `status`.

`network_status` starts at `PENDING` and moves among `PENDING`, `CREDENTIALED`, `PROBATION`, `SUSPENDED` and `DEPROVISIONED`, the last of which is terminal. Credential review lifts `PENDING → CREDENTIALED` and requires that, for every one of the four required types, the provider holds a credential whose `status` is `VALID` and whose `expires_on` is on or after the logical clock's date; a gap in that set returns `ERR_PROVIDER_NOT_CREDENTIALED`. A successful review records `last_status_reason_code` as `CREDENTIAL_REVIEW_PASSED` when no `reason_code` is supplied and recomputes both quality-score variants. A posture change requested directly carries a `target_status` and a `reason_code`, and a target unreachable from the current posture — `PENDING` to `PROBATION`, or `SUSPENDED` to `PROBATION`, for instance — returns `ERR_PROVIDER_STATE_INVALID`, while any request against a `DEPROVISIONED` provider returns `ERR_PROVIDER_TERMINAL`.

`CREDENTIALED → PROBATION` is a demotion that keeps the provider working: it records `last_status_reason_code` from the supplied reason code when a `network_admin` names `PROBATION` as `target_status` directly, and from the fixed string `INCIDENT_SUBSTANTIATED` — never from that report's own `resolution_reason_code` — when the demotion is instead driven by a substantiated incident, causes every later ranking evaluation to multiply this provider's score by one half and to stamp `probation_penalty_applied` true on the offers it generates, and withdraws no reservation whatsoever — providers on probation remain confirmable. The reverse move, `PROBATION → CREDENTIALED`, requires both a complete unexpired required credential set and a `lifetime_quality_score` of at least 60; a score below that floor returns `ERR_REINSTATE_SCORE_TOO_LOW`. On success it records `last_status_reason_code` from the supplied reason code, stops applying the one-half probation factor to later rankings, and recomputes both score variants without resetting them — substantiated incidents keep deducting after reinstatement.

`CREDENTIALED → SUSPENDED` and `PROBATION → SUSPENDED` share one side-effect set and four triggers: a `network_admin` revoking a required credential, the nightly maintenance sweep detecting that a required credential has lapsed, a `network_admin` naming `SUSPENDED` as `target_status`, or a substantiated incident carrying a `qa_action` of `SUSPENSION`. Each records `last_status_reason_code`, removes the provider from every later candidate set, and runs the **withdrawal cascade**: for every reservation whose `matched_provider_id` is this provider, whose `fulfillment_status` is `CONFIRMED` and whose `care_start_utc` is still after the logical clock, the reservation is driven `CONFIRMED → MATCHING`. That per-reservation move appends a `UsageLedgerEntry` of type `RELEASE` whose `days_delta` is the negation of `days_charged_provisional`, with `cents_delta` zero and `memo` `PROVIDER_WITHDRAWN`; recomputes the employee's `entitlement_days_reserved`; recomputes `reserved_slots` and `block_status` on the vacated capacity block and bumps that block's `version` by 1; clears `matched_provider_id`, `matched_capacity_block_id` and `confirmation_code` to null; resets `days_charged_provisional`, `covered_days`, `overage_days`, `copay_cents` and `overage_cents` to 0 and `overage_tier_multiplier` to 1; leaves `billing_status` untouched at `NOT_BILLABLE`; and — this is deliberate — does **not** append the withdrawn provider to `excluded_provider_ids`, so the same provider may legitimately be offered again if it returns to the network before the care date.

Reinstatement from suspension, `SUSPENDED → CREDENTIALED`, carries the same two preconditions as reinstatement from probation (the full unexpired required set, and a `lifetime_quality_score` of at least 60, else `ERR_REINSTATE_SCORE_TOO_LOW`), records `last_status_reason_code`, and returns the provider to later candidate sets — but reservations withdrawn during the suspension are never re-attached. Deprovisioning is one-way: `CREDENTIALED → DEPROVISIONED` and `PROBATION → DEPROVISIONED` run exactly the same withdrawal cascade as suspension and the provider can never return to any other posture, while `SUSPENDED → DEPROVISIONED` merely records `last_status_reason_code` because no reservation can still be `CONFIRMED` against a suspended provider.

Capacity is published as `CapacityBlock` rows by a `network_admin` or the owning `provider_manager`, each carrying its `provider_id`, an inclusive `start_time_utc`, an exclusive `end_time_utc` that must be strictly later and fall on the same UTC calendar date (otherwise `ERR_BLOCK_DATE_MISMATCH`), and a `total_slots` seat count between 0 and 500 inclusive that defaults to the provider's `daily_capacity_slots` when omitted. The `service_date` is derived from `start_time_utc`. Blocks of the same provider on the same `service_date` may not overlap, and because each interval is treated as half-open, a block that starts at exactly the instant another ends is accepted; a genuine overlap returns `ERR_BLOCK_OVERLAP`. Two occupancy counters are derived: `reserved_slots` is the sum of `required_seats` over reservations occupying this block whose `fulfillment_status` is `CONFIRMED` or `IN_SERVICE`, and `committed_slots` is the same sum over those whose `fulfillment_status` is `COMPLETED` or `NO_SHOW`. `block_status` follows in a pinned order: it is `CLOSED` once the block is past-dated or closed by maintenance; failing that it is `FULL` when the owning provider's `care_mode` is `CENTER_BASED` and `reserved_slots` plus `committed_slots` has reached `total_slots` or beyond; otherwise it is `OPEN`. `FULL` is unreachable for an in-home provider. `total_slots` governs aggregate capacity only for a centre-based provider; for an in-home provider the block bounds the servable window and nothing else, with concurrency governed instead by `max_concurrent_assignments` and the travel buffer. Blocks may not be published against a `DEPROVISIONED` provider (`ERR_PROVIDER_TERMINAL`), and block listings are filterable by `service_date` and `block_status`.

**Window and capacity admission** is one shared decision procedure, consulted twice: once by the matching ranker when it picks a candidate block, and again as a precondition of confirmation. First, containment: the block must start at or before `care_start_utc` and end at or after `care_end_utc`; a reservation window not fully inside the block's window is refused with `ERR_WINDOW_OUTSIDE_BLOCK`. Then the two semantics diverge on the provider's `care_mode`. For `CENTER_BASED`, the seats needed are the reservation's `dependent_count` and the seats available are `total_slots` less `reserved_slots` less `committed_slots`; admission requires availability to be at least the seats needed, and a shortfall is `ERR_CAPACITY_EXHAUSTED`. Only the seat *sum* is constrained, and the interval is half-open, so two reservations whose windows merely touch — one ending at exactly the instant the other begins — coexist freely. For `IN_HOME`, the reservation occupies the caregiver exclusively and requires one seat regardless of dependent count, `total_slots` is ignored entirely, and a one-hour travel buffer is applied to both ends of every comparison. A previously booked reservation of the same provider, other than the one being admitted and with `fulfillment_status` `CONFIRMED` or `IN_SERVICE`, conflicts with the candidate exactly when the candidate's `care_start_utc` falls strictly before that reservation's `care_end_utc` advanced by the sixty-minute buffer **and** that reservation's `care_start_utc` falls strictly before the candidate's `care_end_utc` advanced by the same buffer. Admission requires the number of conflicting reservations to be strictly fewer than the provider's `max_concurrent_assignments`; otherwise `ERR_CAREGIVER_WINDOW_CONFLICT`. The buffer boundary is exact: a gap of precisely sixty minutes between two visits does not conflict, while a gap one minute shorter does.

### 3.4. Reservation Intake and Plan Pinning

A reservation may be opened by a `care_coordinator`, a `benefits_admin`, or the employee themselves. The payload names the `employee_id`, a `requested_care_mode` of `CENTER_BASED`, `IN_HOME` or `EITHER`, a `market_code` of at most 16 non-empty characters in which the care must be delivered, the inclusive `care_start_utc` and exclusive `care_end_utc` bounding the requested window, and `dependent_ids`, the array of dependents to be covered. The window must be well-formed (end strictly after start), must fall entirely on one UTC calendar date (otherwise `ERR_CARE_WINDOW_SPANS_DAYS`, which also covers a window longer than 14 hours), and must begin strictly after the logical clock (otherwise `ERR_CARE_WINDOW_IN_PAST`). The reservation is born with `fulfillment_status` `INTAKE` and `billing_status` `NOT_BILLABLE`, and consumes no entitlement whatsoever.

Intake screens the request through the eligibility gates in a fixed order. The employee's `eligibility_status` must be `ELIGIBLE`; a `RESTRICTED` employee (two or more no-show strikes this benefit year) or an `INELIGIBLE` one (non-active employment, or an employer whose contract is not active) is refused with `ERR_EMPLOYEE_NOT_ELIGIBLE`. Then the number of dependents named may not exceed the pinned plan's `max_dependents_per_reservation`; exactly at the limit is accepted, and beyond it returns `ERR_TOO_MANY_DEPENDENTS`. Then each dependent must have `status` `ACTIVE` and a `dependent_type` present in the plan's `eligible_dependent_types`, and an `ADULT_ELDER` dependent additionally requires the employer's `adult_elder_extension_enabled` to be true — the adult and elder extension is an employer-level switch that overrides plan eligibility, so an employer with the extension off refuses adult-and-elder care even under a plan that lists the type. Every failure in that group is `ERR_DEPENDENT_NOT_ELIGIBLE`. Earlier bands still apply: a dependent belonging to a different employee is `ERR_DEPENDENT_NOT_OWNED`, and a plan that is not `ACTIVE` is `ERR_PLAN_NOT_ACTIVE`.

Intake also pins the design. The employee's current `benefit_plan_id` is copied onto the reservation and never re-read afterwards, and the plan's current `version` is captured as `plan_version_pinned`; all charge arithmetic for the reservation's whole life reads the plan design as of that version, so a later plan amendment or supersession cannot retroactively reprice care already booked. From the window and the dependent list, intake derives `care_date` (the UTC calendar date of `care_start_utc`), `dependent_count` (the length of `dependent_ids`, frozen from this point on), `dependent_type_mix` (`CHILD_ONLY` when every referenced dependent is a `CHILD`, `ADULT_ELDER_ONLY` when every one is an `ADULT_ELDER`, and `MIXED` in any other case), `required_seats` (the dependent count when the care will be delivered centre-based, and 1 when it will be delivered in-home; before a provider has been matched the requested mode decides, so it is `dependent_count` when `requested_care_mode` is `CENTER_BASED` and 1 otherwise, `EITHER` included), and `cancellation_deadline_utc`, which is `care_start_utc` moved earlier by the pinned plan's `cancellation_window_hours` and is frozen for the reservation's life. The remaining charge fields start empty: `billable_hours_provisional`, `days_charged_provisional`, `covered_days`, `overage_days`, `copay_cents`, `overage_cents` and `penalty_cents` at 0, `overage_tier_multiplier` at 1, `excluded_provider_ids` as an empty array, and `billable_hours_final`, `days_charged_final`, `matched_provider_id`, `matched_capacity_block_id`, `confirmation_code`, `unfulfilled_reason_code`, `cancel_reason_code`, `actual_start_utc` and `actual_end_utc` all null.

Reservation listings support reverse traversal of all three forward references: `benefit_plan_id`, `matched_provider_id` and `matched_capacity_block_id` are each filterable, a `dependent_id` filter searches inside the frozen dependent array, and `employee_id`, `fulfillment_status`, `billing_status`, `care_date` and `market_code` narrow further.

### 3.5. Matching, Ranking and the Offer Cycle

Matching is exclusive to the `care_coordinator` and is callable from three fulfillment states: `INTAKE`, `MATCHING` and `UNFULFILLED`. From `INTAKE` and from `MATCHING` it requires that the employee's `eligibility_status` is `ELIGIBLE` (`ERR_EMPLOYEE_NOT_ELIGIBLE`), that the pinned plan's `status` is still `ACTIVE` (`ERR_PLAN_NOT_ACTIVE`), and that `care_start_utc` is still after the logical clock (`ERR_CARE_WINDOW_IN_PAST`). From `UNFULFILLED` it requires that `care_start_utc` is still after the logical clock. Any other origin state yields `ERR_RESERVATION_STATE_INVALID`, and a terminal reservation yields `ERR_RESERVATION_TERMINAL`.

**The candidate filter.** A provider survives only if *every* one of these holds: its `market_code` equals the reservation's `market_code`; its `network_status` is `CREDENTIALED` or `PROBATION`; either the reservation's `requested_care_mode` is `EITHER` or the provider's `care_mode` equals that requested mode; its identifier is not present in `excluded_provider_ids`; for each of the four required credential types it holds a credential whose `status` is `VALID` and whose `expires_on` is on or after the reservation's `care_date`; either the `care_date` differs from the logical clock's UTC date or the provider's `same_day_available` is true; and a candidate block exists for it. **The candidate block** for a surviving provider is chosen from that provider's blocks whose `block_status` is `OPEN`, whose `service_date` equals the reservation's `care_date`, whose `start_time_utc` is at or before `care_start_utc`, whose `end_time_utc` is at or after `care_end_utc`, and which the window-and-capacity admission procedure admits; among those, the block with the largest availability (its `total_slots` less its `reserved_slots` less its `committed_slots`) wins, ties broken by the earliest `start_time_utc` and then the earliest `created_at`. When that set is empty, the provider has no candidate block and drops out of the filter.

**The ranking expression.** For each surviving provider, the seats figure is `required_seats` recomputed for that provider's `care_mode`, and the remaining figure is the candidate block's `total_slots` less its `reserved_slots` less its `committed_slots`. Four components are then formed. `quality_component` is the provider's `quality_score` divided by one hundred, rounded to four decimal places. `capacity_component` is the remaining figure divided by twice the seats figure — or by 1 when twice the seats figure would be smaller than 1 — capped at 1.0 and rounded to four decimal places. `mode_component` is 1.0 when the reservation named a specific mode; when the reservation asked for `EITHER`, it is 1.0 for a `CENTER_BASED` provider and 0.6 for an `IN_HOME` one, which is how the system expresses a mild institutional preference for centre-based care when the family is indifferent. `continuity_component` is 1 when this provider already holds a `COMPLETED` reservation for this same employee and 0 otherwise, rewarding a caregiver the family has met before. The base score weights those four at forty-five hundredths for quality, thirty hundredths for capacity, fifteen hundredths for modality fit and ten hundredths for continuity, summed. The stored `rank_score` is that base multiplied by one half when the provider's `network_status` is `PROBATION` and by 1.0 otherwise, rounded to four decimal places; when the halving applies, `probation_penalty_applied` is stamped true on the offer. All four components are persisted on the offer alongside `remaining_slots_at_offer`, the candidate block's availability at generation time.

**Ordering and tie-breaks.** Candidates are sorted by `rank_score` descending; where scores tie, the higher `quality_score` wins; where those tie as well, the earlier `created_at` wins. A provider's identifier is never consulted as a tie-break. `rank_position` is the 1-based position in that sorted list.

**What a match run writes.** When the candidate set is non-empty the reservation lands in `OFFERED`. One `MatchOffer` is created per candidate, each recording its `reservation_id` and `provider_id`, its `rank_score` and `rank_position`, the four components, `probation_penalty_applied`, `remaining_slots_at_offer`, and an `offer_expires_at` instant that is the logical clock at generation advanced by 48 hours but never later than the reservation's `care_start_utc`; an action taken at exactly `offer_expires_at` is still in time. The offer at `rank_position` 1 is given `offer_status` `SELECTED`; every other new offer gets `PROPOSED`. `matched_provider_id` is set to the selected offer's provider, and `required_seats` is recomputed from that provider's `care_mode` — the dependent count for `CENTER_BASED`, 1 for `IN_HOME`. An `offer_status` moves among `PROPOSED`, `SELECTED`, `REJECTED` and `EXPIRED`, and a `reason_code` records why an offer was rejected or expired, starting null. Re-running matching from `MATCHING`, and likewise from `UNFULFILLED`, first expires every surviving `PROPOSED` offer of the previous batch with `reason_code` `REMATCHED` before publishing the new batch; a run from `UNFULFILLED` additionally clears `unfulfilled_reason_code` back to null. Offer listings are filterable by `reservation_id`, `provider_id` and `offer_status`, which is how the many-to-many candidate graph between reservations and providers is walked in either direction.

**When nobody is available.** An empty candidate pool is not an error. From `INTAKE` and from `MATCHING` (the latter after removing every provider in `excluded_provider_ids`), an empty pool moves the reservation to `UNFULFILLED`; from `UNFULFILLED` it simply leaves the reservation where it already is. In every case an empty pool sets `unfulfilled_reason_code` to `NO_ELIGIBLE_PROVIDER`, creates zero offers, leaves `matched_provider_id` null, and returns 200. From `MATCHING`, the same run also expires every surviving `PROPOSED` offer with `reason_code` `REMATCHED`.

**Declining the selected offer.** A `care_coordinator` or the employee may reject the offer on the table by naming `match_offer_id` and a `reason_code`. The named offer must belong to the path reservation (`ERR_OFFER_RESERVATION_MISMATCH`) and must currently be `SELECTED` (`ERR_OFFER_NOT_SELECTED`), and the logical clock must be at or before its `offer_expires_at` (`ERR_OFFER_EXPIRED`, which also covers an offer already `EXPIRED`). Rejection moves the reservation `OFFERED → MATCHING`: the named offer becomes `REJECTED` with the supplied reason code, its provider is appended to `excluded_provider_ids` and can never be offered for this reservation again, every other `PROPOSED` offer of the batch becomes `EXPIRED` with `reason_code` `OFFER_BATCH_CLOSED`, `matched_provider_id` is cleared to null, and `billing_status` is left untouched at `NOT_BILLABLE`. The growing exclusion list is what guarantees the `OFFERED → MATCHING → OFFERED` cycle terminates.

### 3.6. Confirmation, Entitlement Reservation and the Provisional Charge

Confirmation is exclusive to the `care_coordinator`, moves `OFFERED → CONFIRMED`, and is the single most heavily guarded operation in the system. Its payload is small — `capacity_block_id` and `expected_capacity_block_version` — and its checks are many. Once the named block resolves, the stale-version guard fires first, rejecting a mismatch with `ERR_STALE_CAPACITY_BLOCK_VERSION` (412). Then the reservation's state must permit the move (`ERR_RESERVATION_STATE_INVALID`, or `ERR_RESERVATION_TERMINAL` for an already-closed reservation) and the block's `block_status` must be `OPEN` (`ERR_BLOCK_NOT_OPEN`). Then the selected offer must still be live against `offer_expires_at` (`ERR_OFFER_EXPIRED`). Then the block must belong to the provider named by `matched_provider_id` (`ERR_BLOCK_PROVIDER_MISMATCH`) and its `service_date` must equal the reservation's `care_date`. Then the fiscal gate: if the employer's `overage_billing_enabled` is false and the entitlement split below would yield any overage days at all, the confirmation is refused with `ERR_OVERAGE_NOT_PERMITTED` — such an employer buys a hard cap rather than a billable overflow. Then the capacity gates in order: centre-based seat availability (`ERR_CAPACITY_EXHAUSTED`), window containment inside the block (`ERR_WINDOW_OUTSIDE_BLOCK`), in-home caregiver concurrency after the travel buffer (`ERR_CAREGIVER_WINDOW_CONFLICT`), and the one-reservation-per-day rule: an employee may hold at most one reservation with `fulfillment_status` `CONFIRMED` or `IN_SERVICE` on any single `care_date`, and a second returns `ERR_DUPLICATE_CARE_DATE`. Last come the safety gates: the provider must hold a `VALID` credential of each of the four required types that does not expire before the `care_date` (`ERR_PROVIDER_NOT_CREDENTIALED`); its `network_status` must be `CREDENTIALED` or `PROBATION`, with `PENDING`, `SUSPENDED` and `DEPROVISIONED` all refused as `ERR_PROVIDER_NOT_IN_NETWORK`; and when the `care_date` is the logical clock's own UTC date, the provider's `same_day_available` must be true (`ERR_SAME_DAY_UNAVAILABLE`).

The charge arithmetic runs in four pinned stages, all of them reading the plan design as of `plan_version_pinned`, and all of them using the **effective care mode**, which is the `care_mode` of the provider named by `matched_provider_id`.

**Stage one — billable hours.** For centre-based care, billable hours are zero, because centre-based care is billed in whole entitlement days. For in-home care, the raw hours are the total number of seconds between the window's start and its exclusive end divided by 3600, held as an exact decimal; that raw figure is then raised to the next whole multiple of a quarter hour; and the billable figure is the greater of that stepped value and the plan's `in_home_min_billable_hours` floor. The stored value carries two decimal places, rounded half up, while the raise-to-a-quarter-hour step is exact and never rounded. At confirmation the window used is the *requested* one — `care_start_utc` to `care_end_utc` — and the result is written to `billable_hours_provisional`.

**Stage two — day charge.** For centre-based care, the days charged equal `dependent_count`: one entitlement day per dependent per care date. For in-home care, one caregiver visit covers every dependent at once, so the days charged are the billable hours divided by eight and then raised to the next whole number; day counts are non-negative integers and the raise is exact. At confirmation the result is written to `days_charged_provisional`.

**Stage three — the entitlement waterfall.** This runs immediately after stage two, in exactly six steps, and no step may read a value written by a later step. Step one totals the `days_delta` of this employee's `COMMIT` entries in the current benefit year, excluding any entry belonging to this same reservation, replayed in `effective_at` ascending and then `created_at` ascending order — the days already consumed. Step two totals the `days_delta` of this employee's `RESERVE` and `RELEASE` entries in the same year and the same replay order, again excluding this reservation's own entries — the days already held. Step three takes the plan's `annual_use_limit_days`, subtracts both of those totals, and floors the result at zero — the days remaining. Step four sets `covered_days` to the smaller of the days charged and the days remaining. Step five sets `overage_days` to the days charged less `covered_days`. Step six snapshots the tier: reading the employer's `accrued_overage_cents_current_period` *as it stands before this reservation's own overage accrual exists*, `overage_tier_multiplier` becomes 1.00 when that accrual is below 100000 cents (one thousand dollars), 0.90 when it is below 500000 cents (five thousand dollars), and 0.80 otherwise. The ordering here is load-bearing in both directions: a reservation never influences its own tier multiplier, even though the multiplier feeds the accrual from which later tiers are computed. The exclusion of this reservation's own entries matters mainly on the second pass at completion, when the reservation's `RESERVE` entry already exists and would otherwise cause the reservation to be charged against its own provisional hold; at confirmation there is nothing of the reservation's own to exclude. Day quantities carry two decimal places, rounded half up; the multiplier is exact to two decimals.

**Stage four — money.** For centre-based care, `copay_cents` is `covered_days` multiplied by the plan's `copay_center_cents_per_day`, rounded to a whole cent; the overage unit rate is the plan's `overage_rate_center_cents_per_day` multiplied by `overage_tier_multiplier` and rounded to a whole cent; `overage_cents` is `overage_days` multiplied by that rounded unit rate and rounded again to a whole cent; and the covered and overage billed quantities are `covered_days` and `overage_days` respectively. For in-home care the split is expressed in hours instead. When the days charged are zero, both hour quantities are zero. Otherwise the covered hours are the billable hours multiplied by `covered_days` and divided by the days charged, rounded to two decimal places, and the overage hours are the billable hours less those covered hours, rounded to two decimal places. `copay_cents` is then the covered hours multiplied by the plan's `copay_in_home_cents_per_hour`, rounded to a whole cent; the overage unit rate is the plan's `overage_rate_in_home_cents_per_hour` multiplied by `overage_tier_multiplier` and rounded to a whole cent; and `overage_cents` is the overage hours multiplied by that rounded unit rate, rounded to a whole cent. The covered and overage billed quantities are the covered and overage hours. Those quantities, and the rounded overage unit rate, are exactly what invoicing later records as a line's `quantity` and `unit_cents`.

A successful confirmation then writes its side effects. It sets `matched_capacity_block_id` to the named block and mints a `confirmation_code` as the family's care reference. It writes `billable_hours_provisional`, `days_charged_provisional`, `covered_days`, `overage_days`, `overage_tier_multiplier`, `copay_cents` and `overage_cents` from the provisional pass just described. It appends one `UsageLedgerEntry` of type `RESERVE` whose `days_delta` is the positive `days_charged_provisional`, whose `cents_delta` is zero and whose `memo` is `CONFIRM`. It recomputes the employee's `entitlement_days_reserved` and `eligibility_status`. It recomputes the block's `reserved_slots` and `block_status` and bumps that block's `version` by 1. And it expires every remaining `PROPOSED` offer of the batch with `reason_code` `CONFIRMED_ELSEWHERE`.

### 3.7. Delivery Outcomes: Check-In, Completion, No-Show and Cancellation

**Check-in** moves `CONFIRMED → IN_SERVICE` and may be performed by a `care_coordinator` or by the owning `provider_manager`. The window opens one hour before `care_start_utc` — the logical clock must be at or after `care_start_utc` moved earlier by sixty minutes — and closes at `care_end_utc`, which the clock must still be strictly before; outside that window the answer is `ERR_CHECK_IN_TOO_EARLY`. The provider's `network_status` must still be `CREDENTIALED` or `PROBATION` (`ERR_PROVIDER_NOT_IN_NETWORK`). Check-in appends no ledger entry and moves no money: the reservation continues to occupy `reserved_slots` on its block, exactly as it did while `CONFIRMED`.

**Completion** moves `IN_SERVICE → COMPLETED` and reports the care that actually happened via `actual_start_utc` and `actual_end_utc`. The reported end must be strictly after the reported start, both instants must fall on the reservation's `care_date`, and the logical clock must be at or after the reported end; any of those failing returns `ERR_INVALID_ACTUAL_WINDOW`. Completion re-runs stages one through four of the charge arithmetic against the *actual* window rather than the requested one, writing `billable_hours_final` and `days_charged_final` and then overwriting `covered_days`, `overage_days`, `overage_tier_multiplier`, `copay_cents` and `overage_cents` from that final pass. This is where the provisional and final variants can genuinely disagree: an in-home visit requested for six hours but actually running nine and a half hours yields one provisional day and two final days from identical plan inputs.

The ledger movement at completion is a pinned sequence of two entries, and then conditionally a third. First a `RELEASE` entry whose `days_delta` is the negation of `days_charged_provisional`, `cents_delta` zero, `memo` `COMPLETE_RELEASE`, which hands back the optimistic hold. Then a `COMMIT` entry whose `days_delta` is the positive `days_charged_final`, `cents_delta` zero, `memo` `COMPLETE_COMMIT`, which consumes the real thing. Then, only when the final pass produced overage days, an `OVERAGE_ACCRUE` entry whose `days_delta` is zero, whose `cents_delta` is the positive `overage_cents` and whose `memo` is `COMPLETE_OVERAGE`. Completion then recomputes the employee's `entitlement_days_used` and `entitlement_days_reserved` and the employer's `accrued_overage_cents_current_period`; recomputes the block's `reserved_slots`, `committed_slots` and `block_status` and bumps its `version` by 1; recomputes the provider's `completed_reservation_count`, `quality_score` and `lifetime_quality_score`; and moves `billing_status` from `NOT_BILLABLE` to `ACCRUED`.

**A no-show** moves `CONFIRMED → NO_SHOW` and may be reported by a `care_coordinator` or the owning `provider_manager`, with an optional `reason_code`; it is refused while the logical clock is still strictly before `care_start_utc` (`ERR_NO_SHOW_TOO_EARLY`). It sets `penalty_cents` to the plan's `no_show_charge_cents` as pinned at `plan_version_pinned` — the full charge, not a fraction — and appends three entries in this pinned order: a `RELEASE` of the negated `days_charged_provisional` with `memo` `NO_SHOW_RELEASE`; a `COMMIT` of the positive `days_charged_provisional` with `memo` `NO_SHOW_COMMIT`, because the capacity was held and burned even though nobody arrived; and a `NO_SHOW_CHARGE` entry with `days_delta` zero, `cents_delta` the positive `penalty_cents` and `memo` `NO_SHOW`. It recomputes the employee's `entitlement_days_used` and `entitlement_days_reserved`, recomputes `no_show_strike_count` from the number of `NO_SHOW_CHARGE` entries in the current benefit year, and recomputes `eligibility_status`, which becomes `RESTRICTED` once that strike count reaches two. It recomputes the block's `reserved_slots` and `committed_slots` and bumps the block's `version` by 1, and moves `billing_status` from `NOT_BILLABLE` to `ACCRUED`. The cascade is four levels deep — reservation to ledger to strike count to the eligibility gate on all of that employee's future intake — and a second no-show in one benefit year therefore locks the employee out of the benefit entirely.

**Cancellation** is available to a `care_coordinator`, a `benefits_admin` or the employee, requires a `cancel_reason_code`, and is permitted from `INTAKE`, `MATCHING`, `OFFERED`, `UNFULFILLED` and `CONFIRMED`. Whether it costs anything is decided by the frozen `cancellation_deadline_utc`, which was written at intake as `care_start_utc` moved earlier by the pinned plan's `cancellation_window_hours` and is never recomputed. A cancellation is late exactly when the logical clock is strictly after that deadline; cancelling at precisely the deadline instant is on time. A late cancellation *from `CONFIRMED`* sets `penalty_cents` to the plan's `no_show_charge_cents` multiplied by one half and rounded to a whole cent. In every other case — any cancellation from `INTAKE`, `MATCHING`, `OFFERED` or `UNFULFILLED`, however late, and an on-time cancellation from `CONFIRMED` — `penalty_cents` stays 0, because no capacity was ever held or the notice was adequate.

The side effects of cancelling therefore depend on the origin state. From `INTAKE`, `MATCHING` or `UNFULFILLED`, cancellation records `cancel_reason_code` and does nothing else: no ledger entry, no penalty, `billing_status` staying `NOT_BILLABLE`. From `OFFERED` it additionally expires every offer of that reservation whose `offer_status` is `PROPOSED` or `SELECTED` with `reason_code` `RESERVATION_CANCELLED` and clears `matched_provider_id` to null, still with no ledger entry, no penalty and `billing_status` at `NOT_BILLABLE` — no entitlement had been reserved before confirmation, so there is nothing to give back. From `CONFIRMED`, cancellation is the exact compensating transition for confirmation: it appends a `RELEASE` entry whose `days_delta` is the negation of `days_charged_provisional`, `cents_delta` zero and `memo` `CANCEL`; recomputes the employee's `entitlement_days_reserved`; recomputes `reserved_slots` and `block_status` on `matched_capacity_block_id` and bumps that block's `version` by 1; and keeps `matched_provider_id` and `matched_capacity_block_id` populated for audit rather than clearing them. If that cancellation was late, it further sets `penalty_cents`, appends a `LATE_CANCEL_CHARGE` entry with `days_delta` zero, `cents_delta` the positive `penalty_cents` and `memo` `LATE_CANCEL`, and moves `billing_status` from `NOT_BILLABLE` to `ACCRUED`; if it was on time, `penalty_cents` stays 0, no money entry is appended, and `billing_status` stays `NOT_BILLABLE`.

A reservation's own ledger trail is readable in the pinned replay order, filterable by `entry_type`, and so are the invoice lines that have billed it, filterable by `line_type`.

### 3.8. Quality Assurance, Provider Scoring and Network Consequences

Any of the four human-facing roles — a `care_coordinator`, a `benefits_admin`, an `employee_user` or a `network_admin` — may file an incident against a provider. The report names the `provider_id`, optionally the `reservation_id` during which the incident occurred (null for a network-level report), a `severity` of `MINOR`, `MODERATE` or `SEVERE`, a `category` of `SUPERVISION`, `FACILITY`, `MEDICAL`, `CONDUCT` or `DOCUMENTATION`, and a `narrative` of between one and 2000 characters. When a reservation is named, its `matched_provider_id` must be the same provider the report is filed against, otherwise `ERR_INCIDENT_PROVIDER_MISMATCH`. Filing stamps `reported_at` from the logical clock and `reported_by_user_id` from `X-User-ID`, sets `incident_status` to `OPEN`, `qa_action` to `NONE`, and leaves `reviewed_by` and `resolution_reason_code` null. Filing alone moves no score: the provider's `quality_score`, `lifetime_quality_score` and `substantiated_incident_count` are all untouched. Incident listings are filterable by `provider_id`, `reservation_id`, `incident_status`, `severity` and `category`.

`incident_status` runs `OPEN → UNDER_REVIEW` and then forks to one of two terminal outcomes with disjoint consequences. Taking a report under review is done by a `care_coordinator` or a `network_admin` and requires the subject provider not to be `DEPROVISIONED` (`ERR_PROVIDER_NOT_IN_NETWORK`); it records `reviewed_by` from `X-User-ID` and moves no score. Resolving the report is reserved to a `network_admin`, and the `X-User-ID` doing so may not equal the `reported_by_user_id` that filed it (`ERR_SEGREGATION_OF_DUTIES`). Reviewing a report that is not `OPEN`, or resolving one that is not `UNDER_REVIEW`, returns `ERR_INCIDENTREPORT_STATE_INVALID`; touching one already `SUBSTANTIATED` or `DISMISSED` returns `ERR_INCIDENTREPORT_TERMINAL`.

**Substantiation** carries a `qa_action` — one of `NONE`, `PROBATION`, `SUSPENSION` or `DEPROVISION` — and a `resolution_reason_code`. It records both, then recomputes the provider's `substantiated_incident_count` and both quality-score variants. Then the network consequence follows the action exactly: `PROBATION` drives the provider `CREDENTIALED → PROBATION`; `SUSPENSION` drives it from `CREDENTIALED` or `PROBATION` to `SUSPENDED` and runs the full withdrawal cascade over that provider's future confirmed care; `DEPROVISION` drives it from `CREDENTIALED` or `PROBATION` to `DEPROVISIONED` and runs the same withdrawal cascade irreversibly; and `NONE` leaves `network_status` entirely untouched, moving only the scores. The reason code the move records differs by action: a `PROBATION` action stamps `last_status_reason_code` with `INCIDENT_SUBSTANTIATED`, while a `SUSPENSION` or a `DEPROVISION` action stamps it with the `resolution_reason_code` supplied on this substantiation. A posture move the provider's current state cannot accept surfaces as `ERR_PROVIDER_STATE_INVALID`.

**Dismissal** is the disjoint sibling branch and carries only a `resolution_reason_code`, which must be non-empty. It records that reason code, leaves `qa_action` at `NONE`, leaves `network_status` entirely unchanged, and leaves `substantiated_incident_count`, `quality_score` and `lifetime_quality_score` unchanged: a dismissed report never deducts, ever.

**The two score variants.** Both are recomputed when a report is substantiated, when a provider passes credential review, on every network-posture movement, when a reservation completes, and whenever the logical clock is advanced. Both start from a baseline of 100 and are computed the same way apart from one decision. Deductions accumulate over this provider's reports whose `incident_status` is `SUBSTANTIATED` — reports that are `OPEN`, `UNDER_REVIEW` or `DISMISSED` contribute nothing at all. Each substantiated report contributes a severity weight of 4 for `MINOR`, 12 for `MODERATE` or 30 for `SEVERE`, multiplied by a decay factor. The report's age in days is the number of whole days between `reported_at` and the logical clock, that is the total seconds between them divided by 86400 and floored. For the rolling variant, the decay factor is 1.00 for an age of 30 days or fewer, 0.60 for an age above 30 but at most 60 days, 0.30 for an age above 60 but at most 90 days, and 0.00 beyond 90 days, so an incident older than a quarter stops counting. For the lifetime variant the decay factor is always 1.00 — age is ignored entirely and every substantiated incident deducts at full weight forever. A tenure bonus is then added: the provider's `completed_reservation_count` divided by five and floored, multiplied by two, capped at 10. The score is the baseline less the deductions plus the bonus, rounded to two decimal places, then clamped into the range from 0 to 100 inclusive. The rolling result is written to `quality_score` and is the only variant the matching ranker reads; the undecayed result is written to `lifetime_quality_score` and is the value the reinstatement floor and the renewal-risk analytics read. The divergence is substantial and intended: one `SEVERE` report 92 days old, one `MODERATE` 42 days old and one `MINOR` 7 days old yield 88.80 rolling and 54.00 lifetime from identical rows.

### 3.9. Employer Invoicing, Renewal Analytics and the Nightly Maintenance Sweep

**Sweeping an invoice.** A `network_admin` or `benefits_admin` opens a billing run for an employer over an inclusive `period_start` to `period_end` window of calendar dates. The requested period may not overlap any existing non-void invoice period of the same employer (`ERR_INVOICE_PERIOD_OVERLAP`). The billable set is every reservation belonging to an employee of that employer whose `billing_status` is `ACCRUED`, whose `fulfillment_status` is `COMPLETED`, `NO_SHOW` or `CANCELLED`, and whose `care_date` falls within the period inclusive of both ends. Reservations already `INVOICED` or `PAID` are excluded by that `ACCRUED` filter, and that exclusion is the whole double-billing defence. The set is processed in a deterministic order: `care_date` ascending, then `created_at` ascending.

For each reservation in that order, lines are emitted according to its fulfillment outcome. A `COMPLETED` or `NO_SHOW` reservation emits a `CARE_COPAY` line whose `quantity` is its covered billed quantity (covered days for centre-based care, covered hours for in-home) and whose `unit_cents` is the corresponding pinned copay rate, plus a `CARE_OVERAGE` line whose `quantity` is its overage billed quantity and whose `unit_cents` is the tier-multiplied overage unit rate already rounded during stage four. A `NO_SHOW` reservation additionally emits a `NO_SHOW_CHARGE` line with `quantity` 1 and `unit_cents` equal to its `penalty_cents`. A `CANCELLED` reservation emits a `LATE_CANCEL_CHARGE` line with `quantity` 1 and `unit_cents` equal to its `penalty_cents`, and only when that penalty is greater than zero. A line whose computed amount would be zero is not written at all.

Each `InvoiceLine` records the `employer_invoice_id` it belongs to, the `reservation_id` it bills, a denormalised `employee_id` copied from that reservation for per-employee grouping, its `line_type`, its `quantity`, its `unit_cents`, and an `amount_cents` that is the quantity multiplied by the unit rate and rounded to a whole cent, evaluated independently for that line. The invoice then totals: `subtotal_cents` is the sum of the already-rounded `amount_cents` of every line; `admin_fee_cents` is that integer subtotal multiplied by the employer's `admin_fee_pct` and rounded to a whole cent; `total_cents` is the subtotal plus the fee. Three reporting breakdowns follow the same per-line sums — `copay_cents` over the `CARE_COPAY` lines, `overage_cents` over the `CARE_OVERAGE` lines, and `penalty_cents` over the `NO_SHOW_CHARGE` and `LATE_CANCEL_CHARGE` lines together — alongside `line_count`, the number of lines written, and `reservation_count`, the number of distinct reservations across those lines. The sweep creates the invoice with `invoice_status` `DRAFT`, `issued_at` null, `paid_amount_cents` 0 and `void_reason_code` null, and moves every swept reservation's `billing_status` from `ACCRUED` to `INVOICED`. A period containing only zero-copay covered care therefore produces an invoice with `line_count` 0, which cannot be issued.

**Issuing, paying and voiding.** `invoice_status` runs `DRAFT`, `ISSUED`, `PAID` and `VOID`, with `PAID` and `VOID` terminal. A `network_admin` issues a `DRAFT` invoice; issuance requires at least one line, so an invoice whose `line_count` is 0 (equivalently, whose `total_cents` is 0 because the period produced no non-zero billable component) is refused with `ERR_INVOICE_EMPTY`, and it also requires that none of the reservations the invoice bills is still `IN_SERVICE`. Issuance stamps `issued_at` from the logical clock and recomputes the employer's `ytd_billed_cents`. A `network_admin` or `benefits_admin` then records payment by supplying `paid_amount_cents`, which must equal `total_cents` exactly (`ERR_PAYMENT_AMOUNT_MISMATCH`); payment records that amount, moves every billed reservation's `billing_status` from `INVOICED` to `PAID`, and recomputes `ytd_billed_cents`. Issuing something that is not `DRAFT`, or paying something that is not `ISSUED`, returns `ERR_INVOICE_STATE_INVALID`; touching an invoice already `PAID` or `VOID` returns `ERR_EMPLOYERINVOICE_TERMINAL`.

Voiding is the compensating transition for the sweep and is reserved to a `network_admin`, who supplies a `void_reason_code`. It is available from `DRAFT` and from `ISSUED` but never from `PAID` (`ERR_INVOICE_NOT_VOIDABLE`). It records the reason code, deletes every line of the invoice, zeroes `copay_cents`, `overage_cents`, `penalty_cents`, `subtotal_cents`, `admin_fee_cents`, `total_cents`, `line_count` and `reservation_count`, and returns every billed reservation's `billing_status` from `INVOICED` to `ACCRUED` so it can be swept into a corrected invoice. Voiding from `ISSUED` additionally recomputes `ytd_billed_cents`. Critically, voiding appends no ledger entry and removes none, which is exactly why the employer money-conservation invariant survives a draft-issue-void round trip. Invoice listings are filterable by `invoice_status`, and line listings by `line_type` and `employee_id`.

**Renewal analytics.** The utilization report takes the same inclusive `period_start` to `period_end` window and covers every reservation of that employer's employees whose `care_date` falls inside it, in every fulfillment state — though rows sitting in `INTAKE`, `MATCHING`, `OFFERED`, `CANCELLED` or `UNFULFILLED` contribute to none of the counters. It reports the `employer_id`, the `period_start` and `period_end` echoed back, `reservations_confirmed` as the count of in-scope reservations whose `fulfillment_status` is `CONFIRMED`, `IN_SERVICE`, `COMPLETED` or `NO_SHOW`; `reservations_completed` as the count of those that are `COMPLETED`; `no_show_count` as the count of those that are `NO_SHOW`; `days_used` as the sum of `covered_days` over the `COMPLETED` and `NO_SHOW` rows; `days_overage` as the sum of `overage_days` over the same rows; and `unique_employees_served` as the number of distinct employees among the `COMPLETED` rows. `center_share_pct` is zero when nothing completed, and otherwise one hundred multiplied by the number of completed reservations whose matched provider is `CENTER_BASED`, divided by `reservations_completed`, rounded to two decimal places; `in_home_share_pct` is zero when nothing completed, and otherwise one hundred less `center_share_pct`, rounded to two decimal places. `no_show_rate_pct` is zero when `reservations_confirmed` is zero, and otherwise one hundred multiplied by `no_show_count` divided by `reservations_confirmed`, rounded to two decimal places. `min_provider_lifetime_score` is the smallest `lifetime_quality_score` among the providers matched to the `COMPLETED` and `NO_SHOW` rows, and is null when that set is empty. `renewal_risk_band` is then assigned by testing three bands top to bottom, first match winning: it is `HIGH` when `no_show_rate_pct` has reached 25 percent or more, or when the minimum lifetime score exists and is below 70; failing that it is `MEDIUM` when `days_overage` is greater than zero or `no_show_rate_pct` has reached 10 percent or more; otherwise it is `LOW`. Employers are grouped by `industry_code` when these figures are compared across a book of business.

**The nightly maintenance sweep.** A `network_admin` runs a single sweep that advances every clock-driven transition in a pinned six-step order, where each step observes the writes of every earlier step. Step one moves every credential whose `expires_on` is strictly earlier than the current UTC date from `VALID` to `EXPIRED`. Step two suspends every provider that, after step one, no longer holds a `VALID` credential of all four required types and whose `network_status` is `CREDENTIALED` or `PROBATION`, each such suspension running its full withdrawal cascade over that provider's future confirmed reservations. Step three moves every reservation in `INTAKE`, `MATCHING` or `OFFERED` whose `care_start_utc` is earlier than the logical clock to `UNFULFILLED` with `unfulfilled_reason_code` `CARE_WINDOW_ELAPSED`; for a reservation leaving `OFFERED`, that step also expires every offer whose `offer_status` is `PROPOSED` or `SELECTED` with `reason_code` `CARE_WINDOW_ELAPSED` and clears `matched_provider_id` to null. Step four expires every offer whose `offer_status` is still `PROPOSED` or `SELECTED` after step three and whose `offer_expires_at` is earlier than the logical clock, with `reason_code` `OFFER_TTL_ELAPSED`; the step reads the offer alone and never the state of the reservation that owns it, so a `SELECTED` offer belonging to a reservation that has already been confirmed is expired here exactly like any other, while offers already `REJECTED` or `EXPIRED` are left as they are. Step five moves every capacity block whose `service_date` is earlier than the current UTC date to `block_status` `CLOSED`. Step six moves every reservation still `CONFIRMED` whose `care_end_utc` is earlier than the logical clock to `NO_SHOW`, applying exactly the same side-effect set as an operator-reported no-show: the release, the commit, the no-show charge, the strike recount and the eligibility recomputation. Two of those adjacencies are order-sensitive and reversing either pair changes the resulting row set: step one must precede step two, because a credential only lapses into expiry before the suspension test reads it, and step three must precede step four, so that offers belonging to reservations that have just gone unfulfilled are not double-processed. The sweep reports what it did through seven counters: `credentials_expired`, `providers_suspended`, `reservations_unfulfilled`, `offers_expired`, `blocks_closed`, `reservations_no_showed` and `reservations_withdrawn`.

## 4. Endpoint Definitions

Requests that mint a brand-new resource — an employer, a benefit plan, an employee, a dependent, a provider, a credential, a capacity block, a reservation, an invoice or an incident report — return `201 Created`. Every other successful request, including all state transitions, all amendments, all reads and all reports, returns `200 OK`. Authorised roles are named with the exact spellings from Section 2.1.

| ------ | ---- | ----------- | ------------------ |
