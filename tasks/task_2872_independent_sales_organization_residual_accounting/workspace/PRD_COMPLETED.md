# ISO Residual Accounting API — Product Requirements Document

## 1. Introduction

An Independent Sales Organization (ISO) in merchant services lives or dies on the accuracy of its residual accounting. Every month a processor delivers a residual file: one row per merchant, carrying the authorization count, the settled sales volume, the interchange the card networks took, the brand assessments, and the total fee income billed to the merchant. From that file the ISO must reconstruct what it actually earned, subtract its own processor buy rate, absorb chargebacks and equipment leases, and then split what remains across a multi-level sales hierarchy in which every agent earns a direct percentage on the merchants it personally boarded and a differential override on the production of everyone beneath it. Today this work is done in spreadsheets that no two people reconcile the same way, and disputes with agents routinely take longer to settle than the period they concern.

This document specifies the API for a system that replaces those spreadsheets with an auditable ledger. The system ingests processor residual files as batches, normalizes each line against the buy-rate economics of the processor program the merchant was boarded under, and posts the result to produce two deliberately divergent bottom lines per merchant: the ISO's own profit view, which absorbs every chargeback, and the narrower agent split basis, which absorbs only the chargebacks the agent is contractually charged for. Posting drives a cascade — profitability rows produce allocations, allocations attach to draft statements, statements refresh each agent's production KPI — and the same cascade must be exactly reversible, because processors reissue corrected files and the ISO must be able to un-post a period without leaving orphaned money behind.

Beyond the monthly cycle, the system carries the commercial machinery that surrounds a residual stream: cash advances and portfolio buyouts recouped against future statements under two different amortization variants, contractual monthly minimums reconciled against per-transaction fee income, upfront boarding bonuses clawed back when a merchant attrites early, portfolio vesting that determines how much of a departing agent's book keeps paying, and a review workflow for disputes and manual corrections that is bound by segregation of duties. Money leaves the building through exactly one door — statement settlement — and every guard in this specification exists to make sure the amount passing through that door can be defended line by line.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. If either header is absent — or present but empty, an empty value being treated exactly as an absent one — or if `X-User-Role` is not exactly one of the four role names below, the request is refused with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). Authentication inspects the header values alone: even when `X-User-Role` is `Agent`, the server does not verify that `X-User-ID` names an existing `Agent` row, so this check never reports a not-found error of its own. This is the very first check performed on any request, ahead of routing concerns such as whether the requested path and method are routable at all and whether the addressed resource exists — a request that carries no headers to a path this API does not define is still answered with `ERR_MISSING_AUTH_HEADERS` (HTTP 401) rather than with a 404. Once the headers are accepted, the acting role must appear in the set of roles authorized for the endpoint being called; if it does not, the response is `ERR_UNAUTHORIZED` (HTTP 403).

The four roles are:

- **`IsoAdmin`** — the ISO back-office operator. Owns all master data: processor programs, agents and the hierarchy that connects them, merchants, advances, portfolio transfers, and the logical clock. When `X-User-Role` is `IsoAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it (for example, as `created_by_user_id` or `approved_by_user_id` on a `StatementAdjustment` where a transition writes it) but never compares it to any entity's `id`.
- **`ResidualAnalyst`** — the residual operations analyst. Ingests processor files, appends and corrects lines, normalizes batches, books chargebacks, and proposes adjustments. This role never posts to the ledger and never moves money. When `X-User-Role` is `ResidualAnalyst`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity; the server may record it as `created_by_user_id` or `approved_by_user_id` but does not compare it to any entity's `id`.
- **`ResidualController`** — the residual controller, and the only role that moves money. Posts and reverses batches, issues, recalls, finalizes, holds, releases and settles statements, and adjudicates adjustments. When `X-User-Role` is `ResidualController`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; it is recorded as `created_by_user_id` when this role proposes an adjustment and as `approved_by_user_id` when it approves or rejects one, but it is never matched against any entity's `id`. Segregation of duties nonetheless makes the value load-bearing: an adjustment this user proposed may never be approved by the same user.
- **`Agent`** — a sales agent acting on its own book of business. When `X-User-Role` is `Agent`, `X-User-ID` is the `id` of the acting `Agent` row; ownership checks on any resource that references an `Agent` compare the resource's foreign-key field to `X-User-ID`. Concretely: an agent reading a single agent record may address only the record whose `id` equals `X-User-ID`; statement and allocation reads compare `AgentStatement.agent_id` and `ResidualAllocation.agent_id` to `X-User-ID`; merchant reads compare `Merchant.owning_agent_id` to `X-User-ID`; and proposing or resubmitting an adjustment requires that the `agent_id` of the statement being corrected equal `X-User-ID`.

An acting `Agent` that addresses another agent's record, portfolio summary, merchant, statement, allocation or adjustment is refused with `ERR_AGENT_SCOPE_VIOLATION` (HTTP 403). The same error is returned when an acting `Agent` performs a filtered list read without narrowing it to itself: agent list reads of statements, allocations and adjustments must carry an `agent_id` filter equal to `X-User-ID`, and merchant list reads must carry an `owning_agent_id` filter equal to `X-User-ID`. An omitted or mismatched filter is a scope violation, not an empty result. This scope check applies to exactly eleven operations: the single-agent read, the agent portfolio-summary read, the merchant list read, the single-merchant read, the statement list read, the single-statement read, the allocation list read, the single-allocation read, the adjustment list read, proposing an adjustment against a statement, and resubmitting an adjustment after an information request. Two of those eleven — the single-agent read and the agent portfolio-summary read — compare the path `{id}` to `X-User-ID` directly, and so refuse another agent's id even when that id names no row at all. The rest can only learn the owning agent by reading a resource or a filter, which pins their interaction with the existence checks as described in §2.8.

Beyond those four names, no other role exists, and no endpoint is public. The `IsoAdmin` role holds every master-data write exclusively; the `ResidualController` role holds every ledger-posting and settlement write exclusively; batch ingest, line append, normalization, recall and chargeback booking are shared between `IsoAdmin` and `ResidualAnalyst`; adjustment proposal and resubmission are open to all four roles; advance reads are shared only between `IsoAdmin` and `ResidualController`; and every other read is open to `IsoAdmin`, `ResidualAnalyst` and `ResidualController`, with `Agent` added on the self-scoped reads listed above. §4 states the authorized roles for each endpoint individually.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request: the literal prefix `req_` followed by exactly twenty characters drawn from the upper-case letters `A` through `Z` and the digits `0` through `9`, randomized afresh for every request.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.6 rather than from host wall-clock time. Every response therefore carries the same timestamp until the clock is explicitly moved, and the response that moves it already reports the new instant.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- The HTTP status of an error response is the one paired with its `error_id` in §5, with one exception on either side of routing. A request whose path this API does not define is answered with `error_id` `ERR_INVALID_REQUEST` under HTTP 404, and a request whose path exists but whose HTTP method is not defined on that path is answered with `ERR_INVALID_REQUEST` under HTTP 405 — in both cases inside this same error envelope, and in both cases only after the authentication check of §2.1 has passed. A trailing slash is accepted on every path as equivalent to the path without one. No request is ever answered with a 5xx status: an unexpected server-side failure surfaces as `ERR_INVALID_REQUEST` under HTTP 400.


### 2.3. Pagination

Every list endpoint in this API accepts two optional query parameters. `limit` controls the page size: it defaults to 10 when omitted, must be at least 1, and may not exceed 100. `offset` controls the starting position within the result set: it defaults to 0 and its minimum is 0. Both are read out of the query string and each must be written as an optionally signed run of decimal digits, with surrounding whitespace ignored; an empty, non-numeric or fractional value — `limit=`, `limit=abc`, `limit=10.0` — is refused just as an out-of-range one is. A `limit` or `offset` outside those bounds, or of the wrong JSON type, is a request-shape failure and is refused with `ERR_INVALID_REQUEST` (HTTP 400). `offset` has no upper bound: an `offset` at or beyond `total_count` is a perfectly valid read that returns an empty `data` array, `has_more` false, and the unpaginated `total_count` intact.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending — oldest row first — and rows sharing the same `created_at` are ordered by the sequence in which the server created them, earliest insertion first. That tiebreak carries the whole ordering in practice: the logical clock of §2.6 never advances on its own, so every row written between two clock moves carries an identical `created_at` and the observable order is simply creation order. This default matters well beyond cosmetics: several calculations in this system are order-sensitive, and the ascending creation order used for reads is the same order the engine walks when normalizing residual lines and when consuming the advance recoupment cap.

List responses populate the pagination fields in `meta`: `limit` (the page size actually applied), `offset` (the starting position actually applied), `total_count` (the number of rows matching the filters before pagination), and `has_more` (true when rows remain beyond the current page). Single-resource responses omit all four.

### 2.4. Resource Identity, Versioning and Audit Timestamps

Every persisted resource carries a server-minted `id`: a UUID, with no type prefix and no embedded semantics. Clients never supply an `id`; a client-supplied value in a creation payload is ignored. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written.

Most resources additionally carry `updated_at` — same format as `created_at`, refreshed on every mutation — and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row. When a rule in this document says an operation "bumps the version" of some entity, it means that entity's `version` advances by 1 and its `updated_at` is refreshed, even when the entity in question is not the one addressed in the request path. Because the logical clock does not tick on its own, `updated_at` is stamped as the current logical instant offset forward by one millisecond for every mutation already applied to that row — precisely, the clock plus `version` minus one milliseconds, evaluated after the increment. A row at `version` 1 therefore carries an `updated_at` exactly equal to its `created_at`; while the clock stays put, the first mutation moves `updated_at` one millisecond past `created_at`, the second two, and so on, so a mutated row always shows `updated_at` strictly later than `created_at` even though no clock move occurred. A refused request changes neither field.

One entity is deliberately different. A `ChargebackEvent` is an append-only accounting event: it is written once and never mutated, so it carries only `id` and `created_at`. Both `updated_at` and `version` are absent from a `ChargebackEvent` — not null, absent. There is no endpoint that amends or deletes a chargeback; a mis-booked chargeback is corrected by booking a compensating adjustment against the affected statement, not by editing the event. Every other entity in this system — the processor program, the agent, the merchant, the residual batch, the residual line, the merchant profitability row, the residual allocation, the agent statement, the statement adjustment and the agent advance — carries the full quartet of `id`, `created_at`, `updated_at` and `version`.

Version increments are the system's audit trail for derived money. A single write frequently bumps versions on several rows: posting a batch bumps the batch, reassigning a merchant bumps the merchant, approving an adjustment bumps both the adjustment and its parent statement, funding an advance bumps the agent, and a portfolio transfer bumps both agents plus every merchant that moved. Every cascade described in §3 states which rows it touches, and each touched row's `version` advances.

### 2.5. The Cent Convention, Percentages and Rounding

Every monetary quantity in this system — without exception — is an integer count of cents. There are no floating-point money fields, no currency strings, and no minor-unit ambiguity. A field name ending in `_cents` is an integer, and a field name ending in `_bps` is an integer count of basis points, where one basis point is one hundredth of one percent.

Percentages that describe entitlements are decimal fractions carried to four decimal places: a `split_pct` of `0.3500` means thirty-five percent. Four decimal places bounds the precision the server accepts and preserves in its arithmetic rather than the way a value is rendered back: `split_pct`, `override_pct`, `applied_pct` and `recoupment_pct` are supplied as JSON numbers and returned as JSON numbers in shortest exact form, so a thirty-five percent split reads back as `0.35`, never as the zero-padded `0.3500` and never as a string. Vesting is the one exception, expressed as a whole-number percentage between 0 and 100 rather than as a fraction.

Wherever a computation produces a fractional cent, the result is rounded to the nearest whole cent with halves rounded away from zero — the convention this document calls **round half up**. Two consequences of that rule are load-bearing throughout §3. First, rounding order is pinned: where a total is described as the sum of per-item results, each item is rounded to the cent first and the already-rounded values are then added. Summing the raw inputs and rounding once at the end produces different answers and is incorrect. Second, rounding remainders are never redistributed between agents. When a merchant's split basis is divided across a direct agent and several override tiers, each tier is rounded independently and whatever pennies fall out of the arithmetic land in the ISO's retained residue, never in another agent's pocket.

Basis-point results are likewise integers, rounded half up.

### 2.6. The Logical Clock

Time in this system is explicit and injectable rather than read from the host. The server maintains a logical current UTC instant, and every date-sensitive rule reads it: the vesting schedule, the boarding-bonus clawback window, the timestamp frozen when a statement is issued, the date bounds on merchant attrition and reactivation, and the departure-date bounds. The recoupment window of a new advance is the one date rule that reads no clock at all: `first_recoupment_month` is compared against the calendar month of the supplied `funded_on`, so `funded_on` itself is never bounded against the clock and an advance may legitimately be funded on a date the clock has not yet reached. At server startup the logical clock reads exactly `2026-08-01T00:00:00Z`; until it is explicitly moved, that is the instant every rule sees, and the server must never fall back to real wall-clock time.

An `IsoAdmin` may advance or rewind the clock through a dedicated test-driving capability that takes a single `current_utc` instant and returns the value now in force as `current_utc`. `current_utc` must be a string, and any ISO 8601 form the server can parse is accepted: a `Z`-suffixed UTC instant, an instant carrying a numeric UTC offset such as `+05:00` (converted to UTC before it is stored), an instant with no zone at all (read as UTC), or a bare `YYYY-MM-DD` date (read as midnight UTC on that day). Fractional seconds finer than a millisecond are accepted and truncated to three digits wherever the clock is subsequently rendered. An unparseable value is `ERR_INVALID_REQUEST` (HTTP 400) and leaves the clock where it was. The response echoes the string exactly as the client supplied it rather than a normalized rendering, while every date-sensitive rule and every `api_request_timestamp` from that point on reads the parsed UTC instant. This capability exists so that a full vesting cliff or a nine-month clawback window can be exercised without waiting for calendar time; it has no other business meaning, and no other role may call it.

Where a rule compares a date-only value (`YYYY-MM-DD`) against the clock, the comparison is made against the clock's current UTC calendar date. Where a rule compares an accounting month (`YYYY-MM`), the comparison is made on the calendar month.

### 2.7. Optimistic Concurrency on the Three Guarded Writes

Three write operations in this system make a decision whose correctness depends on the state the client last observed. Each one is guarded by optimistic concurrency control against the `version` of a **parent** entity, and each requires a non-optional version field in its request body. These three are the only endpoints in the API that take a version field; no other endpoint accepts one, and supplying one elsewhere is not part of the contract.

- `POST /agents/{id}/advances` requires `expected_agent_version`, carrying the client's last observed `version` of the addressed `Agent`. If it does not equal that agent's current `version`, the funding request is rejected with `ERR_STALE_AGENT_VERSION` (HTTP 412). Advances legitimately stack on one agent, so no state precondition blocks a second funding request — but the aggregate-exposure and recoupment-capacity decisions are made against the agent's advance set as the writer last saw it, so a stale version means that decision rested on out-of-date data.
- `POST /merchants/{id}/reassign-agent` requires `expected_merchant_version`, carrying the client's last observed `version` of the addressed `Merchant`. A mismatch against the merchant's current `version` is rejected with `ERR_STALE_MERCHANT_VERSION` (HTTP 412). Reassignment legitimately supersedes previous ownership, so a second sequential reassignment to a different agent would otherwise succeed and silently overwrite the ownership a previous writer had established.
- `POST /agent-statements/{id}/adjustments` requires `expected_statement_version`, carrying the client's last observed `version` of the addressed `AgentStatement`. A mismatch against the statement's current `version` is rejected with `ERR_STALE_STATEMENT_VERSION` (HTTP 412). Multiple adjustments legitimately coexist on one statement, so no state precondition blocks a second proposal; the guard exists because a proposed `amount_cents` is usually derived from the `net_payable_cents` the proposer read, and a newly posted batch or a newly applied adjustment has since moved that number.

In all three cases the check is a pure equality test against the parent's current `version` at the moment the write is evaluated, and it sits at priority band 8 — after the addressed resource has been confirmed to exist and after body-referenced foreign keys have been resolved, but before any state precondition or business rule is consulted.

### 2.8. The Order in Which a Request Is Refused

Many requests in this system violate more than one rule at once, and which error the caller sees is part of the contract rather than an implementation detail. Checks are evaluated in thirteen ordered bands; the first band that produces a failure determines the response, and no later band is consulted.

1. **Authentication.** Both headers present, and `X-User-Role` one of the four declared roles — otherwise `ERR_MISSING_AUTH_HEADERS` (401).
2. **Authorization.** The acting role is authorized for the endpoint — otherwise `ERR_UNAUTHORIZED` (403).
3. **Actor scope.** An acting `Agent` is confined to its own book of business — otherwise `ERR_AGENT_SCOPE_VIOLATION` (403). This band strictly precedes band 6 only for the two checks that read the acting agent's identity straight off the path, the single-agent read and the portfolio-summary read, and for the four list reads whose mandatory self-narrowing filter is missing or mismatched. The remaining single-resource ownership checks must read the addressed row before they can learn its owning agent, so on those a path id that names no row is answered from band 6 with that entity's not-found error rather than from here. For the same reason, proposing or resubmitting an adjustment is scope-checked only when the statement it hangs off actually exists: against a statement or adjustment id that names nothing, such a request falls through to band 4 and reports the first request-shape failure of its body, and reports `ERR_STATEMENT_NOT_FOUND` or `ERR_ADJUSTMENT_NOT_FOUND` from band 6 once the body is well formed.
4. **Request shape.** Every required input field is present, every value has the declared JSON type, every enum-typed field carries a value drawn from that field's declared set, integer cent fields are integers, and the fields that must be non-negative are non-negative: `principal_cents`, `monthly_minimum_cents`, `per_transaction_fee_cents`, `equipment_lease_monthly_cents`, `upfront_bonus_cents`, `transaction_count`, `sales_volume_cents`, `interchange_cents`, `assessments_cents`, `gross_income_cents`, and the `amount_cents` of a chargeback. Any failure here yields `ERR_INVALID_REQUEST` (400). This band applies to every write endpoint. Every write endpoint reads its input from a JSON object body, and the surrounding conventions are pinned as follows. `Content-Type` is not enforced; a body that is absent, empty or unparseable is treated as an empty object, so what gets reported is the first required field the endpoint declares; and a body that parses to something other than an object — an array or a bare scalar — is refused here directly. A field supplied as an explicit `null` is treated exactly as if it had been omitted, so a required field reports its missing-field failure and an optional one falls back to its documented default. Three optional fields are deliberate exceptions to that convention, because the endpoints that own them distinguish a supplied `null` from an absent key: `parent_agent_id` on an agent amendment, and `recoupment_pct` and `amortization_months` on an advance restructure. In each of those three an explicit `null` clears the stored value — detaching the agent to the top of the hierarchy, or dropping the advance's percentage or its amortization term — while omitting the key leaves the stored value in place. Fields the endpoint does not declare are ignored rather than refused, which is also how a client-supplied `id` is discarded. Integer fields accept only JSON integers: a boolean and an integral float such as `25.0` are both refused. The decimal percentage fields accept any JSON number but never a numeric string such as `"0.35"`. Date-only fields must be `YYYY-MM-DD` strings naming a day that exists, so `2026-02-30` fails here rather than later.
5. **Field domains.** Two checks share this band. `split_pct`, `override_pct` and `recoupment_pct` must be decimal fractions inside the closed interval from 0 through 1 inclusive; a value outside that interval yields `ERR_INVALID_PCT_RANGE` (422) on agent creation, agent amendment and advance funding. Separately, every accounting-month input must match the exact four-digit-year, hyphen, two-digit-month shape with the month between 01 and 12 inclusive; a malformed value yields `ERR_INVALID_PERIOD_MONTH` (422) on batch ingest, on chargeback booking, and on the `first_recoupment_month` and `last_recoupment_month` of an advance at funding time. An advance restructure is the single exception: the `last_recoupment_month` it carries back is shape-checked in band 4 and reports `ERR_INVALID_REQUEST` (400) instead. Only a value that is already a string reaches this band: an accounting month supplied as a number or any other JSON type is caught in band 4 as `ERR_INVALID_REQUEST` instead, so the two failures are distinguishable by type versus shape.
6. **Existence of path resources**, resolved left to right along the URL. A path segment that names no row produces that entity's not-found error: `ERR_PROGRAM_NOT_FOUND`, `ERR_AGENT_NOT_FOUND`, `ERR_ADVANCE_NOT_FOUND`, `ERR_MERCHANT_NOT_FOUND`, `ERR_CHARGEBACK_NOT_FOUND`, `ERR_BATCH_NOT_FOUND`, `ERR_LINE_NOT_FOUND`, `ERR_PROFITABILITY_NOT_FOUND`, `ERR_ALLOCATION_NOT_FOUND`, `ERR_STATEMENT_NOT_FOUND` or `ERR_ADJUSTMENT_NOT_FOUND` — all HTTP 404.
7. **Existence of body-referenced foreign keys**, resolved in the order the fields are declared for the endpoint. An agent reference that names no agent — `parent_agent_id` on agent creation or amendment, `owning_agent_id` on merchant boarding, `new_agent_id` on reassignment, `target_agent_id` on portfolio transfer — yields `ERR_REFERENCED_AGENT_NOT_FOUND` (404). A `processor_program_id` that names no program, whether on merchant boarding or on batch ingest, yields `ERR_REFERENCED_PROGRAM_NOT_FOUND` (404). A merchant reference that names no merchant — `merchant_id` on a residual line, `source_merchant_id` on an adjustment proposal — yields `ERR_REFERENCED_MERCHANT_NOT_FOUND` (404).
8. **Optimistic concurrency**, as specified in §2.7.
9. **State preconditions** on the addressed resource, yielding `ERR_BATCH_STATE_INVALID`, `ERR_STATEMENT_STATE_INVALID`, `ERR_SETTLEMENT_STATE_INVALID`, `ERR_ADJUSTMENT_STATE_INVALID`, `ERR_MERCHANT_STATE_INVALID`, `ERR_AGENT_STATE_INVALID` or `ERR_ADVANCE_STATE_INVALID` — all HTTP 409.
10. **Business safety** — segregation of duties (`ERR_SEGREGATION_OF_DUTIES`) and the portfolio risk hold (`ERR_RESIDUAL_HOLD_ACTIVE`), both HTTP 409.
11. **Business temporal** — coverage windows, coverage overlap, period locks, recoupment windows, merchant lifecycle dates and departure dates.
12. **Business constraint** — program suspension, uniqueness, hierarchy shape, cross-entity readiness and override monotonicity.
13. **Business fiscal** — money ceilings, aggregate exposure, the payout floor and adjustment sign discipline.

Two orderings inside this scheme deserve to be called out because they are easy to get backwards. Approving an adjustment that is still `PROPOSED` as its own creator reports `ERR_ADJUSTMENT_STATE_INVALID` from band 9, not the segregation-of-duties error from band 10 — the state check wins. And restructuring an advance whose `state` is `RECOUPED` reports `ERR_ADVANCE_STATE_INVALID` from band 9 even when the patch would also leave the advance without the field its `recoupment_mode` requires; only an `ACTIVE` advance ever reaches that shape check, which itself sits at band 9 immediately after the state check and reports `ERR_INVALID_REQUEST` (400).

### 2.9. Derived Totals, Cascades and Compensating Reversals

A large fraction of the fields in this system are derived rather than supplied, and the specification treats a derived field as wrong the instant one of its inputs changes. Every operation that changes an input therefore recomputes the dependent rows in a stated order, and every operation that can be undone specifies its compensation explicitly.

Two invariants govern the reversible operations, and both are testable at any moment. First, **residual distribution is conserved**: after a posted batch is reversed, every statement that batch had touched shows exactly the `gross_after_trueup_cents` it showed before the post. Second, **advance principal is conserved**: for every advance, `principal_cents` always equals `outstanding_cents` plus `cumulative_recouped_cents` — before an issue, after an issue and after a recall. A third holds for the boarding bonus: after a merchant has been attrited and then reactivated, that merchant's `clawed_back_bonus_cents` is back to 0 and its owning agent's `lifetime_clawback_cents` is back to the value it held before the attrition.

Cascades propagate strictly downstream and never loop. A merchant profitability row depends on a residual line and the chargebacks of its period; an allocation depends on a profitability row and the hierarchy as it stood at post time; a statement's money lines depend on its own allocations and applied adjustments; and an agent's production and exposure KPIs depend on its statements, merchants and advances. Where an operation touches several levels, §3 names the levels in order, and the recomputation follows that order.

### 2.10. Nested Paths and Reverse-Reachability Reads

The resource model is deliberately flat: every collection is a top-level peer joined to its neighbours by explicit foreign keys, and no business entity is nested inside another entity's URL. The only multi-segment paths in this API are action sub-paths on a single addressed resource and two sub-resource creation paths — appending a residual line to a batch, booking a chargeback against a merchant, funding an advance for an agent, and proposing an adjustment against a statement. Where such a path exists, its segments are validated left to right, and the parent named by the first `{id}` must resolve before any foreign key carried in the body is resolved: appending a line to a batch that does not exist reports `ERR_BATCH_NOT_FOUND` even when the body's `merchant_id` is also unknown. The request-shape band still precedes both, exactly as §2.8 orders them — a body missing a required field, or carrying one of the wrong JSON type, reports `ERR_INVALID_REQUEST` even when the parent named in the path does not exist either.

Because nothing is nested, every "children of X" question is answered by a filter on the flat collection instead of a nested URL. Agents are filtered by `parent_agent_id` to walk the hierarchy downward; merchants by `owning_agent_id` and by `processor_program_id`; chargebacks by `merchant_id`; batches by `processor_program_id`; residual lines by `residual_batch_id` and `merchant_id`; profitability rows by `merchant_id` and `residual_batch_id`; allocations by `agent_id`, `merchant_id` and `statement_id`; statements by `agent_id`; adjustments by `statement_id`, by `source_merchant_id` and by `agent_id`; and advances by `agent_id`. That last one is the only filter in this API that is not a comparison against a column of the filtered row: an adjustment carries no `agent_id` of its own, so `agent_id` on the adjustment collection is resolved through the parent statement — the server collects the ids of the statements whose `agent_id` equals the supplied value and keeps the adjustments whose `statement_id` falls in that set. It is available to every role that may read the collection, it is the filter an acting `Agent` must supply to satisfy §2.1, an `agent_id` that names no agent (or an agent with no statements) simply matches nothing and returns an empty array, and it narrows conjunctively with `statement_id`, `source_merchant_id`, `kind` and `state` exactly like any other filter. Most collections additionally accept the enumerated filters named in §4 — `status`, `state`, `period_month`, `liability`, `allocation_type`, `lifecycle_state`, `settlement_state`, `kind` and `recoupment_mode` — each matching the exact enum value supplied. Every filter, foreign-key or enumerated, is applied as an exact case-sensitive string comparison against the stored value, and filters supplied together combine conjunctively. A filter value that matches nothing — including an enum value in the wrong case, such as `status=active` — is a successful read that returns an empty `data` array and a `total_count` of 0, never a validation error; a row whose filtered field is null matches no supplied value at all; and a query parameter the endpoint does not recognize is ignored rather than refused. Filtering is applied before pagination, so `total_count` counts the filtered rows and the default `created_at` ordering of §2.3 is applied to the filtered set.

## 3. Business Logic & Workflows

### 3.1. Processor Programs: Where the Economics Are Fixed

Everything downstream of the processor file is priced by a **processor program** — the configuration record that captures what one processor charges the ISO and how the ISO chooses to present that cost to its agents. An `IsoAdmin` registers a program with a human label in `name` (between 1 and 120 characters), a buy rate in basis points as `buy_rate_bps` (an integer from 0 through 500 inclusive, so no program may be configured above five percent of volume), a per-authorization buy rate in whole cents as `buy_rate_per_item_cents` (zero or greater), and the card-brand assessment rate `assessment_bps` (an integer from 0 through 100 inclusive). Both basis-point ceilings are enforced in band 4 alongside the type checks, so a `buy_rate_bps` of 501 or an `assessment_bps` of 101 is `ERR_INVALID_REQUEST` (HTTP 400) rather than any field-domain error. The assessment rate is recorded for audit only; the authoritative assessment deduction on any given month is the `assessments_cents` figure the processor states on each file line, never a rate re-applied to volume.

Two enumerated switches on the program change the arithmetic for every merchant boarded under it. `normalization_mode` is required at registration and is either `NET_REVENUE_SPLIT` or `GROSS_SPLIT`; it selects which of the two buy-rate normalization variants applies to each residual line, and it cannot be amended afterwards. `minimum_billing_mode` is optional at registration, defaults to `SHORTFALL_BILLED` when omitted, and is either `SHORTFALL_BILLED` — the ISO bills monthly-minimum shortfalls and shares them with the direct agent — or `NO_MINIMUM`, which forces every shortfall on that program's merchants to zero.

A newly registered program begins with `status` set to `ACTIVE` and `posted_batch_count` at 0, the latter being simply the number of that program's residual batches whose `state` is `POSTED`. It rises by one each time one of the program's batches is posted and falls by one each time a posted batch is reversed. An `IsoAdmin` may amend `name`, `buy_rate_bps`, `buy_rate_per_item_cents`, `assessment_bps` and `minimum_billing_mode` at any time; amendments are never retroactive, and residual lines that were already normalized keep the values computed at their normalization instant. The amendment has no state precondition, so a `SUSPENDED` program may still be re-priced. `normalization_mode` is simply not a declared input here: a payload that carries one is ignored under the undeclared-field rule of §2.8 band 4 rather than refused, which is how "cannot be amended afterwards" is enforced. Every accepted amendment bumps the program's `version` by exactly one, including an amendment whose payload names no amendable field at all and one that repeats the values already stored — the bump records the write, not a diff.

Suspension is the program's kill switch. Moving a program from `ACTIVE` to `SUSPENDED` stops four operations dead: ingesting a new batch for that program, appending a line to one of its batches, normalizing one of its batches, and posting one of its batches. All four are refused with `ERR_PROGRAM_SUSPENDED` (HTTP 409), and — this is the point of the switch — the refusal applies even to batches that were ingested before the suspension. Reinstatement returns `status` to `ACTIVE` and all four operations become available again. Neither switch carries a state precondition: suspending a program that is already `SUSPENDED` and reinstating one that is already `ACTIVE` are both accepted as self-loops that leave `status` where it stands and still bump the program's `version` by one. Note the asymmetry: recalling a normalized batch back to `RECEIVED` and reversing a posted batch are *not* blocked by suspension, so an operator can always unwind work on a program that has been switched off.

### 3.2. The Agent Hierarchy and Its Override Entitlements

Agents form a self-referential tree. Each agent has a display `name` (1 to 120 characters), a `parent_agent_id` naming the agent immediately above it — null for a top-level principal, and null by default when the field is omitted at creation — a `split_pct`, an `override_pct`, and a `vesting_start_date` given as a date-only `YYYY-MM-DD` value that anchors the portfolio vesting schedule. `split_pct` is the share of a directly owned merchant's split basis that this agent is paid; `override_pct` is the *cumulative-to-this-tier* share used for the differential override arithmetic on downline production. Both are decimal fractions carried to four decimal places, and both must lie in the closed interval from `0.0000` through `1.0000`; a value outside it is `ERR_INVALID_PCT_RANGE`.

A new agent is created with `status` set to `ACTIVE`, `departure_effective_date` and `vested_pct_at_departure` both null, `residual_hold` false, `portfolio_attrition_bps` at 0, `vested_pct` evaluated immediately against the vesting schedule and the logical clock, and every money counter — `lifetime_clawback_cents`, `trailing_residual_cents`, `advance_outstanding_cents` — at 0, alongside `portfolio_merchant_count` at 0. Its `hierarchy_depth` is 0 when no parent was named, and otherwise one greater than the parent's `hierarchy_depth`.

Three shape rules police the tree, and all three are enforced both when an agent is created and when an existing agent is amended or re-parented. A `parent_agent_id` that names no agent is `ERR_REFERENCED_AGENT_NOT_FOUND`; a `parent_agent_id` naming an agent whose `status` is not `ACTIVE` is `ERR_AGENT_STATE_INVALID`. A `parent_agent_id` that is the agent itself, or any agent reachable by following `parent_agent_id` upward from the agent — equivalently, any of the agent's own descendants — is `ERR_HIERARCHY_CYCLE` (HTTP 422). And the resulting `hierarchy_depth` of the agent, plus that of every one of its descendants after a re-parent, may not exceed 4; a write that would push any of them past that depth is `ERR_HIERARCHY_DEPTH_EXCEEDED` (HTTP 422). Because a top-level principal sits at depth 0, four is the deepest level a tree may reach, giving five tiers in total. The three rules that share band 12 are evaluated in a fixed order — the cycle check first, then the depth check, then override monotonicity — so a re-parent under one of the agent's own descendants that would also breach the depth limit reports `ERR_HIERARCHY_CYCLE`. The two percentage-domain checks of band 5 are ordered too: `split_pct` is validated before `override_pct`, so a write in which both fall outside the closed interval reports the `split_pct` failure.

The third rule is **override monotonicity**, and it is the constraint that makes the differential override walk meaningful. For every parent-child edge the write creates or moves, the parent's `override_pct` must be greater than or equal to the larger of the child's `split_pct` and the child's `override_pct`. An upline tier can never be entitled to a smaller cumulative share than the tier beneath it, because the differential walk would then pay that tier nothing at all. A violation is `ERR_OVERRIDE_PCT_NOT_MONOTONIC` (HTTP 422). Both directions of the constraint are re-tested on every amendment, whether or not an edge moved: an amendment that changes only `split_pct` or `override_pct` is still validated upward against the agent's existing parent edge and downward against every one of its child edges, so raising an agent's `split_pct` above its unchanged parent's `override_pct` is a violation, and so is lowering an agent's `override_pct` below what one of its children already carries. When the amendment does re-parent, the edge tested upward is the new parent's; when it re-parents to no parent at all there is no upward edge left to test, only the child edges.

An `IsoAdmin` may amend `name`, `split_pct`, `override_pct`, `vesting_start_date` and `parent_agent_id` on an existing agent. Amendment is never retroactive: existing allocation rows keep the percentages that were in force when they were written. A re-parent recomputes `hierarchy_depth` for the agent and for every descendant, and any amendment refreshes `vested_pct` from the vesting schedule. Three details of the amendment are pinned. `parent_agent_id` is the one field on this endpoint where an explicit `null` is not the same as an absent key: supplying `null` detaches the agent to the top of the hierarchy and resets its `hierarchy_depth` to 0, while omitting the key leaves the existing parent in place. The descendant depth recomputation is silent — the agent named in the path has its own `version` bumped once, but the descendants whose `hierarchy_depth` was rewritten keep the `version` and `updated_at` they already had. And an amendment that supplies no amendable field at all, or only values identical to the stored ones, still bumps the addressed agent's `version` by one.

Alongside the plain agent read, the system exposes a computed portfolio snapshot for one agent, derived on the fly rather than stored. It reports the agent's own `agent_id` together with `portfolio_merchant_count`, `active_merchant_count`, `attrited_merchant_count`, `portfolio_attrition_bps`, `residual_hold`, `vested_pct`, `trailing_residual_cents`, `advance_outstanding_cents` and `lifetime_clawback_cents`. Those ten fields are the entirety of the snapshot: being computed rather than stored, it carries no `id`, no `created_at`, no `updated_at` and no `version`. The two count breakdowns are exactly what their names say — the number of the agent's merchants whose `status` is `ACTIVE`, and the number whose `status` is `ATTRITED` — while `portfolio_merchant_count` is the broader count of the agent's merchants in any of `PENDING`, `ACTIVE` or `ATTRITED`. An acting `Agent` may request this snapshot only for itself.

### 3.3. Boarding a Merchant, Losing It, and Getting It Back

A merchant enters the system when an `IsoAdmin` boards it. The payload names the `owning_agent_id` that will receive the direct split, the `processor_program_id` that fixes the buy rate and normalization variant, and the processor's own merchant identifier as `mid` — between 4 and 32 characters, and unique across every merchant row regardless of status. A `mid` already in use is refused with `ERR_DUPLICATE_MID` (HTTP 409). The commercial terms follow: `monthly_minimum_cents` is the contractual monthly minimum the ISO bills, `per_transaction_fee_cents` is the ISO's per-transaction fee used when that minimum is reconciled, and `equipment_lease_monthly_cents` is the monthly lease cost charged against the merchant's profitability. All three are zero or greater. `boarded_on` is the date-only boarding date and doubles as the origin of the clawback window. `upfront_bonus_cents` — the boarding bonus already paid to the owning agent — is optional and defaults to 0 when omitted; it too must be zero or greater. A merchant may only be boarded under an agent whose `status` is `ACTIVE`; otherwise `ERR_AGENT_STATE_INVALID`.

Boarding leaves the merchant with `status` `PENDING`, `attrition_date` and `reactivation_date` both null, and `clawed_back_bonus_cents` at 0, and it raises the owning agent's `portfolio_merchant_count` by one. Fee terms may later be amended — `monthly_minimum_cents`, `per_transaction_fee_cents` and `equipment_lease_monthly_cents` are all patchable — but amendments bind future periods only; profitability rows already posted are untouched. That amendment carries no state precondition of its own: a `PENDING`, an `ACTIVE` and an `ATTRITED` merchant may all be re-priced, and the owning agent's status is not consulted. It bumps the merchant's `version` once even when the payload names nothing amendable or repeats the stored values.

Activation moves a merchant from `PENDING` to `ACTIVE` and is what makes it eligible for monthly-minimum reconciliation. It is refused with `ERR_MERCHANT_STATE_INVALID` from any other status, and refused with `ERR_AGENT_STATE_INVALID` when the owning agent is no longer `ACTIVE`. Both refusals sit in band 9 and are ordered — the addressed merchant's own status first, the referenced owning agent's second — so an already-`ACTIVE` merchant whose owning agent has since departed reports `ERR_MERCHANT_STATE_INVALID`. Activation also re-evaluates the owning agent's attrition rate and hold flag, because the denominator of that rate has just changed.

**Portfolio attrition rate.** An agent's `portfolio_attrition_bps` is recomputed whenever any of its merchants changes status — activation, attrition or reactivation — whenever a merchant is reassigned into or out of its book, and whenever a departed agent's portfolio is transferred. The denominator is the number of merchants owned by that agent whose `status` is either `ACTIVE` or `ATTRITED`; merchants still `PENDING` are excluded from both the numerator and the denominator, which is precisely where this figure diverges from `portfolio_merchant_count`. When the denominator is zero the rate is 0. Otherwise the numerator is the number of that agent's merchants whose `status` is `ATTRITED`, and the rate is ten thousand multiplied by the numerator, divided by the denominator, rounded half up to a whole basis point. The agent's `residual_hold` flag is then set to true exactly when that rate is greater than or equal to 2,500 basis points — a quarter of the qualifying book — and false otherwise. The comparison is inclusive: an agent with four qualifying merchants of which exactly one has attrited stands at exactly 2,500 basis points and is held.

**Attriting a merchant.** Closing a merchant moves it from `ACTIVE` to `ATTRITED` and takes an `attrition_date` in the payload. That date must be on or after the merchant's `boarded_on` and no later than the logical clock's current date; a date outside those bounds is `ERR_MERCHANT_DATE_OUT_OF_RANGE` (HTTP 422). The date is written to `attrition_date` and `reactivation_date` is cleared. Attrition places no precondition on the owning agent's status, unlike activation and reactivation: a merchant whose owning agent is in `DEPARTURE_NOTICE` or already `DEPARTED` may still be closed. The operation then fans out along two branches, and they run in the order given below — the clawback first, the risk hold second. That order is observable: a statement the clawback branch has just brought into existence is itself a `DRAFT`, `UNSETTLED` statement of that agent, so the second branch sweeps it into `HELD` in the same request.

The first branch is the **boarding-bonus clawback**. Count the whole days from `boarded_on` to `attrition_date`. If that count is greater than or equal to 270 — a nine-month retention window — nothing is clawed back and the amount is zero. Otherwise the clawback is `upfront_bonus_cents` multiplied by the number of days remaining in the window (270 minus the days the merchant was active), divided by 270, rounded half up to the cent. The boundary excludes clawback exactly at the window edge: a merchant active for precisely 270 days owes nothing, while one active for 269 days owes the bonus divided by 270, rounded half up. Reactivation never reopens the window — a later attrition recomputes from the same original `boarded_on`. When the clawback is greater than zero, the system upserts the owning agent's statement for the calendar month of `attrition_date`, creating it in `DRAFT` and `UNSETTLED` when no statement for that agent and month exists, and creates an adjustment on it of `kind` `BONUS_CLAWBACK` in `state` `APPLIED`, with `created_by_user_id` set to the literal `system`, `source_merchant_id` pointing at this merchant, and `amount_cents` equal to the negative of the clawback. That applied adjustment then cascades: the statement's `adjustment_cents`, `net_payable_cents` and `carry_forward_deficit_cents` are recomputed, and that recompute in turn refreshes the agent's `lifetime_clawback_cents` and `trailing_residual_cents` and the merchant's `clawed_back_bonus_cents`.

The second branch is the **attrition risk hold**. The owning agent's `portfolio_attrition_bps` is recomputed as described above. When the result reaches 2,500 basis points the agent's `residual_hold` flips to true, and every statement of that agent whose `lifecycle_state` is `DRAFT` or `ISSUED` and whose `settlement_state` is `UNSETTLED` is moved along the settlement dimension from `UNSETTLED` to `HELD`, with `hold_reason` recorded as `PORTFOLIO_ATTRITION_THRESHOLD`. Statements already `SETTLED`, and statements already `HELD`, are left alone. The merchant's own `version` is bumped by the attrition, and the cascade's version bookkeeping is one bump per row per write, never two. A statement that already existed advances its `version` exactly once however many of the two branches reach it: a statement that receives the bonus-clawback adjustment **and** is then moved to `HELD` by the risk hold ends the request one version higher than it started, not two. A statement the clawback branch itself created is not bumped at all — it stays at `version` 1 with `updated_at` equal to `created_at` even though the hold branch then writes `HELD` and `PORTFOLIO_ATTRITION_THRESHOLD` onto it — because its creation and every later write of this same request are one write. Every other statement the hold sweeps up, having been touched by nothing else in the request, is bumped exactly once. The adjustment row the clawback creates is written once at `version` 1 and never bumped.

**Reactivating a merchant.** An `ATTRITED` merchant may be reopened, moving it back to `ACTIVE`. The payload carries a `reactivation_date` that must be on or after the merchant's `attrition_date` and no later than the logical clock's current date; otherwise `ERR_MERCHANT_DATE_OUT_OF_RANGE`. The owning agent must still be `ACTIVE`, or the request is `ERR_AGENT_STATE_INVALID`. Reactivation is a compensating transition: when the merchant's `clawed_back_bonus_cents` is greater than zero, the system creates an adjustment of `kind` `CLAWBACK_REVERSAL` in `state` `APPLIED` with `created_by_user_id` set to `system`, `source_merchant_id` pointing at this merchant, and `amount_cents` equal to the positive of `clawed_back_bonus_cents`, placing it on the owning agent's statement for the calendar month of `reactivation_date` and upserting that statement as `DRAFT` and `UNSETTLED` if it does not yet exist. That statement is then recomputed, the agent's `lifetime_clawback_cents` is refreshed downward, and the merchant's `clawed_back_bonus_cents` returns to 0. `reactivation_date` is written and `attrition_date` is cleared. Finally the owning agent's `portfolio_attrition_bps` is recomputed, and when it falls back below 2,500 basis points `residual_hold` flips to false — but statements that were already moved to `HELD` stay `HELD` until they are explicitly released. The precondition order is pinned: the addressed merchant's own status first, then the owning agent's, and only then the date bounds, so reactivating a merchant that is not `ATTRITED` reports `ERR_MERCHANT_STATE_INVALID` even when the owning agent has also departed and the supplied date is out of range. Reactivation runs no hold cascade of its own — it neither holds nor releases any statement — and its reversal branch follows the same version bookkeeping as the clawback: a statement that already existed is bumped exactly once, while a statement the reversal itself creates stays at `version` 1.

**Reassigning ownership.** A merchant may be moved to a different agent, naming the destination as `new_agent_id`. The destination agent must exist — a `new_agent_id` naming no agent is `ERR_REFERENCED_AGENT_NOT_FOUND` from band 7 — and must have `status` `ACTIVE`, otherwise `ERR_AGENT_STATE_INVALID`; the merchant itself must not be `ATTRITED`, otherwise `ERR_MERCHANT_STATE_INVALID`. Those two state checks share band 9 and here, uniquely among the merchant transitions, the *referenced* agent is evaluated before the addressed merchant: reassigning an `ATTRITED` merchant to a departed agent reports `ERR_AGENT_STATE_INVALID`. Naming the merchant's current owner as `new_agent_id` is not an error — the self-reassignment succeeds and bumps the merchant's `version` like any other. This is one of the three optimistically guarded writes, so the payload must also carry `expected_merchant_version` matching the merchant's current `version`. On success, `owning_agent_id` becomes the new agent, `portfolio_merchant_count` falls by one on the previous owner and rises by one on the new owner, and `portfolio_attrition_bps` — with `residual_hold` alongside it — is recomputed for both agents.

**Chargebacks.** A chargeback is booked against a merchant by an `IsoAdmin` or a `ResidualAnalyst` as an immutable event carrying `amount_cents` (strictly greater than zero), the date-only `occurred_on` on which it was received, the `period_month` it is charged against, and a `liability` of either `AGENT_CHARGED` or `ISO_ABSORBED`. The strict positivity of `amount_cents` is enforced in band 4 alongside its type, so a zero or negative amount is `ERR_INVALID_REQUEST` (HTTP 400) rather than any fiscal error, and it is reported before the `period_month` shape check of band 5. Booking carries no state precondition at all: a chargeback may be booked against a `PENDING`, an `ACTIVE` or an `ATTRITED` merchant alike, and the owning agent's status is never consulted. The distinction is the whole point: an `AGENT_CHARGED` chargeback reduces the agent's split basis as well as ISO profit, while an `ISO_ABSORBED` chargeback reduces ISO profit only and leaves the agent whole. Booking a chargeback moves no money by itself — the event enters the ledger only when a batch for the same `period_month` is posted, and it is matched by exact equality on `period_month`, so an event booked to a different period never enters no matter when it actually occurred.

### 3.4. Ingesting a Processor File and Normalizing the Buy Rate

A residual batch is one processor file, for one program, for one accounting month. An `IsoAdmin` or a `ResidualAnalyst` ingests the file header first, naming the `processor_program_id` it belongs to, the `period_month` in `YYYY-MM` form that every derived row will be keyed on, a `coverage_start` and a `coverage_end` delimiting the days the file covers, and the processor's `file_checksum` (between 8 and 80 characters). The batch is created with `state` `RECEIVED`, `line_count` and `recall_count` at 0, `posted_at` null, and `gross_volume_cents`, `total_normalized_net_revenue_cents` and `iso_retained_cents` all at 0.

The coverage window is half-open: `coverage_start` is the inclusive first day covered and `coverage_end` is the exclusive end. Three shape conditions apply together, and any failure is `ERR_COVERAGE_WINDOW_INVALID` (HTTP 422): `coverage_end` must be strictly later than `coverage_start`; `coverage_start` must fall inside the accounting month, meaning on or after its first day and strictly before the first day of the following month; and `coverage_end` may be no later than the first day of the second month after `period_month`, so a file may spill at most one month past the period it reports. Beyond its own shape, the window must not collide with another file: the half-open day interval from `coverage_start` up to but excluding `coverage_end` may not overlap the interval of any existing batch of the same program whose `state` is anything other than `REVERSED`. An overlap is `ERR_COVERAGE_OVERLAP` (HTTP 409). Touching intervals do not overlap — an existing window that ends on 10 August and a new window that starts on 10 August are both accepted, because the earlier window excludes its end day.

`file_checksum` is unique across all batches whose `state` is not `REVERSED`; a repeat is `ERR_DUPLICATE_FILE_CHECKSUM` (HTTP 409). Reversal deliberately releases the checksum, so when a processor reissues a corrected file the ISO can reverse the bad batch and re-ingest the corrected one under the same checksum. Ingest is also refused with `ERR_PROGRAM_SUSPENDED` when the named program is `SUSPENDED`, and with `ERR_REFERENCED_PROGRAM_NOT_FOUND` when the `processor_program_id` names nothing. Suspension and the checksum share band 12 and are ordered within it: when the named program is suspended and the supplied `file_checksum` is also already in use, `ERR_PROGRAM_SUSPENDED` is the error reported.

Lines are appended one merchant at a time, and only while the batch is `RECEIVED`; an append against a batch in any other state is `ERR_BATCH_STATE_INVALID` (HTTP 409). Each line records the `merchant_id` it reports on together with the five figures the processor states: `transaction_count`, `sales_volume_cents`, `interchange_cents`, `assessments_cents` and `gross_income_cents`, each of them zero or greater. The line's `residual_batch_id` is taken from the batch being appended to. A processor file states each merchant once per period, so at most one line may exist for a given batch and merchant pair; a second attempt is `ERR_DUPLICATE_LINE_FOR_MERCHANT` (HTTP 409). The merchant must also be boarded on the same program as the batch — its `processor_program_id` must equal the batch's `processor_program_id` — and a mismatch is `ERR_LINE_PROGRAM_MISMATCH` (HTTP 422). Those two conditions share band 12 with the suspension check, and the three are evaluated in a fixed order — program suspension first, then the duplicate-line check, then the program-mismatch check — so a suspended program is reported ahead of a duplicate line, and a duplicate line ahead of a program mismatch. A line may be appended for a merchant in any status whatsoever, including `PENDING` and `ATTRITED`; the processor reports what it settled, and status filtering happens later in the pipeline. Appending raises the batch's `line_count` by one and bumps the batch's `version`; the line's own normalization outputs are not yet computed, so `processor_cost_cents` and `normalized_net_revenue_cents` sit at 0 and `normalization_mode_applied` is null.

**Normalization** moves the batch from `RECEIVED` to `NORMALIZED` and is where the program's economics are applied. It is refused with `ERR_BATCH_STATE_INVALID` from any other state and with `ERR_PROGRAM_SUSPENDED` when the governing program is not `ACTIVE`. Every line whose `residual_batch_id` is this batch is processed, in ascending `created_at` order, regardless of the referenced merchant's status; lines belonging to other batches are never touched.

For each line, the processor cost is computed in two terms and the volume term is rounded on its own. Take the line's `sales_volume_cents`, multiply by the program's `buy_rate_bps`, divide by ten thousand, and round that product half up to a whole cent; then add the program's `buy_rate_per_item_cents` multiplied by the line's `transaction_count`. The sum is written to `processor_cost_cents`. The rounding order here is pinned and consequential: the volume term is rounded per line, before the per-item term is added and before any batch-level summation. Adding up all the merchants' sales volumes first and applying the buy rate once to the grand total gives a different answer and is wrong.

The line's net revenue then depends on which variant the program declares, and the two variants differ by exactly the processor cost:

- Under `NET_REVENUE_SPLIT`, `normalized_net_revenue_cents` is the line's `gross_income_cents` less its `interchange_cents`, less its `assessments_cents`, less the `processor_cost_cents` just computed. The buy rate is deducted at the line, so the agent split basis is net of processor cost and the ISO carries no buy-rate exposure.
- Under `GROSS_SPLIT`, `normalized_net_revenue_cents` is the line's `gross_income_cents` less its `interchange_cents`, less its `assessments_cents`, and the processor cost is **not** deducted. The ISO absorbs the buy rate at the house level, which means that for identical file data the normalized net revenue under `GROSS_SPLIT` is higher than under `NET_REVENUE_SPLIT` by exactly `processor_cost_cents`.

Either result may be negative — a month of heavy interchange against thin fee income legitimately produces a negative line, and nothing floors it. Whichever variant ran, the program's mode is stamped onto the line as `normalization_mode_applied`, so a later amendment of the program never rewrites history.

Once every line has been normalized, the batch rolls up: `line_count` becomes the number of lines attached to the batch, `gross_volume_cents` becomes the sum of their `sales_volume_cents` values, and `total_normalized_net_revenue_cents` becomes the sum of their `normalized_net_revenue_cents` values. That last total sums the already-rounded per-line results — round first, then add, never the reverse. A batch with no lines at all normalizes successfully, and all three totals stay at 0. Normalization rewrites every line it processes, so each of those lines has its `version` bumped by one and its `updated_at` refreshed, and the batch's own `version` is bumped once alongside them.

**Recall** is normalization's undo, moving the batch from `NORMALIZED` back to `RECEIVED` so a corrected file can be re-ingested or a missing merchant added. It is available only from `NORMALIZED`. Recall resets `processor_cost_cents` and `normalized_net_revenue_cents` to 0 and `normalization_mode_applied` to null on every line of the batch, and resets the batch's `total_normalized_net_revenue_cents` to 0 — while `line_count` and `gross_volume_cents` deliberately keep their ingested values, because those describe the file rather than the pricing. Each recall raises `recall_count` by one, and the loop may be traversed as many times as the operator needs. Recall rewrites every line of the batch just as normalization did, so each line's `version` advances by one again and the batch's own `version` advances with it. Its only precondition is the `NORMALIZED` state: recall is gated neither by program suspension, as §3.1 already notes, nor by the period lock, so it stays available even when a statement for the batch's `period_month` has already been issued or finalized.

### 3.5. Posting the Ledger: Profitability, the Override Waterfall, and Reversal

Posting is the single operation in this system that turns a priced file into money owed, and only a `ResidualController` may perform it. It advances the batch from `NORMALIZED` to `POSTED` and is refused with `ERR_BATCH_STATE_INVALID` from any other state, with `ERR_PROGRAM_SUSPENDED` when the governing program is not `ACTIVE`, and with `ERR_PERIOD_LOCKED` (HTTP 409) when any statement anywhere in the system whose `period_month` equals the batch's `period_month` has a `lifecycle_state` of `ISSUED` or `FINALIZED`. That last guard is the period lock: once a single agent's statement for a month has been reported, no further batch may be posted into that month.

A successful post writes `posted_at` from the logical clock, raises the governing program's `posted_batch_count` by one, and then runs a four-level cascade.

**Cascade link 1 — per-merchant profitability.** One profitability row is created for each line of the batch, walked in ascending `created_at` order. Each row copies the line's `merchant_id`, the batch's own identity as `residual_batch_id`, the batch's `period_month`, and the line's `normalized_net_revenue_cents`.

Chargebacks are then aggregated twice over the same event set with two different filters. `chargeback_cost_cents` is the sum of `amount_cents` over every chargeback of that merchant whose `period_month` equals this row's `period_month`, across **both** liability values. `agent_chargeable_chargeback_cents` is the same sum restricted to events whose `liability` is `AGENT_CHARGED`. Events booked to any other period are excluded regardless of their `occurred_on`.

Equipment cost is charged for the period and prorated only when the merchant went dark inside it. Let the period's first day be the first calendar day of `period_month` and let the number of days in the period be the count of days from that first day to the first day of the following month. If the merchant's `status` is `ATTRITED` and its `attrition_date` falls on or after the period's first day and strictly before the first day of the following month, count the active days as the number of days from the period's first day to `attrition_date` plus one — the attrition day itself counts, so a merchant that closes on the first of the month is still charged for one day — then take the smaller of that active-day count and the number of days in the period, multiply `equipment_lease_monthly_cents` by it, divide by the number of days in the period, and round half up to the cent. If the merchant is `ATTRITED` with an `attrition_date` earlier than the period's first day, `equipment_cost_cents` is 0 — the lease had already ended. In every other case, including a merchant that is still `PENDING` or `ACTIVE`, `equipment_cost_cents` is the full `equipment_lease_monthly_cents`.

The row then closes with two deliberately divergent bottom lines. `profit_cents`, the ISO's view, is the line's `normalized_net_revenue_cents` less `chargeback_cost_cents` less `equipment_cost_cents`. `agent_basis_cents`, the split basis, is the same `normalized_net_revenue_cents` less only `agent_chargeable_chargeback_cents` and less `equipment_cost_cents`. The split basis is never floored at zero: a negative basis flows straight through into negative allocations, and an agent can legitimately owe the ISO for a bad month.

**Cascade link 2 — the override waterfall.** Each profitability row created by link 1 immediately triggers the split. The basis is that row's `agent_basis_cents`, and the direct agent is the one named by the merchant's `owning_agent_id` **as it stands at post time** — a later reassignment does not rewrite an allocation already written.

Paying a tier always follows the same three steps. First compute the raw entitlement: the basis multiplied by the percentage for that tier, rounded half up to the cent. Second, decide what is actually paid: if the receiving agent's `status` is `DEPARTED`, the amount paid is the basis multiplied by the tier percentage multiplied by that agent's `vested_pct_at_departure`, divided by one hundred, rounded half up to the cent; otherwise the amount paid equals the raw entitlement. Third, record the difference: `vesting_withheld_cents` is the raw entitlement minus the amount actually paid, which is zero for any agent that is not `DEPARTED`. An allocation row is written carrying `applied_pct` (the percentage that was applied), `basis_cents` (the basis it was computed from), `gross_allocation_cents` (the amount actually paid), `vesting_withheld_cents`, the receiving `agent_id`, the `merchant_id` whose basis was split, the batch's `period_month`, plus the `allocation_type` and `tier_level` described below. A row is created only when the amount paid is non-zero or the withheld amount is non-zero; a tier that would produce nothing at all leaves no row behind — and no statement either, because the statement of link 3 is upserted only once a tier actually has something to record, so a tier that pays nothing and withholds nothing never brings a `DRAFT` statement into existence for that agent.

The direct tier is paid first, at the owning agent's own `split_pct`, with `allocation_type` `DIRECT_SPLIT` and `tier_level` 0. A running cumulative percentage starts at that same `split_pct`. The walk then climbs the hierarchy by following `parent_agent_id` upward, visiting at most three ancestors and stopping early if the chain runs out. Each visit is numbered from 1 upward, and that visit number becomes the `tier_level` of any row it writes. At each visited ancestor the differential entitlement is the ancestor's `override_pct` minus the running cumulative percentage, or zero if that difference would be negative; when the differential is strictly greater than zero the ancestor is paid at that differential with `allocation_type` `OVERRIDE`. Whether or not the ancestor was paid, the running cumulative percentage then becomes the larger of its previous value and that ancestor's `override_pct`. Two subtleties follow from this. The cumulative percentage always advances on **nominal** percentages — vesting scaling changes what a departed agent is paid, never the tier arithmetic that the tiers above it inherit. And a `DEPARTED` ancestor still consumes one of the three visits: the limit counts ancestors visited, not ancestors paid, so a departed intermediary does not let a fourth-level upline slip into the waterfall.

Once the tiers are done, the house takes the residue. The profitability row's `allocated_total_cents` is the sum of `gross_allocation_cents` over the rows just created, and its `iso_retained_cents` is `agent_basis_cents` minus `allocated_total_cents`. That single figure absorbs three different things at once: the percentage points no tier claimed, every cent withheld from a departed agent by vesting, and every rounding remainder from the independently rounded tiers.

**Cascade link 3 — statement attachment and recompute.** Each allocation is attached to the `DRAFT` statement identified by its receiving agent and the batch's `period_month`, and when no statement exists for that agent and month the system creates one in `lifecycle_state` `DRAFT` and `settlement_state` `UNSETTLED`. The attachment then triggers a recompute of that statement's `direct_residual_cents`, `override_residual_cents`, `gross_after_trueup_cents`, `net_payable_cents` and `carry_forward_deficit_cents` under the draft evaluation described in §3.7.

**Cascade link 4 — agent KPI refresh.** Each statement recompute in turn refreshes `trailing_residual_cents` on that statement's agent.

Finally the batch itself records `iso_retained_cents` as the sum of `iso_retained_cents` over the profitability rows it produced, and the batch's `version` is bumped along with the versions of every statement the cascade touched. The bump count is pinned: a statement that already existed is bumped exactly once by the whole post, no matter how many of the batch's allocations attached to it, while a statement the post itself brought into existence is not bumped at all and stays at `version` 1 with its `updated_at` equal to its `created_at`, because its creation and its first recompute are the same write. The profitability rows and allocation rows the cascade creates are likewise written once and never bumped afterwards — the `allocated_total_cents` and `iso_retained_cents` a profitability row receives at the end of its own split are part of that single write — so both kinds of row always read `version` 1.

**Reversal** is posting's exact compensation, again available only to a `ResidualController`, and it moves the batch from `POSTED` to `REVERSED` — a terminal state from which nothing returns. It is refused with `ERR_BATCH_STATE_INVALID` from any other state, and with `ERR_PERIOD_LOCKED` when any statement whose `period_month` equals the batch's `period_month` has a `lifecycle_state` of `ISSUED` or `FINALIZED`. Because of that guard, every statement a reversal touches is necessarily `DRAFT`, and every recompute it triggers therefore uses the draft evaluation.

The unwinding runs in a fixed order: first every allocation produced by this batch's post is deleted, then every profitability row produced by this batch is deleted, then each affected statement is recomputed (`direct_residual_cents`, `override_residual_cents`, `gross_after_trueup_cents`, `net_payable_cents`, `carry_forward_deficit_cents`), and only then is `trailing_residual_cents` recomputed on each affected agent. The batch's `iso_retained_cents` returns to 0 and its `posted_at` to null, and the governing program's `posted_batch_count` falls by one. Statements that only existed because the post had created them are kept as empty `DRAFT` statements rather than deleted — they are harmless and they preserve the audit trail. Every affected statement's `version` is bumped exactly once by the reversal, those included, so a statement the post had created moves from `version` 1 to `version` 2. The batch's own residual lines are not disturbed: `processor_cost_cents`, `normalized_net_revenue_cents` and `normalization_mode_applied` all stand, and the batch keeps the `line_count`, `gross_volume_cents` and `total_normalized_net_revenue_cents` it carried into the post, because reversal unwinds the posting and not the pricing. Reversal also releases the batch's `file_checksum` for re-ingest. When the dust settles, every affected statement's `gross_after_trueup_cents` equals exactly what it was before the post.

### 3.6. Advances, Portfolio Buyouts and the Recoupment Waterfall

The ISO funds money to agents ahead of their residual stream and takes it back out of later statements. An `IsoAdmin` funds an advance against one agent, whose `status` must be `ACTIVE` — funding a non-active agent is `ERR_AGENT_STATE_INVALID`. The payload declares an `advance_type` of either `CASH_ADVANCE` (working capital) or `PORTFOLIO_BUYOUT` (the ISO purchasing a residual stream outright), a `recoupment_mode` of either `PERCENT_OF_RESIDUAL` or `STRAIGHT_LINE_AMORTIZATION`, a `principal_cents` strictly greater than zero, the recoupment window as `first_recoupment_month` and `last_recoupment_month`, the date-only `funded_on`, and the optimistic-concurrency field `expected_agent_version`. Two further fields are conditional on the mode: `recoupment_pct` is required when `recoupment_mode` is `PERCENT_OF_RESIDUAL` and must be absent or null otherwise, while `amortization_months` gives the length of the recoupment window in whole months — an integer from 1 through 60 inclusive — and doubles as the divisor under straight-line amortization. When supplied, `recoupment_pct` must be strictly greater than `0.0000` and no greater than `1.0000`. The two strictness rules are reported from different bands: a `principal_cents` at or below zero is a band-4 `ERR_INVALID_REQUEST` (400), while a `recoupment_pct` of exactly `0.0000` is a band-5 field-domain failure and reports `ERR_INVALID_PCT_RANGE` (422) just as a value above `1.0000` does. Inside band 5 the percentage is validated before the two accounting months, so a funding request that is wrong in both respects reports `ERR_INVALID_PCT_RANGE` rather than `ERR_INVALID_PERIOD_MONTH`.

The window is validated as a shape. `last_recoupment_month` must be greater than or equal to `first_recoupment_month`; `first_recoupment_month` must be greater than or equal to the calendar month of `funded_on`, so an advance can never reach back before it was funded; and when the mode is `STRAIGHT_LINE_AMORTIZATION` the inclusive count of months from `first_recoupment_month` through `last_recoupment_month` must equal `amortization_months` exactly. Under `PERCENT_OF_RESIDUAL` the window may be any length. A failure on any of the three is `ERR_RECOUPMENT_WINDOW_INVALID` (HTTP 422).

Two fiscal ceilings then apply. No single advance may be written to claim more than half of a monthly residual, so `recoupment_pct` may not exceed `0.5000`; a larger figure is `ERR_RECOUPMENT_PCT_EXCEEDS_CAP` (HTTP 422). And the agent's total exposure is capped: the sum of `outstanding_cents` over that agent's advances whose `state` is `ACTIVE`, plus the new `principal_cents`, may not exceed the larger of a bootstrap floor of 250,000 cents — two thousand five hundred dollars, the allowance that lets a brand-new agent with no production history be funded at all — and six times the agent's `trailing_residual_cents`. Exceeding it is `ERR_ADVANCE_EXPOSURE_EXCEEDED` (HTTP 409). Each advance in a stack may be individually acceptable while the portfolio total is not, which is exactly why this check is aggregate rather than per-advance.

A funded advance starts with `state` `ACTIVE`, `outstanding_cents` equal to `principal_cents`, `cumulative_recouped_cents` at 0 and `months_recouped` at 0; the receiving agent's `advance_outstanding_cents` rises by the principal and its `version` is bumped. Advances legitimately stack, so nothing prevents a second funding on the same agent beyond the exposure ceiling and the staleness guard.

An `ACTIVE` advance's terms may be restructured, including switching between the two recoupment variants: `recoupment_mode`, `recoupment_pct`, `amortization_months` and `last_recoupment_month` are all amendable. Restructuring is never retroactive — amounts already recouped stand. An advance whose `state` is `RECOUPED` is closed and may not be restructured: that is `ERR_ADVANCE_STATE_INVALID` (HTTP 409), and it is reported ahead of any shape complaint about the patch itself. For an advance that is `ACTIVE`, a shape rule then applies to the *result* of the patch: if the resulting `recoupment_mode` is `STRAIGHT_LINE_AMORTIZATION` the advance must have an `amortization_months` after the patch is applied, and if it is `PERCENT_OF_RESIDUAL` the advance must have a `recoupment_pct` after the patch is applied; a patch that leaves the advance without the field its mode requires is `ERR_INVALID_REQUEST`. The window shape rule and the half-of-residual cap are both re-evaluated against the restructured terms, the window against the advance's unchanged `first_recoupment_month` and `funded_on`. Four further details of the restructure are pinned. The `last_recoupment_month` it carries is shape-checked in band 4, so a malformed month reports `ERR_INVALID_REQUEST` (400) here rather than the `ERR_INVALID_PERIOD_MONTH` the same field yields at funding time. An explicit `null` is meaningful for `recoupment_pct` and `amortization_months` — it clears the stored value, which is exactly how an advance switching variant sheds the field it no longer needs — while for `recoupment_mode` and `last_recoupment_month` a `null` is read as an omission and the stored value stands. The closed-interval domain check of band 5 is not re-applied to a restructured `recoupment_pct`: only the half-of-residual cap is, so a restructure above `0.5000` is `ERR_RECOUPMENT_PCT_EXCEEDS_CAP` while a negative percentage is never answered with `ERR_INVALID_PCT_RANGE` and is stored as supplied. And a successful restructure bumps the advance's `version` only — the owning agent is not touched — including a restructure whose resulting terms are identical to the stored ones.

**The recoupment waterfall** runs when a statement is issued, and it consumes a single aggregate cap. Let the statement's gross after true-up be the figure produced by step 4 of the statement evaluation in §3.7. The aggregate cap is that gross multiplied by one half, rounded half up to the cent, and floored at zero — no statement ever gives up more than fifty percent of its gross to advance recovery, no matter how many advances are outstanding. Eligible advances are those belonging to the statement's agent whose `state` is `ACTIVE` and whose closed window contains the statement's `period_month`, meaning `first_recoupment_month` is less than or equal to that month and `last_recoupment_month` is greater than or equal to it. Advances already `RECOUPED`, and advances whose window does not contain the period, contribute nothing. The eligible set is consumed in ascending `funded_on` order, with ascending `created_at` breaking ties — the oldest money is repaid first, and when the cap runs out it is the later advance that is truncated, never the earlier one.

For each eligible advance in that order, the instalment it *wants* depends on its variant:

- Under `PERCENT_OF_RESIDUAL` the instalment floats with the statement. A tier cap is selected from the statement's gross after true-up: twenty-five hundredths when that gross is below 50,000 cents, forty hundredths when it is at least 50,000 cents but below 150,000 cents, and fifty hundredths at 150,000 cents or above. In dollars, an agent grossing under five hundred dollars gives up at most a quarter of it, an agent between five hundred and fifteen hundred dollars at most forty percent, and an agent at fifteen hundred dollars or more at most half. The effective percentage is the smaller of the advance's own `recoupment_pct` and that tier cap, and the wanted amount is the gross multiplied by the effective percentage, rounded half up to the cent. A weak month therefore recoups little and stretches the horizon.
- Under `STRAIGHT_LINE_AMORTIZATION` the instalment is fixed and ignores the statement entirely. If this recoupment would be the final scheduled one — that is, if `months_recouped` plus one is greater than or equal to `amortization_months` — the wanted amount is the advance's entire `outstanding_cents`, so the last instalment absorbs whatever the earlier roundings left behind. Otherwise the wanted amount is `principal_cents` divided by `amortization_months`, rounded half up to the cent.

The amount actually taken from an advance is the smallest of three quantities: what it wanted, its own `outstanding_cents`, and the cap remaining after earlier advances took their share. The remaining cap is reduced by what was taken, and the statement's `advance_recoupment_cents` is the total taken across the whole eligible set. Because the two variants compute their wanted amount from different inputs, two otherwise identical statements against identical principal recoup different amounts under the two modes. An advance whose take works out to zero or less — because earlier advances already exhausted the aggregate cap, because its own `outstanding_cents` is already nothing, or because its wanted instalment rounded to nothing — is left completely untouched: no money moves against it, its `months_recouped` does not advance, its `version` is not bumped, and it is not recorded among the takes that a later recall would have to compensate. A zero take is not a month the advance was recouped from. The walk simply moves on to the next advance, and once the remaining cap has reached zero every advance still behind it in the order is treated exactly this way.

Each advance touched by an issue has its `cumulative_recouped_cents` raised by its take, its `months_recouped` raised by one, and its `outstanding_cents` lowered by its take; `months_recouped` is simply the count of distinct accounting months this advance has been recouped from, and it serves as the amortization index. An advance whose `outstanding_cents` reaches exactly zero auto-transitions from `ACTIVE` to `RECOUPED` without any operator action. The agent's `advance_outstanding_cents`, which is the sum of `outstanding_cents` over that agent's `ACTIVE` advances, is refreshed afterwards. Recalling the statement reverses all of it exactly — each advance's `cumulative_recouped_cents` falls by precisely the amount that statement had taken, `months_recouped` falls by one, `outstanding_cents` is restored, and an advance that had reached `RECOUPED` auto-transitions back from `RECOUPED` to `ACTIVE` as soon as its outstanding balance is positive again.

### 3.7. Statement Authoring: Draft, Issue, Recall, Finalize

A statement is one agent's residual month. It is never created directly by a client: it comes into existence as a side effect of a posting cascade or of a system-generated adjustment, always in `lifecycle_state` `DRAFT` and `settlement_state` `UNSETTLED`. A statement is identified by its `agent_id` and its `period_month`, and the pair is unique — an agent has at most one statement per accounting month.

The statement carries two independent state dimensions on the same row, and this is the single most important structural fact about it. `lifecycle_state` is the authoring dimension and moves `DRAFT` → `ISSUED` → `FINALIZED`, with an `ISSUED` → `DRAFT` recall edge. `settlement_state` is the payment dimension and moves `UNSETTLED` → `HELD` → `UNSETTLED` → `SETTLED`. Neither dimension gates the other except where this document says so explicitly: a `HELD` statement can still be issued, and a `HELD` statement can still be finalized.

**The money lines, and the order they are evaluated in.** Every mutation that touches a statement — an allocation attaching, an allocation being deleted by a reversal, an adjustment becoming applied, an issue, a recall — recomputes the statement's money lines. The order is pinned, because step 5 reads step 4 and step 4 includes step 3, so the answer is only well defined in this sequence.

1. `direct_residual_cents` is the sum of `gross_allocation_cents` over the allocations attached to this statement whose `allocation_type` is `DIRECT_SPLIT`.
2. `override_residual_cents` is the same sum restricted to allocations whose `allocation_type` is `OVERRIDE`.
3. `minimum_true_up_cents` is 0 while the statement is `DRAFT`, and is the monthly-minimum reconciliation described below once the statement is issued.
4. `gross_after_trueup_cents` is `direct_residual_cents` plus `override_residual_cents` plus `minimum_true_up_cents`.
5. `advance_recoupment_cents` is 0 while the statement is `DRAFT`, and is the result of the recoupment waterfall of §3.6 — evaluated with the gross produced by step 4 — once the statement is issued.
6. `adjustment_cents` is the signed sum of `amount_cents` over this statement's adjustments whose `state` is `APPLIED`. Adjustments in any other state, including `REJECTED` ones, contribute nothing.
7. `opening_deficit_cents` is the `carry_forward_deficit_cents` of this same agent's statement for the calendar month immediately preceding this statement's `period_month`, and only when that predecessor's `lifecycle_state` is `ISSUED` or `FINALIZED`. When no such statement exists, or when the predecessor is still `DRAFT`, this is 0.
8. The pre-floor balance is `gross_after_trueup_cents` minus `advance_recoupment_cents`, plus `adjustment_cents`, minus `opening_deficit_cents`.
9. `net_payable_cents` is that pre-floor balance when it is zero or positive, and 0 when it is negative. `carry_forward_deficit_cents` is the absolute value of the pre-floor balance when that balance is negative, and 0 when the balance is zero or positive. A deficit therefore never chases the agent for cash; it rolls into the following month through step 7.

Only steps 3 and 5 involve any rounding at all; everything else is integer addition and subtraction of cents. The two variants of this evaluation matter operationally: a `DRAFT` statement forces steps 3 and 5 to zero, so it shows allocations and applied adjustments but never a minimum true-up and never an advance recoupment, while a statement being issued — and thereafter while its `lifecycle_state` is `ISSUED` or `FINALIZED` — evaluates and persists both. The same allocation set therefore yields a different `net_payable_cents` before and after issue, by design. Steps 3 and 5 are evaluated exactly once, by the issue itself. Every later recompute of a statement whose `lifecycle_state` is `ISSUED` or `FINALIZED` — an adjustment becoming applied, for instance — carries the `minimum_true_up_cents` and `advance_recoupment_cents` that the issue persisted forward unchanged, re-running neither the monthly-minimum reconciliation nor the recoupment waterfall, so no advance is ever recouped twice for one accounting month and no true-up is ever recomputed against a merchant whose status has since moved. A recompute performed while the statement is `DRAFT`, by contrast, forces both fields back to 0 every time.

**Issuing.** Only a `ResidualController` may issue, and only from `DRAFT`; an issue attempt from `ISSUED` or `FINALIZED` is `ERR_STATEMENT_STATE_INVALID` (HTTP 409). The period must also be closed out on the ingestion side: every batch anywhere in the system whose `period_month` equals the statement's `period_month` must have a `state` of `POSTED` or `REVERSED`. A single batch for that period still sitting in `RECEIVED` or `NORMALIZED` blocks the issue of *every* statement of that period with `ERR_BATCHES_NOT_POSTED` (HTTP 409). Issue leaves `settlement_state` completely untouched, so a statement already on payment hold can still be issued.

On issue the system runs the monthly-minimum reconciliation and writes `minimum_true_up_cents`, then runs the recoupment waterfall and writes `advance_recoupment_cents` along with all the advance bookkeeping described in §3.6, then refreshes the agent's `advance_outstanding_cents`, then writes `opening_deficit_cents`, `net_payable_cents` and `carry_forward_deficit_cents` under the issued evaluation, stamps `issued_at` with the logical clock, and finally refreshes the agent's `trailing_residual_cents`. However many advances the waterfall consumed, the whole issue bumps the statement's `version` exactly once; each advance the waterfall actually took money from is bumped once as well, and an advance it passed over is not bumped at all.

**The monthly-minimum reconciliation.** Merchants owe the ISO a contractual monthly minimum, and when their per-transaction fee income falls short of it the ISO bills the shortfall and shares half of the agent's contractual portion of it with the agent. The calculation walks this statement's allocations whose `allocation_type` is `DIRECT_SPLIT`, in ascending `created_at` order — override tiers receive no share of a monthly-minimum shortfall at all. For each such allocation, take the merchant it points at and the processor program that merchant is boarded on, and skip the merchant entirely in two cases: when its `status` is anything other than `ACTIVE` at issue time (an attrited merchant owes no minimum, even if it produced a line for the period), and when its program's `minimum_billing_mode` is `NO_MINIMUM`. Otherwise find the residual line for that merchant belonging to a batch whose `period_month` equals the statement's `period_month` and whose `state` is `POSTED`; if no such line exists the merchant is skipped, and in the unusual case where two posted batches of that same month each carry a line for the merchant, the earliest of those lines by `created_at` is the one read. The billable fee income is the merchant's `per_transaction_fee_cents` multiplied by that line's `transaction_count`. The shortfall is the merchant's `monthly_minimum_cents` minus that billable fee income, or zero when the fee income already covers the minimum — the comparison is inclusive, so billable fee income exactly equal to the monthly minimum yields a shortfall of zero and bills nothing. The agent's share of that shortfall is the shortfall multiplied by the agent's `split_pct` multiplied by one half, rounded half up to the cent. The percentage used is the live `split_pct` on the agent row as it stands at issue time, not the `applied_pct` frozen onto the allocation when the batch was posted, so a `split_pct` amended between the post and the issue does move the true-up even though it never moves the allocation. Nor is any vesting scaling applied here: a `DEPARTED` agent's true-up is computed from its full `split_pct`, even though the allocations on the same statement were scaled down by `vested_pct_at_departure`. Each merchant's share is rounded on its own and the rounded shares are then added; `minimum_true_up_cents` is that total.

**Recalling.** An issued statement may be pulled back to `DRAFT` by a `ResidualController` — the edge exists because a processor correction or a missed adjustment is discovered after issue more often than anyone would like. Recall is available only from `lifecycle_state` `ISSUED` (otherwise `ERR_STATEMENT_STATE_INVALID`) and only while `settlement_state` is not `SETTLED`; recalling a settled statement is `ERR_SETTLEMENT_STATE_INVALID` (HTTP 409), because the money has already left. Recall reverses everything the issue booked: every advance recoupment is unwound exactly as described in §3.6, `minimum_true_up_cents` and `advance_recoupment_cents` both return to 0, `issued_at` returns to null, and `gross_after_trueup_cents`, `opening_deficit_cents`, `net_payable_cents` and `carry_forward_deficit_cents` are recomputed under the draft evaluation. The agent's `advance_outstanding_cents` and `trailing_residual_cents` are both refreshed afterwards. When both dimensions are wrong at once the authoring dimension is the one reported: recalling a `FINALIZED` statement that has already been settled is `ERR_STATEMENT_STATE_INVALID`, not `ERR_SETTLEMENT_STATE_INVALID`. That is the opposite order from the hold and settle transitions of §3.9, which consult the settlement dimension first. Recall leaves `settlement_state` and `hold_reason` exactly as it found them.

**Finalizing.** Finalizing moves the statement from `ISSUED` to `FINALIZED` and is available only from `ISSUED`; anything else is `ERR_STATEMENT_STATE_INVALID`. It is the authoring dimension's terminal state and it freezes the statement: no allocation may be attached to it afterwards and no adjustment may be applied to it afterwards. Finalizing is permitted while `settlement_state` is `HELD`, since the two dimensions do not gate each other.

**The production KPI.** An agent's `trailing_residual_cents` is the sum of `gross_after_trueup_cents` over that agent's three most recent statements — or fewer, when fewer exist — ordered by `period_month` descending, and it counts statements in **all** three lifecycle states: `DRAFT`, `ISSUED` and `FINALIZED`. This is deliberately wider than the window used by the departure buyout in §3.9, which admits only `ISSUED` and `FINALIZED` statements; the two must not be conflated.

### 3.8. Corrections: Disputes, Debits and Segregation of Duties

Not every correction fits inside the monthly arithmetic. A merchant disputes a fee and the ISO credits the agent; an agent is overpaid and the ISO debits it back; a clawback turns out to have been wrong. All of these enter the ledger as **statement adjustments**: signed corrections attached to exactly one statement.

Any of the four roles may propose an adjustment against a statement, with an acting `Agent` confined to its own statements. The proposal names a `kind`, a signed `amount_cents`, a free-text `reason` between 1 and 300 characters, the optimistic-concurrency field `expected_statement_version`, and optionally a `source_merchant_id`. The `kind` is one of `DISPUTE_CREDIT`, `MANUAL_DEBIT`, `BONUS_CLAWBACK`, `CLAWBACK_REVERSAL` or `VESTED_BUYOUT`. In practice `DISPUTE_CREDIT` and `MANUAL_DEBIT` are the kinds an operator or agent proposes, while `BONUS_CLAWBACK`, `CLAWBACK_REVERSAL` and `VESTED_BUYOUT` are the kinds the system generates from its own cascades — merchant attrition, merchant reactivation and agent departure respectively — and those system-generated rows are created directly in `state` `APPLIED` with `created_by_user_id` set to the literal `system`, bypassing the review cycle entirely. Because no client supplied it, the `reason` on such a row is server-generated: the literal `System-generated ` followed by the row's own `kind`, so a system clawback reads `System-generated BONUS_CLAWBACK`. Both `approved_by_user_id` and `info_request_note` are null on a system-generated row, since nobody reviewed it. `source_merchant_id` is populated only for the merchant-originated kinds `BONUS_CLAWBACK`, `CLAWBACK_REVERSAL` and `DISPUTE_CREDIT`, and is null for the others — but it is still resolved against the merchant collection in band 7 whatever the `kind` is, so a `MANUAL_DEBIT` naming an unknown merchant is `ERR_REFERENCED_MERCHANT_NOT_FOUND` and only a known merchant is then discarded to null. Nothing stops a client from proposing one of the three system kinds by hand either: all five values are accepted from any authorized role, and a client-proposed `BONUS_CLAWBACK`, `CLAWBACK_REVERSAL` or `VESTED_BUYOUT` is created in `state` `PROPOSED` with the proposer's own `X-User-ID` and walks the ordinary review cycle like any other proposal.

Sign discipline is absolute and is checked on every proposal. `amount_cents` may never be zero. It must be strictly positive for `DISPUTE_CREDIT`, `CLAWBACK_REVERSAL` and `VESTED_BUYOUT`, and strictly negative for `MANUAL_DEBIT` and `BONUS_CLAWBACK`. A zero amount, or a sign that contradicts the kind, is `ERR_ADJUSTMENT_SIGN_INVALID` (HTTP 422). One further ceiling guards the reversal kind: a `CLAWBACK_REVERSAL` may not give back more than was taken, so its `amount_cents` may not exceed the owning agent's `lifetime_clawback_cents`; a larger figure is `ERR_CLAWBACK_REVERSAL_EXCEEDS_CLAWBACK` (HTTP 409). That agent-level counter is the sum of the absolute values of `amount_cents` over the agent's `APPLIED` adjustments of `kind` `BONUS_CLAWBACK`, less the same over its `APPLIED` adjustments of `kind` `CLAWBACK_REVERSAL`, taken across all of that agent's statements. Its per-merchant analogue, `clawed_back_bonus_cents`, is computed the same way but restricted to adjustments whose `source_merchant_id` is that merchant.

Adjustments may be proposed only against a statement whose `lifecycle_state` is `DRAFT` or `ISSUED`; a proposal against a `FINALIZED` statement is `ERR_STATEMENT_STATE_INVALID`. A client-proposed adjustment is created in `state` `PROPOSED` with `created_by_user_id` set to the proposing `X-User-ID` and `approved_by_user_id` null. No money moves at proposal time — the statement's `adjustment_cents` counts only `APPLIED` rows — but the parent statement's `version` is nonetheless bumped, which is precisely why the next proposer must re-read the statement before submitting.

The review cycle is walked by a `ResidualController` and its states are `PROPOSED`, `UNDER_REVIEW`, `INFO_REQUESTED`, `APPLIED` and `REJECTED`, of which the last two are terminal. Taking a `PROPOSED` adjustment under review moves it `PROPOSED` → `UNDER_REVIEW`, and requires the parent statement's `lifecycle_state` to still be `DRAFT` or `ISSUED`. From `UNDER_REVIEW` the controller may send it back to the proposer for more information, moving `UNDER_REVIEW` → `INFO_REQUESTED` and recording the question as `info_request_note`. Answering that question returns the adjustment `INFO_REQUESTED` → `UNDER_REVIEW`, clears `info_request_note`, and optionally overwrites `reason` when a new one is supplied; any of the four roles may answer, with an acting `Agent` again confined to its own statements. This loop closes on itself and may be traversed as many times as the review demands. Any transition attempted from a state that does not admit it — review from anything but `PROPOSED`, an information request from anything but `UNDER_REVIEW`, an answer from anything but `INFO_REQUESTED`, an approval or a refusal from anything but `UNDER_REVIEW` — is `ERR_ADJUSTMENT_STATE_INVALID` (HTTP 409). Two things about the cycle are pinned. The addressed adjustment's own `state` is always consulted before the parent statement, so taking an already-`APPLIED` adjustment under review reports `ERR_ADJUSTMENT_STATE_INVALID` even when its statement has since been finalized; and only review and approval consult the parent statement at all, so an information request, an answer and a refusal all remain available while the parent statement is `FINALIZED`. The `info_request_note` is required on the information request and must be at least one character long, with no upper bound on its length. Each of these four transitions — review, information request, answer and refusal — bumps only the adjustment's own `version` and leaves the parent statement's `version` and `updated_at` untouched, because none of them moves money.

Approval is where **segregation of duties** bites. Moving an adjustment `UNDER_REVIEW` → `APPLIED` requires that the approving `X-User-ID` differ from that adjustment's `created_by_user_id`; when they are the same principal the approval is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 409). This holds even when both the proposer and the approver were acting as `ResidualController` — the rule is about the person, not the role. The parent statement must also still be `DRAFT` or `ISSUED`, or the approval is `ERR_STATEMENT_STATE_INVALID`. Note the ordering once more: approving a still-`PROPOSED` adjustment as its own creator reports `ERR_ADJUSTMENT_STATE_INVALID`, because the state check is evaluated before the duty-segregation check. The parent-statement check sits in that same band 9 and is likewise evaluated ahead of segregation of duties, so approving one's own adjustment against a `FINALIZED` statement reports `ERR_STATEMENT_STATE_INVALID`. A successful approval writes `approved_by_user_id` from `X-User-ID`, recomputes the parent statement's `adjustment_cents`, `net_payable_cents` and `carry_forward_deficit_cents`, then refreshes the agent's `lifetime_clawback_cents` and — when `source_merchant_id` is set — the merchant's `clawed_back_bonus_cents`, and bumps both the adjustment's `version` and the statement's `version`.

Refusal moves the adjustment `UNDER_REVIEW` → `REJECTED`, records the refusing `X-User-ID` as `approved_by_user_id` and an optional `reason` of record, and leaves the statement's money entirely untouched, because rejected rows are excluded from the applied-only filter that feeds `adjustment_cents`. Segregation of duties does not reach refusal: the principal that proposed an adjustment may reject it, and `approved_by_user_id` then records that same principal. Only approval is bound by the rule.

### 3.9. Settlement, Departure, Vesting and Portfolio Transfer

**Holding and releasing payment.** The settlement dimension exists so that payment can be stopped without disturbing the authoring dimension. A `ResidualController` may place a statement whose `settlement_state` is `UNSETTLED` on hold, moving it `UNSETTLED` → `HELD` and recording the supplied `hold_reason`; the statement's `lifecycle_state` must be `DRAFT` or `ISSUED` at the time, so a `FINALIZED` statement cannot be newly placed on hold and the attempt is refused with `ERR_STATEMENT_STATE_INVALID`. A hold attempted from `HELD` or `SETTLED` is `ERR_SETTLEMENT_STATE_INVALID`. `hold_reason` is required on a manual hold and must be at least one character long, with no upper bound on its length. The two state checks are ordered settlement dimension first, authoring dimension second, so a statement that is `FINALIZED` *and* already `HELD` reports `ERR_SETTLEMENT_STATE_INVALID`. The same transition also happens automatically, without any operator action, when an agent's `residual_hold` flips to true through the attrition cascade of §3.3 — in which case the `hold_reason` written is `PORTFOLIO_ATTRITION_THRESHOLD`.

Releasing a hold moves the statement `HELD` → `UNSETTLED` and clears `hold_reason`, and is available only from `HELD`. It is refused with `ERR_RESIDUAL_HOLD_ACTIVE` (HTTP 409) while the owning agent's `residual_hold` flag is still set: an operator cannot simply release a risk hold, because the flag can only be cleared by bringing the agent's `portfolio_attrition_bps` back under 2,500 basis points — in practice by reactivating a merchant. This is the one place where the two dimensions and the agent-level risk flag interlock.

**Settling.** Settlement is the only door money leaves through. A `ResidualController` settles a statement by supplying the date-only `paid_on`, and four conditions must all hold. The `settlement_state` must be `UNSETTLED`; settling from `HELD` or from `SETTLED` is `ERR_SETTLEMENT_STATE_INVALID`. The `lifecycle_state` must be `ISSUED` or `FINALIZED`; settling a `DRAFT` statement is `ERR_STATEMENT_STATE_INVALID`, because a draft has no true-up and no recoupment booked against it. The owning agent's `residual_hold` must be false, or the settlement is `ERR_RESIDUAL_HOLD_ACTIVE`. And the statement's `net_payable_cents` must be at least 2,500 cents — twenty-five dollars — or the settlement is `ERR_BELOW_MIN_PAYOUT` (HTTP 409); balances below the floor stay unsettled and roll into the next period through the opening-deficit mechanism. The four are evaluated in exactly the order just listed — settlement dimension, then authoring dimension, then the risk hold, then the payout floor — so settling a `DRAFT` statement that has somehow already been settled reports `ERR_SETTLEMENT_STATE_INVALID`, and a held agent whose statement also sits below the floor reports `ERR_RESIDUAL_HOLD_ACTIVE`. On success `paid_on` is recorded and the statement moves `UNSETTLED` → `SETTLED`, which is the settlement dimension's terminal state. `paid_on` is stored exactly as supplied and is constrained only by the date-shape rule of band 4: it is never compared against the logical clock, so a settlement may legitimately be dated in the clock's past or its future.

**Portfolio vesting.** An agent's entitlement to its book after it leaves is governed by a step-vesting schedule anchored on `vesting_start_date`. Count the elapsed months as twelve times the difference in years between the logical clock's current date and the vesting anchor, plus the difference in their month numbers; then, if the clock's day-of-month is earlier than the anchor's day-of-month, subtract one month, because that month has not completed. If the elapsed month count is fewer than twelve, `vested_pct` is 0 — that is the cliff, and nothing vests before it. Otherwise `vested_pct` is twenty-five percentage points multiplied by the elapsed month count divided by twelve and rounded **down** to a whole number of twelve-month steps, capped at 100. The cliff boundary is inclusive at twelve: exactly twelve elapsed months returns 25, while eleven returns 0. Full vesting is therefore reached after four completed years. Once an agent has reached `DEPARTED` and has a frozen `vested_pct_at_departure`, `vested_pct` simply returns that frozen value and stops moving. No merchant or statement data participates in this calculation — only the agent's own anchor against the clock.

**Filing and rescinding a departure notice.** An `IsoAdmin` records an agent's intention to leave by filing a notice, which moves the agent `ACTIVE` → `DEPARTURE_NOTICE` and writes the supplied `departure_effective_date`. That date must be on or after the logical clock's current date — a notice cannot be backdated — and a violation is `ERR_DEPARTURE_DATE_OUT_OF_RANGE` (HTTP 422). A notice may be withdrawn, moving the agent `DEPARTURE_NOTICE` → `ACTIVE` and clearing `departure_effective_date`. Both transitions are refused with `ERR_AGENT_STATE_INVALID` when the agent is not in the required starting status.

**Completing the departure.** Departure moves the agent `DEPARTURE_NOTICE` → `DEPARTED`, the agent lifecycle's terminal status, and is permitted only once the logical clock's current date has reached `departure_effective_date`; an early attempt is `ERR_DEPARTURE_DATE_OUT_OF_RANGE`. Two things happen. First the vesting schedule is evaluated against the clock and the result is frozen into `vested_pct_at_departure`. Second, the **vested portfolio buyout** is computed: take that agent's statements whose `lifecycle_state` is `ISSUED` or `FINALIZED`, order them by `period_month` descending — the ordering is total, since `period_month` is unique per agent — and keep the first three, or all of them when fewer exist. Draft statements never enter this window, including the very statement the departure cascade is about to create. If the window is empty the buyout is exactly 0. Otherwise take the average `gross_after_trueup_cents` across the window — the sum divided by the number of statements in it, rounded half up to the cent — then multiply that average by twenty-four and by `vested_pct_at_departure`, divide by one hundred, and round half up to the cent. Two roundings occur, one on the trailing average and one on the multiple. An agent with zero vesting buys out at exactly 0, and no adjustment is created when the buyout evaluates to 0. When it is greater than 0, the system upserts the agent's statement for the calendar month of `departure_effective_date` — creating it `DRAFT` and `UNSETTLED` when absent — and creates an adjustment on it of `kind` `VESTED_BUYOUT` in `state` `APPLIED`, with `created_by_user_id` set to `system`, `source_merchant_id` null, and `amount_cents` equal to the positive buyout. That statement is then recomputed and the agent's `trailing_residual_cents` refreshed. The version bookkeeping matches the attrition cascade: a statement the departure itself created stays at `version` 1, while a statement that already existed for that month is bumped exactly once, and the adjustment row is written at `version` 1. The agent named in the path is bumped once whether or not a buyout was booked.

Departure changes what the agent earns going forward without unwinding anything already earned. Every allocation credited to a `DEPARTED` agent thereafter is scaled by `vested_pct_at_departure` as described in §3.5, and the withheld remainder falls into the profitability row's `iso_retained_cents` rather than to another agent.

**Transferring the portfolio.** Once an agent is `DEPARTED`, an `IsoAdmin` may hand its book to someone else by naming a `target_agent_id`. The target must exist, must have `status` `ACTIVE`, and must not be the departing agent itself, but those three failures do not share one error. A `target_agent_id` that names no agent at all is `ERR_REFERENCED_AGENT_NOT_FOUND` (404) from band 7, reported ahead of the departing agent's own state precondition; a target that exists but is not `ACTIVE`, or that is the departing agent itself, is `ERR_TRANSFER_TARGET_INVALID` (HTTP 422) from band 12 and is therefore reported after it. The transfer is only available from `DEPARTED` — from anywhere else it is `ERR_AGENT_STATE_INVALID` — and it does not change the departing agent's status, which stays `DEPARTED`. The cascade is conditional: every merchant owned by the departing agent whose `status` is `PENDING` or `ACTIVE` has its `owning_agent_id` re-pointed to the target and its `version` bumped, while merchants whose `status` is `ATTRITED` deliberately keep the departing agent for audit. Afterwards `portfolio_merchant_count`, `portfolio_attrition_bps` and `residual_hold` are recomputed on both agents, in that order and with the departing agent evaluated before the receiving one, and both agents' `version` values are bumped — once each, even when the departing agent owned no transferable merchant at all. The resource returned in `data` is the departing agent, not the target and not the merchants that moved.
