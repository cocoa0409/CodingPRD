# Retail FX & Travel Money API — Product Requirements Document

## 1. Introduction

A retail foreign-exchange network sells and buys physical banknotes across a chain of branches, and almost every hard problem in the business is a problem of *reconciling paper with policy*. Notes are a conserved physical quantity: a note that leaves a till has to appear somewhere else — in a customer's hand, in a quarantine tray, on an armored-transport manifest, or in a write-off. At the same time the money value of that same paper moves continuously with the wholesale market, so the same drawer is worth a different number of dollars at nine in the morning than at four in the afternoon. Branch staff need a system that prices a deal in seconds at the counter, while head-office treasury needs the same system to answer, at any instant, how much foreign cash each vault is carrying against its ceiling, how much rate-lock liability the network has written, and which customers are drifting toward a reportable pattern.

This document specifies the Retail FX & Travel Money API, the service of record for that network. It governs seasonal inventory planning per branch and travel corridor down to the denomination mix; wholesale-rate ingestion and the derivation of retail buy and sell rates from spreads and a tiered commission schedule; the physical cash chain, including armored routes, vault ceilings and the automatic repatriation of surplus currency; customer identification, threshold reporting and structuring detection; counterfeit, damaged and obsolete-note handling; buy-back guarantee products with fixed-term rate locks; the special handling of exotic and export-restricted currencies; and the disclosure-controlled rate board that is legally required to be displayed at the counter.

Two design commitments run through everything that follows. First, **every monetary and rate quantity is an integer** — there are no floating-point amounts anywhere in this API, and the rounding step of every formula is pinned so that two correct implementations produce byte-identical numbers. Second, **derived state is never supplied by a client**: vault utilisation, branch posture, risk scores, liabilities and manifests are recomputed by the server at the end of the request that disturbed them, and the order of that recomputation is part of the contract rather than an implementation detail.

## 2. Global Specifications & System-Wide Principles

This section fixes the rules that hold for every endpoint in the service: how callers identify themselves, what a response looks like, how lists are paged, how numbers are rounded, and the order in which a bad request is refused.

### 2.1. Counter Staff, Head Office and Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they are acting. If either header is absent or present but empty, or if `X-User-Role` is not exactly one of the six role names below — the comparison is case-sensitive — the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). The six roles are `PlatformAdmin`, `TreasuryOfficer`, `BranchManager`, `BranchTeller`, `ComplianceOfficer` and `Customer`. Once the caller is authenticated, the role is matched against the set of roles permitted on the endpoint being called; a role outside that set is refused with `ERR_UNAUTHORIZED` (HTTP 403). This permission check runs **before** any identifier in the path is resolved, so an unauthorized role calling an endpoint with a non-existent resource id receives 403 and never 404.

The roles divide along conventional lines of segregation of duties. A `PlatformAdmin` operates the platform itself: it registers branches, currency profiles and armored routes, and it alone drives the logical clock. A `TreasuryOfficer` sits in head office, records wholesale quotes, drafts and publishes rate cards, reviews branch stocking plans and runs cash logistics — scheduling, dispatching and reconciling shipments. A `BranchManager` runs a single branch: opening currency positions, drafting, submitting and activating stocking plans, assessing detained notes, reversing settled deals and receiving shipments. A `BranchTeller` works the counter — on-boarding customers, quoting, authorising, settling and voiding deals, detaining suspect notes and redeeming buy-back guarantees, the last of which is the teller's exclusive capability. A `ComplianceOfficer` forms the second line of defence: it records compliance decisions on transactions, files and amends regulatory reports and controls customer compliance holds, and it is deliberately barred from quoting, authorising or settling anything. Position creation, shipment raising and buy-back cancellation are shared between `TreasuryOfficer` and `BranchManager`; customer on-boarding, quoting, authorising, settling, voiding, buy-back issuance and note detention are shared between `BranchManager` and `BranchTeller`.

Identity semantics differ between the staff roles and the customer role, and the distinction matters for ownership checks. When `X-User-Role` is `PlatformAdmin`, `TreasuryOfficer`, `BranchManager`, `BranchTeller` or `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it wherever an audit trail demands it — as `quoted_by_user_id`, `authorized_by_user_id`, `settled_by_user_id`, `submitted_by_user_id`, `reviewed_by_user_id` or `assessed_by_user_id` — and compares one recorded operator identifier against another when segregation of duties requires it, but it never compares an opaque identifier to any row's `id`. When `X-User-Role` is `Customer`, by contrast, `X-User-ID` is the `id` of the acting customer row; ownership checks on any resource that references a customer compare that resource's `customer_id` to `X-User-ID`. The `Customer` role is read-only in this API: it may consult the public rate board of a branch and the currency catalogue, and nothing else. Because none of those three reads — the branch rate board, the single-currency read and the currency list — references a customer row, the acting `X-User-ID` is not resolved on them: it is neither looked up nor required to name an existing `Customer` row, so those reads succeed for any non-empty identifier. Every money-moving call is made by branch staff on the customer's behalf.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the real wall-clock instant at which the response was built, and it is the one timestamp in this service that does **not** read the logical clock of §2.4.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0. A value outside those bounds is a malformed request and is refused with `ERR_INVALID_REQUEST` (HTTP 400), as is a value that is not a decimal integer; a `limit` or `offset` supplied as an empty string is instead treated as absent and its default applies.

Unless a specific list endpoint says otherwise, results are ordered by `created_at` ascending; because the logical clock stands still between clock calls those stamps tie constantly, and rows sharing a `created_at` are ordered by the sequence in which the server created them, oldest first. List responses populate four pagination fields inside `meta`: `limit` and `offset` echo the effective values applied to the query, `total_count` reports the number of rows matching the filters before paging, and `has_more` is true when rows remain beyond the current page. Single-resource reads do not carry those four fields. Every documented list filter is an exact-match filter and every one of them is optional: a filter supplied as an empty string is ignored, a query parameter the endpoint does not document is ignored, and a boolean filter is honoured only for the values `true`, `1`, `false` and `0` compared case-insensitively — any other value leaves that filter unapplied rather than refusing the request.

### 2.4. Resource Identity, Audit Stamps and the Logical Trading Clock

Every persisted resource carries an `id` that is a server-minted UUID with no type prefix, and a `created_at` timestamp in ISO 8601 UTC form with three fractional digits. Most resources additionally carry an `updated_at` timestamp in the same format and an integer `version` that starts at 1 when the row is created and increases by exactly one on every mutation of that row; `updated_at` is refreshed at the same moment. The bump is counted per request rather than per write: a request that touches the same row more than once — directly and then again through a cascade, or through two cascades at once — raises that row's `version` by exactly one in total, and a row created inside a request is never bumped again by a cascade later in that same request, so a newly created row is always returned at `version` 1. `Branch`, `RateCard`, `InventoryPosition`, `InventoryPlan`, `Customer`, `ExchangeTransaction`, `BuybackContract`, `NoteAssessment`, `ComplianceReport` and `CashShipment` all carry the full set. Four reference resources are deliberately immutable reference data and carry only `id` and `created_at`, with **no** `updated_at` and **no** `version` field at all: `CurrencyProfile`, `WholesaleRate`, `TravelCorridor` and `ArmoredRoute`. A client must not expect either field on those four, and the server must not emit them.

Clients never supply `id`, `created_at`, `updated_at` or `version` on a create call, and no endpoint accepts a direct write to a computed field. A field supplied explicitly as `null` is treated exactly as an absent field: an optional input falls back to its documented default and a required input is refused as malformed. Server-stamped instants — `created_at`, `updated_at`, `published_at`, `quote_expires_at`, `authorized_at`, `settled_at`, `reversed_at`, `rate_lock_expires_at`, `filed_at`, the board's `as_of` and a report's window bounds — are written in the canonical three-fractional-digit `Z` form, whereas an ISO 8601 instant supplied by a client is stored and echoed back byte-for-byte as the client wrote it, including a non-UTC offset or an omitted seconds field, and is converted to UTC only for comparison.

Path identifiers are resolved strictly left to right. The branch rate-board read, which nests a currency-board projection beneath a branch identifier, therefore resolves the branch first: a request naming a branch that does not exist fails with `ERR_BRANCH_NOT_FOUND` (HTTP 404) before anything else about the request is considered. The same left-to-right discipline governs foreign-key identifiers inside a request body, which are resolved in the declaration order of the endpoint's input list; the first one that fails to resolve determines the error. Depending on which identifier failed, the code is one of `ERR_BRANCH_NOT_FOUND`, `ERR_CURRENCY_NOT_FOUND`, `ERR_WHOLESALE_RATE_NOT_FOUND`, `ERR_CORRIDOR_NOT_FOUND`, `ERR_ROUTE_NOT_FOUND`, `ERR_RATE_CARD_NOT_FOUND`, `ERR_POSITION_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_CUSTOMER_NOT_FOUND`, `ERR_TRANSACTION_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_REPORT_NOT_FOUND` or `ERR_SHIPMENT_NOT_FOUND`, each of which is HTTP 404.

Time in this service is a **logical clock**, not wall-clock time. Every window, expiry, aggregation window and calendar-day bucket in this specification reads that logical clock. At start-up the logical clock reads exactly `2026-08-01T00:00:00Z`, and it stays at that instant — never falling back to real wall-clock time — until a `PlatformAdmin` moves it. The clock-setting capability accepts a single `current_utc` instant, sets the logical clock to it, and returns an object carrying exactly two fields — `current_utc`, echoed back byte-for-byte as it was supplied, and `expired_contract_count`. Any well-formed instant is accepted, including one equal to or earlier than the current reading, so the clock may be wound backwards as freely as forwards. Advancing the clock is not a passive act: it sweeps every buy-back contract whose rate lock has fallen into the past into an expired state and recomputes the affected branches' outstanding rate-lock liability, as §3.7 describes; `expired_contract_count` reports how many contracts the sweep expired.

### 2.5. Integer Money, Micro-Rates and Rounding

There is exactly one rounding rule in this API: **round half up**, applied to a non-negative magnitude, producing an integer. Wherever this document says a value is rounded, it means rounded half up to a whole unit of the stated denomination — whole US cents for money, whole basis points for ratios, whole minor units for foreign cash, whole micros for rates. No value in any response is a decimal fraction.

Three integer scales are in play and they must not be confused. **US amounts** are always whole cents of the branch settlement currency; `home_currency_code` on a branch is the settlement currency of the till, defaults to `USD`, and is fixed at `USD` throughout this service. **Foreign cash quantities** are always whole *minor units* of the foreign currency — the smallest indivisible unit implied by the currency's ISO 4217 exponent, which is recorded as `minor_unit_digits` and is 0 for a currency such as JPY, 2 for EUR, CHF and USD, and 3 for BHD; `minor_unit_digits` is accepted only as an integer from 0 to 4 inclusive, and it is recorded for reference alone — no formula in this service divides or multiplies by it. **Rates** are expressed in *micros*: a rate value is the number of foreign-currency minor units obtained per one US cent, multiplied by 1,000,000. Under that convention a euro mid rate of 0.92 EUR per USD is carried as 920000 and a yen mid rate of 147.5 JPY per USD is carried as 1475000, and a **larger** rate number always means **more foreign currency per dollar**. Consequently converting foreign minor units into US cents means multiplying the minor-unit quantity by 1,000,000, dividing by the rate in micros, and rounding half up; converting a US-cent amount into foreign minor units means multiplying by the rate and dividing by 1,000,000.

Ratios and percentages are carried in **basis points**, where 10000 basis points is exactly one hundred percent and 10000 is therefore the neutral multiplier. A spread of 250 basis points is two and a half percent; a demand index of 10000 is baseline demand.

### 2.6. The Vault Posture Gate

Each branch declares a `vault_limit_usd_cents` — the maximum US-dollar-equivalent value of foreign cash the vault may hold, which must be at least 100000 cents (one thousand dollars). Against that ceiling the server continuously maintains three derived fields on the branch. `vault_usd_equivalent_cents` is the sum of `usd_equivalent_cents` over every one of the branch's inventory positions whose `status` is `OPEN`; positions whose `status` is `CLOSED` contribute nothing. Where an operation has to test a *post-credit* valuation before it commits the credit, the projection is built to exactly that shape: the position being credited is re-valued in one single conversion from its post-credit `total_minor_units` — never by adding a separately-rounded increment to its stored `usd_equivalent_cents` — and that projected figure is summed with the stored `usd_equivalent_cents` of the branch's other `OPEN` positions. `vault_utilization_bps` is 10000 multiplied by `vault_usd_equivalent_cents`, divided by `vault_limit_usd_cents`, rounded half up to a whole basis point. And `posture` is a three-valued gate derived from that utilisation: `OPEN` while utilisation is below 9000 basis points, `RESTRICTED` when utilisation is at least 9000 basis points and at most 10000 basis points, and `FROZEN` only when utilisation is strictly above 10000 basis points. The band edges are inclusive on `RESTRICTED` in both directions: exactly 9000 basis points is `RESTRICTED`, exactly 10000 basis points is still `RESTRICTED` and not `FROZEN`, and 10001 basis points is `FROZEN`.

`posture` is never accepted in a request body. It is recomputed at the end of every request that mutated any inventory position belonging to the branch, and the recomputation may move it in either direction: `OPEN → RESTRICTED`, `OPEN → FROZEN`, `RESTRICTED → FROZEN`, `RESTRICTED → OPEN`, `FROZEN → RESTRICTED` and `FROZEN → OPEN` are all reachable. Every one of those six moves writes the new value to `posture`, refreshes the branch's `updated_at` and increases the branch's `version` by one. The recomputation itself writes the branch row only when it actually changed something: when `vault_usd_equivalent_cents`, `vault_utilization_bps`, `posture` and `repatriation_pending` all come back equal to the values already stored — as they do when a mutation moved only quarantined or written-off notes — the recomputation leaves the branch's `updated_at` and `version` untouched. An operation that stamps the branch for its own reasons, such as opening a position or settling a deal, bumps the branch's `version` regardless of whether the recomputation moved anything.

Posture is a gate over child operations, and it bites in three distinct ways. A `FROZEN` branch refuses authorisation of a deal, settlement of a deal, activation of a stocking plan and redemption of a buy-back contract, in each case with `ERR_BRANCH_POSTURE_FROZEN` (HTTP 409). A `RESTRICTED` branch still permits cash to leave the vault but refuses any operation that would *add* foreign cash to it: authorising a deal whose `direction` is `BUY_FX_FROM_CUSTOMER`, and raising a `REPLENISHMENT` shipment, are both refused with `ERR_BRANCH_POSTURE_RESTRICTED` (HTTP 409). Separately from posture, the branch's administrative `status` — one of `ACTIVE`, `SUSPENDED` or `CLOSED`, set at creation and never mutated afterwards — must be `ACTIVE` for a deal to be quoted or authorised, for a rate card to be created, or for a stocking plan to be drafted; otherwise the call is refused with `ERR_BRANCH_NOT_ACTIVE` (HTTP 409).

Arriving at `RESTRICTED` or `FROZEN` is also a *trigger*, not merely a label. Whenever a posture recomputation lands the branch on `RESTRICTED` or `FROZEN` — that is, on the `OPEN → RESTRICTED`, `OPEN → FROZEN`, `RESTRICTED → FROZEN` moves — and the branch's `repatriation_pending` flag is currently false, and at least one of the branch's positions has `status` `OPEN` with a positive `total_minor_units`, the server raises exactly one surplus-repatriation shipment for the branch and sets `repatriation_pending` to true. The manifest of that shipment is computed by the surplus waterfall described in §3.9. When `repatriation_pending` is already true, no second automatic shipment is raised, which is why the `RESTRICTED → FROZEN` move normally raises nothing. Those three are the only triggering moves: a `FROZEN → RESTRICTED` recovery still leaves the branch standing on `RESTRICTED`, yet because it arrives from `FROZEN` it raises nothing even when `repatriation_pending` is false. The reverse moves are asymmetric on purpose: recovering to `OPEN` from either `RESTRICTED` or `FROZEN` leaves any already-raised automatic repatriation shipment exactly where it is and leaves `repatriation_pending` unchanged. `repatriation_pending` reads as true for precisely as long as the branch has a repatriation-direction shipment whose `status` is `REQUESTED`, `SCHEDULED` or `IN_TRANSIT`.

### 2.7. Reserve-and-Truncate Writes and Version Pinning

Two create operations in this service are *reserve-and-truncate*: they do not merely add a row, they silently retire an incumbent row that the caller may never have read. Both are therefore protected by optimistic concurrency against a pinned parent version, and both reject a stale pin deterministically rather than performing the retirement.

The first is rate-card creation. A `POST /rate-cards` request must carry `expected_branch_version` as a mandatory, non-optional field whose value is the `version` of the target branch as the client last observed it. It must be an integer of at least 1; a smaller value, or one that is not an integer, is malformed and is refused with `ERR_INVALID_REQUEST` at rank 4 rather than treated as stale. If a well-formed value does not equal the branch's current `version`, the request is rejected with `ERR_STALE_BRANCH_VERSION` (HTTP 412). The reason is that creating a card may legitimately truncate the branch's incumbent open-ended published card for the same currency and move it to `SUPERSEDED`; a writer working from a stale view of the branch would otherwise cut short a board window it never saw.

The second is buy-back issuance. A `POST /buyback-contracts` request must carry `expected_customer_version` as a mandatory, non-optional field whose value is the `version` of the target customer as the client last observed it. Like the rate-card pin it must be an integer of at least 1; a smaller value, or one that is not an integer, is malformed and is refused with `ERR_INVALID_REQUEST` at rank 4 rather than treated as stale. If a well-formed value does not equal the customer's current `version`, the request is rejected with `ERR_STALE_CUSTOMER_VERSION` (HTTP 412). Issuance legitimately cancels the customer's incumbent contract in the same currency and stamps the supersession pointer on it, so a writer holding a stale customer view would otherwise cancel a rate lock it never read.

No other endpoint in this service accepts a version-pinning field. Neither `expected_branch_version` nor `expected_customer_version` may appear on any other request, and no other write is version-checked.

Both pins are evaluated **after** the parent row has been confirmed to exist and **after** the target-state checks of the operation have passed. A request that both cites a stale version and violates a state precondition therefore reports the state error, not the 412.

### 2.8. The Order in Which a Request Is Refused

A single request can violate several rules at once, and which error the caller sees is part of the contract. Checks are grouped into thirteen ranks and evaluated strictly in rank order; the first rank that produces a violation determines the response, and no lower rank is consulted. Within this document, "rank 1" is checked first and "rank 13" last.

**Rank 1 — authentication.** Both `X-User-Role` and `X-User-ID` are present and `X-User-Role` is one of the six declared roles, on every endpoint without exception. Otherwise `ERR_UNAUTHENTICATED` (401).

**Rank 2 — authorization.** The acting role appears in the called endpoint's permitted-role list, on every endpoint without exception, and evaluated before any path identifier is resolved. Otherwise `ERR_UNAUTHORIZED` (403).

**Rank 3 — existence.** Three checks share this rank. Every identifier in the request path resolves to a live row, checked left to right, on every endpoint that carries a path identifier. Every foreign-key field in the request body resolves to a live row, checked in the declaration order of the endpoint's input list, on every endpoint whose input carries a foreign key. And every `currency_code` in the request body — including each entry's `currency_code` inside `target_lines` — equals an existing currency profile's `iso_code`, which applies to `POST /wholesale-rates`, `POST /travel-corridors`, `POST /rate-cards`, `POST /inventory-positions`, `POST /inventory-plans`, `POST /inventory-plans/{id}/submit`, `POST /exchange-transactions` and `POST /cash-shipments`, failing with `ERR_CURRENCY_NOT_FOUND` (404). The other two produce the entity-specific 404 codes listed in §2.4. These existence checks are not hoisted above rank 4 wholesale, though: an endpoint reads and validates its declared body fields in declaration order, so a rank-4 malformedness in a field declared *before* a foreign-key or `currency_code` reference is reported as `ERR_INVALID_REQUEST` even though that later reference resolves to no live row, and a foreign-key field that is itself absent or not a non-empty string is likewise reported as `ERR_INVALID_REQUEST` rather than as its 404. Rank 3 beats rank 4 in the ordinary case, where the unresolvable reference is declared earlier than the malformed field.

**Rank 4 — request well-formedness**, on every write endpoint, failing with `ERR_INVALID_REQUEST` (400). This rank covers: required input fields present; every enum value inside its declared domain; every integer inside its declared range; arrays non-empty where a non-empty array is required and free of duplicate denominations; `effective_to` strictly after `effective_from`; `season_end_date` strictly after `season_start_date`; `window_end` strictly after `window_start`; `export_limit_minor_units` non-null exactly when `currency_class` is `RESTRICTED` and null in every other case; `id_document_number` and `id_document_expiry` both present exactly when `id_document_type` is present; and any requested, returned, manifested or delivered denomination that is absent from the currency profile's `standard_denominations` — the check applies alike to `requested_denominations` on a quote, `returned_denominations` on a redemption, `manifest_denominations` on a shipment request and `delivered_denominations` on an arrival, and only the `opening_denomination_mix` of a position is exempt from it. Types are taken strictly at this rank: an integer field accepts only a JSON integer, so a boolean or a numeric string such as `"100"` is malformed, and a required string field accepts only a non-empty string. Three natural-key clashes also land at this rank rather than at rank 5, each refused with `ERR_INVALID_REQUEST`: a duplicate `iso_code` on `POST /currencies`, a duplicate `code` on `POST /travel-corridors` and a duplicate `code` on `POST /armored-routes` — only the branch-code clash of `POST /branches` carries a dedicated 409.

**Rank 5 — state preconditions on the target row**, on every state-transition endpoint, HTTP 409. The target row must be in a state the requested transition leaves from, producing whichever of `ERR_RATE_CARD_NOT_DRAFT`, `ERR_PLAN_INVALID_STATE`, `ERR_TRANSACTION_NOT_QUOTED`, `ERR_TRANSACTION_NOT_AUTHORIZED`, `ERR_TRANSACTION_NOT_SETTLED`, `ERR_TRANSACTION_NOT_VOIDABLE`, `ERR_CONTRACT_NOT_REDEEMABLE`, `ERR_CONTRACT_NOT_CANCELLABLE`, `ERR_ASSESSMENT_ALREADY_ASSESSED`, `ERR_REPORT_INVALID_STATE`, `ERR_SHIPMENT_INVALID_STATE` or `ERR_COMPLIANCE_DECISION_FINAL` matches the operation. Three cross-row uniqueness rules behave as state preconditions and sit at the same rank, also HTTP 409: at most one buy-back contract per origin transaction (`ERR_CONTRACT_ALREADY_ISSUED` on `POST /buyback-contracts`), at most one inventory position per branch-and-currency pair (`ERR_POSITION_ALREADY_EXISTS` on `POST /inventory-positions`), and a unique branch `code` (`ERR_DUPLICATE_BRANCH_CODE` on `POST /branches`).

**Rank 6 — optimistic concurrency**, on `POST /rate-cards` and `POST /buyback-contracts` only, HTTP 412: `expected_branch_version` equals the branch's current `version`, and `expected_customer_version` equals the customer's current `version`, producing `ERR_STALE_BRANCH_VERSION` or `ERR_STALE_CUSTOMER_VERSION`. Because this rank sits below rank 5, a stale pin against an already-superseded parent still reports the state error first.

**Rank 7 — branch gates**, all HTTP 409. The branch's administrative `status` must be `ACTIVE` on `POST /exchange-transactions`, `POST /exchange-transactions/{id}/authorize`, `POST /rate-cards` and `POST /inventory-plans`, otherwise `ERR_BRANCH_NOT_ACTIVE`. The branch's `posture` must not be `FROZEN` on `POST /exchange-transactions/{id}/authorize`, `POST /exchange-transactions/{id}/settle`, `POST /inventory-plans/{id}/activate` and `POST /buyback-contracts/{id}/redeem`, otherwise `ERR_BRANCH_POSTURE_FROZEN`. And the branch's `posture` must not be `RESTRICTED` when the operation would add foreign cash to the vault — a deal whose `direction` is `BUY_FX_FROM_CUSTOMER` on `POST /exchange-transactions/{id}/authorize`, or a `REPLENISHMENT` shipment on `POST /cash-shipments` — otherwise `ERR_BRANCH_POSTURE_RESTRICTED`.

**Rank 8 — compliance and identification safety.** Six checks live here. On `POST /exchange-transactions/{id}/authorize`: the customer must have a complete identification document on file — `id_document_type`, `id_document_number` and `id_document_expiry` all non-null — whenever `quoted_usd_gross_cents` is at least 100000 cents (one thousand dollars), otherwise `ERR_CUSTOMER_ID_REQUIRED` (422); whenever the customer has an `id_document_expiry` on file at all it must be strictly after the logical clock, and an expired document blocks authorisation at *every* amount independently of the one-thousand-dollar identification floor, otherwise `ERR_CUSTOMER_ID_EXPIRED` (422); and selling a `RESTRICTED`-class currency requires the customer's `travel_document_reference` to be non-null, otherwise `ERR_RESTRICTED_CURRENCY_DOC_REQUIRED` (422). Also at this rank: `compliance_hold_active` on the customer must be false on both `POST /exchange-transactions/{id}/authorize` and `POST /buyback-contracts`, otherwise `ERR_CUSTOMER_COMPLIANCE_HOLD` (409); a transaction's `compliance_status` must not be `BLOCKED` on both `POST /exchange-transactions/{id}/settle` and `POST /exchange-transactions/{id}/reverse`, otherwise `ERR_TRANSACTION_COMPLIANCE_BLOCKED` (409); and a hold release on `POST /customers/{id}/compliance-hold` is refused while the customer still has a structuring-suspicion report whose `status` is `DRAFT` or `AMENDING`, with `ERR_STRUCTURING_REPORT_PENDING` (409).

**Rank 9 — segregation of duties**, HTTP 403. The acting `X-User-ID` must differ from the user who performed the previous step of the same workflow. On `POST /inventory-plans/{id}/review` a reviewer may not be the plan's own submitter, failing with `ERR_SEGREGATION_OF_DUTIES`. On `POST /exchange-transactions/{id}/settle` the settling user may not be the authorising user once `settled_usd_gross_cents` reaches 500000 cents (five thousand dollars) or more, failing with `ERR_DUAL_CONTROL_REQUIRED`.

**Rank 10 — temporal windows**, all HTTP 409. The logical clock must be at or before `quote_expires_at` on `POST /exchange-transactions/{id}/authorize`, otherwise `ERR_QUOTE_EXPIRED`. The logical clock must be at or before `settled_at` plus 24 hours on `POST /exchange-transactions/{id}/reverse`, otherwise `ERR_REVERSAL_WINDOW_CLOSED`. Publishing on `POST /rate-cards/{id}/publish` must not create two published cards for the same branch-and-currency pair with intersecting windows — board windows are **half-open**, covering `effective_from` inclusively up to but excluding `effective_to`, so two windows that merely touch at an endpoint do not intersect — otherwise `ERR_RATE_WINDOW_OVERLAP`. A shipment window on `POST /cash-shipments/{id}/schedule` must be separated from every other scheduled or in-transit window on the same route by at least 45 minutes — transport windows are **closed**, including both `window_start` and `window_end`, so windows that merely touch *do* conflict — otherwise `ERR_ROUTE_WINDOW_CONFLICT`. The logical clock must have reached `window_start` on `POST /cash-shipments/{id}/dispatch`, otherwise `ERR_SHIPMENT_WINDOW_NOT_OPEN`; and the logical clock must be at or after the corridor's `season_start_date` and strictly before its `season_end_date` on `POST /inventory-plans/{id}/activate`, otherwise `ERR_PLAN_OUTSIDE_SEASON`.

**Rank 11 — business constraints**, all HTTP 422. On `POST /exchange-transactions/{id}/authorize`: `fx_gross_minor_units` must not exceed the currency profile's `export_limit_minor_units` for a `RESTRICTED`-class currency sold to a customer, otherwise `ERR_EXPORT_LIMIT_EXCEEDED`; and selling an `EXOTIC`-class currency requires an `ACTIVE` stocking plan at that branch whose `computed_targets` contain the currency, otherwise `ERR_EXOTIC_PLAN_REQUIRED`. On `POST /rate-cards/{id}/publish`, `disclosure_text_version` must be at least 3, otherwise `ERR_DISCLOSURE_VERSION_UNSUPPORTED`. Six further constraints share this rank across six endpoints: a plan submitted through `POST /inventory-plans/{id}/submit` must carry at least one target line (`ERR_PLAN_NO_TARGET_LINES`); on `POST /buyback-contracts` the origin transaction must be settled with `direction` `SELL_FX_TO_CUSTOMER` and the currency's `buyback_eligible` must be true (`ERR_BUYBACK_NOT_ELIGIBLE`); on `POST /buyback-contracts/{id}/redeem` the returned note value must not exceed `remaining_fx_minor_units` (`ERR_REDEEM_EXCEEDS_REMAINING`); on `POST /cash-shipments/{id}/schedule` the route's `status` must be `ACTIVE` (`ERR_ROUTE_SUSPENDED`) and its `region_code` must equal the branch's `region_code` (`ERR_ROUTE_BRANCH_NOT_SERVICED`); on `POST /note-assessments/{id}/assess` the requested `outcome` must be permitted for the recorded `defect_type` (`ERR_OUTCOME_NOT_PERMITTED_FOR_DEFECT`); and on `POST /exchange-transactions/{id}/reverse` the transaction must not still carry a `buyback_contract_id` (`ERR_BUYBACK_BLOCKS_REVERSAL`).

**Rank 12 — rate-board referential currency**, both HTTP 409. The rate card the operation depends on must have `status` `PUBLISHED` on `POST /exchange-transactions`, `POST /buyback-contracts/{id}/redeem` and `POST /note-assessments/{id}/assess`, otherwise `ERR_RATE_CARD_NOT_PUBLISHED`; on the assess endpoint both of this rank's checks apply only when the requested `outcome` is `EXCHANGED_AT_DISCOUNT`, since the other two outcomes read no rate at all, and settlement is the one card-dependent operation that never reports `ERR_RATE_CARD_NOT_PUBLISHED`. That card's half-open window must cover the instant the operation reads it — at or after `effective_from` and strictly before `effective_to`, with a null `effective_to` meaning the window never closes — on `POST /exchange-transactions`, `POST /exchange-transactions/{id}/settle`, `POST /buyback-contracts/{id}/redeem` and `POST /note-assessments/{id}/assess`, otherwise `ERR_RATE_CARD_NOT_EFFECTIVE`. The instant read is the logical clock at quote time and `authorized_at` at settlement time.

**Rank 13 — fiscal capacity, evaluated last**, all HTTP 422. On `POST /exchange-transactions/{id}/settle`, every requested denomination must already exist on the branch's inventory position for the currency (`ERR_DENOMINATION_NOT_STOCKED`), and for a sale to a customer each denomination's `available_note_count` must be at least the requested `note_count` (`ERR_INSUFFICIENT_INVENTORY`) — the two being tested together, denomination by denomination in ascending face value, rather than as two separate sweeps over the whole request. Whenever cash is being added to the vault — a `BUY_FX_FROM_CUSTOMER` settlement or a buy-back redemption — the post-credit `vault_usd_equivalent_cents` must not exceed `vault_limit_usd_cents`, so this check applies to both `POST /exchange-transactions/{id}/settle` and `POST /buyback-contracts/{id}/redeem` with `ERR_VAULT_LIMIT_WOULD_EXCEED`. And on `POST /cash-shipments/{id}/schedule` the route's summed day capacity must still hold the manifest (`ERR_ROUTE_CAPACITY_EXCEEDED`).

Three precedence conflicts are worth calling out explicitly, because each pair can be violated by one request on one endpoint. On settlement, the rank-5 state error `ERR_TRANSACTION_NOT_AUTHORIZED` beats the rank-13 fiscal error `ERR_INSUFFICIENT_INVENTORY`, so a settle attempt on a quoted-but-unauthorised deal with an empty till reports the state problem. On authorisation, the rank-8 safety error `ERR_CUSTOMER_ID_EXPIRED` beats the rank-11 constraint error `ERR_EXPORT_LIMIT_EXCEEDED`, so an over-limit restricted-currency sale to a customer with a lapsed passport reports the document problem. On shipment scheduling, the rank-10 temporal error `ERR_ROUTE_WINDOW_CONFLICT` beats the rank-13 fiscal error `ERR_ROUTE_CAPACITY_EXCEEDED`, so a window that both crowds a neighbour and blows the day's capacity reports the window conflict.

### 2.9. Cascade Discipline

Several operations in this service mutate more than one row, and the *order* of the resulting recomputation is fixed. The canonical inventory cascade runs in four hops and always in this sequence: first the affected inventory position's `denomination_mix` note counts are adjusted; second that position's `total_minor_units`, `quarantined_minor_units` and `usd_equivalent_cents` are recomputed from the new mix; third the branch's `vault_usd_equivalent_cents` and `vault_utilization_bps` are recomputed from the position totals; and fourth the branch's `posture` is re-derived and may move per §2.6 — which, as a fifth hop, may itself raise an automatic repatriation shipment and set `repatriation_pending`. An implementation that recomputes the branch before the position, or that skips the posture re-derivation because the utilisation band did not appear to change, will diverge.

Each entry of a position's `denomination_mix` is an object carrying `denomination_minor_units`, `available_note_count`, `quarantined_note_count` and `written_off_note_count`, and the array is always ordered by `denomination_minor_units` ascending. Only `available_note_count` feeds `total_minor_units`; quarantined and written-off notes are excluded from it and therefore from vault valuation entirely. The invariant that `total_minor_units` equals the sum, over the mix, of each entry's `denomination_minor_units` multiplied by its `available_note_count` must hold after **every** mutation — it is the conserved physical-cash quantity of this system. Likewise `quarantined_minor_units` equals the sum, over the mix, of each entry's `denomination_minor_units` multiplied by its `quarantined_note_count`. The mix grows on demand: where a mutation names a denomination the mix does not yet carry — as a buy-back redemption or a shipment arrival may — a fresh entry for that denomination is appended with all three of its counters at 0 before the adjustment is applied, and the array is re-sorted into ascending order. Settlement is the one path that refuses an unknown denomination outright instead of growing the mix, with `ERR_DENOMINATION_NOT_STOCKED`.

The `usd_equivalent_cents` of a position is `total_minor_units` multiplied by 1,000,000, divided by the selected wholesale mid rate in micros for the position's `currency_code`, rounded half up to whole cents. This valuation is refreshed on every mutation of the mix, whichever operation caused it: position creation, deal settlement, deal reversal, shipment arrival, note quarantine, note assessment or buy-back redemption.

Selecting "the" wholesale mid rate is itself a pinned rule, used everywhere a valuation needs a mid rate — position valuation, shipment manifest valuation and the vault cap inside inventory planning. The candidates are all wholesale-rate rows whose `currency_code` equals the currency being valued and whose `effective_at` is at or before the logical clock; future-dated quotes are excluded. If that candidate set is empty the operation fails with `ERR_WHOLESALE_RATE_NOT_FOUND` (HTTP 404). Otherwise the candidates are ordered by `effective_at` descending and, where two share the same `effective_at`, by `created_at` descending, with a remaining tie — the normal case, since the logical clock stands still between clock calls — broken by the sequence in which the server created the rows, newest first; the first candidate's `mid_rate_micros` is used — so the later-recorded of two simultaneously-effective quotes wins, and the row's `id` never participates in the ordering. No rounding happens at this step; the value is an integer number of micros already.

### 2.10. Currency Handling Classes and the Disclosure Regime

A currency profile is the network's reference record for one ISO 4217 currency and it is immutable once written. `iso_code` is exactly three uppercase letters and is unique across the catalogue; it is the natural key that every other resource's `currency_code` field resolves against, which is why a currency is never referenced by UUID. `display_name` carries the board name of the currency, such as Euro. `standard_denominations` is an array of between one and eight integers, each at least 1, listed in strictly ascending order, giving the face value in minor units of each note the network handles — for the euro, for example, values of 500, 1000, 2000, 5000 and 10000 minor units. Any denomination cited in a deal, a redemption or a manifest must be one of these values.

`currency_class` divides the catalogue into three handling classes that gate both transaction eligibility and inventory planning. A `MAJOR` currency is unconstrained. An `EXOTIC` currency may only be sold at a branch that has an active stocking plan naming it, and its planning target is capped at 5,000,000 minor units. A `RESTRICTED` currency is subject to a per-transaction physical export cap recorded in `export_limit_minor_units`, and its planning target is capped at twice that export limit. `export_limit_minor_units` is required — that is, non-null — exactly when `currency_class` is `RESTRICTED`, and must be null for `MAJOR` and `EXOTIC` currencies; violating either half of that rule is a malformed request. Two further flags complete the profile: `buyback_eligible`, which defaults to false and, while false, bars any buy-back guarantee from being written in that currency; and `damaged_note_recovery_bps`, which defaults to 6500 basis points, is constrained to the range from 0 to 10000 inclusive, and gives the proportion of a damaged note's US face value the network pays back when the note is exchanged at a discount.

The rate board is a regulated display, not just a data structure. Each board line is a rate card whose `board_display_label` is the exact text shown on the physical board for that currency line, and whose `disclosure_text_version` identifies the version of the consumer-disclosure wording printed beneath the board. `disclosure_text_version` must be at least 1 to be accepted at all, but a card may only be published once its `disclosure_text_version` is at least 3 — the minimum version the current disclosure regime recognises. The board read for a branch is a computed projection rather than a stored row: it returns the requesting branch's `branch_id`, an `as_of` instant equal to the current logical clock, a `line_count`, the `min_disclosure_text_version` being displayed, and a `lines` array holding one entry per currency whose published card's window covers the clock. The `lines` array is ordered by `currency_code` ascending and each entry carries exactly nine fields — `currency_code`, `rate_card_id`, `board_display_label`, `buy_rate_micros`, `sell_rate_micros`, `commission_schedule_code`, `disclosure_text_version`, `effective_from` and `effective_to` — copied from the covering card; `min_disclosure_text_version` is the smallest `disclosure_text_version` among the emitted lines and is 0 when there are none. The read accepts an optional `currency_code` filter to narrow the projection to a single line; that filter is a plain match against each candidate card and is never resolved against the currency catalogue, so an unknown code simply yields a board with no lines rather than `ERR_CURRENCY_NOT_FOUND`. It is the one read a `Customer` may perform against a branch.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Network

Before a single note changes hands, a `PlatformAdmin` populates the network's three pieces of static furniture: the branches, the currency catalogue and the armored-transport routes.

Registering a branch means declaring its identity and its vault ceiling. The payload supplies a `code` of between 1 and 16 characters that must be unique across all branches — a repeat is refused with `ERR_DUPLICATE_BRANCH_CODE` — together with a human-readable `name`, a `region_code`, and the `vault_limit_usd_cents` ceiling, which must be at least 100000. The `region_code` is not decorative: it names the armored-transport service region the branch sits in, and a shipment can only ever be scheduled onto a route whose own `region_code` matches it. Two optional inputs round out the call: `home_currency_code`, the settlement currency of the till, which defaults to `USD` and is fixed at `USD` throughout this service — any non-empty string is nevertheless accepted and stored verbatim, since the value is neither resolved against the currency catalogue nor forced back to `USD`, and no formula reads it; and `status`, one of `ACTIVE`, `SUSPENDED` or `CLOSED`, which defaults to `ACTIVE` and is never mutated after creation. A freshly registered branch begins with `posture` `OPEN`, `vault_usd_equivalent_cents` 0, `vault_utilization_bps` 0, `buyback_liability_usd_cents` 0, `repatriation_pending` false and `version` 1. Branches can subsequently be read individually — the read exposes the derived utilisation, posture and buy-back liability — or listed with optional `region_code`, `status` and `posture` filters.

Armored routes are registered the same way and by the same role. A route carries a unique `code`, the `carrier_name` of the operator, the `region_code` it serves, and a `daily_capacity_usd_cents` of at least 1 that caps the total manifest value the route may carry across every transport window beginning on a single UTC calendar day. A route's `status` is either `ACTIVE` or `SUSPENDED`, defaults to `ACTIVE`, and — like a branch's administrative status — is set once at creation and never mutated; a suspended route refuses to accept new shipment scheduling. Routes are readable individually and listable with optional `region_code` and `status` filters.

The currency catalogue is described in §2.10; registering an entry is a `PlatformAdmin` operation whose payload supplies `iso_code`, `display_name`, `minor_unit_digits`, `currency_class` and `standard_denominations`, plus the three optional inputs `export_limit_minor_units`, `buyback_eligible` and `damaged_note_recovery_bps`. Note that a currency profile is addressed by its ISO 4217 code rather than by a UUID, so the single-currency read takes the three-letter code. Currency profiles may be listed with optional `currency_class` and `buyback_eligible` filters, and both the individual read and the list are among the very few surfaces a `Customer` may touch.

### 3.2. The Wholesale Feed and the Retail Board

Head office feeds the network its raw prices. A `TreasuryOfficer` records a wholesale quote for one currency by supplying `currency_code`, the `mid_rate_micros` mid rate — an integer of at least 1, expressed in the micros convention of §2.5 — the `effective_at` instant from which the quote may be cited, and a `source_code` of either `REUTERS_MID` or `INTERBANK_CLOSE` recording the quote's provenance. Wholesale quotes are immutable: correcting a price means recording a new row, never editing an old one, and the new row becomes eligible for mid-rate selection the moment the logical clock reaches its `effective_at`. Quotes may be read individually or listed with optional `currency_code` and `source_code` filters; the wholesale list is the one collection in this service that departs from the default ordering, returning the newest `effective_at` first, with two quotes sharing an `effective_at` ordered by `created_at` descending and a remaining tie broken by creation sequence descending, so the later-recorded row is listed first.

Turning a wholesale mid into a counter price is what a rate card does. Drafting one is a `TreasuryOfficer` act against an `ACTIVE` branch, and the payload names the `branch_id` whose board the card belongs to, the `currency_code` of the line, the `wholesale_rate_id` of the quote the card derives from — whose own `currency_code` must equal the card's, a mismatch being a malformed request refused with `ERR_INVALID_REQUEST` at rank 4, and which is cited directly rather than re-selected, so the card is anchored to exactly that row even if a newer quote has become effective — the two retail spreads `buy_spread_bps` and `sell_spread_bps`, each an integer from 0 to 5000 inclusive, the `board_display_label` printed on the physical board, the `disclosure_text_version`, the `effective_from` instant at which the card's board window opens, and the `expected_branch_version` pin required by §2.7. Two optional inputs complete it: `commission_schedule_code`, which is `STANDARD` or `PREMIUM` and defaults to `STANDARD`, and `effective_to`, the exclusive end of the board window, which defaults to null meaning open-ended and, when supplied, must be strictly after `effective_from`.

Card creation derives the two retail rates once and freezes them on the row. `sell_rate_micros` is the cited quote's mid rate multiplied by the quantity ten thousand minus `sell_spread_bps`, divided by ten thousand, rounded half up to whole micros. `buy_rate_micros` is the same mid rate multiplied by the quantity ten thousand plus `buy_spread_bps`, divided by ten thousand, rounded half up to whole micros. Because a larger rate number means more foreign currency per dollar, the spread-reduced `sell_rate_micros` is the smaller of the two and governs what the branch hands over when it sells foreign notes, while the larger `buy_rate_micros` governs what the branch pays when it takes foreign notes in. The new card is born in `DRAFT` with `published_at` and `superseded_by_rate_card_id` both null.

Creation is also the truncation point. When the branch already holds a card for the same currency whose `status` is `PUBLISHED` and whose `effective_to` is null — that is, an open-ended incumbent — and the new card's `effective_from` is at or after the incumbent's `effective_from`, the incumbent is truncated rather than left running: its `effective_to` is set to the new card's `effective_from`, its `status` moves `PUBLISHED → SUPERSEDED`, and its `superseded_by_rate_card_id` is set to the new card's `id`. `SUPERSEDED` is terminal; a superseded card never returns to the board. Whether or not a truncation occurred, the branch's `version` increases by one on every card creation, and that is precisely the version the `expected_branch_version` pin of the *next* creation must match.

Publishing is a separate step, also by a `TreasuryOfficer`, and it takes no payload. The card must still be in `DRAFT`, otherwise `ERR_RATE_CARD_NOT_DRAFT`; its `disclosure_text_version` must be at least 3, otherwise `ERR_DISCLOSURE_VERSION_UNSUPPORTED`; and its half-open window must not intersect the window of any other `PUBLISHED` card for the same branch and currency, otherwise `ERR_RATE_WINDOW_OVERLAP`. For that last check a null `effective_to` behaves as positive infinity, and because the windows are half-open two cards whose windows merely touch at an endpoint — one ending exactly where the next begins — do **not** intersect and both may be published. The three checks are listed above in narrative order but are evaluated in the rank order of §2.8: the `DRAFT` check first, then the window-overlap check, and the disclosure-version check only once no overlap was found, so a draft that both overlaps an incumbent window and carries a `disclosure_text_version` below 3 reports `ERR_RATE_WINDOW_OVERLAP`. On success the card moves `DRAFT → PUBLISHED` and `published_at` is stamped with the logical clock, after which the card appears on the branch's board for its currency line for as long as the clock sits inside the window. Cards may be read individually, exposing the derived rates and the supersession pointer, or listed with optional `branch_id`, `currency_code`, `wholesale_rate_id`, `superseded_by_rate_card_id` and `status` filters — the list being the reverse-lookup channel for all three of those pointer fields.

### 3.3. Seasonal Stocking: Corridors, Plans and Treasury Review

Travel money is a seasonal business, and the unit of seasonality is the **travel corridor** — one origin/destination pair for one season. A `TreasuryOfficer` registers a corridor with a unique `code`, an `origin_country_code` and `destination_country_code` in ISO 3166-1 alpha-2 form, the `destination_currency_code` naming the corridor's spend currency, a `season` of `SPRING`, `SUMMER`, `AUTUMN` or `WINTER`, a `season_start_date` that opens the season window inclusively, a `season_end_date` that closes it exclusively and must fall strictly after the start, and a `demand_index_bps` from 1 to 50000 inclusive expressing seasonal demand as a multiplier in basis points, where 10000 means baseline demand. On this one endpoint the two country codes are format-checked before `destination_currency_code` is resolved, so a request whose `origin_country_code` or `destination_country_code` is not two uppercase letters reports `ERR_INVALID_REQUEST` even when the cited destination currency does not exist either. Corridors are readable individually and listable with optional `season` and `destination_currency_code` filters.

A `BranchManager` drafts a stocking plan against a corridor by supplying the `branch_id` — whose administrative status must be `ACTIVE` — the `travel_corridor_id`, a `season_days` count from 1 to 366 inclusive giving how many days of demand the plan covers, and optionally `target_lines`, an array of requested lines with one object per currency carrying that line's `currency_code` and its `baseline_daily_minor_units`. Each entry must be an object; its `baseline_daily_minor_units` must be an integer of at least 0, and 0 is a legitimate baseline rather than a malformed one; and two entries naming the same currency are malformed, so the array carries at most one line per currency. Every entry's `currency_code` is resolved against the catalogue — the rank-3 existence check, applied to every entry before any entry's baseline is inspected — so an unknown code reports `ERR_CURRENCY_NOT_FOUND` even when a later entry also carries a malformed baseline. The array is stored normalised into ascending `currency_code` order regardless of the order the client wrote it in, and it may legitimately be left empty at creation and filled in later. A new plan is born in `DRAFT` with `computed_targets` empty, `revision_count` 0, and `submitted_by_user_id`, `reviewed_by_user_id` and `review_note` all null.

Submitting the plan for treasury review moves it `DRAFT → SUBMITTED` and is again a `BranchManager` act; the submit payload may supply a replacement `target_lines` array, which overwrites whatever the plan held. An absent `target_lines` leaves the plan's existing lines exactly as they were, whereas an explicitly empty array is a replacement like any other and is written onto the plan *before* the at-least-one-line check runs — so a submit carrying an empty array both fails with `ERR_PLAN_NO_TARGET_LINES` and leaves the plan holding no target lines, its `status`, `updated_at` and `version` untouched. The plan must currently be in `DRAFT` — otherwise `ERR_PLAN_INVALID_STATE` — it must end up carrying at least one target line, since submitting an empty plan is refused with `ERR_PLAN_NO_TARGET_LINES`, and every line's `currency_code` must resolve to a catalogued currency or the call fails with `ERR_CURRENCY_NOT_FOUND`. On success `submitted_by_user_id` records the acting `X-User-ID` and the per-currency targets are computed.

That computation is the heart of seasonal planning, and it walks the plan's target lines ordered by `currency_code` ascending, emitting one object per line into `computed_targets` — each carrying the line's `currency_code` and its resulting `target_minor_units`, in that same ascending order. For each line, five quantities are derived in sequence. First, a **raw seasonal requirement**: the line's `baseline_daily_minor_units` multiplied by the plan's `season_days`, multiplied by the corridor's `demand_index_bps`, divided by ten thousand, with the result rounded down to a whole minor unit. Second, a **class cap** that depends on the currency's `currency_class`: for a `MAJOR` currency the class cap is the raw seasonal requirement unchanged; for an `EXOTIC` currency it is the lesser of the raw requirement and 5,000,000 minor units; and for a `RESTRICTED` currency it is the lesser of the raw requirement and twice the currency's `export_limit_minor_units`. Third, a **vault cap**: the branch's `vault_limit_usd_cents` multiplied by 2500 and divided by ten thousand — one quarter of the vault ceiling — then converted into foreign minor units by multiplying by the selected wholesale mid rate for that currency and dividing by 1,000,000, with the whole expression rounded down to a whole minor unit. Fourth, a **bounded requirement**: the lesser of the class cap and the vault cap, but never allowed to fall below the largest value in the currency's `standard_denominations`, so that the plan always asks for at least one of the currency's biggest notes. Fifth and last, the bounded requirement is expressed in whole notes of that largest denomination: it is divided by the largest denomination, that quotient is rounded half up to a whole number of notes, and the result is multiplied back by the largest denomination to give `target_minor_units`. Every target is therefore always an exact whole multiple of the currency's largest standard denomination. Four independent inputs — the baseline, the season length, the corridor's demand index and the branch's vault ceiling — interact through that nested pair of bounds, and no single one of them dominates the outcome. Because the vault cap needs a mid rate for every line, a target line naming a currency that has no wholesale quote effective at the logical clock makes the whole call fail with `ERR_WHOLESALE_RATE_NOT_FOUND` (HTTP 404); that failure arises inside the computation rather than from an identifier in the request, so it is reported only after the transition's own state and target-line checks have already passed, and it leaves `computed_targets` and the plan's `status` exactly as they were.

Treasury review is a `TreasuryOfficer` act on a `SUBMITTED` plan, carrying a mandatory `decision` of either `APPROVE` or `REJECT` and an optional `review_note`. The plan must be in `SUBMITTED`, otherwise `ERR_PLAN_INVALID_STATE`, and the reviewing `X-User-ID` must differ from the plan's `submitted_by_user_id` — a manager may not rubber-stamp their own submission, and an attempt to do so is refused with `ERR_SEGREGATION_OF_DUTIES`. An `APPROVE` decision moves the plan `SUBMITTED → APPROVED` and recomputes `computed_targets` a second time by exactly the procedure above, so a plan approved after the branch's vault ceiling or the wholesale rate has moved can legitimately carry different targets than it did at submission. A `REJECT` decision instead sends the plan `SUBMITTED → DRAFT` and increases `revision_count` by one, leaving `computed_targets` holding exactly the figures the submission computed rather than clearing them; the plan may then be revised and resubmitted any number of times, and `revision_count` counts exactly those loops. Either decision writes the reviewer's `X-User-ID` into `reviewed_by_user_id` and stores the supplied `review_note` — writing null when the field is absent, so a later review that omits the note clears the note an earlier one left behind.

Activation is what finally makes a plan operative, and it belongs to the `BranchManager`. The plan must be in `APPROVED`, otherwise `ERR_PLAN_INVALID_STATE`; the branch's `posture` must not be `FROZEN`, otherwise `ERR_BRANCH_POSTURE_FROZEN`; and the logical clock must sit inside the corridor's season window — at or after `season_start_date` and strictly before `season_end_date` — otherwise `ERR_PLAN_OUTSIDE_SEASON`. On success the plan moves `APPROVED → ACTIVE`, which is terminal. Activation does **not** recompute `computed_targets` — unlike submission and approval, it is a pure state move, and the plan goes live carrying exactly the figures the approval left on it. Activation is deliberately **additive**: any other plan of the same branch and corridor that is already `ACTIVE` keeps its state, and none is superseded, so a branch may carry several active plans at once. The operational consequence of activation is narrow and specific: every `EXOTIC`-class currency appearing in the plan's `computed_targets` becomes sellable at that branch, satisfying the exotic-plan requirement described in §3.5. Plans are readable individually and listable with optional `branch_id`, `travel_corridor_id` and `status` filters.

### 3.4. Opening a Currency Position and Keeping the Mix Honest

A branch's stock of one foreign currency lives in a single **inventory position**, and exactly one position may exist per branch-and-currency pair; a second attempt is refused with `ERR_POSITION_ALREADY_EXISTS`. Either a `BranchManager` or a `TreasuryOfficer` may open one, supplying the `branch_id`, the `currency_code`, and an `opening_denomination_mix` array describing the notes going in. The array must be present and non-empty, its `denomination_minor_units` values must be distinct and each at least 1, and each entry's note count may be named either `note_count` or `available_note_count` — when both appear, `note_count` is the one read. Unlike the note counts of a deal, a redemption or a shipment manifest, an opening count of 0 is accepted, so a position may legitimately be opened with denominations stocked but empty; and unlike those arrays, the opening mix is **not** checked against the currency profile's `standard_denominations`, so it may seed a denomination the profile does not list. Each entry of that opening array is expanded into a full mix entry: its `denomination_minor_units` is carried across, its note count becomes the entry's `available_note_count`, and both `quarantined_note_count` and `written_off_note_count` start at 0. The position is born with `status` `OPEN`; the only other possible value is `CLOSED`, and a closed position drops out of the branch's vault valuation entirely — but no operation in this service ever moves a position to `CLOSED`, so a position that has been opened stays `OPEN` for its whole life and the `status` filter on the position list only ever matches `OPEN` rows.

Creating a position immediately runs the four-hop cascade of §2.9: `total_minor_units`, `quarantined_minor_units` and `usd_equivalent_cents` are computed from the seeded mix, the branch's `vault_usd_equivalent_cents` and `vault_utilization_bps` are recomputed, and the branch's `posture` is re-derived — which means that seeding a large opening mix into a branch with a modest ceiling can move the branch straight to `RESTRICTED` or `FROZEN` and raise an automatic repatriation shipment in the very same request. The branch's `version` increases by one, whether or not the recomputation moved any of its derived values. Because that cascade has to value the new stock, opening a position in a currency for which no wholesale quote is yet effective at the logical clock fails with `ERR_WHOLESALE_RATE_NOT_FOUND` (HTTP 404) — reported after the duplicate-position check, since it arises inside the cascade rather than from an identifier in the request — and the position row is nevertheless kept, so a retry once the quote has been recorded is refused with `ERR_POSITION_ALREADY_EXISTS`. Positions may be read individually, exposing the full mix and the USD valuation, or listed with optional `branch_id`, `currency_code` and `status` filters, the list being the reverse-lookup channel for a branch's positions.

### 3.5. The Counter: Quoting, Authorising, Settling, Voiding and Reversing

A retail customer is on-boarded by a `BranchTeller` or a `BranchManager` before any deal can be quoted. The payload supplies the customer's `full_name` exactly as it appears on their identification document and a `nationality_code` in ISO 3166-1 alpha-2 form — exactly two uppercase letters, any other string being malformed; the code is format-checked only and is never resolved against a table. Five further inputs are optional and all default to null: `home_branch_id`, the branch that on-boarded them, which must resolve to a live branch when it is supplied — and resolution is all it is used for, since on-boarding checks neither that branch's administrative `status` nor its `posture` and leaves its `updated_at` and `version` untouched; `id_document_type`, which is one of `PASSPORT`, `NATIONAL_ID` or `DRIVING_LICENCE`; `id_document_number`; `id_document_expiry`; and `travel_document_reference`, a boarding-pass or ticket reference. Identification is treated as a *bundle*: if `id_document_type` is supplied then `id_document_number` and `id_document_expiry` must both be supplied too, and supplying either of the latter without the type is equally malformed. Nothing about identification is enforced at on-boarding beyond that internal consistency; the substantive gates fire later, at authorisation. A new customer starts with `structuring_risk_tier` `NORMAL`, every aggregate at 0, `compliance_hold_active` false and `version` 1. Customers are readable individually — the read exposes both aggregate variants, the score, the derived tier and the hold flag — and listable with optional `home_branch_id`, `structuring_risk_tier` and `compliance_hold_active` filters.

**Quoting.** A teller or manager opens a deal by quoting it against one specific board line. The payload carries the `branch_id` performing the exchange, the `customer_id` of the counterparty, the `rate_card_id` of the board line being quoted — whose own `branch_id` and `currency_code` must both match this deal's, a mismatch on either being malformed and refused with `ERR_INVALID_REQUEST` at rank 4, ahead of the branch's own status gate and of the card's publication and window checks — the `currency_code` of the foreign currency, the `direction`, and a `requested_denominations` array giving the note breakdown of the deal. `direction` is either `SELL_FX_TO_CUSTOMER`, which debits branch inventory while the customer pays US dollars, or `BUY_FX_FROM_CUSTOMER`, which credits branch inventory while the customer receives US dollars. Each entry of `requested_denominations` carries a `denomination_minor_units` face value and a `note_count` of at least 1; the array must contain at least one entry, the denominations within it must be distinct, and each must appear in the currency profile's `standard_denominations`. The branch's administrative status must be `ACTIVE`. The cited card must have `status` `PUBLISHED`, otherwise `ERR_RATE_CARD_NOT_PUBLISHED`, and its half-open window must cover the logical clock, otherwise `ERR_RATE_CARD_NOT_EFFECTIVE`.

Quoting writes five derived money fields and one deadline. `fx_gross_minor_units` is the sum, over every entry of `requested_denominations`, of that entry's `denomination_minor_units` multiplied by its `note_count`. `applied_rate_micros` is taken from the cited card by direction: the card's `sell_rate_micros` for a `SELL_FX_TO_CUSTOMER` deal and its `buy_rate_micros` for a `BUY_FX_FROM_CUSTOMER` deal. `quoted_usd_gross_cents` then converts the notes to US cents under a **pinned rounding order** that matters: each denomination line is converted and rounded *first*, and the rounded line values are summed afterwards. Concretely, the lines are taken in ascending order of `denomination_minor_units`; for each line the note value is its `denomination_minor_units` multiplied by its `note_count`; that note value is multiplied by 1,000,000, divided by `applied_rate_micros`, and rounded half up to whole cents; and the resulting per-line cent amounts are added together. Summing the foreign minor units first and rounding once at the end produces a different number of cents and is wrong.

Commission is then layered on top under its own pinned evaluation order, and the order matters because the tier is keyed on a **tier basis** rather than on the total the customer eventually sees. The five steps are: establish the gross; establish the tier basis; select the tier rate; compute the commission; compute the total charge. At quote time the tier basis is simply this deal's own `quoted_usd_gross_cents` and nothing at all about the customer is consulted. The tier rate is 350 basis points when the basis is below 25000 cents (two hundred and fifty dollars), 250 basis points when the basis is below 100000 cents (one thousand dollars) but not below 25000, and 150 basis points when the basis is 100000 cents or more. If the card's `commission_schedule_code` is `PREMIUM`, a further 50 basis points is added to whichever tier rate was selected; a `STANDARD` schedule adds nothing. `quoted_commission_cents` is then the gross multiplied by the resulting rate in basis points, divided by ten thousand and rounded half up to whole cents, with a floor of 400 cents (four dollars) applied **after** that rounding — so a tiny deal always carries at least a four-dollar commission. Finally `quoted_total_charge_cents` is the gross **plus** the commission for a `SELL_FX_TO_CUSTOMER` deal, and the gross **minus** the commission for a `BUY_FX_FROM_CUSTOMER` deal, reflecting that the customer pays the commission in the first case and absorbs it out of their proceeds in the second. Keying the tier on the total charge rather than on the tier basis lands some deals in a different band and produces different cents; it is the wrong reading.

The quote also stamps `quote_expires_at` at the deal's `created_at` plus 15 minutes on the logical clock, and records the acting `X-User-ID` as `quoted_by_user_id`. The new row is born with `settlement_status` `QUOTED` and `compliance_status` `PENDING`, with `buyback_contract_id` null and with every settlement-side field null as well — `settled_usd_gross_cents`, `settled_commission_cents`, `settled_total_charge_cents`, `price_adjustment_cents`, `authorized_at`, `authorized_by_user_id`, `settled_at`, `settled_by_user_id` and `reversed_at`. No cash moves and no compliance aggregate changes at quote time, and neither the branch nor the customer row is stamped, so a quote leaves both of their `version` numbers alone.

**Authorising.** A teller or manager then authorises the deal, which takes no payload and advances `settlement_status` `QUOTED → AUTHORIZED`. The deal must still be `QUOTED`, otherwise `ERR_TRANSACTION_NOT_QUOTED`; the logical clock must be at or before `quote_expires_at`, otherwise `ERR_QUOTE_EXPIRED`; the branch's administrative status must be `ACTIVE`, otherwise `ERR_BRANCH_NOT_ACTIVE`; the branch's `posture` must not be `FROZEN`, otherwise `ERR_BRANCH_POSTURE_FROZEN`; and for a `BUY_FX_FROM_CUSTOMER` deal — which would add foreign cash to the vault — the branch's `posture` must additionally not be `RESTRICTED`, otherwise `ERR_BRANCH_POSTURE_RESTRICTED`. A `SELL_FX_TO_CUSTOMER` deal is unaffected by a `RESTRICTED` posture, because selling drains the vault rather than filling it. The customer's `compliance_hold_active` must be false, otherwise `ERR_CUSTOMER_COMPLIANCE_HOLD`. Those preconditions are listed here in narrative order but evaluated in the rank order of §2.8, which puts the quote-expiry check *last* of them: an expired quote presented at a `FROZEN` branch reports `ERR_BRANCH_POSTURE_FROZEN`, and one presented on behalf of a held customer reports `ERR_CUSTOMER_COMPLIANCE_HOLD`.

Authorisation is also where the identification and currency-class gates fire, in the rank order of §2.8 — behind the compliance-hold check above, so a held customer carrying no document at all reports `ERR_CUSTOMER_COMPLIANCE_HOLD` and not `ERR_CUSTOMER_ID_REQUIRED`, and with the export-limit and exotic-plan constraints of the last two sentences below sitting at rank 11 and therefore reached only once the quote is still live. If `quoted_usd_gross_cents` has reached 100000 cents (one thousand dollars), the customer must have a complete document bundle on file — `id_document_type`, `id_document_number` and `id_document_expiry` all non-null — or the call is refused with `ERR_CUSTOMER_ID_REQUIRED`. Independently of that amount threshold, if the customer has an `id_document_expiry` recorded at all then it must be strictly after the logical clock; a lapsed document blocks authorisation of a five-dollar deal just as firmly as a five-thousand-dollar one, with `ERR_CUSTOMER_ID_EXPIRED`. Selling a `RESTRICTED`-class currency additionally requires the customer's `travel_document_reference` to be non-null, otherwise `ERR_RESTRICTED_CURRENCY_DOC_REQUIRED`, and requires `fx_gross_minor_units` to be at most the currency's `export_limit_minor_units`, otherwise `ERR_EXPORT_LIMIT_EXCEEDED`. Selling an `EXOTIC`-class currency requires the branch to hold an `ACTIVE` stocking plan whose `computed_targets` contain that currency, otherwise `ERR_EXOTIC_PLAN_REQUIRED`.

On success `authorized_at` is stamped with the logical clock and `authorized_by_user_id` with the acting `X-User-ID`. `authorized_at` is not merely an audit stamp: it fixes the instant at which settlement will later re-read the rate board. One further effect fires here and it crosses the two status axes: if the customer's `structuring_risk_tier` is `HIGH` at the moment of authorisation, the deal's `compliance_status` advances `PENDING → FLAGGED` automatically — if and only if it is currently `PENDING`, so a deal a compliance officer has already moved to `CLEARED`, `FLAGGED` or `BLOCKED` is left exactly as it stands — while `settlement_status` is untouched. No notes move at authorisation; inventory is only disturbed at settlement. Authorisation stamps the transaction row and nothing else: the branch and the customer keep their `updated_at` and `version`, and the customer's surveillance aggregates are not recomputed here.

**Settling.** Settlement, again by a teller or a manager, advances `settlement_status` `AUTHORIZED → SETTLED` and is the request in which everything happens at once. The deal must be `AUTHORIZED`, otherwise `ERR_TRANSACTION_NOT_AUTHORIZED`. Its `compliance_status` must not be `BLOCKED`, otherwise `ERR_TRANSACTION_COMPLIANCE_BLOCKED` — note that a `FLAGGED` deal settles perfectly well; only `BLOCKED` bars settlement. The branch's `posture` must not be `FROZEN`. Once `settled_usd_gross_cents` reaches 500000 cents (five thousand dollars) or more, **dual control** applies and the settling `X-User-ID` must differ from `authorized_by_user_id`, otherwise `ERR_DUAL_CONTROL_REQUIRED`; below that amount one person may do both steps. Because that figure cannot be established without the rate card described in the next paragraph, a settlement for which no card is effective at `authorized_at` reports `ERR_RATE_CARD_NOT_EFFECTIVE` and the dual-control comparison is never made at all, even though rank 9 sits above rank 12. In **both** directions the branch must hold an inventory position for the deal's currency and every requested denomination must already have an entry on that position's `denomination_mix`, otherwise `ERR_DENOMINATION_NOT_STOCKED`: a purchase *from* a customer is refused just as firmly as a sale, because the notes coming in have to land on a denomination the branch already carries. Only for a `SELL_FX_TO_CUSTOMER` deal must each entry's `available_note_count` additionally be at least the requested `note_count`, otherwise `ERR_INSUFFICIENT_INVENTORY`; and the two are tested together, denomination by denomination in ascending face value, so a request whose smallest denomination is stocked but thin and whose largest is missing from the mix entirely reports `ERR_INSUFFICIENT_INVENTORY` rather than `ERR_DENOMINATION_NOT_STOCKED`. For a `BUY_FX_FROM_CUSTOMER` deal, the post-credit `vault_usd_equivalent_cents` must not exceed the branch's `vault_limit_usd_cents`, otherwise `ERR_VAULT_LIMIT_WOULD_EXCEED`.

Settlement re-prices the deal rather than trusting the quote. `settled_usd_gross_cents` is computed by exactly the pinned per-line procedure described above, but the rate it applies is re-read from the `PUBLISHED` card for this branch and currency whose half-open window covers `authorized_at` — not the settle instant, and not necessarily the same row that was cited at quote time. That re-read rate drives the settlement arithmetic only: the transaction's stored `applied_rate_micros` is **never** rewritten and keeps the quote-time rate for the row's whole life, so a deal repriced off a newer card is returned with an `applied_rate_micros` that no longer explains its `settled_usd_gross_cents`. If no such card exists the settlement fails with `ERR_RATE_CARD_NOT_EFFECTIVE` — and only ever with that code, since settlement, unlike quoting, does not separately require a `PUBLISHED` card to exist for the pair. When that card happens to be the same row as the quoted card, `settled_usd_gross_cents` equals `quoted_usd_gross_cents` exactly.

The settlement commission uses the same five-step order but a **different tier basis**, and this is the single most consequential difference between the two pricing variants. The basis is this deal's `settled_usd_gross_cents` **plus** the sum of `settled_usd_gross_cents` over the same customer's *other* transactions that have `settlement_status` `SETTLED`, the same `branch_id`, and a `settled_at` falling on the same UTC calendar day as this settlement; `VOIDED` and `REVERSED` rows contribute nothing. A customer's earlier same-day, same-branch settlements can therefore pull this deal into a cheaper tier even though its gross is unchanged. From that basis the tier rate is selected against the same 25000-cent and 100000-cent ceilings, the same `PREMIUM` uplift of 50 basis points is applied when the card's schedule calls for it, and `settled_commission_cents` is the gross multiplied by the rate in basis points, divided by ten thousand, rounded half up, and then floored at 400 cents. `settled_total_charge_cents` is the settled gross plus the settled commission for a sale to the customer and the settled gross minus it for a purchase from the customer. `price_adjustment_cents` records the signed difference — `settled_total_charge_cents` minus `quoted_total_charge_cents` — and may legitimately be negative.

Settlement then stamps `settled_at` with the logical clock and `settled_by_user_id` with the acting `X-User-ID`, and fires two independent cascades plus one independent report rule. The **inventory cascade** runs the four hops of §2.9: each requested denomination's `available_note_count` on the branch's position for the currency is decremented for a sale and incremented for a purchase; that position's `total_minor_units` and `usd_equivalent_cents` are recomputed from the new mix; the branch's `vault_usd_equivalent_cents` and `vault_utilization_bps` are recomputed from the position totals; and the branch's `posture` is re-derived, which may itself raise an automatic repatriation shipment as a fifth hop. The **surveillance cascade** runs in parallel and is described in §3.6: the customer's `rolling_30d_settled_usd_cents`, `calendar_month_settled_usd_cents`, `near_threshold_txn_count` and `distinct_branch_count` are recomputed, then `structuring_risk_score` and `structuring_risk_tier` are re-derived from those aggregates, then an arrival at the `HIGH` tier creates a structuring-suspicion report, and then the creation of that report — not the settlement itself — sets `compliance_hold_active` to true. Independently of both cascades, if `settled_usd_gross_cents` has reached 1,000,000 cents (ten thousand dollars), one regulatory report of type `THRESHOLD_REPORT` is created in `DRAFT` for this transaction, citing this branch and this customer. It is created *last* of everything the settlement does — after the inventory cascade and after any `STRUCTURING_SUSPICION` report the surveillance cascade raised — so when one settlement raises both reports, the structuring report is the earlier of the two in the report list's creation ordering. Settlement increases both the branch's `version` and the customer's `version` by one.

**Voiding.** A deal that has not yet settled can be abandoned by a teller or manager with an optional `void_reason` — accepted, malformed if present but not a non-empty string, and checked for that before the state precondition below, yet stored on no field of the transaction. `settlement_status` must be either `QUOTED` or `AUTHORIZED`, otherwise `ERR_TRANSACTION_NOT_VOIDABLE`; both `QUOTED → VOIDED` and `AUTHORIZED → VOIDED` are permitted and both are terminal. A void has no inventory effect, no customer-aggregate effect and no reporting effect whatsoever — it is the cheap exit.

**Reversing.** A settled deal can be unwound by a `BranchManager` alone, with an optional `reversal_reason` — accepted and validated exactly as `void_reason` is, and likewise persisted on no field — moving `settlement_status` `SETTLED → REVERSED`, which is terminal. Four preconditions guard it: the deal must be `SETTLED`, otherwise `ERR_TRANSACTION_NOT_SETTLED`; the logical clock must be at or before `settled_at` plus 24 hours, otherwise `ERR_REVERSAL_WINDOW_CLOSED`; the `compliance_status` must not be `BLOCKED`, otherwise `ERR_TRANSACTION_COMPLIANCE_BLOCKED`; and `buyback_contract_id` must be null, otherwise `ERR_BUYBACK_BLOCKS_REVERSAL` — a deal that has had a rate lock written against it cannot be reversed until that lock is cancelled.

Reversal is a full compensation, not a status flip, and it has four parts. First, every requested denomination's `available_note_count` on the branch's position is adjusted by the settlement's own note counts in the opposite direction — incremented for a sale that is being undone, decremented for a purchase. That compensation is a **delta**, never a restore from a stored snapshot, so it returns `total_minor_units` to exactly its pre-settlement value only when nothing else has disturbed the mix in between; it re-checks neither stock nor the vault ceiling, and it may therefore drive an `available_note_count`, and with it the position's `total_minor_units`, negative. A denomination the mix no longer carries is appended to it with all three counters at 0 before the adjustment, exactly as §2.9 describes, and when the branch holds no position at all for the deal's currency the reversal moves no notes and still succeeds. Second, the position's `usd_equivalent_cents` and then the branch's `vault_usd_equivalent_cents`, `vault_utilization_bps` and `posture` are recomputed from the adjusted mix, in that order. Third, because the surveillance aggregates count only `SETTLED` rows, this transaction drops out of both aggregation windows: `rolling_30d_settled_usd_cents`, `calendar_month_settled_usd_cents`, `near_threshold_txn_count` and `distinct_branch_count` are all re-derived from scratch over the customer's surviving `SETTLED` population against the logical clock as it reads at the moment of the reversal — which reproduces the pre-settlement figures only while the clock has not moved in between, as §3.6 pins — and the score and tier are re-derived from them, so a reversal can walk the tier back down `HIGH → ELEVATED` or `ELEVATED → NORMAL`. A reversal never raises a structuring-suspicion report, whatever tier that re-derivation happens to land on. Fourth, any `THRESHOLD_REPORT` still in `DRAFT` whose `triggering_transaction_id` is this transaction is deleted outright, while reports that have reached `FILED` or `AMENDING` are retained — a filed report is a regulatory fact and is never withdrawn by an operational reversal. One thing a reversal deliberately does **not** do is clear `compliance_hold_active`; the hold survives, and only an explicit release lifts it. `reversed_at` is stamped with the logical clock, and both the branch's `version` and the customer's `version` increase by one.

Transactions may be read individually, exposing both the quoted and settled money fields, the signed adjustment and both status axes, or listed with optional `branch_id`, `customer_id`, `rate_card_id`, `buyback_contract_id`, `settlement_status`, `compliance_status` and `direction` filters — the list being the reverse-lookup channel for all four of those pointers.

### 3.6. Structuring Surveillance, Compliance Decisions and the Filing Cycle

Structuring — deliberately breaking one reportable exchange into several smaller ones — is the abuse this network is required to detect, and the detection runs entirely off settled volume. Two aggregate windows are maintained on every customer, and they are computed from exactly the same population: the customer's transactions whose `settlement_status` is `SETTLED`. Quoted, authorised, voided and reversed rows are all excluded, which is precisely why a reversal makes an aggregate fall back. Both windows are inclusive at both ends and both are evaluated at the end of a settlement and at the end of a reversal.

The **rolling window** looks back 30 days: it starts at the logical clock minus 30 days and ends at the logical clock, and it writes `rolling_30d_settled_usd_cents` as the sum of `settled_usd_gross_cents` over the settlements whose `settled_at` falls inside it. It also writes two counters over that same population: `near_threshold_txn_count`, the number of settlements whose `settled_usd_gross_cents` sits between 800000 cents (eight thousand dollars) and 999999 cents inclusive — that is, at or above the near-threshold floor and strictly below the reporting threshold of 1,000,000 cents; and `distinct_branch_count`, the number of distinct `branch_id` values across those same settlements. The **calendar-month window** covers the same population but starts at the first instant of the UTC calendar month containing the logical clock and ends at the logical clock, and it writes `calendar_month_settled_usd_cents`. Settlements from the previous month are excluded, so whenever a customer's activity straddles a month boundary the calendar-month figure is strictly smaller than the rolling figure — the two fields diverging is expected behaviour, not a bug. Only the rolling window's three outputs feed the live risk score; the calendar-month figure exists to be cited by a report. None of the four aggregates is ever patched incrementally by the operation that disturbed it: every one of them is re-derived from scratch by re-scanning the customer's whole `SETTLED` population against the logical clock as it reads at the moment of the recomputation. Consequently, when a reversal happens after the clock has moved on, the customer is left with the aggregates that the surviving population implies at the **new** clock reading — which is a literal restoration of the pre-settlement figures only while the clock has not moved in between.

`structuring_risk_score` is a weighted score in the range 0 to 100 built from exactly those three rolling outputs and nothing else. Its **volume component** is 40 multiplied by `rolling_30d_settled_usd_cents`, divided by 1,000,000 cents, rounded down to a whole number of points, and then capped at 40 — so a customer who has settled ten thousand dollars in the last 30 days earns the full 40 points. Its **frequency component** is 11 points for each near-threshold settlement, that is 11 multiplied by `near_threshold_txn_count`, capped at 35 points. Its **dispersion component** is 12 points for each *additional* branch beyond the first, that is 12 multiplied by the quantity `distinct_branch_count` minus one, capped at 25 points above and clamped at 0 points below — the lower clamp matters, because a customer with no settled transactions at all would otherwise contribute a negative twelve. Each component is floored to a whole number of points individually and the three are summed afterwards, so no fractional drift accumulates. The resulting score drives `structuring_risk_tier`: `NORMAL` while the score is below 25, `ELEVATED` while it is at least 25 and below 70, and `HIGH` once it reaches 70.

Because the score is re-derived at the end of every settlement and every reversal, the tier climbs and falls. A settlement can move a customer `NORMAL → ELEVATED`, `ELEVATED → HIGH` or straight `NORMAL → HIGH`, and each of those writes the new `structuring_risk_tier` and increases the customer's `version`. A reversal can move a customer back `HIGH → ELEVATED` or `ELEVATED → NORMAL`. Arriving at `HIGH` by either the `ELEVATED → HIGH` or the `NORMAL → HIGH` route has one further consequence, identical in both cases: one regulatory report of type `STRUCTURING_SUSPICION` is created in `DRAFT` for that customer — unless the customer already has a `STRUCTURING_SUSPICION` report whose `status` is `DRAFT` or `AMENDING`, in which case no duplicate is raised — and if and only if that report was actually created, the customer's `compliance_hold_active` is set to true. The hold is caused by the report, not by the settlement, and the distinction is load-bearing: a second `HIGH` arrival while an earlier report is still outstanding creates no report and therefore raises no new hold. Coming back down from `HIGH` to `ELEVATED` does not clear the hold either.

`compliance_hold_active` is the blunt instrument of this section: while it is true, no new transaction for that customer can be authorised, and no buy-back guarantee can be issued for them. A `ComplianceOfficer` controls it directly, supplying a mandatory `action` of either `APPLY` or `RELEASE` and an optional `reason` — accepted, and malformed if present but not a non-empty string, yet stored on no field of the customer. `APPLY` sets `compliance_hold_active` to true; `RELEASE` sets it to false. Either action is accepted even when the flag already reads the requested value, in which case it rewrites the same value rather than being refused. A `RELEASE` is refused with `ERR_STRUCTURING_REPORT_PENDING` while the customer still has a `STRUCTURING_SUSPICION` report whose `status` is `DRAFT` or `AMENDING` — the paperwork has to be filed before the customer is let back through the counter. Either action increases the customer's `version` by one.

Compliance decisions on an individual deal are a separate control, and they move the transaction's second, independent status axis without touching the settlement axis at all. A `ComplianceOfficer` supplies a mandatory `decision` of `CLEAR`, `FLAG` or `BLOCK` and an optional `decision_note` — accepted, malformed if present but not a non-empty string, yet stored on no field of the transaction. The deal's `settlement_status` is never consulted, so a decision may be recorded on a `QUOTED`, `AUTHORIZED`, `SETTLED`, `VOIDED` or `REVERSED` deal alike, and the call stamps the transaction row alone: neither the branch nor the customer is touched. A `CLEAR` decision is accepted while `compliance_status` is either `PENDING` or `FLAGGED`, producing `PENDING → CLEARED` or `FLAGGED → CLEARED`. A `BLOCK` decision is likewise accepted from either of those two, producing `PENDING → BLOCKED` or `FLAGGED → BLOCKED`. A `FLAG` decision is narrower: it is accepted only while `compliance_status` is exactly `PENDING`, producing `PENDING → FLAGGED`. Any decision that does not satisfy its own precondition — a decision on a row that is already `CLEARED` or `BLOCKED`, or a `FLAG` on a row that is no longer `PENDING` — is refused with `ERR_COMPLIANCE_DECISION_FINAL`. The operational weight of the three outcomes is asymmetric: a `CLEARED` or `FLAGGED` deal settles and reverses normally, whereas a `BLOCKED` deal has every later settlement and every later reversal refused with `ERR_TRANSACTION_COMPLIANCE_BLOCKED`.

Regulatory reports themselves are never created by a client request; every one of them is raised by a cascade, and the report list is the only channel through which those cascade-created rows can be discovered. A report records the `customer_id` it concerns and the `branch_id` where the triggering event occurred — on a `COUNTERFEIT_SEIZURE` the `customer_id` is copied from the cited exchange transaction's own `customer_id` and the `branch_id` is the branch that detained the notes — together with a `report_type` of `THRESHOLD_REPORT`, `STRUCTURING_SUSPICION` or `COUNTERFEIT_SEIZURE`. Exactly one of two pointers is populated according to type: `triggering_transaction_id` names the settlement that raised the report and is null on a `COUNTERFEIT_SEIZURE`, while `note_assessment_id` names the assessment that raised it and is null on both settlement-driven types. Every report cites an aggregation window through `window_start`, the inclusive start, and `window_end`, the inclusive end, which is the triggering instant itself. On a `THRESHOLD_REPORT` and on a `COUNTERFEIT_SEIZURE` that window is **zero-width**: `window_start` and `window_end` carry the same instant — the triggering transaction's `settled_at` for a threshold report, and the logical clock at the moment the outcome was recorded for a seizure — so those two types legitimately cite a window that spans no time at all. On a `STRUCTURING_SUSPICION` that window is the calendar-month window this section defines: `window_start` is the first instant of the UTC calendar month containing the logical clock and `window_end` is the clock itself, both stamped in the canonical form of §2.4. `aggregate_usd_cents` carries the amount the report is about, and it differs by type: for a `THRESHOLD_REPORT` it is the triggering transaction's `settled_usd_gross_cents`; for a `STRUCTURING_SUSPICION` it is the calendar-month aggregate described above; and for a `COUNTERFEIT_SEIZURE` it is the seized notes' US face value, computed as the assessment's `face_fx_minor_units` multiplied by 1,000,000, divided by the **selected wholesale mid rate** of §2.9 for the assessment's currency and rounded half up to whole cents — the wholesale mid, never the board card's `buy_rate_micros`. `transaction_count` carries the number of `SETTLED` transactions inside the cited window, which is 1 for a `THRESHOLD_REPORT` and 0 for a `COUNTERFEIT_SEIZURE`; for a `STRUCTURING_SUSPICION` it counts that customer's `SETTLED` transactions at **any** branch whose `settled_at` falls inside the cited inclusive window, so it is not restricted to the branch the report names. However a report is raised, it is born with `status` `DRAFT`, `filing_reference` and `filed_at` null and `amendment_count` 0.

Filing is a `ComplianceOfficer` act that carries a mandatory `filing_reference` — the regulator's acknowledgement — and moves the report to `FILED` from either `DRAFT` or `AMENDING`; a report already in `FILED` is refused with `ERR_REPORT_INVALID_STATE`. Filing stamps `filed_at` with the logical clock and stores the reference, overwriting any earlier one on a re-file. Amendment is the reverse move: it requires the report to be exactly `FILED` — otherwise `ERR_REPORT_INVALID_STATE` — takes an optional `amendment_reason` — accepted, and rejected as malformed if it is present but not a non-empty string, yet persisted on no field of the report — moves the report `FILED → AMENDING` and increases `amendment_count` by one while retaining the `filing_reference` and `filed_at` of the filing it re-opens, so an amending report still shows when and under what reference it was last filed. The cycle `FILED → AMENDING → FILED` may repeat indefinitely and `amendment_count` counts exactly those loops. The two moves also gate the hold-release path in opposite directions: filing the last outstanding `STRUCTURING_SUSPICION` report of a customer is what makes a hold release permissible, and re-opening such a report for amendment blocks that path again. Reports are readable individually and listable with optional `customer_id`, `branch_id`, `triggering_transaction_id`, `note_assessment_id`, `report_type` and `status` filters.

### 3.7. Buy-Back Guarantees and Rate Locks

A buy-back guarantee is the network's flagship travel product: a customer who bought foreign notes for a trip can bring the unspent ones back and be paid at the rate that was in force when they bought, however the market has moved since. Issuing one is a `BranchTeller` or `BranchManager` act whose payload is deliberately minimal — the `customer_id` holding the lock, the `origin_transaction_id` of the deal the guarantee attaches to, and the `expected_customer_version` pin of §2.7 — because every commercial term is derived rather than supplied.

The origin must be a settled sale: its `settlement_status` must be `SETTLED` and its `direction` must be `SELL_FX_TO_CUSTOMER`, and the currency involved must have `buyback_eligible` true on its profile; any of those three failing produces `ERR_BUYBACK_NOT_ELIGIBLE`. At most one contract may ever be written against a given origin, so a second attempt against the same deal is refused with `ERR_CONTRACT_ALREADY_ISSUED` whatever `status` the earlier contract now carries: a `CANCELLED`, `EXPIRED` or fully `REDEEMED` predecessor still bars a replacement, even though cancelling or superseding it reset that origin's own `buyback_contract_id` back to null. The customer's `compliance_hold_active` must be false, otherwise `ERR_CUSTOMER_COMPLIANCE_HOLD`.

Issuance copies `branch_id` and `currency_code` from the origin transaction and then prices the lock. `locked_buy_rate_micros` is frozen from the `buy_rate_micros` of the origin transaction's own rate card — the card that was cited at quote time, not whatever card is on the board today. `locked_fx_minor_units` is copied from the origin's `fx_gross_minor_units` and is the maximum notional the lock covers; `remaining_fx_minor_units` starts equal to it. `fee_usd_cents` is the greater of 200 cents (two dollars) and the origin's `settled_usd_gross_cents` multiplied by 300 basis points — three percent — divided by ten thousand and rounded half up to whole cents. `liability_usd_cents` is `remaining_fx_minor_units` multiplied by 1,000,000, divided by `locked_buy_rate_micros`, rounded half up to whole cents; it is the branch's exposure if the customer brings everything back. `rate_lock_expires_at` is the issue-time logical clock plus 31 days. The contract is born with `status` `ISSUED`, `redemption_count` 0 and `superseded_by_contract_id` null.

Issuance also writes back into two other rows. The origin transaction's `buyback_contract_id` is set to the new contract's `id`, which is exactly what bars that transaction from being reversed. And any incumbent contract of the same customer in the same currency whose `status` is `ISSUED` or `PARTIALLY_REDEEMED` is cancelled: its `status` moves to `CANCELLED`, its `superseded_by_contract_id` is set to the new contract's `id`, its `remaining_fx_minor_units` and `liability_usd_cents` are both zeroed exactly as an explicit cancellation would zero them, and *its* own origin transaction's `buyback_contract_id` is reset to null, which re-opens that older deal for reversal. The incumbent is matched on customer and currency alone and never on branch, so a lock written at one branch supersedes the customer's lock at another; incumbents are swept oldest first, and each one's own branch has its `buyback_liability_usd_cents` reconciled as that incumbent is cancelled, before the new contract's branch is reconciled. Because the new contract and its origin transaction reference each other, the two rows form a reference cycle and must be written in a pinned order: the contract row is created first and the origin's pointer is stamped afterwards. Finally the branch's `buyback_liability_usd_cents` is reconciled and the customer's `version` increases by one.

`buyback_liability_usd_cents` on a branch is the network's conserved monetary quantity, and it is recomputed from scratch — never incrementally patched — on every contract creation, redemption, cancellation and clock-driven expiry. It is the sum, over that branch's contracts whose `status` is `ISSUED` or `PARTIALLY_REDEEMED`, of each contract's `remaining_fx_minor_units` multiplied by 1,000,000, divided by that contract's `locked_buy_rate_micros`, and rounded half up to whole cents — each contract rounded individually, and the rounded values summed afterwards. Contracts in `REDEEMED`, `EXPIRED` or `CANCELLED` contribute nothing. The reconciliation writes the branch row only when the recomputed total differs from the figure already stored; a reconciliation that reproduces the stored figure leaves the branch's `updated_at` and `version` alone. The invariant this guarantees is strict: issuing a contract and then cancelling it with no redemption in between must return the branch's `buyback_liability_usd_cents` to exactly the value it held before the issue, provided no other contract changed in the interim.

**Redemption** is the `BranchTeller`'s exclusive capability and takes a `returned_denominations` array of the notes the customer is handing back. Six preconditions guard it. The contract's `status` must be `ISSUED` or `PARTIALLY_REDEEMED`, otherwise `ERR_CONTRACT_NOT_REDEEMABLE`. The branch's `posture` must not be `FROZEN`, otherwise `ERR_BRANCH_POSTURE_FROZEN`. A card for the contract's branch and currency must exist with `status` `PUBLISHED` and a window covering the logical clock — at or after `effective_from` and strictly before `effective_to`, a null `effective_to` meaning never closing — otherwise `ERR_RATE_CARD_NOT_PUBLISHED` or `ERR_RATE_CARD_NOT_EFFECTIVE`; the branch must be openly trading in the currency even though the price paid ignores today's board. The returned total — the sum over `returned_denominations` of each entry's `denomination_minor_units` multiplied by its `note_count` — must not exceed `remaining_fx_minor_units`, otherwise `ERR_REDEEM_EXCEEDS_REMAINING`. Every returned denomination must appear in the currency profile's `standard_denominations`, otherwise the request is malformed. And the post-credit `vault_usd_equivalent_cents` of the branch must not exceed its `vault_limit_usd_cents`, otherwise `ERR_VAULT_LIMIT_WOULD_EXCEED`.

A successful redemption subtracts the returned total from `remaining_fx_minor_units`, increases `redemption_count` by one, and pays the customer the returned total multiplied by 1,000,000, divided by `locked_buy_rate_micros` and rounded half up to whole cents — at the **locked** rate, never at today's board rate. `liability_usd_cents` is then recomputed from the new `remaining_fx_minor_units` and the branch's `buyback_liability_usd_cents` is reconciled. The inventory cascade then runs in the pinned order of §2.9: the branch's position for the currency is credited with the returned notes, then the position's `total_minor_units` and `usd_equivalent_cents` are recomputed, then the branch's `vault_utilization_bps` and finally its `posture`. When the branch holds no inventory position for the contract's currency at all, the redemption still succeeds and simply moves no notes: there is no mix to credit, and the pre-commit vault projection then falls back to adding the returned notes' own wholesale valuation — the returned total multiplied by 1,000,000, divided by the selected wholesale mid rate and rounded half up to whole cents — to the branch's stored `vault_usd_equivalent_cents`, which is the one place in this service where the projection of §2.6 is built from a separately-rounded increment rather than from a re-valued position. The branch's `version` increases by one. Which state the contract lands in depends purely on whether notional remains: a redemption that leaves `remaining_fx_minor_units` above zero produces `ISSUED → PARTIALLY_REDEEMED` on a first redemption and `PARTIALLY_REDEEMED → PARTIALLY_REDEEMED` on any subsequent one, the state being re-entrant so the loop may repeat as long as notional remains; a redemption that consumes the entire remaining notional instead produces `ISSUED → REDEEMED` or `PARTIALLY_REDEEMED → REDEEMED`, setting `remaining_fx_minor_units` to 0 and `liability_usd_cents` to 0. `REDEEMED` is terminal.

**Cancellation** is shared between `BranchManager` and `TreasuryOfficer` and takes an optional `cancellation_reason` — accepted, malformed if present but not a non-empty string, and stored on no field of the contract. The contract must be `ISSUED` or `PARTIALLY_REDEEMED`, otherwise `ERR_CONTRACT_NOT_CANCELLABLE`; both `ISSUED → CANCELLED` and `PARTIALLY_REDEEMED → CANCELLED` are permitted and `CANCELLED` is terminal. Cancellation sets `remaining_fx_minor_units` to 0 and `liability_usd_cents` to 0, resets the origin transaction's `buyback_contract_id` to null so that deal becomes reversible again, and reconciles the branch's `buyback_liability_usd_cents`. Notes already redeemed under a partially-redeemed contract are **not** clawed back. When the cancellation was caused by a newer contract superseding this one rather than by an explicit request, `superseded_by_contract_id` additionally carries the new contract's `id`.

**Expiry** is driven by the clock rather than by a request. When a `PlatformAdmin` advances the logical clock, every contract whose `status` is `ISSUED` or `PARTIALLY_REDEEMED` and whose `rate_lock_expires_at` now lies strictly before the new clock value moves to `EXPIRED` — `ISSUED → EXPIRED` and `PARTIALLY_REDEEMED → EXPIRED` behave identically — with `liability_usd_cents` set to 0 while `remaining_fx_minor_units` is retained unchanged for audit. `EXPIRED` is terminal. Every branch that had a contract expire has its `buyback_liability_usd_cents` reconciled, and the count of contracts swept is what the clock call reports as `expired_contract_count`. Contracts are readable individually — the read exposes the locked rate, remaining notional and current liability — and listable with optional `customer_id`, `branch_id`, `origin_transaction_id`, `superseded_by_contract_id` and `status` filters.

### 3.8. Counterfeit, Damaged and Obsolete Notes

Notes taken in over the counter are not always good. When a teller or manager pulls a class of notes out of circulation, they raise a **note assessment**, which is simultaneously a quarantine record and an audit trail. The payload names the `branch_id` that detained the notes, the `inventory_position_id` of the position the notes are being quarantined out of — whose own `branch_id` must equal the one supplied, a mismatch being refused with `ERR_INVALID_REQUEST` — and the `exchange_transaction_id` of the settled purchase-from-customer deal the notes arrived on, which is resolved and nothing more: neither its `settlement_status` nor its `direction` nor its currency is examined, so any live transaction may in fact be cited. It then names the note class itself: `denomination_minor_units`, the face value of the class, which must already exist as an entry on the position's `denomination_mix` with an `available_note_count` of at least the detained quantity — both of those failures being plain `ERR_INVALID_REQUEST` (HTTP 400) at rank 4 rather than the rank-13 fiscal codes `ERR_DENOMINATION_NOT_STOCKED` and `ERR_INSUFFICIENT_INVENTORY`, and the detained denomination is not required to appear in the currency profile's `standard_denominations`; `note_count`, how many notes are detained, which must be at least 1; and `defect_type`, one of `SUSPECTED_COUNTERFEIT`, `DAMAGED` or `OBSOLETE_SERIES`. An optional `serial_reference` records the serial or batch reference the teller noted down.

Raising the assessment copies `currency_code` from the cited position and computes `face_fx_minor_units` as `denomination_minor_units` multiplied by `note_count`. The notes move immediately: on the position's mix entry, `available_note_count` is reduced by `note_count` and `quarantined_note_count` is increased by the same amount. Because quarantined notes are excluded from `total_minor_units`, the position's conserved quantity drops, its `usd_equivalent_cents` is revalued, and the branch's vault fields and `posture` are recomputed in the pinned order — so detaining a large tranche of notes can pull a `RESTRICTED` branch back to `OPEN` inside the very request that detained them. The branch's `version` increases by one. The assessment is born with `status` `SUBMITTED`, `outcome` null, `recovery_usd_cents` null and `assessed_by_user_id` null.

Recording the outcome is the `BranchManager`'s exclusive act. It carries a mandatory `outcome` and an optional `assessment_note` — accepted, malformed if present but not a non-empty string, yet stored on no field of the assessment — moves the assessment `SUBMITTED → ASSESSED` — a second attempt is refused with `ERR_ASSESSMENT_ALREADY_ASSESSED` — and writes the acting `X-User-ID` into `assessed_by_user_id`. `ASSESSED` is terminal. Three outcomes are possible, each permitted only for specific defect types and each carrying a completely disjoint set of consequences; requesting an outcome the recorded `defect_type` does not allow is refused with `ERR_OUTCOME_NOT_PERMITTED_FOR_DEFECT`.

`CONFISCATED` is permitted only when `defect_type` is `SUSPECTED_COUNTERFEIT`. The notes are written off rather than returned: on the position's mix entry, `quarantined_note_count` is reduced by `note_count` and `written_off_note_count` is increased by the same amount, while `available_note_count` and therefore `total_minor_units` are left untouched — the notes were already out of circulation, so nothing re-enters it. `quarantined_minor_units` falls by `face_fx_minor_units`. `recovery_usd_cents` stays null, because nothing is paid for counterfeit paper. Recording an outcome is not an operation that stamps the branch for its own reasons, so because `total_minor_units` did not move here the branch's derived vault fields all come back unchanged and its `updated_at` and `version` are left alone; the position row is stamped all the same, since its mix did change. Two cross-entity effects follow: one regulatory report of type `COUNTERFEIT_SEIZURE` is created in `DRAFT` with its `note_assessment_id` pointing at this assessment, and the cited transaction's `compliance_status` is advanced `PENDING → FLAGGED` if and only if it is currently `PENDING` — a deal already `CLEARED`, `FLAGGED` or `BLOCKED` is left as it stands.

`RETURNED` is permitted when `defect_type` is `DAMAGED` or `OBSOLETE_SERIES`, and never for a suspected counterfeit. The notes are handed back to the customer and leave the branch: `quarantined_note_count` is reduced by `note_count` on the mix entry, `available_note_count` and `total_minor_units` are unchanged, and `quarantined_minor_units` falls by `face_fx_minor_units`. `recovery_usd_cents` stays null. No report is created and the cited transaction's `compliance_status` is untouched, and the branch row goes unstamped for the same reason as a confiscation while the position row is stamped.

`EXCHANGED_AT_DISCOUNT` is permitted only when `defect_type` is `DAMAGED`, and it additionally requires that a card for the branch and currency exists with `status` `PUBLISHED` and a window covering the logical clock, otherwise `ERR_RATE_CARD_NOT_PUBLISHED` or `ERR_RATE_CARD_NOT_EFFECTIVE`. The notes come back into stock at reduced value to the customer: `quarantined_note_count` is reduced by `note_count` **and** `available_note_count` is increased by the same amount, so `total_minor_units` returns to exactly its pre-quarantine value, after which the position's `usd_equivalent_cents`, then the branch's `vault_usd_equivalent_cents` and `vault_utilization_bps`, then the branch's `posture` are recomputed in that order. `recovery_usd_cents` is what the customer is paid, and it is derived in a pinned **two-step** rounding: first the US face value of the detained notes is computed as `face_fx_minor_units` multiplied by 1,000,000, divided by the effective published card's `buy_rate_micros`, and rounded half up to whole cents; then that US face value is multiplied by the currency profile's `damaged_note_recovery_bps`, divided by ten thousand, and rounded half up to whole cents again. Folding the recovery percentage into the conversion and rounding once yields a different number and is wrong.

Assessments are readable individually, exposing the outcome and recovery amount, and listable with optional `branch_id`, `inventory_position_id`, `exchange_transaction_id`, `defect_type` and `status` filters — the list being the reverse-lookup channel for all three pointers.

### 3.9. Cash Logistics: Armored Movement, Arrival Variance and Repatriation

Physical currency reaches and leaves a branch on an armored route, and the shipment record tracks it from request to reconciliation. Either a `TreasuryOfficer` or a `BranchManager` may raise one, supplying the `branch_id`, the `currency_code` being moved, the `direction` — `REPLENISHMENT` moves currency into the branch vault, `REPATRIATION` moves surplus out — and a `manifest_denominations` array whose entries each carry a `denomination_minor_units` and a `note_count`. Raising a `REPLENISHMENT` shipment is one of the operations blocked by a `RESTRICTED` posture, since it would add cash to an already-crowded vault; that gate tests for `RESTRICTED` exactly and for nothing else, so a `FROZEN` branch — crowded worse still — may raise a replenishment freely, and no posture value at all blocks a `REPATRIATION`. Nor is the branch's administrative `status` consulted on this endpoint. The shipment is born with `status` `REQUESTED`, `auto_generated` false, `armored_route_id` null, both `window_start` and `window_end` null, and `delivered_minor_units`, `variance_minor_units`, `exception_reason` and `written_off_minor_units` all null; `manifest_minor_units` is the sum over the manifest of each entry's `denomination_minor_units` multiplied by its `note_count`, and `manifest_usd_equivalent_cents` is that quantity multiplied by 1,000,000, divided by the selected wholesale mid rate for the currency, and rounded half up to whole cents. Manifests are always valued at the wholesale mid, never at a retail board rate. Because that valuation needs a mid rate, raising a shipment in a currency for which no wholesale quote is yet effective at the logical clock fails with `ERR_WHOLESALE_RATE_NOT_FOUND` (HTTP 404) — reported after the posture gate, since it arises inside the valuation rather than from an identifier in the request — and no shipment row survives the attempt.

**Scheduling** is a `TreasuryOfficer` act on a `REQUESTED` shipment — any other state is refused with `ERR_SHIPMENT_INVALID_STATE` — and it supplies the `armored_route_id` together with the closed transport window `window_start` and `window_end`, the latter of which must be strictly after the former. The chosen route's `status` must be `ACTIVE`, otherwise `ERR_ROUTE_SUSPENDED`, and its `region_code` must equal the branch's `region_code`, otherwise `ERR_ROUTE_BRANCH_NOT_SERVICED`. Both of those route checks sit at rank 11 while the window-separation rule below sits at rank 10, so they are listed here in narrative order only: a request that cites a `SUSPENDED` or wrongly-regioned route *and* crowds a neighbouring window reports `ERR_ROUTE_WINDOW_CONFLICT`. Two capacity-shaped rules then apply. The first is window separation: the requested window must be separated from the window of every other shipment on the same route whose `status` is `SCHEDULED` or `IN_TRANSIT` by at least 45 minutes. Because transport windows are **closed** — they include both `window_start` and `window_end` — the requested window is accepted only when its `window_start` is at or after the other window's `window_end` plus 45 minutes, or its own `window_end` plus 45 minutes is at or before the other window's `window_start`. Back-to-back windows that merely touch therefore **conflict** and are refused with `ERR_ROUTE_WINDOW_CONFLICT`, which is the opposite of how the half-open board windows of §3.2 behave. The second is day capacity: taking the UTC calendar date of the requested `window_start`, the sum of `manifest_usd_equivalent_cents` over every *other* shipment on that route whose `status` is `SCHEDULED` or `IN_TRANSIT` and whose own `window_start` falls on that same UTC date, plus this shipment's own `manifest_usd_equivalent_cents`, must not exceed the route's `daily_capacity_usd_cents`. Shipments in `REQUESTED`, `DELIVERED`, `EXCEPTION` or `RECONCILED` are excluded from that sum. The comparison is strictly greater-than, so booking a route exactly up to its capacity is permitted and only the next cent over is refused, with `ERR_ROUTE_CAPACITY_EXCEEDED`. Individually legal shipments can violate this rule collectively, which is why it is evaluated last. On success the shipment moves `REQUESTED → SCHEDULED` and the route and both window fields are written from the request.

**Dispatch** is likewise a `TreasuryOfficer` act, takes no payload, requires `status` `SCHEDULED` and requires the logical clock to have reached `window_start`, otherwise `ERR_SHIPMENT_WINDOW_NOT_OPEN`. It moves the shipment `SCHEDULED → IN_TRANSIT` and, deliberately, moves no notes at all — cash is only recognised at arrival.

**Arrival** is the `BranchManager`'s exclusive act and carries a `delivered_denominations` array of what was actually counted off the van. The array is mandatory — absent or explicitly null is malformed — but, uniquely among the denomination arrays of this service, it may legitimately be **empty** and its entries' `note_count` may be 0, because a van can arrive carrying nothing; its denominations must still be distinct and must still appear in the currency profile's `standard_denominations`. The shipment must be `IN_TRANSIT`. `delivered_minor_units` is the sum over the delivered array of each entry's `denomination_minor_units` multiplied by its `note_count`, and `variance_minor_units` is `manifest_minor_units` minus `delivered_minor_units`. The count then selects one of two branches. When the count reproduces the manifest exactly — `delivered_minor_units` equal to `manifest_minor_units`, a variance of zero — the shipment moves `IN_TRANSIT → DELIVERED`, `variance_minor_units` is written as 0 and `exception_reason` stays null. When the counts differ in either direction, the shipment moves `IN_TRANSIT → EXCEPTION` instead, `variance_minor_units` carries the signed difference and `exception_reason` is set to `MANIFEST_VARIANCE`.

Both branches move cash, and both move only the notes that were actually counted, never the notes the manifest claimed. For a `REPLENISHMENT` shipment each delivered denomination's `available_note_count` on the branch's position for the currency is incremented; for a `REPATRIATION` shipment it is decremented. No sufficiency check guards that decrement, so a repatriation arrival may drive an `available_note_count` negative. The remaining three hops then run in the pinned order: the position's `total_minor_units` and `usd_equivalent_cents` are recomputed, the branch's `vault_usd_equivalent_cents` and `vault_utilization_bps` are recomputed, and the branch's `posture` is re-derived — which, on an arrival at `RESTRICTED` or `FROZEN`, itself raises an `auto_generated` repatriation shipment and sets `repatriation_pending` to true as a fifth hop. The branch's `version` increases by one. When the branch holds no inventory position for the shipment's currency at all, none of those hops happens: no notes move, the position and vault figures have nothing to recompute, no `posture` is re-derived and no automatic repatriation can be raised — yet the arrival still succeeds, with the variance, `status` and `exception_reason` written exactly as they otherwise would be, and the branch's `version` still increases by one. The two arrival branches differ in exactly one further respect, and it is easy to miss: a `REPATRIATION` shipment that lands `DELIVERED` sets the branch's `repatriation_pending` back to false, whereas one that lands in `EXCEPTION` does **not** clear the flag — the surplus is not provably gone while the count is in dispute.

**Reconciliation** closes the shipment out and belongs to the `TreasuryOfficer`. The shipment must be `DELIVERED` or `EXCEPTION`, otherwise `ERR_SHIPMENT_INVALID_STATE`; both `DELIVERED → RECONCILED` and `EXCEPTION → RECONCILED` are permitted and `RECONCILED` is terminal. The two paths differ in what is written off: reconciling from `DELIVERED` sets `written_off_minor_units` to 0, while reconciling from `EXCEPTION` sets it to `variance_minor_units`, formally absorbing the discrepancy. Reconciling a `REPATRIATION` shipment out of `EXCEPTION` is also the point at which its branch's `repatriation_pending` is finally cleared to false. Neither path moves a note or revalues the vault — reconciliation is a bookkeeping close-out and takes no payload — and the branch row is stamped only on that one `REPATRIATION`-out-of-`EXCEPTION` path, and there only when the flag was still standing at true.

Automatic repatriation deserves its own account, because no operator ever asks for it. When a posture recomputation lands a branch on `RESTRICTED` or `FROZEN` while `repatriation_pending` is false, the server picks one position and builds a manifest from it. Eligibility is pinned: only the branch's positions whose `status` is `OPEN` and whose `total_minor_units` is strictly positive are candidates, and if that candidate set is empty then no shipment is raised at all and `repatriation_pending` stays false. Candidates are ranked by `usd_equivalent_cents` descending, with ties broken by `created_at` ascending and any remaining tie — the normal case, since the logical clock stands still between clock calls — broken by the sequence in which the server created the positions, oldest first; the first one is selected — the fattest position, earliest-created first on a tie. The surplus to remove is then computed in US cents as the branch's `vault_usd_equivalent_cents` minus the quantity `vault_limit_usd_cents` multiplied by 8500 basis points and divided by ten thousand, rounded half up — in other words, enough to bring the vault back down to eighty-five percent of its ceiling. That US surplus is converted to the selected position's currency by multiplying by the selected wholesale mid rate for that currency and dividing by 1,000,000, with the result rounded **down** to a whole minor unit.

The manifest is then filled by a largest-note-first waterfall over the selected position's mix. Walking the mix entries in **descending** order of `denomination_minor_units`, the number of notes taken from an entry is the lesser of that entry's `available_note_count` and the remaining surplus divided by the entry's `denomination_minor_units` rounded down to a whole note count; if that number is greater than zero, an entry naming the `denomination_minor_units` and that `note_count` is added to the manifest and the remaining surplus is reduced by the notes taken multiplied by their face value. Only available notes are eligible — quarantined and written-off notes never ship. Because whole notes are only ever taken while they still fit inside the remaining surplus, the finished manifest may be worth somewhat less than the theoretical surplus, and that is intended. It may even come out empty, when every available note is individually larger than the surplus that has to leave; the shipment is raised all the same — with an empty `manifest_denominations`, a `manifest_minor_units` of 0 and a `manifest_usd_equivalent_cents` of 0 — and `repatriation_pending` is still set to true, so no second automatic shipment follows it. The manifest is emitted ordered by `denomination_minor_units` ascending, matching the ordering convention of every other denomination array in this service. The resulting shipment is created with `direction` `REPATRIATION`, `status` `REQUESTED`, `auto_generated` true, and its `currency_code` taken from the selected position; from there it follows exactly the same scheduling, dispatch, arrival and reconciliation path as an operator-raised shipment. Since nothing else announces its existence, the shipment list is the only discovery channel for automatically generated repatriations; it accepts optional `branch_id`, `armored_route_id`, `direction`, `status` and `auto_generated` filters, and individual shipments may be read to inspect the manifest, window, variance and write-off.

## 4. Endpoint Definitions

Every endpoint in this service is mounted at the root; there is no shared API prefix. A trailing slash is insignificant, so `/branches` and `/branches/` reach the same endpoint. Routing is decided before the rank-1 authentication check of §2.8, and it produces the only two error responses in this service that carry `ERR_INVALID_REQUEST` at a status other than 400: a path that matches no route at all is refused with `ERR_INVALID_REQUEST` at HTTP 404, and a known path called with a method it does not support is refused with `ERR_INVALID_REQUEST` at HTTP 405 — in both cases regardless of whether the authentication headers were present or valid. Creation endpoints that mint a new resource respond with HTTP 201; every other successful call — reads, lists, state transitions and the clock control — responds with HTTP 200. A successful mutation returns the created or updated resource in `data` unless stated otherwise; the clock control and the branch rate board return their own computed shapes as described in §2.4 and §2.10.
