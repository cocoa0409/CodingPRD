# Dam Safety Program API — Product Requirements Document

## 1. Introduction

A state dam safety program is, at bottom, a consequence-management program. The engineering condition of an embankment matters only in proportion to what lies downstream of it, and downstream development changes far faster than dams do. A structure that was farmed pasture in 1961 may sit above a subdivision, a school and an evacuation route today, and the moment that becomes true the same dam demands a shorter inspection interval, a richer emergency action plan, a more expensive permit review and a compressed remediation clock. The service specified here is the regulatory system of record for that reality: it holds the dam inventory, the breach-analysis and consequence-assessment record that assigns hazard class, the engineer-performed inspection cycle, the deficiency and enforcement ladder run against owners, the emergency action plan and annual exercise regime, the permitting queue for construction, repair and removal, the owner fee ledger, and the high-water monitoring and coordinated emergency drawdown workflow.

Three problems drive the design. First, **the program staff cannot be the arithmetic**: consequence scores, inspection due dates, statutory response windows, daily civil penalty accruals, permit fees and reservoir storage commitments must all be derived by the server from stored inputs, identically every time, so that an owner disputing a penalty and an engineer defending a classification are looking at the same numbers. Second, **reclassification must propagate**: when a newly certified consequence assessment moves a dam from `SIGNIFICANT` to `HIGH`, the inspection schedule, the plan validity, the notification-contact minimum, the permit fee uplift and the penalty rate must all move with it, and an emergency action plan built on a superseded inundation map must be pulled back for revision rather than silently kept on the shelf. Third, **the emergency path must be safe under contention**: a coordinated drawdown consumes shared downstream channel capacity and finite reservoir storage, so the system has to reject a release request whose author was working from an out-of-date picture of the reach rather than let two coordinators oversubscribe the same channel.

The API is a flat REST surface — every business collection is addressed at a top-level path segment, and parent linkage travels in the request body rather than in nested URLs. Time is explicit and injectable: every temporal rule in this document reads a **logical UTC clock** that scenarios advance deliberately, never the host wall clock. That single decision is what makes overdue detection, licence lapse, plan expiry, penalty accrual and exercise currency testable and auditable.

## 2. Global Specifications & System-Wide Principles

### 2.1. Program Actors and Role-Based Access Control

Every request to the service carries two mandatory headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they are acting. Both must be present and non-empty on every endpoint with the single exception of the logical-clock capability described in §2.4, which is a test-harness affordance; a request missing either header, or supplying one that is empty or consists only of whitespace, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The program recognises exactly four roles, spelled here exactly as they must appear in `X-User-Role`: `ProgramAdmin`, `Engineer`, `DamOwner`, and `EmergencyCoordinator`. If the supplied role is not among the roles authorised for the requested operation, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). Role authorisation is decided **before the request body is parsed**, so a `DamOwner` who posts a syntactically broken inspection payload still receives `ERR_FORBIDDEN_ROLE` rather than a validation error.

`ProgramAdmin` is state dam safety program staff: they own the inventory, the inspection calendar, enforcement, the fee ledger and the state's intervention authority. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — for example as `posted_by_user_id` on a ledger entry, or as `accepted_by_user_id` when an administrator accepts an inspection — but it never compares it to any entity's `id`.

`EmergencyCoordinator` is the state emergency management coordinator who runs high-water monitoring and executes coordinated drawdowns. When `X-User-Role` is `EmergencyCoordinator`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The server may record it — for example as `recorded_by_user_id` on a pool-elevation reading, or as `logged_by_user_id` on an exercise this coordinator logs — but does not compare it to any entity's `id`.

`Engineer` is a licensed professional engineer who performs inspections, certifies consequence assessments, reviews emergency action plans and permit applications, and verifies remediation work. When `X-User-Role` is `Engineer`, `X-User-ID` is the `id` of the acting `Engineer` row; ownership and assignment checks on any resource that references an engineer compare the resource's engineer reference to `X-User-ID`. Concretely, an engineer's own identifier is what lands in `prepared_by_user_id` when they file a consequence assessment, in `accepted_by_user_id` when they accept another engineer's inspection, and in `verified_by_user_id` when they verify or reject a remediation response.

`DamOwner` is a registered owner of record. When `X-User-Role` is `DamOwner`, `X-User-ID` is the `id` of the acting `Owner` row; ownership checks on any resource that references an owner compare the resource's owner reference to `X-User-ID`. An owner's identifier lands in `logged_by_user_id` when they log an emergency exercise.

Two failures are specific to the entity-backed roles. If `X-User-Role` is `Engineer` or `DamOwner` but `X-User-ID` does not resolve to a row of the corresponding backing entity, the request fails with `ERR_IDENTITY_UNKNOWN` (HTTP 403); this is checked after resource existence and before any ownership comparison. If the identity resolves but the acting owner is not the owner of the targeted dam, plan, permit or order, the request fails with `ERR_NOT_RESOURCE_OWNER` (HTTP 403) — one owner may never act on another owner's dam. The parallel check for engineers, where the acting engineer is not the engineer bound to the target row, yields `ERR_NOT_ASSIGNED_ENGINEER` (HTTP 403). §2.5 fixes the precedence among all of these.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly 20 characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one instant in the API read from the host wall clock rather than from the logical clock of §2.4, so it keeps moving between requests and does not jump when a scenario advances the logical clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes, and the 5xx fault noted below) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. Its wording is free text and carries no contract; only `error_id` and the HTTP status code do.
- Failures raised before any business handler runs use this same envelope with an `error_id` of `ERR_INVALID_REQUEST`, served with the framework's own status rather than 400: a request whose path matches no route is `ERR_INVALID_REQUEST` at HTTP 404, a request whose method is not allowed on an otherwise-matched path is `ERR_INVALID_REQUEST` at HTTP 405, a request rejected as malformed before dispatch is `ERR_INVALID_REQUEST` at HTTP 400, and an unexpected server fault is `ERR_INVALID_REQUEST` at HTTP 500 (the only 5xx this API emits, and the only place the error envelope accompanies a non-4xx status). Every rule in §2.5 and §3 that raises `ERR_INVALID_REQUEST` does so at HTTP 400, as §5 records. A trailing slash is not significant in any path: `/dams` and `/dams/` address the same route.

### 2.3. Pagination

Every list endpoint is paginated through two optional query parameters. `limit` defaults to 10, has a minimum of 1 and a maximum of 100; a supplied `limit` below 1 or above 100 is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400). `offset` defaults to 0, has a minimum of 0, and a negative value is likewise rejected with `ERR_INVALID_REQUEST`.

List results are ordered by `created_at` ascending in every case, with ties on `created_at` — routine here, because `created_at` is stamped from the logical clock — broken by insertion order so that the earlier-inserted row is returned first; never by `id`, and never by any domain field, even where a domain ordering (such as ledger `sequence_no`) coincides with insertion order. The `meta` block of a list response carries `limit` and `offset` as they were resolved for the request, `total_count` as the number of rows matching the filters **before** the limit and offset window is applied, and `has_more` as a boolean that is true exactly when rows matching the filters remain beyond the returned window.

Filters named on a list endpoint are combined conjunctively: a request for dams filtered by both `hazard_class` and `inspection_overdue` returns only dams satisfying both. An unknown enum member supplied to a filter is a malformed request, not an empty result set. An id-valued filter is the opposite case: it is matched literally and is never checked for existence, so a filter naming an id no row references is not an error but simply matches nothing, returning an empty `data` array with `total_count` 0 and `has_more` false.

### 2.4. Resource Identity, Timestamps, Versioning and the Logical Clock

Every resource the program stores is identified by a server-minted UUID exposed as `id`. Identifiers carry no type prefix and no embedded meaning; clients must never construct or parse them. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was inserted, read from the logical UTC clock described below and never from the host wall clock — so two rows created without an intervening clock advance carry byte-identical `created_at` values. That rendering is universal rather than specific to `created_at`: every instant this API emits — `updated_at`, `certified_at`, `performed_at`, `window_start`, `compliance_deadline_at`, `expires_at`, `conducted_at`, `reading_at`, `swept_at` and all the rest — is normalised to UTC and written with exactly three fractional digits and a trailing `Z`, whatever offset or fractional precision it was supplied in. Conversely, on input an instant supplied without a timezone offset is read as UTC, an offset-bearing instant is converted to UTC before storage, and fractional seconds are honoured to microsecond precision with any further digits truncated.

Most resources additionally carry `updated_at` — same format, refreshed on every mutation of that row — and `version`, an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation. Three record types are append-only journal rows and therefore carry **only** `id` and `created_at`: an `EapExercise` (a logged emergency exercise), an `ElevationReading` (a pool observation during a high-water event), and a `FeeLedgerEntry` (a posting on an owner's fee ledger). For those three, both `updated_at` and `version` are absent from the resource entirely. Owners, engineers, river reaches, dams, consequence assessments, inspections, deficiencies, remediation orders, emergency action plans, permits, high-water events and drawdown orders all carry the full set.

Because a dam is the hub of this domain, its `version` is the busiest counter in the system: it advances when a certification reclassifies it, when an inspection acceptance rates it, when a plan write refreshes its plan status, when a deficiency opens or closes, when enforcement or intervention moves its regulatory posture, and when a drawdown commits or releases storage. Every one of those advances is called out explicitly in §3 where it occurs. A river reach's `version` advances whenever its committed release rate changes.

Time is a first-class, injectable input. A **logical UTC clock** — not the host wall clock — is the sole time source for every temporal rule in this document: licence expiry, inspection due dates and overdue flags, remediation deadlines, penalty accrual, plan expiry, exercise currency, and the "not in the future" checks on reported instants. A `ProgramAdmin`-only capability sets the clock to a supplied `to_iso8601` instant, and it is the one endpoint that accepts a request carrying no identity headers at all; once either header is present and non-blank, though, the pair is judged and the request is rejected with `ERR_FORBIDDEN_ROLE` (403) unless `X-User-Role` reads exactly `ProgramAdmin` — so a lone `X-User-ID` with no role header, and any role other than `ProgramAdmin`, both fail with 403 rather than 401. That role judgement precedes the body, and a successful set returns HTTP 200 with an empty `data` object rather than any resource. The clock is strictly monotonic: a requested value earlier than the current clock is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while setting it to exactly its current value succeeds as a no-op. At the start of every scenario the clock reads `2026-08-01T00:00:00Z`. Advancing the clock does not itself mutate any row: an engineer's `license_status` and a dam's `inspection_overdue` are re-derived on the next read, and the enforcement consequences of elapsed time are applied only by the compliance sweep described in §3.9.

Path parameters are validated left to right against the URL hierarchy: the leftmost `{id}` must resolve to an existing row of its expected entity before any deeper segment, any body **reference** or any business rule is considered. That resolution is rung 4 of the ladder in §2.5 and therefore sits *after* the whole syntactic layer rather than before it: a request whose body is malformed and whose path id is also unknown reports `ERR_INVALID_REQUEST`, and the not-found error surfaces only once the payload has been read successfully. Nested reads — a plan's exercises, an event's readings, an owner's ledger entries — therefore report the parent's own not-found error when the parent does not exist, and never an empty list.

### 2.5. Rejection Precedence: The Order in Which a Request Is Judged

Requests are judged against an explicitly ordered ladder of checks. The **first** violated rule determines the response, and no later rule is evaluated. This ordering is part of the contract: two defects in a single request always surface as the higher-priority one. Reading the ladder from the top:

1. **Identity headers present** — both `X-User-ID` and `X-User-Role` non-empty on every endpoint except the clock-setting capability; otherwise `ERR_UNAUTHENTICATED` (401).
2. **Role authorised** for the endpoint; otherwise `ERR_FORBIDDEN_ROLE` (403). Decided before the body is parsed.
3. **Syntactic validity** of body and query parameters — required fields present, enum members known, numbers within their stated bounds, ISO 8601 instants parseable, `window_start` strictly before `window_end`, an elevation reading's `reading_at` at or before the logical clock, `limit` within 1 to 100, `offset` at least 0; otherwise `ERR_INVALID_REQUEST` (400). Two of those are semantic tests carried at the syntactic layer on purpose — a drawdown window that ends at or before it starts, and a pool reading dated after the clock, are both reported as `ERR_INVALID_REQUEST` before the path or body ids in the same request are resolved at all, unlike the future-dating checks on an inspection (rung 27) and on an exercise (rung 34), which carry their own error codes far lower down the ladder. This layer catches a non-positive `height_ft`, a negative `population_at_risk`, a `requested_release_cfs` that is zero or negative, an `amount_cents` of exactly zero, and any unknown enum member. Three conventions fix how this layer reads a payload. A field that is present but JSON `null` is treated exactly as if it had been omitted: a required field so supplied is reported as missing, and an optional one falls back to its documented default. Scalars are coerced before they are bounds-checked, so a JSON string that parses as a number is accepted wherever a number or an integer is required, a float with no fractional part is accepted wherever an integer is required, a date-only string is accepted wherever an instant is required and read as midnight UTC on that date, and the strings `true` and `false` in any letter case are accepted wherever a boolean is required — while a JSON boolean is never accepted as a number or an integer. And a request body that is absent or unparseable is read as an empty JSON object, so its required fields are reported as missing rather than as a distinct malformed-body failure, whereas a body that parses to a JSON value that is not an object is rejected outright. Query parameters are checked in the order `limit` then `offset`, so a request supplying both out of range reports the `limit` failure.
4. **Path existence** — every `{id}` in the path resolves to an existing row of its expected entity, reported as `ERR_OWNER_NOT_FOUND`, `ERR_ENGINEER_NOT_FOUND`, `ERR_REACH_NOT_FOUND`, `ERR_DAM_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND`, `ERR_DEFICIENCY_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_EAP_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_EVENT_NOT_FOUND` or `ERR_DRAWDOWN_NOT_FOUND` as appropriate (all HTTP 404). Path existence outranks body references, so a request carrying both a bad path id and a bad body id reports the path error.
5. **Body reference existence** — every foreign reference in the request body resolves to an existing row, reported with the same 404 family (`ERR_OWNER_NOT_FOUND`, `ERR_ENGINEER_NOT_FOUND`, `ERR_REACH_NOT_FOUND`, `ERR_DAM_NOT_FOUND`, `ERR_EVENT_NOT_FOUND`). This layer applies to dam registration, consequence-assessment filing, inspection scheduling, plan drafting, permit application, high-water event declaration, drawdown request, and permit review assignment. Body references are resolved in the order the fields are listed for that operation.
6. **Backing-entity identity** — for the entity-backed roles `Engineer` and `DamOwner`, `X-User-ID` resolves to a row of the backing entity; otherwise `ERR_IDENTITY_UNKNOWN` (403). Applies to every endpoint authorised for `Engineer` or `DamOwner`, and sits after existence checks and before ownership checks.
7. **Owner ownership** — for `DamOwner`-authorised operations, `X-User-ID` equals the owning owner of the target dam, plan, order or permit; otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to plan drafting, plan submission, remediation-order response, permit application, permit resubmission, and reading an owner's fee ledger. The check is scoped to the acting role, not to the endpoint: it is evaluated only when `X-User-Role` is `DamOwner`, so on an operation open to both roles a `ProgramAdmin` is never subject to it whatever `X-User-ID` they present.
8. **Engineer assignment** — for engineer-bound operations, `X-User-ID` equals the engineer bound to the target row; otherwise `ERR_NOT_ASSIGNED_ENGINEER` (403). Applies to inspection submission (the inspection's engineer of record) and permit decision (the permit's assigned review engineer). For a permit decision this check is **skipped entirely while the permit has no assigned review engineer** — an unassigned permit is reported instead by the permit state check at rung 14.
9. **Assessment state** — certification requires the assessment to be `DRAFT`; otherwise `ERR_ASSESSMENT_INVALID_STATE` (409). A second certification of the same row fails here.
10. **Inspection state** — submission requires `SCHEDULED` or `RETURNED`; acceptance and return both require `SUBMITTED`; `ACCEPTED` is terminal. Otherwise `ERR_INSPECTION_INVALID_STATE` (409).
11. **Deficiency state** — issuing a remediation order requires the deficiency to be `OPEN` or `ESCALATED`; a deficiency already `ORDERED`, `REMEDIATION_SUBMITTED` or `CLOSED_VERIFIED` fails with `ERR_DEFICIENCY_INVALID_STATE` (409).
12. **Remediation order state** — filing a response requires `ISSUED`; verification requires `RESPONSE_FILED`; the penalty preview requires `ISSUED` or `RESPONSE_FILED`. Otherwise `ERR_ORDER_INVALID_STATE` (409).
13. **Plan state** — submission requires `DRAFT` or `REVISION_REQUIRED`; review requires `SUBMITTED`; logging an exercise requires `APPROVED`. Otherwise `ERR_EAP_INVALID_STATE` (409).
14. **Permit state** — review assignment requires `SUBMITTED`; a decision requires `UNDER_ENGINEERING_REVIEW`; resubmission requires `RETURNED_FOR_REVISION`. Otherwise `ERR_PERMIT_INVALID_STATE` (409). This rung outranks every fiscal check below, so a decision attempted on a still-`SUBMITTED` permit reports the state error even when the owner is also delinquent.
15. **High-water event state** — recording a reading and standing an event down both require `MONITORING` or `EMERGENCY`; requesting a drawdown against a `STOOD_DOWN` event fails here. Otherwise `ERR_EVENT_INVALID_STATE` (409).
16. **Drawdown order state** — coordination requires `REQUESTED`; activation requires `COORDINATED`; completion requires `ACTIVE`; cancellation requires any non-terminal status. Otherwise `ERR_DRAWDOWN_INVALID_STATE` (409).
17. **Dam operability** — the dam's regulatory posture is not `BREACHED`, and is not `REMOVAL_PERMITTED` for operations that presuppose a standing dam; otherwise `ERR_DAM_NOT_OPERABLE` (409). Applies to consequence-assessment filing, certification, inspection scheduling, permit application, high-water event declaration, drawdown request, and plan drafting. A breached dam is out of the program entirely, so this rung fires on all seven of those operations; the `REMOVAL_PERMITTED` half of the rung is narrower and fires on exactly two of them — filing a new consequence assessment and applying for a permit. A removal-permitted dam therefore still accepts inspection scheduling, plan drafting, high-water event declaration, drawdown requests and the certification of an assessment already on file, but refuses a new consequence assessment and refuses a permit application of any type, `REPAIR` and `REMOVAL` included.
18. **Dam stale-view rejection** — plan drafting must quote the dam version the client last observed; otherwise `ERR_STALE_DAM_VERSION` (412). Placed after every state check, so a stale version quoted against a breached dam still reports `ERR_DAM_NOT_OPERABLE`.
19. **Reach stale-view rejection** — drawdown coordination must quote the reach version the coordinator last observed; otherwise `ERR_STALE_REACH_VERSION` (412). This outranks the capacity and storage checks, so a stale reach version is reported even when the reach is simultaneously over capacity.
20. **Engineer licence current** — the acting or referenced engineer's licence has not lapsed against the logical clock; otherwise `ERR_ENGINEER_LICENSE_EXPIRED` (422). Applies to eight operations: inspection scheduling, inspection submission, inspection acceptance, assessment certification, plan review, permit review assignment, permit decision, and remediation verification. No unlicensed engineering act is ever recorded, which is why this rung outranks every temporal and constraint check beneath it.
21. **Engineer hazard certification** — the dam's hazard class is among the engineer's certified classes; otherwise `ERR_ENGINEER_NOT_CERTIFIED` (422). Applies to inspection scheduling, inspection submission, and assessment certification.
22. **Construction blocked on an unsatisfactory dam** — a `CONSTRUCTION` permit may not be issued while the dam's safety rating is `UNSATISFACTORY`; otherwise `ERR_UNSAFE_DAM_PERMIT_BLOCKED` (422). Applies to the permit decision only. `REPAIR` and `REMOVAL` permits remain issuable — that carve-out is the entire point of the rule.
23. **Approved plan required for high-hazard operations** — when the dam's hazard class is `HIGH`, its latest plan status must be `APPROVED`; otherwise `ERR_EAP_NOT_APPROVED` (422). Applies to two operations: the permit decision and the drawdown request.
24. **Event escalated before release begins** — activating a coordinated release requires the event to have reached `EMERGENCY`; otherwise `ERR_EVENT_NOT_IN_EMERGENCY` (422). Applies to drawdown activation only.
25. **Dam classified** — the dam's hazard class is not `UNCLASSIFIED`; otherwise `ERR_DAM_UNCLASSIFIED` (422). Applies to four operations: inspection scheduling, permit application, plan submission, and drawdown request. Nothing may be scheduled, permitted or planned against a dam that has never had a certified consequence assessment, and this rung outranks the engineer window-conflict and reach-capacity checks beneath it.
26. **Inspection performed inside its window** — the reported `performed_at` falls within the reserved field-visit window; otherwise `ERR_OUTSIDE_INSPECTION_WINDOW` (422). Applies to inspection submission.
27. **Inspection not reported from the future** — `performed_at` is at or before the logical clock; otherwise `ERR_PERFORMED_AT_IN_FUTURE` (422). Applies to inspection submission.
28. **Reach channel capacity** — the windowed committed release plus the new release does not exceed the reach's channel capacity; otherwise `ERR_REACH_CAPACITY_EXCEEDED` (409). Applies to drawdown coordination. This is an aggregate rule: each individual order can sit within capacity while their overlapping sum does not.
29. **Reservoir storage sufficiency** — the planned release volume does not exceed the dam's available conservation storage; otherwise `ERR_INSUFFICIENT_STORAGE` (409). Applies to drawdown coordination, and is evaluated after the capacity rule, so an order failing both reports `ERR_REACH_CAPACITY_EXCEEDED`.
30. **Engineer calendar conflict** — the requested field-visit window does not conflict with any of the engineer's other non-accepted windows once the travel buffer is applied; otherwise `ERR_ENGINEER_WINDOW_CONFLICT` (409). Applies to inspection scheduling.
31. **Notification contacts sufficient** — the plan lists at least the hazard-class minimum number of notification contacts; otherwise `ERR_INSUFFICIENT_NOTIFICATION_CONTACTS` (422). Applies to plan submission.
32. **Inundation map current** — for a dam that requires a plan, the plan's inundation map reference matches the dam's certified assessment; otherwise `ERR_INUNDATION_MAP_STALE` (422). Applies to plan submission.
33. **Breach analysis complete** — travel time, inundation area and peak outflow are all strictly positive at certification; otherwise `ERR_BREACH_ANALYSIS_INCOMPLETE` (422). Applies to assessment certification.
34. **Exercise not logged from the future** — the exercise's `conducted_at` is at or before the logical clock; otherwise `ERR_EXERCISE_DATE_IN_FUTURE` (422). Applies to exercise logging.
35. **Owner not delinquent** — the owner's fee balance is below the delinquency threshold when a permit decision is taken; otherwise `ERR_OWNER_DELINQUENT` (402). Applies to the permit decision, and is outranked by the permit state check at rung 14.
36. **Financial assurance posted** — when the dam's hazard class is `HIGH`, the owner's posted bond meets the statutory floor; otherwise `ERR_INSUFFICIENT_FINANCIAL_ASSURANCE` (402). Applies to the permit decision, and is evaluated after the delinquency check, so an owner failing both reports `ERR_OWNER_DELINQUENT`.
37. **Segregation of duties** — the acting user is not the same person who performed the step being reviewed; otherwise `ERR_SEGREGATION_OF_DUTIES` (409). Applies to two operations: inspection acceptance and permit review assignment. Because this rung sits below the state checks, an engineer who tries to accept their own already-`ACCEPTED` inspection receives `ERR_INSPECTION_INVALID_STATE` instead.
38. **Inventory code uniqueness** — a dam's `nid_code` is unique program-wide, independent of owner; otherwise `ERR_DUPLICATE_NID_CODE` (409). Applies to dam registration.
39. **Licence number uniqueness** — an engineer's `license_number` is unique across all engineers; otherwise `ERR_DUPLICATE_LICENSE_NUMBER` (409). One professional licence, one engineer row. Applies to engineer registration.
40. **Ledger sign agreement** — the sign of a posted `amount_cents` agrees with its `entry_type`; otherwise `ERR_LEDGER_SIGN_MISMATCH` (422). Applies to owner fee adjustments. A zero amount never reaches this rung; it is rejected at rung 3.
41. **Event and dam agreement** — a drawdown order names the same dam as the high-water event it responds to; otherwise `ERR_EVENT_DAM_MISMATCH` (422). Applies to the drawdown request.
42. **Clock monotonicity** — a requested clock value is at or after the current logical clock; otherwise `ERR_CLOCK_NOT_MONOTONIC` (422). Applies to the clock-setting capability.

### 2.6. Precision, Rounding and Units

Every rounding operation in this specification is **round half up** — a value exactly at the midpoint rounds away from zero. Three precision regimes coexist:

- **Money is whole cents.** Every monetary field ends in `_cents` and holds an integer. Permit fees, penalty rates, penalty assessments and ledger amounts are all rounded half up to whole cents, and where a formula rounds more than once (a review fee, a surcharge and a credit are each rounded independently; a daily penalty is rounded once per day) the intermediate roundings are part of the contract and cannot be collapsed into one final rounding.
- **Consequence scores and freeboard are two decimal places**, rounded half up. A consequence score therefore lies on the `0.00` to `100.00` scale in hundredths, and a freeboard measurement in feet likewise.
- **Reservoir volumes in acre-feet are three decimal places**, rounded half up — both a planned release volume and the committed and available storage figures derived from it. Every quantity in all three regimes travels in the JSON body as a number, never as a string, and JSON numeric rendering does not preserve trailing zeros — a consequence score of `45.00` is emitted as `45.0` and a freeboard of `3.00` feet as `3.0`. The rounded value is the contract; the width of the literal is not.

Day counts, month counts, contact counts, participant counts and ledger sequence numbers are integers with no rounding. Calendar-month arithmetic preserves the day of month: an instant of 2019-04-15 advanced by 24 calendar months is 2019-04-15 plus two years, that is 2021-04-15, with the time of day carried through unchanged; where the target month is too short to hold the source day of month the day is clamped down to that month's last day, so 31 January advanced by one calendar month is 28 February in a common year and 29 February in a leap year, and the clamp never carries into the following month. Day arithmetic adds exact 24-hour days, so a deadline computed from an issue instant carries that instant's time of day. All instant comparisons are made at full ISO 8601 precision.

### 2.7. Stale-View Protection on Shared Program Records

Two operations write through a parent record that other actors are concurrently reshaping, and both use optimistic concurrency control against that parent's `version`.

Drafting an emergency action plan requires a non-optional `expected_dam_version` field carrying the `version` of the dam that the owner last observed. If that value does not equal the dam's current `version`, the draft is rejected with `ERR_STALE_DAM_VERSION` (HTTP 412). The rule exists because a new plan legitimately supersedes the dam's plan of record once approved, and because every plan write refreshes the dam's plan-status field — so a writer holding a stale view of the dam would be filing a superseding plan without having seen the plan or the reclassification that moved the dam in the meantime.

Coordinating a drawdown order requires a non-optional `expected_reach_version` field carrying the `version` of the river reach the coordinator last observed. If that value does not equal the reach's current `version`, coordination is rejected with `ERR_STALE_REACH_VERSION` (HTTP 412). Coordinating any order on a reach advances that reach's `version`, so a request still quoting an earlier version is working from an out-of-date picture of how much of the channel is already committed. Note that such a request's own status precondition — the order still being `REQUESTED` — remains satisfied in that situation, which is precisely why the version check is required rather than implied.

Both fields are validated only as integers, with no lower bound of their own: a zero or negative expectation is not a malformed request but simply a value no stored `version` can equal, so it is reported as the stale-view rejection (412) rather than as `ERR_INVALID_REQUEST`. Both checks are pure equality against the parent's current `version` — being *ahead* of the stored version fails exactly as being behind it does. No other endpoint accepts a version field. Requests to operations outside these two must not be expected to carry one, and the presence of `version` on a resource is a read-only artefact everywhere else.

### 2.8. Hazard Class as the Program's Master Dial

A dam's `hazard_class` is the single dial from which nearly every program obligation is read. It takes exactly one of four values — `UNCLASSIFIED`, `LOW`, `SIGNIFICANT`, `HIGH` — and it is never set directly by any actor. A newly registered dam is `UNCLASSIFIED`; thereafter the dam's class is always the `certified_hazard_class` of its single certified consequence assessment, and its `current_consequence_score` is that assessment's `certified_score`. While no certified assessment exists, `hazard_class` is `UNCLASSIFIED` and `current_consequence_score` is null.

Six program requirements tighten monotonically as the dial turns:

- **Periodic inspection interval.** A `HIGH`-hazard dam is inspected every 12 months; a `SIGNIFICANT` dam every 24 months; a `LOW` dam every 60 months. An `UNCLASSIFIED` dam is scheduled on the same 60-month interval as a `LOW` dam.
- **Whether a plan is required at all.** The derived flag `eap_required` on a dam is true exactly when its `hazard_class` is `SIGNIFICANT` or `HIGH`, and false for `LOW` and `UNCLASSIFIED`.
- **Notification contacts a plan must list.** A plan on a `HIGH`-hazard dam must wire at least 8 downstream notification contacts into its flowchart; a `SIGNIFICANT` dam at least 4; a `LOW` or `UNCLASSIFIED` dam at least 1. Each minimum is inclusive — a count exactly equal to the minimum passes.
- **How long an approved plan stays valid.** An approved plan on a `HIGH`-hazard dam expires 36 calendar months (three years) after approval; on a `SIGNIFICANT` dam, 60 calendar months (five years). A plan on a `LOW`-hazard dam never expires: its `expires_at` stays null and no sweep can ever move it to `EXPIRED`.
- **Exercise rigour.** The minimum number of notification-chain participants in an annual exercise is 6 for a `HIGH`-hazard dam, 4 for `SIGNIFICANT`, and 2 for `LOW` and `UNCLASSIFIED`, each minimum inclusive. A `HIGH`-hazard dam additionally accepts only `FUNCTIONAL` or `FULL_SCALE` exercise formats; `SIGNIFICANT`, `LOW` and `UNCLASSIFIED` dams accept `TABLETOP`, `FUNCTIONAL` or `FULL_SCALE`.
- **Financial assurance floor.** Before any permit may issue on a `HIGH`-hazard dam, the owner's `financial_assurance_bond_cents` must be at least 25,000,000 cents — a quarter of a million dollars posted against removal obligations. The comparison is inclusive, and no floor applies at the other three classes.

Two further dials read the same value: a remediation deadline is compressed by hazard class and a daily penalty rate is uplifted by it (§3.4), and a permit's engineering review fee carries a hazard uplift (§3.6). In every one of these lookups, `UNCLASSIFIED` behaves identically to `LOW`.

The engineer side of the dial is `certified_hazard_classes`, a non-empty array on each engineer drawn from `LOW`, `SIGNIFICANT` and `HIGH`. An engineer may only be scheduled to inspect, submit findings on, or certify an assessment for a dam whose hazard class appears in that array; an `UNCLASSIFIED` dam is checked against `LOW` certification. A `HIGH`-hazard dam therefore cannot be touched by an engineer certified only for `LOW` and `SIGNIFICANT` work.

### 2.9. Cascade Discipline and Derived-Field Reconciliation

The dam record carries a large number of derived fields, and the program's correctness rests on them being reconciled inside the same request that changes their inputs — never lazily, never on a later read. A dam exposes `registered_at`, its structural inputs `height_ft`, `gross_storage_acre_ft`, `crest_elevation_ft`, `normal_pool_elevation_ft` and `year_completed`, and its identity fields `name` and `nid_code`; alongside those it exposes the derived `hazard_class`, `current_consequence_score`, `safety_status`, `next_inspection_due_at`, `inspection_overdue`, `open_deficiency_count`, `latest_eap_status`, `eap_required`, `committed_drawdown_acre_ft` and `available_conservation_storage_acre_ft`, plus the system-managed `regulatory_status`. Whenever an operation in §3 changes any input to one of those, the derived value is rewritten in the same request and the dam's `version` and `updated_at` advance.

Two independent state dimensions live on a dam and they never write each other. `safety_status` — one of `UNRATED`, `SATISFACTORY`, `CONDITIONALLY_SATISFACTORY`, `POOR`, `UNSATISFACTORY` — is advanced **only** by inspection acceptance, and always to the accepted inspection's condition rating. `regulatory_status` — one of `REGISTERED`, `UNDER_ENFORCEMENT`, `REMOVAL_PERMITTED`, `STATE_INTERVENTION`, `BREACHED` — is advanced **only** by enforcement default, order satisfaction, removal permitting and state intervention. No transition on the safety dimension ever touches the regulatory dimension, and no transition on the regulatory dimension ever touches the safety dimension; an operation that legitimately writes both does so through two separately specified rules.

Counters are recomputed, not incremented blindly. An owner's `registered_dam_count` is the number of dams whose owner reference is that owner. An engineer's `open_inspection_count` is the number of their inspections whose status is `SCHEDULED`, `SUBMITTED` or `RETURNED`. A dam's `open_deficiency_count` is the number of its deficiencies whose status is `OPEN`, `ORDERED`, `REMEDIATION_SUBMITTED` or `ESCALATED`. A deficiency's `order_count` is the number of remediation orders issued against it. An inspection's `deficiency_count` is the number of deficiency rows it produced, and its `return_count` the number of times it has been returned. A reach's `active_drawdown_count` is the number of its drawdown orders whose status is `COORDINATED` or `ACTIVE`, and its `committed_release_cfs` the sum of those orders' requested release rates. A high-water event's `reading_count` is the number of readings logged against it, its `peak_pool_elevation_ft` the greatest pool elevation among them (null while none exists), and its `current_alert_level` the alert level of the latest reading by `reading_at` descending with ties broken by `created_at` ascending — `NORMAL` while no reading exists. A plan's `accepted_exercise_count` is the number of its exercises graded `ACCEPTED`.

Where a "latest" row must be picked, the tie-break rule is fixed and never involves `id`. The dam's `safety_status` follows the latest accepted inspection ordered by `performed_at` descending with ties broken by `created_at` ascending. The dam's `latest_eap_status` follows the most recently created plan by `created_at` descending, with ties on `created_at` broken by insertion order and the more recently inserted plan winning, and reads `NONE` while the dam has no plan at all. A plan's `last_accepted_exercise_at` is the greatest `conducted_at` among its accepted exercises, ties broken by `created_at` ascending, and null when it has none. An elevation reading's predecessor is the reading of the same event with the greatest `reading_at` strictly earlier than it, again with ties broken by `created_at` ascending. In every one of these rules the tie-break falls through one further level when the two candidates also share an identical `created_at`: insertion order decides, keeping whichever row the rule's own direction favours — the earlier-inserted row wherever the tie-break reads `created_at` ascending — and `id` is never consulted at any level.

### 2.10. Licensure, Certification and Segregation of Duties

An engineer record carries `full_name`, a unique `license_number`, and `license_expires_at`, the instant at which the professional licence lapses. The derived `license_status` reads `ACTIVE` while `license_expires_at` is strictly later than the current logical clock and `EXPIRED` from the moment the clock reaches it. Advancing the clock past an engineer's expiry therefore silently disqualifies them from every engineering act in the program without any row being rewritten.

Segregation of duties is enforced at two points, both grounded in the same principle: no engineer reviews their own work. An inspection may not be accepted by the engineer who submitted it — the acting `X-User-ID` must differ from the inspection's engineer of record. And a permit may not be assigned for engineering review to the engineer of record on the dam's latest accepted inspection, because that engineer's own rating of the structure is an input to the permit decision. Both failures are reported as `ERR_SEGREGATION_OF_DUTIES` (HTTP 409).

## 3. Business Logic & Workflows

### 3.1. Building the Inventory: Owners, Engineers, Reaches and Dams

Program staff seed the world before any regulatory activity can happen. Registering an owner records their `legal_name` (1 to 160 characters, non-empty once surrounding whitespace is trimmed), their statutory `owner_type` — one of `PRIVATE`, `MUNICIPAL`, `UTILITY`, `IRRIGATION_DISTRICT`, the category that determines how far the state's intervention authority reaches — a `contact_email` that must contain an `@` character and is the address to which orders and enforcement correspondence are sent, and a `financial_assurance_bond_cents` amount of at least 0 that defaults to 0 when omitted. A freshly registered owner starts with `fee_balance_cents` of 0, a `delinquency_status` of `CURRENT`, and a `registered_dam_count` of 0.

Registering an engineer records `full_name`, `license_number` (1 to 40 characters and unique program-wide, a duplicate being rejected with `ERR_DUPLICATE_LICENSE_NUMBER`), `license_expires_at`, and the non-empty `certified_hazard_classes` array, which is stored and echoed back exactly as it was supplied — member order is preserved and a repeated member is not collapsed. The response carries the derived `license_status` evaluated against the current clock and an `open_inspection_count` of 0.

A river reach is the downstream channel that receives any coordinated release. It records a `name`, a `channel_capacity_cfs` that must be a whole number of cubic feet per second of at least 1 — a fractional capacity is a malformed request — and represents the maximum aggregate release the channel can carry without flooding what lies along it, and a `downstream_community` naming the principal community in the reach's inundation corridor. A new reach starts with `committed_release_cfs` of 0, `active_drawdown_count` of 0 and `version` of 1.

Adding a dam to the state inventory is the moment an owner and a reach are bound together. The payload names the `owner_id` of the financially responsible owner and the `river_reach_id` of the reach that would receive a drawdown, plus the dam's `name`, its `nid_code` (1 to 20 characters, unique across all dams — a collision is rejected with `ERR_DUPLICATE_NID_CODE` regardless of which owner holds the other dam), `height_ft` and `gross_storage_acre_ft` both strictly greater than 0, `crest_elevation_ft` as the overtopping datum against which freeboard is measured, `normal_pool_elevation_ft` which must be strictly below the crest — that comparison is a syntactic rule judged at rung 3 and reported as `ERR_INVALID_REQUEST`, so a payload that inverts the two elevations is rejected for that before its `owner_id` or `river_reach_id` is looked up — a `year_completed` between 1700 and 2100 inclusive, and `registered_at`, the instant the dam entered the inventory. A newly registered dam is `UNCLASSIFIED` on hazard, `UNRATED` on safety and `REGISTERED` on regulatory posture. Its inspection clock starts immediately on the unclassified interval: `next_inspection_due_at` is `registered_at` advanced by 60 calendar months, and `inspection_overdue` is derived from that against the current logical clock. Its storage split starts whole — `committed_drawdown_acre_ft` of 0 and `available_conservation_storage_acre_ft` equal to `gross_storage_acre_ft` — and the owner's `registered_dam_count` is incremented in the same request, that write advancing the owner's own `updated_at` and `version` by 1.

Inventory reads are broad. Dams can be listed filtered by `owner_id`, `river_reach_id`, `hazard_class`, `safety_status`, `regulatory_status` and the boolean `inspection_overdue`; owners by `owner_type` and `delinquency_status`; engineers by `license_status`; river reaches take no filter at all. Each list is available to the roles named in §4 and is ordered and paginated per §2.3, and no list is implicitly narrowed to the acting user: a `DamOwner` listing dams, inspections, deficiencies or remediation orders sees every row in the program rather than only their own, and must supply the relevant id filter to narrow the view. The same is true of the single-resource reads in this section and in §3.3 and §3.4 — an owner may read another owner's record, and an engineer another engineer's, because rung 7 of §2.5 does not reach those endpoints.

Alongside the plain dam read sits a computed regulatory snapshot for a single dam, available to `ProgramAdmin`, `Engineer` and `DamOwner`. It reconciles everything the program knows about the structure at the moment of the call, and returns exactly these keys: `dam_id`, `hazard_class`, `safety_status`, `regulatory_status`, `current_consequence_score`, `next_inspection_due_at`, `inspection_overdue`, `open_deficiency_count`, `escalated_deficiency_count` (the number of the dam's deficiencies currently in `ESCALATED`), `latest_eap_status`, `eap_expires_at` (the `expires_at` of the plan that `latest_eap_status` reports, null when the dam has no plan or the plan has no expiry), `eap_exercise_current` (the exercise-currency flag of the dam's `APPROVED` plan, false when there is no approved plan), `outstanding_penalty_cents` (the sum of `assessed_penalty_cents` across all of the dam's remediation orders, where orders that never defaulted contribute 0), `owner_delinquency_status`, `committed_drawdown_acre_ft` and `available_conservation_storage_acre_ft`. Producing the snapshot recomputes the inspection schedule and the exercise-currency flag against the current clock, so a snapshot taken after the clock has advanced past a due date reports `inspection_overdue` as true even before any sweep has run.

### 3.2. Downstream Consequence: Breach Analysis, Scoring and Reclassification

An engineer opens the classification file for a dam by filing a **consequence assessment** — a `DRAFT` record of what a breach would do downstream. The payload names the `dam_id` and carries the corridor census: `population_at_risk`, the permanent population inside the breach inundation corridor; `habitable_structures`, the habitable buildings inside it; `critical_facilities`, counting hospitals, schools, lifeline utilities and evacuation routes; and the breach-analysis outputs `breach_peak_outflow_cfs` (strictly positive), `breach_travel_time_minutes` (a whole number of minutes, at least 1 — the flood-wave travel time to the first habitable structure) and `inundation_area_acres` (strictly positive), together with `inundation_map_ref`, the document reference for the map the breach analysis produced. The three census counts must each be at least 0. Filing records `prepared_by_user_id` as the acting engineer's own identifier — an audit identity, not a foreign-key constraint — and leaves the dam's classification untouched: `status` is `DRAFT`, `certified_score` and `certified_hazard_class` are both null while it stays there, and `certified_at` and `superseded_at` are null.

What filing does produce is the **screening score** in `screening_score` and the class it implies in `recommended_hazard_class`. The score is assembled on a `0.00` to `100.00` scale from four independently capped components, and it is the same assembly for both variants of the calculation with two deliberate differences described below.

The **population component** is the population at risk multiplied by a weight of 2.0 and then by the travel-time multiplier, capped at 60 points. The **structure component** is the number of habitable structures multiplied by a weight of 1.5, capped at 20 points. The **infrastructure component** is the number of critical facilities multiplied by a weight of 5.0, capped at 15 points. The **economic component** is the inundation area in acres divided by 100 and rounded **down** to a whole number — one point per hundred acres of mapped inundation, discarding any remainder — capped at 5 points. Each of the four is capped individually **before** the four are added together, and the sum is never capped again; a score can therefore reach exactly `100.00` only when all four components sit at their caps. The four capped components are then added and the total rounded half up to two decimal places.

The travel-time multiplier is a three-band tier on `breach_travel_time_minutes`: a travel time of less than 30 minutes gives a multiplier of 1.5; a travel time of at least 30 minutes but less than 120 minutes gives 1.0; a travel time of 120 minutes or more gives 0.6. In the **screening variant**, computed at filing and stored in `screening_score`, the multiplier is forced to 1.0 no matter what the travel time is, and the economic component is forced to 0 because the inundation area has not yet been engineer-verified; every other term is identical. In the **certified variant**, computed at certification and stored in `certified_score`, the multiplier is applied to the population component and the economic component is included. The two numbers therefore diverge for the same stored row: for a fast-travel dam the certified score exceeds the screening score, and for a slow-travel dam it can fall below it.

Turning a score into a class uses raw population as an independent path, evaluated in this order. If `population_at_risk` is 25 or more, the class is `HIGH` regardless of score — twenty-five lives at risk is a high-hazard dam by statute. Otherwise, if the score is `45.00` or above, the class is `HIGH`. Otherwise, if the score is `15.00` or above, the class is `SIGNIFICANT`. Otherwise, if `population_at_risk` is 1 or more, the class is `SIGNIFICANT` — any life at risk lifts a dam out of low hazard. Otherwise the class is `LOW`. Every comparison is inclusive at its threshold: a score of exactly `45.00` is `HIGH`, while a score of exactly `44.99` with a population at risk of 0 is `SIGNIFICANT`. This same mapping produces `recommended_hazard_class` from the screening score at filing and `certified_hazard_class` from the certified score at certification.

**Certification** is the act that reclassifies the dam, and it is the widest cascade in the program. Only an `Engineer` may certify, the assessment must still be `DRAFT` (moving `DRAFT → CERTIFIED`), the acting engineer's licence must be active, the engineer must be certified for the dam's current hazard class, and the dam must not be `BREACHED`. The breach analysis must also be complete: `breach_travel_time_minutes`, `inundation_area_acres` and `breach_peak_outflow_cfs` must all be strictly greater than 0, and a screening-only assessment carrying a zero in any of the three is rejected with `ERR_BREACH_ANALYSIS_INCOMPLETE`. On success `certified_score` and `certified_hazard_class` are written from the certified variant and `certified_at` is stamped with the logical clock. The response body of the certification call is the certified assessment itself, not the reclassified dam.

Four cascade links then fire in order, each because of the one before it:

- **Link 1.** Because this row has become the dam's certification of record, the dam's previously certified assessment — there is at most one — moves `CERTIFIED → SUPERSEDED` with `superseded_at` stamped at the clock, and stops contributing to the dam's classification from that instant.
- **Link 2.** Because link 1 replaced the classification source, the dam's `hazard_class` is set to the new `certified_hazard_class`, its `current_consequence_score` to the new `certified_score`, its `eap_required` flag is recomputed, and its `next_inspection_due_at` and `inspection_overdue` are recomputed on the new class's interval. A reclassification from `SIGNIFICANT` to `HIGH` halves the interval from 24 to 12 months against the same baseline visit, so a dam inspected 18 months ago and comfortably current a moment earlier can become overdue the instant it is certified `HIGH`.
- **Link 3.** Because link 2 changed the classification, any emergency action plan on this dam whose status is `APPROVED` and whose `inundation_map_ref` differs from this assessment's `inundation_map_ref` moves `APPROVED → REVISION_REQUIRED`, has its `expires_at` cleared to null, and the dam's `latest_eap_status` is refreshed accordingly. A plan whose map reference already matches the newly certified assessment is left approved and untouched.
- **Link 4.** Because link 3 has left a dam that requires a plan without an approved one, a deficiency is opened automatically: `source` of `SYSTEM_EAP`, `category` of `EAP_MISSING`, `severity` of `SERIOUS`, `status` of `OPEN`, and no inspection reference. It is not opened twice — if a deficiency of that category already sits in `OPEN`, `ORDERED`, `REMEDIATION_SUBMITTED` or `ESCALATED` on this dam, none is created. The dam's `open_deficiency_count` is incremented when a row is created. This link fires **only** as a consequence of link 3 actually moving a plan out of `APPROVED`: certifying an assessment on a dam that has never had an approved plan opens no deficiency at all, however high its new class. The requirement flag itself is read **after** link 2, on the dam's newly certified class, so a certification that reclassifies a dam down to `LOW` moves its approved plan to `REVISION_REQUIRED` under link 3 yet opens no deficiency under link 4.

The dam's `version` increments by 1 across the whole certification, and its safety rating is left exactly as it was — reclassification is a consequence judgement, not a condition judgement. Assessments can be listed filtered by `dam_id` and `status`, and read individually with both the screening and certified figures side by side, which is how a reviewer sees how much the certified breach analysis moved the intake number.

### 3.3. The Periodic Inspection Cycle

Program staff schedule inspections; engineers perform them; someone other than the performing engineer accepts them. Scheduling names the `dam_id`, the `engineer_id` of the engineer of record who must personally perform and submit the field visit, an `inspection_type` of `PERIODIC`, `FOLLOW_UP` or `HIGH_WATER`, and the reserved field-visit window as `window_start` (inclusive) and `window_end` (exclusive, and strictly after the start). Only `PERIODIC` inspections reset the dam's schedule; follow-ups and high-water visits are recorded and rated but leave `next_inspection_due_at` alone. A dam that has never been classified cannot be scheduled at all, which surfaces as `ERR_DAM_UNCLASSIFIED`; the nominated engineer's licence must be active and their certification must cover the dam's hazard class. A new inspection lands in `SCHEDULED` with `performed_at`, `condition_rating` and `narrative` all null, `deficiency_count` and `return_count` at 0, and `accepted_by_user_id` and `accepted_at` null; the engineer's `open_inspection_count` rises by one.

An engineer's calendar is protected by a **travel buffer of 120 minutes** — two hours between consecutive site visits. The conflict test runs against that engineer's inspections across every dam whose status is `SCHEDULED`, `SUBMITTED` or `RETURNED`; accepted inspections are excluded, because once a visit is accepted the engineer's calendar is released. The new window conflicts with an existing one when the new window's start is strictly earlier than the existing window's end plus two hours **and** the existing window's start is strictly earlier than the new window's end plus two hours. Both comparisons are strict, so a new window beginning exactly 120 minutes after an existing window ends does not conflict, while one beginning 119 minutes after it does. A conflict is rejected with `ERR_ENGINEER_WINDOW_CONFLICT`.

Submitting findings is the engineer's own act: the acting `X-User-ID` must equal the inspection's engineer of record, and a mismatch is `ERR_NOT_ASSIGNED_ENGINEER`. Submission carries `performed_at` (the instant the field visit actually happened), a `condition_rating` of `SATISFACTORY`, `CONDITIONALLY_SATISFACTORY`, `POOR` or `UNSATISFACTORY`, a `narrative` recording the findings, and an optional `deficiencies` array. The reported instant must sit inside the reserved window — at or after `window_start` and strictly before `window_end`, so an instant exactly at the start is inside and one exactly at the end is outside, the boundary case rejected with `ERR_OUTSIDE_INSPECTION_WINDOW` — and it must be at or before the current logical clock, equality being permitted, with a later instant rejected as `ERR_PERFORMED_AT_IN_FUTURE`. The engineer's licence must be active and their hazard certification must still cover the dam. Submission moves the inspection `SCHEDULED → SUBMITTED`.

Each element of the `deficiencies` array carries the defect's `category`, its `severity` and a `description`, and produces one deficiency row with `source` of `INSPECTION`, `status` of `OPEN` and the inspection recorded as its `inspection_id`, its `remediation_due_at` and `closed_at` both null and its `order_count` at 0. Categories available to an engineer are `SPILLWAY_CAPACITY`, `SEEPAGE`, `EROSION`, `STRUCTURAL` and `OPERATIONAL`; the two remaining categories, `EAP_MISSING` and `EAP_EXERCISE`, are written only by the system cascades of §3.2, §3.5 and §3.9 and may not be supplied by an engineer: either of them appearing as the `category` of a submitted `deficiencies` element is a malformed request rejected with `ERR_INVALID_REQUEST`, exactly as a wholly unknown member would be. Severity is `MINOR`, `MODERATE`, `SERIOUS` or `CRITICAL`. The inspection's `deficiency_count` is set to the length of the submitted array, the dam's `open_deficiency_count` rises by the number of rows created, and the dam's `version` increments by 1 when that count changes.

A submitted inspection can be sent back. Returning it — an administrator's act carrying a `reason` — moves it `SUBMITTED → RETURNED`, increments `return_count` by one, and retains both `narrative` and `performed_at` for the record. A return never changes the dam's `safety_status`, and it writes nothing on the dam at all: the dam's `updated_at` and `version` are left exactly as they were. The engineer then resubmits, moving `RETURNED → SUBMITTED` again, and this loop may repeat without bound with `return_count` recording how many times it has run. On resubmission `performed_at`, `condition_rating` and `narrative` are overwritten with the newly submitted values; deficiency rows created by the previous submission that are still `OPEN` are deleted and replaced by the rows implied by the new `deficiencies` array, the dam's `open_deficiency_count` is recomputed from scratch, and the dam's `version` increments by 1 when that count changes. Deficiencies from the earlier submission that have already been ordered against are not disturbed by a resubmission.

Acceptance is the terminal act and the only thing in the program that writes a dam's safety rating. Either a `ProgramAdmin` or an `Engineer` may accept, the inspection must be `SUBMITTED`, the acting engineer's licence must be active, and the acting `X-User-ID` must differ from the inspection's engineer of record — accepting one's own submission is `ERR_SEGREGATION_OF_DUTIES`. Acceptance moves the inspection `SUBMITTED → ACCEPTED`, which is terminal, stamps `accepted_at` with the logical clock and records `accepted_by_user_id` as the acting identifier, and decrements the engineer's `open_inspection_count`.

The dam's `safety_status` is then set to the accepted inspection's `condition_rating`, whatever it was. Because the target state is always the accepted rating, every ordered pair over `UNRATED`, `SATISFACTORY`, `CONDITIONALLY_SATISFACTORY`, `POOR` and `UNSATISFACTORY` is a legal move under one and the same rule: a first inspection typically runs `UNRATED → CONDITIONALLY_SATISFACTORY`, a bad first inspection runs `UNRATED → UNSATISFACTORY`, a deteriorating structure runs `CONDITIONALLY_SATISFACTORY → POOR`, and completed repairs run `POOR → SATISFACTORY`. A dam sitting at `UNSATISFACTORY` cannot be issued a `CONSTRUCTION` permit (§3.6) until a later accepted inspection rates it something else. The dam's `version` increments by 1 on every acceptance, and its `regulatory_status` is never touched.

When — and only when — the accepted inspection's `inspection_type` is `PERIODIC`, the dam's schedule is rebuilt from that visit. The baseline is the `performed_at` of the accepted periodic inspection with the greatest `performed_at`, with ties broken by `created_at` ascending and never by `id`; where the dam has no accepted periodic inspection at all, the baseline is its `registered_at`. `next_inspection_due_at` is that baseline advanced by the hazard class's interval in whole calendar months — 12 months at `HIGH`, 24 at `SIGNIFICANT`, 60 at `LOW` and 60 while `UNCLASSIFIED` — preserving the day of month. `inspection_overdue` is then true exactly when the current logical clock is **strictly later** than `next_inspection_due_at`; a clock reading exactly the due instant is not overdue. Inspections can be listed filtered by `dam_id`, `engineer_id`, `status` and `inspection_type`, and read one at a time.

### 3.4. Deficiencies, Remediation Orders and the Enforcement Ladder

A deficiency is the program's unit of non-compliance. It always names the `dam_id` it burdens, carries a `category`, a `severity`, a free-text `description`, and a `source` recording where it came from — `INSPECTION` for the engineer-identified rows of §3.3, which also carry the originating `inspection_id`, `SYSTEM_EAP` for the plan-gap rows opened by the reclassification cascade and by plan expiry, and `SYSTEM_EXERCISE` for the rows opened by a failed annual exercise. System-born rows carry no inspection reference. Deficiencies cannot be created directly through the API; they arrive only through those three routes. They can be listed filtered by `dam_id`, `inspection_id`, `status`, `severity`, `source` and `category`, and read individually. A deficiency's lifecycle runs `OPEN`, `ORDERED`, `REMEDIATION_SUBMITTED`, `ESCALATED` and the terminal `CLOSED_VERIFIED`, and it also exposes `remediation_due_at`, `order_count` and `closed_at`.

Enforcement begins when program staff issue a **remediation order** against a deficiency that is `OPEN` or `ESCALATED`, moving it `OPEN → ORDERED`; the dam must not be `BREACHED`. The request carries only an `order_type` — `NOTICE_OF_DEFICIENCY`, `COMPLIANCE_ORDER` or `EMERGENCY_ORDER` — and the `requested_response_days` the staff want to grant, which must be at least 1. Everything else is computed. The order copies `dam_id` from the deficiency and `owner_id` from that dam, so the owner served is fixed at issue time and cannot drift; it stamps `issued_at` with the logical clock and lands in `ISSUED`, with `corrective_action_summary`, `completed_at`, `response_filed_at`, `verified_by_user_id` and `defaulted_at` all null and `assessed_penalty_cents` at 0. The deficiency's `remediation_due_at` becomes the new order's `compliance_deadline_at` and its `order_count` rises by one.

The statutory window granted is built from severity, compressed by hazard class, clamped, and finally intersected with what staff asked for — the state may grant less time than the schedule allows but never more. The base window by severity is 180 days for `MINOR`, 90 days for `MODERATE`, 45 days for `SERIOUS` and 10 days for `CRITICAL`. That base is multiplied by the hazard compression factor — 0.5 for a `HIGH`-hazard dam, 0.75 for `SIGNIFICANT`, and 1.0 for both `LOW` and `UNCLASSIFIED` — and the product is rounded **down** to a whole number of days. The rounded-down figure is then clamped to a floor of 5 days and a ceiling of 365 days, in that order: the larger of 5 and the smaller of 365 and the rounded product. The result is the schedule's allowance, and `effective_response_days` is the smaller of `requested_response_days` and that allowance. When the `order_type` is `EMERGENCY_ORDER`, `effective_response_days` is further capped at 5 days. Because the flooring happens before the clamp, a `SERIOUS` deficiency on a `HIGH`-hazard dam allows 45 multiplied by 0.5, that is 22.5, floored to 22 days — not 22.5 and not 23. Finally `compliance_deadline_at` is `issued_at` advanced by `effective_response_days` exact days, carrying the issue instant's time of day.

The order also pins its `daily_penalty_rate_cents` at issue time, so that later reclassification of the dam cannot retroactively reprice a violation. The rate is the severity's daily base — 2,000 cents for `MINOR`, 5,000 cents for `MODERATE`, 12,500 cents for `SERIOUS` and 25,000 cents for `CRITICAL` — multiplied by the hazard penalty factor of 1.6 for `HIGH`, 1.25 for `SIGNIFICANT` and 1.0 for both `LOW` and `UNCLASSIFIED`, with the product rounded half up to whole cents.

The owner answers by **filing a response** on an order that is still `ISSUED`, an act reserved to the owner served — the acting `X-User-ID` must equal the order's owner, and anyone else receives `ERR_NOT_RESOURCE_OWNER`. The response carries a `corrective_action_summary` describing the work performed and a `completed_at` instant asserting when it finished; no temporal constraint is placed on `completed_at` — it may precede `issued_at` and it may lie in the future of the logical clock. Both of those two fields are overwritten wholesale by a later re-response after a rejection. The order moves `ISSUED → RESPONSE_FILED` and the deficiency moves `ORDERED → REMEDIATION_SUBMITTED`. `response_filed_at` is stamped with the logical clock **only when it is currently null**, and is never overwritten by a later re-response; that single field is the good-faith abatement flag, and it must survive a rejection for the abatement in §3.4's penalty rule to work as intended.

An engineer then verifies, supplying an `outcome` of either `SATISFIED` or `REJECTED` together with `notes`, on an order that is `RESPONSE_FILED`, with an active licence. `verified_by_user_id` records the acting engineer either way. On `SATISFIED` the order moves `RESPONSE_FILED → SATISFIED`, which is terminal, the deficiency moves `REMEDIATION_SUBMITTED → CLOSED_VERIFIED` with `closed_at` stamped at the clock, the dam's `open_deficiency_count` falls by one and the dam's `version` increments. If at that point no deficiency on the dam remains in `ESCALATED` **and** the owner's `delinquency_status` is `CURRENT` — meaning the assessed penalty has been settled through the fee ledger — the dam's regulatory posture cycles back `UNDER_ENFORCEMENT → REGISTERED` and the dam's `version` increments for that move as well. On `REJECTED` the order cycles back `RESPONSE_FILED → ISSUED` with `response_filed_at` retained, and the deficiency moves `REMEDIATION_SUBMITTED → ORDERED` with `remediation_due_at` unchanged — the original deadline keeps running, and the owner has not been granted more time by having their work rejected. This rejection loop may repeat without bound.

Where a deficiency has been escalated by a default and staff wish to compel it again, a further order may be issued on it, moving it `ESCALATED → ORDERED`; `remediation_due_at` is replaced by the new order's `compliance_deadline_at` and `order_count` rises again.

**Civil penalty accrual** is the price of a missed deadline, and it steps up as the violation ages. The number of overdue days is the count of whole days by which the current logical clock exceeds `compliance_deadline_at` — the elapsed interval rounded down to whole days, and 0 when the clock is at or before the deadline. The penalty is then accumulated strictly chronologically, day 1 first: for each overdue day, the day's factor is 1.0 for days 1 through 7, 1.15 for days 8 through 30, and 1.3225 from day 31 onward; the day's charge is `daily_penalty_rate_cents` multiplied by that factor and **rounded half up to whole cents for that day**, and the rounded day charge is added to the running total. Rounding once per day is part of the contract: summing unrounded day amounts and rounding at the end produces a different figure.

That raw accrual is what the **penalty preview** returns, a read available to `ProgramAdmin` and `DamOwner` on an order that is still `ISSUED` or `RESPONSE_FILED`. The preview applies **no cap and no abatement** and returns exactly `order_id`, `overdue_days`, `daily_penalty_rate_cents`, `provisional_penalty_cents` and `response_filed` (true exactly when `response_filed_at` is non-null). An owner who has already filed a response therefore previews a strictly larger number than the amount that will actually be assessed against them.

The **final assessment** happens only at default, inside the compliance sweep of §3.9, and continues from the raw accrual in a fixed order. First the total is capped at 5,000,000 cents — a fifty-thousand-dollar ceiling per order. Then, if `response_filed_at` is non-null, a good-faith abatement of 25 percent of the capped total, rounded half up to whole cents, is subtracted from it. The order matters: abating before capping would yield a different figure for a capped penalty. The result is written to `assessed_penalty_cents`. Orders can be listed filtered by `deficiency_id`, `dam_id`, `owner_id`, `status` and `order_type`, and read individually with their full deadline and penalty figures.

### 3.5. Emergency Action Plans, Inundation Maps and the Annual Exercise

An emergency action plan is the owner's obligation, not the state's. Drafting one is reserved to the `DamOwner` who owns the dam, and the payload names the `dam_id`, an owner-assigned `version_label`, the `inundation_map_ref` the plan is built on, a `notification_flowchart_ref` pointing at the downstream notification chart, the `notification_contact_count` of contacts wired into that chart (at least 0), a `drawdown_procedure_ref` for the emergency drawdown procedure, and the `expected_dam_version` demanded by §2.7. A stale dam version is rejected with `ERR_STALE_DAM_VERSION`, an owner drafting against someone else's dam gets `ERR_NOT_RESOURCE_OWNER`, and a `BREACHED` dam refuses the draft with `ERR_DAM_NOT_OPERABLE`. The new plan lands in `DRAFT` with `review_findings`, `approved_at`, `expires_at` and `last_accepted_exercise_at` all null, `accepted_exercise_count` at 0 and `exercise_current` false; the dam's `latest_eap_status` becomes `DRAFT` and the dam's `version` increments by 1.

**Submission** moves the plan `DRAFT → SUBMITTED`, and is also how a plan sent back for revision returns to review, moving `REVISION_REQUIRED → SUBMITTED` and retaining the reviewer's earlier `review_findings` for the record. Either way the acting owner must own the dam. Submission accepts optional `inundation_map_ref`, `notification_flowchart_ref`, `notification_contact_count` and `drawdown_procedure_ref` values, and any that are supplied **are the values the two admission checks below are evaluated against**, each omitted or null field falling back to what the plan already holds — which is precisely how an owner recovers a plan that a reclassification pushed into `REVISION_REQUIRED`, by resubmitting it with a refreshed map reference. The supplied values are written onto the plan only once both checks have passed, so a submission that either check rejects leaves the stored plan, its `updated_at`, its `version` and the dam entirely unchanged; there is no partial write. A dam that has never been classified rejects submission with `ERR_DAM_UNCLASSIFIED`, and submission is not one of the operations that re-checks the dam's operability, so the plan of a `BREACHED` dam may still be submitted.

The two admission checks then run. First, `notification_contact_count` must be at least the hazard-class minimum from §2.8 — 8 contacts at `HIGH`, 4 at `SIGNIFICANT`, 1 at `LOW` or `UNCLASSIFIED`, inclusive — and a shortfall is `ERR_INSUFFICIENT_NOTIFICATION_CONTACTS`. Second, when the dam's `eap_required` flag is true, the plan's `inundation_map_ref` must equal the `inundation_map_ref` of the dam's certified consequence assessment; a mismatch is `ERR_INUNDATION_MAP_STALE`, and a dam that does not require a plan is exempt from this check entirely. On success the dam's `latest_eap_status` becomes `SUBMITTED` and the dam's `version` increments by 1.

**Review** is an engineer's act on a `SUBMITTED` plan, carrying a `decision` of either `APPROVE` or `REVISE` together with `findings`; the reviewing engineer's licence must be active. `REVISE` moves the plan `SUBMITTED → REVISION_REQUIRED`, stores the supplied findings in `review_findings`, refreshes the dam's `latest_eap_status` to `REVISION_REQUIRED` and increments the dam's `version` by 1. `APPROVE` stores the supplied `findings` in `review_findings` exactly as `REVISE` does — the field records the reviewer's remarks on both outcomes, not only on a rejection — moves the plan `SUBMITTED → APPROVED`, stamps `approved_at` with the logical clock, and computes `expires_at` as `approved_at` advanced by the hazard class's validity in whole calendar months preserving the day of month — 36 months at `HIGH`, 60 months at `SIGNIFICANT`, and no expiry at all at `LOW`, where `expires_at` stays null. Approval also supersedes the incumbent: any other plan on the same dam whose status is `APPROVED` moves `APPROVED → SUPERSEDED`, which is terminal, keeping its own `expires_at` for the audit record and keeping every exercise already logged against it attached to it. The dam's `latest_eap_status` becomes `APPROVED` and the dam's `version` increments by 1.

A plan can leave `APPROVED` in two further ways, both driven by the system rather than by an actor. The reclassification cascade of §3.2 moves an approved plan `APPROVED → REVISION_REQUIRED` and clears its `expires_at` when a newly certified assessment carries a different map reference. And the compliance sweep of §3.9 moves an approved plan `APPROVED → EXPIRED` — terminal — once its `expires_at` is non-null and the clock has passed it.

**Annual exercises** are logged against a plan that is `APPROVED`, by either the `DamOwner` or the `EmergencyCoordinator`; a plan in any other status refuses the log with `ERR_EAP_INVALID_STATE`. The log carries an `exercise_type` of `TABLETOP`, `FUNCTIONAL` or `FULL_SCALE`, a `conducted_at` instant, a `participant_count` of at least 0, and the boolean `notification_test_passed` recording whether the notification flowchart test succeeded end to end. Exercises are logged after the fact, so `conducted_at` must be at or before the current logical clock, equality permitted, with a later instant rejected as `ERR_EXERCISE_DATE_IN_FUTURE`. The acting identifier is recorded as `logged_by_user_id`, and the exercise's `eap_id` is taken from the plan it is logged against. An exercise row is a journal entry: it carries `id` and `created_at` only, with no `updated_at` and no `version`.

Grading happens at logging time and produces an `outcome` of `ACCEPTED` or `DEFICIENT`. Three checks are considered in a fixed order — the notification test first, then participation, then format. The exercise fails the notification test when `notification_test_passed` is false; it fails participation when `participant_count` is below the hazard-class minimum of 6 at `HIGH`, 4 at `SIGNIFICANT` and 2 at `LOW` or `UNCLASSIFIED` (a count exactly equal to the minimum passes); and it fails format when `exercise_type` is not among the formats the hazard class permits — only `FUNCTIONAL` and `FULL_SCALE` at `HIGH`, and any of `TABLETOP`, `FUNCTIONAL` and `FULL_SCALE` at `SIGNIFICANT`, `LOW` and `UNCLASSIFIED`. If no check fails, `outcome` is `ACCEPTED` and `deficiency_reason` is null. If any fails, `outcome` is `DEFICIENT` and `deficiency_reason` is the **first** failure in that same fixed order, recorded as `NOTIFICATION_TEST_FAILED`, `INSUFFICIENT_PARTICIPANTS` or `EXERCISE_TYPE_NOT_PERMITTED`; a tabletop exercise on a high-hazard dam that also failed its notification test records `NOTIFICATION_TEST_FAILED`, not the format failure. A deficient exercise additionally opens a deficiency with `source` of `SYSTEM_EXERCISE`, `category` of `EAP_EXERCISE`, `severity` of `MODERATE` and `status` of `OPEN`, and with `inspection_id`, `remediation_due_at` and `closed_at` all null, incrementing the dam's `open_deficiency_count`. Unlike the `EAP_MISSING` deficiency of §3.9 this opening is **never suppressed** by an existing unclosed deficiency of the same category, so a second and a third deficient exercise each open their own row and the count keeps climbing.

An accepted exercise refreshes the plan's currency fields: `accepted_exercise_count`, `last_accepted_exercise_at`, and the boolean `exercise_current`. All three are derived from the exercise journal on every read rather than stored on the plan, so logging an exercise — accepted or deficient — writes nothing to the plan row itself and leaves the plan's `updated_at` and `version` exactly where they were. An accepted exercise therefore writes nothing at all outside the journal row it creates; a deficient one writes only the deficiency it opens, and that opening is what advances the dam's `updated_at` and `version` by 1. Currency runs on a **rolling 365-day window** ending at the current clock. The plan is current exactly when at least one exercise on the dam's `APPROVED` plan is graded `ACCEPTED` and its `conducted_at` is **strictly later** than the clock less 365 days and at or before the clock — the lower bound is exclusive, so an exercise conducted exactly 365 days ago no longer counts, while the upper bound is inclusive. Exercises attached to a `SUPERSEDED` or `EXPIRED` plan never count towards currency, however recent they are, which is why an approval that supersedes an incumbent plan starts the exercise obligation over. A plan's exercises can be listed filtered by `outcome`, and plans themselves listed filtered by `dam_id` and `status`.

### 3.6. Permitting Construction, Repair and Removal

Any physical work on a dam needs a permit, and the fee is computed at intake rather than at decision so that an applicant knows the cost before an engineer is assigned. An owner applies against their own dam, naming the `dam_id`, a `permit_type` of `CONSTRUCTION`, `REPAIR` or `REMOVAL`, a `scope_description` narrating the proposed work, an `estimated_project_cost_cents` strictly greater than 0, and a `proposed_start_date`. The `proposed_start_date` is a plain instant recorded as given: it is never compared against the logical clock or against anything else, so a start date already in the past is accepted without complaint. The application copies `owner_id` from the dam, lands in `SUBMITTED` with `revision_count` at 0 and `review_engineer_id`, `decision_findings`, `conditions` and `issued_at` all null. A dam that has never been classified refuses the application with `ERR_DAM_UNCLASSIFIED`; a `BREACHED` dam, and a dam already `REMOVAL_PERMITTED`, refuse it with `ERR_DAM_NOT_OPERABLE`; and an owner applying against another owner's dam receives `ERR_NOT_RESOURCE_OWNER`.

The fee is built in five movements and stored in four component fields plus a total. **First**, a flat base tier on project cost, with every tier's upper bound exclusive: a cost below 5,000,000 cents pays a base of 25,000 cents; a cost of 5,000,000 cents or more but below 50,000,000 cents pays 100,000 cents; a cost of 50,000,000 cents or more but below 500,000,000 cents pays 350,000 cents; and a cost of 500,000,000 cents or more pays 900,000 cents. That figure is `base_fee_cents`. **Second**, an engineering review fee proportional to the project: the cost is multiplied by the work class's percentage — 0.75 percent for `CONSTRUCTION`, 0.5 percent for `REPAIR`, 0.35 percent for `REMOVAL` — and then by the hazard uplift of 1.25 at `HIGH`, 1.10 at `SIGNIFICANT`, and 1.0 at both `LOW` and `UNCLASSIFIED`; the product is rounded half up to whole cents and then capped at 750,000 cents. That capped figure is `engineering_review_fee_cents`. The base and the review fee together form the subtotal. **Third**, if the owner's `delinquency_status` is `DELINQUENT` at the moment of application, a surcharge of 15 percent of that subtotal, rounded half up to whole cents, is charged as `delinquency_surcharge_cents`; a current owner is charged 0. The subtotal plus the surcharge is the pre-credit total. **Fourth**, a program volume credit is decided **once** on that pre-credit total: if the pre-credit total is at least 500,000 cents, `volume_credit_cents` is 10 percent of it rounded half up to whole cents, and otherwise it is 0. **Fifth**, `total_fee_cents` is the pre-credit total less the credit. The credit is never re-evaluated after being applied, so a permit whose total lands below the 500,000-cent credit threshold once the credit is deducted keeps the credit anyway.

The whole `total_fee_cents` is posted to the owner's ledger at application time as a single `PERMIT_REVIEW_FEE` entry whose `source_ref` names the newly created permit, and the owner's balance and delinquency flag are recomputed immediately (§3.8) — recomputed, not rewritten: the owner row is not touched, so its `updated_at` and `version` do not move. A large application can therefore make an owner delinquent, and a delinquent owner pays the 15 percent surcharge on their next application — the two rules compound deliberately.

Program staff then assign a reviewer, moving the application `SUBMITTED → UNDER_ENGINEERING_REVIEW` and storing the nominated `review_engineer_id`. The nominated engineer's `license_status` must be `ACTIVE`, and they must not be the engineer of record on the dam's latest accepted inspection — that collision is `ERR_SEGREGATION_OF_DUTIES`, because an engineer's own condition rating of the structure feeds the very decision they would be making. "Latest accepted inspection" here is exactly the row §2.9 uses for `safety_status`: the dam's accepted inspection with the greatest `performed_at` whatever its `inspection_type`, ties broken by `created_at` ascending. A dam with no accepted inspection at all has no engineer of record, so no nomination can collide and the check passes for every licensed engineer. Assignment writes only the permit — the dam and the engineer are left untouched.

The assigned engineer decides, supplying a `decision` of `ISSUE`, `DENY` or `RETURN` together with `findings` and, for a conditioned issuance, optional `conditions` — any string, the empty one included, and null or omitted when there are none. `conditions` belongs to issuance alone: a value supplied alongside a `DENY` or a `RETURN` is validated and then discarded, and the permit's `conditions` stays null on both of those paths. The acting `X-User-ID` must equal the permit's `review_engineer_id`; on an unassigned permit this comparison is skipped and the request is instead reported as `ERR_PERMIT_INVALID_STATE`, because a permit with no reviewer is still `SUBMITTED`. The engineer's licence must be active. Four further gates then apply, in the order §2.5 fixes: a `CONSTRUCTION` permit on a dam whose `safety_status` is `UNSATISFACTORY` is barred with `ERR_UNSAFE_DAM_PERMIT_BLOCKED` while `REPAIR` and `REMOVAL` work stays permissible on the same dam; a dam whose `hazard_class` is `HIGH` must have a `latest_eap_status` of `APPROVED` or the decision fails with `ERR_EAP_NOT_APPROVED`; the owner must not be delinquent, or the decision fails with `ERR_OWNER_DELINQUENT`; and on a `HIGH`-hazard dam the owner's `financial_assurance_bond_cents` must be at least 25,000,000 cents, or the decision fails with `ERR_INSUFFICIENT_FINANCIAL_ASSURANCE`. Note that all four gates guard the decision itself, not just an issuance: a delinquent owner's permit cannot even be denied on the merits until the balance is settled.

`ISSUE` moves the permit `UNDER_ENGINEERING_REVIEW → ISSUED`, which is terminal, stamps `issued_at` with the logical clock and stores the supplied findings in `decision_findings` and any `conditions`. When the `permit_type` is `REMOVAL`, issuance also moves the dam `REGISTERED → REMOVAL_PERMITTED` on the regulatory dimension and increments the dam's `version` by 1 — and `REGISTERED` is the only posture from which that move is written, so a dam standing on `UNDER_ENFORCEMENT` or `STATE_INTERVENTION` still has its removal permit issued in full while keeping its posture, its `updated_at` and its `version` untouched. The state has authorised the structure's removal, and from that point no new consequence assessment and no further permit application of any type — `CONSTRUCTION`, `REPAIR` or `REMOVAL` alike — may be filed against it. `DENY` moves the permit `UNDER_ENGINEERING_REVIEW → DENIED`, also terminal, storing `decision_findings`; the review fee already posted to the ledger is **not** refunded, because the review work was performed. `RETURN` moves the permit `UNDER_ENGINEERING_REVIEW → RETURNED_FOR_REVISION`, stores `decision_findings`, and retains `review_engineer_id` on the record.

The owner may then revise and resubmit, moving the permit `RETURNED_FOR_REVISION → SUBMITTED`; the acting owner must be the permit's owner. Resubmission overwrites `scope_description` and `estimated_project_cost_cents`, increments `revision_count` by 1, and clears `review_engineer_id` back to null so the application must be assigned afresh — and that clearing is what lets a returned permit be reassigned to a different reviewer. The full five-movement fee schedule is then re-evaluated on the revised cost, on the dam's current hazard class, and on the owner's `delinquency_status` as it stands at the moment of resubmission — so movement three charges the 15 percent surcharge exactly when the owner is delinquent right then and charges 0 when they are not, whatever was charged at intake, and movement four decides the volume credit afresh on the new pre-credit total — and all four component fields plus the total are overwritten with the recomputed figures. Only the **difference** between the new `total_fee_cents` and the previously posted total is appended to the ledger: a positive difference as a `PERMIT_REVIEW_FEE` entry, a negative difference as a `FEE_VOID` entry carrying that negative amount, and a difference of exactly zero appending nothing at all; either entry names the permit in `source_ref`. Resubmission re-checks neither the dam's operability nor its classification, so a permit returned before the dam was breached or taken over can still be revised and resubmitted. This revision loop is bounded only by `revision_count`. Permits can be listed filtered by `dam_id`, `owner_id`, `review_engineer_id`, `permit_type` and `status`, and read individually with the full fee breakdown.

### 3.7. High-Water Monitoring and Coordinated Emergency Drawdown

When a storm arrives, an emergency coordinator or program administrator **declares a high-water event** on a dam, naming the `dam_id`, the `declared_at` instant the coordinator declared it, a `trigger_description` recording the hydrologic trigger that prompted the declaration, and the `declared_inflow_cfs` estimate at declaration, which must be at least 0. Unlike a reading's `reading_at`, `declared_at` is never compared against the logical clock — it is stored as supplied, a future instant included. The event opens in `MONITORING` with `reading_count` at 0, `current_alert_level` at `NORMAL`, and `peak_pool_elevation_ft`, `escalated_at`, `stood_down_at` and `final_pool_elevation_ft` all null. A `BREACHED` dam cannot have an event declared on it; an `UNCLASSIFIED` dam, by contrast, can — declaration is not one of the operations that demands a certified consequence assessment.

Monitoring proceeds by **recording pool-elevation readings** against an event that is `MONITORING` or `EMERGENCY`; a stood-down event refuses further readings with `ERR_EVENT_INVALID_STATE`. Each reading carries a `reading_at` instant that must be at or before the current logical clock — equality permitted, and a later instant rejected as a plain `ERR_INVALID_REQUEST` (400) at rung 3 of §2.5, before the event named in the path is even resolved, so a future-dated reading against a non-existent event reports the malformed request and not `ERR_EVENT_NOT_FOUND` — the observed `pool_elevation_ft`, which carries no bounds of its own and may be negative, and the `observed_inflow_cfs` at that instant, which must be at least 0. The acting identifier is recorded as `recorded_by_user_id`. Like an exercise, a reading is a journal row carrying `id` and `created_at` only, with no `updated_at` and no `version`.

Two figures are derived for every reading. `freeboard_ft` is the dam's `crest_elevation_ft` less the submitted `pool_elevation_ft`, rounded half up to two decimal places — the vertical margin remaining before the pool tops the crest. The reading's `alert_level` is then a four-band ladder on that freeboard, each band inclusive at its upper bound: a freeboard of 0.00 feet or below is `OVERTOPPING`; above that but at or below 1.00 feet is `CRITICAL`; above that but at or below 3.00 feet is `WATCH`; anything greater is `NORMAL`. So exactly 1.00 feet of freeboard is `CRITICAL`, exactly 3.00 feet is `WATCH`, and exactly 0.00 feet is `OVERTOPPING`. The boolean `rising` compares the reading to its predecessor — the event's reading with the greatest `reading_at` strictly earlier than this one, ties broken by `created_at` ascending and never by `id` — and is true exactly when such a predecessor exists and this reading's `pool_elevation_ft` is strictly greater than the predecessor's. The first reading of an event is therefore never rising. The event's `reading_count`, `current_alert_level` and `peak_pool_elevation_ft` are refreshed in the same request, all three being derived from the reading journal rather than stored: `reading_count` is simply how many readings the event has, `current_alert_level` is the `alert_level` of the reading with the greatest `reading_at` — ties broken by `created_at` ascending, and reading `NORMAL` while the event has none — and `peak_pool_elevation_ft` is the greatest `pool_elevation_ft` among them, echoed exactly as it was submitted and null until the first reading arrives. Every reading refreshes the event's `updated_at`, but only a reading that escalates the event advances the event's `version`: a reading that changes the alert level without triggering the escalation below leaves `version` where it was.

**Auto-escalation** is the one transition in this workflow that no actor performs. If the event is still `MONITORING` and the new reading's `alert_level` is `CRITICAL` or `OVERTOPPING` **and** its `rising` flag is true, the event moves `MONITORING → EMERGENCY` and `escalated_at` is stamped with the logical clock. A critical reading on a falling pool escalates nothing: the state escalates on a deteriorating trend, not on a bad instantaneous number. Readings can be listed for an event filtered by `alert_level`, and events listed filtered by `dam_id` and `status`.

**Standing an event down** is the emergency coordinator's closing act on an event that is `MONITORING` or `EMERGENCY`, moving it `MONITORING → STOOD_DOWN` or `EMERGENCY → STOOD_DOWN` — terminal in both cases — stamping `stood_down_at` with the clock and storing the supplied `final_pool_elevation_ft`. Standing down also cancels the releases the event authorised: every drawdown order on the event whose status is `REQUESTED`, `COORDINATED` or `ACTIVE` is moved to `CANCELLED` with `cancel_reason` set to `EVENT_STOOD_DOWN`, taken in `created_at` order, and each cancellation releases exactly the reach capacity and reservoir storage that order had committed, incrementing the reach's `version` and the dam's `version` for the changes it makes. Here the increment is **once per released order**, not once per request: an event standing down two `COORDINATED` orders advances its dam's `version` by 2 and its reach's `version` by 2 — which is the opposite convention to the state-intervention cascade of §3.9, where the reach write is collapsed to one per reach however many orders it cancelled. As there too, a merely `REQUESTED` order held no commitment and so writes neither the reach nor the dam.

A **drawdown order** is a request to release water down the reach at a sustained rate for a window. It names the `dam_id`, the `high_water_event_id` under which the release is coordinated, the `requested_release_cfs` (strictly greater than 0), and the release window as `window_start` and `window_end`, both inclusive, with the end strictly after the start. The reach is not chosen by the requester: `river_reach_id` is copied from the dam at request time, and it is that reach's channel capacity the release will consume. Its two body references are resolved `dam_id` first and `high_water_event_id` second, and the gates then run in the order §2.5 fixes: the event must not be stood down, the dam must be operable, a `HIGH`-hazard dam must carry a `latest_eap_status` of `APPROVED` or the request fails with `ERR_EAP_NOT_APPROVED` — and that is the *latest* plan status of §2.9, the newest plan on the dam by `created_at`, so drafting a fresh plan alongside an approved one closes this gate again until the new plan is itself approved — the dam must not be `UNCLASSIFIED`, and the named event must belong to the same dam as the order, a mismatch being `ERR_EVENT_DAM_MISMATCH`. The order lands in `REQUESTED` with `coordinated_at`, `activated_at`, `completed_at`, `cancelled_at`, `cancel_reason` and `actual_release_acre_ft` all null, and **nothing is committed yet**.

What is computed at request time is `planned_release_acre_ft`, the volume the window would release. The window's duration is measured in hours, fractional hours allowed, as `window_end` less `window_start`; that number of hours is multiplied by `requested_release_cfs` and by the conversion factor 0.0826446 acre-feet per cubic-foot-per-second-hour, and the product is rounded half up to three decimal places.

**Coordination** is where scarcity bites, and it is a `ProgramAdmin` act on an order that is `REQUESTED` — the only status precondition it imposes. It re-examines the governing event not at all: the stand-down cascade above guarantees that no `REQUESTED` order can survive its event's stand-down, so an order still eligible for coordination necessarily hangs off an event still `MONITORING` or `EMERGENCY`, and coordination never reports `ERR_EVENT_INVALID_STATE`. The request carries the `expected_reach_version` of §2.7, and a stale value is rejected with `ERR_STALE_REACH_VERSION` before either scarcity check runs. The **channel-capacity check** treats release windows as closed intervals, so windows that merely touch at an endpoint do overlap: the set of competing orders is every order on the same reach whose status is `COORDINATED` or `ACTIVE` and whose `window_start` is at or before the new order's `window_end` while its `window_end` is at or after the new order's `window_start`. Their `requested_release_cfs` values are summed, and if that sum plus the new order's requested rate is strictly greater than the reach's `channel_capacity_cfs`, coordination is rejected with `ERR_REACH_CAPACITY_EXCEEDED`; exact equality with the channel capacity is allowed. Orders in `REQUESTED`, `COMPLETED` or `CANCELLED` contribute nothing to that sum, which is exactly what makes a cancellation genuinely free the channel again. The **storage check** then requires the order's `planned_release_acre_ft` to be at or below the dam's `available_conservation_storage_acre_ft`, equality allowed, with a shortfall rejected as `ERR_INSUFFICIENT_STORAGE`.

On success the order moves `REQUESTED → COORDINATED`, `coordinated_at` is stamped with the clock, and both shared quantities are committed in the same request: the reach's `committed_release_cfs` rises by the order's requested rate and its `active_drawdown_count` by one, incrementing the reach's `version` by 1; and the dam's `committed_drawdown_acre_ft` rises by the order's planned volume with `available_conservation_storage_acre_ft` recomputed, incrementing the dam's `version` by 1. The storage split is maintained as a strict conservation law: a dam's `committed_drawdown_acre_ft` is the sum of `planned_release_acre_ft` over its orders in `COORDINATED` or `ACTIVE`, and its `available_conservation_storage_acre_ft` is `gross_storage_acre_ft` less that committed figure, rounded half up to three decimal places, so that committed plus available always equals gross storage — before and after every coordination, completion, cancellation and cascade cancellation. The reach's own `committed_release_cfs` obeys the same discipline as the sum of `requested_release_cfs` over its `COORDINATED` and `ACTIVE` orders.

**Activation** opens the gates, and only the emergency coordinator may do it, on an order that is `COORDINATED`. It requires the governing event to have reached `EMERGENCY`; an order coordinated under an event still in `MONITORING` cannot be activated, and the attempt is rejected with `ERR_EVENT_NOT_IN_EMERGENCY`. That is the deliberate coupling between the auto-escalation rule above and the release itself: capacity may be reserved on a watch, but water moves only in an emergency. Activation carries no payload of its own — no body is read, so anything sent is ignored rather than rejected — and it moves the order `COORDINATED → ACTIVE`, stamps `activated_at`, and changes no commitment: neither the reach nor the dam is written, and neither `version` advances, because the reach capacity and dam storage were taken at coordination.

**Completion** closes out a release that is `ACTIVE`, carrying the `actual_release_acre_ft` volume genuinely released. The order moves `ACTIVE → COMPLETED`, terminal, with `completed_at` stamped; the reach's `committed_release_cfs` falls by the order's requested rate and its `active_drawdown_count` by one with the reach's `version` incremented; and the dam's `committed_drawdown_acre_ft` falls by the order's planned volume with `available_conservation_storage_acre_ft` recomputed back to its pre-coordination value and the dam's `version` incremented. Note that the released commitment is the **planned** volume, not the actual one: `actual_release_acre_ft` is recorded for the hydrologic record and does not enter the conservation arithmetic. It must be at least 0, and because it is a reported observation rather than a computed volume it is stored and echoed exactly as supplied — the three-decimal quantisation §2.6 imposes on planned, committed and available acre-feet is not applied to it.

**Cancellation** is available to either a `ProgramAdmin` or an `EmergencyCoordinator` on any non-terminal order and carries a `reason` stored in `cancel_reason`. The order moves `REQUESTED → CANCELLED`, `COORDINATED → CANCELLED` or `ACTIVE → CANCELLED`, all terminal, with `cancelled_at` stamped. A `REQUESTED` order releases nothing, because it never took a commitment. A `COORDINATED` or `ACTIVE` order releases exactly the reach capacity and dam storage it took, incrementing both the reach's and the dam's `version` — the pair of coordinate-then-cancel leaves both conserved quantities precisely as they were. Cancelling an `ACTIVE` order leaves `actual_release_acre_ft` null. Orders can be listed filtered by `dam_id`, `river_reach_id`, `high_water_event_id` and `status`.

### 3.8. Owner Financial Responsibility and the Fee Ledger

An owner's money position is not a stored number that the program edits; it is the replay of an append-only ledger. Each ledger entry names the `owner_id` whose balance it moves, carries a `sequence_no`, an `entry_type`, a signed `amount_cents`, an optional `source_ref` free-text reference to the originating permit or order (null when the entry relates to neither), an optional operator `memo` (null when omitted), a derived `balance_after_cents`, and `posted_by_user_id`. A ledger entry is a journal row: it carries `id` and `created_at` only, with no `updated_at` and no `version`.

`sequence_no` is a monotonic per-owner posting sequence starting at 1: a new entry takes the greatest existing `sequence_no` for that owner plus 1, or 1 when the owner has no entries yet. It is the **only** ordering key for the running-balance replay. The replay walks the owner's entries in ascending `sequence_no`, accumulating the signed amounts, and writes the accumulated figure into each entry's `balance_after_cents`; the final accumulated figure is the owner's `fee_balance_cents`. A positive balance means money is owed to the state.

The sign of an amount is dictated by its type, and six types exist. `PERMIT_REVIEW_FEE`, `ANNUAL_REGISTRATION_FEE` and `CIVIL_PENALTY` are charges and must be positive. `PAYMENT_RECEIVED` reduces the balance, `PENALTY_ABATEMENT` is a statutory reduction of an assessed penalty, and `FEE_VOID` reverses a previously posted charge; all three must be negative. An entry whose `amount_cents` sign disagrees with its `entry_type` is rejected with `ERR_LEDGER_SIGN_MISMATCH`, and an `amount_cents` of exactly 0 is never accepted at all — it is caught as a malformed request. Program staff post entries directly through a fee adjustment, supplying `entry_type`, `amount_cents` and optionally `memo` and `source_ref`, and `posted_by_user_id` records the acting administrator's identifier; the posting is returned as the newly created ledger entry. Appending an entry by hand, or as part of the permit-fee postings of §3.6, writes only that journal row — the owner record itself is not rewritten, so the owner's `updated_at` and `version` stay exactly where they were even though the `fee_balance_cents` and `delinquency_status` the owner reports have both moved. The single exception is the compliance sweep's civil penalty (§3.9), which writes the owner row as well as the journal. Entries appended by the system's own cascades — the permit fee at application and resubmission, and the civil penalty at default — carry the literal string `SYSTEM` in `posted_by_user_id` instead, and `PERMIT_REVIEW_FEE` entries are ordinarily posted this way rather than by hand.

`delinquency_status` is a pure function of the replayed balance and is recomputed on every posting: it reads `DELINQUENT` when `fee_balance_cents` is at or above 25,000 cents — two hundred and fifty dollars, and the threshold is inclusive, so a balance of exactly 25,000 cents is delinquent — and `CURRENT` otherwise. A balance may go negative, representing a credit with the state, and a negative balance is `CURRENT`. Delinquency has teeth in three places: it adds the 15 percent surcharge to a permit fee at application (§3.6), it blocks any permit decision with `ERR_OWNER_DELINQUENT`, and it prevents a dam from cycling out of `UNDER_ENFORCEMENT` even after its remediation is verified (§3.4). An owner may read their own ledger, filtered by `entry_type`; an owner reading another owner's ledger receives `ERR_NOT_RESOURCE_OWNER`.

### 3.9. State Intervention, Abandonment, and the Compliance Sweep

The state's ultimate authority over an abandoned or dangerous structure is exercised through a single administrator capability that supplies an `intervention_type` and a written `justification`. The `justification` must be a non-empty string but is not persisted on any resource, and the call returns the updated dam record. Two of the three types — `ABANDONMENT_TAKEOVER` and `EMERGENCY_REPAIR` — move the dam onto `STATE_INTERVENTION`, and either `REGISTERED → STATE_INTERVENTION` or `UNDER_ENFORCEMENT → STATE_INTERVENTION` is a legal move — and those two are the only legal starting postures, so a dam already sitting on `STATE_INTERVENTION`, or on `REMOVAL_PERMITTED` or `BREACHED`, refuses the takeover with `ERR_DAM_NOT_OPERABLE` (409); a second takeover is not an idempotent no-op. Because the state is taking operational control, every drawdown order on that dam whose status is `REQUESTED`, `COORDINATED` or `ACTIVE` is cancelled with `cancel_reason` set to `STATE_INTERVENTION`, each cancellation releasing the reach capacity and reservoir storage it had committed under the conservation discipline of §3.7. Only an order that actually held a commitment — one in `COORDINATED` or `ACTIVE` — moves a reach, and each reach so affected has its `updated_at` and `version` advanced exactly once for the whole request however many of its orders this one intervention cancelled; cancelling a merely `REQUESTED` order writes no reach at all. The dam's `version` increments by 1.

The third type, `BREACH_ORDER`, is the end of the road: it moves the dam to `BREACHED`, which is terminal, and it may be issued from `REGISTERED`, `UNDER_ENFORCEMENT` or `STATE_INTERVENTION` — and from nowhere else, so a `REMOVAL_PERMITTED` dam and an already-`BREACHED` dam both refuse it with `ERR_DAM_NOT_OPERABLE` (409). A breached dam is out of the program, and every subsequent consequence certification, inspection scheduling, permit application, event declaration, plan draft and drawdown request against it is rejected with `ERR_DAM_NOT_OPERABLE`. Because there is no longer a structure to remediate, every deficiency on the dam whose status is `OPEN`, `ORDERED`, `REMEDIATION_SUBMITTED` or `ESCALATED` is closed as `CLOSED_VERIFIED` with `closed_at` stamped at the logical clock, and the dam's `open_deficiency_count` becomes 0. A breach order does not touch the dam's drawdown orders: unlike the two intervention types above it cancels nothing, so any `REQUESTED`, `COORDINATED` or `ACTIVE` release on the dam keeps its status and its reach and storage commitments, and no reach is written. The dam's `version` increments by 1.

The **compliance sweep** is the program's periodic enforcement run, invoked by an administrator with no request body — and no body is read, so anything a client does send is ignored rather than rejected. It is the only place where the passage of logical time turns into enforcement consequences, and it does four things.

First, it defaults overdue orders and runs the **four-link enforcement cascade**. Any remediation order whose status is `ISSUED` or `RESPONSE_FILED` and whose `compliance_deadline_at` the clock has strictly passed moves to `DEFAULTED`. **Link 1** stamps `defaulted_at` with the clock, computes `assessed_penalty_cents` from the final-assessment variant of §3.4 — the tiered daily accrual, capped at 5,000,000 cents, then reduced by the 25 percent good-faith abatement if `response_filed_at` is non-null — and moves the governing deficiency `ORDERED → ESCALATED` in the same step. That escalation is written **only** from `ORDERED`: an order that reached `RESPONSE_FILED` left its deficiency in `REMEDIATION_SUBMITTED`, and such a deficiency is passed over entirely — it keeps its status, is not written, and contributes nothing to `escalated_deficiency_count`, so an order can default without escalating anything. An order that reached `RESPONSE_FILED` before defaulting nonetheless carries the abatement even though its work was never verified, which is exactly why `response_filed_at` is never overwritten. Note too that overdue days are counted in whole days floored, so an order the clock has passed by less than a full 24 hours defaults with `assessed_penalty_cents` of exactly 0. **Link 2** fires only because link 1 assessed a penalty **strictly greater than 0**: a zero assessment posts no ledger entry at all and links 2, 3 and 4 all stay silent, leaving the owner, the balance and the dam untouched. When it does fire: a ledger entry with `entry_type` of `CIVIL_PENALTY`, an `amount_cents` equal to the assessed penalty, a `source_ref` naming the defaulted order and `posted_by_user_id` of `SYSTEM` is appended to the owner's ledger, and the owner's `fee_balance_cents` and the affected `balance_after_cents` figures are recomputed. This is the one ledger posting that also writes the owner row itself, advancing the owner's `updated_at` and `version` by 1 — the hand-posted adjustments and permit fees of §3.6 and §3.8 leave the owner row alone. **Link 3** fires because link 2 moved the balance across the 25,000-cent threshold: the owner's `delinquency_status` becomes `DELINQUENT`. **Link 4** fires because link 3 made the owner delinquent: the dam moves `REGISTERED → UNDER_ENFORCEMENT` on the regulatory dimension and its `version` increments by 1. Link 4 is conditional on link 3 having actually flipped the owner from `CURRENT` to `DELINQUENT` — an owner who was already delinquent does not drive a second dam transition, and a penalty too small to cross the threshold drives none at all. The posture move itself is equally conditional: it is written only for a dam standing on `REGISTERED`, so a dam already `UNDER_ENFORCEMENT` or sitting on `STATE_INTERVENTION`, `REMOVAL_PERMITTED` or `BREACHED` is left entirely alone — no `version` advance and no contribution to `dams_moved_under_enforcement`. This is the sole route into `UNDER_ENFORCEMENT`, and the verification path of §3.4 is the sole route back out.

Second, the sweep refers aged defaults for prosecution. An order that has been `DEFAULTED` for longer than the referral period — that is, where the clock has strictly passed `defaulted_at` advanced by 30 days — moves `DEFAULTED → REFERRED_FOR_ENFORCEMENT`, which is terminal, and no further penalty is ever assessed on that order — its `assessed_penalty_cents` is left standing at the figure link 1 computed. Because the first stage stamps `defaulted_at` at the very clock the run is executing at, an order defaulted by this same sweep can never also be referred by it: referral always waits for a later run.

Third, the sweep expires stale plans. An emergency action plan that is `APPROVED` with a non-null `expires_at` that the clock has strictly passed moves `APPROVED → EXPIRED`, terminal, and the dam's `latest_eap_status` becomes `EXPIRED`. When that dam's `eap_required` flag is true, a deficiency with `source` of `SYSTEM_EAP`, `category` of `EAP_MISSING`, `severity` of `SERIOUS` and `status` of `OPEN` is opened — unless an unclosed deficiency of that category already exists on the dam — the dam's `open_deficiency_count` is updated and the dam's `version` increments by 1. That dam write is unconditional within the `eap_required` branch: the `version` advances by 1 even on the run where the suppression rule meant no new deficiency was actually created. If instead the dam no longer requires a plan — a reclassification down to `LOW` having overtaken the approval that set `expires_at` — the plan still expires, but no deficiency is opened and the dam's `updated_at` alone is refreshed, with its `version` left where it was. A plan approved while the dam was `LOW`, whose `expires_at` is null by construction, can never be expired by the sweep at all.

Fourth, the sweep evaluates `inspection_overdue` for every dam in the inventory against the current logical clock, on the schedule rule of §3.3, purely in order to count them. The flag is derived on every read rather than stored, so this fourth stage writes nothing: no dam's `updated_at` moves, no `version` advances, and running the sweep twice in a row reports the same `overdue_inspection_count` both times.

The sweep reports what it did, returning exactly these keys: `swept_at` (the logical clock at which the run executed), `defaulted_order_count`, `defaulted_order_ids` (the ids of the orders this run moved to `DEFAULTED`, as an array of id strings ordered by the orders' `created_at` ascending), `escalated_deficiency_count`, `referred_order_count`, `expired_eap_count`, `penalty_cents_assessed` (the sum of the penalties assessed by this run), `newly_delinquent_owner_count`, `dams_moved_under_enforcement` and `overdue_inspection_count` (the number of dams in the whole inventory whose `inspection_overdue` flag reads true at the clock the run executed at, unfiltered by owner, posture or hazard class). `swept_at` is that clock, and since the sweep never moves the clock it is identical for every consequence the run records. A sweep on a program with nothing due is a legitimate no-op that returns zeros.
