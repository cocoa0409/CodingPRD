# Mutual Fund Transfer Agency API — Product Requirements Document

## 1. Introduction

A mutual fund transfer agent is the official recordkeeper standing between a fund's shareholders and the fund's books. It opens and maintains registrations, captures purchase, redemption and exchange orders, applies the forward-pricing discipline that determines which day's net asset value an order receives, books settled activity to an append-only share ledger, declares and pays distributions, and answers to state securities regulators for every dollar of shares sold. When any of these functions drifts out of alignment — a NAV struck on a stale share balance, a late order priced at yesterday's favourable price, a breakpoint discount granted on a household the agent cannot actually see — the consequences are regulatory rather than merely operational.

This document specifies the API for such a transfer agency platform. The system is deliberately built around a small number of flat, peer-level records — funds, share classes, shareholder accounts, positions, NAV records, trades, distributions and their payments, systematic plans, state registrations, pricing error cases and reconciliations — linked to one another by identifier rather than by nesting. Two ideas dominate the design. The first is that a trade carries two independent lifecycles at once: a pricing lifecycle that says which NAV has been applied, and a book-entry lifecycle that says whether the shares have actually moved. The second is that almost every derived number in the system — a household's breakpoint basis, a class's shares outstanding, a state registration's remaining capacity — is a reconciliation of primary records rather than a value a client may set, and must be recomputed the moment its inputs change.

Because the platform must be exercised deterministically, it does not read the wall clock. Every date and time decision — which business day an order prices on, whether a distribution's record date has arrived, whether a systematic plan is due — is taken against a logical clock that only moves when an operator moves it. Segregation of duties is likewise enforced structurally rather than by convention: the officer who approves a backdated order may not be the operator who captured it, and the accountant who reprocesses a material pricing correction may not be the accountant who reported it.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across every endpoint: authentication, envelope shape, pagination, the logical clock, audit fields, numeric precision, rejection precedence, version gating, and the cascade discipline that keeps derived values honest.

### 2.1. Desk Roles and Request Authentication

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the desk that user is acting for. Five roles are recognized, and their spellings are exact: `TransferAgentOperator`, `FundAccountant`, `ComplianceOfficer`, `DealerOperations`, and `AccountHolder`. A request that omits either header, or that presents an `X-User-Role` value outside those five, is rejected with `ERR_UNAUTHENTICATED`. A request whose role is well-formed but is not listed for the endpoint being called is rejected with `ERR_FORBIDDEN_ROLE`. The authorized roles for each endpoint are given in the table in §4.

The `TransferAgentOperator` staffs the shareholder-services desk: account opening and lifecycle, order capture, pricing, settlement, and systematic plan administration. The `FundAccountant` owns fund and share-class reference data, the daily NAV strike, distribution declarations, and pricing error case handling. The `ComplianceOfficer` owns state registrations, as-of approvals, account restrictions and reinstatements, material-correction sign-off, trade and distribution reversals, and break disposition. `DealerOperations` is the selling dealer's back office; it may open and trade only on the accounts it services and files the dealer activity summaries that drive reconciliation. The `AccountHolder` is the registered shareholder acting on their own account.

When `X-User-Role` is `TransferAgentOperator`, `FundAccountant`, `ComplianceOfficer`, or `DealerOperations`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it — it is stamped into `captured_by_user_id` and `approved_by_user_id` on a trade, and into `detected_by_user_id`, `approved_by_user_id` and `reprocessed_by_user_id` on a pricing error case — but it never compares that value to any entity's `id`. When `X-User-Role` is `AccountHolder`, by contrast, `X-User-ID` is the `id` of the acting `ShareholderAccount`; ownership checks on any resource that references a shareholder account compare the resource's account foreign key to `X-User-ID`, and a mismatch is rejected with `ERR_ACCOUNT_OWNERSHIP_REQUIRED`. `DealerOperations` carries a second, channel-shaped restriction described in §2.10, enforced through `ERR_DEALER_CHANNEL_REQUIRED`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Endpoints that return collections are paginated through two query parameters. `limit` sets the maximum number of items returned; when it is not supplied it defaults to 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` sets the number of items to skip and defaults to 0. A `limit` outside the 1-to-100 range, a `limit` or `offset` that is not an integer, a negative `offset`, and an unrecognized value supplied to any enum-valued or date-valued filter are each rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint says otherwise, collections are returned sorted by `created_at` in ascending order.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope. `total_count` reflects the number of records matching the request's filters before pagination is applied, and `has_more` is true when records matching those filters remain beyond the current page.

Beyond `limit` and `offset`, most collections accept resource-specific filters; those filters are named in the §3 narrative that introduces the resource they belong to. Every such filter is an exact-match filter, and supplying several of them narrows the result to records matching all of them.

### 2.4. The Logical Clock and the Business-Day Calendar

The platform never reads wall-clock time. All temporal reasoning — the instant stamped into `received_at`, the date an order prices on, whether a distribution's record date or pay date has arrived, whether a systematic plan is due, and the instants written into `finalized_at` and `closed_at` — is taken against a single logical clock. Before that clock has been moved for the first time, it reads exactly `2026-08-01T00:00:00Z`, which is a Saturday. It never falls back to real time.

Moving the clock is an operational capability exposed at `POST /_clock/set_current_utc`, available to `TransferAgentOperator`, `FundAccountant` and `ComplianceOfficer`. The request supplies `to_iso8601`, the instant the clock should read from that point forward, and the response reports the resulting `current_utc`. Every subsequent date and time comparison in the system reads the new instant.

Business days are Monday through Friday. No holiday calendar is modelled, so every weekday is a business day and Saturday and Sunday are not. Where the specification counts business days between two dates — written here as the number of business days separating an earlier date from a later one — the count includes every business day strictly after the earlier date and up to and including the later date.

### 2.5. Record Identity, Audit Fields and the Share Ledger

Every resource in the system carries an `id`: a server-minted UUID, with no type prefix and no client-supplied component. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the record was first written. The audit stamps are the one place real time survives: `created_at`, `updated_at` and the envelope's `api_request_timestamp` are taken from the server's own clock, not from the logical clock of §2.4, which governs only the domain instants that section names.

All resources except share ledger entries additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation of the record, and `version`, an integer that begins at 1 on creation and increments by one on every mutation. This applies to funds, share classes, shareholder accounts, positions, NAV records, trades, distributions, distribution payments, systematic plans, blue-sky registrations, pricing error cases and omnibus reconciliations alike, and it applies to mutations of derived fields just as much as to mutations a client requested directly: when a settlement moves a position's `shares`, that position's `updated_at` and `version` move with it. A single request advances a given record's `version` by exactly one no matter how many times that request mutates it, and a recomputation that leaves a derived value exactly as it already stood is not a mutation at all and advances nothing.

A `ShareLedgerEntry` is the one exception. The share ledger is append-only: an entry is written once and never modified, so an entry carries only `id` and `created_at`. It has no `updated_at` field and no `version` field at all.

### 2.6. Precision: Dollars, Shares, Prices and Percentages

Four numeric conventions run through the whole system, and all rounding is round-half-up.

- **Dollar amounts** are carried to exactly 2 decimal places. This covers gross and net trade amounts, sales loads, contingent deferred sales charges, cost basis, household basis, registration capacity, distribution amounts and reconciliation breaks.
- **Share quantities** are carried to exactly 3 decimal places, and share balances may never be negative.
- **Prices per share** — the struck NAV, the NAV applied to a trade, a class's seed price and a distribution's reinvestment price — are carried to exactly 4 decimal places, and a struck NAV must be greater than zero.
- **Percentages** — sales-load percentages drawn from a breakpoint schedule, the tier percentage recorded on a position, and the 12b-1 fee — are carried to 4 decimal places as decimal fractions, so one and a half percent is expressed as `0.0150`. A load percentage taken from a breakpoint schedule is used exactly as configured and is never itself rounded.

Where a calculation both multiplies and sums, the order in which rounding is applied is part of the specification and is stated with the calculation in §3. As a general principle the system rounds each individual component to its own precision first and sums the already-rounded components afterwards, rather than rounding an aggregate at the end.

### 2.7. Order of Rejection

Many operations are guarded by several checks at once, and which error a caller receives depends on evaluation order, not on which check the reader notices first. The server evaluates guards in the following fixed precedence; the first guard that fails determines the response, and no later guard is consulted.

1. **Authentication.** Both headers present and `X-User-Role` one of the five declared roles, otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorization.** The acting role appears in the endpoint's authorized-role list in §4, otherwise `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint.
3. **Request shape.** Every required field present, every enum value inside its declared set, every number within its declared decimal precision and sign, every date a well-formed ISO `YYYY-MM-DD` value; `gross_amount` present exactly for a `PURCHASE` and absent for a `REDEMPTION` or `EXCHANGE`; `shares_requested` present exactly for a `REDEMPTION` or `EXCHANGE` and absent for a `PURCHASE`; `exchange_target_share_class_id` present exactly for an `EXCHANGE`; `target_share_class_id` present exactly for a `SYSTEMATIC_EXCHANGE`; `dealer_firm_code` present exactly when `account_channel` is `NETWORKED` or `OMNIBUS`; `breakpoint_tiers` starting at a `min_qualifying_amount` of 0 and strictly ascending thereafter. A failure here is `ERR_INVALID_REQUEST` (422). Applies to every write endpoint.
4. **Path existence.** Every resource named in the URL path exists, validated left to right, so the leftmost missing identifier decides the response. The code is the one belonging to the missing resource type: `ERR_FUND_NOT_FOUND`, `ERR_SHARE_CLASS_NOT_FOUND`, `ERR_ACCOUNT_NOT_FOUND`, `ERR_POSITION_NOT_FOUND`, `ERR_NAV_RECORD_NOT_FOUND`, `ERR_TRADE_NOT_FOUND`, `ERR_DISTRIBUTION_NOT_FOUND`, `ERR_PAYMENT_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_REGISTRATION_NOT_FOUND`, `ERR_CASE_NOT_FOUND`, `ERR_RECONCILIATION_NOT_FOUND` or `ERR_LEDGER_ENTRY_NOT_FOUND`, each 404. Applies to every endpoint with a path parameter.
5. **Body reference existence.** Every foreign key supplied in a request body resolves to an existing row, answered with the same 404 family (`ERR_FUND_NOT_FOUND`, `ERR_SHARE_CLASS_NOT_FOUND`, `ERR_ACCOUNT_NOT_FOUND`, `ERR_NAV_RECORD_NOT_FOUND`, `ERR_TRADE_NOT_FOUND`). Applies to `POST /share-classes`, `POST /shareholder-accounts`, `PATCH /shareholder-accounts/{id}`, `POST /nav-records`, `POST /blue-sky-registrations`, `POST /trades`, `POST /distributions`, `POST /systematic-plans`, `POST /pricing-error-cases`, `POST /omnibus-reconciliations` and `POST /omnibus-reconciliations/{id}/adjust`.
6. **Account holder ownership.** When the acting role is `AccountHolder`, the account the request touches must be the account whose `id` equals `X-User-ID`, otherwise `ERR_ACCOUNT_OWNERSHIP_REQUIRED` (403). Applies to `GET /shareholder-accounts/{id}`, `PATCH /shareholder-accounts/{id}`, `GET /shareholder-accounts/{id}/positions`, `POST /trades`, `POST /systematic-plans` and `PATCH /systematic-plans/{id}`.
7. **Dealer channel entitlement.** When the acting role is `DealerOperations`, the account the request touches must have an `account_channel` of `NETWORKED` or `OMNIBUS`, otherwise `ERR_DEALER_CHANNEL_REQUIRED` (403). Applies to `POST /trades`, `POST /shareholder-accounts` and `POST /omnibus-reconciliations`.
8. **Version gating.** The supplied `expected_account_version` equals the target `ShareholderAccount`'s current `version`, and the supplied `expected_nav_record_version` equals the target `NavRecord`'s current `version`; a mismatch is `ERR_STALE_ACCOUNT_VERSION` or `ERR_STALE_NAV_RECORD_VERSION` (412). Applies to `POST /systematic-plans` and `POST /pricing-error-cases`. See §2.8.
9. **Account state.** The account referenced by the operation is in a state that permits it: purchase-side and redemption-side order capture, systematic plan creation and systematic plan execution all require the account's `status` to be `ACTIVE` or `RESTRICTED`, and `PENDING_DOCS` or `CLOSED` is rejected with `ERR_ACCOUNT_NOT_ACTIVE` (409). Applies to `POST /trades`, `POST /systematic-plans`, `POST /systematic-plans/{id}/execute`, `POST /shareholder-accounts/{id}/activate` and `POST /shareholder-accounts/{id}/close`.
10. **Declared transition.** The target resource is in a state from which the requested transition is declared. The code names the resource whose state blocked the request: `ERR_INVALID_TRADE_STATE`, `ERR_INVALID_NAV_STATE`, `ERR_INVALID_CASE_STATE`, `ERR_INVALID_DISTRIBUTION_STATE`, `ERR_INVALID_PLAN_STATE` or `ERR_INVALID_RECONCILIATION_STATE`, each 409. Applies to every action endpoint that drives a state machine transition.
11. **Restriction on purchase-side activity.** A `RESTRICTED` account may not originate purchase-side activity: capture of a `PURCHASE` or `EXCHANGE`, and execution of a `SYSTEMATIC_INVESTMENT` or `SYSTEMATIC_EXCHANGE` plan, are rejected with `ERR_ACCOUNT_RESTRICTED` (409). Applies to `POST /trades` and `POST /systematic-plans/{id}/execute`.
12. **Segregation of duties.** The compliance officer approving an as-of order must not be the actor that captured it, and the fund accountant running a reprocessing sweep must not be the actor that opened the case; a violation is `ERR_SEGREGATION_OF_DUTIES` (403). Applies to `POST /trades/{id}/approve-as-of` and `POST /pricing-error-cases/{id}/reprocess`.
13. **Late trading.** An order whose `as_of_date` equals the current logical clock date while the clock time is at or after the fund's cutoff is rejected outright with `ERR_LATE_TRADE_PROHIBITED` (422). Applies to `POST /trades`.
14. **As-of date sanity.** An `as_of_date` strictly after the current logical clock date, or falling on a Saturday or a Sunday, is rejected with `ERR_AS_OF_FUTURE_DATE` (422). Applies to `POST /trades`.
15. **As-of window.** The number of business days separating the `as_of_date` from the current business date must be at most three, otherwise `ERR_AS_OF_WINDOW_EXCEEDED` (422). Applies to `POST /trades`.
16. **Registration window overlap.** `ERR_BLUE_SKY_WINDOW_OVERLAP` (409) on `POST /blue-sky-registrations`, as described in §3.4.
17. **Distribution period overlap.** `ERR_DISTRIBUTION_PERIOD_OVERLAP` (409) on `POST /distributions`, as described in §3.7.
18. **NAV date uniqueness.** At most one NAV record may exist for a given share class and valuation date, otherwise `ERR_NAV_DATE_DUPLICATE` (409). Applies to `POST /nav-records`.
19. **Household link validity.** `ERR_ROA_LINK_INVALID` (422) on `POST /shareholder-accounts` and `PATCH /shareholder-accounts/{id}`, as described in §3.2.
20. **Exchange target validity.** An exchange's target class must differ from its source class, otherwise `ERR_EXCHANGE_TARGET_INVALID` (422). Applies to `POST /trades` and `POST /systematic-plans`.
21. **Reconciliation channel.** `ERR_RECON_CHANNEL_INVALID` (422) on `POST /omnibus-reconciliations`, as described in §3.10.
22. **Closed fund.** Purchase-side capture on a class whose fund has a `status` of `CLOSED_TO_NEW` is rejected with `ERR_FUND_CLOSED_TO_NEW` (422). Applies to `POST /trades`.
23. **NAV availability.** A NAV record must exist for the class and date the operation prices against, otherwise `ERR_NAV_NOT_AVAILABLE` (409). Applies to `POST /trades/{id}/price` and `POST /distributions/{id}/pay`.
24. **NAV usability.** The NAV record that would price the operation must not be `UNDER_ERROR_REVIEW` or `STALE_REPRICE_REQUIRED`, and for a distribution payment it must additionally be `FINAL` or `CORRECTED`; otherwise `ERR_NAV_NOT_FINAL` (409). Applies to `POST /trades/{id}/price` and `POST /distributions/{id}/pay`.
25. **State registration coverage.** `ERR_BLUE_SKY_NOT_REGISTERED` (422) on `POST /trades`, as described in §3.4.
26. **Adjustment citation.** `ERR_ADJUSTMENT_MISMATCH` (422) on `POST /omnibus-reconciliations/{id}/adjust`, as described in §3.10.
27. **Plan due date.** A systematic plan may execute only when the logical clock date is on or after the plan's `next_run_date`, otherwise `ERR_PLAN_NOT_DUE` (409). Applies to `POST /systematic-plans/{id}/execute`.
28. **Registration capacity.** `ERR_BLUE_SKY_CAPACITY_EXCEEDED` (422) on `POST /trades`, as described in §3.4.
29. **Share sufficiency.** A redemption or an exchange must not request more shares than the owning position holds, checked at capture and again at settlement; a failure is `ERR_INSUFFICIENT_SHARES` (422). Applies to `POST /trades` and `POST /trades/{id}/settle`.

Two consequences of this ordering are worth stating plainly. Because account state (rule 9) is evaluated before the declared-transition check (rule 10), an operation aimed at a `CLOSED` account surfaces as `ERR_ACCOUNT_NOT_ACTIVE` rather than as a state-machine rejection. And because version gating (rule 8) sits ahead of every business rule, a caller holding a stale view of an account or a NAV record learns that first, before any domain-specific complaint.

### 2.8. Version Gating on Superseding Writes

Two creation endpoints quietly supersede work that another writer may have created, and both are therefore gated on the version of the record they supersede against.

Creating a systematic plan — `POST /systematic-plans` — requires `expected_account_version` in the request body — it is a required field, not an optional one — carrying the `version` of the target `ShareholderAccount` as the client last observed it. If that value does not equal the account's current `version`, the creation is rejected with `ERR_STALE_ACCOUNT_VERSION` and HTTP 412. The protection matters because a new plan of the same `plan_type` and `source_share_class_id` terminates the account's prior `ACTIVE` plan of that shape; without the gate, a client working from an out-of-date view of the account would silently terminate a plan it never saw. Note that a successful plan creation itself increments the account's `version`, so a client creating two plans in sequence must re-read the account between them.

Opening a pricing error case — `POST /pricing-error-cases` — requires `expected_nav_record_version` in the request body, likewise a required field, carrying the `version` of the target `NavRecord` as the client last observed it. If that value does not equal the record's current `version`, the request is rejected with `ERR_STALE_NAV_RECORD_VERSION` and HTTP 412. Here the superseded work is a determination rather than a plan: a newly opened case supersedes any case still in `DETECTED` or `ASSESSED` on the same record, so a client holding a stale view of the record would discard a materiality determination it never observed.

No other endpoint accepts a version field. Endpoints outside these two neither require nor honour one, and a version supplied elsewhere carries no meaning.

### 2.9. Cascade Discipline and Derived-Field Reconciliation

Derived values in this system are never client-supplied and are never left to drift. A class's `total_shares_outstanding` is the sum of the `shares` of every position in that class; a position's `shares` is the sum of the `share_delta` of every share ledger entry written against it; a registration's `remaining_amount` is its `registered_amount` less its `reserved_amount` and less its `consumed_amount`; an account's `household_basis_amount` is a live aggregation over its household's positions. Whenever an input to one of these values changes, the value is recomputed within the same request that changed the input, and the recomputation is a mutation in the sense of §2.5 — it refreshes `updated_at` and increments `version` on the record it touches.

Cascades run to their full depth rather than one level. A single settlement, for example, moves a position balance, appends a ledger entry, moves the class share balance, moves cost basis, converts reserved state-registration capacity into consumed capacity, may drive that registration from `ACTIVE` to `EXHAUSTED`, and then recomputes the owning account's `household_basis_amount` and the `current_roa_tier_pct` of every position held by every account in that household — not merely of the position that moved. The reprocessing sweep that follows a material pricing correction is the deepest such chain in the system and is described link by link in §3.9.

Two properties hold throughout. First, cascades are immediate: by the time a request returns, every derived value it disturbed has been brought back into agreement, and a subsequent read observes the reconciled state. Second, cascades are symmetric: an operation that unwinds a prior operation — a cancellation, a trade reversal, a distribution reversal — reverses every derived value the original moved, including returning an `EXHAUSTED` registration to `ACTIVE` once its `remaining_amount` rises above zero again.

### 2.10. Segregation of Duties and Channel Entitlement

Two structural safeguards cut across the whole workflow rather than belonging to any one endpoint.

The first is segregation of duties, which applies at exactly two points. A backdated order is captured by one actor and approved by another: the approving compliance officer's `X-User-ID` must differ from the order's `captured_by_user_id`. A material pricing correction is opened by one fund accountant and reprocessed by another: the sweeping accountant's `X-User-ID` must differ from the case's `detected_by_user_id`. Both violations answer with `ERR_SEGREGATION_OF_DUTIES`. Note that the compliance officer who approves a correction and the compliance officer who closes an immaterial one are under no such restriction; the constraint binds only the two pairs named here.

The second is channel entitlement. `DealerOperations` acts on behalf of a selling dealer and is therefore confined to the accounts a dealer services — those whose `account_channel` is `NETWORKED` or `OMNIBUS`. An attempt by `DealerOperations` to open an account, capture an order, or file a reconciliation against an account whose `account_channel` is `DIRECT` is rejected with `ERR_DEALER_CHANNEL_REQUIRED`. The same channel value has a second, unrelated consequence: it selects which basis variant computes the account's household breakpoint qualification, as §3.2 describes.

## 3. Business Logic & Workflows

### 3.1. Reference Data: Funds, Share Classes and Breakpoint Schedules

Nothing else in the system can exist until fund accounting has registered the products. A `FundAccountant` registers a **Fund** by supplying its registrant `name` — non-empty and at most 120 characters — and its `fund_family_code`, a non-empty grouping code of at most 12 characters that identifies the family the fund belongs to. Two optional attributes complete the record. `cutoff_time_utc` is the fund's daily forward-pricing cutoff expressed as a 24-hour `HH:MM:SS` time in UTC and defaults to `16:00:00`; orders received strictly before that time of day on a business day price at that day's NAV. `status` is the fund's offering posture, either `ACTIVE` or `CLOSED_TO_NEW`, and defaults to `ACTIVE`. A fund that has moved to `CLOSED_TO_NEW` still supports redemptions and still pays distributions, but purchase-side capture against any of its classes is refused with `ERR_FUND_CLOSED_TO_NEW`.

Each fund is sold through one or more **Share Classes**, also registered by a `FundAccountant`. A class is created against a `fund_id` and carries a `class_code` — one of `A`, `B`, `C` or `I`, unique within its fund, a duplicate pairing being refused with `ERR_INVALID_REQUEST` — plus a `seed_nav_per_share` price to four decimal places and greater than zero, which is the price the class strikes at while it has no shares outstanding at all. The class's sales-load schedule arrives as `breakpoint_tiers`: an ordered array in which each element is an object with a `min_qualifying_amount` in dollars to two decimal places and a `load_pct` to four decimal places. At least one tier is required, the first tier's `min_qualifying_amount` must be exactly 0, the `min_qualifying_amount` values must strictly ascend across the array, and every `load_pct` must lie between 0 and 0.0850 inclusive — that is, no tier may charge more than eight and a half percent.

Two further class-level attributes shape downstream behaviour. `cdsc_enabled` is a boolean defaulting to false; when it is true, redemptions out of the class may carry a contingent deferred sales charge under the aging rules in §3.5. `twelve_b_one_fee_pct` is the annual 12b-1 distribution fee percentage, carried to four decimal places, never negative and otherwise unbounded, defaulting to `0.0025`; it is recorded for disclosure and is informational only — no calculation in this system consumes it. Finally, every class carries `total_shares_outstanding`, a computed three-decimal share balance that begins at `0.000`, never goes negative, and always equals the sum of `shares` across every position held in that class. It is the transfer agent's own share count, and the daily NAV strike reads it.

Share classes may be listed and narrowed by `fund_id` or by `class_code`, and a single class may be read directly to observe its live `total_shares_outstanding`. Funds may be read individually.

### 3.2. Shareholder Accounts, Households and Account Lifecycle

A **ShareholderAccount** is opened by a `TransferAgentOperator` or by `DealerOperations` and requires five attributes: the `registration_type`, which is the legal registration of the account and is one of `INDIVIDUAL`, `JOINT_TENANTS`, `UGMA_UTMA`, `IRA_TRADITIONAL`, `ROTH_IRA`, `TRUST` or `CORPORATE`; the `account_channel`, one of `DIRECT`, `NETWORKED` or `OMNIBUS`; the `state_code` of the registered owner, exactly two uppercase letters, which selects the state registration that the account's purchases will consume; the `tax_id` of record, non-empty; and the `primary_owner_name`, also non-empty. Three optional attributes may accompany them: `dividend_option`, the standing instruction for distributions, either `CASH` or `REINVEST` and defaulting to `CASH`; `linked_primary_account_id`, discussed below and defaulting to null; and `dealer_firm_code`, the selling dealer's firm code, which is required when `account_channel` is `NETWORKED` or `OMNIBUS` and must be omitted or null when it is `DIRECT`.

A newly opened account is created in `PENDING_DOCS` with `tin_certified` false, `household_basis_amount` `0.00`, and `restriction_reason` and `closed_at` both null. Its `household_basis_variant` is fixed from the channel at creation: an account whose `account_channel` is `DIRECT` or `NETWORKED` is a `MARKET_VALUE_BASIS` account, and an account whose `account_channel` is `OMNIBUS` is a `HISTORICAL_COST_BASIS` account. The reasoning is recordkeeping reach — for direct and networked accounts the transfer agent holds position-level records and may mark them to the struck NAV, whereas for an omnibus account it sees only dealer-supplied cost and may not mark the underlying sub-accounts to market.

**Rights of accumulation** work through household linking. An account whose `linked_primary_account_id` is null is a *primary* account and is a household of its own; an account that sets `linked_primary_account_id` to another account's `id` is aggregated into that primary's household. Linking is single-level and self-exclusive, and all three of the following must hold or the request is rejected with `ERR_ROA_LINK_INVALID`: the supplied identifier must not be the account's own `id`, it must reference an account whose own `linked_primary_account_id` is null, and it must reference an account whose `status` is `ACTIVE` or `RESTRICTED`. The same three conditions are enforced both when the account is opened and when the link is later changed.

The account's `household_basis_amount` is the rights-of-accumulation basis of that whole household, recomputed on every position change anywhere in the household — trade settlement, trade reversal, restatement following a NAV correction, distribution reinvestment and distribution reversal alike — and read whenever a purchase or an exchange is priced. It is computed as follows. The household of an account is its primary account together with every account linked into that primary; only household members whose `status` is `ACTIVE` or `RESTRICTED` participate, and members in `PENDING_DOCS` or `CLOSED` contribute `0.00`. Only positions whose `shares` is greater than `0.000` are considered. Under `MARKET_VALUE_BASIS`, each such position is valued at its share balance multiplied by the price of its class on the valuation date in question, rounded to cents, and those per-position amounts are then summed; the price of a class on a date is the `nav_per_share` of that class's NAV record whose `status` is `FINAL` or `CORRECTED` and whose `valuation_date` is on or before the date in question, taking the greatest such `valuation_date`, and breaking a tie between two records sharing that date in favour of the one with the earlier `created_at`. If no such record exists the position has no market price and contributes its `cost_basis_amount` instead. Under `HISTORICAL_COST_BASIS`, every qualifying position contributes its `cost_basis_amount` and nothing is marked to market, so appreciation never raises the qualifying amount and identical holdings can land in a lower breakpoint tier than they would in a direct account. In either variant the summed basis is rounded half-up to two decimal places to produce `household_basis_amount`. The valuation date used is the `trade_date` of the trade being priced when the figure is computed for a pricing decision, and the current logical clock date whenever the field is recomputed outside a trade.

The account's lifecycle runs through four states. A `TransferAgentOperator` records receipt of the account documents, which moves the account `PENDING_DOCS → ACTIVE`; that request supplies `tin_certified`, whose value is stamped onto the account, and it recomputes `household_basis_amount` — which for a brand-new account is `0.00` — and increments the account's `version`. Only an `ACTIVE` account may originate purchase-side orders. A `ComplianceOfficer` may place a restriction, moving `ACTIVE → RESTRICTED`; the supplied `restriction_reason` is stamped onto the account, every systematic plan on the account that was `ACTIVE` moves to `SUSPENDED` with its `suspension_reason` set to `ACCOUNT_RESTRICTED`, and the account's `version` increments. A `RESTRICTED` account may still redeem and still receives distributions, but it may not purchase or exchange. The same officer may reinstate the account, moving `RESTRICTED → ACTIVE`, which clears `restriction_reason` back to null and increments `version`; plans suspended by the restriction are deliberately *not* resumed automatically, and must be resumed explicitly if the shareholder wants them back.

Closing is the terminal act and is performed by a `TransferAgentOperator`. It is available from either `ACTIVE → CLOSED` or `RESTRICTED → CLOSED`, and it requires that every position belonging to the account holds exactly `0.000` shares and that the account has no trade still `UNSETTLED` whose `execution_status` is anything other than `CANCELLED`. On success `closed_at` is stamped with the current logical clock instant, every systematic plan on the account that is `ACTIVE` or `SUSPENDED` moves to `TERMINATED`, and the account's `version` increments. An attempt to activate, restrict, reinstate or close an account whose state does not permit it answers with `ERR_ACCOUNT_NOT_ACTIVE`, as does a close request against an account one of whose positions still holds a non-zero balance; a close blocked instead by an order still `UNSETTLED` answers `ERR_INVALID_TRADE_STATE`.

Two attributes may be revised after opening: a `TransferAgentOperator` or the `AccountHolder` themselves may submit `dividend_option`, `linked_primary_account_id`, or both. When the link changes, the `household_basis_amount` of both the household the account is leaving and the household it is joining is recomputed, and the account's `version` increments. The link is rewritten only when the `linked_primary_account_id` key is actually present in the body — supplying it as null unlinks the account back into a household of its own, while omitting it leaves the existing link alone — and a request that supplies neither attribute is still accepted and still increments `version`. Accounts may be listed and narrowed by `status`, by `account_channel`, by `state_code`, and by `linked_primary_account_id` — the last of which returns the household members aggregated into a given primary account.

A **Position** is the account's holding in a single class, identified by its `account_id` and `share_class_id`. Positions are never created directly by a client; the system creates one the first time a trade settles into that account-and-class pair, and a freshly created position starts with `shares` at `0.000`, `cost_basis_amount` at `0.00`, `reinvested_shares` at `0.000`, `avg_cost_per_share` at `0.0000`, `current_roa_tier_pct` at `0.0000`, `market_value_amount` at `0.00` and `first_purchase_date` null. A position carries `shares`, its three-decimal balance, which is always the sum of the `share_delta` of every ledger entry written against it and never negative; `cost_basis_amount`, its aggregate dollar cost basis to two decimals, increased by the gross amount of purchases and reinvestments and reduced proportionally on redemptions; `reinvested_shares`, the cumulative three-decimal quantity acquired through distribution reinvestment, a bucket that is exempt from contingent deferred sales charges; `avg_cost_per_share`, which is `cost_basis_amount` divided by `shares` to four decimal places and is `0.0000` whenever `shares` is `0.000`; `first_purchase_date`, the ISO `YYYY-MM-DD` trade date of the first settled purchase into the position, which drives contingent deferred sales charge aging and is null until that first purchase settles; `current_roa_tier_pct`, the four-decimal sales-load percentage that the owning account's `household_basis_amount` currently qualifies for in this class's breakpoint schedule; and `market_value_amount`, the position's `shares` multiplied by the class's most recent priced NAV, rounded to two decimals. Positions can be read individually, listed for an account with an optional `share_class_id` narrowing, or listed globally and narrowed by `account_id` or `share_class_id`.

### 3.3. The Daily NAV Strike, Finalization and Repost

A **NavRecord** is a `FundAccountant`'s statement of what one share class was worth on one business date. Striking one supplies the `share_class_id`, the `valuation_date` — an ISO `YYYY-MM-DD` date that must fall Monday through Friday, a Saturday or Sunday being refused with `ERR_INVALID_REQUEST` — and `total_net_assets`, the class's net assets on that date to two decimal places and never negative. At most one record may exist per share class and valuation date; a second attempt at the same pair is refused with `ERR_NAV_DATE_DUPLICATE`.

The strike itself is mechanical. At the moment of the call the class's live `total_shares_outstanding` is captured into `shares_outstanding_snapshot`. If that snapshot is exactly `0.000` — the class has no shares on the transfer agent's books — then `nav_per_share` is set to the class's configured `seed_nav_per_share`. Otherwise `nav_per_share` is the supplied `total_net_assets` divided by `shares_outstanding_snapshot`, rounded half-up to four decimal places. The same computation runs on every re-strike, always reading the share balance as it stands at that moment rather than as it stood originally.

A record is born `PRELIMINARY` and lives through five possible states: `PRELIMINARY`, `FINAL`, `UNDER_ERROR_REVIEW`, `CORRECTED` and `STALE_REPRICE_REQUIRED`. Finalizing a preliminary strike is a `FundAccountant` action that moves it `PRELIMINARY → FINAL`, stamps `finalized_at` with the current logical clock instant, and increments the record's `version`. Only a record that is currently `PRELIMINARY` may be finalized; anything else answers `ERR_INVALID_NAV_STATE`.

Re-striking is available in two situations and is likewise a `FundAccountant` action, supplying a fresh `total_net_assets`. A record that is still `PRELIMINARY` may be re-struck any number of times before it is finalized, leaving it `PRELIMINARY` — the `PRELIMINARY → PRELIMINARY` self-transition. A record that has been driven to `STALE_REPRICE_REQUIRED` by a share-balance restatement is re-struck `STALE_REPRICE_REQUIRED → PRELIMINARY`, completing the `PRELIMINARY → STALE_REPRICE_REQUIRED → PRELIMINARY` cycle. In both cases `shares_outstanding_snapshot` and `nav_per_share` are recomputed by the strike rule above from the supplied net assets and the live share balance, and `version` increments. Because a revision overwrites `nav_per_share`, an order already priced provisionally against that record will produce a different share quantity when it is repriced — this is the intended consequence of provisional pricing, not an anomaly. A re-strike attempted on a record that is `FINAL`, `UNDER_ERROR_REVIEW` or `CORRECTED` is rejected with `ERR_INVALID_NAV_STATE`.

The record also carries `original_nav_per_share`, which stays null for the record's whole ordinary life. It is written only when a pricing-error correction overwrites the price, at which point it preserves the `nav_per_share` value that was in force immediately beforehand. The remaining NAV states — `UNDER_ERROR_REVIEW` and `CORRECTED` — are reached only through the pricing-error workflow in §3.9, never by direct request. NAV records may be listed for a share class and narrowed by `valuation_date` or by `status`, and may be read individually.

### 3.4. State Registration Capacity and Order Capture

Before a class may be sold into a state, a `ComplianceOfficer` files a **BlueSkyRegistration** covering it. The filing names the `share_class_id`, the two-uppercase-letter `state_code` the notice filing covers, the `registered_amount` of shares registered for sale in that state in dollars to two decimal places and greater than zero, and the registration window's `effective_date` and `expiration_date`, both ISO `YYYY-MM-DD` dates with the expiration strictly later than the effective date. The window is half-open: the `effective_date` is inside it and the `expiration_date` is outside it. For a given share class and state, a new window may not intersect the window of an existing registration whose `status` is `ACTIVE` or `EXHAUSTED`; because the interval is half-open, touching endpoints do not intersect, so a new registration whose `effective_date` equals an existing registration's `expiration_date` is accepted, while any genuine overlap is refused with `ERR_BLUE_SKY_WINDOW_OVERLAP`. A new filing starts with `reserved_amount` and `consumed_amount` at `0.00`, `remaining_amount` equal to `registered_amount`, and `status` `ACTIVE`. Registrations may be read individually and listed for a share class with optional narrowing by `state_code` or `status`.

Capacity is a three-way split that must always reconcile: `remaining_amount` is `registered_amount` less `reserved_amount` less `consumed_amount`, and that identity holds after every step of the workflow. Reserved capacity is held for captured but not yet settled purchase-side dollars; consumed capacity is permanently used by settled purchase-side dollars. Redemptions never restore capacity. Whenever `remaining_amount` reaches exactly `0.00` the registration moves `ACTIVE → EXHAUSTED`, and whenever it rises back above `0.00` after a cancellation or a reversal it moves `EXHAUSTED → ACTIVE`, so the two states cycle freely. A registration whose `expiration_date` is on or before the trade date of an order being captured moves `ACTIVE → EXPIRED`, and because an `EXPIRED` registration is no longer a candidate for anything, that capture is refused with `ERR_BLUE_SKY_NOT_REGISTERED` unless some other window still covers it. The sweep is scoped to the capture that provoked it: only purchase-side capture consults the ledger at all, and it expires only those registrations sharing the class it is resolving against — the target class for an `EXCHANGE` — and the account's `state_code`.

**Order capture** is the entry point for all shareholder activity, and is open to a `TransferAgentOperator`, a `ComplianceOfficer`, `DealerOperations` and the `AccountHolder`. The order names the `account_id` it books to, the `share_class_id` being purchased, redeemed or exchanged out of, and the `trade_type`, which is one of `PURCHASE`, `REDEMPTION`, `EXCHANGE` or `REINVESTMENT`. A `PURCHASE` carries `gross_amount`, the dollar amount invested to two decimals and greater than zero, and no `shares_requested`. A `REDEMPTION` or an `EXCHANGE` carries `shares_requested`, the three-decimal quantity to redeem or exchange out, greater than zero, and no `gross_amount`. An `EXCHANGE` additionally names its `exchange_target_share_class_id`, the class being exchanged into, which must be present for an exchange, must be null otherwise, and must differ from `share_class_id` — an exchange into the same class is refused with `ERR_EXCHANGE_TARGET_INVALID`. The `REINVESTMENT` kind is reserved for the trades the system creates for itself when a distribution pays; a client that names it on `POST /trades` is refused with `ERR_INVALID_REQUEST`. Two optional attributes complete the payload: `as_of_date`, the past business date the client asks the order to be priced at, which is null for an ordinary forward-priced order; and `dealer_reference`, free text retained for reconciliation.

Capture stamps `received_at` from the current logical clock instant and `captured_by_user_id` from the caller's `X-User-ID`, and computes `trade_date`, the effective pricing date. The forward-pricing rule is this. Read the logical clock's calendar date and time-of-day in UTC, and read the `cutoff_time_utc` of the fund that owns the class being traded. If an `as_of_date` was supplied, `trade_date` is that date, subject to the as-of controls below. Otherwise, if the clock's date is a business day and the clock's time-of-day is strictly earlier than the cutoff, `trade_date` is the clock's date; in every other case — the clock's date falls on a weekend, or the time-of-day is exactly at or later than the cutoff — `trade_date` is the earliest business day strictly after the clock's date. The comparison against the cutoff is strict in the shareholder's disfavour: an order arriving at exactly the cutoff second prices on the next business day, not the current one.

Backdating is where the discipline concentrates. An order that carries an `as_of_date` is created directly with an `execution_status` of `PENDING_AS_OF_APPROVAL` rather than `RECEIVED` — the `RECEIVED → PENDING_AS_OF_APPROVAL` step is taken at capture, not by a later request — and it is not priced at all until compliance releases it. Its `trade_date` is the supplied `as_of_date`, and `captured_by_user_id` is stamped from the caller exactly as for an ordinary order. Three controls guard it. First, late trading: an `as_of_date` equal to the current logical clock date while the clock's time-of-day is at or after the fund's cutoff is refused outright with `ERR_LATE_TRADE_PROHIBITED` — this is the prohibition against handing a shareholder today's already-known price after today's book has closed. Second, an `as_of_date` strictly after the current logical clock date, or one that falls on a Saturday or a Sunday, is refused with `ERR_AS_OF_FUTURE_DATE`. Third, the number of business days separating the `as_of_date` from the current business date must be at most three; a wider gap is refused with `ERR_AS_OF_WINDOW_EXCEEDED`. What remains permitted, therefore, is an `as_of_date` on a business date strictly before the capture date, or equal to the capture date while the clock's time-of-day is still strictly before the fund's cutoff.

A pending order is released by a `ComplianceOfficer`, moving it `PENDING_AS_OF_APPROVAL → RECEIVED`; the approval stamps `approved_by_user_id` from the approver's `X-User-ID` and increments the trade's `version`. The approver's identifier must differ from the order's `captured_by_user_id`, or the release is refused with `ERR_SEGREGATION_OF_DUTIES`. Only an order actually sitting in `PENDING_AS_OF_APPROVAL` may be released; any other execution state answers `ERR_INVALID_TRADE_STATE`.

Capture also runs the eligibility gauntlet. The owning account must be `ACTIVE` or `RESTRICTED`, and a `PENDING_DOCS` or `CLOSED` account is refused with `ERR_ACCOUNT_NOT_ACTIVE`; a `RESTRICTED` account may redeem but a `PURCHASE` or `EXCHANGE` from it is refused with `ERR_ACCOUNT_RESTRICTED`. A `PURCHASE` or `EXCHANGE` on a class whose fund is `CLOSED_TO_NEW` is refused with `ERR_FUND_CLOSED_TO_NEW`; for an `EXCHANGE` both funds are examined, the target class's fund first and the source class's fund second. A `REDEMPTION` or `EXCHANGE` asking for more shares than the owning position holds is refused with `ERR_INSUFFICIENT_SHARES`.

For purchase-side orders the registration ledger is consulted at capture. The system selects among the registrations for the class being bought — for an `EXCHANGE`, the *target* class — whose `state_code` equals the owning account's `state_code`, whose `status` is `ACTIVE` or `EXHAUSTED`, and whose window covers the `trade_date` in the half-open sense of `effective_date` on or before the trade date and `expiration_date` strictly after it. Among the candidates the one with the greatest `effective_date` wins, and a tie between equally recent windows is broken in favour of the earlier `created_at`. If no candidate survives, capture is refused with `ERR_BLUE_SKY_NOT_REGISTERED`. The selected registration's identifier is recorded on the order as `blue_sky_registration_id`, which stays null for orders that consume no capacity at all. For a `PURCHASE`, the order's `gross_amount` must be less than or equal to that registration's `remaining_amount` — equality is accepted and drives the registration straight to `EXHAUSTED` — and an amount above it is refused with `ERR_BLUE_SKY_CAPACITY_EXCEEDED`; on success `reserved_amount` increases by `gross_amount`. An `EXCHANGE` reserves nothing at capture: its registration is resolved and validated, but its dollars only move through the ledger at settlement.

Every captured order begins life with a `settlement_status` of `UNSETTLED`, and with `pricing_variant`, `nav_per_share_applied`, `roa_qualifying_amount`, `roa_basis_variant`, `sales_load_pct`, `sales_load_amount`, `net_invested_amount`, `shares_transacted`, `gross_proceeds_amount`, `cdsc_amount`, `net_proceeds_amount`, `exchange_target_shares` and `restated_share_delta` all null, together with `cancel_reason`, `reversal_reason`, `approved_by_user_id`, `parent_distribution_id` and `originating_plan_id`. Orders may be read individually and listed with narrowing by `account_id`, `share_class_id`, `exchange_target_share_class_id`, `parent_distribution_id`, `originating_plan_id`, `blue_sky_registration_id`, `execution_status`, `settlement_status`, `trade_date` or `trade_type`.

### 3.5. Pricing: Rights of Accumulation, Breakpoints, Redemption Charges and Exchanges

Pricing an order is performed by a `TransferAgentOperator` or a `FundAccountant` and is the step that attaches money and shares to an order that so far carries only an instruction. It reads the NAV record for the order's own `share_class_id` and `trade_date`; for an `EXCHANGE` it additionally reads the record for the `exchange_target_share_class_id` on that same date. If a required record does not exist, pricing is refused with `ERR_NAV_NOT_AVAILABLE`. If a required record exists but is `UNDER_ERROR_REVIEW` or `STALE_REPRICE_REQUIRED`, pricing is refused with `ERR_NAV_NOT_FINAL` — an order may not be priced against a NAV whose correctness is in question or whose share base has been invalidated.

Pricing has two variants and they are decided by the state of the record for the order's own `share_class_id` at the moment pricing runs — for an `EXCHANGE` the target class's record is consulted for existence and usability only and never decides the variant, so a final source strike prices the order finally even while the target strike is still preliminary. When the record is still `PRELIMINARY`, the order prices against the preliminary strike, `pricing_variant` is set to `PRELIMINARY_NAV`, and the order moves `RECEIVED → PRICED_PROVISIONAL`; provisional pricing touches no position and settlement remains blocked. When the record is `FINAL` or `CORRECTED`, the order prices against the final strike, `pricing_variant` is set to `FINAL_NAV`, and the order moves either `RECEIVED → PRICED_FINAL` directly or `PRICED_PROVISIONAL → PRICED_FINAL` if it had been priced provisionally before; every priced field is recomputed against the final NAV, so `shares_transacted` may well differ from the provisional quantity, and it is the final quantity that reaches the ledger. In both variants `nav_per_share_applied` records the NAV per share actually used. Pricing an order whose `execution_status` is not one of `RECEIVED` or `PRICED_PROVISIONAL` — a cancelled order, a pending as-of order, an order already `PRICED_FINAL` when the record is not yet final — answers `ERR_INVALID_TRADE_STATE`.

For a `PURCHASE`, the sales-load computation runs in a pinned order and the tier is never re-derived once chosen. Step one computes `roa_qualifying_amount` as the buying account's `household_basis_amount` — evaluated under the household rules of §3.2 with the valuation date set to the order's `trade_date` — plus the order's `gross_amount`, and records which basis variant produced it in `roa_basis_variant`, either `MARKET_VALUE_BASIS` or `HISTORICAL_COST_BASIS`. Step two selects the tier: among the class's `breakpoint_tiers`, the tier chosen is the one with the greatest `min_qualifying_amount` that is less than or equal to `roa_qualifying_amount`, and that tier's `load_pct` becomes the order's `sales_load_pct`. Step three computes `sales_load_amount` as `gross_amount` multiplied by that percentage, rounded half-up to two decimal places. Step four computes `net_invested_amount` as `gross_amount` minus `sales_load_amount`. Step five computes `shares_transacted` as `net_invested_amount` divided by the applied NAV, rounded half-up to three decimal places, and the result is positive because a purchase adds shares. The tier is selected from the qualifying amount computed in step one and is never recomputed against the net amount produced in step four, even though the net amount is smaller. Pricing a purchase leaves `gross_proceeds_amount`, `cdsc_amount`, `net_proceeds_amount` and `exchange_target_shares` null, just as pricing a redemption leaves `sales_load_pct`, `sales_load_amount`, `net_invested_amount` and `exchange_target_shares` null. A system-created `REINVESTMENT` order bypasses steps one through four entirely: its `sales_load_pct` is `0.0000`, its `sales_load_amount` is `0.00`, and its `net_invested_amount` is the net amount of the distribution payment that produced it; only step five applies.

A `REDEMPTION` is priced through a waterfall. Its `gross_proceeds_amount` is `shares_requested` multiplied by the applied NAV, rounded half-up to two decimals. If the class's `cdsc_enabled` is false, its `cdsc_amount` is `0.00` and nothing further is computed. If the class does carry a contingent deferred sales charge but no position exists yet or its `first_purchase_date` is still null, `cdsc_amount` is likewise `0.00`. Otherwise the holding period is the number of calendar days from the position's `first_purchase_date` to the order's `trade_date`, and the charge rate is one percent — `0.0100` — while the holding period is under 365 days, one half of one percent — `0.0050` — while it is at least 365 days and under 730 days, and zero — `0.0000` — from 730 days onward. Three deductions then shrink the charge's reach. The free allowance is ten percent of the position's current `shares`, rounded half-up to three decimals. The reinvestment exclusion is the smaller of the position's `reinvested_shares` and the order's `shares_requested`, because shares acquired through reinvestment are never charged. The chargeable quantity is the order's `shares_requested` less the free allowance less the reinvestment exclusion, floored at `0.000` so it can never go negative. The charge basis is the smaller of the position's `avg_cost_per_share` and the applied NAV. `cdsc_amount` is then the chargeable quantity multiplied by the charge basis multiplied by the charge rate, with that whole product rounded half-up to two decimals exactly once, at the end. `net_proceeds_amount` is `gross_proceeds_amount` minus `cdsc_amount`, and `shares_transacted` is the negative of `shares_requested`, because a redemption removes shares.

An `EXCHANGE` is priced against both classes on the trade date. Its `gross_proceeds_amount` is `shares_requested` multiplied by the source class's NAV, rounded half-up to two decimals; its `cdsc_amount` is always `0.00`, because an exchange never carries a contingent deferred sales charge; and its `net_proceeds_amount` therefore equals its `gross_proceeds_amount`. The load charged on the way in depends on whether the shareholder is staying inside the same fund. When the source and target classes belong to the same fund — that is, when the two classes carry the same `fund_id`, which is how a family's own share classes are grouped — the target load percentage is `0.0000` and the exchange is load-free. When they belong to different funds, the qualifying amount is the account's `household_basis_amount` plus the `gross_proceeds_amount`, the tier is the one in the *target* class's `breakpoint_tiers` with the greatest `min_qualifying_amount` less than or equal to that qualifying amount, and that tier's `load_pct` is the target load percentage. Either way the target load percentage is what the order records as its `sales_load_pct`, so a same-fund exchange records `0.0000`; `roa_qualifying_amount` and `roa_basis_variant` are written only on the cross-fund branch — and from the account's stored `household_basis_amount` exactly as it stands, not re-evaluated against the trade date — staying null on the same-fund branch. `sales_load_amount` is `gross_proceeds_amount` multiplied by the target load percentage, rounded half-up to two decimals. `exchange_target_shares` is `gross_proceeds_amount` minus `sales_load_amount`, divided by the target class's NAV, rounded half-up to three decimals. As with a redemption, `shares_transacted` is the negative of `shares_requested`, since it describes the movement out of the source class.

### 3.6. Settlement, the Share Ledger, Cancellation and Reversal

Settlement is the moment shares actually move, and it is reserved to a `TransferAgentOperator`. An order may settle only when its `execution_status` is `PRICED_FINAL` and its `settlement_status` is still `UNSETTLED`; an attempt from any other combination answers `ERR_INVALID_TRADE_STATE`, which is what blocks a provisionally priced order from reaching the books. For a `REDEMPTION` or an `EXCHANGE` the owning position must still hold at least the `shares_requested` quantity at this second checkpoint, and a shortfall that has opened up since capture is refused with `ERR_INSUFFICIENT_SHARES`.

A successful settlement moves the order `UNSETTLED → SETTLED` and carries out a chain of book entries. The position for the order's `account_id` and `share_class_id` is created if it does not yet exist, and its `shares` then changes by the order's `shares_transacted` — upward for a purchase or a reinvestment, downward for a redemption or an exchange out. A **ShareLedgerEntry** is appended recording the movement, with its `position_id` naming the position, its `trade_id` naming the order, its `share_delta` equal to the order's `shares_transacted`, its `effective_date` set to the order's `trade_date`, its `resulting_share_balance` set to the position's `shares` immediately after the entry was appended, and its `entry_reason` set to the cause of the movement. The reason vocabulary is `PURCHASE_SETTLEMENT`, `REDEMPTION_SETTLEMENT`, `EXCHANGE_OUT`, `EXCHANGE_IN`, `DIVIDEND_REINVESTMENT`, `NAV_CORRECTION_RESTATEMENT`, `TRADE_REVERSAL` and `DISTRIBUTION_REVERSAL`; a `trade_id` is null only for the distribution-driven adjustments that are booked without a trade of their own, and a `share_delta` is never exactly zero. The class's `total_shares_outstanding` then changes by the same `shares_transacted`.

The remaining effects depend on the kind of order. A settling `PURCHASE` increases the position's `cost_basis_amount` by the order's `gross_amount`, and converts its state-registration hold into permanent use: the selected registration's `reserved_amount` decreases by `gross_amount` while its `consumed_amount` increases by the same figure. A settling `REDEMPTION` reduces the position's `cost_basis_amount` proportionally — by the cost basis before the settlement multiplied by the `shares_requested` quantity divided by the share balance before the settlement, rounded half-up to two decimal places. A settling `EXCHANGE` does double duty: the target position gains the order's `exchange_target_shares`, a second ledger entry with an `entry_reason` of `EXCHANGE_IN` is appended for that target position while the source movement carries `EXCHANGE_OUT`, and the target class's registration consumes the order's `gross_proceeds_amount` — this is the point at which an exchange finally touches state-registration capacity, since it reserved none at capture. Whenever a registration's `remaining_amount` falls to exactly `0.00` as a result, its `status` moves to `EXHAUSTED`. The first settled purchase into a position stamps that position's `first_purchase_date` with the order's `trade_date`, which is where the contingent deferred sales charge clock starts. Finally the owning account's `household_basis_amount` is recomputed and, because the household's qualification may have shifted, the `current_roa_tier_pct` of every position held by every account in that household is recomputed against its own class's `breakpoint_tiers`.

An order that has not settled can still be withdrawn. Cancellation is available to a `TransferAgentOperator` from `RECEIVED → CANCELLED`, `PRICED_PROVISIONAL → CANCELLED` and `PRICED_FINAL → CANCELLED`, and to a `ComplianceOfficer` from `PENDING_AS_OF_APPROVAL → CANCELLED`, though the check is on the state rather than on the pairing, so either of those two roles may in fact drive any of the four transitions; in every case the order's `settlement_status` must still be `UNSETTLED`, and the request supplies a `cancel_reason` that is stamped onto the order. Cancelling releases whatever state-registration capacity the order was holding, which only a `PURCHASE` ever has, so a cancelled `REDEMPTION` or `EXCHANGE` releases nothing: the registration's `reserved_amount` decreases by the order's `gross_amount`, and if that lifts the registration's `remaining_amount` above `0.00` while its `status` was `EXHAUSTED`, the registration returns to `ACTIVE`. `CANCELLED` is terminal on the pricing dimension.

Reversal is the settled counterpart and belongs to a `ComplianceOfficer`. It moves an order `SETTLED → REVERSED` and requires that the order is currently `SETTLED`, that its `trade_type` is not `REINVESTMENT` — reinvestment trades are unwound only through their parent distribution — and that the resulting position balance would not go negative; each of those three failures answers `ERR_INVALID_TRADE_STATE`. The supplied `reversal_reason` is stamped onto the order, and a compensating ledger entry with an `entry_reason` of `TRADE_REVERSAL` and a `share_delta` equal to the negative of the order's `shares_transacted` is appended, so the position's `shares` and the class's `total_shares_outstanding` both move back by the same magnitude. Reversing a `PURCHASE` additionally decreases the position's `cost_basis_amount` by the order's `gross_amount` and decreases the registration's `consumed_amount` by the same amount; if that lifts `remaining_amount` above `0.00` while the registration was `EXHAUSTED`, it returns to `ACTIVE`. Reversing an `EXCHANGE` unwinds the source side only: the target position's shares, the target class's `total_shares_outstanding` and the target registration's `consumed_amount` are all left exactly as they stand. As with settlement, the owning account's `household_basis_amount` and every household position's `current_roa_tier_pct` are recomputed afterwards. `REVERSED` is terminal on the settlement dimension.

The two dimensions are genuinely independent, and the pair of them is the order's full state. An order can be `PRICED_FINAL` and `UNSETTLED`, `PRICED_FINAL` and `SETTLED`, or — after a material pricing correction — `RESTATED` and `SETTLED`. Ledger entries can be read individually and listed with narrowing by `position_id`, `trade_id`, `entry_reason` or `effective_date`; the ledger is visible to a `TransferAgentOperator`, a `FundAccountant` and a `ComplianceOfficer` only.

### 3.7. Distributions: Declaration, Record Date, Payment and Reversal

A **Distribution** is declared by a `FundAccountant` against a `share_class_id`. Its `distribution_type` states its character and is one of `ORDINARY_INCOME`, `SHORT_TERM_CAPITAL_GAIN` or `LONG_TERM_CAPITAL_GAIN`. Its `rate_per_share` is the declared rate to four decimal places, greater than zero. Three dates order the workflow: `record_date`, on which holders of record are determined; `ex_date`, on or after the record date, whose NAV prices reinvestment; and `pay_date`, on or after the ex date. Either ordering violated is an `ERR_INVALID_REQUEST`. For a given share class and distribution type, the closed interval running from a new declaration's `record_date` through its `pay_date` inclusive may not intersect that of an existing declaration whose `status` is `DECLARED`, `RECORDED` or `PAID`. Because both endpoints of that interval are inclusive, a new declaration whose `record_date` equals an existing declaration's `pay_date` *is* an intersection and is refused with `ERR_DISTRIBUTION_PERIOD_OVERLAP`. A new declaration begins `DECLARED` with `payment_count` at 0, `total_gross_amount`, `total_withholding_amount`, `total_cash_amount` and `total_reinvested_amount` all `0.00`, and `reinvest_nav_per_share` null. Distributions may be listed for a share class and narrowed by `distribution_type` or `status`.

Recording is the second step, again a `FundAccountant` action, and it is permitted only when the distribution is `DECLARED` and the logical clock date is on or after its `record_date`; otherwise it answers `ERR_INVALID_DISTRIBUTION_STATE`. Recording moves the distribution `DECLARED → RECORDED` and freezes the holders of record by creating one **DistributionPayment** per eligible position. A position is eligible when its `share_class_id` matches the declaring class, its `shares` is greater than `0.000`, and its owning account's `status` is `ACTIVE` or `RESTRICTED`; eligible positions are processed in ascending `created_at` order. Positions created after the record step are never picked up by that distribution.

Each payment records its `distribution_id`, its `account_id`, its `position_id`, and the position's `shares` at that instant as `shares_of_record` to three decimals. Its `gross_amount` is `shares_of_record` multiplied by the distribution's `rate_per_share`, rounded half-up to cents *before* anything is summed. Its `withholding_amount` is backup withholding retained from the gross: when the owning account's `tin_certified` is false and its `registration_type` is not one of `IRA_TRADITIONAL`, `ROTH_IRA` or `UGMA_UTMA`, it is twenty-four percent of `gross_amount` rounded half-up to cents; in every other case — a certified account, or any of those three tax-advantaged registrations regardless of certification — it is `0.00`. Its `net_amount` is `gross_amount` minus `withholding_amount`. Its `payout_option` captures the owning account's `dividend_option` as it stood at record time, either `CASH` or `REINVEST`, so a later change to the standing instruction does not re-route a payment already recorded. Each payment is created with a `status` of `PENDING`, with `cash_amount` `0.00`, `reinvested_shares` `0.000` and `reinvestment_trade_id` null. The distribution's `payment_count` is the number of payment rows created, its `total_gross_amount` is the sum of the already-rounded per-payment `gross_amount` values, and its `total_withholding_amount` is the sum of the already-rounded per-payment `withholding_amount` values. The rounding order is part of the specification: rounding each payment to cents and then summing is required, and rounding an aggregate of unrounded products instead can differ by a cent or more.

Payment is the third step and is permitted only when the distribution is `RECORDED` and the logical clock date is on or after its `pay_date`, otherwise `ERR_INVALID_DISTRIBUTION_STATE`. It additionally requires a NAV record for the declaring class on the distribution's `ex_date`: if none exists the request answers `ERR_NAV_NOT_AVAILABLE`, and if one exists whose `status` is not `FINAL` or `CORRECTED` it answers `ERR_NAV_NOT_FINAL`. On success the distribution moves `RECORDED → PAID`, that record's `nav_per_share` is stamped onto the distribution as `reinvest_nav_per_share`, and every payment moves `PENDING → PAID`. A payment whose `payout_option` is `CASH` takes its `net_amount` as its `cash_amount` and leaves `reinvested_shares` at `0.000`. A payment whose `payout_option` is `REINVEST` takes `reinvested_shares` as its `net_amount` divided by the reinvestment NAV, rounded half-up to three decimals, and leaves `cash_amount` at `0.00`; a `REINVESTMENT` order is created for it carrying `parent_distribution_id` pointing at the distribution, and that order is created already `PRICED_FINAL` on the pricing dimension and `SETTLED` on the settlement dimension in one step, with its identifier stamped onto the payment as `reinvestment_trade_id`. That order's `trade_date` is the distribution's `ex_date`, its `received_at` is the current logical clock instant, its `captured_by_user_id` is the paying accountant, its `pricing_variant` is `FINAL_NAV` and its `nav_per_share_applied` is the reinvestment NAV, while its `gross_amount`, `shares_requested` and `blue_sky_registration_id` stay null — a reinvestment consumes no state-registration capacity. Because that order settles, the position's `shares` and its `reinvested_shares` both increase by the payment's `reinvested_shares`, a ledger entry with an `entry_reason` of `DIVIDEND_REINVESTMENT` is appended, the position's `cost_basis_amount` increases by the payment's `net_amount`, and the class's `total_shares_outstanding` increases by the same share quantity. Because those balances changed, each affected account's `household_basis_amount` is recomputed, and because that basis changed, every position of every affected household has its `current_roa_tier_pct` recomputed from its class's `breakpoint_tiers`. The distribution's `total_cash_amount` is written as the sum of the per-payment `cash_amount` values, and its `total_reinvested_amount` as the sum of the `net_amount` values of the reinvesting payments.

Reversal is a `ComplianceOfficer` action available only from `PAID → REVERSED`, and only while every `REINVESTMENT` order the distribution created still has a `settlement_status` of `SETTLED` — if one has already been unwound by other means the reversal is refused with `ERR_INVALID_DISTRIBUTION_STATE`. The request may carry an optional `reversal_reason`, which when supplied is stamped onto each reinvestment order the reversal unwinds rather than onto the distribution itself. Reversing moves every payment `PAID → REVERSED`, moves each reinvestment order `SETTLED → REVERSED` with a compensating ledger entry whose `entry_reason` is `DISTRIBUTION_REVERSAL`, and returns each affected position's `shares`, `reinvested_shares` and `cost_basis_amount`, together with the class's `total_shares_outstanding`, to their pre-payment values. The distribution's `total_cash_amount`, `total_reinvested_amount`, `total_withholding_amount` and `total_gross_amount` are all reset to `0.00`, while `payment_count` and `reinvest_nav_per_share` are deliberately left as they stood, so the record still shows how many holders were paid and at what price. Payments may be read individually and listed with narrowing by `distribution_id`, `account_id`, `position_id`, `reinvestment_trade_id` or `status`.

### 3.8. Systematic Plans

A **SystematicPlan** is a standing instruction that generates orders on a cadence. It is created by a `TransferAgentOperator` or by the `AccountHolder` for an `account_id`, and names its `plan_type` — one of `SYSTEMATIC_INVESTMENT`, `SYSTEMATIC_WITHDRAWAL` or `SYSTEMATIC_EXCHANGE` — its `source_share_class_id`, the class invested into, redeemed from or exchanged out of, and its `target_share_class_id`, the class exchanged into, which is required for a `SYSTEMATIC_EXCHANGE`, must be null for the other two kinds, and must differ from `source_share_class_id` or the creation is refused with `ERR_EXCHANGE_TARGET_INVALID`. The plan's `amount` is a dollar figure to two decimals greater than zero: the amount invested per run for a `SYSTEMATIC_INVESTMENT`, and the amount to liquidate per run for a `SYSTEMATIC_WITHDRAWAL` or a `SYSTEMATIC_EXCHANGE`. Its `frequency` is `MONTHLY` or `QUARTERLY`, and its `next_run_date` is the ISO `YYYY-MM-DD` date on which it may next be executed. Creation also requires `expected_account_version` under the version gate of §2.8, because a new plan of the same `plan_type` and `source_share_class_id` on that account terminates the account's prior `ACTIVE` plan of that shape, moving it to `TERMINATED`; a successful creation increments the owning account's `version`. The owning account must itself be `ACTIVE` or `RESTRICTED`, otherwise `ERR_ACCOUNT_NOT_ACTIVE`.

A plan is born `ACTIVE` with `executed_count` at 0, `last_run_date` null and `suspension_reason` null. A `TransferAgentOperator` or the `AccountHolder` may revise it by submitting a new `status`, a new `amount`, or both; a new `amount` is accepted whatever the plan's status, a `TERMINATED` plan included, and a request that submits neither field is still accepted and still increments the plan's `version`. Submitting `SUSPENDED` while the plan is `ACTIVE` moves it `ACTIVE → SUSPENDED` and stamps `suspension_reason` as `OPERATOR_REQUEST`. Submitting `ACTIVE` while the plan is `SUSPENDED` moves it `SUSPENDED → ACTIVE` and clears `suspension_reason` to null, but only if the owning account's `status` is itself `ACTIVE`, a `RESTRICTED` or otherwise non-`ACTIVE` owner answering `ERR_INVALID_PLAN_STATE`. Submitting `TERMINATED` moves the plan `ACTIVE → TERMINATED` or `SUSPENDED → TERMINATED` depending on where it stood, after which no further execution is possible. Any transition not declared here — resuming a plan that is already `ACTIVE`, reviving a `TERMINATED` one — answers `ERR_INVALID_PLAN_STATE`. Two other paths reach the same states without a client asking: restricting the owning account suspends its `ACTIVE` plans with `suspension_reason` `ACCOUNT_RESTRICTED`, and closing the account terminates every plan that was `ACTIVE` or `SUSPENDED`.

Execution is a `TransferAgentOperator` capability. The plan must be due — the logical clock date on or after its `next_run_date`, otherwise `ERR_PLAN_NOT_DUE` — the plan itself must be `ACTIVE`, and the owning account must be `ACTIVE` or `RESTRICTED`; a `RESTRICTED` account may run a `SYSTEMATIC_WITHDRAWAL` but running a `SYSTEMATIC_INVESTMENT` or a `SYSTEMATIC_EXCHANGE` from it is purchase-side activity and is refused with `ERR_ACCOUNT_RESTRICTED`. A successful run generates one order carrying `originating_plan_id` pointing back at the plan: a `PURCHASE` for a `SYSTEMATIC_INVESTMENT` whose `gross_amount` is the plan's `amount`, a `REDEMPTION` for a `SYSTEMATIC_WITHDRAWAL`, or an `EXCHANGE` for a `SYSTEMATIC_EXCHANGE`. For the two liquidating kinds the plan's dollar `amount` is converted into a `shares_requested` quantity at the source class's most recent priced NAV — the same price that produces a position's `market_value_amount` — rounded half-up to three decimals; if the source class has no priced NAV at all the run is refused with `ERR_NAV_NOT_AVAILABLE`. The generated order follows the ordinary capture path: it is created with an `execution_status` of `RECEIVED` and a `settlement_status` of `UNSETTLED`, its `trade_date` comes from the forward-pricing rule, and a generated purchase reserves state-registration capacity exactly as a hand-captured one would. The plan's `executed_count` increments, its `last_run_date` is stamped with the run date, and its `next_run_date` advances by one month for a `MONTHLY` plan or by three months for a `QUARTERLY` plan, with the day-of-month clamped to the last day of the target month when the target month is too short to hold it.

One branch of execution produces no order at all. When a `SYSTEMATIC_WITHDRAWAL` runs against a source position whose `market_value_amount` is below the plan's `amount`, there is not enough value to liquidate: no order is created, `executed_count` and `next_run_date` are both left exactly as they were, and the plan moves `ACTIVE → SUSPENDED` with `suspension_reason` set to `INSUFFICIENT_POSITION_VALUE`. The shareholder or an operator must then resume it deliberately. A `SYSTEMATIC_EXCHANGE` carries no such guard: it converts and captures regardless, and an oversized run simply fails the capture-time share-sufficiency check with `ERR_INSUFFICIENT_SHARES`. Plans may be read individually and listed with narrowing by `account_id`, `source_share_class_id`, `target_share_class_id`, `status` or `plan_type`.

### 3.9. Pricing Errors: Materiality, Correction and the Reprocessing Cascade

When fund accounting concludes that a published NAV was wrong, it opens a **PricingErrorCase**. Opening one is a `FundAccountant` action naming the `nav_record_id` of the mispriced record, the `corrected_nav_per_share` the accountant believes is right — four decimals, greater than zero — and a non-empty `error_reason` describing the cause, together with `expected_nav_record_version` under the version gate of §2.8. The targeted record must currently be `FINAL`; a case opened against a record in any other state answers `ERR_INVALID_NAV_STATE`. Opening captures the record's current `nav_per_share` into the case's `original_nav_per_share`, stamps `detected_by_user_id` from the caller's `X-User-ID`, creates the case in `DETECTED` with `error_bps` and `materiality` both null, `restated_trade_count` and `invalidated_nav_record_count` both 0, and `approved_by_user_id` and `reprocessed_by_user_id` null, and drives the NAV record `FINAL → UNDER_ERROR_REVIEW`, incrementing that record's `version`. While a record sits `UNDER_ERROR_REVIEW`, no order may be priced against it. Opening a case also supersedes any earlier case on the same record still sitting in `DETECTED` or `ASSESSED`, moving it `DETECTED → SUPERSEDED` or `ASSESSED → SUPERSEDED` respectively; a superseded case keeps whatever `materiality` and `error_bps` it had already reached, which are left exactly as they stood.

The second step is assessment, again a `FundAccountant` action, which moves the case `DETECTED → ASSESSED` and computes the size of the error. `error_bps` is the absolute difference between the corrected NAV and the original NAV, divided by the original NAV, multiplied by ten thousand to express it in basis points, and rounded half-up to two decimal places. `materiality` is then `MATERIAL` when `error_bps` is greater than or equal to fifty basis points — half of one percent — and `IMMATERIAL` when it is strictly below fifty. The comparison is inclusive at the boundary: an error of exactly `50.00` basis points is `MATERIAL`.

The determination forks the case into two branches, and a `ComplianceOfficer` owns both. Neither branch may be taken from a case that is not `ASSESSED`, and neither may be taken against the wrong determination; both mistakes answer `ERR_INVALID_CASE_STATE`.

The immaterial branch closes the case out. It requires `materiality` to be `IMMATERIAL`, moves the case `ASSESSED → IMMATERIAL_CLOSED`, and stamps `approved_by_user_id` from the officer's `X-User-ID`. On the pricing side it returns the NAV record `UNDER_ERROR_REVIEW → FINAL`: the record's `original_nav_per_share` is set to the `nav_per_share` that was in force, `nav_per_share` is replaced by the case's `corrected_nav_per_share` so that the price applies from here forward, and the record's `version` increments. Crucially, nothing is restated — no already-settled trade is touched, no position moves, no share balance changes. The correction is prospective only, which is precisely what makes it cheap enough to apply without a sweep.

The material branch merely authorizes the sweep. It requires `materiality` to be `MATERIAL`, moves the case `ASSESSED → MATERIAL_APPROVED`, and stamps `approved_by_user_id` from the officer's `X-User-ID`. Nothing else changes at this point: the NAV record stays `UNDER_ERROR_REVIEW`, no trade is touched, and the actual reprocessing is a separate, segregated step.

That step is the reprocessing sweep, run by a `FundAccountant` whose `X-User-ID` must differ from the case's `detected_by_user_id`, or the run is refused with `ERR_SEGREGATION_OF_DUTIES`. It is available only from `MATERIAL_APPROVED → REPROCESSED`, stamps `reprocessed_by_user_id`, and then executes a five-link cascade in which each link exists because the previous one changed something.

1. The NAV record moves `UNDER_ERROR_REVIEW → CORRECTED`. Its `original_nav_per_share` preserves the price that was in force and its `nav_per_share` is replaced by the case's `corrected_nav_per_share`; its `version` increments.
2. Because that price changed, every order with a `settlement_status` of `SETTLED` that was priced on that record — that is, whose `trade_date` equals the corrected record's `valuation_date` and whose `share_class_id` equals that record's `share_class_id` — moves `PRICED_FINAL → RESTATED`. Each such order has its `nav_per_share_applied` replaced by the corrected NAV, its `shares_transacted` recomputed at that corrected NAV under the same pricing rules that produced it originally — for a `PURCHASE` or a `REINVESTMENT` that is the order's existing `net_invested_amount` divided by the corrected NAV, while a `REDEMPTION` or an `EXCHANGE` keeps the negative of its `shares_requested` and so does not move at all — and its `restated_share_delta` written as the new `shares_transacted` minus the previous one. Nothing else on the order is rewritten: its load, proceeds and charge figures, and the position's `cost_basis_amount`, all stand as they were. The case's `restated_trade_count` records how many orders were restated, a zero-delta restatement included.
3. Because those share quantities changed, one ledger entry with an `entry_reason` of `NAV_CORRECTION_RESTATEMENT` is appended per restated order whose `restated_share_delta` is not `0.000`, each position's `shares` moves by that order's `restated_share_delta`, and the class's `total_shares_outstanding` moves by the total of those deltas.
4. Because the class's share balance changed underneath every later strike, every NAV record of that same class whose `valuation_date` is strictly later than the corrected record's `valuation_date` and whose `status` is `PRELIMINARY` moves `PRELIMINARY → STALE_REPRICE_REQUIRED`, with its `version` incremented. The case's `invalidated_nav_record_count` records how many records were invalidated. Each of them must be re-struck before it can be used again, as described in §3.3.
5. Because those NAV records were invalidated, every order priced against one of them whose `execution_status` is `PRICED_PROVISIONAL` falls back `PRICED_PROVISIONAL → RECEIVED`, and its pricing fields — `pricing_variant`, `nav_per_share_applied`, `sales_load_pct`, `sales_load_amount`, `net_invested_amount`, `shares_transacted`, `roa_qualifying_amount` and `roa_basis_variant` — are all cleared back to null, so the order must be priced again once its NAV record has been re-struck and finalized.

After the five links, each affected account's `household_basis_amount` is recomputed and every position of every affected household has its `current_roa_tier_pct` recomputed, because positions and share balances moved. `IMMATERIAL_CLOSED`, `REPROCESSED` and `SUPERSEDED` are all terminal case states. Cases may be read individually and listed with narrowing by `nav_record_id`, `status` or `materiality`; they are visible to a `TransferAgentOperator`, a `FundAccountant` and a `ComplianceOfficer` only.

### 3.10. Omnibus and Networked Reconciliation

Accounts held through a dealer are traded in bulk, and the dealer's own record of a day's activity must be reconciled against the transfer agent's. An **OmnibusReconciliation** is filed by a `TransferAgentOperator` or by `DealerOperations` against an `account_id` whose `account_channel` is `NETWORKED` or `OMNIBUS`; filing one against a `DIRECT` account is refused with `ERR_RECON_CHANNEL_INVALID`. The filing names the `as_of_date` the dealer file covers and three claimed figures: `dealer_reported_purchase_amount` and `dealer_reported_redemption_amount`, each in dollars to two decimals and never negative, and `dealer_reported_net_shares`, the net share movement the dealer claims, to three decimals.

The system then computes its own side of the comparison from settled activity dated exactly on the `as_of_date`. `ta_purchase_amount` is the sum of `gross_amount` over that account's orders whose `trade_type` is `PURCHASE`, whose `settlement_status` is `SETTLED`, and whose `trade_date` equals the `as_of_date`. `ta_redemption_amount` is the sum of `gross_proceeds_amount` over that account's orders whose `trade_type` is `REDEMPTION` under the same settlement and date filters. Orders still `UNSETTLED`, or `CANCELLED`, or `REVERSED` are excluded, and `REINVESTMENT` and `EXCHANGE` orders are excluded from both dollar sums entirely. `ta_net_shares` is the sum of `share_delta` over every ledger entry whose `effective_date` equals the `as_of_date` and whose position belongs to that account, and it is reported alongside the dealer's own `dealer_reported_net_shares` for comparison.

The break is a dollar difference of nets. The transfer agent's net is `ta_purchase_amount` minus `ta_redemption_amount`; the dealer's net is `dealer_reported_purchase_amount` minus `dealer_reported_redemption_amount`; and `break_amount` is the agent's net minus the dealer's net, rounded half-up to two decimals, so its sign says which side is claiming more. The `tolerance_amount` applied to it is the greater of a floor of one dollar and one basis point of the dealer's gross activity — that is, `dealer_reported_purchase_amount` plus `dealer_reported_redemption_amount`, multiplied by `0.0001` and rounded half-up to two decimals. The reconciliation is created directly in one of two states: `MATCHED` when the absolute value of `break_amount` is less than or equal to `tolerance_amount`, and `BREAK_IDENTIFIED` when it is strictly greater. The comparison is inclusive, so a break exactly equal to the tolerance is `MATCHED`.

A `MATCHED` reconciliation is finished on arrival. A `BREAK_IDENTIFIED` one must be dispositioned by a `ComplianceOfficer`, in one of two ways, and both require the reconciliation to be `BREAK_IDENTIFIED` — any other state answers `ERR_INVALID_RECONCILIATION_STATE`. Adjusting the break away moves it `BREAK_IDENTIFIED → RESOLVED` by citing the settled backdated order that corrected the books: the request supplies `adjustment_trade_id` and a `resolution_note`, both of which are stamped onto the reconciliation. The cited order must exist, must belong to the same account, must carry a `trade_date` equal to the reconciliation's `as_of_date`, must have a `settlement_status` of `SETTLED`, and its booked dollar magnitude — `gross_amount` for a `PURCHASE`, `gross_proceeds_amount` for a `REDEMPTION` or an `EXCHANGE`, and `net_invested_amount` for a `REINVESTMENT` — must equal the absolute value of `break_amount`; any of those failing is refused with `ERR_ADJUSTMENT_MISMATCH`. Referring the break back to the dealer instead moves it `BREAK_IDENTIFIED → DISPUTED`, stamping the supplied `dispute_note`. `RESOLVED` and `DISPUTED` are both terminal. Reconciliations may be read individually and listed with narrowing by `account_id`, `adjustment_trade_id`, `status` or `as_of_date`.

## 4. Endpoint Definitions

Operations that bring a new resource into existence — registering a fund or a share class, opening an account, filing a state registration, striking a NAV, capturing an order, declaring a distribution, creating a systematic plan, opening a pricing error case, or filing a reconciliation — return `201 Created`. Every other operation, including all action endpoints that drive a state transition, all updates, all reads, and the logical clock capability, returns `200 OK`. The `data` field of a successful response carries the affected resource, and for the action endpoints that is the resource named in the path rather than any secondary resource the cascade touched.
