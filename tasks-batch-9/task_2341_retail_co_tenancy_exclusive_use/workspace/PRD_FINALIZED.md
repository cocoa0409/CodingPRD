# Retail Co-Tenancy & Exclusive Use Administration API — Product Requirements Document

## 1. Introduction

Shopping-center leasing lives or dies on promises the landlord made to tenants years before the current asset manager arrived. A grocery anchor agreed to open only if 70% of the gross leasable area would be occupied on day one. A bookstore paid a premium for the exclusive right to be the only bookseller in the center. A national juice chain accepted a five-mile radius restriction. Each of those promises is a contingent liability that becomes payable the moment occupancy slips, an anchor goes dark, or a new lease is signed with a use code somebody forgot to screen. Today those provisions sit in lease abstracts and spreadsheets, and the landlord typically discovers a co-tenancy breach when the tenant's counsel sends a rent-abatement letter.

This API is the system of record for those provisions and for the remedies they trigger. It abstracts co-tenancy conditions with their opening and ongoing occupancy thresholds, tracks named-anchor requirements and substitution rights, maintains an inventory of exclusive-use clauses that screens every new lease before execution, enforces radius restrictions with a recapture assessment, runs the use-violation notice and cure workflow including tenant disputes, remeasures occupancy whenever a tenant goes dark or falls into default, prices and books rent abatements, and discloses all of it to lenders through tenant estoppel certificates.

Two design tensions drive most of the complexity below, and implementers should internalize them before reading further. First, **the same co-tenancy condition is judged by two different engines over the same lease population**: a strict live evaluation that fires on every lease and tenant status change, and a certified-measurement evaluation whose counting variant may legitimately cure a condition the live engine had breached. Both are correct; whichever fires last owns the stored status. Second, **rent abatement is deliberately rounded in two different orders in two different fields**, because a per-election audit ledger and an aggregate rent roll answer different questions. Neither order is a bug, and neither may be "unified" for convenience. Every temporal rule in this system reads a server-controlled logical clock rather than wall time, so that these interactions can be tested deterministically.

## 2. Global Specifications & System-Wide Principles

This section defines the structural contract of the API: authentication, response shape, pagination, record identity, the shared measurement and posture machinery, precision rules, concurrency control, and the order in which validations are evaluated. Everything here applies system-wide unless a workflow in §3 explicitly narrows it.

### 2.1. Operator Identity, Roles and Segregation of Duties

Every request carries two mandatory headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, declaring the capacity in which that operator acts. The system recognizes exactly five roles: `LeaseAdministrator`, `ComplianceOfficer`, `AssetManager`, `TenantRep`, and `LenderRep`. A request whose `X-User-Role` header is absent, blank, or carries a string that is not one of those five names is rejected with `ERR_UNAUTHENTICATED` (401). A request whose role is well-formed but is not listed among the authorized roles of the addressed endpoint in §4 is rejected with `ERR_UNAUTHORIZED` (403). The single exception to the authentication requirement is the logical-clock capability described in §2.4, which is a test-driving facility and does not require a role header; authorization, however, still applies to it, so a clock request that does supply a role outside its authorized list is refused with `ERR_UNAUTHORIZED`.

Four of the five roles use an **opaque** identity. When `X-User-Role` is `LeaseAdministrator`, `ComplianceOfficer`, `AssetManager`, or `LenderRep`, the `X-User-ID` value is an opaque operator identifier that is not tied to any persisted entity. The server records it where a workflow demands an audit subject — as `issued_by_user_id` on a use-violation notice, `adjudicated_by_user_id` on a dispute, `created_by_user_id` and `certified_by_user_id` on an occupancy measurement, `approved_by_user_id` on a remedy election, and `requested_by_user_id` on an estoppel certificate — but it never compares that value to any entity's `id`.

`TenantRep` is different: it is **entity-backed by the Tenant record**. When `X-User-Role` is `TenantRep`, `X-User-ID` is the `id` of the acting `Tenant`, and ownership checks on any resource that references a tenant compare that resource's `tenant_id` — reached through the addressed lease where the resource is a notice, dispute, election, or certificate — to `X-User-ID`. A `TenantRep` acting outside its own tenant's leases is refused with `ERR_TENANT_SCOPE_FORBIDDEN` (403). When a tenant files a dispute, the server stamps `filed_by_tenant_id` from `X-User-ID` rather than accepting it from the body.

Because `X-User-ID` is an audit subject and not merely a log line, two **segregation-of-duties** rules bind the `ComplianceOfficer` role. The officer who issued a use-violation notice may not adjudicate a dispute against that notice, and the officer who prepared an occupancy measurement may not certify it. Both violations answer `ERR_SEGREGATION_OF_DUTIES` (409); neither can be waived by any other role.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection endpoints paginate through two query parameters. `limit` caps the number of records returned; it defaults to 10, accepts a minimum of 1 and a maximum of 100. `offset` skips a number of leading records and defaults to 0. Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending.

List responses carry `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope, where `total_count` is the number of records matching the filters before pagination is applied and `has_more` indicates whether records remain beyond the current page.

### 2.4. Record Identity, Audit Stamps and the Logical Clock

Every persisted record exposes an `id`, which is a server-minted UUID with no type prefix, and a `created_at` timestamp rendered as an ISO 8601 UTC instant with three fractional digits. Almost every record additionally exposes `updated_at`, refreshed on every mutation and formatted identically, and `version`, an integer that starts at 1 on creation and increments by one on every mutation of that record — including mutations that only touch derived fields such as a center's occupancy percentages or a lease's effective rent. The one exception is the `AnchorRequirement` record, which is immutable after creation: it carries only `id` and `created_at`, and both `updated_at` and `version` are absent from it. There is no update endpoint for an anchor requirement.

All temporal rules in this system — cure deadlines, grace and cure periods, abatement windows, measurement windows, radius enforcement windows, dark-premises grace, and breach duration — read a **logical clock** rather than wall-clock time. A fresh instance starts its clock at `2026-08-01T00:00:00Z`. An operator may reposition the clock by submitting `to_iso8601`, and the response reports the new instant as `current_utc`. Repositioning the clock re-runs the abatement ledger and the effective-rent recomputation for every lease that has an active reduction, and re-derives estoppel-certificate staleness — but it never escalates a notice and never changes a co-tenancy condition's status. Advancing compliance state is the sweep's job, described in §3.7.

Whole-day arithmetic in this system is a floor difference over UTC calendar dates: the number of days between two instants is the number of whole calendar days from the earlier date to the later date, and a partial day contributes nothing.

### 2.5. The Center Denominator and the Two Counting Engines

Occupancy is always a ratio whose denominator is the center's `total_gla_sqft` and whose numerator is the sum of `gla_sqft` over the leases that a given engine counts as open. Whether a lease counts open is decided by a single inclusion predicate that takes a counting variant and an instant, and every occupancy figure anywhere in the system is produced by that one predicate.

Under the **`SNAPSHOT_STRICT`** variant, a lease counts open only when its `premises_status` is `OPEN` **and** its tenant's `status` is `ACTIVE`. Dark premises and defaulted tenants drop out immediately. Under the **`TRAILING_GRACE`** variant, a lease whose tenant's `status` is `BANKRUPT` never counts; a lease whose `premises_status` is `OPEN` always counts, whether its tenant is `ACTIVE` or `DEFAULTED`; and a lease whose `premises_status` is `DARK` with a non-null `dark_since` still counts provided the number of whole days from `dark_since` to the measurement instant is strictly less than the center's `occupancy_grace_days`. Anything else does not count. The grace window is consulted by the `TRAILING_GRACE` variant alone.

The **assessed population** for any occupancy figure is the set of leases of the center whose `premises_status` is `EXECUTED`, `OPEN`, or `DARK`. Leases in `DRAFT` and `TERMINATED` sit outside the population entirely and are never counted in either the numerator or in `excluded_lease_count`. From that population an engine derives: the counted gross leasable area as the sum of `gla_sqft` over counted leases; a GLA occupancy percentage equal to the counted area divided by the total area, multiplied by 100, and rounded half up to two decimal places; a non-anchor open-store count as the number of counted leases whose `is_anchor` is false; an anchor count as the number of counted leases whose `is_anchor` is true; a total counted-lease count; and an excluded count equal to the population size minus the counted size. Counts are exact integers.

Two engines drive that machinery. The **live strict engine** recomputes the center's own derived fields — `occupied_gla_sqft`, `open_occupancy_pct`, `operating_store_count`, `open_anchor_count`, `aggregate_effective_rent_cents`, `protected_exclusive_count`, and `open_violation_count` — always under the `SNAPSHOT_STRICT` variant and always at the current logical clock. It fires when a lease's `premises_status` changes, when a tenant's credit `status` changes, and when a redevelopment plan is recorded or abandoned. The **certified-measurement engine** runs when a prepared `OccupancyMeasurement` is certified, and it uses that measurement's own `variant`, its frozen `total_gla_sqft`, its `occupied_gla_sqft`, its `gla_occupancy_pct`, its `open_store_count`, its `open_anchor_count`, and its `measured_at` instant.

That is the density at the heart of this domain: the two engines see the same leases and can legitimately disagree. A `TRAILING_GRACE` certification can cure a condition the live engine had marked breached, and superseding that certification can re-breach it on the spot.

### 2.6. Compliance Posture and the Frozen Center Gate

Each center carries a derived `compliance_posture` drawn from `COMPLIANT`, `WATCH`, `BREACH`, and `FROZEN`. It is recomputed at the end of every mutation that changes a lease's `premises_status` or `remedy_status`, a co-tenancy condition's `status`, a use-violation notice's `status`, an exclusive-use clause's `status`, or the center's `total_gla_sqft`.

The derivation counts the center's **breached conditions**: co-tenancy conditions whose benefited lease belongs to this center, whose benefited lease is not `TERMINATED`, and whose `status` is `BREACHED`. It also determines whether the center is **assessable**, meaning at least one lease of the center sits in `OPEN` or `DARK`. Assessability is deliberately narrower than the assessed population of §2.5: an `EXECUTED` lease contributes nothing to the numerator, so a lease that has not yet opened does not make the center assessable either. The rungs are then evaluated top to bottom and the first match wins:

1. The posture is `FROZEN` when the breached-condition count is at least two, or when the center is assessable and its `open_occupancy_pct` is strictly below 50.00.
2. Otherwise the posture is `BREACH` when the breached-condition count is at least one.
3. Otherwise the posture is `WATCH` when `open_violation_count` is at least one, or when the center is assessable and its `open_occupancy_pct` is strictly below 70.00.
4. Otherwise the posture is `COMPLIANT`.

Both occupancy rungs are gated on assessability, so a center whose `open_occupancy_pct` is 0.00 and which holds no `OPEN` or `DARK` lease — a newly registered center, or one whose leases have only been drafted or executed — cannot reach `FROZEN` or `WATCH` on the occupancy rungs; absent breached conditions and open violations it is `COMPLIANT`. Comparisons use the stored two-decimal percentage without re-rounding, and both occupancy tests are strictly-less-than: exactly 50.00 is not `FROZEN`, and exactly 70.00 is not `WATCH`.

A `FROZEN` posture is a hard gate on new commitments. While a center is `FROZEN` it accepts no lease execution, no new exclusive-use clause, no new radius restriction, and no redevelopment recording; all four are refused with `ERR_CENTER_EXECUTION_FROZEN` (409), and those four are the whole of the gate — the same list §2.9 rung 9 names. Opening a store is *not* gated by posture: `POST /leases/{id}/open` is accepted while the center is `FROZEN`, because a store that has already been executed is not a new commitment and opening it is one of the ways the center works its way back out. Nothing else is gated by posture either — notices, disputes, measurements, elections, sweeps, estoppel certificates, terminations, and waivers all remain available, which is deliberate: a frozen center must still be able to work its way out.

### 2.7. Percentages, Whole Cents and the Two Pinned Rounding Orders

Money in this system is always an integer number of whole cents, and every field whose name ends in `_cents` is a non-negative integer. Percentages are numbers constrained to the closed range from 0 through 100 and are carried at two decimal places, rounded half up. Every rounding operation in this document is **round half up**, and every threshold comparison is stated explicitly as inclusive or exclusive — none may be relaxed.

Two rent fields are computed from the same set of approved reductions in **deliberately opposite orders**, and both orders are pinned:

- `Lease.effective_rent_monthly_cents` is **sum-then-round**. Take the reductions that are currently active and currently in window, add their `reduction_pct` values together into a single total percentage, subtract that total from 100, multiply the lease's `base_rent_monthly_cents` by the result, divide by 100, and round to whole cents exactly once at the end. Never round per election here.
- `Lease.total_abated_cents` is **round-then-sum**. Compute each qualifying election's accrual, round that accrual to whole cents first, and only then add the rounded per-election amounts together.

Those two orders yield different answers whenever the fractional parts of two or more accruals sum to at least one cent, and that divergence is expected. Any implementation that "harmonizes" the two fields onto one rounding policy is wrong. Each field's full formula appears with the workflow that produces it in §3.5.

### 2.8. Version Pinning and Stale-View Rejection

Two write operations mutate more than the resource they name, and both therefore require the client to prove it was looking at the current parent when it composed the request.

A `POST /centers/{id}/occupancy-measurements` request must carry `expected_center_version` as a non-optional body field, holding the `version` of the `ShoppingCenter` the client last observed. If that value does not equal the center's current `version`, the request is rejected with `ERR_STALE_CENTER_VERSION` (412). The protection matters because creating a measurement is itself a supersede operation — it drives every other draft measurement of the center to `SUPERSEDED` — so a writer holding a stale view of the center would silently discard a measurement prepared from figures it never saw.

A `POST /leases/{id}/remedy-elections` request must carry `expected_lease_version` as a non-optional body field, holding the `version` of the `Lease` the client last observed. If that value does not equal the lease's current `version`, the request is rejected with `ERR_STALE_LEASE_VERSION` (412). Creating an election legitimately supersedes any prior unapproved election on the same lease by driving it to `RESCINDED`, so a stale-view writer would discard an election that had been priced against different occupancy figures.

No other endpoint accepts a version field. Endpoints outside these two do not take `expected_center_version`, do not take `expected_lease_version`, and perform no version check of their own.

Version pinning appears a second time, with different mechanics, on estoppel certificates: a certificate records `pinned_lease_version` at request time and is driven to `STALE` by any later lease mutation. That is a state transition rather than a request-rejection rule, and it is specified in §3.8.

### 2.9. Path Resolution and the Validation Precedence Ladder

When a path contains an identifier, the server resolves it before applying any business rule, and where a path contains more than one identifier they are resolved strictly left to right, answering for the first one that fails to resolve. Resolution failures are 404s and are named per entity: `ERR_CENTER_NOT_FOUND`, `ERR_TENANT_NOT_FOUND`, `ERR_LEASE_NOT_FOUND`, `ERR_CONDITION_NOT_FOUND`, `ERR_REQUIREMENT_NOT_FOUND`, `ERR_CLAUSE_NOT_FOUND`, `ERR_RESTRICTION_NOT_FOUND`, `ERR_NOTICE_NOT_FOUND`, `ERR_DISPUTE_NOT_FOUND`, `ERR_ELECTION_NOT_FOUND`, `ERR_MEASUREMENT_NOT_FOUND`, `ERR_CERTIFICATE_NOT_FOUND`, and `ERR_PLAN_NOT_FOUND`. The same catalogue serves foreign keys supplied in a request body.

Because many operations are guarded by several rules at once, the order of evaluation is fixed. Validations are evaluated in ascending priority and **the first violation found is the one reported**; later checks are not consulted:

1. Authentication — `X-User-Role` present and naming one of the five roles. `ERR_UNAUTHENTICATED`, 401. Applies to every endpoint except `POST /_clock/set_current_utc`.
2. Authorization — the caller's role appears in the endpoint's role list. `ERR_UNAUTHORIZED`, 403. All endpoints.
3. Schema — every required body field present with its declared type, every enum field carrying a declared member, every percentage between 0 and 100 inclusive, every `_cents` field a non-negative integer, and every date a well-formed ISO 8601 calendar date. `ERR_INVALID_REQUEST`, 400. All write endpoints.
4. Path existence — every path identifier resolves. The per-entity 404 above. All endpoints with path parameters.
5. Body foreign-key existence — every foreign key supplied in a body resolves, covering `tenant_id`, `condition_id`, `source_notice_id`, `clause_id`, `radius_restriction_id`, `measurement_id`, `anchor_lease_id`, `replacement_for_lease_id`, and `pad_parcel_lease_id`. The per-entity 404 above. All write endpoints carrying foreign keys.
6. Tenant scope — a `TenantRep` may only address leases, notices, disputes, elections, and certificates whose lease belongs to the tenant whose `id` equals the caller's `X-User-ID`. `ERR_TENANT_SCOPE_FORBIDDEN`, 403. Applies to exactly seven operations: `POST /leases/{id}/go-dark`, `POST /leases/{id}/reopen`, `POST /leases/{id}/open`, `POST /use-violation-notices/{id}/disputes`, `POST /leases/{id}/remedy-elections`, `POST /remedy-elections/{id}/rescind`, and `POST /estoppel-certificates/{id}/sign`.
7. Center scope — every entity referenced by one request must sit inside the same shopping center: a condition's `anchor_lease_id`, an election's `condition_id`, a notice's `clause_id` and `violating_lease_id`, a certificate's `measurement_id`, and a plan's `pad_parcel_lease_id`. `ERR_CENTER_SCOPE_MISMATCH`, 409. Applies to five operations: `POST /co-tenancy-conditions/{id}/anchor-requirements`, `POST /use-violation-notices`, `POST /leases/{id}/remedy-elections`, `POST /leases/{id}/estoppel-certificates`, and `POST /centers/{id}/redevelopment-plans`.
8. Concurrency — the declared version field matches the parent's current `version`. `ERR_STALE_CENTER_VERSION` or `ERR_STALE_LEASE_VERSION`, 412. Applies to `POST /centers/{id}/occupancy-measurements` and `POST /leases/{id}/remedy-elections`.
9. Frozen posture — a `FROZEN` center accepts no lease execution, no new exclusive-use clause, no new radius restriction, and no redevelopment recording. `ERR_CENTER_EXECUTION_FROZEN`, 409. Applies to `POST /leases/{id}/execute`, `POST /leases/{id}/exclusive-use-clauses`, `POST /leases/{id}/radius-restrictions`, and `POST /redevelopment-plans/{id}/record`.
10. Declared transition — the addressed entity sits in a state from which the requested transition exists. `ERR_LEASE_STATE_INVALID`, `ERR_CONDITION_STATE_INVALID`, `ERR_NOTICE_STATE_INVALID`, `ERR_DISPUTE_STATE_INVALID`, `ERR_ELECTION_STATE_INVALID`, `ERR_MEASUREMENT_STATE_INVALID`, `ERR_CERTIFICATE_STATE_INVALID`, or `ERR_PLAN_STATE_INVALID`, all 409. All transition endpoints. **Exception:** a notice whose `status` is `DISPUTED` is not reported by this rung for cure, escalate, or withdraw; that from-state carries the more specific error at rung 15.
11. Remedy eligibility — an election may be created only while the benefited lease's `remedy_status` is `ELIGIBLE` or `REMEDY_ACTIVE`. `ERR_REMEDY_NOT_ELIGIBLE`, 409. Applies to `POST /leases/{id}/remedy-elections`.
12. Segregation of duties on adjudication — `X-User-ID` differs from the notice's `issued_by_user_id`. `ERR_SEGREGATION_OF_DUTIES`, 409. Applies to `POST /use-violation-disputes/{id}/adjudicate`.
13. Segregation of duties on certification — `X-User-ID` differs from the measurement's `created_by_user_id`. `ERR_SEGREGATION_OF_DUTIES`, 409. Applies to `POST /occupancy-measurements/{id}/certify`.
14. Exclusive-use screening — a lease may not be executed while screening returns a conflicting decision for its `primary_use_code`. `ERR_EXCLUSIVE_USE_CONFLICT`, 422. Applies to `POST /leases/{id}/execute`.
15. Pending dispute — a notice whose `status` is `DISPUTED` may not be cured, escalated, or withdrawn until its pending dispute is adjudicated. This rung supplies the specific error for that from-state in place of rung 10's generic notice-state error. `ERR_DISPUTE_PENDING`, 409. Applies to `POST /use-violation-notices/{id}/cure`, `POST /use-violation-notices/{id}/escalate`, `POST /use-violation-notices/{id}/withdraw`, and to `POST /centers/{id}/compliance-sweep`, where the sweep's escalation step **skips** disputed notices instead of failing.
16. Permitted election kind — the requested `election_kind` must be permitted by the condition's `remedy_type`. `ERR_REMEDY_KIND_NOT_PERMITTED`, 422. Applies to `POST /leases/{id}/remedy-elections`.
17. Cure period expiry on escalation — a notice may be escalated only after its `cure_deadline_at` has passed on the logical clock. `ERR_CURE_PERIOD_NOT_EXPIRED`, 409. Applies to `POST /use-violation-notices/{id}/escalate`, including when it is invoked through the sweep.
18. Radius window overlap — radius windows for one lease are closed-closed and may not share even a single day. `ERR_RADIUS_WINDOW_OVERLAP`, 409. Applies to `POST /leases/{id}/radius-restrictions`.
19. Measurement window overlap — measurement windows for one center are half-open, so a new window may start exactly on an existing window's through-date, but any interior overlap is rejected. `ERR_MEASUREMENT_WINDOW_OVERLAP`, 409. Applies to `POST /centers/{id}/occupancy-measurements`.
20. Abatement window validity — `window_from_date` must be strictly before `window_through_date`, and `window_from_date` must not precede the date of the condition's `breach_detected_at`. `ERR_ABATEMENT_WINDOW_INVALID`, 422. Applies to `POST /leases/{id}/remedy-elections` and `POST /remedy-elections/{id}/approve`.
21. Abatement stacking cap — the summed `reduction_pct` across the lease's active reductions whose half-open windows overlap the approved election's window may not exceed 100.00. `ERR_ABATEMENT_STACK_EXCEEDED`, 422. Applies to `POST /remedy-elections/{id}/approve`.
22. Lender conditions — a lender may accept a certificate only while `lender_conditions_met` is true. `ERR_LENDER_CONDITIONS_NOT_MET`, 422. Applies to `POST /estoppel-certificates/{id}/accept`.
23. Protected-rights consent — a plan whose `consent_required` is true may only be recorded with `consent_confirmed` true in the body. `ERR_PROTECTED_RIGHTS_CONSENT_REQUIRED`, 409. Applies to `POST /redevelopment-plans/{id}/record`.
24. Measurement basis coherence — a `GLA_PCT` condition requires `required_occupancy_pct` and forbids `required_open_store_count`; a `STORE_COUNT` condition requires `required_open_store_count` with a value of at least 1 and forbids `required_occupancy_pct`. `ERR_MEASUREMENT_BASIS_MISMATCH`, 422. Applies to `POST /leases/{id}/co-tenancy-conditions`.
25. Suite uniqueness — a center may not hold two leases with the same `suite_code` unless the other one is `TERMINATED`. `ERR_SUITE_ALREADY_LEASED`, 409. Applies to `POST /centers/{id}/leases` and `POST /leases/{id}/execute`.
26. Clause enforceability — a notice may only cite an exclusive-use clause whose `status` is `ACTIVE`; a clause suspended by a recorded redevelopment plan cannot be enforced. `ERR_CLAUSE_NOT_ACTIVE`, 422. Applies to `POST /use-violation-notices`.
27. Radius window active — a radius violation may only be reported against a restriction whose `status` is `ACTIVE` and whose closed enforcement window contains the current logical clock date. `ERR_RADIUS_WINDOW_INACTIVE`, 409. Applies to `POST /radius-restrictions/{id}/violation-report`.
28. Condition kind coherence — an `OPENING` condition may not be added to a lease that is already `OPEN`, and an `ONGOING` condition may not be added to a `DRAFT` lease. `ERR_CONDITION_KIND_INVALID`, 422. Applies to `POST /leases/{id}/co-tenancy-conditions`.
29. Cure period expiry on termination approval — a terminating election may not schedule a `termination_effective_date` earlier than the condition's `cure_period_days` measured from `breach_detected_at`. `ERR_CURE_PERIOD_NOT_EXPIRED`, 409. Applies to `POST /remedy-elections/{id}/approve`.

Three collisions between these rungs are called out explicitly because the naive reading picks the wrong error:

- **Executing into a frozen center whose use also collides.** When a lease execution targets a `FROZEN` center *and* the candidate use conflicts with an active exclusive-use clause, the answer is `ERR_CENTER_EXECUTION_FROZEN` (409), never `ERR_EXCLUSIVE_USE_CONFLICT` (422). Rung 9 outranks rung 14.
- **Approving an out-of-window election that also overstacks.** When an approval's window predates `breach_detected_at` *and* the aggregate reduction would exceed 100%, the answer is `ERR_ABATEMENT_WINDOW_INVALID` (422), never `ERR_ABATEMENT_STACK_EXCEEDED` (422). Rung 20 outranks rung 21.
- **Electing an impermissible kind on an ineligible lease.** When an election's kind is not permitted by the condition *and* the lease is not yet eligible, the answer is `ERR_REMEDY_NOT_ELIGIBLE` (409), never `ERR_REMEDY_KIND_NOT_PERMITTED` (422). Rung 11 outranks rung 16.

### 2.10. Cascade Discipline, Conserved Quantities and Compensating Actions

Almost no operation in this system touches a single record. A tenant going dark moves the lease, then the center's occupancy figures, then every ongoing condition of that center, then the benefited lease of each newly breached condition, then every estoppel certificate pinned to that benefited lease — five hops, each caused strictly by the one before it, all inside one request. Every record touched along the way has its `updated_at` refreshed and its `version` incremented; the center's `version` is incremented by every operation that changes any center-derived figure or posture. Where §3 numbers the hops of a cascade, the numbering is normative: the whole chain completes within the request, and a partially applied chain is not an acceptable outcome.

Three quantities are **conserved across compensating pairs**, meaning the reversing operation must restore them to exactly their prior value with no drift:

- **Occupied area.** Going dark and reopening are a compensating pair. Reopening restores `occupied_gla_sqft`, `open_occupancy_pct`, `operating_store_count`, and `open_anchor_count` to exactly their pre-dark values.
- **Aggregate rent.** Approving a reduction and rescinding it are a compensating pair. Rescinding returns `aggregate_effective_rent_cents` to exactly its pre-approval value.
- **Protected rights.** Recording a redevelopment plan and abandoning it are a compensating pair. Abandoning restores `protected_exclusive_count` to exactly its pre-record cardinality and `total_gla_sqft` to exactly its pre-record value.

Withdrawing an escalated notice and superseding a certified measurement are compensating actions of the same kind: each reverses its counterpart's full cascade, and superseding in particular releases every condition the measurement controlled back to the live strict engine — which may immediately re-breach a condition the certified figures had cured.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Center, the Tenant and the Lease Abstract

An `AssetManager` registers a shopping center by supplying its legal `name` and its `total_gla_sqft`, optionally overriding `occupancy_grace_days`, which defaults to 90 days when omitted. The total area must be greater than zero, and the grace window must be at least zero days. A newly registered center starts with `occupied_gla_sqft` at 0, `open_occupancy_pct` at 0.00, `operating_store_count`, `open_anchor_count`, `protected_exclusive_count`, and `open_violation_count` all at 0, `aggregate_effective_rent_cents` at 0, `compliance_posture` at `COMPLIANT`, `redevelopment_status` at `NONE`, `last_sweep_at` at null, and `version` at 1. The `redevelopment_status` field tracks `NONE`, `PLANNED`, and `RECORDED` and is explained in §3.9; `last_sweep_at` records the logical instant of the center's most recent compliance sweep and stays null until the first one runs.

Tenants are registered separately by a `LeaseAdministrator` with a `legal_name`, a `notice_email` that becomes the address of record for use-violation notices, and a `primary_use_code` naming the tenant's principal merchandising category in uppercase — `GROCERY`, `BOOKS`, and `JUICE_BAR` are typical. The abstracting flag `is_national_chain` defaults to false and marks the tenants who most often hold radius restrictions. A tenant's credit `status` starts at `ACTIVE` and may later be moved to `DEFAULTED` or `BANKRUPT`; the counting consequences of each are in §2.5, and the consequences of moving it are in §3.3.

A lease abstract is drafted against a center by a `LeaseAdministrator`, who supplies the `tenant_id`, the `suite_code`, the demised `gla_sqft` (which must be greater than zero), the `parcel_kind` drawn from `INLINE`, `ANCHOR_BOX`, and `PAD`, the `primary_use_code` that will be screened against the center's exclusive-use inventory, the `base_rent_monthly_cents` (which must be greater than zero), and the term boundaries `commencement_date` and `expiration_date` as ISO calendar dates. Two optional fields describe incidental merchandising: `incidental_use_codes`, an array of uppercase codes the tenant conducts only incidentally, which defaults to an empty array; and `projected_incidental_sales_pct`, the projected share of gross sales attributable to those incidental codes, which defaults to 0 and must lie between 0 and 100 inclusive. During a redevelopment a new lease may point back at the lease it displaces through `replacement_for_lease_id`, which is null for original leases and makes the lease graph self-referential.

`is_anchor` is not an input. It is derived as true exactly when `parcel_kind` is `ANCHOR_BOX`, and any value a client supplies for it is discarded. A drafted lease starts with `premises_status` at `DRAFT`, `remedy_status` at `NONE`, `use_compliance_status` at `CLEAR`, `effective_rent_monthly_cents` equal to `base_rent_monthly_cents`, `total_abated_cents` at 0, and `opened_at`, `dark_since`, and `remedy_eligible_at` all null. A `DRAFT` lease sits outside the occupancy population and moves no center field whatsoever. Two leases of the same center may not share a `suite_code` unless one of them is `TERMINATED`; the collision answers `ERR_SUITE_ALREADY_LEASED`, and it is checked both when the lease is drafted and again when it is executed, because a competing lease may have been executed in between.

The lease carries two **parallel status dimensions** that evolve independently. `premises_status` runs `DRAFT`, `EXECUTED`, `OPEN`, `DARK`, and the terminal `TERMINATED`, and describes the physical premises. `remedy_status` runs `NONE`, `ELIGIBLE`, `REMEDY_ACTIVE`, `TERMINATION_PENDING`, and the terminal `TERMINATED_BY_REMEDY`, and describes the tenant's co-tenancy remedy posture. A single lease can perfectly legitimately be `DARK` on the premises dimension while sitting at `REMEDY_ACTIVE` on the remedy dimension. A third derived field, `use_compliance_status`, tracks enforcement rather than either dimension: it reads `CLEAR` when no notice against the lease is `ISSUED`, `DISPUTED`, or `ESCALATED`; `UNDER_NOTICE` when at least one is `ISSUED` or `DISPUTED`; and `IN_VIOLATION` when at least one is `ESCALATED`.

### 3.2. Exclusive-Use Inventory and the Prohibited-Use Screen

A `LeaseAdministrator` records an exclusive-use clause benefiting a lease by supplying `protected_use_codes` — a non-empty array of uppercase codes no other lease of the center may conduct within the clause's scope — an `exclusivity_scope`, and the closed effective window `effective_from_date` through `effective_through_date`, where the through-date must be strictly after the from-date. Two carve-out parameters may be supplied: `gla_carve_out_sqft`, defaulting to 0, and `incidental_sales_pct_cap`, also defaulting to 0. The scope is one of three values with materially different reach: `CENTER_WIDE` binds every parcel of the center; `PAD_EXCLUDED` binds every parcel except those whose `parcel_kind` is `PAD`; and `RADIUS_INCLUSIVE` binds every parcel and additionally survives a pad sale. A new clause is created `ACTIVE` with `suspended_by_plan_id` null, increments the center's `protected_exclusive_count`, and is refused while the center is `FROZEN`. Recording a clause never retroactively invalidates an already-executed conflicting lease, because screening runs only at execution time.

The **prohibited-use screen** is the heart of this subsection, and it can be run as a read-only decision by a `LeaseAdministrator` or a `ComplianceOfficer` before anyone commits, as well as being applied as a hard gate inside lease execution. The screen begins by building the **eligible pool** at the current logical clock date: every exclusive-use clause of the same center that benefits a lease other than the candidate, whose `status` is `ACTIVE`, whose benefited lease sits in `EXECUTED`, `OPEN`, or `DARK`, whose closed effective window contains the screening date (the from-date on or before it and the through-date on or after it), whose `protected_use_codes` array contains the candidate's `primary_use_code`, and whose scope binds the candidate. Scope binds unconditionally for `CENTER_WIDE` and `RADIUS_INCLUSIVE`; for `PAD_EXCLUDED` it binds only when the candidate's `parcel_kind` is something other than `PAD`. Clauses that are `SUSPENDED`, `EXPIRED`, or `WAIVED` never conflict, and clauses benefiting a `DRAFT` or `TERMINATED` lease never conflict.

Each eligible clause is then tested for **carve-out suppression**, and all three conditions must hold for the clause to be suppressed: the candidate's `primary_use_code` must appear in the candidate's own `incidental_use_codes` array, the candidate's `projected_incidental_sales_pct` must be at most the clause's `incidental_sales_pct_cap`, and the candidate's `gla_sqft` must be at most the clause's `gla_carve_out_sqft`. Both comparisons are at-most comparisons, so a value exactly equal to the cap still qualifies for suppression. The clauses that survive suppression are the **conflicts**, and their number is reported as `conflicting_clause_count`. The number of clauses in the eligible pool before suppression is reported as `eligible_clause_count`, the code that was tested is echoed as `screened_use_code`, and `carve_out_applied` is true exactly when the eligible pool was non-empty and every member of it was suppressed.

When there are no conflicts the `decision` is `CLEAR` and `controlling_clause_id` is null — this is also the fallback when the eligible pool was empty to begin with. When there is at least one conflict the `decision` is `CONFLICT` and `controlling_clause_id` names the single controlling clause, chosen by ranking the conflicts on three keys in order: scope severity descending, where `CENTER_WIDE` ranks 3, `RADIUS_INCLUSIVE` ranks 2, and `PAD_EXCLUDED` ranks 1; then `gla_carve_out_sqft` ascending; then `created_at` ascending. A record's `id` never participates in the ranking. Ties broken by nothing else can occur only between clauses identical on all three keys.

Executing a lease is the moment the abstract becomes binding. A `LeaseAdministrator` advances `premises_status` from `DRAFT` to `EXECUTED`, and four preconditions must hold: the center's `compliance_posture` must not be `FROZEN`, no other lease of the center with a non-`TERMINATED` `premises_status` may hold the same `suite_code`, the prohibited-use screen must return a clear decision, and `expiration_date` must be strictly after `commencement_date`. The frozen-posture refusal outranks the screening refusal, as §2.9 pins. On success the lease enters the occupancy population as an **uncounted** member — an `EXECUTED` lease contributes nothing to the numerator, so the center's occupancy figures do not move — every `OPENING` co-tenancy condition of the lease is evaluated for the first time, and the center's posture is re-derived.

### 3.3. Co-Tenancy Conditions: Abstraction, the Opening Gate, and Continuous Evaluation

A `LeaseAdministrator` abstracts a co-tenancy condition from the lease document by declaring a `condition_kind` of either `OPENING` or `ONGOING`, a `measurement_basis` of either `GLA_PCT` or `STORE_COUNT`, and a `remedy_type` drawn from `RENT_REDUCTION_ONLY`, `RENT_REDUCTION_THEN_TERMINATION`, and `TERMINATION_ONLY`. Exactly one threshold field is mandatory and the other must be omitted: a `GLA_PCT` condition requires `required_occupancy_pct` (greater than 0 and at most 100) and must not carry `required_open_store_count`; a `STORE_COUNT` condition requires `required_open_store_count` of at least 1 and must not carry `required_occupancy_pct`. Getting that pairing wrong answers `ERR_MEASUREMENT_BASIS_MISMATCH`. Independently of the basis, `required_anchor_count` states a minimum number of open anchor boxes and defaults to 0. `grace_period_days` defaults to 30 and is the number of days a breach must persist before the benefited lease becomes remedy-eligible — a value of 0 makes eligibility immediate at breach detection. `cure_period_days` defaults to 120 and is the landlord's cure window; a terminating remedy requires the breach to have persisted at least that many days. `max_reduction_pct` defaults to 50 and caps the abatement this condition can produce; it must be greater than 0 and at most 100.

The two kinds attach at different points in the premises lifecycle, and abstracting one at the wrong point answers `ERR_CONDITION_KIND_INVALID`: an `OPENING` condition may not be added to a lease that is already `OPEN`, and an `ONGOING` condition may not be added to a lease still in `DRAFT`. A condition is **evaluated immediately at creation** under the live strict engine, so its `status` is either `SATISFIED` or `BREACHED` the instant it exists — there is no pending or unevaluated state. A creation that lands on `BREACHED` stamps `breach_detected_at` with the current logical instant, sets `consecutive_breach_days` to 0, and re-derives the center's posture, which means that merely abstracting a condition faithfully from a lease document can freeze the center.

**The evaluation predicate.** A condition is satisfied only when all three of the following hold, and the three are combined without regard to order. First, the **basis test**: for a `GLA_PCT` condition, the controlling occupancy percentage must be greater than or equal to `required_occupancy_pct`; for a `STORE_COUNT` condition, the controlling non-anchor open-store count must be greater than or equal to `required_open_store_count`. A percentage exactly equal to the requirement is satisfied. Second, the **anchor count test**: the controlling open-anchor count must be greater than or equal to `required_anchor_count`. Third, the **named-anchor test**, described below. The controlling figures come from whichever engine is driving the evaluation: a live strict evaluation reads the center's `open_occupancy_pct`, `operating_store_count`, and `open_anchor_count` under the `SNAPSHOT_STRICT` variant at the current clock, while a certified-measurement evaluation reads the certifying measurement's `gla_occupancy_pct`, `open_store_count`, and `open_anchor_count` under that measurement's own `variant` at its `measured_at` instant. Percentages are compared at the two decimal places the snapshot produced, with no re-rounding before comparison. Conditions of a `TERMINATED` lease and conditions already `WAIVED` are excluded from evaluation entirely; `ONGOING` conditions are evaluated only while the benefited lease is `OPEN` or `DARK`, and `OPENING` conditions only while it is `EXECUTED`.

**Named anchors and substitution.** A condition may name specific anchors whose continued operation it requires. A `LeaseAdministrator` adds such a requirement by supplying `anchor_lease_id` — which must belong to a lease whose `parcel_kind` is `ANCHOR_BOX` in the same center as the condition's benefited lease — together with `substitution_allowed` and `min_substitute_gla_sqft` (at least 0). The requirement row is immutable, and adding one re-evaluates the parent condition on the spot, so naming an already-dark anchor breaches the condition immediately and increments the center's `version`. The named-anchor test walks every requirement of the condition. If the named anchor lease counts open under the controlling variant at the controlling instant, that requirement is satisfied and the walk continues. If it does not count open and `substitution_allowed` is false, the named-anchor test fails. If it does not count open and substitution is allowed, the system looks for a qualifying substitute: a lease of the same center whose `parcel_kind` is `ANCHOR_BOX`, which is neither the named anchor itself nor named by any other requirement of the same condition, which counts open under the controlling variant at the controlling instant, and whose `gla_sqft` is at least `min_substitute_gla_sqft`. If no such lease exists, the named-anchor test fails. All requirements must pass for the test as a whole to pass.

**Opening the store.** A `LeaseAdministrator` or the tenant's own `TenantRep` advances the premises from `EXECUTED` to `OPEN`. One precondition governs — the center's `compliance_posture` is *not* consulted here, so a `FROZEN` center still accepts an opening: every `OPENING` co-tenancy condition of that lease must evaluate satisfied against the **controlling figures**, which are those of the center's latest certified occupancy measurement — ordered by `measured_at` descending and then `created_at` descending — or, when the center has no certified measurement at all, the center's own live strict figures. On success, `premises_status` becomes `OPEN`, `opened_at` is stamped with the current logical instant, `dark_since` is cleared to null, and the lease's `version` advances. The center then recomputes `occupied_gla_sqft`, `open_occupancy_pct`, `operating_store_count`, `open_anchor_count`, and `aggregate_effective_rent_cents`; every `ONGOING` condition of the center is re-evaluated under the live strict engine, so one tenant opening can cure another tenant's breach; and the center's posture is re-derived.

**Going dark — the five-hop cascade.** When a `LeaseAdministrator` or `TenantRep` records that a tenant has ceased operating while the lease survives, the premises move `OPEN → DARK` and five hops complete inside the request. Hop 1 sets `premises_status` to `DARK`, stamps `dark_since` with the current logical instant, and increments the lease's `version`. Hop 2, caused by hop 1 because the lease is no longer counted open, subtracts the lease's `gla_sqft` from the center's `occupied_gla_sqft`, recomputes `open_occupancy_pct`, and decrements either `operating_store_count` or `open_anchor_count` according to the lease's `is_anchor`. Hop 3, caused by hop 2 because the center's occupancy figures moved, re-evaluates every `ONGOING` condition of the center under the live strict engine; a condition that now fails flips from `SATISFIED` or `CURED` to `BREACHED` with `breach_detected_at` stamped at the current instant and `consecutive_breach_days` reset to 0. Hop 4, caused by hop 3 because a condition flipped, moves the benefited lease of each newly breached condition from `remedy_status` `NONE` to `ELIGIBLE` with `remedy_eligible_at` stamped — but only when that condition's `grace_period_days` is 0; a condition with a non-zero grace window waits for the sweep — and bumps that benefited lease's `version`, while the center's posture is re-derived to `BREACH` or `FROZEN`. Hop 5, caused by hop 4 because the benefited lease's version advanced, flips every estoppel certificate of that benefited lease whose `status` is `REQUESTED` or `TENANT_SIGNED` to `STALE` and recomputes its `lender_conditions_met` to false. The only precondition on going dark is that the premises are currently `OPEN`.

**Reopening** is the exact compensating action. A `LeaseAdministrator` or `TenantRep` moves the premises `DARK → OPEN` provided they are currently `DARK` and the tenant's `status` is not `BANKRUPT`. `opened_at` is re-stamped, `dark_since` returns to null, and `occupied_gla_sqft`, `open_occupancy_pct`, `operating_store_count`, and `open_anchor_count` are restored to exactly their pre-dark values. Every `ONGOING` condition of the center is re-evaluated; conditions that now pass flip `BREACHED → CURED` with `breach_detected_at` cleared to null and `consecutive_breach_days` reset to 0. A benefited lease whose only breach has cured returns `remedy_status` from `ELIGIBLE` to `NONE` with `remedy_eligible_at` cleared, while a lease that already has an approved active reduction stays at `REMEDY_ACTIVE` until that election is rescinded or consummated. Posture is re-derived.

**The condition status cycle.** A condition's `status` is cyclic across `SATISFIED`, `BREACHED`, `CURED`, and the terminal `WAIVED`, and `BREACHED → CURED → BREACHED` is reachable as many times as occupancy oscillates. A satisfied condition breaches when an evaluation returns unsatisfied, stamping `breach_detected_at` and zeroing `consecutive_breach_days`. A breached condition cures when an evaluation returns satisfied, clearing `breach_detected_at` to null and zeroing `consecutive_breach_days`; the benefited lease then falls from `ELIGIBLE` back to `NONE` when no other condition of that lease is breached and no live election exists, while `REMEDY_ACTIVE` is retained until the election is rescinded or consummated. A cured condition re-breaches on a later unsatisfied evaluation, and this stamps `breach_detected_at` afresh — it is a **new breach episode**, not a continuation, so `consecutive_breach_days` restarts at 0. A condition that is already breached and still failing takes a self-transition on each later evaluation and on each compliance sweep: `consecutive_breach_days` is set to the number of whole days from `breach_detected_at` to the evaluation instant, `breach_detected_at` itself is left untouched, and the benefited lease moves from `NONE` to `ELIGIBLE` once `consecutive_breach_days` reaches or exceeds `grace_period_days`. Whenever an evaluation is driven by a certification, the evaluated condition's `last_evaluated_measurement_id` is pinned to that measurement's id; a live strict evaluation leaves that field exactly as it found it. `consecutive_breach_days` reads 0 whenever the condition is not breached.

An `AssetManager` may **waive** a condition outright — the landlord buying out the protection — by supplying a `waiver_reason_code`. A waive is accepted from `SATISFIED`, `CURED`, or `BREACHED` and drives the condition to the terminal `WAIVED` with `breach_detected_at` cleared to null and `consecutive_breach_days` zeroed; from any other status it answers `ERR_CONDITION_STATE_INVALID`. Waiving a breached condition additionally returns the benefited lease from `ELIGIBLE` to `NONE` when it was that lease's only breached condition, rescinds every election naming that condition that is still merely elected and reverses its reduction, and re-derives the center's posture — which is the mechanism by which a `FROZEN` center can fall back to `BREACH` or `COMPLIANT`.

**Tenant credit status.** A `LeaseAdministrator` or `ComplianceOfficer` may update a tenant's `status`. Doing so triggers a live strict recompute of every center holding a lease of that tenant, re-evaluates every co-tenancy condition of those centers, and re-derives posture. Because a `DEFAULTED` tenant stops counting under the strict variant, a credit downgrade can breach a condition **without a single store going dark** — and because a `DEFAULTED` tenant still counts under the trailing-grace variant, a certified trailing-grace measurement can subsequently cure it.

**Termination.** An `AssetManager` terminates a lease with a `termination_reason_code`, from `EXECUTED`, `OPEN`, or `DARK`; from any other premises status the request answers `ERR_LEASE_STATE_INVALID`. `premises_status` becomes the terminal `TERMINATED`, `dark_since` is cleared to null, and the lease leaves the occupancy population entirely. Every exclusive-use clause of that lease whose `status` is `ACTIVE` or `SUSPENDED` becomes `EXPIRED`, and every radius restriction of that lease whose `status` is `ACTIVE` becomes `EXPIRED`. Every non-terminal co-tenancy condition of the lease becomes `WAIVED`, and every election of the lease that is still elected or actively reducing becomes `CONSUMMATED` with its accrual frozen. The center then recomputes `occupied_gla_sqft`, `open_occupancy_pct`, `operating_store_count`, `open_anchor_count`, `aggregate_effective_rent_cents`, and `protected_exclusive_count`, re-evaluates every `ONGOING` condition of the center under the live strict engine — skipping the conditions of the terminated lease itself — and re-derives posture.

### 3.4. Remeasurement: Preparing, Certifying and Superseding

A `ComplianceOfficer` prepares an occupancy measurement for a center by declaring the counting `variant` — `SNAPSHOT_STRICT` or `TRAILING_GRACE` — the half-open measurement window `window_from_date` (inclusive) through `window_through_date` (exclusive), and `expected_center_version`. Measurement windows for one center are half-open, so a new window may begin exactly on an existing window's through-date; any interior overlap against a non-superseded measurement of the same center answers `ERR_MEASUREMENT_WINDOW_OVERLAP`.

A prepared measurement is created in `DRAFT` with `created_by_user_id` taken from `X-User-ID` and `measured_at` stamped from the logical clock. Every figure on it is computed by the snapshot machinery of §2.5 under the requested variant: `total_gla_sqft` is the center's total area **frozen onto the row** at `measured_at`, which is the denominator actually used and which insulates the measurement from any later redevelopment remeasurement; `occupied_gla_sqft` is the numerator actually used, equal to the center's own live figure only for a strict measurement taken with no defaulted tenants; `gla_occupancy_pct`, `open_store_count`, `open_anchor_count`, `counted_lease_count`, and `excluded_lease_count` follow. `breached_condition_count` is computed at preparation time by running the evaluation predicate against this measurement's own figures **without persisting any condition status**, and it reads 0 while the row is not certified. Creating a measurement drives every other `DRAFT` measurement of the same center to the terminal `SUPERSEDED`, which is precisely why the operation is version-pinned.

**Certification** is where a measurement's figures become the controlling numbers. A `ComplianceOfficer` whose `X-User-ID` differs from the row's `created_by_user_id` certifies a `DRAFT` measurement; the same officer who prepared it is refused with `ERR_SEGREGATION_OF_DUTIES`, and certifying a row that is not `DRAFT` answers `ERR_MEASUREMENT_STATE_INVALID`. Certification additionally requires that no other certified measurement of the same center has a half-open window overlapping this row's window. On success the `status` moves `DRAFT → CERTIFIED`, `certified_by_user_id` and `certified_at` are stamped, and every non-waived co-tenancy condition of the center is re-evaluated with the certified-measurement source using **this row's variant figures**, each evaluated condition having its `last_evaluated_measurement_id` pinned to this row. `breached_condition_count` is then set to the number of conditions of the center left `BREACHED` after that evaluation, benefited leases move their `remedy_status` according to the condition transitions of §3.3, and posture is re-derived. Certifying a trailing-grace measurement can therefore flip a condition the live engine had breached to `CURED` and unfreeze the center — the single most important interaction in this system.

**Superseding** a certified measurement is the compensating action. A `ComplianceOfficer` supplies a `supersede_reason_code`; the row must be `CERTIFIED`, or the request answers `ERR_MEASUREMENT_STATE_INVALID`. The `status` moves to the terminal `SUPERSEDED`, every condition whose `last_evaluated_measurement_id` pointed at this row has that field cleared to null and is re-evaluated under the live strict engine — which can re-breach it immediately — and posture is re-derived.

### 3.5. Electing, Pricing and Booking a Remedy

Once a lease's `remedy_status` is `ELIGIBLE` or `REMEDY_ACTIVE`, its `TenantRep` may elect a remedy. The election declares an `election_kind` drawn from `RENT_REDUCTION`, `TERMINATION`, and `SUBSTITUTE_RENT`, the abatement window `window_from_date` (inclusive) through `window_through_date` (exclusive), and `expected_lease_version`. Exactly one of two sources is named: `condition_id`, pointing at the breached co-tenancy condition being remedied, or `source_notice_id`, pointing at the escalated use-violation notice that made the lease eligible. Co-tenancy elections carry a condition and no source notice; self-help elections sourced from an escalated exclusive-use notice carry a source notice and no condition. An election against a lease whose `remedy_status` is neither `ELIGIBLE` nor `REMEDY_ACTIVE` answers `ERR_REMEDY_NOT_ELIGIBLE`.

The condition's `remedy_type` constrains which kinds are permitted, and a mismatch answers `ERR_REMEDY_KIND_NOT_PERMITTED`: `RENT_REDUCTION_ONLY` permits only `RENT_REDUCTION`; `TERMINATION_ONLY` permits only `TERMINATION`; `RENT_REDUCTION_THEN_TERMINATION` permits both `RENT_REDUCTION` and `TERMINATION`; and `SUBSTITUTE_RENT` is permitted only for an election sourced from an escalated notice. Creating an election supersedes any prior election on the same lease that is still merely `ELECTED`, driving it to `RESCINDED` without touching `remedy_status`, since an unapproved election never moved it.

**Pricing the abatement.** At election time, and never afterwards, the system pins `shortfall_pct_at_election`, `anchor_bonus_applied`, `reduction_pct`, and `reduced_rent_monthly_cents` through the following five steps. The **controlling figures** for the pricing are those of the occupancy measurement named by the condition's `last_evaluated_measurement_id` when that field is not null, and otherwise the center's live strict figures.

1. **The shortfall.** For an election sourced from an escalated notice with no condition named, the shortfall is a fixed 20.00 percentage points. Otherwise, for a `GLA_PCT` condition, the shortfall is the condition's `required_occupancy_pct` minus the controlling occupancy percentage, floored at zero and rounded half up to two decimal places. For a `STORE_COUNT` condition, the shortfall is the condition's `required_open_store_count` minus the controlling non-anchor open-store count, divided by `required_open_store_count`, multiplied by 100, floored at zero and rounded half up to two decimal places.
2. **The tier multiplier.** A shortfall of at most 5.00 points takes a multiplier of 1.0; a shortfall above 5.00 but at most 15.00 takes 1.5; a shortfall above 15.00 takes 2.0. Both tier boundaries are inclusive on their upper edge.
3. **The anchor-closure adder.** The shortfall is multiplied by the tier multiplier and that product is rounded half up to two decimal places; then, if any named anchor requirement of the breached condition is unsatisfied under the controlling figures — the named anchor not counted open and no qualifying substitute available — a flat 10.00 percentage points is added on top. The adder is applied **after** the multiplier and **before** the cap, and `anchor_bonus_applied` records true exactly when it was added, false otherwise. Like every other pinned figure it is never recomputed.
4. **The floor, then the cap.** The result is raised to a minimum of 5.00 points, and the raised value is then lowered to a maximum of the condition's `max_reduction_pct`. That nested order is pinned: floor first, cap second, so a condition whose cap is below 5.00 yields the cap. The outcome is `reduction_pct`.
5. **The informational snapshot.** `reduced_rent_monthly_cents` is the lease's `base_rent_monthly_cents` multiplied by 100 minus `reduction_pct`, divided by 100, and rounded half up to whole cents. It is a snapshot of what this election alone would leave payable and is deliberately distinct from the lease's `effective_rent_monthly_cents`, which sums every active reduction.

A new election is created in `ELECTED` with `elected_at` stamped and `abated_to_date_cents` at 0, and an election in that status **does not yet change effective rent at all**. Its window must satisfy `window_from_date` strictly before `window_through_date`, and `window_from_date` must not precede the date of the condition's `breach_detected_at`; either failure answers `ERR_ABATEMENT_WINDOW_INVALID`.

**Approval forks.** An `AssetManager` approves an election that is still `ELECTED` while the benefited lease's `remedy_status` is `ELIGIBLE` or `REMEDY_ACTIVE`, and the two branches are disjoint.

For `RENT_REDUCTION` and `SUBSTITUTE_RENT`, the election moves `ELECTED → REDUCTION_ACTIVE`, stamping `approved_by_user_id` from `X-User-ID` and `approved_at` from the clock. The window must lie within the lease's `commencement_date` through `expiration_date` term, and for every date the half-open window covers, the sum of `reduction_pct` over the lease's already-active reductions covering that date plus this election's own `reduction_pct` must be at most 100 — exceeding it answers `ERR_ABATEMENT_STACK_EXCEEDED`, and the window check of rung 20 is evaluated ahead of it. The lease's `remedy_status` becomes `REMEDY_ACTIVE`, `effective_rent_monthly_cents` is recomputed sum-then-round, `total_abated_cents` is recomputed round-then-sum, the lease's `version` advances, and the center's `aggregate_effective_rent_cents` drops by exactly the lease delta.

For `TERMINATION`, the election moves `ELECTED → TERMINATION_SCHEDULED` with the same stamps, and two extra preconditions apply: the condition's `remedy_type` must be `RENT_REDUCTION_THEN_TERMINATION` or `TERMINATION_ONLY`, and the condition's `consecutive_breach_days` must be greater than or equal to its `cure_period_days`. `termination_effective_date` is pinned at approval as the `window_from_date` plus 90 days, expressed as an ISO date; it stays null for every other kind and for an election that has not been approved. A scheduled termination whose effective date falls earlier than `breach_detected_at` plus `cure_period_days` is refused with `ERR_CURE_PERIOD_NOT_EXPIRED`. The lease's `remedy_status` becomes `TERMINATION_PENDING`, and — this is the asymmetry to watch — `effective_rent_monthly_cents` is left completely unchanged and the center's `aggregate_effective_rent_cents` does not move, because no abatement attaches to a termination election.

Approving an election from any status other than `ELECTED` answers `ERR_ELECTION_STATE_INVALID`.

**Effective rent — sum-then-round.** The lease's `effective_rent_monthly_cents` is recomputed on every approval, every rescission, every compliance sweep, every clock reposition, and every premises transition. Gather the lease's elections whose `status` is `REDUCTION_ACTIVE` and whose half-open window covers the current logical clock date — the `window_from_date` on or before it and the `window_through_date` strictly after it. Add their `reduction_pct` values into a single total. Subtract that total from 100, multiply the lease's `base_rent_monthly_cents` by the result, divide by 100, and round half up to whole cents **once, at the end**. Elections that are `TERMINATION_SCHEDULED`, `ELECTED`, `RESCINDED`, or `CONSUMMATED` never reduce effective rent. The center's `aggregate_effective_rent_cents` is then the sum of `effective_rent_monthly_cents` over the leases of that center whose `premises_status` is `OPEN` or `DARK`.

**The abatement ledger — round-then-sum.** `RemedyElection.abated_to_date_cents` and `Lease.total_abated_cents` are recomputed on every approval, every rescission, every compliance sweep, and every clock reposition. For one election, take the earlier of the current logical clock date and the election's `window_through_date` as the accrual end date; count the whole days from `window_from_date` to that end date, flooring the count at zero; divide that day count by 30 and round the quotient half up to four decimal places to obtain a month figure; then multiply the lease's `base_rent_monthly_cents` by the election's `reduction_pct`, divide by 100, multiply by the month figure, and **round half up to whole cents at this point, per election**. That value is the election's `abated_to_date_cents`. The lease's `total_abated_cents` is then the sum of the already-rounded per-election amounts over the lease's elections whose `status` is `REDUCTION_ACTIVE` or `CONSUMMATED`. Elections that are `ELECTED` or `RESCINDED` contribute zero and carry `abated_to_date_cents` of 0. Rounding once at the end of the sum instead of per election is the rejected alternative and must not be used: it differs whenever the fractional parts of two or more accruals sum to at least one cent.

**Rescission.** An `AssetManager` or the lease's own `TenantRep` rescinds an election with a `rescission_reason_code`, from `ELECTED`, `REDUCTION_ACTIVE`, or `TERMINATION_SCHEDULED`, driving it to the terminal `RESCINDED`. Rescinding an active reduction reverses the abatement retroactively and in full: `abated_to_date_cents` is reset to 0, `total_abated_cents` is recomputed from the remaining qualifying elections, `effective_rent_monthly_cents` is recomputed, and `aggregate_effective_rent_cents` returns to exactly its pre-approval value with zero drift. The lease's `remedy_status` falls from `REMEDY_ACTIVE` to `ELIGIBLE` when no active reduction remains and at least one condition of the lease is still `BREACHED`, or to `NONE` when no breached condition remains. Rescinding a scheduled termination returns the lease from `TERMINATION_PENDING` to `ELIGIBLE` while `termination_effective_date` is retained for audit. Rescinding an election that was merely `ELECTED` leaves `remedy_status` untouched.

**Consummation.** An `AssetManager` consummates an election, and both branches join here at the terminal `CONSUMMATED`. An active reduction may be consummated once its `window_through_date` is on or before the current date; `abated_to_date_cents` freezes at its final value and keeps contributing to `total_abated_cents`, `effective_rent_monthly_cents` is recomputed because the window no longer covers today, and the lease's `remedy_status` falls to `ELIGIBLE` when a breached condition remains or to `NONE` otherwise. A scheduled termination may be consummated once its `termination_effective_date` is on or before the current logical clock date; the lease's `remedy_status` becomes the terminal `TERMINATED_BY_REMEDY` and its `premises_status` becomes `TERMINATED`, with the full termination cascade of §3.3 — clauses and radius restrictions expired, center derived fields, `protected_exclusive_count`, and posture all recomputed.

The remedy dimension also moves on its own in response to condition changes. A lease reaches `ELIGIBLE` from `NONE` when a condition of that lease flips to breached with a zero grace period, when a sweep observes `consecutive_breach_days` at or above `grace_period_days`, or when a notice citing a clause of that lease is escalated; the lease must be in `EXECUTED`, `OPEN`, or `DARK` and must actually have a breached condition or an escalated notice against a clause it benefits from, and `remedy_eligible_at` is stamped while every estoppel certificate of the lease that is `REQUESTED` or `TENANT_SIGNED` flips to `STALE`. A lease returns from `REMEDY_ACTIVE` to `ELIGIBLE` when the last active reduction leaves that status while a breached condition remains. It returns from `REMEDY_ACTIVE` to `NONE` when every condition of the lease is `SATISFIED`, `CURED`, or `WAIVED` and no election of the lease remains `ELECTED`, `REDUCTION_ACTIVE`, or `TERMINATION_SCHEDULED`, at which point `remedy_eligible_at` is cleared and `effective_rent_monthly_cents` returns to `base_rent_monthly_cents`. It returns from `ELIGIBLE` to `NONE` when no condition of the lease is breached and no election of the lease remains in one of those three live statuses.

### 3.6. Use Violations, Radius Enforcement, Disputes and Adjudication

A `ComplianceOfficer` or `LeaseAdministrator` issues a use-violation notice against an operating tenant by supplying the `violating_lease_id`, the `notice_kind`, an optional `narrative` describing the observed violation (defaulting to an empty string), an optional `cure_period_days` (defaulting to 30), and, where the kind demands it, the `clause_id`. The three kinds differ in what they cite: `EXCLUSIVE_USE` cites a specific benefited clause and therefore requires `clause_id`; `PROHIBITED_USE` cites the center's prohibited-use list without any clause and therefore requires `clause_id` to be null; and `RADIUS` is never issued directly — it is minted only by the radius violation-report capability. A cited clause whose `status` is anything other than `ACTIVE` — including a clause suspended by a recorded redevelopment plan — answers `ERR_CLAUSE_NOT_ACTIVE`.

An issued notice starts in `ISSUED` with `issued_by_user_id` taken from `X-User-ID`, `issued_at` stamped from the logical clock, `cure_deadline_at` set to `issued_at` plus `cure_period_days` days, `cure_restart_count` at 0, `recapture_assessed_cents` at 0, `radius_restriction_id` null, `reported_offending_sales_cents` at 0, and `escalated_at` null. The violating lease's `use_compliance_status` moves from `CLEAR` to `UNDER_NOTICE`, the center's `open_violation_count` increments, and posture is re-derived — which is how a first notice against an otherwise healthy center moves it from `COMPLIANT` to `WATCH`.

**Radius restrictions.** A `LeaseAdministrator` records a radius restriction binding a lease's tenant with `radius_miles` (greater than 0), a `measured_from` origin of either `CENTER_BOUNDARY` or `PREMISES_CENTROID`, a `recapture_basis` of either `GROSS_SALES` or `INCREMENTAL_SALES`, a `recapture_pct` (greater than 0 and at most 100), an optional `protected_baseline_cents` defaulting to 0, and the closed enforcement window `window_from_date` through `window_through_date`, both inclusive. The restriction is created `ACTIVE`. Windows for one lease are closed-closed and may not share even a single day: two restrictions collide when the first's from-date is on or before the second's through-date and the second's from-date is on or before the first's through-date, so **touching endpoints do collide**, and the collision answers `ERR_RADIUS_WINDOW_OVERLAP`. Recording a restriction is refused while the center is `FROZEN`. A restriction becomes `EXPIRED` when its lease is terminated, and `WAIVED` when a dispute against a radius notice is upheld on inapplicable-scope grounds.

A `ComplianceOfficer` reports an in-radius violation against a restriction by supplying `reported_offending_sales_cents`, a `narrative`, and optionally `cure_period_days`. The restriction must be `ACTIVE` and its closed enforcement window must contain the current logical clock date, or the report answers `ERR_RADIUS_WINDOW_INACTIVE`. The report mints a notice with `notice_kind` set to `RADIUS`, `radius_restriction_id` set from the addressed restriction, `clause_id` null, `status` `ISSUED`, `issued_by_user_id` from `X-User-ID`, and `cure_deadline_at` set to `issued_at` plus `cure_period_days` days. **The recapture assessment** is computed onto `recapture_assessed_cents` at that moment: under the `GROSS_SALES` basis the chargeable base is the entire `reported_offending_sales_cents` and `protected_baseline_cents` is ignored; under the `INCREMENTAL_SALES` basis the chargeable base is `reported_offending_sales_cents` minus `protected_baseline_cents`, floored at zero. The assessment is that base multiplied by `recapture_pct`, divided by 100, and rounded half up to whole cents. A reported volume exactly equal to `protected_baseline_cents` therefore yields 0 under the incremental basis and a positive assessment under the gross basis. The notice's other side effects mirror a directly issued notice: the lease's `use_compliance_status` moves from `CLEAR` to `UNDER_NOTICE`, the center's `open_violation_count` increments, and posture is re-derived. Non-radius notices carry `recapture_assessed_cents` of 0.

**Curing.** A `LeaseAdministrator` or `ComplianceOfficer` accepts the tenant's cure by supplying a `cure_evidence_code`. A cure is accepted from `ISSUED` or `ESCALATED` and requires that no dispute of the notice is still `PENDING`; the notice reaches the terminal `CURED`, the lease's `use_compliance_status` returns to `CLEAR` when no other notice against it remains `ISSUED`, `DISPUTED`, or `ESCALATED`, the center's `open_violation_count` decrements, and posture is re-derived. Curing a notice that is `CURED` or `WITHDRAWN` answers `ERR_NOTICE_STATE_INVALID`, while curing one that is `DISPUTED` answers the more specific `ERR_DISPUTE_PENDING`. Curing an escalated notice does not itself unwind the benefited lease's remedy posture: that lease keeps `remedy_status` `ELIGIBLE` until its elections are rescinded.

**Escalation — the four-hop cascade.** A notice that is `ISSUED`, whose `cure_deadline_at` is on or before the sweep instant, and against which no dispute is `PENDING`, escalates. Attempting it before the cure deadline has passed answers `ERR_CURE_PERIOD_NOT_EXPIRED`. Hop 1 sets the notice `status` to `ESCALATED` and stamps `escalated_at` with the sweep instant. Hop 2, caused by hop 1 because an escalated notice now stands against the premises, sets the violating lease's `use_compliance_status` to `IN_VIOLATION` and advances that lease's `version`. Hop 3, caused by hop 2 because the violating lease's version has moved past the pinned value, flips every estoppel certificate of that lease whose `status` is `REQUESTED` or `TENANT_SIGNED` to `STALE`. Hop 4, caused by hop 3 because the certificate is no longer current, recomputes each stale certificate's `lender_conditions_met` to false. Separately from that hop chain, an `EXCLUSIVE_USE` notice fans out to the benefited lease of its `clause_id`, moving that lease's `remedy_status` from `NONE` to `ELIGIBLE` with `remedy_eligible_at` stamped at the sweep instant — opening the door to a substitute-rent election — and the center's posture is re-derived. For a radius notice the eligibility lands on the same lease the restriction binds.

**Withdrawal.** A `ComplianceOfficer` withdraws a notice the landlord no longer stands behind, supplying a `withdrawal_reason_code`. Withdrawal is accepted from `ISSUED` or `ESCALATED`, drives the notice to the terminal `WITHDRAWN`, and — when the notice had escalated — is the compensating action that reverses the entire hop chain: `escalated_at` returns to null, the violating lease's `use_compliance_status` moves from `IN_VIOLATION` back to `CLEAR`, or to `UNDER_NOTICE` when another issued notice against that lease remains; the benefited lease of the cited clause returns from `ELIGIBLE` to `NONE` when this notice was its only escalation source and no condition of that lease is `BREACHED`; the center's `open_violation_count` decrements; and posture is re-derived. Withdrawing a `DISPUTED` notice answers `ERR_DISPUTE_PENDING`.

**Disputes.** The violating tenant's `TenantRep` disputes an `ISSUED` notice, which requires that `X-User-ID` equal the violating lease's `tenant_id` and that no dispute of that notice is already `PENDING`. The dispute declares a `grounds_code` drawn from `NO_PROHIBITED_USE`, `CARVE_OUT_APPLIES`, `CLAUSE_EXPIRED`, and `SCOPE_INAPPLICABLE`, a `narrative` setting out the tenant's written grounds, and an optional `cure_extension_days` defaulting to 0 and constrained to between 0 and 90 inclusive. The dispute is created `PENDING` with `filed_by_tenant_id` copied from `X-User-ID`, `adjudicated_by_user_id` null, and `adjudicated_at` null; the parent notice moves `ISSUED → DISPUTED`, its `use_compliance_status` contribution becomes `UNDER_NOTICE`, and its cure clock is suspended — `cure_deadline_at` is frozen where it stands, so escalation is blocked until adjudication.

**Adjudication.** A `ComplianceOfficer` whose `X-User-ID` differs from the notice's `issued_by_user_id` adjudicates a `PENDING` dispute by supplying an `outcome`; the notice's own issuer is refused with `ERR_SEGREGATION_OF_DUTIES`, and adjudicating a dispute already `UPHELD`, `DENIED`, or `WITHDRAWN` answers `ERR_DISPUTE_STATE_INVALID`. Either outcome stamps `adjudicated_by_user_id` from `X-User-ID` and `adjudicated_at` from the clock.

An **upheld** dispute moves to the terminal `UPHELD` and drives the notice `DISPUTED → WITHDRAWN` with every notice side effect reversed. Additionally, and only when `grounds_code` is `SCOPE_INAPPLICABLE`, the cited protection itself is given up: the cited exclusive-use clause moves from `ACTIVE` to `WAIVED`, or the cited radius restriction moves from `ACTIVE` to `WAIVED`, and the center's `protected_exclusive_count` is recomputed. No other grounds waives the cited protection. The violating lease's `use_compliance_status` is recomputed, `open_violation_count` decrements, and posture is re-derived.

A **denied** dispute moves to the terminal `DENIED` and re-arms the notice, which is the system's one genuinely cyclic path: the notice returns `DISPUTED → ISSUED`, `cure_restart_count` increments by one, and `cure_deadline_at` is re-armed to the dispute's `adjudicated_at` plus the sum of the notice's `cure_period_days` and the dispute's `cure_extension_days`, expressed in days. `ISSUED → DISPUTED → ISSUED` is reachable any number of times, and `cure_restart_count` counts exactly those cycles.

A dispute may also reach the terminal `WITHDRAWN` without adjudication, but only in one narrow circumstance: because a notice cannot be cured while a dispute is pending, this happens solely when the cited exclusive-use clause or the cited radius restriction becomes `EXPIRED` through the termination of its lease. The dispute is withdrawn and its notice is withdrawn with it.

### 3.7. The Compliance Sweep

A `ComplianceOfficer` advances the whole center's compliance state at the current logical clock through a single sweep. The sweep is the only operation that lets time itself change compliance state, and it performs the following in one request. Every notice of the center whose cure deadline has passed and against which no dispute is `PENDING` is escalated with the full four-hop cascade of §3.6; notices with a pending dispute are **skipped rather than failed**. Every lease whose breached condition has reached the point where `consecutive_breach_days` is greater than or equal to that condition's grace requirement moves `remedy_status` from `NONE` to `ELIGIBLE`. Every condition of the center is re-evaluated under the live strict engine, so both `BREACHED → CURED` and `CURED → BREACHED` are possible in the same sweep, and conditions that are still failing take their self-transition with `consecutive_breach_days` advanced to the whole days elapsed since `breach_detected_at`. Every active reduction whose `window_through_date` has arrived on or before the sweep date is consummated, and every scheduled termination whose `termination_effective_date` has arrived on or before the sweep date is consummated with its lease driven to `TERMINATED_BY_REMEDY` and `TERMINATED`. The abatement ledger and the effective-rent recomputation are re-run for every lease, `aggregate_effective_rent_cents` is refreshed, `last_sweep_at` is set to the sweep instant, `compliance_posture` is re-derived, and the center's `version` increments.

The sweep reports what it did: `as_of` carries the instant it ran at, `escalated_notice_count` the number of notices it escalated, `newly_eligible_lease_count` the number of leases it moved into remedy eligibility, `cured_condition_count` the number of conditions it cured, `breached_condition_count` the number left breached afterwards, and `compliance_posture` the center's resulting posture.

### 3.8. Estoppel Certificates and Lender Requirements

A `LenderRep` or an `AssetManager` requests a tenant estoppel certificate against a lease, optionally pinning a certified occupancy measurement through `measurement_id` — leaving it null means the certificate discloses the center's live figures — and optionally setting `expedite_requested`, which defaults to false. The certificate is created `REQUESTED` with `requested_by_user_id` from `X-User-ID`, `signed_at` and `accepted_at` null, and `pinned_lease_version` set to the lease's `version` observed at request time. Three disclosures are computed at that same instant: `disclosed_cotenancy_breach` is true when at least one co-tenancy condition of the estopped lease is `BREACHED`; `disclosed_exclusive_count` is the number of `ACTIVE` exclusive-use clauses benefiting that lease; and `disclosed_effective_rent_cents` is the lease's `effective_rent_monthly_cents`. `lender_conditions_met` is false on a freshly requested certificate.

**The certificate fee** is assessed in three pinned steps, and the order matters because the dependency looks circular — the surcharge is a percentage of the fee while the tier is a function of the fee. First, the pre-surcharge subtotal is 25,000 cents of base fee, plus 5,000 cents for each disclosed exclusive-use clause, plus a further 15,000 cents when `disclosed_cotenancy_breach` is true. That subtotal is `base_fee_cents`. Second, the surcharge tier is selected **on that subtotal, exactly once**: a subtotal of at most 40,000 cents takes a 10.0% tier, a subtotal above 40,000 but at most 75,000 cents takes 15.0%, and a subtotal above 75,000 cents takes 20.0%. Third, when `expedite_requested` is true, the surcharge is the subtotal multiplied by the tier percentage, divided by 100, and rounded half up to whole cents; when it is false the surcharge is zero. `total_fee_cents` is the subtotal plus the surcharge, and it is **never re-tiered** — a subtotal of exactly 40,000 cents takes the 10.0% tier even though the resulting total of 44,000 cents sits inside the next tier's range.

**Lender conditions.** `lender_conditions_met` is true only when all four of the following hold, and it is recomputed at request time, at signing, and whenever the certificate goes stale: the certificate's `status` is `TENANT_SIGNED`; `pinned_lease_version` still equals the lease's current `version`; the lease's `use_compliance_status` is `CLEAR`; and either no co-tenancy condition of the lease is `BREACHED` or `disclosed_cotenancy_breach` is true. That last clause is the point of the whole instrument: a breach does **not** block acceptance once the certificate discloses it — only an **undisclosed** breach does.

The tenant's `TenantRep` signs a certificate that is `REQUESTED`, which requires that `pinned_lease_version` still equal the lease's `version` and that `X-User-ID` equal the lease's `tenant_id`. Signing stamps `signed_at`, moves the status to `TENANT_SIGNED`, and recomputes `lender_conditions_met`. A `LenderRep` then accepts a `TENANT_SIGNED` certificate, which requires `pinned_lease_version` still to match and `lender_conditions_met` to be true; acceptance stamps `accepted_at` and reaches the terminal `LENDER_ACCEPTED`. Accepting while `lender_conditions_met` is false answers `ERR_LENDER_CONDITIONS_NOT_MET` — typically a signed certificate whose lease has drifted to `UNDER_NOTICE` or `IN_VIOLATION`, or whose lease has a breached condition the certificate never disclosed. Signing a certificate that is not `REQUESTED`, or accepting one that is not `TENANT_SIGNED`, answers `ERR_CERTIFICATE_STATE_INVALID`.

**Staleness.** Any mutation that pushes the lease's `version` above `pinned_lease_version` drives a certificate that is `REQUESTED` or `TENANT_SIGNED` to `STALE` and forces `lender_conditions_met` to false. A stale certificate cannot be signed: the attempt answers `ERR_CERTIFICATE_STALE` (409) and mutates nothing. Nor can it be accepted; accepting a stale row is likewise refused with `ERR_CERTIFICATE_STALE` and mutates nothing, and only an explicit rejection moves a stale row onward. A `LenderRep` or `AssetManager` rejects a certificate that is `REQUESTED`, `TENANT_SIGNED`, or `STALE` by supplying a `rejection_reason_code`, driving it to the terminal `REJECTED`. The fee survives rejection: `total_fee_cents` is neither refunded nor zeroed.

### 3.9. Redevelopment, Pad Sales and Protected Rights

An `AssetManager` plans a redevelopment against a center by declaring a `plan_kind` drawn from `PAD_SALE`, which conveys a pad parcel, `REDEMISE`, which re-splits existing area, and `EXPANSION`, which adds area and never removes any. `removed_gla_sqft` defaults to 0, must be at least 0 and strictly less than the center's `total_gla_sqft`, and must be exactly 0 when the kind is `EXPANSION`. A pad sale names the conveyed lease through `pad_parcel_lease_id`, which when supplied must belong to a lease whose `parcel_kind` is `PAD`.

Planning computes the plan's impact before anything moves. `gla_after_sqft` is the center's `total_gla_sqft` minus `removed_gla_sqft` at creation time. `impacted_clause_count` is the number of `ACTIVE` exclusive-use clauses on non-`TERMINATED` leases of the center whose `exclusivity_scope` is `CENTER_WIDE` or `RADIUS_INCLUSIVE` — a `PAD_EXCLUDED` clause is by construction not impacted by a pad sale. `impacted_condition_count` is the number of `ONGOING` `GLA_PCT` conditions whose `status` is `SATISFIED` or `CURED` and which would fail when tested against the post-plan denominator. `consent_required` is true when either count is greater than zero. The plan is created `CONSENT_PENDING` when consent is required and `PLANNED` otherwise, with `recorded_at` null, and the center's `redevelopment_status` moves to `PLANNED`. That center field reads `NONE` until a plan for the center exists, `PLANNED` while any plan of the center sits in `PLANNED` or `CONSENT_PENDING`, `RECORDED` once any plan of the center reaches `RECORDED`, and returns to `NONE` when every plan of the center has been abandoned.

**Recording** applies the plan. It is refused while the center is `FROZEN`, and a plan whose `consent_required` is true may only be recorded with `consent_confirmed` true in the body — omitting it answers `ERR_PROTECTED_RIGHTS_CONSENT_REQUIRED`. Recording from a status other than `PLANNED` or `CONSENT_PENDING` answers `ERR_PLAN_STATE_INVALID`. On success the plan becomes `RECORDED` with `recorded_at` stamped, and the center's `total_gla_sqft` is reduced by `removed_gla_sqft` while `occupied_gla_sqft` is left exactly where it was — so `open_occupancy_pct` is recomputed against a **smaller denominator**, which can cure a `GLA_PCT` condition without a single tenant opening a door. `redevelopment_status` becomes `RECORDED`. When the plan required consent, every `ACTIVE` exclusive-use clause of the center whose `exclusivity_scope` is `CENTER_WIDE` becomes `SUSPENDED` with `suspended_by_plan_id` set to this plan's id, while `RADIUS_INCLUSIVE` clauses survive the pad sale untouched; `protected_exclusive_count` is recomputed, and a use that previously conflicted may now screen clear. When `pad_parcel_lease_id` is not null, every co-tenancy condition of that pad lease becomes `WAIVED` — the one path by which a waive is written by something other than an explicit landlord waiver. Every `ONGOING` condition of the center is then re-evaluated under the live strict engine on the smaller denominator, and posture is re-derived.

**Abandoning** is the compensating action, and it must restore every conserved quantity exactly. An `AssetManager` supplies an `abandon_reason_code`; a plan may be abandoned from `PLANNED`, `CONSENT_PENDING`, or `RECORDED`, and reaches the terminal `ABANDONED`. Abandoning a recorded plan adds `removed_gla_sqft` back to the center's `total_gla_sqft`, returns every clause whose `suspended_by_plan_id` names this plan to `ACTIVE` with `suspended_by_plan_id` cleared to null, restores `protected_exclusive_count` to exactly its pre-record cardinality, recomputes `open_occupancy_pct` against the restored denominator, re-evaluates every `ONGOING` condition of the center — which can re-breach a condition the recording had cured — and re-derives posture. `recorded_at` is retained for audit. Abandoning a plan that had not yet been recorded simply moves it to `ABANDONED` with no denominator or clause effects. In every case the center's `redevelopment_status` returns to `NONE` once no other plan of that center is `RECORDED` or `PLANNED`.

The center's `protected_exclusive_count` is the conserved quantity of this whole subsection. It counts exclusive-use clauses whose `status` is `ACTIVE` and whose benefited lease's `premises_status` is not `TERMINATED`, across the leases of the center, and the record-then-abandon pair must leave it exactly where it started.

## 4. Endpoint Definitions

Operations that create a new resource — a center, a tenant, a lease, a condition, an anchor requirement, a clause, a restriction, a notice, a dispute, an election, a measurement, a certificate, or a plan — return `201 Created`. Operations that modify an existing resource, including every state transition, every patch, the read-only screening decision, the compliance sweep, and the logical-clock capability, return `200 OK`. Reads return `200 OK`.
