# Field-Erected Storage Tank Construction API — Product Requirements Document

## 1. Introduction

An aboveground storage tank is not manufactured; it is *erected*. Plate arrives from a rolling mill on trucks, a civil contractor hands over a foundation whose settlement behaviour is still unknown, welders build a shell course by course in the open air, and a radiographer decides — one film set at a time — whether the tank is fit to hold product. Between the first design calculation and the day an authorized inspector signs the commissioning package, several hundred discrete facts must be recorded, cross-checked against a design standard, and kept mutually consistent. Today that record lives in a mix of spreadsheets, e-mailed PDFs and a field superintendent's memory, which means a rejected weld can be discovered only after the tank has been filled with test water, and a lapsed welder qualification can be discovered only during an audit two years later.

This document specifies the API for a single system of record covering that whole erection sequence: tank design registration and shell-course thickness calculation, foundation acceptance with settlement monitoring, plate procurement and steel accountability, welder qualification and continuity, field weld sequencing with radiographic examination, hydrostatic test planning with water sourcing and disposal costing, coating and lining with surface-preparation and holiday testing, appurtenance installation, and finally the commissioning documentation package that fixes the in-service inspection intervals. The system's governing design goal is that **a defect discovered anywhere propagates immediately to everything downstream of it**. A rejected radiograph does not merely mark a seam; it reverses the tank's construction phase, degrades the tank's quality posture, suspends the live hydrostatic test plan, and releases the water reservations that plan was holding against a permitted source.

The reader should treat two ideas as load-bearing throughout. First, a tank carries **two independent state dimensions** — how far the physical build has progressed, and how clean its quality record currently is — and neither one is derivable from the other. Second, every deadline, expiry, continuity window and hold period is read from a **server-side logical clock**, never from wall-clock time, so that a test harness can drive a two-year in-service interval in a single request.

## 2. Global Specifications & System-Wide Principles

Every collection in this API is a flat, top-level resource: there are no nested resource URLs. Relationships between records are expressed exclusively through foreign-key fields carried in request bodies and through filtered list reads. Where a caller wants "the settlement surveys of this foundation package", the caller lists settlement surveys filtered by the package identifier rather than walking a nested path.

### 2.1. Project Roles and Access Control

Every request — without exception, including reads — must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the role that operator is acting in. If either header is absent, or is present but holds an empty string, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A blank string is treated exactly as if the header had not been sent at all.

Six peer roles divide the work of erecting a tank, and their write privileges are disjoint by design:

- **`ProjectEngineer`** — owns tank design registration, shell course specification, water-source registration, hydrostatic test planning and plan approval, coating specification, appurtenance design, and the whole commissioning documentation path. The project engineer is also the party who accepts or rejects the civil contractor's foundation.
- **`CivilContractor`** — registers the foundation package and shoots every settlement survey round, but is never permitted to decide whether the foundation it built is acceptable.
- **`ErectionSuperintendent`** — runs the field: plate lot registration and receipt, plate allocation and release, course fit-up, seam declaration, repair initiation, water withdrawal reservation and cancellation, fill advance, and appurtenance installation.
- **`Welder`** — a qualified field welder whose only write capability is logging their own completed welds.
- **`QcInspector`** — schedules and reports nondestructive examinations, and performs every coating quality step: surface preparation, dry film thickness readings, and the holiday test.
- **`AuthorizedInspector`** — the independent inspector. Qualifies and revokes welders, voids erroneous examination reports, records the hydrostatic test pass-or-fail decision, and reviews the commissioning package.

If `X-User-Role` holds a string that is not one of those six spellings, or holds a valid role that is not authorised for the endpoint being called, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). Every read endpoint in the system is available to all six roles, and so is the logical-clock capability described in §2.4; all other writes are restricted as listed in §4.

Role identity binds to `X-User-ID` differently for one role than for the other five. When `X-User-Role` is `Welder`, `X-User-ID` is the `id` of the acting `Welder` row; ownership checks on any resource that references a `Welder` compare the resource's welder foreign-key field to `X-User-ID`. Concretely, a welder logging a weld must supply a `welder_id` equal to their own `X-User-ID`; a mismatch is rejected with `ERR_WELDER_IDENTITY_MISMATCH` (HTTP 403), because a qualified welder may only log welds under their own stamp. When `X-User-Role` is `ProjectEngineer`, `CivilContractor`, `ErectionSuperintendent`, `QcInspector` or `AuthorizedInspector`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands an audit trail — as `decided_by_user_id` on a foundation package, `qualified_by_user_id` on a welder, `reported_by_user_id` on an examination report, `approved_by_user_id` on a hydrostatic test plan, and `submitted_by_user_id` or `reviewed_by_user_id` on a commissioning package — but it never compares that value against any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` defaults to 0 and counts records to skip from the start of the ordered result. Results are always ordered by `created_at` ascending, so a caller paging through a collection sees records in the order the system recorded them. List responses populate all four pagination keys inside `meta` — `limit` and `offset` echo the effective values in use, `total_count` reports how many records match the filter before pagination is applied, and `has_more` is true when records remain beyond the current page. Single-resource reads and writes carry no pagination keys in `meta`.

Beyond `limit` and `offset`, list endpoints accept domain filters that stand in for the nested paths this API does not have. Tanks may be filtered on `tank_tag`, `construction_phase` and `quality_posture`; foundation packages on `tank_id`, `status` and `foundation_type`; settlement surveys on `foundation_package_id`, `hydrotest_plan_id`, `survey_role`, `verdict` and `nonconformance_state`; plate lots on `tank_id`, `status` and `heat_number`; shell courses on `tank_id`, `allocated_plate_lot_id`, `status`, `allocation_status` and `thickness_verdict`; welders on `welder_stamp`, `process` and `qualification_status`; weld seams on `shell_course_id`, `welder_id`, `predecessor_seam_id`, `status` and `seam_type`; examination reports on `weld_seam_id`, `status`, `method` and `nonconformance_open`; water sources on `source_name` and `source_type`; hydrostatic test plans on `tank_id`, `water_source_id` and `status`; withdrawal windows on `hydrotest_plan_id`, `water_source_id` and `status`; coating applications on `tank_id`, `scope`, `status` and `dft_verdict`; appurtenances on `tank_id`, `host_shell_course_id`, `appurtenance_type` and `status`; and commissioning packages on `tank_id` and `status`.

### 2.4. Resource Identity, Revision Stamps and the Logical Clock

Every resource in the system carries the same four common properties. `id` is a server-minted UUID with no type prefix of any kind — a tank identifier and a weld-seam identifier are indistinguishable by shape. `created_at` and `updated_at` are ISO 8601 UTC timestamps with exactly three fractional-second digits. `version` is an integer that starts at 1 when the resource is created and increases by exactly 1 on every mutation of that resource; `updated_at` is refreshed on the same mutation. This applies to all fourteen resource families in the system without exception, so there is no resource that lacks `updated_at` or lacks `version`.

Identifiers arriving in a URL are resolved left to right, and the resource family named by the path segment determines the error identifier when resolution fails. A tank identifier that does not resolve yields `ERR_TANK_NOT_FOUND`; a foundation package identifier yields `ERR_FOUNDATION_PACKAGE_NOT_FOUND`; a settlement survey identifier yields `ERR_SETTLEMENT_SURVEY_NOT_FOUND`; a plate lot identifier yields `ERR_PLATE_LOT_NOT_FOUND`; a shell course identifier yields `ERR_SHELL_COURSE_NOT_FOUND`; a welder identifier yields `ERR_WELDER_NOT_FOUND`; a weld seam identifier yields `ERR_WELD_SEAM_NOT_FOUND`; an examination report identifier yields `ERR_NDE_REPORT_NOT_FOUND`; a water source identifier yields `ERR_WATER_SOURCE_NOT_FOUND`; a hydrostatic test plan identifier yields `ERR_HYDROTEST_PLAN_NOT_FOUND`; a withdrawal identifier yields `ERR_WATER_WITHDRAWAL_NOT_FOUND`; a coating application identifier yields `ERR_COATING_APPLICATION_NOT_FOUND`; an appurtenance identifier yields `ERR_APPURTENANCE_NOT_FOUND`; and a commissioning package identifier yields `ERR_COMMISSIONING_PACKAGE_NOT_FOUND`. All fourteen carry HTTP 404. Exactly the same mapping governs foreign keys arriving in a request **body**, which are resolved in the order the endpoint declares its input fields; a body-borne `tank_id` that does not resolve therefore also yields `ERR_TANK_NOT_FOUND`, a `host_shell_course_id` that does not resolve yields `ERR_SHELL_COURSE_NOT_FOUND`, and a `predecessor_seam_id` that does not resolve yields `ERR_WELD_SEAM_NOT_FOUND`.

Time in this system is a server-side **logical clock**. Every expiry, continuity window, examination window comparison, permit-expiry check and hold-period computation reads that clock and never the host's wall-clock time. Before any request sets it, the clock reads exactly `2026-08-01T00:00:00Z`; that startup default is mandatory and the server never falls back to real time. Any of the six roles may advance or rewind the clock by posting a single field, `to_iso8601`, to the clock-setting endpoint listed in §4; the response reports the new `current_utc`. Setting the clock has one deferred consequence: a welder's continuity is re-evaluated lazily, on the next read of that welder or the next attempt to log a weld under them, rather than eagerly at the moment the clock moves.

### 2.5. Numeric Precision and Rounding

All rounding in this system is **round half up** — a value exactly at the midpoint rounds away from zero — and the number of decimal places is fixed per quantity rather than chosen globally. Shell-course thicknesses are carried to 3 decimal places. Settlement metrics are carried to 3 decimal places, except the arc spacing between monitoring points, which is carried to 4. Dry film thickness averages are carried to 1 decimal place on the entity record, and the spot averages and overall average are rounded to 2 decimal places before being compared against their acceptance limits. Every monetary amount and every weight in pounds is carried to 2 decimal places. The weld reject rate is carried to 4 decimal places and the mandated examination percentage to 1. Angular clearances and separations are carried to 1 decimal place, aggregate withdrawal rates likewise to 1. Remaining bottom life is carried to 2 decimal places, and both in-service inspection intervals are whole integers. Counts are plain integers and are never rounded.

Two ordering rules are load-bearing and are repeated in the workflows that depend on them. First, where a formula rounds intermediate terms, the **rounded** intermediates are the values compared against limits and fed into any subsequent maximum or minimum, not the full-precision ones. Second, where a total is assembled from many line items, the specification always states whether each item is rounded before summation or whether a single sum is rounded once; those two orders can differ by cents and the stated order is the correct one.

### 2.6. Version Guards on Contested Parents

Two write operations in the system commit resources whose parent is shared by other writers, and both are guarded by an optimistic-concurrency check on the parent's `version`.

Creating a hydrostatic test plan requires a non-optional `expected_tank_version` field in the request body, carrying the `version` of the target `Tank` as the client last observed it. If that value does not equal the tank's current `version`, the create is rejected with `ERR_STALE_TANK_VERSION` (HTTP 412). The guard exists because a new plan legitimately supersedes the tank's prior draft or rejected plan and re-points the tank's `active_hydrotest_plan_id`; a writer working from an outdated view of the tank would silently discard a plan it never saw. Every successful create advances the tank's `version` by 1, so a second create still carrying the older value fails.

Reserving a water withdrawal window requires a non-optional `expected_water_source_version` field in the request body, carrying the `version` of the target `WaterSource` as the client last observed it. If that value does not equal the source's current `version`, the reservation is rejected with `ERR_STALE_WATER_SOURCE_VERSION` (HTTP 412). Each reservation consumes part of the source's `available_volume_gal` and part of its concurrent-rate envelope, so a writer holding an outdated view of the source would size its reservation against capacity that has already been committed. Every accepted reservation advances the source's `version` by 1.

No other write in the system takes a version field. Endpoints not named in the two paragraphs above must not require, and must not honour, an expected-version input.

### 2.7. The Two State Dimensions of a Tank

A `Tank` record carries two state fields that evolve independently and must never be conflated.

`construction_phase` tracks physical build progress through exactly seven values: `DESIGN_REGISTERED`, `FOUNDATION_ACCEPTED`, `ERECTION_IN_PROGRESS`, `SHELL_COMPLETE`, `HYDROTEST_PASSED`, `COATED` and `COMMISSIONED`. A newly registered tank starts at `DESIGN_REGISTERED`; `COMMISSIONED` is terminal. Almost every advance along this dimension is a *side effect* of some other operation succeeding, not something an operator asks for directly: foundation acceptance drives `DESIGN_REGISTERED → FOUNDATION_ACCEPTED`, the first successful course fit-up drives `FOUNDATION_ACCEPTED → ERECTION_IN_PROGRESS`, a passing hydrostatic test drives `SHELL_COMPLETE → HYDROTEST_PASSED`, the last coating application reaching acceptance drives `HYDROTEST_PASSED → COATED`, and commissioning acceptance drives `COATED → COMMISSIONED`. The dimension also **reverts** on quality events: a shell course that leaves radiographic acceptance drives `SHELL_COMPLETE → ERECTION_IN_PROGRESS`, and a coating application entering rework drives `COATED → HYDROTEST_PASSED`. Exactly one transition on this dimension is requestable by an operator, and only by a `ProjectEngineer`: `ERECTION_IN_PROGRESS → SHELL_COMPLETE`, supplied as a `target_phase` of `SHELL_COMPLETE` together with optional `remarks`. Its gate is that the tank has at least one shell course and that **every** shell course of the tank is in radiographic acceptance. Any other `target_phase` — including every system-driven target `FOUNDATION_ACCEPTED`, `ERECTION_IN_PROGRESS`, `HYDROTEST_PASSED`, `COATED` and `COMMISSIONED`, and including an enum-valid target that is simply not declared from the tank's current phase — is rejected with `ERR_PHASE_TRANSITION_INVALID` (HTTP 409), as is a request whose gate is unmet.

`quality_posture` tracks how clean the tank's quality record currently is, through three values: `OPEN`, `RESTRICTED` and `FROZEN`. It is never set by a request field. It is recomputed from scratch at the end of every request that can open or close a nonconformance, exactly as §2.8 describes, and it gates child operations regardless of where the build has got to. The two dimensions are genuinely orthogonal: a tank may be `SHELL_COMPLETE` and `FROZEN`, or `ERECTION_IN_PROGRESS` and `OPEN`, in any combination.

### 2.8. Nonconformance Accounting, Posture Gates and the Suspension Cascade

The tank's `open_nonconformance_count` is a full recount, never an increment, and it sums four independent carriers: the number of examination reports that stand as unresolved rejections and whose seam belongs to this tank; the number of settlement surveys whose nonconformance is open and whose foundation package belongs to this tank; the number of coating applications of this tank that are currently in rework; and the number of hydrostatic test plans of this tank that have failed. `quality_posture` is then `OPEN` when the count is zero, `RESTRICTED` when the count is 1 or 2 inclusive, and `FROZEN` when the count is 3 or more. A single request can change more than one carrier, and the count is always recomputed in full afterwards; a count that jumps from 0 straight to 3 or more moves the posture from `OPEN` directly to `FROZEN` in one step, and a count that falls to 0 in one step moves `FROZEN` directly back to `OPEN`.

Whenever the recomputed posture leaves `OPEN`, the change propagates in a fixed order until it reaches a fixed point, which is always within a single pass because suspending a plan cannot itself open or close a nonconformance. First, every hydrostatic test plan of the tank that is `APPROVED`, `FILLING` or `FILL_HOLD` records its current status in `state_before_suspension`, stamps a `suspension_reason`, and moves to `SUSPENDED`; its `fill_percent_current` and `hold_started_at_utc` are preserved untouched, so the hold clock is never restarted. Second, each newly suspended plan cancels its reserved withdrawal windows in `created_at` order with `cancellation_reason` set to `PLAN_SUSPENDED`, and each cancellation returns that window's `reserved_volume_gal` to its water source. Third, when the posture later returns to `OPEN`, every suspended plan of the tank is restored to the status recorded in `state_before_suspension`, and both `state_before_suspension` and `suspension_reason` are cleared to null. Compensation is deliberately partial: the plan comes back, but the cancelled withdrawal windows are **not** resurrected and must be reserved again explicitly.

Posture also acts as a gate, at two different strictnesses. A `FROZEN` tank accepts no production work at all — no course fit-up, no weld log, no plate allocation, no fill advance, no coating step, no appurtenance installation, no operator phase transition, no hydrostatic plan approval and no commissioning submission — and any such attempt is rejected with `ERR_TANK_POSTURE_FROZEN` (HTTP 409). Only the operations that can *close* a nonconformance remain available on a frozen tank: reporting examination results, voiding examination reports, recording settlement surveys, and welder qualification actions. A second, stricter gate applies to four operations that additionally require a completely clean tank: hydrostatic plan approval, fill advance, commissioning submission and commissioning review. Those four require `quality_posture` to be exactly `OPEN`; `RESTRICTED` is sufficient for ordinary erection work but not for these, and an attempt made while the posture is `RESTRICTED` is rejected with `ERR_TANK_POSTURE_RESTRICTED` (HTTP 409).

### 2.9. Segregation of Duties

Three pairs of steps in this system must be performed by two different people, and in each pair the server has already recorded who performed the first step. First, the `QcInspector` who reports an examination result must not be the operator recorded in the seam welder's `qualified_by_user_id` — that is, the inspector who witnessed and recorded that welder's qualification may not then judge that welder's radiographs. Second, the `AuthorizedInspector` who records a hydrostatic test completion decision must not be the operator recorded in the plan's `approved_by_user_id`. Third, the `AuthorizedInspector` who reviews a commissioning package must not be the operator recorded in the package's `submitted_by_user_id`. In all three cases the comparison is between the acting `X-User-ID` and the stored value, and a collision is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.10. Order of Rejection

When a request violates more than one rule, the response is determined by the **first** violated rule in the ordering below; later violations are never reported. The ordering is fixed and is part of the contract.

Authentication and authorisation come first, in three steps: header presence (`ERR_UNAUTHENTICATED`), then role validity and endpoint authorisation (`ERR_FORBIDDEN_ROLE`), then — on a weld log only — the welder-identity match (`ERR_WELDER_IDENTITY_MISMATCH`). Fourth comes resolution of path identifiers, left to right, using the mapping in §2.4. Fifth comes request shape: every required input field present, every enum field carrying a declared value, numeric fields numeric and inside their declared ranges (weights, volumes, rates and thicknesses non-negative; `fill_percent` between 0 and 100 inclusive; `coverage_pct` greater than 0 and at most 100; `indication_count` and `film_count` non-negative integers), datetime fields parseable as ISO-8601 UTC instants, required arrays non-empty — this covers `point_readings`, `spot_readings` and `qualified_positions` — and every spot inside `spot_readings` carrying exactly three numeric gauge readings. A shape violation yields `ERR_INVALID_REQUEST` (HTTP 400). Unknown fields in a body are ignored rather than rejected. Sixth comes resolution of foreign keys supplied in the body, in the order the endpoint declares its inputs, using the same mapping. Seventh and eighth come the two optimistic-concurrency guards of §2.6: `expected_tank_version` on hydrostatic plan creation, then `expected_water_source_version` on withdrawal reservation.

Ninth through twenty-second come the state-machine gates, one per resource family, in this order: the operator phase transition (`ERR_PHASE_TRANSITION_INVALID`); foundation acceptance (`ERR_FOUNDATION_STATE_INVALID`); plate lot status transitions (`ERR_PLATE_LOT_STATE_INVALID`); plate allocation and allocation release (`ERR_ALLOCATION_STATE_INVALID`); course fit-up (`ERR_COURSE_STATE_INVALID`); weld logging (`ERR_SEAM_NOT_WELDABLE`); repair start (`ERR_SEAM_STATE_INVALID`); examination scheduling, result and void (`ERR_NDE_STATE_INVALID`); welder qualification actions (`ERR_WELDER_STATE_INVALID`); hydrostatic plan approval, fill advance and completion (`ERR_PLAN_STATE_INVALID`); withdrawal cancellation (`ERR_WITHDRAWAL_STATE_INVALID`); coating steps (`ERR_COATING_STEP_INVALID`); appurtenance installation (`ERR_APPURTENANCE_STATE_INVALID`); and commissioning documents, submission and review (`ERR_PACKAGE_STATE_INVALID`). All fourteen carry HTTP 409.

Twenty-third and twenty-fourth come the two posture gates of §2.8, frozen before restricted. Then come the safety checks, in this order: welder qualification currency (`ERR_WELDER_NOT_QUALIFIED`), then qualified thickness range (`ERR_THICKNESS_OUT_OF_QUALIFIED_RANGE`), then achieved surface preparation grade (`ERR_SURFACE_PREP_DEFICIENT`), then dew-point spread (`ERR_DEW_POINT_SPREAD_INSUFFICIENT`), then holiday-test voltage (`ERR_HOLIDAY_TEST_VOLTAGE_LOW`), then the dry-film verdict gate on acceptance (`ERR_DFT_NOT_PASSED`), then segregation of duties (`ERR_SEGREGATION_OF_DUTIES`). Note that segregation of duties is evaluated *after* the state gates and the posture gates, so an examination result recorded by the wrong operator on a report that is not scheduled reports the state error, not the duties error.

Next come the referential checks: same-tank agreement between every entity referenced in one request (`ERR_CROSS_TANK_REFERENCE`), then the accepted-foundation precondition for fit-up and weld logging (`ERR_FOUNDATION_NOT_ACCEPTED`), then the host-course acceptance precondition for appurtenance installation (`ERR_HOST_COURSE_NOT_ACCEPTED`), then the all-appurtenances-installed precondition for commissioning submission (`ERR_APPURTENANCES_NOT_INSTALLED`).

Then come the constraint checks, in this order: weld sequence honoured (`ERR_WELD_SEQUENCE_VIOLATION`), predecessor chain acyclic (`ERR_SEAM_SEQUENCE_CYCLE`), scoped uniqueness (`ERR_DUPLICATE_IDENTIFIER`), singleton packages (`ERR_SINGLETON_EXISTS`), survey point completeness (`ERR_INSUFFICIENT_SURVEY_POINTS`), appurtenance clearance (`ERR_APPURTENANCE_CLEARANCE_VIOLATION`), commissioning document completeness (`ERR_MISSING_COMMISSIONING_DOCUMENTS`), fill level strictly advancing (`ERR_FILL_PERCENT_NOT_ADVANCING`), mandatory settlement hold points (`ERR_SETTLEMENT_HOLD_POINT_MISSING`), and the repair-cycle cap (`ERR_REPAIR_LIMIT_EXCEEDED`).

The temporal checks follow: window ordering (`ERR_INVALID_WINDOW`), radiographic window exclusivity (`ERR_EXAM_WINDOW_CONFLICT`), water permit currency (`ERR_WATER_PERMIT_EXPIRED`), hold-period elapse (`ERR_HOLD_PERIOD_NOT_ELAPSED`), and concurrent withdrawal rate capacity (`ERR_WITHDRAWAL_CAPACITY_CONFLICT`). The fiscal checks follow those: permitted volume not oversubscribed (`ERR_PERMITTED_VOLUME_EXCEEDED`), then plate weight not over-allocated (`ERR_PLATE_WEIGHT_EXCEEDED`). Last of all come two checks that are deliberately placed at the bottom of the order: the agreement between an examination decision and its film evidence (`ERR_INDICATION_COUNT_INCONSISTENT`), and the shell-course thickness adequacy gate on fit-up (`ERR_COURSE_THICKNESS_DEFICIENT`). Because thickness adequacy sits below the fit-up state gate, a repeat fit-up on an already fitted course reports the state error rather than the thickness error even when the course is also deficient.

## 3. Business Logic & Workflows

### 3.1. Registering a Tank Design

A project begins when a `ProjectEngineer` registers the tank design. The payload names the owner's identifier for the tank in `tank_tag`, a string of 1 to 32 characters that must be unique across every tank in the system — a repeat is rejected with `ERR_DUPLICATE_IDENTIFIER`. The governing design standard is supplied as `design_standard`, one of `API_650_BASIC`, `API_650_ANNEX_A` or `API_620`, and defaults to `API_650_BASIC` when the field is omitted. Geometry arrives as `diameter_ft` and `shell_height_ft`, both strictly greater than zero, together with `design_liquid_level_ft`, which must be strictly greater than zero and no greater than `shell_height_ft` — a tank cannot be designed to be filled above its own shell. The stored product's `product_specific_gravity` must be at least 0.5 and at most 2.0. The weld joint efficiency, supplied as `joint_efficiency`, is one of exactly three values — `0.70`, `0.85` or `1.00` — and `corrosion_allowance_in` must be zero or positive, defaulting to 0.0625 inches (one sixteenth of an inch) when omitted. Roof configuration arrives as `roof_type`, one of `CONE_SUPPORTED`, `CONE_SELF_SUPPORTING`, `DOME_SELF_SUPPORTING`, `EXTERNAL_FLOATING` or `INTERNAL_FLOATING`, defaulting to `CONE_SUPPORTED`; it is carried purely for the commissioning record and gates nothing.

Three further inputs describe the tank bottom and are used only years later, when the in-service inspection schedule is computed. `bottom_thickness_in` is the as-built bottom plate thickness and must be positive. `bottom_minimum_thickness_in` is the retirement thickness and must be positive and strictly less than `bottom_thickness_in`. `assumed_corrosion_rate_ipy` is the assumed bottom corrosion rate in inches per year and must be positive.

Registration derives one value immediately. `min_nominal_thickness_in` is the minimum nominal shell plate thickness the standard imposes on a tank of this diameter, selected on `diameter_ft` in four bands: below 50 feet the floor is 0.188 inches; from 50 feet up to but not including 120 feet it is 0.250 inches; from 120 feet up to but not including 200 feet it is 0.313 inches; and at 200 feet and above it is 0.375 inches. The new tank is created with `construction_phase` at `DESIGN_REGISTERED`, `quality_posture` at `OPEN`, `open_nonconformance_count` at 0, `weld_reject_rate` at 0.0, `required_examination_pct` at 10.0 (the base radiographic examination percentage before any escalation), both `steel_received_lb` and `steel_allocated_lb` at 0.0, `active_hydrotest_plan_id` null, and `version` at 1.

A dedicated progress read returns a flat computed snapshot of the tank rather than the stored row. It reports `tank_id`, `construction_phase`, `quality_posture` and `open_nonconformance_count`; the course tallies `course_count` and `rt_accepted_course_count`; the seam tallies `seam_count`, `welded_seam_count` and `rt_accepted_seam_count`; the examination figures `weld_reject_rate` and `required_examination_pct`; the steel figures `steel_received_lb`, `steel_allocated_lb` and `steel_remaining_lb`; the pointer `active_hydrotest_plan_id` alongside `total_hydrotest_cost_usd`; and the appurtenance tallies `installed_appurtenance_count` and `designed_appurtenance_count`. The latter pair deserves care: `designed_appurtenance_count` is the size of the tank's whole design set — every appurtenance row of the tank whatever its status — while `installed_appurtenance_count` counts only the subset already installed, so the two are equal exactly when the appurtenance scope is complete.

Advancing the tank to `SHELL_COMPLETE` is the one phase move a `ProjectEngineer` requests directly, supplying `target_phase` and optionally `remarks`; §2.7 states the gate and the rejection code, and every successful advance increments the tank's `version` by 1.

### 3.2. Foundation Coordination and Settlement Monitoring

The civil contractor owns the ground. A `CivilContractor` registers exactly one foundation package per tank — a second attempt for the same tank is rejected with `ERR_SINGLETON_EXISTS` — supplying the `tank_id` it belongs to, the `foundation_type` actually built (`RINGWALL_CONCRETE`, `CRUSHED_STONE_RINGWALL`, `EARTHEN_PAD` or `SLAB`), and optionally the surveyed `ringwall_top_elevation_ft` recorded for the civil handover, which defaults to 0.0. The package also fixes the tolerance regime the tank will be judged against for the rest of the project: `permitted_uniform_settlement_in` is the maximum allowed mean settlement across all monitoring points in inches and must be positive; `permitted_differential_ratio` expresses the allowed differential settlement as a fraction of the arc distance between adjacent monitoring points and must be positive and no greater than 0.05; `monitoring_point_count` is the number of equally spaced monitoring points around the circumference and must be at least 8 and an even number; and `settlement_evaluation_method` selects which of two differential metrics will decide each survey's verdict, either `COSINE_BEST_FIT` or `ADJACENT_PAIR`.

Creating the package freezes a tolerance envelope from that configuration and the parent tank's geometry. The arc distance between adjacent monitoring points, stored as `point_spacing_in`, is the tank circumference in inches divided by the number of monitoring points: take the mathematical constant pi (3.141592653589793), multiply by `diameter_ft`, multiply by the 12 inches in a foot, and divide by `monitoring_point_count`; the result is rounded half up to 4 decimal places. The allowable differential settlement, stored as `allowable_differential_in`, is `permitted_differential_ratio` multiplied by that spacing, rounded half up to 3 decimal places. The package is created with `status` at `PLANNED`, `baseline_survey_id` null, and `decided_by_user_id`, `decided_at_utc` and `decision_remarks` all null.

Every settlement survey round is shot by the `CivilContractor` and is immutable once recorded. A survey names its `foundation_package_id`, carries a `fill_percent` between 0 and 100 inclusive describing the tank fill level at the moment of measurement, and carries `point_readings` — an array of objects each holding a `point_index` of at least 1 and an `elevation_in` reading. The array must contain exactly as many entries as the package's `monitoring_point_count`, with `point_index` values running from 1 to that count and each value appearing exactly once; anything else is rejected with `ERR_INSUFFICIENT_SURVEY_POINTS`. An optional `measured_at_utc` records the instant of measurement and defaults to the logical clock's current value when omitted. During hydrostatic filling the survey also carries the `hydrotest_plan_id` it was taken for; for pre-test rounds that field is null. When a plan is named, it must belong to the same tank as the foundation package, or the request is rejected with `ERR_CROSS_TANK_REFERENCE`.

The first survey recorded against a package — the one taken while the package still has no `baseline_survey_id` — becomes the datum. Its `survey_role` is set to `BASELINE`, its `verdict` is set to `BASELINE`, its `uniform_settlement_in` is 0.000 by definition, the package's `baseline_survey_id` is pointed at the new survey, and the package moves `PLANNED → BASELINE_SET`. Every later survey on the package has `survey_role` `MONITORING` and is evaluated against that original baseline, matched point index to point index — never against the previous monitoring round.

Evaluation proceeds as follows, always processing the readings in ascending `point_index` order rather than in submission order. For each point, the settlement in inches is the baseline survey's elevation at that point index minus this survey's elevation at the same point index. `uniform_settlement_in` is the arithmetic mean of those per-point settlements. Two differential metrics are then computed and **both** are stored on every survey row. The first is the cosine-best-fit metric: for each point, take an angle equal to two times pi times the point index divided by the number of points; form a first coefficient as two divided by the number of points, multiplied by the sum over all points of the point's settlement times the cosine of that point's angle; form a second coefficient the same way using the sine of the angle; predict each point's settlement as the uniform settlement plus the first coefficient times the cosine of that point's angle plus the second coefficient times the sine of that point's angle; then take the largest absolute difference between an actual per-point settlement and its prediction. That largest deviation is `max_out_of_plane_in`. The second is the adjacent-pair metric: walk the points circularly so that the last point is compared against the first, take the absolute difference between each point's settlement and the next point's settlement, and keep the largest. That is `max_adjacent_differential_in`. Each of `uniform_settlement_in`, `max_out_of_plane_in` and `max_adjacent_differential_in` is rounded half up to 3 decimal places after the full-precision computation.

Which metric governs is the package's decision, not the survey's. Under `COSINE_BEST_FIT`, `governing_metric_in` takes the value of `max_out_of_plane_in`: smooth ovalling of the shell is treated as acceptable rigid-body distortion, so a settlement pattern that follows a cosine curve exactly scores 0.000 no matter how large the point-to-point steps are. Under `ADJACENT_PAIR`, `governing_metric_in` takes the value of `max_adjacent_differential_in`: every point-to-point step is charged in full, so the same readings a cosine fit accepts can exceed the envelope. The rounded governing metric is what is compared against the envelope. A monitoring survey's `verdict` is `WITHIN_TOLERANCE` when the governing metric is no greater than the package's `allowable_differential_in` **and** the uniform settlement is no greater than the package's `permitted_uniform_settlement_in`; otherwise it is `OUT_OF_TOLERANCE`. Both comparisons are inclusive — a reading landing exactly on an allowable value is within tolerance.

A survey's `nonconformance_state` starts at `NOT_APPLICABLE`, which is where a baseline survey and a within-tolerance monitoring survey stay. An `OUT_OF_TOLERANCE` monitoring survey instead moves to `OPEN`, which raises the tank's `open_nonconformance_count` and triggers the posture recomputation and the suspension cascade of §2.8 — suspending the tank's live hydrostatic test plan and releasing its water reservations. That nonconformance closes when a later survey on the same foundation package comes back `WITHIN_TOLERANCE` at a `fill_percent` greater than or equal to the open survey's own `fill_percent`: the earlier survey moves `OPEN → CLOSED_BY_SUPERSEDING_SURVEY`, its `superseded_by_survey_id` is pointed at the new survey, the tank's count is decremented, and a return to `OPEN` posture restores every suspended plan to its `state_before_suspension`. The cancelled withdrawal windows, as always, stay cancelled.

The `ProjectEngineer` — not the contractor who built it — records the acceptance decision, supplying a `decision` of either `ACCEPT` or `REJECT` plus optional `decision_remarks`. The package must be in `BASELINE_SET` and a baseline survey must exist; a decision recorded on a package in any other status, or a monitoring survey submitted before a baseline exists, is rejected with `ERR_FOUNDATION_STATE_INVALID`. The tank must also not be `FROZEN`. The two branches have deliberately different consequences. On `ACCEPT`, the package moves `BASELINE_SET → ACCEPTED` (a terminal status), `decided_by_user_id` and `decided_at_utc` are stamped from the acting operator and the logical clock, `decision_remarks` is stored, and the tank advances `DESIGN_REGISTERED → FOUNDATION_ACCEPTED` with its `version` incremented and `updated_at` refreshed. On `REJECT`, the package moves `BASELINE_SET → REJECTED`, `decided_by_user_id`, `decided_at_utc` and `decision_remarks` are stamped exactly as on the accept branch, the tank's `construction_phase` is left untouched at `DESIGN_REGISTERED`, and — the divergence that matters — `baseline_survey_id` is cleared back to null so that a fresh baseline can be shot after the civil rework. Shooting that fresh baseline, a survey at `fill_percent` 0 against a package whose `baseline_survey_id` is null, moves the package `REJECTED → BASELINE_SET` and puts the decision back in front of the engineer.

### 3.3. Plate Procurement, Receipt and the Steel Ledger

Steel is bought in lots. An `ErectionSuperintendent` registers a lot against the `tank_id` it was ordered for, recording the `mill_name` that rolled it, the `heat_number` carried on the material test report, the as-rolled `thickness_in` of every plate in the lot (strictly positive), the `plate_count` (at least 1), the `plate_weight_lb` of a single plate (strictly positive), and the contract price in `unit_cost_usd_per_lb` (strictly positive, recorded for procurement records only). An `mtr_number` may be supplied at registration but is usually not yet known. A new lot starts at `status` `ORDERED` with `received_weight_lb`, `allocated_weight_lb` and `remaining_weight_lb` all at 0.0 and `quarantine_reason` null.

The lot then walks a procurement chain, one step per request, each supplying a `target_status` and optionally `mtr_number`, `quarantine_reason` and `remarks`. From `ORDERED` the lot may go to `ROLLED`; from `ROLLED` to `SHIPPED`; from `SHIPPED` to `RECEIVED`; from `RECEIVED` to either `QUARANTINED` or `RELEASED`; and from `QUARANTINED` to `RELEASED`. A `target_status` that is not reachable from the lot's current status is rejected with `ERR_PLATE_LOT_STATE_INVALID`, and so is a move to `RECEIVED` or `RELEASED` that does not carry the required material test report number. Reaching `RECEIVED` requires `mtr_number` to be present in the body and stores it; reaching `RELEASED` from `QUARANTINED` requires `mtr_number` to be present in the body and **overwrites** the stored value with the corrected report number, while reaching `RELEASED` directly from `RECEIVED` requires only that the lot already has a non-null `mtr_number`. Quarantine is available only while the lot holds no allocations at all — its `allocated_weight_lb` must be exactly 0.0 — and stores the reason on `quarantine_reason`, taken from the `quarantine_reason` field when the caller supplies it and otherwise from `remarks`.

Receipt is the moment steel enters the ledger. On reaching `RECEIVED`, the lot's `received_weight_lb` is set once and for all to `plate_count` multiplied by `plate_weight_lb`, and its `remaining_weight_lb` is set to the same figure because nothing has yet been allocated. The parent tank's `steel_received_lb` is then recomputed as the sum of `received_weight_lb` over every lot of the tank whose status is `RECEIVED`, `RELEASED` or `QUARANTINED`. Quarantine deliberately does **not** roll that back: quarantined steel is physically on site but contractually unavailable, so it continues to count toward `steel_received_lb` while being barred from allocation.

Allocation charges plate weight from one lot to one shell course. The request names the `shell_course_id` and the `allocated_weight_lb` to charge, and returns the updated shell course. The lot must be `RECEIVED` or `RELEASED` — a `QUARANTINED` lot may not be allocated — and the target course's `allocation_status` must still be `UNALLOCATED`; either violation is rejected with `ERR_ALLOCATION_STATE_INVALID`. The course must belong to the same tank as the lot, or the request is rejected with `ERR_CROSS_TANK_REFERENCE`. The requested weight may not exceed the lot's `remaining_weight_lb`; a weight exactly equal to the remaining figure is accepted, and anything above it is rejected with `ERR_PLATE_WEIGHT_EXCEEDED`. On success the course records `allocated_plate_lot_id` and `allocated_weight_lb` and moves its `allocation_status` to `ALLOCATED`.

Releasing an allocation hands the steel back. The request carries a `reason`, clears the course's `allocated_plate_lot_id` and resets its `allocated_weight_lb` to 0.0, and moves `allocation_status` back to `UNALLOCATED`. A release is permitted only while the course still holds an allocation and its own `status` is still `SPECIFIED` — once a course has been fitted up its steel is committed — and a release that fails either condition is rejected with `ERR_ALLOCATION_STATE_INVALID`.

All three of those writes — receipt, allocation and release — re-derive the whole steel ledger rather than adjusting it incrementally. A lot's `allocated_weight_lb` is the sum of `allocated_weight_lb` over every shell course whose `allocated_plate_lot_id` points at that lot and whose `allocation_status` is `ALLOCATED`; its `remaining_weight_lb` is its `received_weight_lb` less that allocated figure and is never permitted to fall below 0.0. The tank's `steel_allocated_lb` is the sum of `allocated_weight_lb` over every lot of the tank. Every weight is carried to 2 decimal places, rounded half up. One conservation identity must hold after each of the three writes: the tank's `steel_received_lb` minus its `steel_allocated_lb` equals the sum of `remaining_weight_lb` across every lot of the tank. A release therefore reconciles the lot's remaining weight and the tank's allocated total back to exactly their pre-allocation values.

### 3.4. Shell Course Specification, Thickness Adequacy and Fit-Up

A `ProjectEngineer` specifies the shell one course at a time. Each course names its `tank_id` and a `course_number` of at least 1, where 1 is the bottom course and courses stack upward in ascending order; the number must be unique within its tank, and a repeat is rejected with `ERR_DUPLICATE_IDENTIFIER`. The course carries its vertical `course_width_ft` in feet and the ordered nominal `plate_thickness_in`, both strictly positive, the plate `material_spec` (for example `A36` or `A516-70`), and two allowable stresses in pounds per square inch, both strictly positive: `allowable_stress_design_psi` for the design condition and `allowable_stress_test_psi` for the hydrostatic test condition.

Specifying a course runs the one-foot-method thickness calculation, whose whole point is that a course must satisfy **two different loading cases and a flat minimum**, and that the operator finds out which of the three governs. First the geometry: the course's `course_bottom_elevation_ft` is the sum of `course_width_ft` over every course of the same tank with a lower `course_number`, taken in ascending order, so the bottom course sits at elevation 0. Courses of other tanks never contribute. The course's `design_liquid_height_ft` is then the tank's `design_liquid_level_ft` less that bottom elevation — the head of liquid standing above the bottom of this particular course.

Both thickness variants are evaluated one foot above the bottom of the course, so both use the design liquid height reduced by one foot. The design-condition thickness, `required_thickness_design_in`, is the one-foot-method coefficient 2.6, multiplied by the design liquid height less one foot, multiplied by the tank's `diameter_ft`, multiplied by the tank's `product_specific_gravity`, all divided by the product of `allowable_stress_design_psi` and the tank's `joint_efficiency`, and then with the tank's `corrosion_allowance_in` added on. The hydrostatic-test-condition thickness, `required_thickness_test_in`, is the same coefficient 2.6, multiplied by the design liquid height less one foot, multiplied by `diameter_ft`, divided by the product of `allowable_stress_test_psi` and `joint_efficiency` — with no specific gravity term, because the test medium is water, and with **no corrosion allowance added**. That asymmetry is deliberate: the corrosion allowance belongs to the design case only and never to the test case.

Each of `required_thickness_design_in` and `required_thickness_test_in` is rounded half up to 3 decimal places *before* anything is compared. The governing requirement, `required_thickness_in`, is the largest of three candidates: the rounded design-condition thickness, the rounded test-condition thickness, and the tank's `min_nominal_thickness_in` diameter floor from §3.1; it too is expressed to 3 decimal places. `governing_case` records which candidate produced it — `DESIGN`, `TEST` or `MIN_NOMINAL` — and ties are broken in exactly that order, so `DESIGN` wins a tie against `TEST` and `TEST` wins a tie against `MIN_NOMINAL`. Finally, `thickness_verdict` is `ADEQUATE` when the ordered `plate_thickness_in` is greater than or equal to `required_thickness_in`, and `DEFICIENT` otherwise. Because the elevation stack of a course depends on the courses below it, adding a lower course re-evaluates the calculation for the courses whose elevation stack changed.

A course is created with `status` `SPECIFIED`, `allocation_status` `UNALLOCATED`, `allocated_plate_lot_id` null, `allocated_weight_lb` 0.0 and `fitup_at_utc` null. Fit-up is recorded in the field by an `ErectionSuperintendent` and takes no body fields at all. It requires the course to still be `SPECIFIED` — a course already `FITTED`, `WELDED` or `RT_ACCEPTED` cannot be fitted up again, and a repeat is rejected with `ERR_COURSE_STATE_INVALID`. It requires the tank's foundation package to have reached `ACCEPTED`, or the request is rejected with `ERR_FOUNDATION_NOT_ACCEPTED`. It requires the tank's `construction_phase` to be either `FOUNDATION_ACCEPTED` or `ERECTION_IN_PROGRESS`, and it requires the tank not to be `FROZEN`. And it requires the course's `thickness_verdict` to be `ADEQUATE`: a course whose ordered plate is thinner than the governing requirement may never be erected, and the attempt is rejected with `ERR_COURSE_THICKNESS_DEFICIENT`. That thickness gate is evaluated after the status gate, which is why a repeat fit-up on an already-fitted deficient course still reports the state error. On success the course moves `SPECIFIED → FITTED`, `fitup_at_utc` is stamped from the logical clock, and — on the first successful fit-up anywhere on the tank — the tank advances `FOUNDATION_ACCEPTED → ERECTION_IN_PROGRESS` with its `version` incremented.

After fit-up a course's `status` stops being something anyone sets and becomes a pure function of its weld seams, re-derived on every seam status change. The course is `RT_ACCEPTED` when it has at least one seam and every one of its seams is `RT_ACCEPTED`. It is `WELDED` when every one of its seams is `WELDED`, `EXAM_SCHEDULED` or `RT_ACCEPTED` and at least one seam is not yet `RT_ACCEPTED`. It is `FITTED` in every other case — that is, whenever any seam is `FIT_READY`, `RT_REJECTED`, `REPAIR_IN_PROGRESS` or `REPLACEMENT_REQUIRED`, and also while the course has no seams at all. Two of those re-derivations reach further than the course itself. A course falling out of `RT_ACCEPTED` back to `WELDED`, because a fresh examination was scheduled on an already accepted seam, also reverts the tank `SHELL_COMPLETE → ERECTION_IN_PROGRESS` when the tank had reached `SHELL_COMPLETE`; and a course falling from `RT_ACCEPTED` to `FITTED`, because a seam was rejected, does the same. A course falling from `WELDED` to `FITTED` changes only the course.

### 3.5. Welder Qualification, Field Welding and the Repair Loop

Welders are entered onto the project by the `AuthorizedInspector` who has just witnessed their performance qualification test, and they are created already qualified. The record carries the `welder_stamp` the welder marks on every seam — unique across every welder in the system, a repeat being rejected with `ERR_DUPLICATE_IDENTIFIER` — the `full_name` printed on the performance qualification record, the `process` the qualification covers (`SMAW`, `SAW`, `FCAW` or `GTAW`), and a non-empty `qualified_positions` array of position codes such as `3G` or `4G`. Two independent thickness ceilings are recorded: `welder_qualified_thickness_max_in`, the maximum base-metal thickness the welder's own performance qualification covers, and `wps_qualified_thickness_max_in`, the maximum thickness the referenced welding procedure specification is itself qualified for; the procedure is identified by `wps_number`. Both ceilings must be strictly positive. `qualification_date_utc` is the instant the test was witnessed, and `continuity_limit_days` — the number of days the qualification survives without further welding — must be at least 1 and defaults to 180.

On creation the welder's `qualification_status` is `QUALIFIED`, `last_weld_date_utc` is set to `qualification_date_utc`, `continuity_expires_at_utc` is that base date advanced by `continuity_limit_days` days and is held to the second, `revoked_at_utc` is null, and `qualified_by_user_id` records the acting inspector's `X-User-ID`. That last field is what later bars the same person from judging this welder's radiographs, as §2.9 describes.

Continuity decays on a clock, not on a schedule. Whenever the system consults a welder's qualification — on any read of that welder, on any list that includes them, and on every attempt to log a weld under them — it re-evaluates the status against the logical clock. A welder who has been revoked stays `REVOKED`; otherwise, a welder whose `continuity_expires_at_utc` is strictly before the logical clock moves `QUALIFIED → LAPSED`, and a welder whose expiry has not yet been passed remains `QUALIFIED`. The boundary is inclusive in the welder's favour: exactly at `continuity_expires_at_utc` the welder is still `QUALIFIED`, and one second later they are `LAPSED`. Every production weld resets the decay curve — the welder stays `QUALIFIED`, `last_weld_date_utc` is moved forward to the instant of that weld, and `continuity_expires_at_utc` is recomputed as the new base date plus `continuity_limit_days`.

The `AuthorizedInspector` may also act on a qualification directly, supplying an `action` of `RENEW` or `REVOKE` together with optional `effective_date_utc` and `remarks`. `RENEW` is available only from `LAPSED`: the welder returns to `QUALIFIED`, `last_weld_date_utc` is reset to `effective_date_utc` when that field is supplied and otherwise to the logical clock, `continuity_expires_at_utc` is recomputed from the new base date plus `continuity_limit_days`, and `qualification_date_utc` is deliberately **not** changed — the original performance-test date is part of the permanent record. `REVOKE` is available from either `QUALIFIED` or `LAPSED` and drives the welder to the terminal `REVOKED` status with `revoked_at_utc` stamped from the logical clock; seams the welder has already completed keep their status, because revocation is not retroactive. A `RENEW` requested on a welder who is not `LAPSED`, and any action at all requested on a `REVOKED` welder, is rejected with `ERR_WELDER_STATE_INVALID`.

Seams are declared by the `ErectionSuperintendent` before anyone welds them. A seam names its `shell_course_id` and its `seam_type` — `VERTICAL` for a course butt joint, `HORIZONTAL` for a course-to-course girth joint — carries the field mark in `seam_label`, its `length_in` in inches (strictly positive, and what sets expectations for the radiographic film count), and a `sequence_index` of at least 1 giving its position in the distortion-control weld sequence for its course. Both `seam_label` and `sequence_index` must be unique within the host course, and a collision on either is rejected with `ERR_DUPLICATE_IDENTIFIER`. A seam may optionally name a `predecessor_seam_id`, the self-referential link that enforces the weld sequence; sequence heads leave it null. The predecessor must belong to the same tank, or the request is rejected with `ERR_CROSS_TANK_REFERENCE`, and following the chain of predecessors must terminate at a seam with no predecessor — a chain that would close on itself is rejected with `ERR_SEAM_SEQUENCE_CYCLE`. New seams start at `status` `FIT_READY` with `repair_cycle_count` 0, `welder_id`, `filler_lot`, `welded_at_utc` and `last_nde_report_id` all null.

Logging a weld is the only write available to the `Welder` role. The body carries the acting welder's own `welder_id` — §2.1 covers the identity match — plus an optional `filler_lot` naming the consumable lot used and an optional `completed_at_utc`. Six gates stand in front of it. The seam must be `FIT_READY` or `REPAIR_IN_PROGRESS` and its host course must be `FITTED` or `WELDED`, or the attempt is rejected with `ERR_SEAM_NOT_WELDABLE`. The tank must not be `FROZEN`, and the tank's foundation package must already be `ACCEPTED` (`ERR_FOUNDATION_NOT_ACCEPTED`). The welder's `qualification_status`, re-evaluated against the logical clock as described above, must be `QUALIFIED`; a `LAPSED` or `REVOKED` welder may not weld and the attempt is rejected with `ERR_WELDER_NOT_QUALIFIED`. The host course's `plate_thickness_in` must fall within **both** thickness ceilings, meaning it must be no greater than the smaller of `welder_qualified_thickness_max_in` and `wps_qualified_thickness_max_in`; the comparison is inclusive at that binding limit and a breach is rejected with `ERR_THICKNESS_OUT_OF_QUALIFIED_RANGE`. And where the seam has a `predecessor_seam_id`, that predecessor must already have reached `RT_ACCEPTED`, because distortion control depends on the sequence being honoured; welding out of sequence is rejected with `ERR_WELD_SEQUENCE_VIOLATION`.

On success the seam moves to `WELDED` — either `FIT_READY → WELDED` for a first weld or `REPAIR_IN_PROGRESS → WELDED` for a re-weld after excavation, in which case `repair_cycle_count` is incremented by 1. `welder_id` and `filler_lot` are recorded (both overwritten on each repair re-weld), and `welded_at_utc` is set to `completed_at_utc` when supplied and otherwise to the logical clock. The welder's continuity is refreshed from that same instant, and the host course's `status` is re-derived from its seams — typically `FITTED → WELDED` once every sibling seam is welded or better.

A rejected seam is opened for repair by the `ErectionSuperintendent`, who supplies a `defect_disposition` and optional `remarks`. The seam must be `RT_REJECTED`, or the request is rejected with `ERR_SEAM_STATE_INVALID`; on success it moves `RT_REJECTED → REPAIR_IN_PROGRESS`, and the open rejection on the seam stays open until a fresh examination is accepted. The repair loop `FIT_READY → WELDED → EXAM_SCHEDULED → RT_REJECTED → REPAIR_IN_PROGRESS → WELDED` may be traversed at most twice: a rejection recorded while `repair_cycle_count` is already 2 sends the seam to the terminal `REPLACEMENT_REQUIRED` instead of `RT_REJECTED`, meaning the plate must be cut out and replaced. A seam in `REPLACEMENT_REQUIRED` accepts neither a further weld log nor a further repair start, and either attempt is rejected with `ERR_REPAIR_LIMIT_EXCEEDED`.

### 3.6. Radiographic Examination, Escalation and Voiding

Examinations are scheduled and reported by the `QcInspector`. Scheduling names the `weld_seam_id` under examination, the `method` (`RT` for radiography, or `UT`, `MT`, `PT` or `VT`), a closed examination window bounded by `window_start_utc` and `window_end_utc`, the `coverage_pct` of the seam length this examination covers (greater than 0 and at most 100), and the examining `technician_stamp`. The window end must be strictly after the window start, or the request is rejected with `ERR_INVALID_WINDOW`. The seam must be `WELDED` or `RT_ACCEPTED`, and the seam must not already have another report sitting in `SCHEDULED`; either violation is rejected with `ERR_NDE_STATE_INVALID`.

Radiography excludes every other trade from the shot area, so `RT` windows on a single tank are mutually exclusive with a 60-minute clearance buffer applied on each side. To test a proposed window, extend its start 60 minutes earlier and its end 60 minutes later, then look for any existing report on the same tank — across every shell course, not just this one — whose `method` is `RT`, whose `status` is `SCHEDULED`, `REPORTED_ACCEPT` or `REPORTED_REJECT`, and whose own window overlaps the buffered one. Overlap is judged on closed intervals: the buffered start being no later than the existing window's end, together with the existing window's start being no later than the buffered end, is a conflict — so buffered windows that merely touch **do** conflict. A conflict is rejected with `ERR_EXAM_WINDOW_CONFLICT`. The rule applies only when both the new and the existing report use `RT`; `UT`, `MT`, `PT` and `VT` examinations never conflict with anything, and a voided report frees its window entirely. Instants are compared to the second.

A new report is created at `status` `SCHEDULED` with `nonconformance_open` false, `reported_by_user_id` and `reported_at_utc` null, and `void_reason` null. The seam moves to `EXAM_SCHEDULED` and its `last_nde_report_id` is pointed at the new report. Scheduling on a seam that had already been accepted — the way an escalated examination percentage brings accepted seams back under the camera — therefore drives `RT_ACCEPTED → EXAM_SCHEDULED` on the seam, which in turn re-derives the host course `RT_ACCEPTED → WELDED`, which in turn reverts the tank `SHELL_COMPLETE → ERECTION_IN_PROGRESS` if the tank had got that far. Those three hops fire from a single scheduling request.

Reporting the result carries a `decision` of `ACCEPT` or `REJECT`, an `indication_count` of rejectable indications, a `film_count` of radiographs in the film set, and — on a rejection — a `defect_type` of `POROSITY`, `SLAG_INCLUSION`, `INCOMPLETE_PENETRATION`, `CRACK` or `UNDERCUT`. The decision must agree with the film evidence: `ACCEPT` requires `indication_count` to be exactly 0, and `REJECT` requires `indication_count` to be at least 1 **and** a `defect_type` to be present; a disagreement is rejected with `ERR_INDICATION_COUNT_INCONSISTENT`. The report must be `SCHEDULED` (`ERR_NDE_STATE_INVALID`), and the acting operator must not be the one recorded in `qualified_by_user_id` for the seam's welder (`ERR_SEGREGATION_OF_DUTIES`). On either decision, `reported_by_user_id` is stamped with the acting `X-User-ID` and `reported_at_utc` from the logical clock.

An acceptance moves the report `SCHEDULED → REPORTED_ACCEPT` and the seam `EXAM_SCHEDULED → RT_ACCEPTED`. Any earlier report on the same seam that still stands as an open rejection has its `nonconformance_open` set back to false, which is how a successful repair finally clears the seam's nonconformance. The host course's `status` is re-derived — `WELDED → RT_ACCEPTED` once every sibling seam is accepted — and the tank's `weld_reject_rate`, `required_examination_pct`, `open_nonconformance_count` and `quality_posture` are all recomputed.

A rejection moves the report `SCHEDULED → REPORTED_REJECT` with `nonconformance_open` set to true, and fires the longest cascade in the system, five links deep. First, the seam moves to `RT_REJECTED`, or straight to the terminal `REPLACEMENT_REQUIRED` when its `repair_cycle_count` has already reached 2. Second, that newly open rejection raises the tank's `open_nonconformance_count`, so `quality_posture` is recomputed. Third, a resulting `RESTRICTED` or `FROZEN` posture suspends every hydrostatic test plan of the tank sitting in `APPROVED`, `FILLING` or `FILL_HOLD`, each recording its `state_before_suspension`. Fourth, each newly suspended plan cancels its `RESERVED` withdrawal windows with `cancellation_reason` `PLAN_SUSPENDED`. Fifth, each cancelled window releases its `reserved_volume_gal` back into its source's `available_volume_gal`. Alongside that chain, the host course is re-derived to `FITTED` and the tank reverts `SHELL_COMPLETE → ERECTION_IN_PROGRESS` if it had reached `SHELL_COMPLETE`, and the reject rate and required examination percentage are recomputed.

Escalation of radiographic coverage is driven by the tank's own rejection history. Count the tank's examined population: every report whose `method` is `RT`, whose `status` is `REPORTED_ACCEPT` or `REPORTED_REJECT`, and whose seam belongs to this tank. Reports still `SCHEDULED` have not been examined yet and voided reports leave the population entirely. `weld_reject_rate` is 0.0 when that population is empty, and otherwise the count of rejected reports divided by the count of examined reports, rounded half up to 4 decimal places. `required_examination_pct` is then selected from the rounded rate in three bands: a rate of 0.50 or higher mandates 100.0 percent examination; a rate of at least 0.25 but below 0.50 mandates 50.0 percent; and a rate below 0.25 leaves the base 10.0 percent in force. The boundaries are inclusive from below, so a rate of exactly 0.2500 escalates to 50.0. Because voiding removes a report from the population, voiding a rejection can pull the rate back under a boundary and de-escalate the mandated percentage.

Voiding is the `AuthorizedInspector`'s compensating action and carries a single `void_reason`. It is available in exactly two situations. A report still `SCHEDULED` — a window that was never shot — moves `SCHEDULED → VOIDED`, and the seam falls back from `EXAM_SCHEDULED` to `WELDED`, or to `RT_ACCEPTED` when the seam had already been accepted before this re-examination was scheduled; the host course status is re-derived accordingly. A report that stands as an erroneous rejection may also be voided, but only while it is `REPORTED_REJECT` with `nonconformance_open` true **and** the seam is still `RT_REJECTED` — once a repair has started, the rejection can no longer be undone. That void moves the report `REPORTED_REJECT → VOIDED` with `nonconformance_open` set to false and `void_reason` stored, returns the seam `RT_REJECTED → WELDED` **without** incrementing `repair_cycle_count`, decrements the tank's `open_nonconformance_count` and recomputes `quality_posture` — a return to `OPEN` restoring every suspended plan of the tank to its `state_before_suspension` — and recomputes the reject rate and required examination percentage with this report excluded from the examined population. Every side effect of the rejection is reversed with no residual drift. A void attempted on a report that is neither `SCHEDULED` nor a still-open `REPORTED_REJECT` with its seam still `RT_REJECTED` is rejected with `ERR_NDE_STATE_INVALID`.

### 3.7. Water Sourcing, Hydrostatic Test Planning and Test Cost

Filling a field-erected tank with water is a permitted activity, and the permit — not the tank — is the scarce resource. A `ProjectEngineer` registers each permitted source under a `source_name` unique across every source in the system (a repeat being rejected with `ERR_DUPLICATE_IDENTIFIER`) and a `source_type` of `MUNICIPAL`, `RIVER`, `WELL` or `RECLAIMED`. The permit itself is described by `permitted_volume_gal`, the total volume the withdrawal permit allows in gallons, and `max_concurrent_rate_gpm`, the maximum aggregate withdrawal rate allowed at any single instant in gallons per minute; both must be strictly positive. Pricing arrives as `water_cost_usd_per_kgal`, the supply cost per thousand gallons, and `disposal_cost_usd_per_kgal`, the base disposal cost per thousand gallons before any volume-tier factor is applied; both may be zero but not negative. `permit_expiry_utc` is the instant the permit lapses. A new source starts with `reserved_volume_gal` and `consumed_volume_gal` at 0.0 and `available_volume_gal` equal to `permitted_volume_gal`.

Those three volume fields are a strict ledger, re-derived from the withdrawal rows rather than adjusted incrementally, and they span **every** hydrostatic test plan and every tank, because the permit belongs to the source and not to one tank. `reserved_volume_gal` is the sum of `reserved_volume_gal` over every withdrawal against the source whose `status` is `RESERVED`; `consumed_volume_gal` is the same sum over withdrawals whose `status` is `CONSUMED`; and `available_volume_gal` is `permitted_volume_gal` less both of those. Cancelled withdrawals contribute to none of the three. The identity that `permitted_volume_gal` equals `available_volume_gal` plus `reserved_volume_gal` plus `consumed_volume_gal` must hold after every hop, and every volume is carried to 2 decimal places rounded half up.

A hydrostatic test plan is created by a `ProjectEngineer` against a `tank_id` and the single `water_source_id` that all of the plan's withdrawals must draw from. It records `fill_volume_gal`, the water volume required to reach the design liquid level (strictly positive), the planned `disposal_method` for the test water (`DISCHARGE_TO_POTW`, `LAND_APPLICATION`, `HAUL_OFFSITE` or `REUSE_NEXT_TANK`), and `hold_hours`, the hold time at full level before the test may be signed off, which must be at least 24. The create also carries `expected_tank_version` as §2.6 requires. A new plan starts at `status` `DRAFT` with `fill_percent_current` 0.0, `settlement_survey_count` 0, `hold_started_at_utc`, `completed_at_utc`, `approved_by_user_id`, `state_before_suspension` and `suspension_reason` all null, and every cost field — `water_cost_usd`, `disposal_cost_usd`, `subtotal_usd`, `permit_surcharge_pct`, `surcharge_usd` and `total_cost_usd` — at 0.0.

Creating a plan supersedes whatever plan the tank already had in `DRAFT` or `REJECTED`: the older plan moves to the terminal `SUPERSEDED`, the new plan's `previous_plan_id` is pointed at it, and the tank's `version` is incremented by 1. A superseded plan that was still `DRAFT` also has its `RESERVED` withdrawal windows cancelled with `cancellation_reason` `PLAN_SUPERSEDED` and their volume released; a plan that was already `REJECTED` released its reservations at rejection time and has none left to release. `previous_plan_id` stays null for a tank's first plan.

Approval is recorded by a `ProjectEngineer` supplying a `decision` of `APPROVE` or `REJECT` plus optional `remarks`. The plan must be `DRAFT` and the parent tank must be in `construction_phase` `SHELL_COMPLETE`; a plan in any other status, or an approval requested at any other construction phase, is rejected with `ERR_PLAN_STATE_INVALID` — the plan-state gate and the tank-phase gate deliberately share one error identifier. Approval additionally requires the tank's posture to be exactly `OPEN`, and it requires the water source's `permit_expiry_utc` to be at or after the logical clock; an expired permit is rejected with `ERR_WATER_PERMIT_EXPIRED`. On `APPROVE` the plan moves `DRAFT → APPROVED`, `approved_by_user_id` records the acting `X-User-ID` (which then bars that operator from recording the completion decision), and the tank's `active_hydrotest_plan_id` is pointed at the plan. On `REJECT` the plan moves `DRAFT → REJECTED` and every `RESERVED` withdrawal of the plan is cancelled with `cancellation_reason` `PLAN_REJECTED`, each releasing its volume back to the source.

Withdrawal windows are reserved by the `ErectionSuperintendent`. Each reservation names the `hydrotest_plan_id` it serves and the `water_source_id` it draws from, which must be the same source the plan named — a mismatch is rejected with `ERR_CROSS_TANK_REFERENCE`. The window runs from `window_start_utc` to `window_end_utc` and is **half-open**: a window that starts exactly when another ends does not overlap it. The end must be strictly after the start (`ERR_INVALID_WINDOW`), and the source's `permit_expiry_utc` must be at or after `window_end_utc`, since a withdrawal may not run past the permit (`ERR_WATER_PERMIT_EXPIRED`). `rate_gpm` is the instantaneous withdrawal rate during the window and `reserved_volume_gal` is the volume reserved against the permit for it, both strictly positive, and the body carries `expected_water_source_version` as §2.6 requires.

Two capacity checks then apply. The rate envelope is evaluated by collecting every withdrawal against the **same** source whose `status` is `RESERVED` and whose window overlaps the proposed one under half-open semantics — that is, the existing window starts strictly before the proposed end and the proposed start is strictly before the existing end — and adding the proposed `rate_gpm` to the sum of the overlapping windows' rates. That peak figure, carried to 1 decimal place rounded half up, may not exceed the source's `max_concurrent_rate_gpm`; exactly at the ceiling the reservation is accepted, and above it the request is rejected with `ERR_WITHDRAWAL_CAPACITY_CONFLICT`. Cancelled and consumed windows consume no rate. Separately, the requested `reserved_volume_gal` may not exceed the source's current `available_volume_gal`; exactly equal is accepted, and oversubscribing the permit is rejected with `ERR_PERMITTED_VOLUME_EXCEEDED`. A withdrawal's `status` is one of `RESERVED`, `CONSUMED` or `CANCELLED`, and a new withdrawal starts at `RESERVED` with `cancellation_reason` null.

Each withdrawal is priced at the moment it is reserved. Its `withdrawal_cost_usd` is `reserved_volume_gal` divided by the 1,000 gallons in a thousand-gallon unit, multiplied by the source's `water_cost_usd_per_kgal`, rounded half up to 2 decimal places. The plan's `water_cost_usd` is then the **sum of those already-rounded per-withdrawal amounts**, taken over every withdrawal of the plan whose `status` is `RESERVED` or `CONSUMED`, processed in `created_at` order. That order is load-bearing: rounding each withdrawal first and summing the rounded amounts can differ by cents from rounding a single summed volume, and the former is correct. Cancelled withdrawals are excluded entirely.

Disposal is priced once, on the plan's aggregate volume. Sum `reserved_volume_gal` across the same input set and divide by 1,000 to obtain the plan's volume in thousands of gallons, then select a disposal multiplier from that figure: at or below 500 thousand gallons the multiplier is 1.00; above 500 and at or below 2,000 thousand gallons it is 0.85; and above 2,000 thousand gallons it is 0.70. `disposal_cost_usd` is the volume in thousands of gallons multiplied by `disposal_cost_usd_per_kgal` multiplied by that multiplier, rounded half up to 2 decimal places. `subtotal_usd` is `water_cost_usd` plus `disposal_cost_usd`.

The permit surcharge is then selected from the subtotal, and only from the subtotal, so that the surcharge is never compounded on itself. `permit_surcharge_pct` is 0.00 when `subtotal_usd` is below 1000.00, 0.03 when the subtotal is at least 1000.00 and below 2000.00, and 0.05 when the subtotal is 2000.00 or more; it is stored exactly as that two-decimal tier value. `surcharge_usd` is `subtotal_usd` multiplied by `permit_surcharge_pct`, rounded half up to 2 decimal places, and `total_cost_usd` is `subtotal_usd` plus `surcharge_usd`. The whole cost chain is recomputed on every withdrawal reservation and on every withdrawal cancellation, and it is frozen onto the plan when the plan passes. Because a cancellation removes a withdrawal from the input set, it lowers both cost components and can move the disposal tier and the surcharge tier downward.

A reserved window may be released by the `ErectionSuperintendent`, who supplies a `cancellation_reason`. The withdrawal must be `RESERVED`, or the request is rejected with `ERR_WITHDRAWAL_STATE_INVALID`. On success it moves `RESERVED → CANCELLED`, the reason is stored, the source's `reserved_volume_gal` falls and its `available_volume_gal` rises by the released `reserved_volume_gal`, the cancelled window stops participating in both the rate-overlap check and the permitted-volume check, and the owning plan's cost fields are recomputed with the withdrawal excluded. The system cancels windows the same way, and with the same ledger effect, when the owning plan becomes `SUSPENDED`, `REJECTED` or `SUPERSEDED`; those cascades stamp `cancellation_reason` as `PLAN_SUSPENDED`, `PLAN_REJECTED` or `PLAN_SUPERSEDED` respectively. Such cascades are conditional — only windows still `RESERVED` are touched, and already-cancelled rows are skipped.

Filling proceeds in stages, each requested by the `ErectionSuperintendent` with a `target_fill_percent` and, at hold points, a `settlement_survey_id`. The plan must be `APPROVED` or `FILLING` (`ERR_PLAN_STATE_INVALID`) and the tank's posture must be exactly `OPEN`. The target must be strictly greater than the plan's `fill_percent_current`; refilling to the same level or draining is not an advance and is rejected with `ERR_FILL_PERCENT_NOT_ADVANCING`. Four fill levels — 25, 50, 75 and 100 percent — are mandatory settlement hold points, and an advance to any of them must carry a `settlement_survey_id` whose survey belongs to the tank's foundation package, whose own `fill_percent` equals the requested `target_fill_percent`, and whose `verdict` is `WITHIN_TOLERANCE`; a missing or non-matching survey is rejected with `ERR_SETTLEMENT_HOLD_POINT_MISSING`. Each advance sets `fill_percent_current` to the target and increments `settlement_survey_count` by 1 whenever a survey is supplied. An advance from `APPROVED` with a target above 0 and below 100 moves the plan `APPROVED → FILLING`; a further advance below 100 keeps it `FILLING`; and an advance to exactly 100 moves it `FILLING → FILL_HOLD` and stamps `hold_started_at_utc` from the logical clock.

Completion is the `AuthorizedInspector`'s call, carrying a `decision` of `PASS` or `FAIL` plus optional `remarks`. The plan must be `FILL_HOLD` (`ERR_PLAN_STATE_INVALID`) and the acting operator must not be the plan's `approved_by_user_id` (`ERR_SEGREGATION_OF_DUTIES`). A `PASS` additionally requires that the hold period has elapsed — the logical clock at or after `hold_started_at_utc` advanced by `hold_hours` hours, a breach being rejected with `ERR_HOLD_PERIOD_NOT_ELAPSED` — and that `settlement_survey_count` has reached at least 4, so that all four mandatory hold-point surveys were actually taken; a shortfall is rejected with `ERR_SETTLEMENT_HOLD_POINT_MISSING`. A `FAIL` may be recorded at any point during the hold and is not subject to the hold-period check. `PASS` moves the plan `FILL_HOLD → PASSED` (terminal), stamps `completed_at_utc`, advances the tank `SHELL_COMPLETE → HYDROTEST_PASSED`, and freezes every cost field from the calculation above. `FAIL` moves the plan `FILL_HOLD → FAILED` (terminal), stamps `completed_at_utc`, clears the tank's `active_hydrotest_plan_id` to null, and counts as one open nonconformance so the tank's posture is recomputed and a previously clean tank becomes `RESTRICTED`. Either decision converts the plan's remaining `RESERVED` withdrawals to `CONSUMED`, which moves their volume out of the source's `reserved_volume_gal` and into its `consumed_volume_gal` while leaving `available_volume_gal` unchanged — consumption turns a reservation into a permanent draw against the permit.

Suspension does not destroy progress. When the tank's posture leaves `OPEN`, a plan in `APPROVED`, `FILLING` or `FILL_HOLD` moves to `SUSPENDED` with its prior status recorded in `state_before_suspension` and a `suspension_reason` stamped, while `fill_percent_current` and `hold_started_at_utc` are preserved untouched so the hold clock is never restarted. When the posture returns to `OPEN`, the plan returns to precisely the status in `state_before_suspension` — `SUSPENDED → APPROVED`, `SUSPENDED → FILLING` or `SUSPENDED → FILL_HOLD` — and `state_before_suspension` and `suspension_reason` are cleared to null; `fill_percent_current` and `hold_started_at_utc` come back unchanged. While a plan is `SUSPENDED`, and likewise once it is `SUPERSEDED`, `PASSED`, `FAILED` or `REJECTED`, it accepts no further action of any kind, and any attempt is rejected with `ERR_PLAN_STATE_INVALID`.

### 3.8. Coating, Lining and the Rework Cascade

A coating specification is issued by a `ProjectEngineer` against a `tank_id`. Its `scope` is either `INTERNAL_LINING` or `EXTERNAL_COATING` — a distinction that decides both whether a holiday-test voltage floor applies and, much later, which in-service external inspection interval the tank earns. The specification fixes `surface_area_sqft`, the coated area in square feet (strictly positive); `specified_prep_standard`, the surface-preparation grade the specification demands, one of `SSPC_SP5`, `SSPC_SP6` or `SSPC_SP10`; `specified_min_dft_mils`, the specified minimum dry film thickness in mils (strictly positive); `dft_acceptance_method`, which selects the acceptance variant and is either `SPOT_AVERAGE_80_120` or `INDIVIDUAL_GAUGE_MIN`; and a free-text `coating_system` such as an epoxy/polyurethane two-coat description. A tank may carry any number of applications, and each is independent. A new application opens at `status` `SPEC_ISSUED` with `achieved_prep_standard`, `profile_mils`, `dew_point_spread_f`, `holidays_found` and `holiday_test_voltage_v` all null, `spot_count` and `rework_cycle_count` at 0, every computed DFT aggregate at 0.0, and `dft_verdict` at `NOT_EVALUATED`.

Each application then walks a three-step cycle recorded entirely by the `QcInspector`: surface preparation, dry-film-thickness readings, holiday test. Every step checks that the application is in the state that step expects — `SPEC_ISSUED` or `REWORK_REQUIRED` for preparation, `PREP_ACCEPTED` for readings, `DFT_RECORDED` for the holiday test — and any step requested out of turn, including any step at all on a terminal `ACCEPTED` application, is rejected with `ERR_COATING_STEP_INVALID`.

Recording surface preparation supplies `achieved_prep_standard`, `profile_mils` (the measured anchor profile in mils) and `dew_point_spread_f` (the surface-temperature-minus-dew-point spread in degrees Fahrenheit at preparation time). Cleanliness grades are ordered `SSPC_SP3 < SSPC_SP6 < SSPC_SP10 < SSPC_SP5` — note that this is a cleanliness ranking and not a numeric one, so `SSPC_SP5` is the cleanest grade and `SSPC_SP3` the dirtiest, and `SSPC_SP3` is accepted only where the specification itself is `SSPC_SP3`, which the specification's own constraint never permits. The achieved grade must be at least as clean as the specified grade, equality being acceptable; a shortfall is rejected with `ERR_SURFACE_PREP_DEFICIENT`. The spread must be at least 5.0 degrees Fahrenheit, exactly 5.0 being acceptable, and a tighter spread risks condensation and is rejected with `ERR_DEW_POINT_SPREAD_INSUFFICIENT`. From `SPEC_ISSUED` the application moves to `PREP_ACCEPTED` and the three measurements are stored.

Readings arrive as `spot_readings`, an array of spots where each spot is itself an array of exactly three individual gauge readings in mils. The array must be non-empty and every spot must carry exactly three numeric readings; anything else is a shape failure rejected with `ERR_INVALID_REQUEST`. Each call **replaces** the previous measurement set rather than accumulating onto it, and every aggregate is recomputed from scratch over the submitted payload alone. `spot_count` is the number of spots. Each spot's average is the mean of its three readings, rounded half up to 2 decimal places, and those rounded per-spot averages — not their unrounded originals — are the values compared against the acceptance limits. `computed_spot_average_min_mils` and `computed_spot_average_max_mils` are the lowest and highest of those per-spot averages, `computed_overall_average_mils` is the mean of every individual gauge reading across every spot rounded half up to 2 decimal places, and `computed_min_gauge_reading_mils` is the single lowest gauge reading anywhere in the payload. The application then moves `PREP_ACCEPTED → DFT_RECORDED`. Because a second readings call from `DFT_RECORDED` is refused, the only route to a re-measurement is around the rework loop.

`dft_verdict` becomes `PASS` or `FAIL` according to whichever variant the application's `dft_acceptance_method` selected, and the two variants can disagree on the very same readings. Under `SPOT_AVERAGE_80_120` a `PASS` requires all three of: every per-spot average at or above 0.80 times `specified_min_dft_mils`; every per-spot average at or below 1.20 times `specified_min_dft_mils`; and `computed_overall_average_mils` at or above `specified_min_dft_mils`. This method is a band, not a floor — an application fails it for being too thick as well as too thin — and an individual gauge reading below specification is tolerated so long as its spot average holds up. Under `INDIVIDUAL_GAUGE_MIN` a `PASS` requires only two conditions, but stricter ones: `computed_min_gauge_reading_mils` at or above `specified_min_dft_mils`, and `computed_overall_average_mils` at or above `specified_min_dft_mils`. The 0.80 and 1.20 factors are not applied at all under this method, and no upper bound exists, so a very thick coating that `SPOT_AVERAGE_80_120` would reject passes here, while a set of readings with one thin outlier that `SPOT_AVERAGE_80_120` would accept fails here. Every comparison in both variants is inclusive at the limit.

The holiday test supplies `holidays_found`, the count of pinholes detected (a non-negative integer), and `test_voltage_v`, the voltage applied during detection, which is stored on the application as `holiday_test_voltage_v`. When the `scope` is `INTERNAL_LINING`, `test_voltage_v` must be at least 67.5 multiplied by `specified_min_dft_mils`, exactly at that floor being acceptable; below it the test is not probative and is rejected with `ERR_HOLIDAY_TEST_VOLTAGE_LOW`. An `EXTERNAL_COATING` scope has no voltage floor whatsoever. A test reporting zero holidays may only be accepted when `dft_verdict` is `PASS`; a `FAIL` verdict must be reworked no matter how clean the holiday test came back, and the attempt is rejected with `ERR_DFT_NOT_PASSED`. Note the asymmetry: that verdict gate applies only on the clean-test branch, so a test that finds holidays proceeds into rework whatever the verdict says. On a clean test with a passing verdict the application moves `DFT_RECORDED → ACCEPTED`, which is terminal.

Acceptance of the last outstanding application closes out the tank's coating work. When the tank has at least one coating application and every one of them is `ACCEPTED`, and the tank's posture is `OPEN`, the tank advances `HYDROTEST_PASSED → COATED` and its `version` is incremented by 1. A tank with no coating applications at all never reaches `COATED` on its own — the count-at-least-one condition is deliberate.

A holiday test that finds one or more holidays opens the four-link rework cascade, and each link fires within the same request. First, the application moves `DFT_RECORDED → REWORK_REQUIRED` with `holidays_found` and `holiday_test_voltage_v` stored. Second, the tank's posture is recomputed: an open coating rework counts as one nonconformance, so a previously `OPEN` tank becomes `RESTRICTED`. Third, if the tank had already been marked `COATED`, its `construction_phase` reverts `COATED → HYDROTEST_PASSED` and its `version` is incremented by 1 — a completed milestone is genuinely taken back. Fourth, any `SUBMITTED` commissioning package for that tank is returned: its `status` becomes `RETURNED_FOR_CORRECTION`, its `deficiency_count` is incremented by 1, and `next_internal_due_utc` and `next_external_due_utc` are cleared to null. That fourth link deliberately leaves `reviewed_by_user_id` untouched, because no inspector acted — the return was mechanical. Each link is conditional on its own precondition, so a tank that was never `COATED` skips link three and a tank with no submitted package skips link four.

Rework is closed by re-preparing the reworked area, which moves the application `REWORK_REQUIRED → PREP_ACCEPTED` under the same preparation-grade and dew-point checks as the first time. That step increments `rework_cycle_count` by 1, resets `dft_verdict` to `NOT_EVALUATED`, resets `spot_count` to 0 and every computed DFT aggregate to 0.0, and resets `holidays_found` and `holiday_test_voltage_v` to null — the previous cycle's evidence is discarded rather than kept alongside the new cycle's. The coating nonconformance closes at that moment, as soon as the rework re-enters preparation and before any new measurement proves anything, so the tank's posture is recomputed there and a tank whose only open nonconformance was this rework returns to `OPEN`. `rework_cycle_count` has no ceiling; the cycle `SPEC_ISSUED → PREP_ACCEPTED → DFT_RECORDED → REWORK_REQUIRED → PREP_ACCEPTED` may repeat indefinitely.

Coating steps are production work for the purpose of the posture gates, so none of the three may be recorded while the tank is `FROZEN`, and each is then rejected with `ERR_TANK_POSTURE_FROZEN`. `RESTRICTED` does not block them, which matters directly: a coating rework itself sets the tank to `RESTRICTED`, and if `RESTRICTED` blocked coating steps the rework could never be closed.

### 3.9. Appurtenances, Commissioning Documentation and the In-Service Schedule

Appurtenances are designed before they are installed. A `ProjectEngineer` places one against a `tank_id` and a `host_shell_course_id`, the course whose plate the penetration or attachment lands on, which must belong to the same tank or the request is rejected with `ERR_CROSS_TANK_REFERENCE`. The `appurtenance_type` is one of `NOZZLE`, `MANWAY`, `STAIRWAY`, `MIXER` or `ROOF_VENT`. `nominal_size_in` is the nominal size in inches, strictly positive, and selects the clearance tier. `elevation_ft` is the centerline elevation above the tank bottom in feet, zero or more. `azimuth_deg` is the circumferential position in degrees measured clockwise from north, at least 0 and strictly less than 360 — so 360 is never a legal azimuth and must be expressed as 0. `reinforcement_required` records whether the design calls for a reinforcing pad and defaults to `false` when omitted. The pair of `appurtenance_type` and `azimuth_deg` must be unique within the host shell course, a repeat being rejected with `ERR_DUPLICATE_IDENTIFIER`; two different types may share an azimuth, and the same type may recur at a different azimuth. A new appurtenance opens at `status` `DESIGNED` with `installed_at_utc` null.

The design call computes `required_clearance_deg`, the minimum angular separation this appurtenance demands from any other on the same course, from the type and the nominal size. For a `NOZZLE` or a `MANWAY` it is the greater of 8.0 degrees and `nominal_size_in` multiplied by 1.5, so small nozzles all sit at the 8.0-degree floor while a size above 5.333… inches begins to drive the requirement upward. A `STAIRWAY` requires 30.0 degrees, a `MIXER` 20.0 degrees, and a `ROOF_VENT` 5.0 degrees; those three are flat values and ignore `nominal_size_in` entirely. The result is rounded half up to 1 decimal place.

Installation is recorded by the `ErectionSuperintendent`, optionally supplying `installed_at_utc`; when omitted, the installation instant is taken from the logical clock. The appurtenance must be `DESIGNED`, or the request is rejected with `ERR_APPURTENANCE_STATE_INVALID`; the tank must not be `FROZEN`; and the host shell course must already be `RT_ACCEPTED`, since nobody cuts a hole in plate whose seams have not yet been radiographically accepted — a course in any other state is rejected with `ERR_HOST_COURSE_NOT_ACCEPTED`. This is a guarded transition whose gate lives on a different entity altogether.

The clash check then runs against every other appurtenance of the same tank that shares the same `host_shell_course_id` **and** is already `INSTALLED`. For each such neighbour, take the absolute difference of the two `azimuth_deg` values as a raw gap, and let the separation be the smaller of that raw gap and 360 minus that raw gap — the shell is a circle, so a pair at 355 and 5 degrees is 10 degrees apart, not 350. Compare that separation, rounded half up to 1 decimal place, against the larger of the two appurtenances' `required_clearance_deg` values: the pair is acceptable when the separation is at or above that requirement, and exactly at the limit the envelope is closed and the installation is accepted. A separation strictly below the requirement is rejected with `ERR_APPURTENANCE_CLEARANCE_VIOLATION`. The requirement is the maximum of the two, so a 5.0-degree roof vent still has to respect a 30.0-degree stairway's envelope. Because only `INSTALLED` neighbours participate, `DESIGNED` neighbours never clash, and installation order decides which of two mutually conflicting designs is the one that gets in. Appurtenances on different courses of the same tank never clash with one another, however close their azimuths. On success the appurtenance moves `DESIGNED → INSTALLED`, which is terminal, and `installed_at_utc` is stamped.

Commissioning documentation is a per-tank singleton. A `ProjectEngineer` opens exactly one package per `tank_id`; a second attempt is rejected with `ERR_SINGLETON_EXISTS`. The package fixes `required_document_types` as the four types every tank must produce — `MILL_TEST_REPORTS`, `RT_FILM_LOG`, `HYDROTEST_RECORD` and `AS_BUILT_DRAWING`, in that order — and opens with `submitted_document_types` empty, `missing_document_types` equal to all four in that same order, `document_count` and `deficiency_count` at 0, `status` `DRAFT`, `submitted_by_user_id` and `reviewed_by_user_id` null, and `bottom_remaining_life_years`, `internal_inspection_interval_years`, `external_inspection_interval_years`, `next_internal_due_utc`, `next_external_due_utc` and `accepted_at_utc` all null.

Documents are recorded one at a time by a `ProjectEngineer` with a `document_type` and a `reference_number`. Two further types beyond the required four are accepted — `COATING_REPORT` and `SETTLEMENT_LOG` — and they are optional: recording them is permitted but never required for submission. Any value outside those six is rejected with `ERR_INVALID_REQUEST`. Documents may only be attached while the package is `DRAFT` or `RETURNED_FOR_CORRECTION`; attaching to a `SUBMITTED` or `ACCEPTED` package is rejected with `ERR_PACKAGE_STATE_INVALID`. Every record increments `document_count`, duplicates included, so `document_count` is a count of documents and not a count of types. `submitted_document_types` holds the distinct types recorded, emitted in the required order first and then any extra types in the order they were first recorded, and `missing_document_types` is the required list minus the submitted types, preserving the required order. A second document of a type already present raises `document_count` but leaves `submitted_document_types` and `missing_document_types` untouched.

Submission is the `ProjectEngineer`'s act. The package must be `DRAFT` or `RETURNED_FOR_CORRECTION`, and the parent tank must be in `construction_phase` `COATED`; a submission from any other package status, or at any other construction phase, is rejected with `ERR_PACKAGE_STATE_INVALID`. `missing_document_types` must be empty, a shortfall being rejected with `ERR_MISSING_COMMISSIONING_DOCUMENTS`. Every appurtenance of the tank must be `INSTALLED`, any still `DESIGNED` causing rejection with `ERR_APPURTENANCES_NOT_INSTALLED`. The tank's posture must be exactly `OPEN`, so submission is one of the four operations that `RESTRICTED` blocks with `ERR_TANK_POSTURE_RESTRICTED`. On success the package moves `DRAFT → SUBMITTED`, or `RETURNED_FOR_CORRECTION → SUBMITTED` on a re-submission after correction, and `submitted_by_user_id` records the acting `X-User-ID`, overwriting any earlier value so that the operator barred from reviewing is always the one who submitted most recently. `deficiency_count` is never reset by a re-submission; it is a permanent tally of how many times the package was sent back.

Review is the `AuthorizedInspector`'s act, carrying a `decision` of `ACCEPT` or `RETURN` plus optional `remarks`. The package must be `SUBMITTED` (`ERR_PACKAGE_STATE_INVALID`) and the acting `X-User-ID` must differ from `submitted_by_user_id` (`ERR_SEGREGATION_OF_DUTIES`). Acceptance additionally requires the tank's posture to be exactly `OPEN` (`ERR_TANK_POSTURE_RESTRICTED`); a `RETURN` carries no posture requirement, since sending a package back is always safe. On `ACCEPT` the package moves `SUBMITTED → ACCEPTED`, which is terminal, `reviewed_by_user_id` records the acting operator, `accepted_at_utc` is stamped from the logical clock, the in-service schedule below is computed, and the tank advances `COATED → COMMISSIONED` — the terminal construction phase — with its `version` incremented by 1. On `RETURN` the package moves `SUBMITTED → RETURNED_FOR_CORRECTION`, `deficiency_count` is incremented by 1, and `reviewed_by_user_id` records the acting operator.

Acceptance is also where the tank's in-service inspection intervals are fixed. `bottom_remaining_life_years` is the tank's `bottom_thickness_in` less its `bottom_minimum_thickness_in`, divided by its `assumed_corrosion_rate_ipy`, rounded half up to 2 decimal places. `internal_inspection_interval_years` is the smaller of 20 and the floor of half that remaining life, taken as a whole number of years — the floor is applied after the two-decimal rounding, and the 20-year ceiling caps even a very thick bottom. `external_inspection_interval_years` is 5 when the tank has a coating application with `scope` `EXTERNAL_COATING` whose `status` is `ACCEPTED`, and 2 otherwise; an internal lining, however well it passed, earns nothing here. `next_internal_due_utc` is `accepted_at_utc` advanced by `internal_inspection_interval_years` whole years and `next_external_due_utc` is `accepted_at_utc` advanced by `external_inspection_interval_years` whole years, calendar arithmetic landing on the same month and day-of-month. Both due dates are anchored on `accepted_at_utc`, so a package returned and later re-accepted re-anchors the entire schedule at the new acceptance instant.

## 4. API Endpoint Reference

Every endpoint below is rooted at the API base path and takes both the `X-User-ID` and `X-User-Role` headers described in §2.1. A successful creation returns HTTP 201; every other successful call — reads, state transitions, decisions, cancellations and the clock control — returns HTTP 200. All responses, successful or not, use the envelope of §2.2, and the `data` field of a successful write carries the full created or updated resource with all of its computed fields recalculated. Failures use the error identifiers and status codes catalogued in §5, selected in the priority order of §2.10.

Each path parameter carries the `id` of the addressed resource: `tank_id`, `foundation_package_id`, `settlement_survey_id`, `plate_lot_id`, `shell_course_id`, `welder_id`, `weld_seam_id`, `nde_report_id`, `water_source_id`, `hydrotest_plan_id`, `water_withdrawal_id`, `coating_application_id`, `appurtenance_id` and `commissioning_package_id` respectively. Where a request body also carries one of those names it is a foreign key to that same entity, and both the path parameters and the body foreign keys are resolved with the not-found mapping of §2.10.
