# Gift Basket Gifting API — Product Requirements Document

## 1. Introduction

Corporate gift-giving has outgrown the shopping cart. A single onboarding season can mean a `CorporateAccount` sending hundreds of branded baskets to remote employees and clients across a dozen countries, each recipient expecting a personalized card, a perishable component that survives transit, and delivery timed to an occasion rather than a warehouse's convenience. Coordinating that volume manually — matching a spreadsheet of addresses to warehouse stock, catching a compliance problem in a printed logo before it ships, keeping a finance team's monthly ceiling from being blown out by an enthusiastic account manager — is exactly the kind of cross-department choreography that breaks down without a system of record.

This platform is that system of record. It carries a corporate customer from catalog browsing (`GiftBasketTemplate`, `ComponentSKU`) through bulk order construction and CSV recipient import, through a two-track approval process that pairs a spending-budget decision with a brand-compliance sign-off, into warehouse assembly and multi-zone shipping, and finally into optional recurring re-ordering. Two internal safety nets run underneath the whole flow: a segregation-of-duties rule that forbids the employee who requested a decision from also being the one who grants it, and a perishability ledger that refuses to let a basket be assembled from stock that will have spoiled by the scheduled day.

Consistency is immediate throughout — there is no eventually-settling background reconciliation; every state transition, cascade, and ledger adjustment described below is visible to the very next read. The remainder of this document is organized as global contract rules (§2), the scattered business narrative that a client engineer must piece together to build a conforming implementation (§3), the endpoint summary (§4), and the error catalogue (§5).

## 2. Global Specifications & System-Wide Principles

### 2.1 User and Role-Based Access Control

Every request is authenticated by two headers: `X-User-ID` and `X-User-Role`. Six role values are recognized: `PlatformAdmin`, `AccountManager`, `FinanceApprover`, `ProofApprover`, `WarehouseOps`, and `ShippingOps`. A request missing either header, or presenting an `X-User-Role` value outside this set, is rejected with `ERR_UNAUTHENTICATED` (401) before any other processing occurs. A request from an authenticated but unpermitted role for the target operation is rejected with `ERR_FORBIDDEN_ROLE` (403).

Five of the six roles carry an **opaque** identity. When `X-User-Role` is `PlatformAdmin`, `FinanceApprover`, `ProofApprover`, or `WarehouseOps` or `ShippingOps`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against an entity's `id`. The server may still record that opaque identifier on downstream data — for instance, a `FinanceApprover`'s `X-User-ID` ends up on `BudgetApproval.approver_user_id` after a budget decision, and a `ProofApprover`'s `X-User-ID` ends up on `MessageProof.decided_by_user_id` after a proof decision — but these are bookkeeping writes, not ownership checks.

The sixth role, `AccountManager`, is **entity-backed**: `X-User-ID` is the `id` of the acting `CorporateAccount`. Every ownership check on a resource that descends from a `CorporateAccount` — a `BrandingProfile`, a `CorporateOrder`, a `RecurringOrderSeries` — compares that resource's `corporate_account_id` foreign key against the caller's `X-User-ID`. Note that this account-level identity is distinct from the individual-employee identifiers `requested_by_user_id` and `submitted_by_user_id` carried as ordinary payload fields on specific operations (detailed in §2.8) — an `AccountManager` authenticates as its account, but separately names the individual staff member behind a given budget request or message submission.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3 Pagination

List endpoints accept `limit` and `offset` query parameters. `limit` defaults to 10 when omitted, and must be no smaller than 1 and no larger than 100. `offset` defaults to 0 when omitted and has no declared upper bound. Every list endpoint sorts its results by `created_at` in ascending order — oldest first — with no alternative sort offered. The response `meta` object for a list endpoint carries `limit`, `offset`, `total_count` (the number of matching rows across all pages), and `has_more` (whether a subsequent page exists beyond the returned slice).

### 2.4 Resource Identity, Timestamps, and Versioning

Every entity's `id` is a server-minted UUID with no type-prefix. `created_at` and `updated_at` are ISO 8601 UTC timestamps carrying three fractional digits, matching the `api_request_timestamp` format shown in §2.2. `version` is an integer that starts at 1 on creation and increments by exactly 1 on every mutating write to that row. Two entities are the exception to this rule: `AssemblyStation` and `ShippingZone` are configuration-only records that carry just `id` and `created_at` — they have no `updated_at` and no `version` field at all, because nothing in the scaffold ever mutates them after creation.

Version increments are not always confined to the entity being written. Creating a `BrandingProfile` under a `CorporateAccount`, creating a `CorporateOrder` under a `CorporateAccount`, and adjusting a `CorporateAccount`'s budget via its budget-update endpoint each increment `CorporateAccount.version` — even though the primary resource created or returned by the call is the `BrandingProfile` or `CorporateOrder`, not the account itself. Separately, editing a `GiftBasketTemplate`'s catalog price, composition, or `active` flag increments `GiftBasketTemplate.version` by 1; this is precisely the mechanism that lets a price change land between one order's submission and its later approval decision, discussed further in §2.6 and §3.4.

### 2.5 Optimistic Concurrency Control on Account-Scoped Writes

Two write paths are guarded by optimistic concurrency control against `CorporateAccount.version`, and both share the same rejection code and the same field-naming convention.

Creating a `BrandingProfile` (via the account's branding-profile creation endpoint) must carry `expected_corporate_account_version`, matching the target `CorporateAccount`'s current `version` at the instant of the write. If another writer has advanced the account's version since the client last read it — for example, because a different branding profile was already created for the account since then — the create is rejected with `ERR_STALE_VERSION` (HTTP 412), preventing the client from building a profile against a view of the account it no longer accurately reflects.

Creating a `CorporateOrder` (via the account's order creation endpoint) is guarded the identical way: the request body must carry `expected_corporate_account_version` matching the account's current `version`, and a mismatch is rejected with the same `ERR_STALE_VERSION` (HTTP 412). The scenario this protects against is a budget adjustment: if the account's monthly budget or approval threshold was just changed through the account's budget-update endpoint (which itself bumps `CorporateAccount.version`, per §2.4), an order-creation request holding a stale version number is proceeding against outdated affordability assumptions and is rejected rather than allowed to silently use the old policy. No other write endpoint in this API takes any `expected_<parent>_version` field — the two rules above are the complete set.

### 2.6 Pricing Precision and Rounding Discipline

All monetary fields in this system are integer cents, and every rounding operation in every calculation is round-half-up applied to whole cents — never truncation, never round-half-to-even. Where a calculation touches more than one intermediate value, the point at which rounding is applied is fixed and must not be reordered: the bulk-order discount (§3.4) is rounded exactly once, on the whole discounted subtotal, never per individual recipient row; the loyalty discount that finalizes `total_cost_cents` (§3.4) is rounded once on its own result before the rush fee is added on top, unrounded itself since it is already a whole-cent constant; and each shipment's cost (§3.7) is rounded independently at creation time, with any order-level shipping total formed by summing those already-rounded per-shipment figures rather than by summing raw fractional costs and rounding once at the end — the latter ordering would systematically understate the total whenever any shipment carries a fractional-cent remainder, and this scaffold forbids it.

### 2.7 Perishability and Inventory Ledger Principles

`GiftBasketTemplate` and `ComponentSKU` both carry an `is_perishable` flag; when `is_perishable` is true on either, a `shelf_life_days` value is required, expressing how many days from the record's creation the physical stock remains safe to use. On an `InventoryReservation`, `expires_at` is computed as the reservation's own `created_at` plus its `ComponentSKU`'s `shelf_life_days` — only for perishable SKUs; non-perishable reservations carry no expiry. `ComponentSKU.on_hand_qty` is the physical warehouse count and is only ever decremented when an `AssemblyTask` referencing that SKU reaches `COMPLETE` (units physically consumed); it is tracked independently of the reservation-status bookkeeping that determines availability for new reservations (§3.3, §3.6). Throughout the system, only reservations in `RESERVED` or `ALLOCATED` status compete for a SKU's available stock — reservations that have moved to `RELEASED`, `EXPIRED`, `ASSEMBLED`, or `CANCELLED` are excluded from that competing set, which is what makes cancellation and expiry effective compensations rather than permanent stock loss.

### 2.8 Segregation of Duties

Two independent pairs of fields enforce that the person who asks for a decision is never the person who makes it. On the budget-approval path, `BudgetApproval.requested_by_user_id` — populated from the `requested_by_user_id` supplied when the order was submitted for approval — must differ from the deciding `FinanceApprover`'s submitted `approver_user_id`; a match is rejected with `ERR_SELF_APPROVAL_FORBIDDEN` (403). On the gift-message-proofing path, `MessageProof.submitted_by_user_id` — populated from the `submitted_by_user_id` supplied when the message was submitted for proof — must differ from the deciding `ProofApprover`'s submitted `decided_by_user_id`; a match is rejected with `ERR_SELF_PROOF_APPROVAL_FORBIDDEN` (403). Both `requested_by_user_id` and `submitted_by_user_id` are opaque individual-employee identifiers distinct from the `AccountManager` account-level `X-User-ID` described in §2.1 — they identify the specific staff member behind a submission, not the corporate account as a whole.

The self-approval check has exactly one exception: when an order's total cost does not exceed its account's approval threshold, the system auto-fires its own approval with `approver_user_id` set to null and no human `FinanceApprover` involved at all — because there is no decider in that path, the segregation-of-duties comparison simply does not apply (§3.4).

### 2.9 Nested Resource Retrieval and Global Validation Ordering

Path parameters are validated left to right along the URL hierarchy, and each level's existence check must pass before evaluation proceeds to the next. Any endpoint mounted under an account (`/corporate-accounts/{id}/...`) or referencing a `corporate_account_id` in its body first confirms the named `CorporateAccount` exists, failing with `ERR_ACCOUNT_NOT_FOUND` (404) otherwise. Any endpoint mounted under an order (`/orders/{id}/...`) first confirms the named `CorporateOrder` exists, failing with `ERR_ORDER_NOT_FOUND` (404) otherwise. Any endpoint mounted under a recipient (`/recipients/{id}/...`) first confirms the named `Recipient` exists, failing with `ERR_RECIPIENT_NOT_FOUND` (404) otherwise. Deeper sub-resource path ids — on the assembly-task advance, shipment advance, message-proof fetch, message-proof decision, and recurring-series update operations — are checked for existence against `ERR_SUBRESOURCE_NOT_FOUND` (404).

Beyond path resolution, every request is evaluated against the full validation table in strict ascending priority order: header authentication failures surface before role-authorization failures, which surface before any not-found error for a referenced resource (accounts, orders, recipients, templates, branding profiles, SKUs, fulfillment references, and sub-resources), which surface before state-machine legality failures, which surface before business-safety and referential failures (perishable safety, chronological inventory sufficiency, branding approval, message-proof lock), which surface before business-constraint failures (self-approval, self-proof-approval, empty recipient list, all-rows-rejected imports, duplicate recipient email, forward-looking inventory sufficiency, assembly capacity), which surface before temporal failures (past scheduled-send dates, shipping blackout conflicts), which surface before the fiscal hard-cap failure. Endpoint-specific orderings within this framework — where several of these checks share a single endpoint — are called out where each workflow is discussed in §3.

## 3. Business Logic & Workflows

### 3.1 Catalog and Fulfillment Configuration

Before any corporate customer can order anything, a `PlatformAdmin` populates four catalog and fulfillment registries. A `GiftBasketTemplate` is created with a `name`, a merchandising `category` — one of `HOLIDAY`, `CORPORATE_WELCOME`, `CLIENT_APPRECIATION`, or `CUSTOM` — a `base_price_cents` that must be greater than zero, an `is_perishable` flag, and a `components` array. Each entry of `components` is an object naming a `sku_id` and a `quantity`, describing how many units of that `ComponentSKU` go into one basket of the template; every `sku_id` referenced this way is validated against an existing `ComponentSKU.id` at write time, and a reference to a SKU that does not exist is rejected with `ERR_SKU_NOT_FOUND` (404). When `is_perishable` is true, `shelf_life_days` is required — it has no meaningful default in that case. An `active` flag (defaulting to true) controls whether the template is currently orderable; a template that is not `active` cannot be used to start a new order (§3.4). Templates can later be revised through a dedicated update capability that accepts new values for `base_price_cents`, `active`, and `components`; every such edit increments `GiftBasketTemplate.version` by 1, which is precisely the mechanism that lets a mid-flight catalog price change cause an order's provisional and final cost figures to diverge (§2.4, §2.6, §3.4).

Registering warehouse stock is a separate call: a `ComponentSKU` is created with a `name`, a `unit_cost_cents` (informational only — it never enters customer-facing pricing), its own `is_perishable` flag and, when perishable, its own `shelf_life_days`, and an `on_hand_qty` that defaults to 0 and can never go negative. `on_hand_qty` behaves as the warehouse's physical ledger — it is untouched by reservation bookkeeping and only decreases when a basket referencing that SKU is physically assembled (§3.7).

Shipping is configured per `ShippingZone`: a `zone_code` label, the `country_codes` the zone serves, the `carrier` name, a flat `base_rate_cents`, a marginal `per_kg_rate_cents`, a fastest guaranteed `transit_days_min` and slowest guaranteed `transit_days_max`, and an optional list of `blackout_dates` — calendar days the carrier will not accept pickups in that zone. A recipient's `country_code` is only shippable once some `ShippingZone.country_codes` entry covers it. Separately, an `AssemblyStation` is registered with a `name` and a `daily_capacity` — the maximum total basket quantity, summed across every `AssemblyTask` scheduled there on one calendar day, that the station can produce (the constraint this enforces is detailed in §3.6).

Finally, the whole system runs against a logical clock rather than the wall clock, exposed to `PlatformAdmin` alone: the server starts at the fixed instant `2026-03-01T00:00:00Z` and only moves forward when a clock-advance call supplies a new `to_iso8601` value. That single call is also the trigger for two sweeps described in later sections: expiring perishable reservations past their shelf life (§3.3, §3.6) and generating the next order in any due recurring series (§3.9).

### 3.2 Corporate Account Onboarding and Budget Governance

A `PlatformAdmin` onboards a corporate customer by creating a `CorporateAccount` with a `name`, a `billing_email`, a `monthly_budget_cents` ceiling (greater than zero), and an `approval_threshold_cents` (zero or greater). The account's `status` field starts, and is expected to remain, `ACTIVE`; `SUSPENDED` is the only other recognized value of this enumeration in the current scaffold. `approval_threshold_cents` is the line an order's finalized cost must strictly exceed before a human `FinanceApprover` sign-off is required — at or below the threshold, the order auto-approves (the full mechanics are in §3.4).

`ytd_spend_cents` is a running total, maintained incrementally rather than recomputed from scratch on every read, of the `total_cost_cents` of every order that has become `APPROVED` within the current calendar month. It is zeroed automatically at the first mutation the system observes after the logical clock crosses into a new UTC calendar month — any instant from the first day's midnight through the last instant of the prior month counts as still belonging to that prior month. `ytd_spend_cents` only ever moves in two circumstances: it increases by an order's `total_cost_cents` the moment that order is approved, and it decreases by the same amount if that already-approved order is later cancelled (§3.9) — both legs share the same incremental, single-order-at-a-time update rule, never a full re-sum across all orders.

A dedicated budget-adjustment call, restricted to `PlatformAdmin`, lets `monthly_budget_cents` and/or `approval_threshold_cents` be revised after onboarding; each such call increments `CorporateAccount.version` by 1 (§2.4), which is exactly the change the order-creation OCC guard (§2.5) is designed to protect against.

### 3.3 Branding Customization and Compliance Sign-Off

An `AccountManager` may define one or more `BrandingProfile` records under its account, each carrying a `name` label, a `logo_url`, an `accent_color` hex code, and a `card_stock` selection — one of `MATTE`, `GLOSS`, or `RECYCLED`. Creating a profile requires `expected_corporate_account_version` and is subject to the stale-version rejection described in §2.5. A freshly created profile's `approved` flag defaults to false; it is flipped to true only through a `PlatformAdmin`-exclusive compliance sign-off call, and there is no path for it to become false again once approved.

That `approved` flag gates production, not order creation: a `CorporateOrder` may reference a `branding_profile_id` (or leave it null for unbranded default packaging) at creation time with no approval check at all, but the order cannot advance out of `PENDING_APPROVAL` into `APPROVED` while its `branding_profile_id` points at a profile whose `approved` is still false — that attempt is rejected with `ERR_BRANDING_PROFILE_NOT_APPROVED` (422). An order with no `branding_profile_id` set skips this check entirely. A companion listing call lets an `AccountManager` or `PlatformAdmin` enumerate every `BrandingProfile` created under a given account.

### 3.4 Order Creation, Recipient Import, and the Budget Approval Cascade

An `AccountManager` starts a bulk order by creating a `CorporateOrder` against one of its account's active templates: the request names a `template_id`, optionally a `branding_profile_id`, an `occasion` — one of `HOLIDAY`, `ANNIVERSARY`, `ONBOARDING`, `THANK_YOU`, or `CUSTOM` — an optional `scheduled_send_date` for send-immediately orders that skip it, and the mandatory `expected_corporate_account_version` OCC guard from §2.5. Creation fails with `ERR_TEMPLATE_NOT_FOUND` (404) if the named template does not exist or is not `active`, and with `ERR_BRANDING_PROFILE_NOT_FOUND` (404) if a `branding_profile_id` is supplied that either does not exist or belongs to a different account. If `scheduled_send_date` is supplied, it must be strictly later than the server's current logical time, or the request is rejected with `ERR_SCHEDULED_SEND_IN_PAST` (422) — the same temporal check is re-applied later at submission time, since the clock may have advanced in between. The new order starts with both of its independent dimensions — `approval_status` and `production_status` — at `DRAFT`.

Recipients are loaded through a dedicated bulk-import call that accepts a `rows` array (the CSV payload, one object per intended recipient) and behaves as a **partial-success** operation: each row is evaluated independently and is persisted as a `Recipient` whose `import_row_status` is either `ACCEPTED` or `REJECTED` — a rejected row never contributes to recipient counts, cost calculations, or any downstream cascade. Each row supplies `full_name`, `email`, a shipping address (`shipping_address_line1`, `city`, `state_code`, `postal_code`, `country_code`), and a `quantity` (defaulting to 1, required to be greater than zero) of baskets to send that person. Two per-row checks run, in this order: first, a row's `email` may not duplicate another `ACCEPTED` row's email within the same import batch or against the order's already-existing recipients — a collision is rejected with `ERR_DUPLICATE_RECIPIENT_EMAIL` (422) and only that row is dropped; second, for every `sku_id` in the template's `components`, the forward-looking variant of the component-availability calculation (§3.6) must show at least as many available units as `components[sku].quantity` multiplied by the row's own `quantity` — a shortfall is rejected with `ERR_INSUFFICIENT_INVENTORY_FORWARD` (422), again dropping only that row rather than the batch. After every row in the batch has been evaluated this way, if not a single row was accepted, the entire batch call fails with `ERR_IMPORT_BATCH_ALL_ROWS_REJECTED` (422). Every `Recipient` row created this way (and every `BudgetApproval` row created later in this workflow) carries a `corporate_order_id` tying it back to the owning order. For every row that is `ACCEPTED`, the system creates the `Recipient` plus one `InventoryReservation` per SKU in the template's composition: `reserved_qty` equals that SKU's `components` quantity multiplied by the recipient's `quantity`, the reservation starts in `RESERVED`, and — only when the underlying `ComponentSKU.is_perishable` is true — `expires_at` is set to the reservation's own `created_at` plus that SKU's `shelf_life_days`.

An `AccountManager` submits a `DRAFT` or `REJECTED` order for approval by naming the individual employee behind the request as `requested_by_user_id`, plus an optional `station_id` and `scheduled_date` that are **required** whenever the submission might auto-approve (explained below) and otherwise simply ignored. This call is only legal while `order.approval_status` is `DRAFT` or `REJECTED` and `order.production_status` is not `CANCELLED` — otherwise `ERR_INVALID_ORDER_STATE` (409). It further requires at least one `ACCEPTED` recipient on the order, or `ERR_EMPTY_RECIPIENT_LIST` (422), and that any `scheduled_send_date` on the order still lies strictly in the future, or `ERR_SCHEDULED_SEND_IN_PAST` (422) again. Relative to the order-lookup itself, these checks fire in ascending order — order-state legality, then the empty-recipient-list constraint, then the scheduled-date recheck. On success, the system runs the bulk-pricing calculation described below (provisional variant), then the budget-utilization calculation, storing the results onto `subtotal_cents`, `total_cost_cents`, and the boolean `requires_approval`; it also creates a `BudgetApproval` row with `decision` set to `PENDING` and `requested_by_user_id` copied from the payload — but only the *first* time this order is ever submitted. If the same order is later resubmitted after having been `REJECTED`, the system resets that **same** `BudgetApproval` row (`decision` back to `PENDING`, `requested_by_user_id` overwritten, `approver_user_id` and `decided_at` cleared to null) instead of creating a second one, preserving a strict one-to-one relationship between an order and its budget-approval record. `order.approval_status` moves to `PENDING_APPROVAL`.

If `requires_approval` resolves to false, the system does not stop at `PENDING_APPROVAL` — it immediately and atomically re-fires the same transition that a human `FinanceApprover` would otherwise trigger, using `approver_user_id = null` and `decision = APPROVED` (since no human decider is involved, the segregation-of-duties comparison in §2.8 simply does not apply here), consuming the submission's own `body.station_id`/`body.scheduled_date` as the values that the approval cascade (below) needs. This auto-approval attempt is held to the exact same preconditions a manual approval would face — in ascending priority order: the named `station_id` must resolve to an existing `AssemblyStation` (`ERR_FULFILLMENT_REF_NOT_FOUND`, 404); every `ComponentSKU` in the order's basket composition must clear the perishable-safety check (`ERR_PERISHABLE_SAFETY_VIOLATION`, 422, detailed in §3.6); the chronological inventory-availability calculation must have enough stock for every reservation this order would move to `ALLOCATED` (`ERR_INSUFFICIENT_INVENTORY_CHRONOLOGICAL`, 409); any referenced branding profile must be `approved` (`ERR_BRANDING_PROFILE_NOT_APPROVED`, 422); the target station's `daily_capacity` must not be exceeded (`ERR_ASSEMBLY_CAPACITY_EXCEEDED`, 409, §3.6); and the account's monthly budget must not be exceeded even though no threshold breach was triggered (`ERR_BUDGET_EXCEEDED`, 402). If **any** of these fail during the auto-fire, the entire submit-for-approval call fails as one atomic unit: the order is left exactly as it was, still `DRAFT`, and — critically — no `BudgetApproval` row is persisted at all, not even the `PENDING` one that a normal (non-auto-approving) submission would have created.

When a human decision is required, a `FinanceApprover` calls the budget-decision endpoint with `decision` (`APPROVE` or `REJECT`), its own `approver_user_id`, and — only relevant to `APPROVE` — the same optional-but-conditionally-required `station_id`/`scheduled_date` pair, plus an optional `decision_reason` used on rejection. Both decisions share two checks, evaluated in this order: the order must exist (`ERR_ORDER_NOT_FOUND`, 404), and the order's `BudgetApproval.decision` must still be `PENDING` (`ERR_INVALID_DECISION_STATE`, 409). `REJECT` additionally requires `approver_user_id` to differ from the `BudgetApproval.requested_by_user_id` on file (`ERR_SELF_APPROVAL_FORBIDDEN`, 403, §2.8); on success it simply records `decision = REJECTED`, the supplied `approver_user_id`, the optional `decision_reason`, and a `decided_at` timestamp — the order's `production_status` stays `DRAFT`, and the `AccountManager` may resubmit later, closing the cycle `PENDING_APPROVAL → REJECTED → PENDING_APPROVAL`. `APPROVE` is held to the fuller ordered check list already enumerated in the auto-approval paragraph above, with the fulfillment-reference existence check firing first, then the decision-state check, then perishable safety, chronological inventory sufficiency, branding approval, self-approval (here it does apply, since a human decider is present), assembly capacity, and finally the budget hard cap.

A finalized `APPROVE` recomputes the bulk-pricing calculation using the **final** variant (locked catalog prices, described below) and overwrites `total_cost_cents`; it snapshots `locked_template_version` and `locked_branding_version` to the referenced `GiftBasketTemplate`'s and `BrandingProfile`'s current `version` values (null for the latter if no branding profile is set) so that a later catalog edit can never retroactively change what an already-approved order is billed; it stamps `BudgetApproval.decision = APPROVED` with the supplied `approver_user_id` and a `decided_at`; and it runs the forward leg of the year-to-date spend recompute (§3.2). This is also the moment the approval cascade fires, carrying `production_status` from `DRAFT` toward `ASSEMBLING` — detailed in §3.6.

Two calculations govern how much an order costs. **Bulk-order pricing** starts from a per-unit price equal to the template's `base_price_cents`, plus a branding surcharge of $1.50 (150 cents) added only when the order carries a non-null `branding_profile_id`. That per-unit price is multiplied by the total quantity summed across every `ACCEPTED` recipient on the order to produce a subtotal. That total-unit count is also what selects a volume tier: fewer than 25 total units is `TIER_0`; at least 25 but fewer than 100 is `TIER_1`; at least 100 but fewer than 500 is `TIER_2`; 500 or more is `TIER_3`. Each tier carries a fixed discount off the subtotal — 0% for `TIER_0`, 5% for `TIER_1`, 10% for `TIER_2`, and 15% for `TIER_3` — and that discount is applied and rounded half-up to the nearest whole cent exactly once, on the whole subtotal, never per recipient row (§2.6). Separately, a rush fee of $25.00 (2,500 cents) is added on top whenever three conditions all hold: the order has a `scheduled_send_date`, that date is no more than 72 hours away from the server's current logical time, and the order's volume tier is `TIER_0` (i.e., fewer than 25 total units — large orders are assumed to already be on an expedited production track and never draw the rush fee). This entire calculation is evaluated twice with two different catalog snapshots: a **provisional** variant, used whenever `approval_status` is `DRAFT` or `PENDING_APPROVAL`, that reads the template's and branding profile's current (live) `base_price_cents`/version and is recomputed on every submission — so a catalog price edit landing between one submission and the next changes the provisional figure — and a **final** variant, used once `approval_status` is `APPROVED`, that instead reads the template and branding profile pinned at `locked_template_version`/`locked_branding_version`, freezing the figure at the price snapshot taken the moment of approval even if the catalog changes afterward; for identical recipient data, the final figure can therefore differ numerically from the last provisional figure whenever a `PlatformAdmin` edited `base_price_cents` in between.

**Budget-utilization and the approval trigger** run immediately after bulk-order pricing, before any `BudgetApproval` row exists, and their own evaluation order is fixed and does not feed back on itself: first, a remaining-budget figure is computed as the account's `monthly_budget_cents` minus its `ytd_spend_cents` — using only account-level figures, never this order's own cost. That remaining-budget figure alone (computed before this order's cost exists) selects a loyalty tier: `GOLD` when remaining budget is at least $10,000.00 (1,000,000 cents), `SILVER` when it is at least $2,500.00 (250,000 cents) but below the `GOLD` line, and `STANDARD` otherwise — carrying discounts of 3%, 1%, and 0% respectively. That loyalty discount is then applied, rounded half-up to the nearest cent, to the discounted subtotal from the bulk-pricing calculation, and the (unrounded, already whole-cent) rush fee is added on top of that rounded figure to produce the order's final `total_cost_cents` — the order's own cost is never allowed to feed back into the remaining-budget figure that selected its own loyalty tier, which would make the dependency circular. `requires_approval` is then set to true only when this `total_cost_cents` **strictly** exceeds the account's `approval_threshold_cents` — equal to the threshold still auto-approves. A separate, independent hard-cap flag notes whether `ytd_spend_cents` plus this `total_cost_cents` would exceed `monthly_budget_cents`; that flag is not enforced at submission time but is re-checked at the moment of approval (manual or automatic alike) as the `ERR_BUDGET_EXCEEDED` (402) check described above — meaning a request can auto-approve on the threshold check yet still be rejected on the hard-cap check if account spending has moved in between.

The order list endpoint supports optional filtering by `corporate_account_id`, `template_id`, `branding_profile_id`, `approval_status`, and `production_status`, and a companion endpoint lists the (zero or one) `BudgetApproval` records tied to a given order.

### 3.5 Gift Message Proofing

Every recipient's gift card goes through its own independent proofing cycle, separate from the order's approval dimensions. An `AccountManager` submits card copy for a recipient by supplying `message_text` and the submitting individual's `submitted_by_user_id`; this is legal only when no `MessageProof` yet exists for that recipient, or when one exists and its `proof_status` is `DRAFT` or `REVISION_REQUESTED` — attempting it from any other status is rejected. On success, `proof_status` becomes `SUBMITTED`.

A `ProofApprover` then renders a `decision` on a `SUBMITTED` proof, supplying its own `decided_by_user_id`. Two checks gate this call, in order: the target `MessageProof` must exist (`ERR_SUBRESOURCE_NOT_FOUND`, 404), and its `proof_status` must still be `SUBMITTED` (`ERR_INVALID_DECISION_STATE`, 409); both of the decision's two branches additionally require `decided_by_user_id` to differ from the `submitted_by_user_id` on file, or the request is rejected with `ERR_SELF_PROOF_APPROVAL_FORBIDDEN` (403, §2.8) — this segregation check applies identically and with equal force to both possible decisions, with no exception on either branch. The `APPROVE` branch sets `proof_status` to `APPROVED` and records `decided_by_user_id`; the system then immediately, as its own follow-up step, advances that same proof from `APPROVED` to `LOCKED`, permanently freezing the final card text and — as detailed in §3.8 — unblocking shipment creation for that recipient. The sibling `REQUEST_REVISION` branch is symmetric in structure: it sets `proof_status` to `REVISION_REQUESTED`, records the same `decided_by_user_id`, and increments `revision_count` by one; the system then immediately, as its own follow-up step, advances that proof from `REVISION_REQUESTED` back to `DRAFT`, at which point the `AccountManager` may resubmit — closing the cycle `SUBMITTED → REVISION_REQUESTED → DRAFT → SUBMITTED`. A dedicated fetch lets either an `AccountManager` or a `ProofApprover` retrieve the (zero or one) `MessageProof` tied to a given recipient.

### 3.6 The Approval Cascade: Inventory Allocation and Assembly Kickoff

Component availability is judged by two different variants of the same calculation, and the choice of variant is what makes an inventory shortfall visible at different times to different callers. The **forward-looking** variant, used per recipient row during CSV import (§3.4) before that row's `InventoryReservation` is even created, takes a SKU's `on_hand_qty` and subtracts the `reserved_qty` of every existing reservation on that SKU that is still `RESERVED` or `ALLOCATED` **and** whose `expires_at` is either unset or lies after the importing order's `scheduled_send_date` (or the current instant, for unscheduled orders) — reservations that will have already spoiled by the relevant fulfillment date are excluded from the competing set, projecting availability forward to when the basket would actually be needed. The **chronological** variant, used once per reservation at the moment an order's budget decision moves it toward `ALLOCATED`, ignores future expiry entirely: it walks every `RESERVED`/`ALLOCATED` reservation on the SKU strictly in ascending `created_at` order (ties are broken by `created_at` alone, no other field), accumulating reserved quantity as it goes, and a reservation is only satisfiable if that running total — including the reservation being checked — does not exceed `on_hand_qty`. Because it is first-come-first-served by creation time rather than by projected expiry, the chronological variant can find a shortfall that the forward-looking variant did not, whenever a reservation created earlier — but not yet expired — consumes stock that a later reservation's forward-looking check had assumed would still be available; that shortfall is rejected with `ERR_INSUFFICIENT_INVENTORY_CHRONOLOGICAL` (409).

A second safety check runs alongside the chronological availability check whenever an order moves toward approval: every `ComponentSKU` in the order's basket composition must still have unexpired shelf life — computed as that SKU's `created_at` plus its `shelf_life_days` — on the calendar day named by `scheduled_date` for the assembly station handling the order (assembly stations themselves add no additional lead time to this calculation, so the requirement collapses to the SKU's computed expiry instant falling on or after `scheduled_date`). A violation is rejected with `ERR_PERISHABLE_SAFETY_VIOLATION` (422). Separately, the target `AssemblyStation` named by `station_id` has a `daily_capacity` ceiling: summing the `quantity` of every `AssemblyTask` — across every order, not just this one — already scheduled at that station on that `scheduled_date`, plus this order's own total recipient quantity, must not exceed that ceiling, or the request fails with `ERR_ASSEMBLY_CAPACITY_EXCEEDED` (409).

Once every check above clears, `BudgetApproval` decision `APPROVE` sets off a three-hop cascade, and each hop is caused by the previous hop's outcome rather than by the approval event directly. Hop one, caused directly by the `APPROVE` decision: every `InventoryReservation` belonging to this order's recipients moves from `RESERVED` to `ALLOCATED` (guarded by its own precondition that it is still `RESERVED` and either has no `expires_at` or has not yet passed it). Hop two, caused by hop one's `ALLOCATED` reservations now existing — not by the approval event itself: exactly one `AssemblyTask` is created per `Recipient` on the order, starting `QUEUED`, carrying the `station_id` and `scheduled_date` supplied on the approval call and a `quantity` mirroring that recipient's own. Hop three, caused by hop two's new `AssemblyTask` rows now existing — again, not directly by the approval event: the order's `production_status` advances from `DRAFT` to `ASSEMBLING`. The reservation-list and assembly-task-list endpoints support optional filtering by `recipient_id` and `sku_id`/`station_id` respectively, plus `status` on both.

### 3.7 Assembly Execution and Production Tracking

`WarehouseOps` drives each `AssemblyTask` forward by supplying a `target_status`. From `QUEUED` it may advance to `IN_PROGRESS`; from `IN_PROGRESS` it may advance to `COMPLETE`; and from either `QUEUED` or `IN_PROGRESS` it may be marked `FAILED` directly. Any target that is not a legal next state for the task's current status is rejected with `ERR_INVALID_FULFILLMENT_STATE` (409). Reaching `COMPLETE` is the point at which physical stock is actually spent: for every SKU in the recipient's basket composition, `ComponentSKU.on_hand_qty` is decremented by the `reserved_qty` of the matching `InventoryReservation` tied to that task's recipient — a separate and later event from the reservation-status bookkeeping in §3.6, which only tracks competing claims on stock rather than physical consumption.

Completing the very last outstanding `AssemblyTask` among an order's recipients triggers a two-hop cascade of its own. Hop one is the completing task's own transition to `COMPLETE`, driven by a `WarehouseOps` call — a different trigger from the approval event that drives the cascade in §3.6. Hop two, caused by hop one only once it makes the order's `production_status` reach `READY_TO_SHIP` (not caused directly by the task completion itself): every `InventoryReservation` belonging to the order's recipients that is still `ALLOCATED` moves to `ASSEMBLED`. If an order is cancelled while an `AssemblyTask` is still `QUEUED` or `IN_PROGRESS`, that task is force-transitioned to `FAILED` as one of the cancellation's compensating side effects (§3.9).

### 3.8 Shipping and Multi-Zone Delivery

Before a recipient's basket can ship, its gift message must be frozen: `ShippingOps` may only create a `Shipment` for a recipient whose `MessageProof.proof_status` is `LOCKED` (§3.5) — any earlier status is rejected with `ERR_MESSAGE_PROOF_NOT_LOCKED` (422). Creating a shipment names a `zone_id` (must resolve to an existing `ShippingZone`, or `ERR_FULFILLMENT_REF_NOT_FOUND`, 404) and a `ship_date`. A temporal check then applies: every calendar day from `ship_date` up to, but not including, `ship_date` plus the zone's `transit_days_min` must contain none of that zone's `blackout_dates`; and, when the owning order carries a `scheduled_send_date`, `ship_date` plus the zone's `transit_days_max` — the slowest guaranteed delivery estimate — must land on or before that scheduled date. Either failure is rejected with `ERR_SHIPPING_BLACKOUT_CONFLICT` (409).

Each shipment's cost is computed once, at creation, never recomputed afterward. An estimated weight in kilograms is formed by multiplying a fixed per-basket weight of 1.2 kg by the recipient's `quantity`; that weight is multiplied by the zone's `per_kg_rate_cents` and added to the zone's flat `base_rate_cents`, and the sum is rounded half-up to the nearest cent to produce `shipping_cost_cents` for that one shipment (§2.6). Any order-wide shipping total shown to a caller is simply the sum of its shipments' already-rounded `shipping_cost_cents` values — summing unrounded fractional costs first and rounding once at the end is explicitly not how this figure is produced, since it would understate the total whenever any shipment carries a fractional-cent remainder.

A shipment then moves through its own lifecycle at `ShippingOps`'s direction, again by supplying a `target_status`: `CREATED` advances to `LABEL_GENERATED`, at which point a `tracking_number` is generated and stored; `LABEL_GENERATED` advances to `IN_TRANSIT`; `IN_TRANSIT` advances to `DELIVERED`, at which point `delivered_at` is stamped with the current logical time; and, symmetrically, either `LABEL_GENERATED` or `IN_TRANSIT` may instead be marked `EXCEPTION`, from which the only further move is to `RETURNED`. An illegal target for the shipment's current status is rejected with `ERR_INVALID_FULFILLMENT_STATE` (409), exactly as for assembly tasks. Two more order-level cascades ride on these transitions: the moment every shipment among an order's recipients has reached `IN_TRANSIT` or later, the order's `production_status` advances from `READY_TO_SHIP` to `SHIPPED`; and the moment every one of those shipments has reached `DELIVERED`, `production_status` advances from `SHIPPED` to `COMPLETED` — which in turn moves every still-`ASSEMBLED` `InventoryReservation` among the order's recipients to `RELEASED`, since a fully shipped basket no longer competes for stock. The shipment-list endpoint supports optional filtering by `recipient_id`, `zone_id`, and `status`.

### 3.9 Cancellation, Compensating Adjustments, and Recurring Order Series

Either an `AccountManager` or a `PlatformAdmin` may cancel a `CorporateOrder` whose `production_status` is still `DRAFT` or `ASSEMBLING`; any later `production_status` is rejected with `ERR_ORDER_ALREADY_TERMINAL` (409). Cancellation drives `production_status` to `CANCELLED` and fires two independent compensations. The first restores inventory: every `InventoryReservation` belonging to the order's recipients that is still `RESERVED` or `ALLOCATED` moves to `RELEASED`, which removes it from the active-status filter that the availability calculations in §3.6 use — the SKU's available quantity returns to exactly what it was before the reservation existed. The second restores budget, but only conditionally: if `order.approval_status` was already `APPROVED` at the moment of cancellation (meaning its cost had already been counted), the reverse leg of the year-to-date spend recompute runs, subtracting `total_cost_cents` back out of `ytd_spend_cents` (§3.2); if the order had never reached `APPROVED`, nothing was ever added, so nothing is subtracted. Alongside both compensations, every `AssemblyTask` belonging to the order's recipients that is still `QUEUED` or `IN_PROGRESS` is force-transitioned to `FAILED`.

A `RecurringOrderSeries` lets an `AccountManager` turn a one-off order into a repeating template: the request names a `source_order_id` — the existing `CorporateOrder` whose `template_id`, `branding_profile_id`, and `occasion` will be cloned on each cycle — and an `interval_days` (greater than zero) between generated orders. Note that `source_order_id` is referenced purely as a cloning source rather than as a structural parent: `RecurringOrderSeries` rows are discovered through their own account-scoped listing call, not by walking backward from a `CorporateOrder`, so no reverse-reachability is required for it. The series starts `active` (true) with `next_run_date` set to the creation instant plus `interval_days`. An `AccountManager` may pause an active series (setting `active` to false) or resume a paused one (setting `active` back to true) through the same update call; pausing when already inactive, or resuming when already active, is rejected with `ERR_INVALID_SERIES_STATE` (409). The two directions are not perfectly symmetric: resuming a series recomputes `next_run_date` as the current logical time plus `interval_days`, while pausing leaves `next_run_date` untouched. Whenever the logical clock is advanced past a series's `next_run_date` while that series is still `active`, the system automatically clones the source order's `template_id`, `branding_profile_id`, and `occasion` into a brand-new `CorporateOrder` — starting `DRAFT`, with no recipients yet imported — under the same corporate account; it records that new order's id onto `last_generated_order_id` (a system-set cache, not itself a reverse-reachability foreign key) and advances `next_run_date` by another `interval_days`. The same clock-advance call also sweeps every reservation still `RESERVED` whose `expires_at` has now passed to `EXPIRED` (§2.7, §3.6) — a perishable stock spoilage that removes it from the active-status filter without ever having been allocated. The recurring-series list endpoint supports optional filtering by `corporate_account_id`.
