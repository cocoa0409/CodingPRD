# Retail Cash Reload Network API — Product Requirements Document

## 1. Introduction

Consumers who hold a prepaid or partner-issued account expect to add cash to it the way they add cash to anything else: at a register, in a store they already visit, in real time. Delivering that experience means a retailer can accept physical currency at the point of sale and have the value land on a funded account within seconds, while four separate parties — the retailer, the program manager, the brand whose card is being reloaded, and the chartered bank that sponsors the whole arrangement — each carry a defined slice of the money, the risk, and the regulatory obligation. This document specifies the interface that governs all of it.

The network is deliberately multi-tenant. A single platform hosts many reload programs; each program is sponsored by exactly one chartered bank of record, is operated by a program manager, carries any number of third-party brand partners whose cards are issued under it, and is sold into retail chains through negotiated agreements that fix fee splits and per-transaction ceilings. Because the cash arriving at a register is anonymous currency, the platform is also the first line of anti-money-laundering defence, and the compliance posture of a program is not advisory — it gates writes against everything beneath it.

What follows is the complete contract: the roles and their authority, the response envelope, the money arithmetic down to the rounding order, the state machines that carry a load, an alert, a dispute and a settlement batch from inception to closure, and the error vocabulary used to refuse work. Where a rule is scattered across the workflow narratives rather than stated in a single block, that is intentional — the business logic is meant to be assembled from the way the money actually moves.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which that principal is acting. A request missing either header, or presenting a role string that is not one of the declared roles, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose declared role is not among the roles authorised for that operation is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The platform recognizes exactly seven roles, spelled verbatim: `PlatformAdmin`, `BankSponsor`, `ProgramManager`, `RetailerClerk`, `ComplianceAnalyst`, `ComplianceOfficer`, and `SettlementOperator`.

Three of these roles are anchored to a persisted entity. When `X-User-Role` is `BankSponsor`, `X-User-ID` is the `id` of the acting `BankSponsor`; ownership checks on any resource that references a `BankSponsor` compare the resource's foreign-key field to `X-User-ID`, so a posture move or oversight review is refused unless the target program's `sponsor_bank_id` equals `X-User-ID`. When `X-User-Role` is `ProgramManager`, `X-User-ID` is the `id` of the acting `Program`; a retailer agreement is actionable only when its `program_id` equals `X-User-ID`, and a reload location only when the location's agreement's `program_id` equals `X-User-ID`. When `X-User-Role` is `RetailerClerk`, `X-User-ID` is the `id` of the acting `RetailerAgreement`; a clerk may accept cash only at a location governed by the clerk's own agreement, and may answer a dispute only where the clerk's agreement is party to the disputed load.

Four roles act as operators rather than entities. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a transition writes an actor identifier but does not compare it to any entity's `id`. The same is true of `ComplianceAnalyst`, whose identifier is recorded as the `assigned_analyst_id` or `raised_by_analyst_id` on an alert but is never matched against an entity primary key, and of `ComplianceOfficer`, whose identifier is recorded as the `confirmed_by_analyst_id` on a confirmation. When `X-User-Role` is `SettlementOperator`, `X-User-ID` is likewise an opaque operator identifier held only for audit purposes.

`PlatformAdmin` holds the cross-tenant administrative surface: only that role may register a sponsor bank, create a program, or set the logical clock. The remaining authority is partitioned by segregation of duties, described in §2.10.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept two query parameters. The `limit` parameter caps how many rows are returned; it defaults to 10 and must fall between 1 and 100 inclusive. The `offset` parameter names how many rows to skip before harvesting the page and defaults to 0. Both are optional on every list operation; several list operations accept additional filter parameters alongside them, and those filters are described where the relevant resource is discussed in §3.

List responses are ordered by creation time, oldest first — that is, ascending `created_at`.

Every list response carries four pagination values in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`. `total_count` is the number of rows matching the query before pagination is applied, and `has_more` is true when further rows remain beyond the returned page.

### 2.4. The Reload Network Hierarchy and Posture Gating

Entities nest in five families. A `BankSponsor` stands alone at the top. A `Program` names its sponsor. Beneath a program hang four independent collections — its `BrandPartner` brands, its `RetailerAgreement` contracts, its `CardAccount` cards, and its `AmlAlert` filings, plus the `DisputeCase` and `LossAllocation` records that accrue against it. Beneath a retailer agreement hang its `ReloadLocation` stores and its `SettlementBatch` periods. Beneath a reload location hang the `LoadTransaction` cash loads it accepted and the `FloatWindow` armored-carrier deliveries it scheduled. Every nested creation is submitted with a payload that names the parent identifier, and the relationship is implied by that payload rather than declared as a schema constraint.

Resolution of identifiers is strictly ordered. When a request path carries one or more resource identifiers, the server resolves them left to right and rejects the request with `ERR_ENTITY_NOT_FOUND` (HTTP 404) at the first identifier that does not correspond to a stored row; it does not attempt to resolve a later identifier until every earlier one has resolved. Identifiers supplied in the request body — a sponsor named by a program, an account named by a load, an agreement named by a location — are resolved separately, and an unresolvable body reference is rejected with `ERR_REFERENCED_RESOURCE_NOT_FOUND` (HTTP 404). Both checks precede every business rule: existence is settled before state, and state is settled before amounts.

Two cross-cutting gate conditions sit above all child writes. A program's `compliance_posture` is one of `OPEN`, `RESTRICTED` or `FROZEN`, and it gates every child write. A write that creates or mutates a child of a program whose `compliance_posture` is `FROZEN` is refused with `ERR_PROGRAM_FROZEN` (HTTP 409) — this guard covers brand onboarding and brand state moves, agreement and location creation and state moves, load creation, alert filing, dispute filing, loss allocation creation and posting, settlement batch creation, float window creation, and the oversight review itself. A separate, narrower guard refuses onboard, first-fund, and re-instatement work against a program whose `compliance_posture` is `RESTRICTED`, with `ERR_PROGRAM_RESTRICTED` (HTTP 409).

State-based refusals are otherwise uniform. A transition attempted from a state the machine does not permit surfaces `ERR_INVALID_STATE` (HTTP 409), and the same identifier is used when a precondition on a related entity fails rather than a state precondition on the row itself. A transition attempted from a terminal state, or a second terminal write against the same row, surfaces `ERR_ALREADY_TERMINAL` (HTTP 409).

### 2.5. Common Resource Properties

Every entity in this system — `BankSponsor`, `Program`, `BrandPartner`, `RetailerAgreement`, `ReloadLocation`, `CardAccount`, `LoadTransaction`, `AmlAlert`, `DisputeCase`, `LossAllocation`, `SettlementBatch` and `FloatWindow` — carries the full set of system-managed properties. There is no entity in this domain that omits them.

- **`id` (string):** a server-minted UUID that is unique across the platform and carries no type prefix or human-readable segment. Every resource is addressed by this value alone.
- **`created_at` (string):** an ISO 8601 UTC timestamp with three fractional digits recording when the row was created.
- **`updated_at` (string):** an ISO 8601 UTC timestamp with three fractional digits recording when the row was last mutated. Every field change refreshes it, including changes to derived and computed fields.
- **`version` (integer):** a counter that starts at its initial value and increments by one on every mutation of the row. It is the anchor for the optimistic concurrency checks described in §2.7.

A mutation that only recomputes a derived field is still a mutation: it refreshes `updated_at` and increments `version` on the row it touched. Cascades are particularly important here — a single posture move may increment the version of the program and of dozens of locations, agreements and accounts, and each of those increments is visible to a later version check.

### 2.6. Monetary Values, Precision and Rounding

Money in this system is stored in cents. Fields whose names end in `_cents` — `principal_cents`, `convenience_fee_cents`, `posted_total_cents`, `retailer_fee_share_cents`, `program_fee_share_cents`, `balance_cents`, `ledger_posted_cents`, `ledger_reversed_cents`, `window_load_cents`, `observed_total_cents`, `claimed_amount_cents`, `provisional_credit_cents`, `final_liability_cents`, `total_loss_cents`, `retailer_share_cents`, `program_share_cents`, `bank_share_cents`, `gross_principal_cents`, `accrued_retailer_share_cents`, `net_fee_payable_cents`, `settlement_rounding_delta_cents`, `chargeback_total_cents`, `float_retained_cents`, `float_amount_cents`, `per_transaction_limit_cents`, `daily_location_limit_cents`, `daily_accepted_cents`, and `effective_per_transaction_limit_cents` — hold cents. A field whose rule pins a 2-decimal-place value keeps that scale rather than being re-truncated to whole cents: `convenience_fee_cents`, the `posted_total_cents` it feeds, `retailer_fee_share_cents` and `program_fee_share_cents` are 2-decimal-place half-up values (§3.4), as are the settlement accrual, payable and rounding-delta fields (§3.8).

Where a rule names a precision, that precision governs. Computed monetary and score values that are not integral are rounded to exactly 2 decimal places using the round-half-up rule, and the rounding is applied at the single point the rule nominates — never incrementally along the way. The `posture_score` and `aml_velocity_score` fields are 2-decimal-place half-up values. Fee arithmetic is rounded once, at the end of its walk, as described in §3.4 and §3.8. Any intermediate arithmetic is performed exactly; only the final stored value is rounded.

### 2.7. Optimistic Concurrency Control

Three write operations are protected by an explicit expected-version input, and for each of them the input is mandatory — a request that omits it is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

- Creating a `LoadTransaction` requires `expected_card_account_version`, carrying the client's last observed `version` of the target `CardAccount`. A mismatch with the account's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412). This catches the case where a load or a compliance hold has already advanced the account — the hold path legitimately bumps the account's version — and the writer's view of the account is therefore stale.
- Opening a `DisputeCase` requires `expected_load_transaction_version`, carrying the client's last observed `version` of the disputed `LoadTransaction`. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412), because a reversal, a settlement or a re-instatement legitimately supersedes the prior state of the load.
- Onboarding a `BrandPartner` requires `expected_program_version`, carrying the client's last observed `version` of the sponsoring `Program`. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412), because an oversight review or a posture transition legitimately changes the program a partner is being onboarded against.

The remaining version-bearing writes are the load reversal and the load re-instatement described in §3.4, which each carry an expected load version and, for re-instatement, an expected account version; a mismatch on either is likewise rejected with `ERR_STALE_VERSION` (HTTP 412). No other operation accepts a client-supplied version field. A stale-version rejection is a rejection of the client's *observation*, not of a race: the server compares the supplied value against the row's current `version` at the moment of the write and refuses when they disagree, whatever the reason for the disagreement.

### 2.8. The Two-Dimension Card Account Model

A `CardAccount` carries two state dimensions that move independently. Its `funding_status` is one of `UNFUNDED`, `FUNDED` or `DRAINED`, and it describes the money. Its `compliance_hold_status` is one of `CLEAR`, `REVIEW` or `FROZEN`, and it describes the compliance posture of the account. Funding activity never writes the hold dimension, and compliance activity never writes the funding dimension — the single exception is the load reversal that a freeze provokes, which is a money effect triggered by compliance and therefore moves `funding_status` as a consequence of the money movement, not as a direct compliance write.

The spendable `balance_cents` is derived, never independently assigned: it is the maximum of zero and the difference between `ledger_posted_cents` and `ledger_reversed_cents`. The two ledger fields move only at funding and at reversal, so the balance is always reconcilable from them. `funding_status` follows the ledger too: an account with no posted principal at all is `UNFUNDED`; an account whose balance has been driven to zero is `DRAINED`; anything in between is `FUNDED`.

Reversals never drive a balance below zero. A hold dimension of `FROZEN` blocks money-affecting work on the account with `ERR_ACCOUNT_FROZEN` (HTTP 409); a hold dimension that is not `CLEAR` combined with a live alert blocks the same work with `ERR_AML_ALERT_PENDING` (HTTP 409) when a non-terminal `AmlAlert` references the account or an unresolved confirmed alert sits on it. The `frozen_at` field records the clock instant the hold dimension last became `FROZEN` and is cleared to null whenever the dimension leaves `FROZEN`.

### 2.9. The Logical Clock and Epoch Discipline

The server runs on a logical clock, not on wall-clock time. On startup the clock reads exactly `2026-09-01T00:00:00Z`, and it never falls back to real time. Every deadline, every trailing window, every due date and every epoch index is computed from that fixed default until an operator supplies a different instant through the admin-only clock-setting capability, whose payload field is `current_utc`. Advancing the clock is the only way a deadline moves. Domain datetime fields — the stamps a workflow writes (a load's `funded_at`, an account's `frozen_at`, an allocation's `posted_at`, a dispute's `retailer_response_due_at` and the like) and the deadlines supplied in a payload — are rendered at the instant's own precision: an integer-second instant such as `2026-09-01T00:00:00Z` is echoed with no fractional part, and a fractional part appears only when the instant carries one. The three-fractional-digit rendering applies to the system-managed common properties (§2.5) and the response envelope's own timestamp (§2.2), not to these domain stamps.

Two clock-derived concepts recur. A *trailing window* extends backwards from the current clock instant and moves with every read — nothing is ever reset. An *epoch day* is a logical-day bucket derived from the clock, and the `epoch_index` recorded on a load at creation, together with the `last_epoch_index` on a location, is what allows the daily counters to be reset at a day rollover rather than drifting. The two concepts are used deliberately in different places, and §3.6 explains which computation uses which.

### 2.10. The Segregation-of-Duties Principle

Confirming an AML alert is a two-person act. The confirming principal must be neither the analyst who raised the alert nor the analyst who took it into review: if `X-User-ID` equals the alert's `raised_by_analyst_id`, or equals its `assigned_analyst_id`, the confirmation is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). A `ComplianceAnalyst` may take an alert into review and may return it to the queue, but confirming, reopening and dismissing an alert belong to a `ComplianceOfficer`; the analyst who worked an alert can never be the officer who confirms it. A primary principal that is persona non-grata in this system is the one who raised it. The officer role, meanwhile, may not hold the raised or assigned persona on the alert it confirms, so an officer who raised an alert must hand the confirmation to a different officer.

### 2.11. Cascading Reconciliation and Hop Ordering

Many operations here are sagas rather than single-row writes. When a program's posture moves, when a brand is suspended, when an alert is confirmed, when a load is reversed, or when a batch is clawed back, the server performs an ordered sequence of hops, and each hop's effect is predicated on the state produced by the hop before it. The hop numbers are part of the contract: hop 1 is the anchor transition, later hops cascade into accounts, loads, alert filings, and posted loss allocations, and the final hop recomputes the derived program counters.

Two invariants govern every cascade. First, a hop that reverses money also unwinds the counters that money produced — the location's daily totals, the agreement's accrual and float, the account's ledger and balance, and the program's alert count and posture score are all brought back into agreement with the new reality, not left as they were. Second, a cascade never re-instates what an earlier cascade reversed. Un-freezing a program restores a hold dimension to `REVIEW` rather than `CLEAR`, restores a location to `RESTRICTED` rather than `OPEN`, and leaves previously reversed loads reversed and previously recovered allocations recovered. Re-instatement of a load is always a separate, explicitly requested act.

Every hop that touches a row refreshes that row's `updated_at` and increments its `version`, and cascades that recompute a program's `posture_score` or `open_aml_alert_count` count as mutations of the program.

## 3. Business Logic & Workflows

### 3.1. Sponsorship and Program Stand-Up

A `PlatformAdmin` begins the network by registering a `BankSponsor`. The payload names the chartered bank's `legal_name`, its `charter_state_code`, its `sponsorship_capacity_programs` — which must be at least 1 and is the ceiling on how many programs the bank may carry — an optional `oversight_tier` that is either `TIER_1` or `TIER_2` and defaults to `TIER_2` when omitted, and the `regulator_exam_due_at` instant of its next examination. A newly registered sponsor reports `active_program_count` of 0, `oversight_reviews_completed` of 0, and `is_capacity_exhausted` false.

With a bank of record in place, the same administrator creates a `Program`. The payload supplies the program's `name`, the `sponsor_bank_id` of its bank of record, its `program_type` — either `BAAS_PROGRAM_MANAGER` for a program the manager runs on behalf of a third party or `OWN_BANK_PROGRAM` for a bank-run program — an optional `settlement_cycle` of either `DAILY` or `WEEKLY` that defaults to `DAILY`, and the `oversight_review_due_at` deadline by which the bank must next review it. A fresh program opens with `compliance_posture` of `OPEN`, a `posture_breach_count` of 0, a `posture_score` of 0.00, and an `open_aml_alert_count` of 0. The act of creating the program also advances its sponsor: the sponsor's `active_program_count` increases by one and its `is_capacity_exhausted` flag is recomputed, becoming true once the count reaches the bank's `sponsorship_capacity_programs`. Every program counts toward that total, regardless of the program's own compliance posture, so a frozen program still occupies a slot in its sponsor's capacity.

### 3.2. Brand Partners, Service Scopes and Suspension Cascades

A `ComplianceOfficer` — or a `PlatformAdmin` — onboards a third-party brand by submitting a `BrandPartner` payload naming the `program_id` it sits under, the `brand_name`, and a `services_scope` drawn as a subset of `CARD_ISSUANCE`, `LEDGERING`, `COMPLIANCE_OVERSIGHT` and `DISPUTE_HANDLING`. The created row carries its own `brand_partner_id`, and cards may later be issued under it by naming that identifier as the `brand_partner_id` of an account. Three optional booleans toggle which of those services the program manager actually performs on the brand's behalf: `card_issuance_enabled`, which defaults to true because a brand normally runs its own issuance, `ledgering_enabled`, and `compliance_oversight_enabled`. The payload must also carry `expected_program_version` per §2.7, and creating the brand advances the program's `version`. The new brand starts in `PENDING_ONBOARDING` with a `suspension_source` of `NONE`.

The `onboarding_checklist_complete` flag is a derived readiness signal: it is true exactly when every element of the declared `services_scope` has its enabling flag set true. A brand cannot leave `PENDING_ONBOARDING` for `ACTIVE` until that flag is true, and an attempt to activate an incomplete brand is refused with `ERR_BRAND_ONBOARDING_INCOMPLETE` (HTTP 422). The requested target is carried on `to_status`, and the same field drives every brand move discussed below. Activation additionally requires the parent program's `compliance_posture` to be `OPEN`, otherwise `ERR_PROGRAM_FROZEN` (HTTP 409) applies; a `RESTRICTED` program refuses the same activation (and the restoration of a suspended brand to `ACTIVE`) with `ERR_PROGRAM_RESTRICTED` (HTTP 409), the narrower onboarding guard of §2.4. Reaching `ACTIVE` increments the brand's `version`.

Suspending an `ACTIVE` brand is a compliance act with a two-hop cascade. The brand is refused if the program is already `FROZEN`, because a frozen program has already pushed that suspension down the tree — the rejection is `ERR_PROGRAM_FROZEN` (HTTP 409). When the suspension is permitted, hop 1 sets `partner_status` to `SUSPENDED` with `suspension_source` of `COMPLIANCE`; hop 2 moves every `CardAccount` of that brand whose `compliance_hold_status` is `CLEAR` into `REVIEW`; and hop 3 declines every pending load of those accounts, moving `load_status` from `INITIATED` to `DECLINED` with `reversal_reason` of `NONE`, because a pending load of a suspended brand can never be funded. This suspension counts toward the program's `posture_breach_count` — a `COMPLIANCE`-sourced suspension is a breach — and the program's `posture_score` is recomputed and its `suspended_brand_count` increases by one, but the suspension does not by itself move the program's `compliance_posture`. That move is always an explicit program act.

Restoring a suspended brand to `ACTIVE` requires the program to be `OPEN` (`ERR_PROGRAM_FROZEN` or, for a `RESTRICTED` program, `ERR_PROGRAM_RESTRICTED`, HTTP 409) and clears `suspension_source` back to `NONE`. Restoration sweeps the brand's accounts: those in `REVIEW` return to `CLEAR`, unless a non-terminal `AmlAlert` references the account, in which case the account stays in `REVIEW`; accounts that a program freeze had pushed to `FROZEN` first return to `REVIEW` and are then subject to the same clearing rule. A brand still carrying any non-terminal dispute — an `open_dispute_count` greater than zero — cannot be reverted from `ACTIVE` back to `PENDING_ONBOARDING`, and cannot be offboarded from `SUSPENDED` either; both moves are refused with `ERR_INVALID_STATE` (HTTP 409). Offboarding sets `partner_status` to `OFFBOARDED`, which is terminal, and freezes every account of the brand whose hold dimension is `CLEAR` or `REVIEW`.

### 3.3. Retailer Agreements, Fee Splits and Store Enablement

Retail chains are brought into a program through a `RetailerAgreement`, created by a `ProgramManager` or a `PlatformAdmin`. The payload names the `program_id`, the `retailer_name`, the `fee_split_retailer_pct` — the retailer's share of each convenience fee, strictly greater than 0 and strictly less than 1 — the `per_transaction_limit_cents` that caps a single load, which must be at least 1, and the `daily_location_limit_cents` that caps a day's aggregate acceptance at one store. Two optional fields round out the contract: `settlement_period_hours`, the length of a settlement period, which defaults to 24, and `reload_enabled`, which defaults to true and records whether reloads are contractually switched on. A new agreement opens in `DRAFT` with `fee_split_program_pct` computed as one minus `fee_split_retailer_pct`, and with `accrual_pending_cents`, `float_position_cents` and `settled_fee_total_cents` all at zero and `contract_version_locked` false.

The agreement lives through `DRAFT`, `ACTIVE`, `SUSPENDED` and `TERMINATED`, and a `ProgramManager` drives every move. Moving from `DRAFT` to `ACTIVE` requires the program to be `OPEN` (`ERR_PROGRAM_FROZEN` otherwise) and recomputes the program's share of the split as one minus the retailer's percentage. Suspending an `ACTIVE` agreement requires no additional condition beyond the requested target, and its effect is to restrict every store under it — each `ReloadLocation` in `OPEN` becomes `RESTRICTED`. Reactivating a `SUSPENDED` agreement likewise requires the program to be `OPEN`.

Renegotiation is a return to `DRAFT` from `ACTIVE`, permitted only while `contract_version_locked` is false. That flag is set the first time a posted or recovered loss allocation cites the agreement, and once it is set the contract version is pinned: a renegotiation write against a locked agreement is refused, with `ERR_CONTRACT_VERSION_LOCKED` (HTTP 409) as the designated rejection and with the same guard annotated as an `ERR_INVALID_STATE` precondition on the transition. Termination is available from `DRAFT` unconditionally, and from `SUSPENDED` only when `accrual_pending_cents` is zero, so that unsettled accruals must be settled before the contract can be closed (`ERR_INVALID_STATE`, HTTP 409). Terminating an agreement closes every store beneath it.

Stores themselves are `ReloadLocation` rows registered by a `ProgramManager` or a `PlatformAdmin` under a specific agreement, carrying the `retailer_agreement_id`, a `location_code` that is unique within that agreement, the `state_code` of the store, and its `register_count`, which must be at least 1. A fresh store opens in `OPEN` status with `daily_accepted_cents` and `daily_txn_count` at zero, an `aml_velocity_score` of 0.00, `is_velocity_breached` false, and `last_epoch_index` set to the epoch index of the current clock instant. Stores move between `OPEN`, `RESTRICTED` and `CLOSED`. Restriction halves the effective ceiling: while a location is `RESTRICTED`, its `effective_per_transaction_limit_cents` is the agreement's `per_transaction_limit_cents` divided by two and rounded down. A store may be closed from either `OPEN` or `RESTRICTED`, but only when it holds no `LoadTransaction` whose `load_status` is `INITIATED` or `FUNDED` (`ERR_INVALID_STATE`, HTTP 409), and closing a store cancels its pending float deliveries, moving every `FloatWindow` of that location whose `window_status` is `REQUESTED` or `CONFIRMED` to `CANCELLED`. A location may only be reopened from `RESTRICTED` when the program is `OPEN`. Cash may only be accepted at a store whose `location_status` is `OPEN` (`ERR_LOCATION_NOT_OPEN`, HTTP 409), and only under an agreement whose `agreement_status` is `ACTIVE` (`ERR_AGREEMENT_NOT_ACTIVE`, HTTP 409).

### 3.4. Card Accounts and Taking Cash at the Register

Money needs somewhere to land before a register can accept it. A `PlatformAdmin` or `ProgramManager` opens a `CardAccount` with a payload naming the `program_id` that issues it, the `brand_partner_id` of the brand under which it is issued, a partner-visible `account_ref` that is unique within that program, the `cardholder_name`, and the `cardholder_agreement_type` — `REG_E`, `VOLUNTARY` or `CORPORATE`. That agreement type is the single field that later decides how a dispute is credited, so it is settled here and copied onto every dispute the account generates. A new account opens with `funding_status` of `UNFUNDED`, `compliance_hold_status` of `CLEAR`, `balance_cents`, `ledger_posted_cents` and `ledger_reversed_cents` all at zero, and `is_structuring` false.

The heart of the network is the `LoadTransaction`. A `RetailerClerk` opens one by submitting the `reload_location_id` of the accepting store, the `card_account_id` being funded, the `principal_cents` of cash tendered, and the `expected_card_account_version` required by §2.7. The load starts in `INITIATED`, and its price is computed at creation rather than at funding.

The convenience fee is a marginal tier walk over the principal. The first band runs from 0 to 2000 cents and is flat: any load whose principal exceeds 0 pays a flat 199 cents, so a 1500-cent load and a 2000-cent load pay the same opening fee. The second band runs from 2000 to 10000 cents and its 249-cent rate is proportional rather than flat: the fee adds 249 cents multiplied by the fraction of that band the principal actually covers, where the band spans 8000 cents, so the covered span is the principal minus 2000 capped at 10000. The third band opens above 10000 cents and contributes a flat 399 cents whenever the principal exceeds 10000. Bands the principal never reaches contribute nothing — the walk stops as soon as the running principal no longer exceeds the band's lower bound — and the whole running fee is rounded half-up to two decimal places exactly once, at the end of the walk. The three tier values are fixed constants: 199, 249 and 399 cents. A flat reading of the second band, in which any principal above 2000 simply pays 249 flat, is a misreading; the proportional walk is authoritative.

`posted_total_cents` is the principal plus the convenience fee plus any large-load surcharge the schedule applies; the fee's 2-decimal-place scale carries through, so a 3000-cent principal whose fee is `230.13` has a posted total of `3230.13`. The retailer's cut is `retailer_fee_share_cents`, a per-transaction rounded share of the convenience fee, and the remainder is `program_fee_share_cents`, computed as the fee minus the retailer's share. The load also records the epoch index of the current clock instant as its `epoch_index`, and sets `risk_flag` to `STRUCTURING` when the creation itself trips the structuring predicate of §3.6 and to `NONE` otherwise. Creating a load advances the account's `version`.

Admission control runs in a fixed order before the load is accepted, and the order is part of the contract — when more than one of these conditions fails, the earliest one is the one reported. First, the principal must be at least 100 cents, the platform-wide minimum load; a smaller principal is refused with `ERR_MINIMUM_LOAD_AMOUNT` (HTTP 422). Second, the principal must not exceed the store's `effective_per_transaction_limit_cents`; a breach is `ERR_PER_TRANSACTION_LIMIT_EXCEEDED` (HTTP 422). Third, the load's posted total must not push the store past its agreement's `daily_location_limit_cents` — the check adds the store's current `daily_accepted_cents` to the candidate `posted_total_cents` — and a breach is `ERR_DAILY_LOCATION_LIMIT_EXCEEDED` (HTTP 422). Fourth, a load whose principal falls inside the sub-threshold structuring band while the account's `structuring_txn_count` already stands at or above the structuring transaction count is refused with `ERR_STRUCTURING_BAND` (HTTP 422), because the band is closed once the account has been flagged. Fifth, the account's hold dimension must be `CLEAR` (`ERR_ACCOUNT_FROZEN`, HTTP 409), and the account must not be carrying a live alert (`ERR_AML_ALERT_PENDING`, HTTP 409). Only then is the load written.

Funding is a separate, real-time action by the same clerk, and it is the moment money moves. Before it lands, the load must still be `INITIATED` — a `DECLINED` load can never be funded, and the refusal is `ERR_ALREADY_TERMINAL` (HTTP 409), while a load in any other non-permitted source state surfaces `ERR_INVALID_STATE` (HTTP 409) — the account must still be `CLEAR` (`ERR_ACCOUNT_FROZEN`), the program must still be `OPEN` (`ERR_PROGRAM_FROZEN`), and the window trip that the load would produce must not exceed the velocity transaction limit or the velocity amount limit under the active variant, else `ERR_VELOCITY_LIMIT_EXCEEDED` (HTTP 422). A load that lands exactly at a limit is permitted, and it is precisely at that boundary that a `VELOCITY` alert is raised.

A successful funding writes across four entities at once. The load becomes `FUNDED` and stamps `funded_at` with the current clock instant. The account's `balance_cents` and `ledger_posted_cents` both increase by the principal, and `funding_status` becomes `FUNDED`. The store's `daily_accepted_cents` increases by the load's `posted_total_cents` and its `daily_txn_count` increases by one, after which its `aml_velocity_score` and `is_velocity_breached` are recomputed. The agreement's `accrual_pending_cents` increases by the load's `retailer_fee_share_cents` and its `float_position_cents` increases by the load's `posted_total_cents`. The account's window counters — `window_load_count`, `window_load_cents` and `structuring_txn_count` — are recomputed per the active velocity variant, and a `VELOCITY` alert is raised for the account if the recomputed trip now satisfies the predicate. That alert is idempotent: an account never accumulates a second `OPEN` `VELOCITY` alert, and the raised alert captures its observed counts and its `linked_load_ids` as of the moment of raising. Both the program's `open_aml_alert_count` and its `posture_score` are recomputed as part of the same act.

A clerk may also decline a pending load before funding it, supplying an optional `decline_reason`. Declining is permitted only from `INITIATED` — any other source state surfaces `ERR_ALREADY_TERMINAL` (HTTP 409) — and it sets `load_status` to `DECLINED` with `reversal_reason` of `NONE` while mutating no balance, ledger, accrual, float or counter value whatsoever.

Reversing a funded load is a compliance act available to a `ComplianceAnalyst` or a `ComplianceOfficer`, and the payload must name the `reversal_reason` and the `expected_load_transaction_version`. The load must be `FUNDED` (`ERR_INVALID_STATE` otherwise), and the requested reason must be one of `AML_CONFIRMED`, `DISPUTE_FAVOR_CARDHOLDER`, `RETAILER_REQUEST` or `STRUCTURING`; a reason of `NONE` is refused with `ERR_INVALID_REQUEST` (HTTP 400). Hop 1 sets the load to `REVERSED` with the requested reason and stamps `reversed_at`, then unwinds the money: the account's `balance_cents` decreases by the principal but is floored at zero, its `ledger_reversed_cents` increases by the principal, and its `funding_status` is recomputed — becoming `DRAINED` when the balance has been driven to zero; the store's `daily_accepted_cents` decreases by the load's `posted_total_cents` and its `daily_txn_count` decreases by one, with `aml_velocity_score` recomputed; and the agreement's `accrual_pending_cents` decreases by the load's `retailer_fee_share_cents` while its `float_position_cents` decreases by the load's `posted_total_cents`. Hop 2 dismisses the account's `OPEN` `STRUCTURING` alerts if the account's recomputed window trip no longer satisfies the structuring predicate. Hop 3 recomputes the program's `open_aml_alert_count` from the surviving alerts and recomputes its `posture_score`. Reversal advances both the account's and the load's `version`.

A reversed load may be re-instated by a `ComplianceOfficer`, but only through a guarded door. The payload must carry both the `expected_load_transaction_version` and the `expected_card_account_version`. The load must be `REVERSED` (`ERR_LOAD_NOT_REVERSED`, HTTP 409), neither expected version may be stale (`ERR_STALE_VERSION`, HTTP 412), no `POSTED` or `RECOVERED` loss allocation may reference the load — a compensated loss must be un-posted first, and the refusal is `ERR_INVALID_STATE` (HTTP 409) — and the account's hold dimension must not be `FROZEN` (`ERR_ACCOUNT_FROZEN`, HTTP 409). On success the load becomes `SETTLED` with its `settlement_batch_id` cleared to null, the account's `balance_cents` increases by the principal and its `ledger_reversed_cents` decreases by the principal, `funding_status` returns to `FUNDED`, and if the reversal reason was `AML_CONFIRMED` the program's `unallocated_confirmed_loss_cents` is reduced by the principal. Re-instatement is the only path by which a reversed load's money returns; restoring a program or a brand never re-instates a load.

### 3.5. Posture Scoring, Posture Moves and Bank Oversight

A program's `compliance_posture` is a band derived from a score, and the score is driven by breaches. The `posture_breach_count` is the number of confirmed AML alerts for the program plus the number of its brand partners whose `partner_status` is `SUSPENDED` and whose `suspension_source` is `COMPLIANCE` — posture-sourced suspensions are deliberately excluded from that sum so that a posture cascade never sustains itself by counting the very brands it suspended. The `posture_score` then compounds rather than accumulating: with `n` breaches and a decay factor λ, the score is one hundred multiplied by one minus the quantity one minus λ raised to the power `n`. λ is 0.10 by default, and rises to 0.20 whenever the program's `is_oversight_overdue` flag is true or an earlier oversight review remains overdue. The result is clamped to the range 0.00 to 100.00 and rounded half-up to two decimal places after the clamp. Because the form compounds, two breaches at the base decay factor yield 19.00 rather than the 20.00 a linear reading would produce — the compounding form is authoritative.

The `is_oversight_overdue` flag is itself derived: it is true whenever the current logical clock is later than the program's `oversight_review_due_at`. Two eligibility predicates are read off the score, and both are independent of the decay factor: a program becomes eligible to unfreeze at a score of 3.99 or lower, and eligible to freeze at a score of 60.00 or higher. The score never moves the posture on its own. Drift is permitted and merely constrains the next explicit move.

Every posture move is performed by the program's own `BankSponsor` — or by a `PlatformAdmin` — through a program state transition whose payload names the target `to_posture` and the `expected_program_version`. The target must differ from the current `compliance_posture`, else `ERR_INVALID_STATE` (HTTP 409). Eligibility is enforced against the score at request time: a move to `RESTRICTED` requires a score of at least 4.00 and at most 59.99, a move to `FROZEN` requires a score of at least 60.00, and a move to `OPEN` requires a score of at most 3.99. A move that does not meet its band is refused with `ERR_PROGRAM_POSTURE_TRANSITION_BLOCKED` (HTTP 409). Each successful move sets `compliance_posture`, stamps `last_posture_review_at` with the current clock instant, and advances the program's `version` by one.

Moving from `OPEN` to `RESTRICTED` performs a single hop that touches three subordinate collections: every `ACTIVE` brand of the program is suspended with a `suspension_source` of `POSTURE`; every store under the program's agreements whose `location_status` is `OPEN` becomes `RESTRICTED`, and each of those stores has its `aml_velocity_score` increased by 5.00, capped at 100.00; and every agreement of the program whose `agreement_status` is `ACTIVE` becomes `SUSPENDED`.

Moving from `OPEN` to `FROZEN` is the deepest cascade in the system, and its hops are ordered. Hop 1 suspends every brand whose status is `ACTIVE` or `SUSPENDED`, always with a `suspension_source` of `POSTURE`, and closes every store under the program's agreements whose status is `OPEN` or `RESTRICTED`. Hop 2 takes every `OPEN` alert of the program into `UNDER_REVIEW`, recomputing its `severity` to `HIGH` and leaving its `assigned_analyst_id` untouched. Hop 3 pushes every account of the program to a hold dimension of `FROZEN` and stamps each `frozen_at` with the current clock instant. Hop 4 reverses every `FUNDED` load of an account frozen in hop 3, setting `load_status` to `REVERSED` with a `reversal_reason` of `AML_CONFIRMED` and stamping `reversed_at`; for each such load the account's `ledger_reversed_cents` increases by the principal, its `balance_cents` decreases by the principal and is floored at zero, and its `funding_status` is recomputed; the store's `daily_accepted_cents` decreases by the load's `posted_total_cents`, its `daily_txn_count` decreases by one, and the agreement's `accrual_pending_cents` decreases by the load's `retailer_fee_share_cents` while its `float_position_cents` decreases by the load's `posted_total_cents`; the account's window trips and `structuring_txn_count` are then recomputed, and the program's `open_aml_alert_count` and `posture_score` are recomputed. Hop 5 marks every posted loss allocation covering a load reversed in hop 4 as `RECOVERED`, while the program's `allocated_loss_total_cents` is deliberately left unchanged, because both `POSTED` and `RECOVERED` allocations remain allocated. Finally the program's `compliance_posture` becomes `FROZEN`, `last_posture_review_at` is stamped, and its `version` advances.

Moving from `RESTRICTED` to `FROZEN` repeats the same five-hop shape with a narrower opening: hop 1 closes the stores that are `RESTRICTED`, and hops 2 through 5 behave as above, including the reversal of funded loads and the recovery of posted allocations.

Returning to `OPEN` from `RESTRICTED` requires a score of 3.99 or lower and revives only what the posture cascade suspended: brands with a `suspension_source` of `POSTURE` become `ACTIVE` again, while brands suspended by `COMPLIANCE` stay `SUSPENDED`; stores that are `RESTRICTED` become `OPEN`; and the agreements suspended by the posture cascade become `ACTIVE`. Restoring `OPEN` never re-funds or re-instates a load; load-level compensation is always a separate explicit act.

Un-freezing has two doors, and they differ in what they revive. Moving from `FROZEN` back to `RESTRICTED` requires a score of 0.00 or lower, and it restores only partway: stores that the freeze closed become `RESTRICTED` rather than `OPEN`, accounts in `FROZEN` become `REVIEW` rather than `CLEAR`, and the program's `compliance_posture` becomes `RESTRICTED`. Moving from `FROZEN` straight to `OPEN`, also requiring a score of 0.00 or lower, revives brand partners with a `suspension_source` of `POSTURE` to `ACTIVE` and reopens the stores the freeze closed — but it still leaves every account at `REVIEW`, never `CLEAR`, because an unfrozen program is not a cleared network. Neither door compensates: loads reversed by the freeze stay `REVERSED` and posted allocations recovered by the freeze stay `RECOVERED`.

Bank oversight reviews are the counterweight to posture drift. The program's own `BankSponsor`, or a `PlatformAdmin`, records one, optionally attaching a `review_note`. The review computes an `overdue_days` figure as the whole number of days between the program's `oversight_review_due_at` and the current clock, counting only complete days and reporting zero when the review is on time or early — a review performed exactly at the deadline is not late. It then evaluates whether the program passed, which is true exactly when the `open_aml_alert_count` is zero. A review is recorded either way: a late review that passes still counts, because the bank's oversight metric measures completions rather than timeliness. Recording a review increments the sponsor's `oversight_reviews_completed`, stamps the program's `last_posture_review_at` with the current clock, pushes `oversight_review_due_at` forward by 90 days, recomputes the `posture_score` — the decay factor drops back to its base 0.10 value as soon as no overdue review remains — and advances the program's `version`.

### 3.6. AML Monitoring: Velocity, Structuring and Alert Adjudication

Two predicates are monitored continuously, and both are recomputed on every funding, every reversal, and every state transition of the enclosing program.

The velocity trip measures an account's recent load activity against two ceilings: five transactions and 1,000,000 cents of principal. Two window variants are declared, and the system uses each in its own place. The trailing variant looks back 24 hours from the current clock instant, counting loads whose `funded_at` is strictly later than the instant 24 hours ago and no later than the current instant; the window moves with every read and nothing is ever reset, which is why a burst that straddles midnight still counts in full. The epoch-day variant counts loads belonging to the current logical day instead, so it drops to zero at each day rollover and splits the same burst across two days. Under either variant, only loads whose `load_status` is `FUNDED` or `SETTLED` qualify; reversed and declined loads are excluded from both the count (`window_load_count`) and the amount (`window_load_cents`). The breach predicate is that the count reaches the transaction limit or the amount reaches the amount limit under whichever variant is being evaluated, and both boundaries are inclusive. The trailing variant governs per-load admission control and the structuring window; the epoch-day variant governs the location's daily counter and its reset on rollover.

The structuring predicate is a two-tier test with a pinned evaluation order, and the order matters. The server first takes the trailing 24-hour window, using the same inclusive upper and strict lower bound as the velocity window, and identifies the loads whose principal falls inside the sub-threshold band from 9000 to 9999 cents inclusive on both ends. It counts them into `structuring_txn_count` and sums their principal. The count tier is met when that count reaches 3, and the total tier is met when the summed principal reaches 27,000 cents. The account is structuring exactly when *both* tiers are met. The count tier is the key: below three sub-threshold loads the answer is false however large the total, and a load outside the band never contributes to either figure. Three loads of 9000 cents satisfy both tiers and yield true — the account is structuring, and `is_structuring` is true; two loads of 9999 cents sum to 19,998 cents and count only two, so both tiers fail and the answer is false; three loads of 10,000 cents each sit outside the band because 10,000 exceeds the band's upper bound, so they yield false as well.

An `AmlAlert` is filed by a `ComplianceAnalyst` with a payload naming the `program_id`, the `card_account_id`, the `alert_type` — either `VELOCITY` or `STRUCTURING` — the `window_start_at` marked inclusive, the `window_end_at` marked exclusive, and an optional `resolution_note` recorded at filing time. A manually filed `STRUCTURING` alert is only accepted when the account already satisfies the structuring predicate — three or more sub-threshold loads in the trailing window summing to at least 27,000 cents — and otherwise is refused with `ERR_STRUCTURING_SUSPECTED` (HTTP 422). A new alert opens in `OPEN` with a `severity` of `LOW`, `MEDIUM` or `HIGH` computed from the observed window trip, an `observed_txn_count` and an `observed_total_cents` captured from the window at raise time, a `structuring_hit_count` counting the sub-threshold loads at raise time, a `linked_load_ids` list of the loads inside the window that carried the alert, and no assigned analyst. System-raised alerts, by contrast, are raised by the funding path of §3.4 and are idempotent for the velocity type.

An alert moves through `OPEN`, `UNDER_REVIEW`, `CONFIRMED` and `DISMISSED`, and two roles share the work. A `ComplianceAnalyst` may take an `OPEN` alert into review — any other source state is `ERR_INVALID_STATE` (HTTP 409) — which records `assigned_analyst_id` as the analyst's `X-User-ID` and stores the `resolution_note`. The same analyst may return an alert that is `UNDER_REVIEW` to the queue, which sets it back to `OPEN` and clears `assigned_analyst_id` to null so a different analyst may pick it up. A `ComplianceOfficer` may dismiss an alert that is `UNDER_REVIEW`, moving it to `DISMISSED` and decrementing the program's `open_aml_alert_count` before recomputing `posture_score`. The system itself may dismiss an `OPEN` alert when the account's window trip no longer satisfies that alert's predicate — a `STRUCTURING` alert once the account's structuring flag has cleared, or a `VELOCITY` alert once the account's window trip has fallen back below the velocity limits — with the same counter and score effects.

Confirming is the consequential act, and it is reserved to a `ComplianceOfficer` under the segregation rule of §2.10. The alert must be `UNDER_REVIEW`, and the confirming principal must be neither the `raised_by_analyst_id` nor the `assigned_analyst_id`, else `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Confirmation then cascades. Hop 1 sets `alert_status` to `CONFIRMED` and records `confirmed_by_analyst_id` as the confirming operator. Hop 2 pushes the account's hold dimension to `FROZEN` and stamps `frozen_at` with the current clock instant. Hop 3 reverses every `FUNDED` load of that account with a `reversal_reason` of `AML_CONFIRMED`. Hop 4 marks every `POSTED` loss allocation covering a load reversed in hop 3 as `RECOVERED`, again leaving the program's `allocated_loss_total_cents` unchanged. Hop 5 decrements the program's `open_aml_alert_count`, recomputes its `posture_score`, and increases its `unallocated_confirmed_loss_cents` by the principal of each load reversed in hop 3 — these are the confirmed losses that no allocation has yet taken responsibility for.

Reopening reverses the classification without reversing the money. A `ComplianceOfficer` may reopen an alert that is `CONFIRMED` (`ERR_INVALID_STATE` otherwise), setting it back to `UNDER_REVIEW`, clearing `confirmed_by_analyst_id` to null, incrementing the program's `open_aml_alert_count`, and recomputing the score. It does not re-instate the loads that the confirmation reversed; reopen is purely the classification-correction loop. The same is true of dismissing a confirmed alert's consequences: no alert transition ever returns money to a cardholder account.

Account hold moves are the analyst-side complement to alert confirmation. A `ComplianceAnalyst` or `ComplianceOfficer` may move an account's hold dimension directly, targeting `REVIEW`, `CLEAR` or `FROZEN` through the `to_hold_status` field, and the move advances the account's `version`. Entering `REVIEW` from `CLEAR` requires nothing beyond the target. Returning from `REVIEW` to `CLEAR` requires that no non-terminal alert reference the account (`ERR_AML_ALERT_PENDING`, HTTP 409) and that the program not be frozen (`ERR_PROGRAM_FROZEN`, HTTP 409), and it clears `frozen_at` back to null. Freezing from `REVIEW` is unconditional beyond the target; freezing from `CLEAR` is permitted only when the account carries at least one `CONFIRMED` alert or the program is itself `FROZEN`, else `ERR_INVALID_STATE` (HTTP 409). Either freeze performs a three-hop cascade: the hold dimension becomes `FROZEN` with `frozen_at` stamped; the account's `FUNDED` loads are reversed with a `reversal_reason` of `AML_CONFIRMED`; and posted loss allocations covering those loads become `RECOVERED`. Leaving `FROZEN` goes only to `REVIEW` — never straight to `CLEAR`, so a move from `FROZEN` to `CLEAR` is refused with `ERR_INVALID_STATE` (HTTP 409) — and never re-instates a reversed load, though it does recompute `balance_cents` and `funding_status` from the account's posted and reversed ledgers.

### 3.7. Disputes and Error Resolution Across Cardholder Agreements

A `DisputeCase` is opened by a `ComplianceAnalyst` or a `RetailerClerk` against a specific load, with a payload naming the `program_id`, the `load_transaction_id`, the `card_account_id`, the `dispute_reason` — one of `UNAUTHORIZED_LOAD`, `INCORRECT_AMOUNT`, `GOODS_NOT_RECEIVED` or `ERROR_RESOLUTION` — the `claimed_amount_cents`, which must be at least 1, and the `expected_load_transaction_version` required by §2.7. Opening the case advances the disputed load's `version`. The case opens in `OPEN` with `response_round` of 0, copies the account's `cardholder_agreement_type` onto itself so that the recorded agreement can never drift from the account later, and computes `error_resolution_eligible`, which is true exactly when the reason is `ERROR_RESOLUTION` and the disputed load is `FUNDED` or `SETTLED`.

The response deadline is set at creation and depends on the cardholder agreement. A `REG_E` case gives the retailer 24 hours, a `VOLUNTARY` case 48 hours, and a `CORPORATE` case 72 hours; the deadline is the current clock instant plus that many hours, and the comparison is inclusive, so a retailer response arriving exactly at the deadline is in time. A response arriving after it is refused with `ERR_DISPUTE_RESPONSE_WINDOW_CLOSED` (HTTP 409). The `retailer_response_due_at` field is recomputed afresh whenever a case is sent back to the retailer for another round.

Provisional credit follows the agreement too, and the three variants differ in both timing and ceiling. A `REG_E` case grants `provisional_credit_cents` at creation, capped at 2500 cents; a `VOLUNTARY` case grants nothing while the case is open and grants it on entry to `PROGRAM_REVIEW`, capped at 1500 cents; a `CORPORATE` case grants nothing until the case is resolved in the cardholder's favour, capped at 500 cents. In every variant the provisional is the lesser of the claimed amount and the variant's ceiling, and in every variant a case resolved in the retailer's favour drives `provisional_credit_cents` back to zero. One further floor applies to error-resolution work: when `error_resolution_eligible` is true, a `REG_E` case's provisional is floored at 250 cents, so a claimed amount of 100 cents still yields a provisional of 250.

The case moves through a cyclic negotiation. A `RetailerClerk` records the retailer's position from `OPEN`, which requires the current clock to be at or before the deadline (`ERR_DISPUTE_RESPONSE_WINDOW_CLOSED` otherwise) and requires the acting clerk's agreement to be a party to the disputed load's agreement — a response from a clerk whose agreement is not party is refused with `ERR_RETAILER_NOT_PARTY` (HTTP 403). That move advances the case to `RETAILER_RESPONSE`, increments `response_round`, and stores `retailer_position`. The retailer may supplement its narrative while the case sits in `RETAILER_RESPONSE`, provided the deadline has not passed, the acting clerk remains a party, and `response_round` is still below 3 — a third supplemental response is refused with `ERR_INVALID_STATE` (HTTP 409), which is what caps the loop. Each supplemental supersedes the stored `retailer_position` and leaves the status where it was.

From `RETAILER_RESPONSE` a `ComplianceAnalyst` moves the case into `PROGRAM_REVIEW`. A `ComplianceAnalyst` may also send a case in `PROGRAM_REVIEW` back to the retailer for another round, provided `response_round` is still below 3 — the third round must be resolved or escalated rather than returned — and doing so recomputes `retailer_response_due_at`. A case in `RETAILER_RESPONSE` may be escalated by a `ComplianceAnalyst` into `ESCALATED`, and the call may carry an optional `escalation_note` recording why the retailer window was allowed to lapse. Escalation opens only after the retailer window has closed: while the clock is still at or before the deadline the attempt is refused with `ERR_INVALID_STATE` (HTTP 409). A case in `ESCALATED` may be taken into `PROGRAM_REVIEW` by a `ComplianceOfficer`.

Resolution is a `ComplianceOfficer` act performed from `PROGRAM_REVIEW` through a `resolution` of `CARDHOLDER` or `RETAILER`. Resolving for the cardholder sets `case_status` to `RESOLVED_CARDHOLDER`, pins `final_liability_cents` at the full `claimed_amount_cents`, and finalises `provisional_credit_cents` at the agreement variant's amount; it then reverses the disputed load with a `reversal_reason` of `DISPUTE_FAVOR_CARDHOLDER`, decreasing the account's `balance_cents` by the principal with a floor at zero and increasing its `ledger_reversed_cents` by the principal, and recomputes the program's `open_aml_alert_count` and `posture_score`. Resolving for the retailer sets `case_status` to `RESOLVED_RETAILER` and drives both `final_liability_cents` and `provisional_credit_cents` to zero, with no load movement at all.

Closing a case is available to a `ComplianceOfficer` from either resolved state. A case resolved for the retailer requires only that it be in `RESOLVED_RETAILER`. A case resolved for the cardholder is closed only when either at least one loss allocation in `POSTED` or `RECOVERED` status references the case, or the pinned `final_liability_cents` is at most the agreement's `per_transaction_limit_cents` — otherwise the closure is refused with `ERR_INVALID_STATE` (HTTP 409), because a large cardholder-favouring loss must be taken up by an allocation before it can be filed away. Closing sets `case_status` to `CLOSED`, which along with the two resolved states is terminal.

### 3.8. Loss Allocation, Settlement, Clawback and Float

Loss is apportioned across three parties through a `LossAllocation`, raised by a `ComplianceOfficer` or a `PlatformAdmin` with a payload naming the `program_id`, the `load_transaction_id`, the `retailer_agreement_id`, an optional `dispute_case_id` that is null for an AML-produced loss, the `total_loss_cents` to be borne, which must be at least 1, the `allocation_basis` — `FRAUD_LOSS`, `AML_CONFIRMED` or `DISPUTE_FAVOR_CARDHOLDER` — and an optional `retailer_share_cents`. The allocation opens in `DRAFT` with the three shares computed and persisted.

The split is a waterfall, and the order is the contract. First the retailer's layer is capped at the lesser of the total loss and the cited agreement's `per_transaction_limit_cents`; the retailer's share is the lesser of the total loss and that capped layer. What remains after the retailer's share is allocated next to the bank at a percentage that depends on the program type: 15 percent for a `BAAS_PROGRAM_MANAGER` program, and zero percent for an `OWN_BANK_PROGRAM`, so a bank-run program never takes a loss slice. That percentage is applied to the remainder and rounded *down* to a whole cent, and the program absorbs whatever is left — the program share is the remainder minus the bank share. The floor is therefore not a rounding nicety: the program's share deliberately absorbs the remainder so that the three shares sum exactly to the total. Banks are never allocated a slice of the retailer's capped layer, because the bank percentage is applied only to what remains above it. The invariant that the three shares sum exactly to `total_loss_cents` is enforced both when the allocation is created and again when it is posted; a violation is refused with `ERR_LOSS_ALLOCATION_MISMATCH` (HTTP 422).

Posting a draft allocation is a `ComplianceOfficer` act that requires the program to be `OPEN` (`ERR_PROGRAM_FROZEN` otherwise) and re-checks the summation invariant. Posting sets `allocation_status` to `POSTED` and stamps `posted_at` with the current clock instant; it then pins the cited contract by setting the agreement's `contract_version_locked` true, increases the program's `allocated_loss_total_cents` by the total loss, and recomputes the program's confirmed-loss identity modulo the fact that `POSTED` and `RECOVERED` are treated alike. The lock is applied at posting, not at drafting, so a draft allocation does not freeze a contract. Note that a program may be charged through a disputed loss; the posted allocation becomes the retailer's own loss. A `SettlementOperator` later marks a posted allocation `RECOVERED` once the retailer's share has actually been charged through a settlement of the cited agreement, and this leaves `allocated_loss_total_cents` unchanged, because a recovered allocation is still an allocated one. Both the agreement's and the program's `version` advance when an allocation is posted.

Settlement turns a period of loads into a payable. A `SettlementOperator` or a `PlatformAdmin` schedules a `SettlementBatch` by naming the `retailer_agreement_id` of the agreement being settled and the `period_start_at` and `period_end_at` of the period. A new batch opens in `SCHEDULED` with every monetary total initialised to zero. Its lifecycle status is carried on `batch_status`, which is one of `SCHEDULED`, `OPEN`, `SETTLED` or `CLAWED_BACK`, and list queries may filter on the `batch_status` and `retailer_agreement_id` values. Scheduling refuses a period that shares any interior time with an already-open batch of the same agreement — half-open periods that merely touch at an endpoint are adjacent rather than overlapping and are permitted — with `ERR_SETTLEMENT_PERIOD_OVERLAP` (HTTP 409). Opening a scheduled batch requires that no other batch of the same agreement is already `OPEN` and that the agreement's `agreement_status` is `ACTIVE`, else `ERR_AGREEMENT_NOT_ACTIVE` (HTTP 409); opening advances the batch to `OPEN`. Month-to-month, the period boundaries are half-open: the start is inclusive and the end is exclusive. Note that a batch may be opened for a settlement programme into which the retailer has already paid; the settle step refuses a load outside its period with `ERR_LOAD_OUTSIDE_SETTLEMENT_PERIOD` (HTTP 409).

Settling is where the fee arithmetic is finally pinned, and the rounding order is the contract. The batch must be `OPEN`, and at least one load in its period must be `FUNDED` — a period with nothing to settle is refused with `ERR_SETTLEMENT_EMPTY_PERIOD` (HTTP 422). A `ComplianceAnalyst` or `SettlementOperator` may then settle the batch: every `FUNDED` load whose `funded_at` falls inside the half-open period is attached to the batch and becomes `SETTLED`, and the batch fields are computed from them. `gross_principal_cents` is the sum of the attached loads' principal. The retailer's accrual `accrued_retailer_share_cents` is the sum, over the attached loads, of each load's `retailer_fee_share_cents` — and each of those is itself rounded to two decimal places per load, so the accrual is a round-then-sum figure. The amount actually payable, `net_fee_payable_cents`, is computed the other way: the batch's total convenience fee is summed first and then multiplied once by the agreement's `fee_split_retailer_pct`, and the product is rounded half-up to two decimal places — a sum-then-round figure. The two orders genuinely differ, and `settlement_rounding_delta_cents` exists precisely to expose the difference: it is the accrual minus the payable, and it accumulates the per-load rounding drift into a single period-level figure. Neither order may be collapsed into the other. `chargeback_total_cents` is the sum of the total losses of `POSTED` allocations charged to the agreement with a `posted_at` inside the period, and `float_retained_cents` is the float retained by the program through the batch — the sum of the batch's attached loads' `posted_total_cents`, capped at the agreement's current `float_position_cents`. Settling also posts the accrual to the agreement: `settled_fee_total_cents` increases by `accrued_retailer_share_cents` and `accrual_pending_cents` decreases by the same amount. The batch becomes `SETTLED` and stamps `settled_at`.

Clawback unwinds a settled batch, and it is available from a `SettlementOperator` only when the batch is `SETTLED` — a clawback attempted against any other status is refused with `ERR_SETTLEMENT_NOT_SETTLED` (HTTP 409). The request may carry an optional `reason` free-text field recording why the batch is being clawed back. Hop 1 marks the batch `CLAWED_BACK` and reverses every `SETTLED` load of the batch, setting `load_status` to `REVERSED` with a `reversal_reason` of `RETAILER_REQUEST` and adjusting each affected account's balance and ledger. Hop 2 recomputes the accounts' window trips and dismisses any `OPEN` `STRUCTURING` alerts that no longer qualify, and hop 3 recomputes the program's `open_aml_alert_count` and `posture_score`. The agreement's `float_position_cents` decreases by the batch's `float_retained_cents` and its `accrual_pending_cents` is restored by the `accrued_retailer_share_cents`, so the settlement is undone economically as well as on the load rows; the reversal hop itself adjusts each affected account's balance and ledger and the store counters, and deliberately leaves the agreement's accrual and float to this separate compensation.

Float is the physical cash the network keeps on hand, managed as a `FloatWindow` requested by a `SettlementOperator` or a `ProgramManager`. The payload names the `reload_location_id`, the `window_start_at` and `window_end_at` of the delivery, the `armored_carrier` making the delivery, the `float_amount_cents` of cash, which must be at least 1, and an optional `buffer_minutes` clear gap required before and after the window, which defaults to 120. A window opens in `REQUESTED` and moves through `CONFIRMED` and on to `COMPLETED`, or to `CANCELLED` from `REQUESTED`. A requested window is confirmed by a `SettlementOperator`, a requested window may be cancelled, and a confirmed window is completed — completing adds the window's `float_amount_cents` to the agreement's `float_position_cents`. Float windows may not stack up at a location: a candidate window's interval, extended by its `buffer_minutes` on both sides, may not overlap any non-cancelled window of the same location (the stored window being compared as its own unstretched interval), else `ERR_FLOAT_WINDOW_OVERLAP` (HTTP 409). And the network will not let cash pile up beyond its cap: a window may not be requested, nor completed, if doing so would push the agreement's `float_position_cents` past the float cap of 3,000,000 cents, else `ERR_FLOAT_CAP_EXCEEDED` (HTTP 422).

Float windows are the last piece of the operational picture, and they are also the only place where cash physically enters the network without a cardholder on the other side — everything else in this document moves value between a register, an account and the three parties standing behind them.

## 4. Endpoint Definitions

Every operation is mounted under the prefix `/v1`, with the single exception of the administrative clock-setting capability, which is mounted at the API root. Operations that create a new, addressable resource — a sponsor bank, a program, a brand partner, an agreement, a location, a card account, a load, an alert, a dispute, a loss allocation, a settlement batch, a float window — respond with `201 Created` and return the created resource in the envelope's `data`. Operations that modify an existing resource or drive a state machine respond with `200 OK` and return the updated resource. List operations respond with `200 OK` and return an array. The clock-setting capability is the one operation that returns no resource.
