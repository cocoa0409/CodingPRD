# Egg Layer Grading Plant API — Product Requirements Document

## 1. Introduction

A commercial egg layer operation lives and dies by two clocks that never stop: the biological clock of the flock — pullets placed, hens maturing into lay, production peaking and then declining week by week, a single induced molt to buy a second laying cycle, and finally spent-hen depopulation — and the regulatory clock of the grading plant, where cage-free and pasture claims must be substantiated, salmonella surveillance must land inside fixed cadence windows, and every packed dozen must remain traceable from grading run to retailer shipment so a recall can be executed with surgical precision. This document specifies the API for an integrated layer-farm and grading-plant management system that keeps those two clocks synchronized. The system tracks flocks and their age-driven lay curves, converts daily collection records into feed-conversion and cost-per-dozen economics, materializes graded and sized egg lots from candling runs, prices and settles those lots against retailer contracts under two distinct pricing models, and maintains a per-farm compliance posture that can gate lot release and contract activity at any moment.

The design rests on a small set of non-negotiable principles. Every hen and every gradable egg is accounted for by conserved ledgers: mortality, disposition, grading, and compensating void operations must net to zero drift. Duties are segregated — the operator who submits a grading run may not confirm it, and the technician who collects a salmonella sample may not record its result. Time itself is a controlled input: the server runs on a logical clock that operators advance explicitly, and a single daily ops-run checkpoint drives every automatic transition (flock aging, shelf-life expiry, contract expiry, house turnaround, sampling-window scheduling, and posture recomputation) in a pinned processing order. Financial figures follow strict rounding rules, settlement pricing follows a pinned evaluation order, and settlement creation is guarded by optimistic concurrency control against the parent contract. The sections below define the global contract first, then walk each business workflow in narrative form, and close with the endpoint and error catalogues.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

All interactions with the API must be authenticated through a pair of mandatory HTTP headers. Each request must carry `X-User-ID` to identify the acting operator and `X-User-Role` to declare the operational capacity in which they act. The system recognizes exactly six roles, spelled precisely as follows: `PlatformAdmin`, `FarmManager`, `QualityGrader`, `QAManager`, `ContractManager`, and `ComplianceOfficer`. A request that arrives without these headers, or whose declared role is not one of the six declared roles, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is authenticated but not listed among the roles permitted on the target endpoint is rejected with `ERR_FORBIDDEN` (HTTP 403).

The role model follows a segregation-of-duties philosophy. `PlatformAdmin` is the system operator: it creates farms, drives the logical clock, and triggers the daily ops run. `FarmManager` runs the layer operation itself: houses (shared with `PlatformAdmin`), flocks and their molt/depopulation actions, feed deliveries, production days, and spent-hen dispositions. `QualityGrader` is the grading-floor operator and sample collector: it opens and submits grading runs and collects salmonella samples. `QAManager` is the quality-assurance authority: it confirms or voids grading runs, records laboratory results, and releases, holds, or clears holds on egg lots. `ContractManager` owns the commercial side: retailer contracts and their activate/suspend/reinstate actions, lot allocation and shipping, and settlements. `ComplianceOfficer` owns audits and recalls, and shares salmonella-test scheduling with `QualityGrader`. Every `GET` endpoint in the system is open to all six roles.

For every role, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow calls for attribution — for example as `submitted_by` and `confirmed_by` on a grading run, or as `collected_by` and `resulted_by` on a salmonella test — but it never compares `X-User-ID` to any entity's `id`. The single exception to this opacity is the pair of segregation-of-duties checks, which compare `X-User-ID` strings stored on the resource: the operator confirming a grading run must not be the operator recorded in that run's `submitted_by`, and the operator recording a salmonella result must not be the operator recorded in that test's `collected_by`. Either violation is rejected with `ERR_SOD_VIOLATION` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Endpoints that return lists of resources are paginated through two query parameters. The `limit` parameter caps the number of items returned; when omitted it defaults to 10, and it accepts a minimum of 1 and a maximum of 100. The `offset` parameter states how many items to skip and defaults to 0. Paginated list responses carry `limit`, `offset`, `total_count`, and `has_more` in the `meta` object of the envelope.

Unless a list states otherwise, resources sort by `created_at` in ascending order. Three lists refine that default: the egg-lot list breaks `created_at` ties by size-class rank in descending order, so `JUMBO` lots precede `XLARGE`, then `LARGE`, `MEDIUM`, `SMALL`, and finally `PEEWEE` (lots created together share pack timestamps); the production-day list sorts chronologically by `lay_date` ascending; and the feed-delivery list sorts in FIFO order, `delivered_at` ascending with `created_at` ascending as the tie-break. List endpoints also accept optional equality filters named after the resource's own fields — for example `farm_id`, `house_id`, `flock_id`, `grading_run_id`, `contract_id`, `recall_id`, `salmonella_test_id`, `scope_flock_id`, `prior_flock_id`, `status`, `lifecycle_status`, `hold_status`, `size_class`, `test_type`, and `lay_date` — alongside the pagination parameters.

### 2.4. The Logical Clock and the Daily Ops Run

Time in this system is logical, not wall-clock. At startup the server's clock reads exactly `2026-08-01T00:00:00Z`; before any operator call the clock holds that default and never falls back to wall-clock time. A `PlatformAdmin` may set the clock through an admin-only test-driving capability that accepts an ISO 8601 instant in the `to_iso8601` field and answers with the resulting `current_utc`. Every date in the domain — placement dates, pack dates, sell-by dates, contract windows, audit dates, sampling gaps — is an ISO 8601 calendar date interpreted against this logical clock, and every relative rule (a flock's age in weeks, the fourteen-day molt rest, the seven-day cleaning dwell) is evaluated against it.

A second `PlatformAdmin`-only capability, the daily ops-run checkpoint, applies every time-driven rule in one fixed processing order. The run executes six steps, in exactly this sequence: (1) expire egg lots whose sell-by date has passed, processing them in `pack_date` ascending, `created_at` ascending order; (2) expire contracts whose effective window has ended, in `effective_end` ascending order; (3) advance flock age transitions `PLACED` → `GROWING` → `LAYING`, in `placement_date` ascending order (a flock placed at eighteen weeks of age or older passes through both transitions within a single run); (4) advance house turnaround transitions `CLEANING` → `RESTING` after seven days and `RESTING` → `EMPTY` after fourteen days, in `status_changed_date` ascending order; (5) auto-schedule any due environmental salmonella sampling windows, in flock `placement_date` ascending order; and (6) recompute every farm's compliance posture. The run answers with a summary object containing `lots_expired`, `contracts_expired`, `flocks_advanced`, `houses_advanced`, and `tests_auto_scheduled`. Every entity the run mutates has its own `version` incremented and its `updated_at` refreshed.

### 2.5. Common Resource Properties

With one deliberate exception, every resource in the system carries a standard set of system-managed fields. The `id` is a server-minted UUID with no type prefix. The `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first created. The `updated_at` is an ISO 8601 UTC timestamp with three fractional digits refreshed upon any modification. The `version` is a system-managed integer that increments by exactly one with every modification to the resource — and a modification includes system-driven cascades, so when one operation touches several entities (a depopulation that also flips a house, a hold that also suspends a contract), each mutated entity increments its own `version` and refreshes its own `updated_at` independently.

The exception is the production day. A production day is an immutable event log entry: it carries `id` and `created_at` only, and both `updated_at` and `version` are absent from it. Production days support creation and reads; no update or delete operation exists for them.

### 2.6. Units, Precision, and Rounding

Money is counted in integer cents throughout the API: feed is priced in whole cents per kilogram, overheads and pullet costs are integer cents, lot prices and settlement totals are integer cents, and no monetary field ever carries a fractional cent. Where a computed rate or unit cost is genuinely fractional, the rounding rule is always round-half-up, and the number of decimal places is fixed per quantity. Lay rates (`current_lay_rate_pct`, `lay_rate_pct`) and per-dozen costs (`cost_per_dozen_cents`) are rounded half-up to two decimal places. The feed conversion ratio is rounded half-up to three decimal places. Within settlement pricing, the per-dozen price of each line is rounded half-up to zero decimal places — a whole number of cents — before any line amount is computed, and the rebate is likewise rounded half-up to a whole number of cents. Feed quantities are integer kilograms; egg counts, dozen counts, and hen counts are integers.

### 2.7. Optimistic Concurrency Control

Exactly one write in the system carries an optimistic-concurrency guard: creating a settlement against a retailer contract. The request must include `expected_contract_version`, a non-optional integer carrying the `version` of the target `RetailerContract` as last observed by the client. If the contract's current `version` has advanced beyond that observation — for example because another writer created a settlement for an overlapping period (which legitimately supersedes the prior draft), or allocated or shipped lots against the contract — the create is rejected with `ERR_STALE_VERSION` (HTTP 412), preventing the client from settling against a contract state it has not observed. No other endpoint in the system accepts a version field; requests to every other write endpoint are processed without an expected-version input.

### 2.8. Validation Order and Error Precedence

When a single request violates several rules at once, the rejection it receives is not arbitrary: checks are evaluated in twelve fixed priority tiers, and the lowest tier number wins. Tier 1 is authentication — the `X-User-Role` and `X-User-ID` headers must be present and the role must be a declared role, else `ERR_UNAUTHENTICATED` (HTTP 401). Tier 2 is authorization — the role must be listed for the endpoint, else `ERR_FORBIDDEN` (HTTP 403). Tier 3 is segregation of duties — the grading-run confirmer must differ from `submitted_by` and the salmonella result recorder must differ from `collected_by`, else `ERR_SOD_VIOLATION` (HTTP 403); this tier applies only to the grading-run confirm and record-result actions. Tier 4 is existence — every identifier in the path and every foreign-key identifier in the body must resolve, validated left to right with path identifiers first, else `ERR_NOT_FOUND` (HTTP 404). Tier 5 is request schema — required fields present, types correct, enum values valid, integers within their stated bounds, dates well-formed, `period_start` not after `period_end`, and spread/margin consistency with the pricing model, else `ERR_VALIDATION` (HTTP 400); this tier applies to all creation and action payloads. Tier 6 is the target entity's own state machine — the requested transition must be permitted from its current state, else `ERR_INVALID_STATE` (HTTP 409). Tier 7 is the optimistic-concurrency check on settlement creation — `expected_contract_version` must equal the contract's current `version`, else `ERR_STALE_VERSION` (HTTP 412). Tier 8 is cross-entity state gates — the farm posture gate (`ERR_FARM_SUSPENDED`, HTTP 409), the house-empty gate on placement (`ERR_HOUSE_NOT_EMPTY`, HTTP 409), the flock-laying gate on production recording (`ERR_FLOCK_NOT_LAYING`, HTTP 409), and the contract-active gate (`ERR_CONTRACT_INACTIVE`, HTTP 409). Tier 9 is health and claim gates — the lot hold gate (`ERR_LOT_QUALITY_HELD`, HTTP 409), the flock quarantine gate (`ERR_UNRESOLVED_POSITIVE`, HTTP 409), claim compatibility (`ERR_CLAIM_MISMATCH`, HTTP 409), and the one-open-recall-per-farm rule (`ERR_RECALL_ACTIVE`, HTTP 409). Tier 10 is temporal rules — shelf life on shipping (`ERR_SHELF_LIFE_EXCEEDED`, HTTP 422), contract window overlap (`ERR_CONTRACT_WINDOW_OVERLAP`, HTTP 409), audit spacing (`ERR_AUDIT_INTERVAL_TOO_SOON`, HTTP 409), molt age (`ERR_MOLT_AGE_INELIGIBLE`, HTTP 422), molt rest duration (`ERR_MOLT_REST_TOO_SHORT`, HTTP 422), and sampling cadence (`ERR_SAMPLING_TOO_SOON`, HTTP 409). Tier 11 is domain integrity — one production day per flock and date (`ERR_DUPLICATE_PRODUCTION_DAY`, HTTP 409), hen-count ceilings (`ERR_HEN_COUNT_EXCEEDED`, HTTP 422), feed stock sufficiency (`ERR_FEED_STOCK_EXHAUSTED`, HTTP 422), ungraded-pool sufficiency (`ERR_INSUFFICIENT_UNGRADED_EGGS`, HTTP 422), the size-distribution sum (`ERR_SIZE_DISTRIBUTION_MISMATCH`, HTTP 422), and the molt cap (`ERR_MOLT_LIMIT_REACHED`, HTTP 422). Tier 12 is money and volume — the contract open-dozen cap (`ERR_CONTRACT_VOLUME_EXCEEDED`, HTTP 422) and the non-empty settlement requirement (`ERR_SETTLEMENT_EMPTY`, HTTP 422). Because lower tiers win, an unauthenticated caller is told so before any business rule is examined, and a stale contract version surfaces before, say, an empty-settlement rejection on the same request.

### 2.9. Identifier Resolution and Existence Checks

The resource topology is flat: every entity is a top-level peer, and relationships are expressed through foreign-key fields in request bodies and list filters rather than through nested URLs. Each action endpoint addresses its target by a single identifier in the path — `farmId`, `houseId`, `flockId`, `feedDeliveryId`, `productionDayId`, `gradingRunId`, `lotId`, `contractId`, `settlementId`, `salmonellaTestId`, `complianceAuditId`, `recallId`, or `dispositionId` as applicable. Existence checking validates the path identifier first and then any foreign-key identifiers in the body, working left to right, and the first identifier that does not resolve to an existing resource produces `ERR_NOT_FOUND` (HTTP 404).

### 2.10. Conserved Quantities: the Hen Ledger, the Egg Ledger, and the Feed Queue

Three conservation principles run underneath every workflow in §3, and the server maintains them automatically. First, the hen ledger: for any flock, `initial_hen_count` always equals `current_hen_count` plus the sum of `mortality_count` across the flock's production days plus the sum of `hen_count` across the flock's completed, non-voided dispositions. Completing a disposition deducts hens; voiding a completed disposition restores exactly the same hens; net drift must be zero. Second, the egg ledger: for any flock, the sum of `eggs_collected` minus `rejected_eggs` across its production days always equals `ungraded_egg_pool` plus the sum of `eggs_to_grade` across the flock's confirmed, non-voided grading runs. Confirming a run deducts its draw from the pool; voiding a confirmed run returns exactly that draw (and reclaims the loose remainders it released); net drift must be zero. Undergrades — cracked, dirty, and blood-spot eggs found at candling — are part of `eggs_to_grade` and therefore remain inside the second term of this invariant; they never enter lots. Third, feed is consumed from a per-farm FIFO queue of deliveries, oldest delivery first, so a kilogram issued to a flock is always costed against the oldest remaining stock.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Operation: Farms, Houses, and Flock Placement

Everything begins with a **Farm**, created by a `PlatformAdmin` with a display `name`, a `certification_program` of `CONVENTIONAL`, `CAGE_FREE`, or `PASTURE`, and a `daily_overhead_cents` of zero or more — the fixed daily overhead that will later be allocated into cost-per-dozen. The certification program is not decorative: it drives the shelf-life days stamped onto every egg lot and becomes the `claim_program` snapshot each lot carries. A new farm's `compliance_posture` starts at `CLEAR`, and its `active_flock_count` starts at zero; thereafter `active_flock_count` is computed as the number of flocks, reached through the farm's houses, whose status is anything other than `DEPLETED`, and `compliance_posture` is derived by the posture rules of §3.8.

Houses come next, created by a `PlatformAdmin` or a `FarmManager` with the parent `farm_id`, an operator-chosen `house_code` that must be unique within the farm, an `environment_type` of `CAGED`, `AVIARY`, or `PASTURE_RANGE`, and a `capacity_hens` greater than zero. A house is born in `EMPTY` status with `status_changed_date` stamped to the clock date and `current_flock_id` unset. The house status cycle is `EMPTY` → `OCCUPIED` → `DEPOPULATING` → `CLEANING` → `RESTING` → back to `EMPTY`; the first three transitions are driven by flock events, and the last two by the daily ops run as described in §3.9.

With an `EMPTY` house available, a `FarmManager` places a **Flock** by supplying the `house_id`, a free-form `breed_code` label (for example `HYLINE_BROWN`), the breed's `breed_peak_rate_pct` peak lay percentage (for example 95.0, which feeds the lay-curve projection), a `placement_date` that must not be later than the current clock date (a future placement date is rejected with `ERR_VALIDATION`, HTTP 400), an `initial_hen_count` greater than zero and no more than the house's `capacity_hens`, and a `pullet_cost_cents` acquisition cost of zero or more that will be amortized over 420 days into cost-per-dozen. Placement into a house that is not `EMPTY` is rejected with `ERR_HOUSE_NOT_EMPTY` (HTTP 409). The new flock starts in `PLACED` status with `quarantine_status` `CLEAR`, `lay_cycle` `FIRST`, and `molt_count` zero. Placement also links the flock's self-referential `prior_flock_id` to the house's most recently depleted flock — selected as the house's flock in `DEPLETED` status with the latest `depleted_date`, ties broken by the earliest `created_at` — or leaves it null for the house's first flock, which is how the system expresses flock turnover inside a house. In the same operation the house cascades from `EMPTY` to `OCCUPIED`, its `current_flock_id` is set to the new flock, its `status_changed_date` is stamped to the clock date, and its `version` increments.

### 3.2. The Flock Lifecycle: Growth, the Lay Curve, Molting, and Depopulation

A flock's age drives everything. `age_weeks` is computed as the number of whole weeks between `placement_date` and the current clock date — the day difference divided by seven and rounded down. The daily ops run moves a `PLACED` flock to `GROWING` once `age_weeks` reaches at least 1, and a `GROWING` flock to `LAYING` once `age_weeks` reaches at least 18; each advance increments the flock's `version` by 1. A flock placed already at or past 18 weeks of age walks both steps in a single ops run.

While a flock is `LAYING`, its `current_lay_rate_pct` projects the percentage of hens expected to lay each day; at any other status the rate reads exactly 0.00, and it is recomputed whenever `age_weeks`, `lay_cycle`, or `status` changes. The projection works from the flock's `breed_peak_rate_pct` as its peak. Below 18 weeks of age the base rate is 0. From week 18 through week 20 the base ramps linearly toward peak: the peak multiplied by the number of weeks past week 17, divided by 4. From week 21 through week 30 the base holds at the full peak. Beyond week 30 the base declines by 0.015 of peak per week past week 30 — that is, the peak multiplied by the larger of one minus 0.015 times the number of weeks beyond 30, and a floor of 0.40, so production never projects below forty percent of peak. A flock in its `SECOND` lay cycle — one that has completed a molt — multiplies the resulting base by a post-molt factor of 0.85. The final rate is rounded half-up to two decimal places. Read against a peak of 95.0, the curve produces 23.75 at week 18, 71.25 at week 20, a plateau of 95.00 from week 21 through week 30, 93.58 at week 31, 52.25 at week 60 for a `FIRST`-cycle flock against 44.41 for a `SECOND`-cycle flock, 50.83 at week 61 for `FIRST` against 43.20 for `SECOND`, and the floor values of 38.00 (`FIRST`) and 32.30 (`SECOND`) from week 70 onward.

A `FarmManager` may induce a molt in a `LAYING` flock, moving it to `MOLT_REST`, only when three conditions hold: the flock's `age_weeks` is at least 60 — exactly 60 is eligible — else `ERR_MOLT_AGE_INELIGIBLE` (HTTP 422); its `molt_count` is still below the hard cap of 1 completed molt, else `ERR_MOLT_LIMIT_REACHED` (HTTP 422); and its `quarantine_status` is `CLEAR`, else `ERR_UNRESOLVED_POSITIVE` (HTTP 409). Inducing the molt stamps `molt_started_date` to the clock date, drops `current_lay_rate_pct` to 0.00 for the duration of the rest, and increments the flock's `version` by 1.

Returning from molt rest is the mirror action: a `FarmManager` resumes lay, moving the flock from `MOLT_REST` back to `LAYING`, only once the clock date is at least 14 days after `molt_started_date`; an earlier attempt is rejected with `ERR_MOLT_REST_TOO_SHORT` (HTTP 422). Resuming increments `molt_count` by 1, sets `lay_cycle` to `SECOND` (so the lay curve thereafter applies the 0.85 post-molt factor), and increments the flock's `version` by 1.

When a flock's productive life ends, a `FarmManager` begins depopulation, moving the flock from `LAYING` — or directly from `MOLT_REST`, if the decision is made mid-rest — to `DEPOPULATING`. The move cascades to the house: its status flips from `OCCUPIED` to `DEPOPULATING` with `status_changed_date` stamped to the clock date, and both the flock's and the house's `version` increment by 1. There are no preconditions on depopulation itself. The terminal step, `DEPOPULATING` → `DEPLETED`, is not an action anyone calls: it fires automatically when `current_hen_count` reaches zero after a disposition completes (see §3.9). Reaching `DEPLETED` stamps `depleted_date` to the clock date, cascades the house from `DEPOPULATING` to `CLEANING` with `status_changed_date` restamped, clears the house's `current_flock_id` to null, and increments the flock's `version` by 1.

Several flock figures are computed rather than stored as inputs. `current_hen_count` is `initial_hen_count` minus `cumulative_mortality` minus the total `hen_count` of completed, non-voided dispositions, where `cumulative_mortality` is the sum of `mortality_count` across the flock's production days. `cumulative_eggs` is the sum of `eggs_collected` across those days. `ungraded_egg_pool` is the sum of `eggs_collected` minus `rejected_eggs` across the flock's production days, less the sum of `eggs_to_grade` across the flock's confirmed, non-voided grading runs. `loose_egg_pool` accumulates the sub-dozen remainder eggs released by confirmed grading runs — each size class contributes its count modulo 12. The single-flock read exposes these computed fields alongside `age_weeks` and `current_lay_rate_pct`.

### 3.3. Feed Intake, Daily Production Records, and Flock Economics

Feed arrives as a **FeedDelivery**, recorded by a `FarmManager` with the `farm_id`, a `delivered_at` date, a `quantity_kg` greater than zero, and a `cost_per_kg_cents` greater than zero. A delivery's `remaining_kg` starts equal to `quantity_kg`, and its status is derived: `ACTIVE` while kilograms remain, flipping to `DEPLETED` when `remaining_kg` reaches zero. The farm's deliveries form a single FIFO queue ordered by `delivered_at` ascending with `created_at` ascending as the tie-break.

Once a flock is `LAYING`, a `FarmManager` records one **ProductionDay** per date with `flock_id`, `lay_date`, `eggs_collected`, `rejected_eggs`, `feed_issued_kg`, and `mortality_count`. The flock must be `LAYING`, else `ERR_FLOCK_NOT_LAYING` (HTTP 409). The `lay_date` must be on or after the flock's `placement_date` and not later than the clock date, and only one production day may exist per flock per date — a duplicate is rejected with `ERR_DUPLICATE_PRODUCTION_DAY` (HTTP 409). `eggs_collected` is the total eggs collected that day, zero or more, including rejects; `rejected_eggs` is the cracked and dirty eggs removed at collection, zero or more and no more than `eggs_collected`; `feed_issued_kg` is the feed issued to the flock that day, zero or more; `mortality_count` is the dead hens removed that day, zero or more and no more than the flock's `current_hen_count`, else `ERR_HEN_COUNT_EXCEEDED` (HTTP 422). Because a production day is an immutable event (§2.5), these figures can never be edited after creation.

Issued feed is costed against the farm's FIFO queue at creation time, chronologically. The system walks the farm's deliveries with `remaining_kg` above zero from oldest to newest, taking from each layer the smaller of the outstanding need and that layer's `remaining_kg`, multiplying each take by the layer's `cost_per_kg_cents`, and accumulating integer cents with no rounding until the day's `feed_issued_kg` is fully covered; each layer's `remaining_kg` is reduced by what was taken. If the farm's total remaining stock across the queue is less than `feed_issued_kg`, the creation is rejected outright with `ERR_FEED_STOCK_EXHAUSTED` (HTTP 422) and nothing is consumed. The accumulated cost lands on the record as `feed_cost_cents`.

Two more computed fields land on each production day. `hens_at_start` snapshots the flock's `current_hen_count` immediately before that record's mortality is applied. `lay_rate_pct` is `eggs_collected` multiplied by 100 and divided by `hens_at_start`, rounded half-up to two decimal places — and reads exactly 0.00 when `hens_at_start` is zero. Recording the day then updates the flock ledgers: `cumulative_eggs` grows by `eggs_collected`, `cumulative_mortality` grows by `mortality_count`, `current_hen_count` falls by `mortality_count`, `ungraded_egg_pool` grows by `eggs_collected` minus `rejected_eggs`, and the flock's `version` increments by 1.

A computed economics read — available to `PlatformAdmin`, `FarmManager`, and `ContractManager` — answers cost and efficiency questions for a flock over a period bounded by the `period_start` and `period_end` query parameters (both inclusive) and shaped by the `variant` parameter. The response carries `cost_per_dozen_cents`, `feed_conversion_ratio`, `total_eggs`, `feed_cost_cents`, `overhead_cents`, `amortization_cents`, and `spent_hen_credit_cents`.

The feed conversion ratio aggregates the flock's production days whose `lay_date` falls within the inclusive period. It divides the total kilograms of feed issued across the window by the total egg mass collected, where egg mass in kilograms is the sum of `eggs_collected` across the window multiplied by an average egg weight in grams and divided by 1000. The average egg weight defaults to 60 grams until the flock has a confirmed, non-voided grading run; once one exists, it becomes the size-weighted average over the most recently confirmed run's six size-class counts, using reference weights of 42 grams for `PEEWEE`, 49 for `SMALL`, 56 for `MEDIUM`, 63 for `LARGE`, 70 for `XLARGE`, and 77 for `JUMBO` — each class count multiplied by its reference weight, the products summed, and the sum divided by the total count of eggs in the six size classes. The ratio itself is rounded half-up to three decimal places, and it is reported as null when the egg mass over the window is zero.

The cost per dozen comes in two variants, and both share three period terms. Across the flock's production days in the inclusive window, `hens_at_start` is summed into the flock's hen-days; the same sum over all production days of all flocks of the same farm in the window gives farm hen-days; and the flock's share is the ratio of the two — which is 1 when the farm has a single flock. `overhead_cents` is then the farm's `daily_overhead_cents` multiplied by the number of days in the period and by the flock's share, rounded half-up. `amortization_cents` is the flock's `pullet_cost_cents` multiplied by the number of days in the period and divided by 420 — the fixed amortization horizon — rounded half-up. `spent_hen_credit_cents` is the sum of `revenue_cents` over the flock's completed, non-voided dispositions whose `completed_date` falls within the inclusive period.

The `ACTUAL_FIFO` variant works from trailing actuals and is the variant a `COST_PLUS` settlement uses at finalize time. `feed_cost_cents` is the sum of the window's recorded `feed_cost_cents` values (the FIFO layer costs), and `total_eggs` is the sum of `eggs_collected` over the window. The cost per dozen is then the sum of feed cents, overhead cents, and amortization cents, minus the spent-hen credit, the difference multiplied by 12 and divided by `total_eggs`, rounded half-up to two decimal places. When `total_eggs` is zero the economics read is rejected with `ERR_VALIDATION` (HTTP 400); when a `COST_PLUS` settlement is finalized over a period with zero eggs, the finalize instead fails with `ERR_SETTLEMENT_EMPTY` (HTTP 422).

The `PROJECTED_STANDARD` variant supports forward-looking quotes. Its egg projection applies the lay-curve projection evaluated at the flock's `age_weeks` as of `period_end`, using the current `lay_cycle`, `breed_peak_rate_pct`, and `status`: projected eggs equal `current_hen_count` multiplied by that projected rate divided by 100 and by the number of days in the period, rounded half-up to a whole number. Its feed term prices a standard intake of 115 grams per hen per day: `current_hen_count` multiplied by 115 and by the number of days in the period, divided by 1000 to reach kilograms, then multiplied by the `cost_per_kg_cents` of the farm's most recent feed delivery — the one with the latest `delivered_at`, ties broken by earliest `created_at` — and rounded half-up to cents. Overhead in this variant uses projected hen-days: the flock's projected hen-days are `current_hen_count` times the number of days in the period, the farm's projected hen-days are the same figure summed over all of the farm's flocks, and the share and `overhead_cents` follow the same formula as the actual variant. Amortization and the spent-hen credit are identical in both variants. The projected cost per dozen is the sum of feed cents, overhead cents, and amortization cents, minus the spent-hen credit, multiplied by 12 and divided by the projected eggs, rounded half-up to two decimal places.

### 3.4. Grading Runs and Lot Materialization

Grading converts a flock's pooled eggs into sellable lots, and it does so under segregation of duties. A `QualityGrader` opens a **GradingRun** with the `flock_id`, a whole-run `grade` of `AA`, `A`, or `B`, and `eggs_to_grade` — the number of eggs to draw from the flock's `ungraded_egg_pool`, greater than zero and no more than the pool, else `ERR_INSUFFICIENT_UNGRADED_EGGS` (HTTP 422); the same pool check runs again at confirm time, because intervening runs may have drained it. A new run starts in `DRAFT`.

The grader then submits the candling results, moving the run from `DRAFT` to `SUBMITTED`. The payload carries six size-class counts — `peewee_count`, `small_count`, `medium_count`, `large_count`, `xlarge_count`, and `jumbo_count` — and three undergrade counts found at candling — `cracked_count`, `dirty_count`, and `blood_spot_count` — each zero or more. The nine counts must sum exactly to `eggs_to_grade`; any other total is rejected with `ERR_SIZE_DISTRIBUTION_MISMATCH` (HTTP 422). Submitting stamps `submitted_by` with the caller's `X-User-ID` and increments the run's `version` by 1.

Confirmation is a different desk: a `QAManager` confirms a `SUBMITTED` run, and the confirming `X-User-ID` must differ from `submitted_by`, else `ERR_SOD_VIOLATION` (HTTP 403); the pool check re-validates that the flock's `ungraded_egg_pool` still covers `eggs_to_grade`, else `ERR_INSUFFICIENT_UNGRADED_EGGS` (HTTP 422). Confirming stamps `confirmed_by` and sets `pack_date` to the clock date, then materializes lots in a fixed, deterministic order — `JUMBO` first, then `XLARGE`, `LARGE`, `MEDIUM`, `SMALL`, and finally `PEEWEE`. For each size class, the class count divided by 12 and rounded down gives the whole dozens; when that dozen figure is greater than zero an **EggLot** is created carrying that `size_class`, the run's `grade`, the computed `dozen_count`, a `claim_program` snapshotted from the farm's `certification_program` at that moment, the run's `pack_date`, and a `sell_by_date` computed as `pack_date` plus the shelf life for the claim program — 45 days for `CONVENTIONAL`, 30 days for `CAGE_FREE`, and 30 days for `PASTURE`. Each new lot starts with `lifecycle_status` `FRESH` and `hold_status` `CLEAR`, linked back through `grading_run_id`, `flock_id`, and a denormalized `farm_id` taken via the flock's house so recall sweeps can find it. The remainder eggs of each class — the class count modulo 12 — flow into the flock's `loose_egg_pool`, while the flock's `ungraded_egg_pool` falls by the full `eggs_to_grade`, keeping the egg ledger of §2.10 conserved. The run's `lot_ids` records the created lot identifiers in that same deterministic creation order, and both the grading run's and the flock's `version` increment by 1.

Voiding is the compensating action, available to a `QAManager`. Voiding a `DRAFT` or `SUBMITTED` run simply moves it to `VOIDED` and increments its `version` by 1. Voiding a `CONFIRMED` run is a true reversal and is permitted only while no child lot has reached `SHIPPED`, `CLOSED`, or `RECALLED` — otherwise the request is rejected with `ERR_INVALID_STATE` (HTTP 409). The compensation walks every child lot still in `FRESH`, `RELEASED`, or `ALLOCATED` and moves it to `EXPIRED`; a lot that was `ALLOCATED` first releases its contract — the contract's `allocated_dozen` falls by the lot's `dozen_count` and the lot's `contract_id` is cleared. The full `eggs_to_grade` draw returns to the flock's `ungraded_egg_pool`, and the loose remainders the run released — the sum, over the six size counts, of each count modulo 12 — are deducted back out of `loose_egg_pool`. Both the run's and the flock's `version` increment by 1.

### 3.5. The Egg Lot Journey: Release, Quality Holds, Allocation, and Shipping

An egg lot carries two parallel status dimensions on one row. The first, `lifecycle_status`, walks the commercial path `FRESH` → `RELEASED` → `ALLOCATED` → `SHIPPED` → `CLOSED`, with two side exits to `EXPIRED` and `RECALLED`; `CLOSED`, `EXPIRED`, and `RECALLED` are terminal. The second, `hold_status`, toggles between `CLEAR` and `HELD` entirely independently — a hold transition never changes the lifecycle, and a lifecycle transition never changes the hold. Lots are created only by grading-run confirmation; there is no direct lot-creation endpoint.

Release is the quality gate that makes a lot sellable: a `QAManager` moves a `FRESH` lot to `RELEASED`, and three gates guard the move. The lot's `hold_status` must be `CLEAR`, else `ERR_LOT_QUALITY_HELD` (HTTP 409); the farm's `compliance_posture` must not be `SUSPENDED`, else `ERR_FARM_SUSPENDED` (HTTP 409); and the flock's `quarantine_status` must be `CLEAR`, else `ERR_UNRESOLVED_POSITIVE` (HTTP 409). Releasing increments the lot's `version` by 1.

A `QAManager` may place a quality hold on any lot whose lifecycle is `FRESH`, `RELEASED`, or `ALLOCATED`, provided the hold is currently `CLEAR` — toggling otherwise is rejected with `ERR_INVALID_STATE` (HTTP 409). The hold sets `hold_status` to `HELD`, leaves the lifecycle untouched, and increments the lot's `version` by 1. Holding an `ALLOCATED` lot has teeth: the contract's `held_allocated_dozen` — the sum of `dozen_count` over its allocated lots currently `HELD` — rises above zero, and any positive `held_allocated_dozen` automatically suspends the contract, cascading it from `ACTIVE` to `SUSPENDED` and auto-voiding every `DRAFT` settlement of that contract. Clearing a hold is the same three-lifecycle action in reverse: the hold must currently be `HELD`, else `ERR_INVALID_STATE` (HTTP 409), and the flock's `quarantine_status` must be `CLEAR`, else `ERR_UNRESOLVED_POSITIVE` (HTTP 409) — a hold that exists because of a quarantine cannot be cleared by hand while the quarantine stands. Clearing sets `hold_status` back to `CLEAR`, recomputes `held_allocated_dozen`, and increments the lot's `version` by 1; deliberately, clearing the last held allocated lot does not by itself reinstate a suspended contract — reinstatement is a separate, explicit act (§3.6).

Allocation is where lots meet contracts: a `ContractManager` allocates a `RELEASED` lot by supplying the target `contract_id`, moving the lot to `ALLOCATED`. Five gates apply. The lot's `hold_status` must be `CLEAR`, else `ERR_LOT_QUALITY_HELD` (HTTP 409). The contract must be `ACTIVE`, else `ERR_CONTRACT_INACTIVE` (HTTP 409). The clock date must fall within the contract's effective window — on or after `effective_start` and strictly before `effective_end` — else the same `ERR_CONTRACT_INACTIVE` (HTTP 409), because outside its window a contract is not in force. The lot's claim must satisfy the contract's `claim_required`: `NONE` accepts every claim program; `CAGE_FREE` accepts a lot whose `claim_program` is `CAGE_FREE` or `PASTURE`; `PASTURE` accepts only a `PASTURE` lot — a failure is `ERR_CLAIM_MISMATCH` (HTTP 409). And the volume must fit: the contract's `allocated_dozen` plus the lot's `dozen_count` must not exceed `max_open_dozen`, else `ERR_CONTRACT_VOLUME_EXCEEDED` (HTTP 422). Allocating sets the lot's `contract_id`, adds its `dozen_count` into the contract's `allocated_dozen`, and increments both the lot's and the contract's `version` by 1.

Shipping completes the commercial leg: a `ContractManager` ships an `ALLOCATED` lot, moving it to `SHIPPED`. The lot's `hold_status` must be `CLEAR`, else `ERR_LOT_QUALITY_HELD` (HTTP 409), and the clock date must be on or before the lot's `sell_by_date` — equality ships on the last day — else `ERR_SHELF_LIFE_EXCEEDED` (HTTP 422). Shipping stamps `ship_date` to the clock date, moves the lot's `dozen_count` from the contract's `allocated_dozen` into its `shipped_dozen` (which sums the dozens of lots `SHIPPED` or `CLOSED` on the contract), and increments both versions by 1. The final step to `CLOSED` is not an action; it arrives by cascade when a settlement covering the lot is finalized (§3.6).

Shelf life is also enforced from the other side by the daily ops run. Any lot still in `FRESH`, `RELEASED`, or `ALLOCATED` whose `sell_by_date` is strictly before the clock date moves to `EXPIRED`, processed in `pack_date` ascending, `created_at` ascending order. Expiring a `FRESH` or `RELEASED` lot simply increments its `version` by 1; expiring an `ALLOCATED` lot additionally releases the contract — `allocated_dozen` falls by the lot's `dozen_count`, `contract_id` is cleared — and increments both versions by 1. The `RECALLED` exit belongs to the recall sweep of §3.8.

### 3.6. Retailer Contracts and Settlement Pricing

A `ContractManager` opens a **RetailerContract** with the `farm_id`, a `retailer_name`, a `pricing_model` of `MARKET_INDEX` or `COST_PLUS`, and the commercial terms. `spread_cents` — the cents added to the market index per dozen — is zero or more, belongs to `MARKET_INDEX` contracts, and must be exactly 0 on a `COST_PLUS` contract; `margin_pct` — the cost-plus margin fraction — is zero or more, belongs to `COST_PLUS` contracts, and must be exactly 0 on a `MARKET_INDEX` contract; a payload inconsistent with its pricing model is rejected with `ERR_VALIDATION` (HTTP 400). `claim_premium_pct`, zero or more, is the extra per-dozen price multiplier that applies whenever `claim_required` is something other than `NONE`. `claim_required` itself — `NONE`, `CAGE_FREE`, or `PASTURE` — sets the minimum claim a lot must satisfy to allocate. The effective window runs from `effective_start` inclusive to `effective_end` exclusive — a half-open window — and `effective_start` must precede `effective_end`. `weekly_min_dozen`, zero or more, records the weekly volume commitment as a reference figure, while `max_open_dozen`, greater than zero, caps the dozens that may be allocated but unshipped at any moment. Among contracts of the same farm that have not reached `EXPIRED`, the half-open windows must not overlap — touching at a boundary is allowed — and the check runs both at creation and again at activation, where a violation is rejected with `ERR_CONTRACT_WINDOW_OVERLAP` (HTTP 409). A new contract starts in `DRAFT`.

Activation moves a contract from `DRAFT` to `ACTIVE`: the window overlap is re-checked, and the farm's `compliance_posture` must not be `SUSPENDED`, else `ERR_FARM_SUSPENDED` (HTTP 409); the contract's `version` increments by 1. Suspension moves an `ACTIVE` contract to `SUSPENDED` and arrives three ways — a `ContractManager` suspending it directly, the farm posture cascading to `SUSPENDED` (§3.8), or an allocated lot becoming `HELD` (§3.5) — and in every case each `DRAFT` settlement of the contract is auto-voided and the contract's `version` increments by 1. Reinstatement moves a `SUSPENDED` contract back to `ACTIVE` and requires two things: the farm posture must not be `SUSPENDED`, else `ERR_FARM_SUSPENDED` (HTTP 409), and `held_allocated_dozen` must be zero, else `ERR_LOT_QUALITY_HELD` (HTTP 409); the `version` increments by 1. Finally, the daily ops run expires any contract whose `effective_end` has arrived — the clock date on or after `effective_end` — from `DRAFT`, `ACTIVE`, or `SUSPENDED` into terminal `EXPIRED`, processing contracts in `effective_end` ascending order; expiry from `ACTIVE` or `SUSPENDED` also auto-voids the contract's `DRAFT` settlements, and each transition increments the contract's `version` by 1. Three contract counters are computed: `allocated_dozen` sums the `dozen_count` of its lots currently `ALLOCATED`, `shipped_dozen` sums lots `SHIPPED` or `CLOSED`, and `held_allocated_dozen` sums `ALLOCATED` lots currently `HELD`.

Settlements bill the shipped volume. A `ContractManager` creates a **Settlement** with the `contract_id`, a `period_start` and `period_end` (both inclusive, `period_start` not after `period_end`, else `ERR_VALIDATION`), `market_index_cents` — zero or more, required when the contract prices by `MARKET_INDEX` and ignored for `COST_PLUS` — and the OCC guard `expected_contract_version` described in §2.7, whose mismatch yields `ERR_STALE_VERSION` (HTTP 412). The contract must be `ACTIVE`, else `ERR_CONTRACT_INACTIVE` (HTTP 409). Creation starts the settlement in `DRAFT`, and supersession is immediate: any existing `DRAFT` settlement of the same contract whose period overlaps the new one — the two periods share at least one calendar day — is automatically moved to `VOIDED`. Creating a settlement also increments the parent contract's `version` by 1, which is precisely what makes a stale `expected_contract_version` detectable.

Finalization is a `ContractManager` action that moves a `DRAFT` settlement to `FINALIZED`. The contract must be `ACTIVE`, else `ERR_CONTRACT_INACTIVE` (HTTP 409), and there must be at least one `SHIPPED` lot of the contract whose `ship_date` falls within the inclusive period, else `ERR_SETTLEMENT_EMPTY` (HTTP 422). Finalizing snapshots the contract's `pricing_model` into `pricing_model_used` and computes the bill in a pinned seven-step order, with no reordering permitted. Step one selects the lines: every `SHIPPED` lot of the contract with `ship_date` inside the inclusive period, ordered by `pack_date` ascending with `created_at` ascending as the tie-break; an empty selection is the `ERR_SETTLEMENT_EMPTY` rejection just described. Step two prices each line. Under `MARKET_INDEX` the base is the settlement's `market_index_cents` plus the contract's `spread_cents`. Under `COST_PLUS` the base is the `ACTUAL_FIFO` cost per dozen of §3.3 computed over the settlement period — recorded on the settlement as `cost_per_dozen_cents`, rounded half-up to two decimal places — multiplied by one plus the contract's `margin_pct`; a period with zero eggs fails the finalize with `ERR_SETTLEMENT_EMPTY` (HTTP 422). Either way, the price multiplier is one plus the size premium for the lot's `size_class` plus the grade uplift for the lot's `grade` plus the contract's `claim_premium_pct` when `claim_required` is not `NONE` (and zero when it is). The size premiums are: `JUMBO` 0.20, `XLARGE` 0.10, `LARGE` 0.0, `MEDIUM` negative 0.05, `SMALL` negative 0.10, and `PEEWEE` negative 0.15. The grade uplifts are: `AA` 0.05, `A` 0.0, and `B` negative 0.08. The line's `price_cents_per_dozen` is the base multiplied by this multiplier, rounded half-up to a whole number of cents — the rounding happens per line, before anything is summed. Step three multiplies each line's `price_cents_per_dozen` by its `dozen_count` to get `line_amount_cents`, an exact integer. Step four sums the line amounts into `subtotal_cents`. Step five selects the volume rebate tier from the pre-rebate subtotal — never from the final total: a `subtotal_cents` of at least 500000 earns a `rebate_pct` of 0.04; at least 100000 earns 0.02; anything below earns 0. Step six computes `rebate_cents` as the subtotal multiplied by `rebate_pct`, rounded half-up to a whole number of cents. Step seven sets `total_cents` to `subtotal_cents` minus `rebate_cents`. The finalized `lines` array exposes one entry per covered lot with `lot_id`, `size_class`, `grade`, `dozen_count`, `price_cents_per_dozen`, and `line_amount_cents`, in the selection order of step one. Every covered lot cascades from `SHIPPED` to `CLOSED`, each lot's `version` incrementing by 1, and the settlement's own `version` increments by 1.

A settlement moves from `DRAFT` to `VOIDED` only by system action — supersession by a newer overlapping draft at creation time, or cascade when its contract suspends or expires — and the transition increments the settlement's `version` by 1. `FINALIZED` and `VOIDED` are both terminal.

### 3.7. Salmonella Testing, Quarantine, and the Positive-Result Cascade

Salmonella surveillance is scheduled per flock. A `QualityGrader` or a `ComplianceOfficer` schedules a **SalmonellaTest** with the `flock_id`, a `test_type` of `ENVIRONMENTAL` or `EGG_POOL`, and a `scheduled_date` that must not be earlier than the clock date at creation, else `ERR_VALIDATION` (HTTP 400). The test starts in `SCHEDULED`.

The daily ops run adds a second, automatic scheduling path for environmental surveillance, driven by two windows per flock — evaluated only for flocks that are `LAYING` and whose `quarantine_status` is `CLEAR`. The first window covers `age_weeks` from 40 through 45 inclusive. The second applies only after a completed molt — `molt_count` of at least 1 — and covers the span from 4 through 6 whole weeks after `molt_started_date`, inclusive. When the clock falls inside a window, and no environmental test for the flock already has a `collected_date` inside that window, and no `SCHEDULED` test exists for the flock, the run auto-creates an `ENVIRONMENTAL` test with a pinned `scheduled_date`: for the first window, `placement_date` plus 321 days — the last day on which `age_weeks` still reads 45; for the post-molt window, `molt_started_date` plus 48 days — the last day on which the time since molt still reads 6 weeks. If a window closes entirely with no environmental test for the flock having reached collection inside it, the farm's `compliance_posture` is raised to at least `WATCH` at the next posture recomputation.

Collection is a `QualityGrader` action moving a test from `SCHEDULED` to `COLLECTED`. The clock date must be on or after `scheduled_date`, else `ERR_VALIDATION` (HTTP 400), and collections on the same house must be at least 7 days apart: the gap between this collection and the most recent test on that house that reached `COLLECTED` or beyond must be no less than 7 days — exactly 7 days is allowed — else `ERR_SAMPLING_TOO_SOON` (HTTP 409). Collecting stamps `collected_date` to the clock date and `collected_by` to the caller's `X-User-ID`, and increments the test's `version` by 1.

Recording the result is a `QAManager` action on a `COLLECTED` test, carrying the `result` of `NEGATIVE` or `POSITIVE`. Segregation of duties applies: the recorder's `X-User-ID` must differ from `collected_by`, else `ERR_SOD_VIOLATION` (HTTP 403). The test moves to `RESULTED` with `resulted_by` stamped and its `version` incremented by 1. A `NEGATIVE` result continues automatically to terminal `CLEARED` within the same request. A `POSITIVE` result does not continue: the test holds in `RESULTED` while a six-link cascade fires immediately, in the same request. Link one sets the flock's `quarantine_status` from `CLEAR` to `QUARANTINED`. Link two places every egg lot of that flock whose lifecycle is `FRESH`, `RELEASED`, or `ALLOCATED` and whose hold is `CLEAR` into `HELD` — and when an allocated lot becomes held, its contract's `held_allocated_dozen` rises above zero. Link three suspends every contract whose `held_allocated_dozen` is above zero, moving it from `ACTIVE` to `SUSPENDED`. Link four auto-voids every `DRAFT` settlement of each such suspended contract. Link five auto-creates a **Recall** in `INITIATED` status: its `farm_id` is taken from the flock's house's farm, `salmonella_test_id` points at this test, `scope_flock_id` restricts the recall to this flock, `reason` is `SALMONELLA`, and the pack window spans every `pack_date` found among the held lots. Link six sets the farm's `compliance_posture` to `SUSPENDED`, the unresolved-positive condition of §3.8.

The quarantine dimension on the flock is what unwinds the cascade. While a flock is `QUARANTINED`, lot release, manual clear-hold, and induce-molt are all refused with `ERR_UNRESOLVED_POSITIVE` (HTTP 409). The quarantine lifts only when the linked recall closes (§3.8): closing the recall moves the originating `POSITIVE` test from `RESULTED` to terminal `RESOLVED` and returns the flock's `quarantine_status` to `CLEAR`.

### 3.8. Compliance Audits, Farm Posture, and Recalls

A **ComplianceAudit** is scheduled by a `ComplianceOfficer` with the `farm_id`, a `standard` of `USDA_CAGE_FREE`, `PASTURE_RAISED`, or `FDA_EGG_SAFETY`, and an `audit_date`. Audits of the same farm must be spaced: the new `audit_date` must sit at least 30 days away from the `audit_date` of every audit of that farm that has not yet reached a closed state — the gap applies in either direction, and a gap of exactly 30 days is allowed — else `ERR_AUDIT_INTERVAL_TOO_SOON` (HTTP 409). The audit starts in `SCHEDULED`.

The audit then walks a simple ladder under the `ComplianceOfficer`. Starting a scheduled audit moves it to `IN_PROGRESS` and requires the clock date to be on or after `audit_date`, else `ERR_VALIDATION` (HTTP 400); the `version` increments by 1. Recording findings moves it to `FINDINGS_RECORDED` with a `findings_count` of zero or more and a `corrective_actions_open` of zero or more; when `corrective_actions_open` is above zero the farm's `compliance_posture` moves to `WATCH` — unless the farm is already `SUSPENDED`, which stands — and the audit's `version` increments by 1. Closing the audit carries an `outcome` of `PASSED` or `FAILED`. Closing with `PASSED` requires `corrective_actions_open` to be exactly 0, else `ERR_VALIDATION` (HTTP 400); it stamps `closed_date` to the clock date, moves the audit to terminal `CLOSED_PASSED`, recomputes the farm's posture, and increments the `version` by 1. Closing with `FAILED` stamps `closed_date`, moves the audit to terminal `CLOSED_FAILED`, and fires a two-link cascade: the farm's `compliance_posture` becomes `SUSPENDED` on the strength of a failed audit closed within the trailing 30 days, and every `ACTIVE` contract of the farm moves to `SUSPENDED`, each such suspension auto-voiding the contract's `DRAFT` settlements; the audit's `version` increments by 1.

The farm's `compliance_posture` is a pure derivation, recomputed after every result recording, recall close, audit findings recording or close, and each daily ops run. It is `SUSPENDED` when either of two conditions holds: any salmonella test belonging to the farm's flocks has a `POSITIVE` result and has not yet reached `RESOLVED`; or any audit of the farm closed `FAILED` within the trailing 30 days, inclusive, with no later audit of the farm closed `PASSED`. Failing that, it is `WATCH` when any audit of the farm sits in `FINDINGS_RECORDED` with `corrective_actions_open` above zero, or when any flock has missed a sampling window per §3.7. Otherwise it is `CLEAR`. Two gates key off the posture: lot release and contract activation or reinstatement all require a posture other than `SUSPENDED`, answering with `ERR_FARM_SUSPENDED` (HTTP 409). And the transition into `SUSPENDED` is itself a cascade: every `ACTIVE` contract of the farm moves to `SUSPENDED`, auto-voiding its `DRAFT` settlements.

Recalls are the remediation instrument. A `ComplianceOfficer` opens a **Recall** manually with the `farm_id`, a `reason` of `SALMONELLA`, `QUALITY`, or `LABELING`, a pack window from `pack_window_start` to `pack_window_end` (both inclusive, start not after end), and an optional `scope_flock_id` that restricts the sweep to a single flock — omitted, the recall sweeps the whole farm. A farm may have only one open recall at a time: creating a manual recall while the farm already has one in `INITIATED` or `SCOPED` is rejected with `ERR_RECALL_ACTIVE` (HTTP 409). A manually opened recall starts in `INITIATED` with `salmonella_test_id` null; a recall auto-created by the positive cascade of §3.7 carries that test's id instead.

Scoping is the sweep. A `ComplianceOfficer` executes the scope action on an `INITIATED` recall, moving it to `SCOPED`. The sweep selects egg lots whose `farm_id` equals the recall's farm, whose `flock_id` equals `scope_flock_id` when one is set (all flocks when null), whose `pack_date` falls within the inclusive pack window, and whose `lifecycle_status` is `FRESH`, `RELEASED`, or `ALLOCATED` — and it processes them in `pack_date` ascending, `created_at` ascending order. Each swept lot moves to terminal `RECALLED` with its `recall_id` set to the recall and its `version` incremented by 1; a swept lot that was `ALLOCATED` first releases its contract — `allocated_dozen` falls by the lot's `dozen_count` and `contract_id` is cleared, with the contract's `version` incremented by 1 as well — so recall release and contract accounting stay consistent. The recall's `scoped_lot_count` records how many lots were swept, and zero is a legitimate outcome; the recall's `version` increments by 1.

Closing is the unwind. A `ComplianceOfficer` closes a `SCOPED` recall, moving it to terminal `CLOSED`. When the recall's `salmonella_test_id` is set and that test is still `RESULTED` with a `POSITIVE` result, the test moves to `RESOLVED` and its flock's `quarantine_status` returns to `CLEAR`. The farm's `compliance_posture` is then recomputed and may drop out of `SUSPENDED` — provided no other unresolved positive test and no recently failed audit still holds it there. The recall's `version` increments by 1.

### 3.9. Spent-Hen Disposition, House Turnaround, and Flock Turnover

Depopulation empties a house one disposition at a time. A `FarmManager` plans a **SpentHenDisposition** with the `flock_id`, a `method` of `RENDERING`, `COMPOST`, `LIVE_SALE`, or `EUTHANIZED`, a `hen_count` greater than zero, and a `revenue_cents` of zero or more — the realized revenue that will later be credited into cost-per-dozen as the spent-hen credit. The plan starts in `PLANNED`.

Completion is where hens actually leave: a `FarmManager` completes a `PLANNED` disposition, and two gates apply. The flock must be in `DEPOPULATING`, else `ERR_INVALID_STATE` (HTTP 409), and `hen_count` must not exceed the flock's `current_hen_count`, else `ERR_HEN_COUNT_EXCEEDED` (HTTP 422). Completing deducts `hen_count` from the flock's `current_hen_count` — maintaining the hen ledger of §2.10 — stamps `completed_date` to the clock date, and increments both the disposition's and the flock's `version` by 1. When the deduction brings `current_hen_count` to exactly zero, the flock automatically moves from `DEPOPULATING` to `DEPLETED` — the first cascade link — and its house moves from `DEPOPULATING` to `CLEANING` with `status_changed_date` stamped and `current_flock_id` cleared, the second cascade link.

A completed disposition can still be voided by a `FarmManager` — but only while the flock has not yet reached `DEPLETED`, because hens cannot return to a depleted flock; the attempt otherwise is rejected with `ERR_INVALID_STATE` (HTTP 409). Voiding is the exact compensation: `hen_count` is added back to the flock's `current_hen_count`, the disposition's `revenue_cents` is withdrawn from the spent-hen credit, the disposition moves to terminal `VOIDED`, and both versions increment by 1. Note that voiding is defined only from `COMPLETED`; there is no path that voids a still-`PLANNED` disposition.

The house then completes its turnaround on the daily ops run. A house in `CLEANING` moves to `RESTING` once the clock date is at least 7 days after its `status_changed_date`; a house in `RESTING` moves back to `EMPTY` once the clock date is at least 14 days after its `status_changed_date`. Each step restamps `status_changed_date` to the clock date and increments the house's `version` by 1. Back at `EMPTY`, the house is eligible for the next placement — and that next flock's `prior_flock_id` will link back to the flock just depleted, closing the turnover loop that §3.1 opened.
