# Shellfish Harvest Classification API — Product Requirements Document

## 1. Introduction

Shellfish are filter feeders, and that single biological fact is what makes this product necessary. Whatever is in the water ends up in the animal, so the regulatory apparatus around a shellfish farm is not a paperwork layer bolted onto production — it is the production schedule itself. A rain gauge reading closes a growing area; a closed area silently invalidates every harvest authorization written against the leases inside it; an invalidated authorization strands shellstock that has already been landed and possibly already loaded onto a truck. Today those chains are reconstructed by hand, days later, from three different spreadsheets and a telephone call, which is exactly when an illness cluster is least forgiving.

This document specifies the Shellfish Harvest Classification API, a single system of record shared by a shellfish farm operation and the state shellfish control authority that regulates it. It spans the whole chain of custody: acquiring a lease over a growing area through navigation and environmental siting review; buying certified seed from a hatchery and growing it out through a nursery; deploying bottom, rack-and-bag and floating gear on leased plots with husbandry and predator-control obligations; the authority's sanitary classification of the growing area from fecal-coliform statistics; rainfall closures and the clean-sample record required to reopen; the time-to-temperature clock and the seasonal vibrio management plan that governs it; the tag that carries harvest date, harvest location and dealer certification for traceability; dealer certification and interstate shipper listing; and finally recall and illness-investigation traceback.

The API is mounted under `/shellfish`. Two design commitments run through every section that follows. First, **regulatory acts cascade immediately and completely** — when the authority closes an area, the system itself walks down through authorizations, gear, landed lots and assembled shipments in one atomic request rather than leaving a reconciliation job for tomorrow. Second, **every temporal rule reads a server-controlled logical clock** rather than wall-clock time, so a closure duration, a nursery period or a certificate expiry can be exercised deterministically. Readers implementing this specification should treat §2 as the binding structural contract and §3 as the binding behavioural contract; neither is decorative.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Identity Headers and Role-Based Access Control

Every request to the API — without exception, including the logical-clock endpoint — must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names the role it is acting in. Both must be present and must be non-empty strings; a request that omits either, or supplies an empty string for either, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about the request is examined. Once the headers are accepted, the value of `X-User-Role` is checked against the roles authorised for the addressed endpoint in §4. A role that is not on that endpoint's list — including a value that is not a recognised role name at all — is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

There are exactly five roles, spelled precisely as follows: `ShellfishControlAuthority`, `SitingReviewer`, `FarmOperator`, `HatcheryOperator` and `SeafoodDealer`.

The `ShellfishControlAuthority` is the state shellfish control authority. It owns growing-area registration and classification, all monitoring data (water samples and rainfall events), seed screening, the lease decision, dealer certification and listing, illness investigations, and the seasonal vibrio control plans. When `X-User-Role` is `ShellfishControlAuthority`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity: the server never compares it to any record's `id`, and no ownership check is performed against it.

A `SitingReviewer` records the two clearance legs of a lease application. When `X-User-Role` is `SitingReviewer`, `X-User-ID` is likewise an opaque reviewer identifier not tied to any persisted entity. The server does record it — a navigation finding is stamped onto the lease as `navigation_reviewer_user_id` and an environmental finding as `environmental_reviewer_user_id` — but it is never compared to any entity's `id`. What the server does compare it to is the *sibling* reviewer identifier already recorded on the same lease, which is how segregation of duties is enforced (§3.4).

A `FarmOperator` applies for leases, runs nursery and grow-out, records husbandry, registers vessels, issues harvest authorizations, lands lots and tags them. When `X-User-Role` is `FarmOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; it is not the `id` of any record. The server records it as `operator_user_id` on every lease the operator drafts, and as `performed_by_user_id` on every husbandry log the operator files. Ownership on lease-scoped work is therefore an equality test against that recorded value rather than against a record `id`: for any write on a lease, a seed lot, a deployment, an authorization or a landed lot, the acting `X-User-ID` must equal the `operator_user_id` of the lease that object hangs from, and a mismatch is refused with `ERR_LEASE_OWNERSHIP_VIOLATION` (HTTP 403).

A `HatcheryOperator` records seed shipments. When `X-User-Role` is `HatcheryOperator`, `X-User-ID` is the `id` of the acting `Hatchery`; ownership checks on any resource that references a `Hatchery` compare the resource's foreign-key field to `X-User-ID`. Concretely, a seed shipment may only be recorded against the hatchery the caller *is*: the `hatchery_id` named in the request body must equal `X-User-ID`, and a mismatch is refused with `ERR_HATCHERY_OWNERSHIP_VIOLATION` (HTTP 403).

A `SeafoodDealer` assembles and releases shipments. When `X-User-Role` is `SeafoodDealer`, `X-User-ID` is the `id` of the acting `Dealer`; ownership checks on any resource that references a `Dealer` compare the resource's foreign-key field to `X-User-ID`. A shipment may only be assembled for the dealer the caller is (the `dealer_id` in the body must equal `X-User-ID`) and may only be released by that same dealer (the shipment's stored `dealer_id` must equal `X-User-ID`); either mismatch is refused with `ERR_DEALER_OWNERSHIP_VIOLATION` (HTTP 403).

Read access is deliberately wide, because the value of a shared system of record is that the authority and the industry look at the same rows. Growing-area reads are open to all five roles. Lease reads are open to `ShellfishControlAuthority`, `SitingReviewer` and `FarmOperator`. Hatchery and seed-lot reads are open to `ShellfishControlAuthority`, `HatcheryOperator` and `FarmOperator`. Deployment, husbandry-log, vessel and authorization reads are open to `ShellfishControlAuthority` and `FarmOperator`. Harvest-lot reads are open to `ShellfishControlAuthority`, `FarmOperator` and `SeafoodDealer`. Dealer reads are open to `ShellfishControlAuthority`, `SeafoodDealer` and `FarmOperator`. Shipment reads are open to `ShellfishControlAuthority` and `SeafoodDealer`. Vibrio-control-plan reads and the classification summary are open to `ShellfishControlAuthority` and `FarmOperator`; the classification summary is the one computed read that industry may pull. Illness-investigation reads are restricted to `ShellfishControlAuthority` alone. The logical-clock endpoint is open to all five roles. §4 is authoritative for every endpoint's role list.

Two things role membership does **not** buy. It does not buy ownership: a `FarmOperator` who is authorised for the deployment endpoints is still refused with `ERR_LEASE_OWNERSHIP_VIOLATION` on another operator's lease. And it does not buy a bypass of the read-scope: read endpoints do not filter rows by ownership, so a role that may read a collection sees every row in it.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every collection endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0, with no upper bound. A `limit` below 1 or above 100, or a negative `offset`, is a request-shape failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400) rather than being silently clamped.

For list responses the `meta` object carries the four pagination fields `limit`, `offset`, `total_count` and `has_more`. `limit` and `offset` echo the values actually applied (including the defaults when the client sent nothing). `total_count` is the number of rows matching the filters *before* the page window is applied, not the number of rows in the current page. `has_more` is true exactly when the sum of `offset` and the number of rows returned in this page is less than `total_count`. `response_type` is `"array"` for list endpoints and `data` is the array of resource objects; an empty page returns an empty array with `total_count` reflecting the true match count.

The default ordering for every list endpoint is `created_at` ascending — oldest record first. Five collections override that default because the domain reads them as journals rather than registries: the area's water samples are returned newest `collected_at` first; the area's rainfall events newest `observed_at` first; a deployment's husbandry logs newest `performed_at` first; the lots landed under one authorization oldest `first_out_of_water_at` first; and the investigations naming one shipment as source newest `reported_at` first. Wherever the declared sort key ties, rows are ordered by `created_at` ascending, and where `created_at` also ties, by `id` ascending, so that every page is deterministic.

Filter query parameters, where an endpoint declares them, are all optional and combine conjunctively: supplying two filters returns only rows matching both. A filter naming a value outside the field's enumeration is a request-shape failure (`ERR_INVALID_REQUEST`, HTTP 400), not an empty result.

### 2.4. Resource Identity, Timestamps and Record Versions

Every persisted resource carries an `id` that is a server-minted UUID. Identifiers carry no type prefix and no domain-flavoured decoration: they are bare UUID strings. Clients never supply an `id`, and a client-supplied `id` in a request body is ignored.

Every persisted resource also carries a `created_at` timestamp: an ISO 8601 UTC instant with exactly three fractional-second digits, stamped from the logical clock at the moment the row is written.

Most resources additionally carry `updated_at` — same format as `created_at`, refreshed on every mutation of the row — and `version`, an integer that starts at 1 when the row is created and increases by exactly 1 on each mutation of that row. Three resources are append-only event records and deliberately carry **neither** `updated_at` **nor** `version`: `HusbandryLog`, `WaterSample` and `RainfallEvent`. For those three, only `id` and `created_at` are present alongside their domain fields, and both `updated_at` and `version` are absent from the response object entirely. Every other resource type in this system — growing areas, leases, hatcheries, seed lots, grow-out units, harvest vessels, harvest authorizations, harvest lots, dealers, shipments, illness investigations and vibrio control plans — carries the full quartet of `id`, `created_at`, `updated_at` and `version`.

A note on what "mutation" means for `version`. A cascade counts. When the authority ingests a rainfall event that closes an area, the area's own `version` advances and its `updated_at` refreshes, and so does the `version` and `updated_at` of every authorization, deployment, lot and shipment the cascade touched. Conversely, when a request changes nothing on a row, that row's `version` does not move: ingesting a water sample that leaves every growing-area field exactly as it was does not advance the area's `version`.

Computed fields are first-class parts of the response. Every field this document describes as derived — the area statistics, the seed allocation counters, the two time-to-temperature bases, the settlement breakdown, the traced-lot roster and so on — is materialised on the resource and returned in `data` on both reads and writes, exactly as the input fields are. There is no "computed fields are internal" carve-out. Fields described as null before some event has occurred are present in the response object with a JSON null value, not omitted.

### 2.5. The Logical Clock and Temporal Admissibility

Nothing in this system reads the host's wall clock. Instead the server maintains a **logical clock**, and every temporal rule in this document — closure durations, certificate expiry, nursery length, husbandry currency, harvest windows, tag dates — evaluates against it. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real wall-clock time. An admin-style test-driving capability, available to all five roles, sets the clock to a supplied `to_iso8601` instant and answers with the object `{ "current_utc": "<the new instant>" }`. Setting the clock mutates no entity and triggers no recomputation: it only changes what "now" means for subsequent requests.

Because the system records history as well as intent, a broad admissibility rule applies to client-supplied instants and calendar dates that describe something that has *already happened*. Such a value must be at or before the logical clock; a value strictly after it is refused with `ERR_FUTURE_DATED_EVENT` (HTTP 422). The fields subject to this rule are the sample collection instant `collected_at`, the rainfall observation instant `observed_at`, the husbandry instant `performed_at`, the deployment date `deployed_on`, the retrieval date `retrieved_on`, the seed shipping date `shipped_on`, the screening date `screened_on`, the nursery dates `nursery_started_on` and `nursery_completed_on`, the harvest instants recorded when a lot is landed and when an authorization is closed, the shipment release instant `shipped_at`, and the illness report instant `reported_at`. Fields that describe intent rather than history — a harvest window's `window_start` and `window_end`, a deployment's `planned_retrieval_on`, a certificate's `certified_through`, a listing's `icssl_listed_through`, a lease's `rent_paid_through_date` — are expected to lie in the future and are not subject to this rule.

Instants are compared at second resolution throughout. Calendar-date fields use the `YYYY-MM-DD` form and are compared as whole UTC calendar dates; wherever this document derives a calendar date from an instant, the date is the instant's UTC calendar date.

### 2.6. Path Resolution and Referential Existence

Many endpoints in this API address a child collection through its parent, and a few — the classification summary, the water-sample and rainfall-event journals, the husbandry-log journal, the lots landed under an authorization, and the investigations opened against a shipment — nest a collection under a single parent identifier. Path parameters are resolved strictly left to right. The leftmost identifier is looked up first, and if it does not resolve, the request fails on that identifier's not-found error without the rest of the path or the body being examined. Only when every path identifier has resolved does the server look at foreign keys inside the request body, and those are checked in the order the endpoint's narrative introduces them.

Each entity type has its own not-found error, all at HTTP 404, and each covers both the addressed path identifier and the same reference appearing inside a request body. A missing growing area — whether addressed in the path or named as `growing_area_id` when drafting a lease — yields `ERR_GROWING_AREA_NOT_FOUND`. A missing lease, addressed or named as `lease_id` when recording a seed shipment, deploying gear or issuing an authorization, yields `ERR_LEASE_NOT_FOUND`. A missing hatchery, addressed or named as `hatchery_id`, yields `ERR_HATCHERY_NOT_FOUND`. A missing seed lot, addressed or named as `seed_lot_id`, yields `ERR_SEED_LOT_NOT_FOUND`. A missing deployment, addressed or named as `growout_unit_id`, yields `ERR_GROWOUT_UNIT_NOT_FOUND`. A missing vessel, addressed or named as `vessel_id`, yields `ERR_VESSEL_NOT_FOUND`. A missing authorization yields `ERR_AUTHORIZATION_NOT_FOUND`. A missing harvest lot — addressed, or appearing as any member of the `lot_ids` roster when a shipment is assembled — yields `ERR_HARVEST_LOT_NOT_FOUND`. A missing dealer, addressed or named as `dealer_id` when issuing an authorization or assembling a shipment, yields `ERR_DEALER_NOT_FOUND`. A missing shipment yields `ERR_SHIPMENT_NOT_FOUND`, a missing illness investigation yields `ERR_INVESTIGATION_NOT_FOUND`, and a missing vibrio control plan yields `ERR_VIBRIO_PLAN_NOT_FOUND`.

Existence is checked before ownership. A `FarmOperator` addressing a lease that does not exist gets `ERR_LEASE_NOT_FOUND`, never `ERR_LEASE_OWNERSHIP_VIOLATION` — the server cannot compare an owner it has not found.

### 2.7. Validation Precedence — The Order Every Request Is Judged In

Because most operations in this domain guard several conditions at once, the *order* in which they are evaluated is part of the contract, not an implementation detail. A request that violates three rules must fail with one specific error, and the following ladder determines which. Checks are evaluated strictly from the top; the first check that fails ends the request and nothing below it is evaluated. When a rung does not apply to the addressed endpoint, evaluation simply moves to the next rung.

1. **Authentication.** Both identity headers present and non-empty — `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorisation.** `X-User-Role` appears on the addressed endpoint's role list — `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Existence.** Path identifiers left to right, then body references, per §2.6 — the entity-specific not-found error (404).
4. **Ownership.** `ERR_LEASE_OWNERSHIP_VIOLATION`, `ERR_HATCHERY_OWNERSHIP_VIOLATION` or `ERR_DEALER_OWNERSHIP_VIOLATION` (403), per §2.1.
5. **Request shape.** Required fields present; types correct; enum members recognised; numbers inside their declared ranges; calendar dates in `YYYY-MM-DD` form; instants ISO 8601 UTC; `limit` between 1 and 100 inclusive; `offset` at least 0 — `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
6. **Optimistic concurrency.** `ERR_STALE_AREA_VERSION` or `ERR_STALE_DEALER_VERSION` (412), per §2.8.
7. **State preconditions**, in this internal order: lease state `ERR_INVALID_LEASE_STATE` (409); seed-lot state `ERR_INVALID_SEED_LOT_STATE` (409); deployment state `ERR_INVALID_GROWOUT_UNIT_STATE` (409); authorization state `ERR_INVALID_AUTHORIZATION_STATE` (409); lot state `ERR_INVALID_LOT_STATE` (409); shipment state `ERR_INVALID_SHIPMENT_STATE` (409); investigation state `ERR_INVALID_INVESTIGATION_STATE` (409); dealer listing state `ERR_INVALID_DEALER_LISTING_STATE` (409); and finally, on a reopen request only, the area must not already be open — `ERR_AREA_ALREADY_OPEN` (409).
8. **Sanitary and public-health gates**, in this internal order: area classification harvestable `ERR_AREA_CLASSIFICATION_NOT_HARVESTABLE` (409); area not prohibited `ERR_AREA_PROHIBITED` (409); area harvest-open `ERR_AREA_HARVEST_CLOSED` (409); hatchery certificate current `ERR_HATCHERY_CERTIFICATE_EXPIRED` (409); species certified `ERR_SPECIES_NOT_CERTIFIED` (409); disease certificate fresh `ERR_DISEASE_CERTIFICATE_STALE` (409); time-to-temperature compliant `ERR_TIME_TEMPERATURE_EXCEEDED` (409); a vibrio plan exists for the season `ERR_NO_VIBRIO_PLAN_FOR_SEASON` (409).
9. **Deployment referential coherence**, in this internal order: plot belongs to the lease `ERR_PLOT_NOT_IN_LEASE` (409); gear type permitted on the lease `ERR_GEAR_TYPE_NOT_PERMITTED` (409); seed lot belongs to the same lease `ERR_SEED_LOT_LEASE_MISMATCH` (409). A request naming a plot the lease does not hold, or seed that is not the lease's, is answered on that ground rather than on a downstream capacity ground.
10. **Temporal coherence**, in this internal order: reopen not too early `ERR_REOPEN_TOO_EARLY` (409); nursery period long enough `ERR_NURSERY_PERIOD_TOO_SHORT` (422); nothing future-dated `ERR_FUTURE_DATED_EVENT` (422); deployment window ordered `ERR_INVALID_DEPLOYMENT_WINDOW` (422); authorization window valid `ERR_AUTHORIZATION_WINDOW_INVALID` (422); inside the authorization window `ERR_OUTSIDE_AUTHORIZATION_WINDOW` (409); screening date not before shipment `ERR_SCREENING_DATE_INVALID` (422); harvest instants ordered `ERR_INVALID_HARVEST_INSTANTS` (422).
11. **Seed plantability.** The seed lot is in a plantable state — `ERR_SEED_LOT_NOT_PLANTABLE` (409). This rung sits below the temporal rung and above every capacity and interval check.
12. **Business constraints**, in this internal order: enough clean samples to reopen `ERR_INSUFFICIENT_CLEAN_SAMPLES` (409); enough accepted samples to decide `ERR_INSUFFICIENT_SAMPLE_DATA` (409); classification supported by the data `ERR_CLASSIFICATION_NOT_SUPPORTED_BY_DATA` (409); upgrade advances exactly one rank `ERR_CLASSIFICATION_STEP_SKIPPED` (409); conditional management plan on file `ERR_CONDITIONAL_PLAN_REQUIRED` (409); segregation of duties `ERR_SEGREGATION_OF_DUTIES` (409); revision limit `ERR_REVISION_LIMIT_EXCEEDED` (409); plot not occupied `ERR_PLOT_OCCUPIED` (409); plot fallow buffer respected `ERR_PLOT_FALLOW_CONFLICT` (409); vessel concurrency `ERR_VESSEL_CAPACITY_CONFLICT` (409); deployment not already authorised `ERR_UNIT_ALREADY_AUTHORIZED` (409); inspection current `ERR_HUSBANDRY_LAPSED` (409); predator control current `ERR_PREDATOR_CONTROL_LAPSED` (409); lease gear capacity `ERR_LEASE_GEAR_CAPACITY_EXCEEDED` (409); seed allocation `ERR_SEED_ALLOCATION_EXCEEDED` (409); survival floor `ERR_SEED_SURVIVAL_BELOW_FLOOR` (409); harvest within projection `ERR_HARVEST_EXCEEDS_PROJECTION` (409); area code unique `ERR_DUPLICATE_AREA_CODE` (409); lot code unique `ERR_DUPLICATE_LOT_CODE` (409).
13. **Dealer and tag referential coherence**, in this internal order: dealer category permitted `ERR_DEALER_CATEGORY_NOT_PERMITTED` (409); interstate listing current `ERR_DEALER_NOT_LISTED_FOR_INTERSTATE` (409); dealer certification current `ERR_DEALER_CERTIFICATION_EXPIRED` (409); lots tagged `ERR_LOT_NOT_TAGGED` (409); lot–dealer roster coherent `ERR_LOT_DEALER_MISMATCH` (409); tag harvest date matches `ERR_TAG_HARVEST_DATE_MISMATCH` (409); tag dealer certification matches `ERR_TAG_DEALER_CERT_MISMATCH` (409); deployment belongs to the named lease `ERR_UNIT_LEASE_MISMATCH` (409); dealer not suspended `ERR_DEALER_SUSPENDED` (409); dealer listed `ERR_DEALER_NOT_LISTED` (409). The shipment-release endpoint of §3.9 is the one place whose internal order within this rung differs, because there the interstate window only refines a listing that is already current: on that endpoint the grounds are judged in the order `ERR_DEALER_CERTIFICATION_EXPIRED`, `ERR_DEALER_SUSPENDED`, `ERR_DEALER_NOT_LISTED`, `ERR_DEALER_NOT_LISTED_FOR_INTERSTATE`, `ERR_LOT_NOT_TAGGED`. Every other endpoint follows the order listed above.
14. **Fiscal standing, last of all.** The lease's rent must be paid through at least the logical clock's calendar date — `ERR_LEASE_RENT_DELINQUENT` (HTTP 402). This is the final rung in the whole ladder: a delinquent lease is told so only once every sanitary, referential, capacity and husbandry ground has been cleared.

Two consequences worth spelling out, because they are easy to get backwards. First, a deployment request that names a plot outside the lease *and* would blow the lease's gear ceiling fails with `ERR_PLOT_NOT_IN_LEASE`, because rung 9 precedes rung 12. Second, a landing request into a season with no published vibrio plan *and* with out-of-order harvest instants fails with `ERR_NO_VIBRIO_PLAN_FOR_SEASON`, because rung 8 precedes rung 10.

### 2.8. Optimistic Concurrency on Classification and Certification Records

Two records in this system are repeatedly rewritten by decisions that legitimately supersede one another, and for those two the API requires the client to prove it was looking at the current row.

A classification decision on a growing area must carry `expected_area_version` in its request body. The field is **not** optional: it must be supplied on every such request, and it must equal the addressed growing area's current `version`. If the area's `version` has advanced since the client last read it — because another operator recorded a decision, or because the system's own sample sweep downgraded the area, or because a rainfall closure bumped it — the decision is rejected with `ERR_STALE_AREA_VERSION` (HTTP 412) and nothing is written. Without this, a writer holding a stale view of the area could overwrite a classification, or an automatic downgrade, that it never saw.

A dealer certification renewal must likewise carry `expected_dealer_version`, again as a non-optional input field, matching the addressed dealer's current `version`. A mismatch is rejected with `ERR_STALE_DEALER_VERSION` (HTTP 412). Each renewal replaces the incumbent certification and listing period outright, so a stale writer would silently roll an already-extended listing back.

No other endpoint in this API takes a version field. Suspension, reinstatement, lease submission, reviews, decisions, deployments, authorizations, landings, tagging, shipping and every investigation step are all version-free, and supplying a version field to them has no effect.

### 2.9. Measurement Precision, Rounding and Money

Rounding in this system is always **half-up**, and it always happens at a stated point rather than opportunistically.

Water-quality statistics round in a fixed cascade: each sample's base-10 logarithm is rounded to 4 decimal places, the mean of those logarithms is rounded to 4 decimal places, the sample standard deviation of those logarithms is rounded to 4 decimal places, and only then are the geometric mean and the estimated 90th percentile rounded to 1 decimal place. No other intermediate rounding takes place, and the order of those roundings is not interchangeable. Classification thresholds are then compared against the 1-decimal-place statistics with no further rounding.

Seed survival is expressed as a percentage rounded half-up to 2 decimal places. Time-to-temperature figures and vibrio allowances are whole minutes, with elapsed minutes truncated toward zero from second-resolution instants. Husbandry ages are whole days measured as exact 24-hour multiples between second-resolution instants. Plot occupancy and fallow buffers are whole UTC calendar dates. Gear units, bushels, sample counts, strike counts and roster counts are integers.

All money in this system is **integer cents**. There are no floating-point currency fields and no decimal-dollar fields. The one place a rounding decision arises is the conservation surcharge, and it is rounded exactly once per lot, half-up, to whole cents, before it enters any accumulator — never by summing a base across lots and rounding at the end. §3.8 states the six settlement steps and their order.

### 2.10. Cascade Discipline and Compensating Reversals

Two structural habits govern how state moves through this system.

**Cascades run to completion inside the triggering request.** When a growing area closes, when a seed lot is rejected, when a dealer is suspended or when an illness investigation is confirmed, the system does not merely mark the originating record and schedule follow-up work. It walks every declared hop in order, within the same request, and every row it touches has its `updated_at` refreshed and its `version` advanced. The hops for each cascade are enumerated where they belong in §3; a partially applied cascade is never an acceptable outcome.

**Voids are compensations, not deletions.** A voided record stays readable, keeps its audit fields (including tag fields already stamped), and reverses precisely the counters its creation moved — no more and no less. Voiding a deployment gives back exactly the gear units it consumed and exactly the seed it drew. Voiding a landed lot subtracts exactly the settlement figure that lot contributed, restoring the lease's accrual to its pre-landing value, and never re-tiers the royalty rate already stamped on surviving lots. A retrieval, by contrast, is a completion rather than a correction: it releases gear capacity but does *not* give seed back, because those animals were harvested rather than returned.

**Both status dimensions on a growing area are independent.** A growing area carries two orthogonal state fields — `classification`, the sanitary classification, and `harvest_status`, harvest availability — stored on the same row and advanced by different triggers. A rainfall closure moves `harvest_status` and never touches `classification`. A reopen moves `harvest_status` back and never touches `classification`. A classification decision moves `classification`, and touches `harvest_status` only in the single coupled case documented in §3.1. Implementers must resist the temptation to collapse the two.

## 3. Business Logic & Workflows

### 3.1. Registering a Growing Area and Deciding Its Sanitary Classification

A growing area is the regulatory unit of this whole system: leases sit inside one, monitoring data is collected from one, and harvest permission is ultimately a property of one. Only the `ShellfishControlAuthority` may register one. Registration requires the authority-assigned `code` — at least 3 and at most 32 characters, and unique across all growing areas, with a collision refused as `ERR_DUPLICATE_AREA_CODE` — together with the `water_body` the area sits in.

Five further inputs configure how the area closes and reopens, and all five are optional with defaults that encode the ordinary case. `rainfall_closure_threshold_in` is the rainfall accumulation, in inches over 24 hours, at or above which the area closes; it must be greater than zero, is carried to two decimals, and defaults to 1.00 inch. `rainfall_closure_hours` is the minimum closure duration in hours after a qualifying rainfall event; it must be at least 1 and defaults to `DEFAULT_RAINFALL_CLOSURE_HOURS`, which is 96 hours — four full days. `reopen_sample_count_required` is how many consecutive clean samples must be on file before the area may reopen; it must be at least 1 and defaults to `DEFAULT_REOPEN_SAMPLE_COUNT`, which is 3. `clean_sample_mpn_limit` is the fecal-coliform figure at or below which a post-closure sample counts as clean, and defaults to 14.0. `conditional_management_plan_on_file` is a boolean that defaults to false and records whether a conditional-area management plan exists; it is a precondition of the `CONDITIONALLY_APPROVED` classification.

A newly registered area is born permissive and open: `classification` is `APPROVED`, `harvest_status` is `OPEN`, and `version` is 1. Its counters start at zero — `accepted_sample_count`, `consecutive_clean_samples` and `open_authorization_count` are all 0 — while `geometric_mean_mpn`, `p90_mpn`, `last_closure_started_at` and `closure_reopen_eligible_at` are all null and `eligible_classification` reads `INSUFFICIENT_DATA`.

**The two dimensions and the restrictiveness rank.** `classification` takes one of four values, and they are ordered by how restrictive they are: `APPROVED` is rank 0, `CONDITIONALLY_APPROVED` is rank 1, `RESTRICTED` is rank 2 and `PROHIBITED` is rank 3. Moving to a higher rank is a *downgrade*; moving to a lower rank is an *upgrade*. The second dimension, `harvest_status`, takes one of `OPEN`, `CLOSED_RAINFALL` or `CLOSED_SAMPLE_FAILURE` and is governed entirely by §3.3 and the sweep in §3.2.

**Recording a decision.** The authority records a sanitary classification decision by naming the target `classification`, supplying `expected_area_version` (mandatory, per §2.8) and optionally a `decision_note` for the file. The response is the updated area, at HTTP 200, and the area's `version` advances by 1.

Decisions are judged in a fixed order. After the stale-version check, the area must hold at least 5 accepted samples — `accepted_sample_count` at least `MIN_SAMPLES_FOR_DECISION`, which is 5 — or the request is refused with `ERR_INSUFFICIENT_SAMPLE_DATA`. This threshold applies to *every* decision, downgrades included: the authority may not act on an area it has barely sampled. Then comes the data-support test (`ERR_CLASSIFICATION_NOT_SUPPORTED_BY_DATA`), then the single-rank test (`ERR_CLASSIFICATION_STEP_SKIPPED`), then the management-plan test (`ERR_CONDITIONAL_PLAN_REQUIRED`). That ordering matters: a request to lift a `PROHIBITED` area straight to `APPROVED` while the data supports only `RESTRICTED` fails with `ERR_CLASSIFICATION_NOT_SUPPORTED_BY_DATA`, not with `ERR_CLASSIFICATION_STEP_SKIPPED`, even though it also skips two ranks.

**When the data must support the decision.** A decision requires data support unless it is a strict downgrade to `RESTRICTED` or `PROHIBITED`; those two downgrades never require the statistics to agree, because the authority must always be able to tighten. Where support is required, the bar depends on the target. A decision to `APPROVED` requires the computed `eligible_classification` to read exactly `APPROVED`. A decision to `CONDITIONALLY_APPROVED`, and an upgrade to `RESTRICTED` out of `PROHIBITED`, require `eligible_classification` to be either `APPROVED` or `RESTRICTED`. Failing that bar is `ERR_CLASSIFICATION_NOT_SUPPORTED_BY_DATA`. Note that because at least 5 accepted samples are already guaranteed by the preceding rung, `eligible_classification` can never read `INSUFFICIENT_DATA` at this point.

**One rank at a time, upward only.** An upgrade must improve the restrictiveness rank by exactly 1, or it is refused with `ERR_CLASSIFICATION_STEP_SKIPPED`. So `PROHIBITED` may be lifted to `RESTRICTED`, `RESTRICTED` to `CONDITIONALLY_APPROVED`, and `CONDITIONALLY_APPROVED` to `APPROVED` — but `PROHIBITED` to `CONDITIONALLY_APPROVED` and `PROHIBITED` to `APPROVED` are both refused with `ERR_CLASSIFICATION_STEP_SKIPPED`. Downgrades face no such limit and may skip ranks freely: `APPROVED` straight to `PROHIBITED` is a legitimate single decision. A request naming the classification the area already holds moves no rank at all and is likewise refused with `ERR_CLASSIFICATION_STEP_SKIPPED`.

**The conditional classification is administrative.** A decision to `CONDITIONALLY_APPROVED` — whether reached from `APPROVED` or as an upgrade from `RESTRICTED` — additionally requires `conditional_management_plan_on_file` to be true, failing which the request is refused with `ERR_CONDITIONAL_PLAN_REQUIRED`. This is why the statistics never produce `CONDITIONALLY_APPROVED` themselves: it is a classification that depends on a document, not on a number.

**What each decision touches.** Decisions to `CONDITIONALLY_APPROVED`, `RESTRICTED` or `APPROVED` write `classification` and advance `version`, and they do **not** touch `harvest_status`. That includes the upgrade out of `PROHIBITED`: lifting a prohibited area to `RESTRICTED` leaves `harvest_status` sitting at `CLOSED_SAMPLE_FAILURE`, because reopening is a separate act on the other dimension (§3.3).

**The prohibition coupling.** A decision into `PROHIBITED` is the one case where the two dimensions are wired together, and it is the most consequential single request in the API. Alongside setting `classification` to `PROHIBITED` and advancing `version`, it sets `harvest_status` to `CLOSED_SAMPLE_FAILURE`, sets `last_closure_started_at` to the logical clock, sets `closure_reopen_eligible_at` to the logical clock plus `rainfall_closure_hours` hours, and resets `consecutive_clean_samples` to 0. It then runs the **four-hop area-closure cascade**, in this order:

- *Hop 1.* Every harvest authorization whose snapshotted growing area is this area and whose `status` is `ISSUED` or `ACTIVE` moves to `VOIDED` with `void_reason` set to `AREA_CLOSURE`.
- *Hop 2.* Each authorization voided in hop 1 releases its vessel, decreasing that vessel's `active_authorization_count` by 1, and returns its deployment from `HARVESTING` to `DEPLOYED` if it was in `HARVESTING`.
- *Hop 3.* Each authorization voided in hop 1 embargoes its landed lots: every one of its harvest lots whose `status` is `HARVESTED` or `TAGGED` moves to `EMBARGOED` with `embargo_reason` set to `AREA_CLOSURE`.
- *Hop 4.* Each lot embargoed in hop 3 that has already been placed on a shipment — that is, whose `shipment_id` is set — and whose shipment's `status` is `CREATED`, drags that shipment to `HELD` with `held_reason` set to `LOT_EMBARGO`. A shipment already `SHIPPED`, already `HELD` or `RECALLED` is left alone.

Whenever this cascade runs, `open_authorization_count` on the area is recomputed afterwards: it is the number of harvest authorizations with `status` in `ISSUED` or `ACTIVE` whose snapshotted growing area is this area. That count is likewise recomputed whenever an authorization is issued, closed or voided for any reason.

### 3.2. Water-Quality Monitoring, the Statistics Window and the Automatic Downgrade Sweep

Sampling is the authority's exclusive activity, and each sample is an append-only record: a water sample carries only `id` and `created_at` beside its own fields, never `updated_at` and never `version`. A sample is ingested against a growing area with the sampling `station_code` inside the area, the collection instant `collected_at`, the `fecal_coliform_mpn` figure (fecal coliform most-probable-number per 100 mL, which must be at least 1), the `water_temp_c` water temperature in Celsius at collection, and optionally the `salinity_ppt` salinity in parts per thousand — omitted, `salinity_ppt` is stored as null. Ingest answers HTTP 201 with the new sample.

**Supersession.** Every newly ingested sample is `ACCEPTED`. Ingest also demotes history: any earlier sample of the same area that is currently `ACCEPTED`, shares the new sample's `station_code`, and shares the new sample's `collected_at` **calendar date** has its `sample_status` set to `SUPERSEDED`. One station contributes at most one accepted figure per calendar day, and the latest ingest wins. `sample_status` takes exactly `ACCEPTED` or `SUPERSEDED`, and superseded rows are excluded from every statistic in this section.

**Per-sample derived flags.** `is_adverse_condition` is true when the sample's `collected_at` falls within `ADVERSE_WINDOW_HOURS` — 120 hours, five full days — after the `observed_at` of a rainfall event for the same area whose `triggered_closure` is true. `counted_clean` is true when three things hold together: the sample's `sample_status` is `ACCEPTED`, its `collected_at` is strictly after the area's `last_closure_started_at`, and its `fecal_coliform_mpn` is at or below the area's `clean_sample_mpn_limit`. When the area has never closed and `last_closure_started_at` is null, no sample is post-closure, so `counted_clean` is false for every sample.

**The statistics window.** The persisted area statistics are computed over what this document calls the `SYSTEMATIC_RANDOM` window. Take every water sample of this area whose `sample_status` is `ACCEPTED` — superseded rows are excluded entirely — and order them by `collected_at` ascending, breaking ties by `created_at` ascending and by nothing else. The window is the last `SAMPLE_WINDOW_SIZE` rows of that ordering, that is the 15 most recent; when fewer than 15 accepted rows exist, all of them are used. Both endpoints of the window are inclusive. `accepted_sample_count` records how many accepted samples the area holds; the window is capped at 15 even when that count is larger.

The six computation steps run in exactly this order. First, select and order the window as above. Second, for each sample in the window take the base-10 logarithm of its `fecal_coliform_mpn` and round it half-up to 4 decimal places; let the number of samples in the window be the window count. Third, sum those rounded logarithms, divide by the window count, and round the result half-up to 4 decimal places — this is the mean logarithm. Fourth, raise 10 to the power of that mean logarithm and round half-up to 1 decimal place: that is `geometric_mean_mpn`. Fifth, compute the sample standard deviation of the rounded logarithms about the mean logarithm using a denominator of the window count minus 1, and round it half-up to 4 decimal places; when the window holds fewer than 2 samples this standard deviation is taken as 0.0000 rather than being undefined. Sixth, multiply that standard deviation by `P90_Z`, which is 1.28, add the mean logarithm, raise 10 to that power, and round half-up to 1 decimal place: that is `p90_mpn`. No rounding occurs anywhere else in the chain. When the area holds no accepted samples at all, both `geometric_mean_mpn` and `p90_mpn` are null.

**From statistics to eligibility.** `eligible_classification` is the most permissive classification those statistics support, and it takes one of `INSUFFICIENT_DATA`, `APPROVED`, `RESTRICTED` or `PROHIBITED` — never `CONDITIONALLY_APPROVED`. It is decided by walking three tests in order. If the window count is below `MIN_SAMPLES_FOR_DECISION`, which is 5, the answer is `INSUFFICIENT_DATA`. Otherwise, if `geometric_mean_mpn` is at or below `GEOMEAN_APPROVED_LIMIT` of 14.0 **and** `p90_mpn` is at or below `P90_APPROVED_LIMIT` of 43.0, the answer is `APPROVED`. Otherwise, if `geometric_mean_mpn` is at or below `GEOMEAN_RESTRICTED_LIMIT` of 88.0 **and** `p90_mpn` is at or below `P90_RESTRICTED_LIMIT` of 260.0, the answer is `RESTRICTED`. Otherwise the answer is `PROHIBITED`. Every comparison is inclusive: a geometric mean of exactly 14.0 with a 90th percentile of exactly 43.0 is `APPROVED`. Both conditions in a tier must hold — a passing geometric mean with a failing 90th percentile falls through to the next tier down.

**The adverse-condition variant.** The same six steps can be run over a deliberately smaller window. The `ADVERSE_CONDITION` variant restricts the window to accepted samples whose `is_adverse_condition` is true — samples collected inside the five-day adverse window after a closure-triggering rainfall event — and then applies the identical six steps and the identical eligibility ladder to that smaller set. Because storm-influenced samples are the dirty ones, identical stored data yields a materially higher geometric mean and frequently a different eligible classification under this variant. The `ADVERSE_CONDITION` result is **never** persisted on the area: `geometric_mean_mpn`, `p90_mpn` and `eligible_classification` on the growing-area record always hold the `SYSTEMATIC_RANDOM` figures.

**The computed summary read.** A computed read, available to `ShellfishControlAuthority` and `FarmOperator`, returns the statistics for a requested `variant`. The `variant` query parameter accepts `SYSTEMATIC_RANDOM` or `ADVERSE_CONDITION` and defaults to `SYSTEMATIC_RANDOM` when omitted. The response object carries eight fields: `variant` echoing the variant applied; `sample_count`, the number of samples in the window actually used; `mean_log10`, the 4-decimal-place mean logarithm from step three; `geometric_mean_mpn` and `p90_mpn` at 1 decimal place; `eligible_classification` for that variant; and `window_start_at` and `window_end_at`, the `collected_at` of the earliest and latest samples in the window respectively. When the window is empty, `sample_count` is 0, `mean_log10`, `geometric_mean_mpn`, `p90_mpn`, `window_start_at` and `window_end_at` are null, and `eligible_classification` reads `INSUFFICIENT_DATA`.

**The sample sweep.** Ingesting a sample recomputes `accepted_sample_count`, `geometric_mean_mpn`, `p90_mpn`, `eligible_classification` and `consecutive_clean_samples` on the area, and the area's `version` advances by 1 whenever any growing-area field actually changes as a result. The sweep then asks whether the new data has condemned the area. Three conditions must hold together: `accepted_sample_count` must be at least 5; the recomputed `geometric_mean_mpn` must be strictly greater than 14.0; and the recomputed `eligible_classification` must carry a strictly higher restrictiveness rank than the area's current `classification`. When all three hold, the system itself downgrades `classification` to that `eligible_classification` value, sets `harvest_status` to `CLOSED_SAMPLE_FAILURE`, sets `last_closure_started_at` to the logical clock, sets `closure_reopen_eligible_at` to the logical clock plus `rainfall_closure_hours`, resets `consecutive_clean_samples` to 0, and runs the same four-hop area-closure cascade declared in §3.1 — authorizations voided with `void_reason` `AREA_CLOSURE`, vessels released and deployments returned from `HARVESTING` to `DEPLOYED`, lots in `HARVESTED` or `TAGGED` embargoed with `embargo_reason` `AREA_CLOSURE`, and their `CREATED` shipments held with `held_reason` `LOT_EMBARGO`.

The sweep trigger is the **geometric mean alone**. A 90th-percentile exceedance can move `eligible_classification` — a geometric mean of 12.0 with a 90th percentile of 300.0 makes the area eligible only for `PROHIBITED` — but with the geometric mean at or below 14.0 the sweep does not fire and the area stays open at its administratively decided classification. This asymmetry is deliberate: the sweep is an emergency brake, not a reclassification engine. Note also that the sweep can move `harvest_status` from `CLOSED_RAINFALL` to `CLOSED_SAMPLE_FAILURE`, which restarts the closure clock: `last_closure_started_at` becomes the logical clock and `closure_reopen_eligible_at` becomes the logical clock plus `rainfall_closure_hours`, so a storm closure that then fails on bacteriology serves a fresh waiting period.

### 3.3. Rainfall Closures and the Road Back to OPEN

A rainfall event is the other append-only monitoring record — `id` and `created_at` only, no `updated_at` and no `version` — and only the `ShellfishControlAuthority` records one. It carries the `gauge_code` identifying the rain gauge that serves the area, the `observed_at` instant that ends the 24-hour accumulation window, and `inches_24h`, the accumulation in inches over the 24 hours ending at `observed_at`, which must be at least 0 and is carried to two decimals. Ingest answers HTTP 201.

`triggered_closure` is computed at ingest and is true exactly when `inches_24h` is at or above the area's `rainfall_closure_threshold_in`. The comparison is inclusive: an accumulation of exactly the threshold closes the area. `voided_authorization_count` on the event records how many harvest authorizations the cascade this event started actually voided, and it is 0 when the event triggered no cascade.

**Closing an open area.** When `triggered_closure` is true and the area's `harvest_status` is `OPEN`, `harvest_status` moves to `CLOSED_RAINFALL`. `last_closure_started_at` is set to the event's `observed_at` — not to the logical clock — and `closure_reopen_eligible_at` becomes that `observed_at` plus `rainfall_closure_hours` hours. `consecutive_clean_samples` resets to 0, the area's `version` advances by 1, and `classification` is never touched by a rainfall event. The four-hop area-closure cascade from §3.1 then runs in the same order — authorizations in `ISSUED` or `ACTIVE` to `VOIDED` with `void_reason` `AREA_CLOSURE`; each voided authorization releasing its vessel's `active_authorization_count` by 1 and returning its deployment from `HARVESTING` to `DEPLOYED`; each voided authorization's lots in `HARVESTED` or `TAGGED` to `EMBARGOED` with `embargo_reason` `AREA_CLOSURE`; and each of those lots whose `shipment_id` is set and whose shipment is `CREATED` dragging that shipment to `HELD` with `held_reason` `LOT_EMBARGO`. The count of authorizations voided in the first hop is written to the event's `voided_authorization_count`.

**Closing an already-closed area.** A second qualifying event during an existing rainfall closure does not merely log; it **restarts** the closure. When `harvest_status` is already `CLOSED_RAINFALL`, the accumulation qualifies, and the new `observed_at` is strictly after the current `last_closure_started_at`, then `last_closure_started_at` becomes the new `observed_at`, `closure_reopen_eligible_at` becomes that instant plus `rainfall_closure_hours`, `consecutive_clean_samples` resets to 0, the area's `version` advances by 1, and the four cascade hops fire again against whatever is still open — which is normally nothing, since the first closure already swept the area, but the hops are unconditional. The practical effect is that a storm sequence keeps pushing the reopening date out and wipes out any clean-sample run the operator had begun to build.

Two non-transitions round out the picture, and both matter because they are easy to implement wrongly. A qualifying event whose `observed_at` is at or before the current `last_closure_started_at` is still recorded with `triggered_closure` true, but the closure clock is not restarted, `consecutive_clean_samples` is not reset, no cascade runs, and the area's `version` does not advance — back-filling an older gauge reading cannot retroactively extend a closure. And a qualifying event arriving while `harvest_status` is `CLOSED_SAMPLE_FAILURE` is likewise recorded with `triggered_closure` true but changes nothing on the area: there is no declared move from a sample-failure closure into a rainfall closure, so `harvest_status` stays `CLOSED_SAMPLE_FAILURE` and no cascade runs. An event whose `triggered_closure` computes false is simply filed; it changes nothing.

**Building the clean-sample run.** `consecutive_clean_samples` is not a lifetime tally — it is a *run measured backwards from the newest post-closure sample*. Take every accepted sample of the area whose `collected_at` is strictly after `last_closure_started_at`, excluding any sample collected at exactly that instant, and order them by `collected_at` ascending with `created_at` ascending as the tie-break. Then walk that ordering from its **end** toward its beginning, counting samples whose `fecal_coliform_mpn` is at or below `clean_sample_mpn_limit`, and stop at the first sample that exceeds the limit. The count reached is `consecutive_clean_samples`. A single dirty sample therefore resets the run to 0 without extending the reopening clock — the operator loses their accumulated evidence but not additional waiting time. `closure_reopen_eligible_at` is derived as `last_closure_started_at` plus `rainfall_closure_hours` hours, and is null whenever the area has never closed.

**Reopening.** The authority reopens a closed area by requesting the reopen capability, optionally attaching a `reopen_note`; the response is the updated area at HTTP 200. Reopening is judged in the order the §2.7 ladder prescribes, and four distinct grounds can refuse it. If `harvest_status` is already `OPEN`, the request is refused with `ERR_AREA_ALREADY_OPEN`. If `classification` is `PROHIBITED`, it is refused with `ERR_AREA_PROHIBITED` — a prohibited area must first be upgraded to `RESTRICTED` on the classification dimension, which by itself does not reopen it. If the logical clock is strictly before `closure_reopen_eligible_at`, it is refused with `ERR_REOPEN_TOO_EARLY`; the comparison is inclusive, so a reopen requested at exactly `closure_reopen_eligible_at` is in time. And if `consecutive_clean_samples` is strictly below `reopen_sample_count_required`, it is refused with `ERR_INSUFFICIENT_CLEAN_SAMPLES`; here too the comparison is inclusive, so exactly the required number of clean samples suffices. Note the relative order: an area that is both too early and short of samples is told `ERR_REOPEN_TOO_EARLY`, because the temporal rung precedes the business-constraint rung.

A successful reopen sets `harvest_status` to `OPEN`, resets `consecutive_clean_samples` to 0, sets `closure_reopen_eligible_at` back to null, and advances the area's `version` by 1. `last_closure_started_at` is deliberately **retained** as the audit trail of the most recent closure, and `classification` is not touched. Reopening works identically out of `CLOSED_RAINFALL` and out of `CLOSED_SAMPLE_FAILURE`: same four grounds for refusal, same four state effects. Reopening does not resurrect anything the closure cascade voided, embargoed or held — those records stay where the cascade left them, and fresh authorizations must be issued to harvest again.

### 3.4. Lease Acquisition: Two Clearance Legs, Revision Cycles and the Decision

A lease is a `FarmOperator`'s tenure over part of a growing area, and it is the ownership anchor for everything downstream — seed, gear, husbandry, authorizations and lots are all reachable only through the operator who holds the lease.

**Drafting.** The operator drafts an application naming `growing_area_id`, the `lease_code` (which must be unique across all leases), the `requested_acreage` in acres (which must be greater than zero), `plot_codes` (between 1 and 12 unique non-empty strings, for example the pair "P1" and "P2"), `gear_types_permitted` (a non-empty subset of `BOTTOM`, `RACK_AND_BAG` and `FLOATING_BAG`), and `authorized_gear_units`, the ceiling of at least 1 on concurrently deployed gear units across all plots. Nothing here is optional. Creation answers HTTP 201, stamps `operator_user_id` with the acting user's identity, and sets `status` to `DRAFT`, `navigation_clearance` and `environmental_clearance` to `PENDING` with `navigation_reviewer_user_id` and `environmental_reviewer_user_id` null, `revision_round` to 0, `deployed_gear_units` to 0 and `royalty_accrued_cents` to 0, while `rent_paid_through_date` and `decided_at` stay null.

`status` walks `DRAFT`, `UNDER_REVIEW`, `REVISION_REQUESTED`, `PENDING_DECISION`, `APPROVED` and `DENIED`, and `DENIED` is terminal — nothing further can be done with a denied lease. Every production operation that consumes a lease requires `status` to be `APPROVED`; a lease in any other state refuses seed shipments, gear deployment and authorization issue with `ERR_INVALID_LEASE_STATE`.

**Submission.** The owning operator submits a `DRAFT` lease for siting review, optionally attaching a `submission_note`. Two things can stop it: acting as a `FarmOperator` who does not own the lease is `ERR_LEASE_OWNERSHIP_VIOLATION`, and submitting a lease whose growing area is classified `PROHIBITED` is `ERR_AREA_PROHIBITED`. Submission moves `status` to `UNDER_REVIEW` and resets both clearance legs to `PENDING` with both reviewer identities set back to null. The response is the lease at HTTP 200.

**The two review legs run in parallel.** A `SitingReviewer` records the navigation leg and the environmental leg through two separate capabilities, each taking a `decision` of `CLEARED` or `OBJECTION` and an optional `review_note`. The legs are independent — either may be recorded first — and the addressed leg must currently read `PENDING`, otherwise the request is refused with `ERR_INVALID_LEASE_STATE`. Recording a leg writes that leg's clearance field and stamps that leg's reviewer identity with the acting user.

**Segregation of duties.** One human may not sign off both legs of the same lease. Before a leg is recorded, the acting user's identity is compared against the *sibling* leg's reviewer identity; if they match, the request is refused with `ERR_SEGREGATION_OF_DUTIES`. A null sibling reviewer identity can never match, so the first leg on a fresh review round is never blocked by this rule. Note the precedence: the state check on the addressed leg (`ERR_INVALID_LEASE_STATE`) runs before the segregation check, so a reviewer trying to re-record a leg that is already `CLEARED` is told the state is wrong even if they were also the sibling reviewer.

**The join.** Clearing a leg while the sibling leg still reads `PENDING` leaves `status` at `UNDER_REVIEW` — the fork is half done. Clearing a leg while the sibling leg already reads `CLEARED` completes the join and moves `status` to `PENDING_DECISION`. The join fires on the second `CLEARED`, whichever leg that is.

**The two objections are deliberately asymmetric.** An objection on either leg moves `status` to `REVISION_REQUESTED`, but the collateral damage differs. A navigation objection writes `navigation_clearance` as `OBJECTION` with `navigation_reviewer_user_id` set to the acting user and **leaves `environmental_clearance` exactly as it stands** — a recorded environmental `CLEARED`, and its reviewer identity, survive a navigation objection. An environmental objection writes `environmental_clearance` as `OBJECTION` with `environmental_reviewer_user_id` set to the acting user and additionally **resets `navigation_clearance` to `PENDING` and `navigation_reviewer_user_id` to null**, because an environmental objection will move the footprint and any navigation finding about the old footprint is worthless. Implementers must not unify these two branches.

**Resubmission is a cycle with a hard limit.** The owning operator resubmits a `REVISION_REQUESTED` lease through the same submission capability. Resubmission requires `revision_round` to be strictly below `MAX_REVISION_ROUNDS`, which is 3; at 3 completed rounds the request is refused with `ERR_REVISION_LIMIT_EXCEEDED`, and the application is stuck in `REVISION_REQUESTED` forever. It also requires the area not to be `PROHIBITED` (`ERR_AREA_PROHIBITED`) and the acting user to own the lease. A successful resubmission increments `revision_round` by 1, resets **both** clearance legs to `PENDING` with both reviewer identities null — including a leg that had survived as `CLEARED` — and moves `status` back to `UNDER_REVIEW`. Because both reviewer identities are cleared, the segregation-of-duties rule starts fresh each round: a reviewer who cleared navigation in round 0 may clear environmental in round 1.

**The decision.** The `ShellfishControlAuthority` decides a lease in `PENDING_DECISION` by naming a `decision` of `APPROVE` or `DENY`, optionally with `rent_paid_through_date` and `decision_note`. Both branches require both clearance legs to read `CLEARED`, and both branches require the growing area not to be classified `PROHIBITED` — the `ERR_AREA_PROHIBITED` guard applies symmetrically to `APPROVE` and to `DENY`, because the guard is scoped to the decision capability rather than to one outcome. `APPROVE` sets `status` to `APPROVED` and `decided_at` to the logical clock, and sets `rent_paid_through_date` to the supplied `rent_paid_through_date` when one was supplied and otherwise to the logical clock's own calendar date. `DENY` sets `status` to `DENIED` and `decided_at` to the logical clock, and leaves `rent_paid_through_date` null. Either way the response is the lease at HTTP 200.

**Rent delinquency.** `rent_paid_through_date` is not merely decorative: issuing a harvest authorization requires it to be at or after the logical clock's calendar date, and a lease whose rent has lapsed is refused with `ERR_LEASE_RENT_DELINQUENT` at HTTP 402 — the only payment-required status in the API, and the last rung of the validation ladder, so every other objection to an authorization is reported first.

**The two lease counters.** `deployed_gear_units` is the sum of `gear_units` over this lease's grow-out units whose `status` is `DEPLOYED` or `HARVESTING`; `RETRIEVED` and `VOIDED` units are excluded, so retrieving or voiding gear frees capacity. `royalty_accrued_cents` is the sum of `lot_settlement_cents` over this lease's harvest lots whose `status` is not `VOIDED`.

### 3.5. Seed: Hatchery Certificates, Screening and Nursery Grow-Out

**Hatcheries.** Only the `ShellfishControlAuthority` registers a hatchery, supplying its `name`, its two-letter `state_code` (exactly two uppercase letters), its National Shellfish Sanitation Program hatchery certificate number `ncsp_certificate_no` (unique across hatcheries), the `certificate_expires_on` calendar date, and `pathogen_free_species`, a non-empty subset of `CRASSOSTREA_VIRGINICA` (the Eastern oyster), `MERCENARIA_MERCENARIA` (the hard clam) and `MYTILUS_EDULIS` (the blue mussel). Registration answers HTTP 201. Hatcheries carry no state machine and are never mutated after registration.

**Recording a seed shipment.** A `HatcheryOperator` records a shipment. Because that role is backed by a hatchery record, the acting user's identity *is* a hatchery identifier, and the request must name that same hatchery in `hatchery_id`, or it is refused with `ERR_HATCHERY_OWNERSHIP_VIOLATION`. The shipment also names `lease_id` (the destination lease, which must be `APPROVED` or the request is `ERR_INVALID_LEASE_STATE`), the `species` shipped, `received_seed_count` (at least 1), the `disease_certificate_no` accompanying the shipment, the `disease_cert_issued_on` calendar date the certificate was issued, and the `shipped_on` calendar date the seed left the hatchery. All seven inputs are required. Creation answers HTTP 201, sets `status` to `RECEIVED`, leaves `screening_result`, `screened_on`, `nursery_started_on`, `nursery_system`, `nursery_completed_on`, `surviving_seed_count` and `survival_rate_pct` null, and sets `allocated_seed_count` and `unallocated_seed_count` to 0.

Three sanitary gates guard the shipment, and they run in this order. The hatchery's `certificate_expires_on` must be at or after `shipped_on` — a certificate expiring the very day of shipment is still good — otherwise `ERR_HATCHERY_CERTIFICATE_EXPIRED`. The shipped `species` must be a member of the hatchery's `pathogen_free_species`, otherwise `ERR_SPECIES_NOT_CERTIFIED`. And the disease certificate must be fresh: `shipped_on` minus `disease_cert_issued_on` must be at most `DISEASE_CERT_MAX_AGE_DAYS`, which is 30 days, otherwise `ERR_DISEASE_CERTIFICATE_STALE`. Exactly 30 days passes; 31 does not.

**Screening.** `status` walks `RECEIVED`, `SCREENED`, `NURSERY`, `READY_FOR_PLANTING`, `PLANTED` and `REJECTED`, with `REJECTED` terminal. The `ShellfishControlAuthority` screens a lot in `RECEIVED` — any other state is `ERR_INVALID_SEED_LOT_STATE` — supplying the `result` (`NEGATIVE` or `POSITIVE`) and the `screened_on` calendar date. `screened_on` must be at or after `shipped_on`, or the request is refused with `ERR_SCREENING_DATE_INVALID` at HTTP 422, and it must not be after the logical clock's calendar date, which is `ERR_FUTURE_DATED_EVENT`. Both branches stamp `screening_result` and `screened_on` and answer HTTP 200.

A `NEGATIVE` result simply moves `status` to `SCREENED`. A `POSITIVE` result condemns the lot: `status` becomes `REJECTED`, and a **three-hop rejection cascade** runs in this order. Hop 1: every grow-out unit of this seed lot whose `status` is `DEPLOYED` or `HARVESTING` moves to `VOIDED` with `void_reason` set to `SEED_LOT_REJECTED`. Hop 2: each unit voided in hop 1 releases its resources — its `gear_units` come off the lease's `deployed_gear_units` and its `seed_count_planted` comes off the seed lot's `allocated_seed_count`. Hop 3: each unit voided in hop 1 voids its own harvest authorizations whose `status` is `ISSUED` or `ACTIVE`, setting their `status` to `VOIDED` with `void_reason` set to `SEED_LOT_REJECTED` and decreasing each referenced vessel's `active_authorization_count` by 1. Every row the cascade touches has its `updated_at` and `version` advanced.

**Nursery grow-out.** The owning operator — the acting identity must equal the `operator_user_id` of the lease named by the seed lot's `lease_id`, or `ERR_LEASE_OWNERSHIP_VIOLATION` — starts nursery grow-out on a lot in `SCREENED`, supplying `nursery_started_on` and the `nursery_system` in use (`UPWELLER`, `FLOAT_UPWELLER` or `RACK`). `nursery_started_on` must be at or after `shipped_on` — an earlier date is a malformed request, `ERR_INVALID_REQUEST` at HTTP 400 — and not after the logical clock's calendar date, which is `ERR_FUTURE_DATED_EVENT`. The transition stamps both fields and moves `status` to `NURSERY`.

The same operator completes grow-out on a lot in `NURSERY`, supplying `nursery_completed_on` and `surviving_seed_count`. Three checks apply, in this order: `nursery_completed_on` must not be after the logical clock's calendar date (`ERR_FUTURE_DATED_EVENT`, HTTP 422); the nursery must have run long enough, meaning `nursery_completed_on` is at or after `nursery_started_on` plus `MIN_NURSERY_DAYS`, which is 21 days — three weeks — otherwise `ERR_NURSERY_PERIOD_TOO_SHORT` at HTTP 422; and the survival figures must be credible. `survival_rate_pct` is 100 multiplied by `surviving_seed_count`, divided by `received_seed_count`, rounded half-up to 2 decimal places. It must be at or above `SURVIVAL_FLOOR_PCT`, which is 40.00 — exactly 40.00 passes — and `surviving_seed_count` must not exceed `received_seed_count`; either failure is `ERR_SEED_SURVIVAL_BELOW_FLOOR` at HTTP 409. A successful completion stamps `surviving_seed_count` and `nursery_completed_on`, writes the computed `survival_rate_pct`, sets `unallocated_seed_count` to `surviving_seed_count` with `allocated_seed_count` at 0, and moves `status` to `READY_FOR_PLANTING`.

**The compound bubble-up.** The last two seed-lot states are not driven by any seed-lot capability at all — they follow the gear. `allocated_seed_count` is the sum of `seed_count_planted` over this lot's grow-out units whose `status` is `DEPLOYED`, `HARVESTING` or `RETRIEVED`; `VOIDED` units are excluded. `unallocated_seed_count` is `surviving_seed_count` minus `allocated_seed_count`, and reads 0 before nursery completion. When a deployment allocates the last unallocated seed, so that `unallocated_seed_count` reaches exactly 0, the lot moves from `READY_FOR_PLANTING` to `PLANTED`. When voiding a deployment returns seed so that `unallocated_seed_count` becomes greater than 0, the lot moves from `PLANTED` back to `READY_FOR_PLANTING`. Both moves happen inside the deployment request that caused them, and both bump the lot's `updated_at` and `version`.

### 3.6. Grow-Out Gear, Plot Occupancy and Husbandry Currency

**Deploying gear.** The owning operator deploys gear by naming `lease_id`, `seed_lot_id`, the `plot_code` the gear goes into, the `gear_type` (`BOTTOM`, `RACK_AND_BAG` or `FLOATING_BAG`), `gear_units` (the countable bags, cages or bottom-acre units occupied, at least 1), `seed_count_planted` (at least 1), `deployed_on` and `planned_retrieval_on`. All eight inputs are required, and the response is the new unit at HTTP 201, with `status` `DEPLOYED`, `husbandry_current` false, `mortality_count_total` 0, and `retrieved_on`, `void_reason`, `last_inspection_at` and `last_predator_control_at` all null.

Deployment is the most heavily guarded write in the system, and the order of its guards is load-bearing. The lease must be `APPROVED` (`ERR_INVALID_LEASE_STATE`) and the area must not be `PROHIBITED` (`ERR_AREA_PROHIBITED`). Then come three referential coherence checks: `plot_code` must be a member of the lease's `plot_codes`, otherwise `ERR_PLOT_NOT_IN_LEASE`; `gear_type` must be a member of the lease's `gear_types_permitted`, otherwise `ERR_GEAR_TYPE_NOT_PERMITTED`; and the seed lot's own `lease_id` must equal the deployment's `lease_id`, otherwise `ERR_SEED_LOT_LEASE_MISMATCH` — seed shipped to one lease cannot be planted on another. Then the window check: `planned_retrieval_on` must be strictly after `deployed_on`, otherwise `ERR_INVALID_DEPLOYMENT_WINDOW` at HTTP 422; `deployed_on` must not be after the logical clock's calendar date, otherwise `ERR_FUTURE_DATED_EVENT`, while `planned_retrieval_on` is a future intent and is exempt. Then the seed must be plantable: the lot's `status` must be `READY_FOR_PLANTING` or `PLANTED`, otherwise `ERR_SEED_LOT_NOT_PLANTABLE`. Only after all of that do the occupancy, capacity and allocation checks run. The consequence worth spelling out: a request naming a plot the lease does not hold is answered `ERR_PLOT_NOT_IN_LEASE` even when it would also blow the gear ceiling, and a request against a lot still in `NURSERY` is answered `ERR_SEED_LOT_NOT_PLANTABLE` even when the requested seed count also exceeds what is available.

**Plot occupancy and the fallow rule.** A plot may hold one deployment at a time and must then rest. Consider every existing grow-out unit on the same lease with the same `plot_code` whose `status` is `DEPLOYED`, `HARVESTING` or `RETRIEVED`; `VOIDED` units are excluded entirely, which is precisely what makes voiding a true compensation for plot occupancy. Each such unit occupies the half-open calendar-date interval starting at its `deployed_on` and ending at its *effective end*, where the effective end is `retrieved_on` for a unit in `RETRIEVED` and `planned_retrieval_on` for a unit in `DEPLOYED` or `HARVESTING`. The new unit occupies the half-open interval from its `deployed_on` to its `planned_retrieval_on`.

Two rejections follow, in this order. First, if any existing unit *truly overlaps* the new interval — meaning that existing unit's `deployed_on` is strictly before the new `planned_retrieval_on` **and** the new `deployed_on` is strictly before that existing unit's effective end — the request is refused with `ERR_PLOT_OCCUPIED`. Second, if no true overlap exists but the new `deployed_on` is strictly before some existing unit's effective end plus `FALLOW_DAYS`, which is 14 days — a fortnight of rest — the request is refused with `ERR_PLOT_FALLOW_CONFLICT`. Both right-hand boundaries are exclusive: deploying exactly on an existing unit's effective end is not an overlap, and deploying exactly on the effective end plus 14 days satisfies the fallow rule. Checking true overlap before the buffer matters because a genuinely overlapping deployment always also violates the buffer, and the more specific error must win.

**Gear capacity and seed allocation.** After occupancy, the lease's `deployed_gear_units` plus the new `gear_units` must be at most the lease's `authorized_gear_units`; strictly exceeding it is `ERR_LEASE_GEAR_CAPACITY_EXCEEDED`, and landing exactly on the authorized total is permitted. Then `seed_count_planted` must be at most the seed lot's `unallocated_seed_count`, otherwise `ERR_SEED_ALLOCATION_EXCEEDED`. A successful deployment adds `gear_units` to the lease's `deployed_gear_units`, adds `seed_count_planted` to the lot's `allocated_seed_count` and subtracts the same figure from its `unallocated_seed_count`, and, when `unallocated_seed_count` thereby reaches 0, moves the lot from `READY_FOR_PLANTING` to `PLANTED`.

**Husbandry logs.** The owning operator records husbandry work on a unit whose `status` is `DEPLOYED` or `HARVESTING` — a `RETRIEVED` or `VOIDED` unit refuses with `ERR_INVALID_GROWOUT_UNIT_STATE` — supplying the `log_type` (`INSPECTION`, `PREDATOR_CONTROL`, `DENSITY_THINNING` or `GEAR_MAINTENANCE`), the `performed_at` instant, and, when `log_type` is `PREDATOR_CONTROL`, both the `predator_species` addressed (`OYSTER_DRILL`, `BLUE_CRAB`, `COWNOSE_RAY` or `SEA_STAR`) and the `control_method` used (`NETTING`, `TRAPPING`, `MANUAL_REMOVAL` or `FENCING`); omitting either of those two for a predator-control log is `ERR_INVALID_REQUEST`, and they are ignored for the other three log types. `mortality_count`, the dead animals counted during the activity, is optional, must be at least 0, and defaults to 0 when omitted. `notes` is an optional free-text observation and is stored as null when omitted. `performed_at` must not be after the logical clock, otherwise `ERR_FUTURE_DATED_EVENT`. The log answers HTTP 201, stamps `performed_by_user_id` with the acting identity, and — being an append-only journal record — carries neither `updated_at` nor `version` and can never be edited or deleted.

**Husbandry currency.** Each log recomputes three fields on the unit. `last_inspection_at` is the greatest `performed_at` over this unit's logs whose `log_type` is `INSPECTION`, and null when there are none; `last_predator_control_at` is the greatest `performed_at` over logs whose `log_type` is `PREDATOR_CONTROL`, and null when there are none; ties on `performed_at` are broken by `created_at` ascending, which cannot change the resulting instant. `mortality_count_total` is the sum of `mortality_count` over **all** of this unit's logs regardless of `log_type`.

`husbandry_current` then combines two tests against the logical clock. The inspection test passes when `last_inspection_at` is not null and the elapsed time from it to the logical clock is at most `INSPECTION_MAX_AGE_DAYS`, which is 30 days; a log exactly 30 days old is still current. The predator test passes automatically for any `gear_type` other than `BOTTOM`, because `RACK_AND_BAG` and `FLOATING_BAG` enclose the animals; for `BOTTOM` gear it passes only when `last_predator_control_at` is not null and the elapsed time from it to the logical clock is at most `PREDATOR_CONTROL_MAX_AGE_DAYS`, which is 60 days. `husbandry_current` is true only when both tests pass. Because it is evaluated against the logical clock at read time, a unit that was current yesterday becomes stale when the clock is advanced, with no request touching the unit.

Issuing a harvest authorization reads exactly these two tests and refuses on each separately: a failing inspection test is `ERR_HUSBANDRY_LAPSED` and a failing predator test is `ERR_PREDATOR_CONTROL_LAPSED`, and the inspection test is checked first, so a `BOTTOM` unit that has lapsed on both is told `ERR_HUSBANDRY_LAPSED`.

**Retrieval and voiding.** Both are the owning operator's acts on a unit in `DEPLOYED`, both answer HTTP 200, and they differ in what they compensate. Retrieval supplies `retrieved_on`, which must not be after the logical clock's calendar date (`ERR_FUTURE_DATED_EVENT`), and requires that no authorization of this unit has `status` `ISSUED` or `ACTIVE`, failing which the request is refused with `ERR_INVALID_GROWOUT_UNIT_STATE`. It sets `status` to `RETRIEVED`, stamps `retrieved_on`, and subtracts `gear_units` from the lease's `deployed_gear_units`. It deliberately does **not** release seed: `allocated_seed_count` on the lot stays where it is, because the animals were grown out and harvested, not returned to the pool.

Voiding, optionally carrying a `void_note`, is the correction path for a deployment recorded in error, and it is far more restrictive: no authorization of this unit may have `status` `ISSUED`, `ACTIVE` **or** `CLOSED`, and no harvest lot may exist under any authorization of this unit; either condition refuses with `ERR_INVALID_GROWOUT_UNIT_STATE`. A void sets `status` to `VOIDED` with `void_reason` `OPERATOR_CORRECTION` and reverses every counter the deployment moved: it subtracts exactly `gear_units` from the lease's `deployed_gear_units`, subtracts `seed_count_planted` from the lot's `allocated_seed_count` and adds the same figure back to `unallocated_seed_count`, moves the lot from `PLANTED` back to `READY_FOR_PLANTING` when `unallocated_seed_count` becomes greater than 0, and releases the plot's occupation interval so the fallow calculation no longer sees this unit at all. Both `RETRIEVED` and `VOIDED` are terminal.

**The harvest cycle within grow-out.** Between those terminal states a unit oscillates. Activating an authorization that references the unit moves it from `DEPLOYED` to `HARVESTING`; closing that authorization, or any cascade that voids it, moves it back from `HARVESTING` to `DEPLOYED`. The gear stays in the water between harvest windows — that oscillation *is* the grow-out cycle — and a unit may make the round trip any number of times. The one-way exit from `HARVESTING` is the seed-rejection cascade, which voids the unit outright with `void_reason` `SEED_LOT_REJECTED`.

### 3.7. Vessels, Harvest Authorizations and the Harvest Cycle

**Registering a vessel.** A `FarmOperator` registers a harvest vessel with its `name`, its state `registration_no` (unique across vessels) and its `refrigeration_type` — `NONE`, `ICE_SLURRY` or `MECHANICAL`. `concurrent_authorization_capacity`, the maximum number of authorizations in `ISSUED` or `ACTIVE` whose windows may overlap on this vessel, is optional, must be at least 1, and defaults to `DEFAULT_VESSEL_CAPACITY`, which is 2. Registration answers HTTP 201 and sets `active_authorization_count` to 0. Vessels carry no state machine, and `active_authorization_count` is the only field that ever changes: it is incremented by 1 when an authorization is issued and decremented by 1 when an authorization is closed and on every void, whatever caused the void.

**Issuing an authorization.** A harvest authorization is permission for one deployment, one vessel and one receiving dealer, over one window. The owning operator names `lease_id`, `growout_unit_id`, `vessel_id`, `dealer_id`, `window_start` (the inclusive start of the permitted window), `window_end` (the exclusive end) and `projected_bushels` (at least 1). All seven are required. Issue answers HTTP 201 with `status` `ISSUED`, `harvested_bushels` 0, and `harvest_start_at`, `harvest_end_at` and `void_reason` null.

Issue is the widest gate in the API, and its checks fire in exactly this order. The lease must be `APPROVED` (`ERR_INVALID_LEASE_STATE`). The deployment must be in `DEPLOYED` — gear already `HARVESTING`, `RETRIEVED` or `VOIDED` is refused with `ERR_INVALID_GROWOUT_UNIT_STATE`. The growing area's `classification` must be `APPROVED` or `CONDITIONALLY_APPROVED`; `RESTRICTED` and `PROHIBITED` areas are refused with `ERR_AREA_CLASSIFICATION_NOT_HARVESTABLE`. Note that `RESTRICTED` is a harvestable classification for time-to-temperature purposes but not a harvestable classification for authorization purposes — restricted waters require relay or depuration, which this API does not model. The area's `harvest_status` must be `OPEN`, otherwise `ERR_AREA_HARVEST_CLOSED`.

Then the window: `window_end` must be strictly after `window_start`, and the span from `window_start` to `window_end` must be at most `MAX_AUTHORIZATION_WINDOW_HOURS`, which is 24 hours — exactly 24 hours is permitted — and either failure is `ERR_AUTHORIZATION_WINDOW_INVALID` at HTTP 422. Both `window_start` and `window_end` describe future intent and are therefore exempt from the future-dating rule: an authorization may legitimately be issued for a window that has not begun.

Then vessel capacity. Each authorization occupies the half-open instant interval from its `window_start` to its `window_end`. Count the vessel's existing authorizations whose `status` is `ISSUED` or `ACTIVE` — `CLOSED` and `VOIDED` ones release capacity and are excluded — for which the existing `window_start` is strictly before the new `window_end` **and** the new `window_start` is strictly before the existing `window_end`. Adjacency is free: an existing `window_end` equal to the new `window_start` is not an overlap. Containment and partial straddles both count. If that count plus 1 strictly exceeds the vessel's `concurrent_authorization_capacity`, the request is refused with `ERR_VESSEL_CAPACITY_CONFLICT`. The test is aggregate rather than pairwise, so with a capacity of 2 two mutually overlapping authorizations are fine and the third is rejected.

Then the deployment must be free: no other authorization on the same deployment may have `status` `ISSUED` or `ACTIVE`, otherwise `ERR_UNIT_ALREADY_AUTHORIZED`. One deployment, one live authorization — regardless of whether the windows overlap.

Then husbandry currency, read exactly as §3.6 defines it: a failing inspection test is `ERR_HUSBANDRY_LAPSED`, and, for `BOTTOM` gear only, a failing predator-control test is `ERR_PREDATOR_CONTROL_LAPSED`, with the inspection test checked first.

Then the dealer. The dealer's `certification_category` must be `SHELLSTOCK_SHIPPER` or `SHUCKER_PACKER` to receive shellstock directly from a harvest; a `REPACKER` or `DEPURATION_PROCESSOR` is refused with `ERR_DEALER_CATEGORY_NOT_PERMITTED`. The dealer's `certified_through` must be at or after the logical clock's calendar date, otherwise `ERR_DEALER_CERTIFICATION_EXPIRED`. The deployment's own `lease_id` must equal the requested `lease_id`, otherwise `ERR_UNIT_LEASE_MISMATCH` — an operator holding two leases cannot authorize gear on one under the other. The dealer's `listing_status` must not be `SUSPENDED`, otherwise `ERR_DEALER_SUSPENDED`. And last of all, the lease's `rent_paid_through_date` must be at or after the logical clock's calendar date, otherwise `ERR_LEASE_RENT_DELINQUENT` at HTTP 402.

**The area snapshot.** On issue, `growing_area_id` on the authorization is set to a **snapshot** of the lease's `growing_area_id`, taken at issue time and never re-derived afterwards. This snapshot, not a live join through the lease, is what every area-closure cascade matches on, and it is what `open_authorization_count` counts. After every issue, close, void and cascade the snapshot and the count must reconcile: `open_authorization_count` on an area is the number of authorizations whose snapshotted `growing_area_id` is that area and whose `status` is `ISSUED` or `ACTIVE`.

**Activation.** `status` walks `ISSUED`, `ACTIVE`, `CLOSED` and `VOIDED`, with `CLOSED` and `VOIDED` both terminal. The owning operator activates an authorization in `ISSUED` — any other state is `ERR_INVALID_AUTHORIZATION_STATE` — with no request body at all. Activation re-checks the sanitary gates, because conditions can have changed since issue: the deployment must still be `DEPLOYED` (`ERR_INVALID_GROWOUT_UNIT_STATE`), the area's `classification` must still be `APPROVED` or `CONDITIONALLY_APPROVED` (`ERR_AREA_CLASSIFICATION_NOT_HARVESTABLE`), and the area's `harvest_status` must still be `OPEN` (`ERR_AREA_HARVEST_CLOSED`). The logical clock must fall inside the half-open window — at or after `window_start` and strictly before `window_end` — otherwise `ERR_OUTSIDE_AUTHORIZATION_WINDOW`; activating exactly at `window_end` is outside. Activation sets `status` to `ACTIVE`, stamps `harvest_start_at` with the logical clock (never with a client-supplied instant), and moves the deployment from `DEPLOYED` to `HARVESTING`. The response is the authorization at HTTP 200. Note that activation does **not** change `active_authorization_count` on the vessel: that counter covers `ISSUED` and `ACTIVE` alike, so it was already incremented at issue.

**Closing.** The owning operator closes an authorization in `ACTIVE`, again with no request body. Closing sets `status` to `CLOSED`, stamps `harvest_end_at` with the logical clock — which is necessarily at or after `harvest_start_at`, and must be strictly after it — moves the deployment from `HARVESTING` back to `DEPLOYED`, decreases the vessel's `active_authorization_count` by 1, and recomputes the area's `open_authorization_count`. The response is the authorization at HTTP 200. Closing is not gated on the area still being open: an operator must always be able to close out a harvest they have already begun.

**Voiding is never a client act.** There is no capability that voids an authorization. `VOIDED` is reached only by cascade, and only with `void_reason` `AREA_CLOSURE` (from a rainfall closure, the sample sweep, or a decision into `PROHIBITED`) or `SEED_LOT_REJECTED` (from a positive pathogen screening). Voiding from `ISSUED` sets `status` and `void_reason` and decreases the vessel's `active_authorization_count` by 1. Voiding from `ACTIVE` additionally moves the deployment from `HARVESTING` back to `DEPLOYED` and, in the area-closure case, continues into the lot-embargo hop.

**Harvested volume.** `harvested_bushels` is the sum of `bushels` over this authorization's lots whose `status` is not `VOIDED`, so voiding a lot returns its bushels to the projection headroom. Landing a lot requires `harvested_bushels` plus the new `bushels` to be at most `projected_bushels`; strictly exceeding it is `ERR_HARVEST_EXCEEDS_PROJECTION`, and landing exactly on the projection is permitted.

### 3.8. Landing a Lot: Time-to-Temperature, the Vibrio Allowance and Lease Settlement

Landing a harvest lot is the single richest computation in this API: one request selects a vibrio control plan, derives an allowance from four sequential adjustments, measures two independent elapsed times, selects which one governs from the area's classification, judges compliance, and settles the money.

**Vibrio control plans.** The `ShellfishControlAuthority` publishes a plan for one `season_month` (an integer from 1 to 12), giving `max_time_to_temperature_minutes` (the baseline minutes allowed from the first shellstock out of water to temperature control, at least 60), `high_water_temp_c` (the water temperature at or above which the high-temperature reduction applies) and `high_temp_reduction_minutes` (the minutes subtracted at or above that temperature, at least 0). Publication answers HTTP 201 with `status` `ACTIVE`, and any existing plan for the same `season_month` whose `status` is `ACTIVE` is moved to `SUPERSEDED` — one active plan per month, latest publication wins. There is no capability that edits or reactivates a plan.

**The request.** The owning operator lands a lot under an authorization in `ACTIVE` — any other state is `ERR_INVALID_AUTHORIZATION_STATE` — naming `lot_code` (unique across all harvest lots, otherwise `ERR_DUPLICATE_LOT_CODE`), `bushels` (at least 1), the three instants `first_out_of_water_at`, `last_out_of_water_at` and `placed_in_temperature_control_at`, and `water_temp_c`, the water temperature in Celsius at harvest. All six are required. Landing answers HTTP 201 with `status` `HARVESTED`, `harvest_authorization_id` set to the authorization the lot was landed under, `dealer_id` copied from that authorization's dealer, `shipment_id` null, all four tag fields null, and `embargo_reason` and `void_reason` null. Lots can afterwards be listed filtered by `harvest_authorization_id`, `dealer_id`, `shipment_id`, `vibrio_control_plan_id` or `status`.

The gates, in order: the area's `harvest_status` must be `OPEN` (`ERR_AREA_HARVEST_CLOSED`); an `ACTIVE` vibrio control plan must exist for the UTC month of `first_out_of_water_at`, otherwise `ERR_NO_VIBRIO_PLAN_FOR_SEASON`; no instant may be after the logical clock (`ERR_FUTURE_DATED_EVENT`); `first_out_of_water_at` must fall inside the half-open window from `window_start` to `window_end`, otherwise `ERR_OUTSIDE_AUTHORIZATION_WINDOW` — note the window test uses the harvest instant here, whereas activation used the logical clock; the three instants must be ordered, meaning `last_out_of_water_at` at or after `first_out_of_water_at` **and** `placed_in_temperature_control_at` at or after `last_out_of_water_at`, otherwise `ERR_INVALID_HARVEST_INSTANTS` at HTTP 422; the projection must hold (`ERR_HARVEST_EXCEEDS_PROJECTION`); and `lot_code` must be unique. The plan check precedes the instant-ordering check, so a landing in a month with no plan is answered `ERR_NO_VIBRIO_PLAN_FOR_SEASON` even when its instants are also out of order.

**Selecting the plan and deriving the allowance.** `vibrio_plan_month` is the UTC calendar month (1 to 12) of `first_out_of_water_at`, and `vibrio_control_plan_id` is the identifier of the plan whose `status` is `ACTIVE` and whose `season_month` equals that month. `SUPERSEDED` plans are never selected, and there is no default allowance when no active plan exists — the landing is simply refused. From that plan, `allowed_ttt_minutes` is derived in four steps applied in exactly this order. Start from the plan's `max_time_to_temperature_minutes`. First, if the payload `water_temp_c` is at or above the plan's `high_water_temp_c` — an inclusive comparison at one decimal place — subtract the plan's `high_temp_reduction_minutes`, because warm water accelerates vibrio growth. Second, if the deployment's `gear_type` is `BOTTOM` or `RACK_AND_BAG`, subtract `INTERTIDAL_PENALTY_MINUTES`, which is 30, because that gear leaves animals exposed at low tide; `FLOATING_BAG` gear subtracts nothing. Third, if the vessel's `refrigeration_type` is `MECHANICAL`, add `REFRIGERATION_CREDIT_MINUTES`, which is 60; `ICE_SLURRY` and `NONE` add nothing. Fourth and last, apply a hard floor: `allowed_ttt_minutes` is the greater of the running figure and `MIN_FLOOR_MINUTES`, which is 60. The result is not a product of independent factors — the same water temperature yields a different allowance for every gear and refrigeration pairing, and the floor can absorb the entire reduction, so a plan baseline of 120 minutes reduced by 60 for temperature and 30 for intertidal gear yields 60, not 30.

**The two bases.** `ttt_minutes_first_basis` is the whole minutes elapsed from `first_out_of_water_at` to `placed_in_temperature_control_at`. `ttt_minutes_last_basis` is the whole minutes elapsed from `last_out_of_water_at` to `placed_in_temperature_control_at`. Both are always computed and both are always persisted on the lot, whichever one governs; fractional minutes are truncated toward zero.

`ttt_basis_variant` decides which one gates compliance, and it is read from the growing area's `classification` at the moment of landing. When `classification` is `APPROVED`, the variant is `FIRST_HARVEST_BASIS`: the clock starts when the *first* animal leaves the water, so the entire harvest window counts against the allowance. When `classification` is `CONDITIONALLY_APPROVED` or `RESTRICTED`, the variant is `LAST_HARVEST_BASIS`: the clock starts when the *last* animal leaves the water, ignoring the time earlier animals spent on deck. `governing_ttt_minutes` is `ttt_minutes_first_basis` under `FIRST_HARVEST_BASIS` and `ttt_minutes_last_basis` under `LAST_HARVEST_BASIS`. Because the last-basis figure is strictly smaller than the first-basis figure whenever `last_out_of_water_at` is later than `first_out_of_water_at`, the very same instants can be `NONCOMPLIANT` on one basis and `COMPLIANT` on the other — an area downgraded from `APPROVED` to `CONDITIONALLY_APPROVED` becomes *easier* to comply with on this one axis, which is not an error in the specification.

`compliance_status` is `COMPLIANT` when `governing_ttt_minutes` is at or below `allowed_ttt_minutes` — exactly at the allowance is compliant — and `NONCOMPLIANT` otherwise. A `NONCOMPLIANT` lot is still recorded, at HTTP 201, with all its computed fields; nothing about landing is refused on compliance grounds. It is the tag step that refuses it.

**Settlement.** The same request settles the lot in six steps, in this order. Step 1 establishes the season volume *including* the lot being landed: `season_total_bushels_at_creation` is the payload `bushels` plus the sum of `bushels` over the lease's existing harvest lots whose `status` is `HARVESTED`, `TAGGED`, `SHIPPED`, `EMBARGOED` or `RECALLED` — `VOIDED` lots are excluded — and whose `first_out_of_water_at` falls in the same UTC calendar year as the lot being landed. Step 2 selects the tier from that total on a whole-total basis rather than marginally: at or below `TIER1_MAX_BUSHELS` of 500 the rate is `TIER1_RATE_CENTS`, 115 cents per bushel; otherwise at or below `TIER2_MAX_BUSHELS` of 2000 the rate is `TIER2_RATE_CENTS`, 95 cents; otherwise the rate is `TIER3_RATE_CENTS`, 70 cents. That rate is written to `royalty_rate_cents_per_bushel`. Step 3 sets `royalty_cents` to that rate multiplied by this lot's `bushels` — the whole lot is charged at the tier the season total reached, so a lot that crosses a tier boundary is charged entirely at the cheaper rate. Step 4 sets `inspection_fee_cents` to 0 when `royalty_cents` is at or above `INSPECTION_FEE_WAIVER_CENTS`, which is 50000 cents, and otherwise to the flat `INSPECTION_FEE_CENTS` of 2500. Step 5 sets `conservation_surcharge_cents` to `SURCHARGE_RATE`, which is 0.03, multiplied by the sum of `royalty_cents` and `inspection_fee_cents`, rounded half-up to whole cents — rounded exactly once, here, and never by rounding a summed base later. Step 6 sets `lot_settlement_cents` to `royalty_cents` plus `inspection_fee_cents` plus `conservation_surcharge_cents`, adds that figure to the lease's `royalty_accrued_cents`, and adds this lot's `bushels` to the authorization's `harvested_bushels`.

**Voiding a lot.** `status` walks `HARVESTED`, `TAGGED`, `SHIPPED`, `EMBARGOED`, `RECALLED` and `VOIDED`, with `RECALLED` and `VOIDED` terminal. The owning operator voids a lot in `HARVESTED` or `TAGGED`, optionally with a `void_note`, and only while `shipment_id` is null; a lot already on a shipment, or in any other state, is refused with `ERR_INVALID_LOT_STATE`. The void sets `status` to `VOIDED` with `void_reason` `OPERATOR_CORRECTION`, **retains** every tag field for the audit trail, subtracts `lot_settlement_cents` from the lease's `royalty_accrued_cents` — restoring the pre-landing value exactly — and subtracts `bushels` from the authorization's `harvested_bushels`. Critically, **no re-tiering occurs**: the `royalty_rate_cents_per_bushel` already stamped on the lease's surviving lots is never recomputed, even though the season total that selected those rates has now fallen. The void is an exact reversal of one lot's own accrual, not a recomputation of the season.

### 3.9. Tagging, Dealer Certification, Shipping and the Recall Chain

**Certifying a dealer.** The `ShellfishControlAuthority` certifies a dealer with its `name`, its two-letter `state_code` (exactly two uppercase letters), its `certification_category` (`SHELLSTOCK_SHIPPER`, `SHUCKER_PACKER`, `REPACKER` or `DEPURATION_PROCESSOR`), its `certification_no` (unique across dealers, and the number printed on tags) and its `certified_through` calendar date. Certification answers HTTP 201 with `listing_status` `NOT_LISTED`, `icssl_listed_through` null, `recall_strike_count` 0, `suspension_reason` null and `version` 1.

`listing_status` is the interstate-listing dimension and takes `NOT_LISTED`, `LISTED` or `SUSPENDED`; no state is terminal, and a dealer can cycle between `LISTED` and `SUSPENDED` indefinitely.

**Renewals carry the version.** A renewal names `expected_dealer_version` (mandatory, per §2.8, refused with `ERR_STALE_DEALER_VERSION` at HTTP 412 on mismatch), the new `certified_through`, and optionally a new `icssl_listed_through` for the Interstate Certified Shellfish Shippers List. `certified_through` must be strictly after the logical clock's calendar date — renewing to today or to a past date is `ERR_INVALID_REQUEST` at HTTP 400 — and whenever `icssl_listed_through` is supplied it must be at or before `certified_through`, since a dealer cannot be interstate-listed past its own certification, which is likewise `ERR_INVALID_REQUEST`. A renewal replaces `certified_through`, replaces `icssl_listed_through` when supplied, leaves it untouched when omitted, and advances `version` by 1; the response is the dealer at HTTP 200.

The listing dimension moves only on the first listing. A renewal on a `NOT_LISTED` dealer that supplies `icssl_listed_through` moves `listing_status` to `LISTED`; one that omits it leaves the dealer `NOT_LISTED`. A renewal on a `LISTED` dealer leaves it `LISTED`. And a renewal on a `SUSPENDED` dealer updates the certification dates and the `version` but leaves `listing_status` at `SUSPENDED` — renewing paperwork does not lift a suspension.

**Suspension and reinstatement.** The authority suspends a dealer whose `listing_status` is `LISTED`, optionally with a `suspension_note`; any other state is `ERR_INVALID_DEALER_LISTING_STATE`. Suspension sets `listing_status` to `SUSPENDED` with `suspension_reason` `AUTHORITY_ACTION`, and cascades: every shipment of this dealer whose `status` is `CREATED` moves to `HELD` with `held_reason` `DEALER_SUSPENSION`. Shipments already `SHIPPED`, `HELD` or `RECALLED` are untouched. The authority reinstates a dealer whose `listing_status` is `SUSPENDED` — any other state is `ERR_INVALID_DEALER_LISTING_STATE` — optionally supplying a fresh `icssl_listed_through`; reinstatement additionally requires `certified_through` to be at or after the logical clock's calendar date, otherwise `ERR_DEALER_CERTIFICATION_EXPIRED`. It sets `listing_status` to `LISTED`, sets `suspension_reason` back to null, and replaces `icssl_listed_through` when one was supplied. Reinstatement does **not** release the held shipments — they stay `HELD` — and it does **not** reset `recall_strike_count`. Strikes are permanent, so a reinstated dealer standing at two strikes is re-suspended by the very next confirmed recall.

**Tagging a lot.** The owning operator tags a lot in `HARVESTED` — any other state is `ERR_INVALID_LOT_STATE` — supplying `harvest_date` and `dealer_certification_no`, both required. Four checks apply in this order. The lot's `compliance_status` must be `COMPLIANT`, otherwise `ERR_TIME_TEMPERATURE_EXCEEDED`: this is where a time-and-temperature failure actually bites, and it is unrecoverable, because there is no capability that recomputes compliance and the lot can then only be voided. The payload `harvest_date` must equal the UTC calendar date of the lot's `first_out_of_water_at`, otherwise `ERR_TAG_HARVEST_DATE_MISMATCH`. The payload `dealer_certification_no` must equal the `certification_no` of the dealer named by the lot's `dealer_id`, otherwise `ERR_TAG_DEALER_CERT_MISMATCH`. And that dealer's `listing_status` must not be `SUSPENDED`, otherwise `ERR_DEALER_SUSPENDED`. Tagging sets `status` to `TAGGED` and stamps four fields: `tag_harvest_date` from the payload `harvest_date`, `tag_area_code` from the growing area's `code`, `tag_lease_code` from the lease's `lease_code`, and `tag_dealer_certification_no` from the payload `dealer_certification_no`. These four are the shellstock tag — the chain of custody that the recall machinery later reads — and they are never cleared afterwards, not even by a void. The response is the lot at HTTP 200.

**Assembling a shipment.** A `SeafoodDealer` assembles a shipment. Because that role is backed by a dealer record, the acting identity *is* a dealer identifier and must equal the `dealer_id` named in the request, otherwise `ERR_DEALER_OWNERSHIP_VIOLATION`. The request also names the two-letter `destination_state`, the `carrier` moving the shellstock, and `lot_ids`, between 1 and 25 harvest lot identifiers. Every member of `lot_ids` must exist (`ERR_HARVEST_LOT_NOT_FOUND`), every one must have `status` `TAGGED` (`ERR_LOT_NOT_TAGGED`), and every one must have `dealer_id` equal to the shipment's `dealer_id` and `shipment_id` still null (`ERR_LOT_DEALER_MISMATCH`) — a lot cannot ride two shipments, and it cannot be consigned by a dealer it was not landed for. The dealer's `certified_through` must be at or after the logical clock's calendar date (`ERR_DEALER_CERTIFICATION_EXPIRED`) and its `listing_status` must not be `SUSPENDED` (`ERR_DEALER_SUSPENDED`). Creation answers HTTP 201 with `status` `CREATED`, `shipped_at`, `held_reason` and `recall_reason` null, `lot_count` set to the number of entries in `lot_ids`, `total_bushels` set to the sum of `bushels` over those lots, and `is_interstate` set to true exactly when `destination_state` differs from the dealer's own `state_code`. Every lot in `lot_ids` has its `shipment_id` set to this shipment.

**Shipping.** `status` walks `CREATED`, `SHIPPED`, `HELD` and `RECALLED`, with `RECALLED` terminal. The owning dealer ships a shipment in `CREATED` — any other state, including `HELD`, is `ERR_INVALID_SHIPMENT_STATE` — supplying `shipped_at`. Five checks apply. Per §2.7 the two `shipped_at` conditions described at the end of this paragraph are judged first — the cold-chain ordering sits at the state rung and the future-dating check at the temporal rung — and the five then run in the order `ERR_DEALER_CERTIFICATION_EXPIRED`, `ERR_DEALER_SUSPENDED`, `ERR_DEALER_NOT_LISTED`, `ERR_DEALER_NOT_LISTED_FOR_INTERSTATE`, `ERR_LOT_NOT_TAGGED`. The dealer's `listing_status` must not be `SUSPENDED` (`ERR_DEALER_SUSPENDED`) and must be exactly `LISTED` when the shipment leaves the dock (`ERR_DEALER_NOT_LISTED`) — so a `NOT_LISTED` dealer is refused with `ERR_DEALER_NOT_LISTED`. The dealer's `certified_through` must be at or after the logical clock's calendar date (`ERR_DEALER_CERTIFICATION_EXPIRED`). When `is_interstate` is true, the dealer's `icssl_listed_through` must also be at or after the logical clock's calendar date, otherwise `ERR_DEALER_NOT_LISTED_FOR_INTERSTATE`; an intrastate shipment ignores the listing window entirely. Every lot in `lot_ids` must still have `status` `TAGGED` (`ERR_LOT_NOT_TAGGED`) — a lot embargoed since assembly blocks the whole shipment. And `shipped_at` must not be after the logical clock (`ERR_FUTURE_DATED_EVENT`) and must be at or after the greatest `placed_in_temperature_control_at` over the shipment's lots, since a shipment cannot leave before its coldest-chain milestone; violating that last ordering is `ERR_INVALID_SHIPMENT_STATE` at HTTP 409. Shipping sets `status` to `SHIPPED`, stamps `shipped_at`, and moves every lot in `lot_ids` from `TAGGED` to `SHIPPED`. The response is the shipment at HTTP 200.

**Holding.** `HELD` is never a client act. A shipment in `CREATED` moves to `HELD` either because one of its lots was embargoed by an area closure, giving `held_reason` `LOT_EMBARGO`, or because its dealer was suspended, giving `held_reason` `DEALER_SUSPENSION`. There is no capability that releases a hold: a `HELD` shipment can only go on to `RECALLED`.

**Opening an investigation.** The authority opens an illness investigation against a source shipment whose `status` is `CREATED`, `SHIPPED` or `HELD` — a `RECALLED` shipment is refused with `ERR_INVALID_SHIPMENT_STATE` — supplying the `reported_at` instant the cluster was reported (which must not be after the logical clock, otherwise `ERR_FUTURE_DATED_EVENT`), `illness_count` (at least 1) and the suspected `pathogen` (`VIBRIO_PARAHAEMOLYTICUS`, `VIBRIO_VULNIFICUS`, `NOROVIRUS` or `SALMONELLA`). Opening answers HTTP 201 with `source_shipment_id` set, `status` `OPEN`, `scope_variant` and `confirmed_at` null, `traced_lot_ids` an empty array, and `traced_lot_count` and `recalled_shipment_count` both 0.

**The traceback.** `status` walks `OPEN`, `TRACEBACK`, `CONFIRMED` and `CLOSED_UNSUBSTANTIATED`, with the last two terminal. The authority runs the traceback on an investigation in `OPEN` or in `TRACEBACK` — any other state is `ERR_INVALID_INVESTIGATION_STATE` — supplying the required `scope_variant`. Running it from `TRACEBACK` re-runs the analysis with the new scope, replacing `scope_variant` and recomputing both traced fields, so the authority may widen or narrow the net as many times as it likes before confirming. The response is the investigation at HTTP 200.

The seed set is the source shipment's own lots: harvest lots whose `shipment_id` is the investigation's `source_shipment_id` and whose `status` is `TAGGED`, `SHIPPED` or `EMBARGOED`. `VOIDED` and already-`RECALLED` lots are excluded from the seed set and from any expansion of it. Under `NARROW`, the traced set is exactly that seed set — only the lots physically on the source shipment. Under `BROAD`, the traced set additionally pulls in every harvest lot whose `status` is `TAGGED`, `SHIPPED` or `EMBARGOED` that shares a seed lot's `tag_area_code` and whose `tag_harvest_date` is within `TRACEBACK_DAY_WINDOW` — one day, inclusive on both sides — of that seed lot's `tag_harvest_date`. The expansion crosses lease and shipment boundaries freely: it is an epidemiological net cast over the same waters on the same days, not a walk through the consignment. A lot that was never tagged has no `tag_area_code` and can therefore never be pulled in by `BROAD`. `traced_lot_ids` holds the traced set ordered by `tag_harvest_date` ascending with `created_at` ascending as the tie-break and, where `created_at` also ties, `id` ascending as the final tie-break — the same three-key discipline §2.3 applies to list responses — and `traced_lot_count` is its length. For identical stored data `BROAD` returns a strictly larger `traced_lot_count` than `NARROW` whenever a sibling lot exists, and the confirm cascade then recalls a strictly different set of shipments — which is precisely why the scope is an explicit authority decision rather than a derived value.

**Confirming: the four-hop recall cascade.** The authority confirms an investigation in `TRACEBACK` — any other state is `ERR_INVALID_INVESTIGATION_STATE` — optionally supplying `confirmed_at`. `traced_lot_count` must be at least 1, otherwise the request is refused with `ERR_INVALID_INVESTIGATION_STATE`: there is nothing to recall. Confirmation sets `status` to `CONFIRMED` and `confirmed_at` to the supplied instant when one was given and otherwise to the logical clock, and then runs four hops in exactly this order.

- *Hop 1.* Every lot in `traced_lot_ids` whose `status` is `TAGGED` or `SHIPPED` moves to `RECALLED`. A traced lot sitting in `EMBARGOED` is left in `EMBARGOED` — the embargo already stopped it — and so are lots already `RECALLED`.
- *Hop 2.* Each lot recalled in hop 1 drags its shipment: the shipment named by that lot's `shipment_id`, when its `status` is `CREATED`, `SHIPPED` or `HELD`, moves to `RECALLED` with `recall_reason` `ILLNESS_TRACEBACK`. `recalled_shipment_count` on the investigation records the number of **distinct** shipments moved by this hop, so two recalled lots on one shipment count once.
- *Hop 3.* Each shipment recalled in hop 2 adds one strike to its dealer's `recall_strike_count`; a dealer with three shipments recalled by one confirmation gains three strikes. Any dealer whose resulting `recall_strike_count` is at or above `DEALER_SUSPENSION_STRIKE_THRESHOLD`, which is 2, and whose `listing_status` is currently `LISTED`, moves to `SUSPENDED` with `suspension_reason` `RECALL_STRIKES`. The threshold is inclusive, so the second strike suspends. A dealer already `SUSPENDED` or still `NOT_LISTED` accrues the strikes without a listing transition.
- *Hop 4.* Each dealer suspended in hop 3 has its remaining shipments whose `status` is `CREATED` moved to `HELD` with `held_reason` `DEALER_SUSPENSION` — the collateral consignments that were not themselves implicated.

Every row touched by any hop has its `updated_at` and `version` advanced, and the whole cascade completes inside the confirming request.

**Closing unsubstantiated.** The authority closes an investigation in `OPEN` or in `TRACEBACK` — any other state is `ERR_INVALID_INVESTIGATION_STATE` — optionally with a `close_note`. Closing sets `status` to `CLOSED_UNSUBSTANTIATED` and touches no lot, no shipment and no dealer whatsoever. Any `traced_lot_ids` and `traced_lot_count` already produced are **retained** as traceback documentation, and `scope_variant` stays as it was; closing does not erase the analysis, it only declines to act on it. `CONFIRMED` and `CLOSED_UNSUBSTANTIATED` are both terminal, so an investigation is decided exactly once.
