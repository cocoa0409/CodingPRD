# Supermarket In-Store Bakery Production API — Product Requirements Document

## 1. Introduction

A supermarket in-store bakery is one of the few departments in a grocery store that manufactures its own inventory every single morning, sells it against a forecast that shifts by day of week and by daypart, and then throws away whatever the shoppers did not buy. The department manager's day is a chain of irreversible commitments: a forecast becomes a production plan, the plan becomes proof-and-bake slots on a small number of oven decks, the racks become sellable units with a shelf life measured in hours, and everything still on the shelf at close becomes either a donation or a shrink charge against the department's budget. Meanwhile the cake desk is taking custom orders whose decoration work has to be finished before the customer's pickup window opens, the decorator bench has a finite throughput, and a peanut-flour wedding tier cannot share a deck with a product merchandised as nut-free.

This document specifies the API that runs that department. It is deliberately opinionated about arithmetic and about ordering, because in a bakery the difference between a compliant day and a budget breach is often a single rounding step or a single rack. The system must reproduce the department's decisions deterministically: the same forecast, the same ovens and the same clock must always yield the same plan, the same labor charge, the same quote and the same shrink percentage. Every monetary figure is carried in whole cents, every ratio is carried to four decimal places, and every allocation loop has a fixed traversal order.

The API is mounted under `/bakery`. It is a flat resource space — departments, bake days, ovens, products, ingredients, production runs, pickup slots, custom cake orders, ingredient orders and waste records are all peer collections, and parenthood is carried in identifier fields on the child rather than in the URL. A single test-driving capability outside that mount lets an operator move the server's logical clock, because almost every rule in this specification is a rule about time.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the caller's role. If either header is absent, or if `X-User-Role` is not exactly one of the five recognised role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not authorised for the endpoint being called, the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The five roles are `RegionalAdmin`, `DepartmentManager`, `Baker`, `Decorator` and `CakeDesk`.

A `RegionalAdmin` is a chain-level operator. Regional admins provision the reference data that departments operate against — the departments themselves, their products, their ingredients and their ovens — and they alone drive the logical clock. A `DepartmentManager` runs exactly one bakery department: opening bake days, entering forecast lines, generating and locking plans, closing the day, raising and cancelling ingredient orders, taking ovens in and out of service, authorising markdowns and voiding mis-attested waste. A `Baker` works the production floor: proofing, baking and completing runs, attesting waste and booking supplier deliveries. A `Decorator` works the custom cake queue, pulling confirmed orders into decoration and marking them ready. A `CakeDesk` operator staffs the front counter: taking, confirming, revising and releasing custom cake orders, and opening or closing pickup windows. Every role may read every collection and every single resource exposed by the API.

Identity semantics differ by role, and they matter because several rules compare a caller's identity to stored data. When `X-User-Role` is `DepartmentManager`, `X-User-ID` is the `id` of the acting `BakeryDepartment`; ownership checks on any resource that references a department compare the resource's owning department — resolved through `department_id` directly, or through `bake_day_id`, or through `production_run_id` and then that run's bake day — to `X-User-ID`, and a mismatch is rejected with `ERR_DEPARTMENT_SCOPE_VIOLATION` (HTTP 403). When `X-User-Role` is `RegionalAdmin`, `Baker`, `Decorator` or `CakeDesk`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records those opaque identifiers where a rule needs them later — a baker's identifier is stamped onto `executed_by_user_id` when a run is completed, the identifier of whoever attests a waste record is stamped onto `attested_by_user_id`, and the identifier of the manager who voids one is stamped onto `voided_by_user_id` — but it never compares them to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty uppercase alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is read from the host's wall clock, not from the logical clock of §2.11, so moving the logical clock does not move it.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A value outside those bounds is a malformed request and is rejected with `ERR_INVALID_REQUEST`, and so is a value that is not a base-ten integer; an empty-string `limit` or `offset` is treated exactly as though the parameter had been omitted.

List results are always ordered by `created_at` ascending, so pagination is stable as long as no new rows are inserted between calls; rows sharing a `created_at` value are ordered by the sequence in which the server first wrote them, which makes the ordering total. The `meta` block of a list response carries `limit` and `offset` as they were applied, `total_count` as the number of rows matching the filter before the page window is applied, and `has_more` as a boolean that is true exactly when rows remain beyond the current window. Every filter documented in §3 is optional and is matched literally against the stored value; an empty-string filter is treated as absent, a filter whose declared domain is an enumeration rejects any value outside that set with `ERR_INVALID_REQUEST`, a boolean filter accepts only `true`, `false`, `1` or `0` in any letter case and rejects anything else the same way, and a filter naming an identifier that matches no row simply yields an empty page rather than a 404.

### 2.4. Common Resource Properties

Every resource in this system — `BakeryDepartment`, `BakeDay`, `Oven`, `Product`, `Ingredient`, `ProductionRun`, `PickupSlot`, `CustomCakeOrder`, `IngredientOrder` and `WasteRecord` — carries the same four system-managed properties.

- `id` (string): a server-minted UUID. It carries no type prefix and clients never supply it. More generally, a body property an endpoint does not declare — including one naming a field the server derives for itself — is ignored rather than rejected.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, recording when the row was first written.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row. Both of these audit stamps are read from the host's wall clock rather than from the logical clock of §2.11; that clock governs the business `_utc` fields and the time comparisons §2.11 enumerates, not `created_at` or `updated_at`.
- `version` (integer): a counter that starts at 1 on creation and increments by exactly 1 on every mutation of that row.

The `version` counter is not decorative — it is the serialization signal the whole planning workflow leans on, and §2.5 turns it into a hard precondition on two writes. Recomputation of a derived field counts as a mutation: when a completed run pushes a bake day's `production_cost_cents` up, or when a voided waste record pulls its `shrink_cost_cents` back down, that bake day's `updated_at` is refreshed and its `version` increments. The same holds for the derived money field on a department and for the reserved-capacity field on a pickup slot. Where a single request mutates several rows, each mutated row advances its own `version` by 1; the cascade never advances a row twice for a single logical change unless the specification below says two distinct changes occurred.

Identifiers embedded in URL paths are validated left to right before any body field is examined. A path such as `/bakery/production-runs/{runId}/complete` resolves `runId` first, and a path such as `/bakery/waste-records/{wasteRecordId}/void` resolves `wasteRecordId` first; the first identifier that names nothing produces that identifier's own 404 and short-circuits the rest of the request. The path variables the API exposes are `departmentId`, `bakeDayId`, `productId`, `ingredientId`, `ovenId`, `runId`, `pickupSlotId`, `orderId`, `ingredientOrderId` and `wasteRecordId`. Body-borne identifiers are resolved after every path variable, in the order the request body declares them.

### 2.5. Optimistic Concurrency on Planning and Purchasing Writes

Two writes in this system can silently destroy work a client never observed, and both are therefore guarded by an explicit version precondition. Neither guard is optional and neither has a default: the field must be present in the request body.

Generating a production plan (`POST /bakery/bake-days/{bakeDayId}/generate-plan`) requires `expected_bake_day_version`, carrying the client's last observed `version` of the target `BakeDay`. It must be a non-negative JSON integer, and an absent, non-integer or negative value is a request-shape failure answered with `ERR_INVALID_REQUEST` before the version is ever compared. If that number does not equal the bake day's current `version`, the request is rejected with `ERR_STALE_BAKE_DAY_VERSION` (HTTP 412). The reason is direct: plan generation legitimately supersedes the day's plan-generated runs, so a writer holding an older view of the day would discard a plan it never saw. The version check converts that hazard into a deterministic 412.

Creating an ingredient order (`POST /bakery/ingredient-orders`) requires `expected_department_version`, carrying the client's last observed `version` of the target `BakeryDepartment`. It must be a non-negative JSON integer, and an absent, non-integer or negative value is a request-shape failure answered with `ERR_INVALID_REQUEST` before the version is ever compared. If that number does not equal the department's current `version`, the request is rejected with `ERR_STALE_DEPARTMENT_VERSION` (HTTP 412). Here the hazard is fiscal: the run-completion cascade mints automatic reorder drafts and moves the department's open purchase commitment on its own, so a manual order raised from a stale view of the department would double-commit spend the writer believes is still uncommitted.

No other endpoint takes a version field. `expected_bake_day_version` is meaningful only on plan generation and `expected_department_version` only on ingredient-order creation; every other write proceeds on the strength of its own state preconditions.

### 2.6. Money, Minutes and Ratios: Precision Discipline

Money is carried in whole cents as integers everywhere it is stored on a resource — `unit_retail_cents`, `ingredient_cost_cents`, `unit_cost_basis_cents`, `waste_cost_cents`, `markdown_unit_price_cents`, `line_cost_cents`, `order_total_cents`, `quote_subtotal_cents`, `rush_fee_cents`, `volume_discount_cents`, `quote_total_cents`, `production_cost_cents`, `shrink_cost_cents` and `open_purchase_commitment_cents` are all integer cent amounts. The two configuration rates that feed them, `unit_cost_cents` on an ingredient and `labor_rate_cents_per_minute` on a department, are the exception: they are per-unit rates that preserve two decimal places of input precision. The department's `labor_rate_cents_per_minute` is the rate at which planned and actual bakery labor minutes are valued for departmental reporting; it must be greater than zero.

Labor minutes are numbers carried to two decimal places. Ratios — `shrink_budget_pct`, `freight_surcharge_pct`, `markdown_pct`, `shrink_cost_basis_pct` and `shrink_unit_basis_pct` — are fractions of one, not percentages out of a hundred, and are carried to four decimal places. On the wire both ratios and labor minutes are plain JSON numbers, never strings. On input, every money, rate, ratio and labor field must likewise be a JSON number — a numeric string is rejected with `ERR_INVALID_REQUEST` — an integer field accepts a JSON number only when it has no fractional part, and a JSON boolean is never accepted as a number. A rate or ratio supplied with more decimal places than its field holds is rounded half up to the field's precision rather than rejected.

Wherever this document says a value is rounded, the method is round half up: a value exactly halfway between two representable results goes to the larger magnitude. Two rounding-order rules are load-bearing and are stated here once so they are not mistaken for implementation detail. First, when a total is assembled from per-line figures that each need rounding, each line is rounded to whole cents and only the rounded lines are summed; rounding an unrounded sum once at the end produces a different total and is wrong. This governs both ingredient-order costing and a run's ingredient cost. Second, when a per-unit basis is derived by division and then multiplied by a unit count, the division is rounded to whole cents first and the multiplication is exact; rounding after the multiplication is the wrong order and yields different cents. This governs the relationship between a run's cost basis per unit and the cost of any waste attested against it.

Rack counts, case counts, unit counts and minute counts are integers. Where demand must be converted into a whole number of racks or a whole number of cases, the conversion rounds up to the next whole number. Where a budget must be converted into a number of racks the department can afford, the conversion rounds down to the previous whole number. Those two directions are never interchangeable.

### 2.7. The Bake Day's Two Independent Gates

A `BakeDay` is the operating unit of the whole system, and it carries two enumerated dimensions that move independently of one another. Neither dimension constrains the other's value: a day may be `LOCKED` while markdown is still automatic, and it may still be `PLANNED` while markdown has already been restricted to management.

The first dimension is `plan_posture`, the planning lifecycle. It takes the values `DRAFT`, `PLANNED`, `LOCKED` and `CLOSED`, begins at `DRAFT` when the day is opened, and ends at `CLOSED`, which is terminal. `DRAFT` is the forecast-entry posture. `PLANNED` is reached by generating a plan and may be reached again by regenerating it. `LOCKED` freezes the shape of the plan while leaving execution untouched. `CLOSED` freezes everything.

Two error codes police that dimension, and they are not interchangeable. Any write that targets a `CLOSED` bake day, or any of the runs, pickup slots, cake orders or waste records that hang off it, is rejected with `ERR_BAKE_DAY_CLOSED` (HTTP 409). Separately, the three plan-shaping writes — plan generation, forecast-line appending and manual run creation — require a posture of `DRAFT` or `PLANNED`; attempting any of them against a `LOCKED` day is rejected with `ERR_BAKE_DAY_PLAN_LOCKED` (HTTP 409). Execution writes are deliberately excluded from that restriction: starting a proof, starting a bake, completing a run and marking a run down all remain permitted on a `LOCKED` day. Conversely, execution writes are not permitted on a `DRAFT` day at all — a run whose day has never had a plan generated cannot be proofed or baked, and the attempt is rejected as an invalid run state with `ERR_INVALID_RUN_STATE`, whereas the same attempt on a `CLOSED` day is rejected with `ERR_BAKE_DAY_CLOSED`.

The second dimension is `markdown_authorization`, a shrink-driven gate taking the values `AUTO` and `MANAGER_ONLY`. It defaults to `AUTO`, may be supplied explicitly when the day is opened, and thereafter moves only by system recomputation — there is no endpoint that sets it. While it reads `AUTO`, both a `DepartmentManager` and a `Baker` may mark a run down. When it reads `MANAGER_ONLY`, only a `DepartmentManager` may; a `Baker` attempting a markdown is rejected with `ERR_MARKDOWN_AUTHORIZATION_REQUIRED` (HTTP 403). The system re-evaluates the gate only on a recomputation that actually moves the day's `shrink_cost_basis_pct`: such a recomputation sets the gate to `MANAGER_ONLY` when the new ratio is strictly greater than the owning department's `shrink_budget_pct` and to `AUTO` when it is at or below the budget, while a recomputation that leaves the ratio on the value it already held leaves the gate exactly as it stands. A value supplied when the day was opened therefore survives every rollup that does not disturb the cost-basis ratio — a day opened `MANAGER_ONLY` with no waste yet attested stays `MANAGER_ONLY` across run completion — and is overwritten by the first recomputation that does disturb it. Each of those two moves is a mutation of the bake day and increments its `version` by 1. Equality with the budget is compliant and never restricts markdown.

### 2.8. Allergen Segregation and Shared-Equipment Labeling

Allergen codes are drawn from a fixed set of seven values: `PEANUT`, `TREE_NUT`, `MILK`, `EGG`, `SOY`, `WHEAT` and `SESAME`. Both products and ingredients carry an `allergen_tags` array of these codes; on an ingredient the array is informational and feeds shared-equipment labeling, while on a product it actively decides which ovens may bake it.

An `Oven` declares an `allergen_mode` of either `SHARED` or `NUT_FREE_DEDICATED`. The segregation rule has two symmetric halves, and both are enforced with `ERR_ALLERGEN_SEGREGATION_VIOLATION` (HTTP 422). First, an oven whose `allergen_mode` is `NUT_FREE_DEDICATED` refuses any product whose `allergen_tags` contain `PEANUT` or `TREE_NUT`. Second, an oven whose `allergen_mode` is `SHARED` refuses any product whose `allergen_free_claim` is true — a product merchandised as nut-free may only be produced on dedicated equipment. Both halves are evaluated when a run is created and again when the run is loaded into the deck, so a product whose profile was acceptable at scheduling time cannot slip through if the oven's mode has changed in between. The same nut-free requirement reaches custom cakes from a different direction: a cake order whose `allergen_free_required` flag is true must name a base product whose `allergen_free_claim` is true, and confirming such an order against a base product that makes no nut-free claim is rejected with the same `ERR_ALLERGEN_SEGREGATION_VIOLATION`.

Shared ovens are allowed to mix allergens, but the department owes the shopper a label. Each run therefore carries a computed `shared_equipment_label_tags` array: the ascending-sorted union of the `allergen_tags` of every product referenced by any run on the same oven and the same bake day whose `execution_status` is anything other than `CANCELLED`, including the run's own product. A run with no oven — a thaw-and-serve batch — carries an empty array. Because the union depends on the run's siblings, it is recomputed for every non-cancelled run sharing that oven and that day whenever a run on that pairing is created or cancelled: adding a peanut product relabels its neighbours, and cancelling that same run scrubs the peanut code off the neighbours again.

### 2.9. Segregation of Duties

Beyond role permissions, the system enforces one hard separation between the operator who makes product and the operator who writes off product. When a run is completed, the completing baker's `X-User-ID` is stamped onto the run's `executed_by_user_id`. When waste is attested against that run, the attesting caller's `X-User-ID` is stamped onto the record's `attested_by_user_id`, and the two identifiers must differ. If the caller attesting waste is the very operator whose identifier completed the run, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). This applies to both roles that may attest waste, so a `DepartmentManager` who also completed the run is barred exactly as a `Baker` would be. Neither `executed_by_user_id` nor `attested_by_user_id` nor `voided_by_user_id` is a foreign key; they are opaque operator identifiers compared only to each other.

The other identity rule is scope. Every operation performed by a `DepartmentManager` is confined to the department its `X-User-ID` names, whether the department is reached directly through a `department_id`, one hop away through a `bake_day_id`, or two hops away through a `production_run_id`. Crossing that boundary is rejected with `ERR_DEPARTMENT_SCOPE_VIOLATION`.

### 2.10. Rejection Precedence

Many requests in this system fail more than one check at once, and the benchmark for correctness is which failure surfaces. Checks are evaluated in strictly ascending bands, and the first failing check terminates the request.

1. **Authentication** — headers present and `X-User-Role` recognised (`ERR_UNAUTHENTICATED`).
2. **Role authorisation** — the acting role is listed for the endpoint (`ERR_ROLE_NOT_PERMITTED`).
3. **Department scope** — a `DepartmentManager` owns the target (`ERR_DEPARTMENT_SCOPE_VIOLATION`). Ownership can only be read off a resource that exists, so where the target is named by a path variable that resource is resolved before this check runs and a path identifier matching nothing yields its own 404 from band 4 instead of a scope violation.
4. **Existence**, in this fixed order: `department_id` (`ERR_DEPARTMENT_NOT_FOUND`), then `bake_day_id` (`ERR_BAKE_DAY_NOT_FOUND`), then `product_id` (`ERR_PRODUCT_NOT_FOUND`), then `ingredient_id` (`ERR_INGREDIENT_NOT_FOUND`), then `oven_id` (`ERR_OVEN_NOT_FOUND`), then `production_run_id` or `runId` (`ERR_PRODUCTION_RUN_NOT_FOUND`), then `pickup_slot_id` or `pickupSlotId` (`ERR_PICKUP_SLOT_NOT_FOUND`), then `orderId` (`ERR_CAKE_ORDER_NOT_FOUND`), then `ingredientOrderId` (`ERR_INGREDIENT_ORDER_NOT_FOUND`), then `wasteRecordId` (`ERR_WASTE_RECORD_NOT_FOUND`). Within this band, path variables resolve before body identifiers.
5. **Request shape** — required fields present, enum values inside their declared sets, `tier_count` between 1 and 4 inclusive, `units`, `rack_count`, `forecasted_units`, `required_units` and every capacity a non-negative integer with `rack_count` and each order line's `required_units` at least 1, every ratio between 0 and 1, `slot_end_utc` strictly after `slot_start_utc`, `oven_shift_end_utc` strictly after `oven_shift_start_utc`, and `business_date` a valid calendar date (`ERR_INVALID_REQUEST`). An absent or empty request body is read as an empty JSON object, so a write that requires fields fails here on those missing fields; a body that is not parseable JSON, or that parses to anything other than an object, is rejected with the same `ERR_INVALID_REQUEST`. Two shape failures fall outside any endpoint: a request whose path matches no declared route is answered with `ERR_INVALID_REQUEST` under HTTP 404, and a request whose method is not declared for an otherwise known path with `ERR_INVALID_REQUEST` under HTTP 405.
6. **Optimistic concurrency** — `expected_bake_day_version` on plan generation (`ERR_STALE_BAKE_DAY_VERSION`), then `expected_department_version` on ingredient-order creation (`ERR_STALE_DEPARTMENT_VERSION`).
7. **Own-entity state**, in this order: the day is not `CLOSED` (`ERR_BAKE_DAY_CLOSED`); the day's posture permits a plan-shaping write (`ERR_BAKE_DAY_PLAN_LOCKED`); the run's `execution_status` or `disposition_status` permits the requested transition (`ERR_INVALID_RUN_STATE`); proofing is applicable to the run's product (`ERR_PROOF_NOT_REQUIRED`); proofing has not been skipped (`ERR_PROOF_REQUIRED`); the run being written off is completed (`ERR_RUN_NOT_COMPLETED`); the waste record being voided is still active (`ERR_WASTE_RECORD_ALREADY_VOIDED`); the cake order's `order_status` permits the transition (`ERR_INVALID_CAKE_ORDER_STATE`); the ingredient order's `order_status` permits the transition (`ERR_INVALID_INGREDIENT_ORDER_STATE`).
8. **Cross-entity state** — the referenced oven is available (`ERR_OVEN_UNAVAILABLE`), then the referenced pickup slot is open (`ERR_PICKUP_SLOT_CLOSED`).
9. **Safety and compliance** — allergen segregation (`ERR_ALLERGEN_SEGREGATION_VIOLATION`), then segregation of duties (`ERR_SEGREGATION_OF_DUTIES`), then the product has not already expired (`ERR_PRODUCT_EXPIRED`). This band outranks every temporal, constraint, referential and fiscal check below it and is itself outranked by every state check above it.
10. **Temporal** — the markdown window has opened (`ERR_MARKDOWN_WINDOW_NOT_OPEN`), the decoration lead time has not been missed (`ERR_DECORATION_LEAD_TIME_MISSED`), the run fits inside the day's oven shift (`ERR_OVEN_SHIFT_WINDOW_VIOLATION`), the buffered bake interval does not collide on the deck (`ERR_OVEN_SLOT_CONFLICT`), the new pickup window does not overlap an existing one (`ERR_PICKUP_SLOT_OVERLAP`).
11. **Constraint satisfaction** — `deck_index` inside the oven's deck range (`ERR_DECK_INDEX_OUT_OF_RANGE`), no duplicate forecast line (`ERR_DUPLICATE_FORECAST_LINE`), no duplicate `sku`, oven `name` or `business_date` inside the department (`ERR_DUPLICATE_SKU`), the revision ceiling not yet reached (`ERR_REVISION_LIMIT_REACHED`), decorator capacity not exceeded (`ERR_PICKUP_SLOT_CAPACITY_EXCEEDED`), attested waste within the run's remaining shelf units (`ERR_WASTE_EXCEEDS_ON_SHELF`), plan generation actually produced something (`ERR_EMPTY_PRODUCTION_PLAN`).
12. **Referential** — every referenced product, ingredient, oven and pickup slot belongs to the same department or the same bake day as the target (`ERR_INGREDIENT_NOT_IN_DEPARTMENT`), the base product of a cake order is flagged as a custom cake base (`ERR_NOT_CUSTOM_CAKE_BASE`), and oven assignment matches the product's production method (`ERR_OVEN_METHOD_MISMATCH`).
13. **Fiscal and capacity**, evaluated last — markdown authorisation (`ERR_MARKDOWN_AUTHORIZATION_REQUIRED`), rack capacity per deck (`ERR_OVEN_RACK_CAPACITY_EXCEEDED`), the day's labor budget (`ERR_LABOR_BUDGET_EXCEEDED`), and the per-line shelf-life order cap (`ERR_SHELF_LIFE_OVERSTOCK`).

A worked consequence: creating a run that names an unavailable oven, breaks allergen segregation, overruns the deck's rack capacity and busts the labor budget all at once reports `ERR_OVEN_UNAVAILABLE`, because cross-entity state outranks safety, and safety outranks both capacity checks. Whichever check fires, the rejection is atomic: every row the request had already created or modified before the failure is rolled back, so a rejected write never leaves a partial cascade behind.

### 2.11. The Logical Clock

Nothing in this system reads wall-clock time for business evaluation. The server holds a logical clock whose startup value is exactly `2026-08-01T00:00:00Z`, and until an operator moves it the clock reads that instant and never falls back to real time. A `RegionalAdmin` moves it by supplying a `to_iso8601` instant to the clock-setting capability; that field is required, and the instant may sit earlier than the current reading because the clock is free to move backwards. The call answers `200 OK` with a data object whose single property `current_utc` echoes the new reading. It mutates no entity, but every subsequent time-dependent evaluation — the markdown window, product expiry, the decoration deadline, and each `_utc` stamp the system writes — reads the new instant.

Every timestamp in this system is an instant in UTC except `business_date`, which is a calendar date in exactly `YYYY-MM-DD` form and is never a timestamp. An instant the API accepts may carry any UTC offset and is normalised to UTC before it is stored or compared; a value with no offset at all is read as already being UTC. Every instant the API emits is rendered with exactly three fractional digits and a `Z` suffix, any finer precision being truncated rather than rounded. Comparisons against the clock are stated explicitly wherever they occur, because inclusivity differs: the markdown window includes its opening instant and excludes the expiry instant, the decoration deadline includes the deadline instant itself, and the oven shift window includes both endpoints.

## 3. Business Logic & Workflows

### 3.1. Provisioning a Department and Its Reference Data

Everything begins with a `RegionalAdmin` registering a bakery department. Registration takes a display `name` of 1 to 120 non-blank characters and a `store_number` of 1 to 10 characters that must be unique across all departments; a repeat is rejected with `ERR_DUPLICATE_SKU`. Three economic parameters are fixed at registration. `shrink_budget_pct` is the fraction of production cost the department is allowed to waste; it must be greater than 0 and no greater than 0.5000, and it is stored with four decimal places. `labor_rate_cents_per_minute` values the department's labor minutes and must be greater than zero. `freight_surcharge_pct` is the per-line surcharge applied inside ingredient-order costing; it is optional, defaults to 0.05, must be at least 0 and no more than 0.5000, and is likewise held to four decimal places. A fourth, operational parameter is `donation_partner_enabled`, an optional boolean defaulting to true: when it is true the unsold units swept up at the end of the day are booked as a donation, and when it is false they are booked as ordinary day-old shrink. A newly registered department reports `open_purchase_commitment_cents` of 0; that figure is derived, never supplied, and §3.8 explains what moves it. Departments are readable one at a time or as a list filtered by `store_number`.

Products come next, and a product's `production_method` is the single most consequential field in the catalogue because it decides what equipment and which stages the product needs. A `SCRATCH` product is mixed, proofed and baked in store: it consumes an oven, it must pass through a proof stage, and its labor is charged at full weight. A `PAR_BAKED` product is finished from frozen par-baked stock: it consumes an oven, it must never be proofed, and its labor is charged at sixty percent of full weight. A `THAW_AND_SERVE` product is thawed on a rack in the back room: it consumes no oven, has no bake stage at all, and its labor is charged at a quarter of full weight. Those three weights — full for `SCRATCH`, six-tenths for `PAR_BAKED` and one quarter for `THAW_AND_SERVE` — are the method labor factors that reappear in every labor computation in this document.

The rest of a product's definition follows from that choice. `sku` is a 1-to-20-character code that must be unique inside the department, and `name` is its shelf label. `units_per_rack` is how many sellable units one rack yields and lies between 1 and 500. `proof_minutes` must be greater than 0 for a `SCRATCH` product and exactly 0 for `PAR_BAKED` and `THAW_AND_SERVE`; `bake_minutes` must be greater than 0 for `SCRATCH` and `PAR_BAKED` and exactly 0 for `THAW_AND_SERVE`; `cool_minutes` is the cooling time added after the bake finishes. All three are optional, default to 0, and may not exceed 600. `base_labor_minutes_per_rack` is the per-rack labor charge before the method factor, `setup_labor_minutes` is the fixed labor charge levied once per batch of the product, both default to 0 and both carry two decimal places. `unit_retail_cents` is the full shelf price of one unit and must be at least 1. `shelf_life_hours` is how long the product remains sellable after it is ready and lies between 1 and 720. `markdown_pct` is the fraction taken off the shelf price when a batch is discounted; it defaults to 0.5, must be strictly greater than 0 and strictly less than 1, and carries four decimal places. `allergen_tags` is optional, defaults to an empty array and is stored exactly as supplied — entry order is preserved and repeated codes are not collapsed — while `allergen_free_claim` is an optional boolean defaulting to false; together they carry the segregation profile described in §2.8. `is_custom_cake_base` defaults to false, and only a product carrying it as true may be used as the base of a custom cake order.

A product also declares its `recipe_lines`, an array whose entries each pair an `ingredient_id` with the `units_per_rack` of that ingredient consumed per rack of product. Each entry's `units_per_rack` is required and must be a non-negative integer. The array defaults to empty, may name each ingredient at most once — a second entry for the same `ingredient_id` is rejected with `ERR_INVALID_REQUEST` — and every named ingredient must belong to the same department as the product; an ingredient that exists but sits in a different department is rejected with `ERR_INGREDIENT_NOT_IN_DEPARTMENT`, while an `ingredient_id` matching nothing at all is rejected earlier with `ERR_INGREDIENT_NOT_FOUND`. Recipe order is not cosmetic: ingredient cost and ingredient consumption are both walked in `recipe_lines` array order. A `sku` that duplicates one already in the department is rejected with `ERR_DUPLICATE_SKU`. Products can be listed with filters on `department_id`, `production_method` and `is_custom_cake_base`.

Ingredients are provisioned with a `name` unique inside the department — a duplicate is rejected with `ERR_DUPLICATE_SKU` — a `case_pack_units` between 1 and 1000 that is the indivisible purchase quantity, a `unit_cost_cents` greater than zero carrying up to two decimal places, a `shelf_life_days` between 1 and 3650, a `daily_usage_units` of at least 1 describing planned daily consumption, a `reorder_point_units` of at least 0, and an optional `on_hand_units` defaulting to 0 that may not be negative. `allergen_tags` on an ingredient is optional, defaults to an empty array, and is informational. The derived `replenishment_state` takes one of three values — `OK` when the on-hand quantity sits at or above the reorder point, `REORDER_DUE` when it sits strictly below the reorder point with no submitted order covering it, and `ON_ORDER` when a submitted ingredient order carries a line for the ingredient. At creation it is derived from the supplied `on_hand_units` against `reorder_point_units` and therefore reads `OK` or `REORDER_DUE`. Ingredients are listed with filters on `department_id` and `replenishment_state`.

Ovens are the scarce resource. An oven declares a `name` of 1 to 60 characters that must be unique inside the department — uniqueness matters because oven `name` in ascending order is the primary tie-break when the planner ranks candidate ovens, and a duplicate is rejected with `ERR_DUPLICATE_SKU`. `deck_count` is between 1 and 8 and fixes the legal range of `deck_index` as zero through one less than the deck count; `rack_capacity_per_deck` is between 1 and 20 and caps how many racks a single deck can hold for one batch. `changeover_buffer_minutes` is optional, defaults to 0, may not exceed 120, and is the number of minutes a deck stays occupied after the bake finishes for unloading and changeover — it lengthens every occupation interval on that oven. `allergen_mode` is optional and defaults to `SHARED`. Neither `oven_status` nor `status_reason` is a creation input: a newly created oven always reads `AVAILABLE` with a null reason. Ovens are listed with filters on `department_id`, `oven_status` and `allergen_mode`.

An oven's availability is its own small cycle. `oven_status` starts at `AVAILABLE`, and a `DepartmentManager` moves it by submitting the desired `oven_status` together with an optional `status_reason`, which may not exceed 500 characters and simply records the note attached to the most recent change — because it records only that most recent change, omitting it on a transition clears whatever note the previous transition left. The submitted status must differ from the one the oven already carries; asking for the status it already reads is rejected with `ERR_INVALID_RUN_STATE`. Moving `AVAILABLE → MAINTENANCE` is refused with `ERR_INVALID_RUN_STATE` while any production run referencing that oven is in `PROOFING` or `BAKING` — an oven cannot be pulled out from under a loaded deck. Once the oven reads `MAINTENANCE`, every run write that names it is rejected with `ERR_OVEN_UNAVAILABLE`; runs already sitting in `SCHEDULED` are deliberately left in place rather than cancelled, and they are blocked later, when someone tries to load them. Moving `MAINTENANCE → AVAILABLE` has no preconditions at all: the note is stored and the oven re-enters the planner's candidate pool. Either move increments the oven's `version` by 1.

### 3.2. Opening a Bake Day and Building the Forecast

A `DepartmentManager` opens an operating day by naming the owning `department_id` and the `business_date` in `YYYY-MM-DD` form, together with `labor_budget_minutes` — the total bakery labor minutes available that day, which may be zero but never negative — and the pair `oven_shift_start_utc` and `oven_shift_end_utc` that bound the shift. The end instant must be strictly after the start instant. `oven_shift_start_utc` is the earliest instant any batch on the day may begin proofing or baking, and `oven_shift_end_utc` is the latest instant a batch's ready moment may fall on. Only one bake day may exist per department and calendar date; a repeat is rejected with `ERR_DUPLICATE_SKU`. An initial `markdown_authorization` may be supplied; when omitted it is `AUTO`.

From `business_date` the system derives `day_of_week` under the proleptic Gregorian calendar, as one of `MON`, `TUE`, `WED`, `THU`, `FRI`, `SAT` or `SUN`. That single derived value carries real commercial weight, because the planner treats the forecast as a Monday-normal baseline and lifts it for the busy end of the week. Monday, Tuesday and Wednesday get no lift at all — the forecast is taken as entered. Thursday is lifted by five percent, Sunday by ten percent, Friday by fifteen percent, and Saturday, the department's biggest day, by twenty-five percent. Those multipliers are applied per forecast line and never to a total.

A day opens with an empty forecast and a `plan_posture` of `DRAFT`, and with every derived figure at zero: `planned_labor_minutes` and `actual_labor_minutes` at 0.00, `shrink_cost_basis_pct` and `shrink_unit_basis_pct` at 0.0000, and `planned_units_total`, `produced_units_total`, `production_cost_cents`, `waste_units_total`, `shrink_cost_cents` and `plan_unmet_unit_count` all at 0. The manager then appends forecast lines one at a time, each naming a `product_id`, a `daypart` and a count of `forecasted_units`. `daypart` is one of `MORNING`, `MIDDAY` or `EVENING`. The append is an ordinary mutation of the day and answers with the whole bake day, whose `forecast_lines` array grows by one object of the shape product, daypart and forecast count. A `product_id` naming nothing is rejected with `ERR_PRODUCT_NOT_FOUND`; one naming a product owned by a different department is rejected with `ERR_INGREDIENT_NOT_IN_DEPARTMENT`. Only one line may exist per product-and-daypart pair on a given day: a second attempt at the same pair is rejected with `ERR_DUPLICATE_FORECAST_LINE`. Because forecast entry is a plan-shaping write, it is only accepted while the day's `plan_posture` is `DRAFT` or `PLANNED`; a `LOCKED` day rejects it with `ERR_BAKE_DAY_PLAN_LOCKED` and a `CLOSED` day with `ERR_BAKE_DAY_CLOSED`.

Alongside the forecast, a bake day is the reporting surface for the entire day. Nine of its fields are pure rollups over its runs and waste records, and every one of them is recomputed whenever a run is created, cancelled or completed, whenever a waste record is created or voided, and again at close. `planned_labor_minutes` and `planned_units_total` sum the planned labor and the planned unit yield of every run on the day whose `execution_status` is anything other than `CANCELLED` — that is, of runs sitting in `SCHEDULED`, `PROOFING`, `BAKING` or `COMPLETED`. `actual_labor_minutes`, `produced_units_total` and `production_cost_cents` sum the settled labor, the actual unit yield and the ingredient cost of the runs that reached `COMPLETED` only. `waste_units_total` and `shrink_cost_cents` sum the units and the cost of the day's waste records whose `record_status` is `ACTIVE`. Cancelled runs contribute to nothing, and voided waste records contribute to nothing, so a void must pull both waste totals back down. The two remaining derived figures, `shrink_cost_basis_pct` and `shrink_unit_basis_pct`, are the subject of §3.6, and `plan_unmet_unit_count` is the subject of §3.3. Labor rollups carry two decimal places; unit and cent rollups are integers. Each recomputation writes only those rollups whose value actually moved, and refreshes the day's `updated_at` and `version` only when at least one of them did: a recomputation that lands on the figures already stored leaves the bake day's `version` exactly where it was. Bake days are readable individually and listable with filters on `department_id`, `plan_posture` and `business_date`.

### 3.3. Generating the Production Plan

Plan generation is the centrepiece of the system. A `DepartmentManager` triggers it against a bake day, supplying `expected_bake_day_version` as described in §2.5, and the day moves `DRAFT → PLANNED` on the first pass. The same trigger may be used again on an already-`PLANNED` day, which is a `PLANNED → PLANNED` self-loop rather than a new state: the day regenerates its plan in place. Generation is refused on a `LOCKED` day with `ERR_BAKE_DAY_PLAN_LOCKED` and on a `CLOSED` day with `ERR_BAKE_DAY_CLOSED`. Whether the pass is the first or the fortieth, it ends by incrementing the bake day's `version` by 1.

Every run the pass creates is stamped with an `origin` of `PLAN_GENERATED`; runs a human scheduled by hand carry `origin` of `MANUAL`. The distinction exists solely so that regeneration knows what it owns. A regeneration begins with a **supersede pass**: every run on the day whose `origin` is `PLAN_GENERATED` and whose `execution_status` is still `SCHEDULED` is moved to `CANCELLED` with `cancelled_reason` set to `PLAN_SUPERSEDED`, processed in `created_at` ascending order, each cancellation incrementing that run's `version` by 1. Anything a baker has already started, and anything a human created by hand, survives untouched. Each cancellation has two knock-on effects: the run drops out of the day's `planned_labor_minutes` and `planned_units_total`, and — because the surviving population on that oven and day has changed — `shared_equipment_label_tags` is recomputed for every remaining non-cancelled run sharing the cancelled run's oven and bake day. Manual runs are preserved with their labor intact, and that labor still consumes the labor budget the new pass has to work within. The first pass out of `DRAFT` has nothing to supersede and simply skips this step.

The pass then establishes its two accumulators. Committed labor starts as the sum of `planned_labor_minutes` across every run of the day whose `execution_status` is `SCHEDULED`, `PROOFING`, `BAKING` or `COMPLETED`; after the supersede pass that is exactly the labor of the surviving manual and in-flight runs. The unmet-demand accumulator starts at zero, and `plan_unmet_unit_count` is reset to 0 at the very start of every pass so that a regeneration never inherits the previous pass's shortfall.

**The ordered walk.** Forecast lines are processed in a fixed sequence: by daypart rank ascending, where `MORNING` ranks first, `MIDDAY` second and `EVENING` third, and within a daypart by the product's `sku` in ascending order. For each line in that sequence:

1. The line's `forecasted_units` is multiplied by the day-of-week uplift from §3.2 and rounded up to the next whole unit. Call the result the line's effective demand. If the effective demand is zero, the line is skipped entirely and contributes nothing to unmet demand.
2. Required racks is the effective demand divided by the product's `units_per_rack`, rounded up to the next whole rack.
3. Per-rack labor is the product's `base_labor_minutes_per_rack` multiplied by the method labor factor for its `production_method`. Remaining labor is the day's `labor_budget_minutes` less committed labor. If per-rack labor is zero, affordable racks is simply the required racks — a product that costs nothing per rack is never labor-constrained. Otherwise, affordable racks is the greater of zero and the remaining labor less the product's `setup_labor_minutes`, divided by the per-rack labor and rounded down to the previous whole rack.
4. For a `THAW_AND_SERVE` product, the equipment cap is the required racks — no oven is consumed — and the batch is created with no oven, no deck, no proof start and no bake start.
5. For a `SCRATCH` or `PAR_BAKED` product, the planner searches for the earliest feasible oven-deck slot, as specified below. If no slot exists, the line's whole effective demand is added to unmet demand and the line is abandoned. Otherwise the equipment cap is the chosen oven's `rack_capacity_per_deck`.
6. Granted racks is the smallest of the required racks, the affordable racks and the equipment cap. If that number is zero or less, the line's whole effective demand is added to unmet demand and the line is abandoned.
7. A run is created with `origin` `PLAN_GENERATED`, an `execution_status` of `SCHEDULED`, a `disposition_status` of `PENDING`, a `rack_count` equal to the granted racks, and the oven, deck, proof-start and bake-start values the chosen slot supplies. The new run's own planned labor is added to committed labor.
8. Finally, the shortfall this line still carries is added to unmet demand: the greater of zero and the effective demand less the granted racks multiplied by `units_per_rack`. Rack granularity routinely overshoots a line, and that surplus is emphatically not negative unmet demand — it must never be allowed to offset another line's shortfall.

When the walk finishes, the accumulated unmet demand is written to `plan_unmet_unit_count`. If the walk created no run at all — because the day has no forecast lines, because every line's effective demand rounded to zero, or because nothing anywhere proved grantable — the whole request is rejected with `ERR_EMPTY_PRODUCTION_PLAN` (HTTP 422) and the day's posture does not change. The supersede pass is rolled back along with the rest of the request, so a regeneration that ends up granting nothing leaves the previous plan-generated runs sitting in `SCHEDULED` exactly as they stood, at the `version` they already carried. Each run the pass does create computes its own `planned_units`, `planned_labor_minutes`, `ingredient_cost_cents`, `bake_end_utc`, `ready_utc` and `expires_utc` exactly as a manually scheduled run would, and each created run that has an oven forces `shared_equipment_label_tags` to be recomputed for every non-cancelled run on that same oven and bake day. When the pass is finished the day's `planned_labor_minutes`, `planned_units_total` and `plan_unmet_unit_count` are all recomputed.

**Finding the earliest feasible slot.** The candidate pool is the set of ovens belonging to the bake day's department whose `oven_status` is `AVAILABLE`, filtered by both halves of the allergen rule from §2.8: an oven is excluded if the product's `allergen_free_claim` is true and the oven's `allergen_mode` is not `NUT_FREE_DEDICATED`, and an oven is excluded if its `allergen_mode` is not `SHARED` and the product's `allergen_tags` contain `PEANUT` or `TREE_NUT`.

The daypart sets the target bake instant. Starting from the day's `oven_shift_start_utc`, a `MORNING` line targets that instant exactly, a `MIDDAY` line targets five hours later, and an `EVENING` line targets ten hours later. The planner then considers every pairing of a candidate oven with each of its decks, from deck zero up to one less than its `deck_count`, and for each pairing finds the smallest instant at or after the target that sits on a five-minute grid measured from the target instant and satisfies three conditions at once: the instant less the product's `proof_minutes` is at or after `oven_shift_start_utc`; the interval running from that instant for the product's `bake_minutes` plus the oven's `changeover_buffer_minutes` collides with no non-cancelled run already occupying that same oven and deck — including the runs this very pass has already created for earlier forecast lines, which occupy their decks against every line the walk considers after them — judged by the collision test in §3.4; and the instant plus the product's `bake_minutes` plus its `cool_minutes` is at or before the day's `oven_shift_end_utc`.

Among all the pairings that yield an instant, the planner takes the pairing with the earliest instant. Ties are broken first by the oven's `name` in ascending order and then by `deck_index` in ascending order. If no pairing yields any instant, there is no slot. The chosen instant becomes the run's `bake_start_utc`; its `proof_start_utc` is that instant less the product's `proof_minutes` when `proof_minutes` is greater than zero, and null when `proof_minutes` is zero.

### 3.4. Scheduling a Batch by Hand

Not every batch comes out of the planner. Either a `DepartmentManager` or a `Baker` may schedule a single production run directly, naming the `bake_day_id` it belongs to, the `product_id` being made and the `rack_count` committed to the batch, plus — depending on the product's method — an `oven_id`, a `deck_index`, a `proof_start_utc` and a `bake_start_utc`. A run created this way is stamped `MANUAL`, answers with 201, and is refused with `ERR_BAKE_DAY_PLAN_LOCKED` once the day is `LOCKED` and with `ERR_BAKE_DAY_CLOSED` once it is `CLOSED`. Both the product and the oven must belong to the same department as the bake day; one that belongs elsewhere is rejected with `ERR_INGREDIENT_NOT_IN_DEPARTMENT`.

Which of the optional fields are required is decided entirely by the product's `production_method`, and the two equipment rules are symmetric. An `oven_id` is mandatory for a `SCRATCH` or `PAR_BAKED` run and must be omitted for a `THAW_AND_SERVE` run; getting either direction wrong is rejected with `ERR_OVEN_METHOD_MISMATCH`. That mismatch is a referential failure rather than a shape one, so it is diagnosed in the referential band of §2.10 and the method-conditional field rules that follow are suspended for the offending request: once the `oven_id`/method pairing is itself wrong, `deck_index`, `proof_start_utc` and `bake_start_utc` may each be present or absent freely and the answer is still `ERR_OVEN_METHOD_MISMATCH` rather than `ERR_INVALID_REQUEST` — unless a higher band fires first, an unavailable oven, an allergen violation, a `deck_index` outside the named oven's range or a cross-department reference all outranking it. The two temporal constraints below are likewise not applied at all to a request whose method pairing is wrong. `deck_index` is null exactly when `oven_id` is null, and when an oven is named the deck must lie between zero and one less than that oven's `deck_count`, inclusive — anything negative or at or beyond the deck count is rejected with `ERR_DECK_INDEX_OUT_OF_RANGE`. `proof_start_utc` is required for a `SCRATCH` run and must be null for `PAR_BAKED` and `THAW_AND_SERVE`. `bake_start_utc` is required for `SCRATCH` and `PAR_BAKED` and must be null for `THAW_AND_SERVE`. Where a request whose oven and method do agree breaks one of those three field rules — a `deck_index` omitted while an oven is named or supplied while none is, a `proof_start_utc` omitted for a `SCRATCH` product or supplied for a `PAR_BAKED` or `THAW_AND_SERVE` one, a `bake_start_utc` omitted for `SCRATCH` or `PAR_BAKED` or supplied for `THAW_AND_SERVE` — the failure is a request-shape failure and is rejected with `ERR_INVALID_REQUEST`. `rack_count` is at least 1, and when an oven is named it may not exceed that oven's `rack_capacity_per_deck`; exceeding it is rejected with `ERR_OVEN_RACK_CAPACITY_EXCEEDED`, while a rack count exactly equal to the capacity passes. The oven must be `AVAILABLE`, or the request fails with `ERR_OVEN_UNAVAILABLE`, and the allergen pairing from §2.8 is enforced here as well.

Two temporal constraints bound the batch inside the day. Proofing may not begin before the day opens and the batch must be out of the oven and cooled before the day's shift ends: `proof_start_utc` must be at or after `oven_shift_start_utc`, and `bake_start_utc` plus the product's `bake_minutes` plus its `cool_minutes` must be at or before `oven_shift_end_utc`. A violation of either is reported as `ERR_OVEN_SHIFT_WINDOW_VIOLATION`.

**Deck occupation.** A deck can only hold one batch at a time, and the changeover buffer widens the footprint of every batch on that oven. The batch's own bake interval runs from its `bake_start_utc` for the product's `bake_minutes`. It is compared against every other run sitting on the same `oven_id` and the same `deck_index` whose `execution_status` is anything other than `CANCELLED` — whatever bake day that other run belongs to, because a deck is physically occupied without regard to the operating day and the two footprints are compared as absolute instants; that other run's interval runs from its own `bake_start_utc` for its own product's `bake_minutes`. Taking the oven's `changeover_buffer_minutes` as the buffer, the two batches collide when the new batch starts strictly before the other batch's end plus the buffer **and** the other batch starts strictly before the new batch's end plus the buffer. A collision is rejected with `ERR_OVEN_SLOT_CONFLICT`. With a buffer of zero the intervals behave as half-open windows, so a batch starting at the exact instant the previous one ends is not a collision; with a buffer greater than zero that same adjacency *is* a collision, and the gap between the two batches must be at least the buffer in minutes. Different decks of the same oven never collide with one another, and neither do batches on different ovens.

**Planned labor, and the labor budget.** Every run fixes its `planned_labor_minutes` at creation and never revises it. The figure is the product's `setup_labor_minutes` plus the `rack_count` multiplied by the product's `base_labor_minutes_per_rack` multiplied by the method labor factor for the product's `production_method`, with the result rounded half up to two decimal places. This planned figure — not any later actual — is what the labor budget is measured against: the day's current `planned_labor_minutes` plus this run's planned labor must be no greater than the day's `labor_budget_minutes`, and exceeding it is rejected with `ERR_LABOR_BUDGET_EXCEEDED`. Landing exactly on the budget passes. Because the planned variant is deliberately blind to deck history, it never includes any changeover allowance.

**Ingredient cost.** A run also fixes `ingredient_cost_cents` at creation, from its product's recipe. Walking `recipe_lines` in array order, each line contributes the `rack_count` multiplied by that line's `units_per_rack` multiplied by the named ingredient's `unit_cost_cents`, rounded half up to whole cents, and `ingredient_cost_cents` is the sum of those already-rounded line contributions. A product with an empty recipe yields a cost of 0. Ingredient costs are read as they stand at creation time and are not revisited if a price later changes.

The remaining derived timestamps follow mechanically. `bake_end_utc` is `bake_start_utc` plus the product's `bake_minutes`, and is null for a `THAW_AND_SERVE` run that never enters an oven. `ready_utc` is `bake_end_utc` plus the product's `cool_minutes` for a `SCRATCH` or `PAR_BAKED` run, and for a `THAW_AND_SERVE` run it is simply the logical clock instant at which the run was created. `expires_utc` is `ready_utc` plus the product's `shelf_life_hours` and is the run's sell-by moment. `planned_units` is the `rack_count` multiplied by the product's `units_per_rack`; if a client supplies a value for it, that value is ignored. Until the run is completed every execution figure on it is null — `actual_units`, `actual_labor_minutes`, `final_labor_minutes`, `unit_cost_basis_cents`, `on_shelf_units`, `markdown_unit_price_cents` and `executed_by_user_id` — while `wasted_units_total` already reads 0 and `shared_equipment_label_tags` is an array rather than null. Creating the run recomputes the owning day's `planned_labor_minutes` and `planned_units_total`, and — when an oven is involved — the `shared_equipment_label_tags` of every non-cancelled run on that oven and day. Runs are readable one at a time, and listable with filters on `bake_day_id`, `product_id`, `oven_id`, `execution_status` and `disposition_status`; that list is the only channel through which plan-generated runs can be discovered.

### 3.5. Executing the Bake

A run carries two status dimensions that move independently on the same row. `execution_status` tracks the physical work and runs `SCHEDULED` at creation, then `PROOFING`, `BAKING`, and finally either `COMPLETED` or `CANCELLED`, both terminal. `disposition_status` tracks merchandising and is the subject of §3.6. Cancellation is never a caller-driven action: the only two ways a run reaches `CANCELLED` are the supersede pass of a regeneration, which sets `cancelled_reason` to `PLAN_SUPERSEDED` and only ever touches runs whose `origin` is `PLAN_GENERATED`, and the end-of-day sweep, which sets `cancelled_reason` to `DAY_CLOSED` regardless of origin. `cancelled_reason` is null on any run that is not cancelled. Either cancellation drops the run out of the day's `planned_labor_minutes` and `planned_units_total`, forces the sibling label recomputation on its oven and day, and increments the run's `version` by 1.

A `Baker` drives the forward path, and the product's method decides the shape of it. Starting the proof moves a run `SCHEDULED → PROOFING` and is only accepted for a `SCRATCH` product with a positive `proof_minutes`; asking for it on a `PAR_BAKED` or `THAW_AND_SERVE` product, or on any product whose `proof_minutes` is zero, is rejected with `ERR_PROOF_NOT_REQUIRED`. Loading the deck moves a run to `BAKING`, and it accepts two different origin states depending on the same product field: a `SCRATCH` run arrives from `PROOFING`, while a `PAR_BAKED` run goes straight from `SCHEDULED`. Attempting to load a `SCRATCH` run that is still in `SCHEDULED` is rejected with `ERR_PROOF_REQUIRED`, because the proof stage may not be skipped; attempting to load a `THAW_AND_SERVE` run, which has no oven and no bake stage, is rejected with `ERR_OVEN_METHOD_MISMATCH`. Both the proof and the bake require the owning day's `plan_posture` to be `PLANNED` or `LOCKED` and both require the oven to still be `AVAILABLE`, failing with `ERR_OVEN_UNAVAILABLE` if maintenance has intervened since the run was scheduled — this is the moment at which a run left standing by an oven going out of service is finally stopped. Loading the deck also re-evaluates allergen segregation and refreshes the `shared_equipment_label_tags` of the oven-day, and each of these transitions increments the run's `version` by 1.

Completion is where a plan becomes inventory and where the largest cascade in the system fires. A `Baker` completes a run by supplying `actual_units`, the count of sellable units the batch really yielded, which must be present and may not be negative, and optionally `actual_labor_minutes`, the raw labor really spent, which must be non-negative and carries two decimal places. A `BAKING` run completes normally; a `THAW_AND_SERVE` run completes directly from `SCHEDULED`, having never entered an oven, and a `SCRATCH` or `PAR_BAKED` run still sitting in `SCHEDULED` is rejected with `ERR_INVALID_RUN_STATE`. Completion requires the day to be `PLANNED` or `LOCKED`. The side-effect chain is identical on both entry paths.

On the run itself, completion stores `actual_units`, stamps `executed_by_user_id` from the caller's `X-User-ID`, settles `final_labor_minutes`, computes `unit_cost_basis_cents`, sets `wasted_units_total` to 0 and sets `on_shelf_units` to `actual_units`. `unit_cost_basis_cents` is the run's `ingredient_cost_cents` divided by its `actual_units`, rounded half up to whole cents — or 0 when `actual_units` is zero. That rounding happens exactly once, here, per unit; any later waste multiplies this already-rounded per-unit figure rather than re-dividing, and doing the rounding after the multiplication instead produces a different number of cents.

`final_labor_minutes` is the settled counterpart of the planned figure, and unlike the planned figure it looks at the deck's history. The raw figure is the `actual_labor_minutes` the baker supplied, or, when that field was left out entirely, the run's own `planned_labor_minutes`. The system then looks for the run's predecessor on the deck: among the runs sharing this run's `oven_id` and `deck_index` whose `execution_status` is `COMPLETED` and whose `bake_end_utc` is at or before this run's `bake_start_utc`, the predecessor is the first row when they are ordered by `bake_end_utc` descending and then by `created_at` descending. There is no predecessor when the run has no oven, or when no such completed run exists. When a predecessor exists and the set of `allergen_tags` on its product differs from the set on this run's product, an allergen changeover has occurred and a changeover allowance of the oven's `changeover_buffer_minutes` multiplied by one half, rounded half up to two decimal places, is granted; otherwise the allowance is 0.00. `final_labor_minutes` is then the raw figure plus that allowance, rounded half up to two decimal places. This is why two runs with identical inputs can settle to different labor: the planned variant ignores deck history entirely, while the settled variant charges for the scrub-down between two different allergen profiles.

Completion then cascades outward in four hops, and every hop matters. First, the owning bake day absorbs the run: its `produced_units_total`, `actual_labor_minutes` and `production_cost_cents` all take this run in. Second, the product's recipe is consumed — walking `recipe_lines` in array order, each named ingredient's `on_hand_units` is reduced by the run's `rack_count` multiplied by that line's `units_per_rack`. Consumption is driven by the racks committed rather than by the yield, so a batch completed with `actual_units` of 0 consumes exactly as much as a full-yield batch of the same `rack_count`, and the subtraction is not floored at zero: an ingredient consumed beyond its recorded stock is left holding a negative `on_hand_units`. Every ingredient the walk names increments its own `version` by 1, including a line whose `units_per_rack` is 0 and which therefore moves no stock at all. Third, because on-hand levels have fallen, each consumed ingredient is examined against its `reorder_point_units`. One left strictly above the point is passed over entirely and neither its state nor anything else about it is written. One left at or below the point is a reorder candidate, and where the department has no ingredient order in `DRAFT` or `SUBMITTED` already carrying that ingredient, it earns a top-up line on a freshly minted automatic reorder draft as specified in §3.8; a candidate already covered by such an order is skipped and left untouched. The two thresholds are deliberately one step apart: candidacy is at-or-below the reorder point while the `replenishment_state` boundary of §3.1 is strictly below it, so an ingredient landing exactly on its reorder point earns a top-up line while its state still reads `OK`. That state is re-derived only for a candidate currently reading `OK`, which becomes `REORDER_DUE` when it now sits strictly below the point; a candidate already reading `REORDER_DUE` or `ON_ORDER` keeps the state it had. Fourth, because that draft now exists, the department's `open_purchase_commitment_cents` rises by the draft's `order_total_cents` and the department's `version` increments by 1. At most one automatic draft is minted per completion, carrying one top-up line per candidate ingredient in `recipe_lines` order; when the run consumes nothing, when no consumed ingredient is a candidate, or when every candidate is already covered by an open order, no draft is minted at all and the department is left entirely untouched at the `version` it already held. When a draft is minted the department's `version` increments even if the draft's lines total zero cents and the commitment figure therefore does not move. The run's own `version` increments by 1 as well.

### 3.6. Shelf Life, Markdown, Waste and Shrink

The merchandising dimension of a run, `disposition_status`, has no terminal state at all, because product can come back. It starts at `PENDING` and stays there for the whole of the run's execution. Completion moves it: a batch that yielded at least one unit goes `PENDING → ON_SHELF` with `on_shelf_units` set to `actual_units`, while a zero-yield batch goes straight `PENDING → CLEARED` with `on_shelf_units` set to 0 and `unit_cost_basis_cents` set to 0. From `ON_SHELF` the batch may be discounted into `MARKED_DOWN`, and from either `ON_SHELF` or `MARKED_DOWN` it falls to `CLEARED` the moment its shelf stock is exhausted. `on_shelf_units` is always the run's `actual_units` less its `wasted_units_total`, and it is never negative; `wasted_units_total` is the sum of the `units` on every waste record against the run whose `record_status` is `ACTIVE`.

**The markdown window.** A run may be discounted only inside the four hours immediately preceding its sell-by instant. The window opens at the run's `expires_utc` less four hours and it closes at `expires_utc` itself, and the two edges are treated differently on purpose: the opening instant is inside the window, and the expiry instant is outside it. A markdown attempted before the window opens is rejected with `ERR_MARKDOWN_WINDOW_NOT_OPEN`, and one attempted at or after `expires_utc` is rejected with `ERR_PRODUCT_EXPIRED`. Beyond the clock, the run must have an `execution_status` of `COMPLETED` and at least one unit still on the shelf; a markdown against a `PENDING`, an already-`CLEARED` or an already-`MARKED_DOWN` run is rejected with `ERR_INVALID_RUN_STATE` — a batch is discounted once and its price is never restruck. Because that disposition check sits in the own-entity state band it outranks the clock, so a `MARKED_DOWN` run whose sell-by has already passed still answers `ERR_INVALID_RUN_STATE` rather than `ERR_PRODUCT_EXPIRED`. Both a `DepartmentManager` and a `Baker` may discount a batch, but a `Baker` may only do so while the day's `markdown_authorization` reads `AUTO`, as §2.7 sets out. A successful markdown sets `markdown_unit_price_cents` to the product's `unit_retail_cents` multiplied by one less the product's `markdown_pct`, rounded half up to whole cents, moves the disposition `ON_SHELF → MARKED_DOWN`, and increments the run's `version` by 1.

**Attesting waste.** Waste is recorded against a completed run by either a `Baker` or a `DepartmentManager`, naming the `production_run_id`, a `disposition_reason` and a count of `units`. Two of the five reasons are end-of-day dispositions — `DAY_OLD_UNSOLD` and `DONATED` — and three are in-shift dispositions: `DAMAGED`, `BURNT` and `OVERPRODUCTION`. That grouping is descriptive only: any of the five may be attested by hand at any point in the day, and all five feed `waste_units_total` and `shrink_cost_cents` identically. Attestation is neither a plan-shaping nor an execution write, so it is accepted whatever the owning day's `plan_posture` — `DRAFT`, `PLANNED` or `LOCKED` alike — and is refused only once the day is `CLOSED`, with `ERR_BAKE_DAY_CLOSED`. The referenced run must have reached `COMPLETED`, or the attestation is rejected with `ERR_RUN_NOT_COMPLETED`. The `units` figure must be at least 1 and may not exceed the run's remaining `on_shelf_units`; exceeding it is rejected with `ERR_WASTE_EXCEEDS_ON_SHELF`, which is also what a run whose shelf stock has already reached zero returns for any further attestation. The attesting caller's `X-User-ID` is stamped onto `attested_by_user_id` and must differ from the run's `executed_by_user_id`, per §2.9.

A new record is born with a `record_status` of `ACTIVE` and copies two things off the run so shrink can roll up without a join: the run's `bake_day_id`, and the run's `unit_cost_basis_cents` as a frozen snapshot. Its `waste_cost_cents` is that snapshotted per-unit basis multiplied by its own `units`, with no further rounding — the per-unit rounding already happened at completion, and multiplying an already-rounded basis is the whole point of the ordering. The snapshot never changes afterwards, even if the run's own figures are later disturbed. Creating the record drives the run's `wasted_units_total` up and its `on_shelf_units` down, and when `on_shelf_units` reaches exactly zero the run's disposition falls to `CLEARED` — from `ON_SHELF` if it was never discounted, or from `MARKED_DOWN` if it was, in which case `markdown_unit_price_cents` is deliberately retained rather than cleared so that a later reversal can restore the discounted price. On the day, the record adds to `waste_units_total` and `shrink_cost_cents`. Waste records are readable individually and listable with filters on `bake_day_id`, `production_run_id`, `disposition_reason` and `record_status`; that list is the only channel through which the records minted by the end-of-day sweep can be discovered.

**The two shrink ratios.** Every change to the day's waste totals forces both shrink ratios to be recomputed, and the two are computed on genuinely different bases. `shrink_cost_basis_pct` is the day's `shrink_cost_cents` divided by its `production_cost_cents`, rounded half up to four decimal places, and is 0.0000 whenever `production_cost_cents` is zero. `shrink_unit_basis_pct` is the day's `waste_units_total` divided by its `produced_units_total`, rounded half up to four decimal places, and is 0.0000 whenever `produced_units_total` is zero. Because the cost basis weights each wasted unit by the cost basis of the run it came from, wasting expensive units moves it faster than wasting cheap ones, and a day mixing premium cakes with cheap rolls will report two visibly different rates on the same physical waste. Only one of them has teeth: the cost-basis ratio is the sole variant that can restrict markdown, and it does so when it is **strictly** greater than the department's `shrink_budget_pct`, at which point the day's `markdown_authorization` flips to `MANAGER_ONLY`. A ratio exactly equal to the budget is compliant. `shrink_unit_basis_pct` is reported for management and gates nothing whatsoever.

**Voiding a mis-attestation.** Only a `DepartmentManager` may reverse a waste record, supplying a `void_reason` of 1 to 500 characters that may not be blank. The reversing manager need not be the operator who attested the record, and §2.9's segregation of duties plays no part in a void. The record must still be `ACTIVE` — a second attempt is rejected with `ERR_WASTE_RECORD_ALREADY_VOIDED` — and the owning day may not be `CLOSED`, or the request is rejected with `ERR_BAKE_DAY_CLOSED`. The void stores `void_reason`, stamps `voided_by_user_id` from the manager's `X-User-ID`, moves `record_status` from `ACTIVE` to `VOIDED`, and increments the record's `version` by 1. Then it walks the same cascade backwards in three hops. First, the run's `wasted_units_total` falls by the record's `units`, so its `on_shelf_units` rises by the same amount. Second, because shelf stock has risen above zero, the run's disposition leaves `CLEARED` — for `MARKED_DOWN` when `markdown_unit_price_cents` is not null, meaning the units return to the shelf at the discounted price, and for `ON_SHELF` when it is null, meaning the batch is simply sellable again at full price. Third, the day's `waste_units_total` and `shrink_cost_cents` drop, both shrink ratios are recomputed, and `markdown_authorization` returns to `AUTO` when the recomputed cost-basis ratio is at or below the department's `shrink_budget_pct`. A voided record counts toward nothing: it is excluded from every waste rollup on the day.

### 3.7. Custom Cakes: Pickup Windows, Quoting and the Decoration Loop

Custom cake work is scheduled against pickup windows rather than ovens. Either a `CakeDesk` operator or a `DepartmentManager` opens a window on a bake day by naming the `bake_day_id`, a `slot_start_utc`, a `slot_end_utc` strictly after it, and a `decorator_capacity_units` between 1 and 500. The window is half-open: `slot_start_utc` is inside it and `slot_end_utc` is not. Windows on the same bake day may not overlap, and the test is symmetrical — a proposed window collides with an existing one, whatever that one's `slot_status`, when the proposed start falls strictly before the existing end **and** the existing start falls strictly before the proposed end. A collision is rejected with `ERR_PICKUP_SLOT_OVERLAP`. There is no buffer here, so a new window that begins at the exact instant another one ends is pure adjacency and is allowed — a deliberate contrast with oven decks, where the changeover buffer makes that same adjacency illegal. A new window opens with a `slot_status` of `OPEN` and `reserved_decoration_units` of 0. Windows are listable with filters on `bake_day_id` and `slot_status`.

`decorator_capacity_units` is an aggregate, not a per-order limit: many cakes share one window up to that total. `reserved_decoration_units` is the sum of `decoration_units` across the orders on the window whose `order_status` is `CONFIRMED`, `IN_DECORATION` or `READY`. Orders still in `INTAKE`, already `PICKED_UP`, or `EXPIRED` hold no capacity at all. A window may be closed explicitly by a `CakeDesk` operator or a `DepartmentManager`, moving `slot_status` `OPEN → CLOSED` and incrementing the window's `version` by 1; `reserved_decoration_units` is retained on closing so that cakes already confirmed into it stay accounted for. Once closed, the window rejects five operations with `ERR_PICKUP_SLOT_CLOSED`: taking a new order against it, confirming an order into it, starting decoration on one of its orders, requesting a revision on one of its orders, and being closed a second time. Marking one of its orders ready and releasing one to the customer are deliberately not on that list — both stay available after the window has closed, because the cake is already made and the shopper is still owed it.

A `CakeDesk` operator takes an order by naming the `bake_day_id`, the `pickup_slot_id` the customer will collect in, the `product_id` of the base cake, the `customer_name` (1 to 120 characters), a `decoration_complexity` and a `tier_count` between 1 and 4, plus optional `allergen_free_required` and `rush_requested` booleans that both default to false. The named window must belong to the same bake day as the order, and one that belongs to a different day is rejected with `ERR_PICKUP_SLOT_NOT_FOUND`; because that is a 404 it is raised in the existence band as the window is resolved, before any body field of the request is examined. `customer_name` may not be blank. The base product must belong to the same department as the bake day, or the order is rejected with `ERR_INGREDIENT_NOT_IN_DEPARTMENT`, and it must carry `is_custom_cake_base` as true, or the order is rejected with `ERR_NOT_CUSTOM_CAKE_BASE` — the department test is taken first, matching §2.10's referential ordering. A new order opens with an `order_status` of `INTAKE` and a `revision_count` of 0, and every derived figure described below — `decoration_units`, `required_decoration_lead_minutes`, `decoration_deadline_utc` and all four quote amounts — is computed at intake and carried on the `201` response, even though intake itself reserves no decorator capacity.

**Decoration effort and the quote.** `decoration_complexity` is one of `SIMPLE`, `STANDARD` or `PREMIUM`, and it drives two independent things. First, the decoration effort: two units per tier for `SIMPLE`, four per tier for `STANDARD`, seven per tier for `PREMIUM`, so `decoration_units` is that per-tier figure multiplied by `tier_count`. Second, the lead time, described below. The quote is then assembled in five ordered steps, and the ordering is load-bearing because two of the steps are bracket lookups that read off different running totals.

1. `decoration_units` is computed as just described.
2. `quote_subtotal_cents` is the product's `unit_retail_cents` multiplied by `tier_count`, plus 450 cents for every one of the `decoration_units`.
3. `rush_fee_cents` is selected from a bracket read off `quote_subtotal_cents` alone, and only when `rush_requested` is true; when the customer did not accept the rush tier it is 0. For a subtotal below 5000 cents the fee is a flat 800 cents. For a subtotal of at least 5000 but below 15000 cents the fee is twelve percent of the subtotal, rounded half up to whole cents. For a subtotal of 15000 cents or more the fee is eight percent of the subtotal, rounded half up to whole cents.
4. `volume_discount_cents` is selected from a bracket read off the subtotal **plus the rush fee**, never off the subtotal alone. When that fee-inflated total is 20000 cents or more the discount is ten percent of it, rounded half up to whole cents; when it is at least 10000 but below 20000 cents the discount is five percent of it, rounded half up; below 10000 cents there is no discount.
5. `quote_total_cents` is the subtotal plus the rush fee less the volume discount.

Each percentage is rounded at its own step and never deferred to the end. Discounting before the rush fee would change which bracket each lookup lands in — the rush bracket is read off the undiscounted subtotal and the discount bracket off the fee-inflated total — so the two orderings produce different totals for the same cake.

**Lead time and the deadline.** `required_decoration_lead_minutes` is a base figure for the complexity — 60 minutes for `SIMPLE`, 120 for `STANDARD`, 240 for `PREMIUM` — plus 30 minutes for every tier, plus a further 45 minutes when `allergen_free_required` is true, because a nut-free cake needs a scrubbed bench. `decoration_deadline_utc` is the window's `slot_start_utc` less that many minutes: it is the latest instant at which the department can still promise the cake.

Confirming the order is the moment capacity is committed, and it is a `CakeDesk` action moving `order_status` `INTAKE → CONFIRMED`. Four checks guard it beyond the window being `OPEN` and the day not being `CLOSED`. The logical clock must be at or before `decoration_deadline_utc` — exactly at the deadline passes, and any later instant is rejected with `ERR_DECORATION_LEAD_TIME_MISSED`. The window's current `reserved_decoration_units` plus this order's `decoration_units` must be no greater than its `decorator_capacity_units`; exact equality passes, and anything above is rejected with `ERR_PICKUP_SLOT_CAPACITY_EXCEEDED`. And if `allergen_free_required` is true, the base product's `allergen_free_claim` must also be true, failing with `ERR_ALLERGEN_SEGREGATION_VIOLATION`. A successful confirmation adds this order's `decoration_units` to the window's `reserved_decoration_units`, incrementing the window's `version` by 1, and increments the order's own `version` by 1.

A `Decorator` then pulls the order off the queue, moving it `CONFIRMED → IN_DECORATION` and stamping `decoration_started_utc` with the logical clock instant; the window must still be `OPEN` and the day must not be `CLOSED`. When the piping is finished the same `Decorator` moves it `IN_DECORATION → READY`, stamping `ready_at_utc`; the reservation is still held, because the cake is physically sitting in the window. Finally a `CakeDesk` operator releases it `READY → PICKED_UP`, stamping `picked_up_at_utc` and subtracting the order's `decoration_units` from the window's `reserved_decoration_units`, which increments the window's `version` by 1. All three of these transitions require the day not to be `CLOSED` and each increments the order's `version` by 1.

**The revision loop.** While a cake is in the decorator's hands the customer may change their mind, and a `CakeDesk` operator can send it back by supplying a new `decoration_complexity` and, optionally, a new `tier_count`; when `tier_count` is omitted the existing tier count stands. This moves the order `IN_DECORATION → CONFIRMED`, which makes the cake lifecycle genuinely cyclic: a cake can sit in `CONFIRMED` three times in all — the initial confirmation plus two revisions. `revision_count` counts the completed loops and may never exceed 2, so a request made when it already reads 2 is rejected with `ERR_REVISION_LIMIT_REACHED`. The window must still be `OPEN`. The lead time is recomputed for the *requested* complexity and tier count before the clock is checked, and the logical clock must be at or before that freshly recomputed `decoration_deadline_utc`, or the request is rejected with `ERR_DECORATION_LEAD_TIME_MISSED`. Capacity is re-tested the same way, but this order's existing reservation is released first: the window's reserved total excluding this order, plus the order's new `decoration_units`, must be no greater than `decorator_capacity_units`, failing with `ERR_PICKUP_SLOT_CAPACITY_EXCEEDED`.

An accepted revision increments `revision_count` by 1, replaces `decoration_complexity` and — when it was supplied — `tier_count`, and then recomputes the whole derived set: `decoration_units`, `required_decoration_lead_minutes`, `decoration_deadline_utc`, `quote_subtotal_cents`, `rush_fee_cents`, `volume_discount_cents` and `quote_total_cents`, all by exactly the five-step ordering above and all reading the order's original `rush_requested` and `allergen_free_required`, because neither of those flags is revisable. The window's `reserved_decoration_units` is adjusted by the difference between the new and the old `decoration_units`, incrementing the window's `version` by 1 — but only when that difference is non-zero: a revision that happens to land on exactly the same `decoration_units` as before leaves the reserved total and the window's `version` precisely where they stood. `decoration_started_utc` is reset to null because the decorator has to start again. The order's `version` increments by 1.

Any cake-order transition asked for from a state that does not declare it — revising an order that is not in `IN_DECORATION`, confirming one that has already `EXPIRED`, marking a `CONFIRMED` order ready — is rejected with `ERR_INVALID_CAKE_ORDER_STATE`. `PICKED_UP` and `EXPIRED` are terminal. Cake orders are readable individually with their full quote breakdown, and listable with filters on `bake_day_id`, `pickup_slot_id`, `product_id` and `order_status`.

### 3.8. Buying Ingredients: Case Packs, Freight and the Purchase Commitment

Replenishment is where the department's money leaves the building, and the system tracks the exposure continuously. `open_purchase_commitment_cents` on a department is a conserved figure: it is at all times the sum of `order_total_cents` across every ingredient order of that department whose `order_status` is `DRAFT` or `SUBMITTED`. Orders that reached `RECEIVED_FULL`, `RECEIVED_SHORT` or `CANCELLED` all drop out of it, which means both receiving and cancelling must lower the commitment by exactly the amount the order added when it was raised. The figure is recomputed on every ingredient-order creation, submission, receipt and cancellation.

A `DepartmentManager` raises an order by naming the `department_id`, the `expected_department_version` demanded by §2.5, and an array of `lines`. An optional `target_bake_day_id` records which operating day the order is meant to supply and is left null when it is not relevant; it is resolved for existence only, so a day in any `plan_posture` — `LOCKED` and `CLOSED` included — and even a day owned by another department may be named without the order being rejected. Each entry in `lines` is supplied by the client with only two keys — an `ingredient_id` and a `required_units` figure — and the server fills in the other three. Each named ingredient must exist, or the request fails with `ERR_INGREDIENT_NOT_FOUND`, must belong to the ordering department, or the request fails with `ERR_INGREDIENT_NOT_IN_DEPARTMENT`, and may appear at most once in the array, a repeat being rejected with `ERR_INVALID_REQUEST`. Those three tests sit in three different bands of §2.10 and are therefore not evaluated in the order just listed: existence first, walking `lines` in array order; then the duplicate test with the rest of the request shape; then the department test down in the referential band, after the version precondition has already been settled. A line carrying an `ingredient_id` that is not a string naming a stored row is an existence failure, whereas a line that omits the key altogether is a shape failure, and each line's `required_units` must be a JSON integer of at least 1. An empty `lines` array is not rejected at creation: the order is minted carrying no line and an `order_total_cents` of 0, and only submission refuses it.

**Case-pack rounding and freight.** Suppliers sell cases, not units, so each line is costed in a fixed sequence, walking `lines` in the order the request supplied them. `cases` is the line's `required_units` divided by the ingredient's `case_pack_units`, rounded **up** to the next whole case. `ordered_units` is that case count multiplied back by `case_pack_units`, and it is therefore always at least the requested figure and often more. The line's base cost is `ordered_units` multiplied by the ingredient's `unit_cost_cents`, and `line_cost_cents` is that base cost multiplied by one plus the department's `freight_surcharge_pct`, rounded half up to whole cents. `order_total_cents` is the sum of the `line_cost_cents` values — that is, the sum of the already-rounded lines. Applying the freight surcharge to a summed base and rounding once at the end produces a different order total for the same input and is wrong.

**The shelf-life cap.** An ingredient may not be over-bought past what it can survive. Each ingredient's maximum orderable quantity is its `daily_usage_units` multiplied by its `shelf_life_days` — a flour used at 40 units a day with a 30-day life caps out at 1200 units in one order. The cap is compared against the line's `ordered_units` *after* case-pack rounding, never against the `required_units` the client asked for, so a request that looks compliant can still be pushed over the cap by the rounding-up step. Exceeding the cap is rejected with `ERR_SHELF_LIFE_OVERSTOCK`; landing exactly on it passes. A newly raised order answers with 201, opens in `DRAFT` with an `origin` of `MANUAL`, a null `submitted_at_utc`, an empty `received_lines` array, a `shortfall_units_total` of 0 and a null `cancel_reason`, immediately raises the department's `open_purchase_commitment_cents` by its `order_total_cents`, and increments the department's `version` by 1.

**Automatic reorder drafts.** The other way an order comes into existence is the consumption cascade of §3.5, and those orders carry an `origin` of `AUTO_REORDER` and a null `target_bake_day_id`. After a completing run has decremented every ingredient in its product's recipe, the system walks those ingredients in `recipe_lines` array order and decides eligibility twice over. An ingredient whose `on_hand_units` is still strictly above its `reorder_point_units` is not due and is skipped; an ingredient sitting at or below its reorder point is due, so equality with the reorder point does earn a top-up. Note the deliberate asymmetry with the state field: `replenishment_state` reads `OK` whenever `on_hand_units` is at or above `reorder_point_units`, so an ingredient resting exactly on its reorder point keeps a `replenishment_state` of `OK` and still earns a top-up line, while only an ingredient strictly below the point moves `OK → REORDER_DUE`. Second, an ingredient is skipped — and its `replenishment_state` left completely untouched — when the department already has an ingredient order in `DRAFT` or `SUBMITTED` carrying a line for it, because the department is not going to order the same flour twice. For each surviving ingredient the top-up quantity is the greater of zero and twice its `reorder_point_units` less its current `on_hand_units`.

One automatic order is created per run completion, in `DRAFT`, holding one line per eligible ingredient whose `required_units` is that ingredient's top-up quantity, and each of those lines is case-pack rounded and freight-costed by exactly the rule above. The shelf-life cap is **not** applied to an automatic draft — it polices only the order a `DepartmentManager` raises by hand — so a top-up line may sit above an ingredient's cap without the run completion that minted it being rejected. An automatic draft otherwise opens with exactly the field set a manual one does: a null `submitted_at_utc`, an empty `received_lines` array, a `shortfall_units_total` of 0 and a null `cancel_reason`. Drafting the order does **not** move any ingredient to `ON_ORDER`: an ingredient stays `REORDER_DUE` until somebody actually submits the order. Ingredient orders are readable individually with their costed lines and listable with filters on `department_id`, `target_bake_day_id`, `order_status` and `origin`; that list is the only channel through which automatic drafts can be discovered.

**Submission.** A `DepartmentManager` sends a `DRAFT` order to the supplier, which moves it `DRAFT → SUBMITTED`, requires the `lines` array to be non-empty — an empty one is rejected with `ERR_INVALID_REQUEST`, though the `DRAFT` precondition is deliberately taken first, so an order that has already been cancelled or received reports `ERR_INVALID_INGREDIENT_ORDER_STATE` even when it also carries no line — and stamps `submitted_at_utc` with the logical clock instant. Every ingredient named by a line whose `replenishment_state` is `OK` or `REORDER_DUE` moves to `ON_ORDER`, applied in `lines` array order, and each of those advances its own `version` by 1; one already reading `ON_ORDER` is left completely untouched and does not advance its `version`. The department's `open_purchase_commitment_cents` is deliberately **unchanged** by submission, because `DRAFT` and `SUBMITTED` both already count toward the commitment, and the department's `version` therefore does not advance either. The order's `version` increments by 1. Submitting anything that is not in `DRAFT` is rejected with `ERR_INVALID_INGREDIENT_ORDER_STATE`.

**Receipt, and its two branches.** Either a `Baker` or a `DepartmentManager` books the delivery by supplying `received_lines`, an array whose entries each pair an `ingredient_id` with a `received_units` count that must be a non-negative JSON integer and is not capped at the line's `ordered_units`. A repeated `ingredient_id` is not rejected: the stored `received_lines` echoes every entry exactly as it was supplied, while the quantity that reaches stock and the shortfall is the last entry named for that ingredient. Every entry must name an ingredient that appears in the order's `lines`, or the request is rejected with `ERR_INGREDIENT_NOT_FOUND`, and conversely every line of the order must appear in `received_lines`, or the request is rejected with `ERR_INVALID_REQUEST`. Receipt is only accepted from `SUBMITTED`; anywhere else it is rejected with `ERR_INVALID_INGREDIENT_ORDER_STATE`.

One trigger, two destinations. When every line's `received_units` is at least its `ordered_units`, the order lands in `RECEIVED_FULL` and `shortfall_units_total` is set to 0. When at least one line came in short of its `ordered_units`, the order lands in `RECEIVED_SHORT` and `shortfall_units_total` is set to the sum, over all lines, of the greater of zero and that line's `ordered_units` less its `received_units` — the shortfall total is the discriminator between the two branches. Everything else is identical across both branches, and no effect is skipped on either: walking `lines` in array order, each ingredient's `on_hand_units` rises by its `received_units`; each touched ingredient then re-derives `replenishment_state`, reading `OK` when its `on_hand_units` is at or above its `reorder_point_units` and `REORDER_DUE` otherwise, and advances its own `version` by exactly 1 even when the received quantity was 0 and the state did not move; the department's `open_purchase_commitment_cents` falls by the order's `order_total_cents` and the department's `version` increments by 1; and the order's own `version` increments by 1.

**Cancellation.** A `DepartmentManager` may cancel an order from either `DRAFT` or `SUBMITTED`, supplying a `cancel_reason` of 1 to 500 characters that may not be blank, and the two paths have identical effects. The reason is stored, the order moves to `CANCELLED`, and the compensating half of the commitment invariant fires: the department's `open_purchase_commitment_cents` falls by exactly this order's `order_total_cents` and the department's `version` increments by 1. Every ingredient named by a line then re-derives `replenishment_state`, reading `REORDER_DUE` when its `on_hand_units` is strictly below its `reorder_point_units` and `OK` otherwise, which is how an ingredient that was sitting in `ON_ORDER` gets released. Unlike a receipt, a cancellation writes nothing else onto the ingredient, so one already resting on the derived value is left untouched and does not advance its `version`. The order's `version` increments by 1. Cancelling an order that has already reached `RECEIVED_FULL`, `RECEIVED_SHORT` or `CANCELLED` is rejected with `ERR_INVALID_INGREDIENT_ORDER_STATE`, since all three are terminal.

### 3.9. Locking and Closing the Operating Day

Once the manager is satisfied with the plan, locking it moves the day `PLANNED → LOCKED`. The transition is declared only out of `PLANNED`: a day still in `DRAFT`, or one already `LOCKED`, is rejected with `ERR_INVALID_RUN_STATE`, and that posture check is taken before the plan is examined for content. Locking carries no request body of its own, and it requires the day to have at least one production run whose `execution_status` is anything other than `CANCELLED`; a day with nothing left to bake is rejected with `ERR_EMPTY_PRODUCTION_PLAN`. Locking is refused on a `CLOSED` day with `ERR_BAKE_DAY_CLOSED`. After the lock, further production-run creation and forecast-line appending are rejected with `ERR_BAKE_DAY_PLAN_LOCKED`, while starting a proof, loading a deck, completing a run and marking a run down all remain fully available — locking freezes the plan, not the floor. The bake day's `version` increments by 1.

Closing the day is the largest single transaction in the system and moves the day `LOCKED → CLOSED`, which is terminal. A day that has not yet been locked — one still in `DRAFT` or still in `PLANNED` — is rejected with `ERR_INVALID_RUN_STATE`, and a day already `CLOSED` with `ERR_BAKE_DAY_CLOSED`. Before anything is swept, the manager must have got the ovens empty: if any production run on the day is still in `PROOFING` or `BAKING`, the close is rejected with `ERR_INVALID_RUN_STATE`. The manager may supply `donate_remaining`, an optional flag defaulting to true that expresses whether tonight's leftovers should go to the charity partner.

The close then performs its sweep in a fixed sequence. First, the day-old sweep walks the day's `COMPLETED` runs whose `disposition_status` is `ON_SHELF` or `MARKED_DOWN` and whose `on_shelf_units` is greater than zero, in `created_at` ascending order, and creates one waste record per run with `units` equal to that run's entire remaining `on_shelf_units`. The `disposition_reason` on each swept record is `DONATED` when `donate_remaining` is true and the owning department has `donation_partner_enabled` set to true, and `DAY_OLD_UNSOLD` in every other case — a department without a donation partner books day-old shrink no matter what the flag says. Each swept record has `attested_by_user_id` stamped with the closing manager's `X-User-ID`. The sweep is exempt from §2.9's segregation of duties: it stamps that identifier even onto a record against a run whose `executed_by_user_id` is the closing manager, so a manager who completed the day's runs is not thereby barred from closing the day.

Every one of those swept records then triggers the same cascade a hand-attested record would. The run's `wasted_units_total` rises and its `on_shelf_units` falls to 0, which in turn flips that run's `disposition_status` to `CLEARED`. The day's `waste_units_total` and `shrink_cost_cents` grow, which forces both `shrink_cost_basis_pct` and `shrink_unit_basis_pct` to be recomputed and may well flip `markdown_authorization` to `MANAGER_ONLY` on the very day that is being closed — the budget breach is recorded even though nothing can be marked down any more.

With the shelf cleared, the sweep tidies up the unfinished work. Every production run still sitting in `SCHEDULED` moves to `CANCELLED` with `cancelled_reason` set to `DAY_CLOSED`, whatever its `origin` — the supersede pass is selective about origin but the close is not — and each of those cancellations drops the run out of the day's planned rollups and triggers the sibling label recomputation on its oven and day. Every custom cake order on the day whose `order_status` is `CONFIRMED`, `IN_DECORATION` or `READY` moves to `EXPIRED`, and each one releases its `decoration_units` back out of its window's `reserved_decoration_units` as it goes, incrementing that order's `version` by 1; an order still in `INTAKE`, and one already `PICKED_UP` or `EXPIRED`, is left exactly as it stands. Every pickup window on the day that is not already `CLOSED` then moves to a `slot_status` of `CLOSED`, while a window already reading `CLOSED` is not rewritten and does not advance its `version`. A window that both releases a reservation and closes inside this one sweep still advances its `version` by exactly 1. Finally the day's `plan_posture` becomes `CLOSED`, every rollup is frozen where the sweep left it, and the bake day's `version` increments by 1. From that point on, every write against the day or against any of its runs, windows, cake orders and waste records is rejected with `ERR_BAKE_DAY_CLOSED`.
