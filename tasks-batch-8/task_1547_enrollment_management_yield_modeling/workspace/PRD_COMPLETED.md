# Enrollment Yield API — Product Requirements Document

## 1. Introduction

Every admissions office runs the same anxious arithmetic each year: inquiries must become applications, applications must become admits, admits must become deposits, and deposits must survive the summer to become enrolled students — all while finite program seats and a finite scholarship budget are competed for, reserved, released, and re-offered. Small timing mistakes compound: an offer made against a stale view of an applicant, a deposit accepted after a deadline, a waitlist activated a day too early, and the shape of the incoming class drifts away from its target.

This document specifies the Enrollment Yield API, the system of record for that entire funnel. It governs inquiry capture with source attribution, committee review with quorum-gated decisions, merit and need-based financial-aid leveraging, deposit collection with deadline-sensitive refund rules, melt-risk scoring with automatic advisor intervention, ranked waitlist activation, and the forecasting reports an enrollment manager needs to steer a cycle. All resources are mounted under the `/enrollment` prefix, with one administrative clock capability mounted outside it. The API is built around a server-side logical clock, live-recomputed funnel counters and conserved ledgers, and optimistic concurrency on the two writes where a stale view can silently destroy value.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

All interactions with the API are authenticated through two mandatory HTTP headers: `X-User-ID` identifies the acting user and `X-User-Role` declares their operational capacity. The system recognizes exactly six roles: `SystemAdmin`, `EnrollmentManager`, `AdmissionsOfficer`, `ApplicationReader`, `FinancialAidOfficer`, and `Applicant`. A request missing either header, or carrying a role string outside this set, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose authenticated role is not in the endpoint's allowed set is rejected with `ERR_FORBIDDEN` (HTTP 403).

The meaning of `X-User-ID` depends on the role. When `X-User-Role` is `Applicant`, `X-User-ID` is the `id` of the acting `Applicant` record; ownership checks on any resource that references an applicant — deposit payment, aid-offer response, application withdrawal, and applicant self-reads — compare the resource's applicant foreign key to `X-User-ID`, and a mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). When `X-User-Role` is `ApplicationReader`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; it is, however, compared against a committee review's `reader_id` at submission time, and a mismatch is rejected with `ERR_REVIEWER_MISMATCH` (HTTP 403). When `X-User-Role` is `SystemAdmin`, `EnrollmentManager`, `AdmissionsOfficer`, or `FinancialAidOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but does not compare it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits; like every system-stamped timestamp in §2.4, it is taken from the server-side logical clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

A request to a path the API does not recognize answers `ERR_NOT_FOUND` (HTTP 404) in this same envelope; a recognized path called with an unsupported HTTP method answers `ERR_INVALID_REQUEST` with HTTP status 405.

### 2.3. Pagination

List endpoints paginate via two query parameters. The `limit` parameter specifies the maximum number of items to return; it defaults to 10, and a supplied value below 1 or above 100 is clamped into that range rather than rejected, while a non-integer `limit` or `offset` is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The `offset` parameter specifies how many items to skip and defaults to 0, with negative values clamped to 0. Unless otherwise specified, every list endpoint returns resources sorted by creation timestamp in ascending order, breaking ties by `id` ascending. Paginated list responses carry `limit`, `offset`, `total_count`, and `has_more` in the `meta` object of the envelope, where `total_count` counts the filtered result set before pagination and `has_more` is true exactly when `offset` + `limit` is less than `total_count`.

### 2.4. The Logical Clock and Time-Dependent Recomputation

Every deadline, window, and phase gate in this system is evaluated against a **server-side logical clock**, never against wall-clock time. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must not fall back to wall-clock time under any circumstance. A `SystemAdmin`-only test-driving capability advances the logical clock to a supplied `to_iso8601` instant and answers with the resulting `current_utc`. Setting the clock is not a passive read of time: as a side effect it recomputes the `melt_risk_score` of every application currently in `DEPOSITED`, including the threshold-triggered automatic interventions described in §3.7. Creation timestamps stamped by the system — an application's `submitted_at`, a deposit's `paid_at`, a review's `submitted_at` — are all taken from this logical clock.

### 2.5. Common Resource Properties

Every resource in the system — cycles, programs, applicants, applications, committee reviews, aid offers, deposits, waitlist entries, and melt interventions alike — carries a standard set of system-managed fields:

- `id` (string): a unique, server-minted identifier formatted as a UUID, with no type prefix.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the resource was created.
- `updated_at` (string): an ISO 8601 UTC timestamp refreshed on every modification.
- `version` (integer): a system-managed integer that starts at 1 at creation and increments with every modification to the resource.

An operation refreshes a resource's `updated_at` and increments its `version` whenever it writes that resource's own stored state — an explicit update, a lifecycle transition, or a cascade that changes one of its persisted fields — and in the parent-bump cases §3 names: an aid-offer create or transition also bumps the parent application and program, a review submission or an intervention completion also bumps the application, and admission, deposit creation, enrollment, withdrawal from `ADMITTED`, and waitlist activation also bump the program. Pure recomputation of derived fields — funnel counters, `seats_open`, the scholarship ledger, `intake_posture`, `admit_rate`, `submitted_read_count`, `melt_risk_score` — never by itself refreshes `updated_at` or increments `version`; in particular a cycle's `version` advances only on a successful advance, and the clock-driven melt-risk sweep of §2.4 rewrites scores in place without incrementing application versions. This audit trail is what the optimistic-concurrency rules in §2.8 key on.

### 2.6. Conserved Ledgers: Seats, Scholarship Funds, and Intake Posture

Each program maintains two conserved ledger fields that the system recomputes immediately on every funnel mutation, with no eventual-consistency lag. The seat ledger is expressed through `seats_open`, defined as `capacity_seats` minus the program's `deposited_count` minus its `enrolled_count`; it never drifts from that identity. The scholarship ledger tracks `scholarship_committed_cents`, the sum of `amount_cents` over all aid offers of the program's applications currently in `OFFERED` or `ACCEPTED` status, and `scholarship_available_cents`, defined as `scholarship_budget_cents` minus `scholarship_committed_cents`. An offer in `REVISION_REQUESTED` contributes nothing to the committed total — its funds are treated as released while the applicant negotiates — and offers in `DECLINED`, `REVOKED`, or `SUPERSEDED` contribute nothing either.

From these counters the system derives each program's `intake_posture`. The posture is `OPEN` while the sum of the program's `deposited_count` and `enrolled_count` remains below its `target_enrollment` and the parent cycle's `status` is one of `OPEN`, `REVIEW_CLOSED`, `DECISIONS_RELEASED`, or `ENROLLMENT_TRACKING`. The posture flips to `PAUSED` the moment the deposited-plus-enrolled sum reaches or exceeds the target. The posture is `CLOSED` once the cycle itself is in `CLOSED`. While the cycle is still in `SETUP` — none of the four `OPEN`-permitting statuses yet reached — the posture reports `PAUSED`. Posture is a computed field, never set directly, and it gates admissions and waitlist activations wherever those workflows appear in §3.

### 2.7. Monetary Values, Probabilities, and Rounding Conventions

All monetary amounts — `tuition_cents`, `scholarship_budget_cents`, `deposit_amount_cents`, `efc_cents`, offer `amount_cents`, `refund_amount_cents`, and the ledger fields — are integers denominated in cents. Award amounts are rounded half-up to whole cents at the moment they are computed, and package totals are sums of those already-rounded components that are never re-rounded. Probabilities and rates — `melt_risk_score`, `rank_score`, `admit_rate`, forecast probabilities, and conversion rates — are reported to exactly four decimal places using round-half-up. Where a calculation is a weighted sum, each weighted product is rounded half-up to four decimal places before the products are summed, and the sum itself is then rounded half-up to four decimal places.

### 2.8. Optimistic Concurrency Control

Two write operations are guarded by optimistic concurrency control, and no other endpoint accepts a version field.

A request to `POST /enrollment/aid-offers` must carry `expected_application_version`, the client's last observed `version` of the target application, as a non-optional field. If the application's current `version` has advanced since that observation — for example because a transition or a prior offer bumped it — the create is rejected with `ERR_STALE_VERSION` (HTTP 412). This guard exists because a successful offer creation supersedes any currently `OFFERED` offer on the application, so a writer holding a stale view must not be allowed to supersede state it never saw.

A request to `PATCH /enrollment/programs/{programId}` must likewise carry `expected_program_version`, the client's last observed `version` of the program, as a non-optional field. A mismatch with the program's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412), since the client's view of the ledger the new values must satisfy is stale. A successful guarded write itself increments the parent's `version`, so every writer serializes through the version they last read.

### 2.9. Validation Cascade Ordering

Every request is validated in a fixed cascade, and the ordering is observable: when several rules would fail, the earliest one in the cascade determines the error. Structural failures — a required field absent (other than the body foreign keys of tier three, whose absence answers `ERR_NOT_FOUND` like any unresolvable reference), an enum value outside its allowed set, a timestamp that does not parse, a non-integer `limit` or `offset`, or a window whose end is not strictly after its start — are rejected with `ERR_INVALID_REQUEST` (HTTP 400) as the request is read: after authentication, authorization, and resource resolution, and ahead of the numbered tiers below. The two deliberate exceptions are review submission, whose score and recommendation checks run only after the review-window check of tier six (§3.4), and intervention completion, whose `outcome` check runs only after the intervention's state gate (§3.7). First, authentication — missing or unknown headers yield `ERR_UNAUTHENTICATED`. Second, role authorization and ownership — wrong role yields `ERR_FORBIDDEN`, an applicant acting on another's resource yields `ERR_NOT_RESOURCE_OWNER`, a mismatched reader yields `ERR_REVIEWER_MISMATCH`. Third, existence — any path identifier or body foreign key (`applicant_id`, `program_id`, `cycle_id`, `application_id`) that does not resolve yields `ERR_NOT_FOUND`; existence of a target resource is always established before any ownership comparison is applied to it, so a request naming a resource that does not exist answers `ERR_NOT_FOUND` even when the caller could not have owned it. Fourth, optimistic concurrency on the two guarded writes, yielding `ERR_STALE_VERSION`. Fifth, state permission — whether the target resource's current state permits the requested transition or action at all, yielding `ERR_INVALID_STATE`; this tier also carries the application-state gates on deposit creation, review assignment, and intervention scheduling. Sixth, clock-based window and deadline rules — `ERR_REVIEW_WINDOW_CLOSED`, `ERR_DEPOSIT_DEADLINE_PASSED`, and `ERR_PHASE_PRECONDITION_NOT_MET`. Seventh, field-level range, uniqueness, and scheduling rules such as score ranges, duplicate readers, window overlaps, applicant-type data, exact deposit amounts, the target-versus-capacity rule (`ERR_TARGET_EXCEEDS_CAPACITY`), and the applicant–program–cycle alignment check (`ERR_PROGRAM_CYCLE_MISMATCH`). Eighth, cross-entity state references — cycle-phase gates (`ERR_CYCLE_PHASE_MISMATCH`), intake posture (`ERR_INTAKE_PAUSED`), review quorum (`ERR_REVIEW_QUORUM_NOT_MET`), unresolved applications (`ERR_UNRESOLVED_APPLICATIONS`), a cycle without programs (`ERR_CYCLE_HAS_NO_PROGRAMS`), an already-accepted aid offer (`ERR_AID_ALREADY_ACCEPTED`), and an empty waitlist pool (`ERR_WAITLIST_EMPTY`). Ninth and last, fiscal checks — seat capacity (`ERR_CAPACITY_FULL`), scholarship budget (`ERR_SCHOLARSHIP_BUDGET_EXCEEDED`, `ERR_BUDGET_BELOW_COMMITTED`), and aid eligibility (`ERR_NO_AID_ELIGIBILITY`). Because fiscal checks run last, a seat-capacity failure can never mask an earlier state or clock failure; the inverse is always what the caller observes.

## 3. Business Logic & Workflows

### 3.1. Admission Cycles: Setup, Advancement, and the Close Cascade

An `EnrollmentManager` opens a recruiting year by creating an admission cycle with a display `name` (for example, "Fall 2027"), the `application_opens_at` instant when intake begins, the `application_deadline_at` deadline, the `deposit_deadline_at` deadline, the `census_at` instant, and the `target_class_size` — the class-shaping target across the whole cycle, which must be at least one. A new cycle is born in `SETUP` with all of its computed funnel counters at zero. Those counters are maintained live thereafter: `inquiry_count` tracks how many applicants are attributed to the cycle, `application_count` tracks applications filed in it, and `admitted_count`, `deposited_count`, and `enrolled_count` track how many of the cycle's applications currently sit in `ADMITTED`, `DEPOSITED`, and `ENROLLED` respectively. The `decisioned_count` counts every application that has ever received a decision — any application that ever reached `ADMITTED` (including ones that later moved to `DEPOSITED`, `ENROLLED`, `MELTED`, or withdrew after admission) plus every application in `DENIED`. From these the cycle reports `admit_rate`: the count of applications that ever reached `ADMITTED` divided by `decisioned_count`, expressed to four decimal places round-half-up, and reported as 0 when `decisioned_count` is zero.

Cycle advancement is driven by the `EnrollmentManager` supplying a `to_status`, and each step is gated by the calendar or by outstanding work. Moving `SETUP → OPEN` requires that the logical clock has reached `application_opens_at` (otherwise `ERR_PHASE_PRECONDITION_NOT_MET`) and that at least one program exists in the cycle (otherwise `ERR_CYCLE_HAS_NO_PROGRAMS`). Moving `OPEN → REVIEW_CLOSED` requires that the clock has reached `application_deadline_at`. Moving `REVIEW_CLOSED → DECISIONS_RELEASED` requires that no application of the cycle remains in `IN_REVIEW`, `COMMITTEE_REVIEW`, or `DECISION_PENDING`; any straggler fails the advance with `ERR_UNRESOLVED_APPLICATIONS`. Moving `DECISIONS_RELEASED → ENROLLMENT_TRACKING` requires that the clock has reached `deposit_deadline_at`. A request naming a `to_status` that the cycle's current status does not permit is rejected with `ERR_INVALID_STATE`, and every successful advance refreshes the cycle's `updated_at` and increments its `version` by exactly one.

The final step, `ENROLLMENT_TRACKING → CLOSED`, requires that the clock has reached `census_at`, and it triggers the close cascade. Every waitlist entry of the cycle's programs still in `ACTIVE` moves to `EXPIRED`; each expired entry's application, still sitting in `WAITLISTED`, is moved to `DENIED`; every melt intervention of the cycle's applications still in `SCHEDULED` moves to `CANCELLED`; and the program counters and cycle funnel aggregates are then recomputed. Once a cycle is `CLOSED`, every program under it reports `intake_posture` of `CLOSED` as well.

### 3.2. Programs, Capacity, and Class-Shaping Targets

Programs are the unit of capacity. An `EnrollmentManager` creates one inside a cycle by providing the `cycle_id`, a `name`, the physical `capacity_seats`, the class-shaping `target_enrollment` for that program, the sticker `tuition_cents`, the total `scholarship_budget_cents`, and the exact `deposit_amount_cents` a deposit must carry. The target may not exceed capacity: a create or update whose `target_enrollment` is greater than `capacity_seats` is rejected with `ERR_TARGET_EXCEEDS_CAPACITY`. An optional `auto_waitlist_activation` flag — defaulting to false when omitted — controls whether a freed seat automatically activates the top-ranked active waitlist entry, a cascade detailed in §3.6 and §3.8. At creation every counter is zero, so `seats_open` equals `capacity_seats`, `scholarship_available_cents` equals `scholarship_budget_cents`, and `intake_posture` is computed per §2.6.

Programs may be updated after creation — capacity, target, budget, and the auto-activation flag may all change — through the OCC-guarded update described in §2.8. Beyond the stale-version check, the target-versus-capacity rule runs first — an update whose effective `target_enrollment` exceeds its effective `capacity_seats` is rejected with `ERR_TARGET_EXCEEDS_CAPACITY` — and then one fiscal invariant is enforced: the new `scholarship_budget_cents` may not fall below the program's current `scholarship_committed_cents`, and an attempt to set it lower is rejected with `ERR_BUDGET_BELOW_COMMITTED`. Every successful update recomputes `seats_open`, `scholarship_available_cents`, and `intake_posture`, and increments the program's `version` by one. The program listing can be filtered by `cycle_id` and supports the standard `limit` and `offset` pagination parameters.

### 3.3. Inquiry Capture and Application Submission

The funnel begins when an `AdmissionsOfficer` captures an inquiry. The payload carries the `cycle_id` the inquiry is attributed to, the applicant's `full_name` and `email`, the `applicant_type` — one of `FIRST_YEAR`, `TRANSFER`, or `READMIT` — the `inquiry_source`, one of `WEB_FORM`, `CAMPUS_VISIT`, `COLLEGE_FAIR`, `REFERRAL`, or `PURCHASED_LIST`, and the `distance_band`, one of `LOCAL`, `REGIONAL`, `NATIONAL`, or `INTERNATIONAL`, which later feeds melt-risk scoring. Email addresses are unique within a cycle: a second inquiry in the same cycle carrying an `email` already present on another applicant of that cycle is rejected with `ERR_DUPLICATE_APPLICANT_EMAIL`. Applicant-type-specific data is enforced at intake — a `TRANSFER` applicant must supply `transfer_credit_hours` (a non-negative integer), and a `READMIT` applicant must supply `prior_standing`, one of `GOOD_STANDING`, `ACADEMIC_PROBATION`, or `DISMISSED`; missing type-required data is rejected with `ERR_APPLICANT_TYPE_DATA_MISSING`, and a readmit applicant whose `prior_standing` is `DISMISSED` is rejected outright with `ERR_READMIT_NOT_ELIGIBLE`. A captured inquiry starts with `funnel_stage` of `INQUIRY`, and the cycle's `inquiry_count` recomputes immediately. The applicant listing can be filtered by `cycle_id`, `inquiry_source`, and `funnel_stage`.

Submitting an application converts the inquiry. An `AdmissionsOfficer` files an application with the `applicant_id`, the `program_id`, the `cycle_id`, an `academic_score` between 0 and 100 inclusive, and the family's `efc_cents` — the expected family contribution in cents, which must be non-negative and drives need-based aid. Three guards protect the filing, and they fire in this order: an `academic_score` outside the 0-to-100 range is rejected with `ERR_SCORE_OUT_OF_RANGE`; the declared `cycle_id` must equal both the referenced applicant's cycle and the referenced program's cycle, with any divergence rejected as `ERR_PROGRAM_CYCLE_MISMATCH`; and the cycle must currently be in `OPEN`, with filings at any other phase rejected with `ERR_CYCLE_PHASE_MISMATCH`. A successful filing lands in `SUBMITTED`, stamps `submitted_at` from the logical clock, initializes `review_round` to 1, flips the applicant from `INQUIRY` to `APPLIED` — an automatic, absorbing transition that never reverses — and recomputes the cycle's `application_count`. An applicant may hold any number of applications; filing does not require the applicant to be application-free. The application listing can be filtered by `cycle_id`, `program_id`, `applicant_id`, and `status`.

### 3.4. Committee Reads and the Decision Workflow

Review begins when an `AdmissionsOfficer` moves an application from `SUBMITTED` to `IN_REVIEW`. Committee reads are then assigned by creating a review with the `application_id`, the `reader_id` of the opaque `ApplicationReader` user who will read it, and a half-open review window from `window_start_at` (inclusive) to `window_end_at` (exclusive), where the end must be strictly later than the start or the assignment is rejected as malformed with `ERR_INVALID_REQUEST`. Assignment is only possible while the application is in `IN_REVIEW` or `COMMITTEE_REVIEW`; against any other status it is rejected with `ERR_INVALID_STATE`. Two reader-integrity rules apply at assignment: the same `reader_id` may not already hold an `ASSIGNED` or `SUBMITTED` review for the same application (`ERR_DUPLICATE_READER_REVIEW`), and the new window may not overlap another `ASSIGNED` review window for the same reader — the windows being half-open, a new window whose start exactly equals an existing window's end is permitted, while any true overlap is rejected with `ERR_REVIEWER_WINDOW_OVERLAP`. Any assignment created while the application is in `IN_REVIEW` — the very first one, and equally any re-assignment after a send-back — automatically moves it to `COMMITTEE_REVIEW`; the transition endpoint also accepts an explicit `IN_REVIEW` → `COMMITTEE_REVIEW` move. The review listing can be filtered by `application_id`, `reader_id`, and `status`.

Submitting a read is the reader's own act: the caller's `X-User-ID` must equal the review's `reader_id`, or the submission is rejected with `ERR_REVIEWER_MISMATCH`. A submission against a review no longer in `ASSIGNED` is rejected with `ERR_INVALID_STATE`. The submission carries `score_academic` and `score_fit`, each between 0 and 100 inclusive (anything outside is `ERR_SCORE_OUT_OF_RANGE`), and a `recommendation` of `ADMIT`, `DENY`, or `WAITLIST`. It is accepted only while the logical clock falls inside the review window — on or after `window_start_at` and strictly before `window_end_at` — with submissions outside the window rejected as `ERR_REVIEW_WINDOW_CLOSED`; per §2.9 the state and window checks run before the score and recommendation payloads are validated. A successful submission moves the review from `ASSIGNED` to `SUBMITTED`, stamps its `submitted_at` from the logical clock, and recomputes the application's `submitted_read_count`, the number of its reviews in `SUBMITTED`.

Committee work is iterative. An `AdmissionsOfficer` may send an application back from `COMMITTEE_REVIEW` to `IN_REVIEW` for additional reads; the send-back increments the application's `review_round` by one and cancels every still-`ASSIGNED` review on it, moving each to `CANCELLED`. When the file is ready, the move from `COMMITTEE_REVIEW` to `DECISION_PENDING` demands quorum: the application's `submitted_read_count` must be at least two, and a move attempted short of quorum fails with `ERR_REVIEW_QUORUM_NOT_MET`.

Three decisions are possible from `DECISION_PENDING`. Admitting requires two cross-entity gates: the program's `intake_posture` must be `OPEN` (a `PAUSED` or `CLOSED` posture yields `ERR_INTAKE_PAUSED`), and the cycle's `status` must be one of `OPEN`, `REVIEW_CLOSED`, or `DECISIONS_RELEASED` (anything else yields `ERR_CYCLE_PHASE_MISMATCH`); on admission the program's `admitted_count` increases by one, the cycle aggregates recompute, and posture re-derives. Denying moves the application to `DENIED`, cancels any reviews still `ASSIGNED`, and recomputes the cycle's `decisioned_count`. Waitlisting moves the application to `WAITLISTED`, cancels any reviews still `ASSIGNED`, and creates the waitlist entry described in §3.8.

Every committee-side target on the transition endpoint is role-gated: a move to `IN_REVIEW`, `COMMITTEE_REVIEW`, `DECISION_PENDING`, `ADMITTED`, `DENIED`, or `WAITLISTED` is an `AdmissionsOfficer`-only act, and any other role attempting one is rejected with `ERR_FORBIDDEN`; likewise `ENROLLED` is `EnrollmentManager`-only and `WITHDRAWN` is limited to an `AdmissionsOfficer` or the owning applicant. This per-target role gate applies only once the named transition is itself permitted from the current status — an impermissible or unknown `to_status` answers `ERR_INVALID_STATE` regardless of role.

Withdrawal is available throughout the pre-enrollment pipeline — from `SUBMITTED`, `IN_REVIEW`, `COMMITTEE_REVIEW`, `DECISION_PENDING`, and, as detailed in later sections, from `ADMITTED`, `DEPOSITED`, and `WAITLISTED`. Either the applicant or an `AdmissionsOfficer` may withdraw an application, but when the actor is an `Applicant` the caller's `X-User-ID` must equal the application's `applicant_id`, failing which the request is rejected with `ERR_NOT_RESOURCE_OWNER`. Withdrawing from `COMMITTEE_REVIEW` or `DECISION_PENDING` also cancels every still-`ASSIGNED` review on the application.

### 3.5. Financial Aid Leveraging and the Offer Negotiation Cycle

A `FinancialAidOfficer` creates an aid offer for an application by naming the `application_id` and the `fund_type` — `MERIT` or `NEED_BASED` — together with the `expected_application_version` required by §2.8. One exclusivity rule applies: an application that already holds an offer in `ACCEPTED` rejects any new offer with `ERR_AID_ALREADY_ACCEPTED`. When the new offer is created while an earlier offer on the same application is still `OFFERED`, the earlier offer is automatically moved to `SUPERSEDED`, its amount leaves the committed ledger, and the new amount enters it. Because this supersede semantics makes creation destructive to existing state, a successful create also increments the parent application's `version` by one — which is exactly why §2.8 pins the create to the caller's last-observed version.

The offered `amount_cents` is never supplied by the caller; it is computed by the aid-leveraging formula against the program's `tuition_cents`. For a `MERIT` offer, a tier rate is selected from the application's `academic_score`: one-half of tuition when the score is at least 95, 0.35 when the score is at least 90 but below 95, 0.20 when the score is at least 80 but below 90, and zero when the score is below 80; the merit base is the tier rate multiplied by tuition, rounded half-up to whole cents, and then capped at 2,500,000 cents — twenty-five thousand dollars — per offer. For a `NEED_BASED` offer, the need base is the amount by which `tuition_cents` exceeds the application's `efc_cents`, floored at zero; the base is the lesser of that need base and sixty percent of tuition, rounded half-up to whole cents, and then capped at 3,000,000 cents — thirty thousand dollars — per offer. If the base computes to zero the create is rejected with `ERR_NO_AID_ELIGIBILITY`; eligibility is evaluated first, and only a positive base proceeds to the budget check, where a program whose `scholarship_available_cents` is zero rejects the create with `ERR_SCHOLARSHIP_BUDGET_EXCEEDED`. The awarded amount is the lesser of the computed base and the program's currently available scholarship funds, so an award can be partially clipped by the remaining budget but never exceeds it.

The applicant answers an offer in `OFFERED` — always with the ownership check of §2.1, so a caller whose `X-User-ID` differs from the application's `applicant_id` is rejected with `ERR_NOT_RESOURCE_OWNER`. Accepting moves the offer to `ACCEPTED`; declining moves it to `DECLINED`; requesting revision moves it to `REVISION_REQUESTED`. All three recompute the scholarship ledger — committed totals include `OFFERED` and `ACCEPTED` only, so accepting keeps the funds committed, declining releases them, and a revision request releases them while the negotiation is open — and all three recompute the application's aid fields and `melt_risk_score`. The application's `aid_accepted_cents` is the sum of `amount_cents` over its offers in `ACCEPTED` only — a sum of already-rounded per-offer amounts that is itself never re-rounded — and its `aid_gap_cents` is the amount by which `tuition_cents` exceeds `aid_accepted_cents`, floored at zero.

Negotiation continues from `REVISION_REQUESTED`. A `FinancialAidOfficer` may re-offer, moving the offer back to `OFFERED`: the award formula runs again in full against the program's current `scholarship_available_cents` — the offer itself contributes nothing to committed while it sits in `REVISION_REQUESTED`, so its prior amount does not block its own recomputation — and the same two guards apply in the same order, a zero recomputed base failing with `ERR_NO_AID_ELIGIBILITY` and an empty budget with `ERR_SCHOLARSHIP_BUDGET_EXCEEDED`. Alternatively the officer may revoke, moving the offer from `REVISION_REQUESTED` to `REVOKED` with a ledger recompute. Revocation is also available on offers in `OFFERED` or `ACCEPTED`, whether invoked directly by a `FinancialAidOfficer` or triggered by a system cascade when the underlying application withdraws or melts: in each case the offer's `amount_cents` is subtracted from `scholarship_committed_cents` and added back to `scholarship_available_cents`, and the application's `aid_accepted_cents`, `aid_gap_cents`, and `melt_risk_score` recompute. The full lifecycle the transition endpoint permits is `OFFERED` → {`ACCEPTED`, `DECLINED`, `REVISION_REQUESTED`, `REVOKED`, `SUPERSEDED`}, `REVISION_REQUESTED` → {`OFFERED`, `REVOKED`}, and `ACCEPTED` → {`REVOKED`}; every other pairing is rejected with `ERR_INVALID_STATE`, and `DECLINED`, `REVOKED`, and `SUPERSEDED` are terminal. Accept, decline, and revision-request are the owning applicant's acts — a non-applicant caller is rejected with `ERR_FORBIDDEN`, a mismatched applicant with `ERR_NOT_RESOURCE_OWNER` — re-offer and revoke are `FinancialAidOfficer`-only, and a manual `OFFERED` → `SUPERSEDED` carries no further role restriction beyond the endpoint's own and applies the same ledger recompute the automatic supersede does. The aid-offer listing can be filtered by `application_id` and `status`.

### 3.6. Deposits, Enrollment, and Withdrawal

An admitted applicant secures a seat by paying a deposit, naming the `application_id` and the `amount_cents`. The checks fire in the cascade order of §2.9: the caller must be the owning `Applicant`; the application must currently be `ADMITTED`, with any other status rejected as `ERR_INVALID_STATE`; the logical clock must not have passed the cycle's `deposit_deadline_at` — the deadline boundary is inclusive, so a deposit landing exactly at the deadline is accepted and anything strictly later is rejected with `ERR_DEPOSIT_DEADLINE_PASSED`; the `amount_cents` must equal the program's `deposit_amount_cents` exactly, with any mismatch rejected as `ERR_DEPOSIT_AMOUNT_MISMATCH`; the cycle must be in `DECISIONS_RELEASED`, with deposits at any other phase rejected as `ERR_CYCLE_PHASE_MISMATCH`; and only then is seat capacity consulted — a deposit made when the program's `deposited_count` plus `enrolled_count` has already reached `capacity_seats` is rejected with `ERR_CAPACITY_FULL`, while one made when the sum is exactly one below capacity is accepted. At most one non-terminal deposit ever exists per application, a property guaranteed by the admission-state gate itself. `DEPOSITED` and `MELTED` are never valid `to_status` values on the application transition endpoint — the deposit flow and the melt sweep own those moves — and naming either there is rejected with `ERR_INVALID_STATE`.

A successful deposit is born in `PAID`, stamps `paid_at` from the logical clock, leaves `refund_amount_cents` null, and automatically moves the application from `ADMITTED` to `DEPOSITED`. That transition shifts the program's counters — `admitted_count` down by one, `deposited_count` up by one — recomputes `seats_open` and `intake_posture`, and recomputes the application's `melt_risk_score` under the standard variant of §3.7, including the threshold side effect that may auto-create an intervention. The deposit listing can be filtered by `application_id` and `status`.

Enrollment is the registrar's confirmation: an `EnrollmentManager` moves a `DEPOSITED` application to `ENROLLED`. The application's deposit is necessarily in `PAID` at this point — a property implied by the `DEPOSITED` state itself — and the cycle must be in `DECISIONS_RELEASED` or `ENROLLMENT_TRACKING`, failing which the move is rejected with `ERR_CYCLE_PHASE_MISMATCH`. The transition moves `deposited_count` down by one and `enrolled_count` up by one, recomputes `seats_open` and `intake_posture`, and cancels every melt intervention of the application still in `SCHEDULED`, moving each to `CANCELLED`.

Withdrawal after admission carries financial consequences. Withdrawing from `ADMITTED` revokes every aid offer of the application in `OFFERED` or `REVISION_REQUESTED` with the ledger recompute of §3.5, and decrements the program's `admitted_count` with `seats_open` and `intake_posture` recomputed. Withdrawing from `DEPOSITED` resolves the deposit by the calendar: when the logical clock is on or before the cycle's `deposit_deadline_at` the deposit moves from `PAID` to `REFUNDED` and its `refund_amount_cents` is set to the full `amount_cents`; when the clock is past the deadline the deposit moves from `PAID` to `FORFEITED` and `refund_amount_cents` becomes 0. The program's `deposited_count` decrements, `seats_open` and `intake_posture` recompute, every aid offer in `OFFERED`, `REVISION_REQUESTED`, or `ACCEPTED` is revoked with the ledger recompute, and the freed seat triggers the conditional waitlist auto-activation cascade — the same one that follows a melt, described in §3.7 and §3.8.

### 3.7. Summer Melt: Risk Scoring, Interventions, and the Sweep

Every deposited application carries a `melt_risk_score` between 0 and 1, recomputed whenever deposit creation touches the application, on every aid-offer creation and every aid-offer transition — acceptance, decline, revision request, re-offer, revocation, and manual supersede alike — whenever one of its interventions completes, and across every `DEPOSITED` application whenever an administrator sets the logical clock. The recompute applies only while the application is `DEPOSITED`; in every other status the stored score is left untouched. The score blends four factors. The aid-gap factor is the application's `aid_gap_cents` divided by its program's `tuition_cents`, capped at 1 and rounded half-up to four decimals — and defined as 0 when the program's tuition is zero. The distance factor is read from the applicant's `distance_band`: 0.0 for `LOCAL`, 0.3 for `REGIONAL`, 0.6 for `NATIONAL`, and 1.0 for `INTERNATIONAL`. The engagement factor is 0.0 when any of the application's melt interventions has been completed with an `outcome` of `REACHED_ENGAGED` or `REACHED_CONFIRMED`, and 1.0 otherwise. The time factor is the number of whole days between the deposit's `paid_at` and the current logical clock, divided by thirty, capped at 1 and rounded half-up to four decimals.

Two weighting variants exist, selected purely by the clock's position relative to the cycle's `deposit_deadline_at`. While the clock is on or before the deadline, the standard variant applies: the risk is 0.40 times the aid-gap factor plus 0.25 times the distance factor plus 0.20 times the engagement factor plus 0.15 times the time factor. Once the clock passes the deadline, the summer-window variant applies: the distance factor drops out entirely and the weights rebalance to 0.50 times the aid-gap factor plus 0.30 times the engagement factor plus 0.20 times the time factor. Under both variants, each weighted product is individually rounded half-up to four decimal places before the products are summed, and the sum is rounded half-up to four decimal places — so the same underlying fields can legitimately produce a different score on either side of the deadline.

Every recompute carries a threshold side effect: if the application is currently `DEPOSITED`, the fresh score is at least 0.70, and no melt intervention of the application is presently in `SCHEDULED`, the system automatically schedules one — `trigger_source` of `AUTO_THRESHOLD`, `intervention_type` of `EMAIL_CAMPAIGN`, `advisor_id` set to the reserved identifier `AUTO_QUEUE`, and a window running from the current clock instant to exactly seven days later.

Staff can also schedule interventions manually. An `EnrollmentManager` or `AdmissionsOfficer` schedules one by supplying the `application_id`, the `advisor_id` (an opaque advisor user id, with `AUTO_QUEUE` reserved for system-created rows — a manual create naming `AUTO_QUEUE` is rejected with `ERR_INVALID_REQUEST`), the `intervention_type` — `OUTREACH_CALL`, `ADVISOR_MEETING`, or `EMAIL_CAMPAIGN` — and a window from `window_start_at` to `window_end_at`, where the end must be strictly later than the start or the request is rejected as malformed with `ERR_INVALID_REQUEST`. The application must currently be `DEPOSITED`; against any other status the scheduling is rejected with `ERR_INVALID_STATE`. Manually scheduled rows carry `trigger_source` of `MANUAL`. For the two contact-heavy types, `OUTREACH_CALL` and `ADVISOR_MEETING`, an advisor-buffer rule protects schedules: the new intervention conflicts when another `SCHEDULED` intervention of either of those two types exists for the same `advisor_id` whose exclusion span — running from its window start to fifteen minutes past its window end — overlaps the new window, and a conflict is rejected with `ERR_INTERVENTION_WINDOW_CONFLICT`. `EMAIL_CAMPAIGN` interventions and rows under the `AUTO_QUEUE` advisor are exempt from the buffer rule entirely. The intervention listing can be filtered by `application_id`, `advisor_id`, and `status`.

Completing an intervention requires an `outcome` — `REACHED_ENGAGED`, `REACHED_CONFIRMED`, or `NO_CONTACT` — and a completion request without a valid outcome is rejected with `ERR_INVALID_REQUEST`; either an `EnrollmentManager` or an `AdmissionsOfficer` may complete or cancel one. A completion moves the intervention from `SCHEDULED` to `COMPLETED` and immediately recomputes the application's `melt_risk_score`, with the engaged and confirmed outcomes dropping the engagement factor to 0.0 as described above. Cancellation moves `SCHEDULED` to `CANCELLED` and also happens automatically on two cascades: the application enrolling, and the cycle closing.

The summer-melt sweep is the cycle-level intervention of last resort. Invoked by an `EnrollmentManager` against a cycle, it is permitted only while the cycle is in `DECISIONS_RELEASED` or `ENROLLMENT_TRACKING`; against any other status it answers `ERR_INVALID_STATE`. It moves every application of the cycle still in `DEPOSITED` to `MELTED` and runs the full melt cascade on each: the application's deposit moves from `PAID` to `FORFEITED` with `refund_amount_cents` set to 0; the program's `deposited_count` decrements, `seats_open` rises by one, and `intake_posture` re-derives; every aid offer in `OFFERED`, `REVISION_REQUESTED`, or `ACCEPTED` is revoked with the scholarship-ledger recompute; and the freed seat conditionally triggers waitlist auto-activation exactly as in §3.8. Applications are processed in creation order, ties broken by `id`. The sweep answers with `melted_count`, the list of `melted_application_ids`, and the list of `activated_entry_ids` produced by those conditional activations, both lists following that processing order.

### 3.8. Waitlist Ranking and Activation

A waitlist entry is born only from the waitlist decision of §3.4: the entry records the `application_id`, denormalizes the `program_id` from the application at creation, and computes its `rank_score` once, at entry creation. The rank score is six-tenths of the application's `academic_score` plus four-tenths of its recommendation strength, where recommendation strength is one hundred times the share of the application's submitted reads carrying an `ADMIT` recommendation — that is, the count of `SUBMITTED` reviews whose `recommendation` is `ADMIT` divided by the total count of `SUBMITTED` reviews, multiplied by one hundred, and defined as 0 when the application has no submitted reads. The result is rounded half-up to four decimal places. The entry begins in `ACTIVE`; the waitlist listing can be filtered by `program_id`, `application_id`, and `status`.

Activation selects from a ranked pool under a pinned selector. An `EnrollmentManager` activates for a program by supplying its `program_id`: the program's `intake_posture` must be `OPEN` (`ERR_INTAKE_PAUSED` otherwise), the cycle must be in `DECISIONS_RELEASED` or `ENROLLMENT_TRACKING` (`ERR_CYCLE_PHASE_MISMATCH` otherwise), and the eligible pool is exactly the program's entries in `ACTIVE`. The selector ranks the pool by `rank_score` descending, breaking ties by the underlying application's `submitted_at` ascending — earlier filers win — and resolving any remaining tie by entry creation order; an empty pool is rejected with `ERR_WAITLIST_EMPTY`. Activation moves the selected entry from `ACTIVE` to `ACTIVATED`, moves its application from `WAITLISTED` to `ADMITTED`, increments the program's `admitted_count` by one, and re-derives posture. The same activation is also reachable as a `WAITLISTED` → `ADMITTED` move on the application transition endpoint: it requires an `ACTIVE` entry for the application (none answers `ERR_INVALID_STATE`), then an `OPEN` posture (`ERR_INTAKE_PAUSED`), then a cycle in `DECISIONS_RELEASED` or `ENROLLMENT_TRACKING` (`ERR_CYCLE_PHASE_MISMATCH`), and it runs the identical activation cascade; the transition endpoint's own roles govern it, with no further actor restriction.

Seats freed by melt or by a post-deposit withdrawal run the same selection automatically, but only when two conditions both hold: the program's `auto_waitlist_activation` flag is true, and the posture recomputed after the seat frees is `OPEN`. When both hold, the same pinned selector — `rank_score` descending, `submitted_at` ascending as the tie-break, then entry creation order — picks the top-ranked `ACTIVE` entry of that program, moves it to `ACTIVATED`, moves its application from `WAITLISTED` to `ADMITTED`, and increments `admitted_count`; when the pool is empty the seat simply stays open and no error is raised. A waitlisted application's other exits are quieter: a manual move from `WAITLISTED` to `DENIED` moves its `ACTIVE` entry to `REMOVED`, as does the applicant's own withdrawal from `WAITLISTED`, while the cycle-close cascade of §3.1 moves every remaining `ACTIVE` entry to `EXPIRED` and each of their applications from `WAITLISTED` to `DENIED`.

### 3.9. Forecasting and Source-Attribution Reporting

Two computed reads close the loop for the enrollment manager; neither persists anything. The yield forecast takes an optional `variant` query parameter — `historical_band` by default, or `aid_adjusted`; any other value is rejected with `ERR_INVALID_REQUEST` (HTTP 400) — and projects enrollment for a cycle from two bases and a pipeline. The bases are the cycle's current `enrolled_count` and `deposited_count`; the pipeline is exactly the cycle's applications currently in `ADMITTED`, with applications in `SUBMITTED`, `IN_REVIEW`, `COMMITTEE_REVIEW`, `DECISION_PENDING`, `WAITLISTED`, `DENIED`, `WITHDRAWN`, or `MELTED` never entering it. Under the historical-band variant, each pipeline application's probability comes from its `academic_score` alone: 0.65 when the score is at least 90, 0.45 when the score is at least 70 but below 90, and 0.25 when the score is below 70. Under the aid-adjusted variant, a coverage ratio is computed per application — its `aid_accepted_cents` divided by its program's `tuition_cents`, rounded half-up to four decimals, and 0 when the applicant holds no accepted aid or the program's tuition is zero — and the band probability is scaled by one plus the coverage ratio, capped at 1.0, and rounded half-up to four decimals; identical inputs therefore yield a projection that is higher whenever any admitted applicant holds accepted aid. The `projected_enrollment` is the enrolled base plus the deposited base plus the sum of the pipeline probabilities, rounded half-up to a whole number. The response reports the `variant`, the `projected_enrollment`, the cycle's `admit_rate` alongside, and the three counts `admitted_count`, `deposited_count`, and `enrolled_count`.

The funnel report answers the source-attribution question: which inquiry channels convert. For each of the five `inquiry_source` values — `WEB_FORM`, `CAMPUS_VISIT`, `COLLEGE_FAIR`, `REFERRAL`, and `PURCHASED_LIST` — it counts the cycle's applicants attributed to that source and how many of them have reached `funnel_stage` of `APPLIED`, emitting one row per source in that fixed order, each row carrying `inquiry_source`, `inquiries`, `applied`, and a per-source `conversion_rate` of applied divided by inquiries, rounded half-up to four decimals, and reported as 0.0 when the source has no inquiries. The report's `overall_conversion_rate` is computed from the unrounded totals — total applied across all sources divided by total inquiries — and rounded half-up to four decimals exactly once; it is deliberately not an average of the per-source rounded rates, and it is 0.0 when the cycle has no inquiries at all. The response also carries the cycle's `inquiry_count` and `applied_count` alongside the `rows` array.
