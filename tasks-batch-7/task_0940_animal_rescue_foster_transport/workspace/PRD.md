# Animal Rescue & Foster/Transport Network API — Product Requirements Document

## 1. Introduction

A regional rescue network does not run on one system of record; it runs on a dozen improvised ones. Intake logs live in a spreadsheet at the municipal shelter, foster home checks live in a coordinator's inbox, the relay driver roster lives in a group chat, and the restricted donations that were supposed to pay for a specific puppy's surgery live in an accountant's memory. When an animal crosses a state line at 6 a.m. on a Saturday with an expired certificate of veterinary inspection, or when two counselors finalize adoptions for the same dog forty seconds apart, nobody discovers the problem until it has already produced a legal exposure or an unfundable invoice. This document specifies the single API that replaces all of it.

The system tracks an animal from the moment it is registered — before it has been taken into custody at all — through intake and the statutory stray hold, through veterinary work funded by earmarked money, through multi-leg relay transport with driver handoffs at hubs, through foster placement and foster-to-foster transfer, through adoption screening and fee assessment, and finally to a recorded outcome that either counts toward the organization's live-release rate or does not. Along the way it must also handle the reversals: an adopter who brings the animal back inside the return window, a relay leg that aborts mid-route and strands its passengers at a hub, a transport run that gives back the partner-rescue slots it had drawn, a donation whose designated animal has left the system and whose residual must be released to unrestricted funds.

Two design commitments run through everything that follows. First, **custody posture is layered and ordered**: a records freeze, a closed outcome, and three independent kinds of hold each block a different, deliberately asymmetric set of operations, and when several of them apply at once the observable rejection is decided by a fixed gate order rather than by which rule feels most specific to the caller. Second, **every quantity that moves is conserved**: donated cents, foster home slots, partner transfer slots, crate units on a leg, adoption fee components, and custody episodes each obey an identity that must hold after every single mutation. An implementation that gets the happy paths right but drifts on either commitment has not implemented this system.

## 2. Global Specifications & System-Wide Principles

All resources are mounted under the `/rescue` prefix.

### 2.1. User and Role-Based Access Control

Every request to every endpoint — reads included — must carry two headers: `X-User-ID`, identifying the actor, and `X-User-Role`, naming the role the actor is acting in. If either header is absent or is present but empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If `X-User-Role` carries a string that is not one of the eleven role names below, the request is likewise rejected with `ERR_UNAUTHENTICATED` — an unrecognised role is treated as a failure to authenticate, not as a permission problem. Only once the role is recognised does the system ask whether that role is listed as authorised for the endpoint being called; when it is not, the answer is `ERR_UNAUTHORIZED` (HTTP 403).

The eleven roles are `PlatformAdmin`, `IntakeOfficer`, `FosterCoordinator`, `AdoptionCounselor`, `TransportDispatcher`, `Driver`, `Veterinarian`, `FinanceOfficer`, `FosterParent`, `Adopter`, and `PartnerRescue`.

`PlatformAdmin` is the superset operator and appears on the authorised-role list of every endpoint in the system; three operations are reachable by no other role — registering an organization, raising or lifting an organization's records freeze, and setting the server's logical clock. `IntakeOfficer` takes animals into custody, records identification, processes owner reclaims and writes outcome records. `FosterCoordinator` owns the foster pipeline: homes, applications, home checks, placements, activations, endings and transfers. `AdoptionCounselor` screens adoption applications, finalizes adoptions and processes adopter returns. `TransportDispatcher` plans runs and legs, manifests animals onto legs, bumps them off again, aborts runs and legs, administers partner commitments, and grants litter split approval. `Veterinarian` orders and completes medical work and issues health certificates. `FinanceOfficer` records contributions and redesignates unapplied gifts. `Driver`, `FosterParent`, `Adopter` and `PartnerRescue` are the outward-facing roles and are constrained to their own records.

Six of the roles are **opaque identities**. When `X-User-Role` is `PlatformAdmin`, `IntakeOfficer`, `FosterCoordinator`, `AdoptionCounselor`, `TransportDispatcher`, `Veterinarian` or `FinanceOfficer`, the `X-User-ID` value is an operator identifier that is not tied to any persisted row. The server records it where a workflow demands an audit trail — as `released_by_user_id` when a hold is released, as `decided_by_user_id` when a foster application is decided, as `screened_by_user_id` when an adoption application is screened, and as `finalized_by_user_id` when an adoption is finalized — but it never compares that value to any entity's `id` and never requires it to resolve to a row.

The remaining four roles are **entity-backed**, and for them `X-User-ID` must resolve to a real row before anything else about the request is considered beyond role recognition and endpoint authorisation. When `X-User-Role` is `Driver`, `FosterParent` or `Adopter`, `X-User-ID` is the `id` of the acting `Person`; when it is `PartnerRescue`, `X-User-ID` is the `id` of the acting `Organization`. If that lookup fails, the request is rejected with `ERR_PERSON_NOT_FOUND` (HTTP 404). Ownership is then enforced by comparing `X-User-ID` to the foreign key on the resource being touched: a `Driver` may act only on a `TransportLeg` whose `driver_person_id` equals `X-User-ID`; a `FosterParent` may act only on a `FosterApplication` whose `person_id` equals `X-User-ID` and on a `FosterHome` whose `person_id` equals `X-User-ID`, together with the placements belonging to that home; an `Adopter` may act only on an `AdoptionApplication` whose `applicant_person_id` equals `X-User-ID` and on an `Adoption` whose `adopter_person_id` equals `X-User-ID`; and a `PartnerRescue` may read only a `PartnerCommitment` whose `organization_id` equals `X-User-ID`, together with the runs drawing on it and its own organization record. An entity-backed actor reaching for someone else's record is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Segregation of duties is a first-class rule and `PlatformAdmin` is not exempt from it. The actor whose `X-User-ID` screened an adoption application to `APPROVED` may not be the actor who later finalizes that application into an `Adoption`, whatever role either of them holds.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two optional query parameters. `limit` defaults to 10, may be no smaller than 1 and no larger than 100. `offset` defaults to 0 and may be no smaller than 0. A `limit` outside the inclusive range 1 to 100, or a negative `offset`, is a validation failure carrying `ERR_VALIDATION` (HTTP 400); the bounds are inclusive at both ends, so a `limit` of exactly 1 and a `limit` of exactly 100 are both accepted.

Unless a subsection below states otherwise, list results are ordered by `created_at` ascending. The `meta` block of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the number of rows matching the filters before the limit and offset are applied, and `has_more` is true exactly when rows remain beyond the current page.

Filters supplied as query parameters are combined conjunctively — a request naming both a species and a status returns only rows matching both. A filter naming a value that no row carries returns an empty array with a `total_count` of zero, not an error.

### 2.4. Record Identity, Timestamps, Versioning and the Logical Clock

Every resource in the system carries a server-minted `id` — a UUID string with no type prefix of any kind — and a `created_at` timestamp in ISO 8601 UTC with three fractional digits. Every entity in this system also carries an `updated_at` timestamp in the same format and an integer `version`; there are no exceptions, so no entity is missing either field. `version` begins at 1 when the row is created and increases by exactly 1 on each mutation of that row, and `updated_at` is refreshed to the clock instant of the mutation whenever `version` moves. Where a workflow mutates a row more than once — as adoption finalization does when it both writes the fee breakdown and closes the custody episode — the `version` reflects each mutation step that the narrative in §3 attributes to that row, not one bump per HTTP request.

Where a path names a resource — the `{id}` segment of any nested route — the resources are resolved strictly left to right, so a request naming a non-existent parent and a non-existent child reports the parent's absence. §2.11 fixes which error code each entity's absence produces.

The server runs on a **logical clock**, never on wall-clock time. Before any caller sets it, the clock reads exactly `2026-05-01T00:00:00Z`. An administrative test-driving capability sets it to a supplied `to_iso8601` instant and answers with the new `current_utc`; the clock never falls back to real time under any circumstance. Every derived, time-sensitive posture in the system — the latching of a stray hold to `HOLD_EXPIRED`, the lapsing of a foster home check from `PASSED` to `LAPSED`, the expiry of a health certificate, the age of an animal, the length of a custody stay, the return window on an adoption, and the expiry of a partner commitment — is evaluated against this logical clock on the next read or write that touches the affected row. The clock endpoint is the only write in the system that is exempt from the records-freeze gate alongside the freeze toggle itself.

### 2.5. Rejection Precedence: One Global Ladder

When a request violates several rules at once, exactly one error is observable, and which one it is must not depend on implementation order. The system therefore evaluates a single global ladder of 45 rungs in a fixed sequence, and the first rung that fails determines the response. The ladder is stated here once in full; the individual conditions are described where the workflows they guard are described.

1. Both authentication headers are present and non-empty — otherwise `ERR_UNAUTHENTICATED`.
2. `X-User-Role` names one of the eleven roles — otherwise `ERR_UNAUTHENTICATED`.
3. The acting role appears on the endpoint's authorised list — otherwise `ERR_UNAUTHORIZED`.
4. For an entity-backed actor, `X-User-ID` resolves to an existing row of its backing entity — otherwise `ERR_PERSON_NOT_FOUND`. This rung applies to every endpoint reachable by `Driver`, `FosterParent`, `Adopter` or `PartnerRescue`.
5. An entity-backed actor owns the resource it is acting on, per the ownership comparisons in §2.1 — otherwise `ERR_UNAUTHORIZED`. Same scope as rung 4.
6. The body parses as JSON, every required input field for the endpoint is present, and every field carries the declared JSON type — otherwise `ERR_VALIDATION`. Applies to every write.
7. Every enum-typed input field on the closed list in §2.9 carries a declared member — otherwise `ERR_INVALID_ENUM`.
8. Numeric and format constraints hold — otherwise `ERR_VALIDATION`. Applies to every create and update.
9. Pagination parameters are within bounds — otherwise `ERR_VALIDATION`. Applies to every list endpoint.
10. Every resource named in the path exists, checked left to right — otherwise the not-found code from the entity map in §2.11.
11. Every foreign key in the request body resolves to an existing row, checked in the order the fields are listed for that endpoint — otherwise the not-found code from the same entity map.
12. **Gate 1** — the owning organization is not under a records freeze — otherwise `ERR_RECORDS_FROZEN`.
13. **Gate 2** — the target animal's custody is not already closed by a standing outcome — otherwise `ERR_ANIMAL_OUTCOME_CLOSED`.
14. **Gate 3** — no active legal hold restrains the target animal — otherwise `ERR_LEGAL_HOLD_ACTIVE`.
15. **Gate 4** — no active medical hold restrains the target animal — otherwise `ERR_MEDICAL_HOLD_ACTIVE`.
16. **Gate 5** — no active behavioural hold restrains the target animal — otherwise `ERR_BEHAVIORAL_HOLD_ACTIVE`.
17. The supplied expected-version field equals the parent's current `version` — otherwise `ERR_STALE_VERSION`.
18. The target's own state machine declares a transition out of its current state for this trigger — otherwise `ERR_INVALID_STATE`. This rung governs every action endpoint **except** recording identification, whose hold-axis precondition is instead evaluated at rung 21; without that carve-out rung 21 could never be reached.
19. Cross-entity parent state on transport: the parent run is `IN_PROGRESS` before a leg may depart or arrive, and `PLANNED` before a leg may be added — otherwise `ERR_INVALID_STATE`.
20. Cross-entity application state on fostering: the linked foster application is `APPROVED` and its requested species equals the animal's species — otherwise `ERR_INVALID_STATE`.
21. A stray-hold extension is applied only while the animal's current custody episode is still `HOLD_ACTIVE` — otherwise `ERR_HOLD_ALREADY_EXPIRED`.
22. Segregation of duties on adoption finalization — otherwise `ERR_SEGREGATION_OF_DUTIES`.
23. The animal's stray hold has expired before an adoption may be finalized — otherwise `ERR_STRAY_HOLD_NOT_EXPIRED`.
24. The applicant's household satisfies the animal's placement restrictions — otherwise `ERR_HOUSEHOLD_MISMATCH`.
25. The receiving foster home satisfies the animal's restrictions — otherwise `ERR_FOSTER_RESTRICTION_VIOLATION`.
26. The leg's species and temperament policy admits the candidate animal — otherwise `ERR_SPECIES_INCOMPATIBLE_LEG`.
27. Rabies age eligibility holds for every animal on an interstate departure — otherwise `ERR_RABIES_AGE_NOT_MET`.
28. Alteration compliance holds at adoption finalization — otherwise `ERR_ALTERATION_REQUIRED`.
29. The linked foster application's home check is current — otherwise `ERR_HOME_CHECK_NOT_CURRENT`.
30. The adoption application has attempts left — otherwise `ERR_APPLICATION_ATTEMPT_LIMIT`.
31. Littermate grouping is respected — otherwise `ERR_LITTER_SPLIT_NOT_APPROVED`.
32. Every manifested animal's species matches the partner commitment's species — otherwise `ERR_PARTNER_SPECIES_MISMATCH`.
33. Every explicitly named funding contribution is category-eligible — otherwise `ERR_RESTRICTED_FUND_CATEGORY_MISMATCH`.
34. Every animal on an interstate departure has a certificate for the destination state — otherwise `ERR_CVI_REQUIRED`.
35. That governing certificate is still valid at the leg's scheduled departure — otherwise `ERR_CVI_EXPIRED`.
36. Relay sequencing: all lower-sequence legs have arrived — otherwise `ERR_LEG_SEQUENCE_VIOLATION`.
37. The driver's interval occupancy admits the candidate leg — otherwise `ERR_DRIVER_LEG_OVERLAP`.
38. The adoption return falls inside the outer return window — otherwise `ERR_RETURN_WINDOW_CLOSED`.
39. The linked partner commitment has not expired — otherwise `ERR_PARTNER_COMMITMENT_UNAVAILABLE`.
40. The leg's crate capacity admits the candidate — otherwise `ERR_LEG_CRATE_CAPACITY_EXCEEDED`.
41. The leg's weight capacity admits the candidate — otherwise `ERR_LEG_WEIGHT_CAPACITY_EXCEEDED`.
42. The foster home's species slot capacity admits the placement — otherwise `ERR_FOSTER_CAPACITY_EXCEEDED`.
43. The foster home's head count admits the placement — otherwise `ERR_FOSTER_HEADCOUNT_EXCEEDED`.
44. The partner commitment has enough open slots for the run — otherwise `ERR_PARTNER_COMMITMENT_UNAVAILABLE`.
45. The eligible contribution pool covers the medical cost in full — otherwise `ERR_INSUFFICIENT_RESTRICTED_FUNDS`.

Three consequences of this ordering deserve emphasis because they are counter-intuitive. A request that is both malformed and blocked by a gate reports the malformation, because body validation sits above the gates. A request that is both gate-blocked and version-stale reports the gate, because the gates sit above the version check. And a request that would fail both a business-safety rule and a capacity limit reports the safety rule, because safety rungs 24 to 28 sit above the capacity rungs 40 to 43.

### 2.6. The Five Ordered Custody Gates

Rungs 12 through 16 are not ordinary business rules. They are **custody gates**: coarse postures that pre-empt every ordinary rule below them within their own declared scope. Each gate has a deliberately different scope from the others, so that no gate makes a later gate unreachable, and the scopes are asymmetric on purpose — a hold that blocks adoption does not necessarily block transport, and a hold that blocks transport does not necessarily block a reclaim.

**Gate 1 — records freeze.** An `Organization` carries a `records_freeze_active` flag, mirrored on a state axis called `freeze_status` whose members are `UNFROZEN` and `FROZEN`. While the flag is raised on the organization that owns the target resource, every create, update and delete under `/rescue` is rejected with `ERR_RECORDS_FROZEN` (HTTP 409). Only two writes are exempt: the freeze toggle itself, so that the freeze can be lifted, and the logical clock setter. Reads are never gated — an organization under freeze remains fully readable, which is the point of a freeze during litigation or audit. The owning organization for an animal-scoped resource is the animal's `current_organization_id`, reached through the target's animal where the target is not the animal itself.

**Gate 2 — outcome closed.** An animal whose custody episode has been closed by an `OutcomeRecord` that has not been reversed sits in `lifecycle_status` `OUTCOME_CLOSED`, and further writes against it are rejected with `ERR_ANIMAL_OUTCOME_CLOSED` (HTTP 409). This gate covers exactly twelve operations: opening a new custody episode, imposing a hold, ordering a medical record, issuing a health certificate, proposing a foster placement, manifesting the animal onto a transport leg, submitting an adoption application, finalizing an adoption, recording an outcome, processing an owner reclaim, updating the animal's placement restrictions, and recording identification. Notably it does **not** cover completing an already-ordered medical record, releasing a hold, or any transport action other than manifesting.

**Gate 3 — legal hold.** An `ACTIVE` `HoldRecord` whose `hold_type` is `LEGAL` blocks transport and disposition writes only, with `ERR_LEGAL_HOLD_ACTIVE` (HTTP 409). Its scope is exactly: manifesting the animal onto a leg, departing a leg (evaluated per manifested animal, so one restrained animal blocks the whole departure), finalizing an adoption, transferring a foster placement to another home, processing an owner reclaim, and recording an outcome whose `outcome_type` is `ADOPTION`, `TRANSFER_OUT` or `RETURN_TO_OWNER`. Recording a non-live outcome is not blocked by a legal hold.

**Gate 4 — medical hold.** An `ACTIVE` `HoldRecord` whose `hold_type` is `MEDICAL` blocks exactly two operations — finalizing an adoption and transferring a foster placement to another home — with `ERR_MEDICAL_HOLD_ACTIVE` (HTTP 409). A medical hold never blocks an owner reclaim and never blocks transport.

**Gate 5 — behavioural hold.** An `ACTIVE` `HoldRecord` whose `hold_type` is `BEHAVIORAL` blocks exactly one operation — finalizing an adoption — with `ERR_BEHAVIORAL_HOLD_ACTIVE` (HTTP 409). A behavioural hold never blocks transport, never blocks a foster transfer, and never blocks a reclaim.

Because the gates are ordered, an animal carrying an active legal hold **and** an active medical hold **and** an active behavioural hold, whose adoption someone attempts to finalize, is rejected with `ERR_LEGAL_HOLD_ACTIVE` and nothing else. Releasing that legal hold surfaces `ERR_MEDICAL_HOLD_ACTIVE`; releasing that in turn surfaces `ERR_BEHAVIORAL_HOLD_ACTIVE`. Peeling gates one at a time is the intended operator experience.

> **Open point (gate 1 scope).** The freeze gate's scope is declared as every create, update and delete under `/rescue` other than the two exempt writes, but its condition resolves the owning organization only through the target's animal. Two readings are therefore available for writes whose target reaches no animal at all — registering a person, registering a foster home, submitting a foster application, recording a contribution, registering a partner commitment, running the commitment expire sweep. Reading A: the gate can only fire where an owning organization is reachable, so these writes are never frozen. Reading B: the gate applies to the full declared scope, resolving the organization through whatever organization-bearing field the target carries (`organization_id` on a partner commitment, `origin_organization_id` on a transport run) and treating a target with no organization at all as ungated. This PRD does not choose between them; the implementation must pick one and apply it consistently.

### 2.7. Version Pinning on Capacity-Bearing Parents

Three writes in this system compute their outcome from a **capacity view of a parent record** that another actor may have changed since the caller last read it. For those three, and only those three, the request body carries a non-optional expected-version field naming the caller's last observed `version` of that parent. If the value does not equal the parent's current `version` at the moment the request is evaluated, the write is rejected with `ERR_STALE_VERSION` (HTTP 412) at rung 17, and nothing is mutated.

- Finalizing an adoption requires `expected_animal_version`, carrying the caller's last observed `version` of the `Animal` being adopted. Several applications may legitimately stand `APPROVED` on one animal and any of them may legitimately be the one finalized, so no state precondition on the animal alone can decide which finalize is authoritative — the version comparison is what decides it. If a hold, a restriction update, or any other write has advanced the animal's `version` since the counselor read it, the finalize is refused rather than being computed against a posture the counselor never saw.
- Manifesting an animal onto a transport leg requires `expected_leg_version`, carrying the caller's last observed `version` of the `TransportLeg`. Two dispatchers may each legitimately add a different animal to the same leg, so no state precondition covers the second write; the version comparison pins the remaining-crate-and-weight view the request was computed against.
- Proposing a foster placement requires `expected_foster_home_version`, carrying the caller's last observed `version` of the receiving `FosterHome`. Multiple placements into one home are entirely legitimate, so again no state precondition covers the second create; the version comparison pins the free-slot view.

No other endpoint accepts or requires any expected-version field. Supplying one elsewhere has no meaning and confers no protection.

### 2.8. Money, Slots, Precision and Rounding

All monetary amounts in this system are whole integer cents. There are no fractional cents anywhere, in storage or in any response. Wherever a percentage, a multiplier or a proportional share produces a non-integer intermediate, the result is rounded **half up** to a whole cent — a value exactly at the half boundary rounds away from zero, upward.

Where a calculation applies rounding more than once, the **order of rounding is part of the specification and is not interchangeable with an equivalent-looking alternative**. Two places in particular depend on it. When a repeat-offense multiplier is applied during an owner reclaim, the multiplier acts on the impound subtotal alone and the product is rounded before the flat base reclaim fee is added — never the other way round, and never with the base fee included in the multiplication. When administrative overhead is charged against a medical funding draw, the overhead percentage is applied and rounded **once per draw line** and the rounded lines are then summed — summing the lines first and rounding the total once produces a different number and is incorrect.

Weight utilisation on a transport leg is carried to two decimal places, rounded half up, and the capacity comparison is inclusive: a leg is accepted when the resulting used weight is exactly equal to the leg's capacity.

The live-release rate is a ratio, not a money value, and is rounded half up to **four** decimal places.

Slot arithmetic — foster home slots, foster head counts, partner commitment slots and crate units on a leg — is entirely integral. There is no rounding on any slot quantity.

Age arithmetic is deliberately calendar-free. Elapsed whole days between two instants are computed by taking the difference and discarding any fractional day; the animal's `age_weeks` is that whole-day count divided by 7 and rounded down to an integer, and its `age_months` is that same whole-day count divided by 30 and rounded down to an integer. No derivation in this system uses calendar months or leap-year arithmetic, so a month is always exactly 30 days and a year is never a special case.

### 2.9. Enumerations and Enum Error Routing

The system distinguishes two kinds of bad input value. A value that is structurally wrong — missing, of the wrong JSON type, out of numeric range, a malformed state code, a malformed email, an unparseable timestamp — is `ERR_VALIDATION` (HTTP 400). A value that is well-formed but is not a declared member of its enumeration is `ERR_INVALID_ENUM` (HTTP 400), and enum routing is checked at rung 7, above the numeric and format constraints at rung 8.

`ERR_INVALID_ENUM` routes **exactly** the following input fields and no others: `org_type` and `default_methodology` on an organization; `housing_type` on a person; `species`, `size_class` and `temperament` on an animal, together with each element of `restriction_housing_types_excluded`; `intake_type` and `impound_billing_basis` on an intake record; `hold_type` on a hold; `species_requested` on a foster application; `count_basis` on a foster placement; `procedure_type` and `expense_category` on a medical record; `run_type` and `purpose` on a transport run; `species_policy` on a transport leg; `credit_application_order`, `refund_basis` and `deposit_basis` on an adoption; `outcome_type` on an outcome record; `designated_program` and `restriction_category` on a contribution; `species` on a partner commitment; the `decision` field on the two decision-taking endpoints (foster application decision and adoption application screening); the `result` field on the home-check endpoint; the `action` field on the foster application status-change endpoint; the `reason` field on the placement-end endpoint; and the `methodology` query parameter on the live-release report. **No other field routes to `ERR_INVALID_ENUM`** — every other malformed value routes to `ERR_VALIDATION`, at rung 6 if it is missing or of the wrong type and at rung 8 if it is present, well-typed and out of range.

The declared members are: organization `org_type` — `SHELTER`, `PARTNER_RESCUE`; organization `default_methodology` and the report's `methodology` — `SAC`, `ASILOMAR`; person and restriction `housing_type` — `APARTMENT`, `CONDO`, `HOUSE`, `FARM`; animal `species`, foster application `species_requested` and partner commitment `species` — `DOG`, `CAT`, `OTHER`; animal `size_class` — `SMALL`, `MEDIUM`, `LARGE`; animal `temperament` — `SOCIAL`, `REACTIVE`, `UNKNOWN`; `intake_type` — `STRAY`, `OWNER_SURRENDER`, `CONFISCATE`, `TRANSFER_IN`, `RETURN`; `impound_billing_basis` — `CALENDAR_DAY`, `OVERNIGHT`; `hold_type` — `MEDICAL`, `BEHAVIORAL`, `LEGAL`; `count_basis` — `INDIVIDUAL`, `NURSING_UNIT`; `procedure_type` — `EXAM`, `VACCINE_RABIES`, `SPAY_NEUTER`, `TREATMENT`; `expense_category` — `MEDICAL`, `SPAY_NEUTER`, `VACCINE`; `run_type` — `RESCUE_LEG`, `RELAY`; run `purpose` — `INTAKE_TRANSPORT`, `TRANSFER_OUT`; `species_policy` — `DOGS_ONLY`, `CATS_ONLY`, `MIXED_SEGREGATED`, `ANY`; `credit_application_order` — `CREDIT_FIRST`, `WAIVER_FIRST`; `refund_basis` — `FEE_PAID`, `FEE_ASSESSED`; `deposit_basis` — `FLAT`, `AGE_SCALED`; `outcome_type` — `ADOPTION`, `FOSTER_TO_ADOPT`, `TRANSFER_OUT`, `RETURN_TO_OWNER`, `EUTHANASIA_MEDICAL`, `EUTHANASIA_BEHAVIORAL`, `EUTHANASIA_OWNER_REQUESTED`, `DIED_IN_CARE`, `LOST_IN_CARE`; `designated_program` — `NONE`, `ADOPTION_FEE_ASSISTANCE`, `TRANSPORT_FUND`, `MEDICAL_FUND`; `restriction_category` — `UNRESTRICTED`, `MEDICAL`, `SPAY_NEUTER`, `VACCINE`, `TRANSPORT`; `decision` — `APPROVE`, `DECLINE`; `result` — `PASS`, `FAIL`; `action` — `SUSPEND`, `RESUME`, `WITHDRAW`; and the placement-end `reason` — `RETURNED_TO_SHELTER`, `CANCELLED_BEFORE_START` only.

The numeric and format constraints checked at rung 8 are these: every cents amount and every count is at least 0; a contribution's `amount_cents` is strictly greater than 0; an animal's `weight_lb` is strictly greater than 0; a leg's `crate_capacity_units` is at least 1 and its `weight_capacity_lb` is strictly greater than 0; a leg's `sequence_no` is at least 1; a foster home's `max_headcount` is at least 1; a partner commitment's `slots_total` is at least 1; `state_code`, `destination_state` and `destination_state_code` are exactly two uppercase letters; an `email` contains an at-sign; every datetime parses as an ISO 8601 UTC instant; and a leg's `scheduled_arrive_at` is strictly after its `scheduled_depart_at`.

### 2.10. Conservation Identities

Six identities must hold after every successful mutation. They are not reporting conveniences; they are the correctness contract of the ledgers, and any workflow described in §3 that appears to break one has been misread.

1. **Custody episodes.** The number of intake records that are not `VOIDED` equals the number of outcome records that have not been reversed, plus the number of animals whose `lifecycle_status` is `IN_CUSTODY`, `IN_TRANSIT` or `STRANDED`. An adopter return both reverses an outcome and opens a new episode while voiding the superseded one, so the identity survives the compensating pair.
2. **Donated cents.** For every contribution, `amount_cents` equals `applied_cents` plus `released_cents` plus `available_cents`.
3. **Foster slots.** For every foster home, `consumed_dog_slots` plus `consumed_cat_slots` equals the sum of `slot_consumption` over that home's `ACTIVE` placements.
4. **Partner slots.** For every partner commitment, `slots_total` equals `slots_drawn` plus `slots_released` plus `slots_open`.
5. **Crate units.** For every transport leg, `used_crate_units` equals the sum of `crate_units` over that leg's manifest entries whose status is `ASSIGNED`, `LOADED` or `DELIVERED`; `BUMPED` and `STRANDED` entries are excluded.
6. **Adoption fee components.** For every adoption, `base_fee_cents` equals `sponsorship_applied_cents` plus `waiver_applied_cents` plus `adopter_charged_cents`. The deferred-alteration deposit is tracked separately and is deliberately **not** part of this identity.

### 2.11. Path Resolution and the Not-Found Entity Map

When a path segment or a body foreign key names a row that does not exist, the error code is fixed by the following closed map and by nothing else — not by which endpoint was called, and not by which role called it.

`Organization` yields `ERR_ORGANIZATION_NOT_FOUND`. `Person` yields `ERR_PERSON_NOT_FOUND`, which covers `person_id`, `source_person_id`, `donor_person_id`, `applicant_person_id`, `driver_person_id`, `reclaiming_person_id` and `counterparty_person_id`. `Animal` yields `ERR_ANIMAL_NOT_FOUND`. `Litter` yields `ERR_LITTER_NOT_FOUND`. `IntakeRecord` yields `ERR_INTAKE_RECORD_NOT_FOUND`, which is also the code used when an operation requires the animal's currently open custody episode and no such episode exists. `HoldRecord` yields `ERR_HOLD_NOT_FOUND`. `FosterHome` yields `ERR_FOSTER_HOME_NOT_FOUND`, covering both `foster_home_id` and `destination_foster_home_id`. `FosterApplication` yields `ERR_FOSTER_APPLICATION_NOT_FOUND`, covering both `foster_application_id` and `destination_foster_application_id`. `FosterPlacement` yields `ERR_FOSTER_PLACEMENT_NOT_FOUND`. `MedicalRecord` and `HealthCertificate` share `ERR_MEDICAL_RESOURCE_NOT_FOUND`. `TransportRun`, `TransportLeg` and `ManifestEntry` share `ERR_TRANSPORT_RESOURCE_NOT_FOUND`. `AdoptionApplication`, `Adoption` and `OutcomeRecord` share `ERR_ADOPTION_RESOURCE_NOT_FOUND`. `Contribution` and `PartnerCommitment` share `ERR_FUNDING_RESOURCE_NOT_FOUND`. All of these carry HTTP 404.

> **Open point (identity resolution for a partner organization).** Rung 4 resolves an entity-backed actor's `X-User-ID` against its backing entity and declares its rejection as `ERR_PERSON_NOT_FOUND`, but the `PartnerRescue` role is backed by `Organization`, not by `Person`. Two readings follow. Reading A: rung 4 emits `ERR_PERSON_NOT_FOUND` for every entity-backed role including `PartnerRescue`, exactly as the rung declares. Reading B: the backing entity decides via the closed map above, so a `PartnerRescue` actor whose `X-User-ID` names no organization is rejected with `ERR_ORGANIZATION_NOT_FOUND`. This PRD does not choose between them.

## 3. Business Logic & Workflows

### 3.1. Building the Register: Organizations, People, Animals and Litters

A `PlatformAdmin` seeds the network by registering organizations. Each carries a legal `name`, an `org_type` distinguishing a `SHELTER` that holds animals from a `PARTNER_RESCUE` that receives transfers, and a two-letter `state_code` that later drives whether a transport leg counts as interstate. An optional `default_methodology` — `SAC` when omitted — records which live-release accounting convention this organization prefers, and is the convention used when a live-release report is requested without naming one explicitly. A newly registered organization starts `UNFROZEN` on its `freeze_status` axis with `records_freeze_active` false, `records_freeze_reason` null, and all three of its running ledgers — `unrestricted_balance_cents`, `restricted_balance_cents` and `open_commitment_slots_total` — at zero.

Raising and lifting the records freeze is a `PlatformAdmin`-only capability that toggles that axis and is available repeatedly: an organization may cycle `UNFROZEN → FROZEN → UNFROZEN → FROZEN` as often as litigation demands. The call carries `freeze_active`, a boolean, and an optional `reason`. A freeze may only be raised from `UNFROZEN`, and it demands a non-empty `reason` string, which is stored as `records_freeze_reason`. A lift may only be applied from `FROZEN`; `records_freeze_reason` is deliberately **retained** across the lift, so an organization that has ever been frozen keeps the text of its most recent freeze forever. Either direction increments the organization's `version` by one. Attempting to freeze an organization already `FROZEN`, or to lift a freeze on one already `UNFROZEN`, matches no declared transition and is rejected with `ERR_INVALID_STATE`.

> **Open point (missing freeze reason).** A `reason` is an optional field on the freeze call, yet raising a freeze declares a non-empty `reason` as a precondition of the `UNFROZEN → FROZEN` transition. A freeze request with `freeze_active` true and no `reason`, or an empty one, therefore admits two readings. Reading A: the absent value is a body-level failure and reports `ERR_VALIDATION` at rung 6. Reading B: the value is present-but-inadequate at the state-machine level and reports `ERR_INVALID_STATE` at rung 18. This PRD does not choose between them.

People are the network's counterparties: surrendering owners, finders, adopters, foster parents, drivers and donors are all the same kind of record. Creating one requires a `full_name` and an `email` containing an at-sign. Everything else is optional and defaulted, and the defaults are chosen so that a bare person record is maximally permissive. `youngest_child_age_years` defaults to 99, which by convention means *no resident children at all* rather than a household of centenarian toddlers; `resident_cat_count` and `resident_dog_count` default to 0; `housing_type` defaults to `HOUSE`; `has_fenced_yard` defaults to false; `hardship_certified` defaults to false and is the precondition for the reclaim hardship waiver described in §3.2; and `driver_license_number` defaults to null. That last field matters operationally: a person may not be named as the driver of a transport leg until a licence identifier has been recorded. Finally, every new person starts with `reclaim_history_count` at 0 — a derived counter, described in §3.2, that drives the repeat-offense multiplier.

Animals are registered **before** intake, and start in `lifecycle_status` `PRE_INTAKE`. A registration supplies a shelter `name`, a `species`, a `size_class`, a `weight_lb` in pounds, a `date_of_birth` as an ISO 8601 UTC instant, and a `current_organization_id` naming the organization that will hold legal custody. Optional at registration are `temperament`, which defaults to `UNKNOWN`; `microchip_id`, which defaults to null; a `litter_id` naming the litter this animal belongs to; and the five placement restrictions, which default to their permissive values — `restriction_no_children_under_years` 0 (meaning no age restriction), `restriction_no_cats` false, `restriction_no_dogs` false, `restriction_requires_fenced_yard` false, and `restriction_housing_types_excluded` an empty array. Registration derives `identifiable` as true exactly when `microchip_id` is non-null, and where a `litter_id` was supplied it raises that litter's `member_count` by one. The animal's other derived fields start empty: `current_foster_home_id`, `current_intake_record_id`, `current_hub_code` and `rabies_vaccinated_at` are all null, `alteration_status` is `NOT_ALTERED`, and `length_of_stay_days` is 0.

Two derived ages accompany every animal read. `age_weeks` and `age_months` are both computed from the whole elapsed days between `date_of_birth` and the logical clock, divided by 7 and 30 respectively and rounded down, exactly as §2.8 describes. `length_of_stay_days` is the whole elapsed days between the intake instant of the animal's currently open custody episode and the logical clock, rounded down; when `current_intake_record_id` is null it is 0 rather than absent.

Placement restrictions can be revised after a behaviour evaluation, by an `IntakeOfficer`, an `AdoptionCounselor` or a `PlatformAdmin`. All five restriction fields are individually optional on that update; those supplied replace their prior values, those omitted are left alone, and the animal's `version` increments by one. Because the update targets an animal, it is subject to the outcome-closed gate: revising restrictions on an animal whose custody is already closed is refused with `ERR_ANIMAL_OUTCOME_CLOSED`.

Recording identification is a separate operation carrying `microchip_id` and a boolean `extend_stray_hold`, both required. It always sets the animal's `microchip_id` and marks `identifiable` true, and it always increments the animal's `version` by one. When `extend_stray_hold` is true, it additionally reaches into the animal's currently open custody episode and lengthens the stray hold — see §3.2 for the recomputation and for the latch that can refuse it. This is the one action endpoint that is exempt from the generic state-transition rung; its own hold-axis precondition is evaluated further down the ladder instead, so that its dedicated rejection code can actually be observed.

A read-only **eligibility view** is available for any animal, and it is the operational answer to "why can't I do this?". It reports the animal's `animal_id` and `lifecycle_status`; the stray hold posture as `stray_hold_status` and `stray_hold_expires_at`; the five gate conditions as `records_freeze_active`, `outcome_closed`, `legal_hold_active`, `medical_hold_active` and `behavioral_hold_active`; and three roll-ups naming the first gate that would block each of the three most contested operations — `adoption_blocked_by`, `transport_blocked_by` and `foster_transfer_blocked_by`. Each roll-up names the highest-precedence gate in that operation's scope that is currently firing, following the gate order of §2.6, and is null when nothing blocks. Consulting the eligibility view never mutates a gate, but like every read it does re-derive the clock-dependent postures described in §2.4.

Litters group siblings and are self-referential: a litter names an optional `dam_animal_id` pointing at the nursing dam, who is herself an animal whose own `litter_id` is null. A new litter carries a human `label`, starts with `transport_basis` `GROUPED` and `member_count` 0, and has `split_approved_at` null. Under `GROUPED` the whole litter must travel together and is billed a flat crate cost; a `TransportDispatcher` or `PlatformAdmin` may grant split approval, supplying an `approved_reason`, which moves `transport_basis` to `SPLIT_APPROVED`, stamps `split_approved_at` with the current clock instant, and increments the litter's `version` by one. From that point each littermate is billed individually and may ride a different leg. §3.6 covers what that changes in transport.

Animals may be listed with any combination of `species`, `lifecycle_status`, `litter_id`, `current_organization_id`, `current_foster_home_id` and `current_intake_record_id` filters. Litters may be listed filtered by `dam_animal_id` and `transport_basis`. Both accept `limit` and `offset`.

### 3.2. Intake, the Stray Hold Clock, and the Owner Reclaim

Taking an animal into custody opens a **custody episode** and moves the animal `PRE_INTAKE → IN_CUSTODY`. The episode carries the `animal_id`, an `intake_type` recording the legal basis, an `intake_datetime` marking the instant custody began, an optional `source_person_id` naming the surrendering owner, the finder, or the owner of record for a stray, and an optional `impound_billing_basis` that defaults to `CALENDAR_DAY` and is only ever consulted if this episode ends in a reclaim. The operation is refused when the animal already has an episode in `status` `OPEN` — an animal has at most one open episode at a time, and the animal's `current_intake_record_id` points at it.

The **stray hold** is the statutory period during which the animal cannot be adopted out because its owner may still come forward, and its length is selected entirely by the legal basis of the intake. An `OWNER_SURRENDER` carries no hold at all — zero days. A `RETURN`, meaning an animal coming back from a failed adoption, likewise carries zero days. A `TRANSFER_IN` from another organization carries one day. A `CONFISCATE` carries ten days. A `STRAY` carries **seven** days when the animal was identifiable at the moment of intake and only **three** when it was not — the microchipped animal's owner gets four extra days to find them. Whether the animal was identifiable is captured as `identifiable_at_intake`, a snapshot of the animal's `identifiable` flag taken as the episode is written, and it does not track later changes to the animal on its own. The selected day count is stored as `hold_days`, and `hold_expires_at` is the `intake_datetime` advanced by exactly that many 24-hour periods.

Alongside `hold_expires_at`, each episode carries a `hold_status` on a strictly **monotone** axis with two members, `HOLD_ACTIVE` and `HOLD_EXPIRED`. Any read or write that touches the episode while the logical clock has reached or passed `hold_expires_at` latches it to `HOLD_EXPIRED` — the boundary is inclusive, so a clock standing exactly at `hold_expires_at` yields `HOLD_EXPIRED`. Once latched it is permanent. No later event returns it to `HOLD_ACTIVE`: not a microchip registration, not a hold extension, not rewinding the logical clock. This latch is what makes the extension in §3.1 refusable — a stray-hold extension may only be applied while the episode is still `HOLD_ACTIVE`, is only meaningful on a `STRAY` episode whose `identifiable_at_intake` is still false, and once the latch has fired the extension is refused with `ERR_HOLD_ALREADY_EXPIRED` and the hold clock is not moved at all. When it is accepted, it flips `identifiable_at_intake` to true, recomputes `hold_days` to the seven-day identifiable figure, moves `hold_expires_at` correspondingly later, and increments the episode's `version` by one.

An episode's `status` axis runs `OPEN → CLOSED → VOIDED`. It closes when an outcome record is written for the episode, which stamps that outcome's `intake_record_id` with this episode and increments the episode's `version`. It is voided only when the outcome that closed it is later reversed by an adopter return, which supersedes the episode entirely and again increments its `version`; §3.9 explains why voiding is the compensating half that keeps the custody-episode conservation identity intact.

The **owner reclaim** is the path by which a stray goes home. An `IntakeOfficer` or `PlatformAdmin` supplies a `reclaiming_person_id`, and the system computes a four-step charge, writes it onto the episode, creates a `RETURN_TO_OWNER` outcome naming that person as `counterparty_person_id`, closes the episode, moves the animal to `OUTCOME_CLOSED`, raises the reclaiming person's `reclaim_history_count` by one, and increments the animal's `version` by one. A reclaim is blocked by an active legal hold, but — and this asymmetry is deliberate — never by a medical or behavioural hold. An owner may collect a sick or reactive dog.

The charge is assembled in a pinned order. First, **billable days** are counted, and which of two conventions applies is chosen by the episode's `impound_billing_basis`. Under `CALENDAR_DAY`, the count is the number of distinct UTC calendar dates touched by the stay, counting both the date of `intake_datetime` and the date of the current clock instant — so a stay that begins in the morning of one date and ends in the afternoon six dates later bills six days. Under `OVERNIGHT`, the count is the whole 24-hour periods elapsed between `intake_datetime` and the clock, rounded down, with a floor of one day — the same stay bills five. Either way the result is a whole number of at least one, stored as `impound_billable_days`.

Second, those days are priced through **marginal tiers**, not an average rate. The first three billable days are charged at 1500 cents each. Days four through seven — that is, up to four further days — are charged at 2500 cents each. Every day beyond the seventh is charged at 4000 cents. The sum is `impound_subtotal_cents`.

Third, a **repeat-offense multiplier** is selected from the reclaiming person's history. The count consulted is that person's `reclaim_history_count`, being the number of unreversed `RETURN_TO_OWNER` outcomes already naming them as counterparty, and it is read **before** the current reclaim is written — so a first-time owner sees zero and pays the base multiplier of 1.0, a second-time owner sees one and pays 1.5, and an owner with two or more prior reclaims pays 2.0. The selected value is stored as `repeat_offense_multiplier`.

Fourth, the **hardship waiver** is tested against the pre-waiver total. The multiplier is applied to `impound_subtotal_cents` alone — never to the base fee — and that product is rounded half up to whole cents. The flat base reclaim fee of 4500 cents, stored on the episode as `reclaim_base_fee_cents`, is then added to give the pre-waiver total. If that pre-waiver total is **at least** 20000 cents and the reclaiming person's `hardship_certified` flag is true, a flat waiver of 2000 cents applies and is stored as `hardship_waiver_cents`; otherwise `hardship_waiver_cents` is 0. The threshold comparison is inclusive, so a pre-waiver total of exactly 20000 cents qualifies. `reclaim_total_cents` is then the pre-waiver total less the waiver, floored at zero so it can never go negative. The order here matters and is not negotiable: the waiver test reads the pre-waiver total, never the final `reclaim_total_cents`, which would otherwise be circular.

All five fee fields — `reclaim_base_fee_cents`, `impound_billable_days`, `impound_subtotal_cents`, `repeat_offense_multiplier`, `hardship_waiver_cents` — plus `reclaim_total_cents` are null on an episode until a reclaim happens, and are written together when it does.

Custody episodes may be listed filtered by `animal_id`, `source_person_id`, `intake_type`, `status` and `hold_status`, and both the single read and the list re-derive the hold latch as they go.

### 3.3. Holds: Three Independent Restraints

A hold is a restraint imposed on an animal by an `IntakeOfficer`, a `Veterinarian` or a `PlatformAdmin`. It names a `hold_type` and a free-text `reason` recorded for audit, and it starts in `status` `ACTIVE` with `released_at` and `released_by_user_id` both null. The three hold types are independent axes, not a severity scale: an animal may simultaneously carry an active `MEDICAL`, an active `BEHAVIORAL` and an active `LEGAL` hold, and may carry several of the same type at once. What each type blocks is set out exhaustively in §2.6 and is deliberately asymmetric — legal restrains transport and disposition, medical restrains only adoption finalization and foster-to-foster transfer, behavioural restrains only adoption finalization.

Releasing a hold moves it `ACTIVE → RELEASED`, stamps `released_at` with the current clock instant and `released_by_user_id` with the acting `X-User-ID`, increments the hold's `version` by one, and causes that hold's gate to stop firing for the animal. A hold already `RELEASED` cannot be released again; there is no transition out of `RELEASED`, so the attempt is refused with `ERR_INVALID_STATE`. Because a gate only fires while at least one hold of its type is `ACTIVE`, an animal carrying two active legal holds must have both released before transport resumes.

Imposing a hold is itself subject to the outcome-closed gate — an animal whose custody has closed cannot acquire new restraints — but **releasing** a hold is not, so a hold left over on a closed animal can always be cleaned up. Holds may be read individually and listed with `animal_id`, `hold_type` and `status` filters.

### 3.4. The Foster Pipeline: Homes, Applications, Home Checks and Placements

A foster home is registered by a `FosterCoordinator` or `PlatformAdmin` against a `person_id` — the foster parent who owns it — with a human `label` and a required `max_headcount` of at least one. Species capacity is expressed as two separate optional numbers, `dog_slot_capacity` and `cat_slot_capacity`, each defaulting to 0, so a home registered without them can hold no animals at all until they are set. Three home-check-derived restrictions are also recorded: `accepts_cats`, defaulting to true, where false marks a no-cats household; `min_child_age_years`, defaulting to 99 with the same convention as a person's household — 99 means no resident children; and `has_fenced_yard`, defaulting to false. A new home starts with `consumed_dog_slots`, `consumed_cat_slots` and `consumed_headcount` all at zero and a `capacity_status` of `OPEN`.

A foster application binds a `person_id` to a `foster_home_id` for one `species_requested`, and it advances along **two entirely independent axes** that must not be conflated. The first, `application_status`, starts at `SUBMITTED` and covers the coordinator's judgement of the applicant. The second, `home_check_status`, starts at `NOT_SCHEDULED` and covers the physical inspection of the premises. Approving an application does not touch the home-check axis, and passing a home check does not touch the application axis. An `APPROVED` application may sit at `LAPSED`, and a `SUSPENDED` application may sit at `PASSED`; both combinations are legitimate and both are queryable, since applications may be listed filtered by `person_id`, `foster_home_id`, `application_status` and `home_check_status` independently.

On the application axis, a coordinator's decision carries a `decision` of `APPROVE` or `DECLINE`, moves `SUBMITTED → APPROVED` or `SUBMITTED → DECLINED` accordingly, records the acting `X-User-ID` as `decided_by_user_id` on both branches, and increments the application's `version` by one on both branches. `DECLINED` is terminal. An approved application may then be suspended, resumed or withdrawn through a status-change carrying an `action`. `SUSPEND` moves `APPROVED → SUSPENDED`; `RESUME` moves `SUSPENDED → APPROVED`; the pair may cycle indefinitely, and each direction increments `version` by one. `WITHDRAW` moves `APPROVED → WITHDRAWN` and is reserved to the applicant themself — a `FosterParent` whose `X-User-ID` equals the application's `person_id` — and is likewise a `version` increment. `WITHDRAWN` is terminal. Any action naming a transition that is not declared out of the current state — resuming an application that was never suspended, suspending one that is still `SUBMITTED` — is refused with `ERR_INVALID_STATE`.

On the home-check axis, recording a check carries a `result` of `PASS` or `FAIL` together with a `checked_at` instant. A `PASS` is accepted from `NOT_SCHEDULED`, from `FAILED` and from `LAPSED`; it sets `home_check_passed_at` to the supplied `checked_at`, sets `home_check_expires_at` to that instant advanced by 180 days, and increments `version` by one. A `FAIL` is accepted from `NOT_SCHEDULED`, from `PASSED` and from `LAPSED`; it clears both `home_check_passed_at` and `home_check_expires_at` back to null, and likewise increments `version` by one. Note the two gaps that follow from those precondition lists: a `PASS` recorded against an application already sitting at `PASSED`, and a `FAIL` recorded against one already sitting at `FAILED`, match no declared transition and are refused with `ERR_INVALID_STATE`.

Unlike the stray hold, the home-check clock is **not** monotone. A passed check lapses on its own: any read or write touching the application while the logical clock stands strictly later than `home_check_expires_at` moves it `PASSED → LAPSED`. The comparison is strict, so a check whose expiry instant exactly equals the clock is still current. A `LAPSED` check blocks new placements against that application but is fully recoverable — a fresh `PASS` moves it back to `PASSED` and restarts the 180-day window from the new `checked_at`. Contrast this deliberately with the hold latch of §3.2, which never recovers.

**Placements** are where the two axes and the home's capacity meet. Proposing a placement supplies an `animal_id`, a `foster_home_id`, a `foster_application_id` naming the approved application that authorises it, and the mandatory `expected_foster_home_version` described in §2.7. Optionally it supplies a `count_basis`, defaulting to `INDIVIDUAL`, and a `litter_id`, which is required when the basis is `NURSING_UNIT`. A proposal is created in `status` `PROPOSED` with `started_at`, `ended_at`, `end_reason` and `predecessor_placement_id` all null, computes and stores its `slot_consumption` and `headcount_consumption`, and increments the receiving home's `version` by one.

The two consumption figures are deliberately **not** proportional to one another. `slot_consumption` is 1 under `INDIVIDUAL` and a flat 2 under `NURSING_UNIT`, however many littermates the nursing unit actually contains. `headcount_consumption` is 1 under `INDIVIDUAL` and, under `NURSING_UNIT`, one for the dam plus the litter's `member_count`. A home can therefore be slot-open and head-full at the same time, which is exactly why the two capacity rejections are distinct codes. Which slot bucket is charged is decided by the animal's species: a `DOG` consumes dog slots, while a `CAT` **and** an `OTHER` both consume cat slots.

A home's counters are recomputed from scratch on every placement status change, and only `ACTIVE` placements count — `PROPOSED`, `ENDED`, `CANCELLED`, `TRANSFERRED` and `CONVERTED_TO_ADOPTION` rows all contribute nothing. `consumed_dog_slots` is the sum of `slot_consumption` over active placements whose animal is a `DOG`; `consumed_cat_slots` is the same sum over active placements whose animal is a `CAT` or an `OTHER`; `consumed_headcount` is the sum of `headcount_consumption` over all active placements. The home's `capacity_status` is `OPEN` when at least one species bucket still has a free slot **and** at least one head remains free, and `FULL` otherwise — so exhausting either both species buckets or the head count alone flips it to `FULL`. The axis oscillates with placement churn, and each flip in either direction increments the home's `version` by one.

Four cross-cutting conditions guard the placement operations, and their scopes are **not** identical — one of the four deliberately covers only two of the three operations.

- **Application state.** The linked foster application must be `APPROVED` and its `species_requested` must equal the animal's `species`, failing which the answer is `ERR_INVALID_STATE`. This guards all three operations: proposing a placement, activating one, and transferring one.
- **Foster restriction evaluation.** Its three criteria are tested in a pinned order with the first failure reported: first that the animal is not a `CAT` or else the home's `accepts_cats` is true; second that the home's `min_child_age_years` is at least the animal's `restriction_no_children_under_years`, an inclusive comparison so a home whose youngest child is exactly the restriction age qualifies; third that the animal does not require a fenced yard or else the home's `has_fenced_yard` is true. Any failure is `ERR_FOSTER_RESTRICTION_VIOLATION`. This guards exactly two operations — proposing a placement and transferring one. **Activation does not re-run it**, because the receiving home was already vetted when the placement was proposed.
- **Home-check currency.** The linked application's `home_check_status` must be `PASSED` with the clock at or before `home_check_expires_at`; `NOT_SCHEDULED`, `FAILED` and `LAPSED` all fail this and yield `ERR_HOME_CHECK_NOT_CURRENT`. This guards all three operations, which matters because a check can lapse between proposal and activation.
- **Capacity.** Species slots are tested first: the home's consumed slots in the animal's species bucket plus this placement's `slot_consumption` must not exceed that bucket's capacity, failing which the answer is `ERR_FOSTER_CAPACITY_EXCEEDED`. Head count is tested second: `consumed_headcount` plus this placement's `headcount_consumption` must not exceed `max_headcount`, failing which the answer is `ERR_FOSTER_HEADCOUNT_EXCEEDED`. Both comparisons are inclusive — filling the last slot or the last head exactly is permitted. Both guard all three operations, and because only `ACTIVE` placements consume anything, a proposal is measured against the home's live consumption at proposal time and again at activation time.

Activating a proposal moves it `PROPOSED → ACTIVE`, stamps `started_at` with the current clock instant, sets the animal's `current_foster_home_id` to the receiving home, recomputes that home's counters and `capacity_status`, and increments both the placement's `version` and the home's `version` by one.

Ending a placement carries a `reason`, and only two of the five `end_reason` members may be supplied by a caller: `RETURNED_TO_SHELTER` and `CANCELLED_BEFORE_START`. The other three — `TRANSFERRED_OUT`, `ADOPTED` and `ANIMAL_OUTCOME_CLOSED` — are written by the system on the transfer path, the foster-to-adopt path and the outcome cascade respectively, and are rejected here with `ERR_INVALID_ENUM`. A `PROPOSED` placement ended with `CANCELLED_BEFORE_START` moves to `CANCELLED`, stamping `ended_at` and `end_reason` and incrementing `version`; because it never consumed anything, no counters move. An `ACTIVE` placement ended with `RETURNED_TO_SHELTER` moves to `ENDED`, stamping `ended_at` and `end_reason`, clearing the animal's `current_foster_home_id`, recomputing the home's counters and `capacity_status`, and incrementing `version`. Pairing a reason with the wrong current state — ending a `PROPOSED` placement with `RETURNED_TO_SHELTER`, say — matches no declared transition and yields `ERR_INVALID_STATE`.

A **foster-to-foster transfer** supplies a `destination_foster_home_id` and a `destination_foster_application_id`. It is the one placement operation an active medical hold blocks, and it is also blocked by an active legal hold; a behavioural hold never blocks it. On success the source placement moves `ACTIVE → TRANSFERRED` with `ended_at` stamped and `end_reason` set to `TRANSFERRED_OUT`, a **successor placement is created in `ACTIVE`** whose `predecessor_placement_id` points back at the source, both homes' counters and `capacity_status` are recomputed, and the source placement's `version` increments by one. This divergence from the plain ending is the point: `TRANSFERRED` creates a successor row, `ENDED` does not.

The fifth exit from `ACTIVE` is not a placement operation at all. When an adoption is finalized for an animal whose active placement sits in the adopter's own foster home — that is, where the adopter is the home's `person_id` — the placement moves `ACTIVE → CONVERTED_TO_ADOPTION` with `ended_at` stamped, `end_reason` set to `ADOPTED`, the animal's `current_foster_home_id` cleared, and its `version` incremented; and the outcome record written by that adoption carries `outcome_type` `FOSTER_TO_ADOPT` rather than `ADOPTION`. The animal never returns to the shelter.

Foster homes may be listed filtered by `person_id` and `capacity_status`; placements may be listed filtered by `animal_id`, `foster_home_id`, `foster_application_id`, `litter_id`, `predecessor_placement_id` and `status`.

### 3.5. Veterinary Work, Restricted Funding and Health Certificates

Ordering a procedure creates a medical record against an animal, naming a `procedure_type`, an `expense_category` bucket that restricted money must match to fund it, a `cost_cents` gross cost of at least zero, and a `scheduled_at` instant. An optional `funding_required` flag defaults to **false**, and that default carries real consequence, described below. A newly ordered record sits in `status` `ORDERED` with `completed_at` null, `funded_contribution_ids` an empty list, `funded_amount_cents` 0 and `admin_overhead_cents` 0.

Completing the procedure moves it `ORDERED → COMPLETED` and stamps `completed_at` with the current clock instant. Two of the four procedure types have cross-entity consequences: completing a `SPAY_NEUTER` sets the animal's `alteration_status` to `ALTERED`, and completing a `VACCINE_RABIES` sets the animal's `rabies_vaccinated_at` to that same `completed_at`. Where several rabies vaccinations exist, `rabies_vaccinated_at` reflects the `completed_at` of the most recent completed one. Completion increments both the medical record's `version` and the animal's `version` by one. A record already `COMPLETED` cannot be completed again — `ERR_INVALID_STATE`.

The money branches sharply on `funding_required`. When it is **false**, completion draws no contributions at all: the whole `cost_cents` is charged against the organization's `unrestricted_balance_cents`, which may drive that balance negative, and `funded_amount_cents` and `admin_overhead_cents` both stay at zero. When it is **true**, completion runs a funding allocation and **fails outright** if the eligible money does not cover the cost.

The eligible pool for a funded completion consists of contributions that are still in `status` `RECEIVED` or `PARTIALLY_APPLIED`, whose `available_cents` is strictly greater than zero, whose `restriction_category` either equals the medical record's `expense_category` or is `UNRESTRICTED`, and which are either undesignated or designated to this very animal — a gift earmarked for a different animal is never eligible, whatever its category. They are drawn in a fully pinned order: `created_at` ascending first; then, among rows created at the same instant, `amount_cents` **descending**; and finally, as a last resort, `donor_reference` ascending lexicographically. If the total `available_cents` across the eligible pool is less than `cost_cents`, the completion is rejected with `ERR_INSUFFICIENT_RESTRICTED_FUNDS` and **nothing is drawn** — there are no partial draws and no partial completions.

Otherwise the cost is consumed line by line down that order. Each line draws the smaller of the contribution's remaining `available_cents` and the cost still outstanding, raising that contribution's `applied_cents` by the line amount and lowering its `available_cents` correspondingly. Administrative overhead of 8 percent is computed on **each individual line**, rounded half up to whole cents at that point, and the rounded per-line figures are then summed into `admin_overhead_cents`; as §2.8 insists, summing the lines and rounding once at the end is a different and incorrect number. The identifiers of the drawn contributions are recorded in draw order as `funded_contribution_ids`, `funded_amount_cents` is set to the full `cost_cents`, and the organization's `unrestricted_balance_cents` is lowered by `admin_overhead_cents`. Note the asymmetry: under funded completion the organization pays only the overhead, because the donors paid the cost; under unfunded completion the organization pays the entire cost and no overhead.

A caller may optionally name `funding_contribution_ids` on the completion request to pin which gifts should pay. Every explicitly named contribution must have a `restriction_category` equal to the record's `expense_category` or equal to `UNRESTRICTED`, and must not be designated to a different animal; a named contribution failing either test is rejected with `ERR_RESTRICTED_FUND_CATEGORY_MISMATCH`, and that check sits above the sufficiency check on the ladder, so an ineligible nomination reports the mismatch rather than an insufficiency.

Medical records may be read individually — the read exposes the full draw trail — and listed filtered by `animal_id`, `procedure_type` and `status`.

**Health certificates** authorise interstate movement. Issuing one names an `issued_at` instant, a two-letter `destination_state` the certificate authorises movement into, and the accredited veterinarian's `vet_license_number`. The validity window is selected by the animal's species and nothing else: a `DOG` gets 30 days, a `CAT` gets 15, and an `OTHER` gets 10. The selected figure is stored as `window_days` and `expires_at` is `issued_at` advanced by that many 24-hour periods. A certificate starts in `status` `VALID`.

Expiry is evaluated with a strict comparison — the certificate is still valid at an instant exactly equal to `expires_at` — and the transition `VALID → EXPIRED` is one-way. An expired certificate can no longer authorise an interstate departure, and the remedy is to issue a fresh one rather than to amend the old. Critically, **a certificate expiring mid-relay does not mutate any transport leg**. Legs that have already arrived keep their status; every remaining leg carrying that animal is simply rejected at its own departure check until a fresh certificate exists. Certificates may be listed filtered by `animal_id`, `status` and `destination_state`.

Where an animal holds several certificates for the same destination state, exactly one **governs**: the row with the greatest `issued_at`, tie-broken by the greatest `created_at`. An older, already-expired certificate for the same animal and state does not block a departure once a newer one governs.

> **Open point (certificate expiry latch).** The certificate axis is described in one place as latching to `EXPIRED` on any read or write that observes the clock past `expires_at`, and in another as being written the first time a **departure check** observes it. Reading A: any read of the certificate, including a plain single read or a list, latches the status. Reading B: only a departure evaluation latches it, so a certificate read in isolation may still report `VALID` after its expiry instant. This PRD does not choose between them; note that under either reading the departure itself is refused identically.

### 3.6. Transport: Runs, Legs, Manifests and the Relay Chain

A `TransportDispatcher` plans a run by naming the `origin_organization_id` dispatching it, a `run_type` distinguishing a single field-pickup `RESCUE_LEG` from a multi-leg `RELAY` with driver handoffs at hubs, and the `origin_hub_code` and `destination_hub_code` bracketing the whole journey. An optional `purpose` defaults to `INTAKE_TRANSPORT`, meaning the run moves animals into the network; the alternative, `TRANSFER_OUT`, delivers them to a partner rescue and draws that partner's committed slots, and it requires a `partner_commitment_id` naming the commitment to draw against. A new run starts in `status` `PLANNED` with `slots_drawn` 0, `started_at` null and `aborted_at` null.

Legs are then added to the run **while it is still `PLANNED`** — adding a leg to a run that has already started is refused with `ERR_INVALID_STATE`. Each leg names a `driver_person_id`, a 1-based `sequence_no` that is unique within the run and fixes the order in which legs depart, an `origin_hub_code` and a `destination_hub_code` marking its own segment, a `scheduled_depart_at` and a strictly later `scheduled_arrive_at`, a `crate_capacity_units` of at least one, and a `weight_capacity_lb` greater than zero. Three optional fields shape what the leg will accept: `crosses_state_line` defaults to false; `destination_state_code` defaults to null and is required whenever `crosses_state_line` is true, since the certificate check matches against exactly that value; and `species_policy` defaults to `ANY`. A leg is created in `status` `SCHEDULED` with `used_crate_units` 0, `used_weight_lb` 0, and `departed_at` and `arrived_at` null, and adding it increments the parent run's `version` by one. The named driver must be a person carrying a non-null `driver_license_number`.

**Driver occupancy is exclusive with an asymmetric turnaround buffer.** The candidate leg occupies the half-open interval from its `scheduled_depart_at` up to but not including its `scheduled_arrive_at`. Every existing leg of the same driver whose `status` is `SCHEDULED` or `DEPARTED` occupies the half-open interval from its own `scheduled_depart_at` up to but not including its `scheduled_arrive_at` **advanced by 60 minutes** — the buffer is appended to the end of the existing leg only, never to its start and never to the candidate. Two intervals overlap when each one starts strictly before the other ends. A candidate that ends exactly when an existing leg begins is therefore accepted, and a candidate that begins exactly 60 minutes after an existing leg's scheduled arrival is accepted, while one beginning 59 minutes after is rejected with `ERR_DRIVER_LEG_OVERLAP`. Legs that have reached `ARRIVED`, `ABORTED` or `INVALIDATED` never conflict with anything.

**Manifesting** an animal onto a leg supplies the `animal_id` and the mandatory `expected_leg_version` of §2.7. The crate cost the entry consumes depends on the animal's litter posture. An animal with no `litter_id`, or one whose litter has been split-approved, is billed by its own `size_class`: 1 crate unit for `SMALL`, 2 for `MEDIUM`, 3 for `LARGE`, with `is_litter_anchor` false. An animal belonging to a `GROUPED` litter is billed differently: the first such littermate to land on a given leg — meaning no other entry for that litter already sits on that leg with `status` `ASSIGNED`, `LOADED` or `DELIVERED` — is the **anchor**, carrying `is_litter_anchor` true and a flat 2 crate units for the whole litter, and every subsequent littermate on the same leg carries `is_litter_anchor` false and **zero** crate units. Four small littermates travelling grouped therefore cost 2 crate units in total, where the same four travelling split-approved would cost 4.

Weight is counted quite differently, and the difference is the point: `used_weight_lb` is the sum of the `weight_lb` of every animal on the leg with `status` `ASSIGNED`, `LOADED` or `DELIVERED`, **including** grouped littermates whose crate contribution is zero. The crate axis and the weight axis therefore fail independently. A manifest add is accepted only when `used_crate_units` plus the candidate's crate units is at most `crate_capacity_units` — otherwise `ERR_LEG_CRATE_CAPACITY_EXCEEDED` — and only when `used_weight_lb` plus the candidate's `weight_lb` is at most `weight_capacity_lb` — otherwise `ERR_LEG_WEIGHT_CAPACITY_EXCEEDED`. Both comparisons are inclusive, so filling a leg exactly to capacity on either axis succeeds. On success the entry is created in `status` `ASSIGNED` with `stranded_at_hub_code` null, both leg utilisation figures rise, and the leg's `version` increments by one.

Two further rules police a manifest. The **species and temperament policy** is evaluated over the leg's existing entries in `status` `ASSIGNED` or `LOADED` together with the candidate — note that `DELIVERED` entries are excluded from this particular test even though they count toward crate and weight. Under `DOGS_ONLY` every animal in that set must be a `DOG`; under `CATS_ONLY` every animal must be a `CAT`; under `MIXED_SEGREGATED` the add is refused if any `REACTIVE` animal would share the leg with an animal of a different species; and under `ANY` the add is refused if the resulting manifest would carry two or more `REACTIVE` animals. Any refusal is `ERR_SPECIES_INCOMPATIBLE_LEG`. Separately, **littermate grouping** is enforced across the whole network: when the candidate belongs to a litter whose `transport_basis` is still `GROUPED`, no littermate may already sit on a *different* leg of any run with `status` `ASSIGNED` or `LOADED`, and an attempt to split them that way is refused with `ERR_LITTER_SPLIT_NOT_APPROVED`. Split approval, described in §3.1, is what unlocks it. On the ladder the species check sits above the litter check, which sits above the two capacity checks.

An assigned animal may be bumped back off a leg by a dispatcher, moving the entry `ASSIGNED → BUMPED`, lowering the leg's `used_crate_units` and `used_weight_lb` by that entry's contribution, and incrementing both the entry's `version` and the leg's `version` by one. `BUMPED` is terminal. Manifest entries may be read individually and listed filtered by `transport_leg_id`, `animal_id` and `status`; legs may be listed filtered by `transport_run_id`, `driver_person_id` and `status`; runs may be listed filtered by `origin_organization_id`, `partner_commitment_id`, `run_type`, `purpose` and `status`.

**Starting** a run moves it `PLANNED → IN_PROGRESS`, stamps `started_at` with the current clock instant and increments the run's `version` by one. At least one leg must exist on the run. Everything else that happens at start belongs to the transfer-out path and is described in §3.7.

**Departing** a leg moves it `SCHEDULED → DEPARTED` and is the single most heavily guarded action in the system. The parent run must be `IN_PROGRESS`. No manifested animal may carry an active legal hold — this is a gate, so it pre-empts everything below it, and one restrained animal blocks the entire departure. On an interstate leg, every manifested animal must satisfy rabies eligibility, must hold a certificate for the destination state, and that certificate must still be valid. And every leg of the same run with a lower `sequence_no` must already have reached `ARRIVED`, failing which the answer is `ERR_LEG_SEQUENCE_VIOLATION` — this is the relay handoff, and it means legs strictly cannot leapfrog one another.

**Rabies eligibility**, tested only when `crosses_state_line` is true, requires the animal's `rabies_vaccinated_at` to be non-null and requires the animal to have been at least 12 weeks old at the moment of that vaccination. The vaccination age is computed the same calendar-free way as every other age: whole elapsed days between `date_of_birth` and `rabies_vaccinated_at`, divided by 7 and rounded down. The boundary is inclusive at 12 weeks. A failure on either count — never vaccinated, or vaccinated too young — is `ERR_RABIES_AGE_NOT_MET`. Note that this check sits **above** both certificate checks on the ladder, so an animal that is both unvaccinated and uncertified reports the rabies failure.

**Certificate presence** then requires each manifested animal to hold at least one health certificate whose `destination_state` equals the leg's `destination_state_code`; if none exists the answer is `ERR_CVI_REQUIRED`. **Certificate validity** then requires that animal's governing certificate — greatest `issued_at`, tie-broken by greatest `created_at`, among those matching the destination state — to have an `expires_at` at or after the leg's `scheduled_depart_at`. The comparison is against the leg's *scheduled* departure instant, not against the clock at the moment of the call. A failure is `ERR_CVI_EXPIRED`.

On success, departure stamps `departed_at` with the current clock instant, moves every `ASSIGNED` entry on the leg to `LOADED`, and moves each carried animal to `IN_TRANSIT` — from `IN_CUSTODY` on a first departure, or from `STRANDED` when this is a replacement leg picking up an animal left behind. In the latter case the animal's `current_hub_code` is cleared. The leg's `version` and each carried animal's `version` each increment by one.

**Arriving** a leg moves it `DEPARTED → ARRIVED` and stamps `arrived_at`. On an intermediate leg the animals stay `IN_TRANSIT`, waiting at the handoff hub for the next leg's departure, and their entries stay `LOADED`. On the run's highest-`sequence_no` leg the journey completes: every `LOADED` entry moves to `DELIVERED`, every carried animal returns to `IN_CUSTODY`, and the run itself moves `IN_PROGRESS → COMPLETED` once every leg of the run has reached `ARRIVED`. On an `INTAKE_TRANSPORT` run, arrival at the final leg also repoints each carried animal's `current_organization_id` to the run's destination organization. Both the leg's `version` and the run's `version` increment.

> **Open point (which organization an intake transport delivers to).** Arrival on the final leg of an `INTAKE_TRANSPORT` run is declared to repoint each carried animal's `current_organization_id` to "the run's destination organization", but a run models only an `origin_organization_id` and a `destination_hub_code` — no destination organization is stored anywhere. Reading A: the dispatching organization is the receiving one on an intake transport, so `current_organization_id` is repointed to the run's `origin_organization_id`. Reading B: because no destination organization exists on the run, there is nothing to repoint to and each animal's `current_organization_id` is left unchanged by arrival. This PRD does not choose between them. Note the consequence either way: the animal's owning organization is what the records-freeze gate of §2.6 and the organization filter on the live-release report both key on.

**Aborting a leg** has two disjoint branches, and which one applies is decided purely by whether the leg had departed. Aborting a `SCHEDULED` leg moves it to `ABORTED` and simply moves every `ASSIGNED` entry to `BUMPED`; nobody is stranded, because nobody was loaded. Aborting a `DEPARTED` leg triggers the system's deepest cascade, six hops from a single call. Hop one is the leg itself moving `DEPARTED → ABORTED` and incrementing its `version`. Hop two moves every `LOADED` entry on that leg to `STRANDED`, stamping each with a `stranded_at_hub_code` equal to the aborted leg's `origin_hub_code`. Hop three moves each of those animals `IN_TRANSIT → STRANDED` and sets each animal's `current_hub_code` to that same hub, incrementing each animal's `version`. Hop four moves the parent run `IN_PROGRESS → ABORTED`, stamping `aborted_at` and invalidating the run's remaining scheduled legs. Hop five, on a transfer-out run, returns the drawn slots to the partner commitment. Hop six recomputes the partner organization's `open_commitment_slots_total`. An optional `reason` may accompany the abort.

A stranded animal is not lost. The dispatcher manifests it onto a **replacement leg** whose `origin_hub_code` equals the animal's `current_hub_code`, and departing that leg returns the animal to `IN_TRANSIT`. The cycle `STRANDED → IN_TRANSIT → STRANDED` may repeat any number of times.

> **Open point (what happens to the stranded entry on re-manifest).** Re-manifesting a stranded animal is declared both as a `STRANDED → ASSIGNED` transition on the manifest axis and, in the same breath, as an operation whose effect is that the old stranded entry **stays** `STRANDED` for audit while a brand-new entry is created in `ASSIGNED` on the replacement leg. Reading A: the original entry is mutated to `ASSIGNED` and re-pointed at the replacement leg, so one row exists per animal per journey. Reading B: the original entry is left untouched at `STRANDED` with its `stranded_at_hub_code` intact and a second, fresh entry is created on the replacement leg, so two rows exist. Under both readings the replacement leg's `used_crate_units` and `used_weight_lb` rise by the animal's contribution. This PRD does not choose between them.

**Aborting a run** likewise branches. A run still `PLANNED` moves to `CANCELLED`: every `SCHEDULED` leg moves to `INVALIDATED` and every `ASSIGNED` entry moves to `BUMPED`, and because the run never started, no partner slots were ever drawn and none are returned. A run that is `IN_PROGRESS` moves to `ABORTED`: `aborted_at` is stamped, every `SCHEDULED` leg moves to `INVALIDATED`, and any drawn partner slots are returned as described in §3.7. Both branches increment the run's `version`. An `INVALIDATED` leg can never depart, and its `ASSIGNED` entries move to `BUMPED`. Only a run abort or cancel invalidates a leg — an expired certificate never does; it only blocks that leg's own departure.

### 3.7. Partner Commitments and the Transfer-Out Slot Ledger

A partner rescue pledges capacity by registering a commitment against its `organization_id` for one `species`, with a `slots_total` of at least one and an `expires_at` instant after which unused slots may no longer be drawn. The commitment opens in `status` `OPEN` with `slots_drawn` 0, `slots_released` 0 and `slots_open` equal to `slots_total`, and registering it raises that organization's `open_commitment_slots_total`. That organization-level roll-up is the sum of `slots_open` across the organization's commitments whose `status` is `OPEN` or `PARTIALLY_DRAWN`, and it is recomputed after every draw, return and expiry. `slots_open` itself is always `slots_total` less `slots_drawn` less `slots_released`.

Slots are drawn at the moment a **transfer-out run starts**, not when its legs are manifested and not when they depart. The number needed is the count of **distinct** animals across all of the run's legs whose manifest entries stand at `ASSIGNED` or `LOADED` — an animal manifested onto two legs of a relay counts once. Three conditions must hold. Every one of those distinct animals must be of the commitment's `species`, failing which the start is refused with `ERR_PARTNER_SPECIES_MISMATCH`. The commitment must not have expired — the clock must be at or before `expires_at` and the `status` must not be `EXPIRED` — failing which the answer is `ERR_PARTNER_COMMITMENT_UNAVAILABLE`. And `slots_open` must be at least the needed count, an inclusive comparison so drawing the last available slot exactly is permitted, failing which the answer is again `ERR_PARTNER_COMMITMENT_UNAVAILABLE`.

> **Open point (order of the species and expiry checks on run start).** For a transfer-out run whose commitment has expired **and** whose manifested animals are of the wrong species, the two available orderings disagree on the observable code. Reading A follows the global ladder, which places the species check at rung 32 above the expiry check at rung 39, and reports `ERR_PARTNER_SPECIES_MISMATCH`. Reading B follows the run-start transition's own precondition list, which states the expiry condition first, and reports `ERR_PARTNER_COMMITMENT_UNAVAILABLE`. This PRD does not choose between them.

On a successful draw the run's `slots_drawn` is set to the needed count, the commitment's `slots_drawn` rises by the same amount and its `slots_open` falls correspondingly, the partner organization's `open_commitment_slots_total` is recomputed, and the commitment's own axis advances: `OPEN → PARTIALLY_DRAWN` when some but not all slots are now drawn, or straight to `EXHAUSTED` when the draw consumes every slot. A commitment already `PARTIALLY_DRAWN` moves to `EXHAUSTED` when a further run consumes the remainder. A run whose `purpose` is `INTAKE_TRANSPORT` draws nothing and leaves `slots_drawn` at zero.

Returns run the axis backwards, which is why it is cyclic rather than linear. When a drawing run aborts — whether by an explicit run abort or through hop five of the leg-abort cascade — its `slots_drawn` are returned: the commitment's `slots_drawn` falls and its `slots_open` rises by the same amount, and the status moves `EXHAUSTED → PARTIALLY_DRAWN` when some draws remain from other runs, or `PARTIALLY_DRAWN → OPEN` when nothing is drawn any longer. The organization roll-up is recomputed on every such move.

Expiry is not automatic; it is applied by an **ops-run sweep** available to a `TransportDispatcher` or `PlatformAdmin`. The sweep visits every commitment whose `expires_at` the clock has strictly passed and whose `status` is `OPEN` or `PARTIALLY_DRAWN`, moves each to `EXPIRED`, shifts its remaining `slots_open` into `slots_released` and sets `slots_open` to zero, and recomputes each affected organization's `open_commitment_slots_total`. Slots already drawn stay drawn — expiry forfeits only what was never taken up. The sweep answers with an `expired_count`, the list of `expired_commitment_ids`, and the total `slots_forfeited` across them. `EXPIRED` is terminal.

Commitments may be read individually and listed filtered by `organization_id`, `species` and `status`. A `PartnerRescue` actor sees only its own.

### 3.8. Adoption: Application, Screening, Finalization and the Fee Waterfall

An adoption application names an `animal_id` and an `applicant_person_id`, and the applicant's declared household is matched against the animal's placement restrictions **at submission time**, before any row is written. The five criteria are evaluated in a pinned order and the first failure ends the evaluation: first, the applicant's `youngest_child_age_years` must be at least the animal's `restriction_no_children_under_years`, an inclusive comparison so a household whose youngest child is exactly the restriction age qualifies; second, either the animal's `restriction_no_cats` is false or the applicant's `resident_cat_count` is zero; third, either `restriction_no_dogs` is false or `resident_dog_count` is zero; fourth, either `restriction_requires_fenced_yard` is false or the applicant's `has_fenced_yard` is true; fifth, the applicant's `housing_type` must not appear in the animal's `restriction_housing_types_excluded` array. Any failure rejects the submission with `ERR_HOUSEHOLD_MISMATCH` (HTTP 422). Because the match happens at create time, **no application row ever exists carrying a household-mismatch decline** — the only two members of `decline_reason` are `COUNSELOR_DECISION` and `SUPERSEDED_BY_FINALIZED_SIBLING`.

A surviving application is created in `status` `SUBMITTED` with `attempt_count` 1, and with `screened_by_user_id`, `screened_at` and `decline_reason` all null. Screening by an `AdoptionCounselor` carries a `decision`. `APPROVE` moves it `SUBMITTED → APPROVED`; `DECLINE` moves it `SUBMITTED → DECLINED` and sets `decline_reason` to `COUNSELOR_DECISION`. Both branches record the acting `X-User-ID` as `screened_by_user_id` and the current clock instant as `screened_at`, and both increment the application's `version` by one. Screening is deliberately permitted while the animal's stray hold is still `HOLD_ACTIVE` — the counselor can do the paperwork during the hold; it is only finalization that must wait.

A declined applicant may try again. Resubmission is reserved to the applicant themself — an `Adopter` whose `X-User-ID` equals the application's `applicant_person_id` — moves it `DECLINED → SUBMITTED`, raises `attempt_count` by one, clears `decline_reason`, `screened_by_user_id` and `screened_at` back to null, and increments `version`. The loop is capped at three submissions counting the original, so the third submission is permitted and the fourth is refused with `ERR_APPLICATION_ATTEMPT_LIMIT`.

**Finalization** creates the `Adoption` and is the busiest single operation in the system. It names the `adoption_application_id` being finalized and carries the mandatory `expected_animal_version` of §2.7, plus three optional variant selectors that shape the money: `credit_application_order` defaulting to `CREDIT_FIRST`, `refund_basis` defaulting to `FEE_PAID`, and `deposit_basis` defaulting to `FLAT`. The `animal_id` and `adopter_person_id` on the resulting adoption are copied from the application rather than supplied.

Before any money is computed, five conditions are tested in ladder order. All four animal-scoped gates apply here — outcome-closed, legal hold, medical hold and behavioural hold — making adoption finalization the only operation in the system inside every gate's scope. The application must be `APPROVED`. The finalizing `X-User-ID` must differ from the application's `screened_by_user_id`, failing which the answer is `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) — and `PlatformAdmin` gets no exemption. The animal's current custody episode must have latched to `HOLD_EXPIRED`, failing which the answer is `ERR_STRAY_HOLD_NOT_EXPIRED`. And **alteration compliance** must hold: the animal must either already be `ALTERED`, or be younger than 16 weeks so that a deferred deposit can be taken instead. An unaltered animal at or over 16 weeks simply cannot be adopted out, and the refusal is `ERR_ALTERATION_REQUIRED` (HTTP 422).

The fee is then assembled in four stages. **The base fee** is selected by species alone: 25000 cents for a `DOG`, 12500 for a `CAT`, 6000 for an `OTHER`, stored as `base_fee_cents`.

**The promotional waiver** is selected next, and waivers never stack. An animal qualifies for the senior waiver when its `age_months` is at least 84 — that is, seven years — which discounts 60 percent. It qualifies for the long-stay waiver when its `length_of_stay_days` is at least 120 — four 30-day months in this system's arithmetic — which discounts 50 percent. Both boundaries are inclusive. When both qualify, only the strictly larger percentage is used, so `SENIOR` always wins over `LONG_STAY` and the two can never tie. When neither qualifies, `waiver_kind` is `NONE` and the waiver percentage is zero. The chosen member is recorded as `waiver_kind`.

**The sponsorship pool** is assembled from contributions only; no other entity contributes to it. A contribution is eligible when its `status` is `RECEIVED` or `PARTIALLY_APPLIED`, its `available_cents` is strictly greater than zero, and it is either designated to this very animal through `designated_animal_id` or carries a `designated_program` of `ADOPTION_FEE_ASSISTANCE`. The eligible rows are ranked by three keys applied in sequence: rows designated to this animal come before program-designated rows; then `created_at` ascending; then `donor_reference` ascending lexicographically as the final tie-break. Entity identifiers never participate in the ordering. The pool's total is the sum of `available_cents` across the eligible rows; when nothing is eligible the total is zero and the waterfall simply proceeds with no sponsorship applied.

**The waterfall** then divides the base fee three ways, and which of two orders applies is chosen by `credit_application_order`. Under `CREDIT_FIRST`, sponsorship goes first: `sponsorship_applied_cents` is the smaller of `base_fee_cents` and the pool total; what remains of the base fee after that is then reduced by the waiver, with `waiver_applied_cents` being the waiver percentage applied to that remainder and rounded half up; and `adopter_charged_cents` is the remainder less the waiver. Under `WAIVER_FIRST`, the waiver goes first: `waiver_applied_cents` is the waiver percentage applied to the full `base_fee_cents` and rounded half up; `sponsorship_applied_cents` is then the smaller of the post-waiver amount and the pool total; and `adopter_charged_cents` is the post-waiver amount less the sponsorship. Either way exactly one rounding occurs, and the three components always sum back to `base_fee_cents`.

The two orders are not merely a presentation choice. Under `CREDIT_FIRST` the credit absorbs the fee before the waiver shrinks it, so the waiver acts on a smaller base and the adopter typically still owes something. Under `WAIVER_FIRST` a large waiver can drop the fee below the available credit, so the adopter owes nothing and a strictly positive `residual_credit_cents` appears. `residual_credit_cents` is always the pool total less `sponsorship_applied_cents`, and there is a non-monotone consequence worth stating plainly: a **larger** waiver under `WAIVER_FIRST` consumes **less** sponsorship and therefore leaves **more** residual credit. That residual is never refunded to the adopter and is never applied beyond the fee. It stays on its contribution until the adoption's own outcome cascade releases it into the organization's unrestricted funds — see §3.9.

The contributions actually drawn are consumed down the pool's ranking until `sponsorship_applied_cents` is exhausted, each drawn row having its `applied_cents` raised and its `available_cents` lowered by its line amount, which advances it along its own axis as §3.9 describes.

**The deferred-alteration deposit** is a separate, refundable amount assessed only when the animal is not `ALTERED` and its `age_weeks` is below 16. Under a `FLAT` `deposit_basis` it is always 15000 cents, however young the animal is. Under `AGE_SCALED` it is 1200 cents for each week the animal falls short of 16 weeks, clamped to a floor of 6000 cents and a cap of 18000 cents — so a twelve-week animal's raw figure sits below the floor and the floor binds, while a newborn's raw figure exceeds the cap and the cap binds. The result is stored as `alteration_deposit_cents`, defaulting to 0 when no deposit is due, and assessing a deposit moves the animal's `alteration_status` to `DEFERRED_DEPOSIT`. The deposit is deliberately **outside** the three-way fee identity of §2.10: it is money held, not fee assessed.

The adoption row is written in `status` `FINALIZED` and `fee_status` `UNPAID`, with `finalized_at` stamped at the current clock instant, `finalized_by_user_id` recording the acting `X-User-ID`, `adopter_paid_cents`, `refund_issued_cents`, `credit_restored_cents` and `alteration_deposit_refunded_cents` all at zero, and `returned_at` null. The application moves `APPROVED → FINALIZED`. Every **other** application on the same animal standing at `SUBMITTED` or `APPROVED` is moved to `AUTO_DECLINED` with `decline_reason` `SUPERSEDED_BY_FINALIZED_SIBLING`. An outcome record is written and the custody episode closes, exactly as §3.9 sets out; where the adopter is the person owning the foster home that currently holds the animal, that outcome carries `FOSTER_TO_ADOPT` and the placement converts as described in §3.4. The animal's `version` increments.

**Payment** runs on a second, entirely parallel axis. `fee_status` advances independently of `status`: it may reach `PAID` while the adoption is still `FINALIZED`, and the adoption may reach `RETURNED` while `fee_status` is still `UNPAID`. A payment carries an `amount_cents` and raises `adopter_paid_cents` by it, incrementing the adoption's `version`. The target the payment is measured against is `adopter_charged_cents` **plus** `alteration_deposit_cents` — the adopter must cover both. When the new `adopter_paid_cents` still falls short of that target the axis moves `UNPAID → PARTIALLY_PAID`; when it reaches or exceeds the target it moves `UNPAID → PAID` or `PARTIALLY_PAID → PAID`.

**Redeeming the deposit** happens when proof of surgery arrives. Supplying a `proof_reference` sets `alteration_deposit_refunded_cents`, moves the animal's `alteration_status` `DEFERRED_DEPOSIT → ALTERED`, and increments both the adoption's `version` and the animal's `version`. This operation does not touch `fee_status`; no transition on that axis is declared for it.

> **Open point (how much of the deposit is refunded).** Redeeming the deposit is declared to set `alteration_deposit_refunded_cents` but no formula is given for the amount. Reading A: the full `alteration_deposit_cents` assessed at finalization is recorded as refunded, regardless of how much cash the adopter has actually handed over. Reading B: only the portion of the deposit the adopter has actually covered through `adopter_paid_cents` is refunded, so an adopter who paid nothing gets nothing back. This PRD does not choose between them.

Adoption applications may be listed filtered by `animal_id`, `applicant_person_id` and `status`; adoptions may be listed filtered by `adoption_application_id`, `animal_id`, `adopter_person_id`, `status` and `fee_status`. An `Adopter` reads only their own.

### 3.9. Outcomes, Reversals, Contributions and Live-Release Reporting

An **outcome record** closes a custody episode. It may be written directly by an `IntakeOfficer`, naming an `outcome_type`, an optional `partner_commitment_id` that is required when the type is `TRANSFER_OUT`, and an optional `counterparty_person_id` that names the adopter on an `ADOPTION` or the reclaiming owner on a `RETURN_TO_OWNER`. It is also written implicitly by the two operations that end custody as a side effect: adoption finalization, which additionally stamps the outcome's `adoption_id`, and the owner reclaim of §3.2. In every case the record stamps `recorded_at` with the current clock instant, stamps `intake_record_id` with the episode it closes, and leaves `reversed_at` and `reversal_reason` null; `reversal_reason` has exactly one member, `ADOPTER_RETURN`.

`is_live_release` is derived from the type and is true for exactly four members — `ADOPTION`, `FOSTER_TO_ADOPT`, `TRANSFER_OUT` and `RETURN_TO_OWNER`. The other five — `EUTHANASIA_MEDICAL`, `EUTHANASIA_BEHAVIORAL`, `EUTHANASIA_OWNER_REQUESTED`, `DIED_IN_CARE` and `LOST_IN_CARE` — are non-live.

Writing an outcome requires the animal to be `IN_CUSTODY` with its current episode still `OPEN`, and it fires a cascade across four entities. The episode moves `OPEN → CLOSED`. Any `ACTIVE` foster placement for this animal is ended with `end_reason` `ANIMAL_OUTCOME_CLOSED`, which clears the animal's `current_foster_home_id` and recomputes that home's consumed slots, consumed head count and `capacity_status`. Every contribution designated to this animal that still carries `available_cents` greater than zero moves to `RELEASED`: its remaining `available_cents` shifts into `released_cents` and the organization's `unrestricted_balance_cents` rises by the same amount — this is what finally frees the residual credit that a `WAIVER_FIRST` adoption left stranded. And the animal itself moves `IN_CUSTODY → OUTCOME_CLOSED`, with its `version` incremented. From that moment the outcome-closed gate of §2.6 fires against it.

Note carefully what the gate ordering means for a second outcome: attempting to record another outcome on an animal whose custody is already closed reports `ERR_ANIMAL_OUTCOME_CLOSED`, not `ERR_INVALID_STATE`, because the gate sits above the state rung.

**The adopter return** is the only reversal in the system. It is available to an `AdoptionCounselor`, carries an optional `reason`, and requires the adoption to be `FINALIZED` and the animal's standing outcome to be an unreversed `ADOPTION` or `FOSTER_TO_ADOPT`. It also requires the clock to be at or before `finalized_at` advanced by 30 days; beyond that outer window the return itself is refused with `ERR_RETURN_WINDOW_CLOSED`.

Inside the window the refund tier is chosen by whole elapsed days between `finalized_at` and the clock, rounded down. Fourteen days or fewer refunds 100 percent; more than fourteen but no more than thirty refunds 50 percent; beyond thirty the tier would be 0 percent, but that case is unreachable in practice because the return is refused outright at the same boundary — the zero tier is retained only for completeness. Both tier boundaries are inclusive. `refund_issued_cents` is the tier percentage applied to `adopter_paid_cents` and rounded half up.

Whether sponsorship credit also comes back is decided by the adoption's `refund_basis`. Under `FEE_PAID`, only the adopter's cash is refunded: `credit_restored_cents` stays at zero, and the sponsoring contributions keep their `applied_cents` untouched. Under `FEE_ASSESSED`, the same cash refund is issued **and** the same tier percentage of `sponsorship_applied_cents`, rounded half up, is returned to the sponsoring contributions as `credit_restored_cents`, raising their `available_cents` and possibly moving a contribution `FULLY_APPLIED → PARTIALLY_APPLIED`.

> **Open point (which contributions receive the restored credit).** When a `FEE_ASSESSED` return restores credit and the original waterfall drew from more than one contribution, the allocation of `credit_restored_cents` across those contributions is not pinned. Reading A: the restoration is spread proportionally across each drawn contribution in proportion to what each one supplied. Reading B: the restoration is applied in reverse draw order — the last contribution drawn is unwound first — until the restored amount is exhausted. This PRD does not choose between them; under both readings the total restored and every conservation identity are identical.

The return then cascades in four hops. Hop one writes `returned_at`, `refund_issued_cents` and `credit_restored_cents`, and advances the money axis: from `PAID` to `REFUNDED_PARTIAL` when the refund is strictly positive and strictly less than `adopter_paid_cents`, or from `PAID` to `REFUNDED_FULL` when the refund equals `adopter_paid_cents` and that figure is itself strictly positive. Hop two stamps the standing outcome record's `reversed_at` with the current clock instant and its `reversal_reason` with `ADOPTER_RETURN`, which removes it from the live-release numerator and denominator alike. Hop three moves the superseded custody episode `CLOSED → VOIDED` and creates a fresh episode with `intake_type` `RETURN`, a `hold_days` of zero and a `hold_status` already latched to `HOLD_EXPIRED` — an animal coming back from an adoption serves no stray hold. Hop four moves the animal `OUTCOME_CLOSED → IN_CUSTODY` and repoints its `current_intake_record_id` at the new episode. The adoption's `status` moves `FINALIZED → RETURNED`, and both the adoption's `version` and the animal's `version` increment. Because the pair voids one episode and opens another while reversing one outcome, the custody-episode identity of §2.10 is preserved exactly.

> **Open point (returning a partly-paid adoption).** The money axis declares refund transitions out of `PAID` only. An adoption returned while its `fee_status` is `PARTIALLY_PAID` therefore admits two readings. Reading A: no transition is declared out of `PARTIALLY_PAID`, so the axis stays at `PARTIALLY_PAID` even though a refund is issued. Reading B: the refund tiers apply from any state in which cash was received, so a partly-paid adoption advances to `REFUNDED_PARTIAL` or `REFUNDED_FULL` under the same comparison against `adopter_paid_cents`. This PRD does not choose between them. Where `adopter_paid_cents` is zero, the refund is zero and neither refunded state is reached under either reading.

**Contributions** are the network's money. Recording one names a `donor_person_id`, a positive `amount_cents` and a donor-supplied `donor_reference` string that serves as the final tie-break in every contribution ordering rule in this document. Three optional fields shape where the money may go: `designated_animal_id`, which earmarks the gift to one animal; `designated_program`, defaulting to `NONE`, which earmarks it to a program when it is not animal-specific; and `restriction_category`, defaulting to `UNRESTRICTED`, which names the expense category the money may be drawn against — `UNRESTRICTED` money may fund any category. A new contribution opens in `status` `RECEIVED` with `applied_cents` and `released_cents` at zero, `available_cents` equal to `amount_cents`, and `redesignation_count` at zero. Recording it raises the organization's `unrestricted_balance_cents` when the category is `UNRESTRICTED` and its `restricted_balance_cents` otherwise.

`available_cents` is always `amount_cents` less `applied_cents` less `released_cents`. Draws — whether from an adoption fee waterfall or a medical funding allocation — raise `applied_cents` and move the axis `RECEIVED → PARTIALLY_APPLIED` when some but not all of the gift is consumed, or straight to `FULLY_APPLIED` when a single draw consumes it whole; a later draw moves `PARTIALLY_APPLIED → FULLY_APPLIED`. Release is the other exit: when the designated animal's custody closes, a contribution still holding `available_cents` moves to `RELEASED` from either `RECEIVED` or `PARTIALLY_APPLIED`, shifting the residual into `released_cents`. A designated gift therefore ends either `FULLY_APPLIED`, every cent spent, or `RELEASED`, the residual handed to unrestricted funds — never both.

**Redesignation** is a self-loop on `RECEIVED` and is legal only before a single cent has been applied: the contribution's `applied_cents` must still be zero. It replaces `designated_animal_id`, `designated_program` and `restriction_category`, raises `redesignation_count` by one, recomputes the organization's `restricted_balance_cents`, and increments the contribution's `version`. Attempting it on a gift that has already been drawn against matches no declared transition and yields `ERR_INVALID_STATE`. Contributions may be listed filtered by `donor_person_id`, `designated_animal_id`, `designated_program`, `restriction_category` and `status`.

An organization's two money figures are derived, never stored independently. `restricted_balance_cents` is the sum of `available_cents` over contributions whose `restriction_category` is not `UNRESTRICTED` and whose `status` is `RECEIVED` or `PARTIALLY_APPLIED`. `unrestricted_balance_cents` is the sum of `available_cents` over contributions whose `restriction_category` **is** `UNRESTRICTED` and whose `status` is `RECEIVED` or `PARTIALLY_APPLIED`, **plus** the sum of `released_cents` over every contribution whatever its category, **less** the sum of `admin_overhead_cents` over every completed medical record, **less** the sum of `cost_cents` over every completed medical record whose `funding_required` was false. That last term is why an organization completing unfunded veterinary work can drive its unrestricted position **negative**; the figure is not floored at zero.

**The live-release report** is a computed read over an inclusive date window. It requires a `from_date` and a `to_date`, and accepts an optional `methodology` and an optional `organization_id`. When `methodology` is omitted the reporting organization's `default_methodology` supplies it. The pool consists of outcome records whose `reversed_at` is null and whose `recorded_at` date falls on or after `from_date` and on or before `to_date`; when `organization_id` is supplied, the pool is further narrowed to outcomes whose animal's `current_organization_id` matches. Reversed outcomes leave the numerator and the denominator together.

Three counts are then taken over that pool and reported: `live_outcome_count` over the four live types, `non_live_outcome_count` over the five non-live types, and `owner_requested_euthanasia_count` over `EUTHANASIA_OWNER_REQUESTED` alone. The `denominator` is where the two methodologies diverge. Under `SAC` it is the live count plus the non-live count, leaving owner-requested euthanasia in and depressing the rate. Under `ASILOMAR` it is that same sum **less** the owner-requested count, removing those cases from the denominator entirely, so identical data yields a strictly higher rate whenever any owner-requested euthanasia falls in the window. `live_release_rate` is the live count divided by the denominator, rounded half up to four decimal places — and is reported as null, not zero, when the denominator is zero. The response echoes the `methodology`, `from_date` and `to_date` it was computed under.


## 4. Endpoint Definitions

Every endpoint is mounted under the `/rescue` prefix and every request carries the `X-User-ID` and `X-User-Role` headers described in §2.1. Operations that bring a new resource into existence answer with HTTP 201; operations that modify an existing resource, including every computed read and every list, answer with HTTP 200. A rejected request answers with the HTTP status paired with its error identifier in §5.

The 201 rule follows the resource, not the URL shape, so several **action** endpoints also answer 201 because they mint a row: processing an owner reclaim returns the new outcome record, adding a leg returns the new leg, manifesting returns the new manifest entry, a foster-to-foster transfer returns the newly created successor placement, recording an outcome returns the new outcome record, and finalizing an adoption returns the new adoption. Every other action endpoint answers 200 with the updated resource — including the bump, which answers 200 with the bumped manifest entry rather than an empty body.
