# ML Model Deployment & Monitoring API — Product Requirements Document

## 1. Introduction

A machine-learning platform team is accountable for every model that reaches production traffic, and today that accountability is spread across spreadsheets, chat threads and tribal memory. Nobody can answer, in one query, which artifact is currently champion for a given model, which frozen training snapshot it was fitted on, whether that snapshot's PII review ever passed, how much of a serving cluster's traffic it holds, or whether its prediction quality has drifted away from the offline baseline it was approved against. When a model starts predicting badly at three in the morning, the on-call reliability engineer needs a fallback path, a way to cap exposure, and an audit trail that survives the incident review — none of which exists as a system of record.

This document specifies the **ML Model Deployment & Monitoring API**: a single system of record for the model registry, the training-data references that gate approval, the deployment patterns that carry traffic, the monitoring evidence that scores prediction quality against baseline, and the drift, skew, incident and revalidation machinery that closes the loop back to retraining. The service is deliberately built around segregation of duties. No single operator role can walk a model from registration to live traffic: the engineer who registers an artifact cannot approve it, the steward who registers a snapshot cannot decide it, the approver who signed a version cannot conduct its own periodic revalidation, and the platform administrator — despite being the operational owner — cannot create deployments, ramp traffic, decide datasets or edit documentation.

Two design commitments run through the whole surface and should be read as non-negotiable. First, **safety outranks capacity**: when a deployment is unhealthy and its serving cluster is also full, the caller learns about the health problem, never about the capacity problem. Second, **every ledger is recomputed, never patched**: traffic allocation on a cluster and evaluation-sample reservations on an artifact version are derived by re-summing their contributing rows on every write, so a rollback or a released reservation telescopes back to exactly the value that preceded it rather than to an accumulated approximation. Because the service must be exercised deterministically by tests and by rehearsal scripts, it also runs on an operator-driven **logical clock** rather than wall-clock time.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operators, Roles and Access Control

Every request to the service — including every read — must carry two headers. `X-User-ID` identifies the acting operator and `X-User-Role` names the capability set that operator is acting under. If either header is missing or empty, or if `X-User-Role` does not name one of the five roles defined below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This check runs before everything else, including path-identifier resolution: a request with an unknown role against a nonexistent resource returns 401, never 404.

Five roles exist, spelled exactly as follows:

- **`MLEngineer`** — builds models. Registers registry entries, training-data snapshots and artifact versions; edits version documentation; submits versions for review; records observation windows, drift reports and skew checks; and dispositions retraining triggers. An `MLEngineer` can approve nothing.
- **`DataSteward`** — owns the training-data reference lifecycle. Registering and submitting snapshots is shared with `MLEngineer`; deciding a submitted snapshot is exclusive to `DataSteward`; revoking an approved snapshot is shared with `PlatformAdmin`.
- **`ModelApprover`** — owns model approval and periodic revalidation. Deciding an artifact version is exclusive to this role. A `ModelApprover` can neither register nor document versions, and cannot move traffic.
- **`ReliabilityEngineer`** — owns serving traffic and incident response. Creating a deployment and ramping its traffic are exclusive to this role; there is deliberately no administrative override for either.
- **`PlatformAdmin`** — operates the platform. Archiving a registry entry, driving the logical clock and running the operational sweep are exclusive to this role. A `PlatformAdmin` may stand in for rollout, evaluation and incident actions, but is explicitly **not** a superuser: it cannot create deployments, ramp traffic, decide snapshots, decide versions, register versions or edit documentation.

Every read endpoint is available to all five roles. If the authenticated role is not among the roles listed for the target endpoint in §4, the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). Role authorization is evaluated **before** existence: a `DataSteward` attempting to create a deployment against a serving cluster that does not exist receives 403, never 404.

All five roles are **opaque identities**. When `X-User-Role` is `MLEngineer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the same holds for `DataSteward`, `ModelApprover`, `ReliabilityEngineer` and `PlatformAdmin`. The server never compares `X-User-ID` to any resource's `id`. It does, however, record the acting operator's identifier on business rows so that the service can later ask "who performed the preceding step?" — those recorded fields are `registered_by_user_id` (on registry entries and on training-data snapshots), `submitted_by_user_id` and `decided_by_user_id` (on artifact versions), `decided_by_user_id` (on snapshots), `acknowledged_by_user_id` (on retraining triggers), `reviewer_user_id` (on revalidation tasks) and `created_by_user_id` (on deployments and challenger evaluations). Comparisons are made only between two such recorded operator identifiers, or between a recorded identifier and the current `X-User-ID`; a mismatch requirement failing yields `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The three segregation-of-duties rules are described in §2.10.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two optional query parameters. `limit` defaults to 10 when omitted, must be an integer, and must lie between a minimum of 1 and a maximum of 100 inclusive. `offset` defaults to 0 when omitted, must be an integer, and must be greater than or equal to 0. An explicitly supplied value outside those ranges is an error, not something the server silently clamps: it is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

Unless a specific list endpoint declares a different ordering in its §4 description, list results are sorted by `created_at` ascending. Four endpoints declare a domain-specific ordering instead, and those orderings are load-bearing because downstream calculations read the first row: observation windows are ordered by `window_end` descending then `created_at` descending; skew checks are ordered by `checked_at` descending then `created_at` descending; retraining triggers are ordered by `total_urgency` descending then `created_at` ascending; revalidation tasks are ordered by `due_at` ascending then `created_at` ascending. The ramp-step ledger, both through the per-deployment read and through the flat collection, is ordered by `created_at` ascending.

For list responses the `meta` block carries `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of rows matching the filters before pagination is applied, and `has_more` is true when rows remain beyond the current page.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries an `id` that is a server-minted UUID with no type prefix; clients never supply it. Eleven of the thirteen resource families additionally carry `created_at`, `updated_at` and `version`. `created_at` and `updated_at` are ISO 8601 UTC timestamps with three fractional digits. `version` is an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row, including mutations applied to it as a side effect of a request that targeted a different resource. Whenever a row's `version` increments, its `updated_at` is refreshed to the same instant.

Two resource families are deliberately append-only and therefore carry **only** `id` and `created_at` — they have no `updated_at` field and no `version` field at all: the traffic-ramp ledger rows, and nothing else. Ramp-ledger rows are immutable once written; the audit trail they form is the witness for the compensation invariants described in §2.5 and §3.4. (All twelve other families — registry entries, training-data snapshots, artifact versions, serving clusters, deployments, observation windows, drift reports, skew checks, retraining triggers, challenger evaluations, prediction incidents and revalidation tasks — carry the full `id` / `created_at` / `updated_at` / `version` set.)

Time in this service is a **logical clock**, not wall-clock time. Before any operator sets it, the clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. An administrative capability replaces the clock's value with a supplied `current_utc` instant and reports both the new value and the `previous_utc` value it replaced. The clock is monotonic: a `current_utc` that is not strictly after the clock's present value is rejected with `ERR_CLOCK_REGRESSION` (HTTP 409), because rewinding it would invalidate instants the server has already stamped. Every timestamp the server writes reads this clock — `created_at`, `updated_at`, `approved_at`, `closed_at`, `checked_at`, `opened_at`, `resolved_at`, `decided_at`, `swept_at` and `clock_at_step` — and every deadline comparison in the specification means "compared against the logical clock's present value".

### 2.5. Numeric Precision and Rounding Discipline

Unless a rule says otherwise, monetary-style and percentage quantities are carried at **2 decimal places and rounded half up**. Four places of precision are used where a threshold comparison needs the extra resolution: drift indices, per-feature skew ratios, per-metric promotion lines and promotion scores are all carried at 4 decimals, rounded half up. Sample counts are integers with no rounding at all.

Three rounding rules are pinned deliberately, and a naive implementation gets each of them wrong:

1. **The composite health score rounds once, at the end.** Its three weighted components are carried in full floating-point precision, summed, multiplied by 100, and only then rounded half up to two decimals. Rounding the individual components first is not the specified order.
2. **The promotion score rounds twice, in a fixed order.** Each of the four weighted per-metric lines is rounded half up to four decimals *first*; the four rounded lines are then summed; the sum is then rounded half up to four decimals again. Summing in full precision and rounding once produces a different fourth decimal and is not the specified order. A resulting negative zero is normalised to `0.0000`.
3. **The degraded ramp halving truncates toward zero.** When a deployment's health dimension is degraded, the halved step size is truncated toward zero at two decimals rather than rounded half up, so a raw step of 5 percentage points halves to exactly 2.50 and a raw step of 4.99 percentage points halves to exactly 2.49.

Two further precision rules apply where a distribution is involved. Expected bin proportions used for drift scoring are each rounded half up to four decimals *before* the index sum is accumulated; the sum itself is carried in full precision and rounded once to four decimals at the end. Documentation and reproducibility percentages are carried to two decimals, rounded half up. Days added to an instant are always whole days, and the time-of-day component of the anchor instant is preserved exactly.

### 2.6. Stale-Version Guards on Capacity-Bearing Parents

Two creation operations write into a ledger that belongs to a parent row, and for both the client's view of that parent can be stale in a way no state precondition can detect. Both are guarded by an optimistic-concurrency check on the parent's `version`.

Creating a deployment requires a non-optional `expected_serving_endpoint_version` field in the request body, carrying the `version` the client last observed on the target serving cluster. If that value does not equal the cluster's current `version`, the create is rejected with `ERR_STALE_SERVING_ENDPOINT_VERSION` (HTTP 412). A second deployment on the same cluster is entirely legitimate whenever headroom remains, so the rejection cannot be expressed as a state rule; what it prevents is a caller writing against a capacity ledger, an operator posture or a cooldown geometry it has not actually seen. A successful create increments the cluster's `version` by 1, which is why a client that creates two deployments back to back must re-read the cluster between them.

Scheduling a champion-challenger evaluation requires a non-optional `expected_model_version` field in the request body, carrying the `version` the client last observed on the target registry entry. If that value does not equal the registry entry's current `version`, the create is rejected with `ERR_STALE_MODEL_VERSION` (HTTP 412). Here the stale reads that matter are `champion_version_id` and `open_retraining_trigger_count` — a newly created evaluation legitimately supersedes the caller's understanding of which artifact is champion, so again a state precondition cannot express the rule. A successful create increments the registry entry's `version` by 1.

No other endpoint in the service accepts a version field. The stale-version check is evaluated after header authentication, role authorization, path-identifier resolution, body foreign-key resolution and interval shape, but **before** every state rule and every business rule. A stale-version request aimed at a frozen serving cluster therefore returns 412, not the cluster-posture error.

### 2.7. The Validation Ladder

Every request walks a single ordered ladder of checks and returns the **first** violated rule. The ladder is what makes error responses predictable when several things are wrong at once; the domain rationale for its shape is that an ML serving surface is a safety-before-money problem — a model that predicts badly is worse than a model that is expensive — so safety rules precede referential rules, which precede constraint rules, which precede temporal rules, which precede capacity and quota rules. The bands, in evaluation order:

**Authentication and authorization.** Header presence and role validity (`ERR_UNAUTHENTICATED`, 401) comes first, then endpoint role membership (`ERR_ROLE_NOT_PERMITTED`, 403).

**Existence and shape.** Then every identifier in the URL path is resolved, left to right in path order, each against its own not-found code. Then every foreign-key identifier supplied in the request body is resolved, in the order the endpoint declares its input fields. Then general field shape: required fields present, JSON types correct, enum values inside their declared sets, numeric fields inside their declared ranges (percentages between 0 and 100, proportions between 0.0 and 1.0, counts at least 0) — all under `ERR_INVALID_REQUEST` (400). Four specialised shape codes are raised **in preference to** `ERR_INVALID_REQUEST` when the offending field is identifiable, and they are evaluated in this order: bin-proportion arrays (`ERR_INVALID_BIN_PROPORTIONS`), label-count consistency (`ERR_LABEL_COUNT_INCONSISTENT`), feature-statistics maps (`ERR_INVALID_FEATURE_STATS`) and metric maps (`ERR_INVALID_METRIC_SET`). Pagination range checking (`ERR_INVALID_PAGINATION`) closes the band.

**Interval shape and clock monotonicity.** Strict interval ordering (`ERR_INVALID_INTERVAL`, 400) is checked next, before any overlap rule, so a self-inverted interval is never compared against a stored one. Clock monotonicity (`ERR_CLOCK_REGRESSION`, 409) sits at the same rank for the clock capability.

**Stale-version guards.** The two optimistic-concurrency checks of §2.6 (both 412).

**State.** Terminal lockdown (`ERR_TERMINAL_STATE`, 409) is checked before wrong-state (`ERR_INVALID_STATE`, 409) so that callers can distinguish "this row is finished forever" from "this row is not ready yet". The terminal states are: a snapshot that is `REVOKED`; an artifact version that is `REJECTED` or `DEPRECATED`; a deployment whose rollout dimension is `ROLLED_BACK` or `RETIRED`; an observation window that is `CLOSED`, for mutating actions; a challenger evaluation that is `PROMOTED` or `REJECTED`; a retraining trigger that is `SATISFIED`, `DISMISSED` or `STALE`; an incident that is `RESOLVED`; a revalidation task that is `PASSED` or `FAILED`. `ERR_INVALID_STATE` covers every requested transition that is not declared from the row's current non-terminal state, including the parallel health dimension of a deployment where an action reads it. Because `ERR_INVALID_STATE` outranks every business rule, approving an already-approved version returns `ERR_INVALID_STATE` even when that version's snapshot has since been revoked. Then, still in the state band and in this order: window-not-elapsed (`ERR_WINDOW_NOT_ENDED`), window-not-closed (`ERR_WINDOW_NOT_CLOSED`), ramp-exhausted (`ERR_RAMP_ALREADY_COMPLETE`) and manual-override-active (`ERR_MANUAL_OVERRIDE_ACTIVE`), all 409.

**Segregation of duties.** The three `ERR_SEGREGATION_OF_DUTIES` rules (403) sit here, after existence and state. They are business rules, not auth rules: deciding a revoked snapshot as its own registrar returns `ERR_TERMINAL_STATE`, not the segregation code. Within the band the order is: snapshot decision, then version decision, then revalidation review start.

**Safety.** In order: the documentation and reproducibility gate (`ERR_DOCUMENTATION_INCOMPLETE`, 422), the PII-review gate (`ERR_PII_REVIEW_MISSING`, 422), the critical-health block (`ERR_HEALTH_CRITICAL_BLOCKED`, 422), the open-incident block (`ERR_OPEN_INCIDENT_BLOCKS_ACTION`, 422), the failing-skew block (`ERR_SKEW_CHECK_FAILED`, 422), the missing-fallback check (`ERR_FALLBACK_NOT_CONFIGURED`, 422) and the override-magnitude check (`ERR_OVERRIDE_EXCEEDS_CURRENT_TRAFFIC`, 422).

**Referential cross-entity gates.** In order: snapshot-approved (`ERR_DATASET_NOT_APPROVED`), version-approved (`ERR_VERSION_NOT_APPROVED`), cluster-open (`ERR_SERVING_ENDPOINT_NOT_OPEN`), feature-specification identity (`ERR_FEATURE_SPEC_MISMATCH`), window-version attribution (`ERR_WINDOW_VERSION_MISMATCH`), skew-check attribution (`ERR_SKEW_DEPLOYMENT_MISMATCH`), challenger-model membership (`ERR_CHALLENGER_MODEL_MISMATCH`), retraining lineage on registration (`ERR_LINEAGE_MODEL_MISMATCH`) and retraining lineage on linking (`ERR_RETRAINED_VERSION_LINEAGE_INVALID`) — all 422.

**Uniqueness and constraint.** In order: duplicate registry name (`ERR_DUPLICATE_MODEL_NAME`), duplicate semantic version (`ERR_DUPLICATE_SEMVER`), duplicate cluster name (`ERR_DUPLICATE_SERVING_ENDPOINT_NAME`), duplicate open window (`ERR_DUPLICATE_OPEN_WINDOW`), an already-active evaluation (`ERR_ACTIVE_EVALUATION_EXISTS`), challenger pattern shape (`ERR_CHALLENGER_NOT_SHADOW`, 422), extension ceiling (`ERR_MAX_EXTENSIONS_REACHED`), mandatory-retrain block on dismissal (`ERR_RETRAIN_REQUIRED`), still-serving block on deprecation (`ERR_VERSION_STILL_SERVING`), champion-protection block on deprecation (`ERR_CANNOT_DEPRECATE_CHAMPION`) and archived-registry block (`ERR_MODEL_ARCHIVED`).

**Temporal overlap and maturity.** In order: serve-window collision (`ERR_SERVE_WINDOW_CONFLICT`), observation-window overlap (`ERR_MONITORING_WINDOW_OVERLAP`), expired serve window (`ERR_SERVE_WINDOW_EXPIRED`), immature evaluation (`ERR_EVALUATION_NOT_MATURE`), then the two evaluation-arm liveness codes with the challenger arm evaluated first (`ERR_CHALLENGER_NOT_SERVING`) and the champion arm second (`ERR_CHAMPION_NOT_LIVE`), then the general not-serving check (`ERR_DEPLOYMENT_NOT_SERVING`) — all 409.

**Capacity and quota, last.** `ERR_ENDPOINT_CAPACITY_EXHAUSTED` (409), `ERR_SAMPLE_BUDGET_EXCEEDED` (409) and `ERR_NO_LABELED_PREDICTIONS` (422) close the ladder. Capacity is the final gate precisely so that it is only ever returned when the request is otherwise perfectly eligible.

Three ordering conflicts are worth calling out because they are easy to get backwards. First, an already-approved version whose snapshot has been revoked returns `ERR_INVALID_STATE`, not `ERR_DATASET_NOT_APPROVED`. Second, ramping a deployment whose health dimension is `CRITICAL` on a cluster with zero headroom returns `ERR_HEALTH_CRITICAL_BLOCKED`, not `ERR_ENDPOINT_CAPACITY_EXHAUSTED`. Third, an observation window that is both a duplicate open window and an interval overlap returns `ERR_DUPLICATE_OPEN_WINDOW`, not `ERR_MONITORING_WINDOW_OVERLAP`.

### 2.8. Resource Addressing and Nested Reads

The service is mounted at the server root; there is no shared API prefix. Every business collection is addressed at its own top-level path, and relationships between resources are expressed through foreign-key identifiers in bodies and through filtered list queries, not through URL nesting. The only exceptions are three deliberate sub-resource routes: scheduling a challenger evaluation for a registry entry, and the two computed reads under a deployment (its ramp-step ledger and its health summary).

Path identifiers are resolved strictly left to right in path order, each against its own not-found code: `model_id` yields `ERR_MODEL_NOT_FOUND`, `dataset_id` yields `ERR_TRAINING_DATASET_NOT_FOUND`, `version_id` yields `ERR_MODEL_VERSION_NOT_FOUND`, `serving_endpoint_id` yields `ERR_SERVING_ENDPOINT_NOT_FOUND`, `deployment_id` yields `ERR_DEPLOYMENT_NOT_FOUND`, `ramp_step_id` yields `ERR_TRAFFIC_RAMP_STEP_NOT_FOUND`, `window_id` yields `ERR_MONITORING_WINDOW_NOT_FOUND`, `drift_report_id` yields `ERR_DRIFT_REPORT_NOT_FOUND`, `skew_check_id` yields `ERR_SKEW_CHECK_NOT_FOUND`, `retraining_trigger_id` yields `ERR_RETRAINING_TRIGGER_NOT_FOUND`, `evaluation_id` yields `ERR_CHALLENGER_EVALUATION_NOT_FOUND`, `incident_id` yields `ERR_PREDICTION_INCIDENT_NOT_FOUND` and `revalidation_task_id` yields `ERR_REVALIDATION_TASK_NOT_FOUND`. Left-to-right means that scheduling an evaluation under a nonexistent registry entry returns `ERR_MODEL_NOT_FOUND` even when the body's `champion_deployment_id` is also bogus.

Foreign-key identifiers supplied in a request body are resolved after all path identifiers and before any field-shape validation, so a body carrying both a dangling reference and a malformed enum value returns the 404. Body references resolve against the same code family as their target: `model_id` and `training_dataset_id` against the registry and snapshot codes; `model_version_id`, `parent_version_id` and `retrained_version_id` against `ERR_MODEL_VERSION_NOT_FOUND`; `serving_endpoint_id` against `ERR_SERVING_ENDPOINT_NOT_FOUND`; `deployment_id`, `champion_deployment_id` and `challenger_deployment_id` against `ERR_DEPLOYMENT_NOT_FOUND`; `monitoring_window_id` against `ERR_MONITORING_WINDOW_NOT_FOUND`.

Every foreign key in the model is reverse-reachable through a filtered list query, so an operator can always walk the graph in either direction. Ramp-ledger rows are reachable both through the per-deployment nested read and through the flat ramp-step collection filtered by `deployment_id`.

### 2.9. Cascade Discipline

The service is immediately consistent. Every cascade completes inside the request that triggered it; there is no deferred reconciliation, no read-repair and no background worker. The single epoch-style batch operation — the revalidation and staleness sweep — is an explicit operator call, not a scheduled job.

Three cascades in the specification are multi-hop, and each hop is described in the workflow subsection where it belongs. What is universal is the bookkeeping: **every row a cascade mutates has its `version` incremented by 1 and its `updated_at` refreshed**, whether it was the request's target or a fourth-hop bystander. When a cascade hop iterates over a set of rows — dependent artifact versions, their deployments, the challenger evaluations on those deployments — the rows are processed in `created_at` ascending order, so the resulting ledger of ramp-step rows and the resulting sequence of version increments are deterministic.

Ledgers are always recomputed from their contributing rows, never incrementally patched. A serving cluster's allocated traffic is re-summed from its deployments on every write that could change it; an artifact version's evaluation-sample budget is re-derived from the evaluations holding reservations against it. This is what makes the two compensation invariants exact rather than approximate: after a rollback, a deployment's traffic is exactly 0.00, the sum of its ramp-step deltas is exactly 0.00, and the cluster's allocated traffic is exactly what it was immediately before that deployment's first ramp. Likewise, once every evaluation on an artifact version has ended in a non-promoted outcome, that version's sample budget is exactly its quota again.

### 2.10. Segregation of Duties

Three separations are enforced by comparing `X-User-ID` against a previously recorded operator identifier, and all three yield `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

The operator deciding a training-data snapshot must not be the operator who registered it — the acting `X-User-ID` must differ from that snapshot's `registered_by_user_id`. The operator deciding an artifact version must not be the operator who submitted it for review — the acting `X-User-ID` must differ from that version's `submitted_by_user_id`, and this holds even when the submitter genuinely holds the `ModelApprover` role. The operator taking a periodic revalidation task into review must not be the operator who approved the version in the first place — the acting `X-User-ID` must differ from the referenced version's `decided_by_user_id`. Once a revalidation task is in review, the reverse constraint applies to its disposition: the operator passing or failing it must be the same operator recorded as `reviewer_user_id`, and a different operator attempting the disposition is rejected with the same code.

## 3. Business Logic & Workflows

### 3.1. Registry Entries and Their Champions

Everything in this service hangs off a **registry entry** — the durable record of "a model" as the organisation talks about it, distinct from the artifact versions that implement it. An `MLEngineer` or a `PlatformAdmin` registers one by supplying a `name`, a `task_type` and an `owner_team`. The `name` is between 1 and 120 characters; the `owner_team` is a team slug between 1 and 60 characters; `task_type` is exactly one of `CLASSIFICATION`, `REGRESSION` or `RANKING`. Registry names are unique per owning team: the pair of `name` and `owner_team` must not already exist, compared as a case-sensitive exact match on both members, and a collision is rejected with `ERR_DUPLICATE_MODEL_NAME`. The caller's `X-User-ID` is stamped onto `registered_by_user_id`.

One optional input governs the entry's revalidation cadence. `revalidation_interval_days` is an integer between 1 and 365 and defaults to 90 when omitted; it is the number of days between periodic revalidations of every approved version of this entry. No endpoint mutates it afterwards — it is immutable once the entry exists, so the cadence a team commits to at registration is the cadence they live with.

A fresh entry starts with `registry_status` of `ACTIVE`, a null `champion_version_id`, a null `champion_promoted_at` and an `open_retraining_trigger_count` of 0. `registry_status` is one of `ACTIVE` or `ARCHIVED`, and the only way to reach `ARCHIVED` is an administrative archive action available to `PlatformAdmin` alone, which sets `registry_status` to `ARCHIVED` and increments the entry's `version`. Archiving is a soft freeze on *new* work rather than a shutdown: existing deployments keep serving their traffic, but registering a new artifact version against an archived entry and scheduling a new champion-challenger evaluation for it are both rejected with `ERR_MODEL_ARCHIVED`.

Three fields on the entry are computed and never written directly by a client. `champion_version_id` points at whichever artifact version is currently serving as champion; it stays null until either the promotion outcome of a champion-challenger evaluation writes it, or a real-time deployment of an approved version completes its traffic ramp and reaches `LIVE`, which writes the deployed version into it. Whenever `champion_version_id` is written, `champion_promoted_at` is stamped with the logical clock's present instant. `open_retraining_trigger_count` is the number of retraining triggers for this entry whose `status` is `PROPOSED`, `ACKNOWLEDGED` or `IN_PROGRESS`, and it is recomputed every time any of those triggers changes state.

Reading a single entry returns all of the above. The list view can be narrowed by `owner_team`, by `task_type`, by `registry_status` and by `champion_version_id`, which is how an operator answers "which registry entry currently promotes this artifact?" in one query.

### 3.2. Training-Data Snapshots: Registration, Approval and Revocation

No artifact version may be approved without an approved reference to the frozen data it was fitted on. A **training-data snapshot** is that reference. An `MLEngineer` or a `DataSteward` registers one with a `name` between 1 and 120 characters, a `snapshot_uri` between 1 and 400 characters naming the immutable storage location of the frozen data, a `row_count` of at least 1, a `feature_hash` between 1 and 80 characters digesting the feature-pipeline specification that materialised the snapshot, a `license_class` of `OPEN`, `INTERNAL` or `RESTRICTED`, a `baseline_positive_rate` between 0.0 and 1.0 recording the positive-class rate observed in the snapshot, and a `baseline_bin_proportions` array. That array is the expected distribution of the monitored feature and must contain exactly five numbers, each between 0.0 and 1.0, whose sum is within 0.0001 of 1.0; anything else is rejected with `ERR_INVALID_BIN_PROPORTIONS`, because a distribution that does not sum to one would make every subsequent drift index meaningless and normalising it silently would hide the operator's mistake. An optional `pii_review_passed` boolean defaults to false. `registered_by_user_id` is stamped from the caller's `X-User-ID`, `dependent_version_count` is initialised to 0, and `approval_state` starts at `DRAFT`.

The `approval_state` dimension moves through `DRAFT`, `SUBMITTED`, `APPROVED`, `REJECTED` and `REVOKED`, with `REVOKED` terminal. Submitting a snapshot — available to `MLEngineer` and `DataSteward` — takes it from `DRAFT` to `SUBMITTED`, but only when `pii_review_passed` is true and the `baseline_bin_proportions` array still satisfies the five-entry, sums-to-one condition; a snapshot whose PII review has not passed is rejected with `ERR_PII_REVIEW_MISSING`. The transition increments the snapshot's `version` and refreshes `updated_at`.

The same submit capability carries the **resubmission loop** of this machine. When it is invoked on a snapshot whose `approval_state` is `REJECTED`, the row first returns `REJECTED → DRAFT` — clearing `decided_by_user_id` and `decided_at` back to null — and then, in the very same request, the `DRAFT → SUBMITTED` transition is applied. A single call therefore lands on `SUBMITTED` with a cleared decision record. The `pii_review_passed` requirement applies to this path exactly as it does to the plain `DRAFT → SUBMITTED` path.

Deciding a submitted snapshot is exclusive to `DataSteward` and takes a `decision` of either `APPROVE` or `REJECT`, plus an optional free-text `note`. The acting operator must not be the snapshot's registrar. `APPROVE` moves `SUBMITTED → APPROVED`, stamps `decided_by_user_id` from `X-User-ID` and `decided_at` from the logical clock, and increments `version`. `REJECT` moves `SUBMITTED → REJECTED` with the same two stamps, and additionally recomputes `dependent_version_count`: a rejected snapshot keeps whatever count it had, because rejection does not delete the versions pointing at it — it only makes them unapprovable.

`dependent_version_count` is the count of artifact versions whose `training_dataset_id` names this snapshot and whose own `approval_state` is anything other than `REJECTED`. It is recomputed whenever a version is registered against the snapshot and whenever any version's `approval_state` changes. A rejected version stops being a dependency; a blocked one keeps counting, because a blocked version can still recover to `APPROVED`. Consider a snapshot with three versions — one approved and serving, one still in draft, one rejected: its `dependent_version_count` is 2, and it stays 2 after the approved one is pushed into `BLOCKED`, since blocked rows remain dependencies.

Revoking an approved snapshot is available to `DataSteward` and `PlatformAdmin`, requires a `revocation_reason` in the body, and is the single most consequential action in the service. It is permitted regardless of `dependent_version_count` — that counter exists so the blast radius is observable before and after, not to block the revocation. The `APPROVED → REVOKED` transition records `revocation_reason`, stamps `decided_at` from the logical clock, and then walks a four-hop cascade. Hop 1 is the snapshot's own transition. Because the snapshot left `APPROVED`, hop 2 takes every artifact version whose `training_dataset_id` names this snapshot and whose `approval_state` is `APPROVED` from `APPROVED` to `BLOCKED`, writing `blocked_reason` of `TRAINING_DATA_REVOKED`, processing those versions in `created_at` ascending order. Because each of those versions entered `BLOCKED`, hop 3 takes every deployment referencing such a version whose `rollout_state` is `RAMPING`, `HELD` or `LIVE` into `DRAINING`, sets its `traffic_pct` to 0.00, appends one ramp-ledger row whose `reason` is `DRAIN_RELEASE` and whose `delta_pct` is the negative of the traffic the deployment held immediately before, and recomputes the owning serving cluster's `allocated_traffic_pct`; those deployments are also processed in `created_at` ascending order. Because each of those deployments left the serving set, hop 4 takes every challenger evaluation whose `champion_deployment_id` or `challenger_deployment_id` names such a deployment and whose `status` is `COLLECTING` from `COLLECTING` to `INCONCLUSIVE`, appends `DEPLOYMENT_DRAINED` to that evaluation's `criteria_failures`, and returns its `reserved_samples` to the challenger version's `evaluation_sample_budget`; evaluations are processed in `created_at` ascending order. The snapshot's `version` increments, as does the `version` of every row touched by hops 2, 3 and 4, and `dependent_version_count` is recomputed at the end.

Snapshot lists can be narrowed by `approval_state`, by `license_class` and by `pii_review_passed`, which is how a steward finds the queue of snapshots waiting for a PII review to land.

### 3.3. Artifact Versions: Registration, Documentation, Review and Approval

An **artifact version** is a concrete trained model bound to one registry entry and one training snapshot. Registration is exclusive to `MLEngineer` and requires a `model_id` naming the registry entry, a `training_dataset_id` naming the snapshot, a `semver` string, an `artifact_digest` between 1 and 120 characters, a `feature_spec_hash`, and three offline baselines: `baseline_accuracy` between 0.0 and 1.0, `baseline_positive_rate` between 0.0 and 1.0, and `baseline_p95_latency_ms` of at least 1 millisecond. The `semver` must match the three-part numeric shape of a major, minor and patch component separated by dots, each component being one or more digits, and it must be unique among the versions of the same registry entry; a collision is rejected with `ERR_DUPLICATE_SEMVER`, since duplicate version strings would make a rollback conversation ambiguous. Registration against an archived registry entry is rejected with `ERR_MODEL_ARCHIVED`.

Feature-pipeline consistency is enforced **structurally, twice**, and the first enforcement happens here: the submitted `feature_spec_hash` must be exactly equal to the `feature_hash` of the snapshot named by `training_dataset_id`, or the registration is rejected with `ERR_FEATURE_SPEC_MISMATCH`. The second enforcement happens at deployment time, against the serving cluster; statistical divergence between training and serving is a separate concern handled by skew detection at runtime.

Retraining lineage is expressed with an optional `parent_version_id` naming the predecessor this artifact was retrained from; it is null for a registry entry's first version. When supplied, the referenced version must belong to the same registry entry — the same `model_id` — or the registration is rejected with `ERR_LINEAGE_MODEL_MISMATCH`, because retraining lineage may not cross registry entries.

Two optional arrays carry the version's paper trail. `doc_sections` defaults to an empty array and holds documentation-section keys, each of which must be one of `INTENDED_USE`, `TRAINING_DATA`, `EVALUATION`, `LIMITATIONS` or `ETHICAL_REVIEW`. `repro_artifacts` also defaults to an empty array and holds reproducibility-artifact keys, each of which must be one of `TRAINING_CODE_COMMIT`, `ENV_LOCKFILE_DIGEST`, `RANDOM_SEED` or `FEATURE_SPEC_HASH`. A duplicate entry in either array is rejected with `ERR_INVALID_REQUEST`. From these two arrays the service derives two percentages. `doc_completeness_pct` is 100 multiplied by the number of the five required documentation keys that appear in `doc_sections`, divided by 5, rounded half up to two decimals. `reproducibility_score` is 100 multiplied by the number of the four required reproducibility keys that appear in `repro_artifacts`, divided by 4, rounded half up to two decimals. A required key counts as present when it appears at least once, counts once no matter how often it appears, and array members outside the two required lists are ignored entirely and never raise either percentage.

Registration also initialises the evaluation-sample ledger. `evaluation_sample_quota` is an optional integer between 1 and 1,000,000 that defaults to 50,000; it is the total number of labelled prediction samples this version may reserve across all of its challenger evaluations. `evaluation_sample_budget` starts equal to the quota. Registration finally recomputes the snapshot's `dependent_version_count` and increments the snapshot's `version` by 1.

An `MLEngineer` may replace a version's documentation at any point while it is in `DRAFT` or `CHANGES_REQUESTED`. The documentation update supplies `doc_sections` and `repro_artifacts` and **replaces both arrays wholesale — there is no merge** — then recomputes `doc_completeness_pct` and `reproducibility_score` and increments the version's `version` by 1. This capability also carries the revision loop of the approval machine: applied to a version in `CHANGES_REQUESTED`, it moves the row `CHANGES_REQUESTED → DRAFT` and clears `decided_by_user_id` back to null, so the version can be resubmitted. Applied to a version already in `DRAFT` it leaves `approval_state` alone. Attempting it on any other state is rejected with `ERR_INVALID_STATE`.

The `approval_state` dimension of an artifact version spans `DRAFT`, `PENDING_REVIEW`, `CHANGES_REQUESTED`, `APPROVED`, `BLOCKED`, `REJECTED` and `DEPRECATED`, with `REJECTED` and `DEPRECATED` terminal. Submitting for review is exclusive to `MLEngineer` and moves `DRAFT → PENDING_REVIEW`. It is gated on the **documentation and reproducibility gate**: `doc_completeness_pct` must be at least 80.00 and `reproducibility_score` must be at least 100.00, or the request is rejected with `ERR_DOCUMENTATION_INCOMPLETE`. There is no partial credit on reproducibility — four of five documentation sections with all four artifacts satisfies the gate exactly at the 80.00 boundary, three of five sections does not, and five of five sections with only three of four artifacts does not either. Submission also requires the owning registry entry to be `ACTIVE`, rejecting with `ERR_MODEL_ARCHIVED` otherwise, stamps `submitted_by_user_id` from the caller's `X-User-ID`, recomputes both percentages, and increments the version's `version` by 1.

Deciding a version is exclusive to `ModelApprover` and takes a `decision` of `APPROVE`, `REQUEST_CHANGES` or `REJECT`, plus an optional `note`. In every case the acting operator must not be the version's submitter. `REQUEST_CHANGES` moves `PENDING_REVIEW → CHANGES_REQUESTED`, stamps `decided_by_user_id` and increments `version`. `REJECT` moves `PENDING_REVIEW → REJECTED`, stamps `decided_by_user_id`, recomputes the snapshot's `dependent_version_count` — a rejected version leaves that count — and increments both the version's `version` and the snapshot's `version` by 1.

`APPROVE` from `PENDING_REVIEW` is the busiest transition in the registry. It requires the documentation and reproducibility gate to still hold, requires the snapshot's `pii_review_passed` to be true, and requires the snapshot named by `training_dataset_id` to be in `approval_state` `APPROVED`, rejecting with `ERR_DATASET_NOT_APPROVED` otherwise. On success it stamps `decided_by_user_id` from `X-User-ID`, stamps `approved_at` with the logical clock's present instant, and computes `revalidation_due_at` as `approved_at` plus the owning registry entry's `revalidation_interval_days` whole days, preserving the time-of-day component of `approved_at` exactly. It increments the version's `version` by 1 and also increments the registry entry's `version` by 1, since the entry's computed counters are re-read on approval.

Two recovery paths exist out of `BLOCKED`. A version enters `BLOCKED` only as a cascade — either hop 2 of a snapshot revocation, which writes `blocked_reason` of `TRAINING_DATA_REVOKED`, or hop 2 of a failed periodic revalidation, which writes `blocked_reason` of `REVALIDATION_FAILED` and additionally clears `revalidation_due_at` back to null. Either way, entering `BLOCKED` triggers the deployment-draining hop on that version's non-terminal deployments, and increments the version's `version` by 1. From `BLOCKED`, a `ModelApprover` can restore the version with the same `APPROVE` decision — a recovery cycle that skips a fresh review round. `BLOCKED → APPROVED` requires the acting operator not to be the submitter and requires the referenced snapshot to be `APPROVED` again (or repointed to an approved snapshot), rejecting with `ERR_DATASET_NOT_APPROVED` otherwise. On success it clears `blocked_reason` to null, stamps `decided_by_user_id` and a fresh `approved_at`, recomputes `revalidation_due_at` from that new anchor, and increments `version` by 1.

Deprecation, available to `ModelApprover` and `PlatformAdmin`, is the terminal retirement of a version and is accepted from `APPROVED` or from `BLOCKED`. It is rejected with `ERR_VERSION_STILL_SERVING` while any deployment of the version has a `rollout_state` of `RAMPING`, `HELD`, `LIVE` or `DRAINING` — traffic must be drained first — and rejected with `ERR_CANNOT_DEPRECATE_CHAMPION` when the version is the one named by the registry entry's `champion_version_id`, because the registry must always be able to name its champion and a replacement has to be promoted first. On success it clears `revalidation_due_at` to null so no future sweep raises work for it, forces every revalidation task for this version whose `status` is `DUE` or `IN_REVIEW` to `PASSED` with `findings` set to `VERSION_DEPRECATED` — such tasks are never simply abandoned — recomputes the snapshot's `dependent_version_count`, and increments the version's `version` by 1 along with the `version` of every revalidation task it closed.

Version lists can be narrowed by `model_id`, by `training_dataset_id`, by `parent_version_id` and by `approval_state`; filtering by `parent_version_id` is how an operator walks a retraining lineage forwards.

### 3.4. Serving Clusters, Deployment Creation, Traffic Ramping and Rollout Control

A **serving cluster** is a capacity pool in one region. `PlatformAdmin` and `ReliabilityEngineer` register one with a `name` between 1 and 120 characters, a `region` slug between 1 and 40 characters, and a `serving_feature_spec_hash` between 1 and 80 characters digesting the feature-pipeline specification the cluster actually serves. Cluster names are unique within a region: the pair of `name` and `region` must not already exist, compared as a case-sensitive exact match on both members, and a collision is rejected with `ERR_DUPLICATE_SERVING_ENDPOINT_NAME`. Two optional inputs shape the cluster's geometry. `max_traffic_pct` is the total traffic percentage the cluster may have allocated across all of its non-terminal deployments; it carries two decimals, lies between 1.00 and 100.00, and defaults to 100.00 when omitted. `deploy_cooldown_minutes` is an integer between 0 and 240 that defaults to 30; it is the trailing buffer appended to every deployment's serve window when the cluster tests for serve-window collisions. A new cluster starts with `allocated_traffic_pct` of 0.00 and `operational_state` of `OPEN`.

`operational_state` is one of `OPEN`, `FROZEN` or `DRAINED`, and `PlatformAdmin` or `ReliabilityEngineer` can set it directly by supplying the desired `operational_state`. This is a posture switch on *new* traffic only: existing allocations are untouched, but while the cluster is `FROZEN` or `DRAINED`, both creating a deployment on it and ramping any deployment on it are rejected with `ERR_SERVING_ENDPOINT_NOT_OPEN`. Setting the posture increments the cluster's `version` by 1. Cluster lists can be narrowed by `region` and by `operational_state`.

`allocated_traffic_pct` is the cluster's **traffic ledger** and is never patched incrementally. It is the sum of `traffic_pct` over exactly those deployments whose `serving_endpoint_id` names this cluster and whose `rollout_state` is `RAMPING`, `HELD`, `LIVE` or `DRAINING`, rounded half up to two decimals. Deployments in `PENDING`, `ROLLED_BACK` or `RETIRED` contribute nothing at all — a retired deployment that once held 65.00 percentage points releases every one of them. The ledger is recomputed from scratch after every write that could change any contributing deployment's `traffic_pct` or `rollout_state`: deployment creation, every ramp, every rollout action, the fallback-engagement and manual-override incident actions, and the draining hop of a snapshot revocation or a failed revalidation.

Creating a deployment is exclusive to `ReliabilityEngineer` and requires a `model_version_id`, a `serving_endpoint_id`, a `pattern`, a `serve_from`, a `serve_until`, and the `expected_serving_endpoint_version` stale-version token described in §2.6. An optional `fallback_strategy` defaults to `NONE`. `pattern` is one of `BATCH`, `REALTIME` or `SHADOW` and selects both the ramp checkpoint table and the headroom reserve rule. `fallback_strategy` is one of `NONE`, `PREVIOUS_CHAMPION`, `STATIC_DEFAULT` or `RULE_BASED` and declares what prediction path is available if an incident engages fallback. The serve interval is half-open — `serve_from` is inclusive and `serve_until` is exclusive — and `serve_until` must be strictly greater than `serve_from`, or the create is rejected with `ERR_INVALID_INTERVAL`.

Three cross-entity gates guard creation. The referenced artifact version's `approval_state` must be `APPROVED`, or the create is rejected with `ERR_VERSION_NOT_APPROVED`; a version pushed into `BLOCKED` by a cascade cannot receive new traffic even though its existing deployment rows survive. The cluster's `operational_state` must be `OPEN`. And the second structural feature-pipeline identity applies: the cluster's `serving_feature_spec_hash` must be exactly equal to the version's `feature_spec_hash`, or the create is rejected with `ERR_FEATURE_SPEC_MISMATCH`.

Serve windows do not collide within a pattern on a cluster. The new deployment's half-open interval, extended by the cluster's trailing `deploy_cooldown_minutes` buffer, must not overlap the interval of any existing non-terminal deployment that shares the same `serving_endpoint_id` and the same `pattern`; a collision is rejected with `ERR_SERVE_WINDOW_CONFLICT`. The buffer is deliberately **asymmetric and trailing**: a new `serve_from` must be at or after the existing deployment's `serve_until` plus `deploy_cooldown_minutes` minutes, whereas a new `serve_until` exactly equal to an existing `serve_from` is allowed with no buffer at all, because the half-open geometry means the two intervals do not actually share an instant.

A newly created deployment starts with `rollout_state` of `PENDING`, `health_state` of `HEALTHY`, `traffic_pct` of 0.00, `ramp_step_index` of 0, `cumulative_ramp_delta_pct` of 0.00, `manual_override_active` false, a null `override_traffic_pct`, a null `health_score_provisional`, a null `health_score_final` and a null `rolled_back_at`. Its `target_traffic_pct` is set to the final checkpoint of its pattern's ramp table, which is 100.00 for every pattern. `created_by_user_id` is stamped from the caller's `X-User-ID`. The cluster's ledger is recomputed — a `PENDING` deployment contributes 0.00 — and the cluster's `version` increments by 1.

Deployments carry **two independent state dimensions on the same row**. `rollout_state` spans `PENDING`, `RAMPING`, `HELD`, `LIVE`, `DRAINING`, `ROLLED_BACK` and `RETIRED`, with `ROLLED_BACK` and `RETIRED` terminal. `health_state` spans `HEALTHY`, `DEGRADED` and `CRITICAL`, has no terminal state, and evolves entirely independently of the rollout dimension — it is driven by drift severity, by window closures and by incident resolution, never by a rollout action.

Ramping is exclusive to `ReliabilityEngineer` and takes no body at all. Each call advances the deployment one step along its pattern's checkpoint table and appends exactly one row to the immutable traffic-ramp ledger. The checkpoint tables are fixed by pattern and expressed in percentage points of cluster traffic: a `REALTIME` deployment steps through 5, 15, 35, 65 and 100; a `SHADOW` deployment steps through 10, 50 and 100; a `BATCH` deployment steps through 50 and 100. The first successful ramp moves `PENDING → RAMPING`. Subsequent ramps hold the row at `RAMPING` while checkpoints remain. The ramp that advances `ramp_step_index` to exactly the number of checkpoints in the table moves `RAMPING → LIVE`.

Before any of that, the ramp planner runs, and it is the most intricate calculation in the service. Its inputs are the single deployment being ramped plus its serving cluster; no other deployment is read directly, because every other deployment's contribution arrives through the cluster's `allocated_traffic_pct`. The planner proceeds in six steps, in this order:

1. **Checkpoint selection.** If `ramp_step_index` is already greater than or equal to the number of checkpoints in the pattern's table, there is nothing left to advance to and the request is rejected with `ERR_RAMP_ALREADY_COMPLETE`. Otherwise the *nominal target* is the checkpoint sitting at position `ramp_step_index` in that table, counting from zero. The *raw step* is the nominal target minus the deployment's current `traffic_pct`.
2. **The health branch.** When `health_state` is `DEGRADED`, the raw step is multiplied by one half and the product is truncated toward zero at two decimals — not rounded half up — producing the capped step. When `health_state` is `HEALTHY`, the capped step is the raw step unchanged. A `CRITICAL` deployment never reaches this point, because it is blocked earlier by the safety band.
3. **The per-step ceiling.** The step size is the smaller of the capped step and 30 percentage points; no single ramp may ever move more than 30 points of traffic.
4. **The pattern branch.** When the deployment's `pattern` is `REALTIME` **and** the nominal target is strictly less than the last checkpoint in the table, a headroom reserve of 5 percentage points is held back from the cluster. In every other case — any non-`REALTIME` pattern, or a `REALTIME` step whose nominal target is the final checkpoint — the reserve is 0.
5. **The headroom clamp.** The available headroom is the cluster's `max_traffic_pct`, minus the reserve, minus the cluster's current `allocated_traffic_pct` (which already includes whatever this deployment itself currently holds once it is ramping). The *granted delta* is the larger of 0 and the smaller of the step size and the available headroom. If the granted delta is exactly 0, the request is rejected with `ERR_ENDPOINT_CAPACITY_EXHAUSTED`.
6. **The landing test.** The new `traffic_pct` is the current `traffic_pct` plus the granted delta, rounded half up to two decimals. `ramp_step_index` advances by 1 **only when the new `traffic_pct` equals the nominal target exactly**. A partial grant leaves the index where it was, so the next ramp re-aims at the same checkpoint.

Walking a `REALTIME` deployment up an otherwise empty cluster whose `max_traffic_pct` is 100.00 illustrates both the reserve and the partial landing. The first four ramps aim at 5, 15, 35 and 65, each raw step (5, 10, 20 and 30 points) fitting inside both the 30-point ceiling and the headroom left after the 5-point reserve, so `traffic_pct` lands exactly on each checkpoint and `ramp_step_index` advances each time. The fifth ramp aims at 100, so the reserve drops to 0, but the raw step of 35 points is trimmed to 30 by the per-step ceiling and further trimmed to the 35 points of headroom that remain; the deployment lands on 95.00 rather than 100.00, so `ramp_step_index` does not advance. A sixth ramp aims at 100 again, moves the last 5 points, lands exactly on the checkpoint, advances the index to 5 and therefore takes the row `RAMPING → LIVE`. Had that same deployment been at 15.00 on index 2 with `health_state` of `DEGRADED`, the raw step of 20 points would have halved to exactly 10.00 and the deployment would have landed on 25.00 with the index still at 2.

Each ramp writes one ledger row and refreshes several derived quantities. The ledger row records `deployment_id`, a `step_index` equal to the deployment's `ramp_step_index` **before** any advance, `from_traffic_pct` and `to_traffic_pct` bracketing the move, a `delta_pct` equal to the granted delta, a `reason` of `RAMP_STEP`, a `health_state_at_step` equal to the `health_state` observed when the step was computed, and a `clock_at_step` stamped from the logical clock. The deployment's `cumulative_ramp_delta_pct` is then recomputed as the sum of `delta_pct` over all of its ledger rows ordered by `created_at` ascending, rounded half up to two decimals, and the cluster's `allocated_traffic_pct` is recomputed. The deployment's `version` and the cluster's `version` each increment by 1. When the ramp that reaches `LIVE` belongs to a `REALTIME` deployment, it also writes the deployed `model_version_id` into the owning registry entry's `champion_version_id`, stamps `champion_promoted_at` from the logical clock and increments the registry entry's `version` by 1 — this is the non-experimental path by which a registry entry acquires its first champion.

Ramping is gated by an unusually long list of preconditions, and every one of them is re-checked on every call, whether the transition is `PENDING → RAMPING`, `RAMPING → RAMPING` or `RAMPING → LIVE`. The cluster's `operational_state` must be `OPEN`. `health_state` must not be `CRITICAL`, rejecting with `ERR_HEALTH_CRITICAL_BLOCKED`. `manual_override_active` must be false, rejecting with `ERR_MANUAL_OVERRIDE_ACTIVE`, because while an incident's override pins `traffic_pct` the planner must not move it and the override has to be released through the incident first. `serve_until` must be strictly after the logical clock's present value, rejecting with `ERR_SERVE_WINDOW_EXPIRED`. No prediction incident on this deployment may be in `OPEN`, `MITIGATING` or `ESCALATED` status, rejecting with `ERR_OPEN_INCIDENT_BLOCKS_ACTION`; a `MONITORING` incident deliberately does not block, because that state exists precisely to permit cautious resumption. The most recent skew check for this pair of `model_version_id` and `deployment_id`, ordered by `checked_at` descending then `created_at` descending, must not have a `status` of `FAIL_SKEW` or `FAIL_MISSING_FEATURE`, rejecting with `ERR_SKEW_CHECK_FAILED` — the absence of any skew check does not block. The referenced version must still be `APPROVED`. And finally the capacity gate fires last.

Four rollout actions are driven through a single capability shared by `ReliabilityEngineer` and `PlatformAdmin`, selected by an `action` field whose value is one of `HOLD`, `RESUME`, `ROLLBACK` or `RETIRE`.

`HOLD` moves `RAMPING → HELD` and does nothing else: `traffic_pct` and `ramp_step_index` are left exactly as they were, so the cluster's `allocated_traffic_pct` does not change either — `HELD` is inside the ledger's contributing state set. No ledger row is appended. The deployment's `version` increments by 1. The same `RAMPING → HELD` transition is also applied automatically as a cascade hop when a critical drift breach is recorded against the deployment.

`RESUME` moves `HELD → RAMPING` with `traffic_pct` unchanged, and re-runs the safety and temporal gates before allowing it: `manual_override_active` must be false, `health_state` must not be `CRITICAL`, no incident on the deployment may be `OPEN`, `MITIGATING` or `ESCALATED`, the cluster must be `OPEN`, the referenced version must be `APPROVED`, and `serve_until` must still be in the future. The deployment's `version` increments by 1.

`ROLLBACK` is accepted from `RAMPING`, `HELD` or `LIVE` and is a **compensating action**. It sets `traffic_pct` to 0.00, resets `ramp_step_index` to 0, stamps `rolled_back_at` from the logical clock, and appends exactly one ledger row whose `reason` is `ROLLBACK_RELEASE` and whose `delta_pct` is the negative of the `traffic_pct` the deployment held at the moment of rollback. Because that single release exactly cancels every prior step, the deployment's `cumulative_ramp_delta_pct` telescopes back to exactly 0.00 and the cluster's recomputed `allocated_traffic_pct` returns to exactly the value it had immediately before this deployment's very first ramp. Consider a cluster whose `max_traffic_pct` is 100.00: deployment A ramps through 5.00, 15.00 and 35.00 with steps of positive 5.00, 10.00 and 20.00, leaving the cluster allocated at 35.00 and A's `cumulative_ramp_delta_pct` at 35.00; deployment B is then created and ramped to 5.00, leaving the cluster at 40.00; rolling A back writes a single step of negative 35.00, so A's `traffic_pct` is 0.00, A's `cumulative_ramp_delta_pct` is 0.00, and the cluster's `allocated_traffic_pct` is 5.00 — B's contribution on top of the 0.00 that preceded A's first ramp. `ROLLBACK` also releases the champion pointer when it was pointing here: if the registry entry's `champion_version_id` equals this deployment's `model_version_id`, the pointer is rewritten to that version's `parent_version_id` — null when the version has no parent — and `champion_promoted_at` is stamped from the logical clock. As a second hop, every challenger evaluation whose `champion_deployment_id` or `challenger_deployment_id` names this deployment and whose `status` is `COLLECTING` moves `COLLECTING → INCONCLUSIVE`, gains `DEPLOYMENT_ROLLED_BACK` in its `criteria_failures`, and returns its `reserved_samples` to the challenger version's `evaluation_sample_budget`. The deployment's `version`, the cluster's `version` and the `version` of every other row mutated all increment by 1.

`RETIRE` is accepted from `PENDING`, `LIVE` or `DRAINING` and is the clean end of a deployment's life. It sets `traffic_pct` to 0.00; it appends one ledger row whose `reason` is `DRAIN_RELEASE` when `traffic_pct` was non-zero, and appends no ledger row at all when `traffic_pct` was already 0.00. The cluster's ledger is then recomputed, and because `RETIRED` sits **outside** the contributing state set, the retired deployment's former allocation is fully released. Retiring a `PENDING` deployment changes the ledger not at all, since `PENDING` contributed 0.00 already. The deployment's `version` and the cluster's `version` increment by 1.

`DRAINING` is never reached by an operator action; it is reached only as the third hop of a snapshot revocation or of a failed periodic revalidation, from `RAMPING`, `HELD` or `LIVE`. On that hop the deployment's `traffic_pct` is set to 0.00 and one ledger row is appended whose `reason` is `DRAIN_RELEASE` and whose `delta_pct` is the negative of the traffic held immediately before the cascade. The cluster's ledger is recomputed; `DRAINING` remains inside the contributing state set, but the deployment now contributes exactly 0.00. The hop then continues into the challenger-evaluation hop. Both the deployment's `version` and the cluster's `version` increment by 1.

The ramp-step ledger is readable two ways — per deployment as an ordered audit trail, and as a flat collection across all deployments — and both views can be narrowed by `reason`, while the flat collection can additionally be narrowed by `deployment_id`. A single ledger row can also be read by its own identifier. Deployment lists can be narrowed by `model_version_id`, by `serving_endpoint_id`, by `pattern`, by `rollout_state` and by `health_state`.

### 3.5. Observation Windows and the Composite Health Score

Prediction quality is evidenced by **observation windows**: intervals of served traffic with counts and summary statistics attached. An `MLEngineer` or a `ReliabilityEngineer` records one against a serving deployment by supplying a `deployment_id`, a `model_version_id`, a `window_kind`, a `window_start`, a `window_end`, a `prediction_count`, a `labeled_prediction_count`, a `correct_labeled_count`, a `positive_rate`, a `p95_latency_ms` and an `observed_bin_proportions` array. Every one of those eleven fields is required.

`window_kind` is one of `PERFORMANCE`, `DISTRIBUTION` or `LATENCY`, and it scopes both uniqueness and overlap. `window_start` is inclusive, `window_end` is inclusive, and `window_end` must be strictly greater than `window_start` or the record is rejected with `ERR_INVALID_INTERVAL`. `prediction_count` is at least 0. `labeled_prediction_count` is the subset of those predictions for which a ground-truth label has arrived and must be at least 0 and at most `prediction_count`; `correct_labeled_count` is the subset of labelled predictions that matched their label and must be at least 0 and at most `labeled_prediction_count`. Violating either of those two orderings is rejected with `ERR_LABEL_COUNT_INCONSISTENT`, which is what guarantees that both variants of the health score stay inside the unit interval without any clamping. `positive_rate` lies between 0.0 and 1.0 and records the observed positive-class rate of the served predictions. `p95_latency_ms` is at least 1 millisecond. `observed_bin_proportions` must contain exactly five numbers, each between 0.0 and 1.0, summing to within 0.0001 of 1.0, and otherwise is rejected with `ERR_INVALID_BIN_PROPORTIONS`.

Three gates guard the record. The deployment's `rollout_state` must be `RAMPING`, `HELD` or `LIVE`, or the record is rejected with `ERR_DEPLOYMENT_NOT_SERVING`, because observations only mean something against a deployment that is or was carrying traffic. The submitted `model_version_id` must equal the deployment's own `model_version_id`, or the record is rejected with `ERR_WINDOW_VERSION_MISMATCH` — observations attributed to the wrong version would be compared against the wrong baseline. And no other window sharing this `deployment_id` and this `window_kind` may still be in `status` `OPEN`, or the record is rejected with `ERR_DUPLICATE_OPEN_WINDOW`: exactly one open window per deployment per monitoring family. Separately, the new window's **fully closed** interval must not overlap any existing window sharing the same `deployment_id` and `window_kind`, or the record is rejected with `ERR_MONITORING_WINDOW_OVERLAP`. That geometry is closed at both ends with zero buffer, deliberately unlike the half-open serve-window rule of §3.4: a new `window_start` exactly equal to an existing window's `window_end` **is** an overlap and is rejected. When a candidate window is both a second open window and an interval overlap, the duplicate-open code is what the caller sees.

A recorded window starts in `status` `OPEN` with `health_score_variant` of `PROVISIONAL`, and its `health_score` is computed immediately. The **composite health score** reads exactly one window plus the artifact version named by its `model_version_id`, from which it takes `baseline_accuracy`, `baseline_positive_rate` and `baseline_p95_latency_ms`. It is a weighted blend of three components, each on a zero-to-one scale:

- The **prediction-distribution component** is 1 minus the absolute difference between the window's `positive_rate` and the version's `baseline_positive_rate`, divided by a tolerance band of 0.20, with the result floored at 0. A positive rate exactly on baseline scores 1; a positive rate 0.20 or more away from baseline scores 0.
- The **latency component** is the version's `baseline_p95_latency_ms` divided by the window's `p95_latency_ms`, capped above at 1 and floored below at 0. Serving at or faster than the offline baseline scores 1; serving twice as slow scores one half.
- The **accuracy-proxy component** differs between the two variants and is described below.

The three components are combined with fixed weights — 0.45 on the accuracy proxy, 0.30 on the prediction-distribution component and 0.25 on the latency component — the weighted sum is multiplied by 100, and the product is rounded half up to two decimals **once, at the very end**. Alongside it, `baseline_delta_pct` is written as the `health_score` minus 100 times the version's `baseline_accuracy`, rounded half up to two decimals; a negative value means the deployment is performing below the baseline it was approved against.

The two variants differ only in how the accuracy proxy treats unlabelled predictions, and that difference is the whole point of the pair. The `PROVISIONAL` variant applies while a window is `OPEN`: the accuracy proxy is `correct_labeled_count` divided by `labeled_prediction_count`, so the labelled subset is the entire denominator and unlabelled predictions are invisible. When `labeled_prediction_count` is 0 the accuracy proxy is defined as 0.0 — there is no divide-by-zero — and the window's `health_score` is still written. The `FINAL` variant applies once a window is `CLOSED`: the accuracy proxy is `correct_labeled_count` plus 0.60 multiplied by the difference between `prediction_count` and `labeled_prediction_count`, all divided by `prediction_count`, so every served prediction is in the denominator and the unlabelled remainder is imputed at a rate of 0.60. When `prediction_count` is 0 the accuracy proxy is defined as 0.0.

The two variants can disagree dramatically on the same data, which is why the closure of a window is a genuine decision point rather than a formality. Take a window with a `prediction_count` of 10,000, a `labeled_prediction_count` of 2,000, a `correct_labeled_count` of 1,700, a `positive_rate` of 0.32 against a `baseline_positive_rate` of 0.30, and a `p95_latency_ms` of 240 against a `baseline_p95_latency_ms` of 200. The distribution component is 0.9 and the latency component is 200 divided by 240. The `PROVISIONAL` accuracy proxy is 1,700 divided by 2,000, or 0.85, giving a `health_score` of 86.08. The `FINAL` accuracy proxy is 1,700 plus 0.60 of the 8,000 unlabelled predictions, all over 10,000, or 0.65, giving a `health_score` of 77.08.

Recording a window also mirrors its `PROVISIONAL` score into the deployment's `health_score_provisional` and increments the deployment's `version` by 1.

Closing a window is available to `MLEngineer` and `ReliabilityEngineer`, takes no body, and moves `OPEN → CLOSED`. It is rejected with `ERR_WINDOW_NOT_ENDED` unless `window_end` is at or before the logical clock's present value, so a `FINAL` score is never computed over an interval that has not yet elapsed. On success it stamps `closed_at` from the logical clock, sets `health_score_variant` to `FINAL`, recomputes `health_score` under the `FINAL` variant, rewrites `baseline_delta_pct` from that new score, and increments the window's `version` by 1 and the deployment's `version` by 1.

Closing a `PERFORMANCE` window does two extra things. It mirrors the `FINAL` score into the deployment's `health_score_final`. And it is the deployment's **only health-recovery path**: when the deployment's `health_state` is `DEGRADED` and the newly computed `FINAL` `health_score` is at least 80.00, the health dimension moves `DEGRADED → HEALTHY`. A deployment whose `health_state` is `CRITICAL` does not recover this way — critical health is released only by resolving the incident that accompanied it. Closing a `DISTRIBUTION` or `LATENCY` window never touches the health dimension, although closed `DISTRIBUTION` windows are exactly the pool the rolling drift baseline draws from.

A computed health read is available on every deployment to all five roles. It selects the deployment's most recent `PERFORMANCE` window ordered by `window_end` descending then `created_at` descending, and returns a small object carrying `deployment_id`, the deployment's current `health_state`, the `score_variant` it evaluated, the resulting `health_score`, the `baseline_delta_pct`, the `monitoring_window_id` it read, and that window's `prediction_count` and `labeled_prediction_count`. The optional `score_variant` query parameter is either `PROVISIONAL` or `FINAL` and defaults to `PROVISIONAL` when omitted. Asking for the `FINAL` variant over a window that is still `OPEN` computes the score on demand and **does not** persist it into the window's `health_score`. When the deployment has no `PERFORMANCE` window at all, both `health_score` and `monitoring_window_id` come back null.

Window lists can be narrowed by `deployment_id`, by `model_version_id`, by `window_kind` and by `status`; that list is also the discovery channel for the rolling-baseline candidate pool.

### 3.6. Drift Scoring, Skew Detection and Retraining Triggers

A **drift report** scores one closed observation window's distribution against an expected distribution. An `MLEngineer` or a `ReliabilityEngineer` creates one with a `monitoring_window_id`, a `drift_kind` and a `baseline_mode`. `drift_kind` is one of `DATA_DRIFT` or `CONCEPT_DRIFT` and records whether feature-input drift or label-outcome drift is being scored. `baseline_mode` is one of `TRAINING_BASELINE` or `ROLLING_BASELINE` and selects where the expected distribution comes from. The named window's `status` must be `CLOSED`, or the create is rejected with `ERR_WINDOW_NOT_CLOSED`: only closed windows carry a settled observed distribution and a `FINAL` score, so only they may be scored or used as baselines. On creation the report copies `model_version_id` from the window and starts in `status` `COMPUTED`.

The **drift index** is a population-stability index over five bins. The observed distribution is the window's `observed_bin_proportions`. The expected distribution depends on the variant. Under `TRAINING_BASELINE`, the expected distribution is the `baseline_bin_proportions` of the training snapshot named by the version's `training_dataset_id`; `baseline_dataset_id` is set to that snapshot, `effective_baseline_mode` is set to `TRAINING_BASELINE`, and `windows_used_count` is set to 0. Under `ROLLING_BASELINE`, the eligible pool is every observation window that shares the report's window's `deployment_id`, has `window_kind` of `DISTRIBUTION`, has `status` of `CLOSED`, and is not the report's own window; those candidates are ranked by `window_end` descending then `created_at` descending and the first three, or fewer if fewer exist, are taken; each expected bin is the arithmetic mean of that bin's value across the taken windows. In this case `baseline_dataset_id` is set to null, `effective_baseline_mode` is set to `ROLLING_BASELINE`, and `windows_used_count` is set to the number of windows actually averaged. When `ROLLING_BASELINE` is requested but **zero** eligible prior windows exist, the report silently falls back to the training baseline: `effective_baseline_mode` is written as `TRAINING_BASELINE`, `baseline_dataset_id` is set to the snapshot, and `windows_used_count` stays 0. `baseline_mode` always records what was asked for; `effective_baseline_mode` always records what was used.

Whichever variant supplied it, each of the five `expected_bin_proportions` is rounded half up to four decimals **before** any summation, and the rounded array is what the report persists. The index is then accumulated over the five bins: for each bin, the observed proportion minus the expected proportion, multiplied by the natural logarithm of the ratio between the observed proportion and the expected proportion, where each of those two proportions is first replaced by the larger of itself and 0.0001 so the logarithm is always defined. The five bin contributions are summed in full precision and the sum is rounded half up to four decimals once, giving `drift_index`.

`severity` bands the index with two thresholds, and **both comparisons are inclusive**: a `drift_index` of at least 0.25 is `CRITICAL`, otherwise a `drift_index` of at least 0.10 is `WARN`, otherwise `severity` is `NONE`. That the same observed data can produce two different verdicts under two different baselines is a feature, not an accident: an observed distribution of 0.10, 0.15, 0.20, 0.25 and 0.30 scored against a flat training baseline of five equal 0.20 bins yields a `drift_index` of 0.1354 and a `severity` of `WARN`, while the same observed distribution scored against three prior closed distribution windows of 0.12/0.16/0.20/0.24/0.28, 0.14/0.16/0.20/0.24/0.26 and 0.10/0.18/0.20/0.26/0.26 yields expected bins of 0.1200, 0.1667, 0.2000, 0.2467 and 0.2667, a `drift_index` of 0.0094 and a `severity` of `NONE`.

`severity` of `NONE` produces no transition at all: the report stays in `status` `COMPUTED`, no trigger is raised, no health dimension moves, no deployment is held, no incident appears. `severity` of `WARN` or `CRITICAL` moves the report `COMPUTED → BREACHED` and opens a cascade of up to five hops. The deployment the cascade acts on is the one named by the report's window.

Hop 1 is the report's own `COMPUTED → BREACHED` transition. Because the report breached, hop 2 creates exactly one **retraining trigger** in `status` `PROPOSED`, carrying `model_id` copied from the version's registry entry, `drift_report_id` set to this report, and `skew_check_id` set to the most recent skew check for the report's deployment ordered by `checked_at` descending then `created_at` descending — null when no skew check exists for that deployment — then computes the urgency snapshot described below and recomputes the registry entry's `open_retraining_trigger_count`. Because the trigger was raised, hop 3 moves the deployment's health dimension: `HEALTHY → DEGRADED` when `severity` is `WARN`, or `HEALTHY → CRITICAL` or `DEGRADED → CRITICAL` when `severity` is `CRITICAL`. On the `CRITICAL` branch only, hop 4 follows: because the health dimension became `CRITICAL`, a deployment whose `rollout_state` is `RAMPING` moves `RAMPING → HELD`. Still on the `CRITICAL` branch only, hop 5 follows: because the deployment was auto-held, one prediction incident is created in `status` `OPEN` with `source` of `DRIFT`, `severity` of `SEV2`, `drift_report_id` set to this report, `model_version_id` copied from the deployment, and a `summary` of `AUTO: critical drift breach`. Every row mutated by hops 2 through 5 has its `version` incremented by 1. The `WARN` branch therefore ends after hop 3 with a degraded deployment and a proposed trigger; the `CRITICAL` branch ends after hop 5 with a held deployment and an open incident on top.

A breached report leaves `BREACHED` for the terminal `ACKNOWLEDGED` state only when the trigger it raised is acknowledged; that transition increments the report's `version` by 1. Drift-report lists can be narrowed by `monitoring_window_id`, by `model_version_id`, by `baseline_dataset_id`, by `drift_kind`, by `severity` and by `status`.

**Skew checks** attack the other half of the feature-pipeline problem. Structural identity is already enforced by hash equality at registration and at deployment; a skew check catches *statistical* divergence at serving time. An `MLEngineer` or a `ReliabilityEngineer` creates one with a `model_version_id`, a `deployment_id`, a `training_feature_stats` map and a `serving_feature_stats` map. Each map is keyed by feature name and each value is an object carrying a numeric `mean`; `training_feature_stats` must be non-empty and every value in either map must carry a numeric `mean`, or the create is rejected with `ERR_INVALID_FEATURE_STATS` — an empty training map would leave the maximum ratio undefined, and defaulting it to 1.0000 would silently pass a check that was never performed. The named deployment must serve exactly the submitted `model_version_id`, or the create is rejected with `ERR_SKEW_DEPLOYMENT_MISMATCH`, and the deployment's `rollout_state` must be `RAMPING`, `HELD` or `LIVE`, or the create is rejected with `ERR_DEPLOYMENT_NOT_SERVING`. On creation the check copies `training_dataset_id` from the version and stamps `checked_at` from the logical clock.

The authoritative feature list is the **key set of `training_feature_stats`** — the training snapshot defines which features the artifact expects — and any extra key present only in `serving_feature_stats` is ignored entirely. `missing_features` is the list of training feature names absent from `serving_feature_stats`, sorted lexicographically ascending by ASCII order. For every training feature that is *not* missing, a symmetric ratio is computed: take the absolute value of the training `mean` and the absolute value of the serving `mean`, replace each by the larger of itself and 0.0001, divide the larger of the two results by the smaller, and round half up to four decimals. Such a ratio is always at least 1.0000. `max_skew_ratio` is the maximum of those rounded per-feature ratios, or exactly 1.0000 when no feature is comparable at all. `max_skew_feature` names the feature attaining that maximum, ties broken by the lexicographically smallest feature name in ASCII order — never by insertion order and never by any identifier — and is null when `serving_feature_stats` shares no feature with `training_feature_stats`.

`status` is then decided by a single ordered ladder in which the first matching row wins: `FAIL_MISSING_FEATURE` when `missing_features` is non-empty, otherwise `FAIL_SKEW` when `max_skew_ratio` is at least 1.25, otherwise `WARN` when `max_skew_ratio` is at least 1.10, otherwise `PASS`. Both numeric comparisons are inclusive. Suppose the training map carries `amount` at 0.8000, `tenure_days` at 30.0000 and `zscore` at 1.0000, and the serving map carries `amount` at 1.0000, `tenure_days` at 31.5000 and `zscore` at 1.0000: the ratios are 1.2500, 1.0500 and 1.0000, so `max_skew_ratio` is 1.2500, `max_skew_feature` is `amount`, and `status` is `FAIL_SKEW` because the comparison against 1.25 is inclusive. Move the serving `amount` to 0.8800 and the ratio becomes exactly 1.1000, landing on `WARN` for the same inclusive reason. Omit `zscore` from the serving map entirely and the ladder short-circuits: `status` is `FAIL_MISSING_FEATURE` with `missing_features` of `zscore`, and the offending 1.2500 ratio on `amount` never gets a chance to make it `FAIL_SKEW`.

A `FAIL_SKEW` or `FAIL_MISSING_FEATURE` verdict also raises a retraining trigger, in `status` `PROPOSED`, with `model_id` from the version, `skew_check_id` set to this check, `drift_report_id` left null, and the urgency snapshot computed with a zero drift contribution; the registry entry's `open_retraining_trigger_count` is recomputed. Beyond that, a failing check blocks further ramping of the deployment and blocks the conclusion of any challenger evaluation on it, until a later `PASS` or `WARN` check for the same version-and-deployment pair supersedes it in the `checked_at` ordering. Skew-check lists can be narrowed by `model_version_id`, by `deployment_id`, by `training_dataset_id` and by `status`.

The **retraining urgency snapshot** is written once, at the moment a trigger is raised, and is never recomputed afterwards — it is a frozen record of the evidence that raised it. Its inputs are the source drift report when `drift_report_id` is set, the source skew check when `skew_check_id` is set, and the *evidence version*: the artifact version named by the drift report when there is one, and otherwise the version named by the skew check. The registry entry's `champion_version_id` is deliberately **not** read, so the snapshot is well defined even before any champion exists. The computation runs in a pinned order:

1. The **drift contribution** is 120 multiplied by the source report's `drift_index`, or 0 when no drift report is attached.
2. The **skew contribution** is 80 multiplied by the source check's `max_skew_ratio` minus 1.0, floored at 0, or 0 when no skew check is attached.
3. The **staleness contribution** is one half of a point per whole day elapsed from the evidence version's `approved_at` to the logical clock's present value, counting whole days only and discarding any partial day; it is 0 when `approved_at` is null.
4. `base_urgency` is the sum of those three contributions, rounded half up to two decimals.
5. The **escalation tier** is chosen from `base_urgency` alone, and never re-chosen from the total it produces. Four tiers exist, each with a floor and a bonus percentage: a floor of 0 grants a bonus of 0, a floor of 20 grants 10 percent, a floor of 45 grants 25 percent, and a floor of 70 grants 40 percent. The tier that applies is the last one whose floor is less than or equal to `base_urgency`, and its bonus is recorded as `escalation_tier_bonus_pct`.
6. `total_urgency` is `base_urgency` multiplied by one plus the bonus percentage expressed as a fraction of one hundred, rounded half up to two decimals, and then capped at a ceiling of 100.
7. `priority_band` bands the total: `CRITICAL` at 75 or above, otherwise `HIGH` at 50 or above, otherwise `MEDIUM` at 25 or above, otherwise `LOW`.
8. `retrain_required` is true when `total_urgency` is at least 45.
9. `stale_after` is the raise instant plus 90 whole days.

The pinned tier order is the part implementations get wrong. A trigger raised from a `drift_index` of 0.1354, a `max_skew_ratio` of 1.15 and 56 whole days since approval has contributions of 16.248, 12.0 and 28.0, so `base_urgency` is 56.25; the last tier floor at or below 56.25 is 45, so `escalation_tier_bonus_pct` is 25 and `total_urgency` is 70.31, with `priority_band` of `HIGH` and `retrain_required` true. Re-selecting the tier against 70.31 would pick the 70 floor and its 40 percent bonus, producing 78.75 and a `priority_band` of `CRITICAL` — that is the wrong answer. The ceiling matters too: a `drift_index` of 0.5055, a `max_skew_ratio` of 1.354 and 20 days give contributions of 60.66, 28.32 and 10.0, a `base_urgency` of 98.98, a bonus of 40 percent and an uncapped product of 138.57, which is clamped to a `total_urgency` of exactly 100.00. At the quiet end, a `drift_index` of 0.09, a `max_skew_ratio` of 1.05 and 10 days give 10.8, 4.0 and 5.0, a `base_urgency` of 19.80, a bonus of 0 percent, a `total_urgency` of 19.80, a `priority_band` of `LOW` and `retrain_required` false.

A trigger's `status` spans `PROPOSED`, `ACKNOWLEDGED`, `IN_PROGRESS`, `SATISFIED`, `DISMISSED` and `STALE`, with the last three terminal. `MLEngineer` and `PlatformAdmin` drive it through a single disposition capability whose `action` is one of `ACKNOWLEDGE`, `DISMISS` or `LINK_VERSION`, with an optional `retrained_version_id` and an optional `dismissed_reason`.

`ACKNOWLEDGE` moves `PROPOSED → ACKNOWLEDGED`, stamps `acknowledged_by_user_id` from the caller's `X-User-ID`, moves the source drift report `BREACHED → ACKNOWLEDGED` when `drift_report_id` is set, recomputes the registry entry's `open_retraining_trigger_count`, and increments the trigger's `version`, the report's `version` and the registry entry's `version` each by 1.

`DISMISS` moves `PROPOSED → DISMISSED`. It requires a `dismissed_reason` in the body, rejecting with `ERR_INVALID_REQUEST` when it is absent, and it is rejected with `ERR_RETRAIN_REQUIRED` while `retrain_required` is true — a trigger whose `total_urgency` reached 45 may not be waved away and must be linked to a retrained version instead. On success it records `dismissed_reason`, recomputes `open_retraining_trigger_count`, and increments the trigger's `version` and the registry entry's `version` by 1.

`LINK_VERSION` requires a `retrained_version_id`, and the referenced version must genuinely be a descendant inside the same registry entry: its `model_id` must equal the trigger's `model_id`, and its `parent_version_id` must be the drift report's `model_version_id`. Either lineage failure is rejected with `ERR_RETRAINED_VERSION_LINEAGE_INVALID`, because a retraining outcome must be a real descendant rather than an unrelated artifact relabelled as the fix. From `ACKNOWLEDGED` the action **forks on the linked version's own approval state**: when that version's `approval_state` is already `APPROVED`, the trigger lands directly on `SATISFIED` and leaves the open set; when it is anything else, the trigger lands on `IN_PROGRESS` and stays in the open set. Both branches write `retrained_version_id`, recompute `open_retraining_trigger_count`, and increment the trigger's `version` and the registry entry's `version` by 1. The action may then be re-issued from `IN_PROGRESS` once the linked version has been approved, moving `IN_PROGRESS → SATISFIED`; on that re-issue the `retrained_version_id` in the body must equal the already-linked value, rejecting with `ERR_RETRAINED_VERSION_LINEAGE_INVALID` otherwise, and the referenced version's `approval_state` must be `APPROVED`, rejecting with `ERR_INVALID_STATE` otherwise. The re-issue recomputes the counter and increments both `version` values by 1.

Trigger lists can be narrowed by `model_id`, by `drift_report_id`, by `skew_check_id`, by `retrained_version_id`, by `status` and by `priority_band`. Reading a single trigger returns its frozen `base_urgency`, `escalation_tier_bonus_pct`, `total_urgency`, `priority_band`, `retrain_required` and `stale_after` alongside its lifecycle fields.

### 3.7. Champion-Challenger Evaluation and Promotion

Promotion of a new champion is never a bare administrative write. It runs through a **champion-challenger evaluation**: a scheduled experiment that compares an incumbent realtime deployment against a shadow deployment carrying the candidate artifact, and that either promotes the candidate or does not.

A `ReliabilityEngineer` or a `PlatformAdmin` schedules one against a registry entry, supplying a `champion_deployment_id`, a `challenger_deployment_id`, a `reserved_samples` count, an `evaluation_ends_at` instant, a `champion_metrics` map, a `challenger_metrics` map and an `expected_model_version`. The `model_id` comes from the path. `challenger_version_id` is copied from the challenger deployment's `model_version_id`, `created_by_user_id` is stamped from the caller's `X-User-ID`, `status` starts at `SCHEDULED`, and `extension_count` starts at 0.

`reserved_samples` must be at least 1. `evaluation_ends_at` must be strictly greater than the logical clock's present value at creation, or the create is rejected with `ERR_INVALID_INTERVAL` — an experiment that is already mature at the moment it is scheduled has no collection period. Both `champion_metrics` and `challenger_metrics` must carry exactly the keys `ACCURACY_PROXY`, `CALIBRATION`, `LATENCY` and `COST` with numeric values, or the create is rejected with `ERR_INVALID_METRIC_SET`; the score iterates a fixed metric order and a missing key would silently drop a weighted line rather than fail loudly.

Both arms must also belong to the registry entry named in the path: the version served by the champion deployment and the version served by the challenger deployment must each have a `model_id` equal to the path's `model_id`, or the create is rejected with `ERR_CHALLENGER_MODEL_MISMATCH`, because a champion-challenger comparison is only meaningful within one registry entry.

Four business gates then apply. The registry entry's `registry_status` must be `ACTIVE`, or the create is rejected with `ERR_MODEL_ARCHIVED`. No other evaluation for the same `model_id` may be in `status` `SCHEDULED` or `COLLECTING`, or the create is rejected with `ERR_ACTIVE_EVALUATION_EXISTS`: one live experiment per registry entry at a time, because overlapping experiments would contaminate each other's traffic. The challenger deployment's `pattern` must be `SHADOW` and the champion deployment's `pattern` must be `REALTIME`, or the create is rejected with `ERR_CHALLENGER_NOT_SHADOW` — a challenger must be observed in shadow mode, and promoting one that already carries live traffic would defeat the experiment. And the requested `reserved_samples` must not exceed the challenger version's current `evaluation_sample_budget`, or the create is rejected with `ERR_SAMPLE_BUDGET_EXCEEDED`.

The `expected_model_version` token guards all of that. It must equal the registry entry's current `version`, or the request is rejected with `ERR_STALE_MODEL_VERSION`. This is deliberately a stale-read check rather than a state precondition: a second evaluation against the same registry entry is legitimate product behaviour once the first has ended, and what the token protects is the caller's view of `champion_version_id` and `open_retraining_trigger_count`, both of which the caller read before deciding what to compare. The check sits after existence and interval shape but before every state and business rule, so a stale token against an archived registry entry returns the stale-version code rather than `ERR_MODEL_ARCHIVED`. On success the registry entry's `version` is incremented by 1.

The **evaluation sample ledger** is a recomputed ledger over the challenger version, in whole samples with no rounding. The holding set is every evaluation whose `challenger_version_id` is this version and whose `status` is `SCHEDULED`, `COLLECTING` or `PROMOTED`; the reserved total is the sum of their `reserved_samples`; and the version's `evaluation_sample_budget` is its `evaluation_sample_quota` minus that total. Evaluations in `REJECTED` or `INCONCLUSIVE` are outside the holding set, which is precisely how they release their reservation in full. The compensating invariant is that after any sequence of schedulings, extensions and conclusions, the budget equals the quota minus the reservations of the still-holding rows, so once every evaluation on a version has ended non-promoted the budget is back to exactly its pre-scheduling value — the release returns the samples the evaluation actually held, never a recomputed estimate. With an `evaluation_sample_quota` of 5000, scheduling a first evaluation reserving 3000 leaves a budget of 2000; a second evaluation requesting 2500 is rejected because 2500 exceeds 2000; concluding the first as `REJECTED` restores the budget to 5000, and the 2500 request then succeeds, leaving 2500. The ledger is recomputed on scheduling, on starting, on extending and on concluding.

Starting an evaluation is available to `ReliabilityEngineer` and `PlatformAdmin`, takes no body, and moves `SCHEDULED → COLLECTING`. Both arms must actually be serving, and the two codes are evaluated in a fixed order: the challenger deployment's `rollout_state` must be `RAMPING`, `HELD` or `LIVE`, or the request is rejected with `ERR_CHALLENGER_NOT_SERVING`, and only then must the champion deployment's `rollout_state` be exactly `LIVE`, or the request is rejected with `ERR_CHAMPION_NOT_LIVE`. Both arms are re-checked in the same order when the evaluation is concluded. Starting increments the evaluation's `version` by 1.

Concluding is available to the same two roles and takes a `labeled_prediction_count` of at least 0. It is rejected with `ERR_EVALUATION_NOT_MATURE` unless `evaluation_ends_at` is at or before the logical clock's present value, so promotion decisions cannot be rushed, and rejected with `ERR_NO_LABELED_PREDICTIONS` when `labeled_prediction_count` is 0 — a verdict on zero labelled predictions is not a verdict. It then runs the promotion score and resolves the three-way fork.

The **challenger promotion score** reads only the evaluation's own `champion_metrics` and `challenger_metrics` maps; it aggregates nothing. The four metrics are evaluated in the fixed order `ACCURACY_PROXY`, `CALIBRATION`, `LATENCY`, `COST`. For each, the denominator is the larger of the absolute value of the champion's reading and 0.0001; the normalised delta is the challenger's reading minus the champion's reading, divided by that denominator; for `LATENCY` and `COST` — the two metrics where lower is better — the normalised delta is negated, so that a faster or cheaper challenger scores positively; and the weighted line is the metric's weight multiplied by that normalised delta. The weights are 0.50 on `ACCURACY_PROXY`, 0.20 on `CALIBRATION`, 0.15 on `LATENCY` and 0.15 on `COST`. Each of the four weighted lines is **rounded half up to four decimals first**, the four rounded lines are then summed, and the sum is rounded half up to four decimals again. The four rounded lines are persisted in `metric_lines` and the final sum in `promotion_score`. A computed value of negative zero is normalised to 0.0000.

That rounding order is pinned and summing in full precision before a single rounding is the wrong answer. With champion metrics of `ACCURACY_PROXY` 0.8200, `CALIBRATION` 0.9100, `LATENCY` 180.0 and `COST` 0.00420 against challenger metrics of 0.8570, 0.9230, 171.0 and 0.00390, the four rounded lines are 0.0226, 0.0029, 0.0075 and 0.0107, and the pinned per-line-then-sum order gives a `promotion_score` of 0.0437, whereas summing at full precision and rounding once gives 0.0436 — a different fourth decimal, on a value compared against a threshold expressed to four decimals.

Six promotion criteria are then evaluated, and every one that fails appends its key to `criteria_failures`, which is finally sorted lexicographically ascending in ASCII order:

- `SCORE_BELOW_MIN` when `promotion_score` is strictly below 0.0300. The comparison is strict, so a score of exactly 0.0300 passes. With champion metrics of 0.8000, 0.9000, 200.0 and 0.00500 against challenger metrics of 0.8400, 0.9090, 198.0 and 0.00495, the lines are 0.0250, 0.0020, 0.0015 and 0.0015 and the `promotion_score` is exactly 0.0300, so this key does not fire.
- `INSUFFICIENT_LABELS` when `labeled_prediction_count` is strictly below 1000.
- `LATENCY_REGRESSION` when the challenger's `LATENCY` reading exceeds the champion's `LATENCY` reading by more than 25 milliseconds. A challenger slower by exactly 25 milliseconds does not fire this key.
- `CHALLENGER_UNHEALTHY` when the challenger deployment's `health_state` is anything other than `HEALTHY`.
- `SKEW_CHECK_FAILED` when a skew check exists for the challenger version and challenger deployment pair — the most recent by `checked_at` descending then `created_at` descending — and its `status` is `FAIL_SKEW` or `FAIL_MISSING_FEATURE`. A version with no skew check at all does not fire this key; a version whose latest check is `PASS` or `WARN` does not fire it either, even if an older check failed.
- `OPEN_INCIDENT` when any prediction incident whose `deployment_id` is the challenger deployment has `status` of `OPEN`, `MITIGATING` or `ESCALATED`.

The fork is then decided by the exact contents of that list, and the three branches have genuinely different side effects. When `criteria_failures` is empty, the evaluation moves `COLLECTING → PROMOTED`: the registry entry's `champion_version_id` is set to `challenger_version_id` and its `champion_promoted_at` to the logical clock's present value, and its `version` is incremented by 1. The reserved samples **stay consumed**, because `PROMOTED` is inside the holding set of the sample ledger, so the challenger version's `evaluation_sample_budget` is unchanged by this transition — a promoted experiment permanently spent its allowance. When `criteria_failures` is exactly the single key `INSUFFICIENT_LABELS` — which is to say `labeled_prediction_count` was at least 1 but below 1000 and nothing else failed — the evaluation moves `COLLECTING → INCONCLUSIVE`, and the reserved samples are returned through the ledger because `INCONCLUSIVE` is outside the holding set. When `criteria_failures` is non-empty and is anything other than exactly that one key, the evaluation moves `COLLECTING → REJECTED`, the registry entry's `champion_version_id` is **not** touched, and the reserved samples are likewise returned, restoring the budget to exactly its pre-scheduling value. On both the rejected and inconclusive branches the evaluation's `version` and the challenger version's `version` are each incremented by 1; on the promoted branch the evaluation's `version` and the registry entry's `version` are incremented by 1. All three branches write `metric_lines`, `promotion_score` and `criteria_failures`. `PROMOTED` and `REJECTED` are terminal; `INCONCLUSIVE` is not.

An inconclusive evaluation can be re-opened for another collection round, and this is the one bounded cycle in the system. Extending is available to `ReliabilityEngineer` and `PlatformAdmin`, takes no body, and moves `INCONCLUSIVE → COLLECTING`. It requires `extension_count` strictly below 2, or it is rejected with `ERR_MAX_EXTENSIONS_REACHED`; that bound is what makes the cycle terminate, so a third extension is impossible. It requires that `criteria_failures` does **not** contain `DEPLOYMENT_DRAINED`, or it is rejected with `ERR_CHALLENGER_NOT_SERVING` — an evaluation invalidated because its deployment stopped serving cannot be resurrected, unlike one that merely ran short of labels. And it requires that the samples can be re-reserved: the re-reserved amount must not exceed the challenger version's current `evaluation_sample_budget`, or it is rejected with `ERR_SAMPLE_BUDGET_EXCEEDED`, which can genuinely fail even though the samples were held before, because the budget may have been spent by another experiment in the meantime. On success it increments `extension_count` by 1, clears `criteria_failures` to the empty list, clears `promotion_score` and `metric_lines` back to null, pushes `evaluation_ends_at` out by 7 whole days from its previous value rather than from the logical clock, adds 500 to `reserved_samples`, re-reserves that increased amount through the ledger, and increments the evaluation's `version` and the challenger version's `version` by 1.

The system itself can also end a collecting evaluation. Whenever an evaluation's `champion_deployment_id` or `challenger_deployment_id` leaves the serving set of `RAMPING`, `HELD` and `LIVE` inside a single request — the snapshot-revocation cascade, the rollback action, or the revalidation-failure cascade — every evaluation on that deployment still in `COLLECTING` moves `COLLECTING → INCONCLUSIVE`, gains the appropriate drain key in `criteria_failures`, returns its reserved samples through the ledger, and has its `version` and the challenger version's `version` incremented by 1. Affected evaluations are processed in ascending `created_at` order.

Reading one evaluation returns its `metric_lines`, `promotion_score`, `criteria_failures`, `reserved_samples`, `extension_count`, `labeled_prediction_count`, `evaluation_ends_at`, `champion_metrics`, `challenger_metrics`, `created_by_user_id` and `status`. Evaluation lists can be narrowed by `model_id`, by `champion_deployment_id`, by `challenger_deployment_id`, by `challenger_version_id` and by `status`, and that list is the reverse-lookup channel from any of those four references back to the experiments that used them.

### 3.8. Incident Response: Fallback, Override and Recurrence

A **prediction incident** is the operational record of degraded predictions on a serving deployment. A `ReliabilityEngineer`, an `MLEngineer` or a `PlatformAdmin` raises one with a `deployment_id`, a `summary` of between 1 and 300 characters, an optional `source` and an optional `severity`. `source` is one of `MANUAL`, `DRIFT`, `SKEW` or `LATENCY` and defaults to `MANUAL`; `severity` is one of `SEV3`, `SEV2` or `SEV1` and defaults to `SEV3`. The deployment's `rollout_state` must be `RAMPING`, `HELD` or `LIVE`, or the request is rejected with `ERR_DEPLOYMENT_NOT_SERVING`. On creation `model_version_id` is copied from the deployment, `drift_report_id` stays null for a manually raised incident, `opened_at` is stamped from the logical clock, `status` starts at `OPEN`, `fallback_engaged` starts false and `recurrence_count` starts 0. The drift cascade of §3.6 raises incidents through the same entity but stamps `source` as `DRIFT`, `severity` as `SEV2` and `drift_report_id` as the breaching report, ignoring any caller-supplied `source` and `severity` because there is no caller.

An open incident is a hard brake on the deployment it names. While any incident on a deployment has `status` of `OPEN`, `MITIGATING` or `ESCALATED`, neither a ramp nor a resume may proceed, and both are rejected with `ERR_OPEN_INCIDENT_BLOCKS_ACTION`. Note the asymmetry: `MONITORING` is deliberately **not** in that blocking set, so a deployment under observation after mitigation can be ramped again, while one still mitigating or escalated cannot.

Incident response runs through a single action capability available to `ReliabilityEngineer` and `PlatformAdmin`, whose `action` is one of `ENGAGE_FALLBACK`, `MANUAL_OVERRIDE`, `MONITOR`, `RECUR` or `RESOLVE`, with an optional `override_traffic_pct` and an optional `note`. The lifecycle spans `OPEN`, `MITIGATING`, `MONITORING`, `ESCALATED` and `RESOLVED`, with `RESOLVED` terminal, and it contains a bounded recurrence loop.

`ENGAGE_FALLBACK` moves `OPEN → MITIGATING`. The deployment's `fallback_strategy` must be something other than `NONE`, or the request is rejected with `ERR_FALLBACK_NOT_CONFIGURED` — there is nothing to fall back to. The deployment's `rollout_state` must be `RAMPING`, `HELD` or `LIVE`, or the request is rejected with `ERR_DEPLOYMENT_NOT_SERVING`. On success `fallback_engaged` is set true and `fallback_strategy_used` captures the deployment's `fallback_strategy` **as it stood at that instant**, so that a later change to the deployment's configured strategy does not rewrite the history of what was actually engaged. The incident's `version` is incremented by 1; no traffic moves.

`MANUAL_OVERRIDE` also moves `OPEN → MITIGATING`, and it does move traffic. It requires `override_traffic_pct` in the body, at least 0.00 and strictly less than the deployment's current `traffic_pct`, or the request is rejected with `ERR_OVERRIDE_EXCEEDS_CURRENT_TRAFFIC`: an override is a way of pulling traffic back, never a back door for raising it, and pinning traffic to the value it already carries is not an intervention. The deployment's `manual_override_active` must be false, or the request is rejected with `ERR_MANUAL_OVERRIDE_ACTIVE` — two concurrent overrides on the same deployment would make the release compensation ambiguous about which value to restore. The deployment's `rollout_state` must be `RAMPING`, `HELD` or `LIVE`, or the request is rejected with `ERR_DEPLOYMENT_NOT_SERVING`. On success the incident records `manual_override_traffic_pct`; the deployment has `manual_override_active` set true, `override_traffic_pct` set to the requested value and `traffic_pct` pinned to the same value; one ramp-ledger row is appended with `reason` of `MANUAL_OVERRIDE`, `from_traffic_pct` equal to the deployment's traffic percentage **before** the call, `to_traffic_pct` equal to the override, and `delta_pct` equal to the override minus that pre-call value — a negative delta, since the override is strictly lower; the serving cluster's `allocated_traffic_pct` is recomputed through the endpoint traffic ledger, which frees the surrendered headroom for other deployments; and the incident's `version`, the deployment's `version` and the cluster's `version` are each incremented by 1.

`MONITOR` moves `MITIGATING → MONITORING` with no preconditions beyond the state itself and increments the incident's `version` by 1. It is the declaration that mitigation is in place and the deployment is being watched.

`RECUR` is issued from `MONITORING` when the degradation returns, and it forks on the recurrence ceiling of 2. The comparison is made against the **incremented** count, not the stored one: when `recurrence_count` plus 1 is strictly below 2 the incident moves `MONITORING → MITIGATING` and the loop continues; when `recurrence_count` plus 1 is at least 2 the incident moves `MONITORING → ESCALATED` and `severity` is forcibly raised to `SEV1`. Either branch increments `recurrence_count` by 1 and the incident's `version` by 1. Concretely, an incident raised at `recurrence_count` 0 and mitigated then monitored takes its first `RECUR` back to `MITIGATING` with `recurrence_count` 1; after a second `MONITOR` the next `RECUR` sees 1 plus 1 equal to 2 and therefore escalates rather than looping, landing on `ESCALATED` with `recurrence_count` 2 and `severity` `SEV1`. There is no third pass through the loop, which is what makes the cycle terminate, and `ESCALATED` accepts no further `RECUR`.

`RESOLVE` is accepted from `MONITORING` and from `ESCALATED`, and both paths behave identically. It moves the incident to `RESOLVED` and stamps `resolved_at` from the logical clock. When `manual_override_traffic_pct` is non-null it also **releases the override**, which is a compensating write rather than a recomputation: the deployment's `manual_override_active` is cleared to false and its `override_traffic_pct` to null; its `traffic_pct` is restored to the `from_traffic_pct` of the most recent ramp-ledger row for this deployment whose `reason` is `MANUAL_OVERRIDE`, ordered by `created_at` descending — the exact value that was displaced, not a re-derived estimate; one further ramp-ledger row is appended with `reason` of `OVERRIDE_RELEASE` and `delta_pct` equal to the restored percentage minus the override percentage, which is the exact negation of the override row's delta, so the deployment's `cumulative_ramp_delta_pct` telescopes back to its pre-override value; and the serving cluster's `allocated_traffic_pct` is recomputed through the endpoint traffic ledger, reclaiming the headroom. A deployment ramped to 65.00 and then overridden down to 20.00 carries an override row with a `delta_pct` of -45.00; resolving the incident restores `traffic_pct` to 65.00 and appends a release row with a `delta_pct` of +45.00, leaving `cumulative_ramp_delta_pct` exactly where the ramp history had put it, with both rows preserved as an audit trail. An incident that never applied an override releases nothing and touches no traffic.

`RESOLVE` also carries the deployment's only exit from critical health. When the deployment's `health_state` is `CRITICAL` and **no other** incident on that deployment has `status` of `OPEN`, `MITIGATING`, `MONITORING` or `ESCALATED`, the health dimension moves `CRITICAL → DEGRADED`. Note that the blocking set here is wider than the ramp-blocking set: `MONITORING` counts as an unresolved incident for the purpose of clearing critical health, so a deployment with one resolved and one monitored incident stays `CRITICAL`. Recovery is also only ever partial — critical health steps down to `DEGRADED`, never straight to `HEALTHY`, and the return to `HEALTHY` still requires closing a performance window at a `FINAL` score of at least 80.00 as described in §3.5. Resolution increments the incident's `version` by 1, and the deployment's and cluster's `version` by 1 whenever traffic or health was touched.

Reading one incident returns `fallback_engaged`, `fallback_strategy_used`, `manual_override_traffic_pct`, `recurrence_count`, `opened_at`, `resolved_at`, `source`, `severity`, `summary` and `status`. Incident lists can be narrowed by `deployment_id`, by `model_version_id`, by `drift_report_id`, by `source`, by `severity` and by `status`, and that list is the reverse-lookup channel from a deployment, a version or a drift report back to its incidents.

### 3.9. Periodic Revalidation and Operational Sweeps

Approval is not permanent. Every approved artifact version carries a `revalidation_due_at` instant, and when the logical clock passes it the version owes a fresh review. The **revalidation schedule** computes that instant by adding the owning registry entry's `revalidation_interval_days` — which defaults to 90 when the entry was created without one — as whole days to an anchor instant, preserving the anchor's time-of-day component exactly. Which anchor is used depends entirely on why the schedule is being recomputed, and that is the distinction to get right.

On the approval anchor, used when a version moves `PENDING_REVIEW → APPROVED`, `revalidation_due_at` is `approved_at` plus the interval. On the pass anchor, used when a revalidation task is passed, `revalidation_due_at` is the logical clock's **present value at disposition time** plus the interval — not the task's `due_at`, and not the original `approved_at`. The consequence is deliberate: a late revalidation pushes the next due date out by the full interval rather than snapping back to the original cadence. With a `revalidation_interval_days` of 90 and an `approved_at` of 2026-08-01T00:00:00Z, `revalidation_due_at` is 2026-10-30T00:00:00Z. If the clock reaches 2026-11-01T00:00:00Z before anyone looks, and the review is then started and passed at a clock of 2026-11-05T00:00:00Z, the new `revalidation_due_at` is 2027-02-03T00:00:00Z — not the 2027-01-28T00:00:00Z that anchoring on the original due date would have produced.

**Revalidation tasks are never created by a caller.** They are raised only by the sweep, which is why there is no create capability for them. The sweep is exclusive to `PlatformAdmin`, takes no body, and is the only epoch-style batch operation in the service. It selects every artifact version whose `approval_state` is `APPROVED`, whose `revalidation_due_at` is non-null and at or before the logical clock's present value, and which has no existing task in `status` `DUE` or `IN_REVIEW`; it orders those versions by `revalidation_due_at` ascending then `created_at` ascending — never by identifier — and creates one task for each, in `status` `DUE`, with `model_version_id` set to the version, `due_at` copied from the version's `revalidation_due_at` as it stood at sweep time, and `swept_at` stamped from the clock.

The sweep returns four counters: `evaluated_count` is the number of approved versions with a non-null `revalidation_due_at` that it examined, `created_count` is the number of tasks it created, `skipped_existing_count` is the number of due versions it passed over because a `DUE` or `IN_REVIEW` task already existed for them, and `staled_trigger_count` is the number of retraining triggers it staled. The sweep is idempotent at a fixed clock: a second call at the same clock value reports a `created_count` of 0 and counts the same versions under `skipped_existing_count` instead. Continuing the example above, the first sweep at 2026-11-01T00:00:00Z creates one task with a `due_at` of 2026-10-30T00:00:00Z and a `swept_at` of 2026-11-01T00:00:00Z, and a second sweep at that same clock reports a `created_count` of 0 and a `skipped_existing_count` of 1.

The same sweep also runs the **trigger staleness pass**. Every retraining trigger whose `status` is `ACKNOWLEDGED` or `IN_PROGRESS` and whose `stale_after` is at or before the logical clock's present value moves to `STALE`, and for each one the owning registry entry's `open_retraining_trigger_count` is recomputed downward. A trigger whose `stale_after` falls exactly on the clock is staled. `PROPOSED` triggers are deliberately not swept — an unacknowledged trigger stays visible until somebody dispositions it — and `SATISFIED`, `DISMISSED` and already-`STALE` triggers are terminal. Every row the sweep mutates has its `version` incremented by 1.

A task's `status` runs `DUE`, `IN_REVIEW`, `PASSED`, `FAILED`, with the last two terminal, and it is driven by a single disposition capability available to `ModelApprover` and `PlatformAdmin` whose `action` is one of `START_REVIEW`, `PASS` or `FAIL`, with an optional `findings` string of between 1 and 500 characters when present.

`START_REVIEW` moves `DUE → IN_REVIEW` and stamps `reviewer_user_id` from the caller's `X-User-ID`. It carries the service's third segregation-of-duties rule: the acting operator must differ from the version's `decided_by_user_id`, or the request is rejected with `ERR_SEGREGATION_OF_DUTIES`. Periodic revalidation exists to catch what the original approval missed, so the original approver may not perform it — this closes the self-review loop that the submit-versus-approve split opened. The task's `version` is incremented by 1.

`PASS` and `FAIL` both require the task to be in `IN_REVIEW`, both require the acting `X-User-ID` to equal the `reviewer_user_id` recorded at `START_REVIEW` — rejected with `ERR_SEGREGATION_OF_DUTIES` otherwise, so a review may not be handed off mid-flight — and both require `findings` in the body, rejected with `ERR_INVALID_REQUEST` otherwise, because a revalidation verdict with no recorded reasoning is not an audit record. Both stamp `decided_at` from the logical clock and record `findings`.

`PASS` moves `IN_REVIEW → PASSED` and recomputes the version's `revalidation_due_at` under the pass anchor, incrementing the task's `version` and the version's `version` by 1. Nothing else moves: the version stays `APPROVED` and its deployments keep serving.

`FAIL` moves `IN_REVIEW → FAILED` and opens a four-hop cascade — the mirror image of the snapshot-revocation cascade of §3.2, reached from a different entry point. Hop 1 is the task's own transition. Because the task became `FAILED`, hop 2 takes the artifact version named by `model_version_id`, when its `approval_state` is `APPROVED`, from `APPROVED` to `BLOCKED`, writes `blocked_reason` of `REVALIDATION_FAILED`, and clears `revalidation_due_at` to null so the sweep stops raising further tasks for a version that is no longer approved. Because that version entered `BLOCKED`, hop 3 takes every deployment referencing it whose `rollout_state` is `RAMPING`, `HELD` or `LIVE` into `DRAINING`, sets `traffic_pct` to 0.00, appends one ramp-ledger row whose `reason` is `DRAIN_RELEASE` and whose `delta_pct` is the negative of the traffic the deployment held immediately before, and recomputes the owning serving cluster's `allocated_traffic_pct`, processing those deployments in `created_at` ascending order. Because those deployments left the serving set, hop 4 takes every challenger evaluation on them whose `status` is `COLLECTING` into `INCONCLUSIVE` with `DEPLOYMENT_DRAINED` recorded in `criteria_failures` and its `reserved_samples` returned to the challenger version's `evaluation_sample_budget`. Every row mutated by hops 2 through 4 has its `version` incremented by 1. A version blocked this way recovers only through the unblock path of §3.3, which recomputes its `revalidation_due_at` afresh.

Reading one task returns its `model_version_id`, `due_at`, `swept_at`, `reviewer_user_id`, `findings`, `decided_at` and `status`. The task list is ordered by `due_at` ascending then `created_at` ascending, can be narrowed by `model_version_id` and by `status`, and is the reverse-lookup channel from a version to its revalidation history.

Finally, the **logical clock** is settable, exclusively by `PlatformAdmin`, by supplying a `current_utc` instant. The clock's startup default is exactly 2026-08-01T00:00:00Z: before any such call the logical clock reads that instant and never falls back to real wall-clock time. The clock is monotonic — a `current_utc` that is not strictly after the present value is rejected with `ERR_CLOCK_REGRESSION`, because rewinding it would invalidate instants the service has already stamped. The call returns an object carrying `current_utc` and `previous_utc` and mutates no business row; it only changes what every subsequent request reads as the present moment. Every stamped datetime in the service — `created_at`, `updated_at`, `approved_at`, `closed_at`, `checked_at`, `opened_at`, `resolved_at`, `decided_at`, `swept_at` and `clock_at_step` — and every deadline comparison reads this clock.

## 4. Endpoint Definitions

Every endpoint below returns the standard envelope of §2.2 and requires the `X-User-Role` and `X-User-ID` headers of §2.1. Endpoints that bring a new resource into existence return HTTP 201 with the created resource in `data`; every other successful call returns HTTP 200. State-transition and action endpoints return the full updated resource, not a fragment, so a caller always has the row's new `version` in hand. List endpoints accept `limit` and `offset` as described in §2.3 in addition to the filters named in their descriptions, and single-resource reads accept no query parameters. Endpoints in the underscore-prefixed operational namespace exist to drive the logical clock and the periodic sweep and are restricted to `PlatformAdmin`.
