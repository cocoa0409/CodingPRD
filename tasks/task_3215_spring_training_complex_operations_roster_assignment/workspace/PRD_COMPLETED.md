# Spring Training Complex Operations API - Product Requirements Document

## 1. Introduction

Every February, the Chicago Cubs converge on a handful of desert facilities that must, within a few short weeks, absorb two full professional rosters, their medical evaluations, their travel, and an exhibition calendar. This document specifies the operations platform that runs that convergence. It covers the physical complexes themselves — their fields, clubhouses and training rooms, their occupancy posture and their maintenance windows — together with the people who move through them: players arriving on invitation letters, pitchers working through throwing programs, and staff coordinating daily workout groups.

The platform is not a single workflow but a set of interlocking gates. Roster decisions depend on medical clearance; medical clearance depends on physicals; physicals depend on travel windows; travel depends on the host community's stadium lease and its sponsorship ledger. An operation that ignores one of these dependencies produces an inconsistent camp — a player cleared to travel who was never examined, or a group published in a ballpark that is closed for field work. The rules in this document exist to make those states unreachable.

The specification below is organized for two audiences. Sections 2 and 3 describe the domain in business language: what each role is allowed to do, what each gate protects, and what consequences follow from each action. Section 4 gives the HTTP contract, and Section 5 lists the error identifiers that accompany each rejection.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the platform carries two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role the principal is acting in. When either header is absent, or when `X-User-Role` carries a value that is not one of the ten roles declared below, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). When both headers are present and well formed but the named role is not among the roles the target operation permits, the refusal is `ERR_UNAUTHORIZED` (HTTP 403).

The platform recognizes exactly ten roles: `PlatformAdmin`, `ComplexDirector`, `CommunityLiaison`, `FieldCoordinator`, `PitchingCoordinator`, `TravelCoordinator`, `TeamPhysician`, `RosterManager`, `MinorLeagueCoordinator`, `Analytics`, and `Player`. Each name is spelled exactly as written here; a role string that differs in case or spacing is not recognized and falls to `ERR_UNAUTHENTICATED` rather than `ERR_UNAUTHORIZED`.

Nine of the ten roles are opaque operators. When `X-User-Role` is `PlatformAdmin`, `ComplexDirector`, `CommunityLiaison`, `FieldCoordinator`, `PitchingCoordinator`, `TravelCoordinator`, `TeamPhysician`, `RosterManager`, `MinorLeagueCoordinator`, or `Analytics`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record such an identifier — for instance as `last_decision_actor_id` on a roster record, or as `settlement_actor_id` on a minor league assignment, or as the actor captured by any transition that writes an actor field — but it never compares an opaque identifier to any entity's `id`, and two distinct opaque strings are simply two distinct people even where they look alike.

`Player` is the single entity-backed role. When `X-User-Role` is `Player`, `X-User-ID` is the `id` of the acting `Player` entity, and ownership checks on any resource that references a `Player` compare the resource's foreign-key field to `X-User-ID`. The acknowledgement of a camp invitation is the one operation only the invited player may perform, and the check is that the acting `Player` entity's `id` equals the invitation's `player_id`.

Separately from authentication and authorization, the platform enforces segregation of duties on certain finalization steps. A record's `last_decision_actor_id` naming the same `X-User-ID` as the actor now requesting finalization is a conflict, and the request is rejected with `ERR_SOD_VIOLATION` (HTTP 403). The same identifier comparison applies to `settlement_actor_id` when a settled break-out is voided by the person who settled it; that rejection also carries `ERR_SOD_VIOLATION` with HTTP 403.

Authorization failures always take precedence over domain rejections: a role that is not permitted for an operation is refused before any state, window or business rule is examined.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list operation accepts `limit` and `offset`. The default `limit` is 10, the smallest permitted `limit` is 1 and the largest is 100; a `limit` outside that span is a structurally invalid value and is refused the same way any malformed request is, with `ERR_INVALID_REQUEST` (HTTP 400). The default `offset` is 0, and offset counts whole records skipped from the front of the result set. Both parameters are always optional; a negative `offset` is likewise structurally invalid and is refused with `ERR_INVALID_REQUEST` (HTTP 400).

List results are returned oldest-first: the ordering key is `created_at` ascending. The `meta` object of a list response additionally carries all four pagination fields — `limit`, `offset`, `total_count` and `has_more` — where `total_count` is the number of records matching the filter across all pages, not merely the number on the current page, and `has_more` states whether any records remain beyond the current window.

### 2.4. Identity, Denominations and Rounding

Every entity in this specification carries an `id` that is a server-minted UUID, unique across the platform and carrying no type prefix — a `Complex` id and a `Player` id are indistinguishable in shape. Every entity also carries `created_at`, an ISO 8601 UTC instant rendered with exactly three fractional digits. The great majority of entities carry `updated_at` and `version` as well: `updated_at` refreshes to the current logical clock on every mutation of that row, and `version` is an integer that begins at its initial value and increments by one on each mutation of that row. The `version` counter of an entity is the anchor for the optimistic concurrency rules in §2.8, and it is never a UUID. When a complex or a player is created, a body that supplies any of these server-minted fields — the entity `id`, `created_at`, `updated_at`, `version`, or any derived read such as `posted_occupancy_units`, `reserved_major_units`, `reserved_minor_units`, `maintenance_block_units`, `facility_posture`, `contention_flagged` or `posture_sweep_index` — is structurally invalid and is refused with `ERR_INVALID_REQUEST` (HTTP 400); such fields are never set directly by a client.

Every one of the nineteen entities in this specification carries all four common properties — `id`, `created_at`, `updated_at` and `version` — with no exceptions. That includes the join-style rows such as `GroupAssignment`, `GameParticipation` and `ThrowProgramSession`, which are as fully versioned as the aggregates they hang from. The three expected-version inputs described in §2.8 nevertheless name only the parent aggregate whose state the write depends on: no request supplies an expected version for a participation row, an assignment row, or a session row, because no write is guarded on those rows' own versions.

All monetary quantities in this system are integer cents. There are no fractional cents anywhere in the specification, no per-row rounding step, and no monetary field is ever expressed as a decimal fraction of a dollar. Where a monetary figure is produced by a formula, the arithmetic is integer arithmetic and any division is a floor division performed exactly once, at the point the specification names — never applied incrementally row by row, and never rounded half-up. Ratios expressed in per-mille (a value out of one thousand) are likewise integer quantities obtained by floor division. Where a threshold is stated as a percentage of a capacity, the percentage is applied with a floor, never with a round-half-up step.

### 2.5. The Logical Clock

The platform does not read wall-clock time. It maintains a single logical clock whose value at server startup is exactly `2026-09-01T00:00:00Z`, and the server must never substitute the real current time for it. Every temporal gate in this document — report windows, lease windows, the gameday packaging window, the void-decision cutoff, gameday detection, the day-of-game throwing bump — is evaluated against this logical clock and nothing else.

A `PlatformAdmin` may advance the clock to an arbitrary instant through a dedicated test-driving capability that accepts a `current_utc` value and makes it the clock's new value, returning the resulting `current_utc`. Comparisons against the clock are half-open wherever this document says "before" or "at or after": an operation permitted while the clock is strictly before an instant is refused at exactly that instant. Setting the clock also re-runs the posture sweep against every complex, so each complex's posture is re-derived — subject to the stickiness of §2.6 — and every complex's `posture_sweep_index` advances under the new instant.

Two derived instants on a `GameSchedule` are computed once from `game_datetime` and `duration_units`, where a duration unit spans one hour: `game_interval_start` is the first-pitch instant minus the game's duration units, and `game_interval_end` is the first-pitch instant plus the same duration units. These define the half-open field-time interval the game occupies, and they are the interval against which session blocks are compared in §2.7.

### 2.6. Aggregate Posture and Maintenance Windows

A `Complex` presents a derived operational posture in `facility_posture`, one of `NORMAL`, `FIELD_RESTRICTED` or `CLOSED`. The posture is never set directly; it is the output of a sweep. Four occupancy aggregates feed that sweep. `posted_occupancy_units` is the sum of `capacity_units` over the complex's workout groups, counting only groups whose `group_status` is `PUBLISHED` — groups that are still `FORMING` or already `DISBANDED` contribute zero. `reserved_major_units` counts the group assignments on this complex whose `roster_bucket` is `MAJOR` and whose `assignment_status` is `PROVISIONAL` or `ACTIVE`, restricted to assignments whose owning group is `PUBLISHED`. `reserved_minor_units` is the same count for assignments whose `roster_bucket` is `MINOR`. `maintenance_block_units` records the capacity withheld by the most recent field-maintenance action.

The withheld capacity is a function of `field_maintenance_status`, which is one of `OPEN`, `HALF_FIELD` or `CLOSED`. When the status is `OPEN`, `maintenance_block_units` is zero. When the status is `HALF_FIELD`, the withheld amount is half of `facility_capacity_units`, rounded up to a whole unit — so an odd capacity withholds the larger half. When the status is `CLOSED`, the withheld amount is the whole of `facility_capacity_units`. Asking to close a complex whose `field_maintenance_status` is already `CLOSED` is refused with `ERR_INVALID_STATE` (HTTP 409).

The sweep compares occupancy against *effective* capacity, which is `facility_capacity_units` less `maintenance_block_units`. The evaluation order is pinned and matters: the sweep first asks whether `posted_occupancy_units` has reached or exceeded effective capacity; if so the posture is `CLOSED`. Only if that is false does it ask whether `posted_occupancy_units` has reached or exceeded ninety-five percent of effective capacity, that ninety-five percent figure being floored to a whole unit; if so the posture is `FIELD_RESTRICTED`. Otherwise the posture is `NORMAL`. Because the first comparison is against effective capacity and not against the raw capacity, a complex under a `HALF_FIELD` block can be driven `CLOSED` by an occupancy that would be perfectly comfortable on an unrestricted field.

Two derived reads accompany the posture. `contention_flagged` is true exactly when `posted_occupancy_units` exceeds the raw `facility_capacity_units` — note that this compares against the *unrestricted* capacity, ignoring the maintenance block, so it is a stricter and differently-keyed condition than the posture thresholds. It is cleared by the next sweep that finds the condition false. `posture_sweep_index` is a monotone counter on the complex, starting at 0, incremented by one every time a posture sweep runs against it; the sweep runs both on demand and as a side effect of any mutation to a group assignment, a workout group, or the complex's own field maintenance.

Once the posture is `CLOSED`, a sweep may never move it back down. The sweep is sticky at `CLOSED`: it will not relax the posture to `FIELD_RESTRICTED` or to `NORMAL` no matter how the aggregates move, and the condition persists until a field-maintenance action explicitly returns the complex to `OPEN` from `FIELD_RESTRICTED`. This stickiness is the reason field closures are treated as a serious operational event rather than a temporary state.

Alongside the posture, a complex reports a contention posture on a four-point scale derived from the same occupancy aggregate. The denominator is `facility_capacity_units` less `maintenance_block_units`, and it is never allowed to fall below one. The ratio is expressed in per-mille, as `posted_occupancy_units` multiplied by one thousand and floor-divided by that denominator. A ratio of one thousand per-mille or more is `OVER`; a ratio of nine hundred and fifty per-mille or more, but less than one thousand, is `TIGHT`; a ratio of nine hundred per-mille or more, but less than nine hundred and fifty, is `WATCH`; anything below nine hundred per-mille is `NORMAL`. The reported value is the enum member, never the raw ratio. On a complex whose `season_split_track` is `SHARED`, one additional rule applies: if any workout group on the complex is `PUBLISHED` and its `assigned_units` has reached its `capacity_units`, a contention posture that would otherwise read `NORMAL` is reported as `TIGHT` instead, even though the aggregate ratio stays below nine hundred and fifty per-mille. The contention posture is a read-only projection on a complex that is obtained only through the complex read operations; no request body accepts it as an input.

### 2.7. Field-Time Intervals and Nested Resource Retrieval

Session blocks on a complex occupy a half-open interval `[session_date, session_end_datetime)`. Games occupy a half-open interval derived from first pitch as described in §2.5. The two kinds of interval are compared on the same complex, and they are compared after truncation to whole minutes. Because both intervals are half-open after truncation, a session that ends at exactly the instant the game interval begins still conflicts, and so does a game whose interval begins at exactly the instant a session ends; the truncated session interval and the truncated game interval are compared closed at both ends, which is what makes a single shared minute boundary a conflict. A candidate game whose interval touches any scheduled session interval on the same complex — including at a single shared minute boundary — may not be published, and the rejection is `ERR_TEMPORAL_OVERLAP` (HTTP 409).

Where this document describes an operation as scoped to a nested path, the path parameters are validated strictly left to right. The outermost identifier is resolved first, then the identifier of the resource nested beneath it, and then any identifier nested beneath that. A path resource that does not exist yields `ERR_RESOURCE_NOT_FOUND` (HTTP 404). A resource that exists but does not belong to the parent named earlier in the path yields the same `ERR_RESOURCE_NOT_FOUND` with HTTP 404 — the platform deliberately does not distinguish "wrong parent" from "no such record" on the path. A body-supplied identifier that fails to resolve to any declared entity is a different failure and yields `ERR_FOREIGN_KEY_NOT_FOUND` (HTTP 404); this code is distinct from the path-level 404 and must be distinguishable from it by the client. The body identifiers subject to this check are the ones named in §3 as foreign references: among them `player_id`, `agreement_id`, `workout_group_id`, `host_community_record_id`, `group_assignment_id`, `complex_id`, `camp_invitation_id`, `game_schedule_id`, and `roster_record_id`.

### 2.8. Optimistic Concurrency Control

Three write operations are guarded by optimistic concurrency control, and only three. Each carries a non-optional expected-version input naming the parent entity whose state the write depends on; a missing value for that input is a structural defect and is refused with `ERR_INVALID_REQUEST` (HTTP 400), never treated as "skip the check". In all three cases the supplied value is compared to the parent entity's current `version`, and a mismatch is refused with `ERR_STALE_VERSION` (HTTP 412).

Creating a group assignment against a workout group must carry `expected_group_version` matching the group's current `version`. If the group has advanced since the client last read it — for instance because a withdrawal just freed a seat and legitimately changed the group's capacity position — the create is refused with `ERR_STALE_VERSION` at HTTP 412, so the writer cannot seat a player against a group picture they have not observed.

Confirming a travel arrangement against a camp invitation must carry `expected_invitation_version` matching the invitation's current `version`. If the invitation has advanced since the client last read it — for instance because its letter was just sent or the player has just arrived, either of which legitimately advances the invitation — the confirmation is refused with `ERR_STALE_VERSION` at HTTP 412.

Confirming a game participation must carry `expected_game_version` matching the game's current `version`. If the game has advanced since the client last read it — for instance because another participation on the same game was just confirmed — the confirmation is refused with `ERR_STALE_VERSION` at HTTP 412.

Version fields are read-only on every resource: they appear in responses, they increment on mutation, and they are never supplied by a client except as the `expected_..._version` input described above. Note also that publishing a workout group and publishing a game both accept an `expected_group_version` and `expected_game_version` respectively as part of their own contract, and both compare against the same `WorkoutGroup.version` and `GameSchedule.version` counters described here; the publish-time check uses the same `ERR_STALE_VERSION` at HTTP 412 when the supplied value does not match.

### 2.9. Validation Precedence

When several rules could reject the same request, the platform evaluates them in a fixed order and reports only the first failure. The order is:

1. Authentication first: missing or unrecognized credentials are `ERR_UNAUTHENTICATED` (HTTP 401).
2. Authorization second: a role not permitted for the operation is `ERR_UNAUTHORIZED` (HTTP 403).
3. Segregation of duties third, on the operations where it applies: a finalizer or voider who is the same principal that advanced the record is `ERR_SOD_VIOLATION` (HTTP 403).
4. Path existence fourth: `ERR_RESOURCE_NOT_FOUND` (HTTP 404).
5. Body-reference existence fifth: `ERR_FOREIGN_KEY_NOT_FOUND` (HTTP 404).
6. Roster-state legality next: `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409), then the terminal-status guard `ERR_ROSTER_ALREADY_FINAL` (HTTP 409).
7. Facility and agreement state legality next: `ERR_INVALID_STATE` (HTTP 409).
8. Temporal windows next — `ERR_OUTSIDE_WINDOW` (HTTP 422) and then the physical scheduling lead `ERR_PHYSICAL_WINDOW_LEAD` (HTTP 422).
9. Safety preconditions next: `ERR_MEDICAL_CLEARANCE_REQUIRED` (HTTP 422), then `ERR_INJURY_TRAVEL_UNSAFE` (HTTP 422), then `ERR_MAINTENANCE_CONFLICT` (HTTP 409).
10. Interval and capacity constraints next, in this order: `ERR_TEMPORAL_OVERLAP` (HTTP 409), `ERR_PHYSICAL_DOUBLE_BOOKED` (HTTP 409), `ERR_GROUP_CAPACITY_EXCEEDED` (HTTP 409), `ERR_PLAYER_ALREADY_ASSIGNED` (HTTP 409), `ERR_BUCKET_MISMATCH` (HTTP 422), `ERR_TRAVEL_RADIUS_EXCEEDED` (HTTP 422), `ERR_DUPLICATE_IDP_NUMBER` (HTTP 409), `ERR_THROW_REQUIREMENT_UNMET` (HTTP 422), `ERR_WAIVER_WINDOW_EXPIRED` (HTTP 409), `ERR_FARM_ENTITY_EXCLUDED` (HTTP 409), `ERR_AGREEMENT_NOT_ACTIVE` (HTTP 409), `ERR_INVITATION_LETTER_MISSING` (HTTP 409), `ERR_SPONSORSHIP_NOT_FULLY_FUNDED` (HTTP 422), the break-out return window `ERR_OUTSIDE_WINDOW` (HTTP 422), `ERR_AGREEMENT_UNDERFUNDED` (HTTP 402), and `ERR_POSTURE_BLOCKS_FISCAL` (HTTP 409).
11. Structural validity last: a missing required body field or a structurally invalid value — an unrecognized enum member, a `capacity_units` below 1, `field_units` below 1, `target_catch_play_throws` or `target_bullpen_sessions` below 1, a negative `travel_radius_miles`, `travel_cost_cents` or `commitment` amount, a `throw_count` below 0, a `play_catch_throws` below 0, a zero or negative ticket `quantity`, or a `report_final_date` earlier than `report_current_date` — is `ERR_INVALID_REQUEST` (HTTP 400).

The practical consequence is that a caller who is both unauthorized and would also violate a business rule sees `ERR_UNAUTHORIZED`, and a caller who names both a missing parent and a missing body reference sees `ERR_RESOURCE_NOT_FOUND`. Within the state families, a roster record with a terminal status is reported as `ERR_ROSTER_ALREADY_FINAL` only after the transition-legality check has already failed to apply.

### 2.10. Farm Exclusion and Trails

A `SpringTrail` maps a player onto the minor-league spring trail at one of four levels: `AAA`, `AA`, `A_PLUS` or `A`. A trail row is created with `trail_status` `ACTIVE` and `mapped_at` set to the current logical clock; ending the trail moves `trail_status` to `ENDED`. While a player is mapped into an `ACTIVE` trail row, that player is outside the farm-scoped camp machinery: the roster-decision path, the finalization and void path, the active-roster selection, the program-profile reinstatement, and the recording of physical examination outcomes are all refused for that player with `ERR_FARM_ENTITY_EXCLUDED` (HTTP 409). The excluded scopes are `PlayerRosterRecord`, `PlayerProgramProfile` and `CampInvitation`; the trail does not block card-and-roster reads, and it does not block operations on other players.

### 2.11. Community Fiscal Ledger

Each host community agreement accumulates a ledger on its `HostCommunityRecord`. `ticketing_revenue_cents` is the cumulative revenue from ticket sales; `sponsorship_recorded_cents` is the sum of `committed_amount_cents` over every sponsorship on this record whose `reconciliation_status` is not `SETTLEMENT_VOIDED`, which in particular still includes a `RECOGNIZED` row; `sponsorship_revenue_cents` is the sum of `received_amount_cents` over sponsorships on this record whose `reconciliation_status` is `UNSETTLED`, `SETTLED` or `SETTLEMENT_VOIDED`, so a recognized row contributes no revenue and a voided settlement posts its received amount back into the ledger. The `community_ledger_cents` is the sum of `ticketing_revenue_cents` and `sponsorship_revenue_cents`. Against that ledger sit two draws: `agreement_funded_cents` is the cumulative travel posted under this agreement, being the sum of `agreement_funded_cents` over the agreement's travel arrangements whose funding source is the agreement, reversed whenever a confirmation is reverted or a cancellation unwinds it; and `recognition_funded_cents` is the sum, over recognized sponsorships, of the recognition allocation described in §3.7.

The `ledger_gap_cents` is `community_ledger_cents` less `recognition_funded_cents`. This gap is a conserved quantity under paired operations: recognizing a sponsorship and then voiding that settlement must leave `ledger_gap_cents` exactly at its pre-settlement value, and a create-cancel pair on a travel arrangement must leave `community_ledger_cents` exactly where a revert alone would leave it. Fiscal operations are locked whenever the owning complex is not in the `NORMAL` posture; voiding a settlement under a restricted or closed complex is refused with `ERR_POSTURE_BLOCKS_FISCAL` (HTTP 409).

## 3. Business Logic & Workflows

### 3.1. Complex Onboarding, Agreements and the Host Community

A `PlatformAdmin` establishes a spring training complex by supplying `name`, `host_city`, `facility_capacity_units`, a `season_split_track` and a `timezone`. The season split track defaults to `SHARED`, meaning major and minor league camps co-tenure the facility, and may be set to `DEDICATED`; the timezone defaults to `America/Phoenix` and is the IANA zone the report and lease dates resolve against. A newly created complex starts with `field_maintenance_status` at `OPEN`, `facility_posture` at `NORMAL`, `maintenance_block_units` at 0 and `posture_sweep_index` at 0, and its `posted_occupancy_units`, `reserved_major_units`, `reserved_minor_units` and `contention_flagged` all sit at their zero values until occupancy accrues.

Each complex may host a stadium lease agreement created by a `CommunityLiaison` — the `CommunityLiaison` and the `PlatformAdmin` are both permitted here. The agreement is created with a `complex_id` tying it to the complex, a `stadium_name` for the host ballpark, a `lease_start_date` and `lease_end_date` bounding the lease, and the community's commercial parameters: `annual_rent_cents`, `sponsorship_minor_league_base_cents`, `sponsorship_major_league_base_cents`, `ticket_price_cents` and `ticket_sellout_capacity`. The lease end must be strictly later than the lease start; an agreement whose dates are equal or inverted is structurally invalid and is refused with `ERR_INVALID_REQUEST` (HTTP 400). A new agreement opens in `DRAFT`.

Activation is the `CommunityLiaison`'s exclusive act, and it is gated three ways: the agreement must still be in `DRAFT` (else `ERR_INVALID_STATE`, HTTP 409); the lease end must be strictly later than the lease start; and the owning complex's `facility_posture` must not be `CLOSED`, since a complex closed for field work cannot be committing to a host community's season. When those hold, `agreement_status` moves to `ACTIVE`. From `ACTIVE` the liaison may send the agreement back to `DRAFT`, but only while no host community record under it has `ticketing_status` `ON_SALE` — an agreement with live ticketing cannot quietly withdraw. Termination is available from both `DRAFT` and `ACTIVE`; terminating an `ACTIVE` agreement additionally cascades to its community records, driving every record whose `ticketing_status` is `ON_SALE` or `SOLD_OUT` to `SUSPENDED`. Termination is terminal.

A separate cascade reaches back into agreements from the fiscal side. Whenever a settlement void is processed under an agreement, `agreement_status` is recomputed back to `DRAFT` when no host community record on that agreement has `ticketing_status` `ON_SALE`. This is the same condition the explicit revert-to-draft enforces, and it means an agreement can slide back to `DRAFT` as a consequence of a sponsorship reversal rather than by a liaison's direct action. The status reverted to here is `DRAFT`, reached from `ACTIVE` rather than from the terminal `TERMINATED` state — so an agreement that had already been terminated stays terminated, and only a live agreement is undone by the reversal.

A `CommunityLiaison` opens the ledger record for an agreement by supplying its `agreement_id`. The record opens with `ticketing_status` at `NOT_OPEN` and every ledger accumulator at zero: `tickets_sold`, `ticketing_revenue_cents`, `sponsorship_recorded_cents`, `sponsorship_revenue_cents`, `community_ledger_cents`, `agreement_funded_cents`, `recognition_funded_cents` and `ledger_gap_cents`. A single agreement may hold several host community records at once; the funding and liability selectors reach the agreement's travel arrangements through the first such record.

### 3.2. Player Registration and the Medical Pipeline

Player records are created with `full_name`, `idp_number`, `position_code`, `acquisition_channel`, `home_country` and `home_complex_id`, plus optional `mlb_service_days` and `minor_league_option_years_used`. The position code is one of `P`, `C`, `INF`, `OF` or `DH`; the acquisition channel is one of `DRAFT_PICK`, `NRI_ASSIGNMENT`, `FREE_AGENT`, `INTERNATIONAL_SIGNING` or `TRADE`. Service days default to 0 and are bounded from 0 to 9999 inclusive; option years used default to 0 and are bounded from 0 to 3 inclusive. The `idp_number` is unique across all players without regard to scope — a duplicate, even for a player on a different complex, is refused with `ERR_DUPLICATE_IDP_NUMBER` (HTTP 409). The `home_complex_id` names the camp complex the player reports to, and it is the complex that resolves as the "owning complex" for travel cost allocation, travel funding source and the travel liability window. A new player opens with `clearance_status` at `PENDING`.

Medical clearance runs on a separate profile. A `TeamPhysician` — or a `RosterManager`, who shares this operation — opens the camp-eligibility profile against a `player_id`. The profile opens with `eligibility_status` at `MEDICALS_PENDING`, `rehab_program_phase` at `PHASE_1`, and `major_group_count`, `minor_group_count` and `active_rehab_assignment_count` all at 0. The profile's `rehab_program_phase` is one of `PHASE_1`, `PHASE_2`, `PHASE_3`, `PHASE_4`, `PHASE_LIVE` or `SHUTDOWN`, and it mirrors the player's throwing program phase with one deliberate exception described in §3.6.

The physician schedules a physical examination against a `player_id` with a `scheduled_visit_date`, and the examination opens with its `status` reading `SCHEDULED`. Recording the outcome supplies a `physical_result` of `PASSED`, `PASSED_WITH_MODIFICATION` or `FAILED` and is permitted only while the examination's `status` is `SCHEDULED` and only once the logical clock has reached the `scheduled_visit_date` — an examination cannot be performed before the day it was booked, while a visit date already in the past remains fully performable. On performance, the examination moves to `PERFORMED` and `performed_at` is captured as the current logical clock.

Two windows govern examination timing. For a player whose `home_country` is not the United States, the `scheduled_visit_date` must sit at least five days before the invitation's `report_current_date`; a visit scheduled closer than that is refused with `ERR_PHYSICAL_WINDOW_LEAD` (HTTP 422). Separately, two performed examinations on the same player may not collide: ordering the two examinations by their `scheduled_visit_date`, the two visits are compatible only when the earlier examination's `performed_at` plus the examination duration — one hour — falls at or before the later examination's `scheduled_visit_date`, or when at least a two-day clearance buffer separates the two visits. A collision is refused with `ERR_PHYSICAL_DOUBLE_BOOKED` (HTTP 409).

Recording an examination outcome is the origin of the clearance cascade. When the result is `PASSED` or `PASSED_WITH_MODIFICATION`, the player's `eligibility_status` moves to `CAMP_ELIGIBLE`; when the result is `FAILED`, it moves to `TURNED_AWAY`. The player's own `clearance_status` then mirrors the profile — to `CAMP_CLEARED` or to `TURNED_AWAY` respectively — so a player whose examination succeeded is cleared, and one whose examination failed is turned away, with the player's stored clearance transitioning directly from `PENDING` to `CAMP_CLEARED` on the successful branch. The player's clearance advances straight from `PENDING` to the cleared band with no intermediate state: the server keeps no `MEDICALS_COMPLETE` value, and the successful outcome is what carries the player to `CAMP_CLEARED`. A failing examination takes the player to `TURNED_AWAY` from either `PENDING` or `CAMP_CLEARED`. If the player was turned away, every group assignment they hold with status `PROVISIONAL` or `ACTIVE` is withdrawn; in both branches the complex's `posted_occupancy_units`, `reserved_major_units` and `reserved_minor_units` are recomputed, and the profile's `major_group_count` and `minor_group_count` and its `active_group_assignment_id` are recomputed.

The compensations mirror this cascade exactly. Voiding a performed examination is permitted only from `PERFORMED`; it moves the examination to `VOIDED` and nulls its `physical_result`. The profile returns to `MEDICALS_PENDING` and the player's `clearance_status` returns to `PENDING`, but only when no other performed examination remains on that player — if a second successful examination is still standing, the clearance stands with it. Every group assignment of that player still in `PROVISIONAL` is withdrawn, and the complex's `reserved_major_units` and `reserved_minor_units` and the profile's group counts are recomputed.

A player who was turned away can be brought back into the pipeline. A `TeamPhysician` may reinstate the profile directly, which requires that the profile is currently `TURNED_AWAY` and that some examination on that player is `PERFORMED` with a result of `PASSED` or `PASSED_WITH_MODIFICATION`; the reinstatement moves `eligibility_status` to `MEDICALS_PENDING` and recomputes the profile's group counts. The same physician may instead reset the player's own clearance from `TURNED_AWAY` back to `PENDING`, which requires that at least one performed examination on that player carries a passing result; that reset also re-derives the profile's `eligibility_status` through the rule above. So a player who failed an examination and is later cleared by a second successful examination has two routes back, one through the profile and one through the player.

### 3.3. Invitations, Letters and the Report Window

A `TravelCoordinator` — or a `RosterManager` — issues a camp invitation against a `player_id`, supplying an `invitation_kind` of `NRI_STANDARD`, `GUEST_INSTRUCTOR` or `CAMP_INVITEE`, and optionally a `report_base_date`. The report dates are computed at issue time and frozen: they are not recomputed later when the player's profile changes.

The computation proceeds from the base date. The base date is the supplied `report_base_date` if one was given, and otherwise `2026-02-10T00:00:00Z`. A lead is subtracted from it: fourteen days for a player whose `position_code` is `P` or `C` — the pitchers and catchers who report first — and twenty-one days for a position player whose `position_code` is `INF`, `OF` or `DH`. A guest instructor invitation adds seven further days to that lead. The resulting instant is truncated to midnight UTC and written as `report_current_date`, the earliest permitted arrival. The mandatory arrival instant is then derived from it: a final grace of fourteen days, plus three further days for each full group of ten active rehab assignments the player holds at invite time with any remainder rounded up to one whole day, gives `report_final_date`. The final date is always at or after the current date; a supplied `report_final_date` earlier than `report_current_date` is structurally invalid and refused with `ERR_INVALID_REQUEST` (HTTP 400). A supplied `report_final_date` is validated against the current date but does not replace it: the record's `report_final_date` is always the derived instant and never the supplied one.

The invitation opens with `invitation_status` at `ISSUED`, `invitation_letter_status` at `LETTER_PENDING`, `travel_arrangement_status` at `NOT_ARRANGED`, and `arrival_band` at `MISSED_WINDOW` until an arrival is recorded. Its `domestic_travel` flag is derived at issue time from the player: it is true exactly when the player's `home_country` is `United States`, and a player from any other country is a non-domestic traveler who does not carry that flag.

Onboarding follows the letter. A `TravelCoordinator` sends the letter, moving `invitation_letter_status` to `LETTER_SENT`; the letter is a precondition for both travel confirmation (§3.4) and arrival. The player then acknowledges the invitation, an act reserved to the `Player` role and permitted only while the invitation is `ISSUED` and only when the acting player's own `id` matches the invitation's `player_id`. Acknowledgement moves `invitation_status` to `ACKNOWLEDGED`.

Arrival is recorded by a `TravelCoordinator` against an `ACKNOWLEDGED` invitation and closes a set of conditions: the letter must already be `LETTER_SENT` (else the arrival is refused with `ERR_INVITATION_LETTER_MISSING` at HTTP 409); a non-domestic player must have an arranged travel arrangement, so the condition is that the invitation is domestic-traveling or its `travel_arrangement_status` is `ARRANGED`; and the logical clock must not be past `report_final_date` — an arrival after the mandatory instant is refused with `ERR_OUTSIDE_WINDOW` (HTTP 422). On success the invitation moves to `ARRIVED` and `actual_report_date` is captured as the current logical clock.

The `arrival_band` is then derived from the captured instant against the two frozen dates. An arrival strictly before `report_current_date` reads `EARLY`. An arrival at exactly `report_current_date` reads `MET_CURRENT`. An arrival strictly after `report_current_date` and at or before `report_final_date` reads `MET_FINAL`. An arrival at any other instant — that is, after the final date — reads `MISSED_WINDOW`. Note that the window is closed at both ends relative to the report dates: arriving exactly at the current date is `MET_CURRENT` rather than `MET_FINAL`, and arriving exactly at the final date is still `MET_FINAL` rather than `MISSED_WINDOW`.

A non-domestic arrival can still be blocked at the border. A `TravelCoordinator` marks a visa block against an `ARRIVED` invitation that is not domestic-traveling; the invitation moves to `VISA_BLOCKED`, its `travel_arrangement_status` moves to `CANCELLED`, and every travel arrangement on it whose status is `PLANNED` or `CONFIRMED` is driven to `CANCELLED`. Each such arrangement that was funded by the agreement then has its post reversed out of the community record, and the record's `sponsorship_recorded_cents`, `recognition_funded_cents`, `community_ledger_cents` and `ledger_gap_cents` are recomputed along with the agreement's travel liability reads. A visa block therefore unwinds everything the community had committed to that trip.

Invitations that are never answered expire. When an operations checkpoint of type `invitation-report-sweep` runs, every invitation still reading `ISSUED` with no `actual_report_date` recorded and whose logical clock is strictly past `report_final_date` is driven to `NO_SHOW`; an invitation that has already moved on — for example to `ACKNOWLEDGED` — is left untouched, since the sweep advances only rows still reading `ISSUED`. That sweep carries the same unwind as a visa block: `travel_arrangement_status` goes to `CANCELLED`, every `PLANNED` or `CONFIRMED` arrangement goes to `CANCELLED`, the agreement-funded posts are reversed out of the community ledger, and the community record's `sponsorship_recorded_cents`, `recognition_funded_cents`, `community_ledger_cents` and `ledger_gap_cents` are recomputed together with the agreement's `travel_liability_window_count`, `travel_liability_days` and `settlement_release_lag_days`. `NO_SHOW` is terminal.

### 3.4. Travel Planning, Confirmation and Community Funding

Travel arrangements hang off an invitation. A `TravelCoordinator` plans or confirms one by supplying the invitation's `camp_invitation_id`, a `mode` of `AIR`, `BUS` or `AUTO`, a `travel_radius_miles`, a `departure_at`, a `travel_cost_cents`, a `confirm` flag, and the `expected_invitation_version` described in §2.8. When no arrangement yet exists for the invitation one is created; when one already exists, the most recent arrangement that has not been cancelled is reused and updated. A second arrangement may legitimately co-exist on one invitation, which is why the invitation carries an arrangement status separate from any single arrangement's own status.

Planning and confirmation differ. With `confirm` false the arrangement is written at `PLANNED` and nothing is funded. With `confirm` true the arrangement is written at `CONFIRMED`, and funding evaluation runs. Confirmation itself is gated: the arrangement must currently be `PLANNED`; the invitation's `invitation_letter_status` must already be `LETTER_SENT`, else the confirmation is refused with `ERR_INVITATION_LETTER_MISSING` (HTTP 409); the `departure_at` must not be later than the invitation's `report_current_date`; and for a non-domestic player the departure must be at least five days before `report_current_date`, because international travel needs a longer runway than a domestic flight. A departure that violates either of those two window bounds is refused with `ERR_OUTSIDE_WINDOW` (HTTP 422), and those bounds are examined before the letter gate. The direction of these comparisons is strict — a departure exactly at `report_current_date` is permitted for a domestic player, and a departure exactly five days before `report_current_date` is permitted for a non-domestic one.

Confirmation also requires an arranged invitation. On success the arrangement moves to `CONFIRMED`, the invitation's `travel_arrangement_status` moves to `ARRANGED`, and two funding decisions are taken. A direct create of an arrangement row is the sole exception to the `expected_invitation_version` requirement: it always appends a fresh row, carries no such input, and is never gated by the optimistic-concurrency check of §2.8.

The first is the funding source. If the player's owning complex — the complex named by `home_complex_id` — has a community agreement in `ACTIVE` status, the arrangement is funded by the agreement. If no such agreement exists but the `travel_cost_cents` is greater than zero, the arrangement is funded by reimbursement. If neither holds — that is, no active agreement and no cost — the funding source is `NONE`. When several active agreements exist on the complex, they are considered in `created_at` ascending order and the first is used. Independently of the source, `reimbursement_status` becomes `LIABLE` whenever `travel_cost_cents` is greater than zero and stays `NOT_LIABLE` otherwise, so a zero-cost trip is never a liability even though it can still be an agreement-funded draw of zero.

The second is the amount, which depends on the source. Under agreement funding the amount is the travel cost scaled down by a per-mille discount selected by the mode and by the distance band of `travel_radius_miles`: distances up to and including 100 miles form the first band, distances up to and including 300 miles form the second, and anything further forms the third. The discount per-mille values are: for `AUTO`, 0 in the first band, 10 in the second and 20 in the third; for `AIR`, 0, 5 and 10; for `BUS`, 0, 15 and 30. The amount is the travel cost multiplied by one thousand less the discount, and then floor-divided by one thousand — the scale is applied first and the single floor division comes last, in that pinned order. Under reimbursement funding the radius discount does not apply at all; instead a holdback of fifty per-mille is withheld from the raw cost, so the amount is the travel cost multiplied by nine hundred and fifty and floor-divided by one thousand — strictly smaller than the agreement-funded figure for the same raw cost. Only the amount matching the chosen source is written: the arrangement's `agreement_funded_cents` carries the agreement figure when the source is the agreement and zero otherwise, and its `reimbursement_cents` carries the reimbursement figure when the source is reimbursement and zero otherwise.

When the source is the agreement, the agreement-funded amount is posted as a travel draw against the community record's `agreement_funded_cents` — which sums, over the agreement's arrangements whose funding source is the agreement, the amount each has drawn — and the agreement's `travel_liability_window_count`, `travel_liability_days` and `settlement_release_lag_days` are recomputed. The draw does not reduce `ticketing_revenue_cents`, which tracks ticket sales alone. A draw that would exceed the record's available agreement funding — that is, `ticketing_revenue_cents` less the funding already posted — is refused with `ERR_AGREEMENT_UNDERFUNDED` (HTTP 402). Nothing is posted against the community ledger under reimbursement funding; the club simply carries the reimbursement.

Both funding directions have compensating actions, and both must restore every conserved quantity. Reverting a confirmed arrangement: the row must currently be `CONFIRMED`; on success it returns to `PLANNED`, the invitation's `travel_arrangement_status` returns to `NOT_ARRANGED`, the agreement-funded draw is reversed out of `agreement_funded_cents`, the row's `funding_source` returns to `NONE` and its `reimbursement_status` returns to `NOT_LIABLE`, and the record's `community_ledger_cents` and `ledger_gap_cents` and the agreement's three travel liability reads are recomputed. Cancelling: an arrangement may be cancelled from either `PLANNED` or `CONFIRMED`. Cancelling a planned row simply moves it to `CANCELLED`. Cancelling a confirmed row moves it to `CANCELLED`, reverses the agreement-funded draw out of `agreement_funded_cents`, sets `reimbursement_status` to `VOIDED`, and recomputes the record's `community_ledger_cents` and `ledger_gap_cents` and the agreement's three travel liability reads. In both cancellation branches, if the cancelled row was the invitation's only arrangement that was not already cancelled, the invitation's `travel_arrangement_status` returns to `NOT_ARRANGED`. The two branches are compensating pairs: for the same starting row, cancelling a confirmed arrangement and reverting it before cancelling must leave `community_ledger_cents` in the same place.

The agreement's liability reads are computed over a defined set of rows. The liability rows are the agreement's travel arrangements whose `reimbursement_status` is `LIABLE` or `VOIDED`, ordered by `created_at` ascending and then by `departure_at` ascending — never by `id`. `travel_liability_window_count` is the number of such rows. `travel_liability_days` is the sum, over those rows, of the whole-day span from the row's `departure_at` to the agreement's `lease_end_date`, counted start-inclusive and end-exclusive. `settlement_release_lag_days` is the whole-day span from the agreement's `lease_end_date` to the latest sponsorship settle, recognize or void-settlement instant under that agreement, and it is zero when no sponsorship under the agreement has been acted on. The window count is variant-sensitive in one specific place: while the arrangement has not been cancelled the default set includes `VOIDED` rows, so a cancelled arrangement still occupies a liability window; after a cancellation the set narrows to `LIABLE` rows only, so the cancelled row drops out and `travel_liability_window_count` decreases by exactly one. Note that the liability set is bounded at its end inclusively, so a row whose span ends exactly on the lease end date still counts. Note also that a zero-cost arrangement, whose `reimbursement_status` is `NOT_LIABLE`, never enters the liability set at all.

### 3.5. Daily Workout Groups, Assignments and Field Sessions

A `ComplexDirector` or a `FieldCoordinator` creates a workout group against a `complex_id`, supplying a `roster_bucket` of `MAJOR` or `MINOR`, a `group_name`, a `facility_kind` of `FIELD`, `CLUBHOUSE` or `TRAINING_ROOM`, and a `capacity_units` of at least 1. The group opens in `FORMING` with `assigned_units` at 0, and its `assignment_group_tag` is derived by normalizing the `group_name` to upper snake case — collapsing each run of non-alphanumeric characters to a single underscore, trimming leading and trailing separators, and upper-casing each alphanumeric character — this tag being the key a throwing program uses to locate its player's active group. The group's `group_status` may later move to `PUBLISHED` or to `DISBANDED`.

Publishing a group is a `ComplexDirector` action and a narrower gate than it looks. The group must be `FORMING` (else `ERR_INVALID_STATE`, HTTP 409); `assigned_units` must not exceed `capacity_units`; the owning complex's `field_maintenance_status` must not be `CLOSED`; and no group assignment on the group may belong to a player whose throwing program has `requirement_status` `UNMET` — publishing a group containing an under-worked pitcher is refused with `ERR_THROW_REQUIREMENT_UNMET` (HTTP 422). Publication moves `group_status` to `PUBLISHED`, recomputes the complex's `posted_occupancy_units`, `reserved_major_units` and `reserved_minor_units`, and runs the posture sweep of §2.6 — so publishing the group that takes a complex past ninety-five percent of effective capacity is itself what pushes that complex to `FIELD_RESTRICTED`.

Disbanding is available directly from `FORMING`, and it is also the endpoint of a forced chain. A direct disband moves `group_status` to `DISBANDED` and withdraws every group assignment on the group whose status is `PROVISIONAL` or `ACTIVE`, then recomputes the complex's three occupancy aggregates and the group counts of the member players.

Field session blocks are a `FieldCoordinator`'s to schedule. A block is created against a `workout_group_id` with a `session_date`, a `session_end_datetime` closing the half-open interval, a `session_kind` of `BULLPEN`, `CATCH_PLAY`, `LIVE_BP` or `DEFENSE`, and a `field_units` of at least 1. The block opens with its `session_status` reading `SCHEDULED`. Publishing the block moves `session_status` to `PUBLISHED`, and that publication is what resolves the reconciliation lag described in §3.6: it is the moment at which a pending throwing-program phase advance finally mirrors onto the player's profile.

Assigning a player into a group is shared work: a `FieldCoordinator` or a `PitchingCoordinator` may do it, and the request carries the `workout_group_id`, the `player_id`, the `roster_bucket`, the `assignment_kind`, and the `expected_group_version` described in §2.8. The `assignment_kind` is `ACTIVE_WORKOUT` or `REHAB`. Two rules bind the create: the assignment's `roster_bucket` must equal the owning group's own `roster_bucket` (an assignment whose bucket differs is refused with `ERR_BUCKET_MISMATCH`, HTTP 422), and the create must not push the group's `assigned_units` above its `capacity_units` (a create that would is refused with `ERR_GROUP_CAPACITY_EXCEEDED`, HTTP 409). On success the assignment opens at `PROVISIONAL`, `assigned_at` is captured, and the group's `assigned_units`, the complex's `reserved_major_units` and `reserved_minor_units`, and the player's profile counts and `active_group_assignment_id` are recomputed.

Call-up is the activation step and belongs to the `FieldCoordinator` alone. An assignment may be called up from `PROVISIONAL` only; the owning group must be `PUBLISHED`; the player's `clearance_status` must be `CAMP_CLEARED` (else the call-up is refused with `ERR_MEDICAL_CLEARANCE_REQUIRED`, HTTP 422); the activation must not push the group's `assigned_units` above its `capacity_units`, since the capacity reservation binds activation exactly as it binds creation (a call-up that would is refused with `ERR_GROUP_CAPACITY_EXCEEDED`, HTTP 409); and no other assignment of that player may already be `ACTIVE`, since a player holds at most one — a second active assignment is refused with `ERR_PLAYER_ALREADY_ASSIGNED` (HTTP 409). The call-up also inherits the throwing gate: if a member pitcher's `requirement_status` is `UNMET`, the call-up is refused with `ERR_THROW_REQUIREMENT_UNMET` (HTTP 422). On success the assignment moves to `ACTIVE` and the group's `assigned_units`, the complex's reserved aggregates, and the profile's `active_group_assignment_id` (selected by the group-assignment selector) are recomputed. Any successful create, call-up or withdrawal of an assignment — and likewise the assignment created by the live-advance cascade of §3.6 — advances the owning group's `version` by one and refreshes its `updated_at`, so the optimistic-concurrency anchor of §2.8 tracks every change to the group's seating.

Withdrawal is available to the `FieldCoordinator` and the `PitchingCoordinator` and requires the `withdrawal_reason` the caller supplies. It may be applied from `PROVISIONAL` or from `ACTIVE`. Withdrawing a provisional assignment records the reason onto `withdrawal_reason`, moves the status to `WITHDRAWN`, recomputes the group's `assigned_units`, the complex's reserved aggregates, and the profile's group counts and `active_group_assignment_id`, and — this is the conditional consequence — if the group's `assigned_units` has fallen to zero while the group is still `FORMING`, the group itself is disbanded, its `group_status` moving directly to `DISBANDED`. Withdrawing an active assignment does the same recomputations but writes no withdrawal reason and carries no auto-disband consequence. `WITHDRAWN` is terminal for the assignment.

The selector deserves a note, because it is what the profile's `active_group_assignment_id` reflects. When several assignments of one player are simultaneously eligible to be the active one, the profile is pointed at the group assignment the selector chooses; when a withdrawal removes the assignment it was pointed at, the pointer is recomputed over what remains, and when nothing remains it is cleared. The related profile reads are recomputed in lockstep: `major_group_count` counts the player's assignments whose `roster_bucket` is `MAJOR` and whose `assignment_status` is `PROVISIONAL` or `ACTIVE`; `minor_group_count` is the same count for `MINOR`; `active_rehab_assignment_count` counts the player's assignments whose `assignment_kind` is `REHAB` and whose status is `PROVISIONAL` or `ACTIVE`; and `active_group_session_date` is the newest `session_date` over the session blocks of the group named by `active_group_assignment_id`. The selector itself, and the pointer it maintains, are defined over enrollment: an assignment is eligible only while it is `PROVISIONAL` or `ACTIVE` and its owning workout group is still `PUBLISHED`, so a `DISBANDED` group's assignments no longer compete for the pointer.

### 3.6. Throwing Programs and Phase Discipline

A `PitchingCoordinator` opens a throwing program under a group assignment by supplying the `group_assignment_id`, a `target_catch_play_throws` of at least 1 and a `target_bullpen_sessions` of at least 1. The program opens with its `program_phase` at `PHASE_1`, with `cumulative_throws` at 0, `cumulative_bullpen_sessions` at 0 and `requirement_status` at `NOT_REQUIRED`. Its `player_id` mirrors the owning assignment's player, and its `last_session_date` and `last_game_scheduled_date` are reads that track the newest logged session and the newest scheduled game respectively.

Work is logged as sessions. A session carries the `throw_program_id`, a `logged_at` instant, a `session_kind` of `CATCH_PLAY` or `BULLPEN`, and a `play_catch_throws` count that must be at least 0 and may only be non-zero for a catch-play session. Each session receives a monotone `session_sequence` from the system, and it opens at `LOGGED`. Only logged sessions count: a voided session is excluded from every accumulator. Because two sessions can share a `logged_at` instant, the chronological tie-break is `logged_at` ascending and then `session_sequence` ascending — never the row's `id`.

The accumulators follow from the logged sessions. `cumulative_throws` is the sum of `play_catch_throws` over the program's catch-play sessions, taken in that chronological order, so a later back-dated session still folds in at its chronological place. `cumulative_bullpen_sessions` is simply the count of the program's bullpen sessions.

The requirement score is recomputed on every logged session, on every phase advance, on shutdown and reinstatement, and on every game action that touches a participating pitcher. It begins with a workload reading: `age_factor` is the whole-day span from the program's `created_at` to the current logical clock, capped at seven days, counted start-inclusive and end-exclusive. A day-of-game bump is added on top: it is zero when no game on the owning complex has `gameday_status` `GAMEDAY`; it is also zero when the player's participation in that gameday carries a `throw_count` greater than zero, because the game itself supplies the work; and otherwise it is thirty throws. The `schedule_requirement_throws` is the accumulated throws plus `age_factor` plus that bump.

That score is then judged against a phase-dependent band. The program's programmed maximum is `target_catch_play_throws` multiplied by a per-mille allowance that varies by phase, floor-divided by one hundred: the allowance is 100 per-mille at `PHASE_1`, 105 at `PHASE_2`, 125 at `PHASE_3`, 150 at `PHASE_4`, 175 at `PHASE_LIVE` and 0 at `SHUTDOWN`. A step tolerance is then derived as one tenth of `target_catch_play_throws`, floored to a whole number, multiplied by two. The `requirement_status` is `MET` when `schedule_requirement_throws` is at least the programmed maximum and at most the programmed maximum plus the step tolerance — a band closed at both ends, so a score exactly equal to either bound is `MET` and a score one throw outside either bound is `UNMET`. It is `UNMET` otherwise. It is `NOT_REQUIRED` while the program is at `SHUTDOWN`, regardless of the arithmetic. Because the band moves with the phase, the same accumulated workload can read `UNMET` at `PHASE_4` and `MET` the instant the program reaches `PHASE_LIVE`, with no new session logged.

Phase movement is a `PitchingCoordinator` action carrying a `direction` of `ADVANCE` or `REGRESS`, and every edge has its own precondition and its own consequence.

From `PHASE_1`, an advance requires `cumulative_throws` to have reached `target_catch_play_throws`; it moves the program to `PHASE_2`, recomputes the score, and mirrors `PHASE_2` onto the player's profile `rehab_program_phase`. From `PHASE_2`, an advance requires `cumulative_bullpen_sessions` to have reached `target_bullpen_sessions`; it moves to `PHASE_3`, recomputes the score, and mirrors `PHASE_3` onto the profile. From `PHASE_2`, a regression requires `cumulative_throws` to be below `target_catch_play_throws`; it moves the program back to `PHASE_1` and mirrors `PHASE_1` onto the profile. From `PHASE_3`, an advance requires the `requirement_status` to be `NOT_REQUIRED` or `MET`; it moves to `PHASE_4` and recomputes the score — but it deliberately does *not* mirror onto the profile, which is the reconciliation lag: the profile's `rehab_program_phase` stays at `PHASE_3` until a session block is published for the player's active group, at which point the pending advance lands. From `PHASE_3`, a regression requires the `requirement_status` to be exactly `UNMET`; it moves back to `PHASE_2` and recomputes the score, and it likewise does not mirror.

From `PHASE_4`, an advance requires the `requirement_status` to be anything other than `UNMET` and the player's `clearance_status` to be `CAMP_CLEARED` (else `ERR_MEDICAL_CLEARANCE_REQUIRED`, HTTP 422). It moves the program to `PHASE_LIVE`; recomputes the score against the wider live band; and, when the post-advance score reads `MET`, causes the group-assignment selector to pick the player's workout group and create a fresh group assignment with status `PROVISIONAL` and a `roster_bucket` equal to that group's own bucket. The new row is seated in the group the player's current assignment already names — the player's own workout group — and it is created only while that group is still `PUBLISHED` and has spare capacity; when the group is not `PUBLISHED`, or is already at capacity, no new assignment is created. The complex's `reserved_major_units` and `reserved_minor_units` are then recomputed from the new assignment, and the profile's `major_group_count`, `minor_group_count` and `active_group_assignment_id` follow. This is the only path in the specification that creates an assignment without an explicit create request.

Shutdown is available only from `PHASE_LIVE`. It moves the program to `SHUTDOWN`, sets `requirement_status` to `NOT_REQUIRED`, mirrors `SHUTDOWN` onto the profile, and withdraws every group assignment of that player still in `PROVISIONAL`; the complex's reserved aggregates and the profile's group counts are then recomputed. Reinstatement returns the program from `SHUTDOWN` to `PHASE_1`, but only while no game on the owning complex is currently `GAMEDAY` — a pitcher may not begin a program afresh on a gameday. On reinstatement both accumulators reset to zero, the score is recomputed, and `PHASE_1` is mirrored onto the profile.

### 3.7. Sponsorships, Recognition and the Community Ledger

A `CommunityLiaison` records a sponsorship against a host community record by supplying the `host_community_record_id`, a `sponsor_name`, a `sponsor_tier` of `LOCAL`, `REGIONAL` or `NATIONAL`, and a `committed_amount_cents` that must be at least zero. The sponsorship opens in `UNSETTLED` with `received_amount_cents` at 0 and `fulfillment_completed` false. Contributions and withdrawals against the commitment are posted through the `amount_cents` and `direction` inputs, where `direction` accepts either spelling of the contributing direction (`CONTRIBUTE` or `CONTRIBUTION`) and either spelling of the withdrawing direction (`WITHDRAW` or `WITHDRAWAL`), and `received_amount_cents` tracks contributions less withdrawals and can never fall below zero. Each posting recomputes the record's `sponsorship_recorded_cents`, `sponsorship_revenue_cents`, `community_ledger_cents` and `ledger_gap_cents`.

Settling a sponsorship requires it to be `UNSETTLED` and requires `received_amount_cents` to have reached `committed_amount_cents`; settling an under-funded commitment is refused with `ERR_SPONSORSHIP_NOT_FULLY_FUNDED` (HTTP 422). On success the sponsorship moves to `SETTLED` and `fulfillment_completed` becomes true, and the record's `sponsorship_recorded_cents`, `sponsorship_revenue_cents`, `community_ledger_cents` and `ledger_gap_cents` are recomputed.

Recognition is available only from `SETTLED`. It moves the sponsorship to `RECOGNIZED`, recomputes the record's `recognition_funded_cents` and recomputes `ledger_gap_cents`. The recognition allocation is a weighted score, and it runs over the camp's recognition corpus — every camp entity whose `major_group_count` plus `minor_group_count` is at least one. Entities with both counts at zero, or a negative sum, are excluded from the corpus entirely. When the corpus is empty the recognition amount is zero and the recognition is still recorded against the sponsorship.

For a member of the corpus the weighting proceeds as follows. A weight sum is formed as five times the member's `major_group_count` plus two times its `minor_group_count`. A match-points figure is that weight sum multiplied by a tier multiplier expressed in per-mille — 100 for a `LOCAL` sponsor, 130 for `REGIONAL` and 165 for `NATIONAL` — and floor-divided by ten. A commitment-points figure is the sponsorship's `committed_amount_cents` floor-divided by one hundred, capped at two thousand. A ceiling on the member's contribution is then formed as a base cap of five thousand points reduced by one hundred points for each of the member's `active_rehab_assignment_count`, and that ceiling is floored at zero so it can never go negative. The member's contribution is the smaller of the match-plus-commitment total and that ceiling.

The corpus totals are then summed once across all members: the major equivalents are the sum of every member's `major_group_count`, and the minor equivalents are the sum of every member's `minor_group_count`. The recognition amount is the sum of two products — the sponsorship's `sponsorship_major_league_base_cents` multiplied by the major equivalents multiplied by the affected contribution, and the sponsorship's `sponsorship_minor_league_base_cents` multiplied by the minor equivalents multiplied by the same contribution — floor-divided once by one thousand. When the corpus holds exactly one member, the contribution used is that member's own. When the corpus holds several members, the recognition is computed member by member and summed. The resulting amount is added to the record's `recognition_funded_cents`, and after the addition `recognition_funded_cents` less `community_ledger_cents` has moved by exactly that amount.

Voiding reverses the settlement and everything built on it. It is refused while the owning complex's `facility_posture` is not `NORMAL`, with `ERR_POSTURE_BLOCKS_FISCAL` (HTTP 409). From `SETTLED` and from `RECOGNIZED` alike, the sponsorship moves to `SETTLEMENT_VOIDED` and `fulfillment_completed` returns to false. From `SETTLED` the record's `sponsorship_recorded_cents`, `sponsorship_revenue_cents`, `community_ledger_cents` and `ledger_gap_cents` are recomputed and `recognition_funded_cents` is recomputed through the recognition allocation. From `RECOGNIZED` the same recomputations run, with `recognition_funded_cents` recomputed so as to exclude this sponsorship's post. In both branches the agreement's status is then recomputed back to `DRAFT` when no host community record on it has `ticketing_status` `ON_SALE`. The two branches are compensating pairs with the settlement chain: because the void recomputes the recognition amount from the corpus state at void time, a recognise followed by a void leaves `recognition_funded_cents` exactly at its pre-recognition value for identical corpus inputs.

Ticketing runs alongside. A `CommunityLiaison` opens ticketing on a record only when the owning agreement is `ACTIVE` — otherwise `ERR_AGREEMENT_NOT_ACTIVE` (HTTP 409) — and only when the logical clock has reached the agreement's `lease_start_date` and is still strictly before its `lease_end_date`; a clock outside that half-open lease window is refused with `ERR_OUTSIDE_WINDOW` (HTTP 422). Opening moves `ticketing_status` to `ON_SALE`. Selling a ticket block supplies a `quantity` and increments `tickets_sold` by it and `ticketing_revenue_cents` by the quantity multiplied by the agreement's `ticket_price_cents`, recomputing `community_ledger_cents` and `ledger_gap_cents`; if the resulting `tickets_sold` has reached the agreement's `ticket_sellout_capacity`, `ticketing_status` moves to `SOLD_OUT`. Closing ticketing is the compensating action for opening it, but it is only available while `tickets_sold` is still exactly zero. Any record still `ON_SALE` or `SOLD_OUT` when its agreement is terminated is driven to `SUSPENDED`, which is terminal.

### 3.8. Exhibition Games and Gameday Packaging

A `ComplexDirector` schedules an exhibition game against a `complex_id`, supplying the `opponent_name`, a `home_away` of `HOME` or `AWAY`, the `game_datetime` first pitch, a `travel_radius_miles`, a `duration_units` and a `split_squad` flag that defaults to false. The game opens with its `game_schedule_status` at `DRAFT` and its `gameday_status` at `NOT_GAMEDAY`, and its `game_interval_start` and `game_interval_end` are derived from first pitch and the duration units as described in §2.5.

Publication is the central gate for a game, and all three of its conditions must hold. First, an away game may be published only if its `travel_radius_miles` is at most 250; a home game carries no radius restriction. A distance of exactly 250 is inside the limit and 250.01 is outside it, and a violation is refused with `ERR_TRAVEL_RADIUS_EXCEEDED` (HTTP 422) — note that this same limit is checked when the game is created, so an away game beyond the radius cannot even be recorded. Second, the owning complex's `facility_posture` must not be `CLOSED`, since a closed complex cannot host or dispatch a game. Third, no session block on the owning complex may collide with the candidate game interval at minute granularity: the two half-open intervals must be disjoint after truncation to whole minutes, so a session ending exactly at the game interval's start still conflicts, and the rejection is `ERR_TEMPORAL_OVERLAP` (HTTP 409). The game's `game_schedule_status` must currently be `DRAFT`, else `ERR_INVALID_STATE` (HTTP 409).

On publication the game moves to `PUBLISHED`, and — this is the gameday box — if the logical clock sits within the closed interval from one day before `game_datetime` to one day after it, `gameday_status` moves to `GAMEDAY`. Either endpoint counts as inside. Publication also recomputes the throwing requirement score for every throwing program belonging to a player participating in the game, which is how a gameday bumps the day-of-game workload of the staff.

The game may be sent back to `DRAFT`, but only while no participation on it is `LOCKED`. It may be marked played, which requires the logical clock to have reached `game_datetime` and moves the status to `PLAYED` with `gameday_status` back to `NOT_GAMEDAY` and the participating pitchers' requirement scores recomputed. It may be cancelled from either `DRAFT` or `PUBLISHED`; cancelling a published game additionally drives every participation on it whose status is `SCHEDULED` or `CONFIRMED` to `WITHDRAWN` and recomputes the requirement scores of those players. `CANCELLED` is terminal, and a game closed out by the field-maintenance cascade of §3.9 enters `CANCELLED` through a different door with no separate unwind.

Participations are a `FieldCoordinator`'s to manage. A participation is added against a `game_schedule_id` with a `player_id`, a `squad_side` of `HOME_SQUAD` or `AWAY_SQUAD` and a `throw_count` that must be at least zero; a non-pitcher participation must carry `throw_count` at exactly zero, and a negative count is structurally invalid. The participation opens with its `participation_status` at `SCHEDULED`.

Confirming a participation is the most heavily gated action in the game workflow. It carries the `expected_game_version` of §2.8; the owning game's `game_schedule_status` must be `PUBLISHED`; the player's `clearance_status` must be `CAMP_CLEARED` (else `ERR_MEDICAL_CLEARANCE_REQUIRED`, HTTP 422); and the player's throwing program `requirement_status` must not be `UNMET` — a pitcher whose programmed work is unmet is not available for the day, and the refusal is `ERR_THROW_REQUIREMENT_UNMET` (HTTP 422). Split-squad eligibility then applies: the player must either hold `HOME_AND_TRAVEL` split-squad eligibility or be on the home squad. A player's split-squad eligibility is `HOME_AND_TRAVEL` when the player has a confirmed travel arrangement whose `travel_radius_miles` is at most 250, and `HOME_ONLY` otherwise — the limit is inclusive at exactly 250. Only confirmed arrangements are consulted; planned and cancelled rows are ignored, and when several confirmed rows exist the most recent by `created_at` ascending is the one read.

The away-game gate is separate and stricter. An away participation is permitted when the player's split-squad eligibility is `HOME_AND_TRAVEL`, or when the game's own `travel_radius_miles` is at most 250. Additionally, if the player's throwing program phase inbound to the confirm is beyond `PHASE_2`, the player must be `CAMP_CLEARED`, and on an away game an injury-travel clearance flag must be false; a strict-precursor phase — `PHASE_1`, `PHASE_2` or `PHASE_3` — on an away participation without that clearance is refused with `ERR_INJURY_TRAVEL_UNSAFE` (HTTP 422). On success the participation moves to `CONFIRMED` and the player's requirement score is recomputed, since the game's day-of-game bump depends on this participation's `throw_count`.

Withdrawal is available from `SCHEDULED` and from `CONFIRMED` and moves the participation to `WITHDRAWN`; withdrawing a confirmed participation additionally recomputes that player's requirement score. Packaging is the final gameday act, and it is time-boxed: a `ComplexDirector` packages the roster only while the logical clock sits within the closed window from six hours before `game_datetime` to `game_datetime` itself, and only for a `PUBLISHED` game. A packaging attempt outside that window is refused with `ERR_OUTSIDE_WINDOW` (HTTP 422). Packaging drives every confirmed participation on the game to `LOCKED` and reports the count locked alongside the game's `gameday_status`. `LOCKED` is terminal, and its presence on any participation is what blocks the game from being reverted to draft.

### 3.9. Facility Maintenance and Its Cascades

Field maintenance is the `ComplexDirector`'s exclusive act and the most consequential single operation in the specification. It carries a `maintenance_action` of `OPEN`, `FIELD_RESTRICTED` or `CLOSED` and moves both `field_maintenance_status` and the derived posture.

The restricted branch requires the complex to be in `NORMAL` with `field_maintenance_status` at `OPEN`, and requires `posted_occupancy_units` to be at most eighty-five percent of `facility_capacity_units`, that eighty-five percent figure being floored to a whole unit. On a complex whose `season_split_track` is `SHARED` — the co-tenured camps — the comparison is made against the raw `facility_capacity_units` while the posture sweep compares against the effective capacity after the maintenance block, so a shared complex can be reported `FIELD_RESTRICTED` at a posting that would leave a dedicated complex `NORMAL`. When the branch's conditions hold, the action sets `field_maintenance_status` to `HALF_FIELD`, sets `maintenance_block_units` to half of `facility_capacity_units` rounded up, and runs the posture sweep. A request whose state does not match, or whose occupancy is already above eighty-five percent of the applicable capacity, is refused with `ERR_INVALID_STATE` (HTTP 409).

The reopen branch requires `field_maintenance_status` to be `HALF_FIELD`. It returns `maintenance_block_units` to zero, sets `field_maintenance_status` to `OPEN`, runs the posture sweep, and recomputes `reserved_major_units` and `reserved_minor_units`. This is the only path by which a complex can leave `FIELD_RESTRICTED`.

The close branch is available from `NORMAL` and from `FIELD_RESTRICTED`, and both variants require that no group assignment on the complex is still `PROVISIONAL`. A provisional assignment left occupying a seat that the closure withdraws is refused with `ERR_MAINTENANCE_CONFLICT` (HTTP 409). When the gate passes, the closure sets `maintenance_block_units` to the full `facility_capacity_units`, sets `field_maintenance_status` to `CLOSED`, and forces `facility_posture` to `CLOSED` directly.

The closure then cascades four hops deep, identically from either source state. The first hop withdraws every group assignment on the complex whose status is `PROVISIONAL`, driving each to `WITHDRAWN` with `withdrawal_reason` recording that the complex field was closed. The second hop disbands every workout group that has lost its last provisional-or-active assignment — that is, every group still `FORMING` or `PUBLISHED` that now holds no `PROVISIONAL` or `ACTIVE` assignment — driving it from `FORMING` to `DISBANDED` or from `PUBLISHED` to `DISBANDED`. The third hop reaches the people: for every member player of a disbanded group, that player's `rehab_program_phase` is reset to `PHASE_1` from whichever of `PHASE_2` or `PHASE_1` it held, and the profile's `active_group_assignment_id` is cleared. The fourth hop recomputes the profile's `major_group_count` and `minor_group_count`, and then the complex's `posted_occupancy_units`, `reserved_major_units` and `reserved_minor_units`.

Two further sweeps ride along with the closure. Every session block belonging to a disbanded group is driven to `CANCELLED`, and every away game on the complex that is still `DRAFT` is driven to `CANCELLED`. Note what is not swept: a home game in draft, and any published game, survive the closure untouched.

### 3.10. Roster Decisions, Options and Waivers

The roster record is the spine of the camp. A `RosterManager` opens one against a `player_id`, and it starts with `current_roster_status` at `NRI`, `roster_decision_status` at `DECISION_PENDING`, `option_decisions_used` at 0, `decision_sequence` at 0 and `split_squad_eligibility` at `HOME_ONLY`. Two dimensions live on this row and move independently: `current_roster_status`, which tracks where the player stands, and `roster_decision_status`, which tracks whether the decision has been settled. A third derived read, `option_eligibility`, is `OPTION_AVAILABLE` or `NO_OPTION_REMAINING`; and `waivers_required` states whether the player must clear waivers before assignment.

Promotion to the active roster is available only from `NRI`, only while the decision status is `DECISION_PENDING`, only when the player's `clearance_status` is `CAMP_CLEARED` (else `ERR_MEDICAL_CLEARANCE_REQUIRED`, HTTP 422) and only when the profile's `eligibility_status` is `CAMP_ELIGIBLE`. On success `current_roster_status` moves to `ACTIVE_ROSTER` and `last_decision_actor_id` records the acting operator.

Applying a roster decision is a `RosterManager` action carrying a `decision_type`. From a pending record, an `OPTION_ASSIGN` decision requires `option_eligibility` to be `OPTION_AVAILABLE` and moves the player to `OPTIONED_MINORS`, applying one charge to the option allowance by incrementing the record's `option_decisions_used` by one; the option reads are then recomputed over the increased charge. Also from a pending record, a `NONROSTER_RELEASE` decision has no additional precondition and moves the player to `NRI_RELEASED`. An `OUTRIGHT_ASSIGN` decision is available only from `OPTIONED_MINORS` and requires `option_eligibility` to be exactly `NO_OPTION_REMAINING`, moving the player to `DESIGNATED_FOR_ASSIGNMENT`. Every decision increments `decision_sequence` by one and refreshes the derived reads below; a decision attempted from a state that is not a valid source is refused with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409). Attempting any decision against a record whose current roster status is terminal is refused up front with `ERR_ROSTER_ALREADY_FINAL` (HTTP 409), unless the record's decision status is already `DECISION_VOIDED` rather than `DECISION_PENDING`.

The option accounting is a threshold on accumulated charges. A charge base is formed as an offset of zero plus the player's `minor_league_option_years_used`. A decision burden is the record's `option_decisions_used`, capped at two. The charges are the base plus the burden. The eligibility read is `OPTION_AVAILABLE` when charges are below three and `NO_OPTION_REMAINING` otherwise, so the boundary sits exactly at three: charges of 2 are available and charges of 3 are exhausted. The `waivers_required` read is true exactly when the eligibility read is `NO_OPTION_REMAINING`. These reads are taken over the counters as they stand after the triggering transition has applied its own update. Which of the two computation variants produced the read is recorded on the record as `option_credit_source`: it is `BASE_ALLOWANCE` while the charges are used as written above, and `VOIDED_OPTION_RESTORES_CHARGE` once a void has supplied the one-charge relief described below.

Waivers carry a second, independent trigger that does not depend on options at all. `waivers_required` is also set true once a credit total reaches five, where the credit total accrues three credits for each minor-bucket trigger row and five credits for each major-bucket trigger row — so a single major row reaches the threshold and two minor rows do as well. This refreshed `waivers_required` is recomputed on every finalize-decision and void-decision as well as on the option path, and the two triggers are additive rather than alternative.

A voided decision can be re-issued. An `OPTION_ASSIGN` decision issued against a record whose decision status is `DECISION_VOIDED` is permitted while `option_decisions_used` is at most three; it moves `current_roster_status` back to `OPTIONED_MINORS`, returns the decision status to `DECISION_PENDING`, and increments `decision_sequence`. This is the revision loop — a voided option decision may be re-issued, and the record accepts the re-issue only while `option_decisions_used` has not risen above three; a record whose counter stands at four or more refuses the re-issue with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409).

Waivers run through two steps. Placing a player on waivers is available only from `DESIGNATED_FOR_ASSIGNMENT` and only when `waivers_required` is true; it moves the player to `WAIVER_PENDING` and records the effective claim window described below. Recording an outcome carries an `outcome` value. An outcome of `CLAIMED` is available while the player is `WAIVER_PENDING` or already `WAIVER_CLAIMED` and while `waivers_required` is true, and moves the player to `WAIVER_CLAIMED`. An outcome of `PENDING` is available only from `WAIVER_CLAIMED` and returns the player to `WAIVER_PENDING`, which is the un-record edge before finalization. An outcome of `RETURNED` is available only from `WAIVER_PENDING` and sends the player back to `DESIGNATED_FOR_ASSIGNMENT`, because returned waivers leave the player awaiting an outright assignment again. An outcome of `CLEARED` is available only from `WAIVER_PENDING` and only while `waivers_required` is true, and moves the player to `RELEASED`. The `CLAIMED` and `CLEARED` edges sit behind the decision-status gate: a record whose decision status is `DECISION_PENDING`, as it is throughout the waiver route, satisfies it, whereas a record whose decision status is `DECISION_VOIDED` does not — recording either of those outcomes against a voided record is refused with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409). Each outcome recording increments the record's `version`, and an outcome attempted from a state that is not its declared source is refused with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409).

A released player can be pulled back. Rescinding a release is available when the decision status is `DECISION_PENDING` or `DECISION_VOIDED`, when `current_roster_status` is `RELEASED`, and only while `waivers_required` is true. It moves the player back to `DESIGNATED_FOR_ASSIGNMENT`, returns the decision status to `DECISION_PENDING`, and increments `decision_sequence`.

The claim window is computed when a player is placed on waivers and consumed when the decision is finalized. Placing the player on waivers records the resulting day count on the record as `waiver_claim_window_days`, and stamps the current logical clock into `waiver_claim_requested_at` so that the window's opening instant is preserved. When no claim is engaged, `waiver_claim_requested_at` is empty. The window begins with a rule span of fifteen days for a player whose `minor_league_option_years_used` is at least four, and eight days for anyone else. A bump is then added, equal to the sum of `agreement_funded_cents` over the player's travel liability rows divided by thirty thousand cents and rounded up to a whole day; the liability rows are the player's travel arrangements whose `reimbursement_status` is `LIABLE` or `VOIDED`, ordered by `created_at` ascending and then `departure_at` ascending, never by `id`. The rule span plus the bump is capped at twenty-one days. From that capped figure the prior claim count is subtracted — the number of the player's already-finalized records whose `current_roster_status` was `WAIVER_CLAIMED` at finalize time. The result is floored at zero, and that floored value is the effective claim days. When `waivers_required` is false the whole computation is moot: the outcome is `NOT_REQUIRED` and the effective claim days are zero. The window opens either `NEWLY_ENGAGED` or `AGED`: it is `NEWLY_ENGAGED` when `waiver_claim_requested_at` still equals the logical clock at finalize time, and `AGED` otherwise. A claim that finalizes inside the window lands the record at `WAIVER_CLAIMED`; a claim attempted once the effective claim days have elapsed would have read `EXPIRED` and is refused at finalize with `ERR_WAIVER_WINDOW_EXPIRED` (HTTP 409), which is the guard that the effective claim days must be strictly positive at finalize time. The record's `waiver_claim_window_days` is always a plain day count; the `NOT_REQUIRED` and `EXPIRED` window states are never written onto the row, so a record whose window has expired keeps its computed day count and is turned away only by the finalize-time guard.

Finalizing is a `RosterManager` action and it is where the two dimensions meet. It requires the decision status to be `DECISION_PENDING`; it requires the current roster status to be one of `OPTIONED_MINORS`, `NRI_RELEASED`, `RELEASED`, `WAIVER_PENDING` or `WAIVER_CLAIMED`; and it requires the finalizing operator's `X-User-ID` to differ from `last_decision_actor_id`, which is the segregation-of-duties gate — the person who applied the decision may not also be the person who finalizes it, and the refusal is `ERR_SOD_VIOLATION` (HTTP 403). A finalization requested from any other decision status or from any other roster status is refused with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409). On success the decision status moves to `DECISION_FINALIZED`, `decision_finalized_at` captures the current logical clock, `decision_sequence` increments, and the option eligibility is recomputed through the base allowance variant. If the record was `WAIVER_CLAIMED` at the moment of finalization, `option_decisions_used` increments by one before that recomputation, so a finalized claim consumes an option credit. The `waivers_required` read is then refreshed from the recomputed eligibility.

Voiding unwinds a finalized decision, and it is time-boxed. It requires the decision status to be `DECISION_FINALIZED`; it requires the current roster status to be `OPTIONED_MINORS` or `NRI_RELEASED`, and a request against either a decision status or a roster status outside that set is refused with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409); and it requires the logical clock to be strictly before the owning player's invitation `report_current_date` — a clock at exactly the report date is too late, and the refusal is `ERR_OUTSIDE_WINDOW` (HTTP 422). On success the decision status moves to `DECISION_VOIDED`, the current roster status returns to `NRI`, `option_decisions_used` is decremented by one but never below zero, `decision_sequence` increments, and the option eligibility is recomputed through the voided-option-restores-charge variant, which uses one charge fewer than the base calculation. `waivers_required` is then refreshed from that recomputation. The one-charge relief is exactly what lets a void immediately after a finalize flip `NO_OPTION_REMAINING` back to `OPTION_AVAILABLE` and clear `waivers_required`.

### 3.11. Camp Break-Out, Minor League Assignments and Spring Trails

Breaking out of camp is a `MinorLeagueCoordinator` action carrying a `level` of `AAA` or `AA`, and it is what settles a rostered player into the minor league season. It requires the record's decision status to be `DECISION_FINALIZED` and its current roster status to be a valid source for the requested level. Breaking to `AAA` is available only from `NRI` and `OPTIONED_MINORS`; breaking to `AA` is available only from `DESIGNATED_FOR_ASSIGNMENT` and `ASSIGNED_AAA`, which is the demotion edge between the two levels. A break-out attempted from a state that is not a valid source — including a terminal state that has no declared edge out of it — is refused with `ERR_ROSTER_STATUS_INVALID_TRANSITION` (HTTP 409), and only a source that is itself terminal-and-reachable reports `ERR_ROSTER_ALREADY_FINAL` (HTTP 409); the transition-legality check is examined before the terminal-status guard, so a terminal state with no declared edge reports the transition error first.

On success the current roster status moves to `ASSIGNED_AAA` or `ASSIGNED_AA`. Except on the `ASSIGNED_AAA`-to-`ASSIGNED_AA` demotion edge, every group assignment of that player whose status is `PROVISIONAL` or `ACTIVE` is driven to `WITHDRAWN`; the complex's `posted_occupancy_units`, `reserved_major_units` and `reserved_minor_units` are recomputed; and for the `AAA` branches the profile's `major_group_count`, `minor_group_count` and `active_group_assignment_id` are recomputed as well. Note the asymmetry: the demotion edge carries no withdrawal and no recomputation, because the player was already out of camp.

The terminal roster statuses are `RELEASED`, `NRI_RELEASED`, `ASSIGNED_AAA` and `ASSIGNED_AA`. Once a record reaches one of them it can no longer accept a further decision or break-out, and the attempt is refused with `ERR_ROSTER_ALREADY_FINAL` (HTTP 409).

The post-break-out assignment record is opened by the `MinorLeagueCoordinator` against a `player_id` with a `roster_record_id`, an `assigned_level` of `AAA` or `AA`, an `affiliate_name` and an `effective_datetime`. It opens at `PENDING`, and two reads are evaluated. The `travel_day_count` is the whole-day span from `effective_datetime` to the owning complex agreement's `lease_end_date`, counted start-inclusive and end-exclusive, and read as zero when the lease end is at or before the effective instant. The `break_out_liability_cents` is the sum of the agreement-funded amounts over the player's travel liability rows at break-out time, and it is fixed once written. This record may not be opened more than a fixed bailout span before its `effective_datetime` — the span is ninety days — and its `effective_datetime` must fall at or before the owning agreement's `lease_end_date`; either violation is refused with `ERR_OUTSIDE_WINDOW` (HTTP 422). Both of these bounds are evaluated only when the player's owning complex resolves to an agreement under the funding selector; with no such agreement the record opens without either bound being examined.

Settling the assignment is the `MinorLeagueCoordinator`'s act and it captures the acting operator into `settlement_actor_id`, moving the assignment to `SETTLED`. Voiding a settled break-out is the compensating action, and it carries the segregation-of-duties gate: the operator voiding must not be the operator recorded in `settlement_actor_id`, else the void is refused with `ERR_SOD_VIOLATION` (HTTP 403). On success the assignment moves to `BREAKOUT_VOIDED`, the liability figure is re-evaluated over the same inputs but written as zero, so a create-and-void pair leaves the player's outstanding agreement-funded travel at zero rather than drifting negative, and the settlement actor is cleared.

Spring trails run alongside and deliberately remove a player from this machinery. A `MinorLeagueCoordinator` maps a player onto the trail at a `trail_level` of `AAA`, `AA`, `A_PLUS` or `A`; the row opens `ACTIVE` with `mapped_at` set to the current logical clock. While that row is `ACTIVE` the farm-scoped operations of §2.10 are refused for that player with `ERR_FARM_ENTITY_EXCLUDED` (HTTP 409). Ending the trail moves `trail_status` to `ENDED` and returns the player to the camp machinery's reach.

### 3.12. Operations Checkpoints

Two periodic checkpoints are run by a `PlatformAdmin` or a `ComplexDirector`, each identified by a `run_type`. The `invitation-report-sweep` checkpoints the invitation population, driving every stale invitation — one whose report window has closed with no arrival recorded — from `ISSUED` to `NO_SHOW` and running the full unwind described in §3.3. The `registration-roster-sweep` checkpoints the roster population, recomputing every roster record's `option_eligibility` and `waivers_required` from its current counters. Either checkpoint also increments `posture_sweep_index` on every complex by one.

## 4. Endpoint Definitions

Operations that create a new, stand-alone resource return `201 Created`. Operations that create a resource nested within a collection, and operations that modify an existing resource or drive a state transition, return `200 OK`. Read operations return `200 OK` with the requested resource or a paginated array. Requests that are refused follow the error envelope of §2.2 and never carry a 2xx status.
