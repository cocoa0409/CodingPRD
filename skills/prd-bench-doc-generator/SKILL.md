# PRD Benchmark Document Generator

## Input / Output

### Input

1. **Scaffold YAML path**: A complete seed-table YAML file generated by `prd-bench-scaffold-generator`, containing these top-level keys:

   ```yaml
   scenario          # Natural-language description of the system
   domain_name       # kebab-case identifier (e.g., hospital-shifts)
   api_prefix        # Top-level URL path (e.g., /treatment-plans)
   complexity_profile # Archetype, layers, structural dimensions

   entities          # Table 1: Entity-Relationship Table
   state_machines    # Table 2: State Machine Table
   calculations      # Table 3: Calculation Rules Table
   validations       # Table 4: Validation Rules Table (priority-ordered)
   response_envelope # API envelope definition (success/error/pagination)
   endpoints         # Table 5: API Endpoint Table
   errors            # Table 6: Error Code Catalog
   roles             # Table 7: RBAC Matrix
   ```

2. **Output folder path**: Directory where the PRD file will be written.

### Output

A single `prd.md` file in the output folder — a prose-style Product Requirements Document written in English.

## Core Principle: Precise Contracts vs. Scattered Logic

Information in the PRD falls into two categories with opposing writing strategies:

### Contract-Level Specifications (must be precise and unambiguous)

These define the API's **structural contract** — what responses look like, field names and types, pagination mechanics. If these are vague, any reasonable implementation could diverge from the fixed test suite, and the benchmark breaks.

Must be precisely defined:
- **Response envelope format**: Complete JSON examples (success + error) with every `meta` field's name, type, and semantics — derived from `response_envelope` in the scaffold
- **Pagination mechanism**: Parameter names, defaults, min/max — derived from `response_envelope.pagination_defaults`
- **Common resource properties**: `id` (UUID), `created_at` (ISO 8601 UTC), `updated_at`, `version` (integer, increments on mutation) — derived from entities with `common_fields: true`
- **Auth headers**: Exact names `X-User-ID` and `X-User-Role`
- **Status code rules**: 201 for new resource creation, 200 for modifications
- **Precision rules**: Decimal places and rounding method — derived from `calculations[].precision`
- **OCC mechanism**: `version` field behavior (omit to skip check, mismatch yields `ERR_STALE_DATA`)
- **Sort order**: List endpoints default to `created_at` ascending
- **Role enumeration**: Exact spelling of all role names — from `roles[].name`
- **State enumeration values**: Exact strings for every state — from `state_machines[].initial_state`, `terminal_states`, and all `transitions[].from`/`to`
- **Certification / category enumeration values**: All enum-type field values — from `entities[].fields` where `type: enum`
- **Error ID format**: All `error_id` strings and their HTTP status — from `errors[]`

### Business Logic (deliberately scattered to increase inference difficulty)

These are the benchmark's discriminating factor — LLMs must piece together complete implementations from scattered narrative.

Should be scattered:
- Which fields each endpoint accepts (spread across multiple §3 subsections)
- Calculation algorithms (narrative, not pseudocode) — derived from `calculations[].formula` and `calculations[].algorithm`
- Numeric thresholds and constants (embedded in business statements) — from `calculations[].constants`
- Entity relationships (implied through actions, not declared as foreign keys)
- Validation trigger conditions (error table has no condition column) — from `validations[].check`
- State transition preconditions and side effects (narrative, not state diagrams) — from `state_machines[].transitions`

## Diversity Principle: Do Not Copy the Example's Structure

The example demonstrates **one** valid transformation. Each new PRD must have its document skeleton designed from scratch based on the current domain. Specific requirements:

1. **§2 subsections must be domain-derived**: The number of subsections (typically 8–12), their titles, and ordering must be derived from the scaffold's actual domain semantics. Do not copy the example's subsection numbers and titles (e.g., don't always name them "System Integrity and Consistency" or "The Principle of Fiscal Responsibility"). Use domain-specific terminology for subsection titles.
2. **§2.2 JSON placeholders must be domain-specific**: Placeholder timestamps, IDs, and example values in JSON blocks should reflect the current domain (e.g., e-commerce uses order-related sample values, logistics uses shipment-related ones). Do not reuse the same `req_RANDOMALPHANUM123456` and `2025-05-24T10:30:00.123Z` every time.
3. **§3 subsections must be freely grouped**: Do not mechanically replicate the example's subsection pattern (lifecycle → structure → core op → pairing → safety → cost → finalization). Group by the current domain's natural business flows; 5–9 subsections are all acceptable.
4. **Sentence variety**: Avoid starting every paragraph with "The system...". Alternate among role names, business events, conditional clauses, scenario-driven narration, passive voice, and temporal markers.
5. **Introduction flexibility**: Can be 1–3 paragraphs, approaching from system goals, user pain points, business context, technical constraints, etc. Length adapts to domain complexity.

## PRD Structure Template

```markdown
# {domain_name as Title Case} API — Product Requirements Document

## 1. Introduction
## 2. Global Specifications & System-Wide Principles
  ### 2.1. User and Role-Based Access Control
  ### 2.2. API Response Structure
  ### 2.3. Pagination
  ### 2.4–2.N. [One subsection per cross-cutting concern]
## 3. Business Logic & Workflows
  ### 3.1–3.N. [One subsection per business process / lifecycle]
## 4. Endpoint Definitions
## 5. Error Code Catalogue
```

## Section Generation Rules

### §1. Introduction

Rewrite the scaffold's `scenario` field into 1–3 paragraphs of formal English. Product-manager perspective. May approach from multiple angles — system goals, user pain points, business context, technical constraints — with length adapting to domain complexity. Do not always default to a single 3–4 sentence paragraph.

### §2. Global Specifications (Precise Zone)

Most content in this section is **contract-level specification** and must be precise and unambiguous.

#### §2.1 User and Role-Based Access Control

- Explicitly state the header names: `X-User-ID` and `X-User-Role`
- List all role names with exact spelling — from `roles[].name`
- Reference the auth-related error IDs from `errors[]` (e.g., the ones for missing headers and insufficient permissions)

#### §2.2 API Response Structure (the most critical contract subsection)

**Must provide complete JSON examples**, derived from `response_envelope` in the scaffold:

Success response — use the structure from `response_envelope.success`, expanding it into a full, formatted JSON block with domain-specific placeholder values. Include pagination fields from `response_envelope.pagination_fields`.

Error response — use the structure from `response_envelope.error`, expanding it into a full, formatted JSON block.

**After the JSON examples**, explain each field's semantics:
- `api_request_id`: server-generated unique identifier, format description
- `api_request_timestamp`: ISO 8601 UTC with 3 fractional digits
- `response_type`: `"object"` | `"array"` | `"error"` enumeration
- `data`: business payload (object, array, or empty object)
- Pagination fields (from `response_envelope.pagination_fields`) appear only in list endpoint responses
- Error response `error_id` and `message` fields

#### §2.3 Pagination

- State defaults, min, max for `limit` and `offset` — from `response_envelope.pagination_defaults`
- State sort order (`created_at` ascending)
- State which pagination fields appear in `meta`

#### §2.4+ Domain-Specific Cross-Cutting Principles

Extract cross-cutting concerns from the scaffold's `calculations`, `validations`, `state_machines`, and `complexity_profile`. **Decide the subsection count (typically 5–8) and grouping yourself.** Subsection titles should use **domain-specific terminology** — avoid generic names. Ordering is flexible; arrange by domain logic.

The following topics **must be covered** (but organization is free — merge related topics into one subsection or split complex topics across multiple):

- **Hierarchical consistency**: From `state_machines[].transitions[].side_effects` — cascade/revert patterns, parent-child state propagation, `updated_at` and `version` semantics on mutation
- **Nested resource retrieval**: Left-to-right path parameter validation — derived from the URL hierarchy in `endpoints[].path`
- **Common resource properties**: `id` (UUID), `created_at`/`updated_at` (ISO 8601 UTC with 3 fractional digits), `version` (integer) semantics. Note which entities omit `updated_at` — those with `common_fields: false` in the scaffold
- **Precision and rounding**: From `calculations[].precision` — state "2 decimal places" and "round half up" (or whatever the scaffold specifies)
- **Optimistic Concurrency Control**: `version` is optional in request body, mismatch yields `ERR_STALE_DATA`, omit to skip check — derived from endpoints accepting `version?` input
- **Domain-specific cross-cutting rules**: Ledger principles, safety protocols, resource utilization rules, capacity constraints, etc. — the specific topics depend entirely on the domain's `calculations` and `validations`

### §3. Business Logic & Workflows (Scattering Zone)

This is the **core section** of the PRD where information-scattering rules apply most intensively.

**Subsection division strategy:**

Based on the scaffold's entity hierarchy, state machine complexity, and calculation rule relationships, **decide on 5–9 subsections yourself**. Do not always apply the same organizational pattern. Choose the most natural strategy for the current domain (or mix strategies):

- **By entity lifecycle stages**: Each core entity's creation → operation → termination as one subsection
- **By role perspective**: Each role's typical workflow as one subsection
- **By business process timeline**: Organized chronologically from initiation to settlement
- **By cross-cutting concerns mixed with entities**: Weave safety, financial, compliance concerns into related entity narratives rather than isolating them

Key requirement: Regardless of strategy, information scattering must cross subsection boundaries — parameters for the same endpoint must still be spread across ≥2 subsections.

**Writing requirements within subsections:**
- Embed field names in backticks within narrative sentences — no field lists or schema tables. Every field from `entities[].fields` must appear at least once in §3.
- Describe state transitions through narrative preconditions and side effects — no state diagrams (but state values use exact UPPERCASE strings, e.g., `PENDING_REVIEW`). Source: `state_machines[].transitions`
- Express calculation logic as business narrative, not pseudocode. Source: `calculations[].formula` — rewrite as prose using phrases like "conservatively estimates", "processes in chronological order"
- Embed `calculations[].constants` within business context — use unit conversions to increase inference difficulty (e.g., "100 hours" when the system works in minutes, requiring conversion to 6000)
- Mention `error_id` values naturally in narrative (e.g., "rejected with `ERR_XXX`") but do not explain trigger conditions in a concentrated way. Source: `errors[].id`
- Distribute the same endpoint's input parameters (`endpoints[].request_body`) across different subsections

### §4. Endpoint Definitions

Write 1 paragraph above the table stating the general status code rules (e.g., new resources get 201, modifications get 200).

Generate a summary table from the scaffold's `endpoints[]`. Core principle: **keep the table minimal — do not expose each endpoint's request body, response body, or side effects.** Readers must refer back to §3 narratives to reconstruct the complete request/response. The table has only 4 columns: Method, Path, Description, Authorized Role(s).

### §5. Error Code Catalogue

Generate a summary table from the scaffold's `errors[]`. Core principle: **the table does not include trigger conditions** — trigger conditions are scattered throughout §2 and §3 narratives. The table has only 2 columns: Error ID, HTTP Status Code.

## Information Scattering Rules (Apply Only to §3)

These rules **apply only to §3 Business Logic**. Contract content in §2 is not subject to these rules.

### Rule 1: Field Names Embedded in Narrative

Every field name from the scaffold's `entities[].fields` must appear in backticks at least once in some paragraph of §3. No field lists or schema tables allowed.

### Rule 2: Parameters Distributed Across Subsections

Input parameters for the same endpoint (from `endpoints[].request_body`) must be distributed across ≥2 subsections. Core parameters appear in the workflow subsection; safety/override parameters appear in the safety-rules subsection (or equivalent).

### Rule 3: Algorithms as Narrative

Calculation logic from `calculations[].formula` must be rewritten as business narrative. Use phrases like "conservatively estimates", "processes in chronological order" — no pseudocode or mathematical formulas.

### Rule 4: Constants Embedded in Context

Numeric thresholds from `calculations[].constants` must be embedded in business statements. Leverage unit conversions to increase inference difficulty (e.g., write "100 hours" when the constant is `THRESHOLD: 6000` in minutes).

### Rule 5: Relationships Expressed Through Actions

Do not declare foreign keys. Imply relationships through actions like "payload containing the `procedure_id`". Entity parent-child relationships from `entities[].parent` should be expressed through workflow narrative, not explicit schema declarations.

### Rule 6: Endpoint Table Stays Minimal

Do not expose request body / response body / side effects in the §4 table. Readers must infer from §3.

### Rule 7: Error Table Has No Conditions

Do not expose trigger conditions (from `errors[].condition`) in the §5 table. Trigger conditions are scattered in §2 and §3.

## Writing Style

- **Language**: English
- **Perspective**: Product manager to engineer — domain first, implementation second
- **Sentence starters — vary them**: Avoid starting every paragraph with "The system...". Alternate among:
  - Role names ("A `ChargeNurse` initiates...")
  - Business events ("Upon activation, the...")
  - Conditional clauses ("When the cumulative usage exceeds...", "If the budget is insufficient...")
  - Scenario-driven narration ("Consider a scenario where...")
  - Passive voice ("Assignments are evaluated against...")
  - Temporal markers ("During the finalization phase...", "Before a plan can be...")
- **Paragraph density**: Primarily 3–6 sentences per paragraph, but occasionally use short paragraphs (2 sentences for simple rules) or long paragraphs (7–8 sentences for complex workflows) to break the uniform rhythm
- **Terminology introduction**: First occurrences of terms may use bold, parenthetical explanation, or natural narrative introduction — vary the approach rather than always using the same style
- **Terminology consistency**: Once introduced, maintain consistent terminology throughout
- **Redundant reinforcement**: The same concept may be repeated in different sections from different angles (reinforcement, not contradiction)
- **State values**: Reference states with exact UPPERCASE strings in narrative (`ACTIVE`, `PENDING_REVIEW`)

## Common Homogeneity Problems (Must Avoid)

These are the most frequent "copying the example" problems when generating PRDs. Self-check before every generation:

1. **§2 subsections mirror the example 1:1**: Subsection numbers, titles, and ordering are nearly identical to the example (e.g., 2.4 is always "System Integrity", 2.5 is always "Fiscal Responsibility"). Subsections should be renamed and reordered based on the domain.
2. **§2.2 JSON placeholders are identical**: Every generation uses `req_RANDOMALPHANUM123456`, `2025-05-24T10:30:00.123Z`, `UNIQUE_ERROR_IDENTIFIER_STRING`. Use domain-relevant sample values.
3. **§3 follows a fixed 7-subsection pattern**: Exactly 7 subsections arranged as "lifecycle → structure → core op → pairing/restriction → safety/compliance → cost calculation → finalization". Group naturally based on the domain.
4. **Monotonous paragraph openings**: Multiple consecutive paragraphs starting with "The system...". Alternate among role names, conditional clauses, business events, etc.
5. **Fixed Introduction format**: Always 1 paragraph of 3–4 sentences starting with "This document outlines...". Adapt length and approach angle to the domain.
6. **Templated §2 subsection prose**: Every domain's cross-cutting subsections use the same sentence structures (e.g., "The system enforces strict X. Every Y is associated with a Z."). Vary expression style based on concept complexity.
