# Corps Recruitment, Placement and Certification API — Product Requirements Document

## 1. Introduction

Corps programs recruit high-performing graduates on college campuses, select them on demonstrated leadership and achievement rather than on completed education coursework, and place them as full-time teachers in partner school districts for a two-year service commitment. This API is the operational backbone of that pipeline: it carries an applicant from a campus recruitment record, through a multi-stage selection process, into a synthesized corps member who trains at a pre-service summer institute, earns an alternative teaching certification, and serves in a partner school until the two-year commitment ends or is cut short.

Certification requirements are set state by state, so they cannot be modelled as a single national constant. Each region carries its own term start date and its own set of certification pathways, and every pathway encodes the coursework hours, the supervised practice-teaching hours, and the number of days before term start by which each requirement must be verified. A corps member's eligibility to be employed in a classroom is derived continuously from that state of progress, which means the certification records, the institute records and the placement records must stay reconciled with one another at all times.

On the district side, the program sells a service: partner districts sign term agreements that commit them to hiring a number of corps members, pay a per-member placement fee, owe a penalty for each committed slot left unfilled, and cap their exposure with a fee budget. Placements, early exits, reinstatements and term completions all move those district balances, and the same events move the school-capacity counters that keep a partner school from being over-committed. This document specifies the resources, the lifecycle rules, the derived calculations and the access model that a conforming implementation must provide.

## 2. Global Specifications & System-Wide Principles

This section states the system-wide rules that apply to every resource and every operation described later in this document.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, which identifies the acting operator, and `X-User-Role`, which declares the acting capacity. The platform recognizes exactly seven roles — `PlatformAdmin`, `SelectionManager`, `Applicant`, `PlacementCoordinator`, `InstituteDirector`, `CertificationOfficer`, and `Coach`. A request that omits either header, or that names a role outside that set, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is valid but is not on the authorized list of the target operation is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). The clock-setting capability described in §2.12 is the sole operation exempt from the header check; the role check, by contrast, applies to every operation without exception.

One role is entity-backed. When `X-User-Role` is `Applicant`, `X-User-ID` is the `id` of the acting Applicant: ownership checks on any resource that references an Applicant compare the resource's foreign-key field — an application's `applicant_id` — against `X-User-ID`, which is what allows an applicant to resubmit their own returned application or answer their own offer and nothing else.

The remaining six roles are opaque operator identities not tied to any persisted entity: `PlatformAdmin`, `SelectionManager`, `PlacementCoordinator`, `InstituteDirector`, `CertificationOfficer` and `Coach`. When `X-User-Role` names one of these, `X-User-ID` is an opaque operator identifier. The server records it wherever a rule requires an operator to be remembered — as `reviewed_by_user_id` and `decided_by_user_id` on a selection decision, and as `completed_by_user_id` and `verified_by_user_id` on a certification milestone — but never compares it to any entity's `id`. The one operator identifier that is not taken from a header is a support record's `coach_user_id`, which the caller supplies explicitly in the request body.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, and it carries the current instant of the logical clock of §2.12 rather than wall-clock time.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list operation accepts two query parameters. The `limit` parameter caps how many rows a single response may return; it defaults to 10, and values below 1 or above 100 are rejected as malformed requests. The `offset` parameter states how many leading rows to skip, defaults to 0, and a negative value is likewise rejected as a malformed request. Unless a rule in §3 overrides it, list responses are ordered by `created_at` ascending, so the natural reading order of a collection is the order in which its rows were created. Paginated responses repeat the effective page window in the envelope's `meta` object through `limit`, `offset`, `total_count`, and `has_more`, where `total_count` is the size of the full filtered collection rather than the size of the returned page.

### 2.4. Regional Configuration as the Deadline Anchor

Everything time-sensitive in this product is measured from a region's school term. A `PlatformAdmin` establishes a Region with a short operator-facing `region_code` that is unique across all regions and immutable after creation, a human-readable `name`, a two-letter `state_code` written as exactly two uppercase letters, the `term_start_date` on which that region's cohort begins teaching, a `base_placement_fee_cents` regional default that must be non-negative, and a `max_corps_members` regional quota that must be at least 1.

Three of those fields reach well beyond the Region row itself. The `term_start_date` is the anchor from which every certification milestone deadline is computed, and it is also the instant at which a district agreement that is still `ACTIVE` expires. The `state_code` records the two-letter code of the state authority the region answers to, and a pathway declares its own two-letter issuing-authority code, which is stored as supplied and is never cross-checked against the region's. The `max_corps_members` quota is the ceiling that an offer acceptance is checked against, counting the region's corps members who are in `ACTIVE` or `ON_LEAVE` service. Finally, `base_placement_fee_cents` is the fallback price of a placement: it applies only when the owning district has not set a per-member fee of its own. Creating a Region initializes its `version` to 1.

### 2.5. Common Resource Properties

All ten top-level resources — Region, PartnerDistrict, PartnerSchool, Applicant, Application, CertificationPathway, CorpsMember, Placement, CertificationMilestone and SupportRecord — share a uniform set of system-managed properties. The `id` is a server-minted UUID with no type prefix and is the only address a client needs. The `created_at` is an ISO 8601 UTC timestamp carrying three fractional digits, and the `updated_at` is the same format, refreshed on every modification. Every other ISO 8601 timestamp a resource carries — a region's `term_start_date`, an application's `offer_expires_at` and `returned_at`, a corps member's `service_started_at` and `leave_started_at`, a placement's `term_start_date`, `term_end_date`, `confirmed_at` and `activated_at`, a certification milestone's `due_date` and `completed_at`, and a support record's `session_start` and `session_end` — is rendered in that same three-fractional-digit notation, even when the client supplied the instant in a different form. The `version` is an integer that starts at 1 and increments by exactly 1 on each mutation of the resource.

Two consequences follow, and they matter for the concurrency rules in §2.7. First, a change to a derived field is a mutation like any other: recomputing `readiness_score`, `employment_eligible`, `invoice_amount_cents`, `committed_placement_count`, `occupied_classrooms`, `certification_hours_verified`, `coursework_hours_completed`, `selection_score`, `final_selection_score`, `placement_fee_cents`, `days_remaining`, `deadline_status` or `institute_stipend_cents` refreshes the owning resource's `updated_at` and increments its `version`. Second, a single client action may therefore advance several resources' versions at once, because the cascades described in §2.8 touch every resource whose derived state depends on the one that changed.

### 2.6. Numeric Precision and Rounding Discipline

Monetary amounts are stored and transported as integer cents, never as floating-point dollars. This covers `base_placement_fee_cents`, `placement_fee_per_member_cents`, `unfilled_slot_penalty_cents`, `fee_budget_cents`, `coursework_fee_cents`, `invoice_amount_cents`, `placement_fee_cents` and `institute_stipend_cents`; those fields carry no fractional part and undergo no rounding step once they are integers. The one calculation that passes through dollars is the institute stipend, which converts back to integer cents as its final step.

The derived scores are decimal numbers. The `selection_score` and `final_selection_score` values are rounded half up to exactly 2 decimal places, and the rounding is applied once, after every bonus has been added — never per term. The `readiness_score` is rounded half up to 2 decimal places twice: its weighted subtotal is rounded before the support-credit tier lookup reads it, and the final sum is rounded again after the credit is added, then capped so it can never exceed 100.0. The `days_remaining` value on a certification milestone is an integer count of whole days, obtained by truncating both the milestone's `due_date` and the logical clock to their UTC date components before subtracting, so the time of day never influences the result. Wherever a half-way value must be resolved anywhere in this document, the rule is round half up.
### 2.7. Optimistic Concurrency Control

Exactly two write operations in this API carry a version precondition, and both are creations that hang a new child resource beneath an existing parent. Creating a Placement through `POST /corps/placements` requires a non-optional `expected_corps_member_version` field carrying the client's last observed `version` of the CorpsMember being placed. When that value does not match the CorpsMember's current `version`, the creation is refused with `ERR_STALE_MEMBER_VERSION` (HTTP 412). Creating a PartnerSchool through `POST /corps/partner-schools` requires a non-optional `expected_district_version` field carrying the client's last observed `version` of the owning PartnerDistrict; when it does not match the district's current `version`, the creation is refused with `ERR_STALE_DISTRICT_VERSION` (HTTP 412).

Both rules are stale-observation guards and nothing more. The product deliberately allows a corps member to carry more than one placement record — a re-placement after an early exit, or a change of subject — so a placement request issued later with a current version would itself be accepted; the write is refused only because the caller's observed version is out of date. The same is true of a district, which may legitimately accumulate many partner schools over a term. No other endpoint in this API requires, accepts or honours a version field.

### 2.8. Cascade Discipline and Derived-Counter Integrity

Several resources hold counters and flags that are not free-standing facts but projections of other rows. `committed_placement_count`, `invoice_amount_cents` and `occupied_classrooms` project the placements attached to a district and its schools; `certification_hours_verified`, `coursework_hours_completed` and `readiness_score` project a member's certification milestones; `employment_eligible` projects the member's service status, institute status, verified hours and overdue milestones. A conforming implementation must treat every one of these as live state that is refreshed by the transitions listed in §3, not as a value written once.

The cascades are multi-hop, and each hop is itself a mutation. Accepting an offer synthesizes a CorpsMember and then a full set of certification milestones, and each synthesized milestone in turn recomputes the member's verified hours and readiness, so a single acceptance advances the member's `version` once per milestone it creates. Verifying a milestone recomputes the member's verified hours and readiness, and that recompute in turn re-evaluates the eligibility flag on every confirmed or active placement the member holds. Confirming a placement raises the district's committed count, which drives a recompute of both the district's invoice total and the placement's own fee. Exiting a placement early lowers the district and school counters, which drives the invoice recompute, which in turn re-evaluates the district's fee ceiling and may suspend the agreement outright.

Whenever a cascade recomputes a resource, it refreshes that resource's `updated_at` and increments its `version`, independently of any change to the resource that started the cascade. An implementation that mutates a derived field without advancing the owning resource's version will be observably wrong to any client using the concurrency guards of §2.7, because a stale-looking version will hide a real state change.

### 2.9. Segregation of Duties in Selection and Certification

Two decisions in this product are consequential enough that the program requires a second pair of eyes. The operator who records a selection decision must not be the operator who ran the review: on a decision, `X-User-ID` must differ from the application's `reviewed_by_user_id`. The operator who verifies a certification milestone must not be the operator who marked it complete: on a verification, `X-User-ID` must differ from the milestone's `completed_by_user_id`. Either violation is rejected with `ERR_SOD_VIOLATION` (HTTP 403), regardless of whether the transition is otherwise legal. Note that the rule constrains only the decision and verification steps — a reviewer may legitimately return an application for revision and later re-review it, and an officer may start and complete a milestone without ever verifying it.
### 2.10. Request Admissibility and the Validation Ladder

Requests are screened in a fixed order, and the first failing tier decides the response. Later tiers are never reached once an earlier tier has rejected the request, which means the error a client sees for a malformed request that also targets a missing resource is the malformed-request error, not the not-found error.

The ladder opens with authentication. Every operation except the clock-setting capability requires both headers, and the declared role must be one of the seven recognized names; otherwise the response is `ERR_UNAUTHENTICATED` (HTTP 401). Authorization follows immediately: the acting role must appear on the operation's authorized list, or the response is `ERR_FORBIDDEN_ROLE` (HTTP 403).

The third tier inspects the request body itself, on every operation that has one. Every field the operation declares as required must be present, and a required string field must carry a non-blank value; every enumerated field must carry a declared member; every numeric field must satisfy its declared range — `leadership_score` and `achievement_score` between 0 and 100, `gpa` and `verified_gpa` between 0.0 and 4.0, `graduation_year` and `cohort_year` at least 2000, `effectiveness_score` between 1 and 5, `classroom_capacity` and `max_corps_members` at least 1, `required_coursework_hours` and `required_practice_hours` at least 1, `deadline_days_before_term`, `required_hours`, `hiring_commitment_slots`, `placement_fee_per_member_cents`, `unfilled_slot_penalty_cents`, `fee_budget_cents` and `coursework_fee_cents` all non-negative, `state_code` exactly two uppercase letters, and `subject_needs` a non-empty selection drawn from the six subject areas. A body field declared unique must not already be held by another row — this applies to a region's `region_code` and to an applicant's `email`. Any breach of this tier is `ERR_INVALID_REQUEST` (HTTP 400).

The fourth tier resolves referenced entities, one kind at a time, and each kind has its own error. A Region that cannot be resolved is `ERR_REGION_NOT_FOUND` (404) and is reported on district creation and pathway creation, the two operations that name a `region_id`. A PartnerDistrict that cannot be resolved is `ERR_DISTRICT_NOT_FOUND` (404), reported on school creation, on the district status change, and on the listing of a district's schools. A PartnerSchool that cannot be resolved is `ERR_SCHOOL_NOT_FOUND` (404), reported on placement creation, on a school read, and on the listing of a school's placements. An Applicant that cannot be resolved is `ERR_APPLICANT_NOT_FOUND` (404), reported on application submission. An Application that cannot be resolved is `ERR_APPLICATION_NOT_FOUND` (404), reported on the application read and on all six application operations — review, return, resubmit, decision, offer, and offer response. A CertificationPathway that cannot be resolved is `ERR_PATHWAY_NOT_FOUND` (404), reported on milestone creation, on a pathway read, and on the listing of a pathway's milestones. A CorpsMember that cannot be resolved is `ERR_MEMBER_NOT_FOUND` (404), reported on the member read, on leave, return-from-leave and exit, on both institute operations, on placement creation, on milestone creation, on support-record creation, and on all three member sub-collections (placements, certification milestones, support records). A Placement that cannot be resolved is `ERR_PLACEMENT_NOT_FOUND` (404), reported on confirmation, activation, early exit and reinstatement. A CertificationMilestone that cannot be resolved is `ERR_MILESTONE_NOT_FOUND` (404), reported on the milestone read, start, complete and verify.

The fifth tier applies the two concurrency guards of §2.7 and nothing else. The sixth tier applies the state gates: a transition requested from a state that does not permit it, or with a transition precondition unmet, is `ERR_INVALID_STATE` (HTTP 409) on every transition operation in this document; a transition requested against a resource already sitting in one of its terminal states is `ERR_ALREADY_TERMINAL` (HTTP 409), which is reported on application review, return, resubmit, decision and offer, on member leave and exit, on placement confirmation and activation, and on the district status change. An offer answered after its window has closed is `ERR_OFFER_EXPIRED` (HTTP 409). A district whose agreement is not `ACTIVE` where an active agreement is required is `ERR_DISTRICT_NOT_ACTIVE` (HTTP 409), reported on placement confirmation, placement reinstatement and offer extension. A member whose service is not `ACTIVE` where active service is required is `ERR_MEMBER_NOT_ACTIVE` (HTTP 409), reported on placement creation, confirmation and reinstatement. A member whose institute is not `COMPLETED` where completion is required is `ERR_INSTITUTE_INCOMPLETE` (HTTP 409), reported on placement activation.

The seventh and final tier holds the business rules: the segregation-of-duties check of §2.9 (`ERR_SOD_VIOLATION`, HTTP 403, on decisions and verifications); the one-live-application rule (`ERR_DUPLICATE_APPLICATION`, HTTP 409, on application submission); the school-capacity rule (`ERR_SCHOOL_CAPACITY_EXCEEDED`, HTTP 409, on placement confirmation and reinstatement); the coach-schedule rule (`ERR_COACH_SCHEDULE_OVERLAP`, HTTP 409, on support-record creation); the milestone deadline rule (`ERR_MILESTONE_PAST_DUE`, HTTP 422, on milestone completion); the pathway-region agreement rule (`ERR_PATHWAY_REGION_MISMATCH`, HTTP 422, on milestone creation); the district fee ceiling (`ERR_DISTRICT_BUDGET_EXCEEDED`, HTTP 402, on placement creation); the selection band (`ERR_SCORE_BELOW_THRESHOLD`, HTTP 422, on a selection decision); and the institute practice ceiling (`ERR_PRACTICE_HOURS_EXCEEDED`, HTTP 422, on the practice-hours operation). Where two business rules could apply to the same request, the ordering above is the order in which they are evaluated.

### 2.11. Nested Resource Retrieval

Paths that nest one resource under another are resolved left to right. The system validates each identifier in the order it appears in the path, and the first identifier that does not correspond to an existing resource determines the failure: a request for the schools of a district that does not exist reports `ERR_DISTRICT_NOT_FOUND` before any school is even considered, and a request for the placements of a school that does not exist reports `ERR_SCHOOL_NOT_FOUND` on the same principle. The same left-to-right discipline governs creation operations whose parent is named in the body rather than the path: a placement payload names both a corps member and a school, and the member is resolved first; a milestone payload names both a corps member and a pathway, and the member is resolved first.

### 2.12. The Logical Clock

Every deadline, window, expiry and band in this document is evaluated against a single server-held logical clock, not against wall-clock time. Before any client sets it, the clock reads the fixed startup instant `2026-09-01T00:00:00Z`; it never falls back to the machine's real time, which is what makes deadline behaviour reproducible. A `PlatformAdmin` may replace the current instant by supplying a `to_iso8601` value through the admin-only clock-setting capability; the replacement takes effect for every subsequent request and persists until it is set again. The clock governs the resubmission window on a returned application, the expiry of an outstanding offer, the deadline bands and overdue state of a certification milestone, the automatic completion of a placement at its term end, and the automatic expiry of a district agreement at its region's term start. The two automatic transitions the clock drives — the completion of a placement at its term end (§3.8) and the expiry of a district agreement at its region's term start (§3.6) — are applied by the server before it handles each request, so they become visible on the first response that follows a clock advance.
## 3. Business Logic & Workflows

The subsections below follow the corps member's journey from campus recruitment to the end of the two-year commitment, interleaving the district-side commercial rules wherever the two narratives meet.

### 3.1. Recruitment and the Applicant Record

Recruitment begins on campus. A `SelectionManager` records a prospect as an **Applicant**, supplying a `full_name`, a contact `email`, the `campus_name` the prospect was sourced from, a `campus_tier`, an expected or actual `graduation_year`, and three assessments: a `leadership_score`, an `achievement_score`, and a self-reported `gpa`. The email is the applicant's identity as far as deduplication is concerned — it must be unique across every applicant on file — and a second registration attempt with an email already on file is refused with `ERR_INVALID_REQUEST` (HTTP 400).

The assessed values are bounded, and a breach of any bound is also `ERR_INVALID_REQUEST`: `leadership_score` and `achievement_score` are measured on a 0-to-100 scale, `gpa` on a 0.0-to-4.0 scale, and `graduation_year` may not precede 2000. The `campus_tier` is one of `PRIORITY`, `STANDARD` or `DEVELOPING`; a `PRIORITY` campus is one the recruitment team has chosen to weight, and applicants sourced there carry a scoring advantage that is applied later, when their selection score is computed. The `leadership_score` is not merely descriptive: the selection pipeline will not open a review for an applicant whose leadership assessment falls below the program's floor, which is discussed in the next subsection.

### 3.2. Entering the Pipeline: Submission, Review and Revision

An application is submitted against an existing applicant, naming that applicant through `applicant_id`, the region the applicant hopes to serve in through `preferred_region_id`, the subject they intend to teach through `subject_area`, and the grade band they prefer through `grade_preference`. The subject is one of `MATH`, `SCIENCE`, `ENGLISH`, `HISTORY`, `SPED` or `BILINGUAL`, and the grade preference is one of `ELEMENTARY`, `MIDDLE` or `HIGH`. A newly submitted application enters the pipeline at `SUBMITTED`, with its `revision_count` set to 0, and its `selection_score` computed immediately using the provisional variant described below. Until a decision is recorded its `final_selection_score` reads 0.0, and its `verified_gpa`, `reviewed_by_user_id`, `decided_by_user_id`, `decision_reason`, `offer_expires_at`, `created_corps_member_id` and `returned_at` all start null.

Applicants are expected to commit to a single live candidacy. An applicant may hold at most one application whose `status` is neither `REJECTED` nor `DECLINED`; a second submission while such an application exists is refused with `ERR_DUPLICATE_APPLICATION` (HTTP 409). Applications that have already been rejected or declined do not stand in the way of a fresh submission.

Review is opened by a `SelectionManager` and moves an application from `SUBMITTED` to `UNDER_REVIEW`. Two things must hold. The application must still be at `SUBMITTED`, and the owning applicant's `leadership_score` must be at least 40.0 — the program's floor for investing reviewer time. If the leadership floor is not met, the review is refused, the application stays at `SUBMITTED`, and the client sees `ERR_INVALID_STATE` (HTTP 409) because a precondition of the transition is false. When the review does open, the server records the reviewer's operator id in `reviewed_by_user_id`, takes the transcript-verified `verified_gpa` supplied by the reviewer on a 0.0-to-4.0 scale, and refreshes `selection_score`.

The provisional selection score is a weighted composite of the three assessed dimensions, with two conditional bonuses. The leadership assessment enters at a weight of 0.45 and the achievement assessment at a weight of 0.40, both taken exactly as recorded on the applicant. The academic dimension enters at a weight of 0.15 after normalization: the GPA used — the self-reported `gpa` in this provisional variant — is compared against 4.0, the smaller of the two values is divided by 4.0, and the result is expressed on a 0-to-100 scale. The three weighted terms are summed, and then two bonuses may apply. If the applicant was sourced from a `PRIORITY` campus, 5.0 is added and the running total is capped at 100.0. If the application's `subject_area` is `MATH`, `SCIENCE` or `SPED` — the subjects the program treats as high-need — a further 7.0 is added, and the total is capped at 100.0 again. Only after every bonus has been added is the result rounded half up to 2 decimal places; that rounded value is the provisional `selection_score`. For orientation, the resulting score falls into one of three informal bands: `STRONG` at or above 85.00, `QUALIFIED` at or above 70.00, and `DEVELOPING` below that.

A reviewer who is not yet ready to decide may return the application for revision. The return moves the application from `UNDER_REVIEW` to `RETURNED_FOR_REVISION`, increments `revision_count`, stamps `returned_at` with the current logical clock, and may carry a free-text `return_reason`, which the server accepts but neither stores nor echoes back. Revision is a bounded loop: a return is only permitted while `revision_count` is below 3, so the fourth return attempt is refused with `ERR_INVALID_STATE`. The applicant — and only the applicant, identified by their own `X-User-ID` matching the application's `applicant_id` — may resubmit; any caller whose `X-User-ID` does not match is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403). The resubmission moves the application back from `RETURNED_FOR_REVISION` to `UNDER_REVIEW` and clears `returned_at` to null. Resubmission is time-boxed: the current logical clock must be at or before `returned_at` plus 30 days. A resubmission attempted after that window is refused with `ERR_INVALID_STATE`, and the revision cycle can then run again up to the three-return ceiling.
### 3.3. Decisions, Offers and the Regional Quota

A decision is recorded by a `SelectionManager` against an application that is `UNDER_REVIEW`, using a `decision` value of either `SELECT` or `REJECT` and an optional free-text `decision_reason`. Two guards apply before the decision lands. The first is the segregation-of-duties rule of §2.9: the deciding operator's `X-User-ID` must differ from the application's `reviewed_by_user_id`, and a decision recorded by the same operator who ran the review is refused with `ERR_SOD_VIOLATION` (HTTP 403). The second guard is the selection band, and it applies only to a positive decision: a `SELECT` requires the final selection score to be at or above 85.00, and a selection requested below that band is refused with `ERR_SCORE_BELOW_THRESHOLD` (HTTP 422). A `REJECT` carries no score gate at all.

The final selection score is the same composite as the provisional score, computed with one substitution: the academic term reads the transcript-verified `verified_gpa` recorded at review instead of the self-reported `gpa`. Everything else — the 0.45, 0.40 and 0.15 weights, the normalization of the GPA against 4.0 onto a 0-to-100 scale, the 5.0 `PRIORITY` campus bonus, the 7.0 high-need subject bonus for `MATH`, `SCIENCE` or `SPED`, the 100.0 caps, the half-up rounding to 2 decimal places applied once after all bonuses — is identical. The two variants therefore diverge on exactly those applications whose verified GPA differs from the self-reported one, and only the final variant feeds the selection band. The decision writes the computed value to `final_selection_score`, records the deciding operator in `decided_by_user_id`, and moves the application to `SELECTED` or `REJECTED`. Note that `REJECTED` and `ACCEPTED` are the application's two terminal states: once an application sits in either, further transitions against it are refused with `ERR_ALREADY_TERMINAL` (HTTP 409).

An offer is extended by a `SelectionManager` to an application that is either `SELECTED` or previously `DECLINED` — a declined offer is recoverable, which is why `DECLINED` is not a terminal state. Extension is contingent on the commercial health of the destination: at least one district in the application's `preferred_region_id` must have an `agreement_status` of `ACTIVE`, and when every district in that region is still a draft, suspended or expired, the extension is refused with `ERR_DISTRICT_NOT_ACTIVE` (HTTP 409). A successful extension moves the application to `OFFER_EXTENDED` and sets `offer_expires_at` to the current logical clock plus 14 days.

The offer is answered by the applicant alone; any other role, or an applicant whose `X-User-ID` does not match the application's `applicant_id`, is turned away with `ERR_FORBIDDEN_ROLE` (HTTP 403). The response carries an `accept` value — true to take the offer, false to turn it down. A decline carries no additional conditions: it moves the application from `OFFER_EXTENDED` to `DECLINED` and clears `offer_expires_at` to null, leaving the door open to a later re-offer. An acceptance is more demanding. The clock must not have passed `offer_expires_at`; an answer that arrives after the window has closed is refused with `ERR_OFFER_EXPIRED` (HTTP 409). The destination region must also still have room: counting every corps member whose owning application selected that same `preferred_region_id` and whose `service_status` is `ACTIVE` or `ON_LEAVE`, the acceptance is refused with `ERR_INVALID_STATE` (HTTP 409) once that count has already reached the region's `max_corps_members`, because a precondition of the transition is false; a region may therefore carry at most that many corps members at a time. A member on leave still consumes regional capacity, which is deliberate: the quota tracks the cohort the region has committed to support, not merely the members currently teaching.

Acceptance is the most consequential single action in the system, because it is where a corps member comes into existence. It runs as a three-hop cascade. The first hop moves the application to `ACCEPTED` and synthesizes a **CorpsMember** whose `application_id` points back at the application, whose `cohort_year` is the calendar year of the region's `term_start_date`, whose `service_status` starts at `ACTIVE` and whose `institute_status` starts at `ENROLLED`, and whose accumulated figures — `practice_teaching_hours`, `coursework_hours_completed`, `certification_hours_verified` — all start at zero along with a `readiness_score` of 0.0 and an `institute_stipend_cents` of 0, and its `service_started_at`, `leave_started_at` and `exit_reason` all start null — `service_started_at` is written only when the member returns from leave (§3.9). The new member's identifier is written back onto the application as `created_corps_member_id`, which is how a client finds the member an offer produced and is the field the member list can be filtered by.

The second hop builds the member's certification schedule. For every certification pathway whose `region_id` equals the application's `preferred_region_id`, the server synthesizes one **CertificationMilestone** per milestone type, so a member in a region with two pathways receives two complete sets. Where the region holds several pathways, they are taken in `created_at` ascending order, the lower pathway `id` string breaking a tie. The hours each milestone contributes are drawn from the pathway: a `PRACTICUM` milestone takes the pathway's `required_practice_hours`, a `COURSEWORK` or `ORIENTATION` milestone takes the pathway's `required_coursework_hours`, and an `EXAM` milestone is worth 0 hours. Each milestone's `due_date` is the region's `term_start_date` minus the pathway's `deadline_days_before_term` days. The milestones are synthesized in the fixed order `COURSEWORK`, `PRACTICUM`, `ORIENTATION`, `EXAM`, and that order is also the order in which the member's milestone collection is returned — a stable, type-based ordering that a client can rely on rather than a creation-time ordering.

The third hop closes the loop: each synthesized milestone, as it is created, recomputes the member's `certification_hours_verified` and `readiness_score`, and each of those recomputes advances the member's `version` once. A member created by an acceptance therefore arrives with a version that already reflects every milestone in its schedule, and any client holding a version observed before the acceptance will fail the concurrency guard described in §2.7.

### 3.4. The Pre-Service Institute: Practice Hours, Stipends and Readiness

Before a corps member may stand in front of a classroom, they must complete the pre-service summer institute. An `InstituteDirector` records supervised practice teaching by submitting a `practice_hours_delta` — a non-negative integer — against the member; a recording attempted once the institute is already `COMPLETED` is refused with `ERR_INVALID_STATE` (HTTP 409). The first such record moves the member's `institute_status` from `ENROLLED` to `IN_TRAINING` and adds the delta to `practice_teaching_hours`; every subsequent record is the self-loop that keeps the member at `IN_TRAINING` while adding further hours. Recording practice hours also recomputes the member's `institute_stipend_cents` and `readiness_score`, so a member's stipend grows as they teach.

The institute is bounded at the top. The member's current `practice_teaching_hours` plus the requested `practice_hours_delta` may not exceed 480 hours, and a record that would push the total past that ceiling is refused with `ERR_PRACTICE_HOURS_EXCEEDED` (HTTP 422) — the same bound is restated as the precondition of the repeated-record edge, so the ceiling holds whether the member is entering training or already inside it. There is a floor as well, but it governs completion rather than recording: an `InstituteDirector` may mark the institute complete only once `practice_teaching_hours` has reached 120, and an attempt below that floor is refused with `ERR_INVALID_STATE` (HTTP 409). Completion moves `institute_status` to `COMPLETED`, recomputes `readiness_score`, and finalizes `institute_stipend_cents`.

The stipend is a prorated share of an annual figure, and the order in which the rounding is applied is pinned. The annual stipend of 6510.00 dollars is divided by the 52 weeks of the year, and that quotient is rounded half up to 2 decimal places, which fixes the weekly amount at 125.19 dollars. The member's `practice_teaching_hours` are then split against a 40-hour week: the whole-week count is the hours divided by 40 discarding any remainder, and the remainder is what is left over. The partial week is paid pro rata — the weekly amount multiplied by the remainder and divided by 40, rounded half up to 2 decimal places. The stipend in dollars is the whole-week count multiplied by the weekly amount, plus the prorated partial amount; a member who has not yet accumulated a full week therefore has a whole-week count of zero and is paid only the prorated partial. Finally the dollar total is multiplied by 100 and rounded half up to 0 decimal places to give `institute_stipend_cents` as an integer. Rounding each week's amount and the partial amount to 2 decimals before summing — rather than summing in full precision and rounding once at the end — is a deliberate requirement, because the two orders produce different cents for some hour totals.

The institute dimension and the service dimension are independent. A member's `institute_status` advances `ENROLLED` to `IN_TRAINING` to `COMPLETED`, while `service_status` runs on its own track described in §3.9; nothing prevents a member from being `ON_LEAVE` while still `IN_TRAINING`.
### 3.5. Certification Milestones and State Deadline Compliance

Certification progress is tracked as a collection of **CertificationMilestone** rows, one per requirement a member must satisfy. Most are born from the acceptance cascade of §3.3, but a `CertificationOfficer` may also add one directly, naming the member through `corps_member_id`, the state pathway through `pathway_id`, a `milestone_type` of `COURSEWORK`, `PRACTICUM`, `EXAM` or `ORIENTATION`, and the `required_hours` the milestone is worth. A direct creation may supply its own `due_date`; when it is omitted, the server derives it exactly as the cascade does, by subtracting the pathway's `deadline_days_before_term` from the owning region's `term_start_date`. Newly created milestones start at `progress_status` `PENDING` and `verification_status` `UNVERIFIED`, and the creation advances the member's `version` because the member's schedule has changed.

The state requirements themselves are configured before any member arrives. A `PlatformAdmin` creates a **CertificationPathway** for a region, declaring the two-letter `state_code` of the issuing authority, which is recorded as supplied and need not equal the owning region's own `state_code`, the `certification_track` the pathway belongs to, one of `STANDARD`, `ALTERNATIVE_EMERGENCY` or `PROVISIONAL`, the `required_coursework_hours` and `required_practice_hours` the state demands, both at least 1, the `deadline_days_before_term` offset by which every milestone must be verified, and the `coursework_fee_cents` charged for the pathway's coursework, prorated by the member's coursework progress. A pathway raised against a region that does not exist is refused with `ERR_REGION_NOT_FOUND` (HTTP 404), and it is the owning region's `term_start_date` that later turns the pathway's deadline offset into concrete milestone due dates.

A milestone must belong to the member's own jurisdiction. The pathway named on the milestone must sit in the same region the member's application selected — the pathway's `region_id` must equal the region that the member's owning application named as its `preferred_region_id`. A milestone raised under a pathway from any other region is refused with `ERR_PATHWAY_REGION_MISMATCH` (HTTP 422), which keeps a member from accumulating credit toward a certification their state will never issue.

Each milestone carries two parallel dimensions that never gate one another except through the explicit preconditions below. The first is `progress_status`, running `PENDING` to `IN_PROGRESS` to `COMPLETED`. A `CertificationOfficer` starts work with a transition that requires the milestone to be `PENDING`, its verification to be `UNVERIFIED`, and the owning member's `service_status` to be `ACTIVE` or `ON_LEAVE` — a member who has exited the corps can no longer be advanced along the certification track. Completion has two entry edges. From `PENDING`, completion is the zero-hour shortcut: it is permitted only when `required_hours` is 0, which is how requirements that are satisfied by attendance or by an examination booking are closed without a work period, and it additionally requires the member's `institute_status` to be `IN_TRAINING` or `COMPLETED`. From `IN_PROGRESS`, completion requires only that the member's `institute_status` be `IN_TRAINING` or `COMPLETED`. Both completion edges stamp `completed_at` with the current logical clock and record the officer in `completed_by_user_id`, and both recompute the member's `readiness_score` and `coursework_hours_completed`, the latter the sum of the `required_hours` of every milestone of that member whose `milestone_type` is `COURSEWORK` or `ORIENTATION` and whose `progress_status` is `COMPLETED`, whether or not that milestone has been verified.

Completion is also deadline-bound. A milestone may not be completed once its `due_date` has passed on the logical clock: comparing the clock's date against the milestone's due date, a completion attempted after that date is refused with `ERR_MILESTONE_PAST_DUE` (HTTP 422). The state deadline is therefore a hard gate on the completion edge, not merely a warning indicator.

The second dimension is `verification_status`, running `UNVERIFIED` to `VERIFIED` or to `REJECTED`. A `CertificationOfficer` supplies an `outcome` of `VERIFY` or `REJECT`, and either path requires the milestone's verification to still be `UNVERIFIED`, its progress to already be `COMPLETED`, and the officer's `X-User-ID` to differ from `completed_by_user_id` — the segregation-of-duties rule of §2.9, whose breach is `ERR_SOD_VIOLATION` (HTTP 403). Whichever outcome is recorded, the officer is stored in `verified_by_user_id`. A milestone may therefore sit indefinitely at `COMPLETED` with verification still `UNVERIFIED`; the two dimensions advance on their own schedules, and the shortcuts and preconditions listed above are the only places they touch.

Verification is what converts work into credit, and it cascades. Verifying a milestone recomputes the member's `certification_hours_verified`, which sums the `required_hours` of every milestone of that member that is simultaneously `COMPLETED` and `VERIFIED`; a milestone that is complete but unverified contributes nothing, and a rejected milestone contributes nothing even though its completion stands. The same recompute refreshes the member's `readiness_score`, and that in turn re-evaluates `employment_eligible` on every placement the member holds whose status is `CONFIRMED` or `ACTIVE`. Rejecting a milestone follows the same recompute path with the rejected milestone contributing 0 hours, so a rejection can pull a member's verified hours back below the certification floor and cost them their employment eligibility.

Deadline pressure is reported on every milestone through two derived values. The `days_remaining` is the whole number of days between the clock's current UTC date and the milestone's `due_date` UTC date, computed after truncating both to their date components. The `deadline_status` band is then assigned with a short-circuit: a milestone that is both `COMPLETED` and `VERIFIED` reports `SATISFIED` regardless of the calendar, so a milestone verified after its due date reports `SATISFIED` rather than `OVERDUE`. Only for a milestone that is not yet satisfied does the day count decide — fewer than zero days remaining is `OVERDUE`, up to and including 14 days remaining is `AT_RISK`, and anything beyond that is `ON_TRACK`. Both values are recomputed on every read of a milestone as well as on every mutation, so a milestone's band can change without the row being written.

The **readiness score** answers a different question: how prepared is this member to be placed in a classroom? It blends three ratios and then awards a small credit. The certified ratio compares the member's verified certification hours against the total hours every one of their milestones requires, capped at 1.0, and it is defined as exactly 1.0 when the member's milestones require no hours at all. The practice ratio compares the member's `practice_teaching_hours` against the selected pathway's `required_practice_hours`, capped at 1.0. The coursework ratio compares the member's `coursework_hours_completed` against the selected pathway's `required_coursework_hours`, also capped at 1.0. When no pathway can be selected at all, both the practice ratio and the coursework ratio are taken as 1.0. The three ratios are weighted 0.5, 0.3 and 0.2 respectively, scaled to 100, and rounded half up to 2 decimal places to give a subtotal. That subtotal is then banded — `STRONG` at or above 80.00, `QUALIFIED` at or above 50.00, `DEVELOPING` below — and a support credit of 3.0, 1.5 or 0.0 is added accordingly. The final `readiness_score` is the subtotal plus the credit, rounded half up to 2 decimal places and capped at 100.0. The credit is keyed on the subtotal as it stood before the credit was added; the tier is never re-derived from the final score.

Which pathway supplies the two requirement figures is pinned, because a region may define several. The selected pathway is the earliest-created pathway whose `region_id` matches the region of the member's placement that is `CONFIRMED` or `ACTIVE`; when the member holds several such placements, they are considered in `created_at` ascending order, the lower `id` string breaking a tie, and the first one whose region holds any pathway decides the selection. When the member holds no such placement, the selection falls back to the pathway of the member's application's `preferred_region_id` whose `created_at` is earliest, and only if two pathways share that earliest creation instant does the lower pathway `id` string break the tie. The `created_at` comparison is always made before the identifier comparison, never the reverse.

**Employment eligibility** is the flag that decides whether a placement may lawfully continue. It is true only when all five of the following hold at once: the placement's `status` is `CONFIRMED` or `ACTIVE`; the member's `service_status` is `ACTIVE`; the member's `institute_status` is `COMPLETED`; none of the member's milestones has a `deadline_status` of `OVERDUE`; and the member's `certification_hours_verified` is at least the sum of the selected pathway's `required_practice_hours` and `required_coursework_hours`, that sum being 0 when no pathway can be selected. A single overdue milestone anywhere in the member's schedule forces the flag to false, however many hours have been verified. The flag is refreshed on placement status changes, on member service and institute changes, and on milestone verification transitions.

Finally, the order in which a member's milestones are returned is not simply the order in which they were created. Milestones synthesized by an acceptance are ordered by `milestone_type` in the fixed sequence `COURSEWORK`, `PRACTICUM`, `ORIENTATION`, `EXAM`, so that every member's schedule reads in the same canonical order; milestones created directly by an officer are appended in `created_at` ascending order instead.
### 3.6. District Partnerships: Agreements, Schools and Hiring Commitments

A `PlatformAdmin` opens a district relationship by creating a **PartnerDistrict** against an existing `region_id`, with the district's legal `name`, the `hiring_commitment_slots` it contractually commits to fill this term, the `placement_fee_per_member_cents` it pays for each corps member actually placed in one of its schools, the `unfilled_slot_penalty_cents` it owes for each committed slot left empty at term start, and a `fee_budget_cents` ceiling on everything it can be invoiced for the term. All four money figures are non-negative, and a district created against a region that does not exist is refused with `ERR_REGION_NOT_FOUND` (HTTP 404). A new agreement starts at `agreement_status` `DRAFT`, with `committed_placement_count` and `invoice_amount_cents` both at 0.

The agreement lifecycle is deliberately narrow. A draft becomes `ACTIVE` only once the district has at least one partner school on file, so an agreement cannot be signed before there is somewhere to place a corps member. An active agreement can be `SUSPENDED` by an administrator at any time, which stops new placements from being confirmed there without disturbing the placements already running. A suspended agreement returns to `ACTIVE` only when the district's invoice total has come back within its budget — that is, when `invoice_amount_cents` is at or below `fee_budget_cents`. Independently of any operator, an agreement that is still `ACTIVE` when the logical clock reaches its region's `term_start_date` expires automatically, moving to `EXPIRED`, which is the district lifecycle's terminal state; any further transition attempted against it is refused with `ERR_ALREADY_TERMINAL` (HTTP 409). The status change itself is driven by a `to_status` value, and for a district that has not yet reached `EXPIRED` only three operator-driven moves are legal: `DRAFT` to `ACTIVE`, `ACTIVE` to `SUSPENDED`, and `SUSPENDED` to `ACTIVE`. Any other `to_status` — a repeat of the current status, a move to `DRAFT`, or an attempt to set `EXPIRED` by hand — is refused with `ERR_INVALID_STATE` (HTTP 409).

A district's schools are created by a `PlatformAdmin` with the district named through `district_id`, the school's `name`, its `grade_band` of `ELEMENTARY`, `MIDDLE` or `HIGH`, its `subject_needs` — a non-empty selection from `MATH`, `SCIENCE`, `ENGLISH`, `HISTORY`, `SPED` and `BILINGUAL` — and its `classroom_capacity`, which must be at least 1. A school starts with `occupied_classrooms` at 0. Because a school is a child of its district, the creation also requires the caller's observed district version in `expected_district_version` and advances the district's `version`, as described in §2.7; a school created under a district that does not exist is refused with `ERR_DISTRICT_NOT_FOUND` (HTTP 404).

The district's invoice is a two-part computation that reflects both what the district got and what it did not. The filled count is the number of placements whose school resolves to this district and whose status is `CONFIRMED` or `ACTIVE`; placements still `MATCHED`, or already `EXITED_EARLY` or `COMPLETED`, are excluded. The unfilled count is the district's `hiring_commitment_slots` minus the filled count, floored at zero, so an over-filled commitment never produces a negative penalty. The gross charge is the filled count multiplied by `placement_fee_per_member_cents`, the penalty is the unfilled count multiplied by `unfilled_slot_penalty_cents`, and `invoice_amount_cents` is the sum of the two. This is the stored, actual variant, and it is recomputed when a placement is confirmed, activated, exited early, reinstated, or completed at its term end.

The district read supports a second, forward-looking view. When the caller passes `projection` with the value `FORWARD_LOOKING`, the invoice reported is the district's `hiring_commitment_slots` multiplied by its `placement_fee_per_member_cents`, with no penalty term at all — the assumption being that every committed slot will eventually be filled. The default projection is `ACTUAL`, which reports the stored value; a `projection` value other than those two is refused with `ERR_INVALID_REQUEST` (HTTP 400). For any district with at least one unfilled slot the two views return different integers, and clients comparing them can read the gap as the district's remaining hiring exposure.

### 3.7. Placement Matching, Confirmation, Capacity and Activation

A **Placement** ties one corps member to one partner school for a term window. A `PlacementCoordinator` creates it by naming the `corps_member_id` and the `school_id`, the `subject_area` the member will teach there, the `grade_band` of the classroom, and the closed term window that runs from `term_start_date` through `term_end_date`; the two instants are not cross-checked against one another, so any parseable window is accepted at match time. The creation request also carries `expected_corps_member_version`, the concurrency guard of §2.7, and a stale value is refused with `ERR_STALE_MEMBER_VERSION` (HTTP 412). A new placement starts at `status` `MATCHED` with `employment_eligible` false and `placement_fee_cents` at 0, since the fee is priced only at confirmation and activation, and its creation advances the member's `version`.

Two gates apply before a match is even recorded. The member must be in `ACTIVE` service — a member on leave or already exited cannot be matched, and the request is refused with `ERR_MEMBER_NOT_ACTIVE` (HTTP 409). And the destination district must be able to absorb the cost: the server projects the district's invoice total as it would stand once this placement is counted among that district's `CONFIRMED` or `ACTIVE` placements, and refuses the match with `ERR_DISTRICT_BUDGET_EXCEEDED` (HTTP 402) when that projected total would exceed the district's `fee_budget_cents`. The district ceiling is therefore checked at match time, before any counter moves.

Confirmation is the step that commits the district. A `PlacementCoordinator` may confirm a placement that is still `MATCHED`, and the transition requires five things to hold together, evaluated in the order given here. The placement's `subject_area` must appear in the target school's `subject_needs`, since a school only hosts placements in subjects it has declared a need for. The placement's `grade_band` must equal the school's `grade_band` and must also equal the `grade_preference` recorded on the corps member's owning application, so the classroom a member is confirmed into matches both what the school serves and what the member asked to teach. The district owning the placement's school must then have an `agreement_status` of `ACTIVE`, or the request fails with `ERR_DISTRICT_NOT_ACTIVE` (HTTP 409). The corps member must be in `ACTIVE` service, or it fails with `ERR_MEMBER_NOT_ACTIVE` (HTTP 409). A breach of the two subject-and-grade conditions is `ERR_INVALID_STATE` (HTTP 409), and because those two are evaluated first they decide the response whenever they fail, even where a district or member gate would also have failed.

School capacity is a separate constraint, evaluated at confirmation and again at reinstatement. The number of placements already at the target school whose status is `CONFIRMED` or `ACTIVE` and whose closed term window overlaps the new placement's closed window must be strictly less than the school's `classroom_capacity`; a confirmation that would reach the capacity is refused with `ERR_SCHOOL_CAPACITY_EXCEEDED` (HTTP 409). The overlap test uses closed intervals at both ends, so two windows that share exactly one endpoint — one ending on the day the other begins — count as overlapping, and a school's capacity is consumed for that shared day by both placements.

A successful confirmation stamps `confirmed_at` with the current logical clock and moves the placement to `CONFIRMED`. It then runs its cascade: the district's `committed_placement_count` rises by 1, which drives a recompute of the district's `invoice_amount_cents` and of the placement's own `placement_fee_cents`, and the placement's `employment_eligible` flag is recomputed from the member's current certification state.

The placement fee is priced off the district, with a regional fallback and a subject uplift. The base is the district's `placement_fee_per_member_cents`; if that value is zero or less, the region's `base_placement_fee_cents` is used instead. When the placement's `subject_area` is `MATH`, `SCIENCE` or `SPED`, the resolved base is multiplied by 1.15 and rounded half up to 0 decimal places. The result is stored as an integer number of cents in `placement_fee_cents`, and the uplift is applied exactly once, to the base that has already been resolved. The fee is recomputed on confirmation and again on activation.

Activation is the final step before a corps member stands in front of a class. A `PlacementCoordinator` activates a placement that is `CONFIRMED`, and two conditions guard it: the member's `institute_status` must be `COMPLETED`, or the request fails with `ERR_INSTITUTE_INCOMPLETE` (HTTP 409), and the member's `readiness_score` must be at least 60.0, or it fails with `ERR_INVALID_STATE` (HTTP 409). Activation stamps `activated_at`, moves the placement to `ACTIVE`, recomputes the placement's `employment_eligible`, and recomputes the district's `invoice_amount_cents`.
### 3.8. Placement Endings, Reinstatement and the Fee Ceiling

A placement ends in one of two ways, and the two are treated very differently by the district's books. The first is ordinary completion. When the logical clock reaches a placement's `term_end_date`, the system itself closes the placement, moving it from `ACTIVE` to `COMPLETED` without any client action. The transition sets `employment_eligible` to false, decrements the owning district's `committed_placement_count` by 1, decrements the school's `occupied_classrooms` by 1, and recomputes the district's `invoice_amount_cents` — so a district that finishes the term with fewer corps members in classrooms than it committed to will see its unfilled-slot penalty grow as those completions land. `COMPLETED` is the placement's terminal state, and any later transition attempted against it is refused with `ERR_ALREADY_TERMINAL` (HTTP 409).

The second ending is an early exit. A `PlacementCoordinator` may end an `ACTIVE` placement before its term end date by recording an `early_exit_reason`, which moves the placement to `EXITED_EARLY` and clears its `employment_eligible` flag. This runs a three-hop cascade. The first hop releases the resources the placement was holding: the district's `committed_placement_count` drops by 1 and the school's `occupied_classrooms` drops by 1. The second hop recomputes the district's `invoice_amount_cents` from the reduced filled count, which raises the unfilled-slot penalty. The third hop re-evaluates the district's fee ceiling, and if the recomputed `invoice_amount_cents` now exceeds the district's `fee_budget_cents`, the district is flagged by setting its `agreement_status` to `SUSPENDED` — a breach of the ceiling suspends the agreement rather than refusing the exit, because the exit has already happened and the district must stop taking on new placements until the balance is resolved.

An early exit is reversible. A `PlacementCoordinator` may reinstate a placement that is `EXITED_EARLY`, restoring it to `ACTIVE`, provided the district owning its school is still `ACTIVE` and the corps member is still in `ACTIVE` service; a suspended district or a member on leave blocks the reinstatement, and the capacity rule of §3.7 is re-evaluated at this point as well, so a school that has since filled up will refuse the reinstatement with `ERR_SCHOOL_CAPACITY_EXCEEDED` (HTTP 409). Reinstatement clears `early_exit_reason` back to null, sets `employment_eligible` from the eligibility calculation rather than from a stored value, increments the district's `committed_placement_count` and the school's `occupied_classrooms` by 1 each, and recomputes the district's `invoice_amount_cents`. It is the compensating action for an early exit, and the pair of them is what keeps the district and school counters honest.

The `occupied_classrooms` counter on a school deserves a precise statement, because it is derived rather than authored: it counts the placements at that school whose status is `CONFIRMED` or `ACTIVE` and whose term window is open at the current logical clock, and it starts at 0 when the school is created. It is recomputed whenever the school is read, so it follows the clock without the row being written, and it moves down on an early exit and back up on a reinstatement; the capacity rule of §3.7 is a separate, overlap-scoped count and does not read this counter.

### 3.9. Service Status, Coaching, Evaluation and Early Exit

A corps member's two-year commitment is tracked by `service_status`, which is entirely independent of the institute dimension described in §3.4. A `PlacementCoordinator` places a member on leave by transitioning them from `ACTIVE` to `ON_LEAVE`, which stamps `leave_started_at` with the current logical clock and forces `employment_eligible` to false on every placement of that member whose status is `CONFIRMED` or `ACTIVE` — a member who is not serving cannot be counted as employable, whatever their certification state. The return from leave closes the cycle: the member goes back from `ON_LEAVE` to `ACTIVE`, `leave_started_at` is cleared to null, and `service_started_at` is set to the current logical clock, which re-anchors the two-year commitment window at the moment service resumed. The return also recomputes `employment_eligible` on the member's confirmed and active placements, so a member returning with their certification in order comes back employable.

The commitment can also be cut short. A `PlacementCoordinator` exits a member in `ACTIVE` service by transitioning them to `EXITED` and supplying the `exit_reason` in the request; `EXITED` is the service dimension's terminal state, and a member who has exited cannot be put on leave, returned from leave, or exited a second time — those attempts are refused with `ERR_ALREADY_TERMINAL` (HTTP 409). Because the eligibility calculation is refreshed whenever a member's service status changes, an exit is reflected on the member's placements as soon as the service status moves.

Support for serving corps members is recorded as **SupportRecord** rows, and the same resource carries two different kinds of interaction, discriminated by `record_type`. A `COACHING` record is a support-coaching session, and an `EVALUATION` record is a formal performance evaluation. A `Coach` creates either kind by naming the `corps_member_id`, the `coach_user_id` of the operator who ran the session, the `session_start` and `session_end` of the session, an integer `effectiveness_score` on a 1-to-5 scale, and optional free-text `notes`; the session's two instants are not cross-checked against one another. A record created against a corps member who does not exist is refused with `ERR_MEMBER_NOT_FOUND` (HTTP 404), and a score outside the 1-to-5 range is refused with `ERR_INVALID_REQUEST` (HTTP 400).

A coach cannot be in two places at once, and the system enforces that with a schedule rule scoped to coaching. No existing `COACHING` record for the same `coach_user_id` may hold a half-open interval running from its `session_start` up to but not including its `session_end` that intersects the new record's half-open interval; a conflicting booking is refused with `ERR_COACH_SCHEDULE_OVERLAP` (HTTP 409). Because the intervals are half-open, a session that begins at the exact instant another session ends does not conflict with it, and back-to-back coaching is therefore permitted. The rule is deliberately scoped to `COACHING` records: evaluations do not participate in the coach's occupancy check.

Evaluations carry a meaning beyond the record itself. An `EVALUATION` whose `effectiveness_score` is below 3 is the program's signal for early-exit review — its mechanism for noticing a struggling teacher before the two-year commitment is abandoned — but recording it stores nothing beyond the support record itself, and the review it prompts is a human process outside this API that may later result in the member's exit described above, or in the early exit of one of their placements described in §3.8.
## 4. Endpoint Definitions
