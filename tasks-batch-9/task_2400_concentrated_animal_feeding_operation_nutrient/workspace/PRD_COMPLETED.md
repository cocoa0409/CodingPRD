# CAFO Nutrient Management API — Product Requirements Document

## 1. Introduction

Livestock operations that confine animals above certain size thresholds sit at the intersection of two regulatory regimes that rarely speak the same language: a permitting regime that asks *how large are you and where can your waste go*, and an agronomic regime that asks *how much nitrogen and phosphorus can this particular acre of ground absorb this year*. Today those two conversations happen in separate binders. Permit coverage is tracked in a state filing cabinet, the nutrient management plan lives in a consultant's spreadsheet, and the field records that prove compliance are hand-written on the back of a fuel receipt. When an inspector arrives, nobody can reconcile the barn's manure production against what was actually hauled to a field, and an operation that is functionally in violation looks perfectly compliant on paper.

This API is the system of record that closes that gap. It carries a livestock operation from its first size determination — animal units, size class, whether permit coverage is required at all — through the five-year coverage term and its renewal, and simultaneously carries the agronomic side: soil tests, per-field nitrogen and phosphorus budgets, setback geometry, storage capacity and freeboard, and every individual land application with its date, rate, method and weather. The two sides are wired together by a single derived signal, the operation's compliance posture, which reacts to inspections, freeboard alerts and spill reports by immediately restricting or suspending the operation's ability to apply or ship manure.

The design priority throughout is **determinism over convenience**. Every derived number — animal units, allowable application rate, storage days of capacity, renewal fee, mass-balance variance — has one pinned evaluation order and one rounding rule, because these numbers are used as evidence in enforcement actions. Two conserved quantities, the per-field nutrient allowance and the volume balance of each storage structure, are maintained as strict ledgers whose invariants must hold exactly after every write. Time is modelled by an explicit server-held logical clock rather than wall-clock time, so that a five-year coverage term, a four-year soil-test validity window, a hauler license lapse and a winter application window can all be exercised and audited reproducibly.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies to the entire API surface, which is mounted under `/cafo`.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. Five roles are recognised, spelled exactly as follows: `Operator`, `CertifiedPlanner`, `StateReviewer`, `Hauler`, and `ComplianceAdmin`. If either header is absent, or if `X-User-Role` is not one of those five strings, the request fails with `ERR_UNAUTHENTICATED`. If the headers are well formed but the declared role is not among the roles authorised for the endpoint being called (see the table in §4), the request fails with `ERR_UNAUTHORIZED`.

Two of the five roles are backed by persisted entities, and for those two the `X-User-ID` value is not an arbitrary label — it is a primary key.

- When `X-User-Role` is `Operator`, `X-User-ID` is the `id` of the acting `Operation`; ownership checks on any resource that references an `Operation` compare the resource's foreign-key field to `X-User-ID`. A permit, plan, field, soil test, budget, storage structure, storage inspection, application record, transfer, incident report, inspection or annual report reached through a chain of parents that resolves to a different operation is refused with `ERR_OWNERSHIP_VIOLATION`.
- When `X-User-Role` is `Hauler`, `X-User-ID` is the `id` of the acting `Hauler`; ownership checks compare the target transfer's `hauler_id` to `X-User-ID`, and a hauler acting on a transfer assigned to a different hauler is refused with `ERR_OWNERSHIP_VIOLATION`. The same comparison guards the hauler record itself: a `Hauler` reading a hauler other than the one its `X-User-ID` names is refused with `ERR_OWNERSHIP_VIOLATION`.

The remaining three roles are opaque operator identities.

- When `X-User-Role` is `CertifiedPlanner`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it — as `certifying_planner_user_id` on a plan when that planner certifies it — but never compares it to any entity's `id`.
- When `X-User-Role` is `StateReviewer`, `X-User-ID` is likewise an opaque operator identifier. The server records it as `inspector_user_id` when a reviewer conducts an inspection and as `closed_by_user_id` when a reviewer closes one, but does not compare it to any entity's `id`.
- When `X-User-Role` is `ComplianceAdmin`, `X-User-ID` is an opaque platform-operator identifier. The server may record it as `closed_by_user_id` on an inspection this administrator closes, and otherwise does not compare it to any entity's `id`.

One rule of **segregation of duties** cuts across the opaque roles: the actor who closes an inspection must never be the actor who conducted it. Closing an inspection whose recorded `inspector_user_id` equals the caller's `X-User-ID` is refused with `ERR_SEGREGATION_OF_DUTIES`, and this holds on both routes into the closed state — the no-findings route straight from the conducted state, and the route that follows an operator's corrective-action response.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` is the number of records to skip before the first returned record, defaults to 0, and may not be negative. A `limit` or `offset` that is not an integer, or that falls outside those bounds, is refused with `ERR_INVALID_REQUEST`; query parameters the endpoint does not recognise are ignored rather than rejected.

Unless a specific endpoint states otherwise, list results are ordered by their creation timestamp, `created_at`, in ascending order. Ownership is not applied to list endpoints: a list returns every record matching the supplied filters, whichever operation or hauler owns it, so an `Operator` listing fields or transfers sees the whole table.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the envelope's `meta` object, where `total_count` is the number of records matching the filters before pagination and `has_more` indicates whether records remain beyond the current page.

### 2.4. Record Identity, Audit Stamps and Immutable Registers

Every record the API creates receives an `id`: a server-minted UUID with no type prefix and no embedded meaning. Every record also receives a `created_at`, an ISO 8601 UTC timestamp with three fractional digits, marking the moment the record was written. Audit stamps are the only instants that always carry three fractional digits; every *domain* instant the API renders — a supplied `effective_on`, `sampled_on`, `applied_on` or `transferred_on` echoed back, or a server-stamped `certified_at`, `approved_at`, `conducted_on`, `oral_notified_at`, deadline or coverage date — is rendered with three fractional digits only when its millisecond part is non-zero and with no fractional part at all otherwise, so a supplied `2026-01-01T00:00:00.000Z` reads back as `2026-01-01T00:00:00Z`.

Most records additionally carry two mutable audit fields. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits refreshed on every **explicit** mutation of the record — a field the request itself writes, or a status transition the server drives on its own initiative as part of a cascade — and `version` is an integer that starts at 1 and increments by one on exactly those mutations. A purely **derived** recomputation is deliberately silent: rewriting a ledger aggregate (`applied_gallons_to_date`, `remaining_gallons`, `cumulative_outflow_gallons`, `committed_outflow_gallons`, `current_volume_gallons`, `available_capacity_gallons`), a days-of-storage figure, a field's `last_application_on`, an operation's animal-unit, production, `recorded_annual_manure_gallons`, posture or counter fields, or a hauler's `hauler_status`, updates the value in place and moves neither `updated_at` nor `version`. Operations, haulers, permits, nutrient management plans, fields, field nutrient budgets, manure storage structures, land application records, manure transfers, incident reports, inspections and annual reports all carry `updated_at` and `version`.

Two record kinds are **immutable registers**: a soil test and a storage inspection are written once, are never edited, and consequently carry only `id` and `created_at`. Neither `updated_at` nor `version` exists on them at all, and their absence is deliberate rather than an omission.

### 2.5. The Logical Clock

The server holds a single logical clock in UTC. Its value at startup is exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time. Every timestamp the server stamps on its own — a certification instant, an approval instant, an acknowledgement instant, a submission instant — is read from this clock, and every temporal comparison in this document ("is the renewal window open", "has the license lapsed", "is this record future-dated") is made against it.

A `ComplianceAdmin` may set the clock to a supplied `to_iso8601` instant, which may be earlier than the clock's current value as freely as later; the assignment itself is unconditional. Doing so is not a passive assignment; it runs four checkpoints in the same request and reports what moved, returning the new `current_utc` together with `permits_expired_count`, `haulers_lapsed_count`, `storages_recomputed_count` and `operations_recomputed_count`. The first two count only records this request actually moved — permits that this call drove into `EXPIRED`, and haulers whose `hauler_status` was something other than `LAPSED` before the call and is `LAPSED` after it — while the last two are simply the number of storage structures and the number of operations that exist in the system, counted whether or not any of their values changed. The checkpoints are coverage expiry, hauler licence lapse, soil-test validity re-evaluation, and the seasonal recomputation of storage days of capacity; each is described where its business rules live, in §3.2, §3.7, §3.3 and §3.5 respectively. The same request also refreshes each operation's `recorded_annual_manure_gallons`, its `animal_units`, `size_class`, `permit_required` and design production figures, and its `compliance_posture`.

### 2.6. Measurement Precision and Rounding Discipline

Unless a specific rule says otherwise, every derived quantity in this system — gallons, pounds of nutrient, acres, feet of setback, inches of freeboard, percentages and currency amounts — is rounded to **2 decimal places using round-half-up**, and the rounding is applied at each named step of a calculation rather than only at the end. Where a multi-step formula names its steps, each step's stated value is the rounded value, and the next step consumes that rounded value.

The same discipline reaches inputs. Every non-integer numeric quantity supplied in a request body is persisted rounded half up to 2 decimal places, and the calculation that reads it consumes that rounded value. Three supplied quantities are the exception, being consumed at the full precision the client sent and only *then* persisted rounded: `yield_goal` in a field nutrient budget, and `setback_maintained_ft` and `precipitation_forecast_in_24h` in a land application record — so a `precipitation_forecast_in_24h` of 0.499 is compared as 0.499 and stored as 0.50.

Four deliberate exceptions exist, and each is stated again where it applies:

- **Effective daily production** is rounded half up to 4 decimal places rather than 2, because it is a divisor and premature rounding would visibly distort a days-of-storage figure.
- **Days of storage** figures are floored to a whole day, never rounded up, and the per-structure figure is additionally clamped so it is never negative.
- **Allowable application rates** are floored to the nearest whole 100 gallons per acre, never rounded up: a computed rate of 1,999 gallons per acre becomes 1,900, and a computed rate below 100 becomes 0.
- **A budget's total allowable volume** is floored to a whole gallon.

The system also pins the **order of rounding relative to summation**. Per-event nutrient masses are rounded to 2 decimal places and persisted at the moment the event is recorded, and every annual nutrient total is the sum of those already-rounded persisted values. Summing raw unrounded masses and rounding once at the end is explicitly not the pinned order and will produce different totals.

### 2.7. Validation Order

When a single request could fail several checks, the outcome must be the error belonging to the **earliest** applicable check in the ordering below. This matters constantly: an operator whose operation has been suspended and who also submits a frozen-ground application record must see the suspension error, not the frozen-ground error, because posture gating is evaluated before agronomic safety.

1. Authentication — headers present and role recognised (`ERR_UNAUTHENTICATED`).
2. Authorisation — acting role listed for the endpoint (`ERR_UNAUTHORIZED`).
3. Ownership — an `Operator`'s `X-User-ID` matches the owning operation, and a `Hauler`'s `X-User-ID` matches the target transfer's `hauler_id` (`ERR_OWNERSHIP_VIOLATION`). This applies to every endpoint whose authorised roles include `Operator` or `Hauler` and whose target resolves to an operation-owned or hauler-assigned record.
4. Segregation of duties on inspection closure (`ERR_SEGREGATION_OF_DUTIES`).
5. Path existence — every identifier embedded in the request path resolves to an existing record, validated left to right, returning the not-found code of the failing segment.
6. Body reference existence — every foreign key supplied in the request body resolves to an existing record, validated in the declaration order of the target entity's fields, returning the not-found code of the failing field.
7. Request shape — required fields present, no unknown fields, declared types, enum members and range constraints satisfied, and the polymorphic incident-subject rule honoured (`ERR_INVALID_REQUEST`).
8. Optimistic concurrency on the parent operation (`ERR_STALE_OPERATION_VERSION`).
9. Permit coverage-state legality (`ERR_PERMIT_STATE_INVALID`).
10. Plan-state legality (`ERR_PLAN_STATE_INVALID`).
11. Storage-state legality (`ERR_STORAGE_STATE_INVALID`).
12. Application-record terminality (`ERR_EVENT_ALREADY_TERMINAL`).
13. Transfer-state legality (`ERR_TRANSFER_STATE_INVALID`).
14. Incident-state legality (`ERR_INCIDENT_STATE_INVALID`).
15. Inspection-state legality (`ERR_INSPECTION_STATE_INVALID`).
16. Annual-report-state legality (`ERR_REPORT_STATE_INVALID`).

18. Operation's permit has not expired (`ERR_PERMIT_COVERAGE_EXPIRED`).
19. Referenced plan is approved (`ERR_PLAN_NOT_APPROVED`).

Checks 1, 2 and 7 apply universally — check 7 to every creating and updating request; the rest apply only to the endpoints whose narrative in §3 names them.

Existence is all that checks 5 and 6 establish. Beyond it the server never verifies that two separately supplied identifiers agree with one another: a field nutrient budget's `field_id` need not belong to its plan's operation, an inspection's `permit_id` need not belong to its `operation_id`, a land application record's `budget_id` need not hang off the plan named by its `plan_id`, a transfer's `storage_id` need not belong to its `operation_id`, and an annual report's `plan_id` need not belong to its `operation_id`. The single exception is the budget's soil test, which must belong to the budget's own `field_id` (§3.4). Because check 6 precedes check 7, a foreign key supplied with the wrong JSON type — a number or an object where an identifier string belongs — counts as an unresolvable reference and is reported with the not-found code of its target entity rather than as a shape error.

Path existence deserves emphasis because nearly every endpoint is path-templated. Identifiers are resolved strictly left to right and the response names the *first* segment that fails, using the entity-specific code: `ERR_OPERATION_NOT_FOUND`, `ERR_HAULER_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_FIELD_NOT_FOUND`, `ERR_SOIL_TEST_NOT_FOUND`, `ERR_BUDGET_NOT_FOUND`, `ERR_STORAGE_NOT_FOUND`, `ERR_STORAGE_INSPECTION_NOT_FOUND`, `ERR_EVENT_NOT_FOUND`, `ERR_TRANSFER_NOT_FOUND`, `ERR_INCIDENT_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND` or `ERR_REPORT_NOT_FOUND`. The same catalogue serves body-supplied foreign keys, and an unresolvable `supersedes_plan_id` is reported as `ERR_PLAN_NOT_FOUND` just like an unresolvable `plan_id`.

### 2.8. Optimistic Concurrency on the Operation Record

Filing a nutrient management plan is the one write in this system that is guarded by optimistic concurrency, because a plan's agronomic content is only defensible against the herd size, storage days and compliance posture that the author actually observed. Creating a nutrient management plan therefore requires a non-optional `expected_operation_version` field in the request body, carrying the client's last observed `version` of the target `Operation`. If that value does not equal the operation's current `version` — because any other writer has advanced it since the client read it — the create is rejected with `ERR_STALE_OPERATION_VERSION` and HTTP 412, and nothing is written. When the value matches, the plan is created and the operation's own `version` is incremented by one as part of the same write, so the same token cannot be replayed for a second plan.

No other endpoint takes a version field. Endpoints not named here perform no concurrency check of any kind, and only two writes in the whole API ever advance an `Operation`'s `version`: the operation update of §3.1 and this plan create. Every other write that touches an operation — recording an intake, recording or voiding a land application, initiating or settling a transfer, filing an incident, issuing a notice, registering a storage structure, setting the clock — leaves the operation's `version` exactly where it was, because those writes only recompute derived values on it.

### 2.9. Compliance Posture: the System-Wide Gate

Each operation carries a single derived enforcement signal, `compliance_posture`, whose value is one of `OPEN`, `RESTRICTED` or `SUSPENDED`. It is recomputed on every write that changes an inspection's status, a permit's compliance status, a storage structure's status or an incident's status, and again whenever the logical clock is set. Because the recomputation is a pure function of those inputs and is idempotent, the server also re-runs it — harmlessly — on every other write that refreshes an operation's derived figures, including an operation update, a storage registration or intake, a land application record or void, and any transfer transition.

Two counters feed it. `open_finding_count` is the number of inspections of the operation whose status is `NOV_ISSUED` or `RESPONSE_SUBMITTED`. `open_discharge_incident_count` is the number of incident reports of the operation whose `incident_type` is `DISCHARGE` or `SPILL` and whose `incident_status` is `OPEN`, `NOTIFIED` or `WRITTEN_SUBMITTED`. Both default to 0 on a newly registered operation.

The posture is then determined in this fixed order — the suspending test is evaluated first, so a suspended posture is never downgraded to merely restricted by a finding that arrives at the same time:

- `SUSPENDED` when `open_discharge_incident_count` is at least 1, **or** any storage structure of the operation has `storage_status` equal to `OVERFLOW_IMMINENT`.
- Otherwise `RESTRICTED` when `open_finding_count` is at least 1, **or** any storage structure of the operation has `storage_status` equal to `FREEBOARD_ALERT`, **or** any permit of the operation has `compliance_status` equal to `NOTICE_ISSUED` or `CORRECTIVE_ACTION`.
- Otherwise `OPEN`.

Whenever a recomputation yields `RESTRICTED` or `SUSPENDED`, two propagation steps run, in this order and within the same request:

1. Every nutrient management plan of the operation whose `plan_status` is `APPROVED` transitions `APPROVED → REVISION_REQUIRED`, which increments that plan's `revision_count` by 1 and locks every field nutrient budget belonging to it.
2. Every manure transfer of the operation whose `transfer_status` is `INITIATED` transitions `INITIATED → SUSPENDED`, processed in ascending `created_at` order with any tie broken by insertion order, which releases each transfer's committed volume back to its source structure.

The recomputation is idempotent: a posture that is already `RESTRICTED` and stays `RESTRICTED` re-runs both steps, finds no candidate rows, and changes nothing.

Posture gates operations in two tiers. A posture of `SUSPENDED` blocks issuing coverage, completing a renewal, approving a plan, recording an intake, recording a land application and initiating a transfer, each with `ERR_OPERATION_SUSPENDED`. A stricter requirement that the posture be exactly `OPEN` applies to approving a plan, recording a land application, initiating a transfer and resuming a suspended transfer; when the posture is `RESTRICTED` those four are refused with `ERR_OPERATION_RESTRICTED`. Resuming a suspended transfer is the one of those four that carries *only* the exact-`OPEN` requirement and no separate suspension gate, so a `SUSPENDED` posture refuses a resume with `ERR_OPERATION_RESTRICTED` rather than `ERR_OPERATION_SUSPENDED`.

### 2.10. The Two Conserved-Quantity Ledgers

Two quantities in this system are ledgers rather than mere numbers, and their invariants must hold exactly after every single write.

The **field allowance ledger** lives on each field nutrient budget. Its total, `allowable_total_gallons`, is fixed when the budget is created; `applied_gallons_to_date` accumulates the volume of every non-voided land application recorded against the budget, and `remaining_gallons` is what is left. At all times `applied_gallons_to_date` plus `remaining_gallons` equals `allowable_total_gallons`. Locking a budget never disturbs any of the three values — a locked budget simply refuses new applications while preserving its history.

The **storage volume balance** lives on each manure storage structure. Intake accumulates into `cumulative_intake_gallons`; outflow accumulates into `cumulative_outflow_gallons`; a reconciliation term, `precipitation_adjustment_gallons`, absorbs the difference between what the counters predict and what an inspector actually measured. At all times `cumulative_intake_gallons` plus `precipitation_adjustment_gallons` minus `cumulative_outflow_gallons` equals `current_volume_gallons`. A separate reservation counter, `committed_outflow_gallons`, holds volume promised to transfers that have not yet left, and `available_capacity_gallons` is the operating capacity less the current volume less those commitments.

Every operation that consumes either ledger has a compensating counterpart that restores it, and those counterparts are described alongside the workflows in §3.6 and §3.7.

## 3. Business Logic & Workflows

### 3.1. Registering an Operation and Determining Whether Coverage Is Required

A `ComplianceAdmin` brings an operation onto the platform by registering it with its legal `name`, its `county` of record, the single dominant `animal_type` confined there, the `head_count` of animals confined, and the `manure_handling` system in use. Two further inputs are optional: `open_lot_area_sqft`, the uncovered lot area whose precipitation runoff reaches storage, which defaults to 0; and `has_conservation_plan`, a flag recording whether an accepted conservation plan is on file, which defaults to false. The permitting authority's `discharge_potential` determination is supplied at registration as well. `animal_type` is one of `DAIRY_COW`, `BEEF_FEEDER`, `SWINE_FINISHING` or `LAYER_HEN`; `manure_handling` is either `LIQUID` or `DRY`; `discharge_potential` is one of `NONE`, `STORMWATER_ONLY` or `CONTINUOUS`. The `head_count` must be at least 1, and `open_lot_area_sqft` must not be negative. The `county` value is carried purely for reporting and list filtering and participates in no calculation.

From those inputs the system immediately derives the operation's regulatory size. Each animal type carries an animal-unit factor: 1.4 for a `DAIRY_COW`, 1.0 for a `BEEF_FEEDER`, and 0.4 for a `SWINE_FINISHING` animal. A `LAYER_HEN` is the one type whose factor depends on the handling system — 0.033 under `LIQUID` handling and 0.0125 under `DRY` handling. The operation's `animal_units` is the `head_count` multiplied by that factor, rounded half up to 2 decimal places. The resulting `size_class` is `LARGE` when `animal_units` is at least 1,000; `MEDIUM` when `animal_units` is at least 300 but below 1,000; and `SMALL` otherwise. Both thresholds are inclusive lower bounds, so an operation computing to exactly 1,000.00 animal units is `LARGE`, not `MEDIUM`.

Whether coverage is required, recorded as `permit_required`, then depends on size class and discharge pathway together. A `LARGE` operation always requires coverage. A `MEDIUM` operation requires coverage when its `discharge_potential` is `STORMWATER_ONLY` or `CONTINUOUS`, and not when it is `NONE`. A `SMALL` operation requires coverage only when its `discharge_potential` is `CONTINUOUS`.

The same registration derives the operation's **design manure production**, the figure that anchors both plan sizing and the annual mass balance. Each animal type has an annual per-head volume: 9,000 gallons for a `DAIRY_COW`, 3,600 for a `BEEF_FEEDER`, 1,400 for a `SWINE_FINISHING` animal and 30 for a `LAYER_HEN`. A dilution factor of 1.15 applies under `LIQUID` handling and 1.0 under `DRY` handling, reflecting the wash and flush water that a liquid system adds. Separately, the uncovered lot contributes precipitation: the lot precipitation volume is `open_lot_area_sqft` multiplied by a net annual precipitation depth of 0.9 feet and then by 7.4805 gallons per cubic foot, rounded half up to 2 decimal places. `design_annual_manure_gallons` is the `head_count` multiplied by the per-head volume multiplied by the dilution factor, plus that lot precipitation volume, the sum rounded half up to 2 decimal places. `daily_production_gallons` is `design_annual_manure_gallons` divided by 365, rounded half up to 2 decimal places. A newly registered operation starts with `recorded_annual_manure_gallons` and `design_storage_days` at 0, both counters at 0, and a `compliance_posture` of `OPEN`. The `recorded_annual_manure_gallons` field persisted on the operation record always covers the calendar year of the logical clock, whatever year a particular read or report asks about.

An `Operator` or a `ComplianceAdmin` may later revise the operation: `county`, `head_count`, `manure_handling`, `open_lot_area_sqft`, `discharge_potential` and `has_conservation_plan` are all individually updatable, and no other field is — `name` and `animal_type` are fixed at registration, and naming either of them, or any field the entity does not declare, is refused with `ERR_INVALID_REQUEST`. A field supplied explicitly as `null` is ignored rather than rejected, and an update that omits every field, or that supplies values identical to the ones already stored, is still accepted and still bumps the version. Any such revision re-derives `animal_units`, `size_class`, `permit_required`, `design_annual_manure_gallons` and `daily_production_gallons`; recomputes the operation's `design_storage_days`; recomputes `days_of_storage_available` on every storage structure of the operation, since the daily production figure is the denominator of both; and increments the operation's `version` by 1. That version bump is exactly what a stale `expected_operation_version` token will collide with, as described in §2.8.

Alongside the raw record, the API offers a **nutrient summary** read that puts the design estimate and the recorded reality side by side for one calendar year. It accepts an optional `basis` selector, which is either `DESIGN_BASIS` or `RECORDS_BASIS` and defaults to `DESIGN_BASIS`, and an optional `year`, which defaults to the calendar year of the logical clock; a `basis` outside those two strings, or a `year` that is not an integer, is refused with `ERR_INVALID_REQUEST`. The selector does not filter the payload — both figures are always computed and always present, and the response merely echoes the selected `basis` and the resolved `year` back alongside them. The design basis derives volume purely from `head_count`, the per-head coefficient, the dilution factor and lot precipitation, and ignores every record ever filed; the records basis derives volume purely from persisted records and ignores `head_count` entirely, so changing the herd does not move it while voiding an application record does. The records figure, `recorded_annual_manure_gallons`, is the sum of `gallons_applied` across land application records whose owning plan belongs to this operation, whose `event_status` is `RECORDED` or `VERIFIED`, and whose `applied_on` falls in the selected UTC calendar year, plus the sum of `gallons_transferred` across transfers of this operation whose `transfer_status` is `ACKNOWLEDGED` or `COMPLETED` and whose `transferred_on` falls in that same year. The summary response also breaks those two contributions out as `recorded_land_applied_gallons` and `recorded_transferred_gallons`, reports `total_n_applied_lbs` and `total_p2o5_applied_lbs` for the year, and echoes `design_annual_manure_gallons`, `design_storage_days` and `compliance_posture`. Operations may also be listed with filters on `county`, `size_class` and `compliance_posture`.

### 3.2. Permit Coverage: Application, Issuance, Renewal, Expiry

An `Operator` drafts a coverage application against its own operation by supplying the `operation_id`, the `permit_type` — either `INDIVIDUAL` or `GENERAL` — and the requested `effective_on`, the first instant of coverage. A freshly drafted application is born with `coverage_status` of `DRAFT_APPLICATION` and, on the independent compliance dimension, `compliance_status` of `IN_GOOD_STANDING`.

These two dimensions live on the same permit record but advance entirely independently: a coverage transition never writes `compliance_status`, and a compliance transition never writes `coverage_status`. The coverage dimension moves through `DRAFT_APPLICATION`, `SUBMITTED`, `COVERED`, `RENEWAL_PENDING` and finally the terminal `EXPIRED`. The compliance dimension cycles among `IN_GOOD_STANDING`, `NOTICE_ISSUED` and `CORRECTIVE_ACTION`, and is driven solely by inspection activity on the same operation, as described in §3.8.

Submission by the `Operator` advances the coverage dimension `DRAFT_APPLICATION → SUBMITTED`. The operation's `permit_required` determination is carried for reporting only and is *not* a precondition of submission: an operation whose `permit_required` is false may still draft and submit an application. Submission does enforce non-overlap: no other permit of the same operation whose `coverage_status` is `SUBMITTED`, `COVERED` or `RENEWAL_PENDING` may have a coverage interval that intersects the interval this application is requesting. A permit that has not yet been issued has no `expiration_on`, so the interval attributed to it — both the interval this application requests and the interval of any other merely `SUBMITTED` permit it is compared against — runs from that permit's `effective_on` to that instant plus the 5-year coverage term. Coverage intervals are half-open — they run from `effective_on` up to but not including `expiration_on` — so two intervals that merely touch at an endpoint do not intersect and both may stand. A genuine intersection is refused with `ERR_PERMIT_COVERAGE_OVERLAP`.

A `StateReviewer` issues coverage, advancing `SUBMITTED → COVERED`, provided the operation's posture is not `SUSPENDED`. Issuance is what stamps the term: `expiration_on` becomes `effective_on` plus a coverage term of 5 years; `renewal_window_opens_on` becomes `expiration_on` minus 180 days; and `renewal_due_on` becomes `expiration_on` minus 90 days. The two renewal dates are computed in whole UTC days and the five-year term by calendar-year replacement, both preserving the time of day, so an `effective_on` of 1 January 2026 yields an `expiration_on` of 1 January 2031, a `renewal_window_opens_on` of 5 July 2030 and a `renewal_due_on` of 3 October 2030 — and an `effective_on` of 29 February yields an `expiration_on` of 28 February five years later, the only day on which the replacement has to give ground. A freshly drafted permit carries `expiration_on`, `renewal_window_opens_on`, `renewal_due_on`, `renewal_submitted_at` and all six fee fields as null, with `is_late_renewal` false, until the transitions that stamp them run.

Renewal is initiated by the `Operator` and advances `COVERED → RENEWAL_PENDING`. It is admissible only once the logical clock has reached or passed `renewal_window_opens_on`; an earlier attempt is refused with `ERR_RENEWAL_WINDOW_NOT_OPEN`. Initiation stamps `renewal_submitted_at` from the logical clock and sets `is_late_renewal` to true exactly when `renewal_submitted_at` is strictly later than `renewal_due_on`.

Initiation is also the moment the **renewal fee** is assessed, in six steps whose order is pinned because the discount tier is keyed on the pre-discount amount while the late surcharge is keyed on the post-discount amount. Keying the surcharge on the pre-discount amount instead produces a different total and is wrong.

1. `gross_fee` is a base fee for the operation's `size_class` — 150 for `SMALL`, 400 for `MEDIUM`, 900 for `LARGE` — plus the operation's `animal_units` multiplied by a per-animal-unit charge of 0.45, the sum rounded half up to 2 decimal places.
2. `conservation_discount_pct` is 0.00 when the operation's `has_conservation_plan` is false, regardless of amount. When it is true, the percentage is keyed on `gross_fee`: 0.00 when `gross_fee` is below 500; 0.05 when `gross_fee` is at least 500 and below 1,500; and 0.10 when `gross_fee` is at least 1,500. Both tier floors are inclusive lower bounds.
3. `conservation_discount_amount` is `gross_fee` multiplied by `conservation_discount_pct`, rounded half up to 2 decimal places.
4. `net_fee` is `gross_fee` less `conservation_discount_amount`, rounded half up to 2 decimal places.
5. `late_surcharge_amount` is `net_fee` multiplied by 0.25, rounded half up to 2 decimal places, when `is_late_renewal` is true; it is exactly 0.00 when `is_late_renewal` is false.
6. `total_due` is `net_fee` plus `late_surcharge_amount`, rounded half up to 2 decimal places.

A `StateReviewer` completes the renewal, closing the coverage cycle `COVERED → RENEWAL_PENDING → COVERED`. Completion requires two things, tested in exactly this order: the operation's posture must not be `SUSPENDED`, and the operation must have at least one nutrient management plan whose `plan_status` is `APPROVED` — an operation cannot roll its coverage forward on the strength of a plan nobody has approved. This is the one endpoint where the posture gate of §2.7's check 21 is evaluated *before* the approved-plan gate of check 19, so an operation that is both suspended and planless sees `ERR_OPERATION_SUSPENDED`. Completion advances `effective_on` to what was previously `expiration_on`, sets a new `expiration_on` 5 years after that new `effective_on`, and recomputes `renewal_window_opens_on` and `renewal_due_on` from the new `expiration_on` using the same 180-day and 90-day offsets; it leaves `renewal_submitted_at`, `is_late_renewal` and the whole six-field fee breakdown exactly as initiation assessed them.

Expiry is a clock-driven system transition, not an operator action. When the logical clock is set to an instant at or after a permit's `expiration_on`, that permit moves to `EXPIRED` from either `COVERED` or `RENEWAL_PENDING` — an unfinished renewal does not extend coverage. Because the coverage interval is half-open, an instant exactly equal to `expiration_on` is already outside coverage and triggers expiry. The count of permits moved this way is what the clock response reports as `permits_expired_count`.

Coverage state is a precondition elsewhere. Certifying a plan and conducting an inspection both require the referenced permit to be in `COVERED` or `RENEWAL_PENDING`, and refuse with `ERR_PERMIT_COVERAGE_REQUIRED` otherwise. Recording a land application and initiating a transfer both require unexpired coverage, refusing with `ERR_PERMIT_COVERAGE_EXPIRED`, but they look at different things. A land application record is tested against the single permit named by its own plan's `permit_id`, and fails when that permit's `coverage_status` is `EXPIRED` (a plan whose `permit_id` no longer resolves simply passes). A transfer is tested against the operation's whole permit collection, and fails only when the operation has at least one permit and *every* one of them is `EXPIRED`; an operation with no permit at all, or with one non-expired permit among several expired ones, passes. Any attempt to drive a coverage transition from a state where it is not declared — submitting something already submitted, issuing coverage on a draft, initiating a renewal from `RENEWAL_PENDING`, completing a renewal that was never initiated — is refused with `ERR_PERMIT_STATE_INVALID`. Permits may be listed filtered by `operation_id`, `coverage_status` and `compliance_status`.

### 3.3. The Land Base: Fields, Setbacks and Soil Tests

Land is registered field by field by an `Operator` or a `CertifiedPlanner`, each field naming its `operation_id` and carrying an operator label in `field_name`. The physical description comprises `total_acres`, which must be greater than 0; `distance_to_water_ft`, the shortest distance from the field edge to surface water, which may not be negative; `has_tile_inlet`, a flag for the presence of a surface tile inlet that defaults to false; `slope_pct`, the dominant slope percentage, which may not be negative; and `water_frontage_ft`, the length of field boundary that adjoins surface water, which may not be negative either.

Registration derives the field's setback geometry and its usable acreage. A base setback is selected by a strict precedence: a field with a tile inlet takes 300 feet regardless of anything else, because a tile inlet is a direct conduit to surface water; a field with no tile inlet whose `distance_to_water_ft` is 200 feet or less takes 200 feet; and every other field takes 100 feet. A slope adder of 100 feet is then added when `slope_pct` is strictly greater than 6, so a field at exactly 6 percent slope adds nothing. `required_setback_ft` is the base setback plus that adder. The setback strip is then converted to acreage: `excluded_acres` is `required_setback_ft` multiplied by `water_frontage_ft`, divided by 43,560 square feet per acre, rounded half up to 2 decimal places. `net_applicable_acres` is `total_acres` less `excluded_acres`, rounded half up to 2 decimal places. A field's `last_application_on` starts null and thereafter tracks the `applied_on` of the most recent non-voided land application recorded on that field — that is, the latest among records whose `event_status` is `RECORDED` or `VERIFIED` — reverting to null when no such record remains. Fields may be listed filtered by `operation_id`.

Soil tests are immutable laboratory records, filed by an `Operator` or a `CertifiedPlanner` against a field named by `field_id`. Each records `sampled_on`, the instant the sample was drawn; `lab_name`, the laboratory that ran the analysis; `soil_test_p_ppm`, the Bray-1 phosphorus concentration in parts per million; `soil_test_k_ppm`, the potassium concentration in parts per million; and `organic_matter_pct`, the soil organic matter percentage. None of the three measurements may be negative, and `sampled_on` may not be later than the logical clock — a future-dated sample is refused with `ERR_FUTURE_DATED_RECORD`.

Filing a soil test derives its phosphorus index. `p_index` is `soil_test_p_ppm` multiplied by one plus the parent field's `slope_pct` divided by 100, rounded half up to 2 decimal places — so steeper ground converts the same measured concentration into a higher runoff risk index. `p_index_category` follows from inclusive lower bounds: `VERY_HIGH` when `p_index` is at least 100; `HIGH` when it is at least 50 but below 100; `MEDIUM` when it is at least 20 but below 50; and `LOW` otherwise. A `p_index` of exactly 50.00 is therefore `HIGH`, not `MEDIUM`.

A soil test also carries `is_valid`, which is true while the logical clock is strictly earlier than four years after `sampled_on`. This flag is re-evaluated on every read and again whenever the logical clock is set, so a test that was valid yesterday can be stale today with no write having occurred. Soil tests may be listed filtered by `field_id`.

### 3.4. Nutrient Management Plans, Field Budgets and the Allowable Rate

A nutrient management plan is the annual agronomic contract between an operation and the agency. Either an `Operator` or a `CertifiedPlanner` may file one, naming the `operation_id`, the `permit_id` under which it is filed, and the `plan_year` it governs. The plan declares `allowed_application_methods`, a non-empty subset of `SURFACE_BROADCAST`, `INCORPORATED_24H`, `INJECTION` and `IRRIGATION`, being the methods the certifying planner is willing to authorise — a repeated member is collapsed rather than rejected, and the stored array preserves the order in which each member first appeared; and `winter_application_allowed`, a flag defaulting to false that determines whether application is permitted at all during December, January and February. A revision names its predecessor through `supersedes_plan_id`, which is null for a first plan. Every create must also carry the `expected_operation_version` token described in §2.8.

A plan's `plan_status` cycles through `DRAFT`, `CERTIFIED`, `SUBMITTED`, `APPROVED`, `REVISION_REQUIRED` and the terminal `SUPERSEDED`. New plans start in `DRAFT` with `revision_count` at 0.

Field nutrient budgets are the plan's line items and may only be added by a `CertifiedPlanner` while the plan is in `DRAFT` or in `APPROVED`; adding one to a plan in any other state — `CERTIFIED`, `SUBMITTED`, `REVISION_REQUIRED` or `SUPERSEDED` — is refused with `ERR_PLAN_STATE_INVALID`. A budget names the `plan_id` it belongs to, the `field_id` it rations, and the `soil_test_id` whose phosphorus index category will set the phosphorus allowance. Only the named soil test participates — other tests on the same field are ignored entirely — and that test must have `is_valid` true and must belong to the same field as the budget, or the request is refused with `ERR_NO_VALID_SOIL_TEST`. The agronomic inputs are the `crop` planned for the plan year, one of `CORN_GRAIN`, `SOYBEAN`, `ALFALFA` or `GRASS_HAY`; the `yield_goal`, expressed in bushels per acre for `CORN_GRAIN` and `SOYBEAN` and in tons per acre for `ALFALFA` and `GRASS_HAY`, which must be greater than 0; the `previous_crop` harvested in the prior year, which is one of the same four crops or `NONE`; and the `planned_application_method`, one of the four application methods, which fixes the nitrogen availability the budget assumes.

The **allowable rate** is then derived in nine steps, evaluated strictly in the order below, with every step persisted. The manure nutrient concentrations depend on an animal group taken from the owning operation's `animal_type`: `DAIRY_COW` maps to the dairy group, `BEEF_FEEDER` to the beef group, `SWINE_FINISHING` to the swine group and `LAYER_HEN` to the layer group.

1. `crop_n_need_lbs` is a per-unit nitrogen requirement for the crop multiplied by `yield_goal`, rounded half up to 2 decimal places. The per-unit requirements are 1.1 pounds per bushel for `CORN_GRAIN`, 45 pounds per ton for `GRASS_HAY`, and 0 for both `SOYBEAN` and `ALFALFA`, which fix their own nitrogen.
2. `legume_credit_lbs` is the nitrogen carried over from the previous crop: 40 pounds after `SOYBEAN`, 100 pounds after `ALFALFA`, and 0 after `CORN_GRAIN`, after `GRASS_HAY`, or when `previous_crop` is `NONE`.
3. `adjusted_n_need_lbs` is `crop_n_need_lbs` less `legume_credit_lbs`, rounded half up to 2 decimal places, with any negative result replaced by 0.
4. `crop_p_removal_lbs` is a per-unit phosphate removal figure for the crop multiplied by `yield_goal`, rounded half up to 2 decimal places. The removal figures are 0.37 pounds per bushel for `CORN_GRAIN`, 0.8 pounds per bushel for `SOYBEAN`, 12 pounds per ton for `ALFALFA` and 13 pounds per ton for `GRASS_HAY`.
5. `p_allowance_lbs` is `crop_p_removal_lbs` multiplied by a multiplier keyed on the referenced soil test's `p_index_category`, rounded half up to 2 decimal places. The multiplier is 4.0 for `LOW`, 2.0 for `MEDIUM`, 1.0 for `HIGH` and 0.0 for `VERY_HIGH` — soil already saturated with phosphorus gets no phosphate allowance at all.
6. The plant-available nitrogen delivered per thousand gallons of manure is a manure nitrogen concentration for the animal group — 24 pounds per thousand gallons for dairy, 32 for beef, 40 for swine, 60 for layer — multiplied by an availability factor keyed on `planned_application_method` — 0.65 for `INJECTION`, 0.55 for `INCORPORATED_24H`, 0.40 for `SURFACE_BROADCAST` and 0.35 for `IRRIGATION` — the product rounded half up to 2 decimal places. `allowable_n_rate_gal_per_acre` is `adjusted_n_need_lbs` divided by that available-nitrogen figure and multiplied by 1,000, then floored to the nearest whole multiple of 100.
7. `allowable_p_rate_gal_per_acre` is `p_allowance_lbs` divided by the manure phosphate concentration for the animal group — 10 pounds per thousand gallons for dairy, 16 for beef, 28 for swine, 45 for layer — multiplied by 1,000, then floored to the nearest whole multiple of 100.
8. `allowable_rate_gal_per_acre` is whichever of the two limits is smaller. `binding_basis` records which limit bound: it is `NITROGEN` when `allowable_n_rate_gal_per_acre` is less than or equal to `allowable_p_rate_gal_per_acre`, and `PHOSPHORUS` otherwise — so a tie is attributed to nitrogen.
9. `allowable_total_gallons` is `allowable_rate_gal_per_acre` multiplied by the field's `net_applicable_acres`, floored to a whole gallon. `applied_gallons_to_date` starts at 0 and `remaining_gallons` starts equal to `allowable_total_gallons`.

If the selection in step 8 yields a rate of 0 — a `VERY_HIGH` phosphorus index zeroes the phosphate allowance, and a legume crop can zero the nitrogen need — the budget is not created; the request is refused with `ERR_ZERO_ALLOWABLE_RATE`, because a budget that authorises nothing is not a budget.

Every budget is born with `budget_status` of `LOCKED`, and that is true even when it is filed against a plan that is already `APPROVED`. Only plan approval activates budgets, so a budget added after approval remains `LOCKED` until the plan has been revised and approved again. Budgets may be listed filtered by `plan_id`, `field_id`, `soil_test_id` and `budget_status`.

Certification by a `CertifiedPlanner` advances the plan `DRAFT → CERTIFIED` and rests on three preconditions. The plan's permit must be in `COVERED` or `RENEWAL_PENDING`. At least one field nutrient budget must exist for the plan, or the request is refused with `ERR_NO_FIELD_BUDGETS`. And the operation's `design_storage_days` must be at least 180 — a full winter-plus of storage — or the request is refused with `ERR_INSUFFICIENT_STORAGE_DAYS`. Certification stamps `certifying_planner_user_id` with the acting planner's `X-User-ID` and `certified_at` with the logical clock.

The `Operator` then files the certified plan with the agency, advancing `CERTIFIED → SUBMITTED`; this is admissible only when `certifying_planner_user_id` is not null. A `StateReviewer` disposes of a submitted plan in one of two ways, and the two are strict mirrors of each other. Approval advances `SUBMITTED → APPROVED`, requires the operation's posture to be exactly `OPEN`, stamps `approved_at` from the logical clock, sets `budget_status` to `ACTIVE` on every field nutrient budget of the plan, and — when the plan names a `supersedes_plan_id` — transitions that referenced predecessor `APPROVED → SUPERSEDED`, which in turn sets `budget_status` to `LOCKED` on every budget of the predecessor. Requiring revision advances `SUBMITTED → REVISION_REQUIRED`, increments `revision_count` by 1, and sets `budget_status` to `LOCKED` on every field nutrient budget of the plan — which in practice changes nothing, since a submitted plan's budgets are already locked — while leaving all three ledger figures untouched.

A plan in `REVISION_REQUIRED` returns to `DRAFT` when a `CertifiedPlanner` revises it, which is also the only way to edit `plan_year`, `allowed_application_methods` or `winter_application_allowed` after creation. Revision is admissible while the plan is in `DRAFT` or `REVISION_REQUIRED`, sets `plan_status` to `DRAFT`, and clears both `certifying_planner_user_id` and `certified_at` — a revised plan must be certified afresh. It clears nothing else: `revision_count`, `approved_at`, `supersedes_plan_id` and every budget of the plan are left exactly as they stood, an omitted or explicitly null revisable field leaves its stored value in place, and a revision that supplies no fields at all is still accepted and still returns the plan to `DRAFT`. This closes the plan cycle `DRAFT → CERTIFIED → SUBMITTED → APPROVED → REVISION_REQUIRED → DRAFT`.

The third route out of `APPROVED` is not an operator action at all: it is the compliance cascade of §2.9, which drives an approved plan to `REVISION_REQUIRED`, increments its `revision_count` by 1, and sets `budget_status` to `LOCKED` on every budget of the plan while leaving `allowable_total_gallons`, `applied_gallons_to_date` and `remaining_gallons` untouched, so the field allowance ledger's invariant survives the lockdown intact. Any transition attempted from a `plan_status` where it is not declared is refused with `ERR_PLAN_STATE_INVALID`. Plans may be listed filtered by `operation_id`, `permit_id`, `supersedes_plan_id`, `plan_status` and `plan_year`.

### 3.5. Manure Storage: Capacity, Freeboard and Structure Condition

An `Operator` registers each storage structure against its `operation_id` with an operator label in `structure_name` and a `structure_type` of `EARTHEN_LAGOON`, `CONCRETE_TANK` or `STACKING_PAD`. Geometry is given as `surface_area_sqft`, the plan-view surface area, which must be greater than 0, and `total_depth_in`, the total inside depth in inches from floor to top of berm or wall, which must also be greater than 0. `required_freeboard_in`, the freeboard that must be preserved above the liquid surface, defaults to 24 inches; it may not be negative and must be strictly less than `total_depth_in`.

Three capacities follow directly from that geometry, each computed with 7.4805 gallons per cubic foot and rounded half up to 2 decimal places. `design_capacity_gallons` is `surface_area_sqft` multiplied by `total_depth_in` divided by 12 to convert inches to feet, multiplied by the gallons-per-cubic-foot factor. `freeboard_reserve_gallons` is the same product computed with `required_freeboard_in` in place of the total depth. `operating_capacity_gallons` is `design_capacity_gallons` less `freeboard_reserve_gallons` — the volume the structure may lawfully hold. A new structure begins with `cumulative_intake_gallons`, `precipitation_adjustment_gallons`, `cumulative_outflow_gallons`, `current_volume_gallons` and `committed_outflow_gallons` all at 0, `available_capacity_gallons` equal to its operating capacity, `last_inspected_on` null, and `storage_status` of `IN_SERVICE`. Registration also writes the structure's own `days_of_storage_available` and rewrites the owning operation's `design_storage_days`, since the operation-wide figure sums the operating capacity of every structure it owns.

Recording an intake is how manure arriving from the barn or lot enters the ledger: the `Operator` supplies the volume of `gallons` entering the structure, which must be greater than 0 and is the only field the request accepts, and which is added to `cumulative_intake_gallons`, after which `current_volume_gallons`, `available_capacity_gallons` and `days_of_storage_available` are recomputed. An intake is refused with `ERR_STORAGE_OPERATING_CAPACITY_EXCEEDED` when the resulting `current_volume_gallons` would exceed `operating_capacity_gallons`, and is refused with `ERR_OPERATION_SUSPENDED` when the operation's posture is `SUSPENDED`. `current_volume_gallons` is always `cumulative_intake_gallons` plus `precipitation_adjustment_gallons` less `cumulative_outflow_gallons`, and `available_capacity_gallons` is always `operating_capacity_gallons` less `current_volume_gallons` less `committed_outflow_gallons`, both rounded half up to 2 decimal places.

**Days of storage** translate volume into time, which is the unit regulators actually think in. Effective daily production is the operation's `daily_production_gallons` multiplied by a seasonal factor, rounded half up to 4 decimal places. That seasonal factor is 1.35 when the structure is an `EARTHEN_LAGOON` or a `STACKING_PAD` and the logical clock's UTC month is November, December, January, February or March — the months in which neither type can be emptied and both keep catching precipitation — and 1.0 in every other case; a `CONCRETE_TANK` never carries the seasonal factor. A structure's own `days_of_storage_available` is the greater of zero and its `available_capacity_gallons`, divided by that effective daily production and floored to a whole day, so the figure shrinks as the structure fills and grows again when a transfer is suspended or cancelled. The operation-wide `design_storage_days` is the sum of `operating_capacity_gallons` across every storage structure of the operation, regardless of each structure's `storage_status`, divided by an effective daily production computed the same way and floored to a whole day. Because that operation-wide divisor cannot belong to any one structure, it takes a single operation-wide seasonal factor: the factor of the *first-registered* structure of the operation whose `structure_type` is `EARTHEN_LAGOON` or `STACKING_PAD`, and 1.0 when the operation owns no structure of either type — so one earthen lagoon puts the whole operation's design figure on the winter factor, while an operation of nothing but concrete tanks never carries it. Because the figure ignores current contents and commitments entirely, it moves only with herd size, structure geometry and the clock's month — and it is this figure that plan certification tests against the 180-day minimum.

A **capacity projection** read exposes both bases for one structure. It takes an optional `basis` selector of either `AVAILABLE_BASIS` or `DESIGN_BASIS`, defaulting to `AVAILABLE_BASIS` and refused with `ERR_INVALID_REQUEST` when it is anything else, and returns the selected `basis` echoed back, the `seasonal_factor` and `effective_daily_gallons` in play, the structure's `operating_capacity_gallons` and `available_capacity_gallons`, the resulting `days_of_storage` for the selected basis, and `min_storage_days_met`, indicating whether that same selected basis satisfies the 180-day threshold. Unlike the operation-wide `design_storage_days`, this read always uses the seasonal factor of the *structure named in the path*, for both bases: `AVAILABLE_BASIS` divides that structure's `available_capacity_gallons`, clamped up to 0 when negative, by that structure's effective daily production, while `DESIGN_BASIS` divides the operation-wide sum of every structure's `operating_capacity_gallons` by the very same divisor — so asking a concrete tank for a design projection in January reports more days than the operation's own `design_storage_days` field does when the operation also owns a lagoon. Structures may be listed filtered by `operation_id` and `storage_status`.

Weekly structure inspections are immutable records filed by an `Operator` or a `ComplianceAdmin` against the `storage_id` of the structure inspected. Each records `inspected_on`, the instant of the inspection, which may not be later than the logical clock; `inspector_name`, the person who performed it; `measured_freeboard_in`, the vertical distance from the liquid surface to the top of the structure, which may not be negative and may not exceed the structure's `total_depth_in`; and `visual_condition`, the recorded state of berms, liner and outlets, being one of `NORMAL`, `SEEPAGE`, `EROSION` or `CRACKING`.

Filing an inspection converts the measured freeboard back into a volume and reconciles the ledger. Liquid depth is `total_depth_in` less `measured_freeboard_in`; `measured_volume_gallons` is `surface_area_sqft` multiplied by that liquid depth divided by 12, multiplied by 7.4805, rounded half up to 2 decimal places. `freeboard_deficit_in` is the structure's `required_freeboard_in` less `measured_freeboard_in`, with any negative result replaced by 0, rounded half up to 2 decimal places. `alert_raised` is true when `freeboard_deficit_in` is greater than 0 or `visual_condition` is anything other than `NORMAL`. The reconciliation term is then rewritten: `precipitation_adjustment_gallons` becomes `measured_volume_gallons` less `cumulative_intake_gallons` plus `cumulative_outflow_gallons`, rounded half up to 2 decimal places, which is precisely the value that makes the volume-balance invariant exact against what the inspector measured. The structure's `current_volume_gallons`, `available_capacity_gallons` and `days_of_storage_available` are then recomputed, and `last_inspected_on` is set to the greatest `inspected_on` among all inspections of the structure — normally the record just filed, but a back-dated filing leaves the field where the later reading already put it, even though that back-dated reading is still the one that rewrites the reconciliation term and drives the state change below. Storage inspections may be listed filtered by `storage_id`.

An inspection may also move the structure's state, and the two thresholds are distinct. When `measured_freeboard_in` is 6 inches or less, the structure moves to `OVERFLOW_IMMINENT` — from `IN_SERVICE` or from `FREEBOARD_ALERT` alike — and the operation's posture is recomputed to `SUSPENDED`. Otherwise, when there is a freeboard deficit at all, meaning `freeboard_deficit_in` is greater than 0 while `measured_freeboard_in` remains above 6 inches, a structure in `IN_SERVICE` moves to `FREEBOARD_ALERT` and the operation's posture is recomputed to `RESTRICTED`. Both recomputations run the propagation steps of §2.9 in full, so a single freeboard reading can revise an approved plan, lock its budgets and suspend outstanding transfers.

Returning a structure to service is an `Operator` action available from either `FREEBOARD_ALERT` or `OVERFLOW_IMMINENT`, and it is gated on evidence rather than assertion: the structure's most recent inspection — the one with the greatest `inspected_on`, ties broken by the greatest `created_at` and any remaining tie by the later insertion order — must show `freeboard_deficit_in` of 0 **and** `visual_condition` of `NORMAL`. A structure whose latest inspection still shows a deficit, or shows `SEEPAGE`, `EROSION` or `CRACKING` even with adequate freeboard, cannot come back, and neither can a structure that is already `IN_SERVICE`; all three cases are refused with `ERR_STORAGE_STATE_INVALID`. A successful return sets `storage_status` to `IN_SERVICE` and recomputes the operation's posture, which returns to `OPEN` when no other restricting condition remains.

### 3.6. Recording Land Application

Land application is where the plan meets the ground, and it is the most heavily gated write in the system. An `Operator` records each application naming the `plan_id` it falls under, the `budget_id` it debits, and the `storage_id` the manure was drawn from. The record carries `applied_on`, the instant the application occurred; `gallons_applied`, the volume, which must be greater than 0; `acres_treated`, the acres actually treated, which must be greater than 0; the `application_method` used; `setback_maintained_ft`, the setback actually left unapplied along surface water, which may not be negative; `soil_condition`, the recorded ground condition, being one of `DRY`, `MOIST`, `SATURATED`, `FROZEN` or `SNOW_COVERED`; `precipitation_forecast_in_24h`, the forecast precipitation in inches for the 24 hours after application, which defaults to 0 and may not be negative; and `applicator_name`, the person who applied the manure.

Contextual preconditions come first. The permit named by the record's own plan must not be `EXPIRED`, or the record is refused with `ERR_PERMIT_COVERAGE_EXPIRED`; no other permit of the operation is consulted. The named plan's `plan_status` must be `APPROVED`, or the record is refused with `ERR_PLAN_NOT_APPROVED`. The named budget's `budget_status` must be `ACTIVE`, or the record is refused with `ERR_BUDGET_NOT_ACTIVE`; this is the gate that catches a budget filed after its plan was approved and therefore still born `LOCKED`. The operation's posture must be exactly `OPEN`, so a `SUSPENDED` operation is refused with `ERR_OPERATION_SUSPENDED` and a `RESTRICTED` one with `ERR_OPERATION_RESTRICTED`.

The agronomic and weather safeguards follow, and they are evaluated in a fixed order so that the most serious hazard is always the one reported. Ground condition is checked first: a `soil_condition` of `FROZEN` is refused with `ERR_FROZEN_GROUND_APPLICATION`, and then a `soil_condition` of `SATURATED` with `ERR_SATURATED_SOIL_APPLICATION`. Next comes the calendar: when the UTC month of `applied_on` is December, January or February, the owning plan's `winter_application_allowed` must be true, or the record is refused with `ERR_WINTER_WINDOW_APPLICATION`. Next the forecast: `precipitation_forecast_in_24h` must be strictly less than 0.50 inches, so a forecast of exactly 0.50 inches is rejected with `ERR_PRECIPITATION_RISK`. Then the setback: `setback_maintained_ft` must be at least the field's `required_setback_ft` scaled by a method multiplier, which is 1.0 for `SURFACE_BROADCAST`, 1.5 for `IRRIGATION`, 0.5 for `INCORPORATED_24H` and 0.25 for `INJECTION` — irrigation throws droplets further and so demands half again the base strip, while injection places manure below the surface and so needs only a quarter of it. A shortfall is refused with `ERR_SETBACK_VIOLATION`.

Three temporal and referential gates come next. `applied_on` may not be later than the logical clock, or the record is refused with `ERR_FUTURE_DATED_RECORD`. The gap between `applied_on` and the field's `last_application_on` must be at least 21 days in absolute terms; the buffer is symmetric, so a back-dated record that lands inside the window of a later existing record is rejected exactly as a too-soon forward record is, while a gap of exactly 21 days is accepted. A violation is refused with `ERR_REAPPLICATION_INTERVAL_CONFLICT`. And the `application_method` must be a member of the owning plan's `allowed_application_methods`, or the record is refused with `ERR_APPLICATION_METHOD_NOT_IN_PLAN`.

The quantitative limits are checked last, in ascending order of the aggregate they protect. `acres_treated` may not exceed the field's `net_applicable_acres`, or the record is refused with `ERR_ACRES_EXCEED_NET_APPLICABLE`. The per-acre rate, `rate_gal_per_acre`, computed as `gallons_applied` divided by `acres_treated` and rounded half up to 2 decimal places, may not exceed the budget's `allowable_rate_gal_per_acre`, or the record is refused with `ERR_RATE_EXCEEDS_LIMIT`. `gallons_applied` may not exceed the budget's `remaining_gallons`, or the record is refused with `ERR_FIELD_ALLOWANCE_EXCEEDED`. Finally `gallons_applied` may not exceed the source structure's `current_volume_gallons` less its `committed_outflow_gallons` — you cannot spread manure you do not have, nor manure you have already promised to a hauler — or the record is refused with `ERR_INSUFFICIENT_STORAGE_VOLUME`.

A record that survives all of that computes its nutrient load and is written with `event_status` of `RECORDED`. The animal group is taken from the operation's `animal_type` exactly as in the budget calculation. `n_applied_lbs`, the plant-available nitrogen, is `gallons_applied` divided by 1,000, multiplied by the manure nitrogen concentration for the group — 24 pounds per thousand gallons for dairy, 32 for beef, 40 for swine, 60 for layer — multiplied by the availability factor for the `application_method` actually used — 0.65 for `INJECTION`, 0.55 for `INCORPORATED_24H`, 0.40 for `SURFACE_BROADCAST`, 0.35 for `IRRIGATION` — and rounded half up to 2 decimal places. `p2o5_applied_lbs` is `gallons_applied` divided by 1,000, multiplied by the manure phosphate concentration for the group — 10 pounds per thousand gallons for dairy, 16 for beef, 28 for swine, 45 for layer — rounded half up to 2 decimal places; no availability factor applies to phosphate. Both values are persisted in their rounded form, and every annual roll-up sums those persisted values rather than re-deriving them.

Writing the record then fans out to four other places in the same request. The budget's `applied_gallons_to_date` increases by `gallons_applied` and its `remaining_gallons` decreases by the same amount. The source structure's `cumulative_outflow_gallons` increases by `gallons_applied`, and its `current_volume_gallons`, `available_capacity_gallons` and `days_of_storage_available` are recomputed. The field's `last_application_on` is stamped with `applied_on` when that instant is later than the value already stored. And the operation's `recorded_annual_manure_gallons` is recomputed. All four effects are visible in the response to the request that caused them and in every subsequent read.

An application record has three states. It is born `RECORDED`; a `CertifiedPlanner` may verify it, advancing `RECORDED → VERIFIED`, which is admissible only while the owning plan's `plan_status` is `APPROVED` — otherwise `ERR_PLAN_NOT_APPROVED` — and which changes neither ledger. Verification is idempotent rather than single-shot: re-verifying a record that is already `VERIFIED` is accepted and simply returns it unchanged, with neither `updated_at` nor `version` moving, since only `VOIDED` is a terminal state to be defended. Verification changes no ledger because both the budget's applied total and the structure's outflow total already count `RECORDED` and `VERIFIED` records alike. Only a `ComplianceAdmin` may void a record, and voiding is available from either `RECORDED` or `VERIFIED`; attempting to verify or void a record whose `event_status` is already `VOIDED` is refused with `ERR_EVENT_ALREADY_TERMINAL`, and `VOIDED` is terminal.

Voiding is the compensating action for both conserved quantities, and the compensation is identical whichever state the record was voided from. `event_status` becomes `VOIDED`. The budget's `applied_gallons_to_date` is credited down by `gallons_applied` and its `remaining_gallons` recomputed, restoring the invariant that applied plus remaining equals `allowable_total_gallons`. The source structure's `cumulative_outflow_gallons` is credited down by `gallons_applied` and its `current_volume_gallons` and `available_capacity_gallons` recomputed, restoring the storage volume-balance invariant, with `days_of_storage_available` following. The field's `last_application_on` is recomputed from the remaining non-voided records, and the operation's `recorded_annual_manure_gallons` is recomputed as well — the voided volume leaves the records-basis total, which is exactly why that figure and the design figure can diverge. Application records may be listed filtered by `plan_id`, `budget_id`, `storage_id` and `event_status`.

### 3.7. Third-Party Manure Transfers

Manure that leaves the operation instead of going onto its own fields moves through a transfer record. Haulers themselves are registered by a `ComplianceAdmin` with a `business_name`, a state `license_number`, and a `license_expires_on` instant at which the licence lapses; `certified_applicator`, recording whether the hauler holds a certified applicator endorsement, defaults to false. A hauler's `hauler_status` is derived, not supplied: it is `ACTIVE` while the logical clock is at or before `license_expires_on` and `LAPSED` thereafter, and it is re-evaluated on every read and again whenever the logical clock is set — the clock response reports how many lapsed as `haulers_lapsed_count`. Haulers may be listed filtered by `hauler_status`.

An `Operator` initiates a transfer naming its own `operation_id`, the `storage_id` the load is drawn from, and the `hauler_id` moving it. Recipient documentation is captured up front: `recipient_name` and `recipient_address` identify the receiving party and are both mandatory non-empty strings at initiation, so the acknowledgement gate below turns in practice on `nutrient_analysis_provided` alone; `transferred_on` records the instant the load left the operation, `gallons_transferred` the volume shipped, which must be greater than 0, and `nutrient_analysis_provided`, defaulting to false, records whether the recipient received the required manure nutrient analysis sheet. Initiation requires that the operation's permit is not `EXPIRED` (`ERR_PERMIT_COVERAGE_EXPIRED`), that the referenced hauler's `hauler_status` is `ACTIVE` (`ERR_HAULER_LICENSE_LAPSED`), that `transferred_on` is not later than the logical clock (`ERR_FUTURE_DATED_RECORD`), that the operation's posture is not `SUSPENDED` (`ERR_OPERATION_SUSPENDED`) and is in fact `OPEN` (`ERR_OPERATION_RESTRICTED`), and that `gallons_transferred` does not exceed the source structure's `current_volume_gallons` less its `committed_outflow_gallons` (`ERR_INSUFFICIENT_STORAGE_VOLUME`).

Initiation computes the recipient's nutrient documentation on a deliberately different basis from a land application. Because the receiving party makes its own availability assumption, a transfer reports **total** nitrogen rather than plant-available nitrogen: `recipient_n_lbs` is `gallons_transferred` divided by 1,000, multiplied by the manure nitrogen concentration for the operation's animal group — 24 pounds per thousand gallons for dairy, 32 for beef, 40 for swine, 60 for layer — rounded half up to 2 decimal places, with no availability factor applied at all. `recipient_p2o5_lbs` is `gallons_transferred` divided by 1,000, multiplied by the manure phosphate concentration for the group — 10 for dairy, 16 for beef, 28 for swine, 45 for layer — rounded half up to 2 decimal places. The transfer is written with `transfer_status` of `INITIATED` and `recipient_ack_signed_at` null, and `gallons_transferred` is added to the source structure's `committed_outflow_gallons`, after which `available_capacity_gallons` and `days_of_storage_available` are recomputed. Committing rather than immediately debiting is what stops two pending loads from overselling the same tank.

The assigned `Hauler` acknowledges the load, advancing `INITIATED → ACKNOWLEDGED`. Acknowledgement is the recipient-documentation gate: `nutrient_analysis_provided` must be true and both `recipient_name` and `recipient_address` must be non-empty, or the request is refused with `ERR_RECIPIENT_DOCUMENTATION_MISSING`; and the hauler's own `hauler_status` must still be `ACTIVE`, or it is refused with `ERR_HAULER_LICENSE_LAPSED`. Acknowledgement stamps `recipient_ack_signed_at` from the logical clock and moves the volume from reservation to fact: `gallons_transferred` is released from the structure's `committed_outflow_gallons` and added to its `cumulative_outflow_gallons`, after which `current_volume_gallons` and `available_capacity_gallons` are recomputed. The same `Hauler` then closes out the delivery, advancing `ACKNOWLEDGED → COMPLETED`, which is admissible only when `recipient_ack_signed_at` is not null and which touches no counter.

Two paths interrupt a transfer. The compliance cascade of §2.9 drives every `INITIATED` transfer of a restricted or suspended operation to `SUSPENDED`, taking them in ascending `created_at` order, and each suspension releases that transfer's `gallons_transferred` from the structure's `committed_outflow_gallons`, after which `available_capacity_gallons` and `days_of_storage_available` are recomputed — so a compliance event visibly frees storage headroom. An `Operator` may resume a suspended transfer, advancing `SUSPENDED → INITIATED`, but only when three things hold: the operation's posture is back to exactly `OPEN` (`ERR_OPERATION_RESTRICTED`), the hauler's `hauler_status` is still `ACTIVE` (`ERR_HAULER_LICENSE_LAPSED`), and `gallons_transferred` is still no greater than the structure's `current_volume_gallons` less its `committed_outflow_gallons` (`ERR_INSUFFICIENT_STORAGE_VOLUME`) — the tank may have been emptied onto fields while the transfer sat suspended. Resuming re-commits `gallons_transferred` to `committed_outflow_gallons` and recomputes `available_capacity_gallons` and `days_of_storage_available`.

An `Operator` may cancel a transfer from either `INITIATED` or `SUSPENDED`, reaching the terminal `CANCELLED`, and the counter treatment differs between the two by exactly the amount already released. Cancelling an `INITIATED` transfer releases `gallons_transferred` from the structure's `committed_outflow_gallons`, restoring `available_capacity_gallons` to its pre-transfer value. Cancelling a `SUSPENDED` transfer leaves `committed_outflow_gallons` untouched, because suspension already released it — double-releasing would silently inflate the structure's apparent headroom. `COMPLETED` and `CANCELLED` are both terminal. Any transition attempted from a `transfer_status` where it is not declared is refused with `ERR_TRANSFER_STATE_INVALID`. Transfers may be listed filtered by `operation_id`, `storage_id`, `hauler_id` and `transfer_status`.

### 3.8. Incidents, Inspections and the Compliance Cascade

Incident reporting covers three genuinely different events behind one record, and `incident_type` — `MORTALITY`, `DISCHARGE` or `SPILL` — is the discriminator that selects both which subject the report must name and which notification rule applies. An `Operator` files a report against its `operation_id` with `discovered_at`, the instant of discovery, which may not be later than the logical clock, and a `description` narrating the event and the immediate actions taken. For a `DISCHARGE` or a `SPILL` the report must name `subject_storage_id` and must leave `subject_field_id` null; for a `MORTALITY` it must name `subject_field_id` and leave `subject_storage_id` null. Both default to null, and a subject that does not match the declared `incident_type` is refused with `ERR_INVALID_REQUEST`. Three further inputs are meaningful only for particular types: `mortality_head_count`, the animals lost, defaults to 0, may not be negative, and matters only for a `MORTALITY`; `disposal_method`, the carcass disposal route, defaults to null and is either null or one of `COMPOSTING`, `BURIAL`, `INCINERATION` or `RENDERING`, and likewise matters only for a `MORTALITY`; `released_gallons`, the volume released, defaults to 0, may not be negative, and matters only for a `DISCHARGE` or a `SPILL`, as does `reached_water`, which defaults to false and records whether the release reached surface water.

Filing derives the notification obligation. For a `DISCHARGE` or a `SPILL`, `requires_oral_notification` is true when `reached_water` is true **or** `released_gallons` is at least 1,000. For a `MORTALITY`, the threshold scales with the herd: it is the greater of 2 head and one percent of the operation's `head_count` rounded up to a whole animal, and `requires_oral_notification` is true when `mortality_head_count` is at least that threshold. When notification is required, `oral_notification_deadline_at` is 24 hours after `discovered_at` and `written_report_deadline_at` is 5 days after `discovered_at`; when it is not required, both are null. All three of those values are derived once, at filing, and are never re-derived afterwards, so later revising the operation's `head_count` does not move a mortality report's threshold or its obligation. A new report is born with `incident_status` of `OPEN`, `oral_notified_at` null and `notification_late` false, and filing recomputes the operation's `open_discharge_incident_count` and `compliance_posture` — which means any `DISCHARGE` or `SPILL` immediately suspends the operation, with all the propagation of §2.9 that entails.

An `Operator` records the oral notification, advancing `OPEN → NOTIFIED`, which is admissible only when `requires_oral_notification` is true. Recording stamps `oral_notified_at` from the logical clock and sets `notification_late` to true exactly when `oral_notified_at` is strictly later than `oral_notification_deadline_at` — a notification recorded at exactly the deadline instant is on time. The `Operator` then files the written follow-up, advancing `NOTIFIED → WRITTEN_SUBMITTED`, which is admissible only when `oral_notified_at` is not null.

A `StateReviewer` closes an incident, and there are two routes to `CLOSED`. An incident below the notification threshold — one whose `requires_oral_notification` is false — may be closed directly from `OPEN` with no notification step at all. An incident that did require notification must have reached `WRITTEN_SUBMITTED` first. Trying to close an `OPEN` incident that still requires oral notification, or driving any other undeclared incident transition, is refused with `ERR_INCIDENT_STATE_INVALID`. Either closure recomputes the operation's `open_discharge_incident_count` and `compliance_posture`, which returns to `OPEN` when no other restricting condition remains. Incident reports may be listed filtered by `operation_id`, `subject_storage_id`, `subject_field_id`, `incident_type` and `incident_status`.

Agency inspections run on a parallel track. A `StateReviewer` schedules one against an `operation_id` and the `permit_id` under which it is conducted, with `scheduled_on` giving the intended instant and `inspection_kind` being one of `ROUTINE`, `COMPLAINT` or `FOLLOW_UP`. A scheduled inspection starts with `inspection_status` of `SCHEDULED`, `findings_count` at 0, `deficiency_categories` as an empty array, and `inspector_user_id`, `conducted_on`, `response_due_on`, `corrective_action_summary` and `closed_by_user_id` all null. `scheduled_on` may fall on either side of the logical clock; no future-dating check applies to it.

Conducting the inspection advances `SCHEDULED → CONDUCTED` and is admissible only when the inspection's permit is in `COVERED` or `RENEWAL_PENDING`, failing otherwise with `ERR_PERMIT_COVERAGE_REQUIRED`. The reviewer supplies `findings_count`, the number of deficiencies recorded, which is mandatory and may not be negative, and optionally `deficiency_categories`, a subset of `RECORDKEEPING`, `FREEBOARD`, `SETBACK`, `TRANSFER_DOCUMENTATION` and `MORTALITY` which defaults to the empty array — supplied as null it is likewise stored as the empty array, a repeated member is collapsed rather than rejected, first-appearance order is preserved, and the list is never cross-checked against `findings_count`. Conducting stamps `inspector_user_id` with the reviewer's `X-User-ID` and `conducted_on` with the logical clock, alongside the supplied findings.

From `CONDUCTED` the inspection branches, and the branch is decided by the findings count alone. When `findings_count` is at least 1, a `StateReviewer` issues a notice of violation, advancing `CONDUCTED → NOV_ISSUED`; issuing on an inspection with `findings_count` of 0 is refused with `ERR_NOV_NOT_WARRANTED`. Issuance stamps `response_due_on` as `conducted_on` plus 30 days — so an inspection conducted at the start of 1 August 2026 and served with a notice is due a response by the start of 31 August 2026 — increments the operation's `open_finding_count`, and starts the compliance cascade. When `findings_count` is 0, a `StateReviewer` or a `ComplianceAdmin` may instead close the inspection directly, advancing `CONDUCTED → CLOSED` and stamping `closed_by_user_id` with the closing actor's `X-User-ID`, provided that actor differs from the recorded `inspector_user_id`. Attempting to close a `CONDUCTED` inspection whose `findings_count` is at least 1, or driving any other undeclared inspection transition, is refused with `ERR_INSPECTION_STATE_INVALID`.

The cascade that a notice of violation starts is the system's longest chain and is worth tracing end to end. Issuing the notice transitions the inspection's own permit on its compliance dimension, `IN_GOOD_STANDING → NOTICE_ISSUED`, leaving that permit's `coverage_status` entirely untouched. Because a `compliance_status` of `NOTICE_ISSUED` is a restricting condition, the operation's `compliance_posture` is recomputed and becomes `RESTRICTED`. That in turn drives every `APPROVED` plan of the operation to `REVISION_REQUIRED`, incrementing each plan's `revision_count` and locking every one of its field nutrient budgets. And that in turn suspends every `INITIATED` transfer of the operation in ascending `created_at` order, releasing each transfer's committed volume back to its source structure and recomputing that structure's `available_capacity_gallons` and `days_of_storage_available`.

The `Operator` answers a notice by filing a corrective-action response, advancing the inspection `NOV_ISSUED → RESPONSE_SUBMITTED` and storing the supplied `corrective_action_summary`. The response also advances the permit's compliance dimension `NOTICE_ISSUED → CORRECTIVE_ACTION`; the operation's posture stays `RESTRICTED`, because `CORRECTIVE_ACTION` is itself a restricting `compliance_status`.

Closing an inspection from `RESPONSE_SUBMITTED` is what unwinds the chain, and it may be done by a `StateReviewer` or a `ComplianceAdmin` provided the closing actor's `X-User-ID` differs from `inspector_user_id`. Closure sets `inspection_status` to `CLOSED`, stamps `closed_by_user_id`, and decrements the operation's `open_finding_count`. It then advances the permit's compliance dimension `CORRECTIVE_ACTION → IN_GOOD_STANDING`, but only when no other inspection of the same operation is still sitting in `NOV_ISSUED` or `RESPONSE_SUBMITTED` — one resolved finding does not clear a permit that is still carrying another. Finally the operation's `compliance_posture` is recomputed and returns to `OPEN` when no other restricting condition remains. This closes the compliance cycle `IN_GOOD_STANDING → NOTICE_ISSUED → CORRECTIVE_ACTION → IN_GOOD_STANDING`. Inspections may be listed filtered by `operation_id`, `permit_id` and `inspection_status`.

### 3.9. Annual Reporting and the Manure Mass Balance

Each calendar year an `Operator` opens an annual report naming its `operation_id`, the `plan_id` in force for the year, and the `report_year` covered. Two operator-reported figures anchor the mass balance: `beginning_storage_gallons`, the storage volume on the first day of the year, and `ending_storage_gallons`, the volume on the last day, neither of which may be negative. `variance_explanation` is an optional narrative, defaulting to null, explaining a mass-balance variance that falls outside tolerance; it may be omitted or supplied as null, but a value that is present must be a non-empty string, an empty or whitespace-only one being refused with `ERR_INVALID_REQUEST`. Only one report may exist per operation and `report_year`, whatever status the earlier one has reached; a second is refused with `ERR_REPORT_PERIOD_DUPLICATE`. A new report is born with `submitted_at`, `accepted_at` and `return_reason` all null.

Opening the report runs the **mass balance** in seven steps.

1. `recorded_land_applied_gallons` is the sum of `gallons_applied` across land application records whose owning plan belongs to this report's operation, whose `event_status` is `RECORDED` or `VERIFIED`, and whose `applied_on` falls in `report_year`. Voided records are excluded.
2. `recorded_transferred_gallons` is the sum of `gallons_transferred` across transfers of this report's operation whose `transfer_status` is `ACKNOWLEDGED` or `COMPLETED` and whose `transferred_on` falls in `report_year`. Transfers still `INITIATED`, or `SUSPENDED`, or `CANCELLED` are excluded.
3. `recorded_total_gallons` is `recorded_land_applied_gallons` plus `recorded_transferred_gallons` plus the change in storage over the year, which is `ending_storage_gallons` less `beginning_storage_gallons`, the whole sum rounded half up to 2 decimal places.
4. `mass_balance_expected_gallons` is simply the operation's `design_annual_manure_gallons` — what the herd and the lot should have produced.
5. `variance_pct` is `recorded_total_gallons` less `mass_balance_expected_gallons`, divided by `mass_balance_expected_gallons`, multiplied by 100, rounded half up to 2 decimal places.
6. `variance_classification` is `WITHIN_TOLERANCE` when the absolute value of `variance_pct` is at most 15.00, and `EXCEEDS_TOLERANCE` otherwise. The comparison is inclusive, so a `variance_pct` of exactly 15.00 or exactly -15.00 is `WITHIN_TOLERANCE`.
7. `total_n_applied_lbs` and `total_p2o5_applied_lbs` are the year's nutrient roll-ups over the same record set as step 1: the sums of the persisted, already-rounded `n_applied_lbs` and `p2o5_applied_lbs` values of those records. Because every addend is already rounded, summation order cannot change the result.

Both year windows run over the whole of `report_year` in UTC, from the first instant of 1 January of `report_year` up to but not including the first instant of 1 January of the following year.

A report's `report_status` takes one of four values — `DRAFT`, `SUBMITTED`, `ACCEPTED` and `RETURNED` — and a new report is born in `DRAFT`. The `Operator` submits it, advancing `DRAFT → SUBMITTED`, which first re-runs the entire mass balance over the current record set — a report drafted in January and submitted in March reflects March's records, not January's — and then stamps `submitted_at` from the logical clock. Submission is admissible only when `variance_classification` is `WITHIN_TOLERANCE` **or** `variance_explanation` is a non-empty string; an unexplained out-of-tolerance report is refused with `ERR_VARIANCE_EXPLANATION_REQUIRED`. The re-run precedes that gate and is not undone by it: a submission rejected for a missing explanation still leaves the seven freshly recomputed mass-balance figures persisted on the report, so a second read shows the new numbers even though `report_status` is still `DRAFT` or `RETURNED` and neither `submitted_at` nor the audit fields moved.

A `StateReviewer` disposes of a submitted report in one of two symmetric ways. Acceptance advances `SUBMITTED → ACCEPTED` and stamps `accepted_at` from the logical clock; `ACCEPTED` is terminal. Return advances `SUBMITTED → RETURNED` and stores the supplied `return_reason`. A returned report goes back to the `Operator`, who may resubmit it, advancing `RETURNED → SUBMITTED` under exactly the same variance-explanation precondition, re-running the mass balance again and re-stamping `submitted_at`. This closes the report cycle `SUBMITTED → RETURNED → SUBMITTED`. Any report transition attempted from a `report_status` where it is not declared is refused with `ERR_REPORT_STATE_INVALID`. Annual reports may be listed filtered by `operation_id`, `plan_id`, `report_year` and `report_status`.

## 4. Endpoint Definitions

Requests that bring a new record into existence return `201 Created`. Every other successful request — a state transition, an update, a read, a list, a computed projection, a clock advance — returns `200 OK`. Request and response bodies are not restated here; the fields each endpoint accepts and the effects it produces are specified in the §3 narrative for the workflow it belongs to. Every transition endpoint whose narrative names no input field accepts no input field either: an absent or empty body is required, and supplying any field is refused with `ERR_INVALID_REQUEST` under check 7, ahead of every state and business gate. Each transition endpoint returns the transitioned record itself, except that filing a storage inspection returns the newly created inspection record rather than the structure it reconciled.
