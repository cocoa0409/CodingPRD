# Structured Cabling Contracting API — Product Requirements Document

## 1. Introduction

A structured-cabling contractor lives or dies by paperwork. The physical work — pulling cable through a tray, terminating a jack, torquing a bonding lug — takes minutes; proving afterwards that every one of two thousand links was installed inside code limits, tested with a calibrated field tester, labelled to a published identifier scheme and drawn on an as-built sheet takes months, and a single unprovable link can cost the contractor a twenty-five-year manufacturer warranty on the whole building. Today that proof lives in spreadsheets, tester export files and a folder of marked-up drawings, which means the answer to "are we ready to hand over?" is a guess. This document specifies the backend service that replaces the guess with a computed number.

The service models the full contract lifecycle: pathway and space design with cable-tray and conduit fill limits and mandated separation from power conductors, cable selection by application with plenum-rating and distance limits, TIA-606 identifier administration, termination, field testing and per-link certification with independent sign-off, rack elevation and telecom-room grounding, bonding and power distribution, coordination with the ceiling, electrical and mechanical trades on installation sequence, manufacturer warranty registration, and moves-adds-changes ticketing once the owner takes occupancy. Every rule that a code inspector, a manufacturer's warranty desk or the owner's representative would ask about is enforced by the server rather than by convention.

Two design commitments run through the whole specification. First, **nothing is certified twice by the same pair of hands**: the crew identity that terminated a link and the identity that tested it are both barred from certifying it. Second, **every derived number is reconciled, never merely appended**: fill area in a conduit, rack units on an elevation, volt-amperes behind a UPS and cents against a moves-adds-changes budget are all conserved quantities, so withdrawing a route or releasing a rack placement returns the ledger to exactly the value it held beforehand. All resources are mounted under the `/cabling` prefix, with the single exception of the test-only clock control described in §2.5.

## 2. Global Specifications & System-Wide Principles

### 2.1. Crew Identity and Role-Based Access Control

Every request other than the clock control of §2.5 must carry two headers: `X-User-ID`, identifying the person or system acting, and `X-User-Role`, naming the role they are acting in. If either header is absent or empty, or if `X-User-Role` is not one of the seven declared roles, the request fails with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well formed but the named role is not authorized for the endpoint being called — see the Authorized Role(s) column of §4 — the request fails with `ERR_UNAUTHORIZED` (HTTP 403).

The seven roles are `ProjectManager`, `DesignEngineer`, `Installer`, `TestTechnician`, `Certifier`, `ManufacturerAgent` and `Client`. A `ProjectManager` owns the project record, its telecom rooms, trade coordination, the occupancy declaration and warranty submission. A `DesignEngineer` designs pathways, racks, elevations, the cable catalogue and the links themselves, and files as-built records. An `Installer` is field crew: pulling, terminating and labelling cable, and executing moves-adds-changes work. A `TestTechnician` operates the field tester and records measurements. A `Certifier` verifies room grounding and certifies links for warranty, and is barred from certifying its own installation or test work. A `ManufacturerAgent` staffs the manufacturer's warranty programme desk and decides submitted registrations. A `Client` is the building owner's representative, who raises moves-adds-changes tickets after occupancy and reads certification evidence.

All seven roles are operational crew identities rather than persisted rows. Accordingly, for every one of `ProjectManager`, `DesignEngineer`, `Installer`, `TestTechnician`, `Certifier`, `ManufacturerAgent` and `Client`, the `X-User-ID` is an opaque operator identifier that is not tied to any stored entity: the server never compares it to any resource's `id`, and there is no notion of a resource being "owned" by the caller. The server does record it in three places where the specification demands an audit trail — `installer_user_id` on a link at termination, `tester_user_id` on a recorded test result, and `certifier_user_id` on a link at certification — and the segregation-of-duties rule of §3.7 compares those three recorded strings to one another. That comparison is the only use the server makes of `X-User-ID`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, may be no smaller than 1 and no larger than 100; `offset` defaults to 0 and may be no smaller than 0. A `limit` outside the range 1 to 100 inclusive, or a negative `offset`, is a malformed request rather than a value to be clamped, and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Results on every list endpoint are ordered by `created_at` ascending — oldest record first — and the ordering is stable across pages. The `meta` object of a list response carries `limit` and `offset` echoing the effective values used, `total_count` giving the number of records matching the filters before pagination is applied, and `has_more` set to true when records remain beyond the current page. Filter query parameters, where an endpoint offers them, are combined conjunctively: a request that supplies both `project_id` and `install_state` returns only the records matching both.

### 2.4. Record Identity, Timestamps and Revision Counters

Every resource is addressed by an `id`, which is a server-minted UUID string carrying no type prefix and no embedded meaning; clients never supply an `id` on creation. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional-second digits, stamped from the logical clock of §2.5 at the moment of creation.

Most resources additionally carry `updated_at`, in the same timestamp format, and `version`, an integer that starts at 1 when the record is created and increases by exactly 1 on every mutation of that record — including mutations caused indirectly by a cascade originating elsewhere. Whenever a rule below says that a record's `version` increments, its `updated_at` is refreshed to the current logical-clock reading in the same operation. Where a single request advances several records, each affected record's own `version` increments independently by 1.

Two resource kinds are immutable once written and therefore deliberately carry neither `updated_at` nor `version`: a cable type in the selection catalogue, and a recorded field-test result. Both expose only `id` and `created_at` from the common property set, and neither has any endpoint that modifies it. A test result additionally stamps `recorded_at`, the logical-clock reading at which the measurement was filed, which is the field used to decide which of a link's results is the latest.

### 2.5. The Logical Site Clock

The server does not read the host wall clock. It maintains a logical clock that starts at the fixed instant `2026-08-01T00:00:00Z` and advances only when the test-only clock-control endpoint is called with a `to_iso8601` value; that endpoint replies with the resulting `current_utc`. Every `created_at`, `updated_at` and `recorded_at` value, and every temporal comparison in this specification — most consequentially the moves-adds-changes work-window check of §3.8 — reads this logical clock. The clock control is the only endpoint that does not require the `X-User-ID` and `X-User-Role` headers, and it modifies no business entity.

### 2.6. Units, Money and Rounding

Money is always an integer count of cents; there are no fractional currency values anywhere in the API. Lengths are metres, cable and conduit areas are square millimetres, cable diameters and power-separation clearances are millimetres, electrical quantities are volt-amperes and whole amperes, ground resistance is milliohms expressed to two decimal places, rack heights are whole rack units, insertion loss and margins are decibels, and crew effort is decimal hours.

All decimal rounding in this system is **round half up** on exact decimal arithmetic — a value exactly at the midpoint rounds away from zero, and binary floating-point drift is never an acceptable explanation for a differing result. Unless a rule below names a different precision, computed decimal quantities are stored and reported to two decimal places: both link length variants, cable cross-sectional area, consumed and used fill area, insertion-loss budget, worst margin, and both completeness percentages. Two quantities depart from the two-place default and are called out where they are defined: a pathway segment's `fill_ratio` is carried to four decimal places, and a segment's `allowed_fill_pct` is a whole-number percentage. Money computations round to whole cents at each step named in §3.8, never once at the end. Where a rule computes a value from an already-rounded value — for instance the channel length variant, which is derived from the already-rounded permanent-link length — the rounded intermediate is the input, not the raw sum.

### 2.7. Optimistic Concurrency on Shared Drawings

Six write operations edit a record whose parent is a shared artefact — a conduit's remaining fill, a rack elevation, a project's certified population — and each requires the client to prove it was looking at the current state of that parent. In each case the named version field is a **required** input, not an optional one; omitting it is `ERR_INVALID_REQUEST`, and supplying a value that does not equal the parent's current `version` rejects the write without any state change.

Creating a routing of a link through a pathway segment requires `expected_segment_version`, carrying the client's last observed `version` of the target pathway segment. If the segment's `version` has advanced since the client read it — because another route was already admitted and took fill area the writer still believes is free — the create is refused with `ERR_STALE_PATHWAY_VERSION` (HTTP 412) rather than silently graded against occupancy the client never saw. Withdrawing such a routing, and re-pointing a segment at a new upstream segment, carry the same `expected_segment_version` requirement and the same rejection code.

Placing equipment on a rack elevation requires `expected_rack_version`, carrying the client's last observed `version` of the target rack; rack units are allotted from a drawing many engineers read at once, so a writer holding a superseded view of `occupied_ru` would place equipment against a layout that no longer exists. A mismatch is refused with `ERR_STALE_RACK_VERSION` (HTTP 412). Releasing an existing placement carries the same field and the same code.

Submitting a warranty registration requires `expected_project_version`, carrying the client's last observed `version` of the owning project. Submission freezes `submitted_certified_link_count` and computes `coverage_years`, so it may only be built on the exact project state the submitter observed; any intervening certification, condemnation or moves-adds-changes completion has advanced the project's `version` and invalidated that view, and the submission is refused with `ERR_STALE_PROJECT_VERSION` (HTTP 412). No endpoint other than these six — route create, route withdraw, segment reparent, elevation placement, placement release and warranty submission — accepts a version field at all, and supplying one elsewhere is an unknown field and therefore `ERR_INVALID_REQUEST`.

### 2.8. The Order in Which a Request Is Screened

When a single request violates more than one rule, only one error may be reported, and which one is reported is part of the contract rather than an implementation detail. Every request is screened in the following strict order, and the **first** check that fails determines the response; no later check is evaluated, and no state is changed by a request that fails any check. The guiding principle behind the ordering is that identity precedes shape, shape precedes existence, existence precedes state, state precedes concurrency, and life-safety and code-compliance rules outrank physical capacity and money — so a request that both violates a code-compliance rule and exceeds a capacity limit reports the compliance error, never the capacity error.

1. **Authentication.** Both headers present and non-empty, and `X-User-Role` one of the seven declared roles — otherwise `ERR_UNAUTHENTICATED`.
2. **Authorization.** The acting role is listed for the endpoint — otherwise `ERR_UNAUTHORIZED`.
3. **Request admissibility.** Every required input field present; every value of the declared type; every enum value a declared member of its domain; every declared numeric constraint satisfied (a placement's `start_ru` no greater than its `end_ru`, a requested or scheduled window ending strictly after it starts, lengths and areas strictly positive, money and counts non-negative); datetimes well-formed ISO 8601 UTC; `limit` between 1 and 100 inclusive and `offset` at least 0; and no unknown fields present. Any failure is `ERR_INVALID_REQUEST`.
4. **Existence.** Each resource named in the path is resolved left to right, then each foreign key in the body is resolved: `project_id`, `telecom_room_id`, `rack_id`, `cable_type_id`, `link_id`, `pathway_segment_id`, `upstream_segment_id` and `predecessor_coordination_id`. A missing target yields the code for the kind that could not be found — `ERR_PROJECT_NOT_FOUND`, `ERR_TELECOM_ROOM_NOT_FOUND`, `ERR_RACK_NOT_FOUND`, `ERR_RACK_ASSIGNMENT_NOT_FOUND`, `ERR_PATHWAY_SEGMENT_NOT_FOUND`, `ERR_CABLE_TYPE_NOT_FOUND`, `ERR_LINK_NOT_FOUND`, `ERR_ROUTE_NOT_FOUND`, `ERR_TEST_RESULT_NOT_FOUND`, `ERR_WARRANTY_REGISTRATION_NOT_FOUND`, `ERR_MAC_TICKET_NOT_FOUND` or `ERR_COORDINATION_NOT_FOUND` — all HTTP 404.
5. **State.** The target resource is in a state from which the requested transition is declared. Depending on the resource this is `ERR_INVALID_PROJECT_STATE`, `ERR_INVALID_ROOM_STATE`, `ERR_INVALID_LINK_STATE`, `ERR_INVALID_RECORD_STATE`, `ERR_INVALID_ROUTE_STATE`, `ERR_INVALID_ASSIGNMENT_STATE`, `ERR_INVALID_TICKET_STATE`, `ERR_INVALID_WARRANTY_STATE`, `ERR_INVALID_COORDINATION_STATE` or `ERR_SEGMENT_CONDEMNED`, all HTTP 409. This generic check governs every transition operation **except** certification, which reports the two more specific codes of the next two steps instead.
6. **Certification readiness — installation dimension.** Certification requires the link's `install_state` to be `TESTED_PASS`; otherwise `ERR_LINK_NOT_TESTED` (409).
7. **Certification readiness — administration dimension.** Certification then requires the link's `record_state` to be `RECORDED`; otherwise `ERR_LINK_NOT_RECORDED` (409).
8. **Optimistic concurrency.** The submitted version field equals the parent's current `version`, per §2.7 — otherwise `ERR_STALE_PATHWAY_VERSION`, `ERR_STALE_RACK_VERSION` or `ERR_STALE_PROJECT_VERSION`, all HTTP 412.
9. **Segregation of duties** on certification — `ERR_SEGREGATION_OF_DUTIES` (403).
10. **Plenum rating** on routing a link through a segment — `ERR_PLENUM_RATING_REQUIRED` (422).
11. **Separation from power** on routing a link through a segment — `ERR_POWER_SEPARATION_INSUFFICIENT` (422).
12. **Room bonded before conductors are terminated or power is switched on** — `ERR_ROOM_NOT_GROUNDED` (409). This check guards exactly two operations: terminating a link, and energizing a telecom room.
13. **Bonding conductor size** on a grounding verification — `ERR_BONDING_NON_COMPLIANT` (422).
14. **Cross-aggregate consistency.** Every referenced link, telecom room, pathway segment and trade coordination belongs to the same project as the request's `project_id` — otherwise `ERR_CROSS_PROJECT_REFERENCE` (409). This check guards five creations: a link, a routing of a link through a segment, a moves-adds-changes ticket, a trade coordination, and a pathway segment.
15. **Pathway continuity** of a routing's `sequence_index` — `ERR_ROUTE_SEQUENCE_GAP` (422).
16. **Acyclicity of the two self-referential graphs** — `ERR_PATHWAY_CYCLE` or `ERR_COORDINATION_CYCLE` (422). These guard three operations: creating a pathway segment, re-pointing a pathway segment at a new upstream segment, and creating a trade coordination.
17. **A link is routed before it is pulled** — `ERR_LINK_NOT_ROUTED` (409).
18. **Trade sequence.** `ERR_TRADE_NOT_COORDINATED` (409) guards three operations: pulling a link, energizing a room, and declaring occupancy.
19. **Occupancy precedes moves-adds-changes ticketing** — `ERR_PROJECT_NOT_OCCUPIED` (409).
20. **Warranty eligibility** on submission — `ERR_WARRANTY_NOT_ELIGIBLE` (409).
21. **Warranty version pinning** on a manufacturer decision — `ERR_WARRANTY_PIN_STALE` (409).
22. **Only a strict pass is certifiable** — `ERR_MARGINAL_TEST_NOT_CERTIFIABLE` (409).
23. **Identifier format** — `ERR_IDENTIFIER_FORMAT_INVALID` (422). This guards two operations: designing a link, and completing a moves-adds-changes ticket that supplies a replacement identifier.
24. **Identifier uniqueness within the project** — `ERR_DUPLICATE_LINK_IDENTIFIER` (409), guarding the same two operations as the format check and evaluated after it.
25. **Applied label matches the designed identifier** — `ERR_LABEL_MISMATCH` (422).
26. **Cable application support** — `ERR_APPLICATION_NOT_SUPPORTED` (422), on designing a link.
27. **Rack-unit interval conflict** — `ERR_RACK_RU_CONFLICT` (409), on placing equipment on an elevation.
28. **Room work-window capacity** — `ERR_ROOM_WINDOW_CONFLICT` (409), on scheduling a ticket.
29. **Work started inside its scheduled window** — `ERR_TICKET_WINDOW_NOT_OPEN` (409), on starting a ticket.
30. **Permanent-link distance limit** — `ERR_LINK_LENGTH_EXCEEDED` (422), on pulling a link.
31. **Conduit or tray fill limit** — `ERR_PATHWAY_FILL_EXCEEDED` (422), on routing a link through a segment.
32. **Rack height capacity** — `ERR_RACK_CAPACITY_EXCEEDED` (422), on placing equipment on an elevation.
33. **Room power capacity** — `ERR_POWER_CAPACITY_EXCEEDED` (422). This check guards two operations: placing equipment on an elevation, and energizing a room.
34. **Moves-adds-changes budget** — `ERR_MAC_BUDGET_EXCEEDED` (402), on scheduling a ticket.
35. **Occupancy readiness** — `ERR_OCCUPANCY_READINESS_NOT_MET` (409), on declaring occupancy.

Two consequences of this ladder deserve emphasis, because they are easy to get backwards. Placing equipment on a rack elevation can fail four different ways, and they are tried in this order: stale rack version, then rack-unit overlap with an existing active placement, then rack height, then room power. And on a routing request, the plenum-rating and power-separation compliance checks are both evaluated before the fill calculation, so a non-plenum cable pushed into a plenum tray that is also over-full reports `ERR_PLENUM_RATING_REQUIRED`, not `ERR_PATHWAY_FILL_EXCEEDED`.

### 2.9. Cascades, Hop Ordering and Conserved Ledgers

Three operations in this system reach beyond the record they name. Each is a **cascade**, and each cascade is specified as an ordered sequence of hops in which every hop is caused by the hop before it, not by the original request. This matters because the intermediate values are observable: a hop that recomputes a roll-up reads the values the previous hop wrote, so an implementation that evaluates the hops out of order or that "shortcuts" straight to the final state produces different numbers. The three are certification of a link (**Cascade A**, §3.7), condemnation of a pathway segment (**Cascade B**, §3.3), and completion of a moves-adds-changes ticket (**Cascade C**, §3.8). Each is spelled out hop by hop in its own subsection.

Cascades propagate downwards from child to parent and never upwards from parent to child: certifying one link recomputes its project's roll-ups, but nothing that happens to a project reaches back into individual links except through the two documented reverting cascades. Every record touched by any hop of a cascade has its own `version` incremented by 1 and its `updated_at` refreshed, exactly as if it had been modified directly.

Four quantities in this system are **conserved ledgers** rather than running totals, and each must be reconcilable from its inputs at any instant. A pathway segment's `fill_area_used_sq_mm` always equals the sum of `consumed_area_sq_mm` over its currently occupying routes, so releasing a route gives back exactly the area that route took and nothing more. A rack's `occupied_ru` always equals the sum of `span_ru` over its active placements, and its `power_draw_va` the sum of their `power_va`. A telecom room's `power_load_va` always equals the sum of `power_draw_va` over its racks, and `power_load_va` plus `power_headroom_va` always equals `ups_capacity_va` — before and after every mutation. A project's `consumed_mac_cents` always equals the sum of `estimated_billed_cents` over its scheduled and in-progress tickets plus the sum of `final_billed_cents` over its completed tickets. In each case a mutation followed by its compensating mutation must return the ledger to the exact value it held beforehand.

### 2.10. Resolving Paths and Reading the Collection Graph

The resource model is a flat graph rather than a nesting hierarchy: every entity has its own top-level collection under `/cabling`, addressed by its own identifier, and relationships are expressed by foreign keys in request bodies rather than by nested URLs. Path identifiers are resolved strictly left to right, so on a two-segment path the outer resource is checked for existence before the inner one, and the error reported is always the one for the leftmost unresolvable identifier. The path identifiers in use are `project_id`, `room_id`, `rack_id`, `assignment_id`, `segment_id`, `cable_type_id`, `link_id`, `route_id`, `test_result_id`, `registration_id`, `ticket_id` and `coordination_id`; note that a telecom room is addressed in a path as `room_id` while being referenced from a body as `telecom_room_id`, and a pathway segment is addressed as `segment_id` while being referenced from a body as `pathway_segment_id`.

Because nothing is nested, traversal in the reverse direction is provided by filters on the collection reads. Projects may be listed filtered by `site_code`, `warranty_status` and `occupancy_status`. Telecom rooms may be filtered by `project_id`, `room_state` and `grounding_status`. Racks may be filtered by `telecom_room_id`; elevation placements by `rack_id` and `assignment_state`. Pathway segments may be filtered by `project_id`, `upstream_segment_id`, `pathway_state` and `pathway_type` — the `upstream_segment_id` filter is how a caller walks the pathway tree downwards, since a segment stores only its parent. The cable catalogue may be filtered by `category` and `jacket_rating`. Links may be filtered by `project_id`, `telecom_room_id`, `cable_type_id`, `install_state`, `record_state` and `application`. Routings may be filtered by `link_id`, `pathway_segment_id` and `route_state`. Test results may be filtered by `link_id`, `outcome` and `test_standard`. Warranty registrations may be filtered by `project_id`, `registration_state` and `manufacturer_program`. Moves-adds-changes tickets may be filtered by `project_id`, `link_id`, `telecom_room_id`, `ticket_state` and `ticket_type`. Trade coordinations may be filtered by `project_id`, `predecessor_coordination_id`, `trade`, `milestone` and `coordination_state`. Every one of these filters is optional, and every one of these list reads also honours `limit` and `offset`.

Two reads are computed rather than stored, and are described where their inputs are defined: a project-level certification summary (§3.7) and a per-link certification report (§3.7).

## 3. Business Logic & Workflows

### 3.1. Opening a Project, Standing Up Telecom Rooms and Proving the Ground

Work begins when a `ProjectManager` opens a project. The payload names the job with `name`, between 1 and 120 characters inclusive, and carries the owner's `site_code` — two to four uppercase letters followed by one or two digits, matching the pattern `^[A-Z]{2,4}[0-9]{1,2}$` exactly, with no trimming and no case folding. Two design decisions are frozen at this moment and govern everything that follows. `plenum_ceiling` is a boolean declaring whether the ceiling cavity is a plenum air-handling space. `identifier_scheme` selects the TIA-606 identifier class the whole job will label to, and is either `TIA_606_CLASS_1` or `TIA_606_CLASS_2`. Optionally the manager may declare `warranty_program`, one of `NONE`, `STANDARD_15Y` or `EXTENDED_25Y` and defaulting to `STANDARD_15Y` when omitted, naming the manufacturer programme the job intends to register under; and `mac_budget_cents`, a non-negative integer count of cents defaulting to 500000 — five thousand dollars — that caps post-occupancy moves-adds-changes spend.

A newly opened project starts at `occupancy_status` `PRE_OCCUPANCY`, with `warranty_status` `NOT_ELIGIBLE`, `total_link_count`, `certified_link_count`, `failed_link_count`, `as_built_cost_cents` and `consumed_mac_cents` all zero, both `completeness_pct_strict` and `completeness_pct_provisional` at 0.00, and `version` 1. All eight of those figures are derived: none of them is ever supplied by a client, and each is recomputed by the rules of §3.7 and §3.8 whenever its inputs move.

Telecom rooms come next, again raised by a `ProjectManager`, who supplies the owning `project_id`, a `room_code` of exactly two uppercase letters followed by exactly two digits — pattern `^[A-Z]{2}[0-9]{2}$`, unique among the rooms of that project — the `floor` the room sits on as an integer, the `branch_circuit_amps` rating of the dedicated circuit feeding it, which must be at least 15, and the `ups_capacity_va` apparent-power capacity available to racks in the room, which must be at least 0. A room is created in `room_state` `ROUGH_IN` with `grounding_status` `UNVERIFIED`, `tgb_installed` false, `power_load_va` 0, `power_headroom_va` equal to the full `ups_capacity_va`, and `version` 1.

Nothing may be terminated in a room that is not bonded, so grounding is verified before any conductor is landed. A grounding verification — which either a `ProjectManager` or a `Certifier` may record — submits three measurements: `tgb_installed`, true when the telecommunications grounding busbar is physically present; `bonding_conductor_awg`, the AWG size of the bonding conductor running to that busbar, where a numerically larger AWG number means a physically thinner conductor; and `ground_resistance_milliohms`, the measured resistance to ground in milliohms. Each verification overwrites the previously recorded measurements rather than merging with them.

The verification is graded in two steps. First, a conductor thinner than #6 AWG is not a measurement to be filed but a code violation to be refused: when `bonding_conductor_awg` is greater than 6 the entire request is rejected with `ERR_BONDING_NON_COMPLIANT`, nothing is recorded, and neither `grounding_status` nor `room_state` moves. Otherwise the room is graded `COMPLIANT` when all three of the following hold — `tgb_installed` is true, `bonding_conductor_awg` is no greater than 6, and `ground_resistance_milliohms` is no greater than 5000 — and graded `NON_COMPLIANT` when any of them fails. The resistance comparison is inclusive, so a room measuring exactly 5000 milliohms grades `COMPLIANT`.

The grade drives `room_state`, which has three values — `ROUGH_IN`, `GROUNDED` and `ENERGIZED` — and moves as follows. A `COMPLIANT` grade on a `ROUGH_IN` room sets `grounding_status` to `COMPLIANT` and advances `ROUGH_IN → GROUNDED`, which is what unblocks termination for every link whose `telecom_room_id` names this room. A `NON_COMPLIANT` grade on a `ROUGH_IN` room is a self-loop: `grounding_status` becomes `NON_COMPLIANT`, `room_state` stays `ROUGH_IN`, and the failing measurement is still recorded — a failed reading is evidence, not a no-op. A `NON_COMPLIANT` grade on a room that had already reached `GROUNDED` is a demotion: `grounding_status` becomes `NON_COMPLIANT` and `room_state` cycles back `GROUNDED → ROUGH_IN`. All three outcomes increment the room's `version` by 1. `ENERGIZED` is terminal, so a verification aimed at an energized room is refused with `ERR_INVALID_ROOM_STATE`.

Energizing the room's rack power distribution is a `ProjectManager` action that advances `GROUNDED → ENERGIZED` and takes no payload. It has three preconditions, and they are checked in the order given in §2.8: `grounding_status` must be `COMPLIANT`, or the request is refused with `ERR_ROOM_NOT_GROUNDED`; the project must hold a trade coordination whose `trade` is `ELECTRICAL` and whose `milestone` is `POWER_ENERGIZE` sitting in `coordination_state` `RELEASED`, or the request is refused with `ERR_TRADE_NOT_COORDINATED`; and the room's `power_load_va` must be no greater than its `ups_capacity_va`, or the request is refused with `ERR_POWER_CAPACITY_EXCEEDED`. Equality with `ups_capacity_va` is admitted — a room loaded to exactly its UPS rating may be energized. Success increments the room's `version` by 1; a second attempt on an already-energized room is refused with `ERR_INVALID_ROOM_STATE`.

### 3.2. Rack Elevations, Rack Units and the Room Power Ledger

Racks are drawn by a `DesignEngineer`, who names the owning `telecom_room_id`, a `rack_code` of exactly one uppercase letter — pattern `^[A-Z]$`, unique among the racks of that room, and reused later as the second field of a link identifier — and `total_ru`, the usable height in rack units, which must be between 1 and 52 inclusive. A new rack starts with `occupied_ru` 0, `available_ru` equal to `total_ru`, `power_draw_va` 0 and `version` 1. All three of those figures are ledgers reconciled from the placements on the rack; a rack has no lifecycle of its own and no state field.

Placing equipment on the elevation is likewise a `DesignEngineer` action. The payload names the `rack_id`, the `equipment_label` that will be printed on the elevation drawing, the closed rack-unit interval the equipment occupies as `start_ru` (at least 1) and `end_ru` (at least `start_ru`), the `power_va` apparent power the equipment draws (at least 0), and the `expected_rack_version` demanded by §2.7. The interval is **closed and inclusive at both ends**, and every rack unit has capacity for exactly one piece of equipment. The server computes `span_ru` as the number of rack units the placement occupies: the highest occupied unit minus the lowest, plus one. A placement is created in `assignment_state` `ACTIVE`, with `released_reason` null, and `version` 1.

Four things can refuse the placement, and §2.8 fixes the order in which they are tried. A mismatched `expected_rack_version` yields `ERR_STALE_RACK_VERSION`. Then the spatial check: the candidate conflicts with an existing `ACTIVE` placement on the same rack whenever the candidate's `start_ru` is less than or equal to that placement's `end_ru` **and** the candidate's `end_ru` is greater than or equal to that placement's `start_ru` — that is, whenever the two closed intervals share even a single rack unit — and a conflict is `ERR_RACK_RU_CONFLICT`. Because the intervals are closed, adjacency is not conflict: units 1 through 2 followed by units 3 through 4 sit flush against each other with no wasted unit and both are admitted, while units 1 through 3 followed by units 3 through 5 collide on unit 3 and the second is refused. Then the height check: an `end_ru` greater than the rack's `total_ru` is `ERR_RACK_CAPACITY_EXCEEDED`. Placements that have been released free their units immediately and are excluded from both the conflict test and the occupancy sums.

Then the power check, which is the point at which the elevation reaches out of the rack and into the room. The room's `power_load_va` plus the candidate's `power_va` must not exceed the room's `ups_capacity_va`; exceeding it is `ERR_POWER_CAPACITY_EXCEEDED`, and equality with `ups_capacity_va` is admitted. On success the effects propagate in three hops. First the placement itself is written with its computed `span_ru`. Second — caused by the first — the rack's ledger moves: `occupied_ru` grows by the placement's `span_ru`, `available_ru` is recomputed as `total_ru` minus `occupied_ru`, and `power_draw_va` grows by the placement's `power_va`. Third — caused by the second — the room's ledger is recomputed from its racks: `power_load_va` becomes the sum of `power_draw_va` across every rack in the room, and `power_headroom_va` becomes `ups_capacity_va` minus `power_load_va`. Both the rack's `version` and the room's `version` increment by 1.

Releasing a placement is the exact compensation of creating one. A `DesignEngineer` supplies a `released_reason` describing why the equipment came out, together with the `expected_rack_version`. The placement must currently be `ACTIVE`, or the request is refused with `ERR_INVALID_ASSIGNMENT_STATE`; that state check is made before the version check, so releasing an already-released placement reports the state error even if the supplied version is also stale. On success `assignment_state` moves `ACTIVE → RELEASED`, the `released_reason` is stored, the rack's `occupied_ru` shrinks by that placement's `span_ru` and its `power_draw_va` shrinks by that placement's `power_va`, `available_ru` is recomputed, and the room's `power_load_va` and `power_headroom_va` are recomputed from the racks. `RELEASED` is terminal — a released placement is never reactivated. The reconciliation must be exact: after a placement is created and then released, the room's `power_load_va` reads exactly what it read before the placement existed, and at every instant `power_load_va` plus `power_headroom_va` equals `ups_capacity_va`. The placement's own `version` increments, as do the rack's and the room's.

### 3.3. Designing the Pathway Graph, Re-Pointing It and Condemning It

Pathways are designed by a `DesignEngineer` as individual segments, each belonging to a project through `project_id` and identified on the pathway drawing by a `segment_code` unique within that project. A segment declares its `pathway_type` — one of `CABLE_TRAY`, `EMT_CONDUIT`, `INNERDUCT` or `J_HOOK` — its `usable_area_sq_mm`, the interior cross-sectional area available for cable in square millimetres, which must be strictly greater than 0, and its `length_m` run length in metres, also strictly greater than 0. Three optional physical properties describe the environment the run passes through: `bend_count`, the number of 90-degree-equivalent bends in the segment, a non-negative integer defaulting to 0; `in_plenum_space`, true when the segment passes through a plenum air-handling space, defaulting to false; and `shared_with_power`, true when the segment shares its space with unshielded power conductors, defaulting to false, accompanied by `power_separation_mm`, the clear separation in whole millimetres from the nearest power conductor, defaulting to 0.

Segments form a tree by way of `upstream_segment_id`, the segment feeding this one, which is null at a pathway root. From that single parent pointer the server derives `pathway_depth`: the number of hops walked up the `upstream_segment_id` chain before reaching a segment whose `upstream_segment_id` is null. A root segment therefore has `pathway_depth` 0, its immediate child 1, and so on. Chains may be at most 8 hops long. When a segment is created, an `upstream_segment_id` belonging to a different project is refused with `ERR_CROSS_PROJECT_REFERENCE`, and a parent pointer that would push the new segment past the 8-hop ceiling is refused with `ERR_PATHWAY_CYCLE`. A new segment starts in `pathway_state` `SERVICEABLE` with `occupying_route_count` 0, `fill_area_used_sq_mm` 0.00, `fill_ratio` 0.0000, `allowed_fill_pct` set to the percentage the fill rule of §3.5 yields for one more cable than the segment currently carries, and `version` 1.

Field conditions move trays and conduits around, so a `DesignEngineer` may re-point a segment at a different parent. The payload carries the new `upstream_segment_id` together with the `expected_segment_version` demanded by §2.7. Before the move is accepted the server walks upstream from the **proposed** parent, following `upstream_segment_id` at each step: if that walk reaches the segment being re-pointed, the move would close a cycle, and if the walk runs longer than 8 hops the graph would be deeper than code allows — either way the request is refused with `ERR_PATHWAY_CYCLE`. On success the segment's `upstream_segment_id` is updated and `pathway_depth` is recomputed not only for the moved segment but for every segment whose upstream chain passes through it, visited in breadth-first order outwards from the moved segment, so that a subtree three levels deep is renumbered consistently in one operation. The moved segment's `version` increments by 1.

When an inspection finds a tray crushed or a conduit filled with someone else's conduit, a `ProjectManager` condemns the segment, supplying a `condemned_reason` that records the finding. The segment must currently be `SERVICEABLE`; a segment already in `CONDEMNED` is refused with `ERR_SEGMENT_CONDEMNED`, and `CONDEMNED` is terminal in every sense — it accepts no new routings, no re-pointing and no second condemnation. Condemnation is **Cascade B**, and it unwinds four hops deep, each hop caused by the hop above it rather than by the request:

- **Hop 1.** `pathway_state` moves `SERVICEABLE → CONDEMNED` and `condemned_reason` is stored.
- **Hop 2**, caused by hop 1. Every routing on this segment that was `OCCUPYING` moves to `SUSPENDED`. Each suspension gives back exactly that routing's `consumed_area_sq_mm`, so `fill_area_used_sq_mm` falls to 0.00 and `occupying_route_count` falls to 0, with `allowed_fill_pct` and `fill_ratio` recomputed on the emptied segment.
- **Hop 3**, caused by hop 2. Every link that lost an occupying routing has its `routed_segment_count` recomputed. Any such link whose `install_state` was `PULLED`, `TERMINATED`, `TESTED_PASS`, `TESTED_FAIL` or `CERTIFIED` is reverted all the way to `DESIGNED`; its `record_state` is reverted to `UNLABELED`; and both `installer_user_id` and `certifier_user_id` are cleared, because the cable that was installed and signed off no longer has a legal path. Each such link's `version` increments by 1. A link that was already `DESIGNED` keeps that state and simply loses a routing. Note what is **not** reset: `test_attempt_count` and the recorded test results survive, so the link's remediation history follows it permanently.
- **Hop 4**, caused by hop 3. The project's roll-ups are recomputed — `total_link_count`, `certified_link_count`, `failed_link_count`, `completeness_pct_strict`, `completeness_pct_provisional` and `as_built_cost_cents` — by the rules of §3.7, and the warranty consequence is applied. If `warranty_status` was `REGISTERED`, it becomes `REVOKED` and the registered warranty registration itself moves to `REVOKED`. If `warranty_status` was `ELIGIBLE` and `completeness_pct_strict` has now fallen below 100.00, `warranty_status` becomes `NOT_ELIGIBLE` and every registration of that project sitting in `READY` reverts to `DRAFT`. The project's `version` increments by 1, as does the `version` of every registration touched.

The segment's own `version` increments by 1 as part of the condemnation.

### 3.4. The Cable Catalogue, Link Design and the Two Length Variants

Before any link can be designed, the cables it may be built from must exist in the catalogue. A `DesignEngineer` registers a cable type with its `category` — one of `CAT5E`, `CAT6`, `CAT6A`, `OM4_MMF`, `OS2_SMF` or `COAX_RG6` — its `jacket_rating`, one of `CM`, `CMR`, `CMP` or `LSZH`, its `outer_diameter_mm` nominal outside diameter in millimetres, strictly greater than 0, its `max_channel_length_m` manufacturer channel length limit in metres, strictly greater than 0, an optional `shielded` boolean defaulting to false that records whether an overall foil or braid screen is present, its `cost_per_meter_cents` installed material cost per metre as a non-negative integer count of cents, and `applications`, a non-empty list drawn from `DATA_HORIZONTAL`, `BACKBONE`, `WAP`, `CAMERA`, `ACCESS_CONTROL` and `AV_DISTRIBUTION` naming what the cable is approved to carry. Of the four jacket ratings, exactly two — `CMP` and `LSZH` — are admissible in a plenum space; `CM` and `CMR` are not.

From the diameter the server derives `cross_section_area_sq_mm`, the area the cable consumes in a pathway: the area of a circle whose diameter is `outer_diameter_mm`, that is, pi multiplied by the square of half the outside diameter, rounded half up to two decimal places, using 3.141592653589793 for pi. A catalogue entry is immutable once written: there is no endpoint that modifies one, and as noted in §2.4 it carries neither `updated_at` nor `version`.

A link is the unit of installation and of certification, and it is designed by a `DesignEngineer`. The payload names the owning `project_id`, the `telecom_room_id` of the room housing the link's horizontal cross-connect, the `cable_type_id` selected from the catalogue, the TIA-606 `identifier` the link will carry, the `application` this link serves — the same six-value domain as the catalogue's `applications` — and the physical lengths. `horizontal_length_m` is the measured horizontal cable run in metres and must be strictly greater than 0. `consolidation_point_stub_m` is the extra cable between a consolidation point and the work-area outlet, non-negative and defaulting to 0. `patch_cord_allowance_m` is the total patch and equipment cord length at both ends, non-negative and defaulting to 0.

Three admissibility rules bite at design time, in the order §2.8 fixes. The `identifier` must match the pattern the project's `identifier_scheme` selects, as a full-string, case-sensitive, untrimmed match, or the request is refused with `ERR_IDENTIFIER_FORMAT_INVALID`. Under `TIA_606_CLASS_1` an identifier is a two-letter, two-digit room code, then a hyphen, then a single uppercase rack letter followed by two digits — pattern `^[A-Z]{2}[0-9]{2}-[A-Z][0-9]{2}$`, for example `TR01-A14`. Under `TIA_606_CLASS_2` the identifier is prefixed with a floor-and-space field of two digits plus one uppercase letter and a hyphen — pattern `^[0-9]{2}[A-Z]-[A-Z]{2}[0-9]{2}-[A-Z][0-9]{2}$`, for example `03B-TR01-A14`. Second, the identifier must not already be carried by another link of the same project; a collision is `ERR_DUPLICATE_LINK_IDENTIFIER`. Third, the link's `application` must appear in the selected cable type's `applications` list, or the design is refused with `ERR_APPLICATION_NOT_SUPPORTED` — a camera drop may not be built from a cable approved only for backbone service. A `telecom_room_id` that resolves to a room in a different project is `ERR_CROSS_PROJECT_REFERENCE`.

Every link stores **two** length figures, because the industry grades the same physical cable two different ways and the two verdicts can disagree. `permanent_link_length_m` is the sum of `horizontal_length_m` and `consolidation_point_stub_m`, rounded half up to two decimal places; patch cords are excluded because the permanent link ends at the outlet and the patch panel. `channel_length_m` is that **already-rounded** permanent-link figure plus `patch_cord_allowance_m` multiplied by the patch-cord derate factor of 1.2 — stranded cords attenuate more per metre than solid horizontal cable — with the result rounded half up to two decimal places. The derate factor is applied to the cord allowance only, never to the horizontal run, and the channel figure is computed from the rounded permanent-link value rather than from the raw sum.

Each variant is graded against its own limit, and which limits apply depends on the cable's `category`. For balanced twisted-pair and coaxial cable — `CAT5E`, `CAT6`, `CAT6A` and `COAX_RG6` — the permanent-link limit is 90.00 metres and the channel limit is 100.00 metres, fixed by the standard. For optical fibre — `OM4_MMF` and `OS2_SMF` — the channel limit is the catalogue's own `max_channel_length_m` for that cable, and the permanent-link limit is nine tenths of that figure, rounded half up to two decimal places. Consider a copper link with `horizontal_length_m` 84.00, `consolidation_point_stub_m` 0.00 and `patch_cord_allowance_m` 14.00: its `permanent_link_length_m` is 84.00, comfortably inside the 90.00-metre permanent-link limit, while its `channel_length_m` is 100.80, which is outside the 100.00-metre channel limit. The same row passes as a permanent link and fails as a channel, and both figures are stored so that either grading can be applied later.

At design time the server also stamps `material_cost_cents` for the link — its `channel_length_m` multiplied by the cable type's `cost_per_meter_cents`, rounded half up to whole cents, as detailed in §3.7 — even though a link that has not yet been terminated contributes nothing to the project's `as_built_cost_cents`. A newly designed link sits in `install_state` `DESIGNED` and `record_state` `UNLABELED`, with `routed_segment_count` 0, `test_attempt_count` 0, `latest_test_outcome` null, `applied_identifier`, `drawing_sheet_ref`, `installer_user_id` and `certifier_user_id` all null, and `version` 1. Creating it increments the project's `total_link_count`, recomputes both `completeness_pct_strict` and `completeness_pct_provisional` — a freshly designed link **dilutes** completeness, because the denominator counts links in every state — and increments the project's `version` by 1.

### 3.5. Routing a Link Through the Pathway: Plenum, Separation, Continuity and Fill

A link and a pathway segment are joined by a routing, created by a `DesignEngineer` from a payload naming the `link_id`, the `pathway_segment_id`, the `sequence_index` of this segment within the link's ordered chain, and the `expected_segment_version` of §2.7. A link normally traverses several segments in order, so `sequence_index` is a 1-based position that must be at least 1 and must not duplicate another currently occupying routing of the same link. Routings are the many-to-many junction between links and segments: one link crosses many segments, and one segment carries many links.

Routings may only be created while the link is still `DESIGNED` — once cable is in the tray the design is settled — and any other `install_state` is refused with `ERR_INVALID_LINK_STATE`. The target segment must be `SERVICEABLE`; a `CONDEMNED` segment is refused with `ERR_SEGMENT_CONDEMNED`. Beyond those two state checks and the stale-version check, four substantive rules govern admission, and they are evaluated in the order below, which is the order §2.8 fixes.

**Plenum rating.** When the target segment has `in_plenum_space` true, the cable's `jacket_rating` must be `CMP` or `LSZH`. A `CM` or `CMR` jacket in a plenum cavity is refused with `ERR_PLENUM_RATING_REQUIRED`, since a burning non-plenum jacket feeds smoke straight into the return air of the whole floor. The project-level `plenum_ceiling` flag records that the building has such a cavity at all; the per-segment `in_plenum_space` flag is what makes the rating mandatory for a given run.

**Separation from power.** The required clearance from unshielded power conductors depends on the cable, not on the pathway: optical fibre — `OM4_MMF` and `OS2_SMF` — carries no induced current and requires 0 millimetres of separation; a `shielded` copper cable requires 25 millimetres; an unshielded copper or coaxial cable requires 50 millimetres. This requirement is only tested when the segment has `shared_with_power` true, in which case the segment's `power_separation_mm` must be at least the required figure. A separation smaller than required is refused with `ERR_POWER_SEPARATION_INSUFFICIENT`; separation exactly equal to the requirement is admitted.

**Chain continuity.** A first routing, at `sequence_index` 1, may sit on any serviceable segment. For any `sequence_index` greater than 1, the segment being routed onto must be the one whose own `upstream_segment_id` is the segment carrying the link's occupying routing at the immediately preceding position — that is, the chain must be walked downstream one parent-child hop at a time with no gaps. A `sequence_index` that leaves a gap, that lands on a segment which is not a child of the previous segment in the chain, or that duplicates a position already occupied by this link, is refused with `ERR_ROUTE_SEQUENCE_GAP`.

**Fill.** Code limits how much of a conduit's or tray's interior may be filled with cable, and the limit itself depends on how many cables are in there. The evaluation counts the candidate: let the resulting cable count be the segment's current `occupying_route_count` plus one. A `CABLE_TRAY` is allowed 50 percent regardless of count. For every other `pathway_type` the base allowance is tiered by that resulting count: 53 percent for a single cable, 31 percent for exactly two cables, and 40 percent for three or more. **This table is deliberately not monotone** — the two-cable allowance of 31 percent is *lower* than the three-or-more allowance of 40 percent — so an implementation that assumes the allowance falls as cables are added will admit a second cable it is required to refuse. Bends tighten the allowance: for every 90-degree-equivalent bend beyond the second, 2 percentage points are subtracted, so the deduction is 2 points multiplied by the segment's `bend_count` less two, treating any `bend_count` of 2 or fewer as no deduction at all. The result is floored at 25 percent: whatever the tier and the bends, `allowed_fill_pct` is never less than 25, and it is always a whole-number percentage.

The candidate's area is the cable type's `cross_section_area_sq_mm`. The used area after admission is the segment's current `fill_area_used_sq_mm` plus that candidate area, rounded half up to two decimal places. The allowed area is the segment's `usable_area_sq_mm` multiplied by `allowed_fill_pct` and divided by 100, rounded half up to two decimal places. If the used area is strictly greater than the allowed area the routing is refused with `ERR_PATHWAY_FILL_EXCEEDED`; an exact tie is admitted. Only routings in `OCCUPYING` count towards either the cable count or the area sum — routings that were withdrawn or suspended contribute nothing to both.

On admission, the routing snapshots the cable's `cross_section_area_sq_mm` into its own `consumed_area_sq_mm`, and that snapshot — not a fresh lookup — is the exact amount given back if the routing is ever released. The routing is created in `route_state` `OCCUPYING` with `version` 1. The segment's `occupying_route_count` grows by one, its `fill_area_used_sq_mm` grows by the snapshotted area, and its `allowed_fill_pct` and `fill_ratio` are recomputed, where `fill_ratio` is the used area divided by `usable_area_sq_mm`, rounded half up to **four** decimal places. The link's `routed_segment_count` grows by one. Both the segment's `version` and the link's `version` increment by 1.

Withdrawing a routing is the compensating operation, again performed by a `DesignEngineer`, and its payload carries only the `expected_segment_version`. The routing must currently be `OCCUPYING`, or the request is refused with `ERR_INVALID_ROUTE_STATE`, and the owning link must still be `DESIGNED`, or it is refused with `ERR_INVALID_LINK_STATE` — a pulled cable cannot have its path deleted from under it. On success `route_state` moves `OCCUPYING → WITHDRAWN`, the segment's `fill_area_used_sq_mm` is reduced by exactly that routing's `consumed_area_sq_mm`, `occupying_route_count` falls by one, `allowed_fill_pct` and `fill_ratio` are recomputed, and the link's `routed_segment_count` falls by one; the segment's and the link's `version` both increment. `WITHDRAWN` is terminal, and so is `SUSPENDED` — the state a routing is driven into by hop 2 of the condemnation cascade of §3.3, which releases fill in exactly the same way a withdrawal does but is applied by the system rather than requested by an engineer. Neither terminal routing can be reinstated; a new routing must be created instead.

### 3.6. Coordinating the Other Trades, Then Pulling and Terminating

A cabling contractor never controls its own schedule. Cable cannot be pulled until the ceiling trade has the grid open, power cannot be switched on until the electrical contractor has energized the panel, and the mechanical trade will close ducts over anything left in the way. A `ProjectManager` therefore records a coordination request against each dependency, naming the owning `project_id`, the `trade` — one of `CEILING`, `ELECTRICAL`, `MECHANICAL` or `FIRE_ALARM` — and the `milestone` at issue, one of `PATHWAY_ROUGH_IN`, `CEILING_CLOSE`, `POWER_ENERGIZE` or `DUCT_CLOSE`. Coordinations may be chained: `predecessor_coordination_id` names the coordination that must be released before this one can be confirmed, and is null when this coordination is the head of its sequence. A coordination is created in `coordination_state` `REQUESTED`, with `confirmed_date` and `block_reason` null and `version` 1.

Chains must be finite and must not be self-serving. A `predecessor_coordination_id` naming a coordination in a different project is refused with `ERR_CROSS_PROJECT_REFERENCE`. Walking the predecessor chain upwards from the proposed predecessor, no coordination in that chain may carry the same combination of `trade` and `milestone` as the row being created — a milestone may not, however indirectly, depend on itself — and the chain may be no more than 8 hops long; either violation is refused with `ERR_COORDINATION_CYCLE`.

The coordination lifecycle has four states and includes a cycle. Confirmation moves `REQUESTED → CONFIRMED` and stores the `confirmed_date`, the calendar date on which the other trade committed to the milestone, written as `YYYY-MM-DD`. Confirmation requires the coordination to be in `REQUESTED` — anything else is `ERR_INVALID_COORDINATION_STATE` — and, when a `predecessor_coordination_id` is set, requires that predecessor to be in `RELEASED`; a predecessor that has not been released yet is refused with `ERR_PREDECESSOR_NOT_RELEASED`. Release moves `CONFIRMED → RELEASED` and takes no payload; `RELEASED` is terminal. Blocking moves `CONFIRMED → BLOCKED` and stores a `block_reason` explaining which trade is in the way, which re-blocks any installation step that was relying on that milestone. Unblocking moves `BLOCKED → REQUESTED`, clearing both `block_reason` and `confirmed_date`, so the milestone must be confirmed afresh — the `REQUESTED → CONFIRMED → BLOCKED → REQUESTED` loop may repeat as often as the job requires. Every one of these four transitions increments the coordination's `version` by 1, and each is a `ProjectManager` action.

Pulling cable is the `Installer`'s first act on a link, advancing `install_state` from `DESIGNED` to `PULLED`, and it takes no payload. Four things must hold. The link must be in `DESIGNED`, or the request is refused with `ERR_INVALID_LINK_STATE`. If any of the link's occupying routings sits on a segment that has been condemned, the request is refused with `ERR_SEGMENT_CONDEMNED`, because the state family is screened before the routing check; and a link with no occupying routing at all — a `routed_segment_count` of zero — is refused with `ERR_LINK_NOT_ROUTED`, since there is no pathway to pull through. The project must hold a coordination whose `trade` is `CEILING` and whose `milestone` is `PATHWAY_ROUGH_IN` sitting in either `CONFIRMED` or `RELEASED`; both of those two states admit the pull, while `REQUESTED` and `BLOCKED` do not and are refused with `ERR_TRADE_NOT_COORDINATED`. Finally the distance limit is enforced: the link's `permanent_link_length_m` must not exceed the permanent-link limit for its cable category, as derived in §3.4 — 90.00 metres for twisted-pair and coaxial cable, nine tenths of `max_channel_length_m` for fibre. A length strictly greater than the limit is refused with `ERR_LINK_LENGTH_EXCEEDED`; a link measuring exactly the limit is admitted. Success increments the link's `version` by 1.

Terminating a link lands both ends — one at the work-area outlet, one on the patch panel — and is again an `Installer` action with no payload. Termination is the point at which the link enters the priced population of §3.7, so it is also the point at which the room must be provably bonded: the link's telecom room must have `grounding_status` `COMPLIANT`, or the request is refused with `ERR_ROOM_NOT_GROUNDED`. Two source states declare this transition, and both are legitimate: `PULLED → TERMINATED` is the first termination, and `TESTED_FAIL → TERMINATED` is a re-termination after a failed test, which is how a crew reworks a bad punch-down. Any other `install_state` is refused with `ERR_INVALID_LINK_STATE`. On success `installer_user_id` is set to the acting `X-User-ID`, overwritten on every re-termination so that it always names the crew member responsible for the currently installed terminations, the project's `as_built_cost_cents` is refreshed because the link has entered the priced set, and both the link's and the project's `version` increment by 1. Note that a re-termination does **not** reset `test_attempt_count`: the remediation loop `TERMINATED → TESTED_FAIL → TERMINATED` may be walked repeatedly, and the attempt count only ever grows.

### 3.7. Administration Records, Field Testing, Certification and the Project Roll-Ups

A link carries **two independent state dimensions**, and confusing them is the single most common way to get this system wrong. `install_state` tracks the physical work through `DESIGNED`, `PULLED`, `TERMINATED`, `TESTED_PASS`, `TESTED_FAIL` and finally `CERTIFIED`. `record_state` tracks the administration and labelling work through `UNLABELED`, `LABELED` and `RECORDED`. They advance on the same row but on separate tracks: a link may be `LABELED` while still sitting at `TESTED_FAIL`, and may be `TESTED_PASS` while still `UNLABELED`. Only certification requires both dimensions to be complete at once.

Labelling is an `Installer` action that moves `record_state` `UNLABELED → LABELED`. The payload carries `applied_identifier`, the identifier string physically applied at the outlet and the patch panel, and it must be exactly equal to the link's designed `identifier` — a mismatch, including one differing only in case, is refused with `ERR_LABEL_MISMATCH`. The link's `record_state` must be `UNLABELED`, or the request is refused with `ERR_INVALID_RECORD_STATE`, and its `install_state` must be one of `TERMINATED`, `TESTED_PASS` or `TESTED_FAIL` — a label goes on cable that has actually been landed, so a `DESIGNED` or `PULLED` link is refused with `ERR_INVALID_LINK_STATE`. Success stores the `applied_identifier` and increments the link's `version` by 1.

Filing the as-built record moves `record_state` `LABELED → RECORDED` and may be performed by either a `DesignEngineer` or a `ProjectManager`. The payload carries `drawing_sheet_ref`, naming the as-built drawing sheet the link now appears on. The link must be in `LABELED`, or the request is refused with `ERR_INVALID_RECORD_STATE`; in particular a link that is still `UNLABELED` cannot be recorded, and a link already `RECORDED` cannot be recorded twice. Success stores the `drawing_sheet_ref` and increments the link's `version` by 1. The reverse edge `RECORDED → UNLABELED` exists but is never requested directly: it is driven by the system when a cascade invalidates the record, either because a moves-adds-changes change ticket renamed the link (§3.8) or because a routing of the link was suspended by a condemnation (§3.3); in both cases `applied_identifier` is cleared along with the state.

Field testing is the `TestTechnician`'s exclusive act. A test result names the `link_id` under test and the `test_standard` the tester was configured for — either `PERMANENT_LINK` or `CHANNEL` — together with the `tester_model` string that will be printed on the certification report, and four measurements: `insertion_loss_db`, the worst-pair insertion loss in decibels, which must be at least 0; `next_margin_db`, the worst-pair near-end crosstalk margin in decibels, where a negative value means the limit line was crossed; `return_loss_margin_db`, the worst-pair return loss margin in decibels; and `length_measured_m`, the length the tester itself reported. The server stamps `tester_user_id` from the acting `X-User-ID` and `recorded_at` from the logical clock. A test result may only be filed against a link whose `install_state` is `TERMINATED`, `TESTED_PASS` or `TESTED_FAIL`; a `DESIGNED`, `PULLED` or already-`CERTIFIED` link is refused with `ERR_INVALID_LINK_STATE`. Results are immutable once filed, and as noted in §2.4 carry neither `updated_at` nor `version`.

Grading is deterministic and consults nothing but this submission, the link's two stored lengths and its cable category; earlier results are never blended in. The graded length is chosen by `test_standard`: a `CHANNEL` test grades the link's `channel_length_m` against the channel limit, while a `PERMANENT_LINK` test grades its `permanent_link_length_m` against the permanent-link limit, with both limits derived exactly as in §3.4. The `worst_margin_db` recorded on the result is whichever of `next_margin_db` and `return_loss_margin_db` is smaller. The `insertion_loss_budget_db` is 0.40 decibels of fixed connector and mated-pair allowance plus 0.19 decibels for every metre of the graded length, rounded half up to two decimal places. The verdict is then reached by four tests applied **in this order, first match winning**:

1. If the graded length is strictly greater than its limit, `outcome` is `FAIL` with `failure_reason` `LENGTH_LIMIT`.
2. Otherwise, if `insertion_loss_db` is strictly greater than `insertion_loss_budget_db`, `outcome` is `FAIL` with `failure_reason` `INSERTION_LOSS`.
3. Otherwise, if `worst_margin_db` is strictly less than 0.0, `outcome` is `FAIL` with `failure_reason` `MARGIN`.
4. Otherwise, if `worst_margin_db` is strictly less than 0.5 — inside the field tester's own accuracy band — `outcome` is `PASS_ASTERISK` and `failure_reason` is null.
5. Otherwise `outcome` is `PASS` and `failure_reason` is null.

Both boundaries matter. A `worst_margin_db` of exactly 0.00 is **not** a failure: it grades `PASS_ASTERISK`, a marginal result the tester cannot distinguish from the limit line. A `worst_margin_db` of exactly 0.50 grades a clean `PASS`. Because the two length variants use different limits and different insertion-loss budgets, the same physical link can pass one standard and fail the other.

Filing a result drives the link's `install_state`. A graded `PASS` or `PASS_ASTERISK` moves the link to `TESTED_PASS`, from any of `TERMINATED`, `TESTED_FAIL` (a retest after rework) or `TESTED_PASS` (a repeat test). A graded `FAIL` moves the link to `TESTED_FAIL`, from any of `TERMINATED`, `TESTED_PASS` (a regression on retest) or `TESTED_FAIL`. In every one of these cases the link's `test_attempt_count` grows by one, `latest_test_outcome` is set to the outcome just graded, and the link's `version` increments by 1; and in every one of these cases the project's `failed_link_count` and `completeness_pct_provisional` are recomputed and the project's `version` increments by 1. `test_attempt_count` is never reset by any operation in this system, and `latest_test_outcome` always reflects the result with the greatest `recorded_at` for that link, or null when the link has never been tested.

Certification is the `Certifier`'s exclusive act, takes no payload, and moves `install_state` `TESTED_PASS → CERTIFIED`. Five preconditions guard it, and §2.8 fixes their order. The link's `install_state` must be `TESTED_PASS`, or the request is refused with the specific code `ERR_LINK_NOT_TESTED` rather than the generic state error. Its `record_state` must be `RECORDED`, or the request is refused with `ERR_LINK_NOT_RECORDED` — this is the point at which the administration dimension is forced to catch up with the installation dimension. Then segregation of duties, twice over: the acting `X-User-ID` must differ from the link's `installer_user_id`, and it must also differ from the `tester_user_id` of the link's latest test result. Either coincidence is refused with `ERR_SEGREGATION_OF_DUTIES`, because a warranty is worthless if the person who punched the jack is the person who signed off on it. Finally the result must be a strict `PASS`: a `latest_test_outcome` of `PASS_ASTERISK` moved the link to `TESTED_PASS` but is **not** certifiable, and certification is refused with `ERR_MARGINAL_TEST_NOT_CERTIFIABLE` until a clean retest replaces it.

Certification is **Cascade A**, four hops deep, each hop caused by the one above it:

- **Hop 1.** `install_state` moves `TESTED_PASS → CERTIFIED` and `certifier_user_id` is set to the acting `X-User-ID`. The link's `version` increments by 1.
- **Hop 2**, caused by hop 1. The project's `certified_link_count`, `completeness_pct_strict`, `completeness_pct_provisional` and `as_built_cost_cents` are recomputed, and the project's `version` increments by 1.
- **Hop 3**, caused by hop 2. If the recomputed `completeness_pct_strict` is at least 100.00 and `total_link_count` is at least 1, the project's `warranty_status` moves `NOT_ELIGIBLE → ELIGIBLE`.
- **Hop 4**, caused by hop 3. Every warranty registration of that project sitting in `DRAFT` moves `DRAFT → READY` and stamps its `pinned_project_version` with the project's version **after** the hop-2 increment. Each such registration's `version` increments by 1.

The roll-up arithmetic of hop 2 is defined once and used everywhere. `total_link_count` is the number of links belonging to the project **in any `install_state` whatsoever** — there is no state filter, so designed-but-unbuilt links dilute completeness. `certified_link_count` counts links in `CERTIFIED`; `failed_link_count` counts links in `TESTED_FAIL`. `completeness_pct_strict` is 100 multiplied by `certified_link_count`, divided by `total_link_count`, rounded half up to two decimal places; `completeness_pct_provisional` is the same figure with a numerator of `certified_link_count` plus the number of links in `TESTED_PASS`. Both percentages are exactly 0.00 when `total_link_count` is zero — an empty project reads 0.00, never 100.00, and is therefore never warranty-eligible. The two variants routinely disagree, and both are reported: a project with one certified link and one tested-but-uncertified link reads `completeness_pct_strict` 50.00 and `completeness_pct_provisional` 100.00 for the same data, and only the strict figure counts for warranty eligibility and for the occupancy gate of §3.8. `warranty_status` follows the strict figure: it moves `NOT_ELIGIBLE → ELIGIBLE` once the strict figure reaches 100.00 with at least one link, and back `ELIGIBLE → NOT_ELIGIBLE` whenever the strict figure falls below 100.00.

The as-built cost roll-up prices the cable that is actually in the building, and its rounding order is pinned. The priced population is every link of the project whose `install_state` is `TERMINATED`, `TESTED_PASS`, `TESTED_FAIL` or `CERTIFIED`; links still `DESIGNED` or `PULLED` are excluded, because nothing has been terminated yet. Links are visited in `created_at` ascending order. For each priced link, the material cost is the cable type's `cost_per_meter_cents` multiplied by that link's `channel_length_m`, **rounded half up to whole cents at this point**, and stored on the link as `material_cost_cents`; the labour cost is a flat 4750 cents per terminated end at two ends per link, that is 9500 cents; and the link's contribution is the sum of the two. `as_built_cost_cents` is then the sum of those already-rounded per-link contributions. The order is load-bearing: two links each priced at 150 cents per metre over a `channel_length_m` of 88.03 each produce an unrounded material figure of 13204.5 cents, which rounds to 13205 per link and sums to 26410 cents, whereas summing first and rounding once would yield 26409 cents. This specification requires 26410. The roll-up is refreshed on every transition that moves a link into or out of the priced population — first termination, each test outcome, certification, and the two reverting cascades of §3.3 and §3.8.

Two computed reads expose all of this without storing anything. The project certification summary returns `total_link_count`, `certified_link_count`, `failed_link_count`, `completeness_pct_strict`, `completeness_pct_provisional`, `warranty_status`, `as_built_cost_cents` and `consumed_mac_cents` for one project, and is the read the owner's representative and the manufacturer's desk both use to judge readiness. The per-link certification report assembles that link's evidence from its latest test result and returns `link_id`, `identifier`, `install_state`, `record_state`, `test_attempt_count`, `latest_test_outcome`, `latest_test_standard` (the `test_standard` of that latest result), `graded_length_m` (the length variant that result was graded against), `insertion_loss_budget_db`, `worst_margin_db`, `failure_reason` and `certifier_user_id`. Where the link has never been tested, the fields drawn from a test result are null.

### 3.8. Occupancy, Moves-Adds-Changes Ticketing and the MAC Budget

Occupancy is the handover moment, declared by a `ProjectManager` with a payload naming the target `occupancy_status` of `OCCUPIED`. Two gates protect it, and the trade gate is evaluated first: every coordination of the project whose `trade` is `CEILING` must be in `coordination_state` `RELEASED` — not merely confirmed — or the declaration is refused with `ERR_TRADE_NOT_COORDINATED`. Then the readiness gate: `completeness_pct_strict` must be at least 90.00, because the owner will not accept the space with more than a tenth of its links uncertified, and a shortfall is refused with `ERR_OCCUPANCY_READINESS_NOT_MET`. Note that this gate uses 90.00 while warranty eligibility demands a full 100.00, so a building is routinely occupied months before it is warrantable. `PRE_OCCUPANCY → OCCUPIED` is the only declared transition and `OCCUPIED` is terminal, so a second declaration on an already-occupied project is refused with `ERR_INVALID_PROJECT_STATE`. Success sets `occupancy_status` to `OCCUPIED`, increments the project's `version` by 1, and unlocks moves-adds-changes ticketing — until then, any attempt to raise a ticket is refused with `ERR_PROJECT_NOT_OCCUPIED`.

A `Client` raises a moves-adds-changes ticket naming the `project_id`, the `link_id` of the link being moved, added to or changed, the `telecom_room_id` of the room the crew will work in, and the `ticket_type`, one of `MOVE`, `ADD` or `CHANGE`. The client's preferred window is given as `requested_window_start` and `requested_window_end`, ISO 8601 UTC instants where the end must be strictly after the start, and the expected effort as `labor_hours_estimate`, a decimal number of crew hours strictly greater than 0. Optionally the client may set `expedite_requested`, defaulting to false, asking for out-of-cycle service; and, on a `CHANGE` ticket, may supply `new_identifier`, the replacement TIA-606 identifier the link is to carry, which is null on every other ticket type. Both the referenced link and the referenced room must belong to the project named by `project_id`, or the ticket is refused with `ERR_CROSS_PROJECT_REFERENCE`. A ticket is created in `ticket_state` `SUBMITTED` with `rework_count` 0, `scheduled_window_start`, `scheduled_window_end`, `actual_labor_hours`, `estimated_billed_cents` and `final_billed_cents` all null, and `version` 1.

Billing is computed twice for every ticket, from the same pinned six-step sequence, and the two runs can differ substantially. First, the billable hours are the greater of the submitted hours and the one-hour minimum call-out — a fifteen-minute patch is billed as an hour. Second, the subtotal is those billable hours multiplied by the labour rate of 9600 cents per hour — 96 dollars — rounded half up to whole cents. Third, the volume discount tier is selected **from the subtotal**: below 50000 cents the discount is 0 percent, from 50000 up to but not including 150000 cents it is 5 percent, and at 150000 cents or above it is 10 percent. Fourth, the discount amount is the subtotal multiplied by that percentage divided by 100, rounded half up to whole cents. Fifth, the expedite fee — charged only when `expedite_requested` is true, and otherwise zero — is 15 percent of the **post-discount** base, that is of the subtotal less the discount, again rounded half up to whole cents. Sixth, the billed amount is the subtotal, less the discount, plus the expedite fee. The tier is keyed on the subtotal and never on the final billed figure, which is easy to get backwards: an expedited ticket of 5.0 hours has a subtotal of 48000 cents, which sits below the 50000-cent threshold, so the discount is 0 percent and the billed amount is 55200 cents; keying the tier off the 55200-cent total would wrongly grant 5 percent and bill 52440.

The **estimate** run of that calculation uses `labor_hours_estimate` and stamps `estimated_billed_cents`; the **final** run uses `actual_labor_hours` and stamps `final_billed_cents`. On the same ticket, 6.0 estimated hours bill 62928 cents while 4.0 actual hours bill 44160 cents. The project's `consumed_mac_cents` is the reconciled ledger over both: the sum of `estimated_billed_cents` across the project's tickets in `SCHEDULED` or `IN_PROGRESS`, plus the sum of `final_billed_cents` across its tickets in `COMPLETED`. Tickets in `SUBMITTED` and `REJECTED` contribute nothing.

Scheduling is a `ProjectManager` action on a `SUBMITTED` ticket — any other `ticket_state` is refused with `ERR_INVALID_TICKET_STATE` — and its payload carries the confirmed `scheduled_window_start` and `scheduled_window_end`, the end strictly after the start. Two capacity checks follow, in this order. The room can host at most two crews at once, and changeover needs half an hour either side: the candidate window is widened by 30 minutes at its start **and** at its end, and that widened window is compared against the unwidened windows of every other ticket in the same room whose `ticket_state` is `SCHEDULED` or `IN_PROGRESS`. Two windows overlap when the existing ticket starts strictly before the widened candidate ends and ends strictly after the widened candidate begins; the intersection is half-open, so a ticket ending exactly 30 minutes before the candidate begins does not overlap and an exact half-hour gap is admitted. If two or more such tickets overlap, the schedule is refused with `ERR_ROOM_WINDOW_CONFLICT` — two overlapping windows in one room are legal, the third is not. Tickets in `SUBMITTED`, `COMPLETED` or `REJECTED` never occupy the room. Then the money check: the project's current `consumed_mac_cents` plus this ticket's estimate must not exceed `mac_budget_cents`, and exceeding it is refused with `ERR_MAC_BUDGET_EXCEEDED`, while landing exactly on the budget is admitted. On success `ticket_state` moves `SUBMITTED → SCHEDULED`, the two window instants are stamped, `estimated_billed_cents` is stamped from the estimate run, `consumed_mac_cents` grows by that amount, and both the ticket's and the project's `version` increment by 1.

A `SUBMITTED` ticket may instead be rejected outright by a `ProjectManager`, moving `SUBMITTED → REJECTED`, which is terminal and takes no payload. The two branches out of `SUBMITTED` have deliberately disjoint consequences: only the scheduling branch touches the budget ledger, while rejection leaves `consumed_mac_cents`, `estimated_billed_cents` and every window field untouched and merely increments the ticket's `version` by 1.

An `Installer` starts the work, moving `SCHEDULED → IN_PROGRESS`, with no payload. The logical clock of §2.5 must sit inside the half-open scheduled window: at or after `scheduled_window_start` and strictly before `scheduled_window_end`. A clock reading exactly at the start instant is inside the window; a reading exactly at the end instant is outside it. Starting outside the window is refused with `ERR_TICKET_WINDOW_NOT_OPEN`, and starting a ticket that is not `SCHEDULED` is refused with `ERR_INVALID_TICKET_STATE`. Success increments the ticket's `version` by 1.

Work in progress can be sent back. A `ProjectManager` reworks an `IN_PROGRESS` ticket, moving it `IN_PROGRESS → SUBMITTED`, clearing `scheduled_window_start`, `scheduled_window_end` and `estimated_billed_cents` to null, incrementing `rework_count` by 1, and reducing the project's `consumed_mac_cents` by exactly the `estimated_billed_cents` that scheduling had committed — after which the ledger identity of §2.9 must still hold exactly. Both the ticket's and the project's `version` increment by 1. The loop `SCHEDULED → IN_PROGRESS → SUBMITTED → SCHEDULED` may be walked as often as the job demands, and `rework_count` counts how many times it has been.

Completion is **Cascade C**, performed by an `Installer` on an `IN_PROGRESS` ticket. The payload carries `actual_labor_hours`, the crew hours actually spent, which must be strictly greater than 0, and on a `CHANGE` ticket may carry `new_identifier`. When a `new_identifier` is supplied on a `CHANGE` ticket it is screened exactly as a designed identifier is: it must match the pattern the project's `identifier_scheme` selects, or the completion is refused with `ERR_IDENTIFIER_FORMAT_INVALID`, and it must not already be carried by another link of the project, or the completion is refused with `ERR_DUPLICATE_LINK_IDENTIFIER`. The cascade then runs four hops deep:

- **Hop 1.** `ticket_state` moves `IN_PROGRESS → COMPLETED`, `actual_labor_hours` is stored, and `final_billed_cents` is stamped from the final billing run. The project's `consumed_mac_cents` is adjusted by the difference between `final_billed_cents` and `estimated_billed_cents` — upwards when the crew overran, downwards when it finished early — and the project's `version` increments by 1. Both the ticket's `version` and the project's `version` increment by 1.
- **Hop 2**, caused by hop 1, and only when the ticket's `ticket_type` is `CHANGE` with a non-null `new_identifier`: the referenced link's `identifier` is replaced by `new_identifier`, its `applied_identifier` is cleared, its `record_state` reverts to `UNLABELED`, and if its `install_state` was `CERTIFIED` it falls back to `TERMINATED` with `certifier_user_id` cleared. The link's `version` increments by 1. A renamed link is by definition no longer labelled to its identifier or drawn correctly, so its certification is void until it is relabelled, refiled and recertified.
- **Hop 3**, caused by hop 2. The project's `certified_link_count`, `completeness_pct_strict`, `completeness_pct_provisional` and `as_built_cost_cents` are recomputed by the rules of §3.7.
- **Hop 4**, caused by hop 3. If `completeness_pct_strict` has fallen below 100.00, the warranty consequence is applied exactly as in §3.3: a `warranty_status` of `ELIGIBLE` becomes `NOT_ELIGIBLE` with every `READY` registration reverting to `DRAFT`, and a `warranty_status` of `REGISTERED` becomes `REVOKED` with the registered registration itself moving to `REVOKED`.

A `MOVE` or `ADD` ticket, or a `CHANGE` ticket completed without a `new_identifier`, stops after hop 1: the money is reconciled and nothing touches the link. `COMPLETED` is terminal, as is `REJECTED`.

### 3.9. Manufacturer Warranty Registration, Decision and Revocation

A warranty registration is the artefact the manufacturer's programme desk decides on, and it is opened by a `ProjectManager` who names the owning `project_id` and the `manufacturer_program` applied for, either `STANDARD_15Y` or `EXTENDED_25Y`. Note that the project-level `warranty_program` field records the programme the job *intends* to register under and may be `NONE`, whereas a registration must name one of the two real programmes. A new registration is created in `registration_state` `DRAFT` with `pinned_project_version`, `submitted_certified_link_count`, `coverage_years`, `registration_number` and `rejection_reason` all null, and `version` 1.

A registration does not become submittable by anyone's decision — it is promoted by the project reaching full certification. `DRAFT → READY` is driven by the system as hop 4 of Cascade A (§3.7), at the instant the project's `warranty_status` becomes `ELIGIBLE`, and at that moment `pinned_project_version` captures the project's `version`. The reverse edge `READY → DRAFT` is likewise system-driven, as hop 4 of the condemnation cascade (§3.3) or of the ticket-completion cascade (§3.8), whenever the project's `completeness_pct_strict` falls back below 100.00 and `warranty_status` leaves `ELIGIBLE`; the demotion clears `pinned_project_version` back to null. Both edges increment the registration's `version` by 1.

Submission is a `ProjectManager` action carrying only the `expected_project_version` demanded by §2.7. Three preconditions are checked in the order §2.8 fixes: the registration must be in `READY`, or the request is refused with `ERR_INVALID_WARRANTY_STATE`; the supplied `expected_project_version` must equal the project's current `version`, or the request is refused with `ERR_STALE_PROJECT_VERSION`; and the project's `warranty_status` must be `ELIGIBLE`, or the request is refused with `ERR_WARRANTY_NOT_ELIGIBLE`. Submission moves `READY → SUBMITTED` and freezes the evidence: `submitted_certified_link_count` is stamped from the project's `certified_link_count` and never moves again, and `coverage_years` is computed. The project's `warranty_status` becomes `SUBMITTED` and its `version` increments by 1; `pinned_project_version` is then re-stamped with the project's version **after** that increment, so the pin always names the exact project revision the manufacturer will be asked to decide on. The registration's `version` increments by 1.

The warranty term is not simply the programme's headline number: rework is penalised. The base term is 15 years for `STANDARD_15Y` and 25 years for `EXTENDED_25Y`. Against that base, every link of the project that has been tested three or more times — a `test_attempt_count` of at least 3, counted across all links regardless of `install_state`, and never reset by re-termination or by any cascade — costs 5 years. `coverage_years` is the base term less 5 years for each such link, but never less than the 10-year floor, and the floor is applied **after** the penalty rather than being blended into it: a `STANDARD_15Y` project with two rework links yields 10 years, not 5, because 15 less 10 is 5 and the floor lifts it to 10.

The manufacturer's desk then decides. A `ManufacturerAgent` supplies `decision`, either `REGISTER` or `REJECT`. A `REGISTER` decision must be accompanied by the manufacturer-issued `registration_number`, and a `REJECT` decision by a `rejection_reason`; a decision missing its required companion field is refused at the admissibility stage with `ERR_INVALID_REQUEST`. The registration must be in `SUBMITTED`, or the request is refused with `ERR_INVALID_WARRANTY_STATE`. For a `REGISTER` decision there is one further gate: the project's current `version` must still equal the registration's `pinned_project_version`. If the certified population moved after submission — another certification, a condemnation, a ticket completion — the pin is stale, the request is refused with `ERR_WARRANTY_PIN_STALE`, and the registration is **left in `SUBMITTED`** rather than being failed, so that the deficiency can be resolved and the decision retried.

A successful `REGISTER` moves `SUBMITTED → REGISTERED`, stores the `registration_number`, and sets the project's `warranty_status` to `REGISTERED`. A `REJECT` moves `SUBMITTED → REJECTED`, stores the `rejection_reason`, and sets the project's `warranty_status` to `REJECTED`. Either way the project's `version` and the registration's `version` each increment by 1.

Rejection is recoverable. A `ProjectManager` reopens a `REJECTED` registration, moving it `REJECTED → DRAFT` — any other state is refused with `ERR_INVALID_WARRANTY_STATE` — which clears `rejection_reason`, `coverage_years`, `submitted_certified_link_count` and `pinned_project_version` back to null and takes no payload. The project's `warranty_status` is then recomputed from scratch against `completeness_pct_strict`: `ELIGIBLE` when the strict figure is at least 100.00 and the project has at least one link, and `NOT_ELIGIBLE` otherwise. The project's `version` and the registration's `version` each increment by 1, and the cycle `DRAFT → READY → SUBMITTED → REJECTED → DRAFT` may be walked again.

`REGISTERED` and `REVOKED` are the terminal states, and no client request leaves either of them. `REGISTERED → REVOKED` is the one further edge, driven by the system as hop 4 of the condemnation cascade or of the ticket-completion cascade when `completeness_pct_strict` falls below 100.00 while the project's `warranty_status` was `REGISTERED`: the registration becomes `REVOKED`, the project's `warranty_status` becomes `REVOKED`, and the registration's `version` increments by 1. A revoked warranty is not reopened; the contractor must open a fresh registration once the deficiency is certified away.
