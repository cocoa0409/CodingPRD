# Roadside Inspection Data Review API — Product Requirements Document

## 1. Introduction

Every roadside inspection a state enforcement agency writes eventually becomes a number attached to a motor carrier's federal safety profile, and that number decides whether the carrier's trucks get waved past a weigh station or pulled in for a Level 1 walk-around. The problem this API exists to solve is that inspection paperwork is frequently wrong. Reports get attributed to the wrong USDOT number when a leased tractor is running under someone else's authority; the same vehicle stop is keyed twice by two different officers; an inspector writes a citation code that the court later dismisses or reduces. Under the current process a carrier discovers the error only after the score has already moved, and has no auditable channel to contest it.

This document specifies a system that holds four things at once: the inspection record as the state agency wrote it, the corrections the agency subsequently files, the formal data challenges carriers submit with supporting evidence, and the court outcomes of the underlying citations. From those inputs the system derives behaviour-category safety measures, maps them onto percentiles against published intervention reference tables, decides each carrier's intervention posture, and computes the roadside screening risk value that drives the inspect-or-pass decision at the next weigh station. Because a carrier's data-quality track record is itself evidence of the profile's reliability, accepted challenges earn a credit against the screening value.

Two design constraints shape everything that follows. First, **nothing in this system is estimated** — every score is a deterministic function of pinned snapshots, and a single accepted challenge must propagate through the whole dependency chain in one atomic request rather than waiting for an overnight batch. Second, the people who write the data, the people who dispute it, the people who adjudicate the dispute, and the people who judge the carrier's remediation plan are deliberately different parties with non-overlapping authority; the API enforces that separation rather than trusting the client to respect it.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold for every endpoint in the system. Where §3 describes what a particular workflow does, this section describes the rules that workflow cannot escape.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which that principal acts. Five roles are recognised, and these spellings are exact: `CarrierAnalyst`, `CarrierSafetyManager`, `StateInspectionOfficer`, `FmcsaReviewOfficer`, and `FmcsaProgramAuditor`. If either header is absent, or if `X-User-Role` is not one of those five strings, the request fails with `ERR_UNAUTHENTICATED`. If the headers are well formed but the declared role is not among the roles authorised for the endpoint being called, the request fails with `ERR_ROLE_NOT_PERMITTED`.

The five roles divide as follows. A `CarrierAnalyst` is the carrier's safety data quality analyst: they open data challenges, attach evidence, submit and withdraw challenges, draft corrective action plans, add action items, and commit those items. A `CarrierSafetyManager` is the carrier's safety manager: they register and update drivers, set or clear driver-level violation attribution, create and run coaching assignments, mark action items implemented, and submit the corrective action plan. A `StateInspectionOfficer` is the state enforcement officer: they ingest inspection reports and violations, mark reports validated, file agency amendments, and record citations and court results. An `FmcsaReviewOfficer` is the federal data review officer: they adjudicate data challenges and push adjudicated court results into violation records. An `FmcsaProgramAuditor` is the federal program auditor: they own reference data (carriers, violation codes, intervention thresholds), the logical clock, the scoring epoch, safety fitness determinations, corrective action plan branch reviews and decisions, and action-item verification and rejection. Report scoring is shared between `StateInspectionOfficer` and `FmcsaProgramAuditor`. Action-item status changes are shared across `CarrierAnalyst`, `CarrierSafetyManager` and `FmcsaProgramAuditor`, but each role may only drive the transitions named for it in §3.10. All read endpoints are open to all five roles.

The meaning of `X-User-ID` depends on the role. When `X-User-Role` is `CarrierAnalyst`, `X-User-ID` is the `id` of the acting `Carrier`; ownership checks on any resource that references a `Carrier` compare the resource's carrier foreign-key field to `X-User-ID`. When `X-User-Role` is `CarrierSafetyManager`, `X-User-ID` is likewise the `id` of the acting `Carrier`, and the same ownership comparison applies. Concretely, the field compared is `Carrier.id` for a carrier itself, `carrier_id` on a `Driver`, `attributed_carrier_id` on a `Violation`, `carrier_id` on a `DataChallenge`, `carrier_id` on a `CoachingAssignment`, `carrier_id` on a `CorrectiveActionPlan`, and `attributed_carrier_id` on an `InspectionReport`. A carrier-side role that addresses a single resource belonging to a different carrier, or attempts a write against one, is rejected with `ERR_CARRIER_SCOPE_VIOLATION`. List endpoints behave differently: rather than erroring, they are silently filtered so that a carrier-side caller sees only rows belonging to its own carrier.

When `X-User-Role` is `StateInspectionOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; no record in the system stores it, and it is never compared to any entity's `id`. The same holds when `X-User-Role` is `FmcsaReviewOfficer`: the identifier is opaque, and the server records it as `resolved_by_user_id` on a resolved `DataChallenge` and as `applied_by_user_id` on a `CitationAdjudication` whose result has been pushed to the record, without ever comparing it to an entity `id`. The same holds again when `X-User-Role` is `FmcsaProgramAuditor`: the identifier is opaque, and the server records it as `fitness_determined_by_user_id` on a `Carrier`, as `safety_review_user_id` or `data_review_user_id` on a `CorrectiveActionPlan` branch review, as `decided_by_user_id` on a plan decision, and as `verified_by_user_id` on a verified action item — again without comparing it to any entity `id`. Those recorded auditor identifiers are, however, compared against each other: that is the mechanism behind the segregation-of-duties rules in §2.11.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of rows returned; it defaults to 10 when omitted, may be no smaller than 1, and may be no larger than 100. `offset` is the number of rows to skip before the first returned row; it defaults to 0 and may not be negative. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint states otherwise, every list endpoint returns its rows sorted by `created_at` in ascending order.

The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` indicates whether rows remain beyond the current window.

### 2.4. The Logical Clock and the Scoring Epoch

Every age computation, deadline evaluation, filing window and aging basis in this system reads a server-held **logical clock** rather than wall-clock time. The clock starts at the fixed instant `2026-08-01T00:00:00Z` and never falls back to real time. An `FmcsaProgramAuditor` may move it by supplying a `to_iso8601` instant to the clock-setting capability; the response reports the new `current_utc` and the `previous_utc` it replaced, and no entity is mutated by the call itself. Every subsequent age, deadline and window evaluation reads the new instant.

Layered on top of the clock is the **scoring epoch**. A scoring run captures the clock into its own `snapshot_utc`, and every score that run writes is aged against that snapshot rather than against the live clock. Scores written by an on-demand pass instead use the live clock as their basis. Whichever basis applies is recorded on the affected rows so a reader can always tell what instant produced a given number.

### 2.5. Common Record Properties

Records in this system carry a standard set of server-managed fields:

- **`id`** (string): a server-minted UUID. It carries no type prefix — the value is a bare UUID.
- **`created_at`** (string): an ISO 8601 UTC timestamp with three fractional digits (for example `2026-08-01T00:00:00.000Z`) recording when the record was first written.
- **`updated_at`** (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the record.
- **`version`** (integer): a counter that starts at 1 on creation and increments by exactly 1 on every mutation of the record.

Two record types are append-only audit rows and carry only `id` and `created_at`: `ReportAmendment` and `ChallengeEvidence`. Neither has an `updated_at` field and neither has a `version` field, so neither can be the subject of a concurrency check.

Writing a derived field counts as a mutation. When a cascade recomputes a carrier's screening risk or a driver's attribution scores, that carrier or driver record has its `updated_at` refreshed and its `version` incremented, exactly as if a client had edited it directly. A single request can therefore legitimately bump the `version` of a dozen records across several entity types.

### 2.6. Optimistic Concurrency on Parent Records

Three write operations create a child record whose meaning depends on the exact state of a parent record, and each of them is guarded by an optimistic concurrency check against that parent's `version`. In all three cases the version field is a required input, not an optional one, and a mismatch is reported with HTTP 412.

Creating a `CorrectiveActionPlan` requires `expected_carrier_version` in the request body, carrying the client's last observed `version` of the target `Carrier`. If that value does not equal the carrier's current `version`, the create is rejected with `ERR_STALE_CARRIER_VERSION` and HTTP 412. This guard exists because plan creation can supersede an earlier `RETURNED` plan for the same carrier; a writer whose view of the carrier predates a superseding event, or predates a re-issued fitness determination, would be replacing a plan it never observed.

Filing a `ReportAmendment` requires `expected_report_version` in the request body, carrying the client's last observed `version` of the target `InspectionReport`. If that value does not equal the report's current `version`, the amendment is rejected with `ERR_STALE_REPORT_VERSION` and HTTP 412. A later amendment legitimately supersedes an earlier correction of the same violation, so the amendment must be written against the report state the issuing officer actually reviewed.

Creating a `CitationAdjudication` requires `expected_violation_version` in the request body, carrying the client's last observed `version` of the target `Violation`. If that value does not equal the violation's current `version`, the create is rejected with `ERR_STALE_VIOLATION_VERSION` and HTTP 412. An appeal outcome legitimately supersedes the prior adjudication of the same violation, so the new record must be written against the violation state the filer observed.

No other endpoint in the system takes a version field, and no other endpoint performs a concurrency check. Requests to endpoints outside these three are processed without any `expected_*_version` input.

### 2.7. Numeric Precision and Rounding

All rounding in this system uses the **round-half-up** convention: a value exactly at the midpoint rounds away from zero. The following precisions are fixed and are applied at the points named, not deferred to the end of a chain:

- Behaviour-category measures — both `provisional_measure` and `certified_measure` — are rounded to 3 decimal places.
- `percentile` is rounded to 1 decimal place, and it is computed from the already-rounded `certified_measure`, not from an unrounded intermediate.
- Each per-category contribution to the screening risk value is rounded to 2 decimal places **before** the contributions are summed. Summing unrounded products and rounding once at the end produces a different number and is incorrect.
- `iss_pre_credit_value` and `iss_value` are rounded to 1 decimal place.
- `data_quality_credit_pct` is rounded to 4 decimal places.
- `strict_attribution_score` and `adjudicated_attribution_score` are rounded to 2 decimal places.
- `completion_pct` is rounded to 1 decimal place.
- `time_weighted_severity` is exact to 1 decimal place, since its inputs are integers.
- Ages in days are whole numbers obtained by discarding any fractional day — a partial day never counts.
- Counters (`open_alert_count`, `challenge_quota_used`, `item_count` and the rest) are integers.
- `max_percentile` keeps the 1-decimal precision of the row it was taken from.

Numeric values are returned in response bodies as JSON numbers, never as strings.

### 2.8. Order of Evaluation for Rejections

When a single request violates more than one rule, the response reports the violation that comes first in the following precedence order. The ordering matters: a caller with a bad header and a stale version sees the header error, and a caller whose payload is malformed never learns that the target resource does not exist.

1. **Authentication.** `X-User-Role` and `X-User-ID` present and the role recognised, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorisation by role.** The acting role appears in the endpoint's authorised list, else `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Request shape.** Required fields present, enum members recognised, numeric ranges honoured, ordering constraints satisfied, and conditionally forbidden fields absent, else `ERR_INVALID_REQUEST` (400). Applies to every endpoint. This tier covers `inspection_level` between 1 and 6 inclusive, `severity_weight` between 1 and 10 inclusive, `oos_add_on` between 0 and 5 inclusive, `limit` between 1 and 100 inclusive, `offset` not negative, `inspection_end` strictly after `inspection_start`, `session_end` strictly after `session_start`, `measure_at_p50` strictly less than `measure_at_p65` which is strictly less than `measure_at_p80`, `monitor_percentile` strictly less than `intervention_percentile` which is no greater than `investigation_percentile`, `resolution_disposition` supplied only on a reject review action, and a `court_status` that is a legal target for the court dimension.
4. **Path resolution, left to right.** Each identifier in the URL path is resolved in the order it appears. Applies to every endpoint that has a path parameter. The reported error is the one belonging to the first identifier that fails: `ERR_CARRIER_NOT_FOUND`, `ERR_DRIVER_NOT_FOUND`, `ERR_VIOLATION_CODE_NOT_FOUND`, `ERR_REPORT_NOT_FOUND`, `ERR_VIOLATION_NOT_FOUND`, `ERR_AMENDMENT_NOT_FOUND`, `ERR_CHALLENGE_NOT_FOUND`, `ERR_ADJUDICATION_NOT_FOUND`, `ERR_BASIC_SCORE_NOT_FOUND`, `ERR_COACHING_NOT_FOUND`, `ERR_CAP_NOT_FOUND`, `ERR_CAP_ITEM_NOT_FOUND` or `ERR_SCORING_RUN_NOT_FOUND`, each at HTTP 404.
5. **Body reference resolution.** Every foreign key carried in a request body resolves to an existing record, else the corresponding 404 from the same family. Applies to every write endpoint that carries foreign keys. The keys checked here are `attributed_carrier_id`, `carrier_id`, `driver_id`, `violation_code_id`, `violation_id`, `report_id`, `target_violation_id`, `corrected_violation_code_id`, `corrected_driver_id`, `corrected_carrier_id`, `asserted_correct_carrier_id`, `asserted_correct_violation_code_id`, `duplicate_of_report_id` and `reduced_to_violation_code_id`.
6. **Carrier scope.** For a `CarrierAnalyst` or `CarrierSafetyManager`, `X-User-ID` matches the carrier owning the addressed resource, else `ERR_CARRIER_SCOPE_VIOLATION` (403). Applies to every single-resource read and every write performed by those two roles; list endpoints are filtered instead of rejected.
7. **Optimistic concurrency.** `expected_carrier_version`, `expected_report_version` and `expected_violation_version` equal their parent's current `version`, else `ERR_STALE_CARRIER_VERSION`, `ERR_STALE_REPORT_VERSION` or `ERR_STALE_VIOLATION_VERSION` (412). Applies to the three operations named in §2.6.
8. **State admissibility.** The target record is in a state that permits the requested transition, else one of `ERR_INVALID_REPORT_STATE`, `ERR_INVALID_CHALLENGE_STATE`, `ERR_INVALID_ADJUDICATION_STATE`, `ERR_ALREADY_APPLIED_TO_RECORD`, `ERR_ADJUDICATION_SUPERSEDED`, `ERR_INVALID_COACHING_STATE`, `ERR_INVALID_CAP_STATE`, `ERR_INVALID_CAP_ITEM_STATE` or `ERR_VIOLATION_NOT_ACTIVE` (409). Applies to every transition endpoint, across report status, challenge status, both adjudication dimensions, coaching status, plan status, action-item status and violation status.
9. **Segregation of duties**, `ERR_SEGREGATION_OF_DUTIES` (403), on the two corrective-action-plan operations described in §2.11: recording a branch review and deciding the plan.
10. **Out-of-service removal bar**, `ERR_OOS_REMOVAL_REQUIRES_ADJUDICATION` (422), on the accept-resolution review action for a data challenge.
11. **Coaching eligibility**, yielding `ERR_DRIVER_NOT_EMPLOYED`, `ERR_VIOLATION_NOT_ATTRIBUTED_TO_DRIVER`, `ERR_INVALID_REPORT_STATE` or `ERR_CODE_NOT_DRIVER_ATTRIBUTABLE` (422), on two operations: creating a coaching assignment and starting one.
12. **Challenge filing window**, `ERR_CHALLENGE_FILING_WINDOW_CLOSED` (422), on challenge submission.
13. **Information-response window**, `ERR_INFO_RESPONSE_WINDOW_CLOSED` (422), on a challenge submission made from the information-requested state.
14. **Scoring epoch monotonicity**, `ERR_SCORING_RUN_SNAPSHOT_REGRESSION` (409), on creating a scoring run.
15. **Challenge payload completeness by type**, `ERR_CHALLENGE_PAYLOAD_INCOMPLETE` or `ERR_CHALLENGE_TARGET_MISMATCH` (422), on creating a data challenge.
16. **Duplicate-target validity**, `ERR_DUPLICATE_TARGET_INVALID` (422), on two operations: creating a data challenge and accepting one.
17. **Amendment payload completeness and target ownership**, `ERR_AMENDMENT_PAYLOAD_INCOMPLETE` or `ERR_AMENDMENT_TARGET_MISMATCH` (422), on filing a report amendment.
18. **Driver-attribution completeness**, `ERR_DRIVER_ATTRIBUTION_MISSING` (422), on marking a report validated.
19. **Driver–carrier employment match**, `ERR_DRIVER_CARRIER_MISMATCH` (422), on three operations: setting a violation's driver attribution, appending a violation to a report, and ingesting a report.
20. **Evidence sufficiency**, `ERR_EVIDENCE_REQUIRED` (422), on challenge submission.
21. **Threshold availability**, `ERR_THRESHOLD_NOT_CONFIGURED` (409), on two operations: scoring a report and creating a scoring run.
22. **Duplicate inspection window on a vehicle**, `ERR_DUPLICATE_INSPECTION_WINDOW` (409), on ingesting a report.
23. **Coaching window conflict on a driver**, `ERR_COACHING_WINDOW_CONFLICT` (409), on creating a coaching assignment.
24. **Uniqueness**, yielding `ERR_DUPLICATE_DOT_NUMBER`, `ERR_DUPLICATE_VIOLATION_CODE`, `ERR_DUPLICATE_REPORT_NUMBER` or `ERR_DUPLICATE_CDL` (409), on registering a carrier, publishing a violation code, ingesting a report and registering a driver respectively.
25. **One open challenge per disputed target**, `ERR_DUPLICATE_OPEN_CHALLENGE` (409), on challenge submission.
26. **Information-request round cap**, `ERR_CHALLENGE_ROUND_LIMIT_EXCEEDED` (409), on the request-information review action.
27. **One pending adjudication per violation**, `ERR_ADJUDICATION_PENDING_EXISTS` (409), on creating a citation adjudication.
28. **One live plan per carrier**, `ERR_ACTIVE_CAP_EXISTS` (409), on creating a corrective action plan.
29. **Plan eligibility by fitness status**, `ERR_CAP_NOT_REQUIRED` (422), on two operations: creating a corrective action plan and submitting one.
30. **Plan item completeness**, `ERR_CAP_ITEMS_INCOMPLETE` (422), on submitting a corrective action plan.
31. **One recording per review branch**, `ERR_REVIEW_BRANCH_ALREADY_RECORDED` (409), on recording a branch review.
32. **Screening-selection consistency**, `ERR_SCREENING_SELECTION_INCONSISTENT` (422), on ingesting a report.
33. **Violation append window**, `ERR_INVALID_REPORT_STATE` (409), on appending a violation to a report.
34. **Challenge quota**, `ERR_CHALLENGE_QUOTA_EXCEEDED` (409), on challenge submission.

### 2.9. Reference Resolution and Nested Reads

Resource identifiers appearing in a URL path are validated in strict left-to-right order, and the first one that fails to resolve determines the 404 that is returned; the server does not attempt to resolve later segments once an earlier one has failed. The same applies to a nested collection under a parent: the parent identifier is resolved before the collection is queried, so a request for the evidence of a non-existent challenge reports `ERR_CHALLENGE_NOT_FOUND` rather than an empty list.

Because much of this system's structure lives in cross-aggregate references rather than in URL nesting, every list endpoint accepts filters on the foreign keys of the rows it returns. That is how a reader reaches records that were written as a side effect rather than by a direct request — a score row created by a cascade, or an amendment written by an accepted challenge, is discoverable by filtering the relevant collection on the identifier that links it back.

### 2.10. The Recomputation Cascade

Because the system is immediately consistent, any change to a violation's contribution propagates all the way to the affected carrier's screening band inside the same request, in a fixed order. The chain runs: pinned violation weights, then the owning report's rolled-up totals, then the affected carrier's behaviour-category score rows, then that carrier's intervention posture, then that carrier's screening risk and selection band. Alongside that chain, any change to which driver a violation is attributed to, or to the court factor applied to it, recomputes that driver's attribution aggregates, and any coaching assignment that a recompute has made pointless is waived, which in turn decrements the open-coaching counters on both the driver and the carrier.

Two ordering details are load-bearing. Intervention posture is always recomputed before screening risk, because the posture step is what refreshes the percentile inputs the screening step reads. And when a challenge resolution changes a carrier's accepted-challenge and resolved-challenge counters, those counters are recomputed **before** the screening-risk step, so the data-quality credit computed in that same request already reflects the resolution just recorded.

When a single request touches two carriers — the only case being a reattribution, which moves a report from a losing carrier to a gaining one — the full chain runs independently for each carrier.

### 2.11. Segregation of Duties

Federal auditors hold both the power to declare a carrier unfit and the power to accept the carrier's remediation plan, and the system refuses to let one person exercise both. Two bars are enforced, and both report `ERR_SEGREGATION_OF_DUTIES`.

The first bar is between determination and decision. When an auditor issues a safety fitness determination, their `X-User-ID` is stored on the carrier as `fitness_determined_by_user_id`. A later attempt to decide that carrier's corrective action plan — whether the decision is to accept or to return — is rejected when the deciding auditor's `X-User-ID` equals the stored `fitness_determined_by_user_id`.

The second bar is between the plan's two review branches. A plan under review is examined along a safety branch and a data branch, and the two branch reviews must be recorded by different auditors. Recording the second branch is rejected when the acting `X-User-ID` equals the identifier already recorded for the other branch.

## 3. Business Logic & Workflows

### 3.1. Carriers, Fleet Bands, Drivers and Reference Data

A motor carrier enters the system when an `FmcsaProgramAuditor` registers it with a `dot_number` — a USDOT number of six to eight digits, unique across all carriers, with a repeat rejected as `ERR_DUPLICATE_DOT_NUMBER` — a `legal_name` between 1 and 200 characters, an `average_power_units` count that may not be negative, and an `annual_vmt` figure for annual vehicle miles travelled that may not be negative either.

Two derived properties fall out of the fleet figures immediately. The `carrier_segment` is the fleet-size band: `SMALL` when `average_power_units` is 15 or fewer, `MEDIUM` when it is between 16 and 100 inclusive, and `LARGE` when it is greater than 100. The `utilization_factor` is a tiered multiplier keyed on miles per power unit, and it is described with the exposure denominator in §3.4 because that is the only place it is consumed. The segment additionally fixes `challenge_quota_limit`, the number of data challenges the carrier may file in a rolling thirty-day window: one for a `SMALL` carrier, three for a `MEDIUM` carrier, six for a `LARGE` one.

A freshly registered carrier starts entirely unscored. Its `safety_fitness_status` is `UNRATED`, with `fitness_determined_at` and `fitness_determined_by_user_id` both empty; `intervention_status` is `NONE`; `open_alert_count` is 0 and `max_percentile` is empty; `iss_pre_credit_value`, `data_quality_credit_pct` and `iss_value` are all 0.0 and `selection_band` is `PASS`; `challenge_quota_used` is 0; and the derived counters `oos_violation_count_24mo`, `scored_violation_count`, `unattributed_violation_count`, `accepted_challenge_count_24mo`, `resolved_challenge_count_24mo` and `open_coaching_count` are all 0. Critically, registration writes **no** behaviour-category score rows at all; those appear only when the carrier's first scoring event runs.

Issuing a safety fitness determination is an auditor action carrying a `determination` value — one of `UNRATED`, `SATISFACTORY`, `CONDITIONAL` or `UNSATISFACTORY` — and a `basis_note` recording why. It writes `safety_fitness_status` from the supplied `determination`, sets `fitness_determined_at` to the current logical clock, records the acting `X-User-ID` as `fitness_determined_by_user_id`, and increments the carrier's `version` by 1. That stored identifier becomes the segregation-of-duties bar of §2.11.

Drivers are the carrier's own to manage. A `CarrierSafetyManager` registers one with a `carrier_id`, a `cdl_number` that must be unique within that employing carrier (a repeat within the carrier is `ERR_DUPLICATE_CDL`), a `full_name` as printed on the licence, and optionally an `employment_status` of `ACTIVE`, `SUSPENDED` or `TERMINATED`, defaulting to `ACTIVE`. A new driver's aggregates all start empty: `attributed_violation_count` at 0, `strict_attribution_score` and `adjudicated_attribution_score` at 0.0, `coaching_required` false, `open_coaching_count` at 0. A safety manager may later revise a driver's `full_name` or `employment_status`; moving a driver to `TERMINATED` waives every coaching assignment of that driver in `ASSIGNED`, `IN_PROGRESS` or `OVERDUE` with a `waived_reason` of `DRIVER_SEPARATED`, which decrements both the carrier's and the driver's `open_coaching_count`, and the driver's `version` is incremented by 1.

The citation catalogue is federal reference data. Publishing a violation code requires a `code` string such as `392.2-SLLS2`, unique across the catalogue with a repeat reported as `ERR_DUPLICATE_VIOLATION_CODE`; a human-readable `description`; a `basic_category` naming the behaviour category the code scores into, one of `UNSAFE_DRIVING`, `HOURS_OF_SERVICE`, `VEHICLE_MAINTENANCE` or `DRIVER_FITNESS`; a `severity_weight` from 1 to 10; an optional `oos_add_on` from 0 to 5 that defaults to 2 and is applied only when the violation was placed out of service; and an optional `driver_attributable` flag defaulting to true, which governs whether the code may motivate driver coaching. Revising a published code may change its `severity_weight`, `oos_add_on`, `description` or `driver_attributable`, and increments the code's `version` by 1 — but it recomputes no scores whatsoever. Violations pinned under the old weight keep their snapshot until the next scoring pass touches them, and that lag is exactly what surfaces as a stale pin in §3.3.

Percentile reference data is published one row per behaviour category and fleet band. An `InterventionThreshold` row names its `basic_category` and its `carrier_segment`, an `effective_from` instant before which it may not be selected, and three reference measures that map onto fixed percentiles: `measure_at_p50` must be greater than zero, `measure_at_p65` must be greater than `measure_at_p50`, and `measure_at_p80` must be greater than `measure_at_p65`. Three percentile bars complete the row: `intervention_percentile`, the percentile at or above which a category goes to alert, defaulting to 65.0 and constrained to be greater than zero and no greater than 100; `monitor_percentile`, the percentile at or above which a category goes to monitor, defaulting to 50.0 and constrained to be greater than zero and strictly less than `intervention_percentile`; and `investigation_percentile`, the percentile at or above which the carrier's posture escalates to investigation, defaulting to 85.0 and constrained to be no less than `intervention_percentile`. Publishing a row recomputes nothing; it takes effect the next time a scoring event selects it.

Reference and roster collections are all readable with filters. Carriers may be listed by `safety_fitness_status`, `intervention_status`, `selection_band` and `carrier_segment`; drivers by `carrier_id`, `employment_status` and `coaching_required`; violation codes by `basic_category` and `driver_attributable`; threshold rows by `basic_category` and `carrier_segment`. Score rows may be listed by `carrier_id`, `basic_category`, `alert_status`, `scoring_run_id` and `threshold_id`.

### 3.2. Report Intake: Ingestion, Violations and Validation

A `StateInspectionOfficer` ingests a roadside inspection with a `report_number` issued by the state — globally unique, with a repeat rejected as `ERR_DUPLICATE_REPORT_NUMBER` — an `inspection_state` given as exactly two uppercase letters, an `inspection_level` from 1 to 6 naming the MCSAP inspection level, an `inspection_start` and an `inspection_end` that must fall strictly after the start, the `vehicle_vin` of the inspected power unit, the `attributed_carrier_id` of the carrier the report will score against, a `selection_source` explaining why the vehicle was pulled in (`ISS_SCREENING`, `RANDOM`, `POST_CRASH`, `COMPLAINT` or `WEIGH_STATION`), and optionally a `driver_id` for the driver recorded on the report. If a `driver_id` is supplied but that driver is not employed by the attributed carrier, ingestion fails with `ERR_DRIVER_CARRIER_MISMATCH`.

Ingestion writes the report in `RECEIVED` status and takes two snapshots of the carrier's screening posture at that moment: `iss_value_at_selection` captures the carrier's current screening risk value and `selection_band_at_selection` captures its current band, one of `PASS`, `OPTIONAL` or `INSPECT`. The report's `original_carrier_id` and `duplicate_master_report_id` are left empty, `reattributed` is false, `active_violation_count` is 0, `total_time_weighted_severity` is 0.0, and both `scored_at` and `severity_basis_utc` are empty until the first scoring pass.

Two intake guards fire at ingestion. The first is duplicate detection on the vehicle. The system takes the new report's closed interval from `inspection_start` to `inspection_end`, widens it by two hours at each end, and rejects the ingestion with `ERR_DUPLICATE_INSPECTION_WINDOW` if any existing report that is not `RESCINDED` and carries the same `vehicle_vin` has a closed interval intersecting the widened one. Endpoints that merely touch count as an intersection — an existing inspection ending at exactly the instant the widened new window begins is a conflict. The two-hour buffer exists because a single stop keyed twice by two officers usually differs by minutes, not hours.

The second guard is screening consistency. A report claiming `ISS_SCREENING` as its `selection_source` asserts that the screening system flagged this carrier, so the attributed carrier's `selection_band` must currently be `OPTIONAL` or `INSPECT`. If it is `PASS`, the assertion contradicts the screening data and the ingestion is rejected with `ERR_SCREENING_SELECTION_INCONSISTENT`.

Violations are appended to a report only while that report is still `RECEIVED`; an append against a report in any other status is rejected with `ERR_INVALID_REPORT_STATE`. Each append names the `violation_code_id` the inspector wrote, the `unit_type` recording whether the violation was written against the `VEHICLE` or the `DRIVER`, an optional `out_of_service` flag defaulting to false, and an optional `driver_id`. On creation the system sets `effective_violation_code_id` equal to the supplied `violation_code_id` — they diverge only when a correction lands — copies `basic_category` from the code, copies `attributed_carrier_id` from the owning report, sets the violation's `status` to `ACTIVE`, leaves `removal_reason` empty, sets `under_challenge` to false, sets `has_stale_code_pin` to false, and initialises `time_weight` to 0 and `time_weighted_severity` to 0.0 because no scoring pass has run. Appending recomputes the report's `active_violation_count` and increments the report's `version` by 1. A `driver_id` supplied on the violation must belong to a driver employed by the violation's attributed carrier, else `ERR_DRIVER_CARRIER_MISMATCH`.

Marking a report validated moves it from `RECEIVED` to `VALIDATED`. The gate is attribution completeness: every violation of the report whose `unit_type` is `DRIVER` must have a non-empty `driver_id` either on the violation itself or on the report, and a report failing that test is rejected with `ERR_DRIVER_ATTRIBUTION_MISSING`. Validation deliberately writes no score — `total_time_weighted_severity` stays at 0.0 — and it refreshes `updated_at` and increments the report's `version` by 1.

Reports are readable with filters on `attributed_carrier_id`, `original_carrier_id`, `driver_id`, `duplicate_master_report_id`, `status` and `vehicle_vin`. Violations are readable with filters on `report_id`, `violation_code_id`, `effective_violation_code_id`, `driver_id`, `attributed_carrier_id`, `status`, `basic_category`, `under_challenge` and `out_of_service`; that last collection is the reverse-reachability channel for every violation foreign key, since violations are frequently mutated by cascades rather than by direct request.

### 3.3. Scoring a Report: Pinning Severity and Time Weight

Scoring is what turns an inspection into a number. It advances a report from `VALIDATED` to `SCORED`, and — this is the correction cycle — also from `AMENDED` back to `SCORED`; a report in any status other than `VALIDATED` or `AMENDED` cannot be scored and is rejected with `ERR_INVALID_REPORT_STATE`. Scoring is available to a `StateInspectionOfficer` and to an `FmcsaProgramAuditor`.

The heart of the pass is the **severity pin**, which is deliberately a snapshot rather than a live lookup. For every violation of the report whose `status` is `ACTIVE` or `RECODED`, the system establishes a basis instant — the scoring run's captured snapshot when the pin runs inside a run, otherwise the current logical clock — and computes the violation's age as the number of whole days from the report's `inspection_start` to that basis, discarding any fractional day. The age then selects an integer `time_weight`: 3 for the first 26 weeks, meaning an age of 182 days or fewer; 2 for an age from 183 through 365 days inclusive; 1 for an age from 366 through 730 days inclusive; and 0 once the age reaches 731 days, so an inspection more than two years old contributes nothing at all.

The pin then reads the `ViolationCode` identified by the violation's `effective_violation_code_id` and copies three values onto the violation. `code_weight_snapshot` takes the code's `severity_weight`. `oos_add_on_snapshot` takes the code's `oos_add_on` when the violation's `out_of_service` flag is true, and is 0 otherwise. `pinned_violation_code_version` takes the code record's current `version`. Finally, `time_weighted_severity` is computed as the sum of `code_weight_snapshot` and `oos_add_on_snapshot`, multiplied by `time_weight`. A violation whose `status` is `REMOVED` is never re-pinned and its `time_weighted_severity` is forced to 0.0, as is the case for any violation before its first scoring pass. The basis instant used for the pass is stamped on the report as `severity_basis_utc`, and `scored_at` records the logical-clock instant of the pass.

Between two scoring passes the pinned snapshot governs. If an auditor revises a code's `severity_weight` after a violation has been pinned, the violation keeps scoring at the old weight; the divergence is visible because `has_stale_code_pin` becomes true whenever the effective code's current `version` differs from the violation's `pinned_violation_code_version`, and the score only moves at the next pass. When a scoring pass runs — or when any correction side effect re-pins a violation, which happens on an accepted incorrect-code challenge, on a code-correction amendment, and when a reduced court result is pushed to the record — the current code row is read again and the snapshot is overwritten.

Scoring rolls the pinned violations up onto the report: `active_violation_count` becomes the number of the report's violations whose `status` is `ACTIVE` or `RECODED`, and `total_time_weighted_severity` becomes the sum of `time_weighted_severity` over that same set. Because the report's totals changed, the cascade of §2.10 then runs for the report's attributed carrier: all four behaviour-category score rows, then the carrier's intervention posture, then the carrier's screening risk and band, then the attribution aggregates of every driver referenced by the report's violations. Scoring also increments the report's `version` by 1. One precondition guards the whole pass: for every behaviour category that holds at least one includable violation of the attributed carrier, a threshold reference row must be selectable, and if none is, the pass is rejected with `ERR_THRESHOLD_NOT_CONFIGURED`.

While a report sits in `AMENDED` it is excluded from every measure, which is why the `SCORED → AMENDED → SCORED` cycle is the mechanism by which a post-amendment code change takes effect: the amendment pulls the report out of the scored population, and the next pass re-pins it with the corrected code. A report that reaches `RESCINDED` is terminal and never returns.

### 3.4. Behaviour-Category Measures, Percentiles and Intervention Posture

Each carrier carries exactly four score rows, one per behaviour category, identified by the pair of `carrier_id` and `basic_category`. Rows are created lazily on the carrier's first scoring event and updated in place from then on; they are never duplicated. Each row records the `snapshot_utc` that is the aging basis of its current numbers, the `scoring_run_id` of the run that last wrote it — empty when the last write came from an on-demand pass rather than from a run — and the `threshold_id` of the reference row used for its percentile mapping.

**Building the denominator.** The system first computes miles per power unit as the carrier's `annual_vmt` divided by its `average_power_units`, treating the divisor as 1 whenever `average_power_units` is 0. That ratio selects the `utilization_factor`: 1.0 below 20,000 miles per power unit; 1.2 from 20,000 up to but not including 60,000; 1.5 from 60,000 up to but not including 100,000; and 1.8 at 100,000 miles per power unit and above. Power-unit exposure is then `average_power_units` multiplied by `utilization_factor`, with a floor of 1.0. Separately, `relevant_inspection_count` is the number of the carrier's reports whose `status` is `SCORED` and whose `inspection_start` is within 730 whole days — two years — of the row's `snapshot_utc`. The `denominator_value` actually used depends on the category: for `VEHICLE_MAINTENANCE` it is `relevant_inspection_count` with a floor of 1.0; for `HOURS_OF_SERVICE` it is the smaller of power-unit exposure and twice `relevant_inspection_count`, again with a floor of 1.0; for `UNSAFE_DRIVING` and `DRIVER_FITNESS` it is power-unit exposure.

**Building the numerator.** A violation is *included* in a category row when its `status` is `ACTIVE` or `RECODED`, its owning report's `status` is `SCORED`, that report's `attributed_carrier_id` is this carrier, its `time_weight` is greater than 0, and its `basic_category` matches the row's category. Over that set, `total_time_weighted_severity` is the sum of `time_weighted_severity`, `challenged_time_weighted_severity` is the portion of that sum contributed by violations whose `under_challenge` flag is true, and `included_violation_count` is the number of included violations.

**Two measures, one operative.** The row publishes both variants. `provisional_measure` is `total_time_weighted_severity` divided by `denominator_value`, rounded half up to 3 decimal places; it is the all-data view reported back to the carrier and it deliberately keeps challenged violations in the numerator. `certified_measure` is `total_time_weighted_severity` less `challenged_time_weighted_severity`, divided by `denominator_value`, rounded half up to 3 decimal places; it is the operative variant, and it alone drives `percentile`, `alert_status`, intervention posture and screening risk. The consequence is intentional: filing a challenge immediately lowers the operative measure even though the underlying report data has not been touched.

**Selecting the reference row.** Candidate threshold rows are those whose `basic_category` equals the row's category, whose `carrier_segment` equals the carrier's `carrier_segment`, and whose `effective_from` is at or before the row's `snapshot_utc`. Candidates are ranked by `effective_from` descending and, for ties, by `created_at` descending; the first is selected. If the candidate set is empty while `included_violation_count` is greater than 0, the scoring event fails with `ERR_THRESHOLD_NOT_CONFIGURED`. If the candidate set is empty and `included_violation_count` is 0, `threshold_id` is simply left empty.

**Mapping to a percentile.** Let the certified measure be the already-rounded `certified_measure` and let the reference row be the selected threshold. When `relevant_inspection_count` is 0, `percentile` is empty. When the certified measure is zero or below, the percentile is 0.0. When it is above zero but no greater than `measure_at_p50`, the percentile is fifty multiplied by the certified measure and divided by `measure_at_p50`. When it is above `measure_at_p50` but no greater than `measure_at_p65`, the percentile is fifty plus fifteen multiplied by the amount by which the certified measure exceeds `measure_at_p50` and divided by the difference between `measure_at_p65` and `measure_at_p50`. When it is above `measure_at_p65` but no greater than `measure_at_p80`, the percentile is sixty-five plus fifteen multiplied by the amount by which the certified measure exceeds `measure_at_p65` and divided by the difference between `measure_at_p80` and `measure_at_p65`. When it is above `measure_at_p80`, the percentile is eighty plus twenty multiplied by the amount by which the certified measure exceeds `measure_at_p80` and divided by `measure_at_p80`, and the result is capped by taking the smaller of that figure and 100.0. Every branch is rounded half up to 1 decimal place.

**Threshold posture.** The row's `alert_status` is `NOT_ENOUGH_DATA` when `relevant_inspection_count` is 0, and that condition wins over everything else. Otherwise it is `ALERT` when `percentile` is at or above the reference row's `intervention_percentile`, `MONITOR` when `percentile` is at or above `monitor_percentile` but below the intervention bar, and `CLEAR` in all remaining cases. A row with no included violations and therefore no selected reference row lands at `percentile` 0.0 and `alert_status` `CLEAR` — unless `relevant_inspection_count` is 0, in which case `NOT_ENOUGH_DATA` applies instead.

**Rolling up to intervention posture.** Immediately after the four rows are rewritten, the carrier's posture is re-derived from them. `open_alert_count` is the number of the carrier's score rows whose `alert_status` is `ALERT`. `max_percentile` is the largest `percentile` across the carrier's rows, ignoring rows whose percentile is empty, and is itself empty when every row's percentile is empty. The investigation bar is the `investigation_percentile` of the threshold row selected for the category that holds `max_percentile`. Then `intervention_status` is `INVESTIGATION` when `open_alert_count` is 2 or more; `INVESTIGATION` also when `max_percentile` is present and at or above the investigation bar; `WARNING_LETTER` when neither of those holds but `open_alert_count` is at least 1; and `NONE` otherwise. Two alerting categories, or one category deep enough into the tail, are equivalent triggers for a full investigation.

### 3.5. Roadside Screening Risk and the Data-Quality Credit

The screening risk value is what a weigh station consults, and it is re-derived immediately after intervention posture on every cascade. It is built in four steps, and the order of the roundings is part of the specification rather than an implementation detail.

**Step one — weighted category contributions.** The four behaviour categories carry fixed weights: `UNSAFE_DRIVING` at 0.35, `HOURS_OF_SERVICE` at 0.30, `VEHICLE_MAINTENANCE` at 0.25 and `DRIVER_FITNESS` at 0.10. A category's contribution is 0.00 whenever that row's `alert_status` is `NOT_ENOUGH_DATA` or its `percentile` is empty; otherwise it is the row's `percentile` multiplied by the category's weight, **rounded half up to 2 decimal places at this point**. The weight of a category with insufficient data is not redistributed to the others — the carrier simply scores lower.

**Step two — sum the rounded contributions.** The raw figure is the sum of the four already-rounded contributions. Summing the unrounded products and rounding once at the end yields a different value and is wrong. To the raw figure the system adds an out-of-service adder: half a point for each of the carrier's out-of-service violations counted in `oos_violation_count_24mo`, capped at 10.0 points however many there are. That counter is the number of the carrier's violations whose `out_of_service` flag is true, whose `status` is `ACTIVE` or `RECODED`, that sit on a report of this carrier whose `status` is `SCORED`, and whose `time_weight` is greater than 0. The sum of the raw figure and the adder is then capped at 100.0 and rounded half up to 1 decimal place to give `iss_pre_credit_value`.

**Step three — the data-quality credit.** A carrier that has successfully challenged bad data has demonstrated that its profile needs correcting, and it earns a credit for that. The credit tier is keyed on `iss_pre_credit_value` and on nothing else: 0.06 when `iss_pre_credit_value` is 75.0 or above, 0.04 when it is 50.0 or above but below 75.0, and 0.02 in all other cases. Re-deriving the tier from the post-credit value is the classic error and produces the wrong answer. The carrier's accepted rate is `accepted_challenge_count_24mo` divided by `resolved_challenge_count_24mo`, treating the divisor as 1 whenever `resolved_challenge_count_24mo` is 0. Then `data_quality_credit_pct` is the credit tier multiplied by the smaller of 1.0 and the accepted rate, rounded half up to 4 decimal places. The two counters behind the rate are maintained over a two-year window: `accepted_challenge_count_24mo` is the number of the carrier's challenges whose `status` is `RESOLVED_ACCEPTED` and whose `resolved_at` falls within 730 days of the current logical clock, and `resolved_challenge_count_24mo` is the number whose `status` is either `RESOLVED_ACCEPTED` or `RESOLVED_REJECTED` with `resolved_at` inside the same 730-day window.

**Step four — apply the credit and band the result.** `iss_value` is `iss_pre_credit_value` multiplied by one minus `data_quality_credit_pct`, rounded half up to 1 decimal place. Note that the credit is applied to the already-rounded pre-credit figure, and the product is rounded again. The `selection_band` then follows directly: `INSPECT` when `iss_value` is 75.0 or above, `OPTIONAL` when it is 50.0 or above but below 75.0, and `PASS` below 50.0.

A dedicated computed read exposes the whole derivation for one carrier without recomputing anything: it returns the `carrier_id`, the `iss_pre_credit_value`, the `data_quality_credit_pct`, the `iss_value`, the `selection_band`, the `oos_adder` that step two applied, the `oos_violation_count_24mo` behind it, the per-category breakdown as `category_contributions`, and the list of categories excluded for insufficient data as `not_enough_data_categories`. The breakdown is an array of exactly four objects, one per behaviour category, in the fixed order `UNSAFE_DRIVING`, `HOURS_OF_SERVICE`, `VEHICLE_MAINTENANCE`, `DRIVER_FITNESS`; each object carries `basic_category`, the category's fixed weight as `category_weight`, the already-rounded `contribution` of step one, and the score row's `percentile` and `alert_status` — the last two being empty when the carrier holds no score row for that category at all. `not_enough_data_categories` lists, in that same fixed order, the `basic_category` values of exactly those categories step one excluded — the ones with no score row at all, with an `alert_status` of `NOT_ENOUGH_DATA`, or with an empty `percentile` — and not merely those whose contribution happened to compute to zero.

### 3.6. Filing, Reviewing and Resolving a Data Challenge

A challenge is the carrier's formal assertion that a piece of inspection data is wrong. A `CarrierAnalyst` opens one in `DRAFT` against a `report_id`, declaring a `challenge_type` of `WRONG_CARRIER`, `DUPLICATE_REPORT`, `INCORRECT_VIOLATION_CODE` or `VIOLATION_NOT_SUPPORTED`, and writing its argument into `narrative`. Depending on the type, the draft also carries the disputed `target_violation_id`, the `asserted_correct_carrier_id` the filer says the report belongs to, the `duplicate_of_report_id` naming the surviving report, or the `asserted_correct_violation_code_id` the filer says should apply. On creation the system copies the report's `attributed_carrier_id` onto the challenge as its own `carrier_id`, sets `status` to `DRAFT`, sets `info_request_count` to 0 and `evidence_count` to 0, and consumes no quota whatsoever — drafting is free.

Payload completeness is enforced at creation, by type. A `WRONG_CARRIER` challenge needs an `asserted_correct_carrier_id` that is not the filing carrier itself. A `DUPLICATE_REPORT` challenge needs a `duplicate_of_report_id`. An `INCORRECT_VIOLATION_CODE` challenge needs both a `target_violation_id` and an `asserted_correct_violation_code_id`. A `VIOLATION_NOT_SUPPORTED` challenge needs a `target_violation_id`. A missing conditional field, or an `asserted_correct_carrier_id` equal to the filing carrier, is rejected with `ERR_CHALLENGE_PAYLOAD_INCOMPLETE`; a `target_violation_id` that does not belong to the named `report_id` is rejected with `ERR_CHALLENGE_TARGET_MISMATCH`. Where a `duplicate_of_report_id` is supplied it must name a *different* report that carries the same `vehicle_vin` and the same `attributed_carrier_id` as the challenged report and whose `status` is not `RESCINDED`; anything else — the same report, a different vehicle, a different carrier, or an already-rescinded target — is `ERR_DUPLICATE_TARGET_INVALID`. That same duplicate-target test is re-run at accept time, because the surviving report may have been rescinded in the interval.

Evidence is attached to a challenge that has not yet resolved. Each document carries an `evidence_type` from `BILL_OF_LADING`, `LEASE_AGREEMENT`, `GPS_LOG`, `ELD_RECORD`, `PHOTO`, `COURT_DOCUMENT` or `OTHER`, a `document_uri` locating the stored file, and a `description` of what the document proves. Each evidence row records its owning challenge as `challenge_id`. The system stamps each row with `submitted_round`, copied from the challenge's `info_request_count` at the moment of upload — that stamp is what distinguishes the original filing package from follow-up material supplied in answer to a later information request. Attaching a document recomputes the challenge's `evidence_count` and increments the challenge's `version` by 1.

Submitting a challenge moves it from `DRAFT` to `SUBMITTED`; submission is also how an analyst answers an information request, moving the challenge from `INFO_REQUESTED` back to `SUBMITTED`. A submit attempted from any other status is rejected with `ERR_INVALID_CHALLENGE_STATE`. A first submission out of `DRAFT` runs five gates. The challenged report must be in `VALIDATED`, `SCORED` or `AMENDED` status, else `ERR_INVALID_REPORT_STATE`. The filing window must be open: the number of whole days between the report's `inspection_start` and the current logical clock must be no more than 730 — two years of contestability, matching the scoring lookback — and a later submission is rejected with `ERR_CHALLENGE_FILING_WINDOW_CLOSED`. The evidence package must satisfy the type: a `WRONG_CARRIER` challenge needs at least one evidence row whose `evidence_type` is `BILL_OF_LADING` or `LEASE_AGREEMENT`; an `INCORRECT_VIOLATION_CODE` challenge needs at least one whose type is `PHOTO`, `ELD_RECORD` or `COURT_DOCUMENT`; a `DUPLICATE_REPORT` or `VIOLATION_NOT_SUPPORTED` challenge needs only that `evidence_count` be at least 1; a shortfall is `ERR_EVIDENCE_REQUIRED`. No other challenge sharing the same combination of `report_id`, `challenge_type` and `target_violation_id` may already be in `SUBMITTED`, `UNDER_REVIEW` or `INFO_REQUESTED`, else `ERR_DUPLICATE_OPEN_CHALLENGE`. And the carrier's `challenge_quota_used` must be strictly below its `challenge_quota_limit`, else `ERR_CHALLENGE_QUOTA_EXCEEDED`.

A successful first submission stamps `submitted_at` with the logical clock and `filing_age_days_at_submit` with the number of whole days between the report's `inspection_start` and that submit instant, and it increments the carrier's `challenge_quota_used` by 1. It then sets `under_challenge` to true on the violations the challenge covers, and coverage depends on type: an `INCORRECT_VIOLATION_CODE` or `VIOLATION_NOT_SUPPORTED` challenge covers only the violation named by `target_violation_id`, while a `WRONG_CARRIER` or `DUPLICATE_REPORT` challenge covers *every* violation of the report. Because `under_challenge` changed, the affected score rows' `challenged_time_weighted_severity` and `certified_measure` are recomputed, which moves `percentile` and `alert_status`, which moves the carrier's `open_alert_count`, `max_percentile` and `intervention_status`, which moves the carrier's screening risk and `selection_band`. The challenge's `version` is incremented by 1.

A resubmission out of `INFO_REQUESTED` runs a different pair of gates. The current logical clock must be at or before the challenge's `info_response_deadline`, else `ERR_INFO_RESPONSE_WINDOW_CLOSED`. And at least one evidence row must exist whose `submitted_round` equals the challenge's current `info_request_count` — answering with nothing new is `ERR_EVIDENCE_REQUIRED`. A resubmission refreshes `submitted_at` and `filing_age_days_at_submit` and increments the challenge's `version` by 1, but it leaves `under_challenge` and `challenge_quota_used` exactly as they are: the round was already counted when the challenge was first filed.

Federal review is an `FmcsaReviewOfficer` capability driven by an `action` value, accompanied by a `review_note` and, for one action, a `resolution_disposition`. The `ASSIGN` action moves a challenge from `SUBMITTED` to `UNDER_REVIEW`, records the reviewing officer and increments `version` by 1. The `REQUEST_INFO` action moves it from `UNDER_REVIEW` to `INFO_REQUESTED`, but only while `info_request_count` is still below 3; a fourth request on one challenge is rejected with `ERR_CHALLENGE_ROUND_LIMIT_EXCEEDED`. A permitted request increments `info_request_count` by 1 and sets `info_response_deadline` to the current logical clock plus 30 days. The cycle `UNDER_REVIEW → INFO_REQUESTED → SUBMITTED → UNDER_REVIEW` may therefore run at most three times before the officer must decide on the record in front of them.

The `RESOLVE_REJECT` action moves a challenge from `UNDER_REVIEW` to `RESOLVED_REJECTED` and requires a `resolution_disposition` of either `INSUFFICIENT_EVIDENCE` or `NOT_SUBSTANTIATED` in the body; any other value, or none, is `ERR_INVALID_REQUEST`. Rejection stamps `resolved_at`, records the officer's identifier as `resolved_by_user_id`, writes the supplied disposition, and clears `under_challenge` on the covered violations — which restores `certified_measure` to its full value, which recomputes `percentile` and `alert_status`, which recomputes the carrier's intervention posture, and then its screening risk. It recomputes the carrier's `resolved_challenge_count_24mo`, leaving `accepted_challenge_count_24mo` unchanged, and increments the challenge's `version` by 1.

The `RESOLVE_ACCEPT` action moves a challenge from `UNDER_REVIEW` to `RESOLVED_ACCEPTED`, and it is where the system does real damage to the record. Two preconditions guard it. For a `VIOLATION_NOT_SUPPORTED` or `INCORRECT_VIOLATION_CODE` challenge whose target violation carries an `out_of_service` flag of true, a non-superseded `CitationAdjudication` on that violation must already show a `court_status` of `DISMISSED` or `NOT_GUILTY`; without one, the acceptance is refused with `ERR_OOS_REMOVAL_REQUIRES_ADJUDICATION`. An out-of-service order is a safety event, and only a court may erase it. For a `DUPLICATE_REPORT` challenge, the duplicate target must still be valid on the terms described above, else `ERR_DUPLICATE_TARGET_INVALID`. Acceptance stamps `resolved_at` and `resolved_by_user_id`, writes the type-specific `resolution_disposition`, clears `under_challenge` on the covered violations, and increments the challenge's `version` by 1.

Each of the four types then drives a distinct cascade, and each cascade is stated here in full because none of them is guessable from the others.

A `WRONG_CARRIER` acceptance takes the disposition `REATTRIBUTED`. It rewrites the report's `attributed_carrier_id` to the `asserted_correct_carrier_id`, stores the previous value as `original_carrier_id`, and sets `reattributed` to true. That report mutation rewrites `attributed_carrier_id` on every violation of the report and clears `driver_id` on any violation whose driver belongs to a different carrier than the new attributed carrier. Those violation mutations force a full score-row recompute for both the losing and the gaining carrier; each carrier's score change forces that carrier's intervention posture recompute; each posture change forces that carrier's screening-risk recompute. Each cleared `driver_id` forces that driver's attribution aggregates to recompute, which waives that driver's `ASSIGNED` and `IN_PROGRESS` coaching assignments with a `waived_reason` of `ATTRIBUTION_CLEARED`.

A `DUPLICATE_REPORT` acceptance takes the disposition `REPORT_RESCINDED` and drives the report to `RESCINDED`, from either `SCORED` or `VALIDATED`. The report's `duplicate_master_report_id` is set to the challenge's `duplicate_of_report_id`, marking which report survived. Every violation of the rescinded report moves to `REMOVED` with a `removal_reason` of `DUPLICATE_RESCINDED` and a `time_weighted_severity` forced to 0.0. When the rescinded report had been `SCORED`, all four of the carrier's score rows are recomputed — note that `relevant_inspection_count` drops by one, so the denominator for `VEHICLE_MAINTENANCE` and possibly for `HOURS_OF_SERVICE` shifts as well — then `open_alert_count` and `intervention_status`, then screening risk. The vanished attributed violations force the affected drivers' aggregates to recompute and their `ASSIGNED` and `IN_PROGRESS` coaching assignments to be waived with `waived_reason` `VIOLATION_REMOVED`. When the rescinded report had only reached `VALIDATED`, the violations still move to `REMOVED` but no score recompute is required, because the report never contributed to a measure.

An `INCORRECT_VIOLATION_CODE` acceptance takes the disposition `CODE_CORRECTED`. It sets the target violation's `effective_violation_code_id` to the `asserted_correct_violation_code_id`, moves the violation's `status` to `RECODED`, re-pins `code_weight_snapshot`, `oos_add_on_snapshot` and `pinned_violation_code_version` from the new code, and recomputes `time_weighted_severity`. Because the violation's `basic_category` may have moved with the code, the changed violation forces a score-row recompute of *both* affected categories — the one it left and the one it joined — which forces the intervention-posture and screening-risk recomputes. The acceptance also writes a `ReportAmendment` row whose `source_challenge_id` points back at the challenge, so the corrective paper trail is identical whether the state agency filed the correction itself or the carrier won it.

A `VIOLATION_NOT_SUPPORTED` acceptance takes the disposition `VIOLATION_REMOVED`. It moves the target violation's `status` to `REMOVED`, writes a `removal_reason` of `CHALLENGE_ACCEPTED`, and forces its `time_weighted_severity` to 0.0. The removal forces the score-row, intervention-posture and screening-risk recomputes, plus an attribution recompute for the violation's driver that waives any coaching assignment linked to that violation with `waived_reason` `VIOLATION_REMOVED`.

One ordering rule spans all four cascades: the carrier's `accepted_challenge_count_24mo` and `resolved_challenge_count_24mo` are recomputed **before** the screening-risk step, so the data-quality credit computed in the same request already reflects the resolution just recorded.

Withdrawal is the analyst's escape hatch and is permitted from `DRAFT`, `SUBMITTED` or `INFO_REQUESTED`, optionally carrying a `withdraw_note`. Withdrawing a `DRAFT` challenge changes no quota — a draft never consumed any — and touches no score. Withdrawing from `SUBMITTED` decrements the carrier's `challenge_quota_used` by 1 as compensation for the submit increment, and clears `under_challenge` on the covered violations with the full downstream cascade through `certified_measure`, `alert_status`, intervention posture and screening risk. Withdrawing from `INFO_REQUESTED` does exactly the same as withdrawing from `SUBMITTED`. In every case the challenge's `version` is incremented by 1. `RESOLVED_ACCEPTED`, `RESOLVED_REJECTED` and `WITHDRAWN` are all terminal.

The quota itself is a small ledger. Between scoring runs it is maintained incrementally: a submit adds 1 to `challenge_quota_used` and a withdrawal subtracts 1, floored at 0 so the counter can never go negative. Every scoring run then re-derives the counter from scratch, walking the carrier's challenges in ascending `submitted_at` order with ties broken by ascending `created_at`, and counting those whose `status` is `SUBMITTED`, `UNDER_REVIEW`, `INFO_REQUESTED`, `RESOLVED_ACCEPTED` or `RESOLVED_REJECTED` and whose `submitted_at` falls after the run's snapshot instant less 30 days and at or before the run's snapshot instant. Withdrawn challenges and challenges that were never submitted are excluded from that re-derivation, which is how the rolling window actually rolls.

An `INFO_REQUESTED` challenge that nobody answers is closed by the scoring epoch rather than by an officer, as described in §3.11. Challenges are readable with filters on `report_id`, `carrier_id`, `status`, `challenge_type`, `target_violation_id`, `asserted_correct_carrier_id`, `duplicate_of_report_id` and `asserted_correct_violation_code_id`.

### 3.7. State-Agency Corrections: Amendments

Carriers dispute data; state agencies simply fix it. An amendment is the issuing agency's own correction, filed by a `StateInspectionOfficer` against a report in `VALIDATED`, `SCORED` or `AMENDED` status — any other status is `ERR_INVALID_REPORT_STATE`. The filing carries `expected_report_version` for the concurrency guard of §2.6, an `amendment_type`, a free-text `rationale` justifying the change, and whichever correction field the type requires.

The four types and their conditional fields are these. A `VIOLATION_CODE_CORRECTION` requires a `target_violation_id` and a `corrected_violation_code_id`. A `DRIVER_ATTRIBUTION_CORRECTION` requires a `target_violation_id` and a `corrected_driver_id`. A `VIOLATION_REMOVAL` requires a `target_violation_id`. A `CARRIER_REATTRIBUTION` requires a `corrected_carrier_id` that differs from the report's current attributed carrier, and is the only type that does not require a `target_violation_id`. A missing conditional field, or a `CARRIER_REATTRIBUTION` that names the carrier the report already scores against, is `ERR_AMENDMENT_PAYLOAD_INCOMPLETE`. A `target_violation_id` that does not belong to the amended report is `ERR_AMENDMENT_TARGET_MISMATCH`.

Each type applies a specific correction. `VIOLATION_CODE_CORRECTION` sets the target violation's `effective_violation_code_id` to the `corrected_violation_code_id` and moves its `status` to `RECODED`. `DRIVER_ATTRIBUTION_CORRECTION` sets the target violation's `driver_id` to the `corrected_driver_id`. `CARRIER_REATTRIBUTION` stores the report's old `attributed_carrier_id` as `original_carrier_id`, writes `corrected_carrier_id` into `attributed_carrier_id`, sets `reattributed` to true, and rewrites `attributed_carrier_id` on every violation of the report. `VIOLATION_REMOVAL` moves the target violation's `status` to `REMOVED`, writes a `removal_reason` of `AMENDMENT_REMOVAL`, and forces its `time_weighted_severity` to 0.0.

Filing an amendment moves the report to `AMENDED` — from `SCORED` or from `VALIDATED`, and `AMENDED` reports may be amended again — and increments the report's `version` by 1. The amendment itself is written as an append-only record capturing `applied_at` (the logical-clock instant at which the correction mutated the report), `report_version_before` (the report's `version` observed before the amendment applied) and `report_version_after` (its `version` afterwards). Its `source_challenge_id` is left empty when the officer filed the correction directly, and is populated only when the amendment was generated by an accepted challenge as described in §3.6.

The consequences differ by the report's prior status. When the amended report was `SCORED`, it has now left the scored population, so all four score rows of the old attributed carrier are recomputed and — for a `CARRIER_REATTRIBUTION` — all four rows of the new attributed carrier as well, minted on the spot when the gaining carrier has never held score rows before; each of those recomputes then drives that carrier's intervention posture and, after it, that carrier's screening risk. Both carriers' rows are aged against the basis already stamped on the old attributed carrier's score rows rather than against a fresh reading of the clock, so the correction alone never re-ages anything. Because violation attribution may have changed, the affected drivers' aggregates recompute, and their `ASSIGNED` and `IN_PROGRESS` coaching assignments are waived where the linked violation has become `REMOVED` (with `waived_reason` `VIOLATION_REMOVED`) or where it has lost its driver (with `waived_reason` `ATTRIBUTION_CLEARED`). When the amended report had only reached `VALIDATED`, the same corrections are applied to the violations but no score recompute is needed, because the report was never scored. Bringing the corrected report back into the measures requires a fresh scoring pass, which re-pins the weights so the correction actually takes effect.

Amendment records are readable with filters on `report_id`, `target_violation_id`, `corrected_violation_code_id`, `corrected_driver_id`, `corrected_carrier_id` and `source_challenge_id`; that last filter is how a reader finds the amendments a challenge produced.

### 3.8. Citations, Court Results and Record Updates

A citation adjudication tracks one violation through the courts, and it deliberately carries **two independent state dimensions on the same row**. The `court_status` dimension follows what the court did; the `record_update_status` dimension follows whether that outcome has been pushed into the safety record. Neither constrains the other, and the divergence between them is where a great deal of this domain's real complexity lives.

A `StateInspectionOfficer` records that a citation was written by supplying the `violation_id`, the `citation_number`, the `court_date` (scheduled or actual), and `expected_violation_version` for the concurrency guard of §2.6. The new record starts with `court_status` `PENDING`, `record_update_status` `NOT_APPLIED`, `severity_factor` 1.0 and `superseded` false. Creating it marks any earlier adjudication of the same violation with `superseded` set to true — that is how an appeal outcome replaces the original ruling — and increments the linked `Violation`'s `version` by 1. A violation may carry at most one non-superseded adjudication whose `court_status` is `PENDING`, and a second attempt is rejected with `ERR_ADJUDICATION_PENDING_EXISTS`.

Recording the court outcome is also a state-officer action. It supplies a `court_status` of `CONVICTED`, `DISMISSED`, `REDUCED` or `NOT_GUILTY`, optionally a `court_note`, and — for `REDUCED` only — the `reduced_to_violation_code_id` naming the lesser code the citation was reduced to; a `REDUCED` result with no reduced code is `ERR_INVALID_REQUEST`. The adjudication's current `court_status` must be `PENDING`, else `ERR_INVALID_ADJUDICATION_STATE`, and its `superseded` flag must be false, else `ERR_ADJUDICATION_SUPERSEDED`. The outcome sets `court_result_recorded_at` to the logical clock and derives `severity_factor` from the result: 0.0 for `DISMISSED` and for `NOT_GUILTY`, 0.5 for `REDUCED`, and 1.0 for `CONVICTED` as well as for a still-`PENDING` record. Critically, `record_update_status` stays at `NOT_APPLIED` — the record dimension does not move just because the court one did, and the violation record itself is untouched. What does move is the driver: the linked violation's driver has `adjudicated_attribution_score` and `coaching_required` recomputed, while `strict_attribution_score` is left exactly as it was, so the two attribution variants diverge from this instant. If that recompute drops `coaching_required` to false, existing `ASSIGNED` and `IN_PROGRESS` coaching assignments are *not* touched here; only a scoring run waives assignments on the strength of a score. The adjudication's `version` is incremented by 1.

Pushing the result into the record is an `FmcsaReviewOfficer` action and moves the second dimension. Three preconditions apply: `record_update_status` must still be `NOT_APPLIED`, else `ERR_ALREADY_APPLIED_TO_RECORD`; `court_status` must not be `PENDING`, else `ERR_INVALID_ADJUDICATION_STATE`; and the linked violation's `status` must be `ACTIVE` or `RECODED`, else `ERR_VIOLATION_NOT_ACTIVE`. An adjudication whose `superseded` flag is true cannot be applied either, and is rejected with `ERR_ADJUDICATION_SUPERSEDED`.

What the push does depends on the court outcome, and the record dimension lands in a different terminal value accordingly. For `DISMISSED` or `NOT_GUILTY`, `record_update_status` moves from `NOT_APPLIED` to `APPLIED` and the violation's `status` becomes `REMOVED` with a `removal_reason` of `ADJUDICATION_DISMISSED` and a `time_weighted_severity` forced to 0.0. For `REDUCED`, `record_update_status` likewise moves to `APPLIED`, and the violation's `effective_violation_code_id` is set to the `reduced_to_violation_code_id`, its `status` becomes `RECODED`, its `code_weight_snapshot`, `oos_add_on_snapshot` and `pinned_violation_code_version` are re-pinned from the new code, and its `time_weighted_severity` is recomputed. For `CONVICTED`, `record_update_status` moves from `NOT_APPLIED` to `NOT_APPLICABLE` and the violation record is left entirely untouched: a conviction confirms the citation, so there is nothing to correct.

Whichever branch runs, the push stamps `applied_at` and `applied_by_user_id` and increments the adjudication's `version` by 1. For the two branches that changed the violation record, the cascade then runs in the order of §2.10: the owning report's `active_violation_count` and `total_time_weighted_severity` recompute, then the carrier's score rows for the affected categories, then the carrier's `open_alert_count`, `max_percentile` and `intervention_status`, then the carrier's screening risk. Because the violation has either left the driver's attributed set or changed weight within it, the driver's aggregates recompute, and every `ASSIGNED` or `IN_PROGRESS` coaching assignment whose `violation_id` points at a now-`REMOVED` violation moves to `WAIVED` with a `waived_reason` of `VIOLATION_REMOVED`, decrementing the carrier's `open_coaching_count`.

Adjudications are readable with filters on `violation_id`, `reduced_to_violation_code_id`, `court_status`, `record_update_status` and `superseded`, so both dimensions can be queried independently.

### 3.9. Driver-Level Attribution and Coaching

A violation may be attributed to one of the carrier's drivers, and a `CarrierSafetyManager` may set or clear that attribution. Setting it supplies a `driver_id`; the named driver must be employed by the violation's attributed carrier, else `ERR_DRIVER_CARRIER_MISMATCH`, and the violation must not already be `REMOVED`, else `ERR_VIOLATION_NOT_ACTIVE`. Setting an attribution increments the violation's `version` by 1, recomputes the aggregates and `coaching_required` of both the previous driver and the new one, and recomputes the carrier's `unattributed_violation_count` and `scored_violation_count`. Clearing an attribution is the compensating action: it empties the violation's `driver_id`, increments the violation's `version` by 1, recomputes the released driver's aggregates, waives that driver's `ASSIGNED` and `IN_PROGRESS` assignments for this violation with `waived_reason` `ATTRIBUTION_CLEARED`, and recomputes the carrier's `unattributed_violation_count` so that the identity between attributed and unattributed counts continues to hold. At the carrier level, `scored_violation_count` is the number of violations with `status` `ACTIVE` or `RECODED` sitting on any of the carrier's reports whose `status` is `SCORED`, regardless of age, and `unattributed_violation_count` is the subset of those whose `driver_id` is empty.

Each driver carries two attribution scores that answer two different questions, and the difference between them matters. Both are built from the same *included set*: violations whose `driver_id` is this driver, whose `status` is `ACTIVE` or `RECODED`, that sit on a report whose `status` is `SCORED`, and whose `time_weight` is greater than 0. `strict_attribution_score` is the sum of `time_weighted_severity` over that included set, rounded half up to 2 decimal places; it ignores court outcomes entirely, so a citation that was dismissed but not yet pushed to the record still counts against the driver. `adjudicated_attribution_score` is the sum, over the same included set, of each violation's `time_weighted_severity` multiplied by that violation's court factor, again rounded half up to 2 decimal places. A violation's court factor comes from its non-superseded `CitationAdjudication` with the latest `court_result_recorded_at`, with ties broken by the later `created_at`; where a violation has no adjudication at all, or its adjudication's `court_status` is still `PENDING`, the factor is 1.0. Otherwise the factor is 0.0 when `court_status` is `DISMISSED` or `NOT_GUILTY`, 0.5 when it is `REDUCED`, and 1.0 in every remaining case. The strict figure is reported as the carrier's raw per-driver exposure; the adjudicated figure is the one that drives coaching, and it diverges from the strict figure the moment a court result is recorded, well before any record update runs.

The count that sits beside the scores is deliberately broader than the set that feeds them. `attributed_violation_count` is the number of violations whose `driver_id` is this driver, whose `status` is `ACTIVE` or `RECODED`, and whose report's `status` is `SCORED` — with no age condition at all, so a violation whose `time_weight` has decayed to 0 still appears in the count while contributing nothing to either score. Finally, `coaching_required` is true exactly when `adjudicated_attribution_score` is at or above the coaching trigger of 12.0.

A computed read exposes the whole derivation for one driver, returning the `driver_id`, the `attributed_violation_count`, both the `strict_attribution_score` and the `adjudicated_attribution_score`, the `coaching_required` flag, and the per-violation `factor_breakdown` showing which court factor was applied where.

Coaching is how a carrier responds. A `CarrierSafetyManager` creates an assignment naming the `driver_id` to coach, the `violation_id` that motivated the coaching, a `curriculum_code` from `UNSAFE_DRIVING_101`, `HOS_ELD_REFRESH`, `PRETRIP_INSPECTION` or `CDL_COMPLIANCE`, and a reserved window on the driver's calendar given as `session_start` and `session_end`, where the end must fall strictly after the start. Four eligibility conditions apply: the driver's `employment_status` must be `ACTIVE`, else `ERR_DRIVER_NOT_EMPLOYED`; the named violation's `driver_id` must equal the assignment's `driver_id`, else `ERR_VIOLATION_NOT_ATTRIBUTED_TO_DRIVER`; the violation's report must be in `SCORED` status, else `ERR_INVALID_REPORT_STATE`; and the violation's effective violation code must have `driver_attributable` set to true, else `ERR_CODE_NOT_DRIVER_ATTRIBUTABLE`. The same eligibility family is re-checked when a session is started.

The reserved window is half-open, covering `session_start` up to but not including `session_end`. A new assignment is rejected with `ERR_COACHING_WINDOW_CONFLICT` when another assignment of the same driver whose `status` is `ASSIGNED`, `IN_PROGRESS` or `OVERDUE` has a half-open window intersecting the new one. Adjacency is explicitly permitted — an existing session ending exactly when the new one starts, or a new session ending exactly when an existing one starts, is fine — and no buffer of any kind is applied. Creation copies `carrier_id` from the driver, sets `status` to `ASSIGNED`, sets `due_at` to `session_end` plus 14 days, and increments `open_coaching_count` on both the carrier and the driver.

The assignment then walks its lifecycle. Starting a session moves it to `IN_PROGRESS` from either `ASSIGNED` or `OVERDUE` and stamps `started_at`; when the source was `OVERDUE`, the `overdue_marked_run_id` stamp is deliberately retained for audit rather than cleared. Completing a session is permitted only from `IN_PROGRESS`, takes an `attestation_note` from the safety manager, stamps `completed_at`, moves the assignment to `COMPLETED`, and decrements `open_coaching_count` on both the carrier and the driver. A start or complete attempted from a status that does not permit it is rejected with `ERR_INVALID_COACHING_STATE`.

Three transitions are driven by the system rather than by the safety manager. An assignment in `ASSIGNED` or `IN_PROGRESS` whose `due_at` has fallen behind the scoring run's snapshot instant moves to `OVERDUE`, recording the run's identifier as `overdue_marked_run_id`. An assignment already in `OVERDUE` whose `due_at` plus 30 days has fallen behind the run's snapshot moves to `ESCALATED`, decrementing `open_coaching_count` on both the carrier and the driver. And an assignment in `ASSIGNED`, `IN_PROGRESS` or `OVERDUE` moves to `WAIVED` under any one of four circumstances, each with its own `waived_reason`: the linked violation's `status` has become `REMOVED`, giving `VIOLATION_REMOVED`; the linked violation's `driver_id` no longer equals the assignment's `driver_id`, giving `ATTRIBUTION_CLEARED`; the driver's `employment_status` has become `TERMINATED`, giving `DRIVER_SEPARATED`; or a run's score sweep observes that the driver's `coaching_required` has fallen to false, giving `SCORE_BELOW_TRIGGER`. Every waiver decrements `open_coaching_count` on both the carrier and the driver. `COMPLETED`, `WAIVED` and `ESCALATED` are all terminal.

Assignments are readable with filters on `driver_id`, `violation_id`, `carrier_id`, `status` and `overdue_marked_run_id`.

### 3.10. Safety Fitness Determinations and Corrective Action Plans

A carrier whose `safety_fitness_status` has been set to `CONDITIONAL` or `UNSATISFACTORY` owes the agency a plan. A `CarrierAnalyst` opens one by supplying the `carrier_id`, the `expected_carrier_version` required by §2.6, and a root-cause `narrative`. The plan starts in `DRAFT` and records `triggering_fitness_status`, a snapshot of the carrier's `safety_fitness_status` at creation, which is therefore always `CONDITIONAL` or `UNSATISFACTORY`. Creating a plan for a carrier whose status is `UNRATED` or `SATISFACTORY` is rejected with `ERR_CAP_NOT_REQUIRED`, and the same check is repeated at submission. A carrier may hold at most one plan in `DRAFT`, `SUBMITTED`, `IN_REVIEW` or `PENDING_DECISION`, and a second one is rejected with `ERR_ACTIVE_CAP_EXISTS`. A plan in `RETURNED` status is different: it is legitimately replaced, so when a `RETURNED` plan exists for the carrier, creating a new one sets the new plan's `superseded_cap_id` to the prior plan's identifier, moves the prior plan to `SUPERSEDED` and increments that prior plan's `version` by 1. Creation also increments the carrier's `version` by 1 — which is precisely why the concurrency guard is needed.

Action items are the substance of the plan. An analyst adds each one with a `basic_category` naming the behaviour category the item addresses, a `description` of what the carrier will change, and a `target_completion_date` the carrier commits to. Each item records its owning plan as `cap_id` and enters in `PROPOSED` status. Their lifecycle is driven by a single status-change capability whose `action` value, together with an optional `note`, selects the transition — and each action belongs to a different party. `COMMIT` is the analyst's action and moves an item from `PROPOSED` to `COMMITTED`; it is also the item-level revision loop, moving an item from `REJECTED_ITEM` back to `COMMITTED`. A commit is permitted only while the owning plan's `status` is `DRAFT`, `RETURNED`, `SUBMITTED` or `IN_REVIEW`, else `ERR_INVALID_CAP_STATE`. `IMPLEMENT` is the safety manager's action and moves an item from `COMMITTED` to `IMPLEMENTED`. `VERIFY` is the auditor's action, moves an item from `IMPLEMENTED` to `VERIFIED`, and records the acting `X-User-ID` as `verified_by_user_id`. `REJECT` is also the auditor's action, moves an item from either `COMMITTED` or `IMPLEMENTED` to `REJECTED_ITEM`, and records a `rejection_note`. Although all three roles reach this one capability, each `action` belongs to exactly one of them, so an `action` driven by any other role is rejected with `ERR_ROLE_NOT_PERMITTED`; that verdict follows from the recognised `action` value alone and is reached before the addressed item is resolved. An action that does not match the item's current status is rejected with `ERR_INVALID_CAP_ITEM_STATE`.

Every item change, and every item addition, rolls the plan's aggregates up again. `item_count` is the number of the plan's items whose `status` is anything other than `REJECTED_ITEM`. `committed_item_count` is the number whose `status` is `COMMITTED`, `IMPLEMENTED` or `VERIFIED`. `verified_item_count` is the number whose `status` is `VERIFIED`. And `completion_pct` is one hundred multiplied by `verified_item_count`, divided by `item_count` where a zero `item_count` is treated as 1, rounded half up to 1 decimal place. A rejected item drops out of `item_count` entirely, which raises `completion_pct` for the items that remain — rejection removes work from the plan rather than blocking it.

Submitting the plan is the safety manager's action and is permitted from `DRAFT` or from `RETURNED`, the latter being the revision loop. Two gates apply beyond the fitness-status check: `item_count` must be at least 1, and `committed_item_count` must equal `item_count`, so every surviving item is committed; a shortfall is `ERR_CAP_ITEMS_INCOMPLETE`. Submission moves the plan to `SUBMITTED`, clears any prior `safety_review_outcome`, `safety_review_user_id`, `data_review_outcome` and `data_review_user_id` so that the review fork restarts from nothing, and increments the plan's `version` by 1.

Review forks into two parallel branches. An `FmcsaProgramAuditor` records one branch at a time by naming the `branch` — `SAFETY` or `DATA` — and an `outcome` of `CLEARED` or `DEFICIENT`, with an optional `note`. The plan must be in `SUBMITTED` or `IN_REVIEW`, else `ERR_INVALID_CAP_STATE`. The named branch must not already carry an outcome for this submission cycle, else `ERR_REVIEW_BRANCH_ALREADY_RECORDED`. And the acting `X-User-ID` must differ from the identifier already recorded for the other branch, else `ERR_SEGREGATION_OF_DUTIES`. A `CLEARED` outcome writes `safety_review_outcome` with `safety_review_user_id`, or `data_review_outcome` with `data_review_user_id`, and moves a `SUBMITTED` plan to `IN_REVIEW`. A `DEFICIENT` outcome records the branch outcome and then short-circuits the fork: the plan moves straight to `RETURNED` without waiting for the other branch to report, from either `SUBMITTED` or `IN_REVIEW`. Either way the plan's `version` is incremented by 1.

The fork rejoins under a compound guard that is evaluated after every branch review and after every item rollup. A plan in `IN_REVIEW` whose `safety_review_outcome` is `CLEARED`, whose `data_review_outcome` is `CLEARED`, and whose `completion_pct` has reached exactly 100.0 — meaning every non-rejected action item is `VERIFIED` — moves to `PENDING_DECISION`. Nothing but `status` changes on that transition, and the plan's `version` is incremented by 1. Because the guard is re-evaluated on item verification as well as on branch review, the last verification an auditor performs can itself be what carries the plan from `IN_REVIEW` to `PENDING_DECISION`.

The decision is the final act. An `FmcsaProgramAuditor` supplies a `decision` of `ACCEPT` or `RETURN` with an optional `note`. The plan must be in `PENDING_DECISION`, else `ERR_INVALID_CAP_STATE`, and the acting `X-User-ID` must not equal the carrier's `fitness_determined_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. Both outcomes write `decision`, `decided_by_user_id` and `decided_at`. `ACCEPT` moves the plan to `ACCEPTED` and upgrades the carrier's `safety_fitness_status` by exactly one step — `UNSATISFACTORY` becomes `CONDITIONAL`, and `CONDITIONAL` becomes `SATISFACTORY` — incrementing both the carrier's `version` and the plan's `version` by 1. `RETURN` moves the plan to `RETURNED`, leaves `safety_fitness_status` untouched, and makes the plan supersedable by a fresh one. `ACCEPTED` and `SUPERSEDED` are terminal.

Plans are readable with filters on `carrier_id`, `status` and `superseded_cap_id`, and a plan's action items are readable as a nested collection.

### 3.11. The Scoring Run Checkpoint

The scoring run is the system's epoch advance, and only an `FmcsaProgramAuditor` may trigger one. It takes an optional `note` describing why the run was triggered, and it captures the current logical clock into its own `snapshot_utc`, which becomes the aging basis for every score the run writes. Epochs may not go backwards: a run whose `snapshot_utc` would fall earlier than the most recent run's `snapshot_utc` is rejected with `ERR_SCORING_RUN_SNAPSHOT_REGRESSION`. A run is created and completed inside one request, so its `status` is always `COMPLETED`.

The run performs six sweeps in order. First it re-pins every violation on every report in `VALIDATED`, `SCORED` or `AMENDED` status, using the run's `snapshot_utc` as the aging basis, which is where age-decayed violations lose their `time_weight` and where stale code pins are refreshed. Second it rewrites every score row of every carrier, then each carrier's intervention posture, then each carrier's screening risk — the same ordering as any other cascade; if a category holding at least one includable violation has no selectable threshold row, the run is rejected with `ERR_THRESHOLD_NOT_CONFIGURED`. Third it closes out unanswered information requests: any challenge in `INFO_REQUESTED` whose `info_response_deadline` falls before the run's `snapshot_utc` moves to `RESOLVED_REJECTED` with a `resolution_disposition` of `EXPIRED_NO_RESPONSE`, a `resolved_at` set to the run's `snapshot_utc` and an empty `resolved_by_user_id`, since no officer decided it; clearing those challenges clears `under_challenge` on their covered violations, which restores `certified_measure` and cascades through `alert_status`, intervention posture and screening risk. Fourth it sweeps coaching: assignments in `ASSIGNED` or `IN_PROGRESS` past their `due_at` become `OVERDUE`, assignments in `OVERDUE` more than 30 days past their `due_at` become `ESCALATED`, and assignments whose driver's `coaching_required` has fallen to false are waived with `waived_reason` `SCORE_BELOW_TRIGGER`. Fifth it re-derives every carrier's `challenge_quota_used` over the rolling thirty-day window exactly as described in §3.6. Sixth, it increments the `version` of every record it mutated by 1.

The run records what it did. `carriers_scored` is the number of carriers whose score rows the run rewrote, `scores_updated` is the number of score rows written, `challenges_expired` is the number of `INFO_REQUESTED` challenges the run auto-rejected, `coaching_marked_overdue` is the number of assignments the run flipped to `OVERDUE`, and `coaching_waived` is the number of assignments the run waived for `SCORE_BELOW_TRIGGER`. All five counters start at 0 and are readable afterwards, which is how an operator confirms what a given epoch advance actually touched.

## 4. Endpoint Definitions

Operations that bring a new record into existence — registering a carrier or driver, publishing reference data, ingesting a report, appending a violation, opening a challenge or plan, attaching evidence, adding an action item, recording a citation, filing an amendment, creating a coaching assignment, or advancing the scoring epoch — return `201 Created`. Operations that modify an existing record, including every state transition and every computed read, return `200 OK`. All paths are mounted at the root.
