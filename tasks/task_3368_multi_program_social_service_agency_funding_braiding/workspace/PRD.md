# Social Service Funding Braiding API — Product Requirements Document

## 1. Introduction

Diocesan social service agencies rarely run on a single purse. A Catholic Charities affiliate typically carries a housing program funded by a federal block grant, a food pantry underwritten by parish collections, a counseling practice drawing on a county contract, and immigration and refugee services paid through a mix of state awards and private foundation grants — each with its own fiscal calendar, its own eligibility screens, its own audit expectations, and its own rules about what public money may and may not touch. The agency meets every one of these clients at a single door: one intake, one assessment, one confidential record, and then a routing decision that fans the person out into whichever programs they actually qualify for.

This document specifies the API that agency staff use to run that operation end to end. Front-door specialists register clients and open assessments; compliance reviewers verify documentation, determine eligibility and return defective work; program managers enroll clients, authorize service units and document what was delivered; finance officers create awards, braid each delivery's cost across every grant that can bear it, bill the funders and reverse mistakes. Every dollar moves through an allocation line that names the grant it came from, every grant carries a live posture that can throttle or freeze the programs that depend on it, and every report filed with a funder is derived from the same delivery records that produced the bills.

The system is built for audit. Nothing in it reads real wall-clock time — a logical clock supplies every temporal judgement, so a reviewer can replay a fiscal year deterministically. Costs are carried in integer cents and rounded by fixed rules. Confidentiality tiers decide, independently of consent, whether one program may see another program's client. And the guardrails that govern faith-based providers operating under public funding are enforced at the moment money is committed, not at the moment a report is filed.

## 2. Global Specifications & System-Wide Principles

The rules in this section apply to every endpoint in the API. They are written as standing policy rather than as per-operation notes, because a violation of any of them is a defect regardless of which workflow triggered it.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting party and `X-User-Role` states the capacity in which they act. If either header is absent, or if `X-User-Role` carries a value that is not one of the declared roles, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other consideration. If the headers are well formed but the acting role is not among the roles an endpoint authorizes, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The agency recognizes six roles: `IntakeSpecialist`, `ProgramManager`, `FinanceOfficer`, `ComplianceOfficer`, `Client`, and `PlatformAdmin`. Their duties are as follows. An `IntakeSpecialist` is front-door staff who register clients, open and submit assessments, and route them into program screens. A `ProgramManager` is program staff who enroll clients, authorize service units, document deliveries and file outcome reports. A `FinanceOfficer` is fiscal staff who create awards, bill funders, reverse misbillings and value in-kind contributions. A `ComplianceOfficer` is review staff who determine eligibility, return defective assessments, recompute grant posture and accept or reject funder reports. A `Client` is the person receiving services, acting through a self-service portal on their own record only. A `PlatformAdmin` is an operator role that drives the logical clock for deterministic temporal testing.

`X-User-ID` means different things for different roles, and the difference governs every ownership comparison in the system. When `X-User-Role` is `Client`, `X-User-ID` is the `id` of the acting `Client`; ownership checks on any resource that references a `Client` compare the resource's foreign-key field to `X-User-ID`, so a client may read only their own record. When `X-User-Role` is `IntakeSpecialist`, `ProgramManager`, `FinanceOfficer`, `ComplianceOfficer`, or `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — for example, as `assessed_by_user_id` on an `IntakeAssessment` when an intake specialist opens an assessment — but it is never compared to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` and an `offset` query parameter. `limit` caps how many rows are returned: it defaults to 10 when omitted, must be at least 1, and must not exceed 100. `offset` states how many rows to skip from the front of the result and defaults to 0. Unless an endpoint says otherwise, rows come back ordered by their creation timestamp ascending, so the oldest record in the collection is the first one returned.

Every paginated list response carries four pagination fields in the `meta` object of the envelope alongside `api_request_id` and `api_request_timestamp`: `limit`, `offset`, `total_count`, and `has_more`. `total_count` reports how many rows match the filters in total, independent of the page size, and `has_more` is true when further rows remain beyond the current page.

### 2.4. Common Resource Properties

Every addressable record in the agency's data model — `Funder`, `Program`, `Grant`, `Client`, `IntakeAssessment`, `EligibilityScreen`, `Enrollment`, `ServiceAuthorization`, `ServiceDelivery`, `CostAllocation`, `InKindDonation` and `OutcomeReport` — carries the same four system-managed properties.

The `id` is a server-minted UUID rendered as a bare string. It carries no type prefix and no embedded meaning: a `Grant` identifier and a `Client` identifier are indistinguishable in form, and no rule in this document may be keyed off the shape of an identifier. The `created_at` property records when the row was first written, as an ISO 8601 UTC timestamp with exactly three fractional digits — `2025-05-24T10:30:00.123Z` is the canonical shape. The `updated_at` property records when the row was last modified and is refreshed on every mutation of that row. The `version` property is an integer that starts at its creation value and increases by one on every modification.

Derived or recomputed properties are mutations like any other. When the server recalculates a computed value — a grant's posture, a program's slot counters, a client's open enrollment count, a delivery's braided totals — that recalculation updates the owning row's `updated_at` and increments its `version`. There are no entities in this API that omit `updated_at` or `version`: all twelve carry the full set.

### 2.5. The Agency Logical Clock

Time in this system is not observed, it is supplied. The server maintains a single logical clock. On startup the clock reads `2026-09-01T00:00:00Z`, and until the clock is explicitly advanced, no rule anywhere in this document may consult real wall-clock time for any purpose. Every temporal precondition, every period comparison, every window boundary and every `created_at`, `updated_at`, `screened_at`, `enrolled_at`, `exited_at` and `posture_computed_at` stamp is derived from the logical clock.

An operator holding the `PlatformAdmin` role has one exclusive capability: setting the logical clock to a supplied instant, passed as `to_iso8601`. This capability exists so that a reviewer can drive a fiscal year forward deterministically and re-run the same scenario twice with identical results. It returns no resource payload — the response envelope carries an empty `data` object — and its only effect is that the clock now reads the supplied instant. Advancing the clock is not a mutation of any resource and does not by itself trigger any state transition; transitions that depend on elapsed time are evaluated when the relevant resource is next written or recomputed.

Several rules in this document are clock-sensitive and are worth naming here so their common mechanism is clear. A grant's award period, an authorization's usable window, an outcome report's reporting window, a client's consent expiry, the rolling seven-day window used for volunteer hours, the calendar-day grouping used to detect duplicated service, and the 180-day expiry applied to an unverified-but-verified screen all read the same clock.

### 2.6. Monetary Precision and Rounding Discipline

Money never travels as a floating-point dollar figure. Every monetary property in the API — award amounts, expended and obligated balances, allocation line amounts, administrative shares, delivery costs, in-kind valuations and disallowed totals — is an integer count of cents. The same is true of the rate properties: `unit_rate_cents`, `rate_cents` and `max_in_kind_rate_cents` are cents, and `verified_income_cents` is a monthly household income expressed in cents.

Where a fractional quantity must be produced, the system rounds it half up — a value exactly at the halfway point moves away from zero — and the number of decimal places is fixed per quantity rather than chosen at the call site. Two derived quantities have their own scales. A grant's `burn_ratio` is carried to exactly six decimal places, round half up. An outcome report's `rate_pct` is carried to exactly two decimal places, round half up.

Percentages and rates that are supplied by staff are expressed as plain fractions, not as whole numbers out of one hundred: `max_admin_rate_pct` and `admin_rate_pct` are fractions between 0.0 and 0.25 inclusive, and `matching_requirement_pct` is a fraction between 0.0 and 1.0 inclusive. A rate of one quarter is written 0.25, and it corresponds to 25 percent of the base it applies to.

Rounding order matters and is pinned. When an administrative share is computed for an allocation line, that line's share is rounded to whole cents first, and the rounded line values are then added together to produce the delivery's administrative total. Summing the unrounded products and rounding once at the end is explicitly not the behaviour: two lines of 1005 cents each at an administrative rate of one tenth contribute 101 cents each, for a total of 202 cents, not 201. The same discipline governs the braiding waterfall, where a computed take below one cent is dropped to zero rather than carried forward as a remainder.

### 2.7. Client Confidentiality and Cross-Program Consent

An agency-wide client record is shared infrastructure, and the programs that sit on top of it are not equally entitled to see it. Two independent instruments control that access. The first is `confidentiality_tier`, an agency-set protection level that is one of `STANDARD`, `PROTECTED` or `SEALED`, defaulting to `STANDARD` at registration. The second is `consent_scope`, a list of `service_domain` values the client has agreed to share across programs, paired with `consent_expires_on`, the instant after which that consent stops authorizing anything.

Resolving whether one program may see a given client's record is governed by a single rule set, evaluated in two variants. The base variant, used on every write path, consults the tier first and takes the first branch that matches. A `SEALED` client is refused outright. A `PROTECTED` client is permitted only when the target domain appears in the client's `consent_scope` and the logical clock has not passed `consent_expires_on`. A `STANDARD` client is permitted. The `SEALED` branch is absolute in this variant: consent never overrides it, so a sealed client whose consent list covers the target domain is still refused.

The second variant, `consent_first`, is used only for the read-only projection that accompanies a client record as `shareable_domains`. It checks consent before the tier: when the target domain appears in `consent_scope` and the clock has not passed `consent_expires_on`, access is allowed and the tier is never consulted; otherwise the evaluation falls through to the tier-first rules unchanged. The practical consequence is that a `SEALED` client with valid consent for housing will list housing in `shareable_domains` while every write path still refuses to act on that client for housing. `shareable_domains` is a diagnostic projection only — it never authorizes a write.

A refusal carries `ERR_CONFIDENTIALITY_SCOPE_DENIED` with HTTP 403, and it guards four operations: opening an eligibility screen under an assessment, recording a determination on an eligibility screen, creating an enrollment directly, and reading a client record. In every one of those four, the check is evaluated under the base tier-first variant.

### 2.8. Public-Funding Guardrails for Faith-Based Service Delivery

Faith-based agencies occupy a specific legal position: they may deliver services under public contracts, but public dollars may not be spent on the explicitly religious components of that work, and the services themselves must be open to everyone regardless of creed. Two flags encode this. A funder declares `allow_faith_based_activity`, which states whether that source permits public dollars to support an explicitly religious activity component. A program declares `faith_based_activity_offered`, which states whether the program actually includes such a component. A third flag, `nondiscrimination_attested`, records whether the program has attested that it serves clients without regard to religion; it defaults to false at program creation and must be explicitly set true.

The first guardrail is a prohibition on commingling. When the governing funder has `allow_faith_based_activity` set to false, the funded program's `faith_based_activity_offered` must be false before public funds may be drawn. A request that would attach such a funder's money to such a program is rejected with `ERR_FAITH_BASED_ACTIVITY_PROHIBITED` (HTTP 422). Three operations enforce this: creating a grant award, authorizing a block of service units, and documenting a delivery so that its cost is braided across grants.

The second guardrail is an attestation gate. A program must carry `nondiscrimination_attested` true before it may be screened or enrolled under a funder whose `funder_type` is `FEDERAL` or `STATE`. A request that screens or enrolls against an unattested program under such a funder is rejected with `ERR_NONDISCRIMINATION_VIOLATION` (HTTP 422). The same requirement is enforced at the moment the program itself is created, so an unattested program cannot be introduced into the roster where federal or state funding is expected to reach it. It applies to program creation, to opening an eligibility screen under an assessment, and to creating an enrollment directly.

### 2.9. Optimistic Concurrency on Authorizations and Deliveries

Two write operations in this API are guarded against acting on a stale view of their parent resource, and both use the same mechanism: the client must state the parent's version as it last observed it, and the server rejects the write when that observation no longer matches.

Authorizing a block of service units requires the request to carry `expected_enrollment_version`, and that value must equal the target enrollment's current `version`. Recording a service delivery requires the request to carry `expected_service_authorization_version`, and that value must equal the target authorization's current `version`. In both cases the field is non-optional: a request that omits it does not fall back to an unchecked write. When the supplied value does not match the parent's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412), and the client must re-read the parent and retry against the version it now sees.

The reason the guard sits on these two operations specifically is that both of them advance their parent. Authorizing units moves the enrollment's own `version` forward, and documenting or voiding a delivery moves the authorization's `units_delivered` and `status` forward. A client that read the parent before one of those advances happened is holding a picture of the parent's consumed units and lifecycle state that is no longer true, and the version check is what prevents that stale picture from being written back over the newer one.

These are the only two endpoints in the API that accept a version field. Every other write operation takes no `expected_..._version` input and performs no version comparison, and an unexpected version field on those requests is ignored rather than enforced.

### 2.10. Request Validation Precedence

Checks are not evaluated in whatever order an implementation finds convenient. Every validation in this system carries a global priority number, and when a request would fail more than one of them, the response carries the error belonging to the failing check with the lowest priority number. A request that trips a priority 4 state check and a priority 8 fiscal check answers with the priority 4 error, and the fiscal problem is never mentioned. This ordering is what makes an error response a stable contract rather than an artifact of evaluation order.

Priority 1 is authentication. The request must carry both `X-User-ID` and `X-User-Role`, and the role must be one of the six declared roles. A failure here is `ERR_UNAUTHENTICATED` (HTTP 401), and it applies to every endpoint without exception.

Priority 2 is authorization. The acting role must appear in the endpoint's own roles set. A failure here is `ERR_FORBIDDEN_ROLE` (HTTP 403), and it likewise applies to every endpoint.

Priority 3 is existence. Every resource the request names must resolve. Path segments resolve left to right in path order, so an unresolvable outer segment is reported before an unresolvable inner one. The specific codes are `ERR_CLIENT_NOT_FOUND` (HTTP 404) when a client path segment does not resolve, and it guards opening an intake assessment under a client and reading a client record; `ERR_PROGRAM_NOT_FOUND` (HTTP 404) when the program named in a body or implied by a screened resource does not exist, guarding grant creation, eligibility-screen opening and direct enrollment; `ERR_GRANT_NOT_FOUND` (HTTP 404) when the grant named in a body or implied by a screened resource does not exist, guarding grant creation, eligibility-screen opening, direct enrollment, unit authorization, delivery recording, in-kind recording and outcome-report opening; `ERR_ENROLLMENT_NOT_FOUND` (HTTP 404) when the enrollment named in a path or body does not exist, guarding enrollment activation, enrollment exit and unit authorization; `ERR_AUTHORIZATION_NOT_FOUND` (HTTP 404) when the `service_authorization_id` in a body does not resolve, guarding delivery recording; `ERR_DELIVERY_NOT_FOUND` (HTTP 404) when a delivery path segment does not resolve, guarding documentation, billing and voiding; and `ERR_OUTCOME_REPORT_NOT_FOUND` (HTTP 404) when an outcome report path segment does not resolve, guarding submission, acceptance and rejection.

Priority 4 is state. `ERR_INVALID_STATE` (HTTP 409) fires whenever the target resource's current status is not the from-state of any transition the endpoint may trigger — which includes any attempt to leave a terminal state — and it guards every action endpoint in this API. `ERR_INTAKE_NOT_ROUTED` (HTTP 409) fires when a determination is attempted on an eligibility screen whose parent assessment is not in `ROUTED` status. `ERR_GRANT_FROZEN` (HTTP 409) fires when the governing grant is at posture `FROZEN`, and it guards six operations: direct enrollment, enrollment activation, unit authorization, delivery recording, delivery documentation and delivery billing.

Priority 5 is concurrency, and it is the `ERR_STALE_VERSION` (HTTP 412) check described in §2.9, guarding unit authorization against `expected_enrollment_version` and delivery recording against `expected_service_authorization_version`. Priority 6 is business safety and covers the confidentiality refusal `ERR_CONFIDENTIALITY_SCOPE_DENIED` (HTTP 403), the commingling refusal `ERR_FAITH_BASED_ACTIVITY_PROHIBITED` (HTTP 422) and the attestation refusal `ERR_NONDISCRIMINATION_VIOLATION` (HTTP 422). Priority 7 is business constraint and covers `ERR_ELIGIBILITY_NOT_ESTABLISHED` (HTTP 409), `ERR_CLIENT_ALREADY_ENROLLED` (HTTP 409), `ERR_AUTHORIZATION_PERIOD_OVERLAP` (HTTP 409), `ERR_OUTCOME_PERIOD_OVERLAP` (HTTP 409), `ERR_INKIND_HOURS_EXCEEDED` (HTTP 422) and `ERR_PROGRAM_CAPACITY_EXCEEDED` (HTTP 409). Priority 8 is business fiscal and covers `ERR_ZERO_UNITS` (HTTP 422), `ERR_NO_ACTIVE_AUTHORIZATION` (HTTP 409), `ERR_ALLOCATION_EXCEEDS_AWARD` (HTTP 409), `ERR_ADMIN_RATE_EXCEEDED` (HTTP 422), `ERR_DUPLICATE_SERVICE_BILLING` (HTTP 409), `ERR_MATCH_REQUIREMENT_UNMET` (HTTP 422) and `ERR_INKIND_VALUATION_INVALID` (HTTP 422).

The consequence of this grouping is worth stating plainly, because it is counterintuitive in a few places. A stale-version refusal and a safety refusal each outrank a capacity refusal and each outrank a money refusal on the same request: a client already at capacity who also presents a stale enrollment version hears about the stale version, and a delivery that would exceed its authorization's remaining capacity but also trips a prohibited-duplication check hears about the duplication first. Within a priority tier, no ordering between the members of that tier is defined, so an implementation is free to evaluate them in any order.

### 2.11. Nested Resource Resolution and Referential Integrity

Where a request names more than one resource, the outer one is resolved before the inner one, and the first unresolvable name in that order determines the error. A request that opens an intake assessment beneath a client path segment resolves that segment against the `Client` collection first; if no client carries that identifier, the answer is `ERR_CLIENT_NOT_FOUND` and the assessment is never considered. The same left-to-right discipline governs the collections that hang beneath a grant: listing the outcome reports or the in-kind donations credited against a grant resolves the grant first, and an unresolvable grant yields `ERR_GRANT_NOT_FOUND` rather than an empty list.

References supplied in a request body rather than in the path are resolved under the same priority-3 rules described in §2.10. A body that names a `program_id`, a `grant_id`, an `enrollment_id` or a `service_authorization_id` must resolve to a live row of the corresponding collection before any later-tier check runs, and an unresolvable one is reported with that collection's not-found code. This applies even when the referenced row is reached only indirectly: a screened resource whose `grant_id` cannot be resolved fails as a missing grant, and an eligibility screen opened against a program that does not exist fails as a missing program.

The entity graph these references trace is a strict hierarchy, and every rule that reads a parent reads it through the child's own reference rather than through a denormalized copy. A client owns assessments; an assessment owns the eligibility screens opened beneath it. An enrollment owns service authorizations; an authorization owns the deliveries recorded against it; a delivery owns the cost allocation lines braided from it. A grant owns the outcome reports filed against it and the in-kind contributions credited to it, and it is itself owned by a funder and pointed at a program. Where a rule in §3 speaks of "the governing grant" for a delivery, for an authorization, or for an enrollment, it means the row reached by following that child's own `grant_id`.

### 2.12. Grant Posture Propagation Across the Program Roster

A grant is not a static pot of money. As costs are braided onto it, it moves through three postures — `OPEN`, `THROTTLED` and `FROZEN` — and its posture is what decides whether the programs drawing on it may keep operating. The measure that drives the posture is `burn_ratio`, the fraction of the award that has been committed. Commitment is counted on the committed basis: the grant's `expended_cents` plus its `obligated_cents`, divided by `total_award_cents`, rounded half up to six decimal places. A grant with an award of zero carries a `burn_ratio` of 0.0 rather than an undefined value. A second, reporting-only projection uses the cash basis — `expended_cents` alone — and is surfaced on the grant read; it never gates a write, which is why a grant can report an unremarkable cash figure while its committed posture has already frozen it.

Posture is assigned by evaluating three cases in order and taking the first that matches. A `burn_ratio` of at least 1.000000 is `FROZEN`. Otherwise a `burn_ratio` of at least 0.850000 is `THROTTLED`. Otherwise the posture is `OPEN`. The comparisons are inclusive, not exclusive: a ratio of exactly 0.850000 is `THROTTLED`, and a ratio of exactly 1.000000 is `FROZEN`. Expressed as percentages of the award, the throttle point is 85 percent and the freeze point is 100 percent.

Posture moves in both directions. A grant that has not yet reached the throttle point and crosses it becomes `THROTTLED`; a grant that reaches the freeze point becomes `FROZEN` from either `OPEN` or `THROTTLED`; and when a cost allocation is reversed and the committed total falls back, a `FROZEN` grant drops to `THROTTLED` or straight to `OPEN`, and a `THROTTLED` grant returns to `OPEN`. Every posture change stamps `posture_computed_at` with the current logical clock and increments the grant's `version`. A finance officer or a compliance officer may also force a recomputation of one grant on demand, which recalculates `burn_ratio`, applies whatever posture transition the new ratio implies, and returns the grant.

Freezing is the posture with teeth. When a grant reaches `FROZEN`, every enrollment carrying that `grant_id` whose status is `ACTIVE` is set to `SUSPENDED` and each affected client's `open_enrollment_count` is decremented. From that point on, the frozen grant refuses all child writes: creating an enrollment, activating an enrollment, authorizing service units, recording a delivery, documenting a delivery and billing a delivery are all rejected with `ERR_GRANT_FROZEN` (HTTP 409) while the governing grant remains frozen. A `THROTTLED` grant is not frozen — it still admits child writes, and the posture exists to signal that the award is close to exhaustion rather than to stop work.

## 3. Business Logic & Workflows

The workflows below are ordered the way the agency actually works a case: the funding landscape is built first, a person arrives at the single door, the door routes them into screens, screens become enrollments, enrollments produce authorized units, delivered units become braided costs, volunteer support offsets the match obligation, and the whole year is finally accounted for to each funder.

### 3.1. Building the Funding Landscape: Funders, Programs and Awards

Everything downstream depends on three records that a `ComplianceOfficer` and a `FinanceOfficer` establish before any client is served. The first is the funding source itself. A `ComplianceOfficer` creates a `Funder` by supplying its legal `name`, which must be non-empty and unique across all funders, together with a `funder_type` drawn from `FEDERAL`, `STATE`, `COUNTY`, `PRIVATE_FOUNDATION`, `DIOCESAN` or `PARISH`. Alongside those come the compliance flags that will govern every dollar drawn from it: `allow_faith_based_activity`, which states whether public dollars may support an explicitly religious activity component; `requires_time_and_effort_documentation`, which states whether the funder demands documented staff time-and-effort records before it will accept an allocation; `max_admin_rate_pct`, the ceiling on the administrative cost share it will reimburse, given as a fraction no lower than 0.0 and no higher than 0.25; and `fiscal_year_start_month`, an integer from 1 through 12 naming the first month of the funder's own fiscal year. A newly registered funder begins in `ACTIVE` status.

The second record is the service program. Also created by a `ComplianceOfficer`, a `Program` carries a public `name` that must be non-empty and unique across programs, and a `service_domain` of `HOUSING`, `FOOD`, `COUNSELING`, `IMMIGRATION` or `REFUGEE`. Two booleans describe how it is run: `faith_based_activity_offered`, which states whether the program includes an explicitly religious activity component, and `nondiscrimination_attested`, which states whether the program has attested that it serves clients without regard to religion and which defaults to false when not supplied. `capacity_slots` sets the maximum number of concurrent open enrollments the program may carry and must be zero or greater. A final flag, `match_eligible`, defaults to false and marks whether in-kind contributions to this program count toward a grant's matching requirement. Registration initializes the program's `enrolled_slots` to 0 and its `status` to `ACTIVE`; the program lifecycle admits `ACTIVE`, `SUSPENDED` and `CLOSED`. A separate counter, `active_slots`, is a reporting-only view that counts only enrollments in `ACTIVE` status, and it is surfaced when programs are listed — it does not participate in any admission decision.

The attestation gate from §2.8 lands here: an unattested program cannot be introduced into the roster where federal or state funding is expected to reach it, and the attempt is refused with `ERR_NONDISCRIMINATION_VIOLATION`. A request that names a program which does not exist fails earlier, at the existence tier, with `ERR_PROGRAM_NOT_FOUND`.

The third record is the award. A `FinanceOfficer` creates a `Grant` by naming the `funder_id` that made it and the `program_id` it funds, and by supplying a `grant_code` that is the funder's own award identifier — non-empty and unique across all grants. The money side of the record is `total_award_cents`, the total obligated award in cents, which must be zero or greater, and `admin_rate_pct`, the administrative cost share applied to allocations drawn from this grant, expressed as a fraction between 0.0 and 0.25. That administrative rate is checked against the governing funder's ceiling: if it exceeds the funder's `max_admin_rate_pct`, the award is refused with `ERR_ADMIN_RATE_EXCEEDED` (HTTP 422).

Braiding behaviour is configured on the same record. `allocation_rank` is the grant's precedence within the program, an integer of at least 1, and a lower value means the grant is drawn first when a cost is braided. `max_in_kind_rate_cents` caps the per-hour value that may be credited for volunteer or parish contributions to this grant and must be zero or greater. `matching_requirement_pct` is the fraction of the award that the grantee must match with in-kind support, between 0.0 and 1.0. `cost_allocation_basis` records the basis the funder mandates for distributing shared costs and is one of `DIRECT_ONLY`, `HEADCOUNT`, `TIME_AND_EFFORT` or `SQUARE_FOOTAGE` — a distinction that later decides which order the braiding waterfall uses. `restricted_purpose` records what the award may be spent on and is one of `HOUSING_ASSISTANCE`, `FOOD_DISTRIBUTION`, `CLINICAL_COUNSELING`, `LEGAL_IMMIGRATION`, `REFUGEE_RESETTLEMENT` or `GENERAL_OPERATING`.

The award period is given by `period_start`, the first instant of the award period and inclusive, and `period_end`, the last instant of the award period and also inclusive. Registration sets `expended_cents` and `obligated_cents` to 0, computes `burn_ratio` through the posture rule of §2.12, and assigns `status` from that computation, so a grant whose configured award is already exhausted by other means opens in `THROTTLED` or `FROZEN` rather than `OPEN`. An award naming a program that does not exist is refused with `ERR_PROGRAM_NOT_FOUND`, and one that would attach money from a funder whose `allow_faith_based_activity` is false to a program whose `faith_based_activity_offered` is true is refused with `ERR_FAITH_BASED_ACTIVITY_PROHIBITED`.

Once the landscape exists, staff read it constantly. Grants are listed with optional filters on `funder_id`, `program_id` and `status`, and a single grant can be read back; that read returns the gating committed-basis `burn_ratio` used by every posture decision, the reporting-only cash-basis figure, and counts of the children hanging off the award. The outcome reports filed against a grant can be listed with filters on `measure_code` and `status`, and the in-kind donations credited against it can be listed with filters on `donor_type` and `status`.

### 3.2. The Single Door: Client Registration and Confidentiality Tiering

The agency meets a person once. An `IntakeSpecialist` registers them as a `Client`, recording `full_name`, which must be non-empty, and `date_of_birth` as an ISO 8601 calendar date. The household is captured with `household_size`, an integer of at least 1, and `county_code`, the county of residence that county funders will later screen against. `immigration_status` records the category that funder eligibility screens care about and is one of `CITIZEN`, `LPR`, `REFUGEE`, `ASYLEE`, `UNDOCUMENTED` or `PENDING_ASYLUM`.

Registration is also where the record's protection posture is set, and it is set once, at the door. `confidentiality_tier` defaults to `STANDARD` and may be raised to `PROTECTED` or `SEALED`; `consent_scope` defaults to an empty list and holds the `service_domain` values the client agrees to share across programs; `consent_expires_on` names the instant after which that consent stops authorizing anything. A newly registered client starts with an `open_enrollment_count` of 0. If the named client cannot be resolved on a later read, the answer is `ERR_CLIENT_NOT_FOUND`.

Reading a client back is not a passive operation. The response recomputes `open_enrollment_count` from the client's live enrollment rows, and it computes `shareable_domains` — the list of `service_domain` values the client's consent currently covers — using the consent-first variant of the confidentiality rule described in §2.7. That projection is diagnostic: it tells staff what the client has agreed to share, and it deliberately diverges from what the write paths will permit, because a `SEALED` client's consent is listed here but never honoured when a screen or an enrollment is attempted. The read is one of the four operations guarded by the confidentiality rule, so a request that the rule refuses is answered with `ERR_CONFIDENTIALITY_SCOPE_DENIED` (HTTP 403).

Access to the record is narrow. An `IntakeSpecialist` and a `ComplianceOfficer` may read any client they are working with. A `Client` acting in the self-service portal may read only their own record, identified by their own `X-User-ID` — any attempt to read a different client's record is refused at the authorization tier.

### 3.3. Intake Assessment Lifecycle

With the client registered, an `IntakeSpecialist` opens an `IntakeAssessment` beneath them. The assessment records `assessment_date`, the logical-clock instant the assessment was opened, and two lists that must each carry at least one element: `presenting_needs`, the free-text needs the specialist recorded, and `requested_domains`, the `service_domain` values the client asked to be screened for. The specialist's own `X-User-ID` is written to `assessed_by_user_id` — this is the one place the API records an opaque operator identifier on a persisted row. A new assessment begins in `DRAFT` status with a `routing_outcome` of `PENDING`. The assessment lifecycle admits `DRAFT`, `SUBMITTED`, `ROUTED`, `RETURNED` and `CLOSED`, and `CLOSED` is terminal. The routing outcome is one of `PENDING`, `ROUTED`, `NO_ELIGIBLE_PROGRAM` or `WITHDRAWN`, and the `return_reason_code` that a reviewer may attach is one of `INCOMPLETE_INCOME`, `MISSING_DOCUMENT` or `WRONG_DOMAIN`.

Submission moves the assessment from `DRAFT` to `SUBMITTED`, and it is also the path back from `RETURNED` to `SUBMITTED`. A specialist submitting a draft must satisfy three conditions: the status is `DRAFT` or `RETURNED`; `presenting_needs` carries at least one element; and `requested_domains` carries at least one element. The submission sets the status to `SUBMITTED` and clears `return_reason_code` to null, so a resubmitted assessment does not carry the previous reviewer's complaint forward. A resubmission out of `RETURNED` is the narrower case — the status must be `RETURNED` and `requested_domains` must still carry at least one element — and it sets the status to `SUBMITTED` without touching the reason code, which was already cleared on the first submission. Either path increments the assessment's `version` by one.

Routing is what turns an assessment into program work, and it cannot happen until documentation exists. A specialist may route an assessment whose status is `SUBMITTED` only when at least one eligibility screen hanging off that assessment has reached `verification_state` of `VERIFIED`. Routing sets the status to `ROUTED` and sets `routing_outcome` to `ROUTED`; in the case where every screen under the assessment carries a determination of `INELIGIBLE`, the routing outcome is recorded as `NO_ELIGIBLE_PROGRAM` instead, which is how the single door records a client who came through intake but qualified for nothing. Routing increments the assessment's `version` by one.

Return is the reviewer's instrument, exercised by a `ComplianceOfficer` on an assessment in `SUBMITTED` status. The reviewer supplies a `return_reason_code` that must be one of `INCOMPLETE_INCOME`, `MISSING_DOCUMENT` or `WRONG_DOMAIN` — a return without one of those three reasons is refused. Returning an assessment is not a local edit. It sets the assessment to `RETURNED`, expires the evidence gathered so far by setting every eligibility screen under the assessment to `verification_state` of `EXPIRED`, and resets every screen that had been determined `ELIGIBLE` back to `determination` of `PENDING`. The assessment's `version` is incremented, and so is the `version` of every screen the return touched.

An assessment reaches `CLOSED` without anyone asking it to. The system evaluates closure after every enrollment exit and after every eligibility screen determination write: an assessment in `ROUTED` status closes when every screen under it carries a determination of `ELIGIBLE` or `INELIGIBLE`, and every enrollment belonging to the same client whose `enrolled_at` is at or after the assessment's `assessment_date` has reached `EXITED` or `DENIED`. When closure fires, the status becomes `CLOSED` and the `version` is incremented; if every one of that client's enrollments reached `DENIED` rather than exiting, the `routing_outcome` is set to `WITHDRAWN` at the same time.

Two refusals frame this whole lifecycle. An operation attempted against an assessment whose status is not the from-state of any transition that operation may trigger — including any attempt to act on a closed assessment — is refused with `ERR_INVALID_STATE` (HTTP 409). An eligibility screen that has not yet been routed cannot be determined at all: the attempt is refused with `ERR_INTAKE_NOT_ROUTED` (HTTP 409). Assessments are listed with optional filters on `client_id` and `status`, and a single assessment can be read back with its current routing outcome.

### 3.4. Eligibility Screening and the Capacity Cascade

An `IntakeSpecialist` or a `ComplianceOfficer` opens an `EligibilityScreen` beneath an assessment to test one funder's rules against one program. The screen records the `program_id` being screened for, the `grant_id` whose eligibility rules govern it, `verified_income_cents` — the documented monthly household income in cents, zero or greater — and `household_size_at_screen`, the household size as verified at screening time, an integer of at least 1. Opening a screen sets `determination` to `PENDING`, `verification_state` to `UNVERIFIED`, and `screened_at` to the current logical clock.

A screen carries two state dimensions that never touch each other. The first is `determination`, one of `PENDING`, `ELIGIBLE` or `INELIGIBLE`. The second is `verification_state`, one of `UNVERIFIED`, `VERIFIED` or `EXPIRED`. A `ComplianceOfficer` advances them through a single determination operation, and the operation always performs the verification hop first.

The verification hop is an unusual transition because it does not change the determination dimension at all: a screen in `PENDING` determination stays in `PENDING` determination. It requires that `verification_state` is `UNVERIFIED` and that `verified_income_cents` is greater than zero — a screen with no documented income cannot be verified. When it fires, `verification_state` becomes `VERIFIED`, `screened_at` is restamped with the current logical clock, and the screen's `version` is incremented. The consequence of restamping `screened_at` is that the 180-day verification clock starts at verification rather than at screen creation.

Once verification is in place, the determination branch is chosen by the `determination` value the reviewer supplies. A screen may be determined `ELIGIBLE` only when the determination is currently `PENDING`, the `verification_state` is `VERIFIED`, the parent assessment's status is `ROUTED`, the confidentiality rule of §2.7 returns an allowed result for this client and the screened program's `service_domain`, and the screened program's `enrolled_slots` is below its `capacity_slots`. Determining a screen eligible is the moment the single door converts into a program seat: it sets `determination` to `ELIGIBLE` and creates an `Enrollment` in `PENDING` status carrying the assessment's client, the screen's `program_id` and the screen's `grant_id`. It then increments that program's `enrolled_slots` by one, and — when that increment brings `enrolled_slots` up to `capacity_slots` — runs the capacity cascade, setting every screen for that program still sitting at `PENDING` determination to `INELIGIBLE` with a `denial_reason_code` of `PROGRAM_AT_CAPACITY`. The screen's `version` is incremented.

A determination of `INELIGIBLE` requires the same two opening conditions — the determination is `PENDING` and the verification state is `VERIFIED` — and at least one of three substantive failures: the `verified_income_cents` exceeds the program's income ceiling, the client's `immigration_status` is not accepted by the governing funder, or the confidentiality rule returns a refusal. The recorded `denial_reason_code` is the first failing check in the fixed order `CONFIDENTIALITY_BAR`, then `INCOME_OVER_LIMIT`, then `IMMIGRATION_STATUS`, then `RESIDENCY`, then `PROGRAM_AT_CAPACITY` — so a screen that fails both the confidentiality rule and the income ceiling is recorded as a confidentiality bar. The `denial_reason_code` vocabulary is `INCOME_OVER_LIMIT`, `RESIDENCY`, `IMMIGRATION_STATUS`, `PROGRAM_AT_CAPACITY` or `CONFIDENTIALITY_BAR`, and it is null on a screen that was never denied. The screen's `version` is incremented.

The capacity cascade also runs backwards. A screen already determined `ELIGIBLE` is flipped to `INELIGIBLE` with a `denial_reason_code` of `PROGRAM_AT_CAPACITY` when its program's `enrolled_slots` has reached or passed `capacity_slots`. This reversal is not a bookkeeping correction — it denies the seat the screen had created: the `Enrollment` row that this screen spawned is set to `DENIED`, the program's `enrolled_slots` is decremented by one, and the screen's `version` is incremented.

The verification dimension expires on its own schedule. A screen whose `verification_state` is `VERIFIED` and whose `determination` is still `PENDING` is set to `verification_state` of `EXPIRED` when the logical clock reaches or passes 180 days after `screened_at`. Expiry touches only the verification dimension; the determination stays `PENDING`, and the screen must be re-verified before it can be determined. A return by a compliance reviewer expires screens immediately regardless of that clock, as described in §3.3.

Capacity itself is counted by a single rule. A program's `enrolled_slots` is the number of enrollment rows pointing at that program whose status is `PENDING`, `ACTIVE` or `SUSPENDED` — those three statuses are the counting set. `available_slots` is `capacity_slots` minus `enrolled_slots`, and a program is exhausted when `available_slots` is at or below zero; a value of exactly zero is exhausted, and a program configured with `capacity_slots` of 0 is exhausted before any enrollment exists. Because suspended seats still count, a program whose grant froze mid-year does not silently free capacity. The compensating pair built into this rule is worth naming: creating an enrollment and then exiting it with an exit reason of `WITHDRAWN` leaves both the program's `enrolled_slots` and the client's `open_enrollment_count` at exactly the values they held before the enrollment was created.

An attempt to consume a slot when `enrolled_slots` is already at or above `capacity_slots` is refused with `ERR_PROGRAM_CAPACITY_EXCEEDED` (HTTP 409), and that refusal guards both direct enrollment creation and eligible determinations. Screens are listed with optional filters on `intake_assessment_id`, `program_id`, `grant_id` and `determination`, and a single screen can be read back with both of its dimensions and its denial reason. A screen determined while the parent assessment is not `ROUTED` is refused with `ERR_INTAKE_NOT_ROUTED`; a screen opened or determined in violation of §2.7 is refused with `ERR_CONFIDENTIALITY_SCOPE_DENIED`; and one opened against an unattested program under a federal or state funder is refused with `ERR_NONDISCRIMINATION_VIOLATION`.

### 3.5. Enrollment: Activation, Suspension and Exit

An enrollment is a client's seat in a program, and it can come into existence two ways: as a cascade from an eligible determination, described in §3.4, or directly from a `ProgramManager`. A direct enrollment names `client_id`, `program_id` and `grant_id`, and it is admissible only when the door has already done its work — an eligibility screen must exist for that client, program and grant carrying a `determination` of `ELIGIBLE` and a `verification_state` of `VERIFIED`. Without it the request is refused with `ERR_ELIGIBILITY_NOT_ESTABLISHED` (HTTP 409). The client must also hold no enrollment for the same program in `PENDING`, `ACTIVE` or `SUSPENDED` status, or the request is refused with `ERR_CLIENT_ALREADY_ENROLLED` (HTTP 409); the program must have room, or it is refused with `ERR_PROGRAM_CAPACITY_EXCEEDED`; the confidentiality and nondiscrimination rules of §2.7 and §2.8 apply as they do everywhere else; and a governing grant at posture `FROZEN` refuses the write with `ERR_GRANT_FROZEN`. A successful direct enrollment starts in `PENDING` status, stamps `enrolled_at` with the current logical clock, and increments the program's `enrolled_slots` by one.

The enrollment lifecycle admits `PENDING`, `ACTIVE`, `SUSPENDED`, `EXITED` and `DENIED`, and the last two are terminal — an enrollment that has exited or been denied can never be reactivated. The `exit_reason` recorded at exit is one of `COMPLETED`, `WITHDRAWN`, `TRANSFERRED`, `GRANT_TERMINATED` or `NONCOMPLIANCE`, and it is null until an exit happens.

Activation is how a seat becomes live, and it is performed by a `ProgramManager` from two different starting points. A `PENDING` enrollment may be activated when its grant is in `OPEN` or `THROTTLED` posture, the program it points at is `ACTIVE`, and the logical clock sits at or after the grant's `period_start` and at or before its `period_end`. A `SUSPENDED` enrollment may be reinstated under a slightly narrower rule: the grant must again be `OPEN` or `THROTTLED` and the clock must again fall inside the award period, but the program's own status is not re-examined. Both paths set the status to `ACTIVE`, increment the client's `open_enrollment_count` by one, and increment the enrollment's `version`.

Suspension is not something staff request. When the governing grant reaches posture `FROZEN`, every enrollment carrying that `grant_id` in `ACTIVE` status is set to `SUSPENDED` and each affected client's `open_enrollment_count` is decremented by one. The enrollment's `version` is incremented. A suspended enrollment keeps its seat: it continues to count against the program's capacity, and it can be reinstated if the grant's posture recovers.

Exit closes a seat, and what is permitted depends on where the enrollment sits. A `PENDING` enrollment may exit only with an `exit_reason` of `WITHDRAWN` — a client who never started cannot have completed. An `ACTIVE` enrollment may exit with any of `COMPLETED`, `WITHDRAWN`, `TRANSFERRED`, `GRANT_TERMINATED` or `NONCOMPLIANCE`. A `SUSPENDED` enrollment may exit with `WITHDRAWN`, `TRANSFERRED`, `GRANT_TERMINATED` or `NONCOMPLIANCE`, but not with `COMPLETED`, since a suspended seat was never finished. Every exit path sets the status to `EXITED`, stamps `exited_at` with the current logical clock, decrements the program's `enrolled_slots` by one, and increments the enrollment's `version`. Exiting from `ACTIVE` additionally decrements the client's `open_enrollment_count` by one; exiting from `SUSPENDED` does not, because suspension already took that decrement. Exiting from `ACTIVE` or from `SUSPENDED` also expires the enrollment's authorizations: every `ServiceAuthorization` row belonging to that enrollment whose status is `ACTIVE` is set to `EXPIRED`, so a client who leaves a program cannot be delivered against afterward. Exiting from `PENDING` has no authorizations to expire.

Denial is the system's own exit. When the capacity cascade described in §3.4 flips an eligible screen to ineligible, the `PENDING` enrollment that screen created is set to `DENIED` and the program's `enrolled_slots` is decremented by one. Nothing about a denied enrollment is staff-initiated, and a denial cannot be appealed through this API.

The client's `open_enrollment_count` is defined as the number of that client's enrollment rows sitting in `PENDING`, `ACTIVE` or `SUSPENDED` status, and it is recomputed from live rows whenever the client record is read. An operation attempted against an enrollment whose status is not the from-state of any transition that operation may trigger is refused with `ERR_INVALID_STATE` (HTTP 409), and an unresolvable enrollment identifier is refused with `ERR_ENROLLMENT_NOT_FOUND`. Enrollments are listed with optional filters on `client_id`, `program_id`, `grant_id` and `status`, and a single enrollment can be read back with its slot accounting and its exit record.

### 3.6. Authorizing and Delivering Service Units

Before a service can be delivered, someone has to promise to pay for it. A `ProgramManager` issues a `ServiceAuthorization` against an enrollment, naming the `enrollment_id` that will draw on it, the `grant_id` that bears the authorized units, and a `service_code` describing the unit being billed. That code is one of `HOUSING_RENT_ASSIST`, `FOOD_PANTRY_BOX`, `CLINICAL_COUNSELING_HOUR`, `IMMIGRATION_LEGAL_HOUR` or `REFUGEE_CASE_MGMT_HOUR`. `authorized_units` states how many units are being authorized and must be at least 1; `unit_rate_cents` is the contract rate for the code and must be at least 1 cent. The usable window is given by `period_start`, the first instant the authorization is usable and inclusive, and `period_end`, the last instant it is usable and exclusive — the window is half-open, and a service rendered exactly at `period_end` falls outside it.

Authorizing units is one of the two operations guarded by optimistic concurrency, so the request must also carry `expected_enrollment_version` matching the target enrollment's current `version`; a stale value is refused with `ERR_STALE_VERSION` (HTTP 412) under the rules of §2.9. A second constraint protects against overlapping promises: the requested half-open window must not overlap any existing authorization for the same `enrollment_id` and the same `service_code` whose status is `DRAFT`, `ACTIVE` or `EXHAUSTED`. Because the intervals are half-open, an existing authorization whose `period_end` exactly equals the new `period_start` is not an overlap and is permitted; anything closer than that is refused with `ERR_AUTHORIZATION_PERIOD_OVERLAP` (HTTP 409). The governing grant must not be frozen, and the faith-based commingling rule of §2.8 applies here as it does at award creation. A successful authorization begins in `ACTIVE` status with `units_delivered` at 0, and it increments the enrollment's `version` by one. The authorization lifecycle admits `DRAFT`, `ACTIVE`, `EXHAUSTED`, `EXPIRED` and `VOIDED`; `units_delivered` is the running sum of the units on this authorization's deliveries that have reached `DOCUMENTED`, `BILLED` or `PAID` status, and an authorization that has consumed all of its authorized units becomes `EXHAUSTED`. Authorizations are listed with optional filters on `enrollment_id`, `grant_id` and `status`, and a single authorization can be read back with its consumed-unit counter and its remaining period.

A `ServiceDelivery` records that a unit was actually rendered. A `ProgramManager` supplies the `service_authorization_id` being consumed, the `grant_id` designated as the primary bearer of the delivery, the `client_id` who received the service, `service_date` — the logical-clock instant the service was rendered — `units_delivered`, and the `unit_rate_cents` applied to each unit. `units_delivered` is constrained to zero or greater as a value, but a delivery created with zero units is never billable and is refused at creation with `ERR_ZERO_UNITS` (HTTP 422). The enrollment behind the authorization must hold at least one authorization in `ACTIVE` status covering the current logical clock, or the request is refused with `ERR_NO_ACTIVE_AUTHORIZATION` (HTTP 409). The request must carry `expected_service_authorization_version` matching the authorization's current `version`, refused with `ERR_STALE_VERSION` when it does not, and an unresolvable authorization identifier is refused with `ERR_AUTHORIZATION_NOT_FOUND`. A frozen governing grant refuses the write with `ERR_GRANT_FROZEN`.

Recording a delivery is deliberately cheap, because documentation comes later. The server assigns the delivery a `sequence_no` from its own counter — a strictly increasing integer starting at 1 that is never reused and never derived from the row's `id`, so it can serve as a stable, identifier-free ordering key when two rows share a timestamp. The delivery begins in `DRAFT` status with `documentation_status` of `INCOMPLETE`, its `gross_cost_cents` is set to the number of units delivered multiplied by the per-unit rate, and the authorization's `version` is incremented by one. Deliveries are listed with optional filters on `service_authorization_id`, `grant_id`, `client_id` and `status`, and each listed row carries `alternate_disallowed_cents`, a diagnostic projection computed under the cheapest-row-wins reading of the duplication rule described in §3.7. A single delivery can be read back with its documentation status, its braided totals and its duplication projections.

### 3.7. Braiding Costs Across Grants: Documentation, Billing and Reversal

A draft delivery is worth nothing until it is documented, and documentation is where the braiding happens. A `ProgramManager` documents a delivery whose status is `DRAFT`, and the operation carries six requirements: the delivery must have delivered at least one unit; the authorization named by `service_authorization_id` must be in `ACTIVE` status; the units on this delivery added to the authorization's existing `units_delivered` must not exceed the authorization's `authorized_units`; the grant named by `grant_id` must be in `OPEN` or `THROTTLED` posture; and the logical clock must sit at or after the authorization's `period_start` and strictly before its `period_end`. Documentation sets `documentation_status` to `COMPLETE`, recomputes `gross_cost_cents` as the units delivered multiplied by the per-unit rate, discards and rewrites the delivery's cost allocation lines, and then propagates the result outward.

The rewrite is the braiding waterfall, and its order is pinned. The amount to be placed is the delivery's total cost — its units delivered multiplied by its per-unit rate. The candidate grants are every grant that is either the grant named on the enrollment behind this delivery's authorization, or the grant named on the authorization itself, restricted to grants currently in `OPEN` or `THROTTLED` posture. That set is ordered once, before any line is written, and the order is never recomputed between lines: under the `RANKED_PRIORITY` basis, grants are drawn in ascending `allocation_rank` with ties broken by ascending creation time; under the `CHRONOLOGICAL_PERIOD` basis, grants are drawn in ascending `period_start` with ties broken by ascending creation time. Which basis applies is decided by the governing funder's `cost_allocation_basis` — `DIRECT_ONLY` and `HEADCOUNT` produce the `RANKED_PRIORITY` order, while `TIME_AND_EFFORT` and `SQUARE_FOOTAGE` produce the `CHRONOLOGICAL_PERIOD` order.

With the order frozen, the waterfall walks the grants in sequence, carrying a residual that starts at the delivery's total cost. For each grant at position i, counting from 1, the grant's remaining capacity is its total award less what it has already expended and what it has already obligated, and the amount taken from it is the smaller of that capacity and the residual still unplaced. A take below one cent is dropped to zero rather than carried forward as a remainder. The resulting line records the take as `allocated_amount_cents`, an administrative share as `admin_amount_cents` computed by multiplying the take by that grant's administrative rate and rounding half up to whole cents, its position as `allocation_rank`, the basis that produced it as `allocation_basis` — `RANKED_PRIORITY` or `CHRONOLOGICAL_PERIOD` — and a commitment state of `PROVISIONAL`. The residual then drops by the take, and the walk continues. If the walk finishes with a residual still above zero — which happens when the combined remaining capacity of every candidate grant falls below the delivery's total cost — the documentation is refused with `ERR_ALLOCATION_EXCEEDS_AWARD` (HTTP 409), and the rewrite is abandoned. Only after the entire pass completes are the receiving grants' `obligated_cents` balances increased.

Once the lines exist, the delivery's own totals are computed from them. The lines are taken in ascending `allocation_rank`. Each line's administrative share is computed and rounded to whole cents on that line, and the rounded values are then added together to produce `admin_total_cents` — the per-line rounding order described in §2.6, not a single rounding of the summed products. `allocated_total_cents` is the sum of the lines' allocated amounts, and the delivery's combined total is the allocated total plus the administrative total. Only lines in `PROVISIONAL` or `COMMITTED` state participate; a line that has been reversed contributes nothing.

The outward propagation from documentation is broad. Each receiving grant's `obligated_cents` increases by the allocated and administrative amounts placed on it, its `burn_ratio` is recomputed under the posture rule of §2.12, and whatever posture transition the new ratio implies is applied. When that cascade drives a grant to `FROZEN`, every `ACTIVE` enrollment carrying that `grant_id` is set to `SUSPENDED` and each affected client's `open_enrollment_count` is decremented, exactly as §2.12 describes. The authorization's `units_delivered` is increased by the units on this delivery, and it is set to `EXHAUSTED` when its consumed units reach its authorized units. The delivery's `documentation_status` becomes `COMPLETE`, its status becomes `DOCUMENTED`, and its `version` is incremented.

Billing is the finance officer's step, and it is where prohibited duplication is caught. A `FinanceOfficer` bills a delivery in `DOCUMENTED` status whose `documentation_status` is `COMPLETE` and every one of whose receiving grants is still in `OPEN` or `THROTTLED` posture. The duplication rule is what makes a double-billed day impossible: peer rows are the deliveries belonging to the same client whose `service_date` falls on the same logical-clock calendar day, whose authorization carries the same `service_code`, and whose status is `DOCUMENTED` or `BILLED`. Those peers are ordered by creation time ascending, with ties broken by ascending `sequence_no`, and the first row in that order is the allowed one while every later row is disallowed — a row is disallowed even when a different grant bears it. The disallowed amount for the delivery being billed is the sum, over the disallowed rows, of each row's `allocated_total_cents` plus its `admin_total_cents`. Only one row per client, per service code, per day is permitted; when the disallowed amount is above zero the billing is refused with `ERR_DUPLICATE_SERVICE_BILLING` (HTTP 409). A separate diagnostic projection computes the same total under the reading where the cheapest row of the day is the allowed one instead of the earliest, and that alternative figure is surfaced as `alternate_disallowed_cents` on delivery reads and listings; it never gates a write.

A successful billing commits the money. Every `PROVISIONAL` line for the delivery becomes `COMMITTED`, and for each receiving grant the same amount moves out of `obligated_cents` and into `expended_cents`. The grants' `burn_ratio` values are recomputed and their posture transitions re-applied, the delivery's status becomes `BILLED`, and its `version` is incremented.

Voiding is the compensating reversal, and it behaves differently depending on how far the delivery got. Voiding a `DOCUMENTED` delivery returns it to `DRAFT`: every allocation line for the delivery becomes `REVERSED` with its `allocated_amount_cents`, `admin_amount_cents` and `disallowed_cents` all zeroed, each receiving grant's `obligated_cents` is decreased by the pre-void sum of allocated and administrative amounts, `burn_ratio` and posture are recomputed, the authorization's `units_delivered` is decreased by the delivery's units and its status returns to `ACTIVE` if it had been `EXHAUSTED`, the delivery's `documentation_status` returns to `INCOMPLETE`, its `allocated_total_cents` and `admin_total_cents` are zeroed, and its status returns to `DRAFT`. Voiding a `BILLED` delivery instead terminates it: the lines become `REVERSED`, each receiving grant's `expended_cents` is decreased by the reversed line totals, `burn_ratio` and posture are recomputed, the authorization's `units_delivered` is decreased and its `EXHAUSTED` status is released back to `ACTIVE` if it applied, and the delivery's status becomes `VOIDED`. `VOIDED` is terminal. In both cases the delivery's `version` is incremented, and in both cases the reversal can move a frozen grant back to `THROTTLED` or all the way to `OPEN`.

Cost allocation lines are listed with optional filters on `service_delivery_id`, `grant_id` and `status`, and a single line can be read back with its rank, its basis and its disallowed amount.

### 3.8. In-Kind Contributions and Match Credit

Many awards oblige the agency to match a share of the money with support it raises itself, and much of that support arrives as volunteer hours and parish effort rather than cash. A `ProgramManager` or a `FinanceOfficer` records an `InKindDonation` against a `grant_id`, identifying who provided it through `donor_type` — `PARISH`, `VOLUNTEER` or `CORPORATE` — and `donor_reference`, which carries the parish code or the volunteer identifier supplied by the coordinator. `donation_date` is the logical-clock instant the support was provided, and `hours` is the documented volunteer time, zero or greater. The contribution's worth is stated two ways: `valuation_method` records how it was valued, one of `IRS_STANDARD_RATE`, `APPRAISAL`, `ACTUAL_COST` or `UNVALUED`, and `rate_cents` is the per-hour valuation the coordinator supplied, zero or greater.

Two rules constrain what may be recorded. The first limits how much one donor can contribute in a short span: the sum of `hours` for the same `donor_reference` across the rolling seven-day window ending at the donation date must not exceed 40 hours, and a record that would push it over is refused with `ERR_INKIND_HOURS_EXCEEDED` (HTTP 422). The second ties the stated valuation to the method: when `valuation_method` is `IRS_STANDARD_RATE`, the `rate_cents` supplied must equal exactly 3390 — the IRS volunteer hour rate of $33.90 — and any other figure is refused with `ERR_INKIND_VALUATION_INVALID` (HTTP 422). A recorded contribution carries a status of `ACCEPTED`, `REJECTED` or `VOIDED`; rows in `REJECTED` or `VOIDED` state contribute nothing to any valuation or credit, and only `ACCEPTED` rows participate in the matching computation.

Match credit is not simply the value of the donation. It is capped twice, once by the grant's per-hour ceiling and once by what remains of the grant's outstanding match obligation, and it is computed in a defined order. The eligible population is every accepted contribution to that grant whose `valuation_method` is `IRS_STANDARD_RATE` or `APPRAISAL`, whose `donation_date` falls at or after the grant's `period_start` and at or before its `period_end`, and whose linked program — the program the grant funds — carries `match_eligible` true. A contribution valued by `ACTUAL_COST` or left `UNVALUED` never earns match credit, and neither does one credited to a program that is not match-eligible.

For the contribution being recorded, the per-hour value credited is the lower of its `rate_cents` and the grant's `max_in_kind_rate_cents`; the resulting `value_cents` is the hours multiplied by that credited hourly value, rounded half up to whole cents. The grant's total requirement is its `matching_requirement_pct` multiplied by its `total_award_cents`, rounded half up to whole cents. What has already been credited is the sum of `match_credit_cents` across the other eligible contributions to the same grant that were created earlier than this one — earlier by creation time, with ties in creation time broken by ascending `sequence_no`. The remaining requirement is that total requirement less what has already been credited, and it never falls below zero. The new contribution's `match_credit_cents` is the smaller of its computed value and the remaining requirement, so a grant whose requirement is already satisfied credits nothing further to later donations even though those donations still have value.

Two figures are surfaced for every contribution. `value_cents` is the capped value described above, and `uncapped_value_cents` is a diagnostic projection that values the same hours at the raw supplied rate without applying the grant's per-hour ceiling; it exists so that a coordinator can see what a contribution would have been worth under a more generous ceiling, and it never participates in match credit. To make the ceiling's effect concrete: a twelve-hour contribution at 3390 cents against a grant whose per-hour ceiling is 3000 credits 36,000 cents rather than the 40,680 cents the uncapped projection reports.

The credited total is what a funder report is measured against. Before an outcome report for a grant may be submitted, the grant's credited in-kind total must stand at or above its `matching_requirement_pct` multiplied by its `total_award_cents`; a submission attempted below that line is refused with `ERR_MATCH_REQUIREMENT_UNMET` (HTTP 422).

### 3.9. Outcome Reporting and Funder Acceptance

Every funder wants the year accounted for on its own terms, and each one measures something different. A `ProgramManager` opens an `OutcomeReport` against a `grant_id` with a `measure_code` naming the funder-specific performance measure — `HOUSING_PLACEMENTS`, `FOOD_UNITS_DISTRIBUTED`, `COUNSELING_COMPLETION`, `IMMIGRATION_CASES_CLOSED` or `REFUGEE_EMPLOYMENT` — and a reporting window bounded by `reporting_period_start`, the first instant covered and inclusive, and `reporting_period_end`, the last instant covered and also inclusive. The claim itself is stated as `numerator`, the count of successful outcomes claimed, and `denominator`, the count of clients in the reporting universe, both zero or greater. A new report opens in `DRAFT` status with `rate_pct` null. The report lifecycle admits `DRAFT`, `SUBMITTED`, `ACCEPTED` and `RETURNED`, and `ACCEPTED` is terminal.

Reporting windows may not be double-filed. The requested closed interval must not overlap any existing report for the same `grant_id` and the same `measure_code` whose status is `DRAFT`, `SUBMITTED` or `ACCEPTED`. Unlike the half-open windows used for authorizations, these intervals are closed and carry a mandatory one-day gap: an existing report whose `reporting_period_end` equals the new report's `reporting_period_start` is an overlap, and the attempt is refused with `ERR_OUTCOME_PERIOD_OVERLAP` (HTTP 409).

Submission is where the rate is computed, and it is available from two states. Submitting out of `DRAFT` — or out of `RETURNED`, which uses the same entry point — requires that the status is `DRAFT` or `RETURNED`, that the report's `denominator` is at least 5, and that the reporting window sits inside the grant's own award period, with `reporting_period_start` at or after the grant's `period_start` and `reporting_period_end` at or before its `period_end`. Submission computes `rate_pct` and `denominator_basis`, evaluates the grant's match position through the in-kind rule of §3.8, and then decides the outcome: when the grant's credited in-kind total is at or above its matching requirement, the report advances to `SUBMITTED`; when the credited total falls short, the report is not advanced and lands in `RETURNED` instead. A resubmission out of `RETURNED` is the narrower path — the status must be `RETURNED` and the report's `denominator` must still be at least 5 — and it recomputes `rate_pct` and sets the status to `SUBMITTED`. Every submission path increments the report's `version` by one.

The rate itself is derived from the delivery record, not from the claimed figures alone. The window is every delivery whose `grant_id` is this report's grant and whose `service_date` falls at or after `reporting_period_start` and at or before `reporting_period_end`; deliveries in `DRAFT`, `REJECTED` or `VOIDED` status are excluded from it. The denominator universe is a set of distinct clients drawn from that window, and which clients qualify depends on the variant. Under the all-served variant, it is every client with at least one window delivery in `DOCUMENTED` or `BILLED` status. Under the completed-only variant, it is the narrower set of clients who both have such a window delivery and whose enrollment for this grant reached `EXITED` status with an `exit_reason` of `COMPLETED`. The variant determines `denominator_basis`: `ALL_SERVED` for the first, `COMPLETED_ONLY` for the second. The effective denominator is the size of that set.

The effective denominator is then checked against a floor. When it is below 5, the sample is too small to report a rate at all: `rate_pct` is set to null and the report is forced into `RETURNED` rather than `SUBMITTED`. Otherwise the rate is the claimed `numerator` divided by the effective denominator, multiplied by 100, and rounded half up to exactly two decimal places — so a numerator of 12 against an all-served universe of 30 clients yields a rate of 40.00, while the same numerator against a completed-only universe of 18 clients yields 66.67. A stored `rate_pct` is either null or a value between 0.00 and 100.00 inclusive.

Acceptance and rejection belong to a `ComplianceOfficer` and are available only on a report in `SUBMITTED` status. Acceptance sets the status to `ACCEPTED` and increments the `version`; it is the end of the report's life. Rejection sets the status to `RETURNED`, clears `rate_pct` back to null so that a corrected claim must be recomputed from scratch, and increments the `version`. An operation attempted against a report whose status is not the from-state of any transition it may trigger is refused with `ERR_INVALID_STATE` (HTTP 409), and an unresolvable report identifier is refused with `ERR_OUTCOME_REPORT_NOT_FOUND`. Reports are listed against their grant with optional filters on `measure_code` and `status`.

## 4. Endpoint Definitions

Operations that bring a new, stand-alone resource into existence — a funder, a program, a grant, a client, an assessment, an eligibility screen, an enrollment, a service authorization, a delivery, an in-kind donation, an outcome report — answer with `201 Created` and return the created resource in the `data` field. Operations that modify an existing resource, including every state-transition action, answer with `200 OK` and return the updated resource. The clock-setting capability answers with `200 OK` and an empty `data` object.
