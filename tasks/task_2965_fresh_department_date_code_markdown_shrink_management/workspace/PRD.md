# Fresh Date-Code, Markdown & Shrink API — Product Requirements Document

## 1. Introduction

Fresh departments lose money in the last forty-eight hours of a product's life. A tray of ground chuck packed on Monday, a bakery batch pulled at 4 a.m., a case of vine tomatoes received on the produce dock — each one carries a sell-by instant, and every hour that passes after that instant converts sellable retail into shrink, regulatory exposure, and a customer who found expired product on a shelf. Today the decisions that govern those hours live in a clerk's head, a laminated card taped inside a walk-in cooler, and a spreadsheet the division office reconciles a week later. Nobody can say, at the moment a markdown is cut, whether the price honours the department's cost floor; nobody can prove, after a food-safety walk, that the past-date case found on shelf was pulled rather than re-tagged.

This document specifies the **Fresh Date-Code, Markdown & Shrink** service: a single system of record for item-level date codes, department-specific shelf-life policy, automated markdown ladders, markdown label printing and scan-price enforcement, food-bank donation eligibility and dock scheduling, shrink capture by cause code with segregated verification, forecast feedback derived from shrink history, gross-margin impact reporting, and past-date compliance auditing. Every collection is mounted under the `/fresh` prefix, and every entity is a peer — departments reference stores, items reference departments, lots reference items, but no resource is nested inside another resource's URL.

Two properties of the design deserve emphasis before the detail begins. First, **every temporal rule in this service reads a logical clock, never the host wall clock**: shelf life, days remaining, donation windows, audit windows, posting lag, and lookback windows are all evaluated against an instant the operator can set, which makes date-code behaviour reproducible in a test harness and auditable after the fact. Second, **money and units are conserved, not estimated**: a lot's received quantity always equals what remains on the shelf plus what was sold, shrunk, and donated, and every compensating action — voiding a markdown, disputing a verified shrink, cancelling a pickup — restores that balance exactly rather than partially.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API, without exception, must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role that user is acting in. If either header is absent, or is present but an empty string, the request is rejected with `ERR_UNAUTHENTICATED` and HTTP 401 before any other consideration — including before the request body is parsed and before any path identifier is looked up.

Five roles exist, and their spellings are exact:

- `StoreOperationsAdmin` — the division operations administrator. Owns the store, food-bank-partner, markdown-ladder and department registry, and may trigger the nightly date-code operations run.
- `DepartmentManager` — the fresh department manager. Approves deep and override markdowns, verifies shrink recorded by clerks, seals and reconciles donation manifests, voids labels and markdowns, and issues order recommendations.
- `FreshClerk` — the fresh department clerk. Receives lots, cuts ladder markdowns, prints and applies labels, rings sales, runs scan-price checks, records shrink, and resubmits disputed shrink.
- `ComplianceAuditor` — the division food-safety auditor. Opens, sweeps and escalates past-date audits, remediates findings, disputes questionable shrink, and pulls product from the shelf. This role cannot price, sell or donate product: every markdown, sale, label, manifest and order-recommendation write returns `ERR_UNAUTHORIZED` for a `ComplianceAuditor`.
- `DonationPartner` — the food-bank coordinator. Confirms, completes and cancels the pickups booked for its own organisation and reads their manifests.

If `X-User-Role` holds any string other than those five, or holds one of the five but that role is not listed as authorised for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` and HTTP 403.

**Identity semantics differ by role, and the difference is load-bearing.** When `X-User-Role` is `StoreOperationsAdmin`, `DepartmentManager`, `FreshClerk` or `ComplianceAuditor`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it wherever a workflow attributes an action to a person — as `recorded_by_user_id` and `verified_by_user_id` on a shrink event, `approved_by_user_id` on a markdown label, `opened_by_user_id` on a compliance audit, `resolved_by_user_id` on an audit finding, and `issued_by_user_id` on an order recommendation — but it never compares that value to any entity's `id`. Where segregation of duties applies, the comparison is user-identifier against user-identifier, never user-identifier against a resource key.

When `X-User-Role` is `DonationPartner`, by contrast, `X-User-ID` is the `id` of the acting `FoodBankPartner` row. Ownership checks on any pickup or manifest resource compare the pickup's `partner_id` foreign key to `X-User-ID`: a `DonationPartner` confirming, completing, cancelling or reading a pickup whose `partner_id` is not its own `X-User-ID` receives `ERR_UNAUTHORIZED` with HTTP 403. That ownership check runs **after** the endpoint's role check and **after** path-identifier existence has been established, so a `DonationPartner` naming a pickup identifier that does not exist at all still receives a 404, not a 403. When a `DonationPartner` lists pickups or manifest lines, the result set is silently narrowed to its own pickups regardless of any filter it supplies.

Segregation of duties is enforced in two places and is described in full where those workflows are specified: the user verifying a shrink event must differ from the user who recorded it (`ERR_SHRINK_SELF_VERIFICATION`, HTTP 403), and the manager nominated to approve an approval-gated or override markdown must differ from the requesting user (`ERR_MARKDOWN_SELF_APPROVAL`, HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint in this service is paginated with the same two query parameters. `limit` controls page size: it defaults to 10 when omitted, must be at least 1, and must be at most 100. `offset` controls the starting position: it defaults to 0 when omitted and must be 0 or greater. A `limit` outside the range 1 through 100, or a negative `offset`, is a request-shape violation and is rejected with `ERR_INVALID_REQUEST` and HTTP 400.

List results are ordered by `created_at` ascending, oldest first, and that ordering is stable across pages — it is never overridden by a filter, and there is no client-supplied sort parameter anywhere in the API. The `meta` block of a list response carries `limit` and `offset` echoing the effective values in force for the page, `total_count` giving the number of rows matching the filters before pagination is applied, and `has_more` set true when rows remain beyond the current page. Single-resource reads and command endpoints do not carry those four fields.

### 2.4. Resource Identity, Timestamps, Versioning and the Logical Clock

Every resource is identified by an `id` that the server mints as a UUID. Identifiers carry no type prefix and no embedded semantics; clients must treat them as opaque strings and must never construct one. Every resource also carries a `created_at` timestamp recording the instant it came into existence, formatted as an ISO 8601 UTC instant with exactly three fractional-second digits — for example `2026-08-12T00:00:00.000Z`. Every instant this API accepts or emits uses that same format and precision.

Most resources additionally carry `updated_at`, refreshed to the current logical clock on every mutation, and `version`, an integer that begins at 1 when the resource is created and increases by exactly 1 on every successful mutation of that resource. **`ScanPriceCheck` is the single exception**: a scan-price check is append-only and immutable once written, so it carries only `id` and `created_at` — it has neither `updated_at` nor `version`, and no endpoint exists that could mutate one.

`Store`, `FoodBankPartner`, `MarkdownLadder`, `Department`, `Item`, `DateCodeLot`, `MarkdownLabel`, `DonationPickup`, `DonationLotAssignment`, `ShrinkEvent`, `ComplianceAudit`, `AuditFinding` and `OrderRecommendation` all carry the full set: `id`, `created_at`, `updated_at` and `version`.

The **logical clock** is the only source of "now" in this system. Shelf-life arithmetic, days-remaining calculations, donation windows, dock windows, audit windows, shrink posting lag, the shrink lookback window, and every `*_at` value the server writes itself all read the logical clock. Before any operator sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; that startup default is fixed and must not fall back to real wall-clock time. A test-driving capability lets any role move the clock to a supplied `current_utc` instant, and it returns that instant back as `current_utc`. Moving the clock recomputes nothing on its own — every derived field is refreshed by the next business call or by the next nightly operations run that touches the affected resource.

### 2.5. Nested Reads, Filters and Path Resolution

The entity topology here is deliberately flat: every collection sits directly beneath the `/fresh` prefix, and no resource identifier appears nested inside another resource's collection path. Parent–child relationships are therefore navigated by filtering a peer collection rather than by walking a URL hierarchy — a store's departments are found by filtering departments on `store_id`, a department's items by filtering items on `department_id`, an item's lots by filtering lots on `item_id`, a lot's labels by filtering labels on `lot_id`, a pickup's manifest lines by filtering assignments on `pickup_id`, and an audit's findings by filtering findings on `audit_id`.

Where a path does carry identifiers, they are validated strictly left to right, and the first identifier that does not resolve decides the response with its own dedicated 404 code: `ERR_STORE_NOT_FOUND`, `ERR_PARTNER_NOT_FOUND`, `ERR_LADDER_NOT_FOUND`, `ERR_DEPARTMENT_NOT_FOUND`, `ERR_ITEM_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_LABEL_NOT_FOUND`, `ERR_CHECK_NOT_FOUND`, `ERR_PICKUP_NOT_FOUND`, `ERR_ASSIGNMENT_NOT_FOUND`, `ERR_SHRINK_EVENT_NOT_FOUND`, `ERR_AUDIT_NOT_FOUND`, `ERR_FINDING_NOT_FOUND` and `ERR_RECOMMENDATION_NOT_FOUND`. The same catalogue serves foreign keys supplied in a request body: a `store_id`, `partner_id`, `markdown_ladder_id`, `department_id`, `item_id` or `lot_id` that names a row which does not exist produces the matching 404 code. Body foreign keys are resolved only after every path identifier has resolved.

### 2.6. Money, Percentages and Rounding Discipline

All money in this API is expressed as **integer cents**. There are no decimal currency values anywhere in a request or a response, and no currency code: `base_retail_cents`, `unit_cost_cents`, `current_price_cents`, `from_price_cents`, `to_price_cents`, `scanned_price_cents`, `expected_price_cents`, `variance_cents`, `line_value_cents`, `line_credit_cents`, `provisional_value_cents`, `manifest_credit_cents`, `cost_value_cents`, `retail_value_cents`, `revenue_cents` and `markdown_giveback_cents` are all whole cents.

Percentages are numbers carried to **two decimal places**, and every rounding operation in this specification — without exception — is **round half up**: a value exactly halfway between two representable results rounds away from zero to the larger magnitude. That applies to `discount_pct`, `total_discount_pct`, `expected_sell_through_pct`, `shrink_rate_pct`, `shrink_cost_ratio_pct`, `gross_margin_pct`, `credit_rate_pct`, `sell_through_floor_pct`, `max_total_discount_pct` and `shrink_budget_pct` alike. Where a percentage may be negative — `gross_margin_pct` on a department that lost money over the window — the rounding is applied to the magnitude and the sign is preserved.

Two rounding-order rules matter more than any individual formula, because getting them backwards changes reported totals by whole cents:

1. **Round each line, then sum the rounded lines.** In the gross-margin report, the store rollup, the shrink cost ratio and the donation manifest credit, every per-lot or per-manifest-line amount is rounded to whole cents first, and only then are the rounded amounts added together. Summing unrounded products and rounding once at the end is wrong.
2. **Tier selection is keyed on the pre-credit total.** The donation credit rate is chosen from the manifest's provisional retail value, never from the credited value that the rate itself produces.

### 2.7. Optimistic Concurrency on Lot and Item Writes

Two write operations in this API are optimistically concurrent, and on both of them the version field is a **required, non-optional** input — omitting it is a request-shape violation answered with `ERR_INVALID_REQUEST` and HTTP 400, not a silent bypass.

**Markdown creation on a lot** requires `expected_lot_version`, carrying the client's last observed `version` of the target `DateCodeLot`. If that value does not equal the lot's current `version`, the markdown is rejected with `ERR_STALE_LOT_VERSION` and HTTP 412. This guard exists because a second markdown on an already `MARKED_DOWN` lot is legitimate product behaviour — the ladder walks deeper and the new label supersedes the old one — so nothing in the lot's state machine would otherwise reject a writer whose view of the lot predates the first markdown, the last sale, or a verified shrink. The version check turns that into a deterministic stale-view rejection.

**Order-recommendation creation** requires `expected_item_version`, carrying the client's last observed `version` of the target `Item`. If that value does not equal the item's current `version`, the create is rejected with `ERR_STALE_ITEM_VERSION` and HTTP 412. Here too a new recommendation legitimately supersedes the prior issued recommendation for the same item and window, so without the guard a writer holding a stale view of the item — its forecast velocity, its unit cost, or a recommendation another writer already issued — would silently overwrite a newer basis.

No other endpoint in this API accepts a version field. Every other write is unconditional on version, and a client must not send `expected_lot_version` or `expected_item_version` anywhere else.

### 2.8. Department Compliance Posture as a Write Gate

Each fresh department carries a derived `compliance_status`, one of `COMPLIANT`, `WATCH` or `BLOCKED`, which begins life as `COMPLIANT` when the department is created. It is never set directly by a client. Instead it is recomputed from scratch every time an audit is swept, an audit is escalated, a finding is remediated or waived, a shrink event is verified or disputed, a lot is withdrawn, a donation pickup is completed, or the nightly date-code operations run executes for the department.

The recomputation evaluates four clauses in a pinned order, and **the first clause that matches wins**:

1. If any `ComplianceAudit` of the department has `disposition_status` equal to `ESCALATED`, the posture is `BLOCKED`.
2. Otherwise, if any `ComplianceAudit` of the department has `severity` equal to `MAJOR` or `CRITICAL` while its `disposition_status` is anything other than `REMEDIATED`, the posture is `WATCH`.
3. Otherwise, if the department's `shrink_cost_ratio_pct` is strictly greater than its `shrink_budget_pct`, the posture is `WATCH`.
4. Otherwise the posture is `COMPLIANT`.

Because the clauses are ordered, `BLOCKED` outranks `WATCH` and `WATCH` outranks `COMPLIANT`: an escalated audit holds the department at `BLOCKED` even when the shrink ratio is comfortably inside budget, and a `MAJOR` audit awaiting follow-up holds it at `WATCH` even when the ratio is inside budget. Note the strictness in clause 3 — a ratio exactly equal to `shrink_budget_pct` does **not** trip `WATCH`; only a ratio above it does.

A `WATCH` posture is advisory: it changes nothing about what callers may do. A `BLOCKED` posture is a hard gate. While a department is `BLOCKED`, four operations on that department's lots are refused with `ERR_DEPARTMENT_COMPLIANCE_BLOCKED` and HTTP 409: cutting a markdown, voiding a lot's live markdown, posting register sales, and adding a lot to a donation manifest. Reads, label handling, scan-price checks, shrink capture, withdrawal and audit follow-up all remain available while blocked — the gate is there to stop the department from pricing, selling or giving away product while a critical food-safety escalation is open, not to freeze the department entirely.

### 2.9. Cascades, Aggregate Recomputation and the Unit-Conservation Invariant

Many operations in this service touch more than one resource. The rule is that a mutation refreshes `updated_at` and increments `version` on **every** resource it actually changes, not only on the resource named in the request path — so a shrink verification bumps both the shrink event's `version` and the affected lot's `version`, and a donation completion bumps the pickup, every picked-up manifest line, and every lot the manifest drained.

Three department-level aggregates are **recomputed in full from current state** whenever a triggering operation fires, never adjusted by an incremental delta:

- `markdown_liability_cents` is the department's open markdown giveback exposure. It is the sum, over every lot belonging to the department's items whose `status` is `FRESH`, `MARKED_DOWN` or `DONATION_PENDING`, of that lot's `quantity_on_hand` multiplied by the difference between its item's `base_retail_cents` and the lot's `current_price_cents`. Lots that are `DONATED`, `WITHDRAWN` or `DEPLETED` are excluded entirely. The arithmetic is exact integer cents with no rounding, and because integer addition is order-insensitive no tie-break is needed. It is recomputed on every markdown, every markdown void, every sale, every shrink verification or dispute, every withdrawal, every donation completion and every nightly operations run.
- `shrink_cost_ratio_pct` is a rolling ratio over a trailing window described in the reporting narrative below, recomputed on every shrink verification, shrink dispute, withdrawal, donation completion and nightly operations run.
- `open_finding_count` is the number of `AuditFinding` rows with `status` equal to `OPEN` across all of the department's compliance audits, recomputed whenever a sweep creates findings and whenever a finding is remediated or waived.

The **unit-conservation invariant** binds every unit-moving operation. For every lot, at every instant, `quantity_original` equals `quantity_on_hand` plus `units_sold` plus `units_shrunk` plus `units_donated` — exactly, in integers, with no tolerance. Two definitional details make the invariant computable: `units_shrunk` counts only shrink events whose `status` is `VERIFIED` or `POSTED`, so events sitting in `RECORDED`, `DISPUTED` or `VOIDED` contribute nothing; and `units_donated` counts only manifest lines whose `status` is `PICKED_UP`, so `ASSIGNED` and `REJECTED` lines contribute nothing. The invariant must hold after a forward action (a sale, a shrink verification, a donation completion, a withdrawal) and again after that action's compensating action (a shrink dispute against a verified event, a pickup cancellation), which is precisely why the compensating actions exist.

### 2.10. Four Kinds of Time Window, and Why They Differ

This service compares four different kinds of interval, and each uses different boundary arithmetic. Implementers should treat the differences as deliberate.

**Dock windows are fully closed and buffered.** A requested pickup window is compared against the store's other pickups on the same dock door whose `logistics_status` is `SCHEDULED` or `CONFIRMED`, after widening the comparison by a 30-minute turnaround buffer on both sides. A conflict exists when the new window's `scheduled_window_start` is at or before the existing window's `scheduled_window_end` plus 30 minutes **and** the existing window's `scheduled_window_start` is at or before the new window's `scheduled_window_end` plus 30 minutes. Both comparisons are inclusive: a new window starting exactly 30 minutes after an existing window ends still conflicts, while one starting a single second later does not. Pickups in `COMPLETED`, `CANCELLED` or `MISSED` have released their dock and never conflict.

**Audit windows are half-open and unbuffered.** A requested audit window on a department is compared against that department's audits whose `disposition_status` is `PENDING` or `ESCALATED`. A conflict exists when the new window's `window_start_at` is strictly before the existing window's `window_end_at` **and** the existing window's `window_start_at` is strictly before the new window's `window_end_at`. Because both comparisons are strict, two windows may abut exactly — an audit starting at the precise instant another ends is accepted — while a single second of true overlap is rejected. Audits already `REMEDIATED` are closed out and never conflict.

**The donation window is half-open on the lot's sell-by instant.** A lot may be pledged to a food bank only while the logical clock is at or after 48 hours before the lot's `sell_by_at` and strictly before `sell_by_at` itself. The instant exactly 48 hours before sell-by is eligible; the sell-by instant itself is not.

**Reporting and recommendation windows are inclusive calendar dates.** `window_start_date` and `window_end_date` are plain `YYYY-MM-DD` calendar dates interpreted in UTC, and both bounds are inclusive: the window runs from the very start of the start date through the very last millisecond of the end date.

### 2.11. Order of Rejection

When a request violates several rules at once, exactly one error is returned, and which one is fully determined. Checks run in the following order, and the **first** violated check decides the response — no later check can mask an earlier one.

1. Header presence — `ERR_UNAUTHENTICATED` (401).
2. Role recognition and endpoint authorisation — `ERR_UNAUTHORIZED` (403).
3. Request shape on every endpoint that takes input: required fields present, JSON types correct, enum members drawn from the declared sets, integers inside their documented ranges, calendar dates formatted `YYYY-MM-DD`, instants formatted as ISO 8601 UTC, `limit` between 1 and 100 and `offset` at least 0 — `ERR_INVALID_REQUEST` (400).
4. Path-identifier existence, validated left to right — the matching 404 code from §2.5.
5. Body foreign-key existence for `store_id`, `partner_id`, `markdown_ladder_id`, `department_id`, `item_id` and `lot_id` on department creation, item creation, lot creation, pickup creation, manifest-line creation, shrink recording, audit opening and recommendation creation — the matching 404 code.
6. Resource ownership for entity-backed roles: a `DonationPartner` must own the pickup it confirms, completes, cancels or reads by identifier — `ERR_UNAUTHORIZED` (403).
7. Optimistic-concurrency version match on markdown creation and recommendation creation — `ERR_STALE_LOT_VERSION` or `ERR_STALE_ITEM_VERSION` (412).
8. Lot state suitability for the requested operation — `ERR_LOT_NOT_PRICEABLE` (409) — on markdown creation, markdown void, withdrawal, sale posting and manifest-line creation.
9. Label lifecycle state on label printing, label application and label voiding — `ERR_LABEL_NOT_PRINTED` or `ERR_LABEL_ALREADY_VOIDED` (409).
10. Shrink-event lifecycle state on verification, dispute, resubmission and voiding — `ERR_SHRINK_NOT_VERIFIABLE` or `ERR_SHRINK_NOT_DISPUTED` (409).
11. Pickup dimension states on confirm, complete, seal, reconcile, cancel and manifest-line creation — `ERR_PICKUP_NOT_CONFIRMABLE`, `ERR_PICKUP_NOT_COMPLETABLE`, `ERR_MANIFEST_NOT_SEALED`, `ERR_MANIFEST_SEALED` or `ERR_PICKUP_NOT_RECONCILABLE` (409).
12. Audit, finding, ladder and recommendation lifecycle states on audit sweep, finding remediation or waiver, audit escalation, recommendation issuance, ladder activation and ladder retirement — `ERR_AUDIT_ALREADY_SWEPT`, `ERR_AUDIT_WINDOW_NOT_OPEN`, `ERR_FINDING_ALREADY_RESOLVED`, `ERR_RECOMMENDATION_NOT_ISSUABLE`, `ERR_LADDER_NOT_DRAFT` or `ERR_LADDER_NOT_ACTIVE` (409).
13. Department compliance gate on markdown creation, markdown void, sale posting and manifest-line creation — `ERR_DEPARTMENT_COMPLIANCE_BLOCKED` (409).
14. Donated product still inside its date code, on manifest-line creation — `ERR_PAST_DATE_NOT_DONATABLE` (422).
15. Cold-chain certification for `MEAT` and `SEAFOOD`, on manifest-line creation — `ERR_COLD_CHAIN_NOT_CERTIFIED` (422).
16. Shrink segregation of duties, on shrink verification — `ERR_SHRINK_SELF_VERIFICATION` (403).
17. Markdown-approval segregation of duties, on markdown creation — `ERR_MARKDOWN_SELF_APPROVAL` (403).
18. Sampling permission, on shrink recording — `ERR_SAMPLING_NOT_ALLOWED` (422).
19. Waiver permission, on finding remediation — `ERR_WAIVER_NOT_PERMITTED` (422).
20. Partner accepts the department's product, on manifest-line creation — `ERR_PARTNER_DEPARTMENT_NOT_ACCEPTED` (422).
21. Partner is active, on pickup creation and pickup confirmation — `ERR_PARTNER_NOT_ACTIVE` (409).
22. Partner region matches store region, on pickup creation — `ERR_PARTNER_REGION_MISMATCH` (422).
23. The department's ladder is active at pricing time, on markdown creation — `ERR_LADDER_NOT_ACTIVE` (409).
24. Ladder department code matches the department it is attached to, on department creation and department update — `ERR_LADDER_DEPARTMENT_MISMATCH` (422).
25. Item is active on lot creation, and the store is active with its donation programme enabled on pickup creation — `ERR_ITEM_DISCONTINUED` or `ERR_DONATION_PROGRAM_DISABLED` (409).
26. Dock door is known to the store, on pickup creation — `ERR_DOCK_DOOR_UNKNOWN` (422).
27. The donation window has opened, on manifest-line creation — `ERR_DONATION_WINDOW_CLOSED` (422).
28. Dock window availability, on pickup creation — `ERR_DOCK_WINDOW_OVERLAP` (409).
29. Audit window availability, on audit opening — `ERR_AUDIT_WINDOW_OVERLAP` (409).
30. Reporting window sanity — the end date is not before the start date and the window spans at most 31 days — on recommendation creation and the department margin report — `ERR_RECOMMENDATION_WINDOW_INVALID` (422).
31. A ladder rung is reachable at all, on markdown creation and markdown quoting — `ERR_RUNG_NOT_REACHED` (422).
32. A re-ladder strictly deepens, on markdown creation — `ERR_RUNG_NOT_DEEPER` (409).
33. Manager approval supplied where the rung or override demands it, on markdown creation — `ERR_MANAGER_APPROVAL_REQUIRED` (422).
34. Requested units do not exceed the lot's units on hand, on sale posting, shrink recording, shrink resubmission, shrink verification and manifest-line creation — `ERR_INSUFFICIENT_UNITS` (422).
35. A manifest carries at least one line, on manifest sealing — `ERR_EMPTY_MANIFEST` (422).
36. A lot appears at most once per manifest, on manifest-line creation — `ERR_DUPLICATE_LOT_ASSIGNMENT` (409).
37. Withdrawal remediation requires the finding's lot to still hold units, on finding remediation — `ERR_REMEDIATION_NOT_PERMITTED` (422).
38. Escalation requires a critical audit, on audit escalation — `ERR_ESCALATION_NOT_WARRANTED` (422).
39. The recommendation window contains received product, on recommendation creation — `ERR_INSUFFICIENT_SHRINK_HISTORY` (422).
40. Uniqueness — store number globally, ladder name globally, department code within a store, item UPC within a department — on store creation, ladder creation, department creation and item creation — `ERR_STORE_NUMBER_DUPLICATE`, `ERR_LADDER_NAME_DUPLICATE`, `ERR_DEPARTMENT_CODE_DUPLICATE` or `ERR_ITEM_UPC_DUPLICATE` (409).
41. Total discount inside the ladder cap, on markdown creation — `ERR_MAX_DISCOUNT_EXCEEDED` (422).
42. Override price at or above the cost floor, on markdown creation — `ERR_PRICE_BELOW_COST_FLOOR` (422).

Two consequences of this ordering are worth calling out explicitly, because they are easy to get backwards. A markdown request that is *both* stale and blocked by compliance returns `ERR_STALE_LOT_VERSION`, because the version check sits above the compliance gate. And a markdown that would exceed the ladder's discount cap *and* also names the requester as its own approver returns `ERR_MARKDOWN_SELF_APPROVAL`, because the segregation-of-duties check sits far above the fiscal caps.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Registry: Stores, Partners, Ladders, Departments and Items

Before a single tray of product can be date-coded, a division operations administrator has to build out the registry, and the order is forced by the foreign keys: stores and markdown ladders first, then departments, then items.

A store is registered with a `store_number`, a `name` and a `region_code`. The `store_number` is exactly four digits, characters `0` through `9` only, and must be globally unique — a second store claiming a number already taken is refused with `ERR_STORE_NUMBER_DUPLICATE`. The `name` runs from 1 to 120 characters. The `region_code` runs from 1 to 24 characters drawn from uppercase letters, digits and the hyphen; it is the key that later matches a food-bank partner to this store. Three optional attributes round out the row. `dock_door_codes` is an array of between 1 and 8 receiving-dock identifiers, each 1 to 8 characters long, and it defaults to the three doors `D1`, `D2` and `D3` when the caller omits it — a pickup naming a dock door outside this array is refused with `ERR_DOCK_DOOR_UNKNOWN`. `donation_program_enabled` is a boolean that defaults to true and decides whether this store may book food-bank pickups at all. `status` is either `ACTIVE` or `SUSPENDED`, defaulting to `ACTIVE`. Later on, an administrator may revise a store's `status`, `donation_program_enabled`, `dock_door_codes` and `name`; each such revision bumps the store's `version` by one. Attempting to schedule a pickup at a store that is `SUSPENDED`, or at one whose donation programme has been switched off, is refused with `ERR_DONATION_PROGRAM_DISABLED`.

Food-bank partners are registered next. A partner carries a `name` of 1 to 120 characters, a `contact_email` that must contain exactly one `@` character, and a `service_region_code` of 1 to 24 characters that must equal the `region_code` of any store whose dock it is booked on — a mismatch is refused with `ERR_PARTNER_REGION_MISMATCH`. `accepted_department_codes` is an array of between 1 and 6 department codes, each drawn from `MEAT`, `DELI`, `BAKERY`, `PRODUCE`, `SEAFOOD` and `DAIRY`, with no duplicates; product from a department whose code is absent from that list cannot be pledged to this partner. `cold_chain_certified` is a boolean defaulting to false, asserting that the partner runs refrigerated transport. `status` is `ACTIVE` or `SUSPENDED`, defaulting to `ACTIVE`. Two counters are maintained by the server and never supplied by a caller: `pickups_completed_count`, the number of this partner's pickups whose `logistics_status` has reached `COMPLETED`, and `units_received_total`, the sum of pledged units across every manifest line of this partner's pickups that reached `PICKED_UP`. Both start at 0. An administrator may later revise a partner's `status`, `cold_chain_certified`, `accepted_department_codes` and `contact_email`, bumping `version` by one. Suspending a partner does **not** retroactively cancel pickups it has already confirmed; it only blocks any further confirmation, which is refused with `ERR_PARTNER_NOT_ACTIVE`.

**Markdown ladders** encode a division's pricing policy for one department code. A ladder has a `name` of 1 to 60 characters that must be globally unique — a duplicate is refused with `ERR_LADDER_NAME_DUPLICATE` — and a `department_code` drawn from the same six-member set, restricting which departments may attach to it. Its substance is `rungs`, an ordered array of between 2 and 6 objects, each carrying a `days_remaining_max` integer, a `discount_pct` number, and a `requires_manager_approval` boolean. **The rung's index is its zero-based position in that array**, and the array must be sorted so that `days_remaining_max` strictly decreases from one entry to the next while `discount_pct` strictly increases; every `discount_pct` must be strictly greater than 0 and strictly less than 100. A ladder whose rungs violate any of those orderings is refused with `ERR_INVALID_REQUEST`. Two policy caps complete the ladder: `sell_through_floor_pct`, defaulting to 60, is the expected-sell-through level below which the sell-through pricing reading begins deepening the rung, and must be greater than 0 and at most 100 with two decimal places; `max_total_discount_pct`, defaulting to 75, caps the cumulative discount any markdown may produce on a lot, and must be greater than 0 and at most 95 with two decimal places.

A ladder is born in `DRAFT` with `activated_at` null, and it cannot price anything in that state. An administrator activates it, which requires the ladder to still be `DRAFT` — activating anything else is refused with `ERR_LADDER_NOT_DRAFT` — and re-checks that the rung array holds at least two entries with `days_remaining_max` strictly decreasing and `discount_pct` strictly increasing. Activation moves `status` from `DRAFT` to `ACTIVE`, stamps `activated_at` with the current logical clock, and bumps the ladder's `version` by one. Later the same administrator may retire it: retirement requires `status` to be `ACTIVE`, refusing anything else with `ERR_LADDER_NOT_ACTIVE`, moves `status` from `ACTIVE` to `RETIRED`, and bumps `version` by one. **Retirement never rewrites already-priced lots.** Every department still pointing at the retired ladder keeps its existing shelf prices exactly as they stand; retirement only closes the pricing gate, so any later markdown attempt on those departments' lots is refused with `ERR_LADDER_NOT_ACTIVE`.

A fresh department is created under a store with a `store_id`, an attached `markdown_ladder_id`, a `code` from the six-member department set, and a `shelf_life_days_default` between 1 and 60 days. The pair of `store_id` and `code` must be unique, so a store cannot hold two `BAKERY` departments — a duplicate is refused with `ERR_DEPARTMENT_CODE_DUPLICATE`. The attached ladder's `department_code` must equal the department's own `code`; attaching a `MEAT` ladder to a `DAIRY` department is refused with `ERR_LADDER_DEPARTMENT_MISMATCH`. Three optional policy knobs carry defaults: `past_date_tolerance_hours`, an integer from 0 to 72 defaulting to 4, is the grace period past a lot's sell-by instant inside which a compliance finding scores at the lightest weight; `shrink_budget_pct`, greater than 0 and at most 100 with two decimal places and defaulting to 2.50, is the shrink ratio above which the department's posture drops to `WATCH`; and `markdown_policy_profile`, one of `STANDARD`, `AGGRESSIVE` or `CONSERVATIVE` and defaulting to `STANDARD`, selects the velocity multiplier applied to the item's forecast when the department's expected sell-through is projected — `STANDARD` multiplies the forecast by 1.00, `AGGRESSIVE` by 1.25, and `CONSERVATIVE` by 0.80. Five server-maintained values complete the department, all starting at their neutral value: `compliance_status` at `COMPLIANT`, `markdown_liability_cents` at 0, `shrink_cost_ratio_pct` at 0, `sweep_epoch` at 0, and `open_finding_count` at 0.

Department policy is revisable by both an administrator and the department's own manager, covering `markdown_ladder_id`, `shelf_life_days_default`, `past_date_tolerance_hours`, `shrink_budget_pct` and `markdown_policy_profile`. Any such revision bumps the department's `version` by one, and when `shrink_budget_pct` in particular changes, the department's compliance posture is immediately recomputed against the new budget. Re-pointing `markdown_ladder_id` re-directs **future** markdowns only; lots already priced under the old ladder keep their prices. The same `ERR_LADDER_DEPARTMENT_MISMATCH` guard applies on revision as on creation.

Items are the last registry layer. An item belongs to a department by `department_id` and carries a `upc` of exactly 12 digits, unique within its department — a repeat is refused with `ERR_ITEM_UPC_DUPLICATE`. Its `description`, 1 to 120 characters, is what prints on the markdown label a clerk sticks on the package. Pricing rests on two integers: `base_retail_cents`, the undiscounted shelf price, which must be greater than 0, and `unit_cost_cents`, the landed unit cost, which must be greater than 0 **and strictly less than** `base_retail_cents` — an item whose cost meets or exceeds its retail is refused with `ERR_INVALID_REQUEST`. `unit_cost_cents` is the basis of the markdown cost floor and of every shrink, cost-of-goods and donation valuation in the reporting layer. `daily_forecast_units`, a number greater than 0 with two decimal places, is the item's baseline velocity in units per day and feeds both expected sell-through and order recommendations. Three optional attributes shape behaviour downstream: `shelf_life_days`, either null or an integer from 1 to 60 and defaulting to null, overrides the department default when present; `donation_eligible`, defaulting to true, decides whether the item may be pledged to a food bank at all; and `sampling_allowed`, defaulting to false, decides whether shrink may ever be booked against this item under the sampling cause code. `status` is `ACTIVE` or `DISCONTINUED`, defaulting to `ACTIVE`; receiving a new lot for a `DISCONTINUED` item is refused with `ERR_ITEM_DISCONTINUED`. An administrator or manager may later revise an item's `status`, `daily_forecast_units`, `donation_eligible` and `sampling_allowed`, and each revision bumps the item's `version` by one — which, as §2.7 explains, invalidates any order-recommendation request still holding the item's previous version.

### 3.2. Receiving a Date-Coded Lot and Fixing Its Sell-By Instant

A clerk, manager or administrator receives product by creating a date-code lot against an item. The payload names the `item_id`, the `production_date` as a plain `YYYY-MM-DD` calendar date, and `quantity_original`, the number of units received, which must be greater than 0. An optional `production_batch_code` — either null or 1 to 24 characters, null by default — records the plant batch code printed on the case label.

The single most consequential thing lot receipt does is fix the lot's `sell_by_at`. The effective shelf life is the item's own `shelf_life_days` when that value is present, and the owning department's `shelf_life_days_default` when the item's value is null. The sell-by instant is then midnight UTC at the start of the `production_date`, advanced by that many days, each day counted as 86,400 seconds — so a lot packed on 2026-08-05 with an effective shelf life of 7 days sells by `2026-08-12T00:00:00.000Z`. **The item's shelf life and the department's default are read once, at receipt, and never re-read.** Changing the department default afterwards does not re-date a single existing lot, and `sell_by_at` is immutable for the life of the lot.

Receipt initialises the rest of the row deterministically. `quantity_on_hand` starts equal to `quantity_original`. `units_sold`, `units_shrunk`, `units_donated`, `revenue_cents` and `markdown_giveback_cents` all start at 0. `current_price_cents` starts equal to the item's `base_retail_cents`, `current_rung_index` starts at -1 to mean "unmarked", and `total_discount_pct` starts at 0. `past_date_flag` starts false. `status` starts at `FRESH`. The lot's `expected_sell_through_pct` is computed immediately, and the owning department's `markdown_liability_cents` is recomputed — which, because the lot is priced at base retail, adds nothing to the exposure.

**Days remaining** is the quantity every date-code rule turns on. It is the number of whole days between the logical clock and the lot's `sell_by_at`, obtained by taking the difference in seconds, dividing by 86,400, and taking the floor toward negative infinity. The floor direction matters at both ends: 1.99 days of remaining life yields 1, and a quarter of a day *past* sell-by yields -1, not 0. The value is an integer and may be negative. It is re-derived from the clock on every markdown quote, every markdown, every donation-eligibility check, and every nightly operations run — it is never stored.

**Expected sell-through** projects how much of the lot the department can reasonably move before its date code expires, expressed as a percentage of the units still on the shelf. The projection has three ingredients. First, the department's velocity multiplier: 1.00 under `STANDARD`, 1.25 under `AGGRESSIVE`, 0.80 under `CONSERVATIVE`. Second, the promotional lift: if at least one of the lot's markdown labels has reached `APPLIED`, one tenth of the lot's `quantity_on_hand` — that is, 10 percent of it — is added as extra projected movement; if no applied label exists, the lift is zero. Third, the calendar: the item's `daily_forecast_units` multiplied by the velocity multiplier multiplied by days remaining, where days remaining is floored at zero so a past-date lot contributes no calendar movement at all. Projected units are the calendar term plus the promotional lift. `expected_sell_through_pct` is then that projected-unit figure divided by `quantity_on_hand`, multiplied by 100, rounded half up to two decimal places, and finally capped at 100 — a lot whose projection exceeds its own shelf balance reports exactly 100.00, never more. When `quantity_on_hand` is 0 the value is exactly 0. This figure is refreshed at lot receipt, on every markdown, on every sale, on every shrink verification or dispute, on every label application or voiding, and on every nightly operations run. Note the sequencing consequence: a markdown creates its label in `QUEUED`, so **a markdown never lifts its own sell-through** — only the separate act of applying a printed label does.

### 3.3. Walking the Markdown Ladder

A markdown is the department's response to a shortening date code, and it is always priced by the ladder attached to the lot's department. Cutting one moves the lot from `FRESH` to `MARKED_DOWN`, or — when the lot is already `MARKED_DOWN` — keeps it in `MARKED_DOWN` while the ladder walks a rung deeper. Both a `FreshClerk` and a `DepartmentManager` may cut a markdown; only a `DepartmentManager` may override the ladder's price.

**Choosing the rung.** Rung selection compares days remaining against the ladder's `days_remaining_max` values. Every rung whose `days_remaining_max` is greater than or equal to the lot's days remaining is a candidate, and the base rung is the **deepest** such candidate — the one with the highest index. The comparison boundary is inclusive, so a lot with exactly as many days remaining as a rung's `days_remaining_max` does select that rung. If no rung qualifies at all — that is, days remaining exceeds the `days_remaining_max` of the very first rung, which is the largest one because the array strictly decreases — the request is refused with `ERR_RUNG_NOT_REACHED` and HTTP 422. That refusal is skipped entirely when the caller supplies an explicit override price.

**Pricing the rung.** The cost floor is a hard fiscal boundary derived from the item's landed cost: it is 40 percent of `unit_cost_cents`, rounded half up to whole cents. The chosen rung's `discount_pct` is applied to the item's `base_retail_cents` — the raw price is base retail reduced by that percentage — and the raw result is rounded half up to whole cents. The label's `to_price_cents` is then the **greater** of that rounded raw price and the cost floor, so the ladder can never drive a price below 40 percent of cost even on its deepest rung. `total_discount_pct` on the lot is recomputed from the price actually landed: the difference between `base_retail_cents` and `to_price_cents`, divided by `base_retail_cents`, multiplied by 100, rounded half up to two decimal places. If that figure exceeds the ladder's `max_total_discount_pct` the markdown is refused with `ERR_MAX_DISCOUNT_EXCEEDED` and HTTP 422.

**Three ways to price, selected by the request.** The payload carries `expected_lot_version` (always required, per §2.7) and three optional inputs that select the pricing reading.

- Omitting `pricing_variant`, or sending it as `LADDER_DAYS`, gives the calendar reading: the effective rung is exactly the base rung, days remaining alone decides the price, and expected sell-through is recorded on the lot but never priced in. This is also the reading the nightly operations run uses when it marks lots down automatically.
- Sending `pricing_variant` as `SELL_THROUGH` deepens the rung for slow movers. If the lot's `expected_sell_through_pct` is at or above the ladder's `sell_through_floor_pct`, the shortfall is zero steps and the effective rung is the base rung. Otherwise the shortfall is the gap between the floor and the lot's expected sell-through, divided by 20 percentage points and rounded **up** to the next whole number of steps; the effective rung is the base rung advanced by that many steps, but never past the last rung in the array. A lot 45 percentage points short of a 60 percent floor therefore advances three rungs (45 divided by 20 is 2.25, rounded up to 3), clamped to the deepest rung the ladder actually defines. Whenever the shortfall is one step or more this reading produces a strictly lower `to_price_cents` than the calendar reading would on identical lot data.
- Supplying `override_price_cents` selects the manual reading. The label's `to_price_cents` becomes exactly the supplied figure, the label's `rung_index` is recorded as -1, and rung selection is bypassed. The override is not exempt from the fiscal guards: an override below the cost floor is refused with `ERR_PRICE_BELOW_COST_FLOOR` and HTTP 422, and an override whose resulting `total_discount_pct` exceeds `max_total_discount_pct` is refused with `ERR_MAX_DISCOUNT_EXCEEDED`.

**Who may authorise a deep price.** Two situations demand a named approver: the effective rung's `requires_manager_approval` flag is true, or the caller supplied `override_price_cents`. In either case the request must come from a `DepartmentManager` **and** carry a non-null `approval_manager_user_id`; if the role is wrong or the approver is missing, the markdown is refused with `ERR_MANAGER_APPROVAL_REQUIRED` and HTTP 422. A `FreshClerk` may cut ladder markdowns freely but can never override the ladder price. And because a manager must not sign off on their own deep discount, `approval_manager_user_id` must differ from the requesting `X-User-ID`; naming yourself is refused with `ERR_MARKDOWN_SELF_APPROVAL` and HTTP 403.

**What a markdown produces.** Every successful markdown cuts a new markdown label, in `QUEUED` status, recording `lot_id`, the `rung_index` it prices (or -1 for an override), a `reason`, `from_price_cents` holding the lot's `current_price_cents` as it stood immediately before this markdown, the new `to_price_cents`, a `discount_pct` computed as the difference between the item's `base_retail_cents` and `to_price_cents` divided by `base_retail_cents` multiplied by 100 and rounded half up to two decimal places, and a `barcode`. The barcode is scannable and its format is fixed: the literal characters `MD-`, then the item's `upc`, then another hyphen, then `to_price_cents` written as a decimal integer left-padded with zeros to exactly 5 digits — a 12-digit UPC of `012345678905` priced at 349 cents yields `MD-012345678905-00349`. The `reason` takes one of four values: `LADDER_AUTO` for a first markdown under the calendar reading, `SELL_THROUGH` for a first markdown under the sell-through reading, `MANUAL_OVERRIDE` whenever the price came from an explicit override, and `RE_LADDER` when the markdown lands the lot on a strictly deeper ladder rung than it already held. `approved_by_user_id` records the approving manager on approval-gated rungs and overrides and is null otherwise. `printed_at` and `applied_at` both start null, and `supersedes_label_id` is null on the first label a lot ever receives.

Alongside the label, the markdown rewrites the lot: `current_price_cents` becomes the label's `to_price_cents`, `current_rung_index` becomes the label's `rung_index`, `total_discount_pct` is recomputed, `expected_sell_through_pct` is recomputed, the department's `markdown_liability_cents` is recomputed, and the lot's `version` is incremented by one.

**Re-laddering an already marked-down lot.** The same operation applied to a lot already in `MARKED_DOWN` is a legitimate self-loop: the lot stays `MARKED_DOWN` while the ladder walks deeper. It requires the lot to still hold units, requires the department not to be `BLOCKED`, requires the ladder to still be `ACTIVE`, and requires the version match. Above all it must **strictly deepen**: the effective rung index must be greater than the lot's `current_rung_index`, and an equal or shallower landing is refused with `ERR_RUNG_NOT_DEEPER` and HTTP 409. An override satisfies the deepening requirement in the only way it can — since an override records `rung_index` -1 rather than a real rung, it counts as deepening exactly when `override_price_cents` is strictly below the lot's current `current_price_cents`; an override at or above the current price is likewise refused with `ERR_RUNG_NOT_DEEPER`. On a re-ladder the new label's `supersedes_label_id` is set to the `id` of the lot's newest label still in `QUEUED`, `PRINTED` or `APPLIED`, and **that superseded label is transitioned to `VOIDED`** in the same operation; if the lot has no such label the field stays null. The lot's price, rung index and total discount are then taken from the new label, the department's `markdown_liability_cents` is recomputed, and the lot's `version` is incremented by one.

**Undoing a markdown.** Only a `DepartmentManager` may void a lot's live markdown, and only while the lot is `MARKED_DOWN` — attempting it on a lot in any other status is refused with `ERR_LOT_NOT_PRICEABLE`, and attempting it in a `BLOCKED` department is refused with `ERR_DEPARTMENT_COMPLIANCE_BLOCKED`. An optional `reason_note` may accompany the request. The void is the exact compensating action for the markdown: every label on the lot in `QUEUED`, `PRINTED` or `APPLIED` transitions to `VOIDED`, `current_price_cents` is restored to the item's `base_retail_cents`, `current_rung_index` returns to -1, `total_discount_pct` returns to 0, `expected_sell_through_pct` is recomputed, and the lot's `version` is incremented by one. Because liability is recomputed from lot state rather than adjusted incrementally, the department's `markdown_liability_cents` returns to precisely the value it held before the lot's first markdown — the `FRESH` → `MARKED_DOWN` → `FRESH` cycle closes exactly, with no residue.

**Quoting without writing.** Before committing, an administrator, manager or clerk may ask for a read-only markdown quote on a lot, which prices it under **both** ladder readings and writes nothing at all — in particular the lot's `version` is left untouched. The quote echoes `lot_id`, the current `days_remaining`, the lot's `expected_sell_through_pct`, the ladder's `sell_through_floor_pct` and `max_total_discount_pct`, the derived `cost_floor_price_cents`, and the `base_rung_index` selected by the calendar alone. For the calendar reading it reports `ladder_days_rung_index`, `ladder_days_price_cents` and `ladder_days_total_discount_pct`; for the sell-through reading it reports `sell_through_shortfall_steps`, `sell_through_rung_index`, `sell_through_price_cents` and `sell_through_total_discount_pct`. Both readings are computed with the same cost-floor clamp and the same rounding rules as a real markdown. When no rung is satisfied at all, the quote itself is refused with `ERR_RUNG_NOT_REACHED`.

### 3.4. Printing Tags, Applying Them, and Enforcing the Scanned Price

A markdown label is a physical price tag, and its lifecycle mirrors what a clerk actually does with paper. A newly cut label sits in `QUEUED`. A `FreshClerk` or `DepartmentManager` prints it, which requires the label to still be `QUEUED` — printing a label in any other status is refused with `ERR_LABEL_NOT_PRINTED` and HTTP 409 — and additionally requires the label's `to_price_cents` to still equal the lot's `current_price_cents`, which is the safety catch that stops a stale tag from reaching the shelf. In practice a queued label whose lot has since re-laddered has already been voided by that re-ladder, so this catch is belt-and-braces. Printing moves `status` from `QUEUED` to `PRINTED`, stamps `printed_at` with the current logical clock, and bumps the label's `version` by one.

Applying the tag is a separate act. It requires the label to be `PRINTED` — applying anything else is refused with `ERR_LABEL_NOT_PRINTED` — and requires the lot to still be `FRESH`, `MARKED_DOWN` or `DONATION_PENDING`. Application moves `status` from `PRINTED` to `APPLIED`, stamps `applied_at` with the current logical clock, bumps the label's `version` by one, and recomputes the lot's `expected_sell_through_pct` — which now, for the first time, includes the 10 percent promotional lift described in §3.2. Application is the single call that turns that lift on.

Voiding a label is the manager's escape hatch for a mis-printed tag, and it does **not** change the shelf price: the lot keeps its `current_price_cents`, `current_rung_index` and `total_discount_pct` exactly as they stand. A label may be voided from `QUEUED`, `PRINTED` or `APPLIED`; only a label already in `VOIDED` refuses the operation, with `ERR_LABEL_ALREADY_VOIDED` and HTTP 409. Voiding bumps the label's `version` by one, and when the voided label was `APPLIED` it also recomputes the lot's `expected_sell_through_pct`, which loses the promotional lift if no other applied label remains on the lot. Labels are also voided by the system, without any explicit request, in five situations: a deeper re-ladder supersedes the label, the lot's markdown is voided, the lot is withdrawn, a donation completion drains the lot to zero, and any other operation depletes the lot to zero.

**Scan-price enforcement** closes the loop between the tag on the package and the price the register rings. A clerk or manager records a scan-price check against a lot, naming the `register_lane_code` that performed it — 1 to 12 characters — and the `scanned_price_cents` the register rang up, which must be 0 or greater. The check captures `expected_price_cents` as the lot's `current_price_cents` at check time, and `variance_cents` as the scanned price minus the expected price, retaining the sign. It also snapshots `label_barcode_snapshot`, the `barcode` of the lot's `APPLIED` label if one exists, and null otherwise. `outcome` classifies the sign: `MATCH` when the variance is exactly zero, `OVERCHARGE` when the variance is positive (the customer was charged more than the shelf price), and `UNDERCHARGE` when it is negative.

`enforcement_action` is then decided in a fixed order. When the outcome is `OVERCHARGE` and the variance is **at least 25 cents**, the action is `LOT_WITHDRAWN`: an overcharge of that magnitude in the customer's disfavour pulls the whole lot off the shelf. When the outcome is `MATCH`, the action is `NONE`. In every remaining case — any `UNDERCHARGE`, and an `OVERCHARGE` smaller than 25 cents — the action is `PRICE_CORRECTION`, which flags the discrepancy without moving product. The 25-cent boundary is inclusive: a variance of exactly 25 cents withdraws the lot, while 24 cents only raises a correction. When the action is `LOT_WITHDRAWN`, the check drives the lot's withdrawal transition and the entire withdrawal cascade described in §3.5, exactly as if a manager had pulled the lot by hand. A scan-price check is append-only: it is written once, carries no `updated_at` and no `version`, and there is no endpoint that can revise or delete one.

### 3.5. Selling Product, Pulling Product, and Running a Lot to Zero

Register sales are posted against a lot by a `FreshClerk` or a `DepartmentManager`. The payload carries `quantity_units`, the number of units rung up, and optionally the `register_lane_code` that rang them. Sales are only accepted on a lot whose status is `FRESH` or `MARKED_DOWN`; posting against a `DONATION_PENDING`, `DONATED`, `WITHDRAWN` or `DEPLETED` lot is refused with `ERR_LOT_NOT_PRICEABLE`. A `BLOCKED` department refuses sales with `ERR_DEPARTMENT_COMPLIANCE_BLOCKED`, and units exceeding the lot's `quantity_on_hand` are refused with `ERR_INSUFFICIENT_UNITS`.

Every sale is valued at the price on the shelf **at the moment of the call**, which is what makes the giveback figure meaningful. The sold units are subtracted from `quantity_on_hand` and added to `units_sold`. `revenue_cents` grows by the units sold multiplied by the lot's `current_price_cents` at call time. `markdown_giveback_cents` grows by the units sold multiplied by the difference between the item's `base_retail_cents` and the lot's `current_price_cents` at call time — so a lot sold partly at full price and partly at two successively deeper markdowns accumulates giveback in three separate slices, each priced as the register saw it. The lot's `expected_sell_through_pct` and the department's `markdown_liability_cents` are recomputed, and the lot's `version` is incremented by one.

When a sale takes `quantity_on_hand` to exactly 0, the lot moves from `FRESH` or `MARKED_DOWN` to `DEPLETED` in the same operation, and every label on it still in `QUEUED`, `PRINTED` or `APPLIED` transitions to `VOIDED`. The same depletion transition fires when a shrink verification drains the last unit. The one thing that never produces `DEPLETED` is a withdrawal: **`WITHDRAWN` outranks `DEPLETED`**, so a lot zeroed by a withdrawal is `WITHDRAWN` and never `DEPLETED`, even though the withdrawal also leaves `quantity_on_hand` at 0.

**Withdrawing a lot** pulls it from the shelf for good and is available to a `DepartmentManager` or a `ComplianceAuditor`, with an optional `reason_note`. It requires the lot to be `FRESH`, `MARKED_DOWN` or `DONATION_PENDING` and to still hold units; a lot in any other status, or one already at zero units, is refused with `ERR_LOT_NOT_PRICEABLE`. Withdrawal is the widest cascade in the service, and every step of it matters:

1. A shrink event is synthesised for the lot's entire remaining balance, with `cause_code` `SPOILAGE`, `origin` `WITHDRAWAL_AUTO`, `quantity_units` equal to the lot's `quantity_on_hand`, and `status` already `VERIFIED`. Its `recorded_by_user_id` is the acting `X-User-ID`, and its `verified_by_user_id` is the literal string `system` — the withdrawal supplies its own verification, so the segregation-of-duties rule is not consulted.
2. Because that synthesised event is already `VERIFIED`, the lot's `units_shrunk` grows by that quantity and `quantity_on_hand` becomes 0, keeping the unit-conservation invariant exact.
3. Because the lot now holds zero units, every label on it in `QUEUED`, `PRINTED` or `APPLIED` transitions to `VOIDED`, and the department's `markdown_liability_cents` is recomputed — the withdrawn lot drops out of the exposure entirely.
4. Because the department's shrink cost has moved, its `shrink_cost_ratio_pct` is recomputed and its `compliance_status` is recomputed from the four clauses of §2.8.
5. Every donation manifest line for this lot still in `ASSIGNED` becomes `REJECTED`; each affected pickup's `assignment_count` is decremented and its `provisional_value_cents` recomputed.
6. The lot's `status` becomes `WITHDRAWN` and its `version` is incremented by one.

That same cascade is reached from three directions: a manager or auditor pulling the lot directly, a scan-price check whose `enforcement_action` came out `LOT_WITHDRAWN`, and an audit finding closed with `remediation` `WITHDRAWN`. All three run every step above.

### 3.6. Shrink: Recording, Verification, Dispute and Posting

Shrink is where a fresh department's margin actually leaks, so this service separates the person who observes it from the person who accepts it. A `FreshClerk` or a `DepartmentManager` records a shrink event against a lot by supplying the `lot_id`, a `cause_code`, the `quantity_units` written off, and optionally a `note` of 1 to 240 characters (null by default). The four cause codes are `SPOILAGE`, `DAMAGE`, `SAMPLING` and `THEFT`. `SAMPLING` is special: it is only accepted when the lot's item has `sampling_allowed` set true, and otherwise the record is refused with `ERR_SAMPLING_NOT_ALLOWED` and HTTP 422. `quantity_units` must be greater than 0 and at most the lot's `quantity_on_hand`; more than that is refused with `ERR_INSUFFICIENT_UNITS`.

A newly recorded event lands in `RECORDED` with `origin` `MANUAL` and `recorded_by_user_id` set to the acting `X-User-ID`. Three valuations are captured at that moment. `unit_cost_cents_snapshot` freezes the item's `unit_cost_cents` as it stands, so the cost basis of this write-off can never be re-dated afterwards. `cost_value_cents` is the fully loaded cost of the shrink: the units written off multiplied by that cost snapshot, then increased by a waste-handling surcharge of 3.5 percent, then rounded half up to whole cents. `retail_value_cents` is the units written off multiplied by the lot's `current_price_cents` at record time. **Recording moves no units whatsoever** — the lot's `quantity_on_hand` and `units_shrunk` are untouched, and the event contributes nothing to any report while it sits in `RECORDED`.

**Verification is the call that actually moves units**, and it belongs exclusively to a `DepartmentManager`. It requires the event to be in `RECORDED`; verifying an event in any other status is refused with `ERR_SHRINK_NOT_VERIFIABLE` and HTTP 409. It requires the verifying `X-User-ID` to differ from the event's `recorded_by_user_id`, and a manager who recorded the shrink personally cannot verify it — a second manager must, and self-verification is refused with `ERR_SHRINK_SELF_VERIFICATION` and HTTP 403. It re-checks that the event's `quantity_units` still fits inside the lot's `quantity_on_hand`, which may have shrunk since the record was written, refusing with `ERR_INSUFFICIENT_UNITS` if it no longer does. Verification sets `verified_by_user_id` and stamps `verified_at` with the current logical clock, recomputes `cost_value_cents`, moves `status` from `RECORDED` to `VERIFIED`, and increments both the event's `version` and the lot's `version` by one.

From there the effects cascade four levels deep, and each level is caused by the one above it rather than by the verify call itself. First, the lot's `units_shrunk` grows by the event's `quantity_units` and its `quantity_on_hand` shrinks by the same amount. Second, **because** `quantity_on_hand` reached zero, the lot's status becomes `DEPLETED` — unless the event's `origin` is `WITHDRAWAL_AUTO`, in which case the lot is already `WITHDRAWN` and stays there. Third, **because** the lot is no longer sellable, every label on it in `QUEUED`, `PRINTED` or `APPLIED` transitions to `VOIDED` and the department's `markdown_liability_cents` is recomputed. Fourth, **because** the department's shrink cost has moved, its `shrink_cost_ratio_pct` is recomputed and its `compliance_status` becomes `WATCH` when that ratio ends up strictly above the department's `shrink_budget_pct`.

**Disputing** an event is available to a `DepartmentManager` or a `ComplianceAuditor`, with an optional `dispute_note`, and its behaviour depends sharply on where the event stands. Disputing a `RECORDED` event is the cheap case: `status` becomes `DISPUTED`, `verified_by_user_id` and `verified_at` are set to null, the event's `version` is incremented by one, and **no unit movement occurs at all** — the lot's `quantity_on_hand`, its `units_shrunk`, the department's `markdown_liability_cents` and the department's `compliance_status` are every one of them untouched. Disputing a `VERIFIED` event whose `origin` is `MANUAL` is the compensating case: the event's `quantity_units` are subtracted from the lot's `units_shrunk` and added back to its `quantity_on_hand`, restoring the unit-conservation invariant exactly; if the lot had been `DEPLETED` it reopens, returning to `MARKED_DOWN` when its `current_rung_index` is 0 or greater and to `FRESH` when that index is -1; the department's `markdown_liability_cents`, `shrink_cost_ratio_pct` and `compliance_status` are all recomputed; `verified_by_user_id` and `verified_at` are cleared to null; and both the event's `version` and the lot's `version` are incremented by one. An event whose `origin` is `WITHDRAWAL_AUTO` can never be disputed, which is exactly why a withdrawn lot is never reopened by this route. Nor can a `POSTED` event ever be disputed. Both refusals carry `ERR_SHRINK_NOT_VERIFIABLE`.

A disputed event has two exits, and they belong to different people. A `FreshClerk` — and only a `FreshClerk` — resubmits it with a corrected `quantity_units` and an optional replacement `note`. Resubmission requires the event to be `DISPUTED`, refusing anything else with `ERR_SHRINK_NOT_DISPUTED` and HTTP 409, and requires the new `quantity_units` to be greater than 0 and no greater than the lot's current `quantity_on_hand`. It overwrites `quantity_units`, `note`, `recorded_by_user_id` (now the resubmitting clerk, which re-arms the segregation-of-duties check against whoever verifies next) and `retail_value_cents`, **preserves the original `unit_cost_cents_snapshot`** so the cost basis cannot be re-dated, recomputes `cost_value_cents`, moves `status` from `DISPUTED` back to `RECORDED`, and increments `version` by one — closing the `RECORDED` → `VERIFIED` → `DISPUTED` → `RECORDED` cycle. No units move until the event is verified again. Alternatively a `DepartmentManager` voids the event for good: this too requires `DISPUTED`, refusing anything else with `ERR_SHRINK_NOT_DISPUTED`, moves `status` to `VOIDED`, and increments `version` by one. A `VOIDED` event never again contributes units or cost to any report.

**Posting** is the system's own final step, performed by the nightly date-code operations run rather than by any user. An event in `VERIFIED` becomes `POSTED` once the logical clock has reached at least 24 hours past the event's `verified_at`. Posting stamps `posted_at` with the current logical clock, increments `version` by one, and makes the event permanently immutable: from `POSTED` there is no dispute, no resubmission and no void. Posted shrink continues to count in `units_shrunk` and in every cost report, exactly as verified shrink does.

### 3.7. Food-Bank Donation: Dock Windows, Manifests and Credit

Product that will not sell before its date code can still feed people, and this service treats a donation as a scheduled logistics event with its own paperwork. A donation pickup carries **two independent status dimensions**: `logistics_status`, tracking the truck and the dock, which starts at `SCHEDULED` and may reach `CONFIRMED`, `COMPLETED`, `CANCELLED` or `MISSED`; and `manifest_status`, tracking the paperwork, which starts at `DRAFT` and may reach `SEALED` and then `RECONCILED`. Neither dimension constrains the other's transition: confirming the truck leaves the manifest exactly where it was, and sealing the manifest does not confirm the truck.

**Reserving the dock.** An administrator or department manager books a window by supplying the `store_id` whose dock the truck will use, the `partner_id` of the collecting food bank, the `dock_door_code` reserved for the window, and the window itself as `scheduled_window_start` and `scheduled_window_end` — both inclusive ISO 8601 UTC instants, with the end strictly after the start; an end at or before the start is refused with `ERR_INVALID_REQUEST`. Five referential checks then run in the order given in §2.11: the partner must be `ACTIVE`, else `ERR_PARTNER_NOT_ACTIVE`; the partner's `service_region_code` must equal the store's `region_code`, else `ERR_PARTNER_REGION_MISMATCH`; the store must be `ACTIVE` with `donation_program_enabled` true, else `ERR_DONATION_PROGRAM_DISABLED`; the `dock_door_code` must appear in the store's `dock_door_codes`, else `ERR_DOCK_DOOR_UNKNOWN`; and the requested window must not collide with another pickup on the same store and dock door under the closed, 30-minute-buffered comparison of §2.10, else `ERR_DOCK_WINDOW_OVERLAP`. A newly booked pickup starts with `logistics_status` `SCHEDULED`, `manifest_status` `DRAFT`, `assignment_count` 0, `provisional_value_cents` 0, `credit_rate_pct` 0, `manifest_credit_cents` 0, `units_picked_up_total` 0 and `completed_at` null.

**Pledging a lot.** A `FreshClerk` or `DepartmentManager` adds a manifest line by naming the `lot_id` and the `quantity_units` pledged from it. A line may be added only while the pickup's `manifest_status` is `DRAFT`; once the manifest is `SEALED` or `RECONCILED`, further lines are refused with `ERR_MANIFEST_SEALED` and HTTP 409. The pickup's `logistics_status` is deliberately **not** consulted here — a pickup the food bank has already confirmed may still take lines onto its draft manifest, because the two dimensions are independent.

Donation eligibility is a conjunction of seven conditions, every one of which must hold:

- The lot's item has `donation_eligible` true, and the lot still holds units — a lot whose item is flagged ineligible, or a lot at zero units, is refused with `ERR_LOT_NOT_PRICEABLE`.
- The lot's `status` is `FRESH` or `MARKED_DOWN`; a lot that is `DONATION_PENDING`, `DONATED`, `WITHDRAWN` or `DEPLETED` is likewise refused with `ERR_LOT_NOT_PRICEABLE`.
- The logical clock is strictly before the lot's `sell_by_at`. Product that has reached or passed its date code may not be given away, and the attempt is refused with `ERR_PAST_DATE_NOT_DONATABLE` and HTTP 422.
- The logical clock is at or after 48 hours before the lot's `sell_by_at`. Product with more than two days of life left is still saleable, so the donation window has not opened, and the attempt is refused with `ERR_DONATION_WINDOW_CLOSED` and HTTP 422. Taken with the previous condition this is the half-open window of §2.10: the instant exactly 48 hours before sell-by qualifies, the sell-by instant itself does not.
- The lot's department `code` appears in the partner's `accepted_department_codes`, else `ERR_PARTNER_DEPARTMENT_NOT_ACCEPTED` and HTTP 422.
- If the lot's department `code` is `MEAT` or `SEAFOOD`, the partner's `cold_chain_certified` must be true; an uncertified partner receiving refrigerated protein is refused with `ERR_COLD_CHAIN_NOT_CERTIFIED` and HTTP 422. Departments other than `MEAT` and `SEAFOOD` impose no cold-chain requirement.
- The department must not be `BLOCKED`, else `ERR_DEPARTMENT_COMPLIANCE_BLOCKED`.

Two further guards protect the manifest itself: `quantity_units` must be greater than 0 and no greater than the lot's `quantity_on_hand` at assignment time, else `ERR_INSUFFICIENT_UNITS`; and a lot may appear at most once per manifest in `ASSIGNED` or `PICKED_UP`, so a second line for the same lot on the same pickup is refused with `ERR_DUPLICATE_LOT_ASSIGNMENT` and HTTP 409.

A successful pledge creates the line in `ASSIGNED`, snapshotting `unit_price_cents_snapshot` from the lot's `current_price_cents` **at assignment time** and computing `line_value_cents` as the pledged `quantity_units` multiplied by that snapshot. `line_credit_cents` stays 0 until the manifest is sealed. The lot moves from `FRESH` or `MARKED_DOWN` to `DONATION_PENDING` — and note that a lot pledged after a markdown snapshots the marked-down price, not base retail, so a later re-pricing of the lot cannot move the manifest's value. The pickup's `assignment_count` is incremented, its `provisional_value_cents` is recomputed, and the lot's `version` is incremented by one.

**Sealing and valuing the manifest.** Only a `DepartmentManager` may seal, and sealing requires `manifest_status` to be `DRAFT` — resealing is refused with `ERR_MANIFEST_SEALED` — requires the pickup's `logistics_status` to still be `SCHEDULED` or `CONFIRMED`, refusing a pickup already `COMPLETED`, `CANCELLED` or `MISSED` with `ERR_PICKUP_NOT_COMPLETABLE`, and requires `assignment_count` to be at least 1, refusing an empty manifest with `ERR_EMPTY_MANIFEST` and HTTP 422. Sealing moves `manifest_status` from `DRAFT` to `SEALED`, leaves `logistics_status` untouched, increments the pickup's `version` by one, and runs the manifest valuation in four pinned steps:

1. `provisional_value_cents` is the sum, over every manifest line on the pickup in `ASSIGNED`, of that line's `quantity_units` multiplied by its `unit_price_cents_snapshot`. This is the manifest's full retail value at 100 percent.
2. `credit_rate_pct` is selected from that provisional total by tier: 62.50 percent when the provisional value is below 50,000 cents (that is, under five hundred dollars), 72.50 percent when it is at or above 50,000 cents but below 200,000 cents, and 80 percent when it is at or above 200,000 cents. **The tier is keyed on the provisional total and never on the credited total** — re-keying from the credited figure, which is by construction smaller and can fall into a lower tier, is wrong, and pinning the order is exactly what removes that ambiguity.
3. Each line, walked in `created_at` ascending order, receives a `line_credit_cents` equal to its `quantity_units` multiplied by its `unit_price_cents_snapshot` multiplied by `credit_rate_pct`, divided by 100, and rounded half up to whole cents. Every line is rounded individually.
4. `manifest_credit_cents` is the exact integer sum of those already-rounded line credits — never a single rounding of the unrounded total.

**The truck.** A `DonationPartner` confirms the pickup it owns. Confirmation requires `logistics_status` to be `SCHEDULED`, refusing anything else with `ERR_PICKUP_NOT_CONFIRMABLE` and HTTP 409, requires the acting `X-User-ID` to equal the pickup's `partner_id`, and requires the partner row itself to still be `ACTIVE`, refusing a suspended partner with `ERR_PARTNER_NOT_ACTIVE`. Confirmation moves `logistics_status` from `SCHEDULED` to `CONFIRMED`, leaves `manifest_status` exactly as it was — a pickup may be confirmed while its manifest is still `DRAFT` — and increments `version` by one.

The same partner records the collection. Completion requires `logistics_status` to be `CONFIRMED`, refusing anything else with `ERR_PICKUP_NOT_COMPLETABLE`, requires `manifest_status` to be `SEALED`, refusing a still-draft manifest with `ERR_MANIFEST_NOT_SEALED` and HTTP 409, and requires ownership. Completion is a broad cascade: every manifest line in `ASSIGNED` becomes `PICKED_UP`; each pledged lot's `units_donated` grows and its `quantity_on_hand` shrinks by the line's `quantity_units`. A lot whose line took its whole remaining balance — that is, a line whose `quantity_units` equalled the lot's `quantity_on_hand` — is drained to zero and becomes `DONATED`, with every label on it in `QUEUED`, `PRINTED` or `APPLIED` transitioning to `VOIDED`. A lot only partially drained leaves `DONATION_PENDING` and returns to `MARKED_DOWN` when its `current_rung_index` is 0 or greater, or to `FRESH` when that index is -1. Completion also sets `completed_at` to the current logical clock and `units_picked_up_total` to the sum of `quantity_units` over the pickup's `PICKED_UP` lines, increments the partner's `pickups_completed_count` and adds those units to the partner's `units_received_total`, moves `logistics_status` from `CONFIRMED` to `COMPLETED`, recomputes `markdown_liability_cents`, `shrink_cost_ratio_pct` and `compliance_status` for every affected department, and increments the pickup's `version` by one.

**When the truck does not come.** Either a `DepartmentManager` or the owning `DonationPartner` may cancel a pickup whose `logistics_status` is `SCHEDULED` or `CONFIRMED`, optionally supplying a `cancel_reason`; cancelling one that has already reached `COMPLETED`, `CANCELLED` or `MISSED` is refused with `ERR_PICKUP_NOT_COMPLETABLE`. Cancellation moves `logistics_status` to `CANCELLED`, turns every `ASSIGNED` line into `REJECTED`, releases the dock window so a later pickup may occupy the overlapping interval, recomputes `markdown_liability_cents` for every affected department, and increments `version` by one. The nightly operations run reaches the same outcome by a different route for a window that simply lapsed, moving `logistics_status` from `SCHEDULED` or `CONFIRMED` to `MISSED`.

In both the cancellation and the missed case, and in the partial-line case on completion, each affected lot unwinds out of `DONATION_PENDING` — but **only when that lot has no other manifest line still in `ASSIGNED` on any pickup whose `logistics_status` is `SCHEDULED` or `CONFIRMED`**. A lot pledged to two live pickups stays `DONATION_PENDING` until the last of them releases it. When the lot does unwind, its destination is fully determined by its own pricing history: `MARKED_DOWN` when `current_rung_index` is 0 or greater, `FRESH` when it is -1. The lot's `version` is incremented by one on each such unwind.

**Reconciling the paperwork.** After the truck outcome is known, a `DepartmentManager` reconciles the manifest. Reconciliation requires `manifest_status` to be `SEALED`, refusing anything else with `ERR_MANIFEST_NOT_SEALED`, and requires `logistics_status` to have reached `COMPLETED`, `CANCELLED` or `MISSED`, refusing a pickup still `SCHEDULED` or `CONFIRMED` with `ERR_PICKUP_NOT_RECONCILABLE` and HTTP 409. It moves `manifest_status` from `SEALED` to `RECONCILED`, increments `version` by one, and reruns all four valuation steps with the input set narrowed to lines in `PICKED_UP` only — so `provisional_value_cents`, `credit_rate_pct`, every surviving line's `line_credit_cents` and the pickup's `manifest_credit_cents` are all rewritten, and lines that ended up `REJECTED` drop out of the credit entirely.

### 3.8. Past-Date Compliance: Audits, Findings, Escalation and Remediation

A division food-safety auditor is the only role that may open a past-date audit. Opening one names the `department_id` under audit and the audit window as `window_start_at` and `window_end_at`, the start inclusive and the end exclusive, with the end strictly after the start — otherwise `ERR_INVALID_REQUEST`. The window is compared against the department's audits whose `disposition_status` is `PENDING` or `ESCALATED` under the half-open, unbuffered arithmetic of §2.10, and an overlap is refused with `ERR_AUDIT_WINDOW_OVERLAP` and HTTP 409; windows that merely abut are accepted. A new audit starts with `sweep_status` `NOT_STARTED`, `disposition_status` `PENDING`, `severity` `NONE`, `past_date_lot_count`, `past_date_units_total` and `severity_points_total` all 0, `swept_at` null, and `opened_by_user_id` set to the auditor's `X-User-ID`. Like the pickup, the audit carries two independent dimensions: the shelf walk and the follow-up.

**The shelf walk.** Sweeping an audit is a once-only act, and it requires `sweep_status` to still be `NOT_STARTED`; a second sweep is refused with `ERR_AUDIT_ALREADY_SWEPT` and HTTP 409. It also requires the logical clock to be inside the audit's window — at or after `window_start_at` and strictly before `window_end_at` — and a clock outside that half-open interval is refused with `ERR_AUDIT_WINDOW_NOT_OPEN` and HTTP 409.

The sweep gathers every lot belonging to the audited department's items whose `status` is `FRESH`, `MARKED_DOWN` or `DONATION_PENDING`, that still holds units, and whose `sell_by_at` the logical clock has reached or passed. Those lots are processed in `created_at` ascending order, and one audit finding is written per lot. Findings are **never** created by a client request; the sweep is the only writer, and it sets each finding's `audit_id` and `lot_id` itself.

Each finding records `hours_past_date`, the whole hours between the lot's `sell_by_at` and the sweep instant, obtained by taking the difference in seconds, dividing by 3,600, and taking the floor; `units_on_shelf`, the lot's `quantity_on_hand` at sweep time; a `severity_multiplier`; and `severity_points`. The multiplier bands the elapsed time against the department's own tolerance: it is **1** when `hours_past_date` is at or below the department's `past_date_tolerance_hours`, **3** when it is above that tolerance but at or below 48 hours, and **6** when it exceeds 48 hours. `severity_points` is `units_on_shelf` multiplied by that multiplier, rounded half up to a whole number. A new finding starts with `remediation` `NONE`, `status` `OPEN` and `resolved_by_user_id` null.

The audit then rolls the findings up. `past_date_lot_count` is the number of findings written, `past_date_units_total` is the sum of their `units_on_shelf`, and `severity_points_total` is the sum of their `severity_points`. `severity` is banded from that total: `NONE` at exactly 0 points, `MINOR` from 1 through 9 points, `MAJOR` from 10 through 29 points, and `CRITICAL` at 30 points or more. The `CRITICAL` boundary is inclusive at 30 — 29 points is `MAJOR`, 30 points is `CRITICAL`. Finally the sweep moves `sweep_status` from `NOT_STARTED` to `SWEPT`, stamps `swept_at` with the current logical clock, **leaves `disposition_status` at `PENDING`** because the shelf walk and the follow-up are independent, sets `past_date_flag` true on every lot it wrote a finding against, increases the department's `open_finding_count` by the number of findings created, recomputes the department's `compliance_status`, and increments the audit's `version` by one.

**Escalation.** An auditor escalates a swept audit whose `severity` is `CRITICAL` and which still has at least one `OPEN` finding, optionally supplying an `escalation_note`. An audit whose `severity` is anything other than `CRITICAL` is refused with `ERR_ESCALATION_NOT_WARRANTED` and HTTP 422 — which is also what an unswept audit receives, since an audit that has not been swept still carries `severity` `NONE`. An audit whose findings have all been closed is refused with `ERR_FINDING_ALREADY_RESOLVED` and HTTP 409. Escalation moves `disposition_status` from `PENDING` to `ESCALATED` while leaving `sweep_status` at `SWEPT`, increments the audit's `version` by one, and recomputes the department's posture — which becomes `BLOCKED`, because an escalated audit is the first and highest clause of §2.8 and outranks every other consideration. While the department is `BLOCKED`, every markdown, markdown void, sale and manifest-line creation on its lots is refused with `ERR_DEPARTMENT_COMPLIANCE_BLOCKED`.

**Closing a finding.** Both a `ComplianceAuditor` and a `DepartmentManager` may close a finding, and the request carries up to three inputs: `remediation`, `waive` and an optional `resolution_note`. A finding must be `OPEN`; closing an already-closed one is refused with `ERR_FINDING_ALREADY_RESOLVED`. Supplying neither `remediation` nor `waive` is refused with `ERR_REMEDIATION_NOT_PERMITTED` and HTTP 422.

Sending `remediation` as `WITHDRAWN` is the substantive path, available to both roles, and it requires the finding's lot to still hold units — a lot already at zero is refused with `ERR_REMEDIATION_NOT_PERMITTED`. It cascades four levels: first the finding itself takes `remediation` `WITHDRAWN`, records `resolved_by_user_id` from the acting `X-User-ID`, moves `status` from `OPEN` to `RESOLVED`, and increments its `version` by one. Second, **because** the finding resolved with a withdrawal, the lot transitions to `WITHDRAWN` and a shrink event with `cause_code` `SPOILAGE`, `origin` `WITHDRAWAL_AUTO` and `status` `VERIFIED` is synthesised for its remaining units. Third, **because** that shrink event is `VERIFIED`, the lot's `units_shrunk` grows, its `quantity_on_hand` becomes 0, its labels in `QUEUED`, `PRINTED` or `APPLIED` transition to `VOIDED`, and the department's `markdown_liability_cents` and `shrink_cost_ratio_pct` are recomputed. Fourth, the department's `open_finding_count` is decremented, and **because** this may have closed the audit's last open finding, the audit's `disposition_status` may bubble up as described below.

Sending `waive` as true is the light path and is reserved to a `ComplianceAuditor`; a `DepartmentManager` attempting to waive receives `ERR_UNAUTHORIZED` and HTTP 403. A waiver is only permitted when the finding scored at `severity_multiplier` 1 — that is, when `hours_past_date` fell at or inside the department's `past_date_tolerance_hours`. A finding whose multiplier is 3 or 6 cannot be waived, and the attempt is refused with `ERR_WAIVER_NOT_PERMITTED` and HTTP 422. A waiver moves `status` from `OPEN` to `WAIVED`, leaves `remediation` at `NONE`, records `resolved_by_user_id`, increments the finding's `version` by one, **leaves the lot on the shelf entirely untouched** — no withdrawal, no shrink event, no price change, no unit movement — decrements the department's `open_finding_count`, and may likewise bubble the audit up.

**Bubble-up.** The audit's follow-up dimension is derived from the aggregate state of its findings rather than set directly. Once the audit has been swept and every one of its findings has reached `RESOLVED` or `WAIVED`, the audit's `disposition_status` moves to `REMEDIATED` — from `PENDING` or from `ESCALATED` alike — and its `version` is incremented by one. The department's `open_finding_count` and `compliance_status` are then recomputed: a remediated audit no longer contributes a `WATCH` or a `BLOCKED` reason, so a department held at `BLOCKED` by an escalation can drop back to `WATCH` or all the way to `COMPLIANT`, depending on what the four ordered clauses of §2.8 now find.

### 3.9. Feeding Shrink History Back Into Ordering, and the Nightly Operations Run

**Order recommendations** turn observed shrink into a buying number. A `DepartmentManager` creates one by naming the `item_id`, the history window as `window_start_date` and `window_end_date`, the required `expected_item_version`, and optionally the `method`. The window must have an end date at or after its start date and must span at most 31 days; a reversed or over-long window is refused with `ERR_RECOMMENDATION_WINDOW_INVALID` and HTTP 422. Both dates are inclusive: the window opens at the very start of `window_start_date` and closes at the last millisecond of `window_end_date`, in UTC.

The computation proceeds in a fixed order. `received_units` is the sum of `quantity_original` across every lot of the item created inside the window; if that comes to 0 there is no history to reason from, and the request is refused with `ERR_INSUFFICIENT_SHRINK_HISTORY` and HTTP 422. `shrink_units` is then counted according to the selected method, over shrink events on those same lots. **Only events whose `cause_code` is `SPOILAGE`, `DAMAGE` or `THEFT` count; `SAMPLING` shrink is deliberately excluded**, because sampling is a merchandising cost the department chose to incur, not a forecasting error. `shrink_rate_pct` is `shrink_units` divided by `received_units`, multiplied by 100, rounded half up to two decimal places. `open_units` is the sum of `quantity_on_hand` across the item's lots whose `status` is `FRESH` or `MARKED_DOWN`, regardless of when those lots were created. Finally `recommended_order_units` is the item's `daily_forecast_units` multiplied by a three-day order horizon, dampened by the shrink rate — that is, multiplied by one minus the shrink rate expressed as a fraction — with `open_units` subtracted, the result rounded half up to a whole number, and then floored at 0 so the recommendation is never negative. **The dampener uses the already-rounded two-decimal `shrink_rate_pct`, not the raw unrounded ratio.**

Two methods select what counts as shrink, and they are genuinely different numbers:

- `CHRONOLOGICAL_ACTUAL`, which is the default when `method` is omitted, counts only shrink events in `VERIFIED` or `POSTED` — money the department has already recognised. Nothing projected, nothing unverified.
- `FORWARD_LOOKING_PROJECTED` counts all of that, plus every event still sitting in `RECORDED` awaiting a manager's verification, plus a projection for each still-open lot of the item whose `status` is `FRESH` or `MARKED_DOWN`: for such a lot, the projected loss is its `quantity_on_hand` less the item's `daily_forecast_units` multiplied by that lot's days remaining floored at zero, that product rounded half up to a whole number, and the difference itself floored at 0 so a lot expected to sell out projects no loss. Because this method adds unverified and projected shrink to the same denominator, it reports a higher `shrink_rate_pct` and a strictly lower `recommended_order_units` than `CHRONOLOGICAL_ACTUAL` whenever any unverified or projected shrink exists.

A new recommendation lands in `DRAFT` with `issued_by_user_id` null, and it writes `received_units`, `shrink_units`, `shrink_rate_pct`, `open_units` and `recommended_order_units`. Creating it **increments the item's `version` by one**, which is why two consecutive recommendation requests cannot reuse the same `expected_item_version`. If an earlier recommendation for the same `item_id`, `window_start_date` and `window_end_date` is currently `ISSUED`, that earlier row moves from `ISSUED` to `SUPERSEDED`, its `version` is incremented by one, and the new row's `supersedes_recommendation_id` points at its `id`; when there was no such row, `supersedes_recommendation_id` stays null. Issuing a recommendation to the buying system requires its `status` to be `DRAFT`, refusing anything else with `ERR_RECOMMENDATION_NOT_ISSUABLE` and HTTP 409, and requires `received_units` to be greater than 0. Issuance moves `status` from `DRAFT` to `ISSUED`, sets `issued_by_user_id` to the acting `X-User-ID`, and increments `version` by one.

**Gross-margin impact** is reported per department over an inclusive calendar window supplied as `window_start_date` and `window_end_date`, and it is a pure read: it writes nothing, and in particular it does **not** rewrite the department's stored `shrink_cost_ratio_pct`. A reversed or over-31-day window is refused with `ERR_RECOMMENDATION_WINDOW_INVALID`. The input set is every lot of the department's items whose `created_at` calendar date falls inside the window in UTC, in **every** status — `DONATED`, `WITHDRAWN` and `DEPLETED` lots are all included, because the money they consumed is exactly what the report is about. Since `units_shrunk` already excludes `RECORDED`, `DISPUTED` and `VOIDED` shrink, only verified and posted shrink reaches the report.

Lots are walked in `created_at` ascending order and each one contributes five lines. Its revenue line is simply its `revenue_cents` and its giveback line its `markdown_giveback_cents`, both already whole cents. Its cost-of-goods line is `units_sold` multiplied by its item's `unit_cost_cents`, increased by the 3.5 percent waste-handling surcharge, rounded half up to whole cents. Its shrink-cost line is the same arithmetic applied to `units_shrunk`, and its donation-cost line the same arithmetic applied to `units_donated`. **Every line is rounded before anything is added.** The report then sums the rounded lines into `revenue_cents`, `markdown_giveback_cents`, `cogs_cents`, `shrink_cost_cents` and `donation_cost_cents`, and reports `lot_count` alongside the `department_id`, `window_start_date` and `window_end_date`. `gross_margin_cents` is revenue less cost of goods less shrink cost less donation cost. `gross_margin_pct` is `gross_margin_cents` divided by `revenue_cents`, multiplied by 100, rounded half up to two decimal places — and exactly 0 when `revenue_cents` is 0. `shrink_cost_ratio_pct` is `shrink_cost_cents` divided by the sum of `cogs_cents`, `shrink_cost_cents` and `donation_cost_cents`, multiplied by 100, rounded half up to two decimal places — and exactly 0 when that denominator is 0.

A store-level rollup is available to an administrator or auditor over the same `window_start_date` and `window_end_date`. It evaluates the department report once per department of the store and adds the department totals, reporting `store_id`, the window, `department_count`, and the same nine money and percentage figures: `revenue_cents`, `markdown_giveback_cents`, `cogs_cents`, `shrink_cost_cents`, `donation_cost_cents`, `gross_margin_cents`, `gross_margin_pct` and `shrink_cost_ratio_pct`. Because each department's lines were rounded before its own totals were formed, and the rollup adds only those already-rounded department totals, **the rollup equals the sum of the department reports exactly** — there is no second rounding pass and no drift.

The department's own stored `shrink_cost_ratio_pct` uses the same per-line rounding as the report but a different window: a **trailing seven days**, running from seven days before the current logical clock through the logical clock itself, closed at both ends, over the department's lots whose `created_at` falls inside that window. It is the shrink-cost total divided by the sum of cost of goods, shrink cost and donation cost, multiplied by 100, rounded half up to two decimal places, and exactly 0 when the denominator is 0. It is recomputed on every shrink verification, every shrink dispute, every withdrawal, every donation completion and every nightly operations run — and it is the value clause 3 of §2.8 compares against `shrink_budget_pct`.

**The nightly operations run** is the department's automated close, available to an administrator or the department's manager, and its five steps execute in this pinned order:

1. Every lot whose `sell_by_at` the logical clock has reached while the lot still holds units has `past_date_flag` set true.
2. Every `FRESH` or `MARKED_DOWN` lot whose days remaining has reached a strictly deeper ladder rung than the lot currently holds is marked down automatically, using the calendar (`LADDER_DAYS`) reading — one markdown label is cut per lot and each affected lot's `version` is incremented.
3. Every shrink event in `VERIFIED` whose `verified_at` is at least 24 hours behind the logical clock moves to `POSTED`.
4. Every pickup of this department's store whose `logistics_status` is `SCHEDULED` or `CONFIRMED` and whose `scheduled_window_end` the logical clock has passed moves to `MISSED`, its `ASSIGNED` lines become `REJECTED`, and each affected lot unwinds out of `DONATION_PENDING` under the rules of §3.7.
5. The department's aggregates are recomputed: every touched lot's `expected_sell_through_pct`, then `markdown_liability_cents`, then `shrink_cost_ratio_pct`, then `compliance_status`.

The run increments the department's `sweep_epoch` by exactly one and reports back the `department_id`, the new `sweep_epoch`, the counts `lots_flagged_past_date`, `lots_auto_marked_down`, `shrink_events_posted` and `pickups_missed`, and the department's resulting `markdown_liability_cents`, `shrink_cost_ratio_pct` and `compliance_status`.

Finally, a test-driving capability available to every role sets the server's logical clock to a supplied `current_utc` instant and echoes that instant back as `current_utc`. It recomputes nothing by itself: every derived field is refreshed by the next business call or the next operations run that touches the resource.
