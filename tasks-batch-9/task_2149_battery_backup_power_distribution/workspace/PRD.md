# Battery Backup Distribution API — Product Requirements Document

## 1. Introduction

Interstate-class battery distribution is not a catalog business. A distributor who moves flooded lead-acid, AGM, gel, nickel-cadmium and lithium-iron-phosphate product simultaneously is running four businesses at once: a stocking business whose goods lose value on the shelf every day they sit uncharged, a regulated-freight business where the wrong carrier on the wrong package is a federal matter, a reverse-logistics business where the scrap lead coming back is worth real money and must be reconciled against a promise made months earlier, and a service business where a UPS string has to be sized correctly before anybody signs a coverage agreement. Today these four run on spreadsheets that disagree with one another. The battery is sold as sellable when the lot is three months past its refresh point; the shipment is tendered to a carrier that will not accept the class; the customer is credited for cores that were never returned; the manifest is filed by the same officer who wrote it.

This document specifies the Battery Backup Distribution API, the single system of record that will replace those spreadsheets. It is mounted under `/distribution`. Every capability described here — receiving a lot, pricing an order, contesting a core inspection, filing a disposal manifest — is a request against that mount, and every capability writes to one ledger whose invariants the platform is responsible for holding: units reserved must equal units committed, lead mass on a manifest must equal lead mass recovered, and an account's open receivable must equal the sum of what its live orders owe.

Two design commitments run through everything that follows. First, **the server owns time.** No shelf-life, cooldown, pickup-window or warranty computation may consult the host's wall clock; all of them read a logical clock that an administrator sets explicitly, so that a storm scenario spanning ninety days can be exercised deterministically. Second, **the server owns money and mass.** Clients never submit a price, a surcharge, a credit, a lead weight or a state; they submit facts, and the platform derives every monetary and physical quantity from those facts using the rules in this document. A value a client supplies for a derived field is ignored, not honoured.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Headers and Role-Based Access Control

Every request to the API — without exception, including reads — must carry two headers. `X-User-ID` identifies the caller and `X-User-Role` declares the capacity in which the caller is acting. If either header is absent or present but empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The same code and status are returned when `X-User-Role` carries a value that is not one of the six roles the platform recognises, which are, spelled exactly: `PlatformAdmin`, `SalesRep`, `WarehouseOperator`, `HazmatCertifier`, `ComplianceOfficer` and `Customer`. A syntactically valid role that is simply not permitted on the requested endpoint is a different failure: that is `ERR_FORBIDDEN_ROLE` (HTTP 403). Section 4 lists the authorised roles for every endpoint.

`PlatformAdmin` is the distributor's operations administrator. It owns the catalog, the sites, the carriers, the accounts and the logical clock, and it is the only role that may register an account, add or discontinue a catalog model, register a warehouse or a carrier, or move the clock. `SalesRep` is inside sales: it opens and prices orders, files and settles warranty claims, opens service contracts, and issues core credits; attaching a service contract to an order is its alone. `WarehouseOperator` is the site operator: it receives and maintains lots, allocates orders, packs, dispatches and delivers shipments, and inspects returned cores. `HazmatCertifier` is the dangerous-goods certifier and the only role that may approve or reject a hazmat tender. `ComplianceOfficer` owns storm declarations and lead-disposal manifests end to end. `Customer` is the buying account acting on its own behalf.

Identity semantics differ between the operator roles and the buying role, and the distinction is load-bearing. When `X-User-Role` is `PlatformAdmin`, `SalesRep`, `WarehouseOperator`, `HazmatCertifier` or `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server records it where a workflow demands an audit stamp — as `packed_by_user_id` and `certified_by_user_id` on a shipment, and as `created_by_user_id` and `filed_by_user_id` on a disposal manifest — but it never compares it to any entity's `id`. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Account`; ownership checks on any resource that references an `Account` compare that resource's account foreign key to `X-User-ID`. Concretely, a `Customer` may act on an order only when `Order.account_id` equals `X-User-ID`, on a core return only when `CoreReturn.account_id` equals `X-User-ID`, on a warranty claim only when `WarrantyClaim.account_id` equals `X-User-ID`, on a service contract only when `ServiceContract.account_id` equals `X-User-ID`, and on a creation request only when the `account_id` in the body equals `X-User-ID`. A `Customer` reaching outside its own account is rejected with `ERR_ACCOUNT_SCOPE_VIOLATION` (HTTP 403); this scoping applies to every endpoint whose authorised-role list includes `Customer`, reads included.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.


### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may be no smaller than 1 and no larger than 100. `offset` controls the starting position within the result set: it defaults to 0 and may be no smaller than 0. A value outside those bounds, or one that is not an integer, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Results on every list endpoint are ordered by `created_at` ascending, oldest row first, before the offset and limit are applied. The `meta` block of a list response carries `limit` and `offset` echoing the values in effect, `total_count` giving the number of rows matching the filters before pagination, and `has_more` set true when rows remain beyond the current page. Filters named on individual list endpoints in Section 4 are combined conjunctively — a request naming both a foreign key and a status filter returns only rows matching both.

### 2.4. Record Identity, Audit Stamps and the Logical Clock

Every resource the platform stores carries an `id`, which is a server-minted UUID with no type prefix; clients never supply one. Every resource also carries `created_at` and `updated_at`, both ISO 8601 UTC timestamps rendered with three fractional digits, and a `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row. All thirteen resource types in this system — accounts, catalog models, warehouses, carriers, inventory lots, orders, order lines, shipments, core returns, warranty claims, service contracts, storm events and disposal manifests — carry the full set: `id`, `created_at`, `updated_at` and `version`. There is no resource in this system that omits `updated_at` or `version`.

`created_at` and `updated_at` are stamped from the platform's **logical clock**, not from host wall-clock time. Before the clock is ever set, it reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. A `PlatformAdmin` moves it by posting a `to_iso8601` instant to the clock endpoint, which replies with the resulting `current_utc`. Every temporal rule in this document — shelf-life ageing, state-of-charge decay, the refresh cooldown, pickup-window admission, dispatch-window admission, the core-return window, warranty settlement dating and every audit stamp — reads that clock and nothing else. Moving the clock has an immediate consequence for stock: every inventory lot re-derives its state of charge and its condition posture the next time it is read or written.

### 2.5. Optimistic Concurrency on Parent Rows

Three write operations in this system modify a parent row that a client must have observed before acting, and all three are guarded by optimistic concurrency control against that parent's `version`.

Packing a shipment — a `POST /distribution/shipments` request — must carry `expected_order_version` as a required, non-optional body field holding the client's last observed `version` of the target `Order`. If it does not equal the order's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412). An order may legitimately carry more than one shipment row over its life, because a refused tender is re-packed onto a different carrier; a second pack against a freshly re-read order version therefore succeeds, and only a stale view of the order is refused. A successful pack increments the order's `version` by 1.

Attaching a service contract to an order — a `POST /distribution/service-contracts/{serviceContractId}/attach` request — must likewise carry `expected_order_version` as a required body field matching the target `Order`'s current `version`, and a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412). Attachment legitimately supersedes any contract the order already carries, so an attach against a freshly observed version succeeds; a stale view means the attaching client never saw the fee it is about to replace. A successful attach increments the order's `version` by 1.

Attaching a credited core return to a disposal manifest — a `POST /distribution/disposal-manifests/{disposalManifestId}/attach-core-return` request — must carry `expected_disposal_manifest_version` as a required body field matching that manifest's current `version`, and a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412). A manifest legitimately accumulates many core returns, so each attach against a freshly observed version succeeds; a stale view means the client's reading of the manifest's accumulated lead mass is behind and its regulatory-cap arithmetic cannot be trusted. A successful attach increments the manifest's `version` by 1.

No other endpoint in this system takes a version field. Requests to endpoints outside these three neither require nor accept `expected_order_version` or `expected_disposal_manifest_version`.

### 2.6. The Rejection Ladder

When a request would fail several checks at once, the platform does not choose arbitrarily among them. Checks are evaluated in a fixed order and the **first** one that fails decides the response; no later check can mask an earlier one, and no earlier check is skipped because a later one looks more specific. The ladder, from first evaluated to last, is:

1. Both authentication headers present and non-empty, otherwise `ERR_UNAUTHENTICATED`.
2. `X-User-Role` naming one of the six declared roles, otherwise `ERR_UNAUTHENTICATED`.
3. The role appearing in the endpoint's authorised-role list, otherwise `ERR_FORBIDDEN_ROLE`.
4. Every id embedded in the request path resolving to a stored row, checked left to right, otherwise the corresponding not-found code.
5. The request body being well formed — every required field present, every value of its declared type, every enum value a declared member — otherwise `ERR_INVALID_REQUEST`.
6. Every foreign key supplied in the request body resolving to a stored row, otherwise the corresponding not-found code.
7. Account scoping for `Customer` callers, otherwise `ERR_ACCOUNT_SCOPE_VIOLATION`.
8. Separation of duties on certification and on manifest filing, otherwise `ERR_SEGREGATION_OF_DUTIES`.
9. The supplied parent-version field matching the parent row's current `version`, otherwise `ERR_STALE_VERSION`.
10. The target row — and every other row the requested transition names in its preconditions, such as the manifest behind a scrap, the order behind a contract attachment, or the storm event behind an allocation — standing in a state this document declares acceptable for that transition, otherwise `ERR_INVALID_STATE`.
11. Account-status, line-count, dispute-round and refresh-cycle gates, in that relative order.
12. Hazmat safety gates: warehouse endorsement, then carrier class acceptance, then the air-mode prohibition, then the lithium watt-hour ceiling.
13. Referential business gates: model discontinuation, then account matching, then storm-region matching, then order-delivered.
14. Fiscal gates: the credit limit, then the storm priority score, then the storm pool.
15. Temporal gates: the core-return window, then the refresh cooldown, then the carrier window conflict, then the dispatch window, then shelf-expired stock.
16. Remaining constraint gates: refresh-required stock, insufficient sellable stock, the core-count promise, lot reservation, dock capacity, manifest emptiness, the manifest lead cap, sizing eligibility, uniqueness of catalog and site and carrier codes, uniqueness of a claim serial number, an already-open shipment, and finally a previously rejected carrier.

Two consequences of this ordering are worth stating explicitly because they are easy to get backwards. Because path-id resolution (rung 4) precedes body validation (rung 5), a request with both a bad path id and a malformed body returns the not-found code, not `ERR_INVALID_REQUEST`. Because parent-version checking (rung 9) precedes every state check (rung 10 onwards), a shipment packed against a stale order version returns `ERR_STALE_VERSION` even when the order is also in the wrong fulfilment state.

### 2.7. Money, Mass and Rounding

Every monetary quantity in this system is an integer number of cents. There are no fractional cents anywhere in storage or in any response; wherever a formula produces a fractional cent, the result is rounded **half up** to a whole cent. Half-up means that a value whose fractional part is exactly one half rounds away from zero, so 1244.5 cents becomes 1245.

Physical and proportional quantities carry fixed precision. Lead mass in kilograms — recovered lead on a core return, and the three lead totals on a disposal manifest — carries 3 decimal places, rounded half up. Shipment weight in kilograms carries 3 decimal places, rounded half up. A lot's state of charge carries 1 decimal place, rounded half up. A watt-hour rating carries 2 decimal places, rounded half up. A line discount carries 4 decimal places, rounded half up. The intermediate electrical quantities of a service-contract sizing — direct-current load in amps, the Peukert-adjusted amp-hour requirement, and usable amp-hours per unit — each carry 3 decimal places, rounded half up.

Where a formula rounds more than once, the order matters and is pinned in the workflow narrative that owns the formula. The two most consequential cases: order line totals are rounded to whole cents on each line *before* the lines are summed into an order subtotal, never summed unrounded and rounded once at the end; and a service-contract monthly fee applies both of its multipliers to the unrounded product and rounds exactly once, at the very end, before the tier floor is applied.

### 2.8. Separation of Duties

Two operations in this system may not be performed by the person who set them up. A shipment's hazmat certification must be performed by an `X-User-ID` different from the `packed_by_user_id` recorded when the shipment was packed. A disposal manifest's filing must be performed by an `X-User-ID` different from the `created_by_user_id` recorded when the manifest was opened. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Both checks sit above every state and business check in the rejection ladder, so a certifier who packed the shipment is told about the conflict of interest even when the shipment is also in the wrong status.

### 2.9. Derived Fields and Cascade Discipline

A substantial fraction of the fields in this system are derived rather than supplied. Some are derived once and frozen — an order line's unit price is a snapshot of the catalog price taken at submission and never revisited. Some are derived once per event — a shipment's package count is fixed when the shipment row is created. And some are re-derived continuously — a lot's state of charge and condition posture are recomputed from the logical clock on *every* read and *every* write of that lot, so a read alone can legitimately show a different posture than the previous read without any write having occurred. A manifest's counts and lead totals are likewise re-derived on every read.

When an operation mutates more than one row, every affected row's `updated_at` is refreshed and its `version` increments by 1. Cascades in this system are transitive: an operation that changes an order's total also changes the buying account's open receivable, and an operation that changes an account's status also changes the credit posture of that account's other live orders. The full cascades are described where the workflows that trigger them are described. What is universal is the discipline: a cascade runs to completion within the triggering request, synchronously, and the response reflects the finished state. There is no deferred or eventual settlement anywhere in this system.

### 2.10. Path Resolution and Referential Integrity

Nested paths are resolved left to right, and each segment must resolve before the next is examined. On a request naming both an order and a nested collection, an unknown order yields `ERR_ORDER_NOT_FOUND` before anything else about the request is considered. Each resource type has its own not-found code — `ERR_ACCOUNT_NOT_FOUND`, `ERR_BATTERY_MODEL_NOT_FOUND`, `ERR_WAREHOUSE_NOT_FOUND`, `ERR_CARRIER_NOT_FOUND`, `ERR_INVENTORY_LOT_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_ORDER_LINE_NOT_FOUND`, `ERR_SHIPMENT_NOT_FOUND`, `ERR_CORE_RETURN_NOT_FOUND`, `ERR_WARRANTY_CLAIM_NOT_FOUND`, `ERR_SERVICE_CONTRACT_NOT_FOUND`, `ERR_STORM_EVENT_NOT_FOUND` and `ERR_DISPOSAL_MANIFEST_NOT_FOUND` — all returning HTTP 404.

The same codes serve foreign keys carried in a request body, but they are evaluated one rung lower on the ladder, after body well-formedness. The body foreign keys that are resolved this way are those on order creation, order line creation, lot receiving, lot scrapping, shipment packing, core-return creation, warranty-claim creation, warranty-claim settlement, service-contract creation, service-contract attachment, manifest creation, manifest core-return attachment, and model discontinuation.

## 3. Business Logic & Workflows

### 3.1. The Catalog, the Sites, the Carriers and the Buying Accounts

Before a single unit moves, an administrator populates four reference collections. Registering a dealer or fleet account captures its legal `name`, its commercial `account_tier` — one of `PLATINUM`, `GOLD` or `STANDARD` — the two-letter `state_code` of its ship-to region, which must be exactly two uppercase letters, and its `credit_limit_cents`, the largest open receivable it may carry, which may not be negative and defaults to 0. An account may optionally declare a `storm_priority_rank`, its contractual storm-callout rank, where 1 is the highest priority and 9 the lowest; when the caller omits it the account is ranked 9, and any supplied value outside the inclusive range 1 through 9 is a malformed request. A new account opens with `status` set to `ACTIVE` — the only other posture is `CREDIT_HOLD`, and only `ACTIVE` permits order submission — and with all four of its ledger fields at zero: `open_receivable_cents`, `core_deposit_balance_cents`, `warranty_credit_cents` and `lifetime_lead_recovered_kg`, the last of which is a cumulative lead mass carried to three decimals.

A catalog entry — a battery model — is where the physics lives. Its `sku` must be unique across every model row regardless of that row's `status`, and a collision is refused with `ERR_DUPLICATE_SKU` (HTTP 409); the same code guards the uniqueness of a warehouse `code` and of a carrier `code` within their own collections. The body carries the cell `chemistry`, one of `FLOODED_LEAD_ACID`, `AGM`, `GEL`, `LITHIUM_IRON_PHOSPHATE` or `NICKEL_CADMIUM`; the `nominal_voltage` of one unit in volts and its `amp_hour_capacity` at the twenty-hour rate, both strictly positive; the `peukert_exponent` governing high-rate behaviour, which must be at least 1.0 and at most 1.5; the `unit_weight_kg` shipping weight of one unit, strictly positive; the `lead_content_kg` recoverable lead mass per unit, which is zero for lithium chemistries and may not be negative; the `core_deposit_cents` charged per unit shipped without an immediate core exchange, which may not be negative; the `list_price_cents` undiscounted per-unit price, strictly positive; the warranty bands, `warranty_free_replacement_months` which may not be negative and `warranty_prorata_months` which must be at least 1; the `shelf_life_days` maximum age before a lot is forced out of service, at least 1; and the `self_discharge_pct_per_month`, the percentage points of charge lost per stored month, strictly positive.

Three model fields are derived at creation and any value a client supplies for them is ignored. The `watt_hour_rating` is the nominal voltage multiplied by the amp-hour capacity, rounded half up to two decimal places. From that rating, the chemistry and the unit weight, the platform derives the shipping classification `hazmat_class_code`, whose value is one of `NON_REGULATED`, `UN2800_EXCEPTED`, `UN2795`, `UN2800`, `UN2794`, `UN3480_SECTION_II` or `UN3480_SECTION_IA`. The classification rules are exhaustive and mutually exclusive: a flooded lead-acid model is always `UN2794`; a nickel-cadmium model is always `UN2795`; an AGM or gel model is `UN2800_EXCEPTED` when its unit weight is at most 30.0 kilograms and `UN2800` when it is heavier, so a unit weighing exactly 30.0 kilograms is excepted; and a lithium-iron-phosphate model is `NON_REGULATED` when its watt-hour rating is at most 20.0 watt-hours, `UN3480_SECTION_II` when the rating is greater than 20.0 but at most 100.0 watt-hours, so a cell rated at exactly 100.0 watt-hours is Section II, and `UN3480_SECTION_IA` above that. `NON_REGULATED` is reachable only through the lithium branch; every other chemistry always lands on one of the six regulated codes. The third derived field, `hazmat_severity_rank`, is the ordinal of that class on a fixed severity scale where `NON_REGULATED` ranks 0, `UN2800_EXCEPTED` ranks 1, `UN2795` ranks 2, `UN2800` ranks 3, `UN2794` ranks 4, `UN3480_SECTION_II` ranks 5 and `UN3480_SECTION_IA` ranks 6.

A model opens with `status` set to `ACTIVE` and `replacement_model_id` null. Retiring a model — an administrator-only action that flips its `status` to `DISCONTINUED` — takes a `replacement_model_id` in the body naming the successor model, and writes that pointer onto the retired row. The pointer is self-referential: it names another catalog model, and the catalog listing accepts `replacement_model_id` as a filter so callers can walk the supersession edge in reverse and find every model pointing at a given successor. That listing also filters on `chemistry` and on `status`. Once a model is `DISCONTINUED`, a new order line naming it is refused with `ERR_MODEL_DISCONTINUED` (HTTP 422); a warranty settlement against it, however, falls through to the successor rather than failing.

Registering a distribution site captures its short `code`, its two-letter `state_code`, a boolean `hazmat_endorsement` that defaults to false and records whether the site holds a hazmat packaging endorsement, a `storm_reserve_pct` between 0.0 and 0.5 inclusive that defaults to 0.0 and expresses the fraction of each lot carved out for storm work while a storm is live in the site's state, and a `dock_capacity_kg_per_window` weight ceiling, strictly positive, that limits how much tonnage the site may tender across mutually overlapping pickup windows. Registering a carrier captures its `code` and display `name`, an explicit `accepts_hazmat_classes` list enumerating exactly which classification codes that carrier will tender, a `max_lithium_watt_hours_per_package` ceiling that may not be negative, and a `ground_only` boolean that defaults to true; a carrier with `ground_only` false moves freight by air, which as Section 3.5 explains prohibits the most severe lithium class outright.

### 3.2. Receiving Stock: Ageing, State of Charge and Refresh Charging

Stock enters the system one lot at a time. Receiving a lot names the `battery_model_id` stocked, the `warehouse_id` holding it, the `manufactured_on` manufacturing date as an ISO 8601 calendar date in `YYYY-MM-DD` form, and the `quantity_on_hand` physical unit count, which may not be negative. The lot's `quantity_reserved` opens at 0 and its posture is derived immediately against the logical clock. Lots may be listed and filtered by `battery_model_id`, by `warehouse_id`, by `scrap_manifest_id` and by `condition_state`.

A lot's charge decays on the shelf. The **state of charge** is computed from a storage baseline: the calendar date of `last_refresh_charged_at` when that stamp is set, and the `manufactured_on` date otherwise. Refresh charging is therefore the reset event — once a lot has been refresh-charged, its manufacturing date no longer participates in the charge calculation at all, though it continues to drive shelf life. The number of whole storage months elapsed is the number of whole days from that baseline date to the logical clock's current date, divided by 30 and rounded down to a whole number. The model's `self_discharge_pct_per_month` is multiplied by that whole month count, the product is subtracted from 100.0, the result is floored at 0.0 so `state_of_charge_pct` is never negative, and the value is rounded half up to one decimal place.

From that charge figure, the lot's age and its disposal pointer, the platform derives `condition_state`, whose value is one of `SELLABLE`, `REFRESH_REQUIRED`, `SHELF_EXPIRED` or `SCRAPPED`. The derivation is a ladder evaluated top to bottom, first match wins, and it runs on every read and every write of the lot. First: if `scrap_manifest_id` is non-null the lot is `SCRAPPED`, whatever else is true of it. Second: if the number of whole days from `manufactured_on` to the clock's current date is strictly greater than the model's `shelf_life_days`, the lot is `SHELF_EXPIRED` — the comparison is strict, so a lot whose age in days exactly equals its shelf life is still in service. Third: if the lot has already absorbed 3 refresh charges and its state of charge is below 75.0 percent, the lot is `SHELF_EXPIRED`; three cycles is the lifetime maximum. Fourth: if its state of charge is below 75.0 percent, the lot is `REFRESH_REQUIRED`. Otherwise the lot is `SELLABLE`. Both comparisons against the refresh threshold are strict, so a lot sitting at exactly 75.0 percent is `SELLABLE`, not `REFRESH_REQUIRED`. Alongside `condition_state`, every read re-derives `quantity_available`, which is the units on hand less the units reserved, reduced further by the storm carve-out described in Section 3.4 when the caller's purpose is ordinary non-storm allocation.

A site operator tops a lot back up by applying a refresh charge, supplying the `measured_open_circuit_voltage` the operator read at the terminals; that reading is stored as `last_measured_open_circuit_voltage`. The action is admissible from `SELLABLE` and from `REFRESH_REQUIRED`, and the `SELLABLE` self-edge is deliberate: topping up an already-sellable lot is legitimate preventive maintenance. It sets `last_refresh_charged_at` to the current logical clock instant, increments `refresh_charge_count` by 1, and resets the storage baseline so that `state_of_charge_pct` re-derives to exactly 100.0 and the lot lands on `SELLABLE`. Two gates bound the action. A lot that has already absorbed 3 refresh charges is refused with `ERR_REFRESH_CYCLES_EXHAUSTED` (HTTP 409), and once that ceiling is reached a lot whose charge subsequently falls below 75.0 percent goes straight to `SHELF_EXPIRED` rather than back to `REFRESH_REQUIRED`. And a lot that was refresh-charged recently is refused with `ERR_REFRESH_COOLDOWN_ACTIVE` (HTTP 409): the cooldown runs 72 hours — three full days — from `last_refresh_charged_at`, and the interval is **closed at both ends**, so a request whose clock instant lands exactly on the upper bound is inside the cooldown and is rejected. Only a clock instant strictly beyond that upper bound is admitted. A lot that has never been refresh-charged has no cooldown to clear.

A dead lot is written off onto a disposal manifest. Scrapping supplies the `disposal_manifest_id` of the target manifest and is available to a site operator and to a compliance officer alike. It is admissible only from `SHELF_EXPIRED` and from `REFRESH_REQUIRED`, and refused with `ERR_INVALID_STATE` (HTTP 409) from any other posture. Two further gates apply: the lot's `quantity_reserved` must be exactly 0, since units already committed to a customer cannot be destroyed, and a reserved lot is refused with `ERR_LOT_RESERVED` (HTTP 409); and the target manifest must itself be in `DRAFT`. A successful scrap writes `scrap_manifest_id` onto the lot, which forces its `condition_state` to `SCRAPPED`, increments that manifest's `scrapped_lot_count` by 1, and re-derives the manifest's `lot_lead_kg` and `total_lead_kg`. The write-off is reversible in exactly one way: if the manifest is later sent back to draft, the lot's `scrap_manifest_id` is cleared and its condition re-derives out of `SCRAPPED` from age and charge alone — in practice back to `SHELF_EXPIRED` or `REFRESH_REQUIRED`, whichever the ladder now selects.

### 3.3. Building and Pricing an Order

An order begins life as a draft. Opening one names the buying `account_id`, the `warehouse_id` whose lots may satisfy it, and a `requested_ship_date` as an ISO 8601 calendar date. It may optionally name a `storm_event_id`; a non-null value marks the order as an emergency draw against that event's pool and changes how it is allocated, as Section 3.4 describes. A new order opens with `fulfillment_status` at `DRAFT` and `credit_status` at `PENDING`, and every money field at zero. Both status fields are independent dimensions on the same row and they advance on different triggers; the full enumerations are `DRAFT`, `SUBMITTED`, `ALLOCATED`, `SHIPPED`, `DELIVERED` and `CANCELLED` for fulfilment, and `PENDING`, `CLEARED`, `HELD` and `CLOSED` for credit. Orders may be listed and filtered by `account_id`, by `warehouse_id`, by `storm_event_id`, by `fulfillment_status` and by `credit_status`, and the two status filters may be combined.

Lines are added to a draft one at a time, each naming a `battery_model_id` and a `quantity` of at least 1. A line may also declare `core_expected_count`, the number of units for which the buyer promises to hand back a core; it defaults to 0, may not be negative, and may not exceed the line's `quantity`. Each successful line increments the order's `line_count`; the order's money fields remain zero until submission. A line naming a model whose `status` is `DISCONTINUED` is refused with `ERR_MODEL_DISCONTINUED`. Lines are individually readable and may be listed and filtered by `order_id`, by `battery_model_id` and by `allocated_lot_id`.

Submitting a draft is where the order is priced and committed, and it is the single busiest operation in the system. Four gates guard it, and because the rejection ladder is strict they are reported in this relative order: the order must stand in `DRAFT`, and any other fulfilment status is `ERR_INVALID_STATE`; the buying account's `status` must be `ACTIVE`, and an account sitting in `CREDIT_HOLD` yields `ERR_ACCOUNT_NOT_ACTIVE` (HTTP 409); the order must carry at least one line, and an empty order yields `ERR_ORDER_HAS_NO_LINES` (HTTP 422); and the priced order must fit inside the account's credit headroom. That last check is evaluated against the freshly computed total: the order's `total_cents` plus the account's `open_receivable_cents` minus the account's `warranty_credit_cents` must be no greater than the account's `credit_limit_cents`, and a breach is refused with `ERR_CREDIT_LIMIT_EXCEEDED` (HTTP 402). Accumulated warranty credit therefore functions as headroom, not as cash. Every model named on the order's lines must also still be `ACTIVE` at submission time.

Pricing runs line by line, in order of each line's `created_at` ascending. For each line the platform snapshots the model's current `list_price_cents` into the line's `unit_price_cents` — this snapshot is permanent and later catalog price changes never disturb it. It then computes two discount components. The tier component comes from the buying account's `account_tier`: 12 percent for `PLATINUM`, 7 percent for `GOLD` and nothing at all for `STANDARD`. The volume component comes from the line's own quantity: 5 percent at 100 units or more, 3 percent at 25 units or more but fewer than 100, 1 percent at 10 units or more but fewer than 25, and nothing below 10. The two components are added together, the sum is capped at 15 percent — no combination of tier and volume may ever discount a line further — and the capped figure is rounded half up to four decimal places and stored as `discount_pct`. The line's `line_total_cents` is then the snapshot unit price multiplied by the line quantity multiplied by one minus that discount, **rounded half up to a whole cent on this line**. Only after every line has been rounded individually are the rounded line totals summed into the order's `subtotal_cents`. Summing the unrounded products and rounding once at the end is explicitly not the rule and yields a different subtotal.

With the subtotal in hand, the order total is assembled in a pinned sequence of steps, and the sequence matters because it looks circular if read casually. Step one is the subtotal just computed. Step two decides `hazmat_fee_waived`, and it is keyed on `subtotal_cents` **alone**: the flag is true when the subtotal is at least 5000000 cents — that is, fifty thousand dollars of product before any fee — and false otherwise. That decision is made exactly once, at submission, and is never re-decided when the hazmat fee or the service-contract fee changes later, even though those fees are part of the order total. Step three sets `hazmat_fee_cents` to zero when the waiver applies and otherwise to the forecast hazmat surcharge described below. Step four computes `core_deposit_charge_cents` as the sum, over every line, of the line's quantity less its promised core count, multiplied by that line's model `core_deposit_cents` — the buyer is charged a deposit only for the units it did not promise to exchange. Step five sets `total_cents` to the subtotal plus the core deposit charge plus the hazmat fee plus `service_contract_fee_cents`, which is zero until a service contract attaches.

The **forecast** hazmat surcharge is a whole-order estimate made before any physical packing exists. Its class is the order's forecast classification, which is the class whose severity rank equals the highest severity rank among the models on the order's lines, taken without quantity weighting. Its weight is the sum, over every line at that line's full quantity, of quantity multiplied by the model's `unit_weight_kg`, rounded half up to three decimal places. The weight component of the fee is 275 cents for every started 10 kilograms — the weight in kilograms divided by 10.0 and rounded **up** to a whole number, multiplied by 275. The class component is the base fee for the order's class, and the base fees are 0 cents for `NON_REGULATED`, 1500 cents for `UN2800_EXCEPTED`, 4200 cents for `UN2795`, 5500 cents for `UN2800`, 7800 cents for `UN2794`, 6400 cents for `UN3480_SECTION_II` and 12500 cents for `UN3480_SECTION_IA`. In the forecast the class base fee is charged exactly once, because the forecast assumes the whole order tenders as a single hazmat package. The two components are added, and if the order's warehouse holds a hazmat endorsement the sum is multiplied by 0.85 — a fifteen percent endorsed-site discount — and rounded half up to whole cents; an unendorsed site pays the sum unreduced.

A successful submission advances `fulfillment_status` from `DRAFT` to `SUBMITTED` and, on the independent credit dimension, advances `credit_status` from `PENDING` to `CLEARED`. It then books the money: the account's `open_receivable_cents` increases by the order's `total_cents`. Nothing else moves — no stock is reserved and no storm pool is drawn at submission.

Cancellation is available from `DRAFT`, from `SUBMITTED` and from `ALLOCATED`, to a sales representative, an administrator or the buying customer, and it always records a free-text `cancellation_reason`. What it unwinds depends on how far the order had travelled, and in all three cases it drives `credit_status` to `CLOSED`. From `DRAFT`, nothing had been booked and nothing is reversed. From `SUBMITTED`, the account's `open_receivable_cents` is reduced by the order's `total_cents`, and any service contract attached to that order standing in `ATTACHED` or `ACTIVE` moves to `CANCELLED`. From `ALLOCATED`, the receivable is reversed the same way; in addition, for every line carrying a non-null `allocated_lot_id` the platform decrements that lot's `quantity_reserved` by the line's `allocated_quantity` and then clears `allocated_lot_id` and resets `allocated_quantity` to 0; if the order draws on a storm event, that event's `allocated_units` is reduced by the sum of the order's line quantities and its `remaining_pool_units` re-derived; any shipment on the order standing in `PACKED` or `CERTIFIED` moves to `VOIDED`, releasing both its carrier window and its dock-capacity contribution; and any attached or active service contract moves to `CANCELLED`. When a voided shipment's `hazmat_surcharge_cents` was the value currently sitting in the order's `hazmat_fee_cents`, the order total is re-derived before the receivable reversal is computed, so the account is credited back exactly what it was charged. An order that has reached `SHIPPED` or `DELIVERED` can no longer be cancelled, and neither can one already `CANCELLED`.

### 3.4. Storm Declarations and the Allocation Contest

A compliance officer or an administrator declares a storm by naming it, giving its `region_state_code` as a two-letter code, choosing its `severity_tier` from `WATCH`, `WARNING` and `EMERGENCY`, and setting the `allocation_pool_units` reserved for it, which must be at least 1. The declaration opens with `status` at `DECLARED`, `allocated_units` at 0, `remaining_pool_units` equal to the whole pool, and `min_priority_score` fixed from the severity tier: a `WATCH` sets no floor at all with a minimum of 0, a `WARNING` sets a minimum of 45, and an `EMERGENCY` sets a minimum of 70.

A declaration has an immediate physical effect on stock, and it has that effect from the moment it is declared rather than from the moment it is opened for draws. Whenever at least one storm event stands in `DECLARED` or in `ALLOCATING` whose region matches a warehouse's own `state_code`, every lot at that warehouse carves out the number of units equal to its `quantity_on_hand` multiplied by the site's `storm_reserve_pct` and rounded **down** to a whole unit. Ordinary non-storm allocation may draw only on the units on hand less those already reserved less that carve-out; a storm order draws on the units on hand less those already reserved, ignoring the carve-out entirely — that is precisely what the carve-out is for. Opening the pool for draws moves the event from `DECLARED` to `ALLOCATING`, and only then may a storm order be allocated; an attempt to allocate a storm order against an event still in `DECLARED` is refused with `ERR_INVALID_STATE`. Closing the event, which is permitted from `DECLARED` and from `ALLOCATING` alike, moves it to `CLOSED`, releases the regional carve-out so that available quantity rises again for ordinary work, and refuses any further draw against that event with `ERR_INVALID_STATE`; draws already made are untouched.

Allocation itself is a site operator's or an administrator's action against a `SUBMITTED` order whose `credit_status` is `CLEARED`. An order sitting in `HELD` cannot be allocated until its credit posture returns to `CLEARED`. For a storm order the platform first computes `allocation_priority_score`, which for a non-storm order is simply 0. The storm score is the sum of four components. Tier points come from the account: 40 for `PLATINUM`, 28 for `GOLD` and 12 for `STANDARD`. Rank points reward a low `storm_priority_rank`: subtract the rank from 6, floor the difference at 0, and multiply by 5 — so rank 1 earns 25 points, rank 5 earns 5, and ranks 6 through 9 earn nothing. Severity points come from the event: 5 for a `WATCH`, 12 for a `WARNING` and 20 for an `EMERGENCY`. Value points reward order size: divide the order's frozen `subtotal_cents` by 100000 — that is, count whole thousand-dollar increments — round down, and cap the result at 15. The four are added into a whole-number score.

Three storm gates then apply, and their relative order is fixed. First, the buying account's `state_code` must equal the event's `region_state_code`, and a mismatch is refused with `ERR_STORM_REGION_MISMATCH` (HTTP 422). Second, the computed score must be at least the event's `min_priority_score`; the comparison is inclusive, so a score exactly equal to the minimum passes, and a score below it is refused with `ERR_STORM_PRIORITY_TOO_LOW` (HTTP 403). Third, the sum of the order's line quantities must be no greater than the event's `remaining_pool_units`, and a shortfall is refused with `ERR_STORM_POOL_EXHAUSTED` (HTTP 422).

Stock selection then runs once per line, taking the lines in `created_at` ascending order. A lot is a candidate for a line only when all four of these hold: the lot's `battery_model_id` matches the line's model; the lot's `warehouse_id` matches the order's warehouse; the lot's `condition_state` is exactly `SELLABLE`; and the lot's effective availability — units on hand less units reserved, less the storm carve-out for a non-storm order and without that deduction for a storm order — is at least the line's whole `quantity`. A line is satisfied from a single lot and is never split across lots. Among the candidates, the winner is the lot with the earliest `manufactured_on` date, which is strict first-in-first-out on age; ties on that date are broken by the earlier `created_at`.

When no candidate qualifies, the platform inspects the lots that match the line's model and the order's warehouse and whose units on hand less units reserved would have covered the line, and it reports the most informative reason in this exact order: if any such lot stands in `SHELF_EXPIRED`, the request fails with `ERR_LOT_SHELF_EXPIRED` (HTTP 422); otherwise if any such lot stands in `REFRESH_REQUIRED`, it fails with `ERR_LOT_REFRESH_REQUIRED` (HTTP 422); otherwise it fails with `ERR_INSUFFICIENT_SELLABLE_STOCK` (HTTP 422). Lots already scrapped never enter either the candidate set or this fallback inspection.

A successful allocation writes `allocation_priority_score` onto the order, advances `fulfillment_status` from `SUBMITTED` to `ALLOCATED`, and for each line writes the chosen lot into `allocated_lot_id`, sets `allocated_quantity` equal to the line's `quantity`, and increments that lot's `quantity_reserved` by the same amount, with `quantity_available` re-derived. Note carefully that `quantity_on_hand` does **not** move at allocation; the units are still physically in the building and only a reservation has been placed. For a storm order, the event's `allocated_units` increases by the sum of the order's line quantities and its `remaining_pool_units` is re-derived.

### 3.5. Packing, Certifying, Tendering and Delivering

Physical fulfilment begins when a site operator packs an allocated order onto a carrier. The pack request names the `order_id` being tendered, the `carrier_id` tendering it, and the dock pickup window as `pickup_window_start` and `pickup_window_end`, both ISO 8601 UTC instants, with the end strictly later than the start. It must also carry `expected_order_version`, as Section 2.5 requires. The order must stand in `ALLOCATED`. The operator's `X-User-ID` is recorded as `packed_by_user_id`, and the order's `version` increments by 1.

Packing derives four values from the order's lines. The shipment's `hazmat_class_code` is the class whose severity rank equals the highest severity rank among the models on the order's lines, computed over every line regardless of its allocated quantity and without quantity weighting — the same rule the order's forecast used, so the two normally agree. The `total_weight_kg` is the sum over the lines of quantity multiplied by the model's unit weight, rounded half up to three decimals; `total_lead_kg` is the same sum against each model's `lead_content_kg`, likewise to three decimals. The `package_count` is the total weight divided by 30.0 kilograms and rounded **up** to a whole number: thirty kilograms is the maximum weight of a single hazmat package.

Six checks guard the pack, and because the ladder is strict they are reported in this relative order. First, the shipment's class must appear in the carrier's `accepts_hazmat_classes`; a class the carrier does not tender is refused with `ERR_CARRIER_HAZMAT_REFUSED` (HTTP 422). Second, a shipment classified `UN3480_SECTION_IA` may only go to a carrier whose `ground_only` is true, because that class may not move by air; an air carrier is refused with `ERR_AIR_MODE_PROHIBITED` (HTTP 422). Third, for every line whose model chemistry is `LITHIUM_IRON_PHOSPHATE`, that model's `watt_hour_rating` must be no greater than the carrier's `max_lithium_watt_hours_per_package`, and a breach is refused with `ERR_LITHIUM_WH_LIMIT_EXCEEDED` (HTTP 422). Fourth, the proposed pickup window must not collide with another window already booked on the same carrier. Fifth, the site's dock must be able to absorb the weight. Sixth, the order must not already carry a live shipment: if any other shipment for the same order stands in `PACKED`, `CERTIFIED`, `DISPATCHED` or `DELIVERED`, the request is refused with `ERR_SHIPMENT_ALREADY_OPEN` (HTTP 409).

The two window checks use deliberately different interval semantics, and confusing them is the single easiest mistake to make here. The **carrier** conflict check treats windows as half-open, spanning from the start instant inclusive up to but excluding the end instant: two windows collide only when they genuinely overlap, so a window that begins at the exact instant another ends does not collide and is accepted. A genuine overlap against any other shipment on the same carrier standing in `PACKED`, `CERTIFIED` or `DISPATCHED` is refused with `ERR_CARRIER_WINDOW_CONFLICT` (HTTP 409). The **dock capacity** check treats windows as closed at both ends, so windows that merely touch at an endpoint *do* aggregate: the new shipment's `total_weight_kg` is added to the total weight of every other shipment at the same warehouse standing in `PACKED`, `CERTIFIED` or `DISPATCHED` whose window shares any instant with the new one, endpoints included, and the sum must be no greater than the site's `dock_capacity_kg_per_window`. Exceeding it is refused with `ERR_DOCK_CAPACITY_EXCEEDED` (HTTP 422). One pair of touching windows on one carrier at one site can therefore pass the carrier check and fail the dock check, and that is intended.

Certification is the dangerous-goods fork, and only a `HazmatCertifier` may perform it, on a shipment standing in `PACKED`, and never the operator who packed it. The request carries a `certification_decision` of either `APPROVE` or `REJECT`, and may carry a free-text `rejection_reason`. Whichever way it goes, the certifier's `X-User-ID` is written to `certified_by_user_id`. The two branches then diverge completely.

An `APPROVE` decision first requires that, when the shipment's class is anything other than `NON_REGULATED`, the order's warehouse holds a hazmat endorsement; an unendorsed site is refused with `ERR_WAREHOUSE_NOT_HAZMAT_ENDORSED` (HTTP 422). The shipment moves `PACKED → CERTIFIED` and the platform recomputes the surcharge against the **actual** package count. The actual computation reads the same order lines, the same weight and the same warehouse as the forecast did, and differs in exactly one respect: the class base fee is charged once per package rather than once per shipment, so the base fee for the shipment's class is multiplied by `package_count` before the per-10-kilogram weight component is added, and the endorsed-site discount of 0.85 is applied to the sum in the same way with the same half-up rounding to whole cents. For identical order contents the actual figure is therefore strictly larger than the forecast whenever the shipment weighs more than 30.0 kilograms. The result is written to the shipment's `hazmat_surcharge_cents`. It then cascades: unless the order's `hazmat_fee_waived` is true, the order's `hazmat_fee_cents` is replaced by the shipment's surcharge and `total_cents` is re-derived; and because the order total changed, the buying account's `open_receivable_cents` is adjusted by the difference between the new order total and the previous one. A waived order absorbs none of this — its hazmat fee stays at zero, its total is untouched, and no receivable moves.

A `REJECT` decision moves the shipment `PACKED → HAZMAT_REJECTED` and records the `rejection_reason`. It sets the order's `hazmat_hold` to true and appends the shipment's `carrier_id` to the order's `rejected_carrier_ids`, and it releases both the shipment's carrier window and its dock-capacity contribution so the freight can be re-packed onto a different carrier. It touches none of the money: the order's `hazmat_fee_cents`, the order's `total_cents` and the account's `open_receivable_cents` are all left exactly as they were.

Tendering a certified shipment is a site operator's action. Two gates apply beyond the requirement that the shipment stand in `CERTIFIED`: the shipment's carrier must not appear in the order's `rejected_carrier_ids`, and a blacklisted carrier is refused with `ERR_CARRIER_PREVIOUSLY_REJECTED` (HTTP 409); and the logical clock must lie inside the pickup window read as **half-open** — at or after `pickup_window_start` and strictly before `pickup_window_end` — with anything outside refused as `ERR_DISPATCH_WINDOW_NOT_OPEN` (HTTP 409). A successful tender writes `dispatched_at` from the clock, moves the shipment `CERTIFIED → DISPATCHED`, and drives the order's `fulfillment_status` from `ALLOCATED` to `SHIPPED`. That order transition moves no money at all; it simply increments the order's `version` by 1. Shipments may be listed and filtered by `order_id`, by `carrier_id` and by `status`, whose full enumeration is `PACKED`, `CERTIFIED`, `HAZMAT_REJECTED`, `DISPATCHED`, `DELIVERED` and `VOIDED`.

Confirming delivery on a `DISPATCHED` shipment is the heaviest single operation in the system, because it drives a five-hop cascade that runs to completion inside the request. **Hop one** writes the shipment's `delivered_at` from the logical clock and moves it `DISPATCHED → DELIVERED`. **Hop two** drives the order's `fulfillment_status` from `SHIPPED` to `DELIVERED`, and that transition carries four effects of its own: the order's `credit_status` moves from `CLEARED` to `CLOSED`; every line is stamped with a `core_due_by` equal to the calendar date of the delivery instant plus 45 days, the window inside which promised cores must come back; every line's allocated lot has **both** its `quantity_reserved` and its `quantity_on_hand` decremented by that line's `allocated_quantity`, because the units have now physically left the building; and any service contract attached to that order standing in `ATTACHED` moves to `ACTIVE`, at which point coverage begins. **Hop three** books the core liability: the account's `core_deposit_balance_cents` increases by the sum over the order's lines of `core_expected_count` multiplied by that line's model `core_deposit_cents`. **Hop four** reacts to that increase: if the account's core-deposit liability now stands at or above 500000 cents — five thousand dollars of outstanding core obligation — and the account's `status` is `ACTIVE`, the account moves to `CREDIT_HOLD`. **Hop five** reacts to that status change: every order belonging to that account whose `fulfillment_status` is `SUBMITTED` or `ALLOCATED` and whose `credit_status` is `CLEARED` moves its `credit_status` to `HELD`, which blocks those orders from being allocated until the hold is lifted. Orders that have already reached `SHIPPED` or `DELIVERED` are not touched, and neither are orders whose credit dimension has already closed.

### 3.6. Core Exchange, Lead Assay and the Credit Release

Every lead-acid unit shipped without an immediate exchange carries a deposit, and the buyer gets that deposit back by shipping the spent core to the distributor. Declaring a return names the returning `account_id`, the `order_id` of the delivered order the cores came from, the `battery_model_id` — one model per return, never a mixture — and the `declared_core_count` the account claims to be sending, which must be at least 1. A sales representative or the customer itself may open one.

Four gates guard the declaration and, again, they are reported in this relative order. The named account must be the same account that owns the source order, and a mismatch is refused with `ERR_ACCOUNT_MISMATCH` (HTTP 422). The source order's `fulfillment_status` must be `DELIVERED`, since cores cannot come back from goods that never went out, and anything else is refused with `ERR_ORDER_NOT_DELIVERED` (HTTP 422). The return must arrive inside the grace period: the current logical-clock date must be no later than the earliest `core_due_by` among the source order's lines for this model, plus 30 grace days; a later arrival is refused with `ERR_CORE_RETURN_WINDOW_CLOSED` (HTTP 422). This check is skipped entirely when no matching line carries a `core_due_by` at all. And the declared count must not outrun the promise: it may be no greater than the sum of `core_expected_count` across the source order's lines for this model, minus the declared counts already committed by that order's other returns for the same model standing in `SUBMITTED`, `INSPECTED`, `DISPUTED` or `CREDITED`; over-claiming is refused with `ERR_CORE_COUNT_EXCEEDS_PROMISE` (HTTP 422). Note that a return already `REJECTED` releases its claim back to the pool.

Two values are computed at declaration. The `late_return` flag is true when the calendar date on which the return was created is strictly after the earliest non-null `core_due_by` among the source order's lines for this model — so a return arriving on the due date itself is not late, and lateness is possible without the window being closed, because the window allows 30 further days of grace. And the **provisional** credit is booked: `provisional_credit_cents` is simply the declared core count multiplied by the model's `core_deposit_cents`. This provisional figure values every declared core at the flat deposit, ignores lead assay and lateness entirely, is written once and is never overwritten. It is an expectation, not a payment. The return opens with `status` at `SUBMITTED` and `inspection_round` at 0. Returns may be listed and filtered by `account_id`, by `order_id`, by `battery_model_id`, by `disposal_manifest_id` and by `status`, whose full enumeration is `SUBMITTED`, `INSPECTED`, `DISPUTED`, `REJECTED` and `CREDITED`.

A site operator inspects what actually arrived, supplying `accepted_core_count`. Inspection is admissible from `SUBMITTED` and from `DISPUTED` alike, which is what makes the cycle work, and the accepted count may not exceed the declared count — a larger value is a malformed request refused with `ERR_INVALID_REQUEST`. Every inspection increments `inspection_round` by 1. The count then forks the outcome. An accepted count of at least 1 moves the return to `INSPECTED` and runs the lead assay: `lead_recovered_kg` is the accepted count multiplied by the model's `lead_content_kg` multiplied by a recovery yield of 0.965 — the smelter returns 96.5 percent of the lead in the case — rounded half up to three decimals; and `scrap_value_cents` is that already-rounded lead mass multiplied by 196 cents per kilogram, rounded half up to whole cents. An accepted count of exactly 0 moves the return to `REJECTED` instead, and zeroes the assay outright: `lead_recovered_kg` becomes 0.0, `scrap_value_cents` becomes 0 and `final_credit_cents` becomes 0, with no movement whatsoever on the account ledger. A re-inspection after a dispute overwrites `accepted_core_count`, `lead_recovered_kg` and `scrap_value_cents` with the new round's values; only the latest round survives.

The customer or its representative may contest an inspection, supplying a free-text `dispute_reason`. A dispute is admissible only from `INSPECTED` and only while `inspection_round` is still below 3; once three rounds have been completed the return is settled as inspected and a further dispute is refused with `ERR_DISPUTE_ROUNDS_EXHAUSTED` (HTTP 409). A successful dispute moves the return `INSPECTED → DISPUTED`, and the next inspection carries it back to `INSPECTED` — or to `REJECTED` if nothing is accepted that round — incrementing the round counter again. `INSPECTED → DISPUTED → INSPECTED` is a genuine cycle, bounded only by that round ceiling.

Issuing the credit is a sales representative's or an administrator's action on a return standing in `INSPECTED`, and it drives a four-hop cascade. **Hop one** computes the **assayed final** credit, which differs from the provisional figure in three ways: it values only the cores actually accepted rather than those declared, it takes the greater of two valuations rather than the deposit alone, and it penalises lateness. Concretely, the deposit valuation is the accepted core count multiplied by the model's `core_deposit_cents`; the gross credit is whichever is larger, that deposit valuation or the `scrap_value_cents` from the last inspection; the penalty is 25 percent of the gross, rounded half up to whole cents, when `late_return` is true and zero otherwise; and `final_credit_cents` is the gross less the penalty. The final figure can therefore land above the provisional one, when recovered lead is worth more than the deposits, and below it, when cores were rejected or the return came back late. It is the final figure, never the provisional one, that moves money. **Hop two** applies it: the account's `core_deposit_balance_cents` is reduced by `final_credit_cents`, floored at 0 so the liability never goes negative, and the account's `lifetime_lead_recovered_kg` increases by the return's `lead_recovered_kg`. **Hop three** reacts to the reduced liability: if the account's core-deposit balance now stands below 500000 cents and the account's `status` is `CREDIT_HOLD`, the account returns to `ACTIVE`. **Hop four** reacts to that release: every order belonging to that account whose `credit_status` is `HELD` moves back to `CLEARED`, and allocation becomes possible again for those orders. This four-hop release is the exact mirror of the five-hop delivery cascade that imposed the hold.

### 3.7. Warranty Adjudication and Settlement

A warranty claim is filed against a single installed unit. It names the claiming `account_id`, the failed `battery_model_id`, the unit's `serial_number`, the `installed_on` installation date and the `failed_on` failure date, both ISO 8601 calendar dates, with the failure date no earlier than the installation date. A serial number may be claimed only once across the whole system; a repeat is refused with `ERR_DUPLICATE_SERIAL_NUMBER` (HTTP 409). A new claim opens with `status` at `SUBMITTED`, and its `months_in_service` and `credit_cents` stay at 0 until it is adjudicated. Claims may be listed and filtered by `account_id`, by `battery_model_id`, by `replacement_order_id` and by `status`, whose full enumeration is `SUBMITTED`, `APPROVED_FREE`, `APPROVED_PRORATA`, `DENIED` and `SETTLED`.

Adjudication computes the service age and forks three ways on it. The `months_in_service` is a whole anniversary-month count: take the difference in calendar years between the failure date and the installation date and multiply it by twelve, add the difference in calendar month numbers, and then subtract one if the failure date's day of month is earlier than the installation date's day of month — so a unit installed on the 15th and failing on the 14th thirteen months later has served twelve months, not thirteen. The three bands are then decided against the model's own warranty terms, and each writes `months_in_service`, a `coverage_band` and a `credit_cents`.

When the service age is **at most** the model's `warranty_free_replacement_months`, the claim moves `SUBMITTED → APPROVED_FREE`, `coverage_band` becomes `FREE` and `credit_cents` becomes the model's full `list_price_cents` with no pro-ration at all. The comparison is inclusive, so a claim landing exactly on the free-band anniversary month is a full replacement. When the service age is strictly greater than the free band but strictly less than the free band plus the model's `warranty_prorata_months`, the claim moves `SUBMITTED → APPROVED_PRORATA`, `coverage_band` becomes `PRORATA`, and the credit is pro-rated: count the whole months remaining in the pro-rata band as the free band plus the pro-rata band minus the service age, multiply the model's `list_price_cents` by that remaining count, divide by the `warranty_prorata_months` alone — the denominator is the pro-rata band's own length, **not** the sum of the two bands — and round half up to whole cents. At exactly one month past the free band this pays strictly less than a free replacement for the same list price; a single month of service separates the two bands. When the service age reaches or exceeds the free band plus the pro-rata band, the claim moves `SUBMITTED → DENIED`, `coverage_band` becomes `EXPIRED` and `credit_cents` becomes 0.

Settlement is available on a claim standing in `APPROVED_FREE` or in `APPROVED_PRORATA` — never on one already denied — and the caller chooses a `settlement_mode` of either `ACCOUNT_CREDIT` or `REPLACEMENT_ORDER`. The two branches are disjoint and both move the claim to `SETTLED`. Choosing `ACCOUNT_CREDIT` adds the claim's `credit_cents` to the account's `warranty_credit_cents`, where it becomes credit-limit headroom on the next order submission, and leaves `replacement_order_id` null. Choosing `REPLACEMENT_ORDER` requires a `replacement_warehouse_id` in the body naming a real warehouse; the platform synthesizes a fresh `DRAFT` order for the claiming account at that warehouse with a `requested_ship_date` equal to the current logical-clock date, attaches to it exactly one line of `quantity` 1 with `core_expected_count` 1, and writes the new order's id into the claim's `replacement_order_id`. The model on that line is the claimed model itself when that model's `status` is still `ACTIVE`, and otherwise the successor named by the claimed model's `replacement_model_id` — which is exactly why discontinuation records a successor. The replacement branch does **not** touch the account's `warranty_credit_cents`; a claimant is paid once, either in credit or in goods.

### 3.8. UPS Service Contracts: Runtime Sizing and Attachment

A backup-power service contract is sold against a sizing, not against a part number. Opening one names the covered `account_id`, the `coverage_tier` chosen from `BRONZE`, `SILVER` and `GOLD`, and the five engineering inputs: the `load_watts` the string must carry, strictly positive; the `required_runtime_minutes` it must sustain at that load, at least 1; the `system_voltage` of the direct-current bus, strictly positive; the design `ambient_temp_c` in Celsius, which may be negative; and `allowed_chemistries`, an explicit non-empty list of the chemistries the customer will accept, drawn from the same five-member enumeration the catalog uses. An empty list is a malformed request. A new contract opens with `status` at `DRAFT` and every sized field at zero or null. Contracts may be listed and filtered by `account_id`, by `order_id`, by `sized_battery_model_id` and by `status`, whose full enumeration is `DRAFT`, `SIZED`, `ATTACHED`, `ACTIVE`, `SUPERSEDED` and `CANCELLED`.

Sizing a draft contract is a sales representative's or an administrator's action, and it is the most involved calculation in the system. Three quantities are established before any candidate is considered. The `dc_load_amps` is the AC load divided by the product of the bus voltage and an inverter efficiency of 0.90, rounded half up to three decimals. The runtime in hours is the required runtime in minutes divided by 60, and it is *not* rounded — it enters the Peukert exponentiation at full precision. The `temp_derate_factor` is selected from the design ambient by a descending ladder: 1.00 at 25.0 degrees Celsius or warmer, 0.95 at 15.0 degrees or warmer but below 25.0, 0.87 at 5.0 degrees or warmer but below 15.0, and 0.75 below 5.0 degrees.

A catalog model is a candidate only when all three of these hold: the model's `status` is `ACTIVE`; the model's `chemistry` is a member of the contract's `allowed_chemistries`; and the model's `nominal_voltage` is no greater than the contract's `system_voltage`. When no model qualifies, the request is refused with `ERR_NO_ELIGIBLE_BATTERY_MODEL` (HTTP 422) and nothing is written. For every candidate the platform computes four figures. The Peukert-adjusted requirement is the direct-current load in amps multiplied by the runtime in hours raised to the power of that model's `peukert_exponent`, rounded half up to three decimals. The usable capacity of one unit is the model's `amp_hour_capacity` multiplied by the depth-of-discharge limit for its chemistry — 0.50 for `FLOODED_LEAD_ACID`, 0.60 for `AGM`, 0.60 for `GEL`, 0.90 for `LITHIUM_IRON_PHOSPHATE` and 0.70 for `NICKEL_CADMIUM` — multiplied by the temperature derate factor, rounded half up to three decimals. The units wired in series inside one string is the bus voltage divided by the model's nominal voltage, rounded **up** to a whole number. The number of parallel strings is the Peukert-adjusted requirement divided by the usable capacity of one unit, again rounded **up** to a whole number; both ceilings are taken on the already-rounded three-decimal values. The model's total unit count is the string count multiplied by the units per string.

Candidates are ranked by total unit count ascending; ties are broken by the total unit count multiplied by the model's `list_price_cents` ascending, which prefers the cheaper of two equally compact designs; and any remaining tie is broken by the earlier `created_at`, compared at millisecond precision. The winner's figures are written onto the contract as `sized_battery_model_id`, `required_peukert_ah`, `sized_string_count`, `sized_units_per_string` and `sized_unit_count`, along with the `dc_load_amps` and `temp_derate_factor` computed earlier, and the `covered_value_cents` equal to the sized unit count multiplied by the winner's list price.

Pricing the coverage follows immediately. The raw monthly figure is the covered value multiplied by the coverage rate for the tier — 0.0075 for `BRONZE`, 0.0125 for `SILVER` and 0.0200 for `GOLD` — multiplied by a chemistry service multiplier reflecting how much attention that chemistry needs in the field: 1.30 for `FLOODED_LEAD_ACID`, 1.10 for `AGM`, 1.15 for `GEL`, 0.90 for `LITHIUM_IRON_PHOSPHATE` and 1.25 for `NICKEL_CADMIUM`. Both multipliers are applied to the unrounded product and the result is rounded half up to whole cents exactly once, at the very end. The `monthly_fee_cents` is then whichever is larger, that rounded figure or the tier floor — 2500 cents for `BRONZE`, 4900 cents for `SILVER` and 9900 cents for `GOLD`. The `prepay_total_cents` is the monthly fee multiplied by 12, a full year prepaid, and that is the amount that will be booked onto an order. Sizing moves the contract `DRAFT → SIZED`.

Attachment is the sales representative's exclusive action and binds a sized contract to one of the account's open orders. The request names the `order_id` and carries `expected_order_version`. Three preconditions apply beyond the version check: the contract must stand in `SIZED`; the order's `account_id` must equal the contract's `account_id`, with a mismatch refused as `ERR_ACCOUNT_MISMATCH`; and the order's `fulfillment_status` must be `SUBMITTED` or `ALLOCATED`, so a contract cannot be hung on a draft, a shipped order or a cancelled one. On success the platform writes the contract's `order_id` and stamps `attached_at` from the logical clock, and moves the contract `SIZED → ATTACHED`. Any other contract already sitting on that same order in `ATTACHED` or `ACTIVE` moves to `SUPERSEDED`; the order's `service_contract_fee_cents` is **set to** the new contract's `prepay_total_cents`, replacing rather than adding to the superseded contract's contribution, so an order never carries two coverage fees at once. The order's `total_cents` is then re-derived — re-running only the final assembly step, reusing the waiver decision made at submission verbatim and leaving `hazmat_fee_cents` untouched — and the account's `open_receivable_cents` is adjusted by the difference between the new order total and the previous one. The order's `version` increments by 1.

The rest of a contract's life is driven by the order it rides on. When that order reaches `DELIVERED`, an `ATTACHED` contract moves to `ACTIVE` and coverage begins, with no ledger movement. When that order is cancelled, a contract standing in `ATTACHED` or `ACTIVE` moves to `CANCELLED` and coverage ends. And a contract standing in `ATTACHED` or `ACTIVE` moves to `SUPERSEDED` when another contract attaches to the same order, at which point its fee contribution has already been taken over by the newcomer.

### 3.9. Lead Disposal Manifests and Regulatory Filing

Recovered lead has to be accounted for to the regulator, and the manifest is the accounting instrument. A compliance officer opens one by naming the generator `warehouse_id`, the `epa_id` printed on the paperwork and the `reporting_period` label such as a quarter designation. The opening officer's `X-User-ID` is recorded as `created_by_user_id`, every count and lead total starts at zero, and the manifest opens with `status` at `DRAFT`. Manifests may be listed and filtered by `warehouse_id` and by `status`, whose full enumeration is `DRAFT`, `SUBMITTED` and `FILED`.

A manifest accumulates mass from two independent sources. Scrapped lots arrive as described in Section 3.2. Credited core returns arrive by explicit attachment: the compliance officer supplies the `core_return_id` together with `expected_disposal_manifest_version`. Both rows must be in the right state — the manifest in `DRAFT` and the core return in `CREDITED` — and either standing anywhere else is refused with `ERR_INVALID_STATE`. A successful attachment writes the manifest's id into that return's `disposal_manifest_id` and increments the manifest's `version` by 1.

The manifest's five aggregate fields are re-derived from scratch whenever a core return is attached or detached, whenever a lot is scrapped onto it or released from it, and on every read. The `core_lead_kg` is the sum of `lead_recovered_kg` over the core returns pointing at this manifest whose `status` is `CREDITED`, rounded half up to three decimals. The `lot_lead_kg` is the sum, over the inventory lots whose `scrap_manifest_id` is this manifest, of each lot's `quantity_on_hand` multiplied by its model's `lead_content_kg`, likewise rounded half up to three decimals. The `total_lead_kg` is the sum of those two already-rounded figures, rounded half up to three decimals again. The `attached_core_return_count` and `scrapped_lot_count` are the counts of those same two row sets. There is no time window on any of these sums and no ordering dependence, so the totals are stable whatever order the attachments happened in.

One regulatory ceiling governs a manifest: its `total_lead_kg` may never exceed 1000.000 kilograms. That ceiling is enforced at three separate moments — when a core return is attached, when a lot is scrapped onto it, and when the manifest is submitted — and a breach at any of them is refused with `ERR_MANIFEST_LEAD_LIMIT_EXCEEDED` (HTTP 422).

Submitting freezes a `DRAFT` manifest for regulatory review and moves it `DRAFT → SUBMITTED`. It requires substance: the sum of `attached_core_return_count` and `scrapped_lot_count` must be at least 1, and an empty manifest is refused with `ERR_MANIFEST_EMPTY` (HTTP 422). Once submitted, the manifest's attachments are frozen and any further attach or scrap against it is refused with `ERR_INVALID_STATE`.

A submitted manifest then goes one of two ways. Filing it with the regulator moves it `SUBMITTED → FILED`, writes `filed_by_user_id` and `filed_at`, and renders the manifest immutable — `FILED` is terminal. The filer must not be the officer who opened it, as Section 2.8 requires. Rejecting it instead moves it `SUBMITTED → DRAFT`, records a free-text `rejection_reason`, and performs a full compensating unwind: every core return whose `disposal_manifest_id` is this manifest has that pointer cleared to null; every inventory lot whose `scrap_manifest_id` is this manifest has that pointer cleared to null, so each of those lots re-derives its `condition_state` out of `SCRAPPED` and back to whatever its age and charge now dictate; and the manifest's `attached_core_return_count`, `scrapped_lot_count`, `core_lead_kg`, `lot_lead_kg` and `total_lead_kg` are all reset to zero. Rejection is what restores the lead-mass invariant when a manifest was assembled wrongly, and it is available to a compliance officer and to an administrator alike. A rejected manifest is a working draft again and may re-accumulate attachments from scratch.
