# Presort Bureau Operations API — Product Requirements Document

## 1. Introduction

A presort mail service provider — a **bureau** — sits between commercial mailers and the postal network. Mailers tender raw address files and physical mail; the bureau cleans the addresses, standardizes them, applies move-update data, then combines mail from many unrelated mailers into a single pooled mailing so that the *combined* volume qualifies for a deeper presort discount than any individual mailer could reach alone. The pooled mail is sorted into trays and pallets, documented, declared on a postage statement, trucked to a postal entry point on a booked dock appointment, and verified by an acceptance clerk who may accept it clean, accept it with a postage surcharge, or return the whole mailing for correction. Each mailer is then billed for its pro-rata share of the postage plus the bureau's own service fee.

Today that workflow is run on spreadsheets, and the failure modes are all arithmetic. Postage is pinned at one moment and re-derived at another, so a batch's declared postage no longer matches the sum of the shares billed to its members. A mailer's pieces are counted twice because two invoices cover overlapping billing periods. A dock appointment is double-booked because nobody summed the pallets already committed to overlapping windows. A statement is filed and accepted by the same operator, defeating the acceptance unit's whole purpose. This API replaces the spreadsheets with a single system of record in which every money figure has exactly one producer, exactly one rounding step, and exactly one moment at which it is frozen.

This document specifies that system in full: the resources it manages, the lifecycle each resource moves through, the pricing and allocation arithmetic, the order in which requests are validated, and the exact error each rejection carries. Every rule stated here is normative. Where a value is described as *frozen*, *pinned*, or *snapshotted*, it must never be re-derived from its source afterwards; where an evaluation order is given, that order is part of the contract because the result depends on it.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API — without exception, including the test-driving clock endpoint — must carry two headers:

- `X-User-ID` — the identifier of the acting principal.
- `X-User-Role` — the role the principal is acting in.

If either header is absent, empty, or consists only of whitespace, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A header containing only spaces or tabs counts as absent; it is not treated as a valid identifier. This check runs before anything else, including body parsing and path resolution.

Five roles exist, and their names are spelled exactly as follows: `ClientContact`, `PresortOperator`, `PostageManager`, `AcceptanceClerk`, and `BureauAdmin`. If `X-User-Role` holds any string outside that set of five, or holds one of the five but that role is not among the roles authorized for the endpoint being addressed, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). The authorized role list for each endpoint is given in §4.

**Role responsibilities.** A `ClientContact` is a mail owner acting on its own account: it tenders jobs and reads its own jobs, permit accounts, statements, invoices and service-level indices. It never touches sortation, verification or billing issuance. A `PresortOperator` runs the production floor — address hygiene and move update, pooling jobs into commingle batches, building trays and pallets, closing sortation, and booking and dispatching drop shipments. A `PostageManager` owns postage and money: opening and funding permit accounts, changing permit account status, and preparing, submitting, revising and voiding postage statements, plus issuing client invoices and recording payments. An `AcceptanceClerk` represents the postal acceptance unit: recording verification findings, closing verification with an accept or a return, receiving the deposit at the dock, and recording the delivery scan. A `BureauAdmin` administers the bureau: onboarding clients and entry facilities, suspending and reinstating clients, opening and closing facilities, cancelling work, and driving the logical clock. `BureauAdmin` does not run production, postage or acceptance actions.

**Identity semantics.** When `X-User-Role` is `ClientContact`, `X-User-ID` is the `id` of the acting `Client`; ownership checks on any resource that references a `Client` compare the resource's client foreign-key field to `X-User-ID`. Concretely, a `ClientContact` may read a client record, its permit-account list, its mail-job list, its invoice list and its service-level index only when the addressed client `id` equals `X-User-ID`; may read a mail job, that job's hygiene runs and that job's standalone postage estimate only when the job's `client_id` equals `X-User-ID`; and may tender a new mail job only when the `client_id` in the request body equals `X-User-ID`. Any violation is rejected with `ERR_CLIENT_SCOPE_VIOLATION` (HTTP 403).

When `X-User-Role` is `PresortOperator`, `PostageManager`, `AcceptanceClerk` or `BureauAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands an audit trail — as `prepared_by_user_id` and `submitted_by_user_id` on a `PostageStatement` written by a `PostageManager`, as `verified_by_user_id` on a `PostageStatement` and `assessed_by_user_id` on a `VerificationFinding` written by an `AcceptanceClerk` — but never compares it to any entity's `id`. The one comparison the server does make between two such opaque identifiers is the segregation-of-duties rule described in §2.10.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection endpoints are paginated through two query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be below 1, and may not exceed 100. `offset` controls the starting position: it defaults to 0 and may not be below 0. A `limit` or `offset` outside those bounds is a request-shape violation and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint's description in §4 states otherwise, every list is ordered by `created_at` ascending — oldest record first — and pagination is applied to that ordering. Two list endpoints have a natural domain ordering that coincides with insertion order and is described that way in §3: a job's hygiene runs are returned in `run_index` order, and a batch's containers are returned in `sequence_index` order. Because both ordinals are assigned in creation order, both orderings are identical to `created_at` ascending.

Every list response carries all four pagination fields inside `meta`: `limit` and `offset` echo the effective values actually applied, `total_count` is the number of records matching the request before the page window is applied, and `has_more` is true exactly when records remain beyond the current window. List responses set `response_type` to `"array"`; single-resource responses set it to `"object"`.

### 2.4. Resource Identity, Timestamps and Revision Counters

Every resource the API persists carries a server-minted `id`: a UUID string, with no type prefix and no embedded meaning. Clients never supply an `id`; a body that includes one is rejected as an unknown field. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, stamped once when the row is written and never modified.

Most resources additionally carry `updated_at` and `version`. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits refreshed on every mutation of that resource. `version` is an integer that starts at 1 when the resource is created and increases by exactly 1 on every mutation of that resource — including mutations the caller did not directly request, such as a batch's counters being refreshed because a member job was pooled into it, or a client's `lifetime_pieces_mailed` growing because one of its jobs reached `MAILED`. Wherever §3 says a version is incremented, that increment is by one, and `updated_at` is refreshed in the same operation.

Two resources are append-only records of history rather than mutable state, and they are deliberately leaner: `AddressHygieneRun` and `VerificationFinding` carry only `id` and `created_at`. Neither has an `updated_at` and neither has a `version`; those two fields are absent from their representations entirely. Every other resource — `Client`, `PermitAccount`, `MailJob`, `EntryFacility`, `CommingleBatch`, `BatchMember`, `SortContainer`, `DropShipment`, `PostageStatement`, `ServiceLevelRecord` and `ClientInvoice` — carries the full set of `id`, `created_at`, `updated_at` and `version`.

### 2.5. The Logical Clock

Time in this system is explicit and deterministic, never read from the host's wall clock. The server maintains a single **logical clock**: an instant that every time-dependent rule consults. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it must not fall back to real wall-clock time under any circumstance. A `BureauAdmin` may move the clock to an arbitrary instant by supplying a `to_iso8601` value; the response reports the new setting as `current_utc` together with a `no_show_shipment_ids` array described in §3.7.

The logical clock is what decides whether a permit account's annual mailing fee has lapsed, whether a dock appointment window is in the past, whether a deposit is happening inside its window, and what instant is stamped into `deposited_at_utc` and `mailed_at_utc`. Client-supplied instants — `annual_fee_paid_through_utc`, `window_start_utc`, `window_end_utc`, `period_start_utc`, `period_end_utc` and `scanned_at_utc` — are ISO 8601 UTC values with three fractional digits, and all instant comparisons are made at millisecond resolution. The `api_request_timestamp` in the response envelope is a real server timestamp and is unrelated to the logical clock.

### 2.6. Addressing Nested Resources

Several resources are addressed through a parent path — a client's permit accounts, invoices, mail jobs and service-level index; a job's hygiene runs, batch memberships, cancellation and postage estimate; a batch's members, containers, sortation, statements and drop shipments; a facility's status and drop shipments; a statement's findings, submission, verification, void and revision; a container's service-level records. Path identifiers are resolved strictly left to right, and the first one that does not resolve determines the error, so a request naming a nonexistent client and a nonexistent job under it reports the client first.

The mapping from an unresolvable identifier to its error is fixed: a `client_id` yields `ERR_CLIENT_NOT_FOUND`, a `permit_account_id` yields `ERR_PERMIT_ACCOUNT_NOT_FOUND`, a `mail_job_id` yields `ERR_MAIL_JOB_NOT_FOUND`, a `commingle_batch_id` yields `ERR_BATCH_NOT_FOUND`, a `batch_member_id` yields `ERR_BATCH_MEMBER_NOT_FOUND`, a `sort_container_id` yields `ERR_CONTAINER_NOT_FOUND`, an `entry_facility_id` yields `ERR_ENTRY_FACILITY_NOT_FOUND`, a `postage_statement_id` yields `ERR_STATEMENT_NOT_FOUND`, a `drop_shipment_id` yields `ERR_DROP_SHIPMENT_NOT_FOUND`, a `service_level_record_id` yields `ERR_SERVICE_LEVEL_RECORD_NOT_FOUND`, and a `client_invoice_id` yields `ERR_INVOICE_NOT_FOUND`. All of these are HTTP 404.

Resolving a nested identifier is not enough on its own: the child must actually belong to the parent named earlier in the path. Withdrawing a batch member is the case where this bites — if the `BatchMember` addressed by `batch_member_id` exists but its `commingle_batch_id` is some other batch than the `commingle_batch_id` in the path, the request is rejected with `ERR_BATCH_MEMBER_NOT_FOUND` rather than being allowed to operate across batch boundaries.

Foreign keys arriving in a request *body* are resolved after path identifiers, and among themselves they are resolved in the order the endpoint lists them: `client_id` first, then `permit_account_id`, then `entry_facility_id`, then `commingle_batch_id`, then `mail_job_id`. This body-level existence check applies when opening a permit account, tendering a mail job, opening a commingle batch, pooling a job into a batch, booking a drop shipment, and preparing a postage statement.

### 2.7. Money, Mills and Rounding Discipline

All money in this system is an integer number of **cents**. There are no fractional-cent balances, no decimal money fields, and no currency codes. Per-piece postage rates, however, are too fine-grained for cents, so they are carried in **mills** — thousandths of a cent — as the integer field `rate_mills_per_piece`. A rate of 29440 mills therefore means 29.44 cents per piece.

Two rounding modes are used, and which one applies is fixed per figure, never chosen at runtime. Per-piece rates are **floored** — truncated toward zero — because a rate is derived by chaining discount factors and the bureau never rounds a rate up in its own favour. Every other derived figure is **rounded half up**: a value exactly on the halfway mark rounds away from zero to the larger magnitude. Money figures round half up to whole cents. `share_basis_pct` rounds half up to four decimal places. `address_quality_pct`, `zone_weighted_index` and `piece_weighted_index` round half up to two decimal places. Day counts, piece counts, pallet counts and basis-point figures are integers and are not rounded at all.

The single most important arithmetic principle in this specification is that **each figure has exactly one rounding step, applied by exactly one producer.** Chained roundings are forbidden: a rate is floored once at the end of its whole expression and not after each intermediate factor; mills are converted to cents once over a whole batch and never per container or per member; a pool of cents is rounded to whole cents by its producer and then split by a remainder-distribution rule rather than by rounding each share. §3 states, for every calculation, exactly where its one rounding step sits.

Discounts and thresholds are expressed in **basis points** — hundredths of a percent — as integers. A `drop_ship_discount_bp` of 300 is a 3% reduction; a tier discount of 2200 basis points is a 22% reduction. Wherever a basis-point figure appears in a formula it is applied as the factor obtained by subtracting it from 10000 and dividing by 10000.

### 2.8. Optimistic Concurrency

Two write operations are guarded by optimistic concurrency control on a parent resource's `version`. In both cases the version field is a required, non-optional member of the request body, and a mismatch is a rejection rather than a merge. Every other endpoint in this API takes no version field at all; supplying one is an unknown field and is rejected with `ERR_INVALID_REQUEST`.

**Funding a permit account.** A `POST /permit-accounts/{id}/funding` request must carry `expected_permit_account_version` holding the client's last observed `version` of the target `PermitAccount`. If that value does not equal the account's current `version`, the deposit is rejected with `ERR_STALE_PERMIT_VERSION` (HTTP 412). Repeated deposits are perfectly legitimate on their own terms, so without this guard a caller whose view of `balance_cents` predates another writer's change would top the account up to the wrong figure and never learn of it; the version check turns that silent error into a deterministic stale-version rejection.

**Preparing a postage statement.** A `POST /postage-statements` request must carry `expected_batch_version` holding the client's last observed `version` of the target `CommingleBatch`. If that value does not equal the batch's current `version`, the creation is rejected with `ERR_STALE_BATCH_VERSION` (HTTP 412). Preparing a statement legitimately supersedes any prior `DRAFT` statement on the same batch, so without this guard a caller holding a stale view of the batch would void a statement that had been prepared from different piece counts; the version check makes that a stale-version rejection instead.

### 2.9. Rejection Precedence: the Validation Ladder

When a request violates more than one rule, the outcome must be predictable. The server therefore evaluates checks in one fixed, strictly ascending order and returns the error of the **first** rule violated; no later rule can mask an earlier one, and no earlier rule can be skipped because a later one also fails. The ladder below is normative and complete. Where a rung names specific endpoints, that rung applies to exactly those endpoints and no others.

1. **Headers present** — `X-User-Role` and `X-User-ID` are both present and non-empty, treating a whitespace-only header as absent. Violation: `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role recognized and permitted** — `X-User-Role` is one of the five declared roles and that role appears in the target endpoint's authorized role list. Violation: `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Request shape** — the body parses, contains every field the endpoint requires, every field holds the declared type, and every enumerated field holds a declared member. Unknown fields are rejected. Violation: `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
4. **Path identifiers resolve** — every identifier in the URL path resolves to an existing row, checked left to right, with the identifier-to-error mapping of §2.6. Applies to every endpoint that has a path identifier.
5. **Body foreign keys resolve** — every foreign key supplied in the body resolves to an existing row, checked in the order `client_id`, `permit_account_id`, `entry_facility_id`, `commingle_batch_id`, `mail_job_id`, again using the mapping of §2.6. Applies to `POST /permit-accounts`, `POST /mail-jobs`, `POST /commingle-batches`, `POST /commingle-batches/{id}/members`, `POST /drop-shipments` and `POST /postage-statements`.
6. **Nested child belongs to path parent** — the addressed `BatchMember`'s `commingle_batch_id` equals the `commingle_batch_id` in the path. Violation: `ERR_BATCH_MEMBER_NOT_FOUND` (404). Applies to `DELETE /commingle-batches/{id}/members/{batch_member_id}`.
7. **Client scope** — a `ClientContact` acts only within its own client, as described in §2.1. Violation: `ERR_CLIENT_SCOPE_VIOLATION` (403). Applies to `GET /clients/{id}`, `GET /clients/{id}/mail-jobs`, `GET /clients/{id}/permit-accounts`, `GET /clients/{id}/invoices`, `GET /clients/{id}/service-level`, `GET /mail-jobs/{id}`, `GET /mail-jobs/{id}/postage-estimate`, `GET /mail-jobs/{id}/hygiene-runs` and `POST /mail-jobs`.
8. **Permit belongs to the client** — the `PermitAccount` named by `permit_account_id` has a `client_id` equal to the request's `client_id`. Violation: `ERR_PERMIT_CLIENT_MISMATCH` (422). Applies to `POST /mail-jobs`.
9. **Segregation of duties** — the acting `X-User-ID` differs from the statement's `submitted_by_user_id`. Violation: `ERR_SEGREGATION_OF_DUTIES` (403). Applies to `POST /postage-statements/{id}/verify` and `POST /postage-statements/{id}/findings`.
10. **Mail job own-state** — the target `MailJob` is in a status the operation allows. On pooling, a job already in `POOLED` yields `ERR_JOB_ALREADY_POOLED` while any other status that is not `HYGIENE_CLEARED` yields `ERR_INVALID_JOB_STATE` (409). On a hygiene run the status must be `RECEIVED` or `HYGIENE_CLEARED`; on cancellation the status must be `RECEIVED` or `HYGIENE_CLEARED`. Applies to `POST /mail-jobs/{id}/hygiene-runs`, `POST /mail-jobs/{id}/cancel` and `POST /commingle-batches/{id}/members`.
11. **Job not already pooled** — the referenced `MailJob` does not already hold a `BatchMember`, that is, its status is not `POOLED`. Violation: `ERR_JOB_ALREADY_POOLED` (409). Applies to `POST /commingle-batches/{id}/members`.
12. **Batch own-state** — the target `CommingleBatch` is in a status the operation allows: `OPEN` for adding and removing members, adding a container and closing sortation; `SORTED` for statement preparation; `OPEN`, `SORTED` or `DOCUMENTED` for booking a drop shipment; `DOCUMENTED` for a deposit. Violation: `ERR_INVALID_BATCH_STATE` (409). Applies to `POST /commingle-batches/{id}/members`, `DELETE /commingle-batches/{id}/members/{batch_member_id}`, `POST /commingle-batches/{id}/containers`, `POST /commingle-batches/{id}/sort`, `POST /postage-statements`, `POST /drop-shipments` and `POST /drop-shipments/{id}/deposit`.
13. **Statement own-state** — the target `PostageStatement` is in a status the operation allows: `DRAFT` for submission and for voiding; `SUBMITTED` for recording findings, for verification and for voiding; `RETURNED_FOR_CORRECTION` for revision. Violation: `ERR_INVALID_STATEMENT_STATE` (409). Applies to `POST /postage-statements/{id}/submit`, `POST /postage-statements/{id}/findings`, `POST /postage-statements/{id}/verify`, `POST /postage-statements/{id}/void` and `POST /postage-statements/{id}/revise`.
14. **Shipment own-state** — the target `DropShipment` is in a status the operation allows: `SCHEDULED` for departure, `IN_TRANSIT` for deposit, `SCHEDULED` or `IN_TRANSIT` for cancellation. Violation: `ERR_INVALID_SHIPMENT_STATE` (409). Applies to `POST /drop-shipments/{id}/depart`, `POST /drop-shipments/{id}/deposit` and `POST /drop-shipments/{id}/cancel`.
15. **Invoice own-state** — the target `ClientInvoice` is in `ISSUED`; a `PAID` invoice cannot be paid again. Violation: `ERR_INVALID_INVOICE_STATE` (409). Applies to `POST /client-invoices/{id}/payment`.
16. **Permit account optimistic concurrency** — `expected_permit_account_version` equals the account's current `version`. Violation: `ERR_STALE_PERMIT_VERSION` (412). Applies to `POST /permit-accounts/{id}/funding`.
17. **Batch optimistic concurrency** — `expected_batch_version` equals the batch's current `version`. Violation: `ERR_STALE_BATCH_VERSION` (412). Applies to `POST /postage-statements`.
18. **Owning client active** — the `Client` that owns the target resource has status `ACTIVE`, checked through `MailJob.client_id` on job creation, on a hygiene run and on pooling, and against the path client identifier on invoice issuance. Violation: `ERR_CLIENT_SUSPENDED` (409). Applies to `POST /mail-jobs`, `POST /mail-jobs/{id}/hygiene-runs`, `POST /commingle-batches/{id}/members` and `POST /clients/{id}/invoices`.
19. **Funding permit active** — the `PermitAccount` funding the operation has status `ACTIVE`; both `HOLD` and `CLOSED` refuse. Reached through `MailJob.permit_account_id` on job creation, on a hygiene run and on pooling, and through `PostageStatement.permit_account_id` on submission. Violation: `ERR_PERMIT_ACCOUNT_NOT_ACTIVE` (409). Applies to `POST /mail-jobs`, `POST /mail-jobs/{id}/hygiene-runs`, `POST /commingle-batches/{id}/members`, `POST /postage-statements/{id}/submit` and `POST /permit-accounts/{id}/funding`.
20. **Entry facility open** — the `EntryFacility` being booked has status `OPEN`. Violation: `ERR_ENTRY_FACILITY_CLOSED` (409). Applies to `POST /drop-shipments`.
21. **Statement accepted before deposit** — the `CommingleBatch` of the shipment being deposited has a `PostageStatement` in `ACCEPTED_CLEAN` or `ACCEPTED_WITH_ADJUSTMENT`. Violation: `ERR_STATEMENT_NOT_ACCEPTED` (409). Applies to `POST /drop-shipments/{id}/deposit`.
22. **Annual permit fee current** — the `PermitAccount`'s `annual_fee_paid_through_utc` is at or after the current logical clock. Violation: `ERR_PERMIT_ANNUAL_FEE_LAPSED` (409). Applies to `POST /mail-jobs`, `POST /mail-jobs/{id}/hygiene-runs` and `POST /postage-statements/{id}/submit`.
23. **Move update currency** — the job's `move_update_compliant` is true. Violation: `ERR_MOVE_UPDATE_STALE` (422). Applies to `POST /commingle-batches/{id}/members`.
24. **Address hygiene floor** — the job's `address_quality_pct` is at least the minimum of 95.00 percent. Violation: `ERR_ADDRESS_QUALITY_BELOW_MINIMUM` (422). Applies to `POST /commingle-batches/{id}/members`.
25. **Mail class agreement** — the job's `mail_class` equals the batch's `mail_class`. Violation: `ERR_MAIL_CLASS_MISMATCH` (422). Applies to `POST /commingle-batches/{id}/members`.
26. **Processing category agreement** — the job's `processing_category` equals the batch's `processing_category`. Violation: `ERR_PROCESSING_CATEGORY_MISMATCH` (422). Applies to `POST /commingle-batches/{id}/members`.
27. **Commingling consent** — the job's `Client` has `commingle_opt_in` set to true. Violation: `ERR_COMMINGLE_OPT_OUT` (422). Applies to `POST /commingle-batches/{id}/members`.
28. **Client code uniqueness** — the supplied `client_code` is not already held by another `Client`. Violation: `ERR_DUPLICATE_CLIENT_CODE` (409). Applies to `POST /clients`.
29. **Permit number uniqueness** — the supplied `permit_number` is not already held by another `PermitAccount`. Violation: `ERR_DUPLICATE_PERMIT_NUMBER` (409). Applies to `POST /permit-accounts`.
30. **Facility code uniqueness** — the supplied `facility_code` is not already held by another `EntryFacility`. Violation: `ERR_DUPLICATE_FACILITY_CODE` (409). Applies to `POST /entry-facilities`.
31. **Piece, pallet and money arithmetic** — `declared_piece_count` is at least 1; a container's `piece_count` is at least 1; `pallet_count` is at least 1; a funding `amount_cents` is at least 1; a hygiene run's `submitted_piece_count` is at least 1 with `cass_matched_count` no greater than `submitted_piece_count`, `ncoa_move_updated_count` no greater than `submitted_piece_count`, and `undeliverable_removed_count` strictly less than `submitted_piece_count`; and a finding's `affected_piece_count` is at least 1 and no greater than the statement's frozen `statement_piece_count`. Violation: `ERR_INVALID_PIECE_COUNT` (400). Applies to `POST /mail-jobs`, `POST /mail-jobs/{id}/hygiene-runs`, `POST /commingle-batches/{id}/containers`, `POST /drop-shipments`, `POST /permit-accounts/{id}/funding` and `POST /postage-statements/{id}/findings`.
32. **Non-empty batch** — the batch has at least one `SortContainer` and at least one `BatchMember`, that is `container_count` is at least 1 and `member_job_count` is at least 1. Violation: `ERR_BATCH_HAS_NO_CONTAINERS` (422). Applies to `POST /commingle-batches/{id}/sort`.
33. **All containers qualify** — every `SortContainer` attached to the batch has `qualifies` true. Violation: `ERR_CONTAINER_NOT_QUALIFIED` (422). Applies to `POST /commingle-batches/{id}/sort`.
34. **Container piece reconciliation** — the sum of `piece_count` over the batch's containers equals the batch's `total_piece_count`. Violation: `ERR_CONTAINER_PIECE_MISMATCH` (422). Applies to `POST /commingle-batches/{id}/sort`.
35. **One live appointment per batch** — at most one `DropShipment` per `CommingleBatch` may be in `SCHEDULED` or `IN_TRANSIT`. Violation: `ERR_SHIPMENT_ALREADY_SCHEDULED` (409). Applies to `POST /drop-shipments`.
36. **Delivery scanned once** — a `ServiceLevelRecord` may be delivery-scanned only once; its `actual_delivery_days` must still be null. Violation: `ERR_DELIVERY_ALREADY_SCANNED` (409). Applies to `POST /service-level-records/{id}/delivery-scan`.
37. **Interval well-formedness** — `window_end_utc` is strictly after `window_start_utc`, and `period_end_utc` is strictly after `period_start_utc`. Violation: `ERR_INTERVAL_INVALID` (400). Applies to `POST /drop-shipments` and `POST /clients/{id}/invoices`.
38. **Appointment not in the past** — `window_start_utc` is at or after the current logical clock. Violation: `ERR_SHIPMENT_WINDOW_IN_PAST` (422). Applies to `POST /drop-shipments`.
39. **Dock aggregate capacity** — the pallets already committed over overlapping half-open windows plus the requested `pallet_count` do not exceed the facility's `dock_capacity_pallets_per_slot`, as specified in §3.7. Violation: `ERR_DOCK_CAPACITY_EXCEEDED` (409). Applies to `POST /drop-shipments`.
40. **Deposit inside the window** — the logical clock is at or after `window_start_utc` and at or before `window_end_utc`. Violation: `ERR_OUTSIDE_APPOINTMENT_WINDOW` (422). Applies to `POST /drop-shipments/{id}/deposit`.
41. **Billing period exclusivity** — the requested period neither touches nor overlaps any `ISSUED` or `PAID` invoice period of the same client, as specified in §3.8. Violation: `ERR_BILLING_PERIOD_OVERLAP` (409). Applies to `POST /clients/{id}/invoices`.
42. **Findings required to return** — a return outcome requires at least one recorded finding, that is `verification_error_count` is at least 1. Violation: `ERR_NO_VERIFICATION_FINDINGS` (422). Applies to `POST /postage-statements/{id}/verify`.
43. **At least one billable job** — the requested invoice period covers at least one billable job. Violation: `ERR_NO_BILLABLE_JOBS` (422). Applies to `POST /clients/{id}/invoices`.
44. **Payment matches the invoice** — the payment `amount_cents` equals the invoice's `total_cents` exactly. Violation: `ERR_PAYMENT_AMOUNT_MISMATCH` (422). Applies to `POST /client-invoices/{id}/payment`.
45. **No reserved funds on close** — a `PermitAccount` may move to `CLOSED` only while `reserved_cents` is exactly 0. Violation: `ERR_PERMIT_HAS_RESERVED_FUNDS` (409). Applies to `POST /permit-accounts/{id}/status`.
46. **Postage funding sufficiency, evaluated last** — on submission, the account's `balance_cents` is at least the statement's `declared_postage_cents`; on an accepting verification that resolves to a positive `adjustment_cents`, the account's `balance_cents` is at least that `adjustment_cents`. Violation: `ERR_INSUFFICIENT_POSTAGE_BALANCE` (402). Applies to `POST /postage-statements/{id}/submit` and `POST /postage-statements/{id}/verify`. This rung sits at the very bottom deliberately: a request that is malformed, unauthorized, out of state or non-compliant must report that fact rather than a money shortfall.

Note the consequence for pooling, which is the endpoint with the most rungs. A job being pooled is checked in this order: batch and job existence, then job state, then already-pooled, then batch state, then client suspension, then permit account status, then move-update currency, then address quality, then mail class, then processing category, then commingling consent. A job that is both from a suspended client *and* below the address-quality floor reports `ERR_CLIENT_SUSPENDED`, not `ERR_ADDRESS_QUALITY_BELOW_MINIMUM`.

### 2.10. Segregation of Duties and the Conservation Invariants

The acceptance unit exists to check the bureau's own work, so the system enforces that the human who files a postage statement can never be the human who signs it off. When a finding is recorded against a statement, or when verification is closed, the acting `X-User-ID` is compared to the statement's `submitted_by_user_id`; if they are equal, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The role check is separate and comes first: only an `AcceptanceClerk` may perform either action at all, and only a `PostageManager` can have filed the statement — but a bureau where one person holds both roles must still use two distinct user identifiers.

Two conservation invariants hold at all times and are the reason several operations look redundant.

**Permit funds conservation.** For any `PermitAccount`, the sum of `balance_cents` and `reserved_cents` changes only when money genuinely enters or leaves the account: it grows by `amount_cents` on a funding deposit, and it shrinks only when postage is actually consumed by an accepted statement. Every other movement is internal — submission moves the declared postage from `balance_cents` into `reserved_cents`, voiding a submitted statement moves it back, and a returned verification moves it back. None of those three changes the total.

**Batch piece-ledger conservation.** For any `CommingleBatch`, `total_piece_count` always equals the sum of `contributed_piece_count` over the batch's currently attached `BatchMember` rows, and `member_job_count` always equals the number of those rows. Withdrawing a member is the exact compensating action for adding one: it subtracts the same `contributed_piece_count` that pooling added and decrements the same counter, then re-derives everything the original pooling derived.

### 2.11. Cascade Integrity and the Documentation Chain

Three operations in this system are **cascades**: a single request drives a chain of state transitions across several resources, and every link in the chain is mandatory. The links are numbered in §3 so that the ordering is unambiguous, and every resource touched by a link has its `version` incremented and its `updated_at` refreshed exactly as if it had been mutated directly.

Sortation drives the batch, its members, its member jobs and its containers together. Deposit drives the shipment, the batch, its containers, the newly created service-level records, the member jobs and the owning clients. A returning verification drives the statement, the permit account, the batch, the member allocations, the member jobs, the containers and — where the rework count has run out of patience — the owning clients. A partial cascade is never an acceptable outcome: if any precondition of the driving operation fails, nothing at all changes.

The chain has a matching **unwind** in each direction. Sortation's freeze is unwound by a returning verification and re-established by a revision; submission's reservation is unwound by a void or a return; pooling's ledger contribution is unwound by withdrawing the member. Wherever a value is described as *reset* during an unwind, it is set to the concrete value stated in §3 — not merely marked stale.

## 3. Business Logic & Workflows

The narrative below follows mail through the bureau in the order it physically moves: a mailer is onboarded and its permit funded, mail is tendered and cleaned, pools are formed, containers are built and sortation is closed, a postage statement is filed and verified, the load is trucked and deposited, and finally delivery performance and money are settled. Cross-cutting concerns are woven into the stage where they first bite rather than collected separately.

### 3.1. Onboarding Mailers and Funding Their Permits

A `BureauAdmin` registers a mail owner before any of its mail can be handled. Registration takes the mailer's legal `name` — between 1 and 120 characters and not blank — and a short operator-facing `client_code` of 2 to 16 characters drawn only from uppercase letters and digits, which must be globally unique across all clients; a collision is rejected with `ERR_DUPLICATE_CLIENT_CODE`. Commercially, the client is defined by two further inputs. `service_fee_rate_per_thousand_cents` is the bureau's own fee in cents charged per thousand mailed pieces before any volume discount, and must be an integer of at least 1. `billing_terms` is the payment term printed on the mailer's invoices and is either `NET_15` or `NET_30`; when omitted it defaults to `NET_30`. A third, optional input decides whether the mailer participates in commingling at all: `commingle_opt_in` is a boolean that defaults to true when omitted, and a mailer that sets it false has chosen to keep its mail out of shared pools.

A newly registered client opens in `ACTIVE` status with `suspension_reason` null, and with both of its running ledgers at zero: `unbilled_postage_cents`, which tracks postage already verified and charged to a permit account but not yet placed on an invoice, and `lifetime_pieces_mailed`, which counts accepted pieces on the client's jobs that have reached `MAILED`.

Trading status is a two-state machine. A `BureauAdmin` may drive `ACTIVE → SUSPENDED`, supplying a `status` of `SUSPENDED` together with an optional `reason` that is stamped into `suspension_reason`; the transition requires the client to currently be `ACTIVE`, and it increments the client's `version`. The reverse move `SUSPENDED → ACTIVE` requires the client to currently be `SUSPENDED`, clears `suspension_reason` back to null, and likewise increments `version`. Suspension is not merely advisory: while a client is `SUSPENDED`, tendering new jobs for it, running a hygiene pass on its jobs, pooling its jobs into a batch, and issuing it an invoice are all refused with `ERR_CLIENT_SUSPENDED`. There is one path into `SUSPENDED` that no administrator requests — the rework cascade of §3.6, which stamps `suspension_reason` with the fixed string `REPEATED_PRESORT_REWORK`.

Postage is never paid out of thin air; it is drawn from a **permit account**, opened by a `PostageManager` against a named `client_id`. The account records the `permit_number` issued by the acceptance unit — 4 to 24 characters, globally unique, with a collision rejected as `ERR_DUPLICATE_PERMIT_NUMBER` — and the `payment_method` under which postage is paid on mail filed under it, one of `PERMIT_IMPRINT`, `METER` or `PRECANCELED_STAMP`. It also records `annual_fee_paid_through_utc`, the instant through which the annual mailing fee has been paid. That instant is a hard regulatory gate: whenever the current logical clock is strictly later than `annual_fee_paid_through_utc`, mail may not be tendered under the account, no hygiene pass may be run on a job funded by it, and no statement drawing on it may be filed — all three are refused with `ERR_PERMIT_ANNUAL_FEE_LAPSED`. A permit account opens in `ACTIVE` status with `balance_cents` and `reserved_cents` both zero.

Money enters the account through a funding deposit, which a `PostageManager` performs by supplying an `amount_cents` of at least 1, the concurrency token `expected_permit_account_version` described in §2.8, and an optional free-text `reference` recorded for the depositor's own reconciliation. The deposit increases `balance_cents` by `amount_cents`, leaves `reserved_cents` untouched — this is what preserves the permit funds conservation invariant of §2.10 — and increments the account's `version` by one. Deposits are refused with `ERR_PERMIT_ACCOUNT_NOT_ACTIVE` unless the account is `ACTIVE`, and refused with `ERR_INVALID_PIECE_COUNT` when `amount_cents` is below 1.

The account's own lifecycle has three states. A `PostageManager` supplying a `status` of `HOLD`, with an optional `reason`, drives `ACTIVE → HOLD`; supplying `ACTIVE` drives `HOLD → ACTIVE`; each requires the account to currently be in the source state and each increments `version`. While an account sits in `HOLD` it funds nothing: pooling a job funded by it and submitting a statement drawn on it are both refused with `ERR_PERMIT_ACCOUNT_NOT_ACTIVE`, as is a further funding deposit. Closure is terminal and can be reached from either live state — `ACTIVE → CLOSED` or `HOLD → CLOSED` — but only while `reserved_cents` is exactly 0, because an account with money encumbered by a statement in flight still has obligations; a close attempted with any reserved funds is rejected with `ERR_PERMIT_HAS_RESERVED_FUNDS`. A `CLOSED` account also refuses every funding operation with `ERR_PERMIT_ACCOUNT_NOT_ACTIVE`, and there is no transition out of `CLOSED`.

Reads round out this stage. A client record can be fetched with its two running ledgers visible; a client's permit accounts and its mail jobs can each be listed by walking back from the client, and the mail-job list accepts `limit` and `offset`. A permit account can be read on its own — the natural way for a `PostageManager` to observe the `version` it will then quote as `expected_permit_account_version` — and the statements filed against a given permit account can be listed.

### 3.2. Tendering Mail and Clearing Address Hygiene

Mail arrives as a **job**. Either a `PresortOperator` on the dock or the mailer's own `ClientContact` tenders it, naming the owning `client_id` and the funding `permit_account_id`, declaring the postal `mail_class` as one of `FIRST_CLASS`, `MARKETING_MAIL` or `PERIODICALS`, declaring the physical `processing_category` as either `LETTERS` or `FLATS`, and stating both a `declared_piece_count` of at least 1 and a `declared_weight_oz_per_piece` that is strictly greater than zero and carries at most three decimal places. A mailer may never file under another mailer's permit: if the named permit account's own `client_id` differs from the job's `client_id`, the tender is rejected with `ERR_PERMIT_CLIENT_MISMATCH`.

A tendered job opens in `RECEIVED`. Its `accepted_piece_count` starts equal to `declared_piece_count`, because nothing has yet been suppressed. Its `hygiene_run_count` and `rework_count` both start at 0, its `address_quality_pct` and `postage_due_cents` both start at 0, its `move_update_compliant` starts false, and its `commingle_batch_id`, `mailed_at_utc` and `cancel_reason` all start null.

Before mail may be pooled it must be cleaned, and cleaning is recorded as an **address hygiene run** by a `PresortOperator`. Each pass reports five figures: the `submitted_piece_count` fed into the pass, which must be at least 1; the `cass_matched_count` of pieces whose addresses were CASS-matched and standardized, which may not exceed `submitted_piece_count`; the `ncoa_move_updated_count` of pieces whose addresses were rewritten by NCOALink move update, which may likewise not exceed `submitted_piece_count`; the `undeliverable_removed_count` of pieces suppressed as undeliverable, which must be strictly less than `submitted_piece_count` so that a pass can never empty the mailing; and `move_update_age_days`, the age in days of the move-update data set used, which must be at least 0. Any of those bounds being broken is rejected with `ERR_INVALID_PIECE_COUNT`.

From those inputs the run derives four values. Its `run_index` is a zero-based ordinal equal to the job's `hygiene_run_count` as it stood immediately *before* this run was counted, so a job's very first pass carries `run_index` 0; the job's `hygiene_run_count` is then incremented by one. Its `net_piece_count` is the `submitted_piece_count` less the `undeliverable_removed_count`. Its `address_quality_pct` is the `cass_matched_count` multiplied by one hundred and divided by the `submitted_piece_count`, rounded half up to two decimal places. Its `move_update_compliant` is true when `move_update_age_days` is less than or equal to the maximum permitted age of 95 days, so a data set exactly 95 days old is compliant while one 96 days old is not.

Those three derived measures are then **mirrored onto the job** from the run with the highest `run_index` — always the newest run. The job's `accepted_piece_count` is set to that run's `net_piece_count`, its `address_quality_pct` to that run's `address_quality_pct`, and its `move_update_compliant` to that run's `move_update_compliant`. Earlier runs are retained as history and are never averaged in; a corrective pass therefore fully replaces its predecessor's verdict. Recording a pass on a job in `RECEIVED` drives it `RECEIVED → HYGIENE_CLEARED`; recording a further pass on a job already in `HYGIENE_CLEARED` is a deliberate self-loop `HYGIENE_CLEARED → HYGIENE_CLEARED`, which is how a stale move-update file gets replaced before pooling. Either way the job's `version` increments by one. A hygiene pass may only be recorded while the job is in `RECEIVED` or `HYGIENE_CLEARED`; from any other status it is refused with `ERR_INVALID_JOB_STATE`. It additionally requires the owning client to be `ACTIVE`, the funding permit account to be `ACTIVE`, and that account's annual fee to be current against the logical clock.

Mail that will not be mailed is cancelled rather than deleted. A `PresortOperator` or a `BureauAdmin` supplies a required `reason`, which is stamped into `cancel_reason`, and the job moves `RECEIVED → CANCELLED` or `HYGIENE_CLEARED → CANCELLED` with its `version` incremented. Cancellation is only available before the job has been pooled; a job in any other status is refused with `ERR_INVALID_JOB_STATE`. Both `CANCELLED` and `BILLED` are terminal for a job — nothing leaves either.

Two computed reads hang off a job. The first, its **standalone postage estimate**, answers the question a mailer always asks: what would this mail cost if we did not commingle it? The estimate prices the job's own `accepted_piece_count` alone, using the same rate machinery as a pooled batch but with two differences. The presort tier is derived from that single job's piece count rather than from any pooled total, and the drop-ship discount in basis points is forced to zero, because an unpooled job is not tendered at an entry point on its own and therefore earns no entry discount. The response reports `piece_count`, the resulting `standalone_tier`, the resulting `standalone_rate_mills_per_piece`, and the resulting `standalone_postage_cents`; nothing is persisted. For a 1200-piece `MARKETING_MAIL` job this prices at the `BASIC` tier with a `standalone_rate_mills_per_piece` of 29440 — 29.44 cents a piece. The second read lists the commingle memberships the job holds, each carrying that membership's allocated postage share.

Jobs can also be listed in bulk. The list accepts optional `client_id`, `permit_account_id`, `commingle_batch_id` and `status` filters — the last matching against any of `RECEIVED`, `HYGIENE_CLEARED`, `POOLED`, `PRESORTED`, `REWORK`, `MAILED`, `BILLED` or `CANCELLED` — together with `limit` and `offset`. A job's hygiene runs can be listed for one job in `run_index` order.

### 3.3. The Entry-Point Network

Deeper postal discounts are earned by carrying mail closer to its destination, so the bureau maintains a register of postal **entry facilities**. A `BureauAdmin` registers one with a globally unique `facility_code` of 3 to 24 characters — a collision is `ERR_DUPLICATE_FACILITY_CODE` — and a `facility_type` describing how deep in the postal network it sits: `DDU` for a destination delivery unit, `SCF` for a sectional center facility, or `NDC` for a network distribution center. Its own location is the exactly-three-digit `zip3` string. Its `dock_capacity_pallets_per_slot`, an integer of at least 1, is the maximum number of pallets the dock can absorb across all appointment windows that overlap any given instant. Its `drop_ship_discount_bp` is the entry discount in basis points that mail entered there earns on the per-piece rate, an integer between 0 and 2000 inclusive — so at most a 20 percent reduction. Finally its `served_zip3_list` is an array of 1 to 40 distinct three-digit strings naming the ZIP prefixes the facility delivers directly; that list is what drives delivery zone and committed service days for every container labelled to one of those prefixes.

A facility opens in `OPEN` status. A `BureauAdmin` supplying a `status` of `CLOSED` drives `OPEN → CLOSED` and supplying `OPEN` drives `CLOSED → OPEN`, each requiring the facility to currently be in the source state and each incrementing `version`. Closing a facility is forward-looking only: dock appointments already booked there are untouched and continue to their conclusion, but a new booking against a `CLOSED` facility is refused with `ERR_ENTRY_FACILITY_CLOSED`. A facility can be read on its own, and the drop shipments booked at it can be listed.

### 3.4. Commingling: Pooling Jobs to Earn a Deeper Tier

Commingling is the bureau's core value proposition, and a **commingle batch** is the pool that realizes it. A `PresortOperator` opens one by declaring the single `mail_class` and the single `processing_category` that every member job must share, together with the `entry_facility_id` naming the entry point the pool is planned against. The batch opens in `OPEN` status with `achieved_tier` at `NONE` and with `member_job_count`, `total_piece_count`, `container_count`, `rate_mills_per_piece` and `batch_postage_cents` all at 0.

Pooling a job into the batch is done by naming its `mail_job_id`, and it is the most heavily gated operation in the system. The job must be in `HYGIENE_CLEARED`; a job already in `POOLED` is refused with `ERR_JOB_ALREADY_POOLED` and a job in any other status with `ERR_INVALID_JOB_STATE`. The batch must be `OPEN`. The job's client must be `ACTIVE` and must have `commingle_opt_in` true, otherwise the request is refused with `ERR_CLIENT_SUSPENDED` or `ERR_COMMINGLE_OPT_OUT` respectively. The job's funding permit account must be `ACTIVE`. The job's `move_update_compliant` must be true, otherwise `ERR_MOVE_UPDATE_STALE`. The job's `address_quality_pct` must be at least 95.00 percent, otherwise `ERR_ADDRESS_QUALITY_BELOW_MINIMUM` — a job at exactly 95.00 passes, a job at 94.99 does not. And the job's `mail_class` and `processing_category` must each equal the batch's, otherwise `ERR_MAIL_CLASS_MISMATCH` or `ERR_PROCESSING_CATEGORY_MISMATCH`. §2.9 fixes the order in which those checks fire.

A successful pooling creates a **batch member** — the junction row that makes the job-to-batch relationship many-to-many over time — carrying the `commingle_batch_id` of the pool and the `mail_job_id` of the job. Its `contributed_piece_count` is a snapshot of the job's `accepted_piece_count` taken at the instant of pooling and is **never re-read afterwards**: a later hygiene run on the job cannot retroactively change what the job contributed to a pool it is already in. The job itself moves `HYGIENE_CLEARED → POOLED` and has its denormalized `commingle_batch_id` pointer set to the batch. On the batch side, `total_piece_count` grows by the new member's `contributed_piece_count` and `member_job_count` grows by one. Both the batch's `version` and the job's `version` increment by one. At most one non-withdrawn batch member exists per job at any time.

Every change of membership immediately re-derives the batch's price, in a pinned three-stage order: first the tier, then the rate and batch postage, then the per-member allocation.

**Stage one — the presort tier.** The `achieved_tier` follows from the pooled volume alone, compared against three inclusive thresholds. A pool of at least 15000 pieces qualifies `FIVE_DIGIT`; failing that, a pool of at least 3000 pieces qualifies `THREE_DIGIT`; failing that, a pool of at least 500 pieces qualifies `BASIC`; a pool below 500 pieces achieves `NONE`. The comparisons are inclusive at every step, so exactly 3000 pieces qualifies `THREE_DIGIT` while 2999 pieces qualifies only `BASIC`. The piece count used is the batch's `total_piece_count`, that is the sum of `contributed_piece_count` over the batch's *currently attached* members; a member that has been withdrawn contributes nothing.

**Stage two — the per-piece rate and the batch postage.** Each mail class has a published base rate in whole cents per piece: `FIRST_CLASS` is 64 cents, `MARKETING_MAIL` is 32 cents, and `PERIODICALS` is 28 cents. Each tier carries a discount in basis points: `NONE` earns 0, `BASIC` earns 800 basis points, `THREE_DIGIT` earns 1500, and `FIVE_DIGIT` earns 2200. The entry point contributes a second discount, the `drop_ship_discount_bp` of the batch's entry facility. The batch's `rate_mills_per_piece` is then derived as follows: take the base rate in cents for the batch's mail class and multiply it by one thousand to express it in mills; multiply that by the tier factor, which is ten thousand less the tier's discount in basis points; multiply that product by the entry factor, which is ten thousand less the facility's `drop_ship_discount_bp`; divide the whole result by one hundred million; and take the floor of that single quotient. The entire numerator is evaluated in exact integer arithmetic and floored **exactly once, at the very end** — flooring after the tier factor and again after the entry factor is forbidden and produces a different rate. The batch's `batch_postage_cents` is then the batch's `total_piece_count` multiplied by `rate_mills_per_piece`, divided by one thousand to convert mills to cents, and rounded half up to a whole number of cents. That mills-to-cents conversion happens exactly once, over the whole pooled piece count — never once per container and never once per member.

This is precisely where commingling pays. Consider 1200 pieces of `MARKETING_MAIL`. Standing alone they reach only the `BASIC` tier with no entry discount, at 29440 mills a piece. Pooled inside a 3000-piece batch entered at an `SCF` facility offering a 300-basis-point entry discount, the same 1200 pieces reach the `THREE_DIGIT` tier and price at 26384 mills a piece — a strictly lower cost for identical mail, purchased entirely with other mailers' volume.

**Stage three — the pro-rata allocation.** Having priced the pool as a whole, the bureau must split it among the mailers who contributed to it, and the split must add up exactly. The rounding order is pinned: the pool is rounded to whole cents **first**, by whichever calculation produced it, and only then split. Rounding each member's raw share half up and summing the results is forbidden, because it can drift from the pool by as much as one cent per member. The allocation runs over the batch's currently attached members, with the denominator being the sum of their `contributed_piece_count` — which is exactly the batch's `total_piece_count`, and is never zero, because sortation cannot run on a batch with no members. For each member, its raw share is the pool of cents multiplied by that member's `contributed_piece_count` and divided by the denominator, held as an exact rational and not rounded at this point. Each member's `share_basis_pct` is separately recorded as its `contributed_piece_count` multiplied by one hundred and divided by the denominator, rounded half up to four decimal places. Each member's provisional allocation is the floor of its raw share. The remainder — the pool of cents less the sum of those floors — is then a whole number strictly less than the number of members, and it is distributed one cent at a time: members are ordered by `contributed_piece_count` descending, and where two members contributed equally, by `created_at` ascending; the first *remainder*-many members in that order each receive one additional cent. A member's final allocation is its floor plus that one cent if it was among them. The invariant is absolute: the allocated amounts sum to the pool exactly, for every pool and every member set. No random or arbitrary tiebreak participates.

While the batch is `OPEN`, this three-stage derivation writes each member's `share_basis_pct` and `allocated_postage_cents` from the batch's current `batch_postage_cents`. It does **not** write any member job's `postage_due_cents` — postage is not attributed to a job until an acceptance clerk accepts the statement covering it.

Withdrawal is the exact compensating action. A `PresortOperator` may withdraw a member from an `OPEN` batch while the member's job is in `POOLED`; the request returns 204 with no body. The batch member row is deleted, the job moves `POOLED → HYGIENE_CLEARED`, its `commingle_batch_id` is cleared back to null and its `postage_due_cents` is reset to 0. The batch's `total_piece_count` decreases by exactly the `contributed_piece_count` the member had contributed and `member_job_count` decreases by one, restoring the batch piece ledger. The three-stage derivation then re-runs over the surviving members, so `achieved_tier`, `rate_mills_per_piece`, `batch_postage_cents` and every remaining member's `share_basis_pct` and `allocated_postage_cents` are all refreshed — a withdrawal that drops the pool below 3000 pieces genuinely costs the remaining mailers their `THREE_DIGIT` rate. Both the batch's `version` and the job's `version` increment. Withdrawal from a batch that is no longer `OPEN` is refused with `ERR_INVALID_BATCH_STATE`.

A batch can be read on its own — the natural way for a `PostageManager` to observe the `version` it will quote as `expected_batch_version` — and batches can be listed with optional `status`, `mail_class` and `entry_facility_id` filters plus `limit` and `offset`. A batch's members can be listed with their pro-rata shares, as can its containers, its postage statements including superseded revisions, and its drop shipments.

### 3.5. Containerization, Documentation and Closing Sortation

Pooled pieces are physically placed into **sort containers** — trays and pallets — before they can be documented. A `PresortOperator` adds one to an `OPEN` batch by declaring its `container_type` as either `TRAY` or `PALLET`, its `destination_zip3` as exactly three digits, its `sort_level` as one of `MIXED_ADC`, `ADC`, `THREE_DIGIT` or `FIVE_DIGIT`, and the `piece_count` physically placed in it, which must be at least 1.

Whether a container earns its keep is decided at once, and written to `qualifies`. The minimum piece count a container must hold depends on both its type and its sortation depth. A `PALLET` must hold at least 250 pieces regardless of sort level. A `TRAY` built at the deep levels `THREE_DIGIT` or `FIVE_DIGIT` must hold at least 150 pieces. A `TRAY` built at the shallow levels `ADC` or `MIXED_ADC` must hold at least 1 piece, which is to say any non-empty shallow tray qualifies. The comparison is inclusive: a `TRAY` at `FIVE_DIGIT` holding exactly 150 pieces qualifies, one holding 149 does not. The container's `sequence_index` is a zero-based ordinal equal to the number of containers already attached to the batch, assigned in creation order, and the batch's `container_count` is then incremented by one. The container's `placard_id` starts null — documentation placards are stamped only at sortation — and its `status` starts at `STAGED`. Adding a container increments the batch's `version` by one.

The same request also settles the container's service commitment, and this is where the `served_zip3_list` of §3.3 earns its place. Take the entry facility referenced by the container's batch. If the container's `destination_zip3` appears as an exact member of that facility's `served_zip3_list` — plain string membership, with no prefix or range logic — then the facility type decides both figures: a `DDU` gives `zone` 1 and a base of 1 day, an `SCF` gives `zone` 2 and a base of 2 days, and an `NDC` gives `zone` 4 and a base of 3 days. If the destination is not in the served list, the container falls to `zone` 8 with a base of 5 days. The container's `committed_days` is that base plus a class adder taken from the batch's mail class: `FIRST_CLASS` adds 0 days, `PERIODICALS` adds 1 day, and `MARKETING_MAIL` adds 2 days. `zone` is therefore always one of 1, 2, 4 or 8. A container's own lifecycle runs through exactly four statuses — `STAGED` while it is being built, `DOCUMENTED` once sortation has stamped its placard, `RETURNED` if the mailing is sent back to the floor, and `DEPOSITED`, which is terminal, once it has been inducted at the entry point. A container can be read on its own, and a batch's containers can be listed in `sequence_index` order.

**Closing sortation** is the moment the pool's economics are frozen, and a `PresortOperator` drives it. Four gates guard it, and §2.9 orders them. The batch must be `OPEN`, or the request is refused with `ERR_INVALID_BATCH_STATE`. The batch must have at least one member and at least one container — a batch whose `member_job_count` or `container_count` is 0 is refused with `ERR_BATCH_HAS_NO_CONTAINERS`. Every container on the batch must have `qualifies` true, or the request is refused with `ERR_CONTAINER_NOT_QUALIFIED`. And the sum of `piece_count` over the batch's containers must equal the batch's `total_piece_count` exactly, or the request is refused with `ERR_CONTAINER_PIECE_MISMATCH` — the physical mail on the floor must reconcile against the pooled ledger to the piece.

When those gates pass, the batch moves `OPEN → SORTED` and the whole three-stage derivation of §3.4 runs one final time and is then frozen: `achieved_tier` is fixed from the pooled volume, `rate_mills_per_piece` and `batch_postage_cents` are fixed from that tier, the mail class base rate and the entry facility's `drop_ship_discount_bp`, and every batch member's `share_basis_pct` and `allocated_postage_cents` are written from `batch_postage_cents`. Every member job moves `POOLED → PRESORTED`, and each such job has its `postage_due_cents` set to 0 — postage is still not attributed to a job at this point — with its `version` incremented. Every container of the batch moves `STAGED → DOCUMENTED` and receives its `placard_id`, formed as the entry facility's `facility_code`, then a hyphen, then the container's `destination_zip3`, then a hyphen, then the container's `sequence_index`; each container's `version` increments. The batch's own `version` increments by one. From `SORTED` onward the batch's pricing is documentation of record: nothing short of the unwind described in §3.6 changes it.

### 3.6. The Postage Statement: Filing, Verification and Correction

The **postage statement** is the document the bureau files with the acceptance unit to declare what the mailing owes, and it is the only place postage actually leaves a permit account. A `PostageManager` prepares one against a `commingle_batch_id` naming a batch in `SORTED`, a `permit_account_id` naming the account of record that will fund and be debited for the whole statement, and the `expected_batch_version` concurrency token of §2.8. A statement prepared against a batch in any status other than `SORTED` is refused with `ERR_INVALID_BATCH_STATE`.

Preparation is an act of freezing. The statement's `statement_piece_count` is frozen from the batch's `total_piece_count`, its `rate_mills_per_piece` is frozen from the batch's `rate_mills_per_piece`, and its `declared_postage_cents` is set from the batch's `batch_postage_cents`. None of the three is ever re-derived from the batch afterwards — the only exception being the deliberate re-freeze performed by a revision, described at the end of this subsection. The `prepared_by_user_id` records the acting `X-User-ID`. The statement opens in `DRAFT` with `adjustment_cents`, `verified_postage_cents`, `verification_error_count` and `revision_index` all at 0, and with `submitted_by_user_id`, `verified_by_user_id` and `void_reason` all null. The batch's `version` increments by one. Preparing a statement legitimately supersedes any statement still sitting in `DRAFT` on the same batch: each such predecessor is driven `DRAFT → VOID` with its `void_reason` set to the fixed string `SUPERSEDED_BY_NEWER_STATEMENT` and its `version` incremented.

**Filing.** A `PostageManager` files the statement, driving `DRAFT → SUBMITTED`. Filing requires the statement to be in `DRAFT`, its batch to be in `SORTED`, its permit account to be `ACTIVE`, that account's `annual_fee_paid_through_utc` to be at or after the logical clock, and — checked last of all, per §2.9 — the account's `balance_cents` to be at least the statement's `declared_postage_cents`; a shortfall is `ERR_INSUFFICIENT_POSTAGE_BALANCE` at HTTP 402. Filing sets `submitted_by_user_id` to the acting `X-User-ID` and moves the declared postage from spendable to encumbered: `declared_postage_cents` is subtracted from the account's `balance_cents` and added to its `reserved_cents`, which changes nothing about the account's total funds. The batch moves `SORTED → DOCUMENTED`. Both the statement's `version` and the permit account's `version` increment by one.

**Findings.** At the acceptance unit an `AcceptanceClerk` records each defect as a **verification finding** against a statement in `SUBMITTED`, naming a `finding_type` from `SHORT_PAID`, `BAD_ADDRESS_QUALITY`, `CONTAINER_NOT_QUALIFIED`, `MOVE_UPDATE_STALE` or `DOC_MISMATCH`, and an `affected_piece_count` between 1 and the statement's frozen `statement_piece_count` inclusive. The clerk's `X-User-ID` is stamped into `assessed_by_user_id`, and it must differ from the statement's `submitted_by_user_id` or the request is refused with `ERR_SEGREGATION_OF_DUTIES`.

Each finding carries two derived values, and how they are derived is the subtlest arithmetic in this specification. The evaluation is deliberately pinned, because a surcharge is a rate applied to a share of the statement while the statement total is what the surcharge changes — left unpinned, the definition would be circular. Two facts break the circle. First, `statement_piece_count` and `rate_mills_per_piece` were frozen onto the statement at preparation; they are never re-read from the batch and are never reduced by the affected pieces. Second, the presort tier is never re-derived from the verified total. With those fixed, the walk proceeds as follows. The statement's findings are taken in `created_at` ascending order, which is exactly the order the clerk recorded them, and a cumulative count of affected pieces is carried through the walk starting at zero. At each finding the cumulative count grows by that finding's `affected_piece_count`. The finding's `severity` is then `MAJOR` when the cumulative count of affected pieces multiplied by ten thousand is at least the statement's frozen `statement_piece_count` multiplied by the major threshold of 500 basis points — equivalently, when the running total of affected pieces has reached five percent of the frozen piece count — and `MINOR` otherwise. That severity picks a surcharge rate in basis points: `MINOR` draws 2500 basis points and `MAJOR` draws 10000 basis points. The finding's `surcharge_cents` is then this finding's own `affected_piece_count` multiplied by the statement's frozen `rate_mills_per_piece`, multiplied by that basis-point rate, divided by ten million, and rounded half up to a whole number of cents.

Severity is therefore **cumulative and order-sensitive**, which is intentional: on a 3000-piece statement, recording a 120-piece finding and then a 400-piece finding yields `MINOR` followed by `MAJOR`, while recording the same two findings in the opposite order yields `MAJOR` followed by `MAJOR` and a strictly larger total adjustment. Both `severity` and `surcharge_cents` are persisted onto the finding when it is recorded and are never recomputed afterwards. After each finding, the statement's `adjustment_cents` is refreshed as the sum of `surcharge_cents` over that same ordered walk — each finding rounded half up individually and the rounded amounts then summed; summing the exact rationals and rounding once at the end is forbidden — and `verification_error_count` is refreshed as the number of findings recorded. The statement's `version` increments by one. A statement's findings can be listed in `created_at` order.

**Closing verification.** An `AcceptanceClerk` closes verification on a statement in `SUBMITTED` by supplying an `outcome` of either `ACCEPT` or `RETURN`. The acting `X-User-ID` must differ from `submitted_by_user_id`. All three branches set `verified_by_user_id` to the acting `X-User-ID` and increment both the statement's `version` and the permit account's `version`; beyond that they diverge sharply, and each is specified in full below.

*Branch one — accepted clean.* When the outcome is `ACCEPT` and the pinned walk resolves `adjustment_cents` to exactly 0, the statement moves `SUBMITTED → ACCEPTED_CLEAN`. Its `adjustment_cents` is set to 0 and its `verified_postage_cents` to its `declared_postage_cents`. The reservation is consumed rather than returned: `declared_postage_cents` is subtracted from the account's `reserved_cents` and is not added back to `balance_cents`, which is the one moment postage genuinely leaves the account. Every batch member has its `allocated_adjustment_cents` set to 0, and every member job has its `postage_due_cents` set to that member's `allocated_postage_cents`. Each member job's `postage_due_cents` is then added to that job's client's `unbilled_postage_cents`. The batch is left in `DOCUMENTED`.

*Branch two — accepted with an adjustment.* When the outcome is `ACCEPT` and the walk resolves `adjustment_cents` to a value greater than 0, the statement moves `SUBMITTED → ACCEPTED_WITH_ADJUSTMENT`, but only if the account's `balance_cents` is at least that `adjustment_cents`; otherwise the whole verification is refused with `ERR_INSUFFICIENT_POSTAGE_BALANCE`. The statement's `adjustment_cents` takes the walked value and its `verified_postage_cents` becomes its `declared_postage_cents` plus that `adjustment_cents`. Two separate movements hit the account: `declared_postage_cents` is subtracted from `reserved_cents`, consuming the reservation, and `adjustment_cents` is subtracted from `balance_cents`, paying the surcharge. The pro-rata allocation of §3.4 then runs a second time, this time over a pool equal to the statement's `adjustment_cents`, writing each batch member's `allocated_adjustment_cents` — same denominator, same floor-plus-remainder rule, same ordering by `contributed_piece_count` descending then `created_at` ascending, and the same absolute invariant that the allocated adjustments sum to `adjustment_cents` exactly. Every member job then has its `postage_due_cents` set to its member's `allocated_postage_cents` plus its `allocated_adjustment_cents`, and each of those amounts is added to that job's client's `unbilled_postage_cents`. The batch is left in `DOCUMENTED`. Unlike branch one, this branch debits `balance_cents` and writes non-zero `allocated_adjustment_cents`.

*Branch three — returned for correction.* When the outcome is `RETURN`, the statement moves `SUBMITTED → RETURNED_FOR_CORRECTION`, and this is only permitted when at least one finding has been recorded during the current filing episode — a return requested while `verification_error_count` is 0 is refused with `ERR_NO_VERIFICATION_FINDINGS`. No money leaves the permit account and the entire batch is unwound, in four numbered links. Link 1: `declared_postage_cents` is subtracted from the account's `reserved_cents` and added back to its `balance_cents`, so the account's total funds are unchanged and the encumbrance is released. The statement's `adjustment_cents` and `verified_postage_cents` are left at 0. Link 2: the batch moves `DOCUMENTED → REWORK`, and its `achieved_tier` is reset to `NONE`, its `rate_mills_per_piece` to 0 and its `batch_postage_cents` to 0, with its `version` incremented. Link 3, caused by link 2: every batch member has its `allocated_postage_cents` and `allocated_adjustment_cents` reset to 0 and its `share_basis_pct` reset to null; every member job moves `PRESORTED → REWORK`, has its `rework_count` incremented by one and its `postage_due_cents` reset to 0, and has its `version` incremented; and every container of the batch moves `DOCUMENTED → RETURNED` with its `version` incremented. Link 4, caused by link 3: for any member job whose `rework_count` has now reached 2 or more, that job's client is driven `ACTIVE → SUSPENDED` with `suspension_reason` set to the fixed string `REPEATED_PRESORT_REWORK` and its `version` incremented — a mailer whose address file has now sent two mailings back to the floor stops tendering new work until an administrator reinstates it.

**Voiding.** A `PostageManager` may void a statement with a required `reason`, which is stamped into `void_reason`, and the statement moves to `VOID` from either `DRAFT` or `SUBMITTED`. Voiding from `DRAFT` touches nothing else beyond incrementing the statement's `version`. Voiding from `SUBMITTED` is the compensating action for filing: `declared_postage_cents` is subtracted from the account's `reserved_cents` and added back to its `balance_cents`, preserving the account's total funds, and the batch is returned `DOCUMENTED → SORTED` so that a replacement statement can be prepared against the same sortation. That return deliberately leaves `achieved_tier`, `rate_mills_per_piece`, `batch_postage_cents` and every batch member allocation intact — the sortation itself was never in question. The statement's `version`, the account's `version` and the batch's `version` all increment. `VOID`, `ACCEPTED_CLEAN` and `ACCEPTED_WITH_ADJUSTMENT` are all terminal for a statement.

**Revising.** A returned statement is reopened by a `PostageManager`, moving `RETURNED_FOR_CORRECTION → DRAFT`; the operation requires the statement to be in `RETURNED_FOR_CORRECTION` and its batch to be in `REWORK`. The statement's `revision_index` increments by one, and its `adjustment_cents`, `verified_postage_cents` and `verification_error_count` are all cleared to 0 while `submitted_by_user_id` and `verified_by_user_id` are cleared to null. Findings already recorded are **retained as history and never discarded**; because `verification_error_count` returns to 0, those historical findings are excluded from the pinned walk of any later filing episode, which considers only findings recorded after the revision. In the same operation the batch is driven `REWORK → OPEN`, which re-runs the full three-stage derivation of §3.4 over the surviving members — recomputing `achieved_tier`, then `rate_mills_per_piece` and `batch_postage_cents`, then every member's `share_basis_pct` and `allocated_postage_cents` — restoring the values the batch held before it was unwound. That same move drives every member job `REWORK → POOLED` and every container `RETURNED → STAGED`, clearing each container's `placard_id` back to null, with a `version` increment on the batch, on each job and on each container. Only **after** the batch has recomputed itself does the statement re-freeze: `statement_piece_count` and `rate_mills_per_piece` are taken again from the batch's freshly recomputed values and `declared_postage_cents` is recomputed from them. The statement's `version` increments by one. The batch is now `OPEN` again, so the floor must re-close sortation before the corrected statement can be filed — which closes the two intertwined cycles this workflow is built around: `POOLED → PRESORTED → REWORK → POOLED` for the jobs, and `SUBMITTED → RETURNED_FOR_CORRECTION → DRAFT → SUBMITTED` for the statement.

A statement can be read on its own, showing its frozen piece count and rate, its adjustment and its verified total.

### 3.7. Dock Appointments, Departure and Deposit

Documented mail has to be physically delivered to the postal entry point, and that happens on a booked dock appointment called a **drop shipment**. A `PresortOperator` books one by naming the `commingle_batch_id` of the pool being inducted, the `entry_facility_id` of the dock, an inclusive `window_start_utc` and an exclusive `window_end_utc` that must be strictly after it, and the `pallet_count` of at least 1 that will be tendered against the dock's capacity in that window. An appointment may be booked while the batch is `OPEN`, `SORTED` or `DOCUMENTED`; any other batch status is refused with `ERR_INVALID_BATCH_STATE`. The facility must be `OPEN`, or the booking is refused with `ERR_ENTRY_FACILITY_CLOSED`. A batch may have at most one live appointment at a time: if the batch already has a shipment in `SCHEDULED` or `IN_TRANSIT`, the booking is refused with `ERR_SHIPMENT_ALREADY_SCHEDULED`. An ill-formed window is `ERR_INTERVAL_INVALID`, and a `window_start_utc` earlier than the current logical clock is `ERR_SHIPMENT_WINDOW_IN_PAST` — appointments may not be booked into the past, though a window starting exactly at the current clock instant is acceptable.

The dock itself is an **aggregate capacity**, not an exclusive slot. To evaluate a booking, take every drop shipment at the same facility whose status is `SCHEDULED` or `IN_TRANSIT`; shipments in `CANCELLED`, `NO_SHOW` or `DEPOSITED` have released their pallets and take no part. Of those candidates, keep the ones whose window overlaps the requested window under half-open geometry: a candidate overlaps when its own `window_start_utc` is strictly earlier than the requested `window_end_utc` **and** the requested `window_start_utc` is strictly earlier than the candidate's `window_end_utc`. Touching endpoints therefore do not overlap at all — a shipment beginning at the exact instant another ends is never a conflict. Sum the `pallet_count` of the overlapping shipments to get the pallets already occupied. The booking is refused with `ERR_DOCK_CAPACITY_EXCEEDED` exactly when those occupied pallets plus the requested `pallet_count` are strictly greater than the facility's `dock_capacity_pallets_per_slot`; a total exactly equal to capacity is accepted. Any number of shipments may share a window as long as their pallets sum within capacity. A successful booking opens the shipment in `SCHEDULED` with `deposited_at_utc` and `cancel_reason` both null.

Dispatch is a simple move: a `PresortOperator` drives the load `SCHEDULED → IN_TRANSIT`, incrementing the shipment's `version`. Departure from any other status is refused with `ERR_INVALID_SHIPMENT_STATE`.

**Deposit** is the second great cascade, and only an `AcceptanceClerk` may record it. The shipment must be in `IN_TRANSIT`, its batch must be in `DOCUMENTED`, that batch must have a statement in `ACCEPTED_CLEAN` or `ACCEPTED_WITH_ADJUSTMENT` — otherwise `ERR_STATEMENT_NOT_ACCEPTED` — and the logical clock must lie inside the appointment window treated as a closed interval, at or after `window_start_utc` and at or before `window_end_utc`, otherwise `ERR_OUTSIDE_APPOINTMENT_WINDOW`. On success the shipment moves `IN_TRANSIT → DEPOSITED` and its `deposited_at_utc` is stamped from the logical clock. Link 1: the batch moves `DOCUMENTED → CLOSED`, which is terminal for a batch. Link 2, caused by link 1: every container of the batch still in `DOCUMENTED` moves `DOCUMENTED → DEPOSITED`, which is terminal for a container. Link 3, caused by link 2: each newly deposited container opens exactly one **service-level record**, created in ascending container `sequence_index` order, carrying that container's `sort_container_id`, its `zone`, its `committed_days` and its `piece_count`, with its own `deposited_at_utc` set from the logical clock and its `actual_delivery_days`, `scanned_at_utc` and `on_time` all null. Also link 3, caused by link 1: every member job of the batch still in `PRESORTED` moves `PRESORTED → MAILED` and has its `mailed_at_utc` stamped from the logical clock. Link 4, caused by link 3: each newly mailed job's `accepted_piece_count` is added to that job's client's `lifetime_pieces_mailed`. The shipment's `version`, the batch's `version`, each container's `version`, each mailed job's `version` and each affected client's `version` all increment by one.

An appointment that will not be kept is cancelled rather than left to rot. A `PresortOperator` or a `BureauAdmin` supplies a required `reason`, stamped into `cancel_reason`, and the shipment moves `SCHEDULED → CANCELLED` or `IN_TRANSIT → CANCELLED` with its `version` incremented. Cancellation releases this shipment's `pallet_count` from the dock's occupancy for every window that overlapped it, so the freed capacity is immediately available to future bookings.

The bureau also runs an **ops checkpoint on every clock advance**. When a `BureauAdmin` moves the logical clock to a supplied `to_iso8601` instant, the server walks all shipments still in `SCHEDULED` in `created_at` ascending order and, for each whose `window_end_utc` is strictly earlier than the new clock value, drives it `SCHEDULED → NO_SHOW`, releases its `pallet_count` from the dock occupancy of every overlapping window, and increments its `version`. Shipments in `IN_TRANSIT` are exempt from the sweep — a truck on the road is not a no-show. The response reports the new clock as `current_utc` together with `no_show_shipment_ids`, the array of identifiers of the shipments the advance just marked. `DEPOSITED`, `CANCELLED` and `NO_SHOW` are all terminal for a shipment. A shipment can be read on its own, and shipments can be listed per facility and per batch.

### 3.8. Service-Level Tracking and Client Billing

Once a container is in the postal network the bureau owes its clients an answer about whether it arrived on time, and the service-level record opened at deposit is where that answer lands. An `AcceptanceClerk` settles a record by supplying the observed `actual_delivery_days`, an integer of at least 0, together with the `scanned_at_utc` instant at which the delivery scan was captured. The record's `on_time` is then set to true when `actual_delivery_days` is less than or equal to the record's `committed_days`, and false otherwise; delivering in exactly the committed number of days counts as on time. The record's `version` increments. A record may be scanned only once — its `actual_delivery_days` must still be null when the scan arrives, and a second scan is refused with `ERR_DELIVERY_ALREADY_SCANNED`. A record can be read on its own, and the records opened for one container can be listed.

Because a commingled container carries mail belonging to several mailers at once, a client's **service-level index** is computed by reaching outward from the records rather than being stored on the client. The population is every service-level record that has actually been delivery-scanned — that is, whose `actual_delivery_days` is not null — whose container belongs to a batch that has at least one member whose job's `client_id` is the client being asked about. Unscanned records are excluded from both numerator and denominator entirely. One commingled container therefore counts once for every client with mail in that batch. If the population is empty, both indexes are reported as null and `record_count` is 0.

Two indexes are reported over that same population, and they deliberately differ. The `zone_weighted_index` is the bureau's contractual metric and weights distant entry zones more heavily: each record contributes a weight determined by its `zone` — `zone` 1 weighs 1, `zone` 2 weighs 2, `zone` 4 weighs 3, and `zone` 8 weighs 5 — the numerator is the sum of those weights over records whose `on_time` is true, the denominator is the sum of those weights over all records in the population, and the index is the numerator multiplied by one hundred, divided by the denominator, rounded half up to two decimal places. The `piece_weighted_index` is the volume-fair metric shown to the client and weights each record by its `piece_count` instead: the numerator is the sum of `piece_count` over records whose `on_time` is true, the denominator is the sum of `piece_count` over the whole population, and the result is again multiplied by one hundred and rounded half up to two decimal places. The response also reports `record_count`, the number of scanned records in the population, and `on_time_count`, the number of those whose `on_time` is true. The two indexes genuinely disagree on identical inputs: one late `zone` 8 container of 2000 pieces alongside one on-time `zone` 2 container of 1000 pieces yields a `zone_weighted_index` of 28.57 and a `piece_weighted_index` of 33.33.

**Invoicing.** A `PostageManager` issues an invoice to a client for a closed billing period bounded by `period_start_utc` and `period_end_utc`, the latter strictly after the former. The client must be `ACTIVE`. Before anything is computed, the period is tested for exclusivity against the client's own history, and the geometry here is deliberately the opposite of the dock rule: the interval is **closed at both ends** and there is no aggregate allowance. Scanning the client's existing invoices in `created_at` ascending order, a conflict exists as soon as one is found whose `period_end_utc` is at or after the requested `period_start_utc` **and** whose `period_start_utc` is at or before the requested `period_end_utc`; both `ISSUED` and `PAID` invoices participate, and no other client's invoices do. The first conflict found is rejected with `ERR_BILLING_PERIOD_OVERLAP`. Adjacency is a conflict: a new period starting exactly on a prior period's end instant is rejected, because that instant would otherwise be billed twice.

The charge itself is then assembled in a pinned order. First, select the client's jobs that are in `MAILED` and whose `mailed_at_utc` falls inside the requested period treated as closed at both ends, ordered by `created_at` ascending. If that selection is empty the request is rejected with `ERR_NO_BILLABLE_JOBS`. Otherwise, for each selected job take the one batch member whose `mail_job_id` is that job — there is exactly one, because a job can only reach `MAILED` through a sorted batch. The invoice's `postage_cents` is the sum of `allocated_postage_cents` over those members, its `adjustment_cents` is the sum of `allocated_adjustment_cents` over the same members, its `billed_piece_count` is the sum of `accepted_piece_count` over the selected jobs, and its `included_job_count` is the number of jobs selected. Next, the billable volume is converted into whole thousands of pieces by dividing `billed_piece_count` by one thousand and taking the ceiling — 1 piece and 1000 pieces both count as one thousand, 1001 pieces count as two. A volume discount in basis points follows from `billed_piece_count` itself: below 5000 pieces the discount is 0, from 5000 up to but not including 25000 pieces it is 500 basis points, and at 25000 pieces or more it is 1200 basis points, the highest satisfied threshold winning. The gross fee is those whole thousands multiplied by the client's `service_fee_rate_per_thousand_cents`. The discounted fee is the gross fee multiplied by ten thousand less the volume discount in basis points, divided by ten thousand, rounded half up to a whole number of cents — and this is the only rounding step in the whole invoice. The invoice's `service_fee_cents` is then the greater of the bureau's minimum charge of 2500 cents and that discounted fee. Finally `total_cents` is `postage_cents` plus `adjustment_cents` plus `service_fee_cents`.

The three inputs interact non-linearly, and the order above is what makes the result well defined: the ceiling on thousands is applied *before* the discount factor, and the minimum-charge floor is applied *after* it, so a small mailing can end up paying the 2500-cent floor while a large one pays a genuinely discounted rate.

Issuing the invoice also settles the ledger. Every included job moves `MAILED → BILLED` with its `version` incremented, which is what makes re-issuing over the same jobs impossible — they are no longer in `MAILED` and so cannot be selected again. The client's `unbilled_postage_cents` decreases by the invoice's `postage_cents` plus its `adjustment_cents`. The invoice opens in `ISSUED` with `paid_amount_cents` at 0.

Settlement is all-or-nothing. A `PostageManager` records a payment against an invoice in `ISSUED` by supplying an `amount_cents` that must equal the invoice's `total_cents` exactly; any other figure is rejected with `ERR_PAYMENT_AMOUNT_MISMATCH`, and a second payment against an already-`PAID` invoice is rejected with `ERR_INVALID_INVOICE_STATE`. On success the invoice moves `ISSUED → PAID`, its `paid_amount_cents` is set to the `amount_cents` paid, and its `version` increments. `PAID` is terminal. An invoice can be read on its own, and a client's invoices can be listed.

All paths below are mounted at the server root; there is no additional API prefix. Creating a new resource returns HTTP 201 with the created resource in `data`; modifying an existing resource returns HTTP 200 with the updated resource in `data`; the one deletion in this API returns HTTP 204 with no body. Read endpoints return HTTP 200. The table below gives only the HTTP contract and the authorized roles — the request payload, the response payload and the side effects of each operation are specified in §3, and the rejection each operation can produce is specified in §2.9 and §5.
