# Waterpark Resort Capacity API — Product Requirements Document

## 1. Introduction

An indoor waterpark resort sells a single product — a stay — but must account for it along four independent axes at once: a bed, a wristband, a slice of a finite pool deck, and a folio that keeps accruing arcade spend long after the guest has left the front desk. This document specifies the API that reconciles those axes. The property maintains a hard ceiling on the number of occupancy units that may be inside the waterpark at any one moment, and every room package, day pass, admitted group member, and cabana occupation draws against that same ceiling. Because the ceiling is shared, the system has to decide, at the moment of booking rather than at the moment of arrival, how many units each commitment will consume and on which service date.

The product surface spans the whole guest relationship. A room package bundles waterpark passes for everyone the room sleeps, priced from the room's nightly rate and the number of nights, with arcade credit folded into the underwriting so that a family's first evening at the arcade is already paid for. Day passes are sold against a separately capped allocation so that hotel guests are never crowded out by walk-in traffic. Wristbands carry more than admission: a reservation guest's band encodes the right to post charges back to the room folio, bounded by an arcade ceiling derived from the size of the party. Attractions — slides, pools, play structures — open and close against lifeguard coverage and water chemistry rather than against a schedule, and a failed water sample closes everything downstream of it, including the arcade credit lines attached to the bands that the closure invalidates.

Two constraints shape the engineering approach. First, capacity is a running sum over four contributors that are maintained by four different subsystems, so every mutating call must recompute rather than increment. Second, a resort day is not the wall-clock day: guests may enter the waterpark on their arrival date before the room is ready, and they retain access on their departure date after they have checked out, which means the platform's notion of "today" has to be an explicit, settable logical clock rather than the host machine's clock. The API is mounted beneath a property scope, `/resorts/{resort_id}`, so that every resource is addressed within the property that owns it.

## 2. Global Specifications & System-Wide Principles

This section collects the rules that hold across the whole API: how callers are identified, what every response looks like, how the platform orders its checks, how occupancy is totalled, and how mutations cascade.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the caller, and `X-User-Role` names the capacity in which the caller acts. A request that omits either header, or that names a role the platform does not recognise, is refused with `ERR_UNAUTHENTICATED` (HTTP 401). A request that supplies a recognised role but reaches for an operation outside that role's remit is refused with `ERR_FORBIDDEN` (HTTP 403), and so is a request in which an entity-backed role attempts to mutate a resource it does not own.

Six roles are recognised. Their names are spelled exactly `platform_ops`, `FrontDesk`, `AquaticsManager`, `GateAttendant`, `Group`, and `Anonymous`.

Five of the six are opaque roles. When `X-User-Role` is `platform_ops`, `FrontDesk`, `AquaticsManager`, `GateAttendant`, or `Anonymous`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it for audit purposes — the rotation roster stores entries of the form `<role>:<name>`, and the acting role forms part of that entry — but it never compares such an identifier against any entity's `id`. For `Anonymous` in particular, the header is required but no audit identifier is pinned, so any value is accepted; the capacity is deliberately limited to public inventory reads and to paying for arcade play against a band that has already been issued.

`Group` is the single entity-backed role. When `X-User-Role` is `Group`, `X-User-ID` is the `id` of the acting `GroupBooking`. Ownership checks on any resource that references a `GroupBooking` compare the resource's foreign-key field to `X-User-ID`; a `Group` caller whose `X-User-ID` differs from the `group_booking_id` it targets is refused with `ERR_GROUP_OWNERSHIP_MISMATCH` (HTTP 403). This check is what allows a group organiser to create a group booking only under its own identity, and to touch only the cabana bookings, activity bookings, group members, and room reservations that their own group owns.

Behaviour that is reserved to a single role — creating properties and room types, editing capacity ceilings, publishing the rotation roster, lapsing advance holds, releasing a booked cabana, advancing the logical clock, simulating the deposit gateway — is exclusive to `platform_ops`. Everything a role may do is enumerated operation by operation in §4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps how many resources are returned and defaults to 10 when the caller omits it; the value must be at least 1 and at most 100. `offset` states how many resources to skip from the start of the result set and defaults to 0. Both are optional on every list endpoint that accepts them.

Unless a listing is described otherwise in §3, resources are returned sorted by their creation timestamp in ascending order. Responses that carry a collection include the four pagination fields in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. Request Evaluation Order

Checks are not applied in the order a reader happens to encounter them; they are applied in a fixed cascade, the first failure short-circuits everything after it, and the resulting `error_id` is therefore observable. Two endpoints that both require a pool to be open but only one of which also requires a staffed attraction will surface different codes for the same underlying disorder, purely because of position in the cascade. The order below is normative.

At the head of the cascade, authentication is evaluated first: both headers must be present and the role must be recognised, otherwise `ERR_UNAUTHENTICATED` is returned; a request body carrying a field that the target endpoint does not declare among its inputs is refused at this same stage with `ERR_INVALID_REQUEST`. Authorisation follows, yielding `ERR_FORBIDDEN` when the acting role is not permitted for the operation or an entity-backed role does not own what it is mutating.

Existence is checked third, and always left to right along the request path: `ERR_NOT_FOUND` names the first identifier — path segment or referenced foreign key — that does not resolve under the named property. Only after all identifiers resolve does the platform start applying business rules.

The remaining checks run in this order: the service-date horizon (`ERR_SERVICE_DATE_OUT_OF_RANGE`, which guards day-pass sales and group bookings, and fires when the requested `service_date` falls more than 365 days after the property's current service date); target state admissibility (`ERR_INVALID_STATE`, guarding every state-transition operation); pool posture (`ERR_POOL_CLOSED`, guarding gate admission posting and wristband activation); attraction readiness (`ERR_ATTRACTION_NOT_OPEN`, guarding gate admission posting and activity-session creation); physical plausibility of a submitted water reading (`ERR_WATER_QUALITY_OUT_OF_RANGE`); cabana overlap and capacity (`ERR_CABANA_DOUBLE_BOOKED` and `ERR_CABANA_UNITS_UNAVAILABLE`); the day-pass ceiling (`ERR_DAY_PASS_CAP_EXCEEDED`); the park capacity ceiling (`ERR_PARK_CAPACITY_EXCEEDED`); the arcade ceiling (`ERR_ARCADE_LIMIT_EXCEEDED`); the birthday-party minimum (`ERR_GROUP_MINIMUM_NOT_MET`); and finally the deposit requirement together with gateway acceptance (`ERR_PAYMENT_DECLINED`).

Because compliance and safety checks sit above capacity checks in this list, a booking that would both breach a ceiling and clash with a standing closure reports the closure, not the ceiling. Implementers should treat the sequence as part of the contract, not as an implementation detail.

### 2.5. The Occupancy-Unit Ledger and Park Capacity

Capacity at a waterpark resort is measured in a single unit — an *occupancy unit*, the accounting quantity equal to one guest admitted — and a property declares, once, the largest number of occupancy units that may be inside the waterpark concurrently. That ceiling is `park_capacity_occupancy_units`, an integer of at least 1. It is not a per-day allocation and it is not a daily total; it bounds a running balance.

Four independent contributors consume against the ceiling on any given service date. Room packages reserve units while a stay is live; day passes reserve units for the single date they admit; confirmed groups reserve the units their checked-in members occupy; and cabana and party-room occupations reserve the units the group intends to seat. The property also publishes, per service date, a separate and much smaller allocation — `day_pass_cap_units`, an integer of at least 0 and no greater than `park_capacity_occupancy_units` — that bounds only the third-party traffic. A property's own representation reports the resulting commitment as a single `day_pass_reserved_units` figure carried alongside the two ceilings, read as the day-pass contribution to the ledger for the property's *current* service date. Day passes may not consume more units on a date than that cap allows, so hotel guests are structurally protected from being displaced by walk-ins even when the park ceiling itself has room.

The consolidated view of this ledger is exposed per service date by a capacity read that reports the requested `service_date` together with the room contribution, the day-pass contribution, the group contribution, the cabana contribution, the total `occupancy_units`, the property's `park_capacity_occupancy_units` and `day_pass_cap_units`, and the resulting `capacity_remaining_units`. Stated as a rule, the total `occupancy_units` for a service date is the sum of the room contribution, the day-pass contribution, the group contribution, and the cabana contribution for that date, taken in that order, and `capacity_remaining_units` is the property's `park_capacity_occupancy_units` minus that total. An attendance-console variant of the same read reports the `service_date`, the `occupancy_units`, and the `capacity_remaining_units` alone.

The two ceilings themselves may be revised after the property exists, but only by `platform_ops` and only against a supplied expected version of the property, so that a ceiling may not be changed out from under a caller who has already priced a sale against it. Such an edit accepts any subset of `park_capacity_occupancy_units`, `day_pass_cap_units`, and the arcade rate `arcade_credit_rate_cents_per_unit`, applying the same lower bounds those fields carry at creation and refusing with `ERR_INVALID_REQUEST` an edit that would leave `day_pass_cap_units` above `park_capacity_occupancy_units` once the supplied values are read together; on success the property's `version` is incremented. The day-pass contribution is a derived figure, recomputed on every read rather than stored, so revising a ceiling needs no separate recomputation step to bring it into line.

A newly created property begins with its `pool_posture` already `OPEN`, an `ops_run_index` of 0, `manager_override_used` false, and an empty rotation roster.

Remaining capacity is never reported as a negative number. An operation that would push the total above the ceiling is refused with `ERR_PARK_CAPACITY_EXCEEDED` (HTTP 409) rather than being stored and clamped, and the same ceiling is enforced separately against the day-pass allocation with `ERR_DAY_PASS_CAP_EXCEEDED` (HTTP 409) when the day-passed units alone would overrun `day_pass_cap_units`. Both ceilings are inclusive at their boundary: a request that lands exactly on the limit is accepted, and a request one unit beyond it is rejected.

Two administrative state fields accompany the capacity configuration. `manager_override_used` is a boolean that starts false and is set true when a capacity manager override is applied for the current service date, recording that an out-of-policy admission was deliberately authorised — it is a record that a ceiling was deliberately crossed on authority, not a licence to cross it silently. `ops_run_index` is a monotonic integer counter, starting at 0, that is incremented by each housekeeping pass so that repeated maintenance runs can be distinguished from one another.

### 2.6. The Logical Clock and the Resort Service Date

The property's "today" is not the host machine's date. Each property carries a logical clock whose startup value is exactly `2026-09-01T00:00:00Z`; before any clock call the logical clock reads that instant, and it never falls back to wall-clock time. A test-driving capability available to `platform_ops` advances the logical clock to a supplied `to_iso8601` instant and answers with the resulting `current_utc` and the derived `service_date`.

Advancing the clock is a mutation, not a read. It expires reservations whose `departure_date` falls strictly before the new service date and releases their room units; expires wristbands whose `valid_on_service_date` plus one day falls strictly before the new service date, stamping `access_denied_reason` as `SERVICE_DATE_EXPIRED`; expires day passes whose `service_date` falls strictly before the new service date; expires cabana holds whose `hold_expires_at` is at or before the new instant and releases their cabanas; and recomputes `pool_posture`. The room contribution to the occupancy ledger is not a stored quantity but a running sum read per service date, so the clock advance needs no explicit recomputation of it: the ledger already reflects the new date, with lapsed reservations no longer contributing and every surviving commitment re-read against the dates it spans. Group bookings are not swept by the clock; a group lapses only through its own cancellation.

Service-date decisions the platform makes — which units a booking consumes, whether a band is stale — are resolved against this logical clock rather than against the instant the request happened to arrive.

### 2.7. Common Resource Properties

Resources created by this API carry a standard set of server-managed fields. `id` is a unique, server-minted identifier formatted as a UUID, used for identity only and carrying no type prefix or embedded meaning. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first persisted. `updated_at` is an ISO 8601 UTC timestamp in the same format recording when the resource was last modified. `version` is an integer that starts at an initial value and increments by one on every mutation of the resource, including mutations performed on the resource's behalf by a cascading operation elsewhere in the system.

Most resources carry the full quartet. Several do not: `RoomType`, `Attraction`, `ArcadeCreditGrant`, `GroupMember`, and `ActivitySession` carry only `id` and `created_at`. Those five resources have no `updated_at` field and no `version` field at all, and clients must not expect either to appear in their representations.

### 2.8. Precision, Rounding, and Monetary Representation

All monetary amounts are whole numbers of cents carried in integer fields whose names end in `_cents`, and all rate configuration — the arcade credit rate, the room base rate, the day-pass base and block charges, the activity base price — is likewise expressed in integer cents. No monetary value is ever transported as a decimal string.

Where a calculation produces a fractional result before it is stored, the platform rounds half up. The package rate, the day-pass price, the activity rate, the activity refund, and the arcade credit accrual are all resolved to whole cents under round-half-up with no intermediate truncation: intermediate terms are carried at full precision and only the value stamped onto the resource is rounded. The single exception is the activity-session opt-in ratio, which is a dimensionless ratio rather than money and is stored to four decimal places under the same round-half-up rule. Floors used inside a formula — the day-pass volume block and the activity bulk-discount block — are explicit flooring steps applied before the final half-up rounding, not a substitute for it.

### 2.9. Optimistic Concurrency Control

Two write operations are protected against stale state, and only those two. The first is day-pass creation, addressed within the property that publishes the ceiling the sale is measured against; the request body must carry `expected_resort_version`, a non-optional integer field naming the caller's last observed `version` of that property. The second is cabana-hold creation, addressed within the property that owns the cabana being held; the request body must carry `expected_cabana_version`, a non-optional integer field naming the caller's last observed `version` of that cabana.

In each case, if the supplied value does not match the parent entity's current `version`, the request is refused before any resource is created: the mismatched day-pass sale is refused with `ERR_STALE_RESORT_VERSION` (HTTP 412) and the mismatched cabana hold with `ERR_STALE_CABANA_VERSION` (HTTP 412). The rationale for confining the check to these two operations is that both are admissions decisions taken against a view of availability — the property's remaining capacity and day-pass headroom in one case, the cabana's availability and the surrounding occupation window in the other — that can have moved on since the caller read it.

The staleness check is a comparison against current state, not a claim about timing. A create whose supplied version matches the parent's current version proceeds regardless of what else is happening, and a create whose supplied version has fallen behind is refused regardless of whether any other request is in flight. Endpoints not named in this subsection take no version field at all; the remaining writes are guarded by their own state and capacity preconditions instead, as described in §2.4 and §3.

### 2.10. Cascading Effects on Parent and Sibling Resources

State changes ripple outward. When a booking is cancelled, the occupancy units it held are returned, but the cancellation itself is refused while any wristband the booking owns is still live, so the platform never has to invalidate a band on this path; when a booking is checked out, the occupancy units it held are returned and every wristband it owns is invalidated; when a group's last occupation is released, its members are un-checked-in; when a closure is recorded, the bands on today's service date are revoked and the arcade grants they carried are declined in the same transaction. These cascades are not deferred and they are not eventually consistent — the platform resolves every dependent resource within the transaction that triggered the change, and a caller that reads a child immediately after mutating its parent observes the post-cascade state.

Two conventions govern how cascades are reported. First, a cascade never republishes a different status code than the operation that triggered it succeeded with; a successful check-out that revokes nine bands still answers `200 OK` with the booking. Second, cascading mutations advance the `version` and refresh `updated_at` of the resources they touch where those fields exist, so a client holding a cached copy of a revoked band sees a version bump even though the band's own write operation was never called.

A cascade into a resource that carries neither field — an `ArcadeCreditGrant` or a `GroupMember`, for instance — is observable through changed field values rather than through a version bump.

### 2.11. Nested Retrieval and Path Scoping

Retrieval paths may name several resources in a single URL, and when they do the identifiers are resolved left to right, one step at a time. The property segment is resolved first, then each successive segment within the property it belongs to. The walk stops at the first identifier that does not resolve under the resource that precedes it, and the caller receives `ERR_NOT_FOUND` (HTTP 404). A request that names a wristband under a property that does not exist is refused for the property, and the platform never goes on to ask whether the wristband exists at all.

This ordering also applies to creation and modification operations whose body carries a foreign-key input rather than a path segment: a referenced resource is resolved before any business rule is evaluated, and a missing referent is reported as `ERR_NOT_FOUND` regardless of what other rule the request might also have violated.

Because every resource belongs to exactly one property, the scoping is enforced rather than merely conventional. An identifier that exists but belongs to a different property is not found within the requested property, and the response distinguishes nothing further.

## 3. Business Logic & Workflows

### 3.1. Booking a Room Package and How It Is Priced

Room inventory is the raw material this workflow consumes, and a property's catalogue of `RoomType` records is maintained by `platform_ops` alone. Each room type is described by a short `code` such as `WOLF_SUITE`, a `max_occupancy` stating the largest party the type may sleep, a `base_rate_cents` giving the nightly rate before package surcharges, and an `is_cabana` flag that marks the type as a poolside cabana rather than a sleeping room and defaults to false when omitted. Room types can be listed per property and fetched individually. A room type carries only an `id` and a `created_at`; it is reference data rather than a mutable transactional record, so it has neither an `updated_at` nor a `version`.

A `FrontDesk` agent or a `Group` organiser opens a stay by supplying the room type to occupy, the size of the party, and the travel dates. `room_type_id` names the `RoomType` being booked; `guest_count` declares how many registered guests the booking covers and must number at least 1 and no more than that room type's `max_occupancy`; `arrival_date` and `departure_date` are service dates written as `YYYY-MM-DD` and carry the property scope's `resort_id`. A booking created in this way begins in `RESERVED` booking status and `NOT_STARTED` stay status, and neither `checked_in_at` nor `checked_out_at` holds a value until the corresponding front-desk action occurs. The booking's `booking_status` is one of `RESERVED`, `CHECKED_OUT`, or `CANCELLED`, and its separately tracked `stay_status` is one of `NOT_STARTED`, `IN_HOUSE`, or `DEPARTED`. A payload that omits a required field, that declares a field the booking operation does not accept, or that carries a `guest_count` outside its bounds is refused with `ERR_INVALID_REQUEST` (HTTP 400).

Three derived quantities are stamped at creation and are not accepted from the client. `nights` is the number of nights between `arrival_date` and `departure_date`. `waterpark_included_units` always equals `guest_count` — every registered guest is entitled to a waterpark pass as part of the package, and the platform never issues a booking with fewer bundled passes than registered guests — and `reserved_units` is initialised to `waterpark_included_units` so that the arrival-day commitment is on the ledger from the moment the booking exists, before anyone has arrived.

Pricing is where the package becomes concrete, and the arithmetic runs in a pinned order. Start from the room subtotal: the number of `nights` multiplied by the room type's `base_rate_cents`. In parallel, the bundled arcade credit is underwritten at twice the nightly room rate for each night of the stay — that is, `base_rate_cents` multiplied by 2 and then by `nights` — so a family's first evenings at the arcade are prepaid inside the package rather than settled later. A room-fee surcharge then applies on a stepped basis. When `waterpark_included_units` is at most the room type's `max_occupancy` minus 2, the party is at or below par and the surcharge is zero. Otherwise the surcharge is the number of complete groups of four guests in `waterpark_included_units` — any remainder discarded, since the division is floored — multiplied by the room fee actuation constant of 1400 cents. The underwritten total of the package is the sum of the arcade half and the room subtotal. The amount actually authorised against the guest's debit instrument, which is what lands in `package_rate_total_cents`, is the underwritten total plus the surcharge, so the surcharge enters the authorised figure once.

Two ordering rules bind this evaluation and are part of the contract rather than an implementation preference. The bundled pass count is read from the requested `guest_count` before any surcharge term is evaluated, and the surcharge amount is never fed back into the par test that decides whether a surcharge applies at all. Both rates are whole cents and the final stored value is rounded half up to whole cents, with no truncation of intermediate terms.

The same booking also carries `package_rate_withheld_cents`, which answers a different question: what the guest is debited if the room fee is withheld from the authorisation hold rather than collected up front. That figure is the arcade half plus the room subtotal, with no surcharge at all. The two fields therefore differ by exactly the surcharge, and they coincide only when the party is at or below par — that is, only when `waterpark_included_units` is at most `max_occupancy` minus 2. In operational terms the platform debits the withheld figure during the stay and the full figure once the room fee is posted at check-out, so the same booking carries one during the visit and the other at its close. Both figures are governed by the same round-half-up rule to whole cents, and both are recalculated whenever a booking's `guest_count` or room type changes.

An existing booking in `RESERVED` status may be revised by a `FrontDesk` agent, supplying any subset of `room_type_id`, `guest_count`, `arrival_date`, and `departure_date`. The revision recalculates `package_rate_total_cents` and `package_rate_withheld_cents`, recomputes the room contribution to the occupancy ledger across both the old and the new service-date spans so that no orphaned units are left behind on the abandoned dates, and increments the booking's `version`. A revision attempted against a booking that is not `RESERVED` is refused with `ERR_INVALID_STATE`.

A booking in `RESERVED` status may also be cancelled by a `FrontDesk` agent, and cancellation requires the booking to own no live band: if any wristband linked to the booking still carries `wristband_status` in either `ISSUED` or `ACTIVE`, the request is refused with `ERR_INVALID_STATE` — the bands must be dealt with first, on the same principle that governs day-pass voiding. On success the booking moves to `CANCELLED`, its stay moves to `DEPARTED`, `reserved_units` is set to 0, and the `version` is incremented; the cancellation does not itself invalidate any band.

One external dependency sits in front of booking creation. If the authorising gate refuses the package or day-pass total at the moment the charge is placed, the booking is not created and the caller receives `ERR_DECLINED_AUTHORIZATION` (HTTP 402).

### 3.2. Arrival Day, Check-In, and the Shape of a Stay

The waterpark day does not begin when the room does. A booking in `RESERVED` status with `NOT_STARTED` stay status is admitted to the waterpark on its own `arrival_date` — guests may swim before the room is ready — and it is exactly this that makes the arrival-date unit commitment real from the moment of booking rather than from the moment of check-in. The room contribution to the occupancy ledger is defined per service date. Written out, for a service date `d`, `room_units_reserved` is the sum of `reserved_units` across all non-terminal reservations whose `arrival_date` is on or before `d` and whose `departure_date` is strictly after `d`. Each reservation's `reserved_units` equals its `waterpark_included_units` on every service date in the half-open span from `arrival_date` inclusive to `departure_date` exclusive. A booking that has been cancelled consumes zero units on every date; a booking that has been checked out consumes zero units on its `departure_date`. When the sum is materialised the reservations are ordered by `created_at` ascending, and the reservation identifier is deliberately not consulted as a tie-break.

Check-in is a front-desk action that moves the stay from `NOT_STARTED` to `IN_HOUSE`. It requires that the booking still be `RESERVED` and that its stay has not already started; a booking in any other combination of statuses is refused with `ERR_INVALID_STATE`. The transition is unusually broad in what it sets in motion. `checked_in_at` is stamped. `reserved_units` is set to `waterpark_included_units`, and the room contribution for the `arrival_date` is increased by that same count. The day-pass contribution is recomputed for both `arrival_date` and `departure_date`, because a stay's arrival reshapes the walk-in headroom on the day the guests enter and on the day they leave. `credited_arcade_cents` is computed as an accrual: the property's `arcade_credit_rate_cents_per_unit` multiplied by the booking's `waterpark_included_units`, rounded half up to whole cents.

The same check-in rebalances who holds what. Every guest band linked to this booking gains `room_charge_enabled` set true and an `arcade_credit_limit_cents` equal to the property's `arcade_credit_rate_cents_per_unit` multiplied by the booking's `waterpark_included_units` — that is, the whole party's arcade ceiling is spread across the party's bands. Simultaneously, every day-pass band whose `valid_on_service_date` is this booking's `arrival_date` is revoked outright, moving to `REVOKED` with `access_status` `DENIED`; the platform treats a room package's arrival as displacing the walk-in allocation on that date. Group-member room-charge privileges on the arrival date are disabled on the same principle. The booking's `version` is incremented once for the whole transaction.

Check-out closes the room while deliberately leaving the waterpark open for the rest of the day. It is refused with `ERR_INVALID_STATE` when the booking's `booking_status` is neither `RESERVED` nor `CHECKED_OUT` — that is, once it has been cancelled, or once the logical clock has already lapsed it — while a booking that is still `RESERVED`, including one that has never checked in at all, and a booking that is already `CHECKED_OUT` are both accepted. The transition moves booking status to `CHECKED_OUT` while the stay moves to `DEPARTED` and `checked_out_at` is stamped. Departure-day access is retained: guest bands are not expired on the departure date itself but only on the next service date that is not the departure date. At the moment of check-out, however, the financial relationship is severed in full. Every guest band linked to the booking is expired, carrying `access_denied_reason` of `CHECKED_OUT`; `room_charge_enabled` is set false on every one of them; and every arcade credit grant that had succeeded on those bands is declined with a `decline_reason` of `RESERVATION_CLOSED`, so the folio can no longer grow after the guest has gone. The room contribution for the `departure_date` is decremented by the booking's `reserved_units`, and `pool_posture` is recomputed. The booking's `version` is incremented.

A check-out is refused when the account is still dirty. If any guest band linked to the booking that is still in `ISSUED` or `ACTIVE` status carries `arcade_credit_spent_cents` greater than zero at the moment of check-out, the close-out is refused with `ERR_ACCOUNT_LIEN_OUTSTANDING` (HTTP 409); a band that has already left the live set — expired, revoked, or re-issued — no longer blocks the close. The front desk must settle or decline the outstanding grants first. A check-out posted against a booking that has already been checked out is not refused: it still moves the stay from `IN_HOUSE` to `DEPARTED`, re-stamps `checked_out_at`, and increments the booking's `version`, and it leaves departure-day waterpark access exactly as it was, because bands are expired only on the next service date that is not the departure date.

### 3.3. Wristbands: Issuance, Room-Charge Privilege, Activation, and Re-Issuance

A wristband is the physical and financial token of the visit, and a single band answers three separate questions: who holds it, whether it may enter the waterpark right now, and whether it may spend against a room folio. Issuance is performed by a `platform_ops` administrator or a `FrontDesk` agent against the property, supplying `holder_type`, the `owner_name` to be printed on the band, and whichever of `reservation_id`, `day_pass_id`, or `group_member_id` identifies the holder. The holder classification is one of `RESERVATION_GUEST`, `DAY_PASS_GUEST`, or `GROUP_MEMBER`; a reservation guest's band names the owning booking through `reservation_id`, a day-pass guest's band names the owning pass through `day_pass_id`, and each of those two references is absent for the other classification. The band's `owner_name` is a free-text label and carries no uniqueness requirement.

A newly issued band starts in `ISSUED` wristband status with `PENDING` access status, and its `valid_on_service_date` defaults to the holder's own operative date — the linked reservation's `arrival_date` for a reservation guest, the linked day pass's `service_date` for a day-pass guest, or the linked group's `service_date` for a group member — unless the caller supplies `valid_on_service_date` explicitly. A band naming the holder classification that does not also carry that classification's reference is refused with `ERR_INVALID_REQUEST`. The band's `wristband_status` runs through `ISSUED`, `ACTIVE`, `REVOKED`, `EXPIRED`, and `REISSUED`, while the independent `access_status` runs through `PENDING`, `GRANTED`, and `DENIED`; the two move together but answer different questions, and a client must read both.

Room-charge privilege is granted at issuance only under a narrow condition, and it is the reason issuance is not simply a status write. When `holder_type` is `RESERVATION_GUEST` *and* the linked booking's `stay_status` is already `IN_HOUSE`, the band is issued with `room_charge_enabled` true and `arcade_credit_limit_cents` equal to the property's `arcade_credit_rate_cents_per_unit` multiplied by the linked booking's `waterpark_included_units`. In every other case — a day-pass or group-member band, or a reservation guest whose booking has not yet checked in — the band is issued with `room_charge_enabled` false and `arcade_credit_limit_cents` set to 0. Guests who issue their bands before checking in therefore acquire spending power only when the booking itself is checked in, at which point the same privilege is conferred by the check-in transaction described in §3.2.

Activation converts an issued band into an admitted one and reserves its occupancy units. It is performed by a `FrontDesk` agent or by a `GateAttendant` at the gate, and the band must be in `ISSUED` status; any other status yields `ERR_WRISTBAND_NOT_ACTIVE` (HTTP 409). Beyond the status itself, four conditions are evaluated in the order given in §2.4. A band held by a reservation guest requires the linked booking to be `IN_HOUSE`. A band held by a day-pass guest requires the linked pass to be `RESERVED`. The property's `pool_posture` must be `OPEN`, failing which the request is refused with `ERR_POOL_CLOSED` (HTTP 409). Finally, the total of the room, group, and day-pass contributions on the band's service date, taken together, must not exceed the property's `park_capacity_occupancy_units`; a breach is refused with `ERR_PARK_CAPACITY_EXCEEDED` (HTTP 409). A successful activation moves the band to `ACTIVE` with `access_status` `GRANTED`, recomputes the room contribution for the band's `valid_on_service_date`, recomputes `pool_posture` from the property's current non-terminal water readings, and increments the band's `version`.

A wristband may leave `ISSUED` without ever having been activated, and this happens automatically in two situations that are deliberately given the same destination. When a booking is checked in, every day-pass band whose `valid_on_service_date` equals that booking's `arrival_date` is moved from `ISSUED` to `REVOKED`. Separately, when a failed water reading is recorded on a service date on which a check-in has already occurred, every guest band on that service date is moved from `ISSUED` to `REVOKED`. Both land on `REVOKED` with `access_status` `DENIED`, `room_charge_enabled` false, and `arcade_credit_limit_cents` 0; the two are distinguished by the circumstance that caused them rather than by any difference in the resulting state, and the platform records no separate status for either.

Revocation of a band that is already active is a deliberate front-desk or aquatics action, and it is gated by how far into the day the band's holder has got. It requires `ACTIVE` status, and it additionally requires that either the band's `valid_on_service_date` has not yet begun, or the band has no accepted admission event with an `IN` direction on that service date — in other words, a guest who has already entered the waterpark today cannot have their band pulled out from under them. `AquaticsManager` may also invoke revocation as the downstream consequence of a pool closure. The state change is the same in both cases: `REVOKED` with `access_status` `DENIED`, `room_charge_enabled` false, `arcade_credit_limit_cents` 0, and the band's `version` incremented. In addition, every arcade credit grant on that band whose `grant_status` is `SUCCEEDED` is moved to `DECLINED` with a `decline_reason` of `WRISTBAND_REVOKED`, so the folio is unwound along with the band. Where the revocation reduces the linked attraction's occupant count below that attraction's `min_occupancy_units`, the attraction is downgraded to `CLOSED` as a consequence.

Re-issuance handles the lost-band case and is confined to a `FrontDesk` agent. Exactly three conditions must hold. The band must be `ACTIVE` — anything else yields `ERR_WRISTBAND_NOT_ACTIVE`. The band must not already have been re-issued, which is to say its `superseded_by_wristband_id` must be null; a band that has already been superseded is refused with `ERR_WRISTBAND_ALREADY_REISSUED` (HTTP 409). And the band must carry no arcade spend: if its `arcade_credit_spent_cents` is greater than zero the request is refused with `ERR_HELD_UNITS_NOT_RELEASABLE` (HTTP 409), because the credits already drawn against the band cannot be transferred to a replacement. Issuing a successor must also fit within capacity: the successor occupies the same service date, so if creating it would push the room, group, and day-pass contributions on that date above the property's `park_capacity_occupancy_units`, the request is refused with `ERR_PARK_CAPACITY_EXCEEDED`.

The re-issuance transaction touches both bands and the booking behind them. The presented band moves to `REISSUED` with `access_status` `DENIED`, `room_charge_enabled` false, `arcade_credit_limit_cents` 0, and `superseded_by_wristband_id` naming the successor; its `version` is incremented, and the response to the operation is this old band rather than the successor, so that the successor's identifier can be read back from `superseded_by_wristband_id`. The successor is created in `ISSUED` status with `access_status` `PENDING`, carrying the old band's `arcade_credit_limit_cents` forward unchanged and starting with `arcade_credit_spent_cents` of 0, and it is issued for the same `valid_on_service_date` as the band it replaces. Because the successor occupies the same service date as the band it replaces, the owning booking's `reserved_units` is recomputed and the room contribution for the successor's `valid_on_service_date` is recomputed. The successor's own version and timestamps begin afresh, and the supersession link is one-directional at rest: the old band names its successor, and the successor carries no back-reference — the list of bands that superseded a given band is retrievable separately, so a replacement chain can be walked in the other direction as well.

A band that has been active but never used lapses on its own. When the logical clock advances such that a band's `valid_on_service_date` plus one day falls strictly before the property's current service date, an `ACTIVE` band moves to `EXPIRED` with `access_status` `DENIED`, `access_denied_reason` of `SERVICE_DATE_EXPIRED`, and a bumped `version`. The day of grace is deliberate: departure-day access must survive a check-out, so a band is not considered stale until the day after its service date has wholly passed.

For a band that reaches the gate in a state that does not permit entry, the platform reports `ERR_WRISTBAND_NOT_ACTIVE` (HTTP 409) — covering both a band whose `wristband_status` is not `ACTIVE` and a band whose `access_status` is not `GRANTED` when presented at a gate or at an arcade post. Reason text describing why access was withheld is stamped onto `access_denied_reason` when `access_status` is `DENIED` and is null at all other times.

### 3.4. Arcade Credit: Ceilings, Grants, and the Room Folio

Arcade spend at this property is not a cash transaction. It is a credit line drawn against the room folio and capped by the size of the party that bought the package. Each band carries a ceiling in `arcade_credit_limit_cents`, set at issuance or conferred at check-in; the amount drawn so far is `arcade_credit_spent_cents`, defined as the sum of the `amount_cents` of every arcade credit grant on that band whose `grant_status` is `SUCCEEDED`; and the amount still available is `arcade_credit_remaining_cents`, defined as the ceiling minus the amount drawn, floored at 0 so that an over-drawn line never reports a negative balance.

A grant is requested either against the band directly or against the reservation that owns the band. The reservation route and the arcade-redemption route both carry a body naming the `wristband_id` being charged together with an `amount_cents` integer of at least 1; the direct grant route names the band in the path and its body carries `amount_cents` alone, so a `wristband_id` supplied alongside it is an undeclared field. `FrontDesk` and `Anonymous` may post a charge against a folio, the latter so that a guest can top up their own band from their phone at the arcade. A grant attempted against a band whose `room_charge_enabled` is false is refused with `ERR_ROOM_CHARGE_DISABLED` (HTTP 409) — this is the code a guest sees when they try to spend before check-in, or after check-out has disabled their band — and the check is applied before the ceiling comparison, so a disabled band reports the disabled code even when the amount would also overrun. A grant whose amount exceeds the band's remaining credit is refused with `ERR_ARCADE_LIMIT_EXCEEDED` (HTTP 402). A grant that fits is recorded with `grant_status` `SUCCEEDED`, and the band's drawn and remaining balances are recomputed. An arcade redemption posted by a `FrontDesk` agent against a band follows the same three rules and the same resulting balances.

### 3.5. Day Passes, the Walk-In Allocation, and Gate Admissions

A day pass is a single-date product sold against an allocation that exists specifically to keep walk-in traffic from displacing hotel guests. A `platform_ops` administrator or a `FrontDesk` agent sells passes by supplying the `service_date` they admit on, the number of `units_requested`, and the `expected_resort_version` described in §2.9; one unit admits one guest, so `units_requested` must be at least 1. A new pass begins in `RESERVED` day-pass status and passes through `ADMITTED`, `VOID`, or `EXPIRED` later in its life.

The price of the pass is a per-unit charge plus a stepped volume addition, and the shape of the addition is the single easiest thing to get wrong in this domain. The per-unit component is `units_requested` multiplied by the day-pass base charge of 4200 cents. The volume component is discontinuous: subtract the 10-unit base allowance from `units_requested`, discard the result entirely if it is negative, divide what remains by the 10-unit block size with any remainder discarded, and multiply the number of complete blocks by 1000 cents. The number of complete blocks is therefore the floor of the excess over ten units divided by ten. Read as a formula, the surcharge applies to every complete ten-unit block above the first ten units, counting blocks from the eleventh unit rather than from the twenty-first, so ten units attract no addition at all, eleven through twenty units attract exactly 1000 cents, and twenty-one through thirty units attract 2000 cents; a partial block adds nothing — a hundred and twenty units attract eleven complete blocks and 11000 cents, the same addition as a hundred and eighteen units. Importantly, the ten-unit allowance is a *floor on the surcharge*, not an alternative rate: the base charge of 4200 cents applies to every unit including the first ten. Twelve units therefore cost twelve times 4200 cents plus a single block of 1000 cents, and not ten units at the base rate plus two units at the block rate. The total, once summed, is stored in `price_total_cents` as whole cents rounded half up.

The walk-in allocation is enforced per service date through `day_pass_reserved_units`, defined as the sum of `units_requested` across every day pass whose `service_date` is that date and whose `day_pass_status` is either `RESERVED` or `ADMITTED`. Passes that have been voided or expired contribute nothing to the sum. A sale or an admission that would push the day-passed total above the property's `day_pass_cap_units` is refused with `ERR_DAY_PASS_CAP_EXCEEDED` (HTTP 409), and the boundary is inclusive — a request that lands exactly on the cap is accepted.

The property's separate chronological horizon applies here and to group bookings alone: a `service_date` set more than 365 days after the property's current service date is refused with `ERR_SERVICE_DATE_OUT_OF_RANGE` (HTTP 409). No other product is date-bounded in this way.

A pass that will not be used is voided, and a pass that was never used by its date lapses. Voiding, which a `FrontDesk` agent may perform, requires the pass to be `RESERVED` and requires that no band of holder classification `DAY_PASS_GUEST` referencing that pass still carries `wristband_status` in either `ISSUED` or `ACTIVE` — a pass with live bands must have the bands dealt with first. Voiding moves the pass to `VOID` and recomputes the day-pass contribution for its service date. A pass left `RESERVED` past its date is moved to `EXPIRED` when the logical clock advances, with the same contribution recomputation. Movement from `RESERVED` to `ADMITTED` is not a direct front-desk action at all; it is the automatic consequence of a guest presenting at the gate, described next.

Admission and exit at the waterpark gate is posted by a `GateAttendant` and is the operation that converts a reservation of units into actual occupancy. The gate post names the `wristband_id` presented, the `service_date` the crossing is posted against, and the `direction`, which is either `IN` or `OUT`. Because the gate is also where a day pass becomes real, a day pass moves from `RESERVED` to `ADMITTED` as a consequence of an accepted `IN` crossing by a band whose holder classification is `DAY_PASS_GUEST`. That acceptance requires the pass to still be `RESERVED`, requires the resulting day-passed total on the pass's service date to remain within `day_pass_cap_units`, and requires the consolidated total of the room, group, and day-pass contributions on that date to remain within `park_capacity_occupancy_units`. A day pass presented when fewer reserved units remain than the presenting band consumes is refused with `ERR_DAY_PASS_UNITS_EXHAUSTED` (HTTP 409).

Every gate crossing is recorded as an admission event carrying the resort scope, the presenting `wristband_id`, the `service_date`, the `direction`, an `event_status` of either `ACCEPTED` or `REJECTED`, and a `units_delta`. The delta is the sign-carrying occupancy movement of the crossing: the band holder's units added on an `IN`, subtracted on an `OUT`, and exactly 0 on any crossing that was rejected. Admission events are addressable individually by their own `admission_event_id` and can be listed per wristband, and the events recorded against a group's members can be listed from the group side. A crossing is accepted only when the band's `access_status` is `GRANTED` and the unit budget for that direction fits. The refusal checks are resolved before the band's own access status is read, and among themselves they run in this order: a day-pass band presented with fewer reserved units remaining than it consumes yields `ERR_DAY_PASS_UNITS_EXHAUSTED`; a breached day-pass allowance yields `ERR_DAY_PASS_CAP_EXCEEDED`; a breached park ceiling yields `ERR_PARK_CAPACITY_EXCEEDED`; and then, only for a band whose `access_status` is already `GRANTED`, a second `IN` for a group whose party has already been admitted yields `ERR_GROUP_SPLIT_ADMISSION`. Each of these is refused with its own error code rather than recorded, even when the presenting band's `access_status` is not `GRANTED`. Only a crossing that clears every check and still presents a band whose `access_status` is not `GRANTED` is recorded as `REJECTED` with a zero delta rather than refused outright, because the gate post itself succeeded and the outcome is the record. The presenting band's `version` is incremented by the crossing.

Group admission is deliberately atomic, and the platform refuses to split a party. A group's member units are admitted all at once: a successful first `IN` crossing for a group member admits the whole party, and after it the group booking's `group_reserved_units` reflects the full party's units rather than an incrementally built total — that recomputation reads every member of the group whose `checked_in` flag is true, including the presenting member, so a member who presents at the gate without having been checked in by a cabana confirmation still counts toward the total. A *second* successful `IN` crossing for the same group booking — that is, a second member presenting separately after another member of that group has already been admitted — raises `ERR_GROUP_SPLIT_ADMISSION` (HTTP 409), refused outright rather than recorded as a `REJECTED` event, since the platform declines to split the party at all. The first member through the gate leaves the group's reserved total at 0 because the units have been admitted rather than merely reserved; any later attempt to trickle members through individually is refused.

Two further gate conditions are inherited from §2.4 and apply to every crossing: the property's `pool_posture` must be `OPEN`, failing which `ERR_POOL_CLOSED` is returned, and the attraction-side readiness check yielding `ERR_ATTRACTION_NOT_OPEN` is evaluated before the capacity ceiling. The consolidated ceiling itself yields `ERR_PARK_CAPACITY_EXCEEDED` when the crossing would push the date's occupancy above `park_capacity_occupancy_units`, and the boundary is inclusive at that ceiling as it is at the day-pass cap.

### 3.6. Attractions, Lifeguard Coverage, and Rotation Discipline

An attraction is a body of water or a structure within the property, created by a `platform_ops` administrator or an `AquaticsManager` with a display `name`, a `min_occupancy_units` floor of at least 0, and a `required_certification` drawn from `LIFEGUARD` or `NONE`. A newly created attraction is `CLOSED`; it does not open because it was created but because it is staffed. Its `attraction_status` takes one of the three values `OPEN`, `LIMITED`, and `CLOSED`, and the platform derives that status from coverage rather than accepting it. Attractions can be listed per property and fetched individually; like room types, an attraction carries only an `id` and a `created_at`, with no `updated_at` and no `version`. The `min_occupancy_units` field states the smallest concurrent occupancy-unit load at which the attraction is expected to be open, and it is used as a staffing floor as described below.

Staffing is expressed as scheduled shifts. A shift names the `attraction_id` it posts to, the `staffer_name` posted, that staffer's `certification_code` of `LIFEGUARD` or `NONE`, the `shift_date`, a `start_minute` in minutes after midnight that must be at least 0 and at most 1439, an `end_minute` that must be greater than `start_minute` and at most 1440, and a `rotation_minutes` maximum of at least 1. The window is half-open: `start_minute` is included and `end_minute` is excluded. A scheduled shift begins in `SCHEDULED` status and moves among `ON_DUTY`, `ROTATED`, and the terminal `COMPLETED`; those four values are the whole of the `shift_status` enumeration. Shifts may be filtered on listing by attraction or by staffer, and a single shift may be retrieved by identifier using its own `shift_id`.

Coverage is computed from a rotation roster that the property publishes as an array named `managers`, holding staffing entries each written as a string of the form `<role>:<name>`. The roster starts empty and is mutated only through a `platform_ops`-only administrative operation that appends an entry formed from a supplied `async_role` and `async_name`; the property's `version` is incremented by that append. A staffer counts toward an attraction's coverage only when the roster carries an entry equal to that staffer's role-prefixed name for the shift in question. Staffers who are scheduled but not rostered do not open anything.

Starting a shift is an `AquaticsManager` action and it is where the certification rule bites. The shift must be `SCHEDULED`, and a staffer whose `certification_code` is not `LIFEGUARD` may not be posted to an attraction whose `required_certification` is `LIFEGUARD` — the barred direction is the uncertified staffer on a lifeguarded attraction; a `LIFEGUARD` staffer is accepted on a `NONE` attraction as well, since the equality between the two codes is not itself required. An attempt to post an uncertified staffer to a lifeguarded attraction is refused with `ERR_SHIFT_ROTATION_VIOLATION` (HTTP 409). Three rotation rules are then checked in the same way and share the same error code. First, no other shift for the same `staffer_name` and `shift_date` may be in `ON_DUTY` or `ROTATED` status with a window overlapping the new shift's `[start_minute, end_minute)`. Second, the shift's own duration — `end_minute` minus `start_minute` — may not exceed `rotation_minutes` plus the maximum consecutive minutes constant of 120; expressed in hours, a shift may not be posted for longer than its rotation allowance plus two hours, so a shift with a 60-minute rotation allowance may run at most three hours. Third, every already-`COMPLETED` shift for the same staffer on the same date must be separated from this shift's window by at least the rotation buffer constant of 30 minutes; in other words, a staffer coming off a completed shift needs a full half-hour of rest before the next posting begins. A shift that satisfies all four checks moves to `ON_DUTY`, the linked attraction's `attraction_status` is recomputed, and the shift's `version` is incremented.

Rotation off an attraction and resumption back onto it are separate `AquaticsManager` actions with asymmetric gates. Rotating off requires `ON_DUTY` status, requires that no other shift for the same staffer and date already be `ROTATED` with an overlapping window, and requires that no other shift for the same staffer and date be `ON_DUTY` with a `start_minute` earlier than the current shift's `end_minute` — that is, the staffer may not be holding two live postings at once. The shift moves to `ROTATED`, and crucially the linked attraction's status is left unchanged, because a rotated staffer still counts as covering the attraction for the purposes of the coverage calculation. Resuming from a rotation requires `ROTATED` status, requires that no other shift for the same staffer and date be `ON_DUTY` with an overlapping window, and adds a safety condition belonging to the water itself: every water reading already recorded for the linked attraction within the shift's `[start_minute, end_minute)` window on its `shift_date` must carry a `log_status` of `PASS`. A staffer may not resume posting to water that has failed a reading. A successful resumption returns the shift to `ON_DUTY` and recomputes the linked attraction's status.

Completing a shift is available from either `ON_DUTY` or `ROTATED` and moves the shift to the terminal `COMPLETED`, recomputing the linked attraction's status and incrementing the shift's `version`.

Attraction status is derived from coverage and from the daily load each rostered staffer has already carried. Briefly, the platform counts the shifts at an attraction that are in `ON_DUTY` or `ROTATED` and whose staffer appears on the rotation roster; it treats an attraction whose `min_occupancy_units` is 0 as having an effective floor of 1 rather than 0; and it compares the count against that floor. A count at or above the floor makes the attraction `OPEN`. A count of at least 1 but below the floor makes it `LIMITED`. A count of 0 makes it `LIMITED` when at least one rostered staffer for that date has not yet exhausted their daily cap, and `CLOSED` when every rostered staffer has. The daily cap is three completed shifts: `completed_today` counts a staffer's `COMPLETED` shifts on the date, and the staffer is exhausted once that count reaches 3. Two consequences of this construction deserve to be stated plainly. An attraction whose `min_occupancy_units` exceeds 1 can never leave `LIMITED` while staffed, because a single attraction posts at most one staffer at a time, so its count can never reach a floor above 1. And the operation that completes a shift recomputes the attraction downward as well as upward: an attraction becomes `LIMITED` while a rostered staffer remains under the daily cap, and `CLOSED` once every rostered staffer has reached it.

Housekeeping passes exist to close out occupations and refresh derived status. A `platform_ops` administrator or an `AquaticsManager` may run a pass against an attraction; the pass marks every cabana occupation that is `BOOKED` with a `service_date` strictly before the property's current service date as `COMPLETED` and returns its cabana to availability, recomputes the attraction's own status, and increments the property's `ops_run_index` so that successive runs are distinguishable.

A scheduled shift can also be retrieved on its own, and a shift that was never started simply never opens anything.

### 3.7. Water Chemistry, the Closure Protocol, and Reopening

Water quality is the one subsystem in this property that can shut down everything else, and it is deliberately authoritative. An `AquaticsManager` records a reading by naming the `attraction_id` whose body of water was sampled, the `sampled_at` instant the sample was taken, and three measurements: `ph_reading`, `free_chlorine_ppm`, and `turbidity_ntu`. The reading is preserved as a log with its own `resort_id`, those five inputs, a derived `log_status` of `PASS` or `FAIL`, a `closure_reason` text stamped when the reading drives a closure and left null on a pass, and a `superseded_at` instant that is null while the reading stands. Readings can be listed for a single attraction or for the property, filtered accordingly, and a single reading can be retrieved by identifier using its own `log_id`.

Two windows govern a submitted reading and they do quite different things. The first is a plausibility window: a reading whose pH falls outside the closed interval from 0 to 14, whose free chlorine falls outside the closed interval from 0.0 to 10.0 parts per million, or whose turbidity falls outside the closed interval from 0 to 50 nephelometric turbidity units is physically impossible and is rejected outright with `ERR_WATER_QUALITY_OUT_OF_RANGE` (HTTP 422). The second is the safe window, and crossing it is not an error at all: the reading is accepted, recorded, and classified. A reading fails — `log_status` of `FAIL` — when its pH lies outside the closed interval from 7.2 to 7.8, or its free chlorine lies outside the closed interval from 1.0 to 3.0 parts per million, or its turbidity exceeds 1.0 nephelometric turbidity units. A reading that sits inside all three bounds passes. In other words, a measurement can be perfectly plausible and still fail, and the failure drives a protocol rather than a rejection. A reading submitted for an attraction and instant that already carries a log is refused with `ERR_DUPLICATE_READING_AT_INSTANT` (HTTP 409).

The property's pool posture is a pure function of the standing failures, and it is what every gate and activation check consults. `pool_posture` is `CLOSED` when at least one water log for the property carries a `log_status` of `FAIL` and a null `superseded_at`; it is `OPEN` when every failed log for the property has a non-null `superseded_at`. The posture is derived, never set directly, and it is recomputed whenever a reading is recorded, whenever a failure is superseded, whenever a booking checks out, whenever a band is activated, and whenever a day pass is admitted — so the value is never more stale than the last mutating call.

Recording a failing reading sets off a cascade that reaches bands, folios, attractions, and the ledger, all inside the same transaction. Every wristband whose `valid_on_service_date` equals the service date the reading itself carries — the service date of its `sampled_at` instant, which is not necessarily the property's current service date at the moment the reading is logged — and whose `wristband_status` is in either `ISSUED` or `ACTIVE` is moved to `REVOKED` with `access_status` `DENIED`, `access_denied_reason` of `WATER_QUALITY_CLOSED`, `room_charge_enabled` false, and `arcade_credit_limit_cents` 0. Every arcade credit grant that had succeeded on any of those bands is declined with `decline_reason` `WRISTBAND_REVOKED`. Every attraction associated with the failed body of water is recomputed to `CLOSED`, and the recomputation treats the closed pool as contributing zero staffers — meaning a fully rostered attraction still closes, because coverage that cannot be delivered is not coverage. Every attraction holding a standing `FAIL` reading for that same service date is likewise closed, whether or not it is the body of water just sampled. The property's `pool_posture` is then recomputed and the property's `version` is incremented. A passing reading performs none of these side effects; it is recorded, if the property was already open nothing changes, and the posture is recomputed to confirm that.

Reopening is a separate, explicit act. An `AquaticsManager` records a later passing reading against the standing failed log by supplying a fresh `sampled_at` and a fresh set of `ph_reading`, `free_chlorine_ppm`, and `turbidity_ntu` measurements. The new passing reading is appended and the standing failure's `superseded_at` is stamped with the instant it was displaced by, `pool_posture` is recomputed, and the property's `version` is incremented. A failure whose `superseded_at` is non-null no longer holds the pool closed — it remains in the log for audit but has no operational effect — and the collision guard `ERR_DUPLICATE_READING_AT_INSTANT` protects the case where a reading is submitted for an instant that already carries a log. Because the closure cascade revokes bands rather than suspending them, reopening does not restore the revoked bands: a guest whose band was pulled when the pool closed needs a fresh band to come back in.

The water subsystem also feeds the attraction staffing calculation described in §3.6. When a failed reading stands for an attraction's service date, that attraction's staffer count is read as zero regardless of how many lifeguards are posted, so the attraction lands `CLOSED` even though its posted staffer count has not changed. A shift resumption is blocked by the same data for the same reason: no staffer may resume posting to water whose readings in their shift window are not all passes.

### 3.8. Groups, Party Inventory, Cabanas, and Deposits

Group business is the property's highest-variance revenue stream, and the platform handles it with an explicit deposit gate and a discrete pool of party inventory. A group booking is created by a `Group` organiser or a `FrontDesk` agent, naming the `group_kind` — one of `BIRTHDAY`, `SCHOOL`, `FAMILY_REUNION`, or `CORPORATE` — the `service_date` of the visit, the `member_count` declared for the group, and, optionally, an opening `deposit_paid_cents` which defaults to 0 when omitted. `member_count` must be at least 1, and a value below that bound is refused as a body-shape failure with `ERR_INVALID_REQUEST` (HTTP 400). A new group booking begins in `PENDING_DEPOSIT` status with `group_reserved_units` at 0; it moves to `CONFIRMED` and may end in `CANCELLED`. The service-date horizon of §3.5 applies here too: a group booking dated more than 365 days beyond the property's current service date is refused with `ERR_SERVICE_DATE_OUT_OF_RANGE`.

One group kind carries a minimum-size rule. A booking whose `group_kind` is `BIRTHDAY` must declare a `member_count` of at least the party minimum of 1 member — that is, the platform declines to accept a birthday booking with no members at all — and a booking that falls below it is refused with `ERR_GROUP_MINIMUM_NOT_MET` (HTTP 409).

Ownership is enforced at creation. A caller acting as `Group` must present an `X-User-ID` equal to the `id` of the group booking being created; a mismatch is refused with `ERR_GROUP_OWNERSHIP_MISMATCH` (HTTP 403). `FrontDesk` may create a group booking on a group's behalf, and is not subject to the identity comparison.

Members are registered against a group individually, by supplying the owning `group_booking_id`, the `member_name`, and optionally `member_units`, which defaults to 1 and must be at least 1. A newly registered member carries `checked_in` false, and that flag is set true by the cabana-confirmation and group-release cascades described below; the admission record of a gate crossing is the admission event and does not itself flip the member's `checked_in` flag. Members belong to the group and are addressable and listable, and each carries a server-minted `id` and `created_at` but no `updated_at` and no `version`.

The group's footprint on the occupancy ledger is deliberately zero until the party actually arrives. `group_reserved_units` is the sum of `member_units` across every member of that group whose `checked_in` flag is true. Two rules collapse the remainder to nothing: a group whose `group_status` has left `CONFIRMED` contributes 0 units whatever its members' flags still say, and a group with no checked-in members contributes 0 units. The status exclusion is exhaustive rather than confined to cancellation: a booking still in `PENDING_DEPOSIT` and a booking in `CANCELLED` both contribute nothing, and `CONFIRMED` is the only status under which a group's checked-in member units reach the ledger. Admission of the party is what turns a group from a reservation into an occupancy, and as described in §3.5 the party is admitted all at once rather than member by member.

Money comes in through two doors. A deposit is recorded against a group by supplying an `amount_cents` and an `external_payment_ref` identifying the external transaction; a recorded deposit increases `deposit_paid_cents` by the amount, retains the most recent reference on the group alongside the running total, and increments the group's `version`. The deposit is refused with `ERR_PAYMENT_DECLINED` (HTTP 409) unless the newly recorded amount added to what has already been paid meets or exceeds the group's requirement of `member_count` multiplied by the per-member deposit of 500 cents, and unless the external payment reference is accepted. Gateway behaviour is controlled separately: a `platform_ops` administrator simulates the external deposit gateway's outcome for a group by naming the `group_booking_id` and the `outcome` the gateway will report, and the platform answers with the `group_booking_id`, the `outcome`, and an `accepted` boolean; when the simulated outcome is `ACCEPTED` the next deposit recording for that group succeeds, and a gateway that refuses the charge surfaces as `ERR_DECLINED_AUTHORIZATION` (HTTP 402).

Confirmation of a group is gated on the same arithmetic seen at the deposit window: a group in `PENDING_DEPOSIT` is confirmed once its `deposit_paid_cents` reaches `member_count` multiplied by the 500-cent per-member requirement, and a booking that has not got there does not satisfy the state precondition and is refused with `ERR_INVALID_STATE`. A confirmed group increments its `version`. Cancellation is available to a `Group` organiser or to `platform_ops` from either `PENDING_DEPOSIT` or `CONFIRMED`, and it is a wide unwind: the group moves to `CANCELLED` and `group_reserved_units` goes to 0; every cabana booking belonging to the group that is in `HELD` or `BOOKED` status is cancelled and every cabana those occupations held returns to availability; and every activity booking attached to the group that is in `PENDING_PAYMENT` or `CONFIRMED` status is cancelled, which for the activity side is a cascade that carries no preconditions of its own. The group's `version` is incremented once.

Cabana and party-room inventory is created by `platform_ops` alone, with a human `cabana_label` unique within the property, a `cabana_kind` of either `CABANA` or `PARTY_ROOM`, and a `capacity_units` count of at least 1. A new cabana is `AVAILABLE`, and its `cabana_status` takes one of the four values `AVAILABLE`, `HELD`, `BOOKED`, and `RELEASED` as occupations come and go. Cabanas are listable per property and individually retrievable, and the occupations recorded against a cabana can be listed from the cabana side.

Placing a hold is how a group claims one, and it is the second of the two operations protected by optimistic concurrency, so the payload must carry the `expected_cabana_version` described in §2.9 in addition to the `cabana_id`, the owning `group_booking_id`, the `service_date`, the occupying window's `start_minute` and `end_minute`, and the `member_units` the group intends to seat. The minute bounds follow the same convention as shifts: `start_minute` is at least 0 and at most 1439, `end_minute` is greater than `start_minute` and at most 1440, and the window is half-open with the start included and the end excluded. The seating must fit the cabana: `member_units` must be at least 1 and no greater than the cabana's `capacity_units`, and an over-large party is refused with `ERR_CABANA_UNITS_UNAVAILABLE` (HTTP 409). The window must also be free: no existing cabana booking in `HELD` or `BOOKED` status may occupy the same cabana on the same service date with a window that overlaps the requested half-open interval, and an overlap is refused with `ERR_CABANA_DOUBLE_BOOKED` (HTTP 409). These two checks are applied before the cabana's own state is consulted: a request that both clashes with a standing occupation and targets a cabana that is not `AVAILABLE` reports the capacity failure or the overlap, and only a request that clears both is then refused with `ERR_CABANA_OCCUPIED` (HTTP 409) for reaching a cabana that is already held or booked. Between the two, the seating check runs first, so a request that both overfills the cabana and clashes with a standing occupation reports `ERR_CABANA_UNITS_UNAVAILABLE` rather than the overlap. A hold creates a provisional cabana booking whose `cabana_booking_status` is `HELD` and whose `hold_expires_at` is defaulted to the logical clock's startup instant of `2026-09-01T00:00:00Z`, and occupies the cabana by moving it from `AVAILABLE` to `HELD`. That cabana booking status is one of `HELD`, `BOOKED`, `CANCELLED`, `EXPIRED`, and `COMPLETED`, and a booking can be retrieved individually by its own `cabana_booking_id`. The hold's `members` array is empty at this stage, and it stays empty for as long as the booking is merely held or has already admitted its members — the array lists only the member object identifiers newly admitted by that particular booking, so it is populated exactly once, at confirmation, and never accumulates. The provisional row is returned to the caller in the response array and is not yet persisted; the cabana's `version` is incremented.

Confirmation converts a hold into a real occupation and is the moment the group's members are actually admitted to the waterpark. It requires the cabana booking to be `HELD` and the linked group booking to be `CONFIRMED`; a booking whose group has not been confirmed is refused with `ERR_CABANA_OCCUPIED` (HTTP 409). On success the cabana booking moves from `HELD` to `BOOKED` and becomes persisted, `hold_expires_at` is cleared to null, every member of the linked group whose `checked_in` flag is false is checked in, the cabana booking's `members` array is populated with those member object identifiers, `group_reserved_units` on the group booking is set to the sum of `member_units` over the checked-in members, the cabana booking's `version` is incremented, and the occupying cabana is moved into `BOOKED` — the cabana's own status table defines that destination as a transition out of `AVAILABLE`.

A hold or an occupation can be cancelled by the owning `Group` organiser, a `FrontDesk` agent, or `platform_ops`. Cancellation is available from `HELD` or `BOOKED` and carries no further precondition on the occupying booking's `members` array; a booking may be cancelled whether it has admitted its members or not, and cancellation moves the cabana booking to `CANCELLED` and returns the occupying cabana to `AVAILABLE`, incrementing the cabana booking's `version`.

Releasing a booked cabana is an operator-only recovery action reserved to `platform_ops`, and it is the only path that unwinds a party that has already been admitted. It requires the cabana to be `BOOKED` and the occupying cabana booking to be `BOOKED`, and it reverses the confirmation in stages: the cabana booking returns to `HELD` with its `members` array emptied and its `hold_expires_at` reset to `2026-09-01T00:00:00Z`; the linked group booking's `group_reserved_units` is zeroed; the occupying cabana returns to `HELD`; and — when the released booking's group is `CONFIRMED` and no other cabana booking in `HELD` or `BOOKED` status still references that group — every member of the group whose `checked_in` flag is true is set back to false. The cabana booking's `version` is incremented.

Holds also lapse on their own, through a dedicated `platform_ops`-only sweep and through the logical clock. The sweep moves every cabana booking that is still `HELD` with a `hold_expires_at` at or before the property's current instant to `EXPIRED` and returns every cabana whose advance holds have all lapsed to `AVAILABLE`, recomputing the cabana day units for the affected service date; the response lists the cabana bookings that lapsed. The same lapse occurs when the logical clock is advanced past a hold's expiry, which covers occupied cabanas as well as merely held ones: a cabana whose `cabana_status` is `HELD` or `BOOKED` and whose occupying booking carries a `hold_expires_at` at or before `2026-09-01T00:00:00Z` returns to `AVAILABLE`. A booked occupation that survives to the end of its day is closed out by the housekeeping pass described in §3.6, which moves it from `BOOKED` to the terminal `COMPLETED` and returns the cabana to availability.

Cabana units are counted for capacity on the same terms as everything else. For a service date, the cabana contribution to the occupancy ledger is the sum of `member_units` across every cabana booking dated that day that is in `HELD` or `BOOKED` status. Because holds count, a cabana whose advance holds have all lapsed surrenders its units outright, while a walk-up hold placed the same day still counts against the ceiling.

### 3.9. Activities, Character Experiences, and Session Pricing

Activities are the upsell tier of the resort, sold by the session and priced by the tier the session belongs to. A `platform_ops` administrator creates a session by naming it, assigning a `tier_code` of `STANDARD`, `PREMIUM`, or `VIP`, setting a `base_price_cents` that is the per-attendee price at the standard tier before any multiplier applies, and declaring a `capacity_units` of at least 1. A session carries a server-minted `id`, a `created_at`, and its property scope, but no `updated_at` and no `version`. Sessions are listable and individually retrievable, and session creation inherits the attraction-readiness check from §2.4 — the property must hold at least one attraction whose derived `attraction_status` is `OPEN`, since that is the state that supports programming, or `ERR_ATTRACTION_NOT_OPEN` is returned. An attraction that is merely `LIMITED` does not satisfy the readiness check, and the same test governs gate admission.

Sessions also carry a read on how large the session is relative to the property's current load, stamped at the instant the session is created and never recomputed afterwards. Three derived fields express that read. The `opt_in_ratio` is the session's `capacity_units` divided by a denominator that is the sum of the room, day-pass, and group contributions to the occupancy ledger over exactly the property's current service date. The `opt_in_ratio_strict` is the same strict division of the session's capacity by that denominator, and it is null when the denominator is zero — a null value is the platform's way of saying there was no load to divide by rather than that the ratio is zero. The `opt_in_ratio_inclusive` reads the session as part of its own denominator: the session's `capacity_units` divided by the denominator plus `capacity_units`. The denominator window is the half-open interval from the current service date to one minute past it, resolved against the call's own instant. All three ratios are stored to four decimal places, rounded half up. A companion field, `opt_in_gate`, records the admission verdict implied by the strict ratio: `ADMIT` when the strict ratio meets or exceeds the configured opt-in ratio threshold, or when the denominator is zero; `HOLD` otherwise.

Booking attendees into a session is performed by a `Group` organiser or a `FrontDesk` agent and names the `activity_session_id` to be booked, the `group_booking_id` the booking attaches to, the number of `attendees`, and the `reservation_id` of the folio the charge will settle against. `attendees` must be at least 1. A new booking begins with `activity_booking_status` of `PENDING_PAYMENT`, the first of its three values `PENDING_PAYMENT`, `CONFIRMED`, and `CANCELLED`, and a cancelled booking settles its refund within the same transition. Creation recomputes `activity_rate_total_cents` and refreshes the opt-in ratio readings of the named session against the service date in effect at that moment; the reading is the session's only recomputation point, since neither confirming nor cancelling a booking disturbs it. Activity bookings are addressable by their own `activity_booking_id`.

Seating is finite and the arithmetic is exact. A session can seat a party when the requested `attendees` is no greater than the session's `capacity_units` minus the seats already taken, where the seats already taken are the sum of `attendees` across every existing booking on that same session whose status is `PENDING_PAYMENT` or `CONFIRMED`. At exact equality the booking is accepted; one attendee more is rejected. Because the session is named explicitly in the request rather than inferred, the platform does no candidate ranking among sessions — but the refusal still carries `ERR_NO_ELIGIBLE_SESSION` (HTTP 409), since a party that cannot be seated in the named session and cannot be accommodated elsewhere in the property has nowhere to go. Cancelled bookings release their seats, since only pending and confirmed bookings count.

Activity pricing multiplies the session's base price by the tier weight of the session and then subtracts a bulk discount. `tier_units` is the number of attendees multiplied by the tier's unit multiplier — 1 for `STANDARD`, 2 for `PREMIUM`, and 3 for `VIP` — and the subtotal is the session's `base_price_cents` multiplied by that figure. The bulk discount applies only to parties of ten or more attendees, and when it applies it is the number of complete groups of five in the attendee count — the division is floored, so a remainder is discarded — multiplied by the 500-cent bulk discount constant. When there are fewer than ten attendees the discount is zero. The booking's `activity_rate_total_cents` is the subtotal less the discount, stored as whole cents rounded half up. The flooring step is load-bearing: it pins the discount to the booking as a whole, so a party of twelve receives two complete five-groups' worth of discount rather than a per-head allowance, and totalling floored per-attendee discounts across the same bookings would produce a larger figure than the platform charges.

Confirmation requires the linked group booking to be `CONFIRMED`; an activity booking whose group has not been confirmed is refused with `ERR_INVALID_STATE` on the state precondition. A confirmed booking moves to `CONFIRMED` and increments its `version`. Cancellation is available to the owning `Group` organiser or to `platform_ops` from `CONFIRMED` status and computes the refund in the same transition, so a booking that is cancelled and a booking that is refunded are never observed separately.

The refund is computed on the attendees who had not yet joined when their group's visit was scheduled to end, and it is computed as a sum rather than as a collection of individually rounded amounts. The number of refundable attendees is the count of attendees whose `joined_at` instant falls strictly before the linked group booking's `service_date`. That count is multiplied by the session's `base_price_cents` and then by the refund rate of 0.375 — three eighths — producing a gross figure that is then rounded half up to whole cents once, at the end, and stored in `activity_rate_refund_cents`. The single rounding step is deliberate and observable. Because 0.375 produces a half-cent for any odd base price, the order of operations changes the answer: at a base price of 3900 cents, one refundable attendee rounds to 1463 cents, and two refundable attendees round as a pair to 2925 cents; rounding each attendee's refund first and then adding them yields 2926 cents, one cent more than the platform pays. The platform sums first and rounds once.

A group's cancellation reaches into its activity bookings as well, as described in §3.8. When a group booking is cancelled, every activity booking attached to it that is in `PENDING_PAYMENT` or `CONFIRMED` status is moved to `CANCELLED` by the platform itself, without any precondition on the activity side and without advancing a refund figure — the cascade is a status unwind, and the refund computation belongs to the explicit cancellation performed by a caller. Activity bookings can be listed per group, per session, or per reservation folio, and a single booking can be retrieved by identifier.

## 4. Endpoint Definitions

Operations that create a new stand-alone resource return `201 Created`. That covers property creation, room types, reservations, day passes, wristbands, attractions, lifeguard shifts, water quality readings, admission events, cabanas, cabana bookings, group bookings, group members, activity sessions, activity bookings, arcade credit grants, and deposit recordings — including the two operations that record a financial posting rather than a new business object. Operations that modify an existing resource, or that drive it through a state transition, return `200 OK`; this includes every check-in, check-out, cancellation, activation, revocation, re-issuance, voiding, confirmation, rotation, resumption, completion, supersession, hold lapse, and administrative edit. Read operations return `200 OK` in both their list and single-resource forms. A single endpoint may answer with more than one status code across its lifetime, since the status of a refusal is governed by the error catalogue in §5 rather than by the endpoint's success code.

Note on payload shapes: a small number of operations return an array where a single resource might be expected. Placing a cabana hold responds with an array containing the provisional hold row, and lapsing expired holds responds with an array of the cabana bookings that lapsed. In both cases the array's `meta` carries `limit`, `offset`, `total_count`, and `has_more` like any other collection.

The unwinding paths matter as much as the granting path. A revoked band declines every succeeded grant upon it, with `decline_reason` `WRISTBAND_REVOKED`. A checked-out booking declines every succeeded grant on its guest bands, with `decline_reason` `RESERVATION_CLOSED`, and until that unwinding is complete the check-out is refused with `ERR_ACCOUNT_LIEN_OUTSTANDING` as described in §3.2. Because grants carry neither an `updated_at` nor a `version` field, a client observes a cascade into a grant only by reading the changed `grant_status` and `decline_reason` values. Grants can be listed per band or queried by the folio they belong to, and a single grant can be retrieved by identifier using its own `grant_id`.
