# Student Loan Servicing API — Product Requirements Document

## 1. Introduction

Federal student loan servicing sits at the intersection of multiple statutory regimes that rarely align cleanly: origination rules differ across Direct Subsidized, Direct Unsubsidized, and Direct PLUS products; repayment options range from the textbook ten-year amortization to a family of income-driven plans (IBR, PAYE, SAVE) whose payment math depends on annually-recertified household economics; and the entire lifecycle is punctuated by long-running periods — grace after school, deferment, forbearance, delinquency, default — that each carry their own interest-accrual and capitalization treatment. Layered on top of this are two distinct discharge tracks: PSLF forgiveness, which counts 120 individually qualifying monthly payments against an actively-certified public-service employment history, and veteran total-and-permanent-disability discharge, which requires VA documentation and a verified military status on file.

This document specifies the Student Loan Servicing API that the Department's servicing operation runs to keep these regimes consistent. The system must produce numerically exact ledgers (every monetary field is stored in integer cents, every interest accrual is computed from the day-count convention statute prescribes), enforce a strict separation between operational staff and the adjudicators who approve forgiveness, and remain auditable across the entire multi-decade life of a loan. It must also be testable: because real time cannot pass during a CI run, the system exposes a logical clock that scripts advance to drive time-gated transitions (delinquency at a missed due date, default at day-270, daily accrual). The product surface is built around a small set of peer entities — Borrower, Loan, RepaymentPlan, Payment, ServicingEvent, EmploymentCertification, PSLFTracker, DischargeApplication, DelinquencyRecord — each with explicit state machines and explicit cross-entity cascades.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

All requests to the API must be authenticated through a mandatory pair of HTTP headers: `X-User-ID`, which identifies the acting user, and `X-User-Role`, which declares the operational capacity under which the request is made. Both headers are required on every endpoint except for `POST /v1/borrowers`, which the servicing operation may invoke without prior authentication context. A request that omits either header is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose `X-User-Role` is not one of the four recognized values is rejected with `ERR_UNAUTHORIZED` (HTTP 403). A request whose role is recognized but is not permitted to invoke the targeted endpoint per the RBAC mapping in §4 is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The system recognizes exactly four roles, each with a distinct identity convention:

- **`Borrower`** — the student loan recipient acting on their own resources. When `X-User-Role` is `Borrower`, `X-User-ID` is the `id` of the acting `Borrower` entity. Ownership checks compare `X-User-ID` to the `borrower_id` carried (directly or transitively through a `Loan`) by any resource the Borrower attempts to read or write. A Borrower acting on a resource whose `borrower_id` does not match `X-User-ID` is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).
- **`LoanServicer`** — operational staff who originate loans, record payments, log servicing events, manage employment certifications, and drive the delinquency machinery. When `X-User-Role` is `LoanServicer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it on resources whose state machine writes it back (for example, as `recorded_by_user_id` on a `Payment` or as `created_by_user_id` on a `ServicingEvent`) but never compares it to any entity's `id`.
- **`PSLFAdjudicator`** — staff who decide PSLF forgiveness applications and may deny PSLF tracking. When `X-User-Role` is `PSLFAdjudicator`, `X-User-ID` is likewise an opaque operator identifier; the server may write it back as `approved_by_user_id` on a `DischargeApplication` but does not compare it to any entity's `id`. PSLF adjudicators are nevertheless subject to a per-borrower segregation-of-duties rule that compares their `X-User-ID` to the `recorded_by_user_id` values on the payments contributing to forgiveness — see §2.6.
- **`VADischargeOfficer`** — staff who decide veteran total-and-permanent-disability discharge applications. When `X-User-Role` is `VADischargeOfficer`, `X-User-ID` is an opaque operator identifier; the server may write it back as `approved_by_user_id` on a `DischargeApplication` but does not compare it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

For endpoints that return lists of resources, pagination is controlled via two query parameters. The `limit` parameter specifies the maximum number of items to return; if not provided, it defaults to 10, with a minimum of 1 and a maximum of 100. The `offset` parameter specifies the number of items to skip and defaults to 0. Unless otherwise specified for a particular endpoint, all list endpoints return resources sorted by their `created_at` timestamp in ascending order. List responses include `limit`, `offset`, `total_count`, and `has_more` in the `meta` envelope.

### 2.4. Common Resource Properties

All primary entities in the system — `Borrower`, `Loan`, `RepaymentPlan`, `Payment`, `EmploymentCertification`, `PSLFTracker`, and `DischargeApplication` — share a common set of system-managed fields:

- **`id`** (string): a server-minted UUID. The identifier carries no type prefix; clients must rely on the URL path or response shape to disambiguate entity kind.
- **`created_at`** (string): an ISO 8601 UTC timestamp with three fractional digits, set once at row creation and never modified.
- **`updated_at`** (string): an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation. Mutations that are driven by automatic cascades (for example, a `Borrower` whose `borrower_status` recomputes after a child `Loan` transitions, or a `Loan` whose balances change as a side effect of a posted `Payment`) update `updated_at` on each touched resource just as a direct write would.
- **`version`** (integer): a non-negative integer that begins at the row's initial value and increments by one on every mutation of that resource, including cascade-driven mutations. This field is the basis of the optimistic concurrency mechanism described in §2.5.

Two entity types deviate from this common shape because they are immutable event records rather than long-lived resources. A `ServicingEvent`, once logged, captures a point-in-time transition (its `event_type`, `effective_on`, `reason_code`, `loan_id`, and `created_by_user_id`) and is never edited; it therefore carries only `id` and `created_at`, and exposes neither `updated_at` nor `version`. A `DelinquencyRecord` is similarly an append-only artifact of the delinquency machinery: it carries only `id` and `created_at`; its mutating fields (`closed_on`, `cumulative_days`, `outcome`) are updated by the system as the delinquency progresses, but neither `updated_at` nor `version` is exposed on this entity.

### 2.5. Optimistic Concurrency Control

Two specific write operations require the client to declare the `Loan` version it last observed, so that the system can refuse silent overwrites whenever another writer has advanced the loan in the meantime. The check is purely a stale-version check: it asks whether the client's observed snapshot is still current, not whether two requests are arriving at the same instant.

Creating a `RepaymentPlan` via a post to the repayment-plans collection requires `expected_loan_version` in the request body as a non-optional integer. The server compares this value to the target loan's current `version`. If the values do not match — because another writer has, for instance, posted a `Payment` or logged a `ServicingEvent` that bumped the loan's `version` since the client's last read — the request is rejected with `ERR_STALE_VERSION` (HTTP 412). The product semantics allow a new plan to legitimately supersede an existing `ACTIVE` plan, so a stream of legitimate creates is permitted; the OCC check exists precisely so that a client cannot supersede a plan it has not yet observed.

Approving a `DischargeApplication` carries a multi-loan variant of the same rule. The approve request body includes `expected_loan_version_by_loan_id`, a map from each non-terminal `loan_id` belonging to the borrower to the `version` value the client most recently observed for that loan. The server compares each entry against the corresponding loan's current `version`; any mismatch — on any one loan — rejects the entire approval with `ERR_STALE_VERSION` (HTTP 412), preventing the cascade from overwriting state the client never saw. No other endpoint takes a version field; only these two writes participate in OCC.

### 2.6. Segregation of Duties on PSLF Forgiveness

Public Service Loan Forgiveness is the only place in the system where a single role decides whether the borrower's debt is extinguished, and the statutory regime therefore separates the operator who counts the qualifying payments from the adjudicator who approves the discharge. Concretely, when a `PSLFAdjudicator` approves a `DischargeApplication` whose `discharge_type` is `PSLF_FORGIVENESS`, the server verifies that the adjudicator's own `X-User-ID` does not appear in `recorded_by_user_id` on any `Payment` that contributed to the borrower's `qualifying_payment_count`. If the adjudicator has ever recorded one of the contributing payments, the approval is rejected with `ERR_SOD_VIOLATION` (HTTP 403). The check considers all loans of the borrower together — recording a single qualifying payment on any one of the borrower's loans disqualifies the adjudicator from approving that borrower's PSLF discharge.

### 2.7. Monetary Precision, Interest Accrual, and Capitalization

All monetary fields in the system — principals, interest balances, payment amounts, monthly payments, capitalized interest — are stored and exchanged as integer cents. There are no fractional cents at rest. Whenever a calculation produces a non-integer cent value, the result is rounded to the nearest whole cent using the round-half-up convention. The arithmetic itself is performed in exact decimal (not binary floating point) so that intermediate divisions on cent quantities are preserved precisely before the final round.

Interest accrues daily, computed on a 365-day basis (not 360, as is the convention for federal Direct loans). On each elapsed day, every loan whose `subsidy_active` flag is false accrues additional interest equal to its `outstanding_principal_cents` multiplied by its `interest_rate_bps`, divided by ten thousand to convert basis points to a decimal rate and then divided by 365 to obtain the daily rate, with the result rounded half-up to a whole cent and added to `accrued_interest_cents`. Loans whose `subsidy_active` is true — Direct Subsidized loans during `IN_SCHOOL`, `GRACE`, or `DEFERMENT` — do not accrue interest on the borrower's side because the federal government pays it; their `accrued_interest_cents` does not increment on those days.

Several state transitions capitalize accrued interest into principal. When a capitalization fires, the system follows a pinned three-step order: first, the capitalizable amount is added to `outstanding_principal_cents` and to the cumulative `capitalized_interest_cents` on the loan; next, `accrued_interest_cents` is set to zero; finally, the loan's `version` is incremented by one. The capitalizable amount itself depends on the transition: a grace-to-repayment, forbearance-to-repayment, or delinquent-to-default transition capitalizes the full `accrued_interest_cents`, whereas a deferment-to-repayment transition for a Direct Subsidized loan capitalizes zero, because the subsidized portion accrued during deferment is paid by the government rather than the borrower. (Equivalently, a deferment-to-repayment transition for a non-subsidized loan capitalizes the full balance.)

### 2.8. Hierarchical Consistency and Cross-Entity Cascades

Mutations frequently cascade across the peer entities. Every cascade is treated as a true write on the touched resource: it refreshes `updated_at`, increments `version`, and is observable through subsequent reads. Three cascade families are central to the system.

First, child-`Loan` activity rolls up onto the parent `Borrower`. The borrower's `borrower_status` is a compound rollup over their non-terminal loans: `CURRENT` whenever every non-terminal loan is in `IN_SCHOOL`, `GRACE`, `REPAYMENT`, `DEFERMENT`, or `FORBEARANCE` and no loan is `DELINQUENT`; `AT_RISK` whenever any loan is `DELINQUENT`; `IN_DEFAULT` whenever any loan is `DEFAULT`; and `CLEARED` whenever every loan is in `PAID_OFF` or `DISCHARGED`. The borrower's `aggregate_outstanding_principal_cents` is the sum of `outstanding_principal_cents` across all non-terminal loans. Both fields recompute whenever any of the borrower's loans transitions or their balances change.

Second, loan-level terminal transitions cascade onto the loan's currently `ACTIVE` `RepaymentPlan`: when a loan moves to `PAID_OFF`, `DEFAULT`, or `DISCHARGED`, the active plan transitions to `EXPIRED`. Any open `DelinquencyRecord` on the loan also closes — with `outcome` of `CURED` when the loan is paid off or discharged, and with `outcome` of `DEFAULTED` when the loan defaults.

Third, an approved `DischargeApplication` cascades across every non-terminal loan of the borrower, transitioning each of them to `DISCHARGED`. The cascade preserves history (the loan's `outstanding_principal_cents` and `accrued_interest_cents` are not zeroed; further accrual simply stops) but each touched loan refreshes `updated_at` and increments `version`, and the borrower's `borrower_status` then recomputes to `CLEARED`. The discharge application also stamps `total_discharged_principal_cents` from the pre-cascade sum of `outstanding_principal_cents` across the cascaded loans, and — if the discharge is PSLF — flips the borrower's `PSLFTracker` to `FORGIVEN`.

### 2.9. Validation Ordering

When several validation conditions could apply to a single request, the server evaluates them in a fixed priority order so that the rejection a client sees is deterministic. Authentication is checked first: missing headers produce `ERR_UNAUTHENTICATED`, an unrecognized `X-User-Role` produces `ERR_UNAUTHORIZED`, and a recognized role that lacks permission for the endpoint produces `ERR_FORBIDDEN_ROLE`; then, for Borrower-role requests, resource ownership is checked with `ERR_NOT_RESOURCE_OWNER`. Only after authentication and authorization does the PSLF-specific segregation-of-duties check fire on discharge approval with `ERR_SOD_VIOLATION`. Existence of every entity referenced by the URL path or request body is then verified, with `ERR_NOT_FOUND`, and path identifiers are validated left-to-right (a non-existent `borrower_id` in the path is reported before a non-existent `loan_id` further down, and parent path identifiers are checked before any body reference). State preconditions for the requested action come next, with `ERR_INVALID_STATE` for in-entity violations and a small family of cross-entity state errors (`ERR_BORROWER_DISCHARGED` for payment attempts on a fully-discharged borrower, `ERR_NOT_VETERAN` for VA discharge requests on a non-veteran borrower) following immediately. Field-shape and business-constraint checks (`ERR_PLAN_FIELDS_INVALID`, `ERR_PAYMENT_DATE_OUT_OF_WINDOW`, `ERR_PAYMENT_EXCEEDS_BALANCE`, `ERR_CERTIFICATION_FIELDS_INVALID`, `ERR_VA_DOC_REQUIRED_OR_FORBIDDEN`, `ERR_DEFAULT_THRESHOLD_NOT_MET`, `ERR_EMAIL_DUPLICATE`) are evaluated after state. Finally, the optimistic-concurrency check is the last gate before the write commits: a mismatched `expected_loan_version` (or any mismatched entry in `expected_loan_version_by_loan_id`) raises `ERR_STALE_VERSION` only after every prior check has passed. A malformed body that does not match any more specific rule falls back to `ERR_INVALID_REQUEST`. Validation errors that do not fit any of the above (for example, an invalid clock advance) carry their own dedicated codes (`ERR_INVALID_CLOCK`).

## 3. Business Logic & Workflows

### 3.1. Originating a Borrower and a Loan

A `LoanServicer` opens an account by creating a `Borrower` record. The submission carries `ssn_last4` (exactly four numeric digits, the last four of the social security number used for matching rather than the full SSN), `full_name` as it appears on the legal record, `date_of_birth` in ISO 8601 YYYY-MM-DD form, and a contact `email`. The `email` is unique across all borrowers, evaluated case-insensitively; an attempt to reuse an existing email is rejected with `ERR_EMAIL_DUPLICATE`. An optional `military_status` may be supplied at creation; if omitted, the field defaults to `NONE` and may later be amended via the dedicated military-status update endpoint (typically when a borrower presents discharge papers). The permitted values are `NONE`, `ACTIVE_DUTY`, `VETERAN`, and `DISABLED_VETERAN`; the latter two are what later authorize a veteran disability discharge application. On creation, the new borrower carries `aggregate_outstanding_principal_cents` of zero and a `borrower_status` of `CURRENT` (no loans yet).

Once a borrower exists, a `LoanServicer` originates a `Loan` by referencing the `borrower_id`, declaring the `loan_type` as one of `DIRECT_SUBSIDIZED`, `DIRECT_UNSUBSIDIZED`, or `DIRECT_PLUS`, supplying the `original_principal_cents` actually disbursed (a positive integer up to two hundred million cents inclusive), the annual `interest_rate_bps` in basis points (a non-negative integer no greater than five thousand — i.e., zero percent up to fifty percent annual), and the `disbursement_date` that anchors the grace clock. The loan is born with `status` of `IN_SCHOOL`, with `outstanding_principal_cents` initialized to `original_principal_cents`, with `accrued_interest_cents` and `capitalized_interest_cents` both at zero, and with `days_delinquent` at zero. The `subsidy_active` flag is computed: it is true precisely when `loan_type` is `DIRECT_SUBSIDIZED` and `status` is one of `IN_SCHOOL`, `GRACE`, or `DEFERMENT`, and false otherwise. The borrower's `borrower_status` and `aggregate_outstanding_principal_cents` recompute immediately. The `borrower_id` on a loan is immutable after creation.

### 3.2. The Loan Lifecycle

Every loan flows through a state machine rooted in `IN_SCHOOL`, with the seven mid-life states `GRACE`, `REPAYMENT`, `DEFERMENT`, `FORBEARANCE`, `DELINQUENT`, and the three terminal states `PAID_OFF`, `DEFAULT`, and `DISCHARGED`. Lifecycle transitions, except those driven by the logical clock or by payments, are initiated by a `LoanServicer` logging a `ServicingEvent` against the loan with an explicit `event_type`, an `effective_on` date, and a documented `reason_code`. The permissible event types are `GRACE_BEGIN`, `REPAYMENT_BEGIN`, `DEFERMENT_BEGIN`, `DEFERMENT_END`, `FORBEARANCE_BEGIN`, `FORBEARANCE_END`, `DELINQUENT_BEGIN`, `REPAYMENT_RESUME`, `DEFAULT_DECLARED`, `CAPITALIZATION`, and `RECERTIFY_IDR`; the permissible reasons are `SCHOOL_ENROLLMENT`, `ECONOMIC_HARDSHIP`, `MILITARY_SERVICE`, `MEDICAL`, `NATURAL_DISASTER`, `ADMIN_FORBEARANCE`, `GRACE_EXPIRY`, `MISSED_PAYMENTS_270D`, `IDR_ANNUAL_RECERT`, and `OTHER`. Each event is stamped with `created_by_user_id` from the acting servicer's `X-User-ID`. Every accepted servicing event also increments the parent loan's `version`.

The transition from `IN_SCHOOL` to `GRACE` fires on a `GRACE_BEGIN` event when the loan is currently in `IN_SCHOOL` and the supplied `effective_on` is on or after the loan's `disbursement_date`; on success the loan's `status` advances to `GRACE` and `subsidy_active` recomputes (still true for a Direct Subsidized loan). A subsequent `REPAYMENT_BEGIN` event with reason `GRACE_EXPIRY`, requiring the loan to be in `GRACE` and `effective_on` to be on or after the grace-begin date, advances the loan to `REPAYMENT`; this transition flips `subsidy_active` to false for Direct Subsidized loans (the borrower is now responsible for interest) and emits a system-generated `CAPITALIZATION` servicing event that capitalizes any `accrued_interest_cents` into principal per the rules in §2.7.

From `REPAYMENT`, the servicer may initiate `DEFERMENT_BEGIN` with reason among `SCHOOL_ENROLLMENT`, `ECONOMIC_HARDSHIP`, `MILITARY_SERVICE`, or `MEDICAL`, provided no `DelinquencyRecord` is currently open on the loan; the loan moves to `DEFERMENT`, `subsidy_active` recomputes (true for Direct Subsidized, false otherwise), and `days_delinquent` is reset to zero. A `DEFERMENT_END` event, requiring the loan to be in `DEFERMENT`, returns the loan to `REPAYMENT` and triggers a capitalization that capitalizes only the unsubsidized portion of `accrued_interest_cents` (for Direct Subsidized loans this is zero because `subsidy_active` held throughout the deferment window; for non-subsidized loans the entire accrued interest capitalizes).

Forbearance follows a parallel structure: `FORBEARANCE_BEGIN` is accepted from either `REPAYMENT` or `DELINQUENT` with reason among `ECONOMIC_HARDSHIP`, `NATURAL_DISASTER`, `ADMIN_FORBEARANCE`, or `MEDICAL`. The loan moves to `FORBEARANCE`, `subsidy_active` is forced to false (forbearance never subsidizes interest, regardless of `loan_type`), `days_delinquent` is reset to zero, and if the loan had been in `DELINQUENT` the open `DelinquencyRecord` closes with `outcome` of `FORBORNE`. `FORBEARANCE_END`, requiring the loan to be in `FORBEARANCE`, returns the loan to `REPAYMENT` and triggers a capitalization of the full `accrued_interest_cents`.

When a discharge approval cascades into the loan, the loan's `status` advances directly to `DISCHARGED` from whichever non-terminal state it occupied; the loan's `outstanding_principal_cents` and `accrued_interest_cents` are left as historical record (no further accrual occurs), any open `DelinquencyRecord` closes with `outcome` of `CURED`, and any `ACTIVE` `RepaymentPlan` on the loan transitions to `EXPIRED`. The cascade only fires when the discharge application's `borrower_id` matches the loan's `borrower_id` and, in the PSLF case, only when the borrower's `PSLFTracker` is already in `ELIGIBLE_FOR_FORGIVENESS`. The transition to `PAID_OFF` is driven by payment posting and is described in §3.4 together with the rest of the payment workflow.

### 3.3. Repayment Plans and the Monthly Payment Formula

A `Loan` may carry at most one `ACTIVE` `RepaymentPlan` at a time, and that plan determines the borrower's scheduled monthly obligation. A plan is created by a `LoanServicer` or by the `Borrower` themselves by referencing the target `loan_id` and choosing a `plan_type` from `STANDARD_10YR`, `IBR`, `PAYE`, or `SAVE`. The request must also carry the `expected_loan_version` per §2.5. Plan creation is permitted only when the loan is in `GRACE`, `REPAYMENT`, `DEFERMENT`, `FORBEARANCE`, or `DELINQUENT`; an attempt on a terminal-state loan is rejected with `ERR_INVALID_STATE`. The submission body and its companion `state_of_residence` (one of `CONTIGUOUS`, `AK`, or `HI`, used to select the poverty-line table) must satisfy the plan-type-specific shape rule described later in this section, or the server returns `ERR_PLAN_FIELDS_INVALID`. If a different plan with `status` of `ACTIVE` already exists for the same `loan_id`, the new plan still proceeds: on successful activation, the prior plan transitions from `ACTIVE` to `SUPERSEDED` and the new plan takes its place as the single `ACTIVE` row. (The system does not require an explicit deactivation call; supersede is automatic. The OCC rule in §2.5 is precisely what prevents two clients from both superseding from the same stale view.) A plan that has been superseded — or that is later cascaded to `EXPIRED` when the parent loan reaches `PAID_OFF`, `DEFAULT`, or `DISCHARGED` — is itself in a terminal state and is read-only thereafter.

The plan body shape varies by `plan_type`. For a `STANDARD_10YR` plan, both `agi_cents` and `family_size` must be null; supplying either field is rejected with `ERR_PLAN_FIELDS_INVALID`. For any of the income-driven plan types (`IBR`, `PAYE`, `SAVE`), both `agi_cents` and `family_size` are required, with `agi_cents` strictly positive and `family_size` between one and twenty inclusive; missing or out-of-range values are rejected with the same code. The same rules apply to the annual income recertification endpoint described below.

A plan row is conceptually born with `status` of `PENDING` and is moved to `ACTIVE` synchronously by the same create request once all preconditions clear; clients never observe a persisted `PENDING` plan after a successful create. On successful activation, the system computes `monthly_payment_cents` and stamps it on the plan; for income-driven plans, it also stamps `certification_expires_on` as the simulation clock's date plus 365 days, and for `STANDARD_10YR` plans `certification_expires_on` is left null. The resulting plan is addressable thereafter by its `plan_id`. The borrower or servicer may submit an annual income recertification against an existing plan, supplying refreshed `agi_cents` and `family_size`; on success the server recomputes `monthly_payment_cents` and resets `certification_expires_on` to the clock date plus 365 days.

The computation of `monthly_payment_cents` is the central calculation of the system, and the formula varies materially across the four plan families. Two anchor inputs are common: the loan's current `outstanding_principal_cents` at the moment of plan creation (call it `P`), and the loan's `interest_rate_bps`. The monthly interest rate `r_monthly` is `interest_rate_bps` divided by ten thousand to convert basis points to a decimal, then divided by twelve. The standard term `n` is 120 months (ten years). All intermediate arithmetic is performed in exact decimal on cents; the final monthly payment is rounded half-up to a whole cent.

For a `STANDARD_10YR` plan, the monthly payment is the textbook fixed-payment amortization: when `r_monthly` is zero, the monthly payment is simply `P` divided by 120 (and then rounded). When `r_monthly` is positive, the monthly payment equals `P` multiplied by `r_monthly`, multiplied again by the quantity `(1 + r_monthly)` raised to the 120th power, divided by the quantity `(1 + r_monthly)` raised to the 120th power minus one. The result is rounded half-up to whole cents. This `STANDARD_10YR` figure is also reused as a cap by some of the income-driven plans below; we will refer to it as the standard reference payment.

The three income-driven plans all share a common front end. Each consults the household poverty line for the borrower's `state_of_residence` and `family_size` — the `CONTIGUOUS` table is used for the forty-eight contiguous states, the `AK` table for Alaska, and the `HI` table for Hawaii. The fixed annual poverty-line table (in cents) used by the system is:

| `family_size` | `CONTIGUOUS` | `AK`     | `HI`     |
|---------------|--------------|----------|----------|
| 1             | 1506000      | 1883000  | 1732000  |
| 2             | 2034000      | 2542000  | 2339000  |
| 3             | 2562000      | 3201000  | 2946000  |
| 4             | 3090000      | 3860000  | 3553000  |
| 5             | 3618000      | 4519000  | 4160000  |

For an `IBR` plan, discretionary annual income is the borrower's `agi_cents` minus 150 percent of the looked-up annual poverty line (in cents), floored at zero (i.e., if `agi_cents` is less than 150 percent of poverty, discretionary income is zero rather than negative). The IBR monthly payment is fifteen percent of discretionary annual income, divided by twelve, and rounded half-up to whole cents. IBR is then capped at the `STANDARD_10YR` reference payment computed above: the actual `monthly_payment_cents` is the smaller of the IBR figure and the standard reference. (For borrowers with high principal and modest income, the IBR figure is lower than the standard and the cap is inactive; for borrowers with very small principal and modest income, the IBR figure may exceed the standard, in which case the cap binds and the borrower simply pays the standard.)

For a `PAYE` plan, the structure is identical to `IBR` except the rate is ten percent rather than fifteen percent of discretionary income. The 150-percent poverty threshold and the standard reference cap both apply.

For a `SAVE` plan, discretionary annual income uses a more generous 225-percent poverty threshold instead of 150 percent (i.e., the deduction is 225 percent of the poverty line, again floored at zero). The SAVE monthly payment is five percent of discretionary annual income, divided by twelve, and rounded half-up to whole cents. SAVE has no standard-payment cap, so `SAVE` can produce a payment smaller than `IBR` or `PAYE` on the same inputs — and, on very high principals, can produce a `monthly_payment_cents` larger than what `IBR` or `PAYE` would have produced (since they would have been capped at the standard reference).

### 3.4. Posting Payments, the Allocation Waterfall, and Loan Closeout

A `LoanServicer` records a `Payment` by posting against the payments collection with the target `loan_id`, the gross `amount_cents` (a positive integer), the effective `posted_on` date, and a `source` from `ACH`, `CHECK`, `PAYROLL_DEDUCT`, `EMPLOYER_BENEFIT`, or `TREASURY_OFFSET`. The resulting payment is addressable thereafter by its `payment_id`. The server stamps `recorded_by_user_id` from the acting servicer's `X-User-ID`, which is what the segregation-of-duties rule in §2.6 later inspects. A payment posts synchronously and immediately — the row is created with `status` of `POSTED` (it is never persisted as `PENDING` after a successful create; the `PENDING` value of `status` exists only as the pre-commit state in the transition machine). Posting is permitted only when the parent loan is in `GRACE`, `REPAYMENT`, `DEFERMENT`, `FORBEARANCE`, `DELINQUENT`, or `DEFAULT`; an attempt against a `PAID_OFF` or `DISCHARGED` loan is rejected with `ERR_INVALID_STATE`. The system additionally refuses to accept a payment for any borrower whose every loan sits in `DISCHARGED` or `PAID_OFF`, returning `ERR_BORROWER_DISCHARGED`; this is the cross-entity guard that prevents stray payments from arriving on a borrower the system considers closed out.

Two `posted_on` rules govern when a payment may be back-dated. No payment may be future-dated relative to the simulation clock: `posted_on` must be no later than the clock date. A payment may be back-dated by up to fifteen days: `posted_on` must be no earlier than the clock date minus fifteen days (so a `posted_on` exactly fifteen days earlier than the clock is accepted; sixteen days earlier is rejected with `ERR_PAYMENT_DATE_OUT_OF_WINDOW`).

The gross `amount_cents` is then disbursed across three internal buckets in a strict waterfall, evaluated in this order; rounding occurs per bucket as integer cents, and the values stored on the resulting `Payment` row are `applied_to_fees_cents`, `applied_to_interest_cents`, and `applied_to_principal_cents`. The first bucket is collection fees, and it is non-zero only for the narrow combination of a loan in `DEFAULT` paying via `TREASURY_OFFSET`: in that case the statutory collection fee is computed as the floor of the gross `amount_cents` multiplied by 0.1825 (that is, 18.25 percent of the gross amount, computed once per payment rather than per bucket and rounded down to a whole cent); the fee bucket then takes the lesser of the remaining amount and that floor. For every other combination, the fee bucket is zero. The second bucket is accrued interest: from whatever remains, the system applies the smaller of the remaining amount and the loan's current `accrued_interest_cents`, and decrements `accrued_interest_cents` by that figure. The third bucket is outstanding principal: from whatever still remains, the system applies the smaller of the remaining amount and the loan's current `outstanding_principal_cents`, and decrements `outstanding_principal_cents` accordingly.

The waterfall has no fourth bucket: any non-zero residue after the three buckets are filled represents an overpayment. An overpayment is permitted only when the payment exactly zeros out both `outstanding_principal_cents` and `accrued_interest_cents` (with fees fully covered when applicable) — that is, the payment is a full payoff that leaves no remaining amount. If non-zero residue remains after fees, interest, and principal are exhausted and the loan is not paid off, the request is rejected with `ERR_PAYMENT_EXCEEDS_BALANCE`. The boundary is strict: a payment whose `amount_cents` equals the sum of fees-due, current interest, and current principal succeeds (full payoff); a payment one cent above that sum fails.

When the posting brings both `outstanding_principal_cents` and `accrued_interest_cents` to zero, the loan cascades to `PAID_OFF`: both balance fields are set to zero, `days_delinquent` is reset to zero, any open `DelinquencyRecord` closes with `outcome` of `CURED`, any `ACTIVE` `RepaymentPlan` transitions to `EXPIRED`, and the loan's `version` increments. The payment posting itself is allowed from any of `REPAYMENT`, `DELINQUENT`, `FORBEARANCE`, or `DEFERMENT` for this payoff cascade. Separately, when the loan was in `DELINQUENT` and the incoming payment is large enough to cover every missed scheduled monthly payment since the open `DelinquencyRecord`'s `opened_on` (i.e., the full arrears), the loan cascades back to `REPAYMENT`, the open `DelinquencyRecord` closes with `outcome` of `CURED`, `days_delinquent` resets to zero, and the loan's `version` increments. Finally, posting a payment always triggers a recount of the borrower's `PSLFTracker` (described in §3.6), which recomputes the `pslf_qualifying` flag on this and prior payments and may flip the tracker forward to `ELIGIBLE_FOR_FORGIVENESS`.

A `LoanServicer` may reverse a previously posted payment for up to thirty days after its `posted_on`. The reversal endpoint requires the payment to be in `POSTED` status and its `posted_on` to be no earlier than the simulation clock date minus thirty days; otherwise it is rejected with `ERR_INVALID_STATE`. On success the payment moves to `REVERSED`, `outstanding_principal_cents` is increased by the prior `applied_to_principal_cents`, `accrued_interest_cents` is increased by the prior `applied_to_interest_cents`, the loan's `version` increments, and the borrower's `PSLFTracker` is recounted — if removing this payment drops `qualifying_payment_count` below `required_payment_count` and the tracker had been in `ELIGIBLE_FOR_FORGIVENESS`, the tracker reverts to `TRACKING`.

### 3.5. Delinquency, Default, and the Logical Clock

The system runs against a logical clock so that time-gated effects can be reproduced in tests. A `LoanServicer` advances the clock by submitting a target instant `to_iso8601` to the clock-advance capability; the target must be strictly greater than the current clock, or the request is rejected with `ERR_INVALID_CLOCK`. The companion read-clock capability returns the current clock without any side effect.

Advancing the clock fires several effects for each elapsed day. First, the daily interest-accrual job runs for every loan whose `subsidy_active` is false per the formula in §2.7, incrementing `accrued_interest_cents`. Second, for every loan currently in `REPAYMENT` that has an `ACTIVE` `RepaymentPlan` with `monthly_payment_cents` greater than zero, the system checks whether a scheduled monthly due date has now passed without a qualifying `POSTED` payment. A monthly schedule is considered satisfied when there exists a posted payment whose `amount_cents` is greater than or equal to the scheduled `monthly_payment_cents` and whose `posted_on` falls within the window of the due date itself through fifteen days after the due date. If a due date has been crossed unsatisfied, the loan transitions to `DELINQUENT`: a new `DelinquencyRecord` opens with `opened_on` set to the missed due date, the loan's `days_delinquent` becomes the count of days from that missed due date to the current clock date, and the loan's `version` increments. Third, for every open `DelinquencyRecord`, the system updates its `cumulative_days` (the running count of consecutive days the loan has been delinquent since `opened_on`). If `cumulative_days` reaches 270 — 270 days triggers default; 269 days does not — the loan transitions to `DEFAULT`: the open `DelinquencyRecord` closes with `outcome` of `DEFAULTED`, a capitalization of all `accrued_interest_cents` is performed per §2.7, any `ACTIVE` `RepaymentPlan` transitions to `EXPIRED`, the borrower's `borrower_status` recomputes to `IN_DEFAULT`, and the loan's `version` increments.

A servicer may also drive the default transition explicitly through a `DEFAULT_DECLARED` `ServicingEvent` with `reason_code` of `MISSED_PAYMENTS_270D`. The same boundary applies: the loan's current open `DelinquencyRecord` must have `cumulative_days` of at least 270; an attempt at 269 or below is rejected with `ERR_DEFAULT_THRESHOLD_NOT_MET`. The list of delinquency records for a loan is exposed via the per-loan delinquency-records list endpoint, which returns the records most recent first by `opened_on` (with `created_at` ascending as a tie-break) and may be filtered by `outcome`.

A delinquent loan may also be cured outside the default path. As described in §3.4, a payment large enough to cover the full arrears moves the loan back to `REPAYMENT` and closes the open record with `outcome` of `CURED`; a forbearance begin while delinquent closes the open record with `outcome` of `FORBORNE` and moves the loan to `FORBEARANCE`. The list of `outcome` values a record may carry is therefore `OPEN`, `CURED`, `FORBORNE`, and `DEFAULTED`.

### 3.6. Public Service Loan Forgiveness: Tracking, Counting, and Approval

The PSLF track requires three streams of evidence to converge on a single borrower: an actively-`APPROVED` `EmploymentCertification` from a qualifying employer covering the dates on which payments were made, an `ACTIVE` `RepaymentPlan` on each loan whose payments are counted, and at least 120 individual `POSTED` payments that satisfy a per-payment qualifying check.

Employment is attested by submitting an `EmploymentCertification` for the borrower. The submission carries the `borrower_id`, the `employer_ein` (the federal Employer Identification Number, exactly nine numeric digits), the `employer_type` (one of `GOVERNMENT_FEDERAL`, `GOVERNMENT_STATE_LOCAL_TRIBAL`, `NONPROFIT_501C3`, `OTHER_NONPROFIT_QUALIFYING`, `FOR_PROFIT`, or `NOT_QUALIFYING`), the inclusive employment window described by `period_start_on` and `period_end_on` (for ongoing employment, the sentinel `2999-12-31` is supplied as `period_end_on`), and the average `weekly_hours` worked during that period as a number between zero and eighty inclusive. Field-level violations on submission — `employer_ein` not exactly nine digits, `weekly_hours` outside the inclusive range [0, 80], or `period_end_on` earlier than `period_start_on` — are rejected at create time with `ERR_CERTIFICATION_FIELDS_INVALID`. A well-formed certification is created with `status` of `PENDING` and is addressable thereafter by its `certification_id`. A `LoanServicer` then approves the certification — moving its `status` to `APPROVED` — or rejects it (moving the `status` to `REJECTED`, which is terminal). Approval additionally re-verifies that `employer_ein` is exactly nine digits and that `period_end_on` is on or after `period_start_on` before the transition fires. On approval, the derived `pslf_qualifying_employer` flag becomes true precisely when `status` is `APPROVED`, `employer_type` is one of `GOVERNMENT_FEDERAL`, `GOVERNMENT_STATE_LOCAL_TRIBAL`, `NONPROFIT_501C3`, or `OTHER_NONPROFIT_QUALIFYING`, and `weekly_hours` is at least 30; the for-profit and not-qualifying employer types, and any approved certification with fewer than 30 weekly hours, all produce `pslf_qualifying_employer` of false. Approval also triggers a PSLF recount for the borrower (described below) and may flip the borrower's `PSLFTracker` from `TRACKING` to `ELIGIBLE_FOR_FORGIVENESS`.

The `PSLFTracker` itself is a per-borrower aggregator; at most one tracker exists per `borrower_id`. A `LoanServicer` or a `PSLFAdjudicator` initializes the tracker by submitting `borrower_id`; the new row carries `status` of `TRACKING`, `qualifying_payment_count` of zero, `required_payment_count` of 120 (the statutory target), and `last_recount_on` set to the simulation clock date. The tracker is addressable thereafter by its `tracker_id`. Recounts are triggered automatically whenever a `Payment` posts, whenever a `Payment` is reversed, and whenever an `EmploymentCertification` is approved; a recount can also be invoked explicitly via the tracker recount capability (which is idempotent — calling it without intervening events leaves the tracker unchanged). Every recount updates `last_recount_on` to the current clock date.

The recount recomputes `qualifying_payment_count` by walking every `POSTED` `Payment` across every `Loan` of the borrower. A given payment counts toward the tally when, and only when, all of the following hold at recount time: the payment's `status` is `POSTED` (reversed payments do not count); the payment's `posted_on` falls within the `period_start_on`/`period_end_on` window of an `APPROVED` `EmploymentCertification` for the same borrower whose `pslf_qualifying_employer` is true; the parent `Loan` had an `ACTIVE` `RepaymentPlan` with `plan_type` in `STANDARD_10YR`, `IBR`, `PAYE`, or `SAVE` on the payment's `posted_on`; the payment's `amount_cents` is at least the `monthly_payment_cents` that was in force on the parent loan's active plan on `posted_on`; and `posted_on` falls within the monthly billing cycle's on-time window, defined as the cycle's scheduled due date through fifteen days after the due date (with no allowance for early payment relative to the cycle's due date — i.e., zero days before, fifteen days after). The `pslf_qualifying` flag on the payment row reflects whether the payment currently satisfies these conditions.

When `qualifying_payment_count` reaches `required_payment_count` (the boundary is strict: 120 triggers, 119 does not), the tracker transitions from `TRACKING` to `ELIGIBLE_FOR_FORGIVENESS`. When an approval is later applied (via a PSLF discharge as described in §3.7), the tracker advances from `ELIGIBLE_FOR_FORGIVENESS` to `FORGIVEN`. A `PSLFAdjudicator` may also deny the tracker outright while it is in `TRACKING`, advancing it to the terminal `DENIED` state. The recount is the engine that absorbs all three triggering events uniformly: a fresh `APPROVED` certification re-evaluates payments by their `posted_on` against the newly approved window, so payments that previously did not qualify (because no certification covered their date) may now begin to count; a fresh `POSTED` payment is evaluated for the first time; and a fresh `REVERSED` payment is excluded going forward, possibly dropping the count below threshold and (per §3.4) reverting an `ELIGIBLE_FOR_FORGIVENESS` tracker back to `TRACKING`.

For tests that need a `PSLFTracker` already at threshold without simulating 120 individual payments, the system exposes a `PSLFAdjudicator`-only test-driving capability that directly overwrites a tracker's `qualifying_payment_count` and `status` (where `status` must be either `TRACKING` or `ELIGIBLE_FOR_FORGIVENESS`). This is a pure test-driving facility and is the only path by which the count can be set without going through the recount machinery.

### 3.7. Discharge: Veteran Total-and-Permanent Disability and PSLF Forgiveness

A `DischargeApplication` is the vehicle through which a loan's outstanding balance may be extinguished. An application is filed by the `Borrower` or by a `LoanServicer` against the borrower's `borrower_id` with a `discharge_type` of `VETERAN_TOTAL_PERMANENT_DISABILITY`, `PSLF_FORGIVENESS`, `DEATH`, or `CLOSED_SCHOOL` and a `filed_on` date. The resulting application is addressable thereafter by its `application_id`. The application carries an optional `va_certification_doc_id` whose presence is tightly coupled to `discharge_type`: it is required and must be non-null when `discharge_type` is `VETERAN_TOTAL_PERMANENT_DISABILITY`, and it must be null for every other `discharge_type`. A violation of either branch — missing on a VA application, or supplied on a non-VA application — is rejected with `ERR_VA_DOC_REQUIRED_OR_FORBIDDEN`. Filing a veteran discharge additionally requires that the borrower's `military_status` already be either `VETERAN` or `DISABLED_VETERAN`; if not, the filing itself is rejected with `ERR_NOT_VETERAN`. New applications are created with `status` of `SUBMITTED`.

Review proceeds in two stages. First, the adjudicator moves the application from `SUBMITTED` to `UNDER_REVIEW` via the begin-review capability; the application must be in `SUBMITTED`, and the acting role must match the `discharge_type` — a `VADischargeOfficer` may begin review only on a `VETERAN_TOTAL_PERMANENT_DISABILITY` application, and a `PSLFAdjudicator` may begin review only on a `PSLF_FORGIVENESS` application. Second, the adjudicator either approves or denies the application from `UNDER_REVIEW`. The deny path moves the application's `status` to `DENIED` and has no further side effects.

The approve path is the system's most consequential transition and carries the heaviest set of preconditions. The application must be `UNDER_REVIEW`. For a `VETERAN_TOTAL_PERMANENT_DISABILITY` application, the acting role must be `VADischargeOfficer`, the borrower's `military_status` must remain `VETERAN` or `DISABLED_VETERAN`, and the application's `va_certification_doc_id` must be non-null. For a `PSLF_FORGIVENESS` application, the acting role must be `PSLFAdjudicator`, the borrower's `PSLFTracker` must already be in `ELIGIBLE_FOR_FORGIVENESS`, and the segregation-of-duties rule from §2.6 fires: the acting `X-User-ID` must not appear in `recorded_by_user_id` on any `Payment` that contributed to `qualifying_payment_count`, on pain of `ERR_SOD_VIOLATION`. The approve request body carries `expected_loan_version_by_loan_id` per §2.5; any stale entry rejects the entire approval with `ERR_STALE_VERSION`.

On a successful approval, the application's `status` becomes `APPROVED` and the acting `X-User-ID` is stamped as `approved_by_user_id`. Before the cascade fires, the system snapshots the sum of `outstanding_principal_cents` across every non-terminal loan of the borrower and stores it on the application as `total_discharged_principal_cents` (so that the field reflects the pre-cascade balances). The cascade then transitions every non-terminal loan of the borrower to `DISCHARGED`, per §2.8 and §3.2: each loan refreshes `updated_at`, increments `version`, any open `DelinquencyRecord` closes with `outcome` of `CURED`, and any `ACTIVE` `RepaymentPlan` transitions to `EXPIRED`. The borrower's `borrower_status` recomputes — `CLEARED` if every loan now sits in `PAID_OFF` or `DISCHARGED`. Finally, when `discharge_type` is `PSLF_FORGIVENESS`, the borrower's `PSLFTracker` advances from `ELIGIBLE_FOR_FORGIVENESS` to `FORGIVEN`.
