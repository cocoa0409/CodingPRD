# Garbage Sorting Points API — Product Requirements Document

## 1. Introduction

Municipal recycling programs increasingly rely on per-resident accountability rather than per-bin collection metrics: residents are asked to sort waste at the source, and the system that grades, rewards, and audits their participation must be precise enough to back redeemable economic value while remaining auditable when a misjudgment must be reversed weeks after the fact. This document specifies the back-end HTTP service that powers such a program for one or more residential communities. Each community runs its own point rules, its own redemption mall, its own ranking leaderboards, and its own violation/appeal pipeline; the system is multi-tenant by community and consistently uses a community-local timezone for daily caps, peak-hour bonuses, and ranking windows.

Four user-facing concerns drive the requirements. First, **residents** need a fair scoring engine that converts a single act of disposal — a bag of recyclables placed on a scale at 7:42 a.m. — into points that they can later redeem at the community mall. Second, **community administrators** need to manage household and resident registration, publish and retire scoring rules, correct or void mis-scored disposals, record violations with escalating deductions for repeat offenders, and close and publish ranking periods. Third, **appeal reviewers**, organizationally separated from the administrators who record violations, take appeals under review and either uphold or overturn them, with overturning cascading through any subsequent violations that depended on the now-reversed one. Fourth, **system operators** bootstrap communities and drive a logical clock so the program can be tested deterministically under accelerated time.

Throughout, the service prioritizes append-only auditability over destructive update. Every point credit and every point debit is materialized as an immutable `PointsTransaction` row whose chronological tail reconciles to the household's current `points_balance`; structurally significant administrative actions are also captured as `AuditLog` entries. Mistakes are remediated not by deleting history but by adding compensating entries — a corrected disposal generates a `MISJUDGMENT_ADJUSTMENT`, an overturned violation generates a `VIOLATION_REVERSAL`, and the ranking leaderboards that touch the affected period are invalidated until re-closed.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request MUST carry two headers: `X-User-ID` (the identifier of the calling principal) and `X-User-Role` (the textual role name). When either header is missing or empty, the request is rejected with `ERR_AUTH_REQUIRED`. When `X-User-Role` is present but does not match one of the four declared role names, the request is rejected with `ERR_UNKNOWN_ROLE`. When the role is recognized but is not permitted to invoke the requested endpoint, the rejection code is `ERR_FORBIDDEN`.

The four roles are spelled exactly as follows:

- **`SystemOperator`** — platform operator who bootstraps communities and drives the test-only clock and sweep capabilities. When `X-User-Role` is `SystemOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example, as `actor_id` on `AuditLog` where a scaffold-driven side-effect writes it) but never compares it to any entity's `id`.
- **`CommunityAdmin`** — community-level operator who manages households, residents, point rules, redemption fulfillment, violation recording, and ranking periods. When `X-User-Role` is `CommunityAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it on audit entries but never compares it to any entity's `id`.
- **`AppealReviewer`** — separate-of-duties appeal handler who takes appealed violations under review and decides them. They MAY NOT record violations. When `X-User-Role` is `AppealReviewer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it on audit entries but never compares it to any entity's `id`.
- **`Resident`** — a verified resident who submits their own disposals and redemption orders, and who files appeals on their own violations. When `X-User-Role` is `Resident`, `X-User-ID` is the `id` of the acting `Resident` entity; ownership checks on any resource that references a `Resident` compare the resource's `resident_id` foreign-key field to `X-User-ID`, and household membership is enforced by requiring that the `Resident` referenced by `X-User-ID` has a `household_id` matching the path's household. Ownership failures surface as `ERR_FORBIDDEN`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept the optional query parameters `limit` and `offset`. The default `limit` is 10, the minimum is 1, and the maximum is 100; any value outside this range is rejected as `ERR_VALIDATION`. The default `offset` is 0. List endpoints sort results by `created_at` in ascending order. The `meta` object of a list response contains `limit`, `offset`, `total_count` (the total number of rows matching any filter, ignoring `limit`/`offset`), and `has_more` (true when `offset + limit < total_count`).

### 2.4. Common Resource Properties

Most resources expose four common fields. The `id` is a server-minted UUID returned as a plain string — no resource type prefix is added. The `created_at` and `updated_at` fields are ISO 8601 UTC timestamps with three fractional digits, and `updated_at` is refreshed whenever any persisted field on the resource changes. The `version` field is a positive integer that starts at 1 on creation and increments by one on every server-side mutation of that row. Resources following this convention include `Community`, `Household`, `Resident`, `Disposal`, `MallItem`, `RedemptionOrder`, `Violation`, and `RankingPeriod`.

Two resources carry only `id` and `created_at` — they are append-only audit-style records with no notion of update: `PointsTransaction` and `AuditLog`. Both lack `updated_at` and `version`. The single exception within the first group is `PointRule`, whose `version` field has a domain meaning that overrides the common convention: it is the monotonically incrementing per-`(community_id, category)` rule generation number. `PointRule` is not subject to optimistic concurrency control via the body's `version` field.

### 2.5. Nested-Path Resolution and Optimistic Concurrency

Every endpoint mounted under `/communities/{community_id}/...` resolves path identifiers left-to-right. If `community_id` does not exist, the response is `ERR_NOT_FOUND` regardless of whether the deeper identifiers are well-formed. The same rule applies sequentially down the chain — `household_id` is checked only after `community_id` has resolved, `resident_id` only after `household_id`, and so on for the deeper identifiers `disposal_id`, `violation_id`, `order_id`, `period_id`, `rule_id`, and `item_id`. Cross-tenant nesting also fails as `ERR_NOT_FOUND`: a `household_id` belonging to a different community than the path's `community_id` does not resolve.

Mutating endpoints accept an optional `version` field in the request body. When supplied, its value MUST equal the current `version` of the target row at the moment of mutation; if it does not, the request is rejected with `ERR_VERSION_CONFLICT`. When omitted, no concurrency check is performed and the mutation proceeds. After a successful mutation, the row's `version` increments by one and its `updated_at` is refreshed.

### 2.6. Numerical Precision, Rounding, and the Community Clock

All monetary, point, and weight quantities use **round half up** as the rounding rule. Per-disposal `base_points` are rounded to a whole integer before any bonus is added. Volume-to-weight conversion produces an `effective_weight_kg` value rounded to three decimal places. Per-violation `final_deduction_points` are rounded to a whole integer. Per-subject `ranking_score` values are rounded to a whole integer. The `rule_effectiveness_score` is rounded to one decimal place. Whenever the prose calls for "rounding," that rounding is half-up unless explicitly stated otherwise.

Time-of-day comparisons (peak-period windows, daily caps, ranking-window membership, consecutive-day streaks) are performed in the **community's IANA timezone**, recorded on `Community.timezone` (default `UTC`). The server runs on a logical clock that an operator can advance, and all "now" references — appeal-deadline comparisons, ranking-period close eligibility, disposal-backdating guards — read from that logical clock.

### 2.7. The Append-Only Points Ledger

The `Household.points_balance` field is a derived quantity. Its source of truth is the chronological stream of `PointsTransaction` rows for the household: each row carries a signed `amount` (positive for credits, negative for debits), a `balance_after` snapshot of `points_balance` immediately after the entry, a `kind` describing the cause, and `related_entity_kind` plus `related_entity_id` linking back to the originating `Disposal`, `RedemptionOrder`, or `Violation`. The system reconciles `Household.points_balance` to the running sum at every mutation: a disposal commit, a corrected misjudgment, a redemption confirmation, a redemption return, a violation creation, and a violation overturn each append exactly one entry (or, in the cascade case, several entries) and adjust `points_balance` by the same total. `Household.lifetime_points_earned` is a separate cumulative tracker of positive disposal credits that does NOT decrease on redemptions but DOES adjust under disposal correction or void.

The `kind` enum is fixed: `DISPOSAL_CREDIT` (a disposal awarded points), `REDEMPTION_DEBIT` (a redemption confirm consumed points), `REDEMPTION_REFUND` (a returned redemption re-credited points), `VIOLATION_DEBIT` (a violation deducted points), `VIOLATION_REVERSAL` (a violation overturn reinstated points), and `MISJUDGMENT_ADJUSTMENT` (a disposal correction or void produced a signed delta, or a cascade following a violation overturn re-baselined a subsequent violation's deduction).

### 2.8. State-Triggered Cascades and Ranking Invalidation

Because `Disposal` rows and `Violation` rows contribute to `RankingPeriod.leaderboard` values, any retrospective change to a row whose timestamp falls inside a still-open or already-closed-but-unpublished period invalidates that period's snapshot. Concretely: when a `Disposal` is corrected or voided, every `RankingPeriod` with `community_id` matching that disposal and a half-open window `[window_start, window_end)` containing `disposal_time` is checked. If such a period has status `CLOSED` and `published_at` is still null, its `leaderboard` is cleared to the empty array and its status is reverted to `OPEN` so that re-closing recomputes the snapshot. A period whose status is already `PUBLISHED` is NOT auto-recomputed — published leaderboards are immutable until an admin explicitly retracts (out of scope for this version, so once published they remain pinned). The same rule applies on `Violation` overturn against the violation's `occurred_at`.

Every mutation that touches a resource refreshes that resource's `updated_at` and increments its `version`. Cross-entity cascades — a `Disposal` correction adjusting `Household.points_balance` and `Household.lifetime_points_earned`, or a redemption confirm decrementing `MallItem.stock` — increment the version of each touched resource individually.

### 2.9. External Event Emission

Several state transitions emit external events to the IM, payment, and community-management sinks: a successful disposal commit emits `GARBAGE_DISPOSAL_COMMITTED`; a successful redemption confirm emits `REDEMPTION_CONFIRMED`; a successful violation recording emits `VIOLATION_RECORDED`; a successful ranking publish emits `RANKING_PUBLISHED`. Emission is best-effort and forms part of the transition's recorded side-effects; downstream consumers reconcile from event payloads independently.

### 2.10. Validation Ordering

When a single request fails more than one check, the rejection code is chosen by validation priority. Header presence is checked first (`ERR_AUTH_REQUIRED`); role recognition next (`ERR_UNKNOWN_ROLE`); role-to-endpoint permission third (`ERR_FORBIDDEN`); path identifier resolution fourth (`ERR_NOT_FOUND`); resident ownership for resident-owned actions fifth (`ERR_FORBIDDEN`); state-transition legality sixth (`ERR_INVALID_STATE`). Only after these structural checks pass does the system evaluate business rules — and those rules are themselves ordered. For appeals, the appeal-window check (`ERR_APPEAL_WINDOW_EXPIRED`) fires before any other business rule. For disposal creation, the order is: resident-active check (`ERR_RESIDENT_INACTIVE`), then active-rule existence (`ERR_NO_ACTIVE_RULE`), then weight/volume exclusivity (`ERR_WEIGHT_VOLUME_EXCLUSIVITY`), then disposal-time bounds (`ERR_DISPOSAL_TIME_INVALID`). For redemption submit, the listed-and-same-community check (`ERR_ITEM_UNAVAILABLE`) precedes lower-priority checks; for redemption confirm, the stock check (`ERR_INSUFFICIENT_STOCK`) precedes the balance check (`ERR_INSUFFICIENT_POINTS`). For point-rule activation, the "no other active rule" check (`ERR_RULE_ALREADY_ACTIVE`) precedes the no-backdating check (`ERR_RULE_BACKDATING`). For ranking-period close, the not-ended check (`ERR_RANKING_PERIOD_NOT_ENDED`) precedes others; for ranking-period creation, the overlap/contiguity check (`ERR_RANKING_PERIOD_OVERLAP`) is the only domain-level constraint. Generic body-shape validation (`ERR_VALIDATION`) sits below the business rules above but above optimistic-concurrency (`ERR_VERSION_CONFLICT`).

## 3. Business Logic & Workflows

### 3.1. Community Bootstrap, Households, and Residents

A `SystemOperator` bootstraps the program by creating a `Community` with a `name` (between 1 and 80 characters and globally unique), a `code` matching the pattern `CMTY-` followed by three to six digits and also globally unique, and an optional `timezone` IANA identifier defaulting to `UTC`. Communities are born `ACTIVE`; the alternative state in the enumeration is `ARCHIVED`. From that point onward, the day-to-day administration of the community is performed by a `CommunityAdmin`.

A `CommunityAdmin` registers a `Household` against a community by providing the household's `address` (between 1 and 200 characters) and a `building_code` (between 1 and 32 characters), which the system uses for building-level ranking aggregation. The household's owning `community_id` is taken from the URL path rather than from the body. Households are born `ACTIVE`; the lifecycle enumeration also recognizes `SUSPENDED` and `ARCHIVED`. The household's `head_resident_id` is null until the first resident registered against it completes identity verification; the system sets `head_resident_id` to that resident's `id` at the moment its `identity_status` flips to `VERIFIED`. Two reconciled counters — `points_balance` and `lifetime_points_earned` — are both initialized to zero and never updated directly; they reflect the running sum of the household's `PointsTransaction` stream.

A `CommunityAdmin` then registers each `Resident` against a household by supplying a `full_name` (between 1 and 80 characters), an `id_document_hash` (exactly 64 lowercase hexadecimal characters, derived from a government identity document), and a `relation` to the head — one of `HEAD`, `SPOUSE`, `CHILD`, `PARENT`, or `OTHER`. The resident's `household_id` is taken from the URL path. New residents are born with `identity_status` of `PENDING` and `account_status` of `INACTIVE`. They cannot submit disposals or redemptions until identity verification advances them to the `VERIFIED` / `ACTIVE` posture. The verify endpoint accepts a `decision` field; an APPROVE decision transitions `identity_status` from `PENDING` to `VERIFIED`, and additionally sets `account_status` to `ACTIVE` provided the account is not currently `RESTRICTED`; a REJECT decision flips `identity_status` to `REJECTED` while leaving `account_status` as `INACTIVE`. Verification requires that `id_document_hash` is set on the resident.

Administrators may temporarily restrict a verified resident — for instance, after a string of violations — by invoking the restrict capability with a body that supplies `until` (the wall-clock instant at which the restriction lifts) and a `reason`. The restrict transition keeps `identity_status` unchanged at `VERIFIED` and sets `account_status` to `RESTRICTED` and `restricted_until` to the supplied `until`. The transition does not auto-revert. Instead, the system operator's sweep capability lifts each expired restriction (transitioning `account_status` back to `ACTIVE` when `restricted_until` is at or before the logical clock) and reports the count of residents unrestricted under the response field `residents_unrestricted`. Residents in `INACTIVE` or `RESTRICTED` posture who attempt a disposal or redemption are rejected with `ERR_RESIDENT_INACTIVE`. Residents accumulate a `consecutive_disposal_days` counter — the longest run of consecutive calendar days in the community timezone ending today on which the resident has at least one disposal whose status is in `{COMMITTED, CORRECTED}`. Voided disposals do not contribute. The streak resets to zero when a day passes with no qualifying disposal.

### 3.2. Point Rules and Rule Effectiveness

For each garbage `category` — `RECYCLABLE`, `HAZARDOUS`, `KITCHEN`, or `OTHER` — a community must publish a `PointRule` before residents can earn points in that category. Rules are versioned per `(community_id, category)`: the `version` integer starts at 1 and increments by one for every published successor. A rule is created in `DRAFT` status with several scoring parameters and is then explicitly activated. The creation payload supplies a `base_rate_per_kg` (a non-negative number no greater than 1000, two decimal places — the base points earned per 1.0 kg of correctly classified disposal), a `bonus_consecutive_threshold_days` (an integer between 1 and 365, defaulting to 7, that determines the streak length at which the consecutive-day bonus activates), a `bonus_consecutive_multiplier` (a number between 1.0 and 5.0 with two decimal places, default 1.20), a peak-period window described by `peak_period_start_hour` and `peak_period_end_hour` (integers in the range 0 to 23, defaulting to 7 and 9 respectively, interpreted as a half-open window in the community's timezone), a `peak_period_bonus_flat` (flat integer points added when the disposal time falls inside that window, default 5), a `category_bonus_flat` (flat integer points added when the rule's category matches a community-promoted category, default 0), and a `daily_cap_points` (the maximum total points that may be credited to a single household per community-local calendar day across all categories, default 200). The rule's category is supplied at creation.

Activation by a `CommunityAdmin` requires that the rule is currently in `DRAFT` and that no other `PointRule` with the same `(community_id, category)` is currently `ACTIVE`; a competing predecessor must be retired first or the activation is rejected with `ERR_RULE_ALREADY_ACTIVE`. Two simultaneous activations targeting the same `(community_id, category)` serialize so exactly one wins; the loser receives `ERR_RULE_ALREADY_ACTIVE`. The activation body supplies an `activated_at` instant that must be at or after the current logical clock — backdating is rejected with `ERR_RULE_BACKDATING`. On success, the rule transitions `DRAFT → ACTIVE`, its `activated_at` is set to the supplied value, and an `AuditLog` entry of action `RULE_PUBLISHED` and subject kind `POINT_RULE` is appended. Retirement is performed via a separate capability that only succeeds when the rule is currently `ACTIVE`: it transitions to `RETIRED`, sets `retired_at` to the current logical clock, and ends the rule's effective window. A rule's effectivity is the half-open interval `[activated_at, retired_at)` — a rule is eligible to score a disposal only when its `activated_at` is at or before the disposal's `disposal_time` and either `retired_at` is null or `retired_at` is strictly after `disposal_time`.

A separate read-only capability returns rule effectiveness for an individual rule: it reports the rule's `participation_tier`, its raw `participation` count, its `avg_accuracy`, its `misjudgment_ratio`, and its weighted `score`. The participation count is the number of distinct households with at least one `COMMITTED` disposal applying this rule across the rule's effective window. The average accuracy is the mean of `accuracy_score` across `COMMITTED` disposals applying this rule. The misjudgment ratio is the count of disposals applying this rule whose current status is `CORRECTED` divided by the maximum of 1 and the total count of disposals applying this rule. The participation tier is then chosen by the raw participation count: `HIGH` when participation is at least 50, `MEDIUM` when participation is at least 10 but less than 50, and `LOW` otherwise. The tier determines a weight vector: `HIGH` gives weight 0.50 to accuracy, 0.30 to misjudgment, and 0.20 to participation; `MEDIUM` gives 0.40, 0.40, and 0.20; `LOW` gives 0.30, 0.50, and 0.20. The weighted score is 100 multiplied by the sum of three terms — the accuracy weight times `avg_accuracy`, the misjudgment weight times one minus `misjudgment_ratio`, and the participation weight times `min(1.0, participation / 100.0)` — the entire expression rounded half-up to one decimal place. Two evaluation-order requirements pin the calculation: the participation tier is determined from the raw participation count BEFORE the weighted score is computed, and the score is computed using that same tier — the tier is never re-derived from the score itself, even if the score would land in a different categorical bucket.

### 3.3. Disposal Submission and Points Award

A `Resident` submits a disposal under their own household by recording the `disposal_time` (which must be at or before the current logical clock and no earlier than 24 hours before it, with violations of either bound rejected as `ERR_DISPOSAL_TIME_INVALID`), the `location_code` (the bin or station code within the community, between 1 and 32 characters), a `declared_category` (the category the resident asserts at submission), an `actual_category` (the category verified by the scoring mechanism — equal to the declared category when scoring agrees), a `scoring_method` (one of `MANUAL`, `AI`, or `SCALE`), an `accuracy_score` in the closed interval [0.0, 1.0] with three decimal places, an `evidence_uri` linking to an archived photo or video (non-empty, no more than 500 characters), and either a `weight_kg` (a non-negative number no greater than 500.0 with three decimal places) OR a `volume_liters` (a non-negative number no greater than 5000.0 with three decimal places). The body must also identify the submitting `resident_id`. Exactly one of `weight_kg` and `volume_liters` must be supplied — both null or both set is rejected with `ERR_WEIGHT_VOLUME_EXCLUSIVITY`. Resident-ownership requires that `X-User-ID` equals the submitting resident's `id` and that the resident's `household_id` matches the path; the resident must also have `identity_status` of `VERIFIED` AND `account_status` of `ACTIVE`. The system resolves which `PointRule` to apply by finding a rule whose `community_id` equals the household's community, whose `category` equals `actual_category`, and whose status is `ACTIVE` at `disposal_time`; the absence of such a rule yields `ERR_NO_ACTIVE_RULE`. The resolved rule's `id` is pinned onto `applied_rule_id` so that subsequent corrections recompute against the rule version active at the original disposal time, not against whatever rule is current at the moment of correction. The denormalized `community_id` is captured on the disposal at commit for ranking aggregation.

Once these checks pass, the system computes the points award. Step one: resolve the effective weight. When `weight_kg` is supplied directly, use it. When only `volume_liters` is supplied, multiply it by the category-specific conversion constant — 0.150 kg per liter for `RECYCLABLE`, 0.500 kg per liter for `HAZARDOUS`, 0.800 kg per liter for `KITCHEN`, and 0.300 kg per liter for `OTHER` — and round half-up to three decimal places. Step two: compute the accuracy multiplier from the scoring method. Under `MANUAL`, the multiplier is 0.50 plus 0.50 times the accuracy score — linearly interpolating from 0.50 at score 0.0 to 1.00 at score 1.0. Under `AI`, the multiplier is a stepwise function: 1.00 when the score is at least 0.80; otherwise 0.70 when the score is at least 0.50; otherwise 0.40. Under `SCALE`, the multiplier is always 1.00 regardless of the accuracy score, though the score is still recorded for audit. Step three: compute the base points as the rule's `base_rate_per_kg` multiplied by the effective weight in kilograms multiplied by the accuracy multiplier, rounded half-up to a whole integer. This rounding happens per disposal — it is never deferred to a later aggregation step. Step four: add the bonus terms, all integer-valued. If the resident's `consecutive_disposal_days` at the moment of commit is at or above the rule's `bonus_consecutive_threshold_days`, the consecutive-day bonus is the base points multiplied by one less than the rule's `bonus_consecutive_multiplier`, rounded half-up to a whole integer — this delta is added on top of the base. If the disposal's local-time hour (the hour-of-day in the community timezone) falls within the half-open peak-period window — at or after `peak_period_start_hour` and strictly before `peak_period_end_hour` — the rule's `peak_period_bonus_flat` is added. The rule's `category_bonus_flat` is added unconditionally (it may be zero). The sum is the `raw_points` for this disposal. Step five: apply the daily cap. Sum the `amount` of every existing `PointsTransaction` for this household whose `kind` is `DISPOSAL_CREDIT` and whose `created_at` falls on the same community-local calendar day as `disposal_time`, excluding this disposal's not-yet-written contribution. The headroom is the maximum of zero and the rule's `daily_cap_points` minus that running sum. The credited `awarded_points` is the minimum of `raw_points` and headroom; the difference, captured as `cap_overflow_points`, records how many raw points were dropped at the cap. Step six: append a `PointsTransaction` whose `kind` is `DISPOSAL_CREDIT`, whose `amount` equals `awarded_points`, whose `related_entity_kind` is `DISPOSAL`, and whose `related_entity_id` is the disposal's id; update `Household.points_balance` and `Household.lifetime_points_earned` upward by `awarded_points`; recompute `Resident.consecutive_disposal_days`; and emit `GARBAGE_DISPOSAL_COMMITTED` to the IM and community-management sinks. The disposal transitions from `PENDING` to `COMMITTED`. Disposal commits that would have a `disposal_time` falling inside an already-`CLOSED`-or-`PUBLISHED` ranking period window for this community are rejected with `ERR_RANKING_PERIOD_CLOSED`.

### 3.4. Disposal Correction and Void

A `CommunityAdmin` may correct a disposal that was mis-scored — the bag was photographed and the AI mis-classified it, or the scale was miscalibrated. The correct capability operates only on disposals whose current status is `COMMITTED`; it accepts an optional `actual_category` override, an optional `accuracy_score` override, and a required non-empty `reason`. The system recomputes the points award using the SAME `applied_rule_id` that was pinned at the original commit (the rule version is not re-resolved), feeding the override fields into steps two through five above; it obtains a `new_awarded_points` integer. It appends a `PointsTransaction` whose `kind` is `MISJUDGMENT_ADJUSTMENT` and whose `amount` is `new_awarded_points` minus the old `awarded_points` — signed positive if the correction increased the credit, signed negative if it reduced it. It updates the disposal's `awarded_points` to the new value and refreshes `cap_overflow_points`. It adjusts `Household.points_balance` and `Household.lifetime_points_earned` by the same signed delta; `lifetime_points_earned` is clamped so that the per-disposal contribution cannot go below zero (in practice, if the original was 30 and the new is 20, lifetime decreases by 10; if the original was 20 and the new is 30, lifetime increases by 10). It invalidates every `OPEN` `RankingPeriod` whose window contains the disposal's `disposal_time` by clearing the period's `leaderboard` to the empty array, and analogously reverts a `CLOSED`-but-unpublished period back to `OPEN`. It appends an `AuditLog` entry of action `POINTS_ADJUSTMENT` and subject kind `DISPOSAL`. The disposal transitions `COMMITTED → CORRECTED`.

The void capability — also admin-only and only valid when the disposal is currently `COMMITTED` or `CORRECTED` — accepts only a non-empty `reason`. It appends a `PointsTransaction` whose `kind` is `MISJUDGMENT_ADJUSTMENT` and whose `amount` is the negative of the disposal's current `awarded_points`; it decreases `Household.points_balance` and `Household.lifetime_points_earned` by `awarded_points`; it recomputes `Resident.consecutive_disposal_days` so that this voided disposal no longer contributes; it invalidates overlapping ranking periods exactly as the correct capability does; and it appends an `AuditLog` entry of action `POINTS_ADJUSTMENT` and subject kind `DISPOSAL`. The disposal terminates at `VOIDED`.

### 3.5. The Redemption Mall

Each community runs a small mall of items that residents may redeem with points. A `CommunityAdmin` lists an item by supplying a display `name` (between 1 and 120 characters), the `cost_points` required per unit (a positive integer no greater than 1,000,000), an initial `stock` count (a non-negative integer), and the fulfillment `channel` (`ONLINE` or `STATION`). Items are born `LISTED`; the alternative status is `DELISTED`. Admins may subsequently adjust an item's `stock`, `cost_points`, or `status` through a partial-update capability that also accepts an optional `version` for optimistic concurrency.

A `Resident` submits a redemption order by referencing a `mall_item_id`, the `quantity` to redeem (a positive integer no greater than 50), the `household_id` (which must match the household of the resident referenced by `X-User-ID`), and the submitting `resident_id` (which must equal `X-User-ID`). Submit requires that the resident is currently `VERIFIED` and `ACTIVE` (else `ERR_RESIDENT_INACTIVE`) and that the target item is currently `LISTED` AND its `community_id` matches the path's community (else `ERR_ITEM_UNAVAILABLE`). On submit, the system snapshots the item's current `cost_points` onto the order as `unit_cost_points` and snapshots the item's current `channel` onto the order as `channel`. The order's `total_cost_points` is the product of `quantity` and `unit_cost_points`. The order is born `SUBMITTED`; no stock has yet been decremented and no points have yet been debited.

Admins then confirm or reject the order. Reject requires the order is currently `SUBMITTED` and performs no stock or points movement; it transitions to `REJECTED` (terminal). Confirm requires `SUBMITTED` AND `MallItem.stock` at or above the order's `quantity` (else `ERR_INSUFFICIENT_STOCK`) AND `Household.points_balance` at or above `total_cost_points` (else `ERR_INSUFFICIENT_POINTS`); on success it decrements `MallItem.stock` by `quantity`, appends a `PointsTransaction` whose `kind` is `REDEMPTION_DEBIT` and whose `amount` is the negative of `total_cost_points`, reduces `Household.points_balance` by `total_cost_points`, sets `confirmed_at` to the current logical clock, and emits `REDEMPTION_CONFIRMED` to the payment sink. Two simultaneous confirms on the same order serialize first-writer-wins on `RedemptionOrder.status`; the loser receives `ERR_INVALID_STATE`. A simultaneous confirm-and-reject on the same order serializes the same way; the loser receives `ERR_INVALID_STATE`. Two confirms competing for the last available stock unit serialize first-writer-wins on the stock decrement; orders that would drive `MallItem.stock` below zero are rejected as `ERR_INSUFFICIENT_STOCK`. Two confirms competing for the last available household point balance serialize first-writer-wins on the balance debit; orders that would drive `points_balance` below zero are rejected as `ERR_INSUFFICIENT_POINTS`.

Confirmed orders progress through fulfillment by admin action: fulfill (requires `CONFIRMED`, performs no further stock or points movement, transitions to `FULFILLED`); deliver (requires `FULFILLED`, sets `delivered_at` to the current logical clock, transitions to `DELIVERED` which is terminal). A return capability operates only on `FULFILLED` orders, requires a non-empty `reason`, re-credits stock by adding `quantity` back to the item, appends a `PointsTransaction` whose `kind` is `REDEMPTION_REFUND` and whose `amount` is the positive `total_cost_points`, and restores `Household.points_balance` by the same amount. The compensating invariant is: between submit and confirm followed by return, the sum of `Household.points_balance` and the total cost across confirmed-but-not-returned orders is conserved. The order transitions to `RETURNED` (terminal). Attempts to invoke any redemption transition on an order already in a terminal state (`DELIVERED`, `REJECTED`, or `RETURNED`) are rejected with `ERR_DELIVERY_TERMINAL`.

### 3.6. Violations, Appeals, and the Repeat-Offender Escalator

A `CommunityAdmin` records a violation by naming the accused `resident_id`, the `violation_type` (one of `MIS_SORTING`, `LITTERING`, or `NO_CLASSIFICATION`), the `occurred_at` instant (which must be at or before the current logical clock), and an `evidence_uri` (non-empty, no more than 500 characters). The resident must exist and not be in the `ARCHIVED` terminal state. The system denormalizes `household_id` and `community_id` from the resident at creation.

Recording is structured as a self-referential `NEW → NEW` transition so that the cascade of side-effects is anchored to creation rather than to entity birth. The system computes `repeat_count_in_window` as the count of prior `Violation` rows for the same resident and the same `violation_type` whose status is one of `NEW`, `APPEALED`, `UNDER_REVIEW`, or `UPHELD` and whose `occurred_at` falls within the trailing 30-day window — inclusive of this new violation. From `repeat_count_in_window` it picks the `escalation_multiplier` by the largest tier minimum at or below the count: one violation maps to 1.00; two violations to 1.50; three violations to 2.00; four or more violations to 3.00. The `base_deduction_points` is fixed by violation type: 20 points for `MIS_SORTING`, 50 points for `LITTERING`, and 30 points for `NO_CLASSIFICATION`. The `final_deduction_points` is `base_deduction_points` multiplied by `escalation_multiplier`, rounded half-up to a whole integer. The system appends a `PointsTransaction` whose `kind` is `VIOLATION_DEBIT` and whose `amount` is the negative of `final_deduction_points`; it reduces `Household.points_balance` by `final_deduction_points` even when the balance would become negative (violation deductions explicitly may drive `points_balance` below zero). It computes `appeal_deadline_at` as `occurred_at` plus 14 days (the appeal window in days). It appends an `AuditLog` entry of action `VIOLATION_RECORDED` and subject kind `VIOLATION`, and emits `VIOLATION_RECORDED` to the IM and community-management sinks. The violation is born with status `NEW`, `appeal_filed_at` null, and `appeal_round` zero.

A `Resident` may appeal their own violation by invoking the appeal capability with a non-empty `reason`. The appeal is allowed only when `now()` is strictly before `appeal_deadline_at` (else `ERR_APPEAL_WINDOW_EXPIRED`), `appeal_round` is strictly less than 2 (else `ERR_VIOLATION_REAPPEAL_LIMIT`), and `X-User-ID` equals the violation's `resident_id` and `X-User-Role` is `Resident` (else `ERR_FORBIDDEN`). On a first appeal — current status `NEW` — the violation transitions `NEW → APPEALED`, `appeal_filed_at` is set to the current logical clock, and `appeal_round` increments to 1. On a second appeal — current status `UPHELD` and `appeal_round` equal to 1 — the violation transitions `UPHELD → APPEALED`, `appeal_filed_at` is updated to the current logical clock, and `appeal_round` becomes 2. The cycle UPHELD-then-APPEALED is permitted exactly once. Two simultaneous appeals on the same violation serialize first-writer-wins on `Violation.status`; the loser receives `ERR_INVALID_STATE`.

An `AppealReviewer` takes an appealed violation under review (transitioning `APPEALED → UNDER_REVIEW` with no points movement) and then decides it. The decide capability accepts a `decision` field whose value is either `UPHOLD` or `OVERTURN`, plus a non-empty `reason`. An UPHOLD decision transitions `UNDER_REVIEW → UPHELD`, performs no points movement (the deduction was already applied at creation), and appends an `AuditLog` entry of action `VIOLATION_APPEAL_DECISION` and subject kind `VIOLATION`. An OVERTURN decision transitions `UNDER_REVIEW → OVERTURNED` (terminal) and cascades: the system appends a `PointsTransaction` whose `kind` is `VIOLATION_REVERSAL` and whose `amount` is the positive `final_deduction_points` of this violation, restores `Household.points_balance` by the same amount, and then walks every subsequent `Violation` row — that is, every other violation for the same resident and the same `violation_type` whose `occurred_at` is strictly after this one and whose current status is in `{NEW, APPEALED, UNDER_REVIEW, UPHELD}`. For each such subsequent violation, the system recomputes `repeat_count_in_window` while excluding this overturned violation, re-derives the escalation multiplier, recomputes `final_deduction_points`, appends a `PointsTransaction` whose `kind` is `MISJUDGMENT_ADJUSTMENT` and whose `amount` is the old final deduction minus the new final deduction, and adjusts `Household.points_balance` by the same delta. The system invalidates every `OPEN`-or-unpublished-`CLOSED` `RankingPeriod` whose window contains the original violation's `occurred_at`, and appends an `AuditLog` entry of action `VIOLATION_APPEAL_DECISION` and subject kind `VIOLATION`. The compensating invariant is that the sum of disposal credits plus violation reversals, minus the sum of violation debits plus cascade misjudgment adjustments, conserves `Household.lifetime_points_earned` across an overturn.

### 3.7. Ranking Periods and Leaderboard Snapshots

A `CommunityAdmin` creates a `RankingPeriod` by specifying the `granularity` (one of `WEEKLY`, `MONTHLY`, or `YEARLY`), the `dimension` (the leaderboard subject: `HOUSEHOLD`, `BUILDING`, or `COMMUNITY`), the inclusive `window_start`, and the exclusive `window_end` — the window is half-open `[window_start, window_end)`. Within the same `(community_id, granularity, dimension)` triple, period windows must not overlap any existing period; for `WEEKLY` and `MONTHLY` granularities, the new period must additionally be contiguous with the immediately prior period, meaning its `window_start` equals the prior period's `window_end`. Violations of either constraint are rejected with `ERR_RANKING_PERIOD_OVERLAP`. Periods are born `OPEN`; their `leaderboard` is the empty array; `published_at` is null.

When the window has ended — that is, the current logical clock is at or after `window_end` — an admin may close the period. Closing earlier is rejected with `ERR_RANKING_PERIOD_NOT_ENDED`. On close, the system computes the leaderboard. The eligible disposals are those whose `community_id` matches the period's, whose status is exactly `COMMITTED` (disposals in `CORRECTED` or `VOIDED` are explicitly excluded from ranking — even though `CORRECTED` still counts for the resident's streak), and whose `disposal_time` falls inside `[window_start, window_end)`. The eligible violations are those whose `community_id` matches the period's, whose status is `UPHELD`, and whose `occurred_at` falls inside the same window. Then for each subject in the dimension's subject set (households for `HOUSEHOLD`, building codes for `BUILDING`, the whole community as a single subject for `COMMUNITY`), the system sums the `awarded_points` of eligible disposals belonging to the subject to obtain `earned`, sums the `final_deduction_points` of eligible violations belonging to the subject to obtain `deducted`, and computes a `raw_score` of `earned` minus `deducted`. The granularity then determines how `raw_score` becomes `score`. Under `WEEKLY`, `score` equals `raw_score` (no normalization). Under `MONTHLY`, `score` equals `raw_score` multiplied by the canonical month length of 30 and divided by the number of days in the window (the difference in days between `window_end` and `window_start`), the entire expression rounded half-up to a whole integer. Under `YEARLY`, the system computes a quality ratio: with `denom` defined as `earned` plus the absolute value of `deducted`, `quality` equals `earned / denom` when `denom` is positive and zero otherwise; `score` equals `raw_score` multiplied by 0.5 plus 0.5 times `quality`, rounded half-up to a whole integer. The leaderboard is sorted by `score` descending; ties are broken by `subject_id` ascending lexicographically. Each leaderboard entry is an object with `subject_id`, `subject_kind`, `score`, and `rank` fields. The period transitions `OPEN → CLOSED` and the leaderboard is persisted on the row. If the eligible subject set is empty (no eligible disposals AND no eligible violations), the leaderboard is the empty array.

Concurrent disposal commits and ranking closes on the same window serialize first-writer-wins on `RankingPeriod.status` transitioning `OPEN → CLOSED`; once the close has succeeded, subsequent disposal commits with `disposal_time` falling inside that window are rejected with `ERR_RANKING_PERIOD_CLOSED`.

When the period is in `CLOSED` (and `published_at` is still null), an upstream `Disposal` correction or void or `Violation` overturn whose timestamp falls inside the window reverts the period back to `OPEN` by clearing the leaderboard. The admin must re-close before publish. Publish requires that the period is currently `CLOSED` and that the leaderboard is non-empty (else `ERR_RANKING_EMPTY`). On publish, the system sets `published_at` to the current logical clock, transitions to `PUBLISHED` (terminal), appends an `AuditLog` entry of action `RANKING_PUBLISHED` and subject kind `RANKING_PERIOD`, and emits `RANKING_PUBLISHED` to the IM and community-management sinks. Published periods are not auto-recomputed.

### 3.8. Audit Logging and Read-Only Histories

Every administratively significant action appends an `AuditLog` entry. The entry captures `actor_role` (the value of `X-User-Role` on the originating request), `actor_id` (the value of `X-User-ID`), `action` (one of `POINTS_ADJUSTMENT`, `VIOLATION_RECORDED`, `VIOLATION_APPEAL_DECISION`, `RULE_PUBLISHED`, or `RANKING_PUBLISHED`), `subject_kind` (one of `DISPOSAL`, `VIOLATION`, `POINT_RULE`, `RANKING_PERIOD`, or `HOUSEHOLD`), `subject_id`, snapshots `before` and `after` of the relevant fields, and a human-supplied `reason`. The `reason` is required (1 to 500 characters) for `POINTS_ADJUSTMENT` and `VIOLATION_APPEAL_DECISION` actions. The household's `PointsTransaction` history is read-only and is the canonical archive used to reconcile `points_balance`; querying it accepts optional `kind`, `from`, and `to` filters in addition to `limit` and `offset`.

### 3.9. Operator Capabilities for Deterministic Testing

The system runs on a logical clock that an admin-only test-driving capability advances to a supplied `to` instant (an ISO 8601 UTC timestamp). The response carries the new logical `now`. A second operator capability runs an automatic sweep that lifts every `Resident.restricted_until` expiry — that is, for every resident whose `account_status` is `RESTRICTED` and whose `restricted_until` is at or before the current logical clock, the system transitions `account_status` back to `ACTIVE`. The response carries the count of residents whose restriction was lifted under the field `residents_unrestricted`.
