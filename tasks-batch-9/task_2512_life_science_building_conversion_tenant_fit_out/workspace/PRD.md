# Life Science Conversion API — Product Requirements Document

## 1. Introduction

Converting a conventional office asset into a life science building is not a renovation; it is an underwriting exercise conducted against physics. A floor plate that cannot carry the load, cannot be reached by an exhaust riser, or trembles above the vibration criterion an analytical instrument needs will never host a laboratory, no matter how attractive the rent. This API is the system of record a life science landlord uses to make that judgement defensible: it captures the base building's nameplate characteristics and its field-measured reality, scores the two against a published rubric, and only then permits capital to be committed to conversion scope for lab exhaust, emergency power, chemical storage and waste handling.

Downstream of the base-building decision sits a second, entirely different negotiation. Each prospective tenant argues for a tenant improvement allowance rich enough to cover lab-specific cost premiums, and the landlord argues back — turn by turn, with an offer that goes stale if nobody accepts it. Once terms are struck, the allowance becomes a ledger that must balance at every instant, the fit-out becomes a set of phase packages that must be sequenced around occupied neighbours and vibration-sensitive equipment, the hazardous materials the tenant intends to use must fit inside code-mandated control area limits shared with every other tenant on the same plate, and the shared amenities — glasswash, autoclaves, an NMR suite — must be programmed so that no two tenants collide. At the far end of the term, restoration obligations must be valued, escrow applied, and unused allowance forfeited.

The product requirement, therefore, is a single API surface where all of this is explicit, ordered and reversible-by-audit: every state change carries its precondition, every dollar movement carries its rounding rule, every safety refusal carries the code that names it, and no operator can quietly overwrite a colleague's decision because they were reading a stale copy of the building.

## 2. Global Specifications & System-Wide Principles

This section fixes the contract-level behaviour that holds for every resource in the system. Where a rule here appears again in Section 3 it is reinforcement, never contradiction.

### 2.1. User and Role-Based Access Control

Every request — reads included — must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names the capacity in which that principal is acting. A request missing either header, or carrying a value in `X-User-Role` that is not one of the five recognised roles, is rejected with `ERR_UNAUTHORIZED` (HTTP 403). A request whose headers are well formed but whose role is not permitted to invoke the operation is rejected with the same `ERR_UNAUTHORIZED`.

The five roles are spelled exactly `LandlordAssetManager`, `BaseBuildingEngineer`, `Tenant`, `AHJPermitOfficer` and `CommissioningAgent`.

Four of the five are operator roles whose identity is opaque. When `X-User-Role` is `LandlordAssetManager`, `X-User-ID` is an opaque asset-management operator identifier not tied to any persisted entity; the server records it where a rule tells it to — as `decided_by_user_id` on an assessment, as `terms_accepted_by_user_id` or `executed_by_user_id` on a lease, as `authored_by_user_id` or `accepted_by_user_id` on a proposal — and compares those recorded values against each other for separation-of-duties purposes, but it never compares `X-User-ID` to any entity's `id`. The same holds for `BaseBuildingEngineer`, whose `X-User-ID` is an opaque engineer identifier; for `AHJPermitOfficer`, whose `X-User-ID` is an opaque permit-officer identifier; and for `CommissioningAgent`, whose `X-User-ID` is an opaque agent identifier that is compared against a commissioning record's `executed_by_user_id` when a result is witnessed.

`Tenant` is the one entity-backed role. When `X-User-Role` is `Tenant`, `X-User-ID` is the `id` of the acting `Tenant` record; ownership checks on any resource that references a `Tenant` compare the resource's `tenant_id` — reached through the lease that owns the fit-out project, phase, permit or allocation in question — to `X-User-ID`. A `Tenant` that reaches for another tenant's lease, project, permit or allocation, whether to read it or to mutate it, receives `ERR_UNAUTHORIZED`.

Role authorisation is a coarse gate applied before domain rules: it decides whether the caller may attempt the operation at all. Section 4 lists the authorised roles per endpoint; Section 3 explains the finer-grained ownership and separation-of-duties tests that a caller who passes the gate must still satisfy.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` controls page size; it defaults to 10, may not be smaller than 1 and may not be larger than 100. `offset` controls the number of records skipped before the page begins; it defaults to 0 and may not be negative. A value outside those bounds, or a non-integer value, is rejected with `ERR_VALIDATION`.

Unless a subsection states otherwise, list results are ordered by `created_at` ascending, so paging through a collection walks it in the order the records were written. The `meta` object of a list response carries `limit` and `offset` as they were applied, `total_count` as the number of records matching the filter before paging, and `has_more` as a boolean that is true when records remain beyond the current page.

Filter parameters are documented with the workflows they serve. They are always optional and always combine conjunctively — supplying `building_id` and `status` together returns only records matching both. An unknown enum value in a filter is a malformed request and yields `ERR_VALIDATION` rather than an empty page.

### 2.4. Resource Identity, Audit Fields and the Logical Clock

All fourteen resource types share four server-managed properties. `id` is a server-minted UUID carrying no type prefix. `created_at` is the ISO 8601 UTC instant of creation with three fractional digits. `updated_at` is the ISO 8601 UTC instant of the most recent mutation, equal to `created_at` immediately after creation. `version` is an integer that begins at 1 on creation and increases by exactly 1 on every mutation of that record, including mutations reached indirectly through a cascade. No resource in this system omits `updated_at` or `version`.

Clients never supply `id`, `created_at`, `updated_at` or `version` on creation, and never supply computed fields; a body that carries them is ignored on those keys rather than honoured.

Time in this system is a logical clock, not the wall clock. It starts at `2026-08-01T00:00:00Z` and an operator in any of the five roles may move it by supplying a `current_utc` instant to the clock-setting capability, which echoes back the `current_utc` now in force. Every temporal rule in this document — proposal expiry, delivery windows, the vibration buffer, amenity windows, expiration notices, the `completed_at`, `permit_applied_at`, `permit_issued_at`, `accepted_at` and `executed_at` stamps — is evaluated against that logical instant. "Now" always means the logical clock's current value.

### 2.5. Flat Collections and Left-to-Right Path Resolution

The API is deliberately flat: buildings, floors, suitability assessments, conversion scope items, shared amenities, tenants, leases, TI proposals, fit-out projects, phase packages, capacity reservations, hazardous material use permits, amenity allocations and commissioning records all live as peer collections at the URL root, and relationships between them are carried by explicit identifier fields in request bodies rather than by deep URL nesting. The only nested paths are creation and reverse-reachability sub-resources — creating a floor, an assessment, a scope item, a shared amenity, a TI proposal, a phase package or a commissioning record under its parent, and listing those children back.

Where a path does carry more than one identifier, it is resolved strictly left to right, and the first identifier that names nothing determines the error. A request against a floor listing under a building that does not exist yields `ERR_BUILDING_NOT_FOUND`, never a floor-level code. The not-found codes are `ERR_BUILDING_NOT_FOUND`, `ERR_FLOOR_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_SCOPE_ITEM_NOT_FOUND`, `ERR_TENANT_NOT_FOUND`, `ERR_LEASE_NOT_FOUND`, `ERR_PROPOSAL_NOT_FOUND`, `ERR_PROJECT_NOT_FOUND`, `ERR_PHASE_NOT_FOUND`, `ERR_RESERVATION_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_AMENITY_NOT_FOUND`, `ERR_ALLOCATION_NOT_FOUND` and `ERR_COMMISSIONING_RECORD_NOT_FOUND`, each returning HTTP 404. An identifier supplied in a request body that names nothing produces the same code for the entity it failed to resolve.

The path placeholders used throughout Section 4 name exactly one entity each, and each resolves to that entity's `id`: `buildingId` a building, `floorId` a floor plate, `assessmentId` a suitability assessment, `itemId` a conversion scope item, `amenityId` a shared amenity, `tenantId` a tenant, `leaseId` a lease, `proposalId` a TI proposal round, `projectId` a fit-out project, `phaseId` a phase package, `reservationId` a capacity reservation, `permitId` a hazardous material use permit, `allocationId` an amenity allocation, and `recordId` a commissioning record. A placeholder value that is not a well-formed UUID is treated as naming nothing and yields that entity's not-found code rather than `ERR_VALIDATION`.

### 2.6. Version Preconditions on Contended Base-Building and Lease Writes

Two write operations in this system create a child record whose validity depends on a parent the client has already read. Both require the client to declare which revision of that parent it reasoned about, and both reject the write when that declaration no longer describes the parent.

A `POST /capacity-reservations` request must carry `expected_building_version` as a required field holding the client's last observed `version` of the building the reservation will draw from. If it does not equal the building's current `version`, the create is rejected with `ERR_STALE_BUILDING_VERSION` (HTTP 412). The invariant this protects is that `exhaust_available_cfm` and `power_available_kw` must never go negative: another actor may have created a reservation, cancelled one, or completed a lab exhaust scope item since the client's read, each of which advances the building's `version` and changes the pool the client believed it was drawing against. Rejecting the stale declaration is what prevents the riser from being overdrawn, and it is observable purely sequentially — read the building's `version`, let any other request bump it, then send the old value and receive 412.

A `POST /leases/{leaseId}/ti-proposals` request must carry `expected_lease_version` as a required field holding the client's last observed `version` of the lease. If it does not equal the lease's current `version`, the create is rejected with `ERR_STALE_LEASE_VERSION` (HTTP 412). The invariant here is that at most one TI proposal per lease may be `OPEN` and that each new round must supersede the round its author actually read: if the counterparty has already countered or accepted since the read, posting against the superseded state would either open a second live round or counter a deal that has already closed.

No other endpoint accepts a version field. In particular, accepting a proposal, executing a lease, drawing on the allowance, scheduling a phase, cancelling a reservation and deciding a permit take no `expected_*_version` input; their safety comes from state preconditions rather than from a revision declaration.

### 2.7. Rounding Discipline for Money, Gallons, Airflow and Scores

Every monetary amount, every gallon quantity, every airflow and power figure and every utilisation percentage is carried and compared to two decimal places, rounded half up. The single exceptions are the suitability score, which is carried to one decimal place, the utility headroom ratio, which is carried to four decimal places, and the four dimension credits, which are whole numbers. All rounding is half up: a value exactly at the midpoint rounds away from zero.

Rounding is applied where the rule says it is applied and nowhere else. Weighted scores are rounded once at the end of the weighted sum, never term by term. The per-phase allocation of a disbursement is rounded line by line and the leftover cent is then reassigned, never absorbed. Chained calculations that feed one another — a per-square-foot allowance into a dollar authorisation, an authorisation into an escrow requirement — round at each named step, and the rounded value is what the next step consumes.

### 2.8. Rejection Precedence

When a request would fail several checks, exactly one error is returned, chosen by a fixed precedence. Four global steps run first, in this order: a malformed body, an unknown enum value or a missing required input yields `ERR_VALIDATION` (HTTP 422); a missing or unrecognised role header, or a role not permitted to invoke the operation, yields `ERR_UNAUTHORIZED` (HTTP 403); an entity named by a path parameter that does not exist yields that entity's not-found code (HTTP 404); and an identifier in the body that resolves to nothing yields the corresponding not-found code.

Only after those four steps do the domain rules run, and each endpoint's domain rules have their own documented order. Section 3 states that order explicitly wherever an endpoint carries more than one domain rule, because the order is part of the contract: a request that violates two rules must surface the earlier one. Where a version precondition is one of an endpoint's domain rules, it runs first among them.

### 2.9. Separation of Duties Across the Deal and the Commissioning Bench

Three separations are enforced by identity comparison rather than by role.

A suitability assessment is scored and submitted by a `BaseBuildingEngineer` and decided by a `LandlordAssetManager`; the engineer may never accept their own score, which is a role-level refusal producing `ERR_UNAUTHORIZED`.

A TI proposal may not be accepted by the party that wrote it. The accepting `X-User-ID` must differ from the proposal's `authored_by_user_id`, and the accepting caller's party must differ from the proposal's `proposed_by`; a violation of either half yields `ERR_SELF_ACCEPT_FORBIDDEN` (HTTP 403). Separately, the operator who executes the lease must be neither the author of the winning proposal nor the person who accepted it: if the executing `X-User-ID` equals the accepted proposal's `authored_by_user_id`, or equals the lease's `terms_accepted_by_user_id`, execution is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

On the commissioning bench, the technician who ran a script may not attest to its outcome. When a result is recorded, the supplied `witnessed_by_user_id` is compared to the record's `executed_by_user_id`, and equality is refused with `ERR_WITNESS_CONFLICT` (HTTP 403).

### 2.10. Cascade Propagation and the Two Conservation Identities

Many operations in this system touch more than one record. Whenever a cascade writes a second entity, that entity's `updated_at` is refreshed and its `version` increases by 1, exactly as if it had been mutated directly. A single request that suspends a project, preempts three amenity allocations and blocks two downstream phases therefore leaves six records at a higher `version` than before. Cascades never skip the version bump, and they never bump a record they did not actually change.

Two identities must hold after every mutation that touches them, and they are the fastest way to check an implementation. The tenant improvement ledger of a lease satisfies: `ti_authorized_usd` equals the sum of `ti_uncommitted_usd`, `ti_committed_usd`, `ti_disbursed_usd` and `ti_forfeited_usd`. The base-building capacity pools satisfy: `exhaust_capacity_total_cfm` equals the sum of `exhaust_available_cfm`, `exhaust_reserved_cfm` and `exhaust_committed_cfm`, and `power_capacity_total_kw` equals the sum of `power_available_kw`, `power_reserved_kw` and `power_committed_kw`. Reservations that end up `CANCELLED` or `RELEASED` contribute to neither the reserved nor the committed bucket, so releasing capacity restores the pool to exactly its prior value with no drift.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Base Building and Its Floor Plates

A `LandlordAssetManager` begins by registering the asset itself. The registration payload carries the building's marketing `name`, its `address_city` of record, and an `occupancy_status` drawn from `VACANT`, `PARTIALLY_OCCUPIED` and `FULLY_OCCUPIED` — the posture that later governs how carefully phased delivery must be coordinated around neighbours. Alongside those descriptive attributes the landlord records the nameplate figures taken from the base-building drawing set: `published_floor_to_floor_ft`, a height in feet greater than zero carried to two decimal places; `published_live_load_psf`, a structural live-load capacity in pounds per square foot greater than zero; and `published_vibration_class`, an ambient vibration criterion curve that is one of `VC_A`, `VC_B`, `VC_C`, `VC_D` or `VC_E`. Three utility figures complete the record: `exhaust_riser_capacity_cfm`, the lab exhaust riser capacity in cubic feet per minute; `emergency_power_capacity_kw`, the emergency generator capacity in kilowatts; and `chilled_water_capacity_tons`, which is reported for underwriting but never pooled or consumed by any rule. All three must be zero or greater.

A newly registered building enters the lifecycle at `suitability_state` `DRAFT` with `latest_assessment_verdict` null. Its capacity pools are initialised from the two nameplate utility figures: `exhaust_capacity_total_cfm` starts equal to `exhaust_riser_capacity_cfm` and `power_capacity_total_kw` starts equal to `emergency_power_capacity_kw`, while `exhaust_reserved_cfm`, `exhaust_committed_cfm`, `power_reserved_kw` and `power_committed_kw` all start at zero, leaving `exhaust_available_cfm` and `power_available_kw` equal to the full nameplate figures. Two further derived lists start empty: `scope_disciplines_covered` and `scope_disciplines_complete`. A building may be read individually by any of the five roles; there is no unfiltered building listing.

Floor plates are the engineer's territory, not the landlord's. A `BaseBuildingEngineer` records each above-grade plate with its `floor_number`, an integer of at least 1 that must be unique within the building — a repeat yields `ERR_DUPLICATE_FLOOR_NUMBER`. The plate's as-built characteristics are `floor_to_floor_ft` and `live_load_psf`, both strictly greater than zero, and `vibration_class`, again one of the five criterion curves. The optional `sprinklered` flag defaults to true when omitted; it matters enormously later, because a fully sprinklered plate is allowed twice the hazardous material quantity of an unsprinklered one.

Two properties of a floor are never supplied by the caller. `control_areas_allowed` and `percent_maq` are derived from `floor_number` alone, using the code table the authority having jurisdiction publishes: the ground floor — floor number 1 — is allowed four control areas at the full hundred percent of the base maximum allowable quantity; floors 2 and 3 are allowed three control areas at seventy-five percent; floors 4 through 6 are allowed two control areas at fifty percent; and every floor from 7 upward, with no upper bound, is allowed two control areas at twenty-five percent. Exactly one band contains any given floor number, so the derivation is unambiguous. Floors can be read individually, listed under their building, or listed across the estate with optional `building_id` and `vibration_class` filters.

Shared amenity records also hang off the building, and are described in the amenity programming narrative below; they are mentioned here only because the amenity's `serving_floor_number` must match a floor that already exists, which means plates are always recorded before the amenities that sit on them.

### 3.2. Assessing Suitability and Approving Conversion

Suitability is assessed by the engineer of record and decided by the landlord, and the two never collapse into one act. Opening an assessment on a building moves that building from `DRAFT` to `ASSESSING` and creates the assessment at `status` `DRAFT`, bumping the building's `version`. The same operation is also the re-assessment path: a building sitting in `ASSESSED_SUITABLE`, `ASSESSED_CONDITIONAL` or `ASSESSED_UNSUITABLE` re-enters `ASSESSING` when a fresh assessment is opened, provided no assessment on that building is currently in `DRAFT` or `SUBMITTED`. Two domain rules guard the opening, evaluated in this order: if an assessment for this building is already in `DRAFT` or `SUBMITTED`, the request fails with `ERR_ASSESSMENT_ALREADY_OPEN`; only then is the building's own posture examined, and a building already in `CONVERSION_APPROVED` or `CONVERSION_COMPLETE` is refused with `ERR_INVALID_BUILDING_STATE`. Ordering the pair this way means a second concurrent draft surfaces as a duplicate-assessment problem rather than being masked by the building's state.

The assessment payload is where the two scoring worlds diverge. `assessment_basis` is either `SCREENING` or `INVESTIGATION`. The intended laboratory programme is described by `required_vibration_class`, one of the five criterion curves; `required_exhaust_cfm`, the programme's lab exhaust demand in cubic feet per minute, strictly positive; and `required_power_kw`, its emergency power demand in kilowatts, strictly positive. Three optional fields carry whatever field work has actually been done: `measured_floor_to_floor_ft`, `measured_live_load_psf` and `measured_vibration_class`, each defaulting to null when the measurement was not taken.

Submitting the assessment moves it from `DRAFT` to `SUBMITTED` and is the moment every derived number is computed and frozen; a submission attempted from any status other than `DRAFT` or `RETURNED` is refused with `ERR_INVALID_ASSESSMENT_STATE`. The engineer must also find the building in `ASSESSING` for the first submission. Resubmission after rework follows the identical path from `RETURNED` back to `SUBMITTED`, recomputing the score and verdict from the field values as they now stand and clearing `return_note` back to null.

The score is built dimension by dimension. First, each of the three physical dimensions resolves to an effective value. The height dimension uses `measured_floor_to_floor_ft` when it is present; when it is null, a `SCREENING` assessment falls back to the building's `published_floor_to_floor_ft` while an `INVESTIGATION` assessment treats the dimension as missing. Structural loading behaves identically, using `measured_live_load_psf` and falling back to `published_live_load_psf` only under `SCREENING`. Vibration behaves identically, using `measured_vibration_class` and falling back to `published_vibration_class` only under `SCREENING`. This resolution step is the only place the two bases differ; everything after it is common.

Second, each dimension earns a credit of 100, 60 or 0, and a dimension whose effective value is missing always earns 0. `height_credit` is 100 when the effective height is at least 14.0 feet, 60 when it is at least 12.5 feet but below 14.0, and 0 otherwise. `structural_credit` is 100 when the effective live load is at least 100 pounds per square foot, 60 when it is at least 80 but below 100, and 0 otherwise. `vibration_credit` compares criterion curves on a strictness ranking in which `VC_E` is the least strict at rank 1, followed by `VC_D` at 2, `VC_C` at 3, `VC_B` at 4 and `VC_A` as the strictest at rank 5: the credit is 100 when the effective curve's rank is greater than or equal to the rank of `required_vibration_class`, 60 when the effective curve's rank is exactly one less than the required curve's rank, and 0 otherwise. `utility_credit` derives from `utility_headroom_ratio`, which is the smaller of two quotients — the building's `exhaust_riser_capacity_cfm` divided by `required_exhaust_cfm`, and the building's `emergency_power_capacity_kw` divided by `required_power_kw` — rounded half up to four decimal places. Note that this ratio deliberately reads the nameplate riser and generator figures, not the conversion-augmented pool totals, because it is judging the building as found. The credit is 100 when the ratio is at least 1.25, 60 when it is at least 1.00 but below 1.25, and 0 otherwise.

Third, the credits are combined into one weighted figure. Height and structural loading each carry a quarter of the weight, vibration carries a fifth, and utility headroom carries three tenths — that is, `height_credit` multiplied by 0.25, plus `structural_credit` multiplied by 0.25, plus `vibration_credit` multiplied by 0.20, plus `utility_credit` multiplied by 0.30. That sum is rounded half up to one decimal place exactly once, at the end; the individual weighted terms are never rounded on their own.

Fourth comes the hard-fail cap, which exists so that no single fatal deficiency can be averaged away. `hard_fail_capped` is set to true only when both conditions hold: at least one of the four credits is 0, and the rounded weighted sum is strictly greater than 49.0. When it is true, `suitability_score` is forced to 49.0; otherwise `suitability_score` is the rounded weighted sum unchanged. A building with a zero credit whose weighted sum already sits at or below 49.0 is therefore not flagged as capped — the cap only records that a reduction actually happened.

Fifth, `verdict` follows from the final score alone: `SUITABLE` when `suitability_score` is at least 75.0, `SUITABLE_WITH_CONVERSION` when it is at least 50.0 but below 75.0, and `UNSUITABLE` below 50.0. `verdict` stays null while the assessment is still in `DRAFT`.

Because a screening assessment substitutes nameplate values while an investigation scores their absence as zero credit, identical inputs routinely produce different verdicts on the two bases, and that divergence is the intended behaviour rather than an inconsistency.

Deciding a submitted assessment belongs to the `LandlordAssetManager` and carries a `decision` of either `ACCEPT` or `RETURN` plus an optional `return_note`. Two domain rules apply, in this order: an assessment whose `status` is anything other than `SUBMITTED` is refused with `ERR_INVALID_ASSESSMENT_STATE`, and only after that is the note requirement tested, so a `RETURN` decision on an already-accepted assessment reports the state problem rather than the missing note. A `RETURN` decision with a `return_note` that is null or blank is refused with `ERR_RETURN_NOTE_REQUIRED`. A `RETURN` stores the note, records the deciding operator in `decided_by_user_id`, moves the assessment from `SUBMITTED` to `RETURNED`, and deliberately leaves the building where it is, still in `ASSESSING`. An `ACCEPT` moves the assessment from `SUBMITTED` to the terminal `ACCEPTED`, records `decided_by_user_id`, copies the frozen `verdict` onto the building as `latest_assessment_verdict`, and advances the building out of `ASSESSING` along the branch the verdict names: `ASSESSING → ASSESSED_SUITABLE` for `SUITABLE`, `ASSESSING → ASSESSED_CONDITIONAL` for `SUITABLE_WITH_CONVERSION`, and `ASSESSING → ASSESSED_UNSUITABLE` for `UNSUITABLE`. Each of the three branches bumps both the assessment's `version` and the building's `version`. Assessments can be read individually, listed under their building filtered by `status`, or listed globally with optional `building_id`, `assessment_basis`, `status` and `verdict` filters.

Conversion scope is the landlord's capital plan for making the building lab-capable, and it is recorded one item per discipline. Each item names a `discipline` — `LAB_EXHAUST`, `EMERGENCY_POWER`, `CHEMICAL_STORAGE` or `WASTE_HANDLING` — carries a `description` narrative and a `budget_usd` of zero or more at two decimal places, and declares the capacity it will add once delivered through `capacity_delta_cfm` and `capacity_delta_kw`, each defaulting to zero and never negative. At most one item may exist per discipline on a building; a second attempt at the same discipline is refused with `ERR_DUPLICATE_SCOPE_DISCIPLINE`. Items are created at `status` `PLANNED` with `completed_at` null, and creating one recomputes the building's `scope_disciplines_covered` — the sorted list of distinct disciplines declared — and bumps the building's `version`. Items can be read individually, listed under their building filtered by `status`, or listed globally with optional `building_id`, `discipline` and `status` filters.

Approving the conversion is a landlord act available only from `ASSESSED_SUITABLE` or `ASSESSED_CONDITIONAL`, and it requires that the most recently accepted verdict be `SUITABLE` or `SUITABLE_WITH_CONVERSION`. Two domain rules run in order: a building in any state other than `ASSESSED_SUITABLE` or `ASSESSED_CONDITIONAL` is refused with `ERR_INVALID_BUILDING_STATE`, and then a building with no `LAB_EXHAUST` scope item at all is refused with `ERR_CONVERSION_SCOPE_INCOMPLETE`. There is no lab building without lab exhaust, so that one discipline is the gate. Approval carries the building to `CONVERSION_APPROVED` and bumps its `version`.

Closing out a scope item is the engineer's job and only makes sense once conversion has been approved. Two domain rules run in order: a building whose `suitability_state` is not `CONVERSION_APPROVED` yields `ERR_BUILDING_NOT_CONVERSION_APPROVED`, and an item already at `COMPLETE` yields `ERR_INVALID_SCOPE_ITEM_STATE`. Completion moves the item `PLANNED → COMPLETE`, stamps `completed_at` with the current logical instant, and folds the item's declared deltas into the building's pools, bumping both the item's `version` and the building's `version`. Specifically, `exhaust_capacity_total_cfm` is the building's `exhaust_riser_capacity_cfm` plus the sum of `capacity_delta_cfm` over every scope item on that building whose `discipline` is `LAB_EXHAUST` and whose `status` is `COMPLETE`; `power_capacity_total_kw` is `emergency_power_capacity_kw` plus the sum of `capacity_delta_kw` over every scope item whose `discipline` is `EMERGENCY_POWER` and whose `status` is `COMPLETE`. Deltas declared on the chemical storage and waste handling disciplines add capacity to neither pool. `exhaust_reserved_cfm` and `exhaust_committed_cfm` are the sums of `exhaust_cfm` across the building's reservations in `RESERVED` and in `COMMITTED` respectively, `power_reserved_kw` and `power_committed_kw` are the analogous sums of `power_kw`, and the two availability figures are what is left: `exhaust_available_cfm` is `exhaust_capacity_total_cfm` less the reserved and committed exhaust, and `power_available_kw` is `power_capacity_total_kw` less the reserved and committed power.

Completion also maintains `scope_disciplines_complete`, the sorted list of distinct disciplines whose item has reached `COMPLETE`. When the item that just completed makes that list equal to `scope_disciplines_covered` and that list covers all four disciplines — `LAB_EXHAUST`, `EMERGENCY_POWER`, `CHEMICAL_STORAGE` and `WASTE_HANDLING` — the building bubbles up from `CONVERSION_APPROVED` to the terminal `CONVERSION_COMPLETE`, with the pools recomputed and the building's `version` bumped in the same operation. A building that declared only two disciplines and completed both does not reach `CONVERSION_COMPLETE`; the full quartet is required.

### 3.3. Tenants and the Tenant-Improvement Negotiation

A tenant record is registered by the landlord with a `legal_name`, a `research_type` chosen from `BSL2_BIOLOGY`, `CHEMISTRY_SYNTHESIS`, `VIVARIUM` and `ANALYTICAL_QC`, and a `credit_tier` of `INVESTMENT_GRADE`, `VENTURE_BACKED` or `EARLY_STAGE` that is recorded for underwriting and consumed by no rule. The research programme, however, drives two derived properties. `lab_premium_psf` is the per-square-foot cost premium the programme carries: 45.00 dollars for `BSL2_BIOLOGY`, 62.50 for `CHEMISTRY_SYNTHESIS`, 88.00 for `VIVARIUM` and 30.00 for `ANALYTICAL_QC`. `required_commissioning_scripts` is the validation battery the programme obliges, sorted ascending by script name: a `BSL2_BIOLOGY` tenant requires the four scripts `CONTAINMENT_VERIFICATION`, `EXHAUST_AIRFLOW`, `IQ` and `OQ`; a `CHEMISTRY_SYNTHESIS` tenant requires the four scripts `EPSS_LOAD_TEST`, `EXHAUST_AIRFLOW`, `IQ` and `OQ`; a `VIVARIUM` tenant requires all six of `CONTAINMENT_VERIFICATION`, `EPSS_LOAD_TEST`, `EXHAUST_AIRFLOW`, `IQ`, `OQ` and `PQ`; and an `ANALYTICAL_QC` tenant requires only `IQ` and `OQ`.

Creating a lease binds a tenant to a specific plate. The payload carries `tenant_id`, `building_id`, `premises_floor_id`, the premises' `rentable_sf` as a positive integer, a `term_months` of at least 12, a positive `base_rent_psf` recorded for reporting only, and a `delivery_deadline` — the outside date by which every fit-out phase window must have ended. The demised plate must actually belong to the named building: when the floor identified by `premises_floor_id` reports a different building than `building_id`, the create is refused with `ERR_FLOOR_NOT_IN_PREMISES`. A new lease starts at `status` `LOI` with an entirely zeroed tenant improvement ledger and every negotiated figure null. Leases can be read individually by any role and listed with optional `tenant_id`, `building_id`, `premises_floor_id` and `status` filters.

The allowance itself is negotiated by turn-taking rounds, and either party may open a round. A round payload carries `expected_lease_version`, the required `proposed_allowance_psf` as a non-negative figure at two decimal places, and an optional `note`. The server derives the rest: `round_number` is one more than the number of rounds already on the lease, `proposed_by` is `LANDLORD` when the caller's role is `LandlordAssetManager` and `TENANT` when it is `Tenant`, `authored_by_user_id` captures the author's `X-User-ID`, and `expires_at` is set to the round's creation instant plus ten days on the logical clock. Every round is created at `status` `OPEN`, and the lease's `negotiation_round_count` is simply the number of rounds it carries.

Creating a round settles the previous one. The lease's prior `OPEN` proposal moves `OPEN → COUNTERED` when its `expires_at` is still at or after the current logical instant, and `OPEN → EXPIRED` when its `expires_at` has already elapsed; either way it stops being live and its `version` is bumped. The lease's own posture alternates: the landlord's opening round carries the lease `LOI → NEGOTIATING`, a tenant counter carries it `NEGOTIATING → COUNTER_PENDING`, and a landlord counter carries it back `COUNTER_PENDING → NEGOTIATING`. Each round creation bumps the lease's `version`.

Five domain rules guard a round creation, and their order is part of the contract. The stale-version comparison runs first, so a caller working from a superseded read learns that fact before anything else and receives `ERR_STALE_LEASE_VERSION`. Second, a lease whose `status` is not `LOI`, `NEGOTIATING` or `COUNTER_PENDING` is refused with `ERR_INVALID_LEASE_STATE` — once terms are accepted there is nothing left to negotiate. Third, the building must have been cleared for lab use: a `suitability_state` that is neither `CONVERSION_APPROVED` nor `CONVERSION_COMPLETE` is refused with `ERR_BUILDING_NOT_CONVERSION_APPROVED`, which keeps the landlord from trading allowance dollars on a plate that may never become a laboratory. Fourth, turn-taking is enforced: when an `OPEN` proposal exists on the lease and its `proposed_by` equals the party the caller's role maps to, the caller is trying to counter itself and receives `ERR_NOT_YOUR_TURN`. Fifth and last, the round budget is checked: once `negotiation_round_count` has reached six, no further round may be created and the request is refused with `ERR_NEGOTIATION_ROUND_LIMIT`. Placing the round limit after turn-taking means an out-of-turn caller at round six hears about the turn, not the ceiling.

Accepting a round closes the deal, and it may be done by either role — but never by the side that wrote the round. Three domain rules run in order: a proposal whose `status` is not `OPEN` yields `ERR_INVALID_PROPOSAL_STATE`; then the self-acceptance test, where an accepting `X-User-ID` equal to the proposal's `authored_by_user_id`, or an accepting party equal to the proposal's `proposed_by`, yields `ERR_SELF_ACCEPT_FORBIDDEN`; and only then is the ten-day window checked, so a stale offer the author tries to accept themselves reports the self-acceptance problem rather than the expiry. A proposal whose `expires_at` is strictly earlier than the current logical instant yields `ERR_PROPOSAL_EXPIRED`; an `expires_at` exactly equal to now is still acceptable. Acceptance moves the proposal `OPEN → ACCEPTED`, records the accepting operator in `accepted_by_user_id`, and carries the lease to `TERMS_ACCEPTED` — from `NEGOTIATING` when a landlord round was accepted by the tenant, and from `COUNTER_PENDING` when a tenant round was accepted by the landlord. Both source states run the identical set of side effects. The lease records `accepted_proposal_round` as the winning round's `round_number`, `accepted_allowance_psf` as that round's `proposed_allowance_psf`, and `terms_accepted_by_user_id` as the accepting `X-User-ID`; its `version` is bumped, and its economics are computed once and never recomputed.

Those economics run in a fixed order, and the order matters because the volume credit depends on the authorisation while the authorisation depends on the credit. The apparent circularity is resolved by selecting the credit tier from the pre-credit authorisation and never re-selecting it afterwards. First, `lab_premium_psf_applied` is the tenant's `lab_premium_psf` for its `research_type`, plus a high-floor stack uplift of 5.00 dollars per square foot when the premises floor's `floor_number` is 4 or greater, and nothing when the premises sit on floors 1 through 3. Second, a per-square-foot subtotal is formed by adding `accepted_allowance_psf` and `lab_premium_psf_applied`. Third, `provisional_authorized_ti_usd` is that subtotal multiplied by `rentable_sf`, rounded half up to two decimal places. Fourth, `volume_credit_psf` is selected from that provisional figure by taking the highest tier whose floor the provisional authorisation reaches: 3.00 dollars per square foot when the provisional authorisation is at least 5,000,000.00 dollars, 1.50 when it is at least 2,000,000.00 but below 5,000,000.00, and 0.00 below 2,000,000.00. Both tier floors are inclusive, so a provisional authorisation of exactly five million dollars earns the 3.00 credit. Fifth, `final_allowance_psf` is the subtotal less `volume_credit_psf`, rounded half up to two decimal places. Sixth, `ti_authorized_usd` is `final_allowance_psf` multiplied by `rentable_sf`, rounded half up to two decimal places. Seventh, `restoration_escrow_required_usd` is one tenth of `ti_authorized_usd` rounded half up to two decimal places, but never more than 250,000.00 dollars — the smaller of the two figures is what is required. Recomputing the tier from the post-credit authorisation is explicitly wrong: a deal whose provisional authorisation clears five million but whose final authorisation falls below it keeps the 3.00 credit.

Acceptance also opens the ledger. `ti_authorized_usd` is set as above, `ti_uncommitted_usd` is set equal to it, and `ti_committed_usd`, `ti_disbursed_usd` and `ti_forfeited_usd` are all zero, so the ledger identity holds from the first instant. Proposals can be read individually, listed under their lease filtered by `status`, or listed globally with optional `lease_id`, `proposed_by` and `status` filters.

### 3.4. Execution, Escrow and the Tenant Improvement Ledger

Between accepted terms and an executed lease sits the restoration escrow. Either the tenant or the landlord may deposit against it by supplying a positive `amount_usd`, which is added to the lease's `restoration_escrow_held_usd` and bumps the lease's `version`. Deposits may be made in as many instalments as the parties like; only the running total matters.

Execution is a landlord act with three domain rules in a fixed order. A lease whose `status` is not `TERMS_ACCEPTED` is refused with `ERR_INVALID_LEASE_STATE`. Next the escrow is tested: when `restoration_escrow_held_usd` is strictly less than `restoration_escrow_required_usd` the request is refused with `ERR_ESCROW_DEPOSIT_INSUFFICIENT`, and an amount exactly equal to the requirement is sufficient. Last comes separation of duties: an executing `X-User-ID` equal to the accepted proposal's `authored_by_user_id`, or equal to the lease's `terms_accepted_by_user_id`, is refused with `ERR_SEGREGATION_OF_DUTIES`. Putting the money test before the identity test means an underfunded escrow is reported even when the same operator would also have been barred from signing. A successful execution carries the lease `TERMS_ACCEPTED → EXECUTED`, records `executed_by_user_id` and stamps `executed_at` with the current logical instant, and bumps `version`. That stamp matters downstream: `executed_at` is the earliest instant any fit-out phase window may begin.

Drawing on the allowance is also a landlord act and is capped in three independent ways. A draw request carries `requested_usd`. Two domain rules run first, in order: a lease whose `status` is neither `EXECUTED` nor `ACTIVE` is refused with `ERR_INVALID_LEASE_STATE`, and a lease whose `ti_committed_usd` is zero is refused with `ERR_TI_ALLOWANCE_EXHAUSTED` — there is nothing to pay out until phases have completed and committed against the allowance. The amount actually disbursed is the smallest of three figures: the `requested_usd` asked for, a draw cap equal to three tenths of `ti_authorized_usd` rounded half up to two decimal places, and the lease's current `ti_committed_usd`. The cap is computed from the original authorisation, not from what remains, so it does not shrink as draws accumulate.

The disbursed amount is then spread across the phases that earned it. Eligible phases are those belonging to any fit-out project on this lease whose `status` is `COMPLETE` and whose `ti_committed_usd` still exceeds its `ti_disbursed_usd`, taken in ascending `created_at` order. Each eligible phase's raw share is the disbursed amount multiplied by that phase's `ti_committed_usd` and divided by the total `ti_committed_usd` across all eligible phases. Every line is then rounded half up to two decimal places on its own, before any comparison to the total. The residual — the disbursed amount less the sum of the rounded lines, which may be positive or negative — is added to the single eligible phase holding the largest `ti_committed_usd`, with ties broken in favour of the earliest `created_at`. Rounding only the grand total, or dumping the residual on the last line, both produce different and incorrect per-phase figures. Each phase's `ti_disbursed_usd` increases by its own allocation, the lease's `ti_committed_usd` decreases and its `ti_disbursed_usd` increases by the full disbursed amount, `last_disbursement_usd` is set to that disbursed amount, and the lease's `version` is bumped. The ledger identity holds across the whole operation because dollars only move between buckets.

`last_disbursement_usd` exists because a draw can be undone. It records exactly what the most recent successful draw paid out, and it is the amount a failing commissioning script reverses — described with the commissioning workflow below. `ti_forfeited_usd` stays at zero for the whole active life of the lease and only receives value at restoration settlement.

### 3.5. Fit-Out Projects, Permitting and Base-Building Capacity Reservations

A fit-out project is the construction envelope for one tenant on one plate. The landlord creates it with `lease_id`, `floor_id`, a strictly positive `design_exhaust_cfm`, a strictly positive `design_power_kw`, and a `scope_summary` narrative. Two domain rules run in order: the project must be built on the demised plate, so a `floor_id` that differs from the lease's `premises_floor_id` is refused with `ERR_FLOOR_NOT_IN_PREMISES`; and the lease must have got at least as far as accepted terms, so a lease whose `status` is not `TERMS_ACCEPTED`, `EXECUTED` or `ACTIVE` is refused with `ERR_INVALID_LEASE_STATE`. Design projects may therefore begin before the lease is signed, but nothing may be permitted or built until it is.

A project carries two status dimensions on the same record, and they are genuinely independent: neither is derived from the other and they advance on disjoint triggers. `permit_status` tracks the authority having jurisdiction and runs `P_UNPERMITTED` at creation, then `P_APPLIED`, then the terminal `P_ISSUED`. `construction_status` tracks the work and runs `C_NOT_STARTED` at creation, then `C_IN_PROGRESS`, with `C_SUSPENDED` as a reversible detour, then `C_SUBSTANTIAL_COMPLETION` and finally the terminal `C_ACCEPTED`. A project also carries `delivery_risk`, which is `AT_RISK` whenever any phase package of the project is in `VIBRATION_HOLD` or `BLOCKED` and `ON_TRACK` otherwise; `required_commissioning_scripts`, copied from the research programme of the tenant reached through the lease; `passed_script_count`, the number of distinct required script types that already have a passed record on this project, starting at zero; and three timestamps — `permit_applied_at`, `permit_issued_at` and `accepted_at` — each null until the corresponding milestone occurs.

Applying for the construction permit is a landlord act with four domain rules in a fixed order. A project whose `permit_status` is not `P_UNPERMITTED` is refused with `ERR_INVALID_PERMIT_STATE`. Then the lease is tested: a `status` that is neither `EXECUTED` nor `ACTIVE` is refused with `ERR_INVALID_LEASE_STATE`, so a project created against merely accepted terms cannot be permitted until the lease is signed. Then the base building: a `suitability_state` that is neither `CONVERSION_APPROVED` nor `CONVERSION_COMPLETE` is refused with `ERR_BUILDING_NOT_CONVERSION_APPROVED`. Finally the exhaust: if the building has no `LAB_EXHAUST` scope item, or has one whose `status` is not `COMPLETE`, the application is refused with `ERR_EXHAUST_SCOPE_INCOMPLETE`. Note the deliberate asymmetry against the negotiation gate — a landlord may trade allowance dollars while the exhaust riser is still being built, but may not apply for a laboratory permit until it is finished. A successful application moves `P_UNPERMITTED → P_APPLIED`, stamps `permit_applied_at`, and bumps `version`.

Ruling on the application belongs exclusively to the `AHJPermitOfficer`, who supplies a `decision` of `ISSUE` plus an optional `decision_note`. A project whose `permit_status` is not `P_APPLIED` is refused with `ERR_INVALID_PERMIT_STATE`. Issuance moves `P_APPLIED → P_ISSUED`, stamps `permit_issued_at`, and bumps `version`. Nothing may physically start before that stamp exists.

Declaring substantial completion is a landlord act carrying a `milestone` of `SUBSTANTIAL_COMPLETION`, and it requires that the work be genuinely quiet. A project whose `construction_status` is not `C_IN_PROGRESS` is refused with `ERR_INVALID_PROJECT_STATE`; after that, if any phase package of the project is in `SCHEDULED`, `VIBRATION_HOLD`, `BLOCKED` or `IN_PROGRESS`, or if no phase package has reached `COMPLETE` at all, the request is refused with `ERR_PHASES_NOT_QUIESCED`. Every phase must be sitting in either `DRAFT` or `COMPLETE`, and at least one must be `COMPLETE`. Success carries the project `C_IN_PROGRESS → C_SUBSTANTIAL_COMPLETION` and bumps `version`. Projects can be read individually and listed with optional `lease_id`, `floor_id`, `permit_status` and `construction_status` filters.

Reserving base-building capacity is how a project claims its share of the shared risers and the shared generator. A reservation payload carries `project_id`, a strictly positive `exhaust_cfm` at two decimal places, a strictly positive `power_kw` at two decimal places, and `expected_building_version`. The server denormalises `building_id` onto the reservation at creation by walking from the project to its floor and from that floor to its building, so the reservation always knows which pool it draws from without the caller stating it. Four domain rules run in a fixed order. The version precondition runs first: an `expected_building_version` that does not equal the building's current `version` is refused with `ERR_STALE_BUILDING_VERSION`, because the pool figures the caller reasoned about are no longer the pool figures in force. Second, the project must be permitted: a `permit_status` other than `P_ISSUED` is refused with `ERR_PROJECT_NOT_PERMITTED`. Third, the exhaust pool is tested: an `exhaust_cfm` strictly greater than the building's `exhaust_available_cfm` is refused with `ERR_EXHAUST_CAPACITY_EXCEEDED`. Fourth, the power pool is tested the same way: a `power_kw` strictly greater than `power_available_kw` is refused with `ERR_POWER_CAPACITY_EXCEEDED`. A request that overdraws both pools reports the exhaust failure, because exhaust is the scarcer and more consequential resource. A reservation exactly equal to what is available succeeds and leaves availability at zero.

A successful reservation is created at `status` `RESERVED`, increases the building's `exhaust_reserved_cfm` by its `exhaust_cfm` and `power_reserved_kw` by its `power_kw`, and bumps the building's `version` by 1 — which is precisely why the next caller's cached version is stale. Cancelling a reservation is a landlord act refused with `ERR_INVALID_RESERVATION_STATE` unless the reservation's `status` is exactly `RESERVED`. Cancellation moves it `RESERVED → CANCELLED`, reduces `exhaust_reserved_cfm` and `power_reserved_kw` by exactly the reservation's own amounts so that availability returns to precisely its pre-reservation value, and bumps both the reservation's `version` and the building's `version`. Reservations follow two further paths that no one calls directly: `RESERVED → COMMITTED` when the project is accepted at the end of commissioning, which shifts the amounts out of the reserved buckets and into `exhaust_committed_cfm` and `power_committed_kw`; and `RESERVED → RELEASED` or `COMMITTED → RELEASED` at restoration settlement, which reduces whichever bucket held them and returns the capacity to the pool. Each of those cascades bumps the reservation's `version` and the building's `version`. Reservations can be read individually and listed with optional `project_id`, `building_id` and `status` filters.

### 3.6. Phased Delivery: Windows, Vibration Holds and Predecessor Cascades

Fit-out work in a partially occupied life science building is delivered as a chain of phase packages. Each package is created by the landlord under its project with a `sequence_no` of at least 1 that must be unique within the project, a `premium_class` of `SHELL`, `LAB_MEP`, `VIVARIUM` or `CLEANROOM`, a `work_class` of `QUIET`, `VIBRATION_GENERATING` or `SHUTDOWN_REQUIRED`, a strictly positive `hard_cost_usd` at two decimal places, and a `restoration_cost_usd` of zero or more at two decimal places. Two optional identifiers shape the chain and the shutdown: `predecessor_phase_id` names the package that must be `COMPLETE` before this one may start and whose hold cascades onto this one, and is null for the first package in a chain; `affected_amenity_id` names the shared amenity that this package's utility shutdown takes out of service, and is null when the package needs no shutdown.

Three domain rules guard package creation, in order. A `predecessor_phase_id` that resolves to a package belonging to a different project is refused with `ERR_PREDECESSOR_NOT_IN_PROJECT`. A `sequence_no` already used on this project is refused with `ERR_DUPLICATE_PHASE_SEQUENCE`. And a package whose `work_class` is `SHUTDOWN_REQUIRED` but whose `affected_amenity_id` is null is refused with `ERR_SHUTDOWN_AMENITY_REQUIRED` — a shutdown that does not say what it takes offline cannot be coordinated with anyone. Packages are created at `status` `DRAFT` with `window_start` and `window_end` both null, `prior_status` and `hold_reason` null, and `ti_eligible_usd`, `ti_committed_usd` and `ti_disbursed_usd` all zero. They can be read individually and listed with optional `project_id`, `predecessor_phase_id`, `affected_amenity_id` and `status` filters.

Scheduling a package is where coordination actually happens. The landlord supplies a `window_start` and `window_end`, and the operation is valid from `DRAFT`, from `SCHEDULED` — a reschedule to a new window — and from `VIBRATION_HOLD`, where it is the release path. Five domain rules run in a fixed order. First, a package whose `status` is not `DRAFT`, `SCHEDULED` or `VIBRATION_HOLD` is refused with `ERR_INVALID_PHASE_STATE`; a package in `BLOCKED`, `IN_PROGRESS` or `COMPLETE` cannot be scheduled. Second, the window must be non-degenerate: a `window_start` at or after `window_end` is refused with `ERR_INVALID_WINDOW`. Third comes the vibration conflict scan, described in the next paragraph, refused with `ERR_VIBRATION_WINDOW_CONFLICT`. Fourth, the window must sit inside the delivery term: a `window_start` earlier than the lease's `executed_at`, or a `window_end` later than the lease's `delivery_deadline`, is refused with `ERR_WINDOW_OUTSIDE_DELIVERY_TERM`. Fifth, the shutdown conflict is checked, refused with `ERR_SHUTDOWN_CONFLICTS_AMENITY`. Putting vibration ahead of the delivery-term test is deliberate: a window that both disturbs a neighbour and overruns the outside date reports the vibration problem, because that is the one that endangers someone else's experiment today.

The vibration conflict scan looks at every other phase package sitting on the same floor plate — reached through each project's `floor_id` — in `SCHEDULED`, `VIBRATION_HOLD`, `BLOCKED` or `IN_PROGRESS` status, excluding the package being scheduled so that a reschedule never conflicts with its own current window. A pair is only interesting when at least one of the two packages has `work_class` `VIBRATION_GENERATING`; two quiet packages may overlap freely, and so may a quiet package and a shutdown package. For an interesting pair, the two windows are compared with a full day of buffer on each side: a conflict exists when the new window's start is at or before the other window's end extended forward by 24 hours, and simultaneously the other window's start is at or before the new window's end extended forward by 24 hours. Both comparisons are inclusive, so windows that merely touch at the buffer boundary still conflict — vibration-sensitive instruments need a settling day, not a shared instant.

The shutdown conflict test is narrower and uses no buffer. It applies only when the package's `work_class` is `SHUTDOWN_REQUIRED`, and it looks for any amenity allocation on the package's `affected_amenity_id` in `CONFIRMED` status whose window overlaps the phase window under the half-open rule: the allocation's `window_start` strictly before the phase's `window_end`, and the phase's `window_start` strictly before the allocation's `window_end`. Windows that abut exactly do not overlap.

A successful schedule stores the window, bumps `version`, and drives the state machine along one of three arcs: `DRAFT → SCHEDULED` for a first schedule, `SCHEDULED → SCHEDULED` for a reschedule that replaces `window_start` and `window_end`, and `VIBRATION_HOLD → SCHEDULED` for a release, which additionally clears `hold_reason` back to null. A release also unwinds the cascade that the hold created, and once no package of the project remains in `VIBRATION_HOLD` or `BLOCKED`, the project moves `C_SUSPENDED → C_IN_PROGRESS` and its `delivery_risk` returns to `ON_TRACK`, bumping the project's `version`.

Placing a package on hold belongs to the `BaseBuildingEngineer` — the one party whose job is to stop work when the plate starts moving. Two domain rules run in order: a package whose `status` is not exactly `SCHEDULED` is refused with `ERR_INVALID_PHASE_STATE`, and a `hold_reason` that is null or blank is refused with `ERR_HOLD_REASON_REQUIRED`. A hold moves the package `SCHEDULED → VIBRATION_HOLD`, stores `hold_reason`, and bumps its `version` — and then fires the widest cascade in the system. Every package transitively downstream of the held one through the `predecessor_phase_id` chain — its direct successors, their successors, and so on to the end of the chain — that is currently in `DRAFT` or `SCHEDULED` moves to `BLOCKED`, recording where it came from in `prior_status`: a `DRAFT → BLOCKED` package records `DRAFT`, and a `SCHEDULED → BLOCKED` package records `SCHEDULED` and retains its `window_start` and `window_end` untouched. Packages already in `IN_PROGRESS`, `COMPLETE` or `VIBRATION_HOLD` are left alone. The project itself moves `C_IN_PROGRESS → C_SUSPENDED` and its `delivery_risk` becomes `AT_RISK`. Finally, every amenity allocation belonging to that project in `REQUESTED` or `CONFIRMED` status whose `window_start` is at or after the current logical instant is preempted; allocations already in the past are left as they are. Each of those records — every blocked package, the project, every preempted allocation — has its `updated_at` refreshed and its `version` bumped.

Releasing the hold restores the chain exactly. Every package that the cascade drove to `BLOCKED` returns to the status recorded in its `prior_status` — `BLOCKED → SCHEDULED` for a package that had already been scheduled, retaining the window it kept throughout, and `BLOCKED → DRAFT` for a package that had not — and `prior_status` is cleared back to null in both cases. The restoration is verbatim: a package that was scheduled does not have to be rescheduled, and a package that was a draft is not silently promoted. Preempted amenity allocations, by contrast, are not restored; preemption is terminal and the tenant must book again.

Advancing the physical work uses a `target_status` of either `IN_PROGRESS` or `COMPLETE`, and is a landlord act. Three domain rules run in order. The state test comes first: a `target_status` of `IN_PROGRESS` requires the package to be in `SCHEDULED`, and a `target_status` of `COMPLETE` requires it to be in `IN_PROGRESS`; anything else is refused with `ERR_INVALID_PHASE_STATE`. Second, starting work requires the permit: a `target_status` of `IN_PROGRESS` on a project whose `permit_status` is not `P_ISSUED` is refused with `ERR_PROJECT_NOT_PERMITTED`. Third, starting work requires the chain: a `target_status` of `IN_PROGRESS` on a package whose `predecessor_phase_id` is not null and whose predecessor's `status` is not `COMPLETE` is refused with `ERR_PREDECESSOR_NOT_COMPLETE`. A package with a null `predecessor_phase_id` passes that test trivially. The `SCHEDULED → IN_PROGRESS` transition also drags the project along when it is the first package to start, moving it `C_NOT_STARTED → C_IN_PROGRESS`.

Reaching `IN_PROGRESS → COMPLETE` is the moment a phase claims tenant improvement dollars, and it happens exactly once per package. `ti_eligible_usd` is computed as the package's `hard_cost_usd` multiplied by the eligible share of its `premium_class` and then by that class's premium multiplier, rounded half up to two decimal places. Shell work is 60 percent eligible at a multiplier of 1.00; lab mechanical, electrical and plumbing work is 85 percent eligible at a multiplier of 1.18; vivarium work is 90 percent eligible at a multiplier of 1.275; and cleanroom work is 88 percent eligible at a multiplier of 1.22. The package's `ti_committed_usd` is then the smaller of its `ti_eligible_usd` and whatever the lease's `ti_uncommitted_usd` holds at that instant. The lease's `ti_uncommitted_usd` decreases and its `ti_committed_usd` increases by that same figure, and both the package's `version` and the lease's `version` are bumped. Because the bucket is consumed in the chronological order in which packages actually reach `COMPLETE` — never in `sequence_no` order — a package that completes late can find the allowance already spent and commit nothing at all, which is a truncation rather than an error. The ledger identity holds after every such commitment.

### 3.7. Shared Amenities and Allocation Programming

Shared amenities are the equipment and space that no single tenant can justify alone. The landlord programmes them onto a building with a `name`, an `amenity_type` of `GLASSWASH`, `AUTOCLAVE`, `NMR_SUITE`, `CONFERENCE` or `LOADING_DOCK`, and a `serving_floor_number` of at least 1 identifying the plate the amenity physically occupies. The amenity resolves to the floor in the same building whose `floor_number` equals that number, and when no such floor exists the create is refused with `ERR_FLOOR_NOT_FOUND`. A `concurrent_capacity` of at least 1 states how many live allocations may overlap at any instant. Two optional attributes complete the record: `vibration_sensitive`, defaulting to false, which when true forbids allocations that coincide with vibration-generating work on the amenity's own plate; and `utility_draw_kw`, defaulting to zero, which is recorded for reporting and consumed by no rule. Amenities can be read individually, listed under their building filtered by `amenity_type`, or listed globally with optional `building_id` and `amenity_type` filters.

Booking an amenity is one of the few operations a `Tenant` may perform directly, and the landlord may also book on a tenant's behalf. An allocation payload carries `amenity_id`, `project_id`, a `window_start`, a `window_end` and a `headcount` of at least 1. Allocation windows are half-open: the interval runs from `window_start` inclusive to `window_end` exclusive, so back-to-back bookings that share an instant do not collide.

Five domain rules guard the booking, in a fixed order. First, a `window_start` at or after `window_end` is refused with `ERR_INVALID_WINDOW`. Second, the amenity and the project must live in the same asset: the amenity's `building_id` is compared against the building reached from the project's `floor_id`, and a mismatch is refused with `ERR_AMENITY_NOT_IN_BUILDING`. Third, the project must be in a posture where its people are actually on site: a `construction_status` of `C_SUSPENDED` or `C_ACCEPTED` is refused with `ERR_INVALID_PROJECT_STATE` — a suspended project has just had its bookings preempted and an accepted project is finished with the fit-out. Fourth, the concurrency ceiling is tested. Fifth, vibration sensitivity is tested.

The concurrency test is an interval-overlap count rather than a simple pairwise comparison, because `concurrent_capacity` is an aggregate limit. The candidate instants examined are the new allocation's own `window_start` together with the `window_start` of every existing allocation on the same amenity in `REQUESTED` or `CONFIRMED` status that falls at or after the new `window_start` and strictly before the new `window_end`. At each candidate instant, the server counts the existing `REQUESTED` and `CONFIRMED` allocations whose half-open window contains that instant, adds the new allocation, and compares the total against `concurrent_capacity`; if any candidate instant produces a total strictly greater than the capacity, the booking is refused with `ERR_AMENITY_CAPACITY_EXCEEDED`. A total exactly equal to the capacity is permitted. Because only allocation start instants can raise the running count, examining those instants is sufficient to find the peak.

The vibration test applies only when the amenity's `vibration_sensitive` flag is true. The server looks for any phase package whose `work_class` is `VIBRATION_GENERATING` and whose `status` is `SCHEDULED` or `IN_PROGRESS`, and whose project's `floor_id` resolves to the floor in the amenity's building whose `floor_number` equals the amenity's `serving_floor_number`. If any such package's window overlaps the requested allocation window under the half-open rule — the package's start strictly before the allocation's end and the allocation's start strictly before the package's end — the booking is refused with `ERR_VIBRATION_WINDOW_CONFLICT`, the same code the phase scheduler uses, because it is the same physical objection seen from the other side.

Allocations are created at `status` `REQUESTED`. Confirming one is a landlord act: an allocation whose `status` is not `REQUESTED` is refused with `ERR_INVALID_ALLOCATION_STATE`, and the aggregate concurrency count is re-evaluated at confirmation time and must still hold, otherwise `ERR_AMENITY_CAPACITY_EXCEEDED` is returned. Confirmation moves `REQUESTED → CONFIRMED` and bumps `version`. Cancellation may be performed by the landlord or by the owning tenant: two domain rules run in order, refusing an allocation whose `status` is neither `REQUESTED` nor `CONFIRMED` with `ERR_INVALID_ALLOCATION_STATE`, and then refusing a `Tenant` caller whose own tenancy differs from the `tenant_id` of the lease behind the allocation's project with `ERR_UNAUTHORIZED`. Cancellation follows `REQUESTED → CANCELLED` or `CONFIRMED → CANCELLED`; a confirmed allocation may only be cancelled while its `window_start` is still strictly in the future. Both `CANCELLED` and `PREEMPTED` are terminal, and preemption arrives only through the vibration-hold cascade described above, taking `REQUESTED → PREEMPTED` or `CONFIRMED → PREEMPTED` for allocations whose `window_start` is at or after the current logical instant. Allocations can be read individually and listed with optional `amenity_id`, `project_id` and `status` filters.

### 3.8. Hazardous Materials and Control-Area Limits

Hazardous material use is the constraint that most often decides how much laboratory a floor can hold, because the limits are per control area, per floor, and shared across every tenant on the plate. An application may be filed by the tenant or by the landlord and carries `project_id`, `floor_id`, a `hazard_class` of `FLAMMABLE_IB`, `FLAMMABLE_II`, `CORROSIVE` or `OXIDIZER_2`, a `use_condition` of `STORAGE_CABINET`, `CLOSED_SYSTEM_USE` or `OPEN_SYSTEM_USE`, a strictly positive `quantity_gal` at two decimal places, and a `control_area_index` of at least 1 identifying which control area on the plate the material will sit in.

The allowance the application is measured against is `allowance_per_control_area_gal`, computed at creation from four factors. The base maximum allowable quantity comes from the hazard class: 120 gallons for `FLAMMABLE_IB`, 240 for `FLAMMABLE_II`, 500 for `CORROSIVE` and 250 for `OXIDIZER_2`. That base is multiplied by the floor's `percent_maq` — the height-derived percentage described with the floor plates above, running from the full hundred percent on floor 1 down to a quarter from floor 7 upward. It is multiplied again by 2.0 when the plate's `sprinklered` flag is true and by 1.0 when it is false, so a sprinklered plate carries exactly twice the allowance. Finally it is multiplied by the use factor of the `use_condition`: 2.0 for `STORAGE_CABINET`, 1.0 for `CLOSED_SYSTEM_USE` and 0.5 for `OPEN_SYSTEM_USE` — material in a listed cabinet is treated most generously and material in an open system most strictly. The product is rounded half up to two decimal places. The whole-floor figure, `aggregate_allowance_gal`, is `allowance_per_control_area_gal` multiplied by the floor's `control_areas_allowed`, again rounded half up to two decimal places.

Three domain rules guard the application, in order. A `control_area_index` below 1, or above the floor's `control_areas_allowed`, is refused with `ERR_CONTROL_AREA_OUT_OF_RANGE`. A `floor_id` that differs from the project's own `floor_id` is refused with `ERR_FLOOR_NOT_IN_PREMISES`. Then the applicant's own footprint is checked: restricted to permits belonging to this same project, on the same floor, with the same `hazard_class`, in the same `control_area_index`, and in `REQUESTED`, `APPROVED` or `ACTIVE` status, the sum of `quantity_gal` plus the newly requested `quantity_gal` must not exceed `allowance_per_control_area_gal` for this application's own `use_condition`; exceeding it is refused with `ERR_CONTROL_AREA_MAQ_EXCEEDED`. Note that a tenant's own pending applications occupy allowance against the tenant itself at application time — other tenants' quantities are not consulted until the authority rules. A successful application is created at `status` `REQUESTED` with `decision_reason` null. Permits can be read individually and listed with optional `project_id`, `floor_id`, `hazard_class`, `control_area_index` and `status` filters.

Ruling on an application belongs exclusively to the `AHJPermitOfficer`, who supplies a `decision` of `APPROVE`, `DENY` or `REVOKE` and an optional `decision_reason`. Four domain rules run in a fixed order. First the decision must match the permit's posture: `APPROVE` and `DENY` both require `status` `REQUESTED`, and `REVOKE` requires `status` `APPROVED` or `ACTIVE`; any other combination is refused with `ERR_INVALID_PERMIT_DECISION`. Second, an `APPROVE` against a project whose `permit_status` is not `P_ISSUED` is refused with `ERR_PROJECT_NOT_PERMITTED`. Third comes the floor-wide cross-tenant limit, which is the substantive code check: for an `APPROVE`, the sum of `quantity_gal` over every permit on the same floor, with the same `hazard_class`, in the same `control_area_index`, in `APPROVED` or `ACTIVE` status, across all projects and therefore across all tenants, plus this permit's own `quantity_gal`, must not exceed `allowance_per_control_area_gal`; exceeding it is refused with `ERR_CONTROL_AREA_MAQ_EXCEEDED`. Unlike the application-time check, this one ignores other permits still in `REQUESTED` and counts every tenant on the plate. Fourth, a `DENY` or `REVOKE` whose `decision_reason` is null or blank is refused with `ERR_DECISION_REASON_REQUIRED`, so the reason requirement is evaluated after the substantive checks rather than before them.

A ruling moves the permit along one of several arcs and bumps its `version`. `REQUESTED → APPROVED` on an approval; `REQUESTED → DENIED` on a denial, storing `decision_reason`; `APPROVED → REVOKED` or `ACTIVE → REVOKED` on a revocation, also storing `decision_reason`. Two further arcs are never called directly: `APPROVED → ACTIVE` when the project is accepted at the end of commissioning, and `APPROVED → SURRENDERED` or `ACTIVE → SURRENDERED` at restoration settlement. `DENIED`, `REVOKED` and `SURRENDERED` are all terminal.

Floor-level code reporting is available to the landlord, the engineer and the authority as a utilisation read on a floor, taking a required `hazard_class` and an optional `control_area_index` that defaults to control area 1 when omitted. The report deliberately expresses the same underlying permits on two different bases, and the two numbers routinely disagree. For reporting purposes only, the `use_condition` factor is fixed at `CLOSED_SYSTEM_USE` — a factor of 1.0 — so that the report is a pure function of the floor and the hazard class rather than of whichever use conditions happen to have been applied for; each individual permit still keeps the allowance derived from its own `use_condition`. On the per-control-area basis, `per_control_area_basis_gal` is the sum of `quantity_gal` over permits on that floor, with that hazard class, in that one control area, in `REQUESTED`, `APPROVED` or `ACTIVE` status — pending applications do occupy allowance — and `per_control_area_utilization_pct` is 100 multiplied by that basis and divided by `allowance_per_control_area_gal`, rounded half up to two decimal places. On the whole-floor basis, `aggregate_basis_gal` is the sum of `quantity_gal` over permits on that floor with that hazard class in `APPROVED` or `ACTIVE` status only — pending applications are ignored — and `aggregate_utilization_pct` is 100 multiplied by that basis and divided by `aggregate_allowance_gal`, rounded half up to two decimal places. The response also echoes `floor_id`, `hazard_class`, `control_area_index`, `control_areas_allowed`, `allowance_per_control_area_gal` and `aggregate_allowance_gal` so that the reader can see both numerators and both denominators. A `control_area_index` outside the floor's allowed range is refused with `ERR_CONTROL_AREA_OUT_OF_RANGE`.

### 3.9. Commissioning, Project Acceptance and Lease Wind-Down

Validation and commissioning are performed by an independent `CommissioningAgent` and are the only path to an accepted project. Scheduling a script under a project carries a `script_type` of `IQ`, `OQ`, `PQ`, `EXHAUST_AIRFLOW`, `EPSS_LOAD_TEST` or `CONTAINMENT_VERIFICATION`, a `scheduled_for` logical instant, and `executed_by_user_id`, the opaque identifier of the technician who will run it. Two domain rules run in order: a `script_type` that is not a member of the project's `required_commissioning_scripts` — which is to say, not required by the tenant's `research_type` — is refused with `ERR_SCRIPT_NOT_REQUIRED`; and a project that already has a record for that same `script_type` in `SCHEDULED` or `PASSED` status is refused with `ERR_DUPLICATE_COMMISSIONING_SCRIPT`. A script that previously failed may therefore be rescheduled, while one already passed or already pending may not be duplicated. Records are created at `status` `SCHEDULED` with `result`, `witnessed_by_user_id` and `measured_value` all null. They can be read individually, listed under their project filtered by `status`, or listed globally with optional `project_id`, `script_type`, `result` and `status` filters.

Recording a result carries a `result` of `PASS` or `FAIL`, the required `witnessed_by_user_id`, and an optional `measured_value`. Three domain rules run in order: a record whose `status` is not `SCHEDULED` is refused with `ERR_INVALID_COMMISSIONING_STATE`, since a result may be written exactly once; a project whose `construction_status` is not `C_SUBSTANTIAL_COMPLETION` is refused with `ERR_COMMISSIONING_INCOMPLETE`, because scripts are run against finished work; and a `witnessed_by_user_id` equal to the record's `executed_by_user_id` is refused with `ERR_WITNESS_CONFLICT`. Either result stores `result`, `witnessed_by_user_id` and `measured_value` and bumps the record's `version`.

A `PASS` takes the record `SCHEDULED → PASSED` and increases the project's `passed_script_count` by one, counting distinct required script types that now hold a passed record. When that count reaches the size of `required_commissioning_scripts` — four scripts for a `BSL2_BIOLOGY` or `CHEMISTRY_SYNTHESIS` tenant, six for a `VIVARIUM` tenant, two for an `ANALYTICAL_QC` tenant — the final pass fires a four-hop acceptance cascade in one request. The project moves `C_SUBSTANTIAL_COMPLETION → C_ACCEPTED` and stamps `accepted_at` with the current logical instant. Every capacity reservation of that project in `RESERVED` moves to `COMMITTED`, shifting its `exhaust_cfm` out of the building's `exhaust_reserved_cfm` and into `exhaust_committed_cfm` and its `power_kw` out of `power_reserved_kw` and into `power_committed_kw`, which leaves `exhaust_available_cfm` and `power_available_kw` unchanged — the capacity was already spoken for and is now permanently allocated. Every hazardous material permit of that project in `APPROVED` moves to `ACTIVE`. And the lease moves `EXECUTED → ACTIVE`. The project, each reservation, the building, each permit and the lease all have their `version` bumped by that single request.

A `FAIL` takes the record `SCHEDULED → FAILED` and reverses money rather than state. The lease's most recent draw is clawed back exactly: `ti_disbursed_usd` decreases by `last_disbursement_usd` and `ti_committed_usd` increases by the same figure, each phase package of the project has its `ti_disbursed_usd` reduced by precisely the amount that draw allocated to it, and `last_disbursement_usd` is then reset to zero so that a second failure cannot reverse the same draw twice. Both the lease's `version` and the record's `version` are bumped. A failure leaves `construction_status` at `C_SUBSTANTIAL_COMPLETION` and leaves `passed_script_count` untouched, so the agent may reschedule the failed script and try again.

Winding the lease down begins with an expiration notice, a landlord act carrying an `expiration_date` that must be at or after the current logical instant. It takes the lease `ACTIVE → EXPIRING`, stores `expiration_date`, computes `restoration_liability_usd`, and bumps `version`. Restoration liability has two components. The phase component is the sum of `restoration_cost_usd` over every phase package of every project on this lease whose `status` is `COMPLETE` and whose `premium_class` is anything other than `SHELL` — shell work is exempt from restoration because it stays with the building. The permit component is, for every hazardous material permit of this lease's projects in `APPROVED` or `ACTIVE` status, a flat decommissioning fee of 250.00 dollars plus 3.00 dollars for every gallon of `quantity_gal`, summed across those permits. The two components are added and rounded half up to two decimal places. An empty set on either side contributes 0.00 and is not an error: a lease with no completed phases and no live permits has a liability of exactly zero.

Settlement is the terminal act. Two domain rules run in order: a lease whose `status` is not `EXPIRING` is refused with `ERR_RESTORATION_ALREADY_SETTLED`, and a lease any of whose phase packages sit in `SCHEDULED`, `VIBRATION_HOLD`, `BLOCKED` or `IN_PROGRESS` is refused with `ERR_PHASES_NOT_QUIESCED`; every package across every project on the lease must be resting in `DRAFT` or `COMPLETE`. Settlement recomputes `restoration_liability_usd` on the same two components and then runs a waterfall in a strictly normative order.

The escrow is applied first: the amount applied is the smaller of `restoration_escrow_held_usd` and `restoration_liability_usd`. `restoration_escrow_refunded_usd` is set to whatever the escrow held in excess of that applied amount — the cash returned to the tenant — and `restoration_escrow_held_usd` is then zeroed. What the escrow could not cover is the remaining obligation. Against that remainder the landlord claws back undrawn allowance: the clawback is the smaller of the remaining obligation and `ti_uncommitted_usd`, and `ti_uncommitted_usd` is reduced by it. This clawback happens before the lapse step below, which is why the sequence is normative rather than a matter of taste. `restoration_cash_due_usd` is then the remaining obligation less the clawback, rounded half up to two decimal places — the residual cash the tenant still owes.

Only then does the allowance lapse. `ti_forfeited_usd` increases by the clawback amount, plus whatever `ti_uncommitted_usd` still holds after the clawback, plus the entire `ti_committed_usd` bucket — allowance committed to completed phases but never drawn is lost at surrender. `ti_uncommitted_usd` and `ti_committed_usd` are both set to zero, which leaves the ledger identity holding with `ti_authorized_usd` equal to `ti_disbursed_usd` plus `ti_forfeited_usd`.

Settlement also closes out the tenant's footprint on the base building. Every hazardous material permit of this lease's projects in `APPROVED` or `ACTIVE` status is surrendered. Every capacity reservation of those projects in `RESERVED` or `COMMITTED` status is released, reducing whichever bucket held it — `exhaust_reserved_cfm` and `power_reserved_kw` for a reserved row, `exhaust_committed_cfm` and `power_committed_kw` for a committed one — and returning that capacity to `exhaust_available_cfm` and `power_available_kw` for the next tenant. The lease finally moves `EXPIRING → SURRENDERED`, which is terminal, and every record the cascade touched — each permit, each reservation, the building and the lease — has its `version` bumped.
