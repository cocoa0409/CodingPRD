# State Revenue Forecasting Reserves API — Product Requirements Document

## 1. Introduction

A state revenue estimating body sits between two adversarial arithmetics. On one side, the executive branch and the legislature each maintain their own economists, their own macroeconomic assumptions, and their own view of what the next fiscal year's receipts will be; statute requires them to arrive at a single certified number. On the other side, that certified number immediately becomes money: it decides whether the budget stabilization account receives a deposit, whether a shortfall is deep enough to authorise a draw without a legislative vote, and what the state tells its bond rating agencies about reserve adequacy. Today this work is carried out in spreadsheets that cannot show who moved a number, cannot prove that a deposit was computed from the recurring base rather than a one-off legal settlement, and cannot stop a treasurer from sizing a withdrawal against a balance that another transaction has already spent.

This document specifies the API that replaces those spreadsheets. It governs the full arc of a forecast: economic scenario inputs with probability weights, revenue source elasticities against four macro drivers, statutory policy change adjustments with phase-in shapes, the identification of non-recurring items, the round-by-round consensus negotiation between the two estimating bodies with documented disagreement resolution, the revision cycles that supersede an earlier certification, the reserve deposit and withdrawal rules that hang off certification, the retrospective scoring of forecast error that feeds methodology review, and the briefings published to rating analysts.

Two engineering constraints shape everything that follows. First, **no floating-point arithmetic exists anywhere in this contract**: money is integer cents and every rate, elasticity, weight, variance and ratio is integer basis points. Second, the system's derived figures are never advisory — a fund's coverage ratio, a cycle's shortfall percentage and a source's mean absolute percentage error are all statutory disclosures, so their step order and rounding direction are part of the specification rather than an implementation detail.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that hold across every endpoint. Everything here is contract: field formats, header names, rounding directions, version semantics and the order in which the server decides to reject a request.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting operator and `X-User-Role` declares the capacity in which that operator acts. A request whose `X-User-Role` is absent, empty, or names a role the system does not recognise is rejected with `ERR_MISSING_ROLE_HEADER` (HTTP 401); a request whose `X-User-ID` is absent or empty is rejected with `ERR_MISSING_USER_HEADER` (HTTP 401). Once both headers are accepted, the endpoint's own role list decides: an operator whose role is not listed for the operation receives `ERR_UNAUTHORIZED` (HTTP 403).

Six roles exist, spelled exactly as follows.

- `ForecastDirector` — chair of the consensus process. Owns the cycle lifecycle (creation, amendment, input locking, reopening, certification), the round lifecycle (opening a round, ratifying it), disagreement resolution, revenue source registration, reserve fund creation, the two ballot-administration actions, and rating-briefing publication and retraction. A director may never file an estimate and may never cast a ballot.
- `ExecutiveEconomist` — the executive branch's estimating staff. Files the `EXECUTIVE` side of every round and maintains economic scenarios and policy adjustments alongside the director. Cannot ratify, certify, or resolve a disagreement.
- `LegislativeEconomist` — the legislature's estimating staff. Files the `LEGISLATIVE` side of every round. A peer of `ExecutiveEconomist`, but with no authority over economic scenarios or policy adjustments.
- `ReserveTreasurer` — custodian of the reserve funds. Posts manual deposits, reverses ledger rows, verifies shortfall triggers and executes approved draws. May neither open nor close a ballot.
- `LegislativeVoter` — a seat holder on the body that must supermajority-approve a withdrawal. Casts exactly one ballot per request and can read reserve state; nothing else.
- `RatingAnalyst` — the rating-agency-facing analyst. Drafts and edits briefings and reads everything, but publication and retraction belong to the `ForecastDirector` alone.

**Identity semantics.** All six roles are *opaque*: this domain has no persisted person entity, so `X-User-ID` is an operator identifier and is never compared against any resource's `id`. Concretely: when `X-User-Role` is `ForecastDirector`, `ExecutiveEconomist`, `LegislativeEconomist`, `ReserveTreasurer`, `LegislativeVoter`, or `RatingAnalyst`, the value of `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — as `submitted_by_user_id` on a source estimate, as `resolved_by_user_id` on a resolved disagreement record, as `requested_by_user_id` on a withdrawal request, and as `voter_user_id` on a ballot — and it compares those recorded values back to `X-User-ID` for the two segregation-of-duties rules described in §3.5 and §3.8 and for the one-ballot-per-voter rule, but it does not compare `X-User-ID` to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by twenty uppercase alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. This one field is read from wall-clock time rather than from the logical clock of §2.5, and it is the only timestamp in the contract that is.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

List endpoints are paginated through two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be lower than 1, and may not exceed 100. `offset` is the number of rows to skip and defaults to 0. A `limit` or `offset` that is not a well-formed integer, a `limit` outside 1–100 or a negative `offset` is rejected with `ERR_VALIDATION` (HTTP 422); a parameter supplied as an empty string is treated as absent and falls back to its default. Both appear in the `meta` block of the response together with `total_count` — the number of rows surviving the filters, before the page window is applied — and `has_more`, which is true when the rows skipped plus the rows returned still fall short of `total_count`.

Unless a specific endpoint says otherwise, every list is ordered by `created_at` ascending, and because every `created_at` is stamped from the logical clock two rows minted in the same clock instant tie: such ties are broken by the order in which the server minted the rows, ascending. This default is load-bearing in several places: the negotiation rounds of a cycle therefore come back with the highest `round_number` last, and the cascade-minted disagreement records of a disputed round come back in the same order the server minted them.

List endpoints additionally accept exact-match filters on the resource attributes named in their §4 description — for example forecast cycles filter on `fiscal_year`, `status`, `cycle_type`, `supersedes_cycle_id` and `ratified_round_id`; revenue sources on `status`, `tax_type`, `volatility_class` and `methodology_flag`; a cycle's scenarios on `label`; a source's policy adjustments on `policy_category`; one-time items on `cycle_id`, `source_id`, `status` and `item_type`; rounds on `cycle_id` and `status`; estimates on `round_id`, `source_id` and `body`; disagreement records on `round_id`, `source_id` and `status`; funds on `deposit_posture`, `adequacy_band` and `deposit_rule_variant`; ledger rows on `fund_id`, `origin`, `source_cycle_id` and `reverses_transaction_id`; withdrawal requests on `fund_id`, `cycle_id`, `status`, `justification_type` and `executed_transaction_id`; ballots on `vote`; actual collections on `source_id`, `fiscal_year`, `matched_cycle_id` and `error_direction`; and briefings on `fund_id`, `cycle_id`, `status` and `stale_reason`. Filters combine conjunctively and never change the ordering. An unrecognised query parameter is ignored, and a filter value that cannot be read as the attribute's type — a non-integer where an integer is expected, or anything but `true`/`false`/`1`/`0` for `methodology_flag` — matches nothing and yields an empty page rather than an error.

### 2.4. Units of Account and Rounding Discipline

Money is always an integer number of cents, carried in a field whose name ends in `_cents`. Rates, elasticities, probability weights, tolerances, variances, forecast errors and coverage ratios are always integer basis points, carried in a field whose name ends in `_bps`, where 10000 basis points represent exactly 1.0000 (one hundred per cent). No value in this contract is a decimal or floating-point number, and no intermediate result is ever truncated except where this document says "floor".

Three rounding operations appear, and which one applies is never a matter of choice.

- **Round half up** — round to the nearest integer, with an exact half rounded away from zero (so a value of one half becomes one, and a value of negative one half becomes negative one). This governs every money product, every trend line, every midpoint, every variance in basis points, the receipts-weighted volatility index, the required reserve, the statutory cap and the rolling forecast-error mean.
- **Floor** — discard the fractional part toward negative infinity. This governs exactly two figures, both for a stated reason: a fund's `coverage_ratio_bps`, so that reserve adequacy is never reported as better than it is, and a cycle's `shortfall_pct_bps`, so that a budget gap is never reported as deeper than it is.
- **Ceiling** — round up to the next integer. This governs only the two ballot requirements, `votes_required` and `quorum_required`, because a fractional legislative seat always rounds up to a whole seat.

Where a calculation names a step order, that order is normative: rounding at a different step produces a different integer and is wrong even when the difference is a handful of cents.

### 2.5. The Fiscal Year and the Logical Clock

A state fiscal year *N* begins at `(N-1)-07-01T00:00:00Z` inclusive and ends at `N-07-01T00:00:00Z` exclusive — so fiscal year 2027 covers 1 July 2026 through 30 June 2027, and its last day is 30 June 2027. Every fiscal-year window in this specification (policy adjustment overlap, actual-collection posting eligibility, the fiscal-year withdrawal cap) uses that definition.

All time in this system comes from a **logical clock**, never from wall-clock time (the sole exception being the envelope's own `api_request_timestamp`, §2.2). Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`. A test-driving endpoint available to the `ForecastDirector` and the `ReserveTreasurer` sets it: the request supplies `current_utc` — any well-formed ISO 8601 datetime, which may move the clock backwards as freely as forwards, a non-parsable value being rejected with `ERR_VALIDATION` — and the response echoes `current_utc` back verbatim as the client wrote it, alongside `lapsed_request_count`. Advancing the clock has one cascade of its own — every withdrawal request in `APPROVED` status whose `deadline_date` falls strictly before the date component of the new clock value transitions to `LAPSED`, processed in ascending `created_at` order, each such request having its `version` incremented by one, and `lapsed_request_count` reports how many requests lapsed on that call. Setting the clock also refreshes the clock-relative ledger figures of every reserve fund — `fy_opening_balance_cents`, `fy_withdrawn_cents`, `cooling_off_until` and `last_transaction_at` — because those are derived from the fiscal year the clock sits in; that refresh is not a mutation and increments no fund's `version`. Every deadline check, cooling-off comparison, vote-closing test and certification timestamp elsewhere in the document reads this same logical clock.

### 2.6. Resource Identity, Timestamps and Version Semantics

Every resource carries an `id`: a server-minted UUID with no type prefix, supplied by the server and never by the client. Every resource also carries `created_at`, an ISO 8601 UTC timestamp taken from the logical clock at creation and written in exactly the precision the clock itself holds: three fractional digits when the clock was set to a sub-second moment, and whole seconds with no fractional part otherwise, so a resource minted against the default clock reads `2026-08-01T00:00:00Z`. Every other logical-clock stamp in this contract — `updated_at`, `certified_at`, `ratified_at`, `resolved_at`, `voided_at`, `cast_at`, `executed_at`, `published_at`, `retracted_at`, `vote_closes_at`, `cooling_off_until`, `last_transaction_at` — is written in the same way.

Most resources additionally carry `updated_at` (same format, refreshed on every mutation) and `version` (an integer that starts at 1 and increments by one on every mutation of that resource, including mutations the server performs on its own initiative when a derived field is rewritten). Two entities are exceptions and carry only `id` and `created_at`: the **reserve ledger row** (`ReserveTransaction`) and the **ballot** (`WithdrawalVote`). Both are immutable audit records; neither has an `updated_at` field and neither has a `version` field. A compensating ledger movement is expressed as a new reversal row, not as an edit of the original.

Version increments are part of the observable contract, because clients pin them (see §2.7). A single business action routinely increments the `version` of several resources: adding a scenario increments both the scenario and its cycle, ratifying a round increments both the round and its cycle, and drafting a withdrawal request increments the version of the reserve fund it draws on even though no money has moved. Two qualifications hold throughout. A client-driven mutation increments the target's `version` even when the request changes nothing — a `PATCH` that carries no optional field at all still counts as one mutation. A server-initiated recompute of a *round* or of a *source estimate*, by contrast, is idempotent: when the recompute lands on values identical to the ones already stored, no `version` is incremented and `updated_at` is left alone.

### 2.7. Version Pinning on Round Openings and Withdrawal Drafts

Two write operations require the client to prove it is acting on a current view of a parent resource. In both cases the write is legitimate product behaviour that supersedes an earlier sibling row, so the pinned version is the *only* signal that distinguishes a writer working from an out-of-date read.

- `POST /consensus-rounds` requires a non-optional `expected_cycle_version` field carrying the `version` of the `ForecastCycle` named by `cycle_id` as the client last observed it. Opening a round legitimately supersedes the cycle's prior non-terminal round, so the server cannot infer staleness from the round's state. If `expected_cycle_version` does not equal the cycle's current `version`, the request is rejected with `ERR_STALE_CYCLE_VERSION` (HTTP 412) and nothing is created or superseded.
- `POST /withdrawal-requests` requires a non-optional `expected_fund_version` field carrying the `version` of the `ReserveFund` named by `fund_id` as the client last observed it. A new draft legitimately rejects any prior draft on the same fund, and the fund's `version` advances on every deposit, execution, reversal, posture flip and adequacy recomputation, so a mismatch means the requester sized the draw against a balance the fund no longer holds. If `expected_fund_version` does not equal the fund's current `version`, the request is rejected with `ERR_STALE_FUND_VERSION` (HTTP 412).

No other endpoint accepts a version field. Endpoints not named above perform no version check and must not require one.

### 2.8. Reconciliation Cascades and Derived-Field Propagation

The system's consistency model is immediate: when a write changes a value another resource derives from, the dependent resource is recomputed inside the same request, not by a later job. Four propagation habits recur throughout §3 and are stated once here.

**Parent state follows child state.** Creating the first negotiation round of a locked cycle drives that cycle from `INPUTS_LOCKED` to `IN_CONSENSUS`; ratifying a round bubbles its cycle from `IN_CONSENSUS` to `CONSENSUS_REACHED`; certifying a revision cycle drives its predecessor from `CERTIFIED` to `SUPERSEDED`. Every one of these server-initiated transitions increments the affected resource's `version` and refreshes its `updated_at` exactly as a client-driven transition would.

**Supersession voids, it does not resolve.** When a round is superseded — because a later round opened on the same cycle, or because the cycle was reopened — every `OPEN` disagreement record of that round becomes `VOIDED`, and a voided record keeps `resolution_method` and `resolved_amount_cents` null. Voiding is not a resolution and never contributes a value to any reconciled total.

**Money movements ripple in a fixed chain.** Any change to a fund's `balance_cents` re-derives the whole adequacy disclosure (§3.7), re-evaluates `deposit_posture`, refreshes `last_transaction_at`, increments the fund's `version`, and marks every `PUBLISHED` briefing of that fund `STALE` with `stale_reason` `RESERVE_BALANCE_CHANGED`. Superseding a cycle marks every `PUBLISHED` briefing of that cycle `STALE` with `stale_reason` `CYCLE_SUPERSEDED`.

**Locking stops recomputation.** Once a round is ratified, each of its source estimates has `locked` set to true, and a locked estimate is never recomputed by a later cascade — a one-time item voided afterwards changes nothing about a certified or ratified figure.

### 2.9. Path Resolution and the Rejection Ladder

Nested paths are resolved strictly left to right. For a request against `/forecast-cycles/{id}/consensus-rounds`, the cycle is looked up first; if it does not exist the response is `ERR_CYCLE_NOT_FOUND` (HTTP 404) and the server never considers the rest of the request. The 404 code always identifies the resource type of the segment that failed: `ERR_CYCLE_NOT_FOUND` for a forecast cycle, `ERR_SCENARIO_NOT_FOUND` for an economic scenario, `ERR_SOURCE_NOT_FOUND` for a revenue source, `ERR_ADJUSTMENT_NOT_FOUND` for a policy change adjustment, `ERR_ONE_TIME_ITEM_NOT_FOUND` for a one-time item, `ERR_ROUND_NOT_FOUND` for a negotiation round, `ERR_ESTIMATE_NOT_FOUND` for a source estimate, `ERR_DISAGREEMENT_NOT_FOUND` for a disagreement record, `ERR_FUND_NOT_FOUND` for a reserve fund, `ERR_TRANSACTION_NOT_FOUND` for a ledger row, `ERR_REQUEST_NOT_FOUND` for a withdrawal request, `ERR_VOTE_NOT_FOUND` for a ballot, `ERR_ACTUAL_NOT_FOUND` for a posted actual collection, and `ERR_BRIEFING_NOT_FOUND` for a rating-agency briefing. The same codes are reused when a foreign key supplied **in a request body** — `cycle_id`, `source_id`, `round_id`, `fund_id`, or a referenced ledger row — names a row that does not exist.

Every request is evaluated against an ordered ladder of checks, and **the first check that fails decides the response**; later checks are never reached and never influence the status code. The ladder runs in this order:

1. **Authentication** — `ERR_MISSING_ROLE_HEADER`, then `ERR_MISSING_USER_HEADER`.
2. **Authorisation** — `ERR_UNAUTHORIZED`.
3. **Path existence**, left to right, then **body foreign-key existence** — the 404 codes above.
4. **Request shape** — `ERR_VALIDATION` (HTTP 422) when a required field is missing, an enum value is outside its declared set, a `_cents`, `_bps` or count value is not an integer, a money or basis-point value is negative where negatives are not allowed (only `judgmental_adjustment_cents` and a ledger row's `signed_amount_cents` may be negative), a date is not a well-formed ISO date, or a `rationale`, `narrative` or `memo` falls outside its length bounds. A body that is syntactically unreadable, or readable but not a JSON object, is the same `ERR_VALIDATION` (HTTP 422); a body that is absent altogether is read as an empty object, so a transition whose fields are all optional — a publication without `refresh_snapshot`, or any transition that declares no body at all — succeeds with no body sent. Outside the ladder entirely sit two generic failures that belong to no resource: a path matching no route at all answers `ERR_NOT_FOUND` (HTTP 404), and a known path addressed with the wrong HTTP method answers `ERR_METHOD_NOT_ALLOWED` (HTTP 405), both before any header is examined.
5. **Version pinning** — `ERR_STALE_CYCLE_VERSION` on a round opening, `ERR_STALE_FUND_VERSION` on a withdrawal draft. Note the position: staleness is decided *before* any state check, so a client holding an old cycle version is told its view is stale rather than being told the cycle is in the wrong state.
6. **Resource state** — the `409 Conflict` family: `ERR_CYCLE_NOT_IN_DRAFT`, `ERR_CYCLE_NOT_LOCKED`, `ERR_CYCLE_ALREADY_RATIFIED`, `ERR_CYCLE_NOT_CONSENSUS_REACHED`, `ERR_ROUND_NOT_OPEN`, `ERR_BODY_ALREADY_SUBMITTED`, `ERR_ROUND_NOT_COMPARED`, `ERR_DISAGREEMENT_NOT_OPEN`, `ERR_ESTIMATE_LOCKED`, `ERR_ONE_TIME_ITEM_NOT_ACTIVE`, `ERR_REQUEST_NOT_DRAFT`, `ERR_VOTE_NOT_OPEN`, `ERR_REQUEST_NOT_APPROVED`, `ERR_AUTHORIZATION_LAPSED`, `ERR_BRIEFING_NOT_PUBLISHABLE`, `ERR_BRIEFING_TERMINAL`, `ERR_FUND_AT_CAP` and `ERR_TRANSACTION_ALREADY_REVERSED`, in exactly that relative order.
7. **Temporal windows** — `ERR_VOTE_STILL_OPEN`, `ERR_COOLING_OFF_ACTIVE`, `ERR_BRIEFING_COOLING_PERIOD`, `ERR_INVALID_EFFECTIVE_WINDOW`, `ERR_POLICY_WINDOW_OVERLAP`, `ERR_FISCAL_YEAR_NOT_CLOSED`, in that relative order. Temporal checks deliberately precede statutory safety checks: a ballot that is still open has no meaningful tally, so `ERR_VOTE_STILL_OPEN` must win over `ERR_QUORUM_NOT_MET` and `ERR_SUPERMAJORITY_NOT_MET`.
8. **Statutory safety** — `ERR_JUSTIFICATION_MISMATCH`, `ERR_SHORTFALL_NOT_TRIGGERED`, `ERR_QUORUM_NOT_MET`, `ERR_SUPERMAJORITY_NOT_MET`, `ERR_DUPLICATE_VOTE`, `ERR_SEGREGATION_OF_DUTIES`, `ERR_EXECUTOR_IS_REQUESTER`, `ERR_ADEQUACY_STALE`, in that relative order.
9. **Referential status** — `ERR_SOURCE_RETIRED`, `ERR_CYCLE_NOT_CERTIFIED`, `ERR_CYCLE_ALREADY_CERTIFIED`, `ERR_NO_CERTIFIED_FORECAST`, `ERR_INVALID_SUPERSEDE_TARGET`, in that relative order.
10. **Uniqueness and completeness constraints** — `ERR_SCENARIO_WEIGHTS_INVALID`, `ERR_DUPLICATE_SCENARIO_LABEL`, `ERR_DUPLICATE_ESTIMATE`, `ERR_INCOMPLETE_SUBMISSION`, `ERR_DUPLICATE_ACTUAL`, `ERR_OVERRIDE_OUT_OF_RANGE`, `ERR_RESOLUTION_AMOUNT_NOT_ALLOWED`, `ERR_RATIONALE_TOO_SHORT`, in that relative order.
11. **Fiscal limits, last of all** — `ERR_JUDGMENTAL_ADJUSTMENT_CAP`, `ERR_DEPOSIT_EXCEEDS_CAP`, `ERR_ANNUAL_CAP_EXCEEDED`, `ERR_INSUFFICIENT_RESERVE_BALANCE`, `ERR_REVERSAL_WOULD_OVERDRAW`, in that relative order. Fiscal checks come last on purpose: a request in the wrong state must never leak balance information through a fiscal error.

Each §3 workflow restates the ladder positions that matter for its own operation, because the interesting orderings are the ones inside a single endpoint.

## 3. Business Logic & Workflows

### 3.1. Opening a Forecast Cycle and Freezing Its Economic Inputs

The **forecast cycle** is the organising unit of the whole system: one cycle is one forecast of one state fiscal year, and it moves through `DRAFT`, `INPUTS_LOCKED`, `IN_CONSENSUS`, `CONSENSUS_REACHED`, `CERTIFIED` and finally `SUPERSEDED`, which is terminal. A `ForecastDirector` opens one by supplying the `fiscal_year` it covers (an integer of at least 2000 and at most 2100), the `cycle_type`, the `reconciliation_policy` that will govern how the two bodies' numbers are combined, the `enacted_appropriation_cents` that the legislature actually appropriated for that year (which must be greater than zero), and the `prior_recurring_baseline_cents` — the documented certified recurring revenue of the preceding fiscal year, at least zero, supplied as an input because the first cycle in the system has no in-database predecessor. A new cycle is created in `DRAFT` with `scenario_weight_total_bps` at 0, `reopen_count` at 0, and every certified aggregate (`certified_total_cents`, `certified_one_time_cents`, `certified_recurring_total_cents`, `certified_at`, `shortfall_gap_cents`, `shortfall_pct_bps`, `ratified_round_id`) null.

`cycle_type` is either `BASELINE`, the first forecast of a fiscal year, or `REVISION`, which replaces an earlier certified forecast of the same year. That choice constrains `supersedes_cycle_id`: a `REVISION` cycle **must** name a `supersedes_cycle_id`, and the cycle it names must be in `CERTIFIED` status and carry the same `fiscal_year`; a `BASELINE` cycle must leave `supersedes_cycle_id` null. Naming no target on a revision, naming a target that is not certified, naming one whose fiscal year differs, or naming any target at all on a baseline cycle are all rejected with `ERR_INVALID_SUPERSEDE_TARGET` (HTTP 422); naming a `supersedes_cycle_id` that matches no stored cycle is instead the body-foreign-key case of §2.9 and reports `ERR_CYCLE_NOT_FOUND` (HTTP 404) before any other field of the request is judged. While the cycle is in `DRAFT` the director may amend `enacted_appropriation_cents`, `prior_recurring_baseline_cents` and `reconciliation_policy`; each of the three is optional on the amendment and only the ones supplied are rewritten, but every accepted amendment increments the cycle's `version` by one even when the body carries none of them. Nothing else about a cycle may be amended — `fiscal_year`, `cycle_type` and `supersedes_cycle_id` are fixed at creation.

`reconciliation_policy` is either `MIDPOINT_AVERAGE` — the statutory default for baseline cycles — or `LOWER_OF_TWO`, the stricter rule a revision cycle may adopt. Its effect is described in §3.5; what matters here is that the policy is a property of the cycle, chosen before any negotiation begins, and that every round of the cycle inherits it.

**Economic scenarios.** Within a `DRAFT` cycle, the director or an `ExecutiveEconomist` attaches **economic scenarios**, each one a weighted view of the macroeconomy. A scenario's `cycle_id` always comes from the creation path and is never read from the body. Its `label` is one of `BASELINE`, `OPTIMISTIC`, `PESSIMISTIC` or `ALTERNATIVE`, and must be unique within its cycle — a second scenario reusing a label is rejected with `ERR_DUPLICATE_SCENARIO_LABEL` (HTTP 409). Its `weight_bps` is the probability weight assigned to the scenario, at least 0 and at most 10000. Four macro drivers follow, all in basis points and all permitted to be negative because a scenario may forecast contraction: `employment_growth_bps` for year-over-year nonfarm employment growth, `wage_income_bps` for wage and salary income growth, `retail_sales_bps` for taxable retail activity growth, and `asset_market_return_bps` for the broad asset market's total return.

Every scenario creation, re-weighting or deletion rewrites the cycle's `scenario_weight_total_bps` to the sum of the weights of the cycle's scenarios and increments the cycle's `version` by one; a re-weighting also increments the scenario's own `version`. All three actions require the owning cycle to be in `DRAFT`; attempted on a cycle in any other status they are rejected with `ERR_CYCLE_NOT_IN_DRAFT` (HTTP 409). For a re-weighting, the label-uniqueness check applies exactly as it does on creation, and the state check comes first: a patch against a locked cycle yields `ERR_CYCLE_NOT_IN_DRAFT`, not a duplicate-label error. Deletion of a scenario is the `ForecastDirector`'s alone and returns no body.

**Locking the inputs.** When the scenario set is complete the director locks it, moving the cycle `DRAFT → INPUTS_LOCKED`. Locking requires the cycle to be in `DRAFT` (otherwise `ERR_CYCLE_NOT_IN_DRAFT`), requires at least one scenario to exist on the cycle, and requires `scenario_weight_total_bps` to equal exactly 10000 — the probabilities must sum to precisely one. Those are the only two conditions: locking imposes no requirement whatever on the revenue portfolio, so a cycle whose scenario weights are sound locks successfully even when the system holds no revenue source at all. A cycle whose scenario weights total anything other than 10000, or that has no scenarios at all, is rejected with `ERR_SCENARIO_WEIGHTS_INVALID` (HTTP 422). Once the cycle is `INPUTS_LOCKED`, its scenarios are immutable: any further attempt to add, re-weight or delete one comes back as `ERR_CYCLE_NOT_IN_DRAFT`. Locking increments the cycle's `version` by one.

**Reopening for re-weighting.** A cycle in `IN_CONSENSUS` can be sent back to `DRAFT` by the director so the economists can re-weight the scenarios — the revision loop of the negotiation. Reopening is legal only while the cycle is in `IN_CONSENSUS` and no round of the cycle has reached `RATIFIED`; otherwise it is rejected with `ERR_CYCLE_ALREADY_RATIFIED` (HTTP 409). Reopening carries a wide cascade: every round of the cycle whose `status` is `OPEN`, `COMPARED` or `DISPUTED` becomes `SUPERSEDED`, every `OPEN` disagreement record of those rounds becomes `VOIDED`, `reopen_count` is increased by one, `ratified_round_id` is set back to null, the cycle's scenarios become mutable again, and the cycle's `version` increments by one.

### 3.2. The Revenue Portfolio: Sources, Elasticities and Statutory Policy Changes

Revenue sources are registered once and shared by every cycle. Only a `ForecastDirector` may register one, supplying a display `name` such as "Personal Income Tax", a `tax_type` drawn from `PIT`, `CIT`, `SALES`, `CAPITAL_GAINS`, `EXCISE` or `OTHER`, the prior fiscal year's actual receipts as `base_year_receipts_cents` (strictly greater than zero, and the multiplicand of every scenario-weighted estimate), four elasticities, and a `volatility_class` of `LOW`, `MEDIUM` or `HIGH`. The elasticities — `elasticity_employment_bps`, `elasticity_wage_income_bps`, `elasticity_retail_bps` and `elasticity_asset_bps` — each express, in basis points, how strongly this source responds to one basis point of movement in the corresponding macro driver. A newly registered source begins with `status` `ACTIVE`, `mape_bps` 0, `methodology_flag` false and `posted_actual_count` 0.

The director may later restate a source's `base_year_receipts_cents` or `volatility_class`, or flip its `status` between `ACTIVE` and `RETIRED` — retirement is not one-way, and a `RETIRED` source may be restored to `ACTIVE` by the same patch; each field is optional, and each such change increments the source's `version` by one whatever the source's current status is. The `status` distinction is consequential: `ACTIVE` sources are in scope for estimates, for the submission-completeness check and for the volatility index, while `RETIRED` sources are excluded from all three. A policy adjustment, one-time item, source estimate or actual collection that references a `RETIRED` source is rejected with `ERR_SOURCE_RETIRED` (HTTP 422).

**Statutory policy changes.** A `ForecastDirector` or an `ExecutiveEconomist` attaches **policy change adjustments** to a source; the adjustment's `source_id` comes from the creation path. Each adjustment records the `statute_code` that enacted it (for example "SB-2026-14"), a `policy_category` of `RATE_CHANGE`, `BASE_CHANGE`, `CREDIT` or `COMPLIANCE`, an `adjustment_kind` of `INCREASE` or `DECREASE`, and an `annualized_amount_cents` giving the full-year revenue impact as a positive magnitude greater than zero — the direction lives entirely in `adjustment_kind`, never in the sign of the amount. The effective window is half-open: `effective_start_date` is the first ISO date on which the statute applies and is *inclusive*, while `effective_end_date` is the first ISO date on which it no longer applies and is *exclusive*, so an adjustment ending on the very day the next one starts is legal adjacency rather than an overlap. `phase_in_type` selects the shape of the impact (`FULL`, `PRORATED` or `TIERED`), `first_effective_fiscal_year` is the fiscal year of first application (an integer of at least 2000 and at most 2100), and `cap_amount_cents` is an absolute ceiling on the fiscal-year impact, defaulting to 0, which means uncapped. Restating an adjustment's `annualized_amount_cents`, window, `phase_in_type` or `cap_amount_cents` increments its `version` by one, each of those being optional on the restatement and only the supplied ones rewritten — except that `effective_end_date` sent explicitly as null clears the end date and reopens the window indefinitely, which is how a closed window is reopened; `statute_code`, `policy_category`, `adjustment_kind` and `first_effective_fiscal_year` are fixed at creation. A director may also delete an adjustment outright. An adjustment has no status field of its own: it is "active", for both the overlap rule and the phase-in arithmetic below, from the moment it is created until it is deleted.

Two window rules guard both creation and restatement, and they are evaluated in this order. First, when `effective_end_date` is present it must be strictly after `effective_start_date`; a window that ends on or before it begins is rejected with `ERR_INVALID_EFFECTIVE_WINDOW` (HTTP 422). Second, no two active adjustments of the *same source and the same `policy_category`* may have overlapping half-open windows; a genuine overlap is rejected with `ERR_POLICY_WINDOW_OVERLAP` (HTTP 409), while two windows that merely share a boundary date pass. Only after both window rules pass does the retired-source check apply on creation, so an adjustment with a malformed window against a retired source reports the window error.

**How an adjustment becomes cents for a given fiscal year.** For a target fiscal year, take the year's first day (1 July of the preceding calendar year) and its last day (30 June of the fiscal year itself). Then, for each active adjustment on the source taken in ascending `created_at` order, work out its contribution:

- If `first_effective_fiscal_year` is greater than the target fiscal year, the adjustment contributes nothing.
- If `effective_start_date` falls after the year's last day, or if `effective_end_date` is present and falls on or before the year's first day, the adjustment contributes nothing — the exclusive end boundary is why an end date equal to the year's first day contributes nothing.
- With `phase_in_type` `FULL`, the raw amount is `annualized_amount_cents` unchanged.
- With `phase_in_type` `PRORATED`, the overlap begins at the later of `effective_start_date` and the year's first day, and ends at the earlier of the year's last day and the day before `effective_end_date` (or the year's last day when there is no end date). Count the whole calendar months that the inclusive overlap spans: twelve times the difference in calendar years, plus the difference in calendar month numbers, plus one — so an overlap running from 1 October through 30 June counts as nine months. The raw amount is `annualized_amount_cents` multiplied by that month count, divided by twelve, rounded half up.
- With `phase_in_type` `TIERED`, subtract `first_effective_fiscal_year` from the target fiscal year to obtain a zero-based tier index, then take that index's phase-in factor from the statutory ladder of 2500, 5000, 7500 and 10000 basis points — a quarter of the annualised impact in the first year, a half in the second, three quarters in the third, and the full impact from the fourth year onward, an index above 3 being clamped to 3. The raw amount is `annualized_amount_cents` multiplied by that factor, divided by 10000, rounded half up.

The cap is applied **after** rounding, never before: when `cap_amount_cents` is 0 the raw amount stands, and otherwise the amount is the lower of the raw amount and `cap_amount_cents`. Finally the sign is applied — the capped amount as it stands when `adjustment_kind` is `INCREASE`, and its negation when `adjustment_kind` is `DECREASE`. The source's `policy_adjustment_cents` for that fiscal year is the sum of all such signed contributions.

### 3.3. Non-Recurring Receipts and the Recurring Control Total

A legal settlement, an asset sale, a slug of federal aid or a tax amnesty inflates a year's receipts without raising the state's underlying revenue capacity, and treating such money as recurring is precisely how a reserve deposit rule gets gamed. Any of the three forecasting roles — `ForecastDirector`, `ExecutiveEconomist` or `LegislativeEconomist` — therefore records **one-time items** explicitly, naming the `cycle_id` of the forecast cycle whose estimates include the amount, the `source_id` of the revenue source it lands in, an `item_type` of `SETTLEMENT`, `ASSET_SALE`, `FEDERAL_AID` or `TAX_AMNESTY`, a positive `amount_cents`, and a free-text `description` identifying the item. A recorded item starts with `status` `ACTIVE`, and `voided_at` null.

Recording an item is not inert. Every unlocked source estimate for that cycle-and-source pair immediately recomputes its `one_time_cents` and `estimate_amount_cents`, and the owning round's variance and reconciled total are recomputed with it. An item may only be recorded against a cycle that has not yet been certified: recording into a cycle that is already `CERTIFIED` or `SUPERSEDED` is rejected with `ERR_CYCLE_ALREADY_CERTIFIED` (HTTP 409), and the retired-source check precedes it, so a `RETIRED` source reports `ERR_SOURCE_RETIRED` first.

**Voiding.** An item may be voided by the same three roles, which sets `status` to `VOIDED`, stamps `voided_at` with the logical clock, and increments the item's `version` by one. Voiding is only legal on an item that is still `ACTIVE` — a second void is rejected with `ERR_ONE_TIME_ITEM_NOT_ACTIVE` (HTTP 409) — and only while the owning cycle is not yet certified, which is checked after the item's own state, so voiding an already-voided item in a certified cycle reports `ERR_ONE_TIME_ITEM_NOT_ACTIVE` rather than `ERR_CYCLE_ALREADY_CERTIFIED`. Every unlocked estimate for the affected cycle-and-source pair then recomputes `one_time_cents` and `estimate_amount_cents`, and the owning round recomputes both its variance and its reconciled total. This recompute has a counter-intuitive consequence that the negotiation must tolerate: removing a non-recurring amount shrinks each body's per-source figure and therefore shrinks the midpoint that per-source variance is measured against, so the same absolute gap between the two bodies can breach a relative tolerance it previously satisfied — a `COMPARED` round can be pushed back to `DISPUTED` by a void, as §3.4 describes.

The recurring/non-recurring split is also what makes certification meaningful: at certification the cycle records `certified_one_time_cents` as the sum of `amount_cents` over its `ACTIVE` one-time items and derives `certified_recurring_total_cents` by subtracting that sum from `certified_total_cents`. The recurring figure, not the headline total, is what reserve deposits are measured against.

### 3.4. The Consensus Negotiation: Filing and Submitting Estimates

Once a cycle's inputs are locked, the `ForecastDirector` opens a **negotiation round**. The request names the `cycle_id`, sets the two tolerances that define what counts as agreement, and pins the cycle version as described in §2.7. `variance_tolerance_bps` is the maximum grand-total variance between the two bodies that still counts as consensus, and `per_source_tolerance_bps` is the maximum variance on any single source — breaching the per-source tolerance disputes the round even when the grand totals agree. Both are at least 0 and at most 10000. The server assigns `round_number` as one more than the count of rounds already on the cycle, so the first round of a cycle is round 1, and creates the round with `status` `OPEN`, `exec_submission_status` and `leg_submission_status` both `PENDING`, and `open_disagreement_count` 0.

Opening a round is only legal against a cycle in `INPUTS_LOCKED` or `IN_CONSENSUS`; any other cycle status is rejected with `ERR_CYCLE_NOT_LOCKED` (HTTP 409). Because the version pin sits above the state ladder, a client whose `expected_cycle_version` is behind gets `ERR_STALE_CYCLE_VERSION` even when the cycle is also in the wrong state. A successful opening drives the cycle `INPUTS_LOCKED → IN_CONSENSUS` on the first round; for a second or later round on a cycle already `IN_CONSENSUS` the cycle re-enters `IN_CONSENSUS` — a self-loop that is legal only while no round of the cycle has reached `RATIFIED` — and in either case the cycle's `version` increments by one. A later round supersedes its predecessors: every round of the cycle whose `status` is `OPEN`, `COMPARED` or `DISPUTED` becomes `SUPERSEDED`, each of those rounds has its `open_disagreement_count` reset to 0, its `OPEN` disagreement records become `VOIDED`, and each superseded round's `version` increments by one.

**Filing an estimate.** Inside an open round each body files one estimate per revenue source. Only an `ExecutiveEconomist` or a `LegislativeEconomist` may file, and the `body` field is derived from the caller's role rather than supplied: `ExecutiveEconomist` produces `EXECUTIVE`, `LegislativeEconomist` produces `LEGISLATIVE`. The request carries the `round_id`, the `source_id` being estimated, and optionally a `judgmental_adjustment_cents` overlay, which defaults to 0 and is the one money field in this system permitted to be negative. `submitted_by_user_id` is taken from the filer's `X-User-ID` header and retained for the segregation-of-duties rule in §3.5. At most one estimate may exist per round, source and body combination; a second attempt is rejected with `ERR_DUPLICATE_ESTIMATE` (HTTP 409). Estimates may be filed while the round is `OPEN` or `COMPARED`; on a round in any other status the attempt is rejected with `ERR_ROUND_NOT_OPEN` (HTTP 409). Filing is not itself a recompute trigger: a new estimate landing in a round that has already reached `COMPARED` leaves that round's `exec_total_cents`, `leg_total_cents`, `variance_bps`, `reconciled_total_cents`, `status` and `version` exactly as they stood, and only a later revision of an estimate, or a one-time-item cascade, re-runs the round's figures.

Four components are computed and stored on every estimate, and their sum is the number the body is committing to.

1. `weighted_scenario_cents` — the scenario-weighted pre-policy revenue level for this source, computed as described below.
2. `policy_adjustment_cents` — the signed sum of the source's statutory policy impacts for the cycle's fiscal year, exactly as specified in §3.2.
3. `judgmental_adjustment_cents` — the body's discretionary overlay, as supplied.
4. `one_time_cents` — the sum of `amount_cents` over the `ACTIVE` one-time items recorded for the round's cycle and this source.

From these, `recurring_component_cents` is the sum of `weighted_scenario_cents`, `policy_adjustment_cents` and `judgmental_adjustment_cents`, and `estimate_amount_cents` is `recurring_component_cents` plus `one_time_cents`. A newly filed estimate has `locked` false.

**The scenario-weighted component, step by step.** The step order here is normative, and getting it wrong produces a number that is close but not equal to the right one. Take the cycle's scenarios in ascending `created_at` order and, for each one:

1. Multiply the scenario's `employment_growth_bps` by the source's `elasticity_employment_bps`, its `wage_income_bps` by `elasticity_wage_income_bps`, its `retail_sales_bps` by `elasticity_retail_bps`, and its `asset_market_return_bps` by `elasticity_asset_bps`, and add the four products together. Divide that sum by 10000 and round half up to obtain **that scenario's growth rate in whole basis points**.
2. Add that growth rate to 10000, multiply the source's `base_year_receipts_cents` by the result, divide by 10000, and round half up to obtain **that scenario's revenue amount in whole cents**.

Then multiply each scenario's amount by that scenario's `weight_bps`, sum the products across all scenarios, divide by 10000, and round half up exactly once. That single figure is `weighted_scenario_cents`. It is wrong to blend the growth rates first and apply one composite rate to the base year receipts: the per-scenario rounding at both steps is part of the specification, and the shortcut is off by tens of thousands of cents on a source of ordinary size.

**The judgmental overlay is bounded.** The absolute value of `judgmental_adjustment_cents` may not exceed 1000 basis points — one tenth — of the absolute value of the sum of `weighted_scenario_cents` and `policy_adjustment_cents`, that is, of the magnitude of the estimate's pre-judgmental recurring amount; the comparison is made in exact integers as `|judgmental| × 10000 ≤ |weighted + policy| × 1000`, so an overlay landing exactly on the ceiling is accepted. A larger overlay is rejected with `ERR_JUDGMENTAL_ADJUSTMENT_CAP` (HTTP 422). This is a fiscal check and therefore sits at the very bottom of the ladder: on a filing that also names a retired source, or that duplicates an existing estimate, the retired-source and duplicate errors are reported instead. An economist may revise the judgmental component of an estimate afterwards by supplying a new `judgmental_adjustment_cents`; `recurring_component_cents` and `estimate_amount_cents` are recomputed, the estimate's `version` increments by one, and when the round has already reached `COMPARED` or `DISPUTED` the round's variance and reconciled total are recomputed too. A revision requires the round to be `OPEN` or `COMPARED`, otherwise `ERR_ROUND_NOT_OPEN`; it is refused with `ERR_ESTIMATE_LOCKED` (HTTP 409) once the estimate's `locked` flag is true, and that check sits below the round-state check, so an estimate belonging to a superseded round reports `ERR_ROUND_NOT_OPEN` first. The same one-tenth ceiling on `judgmental_adjustment_cents` is enforced on a revision as on the original filing, and a revision that breaches it is rejected with `ERR_JUDGMENTAL_ADJUSTMENT_CAP`.

**Submitting a side.** Each body then declares its side complete, which is a transition on its own dimension: `exec_submission_status` moves `PENDING → SUBMITTED` when an `ExecutiveEconomist` submits, and `leg_submission_status` moves `PENDING → SUBMITTED` when a `LegislativeEconomist` submits. These two dimensions live on the same round row, evolve independently, may reach `SUBMITTED` in either order, and neither constrains the other. Submitting requires the round's `status` to be `OPEN`, otherwise `ERR_ROUND_NOT_OPEN`; requires the acting body's own dimension to still be `PENDING`, otherwise `ERR_BODY_ALREADY_SUBMITTED` (HTTP 409); and requires the submitting body to hold an estimate for *every* revenue source with `status` `ACTIVE`, otherwise `ERR_INCOMPLETE_SUBMISSION` (HTTP 422). These three run in exactly that order. A successful submission writes the acting body's total — `exec_total_cents` as the sum of `estimate_amount_cents` over *every* one of the round's `EXECUTIVE` estimates, or `leg_total_cents` as the same sum over its `LEGISLATIVE` estimates, each null until its own dimension is `SUBMITTED` — and increments the round's `version` by one. The two grand totals are unfiltered sums over the estimates actually on the round, so an estimate filed against a source that has since been retired still counts toward its body's total even though that source has dropped out of the per-source comparison and out of the reconciled total.

**Comparison.** When the *second* of the two dimensions reaches `SUBMITTED`, the server compares the two submissions inside that same submission request; the comparison shares the submission's single `version` increment rather than adding a second one, so a round that goes `OPEN → COMPARED` on the second submission comes back with its `version` one higher than before that request, not two. For each revenue source with `status` `ACTIVE`, taken in ascending `created_at` order and skipping any source that lacks one of the two estimates entirely, let the executive figure and the legislative figure be that source's two `estimate_amount_cents` values. The source's midpoint is their sum divided by two, rounded half up, and the source's variance in basis points is the absolute difference between the two figures multiplied by 10000, divided by that midpoint, rounded half up — and defined as 0 when the midpoint is 0. Every relative measure in this system is taken against the midpoint of the two submissions, never against either body's own figure. At the aggregate level, the grand midpoint is `exec_total_cents` plus `leg_total_cents` divided by two, rounded half up, and `variance_bps` is the absolute difference between the two totals multiplied by 10000, divided by the grand midpoint, rounded half up. The aggregate variance is computed from the summed totals; it is never the average of the per-source variances.

The comparison forks. If `variance_bps` is at most `variance_tolerance_bps` **and** no source's variance exceeds `per_source_tolerance_bps`, the round goes `OPEN → COMPARED`: `exec_total_cents`, `leg_total_cents` and `variance_bps` are written, `reconciled_total_cents` is written as described in §3.5, and the round's `version` increments by one. If instead `variance_bps` exceeds `variance_tolerance_bps` **or** at least one source's variance exceeds `per_source_tolerance_bps`, the round goes `OPEN → DISPUTED`: the two totals and `variance_bps` are written; one disagreement record with `status` `OPEN` is minted for each revenue source whose own variance exceeds `per_source_tolerance_bps`, in ascending source `created_at` order, each capturing that source's `exec_amount_cents`, `leg_amount_cents` and `variance_bps` as of comparison time; `open_disagreement_count` is set to the number of records minted; `reconciled_total_cents` is written from the reconciliation policy alone, since no resolutions exist yet; and the round's `version` increments by one. Note that a single source breaching its own tolerance disputes the round even when the grand-total variance is comfortably inside `variance_tolerance_bps`, and that only the breaching sources get records — a source at 64 basis points is left alone while its neighbour at 902 basis points is written up.

A `COMPARED` round is not permanently safe. When a one-time item of the cycle is voided (§3.3) and the resulting recompute pushes at least one per-source variance above `per_source_tolerance_bps`, the round goes `COMPARED → DISPUTED`, which requires that the round's estimates still have `locked` false: one disagreement record is minted per newly breaching source — "newly" meaning a source that carries no `OPEN` and no `RESOLVED` record on this round already, so a source whose disagreement was already documented is never written up twice — `open_disagreement_count` is rewritten as the count of the round's `OPEN` records, `reconciled_total_cents` is recomputed, and the round's `version` increments by one. A recompute that leaves every stored figure unchanged increments nothing, and a recompute never moves a round out of `DISPUTED`: only a resolution does that. Because cascade-minted disagreement records are created without any client request of their own, listing the disagreement records filtered by `round_id` and `status` is the channel through which clients discover them.

### 3.5. Documented Disagreement Resolution and Ratification

A disputed round cannot be ratified while any disagreement is open, and the only way to close one is a documented resolution by the `ForecastDirector`. Each disagreement record already carries the round it belongs to, the `source_id` whose variance breached the tolerance, and the frozen `exec_amount_cents`, `leg_amount_cents` and `variance_bps` from comparison time. Resolving one requires a `resolution_method` and a `rationale`, and optionally a `resolved_amount_cents`.

The four resolution methods are the documented disagreement-resolution rules of the estimating body. `EXEC_VALUE` adopts the executive figure recorded on the record, `LEG_VALUE` adopts the legislative figure, `MIDPOINT` adopts their sum divided by two rounded half up, and `DIRECTOR_OVERRIDE` adopts a figure the director supplies. The three derived methods must **not** carry `resolved_amount_cents` — the server derives the value, and supplying one anyway is rejected with `ERR_RESOLUTION_AMOUNT_NOT_ALLOWED` (HTTP 422). `DIRECTOR_OVERRIDE`, conversely, requires an explicit `resolved_amount_cents` that lies inside the inclusive band bounded below by the lower of `exec_amount_cents` and `leg_amount_cents` and above by the higher of the two; a figure outside that band, on either side, is rejected with `ERR_OVERRIDE_OUT_OF_RANGE` (HTTP 422), while omitting the amount altogether on a `DIRECTOR_OVERRIDE` is the missing-required-field case and reports `ERR_VALIDATION` (HTTP 422). The `rationale` is a written justification of at least 20 characters; anything shorter is rejected with `ERR_RATIONALE_TOO_SHORT` (HTTP 422), while a `rationale` that is absent, null or the empty string is instead the missing-required-field case and reports `ERR_VALIDATION`.

**Segregation of duties.** The director who resolves a disagreement may not be the economist who filed either contested estimate. The server compares the resolver's `X-User-ID` against the `submitted_by_user_id` of both the `EXECUTIVE` and the `LEGISLATIVE` estimate for the disputed source, and a match is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). This check ranks above every constraint check on this operation, so an operator who authored one of the estimates is told about the conflict of interest rather than about a short rationale or an out-of-band override amount. It ranks below the record's own state check, however: a record that is already `RESOLVED` or `VOIDED` is rejected with `ERR_DISAGREEMENT_NOT_OPEN` (HTTP 409) first. In full, this operation's order of evaluation is: the record must be `OPEN`; the resolver must not be either estimate's author; a `DIRECTOR_OVERRIDE` amount must be in band; a derived method must not carry an amount; and the rationale must be long enough.

A successful resolution sets the record's `status` to `RESOLVED`, writes `resolved_amount_cents`, stamps `resolved_by_user_id` with the resolver's `X-User-ID` and `resolved_at` with the logical clock, decreases the round's `open_disagreement_count` by one, recomputes the round's `reconciled_total_cents` with this source's resolved value substituted, and increments both the record's `version` and the round's `version` by one. When the resolution brings `open_disagreement_count` to 0, the round closes the negotiation cycle by moving `DISPUTED → COMPARED`.

**The reconciled total.** A round's `reconciled_total_cents` is the single revenue figure the round stands for, and it is recomputed on entry to `COMPARED`, on entry to `DISPUTED`, on the `DISPUTED → COMPARED` return, and on any estimate recompute while the round is compared. Walk the revenue sources with `status` `ACTIVE` in ascending `created_at` order and pick each source's contribution as follows. If a disagreement record for this round and this source has `status` `RESOLVED`, the contribution is that record's `resolved_amount_cents`, which overrides the cycle's reconciliation policy for that source. Otherwise the cycle's `reconciliation_policy` decides: under `MIDPOINT_AVERAGE`, the contribution is the executive and legislative amounts summed, divided by two and rounded half up, so the reconciled total normally sits between the two submissions; under `LOWER_OF_TWO`, the contribution is simply the lower of the two amounts, with no rounding performed at all, which means the reconciled total can equal neither body's own total when each body is the lower one on a different source. A source that has no `RESOLVED` record and is missing one of the two estimates contributes nothing at all. `reconciled_total_cents` is the sum of the per-source contributions.

**Ratification.** The director ratifies a round to close the negotiation, moving it `COMPARED → RATIFIED`. Ratification requires the round to be `COMPARED` with `open_disagreement_count` equal to 0 — any other combination is rejected with `ERR_ROUND_NOT_COMPARED` (HTTP 409) — and that is the *only* precondition: the round's own state is checked, the owning cycle's status is not, so the cycle is driven to `CONSENSUS_REACHED` from whatever status it happens to hold. Ratifying stamps `ratified_at` with the logical clock, sets `locked` to true on every source estimate of the round, and increments the round's `version` by one. It also bubbles up: the owning cycle moves to `CONSENSUS_REACHED` — in practice always from `IN_CONSENSUS` — records the ratified round's id in `ratified_round_id`, and increments its own `version` by one. `RATIFIED` and `SUPERSEDED` are the two terminal round states; a cycle with a ratified round can no longer be reopened, and no further round can be opened on it.

### 3.6. Certification: Shortfall Sizing and the Deposit Cascade

Certification is the moment a forecast becomes fiscal reality, and it is the single densest cascade in the system. Only a `ForecastDirector` may certify, only from `CONSENSUS_REACHED` — any other status is rejected with `ERR_CYCLE_NOT_CONSENSUS_REACHED` (HTTP 409) — and only when `ratified_round_id` is not null. Certification runs four linked steps plus, on a revision cycle, a fifth branch, and increments the cycle's `version` by one.

**Link one — the certified aggregates and the shortfall.** The cycle copies `certified_total_cents` from the ratified round's `reconciled_total_cents`, reading a null reconciled total as 0, sets `certified_one_time_cents` to the sum of `amount_cents` over the cycle's `ACTIVE` one-time items, derives `certified_recurring_total_cents` by subtracting `certified_one_time_cents` from `certified_total_cents`, and stamps `certified_at` with the logical clock. It then sizes the budget-balancing gap: `shortfall_gap_cents` is `enacted_appropriation_cents` minus `certified_total_cents`, or 0 when the forecast covers the appropriation, whichever is larger — the gap is never negative. `shortfall_pct_bps` is `shortfall_gap_cents` multiplied by 10000, divided by `enacted_appropriation_cents`, and **floored**, so the reported gap is never overstated; it is 0 when `enacted_appropriation_cents` is 0. The statutory threshold that opens the no-vote withdrawal branch is 150 basis points — one and a half per cent of the enacted appropriation — and because the percentage is floored, a gap that computes to 150 basis points exactly qualifies while one that computes to 149 does not.

**Link two — the reserve deposit.** Because `certified_recurring_total_cents` has just been written, every reserve fund is evaluated for a deposit, taken in ascending fund `created_at` order. Each fund's `deposit_rule_variant` decides how "revenue growth above trend" is measured, and the two variants can disagree about whether a deposit is owed at all in a given year.

- Under `GROWTH_ABOVE_TREND`, the measured amount is the cycle's `certified_recurring_total_cents`, and the trend line is the cycle's `prior_recurring_baseline_cents` multiplied by 10000 plus the fund's `trend_growth_rate_bps`, divided by 10000, rounded half up. A fund on this rule deposits on broad-based growth even if every volatile source fell.
- Under `VOLATILE_SOURCE_CAPTURE`, only sources whose `volatility_class` is `HIGH` and whose `status` is `ACTIVE` count, and only their recurring part: the measured amount is the sum, over those sources, of each source's reconciled per-source value from the ratified round — read as 0 when the ratified round produced no reconciled value for that source — minus that source's `ACTIVE` one-time total. The trend line is the summed `base_year_receipts_cents` of the same sources, multiplied by 10000 plus `trend_growth_rate_bps`, divided by 10000, rounded half up once; with no qualifying source at all both the measured amount and the trend line are 0 and no deposit is owed. A fund on this rule can be owed a deposit in a year when the fund on the other rule is owed nothing, and the reverse.

From there both variants share a waterfall. The excess is the measured amount minus the trend line, or 0 when the measured amount is the smaller — growth below trend produces no deposit. `gross_computed_cents` is that excess multiplied by the fund's `capture_rate_bps`, divided by 10000, rounded half up: only the above-trend excess is captured, never the whole revenue level. The statutory ceiling `cap_cents` is the cycle's `certified_total_cents` multiplied by the fund's `cap_pct_bps`, divided by 10000, rounded half up. Headroom is `cap_cents` minus the fund's current `balance_cents`, or 0 when the fund is already at or over its cap. The amount actually deposited is the lower of `gross_computed_cents` and that headroom, and `overflow_returned_cents` is `gross_computed_cents` minus the deposited amount — the portion handed back to the general fund because the reserve is full. A ledger row is minted **only when the deposited amount is greater than zero**, with `origin` `CERTIFICATION_DEPOSIT`, `signed_amount_cents` equal to the positive deposited amount, `source_cycle_id` pointing at the certifying cycle, and both `gross_computed_cents` and `overflow_returned_cents` recorded on the row; its `memo` is generated by the server, since no operator authored it. The fund's `balance_cents` rises by `signed_amount_cents` and `last_transaction_at` becomes the new row's `created_at`.

One further rebasing happens here. On the **first** certification of a given `fiscal_year` — first meaning that no *other* cycle of the same `fiscal_year` yet carries a non-null `certified_at`, a test made before this cycle stamps its own, and one that a `SUPERSEDED` predecessor of the same year still satisfies against — after the deposit has been applied, every reserve fund's `fy_opening_balance_cents` is set to its post-deposit `balance_cents` and its `fy_withdrawn_cents` is reset to 0. That rebased opening balance is the base against which the fiscal-year withdrawal cap is measured for the rest of the year: once rebased it stays pinned at that figure for as long as the logical clock remains inside that fiscal year, no longer re-derived from the rows that precede the year's start, and `fy_withdrawn_cents` thereafter counts only the `WITHDRAWAL` rows minted after the rebasing moment.

**Link three — adequacy and posture.** Because `balance_cents` changed, the fund's entire adequacy disclosure is re-derived by the procedure in §3.7 — `cap_cents`, `volatility_index_bps`, `target_pct_bps`, `required_reserve_cents`, `coverage_ratio_bps`, `adequacy_band`, `cushion_credit_bps` and `disclosed_target_pct_bps` are all rewritten — using the *certifying* cycle as the reference cycle rather than re-running §3.7's greatest-`certified_at` selection, `deposit_posture` is re-evaluated and lands on `AT_CAP` when `cap_cents` is not null and `balance_cents` has reached or passed it and on `ACCEPTING` otherwise, and the fund's `version` increments by one. Links two and three run for every fund on every certification, so a fund owed no deposit at all still has its disclosure rewritten and its `version` incremented.

**Link four — the briefings go stale.** Because the fund's balance moved, every rating-agency briefing of that fund whose `status` is `PUBLISHED` becomes `STALE` with `stale_reason` `RESERVE_BALANCE_CHANGED`, each such briefing's `version` incrementing by one. This link is the one that is conditional: it fires only for a fund whose certification deposit actually minted a ledger row, so a fund owed nothing leaves its published briefings alone even though its disclosure was rewritten.

**The revision branch.** When the certifying cycle's `cycle_type` is `REVISION`, the cycle named by its `supersedes_cycle_id` moves `CERTIFIED → SUPERSEDED` — legal only when that predecessor is in `CERTIFIED` status and carries the same `fiscal_year` — its `version` increments by one, and that supersession in turn marks every `PUBLISHED` briefing *of the predecessor cycle* `STALE`, this time with `stale_reason` `CYCLE_SUPERSEDED`. `SUPERSEDED` is the terminal state of a forecast cycle.

### 3.7. Reserve Fund Custody: Manual Movements, Reversals and Adequacy

A `ForecastDirector` creates a **reserve fund** — a budget stabilization account and its statutory parameters — with a `name`, a `cap_pct_bps` (greater than 0 and at most 10000) expressing the statutory ceiling as basis points of the latest certified all-funds total, a `trend_growth_rate_bps` (at least 0) used by both deposit variants, a `capture_rate_bps` (greater than 0 and at most 10000) giving the share of above-trend revenue captured, a `deposit_rule_variant` of `GROWTH_ABOVE_TREND` or `VOLATILE_SOURCE_CAPTURE`, an `eligible_seats` count greater than 0 that is the base of both ballot requirements, an `annual_withdrawal_cap_pct_bps` (greater than 0 and at most 10000) ceiling on total withdrawals in one fiscal year, a `cooling_off_days` window length of at least 0 days, and an `opening_balance_cents` of at least 0. At creation, `balance_cents` and `fy_opening_balance_cents` both equal `opening_balance_cents`, `fy_withdrawn_cents` is 0, `deposit_posture` is `ACCEPTING`, and the adequacy figures stay at their initial values — `cap_cents` and `required_reserve_cents` null, `volatility_index_bps` 0, `target_pct_bps` and `disclosed_target_pct_bps` 500, `coverage_ratio_bps` 0, `cushion_credit_bps` 0 and `adequacy_band` `INSUFFICIENT` — until a cycle is certified or adequacy is recomputed.

Three derived balance figures deserve exact definitions. `balance_cents` is `opening_balance_cents` plus the sum of `signed_amount_cents` over every ledger row of the fund. `fy_opening_balance_cents` is `opening_balance_cents` plus the sum of `signed_amount_cents` over the fund's rows created strictly before the start of the fiscal year that contains the logical clock, and is rebased by the first certification of a fiscal year as described in §3.6. `fy_withdrawn_cents` is the absolute value of the summed `signed_amount_cents` of the fund's `WITHDRAWAL` rows created within the current fiscal year, net of any reversal rows that reverse them. Two further timestamps drive later rules: `cooling_off_until` is the `created_at` of the most recent non-reversed `WITHDRAWAL` row plus `cooling_off_days`, and is null when no such row exists; `last_transaction_at` is the `created_at` of the fund's most recent ledger row of any kind, and it anchors the rating-briefing blackout window.

**Manual deposits.** A `ReserveTreasurer` may post money into a fund directly, supplying `amount_cents` (greater than zero) and a `memo`. The posting mints a ledger row with `origin` `MANUAL_DEPOSIT`, `signed_amount_cents` equal to the positive `amount_cents`, `gross_computed_cents` equal to the same amount, `overflow_returned_cents` 0, `memo` as supplied, and `source_cycle_id` and `reverses_transaction_id` null; that minted row, not the fund, is the resource returned in `data`. The fund's `balance_cents` rises by that amount, `last_transaction_at` becomes the row's `created_at`, the adequacy disclosure is re-derived, `deposit_posture` may flip `ACCEPTING → AT_CAP`, every `PUBLISHED` briefing of the fund goes `STALE` with `stale_reason` `RESERVE_BALANCE_CHANGED`, and the fund's `version` increments by one. Two guards apply and their order matters. First, the fund's `deposit_posture` must be `ACCEPTING`; a deposit into a fund already at its cap is rejected with `ERR_FUND_AT_CAP` (HTTP 409). Second — and this is where a manual deposit differs sharply from a certification deposit — the amount may not exceed the fund's remaining headroom, that is `cap_cents` minus `balance_cents` or 0 when the balance already reaches the cap; an oversized manual deposit is rejected outright with `ERR_DEPOSIT_EXCEEDS_CAP` (HTTP 422) rather than being trimmed to the cap with an overflow return the way a certification deposit is. This second guard has no force while `cap_cents` is null — a fund that has never seen a certification has no statutory ceiling to test against, so a deposit of any size is accepted.

**Reversals.** Any ledger row may be compensated by an equal and opposite row. A `ReserveTreasurer` reverses a row by supplying a `rationale` of at least 20 characters, and the server mints a new row with `origin` `REVERSAL`, `signed_amount_cents` equal to the exact negation of the original row's amount, `reverses_transaction_id` pointing at the original, the supplied `rationale` persisted as the new row's `memo`, `gross_computed_cents` and `overflow_returned_cents` null, and `source_cycle_id` null; as with a manual deposit, the minted row is the resource returned in `data`. A `rationale` that is absent or not a string is a shape failure reported as `ERR_VALIDATION`, while a present but too-short string is the separate `ERR_RATIONALE_TOO_SHORT`. Reversing a deposit lowers `balance_cents`; reversing a withdrawal restores it and reduces `fy_withdrawn_cents` by the original amount, releasing that much fiscal-year headroom. In every case the adequacy disclosure is re-derived, `deposit_posture` may flip in either direction, `last_transaction_at` becomes the reversal's `created_at`, every `PUBLISHED` briefing of the fund goes `STALE` with `stale_reason` `RESERVE_BALANCE_CHANGED`, and the fund's `version` increments by one. Only a row whose `origin` is `CERTIFICATION_DEPOSIT`, `MANUAL_DEPOSIT` or `WITHDRAWAL` may be reversed, and only once: reversing a reversal, or reversing a row that already has a reversal pointing at it, is rejected with `ERR_TRANSACTION_ALREADY_REVERSED` (HTTP 409). That state check comes first, the rationale length check second, and the fiscal check last — a reversal that would drive `balance_cents` below zero is rejected with `ERR_REVERSAL_WOULD_OVERDRAW` (HTTP 422). Because ledger rows are immutable audit records, they carry only `id` and `created_at`; there is no `updated_at` and no `version` on a ledger row.

**Deposit posture.** `deposit_posture` is a two-state machine on the fund. It flips `ACCEPTING → AT_CAP` on any balance increase — a certification deposit, a manual deposit, or the reversal of a withdrawal — when `cap_cents` is not null and `balance_cents` reaches or passes `cap_cents` after the increase, and while `AT_CAP` further manual deposits are refused with `ERR_FUND_AT_CAP`. It flips `AT_CAP → ACCEPTING` on any balance decrease (a withdrawal execution or the reversal of a deposit) or on a new certification that raises `cap_cents`, whenever `cap_cents` is null or `balance_cents` is strictly below `cap_cents` after the change. Each flip increments the fund's `version` by one.

**The adequacy disclosure.** The figures the state shows its rating agencies are derived in a fixed eight-step order from the fund's balance, the certified recurring revenue base, and the measured forecast volatility of the revenue portfolio. The reference cycle for steps three and eight is the forecast cycle whose `status` is `CERTIFIED` with the greatest `certified_at`, ties broken by the earliest `created_at`; while no cycle is certified, `required_reserve_cents` and `cap_cents` are null and no cap is enforced.

1. `volatility_index_bps` — for every revenue source with `status` `ACTIVE`, multiply its `mape_bps` by its `base_year_receipts_cents`; sum those products, divide by the summed `base_year_receipts_cents` of the same sources, and round half up. This is a receipts-weighted mean, so a large, accurately forecast source dilutes the index — and a source that has never had an actual posted against it carries `mape_bps` 0 and therefore dilutes it too.
2. `target_pct_bps` — the statutory target band, selected by inclusive upper bounds: 500 basis points (five per cent of recurring revenue) when `volatility_index_bps` is at most 300, otherwise 800 basis points when it is at most 800, otherwise 1200 basis points.
3. `required_reserve_cents` — the reference cycle's `certified_recurring_total_cents` multiplied by `target_pct_bps`, divided by 10000, rounded half up.
4. `coverage_ratio_bps` — `balance_cents` multiplied by 10000, divided by `required_reserve_cents`, and **floored** so coverage is never overstated; it is 0 when `required_reserve_cents` is 0.
5. `adequacy_band` — `STRONG` when `coverage_ratio_bps` is at least 10000 (the fund fully covers its requirement), `ADEQUATE` when it is at least 6000, `THIN` when it is at least 3000, and `INSUFFICIENT` below that.
6. `cushion_credit_bps` — 200 basis points when `adequacy_band` is `STRONG`, and 0 in every other band.
7. `disclosed_target_pct_bps` — `target_pct_bps` minus `cushion_credit_bps`. This is a disclosure figure only and is **never** fed back into step three, so a strong fund never becomes non-strong on the strength of its own cushion credit.
8. `cap_cents` — the reference cycle's `certified_total_cents` multiplied by the fund's `cap_pct_bps`, divided by 10000, rounded half up.

This derivation runs automatically after any change to `balance_cents` and on certification. It can also be run on demand by a `ForecastDirector` or a `ReserveTreasurer`: an explicit recompute rewrites `volatility_index_bps`, `target_pct_bps`, `required_reserve_cents`, `coverage_ratio_bps`, `adequacy_band`, `cushion_credit_bps`, `disclosed_target_pct_bps` and `cap_cents`, re-evaluates `deposit_posture` against the recomputed `cap_cents`, and increments the fund's `version` by one — unconditionally, even when every recomputed figure lands on the value it already held. It resolves the reference cycle by the `CERTIFIED`-only rule above, leaves the ledger-derived figures (`balance_cents`, the fiscal-year figures, `cooling_off_until`, `last_transaction_at`) untouched, and returns the fund itself. That recompute is the operator action that propagates a methodology finding — a rise in some source's `mape_bps` — into the fund's statutory target band. A read-only companion view reports the same disclosure without persisting anything, naming the `fund_id` it was asked about and the `reference_cycle_id` it used together with `volatility_index_bps`, `target_pct_bps`, `required_reserve_cents`, `coverage_ratio_bps`, `adequacy_band`, `cushion_credit_bps`, `disclosed_target_pct_bps`, `cap_cents`, the deposit `headroom_cents` left under the cap — `cap_cents` minus `balance_cents` floored at 0, and null whenever `cap_cents` is null — and the withdrawal room left this fiscal year as `annual_withdrawal_cap_cents` and `cap_headroom_cents`.

### 3.8. Authorising and Executing a Reserve Withdrawal

Drawing on a reserve is deliberately hard, and the statute offers exactly two doors. A withdrawal request is drafted by a `ReserveTreasurer` or a `ForecastDirector` against a `fund_id` and a `cycle_id`, with a `requested_amount_cents` greater than zero, a `justification_type` declaring which door the request intends to take, a `deadline_date` after which an approved authorisation may no longer be executed, and the `expected_fund_version` pin from §2.7. The justifying cycle must be in `CERTIFIED` status; a request naming a cycle in any other status is rejected with `ERR_CYCLE_NOT_CERTIFIED` (HTTP 409), a check that sits below the version pin, so a stale `expected_fund_version` is reported first. A drafted request starts in `DRAFT` with `requested_by_user_id` taken from the drafter's `X-User-ID`, `votes_required`, `quorum_required`, `yes_votes`, `no_votes`, `abstain_votes` and `authorized_amount_cents` all 0, `approval_basis` and `vote_closes_at` null. Creating a draft also **rejects any other request on the same fund that is still in `DRAFT`**, moving each to `REJECTED` with `authorized_amount_cents` 0 and `approval_basis` left null and incrementing each one's `version` by one, and it increments the fund's own `version` by one even though no money has moved — which is exactly why the next drafter's pin must be fresh.

Both approval branches require the request to be in `DRAFT`, otherwise `ERR_REQUEST_NOT_DRAFT` (HTTP 409), and both require the branch to match the request's declared `justification_type`, otherwise `ERR_JUSTIFICATION_MISMATCH` (HTTP 422): a request declaring `SHORTFALL_TRIGGER` may only be verified, and one declaring `SUPERMAJORITY_VOTE` may only be voted.

**Branch A — the shortfall trigger.** A `ReserveTreasurer` verifies the shortfall, which moves the request `DRAFT → APPROVED` in one step and with no ballot at all. Verification requires the justifying cycle to be `CERTIFIED` and its `shortfall_pct_bps` to be at least 150; a cycle whose floored shortfall percentage is below that threshold is rejected with `ERR_SHORTFALL_NOT_TRIGGERED` (HTTP 422), and the certified-status check for this operation sits below the shortfall check in the ladder — so an uncertified cycle, whose `shortfall_pct_bps` is still null, reports `ERR_SHORTFALL_NOT_TRIGGERED` rather than `ERR_CYCLE_NOT_CERTIFIED`, a null percentage counting as not triggered. On success `approval_basis` becomes `SHORTFALL_TRIGGER`, `authorized_amount_cents` becomes the lower of `requested_amount_cents` and the cycle's `shortfall_gap_cents` — the authorisation can never exceed the certified gap it is justified by — and the request's `version` increments by one. Nothing about the ballot is touched: `votes_required` and `quorum_required` stay 0, `yes_votes`, `no_votes` and `abstain_votes` stay 0, and `vote_closes_at` stays null. This branch's side-effect set is disjoint from branch B's.

**Branch B — the supermajority vote.** A `ForecastDirector` opens a ballot instead, moving the request `DRAFT → VOTE_OPEN`. Opening the ballot re-examines only the request's own `status` and `justification_type`; it re-checks nothing about the justifying cycle, so a cycle that has since been superseded does not block the ballot. Opening the ballot freezes both seat requirements from the fund's `eligible_seats`: `votes_required` is two thirds of the eligible seats rounded up to a whole seat, and `quorum_required` is one half of the eligible seats rounded up to a whole seat — with eleven eligible seats, eight yes votes are required and six ballots constitute a quorum. `vote_closes_at` is set to the logical clock plus seven days, and the request's `version` increments by one.

Each `LegislativeVoter` then casts one ballot, supplying `vote` as `YES`, `NO` or `ABSTAIN`; `request_id` comes from the path and `voter_user_id` from the voter's `X-User-ID`, and `cast_at` is stamped from the logical clock. Casting increments the request's matching tally — `yes_votes`, `no_votes` or `abstain_votes` — and increments the request's `version` by one. A ballot may only be cast while the request is `VOTE_OPEN`, otherwise `ERR_VOTE_NOT_OPEN` (HTTP 409), and a voter may cast at most one ballot per request: a second ballot from the same `voter_user_id` is rejected with `ERR_DUPLICATE_VOTE` (HTTP 409), with the state check ranking above the duplicate check. An `ABSTAIN` ballot counts toward quorum but never toward the supermajority numerator. Like ledger rows, ballots are immutable audit records carrying only `id` and `created_at` — no `updated_at`, no `version`.

The director closes the ballot, and closing is where the two outcomes fork. Closing requires the request to be `VOTE_OPEN` (otherwise `ERR_VOTE_NOT_OPEN`) and requires either that the logical clock has reached `vote_closes_at` or that every eligible seat has cast a ballot — meaning the summed `yes_votes`, `no_votes` and `abstain_votes` is exactly equal to the fund's current `eligible_seats`; closing early with seats still silent is rejected with `ERR_VOTE_STILL_OPEN` (HTTP 409). Only then is the tally examined, and in a fixed order: total ballots cast must reach `quorum_required`, otherwise `ERR_QUORUM_NOT_MET` (HTTP 422); and only after quorum passes are the yes votes compared against `votes_required`, a shortfall there yielding `ERR_SUPERMAJORITY_NOT_MET` (HTTP 422). Both of those tally failures are errors and nothing else: the request is left exactly as it was, still `VOTE_OPEN` with its tallies, `approval_basis`, `authorized_amount_cents` and `version` unchanged, so the director may close again later once more ballots land or the window expires. With eleven seats, eight yes and three no votes approve; eight yes, one no and two abstentions across all eleven seats also approve; seven yes and four no with all eleven cast meets quorum but fails the supermajority; and four yes with one no and only five ballots cast fails quorum before the yes count is ever considered.

On approval the request moves `VOTE_OPEN → APPROVED` with `approval_basis` `SUPERMAJORITY_VOTE`, and its `authorized_amount_cents` becomes the lower of `requested_amount_cents` and the remaining fiscal-year cap headroom — never the shortfall gap, which is branch A's ceiling alone. That headroom is computed by taking the fund's `fy_opening_balance_cents`, multiplying by `annual_withdrawal_cap_pct_bps`, dividing by 10000 and rounding half up to obtain the fiscal year's withdrawal cap, then subtracting `fy_withdrawn_cents`, with a negative result treated as 0. A fund whose fiscal-year opening balance is 71,958,137 cents and whose `annual_withdrawal_cap_pct_bps` is 3000 has a cap of 21,587,441 cents for the year, so a request for 30,000,000 cents with nothing yet drawn is authorised at 21,587,441 cents, and a request for 10,000,000 cents after 15,000,000 cents has already been drawn is authorised at 6,587,441 cents. Approval increments the request's `version` by one. A failed ballot never moves the request to `REJECTED` of its own accord — `REJECTED` is reached only by the supersession rule above, when a fresh draft on the same fund rejects a request still sitting in `DRAFT`.

**Execution.** A `ReserveTreasurer` executes an approved request, moving it `APPROVED → EXECUTED`. Five conditions guard the execution, and they are checked in this order: the request's `status` must be `APPROVED` or `LAPSED` — every other status is refused with `ERR_REQUEST_NOT_APPROVED` (HTTP 409), the `LAPSED` case being deliberately admitted at this rung so that it falls through to its own error at the next one; a request the clock drove to `LAPSED` past its `deadline_date` is then refused with `ERR_AUTHORIZATION_LAPSED` (HTTP 409); the fund's cooling-off window must have elapsed, meaning `cooling_off_until` is null or the logical clock is strictly past it, otherwise `ERR_COOLING_OFF_ACTIVE` (HTTP 409); the executing treasurer must not be the request's `requested_by_user_id`, otherwise `ERR_EXECUTOR_IS_REQUESTER` (HTTP 403); `fy_withdrawn_cents` plus `authorized_amount_cents` must not exceed the fiscal-year withdrawal cap computed as above, otherwise `ERR_ANNUAL_CAP_EXCEEDED` (HTTP 422); and `authorized_amount_cents` must not exceed the fund's current `balance_cents`, otherwise `ERR_INSUFFICIENT_RESERVE_BALANCE` (HTTP 422). The date component of the logical clock must also be on or before `deadline_date`, and that test is folded into the second rung: an `APPROVED` request whose deadline the clock has already passed — but which no clock advance has yet re-examined — is refused with the same `ERR_AUTHORIZATION_LAPSED`, without its stored `status` being rewritten.

A successful execution runs its own four-link cascade. `executed_at` is stamped from the logical clock and a ledger row is minted with `origin` `WITHDRAWAL`, `signed_amount_cents` equal to the negation of `authorized_amount_cents`, and `source_cycle_id` set to the request's `cycle_id`; `executed_transaction_id` points at that row. Because the row exists, the fund's `balance_cents` falls by `authorized_amount_cents`, `fy_withdrawn_cents` rises by the same amount, `cooling_off_until` becomes the new row's `created_at` plus `cooling_off_days`, `last_transaction_at` becomes the row's `created_at`, and the fund's `version` increments by one. Because the balance changed, the adequacy disclosure is re-derived — `coverage_ratio_bps`, `adequacy_band`, `cushion_credit_bps` and `disclosed_target_pct_bps` all move with it — and `deposit_posture` flips `AT_CAP → ACCEPTING` when `balance_cents` now sits below `cap_cents`. And because the fund's balance changed, every `PUBLISHED` briefing of that fund becomes `STALE` with `stale_reason` `RESERVE_BALANCE_CHANGED`. The request's own `version` increments by one.

**Lapsing.** An authorisation is not open-ended. When the logical clock is advanced past a request's `deadline_date`, that request moves `APPROVED → LAPSED`; `authorized_amount_cents` stays exactly as approved for the audit trail, no ledger row is minted, and the request's `version` increments by one. `EXECUTED`, `REJECTED` and `LAPSED` are the three terminal states of a withdrawal request.

### 3.9. Forecast Error Analysis and Rating-Agency Communication

Once a fiscal year has closed, its audited receipts are posted back against the forecast that was certified for it, and that comparison is what drives methodology improvement. A `ForecastDirector` or an `ExecutiveEconomist` posts an **actual collection** naming the `source_id`, the `fiscal_year` the receipts belong to, and the audited `actual_amount_cents` (at least 0). Posting is only allowed once the fiscal year has actually closed — the date of the logical clock must be strictly after 30 June of that fiscal year, and an early posting is rejected with `ERR_FISCAL_YEAR_NOT_CLOSED` (HTTP 409). At most one actual collection may exist per source and fiscal year; a second is rejected with `ERR_DUPLICATE_ACTUAL` (HTTP 409). A posting against a `RETIRED` source is rejected with `ERR_SOURCE_RETIRED`, and among these checks the fiscal-year-closed rule is evaluated first, then the retired-source rule, then the forecast-matching rule below, and the duplicate rule last.

**Matching and scoring.** The server first selects the forecast to score against: among forecast cycles with the same `fiscal_year` whose `status` is `CERTIFIED` or `SUPERSEDED`, it takes the one with the greatest `certified_at`, breaking ties by the earliest `created_at`, and records it as `matched_cycle_id`. When no such cycle exists the posting is rejected with `ERR_NO_CERTIFIED_FORECAST` (HTTP 422). `matched_forecast_cents` is then the per-source reconciled value that the matched cycle's ratified round produced for this source — the same per-source figure §3.5 builds the reconciled total from — and the same `ERR_NO_CERTIFIED_FORECAST` answers a matched cycle that yields no such figure at all, whether because it holds no `ratified_round_id` or because its ratified round never carried an estimate for this source. `abs_pct_error_bps` is the absolute difference between `actual_amount_cents` and `matched_forecast_cents`, multiplied by 10000, divided by `matched_forecast_cents`, rounded half up; a matched forecast of exactly 0 yields `abs_pct_error_bps` 0 rather than a division failure, however large the actual. `error_direction` records the sign of the miss relative to the forecast: `OVER_FORECAST` when the actual came in *below* the forecast, `UNDER_FORECAST` when it came in above, and `EXACT` when the two are equal.

**The rolling window and the methodology flag.** Posting also increments the source's `posted_actual_count` by one and rerolls its accuracy record. Take the source's actual collections ordered by `fiscal_year` descending and keep at most the three most recent years; `mape_bps` is the sum of those rows' `abs_pct_error_bps` divided by the number of rows actually in the window — not by three — rounded half up. A fourth, older posting never re-enters the window. `methodology_flag` is set true when `mape_bps` reaches 500 basis points (a five per cent mean absolute error) and false below that; a flagged source is marked for methodology improvement review, and its elevated `mape_bps` also raises the receipts-weighted `volatility_index_bps` that drives every fund's statutory target band once adequacy is recomputed. The posting increments the source's `version` by one. A read-only companion view exposes the same window for one source, reporting `window_fiscal_years`, `window_error_bps`, `window_count`, `mape_bps`, `methodology_flag` and `posted_actual_count`.

Alongside it, a second read-only view previews one source's numbers under a cycle's scenario weights before anything is filed: given a `source_id` — a mandatory query parameter, whose absence or emptiness is an `ERR_VALIDATION` shape failure resolved before the source itself is looked up — it runs the scenario-weighted blend and the policy phase-in without persisting anything, and returns the echoed `source_id` together with `weighted_scenario_cents`, `policy_adjustment_cents`, `one_time_cents`, `recurring_component_cents` and `estimate_amount_cents` for that source. Because no estimate exists yet, there is no judgmental adjustment to carry: the previewed `recurring_component_cents` is `weighted_scenario_cents` plus `policy_adjustment_cents` alone, and `estimate_amount_cents` adds `one_time_cents` to that.

**Briefing the rating agencies.** A `ForecastDirector` or a `RatingAnalyst` drafts a **rating-agency briefing** naming the `fund_id` whose adequacy is being communicated, the `cycle_id` of the forecast cycle the briefing narrates, and a `narrative` of at least 20 characters written for analysts. Any cycle may be named — a briefing drafted against a cycle that is still in consensus is perfectly legal; it simply carries whatever adequacy snapshot the fund holds at drafting time. That snapshot is taken automatically: `snapshot_fund_version` records the fund's `version` at creation, `snapshot_adequacy_band` its `adequacy_band`, and `snapshot_coverage_ratio_bps` its `coverage_ratio_bps`. A briefing starts in `DRAFT`, with `published_at`, `stale_reason` and `retracted_at` null. Its `narrative` may be edited in any status but `RETRACTED` — a `DRAFT`, a live `PUBLISHED` and a `STALE` briefing are all editable, the edit rewriting the narrative and incrementing the `version` by one while leaving `status`, `published_at`, `stale_reason` and the three snapshot fields exactly as they were; only a `RETRACTED` briefing refuses the edit, with `ERR_BRIEFING_TERMINAL` (HTTP 409), and even that refusal ranks below the shape check, so a narrative shorter than 20 characters is reported as `ERR_VALIDATION` regardless of the briefing's status.

Publication is the `ForecastDirector`'s alone and moves a briefing to `PUBLISHED` from either `DRAFT` or `STALE`. Three conditions apply, in this order. The briefing must be in `DRAFT` or `STALE`; anything else, including a briefing already `PUBLISHED`, is rejected with `ERR_BRIEFING_NOT_PUBLISHABLE` (HTTP 409), and the separate rule that no transition may be attempted on a `RETRACTED` briefing — `ERR_BRIEFING_TERMINAL` (HTTP 409) — ranks immediately below it. Next comes the blackout window: a briefing may only be published once the logical clock has reached the fund's `last_transaction_at` plus 48 hours, so that analysts never receive a disclosure minted in the immediate wake of a ledger movement; publication inside that window is rejected with `ERR_BRIEFING_COOLING_PERIOD` (HTTP 409), and a fund with a null `last_transaction_at` imposes no blackout at all. Last comes the snapshot check: `snapshot_fund_version` must still equal the fund's live `version` unless the request sets the optional `refresh_snapshot` flag to true, and a behind-the-fund snapshot published without that flag is rejected with `ERR_ADEQUACY_STALE` (HTTP 409).

When `refresh_snapshot` is true, all three snapshot fields — `snapshot_fund_version`, `snapshot_adequacy_band` and `snapshot_coverage_ratio_bps` — are re-read from the live fund *before* publication, so the published briefing always describes a state that existed. Publication then sets `published_at` to the logical clock, clears `stale_reason` back to null, and increments the briefing's `version` by one. A briefing that has gone `STALE` can only return to `PUBLISHED` with `refresh_snapshot` true: republishing a stale briefing on its old snapshot is never permitted, and the 48-hour blackout applies to that republication exactly as it does to a first publication. This is the republication cycle `PUBLISHED → STALE → PUBLISHED`, and its `STALE` leg is entered by the server alone, whenever the briefed fund's balance changes (`stale_reason` `RESERVE_BALANCE_CHANGED`) or the briefed cycle is superseded (`stale_reason` `CYCLE_SUPERSEDED`), each such staling incrementing the briefing's `version` by one.

Finally, the director may pull a briefing out of circulation from `DRAFT`, from `PUBLISHED` or from `STALE`, which stamps `retracted_at` with the logical clock, moves the briefing to `RETRACTED` and increments its `version` by one. `RETRACTED` is terminal: nothing further may be done with the briefing, and any attempt is met with `ERR_BRIEFING_TERMINAL`.

## 4. Endpoint Definitions

Operations that mint a new resource — a forecast cycle, a scenario, a revenue source, a policy adjustment, a one-time item, a negotiation round, a source estimate, a reserve fund, a ledger row (manual deposit or reversal), a withdrawal request, a ballot, an actual collection or a briefing — return `201 Created`. Operations that modify an existing resource, drive a state transition, or return a computed view return `200 OK`. The two deletions return `204 No Content` with no body. Every collection in this API hangs off the API root, so a resource created through a sub-resource path is still addressed afterwards by its own root-level collection path.
