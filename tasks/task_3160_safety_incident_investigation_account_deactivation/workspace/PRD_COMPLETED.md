# Safety Incident Investigation & Account Deactivation API — Product Requirements Document

## 1. Introduction

Riders, drivers and third parties report safety incidents on this platform every day, and each report carries a legal, contractual and human weight that the platform cannot defer. A single mis-clssified report can leave an aggressive rider on the road, while an over-broad interim hold can strand a driver's income for weeks. This API exists to make that triage defensible: every report is classified, investigated, evidenced, decided and — where the law requires it — reported to a regulator, with a complete audit trail behind each step. The system is mounted under `/safety`, and every operation on it carries the acting operator's identity in mandatory request headers so that no anonymous decision can ever enter the record.

The domain is deliberately adversarial. Accounts share handsets and device farms, so risk crosses account boundaries through `AccountDeviceLink` rows and the `DeviceCluster` aggregates built on them. Deactivation is not a single event but a graduated outcome — `WARNING`, `RESTRICTED` or `DEACTIVATED` — whose severity depends on the incident category, the evidence gathered, the account's history and the region's policy. Appeals are heard by a separate team that must never be the team that decided, mandatory reports must be filed within windows the regions control, and every one of those rules is evaluated against a logical clock supplied by the test surface rather than the host machine's wall clock. The server's startup default logical time is `2026-09-01T00:00:00Z` and it must never fall back to real time before that clock is explicitly set.

## 2. Global Specifications & System-Wide Principles

The subsections below define the invariants that hold across the whole API. Where a rule belongs to one workflow only, it lives in §3 next to the narrative that motivates it.

### 2.1. User and Role-Based Access Control

Every request must carry `X-User-ID` and `X-User-Role`. A request that omits either header is rejected with `ERR_UNAUTHENTICATED` (`401`) before any resource work begins, and that check runs ahead of everything else in the request pipeline. A request whose `X-User-Role` names a role that is not permitted for the operation — including a role string the platform does not recognise at all, which is treated as an authorisation failure rather than an authentication failure — is rejected with `ERR_UNAUTHORIZED` (`403`).

The platform recognises eight roles, spelled exactly as follows: `PlatformAdmin`, `SafetyInvestigator`, `SafetyAppealReviewer`, `SafetyOperationsLead`, `RegulatorLiaison`, `BackgroundReviewer`, `Rider` and `Driver`.

When `X-User-Role` is `Rider`, `X-User-ID` is the `id` of the acting `Account`; ownership checks on any resource that references an `Account` compare the resource's foreign-key field to `X-User-ID`. The same is true when `X-User-Role` is `Driver`. When `X-User-Role` is `PlatformAdmin`, `SafetyInvestigator`, `SafetyAppealReviewer`, `SafetyOperationsLead`, `RegulatorLiaison` or `BackgroundReviewer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — for example as `decision_maker_user_id` on a `SafetyIncident` or as `appeal_reviewer_user_id` — but it does not compare it to any entity's `id`.

Two roles carry a separation-of-duties obligation that the server enforces at runtime. A `SafetyAppealReviewer` may never be the same operator who committed the decision being appealed, and `SafetyInvestigator` and `SafetyAppealReviewer` therefore hold disjoint exclusive operations across the decision and appeal surfaces.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` query parameter that caps the number of items returned, defaulting to 10 when omitted, with a minimum of 1 and a maximum of 100. A `limit` outside that band is clamped to the nearer bound rather than refused, and a non-numeric `limit` falls back to the default. The `offset` query parameter skips that many leading items and defaults to 0, a negative `offset` falling back to 0 as well. Only the endpoints that actually return a collection honour these two parameters; they are listed in §4 with a `?` suffix on the ones that may be omitted.

Unless a listing endpoint says otherwise, results are ordered by the resource's `created_at` timestamp in ascending order, with ties on `created_at` broken by the resource's `id` ascending so the order is total.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope described in §2.2.

### 2.4. Account Safety Posture and Contagion Propagation

Each `Account` maintains a derived **safety posture** in the `safety_posture` field, one of `OPEN`, `RESTRICTED` or `FROZEN`, which gates every operation performed on that account's children. The posture is recomputed after every incident and enforcement mutation. It reads `FROZEN` whenever the account's `status` is `APPEAL_PENDING`; otherwise it reads `RESTRICTED` when the account's `status` is `RESTRICTED` or when `standing_enforcement_count` is at least 1; and it reads `OPEN` in every other case.

Risk is not confined to the offending account. The `risk_score` field on an `Account` is a **0 to 1000 clamped** contagion projection recomputed by the risk-propagation rule. The projection begins with an **incident term**, built from the account's `SafetyIncident` rows whose `incident_status` is `OPEN`, `INVESTIGATING`, `PENDING_DECISION`, `MANDATORY_REPORTED_BLOCKED` or `DECIDED` and whose `severity` is `S2`, `S3` or `S4` — with the single carve-out that a `DECIDED` row whose `decision_category` is `WARNING` is excluded from the sum. Each qualifying incident contributes a base weight — 20 for `S1`, 60 for `S2`, 140 for `S3` and 260 for `S4` — multiplied by a decay factor and by the incident's `cluster_risk_multiplier_pct` divided by 100; an incident whose frozen multiplier is absent falls back to the 100 floor. The decay factor is 1.00 while the incident is **strictly less than 90 days** old, 0.50 once it is **strictly less than 180 days** old, and 0.00 from 180 days onward; at exactly 90 days the factor is still 1.00, so a single `S3` incident contributes 140.00 rather than 70.00 at that instant.

The projection adds an **enforcement term** of 180 for every `EnforcementAction` belonging to the account whose `enforcement_status` is `ACTIVE`, `MANDATORY_REPORTED` or `APPEAL_PENDING`. It then adds a **cluster term** equal to the resolved cluster's `aggregate_cluster_risk` multiplied by 0.25. The cluster is resolved by deduplicating the account's `AccountDeviceLink` rows by `device_cluster_id`, keeping for each cluster the row with the greatest `last_seen_at` (ties broken by `created_at` ascending), and then selecting, among the surviving rows whose `link_status` is `LINKED` or `DORMANT`, the one with the greatest `last_seen_at`, again with ties broken by `created_at` ascending; when no such row exists the cluster term is zero. The three terms are summed, rounded once to two decimal places using round-half-up, and finally clamped between 0 and 1000.

Two ancillary adjustments move the score outside the propagation rule. A `CLEAR` background-check adjudication subtracts 15 from the account's `risk_score`, floored at 0, while an `INCONCLUSIVE` adjudication adds 30; both act on the account's already-propagated score and leave the account's incident and enforcement terms — and therefore each cluster aggregate it contributes to — unchanged. Completing a trip subtracts 2 from the `risk_score` of both the rider and the driver account, floored at 0, likewise applied on top of the freshly propagated score.

The `risk_tier` field bands the resulting score into `TIER_LOW`, `TIER_ELEVATED`, `TIER_HIGH` or `TIER_SEVERE`. A score of **640 or more** is `TIER_SEVERE`; otherwise **420 or more** is `TIER_HIGH`; otherwise **210 or more** is `TIER_ELEVATED`; otherwise `TIER_LOW`. A **severity escape hatch** overrides the bands: when the account's maximum `S3`/`S4` incident severity level is at least 3, the account has **no** `S3`/`S4` incident still sitting in `OPEN`, `INVESTIGATING`, `PENDING_DECISION` or `MANDATORY_REPORTED_BLOCKED`, and the projected score is below 400, the account is promoted to `TIER_SEVERE` regardless of the score.

### 2.5. Evidence Admissibility and the Frozen Decision Snapshot

An incident's evidentiary weight is summarised by the **evidence admissibility score**, described in full in §3.4, and the four fields that snapshot it — `decision_evidence_score`, `decision_support`, `decision_distinct_evidence_sources` and the instant `decided_at` — are frozen when the incident reaches `PENDING_DECISION` and are never recomputed afterwards. The decision and appeal surfaces therefore reason over a fixed record rather than a moving one, which is what makes an appeal reviewable.

Precision is pinned for all score arithmetic in this domain. Each admitted evidence item's weighted value is rounded to **three** decimal places using round-half-up, the rounded values are summed, any cap and penalty are applied to that rounded sum, and the final figure is rounded to **two** decimal places using round-half-up. The region-level triage projection deliberately sums the same items **unrounded** and rounds only the final figure, so the two readings of one evidence set can diverge by up to 0.02 whenever an item's third decimal is non-zero. Implementations must expose the primary, per-item-rounded reading on the freeze path.

### 2.6. Graduated Enforcement and the Consumer Safety Report Queue

An `EnforcementAction` is never created by a client. It is synthesised when a decision is committed, carrying the incident's `decision_category` into its `outcome` field, which is one of `WARNING`, `RESTRICTED` or `DEACTIVATED` — the value `NONE` never appears on an action. It is also synthesised outside the decision surface wherever the account is made deactivation-eligible on a path that mints no incident decision — the cluster-ban cascade and an `ADVERSE` screening adjudication — and those actions carry the outcome `DEACTIVATED` directly and address no incident, their `incident_id` reading null. The action begins in `DRAFT` and moves to `ACTIVE` or to `MANDATORY_REPORTED` inside the same request.

Three account-level counters are derived from the enforcement ledger. `standing_enforcement_count` counts the account's enforcement actions whose `enforcement_status` is `ACTIVE`, `MANDATORY_REPORTED` or `APPEAL_PENDING`. `deactivation_count` counts the account's enforcement actions whose `outcome` is `DEACTIVATED`, including every reinstatement generation of the same action. `prior_reinstatement_count` counts completed reinstatements recorded against the account with no intervening deactivation.

An account that has been deactivated twice is a candidate for the platform's periodically published **consumer safety report**. The queue for the next publication is ordered by the account identifier ascending; an account enters it when an enforcement action with `outcome` `DEACTIVATED` is created for an account whose `deactivation_count` has reached 2, and an appeal overturn removes the account from the next publication. Publications are capped per region: the cap is consumed by accounts whose `deactivation_count` is at or above 2, and when it is already exhausted the newly eligible account is not queued at all — the request itself succeeds and the cap simply decrements rather than the write failing with `ERR_MONTHLY_REPORT_CAP_REACHED`.

`rehabilitation_credit` is the free-of-incident completed-trip credit an account earns toward reinstatement. It is recomputed as the count of the subject account's `Trip` rows whose `status` is `COMPLETED` and whose `completed_at` is at or after the enforcement action's `effective_at`. Three scheduled instants hang off every action: `effective_at`, stamped when the action becomes `ACTIVE`; `review_due_at`, which is `effective_at` plus the **180-day** review interval and drives the periodic review round; and `expires_at`, which is `effective_at` plus the **365-day** restriction horizon and drives the expiry sweep. `appeal_deadline_at` is the originating incident's `decided_at` plus the region's appeal-window length, and `decision_made_at` copies that same `decided_at` onto the action so the deadline rule can be evaluated without re-reading the incident.

### 2.7. Device Clusters, Dormancy and Severity Banding

A `DeviceCluster` groups shared-handset and device-farm observations. Its `aggregate_cluster_risk` is the sum, over **every** member account of the cluster — including members whose `status` is `DEACTIVATED` or `REINSTATED` and members reachable only through a `SEVERED` link — of that account's non-cluster risk components, that is, the clamp of its incident term plus its enforcement term between 0 and 1000. Each member's clamped component is itself rounded to two decimals before it enters the sum, and the sum is rounded once more to two decimals using round-half-up. The cluster term is deliberately excluded from the aggregate, which keeps the aggregate well-defined without a circular fixed point. The aggregate carries no upper bound.

`clustered_actor_incident_count` counts the `SafetyIncident` rows belonging to the cluster's member accounts whose `severity` is `S3` or `S4` and whose `incident_status` is `OPEN`, `INVESTIGATING`, `PENDING_DECISION`, `MANDATORY_REPORTED_BLOCKED` or `DECIDED`. Two thresholds govern escalation: a cluster whose count reaches the region's watchlist threshold escalates from `OPEN` to `WATCHLIST`, and a `WATCHLIST` cluster whose `aggregate_cluster_risk` reaches the region's purge threshold while a linked account's `risk_tier` is `TIER_HIGH` or `TIER_SEVERE` escalates from `WATCHLIST` to `BANNED`. The second edge exists only while the region's escalation arm is enabled; with the arm disabled the cluster stays `WATCHLIST`.

A severity band is never supplied by a client. `severity` is always derived and any `severity` sent on intake is ignored. The derivation composes a category base level — 4 for `PHYSICAL_ASSAULT` and `SEXUAL_MISCONDUCT`, 2 for `HARASSMENT`, `SAFETY_VIOLATION`, `FRAUD_IDENTITY` and `DISCRIMINATION`, and 1 for `PROPERTY_DAMAGE` — with at most one escalation level from each distinct code in `aggravator_codes`, where `S3_INJURY` and `S3_LAW_ENFORCEMENT_SEVERITY` each add one level and each code is counted at most once. The sum is clamped to a maximum band level of 4 and a minimum of 1, and rendered as `S` followed by the level. The band also floors at `S2` whenever `prior_incident_count_at_intake` is at least 1 and the category base level is 1, so a second-report `PROPERTY_DAMAGE` incident lands on `S2` rather than the `S1` the base level alone would give. The `derivative_severity_flagged` flag is set true exactly on the saturated branch: the raw level reached 4 and at least one aggravator level was applied, meaning at least one escalation was consumed by the clamp.

### 2.8. Regional Policy Generation and Scheduled Cadence

Every threshold the safety pipeline reads comes from a `PlatformPolicy` row addressed by `region_code`. Periodicity knobs — the rollup window length, the rollup threshold, both cluster thresholds, the rescreen refresh interval, the continuous-monitor acknowledgement deadline, the expedited-appeal baseline and review interval, the standard review interval, the appeal window length and the segregation-of-duties floor severity — advance the policy's `review_generation_index` when they are revised, and a later revision touching only that same family advances the index again. Knobs that may change at any frequency — the segregation-of-duties arm and the escalation arm — advance `knob_generation_index` instead, and a revision touching only those two never moves the periodicity index. Both counters are monotonic and begin at 1.

An advancing `knob_generation_index` drives two deferred recomputations. Each `Account` carries a `policy_generation_index`, stamped from the region's policy at creation and re-stamped on every policy revision; an account is marked policy-drift-stale and evaluated for **three-year deactivation-policy drift** when the generation advances past `three_year_drift_last_run_index` by a multiple of 3. Each `DeviceCluster` carries a `cluster_risk_generation_index`; an advancing generation that reaches a multiple of 2 marks the cluster for a stale-risk recompute of its aggregate.

Driver rescreening follows a cadence driven by `BackgroundCheck` rows. A `RESCREEN` record's `scheduled_due_at` is anchored on the account's most recent completed background-check completion instant — or on the account's `created_at` when none exists — plus the per-drift-step refresh interval multiplied by the drift step, where the per-drift-step refresh interval is 548 days and the drift step is the floor of one third of the generation index minus one. The three-year drift evaluation marks an account when its generation advances past `three_year_drift_last_run_index` by a multiple of three. `trigger_source` records what created the row: `CONTINUOUS` is written by the account-creation synthesis and `CADENCE` by the rescreen sweep, and `triggered_by_incident_id` is reserved for incident-triggered reviews and left null by both. A continuous-monitor record must be acknowledged within the region's acknowledgement deadline, and `monitor_generation` holds the generation index on which the record was opened or last bumped.

### 2.9. Nested Resource Retrieval

Requests that target a resource through a path containing more than one identifier are validated left to right, and the first identifier that does not resolve is the one that decides the error. A request naming an account that does not exist fails with `ERR_RESOURCE_NOT_FOUND` (`404`) before the system even attempts to resolve the child resource beneath it. The same ordering applies to the other addressable roots: an incident that does not exist surfaces as `ERR_INCIDENT_NOT_FOUND` (`404`) on the incident-scoped writes and reads, a trip that does not exist surfaces as `ERR_TRIP_NOT_FOUND` (`404`), and an enforcement action, background check or policy that does not exist surfaces as `ERR_RESOURCE_NOT_FOUND`.

### 2.10. Common Resource Properties

Every top-level resource in this domain — `Account`, `DeviceCluster`, `AccountDeviceLink`, `Trip`, `SafetyIncident`, `IncidentEvidence`, `EnforcementAction`, `RegulatorReport`, `BackgroundCheck` and `PlatformPolicy` — carries the same system-managed skeleton:

- `id` (string): a server-minted identifier formatted as a UUID, with no type prefix or embedded entity name.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, for example `2025-05-24T10:30:00.123Z`, recording when the resource was created.
- `updated_at` (string): an ISO 8601 UTC timestamp recording the resource's last modification; it is refreshed by any mutation of the resource's properties, including mutations of derived fields.
- `version` (integer): a server-managed integer that increments by exactly 1 on every modification of the resource, and that the optimistic-concurrency rules in §2.11 read.

All ten entities set the common-fields flag, so none of them omits `updated_at` or `version`; there is no immutable-after-creation entity in this domain whose skeleton is trimmed to `id` and `created_at` alone. A freshly created resource starts at `version` 1. Where a derived quantity is recomputed on a parent because a child changed, the parent's `updated_at` and `version` move with it.

### 2.11. Optimistic Concurrency Control

Six write operations in this API are protected against a client acting on a stale view of the parent entity. Each one requires its named expectation field as a **non-optional** member of the request body; a request that omits it is malformed and refused with `ERR_STALE_VERSION` (`412`), and a request that carries a value which does not equal the parent entity's current `version` is rejected with the same `ERR_STALE_VERSION` (`412`). The protected operations are:

- Committing an incident decision requires `expected_incident_version`, compared against the target `SafetyIncident`'s current `version`.
- Committing an appeal outcome requires `expected_incident_version`, compared against the target `SafetyIncident`'s current `version`.
- Running the restriction-expiry sweep requires `expected_account_version`, compared against the target `Account`'s current `version`.
- Stabilizing a watchlisted cluster requires `expected_cluster_version`, compared against the target `DeviceCluster`'s current `version`.
- Opening the regulator filing window requires `expected_report_version`, compared against the target `RegulatorReport`'s current `version`.
- Revising a regional policy requires `expected_policy_version`, compared against the target `PlatformPolicy`'s current `version`.

These are stale-view rejections, not arbitration between overlapping requests: the check simply compares the client's observed version against the stored one and refuses the write when the stored value has moved on. No other endpoint in the API accepts a version field, and no version field is optional. Each of the six protected writes bumps the version of the entity it mutates by 1 on success, which is what makes the next writer's stale detection possible.

## 3. Business Logic & Workflows

### 3.1. Filing and Classifying an Incident Report

A report arrives from a `Rider`, a `Driver` or a `SafetyInvestigator` acting as registrar, and it names the account whose conduct is in question through `account_id`, the counterparty the reporter is, and the class of harm alleged. `reporter_type` is one of `RIDER`, `DRIVER` or `THIRD_PARTY`, and it constrains who the reporter is: when the type is `THIRD_PARTY` the `reporter_account_id` member must be omitted, and when it is `RIDER` or `DRIVER` it must be populated. A report that violates that pairing is refused with `ERR_REPORTER_ACCOUNT_MISMATCH` (`422`). The `incident_category` selects the decision-criteria row later and is one of `PHYSICAL_ASSAULT`, `SEXUAL_MISCONDUCT`, `HARASSMENT`, `SAFETY_VIOLATION`, `FRAUD_IDENTITY`, `DISCRIMINATION` or `PROPERTY_DAMAGE`. A report may reference the trip it arose from through an optional `referenced_trip_id`, which is left null when no trip is involved.

Severity is computed at intake, never accepted. The classification combines the category's base level with the escalation codes in `aggravator_codes`, where each of `S3_INJURY` and `S3_LAW_ENFORCEMENT_SEVERITY` contributes exactly one level and a code repeated in the list is still only counted once; the summed level is clamped to the band ceiling of 4 and the band floor of 1 and rendered as `S` plus the level, yielding `S1`, `S2`, `S3` or `S4`. The band floors at `S2` rather than `S1` whenever `prior_incident_count_at_intake` reaches at least 1 and the category's base level is 1. The flag `derivative_severity_flagged` turns true on the saturated branch only — the raw level reached 4 and at least one aggravator level was applied — which is the platform's signal that an escalation request was absorbed by the clamp rather than honoured. Before any interim hold exists, a `SafetyInvestigator` may revise the intake codes by patching the incident's `aggravator_codes`, and the same derivation re-runs.

Three values are frozen onto the new incident at intake so that later reasoning is tamper-evident. `prior_incident_count_at_intake` counts the account's *other* `SafetyIncident` rows created strictly before this incident's `created_at`. `cluster_risk_multiplier_pct` is resolved from the subject account's device links: the links are deduplicated by `device_cluster_id`, keeping for each cluster the row with the greatest `last_seen_at` and breaking ties by `created_at` ascending; among the survivors whose `link_status` is `LINKED` or `DORMANT`, the row with the greatest `last_seen_at` (ties again by `created_at` ascending) identifies the cluster, and the multiplier is 100 plus the floor of the resolved cluster's `aggregate_cluster_risk` divided by 50, clamped between 100 and 300. When no such surviving link exists the multiplier is the 100 floor and no cluster term participates in the account's risk at all. `decision_category` starts at `PENDING` and the investigation state `incident_status` starts at `OPEN`.

A trip earns its place in the record through two optional intake facts. `in_app_message_count` counts the in-app messages exchanged on the trip and is admitted as evidence only when it is at least 1, and `law_enforcement_contact_logged` records whether a law-enforcement contact was logged during intake.

### 3.2. The Interim Hold and Its Release

Once an incident is `OPEN` and its `severity` is `S3` or `S4` and its `account_id` matches the account being acted on, a `SafetyInvestigator` may place an **interim hold** that suspends the account's public standing while the investigation runs. The hold moves the incident from `OPEN` to `INVESTIGATING`, moves the account's `status` from `ACTIVE` to `UNDER_HOLD`, suppresses the account's member announcements for the duration of the interval, and re-propagates the account's `risk_score`. The same hold is available against an account that already sits at `RESTRICTED` from an earlier matter, in which case the account also lands at `UNDER_HOLD`.

Three guards stand in front of the hold. An incident whose `severity` is `S1` or `S2` is below the floor required to open a hold and the request is refused with `ERR_SEVERITY_BELOW_HOLD_FLOOR` (`422`). An account that is currently `APPEAL_PENDING` cannot be held at all, because communication suppression is only permitted for accounts that are `ACTIVE`; the attempt is refused with `ERR_HOLD_BLOCKED_BY_APPEAL` (`409`) before anything is written. And an incident that has already reached `DECIDED` is under terminal lockdown — a hold placed against it performs no transition, is rejected with `ERR_INVALID_STATE` (`409`), and leaves the account's status untouched. The same `ERR_INVALID_STATE` lockdown covers an incident sitting at `MANDATORY_REPORTED_BLOCKED` and one sitting at `WITHDRAWN`. A hold is declared only from an incident at `OPEN` on an account whose `status` is `ACTIVE` or `RESTRICTED`; any other starting state is refused with `ERR_INVALID_STATE` (`409`).

Releasing a hold is the inverse operation and its destination depends on what the account still carries. When the account holds no enforcement action in `ACTIVE` or `MANDATORY_REPORTED` status and no standing action at all, the release returns the account to `ACTIVE` and the incident to `OPEN`, and the account's member announcements resume. When the account still carries at least one standing `ACTIVE` or `MANDATORY_REPORTED` enforcement action, the release instead lands the account at `RESTRICTED` while still returning the incident to `OPEN`. A release requested against an incident that is not `INVESTIGATING` is refused with `ERR_INVALID_STATE`. Every release re-propagates the account's `risk_score`.

The lockstep between the two entities is worth stating plainly, because the two state machines carry parallel edges: a hold always writes both `account.status = UNDER_HOLD` and `incident.incident_status = INVESTIGATING`, and a release always writes the incident back to `OPEN` and the account to whichever of `ACTIVE` or `RESTRICTED` the enforcement ledger dictates. A `SafetyInvestigator` may also revise an incident's aggravator codes by patching `aggravator_codes` while no hold yet exists; the patch re-derives `severity` and `derivative_severity_flagged` and re-propagates the account's risk.

Across the whole lifecycle an incident's `incident_status` moves through `OPEN`, `INVESTIGATING`, `PENDING_DECISION`, the blocked mandatory-report branch `MANDATORY_REPORTED_BLOCKED`, the decided and appeal states `DECIDED`, `APPEAL_PENDING`, `APPEAL_UPHELD` and `APPEAL_OVERTURNED`, and the withdrawal `WITHDRAWN`; of these, `DECIDED`, `APPEAL_UPHELD`, `APPEAL_OVERTURNED` and `WITHDRAWN` are terminal. Withdrawal belongs to a `SafetyOperationsLead` and is available only while the incident's `decision_category` is still `PENDING` and its severity is `S1` or `S2` — an `S1` incident may be withdrawn from `OPEN` and an `S2` incident from `INVESTIGATING`. Withdrawal moves the incident to `WITHDRAWN`, creates **no** enforcement action at all, and returns the account to `ACTIVE` when it had been `UNDER_HOLD`. A decision attempted against an incident already at `WITHDRAWN` is rejected with `ERR_INVALID_STATE` (`409`) and creates no enforcement action — the withdrawn state is a lockdown, not a pause.

### 3.3. Evidence Gathering, Admissibility and the Approach to Decision

Evidence is gathered one item at a time by a `SafetyInvestigator`. Each item carries an `evidence_type` — one of `TRIP_DATA`, `IN_APP_MESSAGE`, `RATINGS_HISTORY`, `LAW_ENFORCEMENT_CONTACT`, `DEVICE_LINK` or `EXTERNAL_RECORD` — an `evidence_weight` of `WEAK`, `STANDARD`, `STRONG` or `DISPOSITIVE`, and an optional `source_entity_id` naming the artifact the item was drawn from: a trip identifier for `TRIP_DATA`, a trip identifier for `IN_APP_MESSAGE`, a device-link identifier for `DEVICE_LINK`, the subject account identifier for `RATINGS_HISTORY`, and nothing at all for `LAW_ENFORCEMENT_CONTACT` and `EXTERNAL_RECORD`. The item is stored with `evidence_status` `PENDING` and `recorded_at` stamped from the logical clock, which is the deterministic ordering key the scoring pass reads. Admitting a `LAW_ENFORCEMENT_CONTACT` item also flips the linked trip's `law_enforcement_contact_logged` flag — the trip the incident references through `referenced_trip_id`, since an admitted `LAW_ENFORCEMENT_CONTACT` item carries no `source_entity_id` of its own — and a referencing trip that does not exist is refused with `ERR_TRIP_NOT_FOUND` (`404`).

Two referential guards protect the item before it is stored. A trip attached as `TRIP_DATA` or `IN_APP_MESSAGE` evidence must name a trip and that trip must involve both the incident's subject account and the reported counterparty account; a trip that involves only one of them is refused with `ERR_TRIP_ACCOUNT_MISMATCH` (`422`). And neither evidence nor a device link may reach across regions: a reference to a prior incident or a device cluster belonging to a different operating region is refused with `ERR_CROSS_REGION_REFERENCE` (`422`). Device links carry the same cross-region constraint applied to their own cluster reference, and an incident's `referenced_trip_id` must likewise name a trip in the subject account's own region, while evidence drawn from a `DEVICE_LINK` whose cluster, or a `RATINGS_HISTORY` whose named account, belongs to another operating region is refused the same way.

Each item resolves through an **acceptance step** where a `SafetyInvestigator` supplies the item's `evidence_id` together with an `accepted` flag. Affirming the flag moves the row to `INCLUDED`; declining it moves the row to `EXCLUDED` and records why in `exclusion_reason`, which an explicit decline stamps with `DECLINED`. Three further exclusions are applied unconditionally, ahead of the scoring pass, and they are what the remaining `exclusion_reason` values name. A `LAW_ENFORCEMENT_CONTACT` item whose `source_entity_id` is null is excluded as `STALE_SOURCE`. An `IN_APP_MESSAGE` item whose source trip has `in_app_message_count` equal to 0 is excluded as `NO_MESSAGE_HISTORY`. And a `DEVICE_LINK` item whose source link's `last_seen_at` is strictly earlier than the logical clock minus **180 days** is excluded as `STALE_LINK`. The `exclusion_reason` field stays null for as long as the item's `evidence_status` is `PENDING` or `INCLUDED`.

When the last `PENDING` item resolves and at least one `INCLUDED` row exists, the investigation advances: the incident moves from `INVESTIGATING` to `PENDING_DECISION` and the account's `status` moves to `PENDING_DECISION` with it. In every case the advance freezes three snapshots onto the incident at that instant: `decision_evidence_score` from the admissibility score, `decision_support` from the support score, and `decision_distinct_evidence_sources` from the count of distinct `evidence_type` values among the `INCLUDED` rows.

The admissibility score itself is worth working through because its rounding is pinned. Each admitted item — every row that is not `EXCLUDED` and that survives the staleness exclusions — is assigned a reliability multiplier: 0.75 for `EXTERNAL_RECORD`, 0.90 for `IN_APP_MESSAGE` and `RATINGS_HISTORY`, and 0.95 for everything else. It is also assigned a base weight from its `evidence_weight`: 0.40 for `WEAK`, 0.70 for `STANDARD`, 1.00 for `STRONG` and 1.50 for `DISPOSITIVE`. The two are multiplied and the product rounded to **three** decimals using round-half-up. Each item also carries a type cap — 0.80 for `IN_APP_MESSAGE` and `RATINGS_HISTORY`, 0.70 for `LAW_ENFORCEMENT_CONTACT`, and 1.00 for every other type. The **raw contribution** is the sum of the rounded per-item values.

A fulfilment requirement is derived from the incident's severity level: one required distinct source for `S1` and `S2`, and two for `S3` and `S4` — that is, the ceiling of half the severity level. The count of distinct `evidence_type` values among the admitted items is compared against that requirement, and each missing source adds a penalty of 0.15 to the **cap penalty**, which is 0.15 multiplied by the number of missing sources. The **continuous score** is the smaller of two quantities: the raw contribution rounded to three decimals and then reduced by the cap penalty, on the one hand, and the **cap ceiling** — the sum of every admitted item's type cap — on the other; that smaller figure is then rounded to **two** decimals. The score's `applied_evidence_cap` is that cap ceiling. A `DISPOSITIVE` item's capped per-item value is at most 1.50 — a type cap of 1.00 times the 1.50 weight — so the `DISPOSITIVE` weight contributes nothing beyond a `STRONG` item's 0.95 once the type cap binds.

A `DISPOSITIVE` item is promotable beyond its weight, but only on two conditions taken together. Its **confidence ratio** — the raw contribution divided by the product of 0.95 and 1.50, reported rounded to two decimals — must be at least 0.80, and the incident must have at least two distinct `evidence_type` values among its admitted items, where the distinct-source count the conditions read is the count of distinct `evidence_type` values among every admitted item, not the support-restricted count. When both hold the incident is **dispositive-promotable**: the promotability flag is set, the item's promotable score is 3.00, and the incident's `decision_evidence_score` freezes at the promoted 3.00 in place of the capped continuous score. The promotion never lifts the score above what the conditions allow, so it re-applies cleanly as more items are admitted. The **support score** is separate from all of the above and much simpler: it is the count of distinct `evidence_type` values among the admitted items, restricted to `TRIP_DATA`, `RATINGS_HISTORY` and `LAW_ENFORCEMENT_CONTACT`.

Two read-only projections exist for triage. One returns the incident's `incident_id`, `evidence_score`, `support_score`, `distinct_evidence_source_count`, `applied_evidence_cap`, `confidence_ratio` and `dispositive_promotable`; the other returns the `incident_id`, `category_tier`, `evidence_tier`, `proposed_decision`, `scope_ratio` and `regulator_report_required` that the decision surface *would* apply right now against the same frozen snapshots.

### 3.4. The Deactivation Decision and Its Graduated Criteria

The decision is the pivot of the whole domain. A `SafetyInvestigator` commits it once the incident sits at `PENDING_DECISION`, supplying a `decision_category` of `NO_ACTION`, `WARNING`, `RESTRICTED` or `DEACTIVATED`, a `decision_basis` of at least twenty characters, and `expected_incident_version`. A decision may also be committed against an incident at `PENDING_DECISION` whose account currently sits at `RESTRICTED` from an earlier matter, which is the repeat-offender path. The committed outcome repeats the `decision_category` the client supplied rather than the projected one, so the projection above is what the surface *would* apply, not a value the server substitutes.

The outcome is not a free choice. It is projected by the decision-criteria rule from the incident's frozen snapshots, and the rule pins its own application order: the **category tier floor** is read first, and the continuous-evidence overrides are then applied in ascending threshold order, each override able to raise the floor result but never to lower it. The floor itself is a ladder of conditions, read top to bottom:

- `PHYSICAL_ASSAULT` and `SEXUAL_MISCONDUCT` floor at `DEACTIVATED`.
- `HARASSMENT` and `DISCRIMINATION` floor at `RESTRICTED` when `decision_support` is at least 2.0.
- `HARASSMENT` floors at `DEACTIVATED` when the account has at least 2 prior `S3`/`S4` incidents created strictly before this one.
- `FRAUD_IDENTITY` floors at `DEACTIVATED` when the **investigation scope ratio** is at least 0.70. That ratio is the count of the account's `SafetyIncident` rows created in the closed-open window from thirty days before this incident up to — but not including — this incident's `created_at`, divided by 5.
- `SAFETY_VIOLATION` floors at `DEACTIVATED` when the account has at least 3 prior `S3`/`S4` incidents created strictly before this one.
- `PROPERTY_DAMAGE` floors at `WARNING` when `decision_evidence_score` is at least 1.50.
- `SAFETY_VIOLATION`, `FRAUD_IDENTITY`, `PROPERTY_DAMAGE`, `DISCRIMINATION` and `HARASSMENT` fall through to `NO_ACTION`.

The overrides then apply. When `decision_evidence_score` is at least **4.00**, or is at least **2.50** with `decision_distinct_evidence_sources` of at least 2, the outcome is `DEACTIVATED`. When `decision_evidence_score` is at least 2.50 but `decision_distinct_evidence_sources` is below 2, the outcome is `RESTRICTED` regardless of where the floor ranks — a provisional deactivation that cannot fire for want of a second corroborating source, so a `PHYSICAL_ASSAULT` incident scoring 3.99 on a single source resolves to `RESTRICTED` rather than escaping all the way to `DEACTIVATED`. In every other case the floor stands alone. One further constraint bites after the overrides: a `NO_ACTION` result is permitted only when `decision_support` is below 2.0, and one that reads `NO_ACTION` while the support score sits at or above 2.0 is raised to `RESTRICTED`.

Two specialised prohibitions are asserted ahead of the shared state check on this surface. A decision cannot be committed while the account carries an `ACTIVE`, `MANDATORY_REPORTED` or `APPEAL_PENDING` enforcement action whose `outcome` is `DEACTIVATED` — the attempt is refused with `ERR_IN_FLIGHT_APPEAL` (`409`), and the reading counts the account's deactivating actions alone, so an earlier non-deactivating `WARNING` or `RESTRICTED` matter leaves the account at `RESTRICTED` without putting a deactivation in flight and the repeat-offender path below stays reachable. And the mandatory regulator-report gate refuses the write when the linked report still sits at `BLOCKED` inside an active regulator window block, even when the enforcement ledger is otherwise in a legal state for the request, with `ERR_REGULATOR_REPORT_BLOCKED` (`409`). The version expectation is checked before these prohibitions: a stale `expected_incident_version` is refused with `ERR_STALE_VERSION` (`412`), and only a request whose observed version still matches is measured against them. An incident that is not in a state from which the requested transition is declared — a withdrawn incident, for instance — is refused with `ERR_INVALID_STATE` (`409`), with no enforcement action created. A decision is declared from an incident at `PENDING_DECISION` whose account sits at `PENDING_DECISION` or `RESTRICTED`.

On success the incident moves to `DECIDED`, `decided_at` is stamped, `decision_category` carries the committed outcome, `decision_maker_user_id` records the acting `X-User-ID`, and the incident's `version` increments by 1. The account's `status` follows the graduated matrix: `DEACTIVATED` for a deactivating outcome, `RESTRICTED` for `RESTRICTED` and for `WARNING`, and back to `ACTIVE` for `NO_ACTION`. `deactivation_count` counts the account's enforcement actions whose `outcome` is `DEACTIVATED`, and a deactivating decision contributes exactly one such action, so the counter advances by one when the graduated matrix lands the account at `DEACTIVATED`; a deactivation also recomputes the account's risk from scratch rather than merely propagating it. In every branch an `EnforcementAction` is synthesised in `DRAFT` carrying the incident's `decision_category` as its `outcome`, and the mandatory-report cascade described in §3.5 then runs. A `NO_ACTION` outcome is not a graduated enforcement outcome, so that branch synthesises no action at all while still moving the account back to `ACTIVE`.

### 3.5. Mandatory Regulator Reporting and the Filing Window

Certain deactivations are reportable, and the platform will not let one slip. An enforcement action carries a derived `regulator_report_required` flag that reads true exactly when the linked incident's `incident_category` is `PHYSICAL_ASSAULT` or `SEXUAL_MISCONDUCT` and its `severity` is `S3` or `S4`. The flag steers the action's first transition out of `DRAFT`: when it is false the action becomes `ACTIVE`, and when it is true the action becomes `MANDATORY_REPORTED` and the incident's regulator report moves out of the `BACKLOG` state and into `FILED`. Both branches stamp `effective_at`, `appeal_deadline_at`, `expires_at`, `review_due_at` and `decision_made_at`, both increment `standing_enforcement_count`, and both recompute the account's safety posture.

A `RegulatorLiaison` may also queue a report directly, supplying the `incident_id`, a `report_channel` of `REGULATOR_PORTAL` or `LAW_ENFORCEMENT`, and a `filing_basis` of `PENDING`, `ROLLUP_THRESHOLD`, `ALWAYS_LAW_ENFORCEMENT` or `BLOCKED_WINDOW_TRIGGER`. A queued report starts with `report_status` `BACKLOG`, copies its `region_code` from the incident's subject account's `home_region_code`, and leaves `filed_at` null until the report is actually filed; `report_status` is one of `BACKLOG`, `BLOCKED` or `FILED`, and the window-open transition is what lets a `BLOCKED` report unblock retroactively. The portal channel is the one the decision cascade files through; the law-enforcement channel is the one the liaison files through directly. A queueing request that names a channel for which the incident already carries a report returns the existing report unchanged as a `201` rather than minting a second one.

The **mandatory-report commit cascade** runs on every decision, and it is where three different entities move at once. First, when `regulator_report_required` is true, the incident's report leaves `BACKLOG` for `FILED` and the enforcement action lands at `MANDATORY_REPORTED`. Second, when the linked device cluster's `clustered_actor_incident_count` has reached the region's watchlist threshold and the cluster is still `OPEN`, the cluster moves `OPEN` to `WATCHLIST` and the enforcement action's `cluster_watchlist_triggered` flag is set true — **only** on that first crossing; a later crossing that finds the cluster already `WATCHLIST` leaves the flag false. Third, when the linked cluster is already `WATCHLIST` and its `aggregate_cluster_risk` has reached the region's purge threshold and the linked account's `risk_tier` is `TIER_HIGH` or `TIER_SEVERE`, the cluster moves `WATCHLIST` to `BANNED`. The escalation arm exists only while the region's `escalation_enabled` knob is true; with it false, the purge edge is unavailable and the cluster stays `WATCHLIST`.

A region may also operate an **always-report regime** for law-enforcement filings. Under it a report queued with the `ALWAYS_LAW_ENFORCEMENT` basis is created and the action enters `MANDATORY_REPORTED`. When the decision instant falls inside the region's active regulator window block, the report instead lands at `BLOCKED`, and a deactivating decision against that incident does not reach `DECIDED` at all — the incident moves from `PENDING_DECISION` to `MANDATORY_REPORTED_BLOCKED`. That state is a genuine dead end, not a pause: a second decision attempt made from it with a `DEACTIVATED` category is rejected with `ERR_REGULATOR_REPORT_BLOCKED` for as long as the linked report remains `BLOCKED`. When the region's blocked window closes, the report moves `BLOCKED` to `FILED`, `filed_at` is stamped, and the incident returns to `PENDING_DECISION` so that a single permitted hold-then-decide cycle can resume; the linked enforcement action moves `DRAFT` to `MANDATORY_REPORTED` at the same moment. Until that window closes the action stays at `MANDATORY_REPORTED` and the account stays `DEACTIVATED`.

History can trigger reporting on its own. A `RegulatorLiaison` runs a **region rollup check** for an incident, which counts the subject account's `SafetyIncident` rows created inside the closed-open window from the region's rollup window length before the incident's `created_at` up to but not including the incident's `created_at`, considering only rows whose `severity` is `S3` or `S4`. The window length defaults to 30 days — so with the default policy the lower edge of the window sits exactly 30 days before the triggering incident's `created_at` — and the count is compared against a threshold that defaults to 3 serious incidents. The lower boundary is inclusive and the upper boundary is exclusive: an incident created at exactly the window start is counted, and one created at exactly the window end — the same instant as the triggering incident — is not, which is why the triggering incident itself is tracked separately as the current incident rather than folded into the historical count. When that count has reached the region's rollup threshold, exactly one report is produced for the pair of subject account and region and moves straight to `FILED`, and the check additionally requires that the subject account's `status` is `DEACTIVATED`, `RESTRICTED`, `UNDER_HOLD`, `PENDING_DECISION` or `APPEAL_PENDING` and that no report already exists for that same account-and-region pair. The **issuance invariant** then holds across the whole region: for any subject account, at most one report may exist for its home region whose `filing_basis` is `ROLLUP_THRESHOLD`, `ALWAYS_LAW_ENFORCEMENT` or `BLOCKED_WINDOW_TRIGGER`; reports carrying the `PENDING` basis are exempt from the invariant, which is what allows an intake-basis report to be filed on a first incident with zero qualifying historical incidents. The same check also projects the account's standing graduated outcome.

Filing windows themselves are opened by a `RegulatorLiaison` once a region's blocked window has closed, and that operation is one of the six stale-version-protected writes of §2.11: it requires `expected_report_version` and is refused with `ERR_STALE_VERSION` (`412`) when the client's observed version has moved on, and it increments the report's `version` by 1 on success. The operation addresses its report through `expected_report_version`'s parent: when the body names no explicit `report_id`, the oldest `BLOCKED` report is the one whose version is read and which is filed. The **publication attempt** for a mandatory report is a window projection. It is driven by two inputs — the report's `report_id` and a `window_index` — and returns a projection rather than a new persisted resource: the projection carries `incident_id`, `window_index`, `included`, `dropped_reason`, `published_at` and a `rollup` field. The `rollup` field carries the account's standing graduated cumulative rollup for the requested `window_index`, as projected by the rollup rule in §3.7. The attempt re-publishes whenever the window in which the account currently sits changes: its projection reports `included` true in every case except the one drop condition below. `published_at` is the report's `created_at` advanced by 365 days multiplied by the requested `window_index`, an attempt persists the requested `window_index` onto the report so the next window is stepped one forward from it, and the attempt bumps the report's `version` by 1. When the account sits at `APPEAL_PENDING` and the report's own published instant is at or past 365 days, the account is dropped from the report — `included` reads false with `dropped_reason` `REINSTATED_AFTER_365_DAYS` — and its `status` moves from `APPEAL_PENDING` to `REINSTATED`, which is the one edge that lets an account leave the appeal posture without the appeal team's verdict. A report still sitting at `BLOCKED` inside an active regulator window block is refused outright with `ERR_REGULATOR_REPORT_BLOCKED` (`409`).

### 3.6. Appeals, the Separate Review Team and the Review Deadline

An account that has been deactivated through an incident whose `decision_category` is `DEACTIVATED` may appeal, and the appeal is heard by a team that never includes the deciding investigator. Filing is the exclusive work of a `SafetyAppealReviewer`. The gate is a conjunction: the incident must sit at `DECIDED`, its committed `decision_category` must be a graduated outcome — `WARNING`, `RESTRICTED` or `DEACTIVATED` — and the region must hold exactly one appeal-eligible record for it whose linked enforcement action still sits at `ACTIVE` or `MANDATORY_REPORTED`, and the filing instant must be **strictly before** the linked enforcement action's `appeal_deadline_at`, which is the originating incident's `decided_at` plus the region's appeal-window length. An arrival at or after that instant is refused with `ERR_APPEAL_WINDOW_CLOSED` (`422`).

Exactly one appeal may be in flight per incident. A second filing while the incident sits at `APPEAL_PENDING`, or after it already carries a committed appeal outcome, is refused with `ERR_APPEAL_ALREADY_FILED` (`409`), which is what keeps `safety_posture` pinned at `FROZEN` for the whole appeal period. The same refusal applies whether the underlying action was `WARNING`, `RESTRICTED` or `DEACTIVATED`: the filing edges exist for all three categories, and the incident and the account both move to `APPEAL_PENDING` while the linked enforcement action — identified by its `incident_id` when the reviewer needs to address it — also moves to `APPEAL_PENDING`. The filing stamps `last_applied_appeal_deadline` with the arrival instant plus the region's appeal-window length, which keeps a later reverted action's deadline deterministic without a per-appeal child entity. A release of the interim hold while the account sits in the appeal posture is not available: the hold surfaces only accept an `INVESTIGATING` incident, so such an attempt is refused with `ERR_INVALID_STATE` (`409`). One thing deliberately does *not* change at filing time — the account's appearance in the periodic consumer safety report is not reversed until the appeal outcome actually commits.

The outcome is committed by a `SafetyAppealReviewer` supplying an `adjudication` of `UPHELD` or `OVERTURNED`, `review_notes`, the `commit_early` boolean and `expected_incident_version`. The reviewer identity is recorded in `appeal_reviewer_user_id`, and it must differ from the incident's `decision_maker_user_id`. When the two are equal and the region's segregation-of-duties floor is armed — the region's segregation arm enabled and its floor severity set at or below the incident's own severity band — the outcome is refused with `ERR_THROWN_ON_APPEAL` (`422`). This is the platform's strongest control: a case can never be reviewed by the person who decided it.

**The review deadline is a floor on when an outcome may be committed, not a ceiling.** An appeal is assigned to the `EXPEDITED` track when `prior_incident_count_at_intake` is at least the region's expedited baseline count, and to the `STANDARD` track otherwise; the baseline is a plain count, so an account whose early history sits at the baseline qualifies however few of those incidents were serious. The review interval is the region's expedited review interval on the `EXPEDITED` track and its standard review interval on the `STANDARD` track. The review becomes due at the appeal's commit instant plus that interval in whole days, where the appeal commit instant is the arrival instant of the first filing that actually committed. **Eligibility to commit an outcome opens when the current instant is at or after that due instant.** An outcome committed strictly before it is refused with `ERR_APPEAL_NOT_ELIGIBLE` (`422`), unless the request sets `commit_early` to true, which is the only way to override the wait; a reinstatement requested with a credit below 1 is refused with the same `ERR_APPEAL_NOT_ELIGIBLE` (`422`) code. The two tracks therefore disagree about the very same request: an outcome committed fifteen days after the commit instant is refused on the `STANDARD` track, whose interval is longer, and accepted on the `EXPEDITED` track, whose interval is shorter. The eligibility read exposes this state directly, reporting `incident_id`, `appealable`, `appeal_track`, `review_due_at`, `appeal_deadline_at` and `prior_incident_count_at_intake`. A stale `expected_incident_version` is refused with `ERR_STALE_VERSION` (`412`).

`UPHELD` means the deactivation stands. The reviewer identity must differ from the decider, and the linked enforcement action's `rehabilitation_credit` must be **below 1** — an account that has earned a completed-trip credit since deactivation is no longer a candidate for a simple uphold. The incident moves to `APPEAL_UPHELD`, the account returns to `DEACTIVATED`, and the action moves to `REVERTED` with its credit decremented by one, floored at 0. A `SafetyAppealReviewer` may then ask for a further review round: once the incident already carries a committed outcome and the current instant has reached the action's `last_applied_appeal_deadline`, an uphold may be re-committed, on the condition that the credit is still below 1, and the cycle re-enters `APPEAL_PENDING` from `APPEAL_UPHELD` and from `APPEAL_PENDING` itself without changing the outcome — each re-entry moving the account briefly through `DEACTIVATED` and incrementing `deactivation_count`.

`OVERTURNED` means the deactivation is lifted, and it too requires a credit of **at least 1**, checked against the action's credit before any decrement, alongside the reviewer-identity difference. The incident moves to `APPEAL_OVERTURNED`, the account moves to `ACTIVE` and increments `prior_reinstatement_count`, the action moves to `REVERTED` and increments `reinstatement_generation`, and the account is dropped from the next published consumer safety report. On that overturn the action's `rehabilitation_credit` is decremented by one when it was standing at `MANDATORY_REPORTED` or `ACTIVE`, and is then recomputed from the account's completed-trip credit count, so a standing action carries a credit equal to the trips completed at or after its `effective_at`; an action reverting from `APPEAL_PENDING` reaches the same recomputed figure without the extra decrement. The account's risk score reverts toward its incident-free baseline and **must equal the pre-incident baseline exactly** — this is an exact-restoration requirement, not an approximation, since the projection is recomputed against the reverted ledger. A superseding reinstatement request may likewise move an `APPEAL_UPHELD` incident straight to `APPEAL_OVERTURNED` when the credit requirement is met, and it reads the same incident, ledger and account state the standard overturn reads.

The enforcement action's own revert edges carry their own conditions. An action at `APPEAL_PENDING` whose linked incident is `WARNING` or `RESTRICTED` reverts on an overturn, though the path applies the same credit decrement-then-recompute the other edges do and so still settles on the recomputed credit count and a decremented `standing_enforcement_count`. A regulator-reportable action at `MANDATORY_REPORTED` reverts on an overturn when the reviewer identity differs, the credit is at least 1, and the linked report is already `FILED`; that path decrements `rehabilitation_credit` by one, recomputes it as the completed-trip credit count, and decrements `standing_enforcement_count`. An action at `ACTIVE` reverts on an overturn when the credit is at least 1, with the same decrement and recomputation plus a posture recalculation. Finally, an appeal that has expired without an outcome may be renamed to a formal rejection: an upheld outcome committed once the current instant has reached `last_applied_appeal_deadline` decrements the credit floored at 0 and leaves the account deactivated; the `standing_enforcement_count` is then re-derived from the ledger rather than nudged, so the action's move to `REVERTED` leaves it out of the standing set.

### 3.7. Device Clusters, Escalation and the Graduated Deactivation Rollup

A `DeviceCluster` is created by a `PlatformAdmin` with a `cluster_key` that must be unique and may not be changed afterwards, and a `region_code`. Any `aggregate_cluster_risk` value supplied at creation is ignored, because the aggregate is always derived: the cluster starts at `OPEN` with `aggregate_cluster_risk` of 0, `clustered_actor_incident_count` of 0 and `cluster_risk_generation_index` of 1. A `SafetyInvestigator` then attributes observations to it by recording an `AccountDeviceLink` that names the `account_id`, the `device_cluster_id` and the `fingerprint_hash` that resolved to the cluster; the link starts at `link_status` `LINKED`, its `first_seen_at` and `last_seen_at` are both stamped from the logical clock at creation, and the cluster's aggregate is recomputed immediately.

Two guards fence link creation. A link aimed at a `BANNED` cluster is refused with `ERR_CLUSTER_BANNED` (`422`), and because the ban must continue to hold against freshly observed fingerprints, **pre-existing links are preserved rather than deleted** — the refusal protects the cluster, not the history. Links are otherwise accepted against a cluster whose `status` is `OPEN` or `WATCHLIST`, in which case the cluster simply stays where it is. A link whose cluster or referenced incident belongs to a different operating region is refused with `ERR_CROSS_REGION_REFERENCE` (`422`).

Links age on their own schedule. A sweep driven by a `PlatformAdmin` walks every link and moves one whose `last_seen_at` has aged at least 180 days from `LINKED` to `DORMANT`, at which point it stops counting toward the cluster's `clustered_actor_incident_count`; a second interval carries a `DORMANT` link past 365 days from `last_seen_at` into `SEVERED`, its terminal state. Clusters holding affected links have their aggregates recomputed.

Escalation is where the cluster reaches back into its members. When a cluster crosses from `OPEN` to `WATCHLIST` on the mandatory-report cascade described in §3.5, every member link whose `link_status` is `LINKED` or `DORMANT` is set to `SEVERED` in the same request. That single clause also subsumes the staleness drain, because a `LINKED` row older than 180 days is by then already `DORMANT` and a `DORMANT` row older than 365 days is already `SEVERED`, so no separate newest-link arithmetic is needed to sweep up stale-but-superseded rows. Crossing to `BANNED` is heavier: every member account still reachable through the cluster whose `status` is still `ACTIVE` becomes deactivation-eligible with the outcome `DEACTIVATED`, including accounts whose only links are `SEVERED`, while a member already in any other status is left where it is. A cluster may also be brought back down. A `SafetyOperationsLead` may stabilize a `WATCHLIST` cluster once 180 consecutive days have passed with no new clustered `S3`/`S4` incident and its aggregate sits below the region's purge threshold, restoring it to `OPEN` and restoring every `SEVERED` member link to `LINKED`; the aggregate is recomputed and `cluster_risk_generation_index` is stamped to the current generation. That stabilization is version-protected — it requires `expected_cluster_version` and refuses a stale one with `ERR_STALE_VERSION` (`412`) — which is what catches the case where a new member link has legitimately re-joined the cluster since the operations lead last read it.

The **graduated deactivation rollup** projects an account's standing outcome from the history of its serious incidents. It walks the account's `SafetyIncident` rows whose `incident_status` is `DECIDED` or `APPEAL_UPHELD` and whose `severity` is `S3` or `S4`, ordered by `decided_at` ascending, then `created_at` ascending, then by category rank ascending — where `PHYSICAL_ASSAULT` ranks 0, `SEXUAL_MISCONDUCT` 1, `HARASSMENT` 2, `SAFETY_VIOLATION` 3, `FRAUD_IDENTITY` 4, `DISCRIMINATION` 5 and `PROPERTY_DAMAGE` 6. A running counter starts at zero and advances by one for **every** entry in the ordered set, not merely for the entry that produces the standing outcome. The rollup is read off that counter: an `S4` incident at counter zero yields `PERMANENT_DEACTIVATION`, at counter one `SIX_MONTH_RESTRICTION` and at counter two `TWELVE_MONTH_RESTRICTION`; an `S3` incident at counter zero yields `THIRTY_DAY_SUSPENSION` and at counter one `TWELVE_MONTH_SUSPENSION`; and any other position yields `PERMANENT_DEACTIVATION`. The rule's ordinal ceiling is five entries, so entries past the fifth are never reached. It is the counter, not the position of the entry that produced the outcome, that decides the band — which is why an account with three `S4` incidents and one `S3` incident reaches `PERMANENT_DEACTIVATION` however those four entries interleave in time. The `decision_category` of an entry is consulted only for the one entry that produces the standing rollup, and this same projection supplies the `rollup` field of the publication attempt described in §3.5. Where an entry carries no `decided_at` the ordering fallback is its `created_at`.

### 3.8. Scheduled Sweeps, Background Screening and the Logical Clock

The platform's deferred work is driven by a testable logical clock rather than by the host machine. An administrative capability sets that clock to a supplied `current_utc` instant. Before it is called, the server's startup default time is `2026-09-01T00:00:00Z`, and the implementation must not fall back to real wall-clock time under any circumstance.

The **restriction-expiry sweep** is run by a `SafetyOperationsLead` against one account, supplying the `account_id` and `expected_account_version`. It moves the account's `ACTIVE` enforcement action whose `expires_at` has arrived to `EXPIRED` — the earliest such action by `effective_at` when more than one qualifies — and the account's destination depends on a projection rather than on the state it is in. The projection recomputes the account's risk score with the expiring action removed from both the score and the tier floor, subtracts 30 from that figure, clamps the result between 0 and 1000, and rounds it to two decimals half-up; the projected tier is then read off the plain score cutoffs of §2.4 alone — the projection does not consult the severity escape hatch — and the pre-sweep tier is the account's stored `risk_tier`. A **regression** occurs only when the account's pre-sweep tier is exactly `TIER_SEVERE` and the projected tier is any other band — so an account whose projected score lands at exactly 640.00 is still `TIER_SEVERE` and no regression fires, and an account whose pre-sweep tier was `TIER_HIGH` and which projects to `TIER_ELEVATED` is likewise not a regression. When a regression fires the account moves to `DEACTIVATED`, and no second deactivating enforcement action is minted alongside the action being expired, so `deactivation_count` — which counts deactivating actions rather than deactivated states — is left unchanged; otherwise the account is restored to `ACTIVE`. **Both branches decrement `standing_enforcement_count` by exactly one**, because the expired action has left the standing set that counter is read from, and both recompute the account's derived counters and recalculate the safety posture, and the sweep increments the account's `version` by 1. The sweep is idempotent in the sense that re-running it cannot mint a further action: the one action it expired already carries the outcome the ledger preserves. Three rejections guard it: a stale `expected_account_version` yields `ERR_STALE_VERSION` (`412`), an account carrying an in-flight appeal yields `ERR_IN_FLIGHT_APPEAL` (`409`), and an account not in a state from which the sweep is declared yields `ERR_INVALID_STATE` (`409`) — as does an account that carries no `ACTIVE` action whose `expires_at` has arrived. The in-flight-appeal reading is made against the account's *other* standing deactivating actions, not the one being expired: the expiring action is itself standing at that instant and carries the `ACTIVE` outcome this sweep exists to expire, so counting it would refuse every legitimate sweep. The sweep is declared from an account whose `status` is `RESTRICTED` and which carries an `ACTIVE` action whose `expires_at` has arrived.

The **periodic review round** is the gentler counterpart, also run by a `SafetyOperationsLead` and also keyed on `account_id`. Every action at or past its `review_due_at` receives `review_due_at` advanced by 180 days, and `effective_at` is left untouched so the effective date of the restriction remains auditable. Re-checking one action also re-checks its peer: the enforcement action on the same account whose `effective_at` is strictly earlier receives its own 180-day advance. The round then re-evaluates whether the account should appear in the next consumer safety report; an account whose `deactivation_count` has fallen below 2 is dropped from the queue, and the projection reports only the actions it ticked.

Driver screening runs on its own cadence. A `BackgroundReviewer` acknowledges a due review when the current instant has reached its `scheduled_due_at` minus the region's continuous-monitor acknowledgement deadline, which moves the record from `SCHEDULED` to `IN_REVIEW` and decrements the region's unacknowledged-review count. A review may only be acknowledged and adjudicated from `SCHEDULED` and `IN_REVIEW` respectively, and any other starting state is refused with `ERR_INVALID_STATE` (`409`). Adjudication then supplies an `adjudication` of `CLEAR`, `ADVERSE` or `INCONCLUSIVE` and, for an adverse verdict, an `adverse_reason_code`. An adverse verdict arriving without a reason code is refused with `ERR_ADVERSE_REASON_REQUIRED` (`422`). The verdict stamps `completed_at`, and its effect on the account is asymmetric: `CLEAR` subtracts 15 from the account's risk score floored at 0, `INCONCLUSIVE` adds 30, and `ADVERSE` makes the account deactivation-eligible by moving its `status` to `DEACTIVATED` and incrementing `deactivation_count` — subject to the same in-flight-appeal and monthly-cap refusals that guard the decision path, surfacing as `ERR_IN_FLIGHT_APPEAL` (`409`) and `ERR_MONTHLY_REPORT_CAP_REACHED` (`422`) respectively. Every verdict recomputes the aggregate of each cluster the account is attributed to; an `ADVERSE` verdict re-propagates the account's risk score, while the `CLEAR` and `INCONCLUSIVE` adjustments sit outside the propagation rule, are applied on top of the account's current `risk_score` between the 0 and 1000 bounds, re-derive the tier from that adjusted figure with the severity escape hatch, and then re-evaluate the watchlisted-to-`BANNED` purge edge of §3.5 against the adjusted tier.

The **rescreen sweep**, run by a `SafetyOperationsLead`, raises a fresh `SCHEDULED` review for each account whose projected cadence due date has passed, but only for accounts whose `status` is `ACTIVE`, `RESTRICTED` or `UNDER_HOLD` and whose `account_type` is `DRIVER`. The projection anchors on the account's most recent completed review — the `COMPLETED` row with the greatest `completed_at`, ties broken by `created_at` ascending — or on the account's `created_at` when no completed review exists, and adds to that anchor the per-drift-step refresh interval multiplied by the drift step, where the per-drift-step refresh interval is 548 days and the drift step is the floor of one third of the generation index minus one, with the generation index being the region's current review generation. The sweep also sets the account's `three_year_drift_last_run_index` to the current generation index and bumps the account's open `CONTINUOUS_MONITOR` record's `monitor_generation`, and the review history can be filtered by `triggered_by_incident_id` alongside `account_id`, `check_kind` and `check_status`.

### 3.9. Regional Policy Revision and the Trip Ledger

A `PlatformAdmin` provisions each region's threshold record. Creation supplies `region_code` and `sd_floor_severity` and may supply any of `sd_floor_enabled`, `rollup_window_days`, `rollup_threshold`, `cluster_watchlist_threshold`, `cluster_purge_threshold`, `escalation_enabled`, `expedite_appeal_baseline_count`, `expedite_review_days`, `standard_review_days`, `appeal_window_days`, `rescreen_refresh_days`, `continuous_monitor_ack_deadline_days`, `review_generation_index` and `knob_generation_index`; every omitted value takes its documented default, and every existing account in the region receives the new record's generation index. Each policy record begins at and stays at the single lifecycle state `PUBLISHED`. Revision is version-protected: it requires `expected_policy_version` and refuses a stale one with `ERR_STALE_VERSION` (`412`), addressing the case where a later patch has already legitimately moved a periodicity knob since the administrator last read the region. A revision may carry any of `sd_floor_severity`, `sd_floor_enabled`, `rollup_window_days`, `rollup_threshold`, `cluster_watchlist_threshold`, `cluster_purge_threshold`, `escalation_enabled`, `expedite_appeal_baseline_count`, `expedite_review_days`, `standard_review_days`, `appeal_window_days`, `rescreen_refresh_days` or `continuous_monitor_ack_deadline_days`, and every patched quantity must be a non-negative integer or a boolean, with a patched `sd_floor_severity` taking one of the severity band spellings `S1` through `S4`. A revision that patches any of the periodicity knobs advances the region's review generation and also steps the logical clock forward by one day. The segregation-of-duties floor is the one knob pair that reaches into the appeal path: the floor refusal in §3.6 fires only while the region's segregation arm is enabled and its floor severity sits at or below the incident's own band. There is also a bulk generation-advance capability, keyed on `region_code` and an `advance_counter` naming which counter to move, which increments that counter by one and then re-stamps every member account's generation, re-anchors every member background check, bumps each account's open continuous-monitor `monitor_generation`, and recomputes and re-stamps every cluster in the region. Only the exact `knob_generation_index` spelling advances the knob counter; an `advance_counter` value the platform does not recognise advances the review generation instead.

Trip records supply the account-level rehabilitation ledger that reinstatement depends on. A trip is requested between a `rider_account_id` and a `driver_account_id` in a `region_code`, with a `requested_at` dispatch instant supplied from the logical clock, plus optional `in_app_message_count` and `law_enforcement_contact_logged` facts, which default to 0 and false respectively when omitted; it starts at `REQUESTED` with `completed_at` left null. A `Driver` signals completion by moving the trip to `COMPLETED_PENDING`, which is permitted only when the acting driver account is the trip's `driver_account_id` and that account's `status` is `ACTIVE` or `RESTRICTED`; a caller who is not the trip's owning driver holds no authority over the resource and is refused with `ERR_UNAUTHORIZED` (`403`), while an owning driver whose account is in a state that is not completable is refused with `ERR_INVALID_STATE` (`409`). Completion itself requires the trip to sit at `COMPLETED_PENDING`, stamps `completed_at` from the logical clock, decrements **both** member accounts' risk scores by 2 floored at 0, and recomputes `rehabilitation_credit` for each open enforcement action of both accounts — the same recomputation the decision and appeal paths depend on. The 2-point trip credit sits outside the propagation rule, so the account's projection is re-derived first and the credit is then applied on top of it, with the tier re-read from the credited score. Completion also re-evaluates the region rollup threshold for each of the two accounts. Cancellation belongs to a `Rider`, requires the trip to still be `REQUESTED`, requires the acting rider account to be the trip's `rider_account_id` — a caller who is not that rider is refused with `ERR_INVALID_STATE` (`409`) — and moves the trip to `CANCELLED` while leaving `completed_at` null; `CANCELLED` and `COMPLETED` are both terminal for a trip, and a trip's lifecycle runs `REQUESTED` → `COMPLETED_PENDING` → `COMPLETED`, or `REQUESTED` → `CANCELLED`.

Finally, the region-level summary read filters on `home_region_code` and reports `region_count`, `incident_count`, `decided_count`, `mandatory_reportable_count`, `monetary_placeholder_count` and `newest_incident_created_at` across the incidents the caller can see. Accounts themselves are provisioned by a `PlatformAdmin` with an `account_type` of `RIDER` or `DRIVER`, a `home_region_code` that is immutable after creation, a `legal_name` and a `contact_email` whose uniqueness scope is the email together with the home region. A new account starts at `status` `ACTIVE` with `safety_posture` `OPEN`, `risk_score` 0, `risk_tier` `TIER_LOW`, `standing_enforcement_count` 0, `deactivation_count` 0 and `prior_reinstatement_count` 0; its `policy_generation_index` is stamped from the region's policy and `three_year_drift_last_run_index` is initialised to that same value. Driver accounts additionally receive a synthesised `CONTINUOUS_MONITOR` background check with `trigger_source` `CONTINUOUS`, `check_status` `SCHEDULED` and `adjudication` `PENDING`, its `monitor_generation` stamped from the region policy's generation at creation and its `scheduled_due_at` stamped 548 days after the account's `created_at`, so the acknowledgement window derived from it is a well-defined instant.
