# Surplus-Imperfect-Produce-Dynamic-Box API — Product Requirements Document

## 1. Introduction

Nobody plans a surplus market into existence. A grower over-orders on a melon variety the retail chains will not accept at full grade; a packer's cold room fills with fruit that is cosmetically inconsistent but perfectly edible; a broker offers a short-dated pallet of yogurt that must move within days. This platform exists to turn that irregular, opportunistic supply into a dependable weekly box for the subscribing household — and to do it without promising the customer a specific list of items, because the list of items simply does not exist until the lots are actually procured. The product therefore commits to a *value* proposition — weight, units, preference shape, and a defensible price comparison against conventional retail — rather than to a catalogue.

The system spans four communities of users. Households register, choose a service region and a delivery cadence, and receive a box each service cycle; they may skip a cycle, pause, or cancel, and may claim a credit when something arrives spoiled. Suppliers offer surplus, off-spec, short-dated or cosmetically imperfect lots, bid against lots that procurement has opened for award, and can withdraw a bid that has not yet been awarded. Fulfillment operators at regional centers inspect arriving lots, build each box out of what was actually procured against the customer's declared allergies and preferences, and pack it with the insulation and coolant that the destination lane and season demand. Platform administrators run the sourcing allocation, substantiate the retail price comparison for every item shown to a customer, adjudicate quality claims, and configure center capacity.

Because the supply picture changes hour by hour, the domain is governed by a small number of hard, interlocking rules rather than by rigid catalogues: a lot may only enter a box after it has cleared make-ready quality inspection; a box may only be built while its owning fulfillment center's derived forward posture is open; every customer-facing price must be traceable to a captured conventional-retail reference; and every one of these decisions must survive an operations team where multiple writers touch the same rows at once. The sections that follow specify those rules precisely enough that an implementation, a test suite, and an operations runbook all agree on the same behaviour.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two identifying headers: `X-User-ID`, which names the acting principal, and `X-User-Role`, which declares the capacity in which that principal is acting. Four roles exist — `Customer`, `Supplier`, `FulfillmentOperator` and `PlatformAdmin` — and the client may also address the API with `X-User-Role` set to `Anonymous`, which is a recognized value rather than a missing one. If either header is absent, if the role is not one of the recognized five values, or if an entity-backed identifier does not resolve to a stored row, the request is refused with `ERR_UNAUTHENTICATED` and HTTP status 401.

The header pair is not merely a label: for three of the four roles it is the ownership key. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Customer`; ownership checks on any resource that references a `Customer` compare the resource's `customer_id` field to `X-User-ID`, and the rows so governed are `BoxOrder` and `Subscription`. When `X-User-Role` is `Supplier`, `X-User-ID` is the `id` of the acting `Supplier`; a `SourcingBid` whose `supplier_id` equals `X-User-ID` is that supplier's own bid, and a `SupplyLot` addressed through the supplier-scoped listing path must belong to that supplier as well. When `X-User-Role` is `FulfillmentOperator`, `X-User-ID` is the `id` of the acting `FulfillmentCenter`; a `BoxOrder` whose `fulfillment_center_id` equals `X-User-ID` is within that operator's scope, and the operator acts for that center's lane. By contrast, when `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity: the server may record it as an audit value on rows an administrator mutates, but it is never compared against any entity's `id`.

An authenticated caller whose role is not permitted for the operation, or an entity-backed caller acting on a resource it does not own, is refused with `ERR_UNAUTHORIZED` and HTTP status 403. To be concrete about the carve-outs: finalising an order, filing a claim against a build item, and skipping, pausing, resuming or cancelling a subscription are operations reserved to the owning `Customer`; placing a bid and withdrawing one are reserved to the bidding `Supplier`; building and packing a box are reserved to the `FulfillmentOperator` of the owning center. Registering a subscriber is open to `Anonymous` and to `PlatformAdmin` alike.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` query parameter giving the maximum number of rows to return, and an `offset` query parameter giving the number of rows to skip before the first returned row. When `limit` is omitted it defaults to 10, and it accepts a minimum of 1 and a maximum of 100 — a value outside that range is a malformed request. When `offset` is omitted it defaults to 0. Unless a specific rule says otherwise, every list endpoint returns its rows ordered by their creation timestamp in ascending order, which means the oldest matching row comes first; the per-lot quality-claim listing and the per-order build-item listing follow that same creation-ascending rule as the global listings.

List responses publish four pagination fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count` and `has_more`. The `total_count` is the number of rows matching the filter before pagination is applied, and `has_more` reports whether at least one matching row exists beyond the returned window.

### 2.4. The Logical Clock

Every deadline, window, expiry and shelf-life rule in this system reads a single server-side logical clock rather than wall-clock time. Before any clock-setting call is made, that clock reads exactly `2026-09-01T00:00:00Z`, and it never falls back to the host's real time under any circumstance — a test harness or an operations replay can therefore place the system at an arbitrary instant and receive fully deterministic behaviour. An administrator advances or rewinds the clock by supplying a `to_iso8601` instant, and the call reports the resulting value back as `current_utc`. Because order cutoffs, build windows, subscription skip windows, claim windows and the lot expiry of every awarded lot are all computed against this value, a single clock call moves the entire system consistently.

### 2.5. Common Resource Properties and Precision

All eleven top-level resources — `Customer`, `FulfillmentCenter`, `Supplier`, `SupplyLot`, `SourcingBid`, `ConventionalQuote`, `BoxOrder`, `BoxBuildItem`, `ColdChainPack`, `QualityClaim` and `Subscription` — carry an `id` that is a server-minted UUID with no type prefix or other decoration. Every one of them also carries a `created_at` value, an ISO 8601 UTC timestamp rendered with three fractional digits. Beyond that pair the resources diverge: ten of the eleven additionally carry an `updated_at` timestamp in the same three-fraction-digit ISO 8601 UTC form, refreshed on every mutation, and a `version` integer that increments by one on every mutation of the row. The lone exception is `ColdChainPack`, which is created once and never modified: it carries `id` and `created_at` only, and has neither an `updated_at` nor a `version` field.

Monetary amounts are integers in cents throughout — `unit_cost_cents`, `display_price_cents`, `line_price_cents`, `conventional_total_cents`, `subtotal_cents`, `tax_cents`, `service_fee_cents`, `shipped_total_cents`, `order_discount_cents`, `lines_total_cents`, `credited_cents`, `requested_credit_cents`, `credit_cents_issued`, `allocation_used_cents`, `allocation_credited_cents`, `bid_unit_cost_cents` and `conventional_unit_price_cents` are all whole-cent integers, and no monetary value is ever carried as a decimal string. Where a rule multiplies a cents figure by a fractional rate, the product is computed at full precision and then rounded half-up to two decimal places, and every such rounding is applied once, at the point the rule names — never accumulated across intermediate steps. Quantities that are naturally integral — `unit_weight_grams`, `billed_unit_weight_grams`, `cold_item_weight_grams`, `weight_total_grams`, `units`, `quantity_available`, `quantity_offered`, `shelf_life_days`, `lane_transit_days` and `coolant_units` — remain integers, with any fractional intermediate rounded upward to the next whole unit where the governing rule calls for a ceiling. Weight-bearing decisions are always made in grams.

### 2.6. Regional Assignment and Center Pinning

A `Customer` names a `service_region` drawn from the four-region enumeration `NE`, `MW`, `SO` and `WE`, and each `FulfillmentCenter` likewise declares the `region` it serves; several active centers may share one region. When a customer is registered without an explicit `home_fulfillment_center_id`, the platform assigns one: the eligible set is every `FulfillmentCenter` whose `is_active` flag is true and whose `region` equals the customer's `service_region`, that set is ranked by `code` ascending, and the first row in that ranking becomes the customer's home center. The rule is a least-loaded-then-code fill: because each successive customer of a region takes the lowest-coded active center first, load spreads across the whole region over time — and a region that contains exactly one active center therefore receives every customer of that region. If the eligible set is empty, registration is refused with `ERR_NO_CENTER_AVAILABLE` and HTTP status 422. A customer who does supply `home_fulfillment_center_id` explicitly has that value honoured as given, and it is never rewritten afterwards by any rule, including a later re-run of the regional rule.

The regional rule also fires when an administrator mutates a center: updating a fulfillment center's configuration re-evaluates the assignment for every `Customer` of that center's region, so a center turned inactive, or added to a region, immediately re-spreads that region's subscribers. Whenever a customer's home center changes by any means, every `Subscription` belonging to that customer is re-pinned to the same new center, and the subscription's own `home_fulfillment_center_id` is stamped from the customer's.

A fulfillment center is configured by an administrator at creation with a human-readable `code` that is unique across all centers, a display `name`, the `region` it serves, an `insulation_profile` describing the grade the center stocks — one of `LIGHT`, `MEDIUM` or `HEAVY` — and a `max_concurrent_building_cycles` capacity that must be a whole number of at least 1 and at most 100, defaulting to 1 when it is not supplied. The `is_active` flag defaults to true and governs whether the center accepts new assignments and new orders. A centre is born with `forward_posture` at `OPEN`, its `serving_cycle_index` at 0 and its `open_claim_count` at 0. Reconfiguration is an update to an existing center and carries a `expected_fulfillment_center_version` alongside whatever of `is_active`, `insulation_profile` and `max_concurrent_building_cycles` the administrator is changing; the same version field is required when an administrator rolls the center's build cycle forward.

### 2.7. Fulfillment-Center Forward Posture

Each fulfillment center carries a derived aggregate called `forward_posture` whose value is one of `OPEN`, `CONSTRAINED` or `DEGRADED`, and that single derived value is the gate on all build and pack activity at the center. It is driven by one counter and one counter only: `serving_cycle_index`, the number of owning cycles currently in `BUILDING` status at that center. A center holding fewer such cycles than its `max_concurrent_building_cycles` sits at `OPEN`; a center whose `serving_cycle_index` has reached exactly the cap sits at `CONSTRAINED`; and a center whose `serving_cycle_index` has passed the cap — that is, is at least one greater than it — sits at `DEGRADED`. The separate `open_claim_count` field on the same center counts `QualityClaim` rows at that center whose status is `IN_REVIEW` or `UNDER_REVIEW`; it is a reported derived figure and does not move the posture.

The transitions between these three postures are automatic. When the counter reaches the cap the posture moves from `OPEN` to `CONSTRAINED`, and when the counter falls strictly below the cap it moves back from `CONSTRAINED` to `OPEN`. When the counter passes the cap the posture moves from `CONSTRAINED` to `DEGRADED`, and when it falls back to exactly the cap the posture returns from `DEGRADED` to `CONSTRAINED`. Two consequences of this arrangement are deliberate and must not be smoothed over. First, `CONSTRAINED` is a throttling posture, not a stop posture: opening a new order and starting a build at a `CONSTRAINED` center are both refused by the posture permit rule described in §3.4, but finalising an order remains admitted at a `CONSTRAINED` center precisely so that the counter can still be advanced and the center worked back down toward `OPEN`. Second, an order that was rerouted out of a center that subsequently recovers does not come back on its own — rerouted orders remain `REROUTED` and there is no automatic return to `READY_TO_BUILD`.

### 2.8. Allocation, Selector and Ranking Rules

Wherever the system has to choose among several eligible rows, the choice is deterministic, and it is deterministic because every ranking is expressed as an ordered list of sort keys ending in a stable tie-break. The lot selector that fills boxes ranks eligible lots by preference-tag specificity in descending order, then by `shelf_life_days` in descending order, then by `unit_cost_cents` in ascending order, and finally by `created_at` in ascending order — so the most specific match wins; among equally specific matches the one with the longest remaining shelf life wins; among those the cheapest wins; and any remaining tie is settled by first-created. No identifier ever participates in an observable decision, so the same inputs always produce the same box.

Alongside the ranking, the box-fill allocation is capped. The preference share of a box is the smallest whole number of units that is at least sixty per cent of the box unit target, which is 6 units; the filler share is the smallest whole number of units that is at least twenty per cent of that target, which is 2 units; and the specialty share is whatever remains of the target after those two shares are subtracted, which is 2 units. The shares are drawn in the fixed order preference-set, then preference-any, then filler, then specialty; each class takes no more than its own cap plus whatever quota earlier classes left unspent, and any shortfall a class cannot fill carries forward to the class after it. Because the caps are computed by ceiling rather than by exact division, the shares can sum to less than the pool, and the final class absorbs that rounding remainder — a specialty selection can therefore carry up to two units more than its nominal twenty per cent share.

### 2.9. Retail-Price Substantiation

Every per-item price shown to a customer is anchored to conventional retail, and the anchor is evidence rather than assertion. A `ConventionalQuote` records one captured reference: the `retailer_label` it came from, the `source_url` it was captured at, the `captured_at` instant, the `conventional_unit_price_cents` observed, the `barcode_gtin` consulted, and the `grade_equivalent` flag stating whether the comparable unit was the same procurement grade as the lot. The `barcode_gtin` must be exactly fourteen digits; a value of any other length is a malformed request. Within a lot's quotes exactly one is designated primary: the `is_primary` flag is true on that one row and on no other, chosen by a deterministic rule so that the same evidence set always yields the same primary.

Substantiation is assessed per lot, not per quote. The lot's `source_count` reports how many substantiating sources it has, capped at the substantiation maximum of three, and the lot's `substantiation_status` is `SUBSTANTIATED` only when both of the following hold: the lot has at least one source whose `grade_equivalent` flag marks it as being of the lot's own procurement grade, and it has no more than three sources in total. A lot with a `ConventionalQuote` on file that has no same-grade source, or that has more than three sources, fails substantiation, and that failed assessment is refused with `ERR_SUBSTANTIATION_REQUIRED` and HTTP status 422. While a lot remains `UNSUBSTANTIATED`, no display-price comparison on it is treated as substantiated. A lot carrying no quote at all is not refused — it simply has no comparison to substantiate, and the display-price rule falls back to its conventional-grade basis as described in §3.1.

### 2.10. Optimistic Concurrency Control

Two write operations in this system are protected by an explicit optimistic concurrency check, and the mechanism is identical in both. A client that has read a row captures its current `version`; when it later writes through a protected operation it must supply that captured value as a non-optional request field, and the server compares it against the parent row's `version` as it stands at the moment of the write. If the two are equal the write proceeds. If they differ — because some intervening transition has legitimately advanced the row since the client's last read — the request is refused before any state change is applied, and no partial mutation is left behind.

Skipping a subscription is the first protected operation. A skip request must carry `expected_subscription_version`, holding the `Subscription` version the client last observed. If the subscription's plan has moved on since that read — through a resume, a pause, or a server-side auto-skip that changed the row — the supplied value no longer matches the subscription's current `version`, and the request is refused with `ERR_STALE_VERSION` and HTTP status 412. Finalising a box order is the second protected operation. A finalise request must carry `expected_box_order_version`, holding the `BoxOrder` version the client last observed, and a value that no longer matches the order's current `version` — because a build or a reprice has rewritten the order's pricing and readiness fields since the client captured its view — is likewise refused with `ERR_STALE_VERSION` and HTTP status 412.

The check is confined to those two operations. Endpoints not named here do not accept a version field in their request body and do not perform this comparison, even when they target the same entity by identifier; an implementation that demands a version on an unprotected operation, or that silently ignores a supplied one on a protected operation, diverges from this specification.

## 3. Business Logic & Workflows

### 3.1. Sourcing an Irregular Lot

A supplier is onboarded with a legal `name` that is unique across all suppliers and a `region` stating where it ships from, and it starts with `status` at `ACTIVE`, `reliability_score_bp` at 10000 and `relationship_status` at `PREFERRED`. A customer is registered with an `email` that is unique across all customers, a `full_name` used as the subscriber's display name, and the `service_region` and delivery preferences described in §2.6; the `dietary_allergy_codes` array defaults to empty and the `grandfathered_service_fee` flag defaults to false, so an ordinary household is registered with no allergies and no fee waiver unless it asks for them.

A supplier's offer begins life as a `SupplyLot`, and a lot is always born out of a relationship: it is listed against the supplier that is offering it, carrying that supplier's identifier in `supplier_id`, and it declares the lane it is being sourced into through `fulfillment_center_id`. The commercial description of the offer is short and blunt — `product_name`, a `category` from `FRUIT`, `VEGETABLE`, `DAIRY`, `BAKERY`, `PANTRY` or `BEVERAGE`, a `procurement_grade` from `OFF_SPEC`, `SURPLUS`, `SHORT_DATED` or `COSMETIC` explaining why the lot is discounted, `unit_weight_grams` for a single unit, `quantity_available` units currently on hand, and `unit_cost_cents` for one unit. The freshness picture is carried by `harvest_date` and by `expiry_date`, which the supplier declares at listing time. A single derived figure summarises that picture: `shelf_life_days` is the whole number of days between `harvest_date` and `expiry_date`, counting neither boundary day — so a lot harvested on the first of a month and expiring on the eleventh has a shelf life of nine days, not ten and not eleven. The lot also carries `ready_date`, the date the supplier promises it will arrive at make-ready inspection.

Two arrays shape every downstream matching decision. `allergen_codes` lists the allergen codes present in the lot; it defaults to an empty array when omitted, and an empty array means the lot is allergen-free. `preference_tags` lists the preference tags the lot is capable of satisfying. Both arrays are stored sorted ascending, and comparisons against them are performed on that sorted form. A lot is `preference_eligible` exactly when `preference_tags` holds at least one element; a lot with no tags at all is not eligible to satisfy a preference, though it may still serve as filler. A new lot starts with `quality_status` of `PENDING_INSPECTION` and a procurement `status` of `QUOTED`, and its `arrived_at` is null until the lot actually enters make-ready inspection; the stamp is written at that point and never before.

Because a lot is procured before it is ever sold on, the make-ready gate is the first of the domain's two hard quality thresholds, and nothing about the lot is trustworthy until it clears. Inspection is run by an administrator, who supplies a `quality_outcome` and may either supply an `arrived_at` instant or leave the server to stamp the current logical clock, and who must supply `expected_supply_lot_version` matching the lot's version. On a passing outcome the lot's `quality_status` becomes `PASS` and its procurement `status` advances to `READY`, which is the state that makes it drawable into boxes at all; on a failing outcome the `quality_status` becomes `REJECTED` and the lot never enters the build pool. Only a supplier whose administrative `status` is `ACTIVE` can carry a lot through inspection — a suspended supplier's lots are refused — and the inspection is also refused whenever any quality claim citing a lot belonging to the same fulfillment center is still in `UNDER_REVIEW`, because an open investigation at a lane blocks new throughput at that lane. Both refusals are state refusals and carry `ERR_INVALID_STATE` with HTTP status 409.

The `quality_status` dimension is derived and moves beyond that initial gate. A lot that is `PASS` may be pushed into `INVESTIGATION` when a rejected review decision cites a build item drawn from it and no other claim citing the same lot is already under review, and it returns from `INVESTIGATION` to `PASS` when that investigation's claim is later upheld. The terminal quality outcome is `REJECTED`, reached when a claim citing a lot already in `INVESTIGATION` is upheld a second time — and that event is catastrophic for the supplier: every lot belonging to the same supplier and the same lane whose procurement `status` is still `QUOTED` or `AWARDED` is expired at the same moment, and those expirations feed straight back into the supplier's reliability score. Every one of these quality transitions also recomputes the lane's open claim count, which in turn refreshes that center's forward posture.

Supplier standing is computed, never set by hand, and it is recomputed on three occasions: when a lot clears make-ready, when a lot is awarded, and when a claim is reviewed. Four lifetime counters on the supplier feed it — `lots_awarded_total`, `lots_accepted_total`, `lots_on_time_total` and `claims_upheld_total`. An awarded lot counts toward the first; it counts toward `lots_accepted_total` once it clears make-ready quality inspection; and it counts toward `lots_on_time_total` only when its `arrived_at` is not after the `ready_date` the supplier promised. The score itself is `reliability_score_bp`, expressed in basis points on a 0–10000 scale, and it is the weighted sum of three ratios each rounded half-up to a whole basis point before weighting: on-time performance worth forty per cent, computed as ten thousand times `lots_on_time_total` divided by `lots_awarded_total`; acceptance worth forty per cent, computed as ten thousand times `lots_accepted_total` divided by `lots_awarded_total`; and quality worth twenty per cent, computed as ten thousand times the difference between `lots_accepted_total` and `claims_upheld_total`, divided by `lots_accepted_total`. When `lots_accepted_total` is zero the quality ratio has no denominator and is pinned to ten thousand rather than being treated as undefined, so a brand-new supplier is never punished for having no acceptance history. The resulting score maps to `relationship_status`, and the mapping is strict at every boundary: at or above 9000 basis points the supplier is `PREFERRED`; at or above 7500 but below 9000 it is `STANDARD`; at or above 6000 but below 7500 it is `ON_WATCH`; and strictly below 6000 it is `SUSPENDED`.

### 3.2. Bidding, Award and the Fork-Join

A supplier that wants a lot places a `SourcingBid` against it, naming the lot in `supply_lot_id`, naming itself in `supplier_id`, and stating `bid_unit_cost_cents` for one unit and `quantity_offered` units. Every new bid enters `PENDING`. Bids are grouped by lot, and a lot's bid set is the pool that the sourcing allocation works over. A supplier may withdraw a bid it no longer stands behind, and withdrawal is permitted from either `PENDING` or `SHORTLISTED`, but a shortlisted bid may only be withdrawn while no award has actually been executed against the owning lot — once the award has run, the shortlist is frozen. Withdrawing moves the bid to `WITHDRAWN`, which is terminal, and a shortlisted bid that leaves the shortlist frees the supplier to bid on a future lot instead. Withdrawing a bid that is already `SELECTED`, `NOT_SELECTED` or `WITHDRAWN` is a state refusal carrying `ERR_INVALID_STATE`.

Award is where the fork-join lives, and it is the most intricate single operation in the domain. The administrator running it supplies a `bidder_quota` and an `expected_supply_lot_version`, and the operation first requires that the lot be in `AWARDED` status. When the lot is not in `AWARDED` — because the award has already been run, or because the lot never advanced past `QUOTED` — the operation does not fail; instead the erroneous attempt is recorded as a non-selected outcome, the bid observed moving from `PENDING` to `NOT_SELECTED` and the lot itself left with no mutation whatsoever. What the award does to the lot's `status` depends on the quota.

With a `bidder_quota` of exactly 1, the allocation shortlists a single bid, moving it from `PENDING` to `SHORTLISTED`, and because the shortlist has exactly one member that member is immediately and automatically joined through to `SELECTED`. With a `bidder_quota` of 2 or more, up to `bidder_quota` bids are moved from `PENDING` to `SHORTLISTED`, and then the shortlist is resolved: the highest-ranked bid by the allocation selector's ordering joins to `SELECTED` in a `SHORTLISTED` to `SELECTED` move, while every other shortlisted bid moves from `SHORTLISTED` to `NOT_SELECTED` and its supplier is freed to bid again on a future lot. Both of these branches require the lot to be in `AWARDED` status, and the top-ranked branch additionally requires that the bid really is the highest-ranked member of the shortlist. Whenever a bid is selected — whether by the sole-bid join or by the ranked join — the lot's own procurement `status` advances to `READY`. Note the asymmetry that an award carries for the two participating entities: selection moves the bid forward and moves the lot to `READY`, whereas the losing branch changes the losing bid alone and leaves the lot untouched.

Advancing a lot from `QUOTED` to `AWARDED` is itself the act of opening it to bids, and it requires at least one bid on the lot to still be in `PENDING`. That single transition does four things at once. It recomputes the lot's `expiry_date` from the award shelf-life matrix and from `shelf_life_days`, which is a genuine rewrite of the supplier's declared expiry based on what the awarded lot actually is rather than what was promised. It cascades that recomputation into the subscription shelf-life rule, so an awarded lot with a shelf life strictly below the subscription shelf-life floor immediately pushes every `ACTIVE` subscription of that lane into `AUTO_SKIPPED`. It moves up to `bidder_quota` bids from `PENDING` to `SHORTLISTED`. And it moves every remaining `PENDING` bid on the lot to `NOT_SELECTED`. Awards are protected writes: the supplied `expected_supply_lot_version` must equal the lot's current version, and a mismatch is refused with `ERR_STALE_VERSION` and HTTP status 412 before any of the four effects above occur.

Two further gates apply to the award beyond the lot's own state. A bid can only be shortlisted if its supplier's administrative `status` is `ACTIVE`, and the withdrawal gate described above — that no award has yet been executed against the owning lot — is what protects a shortlisted bid from vanishing out from under an in-flight award.

### 3.3. Make-Ready Outcomes, Claims and the Credit Ceiling

Claims are filed by customers and adjudicated by administrators, and the adjudication loop is where the domain ties spoilage back to supplier behaviour. A customer filing a claim names the specific build item it is claiming against in `box_build_item_id`, gives a `reason_code` from `SPOILED`, `DAMAGED`, `MISSING_ITEM` or `TEMPERATURE_ABUSE`, attaches evidence as `photo_url`, and states `requested_credit_cents`. The evidence requirement is enforced as a shape rule rather than a judgement call: the `photo_url` path must end in one of the accepted image extensions `.jpg`, `.jpeg`, `.png`, `.webp` or `.heic`, and a claim whose evidence URL does not end in one of those is refused with `ERR_CLAIM_EVIDENCE_REQUIRED` and HTTP status 422. A claim cannot be credible if it asks for nothing: a `requested_credit_cents` of exactly zero is refused with `ERR_CLAIM_NOT_CREDIBLE` and HTTP status 422, and that check runs before any assessment of the cited lot's quality so that a zero-value claim is never able to influence the lot. A filed claim also carries a derived pointer back to the lot: `supply_lot_id` is derived from the claimed build item rather than supplied by the customer. The claim enters `IN_REVIEW`, and it freezes the lot's quality standing at the moment of filing into `cited_lot_quality_status`, so a later reviewer can see what the lot looked like when the customer complained rather than what it looks like at review time. Until a claim is upheld its `credited_cents` is zero, and `outcome` is null until a reviewer decides.

Reviewing a claim is a protected write by an administrator supplying an `outcome` of `UPHELD` or `REJECTED` together with `expected_claim_version`. The reviewer's decision does not always produce the obvious result, because the claim's age and the lot's history both participate. From `IN_REVIEW`, an upheld outcome requires that the cited build item still has status `INCLUDED` and that the cited lot's `quality_status` is `PASS`; when both hold, the claim moves to `UPHELD`, `credited_cents` is set by the credit rule below, the supplier's `claims_upheld_total` increments, and that increment cascades through `reliability_score_bp` into `relationship_status`. Also from `IN_REVIEW`, a rejected outcome does not simply close the claim — it moves the claim to `UNDER_REVIEW` when two conditions hold together: the claim's `created_at` is strictly more than the escalation window of seven days after the cited build item's `created_at`, and at least one other quality claim citing the same supply lot was upheld strictly earlier in time. That move pushes the lot's `quality_status` to `INVESTIGATION` and refreshes the lane's open claim count, which is how a single late complaint about a lot that has already burned another customer turns into a lane-wide investigation. Rejection also moves a claim to a plain close when the claim's `created_at` is at least the seven-day window ahead of the current logical clock — that is, when the claim is young enough that the escalation path did not open — leaving `credited_cents` at zero, leaving the cited build item `INCLUDED`, and writing no credit; a claim resolved this way reaches its terminal `CLOSED` state, which along with `UPHELD` and `REJECTED` is one of the three outcomes that end a claim's life. The two rejection branches are deliberately asymmetric: only the escalation branch touches the lot.

From `UNDER_REVIEW` the paths resolve. An upheld outcome there requires that the claim cite a box whose status is `PACKED` or `SHIPPED`, and on success the claim becomes `UPHELD`, the credit rule runs, the cited lot's `quality_status` returns to `PASS`, and `claims_upheld_total` increments — the investigation is closed out in the supplier's favour as well as the customer's. A rejected outcome there requires the cited lot's `quality_status` to be `INVESTIGATION`, and it leaves `credited_cents` at zero, drives the lot's `quality_status` to its terminal `REJECTED`, and refreshes the open claim count. A `REJECTED` claim is not necessarily finished: it may be reopened for a fresh review, which returns it to `IN_REVIEW` so that a new decision is required, but only while the cited lot's status is not `EXPIRED` — reopening a claim whose lot has already expired is refused with `ERR_INVALID_STATE`.

The credit ceiling is the part of adjudication that most often goes wrong, so it is worth stating exactly. Three ceilings are computed and the smallest of the three wins. The first is a per-reason unit credit: the flat figure for the claim's `reason_code` — 300 cents for `SPOILED`, 350 for `DAMAGED`, 300 for `MISSING_ITEM` and 400 for `TEMPERATURE_ABUSE` — multiplied by the number of `units` on the cited build item and then by a grade multiplier of 1.00 for `OFF_SPEC`, 1.00 for `SURPLUS`, 1.10 for `SHORT_DATED` and 1.15 for `COSMETIC`. The second is three quarters of the line's `line_price_cents`, rounded half-up to two decimal places. The third is the customer's request plus a grace allowance: `requested_credit_cents` plus whichever is smaller of `requested_credit_cents` and the 200-cent per-claim grace, which means a request of 100 cents can reach at most 200 cents and a request of 500 cents can reach at most 700 cents. The issued value, written to `credited_cents`, is the minimum of those three. The order in which the two caps are applied matters to the reconciliation report but not to the customer: the implementation takes the seventy-five-per cent line cap first and the grace ceiling second, so whichever of the two ceilings is lower is the one that binds, and a report that instead took the grace ceiling first and the line cap as a floor would be reporting the larger of the two ceilings rather than the one actually charged.

### 3.4. Opening, Finalising and Building a Box

A box order is opened for one customer against one service cycle. The request names the `customer_id`, the `subscription_id` the order is being generated for, a `serving_cycle_index` starting at 1 and increasing monotonically, and a `cuisine_preference` from `STANDARD`, `FRUIT_FORWARD`, `VEGGIE_FORWARD`, `BAKERY_FORWARD` or `PANTRY_FORWARD` that describes the flavour of box the customer wants. The order's fulfillment center is not supplied by the caller: it is copied from the customer's home center into `fulfillment_center_id`, and the `routing_region` used for lane selection mirrors that center's region. A new order starts in `DRAFT` with its pricing dimension at `UNPRICED`.

Two eligibility gates stand in front of order creation. The subscription feeding the order must not be `PAUSED` and must not be `CANCELLED`, and the order may not duplicate a `serving_cycle_index` that the same subscription has already produced — a second order for a cycle that is already covered is refused with `ERR_SUBSCRIPTION_INELIGIBLE` and HTTP status 409. The center's posture permit is the other gate, and it is the rule that gives the forward posture teeth: an order is refused with `ERR_CENTER_FORWARD_LOCKED` and HTTP status 409 unless the owning center's `forward_posture` is exactly `OPEN`. The same permit guards the start of a build. It guards finalisation as well on its face, but with the deliberate asymmetry that finalisation remains admitted at a `CONSTRAINED` center — only a `DEGRADED` center refuses it — because finalisation is what advances the center's counter and lets the center be worked back toward `OPEN`.

The window arithmetic is computed at creation and is expressed entirely in hours against the logical clock. A service cycle has a start instant, and the `ready_deadline` for an order is that start instant minus a regional cutoff lead: 36 hours in `NE`, 48 hours in `MW`, 48 hours in `SO`, and 60 hours in `WE`. The much-discussed `cutoff_met` flag is then simply the statement that the order's `created_at` is strictly before its `ready_deadline` — an order created at the deadline itself has not met the cutoff. The `build_deadline` is the cycle's start instant plus a build window of 72 hours, doubled to 144 hours when the owning center's posture is `DEGRADED`; an operation executing at exactly the deadline is still inside the window, so the comparison is inclusive on the far end. The `build_blocked` flag reports whether the owning center's posture is anything other than `OPEN`, which is the same condition the permit gate refuses on, surfaced as a readable attribute of the order. The cadence of the underlying subscription sets the cycle length: 168 hours for `WEEKLY`, 336 for `BIWEEKLY` and 720 for `MONTHLY`.

Finalising is the customer's commitment and it is the second of the two optimistic-concurrency-protected writes. The caller supplies `expected_box_order_version`, and a value that no longer matches the order's current version is refused with `ERR_STALE_VERSION` and HTTP status 412 — the correct outcome when a build or a reprice has rewritten the order's pricing and readiness fields since the client captured its view. With the version check satisfied, an order that missed its cutoff is refused with `ERR_ORDER_CUTOFF_MISSED` and HTTP status 422. A successful finalisation moves the order from `DRAFT` to `AWAITING_WINDOW`, and the move is a three-way cascade rather than a single write: it increments the owning center's `serving_cycle_index`, which is the counter that drives the center's forward posture toward `CONSTRAINED`; it advances the subscription's `serving_cycle_index` by one full cadence period; and it runs the pricing plan in both its provisional and its final reading, as described in §3.6. It also requires the owning center's posture not to be `DEGRADED` — an order at a degraded center cannot commit a cycle.

Finalising is also the act that reserves inventory, and the reservation is what the lane's serialisation rule protects. A lot that is `READY` is moved to `COMMITTED` when the finalisation draws on it, and the transition is admitted only while no `READY_TO_BUILD`, `BUILDING` or `REROUTED` order of that lot's fulfillment center still holds an unallocated remainder — the same lane-wide condition that governs promotion out of `AWAITING_WINDOW`, which is why a lane with one box already mid-build cannot let a second box commit against the same unallocated pool. A committed lot has its units reserved against the allocation plan, and the dollar figure each order draws is accumulated on the order as `allocation_used_cents`; the portion of that draw which a particular build line consumes is recorded on the line as `allocation_credited_cents`. When a build has consumed every unit a lot had, the lot moves from `READY` to `DEPLETED`, which requires that the lot's `quality_status` is `PASS` and again that no `READY_TO_BUILD`, `BUILDING` or `REROUTED` order of the lot's center holds an unallocated remainder; a depleted lot is removed from every future build candidate set. `COMMITTED` and `DEPLETED` are both terminal for the procurement dimension, as is `EXPIRED`, and those three are the states from which no lot ever returns to active sourcing.

An order waiting in `AWAITING_WINDOW` becomes buildable when the logical clock reaches its `ready_deadline`, and that automatic promotion requires that no `READY_TO_BUILD`, `BUILDING` or `REROUTED` order of the same center is carrying an unallocated remainder — the domain serialises the whole lane, not just the individual order, so that two boxes cannot both be built against the same unallocated pool. The promotion also recomputes the quality gate of every lot in the candidate set. An order that sits in `READY_TO_BUILD` until its `build_deadline` passes without any of its build items having status `INCLUDED` falls back to `DRAFT`, and the fallback is a full reversal of the finalisation cascade: it decrements the owning center's `serving_cycle_index` by one, decrements the subscription's `serving_cycle_index` by one full cadence period, and refreshes the center's posture.

Building the box is the fulfillment operator's operation, and it is the point at which procurement meets demand. The request carries `expected_box_order_version` and may carry an explicit `line_plan`. There are two entry paths and the specification pins both. When a `line_plan` is supplied it is honoured in the order given: each planned line is committed and priced in plan order, and any line that would take the running unit count past the box unit target of 10 is retired — moved to status `REMOVED` — immediately after the first pricing pass. That retiral is the only path by which a planned line leaves a box. When no plan is supplied, the class waterfall fills the box instead, drawing the preference-set, preference-any, filler and specialty classes in that fixed order with the caps described in §2.8, against a candidate pool restricted to lots in the order's fulfillment center whose `quality_status` is `PASS` and whose status is `READY`.

Both paths share a two-round placeholder mechanic, and getting its ordering right is the difference between a box that ships what it has and a box that discards stock it should have used. In the first round the box's visible placeholder is drawn before any other line is confirmed. The weight that round needs for a category is that category's placeholder base need — 1200 grams for `FRUIT`, 1200 for `VEGETABLE`, 900 for `DAIRY`, 800 for `BAKERY`, 600 for `PANTRY` and 2400 for `BEVERAGE`, and the base need is the sum of those figures over the order's unconfirmed placeholder lines — while the weight the lane is entitled to recall is that base need grossed up by the shortfall rate of ten per cent, so a recalled figure is the base need multiplied by 1.10. Round one commits units against that recalled figure, and the units it actually commits are the figure that will later be deducted. In the second round the residual need is filled from the same category pool under the four-clause eligibility sieve described below, and only after that residual fill is complete are the recalled units deducted from the pool. The order of those two steps is not a matter of taste: the specification pins the deduction to happen after the residual fill and not before it, so a legitimately drawable unit is never taken away by a recall that has not yet been satisfied. The deduction itself is capped, and the cap is the recalled weight minus the category's base need — which for the ten per cent shortfall rate means the deduction can never exceed the grossed-up allowance's increment over the plain base need. A build that instead deducted the recalled units before the residual fill would lose drawable units whenever a category pool is scarce, and the two approaches therefore differ exactly in the case where the category pool has been fully drawn: the pinned ordering keeps the last drawable units available to the residual fill, while the rejected ordering would strand them.

Whichever path is taken, the same eligibility sieve applies to every candidate lot before it can be drawn, and the sieve has four clauses that must all hold: the lot's `quality_status` is `PASS`; the lot has at least the minimum line quantity of 2 units available in `quantity_available`, so a single remaining unit is never enough to open a line; the lot's `allergen_codes` are disjoint from the customer's `dietary_allergy_codes`; and the lot's status is `READY`. The allergy clause is not merely a candidate filter — it is also enforced as a hard safety rule on the build and on finalisation, and a build or finalisation attempt that would place an allergen-bearing lot in a box for an allergic customer is refused with `ERR_ALLERGEN_CONFLICT` and HTTP status 422 rather than silently skipping the lot. A build that tries to draw from a lot that is not `PASS` is refused with `ERR_LOT_QUALITY_HOLD` and HTTP status 409. A build attempted before the box's deadline has passed is refused when the build deadline is already behind the logical clock, and a build attempted without the cutoff having been met, or from a state that does not admit a build at all — including an order in `CRASHED`, which admits no further build, pack or finalise transition whatsoever — is refused with `ERR_INVALID_STATE` and HTTP status 409.

A successful build moves the order from `READY_TO_BUILD` to `BUILDING`, creates up to six build items, and does three cascading things at once. Every included line decrements the source lot's `quantity_available` by the units it consumes, so the pool that later builds draw from is the pool that is actually left on the floor. Every included line freezes its billing weight at build time into `billed_unit_weight_grams`, which is the lot's `unit_weight_grams` clamped up to the per-category minimum billing weight — the clamped figure being the lot's `billing_weight_grams` when the placeholder pass needs a per-lot weight — 120 grams for `FRUIT`, 120 for `VEGETABLE`, 150 for `DAIRY`, 200 for `BAKERY`, 100 for `PANTRY` and 300 for `BEVERAGE` — so a light item is billed at its category floor rather than at its actual weight. Each build item also carries `category`, copied from the lot at build time, and an `item_type` recording how the line entered the box, which is `PREFERENCE` for a line that satisfied a preference tag, `FILLER` for one that filled out the weight, and `RETAINED` for a line that survived a retiral pass. The order's derived figures are recomputed in the same transaction: `lines_total_cents`, `weight_total_grams`, `subtotal_cents`, `tax_cents` and `shipped_total_cents`. The pricing dimension then moves from `UNPRICED` to `PRICED` on the first lines inserted, and it moves from `PRICED` to `REVISED` whenever a planned line is retired to `REMOVED` after the first pricing pass, at which point `lines_total_cents` re-derives from the `INCLUDED` lines alone and the difference is recorded through the provisional delta.

### 3.5. Rerouting, Crashed Builds and the Lane's Recovered Capacity

The lane is not a fixed resource, and the domain treats a center whose counter has passed its cap as a genuine operational failure rather than a queuing condition. When a center enters `DEGRADED`, three things happen in the same instant: new order creation and new build starts at the center are refused under `ERR_CENTER_FORWARD_LOCKED`; every box order at that center whose status is `BUILDING`, `READY_TO_BUILD` or `AWAITING_WINDOW` is moved to `REROUTED`; and every cold-chain pack belonging to those orders recomputes its `lane_transit_days` and re-selects its insulation grade and coolant load against the degraded lane.

Rerouting is not cosmetic, and the cascade differs by the state the order was in when it was struck. An order caught in `AWAITING_WINDOW` simply has `build_blocked` set to true and its cold-chain packs recomputed. An order caught in `READY_TO_BUILD` loses its work: every build item on it moves to `REMOVED`, the removals trigger a reprice, and the order's pricing dimension is left at `REVISED`. An order caught mid-flight in `BUILDING` loses its work as well, but with the additional and important consequence that every cited lot's `quantity_available` is restored by the units the removed lines had consumed — the inventory that was physically reserved comes back to the floor, and the order is left with `pricing_status` at `REVISED` and `lines_total_cents` at zero. Any order struck down by a center entering `DEGRADED` also has `build_blocked` set true.

A cold-chain failure is a separate and independently declared event, distinct from a lane capacity failure. An administrator may declare one against an order that is currently `BUILDING`, and the declaration requires that state explicitly: an order that is not `BUILDING` is refused, because the failure is a statement about a build that was in progress. The declared failure moves the order from `BUILDING` to `CRASHED` and sets `build_blocked` to true — but unlike the `DEGRADED` cascade, the crashed order keeps its build lines intact, and that retention is deliberate: a claim filed later needs a build item to cite, and a claim that cites a removed line cannot be reviewed against an `INCLUDED` item. An order in `CRASHED` is terminal for practical purposes: no build, pack or finalise transition is admitted on it, and an attempt is a state refusal carrying `ERR_INVALID_STATE`.

Recovery has two distinct shapes and they are not interchangeable. An order that was rerouted can be returned to the buildable pool by an operator once the owning center's posture is no longer `DEGRADED` and the order has met its cutoff, which moves it from `REROUTED` to `READY_TO_BUILD` and clears `build_blocked`. An administrator can instead send a rerouted order all the way back to `DRAFT`, which also clears `build_blocked` but discards the order's position in the window and requires it to be finalised again; the administrator path requires the owning center's posture not to be `DEGRADED`. Neither path is automatic. A center that climbs back from `DEGRADED` to `CONSTRAINED` re-admits new orders and new builds, but the orders that were rerouted out of it stay rerouted until someone walks them back deliberately.

Closing the loop on center capacity is an administrator operation: the center's build cycle is rolled forward by decrementing its `serving_cycle_index` to whichever is larger of zero and the counter minus one, and the decrement recomputes the forward posture from the new counter. That decrement is the counterpart of the increment that finalisation performs, and between them they are the only two ways the counter moves.

### 3.6. The Pricing Plan and the Conventional-Retail Comparison

Every price the customer sees has two bases, and keeping them apart is what makes the box arithmetic meaningful. The first is the cost basis, which is what the platform paid. The second is the billing basis, which is the weight the customer is charged for. A lot's `display_price_cents` is the per-item figure shown to a customer, and it is built out of the cost basis by resolving a grade, looking up a multiplier, and then applying a category floor. The grade that resolves is the lot's own `procurement_grade` when a quote on the lot carries `grade_equivalent` true, and it is `CONVENTIONAL` otherwise — which means that a lot whose evidence includes a same-grade reference is priced off the multiplier for `OFF_SPEC` (1.50), `SURPLUS` (1.60), `SHORT_DATED` (1.75) or `COSMETIC` (1.80), while a lot with only non-equivalent evidence, or with no evidence at all, is priced off the `CONVENTIONAL` multiplier of 1.40. The base figure is `unit_cost_cents` multiplied by that multiplier, rounded half-up to whole cents. The floor is `unit_cost_cents` multiplied by the category floor multiplier — 1.25 for `FRUIT`, 1.25 for `VEGETABLE`, 1.20 for `DAIRY`, 1.35 for `BAKERY`, 1.30 for `PANTRY` and 1.30 for `BEVERAGE` — and the displayed price is whichever of the base figure and the floor is larger. The practical reading of this rule is that a thin-margin category can never be sold below its floor, however low the resolved grade multiplier turns out to be.

The billing basis is a separate clamp. A build item's `billed_unit_weight_grams` is the lot's `unit_weight_grams` raised to the per-category minimum billing weight if it falls below it, and left alone otherwise; the category minimums are the same set used at build time — 120 grams for `FRUIT`, 120 for `VEGETABLE`, 150 for `DAIRY`, 200 for `BAKERY`, 100 for `PANTRY` and 300 for `BEVERAGE`. A line's `line_price_cents` is then the line's frozen billing weight multiplied by the lot's `display_price_cents` and divided by one thousand, rounded half-up to whole cents — the division by a thousand being the conversion from grams to a per-kilogram basis. Note that the raw `unit_weight_grams` is still available and is what the diagnostics and reconciliation views report, while the clamped figure is what the customer is actually billed; a report that used the raw weight would understate light items, and a build that billed the raw weight would undercharge them.

An order's merchandise total is computed in chronological plan order, line by line, and it exists in two readings because a planned line can be retired. The provisional reading sums `line_price_cents` over every line the build plan carried. The final reading sums `line_price_cents` over the lines whose status is `INCLUDED` only. The two readings differ by exactly the retired line's `line_price_cents`, and the difference is recorded as the provisional delta: the provisional figure overstates the total by precisely that one line's price, and the final figure is the lower of the two whenever any line is retired at all. The customer-facing total always uses the final reading; the delta exists so that operations can see that a plan changed. There is no path by which a single line's price is recomputed with a different formula at retiral — the line keeps the price it was given in the first pricing pass and is simply excluded from the final sum.

`weight_total_grams` is the sum of `billed_unit_weight_grams` over the `INCLUDED` lines, which means a removed line's weight leaves the order along with its price. From the merchandise total the order-level figures follow in a fixed sequence. `order_discount_cents` is a rate-based discount that is zero whenever the merchandise total is below the discount gate of 5000 cents, and is ten per cent of the merchandise total when the total has reached 5000 cents or more — the gate is inclusive, so a box landing exactly on 5000 cents does earn the discount. `subtotal_cents` is the merchandise total less that discount, and it is the only base against which sales tax is charged. `service_fee_cents` is a flat 599 cents, waived to zero for any customer whose `grandfathered_service_fee` flag is true. `tax_cents` is five per cent of `subtotal_cents`, and it is charged on the subtotal tier alone and never on the service fee. `shipped_total_cents` is the sum of `subtotal_cents`, `tax_cents` and `service_fee_cents` — the merchandise after discount, plus tax, plus the fee.

The conventional-retail comparison is the claim the whole product rests on, so it is weighted rather than averaged and it is deliberately generous to the customer. `conventional_total_cents` is the merchandise total multiplied by a quotient, and the quotient is the sum over the `INCLUDED` lines of each line's billing weight times its lot's primary-quote price, divided by the sum over the same lines of each line's billing weight times its lot's display price. In plain terms, the box's ordinary-retail equivalent is the box's own merchandise total scaled by how much more expensive the same weights were at conventional retail. The weightings matter: a heavy line moves the comparison far more than a light one, so the figure describes the box that was actually built rather than an unweighted list of items. The primary-quote price for a line is the `conventional_unit_price_cents` of that lot's primary quote. When a lot has no quote at all, the line's own `display_price_cents` is substituted for the missing quote price without any clamping, which neutralises that line's contribution to the ratio rather than inflating it, and the box's comparison figure is marked advisory. The product of the merchandise total and the quotient is rounded half-up to two decimal places once, at the end, and never rescaled afterwards.

### 3.7. Cold-Chain Selection and Packing

Packing is the moment the box stops being a list and becomes a shipment, and the load it must survive depends on where it is going and when. A cold-chain pack records the decision for one order: it names the order it belongs to in `box_order_id` and the center the lane runs from in `lane_fulfillment_center_id`, and it carries the derived figures `cold_item_weight_grams`, `insulation_grade`, `coolant_units`, `lane_transit_days` and `selection_status`. Exactly one pack exists for an order, it is created when the order is packed, and it never changes afterwards — a pack carries no `updated_at` and no `version`, and it is the one resource in the system that is genuinely immutable after creation.

The weight the lane must carry is not the box's total weight but the weight of the box's cold-chain-eligible items, being those whose category is `FRUIT`, `VEGETABLE` or `DAIRY`. To that sum a single frozen allowance is added: when a box contains no line outside those three categories at all — that is, when the sum of billing weights over every other line is zero — 250 grams is added to represent the thermal mass of the packaging that carries the perishables. A box with any non-cold line contributes no such allowance, and the allowance is never scaled or prorated; it is either 250 grams or it is absent.

Transit time is a function of the lane and of the center's condition. The base figure for the order's `routing_region` is 2 days for `NE`, 3 days for `MW`, 3 days for `SO` and 4 days for `WE`, and one full day is added when the lane's center is `DEGRADED`, because a degraded center routes its freight the long way round. The requirement itself is a threshold: cold-chain protection is required exactly when `cold_item_weight_grams` has reached 1200 grams or more. A box below that threshold needs nothing — its selection status is `NOT_REQUIRED`, its insulation grade is `LIGHT` and its coolant count is zero, and the cold-chain flag on the order still records that a pack was made for it.

Above the threshold the decision branches on the lane. A warm lane is one whose `routing_region` is `WE` or `SO` and whose `lane_transit_days` has reached the insulated minimum of 3 days or more; only those two regions are ever treated as warm. On a warm lane the insulation grade is `HEAVY` when the transit has reached 4 days or more, and `MEDIUM` when it has not, and in both cases the coolant count is the smallest whole number of units that is at least `cold_item_weight_grams` divided by 1500 grams — a ceiling, so any remainder at all costs an extra unit. On any other lane — which is to say a lane in `NE` or `MW`, or a `WE` or `SO` lane running in under three days — the grade is `MEDIUM` and the coolant count is exactly 2 units, regardless of the box's weight. One override sits on top of all of this: at a center whose posture is `DEGRADED` the coolant load is exactly doubled, so the 2-unit flat case becomes 4 and each ceilinged figure is multiplied by two. The doubled load is the counterpart of the extra transit day, and the two are applied together rather than as alternatives.

Packing an order is an operator operation and it is guarded by three requirements that must all hold. The order must currently be `BUILDING`, because only a built box has contents worth packing. The owning center's posture must not be `DEGRADED`. And the order's subscription must be in `ACTIVE`, `SKIPPED` or `AUTO_SKIPPED` — a `PAUSED` or `CANCELLED` subscription's order cannot be packed. A pack may happen at most once per service cycle, and packing an order that has already been packed for its cycle is refused with `ERR_ALREADY_ALLOCATED` and HTTP status 409; this single-use rule is what stops a box from being packed twice and shipping its inventory twice. A successful pack moves the order from `BUILDING` to `PACKED`, creates exactly one cold-chain pack, sets the order's `cold_chain_selected` flag to true, decrements the owning center's `serving_cycle_index` by one, and decrements the subscription's `serving_cycle_index` by one full cadence period — the pack is the counterpart of the finalisation that committed the cycle, and the pair is what keeps the counter honest. An order that has reached `PACKED` is terminal for the build dimension; the only state beyond it is `SHIPPED`, which the domain models as the far terminal state without a dedicated transition of its own.

### 3.8. Cadence: Skips, Auto-Skips, Pauses and Cancellation

A subscription is opened for a customer by an administrator, naming the `customer_id` and a `cadence` from `WEEKLY`, `BIWEEKLY` or `MONTHLY`; the cadence sets the length of a service cycle, at 168 hours, 336 hours and 720 hours respectively. The subscription is created in `ACTIVE` status with a `serving_cycle_index` of 1 and a `pause_count` of 0, and its `home_fulfillment_center_id` is copied from the customer rather than supplied. A subscription carries a `skipped_cycle_index` that is null when no skip is outstanding, a `skipped_on` timestamp recording when the most recent skip was written and null when none was, a `paused_at` stamp that is null while the subscription is not paused, a `resumed_at` stamp that is null until the subscription is first resumed, and a `cancellation_reason` that is null until the subscription is cancelled.

A customer may skip the next cycle while the subscription is `ACTIVE`. The skip request must carry `expected_subscription_version`, and this is the first of the two optimistic-concurrency-protected writes: a value that no longer matches the subscription's current `version` — because a resume, a pause or a server-side auto-skip has advanced the subscription's plan since the client read it — is refused with `ERR_STALE_VERSION` and HTTP status 412. A skip is also bounded in how far ahead it may reach: it is admitted only while the recorded `skipped_cycle_index` is less than the subscription's current serving cycle index plus four, which is to say that a skip may be recorded no more than three cycles beyond the cycle currently being served. A permitted skip moves the subscription from `ACTIVE` to `SKIPPED`, sets `skipped_cycle_index` to the serving cycle index plus one, stamps `skipped_on` with the current logical clock, and increments the subscription's version by one.

A skip may also be imposed by the platform rather than requested by the customer, and this is the cascade that the lot award triggers. When a lot is awarded whose `shelf_life_days` is strictly below the subscription shelf-life floor, every `ACTIVE` subscription of that lane moves to `AUTO_SKIPPED` and has `skipped_cycle_index` set to its serving cycle index plus one. The customer's complaint is not registered as accepted; it is registered as answered, because a box built from produce that will not survive the delivery window is worse than no box. An `AUTO_SKIPPED` subscription returns to `ACTIVE` automatically when the logical clock reaches the start of `skipped_cycle_index`, and that automatic return clears `skipped_cycle_index` to null. A `SKIPPED` subscription returns to `ACTIVE` on the same clock condition — or on an explicit resume — and clearing a customer-requested skip clears both `skipped_cycle_index` and `skipped_on` to null. The two returns are deliberately not identical: the automatic one clears only the cycle index, while the customer-requested one also clears the timestamp that recorded the request.

Pausing is available from three states and carries the same body of effects from each. Whether the subscription is `ACTIVE`, `SKIPPED` or `AUTO_SKIPPED`, a pause is admitted only while `pause_count` is strictly below the maximum pause hops, and on success the subscription moves to `PAUSED`, `pause_count` increments by one, and `paused_at` is stamped with the current logical clock. The `pause_count` field is bounded to the range 0 to 4 inclusive, and that bound is the practical limit on how many times a subscription may hop into the paused state over its life. Nothing about a pause clears a pending skip: a paused subscription that was `SKIPPED` keeps its `skipped_cycle_index`, which is why a pause and a skip can be nested rather than treated as alternatives.

Resuming from `PAUSED` is admitted only when `resumed_at` is null or the logical clock is strictly after `resumed_at` — the same instant cannot be used to resume the same subscription twice — and on success the subscription returns to `ACTIVE`, `resumed_at` is stamped with the current logical clock, and `paused_at` is cleared to null. Resuming a `SKIPPED` subscription requires that the logical clock has reached the start of `skipped_cycle_index`; the resume cannot be used to jump a skip that has not yet arrived. Resuming through the explicit operation also clears `skipped_cycle_index` to null. A subscription that is `PAUSED` may nonetheless receive a one-off order, and that path has its own side effects: the subscription returns to `ACTIVE` from `PAUSED` when the new order names it, and if the subscription was carrying an auto-skip, the auto-skip is cleared to `ACTIVE` with `skipped_cycle_index` set to null — a paused household that places an order is treated as re-engaged.

Cancellation is available from any of `ACTIVE`, `SKIPPED`, `AUTO_SKIPPED` and `PAUSED`, and it is refused while any box order belonging to the subscription has status `BUILDING`, because a build in flight cannot be abandoned mid-transaction; the refusal is a state refusal carrying `ERR_INVALID_STATE` and HTTP status 409. A permitted cancellation moves the subscription to its terminal `CANCELLED` state, records the supplied `cancellation_reason` — one of `CUSTOMER_REQUEST` or `NONPAYMENT`, and null when the caller relies on the default — and abandons every `DRAFT` order belonging to the subscription, which is the domain's way of saying that an order that was never committed dies with the subscription that would have carried it. A `CANCELLED` subscription is inert: it may not generate a cycle-bound order, and it is the one subscription state that never returns to `ACTIVE`.

### 3.9. Validation Precedence and the Guard Lattice

Every request passes through a fixed ladder of checks, and the ladder's order is part of the contract rather than an implementation detail: when more than one check could legitimately fail, the one that sits earliest in this ordering is the one that produces the response, so a request that is both malformed and unauthorized reports the authorization failure rather than the malformation, and a request against a resource that does not exist reports the missing resource rather than an illegal state on a resource nobody found.

At the top of the ladder sit the two authentication checks. First, the `X-User-ID` and `X-User-Role` headers must both be present, the role must be one of the recognized five values including `Anonymous`, and when the role is entity-backed the identifier must resolve to a persisted instance of that entity — any failure here yields `ERR_UNAUTHENTICATED` with HTTP status 401. Second, the acting role must be permitted for the operation, and an entity-backed role must not be acting on a resource it does not own — a failure yields `ERR_UNAUTHORIZED` with HTTP status 403. Both of these guard the entire API without exception.

Third comes request shape, and it applies wherever an endpoint declares a request body. Every field the endpoint declares as required must be present, every supplied enum member must be one the endpoint actually declares, and a supplied `barcode_gtin` must be exactly fourteen digits; a failure yields `ERR_INVALID_REQUEST` with HTTP status 400. Fourth comes existence: path parameters are resolved left to right in the order they appear in the path, and body foreign keys are resolved in the order the endpoint's input list declares them, with any unresolved reference yielding one of `ERR_CUSTOMER_NOT_FOUND`, `ERR_BOX_ORDER_NOT_FOUND`, `ERR_BUILD_ITEM_NOT_FOUND`, `ERR_SUPPLY_LOT_NOT_FOUND`, `ERR_SUPPLIER_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, `ERR_SUBSCRIPTION_NOT_FOUND`, `ERR_FULFILLMENT_CENTER_NOT_FOUND` or `ERR_BID_NOT_FOUND`, each with HTTP status 404. Because the resolution is left to right, a request naming a nonexistent order under a nonexistent customer reports the customer's error and never reaches the order.

Fifth is the state gate, and it has two halves that are ordered against each other. Within this single rung, the optimistic concurrency comparison runs first: the supplied `expected_<parent>_version` must equal the parent entity's current version, and a mismatch yields `ERR_STALE_VERSION` with HTTP status 412 before the state of the target resource is examined at all. Only once the version matches does the from-state test run, and a target resource that is not in a state admitting the requested transition or operation yields `ERR_INVALID_STATE` with HTTP status 409. A box order in `CRASHED` is the sharpest instance of the from-state half: it admits no further build, pack or finalise transition, so any such attempt on a crashed order is refused. This rung guards the finalise, build, pack, reroute-back, subscription-resume, lot-award and claim-review operations; note that it does not guard order creation or packing's single-use rule, which have their own rungs below.

The remaining rungs are business rules and they are ordered as follows. Sixth is allergen exclusion: no lot whose `allergen_codes` intersect the customer's `dietary_allergy_codes` may be drawn into a box or left inside one, and the offence is refused with `ERR_ALLERGEN_CONFLICT` and HTTP status 422 on both the build and the finalise operations. Seventh is claim credibility, and its position is deliberate: a quality claim whose `requested_credit_cents` is exactly zero is refused as not credible with `ERR_CLAIM_NOT_CREDIBLE` and HTTP status 422 *before* any assessment of the cited lot's quality, so a worthless claim can never be used to probe or disturb a lot's quality standing. Eighth is the order cutoff: an order must have been created strictly before its `ready_deadline`, and a finalise attempt on an order that was created at or after that instant is refused with `ERR_ORDER_CUTOFF_MISSED` and HTTP status 422.

Ninth is the fulfillment-center posture permit. The owning center's `forward_posture` must be exactly `OPEN` for order creation and for a build start, and this rung is listed against order creation, build and finalise alike; a refusal carries `ERR_CENTER_FORWARD_LOCKED` and HTTP status 409. The asymmetry noted in §3.4 stands: for finalisation the permit is satisfied by any posture other than `DEGRADED`, so a `CONSTRAINED` center still admits the operation that advances its own counter. Tenth is substantiation: a lot carrying a `ConventionalQuote` must have at least one source of the lot's own procurement grade and no more than three sources in total before any display-price comparison on it counts as substantiated, and both the substantiation assessment and the make-ready inspection that publishes a price are refused with `ERR_SUBSTANTIATION_REQUIRED` and HTTP status 422 when that evidence is missing or excessive. Eleventh is the lot quality gate: only lots whose `quality_status` is `PASS` may be drawn into boxes or committed, and a build or finalise that would draw from a lot that is not `PASS`, or a review whose cited lot is not `PASS`, is refused with `ERR_LOT_QUALITY_HOLD` and HTTP status 409.

Twelfth is subscription cadence eligibility, guarding order creation: the subscription must not be `PAUSED` or `CANCELLED` for a cycle-bound order, and the order may not duplicate an existing `serving_cycle_index` for the same subscription, with either offence yielding `ERR_SUBSCRIPTION_INELIGIBLE` and HTTP status 409. Thirteenth is photo evidence: a quality claim must carry a `photo_url` whose path ends in one of the accepted image extensions, and a claim without recognised evidence is refused with `ERR_CLAIM_EVIDENCE_REQUIRED` and HTTP status 422. Fourteenth is the single-use packing rule: a box order may be packed at most once per serving cycle, and a second pack against an already-packed order is refused with `ERR_ALREADY_ALLOCATED` and HTTP status 409. Fifteenth and last is regional center availability: registration requires at least one active fulfillment center in the customer's `service_region`, and registration against a region with none is refused with `ERR_NO_CENTER_AVAILABLE` and HTTP status 422.
