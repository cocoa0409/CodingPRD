# Number Portability, Port Credits & Line Migration Operations API — Product Requirements Document

## 1. Introduction

Telecom carriers lose revenue twice when a customer switches networks: once when the number leaves and again when the switching incentive fails to bind the customer to the new plan. This API is the operational backbone that closes both leaks. It turns a port-in from a support ticket into a tracked workflow — a request that carries the losing carrier's transfer credentials, that records every carrier rejection verbatim with the guidance the customer needs to fix it, and that only releases the reserved directory number when the port has genuinely completed or genuinely died.

Three commercial programs sit on top of that workflow. The first is the promotional switch credit: a monthly credit applied across an installment period, projected optimistically at sign-up and earned chronologically as the customer actually retains service, with a clawback path when the line does not stay. The second is device financing, where a retail price is leveled into installments, a trade-in is quoted on the customer's self-report and then re-settled on the inspector's real grade, and an upgrade becomes available part-way through the term. The third is account expansion — family and business line additions underwritten by a credit class that determines whether a deposit is demanded before service is provisioned.

Running underneath all three is a number-inventory discipline. Every directory number has two independent lives: whether service is on, and what the number itself is doing. A number can be held for a customer who has not yet been provisioned, reserved pending a port-in, ported in from another carrier, assigned to a working line, or reclaimed by the pool long after the line was cancelled. The API keeps those two dimensions separate on purpose, protects them against unauthorized transfer through port-out protection cases, and reconciles them against a controllable logical clock so that cutovers, vesting dates and reservation expiries can be driven deterministically. The whole surface is mounted under the `/portability` prefix.

## 2. Global Specifications & System-Wide Principles

This section states the rules that hold across every resource in the API: who may act, what a response looks like, how lists are shaped, how identifiers and versions behave, how money is accounted, and in what order the server evaluates its checks.

### 2.1. User and Role-Based Access Control

Every request must identify its caller through two mandatory HTTP headers. The `X-User-ID` header carries the acting party's identifier and the `X-User-Role` header names the capacity in which that party is acting. If either header is absent, or if `X-User-Role` does not name one of the five roles this API recognizes, the request is rejected with `ERR_UNAUTHENTICATED` and an HTTP status of 401. The recognized role names, spelled exactly, are `PlatformAdmin`, `CustomerService`, `CreditAnalyst`, `TradeInInspector` and `Customer`. A caller that is properly authenticated but attempts an operation its role is not permitted to perform is rejected with `ERR_UNAUTHORIZED` and an HTTP status of 403; every endpoint below lists the roles permitted for it, and any role not listed is refused this way.

The five roles differ in how their identifier relates to stored data. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it on audit fields but does not compare it to any entity's `id`. The same is true of `CustomerService`, whose identifier is an opaque care-agent handle, of `CreditAnalyst`, whose identifier is an opaque underwriting handle, and of `TradeInInspector`, whose identifier is an opaque warehouse-grader handle. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Account`; ownership checks on any resource that references an `Account` compare the resource's foreign-key field to `X-User-ID`. Because `Account` is the only entity-backed role identity, a `Customer` caller reading a resource whose owning account is not their own is treated as unauthorized.

`PlatformAdmin` holds exclusive rights to the carrier-facing, provisioning and audit operations, including setting the logical clock, running the ops-run sweep, opening accounts and subscriber lines, recording carrier rejections, committing held numbers, resolving protection cases and reversing promotional credits. `CreditAnalyst` alone underwrites line-addition requests. `TradeInInspector` alone grades traded-in devices. All four internal roles, together with `Customer`, may read the resources their workflow touches.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
### 2.3. Pagination

List endpoints accept two query parameters. The `limit` parameter caps how many items are returned; when it is omitted the server returns 10 items, and any supplied value must be between 1 and 100 inclusive — a supplied value outside that band is clamped into it rather than refused, so a value above 100 is treated as 100 and a value below 1 as 1, while a value that does not parse as an integer falls back to the default of 10. The `offset` parameter states how many items to skip before the page begins and defaults to 0 when omitted; a negative or unparseable `offset` is treated as 0. Unless a rule elsewhere says otherwise, list endpoints return their resources ordered by `created_at` ascending. Every list response carries `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope, alongside `api_request_id` and `api_request_timestamp`.

### 2.4. The Logical Clock and Deterministic Scheduling

This API never reads wall-clock time. A single logical clock drives every temporal decision, and it starts at exactly `2026-09-01T00:00:00Z` when the server boots; until something advances it, the clock continues to read that default and never silently falls back to the real current time. An operator with the `PlatformAdmin` role advances the clock by supplying a `to_iso8601` instant. The response reports the resulting clock reading as `current_utc` and the prior reading as `previous_utc`. Advancing the clock is not merely a time change: the server evaluates every scheduled transition whose deadline has been reached by the new reading, covering port cutovers, migration cutovers, promotional vesting and reservation expiry, in the same operation.

Two further scheduled behaviours are worth naming here. The `SystemConfig` resource exposes an `ops_run_epoch` counter that begins at 1 and is advanced only by an ops run, a `last_ops_run_at` instant that begins at the clock default `2026-09-01T00:00:00Z`, and a `last_line_cancellation_deadline` that also begins at that same default. An ops run takes a `triggered_at` instant and is idempotent per deadline: the server compares `triggered_at` against `last_line_cancellation_deadline`, which itself is restamped every time a line is cancelled as the cancellation instant plus `line_cancellation_grace_hours` (24 hours by default).

### 2.5. Common Resource Properties

Every top-level resource in this API carries a standard trio of system-managed properties, with one deliberate exception. The `id` is a server-minted unique identifier formatted as a UUID with no type prefix — a subscriber line's id does not begin with `line_`, and a port request's id does not begin with `port_`. The `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first created. The `updated_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was last modified. The `version` is a system-managed integer that begins at 1 and increments by one on every modification to the resource, including modifications the server makes on its own initiative rather than in direct response to a request; derived fields being recomputed counts as a modification for this purpose. The one resource that does not follow this convention is `RejectionCodeCatalog`, which is a static reference table: it carries only an `id` and a `created_at`, and has neither an `updated_at` nor a `version` field.

### 2.6. Monetary Values, Precision and Rounding

Every monetary quantity in this API is an integer count of cents — `monthly_credit_cents`, `device_price_cents`, `deposit_required_cents`, `prepaid_balance_cents` and their peers are all whole integers, never decimals and never strings, and a field name ending in `_cents` always means a whole number of cents. All internal arithmetic on these quantities is performed with decimal arithmetic, and every monetary value that is stored or returned is rounded to whole cents using the round-half-up method — a result falling exactly half a cent is rounded upward to the next whole cent. This precision rule applies identically to every calculation in §3, including those whose intermediate products are fractional.

### 2.7. Optimistic Concurrency Control on Line-Writing Operations

Three creation operations may supersede state that the client last read from a subscriber line, and each therefore requires the client to present the version it observed. A create of a `PromoCreditSchedule`, a create of a `DeviceInstallmentPlan` quote, and a create of a `PortRequest` must each carry an `expected_subscriber_line_version` field naming the `version` of the target `SubscriberLine` as the client last observed it. The request is rejected when the supplied `expected_subscriber_line_version` does not equal the subscriber line's current `version`, and the rejection carries `ERR_STALE_SUBSCRIBER_LINE_VERSION` with an HTTP status of 412. This rule exists because a new promotional schedule supersedes the line's prior promotional posture, a new installment quote supersedes the line's prior quoted plan, and a new port request may supersede the line's prior request — in each case the server would be acting on a stale view of the line, so it refuses rather than overwrite. These three operations are the only ones that take a version field; no other endpoint in this API accepts `expected_subscriber_line_version` or any other client-supplied version. The field is optional on all three: when the caller omits it the version comparison is skipped and the create proceeds, so a create that never presents the field is not refused as stale.

### 2.8. Nested Resource Retrieval

Where a path nests one resource under another, the server validates the segments in a strict left-to-right order and stops at the first identifier that does not resolve. A request naming both an account and a subscriber line under it fails on the account before the subscriber line is even looked up if the account does not exist, and a request naming both a subscriber line and an installment plan under it fails on the subscriber line first. The reader may rely on this ordering whenever a path contains more than one identifier.

### 2.9. Validation Precedence

Validations in this API are evaluated in a fixed priority order, and the first one that fails determines the error the client sees. Authentication is checked before authorization, and both are checked before any resource is looked up. Existence checks follow, ordered `SubscriberLine`, then `Account`, then `PortRequest`, then `NumberReservation`, each returning its own 404 identifier. Only after existence is settled does the server evaluate state, safety, temporal and business constraints. The generic state gate is reported as `ERR_INVALID_STATE` with an HTTP status of 409: this is what a caller receives when it asks for a transition on a resource whose current state is not the starting state that transition requires, and it applies to every state-transition operation in this API — submitting, rejecting, resubmitting, accepting and cancelling a port request; running a migration eligibility check; reviewing a line addition; committing a reservation; activating, denying and clearing a protection case; grading a trade-in; and activating or reversing a promotional schedule. Within those categories the ordering matters most in three places. On a port-request submission or resubmission, the state check for the request comes first, then the attached line's port-protection check, then the transfer-credential check, then the resubmission-eligibility and cooling-off checks, and finally the duplicate-reservation check. On a line-addition review, the credit-class determination runs before the deposit test, so a `BLOCKED` determination surfaces as `ERR_CREDIT_CLASS_BLOCKED` (403) rather than being masked by a deposit shortfall, and the line-count ceiling is checked before the deposit test as well, so `ERR_LINE_LIMIT_EXCEEDED` (409) wins over `ERR_DEPOSIT_REQUIRED` (402) when both would fire. On a `TradeInAssessment` creation no ordering conflict arises. Finally, the generic payload check — every required field present and correctly typed, reported as `ERR_INVALID_REQUEST` with an HTTP status of 400 — is evaluated last of all, so a semantically meaningful rejection is never displaced by a generic one.

## 3. Business Logic & Workflows

The subsections that follow describe how work actually moves through the system. They are written from the operator's and the customer's point of view rather than as a field reference, so that the shape of each workflow — the conditions that gate it, the side effects it leaves behind, and the errors it raises — is clear before the HTTP contract in §4 is consulted.

### 3.1. Bringing a Number In From Another Carrier

A port-in begins when a care agent opens a request against an existing line. The agent supplies a `subscriber_line_id` identifying the line the number will land on, a `losing_carrier_code` naming the carrier that currently serves the number, the customer's `account_number_at_losing_carrier` with that carrier, the `transfer_pin` that carrier issued, and the `requested_cutover_at` instant the customer asked the port to take effect. Because a fresh attempt frequently follows a dead one, the agent may also pass a `supersedes_port_request_id` naming the earlier request this one replaces; it is null on a first attempt, and the server stores it as null when the caller omits it. A `PortRequest` is born in `request_state` `DRAFT`, with `rejection_count` 0, a `last_rejection_code` that is null, a `last_rejection_at` that is null, an empty `rejections` array, a null `submitted_at`, and a null `cutover_completed_at`. Creating one increments the attached line's `version` by one. The request stores the supplied `transfer_pin` and `account_number_at_losing_carrier` verbatim, exactly as the caller presented them, and stores `requested_cutover_at` in the server's canonical millisecond ISO 8601 form; `losing_carrier_code` and `transfer_pin` are required strings, while `requested_cutover_at` is required and must parse as an instant. The create does not consult the line's `number_status`, so a request may be drafted against a line whose number is not `UNASSIGNED` or `RESERVED`; that constraint belongs to submission alone.

Submission is what actually puts the request in front of the losing carrier, and it is where most of the safety checks live. The `PortRequest` must currently be in `DRAFT`. The `subscriber_line_id` must resolve to a `SubscriberLine` whose `number_status` is `UNASSIGNED` or `RESERVED`, the `transfer_pin` must be exactly four digits, and the `requested_cutover_at` must be at or after the current reading of the logical clock. **Before any of those three are examined**, however, the server checks port-out protection: if the attached line's `port_protection_status` is `PROTECTED`, submission is refused with `ERR_PORT_PROTECTION_ACTIVE` (403), because a freeze the account holder or an operator placed on the line must not be defeated by simply submitting a port. Given that the line is unprotected, the `transfer_pin` must be exactly four digits and, together with the `account_number_at_losing_carrier` supplied on the same call, must reproduce the pair of credentials the request itself carries — a `transfer_pin` that is not four digits, or a `transfer_pin` or `account_number_at_losing_carrier` that disagrees with the request's own stored values, is rejected with `ERR_TRANSFER_PIN_MISMATCH` (422). And if any other `SubscriberLine` already holds this request's number with `number_status` `RESERVED`, the submission fails with `ERR_MDN_ALREADY_RESERVED` (409). A `number_status` that is neither `UNASSIGNED` nor `RESERVED`, or a `requested_cutover_at` that is before the current logical clock instant, is reported through the generic state gate as `ERR_INVALID_STATE` (409). The submitted `transfer_pin` is compared to the request's stored `transfer_pin` after the four-digit format test; an `account_number_at_losing_carrier` that is missing entirely is refused as `ERR_INVALID_REQUEST` (400), while one that is present but disagrees is refused with `ERR_TRANSFER_PIN_MISMATCH` (422).

A successful submission moves the request from `DRAFT` to `PENDING`, stamps `submitted_at` with the current logical clock instant, and sets the attached line's `number_status` to `RESERVED` so the number cannot be claimed by anyone else while the carrier is processing. The request now waits on the losing carrier.

That wait ends in one of two ways. The carrier may reject the port, which is the subject of the next subsection, or a platform operator may accept it. Acceptance is available while the request is in `PENDING` and while an already-`REJECTED` request has been resubmitted into `RESUBMITTED`; in both cases the `requested_cutover_at` must still be at or after the current logical clock instant, and the request transitions to `ACCEPTED_PENDING_CUTOVER` with `updated_at` recomputed. An accepted request is a scheduled event: when the clock is subsequently advanced to or past `requested_cutover_at`, the cutover fires on its own, as §3.8 describes, carrying the request into the terminal `PORTED` state.

Cancellation is the other way a port request ends. A request still in `PENDING` may be cancelled by a care agent, which returns the attached line's `number_status` to `UNASSIGNED`; the operator supplies no body for this. A request in `REJECTED` may also be cancelled, but only once `rejection_count` has reached 3 or more — the product treats three carrier rejections as the point at which further retries are not worth pursuing — and cancelling a rejected request recomputes `updated_at` without touching the line's number state. When cancelling a request that has not reached three rejections, the server refuses the transition.

### 3.2. Carrier Rejections, Customer Guidance and Resubmission

A rejection is recorded by a platform operator rather than by the customer, and it arrives as a single `rejection_code` string identifying what the losing carrier objected to. The request must be in `PENDING` at the time, and the code must resolve to a row of the `RejectionCodeCatalog`; an unknown code is refused with `ERR_REJECTION_CODE_NOT_FOUND` (404). The catalog is the reference table an operator maintains ahead of time: each entry carries the `rejection_code` itself, a `description` explaining the objection in plain language, the `guidance_text` shown to the customer, a `resubmission_allowed` flag defaulting to true, a `retry_after_hours` cooling-off period defaulting to 0, and a `requires_action_by` value naming the party responsible for clearing it — one of `CUSTOMER`, `LOSING_CARRIER` or `GAINING_CARRIER`. Catalog entries are created by platform operators and, uniquely among the resources here, each is identified by its own `rejection_code` and is immutable in practice. A create names a `rejection_code` that must be unique across the catalog — a repeat is refused with `ERR_INVALID_REQUEST` (400) — together with a `description` and a `guidance_text`, both required strings, and a `requires_action_by` that must be one of the three recognized values. A catalogue entry carries neither an `updated_at` nor a `version`, so it is the one resource whose creation does not mint that standard pair.

Recording the rejection appends a new entry to the request's append-only `rejections` log. That entry carries `rejection_code`, `guidance_text`, `resubmission_allowed`, `retry_after_hours` — all four copied from the matching catalog row — and an `occurred_at` instant set to the current logical clock instant. The server then recomputes `rejection_count` as the number of entries in `rejections`, sets `last_rejection_code` to the code just supplied, and sets `last_rejection_at` to the new entry's `occurred_at`. The request moves from `PENDING` to `REJECTED`, and, importantly, the attached line's `number_status` is returned to `UNASSIGNED`, releasing the number the submission had reserved. The response to this operation is the rejection record itself, not the whole port request.

Resubmission is how a rejected request gets a second life. It is available to a care agent when the request is in `REJECTED`, and it takes the same `transfer_pin` and `account_number_at_losing_carrier` the submission took. Three gates are evaluated in a fixed order, after the same two safeguards that guard submission: the attached line's `port_protection_status` must be `UNPROTECTED` (otherwise `ERR_PORT_PROTECTION_ACTIVE`, 403), and the supplied `transfer_pin` must be exactly four digits and, together with the `account_number_at_losing_carrier` supplied on the same call, must reproduce the pair of credentials the request itself carries (otherwise `ERR_TRANSFER_PIN_MISMATCH`, 422). First, the most recent `rejection_code` must resolve to a catalog row whose `resubmission_allowed` is true; if the carrier marked that objection as final, the resubmission is refused with `ERR_RESUBMISSION_NOT_ALLOWED` (422). Second, the cooling-off period must have elapsed: the current logical clock instant must be at or after `last_rejection_at` plus the catalog row's `retry_after_hours`, and resubmitting early is refused with `ERR_RESUBMISSION_COOLDOWN` (409). Third, no other `SubscriberLine` may hold this request's number with `number_status` `RESERVED` as of the current clock instant, or the attempt fails with `ERR_MDN_ALREADY_RESERVED` (409).

A successful resubmission sets `request_state` to `RESUBMITTED` and `submitted_at` to the current logical clock instant, and it re-reserves the attached line's number by setting `number_status` to `RESERVED`. Two further side effects ride along. Because the customer has now demonstrated continued intent on a prepaid line, `retention_cycle_count` is incremented by 1 when the attached line's `billing_mode` is `PREPAID`. And the transition's declared side effects include one more, expressed as a conditional: when the attached line's `port_protection_status` is `PROTECTED` at the moment of resubmission, the ACTIVE `PortProtectionCase` on that line has its `case_state` set to `CLEARED` and the line's `port_protection_status` set to `UNPROTECTED`. This conditional and the safety gate above stand in tension, because the gate refuses every resubmission on a `PROTECTED` line, so the conditional's antecedent can never hold when the gate is enforced: the unconditional reading of the gate is the one that governs, and a resubmission on a `PROTECTED` line is refused with `ERR_PORT_PROTECTION_ACTIVE` (403) before any clearing side effect could fire. The side effect is therefore never observable through the API, and it does not soften the safety gate.


### 3.3. The Prepaid-to-Postpaid Migration

A migration request moves a prepaid line onto a postpaid account without changing the number the customer already knows. A care agent opens one by supplying a `subscriber_line_id` for the line being migrated, an optional `prepaid_balance_cents` holding the remaining wallet balance to be carried across (which defaults to 0 when omitted), and the `requested_cutover_at` instant the customer wants the switch to take effect. The `source_billing_mode` the line is leaving and the `target_billing_mode` it is entering are both optional on the request and both carry fixed defaults: `source_billing_mode` defaults to `PREPAID` and is only ever `PREPAID`, while `target_billing_mode` defaults to `POSTPAID` and is only ever `POSTPAID`. A migration request is born in `migration_state` `DRAFT`, with a null `carried_mdn`, `device_balance_cents` 0, `proration_credit_cents` 0 and a null `cutover_completed_at`.

Eligibility is evaluated in two steps rather than one. The care agent first asks for an eligibility check, which requires that the attached line's `billing_mode` is `PREPAID` and moves the request from `DRAFT` to `ELIGIBILITY_CHECK` with `updated_at` recomputed; a line in any other billing mode is refused with `ERR_INVALID_STATE` (409). The evaluation then runs without waiting for a clock advance: it is performed synchronously inside the same eligibility call, so that call returns with the request already routed to one of the two destinations below rather than resting in `ELIGIBILITY_CHECK`. The evaluation routes the request to exactly one of two destinations, on mutually exclusive conditions. If the attached line's `port_protection_status` is `PROTECTED`, or if any `PortRequest` on the attached line is sitting in `PENDING` or `RESUBMITTED`, the request goes to `BLOCKED`; in that branch the attached line's `number_status` is set to `UNASSIGNED`, and when the reason is protection specifically, the attached line's account also has `account_status` set to `SUSPENDED`. When the request is blocked because of an open port request rather than protection, the account is left untouched. If instead the attached line's `port_protection_status` is `UNPROTECTED` and no `PortRequest` on the attached line is in `PENDING` or `RESUBMITTED`, the request goes to `APPROVED` and the attached line's `number_status` is set to `RESERVED`, holding the number for the migration. Both branches recompute `updated_at`.

The care agent may also call the eligibility check again on an already-`APPROVED` request, which is the recovery path for a line that was blocked by protection and then cleared: when the request is in `APPROVED` and the attached line's `PortProtectionCase` has been `CLEARED` since the last evaluation, the request returns to `ELIGIBILITY_CHECK` with `updated_at` recomputed so that a fresh evaluation can run. On this re-entry, "since the last evaluation" is measured against the request's own `updated_at`: a cleared case counts only when its `cleared_at` is strictly later than the request's `updated_at`, and an `APPROVED` request with no such cleared case in its past is refused with `ERR_INVALID_STATE` (409). The call after the re-entry runs a fresh evaluation synchronously, exactly as the first call did. The eligibility call also accepts a `changed_at` instant; when supplied, `requested_cutover_at` is set to `changed_at`. A request in any other state — `ELIGIBILITY_CHECK`, `BLOCKED`, `CUTOVER_SCHEDULED` or `CUTOVER_COMPLETE` — is refused with `ERR_INVALID_STATE` (409).

From `APPROVED`, scheduling is automatic: once `requested_cutover_at` is set to an instant at or after the current logical clock instant, the request moves on to `CUTOVER_SCHEDULED` with `updated_at` recomputed. That step runs in the same operation that produced the approval — the eligibility evaluation that leaves the request `APPROVED`, and any later call that assigns a new `requested_cutover_at` to an approved request, each perform it before returning — and it also runs on a later advance of the logical clock. On that pass the tiers are evaluated in sequence within a single sweep: every migration still in `ELIGIBILITY_CHECK` is routed first, then every `APPROVED` request whose `requested_cutover_at` has come due is promoted to `CUTOVER_SCHEDULED`, and only then is every `CUTOVER_SCHEDULED` request whose instant has come due completed. Because the completion tier runs after the promotion tier, a migration can never complete in the same sweep that left it `APPROVED`; it must pass through `CUTOVER_SCHEDULED`, and a migration whose instant has already come due may therefore remain `APPROVED` until the next advance. A `changed_at` supplied alongside the eligibility call is applied after the evaluation has already run, so it does not retract a routing the evaluation has just produced; a request that has just been scheduled or blocked keeps that outcome, and only a request left `APPROVED` is moved on to `CUTOVER_SCHEDULED` by the newly assigned instant. A migration left `BLOCKED` is not re-routed unless the eligibility call is made again on it, and a `BLOCKED` request that is never re-entered stays blocked regardless of later clock advances. Completion is also automatic, and fires when the clock reaches `requested_cutover_at` while the request is in `CUTOVER_SCHEDULED`, carrying the migration into the terminal `CUTOVER_COMPLETE` state. Completion is a cascading act with a fixed hop order. First, `cutover_completed_at` is stamped with the current logical clock instant, and the attached line's `billing_mode` is set to `POSTPAID` while its `number_status` becomes `ASSIGNED`. Second, because the billing mode has just become postpaid, the migration's `carried_mdn` is set to the attached line's `mdn` — this is the number preservation guarantee — and `device_balance_cents` is set to the sum of `remaining_balance_cents` over every `DeviceInstallmentPlan` attached to that line. The statuses that the cutover writes are not separately gated on a prior state: a port cutover sets the line's `service_status` to `ACTIVE` and its `number_status` to `PORTED_IN` regardless of what those dimensions held before, and a migration cutover likewise writes `POSTPAID` and `ASSIGNED` directly. Third, because `device_balance_cents` has just been set, `proration_credit_cents` is computed from the mid-cycle proration rule in §3.3. The attached `DeviceInstallmentPlan` rows each have their `plan_state` set to `CONVERTED`, reflecting that their financing now belongs to the postpaid account, and the line's `loyalty_tenure_months` and `retention_cycle_count` are both recomputed. The `device_balance_cents` figure is read from the plans as they stood before this conversion, so a plan that this same cutover converts still contributes its `remaining_balance_cents` to the sum.

The proration credit the cutover produces is computed in a pinned evaluation order that must not be rearranged, because each step consumes the previous one's output. First, the post-migration line count is the account's `active_line_count` plus 1, since the migration itself contributes the line. Second, the applicable tier is that count capped at 4 — so an account that will hold four or more lines after the switch sits in the top tier, and a single-line account sits in the bottom one. Third, the tier carries a plan rate in cents: tier 1 is 5 000 cents, tier 2 is 4 000 cents, tier 3 is 3 000 cents and tier 4 is 2 500 cents. Fourth, the remaining days in the current billing cycle are 30 minus the day-of-month of the current logical clock instant, so a cutover landing on the first of the month leaves 29 remaining days, and a cutover landing on the thirtieth or thirty-first leaves a number that is zero or negative. Fifth, the proration component is the plan rate multiplied by the remaining days and divided by 30, rounded half-up to whole cents, with the remaining-days figure floored at zero so that a late-month cutover contributes a proration component of exactly zero rather than a negative one. Sixth, the carry component is one half of the sum of the migration's `prepaid_balance_cents` and its `device_balance_cents`, rounded half-up to whole cents. Seventh, `proration_credit_cents` is the proration component plus the carry component. The input set for this rule reads `prepaid_balance_cents` from the migration request itself, `device_balance_cents` from the sum of `remaining_balance_cents` over the installment plans attached to the subscriber line, and `active_line_count` from the account as observed **before** this migration's line is counted.

Applies to: migration request drafting, the eligibility evaluation, scheduling, and cutover completion.


### 3.4. The Switch-Credit Schedule: Projection, Vesting and Clawback

The promotional switch credit is modeled as a schedule with two totals, because the commercial promise and the earned amount genuinely differ. When a care agent opens a schedule they supply a `subscriber_line_id` naming the line, a `promo_code` for the program, the `monthly_credit_cents` to be applied in each billing cycle of the installment period, the `installment_months` length of that period, an optional `retention_requirement_cycles` giving the number of completed billing cycles the line must retain before the credit vests (which defaults to 12), and the `window_start` instant marking the first instant of the credit window, inclusive. The `monthly_credit_cents` is a required integer and is stored and returned on the schedule, but it does not enter either of the schedule's totals; `installment_months` must be at least 1 and `window_start` is required. The schedule is created in `schedule_state` `PROVISIONAL`, and creating it increments the attached line's `version` by one — which is why this operation is one of the three that require the client's `expected_subscriber_line_version` as described in §2.7. The schedule's `cycles_elapsed` is set at creation to the billing cycles already completed inside the window as of the current logical clock instant — the day the schedule is opened is not itself counted, so a create landing exactly on `window_start` records 0 — and it defaults to 0 when the clock reads before `window_start`.

New promotions cannot be stacked end to end arbitrarily. The requested `window_start` must be at or after every existing `PromoCreditSchedule`'s `window_end` on the same subscriber line **plus** the system's `promo_window_buffer_days` setting, and this test only considers existing schedules whose `schedule_state` is `PROVISIONAL` or `ACTIVE` — a schedule that has already `VESTED` or been `CLAWED_BACK` imposes no buffer. The buffer defaults to 30 days. A window that starts inside another schedule's window plus the buffer is refused with `ERR_PROMO_WINDOW_OVERLAP` (409). The client's `expected_subscriber_line_version` is checked ahead of this buffer test, so a create that presents a stale line version is refused as stale even when its requested window would also collide.

Two totals are computed over the same schedule. The projection counts the months that can be billed — `billable_months` — which is whichever is smaller of `installment_months` and `retention_requirement_cycles`. The provisional total, written to `provisional_total_cents`, is a flat base credit of 20 000 cents plus 1 000 cents for each billable month, so it treats every billable month as if it had already been completed and already includes the retention bonus. The vested total, written to `vested_total_cents`, is different in kind: it credits only the cycles the line has actually completed inside the window, so it is 1 000 cents multiplied by `cycles_elapsed`. Because it is a chronological quantity, `cycles_elapsed` — and with it the vested total — is refreshed on every advance of the logical clock for a schedule that is still `PROVISIONAL` or `ACTIVE`, so the vested total reads the cycles the line has completed as of the new clock instant even while the window is still open; a schedule that has already `VESTED` or been `CLAWED_BACK` is not refreshed this way, and a clawback zeroes its vested total outright. For any schedule whose `cycles_elapsed` is below `billable_months` — the ordinary case while the window is still running — the vested total is strictly smaller than the provisional total, and the difference is exactly the retention bonus that has not yet been earned. Only schedules whose `schedule_state` is `PROVISIONAL`, `ACTIVE` or `VESTED` participate in these totals; a schedule in `CLAWED_BACK` is excluded from the input set entirely. Both totals are whole cents rounded half-up, and the schedule's `window_end` — the last instant of the credit window — is computed from `window_start` plus `installment_months` billing cycles, where a billing cycle is treated as 30 days. The projection reads only `installment_months` and `retention_requirement_cycles` and the vested total only `cycles_elapsed`; `monthly_credit_cents` does not enter either total. The `window_start` boundary is inclusive and the `window_end` boundary is inclusive for the purposes of the transitions below.

Creating the schedule also has account-level and line-level consequences. The attached line's `promo_eligibility_state` is set to `PROVISIONAL_ELIGIBLE`, and the account's `promo_credited_cents` is incremented by the `provisional_total_cents` of the new schedule, after which the account's `net_promo_credit_cents` is recomputed as `promo_credited_cents` minus `promo_clawed_back_cents`. This account-level ledger is conserved: the running credited total, the running clawed-back total and their difference always move together, and no operation may adjust one without leaving the other two consistent.

Starting to apply the credit moves the schedule from `PROVISIONAL` to `ACTIVE`, and it is permitted only while the schedule is `PROVISIONAL` and the current logical clock instant is at or after `window_start`; the transition recomputes the account's `net_promo_credit_cents`. Vesting happens on its own when the clock reaches `window_end` while the schedule is `ACTIVE` and the line has retained service through the window; the declared preconditions are that the schedule's `schedule_state` is `ACTIVE` and that the current logical clock instant is at or after `window_end`. On vesting, `vested_total_cents` is written with the vested-variant projection (1 000 cents per completed cycle inside the window), the attached line's `promo_eligibility_state` is set to `VESTED`, and the account's `net_promo_credit_cents` is recomputed. Critically, vesting does **not** retroactively convert the `vested_total_cents` into the `provisional_total_cents`; the retention bonus is earned by the line's `retention_cycle_count` reaching `retention_requirement_cycles` on the line-side rollup described in §3.7, not by the calendar alone.

Reversal is the other terminal path, and it is a compound cascade. A platform operator may claw a schedule back while it is `ACTIVE`, and only then — a schedule that has already `VESTED` is past the point of reversal; a schedule in any other state is refused with `ERR_INVALID_STATE` (409). Before the reversal proceeds, the attached line's `service_status` must be `ACTIVE`; a line that is not active is refused with `ERR_LINE_NOT_ACTIVE` (403). The schedule's state gate is evaluated ahead of that line test, so only an `ACTIVE` schedule can reach and report the line-activity refusal. The reversal then runs in three hops. First, the schedule's `schedule_state` becomes `CLAWED_BACK` and its `vested_total_cents` is set to 0, and the attached line's `promo_eligibility_state` becomes `CLAWED_BACK`. Second, because the line's promotional posture has just changed, the attached line's `DeviceInstallmentPlan` has its `remaining_balance_cents` incremented by the schedule's `provisional_total_cents` — the previously credited amount is pushed back onto the device balance the customer still owes. Third, because that balance has just increased, the selected plan's `monthly_installment_cents` and its `plan_state` are recomputed through the installment-balance rule in §3.5. The plan that receives the whole `provisional_total_cents` is the line's `ACTIVE` one when it has one; failing that, the most recently created plan on the line whose state is not `CONVERTED`, and failing that the most recently created plan on the line. Independently of the hops, the account's `promo_clawed_back_cents` is incremented by the reversal amount and `net_promo_credit_cents` is recomputed.

The reversal amount is exactly the schedule's own `provisional_total_cents` and nothing else. The rule reads only the schedule's own projected total and never the account's running totals, so a schedule that was created and then clawed back nets the account to zero: the credited increment and the clawed-back increment cancel. A device plan that is present receives the whole `provisional_total_cents` added to its `remaining_balance_cents` regardless of how much of the credit had actually vested, which is why the account-level reversal stays identical whether the clawback lands before or after `window_end`; only the schedule row's own `vested_total_cents` differs between the two cases, and it is zeroed in the same transition that reverses the credit.


### 3.5. Device Financing, Trade-In Grading and Upgrade Eligibility

Financing turns a retail price into a level monthly installment. A care agent quotes a plan by supplying the `subscriber_line_id` of the line that will carry it, a `device_model`, the `device_price_cents` of the device at full retail, an optional `down_payment_cents` paid up front (which defaults to 0), and the `installment_months` over which the balance is repaid. An optional `activation_at` may also be supplied, which activates the plan in the same call rather than leaving it quoted. The plan is created in `plan_state` `QUOTED`, and creating it increments the attached line's `version` by one, which is why this operation requires `expected_subscriber_line_version` as §2.7 describes. A plan carries a `financed_at` instant that is null until activation, a `trade_in_credit_cents` defaulting to 0, a `remaining_balance_cents` defaulting to 0, a `monthly_installment_cents` defaulting to 0 and an `upgrade_eligible_at` that is null until the plan is financed. `device_price_cents` and `installment_months` are required integers, `device_model` a required string, and `installment_months` must be at least 1; when the plan is created without an `activation_at` it is left `QUOTED` with a null `financed_at` and a null `upgrade_eligible_at`, and the financing arithmetic is nonetheless already applied, so a quoted plan already shows the financed balance and the leveled installment it would carry.

The installment arithmetic is pinned in a particular order, and the order is not incidental. The financed balance is the full device price less the down payment, floored at zero so that an excessive down payment can never produce a negative balance. The regular monthly installment is that financed balance divided by `installment_months` with the remainder discarded — the per-installment amount is floored, never rounded — and the entire remainder is then assigned to the first installment, which is therefore as large as or larger than every subsequent one. A quoted plan whose down payment covers the whole price has a financed balance of zero and therefore a zero installment. When no trade-in credit has yet been settled, `remaining_balance_cents` is simply the financed balance, because the trade-in credit is zero.

Only one installment plan exists per subscriber line at a time, and a plan that has already been converted to the postpaid account by a migration is excluded from upgrade-eligibility evaluation. When an `activation_at` is supplied, the plan's `financed_at` is set to `activation_at` and `upgrade_eligible_at` is computed from it as `financed_at` plus half of `installment_months` billing cycles, with a billing cycle counted as 30 days; the halving discards any remainder, so a five-month plan becomes upgrade-eligible after two billing cycles. The plan then enters `ACTIVE`, unless the supplied `activation_at` is already at or after that computed `upgrade_eligible_at`, in which case it enters `UPGRADE_ELIGIBLE` directly. Activation is refused while the attached line already carries a `DeviceInstallmentPlan` in `plan_state` `ACTIVE`, and that refusal is `ERR_DEVICE_PLAN_STATE` (409); a plan already `UPGRADE_ELIGIBLE` is financed and still in force, so it blocks a fresh activation exactly as an `ACTIVE` one does. Whenever a plan's `plan_state` is recomputed rather than set directly, it is derived the same way: a plan already `CONVERTED` stays `CONVERTED`, a plan with a null `financed_at` stays `QUOTED`, and a financed plan reads `UPGRADE_ELIGIBLE` once the current logical clock instant is at or after its `upgrade_eligible_at` and `ACTIVE` before that. Because that derivation is governed by the clock, a plan that is `ACTIVE` and whose clock reaches its `upgrade_eligible_at` is promoted to `UPGRADE_ELIGIBLE` by the next advance of the clock, without any client request; this is what makes the plan's `plan_state` a function of its financing position rather than a value frozen at activation.

A trade-in begins as a customer self-report and is corrected by inspection, and the API stores both. To submit one, the customer's care agent supplies the `installment_plan_id` of the plan the credit will be applied to, the `device_model` being traded in, and the customer's `declared_condition` — one of `FLAWLESS`, `GOOD`, `FAIR`, `POOR` or `BROKEN`. The named plan must exist, or the submission fails with `ERR_INSTALLMENT_PLAN_NOT_FOUND` (404). The assessment is created in `assessment_state` `SUBMITTED`, with a `submitted_at` instant, and the estimated credit, written to `estimated_credit_cents`, is looked up from the condition the customer declared. Each condition carries a fixed value in cents: `FLAWLESS` is 60 000, `GOOD` is 42 000, `FAIR` is 24 000, `POOR` is 8 000 and `BROKEN` is 0. The estimated credit is also written to the attached plan's `trade_in_credit_cents` until grading occurs, which is why an ungraded trade-in already reduces the shown balance. Until that settlement happens the plan's `remaining_balance_cents` and its `monthly_installment_cents` are left exactly where the quote put them; the estimate is carried as the plan's `trade_in_credit_cents` at this stage without those two figures being recomputed from it. An assessment also carries a `parent_plan_id` whose value always mirrors its `installment_plan_id`, so assessments can be listed per plan without a second join. A `declared_condition` outside the five recognized values is refused with `ERR_INVALID_REQUEST` (400), as is a missing `device_model` or `installment_plan_id`. A newly created assessment carries a null `graded_condition`, a null `graded_at`, a `final_credit_cents` of 0 and a `grade_delta_cents` of 0 until the inspector grades it.

The bulk valuation of a trade-in arrives through the assessor's grade, and the `grade_delta_cents` that follows from comparing the two is the API's honest record of how far the customer's self-report was from the truth:

| Declared or graded condition | Credit value in cents |
| --- | --- |
| `FLAWLESS` | 60000 |
| `GOOD` | 42000 |
| `FAIR` | 24000 |
| `POOR` | 8000 |
| `BROKEN` | 0 |

Grading is performed by a warehouse inspector and takes a single `graded_condition` value drawn from the same five-value set. It is available while the assessment is in `SUBMITTED`. The credit being settled must land on a plan that is `ACTIVE`, and grading against a plan in any other state is refused with `ERR_PLAN_NOT_ACTIVE` (409). On grading, the assessment moves to `assessment_state` `GRADED`, its `graded_condition` is set to the supplied value, and `graded_at` is stamped with the current logical clock instant. The final credit, written to `final_credit_cents`, is looked up from the inspector's `graded_condition` using the same five-value table, and `grade_delta_cents` is computed as `final_credit_cents` minus `estimated_credit_cents` — a negative delta means the device graded worse than the customer declared, and a zero delta means the self-report was accurate. If the delta is negative the customer owes more than the quote implied; the estimate is not silently rewritten to match, and both numbers remain on the record.

The graded credit is then settled against the plan. The plan's `trade_in_credit_cents` is set to `final_credit_cents`, and the plan's `remaining_balance_cents` is recomputed as the greatest of the device price less the down payment less the final credit, and zero — the balance floors at zero rather than turning negative when a generous trade-in exceeds what is owed. The plan's `monthly_installment_cents` and `plan_state` are then recomputed by the same installment rule described above, applied to the new remaining balance; because the plan's `plan_state` is re-derived from its financing position rather than re-quoted, a plan that was already financed keeps its `ACTIVE` or `UPGRADE_ELIGIBLE` position through the settlement.

### 3.6. Underwriting a Line Addition

Before any of this can happen the customer must have an account, and an account is opened by a platform operator who declares its `account_type` — either `FAMILY` or `BUSINESS` — and the `tax_id_last4`, the final four characters of the account holder's tax identifier, which must be exactly four characters long. The operator may also supply a `payment_history_score` and an `existing_deposit_cents`, and when both are omitted the account is opened with a score of 500 and no deposit on file. A supplied `payment_history_score` must be an integer between 0 and 1000 inclusive, or the create is refused with `ERR_INVALID_REQUEST` (400); `account_type` must be `FAMILY` or `BUSINESS`, and `tax_id_last4` must be a string of exactly four characters — the final four characters of the account holder's tax identifier, which must be exactly four characters long. An account is created in `account_status` `OPEN`, and opening it derives its `credit_class` and `deposit_required_cents` from its `payment_history_score`, its `existing_deposit_cents` and its `active_line_count` through the same credit-class rule that underwrites line additions, so a new account's class is never left unset. The `account_status` dimension is otherwise quiet in this API: it is set to `OPEN` when a port cutover completes on one of the account's lines, and set to `SUSPENDED` when a migration eligibility evaluation finds one of the account's lines protected. An account's `account_status` is one of `OPEN`, `SUSPENDED` or `CLOSED`, and an account is never created in any status other than `OPEN`; although the lifecycle declares `CLOSED` as well, no operation in this API moves an account into it. Four further account fields are maintained by the server rather than by the operator: `active_line_count`, the count of the account's lines whose `service_status` is `ACTIVE`; `reserved_mdn_count`, the count of its reservations in `reservation_state` `HELD`; and the promotional ledger pair `promo_credited_cents` and `promo_clawed_back_cents` described in §3.4. Each of these begins at 0 on a freshly opened account, as does `deposit_required_cents` when the derived class calls for no deposit, and each is recomputed by the operations that touch the resources it counts. Alongside them sits `net_promo_credit_cents`, the conserved promotional ledger quantity defined as `promo_credited_cents` minus `promo_clawed_back_cents`, which likewise begins at 0.

A customer expanding a family or business account asks for additional lines rather than adding them outright, because the request must be underwritten first. The request is opened with the `account_id` of the account being expanded and a `line_count` naming how many lines are wanted; that count must be at least 1 and at most 10, and any value outside that range is rejected with `ERR_LINE_COUNT_OUT_OF_RANGE` (422). The customer may also name a `requested_mdn` — the directory number they would like reserved for the first of the new lines — or leave it out and let the system choose, in which case the field is stored as null. A request is created in `request_state` `SUBMITTED` with `submitted_at` stamped, a `determined_credit_class` that is not yet assigned, a `required_deposit_cents` of 0, a null `decision_note`, and a `parent_account_id` whose value always mirrors its `account_id` so that requests can be listed per account without a second join. The `account_id` must resolve to an existing account before the `line_count` range test is applied, and `line_count` must be an integer.

Underwriting is performed by a credit analyst, who supplies a `decision` and may optionally supply a `decision_note`. In every case the server first determines the class and the deposit using the review variant of the credit-class rule, writing both to the request's `determined_credit_class` and `required_deposit_cents`. The determination runs against the account's `payment_history_score`, which is an integer between 0 and 1000 inclusive and defaults to 500 when the account was opened without one, and against `active_line_count`, which counts only the account's lines whose `service_status` is `ACTIVE` — lines that are `SUSPENDED` or `CANCELLED` are excluded from the count. The class ladder is read off the score: a score below 300 yields `BLOCKED`; a score from 300 up to but not including 500 yields `CLASS_D`; from 500 up to but not including 650 yields `CLASS_C`; from 650 up to but not including 800 yields `CLASS_B`; and a score of 800 or above yields `CLASS_A`. One adjustment is then applied: if the line count the account would hold after this addition — the current active line count plus the request's `line_count` — is 5 or more, and the class read off the score was `CLASS_A` or `CLASS_B`, the determined class is downgraded to `CLASS_C`. Accounts with four or fewer lines after the addition keep the class the score earned them. The deposit that follows from the class is fixed per class: `CLASS_A` requires 0 cents, `CLASS_B` requires 10 000 cents, `CLASS_C` requires 25 000 cents, `CLASS_D` requires 50 000 cents, and `BLOCKED` requires 0 cents, since a blocked request never gets far enough to owe a deposit.

Approval is a decision with several gates, and the order matters. The request must still be in `SUBMITTED`. The determined class must not be `BLOCKED` — if it is, the approval fails with `ERR_CREDIT_CLASS_BLOCKED` (403), and because the class determination precedes the deposit test, a blocked customer never sees a deposit error. The count of the account's `ACTIVE` lines plus the request's `line_count` must be at or below 10, or the approval fails with `ERR_LINE_LIMIT_EXCEEDED` (409), and this ceiling is tested before the deposit so that an over-limit request that also lacks a deposit surfaces as the line-limit error rather than as `ERR_DEPOSIT_REQUIRED`. Only then is the deposit compared: the account's `existing_deposit_cents` — the deposit already on file, which defaults to 0 at account creation — must be at or above the request's computed `required_deposit_cents`, and a shortfall is refused with `ERR_DEPOSIT_REQUIRED` (402). When all of these pass, the review variant has already written the class and deposit onto the request, and the account's `credit_class` and `deposit_required_cents` are set to those determined values, and the request's `request_state` becomes `APPROVED`. The `decision_note` recorded on the request is set to the supplied `decision_note` when one was given and to a derived explanation of the assigned class otherwise. The account's `active_line_count`, `credit_class` and `deposit_required_cents` are all recomputed as part of this operation.

A decline is the simpler sibling branch: it also requires the request to be in `SUBMITTED`, it also writes the determined class and deposit through the review variant, and it too recomputes the account's `active_line_count`, but it moves `request_state` to `DECLINED`. Its one account-level effect is conditional — the account's `credit_class` is set to `BLOCKED` when the determined class is `BLOCKED`, and is otherwise left alone, so declining a perfectly good applicant does not damage their account; the account's `deposit_required_cents` is likewise left where it stood. When the request is later provisioned, the credit-class calculation is re-evaluated with the post-addition active line count and this time overwrites both the account's `credit_class` and its `deposit_required_cents`.


### 3.7. The Line Itself: Service, Numbers and Tenure

The subscriber line is where the two independent dimensions of a mobile number meet. Service is tracked by `service_status`, which takes one of `PROVISIONED`, `ACTIVE`, `SUSPENDED` or `CANCELLED`; the number itself is tracked by `number_status`, which takes one of `UNASSIGNED`, `RESERVED`, `PORTED_IN`, `ASSIGNED` or `RECLAIMED`. The two evolve independently and a change in one never implies a change in the other unless a rule here says so explicitly. A newly created line is `PROVISIONED` in service and `UNASSIGNED` in number, and it carries whatever `mdn` the creating operator supplied, a `billing_mode` which defaults to `PREPAID` and is only ever `PREPAID` or `POSTPAID`, a null `line_opened_at`, a `loyalty_tenure_months` of 0, a `retention_cycle_count` of 0, a `promo_eligibility_state` of `INELIGIBLE`, a `port_protection_status` of `UNPROTECTED` and a null `cancellation_effective_at`.

A directory number is unique across the fleet in a qualified sense rather than absolutely: the same ten digits may not be held by two lines whose `number_status` is anything other than `RECLAIMED`, so a number that has been reclaimed by the pool can be reissued to a fresh line. Creating a line whose `mdn` collides with a line already holding it as `ASSIGNED`, `RESERVED` or `PORTED_IN` is refused with `ERR_MDN_CONFLICT` (409). A line is created by naming an `account_id`, which must resolve to an existing account, and an `mdn`. Creating a line also recomputes the owning account's `active_line_count` as the count of that account's lines whose `service_status` is `ACTIVE`, and recomputes the account's `credit_class` and `deposit_required_cents` through the credit-class rule.

Activation is what starts service. An operator activates a line that is still `PROVISIONED`; the operation accepts an optional `activation_at` instant, and it sets `service_status` to `ACTIVE`, sets `number_status` to `ASSIGNED` when it was `UNASSIGNED` (leaving an already-assigned, reserved or ported-in number alone), and stamps `line_opened_at` with the current logical clock instant when it is still null. Because service has begun, the line's `loyalty_tenure_months` and `retention_cycle_count` are both recomputed, and the owning account's `active_line_count` is recomputed again. Tenure is measured in whole months between `line_opened_at` and the current logical clock instant, while retention cycles are the count of completed monthly billing cycles since `line_opened_at` with any partial cycle discarded — flooring, never rounding.

Cancellation stops service and starts a clock of a different kind. An operator or a care agent cancels a line by supplying a `reason_code`, which sets `service_status` to `CANCELLED` and stamps `cancellation_effective_at` with the current logical clock instant. Cancelling a line that is already `CANCELLED` is refused with `ERR_INVALID_STATE` (409), and a body without a `reason_code` is refused with `ERR_INVALID_REQUEST` (400). That instant is the exclusive lower bound of the reclamation window the line's number now enters: the number is not immediately free, and it is not immediately the pool's either. Cancelling a line also stamps the system's `last_line_cancellation_deadline` as the current logical clock instant plus `line_cancellation_grace_hours`, which defaults to 24 hours, and recomputes the owning account's `active_line_count`. The `reason_code` is required and must be a string, but it is not validated against any catalogue and carries no further effect.

The reclamation itself is not automatic on the cancellation instant. It happens when a platform operator runs the ops-run sweep with a `triggered_at` instant, and the sweep is idempotent per deadline: the server compares `triggered_at` against `last_line_cancellation_deadline` and, when `triggered_at` is strictly after that deadline, increments the system's `ops_run_epoch` by one, sets `last_ops_run_at` to `triggered_at`, and sets `number_status` to `RECLAIMED` on every subscriber line whose `service_status` is `CANCELLED` and whose `number_status` is `ASSIGNED`. When `triggered_at` is at or before the deadline the sweep is a no-op apart from recording the instant: `ops_run_epoch` is left unchanged and `last_ops_run_at` is set to `triggered_at`, and every subscriber line that was reclaimed has its own `version` incremented as a modification. The response to an ops run is the `SystemConfig` row itself. The response to recording a rejection is the rejection record itself, not the whole port request, and it is answered with a 201 because a new log entry — the resource being created — has been appended. This is the mechanism by which a cancelled line's number returns to the pool and becomes eligible for a new assignment.

Two line-level derived values deserve naming because other workflows depend on them. The line's `port_protection_status` is `PROTECTED` exactly when the line has a `PortProtectionCase` in `case_state` `ACTIVE`, and `UNPROTECTED` otherwise. The line's `promo_eligibility_state` is a rollup of the line's promotional posture across its `PromoCreditSchedule` rows, beginning at `INELIGIBLE`, moving to `PROVISIONAL_ELIGIBLE` when a schedule is created, to `VESTED` when a schedule vests, and to `CLAWED_BACK` when a schedule is reversed. One line-level rollup is driven by the port cutover rather than by the promotion itself: when a cutover completes and recomputes the line's `retention_cycle_count`, the line's `PromoCreditSchedule` row that is still `PROVISIONAL` is moved to `schedule_state` `ACTIVE` once `retention_cycle_count` has reached that schedule's `retention_requirement_cycles`.

### 3.8. Cutover Completion and the Line-Side Cascade

Both the port-in workflow and the migration workflow end at a cutover, and both are driven by the logical clock rather than by a request. For a port-in, the trigger is the clock reaching the request's `requested_cutover_at` while the request is in `ACCEPTED_PENDING_CUTOVER`; for a migration, the trigger is the clock reaching the migration's `requested_cutover_at` while the migration is in `CUTOVER_SCHEDULED`. In both cases the clock-comparison precondition is that the current logical clock instant is at or after the requested instant.

The port cutover cascade runs in four ordered hops, each of which exists because the previous one changed something. First, `cutover_completed_at` is stamped with the current logical clock instant, the attached line's `service_status` is set to `ACTIVE`, and its `number_status` is set to `PORTED_IN`. Second, because the line's `service_status` has just become `ACTIVE`, `line_opened_at` is stamped with the current logical clock instant when it is still null. Third, because `line_opened_at` was just stamped, `loyalty_tenure_months` and `retention_cycle_count` are both recomputed. Fourth, because `retention_cycle_count` was just recomputed, the attached line's `PromoCreditSchedule` row in `schedule_state` `PROVISIONAL` is moved to `schedule_state` `ACTIVE` when `retention_cycle_count` is at or above that schedule's `retention_requirement_cycles`. The attached line's account additionally has its `account_status` set to `OPEN`, which repairs an account a migration had suspended.

The migration cutover cascade is described in §3.3. What the two share is the shape: both stamp a completion instant, both move the line's number into its final state (`PORTED_IN` for a port-in, `ASSIGNED` for a migration), both recompute tenure and retention cycles, and both are the trigger for downstream financial consequences — the promotional activation above for a port-in, and the balance carry and proration credit for a migration.

### 3.9. Number Reservations

A reservation holds a specific directory number for an account that has not yet put it into service. An operator or care agent creates one with the `account_id` that will hold it, the `mdn` being held, a `pool_code` naming the number pool the digits belong to, and the `reserved_at` instant that begins the hold. The `account_id` must resolve to an existing account, and `mdn`, `pool_code` and `reserved_at` are each required. The end of the hold is supplied either explicitly as `reserved_until` — the exclusive upper bound of the interval — or implicitly by a `hold_days` value, which defaults to 45 days and from which `reserved_until` is computed as `reserved_at` plus that many days when the caller omits the explicit instant. The hold interval is half-open: `reserved_at` is inside it and `reserved_until` is outside it. A reservation is created in `reservation_state` `HELD`, with a null `committed_line_id`, and creation recomputes the owning account's `reserved_mdn_count`, which counts the account's reservations whose `reservation_state` is `HELD`.

Overlapping holds in the same pool are refused. The requested interval must not overlap an existing `NumberReservation` on the same `pool_code` whose `reservation_state` is `HELD` and whose `reserved_at` is strictly earlier than the new reservation's `reserved_at`; when it would, the creation fails with `ERR_RESERVATION_WINDOW_OVERLAP` (409). The test is on the existing hold's start alone: when the existing hold began strictly earlier and its `reserved_until` is strictly after the new reservation's `reserved_at` the intervals overlap and the create is refused, whereas an existing hold whose `reserved_until` merely coincides with the new `reserved_at` is not an overlap. Two reservations that begin at the same instant, or that are made on different pools, do not conflict.

Committing a reservation turns the held digits into a working line. Only a platform operator may commit one, and it must be `HELD`, the current logical clock instant must be strictly before the reservation's `reserved_until`, and the named `subscriber_line_id` must resolve to a line whose `number_status` is `UNASSIGNED`. A commit attempted at or after `reserved_until` is refused with `ERR_RESERVATION_WINDOW_CLOSED` (409). That open-window test is evaluated ahead of the reservation's state gate, so a hold the clock has already carried past its upper bound reports the closed window rather than the generic `ERR_INVALID_STATE`, while a commit inside an open window against a reservation that is not `HELD` still reports `ERR_INVALID_STATE`. A successful commit sets the reservation's `committed_line_id` to the supplied `subscriber_line_id`, moves the reservation to the terminal `COMMITTED` state, sets that line's `number_status` to `ASSIGNED` and its `mdn` to the reservation's `mdn`, and puts the line into service by setting its `service_status` to `ACTIVE` and stamping `line_opened_at` with the current logical clock instant when it is still null. The owning account's `reserved_mdn_count` and `active_line_count` are both recomputed.

A reservation that is never committed expires on its own. When the logical clock reaches the reservation's `reserved_until` while the reservation is still `HELD`, the reservation moves to `reservation_state` `EXPIRED` and the owning account's `reserved_mdn_count` is recomputed. Expiry is a scheduled transition, so it fires as part of advancing the clock rather than as a client request.


### 3.10. Protecting a Number Against Unauthorized Transfer

Port-out protection is the counterweight to the port-in workflow: it exists so that a line cannot be moved to another carrier just because someone knows enough of the customer's details to file a request. A protection case is opened by an operator or a care agent with a `subscriber_line_id` naming the line to be protected, a `protection_type` describing the kind of freeze being placed — `ACCOUNT_PIN`, `PORT_FREEZE` or `FRAUD_HOLD` — an optional `verified_identity` flag that defaults to false when the caller omits it, and a `reason_code` recording the operator's grounds for opening the case. A case is born in `case_state` `REQUESTED`, with a null `set_at` and a null `cleared_at`. Opening a case by itself changes nothing about the line; the freeze only takes effect when the case is resolved with an activation.

Resolution is a single operation that takes a `resolution` value and branches three ways, each with its own preconditions and its own side effects. An activation is available while the case is `REQUESTED`, and it demands two things before it will proceed. The case's `verified_identity` must be true — a case opened without verification that is then activated is refused with `ERR_IDENTITY_NOT_VERIFIED` (403), which is what stops a fraudulently opened case from being turned into a real freeze. And no other `PortProtectionCase` on the same subscriber line may already have `case_state` `ACTIVE`, or the activation is refused with `ERR_PROTECTION_ALREADY_ACTIVE` (409); a line carries at most one active protection at a time. When both conditions hold, the case moves to `case_state` `ACTIVE`, its `set_at` is stamped with the current logical clock instant, and the attached line's `port_protection_status` is set to `PROTECTED` — which is precisely the state that blocks port submission and resubmission under `ERR_PORT_PROTECTION_ACTIVE`. The competing-case test is measured against the line's `port_protection_status` rather than against a scan of sibling cases: an activation is refused when the line is already `PROTECTED`, and the case being activated is not counted against itself.

A denial is the rejection branch, and it is deliberately lighter. It is available while the case is `REQUESTED`, it carries no verification requirement and no competing-case requirement, and it simply moves the case to `case_state` `DENIED` with `updated_at` recomputed. Denying a case leaves the line's `port_protection_status` untouched, so the line remains exactly as unprotected as it was; a case in `DENIED` is terminal and cannot be reactivated. A case in any state other than the one the requested resolution requires is refused with `ERR_INVALID_STATE` (409), and a `resolution` that is none of the three recognized values is refused with `ERR_INVALID_REQUEST` (400); the resolution value is checked before the case's state, so an unrecognized resolution is reported as a request error rather than as a state error.

A clearance is the release branch and it is the one with reach beyond the protection subsystem. It is available while the case is `ACTIVE`. Clearing the case moves it to `case_state` `CLEARED`, stamps `cleared_at` with the current logical clock instant, sets the case's `set_at` back to null, and sets the attached line's `port_protection_status` to `UNPROTECTED`; a cleared case is terminal. The clearance also reaches into the port workflow: if the line carries a `PortRequest` whose `request_state` is `RESUBMITTED`, that request is set to `REJECTED` and the line's `number_status` is set to `UNASSIGNED`. This reach applies to every such request on the line, not merely the most recent, and the request's `rejection_count`, `last_rejection_code` and `rejections` log are left exactly as they were, so the request reads as rejected without a fresh rejection entry having been recorded; a request in `PENDING` is not touched by a clearance. The practical reading is that clearing a freeze does not silently bless an in-flight port that was pending during the freeze — the request must be resubmitted afresh once the line is unprotected, and the number is released in the meantime. A protection case is otherwise resolved independently of the migration workflow, whose eligibility evaluation consults the line's `port_protection_status` and, when it finds it `PROTECTED`, blocks the migration and suspends the account as §3.3 describes.

### 3.11. Visibility: What Each Role May Read

Reads mirror the workflows above and are available to every role whose work touches the resource. A platform operator, a care agent and a customer may all read an account by its id, which returns the account's `version`, its `active_line_count`, its `credit_class`, its `deposit_required_cents`, and its conservative promotional ledger fields `promo_credited_cents`, `promo_clawed_back_cents` and `net_promo_credit_cents`. The same three roles may read a single subscriber line, which returns its current `version` — the value a client must echo back as `expected_subscriber_line_version` on the three versioned writes — and may list the subscriber lines belonging to one account.

Port requests are readable in two shapes. A single request may be read by a platform operator, a care agent, a credit analyst or a customer, and the per-line collection returns the requests recorded against one subscriber line, oldest first, including the full `rejections` log so that the customer guidance attached to each rejection is visible after the fact; that collection can also be filtered by `supersedes_port_request_id`, matching the field of the same name. Migration requests, installment plans and promotional schedules follow the same pattern: individually readable by the roles involved in their workflow, plus per-line collections for migrations and per-line and per-plan collections for installment plans and the trade-in assessments attached to them. Concretely, the per-line installment-plan collection is readable by platform operators, care agents, trade-in inspectors and customers, the per-plan trade-in collection by platform operators, care agents, trade-in inspectors and credit analysts but not by a customer, and the flat trade-in collection by a customer alone. A `Customer` caller may read only a resource whose owning account is the one named by `X-User-ID`; a resource reachable only through another account is refused with `ERR_UNAUTHORIZED` (403), and because that ownership test follows the resource lookup, a nonexistent id still yields its own 404 first. Protection cases are readable by platform operators, care agents and credit analysts, both as a flat collection and by line, and that collection accepts a `subscriber_line_id` filter, a `case_state` filter, and the standard `limit` and `offset` pagination parameters. The single system configuration row — exposing the `ops_run_epoch`, the cancellation grace window and the promotional window buffer — is readable by platform operators, care agents and customers alike.

A read that names a resource that does not exist fails with the identifier for that resource type: a missing subscriber line yields `ERR_SUBSCRIBER_LINE_NOT_FOUND` (404), a missing account yields `ERR_ACCOUNT_NOT_FOUND` (404), a missing port request yields `ERR_PORT_REQUEST_NOT_FOUND` (404), a missing reservation yields `ERR_RESERVATION_NOT_FOUND` (404), a missing protection case yields `ERR_PROTECTION_CASE_NOT_FOUND` (404), a missing migration request yields `ERR_MIGRATION_REQUEST_NOT_FOUND` (404), a missing line-addition request yields `ERR_LINE_ADDITION_REQUEST_NOT_FOUND` (404), and a missing trade-in assessment yields `ERR_TRADE_IN_ASSESSMENT_NOT_FOUND` (404). A grade attempted against an installment plan that does not exist yields `ERR_INSTALLMENT_PLAN_NOT_FOUND` (404).
