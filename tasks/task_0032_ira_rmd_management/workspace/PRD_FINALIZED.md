# IRA & RMD Management API — Product Requirements Document

## 1. Introduction

Individual Retirement Accounts straddle two worlds that are unforgiving in different ways. On one side sits the Internal Revenue Code: hard-coded annual contribution caps, modified-AGI phase-outs for Roth eligibility, pro-rata rules on Backdoor Roth conversions, the SECURE Act ten-year window for non-eligible beneficiaries, and the Uniform Lifetime Table that drives required minimum distributions starting in the year an owner turns seventy-three. On the other side sits the custodian's recordkeeping reality: contributions that arrive PENDING and must be reconciled before they confirm, distributions that have to be reported on Form 1099-R with a specific box-7 code, and audit trails that have to survive an IRS examination years after the fact. A single mistake — a Roth contribution from an over-the-phase-out filer, an RMD shortfall surfaced after December 31, a Backdoor conversion that ignored the pretax basis sitting in a second Traditional account — turns into a tax penalty letter for the owner and a procedural finding for the custodian.

This document specifies a REST API that consolidates the bookkeeping. The system holds account owners, the IRA accounts they have opened (Traditional or Roth), the contributions, distributions, and Roth conversions that move money in and out, the beneficiary designations that come into force on death, the per-year RMD schedules computed across all of an owner's Traditional accounts, and the 1099-R forms that document every reportable event. A custodian-side operator opens accounts and runs the year-rollover and freeze/unfreeze controls; the owner drives the day-to-day contribution, distribution, and conversion workflow against their own accounts; an IRS auditor has read-only access to the entire body of records. An explicit server clock — settable through a dedicated test-driving capability — anchors all age-threshold, deadline, and tax-year math, so that the system's behavior is reproducible across test runs rather than tied to wall-clock time.

The remainder of this document fixes the contract: the response envelope and pagination, the cross-cutting rules around concurrency and rounding, the per-workflow narratives for contributions, distributions, conversions, beneficiary management, and RMD compliance, the endpoint table that maps capabilities to HTTP, and the canonical error catalogue.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers identifying the caller: `X-User-ID` and `X-User-Role`. If `X-User-Role` is missing or empty the request is rejected with `ERR_MISSING_AUTH` (HTTP 401). If `X-User-Role` is present but is not one of the three role names enumerated below, the request is rejected with `ERR_INVALID_ROLE` (also HTTP 401). When a recognized role is not permitted for the requested endpoint, or when an `AccountOwner` caller's `X-User-ID` does not match the owner of the resource being acted on, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The system recognizes exactly three roles, spelled and capitalized as follows:

- `PlanAdministrator` — the custodian or recordkeeper. Opens owners and accounts, freezes and unfreezes accounts, rejects and reverses contributions and distributions, runs the year-rollover, declares an owner deceased, edits modified AGI on record, sets the server clock, and creates RMD schedules. When `X-User-Role` is `PlanAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it for audit purposes but does not compare it to any entity's `id`.
- `AccountOwner` — the natural person who owns the IRA. Creates and confirms contributions, distributions, and conversions on their own accounts, manages their own beneficiary designations, and may close their own accounts. When `X-User-Role` is `AccountOwner`, `X-User-ID` is the `id` of the acting `AccountOwner`; ownership checks on any resource that references an `AccountOwner` (directly via `owner_id`, or transitively via an account's `owner_id`) compare the resource's foreign-key field to `X-User-ID`.
- `IRSAuditor` — read-only auditor for compliance review. When `X-User-Role` is `IRSAuditor`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it for audit purposes but does not compare it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All list endpoints accept two query parameters, `limit` and `offset`. `limit` defaults to 10, with a minimum of 1 and a maximum of 100; `offset` defaults to 0 and has no upper bound beyond what the underlying collection supports. List results are always ordered by `created_at` ascending, so that pagination remains stable as new rows arrive. The `meta` block on a list response carries four pagination fields: the echoed `limit`, the echoed `offset`, the `total_count` of rows matching the filter prior to pagination, and a boolean `has_more` indicating whether further rows remain past the current page.

### 2.4. Resource Identifiers, Timestamps, and Versioning

Every resource is identified by a server-minted `id` whose value is a UUID emitted as a plain string with no entity-type prefix. Where a request body or query string references another resource (for example `owner_id`, `account_id`, `source_account_id`, `target_account_id`, `distribution_id`, or `conversion_id`), the value follows the same UUID convention.

The resource entities `AccountOwner`, `IRAAccount`, `BeneficiaryDesignation`, `Contribution`, `Conversion`, `Distribution`, and `RMDSchedule` all carry the common timestamp triple — `id`, `created_at`, `updated_at` — plus an integer `version` that starts at 1 on creation and is incremented by 1 on every server-side mutation of that row. The two non-core entities `Form1099R` and `AuditEvent` are append-only artefacts: they carry only `id` and `created_at`, and they have no `updated_at` and no `version` because they are never updated in place once written. The `SystemClock` is a singleton control-plane row and is exposed with only the fields named below; it is not subject to the optimistic-concurrency contract that governs the core entities.

All timestamp fields — `created_at`, `updated_at`, the various transition stamps such as `opened_at`, `closed_at`, `confirmed_at`, `completed_at`, `occurred_at`, the input-supplied `deceased_at`, the computed `secure_deadline_at` and `deadline_at`, and the clock fields `current_utc` and `to_iso8601` — are ISO 8601 UTC strings with three fractional digits.

### 2.5. Nested Resource Retrieval and Path Validation

Whenever a URL contains a templated id (for example a contribution, distribution, or conversion id, or a beneficiary-designation or RMD-schedule id), the path segments are resolved left-to-right. The first segment whose templated id does not resolve to an existing entity yields `ERR_NOT_FOUND` (HTTP 404). State-of-resource checks and business validations only run after every path id has resolved.

### 2.6. Validation Ordering and Precedence

When a single request body could trip several validations, the system evaluates them in a fixed priority sequence so that the surface error is determined by which check fired first rather than by implementation order. The sequence runs as follows. First, authentication: the `X-User-Role` header presence check, then the recognized-role check, then for owner-scoped action endpoints (`POST` on contributions, contribution confirm, distributions, distribution confirm, conversions, conversion complete, and account close) the `X-User-ID` to `AccountOwner.id` ownership check. Second, existence: every templated path id must resolve, as described in §2.5. Third, state: for action endpoints the target entity must be in the from-state declared by the relevant transition, with rejection code `ERR_INVALID_STATE` (HTTP 409). Fourth, optimistic-concurrency stale-version: on the two endpoints listed in §2.7, the `expected_account_version` value must match the account's current `version`, otherwise `ERR_STALE_VERSION` (HTTP 412) is returned. Only after these gate checks pass do the business-domain validations run — referential symmetry on conversion source/target pairs (`ERR_INVALID_CONVERSION_PAIR`), kind-versus-account compatibility on contributions (`ERR_KIND_ACCOUNT_MISMATCH`), tax-year matching on contribution confirm (`ERR_TAX_YEAR_CLOSED`), the beneficiary-share-sum check on designation activation (`ERR_BENEFICIARY_SHARES_INVALID`), the contribution cap (`ERR_CONTRIBUTION_CAP_EXCEEDED`), the distribution balance check (`ERR_INSUFFICIENT_BALANCE`), and the SECURE-deadline check on inherited Traditional accounts with a non-eligible-individual beneficiary (`ERR_SECURE_DEADLINE_PASSED`). Malformed payloads — a required field missing, an enum value out of range, or a type mismatch — surface as `ERR_INVALID_REQUEST` (HTTP 400) during request parsing, before any of the above evaluate.

### 2.7. Optimistic Concurrency on Account-Bound Confirmations

Two endpoints — confirming a `PENDING` contribution and confirming a `PENDING` distribution — are guarded by optimistic concurrency on the parent `IRAAccount`. Both endpoints require the request body to carry `expected_account_version`, the integer value of the account's `version` as the client last observed it. The server compares this value to the target account's current `version` at the moment of confirmation; if they differ, the confirm is rejected with `ERR_STALE_VERSION` and HTTP 412, and no balances or audit records are touched.

The contribution-confirm rule guards against the case where another writer just confirmed a different contribution against the same account, which bumped `ytd_contribution_cents` and the account's `version`. Without the version check, the current client's view of cap headroom would be stale and a cap-exceeding confirm could slip through. The distribution-confirm rule similarly guards against an offsetting distribution having already drained the cash balance below what the current client's view assumes. In both cases the goal is to prevent a writer from acting on a parent-account snapshot it has not observed.

Endpoints that mutate the parent account through other code paths — owner-AGI patch, owner-declare-deceased, account freeze, account unfreeze, account close, conversion initiate, conversion complete, conversion reverse, contribution reverse, distribution reverse — likewise consume an `expected_<parent>_version` field as named in the endpoint catalogue (`expected_owner_version`, `expected_account_version`, or `expected_source_account_version` depending on the parent entity). Endpoints that are not listed in any concurrency rule and do not appear in the endpoint catalogue with a version input do not take a version field. All transitions that mutate a row refresh its `updated_at` to the server's current clock and increment its `version` by exactly 1.

### 2.8. Hierarchical Consistency and Cascading Side Effects

Many mutations on this API cascade. Confirming a contribution against an `IRAAccount` mutates that account's `cash_balance_cents`, its `ytd_contribution_cents`, and one of `pretax_basis_cents` or `aftertax_basis_cents` depending on the contribution's tax character, and it appends an `AuditEvent` with `event_kind` of `CONTRIBUTION_CONFIRMED`. Confirming a distribution moves the same account's balance the other way, splits the basis decrement across `pretax_basis_cents` and `aftertax_basis_cents`, may advance the relevant `RMDSchedule` toward `SATISFIED`, generates a `Form1099R`, appends an `AuditEvent` with `event_kind` `DISTRIBUTION_CONFIRMED`, and triggers a recomputation of `AccountOwner.rmd_posture` across all of that owner's Traditional accounts. Completing a conversion mutates both the source and target accounts, generates a `Form1099R` with `distribution_code` of `G`, and appends an `AuditEvent` with `event_kind` of `CONVERSION_COMPLETED`. Declaring an owner deceased cascades into every owned account, every active beneficiary designation on those accounts, and every open RMD schedule. Wherever a parent mutation cascades into child rows, every touched row has its `updated_at` refreshed and its `version` incremented by 1, with the order and full set of effects given by the workflow narratives in §3.

### 2.9. Monetary Precision and Calculation Rounding

All monetary fields in the system — `cash_balance_cents`, `pretax_basis_cents`, `aftertax_basis_cents`, `ytd_contribution_cents`, `amount_cents` (on contributions, distributions, and audit events), `gross_amount_cents`, `taxable_amount_cents`, `nontaxable_amount_cents`, `federal_withholding_cents`, `required_amount_cents`, `satisfied_amount_cents`, `gross_distribution_cents`, and `modified_agi_cents` — are integer counts of cents. There is no fractional-cent representation anywhere in the API surface.

All calculations preserve integer-cent precision throughout. Where a calculation must reduce a ratio (the Backdoor Roth pro-rata split, the Traditional-distribution basis split, the RMD divisor application), the system uses sum-then-divide ordering — operands are summed in cents first, then the final ratio step is taken — and the final divide truncates toward zero (floor division). Any cent of remainder produced by a floor at the final step is absorbed by the taxable side or the pretax side as specified in §3, never silently dropped. The Roth eligibility phase-out produces an intermediate allowance in cents that is then floored to the nearest multiple of 1,000 cents (ten dollars) before being returned as headroom; the floor is applied at the end of the formula, after the reduction has been computed.

### 2.10. Explicit Server Clock

The system reads the current instant from an explicit, settable `SystemClock` rather than from wall-clock time, so that age-threshold math, RMD deadlines, SECURE-Act deadlines, and tax-year identification are reproducible. The clock exposes two fields: `current_utc`, the explicit ISO 8601 instant set by the operator, and `current_tax_year`, a four-digit integer derived from `current_utc` (it is the calendar year of `current_utc` interpreted in UTC). Setting the clock through the test-driving capability supplies a `to_iso8601` value, writes it into `current_utc`, and recomputes `current_tax_year`.

## 3. Business Logic & Workflows

### 3.1. Owner Registration, Identity, and Demographic Inputs

A new owner is registered by a `PlanAdministrator` supplying a `full_name`, a `date_of_birth` (ISO 8601 date), the last four numeric digits of the owner's SSN or ITIN as `tax_id_last4` (this value must be exactly four numeric characters and is what eventually renders into the recipient block of the 1099-R), a federal `filing_status` drawn from the set `SINGLE`, `MARRIED_JOINT`, `MARRIED_SEPARATE`, and `HEAD_OF_HOUSEHOLD`, and optionally an initial `modified_agi_cents` value for the current tax year. If `modified_agi_cents` is omitted the system stores it as 0. The owner is created with `rmd_posture` of `NOT_REQUIRED` and a null `deceased_at`. AGI changes mid-year — for example after a corrected W-2 or 1099 — are applied through the owner's AGI patch capability, which is `PlanAdministrator`-exclusive, takes a new `modified_agi_cents` value and `expected_owner_version`, refreshes `updated_at`, and bumps the owner's `version` by 1.

Two fields on `AccountOwner` are demographic gates that quietly drive the rest of the system. The `date_of_birth` determines when the catch-up contribution band opens (the tax year in which the owner reaches age fifty by December 31), when the RMD obligation lands (the tax year in which the owner reaches age seventy-three by December 31), and how box-7 of any 1099-R is coded for that owner's distributions (the fifty-nine-and-a-half boundary disambiguates `EARLY` versus normal). The `filing_status` enters the Roth eligibility phase-out math at contribution-confirm time.

### 3.2. Opening and Operating an IRA Account

A `PlanAdministrator` opens an account on behalf of an owner by supplying an `owner_id` and an `account_type` of either `TRADITIONAL` or `ROTH`. The system stamps `opened_at` to the server clock's current instant, sets `status` to `ACTIVE`, initializes `cash_balance_cents`, `pretax_basis_cents`, `aftertax_basis_cents`, and `ytd_contribution_cents` to zero, sets `tax_year_marker` to the clock's `current_tax_year`, and leaves `closed_at` null.

While the owner is alive and the account is operating normally, the `PlanAdministrator` retains two administrative levers: freezing the account and unfreezing it. Freezing is a transition from `ACTIVE` to `FROZEN`; it is permitted only when no contribution against this account is in `PENDING` and no distribution against this account is in `PENDING`. A frozen account rejects new contributions, distributions, and conversion initiations under the standard from-state rule. Unfreezing returns the account from `FROZEN` to `ACTIVE` and is permitted only if `deceased_at` on the owner is null — once the owner has died, the cascade into `INHERITED` is the only path forward and the unfreeze lever is locked out.

Closing an account requires that `cash_balance_cents` equal zero. A `PlanAdministrator` may close an account that has reached the `INHERITED` state once `cash_balance_cents` is zero and every child contribution, distribution, and conversion row is in a settled terminal status (none remain in `PENDING` or `INITIATED`); the transition runs from `INHERITED` to `CLOSED`. An `AccountOwner` may close their own `ACTIVE` account only when `cash_balance_cents` is zero, when their own `deceased_at` is null, and when no `RMDSchedule` for this owner against this Traditional account is in `OPEN`; the transition runs from `ACTIVE` to `CLOSED`. In either case `status` advances to `CLOSED`, `closed_at` is stamped, `updated_at` is refreshed, and `version` is incremented by 1. `CLOSED` is terminal.

### 3.3. Contributions: Cap Math, Catch-Up, and Roth Phase-Out

An `AccountOwner` creates a contribution against one of their accounts by supplying an `account_id`, a four-digit `tax_year`, a positive integer `amount_cents`, and a `contribution_kind` of `PRETAX`, `AFTERTAX`, or `ROTH`. The contribution lands in `PENDING` and persists in that state until either a `PlanAdministrator` rejects it (moving it to `REJECTED`) or the owner confirms it (moving it to `CONFIRMED`). The confirm step takes `expected_account_version` in its body.

At confirm time the system runs four business-domain checks in addition to the general ordering described in §2.6. First, the contribution kind must be compatible with the account type — `ROTH` contributions are permitted only against `ROTH` accounts, and `PRETAX` and `AFTERTAX` contributions are permitted only against `TRADITIONAL` accounts; a mismatch rejects with `ERR_KIND_ACCOUNT_MISMATCH`. Second, the contribution's `tax_year` must equal the account's `tax_year_marker` at the moment of confirmation; a contribution created before a year-rollover and confirmed after it is rejected with `ERR_TAX_YEAR_CLOSED`. Third, the sum of the account's existing `ytd_contribution_cents` and the contribution's `amount_cents` must not exceed the per-year contribution limit for this owner, account type, and tax year (see below); breach yields `ERR_CONTRIBUTION_CAP_EXCEEDED`. Fourth, if the contribution is `ROTH`, the Roth eligibility phase-out for the owner's `modified_agi_cents` and `filing_status` must return a strictly positive headroom; if the phase-out returns zero (the owner's modified AGI is at or above the ceiling for their filing status), the confirm is rejected with `ERR_CONTRIBUTION_CAP_EXCEEDED` against an effective cap of zero. The account must also be `ACTIVE` for the confirm to proceed.

The contribution limit is computed as follows. First, the owner's age at the end of the tax year is taken as the integer year difference between December 31 of the `tax_year` and `date_of_birth`. A base limit applies to every owner: 700,000 cents (seven thousand dollars) for tax years 2024 and 2025, and 750,000 cents (seven thousand five hundred dollars) for tax year 2026. A catch-up addition is granted when the owner is at least fifty years old at year-end: 100,000 cents (one thousand dollars) for tax years 2024 and 2025, and 110,000 cents (eleven hundred dollars) for tax year 2026; an owner younger than fifty receives no catch-up. For a `TRADITIONAL` account the contribution limit is simply the sum of the base and the catch-up (zero or one thousand or eleven hundred dollars, as applicable). For a `ROTH` account the same combined limit becomes the input headroom to the phase-out described next, and the phase-out's return value is the effective cap.

The Roth eligibility phase-out works against a table of `(floor, ceiling)` modified-AGI brackets keyed by `tax_year` and `filing_status`. For tax year 2024 the brackets are: `SINGLE` and `HEAD_OF_HOUSEHOLD` 14,600,000 cents to 16,100,000 cents, `MARRIED_JOINT` 23,000,000 cents to 24,000,000 cents, `MARRIED_SEPARATE` 0 cents to 1,000,000 cents. For 2025 the brackets are: `SINGLE` and `HEAD_OF_HOUSEHOLD` 15,000,000 cents to 16,500,000 cents, `MARRIED_JOINT` 23,600,000 cents to 24,600,000 cents, `MARRIED_SEPARATE` 0 cents to 1,000,000 cents. For 2026 the brackets are: `SINGLE` and `HEAD_OF_HOUSEHOLD` 15,400,000 cents to 16,900,000 cents, `MARRIED_JOINT` 24,200,000 cents to 25,200,000 cents, `MARRIED_SEPARATE` 0 cents to 1,000,000 cents. If `modified_agi_cents` is less than or equal to the floor, the full headroom passes through unreduced. If `modified_agi_cents` is greater than or equal to the ceiling, the allowance is zero — no Roth contribution may confirm. Otherwise the system computes a linear in-band reduction: take the difference between `modified_agi_cents` and the floor, multiply by the headroom in cents, then floor-divide by the width of the band (ceiling minus floor); subtract that reduction from the headroom; finally, floor the resulting allowance to the nearest multiple of 1,000 cents (ten dollars) by integer-dividing by 1,000 and re-multiplying by 1,000. The phase-out is sum-then-floor: the floor-to-thousand-cents step happens once, at the very end of the formula, not on any intermediate value.

Upon a successful confirm the system stamps `confirmed_at`, advances the contribution's `status` to `CONFIRMED`, adds `amount_cents` to the account's `cash_balance_cents`, adds `amount_cents` to the account's `ytd_contribution_cents`, adds `amount_cents` to `pretax_basis_cents` if `contribution_kind` is `PRETAX` or to `aftertax_basis_cents` if it is `AFTERTAX` (Roth contributions touch neither pretax nor aftertax basis), appends an `AuditEvent` with `event_kind` `CONTRIBUTION_CONFIRMED` and `amount_cents` equal to the contribution amount, refreshes the account's `updated_at`, and increments the account's `version` by 1.

A `PlanAdministrator` may reject a `PENDING` contribution at any time before confirm; the contribution moves to `REJECTED` and no balances change. A `PlanAdministrator` may also reverse a `CONFIRMED` contribution, but only inside the same tax year — concretely, the contribution's `confirmed_at` must lie in the period in which the account's current `tax_year_marker` is still the same as at confirmation — and only if `cash_balance_cents` is at least `amount_cents`. Reversal walks the same balance arithmetic in the opposite direction: `cash_balance_cents`, `ytd_contribution_cents`, and the relevant basis bucket each lose `amount_cents`; the contribution moves to `REVERSED`; `updated_at` is refreshed; `version` increments by 1. `REJECTED` and `REVERSED` are terminal for a contribution, as is `CONFIRMED` once year-rollover passes.

### 3.4. Distributions and 1099-R Generation

An `AccountOwner` initiates a distribution by supplying an `account_id`, a positive integer `amount_cents`, a `distribution_reason` drawn from `NORMAL`, `EARLY`, `RMD`, `INHERITED`, `ROLLOVER`, and `RETURN_OF_CONTRIBUTION`, a `tax_year`, and an optional `federal_withholding_cents` value that defaults to zero. The distribution is created in `PENDING`. Confirming the distribution requires `expected_account_version` and is permitted only when the account's `status` is either `ACTIVE` or `INHERITED`. Three further business checks are run at confirm time. First, `amount_cents` must not exceed `cash_balance_cents` and `federal_withholding_cents` must not exceed `amount_cents`; either violation yields `ERR_INSUFFICIENT_BALANCE`. Second, if `distribution_reason` is `RMD` there must be an `OPEN` (or, on a late-cure, a `DELINQUENT`) `RMDSchedule` for this owner and this `tax_year`; the schedule is what the satisfied amount accumulates against. Third, on an `INHERITED` Traditional account whose active beneficiary relationship is `NON_ELIGIBLE_INDIVIDUAL`, the SECURE Act ten-year rule forbids a confirm that would leave any positive `cash_balance_cents` standing past the beneficiary's `secure_deadline_at` — measured against the system clock at confirmation — and such a confirm is rejected with `ERR_SECURE_DEADLINE_PASSED`.

On a successful confirm, `confirmed_at` is stamped, the distribution moves to `CONFIRMED`, `cash_balance_cents` decreases by `amount_cents`, and on a `TRADITIONAL` account the basis split runs (see below). If `distribution_reason` is `RMD` the matching `RMDSchedule`'s `satisfied_amount_cents` increases by `amount_cents`; if the post-increase `satisfied_amount_cents` is greater than or equal to the schedule's `required_amount_cents`, the schedule transitions from `OPEN` to `SATISFIED`, or from `DELINQUENT` to `SATISFIED` if the confirm is a late cure. A `Form1099R` row is generated documenting the distribution (see below). An `AuditEvent` with `event_kind` `DISTRIBUTION_CONFIRMED` and `amount_cents` equal to the distribution amount is appended. `AccountOwner.rmd_posture` is then recomputed across all owned Traditional accounts to one of `NOT_REQUIRED`, `REQUIRED_PENDING`, `REQUIRED_MET`, or `REQUIRED_DELINQUENT`. The account's `updated_at` is refreshed and `version` is incremented by 1.

On a `TRADITIONAL` account, the distribution's basis split decrements `pretax_basis_cents` and `aftertax_basis_cents` in proportion to their share of the pre-distribution `cash_balance_cents`. Concretely: let pretax be `pretax_basis_cents` and aftertax be `aftertax_basis_cents` immediately before the distribution. If their sum is zero, both basis buckets stay at zero. Otherwise the aftertax decrement is `amount_cents` multiplied by aftertax, floor-divided by the sum of pretax and aftertax; the pretax decrement is `amount_cents` minus the aftertax decrement, so any cent of remainder produced by the floor at the final step is absorbed on the pretax side. Both buckets are then reduced by their respective decrements.

The `Form1099R` generated at distribution confirm is an append-only row that documents the event for the IRS. It carries `distribution_id` set to the distribution's `id` and `conversion_id` set to null (a 1099-R documents either a distribution or a conversion, never both). The `tax_year` is copied from the distribution. `gross_distribution_cents` (1099-R box 1) is set to the distribution's `amount_cents`. `federal_withholding_cents` (1099-R box 4) is set to the distribution's `federal_withholding_cents`. The `ira_sep_simple_flag` (1099-R box 7 checkbox) is set to true for every IRA-sourced transaction. The `taxable_amount_cents` (1099-R box 2a) is computed as follows: on a `ROTH` account it is zero; on a `TRADITIONAL` account whose combined pretax and aftertax basis is zero it equals the gross; otherwise it is the gross minus the nontaxable portion, where the nontaxable portion is the gross multiplied by `aftertax_basis_cents`, floor-divided by the sum of `pretax_basis_cents` and `aftertax_basis_cents`. The `distribution_code` (1099-R box 7) is mapped from `distribution_reason` and the owner's age at the server clock as follows: a `ROLLOVER` is always `G`; an `INHERITED` is always `4`; a `RETURN_OF_CONTRIBUTION` is `8`; if the owner is younger than fifty-nine and a half and the reason is `EARLY`, the code is `1`; if the reason is `RMD`, the code is `7`; otherwise, if the owner is at least fifty-nine and a half, the code is `7`, and in any remaining case the code is `2` (an early distribution taken with an exception).

A `PlanAdministrator` may reverse a `CONFIRMED` distribution within the same tax year — the distribution's `confirmed_at` must lie inside the year currently represented by the system clock, and the `Form1099R` referencing this distribution must also belong to the current tax year. Reversal moves the distribution to `REVERSED`, restores `cash_balance_cents` by `amount_cents`, voids the corresponding `Form1099R` by resetting its `gross_distribution_cents` to zero (the row remains in the audit record, but the gross is zeroed), reduces the matching `RMDSchedule`'s `satisfied_amount_cents` by `amount_cents` if `distribution_reason` was `RMD` (and reverts the schedule from `SATISFIED` back to `OPEN` if the reversal reopens a shortfall), recomputes `AccountOwner.rmd_posture`, refreshes the account's `updated_at`, and increments the account's `version` by 1.

### 3.5. Backdoor Roth Conversions

An `AccountOwner` initiates a Roth conversion — the Backdoor Roth pattern, when funded with `AFTERTAX` Traditional contributions — by supplying `source_account_id`, `target_account_id`, `gross_amount_cents`, and an optional boolean `aggregate_basis`. The source and target must form a valid pair: the source must be `TRADITIONAL` and the target must be `ROTH`, and both accounts must share the same `owner_id`; any violation yields `ERR_INVALID_CONVERSION_PAIR`. The source must be `ACTIVE` and its `cash_balance_cents` must be at least `gross_amount_cents`. Initiation creates the `Conversion` row in `INITIATED`, transitions the source account from `ACTIVE` to `CONVERSION_IN_PROGRESS`, refreshes the source's `updated_at`, and increments the source's `version` by 1. The target account is untouched at this point.

While the conversion is in `INITIATED` the owner may either complete it or reverse it. Reversal (initiated to `REVERSED`) is permitted only while no `Form1099R` has been generated for this conversion; on reversal the source account returns from `CONVERSION_IN_PROGRESS` to `ACTIVE` with no balance changes, and the source's `version` is incremented by 1. Completion (initiated to `COMPLETED`) requires the target Roth account to be `ACTIVE` and consumes `expected_source_account_version`. The complete capability runs the pro-rata split (see below), stamps `completed_at`, sets `taxable_amount_cents` and `nontaxable_amount_cents` on the conversion to the split result, decrements the source's `cash_balance_cents` by `gross_amount_cents`, decrements the source's `pretax_basis_cents` by the share proportional to the taxable split and the source's `aftertax_basis_cents` by the share proportional to the nontaxable split, increments the target Roth's `cash_balance_cents` by `gross_amount_cents`, returns the source's `status` to `ACTIVE`, generates a `Form1099R` with `distribution_code` of `G` referencing the conversion (the form's `distribution_id` is null and its `conversion_id` is the conversion's `id`; its `gross_distribution_cents` equals `gross_amount_cents`; its `taxable_amount_cents` equals the conversion's `taxable_amount_cents`; its `federal_withholding_cents` is zero; the `ira_sep_simple_flag` is true), appends an `AuditEvent` with `event_kind` `CONVERSION_COMPLETED`, refreshes both accounts' `updated_at`, and increments both accounts' `version` by 1.

The pro-rata split is what makes Backdoor Roth conversions tax-honest. In the single-account default (the request omits `aggregate_basis` or sets it to false), the split runs against the source account's own bases only. Let gross be `gross_amount_cents`, let pretax be the source's `pretax_basis_cents` and let aftertax be the source's `aftertax_basis_cents` immediately before the split. If the sum of pretax and aftertax is zero — the source is entirely investment growth with no recorded basis — the entire gross is taxable and the nontaxable portion is zero. Otherwise the nontaxable portion is gross multiplied by aftertax, floor-divided by the sum of pretax and aftertax; the taxable portion is gross minus the nontaxable portion. The floor at the final divide truncates toward zero, and any cent of remainder lands on the taxable side. There is no per-line rounding earlier in the chain.

When the owner sets `aggregate_basis` to true and has two or more Traditional accounts, the split is recomputed against the owner's aggregated basis: the pretax and aftertax inputs to the same formula are replaced by the sums of `pretax_basis_cents` and `aftertax_basis_cents` across every Traditional account belonging to this owner, and the formula then runs identically. The aggregated path produces a different taxable-versus-nontaxable split whenever basis is unevenly distributed across the owner's Traditional accounts — for example, when after-tax basis is concentrated in the source account, the aggregated form dilutes the nontaxable ratio with the larger pretax pool sitting elsewhere, whereas the single-account form would have made the conversion look mostly nontaxable. The choice between the two paths is governed entirely by the request's `aggregate_basis` flag; the system never aggregates implicitly.

### 3.6. Beneficiary Designations and Death-Triggered Cascade

An `AccountOwner` records a beneficiary against one of their accounts by supplying the `account_id`, the `beneficiary_full_name`, a `relationship` from the set `SPOUSE`, `MINOR_CHILD`, `DISABLED`, `CHRONIC_ILL`, `ELIGIBLE_TRUST`, and `NON_ELIGIBLE_INDIVIDUAL`, and a `percentage_bps` in basis points strictly greater than 0 and at most 10000. The designation lands in `PENDING` with a null `secure_deadline_at`. Activation moves the designation from `PENDING` to `ACTIVE` and is gated on a hard arithmetic check: the sum of `percentage_bps` across all designations on this account whose `status` becomes `ACTIVE` after the activation (the newly activated row included with the rows already in `ACTIVE`) must equal exactly 10000; otherwise the activation is rejected with `ERR_BENEFICIARY_SHARES_INVALID`. Revocation moves a designation from either `PENDING` or `ACTIVE` to `REVOKED`.

When a `PlanAdministrator` declares the owner deceased, the system writes the supplied `deceased_at` instant onto the owner, increments the owner's `version` by 1 (consuming `expected_owner_version` for OCC), appends an `AuditEvent` with `event_kind` `OWNER_DECEASED`, and runs a cascade. Every `IRAAccount` belonging to this owner that is currently in `ACTIVE` or `FROZEN` transitions to `INHERITED`; every `BeneficiaryDesignation` currently in `ACTIVE` on those accounts transitions to `INHERITED`; for every inherited designation whose `relationship` is `NON_ELIGIBLE_INDIVIDUAL`, `secure_deadline_at` is computed as the owner's `deceased_at` plus ten years (for relationships exempt from the ten-year rule — `SPOUSE`, `MINOR_CHILD`, `DISABLED`, `CHRONIC_ILL`, and `ELIGIBLE_TRUST` — `secure_deadline_at` remains null); every `OPEN` `RMDSchedule` for this owner is recomputed under the inherited timeline. Every touched row has its `updated_at` refreshed and its `version` incremented by 1.

### 3.7. RMD Schedules, Uniform Lifetime Math, and Year-Rollover

A `PlanAdministrator` creates an `RMDSchedule` by supplying an `owner_id` and a four-digit `tax_year`. The schedule is created with `status` of `OPEN`, `satisfied_amount_cents` of zero, and a computed `required_amount_cents` and `deadline_at`. The boolean `is_first_rmd_year` is set to true if `tax_year` is the year in which the owner reaches age seventy-three by December 31; in that case `deadline_at` is April 1 of `tax_year` plus 1 (the first-year extension granted by the Internal Revenue Code); otherwise `deadline_at` is December 31 of `tax_year`. If the resulting `required_amount_cents` is strictly greater than zero, `AccountOwner.rmd_posture` is set to `REQUIRED_PENDING`.

The required amount is computed differently depending on whether the owner is alive or deceased. For a living owner whose age at the end of `tax_year` (the integer year difference between December 31 of `tax_year` and `date_of_birth`) is below seventy-three, the requirement is zero. For a living owner aged at least seventy-three at year-end, the system aggregates `cash_balance_cents` across the owner's Traditional accounts whose `status` is in the set `ACTIVE` or `FROZEN` (closed accounts are excluded, and inherited accounts use the SECURE path described next instead). The accounts are enumerated in ascending `opened_at` order, ties broken by ascending `created_at` — never by `id` — and their `cash_balance_cents` values are summed into a single total balance as of December 31 of the year before `tax_year`. The Uniform Lifetime divisor is then looked up by the owner's year-end age. The divisor table, stored in basis-point form (the integer 2660 represents the decimal divisor 26.60), runs as follows: age 73 → 2660, age 74 → 2580, age 75 → 2490, age 76 → 2410, age 77 → 2320, age 78 → 2240, age 79 → 2150, age 80 → 2070, age 81 → 1980, age 82 → 1900, age 83 → 1820, age 84 → 1730, age 85 → 1650. The required amount in cents is computed sum-then-divide: the aggregated total balance in cents is multiplied by 100, then floor-divided by the divisor in basis-point form, yielding an integer-cent result. The final divide truncates toward zero.

For a deceased owner whose surviving designated beneficiary's `relationship` is `NON_ELIGIBLE_INDIVIDUAL`, the Uniform Lifetime math is replaced entirely by an even allocation under the SECURE Act ten-year pace. The total inherited balance is taken as the sum of `cash_balance_cents` across all inherited Traditional accounts attached to that beneficiary. The years remaining are computed as the difference between `secure_deadline_at` and the system clock's `current_utc`, divided by 365 days and rounded up to the next whole year. Each year's `required_amount_cents` is the total inherited balance integer-divided by the years remaining. In the final year before `secure_deadline_at`, the required amount is the entire remaining balance, ensuring the account drains to zero by the deadline as the SECURE rule demands.

A `PlanAdministrator` runs the year-rollover capability when the calendar year turns. The capability takes a `new_tax_year` value, advances every account's `tax_year_marker` to that value, resets every account's `ytd_contribution_cents` to zero, then sweeps every `OPEN` `RMDSchedule` and transitions to `DELINQUENT` any schedule whose `deadline_at` has been passed by the current `SystemClock.current_utc` and whose `satisfied_amount_cents` remains strictly below its `required_amount_cents`. For each schedule that flips to `DELINQUENT`, an `AuditEvent` with `event_kind` `RMD_DEADLINE_BREACHED` is appended with `amount_cents` equal to `required_amount_cents` minus `satisfied_amount_cents`, and the relevant owner's `rmd_posture` is set to `REQUIRED_DELINQUENT`. The capability's response carries two summary integers: the count of accounts whose tax-year markers were advanced (the rolled-account count) and the count of schedules that flipped to `DELINQUENT`. The same year-rollover may also generate `AuditEvent` rows of kind `YEAR_ROLLED_OVER` documenting the rollover for the affected owners.

A late cure is permitted: confirming an `RMD`-coded distribution against a `DELINQUENT` schedule pulls the schedule back to `SATISFIED` once `satisfied_amount_cents` reaches `required_amount_cents`, and `rmd_posture` is recomputed accordingly. An `OPEN` schedule similarly transitions to `SATISFIED` the moment a confirm pushes its `satisfied_amount_cents` to or past `required_amount_cents`.

### 3.8. The Audit Event Stream

The system maintains an append-only `AuditEvent` stream that records seven kinds of business events: `CONTRIBUTION_CONFIRMED`, `DISTRIBUTION_CONFIRMED`, `CONVERSION_COMPLETED`, `RMD_DEADLINE_BREACHED`, `BENEFICIARY_INHERITED`, `OWNER_DECEASED`, and `YEAR_ROLLED_OVER`. Each event carries the `owner_id` whose timeline it belongs to, an optional `account_id` (null for owner-scoped events like `OWNER_DECEASED` and `YEAR_ROLLED_OVER`), the `event_kind` discriminator, the `tax_year` context, a positive `amount_cents` whose meaning depends on `event_kind` (the contribution or distribution amount, the converted gross, the RMD shortfall, or zero for events with no inherent amount), and a server-stamped `occurred_at`. Audit events are never updated in place once written, and they are exposed only to `PlanAdministrator` and `IRSAuditor`.

### 3.9. Form 1099-R as the Reporting Artefact

A `Form1099R` is generated exactly once at the moment that produces a reportable event: at distribution confirm for distributions, at conversion complete for conversions. The form carries either a non-null `distribution_id` (with a null `conversion_id`) or a non-null `conversion_id` (with a null `distribution_id`), never both and never neither. Its `tax_year` is copied from the underlying transaction. The box-7 `distribution_code` is one of `1`, `2`, `4`, `7`, `G`, `B`, `J`, or `T` (the same code letters the printed 1099-R uses); for a completed conversion the code is always `G`. The `ira_sep_simple_flag` (the corresponding box-7 checkbox on the printed form) is true for every transaction in this system because every account is an IRA. The form's `gross_distribution_cents`, `taxable_amount_cents`, and `federal_withholding_cents` are computed as described in §3.4 (for distributions) and §3.5 (for conversions). When a distribution is reversed inside the same tax year, the form's `gross_distribution_cents` is reset to zero — the row is retained as evidence of the void rather than deleted — but the form is otherwise immutable.
