# Docs Release Publishing API — Product Requirements Document

## 1. Introduction

Product documentation is the last thing to be planned and the first thing customers blame. A documentation team that ships alongside an engineering release train has to answer several questions at once, and today it answers them in spreadsheets: which features of the coming release actually need pages, who is writing them and whether that person has the hours, whether an engineer and a product manager have both certified the page as technically accurate, whether the terminology matches the style guide, what the release notes should say in customer-facing language, which locales get translated pages on the same day as English and which get them later, and whether a deprecation was announced early enough that nobody is surprised when the feature disappears. Each of these is individually simple. Together, they form a workflow in which a single late decision — a reviewer asking for changes two days before the documentation freeze — silently invalidates approvals, re-prices writer capacity, and moves the whole release's readiness gate.

This document specifies the API for a documentation planning and publishing service that makes that workflow explicit and auditable. The service owns the entire chain from a **release train** (a supported product version with a documentation freeze date, a general-availability date, and an end-of-support date) down to an individual **localized page** delivered by a translation vendor. Every quantity a human would otherwise track by hand — a writer's committed load, a locale's reserved source words, a release's projected translation spend, a page's documentation health — is a server-computed field with a single defined formula, and every state change that ought to ripple outward does ripple outward, in a defined order, within the same request.

Two design commitments run through the whole specification and are worth stating up front. The first is **segregation of duties**: authoring, reviewing, and editorial approval are held by different roles, and within a role by different people — a writer may never be routed a sign-off on their own page, and the operator who files a change record may never be the one who rewrites it for customers. The second is **immediate consistency**: there are no background jobs, no eventual reconciliation, and no deferred recomputation. When a request returns, every derived counter, ledger, and posture field that its action affects has already been brought up to date, and a subsequent read of any affected resource reflects the new value.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API — reads included — must carry two headers. `X-User-ID` identifies the caller and `X-User-Role` declares the capacity in which they are acting. If either header is absent, or is present but sent as an empty string, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); a header consisting only of whitespace is treated as a value, not as absence, and will fail later checks instead — a whitespace-only `X-User-Role` is an unrecognized role, while a whitespace-only `X-User-ID` fails identity resolution for `Writer` and `Reviewer` and is otherwise simply recorded as the caller's opaque identifier. Only the exact empty string counts as absence, and neither header is trimmed before it is compared. There is no session, no token exchange, and no impersonation: the headers are the whole of the authentication contract.

Six roles exist, and their names are spelled exactly as follows: `DocsLead`, `Writer`, `Reviewer`, `LocalizationCoordinator`, `SupportAnalyst`, and `Reader`. A value of `X-User-Role` that is not one of these six is rejected, as is a recognized role that does not appear in the authorized-role list for the endpoint being called; both cases return `ERR_UNAUTHORIZED` (HTTP 403). Section 4 lists the authorized roles for every endpoint, and that list is exhaustive — a role absent from an endpoint's row has no access to it under any circumstances.

Two of the six roles are backed by persisted records. When `X-User-Role` is `Writer`, `X-User-ID` is the `id` of the acting `Writer` row; ownership checks on any resource that references a `Writer` compare that resource's writer reference to `X-User-ID`, which is how a topic's authoring permission is decided against its plan item's `assigned_writer_id`. When `X-User-Role` is `Reviewer`, `X-User-ID` is the `id` of the acting `Reviewer` row, and a sign-off decision is only accepted from the reviewer the sign-off names. For both of these roles, an `X-User-ID` that does not resolve to an existing record of the matching type is rejected with `ERR_ROLE_IDENTITY_MISMATCH` (HTTP 403) before any resource-specific logic runs.

The remaining four roles carry opaque identities. When `X-User-Role` is `DocsLead`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where the workflow requires accountability — as `submitted_by_user_id` and `editorial_by_user_id` on a change record — but never compares it to any entity's `id`. The same holds for `LocalizationCoordinator`, whose `X-User-ID` is an opaque coordinator identifier that the server neither persists nor resolves; for `SupportAnalyst`, an opaque analyst identifier used purely for read authorization; and for `Reader`, an opaque anonymous reader identifier that is likewise never resolved to a record. `Reader` is deliberately the weakest role in the system: it may read a single topic and leave page ratings on a live one, and nothing else.


### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`; concretely it is the literal prefix `req_` followed by exactly 20 characters drawn from uppercase A–Z and the digits 0–9, minted independently for every response, error responses included.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one instant in this API read from the host's real clock rather than from the logical clock of §2.4, so it advances between two requests issued at the same logical instant and is never comparable with a resource's `created_at`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and are omitted from the `meta` block of every single-object and error response.
- Object keys are serialized in the order the server assembles them rather than sorted alphabetically, and key order carries no contractual meaning: a client must read fields by name.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection endpoints accept two optional query parameters. `limit` is the maximum number of records to return; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` is the number of records to skip before the first returned record; it defaults to 0 and may not be negative. Both must be supplied as integers: a supplied value is read as a decimal integer that may carry surrounding whitespace and a leading `+` or `-` sign, and anything else — an empty value, a decimal fraction such as `5.0`, a hexadecimal or exponent form, or a non-numeric word — is not an integer. A `limit` outside the range 1 through 100, an `offset` below 0, or a non-integer value for either is rejected with `ERR_INVALID_PAGINATION` (HTTP 400). An `offset` beyond the end of the matching set is not an error: it returns an empty `data` array with the true `total_count` and `has_more` false.

Every paginated response carries `limit`, `offset`, `total_count`, and `has_more` in its `meta` block. `total_count` is the number of records matching the request's filters before pagination is applied, and `has_more` is true exactly when records matching the filters remain beyond the returned page — that is, when the offset plus the number of records actually returned is still below `total_count`.

Filters are applied by exact string equality against the stored field value; a filter parameter supplied more than once is read as its first occurrence, and query parameters an endpoint does not list are ignored rather than rejected. A filter value that is well formed but outside the enumeration of the field it filters is **not** a request-shape error: it simply matches no records, and the endpoint answers 200 with an empty `data` array and `total_count` 0.

Unless an endpoint states otherwise, collections are sorted by `created_at` in ascending order — oldest record first. Four collections deviate, and their orderings are part of the contract: release trains are returned newest first, by `created_at` descending; a topic's own source revisions are returned by `revision_number` ascending; locale profiles are returned by `locale_code` ascending, which is the same order in which a budget projection walks them; and terminology terms are returned by `term` ascending, which is the same order in which the violation scan walks them.

Because the logical clock of §2.4 moves only when a `DocsLead` moves it, records created inside one clock position legitimately share an identical `created_at`, and the ordering must still be total. Ties on `created_at` are therefore broken by the order in which the server created the records: a `created_at` ascending listing returns the earlier-created record first, the newest-first release-train listing returns the later-created record first, and every cascade that visits siblings in `created_at` ascending order uses that same creation order as its tiebreak. The three orderings keyed on a value rather than a timestamp — `revision_number`, `locale_code`, and `term` — are ordered on that value alone, and where two records could nonetheless carry the same key (a retired term whose spelling an active term has since reused) the earlier-created record is returned first.

### 2.4. Resource Identity, Audit Fields, and the Logical Clock

Every resource is addressed by an `id` that the server mints as a UUID. Identifiers carry no type prefix and are never supplied by the client. Alongside `id`, most resources expose `created_at` and `updated_at` as ISO 8601 UTC instants with exactly three fractional-second digits and a trailing `Z`, plus a `version` integer that begins at 1 when the resource is created and increases by exactly 1 on every mutation the server applies to that resource — including mutations that arrive as the side effect of an operation on a different resource. A mutation means an actual change to one of the resource's own non-audit fields. A side-effect visit that re-derives a field to the value it already held is not a mutation: `version` and `updated_at` are advanced only when the visit leaves at least one observable field different from what it found, so a reviewer whose `open_signoff_count` a supersession does not move, or a release train whose posture, ratio, counts, and commitment a recomputation reproduces unchanged, is left at its previous `version` and its previous `updated_at`. The record a request explicitly transitions is a different matter: an accepted state transition always advances that record's `version` and `updated_at`, because the transition is itself the change.

Two resources in this domain are append-only records of something that happened, and they therefore carry only `id` and `created_at`: a source revision and a page feedback row. Neither has an `updated_at` field and neither has a `version` field, because neither is ever modified after it is written. Every other resource — release trains, writers, reviewers, plan items, topics, sign-offs, doc set versions, change records, release notes, locale profiles, localization jobs, terminology terms, and deprecation notices — carries the full set of `id`, `created_at`, `updated_at`, and `version`.

All date and instant reasoning in this domain reads a **logical clock** rather than the host's wall clock. Before the clock is set for the first time it reads exactly `2026-08-01T00:00:00Z`; this startup default is mandatory, and the server never falls back to real time. A `DocsLead` — the only role with this capability — may move the clock forward by supplying a `current_utc` instant to an administrative clock-setting capability, which responds with HTTP 200 and an empty `data` object: the accepted clock value is not echoed back, and because the clock is not itself a resource the operation mutates no record and advances no `version` anywhere. The clock only moves forward: a requested `current_utc` earlier than the clock's present value is rejected with `ERR_CLOCK_BACKWARD` (HTTP 409), while a value equal to the present value is accepted and is a no-op. Every subsequent `submitted_at`, `approved_at`, `decided_at`, `requested_at`, `published_at`, `compiled_at`, `archived_at`, and `retired_at` stamp is taken from the clock, and every comparison against a calendar date — a freeze date, an announce date, a translation window, an end-of-support date — uses the clock's current date.

Calendar dates are distinct from instants and are represented as `YYYY-MM-DD` strings with no time component: a supplied date is exactly ten characters with a zero-padded month and day, so `2026-8-01` is a shape violation rather than the first of August. Instants are ISO 8601 UTC with a trailing `Z`. A supplied instant is accepted either with a fractional-second part of one to six digits or with none at all, and the `Z` is mandatory — a numeric UTC offset such as `+00:00`, a bare local timestamp, or any other zone designator is a shape violation. An instant is always rendered with exactly three fractional digits, obtained by discarding any precision beyond milliseconds rather than by rounding it; the full supplied precision is nonetheless retained internally and is what every subsequent comparison uses, so a clock advanced to `...T00:00:00.123456Z` displays as `...T00:00:00.123Z` while still comparing as the microsecond value. Where a rule compares a stored instant to a stored date — for example when a delayed translation is scheduled relative to the moment its source page went live — the instant is first reduced to its UTC calendar date and the comparison proceeds on dates.

### 2.5. Validation Precedence

Several operations in this domain are guarded by half a dozen checks at once, and which error a caller sees is a specified behaviour, not an implementation detail. Checks are evaluated in the following order, and the first check that fails determines the response; no later check is evaluated once an earlier one has failed.

1. **Authentication.** Both headers present and non-empty — otherwise `ERR_UNAUTHENTICATED`.
2. **Authorization.** The declared role is one of the six and is listed on the target endpoint — otherwise `ERR_UNAUTHORIZED`.
3. **Role identity.** For a caller whose declared role is `Writer` or `Reviewer`, the presented `X-User-ID` resolves to an existing record of that type — otherwise `ERR_ROLE_IDENTITY_MISMATCH`. The test is driven by the role the caller declared, not by the endpoint's authorized list, so a `DocsLead` calling an endpoint that also admits `Writer` is never resolved against the writer roster, and the four opaque roles are never resolved anywhere.
4. **Request shape.** On every write endpoint: all required fields present, JSON types correct, enum values drawn from their declared sets, integer counts non-negative where declared, a rating between 1 and 5 inclusive, money supplied as integer counts of cents rather than strings, calendar dates formatted `YYYY-MM-DD`, and instants formatted as ISO 8601 UTC with a trailing `Z` — otherwise `ERR_INVALID_REQUEST` (HTTP 400). Three conventions settle how a body is read before those checks apply. A body that is absent, empty, whitespace-only, or the JSON literal `null` is read as an empty object, so its required fields are reported as missing rather than as a parse failure, whereas a body that is not syntactically valid JSON, or that is valid JSON but not an object — an array, a string, a bare number — is itself `ERR_INVALID_REQUEST`. A field explicitly sent as `null` is treated exactly as if it had been omitted: required where the field is required, and defaulted where the field is optional. And a field the operation does not recognize is ignored rather than rejected, which is why the version expectations of §2.6 are inert on the endpoints that do not ask for them. Booleans are not numbers: `true` or `false` supplied where an integer or a decimal is required is a shape violation, as is a numeric value supplied as a string.
5. **Pagination shape.** On every collection endpoint, `limit` and `offset` within their declared bounds — otherwise `ERR_INVALID_PAGINATION`.
6. **Path existence.** Every identifier embedded in the URL is resolved **left to right**, so that on a nested path the outer resource's absence is reported before the inner one is even looked for. A missing resource yields the 404 belonging to that resource's type: `ERR_RELEASE_TRAIN_NOT_FOUND`, `ERR_WRITER_NOT_FOUND`, `ERR_REVIEWER_NOT_FOUND`, `ERR_PLAN_ITEM_NOT_FOUND`, `ERR_TOPIC_NOT_FOUND`, `ERR_SIGNOFF_NOT_FOUND`, `ERR_DOC_SET_VERSION_NOT_FOUND`, `ERR_CHANGE_RECORD_NOT_FOUND`, `ERR_RELEASE_NOTE_NOT_FOUND`, `ERR_LOCALE_PROFILE_NOT_FOUND`, `ERR_LOCALIZATION_JOB_NOT_FOUND`, `ERR_TERM_NOT_FOUND`, or `ERR_DEPRECATION_NOTICE_NOT_FOUND`.
7. **Body reference existence.** Every reference supplied in a request body resolves to a live record, reported with the same family of 404 codes: `writer_id`, `reviewer_id`, `release_train_id`, `plan_item_id`, `parent_topic_id` (reported as `ERR_PARENT_TOPIC_NOT_FOUND`), `locale_profile_id`, `topic_id`, and `migration_guide_topic_id` (reported as `ERR_TOPIC_NOT_FOUND`).
8. **Writer ownership.** Where a `Writer` acts on a topic, `X-User-ID` equals the topic's plan item `assigned_writer_id` — otherwise `ERR_NOT_ASSIGNED_WRITER` (HTTP 403).
9. **Reviewer ownership.** Where a `Reviewer` decides a sign-off, `X-User-ID` equals that sign-off's `reviewer_id` — otherwise `ERR_SIGNOFF_NOT_OWNED` (HTTP 403).
10. **Optimistic concurrency.** The two write operations that carry a parent version expectation compare it against the parent's live `version`, as specified in §2.6, and reject a mismatch with HTTP 412.
11. **State of the target resource.** The resource being acted on is in a state that admits the action.
12. **State of a guarding resource.** A *different* entity's state gates the write — the release train's readiness posture or lifecycle status, the source topic's publication state, the locale profile's availability, and so on.
13. **Safety and segregation of duties.** Self-review prohibition, editorial separation of duties, and the requirement that a breaking change already have a published migration path.
14. **Referential integrity beyond mere existence.** A resolved reference additionally points at the *right* record — the same plan item, the same product line, a non-cyclic parent chain.
15. **Temporal windows.** Date ordering, minimum notice periods, announce dates reached, end-of-support dates reached, translation service-level windows.
16. **Constraint satisfaction.** Uniqueness, interval overlap, aggregate parallelism limits, and non-empty candidate sets.
17. **Fiscal capacity, evaluated last.** Localization budget caps and writer capacity ceilings.

Bands 11 through 17 are ordered as listed, and the ordering matters in several concrete places that are called out again where each workflow is described. A localization job in a terminal state reports its state error and never a service-level breach. A self-review request for a discipline that is already covered reports the self-review prohibition, not the duplicate-discipline conflict. A deprecation notice whose migration guide belongs to a different product line reports the referential mismatch even when its notice period is also too short. A doc set publication with no approved topics reports the empty candidate set and never a budget figure. And an assignment request that both collides with an existing authoring window and would overrun the writer's capacity reports the overlap.

### 2.6. Optimistic Concurrency on Parent Records

Two create operations in this domain implicitly retire an earlier record, which makes them dangerous to issue from a stale view. Both therefore require the caller to state the `version` of the *parent* record they last observed, and both reject a mismatch with HTTP 412.

Opening a draft documentation set for a release train requires `expected_release_train_version` as a mandatory field in the request body, carrying the client's last observed `version` of the target `ReleaseTrain`. If that value does not equal the release train's current `version` — because some other writer advanced the train's lifecycle status, changed its readiness posture, or already opened a newer draft since the client read it — the request is rejected with `ERR_STALE_RELEASE_TRAIN_VERSION` (HTTP 412) and nothing is created. Because a new draft legitimately supersedes the train's previous draft, the operation cannot protect itself by refusing to overwrite; the parent version check is the only defence against a caller acting on an out-of-date picture of the train.

Compiling a release note requires `expected_doc_set_version_version` as a mandatory field in the request body, carrying the client's last observed `version` of the target `DocSetVersion`. If that value does not equal the doc set version's current `version`, the request is rejected with `ERR_STALE_DOC_SET_VERSION` (HTTP 412) and no compilation occurs. A fresh compilation supersedes the doc set's previous compiled note, so a second compile issued from a stale view would silently discard an editor's work; the version check on the parent doc set is what distinguishes an intentional recompilation from one aimed at an out-of-date candidate set.

No other endpoint in this domain accepts a version expectation. An operation that is not one of these two takes no version field, and supplying one is simply an unrecognized field.

### 2.7. Precision, Money, and Rounding

Money is always an integer count of cents and is always transmitted as a JSON number, never as a string or a decimal-formatted string. A monetary value sent as a string is a shape violation and yields `ERR_INVALID_REQUEST`. Vendor rates are the one exception to integrality: a per-word rate is a decimal number of cents carried to two decimal places, because rates below one cent per word are ordinary.

Wherever a formula in this document says a value is rounded, the rounding mode is **half up** — a value exactly at the midpoint rounds away from zero. Load points, coverage factors, ratios, leverage percentages, deflection percentages, mean ratings, impact scores, and health scores are all carried to **two decimal places** and rounded half up. Monetary results are rounded half up to whole cents, and where a formula rounds more than once, each rounding step happens where the formula says it happens; the intermediate rounded value, not the unrounded one, feeds the next step. Day counts, word counts, page counts, and violation counts are integers and are never rounded — where a formula reduces a fractional day count to whole days it takes the floor.

Two consequences of that arithmetic are worth pinning. First, where this document describes a *client-supplied* decimal as carried to one or two decimal places — a writer's `capacity_points`, a locale profile's `tm_coverage_pct` and `per_word_rate_cents` — it describes how such values are quoted in practice, not a validated constraint: a value arriving with more decimal places is accepted, stored exactly as sent, and used at its full precision by every formula that reads it. Rounding is a property of server-computed results only, and the server never rounds an input on the way in. Second, every numeric field, decimal and integral alike, is transmitted as a JSON number, so a two-decimal result is a number rather than a two-decimal string and its trailing zeros do not survive serialization: a ratio of `1.00`, a load figure of `3.00`, and a coverage factor of `0.50` appear on the wire as `1.0`, `3.0`, and `0.5`. Equality against such a field is numeric, never textual.

### 2.8. Ledgers, Conserved Quantities, and Cascades

Three fields in this system are **conserved quantities**: a writer's `committed_load_points`, a locale profile's `committed_source_words`, and a release train's `localization_committed_cents`. Each is defined as an aggregate over a precisely specified set of child records, and each must, at every observable moment, equal exactly what a full recomputation over that set would produce. It does not matter how long a chain of assignments, reassignments, reworks, publications, cancellations, and cascade-driven cancellations preceded a read: incremental bookkeeping that has drifted from the defining aggregate is a defect, not a rounding artefact. A create followed by its compensating cancel must return each affected ledger to precisely its pre-create value. Although only these three carry the label, every other derived counter in the system is maintained the same way rather than by incremental bookkeeping — a writer's `assignment_count`, a reviewer's `open_signoff_count`, a locale profile's `open_job_count`, and a release train's `plan_item_count`, `approved_plan_item_count`, `approved_topic_ratio`, and `doc_readiness_posture` are each re-derived in full from their defining sets whenever an operation could have moved them. Where a workflow below describes such a counter as increasing or decreasing by one, that describes the observable effect of the recomputation, not a mechanism.

Cascades are specified as ordered hops, and the order is part of the contract because later hops read state that earlier hops wrote. Where a cascade visits a set of sibling records, it visits them in `created_at` ascending order unless the workflow says otherwise. Every record a cascade actually changes has its `updated_at` refreshed to the current logical clock instant and its `version` incremented by 1, exactly as if it had been written directly — a topic archived as the fourth hop of an end-of-life cascade is as much a mutation of that topic as an explicit archive would have been. The qualifier matters at the edges of a cascade, where a hop exists only to re-derive a ledger: a record whose recomputed figures come out identical to the figures it already carried is left at its previous `version` and `updated_at`, per §2.4, and does not appear as a mutation at all. Where a cascade settles the ledgers of the parent records standing behind the siblings it visited — the reviewers behind superseded sign-offs, the locale profiles behind cancelled jobs — it collects those parents while sweeping the siblings and settles each distinct parent exactly once, after the sibling sweep has finished, in the order in which the sweep first reached it. Cascades run to completion inside the originating request; a response is never returned with a cascade half-applied.

### 2.9. Immutable Snapshots Versus Live Counters

The terminology scan writes its results in two different modes, and confusing them is the single easiest way to get this system wrong. A source revision's `blocker_violation_count`, `warning_violation_count`, and `violating_term_ids`, together with a change record's `terminology_blocker_count`, are **immutable snapshots** of what the scan saw at the instant the record was written. They are never rewritten, not by a later revision, not by a style-guide change, and not by the retirement of a term they cite.

A topic's `open_blocker_violations` and `open_warning_violations` are **live counters**. They are derived from the newest source revision's `violating_term_ids`, filtered down to the terms that are still active, and they are re-derived whenever that filter's result could have changed — when a new revision lands, and when a terminology term is retired. Retiring a term can therefore lower a topic's live counters, and can make a topic that was blocked from review become submittable, without altering a single stored snapshot anywhere in the system.

Version pinning follows the same philosophy on the review side. An approved sign-off stores the revision number it certified in `pinned_revision_number`, and that pin is what makes the approval falsifiable: a later revision does not update the sign-off, it supersedes it.

### 2.10. Date Windows and Interval Conventions

Two kinds of calendar window appear in this domain and they use deliberately different conventions, because the underlying resources behave differently.

A writer's authoring window is **half open**: it runs from `window_start_date` inclusive up to `window_end_date` exclusive, so a window ending on the 10th does not occupy the 10th. `window_end_date` must be strictly later than `window_start_date`. A translation vendor's window is **closed**: it runs from `window_start_date` through `window_end_date` inclusive, so a window ending on the 10th does occupy the 10th, and `window_end_date` may equal `window_start_date` to describe a single-day window. Any misordered window or timeline is rejected with `ERR_INVALID_DATE_WINDOW` (HTTP 400): an authoring window whose end is not strictly after its start, a translation window whose end is earlier than its start, a deprecation timeline whose announce date is later than its deprecated date or whose deprecated date is not strictly earlier than its removal date, and a release train whose documentation freeze date is later than its general-availability date or whose end-of-support date is not strictly later than its general-availability date — an end-of-support date *equal* to the general-availability date is refused, whereas a general-availability date equal to the freeze date is accepted.

The distinction has a direct consequence for collision detection. Two closed translation windows that share a single date do intersect. Two half-open authoring windows that merely touch — one ending on exactly the day the next begins — do not intersect on the interval arithmetic alone, but they are still refused, because writer windows are additionally padded by a handoff buffer described with the assignment workflow.

## 3. Business Logic & Workflows

### 3.1. Release Trains and the Documentation-Readiness Gate

Everything in this system hangs off a release train. A `DocsLead` registers one by supplying the product line it belongs to as `product_key` — 2 to 12 characters drawn only from uppercase A–Z and the digits 0–9 — a marketing `version_label` of 1 to 20 characters, and three calendar dates: `doc_freeze_date`, the day documentation content freezes; `ga_date`, the day the release becomes generally available, which may not be earlier than the freeze date; and `support_end_date`, the day support ends for this documentation set, which must be strictly later than the general-availability date. The pair of product line and version label must be unique across all release trains; a collision is rejected with `ERR_DUPLICATE_VERSION_LABEL`. A registration also fixes `localization_budget_cap_cents`, a hard ceiling in whole cents (zero or greater) on the projected translation spend of any documentation set published for this train. A newly registered train opens with `status` `PLANNED`, `doc_readiness_posture` `OPEN`, `approved_topic_ratio` `1.00`, `plan_item_count`, `approved_plan_item_count`, `localization_committed_cents` all zero, and `eol_notice_posted` false. Trains can be listed and filtered by `product_key` and by `status`.

The train's `status` moves along a single spine, `PLANNED → DOC_FREEZE → GA → MAINTENANCE → END_OF_LIFE`, and only ever one step at a time. A `DocsLead` advances it by naming the desired `target_status`; if that value is not the immediate successor of the current status in that order — including any attempt to skip a step, to move backwards, or to advance out of the terminal `END_OF_LIFE` — the request is rejected with `ERR_RELEASE_TRAIN_INVALID_ADVANCE`. A `target_status` that is not one of those five spine values at all never reaches that test: it is a request-shape violation reported as `ERR_INVALID_REQUEST` (HTTP 400), and the successor test therefore only ever adjudicates between well-formed spine values. Two of the four hops carry an extra precondition, and each is evaluated only after the successor test has passed. The `DOC_FREEZE → GA` hop requires that at least one documentation set of this train is in `PUBLISHED` status *at the moment of the advance*, and refuses with `ERR_DOC_SET_NOT_PUBLISHED` otherwise — the test is on current status, not on history, so a train whose only documentation set was published and has since been archived does not satisfy the gate — a release cannot go generally available with no published documentation. The `MAINTENANCE → END_OF_LIFE` hop requires that the logical clock's date has reached or passed `support_end_date`, and refuses with `ERR_SUPPORT_END_DATE_NOT_REACHED` while the clock is still earlier than that date. Every successful advance recomputes the train's readiness figures and increments the train's `version` by 1.

**Readiness posture** is the gate that connects release planning to content operations, and it is recomputed on every event that could move it: a plan item being created, assigned, or cancelled; a topic reaching full approval or having an approval invalidated; a documentation set publishing; and every lifecycle advance. It is derived in four steps. First, `plan_item_count` is the number of the train's plan items whose status is anything other than `CANCELLED`. Second, `approved_plan_item_count` is the number of those whose status is either `APPROVED_CONTENT` or `PUBLISHED`. Third, `approved_topic_ratio` is `1.00` when `plan_item_count` is zero — a train with no counted deliverables is vacuously ready, not zero and not null — and otherwise the approved count divided by the total count, rounded half up to two decimal places. Fourth, `doc_readiness_posture` is decided as follows: if the train's status is `MAINTENANCE` or `END_OF_LIFE` the posture is `FROZEN`, and this test short-circuits before the ratio is consulted at all; otherwise, if the status is `PLANNED` the posture is `OPEN`, because planning is always open; otherwise — that is, for `DOC_FREEZE` and `GA`, the ratio-driven band — the posture is `OPEN` when the ratio is at least 0.80, `RESTRICTED` when it is at least 0.50 but below 0.80, and `FROZEN` when it is below 0.50. Both band boundaries are inclusive from below: a ratio of exactly 0.80 yields `OPEN`, exactly 0.50 yields `RESTRICTED`, and 0.49 yields `FROZEN`.

The last hop of the train's spine carries the deepest cascade in the system, and it runs in five ordered hops. **Hop one** sets the train's `status` to `END_OF_LIFE`, forces `doc_readiness_posture` to `FROZEN`, and sets `eol_notice_posted` to true. **Hop two**, caused by hop one, takes every documentation set of this train whose status is `PUBLISHED`, in `created_at` ascending order, to `ARCHIVED`, stamping `archived_at` with the logical clock and writing an `eol_notice_text` of the form `End of life: support for <product_key> <version_label> ended on <support_end_date>.` — with the train's own product key, version label, and end-of-support date substituted in. **Hop three**, caused by hop two, moves every topic whose `published_in_doc_set_version_id` names one of those documentation sets from `publication_state` `PUBLISHED` to `ARCHIVED`, in `created_at` ascending order, and recomputes each such topic's health score under its post-publication variant. **Hop four**, caused by hop three, cancels every translation job of those topics whose state is `QUEUED`, `TRANSLATED`, `REWORK_REQUESTED`, or `SCHEDULED_DELAYED`, in `created_at` ascending order, recording `cancel_reason` as exactly `CASCADE_DOC_SET_ARCHIVED`. **Hop five**, caused by hop four, decreases each affected locale profile's `committed_source_words` by that job's `reserved_source_words` and its `open_job_count` by 1, after which the train's `localization_committed_cents` is recomputed over the jobs that survived. Independently of those five hops, every deprecation notice of this train whose status is `PUBLISHED` moves to `RETIRED` — in `created_at` ascending order, and after the five hops have finished — and the train's own `version` is incremented by 1. The recomputation that closes the cascade is a full one: it refreshes `plan_item_count`, `approved_plan_item_count`, and `approved_topic_ratio` alongside `localization_committed_cents`, and `doc_readiness_posture` remains `FROZEN` afterwards because the terminal-status test short-circuits ahead of the ratio band. Note what the cascade does *not* do: plan items are left in whatever status they held, so an end-of-lifed train still reports its historical counts and ratio rather than being zeroed out.

A release train is readable individually, exposing its live posture and its `localization_committed_cents` commitment, by any of the six roles except `Reader`.

### 3.2. The Writer Roster and the Economics of Assignment

A `DocsLead` registers a technical writer with a `person_key` — 3 to 40 characters, unique across the writer roster — a `full_name` of 1 to 120 characters, a `seniority_tier` of `ASSOCIATE`, `SENIOR`, or `PRINCIPAL`, and `capacity_points`, a positive decimal number carried to one decimal place expressing how much concurrent work the writer may hold. An optional `status` may be supplied as either `ACTIVE` or `ON_LEAVE` and defaults to `ACTIVE`. A duplicate `person_key` is rejected with `ERR_DUPLICATE_PERSON_KEY`. New writers open with `committed_load_points` of `0.00` and `assignment_count` of 0. The roster can be listed and filtered by `status` and by `seniority_tier`, and every writer's own source revisions across all topics can be listed on their behalf, ordered by `created_at` ascending — one of only two ways to discover revisions, since a revision is never returned by any create response other than its own.

`person_key` is deliberately shared vocabulary between the writer roster and the reviewer roster, and it is the mechanism behind the self-review prohibition described in §3.5. A `DocsLead` registers a reviewer with a `person_key` — again 3 to 40 characters, unique across the reviewer roster and rejected with `ERR_DUPLICATE_PERSON_KEY` when it collides — a `full_name` of 1 to 120 characters, and a `discipline` of either `ENGINEERING` or `PRODUCT`, which fixes the single kind of sign-off that reviewer is empowered to give. Reviewers open with `open_signoff_count` of 0 and can be listed and filtered by `discipline`.

A **documentation plan item** is one planned deliverable: the documentation for one feature of one release. A `DocsLead` creates it against a `release_train_id` with a `feature_key` of 1 to 60 characters naming the feature the deliverable documents — uniqueness within the train is a planning convention rather than an enforced constraint, so two plan items of the same train may legitimately carry the identical `feature_key` and no error code exists for a collision — an `ia_placement` of `NEW_TOPIC`, `EXISTING_TOPIC_UPDATE`, or `CONCEPT_HUB` recording the information-architecture decision, an `audience_tier` of `CRITICAL`, `STANDARD`, or `INTERNAL`, a `planned_page_count` between 1 and 500 inclusive, and `complexity_points` between 0 and 100 inclusive as the estimator's judgement of difficulty. A new plan item opens with `status` `DRAFTED`, `load_points` of `0.00`, `rework_count` of 0, and `assigned_writer_id`, `window_start_date`, `window_end_date`, and `cancel_reason` all present and null, and its creation increments the train's `plan_item_count` and triggers a readiness recomputation. Plan items can be listed and filtered by `release_train_id`, `assigned_writer_id`, `status`, and `audience_tier`, and read individually with their computed `load_points` and `rework_count` on display.

Assigning a deliverable to a writer is what turns planning into work, and it moves the item from `DRAFTED` to `ASSIGNED`. That status write is conditional on the item actually being `DRAFTED`: an item already in `ASSIGNED` or `IN_AUTHORING` that is re-assigned keeps the status it holds, so a reassignment never pulls a deliverable whose authoring has begun back to `ASSIGNED`. Every accepted assignment nonetheless rewrites `assigned_writer_id`, both window dates, and `load_points`, and always advances the item's `version` and `updated_at` — even a reassignment that names the same writer and the same window it already carried. The `DocsLead` supplies a `writer_id` together with `window_start_date` and `window_end_date` describing the half-open authoring window the deliverable will occupy on that writer's calendar. Five conditions guard the operation, in this order. The plan item's own status must be `DRAFTED`, `ASSIGNED`, or `IN_AUTHORING`; a deliverable that has already entered review, been approved, published, or cancelled cannot change hands, and the attempt is refused with `ERR_PLAN_ITEM_NOT_ASSIGNABLE`. The train's own lifecycle status must be `PLANNED` or `DOC_FREEZE`; an assignment against a train that has reached `GA`, `MAINTENANCE`, or `END_OF_LIFE` is refused with `ERR_RELEASE_TRAIN_CLOSED_FOR_PLANNING`. The target writer's `status` must be `ACTIVE`; an `ON_LEAVE` writer cannot receive work, and the attempt is refused with `ERR_WRITER_ON_LEAVE`. The window must be well formed, with `window_end_date` strictly later than `window_start_date`, or the request fails with `ERR_INVALID_DATE_WINDOW`. Then the window-collision check runs, and only if it passes is the capacity ceiling evaluated last.

The **window-collision rule** treats the requested interval as half open, from `window_start_date` inclusive to `window_end_date` exclusive, and extends it by a two-day handoff buffer on the **leading edge only**. Concretely, the requested window collides with an already-occupied window of the same writer when the requested start date falls earlier than two days after that existing window's end date **and** the requested end date falls later than that existing window's start date; a collision is rejected with `ERR_WRITER_WINDOW_OVERLAP`. Because of the buffer, two windows that merely touch — one ending exactly on the day the next begins — still collide, and so does a one-day gap; a gap of exactly two days is accepted. The comparison is made against the windows of the writer's other counted plan items only: reassigning the same plan item never collides with the window it currently occupies itself. The sweep additionally skips any such item that carries no authoring window — either date null — so a window-less counted item can never produce a collision; on the transitions this API defines, every counted item has been through an assignment and therefore does carry one, which makes the skip a defensive rule rather than an observable one.

**Assignment load points** are the currency of writer capacity, and the step order of their computation is part of the contract. First, size points are 2 points for each planned page — twice `planned_page_count`. Second, depth points are `complexity_points` or 20, whichever is smaller; the cap is applied here, before any multiplier, so complexity above 20 contributes nothing extra. Third, information-architecture points are 4 for `NEW_TOPIC`, 1 for `EXISTING_TOPIC_UPDATE`, and 6 for `CONCEPT_HUB`. Fourth, those three figures are added together, the sum is multiplied by the audience multiplier — 1.5 for `CRITICAL`, 1.0 for `STANDARD`, 0.75 for `INTERNAL` — and the product is then divided by the seniority divisor of the *target writer* — 1.25 for `PRINCIPAL`, 1.0 for `SENIOR`, 0.80 for `ASSOCIATE`; the audience multiplication happens before the seniority division. Fifth, that raw figure is rounded half up to two decimal places and then compared against a floor of 3.0 points, and the larger of the two becomes the base load — note that the floor is applied to the *rounded* value, not the unrounded one. Sixth and last, `load_points` is the base load plus 1.0 point for each unit of the item's `rework_count`, rounded half up to two decimal places; because the rework points are added *after* the floor, they always raise the total.

The seniority divisor means the same deliverable is genuinely worth different load points to different writers, which is why reassignment is a two-sided operation. When a `DocsLead` re-issues an assignment naming a different `writer_id`, the previous writer's `committed_load_points` decreases by the item's old `load_points` and their `assignment_count` decreases by 1; `load_points` is then recomputed from scratch against the new writer's seniority tier; and the new writer's `committed_load_points` increases by the freshly computed figure while their `assignment_count` increases by 1. The new writer must pass the same window-collision and capacity checks as an original assignee.

A writer's `committed_load_points` is the sum of `load_points` over the plan items assigned to them whose status is `ASSIGNED`, `IN_AUTHORING`, `IN_REVIEW`, `IN_REVISION`, or `APPROVED_CONTENT`, rounded half up to two decimal places, and `assignment_count` is the number of items in that same set. Items that are `PUBLISHED` or `CANCELLED` are excluded, because publishing and cancelling both *release* capacity. As a conserved quantity, both fields must always equal a full recomputation over that set. The capacity ceiling is checked at assignment time against a figure derived for the occasion rather than against the writer's stored ledger. The server sums `load_points` over the target writer's **other** counted plan items — the item being assigned is excluded from that sum on exactly the same footing as it is excluded from the window sweep — adds the freshly computed `load_points` to that sum, rounds the total half up to two decimal places, and compares it against `capacity_points`: equality is accepted and only a strict excess is rejected, with `ERR_WRITER_CAPACITY_EXCEEDED`. Excluding the item matters whenever the item is already assigned to this same writer: its old load is dropped before the comparison rather than being counted alongside the new one, so re-assigning an item to its current writer is measured as a replacement and not as an addition, and the total under test then differs from the writer's live `committed_load_points` by exactly that old load. Where the item is new to this writer the two figures coincide, because the writer's stored ledger is by definition the sum over the very items the sweep visits. The final rounding step is a formality — every addend is already carried to two decimal places — but it is where the comparison value is fixed. Because this check runs after the window-collision check, an assignment that both collides and overruns reports the overlap.

Cancelling a deliverable is the compensating half of assignment. A `DocsLead` supplies a `cancel_reason` and the item moves to `CANCELLED`, which is permitted only from `DRAFTED`, `ASSIGNED`, `IN_AUTHORING`, `IN_REVIEW`, or `IN_REVISION`; an item that is `APPROVED_CONTENT`, `PUBLISHED`, or already `CANCELLED` is refused with `ERR_PLAN_ITEM_NOT_CANCELLABLE`. The cancellation records the reason, clears `assigned_writer_id`, decreases the assigned writer's `committed_load_points` by the item's `load_points` and their `assignment_count` by 1, moves every sign-off on the item's topics that is not already `SUPERSEDED` to `SUPERSEDED` with its `pinned_revision_number` cleared, and returns to `review_state` `NOT_SUBMITTED` exactly those topics on which at least one sign-off was actually superseded by this cancellation. A topic that held no sign-off at all, or only already-superseded ones, keeps whatever `review_state` it carried: a page that had been submitted but never routed to a reviewer stays `PENDING_SIGNOFF` under a cancelled plan item. What cancellation never touches on any of those topics is `publication_state`, `published_at`, `published_in_doc_set_version_id`, `approved_at`, `signoff_latency_days`, `health_score`, or `health_score_variant` — a live page whose deliverable is cancelled stays live and keeps the health figure it last computed. The cancellation finally decrements the train's `plan_item_count` by 1 and recomputes the train's ratio and posture.

### 3.3. Authoring: Topics, Information Architecture, and Source Revisions

A **topic** is one documentation page. Only the writer to whom the plan item is assigned may create its topics: the acting `Writer` supplies a `plan_item_id`, a `slug` of 3 to 60 characters using only lowercase a–z, digits, and hyphens, and a `title` of 1 to 160 characters, optionally naming a `parent_topic_id` to place the page inside the information-architecture tree. A caller whose `X-User-ID` is not the plan item's `assigned_writer_id` — including the case where the item is assigned to nobody at all — is refused with `ERR_NOT_ASSIGNED_WRITER`. The slug must be unique among all topics belonging to the same release train, not merely within the plan item, and a collision returns `ERR_DUPLICATE_TOPIC_SLUG`.

The information-architecture tree is built by `parent_topic_id`, and three rules constrain it. When supplied, the parent must be a topic under the **same** plan item; a parent belonging to a different deliverable is rejected with `ERR_PARENT_TOPIC_MISMATCH`. The resulting parent chain must remain acyclic, and the new topic's depth must not exceed 4 — both failures report `ERR_IA_DEPTH_EXCEEDED`. `ia_depth` is 0 for a root topic (no parent supplied) and otherwise one more than the parent's own `ia_depth`. The referential check on which plan item the parent belongs to runs before the depth-and-cycle check, so a cross-item parent is reported as a mismatch rather than as a depth violation.

A newly created topic opens with `review_state` `NOT_SUBMITTED`, `publication_state` `UNPUBLISHED`, `current_revision_number` and `last_submitted_revision_number` both 0, `latest_body_word_count` 0, both violation counters 0, and `health_score` null — a page with no authored content has no health figure at all, and `health_score_variant` is likewise null. Both are *present* keys holding null rather than absent keys, and the same is true of the five other fields a new topic opens empty: `submitted_at`, `approved_at`, `signoff_latency_days`, `published_at`, and `published_in_doc_set_version_id`. Creating the *first* topic under a plan item moves that item from `ASSIGNED` to `IN_AUTHORING`. Topics can be listed and filtered by `plan_item_id`, by `parent_topic_id`, by `published_in_doc_set_version_id`, and by either state dimension independently via `review_state` and `publication_state`. Reading a single topic — the one read that role `Reader` is permitted — exposes both state dimensions, the live violation counters, and the health score. For a topic whose `publication_state` is exactly `PUBLISHED`, that read re-derives `health_score` under the post-publication variant and rewrites `health_score_variant` to `POST_PUBLICATION` before rendering the response, so a fresh reader rating is visible in the score on the very next read. The refreshed figures are persisted on the topic, but the read is deliberately **not** a mutation for the purposes of §2.4: it advances neither `version` nor `updated_at`, which makes this the one read in the system that can change what a subsequent read returns without the record's audit fields recording that anything happened. The refresh is gated on `PUBLISHED` alone. A topic whose `publication_state` is `ARCHIVED` is **not** refreshed on read, even though §3.10 assigns `ARCHIVED` the post-publication variant; it keeps reporting the score written by the cascade that archived it, and later feedback cannot reach it because feedback is refused on an archived page anyway. An `UNPUBLISHED` topic is likewise never refreshed on read and reports whatever score its last approval or terminology recomputation left behind.

Content arrives as **source revisions**, the docs-as-code commits of this system. The assigned `Writer` appends one by supplying `body_word_count` between 1 and 200,000 inclusive, a `used_terms` array of between 0 and 200 lowercased term forms each 1 to 60 characters long that appear verbatim in the revision body — the field itself is mandatory even though the array may be empty, so a revision with no scannable tokens must send an explicit `[]` rather than omitting the key or sending `null` — and a `summary` of 1 to 200 characters serving as the changelog line. The server stamps `topic_id`, sets `author_writer_id` from the acting writer's `X-User-ID`, and assigns `revision_number` as one more than the topic's `current_revision_number`; the topic's `current_revision_number` and `latest_body_word_count` are updated to match. Revisions are immutable and are never returned by any other create response, so they are discovered either through the topic's own revision list — ordered by `revision_number` ascending — or through the per-writer revision list.

Every revision runs the terminology scan of §3.4 over its `used_terms`, and the results are written twice: as the revision's own immutable `blocker_violation_count`, `warning_violation_count`, and `violating_term_ids`, and as a refresh of the topic's live `open_blocker_violations` and `open_warning_violations`.

A revision landing on a page that is already under review or already approved invalidates that review, and this is the pivot of the topic's two independent state dimensions. If the topic's `review_state` is `PENDING_SIGNOFF` or `FULLY_APPROVED`, it returns to `NOT_SUBMITTED` and every sign-off on the topic that is not already `SUPERSEDED` moves to `SUPERSEDED` with its `pinned_revision_number` cleared. If the topic was `FULLY_APPROVED`, its `approved_at` and `signoff_latency_days` are cleared as well. Its `health_score` and `health_score_variant` are pointedly **not** cleared and not recomputed by the revision: the figure computed at the moment of the now-lost approval stands until some later event recomputes it, so an unpublished page can legitimately report a `PRE_PUBLICATION` score whose latency term reflects an approval its `review_state` no longer claims. A topic already in `CHANGES_REQUESTED` is left in `CHANGES_REQUESTED` — a revision is exactly what that state is waiting for. Correspondingly, the plan item moves from `IN_REVIEW` or `APPROVED_CONTENT` back to `IN_AUTHORING`, and when an approval was invalidated the train's `approved_plan_item_count` drops by 1 and its ratio and posture are recomputed. What the revision does **not** touch is `publication_state`: a page that is live stays `PUBLISHED`, with its `published_at` and `published_in_doc_set_version_id` intact, while its review dimension falls all the way back to `NOT_SUBMITTED`. The two dimensions genuinely evolve independently on the same record.

### 3.4. Terminology Governance and the Violation Scan

Style-guide governance is expressed as a list of terms. A `DocsLead` adds one by supplying `term`, the canonical concept key, 2 to 60 lowercase characters and unique among the terms that are currently active; `preferred_form`, 2 to 60 characters, the wording writers are supposed to use; `forbidden_forms`, an array of 1 to 20 wordings each 2 to 60 characters long — no cross-term check is applied to that array at all, so a forbidden form may freely duplicate another term's `preferred_form`, another active term's forbidden forms, or another entry of its own array, with no error code existing for any of those collisions, and case is not enforced on the entries either, because the scan lowercases both sides of every comparison; and `enforcement_severity`, either `BLOCKER` or `WARNING`. A duplicate `term` among active terms is rejected with `ERR_DUPLICATE_TERM`; because the uniqueness test looks only at active terms, a retired term's spelling may be reused. A new term opens with `status` `ACTIVE` and `retired_at` null, and it takes effect for every subsequent revision and editorial pass while never rewriting an existing snapshot. Terms can be listed and filtered by `status` and `enforcement_severity`, in `term` ascending order — the order the scan walks them in.

The **violation scan** is deliberately simple, and its ordering is fixed. The candidate list is the terminology terms whose `status` is `ACTIVE` only, ordered by `term` ascending; retired terms never produce a violation, and the ordering is by the term's spelling, never by its identifier. The tokens to be examined are the submitted `used_terms` array, compared case-insensitively; the array is described as lowercased because that is the convention, but case is not enforced on the way in — a token supplied in mixed or upper case is accepted and still matches, since the comparison lowercases both sides. Duplicate tokens in the array are harmless: the tokens are reduced to a set before the walk, so repeating a forbidden wording cannot raise the violation count. Only `forbidden_forms` are consulted; a token that happens to equal some term's `preferred_form` is never a violation. Walking the candidate list in that pinned order, a term records exactly **one** violation if any submitted token equals any entry of that term's `forbidden_forms` under a case-insensitive comparison — a term violated by three different tokens still counts once — and that violation carries the term's `enforcement_severity`. The blocker count is then the number of violations whose severity is `BLOCKER`, the warning count is the number whose severity is `WARNING`, and `violating_term_ids` is the list of violated term identifiers in the same `term`-ascending order.

`BLOCKER` and `WARNING` are not two shades of the same thing. An open `BLOCKER` violation prevents a topic from being submitted for review at all; a `WARNING` violation never blocks anything and only lowers the page's health score.

Retiring a term is how a style-guide decision is walked back. A `DocsLead` retires a term whose `status` must be `ACTIVE`; a second attempt on an already-retired term is refused with `ERR_TERM_ALREADY_RETIRED`. Retirement sets `status` to `RETIRED`, stamps `retired_at` with the logical clock, and then — for every topic whose newest source revision lists this term among its `violating_term_ids`, in `created_at` ascending order — recomputes `open_blocker_violations` and `open_warning_violations` over the still-active terms only, and recomputes that topic's `health_score` **only when the topic already carries one**. A topic whose `health_score` is still null keeps a null score and a null `health_score_variant` even though its live counters just moved; a topic that carries a score is rescored under the variant it already reports in `health_score_variant`, so retirement never switches a page from one variant to the other and never invents a variant for a page that had none. Each visited topic's `version` and `updated_at` move only if that recomputation actually changed something, per §2.8. A topic can become submittable as a direct result. What retirement pointedly does **not** do is rewrite any snapshot: each source revision keeps its `blocker_violation_count`, `warning_violation_count`, and `violating_term_ids` exactly as recorded, and every change record keeps its `terminology_blocker_count` exactly as recorded.

### 3.5. Technical-Accuracy Review and Sign-Off Decisions

Submitting a page for review is the assigned writer's act, and it advances `review_state` from `NOT_SUBMITTED` to `PENDING_SIGNOFF`, or from `CHANGES_REQUESTED` back to `PENDING_SIGNOFF` after a fresh revision. Five conditions guard it, and they are evaluated in this order. The acting `Writer`'s `X-User-ID` must equal the plan item's `assigned_writer_id`, else `ERR_NOT_ASSIGNED_WRITER`. The topic's `review_state` must be `NOT_SUBMITTED` or `CHANGES_REQUESTED`; a page already `PENDING_SIGNOFF` or `FULLY_APPROVED` is refused with `ERR_TOPIC_ALREADY_IN_REVIEW`. The topic's `current_revision_number` must be at least 1, because a page with no authored revision has nothing to review — an empty input set, not a zero-length success — and the refusal is `ERR_NO_REVISIONS`. The `current_revision_number` must be strictly greater than `last_submitted_revision_number`, so resubmitting the identical revision is refused with `ERR_NO_NEW_REVISION`; this is the guard that closes the changes-requested loop, since a page can only re-enter review once its author has actually written something new. Then the release train's `doc_readiness_posture` is consulted: `OPEN` admits any submission, `RESTRICTED` admits a submission only when the plan item's `audience_tier` is `CRITICAL`, and `FROZEN` always rejects; a blocked submission returns `ERR_DOC_FREEZE_POSTURE_BLOCKED`. Last, the topic's `open_blocker_violations` must be exactly 0, else `ERR_TERMINOLOGY_BLOCKER_PRESENT` — and because that counter is live, a violation whose term has since been retired no longer stands in the way, while warning-severity violations never did.

A successful submission stamps `submitted_at` with the logical clock, sets `last_submitted_revision_number` to the current revision number, and moves the plan item from `IN_AUTHORING` or `IN_REVISION` to `IN_REVIEW`.

Sign-offs are requested by a `DocsLead`, not by the writer. Naming a `reviewer_id` creates a sign-off in state `PENDING` on the topic, copies the reviewer's `discipline` onto the sign-off so the requirement is fixed at request time, stamps `requested_at` with the logical clock, leaves `pinned_revision_number` null along with `decided_at` and `comment` — all three are present keys holding null on a fresh request — and increases that reviewer's `open_signoff_count` by 1. The topic's `review_state` must be `PENDING_SIGNOFF` — a request against a page that is not currently in review is refused with `ERR_TOPIC_NOT_IN_REVIEW`. Two further rules then apply in a specific order. **The self-review prohibition comes first**: the requested reviewer's `person_key` must differ from the `person_key` of the writer who authored the topic's newest source revision, because an author may never review their own page, and a violation returns `ERR_SELF_REVIEW_FORBIDDEN` (HTTP 403). **Only then** is discipline uniqueness checked: the topic must hold no sign-off in state `PENDING`, `APPROVED`, or `CHANGES_REQUESTED` for the requested reviewer's discipline, else `ERR_DUPLICATE_SIGNOFF_DISCIPLINE`. Because the ordering is fixed, a self-review request aimed at a discipline that is already covered reports the self-review error, not the duplicate. A topic's sign-offs — including superseded history — can be listed in `created_at` ascending order and filtered by `state`; the global sign-off list additionally filters by `topic_id`, `reviewer_id`, `state`, and `discipline`.

The owning `Reviewer` decides a sign-off by supplying a `decision` of either `APPROVED` or `CHANGES_REQUESTED`, optionally with a `comment` of up to 500 characters. The `comment` is copied onto the sign-off on both branches and is stored as null when it is omitted or sent as `null`; an empty string is a legitimate comment and is stored as one. Three preconditions apply to both branches: `X-User-ID` must equal the sign-off's `reviewer_id` (`ERR_SIGNOFF_NOT_OWNED`), the sign-off's `state` must be `PENDING` — an already `APPROVED`, `CHANGES_REQUESTED`, or `SUPERSEDED` sign-off is refused with `ERR_SIGNOFF_ALREADY_DECIDED` — and the topic's `review_state` must be `PENDING_SIGNOFF` (`ERR_TOPIC_NOT_IN_REVIEW`).

On the **`PENDING → APPROVED`** branch, `decided_at` is stamped from the logical clock, `pinned_revision_number` is set to the topic's `current_revision_number`, and the reviewer's `open_signoff_count` decreases by 1. The approval is quasi-terminal: nothing but a later revision moves it, and when that happens it moves to `SUPERSEDED`. A topic reaches `review_state` `FULLY_APPROVED` at the moment it holds one `APPROVED` `ENGINEERING` sign-off and one `APPROVED` `PRODUCT` sign-off **both pinned to the topic's current revision number** — two approvals pinned to different revisions do not constitute full approval. Reaching `FULLY_APPROVED` stamps `approved_at` with the logical clock, computes `signoff_latency_days` as the whole number of days between `submitted_at` and `approved_at` with any fractional day discarded, computes the topic's `health_score` under the pre-publication variant and sets `health_score_variant` to `PRE_PUBLICATION`, moves the plan item from `IN_REVIEW` to `APPROVED_CONTENT`, increments the train's `approved_plan_item_count` by 1, and recomputes the train's ratio and posture.

On the **`PENDING → CHANGES_REQUESTED`** branch, a four-hop cascade runs. **Hop one** stamps `decided_at` from the logical clock, leaves `pinned_revision_number` null, and decreases the reviewer's `open_signoff_count` by 1. **Hop two**, caused by hop one, sets the topic's `review_state` to `CHANGES_REQUESTED` and moves every **other** sign-off of that topic whose state is `PENDING` or `APPROVED` to `SUPERSEDED`, clearing each one's `pinned_revision_number` — a single reviewer asking for changes wipes the slate for both disciplines. **Hop three**, caused by hop two, moves the plan item from `IN_REVIEW` to `IN_REVISION`, increases its `rework_count` by 1, raises its `load_points` by 1.0 point for that additional rework unit, and recomputes the assigned writer's `committed_load_points` so the conserved quantity still equals the sum over the writer's counted items. Notably, the capacity ceiling is **not** re-checked on this cascade path: rework can push a writer above `capacity_points`, and that is intended, because refusing a reviewer's feedback would be worse. **Hop four**, caused by hop three, recomputes the train's `approved_topic_ratio` and `doc_readiness_posture`.

Sign-offs also reach `SUPERSEDED` without any reviewer acting, driven by the system rather than a request: a new source revision on the topic supersedes every sign-off in state `PENDING` or `APPROVED`, a sibling reviewer's changes-requested decision supersedes the others, and cancelling the plan item supersedes all of them. In every such case `pinned_revision_number` is cleared, and where the prior state was `PENDING` the reviewer's `open_signoff_count` decreases by 1; where the prior state was `APPROVED` there is no open count to adjust, since it was already released when the approval was recorded.

### 3.6. Versioned Documentation Sets: Publication, Archival, and End of Life

Customers of a supported release read a **documentation set version** — a labelled snapshot of the release's pages. A `DocsLead` opens one as a draft against a `release_train_id` with a `version_label` of 1 to 40 characters that must be unique among that train's documentation sets whatever status those sets hold, a collision being refused with `ERR_DUPLICATE_VERSION_LABEL`, and, as described in §2.6, must present `expected_release_train_version`. A new draft opens with `status` `DRAFT`, `published_topic_count` 0, and `projected_localization_budget_cents` 0, since no projection exists until publication, and with `eol_notice_text`, `published_at`, and `archived_at` all present and null. Opening a new draft moves any documentation set of that train that is currently the train's only `DRAFT` row to `SUPERSEDED`, and increments the release train's `version` by 1. Documentation sets can be listed and filtered by `release_train_id` and `status`, and read individually with their stored budget projection and end-of-life notice on display.

Publishing the draft is the single densest operation in this system. Three preconditions are evaluated in a fixed order, all of them **before any state is mutated**. The set's `status` must be `DRAFT`; a set that is already `PUBLISHED`, `SUPERSEDED`, or `ARCHIVED` is refused with `ERR_DOC_SET_NOT_DRAFT`. At least one topic of the train must have `review_state` `FULLY_APPROVED`, else `ERR_NO_APPROVED_TOPICS` — this is checked *before* the budget projection, so an empty candidate set never surfaces as a budget error. Then the **localization budget projection** is computed and compared against the train's `localization_budget_cap_cents`; a projection strictly greater than the cap is refused with `ERR_LOCALIZATION_BUDGET_EXCEEDED`, while a projection exactly equal to the cap is allowed to publish. The computed figure reaches `projected_localization_budget_cents` only once that comparison has passed, so a refused publication leaves the draft's stored projection at 0 rather than recording the over-cap number it was rejected for.

The projection is a base quote only — no rush surcharge and no volume discount enters it — and its rounding order is part of the contract: **round per locale, then sum**. First, the publishable word volume is the sum of `latest_body_word_count` over all of the train's `FULLY_APPROVED` topics. Second, the participating locales are the locale profiles whose `status` is `ACTIVE` **and** whose `publication_mode` is `SIMULTANEOUS`, walked in `locale_code` ascending order; paused locales and delayed-publication locales contribute nothing at all. Third, for each locale in that order: the translation-memory word count is the publishable volume multiplied by that locale's `tm_coverage_pct` divided by 100, with any fraction discarded downwards; the effective word count is the publishable volume minus seventy percent of that translation-memory word count, again with any fraction of the seventy-percent figure discarded downwards, because memory matches are cheaper rather than free; and that locale's contribution in cents is the effective word count multiplied by the locale's `per_word_rate_cents`, **rounded half up to whole cents right there**. Fourth, `projected_localization_budget_cents` is the sum of those already-rounded per-locale figures. Summing the unrounded products and rounding once at the end can differ by up to a cent per locale, and that difference is exactly enough to flip the cap comparison, so the pinned order is mandatory.

Once the three preconditions pass, publication proceeds. The set's `status` becomes `PUBLISHED` and `published_at` is stamped from the logical clock. Every topic of the train whose `review_state` is `FULLY_APPROVED` moves `publication_state` from `UNPUBLISHED` to `PUBLISHED`, in `created_at` ascending order, each taking `published_at` from the logical clock and `published_in_doc_set_version_id` from the publishing set; `published_topic_count` is set to the number of topics this publication actually took live. Each of those topics has its `health_score` recomputed under the post-publication variant with `health_score_variant` set to `POST_PUBLICATION`. Each such topic's plan item moves from `APPROVED_CONTENT` to `PUBLISHED`, which releases that writer's load points — the published item leaves the counted set, so the writer's `committed_load_points` decreases by the item's `load_points` and their `assignment_count` decreases by 1. A `FULLY_APPROVED` topic whose `publication_state` is already `PUBLISHED` or `ARCHIVED` — a page an earlier set took live that has since been revised and re-approved — is passed over by all of that: it keeps its existing `published_at` and `published_in_doc_set_version_id`, its `health_score` is not recomputed, its plan item is left untouched even when that item sits in `APPROVED_CONTENT`, and it does not count toward `published_topic_count`. The train's `localization_committed_cents` is recomputed and its ratio and posture are recomputed.

Publication also seeds the translation pipeline. For each topic just taken live, and for each locale profile whose `status` is `ACTIVE` and whose `publication_mode` is `SIMULTANEOUS` — walked in `locale_code` ascending order — a translation job is auto-created in state `QUEUED` with `auto_created` set to true, pinning `source_revision_number` from the topic's `current_revision_number`, reserving that topic's `latest_body_word_count` on that locale and carrying a provisional cost quote. A topic that already has a non-terminal job for that locale is skipped, because the one-open-job-per-topic-and-locale rule is not waived by the cascade. What *is* waived is the locale's parallelism ceiling: auto-created jobs bypass `parallel_job_limit` entirely. Each auto-created job spans from the logical clock's date through that date plus the locale's `sla_days`, which makes its window exactly one day longer than the service-level period, so an auto-created job never carries a rush surcharge. Each new job increases its locale's `committed_source_words` by the reserved volume and its `open_job_count` by 1. The recomputation of the train's `localization_committed_cents` described in the previous paragraph runs *after* this seeding, so it already counts every job auto-created here at its provisional quote.

Archiving a published set retires it with a customer-visible notice, and runs a five-hop cascade. A `DocsLead` supplies `eol_notice_text` of 10 to 300 characters, which will be rendered on every archived page. The set's `status` must be `PUBLISHED`, else `ERR_DOC_SET_NOT_PUBLISHED`, and that is the operation's only precondition: the release train's own lifecycle `status` is **not** consulted, so a set may be archived while its train still sits in `PLANNED` or `DOC_FREEZE`. That is precisely how a train can reach the `DOC_FREEZE → GA` gate of §3.1 with no set in `PUBLISHED` status left and be refused there, having published and then archived the only set it ever had. **Hop one** sets `status` to `ARCHIVED`, stamps `archived_at` from the logical clock, stores the notice text, and sets the release train's `eol_notice_posted` to true. **Hop two**, caused by hop one, moves every topic whose `published_in_doc_set_version_id` names this set from `publication_state` `PUBLISHED` to `ARCHIVED`, in `created_at` ascending order, recomputing each one's `health_score` under the post-publication variant. **Hop three**, caused by hop two, moves every translation job of those topics whose state is `QUEUED`, `TRANSLATED`, `REWORK_REQUESTED`, or `SCHEDULED_DELAYED` to `CANCELLED`, in `created_at` ascending order, with `cancel_reason` recorded as exactly `CASCADE_DOC_SET_ARCHIVED`. **Hop four**, caused by hop three, decreases each affected locale profile's `committed_source_words` by the cancelled job's `reserved_source_words` and its `open_job_count` by 1. **Hop five**, caused by hop four, recomputes the train's `localization_committed_cents` over the jobs that survived.

### 3.7. Change Records, Editorial Passes, and Release-Note Compilation

Release notes are compiled from **change records**, one per shipped change. Either a `DocsLead` or a `Writer` may submit one against a `release_train_id`, supplying an `internal_summary` of 1 to 300 characters copied from the change-management system, a `severity` of `BREAKING`, `SECURITY`, `MAJOR`, `MINOR`, or `PATCH`, a `category` of `FEATURE`, `FIX`, `PERFORMANCE`, `SECURITY_PATCH`, or `DEPRECATION`, and an `affected_component` key of 1 to 60 characters. The record opens in state `SUBMITTED` with `submitted_by_user_id` taken from the submitter's `X-User-ID`, `customer_facing_text` null, `editorial_by_user_id` null, `terminology_blocker_count` 0, `rework_count` 0, and `exclusion_reason` null. Records can be listed and filtered by `release_train_id`, `state`, `severity`, and `category`, ordered by `created_at` ascending — the same order a release note compiles them in — and read individually with their terminology blocker snapshot on display.

An **editorial pass** turns engineering language into customer language, and it is deliberately a different person's job. A `DocsLead` supplies the proposed `customer_facing_text` of 10 to 300 characters together with a mandatory `used_terms` array to be scanned, carrying between 0 and 200 entries each 1 to 60 characters long exactly as a source revision does. Two preconditions guard it, **in this order**, as the bands of §2.5 require. The record's `state` must be `SUBMITTED` or `REWORK_REQUESTED`; a record that is `EDITORIALLY_APPROVED`, `EXCLUDED`, or `PUBLISHED` is refused with `ERR_CHANGE_RECORD_NOT_EDITABLE`. Only then is separation of duties tested: the acting `X-User-ID` must differ from the record's `submitted_by_user_id`, and an editor who is also the submitter is refused with `ERR_EDITORIAL_SOD_VIOLATION` (HTTP 403). Because the state test comes first, a submitter reaching for their own already-approved or already-excluded record is told the record is not editable rather than that they may not edit it.

The pass then forks on the terminology scan of §3.4, and the two branches store **different** field sets. When the scan raises zero `BLOCKER` violations, the record moves to `EDITORIALLY_APPROVED`: `customer_facing_text` is stored, `editorial_by_user_id` is set to the acting `X-User-ID`, and `terminology_blocker_count` is set to 0. Reaching `EDITORIALLY_APPROVED` from `REWORK_REQUESTED` behaves identically, and in particular leaves `rework_count` exactly as it stands — a clean pass never resets the rework history. When the scan raises one or more `BLOCKER` violations, the record moves to `REWORK_REQUESTED` (or stays there, if it was already `REWORK_REQUESTED`): `rework_count` increases by 1 and `terminology_blocker_count` is refreshed to the blocker violation count, while `customer_facing_text` is **not** stored and `editorial_by_user_id` is **not** set. The blocker count is an immutable snapshot: retiring one of the cited terms afterwards does not lower it.

A record can also be dropped from customer communication for good. A `DocsLead` supplies an `exclusion_reason` of 5 to 200 characters and the record moves to `EXCLUDED`, permitted only from `SUBMITTED` or `REWORK_REQUESTED` and otherwise refused with `ERR_CHANGE_RECORD_NOT_EDITABLE`. An excluded record can never enter a release note.

Compiling a **release note** gathers the editorially approved records of a train into a customer-facing document that ships inside a published documentation set. A `DocsLead` supplies a `doc_set_version_id` together with `expected_doc_set_version_version` as described in §2.6; the note also carries the `release_train_id` of the train whose records were compiled. The target documentation set must be `PUBLISHED`, else `ERR_DOC_SET_NOT_PUBLISHED`, and at least one change record of that train must be in state `EDITORIALLY_APPROVED`, else `ERR_NO_PUBLISHABLE_CHANGES` — an empty candidate set is an error, not a note with an empty body and a zero score. Compilation opens the note with `status` `COMPILED`, stamps `compiled_at` from the logical clock, moves any existing `COMPILED` note of that documentation set to `SUPERSEDED` while leaving that superseded note's change records `EDITORIALLY_APPROVED` so they are recompiled into the new note, and increments the documentation set's `version` by 1. Notes can be listed and filtered by `release_train_id`, `doc_set_version_id`, and `status`, and read individually with both provisional and final impact figures.

The **customer-impact score** is computed twice with the same six steps and one differing input, once at compilation and once at publication. The included set is fixed once, at compilation: it is the change records of the documentation set's release train whose `state` is `EDITORIALLY_APPROVED` at that instant, ordered by `created_at` ascending; records that are `SUBMITTED`, `REWORK_REQUESTED`, `EXCLUDED`, or already `PUBLISHED` are never included. `severity_counts` maps each of the five severities to the number of included records carrying it, with keys `BREAKING`, `SECURITY`, `MAJOR`, `MINOR`, and `PATCH`. `included_change_record_ids` lists the compiled records ordered by severity rank ascending and then by `created_at` ascending, where the severity rank runs from the heaviest to the lightest. `headline_severity` is the severity with the highest weight present in the included set, using the weights `BREAKING` 40, `SECURITY` 25, `MAJOR` 12, `MINOR` 4, and `PATCH` 1. The raw impact is the sum of those weights across every included record. A record counts as *documented* when its `affected_component` equals the `feature_key` of at least one plan item of the train in the variant's counted status set, and the coverage factor is the number of documented records divided by the number of included records, rounded half up to two decimal places. The score is the raw impact multiplied by two minus the coverage factor, rounded half up to two decimal places and then capped at 100 — undocumented change is what hurts customers, so a coverage factor of `1.00` leaves the raw figure untouched while a coverage factor of `0.00` doubles it.

The two variants differ only in which plan items count as documentation. At compilation the coverage counts plan items whose status is `APPROVED_CONTENT` **or** `PUBLISHED` — approved-but-unpublished documentation is credited as if it will ship — and the results are stored as `coverage_factor_provisional` and `impact_score_provisional`, with `coverage_factor_final` and `impact_score_final` left null. At publication the coverage counts plan items whose status is `PUBLISHED` **only** — documentation that never went live loses its credit — and the results are stored as `coverage_factor_final` and `impact_score_final`. For an identical set of change records, the final score therefore rises whenever some approved documentation failed to reach publication.

Publishing the note has one hard gate beyond its own state. The note's `status` must be `COMPILED`: an already published note is refused with `ERR_RELEASE_NOTE_ALREADY_PUBLISHED`, and a note that a later compilation superseded is refused with `ERR_RELEASE_NOTE_SUPERSEDED`. Then, for **every** included change record whose `severity` is `BREAKING`, there must exist a deprecation notice of the same release train whose `feature_key` equals that record's `affected_component` and whose `status` is `PUBLISHED`; any breaking change without that published migration path blocks the whole note with `ERR_MIGRATION_GUIDE_NOT_PUBLISHED`. On success, `coverage_factor_final` and `impact_score_final` are computed with the final variant, `published_at` is stamped from the logical clock, and every included change record moves from `EDITORIALLY_APPROVED` to `PUBLISHED`. Both the breaking-change gate and the final figures read the note's stored `included_change_record_ids` rather than re-running the candidate query: a change record that reached `EDITORIALLY_APPROVED` only after this note was compiled is neither scored here nor published here, and a record some earlier note already moved to `PUBLISHED` still sits in this note's list, still has to satisfy the breaking-change gate, and still contributes its severity weight to these final figures, while its own `state` is left exactly as it stands.

### 3.8. The Localization Pipeline

A `LocalizationCoordinator` registers each target language as a **locale profile**, supplying a `locale_code` of exactly 5 characters in the BCP-47 pattern of a lowercase two-letter language, a hyphen, and an uppercase two-letter region — unique across all locale profiles, with a collision refused as `ERR_DUPLICATE_LOCALE_CODE`. The profile also fixes `publication_mode`, either `SIMULTANEOUS` for a language that goes live alongside the source or `DELAYED` for one that follows on a lag; `tm_coverage_pct`, the translation-memory coverage that provisional quotes assume, between 0 and 100 with two decimal places; `per_word_rate_cents`, the vendor's positive rate per effective source word carried to two decimal places; `sla_days`, the contracted turnaround between 1 and 120 days, which doubles as the lag applied to delayed publication; and `parallel_job_limit`, between 1 and 20, the number of overlapping vendor windows the locale can sustain. An optional `status` of `ACTIVE` or `PAUSED` defaults to `ACTIVE`; a paused locale accepts no new jobs and is skipped entirely by publication cascades. Profiles open with `committed_source_words` 0 and `open_job_count` 0, are readable individually with their live word balance, and are listable with filters on `status` and `publication_mode`.

A manual **translation job** is queued by a `LocalizationCoordinator` against a `topic_id` and a `locale_profile_id` over a closed calendar window given by `window_start_date` and `window_end_date`. The two body references resolve in that order, so a request naming an unknown topic *and* an unknown locale profile reports `ERR_TOPIC_NOT_FOUND`. Five conditions then guard it, in this order. The source topic's `publication_state` must be `PUBLISHED` — only live pages are translated — else `ERR_SOURCE_TOPIC_NOT_PUBLISHED`. The locale profile's `status` must be `ACTIVE`, else `ERR_LOCALE_PAUSED`. The window must be well formed, with `window_end_date` on or after `window_start_date`, else `ERR_INVALID_DATE_WINDOW`. The topic must have no non-terminal job for that same locale already, else `ERR_DUPLICATE_LOCALIZATION_JOB`. Finally the locale's parallelism ceiling: count the locale's open jobs whose closed `[window_start_date, window_end_date]` interval intersects the requested closed interval, and reject with `ERR_LOCALE_PARALLEL_JOB_LIMIT_EXCEEDED` when that count has already reached `parallel_job_limit`. Because these intervals are closed, two windows that touch on a single shared date do intersect — the opposite of the half-open writer windows of §3.2 — and jobs the publication cascade auto-created bypass this ceiling in both directions: an auto-created job is never tested against it, and it never occupies one of its slots either, so the count a manual request is measured against is a count of overlapping *manual* open jobs only.

A successful create opens the job in state `QUEUED` with `auto_created` false, pins `source_revision_number` from the topic's `current_revision_number` and `reserved_source_words` from the topic's `latest_body_word_count`, and quotes a provisional cost. The locale's `committed_source_words` increases by `reserved_source_words`, its `open_job_count` increases by 1, and the owning release train's `localization_committed_cents` is recomputed. Jobs are readable individually with both cost figures side by side, and listable with filters on `topic_id`, `locale_profile_id`, `state`, and `cost_variant` in `created_at` ascending order — the only discovery channel for the jobs a documentation-set publication auto-created.

**The quote.** Nine steps produce a job's cost, and their order is part of the contract because the rush surcharge is applied *before* the volume discount and the volume band is selected from the **surcharge-inclusive** subtotal. First, a source word volume and a translation-memory word volume are established, and this is where the two variants differ. Second, `leverage_pct` is `0.00` when the source volume is zero, and otherwise the memory volume multiplied by 100 and divided by the source volume, rounded half up to two decimal places. Third, the effective word count is the source volume minus seventy percent of the memory volume, with any fraction of that seventy-percent figure discarded downwards — memory matches are cheaper, not free. Fourth, the base cost in cents is the effective word count multiplied by the locale's `per_word_rate_cents`, rounded half up to whole cents. Fifth, the window length in days is the number of days from `window_start_date` to `window_end_date` plus one, because the interval is closed; when that window length is strictly shorter than the locale's `sla_days`, `rush_surcharge_cents` is fifteen percent of the base cost rounded half up to whole cents, and otherwise it is 0. Sixth, the subtotal is the base cost plus the surcharge. Seventh, a discount percentage is selected from the subtotal by taking the first matching band in descending order: 10 percent when the subtotal is at least 500,000 cents, otherwise 6 percent when it is at least 200,000 cents, otherwise 3 percent when it is at least 50,000 cents, and otherwise 0 percent; `volume_discount_cents` is that percentage of the subtotal, rounded half up to whole cents. Eighth and last, the cost is the subtotal minus the discount. Applying the discount to the base cost first and adding the surcharge afterwards would select a band from a different number and yield a different total, which is why the order is fixed.

The **provisional** variant runs at job creation. Its source volume is `reserved_source_words` — the topic's word count pinned at creation — and its memory volume is that source volume multiplied by the locale's advertised `tm_coverage_pct` divided by 100, with any fraction discarded downwards. Its result is written to `estimated_cost_cents` with `cost_variant` set to `PROVISIONAL`. The **final** variant runs at delivery. Its source volume is `translated_word_count` as actually delivered and its memory volume is `tm_matched_word_count` as actually measured. Its result is written to `final_cost_cents` with `cost_variant` set to `FINAL`, and `estimated_cost_cents` is deliberately **left intact** so both numbers remain observable on one row. A delivery that matches the reservation word-for-word still diverges from the provisional quote whenever the measured leverage differs from the locale's advertised coverage.

Recording a delivery moves the job from `QUEUED` to `TRANSLATED`, or from `REWORK_REQUESTED` back to `TRANSLATED` to close the rework loop. The coordinator supplies `translated_word_count` between 1 and 400,000 inclusive and `tm_matched_word_count` between 0 and the delivered count inclusive; a matched count exceeding the delivered count is a shape violation reported as `ERR_INVALID_REQUEST`. The job's `state` must be `QUEUED` or `REWORK_REQUESTED`, else `ERR_LOCALIZATION_JOB_NOT_DELIVERABLE` — and this state test runs **before** the service-level test, so a stale delivery aimed at an already-published or cancelled job reports the state error and never a breach. The service-level test then requires that the logical clock's date is on or before `window_end_date` plus a three-day grace period; a delivery arriving later than that is refused outright with `ERR_LOCALIZATION_SLA_BREACH` rather than repriced. On success the two word counts are stored and `leverage_pct`, `rush_surcharge_cents`, `volume_discount_cents`, and `final_cost_cents` are all recomputed under the final variant with `cost_variant` set to `FINAL`; the train's `localization_committed_cents` now counts this job's final figure in place of its provisional one.

Bouncing a delivery back to the vendor moves the job from `TRANSLATED` to `REWORK_REQUESTED` and increases `rework_count` by 1; a job in any other state is refused with `ERR_LOCALIZATION_JOB_NOT_TRANSLATED`. The bounced delivery's `final_cost_cents` and `leverage_pct` stand unchanged until the next delivery overwrites them.

Publishing a localized page is a **fork with two branches that carry different side effects**, rejoining at `PUBLISHED_LOCALIZED`. The job's `state` must be `TRANSLATED` or `SCHEDULED_DELAYED`, else `ERR_LOCALIZATION_JOB_NOT_TRANSLATED`, and the source topic's `publication_state` must be `PUBLISHED`, else `ERR_SOURCE_TOPIC_NOT_PUBLISHED`. On the **simultaneous branch** — taken when the locale's `publication_mode` is `SIMULTANEOUS` — the release train's `status` must additionally be `GA` or `MAINTENANCE`, else `ERR_TRAIN_NOT_GA`; the job then moves `TRANSLATED → PUBLISHED_LOCALIZED` with `published_at` stamped from the logical clock, `publication_mode_applied` set to `SIMULTANEOUS`, and `scheduled_publish_date` left null. On the **delayed branch** — taken when the locale's `publication_mode` is `DELAYED` — the train's status is **not** consulted at all, and the outcome depends on the clock. When the logical clock's date is still earlier than the source topic's publication date plus the locale's `sla_days`, the job moves `TRANSLATED → SCHEDULED_DELAYED`: `scheduled_publish_date` is computed as the calendar date of the topic's `published_at` plus `sla_days` days, `publication_mode_applied` is set to `DELAYED`, `published_at` stays null, and — diverging from the simultaneous branch — the locale's reservation is **not** released. A later publication attempt on that parked job moves `SCHEDULED_DELAYED → PUBLISHED_LOCALIZED` once the logical clock's date has reached or passed `scheduled_publish_date`, keeping that date on the record rather than clearing it; before that date the job simply stays `SCHEDULED_DELAYED` and the response repeats it unchanged — nothing at all is written, so the job's `version` and `updated_at` do not move. When the lag has *already* elapsed at the first publication attempt, that is, when the clock's date is on or after the topic's publication date plus the locale's `sla_days`, the delayed branch skips the parked state altogether and moves `TRANSLATED → PUBLISHED_LOCALIZED` in one step, stamping `published_at`, setting `publication_mode_applied` to `DELAYED`, and still recording the computed date in `scheduled_publish_date` — which is therefore non-null on a delayed job that never actually waited, in contrast to the simultaneous branch, where it is always null.

Whenever a job reaches `PUBLISHED_LOCALIZED`, by either branch, it leaves the locale's active set: `committed_source_words` decreases by `reserved_source_words`, `open_job_count` decreases by 1, and the train's `localization_committed_cents` is recomputed. Cancelling has the same balance effect and is available from `QUEUED`, `TRANSLATED`, `REWORK_REQUESTED`, or `SCHEDULED_DELAYED`; a job that is already `PUBLISHED_LOCALIZED` or `CANCELLED` is refused with `ERR_LOCALIZATION_JOB_NOT_CANCELLABLE`. The coordinator supplies a `cancel_reason` of 5 to 200 characters — the archive and end-of-life cascades write `CASCADE_DOC_SET_ARCHIVED` in that field on the jobs they cancel — and the locale's reserved word balance returns to precisely its pre-creation value.

Two ledger definitions close the pipeline. A locale's `committed_source_words` is the sum of `reserved_source_words` over that locale's jobs whose state is `QUEUED`, `TRANSLATED`, `REWORK_REQUESTED`, or `SCHEDULED_DELAYED`, and `open_job_count` is the count of that same set; jobs that are `PUBLISHED_LOCALIZED` or `CANCELLED` are excluded. A release train's `localization_committed_cents` sums, over the jobs in that same open-state set whose topic belongs to the train through its plan item, each job's `final_cost_cents` when its `cost_variant` is `FINAL` and its `estimated_cost_cents` otherwise — so a delivered job visibly switches which of its two costs the train's ledger counts.

### 3.9. Deprecation Timelines and Migration Guides

Telling customers a feature is going away is a communication problem with a legal shape, so the notice period is enforced arithmetically. A `DocsLead` drafts a **deprecation notice** against a `release_train_id` with a `feature_key` of 1 to 60 characters naming the feature being withdrawn — uniqueness within the train is a drafting convention rather than an enforced constraint, exactly as with the plan-item `feature_key` of §3.2, so two notices of one train may carry the identical key and no error code exists for a collision; the release-note gate of §3.7 is satisfied by *any* published notice whose key matches, so duplicates are harmless there — a `severity_tier` of `BREAKING`, `MAJOR`, or `MINOR`, three dates — `announce_date`, `deprecated_date` (the day the feature stops being recommended), and `removal_date` (the day it disappears) — and a `migration_guide_topic_id` naming the page customers will be sent to.

Three checks then run in a fixed order. First, the migration guide must belong to the same product line: the topic named by `migration_guide_topic_id` must resolve, through its plan item, to a release train whose `product_key` equals the notice's own train's `product_key`, and a mismatch is refused with `ERR_MIGRATION_GUIDE_PRODUCT_MISMATCH`. Second, the timeline must be ordered: `announce_date` on or before `deprecated_date`, and `deprecated_date` strictly before `removal_date`, else `ERR_INVALID_DATE_WINDOW`. Third, the notice period must be long enough. `notice_days` is the whole number of days from `announce_date` to `removal_date`, and the minimum required is 180 days for a `BREAKING` tier, 90 days for `MAJOR`, and 30 days for `MINOR`; a `notice_days` value exactly equal to the minimum is compliant, and only a shorter period is refused, with `ERR_NOTICE_PERIOD_TOO_SHORT`. Because the product-line check precedes the arithmetic, a notice that points at the wrong product line *and* allows too little notice reports the referential mismatch. The release train's own dates never relax the minimum.

A draft stores both computed timeline fields so the accepted plan is auditable afterwards: `notice_days` as above, and `earliest_removal_date` as `announce_date` plus the tier's minimum notice period in days. The notice opens with `status` `DRAFTED` and `published_at` null, and notices are listable with filters on `release_train_id`, `migration_guide_topic_id`, `status`, and `severity_tier`.

Publishing a notice requires three things, tested in this order. Its `status` must be `DRAFTED`; a notice that is `PUBLISHED` or `RETIRED` is refused with `ERR_DEPRECATION_NOTICE_ALREADY_PUBLISHED`. Then the migration guide topic must actually be live, with `publication_state` `PUBLISHED`, else `ERR_MIGRATION_GUIDE_NOT_PUBLISHED`; pointing customers at a page they cannot read is the one failure this workflow exists to prevent. Only last does the calendar enter: the logical clock's date must have reached or passed `announce_date`, else `ERR_ANNOUNCE_DATE_NOT_REACHED` — customers cannot be told before the announcement day. The guarding resource's state therefore precedes the temporal test, as the bands of §2.5 require, so a notice whose guide is still unpublished *and* whose announce date is still in the future reports the guide, never the calendar. Publication moves the notice to `PUBLISHED` and stamps `published_at` from the logical clock. Only a published notice unblocks a release note that carries a breaking change, and a notice in `PUBLISHED` reaches the terminal `RETIRED` state solely through the end-of-life cascade on its release train.

### 3.10. Reader Signals, Deflection, and Documentation Health

Readers are the only anonymous participants in this system, and they contribute exactly one thing. A `Reader` records a rating on a live page by supplying `rating` as an integer from 1 to 5 inclusive, an `outcome` of `RESOLVED_SELF_SERVE`, `OPENED_TICKET`, or `ABANDONED` describing what they did next, a `locale_code` of 5 characters in the `ll-CC` pattern identifying which language variant of the page they saw, a `session_key` of 6 to 60 characters identifying their reading session, and optionally a `comment` of up to 500 characters. The `locale_code` is validated by value rather than by identifier: it must match the `locale_code` of an existing locale profile, whatever that profile's `status` — a paused locale still admits feedback on the English page — and a code no profile carries is refused with `ERR_LOCALE_PROFILE_NOT_FOUND` (HTTP 404). The `session_key` is recorded for attribution only and constrains nothing: it is **not** unique per topic, so one reading session may leave several ratings on the same page, each becoming a separate feedback row that counts separately toward `sample_count`, `mean_rating`, and the deflection denominators. The page's `publication_state` must be `PUBLISHED` — feedback against a page that is `UNPUBLISHED` or `ARCHIVED` is refused with `ERR_FEEDBACK_TOPIC_NOT_PUBLISHED` — and that state check runs *after* the locale lookup, so a request that both names an unknown `locale_code` and targets an unpublished page reports the locale 404. Feedback rows are immutable and carry only `id` and `created_at` beyond their own fields. Recording one recomputes the topic's `health_score` under the post-publication variant, and advances the topic's `version` and `updated_at` only when that recomputation actually moves the score or the variant, per §2.4 — a rating that reproduces the score the page already carried leaves the topic's audit fields alone. A `DocsLead` or a `SupportAnalyst` — and nobody else — may list a page's feedback, filtered by `outcome`, in `created_at` ascending order; rows that have aged out of the metrics window are still returned there even though they no longer influence any figure.

**Deflection metrics** are computed over a trailing 30-day window ending at the logical clock, and are available to a `DocsLead` or `SupportAnalyst` as a computed read on the topic. The window begins 30 days before the logical clock and ends at the logical clock, with **both ends inclusive**; the response reports those bounds as `window_start_date` and `window_end_date`. Membership is decided on **instants**, not on dates: a row qualifies when its `created_at` instant is at or after the instant exactly 30 days before the clock's current value and at or before the clock's current value itself, while the two reported bounds are only the UTC calendar dates of those two instants. When the clock carries a time of day, the two representations therefore disagree at the edge — a row stamped earlier in the day than the clock's time on the reported `window_start_date` is outside the window even though its date equals that bound — and the instant comparison is the one that governs. `sample_count` is the number of the topic's feedback rows whose `created_at` falls inside that window. `mean_rating` is null when `sample_count` is zero and otherwise the sum of the `rating` values divided by `sample_count`, rounded half up to two decimal places. The *decided* rows are those in the window whose `outcome` is `RESOLVED_SELF_SERVE` or `OPENED_TICKET`; rows with `outcome` `ABANDONED` count toward `sample_count` and toward `mean_rating` but are excluded from the deflection denominator, because an abandoned session is neither a deflection nor an escalation. When there are no decided rows at all, both `deflection_pct` and `ticket_rate_pct` are null; otherwise `deflection_pct` is the number of `RESOLVED_SELF_SERVE` rows multiplied by 100 and divided by the number of decided rows, rounded half up to two decimal places, and `ticket_rate_pct` is the number of `OPENED_TICKET` rows treated the same way. Two empty cases are therefore distinct: a page with no feedback in the window reports a null `mean_rating` and a null `deflection_pct`, whereas a page whose window contains only abandoned sessions reports a real `mean_rating` and still a null `deflection_pct`.

**Documentation health** is a 0-to-100 score, carried to two decimal places and rounded half up, computed in seven steps. The churn penalty is 4 points for each revision beyond the second — that is, 4 multiplied by the amount by which `current_revision_number` exceeds 2, or zero when it does not exceed 2. The blocker penalty is 12 points for each of the topic's `open_blocker_violations`. The warning penalty is 3 points for each of its `open_warning_violations`; the weights are deliberately not normalized, so one blocker costs four times what one warning costs. The latency penalty is zero when `signoff_latency_days` is null, and otherwise 2 points for each day by which `signoff_latency_days` exceeds a three-day grace period, or zero when it does not exceed it. Those four penalties are subtracted from 100. The variant-specific deductions of the next paragraph are then subtracted from that figure, and `health_score` is finally the result or 0, whichever is larger, rounded half up to two decimal places — the score is clamped at zero and is never negative.

The **pre-publication** variant is the one used whenever a topic reaches `FULLY_APPROVED`, and it is selected by that event alone rather than by the page's `publication_state`. It is therefore the variant of a page that has not yet gone live, but it is *also* what a page that is already `PUBLISHED` gets when it is revised, re-submitted, and re-approved: such a page reverts to a `PRE_PUBLICATION` `health_score_variant`, and keeps it until some later post-publication event — a fresh reader rating, a single-topic read, or an archive cascade — recomputes it back. The variant applies no reader-signal deductions at all: feedback rows are ignored even if some exist. The **post-publication** variant applies while `publication_state` is `PUBLISHED` or `ARCHIVED`, and subtracts two further penalties in this order. The rating penalty is zero when the deflection window's `sample_count` is zero, and otherwise 4 points for each whole point by which the window's `mean_rating` falls short of 5 — that is, 4 multiplied by five minus the mean rating, rounded half up to two decimal places. The deflection penalty is zero when `deflection_pct` is null, and otherwise 0.06 points for each percentage point by which `deflection_pct` falls short of 100, rounded half up to two decimal places. A consequence worth internalizing: a published page with no feedback inside the window scores exactly what it scored before publication, while reporting `health_score_variant` as `POST_PUBLICATION`. The variant field always records which of the two produced the current `health_score`.

## 5. Error Code Catalogue

Every error response uses the envelope of §2.2, carrying the identifier below in `error_id` together with a human-readable `message`. The conditions that trigger each code are specified in §2 and §3 alongside the rules they enforce. The `message` is prose for a human reader and is never itself part of the contract: clients branch on `error_id` and on the HTTP status, never on message text.

Three responses sit outside the workflow rules and outside the table. A path matches whether or not it is written with a trailing slash. An unanticipated server fault is answered with the same envelope carrying `error_id` `ERR_INTERNAL` under HTTP 500 — a code no workflow rule ever raises deliberately.
