# Membership Overnight Parking API — Product Requirements Document

## 1. Introduction

Overnight parking is the connective tissue of this product. A travelling member with a fully self-contained rig pays an annual subscription for the right to ask a working business — a winery, a farm, a brewery or a road-side attraction — for permission to spend a night on its grounds, and the host asks for no site fee in return. What the host actually wants out of the arrangement is customers: a member who spends the evening tasting, buying merchandise or eating a meal at the host's premises. The platform exists to make that exchange trustworthy on both sides, and to keep it inside the crowded patchwork of state and municipal ordinances that govern commercial parking.

The system therefore has to hold four things in balance at once. Hosts must be onboarded against a local ordinance profile before they may accept anybody, and must be able to declare real physical parking sites with real electrical pedestals and real obstructions. Availability must be expressible in seasons and event weekends rather than as a permanently fixed capacity, because a harvest closure or a festival weekend changes what a host can offer without changing what it owns. Members must be admitted only when their subscription is live and their rig is genuinely self-contained. And the whole stay lifecycle — request, host decision, counter-request, confirmation, check-in, check-out, no-show, cancellation — has to serialize cleanly against a shared pool of sites.

Two operational realities shape the specification that follows. The first is that capacity is contested: several members, several hosts and several live events all move the same arithmetic, so a host's public posture is a derived aggregate recomputed on every change rather than a value anybody sets. The second is that conduct is cumulative: a member's standing score and strike count are consequences of every incident and every stranded stay, and the platform removes a member permanently once those consequences cross a threshold. To make all of this testable without waiting for a calendar, the platform runs on a controllable logical clock that drives window activation, lead-time guards and cancellation bands.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies to every request the platform serves. Where a rule below is derived rather than declared, the derivation is stated explicitly, because the derived fields are what most of the business logic reads.

### 2.1. Roles, Identity Headers and Access Control

Every request must identify its caller through two mandatory HTTP headers. `X-User-ID` carries the identity of the acting principal and `X-User-Role` declares the capacity in which that principal is acting. A request that omits either header, or that names a role the platform does not recognize, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). Four roles exist, and their names are spelled exactly `Anonymous`, `Member`, `HostOperator`, and `PlatformAdmin`.

Role identity binds to the header as follows. When `X-User-Role` is `Member`, `X-User-ID` is the `id` of the acting `Member`; ownership checks on any resource that references a `Member` compare that resource's member foreign-key field to `X-User-ID`, and a member acting on a stay request, vehicle or conduct disposition belonging to a different member is rejected with `ERR_UNAUTHORIZED` (HTTP 403). When `X-User-Role` is `HostOperator`, `X-User-ID` is the `id` of the acting `HostBusiness`; every host-scoped operation — declaring or amending sites, opening and amending availability windows, deciding, checking in and checking out stays, recording no-shows, verifying patronization receipts, and writing the host side of a review — compares the target host against `X-User-ID`. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may record it for audit purposes but never compares it against any entity's `id`. When `X-User-Role` is `Anonymous`, `X-User-ID` is likewise opaque and unpersisted, and the role may perform exactly one operation: registering a new member.

Above identity, every operation is also gated on the role being permitted for it. Acting outside the granted role — including a `Member` attempting an operation reserved to host staff or to platform staff — is rejected with `ERR_UNAUTHORIZED` (HTTP 403). The `Anonymous` role is the only role that may be used without a pre-existing member record, and it is not permitted to read, list or modify anything.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through query parameters. `limit` caps how many items a single response returns; when the caller omits it the value defaults to 10, and any supplied value must fall between 1 and 100 inclusive. `offset` says how many items to skip from the front of the result set and defaults to 0 when omitted. A caller that supplies a `limit` below 1 or above 100, or a non-integer value for either parameter, has its request rejected as malformed.

Unless a caller asks otherwise, every list endpoint returns its resources ordered by creation timestamp in ascending order — that is, by `created_at` ascending. Responses for list endpoints carry `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope so that a client can walk the collection without guessing whether more pages exist. Detail responses for a single resource omit the pagination fields, and their `response_type` is `object` rather than `array`.

### 2.4. The Host Capacity Basis and the Posture Ladder

A host's capacity is never a value the host types in. It is derived from two possible bases, and knowing which basis is live at a given instant is a precondition for every reservation decision in the system. The authority that decides the bases is the logical clock, described in §2.5.

When no availability window of the host is in `ACTIVE` status, capacity runs on the **base basis**: `effective_capacity` equals the number of that host's parking sites whose `is_active` flag is true. Adding a site or deactivating one changes availability immediately under this basis. When exactly one availability window of the host is active, capacity runs on the **live basis**: `effective_capacity` equals that window's `capacity_override` minus its `reserved_sites`, floored at zero. Under the live basis the physical site count is ignored entirely, so an event window may grant far more member sites — or far fewer — than the host physically owns.

The active window is selected as follows. Among the host's windows whose `window_status` is `ACTIVE` and whose `start_date` is at or before the current logical clock and whose `end_date` is after it, the system takes the one with the greatest `start_date`, breaking ties by `created_at` ascending. Inactive sites are excluded from the base basis, and windows in `SCHEDULED` or `CANCELLED` status are never consulted. This derivation is the `host_effective_capacity` rule and fires on any change to a host's site activity, to any window's status, `capacity_override` or `reserved_sites`.

One override sits on top of the basis: whenever a host's `posture` is `UNAVAILABLE` or `SUSPENDED`, `effective_capacity` is forced to 0 regardless of what the basis would otherwise report.

Occupancy is tracked separately. A stay carries a derived boolean, `count_toward_capacity`, that is true when its `request_status` is `CONFIRMED` and also true when its `request_status` is `REQUESTED` and its `request_depth` is 1 or under; in every other case it is false. `committed_sites` is simply the count of the host's stays whose `count_toward_capacity` is true. Stays in `DECLINED`, `CANCELLED`, `CHECKED_IN`, `CHECKED_OUT` or `NO_SHOW` status never contribute. `free_sites` is `effective_capacity` minus `committed_sites`, floored at zero — it is never negative. Because the stay being confirmed is already inside `committed_sites` at the moment of confirmation, the admission test at confirmation is evaluated against `effective_capacity - (committed_sites - 1)`, so a request's own reservation can never block its own confirmation. Two named bases exist for the same underlying set: the **reserved basis** counts `CONFIRMED` stays plus first-round `REQUESTED` requests (so a request at `request_depth` 0 already holds a site before the host has answered), while the **occupied basis** used for a host's public card counts only stays whose `request_status` is `CONFIRMED` or `CHECKED_IN`.

`posture` is derived from capacity by a four-step ladder, evaluated in this order. When `onboarding_status` is `SUSPENDED` or `REJECTED`, `posture` is `SUSPENDED`. Otherwise, when `effective_capacity` is less than 1, `posture` is `UNAVAILABLE`. Otherwise, when `free_sites` is less than 1, `posture` is `LIMITED`. Otherwise, when `free_sites` is at most the value of 20 percent of `effective_capacity` rounded up to the next whole number, `posture` is `LIMITED`. Otherwise `posture` is `OPEN`. The band comparison is inclusive: a host with 10 units of capacity and 2 free sites sits exactly on the rounded-up band and is `LIMITED`, while the same host with 3 free sites is `OPEN`. This is the `host_posture_derivation` rule.

Three further derived quantities ride along with the capacity arithmetic. `seasonal_windows_reserved_sites` is the sum of `reserved_sites` across every availability window of the host whose `window_status` is `ACTIVE`. `electric_site_count` is the number of parking sites belonging to the host that are both active and carry an electric pedestal. `latest_checkout_at` is the latest `occupancy_end` among the host's stays whose status is `CONFIRMED` or `CHECKED_IN`, and is null when the host has no such stay — it is the far edge of the host's outstanding occupancy.

### 2.5. Common Resource Properties, Derived Reconciliation and the Logical Clock

Every entity in this system is addressed by an `id`, which is a server-minted UUID carrying no type prefix or meaning. `HostBusiness`, `HostParkingSite`, `Member`, `HostAvailabilityWindow`, `StayRequest`, `Incident` and `HostPatronizationRecord` additionally carry the full set of system-managed bookkeeping fields: `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording first creation; `updated_at`, an ISO 8601 UTC timestamp with three fractional digits refreshed on every modification; and `version`, an integer that increments by one on every mutation of the resource. Three entities are deliberately lighter. `MemberVehicle`, `HostReview` and `ConductDisposition` carry only `id` and `created_at`; they have no `updated_at` field and no `version` field at all, and a client must not expect to find either.

Recomputation counts as mutation. Whenever a rule in this document recomputes a derived field on a resource — capacity, posture, a rating average, a standing score, a guest-pass pool — that write refreshes the resource's `updated_at` and increments its `version`. This is what makes the derived fields safe to read as part of a concurrency check.

Time itself is under the platform's control. The server owns a logical clock that starts at exactly `2026-09-01T00:00:00Z` on startup and never falls back to real wall-clock time; before any client interaction the clock reads precisely that instant. A platform operator may move the clock forward or backward with an administrative capability that accepts a `to_iso8601` instant, reports the resulting `current_utc`, and returns the `activated_window_ids` and `deactivated_window_ids` affected by the move. Moving the clock forward past a window's `start_date` activates that window; rewinding it to before `start_date` returns the window to `SCHEDULED`. Every temporal rule in §3 — the lead-time guard, the departed-window guard, the late-cancellation bands, window activation and expiry — is evaluated against this clock and never against the host's real time.

### 2.6. The Review Exchange and its Two Rating Aggregates

Reviews are a symmetric exchange rather than a one-way feed. Each review names which side wrote it through its `author_kind`, which is either `HOST` or `MEMBER`. A host-author review is written by host staff and is about a member; a member-author review is written by a member and is about a host. Any review may answer another through `author_review_id`, which points at the review being answered and is left absent for an original review — the link is self-referential and never points at the review itself. A review answering another is a counter-review, and the reviewed review's `counter_review_count` — the number of reviews pointing at it through `author_review_id` — rises by one when such a review is posted in the same exchange.

A review also carries a private channel. `private_report` is free text visible only to platform staff, and a non-empty private report on a host-author review raises a conduct incident of severity `MAJOR` with origin `REVIEW_REPORT` against the member being reviewed. The generic `narrative` field, by contrast, is the description of what a host reported on an incident filed directly.

Two averages are maintained from published reviews, and they are computed over different slices of the same table. `host_rating_average` averages the `rating` of the host's host-author reviews that are in `PUBLISHED` status — withdrawn reviews are excluded from numerator and denominator alike — and is rounded half up to two decimal places over that set. `member_rating_average` averages the `rating` of the member-author reviews written by a given member that are in `PUBLISHED` status, rounded the same way. Both properties are zero when their set is empty; a host whose only review was withdrawn therefore reports 0.00 rather than a null or a division fault. Posting a review recomputes the relevant average, and withdrawing a published review recomputes it again in the other direction, so the aggregate always reflects the currently published set.

Withdrawal is the only way a review leaves circulation, and `PUBLISHED` is the state in which every review begins. A review may be withdrawn by either author or by platform staff, provided it is currently `PUBLISHED`; an attempt to withdraw a review already in `WITHDRAWN` status is rejected with `ERR_REVIEW_ALREADY_WITHDRAWN` (HTTP 409).

### 2.7. The Conduct Ledger: Standing Score, Strikes and Removal

Two members-facing consequences flow from conduct incidents, and they measure different things on purpose. `standing_score` is a penalty ledger: it starts from a baseline of 100 points and each non-withdrawn incident subtracts a penalty determined by its severity — 5 points for a `MINOR` incident, 15 for a `MAJOR` one, and 40 for a `SEVERE` one — with the total floored at 0 so the score never goes negative. Every incident that has not been withdrawn counts toward this sum, including incidents still sitting in `OPEN` status and incidents the review board has since `DISMISSED`. A dismissed incident therefore still costs its penalty, whereas a `WITHDRAWN` incident contributes no penalty at all and restores the points it had removed.

`strike_count` measures something narrower: it counts the member's non-withdrawn incidents whose severity is `MAJOR` or `SEVERE`, and it ignores `MINOR` incidents completely. A strike is never consumed by a response, by an upheld disposition or by the passage of time. That asymmetry is deliberate and consequential — a member with five `MINOR` incidents against them can sit at a standing score of 75 while `strike_count` remains 0 and never approaches removal, while a member with three `MAJOR` incidents is removed on the third regardless of how few points those incidents cost them.

Removal is terminal. `removal_status` is either `NONE` or `REMOVED`, it begins as `NONE`, and there is no reinstatement path back from `REMOVED`. The transition is automatic rather than operator-driven: as soon as a recomputation of the conduct ledger leaves `strike_count` at 3 or above, the member's `removal_status` flips to `REMOVED` and their subscription is set to `CANCELLED` in the same pass. Because the automatic edge is evaluated whenever the ledger is recomputed, it can be reached from an incident disposition, from an automatically filed incident, or as a downstream consequence of another member's conduct cascade.

An incident itself has a small status machine. It begins `OPEN`; a review board may `UPHOLD` or `DISMISS` it, and it may also end `WITHDRAWN` when the report that produced it is retracted. Upholding an incident grants the affected member a dues waiver expressed in whole days through `waived_days_remaining`: 3 days when the incident's severity is `MINOR` or `MAJOR`, and 7 days when it is `SEVERE`. A dismissed incident grants none, and a withdrawn one resets the waiver to 0. An incident also records where it came from through `origin`, which is `MEMBER_REPORT`, `STAFF_FILING` or `REVIEW_REPORT`; incidents raised by the platform's own machinery use `STAFF_FILING`, and incidents raised from a private review report use `REVIEW_REPORT`.

### 2.8. Money, Rounding and the Platform's Ancillary Ceiling

All monetary amounts in this API are integer cents. There are no floating-point dollar values anywhere in the contract, and no monetary field is ever serialized as a string. Where a calculation in this document involves a percentage, the percentage component is rounded half up to zero decimal places — that is, to a whole cent — and any flat component is added only after that rounding has been applied. This ordering is contractual, not incidental: rounding a percentage and then adding a flat fee gives a different answer from adding first, and the tests are written against the former.

Two separate ceilings bound what a member can be charged. The electric component of a stay's ancillary charge is capped per night, so no single night of electric service can exceed 1200 cents regardless of the pedestal requested. The stay's ancillary total is then capped at 25000 cents after the tier discount has been applied, and floored at zero so the charge can never be negative. Both caps belong to the `stay_ancillary_charge` rule described in §3.

Host-side credits move in the other direction and have their own arithmetic discipline. The support-the-host credit accrues at a flat five percent of a verified receipt's value, converted to a whole number of cents by rounding half up, and each individual receipt's credit is capped at 1500 cents. The cap and the rounding both apply per receipt, before any summation: a host's `patronization_credit_cents` is the total of the per-receipt credits of every record in `VERIFIED` status, not a percentage of their combined value. Two verified receipts of 10050 and 33333 cents therefore contribute 503 and 1500 cents respectively for a total of 2003, and three receipts of 40000 cents contribute 4500 rather than 6000. Records still in `PENDING` status or moved to `REJECTED` contribute nothing and are excluded from the recomputation entirely.

One fiscal guard sits outside the charge arithmetic. A member with unsettled membership dues or an unpaid cancellation fee may not open a new stay request at all; the attempt is refused with `ERR_BALANCE_DUE` (HTTP 402).

### 2.9. Optimistic Concurrency Control

Three write operations in this system are protected against acting on a stale view, and only those three carry a version precondition. The protection is a match test, not a locking mechanism, and it never depends on two requests overlapping in time: the client states the version it last read, and the server rejects the write if that version is no longer current.

Confirming or declining a stay request is the first. A request that decides a stay must carry `expected_host_version`, the host's `version` as the caller last observed it — the host, not the stay, because the operator's view of `free_sites` and `posture` is what goes stale as availability windows open and other confirmations consume sites. If the host's current `version` has advanced beyond that value, the decision is rejected with `ERR_STALE_HOST_VERSION` (HTTP 412) and no state change occurs. The field is a required member of the request body for that operation, not an optional one.

Amending a live availability window is the second. Any amendment of a window that is in `ACTIVE` status must carry `expected_window_version`, the window's `version` as the caller last observed it, because the amendment rewrites the capacity basis that reservations are currently being measured against. A mismatch is a version precondition failure and the amendment is refused without any change to the window or the host.

Recording a patronization purchase is the third. A request that files a patronization record must carry `expected_request_version`, the `version` of the stay the purchase is attached to as the caller last observed it. If that stay's `version` no longer matches, the record is rejected with `ERR_STALE_REQUEST_VERSION` (HTTP 412), because the caller's view of which stay is current is no longer reliable.

No other endpoint in this API accepts a version field. A client that sends one of the three declared fields to an operation that does not declare it has its request treated as malformed, and a client that omits the declared field fails the same way. Requests that do not match this pattern — list operations, reads, and every state change not named above — proceed without any version check.

### 2.10. Nested Retrieval and the Order in Which Checks Are Applied

Resources in this API are addressed in a hierarchy, and identifiers nested inside a path are resolved from left to right. When a request targets an inner resource inside an outer one — an availability window inside a host, a parking site inside a host, the dispositions recorded against an incident — the outer identifier is resolved and validated before the inner one is even looked at. If both identifiers are unresolvable, the error reported is the one for the outer resource, not the inner; the caller learns about the first broken link in the chain and nothing further is examined. Every unresolvable path or body identifier produces `ERR_RESOURCE_NOT_FOUND` (HTTP 404).

Validation runs in a fixed priority order across the whole API, and the order determines which error a caller sees when more than one problem exists. Authentication comes first: a caller with a missing or unrecognized role is told `ERR_UNAUTHENTICATED` (HTTP 401) before anything about their payload is examined. Role authorization is evaluated second, yielding `ERR_UNAUTHORIZED` (HTTP 403), including the case where a member acts on a resource owned by a different member. Existence is third, yielding `ERR_RESOURCE_NOT_FOUND` (HTTP 404) under the left-to-right rule above. Payload well-formedness is fourth: every required input must be present, every enumerated value must fall inside its declared set, and every numeric range must hold, or the request fails with `ERR_INVALID_REQUEST` (HTTP 400).

Business safety is evaluated next. Whether a host is accepting stays at all — its `onboarding_status` must be `APPROVED` and its `posture` must not be `SUSPENDED` — is checked before the details of the stay are inspected, and a failure yields `ERR_HOST_NOT_ACCEPTING_STAYS` (HTTP 409). The ordinance profile of a host is evaluated on the platform's onboarding and host-update decisions and fails with `ERR_ORDINANCE_CONSTRAINT` (HTTP 422). State suitability is checked next, yielding `ERR_INVALID_STATE` (HTTP 409) whenever a target resource is not in a state that permits the requested operation.

Temporal and capacity business rules come after the state checks, and they run in a defined sequence so that overlapping guards report deterministically. The lead-time guard is evaluated before the vehicle and site rules and yields `ERR_REQUEST_LEAD_TIME` (HTTP 422) when a stay request is filed inside the guard window without the same-day exemption. The departed-window guard on counter-requests is evaluated before the request is reopened and yields `ERR_STAY_WINDOW_PASSED` (HTTP 422). Vehicle occupancy conflicts come next, producing `ERR_VEHICLE_OCCUPANCY_OVERLAP` (HTTP 409). Blocked-approach conflicts on the assigned site follow, producing `ERR_SITE_APPROACH_BLOCKED` (HTTP 409). Host capacity is evaluated after those, producing `ERR_HOST_CAPACITY_FULL` (HTTP 409).

The remaining business constraints follow in the order catalogued in §5: site-label uniqueness (`ERR_DUPLICATE_SITE_LABEL`, HTTP 409), member email uniqueness (`ERR_MEMBER_EMAIL_DUPLICATE`, HTTP 409), vehicle-fit and pedestal-compatibility checks at confirmation (`ERR_VEHICLE_LENGTH_EXCEEDS_SITE` and `ERR_SITE_ELECTRIC_INCOMPATIBLE`, both HTTP 422), the self-contained vehicle rule (`ERR_VEHICLE_NOT_SELF_CONTAINED`, HTTP 422), member eligibility (`ERR_MEMBER_NOT_ELIGIBLE`, HTTP 403), reviewer eligibility (`ERR_REVIEW_NOT_ELIGIBLE`, HTTP 403), disposition display-name segmentation (`ERR_DISPOSITION_NAME_COLLISION`, HTTP 409), window integrity (`ERR_WINDOW_CAPACITY_BELOW_RESERVED` and `ERR_WINDOW_EVICTS_CONFIRMED_STAY`, both HTTP 422), the fiscal block (`ERR_BALANCE_DUE`, HTTP 402), and finally the version preconditions (`ERR_STALE_HOST_VERSION`, `ERR_STALE_REQUEST_VERSION` and the window's `expected_window_version` check, the first two both HTTP 412). Where a single operation is guarded by several of these, the earlier check in this ordering is the one whose error the caller receives.

### 2.11. Local Ordinance and Zoning Profiles

Commercial overnight parking is regulated locally, so a host's permission to operate depends on both where it is and what it is. The platform encodes this as a profile keyed on the ordered pair of the host's `state_code` and its `category`, and exactly one profile entry can match a given host. Six profiles exist:

| State | Host category | Nightly member site cap | Self-containment forced |
| ----- | ------------- | ----------------------- | ----------------------- |
| `OR`  | `WINERY`      | 2                       | yes                     |
| `OR`  | `FARM`        | 6                       | yes                     |
| `CA`  | `WINERY`      | 4                       | yes                     |
| `CA`  | `BREWERY`     | 3                       | no                      |
| `TX`  | `FARM`        | 8                       | no                      |
| `TX`  | `ATTRACTION`  | 10                      | no                      |

A host whose `state_code` and `category` pair appears in no profile is uncapped and is not forced to require self-contained rigs — the same category is treated differently in a different state, which is the point of keying on the pair rather than on either value alone.

Two obligations arise when a profile does match. The host's base capacity, measured as the count of its active parking sites, may not exceed the profile's nightly member site cap; the cap is inclusive, so a capacity exactly equal to the cap passes and one site beyond it fails. And where the profile forces self-containment, the host may not declare `self_contained_required` as false. Either violation on a platform onboarding or host-update decision is rejected with `ERR_ORDINANCE_CONSTRAINT` (HTTP 422). The cap is assessed against the host's physical site count and never against an availability window's `capacity_override`, so an event window can raise the member ceiling above the physical count without relaxing the ordinance limit.

### 2.12. The Support-the-Host Receipt Programme

The platform's economic bargain with hosts is that members will spend money at the premises. A member records a purchase with a patronization record naming the host, the member, the stay during which the purchase was made, the `receipt_cents` value in cents — which must be positive — and a `purchase_kind` drawn from `TASTING`, `MERCHANDISE`, `TICKET` or `MEAL`. Every record begins in `PENDING` status and is issued a server-minted `verification_code` that the host scans to settle it; the record's `host_credit_cents` stays at zero until it is verified. Verification requires the host to supply the `verification_code`, and a code that does not match the minted one is rejected with `ERR_PATRONIZATION_CODE_INVALID` (HTTP 422). A host may also reject a pending receipt outright, leaving its `host_credit_cents` at zero permanently. The credit arithmetic itself is described in §2.8.

### 2.13. Availability Windows and the Reservation Ceiling

Availability is expressed as dated windows rather than as a permanently fixed capacity, so an availability window is the object a host uses to say "in this season" or "for this festival weekend". A window carries a `kind` of either `SEASONAL` or `EVENT`, a human-readable `label`, an inclusive `start_date` and an exclusive `end_date` that must fall strictly after the start date, a `capacity_override` that replaces the host's base capacity for reservation arithmetic while the window is live, and a `reserved_sites` count that is withheld from member use — typically for festival vendors or event staff. From these the platform derives `member_capacity_ceiling`, the live capacity basis while the window is `ACTIVE`: it is the window's `capacity_override` minus its `reserved_sites`, floored at zero.

A window's `window_status` is `SCHEDULED` when it is declared ahead of its dates, becomes `ACTIVE` when the logical clock reaches its `start_date`, and is `CANCELLED` when it is withdrawn or superseded. Only one window of a host can be `ACTIVE` at a time; when the clock advances and a new window takes over, any other active window of the same host whose `end_date` has already passed is retired to `CANCELLED` in the same pass. The integrity of a window is checked on declaration and on amendment: `capacity_override` must be at least `reserved_sites`, and `end_date` must be strictly after `start_date`, with a violation reported as `ERR_WINDOW_CAPACITY_BELOW_RESERVED` (HTTP 422). An amendment is further restricted from destroying a commitment already made: if the amended ceiling would fall below the number of `CONFIRMED` stays whose `occupancy_start` falls inside the window's date range, the amendment is refused with `ERR_WINDOW_EVICTS_CONFIRMED_STAY` (HTTP 422). Amendments are accepted only while the window is `ACTIVE`, and an amendment attempted against any other status is rejected with `ERR_WINDOW_NOT_ACTIVE` (HTTP 409). An amendment must also carry the window's `expected_window_version` precondition described in §2.9, because it rewrites the capacity basis against which live reservations are measured.

### 2.14. The Recalculation Map

Because so much of this system is derived rather than declared, the trigger set for each derived quantity is part of the contract rather than an implementation detail. The following table records, for each kind of change, everything that must be recalculated in its wake. Every recalculation listed refreshes the affected resource's `updated_at` and increments its `version`, so a stale derived figure is never observable alongside a fresh one.

| Change | What is recomputed |
| ------ | ------------------ |
| A host is declared | `onboarding_status` set to `PENDING_REVIEW`; `posture` `UNAVAILABLE`; `effective_capacity`, `committed_sites`, `free_sites` and `patronization_credit_cents` all 0; `latest_checkout_at` null; `total_amenity_count` 0 |
| A host ruling is made, or a host declaration is updated | `effective_capacity`, `committed_sites`, `free_sites`, `posture`; on a rejection or suspension the four-hop stay and conduct cascade described in §3.1 |
| A parking site is declared, updated or deactivated | `effective_capacity`, `free_sites`, `posture` on the base basis, plus `electric_site_count` |
| An availability window is declared, activated, amended, cancelled, or returned to `SCHEDULED` | `member_capacity_ceiling` on the window, then `effective_capacity`, `committed_sites`, `free_sites`, `posture` and `seasonal_windows_reserved_sites` on the host |
| The logical clock moves | window statuses first, then `effective_capacity`, `free_sites` and `posture` for every host whose live basis changed |
| A stay is filed, decided, cancelled, countered, checked in, checked out or no-showed | `committed_sites`, `free_sites` and `posture` on the host, plus whichever of the member's `standing_score`, `strike_count`, `total_stays_completed` and `guest_passes_remaining` the specific transition names |
| A stay reaches checkout | `Member.total_stays_completed` rises by one, and `guest_passes_remaining` is recalculated when the member has no stay still in `REQUESTED`, `CONFIRMED` or `CHECKED_IN` status |
| An incident is filed or ruled on | the member's `standing_score` and `strike_count`, and `removal_status` plus `subscription_status` when strikes reach 3; a removal declines every countable stay past the first round |
| A review is posted or withdrawn | `host_rating_average` and `member_rating_average` for the relevant side, plus `counter_review_count` on the answered review when the new review is a counter-review |
| A patronization record is verified | that record's `host_credit_cents`, then the host's `patronization_credit_cents` across all of its verified records |
| A member is registered, or a subscription action is taken | `guest_passes_remaining`, `standing_score` and `strike_count`; the first vehicle a member declares also sets `is_primary` true |

## 3. Business Logic & Workflows

### 3.1. Opening a Host for Business: Onboarding and Ordinance Review

A host business enters the platform in a pending state. A prospective host — or platform staff acting on its behalf — declares the venue with its `legal_name`, its `category` drawn from `WINERY`, `FARM`, `BREWERY` or `ATTRACTION`, its `address_line1`, and the two-letter `state_code` that will select its parking ordinance profile. Three declarations may be supplied at the same time and each has a fixed default when it is left out: `arrival_window_start_hour` defaults to 14, the local hour on the arrival day at which a member may occupy a site; `arrival_window_end_hour` defaults to 11, the local hour by which a rig must be gone on the final morning; and `self_contained_required` defaults to true, meaning members must arrive in rigs that carry their own water, waste and power. A freshly declared host sits at `onboarding_status` `PENDING_REVIEW` with `posture` `UNAVAILABLE`, `effective_capacity` 0, `committed_sites` 0, `free_sites` 0, `patronization_credit_cents` 0 and `latest_checkout_at` null. It cannot accept anybody until the platform approves it and it has real sites to offer.

Sites come next, because capacity is counted from them. A host staff member declares each physical `HostParkingSite` with a `site_label` that is unique within the host, a `site_class` of either `PULL_THROUGH` or `BACK_IN`, a `max_vehicle_length_feet` for the longest rig the pad can hold, an optional `has_electric` flag that defaults to false, an `electric_service_code` of `NONE`, `ELECTRIC_30A` or `ELECTRIC_50A` that defaults to `NONE`, and a `blocks_sites` list. That last field is a pipe-delimited list of other sites on the same host whose approach a stay circulates through this one and therefore obstructs; no site may name itself. A newly declared site is active unless the declaration says otherwise, and declaring, re-labelling or deactivating a site immediately changes the host's capacity arithmetic. A site label that already exists on the host is refused with `ERR_DUPLICATE_SITE_LABEL` (HTTP 409).

The approval decision is the platform's, and it is where the ordinance profile bites. Approving a host requires it to still be `PENDING_REVIEW`, requires its derived capacity to be at least 1 — which is to say it must have declared at least one active parking site — and requires its electric amenity surface to be non-empty, measured by `electric_site_count` being at least 1. Independently of those, the ordinance profile described in §2.11 must hold: a cap violation or a missing forced self-containment requirement on the decision is refused with `ERR_ORDINANCE_CONSTRAINT` (HTTP 422). When the decision is an approval, the host's `onboarding_status` becomes `APPROVED`, its `posture` and `committed_sites` are recomputed, and the availability windows are brought into line with the clock: if one of the host's windows is `SEASONAL`, `ACTIVE` and overlaps the current instant, that window stays `ACTIVE`, and if no window is currently active every `SCHEDULED` window whose `capacity_override` is zero or less is `CANCELLED`.

A host may also be ruled out rather than approved. A rejection sets `onboarding_status` to `REJECTED`, which is terminal — there is no path back out of it — and it is where the platform's largest cascade begins. Every stay on the host still in `REQUESTED` status is moved to `DECLINED` in the first hop. In the second hop each of those stranded requests files a `MAJOR` conduct incident against the member who made it, with an origin of `REVIEW_REPORT`, on the reasoning that the platform failed the member and the host did not. That incident then drives the conduct ledger the third hop: the members' `standing_score` and `strike_count` are recomputed, and any member whose `strike_count` reaches 3 or above flips to `REMOVED` and has their subscription set to `CANCELLED`. Those removals release work in the fourth and final hop, where every countable stay of a removed member at a `request_depth` beyond 1 is moved to `DECLINED`. The host's own `posture`, `committed_sites` and `free_sites` are recomputed at the end of the pass.

Suspension is the third ruling the platform can make, and it applies to an already-approved host. It requires the host to be `APPROVED` and its `posture` to be one of `OPEN`, `LIMITED` or `UNAVAILABLE` — a host already `SUSPENDED` is not suspended twice. On a suspension the host's `onboarding_status` becomes `SUSPENDED` and its `posture` collapses to `SUSPENDED` regardless of how many sites are free, with `effective_capacity` forced to 0. The same four-hop cascade runs as for a rejection, except that the stays it strands are those in `REQUESTED` or `CONFIRMED` status and the `MAJOR` incidents it files against their members carry an origin of `STAFF_FILING` rather than `REVIEW_REPORT`; each stranded stay's member has not only their standing ledger but also `total_stays_completed` and `guest_passes_remaining` recomputed. A suspended host is not necessarily finished: a reinstatement returns it to `APPROVED`, provided it still has at least one active parking site, and the capacity arithmetic is recomputed once more. A rejection applied to an already-approved or already-suspended host follows the same cascade shape, and a rejection from `SUSPENDED` simply sets the terminal `REJECTED` status. Every one of these rulings increments the host's `version` by one, and each carries an `action` field naming the ruling, an optional `reason` recording why it was made, and `expected_host_version` carrying the host's version as the ruling operator last observed it.

Host declarations remain editable after approval. A `legal_name`, `category`, `address_line1`, `state_code` or `self_contained_required` change re-evaluates the ordinance profile and the posture, and increments the host's `version`. Because the ordinance profile is re-evaluated on this path, a host that moves a capped category or state across a profile boundary invalidates itself with `ERR_ORDINANCE_CONSTRAINT` on the update itself. The update carries `expected_host_version` alongside whichever of the five declarations are being changed.

### 3.2. Seasons, Event Weekends and the Live Capacity Basis

Availability windows are how a working business reconciles hospitality with its own operating reality. A harvest closure, a festival weekend or a quiet winter all change what a host can offer without changing what it owns, so a window declares a `kind` of `SEASONAL` or `EVENT`, a human-readable `label`, its inclusive `start_date` and exclusive `end_date`, a `capacity_override` that replaces the host's physical capacity while it runs, and a `reserved_sites` count withheld for vendors or event staff. A newly declared window is `ACTIVE` straight away if the logical clock already falls at or after its `start_date` and before its `end_date` and the host's `onboarding_status` is `APPROVED`; otherwise it is parked at `SCHEDULED` until the clock catches up. Declaring a window recomputes the host's capacity arithmetic and increments the host's `version`.

The clock is what moves these windows, not a scheduler the host controls. Advancing the logical clock to an instant at or after a `SCHEDULED` window's `start_date` and before its `end_date` activates that window automatically, provided the host is `APPROVED`, and the same pass retires any other `ACTIVE` window of that host whose `end_date` has already passed. Rewinding the clock to before a window's `start_date` returns an `ACTIVE` window to `SCHEDULED`, from which it can later activate again — the window machine is cyclic rather than one-way. In every one of these moves the host's `effective_capacity`, `committed_sites`, `free_sites` and `posture` are recomputed, because the basis under which availability is measured has changed.

Amending a live window is the host's day-to-day lever for it, and the amendment happens in place: `capacity_override`, `reserved_sites`, `start_date` and `end_date` may each be revised, the window's `member_capacity_ceiling` is recomputed, the host's capacity arithmetic follows, and both the window's `version` and the host's `version` increment. An amendment is admitted only while the window is `ACTIVE` — against any other status it fails with `ERR_WINDOW_NOT_ACTIVE` (HTTP 409), because a scheduled window is edited by cancelling it and declaring a fresh one. The amendment must leave `capacity_override` at or above `reserved_sites` and `reserved_sites` at or above zero, failing with `ERR_WINDOW_CAPACITY_BELOW_RESERVED` (HTTP 422) otherwise. Crucially, an amendment may not evict somebody who has already been promised a site: if the amended ceiling would fall below the number of `CONFIRMED` stays whose `occupancy_start` falls inside the window's date range, the amendment is refused with `ERR_WINDOW_EVICTS_CONFIRMED_STAY` (HTTP 422). A window that is no longer wanted — whether still `SCHEDULED` or already `ACTIVE` — is `CANCELLED`, and if it was active the host's capacity arithmetic is recomputed once more.

Because the live basis replaces the physical count rather than modifying it, a host's numbers can move in counter-intuitive directions. A 4-site farm that declares a festival window with `capacity_override` 30 and `reserved_sites` 24 publishes a member ceiling of 6 — more than it physically owns — while the same host declaring a harvest window with `capacity_override` 5 and `reserved_sites` 3 publishes only 2. The ordinance cap of §2.11 is assessed against the physical site count in both cases and is unaffected by either override.

### 3.3. Membership, Rigs and the Guest-Pass Pool

A person joins by registering with a unique `email`, a `full_name`, a `plan_tier` of `CLASSIC`, `PLUS` or `PREMIER`, and a two-letter `home_state_code` recording their registered residence — the state code that later selects their vehicle inspection requirement. Registration may be performed without authentication and is the only thing an unauthenticated caller can do. An email already on file is refused with `ERR_MEMBER_EMAIL_DUPLICATE` (HTTP 409). A newly registered member opens at `subscription_status` `PENDING` with `standing_score` 100, `strike_count` 0, `removal_status` `NONE`, `total_stays_completed` 0, and a `guest_passes_remaining` pool set from their plan's yearly allotment.

That allotment is a function of the plan: a `CLASSIC` member receives no overnight guest passes at all, a `PLUS` member receives 2, and a `PREMIER` member receives 4. The pool is recomputed rather than decremented, and it is recomputed only when the member is idle. On a stay reaching `CHECKED_OUT`, and on any cascade that recomputes member state, the platform first asks whether the member has any stay in `REQUESTED`, `CONFIRMED` or `CHECKED_IN` status. If they do, the pool is frozen at its current value — even across a calendar-year rollover — because guests may still be travelling with an in-flight stay. If they do not, the pool is recalculated from scratch as the plan allotment minus the member's guest usage so far this calendar year, floored at zero; the usage is the sum over the member's `CHECKED_OUT` stays in the current calendar year of the number of people beyond the driver, where a solo traveller contributes nothing. Because the pool is recalculated rather than spent, upgrading plans can raise it back up on the next idle recomputation.

Subscription status moves on the subscription machine. A `PENDING` subscription becomes `ACTIVE` when a platform operator activates it, and an `ACTIVE` one becomes `LAPSED` when the platform lapses it — but only if the member has no stay in `REQUESTED`, `CONFIRMED` or `CHECKED_IN` status, since a lapsing member must not be mid-stay. A `LAPSED` subscription is restored to `ACTIVE` by renewal. A member may end their own subscription by cancelling it, which sets `subscription_status` to `CANCELLED` and requires the acting member to own the resource; cancellation is available while the subscription is `ACTIVE` or `LAPSED`. A cancelled subscription is not strictly terminal: the platform may lapse it back to `LAPSED` for a re-engagement campaign, after which renewal can bring it back to `ACTIVE`. Platform operators may also pin the `guest_passes_remaining` figure to a supplied value outright, and any subscription action recomputes the member's `standing_score` and `strike_count`.

Member eligibility for transactional work is checked separately from subscription bookkeeping: a member must have `subscription_status` `ACTIVE` and must not have `removal_status` `REMOVED`, and a member failing either test is refused with `ERR_MEMBER_NOT_ELIGIBLE` (HTTP 403) when they try to open or re-open a stay.

Rigs are declared per member. A member records a vehicle with its `vehicle_class` — one of `CLASS_A`, `CLASS_B`, `CLASS_C`, `FIFTH_WHEEL`, `TRAVEL_TRAILER` or `CONVERSION_VAN` — its overall `length_feet`, whether it is `self_contained` in the sense of carrying onboard water, waste and power, an `inspection_state_code` naming the authority that issued its annual self-containment certificate, and, conditionally, an `inspection_expires_on` instant. That expiry is required in the declaration body only when the inspecting authority's `inspection_state_code` differs from the member's `home_state_code`, and must be left absent otherwise; an inspection issued in the member's home state does not need an expiry to be recorded. The first vehicle a member declares becomes their designated primary rig and every subsequent one does not — exactly one rig per member carries `is_primary` true. Vehicle attributes and inspection details remain editable afterwards. Note that the self-containment our hosts care about is the flag on the rig, while the inspection certificate is the evidence that backs it.

### 3.4. Filing a Stay Request and the Host's Decision

A member asks for a night on a host's ground by filing a stay request that carries the `host_id` of the business they are approaching, their own `member_id` — which must match the identity in `X-User-ID` when a member is the actor — and the `vehicle_id` of the rig that will occupy the site. They supply an `arrival_date` at midnight UTC marking the first night, and a `nights` count for the consecutive nights requested. Optional inputs shape the stay: `party_size` records the total people in the rig including the driver and defaults to 1, and `electric_request_code` states whether shore power is wanted, drawn from `NONE`, `ELECTRIC_30A` or `ELECTRIC_50A` and defaulting to `NONE`. Two further fields exist for the platform's own state to be expressed at creation: `request_depth` records how many times the request has been made or answered and defaults to 0, and `same_day_hold` marks the request as exempt from the lead-time guard when the host has enabled same-day availability and defaults to false.

Three values are derived from what the member supplied rather than stored from the payload. The `departure_date` is the arrival date advanced by the requested number of nights, and it is an exclusive checkout boundary — nobody occupies the site on that morning. The `occupancy_start` is the arrival date plus the host's `arrival_window_start_hour`, the hour-level instant at which the rig may roll onto the site. The `occupancy_end` is the departure date plus the host's `arrival_window_end_hour`, the hour-level instant by which the rig must be gone. Subtracting the host's two declared window hours means the same date range produces different occupancy instants at different hosts, and the later of the two hosts' hours is what pushes the physical occupancy out.

One collision rule deliberately uses the simpler date arithmetic instead. Two stays on the same rig may not have occupancy intervals that touch or overlap, and this is judged over the half-open date interval running from the arrival date at midnight UTC up to, but not including, the departure date at midnight UTC. Because the upper bound is excluded and the lower bound is included, a same-day turnaround — one stay departing on the morning another arrives — counts as touching and is therefore a conflict, refused with `ERR_VEHICLE_OCCUPANCY_OVERLAP` (HTTP 409). The rule is evaluated both when a request is filed and when a stored request is decided.

A filed request opens at `request_status` `REQUESTED` with `request_origin` `MEMBER_INITIATED` and an `ancillary_charge_cents` of 0, since charges are computed at confirmation and not before. The other origin value, `HOST_INITIATED`, distinguishes a stay that a host raised on a member's behalf from one the member filed themselves; a member-filed request always carries `MEMBER_INITIATED`. It counts toward the host's occupancy immediately when its `request_depth` is 1 or under, which is what allows a first-round request to hold a site before the host has answered, and the host's `committed_sites`, `free_sites` and `posture` are recomputed as soon as it lands. The derived `count_toward_capacity` flag on the request is true from the moment it lands in that first round.

Several guards are evaluated when a request is filed, in the priority order set out in §2.10. The host must be accepting stays at all: a host whose `onboarding_status` is not `APPROVED`, or whose `posture` is `SUSPENDED`, refuses the request with `ERR_HOST_NOT_ACCEPTING_STAYS` (HTTP 409). The lead-time guard comes next. The logical clock must be at least 48 hours before the request's `occupancy_start`, unless the host has enabled same-day availability and the request carries `same_day_hold` as true, in which case the guard is waived entirely; a request filed inside the guard without that exemption is refused with `ERR_REQUEST_LEAD_TIME` (HTTP 422), and the same guard is re-applied when a decision is later recorded on the request. Host capacity follows: the host's posture must not be `UNAVAILABLE`, and its available room, measured as `effective_capacity` minus its `committed_sites`, must be at least 1; the request being filed has not yet been stored at the moment this test runs, so it contributes nothing to `committed_sites` and no reservation of its own is excluded. A request that cannot be admitted is refused with `ERR_HOST_CAPACITY_FULL` (HTTP 409). Finally, a host that requires self-contained rigs refuses a request whose rig does not carry the self-contained flag or does not have an inspection record on file, with `ERR_VEHICLE_NOT_SELF_CONTAINED` (HTTP 422).

The host's answer to a request is a decision, and it is the host staff — or platform staff — who record it. The decision carries an `action`-style `decision` value of CONFIRM or DECLINE together with `expected_host_version`, the host's version precondition described in §2.9, and may optionally name the site to assign through `site_id`.

Confirming a stay is the platform's most heavily guarded transition, and its checks run in order. The request must still be `REQUESTED`; the host must still be `APPROVED` and its posture must be `OPEN` or `LIMITED`, with a suspended host refused as `ERR_HOST_NOT_ACCEPTING_STAYS` (HTTP 409) and a host with no capacity basis refused as `ERR_HOST_CAPACITY_FULL` (HTTP 409). The lead-time guard is re-evaluated. The vehicle must then fit the site being assigned: the assigned site's `max_vehicle_length_feet` must be at least the rig's `length_feet`, or the confirmation is refused with `ERR_VEHICLE_LENGTH_EXCEEDS_SITE` (HTTP 422). Electric compatibility follows: when the request asks for shore power at all, the assigned site must have an electric pedestal, and that pedestal's `electric_service_code` must be at least as capable as the requested code under the ordering `NONE`, then `ELECTRIC_30A`, then `ELECTRIC_50A`; a request for 50-ampere service may therefore be satisfied only by a 50-ampere pedestal, while a 30-ampere request is satisfied by either. An incompatible match is refused with `ERR_SITE_ELECTRIC_INCOMPATIBLE` (HTTP 422). The occupied-approach rule is checked next: a site may not be assigned while any site whose `blocks_sites` list names it is occupied by a circulating stay over the new interval widened by a two-hour buffer on each side, and a violation is reported as `ERR_SITE_APPROACH_BLOCKED` (HTTP 409). A stay circulates when the site it is assigned to has the `PULL_THROUGH` class, which is what makes the blocked-approach rule meaningful — a back-in site does not send rigs past its neighbours. Capacity is confirmed last, under the own-reservation-excluded form of the admission test: because the stay being confirmed is already counted in the host's `committed_sites` at that moment, the room it is measured against is `effective_capacity` minus one fewer than `committed_sites`, so the request's own reservation is left out of the count and cannot block its own confirmation.

A confirmed stay moves to `request_status` `CONFIRMED`, records the assigned site in `confirmed_site_id`, computes its `ancillary_charge_cents`, and leaves the member's `total_stays_completed` untouched until check-out. The host's `committed_sites` and `free_sites` are recomputed, its posture follows from the derivation in §2.4, and the host's `version` increments. Declining a stay is simpler but not trivial: it requires the request to be `REQUESTED`, and it advances `request_depth` by exactly one on this response — so a first-round request lands at depth 1 (the value the member's later counter-request depends on) and a second-round request, already at depth 2, lands at depth 3 — and that is the mechanism that admits the member's later counter-request exactly once. On a decline the request moves to `DECLINED`, the host's occupancy is recomputed, and the member's `standing_score`, `strike_count`, `total_stays_completed` and `guest_passes_remaining` are all recomputed in the same pass.

#### The Ancillary Charge

Charges are computed once, at confirmation, and the amount is stored on the stay as `ancillary_charge_cents`. The computation runs in four ordered stages, and the ordering of the rounding inside it is contractual.

The first stage prices shore power per night from two inputs: the rig's `vehicle_class` and the requested pedestal. A request for `NONE` costs nothing per night. A request for `ELECTRIC_30A` costs 700 cents per night. A request for `ELECTRIC_50A` costs 1200 cents per night when the rig is a `CLASS_A` or a `FIFTH_WHEEL`, and 900 cents per night for every other vehicle class — a `CONVERSION_VAN` and a `CLASS_A` asking for the same 50-ampere pedestal therefore pay different nightly rates for the same service. That nightly figure is then bounded by a per-night ceiling of 1200 cents, so no single night of electric service can exceed that amount. The electric component of the charge is the nightly figure multiplied by the number of `nights` requested.

The second stage prices guests. The driver is never a guest, so the people beyond the driver are the `party_size` minus one, floored at zero. Of those, only the ones the member's pass pool does not already cover are billable: the billable count is the guests beyond the driver minus the member's current `guest_passes_remaining`, floored at zero. Each billable guest is charged 500 cents, so the guest component is 500 cents multiplied by the billable guest count.

The third stage applies the plan's discount to the stay's subtotal — the electric component plus the guest component. A `CLASSIC` member receives no discount, a `PLUS` member receives a 10 percent discount, and a `PREMIER` member receives a 20 percent discount. The discount amount is the subtotal multiplied by the plan's percentage and divided by 100, rounded half up to a whole cent. That discount is computed exactly once, on the whole subtotal: never per night and never per guest, since discounting each night separately and then adding would produce a different result on multi-night stays with a fractional discount.

The fourth stage clamps the result. The stored charge is the subtotal minus the discount, floored at zero and then capped at 25000 cents, so a large multi-night stay with several guests on a 50-ampere pedestal cannot exceed that hard cap and a stay whose discount is larger than its subtotal simply costs nothing. Site electric capability is validated before this computation runs and never inside it; the charge calculation never looks at the assigned site.

### 3.5. Occupancy, Departure, No-Shows and the Late-Cancellation Bands

A confirmed stay is a promise that a rig will occupy a pad, and the platform tracks the promise being kept. Arrival is recorded by host staff once the logical clock has reached the stay's `occupancy_start` and the stay is still `CONFIRMED`; the stay moves to `CHECKED_IN` and stamps `checked_in_at` with the current clock instant. Departure is recorded on the other side of the same rule: once the clock has reached the stay's `occupancy_end` and the stay is `CHECKED_IN`, host staff record the check-out, which moves the stay to `CHECKED_OUT`, stamps `checked_out_at`, and increments the member's `total_stays_completed` by one. The host's `committed_sites`, `free_sites` and `posture` are recomputed in the same pass, because a departure returns sites to the pool. The member's `guest_passes_remaining` pool is recalculated on departure only if the member has no other in-flight stay in `REQUESTED`, `CONFIRMED` or `CHECKED_IN` status; a member still travelling keeps the pool frozen exactly as it was.

Failing to arrive is a recorded event rather than an absence of one. After the stay's `occupancy_end` has passed, and while the stay is still `CONFIRMED`, host staff may record a no-show, which must be accompanied by a `narrative` describing what happened. The stay moves to `NO_SHOW`, `no_show_recorded_at` is stamped with the current instant, and the platform immediately files a conduct incident against the member with severity `MAJOR`, origin `STAFF_FILING` and status `OPEN`. From that incident the conduct ledger moves: the member's `standing_score` and `strike_count` are recomputed, a `strike_count` of 3 or above flips the member to `REMOVED` and cancels their subscription, and any member so removed has their live reservations past the first round released. The host's occupancy arithmetic is recomputed at the end.

Leaving early is the member's own lever, and the platform prices it by how late the decision is. A request still sitting at `REQUESTED` may be withdrawn by the member who owns it, moving to `CANCELLED` with no charge, no depth advance and no conduct consequence; only the host's `committed_sites` and `free_sites` are recomputed, since a first-round request was holding a site. A stay already at `CONFIRMED` may also be cancelled by its owning member, and that one carries consequences: the stay moves to `CANCELLED`, its `request_depth` advances by one, a fee is computed into `cancellation_fee_cents`, the host's occupancy is recomputed, and the member's `standing_score`, `strike_count`, `total_stays_completed` and `guest_passes_remaining` are all recomputed alongside.

The fee is banded by how much notice the member gave and how large the stay's ancillary charge was, and the bands are evaluated in order. The notice is measured as the number of whole days between the current logical clock and the stay's `occupancy_start`, counted from the clock forward to that instant, so a value below zero means the arrival window has already opened. When that count is at least 7 days, the fee is zero. When the notice is shorter but the stay's `ancillary_charge_cents` is at most 2000 cents, the fee is also zero — cancelling late costs nothing when the stay had almost no ancillaries to begin with. Otherwise, when `ancillary_charge_cents` is at most 5000 cents, the fee is 15 percent of that ancillary charge, rounded half up to a whole cent, plus a flat 500 cents. Otherwise the fee is 25 percent of the ancillary charge, rounded half up to a whole cent, plus a flat 1500 cents. The band is selected from the ancillary charge and the percentage is applied to that same value, with the flat component added only after the percentage has been rounded. The lower band is inclusive: an ancillary charge of exactly 5000 cents takes the middle band and bills 1250 cents, while 5001 cents takes the high band and bills 2750 cents. The fee is computed against the ancillary figure already stored on the stay and is never re-derived from the stay's inputs.

### 3.6. The Second Round: Counter-Requests and Re-Opened Negotiations

A host's decline does not have to be the end of the conversation, and the platform admits exactly one re-opening per stay. A member who owns a stay that sits at `DECLINED` may ask the host to look again, provided the stay's `request_depth` is exactly 1 — the depth a first decline of a first-round request itself set — and provided the logical clock has not passed the stay's `occupancy_end`; a counter-request filed after that boundary is refused with `ERR_STAY_WINDOW_PASSED` (HTTP 422). The same re-opening is available from two other resting states: a stay the member cancelled themselves while it was still at `REQUESTED` or `CONFIRMED`, and a stay recorded as a `NO_SHOW`. In both of those cases the guard is looser on depth — the stay's `request_depth` must be 1 or under — because the cancellation or no-show did not itself advance the depth. All three paths require the acting member to own the stay, and all three share the same departed-window guard.

A successful counter-request returns the stay to `REQUESTED` and sets its `request_depth` to 2, putting it back in front of the host as a second-round negotiation rather than a first-round hold. The member may revise the terms as part of it: `arrival_date`, `nights` and `party_size` are all accepted, so a declined request can come back smaller, shorter or on different dates. Beyond the status and depth, the pass recomputes the host's `committed_sites` and `free_sites` and recomputes the member's `standing_score`, `strike_count`, `total_stays_completed` and `guest_passes_remaining`. The refiled request is then decided by the host exactly as any other request at `REQUESTED` status is, subject to the same lead-time, capacity, vehicle-fit, pedestal, approach and self-containment rules of §3.4 — a second round buys another attempt, not an exemption.

### 3.7. Conduct Incidents, Dispositions and the Removal Edge

Conduct on the platform is recorded as incidents rather than as free-standing reputation. An incident names the `member_id` it is filed against, the `host_id` that reported it or was affected by it, a `severity` drawn from `MINOR`, `MAJOR` or `SEVERE`, and a `narrative` describing what the host reported. An `origin` may be supplied and otherwise takes the platform's default; incidents raised by the platform's own machinery carry `STAFF_FILING` and those raised from a private review report carry `REVIEW_REPORT`. A newly filed incident opens at status `OPEN` with `waived_days_remaining` 0, and the member's `standing_score` and `strike_count` are recomputed immediately, so filing an incident can by itself move a member to the removal edge.

The review board's ruling is a separate operation, performed by a member of the platform's review capability, and it is the only operation in this API that carries the segmentation rule described below. It accepts an `action` — UPHOLD, DISMISS or WITHDRAW — and the `decided_by_display_name` the deciding member supplies, together with an optional `requested_decision` of `UPHOLD` or `DISMISS` that records what the board was asked for. Upholding a `MINOR` or `MAJOR` incident grants the affected member 3 whole days of dues waiver through `waived_days_remaining`, and upholding a `SEVERE` incident grants 7; dismissing leaves the waiver at zero. Withdrawing an incident sets `waived_days_remaining` to 0 and, because a withdrawn incident is excluded from the ledger, restores any points and strikes the incident had cost. Every ruling is recorded as a `ConductDisposition` capturing the `incident_id`, the `member_id` the originating incident was filed against, the `requested_decision` that was asked for, the `decided_by_display_name`, the resulting `decision` of `UPHELD` or `DISMISSED`, and the `decided_at` instant on which the board ruled. Listings of these dispositions are available both per member and per incident.

A ruling is admitted only against an incident that is still `OPEN`; a disposition attempted on an incident that has already been upheld, dismissed or withdrawn is refused with `ERR_INCIDENT_NOT_OPEN` (HTTP 409). The second precondition is the display-name segmentation rule, and it exists so that a member cannot rule on an incident while wearing another member's name. The `decided_by_display_name` supplied in the body must be segmented from every other member's `full_name` on the platform — it may not coincide with any other member's display name — and a collision is refused with `ERR_DISPOSITION_NAME_COLLISION` (HTTP 409). The deciding member's own `full_name` is explicitly exempt from this comparison, so a member may rule using their own name. After a ruling is accepted, the member's `standing_score` and `strike_count` are recomputed from the non-withdrawn incident set, and a `strike_count` of 3 or above flips the member's `removal_status` to `REMOVED` through the automatic edge described in §2.7.

Incidents sourced from a review obey the review rather than the board. When an incident's `origin` is `REVIEW_REPORT` and the review that produced it has itself been withdrawn, an attempted upholding rules the incident `WITHDRAWN` instead of `UPHELD`, sets `waived_days_remaining` to 0, and recomputes the subject member's ledger so that the withdrawn incident contributes neither penalty nor strike. This is the platform's way of ensuring a retracted report cannot be used to punish anyone: retracting the review retracts everything that flowed out of it.

For test-driving purposes, platform staff have a bulk capability that seeds a conduct history for a member in a single operation. It takes a `severity`, a `resolve_as` and a `narrative`, files one incident, and — unless `resolve_as` is `OPEN` — immediately resolves it through the disposition machine, recomputing the member's ledger and applying the removal edge if the strikes have accumulated far enough. Its purpose is to let a test suite reach a conduct-heavy member state without walking a dozen individual operations. It answers `200 OK` rather than the `201 Created` that the generic stand-alone-creation rule of §4 would otherwise suggest, whichever `resolve_as` value is supplied.

### 3.8. The Review Exchange and Support-the-Host Receipts

Reviews are how both sides of a stay are held to account, and the platform keeps them symmetric. A host-author review is written by host staff about a member, and its payload names the `host_id` it belongs to and the `subject_member_id` of the member being reviewed. A member-author review is written by a member about a host, and its payload names the `subject_host_id`; a member-author review may also name `author_member_id` and `host_id` where the platform derives them from the stay instead. Any review may be posted as a counter-review by supplying `author_review_id` — the review being answered, which must exist and must not be the review being created — and a counter-review raises the answered review's `counter_review_count`. Because the link is self-referential, a review may answer another review but never itself.

Every review requires a `rating` between 1 and 5 inclusive and a `public_note`, and may carry `advance_notice_hours` recording the notice the author's stay actually had, which drives whether the review is tagged as having arrived on under 24 hours' notice. A host-author review may additionally carry `private_report` — free text visible only to platform staff — and a non-empty private report raises a conduct incident of severity `MAJOR` with origin `REVIEW_REPORT` against the member being reviewed. A host-author review's payload may also include an `expected_host_version` alongside those inputs. A review enters `PUBLISHED` status on creation, and both rating aggregates of §2.6 are recomputed for whichever side the review belongs to.

Members cannot review a host they never visited. A member-author review requires a stay request between that member and the host that has reached `CHECKED_IN` or `CHECKED_OUT` and whose `occupancy_end` is at or before the current logical clock; a member attempting to review a host with no such completed stay is refused with `ERR_REVIEW_NOT_ELIGIBLE` (HTTP 403). Withdrawal reverses everything a review did: the review moves to `WITHDRAWN`, both rating aggregates are recomputed without it, and any conduct incident sourced from that review is itself set to `WITHDRAWN` with a zero waiver and its subject member's ledger recomputed — which means the member who was penalized by a private report recovers both the points and the strike when the report is retracted.

The platform's economic bargain with hosts runs through receipts rather than through fees. During a stay, a member records a purchase at the host with a patronization record naming the host, the member, the `stay_request_id` of the stay during which the purchase was made, the `receipt_cents` amount — which must be positive — and a `purchase_kind` drawn from `TASTING`, `MERCHANDISE`, `TICKET` or `MEAL`. The recording request must carry `expected_request_version` matching the stay's current `version`, exactly as described in §2.9, and the act of recording increments that stay's `version` by one. A new record opens at `PENDING` status with `host_credit_cents` at 0 and a `verification_code` minted by the server, which the host later scans to settle it. Verification is host-side and requires that code: a verification whose `verification_code` does not equal the record's minted code is refused with `ERR_PATRONIZATION_CODE_INVALID` (HTTP 422), and a verified record computes its `host_credit_cents` and re-totals the host's `patronization_credit_cents` across all of its verified records. A host may also reject a pending record outright, which sets `verification_status` to `REJECTED` and leaves `host_credit_cents` at zero permanently; the credit arithmetic governing both outcomes is set out in §2.8.

### 3.9. Reading a Host's Live Position

Because so much of the preceding sections is derived rather than declared, the platform exposes read-only views that let an operator or a client inspect the current arithmetic without recomputing it themselves. A host's live capacity read reports which basis is currently in force through `capacity_basis`, the physical active-site count as `base_capacity`, the current `effective_capacity`, the occupancy figure under each of the two bases as `committed_sites_reserved_basis` and `committed_sites_occupied_basis`, the resulting `free_sites`, the identifier and member ceiling of the window currently in force as `active_window_id` and `active_window_member_ceiling`, the `latest_checkout_at` edge, and the derived `posture`. A degree of divergence between the two occupancy figures is expected whenever first-round requests are outstanding, since the reserved basis counts them and the occupied basis does not.

A site's availability read answers the blocking question directly for host staff and platform staff, over an optional `from_date` and `to_date` range. It reports the site's `site_id`, the `occupied_intervals` on it over that range, the labels of the sites currently blocking it as `blocked_by_site_labels`, and a boolean `is_assignable` summarising whether the site could be handed to a new stay, evaluated at the current logical clock instant by applying the blocked-approach rule to a zero-length stay beginning and ending at that instant. A site is therefore not assignable while any site whose `blocks_sites` list names it holds a `CONFIRMED` or `CHECKED_IN` stay whose occupancy reaches within two hours either side of the current instant, and an inactive site is never assignable at all. This is the read that explains why a confirmation failed with a blocked-approach refusal, since the blocking site is a different site from the one being assigned.

Listing operations carry optional filters rather than requiring callers to walk the whole set. Hosts filter on `state_code`, `category`, `onboarding_status` and `posture`; parking sites filter on `is_active` and `site_class`; members filter on `plan_tier`, `subscription_status` and `removal_status`; availability windows filter on `window_status`, `kind` and an `overlaps_date` that matches windows spanning a given day; stay requests filter on `host_id`, `member_id`, `vehicle_id`, `confirmed_site_id`, `request_status` and a `from_date`; reviews filter on `host_id`, `author_member_id`, `subject_member_id`, `subject_host_id`, `author_review_id`, `author_kind` and `review_status`; incidents filter on `member_id`, `host_id`, `incident_status` and `severity`; and patronization records filter on `host_id`, `member_id`, `stay_request_id` and `verification_status`. Every list operation accepts `limit` and `offset` under the rules of §2.3. The recalculation triggers that keep these derived values current are catalogued in §2.14.

### 3.10. The Logical-Clock Capability

One administrative capability deserves separate mention because it drives timing for the whole system. A platform operator may set the logical clock to any instant, supplying it as `to_iso8601`; the operation reports the resulting `current_utc`, the window identifiers it activated as `activated_window_ids`, and the window identifiers it deactivated as `deactivated_window_ids`. The clock starts at `2026-09-01T00:00:00Z` on server startup and reads exactly that instant until the first call, and it never silently reverts to real wall-clock time. Advancing it past a window's `start_date` activates that window, rewinding it to before `start_date` returns the window to `SCHEDULED`, and both directions trigger the capacity recomputation for every host whose live basis changed. Every temporal guard quoted in this document — the 48-hour lead-time check, the departed-window check on counter-requests, the seven-day free-cancellation boundary, the window activation and expiry rules — is evaluated against this clock alone.
