# Motor Fuel Tax Licensing & Distributor Reporting API — Product Requirements Document

## 1. Introduction

A state motor fuel tax unit collects most of its revenue at a single physical choke point — the terminal rack — and then spends the rest of the year proving that the gallons which crossed that rack were reported honestly by everyone downstream of it. The unit licenses five statutory classes of participant (suppliers, distributors, blenders, transporters and retailers), bonds each of them in proportion to the tax it is expected to owe, decides for every rack removal whether tax is imposed there or deferred to the purchaser's own monthly return, and then reconciles thousands of independently filed schedules against each other to find gallons that one party sold and the other never bought. This API is the system of record for that entire apparatus.

The operational difficulty the product must absorb is that a single gallon reported on a schedule plays four roles simultaneously. It is a tax-base input, feeding the filer's own liability. It is one endpoint of a cross-match edge that must agree with a counterparty's separately filed schedule. It is refund capacity, because only tax-paid gallons can be claimed back for off-road, power-take-off, refrigeration-unit or export use. And it is a risk-score input, because unreported gallons are what drive audit selection. Because those four roles are computed from the same detail lines, the system cannot afford to recompute anything loosely: the order in which gallons are summed, floored, multiplied by a rate and rounded to cents is part of the statutory contract, not an implementation detail.

This document specifies the API mounted under `/mft` — every resource, state machine, calculation, validation and error it must produce. It is written for engineers who will implement the service without access to the underlying statutes, so wherever a rule has an inclusive or exclusive boundary, an evaluation order, or a compensating counterpart elsewhere in the system, that fact is stated explicitly. Two conventions run through everything that follows: money is always integer cents, and gallons always carry exactly two decimal places.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. A request missing either header, carrying an empty `X-User-ID`, or naming a role outside the six recognized values is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); surrounding whitespace is stripped from both header values before those tests, so a whitespace-only `X-User-ID` counts as empty and a padded role name is still recognized. A syntactically valid request whose role is not authorized for the addressed operation is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The six roles are `LicenseeAgent`, `LicensingOfficer`, `ReturnsExaminer`, `TaxSupervisor`, `AuditManager` and `FieldInspector`.

- **`LicenseeAgent`** is the licensed taxpayer acting for itself: it reports its own rack removals, builds and files its own returns, answers cross-match inquiries, claims refunds and protests assessments. When `X-User-Role` is `LicenseeAgent`, `X-User-ID` is the `id` of the acting `Licensee`; ownership checks on any resource that references a `Licensee` compare the resource's foreign-key field to `X-User-ID`. Concretely, the owning licensee of a resource is: the `Licensee`'s own `id` for a licensee row, `licensee_id` for a `MonthlyReturn`, a `RefundClaim` or a `BondInstrument`, the parent return's `licensee_id` for a `ReturnSchedule`, the grandparent return's `licensee_id` for a `ScheduleLine`, `distributor_licensee_id` for a `MatchDiscrepancy`, and `subject_licensee_id` for an `AuditCase`. Addressing a single resource owned by some other licensee fails with `ERR_LICENSEE_SCOPE_VIOLATION` (HTTP 403). List endpoints behave differently: rather than erroring, they are silently narrowed to rows belonging to the agent's own licensee. That narrowing is how top-level list endpoints behave; a collection or computed read addressed *under* a licensee path — the licensee's bonds, its ledger entries, its bond status — is scope-checked against the licensee named in the path exactly as a single resource is, so an agent naming some other licensee is refused with `ERR_LICENSEE_SCOPE_VIOLATION` rather than handed an empty page.
- **`LicensingOfficer`** runs the licensing and bonding desk: it registers licensees and terminals, issues and revokes exemption certificates, posts and releases surety bonds, and drives the license through `PENDING_BOND`, `ACTIVE`, `SUSPENDED` and `REVOKED`.
- **`ReturnsExaminer`** runs the returns-processing desk: it may key and file returns on a licensee's behalf, run schedule cross-matching, work discrepancies through the inquiry cycle, and review refund claims. It may never decide or pay a refund it reviewed.
- **`TaxSupervisor`** is the money authority: it decides and pays refunds, issues, finalizes and abates audit assessments, dismisses roadside penalties, records taxpayer remittances, and may suspend a license. It never reviews the refunds it decides and never issues an assessment on a case it opened.
- **`AuditManager`** owns audit selection and casework: it opens cases by risk score or referral and drives the case dimension through fieldwork, findings, taxpayer response and closure. It deliberately has no money authority.
- **`FieldInspector`** performs roadside enforcement: it records dyed-fuel inspections in the field. It cannot dismiss its own findings and cannot touch returns, refunds or audits.

For the five operator roles — `LicensingOfficer`, `ReturnsExaminer`, `TaxSupervisor`, `AuditManager` and `FieldInspector` — `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands an audit trail (as `reviewer_user_id` and `decider_user_id` on a `RefundClaim`, and as `opened_by_user_id` and `assessed_by_user_id` on an `AuditCase`) and compares recorded values against the acting `X-User-ID` when segregation of duties is enforced, but it never compares an operator's `X-User-ID` to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.5 rather than from the host's real time, so it moves only when a client moves the clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of rows returned; when omitted it defaults to 10, its minimum accepted value is 1 and its maximum is 100. `offset` is the number of rows to skip; when omitted it defaults to 0 and its minimum accepted value is 0. A parameter supplied as an empty string counts as omitted and takes its default. A `limit` that is not an integer in the inclusive range 1 through 100, or an `offset` that is not an integer of at least 0, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400); a value carrying a decimal point or any non-digit body is not an integer for this purpose.

Unless a specific endpoint states otherwise, list results are sorted by `created_at` in ascending order. Because the logical clock of §2.5 never advances on its own, rows created without moving it share a `created_at` to the millisecond; such ties are broken by creation order, so every list is stable and reproducible. Query parameters the endpoint does not define are ignored rather than rejected, and a defined filter whose value is outside the recognized set of that field is not an error either — it simply matches no rows. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the number of rows matching the filters before pagination is applied.

### 2.4. Common Resource Properties

Every persisted resource carries a server-minted `id` formatted as a UUID with no type prefix, and a `created_at` timestamp rendered as an ISO 8601 UTC instant with three fractional digits (for example `2026-08-01T00:00:00.000Z`).

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row — including mutations the server performs on its own initiative as part of a cascade, and including mutations that only touch fields the row stores. Computed fields are the exception, because they are re-derived on every read rather than stored: a licensee whose `balance_cents` or compliance counters merely move because a row *elsewhere* was written — a ledger entry appended by a refund payment, a roadside penalty, an assessment or an abatement, or a return joining its filed set — is not itself written and does not advance its own `version`, which advances only where §3 says it does. The increment is counted once per request, not once per write: a row that a single request touches several times — because a cascade revisits it, or because the endpoint sets a field and then re-derives the row — still advances its `version` by exactly one and carries a single `updated_at`. Licensees, bond instruments, terminals, exemption certificates, monthly returns, return schedules, cross-match runs, match discrepancies, refund claims, roadside inspections and audit cases all behave this way.

Three record types are append-only observations rather than mutable state, and they carry only `id` and `created_at` — both `updated_at` and `version` are absent from them entirely: rack removals, schedule lines and ledger entries. A rack removal's tax determination is frozen at the instant it is reported; a schedule line is either present or deleted-by-never-existing; and the tax ledger is corrected by appending compensating rows, never by editing rows already posted.

### 2.5. The Logical Clock

Every deadline, days-late count, certificate window test, interest accrual and period-closed check in this system reads a server-side **logical clock** rather than real wall-clock time. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; this startup default is mandated, and the server must never fall back to the host's real time.

An administrative test-driving capability lets any of the five operator roles move the clock: the request supplies the target instant as `to_iso8601`, and the response reports the clock's new reading as `current_utc` — the sole member of the response's `data` object, rendered like every other timestamp as an ISO 8601 UTC instant with three fractional digits, under HTTP 200. Setting the clock modifies no persisted entity — it does not re-derive a single due date, penalty or risk score. Values already computed and stored stay exactly as they were; only computations performed after the clock moves see the new instant.

### 2.6. Gallons, Rates and Rounding Discipline

Gallons are decimal quantities carried to exactly 2 decimal places. Money is always an integer number of cents; the API never returns a fractional cent and never returns money as a string. Gallons are likewise returned as JSON numbers rather than strings, quantized to two decimals before serialization. Every conversion from gallons to cents goes through a per-product tax rate expressed in cents per gallon: 28.6 for `GASOLINE`, 30.9 for `UNDYED_DIESEL`, 0.0 for `DYED_DIESEL`, 5.0 for `JET_FUEL`, 10.0 for `AVIATION_GAS`, 28.6 for `ETHANOL_E100` and 30.9 for `BIODIESEL_B100`. Whenever a rate is applied, the resulting cents figure is rounded **half up** to a whole cent.

Two disciplines about *when* to round matter more than the rounding mode itself, and both are stated again where they apply. First, rounding happens once per rate application, never twice: a quantity of gallons is accumulated at full 2-decimal precision, multiplied by its rate once, and rounded once. Second, where a formula has several money components (tax, then interest, then penalty), each component is rounded half up on its own and the components are then added as integers — the system never computes a single combined product and rounds that.

Comparisons on gallons are exact decimal comparisons at 2 decimal places, not floating-point approximations. A variance of exactly 5.00 gallons against a 5.00-gallon tolerance is *not* out of tolerance; a variance of exactly 10000.00 gallons against the 10000.00-gallon auto-escalation threshold *is* at the threshold. Boundary inclusivity is called out explicitly at each rule.

### 2.7. Bond Sufficiency as a Standing Precondition

Bonding is the state's collateral against deferred tax, and the bond position of a licensee is recomputed — never cached stale — at every event that could change it: when the licensee is registered, when a bond is posted, when a bond is released, when a return is filed, and on every licensee status transition.

The requirement is derived as follows. The system takes the **newest up to three** monthly returns of the licensee whose `filing_status` is `FILED`, ordered by `period_month` descending with ties broken by `created_at` ascending; draft and superseded returns are invisible to this basis. When that set is empty, `avg_monthly_tax_liability_cents` is the assumed liability for a brand-new licensee, 500000 cents. Otherwise `avg_monthly_tax_liability_cents` is the sum of those returns' `tax_due_cents` divided by how many returns are in the set, with any fraction discarded downward to a whole cent. That average is then multiplied by three months of coverage, by a multiplier keyed on `license_type` — 1.0 for `SUPPLIER`, `DISTRIBUTOR` and `BLENDER`, 0.5 for `TRANSPORTER`, 0.25 for `RETAILER` — and by a suspension multiplier of 2.0 while the licensee's `status` is `SUSPENDED` and 1.0 otherwise. The product is rounded **up** to the next whole multiple of 100000 cents, and only then clamped into the statutory band: `required_bond_cents` is the clamped value, never below 200000 cents and never above 100000000 cents. The ceiling to the 100000-cent step always happens **before** the clamp, not after.

`posted_bond_cents` is the sum of `amount_cents` over the licensee's bond instruments whose `status` is `ACTIVE`; released and forfeited instruments contribute nothing. `bond_deficiency_cents` is the amount by which the requirement exceeds what is posted, floored at zero — when posted bond meets or exceeds the requirement, the deficiency is exactly 0. A dedicated computed read exposes `avg_monthly_tax_liability_cents`, `required_bond_cents`, `posted_bond_cents`, `bond_deficiency_cents` and `basis_return_count`, the last being how many filed returns actually entered the average (0, 1, 2 or 3).

A standing deficiency is not merely informational. It blocks activation, it blocks bond release, it freezes pending refund claims, and it refuses deferral of tax to an under-bonded purchaser at the rack. Each of those consequences is specified in §3 next to the workflow it guards.

### 2.8. The Tax Ledger and the Money Invariant

Each licensee has an append-only tax ledger. A ledger entry records `licensee_id`, an `entry_type` drawn from `RETURN_TAX`, `RETURN_TAX_ADJUSTMENT`, `PENALTY`, `INTEREST`, `ASSESSMENT`, `ABATEMENT`, `REFUND`, `PAYMENT` and `PENALTY_REVERSAL`; a signed `amount_cents`; a polymorphic pointer consisting of `source_entity_type` (one of `MonthlyReturn`, `RefundClaim`, `AuditCase`, `RoadsideInspection` or `Payment`) and `source_entity_id`, whose meaning depends on the type and which is deliberately not a declared foreign key because the target type varies — a `PAYMENT` row names `Payment` as its `source_entity_type` and carries a null `source_entity_id`, because no payment entity is persisted anywhere; an `effective_date` taken as an ISO 8601 date from the logical clock at the moment of posting, the one exception being the remittance endpoint of §3.9, whose row carries the `effective_date` submitted with the payment; and a human-readable `memo`, which is null when the posting workflow supplies none.

The sign convention is fixed. `RETURN_TAX`, `PENALTY`, `INTEREST` and `ASSESSMENT` post positive amounts, increasing what the licensee owes the state. `REFUND`, `PAYMENT`, `ABATEMENT` and `PENALTY_REVERSAL` post negative amounts, decreasing it. `RETURN_TAX_ADJUSTMENT` carries whichever sign the amendment produces and may legitimately be negative or zero.

**Invariant M (money).** At every instant, and for every licensee, `balance_cents` equals the signed sum of that licensee's ledger entries' `amount_cents`; a positive balance means the licensee owes the state. The ledger is never edited: an assessment that is later abated leaves *both* rows in place, and the balance returns to exactly its pre-assessment value. A roadside penalty that is later dismissed likewise leaves both the `PENALTY` row and its `PENALTY_REVERSAL` row in place, with the balance restored exactly.

**Invariant G (gallons).** At every instant, and for every licensee, `effective_taxable_gallons_ytd` equals the sum of `taxable_gallons_total` over that licensee's monthly returns whose `filing_status` is `FILED` and whose `period_month` falls in the same calendar year as the logical clock, carried to 2 decimals. Because an amendment supersedes its target inside the very same request in which the amendment row joins the filed set, an amendment whose schedules reproduce the superseded return's gallons leaves `effective_taxable_gallons_ytd` unchanged.

### 2.9. Cascade Discipline and Compensating Actions

A great many operations in this system mutate more than the resource addressed. The rule is that every affected row the server writes is mutated in full — its state field, its derived counters, its `updated_at` and its `version` — and that the server performs these secondary mutations without an explicit client request against the secondary rows. A row the cascade does not write, and whose figures merely read differently afterwards because they are computed on every read, is not an affected row for this purpose and keeps its `version`, as §2.4 explains.

Cascades in this domain reach up to four hops deep. A positive roadside dye test assesses a penalty on the inspection (hop 1), which posts a ledger row and re-derives the licensee's balance, and increments the licensee's dyed-violation counter; the counter reaching its threshold suspends the licensee (hop 2); the suspension doubles the bond requirement and re-derives the deficiency (hop 3); and a resulting deficiency freezes the licensee's pending refund claims (hop 4). Each hop is caused by the hop before it, and all of them complete inside the single request that recorded the inspection.

Several cascades have explicit **compensating** counterparts, and the compensation is deliberately narrower than the original. Reinstating a suspended licensee recomputes the bond requirement with the suspension multiplier back at 1.0, exactly undoing the doubling, and releases the refund claims that the suspension froze for bond reasons. Dismissing a roadside penalty reverses the money and decrements the violation counter but pointedly does **not** un-suspend the licensee: a suspended licensee stays suspended until it is explicitly reinstated, and its bond requirement keeps the doubled multiplier until then. Abating an assessment reverses the assessed total in full but leaves the case's own status history intact. Revoking a certificate stops future presentations of it without retroactively recomputing tax on removals and schedule lines already recorded.

Where a cascade is conditional, the condition is part of the contract: revocation forfeits only the bonds that are still `ACTIVE` and leaves already-released instruments untouched; a suspension freezes refund claims only if the recomputed deficiency is greater than zero.

### 2.10. Stale-View Protection on Two Write Paths

Exactly two write paths in this API take an optimistic-concurrency field, because exactly two of them can silently destroy work the client never observed. On both, the version field is a required, non-optional part of the request body.

Posting a surety bond for a licensee requires `expected_licensee_version`, carrying the client's last observed `version` of the target `Licensee`. If that value does not equal the licensee's current `version`, the request is rejected with `ERR_STALE_LICENSEE_VERSION` (HTTP 412) and no bond is created. This guard exists because bond posting is a create-with-supersede operation: a newly posted bond releases the licensee's prior active bond and becomes the whole of `posted_bond_cents`. A second post carrying the version the client read *before* the first post would otherwise wipe out a bond the client never saw.

Opening an amendment of a filed return requires `expected_return_version`, carrying the client's last observed `version` of the `MonthlyReturn` being amended. If that value does not equal that return's current `version`, the request is rejected with `ERR_STALE_RETURN_VERSION` (HTTP 412) and no amendment row is created. Multiple amendments of one period are legitimate, and the original stays `FILED` until its amendment is itself filed, so without this guard a second amendment request would succeed against a view of the return that predates the first amendment — including a view that predates cross-matching having written a match status onto the same row.

No other endpoint in this API accepts a version field, and no other endpoint performs a version check. Endpoints not named above must not require, and must not honour, an expected-version input.

### 2.11. Path Resolution and Rule Precedence

Path parameters are resolved strictly left to right, and the first identifier that does not resolve determines the 404 that comes back. A request addressing a schedule under a return therefore fails with `ERR_RETURN_NOT_FOUND` when the return is unknown, without ever attempting to locate the schedule. The per-resource 404 codes are `ERR_LICENSEE_NOT_FOUND`, `ERR_BOND_NOT_FOUND`, `ERR_TERMINAL_NOT_FOUND`, `ERR_CERTIFICATE_NOT_FOUND`, `ERR_RACK_REMOVAL_NOT_FOUND`, `ERR_RETURN_NOT_FOUND`, `ERR_SCHEDULE_NOT_FOUND`, `ERR_SCHEDULE_LINE_NOT_FOUND`, `ERR_CROSS_MATCH_RUN_NOT_FOUND`, `ERR_DISCREPANCY_NOT_FOUND`, `ERR_REFUND_CLAIM_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND` and `ERR_AUDIT_CASE_NOT_FOUND`, each HTTP 404.

More generally, every request is evaluated against an ordered ladder of checks. The **first** check that fails produces the response, and no later check may override it. The bands, in order, are:

1. **Authentication** — headers present and the role recognized (`ERR_UNAUTHENTICATED`).
2. **Authorization** — the acting role appears in the endpoint's authorized set (`ERR_UNAUTHORIZED`).
3. **Licensee scope** — for a `LicenseeAgent`, `X-User-ID` owns the addressed resource (`ERR_LICENSEE_SCOPE_VIOLATION`). This runs *before* any state, business or fiscal check, so an agent poking at another licensee's resource never learns whether that resource was in a legal state.
4. **Request shape** — required fields present, types correct, enum members legal, numeric and pattern constraints satisfied, conditional requirements met (`ERR_INVALID_REQUEST`, HTTP 400). This band covers `gross_gallons` greater than 0; `net_gallons` greater than 0 and not greater than `gross_gallons`; `claimed_gallons` greater than 0; `amount_cents` greater than 0; `additional_tax_cents` at least 0; `period_month`, `period_start_month` and `period_end_month` matching a four-digit year, a hyphen and a two-digit month from 01 through 12; `mailing_state`, `state_code` and `destination_state` each exactly two uppercase letters; `fein` exactly two digits, a hyphen and seven digits; `terminal_control_number` the letter `T`, two digits, two uppercase letters and four digits; well-formed ISO 8601 dates and timestamps; `equipment_class` supplied when and only when `claim_type` is `PTO`; and `evasion_indicator` supplied when an assessment is issued.
5. **Pagination shape** — on list endpoints only (`ERR_INVALID_PAGINATION`).
6. **Path existence**, left to right, as described above. A scope check needs an existing row to compare against, so an addressed identifier that resolves to nothing produces that resource's 404 even when the acting `LicenseeAgent` would not have owned the row had it existed.
7. **Body foreign keys**, in the order the fields are declared on the request: identifiers naming a licensee (`licensee_id`, `parent_licensee_id`, `purchaser_licensee_id`, `position_holder_licensee_id`, `counterparty_licensee_id`, `inspected_licensee_id`, `subject_licensee_id`) resolve to a licensee or the request fails with `ERR_LICENSEE_NOT_FOUND`; `terminal_id` resolves or fails with `ERR_TERMINAL_NOT_FOUND`; a non-null `exemption_certificate_id` resolves or fails with `ERR_CERTIFICATE_NOT_FOUND`; a non-null `source_discrepancy_id` resolves or fails with `ERR_DISCREPANCY_NOT_FOUND`.
8. **Optimistic concurrency** — the two version checks of §2.10.
9. **State preconditions** — the addressed resource is in a state that admits the requested action (the HTTP 409 family).
10. **Business safety and compliance rules** — licence validity at the rack, certificate integrity, dyed-fuel prohibitions, segregation of duties, audit and violation holds.
11. **Referential business rules** — schedule/product/counterparty legality, declared-versus-derived reconciliation, amendment-target legality, escalation-source consistency.
12. **Temporal rules** — period closure, certificate window overlap, audit period overlap, date ordering, refund period filed.
13. **Uniqueness and bounded-counter rules** — duplicate identifiers, inquiry and audit round caps, risk-score gating, write-off and partial-decision legality, equipment-class legality.
14. **Fiscal rules, always last** — purchaser bonding at the rack, bond release deficiency, activation deficiency, refund pool capacity, refund minimum, abatement capacity, payment capacity.

Within band 9 the state check for the addressed resource always precedes the state checks of related rows, and within bands 10 through 14 the relative order of individual rules is stated at each rule in §3 wherever two rules could both fire on the same request.

### 2.12. Segregation of Duties

Two money decisions in this system are deliberately split across two human beings, and the split is enforced on the acting `X-User-ID` rather than on the role — a user who happens to hold both roles is still barred from acting twice on the same object.

On refunds, the examiner who reviewed a claim has its `X-User-ID` recorded as `reviewer_user_id`; that user may not then decide the claim. The supervisor who decided the claim has its `X-User-ID` recorded as `decider_user_id`; that user may not then pay the claim. Either violation is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 422).

On audits, the manager who opened a case has its `X-User-ID` recorded as `opened_by_user_id`; that user may not issue the case's assessment. The supervisor who issued the assessment has its `X-User-ID` recorded as `assessed_by_user_id`; that user may not abate it. Either violation is refused with `ERR_ASSESSMENT_SEGREGATION_VIOLATION` (HTTP 422).

## 3. Business Logic & Workflows

### 3.1. Licensing, Classification and the Consolidated Group

A `LicensingOfficer` brings a taxpayer into the system by registering it with its registered `legal_name` (between 1 and 120 characters), its `fein` (a federal employer identification number written as two digits, a hyphen and seven digits), its statutory `license_type`, and the two-letter `mailing_state` of record. The classification is one of `SUPPLIER`, `DISTRIBUTOR`, `BLENDER`, `TRANSPORTER` or `RETAILER`, and it is consequential far beyond labelling: it sets the bond multiplier, it decides which schedules the licensee may report, and it decides whether tax imposition can be deferred to that licensee at a terminal rack. A `fein` must be unique across all licensees; a collision is refused with `ERR_DUPLICATE_FEIN` (HTTP 409), and that duplicate check runs before the consolidated-group validation described next, so a registration that both repeats a `fein` and names an illegal parent reports `ERR_DUPLICATE_FEIN`.

Registration accepts three optional declarations. `gross_net_election` is the licensee's irrevocable choice of the gallons basis applied to its own rack removals — either `NET` or `GROSS`, defaulting to `NET`. `retail_channel` records the channel a retailer serves, one of `HIGHWAY`, `MARINE`, `FARM` or `NOT_APPLICABLE`, defaulting to `NOT_APPLICABLE`; it is the conditional flag behind the dyed-fuel-on-road prohibition, which the system enforces on dyed-sales schedule lines rather than at registration. `parent_licensee_id` names the consolidated group filer this licensee reports under, and defaults to null. Consolidated groups are exactly one level deep: a supplied `parent_licensee_id` must name a licensee whose `license_type` is `SUPPLIER`, whose `status` is `ACTIVE`, and whose own `parent_licensee_id` is null, and a licensee may never name itself. Any of those failures is refused with `ERR_INVALID_PARENT_LICENSEE` (HTTP 422). Listing licensees can be narrowed by `license_type`, by `status`, and by `parent_licensee_id` — the last being how an operator enumerates the members of a group.

A newly registered licensee lands in `PENDING_BOND`. Its bond position is computed immediately, which means a brand-new licensee with no filed returns is assessed against the assumed new-licensee liability of 500000 cents described in §2.7, so `avg_monthly_tax_liability_cents`, `required_bond_cents` and `bond_deficiency_cents` are all populated on the create response while `posted_bond_cents` is 0. Its `balance_cents` starts at 0, and every compliance counter starts at 0: `dyed_violation_count`, `late_filing_count`, `open_audit_count`, `open_discrepancy_count`, `unreported_gallons_total`, `effective_taxable_gallons_ytd`, `risk_score_variance_weighted` and `risk_score_frequency_weighted`.

The licence lifecycle is a cycle with one terminal exit. `PENDING_BOND → ACTIVE` and `SUSPENDED → ACTIVE` are both reinstatement legs driven by a `LicensingOfficer`; `ACTIVE → SUSPENDED` is a suspension leg driven by a `LicensingOfficer` or a `TaxSupervisor` and requires a `reason`; and `PENDING_BOND → REVOKED`, `ACTIVE → REVOKED` and `SUSPENDED → REVOKED` are all the same revocation leg, driven by a `LicensingOfficer` with a `reason`, ending in the terminal `REVOKED` state. Requesting a transition the current `status` does not admit — reinstating an already `ACTIVE` licensee, suspending one that is not `ACTIVE`, or revoking one that is already `REVOKED` — fails with `ERR_LICENSEE_STATE_INVALID` (HTTP 409). Separately, a `REVOKED` licensee accepts no new bonds, no reinstatement, no suspension, no new returns opened against it through the open-return endpoint of §3.4 (opening an *amendment* of a return it already filed is not gated on revocation, as §3.5 spells out), no return filing and no new refund claims; those attempts fail with `ERR_LICENSEE_REVOKED` (HTTP 409). On the transition endpoints the revoked test is evaluated first, ahead of the legal-transition test, which is what separates the two codes: reinstating or suspending a revoked licensee reports `ERR_LICENSEE_REVOKED`, while a second revocation — an action the revoked prohibition above does not name — reports `ERR_LICENSEE_STATE_INVALID`.

Reinstatement is gated by two independent compliance conditions, evaluated in this order after the revoked check and the legal-transition check have passed. First, a licensee whose `dyed_violation_count` has reached 2 or more may not be reinstated at all until that count is brought back below 2 by dismissing an inspection; the attempt fails with `ERR_DYED_VIOLATION_HOLD` (HTTP 422). Second, a licensee whose `bond_deficiency_cents` is greater than zero may not be reinstated; that attempt fails with `ERR_BOND_DEFICIENCY_BLOCKS_ACTIVATION` (HTTP 422). The deficiency for a licensee coming back from `SUSPENDED` is evaluated with the suspension multiplier of 2.0 **still in force**, which is precisely what makes the return leg non-trivial: a suspended licensee must post the doubled bond before it can be reinstated. A deficiency of exactly zero passes — the test is whether posted bond has reached the requirement, and equality is sufficient.

On a successful reinstatement, `status` becomes `ACTIVE`, the bond figures are recomputed with the suspension multiplier back at 1.0 (exactly compensating the doubling that suspension applied), and every refund claim of that licensee sitting in `HELD` with `hold_reason` of `BOND_DEFICIENCY` is returned to whatever `status_before_hold` recorded, with `status_before_hold` and `hold_reason` both cleared back to null. The licensee's `version` increments.

Suspension is the mirror image. `status` becomes `SUSPENDED`, `required_bond_cents` is recomputed with the suspension multiplier at 2.0 and `bond_deficiency_cents` re-derived from it, and *only if* that re-derived deficiency is greater than zero, every refund claim of the licensee whose `status` is `SUBMITTED` or `REVIEWED` has its current status copied into `status_before_hold`, its `status` set to `HELD` and its `hold_reason` set to `BOND_DEFICIENCY`. The licensee's `version` increments.

Revocation is the widest cascade in the licensing area, and it is identical whichever status the licensee is leaving. `status` becomes `REVOKED`. Every bond instrument of the licensee whose `status` is `ACTIVE` becomes `FORFEITED` with `release_reason` set to `LICENSE_REVOKED`, while instruments already `RELEASED` are left untouched — so a revoked licensee whose bonds were previously released carries a full deficiency once `posted_bond_cents` and `bond_deficiency_cents` are re-derived. Every exemption certificate naming this licensee as its purchaser and still `ACTIVE` becomes `REVOKED`. Every refund claim of the licensee whose `status` is `SUBMITTED`, `REVIEWED` or `HELD` becomes `DENIED`, with `allowable_gallons` set to 0.00 and `refund_amount_cents` set to 0. The licensee's `version` increments, as does the `version` of each cascaded bond, certificate and claim.

### 3.2. Surety Bonds: Posting, Supersession and Release

A bond instrument records the licensee it stands for through `licensee_id` (taken from the path rather than the body), a face `amount_cents` of at least 100000 cents — a smaller figure is a request-shape failure and comes back as `ERR_INVALID_REQUEST` from band 4, not as a fiscal refusal — the issuing `surety_name`, and the ISO 8601 calendar date `effective_date` on which it takes effect. An `effective_date` later than the logical clock is refused with `ERR_DATE_RANGE_INVALID` (HTTP 422). Posting also requires `expected_licensee_version` as described in §2.10, and a `LicensingOfficer` is the only role that may post.

Posting is a create-with-supersede. The new instrument is created with `status` `ACTIVE` and `release_reason` null. Any *older* instrument of the same licensee that was still `ACTIVE` is moved to `RELEASED` with `release_reason` set to `SUPERSEDED_BY_NEW_BOND`, so that after the post the licensee's `posted_bond_cents` is exactly the new instrument's `amount_cents` and nothing more. The licensee's `posted_bond_cents` and `bond_deficiency_cents` are then re-derived and the licensee's `version` increments, alongside the `version` increments on the new and superseded instruments. Listing a licensee's instruments can be filtered by `status`, so an operator can see active and released collateral separately.

Operator release is the deliberate, non-superseding path out of `ACTIVE`, and it exists mainly so that over-collateralized licensees can free capital. Releasing sets `status` to `RELEASED` with `release_reason` `OPERATOR_RELEASE`, re-derives the licensee's `posted_bond_cents` and `bond_deficiency_cents`, and increments the versions of both rows. An instrument that is not `ACTIVE` cannot be released and the attempt fails with `ERR_BOND_NOT_ACTIVE` (HTTP 409). A release whose principal licensee has already been revoked fails with `ERR_LICENSEE_REVOKED` — a revoked licensee's collateral is forfeited, not released. And a release that would leave an `ACTIVE` licensee with `posted_bond_cents` below `required_bond_cents` is refused with `ERR_BOND_RELEASE_WOULD_CREATE_DEFICIENCY` (HTTP 422); that fiscal check runs last, after the instrument's own state check.

The third exit from `ACTIVE` is not an operator action at all: the revocation cascade of §3.1 moves active instruments to `FORFEITED` with `release_reason` `LICENSE_REVOKED`. `RELEASED` and `FORFEITED` are both terminal. The three release reasons are therefore fully accounted for: `SUPERSEDED_BY_NEW_BOND` is written by the system when a newer bond arrives, `OPERATOR_RELEASE` by the explicit release action, and `LICENSE_REVOKED` by the revocation cascade; the field stays null for as long as the instrument remains `ACTIVE`.

### 3.3. Terminals, Exemption Certificates and the Imposition Point

Terminals are registered by a `LicensingOfficer` with their IRS `terminal_control_number` — the letter `T`, two digits, two uppercase letters and four digits — a trade `name`, and the two-letter `state_code` of the state the rack physically sits in. The control number is unique across all terminals; a collision is refused with `ERR_DUPLICATE_TCN` (HTTP 409). Terminals are otherwise inert reference data and may be listed filtered by `state_code`.

Exemption certificates are the paper trail behind untaxed gallons. A `LicensingOfficer` issues one naming the exempt `purchaser_licensee_id` — government fleets, farms and out-of-state buyers are all registered as `RETAILER` licensees — an `exemption_type` of `GOVERNMENT`, `AGRICULTURE` or `EXPORT`, the certificate's `document_number`, and a coverage window bounded by `valid_from` and `valid_to`. Both bounds are ISO 8601 calendar dates and the window is **closed**: a transaction dated exactly on `valid_from` or exactly on `valid_to` is covered. A certificate is created with `status` `ACTIVE`.

Issuance is checked in a fixed order. After the named purchaser is confirmed to exist, the system looks for a collision: no other `ACTIVE` certificate for the same combination of `purchaser_licensee_id` and `exemption_type` may have a window that overlaps or even merely *touches* the requested one. Because both windows are closed intervals, sharing a single endpoint date is a collision, and the request is refused with `ERR_CERTIFICATE_PERIOD_OVERLAP` (HTTP 422). Next, `valid_from` must not be later than `valid_to`, or the request fails with `ERR_DATE_RANGE_INVALID` (HTTP 422). Finally, `document_number` must be unique across **all** certificates in the system — not merely across one purchaser's certificates — and a collision is refused with `ERR_DUPLICATE_CERTIFICATE_NUMBER` (HTTP 409). Certificates may be listed filtered by `purchaser_licensee_id`, by `exemption_type` and by `status`. A certificate is not one of the resources §2.1 assigns an owning licensee, so neither the single read nor the list is scope-narrowed: a `LicenseeAgent` may read and list every certificate in the system, including certificates naming other purchasers.

Revocation moves a certificate from `ACTIVE` to the terminal `REVOKED`; the officer's `reason` is a required field of the request, but it is not persisted on the certificate, whose representation changes only in `status`, `updated_at` and `version`. Revoking a certificate that is not `ACTIVE` fails with `ERR_CERTIFICATE_NOT_ACTIVE` (HTTP 409). Revocation is deliberately **not** retroactive: rack removals and schedule lines that already presented the certificate keep the tax figures computed at the time they were recorded, and nothing is recomputed. What changes is the future — every later presentation of that certificate fails with `ERR_CERTIFICATE_NOT_VALID_ON_DATE`, including a presentation made earlier on a schedule line that is only now being filed.

Throughout the system, a certificate counts as **validly presented for a given exemption type** when all six of the following hold: the transaction supplied a non-null `exemption_certificate_id`; the referenced certificate's `status` is `ACTIVE`; its `exemption_type` equals the type being tested; its `purchaser_licensee_id` equals the purchasing party on the transaction; the transaction's own date falls inside the closed window from `valid_from` through `valid_to`; and the transaction's `product_code` is a member of the product set the exemption type covers. Those product sets are fixed: `GOVERNMENT` covers `GASOLINE` and `UNDYED_DIESEL`; `AGRICULTURE` covers `UNDYED_DIESEL` only; `EXPORT` covers `GASOLINE`, `UNDYED_DIESEL`, `JET_FUEL`, `AVIATION_GAS`, `ETHANOL_E100` and `BIODIESEL_B100`.

A **rack removal** is the report that product physically left a terminal rack, and either a `LicenseeAgent` or a `ReturnsExaminer` may record one. The report names the `terminal_id` the fuel left, the `position_holder_licensee_id` holding the terminal position, the `purchaser_licensee_id` taking delivery, optionally an `exemption_certificate_id` presented at the rack, the `product_code` removed (one of `GASOLINE`, `UNDYED_DIESEL`, `DYED_DIESEL`, `JET_FUEL`, `AVIATION_GAS`, `ETHANOL_E100` or `BIODIESEL_B100`), the billed `gross_gallons` and temperature-corrected `net_gallons`, the `removal_date`, the two-letter `destination_state` declared on the bill of lading, and the `bill_of_lading_number`. Gross gallons must be greater than zero; net gallons must be greater than zero and must not exceed gross gallons. The bill-of-lading number must be unique per `terminal_id`, and a repeat is refused with `ERR_DUPLICATE_BOL` (HTTP 409). Removals may be listed filtered by `terminal_id`, `position_holder_licensee_id`, `purchaser_licensee_id`, `exemption_certificate_id`, `removal_month` and `imposition_point`. A rack removal, like an exemption certificate, is not one of the resources §2.1 assigns an owning licensee, so neither the single read nor the list is scope-narrowed: a `LicenseeAgent` reads and lists every removal in the system, including removals naming some other licensee as purchaser or position holder.

Before any tax is computed, five business checks run in this order. The purchaser's `status` must be `ACTIVE` or `SUSPENDED`; a purchaser still in `PENDING_BOND` or already `REVOKED` may not take delivery at a rack at all, and the report is refused with `ERR_PURCHASER_LICENSE_INVALID` (HTTP 422). The position holder must be a licensee whose `license_type` is `SUPPLIER` and whose `status` is `ACTIVE`, or the report fails with `ERR_POSITION_HOLDER_INVALID` (HTTP 422). If a certificate was presented, it must belong to the purchaser named on the removal, or the report fails with `ERR_CERTIFICATE_HOLDER_MISMATCH` (HTTP 422); it must be `ACTIVE` with `removal_date` inside its closed window, or the report fails with `ERR_CERTIFICATE_NOT_VALID_ON_DATE` (HTTP 422); and the removed `product_code` must be a member of that exemption type's product set, or the report fails with `ERR_EXEMPTION_PRODUCT_MISMATCH` (HTTP 422).

One fiscal check then runs last, after the duplicate-bill-of-lading check. When a removal has the shape that would defer tax — the purchaser's `license_type` is `SUPPLIER` or `DISTRIBUTOR`, the `destination_state` equals the home state `MN`, and no valid exemption certificate has been presented — the removal is refused if that purchaser's `bond_deficiency_cents` is greater than zero, whatever the purchaser's `status` happens to be. That refusal carries `ERR_PURCHASER_BOND_DEFICIENT` (HTTP 422). The state does not extend deferred credit to an under-bonded distributor. The certificate half of that condition is keyed on whether a certificate was presented at all, not on whether the presented certificate would actually exempt *this* removal, and that leaves one gap: an under-bonded `SUPPLIER` or `DISTRIBUTOR` purchaser presenting an otherwise valid `EXPORT` certificate on a load whose `destination_state` is nonetheless `MN` escapes this check entirely, and — since branch 2 and branch 3 below both need an out-of-state destination and branch 4 tests only `GOVERNMENT` and `AGRICULTURE` — still reaches branch 5 and gets its tax deferred. Outside that single case the deferral branch of the tax determination below can assume a fully bonded purchaser.

**Determining the imposition point.** Once those checks pass, the system computes the removal's tax treatment in three steps.

*Step one — the gallons basis.* The basis is keyed on the **position holder's** irrevocable `gross_net_election`, never on the purchaser's. When the position holder elected `NET`, `basis_used` is recorded as `NET` and the basis quantity is the removal's `net_gallons`. When the position holder elected `GROSS`, `basis_used` is recorded as `GROSS` and the basis quantity is the removal's `gross_gallons`. The same physical load therefore produces a different tax figure depending on whose position it left: for an eight-thousand-gallon billed load of `UNDYED_DIESEL` temperature-corrected to 7960.00 gallons, the `GROSS` election taxes 40.00 more gallons than the `NET` election, a difference of 1236 cents at the undyed-diesel rate.

*Step two — the imposition point.* Six branches are tested **strictly in the order below**; the first branch that matches decides `imposition_point`, and no later branch may override it.

1. If `product_code` is `DYED_DIESEL`, `imposition_point` is `NONE_EXEMPT`. Dyed product is never taxed at the rack.
2. Otherwise, if `destination_state` is not the home state `MN` **and** a valid `EXPORT` certificate was presented, `imposition_point` is `NONE_EXEMPT`.
3. Otherwise, if `destination_state` is not `MN`, `imposition_point` is `TERMINAL_RACK`. Tax rides at the rack and the purchaser must claim it back later through an `EXPORT` refund claim.
4. Otherwise, if a valid `GOVERNMENT` certificate or a valid `AGRICULTURE` certificate was presented, `imposition_point` is `NONE_EXEMPT`.
5. Otherwise, if the purchaser's `license_type` is `SUPPLIER` or `DISTRIBUTOR` **and** the purchaser's `status` is `ACTIVE`, `imposition_point` is `DEFERRED_TO_PURCHASER` — imposition moves to that purchaser's own monthly return.
6. Otherwise — a `BLENDER`, `TRANSPORTER` or `RETAILER` purchaser, or a suspended supplier or distributor — `imposition_point` is `TERMINAL_RACK`.

*Step three — the money.* The applicable rate is the per-product cents-per-gallon rate of §2.6. When `imposition_point` is `NONE_EXEMPT`, `taxable_gallons` is 0.00, `tax_imposed` is false, and both `tax_amount_cents` and `deferred_tax_cents` are 0. When `imposition_point` is `TERMINAL_RACK`, `taxable_gallons` is the basis quantity, `tax_imposed` is true, `tax_amount_cents` is the basis quantity multiplied by the rate and rounded half up to a whole cent, and `deferred_tax_cents` is 0. When `imposition_point` is `DEFERRED_TO_PURCHASER`, `taxable_gallons` is the basis quantity, `tax_imposed` is false, `tax_amount_cents` is 0, and `deferred_tax_cents` is the basis quantity multiplied by the rate and rounded half up — the tax the purchaser will owe on its own return. In every case the multiplication and the rounding happen exactly once.

### 3.4. Building a Monthly Return: Schedules and Transaction Lines

A monthly return is opened as a draft by a `LicenseeAgent` for itself or by a `ReturnsExaminer` on a licensee's behalf, naming the filer through `licensee_id` and the reporting period through `period_month` (a four-digit year, a hyphen, and a two-digit month from 01 through 12). A `LicenseeAgent` must name its own licensee, and that body field is scope-checked as band 3 of §2.11 — ahead of the licensee's existence and ahead of its status — so an agent naming another licensee is refused with `ERR_LICENSEE_SCOPE_VIOLATION` even when the identifier it named resolves to nothing; a `licensee_id` that is absent or not a string is instead the band-4 `ERR_INVALID_REQUEST`, because there is then no owner to compare against. At most one non-superseded return may exist for a given filer and period; a second attempt is refused with `ERR_DUPLICATE_RETURN_PERIOD` (HTTP 409). A revoked licensee may not open a return at all.

The new row carries two independent status dimensions, and this parallelism is the single most important structural fact about returns. `filing_status` starts at `DRAFT` and progresses `DRAFT → FILED → SUPERSEDED`. `match_status` starts at `NOT_MATCHED` and progresses `NOT_MATCHED → MATCH_CLEAN` or `NOT_MATCHED → MATCH_VARIANCE`, and from `MATCH_VARIANCE → MATCH_RESOLVED`. The two dimensions advance completely independently: a `FILED` return may sit at any match status, and a `SUPERSEDED` return keeps whatever match status it had already reached rather than being reset. The amendment fields also start at their neutral values — `amends_return_id` null, `amendment_sequence` 0, `amendment_count` 0 — as do `attest_name` and `filed_at`, both null while the return is a draft. The lateness and money fields start at zero and stay there until filing computes them: `days_late` is 0, `taxable_gallons_total` is 0.00, and `tax_due_cents`, `interest_cents`, `penalty_cents`, `total_remittance_cents` and `amendment_delta_cents` are all 0 on the draft. The one field computed at creation is `due_at`, the statutory deadline, which is the 20th day of the month **following** `period_month`, at 23:59:59Z. Returns may be listed filtered by `licensee_id`, `period_month`, `filing_status`, `match_status`, and `amends_return_id` — the last walking an amendment chain forward from the row it amends.

Inside a draft return, the filer builds **schedules**. Each schedule is one statutory block keyed by a `schedule_code` and a `product_code`, and the return's `return_id` is taken from the path rather than the body. The six statutory schedules are `SCH_1_RECEIVED_TAX_PAID` (gallons purchased with tax already paid), `SCH_2_RECEIVED_TAX_UNPAID` (gallons purchased tax-free, the taxable base), `SCH_5_DELIVERED_TAX_COLLECTED` (gallons sold with tax collected, the seller side of cross-matching), `SCH_6_EXEMPT_SALES`, `SCH_7_EXPORTS` and `SCH_10_DYED_SALES`. Product legality is tied to the code: `SCH_10_DYED_SALES` accepts `DYED_DIESEL` and nothing else, and every other schedule code rejects `DYED_DIESEL` outright; a violation is refused with `ERR_SCHEDULE_PRODUCT_NOT_ALLOWED` (HTTP 422). At most one schedule may exist per combination of return, schedule code and product code, and a duplicate is refused with `ERR_DUPLICATE_SCHEDULE` (HTTP 409) — a check that runs after the product-legality check. Schedules may be added only while the parent return's `filing_status` is `DRAFT`; a `FILED` or `SUPERSEDED` return accepts no new schedules and the attempt fails with `ERR_RETURN_ALREADY_FILED` (HTTP 409). Schedules of a return may be listed filtered by `schedule_code`; that collection read, and the list of lines under a schedule, are scope-checked against the resource named in the path exactly as a single read is, so a `LicenseeAgent` addressing another licensee's return or schedule is refused with `ERR_LICENSEE_SCOPE_VIOLATION` rather than handed an empty page.

Every schedule carries `total_gallons`, and its semantics are deliberately unusual: this is the gallons total the **filer attests to**, supplied at schedule creation as a two-decimal quantity of zero or greater — an empty statutory block legitimately declares 0.00 — and stored exactly as declared. It is never auto-maintained from the detail lines, and adding a line does not adjust it. The one number the system does maintain is `line_count`, which starts at 0 and increments by one for each line added; the parent schedule's `version` also increments on each line. The declared-versus-derived reconciliation happens exactly once, at filing time, and is described in §3.5.

A **transaction line** under a schedule names the other side of the transaction through `counterparty_licensee_id`, optionally an `exemption_certificate_id`, a `transaction_type` drawn from `PURCHASE`, `SALE`, `EXPORT`, `IMPORT`, `BLEND` and `TRANSFER`, the `gallons` moved (greater than zero; a supplied value carrying more than two decimals is quantized half up to two decimals rather than rejected, here and everywhere else the API accepts gallons), the `document_date` of the underlying document, and the `bill_of_lading_number` of the bill of lading or invoice. The parent schedule's `schedule_id` is taken from the path. A `document_date` that does not fall inside the parent return's `period_month` is refused with `ERR_INVALID_REQUEST`; because that test is made against the parent return reached through the path, it can only run once the addressed schedule resolves, so a line posted to an unknown schedule reports `ERR_SCHEDULE_NOT_FOUND` even when its `document_date` is out of period as well. Bill-of-lading numbers on lines must be unique within the combination of the parent schedule's return and the line's `counterparty_licensee_id`; a repeat is refused with `ERR_DUPLICATE_BOL` (HTTP 409). Lines may only be added while the parent return is `DRAFT`, again with `ERR_RETURN_ALREADY_FILED` on a filed or superseded return. Lines may be listed under their schedule, or across schedules filtered by `schedule_id`, `counterparty_licensee_id`, `exemption_certificate_id` and `transaction_type`.

Line entry enforces four business rules beyond the shape checks, in this order. First, a presented certificate must belong to the line's counterparty, or the line is refused with `ERR_CERTIFICATE_HOLDER_MISMATCH`. Second, that certificate must be `ACTIVE` with the line's `document_date` inside its closed validity window, or the line is refused with `ERR_CERTIFICATE_NOT_VALID_ON_DATE`. Third, the line's product — a line carries no product of its own, so this is the parent schedule's `product_code` — must be covered by that certificate's exemption type, or the line is refused with `ERR_EXEMPTION_PRODUCT_MISMATCH`. Fourth come the dyed-fuel prohibitions: a line on a `SCH_10_DYED_SALES` schedule may not name a counterparty whose `retail_channel` is `HIGHWAY`, and a `DYED_DIESEL` line may never appear on a `SCH_2_RECEIVED_TAX_UNPAID`, `SCH_5_DELIVERED_TAX_COLLECTED` or `SCH_6_EXEMPT_SALES` schedule; either violation is refused with `ERR_DYED_FUEL_ON_ROAD_PROHIBITED` (HTTP 422).

Counterparty classification is then checked, after the dyed-fuel rules and before the duplicate-bill-of-lading check. Lines on `SCH_1_RECEIVED_TAX_PAID` and `SCH_2_RECEIVED_TAX_UNPAID` schedules require a counterparty whose `license_type` is `SUPPLIER` or `DISTRIBUTOR`, because tax-free and tax-paid purchases can only come from a bonded upstream party. Lines on `SCH_7_EXPORTS` require a counterparty whose `mailing_state` is something other than the home state `MN`. A violation of either rule is refused with `ERR_COUNTERPARTY_TYPE_INVALID` (HTTP 422).

Two further requirements about lines are enforced not at entry but at filing, because the facts they depend on can change in between. Every line on a `SCH_6_EXEMPT_SALES` or `SCH_7_EXPORTS` schedule must carry a non-null `exemption_certificate_id`, and that certificate must still be `ACTIVE` with the line's `document_date` inside its closed window at the moment of filing. A certificate revoked between line entry and filing therefore blocks the filing with `ERR_CERTIFICATE_NOT_VALID_ON_DATE`, even though the line was legal when it was keyed — and a line that carries no certificate at all reports the same `ERR_CERTIFICATE_NOT_VALID_ON_DATE` at filing rather than a request-shape error, because the omission is only discovered when the return is reconciled, not when the line is keyed.

### 3.5. Filing, Interest, Penalty and the Amendment Chain

Filing is the moment a draft becomes a legal instrument and money hits the ledger. Either the `LicenseeAgent` that owns the return or a `ReturnsExaminer` acting for it may file, supplying `attest_name`, the name of the officer attesting the return. Filing drives `filing_status` from `DRAFT` to `FILED` and leaves `match_status` untouched.

Seven conditions guard the transition, in this order. The filer must not be revoked (`ERR_LICENSEE_REVOKED`). The return's `filing_status` must be `DRAFT` (`ERR_RETURN_ALREADY_FILED`). The period must be closed — the logical clock must have reached at least the first instant of the month following `period_month`, so a period still in flight cannot be filed; the refusal carries `ERR_PERIOD_NOT_CLOSED` (HTTP 422). Every exempt-sales and exports line must carry a certificate that is still valid on that line's `document_date` (`ERR_CERTIFICATE_NOT_VALID_ON_DATE`). Then the reconciliation: for every schedule of the return, the declared `total_gallons` must equal the exact two-decimal sum of that schedule's line `gallons`, and its `line_count` must equal the number of those lines; a mismatch is refused with `ERR_SCHEDULE_TOTALS_MISMATCH` (HTTP 422). The same error code also guards a second, aggregate condition: when the filer's `license_type` is `DISTRIBUTOR`, `BLENDER` or `RETAILER`, then for each product code separately, the gallons the filer reports as going **out** — the sum across its `SCH_5_DELIVERED_TAX_COLLECTED`, `SCH_6_EXEMPT_SALES`, `SCH_7_EXPORTS` and `SCH_10_DYED_SALES` schedules for that product — must not exceed the gallons it reports as coming **in**, the sum across its `SCH_1_RECEIVED_TAX_PAID` and `SCH_2_RECEIVED_TAX_UNPAID` schedules for that product. Finally, a return may not be filed with zero schedules at all, and a return whose filer is a `SUPPLIER` must carry at least one `SCH_5_DELIVERED_TAX_COLLECTED` schedule; either omission is refused with `ERR_MISSING_REQUIRED_SCHEDULE` (HTTP 422).

**Computing the tax.** `taxable_gallons_total` and `tax_due_cents` are derived from the lines of **this return only** — schedules belonging to a draft or superseded sibling return of the same period contribute nothing. The rounding order here is the whole difficulty of the rule and must be followed exactly. Working through the product codes in the order `GASOLINE`, `UNDYED_DIESEL`, `DYED_DIESEL`, `JET_FUEL`, `AVIATION_GAS`, `ETHANOL_E100`, `BIODIESEL_B100`, the system computes for each product: the exact two-decimal sum of line gallons on that product's `SCH_2_RECEIVED_TAX_UNPAID` schedules, minus the exact two-decimal sum on that product's `SCH_6_EXEMPT_SALES` schedules, minus the exact two-decimal sum on that product's `SCH_7_EXPORTS` schedules. That per-product net is then floored at zero — a product whose exempt sales and exports exceed its tax-unpaid receipts contributes zero, and never a negative figure that would subsidise another product. The floored net is added to `taxable_gallons_total`, and the floored net multiplied by that product's cents-per-gallon rate, rounded half up to a whole cent **once for that product**, is added to `tax_due_cents`.

Two things this pinned order forbids are worth stating plainly. The system does not round per line: two `SCH_2_RECEIVED_TAX_UNPAID` lines of `UNDYED_DIESEL` at 100.01 gallons each sum to 200.02 gallons and yield 6181 cents, whereas rounding each line first would yield 6180 cents and be one cent short. And the system does not round after summing all products either — each product code gets its own single rounding. Gallons from `SCH_1_RECEIVED_TAX_PAID`, `SCH_5_DELIVERED_TAX_COLLECTED` and `SCH_10_DYED_SALES` schedules never enter `tax_due_cents` at all: tax-paid receipts feed only the refund pool, tax-collected deliveries feed only cross-matching, and dyed sales are informational.

**Interest and penalty.** These are computed after the tax, in a pinned order that resolves what looks like a circular dependency: the bracket selecting the penalty percentage is keyed on a subtotal that already contains interest, while interest itself is keyed only on tax.

*Lateness.* `filed_at` is the logical clock at the moment of filing. `days_late` is 0 when `filed_at` is at or before `due_at`; otherwise it is the elapsed time from `due_at` to `filed_at` divided into whole days and rounded **up** to the next whole day, so any part of a day counts as a full day.

*Interest.* `interest_cents` is 0 when `days_late` is 0. Otherwise it is `tax_due_cents` multiplied by a daily interest rate of 0.00025 and by `days_late`, rounded half up to a whole cent. Interest accrues on tax only, never on penalty.

*Penalty.* `penalty_cents` is 0 when `days_late` is 0. Otherwise the system forms a subtotal of `tax_due_cents` plus `interest_cents`, and selects a percentage by lateness tier: 5 percent when `days_late` is 30 or fewer, 10 percent when `days_late` is 60 or fewer, and 15 percent beyond 60 days. If that subtotal reaches 1000000 cents or more, a further 5 percentage points is **added to the tier percentage** — a surcharge on the tier, not a compounding of it, so a 90-day filing with a large deficiency uses 20 percent rather than 15 percent compounded. The penalty is then the greater of a statutory floor of 5000 cents and the subtotal multiplied by that percentage rounded half up to a whole cent.

*Total.* `total_remittance_cents` is `tax_due_cents` plus `interest_cents` plus `penalty_cents`, added as integers after each component has been rounded on its own.

**Ledger postings at filing.** For an **original** return — one whose `amends_return_id` is null — a `RETURN_TAX` entry for the full `tax_due_cents` is appended always, even when the tax is zero; an `INTEREST` entry for `interest_cents` is appended only when interest is greater than zero; and a `PENALTY` entry for `penalty_cents` is appended only when the penalty is greater than zero. For an **amendment**, exactly one entry is appended instead: a `RETURN_TAX_ADJUSTMENT` for `amendment_delta_cents`, and it is appended even when the delta is zero. In both cases the filer's `balance_cents` is re-derived from the ledger and `effective_taxable_gallons_ytd` is re-derived over the licensee's filed returns.

Filing also updates the licensee's compliance and bonding position. When `days_late` is 1 or more **and** the return is an original, `late_filing_count` increases by one; a period is counted late exactly once, on its original filing, so amending an already-late period does not count it again. Because a newly filed return changes the bond basis, `avg_monthly_tax_liability_cents`, `required_bond_cents` and `bond_deficiency_cents` are all re-derived per §2.7. The return's own `version` increments.

**Amendments.** An amendment is opened against a filed return by a `LicenseeAgent` or `ReturnsExaminer`, supplying `expected_return_version` (see §2.10) and a `reason`. The target must have `filing_status` `FILED`, or the request fails with `ERR_RETURN_NOT_FILED` (HTTP 409). The target must additionally be the newest non-superseded return of its filer-and-period chain, and must not itself be an amendment that has already been amended; a violation is refused with `ERR_AMENDMENT_TARGET_INVALID` (HTTP 422). Opening an amendment creates a **new** draft return with the same `licensee_id` and `period_month`, whose `amends_return_id` points at the target and whose `amendment_sequence` is the target's `amendment_sequence` plus one; the target's `amendment_count` increases by one and its `version` increments. The target stays `FILED` — it is only superseded when the amendment is itself filed. Opening an amendment deliberately does **not** re-test the filer's revocation: the §3.1 prohibition on new returns bites on the open-return endpoint of §3.4 and again at filing, so a revoked filer may open an amendment row that it will then never be permitted to file.

When the amendment is filed, the system computes its own tax exactly as for an original return, but the interest and penalty rules differ in two ways. `days_late` is measured from the **same** `due_at` as the original period, not from a new deadline. And if the amendment's own `tax_due_cents` is less than or equal to the amended return's `tax_due_cents`, then `interest_cents` and `penalty_cents` are copied verbatim from the amended return rather than recomputed — a corrective amendment that does not increase tax cannot manufacture new penalty, and `amendment_delta_cents` therefore equals the pure tax difference. If instead the amendment's `tax_due_cents` is greater than the amended return's, interest and penalty are recomputed from scratch on the amendment's own full `tax_due_cents`, using the amendment's own `filed_at` against the original `due_at`.

`amendment_delta_cents` is 0 for an original return. For an amendment it is that amendment's `total_remittance_cents` minus the superseded return's `total_remittance_cents`, and it is the amount posted to the ledger. In the same request that files the amendment, the amended return moves `FILED → SUPERSEDED`, its `match_status` is left exactly as it stood, and its `version` increments. A superseded row immediately drops out of every filed-filtered aggregate in the system: the bond basis, `effective_taxable_gallons_ytd`, the cross-match input set, and the refund tax-paid pool.

### 3.6. Cross-Matching Supplier and Distributor Schedules

Cross-matching is the state's discovery engine: it takes every gallon a supplier says it delivered with tax collected and looks for the matching gallon the purchaser says it received tax-paid. A `ReturnsExaminer` or `TaxSupervisor` starts a run by naming a `period_month`, optionally overriding the default tolerance through `tolerance_gallons`. The run is computed and closed inside the request that creates it — `run_status` is `COMPLETED` on arrival and there is no other value it can take — and the effective tolerance is snapshotted onto the run as `tolerance_gallons` (defaulting to 5.00, and required to be zero or greater when it is supplied) so that a later reading of the run explains its own results.

Two conditions guard a run. The period must be closed, meaning `period_month` is strictly earlier than the logical clock's own month; an in-flight period is not matchable and the attempt fails with `ERR_PERIOD_NOT_CLOSED` (HTTP 422). And at most one run may exist per period, so a second run for the same `period_month` fails with `ERR_DUPLICATE_MATCH_RUN` (HTTP 409). Runs may be read individually and listed filtered by `period_month` and `run_status`.

**Cell enumeration.** Only returns whose `filing_status` is `FILED` and whose `period_month` equals the run's `period_month` enter either side of the comparison; draft and superseded returns are invisible to cross-matching. The run walks supplier licensees — those holding such a return that carries at least one `SCH_5_DELIVERED_TAX_COLLECTED` schedule — in ascending `created_at` order. Within each supplier it walks the distinct pairs of `counterparty_licensee_id` and product appearing on that supplier's tax-collected schedules, ordered first by the counterparty's ascending `created_at` and then by product in the order `GASOLINE`, `UNDYED_DIESEL`, `DYED_DIESEL`, `JET_FUEL`, `AVIATION_GAS`, `ETHANOL_E100`, `BIODIESEL_B100`. Enumeration never orders by row identifier, so the `created_at` ordering of the discrepancies a run creates is reproducible.

For each such cell the run computes `supplier_gallons` as the exact two-decimal sum of that supplier's `SCH_5_DELIVERED_TAX_COLLECTED` line gallons naming this counterparty and product. It then looks for the purchaser's filed return for the same period — at most one can exist. If there is none, `distributor_gallons` is 0.00 and the direction is fixed in advance as `MISSING_COUNTERPARTY_RETURN`. Otherwise `distributor_gallons` is the exact two-decimal sum of that return's `SCH_1_RECEIVED_TAX_PAID` line gallons naming this supplier as counterparty and this product, and the direction is left to be decided by sign. `variance_gallons` is `supplier_gallons` minus `distributor_gallons`, at two decimals. Every cell examined increments `matched_cells_count`, whether or not it produces a finding.

**Tolerance.** A discrepancy is created only when the absolute value of `variance_gallons` is **strictly greater** than the run's `tolerance_gallons`. A variance of exactly 5.00 gallons against the default tolerance creates nothing at all — it increments `matched_cells_count` and is otherwise forgotten. When a discrepancy is created, `direction` is the pre-fixed `MISSING_COUNTERPARTY_RETURN` if the purchaser filed nothing; otherwise it is `UNREPORTED_BY_PURCHASER` when the variance is positive (the supplier reported more than the purchaser did) and `OVERSTATED_BY_PURCHASER` when negative. The row records `run_id`, `supplier_licensee_id`, `distributor_licensee_id`, `product_code`, both gallons figures, the variance, the direction, `supplier_return_id`, and `distributor_return_id` — the last being null exactly when the direction is `MISSING_COUNTERPARTY_RETURN`. `status` starts at `OPEN`, `inquiry_round` at 0, and `last_question`, `last_explanation` and `response_due_date` at null. `discrepancy_count` increments.

**The run's four gallons counters and the conservation law.** For every created discrepancy whose direction is `UNREPORTED_BY_PURCHASER`, the variance is added to both `gross_unreported_gallons_total` and `unreported_gallons_total`. Thereafter the two behave differently, and the difference is the whole point. `gross_unreported_gallons_total` is **frozen** at creation time and is never re-derived by any later action. `unreported_gallons_total` is the live sum over the run's `UNREPORTED_BY_PURCHASER` discrepancies whose status is not `WRITTEN_OFF`, and `written_off_gallons_total` is the live sum over those whose status **is** `WRITTEN_OFF`. Because a write-off moves gallons from the first live counter to the second by the same amount, the live pair always sums to the frozen gross — a conservation law an examiner can check at any time. `escalated_count` and `escalation_skipped_count` complete the counter set.

**Return match statuses.** Once the cells are enumerated, every filed return of the period is stamped: a return whose licensee appears in no discrepancy this run created moves to `MATCH_CLEAN`, and every other filed return of the period moves to `MATCH_VARIANCE`. `filing_status` is untouched.

**Licensee-level counters.** Each created discrepancy increments the purchaser's `open_discrepancy_count` and, when the direction is `UNREPORTED_BY_PURCHASER`, adds the variance to the purchaser's own `unreported_gallons_total`. The one exception is a discrepancy the run auto-escalates: because it is not an open work item, it is excluded from `open_discrepancy_count`.

**Auto-escalation.** When a created discrepancy has direction `UNREPORTED_BY_PURCHASER` and `variance_gallons` reaching 10000.00 gallons or more — the threshold is inclusive, so exactly 10000.00 escalates — the run escalates it immediately: `status` becomes `ESCALATED_TO_AUDIT`, `escalated_count` increments, an audit case is created against the purchaser with `selection_method` `CROSS_MATCH_ESCALATION`, `selection_score` 0, `risk_score_variant` at its default `VARIANCE_WEIGHTED` (the field is still recorded on the case even though §3.9 ignores it for this selection method), `source_discrepancy_id` pointing back at the discrepancy, `period_start_month` and `period_end_month` both equal to the run's `period_month`, and `opened_by_user_id` set to the acting `X-User-ID` of whoever requested the run. The subject's `open_audit_count` increments, and because it is now positive, each of the subject's refund claims in `SUBMITTED` or `REVIEWED` moves to `HELD`. If, however, a non-closed audit case for that same subject already overlaps the run's period under the buffered-overlap rule of §3.9, no case is created: the discrepancy is left `OPEN`, it counts in the purchaser's `open_discrepancy_count` like any other open finding, and `escalation_skipped_count` increments instead. A single run can therefore both escalate some findings and skip others.

**The inquiry cycle.** A `ReturnsExaminer` sends an inquiry to the purchaser with a `question` and a `response_due_date` — any well-formed calendar date is accepted, and the system never requires it to be later than the logical clock — driving `status` to `INQUIRY_SENT`, incrementing `inquiry_round`, and recording the question as `last_question` alongside the due date. Inquiries may be sent from `OPEN` or from `RESPONSE_RECEIVED`; from any other status the request fails with `ERR_DISCREPANCY_STATE_INVALID` (HTTP 409). At most three inquiries may ever be sent on one discrepancy: the round counter must be below 3 before a new inquiry, so the third round is the last permitted one and a fourth attempt fails with `ERR_INQUIRY_ROUND_LIMIT` (HTTP 422).

The purchaser answers with an `explanation` and optionally a `referenced_return_id` pointing at the return that explains the variance. Only the `LicenseeAgent` named by `distributor_licensee_id` may answer, and only from `INQUIRY_SENT`; the explanation is stored as `last_explanation` and `status` becomes `RESPONSE_RECEIVED`. A supplied `referenced_return_id` must first resolve to a return at all — it is an ordinary band-7 body foreign key, so an unknown identifier fails with `ERR_RETURN_NOT_FOUND` ahead of the status check just described — and must then belong to that same `distributor_licensee_id`, or the response is refused with `ERR_RESPONSE_RETURN_MISMATCH` (HTTP 422). The pair of inquiry and response can therefore cycle up to three times before the examiner must dispose of the finding. Discrepancies may be read individually and listed filtered by `run_id`, `supplier_licensee_id`, `distributor_licensee_id`, `supplier_return_id`, `distributor_return_id`, `product_code`, `status` and `direction`.

**The three-way disposition.** A `ReturnsExaminer` closes a discrepancy from `OPEN`, `INQUIRY_SENT` or `RESPONSE_RECEIVED` by supplying a `resolution` of `EXPLAINED`, `WRITTEN_OFF` or `ESCALATE_TO_AUDIT`; from any other status the request fails with `ERR_DISCREPANCY_STATE_INVALID`. The three branches share one side effect and differ in every other respect.

- `EXPLAINED` sets `status` to `RESOLVED_EXPLAINED` and leaves the run's `unreported_gallons_total` and `written_off_gallons_total` exactly as they were. The gallons stay in the run's live unreported pool deliberately, as an audit trail: the state accepted the taxpayer's story about this cell but has not conceded the gallons.
- `WRITTEN_OFF` sets `status` to `WRITTEN_OFF` and moves the gallons: the run's `unreported_gallons_total` decreases by `variance_gallons` and its `written_off_gallons_total` increases by the same amount, conserving the frozen gross. This branch is the most restricted of the three. It requires a `write_off_reason`, which the server keeps but never surfaces — the discrepancy's representation gains no field for it — and it is permitted only when the absolute value of `variance_gallons` is strictly less than 10000.00 gallons; a variance at or above the auto-escalation threshold must be explained or escalated and can never be written off. Either failure is refused with `ERR_WRITE_OFF_NOT_PERMITTED` (HTTP 422).
- `ESCALATE_TO_AUDIT` sets `status` to `ESCALATED_TO_AUDIT` and fires the same audit-case cascade the run's auto-escalation fires: a case is created against the escalation subject — the purchaser when the direction is `UNREPORTED_BY_PURCHASER`, otherwise the supplier — with `selection_method` `CROSS_MATCH_ESCALATION`, `selection_score` 0, `risk_score_variant` at its default `VARIANCE_WEIGHTED`, this discrepancy as `source_discrepancy_id`, and both period bounds set to the run's period; the subject's `open_audit_count` increments; and because that count is now positive, the subject's `SUBMITTED` and `REVIEWED` refund claims move to `HELD` with `hold_reason` `OPEN_AUDIT` and their prior status preserved in `status_before_hold`. Here, unlike inside a run, an overlapping non-closed case is not a silent skip: the escalation is refused with `ERR_AUDIT_PERIOD_OVERLAP` (HTTP 422). Note the asymmetry, which is intentional — a batch run must survive an overlap and keep going, while a hand-driven escalation must tell the examiner why it cannot proceed.

All three branches decrease the purchaser's `open_discrepancy_count` by one, because none of the three resulting statuses is an open work item. The purchaser's `unreported_gallons_total` is re-derived too, but it is narrower than that: it excludes exactly the `WRITTEN_OFF` and `RESOLVED_EXPLAINED` statuses, so a written-off or explained variance drops out of the licensee-level figure that feeds variance-weighted risk scoring, while a variance **escalated to audit** stays in it — an escalation takes the finding out of the open queue without conceding the gallons, and the licensee keeps carrying their weight for as long as the discrepancy sits at `ESCALATED_TO_AUDIT`, whatever the audit case that received it goes on to do. §3.9 states the same input set from the scoring side. And all three then check the purchaser's return: if no discrepancy naming that `distributor_return_id` remains in `OPEN`, `INQUIRY_SENT` or `RESPONSE_RECEIVED`, the return's `match_status` moves from `MATCH_VARIANCE` to `MATCH_RESOLVED`; a return sitting at any other `match_status` is left alone, and a discrepancy whose `direction` is `MISSING_COUNTERPARTY_RETURN` carries a null `distributor_return_id` and so has no return to advance at all. The return's `filing_status` is not consulted and not changed — a superseded return can still reach `MATCH_RESOLVED`.

### 3.7. Refund Claims: The Waterfall, Review and the Decision Fork

Only tax-paid gallons can be refunded, and the state refunds them for four statutory uses named by `claim_type`: `OFF_ROAD` (fuel burned off the highway), `PTO` (fuel burned by power-take-off equipment while the vehicle is stationary), `REFRIGERATION_UNIT` (fuel burned by a trailer reefer) and `EXPORT`. Every refund in this system is a refund of `UNDYED_DIESEL`, at that product's rate of 30.9 cents per gallon. A claim is filed by the claimant's own `LicenseeAgent` or by a `ReturnsExaminer` on its behalf, naming `licensee_id`, `claim_type`, `period_month`, `claimed_gallons` (greater than zero, two decimals) an `equipment_class` of `CONCRETE_MIXER`, `REFUSE_PACKER` or `BULK_TANKER_PUMP`. A `LicenseeAgent` must name its own licensee, and that body field is scope-checked as band 3 of §2.11 — ahead of the licensee's existence and ahead of its revocation — so an agent naming another licensee is refused with `ERR_LICENSEE_SCOPE_VIOLATION` even when the identifier it named resolves to nothing, while a `licensee_id` that is absent, empty or not a string is instead the band-4 `ERR_INVALID_REQUEST`, because there is then no owner to compare against. `equipment_class` is required when and only when `claim_type` is `PTO`: it must be present on a power-take-off claim and null on every other claim type, and a violation of that conditional requirement is refused with `ERR_INVALID_REQUEST` — an explicitly null `equipment_class` on a non-`PTO` claim is accepted as an absent one, while supplying a value there is refused even when the value names a legal class. On a `PTO` claim band 4 requires no more of the field than a non-empty string; whether that string names one of the three recognized classes is the separate band-13 test described next.

Two gates precede any arithmetic, and the whole entry sequence follows the ladder of §2.11 rather than the order in which this paragraph introduces the rules. A revoked claimant is refused first of all, with the `ERR_LICENSEE_REVOKED` of §3.1 (band 9). Next, no audit case for that claimant may be open — any case whose `case_status` is not `CLOSED` freezes new claims, and the filing fails with `ERR_REFUND_BLOCKED_BY_AUDIT` (HTTP 422, band 10). Only then is the return gate reached: the claimant must already have a filed, non-superseded return for `period_month`, because that return is the only source of the tax-paid pool; without one the claim fails with `ERR_REFUND_PERIOD_NOT_FILED` (HTTP 422, band 12). Note the division of labour between this rule and the cascade of §3.6: an open audit blocks claims that have not yet been filed, while claims that already existed when the case opened are not denied but moved to `HELD`. The `equipment_class` legality of band 13 is checked after all three of those, and the pool capacity of step two last of all. A power-take-off claim may not name a class outside the three recognized power-take-off classes — a claim of any other type never reaches this test, because naming a class at all on a non-`PTO` claim already failed band 4 — and a refrigeration-unit claim's `claimed_gallons` may not exceed the monthly reefer cap of 1500.00 gallons by more than a factor of ten: a figure **strictly greater** than 15000.00 gallons is a data-entry error and is rejected outright rather than quietly capped, while exactly 15000.00 passes this test and is merely capped. Either violation carries `ERR_EQUIPMENT_CLASS_INVALID` (HTTP 422).

**Step one — the statutory basis.** For an `OFF_ROAD` or `EXPORT` claim the basis is `claimed_gallons` unchanged. For a `PTO` claim the basis is `claimed_gallons` multiplied by the allocation percentage for the named equipment class — 0.30 for `CONCRETE_MIXER`, 0.25 for `REFUSE_PACKER`, 0.15 for `BULK_TANKER_PUMP` — rounded half up to two decimals. For a `REFRIGERATION_UNIT` claim the basis is the lesser of `claimed_gallons` and the 1500.00-gallon monthly cap, so a claim between the cap and ten times the cap is silently capped rather than rejected. This is the one place in the system where a limit clamps rather than errors, and the boundary between clamping and rejecting is exactly the factor-of-ten check above.

**Step two — the waterfall.** The period's pool is the exact two-decimal sum of `UNDYED_DIESEL` line gallons on the `SCH_1_RECEIVED_TAX_PAID` schedules of the claimant's filed return for `period_month`. Superseded returns contribute nothing, so an amendment that removes tax-paid receipts shrinks the pool available to later claims. Against that pool the system subtracts the gallons already consumed: the sum of `allowable_gallons` over the claimant's other claims for the same period whose `status` is anything other than `DENIED`, walked in ascending `created_at` order. Claims still sitting at `SUBMITTED`, `REVIEWED` or `HELD` consume the pool exactly as approved and paid ones do — a pending claim reserves its gallons. If the new claim's basis exceeds what remains, the claim is **rejected** with `ERR_REFUND_EXCEEDS_TAX_PAID` (HTTP 422); it is never silently reduced to fit. Otherwise `allowable_gallons` is set to the basis.

**Step three — the money.** `refund_amount_cents` is `allowable_gallons` multiplied by 30.9 cents per gallon, rounded half up to a whole cent, exactly once. The gallons rounding of step one happens before this multiplication, never after it. The claim is stored with `status` `SUBMITTED` and all of `status_before_hold`, `hold_reason`, `recommendation`, `recommended_gallons`, `reviewer_user_id`, `decider_user_id` and `payment_reference` null. Claims may be read individually and listed filtered by `licensee_id`, `claim_type`, `period_month` and `status`.

**Review.** A `ReturnsExaminer` reviews a claim from `SUBMITTED`, recording a `recommendation` of `APPROVE`, `PARTIAL` or `DENY`; a `PARTIAL` recommendation must be accompanied by `recommended_gallons` greater than zero and not greater than the claim's current `allowable_gallons`, and a violation is refused with `ERR_INVALID_REQUEST`. On an `APPROVE` or `DENY` recommendation `recommended_gallons` is optional rather than forbidden: it is recorded verbatim on the claim when supplied and left null when it is not, only its own greater-than-zero shape test applies to it there, and the `allowable_gallons` ceiling is not enforced against it. Review moves `status` to `REVIEWED` and stamps `reviewer_user_id` with the acting `X-User-ID`. Reviewing from any other status fails with `ERR_REFUND_STATE_INVALID` (HTTP 409), and because the ceiling comparison needs the persisted claim it is evaluated after that state test — a claim in some other status reports `ERR_REFUND_STATE_INVALID` even when its `recommended_gallons` also exceeds the ceiling.

**The decision fork.** A `TaxSupervisor` decides a `REVIEWED` claim by supplying a `decision`, and the acting `X-User-ID` must differ from the recorded `reviewer_user_id` — the same human may not review and then decide the same claim, and the attempt is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 422). The three branches diverge sharply:

- `APPROVED` leaves `allowable_gallons` and `refund_amount_cents` at their submit-time values and moves `status` to `APPROVED`. It is permitted only when `refund_amount_cents` reaches the 2000-cent payability floor, inclusive; below it the decision is refused with `ERR_REFUND_BELOW_MINIMUM` (HTTP 422).
- `PARTIALLY_APPROVED` is the only branch that changes the money. It is legal only when the review recorded a `recommendation` of `PARTIAL` with a non-null `recommended_gallons`; the decider supplies no gallons of its own, and a decision that cannot draw on such a review is refused with `ERR_DECISION_AMOUNT_INVALID` (HTTP 422). `allowable_gallons` is set to `recommended_gallons` and `refund_amount_cents` is recomputed as the reduced gallons times 30.9, rounded half up once. The payability floor is then re-checked against the **recomputed** amount, so a reduction that drops the refund below 2000 cents is refused with `ERR_REFUND_BELOW_MINIMUM` and nothing at all is written — neither the gallons nor the status nor `decider_user_id`.
- `DENIED` sets `allowable_gallons` to 0.00 and `refund_amount_cents` to 0. Because the waterfall skips denied claims, this releases the claim's gallons back into the period's pool for later claims — the widest path by which pool capacity is recovered, though not the only one, since the waterfall reads each surviving claim's *current* `allowable_gallons` and a `PARTIALLY_APPROVED` reduction therefore frees the difference between the submitted basis and the reduced figure. The payability floor does not apply to a denial.

All three branches stamp `decider_user_id` with the acting `X-User-ID`.

**Payment.** A `TaxSupervisor` pays a claim from `APPROVED` or `PARTIALLY_APPROVED`, supplying a `payment_reference` for the warrant or ACH transfer. The acting `X-User-ID` must differ from the recorded `decider_user_id`, so the supervisor who decided a claim may not also pay it; that violation too is refused with `ERR_SEGREGATION_OF_DUTIES`. `status` becomes `PAID`, and a `REFUND` ledger entry is appended for the negative of `refund_amount_cents` — the sign convention of §2.8 — with the claim as `source_entity_type` and `source_entity_id`, after which the claimant's `balance_cents` is re-derived. Paying from any other status, including `HELD`, fails with `ERR_REFUND_STATE_INVALID`.

**Holds.** `HELD` is never entered by a request against the claim itself; it is only ever entered by cascade, from two different causes. A licensee suspension for bond deficiency holds the licensee's `SUBMITTED` and `REVIEWED` claims with `hold_reason` `BOND_DEFICIENCY`, and an audit case opening on the licensee holds them with `hold_reason` `OPEN_AUDIT`. In both cases the pre-hold status is preserved in `status_before_hold`. The hold is reverted by the cascade that clears its cause — licensee reactivation for a bond hold, and the audit case reaching `CLOSED` with the subject's `open_audit_count` back to zero for an audit hold — restoring `status` to `status_before_hold` and clearing both `status_before_hold` and `hold_reason`. Held gallons continue to consume the period's pool throughout. Revocation of the licensee is the one cascade that disposes of held claims permanently: every claim in `SUBMITTED`, `REVIEWED` or `HELD` is driven to `DENIED` with `allowable_gallons` 0.00 and `refund_amount_cents` 0.

### 3.8. Roadside Enforcement of the Dyed-Fuel Prohibition

Dyed diesel is untaxed because it is meant for off-highway use only, so the state tests supply tanks at the roadside. A `FieldInspector` records a stop with `inspected_licensee_id`, `inspection_date`, a `dye_test_result` of `NEGATIVE` or `POSITIVE`, the `gallons_in_tank` measured in the supply tank (zero or greater, two decimals), the `vehicle_identifier` (plate or VIN) and an optional `location_description` giving the highway and milepost. A revoked licensee's vehicle cannot be the subject of a penalty assessment: the stop is still recorded and still comes back under HTTP 201, but the created row sits at `RECORDED` with `prior_positive_count` 0 and `penalty_cents` 0, no ledger row is written and no hop of the cascade fires, exactly as for a `NEGATIVE` result. No other licensee status is consulted at recording time — a `PENDING_BOND` or already `SUSPENDED` licensee's positive test is assessed normally. Inspections may be read individually and listed filtered by `inspected_licensee_id`, `dye_test_result` and `status`; an inspection is not one of the resources §2.1 assigns an owning licensee, so neither the single read nor the list is scope-narrowed and a `LicenseeAgent` may read and list every inspection in the system, including inspections of other licensees' vehicles.

A `NEGATIVE` result is recorded and nothing else happens: `status` stays `RECORDED`, `penalty_cents` is 0, and no ledger row is written. A `POSITIVE` result triggers the assessment and the cascade.

**The escalating penalty.** First the system freezes `prior_positive_count`, the number of this licensee's earlier inspections with a `POSITIVE` result whose `status` is not `DISMISSED`, counted over rows ordered by `inspection_date` ascending and then `created_at` ascending and taking only rows strictly before this one. A prior offence that was later dismissed does not escalate a subsequent one, and the count is frozen onto the row so that a later dismissal of an earlier inspection does not retroactively cheapen this penalty.

`penalty_cents` is then computed in a strictly pinned order. A base amount is taken as the **greater** of a flat 100000 cents and `gallons_in_tank` multiplied by 1000 cents per gallon rounded half up. A multiplier is selected from the frozen count: 1.0 when it is 0, 2.0 when it is exactly 1, and 3.0 for two or more. `penalty_cents` is the base multiplied by that multiplier, rounded half up to a whole cent. Taking the maximum **before** applying the multiplier is essential: a second offence with 40.00 gallons in the tank pays twice the 100000-cent floor, or 200000 cents, not the 100000-cent floor applied to a doubled per-gallon figure of 80000.

**The four-hop cascade.** A positive test sets off the longest chain in the system, and each hop is caused by the hop before it rather than by the request. Hop one is the assessment itself: `prior_positive_count` and `penalty_cents` are frozen, `status` becomes `PENALTY_ASSESSED`, a `PENALTY` ledger entry for the positive `penalty_cents` is appended naming the inspection as its source, the licensee's `balance_cents` is re-derived, and the licensee's `dyed_violation_count` increases by one. All of hop one is part of *creating* the inspection rather than a later edit of it, so the row the recording request returns already carries its frozen count, its penalty and `PENALTY_ASSESSED`, and its `version` is 1 with `updated_at` equal to `created_at`. The licensee row itself is not written at this hop — its `balance_cents` and `dyed_violation_count` are computed on read, per §2.4 — so the licensee's own `version` advances only if hop two actually suspends it. Hop two fires only if that new count reaches the suspension threshold of 2 **and** the licensee's `status` is `ACTIVE`: the licensee is driven to `SUSPENDED`. Hop three follows from the suspension: `required_bond_cents` is re-derived with the 2.0 suspension multiplier of §2.7, and `bond_deficiency_cents` with it. Hop four follows from the deficiency: if `bond_deficiency_cents` is now greater than zero, the licensee's `SUBMITTED` and `REVIEWED` refund claims move to `HELD` with `hold_reason` `BOND_DEFICIENCY` and their prior status preserved in `status_before_hold`. A licensee that is already suspended, or whose doubled bond requirement is still fully covered by posted bonds, simply stops the chain early — the hops are conditional, not unconditional.

**Dismissal, and what it deliberately does not undo.** A `TaxSupervisor` may dismiss an inspection whose `status` is `PENALTY_ASSESSED`, supplying a `dismissal_reason`; from `RECORDED` or `DISMISSED` the request fails with `ERR_INSPECTION_NOT_DISMISSIBLE` (HTTP 409). The `FieldInspector` that recorded the stop has no dismissal authority at all. Dismissal sets `status` to `DISMISSED`, records the supplied reason on the inspection as `dismissal_reason` (a field the representation carries, null until then, and the inspection's `version` advances to 2 because this is a genuine mutation of an existing row), appends a `PENALTY_REVERSAL` ledger entry for the negative of `penalty_cents` — a compensating entry, never a deletion or mutation of the original `PENALTY` row — and re-derives `balance_cents` back to exactly its pre-penalty value, which is what keeps Invariant M exact. The licensee's `dyed_violation_count` decreases by one.

What dismissal does **not** do is undo the licensee-level consequences. A suspended licensee is not auto-reinstated, so `required_bond_cents` keeps its 2.0 multiplier and any held refund claims stay held. Reinstatement is a separate, deliberate act by a `LicensingOfficer`, and it is itself gated: a licensee whose `dyed_violation_count` still stands at 2 or more cannot be reinstated at all, and the attempt fails with `ERR_DYED_VIOLATION_HOLD` (HTTP 422). The only route back to `ACTIVE` for a twice-caught licensee is therefore to dismiss enough inspections to bring the count below the threshold and then activate — money reversal and status reversal are two independent decisions made by two different desks.

### 3.9. Audit Selection, Casework, Assessment and Collection

**Two defensible readings of the same history.** The risk profile of a licensee can be read individually by an `AuditManager`, `TaxSupervisor` or `ReturnsExaminer`, and the read deliberately returns **both** scoring variants side by side together with the inputs that produced them: `risk_score_variance_weighted`, `risk_score_frequency_weighted`, `unreported_gallons_total`, `open_discrepancy_count`, `late_filing_count`, `dyed_violation_count`, and `audit_selection_threshold`, the selection cut-off of 60 points.

Both variants share two behaviour terms. Late-filing points are 8 points per unit of `late_filing_count`, capped at 24. Dyed-fuel points are 15 points per unit of `dyed_violation_count`, capped at 30. The variants differ only in how the cross-match signal is weighted. The variance-weighted reading measures **magnitude**: the licensee's `unreported_gallons_total` divided by 500 gallons per point, rounded half up to a whole number and then capped at 60. The frequency-weighted reading measures **count**: 6 points per unit of `open_discrepancy_count`, capped at 60. Each variant is then the sum of its cross-match term plus the two shared behaviour terms, capped at 100. The rounding happens before the cap, not after.

The input sets behind the two cross-match terms are not the same, which is why the readings can disagree so sharply. Both look only at discrepancies whose `distributor_licensee_id` is this licensee. The magnitude term uses discrepancies whose `direction` is `UNREPORTED_BY_PURCHASER` and whose `status` is neither `WRITTEN_OFF` nor `RESOLVED_EXPLAINED`. The count term counts discrepancies whose `status` is `OPEN`, `INQUIRY_SENT` or `RESPONSE_RECEIVED`, regardless of direction. Consider a licensee with three open discrepancies of 9999.00 gallons each: the magnitude reading gives 29997 divided by 500, which rounds to 60 and caps at 60, clearing the selection threshold on its own; the frequency reading gives 3 times 6, or 18 points, and the identical licensee is not selectable at all. Neither number is wrong — the state simply has to choose which theory of risk it is auditing under, and it records that choice on the case.

**Opening a case.** An `AuditManager` opens a case naming `subject_licensee_id`, a `selection_method` of `RISK_SCORE`, `CROSS_MATCH_ESCALATION` or `ROADSIDE_REFERRAL`, a `period_start_month`, a `period_end_month` no earlier than the start, optionally a `risk_score_variant` of `VARIANCE_WEIGHTED` (the default) or `FREQUENCY_WEIGHTED`, and optionally a `source_discrepancy_id`. A `period_end_month` earlier than `period_start_month` is refused with `ERR_DATE_RANGE_INVALID` (HTTP 422), and that ordering test runs immediately before the buffered-overlap rule below; a single-month span, where the two are equal, is legal. The subject's own `status` is never consulted — a case may be opened against a `PENDING_BOND`, `SUSPENDED` or even `REVOKED` licensee, because an audit of closed periods has to survive the loss of the licence.

`risk_score_variant` is consulted only when `selection_method` is `RISK_SCORE`; for the other two methods it is ignored for scoring but still stored — whichever variant the request named, or `VARIANCE_WEIGHTED` when it named none, is recorded verbatim on the case and echoed back on every read. Under `RISK_SCORE` the subject's score in the chosen variant must reach 60 points, and a subject below the threshold is refused with `ERR_RISK_SCORE_BELOW_THRESHOLD` (HTTP 422). `selection_score` freezes the score of the chosen variant on the case, and is 0 for any method other than `RISK_SCORE` — the frozen figure documents why the case was opened even after the underlying discrepancies are worked and the live score moves.

When `source_discrepancy_id` is supplied, three things must hold together: `selection_method` must be `CROSS_MATCH_ESCALATION`; the discrepancy's escalation subject — its `distributor_licensee_id` when `direction` is `UNREPORTED_BY_PURCHASER`, otherwise its `supplier_licensee_id` — must equal the requested `subject_licensee_id`; and the discrepancy's `status` must be `OPEN`, `INQUIRY_SENT` or `RESPONSE_RECEIVED`, since a discrepancy already at `ESCALATED_TO_AUDIT` cannot seed a second case. Any failure is refused with `ERR_DISCREPANCY_SOURCE_MISMATCH` (HTTP 422).

**The buffered overlap rule.** No other non-closed case for the same subject may cover an overlapping period, and the comparison is deliberately generous: each window is widened by one month on **both** ends and the two widened windows are then compared **inclusively** at both ends, so windows separated by a single empty month still collide while a two-month gap does not. A non-closed case covering 2026-03 through 2026-04 therefore blocks a new case for 2026-05, because the first widens to 2026-02 through 2026-05 and the second to 2026-04 through 2026-06. A violation is refused with `ERR_AUDIT_PERIOD_OVERLAP` (HTTP 422). Closed cases never block anything.

A new case starts with `case_status` `OPEN`, `assessment_status` `NONE`, `response_rounds` 0, `additional_tax_cents` 0, `evasion_indicator` false, `assessment_penalty_cents`, `assessment_interest_cents` and `assessed_total_cents` all 0, `assessed_by_user_id`, `protest_grounds` and `abatement_reason` null, and `opened_by_user_id` set to the acting `X-User-ID`. Opening the case increments the subject's `open_audit_count` and, because that count is now positive, moves the subject's `SUBMITTED` and `REVIEWED` refund claims to `HELD` with `hold_reason` `OPEN_AUDIT`. Cases may be read individually and listed filtered by `subject_licensee_id`, `case_status`, `assessment_status`, `source_discrepancy_id` and `selection_method` — the `source_discrepancy_id` filter being how an examiner finds the case a particular escalation created. The owning licensee of an audit case is its `subject_licensee_id`, so the single read is scope-checked and the list silently narrowed for a `LicenseeAgent` exactly as §2.1 prescribes — which is what lets the audited taxpayer, and only the audited taxpayer, read and protest its own case.

**Two dimensions on one row.** `case_status` and `assessment_status` advance independently, and the implementation must not treat either as a function of the other. An `AuditManager` drives the case dimension by supplying a `to_status`: `OPEN` to `FIELDWORK`, `FIELDWORK` to `PRELIM_FINDINGS`, `PRELIM_FINDINGS` to `TAXPAYER_RESPONSE`, `TAXPAYER_RESPONSE` back to `FIELDWORK` for another round, and `PRELIM_FINDINGS` to `CLOSED`. Any other combination of current status and requested `to_status` is refused with `ERR_AUDIT_CASE_STATE_INVALID` (HTTP 409) — while a `to_status` outside the five recognized case statuses is the band-4 `ERR_INVALID_REQUEST` instead, since it never reaches the edge test — and once `case_status` is `CLOSED` no action against the case is accepted at all: an advance, an assessment, an abatement, a protest and a finalization addressed to a closed case are all refused with that same `ERR_AUDIT_CASE_STATE_INVALID`, and on the four assessment-dimension endpoints the closed-case test is evaluated ahead of every test on `assessment_status`. The cycle back into fieldwork is bounded: `response_rounds` must be below 2 before the case may re-enter `FIELDWORK` from `TAXPAYER_RESPONSE`, and each traversal of that edge increments it, so a third attempt fails with `ERR_AUDIT_ROUND_LIMIT` (HTTP 422).

Closing the case is the one and only place the two dimensions are coupled: `assessment_status` must be `NONE`, `FINAL` or `ABATED`. An assessment still sitting at `ISSUED` or `PROTESTED` must be finalized or abated before the case can close, and a premature closure is refused with `ERR_ASSESSMENT_PENDING_DISPOSITION` (HTTP 409). Closure decrements the subject's `open_audit_count`, and when that count reaches zero, every refund claim of that licensee at `HELD` with `hold_reason` `OPEN_AUDIT` reverts to its `status_before_hold`. A subject under two concurrent audits therefore keeps its claims held until the second case also closes.

**Issuing the assessment.** A `TaxSupervisor` issues the deficiency assessment, supplying `additional_tax_cents` and `evasion_indicator`. The case's `assessment_status` must be `NONE` — one assessment per case, and a second issuance is refused with `ERR_ASSESSMENT_ALREADY_ISSUED` (HTTP 409) rather than replacing the first — and `case_status` must be `PRELIM_FINDINGS` or `TAXPAYER_RESPONSE`, or the request fails with `ERR_AUDIT_CASE_STATE_INVALID`. The acting `X-User-ID` must differ from `opened_by_user_id`: the manager who opened a case may not also assess it, and the attempt is refused with `ERR_ASSESSMENT_SEGREGATION_VIOLATION` (HTTP 422). Those four guards are evaluated in a fixed order — the closed-case test first, then the already-issued test, then the `case_status` test, then segregation — so a closed case that already carries a `FINAL` assessment reports `ERR_AUDIT_CASE_STATE_INVALID` rather than `ERR_ASSESSMENT_ALREADY_ISSUED`.

The amounts are computed as follows, each component rounded once. `assessment_penalty_cents` is `additional_tax_cents` multiplied by 0.50 when `evasion_indicator` is true and by 0.10 when it is false, rounded half up. Interest runs from the original statutory due date of the audited span's last period — the 20th day of the month following `period_end_month`, at 23:59:59Z — to the logical clock at issuance: the elapsed time is divided into whole days and truncated **down**, with a floor of zero days if the clock has not yet passed that date, and `assessment_interest_cents` is `additional_tax_cents` multiplied by the daily interest rate of 0.00025 and by that number of days, rounded half up. Interest never accrues on the penalty. `assessed_total_cents` is the integer sum of `additional_tax_cents`, `assessment_penalty_cents` and `assessment_interest_cents`. Note the difference from return filing: here the day count truncates downward, whereas a late return's `days_late` rounds upward.

Issuance sets `assessment_status` to `ISSUED` and `assessed_by_user_id` to the acting `X-User-ID`, then appends an `ASSESSMENT` ledger entry for the positive `assessed_total_cents` naming the case as its source and re-derives the subject's `balance_cents`. That entry is appended unconditionally, even when `additional_tax_cents` was 0 and the assessed total is therefore 0 as well. The ledger movement is a consequence of the assessment being recorded, not an independent step.

**Protest, finalization and abatement.** The audited licensee's own `LicenseeAgent` protests an `ISSUED` assessment by supplying `protest_grounds`; `assessment_status` becomes `PROTESTED` and the ledger is deliberately left untouched, because a protest suspends collection but does not extinguish the liability. A `TaxSupervisor` finalizes from `ISSUED` or `PROTESTED`, setting `assessment_status` to `FINAL` and again leaving the ledger unchanged — the liability was already posted; finalization only makes it collectible. Protest is `ISSUED`-only, so the same assessment cannot be protested twice, and finalization is the one action of the three that takes no body fields at all and enforces no segregation rule of its own. An `assessment_status` that does not admit the requested action — protesting anything but an `ISSUED` assessment, or finalizing one still at `NONE` or already `FINAL` or `ABATED` — is refused with `ERR_AUDIT_CASE_STATE_INVALID` (HTTP 409).

Abatement, available from `ISSUED` or `PROTESTED` and from no other `assessment_status` — an attempt from `NONE`, `FINAL` or `ABATED` is refused with `ERR_AUDIT_CASE_STATE_INVALID` (HTTP 409) — is the compensating counterpart of issuance. It takes an `abatement_reason`, sets `assessment_status` to `ABATED`, appends an `ABATEMENT` ledger entry for the negative of `assessed_total_cents` naming the case as its source, and re-derives `balance_cents` back to exactly its pre-assessment value — with both ledger rows retained, because the ledger is append-only. Abatement is always in full; partial abatement is not offered. That absoluteness creates one guard: an abatement is refused with `ERR_ABATEMENT_AMOUNT_INVALID` (HTTP 422) when the licensee's `balance_cents` is below `assessed_total_cents`, because a payment has already retired part of the assessed liability and reversing the full amount would push the balance below its pre-assessment value and mint a credit the state does not owe. Abatement also carries its own segregation rule: the acting `X-User-ID` must differ from `assessed_by_user_id`, and a supervisor abating its own assessment is refused with `ERR_ASSESSMENT_SEGREGATION_VIOLATION`. Abatement's guards run in the order closed-case, then `assessment_status`, then segregation, then the balance test, so a supervisor addressing its own already-abated assessment reports `ERR_AUDIT_CASE_STATE_INVALID`.

**Collection.** A `TaxSupervisor` records a remittance received from a licensee with `amount_cents`, an `effective_date`, and an optional `memo`. The amount must be greater than zero and must not exceed the licensee's current `balance_cents`, since no credit balances are created through payments; a violation is refused with `ERR_PAYMENT_EXCEEDS_BALANCE` (HTTP 422). The request appends a `PAYMENT` ledger entry for the **negative** of the submitted `amount_cents` — the submitted figure is a positive remittance, the posted figure is a negative charge — with `source_entity_type` `Payment`, a null `source_entity_id` and the submitted `effective_date` written onto the row, re-derives `balance_cents`, and increments the licensee's `version`. The created ledger entry, not the licensee, is the resource returned, and because a row is created the status code is 201.

**Reading the ledger.** A licensee's ledger is listed in `created_at` order and may be filtered by `entry_type`, which is how a reader isolates, for example, the `PENALTY` rows from their `PENALTY_REVERSAL` counterparts, or an `ASSESSMENT` from its `ABATEMENT`. Ledger rows carry `licensee_id`, `entry_type`, `amount_cents`, `source_entity_type`, `source_entity_id`, `effective_date` and `memo`, and — as noted in §2.4 — only `id` and `created_at` beyond that. Both parties to every compensating pair remain visible forever, which is what lets an examiner reconstruct not just the current balance but the entire history that produced it.
