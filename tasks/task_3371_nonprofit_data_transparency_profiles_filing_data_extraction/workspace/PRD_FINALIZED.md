# Nonprofit Data Transparency API — Product Requirements Document

## 1. Introduction

The nonprofit sector's public record is fragmented. A foundation that wants to understand a prospective grantee must reconcile a self-reported profile, a stack of information returns printed on different tax-form versions, a leadership roster that changes every year, and a grant history spread across dozens of funders' own spreadsheets. This document specifies the API that closes that gap: a single service through which nonprofit organizations publish verified profiles, through which public filings are extracted and normalized into comparable figures, and through which funders, researchers and platforms license the resulting data under explicit permitted-use terms.

The system is built around a tension that runs through every rule below. Organizations want to present themselves in the best possible light, so the platform separates what an organization *claims* from what has been *evidenced*, and publishes a completeness score that depends on which of the two it is reading. Funders want certainty of identity, so the platform tracks legal-name changes, mergers and dissolutions as first-class workflow objects with their own audit trail rather than as edits to a name column. Regulators and the public want disclosure, so the platform measures how much of a profile is actually public and gates a tiered transparency seal on that measurement — a seal that lapses if it is not renewed and is revoked the moment the underlying disclosure falls away.

Everything in this document is deterministic. There is no wall-clock time in the system: the server starts with a fixed logical clock and every deadline, expiry, window and lapse rule is evaluated against that clock, which only an operator can advance. Every monetary quantity is an integer number of cents. Every derived aggregate is recomputed by an explicitly pinned evaluation order, and every rejection carries a named error identifier that the client can branch on.

## 2. Global Specifications & System-Wide Principles

This section collects the rules that apply across the whole API: who may act, what a response looks like, how time and money are represented, how stale writes are refused, and how the server reconciles derived state when a write lands.

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers. `X-User-ID` identifies the acting user, and `X-User-Role` names the capacity in which that user is acting. If either header is absent, or if `X-User-Role` does not name one of the four declared roles, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401) before any other consideration. If the headers are well formed but the named role is not in the endpoint's authorized role list, the request is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The declared roles are `OrganizationUser`, `PlatformVerifier`, `DataConsumer`, and `PlatformAdmin`.

When `X-User-Role` is `OrganizationUser`, `X-User-ID` is the `id` of the acting `Organization`; ownership checks on any resource that references an `Organization` compare the resource's foreign-key field to `X-User-ID`. This is why an `OrganizationUser` may edit only its own profile and may file correction requests only against extracted data belonging to its own organization. When `X-User-Role` is `DataConsumer`, `X-User-ID` is likewise the `id` of the acting `Organization` — the funder, researcher or platform that holds or is requesting the license — and ownership checks compare the resource's `licensee_organization_id` or `funder_organization_id` to `X-User-ID`. When `X-User-Role` is `PlatformVerifier`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a transition writes it (for example as `decided_by_user_id` on a `CorrectionRequest`) but never compares it to any entity's `id`. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is likewise an opaque operator identifier, recorded where a transition writes it and never matched against an entity `id`.

Two rules cut across roles. First, an `OrganizationUser` acting on a resource that does not belong to its own organization is refused with `ERR_FORBIDDEN_ROLE`. Second, the platform separates duties between the people who author data and the people who verify it; the specific gates are described in §2.6.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` query parameter giving the maximum number of items to return, and an `offset` query parameter giving the number of items to skip. When `limit` is omitted it defaults to 10; the smallest accepted value is 1 and the largest accepted value is 100. When `offset` is omitted it defaults to 0.

Unless a more specific ordering rule is stated for a particular collection, list endpoints return resources ordered by their creation timestamp ascending, and ties are broken deterministically so that repeated reads of an unchanged collection return the same order.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the response envelope, alongside `api_request_id` and `api_request_timestamp`. `total_count` is the number of resources matching the filter across all pages, not the number in the current page, and `has_more` is true exactly when `offset` plus the number of items in the current page is less than `total_count`.

### 2.4. The Logical Clock and Temporal Evaluation

The server never reads wall-clock time. It starts with its logical clock fixed at `2026-09-01T00:00:00Z`, and until an operator advances it, every deadline, expiry, window, lapse and term rule in this document is evaluated against that instant. An admin-only test-driving capability sets the clock to a supplied `current_utc` instant; the request body field is `current_utc` and the response echoes the new instant. Advancing the clock re-evaluates every date-sensitive rule against the new instant — seal expiry and lapse, license term windows, renewal windows and correction timestamps all move together.

Because the clock is the only source of "now", rules phrased as "already lapsed" or "not yet due" are statements about the logical clock's current value, not about elapsed real time. Two consequences matter operationally. A seal whose `expires_on` plus 90 days is behind the current clock is already `LAPSED` and is treated as such by any rule that inspects it. A usage event posted while the clock sits outside a license's `[term_start, term_end)` window is refused, even if the wall clock would have permitted it.

### 2.5. Profile Records, Identifiers and Common Resource Properties

Every entity in this system — `Organization`, `Program`, `Filing`, `ExtractedField`, `LeadershipMember`, `DemographicRecord`, `TransparencySeal`, `Grant`, `DataLicense`, `LicenseUsageEvent`, `CorrectionRequest` and `IdentityResolutionCase` — carries the same four system-managed properties.

- `id` is a server-minted UUID string with no type prefix. Identifiers are opaque; no rule in this document ever ranks, sorts or breaks a tie by identifier value.
- `created_at` is an ISO 8601 UTC timestamp with three fractional digits, set once when the row is created and never changed.
- `updated_at` is an ISO 8601 UTC timestamp with three fractional digits, refreshed whenever the row is mutated, including mutations performed by an automatic cascade rather than by a direct client request.
- `version` is a non-negative integer that starts at 1 and increments by 1 on every mutation of the row. It is the field that optimistic concurrency control reads, as described in §2.9.

Every entity in this version of the API carries all four properties; no entity omits `updated_at` or `version`. When this document says that an operation "increments" a row's version, that increment is accompanied by a refresh of `updated_at`, whether or not the sentence repeats it.

Child rows hang off their parents through ordinary foreign-key fields rather than through nested payloads: a `Program`, `LeadershipMember`, `DemographicRecord`, `Filing`, `TransparencySeal`, `Grant`, `DataLicense` and `CorrectionRequest` each carry the `organization_id` of the organization it belongs to; an `ExtractedField` carries the `filing_id` of its filing; a `LicenseUsageEvent` carries the `license_id` of its license; and an `IdentityResolutionCase` carries the `subject_organization_id` of the organization whose identity it resolves. Creating a child row does not, by itself, advance the parent organization's `version` — only the transitions and cascades that explicitly say so do.

### 2.6. Verification Standing and Segregation of Duties

The platform draws a hard line between the person who authors a record and the person who certifies it. On verification of an organization profile, the acting `X-User-ID` must differ from the organization's `last_profile_editor_user_id` — the identifier of the actor that created or last patched the profile — and a request from the same actor is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). On the adjudication of a correction request, the deciding `X-User-ID` must differ from the request's `submitted_by_user_id`, and again a match is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). A `PlatformVerifier` who edited a profile can never be the verifier who advances it, and an organization can never approve its own correction.

Verification itself is a single step at a time. A verification request carries a `target_level`, and that value must be exactly the next level above the organization's current `verification_level`; any other value — including a repeat of the current level, a skip over one level, or a step backwards — is refused with `ERR_VERIFICATION_STEP_INVALID` (HTTP 409). The three levels form the ordered ladder `SELF_REPORTED`, then `DOCUMENT_VERIFIED`, then `INDEPENDENTLY_AUDITED`, and the level never decreases once advanced.

Good standing is a precondition for several operations, and it is refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403). A filing may be extracted or normalized only while its owning organization's `profile_status` is `DRAFT` or `ACTIVE`. A license may be activated only while the licensee organization's `profile_status` is `ACTIVE`. A transparency seal may be awarded only while the organization named in the request is `ACTIVE`, and a seal may be renewed only while its owning organization's `profile_status` is `ACTIVE`. An organization that is `SUSPENDED`, `MERGED` or `DISSOLVED` therefore fails every one of these gates.

The organization's standing is itself partly automatic. An organization's `open_correction_count` is the number of its correction requests sitting in `SUBMITTED` or `UNDER_REVIEW`. When that count reaches 3, the organization's `profile_status` moves to `SUSPENDED` without any client request, and every one of its `ACTIVE` transparency seals is revoked. An organization in `SUSPENDED` standing can be returned to `ACTIVE` only by a verifier, and only while its `open_correction_count` is less than 3; a request made while the count is 3 or more is refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403).

### 2.7. Taxonomy Reference Data and Closed Sets

Two of the system's checks are pure membership tests against closed tables, and both are refused with a status of 422 when they fail.

The first governs which line codes may be extracted from a return. Every filing declares a `form_version_year`, and the set of legal line codes depends on it. The closed table is:

| `form_version_year` | Permitted `line_code` values |
| --- | --- |
| 2019 | `TOTREV`, `PROGREV`, `CONTRIB`, `SALARIES`, `OCCUPANCY`, `PROF_FUNDRAISING` |
| 2020 | `TOTREV`, `PROGREV`, `CONTRIB`, `SALARIES`, `OCCUPANCY`, `PROF_FUNDRAISING`, `GOV_GRANTS` |
| 2021 | `TOTREV`, `PROGREV`, `CONTRIB`, `SALARIES`, `OCCUPANCY`, `PROF_FUNDRAISING`, `GOV_GRANTS` |
| 2022 | `TOTREV`, `PROGREV`, `CONTRIB`, `SALARIES`, `OCCUPANCY`, `PROF_FUNDRAISING`, `GOV_GRANTS`, `NET_ASSETS` |
| 2023 | `TOTREV`, `PROGREV`, `CONTRIB`, `SALARIES`, `OCCUPANCY`, `PROF_FUNDRAISING`, `GOV_GRANTS`, `NET_ASSETS` |
| 2024 | `TOTREV`, `PROGREV`, `CONTRIB`, `SALARIES`, `OCCUPANCY`, `PROF_FUNDRAISING`, `GOV_GRANTS`, `NET_ASSETS`, `CRYPTO_HOLDINGS` |

The supported version years are exactly 2019, 2020, 2021, 2022, 2023 and 2024. A filing whose `form_version_year` falls outside that set, or an extraction request supplying any `line_code` that is not a member of the row for the filing's declared version, is refused with `ERR_UNSUPPORTED_FORM_VERSION` (HTTP 422). Note the asymmetry this creates: `GOV_GRANTS` does not exist before version 2020 and `CRYPTO_HOLDINGS` does not exist before version 2024, so the identical line code is valid against one version year and rejected against another. The permitted sets are not cumulative by accident — each year's row is the authority for that year.

The second closed set governs data licensing. A license carries a `tier` and a `permitted_use`, and activation succeeds only when the `permitted_use` is a member of the set belonging to that `tier`:

| `tier` | Permitted `permitted_use` values |
| --- | --- |
| `RESEARCHER` | `AGGREGATE_RESEARCH` |
| `FUNDER` | `AGGREGATE_RESEARCH`, `GRANTMAKING_DUE_DILIGENCE` |
| `PLATFORM` | `AGGREGATE_RESEARCH`, `GRANTMAKING_DUE_DILIGENCE`, `PLATFORM_REDISTRIBUTION`, `MARKETING_PROSPECTING` |

A request whose `permitted_use` is not a member of its tier's set is refused with `ERR_PERMITTED_USE_NOT_IN_TIER` (HTTP 403). The sets are nested in the sense that a `PLATFORM` license may do everything a `FUNDER` license may do, but the check is performed against the tier's own row, not against a union.

### 2.8. Precision, Rounding and Integer-Cents Arithmetic

All monetary quantities in this API are integer numbers of cents. Fees, revenues, compensation and grant amounts are never fractional and are never returned as decimal strings. When a computation begins from a decimal value — most often a `raw_value` printed on a tax return — the conversion to cents happens once, at the point the field is normalized, and the rounded integer is what every downstream aggregation consumes.

The single rounding primitive used throughout the system is round half up: an exact one-half fraction rounds away from zero. Rounding is never deferred. The sum-then-round shortcut is explicitly rejected: revenue components are each converted to cents and rounded individually, and only then summed as integers with no second rounding. The difference is observable. A filing with one revenue line whose `raw_value` is `1234.005` and `raw_format` is `USD_WHOLE` contributes 123401 cents, and a second line whose `raw_value` is `5678.005` and `raw_format` is also `USD_WHOLE` contributes 567801 cents; the filing's `total_revenue_cents` is 691202. Adding the two raw dollar figures first and rounding once at the end would produce 691201, and that result is wrong.

Score fields are integers on a bounded scale. Both `provisional_completeness_score` and `verified_completeness_score` are integers between 0 and 100 inclusive, produced by rounding the weighted sum to a whole number half up and then clamping into that range; `profile_completeness_score` publishes one of those two integers and is therefore also an integer from 0 to 100. `match_score` is an integer from 0 to 100 inclusive, capped at 100 when the accumulated points would exceed it. `confidence_pct` values are decimals expressed to one decimal place. `disclosure_pct` is a decimal rounded half up to exactly 4 decimal places. `disclosure_pct_at_award` captures the organization's `disclosure_pct` at the moment of the award and is likewise a 4-decimal value.

### 2.9. Optimistic Concurrency Control

Two write operations in this API are guarded by optimistic concurrency control, and both are guarded by a *required* version field rather than an optional one.

Creating a filing requires `expected_organization_version`. The client supplies the `version` of the target organization as it last observed it, and the create succeeds only when that value equals the organization's current `version`. If another writer has advanced the organization's version since the client last read it, the request is refused with `ERR_STALE_ORGANIZATION_VERSION` (HTTP 412). This is a deliberate serialization point: creating a filing legitimately supersedes the prior revision for the same organization, tax year and form type, so a client whose view of the organization is stale is precisely the client that would otherwise supersede a revision it never saw.

Filing a correction request against an extracted field requires `expected_extracted_field_version`. The client supplies the `version` of the `ExtractedField` as it last observed it, and the create succeeds only when that value equals the field's current `version`. If another writer has corrected or re-normalized the field since the client last read it, the request is refused with `ERR_STALE_EXTRACTED_FIELD_VERSION` (HTTP 412) — the client is disputing a value that no longer exists.

Neither field is optional. A request that omits the relevant version field is not silently processed without the check. No other endpoint in this API takes a version field of this kind, and no other write is refused for staleness.

### 2.10. Nested Resource Retrieval and Validation Precedence

When a request path contains more than one resource identifier, the identifiers are validated for existence in left-to-right path order. The first identifier that does not resolve to a row produces the corresponding not-found error and nothing later in the path is examined. The order in which the not-found conditions are checked is therefore fixed: organization first, then filing, then extracted field, then license and usage event, then seal, grant, correction request and identity case. The corresponding identifiers are `ERR_ORGANIZATION_NOT_FOUND`, `ERR_FILING_NOT_FOUND`, `ERR_EXTRACTED_FIELD_NOT_FOUND`, `ERR_LICENSE_NOT_FOUND`, `ERR_USAGE_EVENT_NOT_FOUND`, `ERR_SEAL_NOT_FOUND`, `ERR_GRANT_NOT_FOUND`, `ERR_CORRECTION_REQUEST_NOT_FOUND` and `ERR_IDENTITY_CASE_NOT_FOUND`, each carrying HTTP 404.

Validation is not a flat set of independent checks; it is a ladder, and when two conditions hold at once the earlier rung wins and its error identifier is the one returned.

1. Authentication comes first. Missing or malformed `X-User-ID` / `X-User-Role` yields `ERR_UNAUTHENTICATED` (HTTP 401).
2. Authorization comes next. A role outside the endpoint's authorized set, or an `entity_backed` actor acting on a resource it does not own, yields `ERR_FORBIDDEN_ROLE` (HTTP 403).
3. Existence of every path identifier comes next, checked left to right, yielding the not-found identifiers listed above (HTTP 404).
4. Request shape comes next. Missing or ill-typed required body fields, body fields not declared in the endpoint's input list, unknown enum members, and out-of-range numerics — `record_count` below 1, `projected_annual_records` below 1, `evidence_count` below 1, or a `corrected_value` equal to the current value — all yield `ERR_INVALID_REQUEST` (HTTP 400). Body identifiers are resolved in the order the endpoint's input list declares them.
5. State comes next. A requested transition that is not declared for the resource's current state yields `ERR_INVALID_STATE` (HTTP 409). This rung includes the cross-entity gate on correction approval: the target extracted field's filing must be `NORMALIZED` or `DISPUTED`.
6. Business safety gates come next, in this order: the segregation-of-duties gates; the exact-one-step verification rule; the profile completeness floor of 50; the good-standing requirement that a filing's organization be `DRAFT` or `ACTIVE` for extraction and normalization; and the good-standing requirement that the organization be `ACTIVE` for license activation and seal award. These yield `ERR_SEGREGATION_OF_DUTIES`, `ERR_VERIFICATION_STEP_INVALID`, `ERR_PROFILE_INCOMPLETE` and `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403).
7. Business constraints come next, yielding HTTP 409: `ERR_EIN_ALREADY_REGISTERED`, `ERR_LICENSE_TERM_OVERLAP`, `ERR_LEADERSHIP_TERM_OVERLAP`, `ERR_FILING_COVERAGE_OVERLAP`, `ERR_MERGE_CYCLE_DETECTED` and `ERR_NO_EXTRACTED_FIELDS`.
8. The license record-quota gate comes next, yielding `ERR_QUOTA_EXCEEDED` (HTTP 402).
9. Reference-data membership comes next, yielding `ERR_UNSUPPORTED_FORM_VERSION` and `ERR_PERMITTED_USE_NOT_IN_TIER` (HTTP 422).
10. Temporal window gates come next, yielding `ERR_LICENSE_TERM_CLOSED` and `ERR_SEAL_LAPSED` (HTTP 409).
11. The seal disclosure floor and the single-active-seal rule come last, yielding `ERR_SEAL_DISCLOSURE_INSUFFICIENT` (HTTP 422) and `ERR_INVALID_STATE` (HTTP 409).

Read this ladder as an override order. An unauthenticated request never reports a not-found condition. A request from the wrong role never reports a missing body field. A request against a filing in the wrong state never reports a line-code membership failure.

### 2.11. Derived Aggregates and Cascade Reconciliation

Most of the numbers a client reads on an organization are not stored by the client and are not computed on demand from raw inputs; they are maintained aggregates that the server reconciles whenever a contributing row changes. This applies to `total_revenue_cents`, `latest_filing_tax_year`, `distinct_funder_count`, `active_license_count`, `open_correction_count`, `transparency_seal_level`, `seal_expires_on`, `provisional_completeness_score`, `verified_completeness_score`, `profile_completeness_score` and `disclosure_pct` on the organization, and to `total_revenue_cents`, `extracted_field_count`, `extraction_confidence_pct` and `is_verified` on a filing.

Reconciliation is immediate, not eventually consistent: the response to the request that triggered a change already reflects the recomputed values. A reconciliation that mutates an organization bumps the organization's `version` and refreshes its `updated_at`; a reconciliation that mutates a filing bumps the filing's `version` and refreshes its `updated_at`. Because several operations reconcile more than one aggregate at once, a single request can legitimately increment both a child row's version and its parent organization's version, and both increments are visible in the response.

Two aggregates deserve special mention because they are the only ones whose *decrease* has a cascading consequence. When a recomputed `profile_completeness_score` falls below 50 and the organization holds an `ACTIVE` transparency seal, that seal is revoked and `transparency_seal_level` returns to `NONE`. When a recomputed `disclosure_pct` falls below the disclosure floor of an `ACTIVE` seal's level, the same revocation occurs. Both cascades are described in full in §3.7.

## 3. Business Logic & Workflows

### 3.1. Organization Profiles and Self-Reported Records

A nonprofit enters the platform when a `PlatformAdmin` creates its profile. The mandatory attributes are the registered `legal_name`, the nine-digit `ein`, the `org_type` and the two-letter `state_code` of incorporation; the optional attributes are a public-facing `display_name`, an NTEE subject-area taxonomy code in `ntee_code`, a free-text `mission_statement`, and a declared `dissolution_date`. The `org_type` must be one of `501C3`, `501C4`, `501C6`, `501C7`, `527` or `OTHER`. The `ein` is globally unique across organizations — a create that supplies an `ein` already held by another organization is refused with `ERR_EIN_ALREADY_REGISTERED` (HTTP 409) and no row is written.

The row that results is deliberately bare. It opens in `DRAFT` profile status with `verification_level` of `SELF_REPORTED`, an empty `former_legal_names` array, `transparency_seal_level` of `NONE`, a null `seal_expires_on`, a null `latest_filing_tax_year`, a null `successor_organization_id`, and every derived counter — `verification_evidence_count`, `total_revenue_cents`, `distinct_funder_count`, `active_license_count` and `open_correction_count` — initialised to zero. The creating actor is recorded as `last_profile_editor_user_id`, which is the field the segregation-of-duties gate later reads.

From that point the organization's own staff maintain the narrative half of the profile. An `OrganizationUser` may patch its own organization (and a `PlatformAdmin` may patch any organization) by supplying `expected_organization_version` together with whichever of `display_name`, `ntee_code`, `mission_statement`, `legal_name` and `state_code` it wishes to change. Every patch records the acting `X-User-ID` as the new `last_profile_editor_user_id`, and every patch increments the organization's `version` by 1.

Programs, leadership and demographics are the three self-reported collections. A program is created with a `program_name` and the `fiscal_year` it describes, and may carry a `subject_code`, a free-text `population_served`, and a `disclosure_level`. The `disclosure_level` of a program, of a leadership member and of a demographic record is one of `PUBLIC`, `RESTRICTED` or `WITHHELD`; when a program or a leadership member is created without one, the server stores `RESTRICTED`. A program is born `ACTIVE` and unverified — `status` is `ACTIVE` and `is_verified` is false — and in this version of the API a program row is never archived, so `ACTIVE` is the only value its `status` can ever hold. Creating a program or a leadership member recomputes the organization's completeness and disclosure scores but does not advance the organization's `version`.

A leadership member is created with a `full_name`, an `office_title` and a `service_start`, and optionally a `service_end`. The service interval is closed at both ends and a null `service_end` means the term is open-ended. The boolean `is_officer` marks a voting officer and defaults to true when omitted; the boolean `is_independent` marks an independent voting board member and defaults to false; `compensation_cents` defaults to zero and is the reported annual compensation in cents. A new leadership row opens with `status` `ACTIVE` and `is_verified` false; `ACTIVE` and `ENDED` are the two members of that enum, but no operation in this version of the API moves a leadership member to `ENDED`, so `ACTIVE` is the only value the field can hold in practice and a departed leader is represented by a `service_end` in the past rather than by an `ENDED` status. Because the roster is a historical record, service intervals for the same organization and the same `office_title` may not collide: a create whose closed interval `[service_start, service_end]` touches or overlaps an `ACTIVE` row with the same `office_title` is refused with `ERR_LEADERSHIP_TERM_OVERLAP` (HTTP 409). Touching endpoints count as an overlap, so a term ending on the same day another begins is rejected. An open-ended row occupies its interval from `service_start` onward without limit.

Demographic records have no creation endpoint of their own. They are authored through the profile patch: when the patch carries a `demographic_records` array, the organization's entire existing demographic set is deleted and one `DemographicRecord` row is created for each element of the array. Each element carries a `category` — one of `RACE_ETHNICITY`, `GENDER_IDENTITY`, `AGE_BAND`, `LGBTQIA`, `DISABILITY` or `VETERAN` — a `value_code` within that category such as `BLACK_AFRICAN_AMERICAN`, `WOMAN` or `AGE_35_44`, a `disclosure_level`, and the `fiscal_year` the record describes. A demographic row is unverified on arrival and becomes verified when the organization supplies supporting evidence. This replacement semantics is the reason the demographic collection is the one collection whose membership can shrink: sending a shorter array than last time deletes the difference.

### 3.2. The Completeness and Disclosure Ledger

Two weighted scores summarise an organization, and the platform publishes whichever one its verification standing entitles it to.

The first is `provisional_completeness_score`, computed from self-reported rows regardless of whether any of them has been verified. It is the weighted sum of six dimension scores, each dimension scored on a 0.0 / 0.5 / 1.0 scale, with weights `PROGRAMS` 0.15, `FINANCES` 0.25, `LEADERSHIP` 0.20, `DEMOGRAPHICS` 0.15, `MISSION` 0.10 and `GOVERNANCE` 0.15. The `PROGRAMS` dimension counts programs whose `status` is `ACTIVE`: no rows scores 0.0; at least one row where at least one carries a non-null `subject_code` scores 1.0; at least one row with no `subject_code` anywhere scores 0.5. The `FINANCES` dimension counts filings whose `status` is `NORMALIZED` or `DISPUTED`: no rows scores 0.0; at least one `NORMALIZED` row with a non-null `total_revenue_cents` scores 1.0; anything else in between scores 0.5. The `LEADERSHIP` dimension counts `ACTIVE` leadership members: no rows scores 0.0; three or more officers (`is_officer` true) scores 1.0; one or two officers scores 0.5; otherwise 0.0. The `DEMOGRAPHICS` dimension counts demographic records: no rows scores 0.0; at least one row whose `disclosure_level` is `PUBLIC` scores 1.0; otherwise 0.5. The `MISSION` dimension scores 1.0 when the `mission_statement` is non-empty and `ntee_code` is non-null, 0.5 when exactly one of the two is present, and 0.0 when neither is. The `GOVERNANCE` dimension counts `ACTIVE` leadership members who are officers: three or more independents scores 1.0, one or two scores 0.5, none scores 0.0. The weighted sum is multiplied by 100, rounded half up to a whole number, and clamped into the range 0 to 100 inclusive.

The second is `verified_completeness_score`. It uses the same six weights and the same dimension membership, but every dimension is evidence-capped. `PROGRAMS` scores 1.0 only when at least one `ACTIVE` program row exists, every `ACTIVE` program row has `is_verified` true, and at least one of them carries a `subject_code`; it scores 0.5 when at least one `ACTIVE` program row exists but that 1.0 condition fails, and 0.0 when no `ACTIVE` program row exists. `FINANCES` scores 1.0 only when at least one filing is `NORMALIZED` and `is_verified`; 0.5 when at least one filing is `NORMALIZED` or `DISPUTED` but the 1.0 condition fails; 0.0 when no such filing exists. `LEADERSHIP` scores 1.0 only when there are at least three `ACTIVE` officer rows and every one of them is verified; 0.5 when at least one `ACTIVE` leadership row exists but the 1.0 condition fails; 0.0 when none exists. `DEMOGRAPHICS` scores 1.0 only when at least one demographic row is both `PUBLIC` and verified; 0.5 when at least one demographic row exists but the 1.0 condition fails; 0.0 when none exists. `MISSION` scores 1.0 only when the `mission_statement` is non-empty, `ntee_code` is non-null, and `ntee_code_verified` is true; 0.5 when the mission statement is non-empty or the NTEE code is present but the 1.0 condition fails; 0.0 when neither is present. `GOVERNANCE` scores 1.0 only when there are at least three `ACTIVE` independent officers and every `ACTIVE` officer row is verified; 0.5 when at least one `ACTIVE` officer row exists but the 1.0 condition fails; 0.0 when none exists. The weighted sum is again multiplied by 100, rounded half up, and clamped to 0 through 100.

The published value, `profile_completeness_score`, is the verified score when the organization's `verification_level` is `DOCUMENT_VERIFIED` or `INDEPENDENTLY_AUDITED`, and the provisional score while the organization remains `SELF_REPORTED`. This is not cosmetic. Consider an organization holding one verified program with a subject code, one verified normalized filing, three verified officers of whom three are independent, one public verified demographic row, and a mission statement with a verified NTEE code: every dimension scores 1.0, the provisional score is 100, and the verified score is also 100. Now consider the same underlying rows with the evidence withheld — the program unverified, the filing unverified, the officers unverified, the demographic row unverified, the NTEE code unconfirmed. The provisional score remains 100, because the provisional calculation ignores verification entirely; the verified score is 50, because every dimension falls to its 0.5 rung. An organization that advances from `SELF_REPORTED` to `DOCUMENT_VERIFIED` therefore watches `profile_completeness_score` drop from 100 to 50 without a single underlying row changing. Verification is not a reward that raises the published number; it is a lens that exposes how much of the number was evidenced.

The disclosure measure is separate and answers a different question: how much of the profile is actually public. `disclosure_pct` is the weighted sum of six disclosure dimensions, with weights `PROGRAMS` 0.15, `FINANCES` 0.30, `LEADERSHIP` 0.20, `DEMOGRAPHICS` 0.15, `MISSION` 0.10 and `GOVERNANCE` 0.10, rounded half up to 4 decimal places. The `PROGRAMS` dimension scores 1.0 when at least one `ACTIVE` program has `disclosure_level` `PUBLIC`, 0.5 when at least one program row exists and none is public, and 0.0 when no row exists. The `FINANCES` dimension scores 1.0 when at least one filing is `NORMALIZED` — information returns are public by law — 0.5 when filings exist and none is normalized, and 0.0 when no filing exists. The `LEADERSHIP` dimension scores 1.0 when at least one `ACTIVE` leadership member is `PUBLIC`, 0.5 when leadership rows exist and none is public, and 0.0 when there is no `ACTIVE` leadership member. The `DEMOGRAPHICS` dimension scores 1.0 when at least one demographic record is `PUBLIC`, 0.5 when demographic rows exist and none is public, and 0.0 when none exists. The `MISSION` dimension scores 1.0 when the `mission_statement` is non-empty and `ntee_code` is non-null, 0.5 when exactly one is present, and 0.0 when neither is. The `GOVERNANCE` dimension scores 1.0 when at least one `ACTIVE` leadership member is both independent and `PUBLIC`, 0.5 when at least one `ACTIVE` officer row exists, and 0.0 otherwise. An organization that publishes its programs, has one normalized filing, a public leadership roster, a public demographic row, a complete mission block and at least one independent public officer reaches `disclosure_pct` 0.9000; the same organization with its governance dimension reduced to the 0.5 rung and its demographics withheld lands at 0.8500. Those two values straddle the `PLATINUM` disclosure threshold, which is exactly why the seal rules in §3.7 read this number so closely.

Both scores are recomputed whenever a program, filing, leadership member, demographic record or organization mission/taxonomy field changes, and the recomputation is part of the response to the request that triggered it.

### 3.3. Verification Advancement and the Standing Gate

A `PlatformVerifier` advances an organization's `verification_level` one rung at a time. The request carries a `target_level` and an `evidence_count`. The evidence count must be at least 1; a smaller value is refused as a malformed request with `ERR_INVALID_REQUEST` (HTTP 400).

Three gates are evaluated in a fixed order, and the first one to fail determines the error the caller sees. The first gate is the segregation of duties: the acting `X-User-ID` must differ from the organization's `last_profile_editor_user_id`, and a match is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The second gate is the step rule: `target_level` must be exactly the next level above the current `verification_level` on the ladder `SELF_REPORTED` → `DOCUMENT_VERIFIED` → `INDEPENDENTLY_AUDITED`, and any other value is refused with `ERR_VERIFICATION_STEP_INVALID` (HTTP 409). The third gate applies only when the organization is still in `DRAFT` profile status: `profile_completeness_score`, evaluated before the transition is applied, must be at least 50, and a lower score is refused with `ERR_PROFILE_INCOMPLETE` (HTTP 409). An organization that is already `ACTIVE` does not face this third gate, so a second and third verification step are governed only by the duties gate and the step rule.

A successful verification does more than move one field. The `verification_level` advances exactly one step; `verification_evidence_count` increases by the supplied `evidence_count`; the organization's `profile_status` moves from `DRAFT` to `ACTIVE` when it was `DRAFT` and the completeness floor was met; and the published `profile_completeness_score` is recomputed under the new verification level, which — per §3.2 — may lower it. The advance also sweeps the organization's existing self-reported records: every `Program`, `LeadershipMember` and `DemographicRecord` row that existed before the call has its `is_verified` flag set to true, and `ntee_code_verified` is set to true. Rows created after the call are not swept and remain unverified until a later advance. Finally, the organization's `version` is incremented by 1.

Suspension has its own exit. An organization in `SUSPENDED` profile status returns to `ACTIVE` through the same verification capability, but with a different gate: the request is accepted only while the organization's `open_correction_count` is less than 3, and is otherwise refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403). This return path does not advance the verification level, does not add evidence, and does not sweep records; it only restores `profile_status` to `ACTIVE` and increments the organization's `version` by 1. The suspension itself is automatic: when the organization's `open_correction_count` reaches 3, `profile_status` moves to `SUSPENDED` with no client request, every one of the organization's `ACTIVE` transparency seals is revoked, `transparency_seal_level` returns to `NONE`, `seal_expires_on` becomes null, and the organization's `version` is incremented by 1.

### 3.4. Information Returns: Revision Creation and Line Extraction

An information return enters the system as a filing revision. An `OrganizationUser` (for its own organization) or a `PlatformAdmin` submits the `organization_id`, the `form_type`, the `form_version_year`, the `tax_year` the return covers, a `coverage_start` and `coverage_end` bounding the fiscal period, and a `source` naming where the document came from — `IRS_BULK_XML`, `ORG_UPLOAD` or `MANUAL_ENTRY`. The `form_type` is one of `FORM_990`, `FORM_990_EZ` or `FORM_990_PF`, and the `form_version_year` is the tax-form printing year, one of 2019 through 2024.

The request must carry `expected_organization_version`, the client's last observed version of the target organization. If the organization's `version` has moved on since the client read it, the create is refused with `ERR_STALE_ORGANIZATION_VERSION` (HTTP 412) and no filing is written. This is the serialization point that keeps revision supersession honest: because creating a filing legitimately supersedes the prior revision for the same organization, tax year and form type, a client working from a stale view of the organization is exactly the client that would otherwise supersede a revision it never saw.

A new filing does not simply coexist with its predecessors. Its `revision_number` is one more than the greatest `revision_number` already recorded for the same `organization_id`, `tax_year` and `form_type`, or 1 when no such filing exists. Any existing filing for that same triple whose status is not `SUPERSEDED` and not `VOIDED` is moved to `SUPERSEDED`; before it moves, its current status is written into `pre_supersede_status`, and its `superseded_by_revision_number` is set to the new filing's `revision_number`. The new row itself opens in `RECEIVED` with `extracted_field_count` 0 and `total_revenue_cents` 0, and the organization's `total_revenue_cents` is recomputed because the set of superseded filings has changed. The organization's `version` is incremented by 1.

Coverage is checked at creation. A filing's coverage interval is closed at both ends, and it may not touch or overlap the coverage interval of a filing of the same organization that carries a *different* `form_type` and is neither `SUPERSEDED` nor `VOIDED`. Touching endpoints count, so a period beginning on the day another ends is an overlap. A collision is refused with `ERR_FILING_COVERAGE_OVERLAP` (HTTP 409). Revisions of the same `form_type` are exempt, because replacing a return with a corrected return is the entire point of revisioning.

Extraction is the act that turns a raw return into structured lines, and it is performed by a `PlatformVerifier`. The request supplies a `raw_lines` array; each element carries a `line_code`, the `raw_value` exactly as printed, a `raw_format` of `USD_WHOLE`, `USD_THOUSANDS`, `USD_MILLIONS` or `PLAIN_INTEGER`, an optional `schedule_code` of `SCHEDULE_A`, `SCHEDULE_O` or `SCHEDULE_I` (null for core-form lines), and an `is_revenue_component` boolean that defaults to false and marks the line as contributing to the filing's revenue total.

Two preconditions guard the extraction. First, `raw_lines` must contain at least one entry. A request carrying an empty array is refused with `ERR_NO_EXTRACTED_FIELDS` (HTTP 422), no extracted rows are created, and the filing is not advanced past `RECEIVED` by that request. Second, every `line_code` in the request must be a member of the permitted set for the filing's declared `form_version_year`, as tabulated in §2.7; a single out-of-set code — including a code that is legal on a different version year — refuses the whole request with `ERR_UNSUPPORTED_FORM_VERSION` (HTTP 422). Extraction is all-or-nothing: there is no partial acceptance.

When both preconditions hold, the extraction produces one `ExtractedField` row per supplied line, each hanging off the filing through `filing_id`, each opening with `normalization_status` of `PENDING`, each with a `normalized_value_cents` that is not yet computed and a `correction_count` of 0. Each row also carries a `confidence_pct` determined solely by its declared `raw_format`: 99.0 for `USD_WHOLE` and for `PLAIN_INTEGER`, 92.0 for `USD_THOUSANDS`, and 85.0 for `USD_MILLIONS`. The filing then advances from `RECEIVED` to `EXTRACTED`, its `extracted_field_count` becomes the number of rows created, and its `extraction_confidence_pct` becomes the mean of those rows' `confidence_pct` values. A filing that has already failed extraction — one sitting in `EXTRACTION_FAILED` — may be re-extracted, and a successful re-extraction moves it to `EXTRACTED` under the same two preconditions and the same row-creation rules.

There is one further outcome. When the request supplies a non-empty `raw_lines` array in which no line yields a parseable decimal `raw_value`, the extraction fails without a client error: the filing moves from `RECEIVED` to `EXTRACTION_FAILED`, `extracted_field_count` is set to 0 and `extraction_confidence_pct` is set to null. This is the case that distinguishes a malformed request from an unreadable document — the array was well formed and the line codes were legal, but the document itself could not be read.

### 3.5. Normalization, Revenue Aggregation, Supersession and Voiding

A `PlatformVerifier` normalizes a filing to convert its pending lines into comparable cent values. Normalization is declared only for a filing in `EXTRACTED` or `DISPUTED`; a normalize request against a filing in any other status — `RECEIVED`, `EXTRACTION_FAILED`, `NORMALIZED`, `SUPERSEDED` or `VOIDED` — is refused with `ERR_INVALID_STATE` (HTTP 409), and that state gate outranks the two preconditions that follow. The filing must have at least one `ExtractedField` row; a normalize request against a filing with none is refused with `ERR_NO_EXTRACTED_FIELDS` (HTTP 422). The organization that owns the filing must also be in good standing — `DRAFT` or `ACTIVE` profile status — or the request is refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403).

Normalization converts each field with a single rounding operation: the `raw_value` is read as a decimal and multiplied by the unit multiplier belonging to its `raw_format` — 100 for `USD_WHOLE`, 100000 for `USD_THOUSANDS`, 100000000 for `USD_MILLIONS`, and 100 for `PLAIN_INTEGER` — and the product is rounded half up to a whole number of cents and stored in `normalized_value_cents`. This is the only rounding applied to an individual field, and it is never deferred.

Which fields get normalized, and to what, depends on the state the filing is in. Normalizing a filing in `EXTRACTED` moves every one of its `PENDING` fields to `NORMALIZED`, except that a field whose `line_code` is duplicated by another field of the same filing moves to `CONFLICT` instead: a duplicate line code is an ambiguity the system will not silently resolve, so the conflicting fields keep a null `normalized_value_cents` and are excluded from the revenue total. Normalizing a filing in `DISPUTED` is the repair pass — every field of that filing still sitting in `PENDING` or `CONFLICT` moves to `NORMALIZED` once its `line_code` is unique within the filing. A field that later becomes unique again is normalized by a subsequent pass of the same capability: a `CONFLICT` field moves to `NORMALIZED` and receives its computed `normalized_value_cents` once the duplicate is gone.

The filing's revenue total is then rebuilt by a pinned evaluation order. First, every `ExtractedField` of the filing whose `is_revenue_component` is true and whose `normalization_status` is `NORMALIZED` or `CORRECTED` has its `normalized_value_cents` computed by the per-field conversion above. Second, `total_revenue_cents` is the exact integer sum of those per-field values, with no second rounding. Fields sitting in `PENDING` or `CONFLICT` are excluded from the set entirely. The order matters and is observable: a filing whose two revenue components have `raw_value` `1234.005` and `5678.005`, both with `raw_format` `USD_WHOLE`, produces per-field values of 123401 and 567801 cents and a filing total of 691202 cents. Summing the raw dollar amounts first and rounding once at the end yields 691201, and that is explicitly not the required result.

A successful normalization also recomputes the filing's own verification flag. `is_verified` becomes true exactly when the filing's `extraction_confidence_pct` is at least 90.0, its `extracted_field_count` is at least 1, and no `ExtractedField` of the filing has `normalization_status` `CONFLICT`; otherwise it is false. All three conditions must hold together — a high mean confidence cannot rescue a filing that still has a conflicting line.

Normalization cascades upward. The owning organization's `total_revenue_cents`, `latest_filing_tax_year`, `provisional_completeness_score`, `verified_completeness_score`, `profile_completeness_score` and `disclosure_pct` are all recomputed. If the recomputed `profile_completeness_score` is below 50 and the organization holds an `ACTIVE` transparency seal, that seal is revoked and `transparency_seal_level` returns to `NONE`. The filing's `version` is incremented by 1 and the organization's `version` is incremented by 1.

The organization-level revenue aggregate is defined over a deliberately narrow set. The included filings are those whose `organization_id` matches, whose `status` is exactly `NORMALIZED`, and whose `superseded_by_revision_number` is null; the organization's `total_revenue_cents` is the exact integer sum of those filings' `total_revenue_cents`, and its `latest_filing_tax_year` is the greatest `tax_year` among them, or null when the set is empty. No tie-break is needed, because the supersession rule guarantees at most one filing per organization, tax year and form type carries a null `superseded_by_revision_number`. Two consequences follow that are easy to miss. A filing in `DISPUTED` status is excluded from the organization total even though its own `total_revenue_cents` is populated — a dispute removes the figure from the public roll-up until the dispute is resolved. And a superseded revision is excluded regardless of how large its number was.

Supersession is automatic. When a new revision is created for an organization, tax year and form type that already has a live revision, the older filing moves from `NORMALIZED` or from `DISPUTED` to `SUPERSEDED`, and three things are recorded on it: `pre_supersede_status` holds the status it held immediately before the move, and `superseded_by_revision_number` holds the new filing's `revision_number`. The organization's `total_revenue_cents` is then recomputed over the non-superseded filings only, so the superseded revision's figure drops out of the roll-up the moment it is replaced.

Voiding is a `PlatformAdmin` capability and it is the inverse of supersession as well as a terminal state of its own. A filing in `RECEIVED`, `EXTRACTED`, `EXTRACTION_FAILED`, `NORMALIZED` or `DISPUTED` moves to `VOIDED`; the organization's `total_revenue_cents` is recomputed in every case, and for the `NORMALIZED` and `DISPUTED` cases the organization's `latest_filing_tax_year` and completeness scores are recomputed as well. Voiding a revision that had superseded an earlier one is more interesting: if the voided filing's `revision_number` equals another filing's `superseded_by_revision_number`, that earlier filing is restored — its `status` returns to the exact value recorded in its `pre_supersede_status`, and both `superseded_by_revision_number` and `pre_supersede_status` are cleared back to null. The organization's `total_revenue_cents` is recomputed over the non-superseded filings, which now include the restored revision. Voiding a filing in `SUPERSEDED` status is therefore not a no-op on the rest of the graph; it resurrects the revision it displaced. The filing's `version` and the organization's `version` are each incremented by 1.

### 3.6. Correction Requests and the Dispute Cascade

When an organization believes an extracted figure is wrong, its staff dispute the line rather than editing it. An `OrganizationUser` files a correction request against a specific `ExtractedField`, supplying the `target_extracted_field_id` through the resource path, a `requested_value` — the corrected value the organization wants recorded — an `evidence_url` pointing at the supporting document, a free-text `justification`, and `expected_extracted_field_version`, the field's version as the client last observed it. If the field's `version` has moved since — because another writer corrected or re-normalized it — the request is refused with `ERR_STALE_EXTRACTED_FIELD_VERSION` (HTTP 412), because the client is disputing a value that no longer exists.

Not every line can be disputed. A field whose `normalization_status` is `PENDING` or `CONFLICT` has no settled value to argue about, and a correction request against it is refused with `ERR_FIELD_NOT_CORRECTABLE` (HTTP 422). A field must be `NORMALIZED` or `CORRECTED` before it can be corrected.

A filed request opens in `SUBMITTED` status with `submitted_by_user_id` set to the acting `X-User-ID` and `requested_at` set to the current logical-clock instant; `decided_by_user_id` and `decided_at` are null. Filing it recomputes the organization's `open_correction_count` and increments the target field's `version` by 1. That counter is what drives suspension, so it is worth being precise about its membership: `open_correction_count` counts correction requests belonging to the organization that sit in `SUBMITTED` or `UNDER_REVIEW`, and requests in `ACCEPTED`, `PARTIALLY_ACCEPTED`, `REJECTED` or `WITHDRAWN` do not count toward it.

Adjudication is a single decision capability that carries a `decision` value — `CLAIM`, `RETURN_FOR_INFO`, `ACCEPT`, `PARTIALLY_ACCEPT`, `REJECT` or `WITHDRAW` — plus an optional `review_note` and an optional `corrected_value`. The `PlatformVerifier` drives the first five decisions; the `OrganizationUser` who submitted the request drives the last.

Claiming a request moves it from `SUBMITTED` to `UNDER_REVIEW`. The acting `X-User-ID` must differ from the request's `submitted_by_user_id`, and a match is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403); on success `decided_by_user_id` is set to the acting user and the request's `version` is incremented by 1.

Returning a request for information moves it back from `UNDER_REVIEW` to `SUBMITTED`. The `review_note` must be non-empty, and an empty one is refused with `ERR_INVALID_REQUEST` (HTTP 400). On success `decided_by_user_id` is cleared back to null, the request re-enters the `SUBMITTED` queue, and a later claim re-enters review; the request's `version` is incremented by 1.

Accepting a request is the heaviest branch, and it is the one with a cross-entity gate. The acting `X-User-ID` must differ from `submitted_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Independently, the target extracted field's filing must be in `NORMALIZED` or `DISPUTED` status; a filing in any other state refuses the acceptance with `ERR_INVALID_STATE` (HTTP 409). When both gates pass, the request moves to `ACCEPTED` with `decided_by_user_id` set to the acting user and `decided_at` set to the logical-clock instant; the target field's `normalized_value_cents` is replaced by the accepted `requested_value` converted to cents by the field's own unit multiplier and rounded half up, and the field's `normalization_status` moves to `CORRECTED` with `is_verified` set true and `correction_count` increased by 1. That field change drags its filing into `DISPUTED` if the filing was `NORMALIZED`, and both the filing's `total_revenue_cents` and the organization's `total_revenue_cents` are recomputed, along with the organization's completeness scores. The accepted request's `version` is incremented by 1 and the organization's `version` is incremented by 1. And because acceptance closes one of the organization's open disputes, the recomputed `open_correction_count` may drop — but the more consequential direction is the opposite one: if the organization's `open_correction_count` reaches 3, the organization's `profile_status` moves to `SUSPENDED` and its `ACTIVE` seals are revoked, exactly as described in §3.3.

A further accepted correction against an already-`CORRECTED` field follows the same shape with one difference: the field's `normalized_value_cents` is replaced by the newly accepted value and `correction_count` increases again, the filing's and organization's revenue totals are recomputed, and the field's `version` is incremented by 1.

Partially accepting a request is the sibling branch, and it is specified as densely as full acceptance. The `corrected_value` must be supplied, and it must differ from both the field's current normalized value and the request's own `requested_value`; either failure is refused with `ERR_INVALID_REQUEST` (HTTP 400). On success the request moves to `PARTIALLY_ACCEPTED`, the target field's `normalized_value_cents` is replaced by the partially accepted `corrected_value` and its `normalization_status` moves to `CORRECTED` with `correction_count` increased by 1, the filing moves to `DISPUTED` if it was `NORMALIZED`, and the organization's `total_revenue_cents` is recomputed. The request's `version` and the organization's `version` are each incremented by 1. Note one asymmetry against the full-acceptance branch: partial acceptance replaces the field's value and bumps its correction count, but it does not increment the field's own `version`.

Rejecting a request moves it from `UNDER_REVIEW` to `REJECTED`. The `review_note` must be non-empty, and an empty one is refused with `ERR_INVALID_REQUEST` (HTTP 400). On success `decided_by_user_id` is set to the acting user, `decided_at` is set to the logical-clock instant, no `ExtractedField` is mutated at all, and the request's `version` is incremented by 1.

Withdrawal is the submitter's escape hatch and it works from either open state: a request in `SUBMITTED` or in `UNDER_REVIEW` moves to `WITHDRAWN`. The acting `X-User-ID` must equal the request's `submitted_by_user_id`, and any other actor — including a verifier — is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403). No `ExtractedField` is mutated, and the request's `version` is incremented by 1. Because withdrawal is available from `UNDER_REVIEW` as well as `SUBMITTED`, a submitter can pull a request back even after a verifier has claimed it.

### 3.7. Transparency Seals: Award, Renewal, Revocation and Lapse

The transparency seal is the platform's public signal that an organization has disclosed enough of itself. A `PlatformVerifier` awards one, and the level is computed rather than chosen.

Three gates precede the computation, and they are evaluated in a fixed order. First, the organization named in the request must have `profile_status` `ACTIVE`; otherwise the award is refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403). Second, the organization must not already hold an `ACTIVE` seal — a second award while one is live is refused with `ERR_INVALID_STATE` (HTTP 409), so a renewal is the only way to extend coverage. Third, the organization's `disclosure_pct` must be at least 0.50; a lower value is refused with `ERR_SEAL_DISCLOSURE_INSUFFICIENT` (HTTP 422). The third gate is the floor, and it is absolute: an organization that discloses less than half of the weighted profile can hold no seal at any level.

When the gates pass, the level is derived in three stages. Two inputs are computed first. The verified filing count is the number of filings belonging to the organization whose `status` is `NORMALIZED`, whose `is_verified` is true, and whose `tax_year` is at least two years below the organization's `latest_filing_tax_year` — that is, the three most recent tax years ending at the latest filed year. The leadership verification percentage is the number of `ACTIVE` leadership members with `is_verified` true divided by the number of `ACTIVE` leadership members, rounded half up to 4 decimal places; when there are no `ACTIVE` leadership members at all, this floor rule is skipped rather than evaluated.

The base level follows the disclosure measure and the verified filing count. A `disclosure_pct` of at least 0.90 together with a verified filing count of at least 2 yields `PLATINUM`. Failing that, a `disclosure_pct` of at least 0.75 together with a verified filing count of at least 1 yields `GOLD`. Failing both, the base level is `SILVER` — which is reachable only when `disclosure_pct` is at least 0.50 and below 0.75, since the 0.50 floor was already enforced.

The cap level follows the organization's verification standing. An organization still at `SELF_REPORTED` is capped at `BRONZE`. One at `DOCUMENT_VERIFIED` is capped at `GOLD`. One at `INDEPENDENTLY_AUDITED` is capped at `PLATINUM`. The awarded level is the lower-ranked of the base level and the cap level, where the ranking runs `BRONZE` below `SILVER` below `GOLD` below `PLATINUM`. Finally, if the leadership verification percentage is below 0.50, the level is lowered once more to `SILVER` if it currently ranks above `SILVER`. The cap and the leadership floor can both bind, and when they do, the lower result stands.

The seal that results records `disclosure_pct_at_award` — the organization's `disclosure_pct` frozen at the moment of award — together with `awarded_on` set to the logical-clock instant, `expires_on` set to `awarded_on` plus 365 days, and `renewal_window_opens_on` set to `expires_on` minus 60 days. `awarded_on`, `expires_on` and `renewal_window_opens_on` are rendered as ISO 8601 UTC timestamps with three fractional digits, the same rendering `created_at` and `updated_at` use (§2.5), and the organization's mirrored `seal_expires_on` carries the same string as the seal's `expires_on`. It opens with `status` `ACTIVE` and `renewal_attempt_count` 0, and the organization's `transparency_seal_level` and `seal_expires_on` are refreshed to mirror it. The organization's `version` is incremented by 1. Note what `level` is not: it is frozen at award, and no later renewal re-evaluates it.

Renewal is a `PlatformVerifier` capability that charges a fee, and it is declared only for a seal that is still `ACTIVE`. A renewal attempted against a seal that is not `ACTIVE` is refused with `ERR_INVALID_STATE` (HTTP 409) — the state rung of the §2.10 precedence ladder outranks the temporal one, so this holds even when the seal's `expires_on` is 91 or more days behind the clock — and such an attempt still increments `renewal_attempt_count` by 1 (the seal's `version` and `updated_at` move with that mutation) while leaving the seal's `status` unchanged and the owning organization untouched. For a seal that is still `ACTIVE`, two gates precede the fee computation. The seal's owning organization must have `profile_status` `ACTIVE`, or the renewal is refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403). And the number of days late must not exceed 90; a request arriving 91 or more days after `expires_on` is refused with `ERR_SEAL_LAPSED` (HTTP 409), though as described below the refusal itself still moves the seal.

The fee is computed in a pinned order, where every step consumes only the values produced above it. First, the level is read from the seal — it is the level frozen at award. Second, the base fee is read from the level: `BRONZE` 0 cents, `SILVER` 25000 cents, `GOLD` 75000 cents, `PLATINUM` 200000 cents. Third, `days_late` is computed as the whole number of days between `expires_on` and the current logical-clock instant, rounded down, floored at zero — a renewal made before expiry is zero days late. Fourth, `days_late` is placed into a tier: tier 0 when it is exactly zero, tier 1 when it is from 1 through 30, tier 2 when it is from 31 through 90, and tier 3 when it is 91 or more. Fifth, the late percentage is read from the tier: 0.00 for tier 0, 0.10 for tier 1, 0.25 for tier 2, and 0.50 for tier 3. Sixth, the late fee is the base fee multiplied by the late percentage, rounded half up to a whole number of cents. Seventh, the renewal fee is the base fee plus the late fee. Eighth, the decision is applied. A `GOLD` seal renewed 15 days late pays a base of 75000 cents plus a tier-1 late fee of 7500 cents, for a renewal fee of 82500 cents. A `PLATINUM` seal renewed 32 days late pays a base of 200000 cents plus a tier-2 late fee of 50000 cents, for a renewal fee of 250000 cents.

The eighth step branches, and both branches increment `renewal_attempt_count` by 1 — the counter is incremented by every attempt, successful or rejected, and its value at the moment of the decision is its pre-increment value, so the increment is a consequence of the decision and never an input to it. In the tier-3 branch the seal's `status` moves to `LAPSED`, the owning organization's `transparency_seal_level` returns to `NONE` and its `seal_expires_on` becomes null, and the seal's `version` and the organization's `version` are each incremented by 1. In every other branch the renewal succeeds: `last_renewal_fee_cents` is set to the computed renewal fee, `expires_on` is set to the current logical-clock instant plus 365 days, `renewal_window_opens_on` is set to that new `expires_on` minus 60 days, the level is not re-evaluated and `disclosure_pct_at_award` is not refreshed, and the seal's `version` is incremented by 1.

Two automatic events can end a seal without any client request. The first is lapse by time: when the logical clock advances past `expires_on` plus 90 days, an `ACTIVE` seal moves to `LAPSED` and the owning organization's `transparency_seal_level` returns to `NONE` with `seal_expires_on` set to null. The second is revocation, which fires in two situations. A seal is revoked when its owning organization transitions to `SUSPENDED`, `MERGED` or `DISSOLVED` — the suspension case was described in §3.3 and the identity cases are described in §3.8. A seal is also revoked when the organization's `disclosure_pct` falls below the disclosure floor of that seal's own level, where the floors are 0.50 for `BRONZE` and `SILVER`, 0.75 for `GOLD`, and 0.90 for `PLATINUM`. A profile patch or a normalization that pushes `disclosure_pct` from 0.9000 down to 0.8500 therefore revokes a `PLATINUM` seal but leaves a `GOLD` seal standing. Revocation moves the seal's own `status` to `REVOKED`, sets the organization's `transparency_seal_level` to `NONE` and `seal_expires_on` to null, and increments the seal's `version` and the organization's `version` by 1.

### 3.8. Organization Identity Resolution: Name Changes, Mergers and Dissolutions

Nonprofits change shape. They rename themselves, they absorb each other, and they close. The platform models all three as an identity resolution case rather than as an edit to a name column, because a merger has to move grant history and a dissolution has to revoke a seal.

A `PlatformAdmin` opens a case with a `subject_organization_id` — the organization whose identity is being resolved — a `case_type` of `MERGE`, `DISSOLUTION` or `NAME_CHANGE`, an `effective_date` on which the change takes legal effect, and an optional `resolution_note`. The remaining inputs are conditional, and the condition is enforced as a field-combination rule. A `MERGE` requires a `surviving_organization_id` that names the surviving organization and differs from the subject. A `DISSOLUTION` requires `surviving_organization_id` to be null. A `NAME_CHANGE` requires `surviving_organization_id` to be null and requires a `new_legal_name` that differs from the subject organization's current `legal_name`. Any combination that violates these rules is refused with `ERR_IDENTITY_CASE_INVALID` (HTTP 409).

A case opens in `OPEN` status with `reassigned_grant_count` 0, a null `finalized_at`, and an incremented `version` on the subject organization. From `OPEN` it can move in exactly two directions: to `FINALIZED`, which applies the change, or to `WITHDRAWN`, which does not. Attempting to finalize a case that is not `OPEN` — one already finalized or already withdrawn — is refused with `ERR_INVALID_STATE` (HTTP 409), and so is finalizing a merge whose surviving organization would create a loop.

Closing a case takes a `resolution_decision` of either `FINALIZE` or `WITHDRAW`. Withdrawal is the quiet branch: a `WITHDRAW` decision moves the case from `OPEN` to `WITHDRAWN`, mutates no organization at all, and increments only the case's own `version` by 1.

Finalization is the loud branch, and its preconditions are checked before any organization is touched. A `MERGE` must carry a `surviving_organization_id` that is present and different from the subject, or the request is refused with `ERR_IDENTITY_CASE_INVALID` (HTTP 409). A `MERGE` must also not create a cycle: following the `successor_organization_id` chain outward from the surviving organization must never arrive back at the subject organization, and a chain that does is refused with `ERR_MERGE_CYCLE_DETECTED` (HTTP 409). A `DISSOLUTION` must carry a null `surviving_organization_id`, and a `NAME_CHANGE` must carry a null `surviving_organization_id` together with a `new_legal_name`; violations are refused with `ERR_IDENTITY_CASE_INVALID` (HTTP 409). The case's own status must be `OPEN` for the organization-side transition to fire, and a case that is not `OPEN` is refused with `ERR_INVALID_STATE` (HTTP 409).

A finalized merge is the most cascading operation in the system. The subject organization's `profile_status` moves to `MERGED` and its `successor_organization_id` is set to the case's `surviving_organization_id`. Every `Grant` whose `recipient_organization_id` is the absorbed organization is re-pointed to the surviving organization, and every `Grant` whose `funder_organization_id` is the absorbed organization is re-pointed as well — the absorbed organization's grant history, both incoming and outgoing, moves wholesale. The number of re-pointed grant rows is recorded on the case as `reassigned_grant_count`, and the surviving organization's `distinct_funder_count` is recomputed because its set of recorded grants has changed. Every `DataLicense` of the absorbed organization that is in `ACTIVE` status moves to `EXPIRED`, and every `TransparencySeal` of the absorbed organization that is in `ACTIVE` status is revoked. Finally, the organization's `version` is incremented by 1 on *both* organizations — the absorbed one and the surviving one. A merge that starts from an organization already in `SUSPENDED` profile status takes the same path to `MERGED`, with the same grant re-pointing, the same `successor_organization_id` assignment and the same version increments on both sides; because a suspended organization has already had its seals revoked and its licenses left in whatever state they were in, only the live license-expiry cascade is additional when the subject was `ACTIVE`.

A finalized dissolution is simpler and just as terminal. The subject organization's `profile_status` moves to `DISSOLVED`, and its `dissolution_date` is set to the case's `effective_date` — the declared date, not the clock instant. Every `ACTIVE` transparency seal of the organization is revoked and every `ACTIVE` data license of the organization expires, and the organization's `version` is incremented by 1. A dissolution of an organization already in `SUSPENDED` status follows the same path with the same two cascades.

A finalized name change edits exactly two fields, in a defined order. The organization's previous `legal_name` is appended to `former_legal_names` — appending, never overwriting, and in the order the cases were finalized, so an organization renamed twice carries both prior names with the older one first — and then `legal_name` is replaced by the case's `new_legal_name`. The organization's `version` is incremented by 1. Nothing else about the organization changes: the `ein` stays with the row, the profile status stays `ACTIVE`, and grants, licenses and seals are untouched.

Whichever branch ran, `finalized_at` on the case is set to the logical-clock instant, and the case's `version` is incremented by 1.

### 3.9. Data Consumers: Licensing, Grant Records and Funder Prospect Research

A funder, researcher or platform organization — acting as a `DataConsumer`, with `X-User-ID` equal to its own organization id — consumes the platform through three capabilities.

**Licensing.** A license request names the licensee organization, a `tier` of `RESEARCHER`, `FUNDER` or `PLATFORM`, a `permitted_use`, a `term_start` marking the first instant of the term inclusive and a `term_end` marking its end exclusive, plus an optional `projected_annual_records` — the licensee's own forecast of how many records it will read — and an optional `auto_renew` boolean that defaults to false. The license opens in `DRAFT` status with `records_accessed` 0, `overage_records` 0 and `overage_flag` false. Its `included_records` is derived from the tier — 10000 for `RESEARCHER`, 100000 for `FUNDER`, 1000000 for `PLATFORM` — and its `projected_annual_fee_cents` is quoted from the forecast: the tier's base fee, which is 500000 cents for `RESEARCHER`, 2500000 cents for `FUNDER` and 10000000 cents for `PLATFORM`, plus the count of projected records beyond `included_records`, floored at zero, multiplied by the tier's overage rate of 5 cents for `RESEARCHER`, 2 cents for `FUNDER` and 1 cent for `PLATFORM`. A `RESEARCHER` license forecasting 50000 records therefore quotes 700000 cents: a 500000-cent base plus 40000 overage records at 5 cents each.

Activation turns a `DRAFT` license into a live one, and four checks stand in the way. The licensee organization must be `ACTIVE`, or the request is refused with `ERR_ORG_NOT_IN_GOOD_STANDING` (HTTP 403). The `permitted_use` must be a member of the tier's permitted set as tabulated in §2.7, or the request is refused with `ERR_PERMITTED_USE_NOT_IN_TIER` (HTTP 403). The half-open term `[term_start, term_end)` must not overlap an existing non-`EXPIRED` license of the same tier held by the same licensee; an overlap is refused with `ERR_LICENSE_TERM_OVERLAP` (HTTP 409), but an adjacent term whose `term_start` exactly equals the prior term's `term_end` is *not* an overlap, because the intervals are half-open. And `projected_annual_records` must be at least 1, or the request is refused as malformed with `ERR_INVALID_REQUEST` (HTTP 400). On success the license moves to `ACTIVE`, its `included_records`, `projected_annual_fee_cents` and `final_annual_fee_cents` are computed, the licensee organization's `active_license_count` is recomputed, and both the license's `version` and the licensee organization's `version` are incremented by 1.

Usage is metered by events. A `DataConsumer` posts one against its own `ACTIVE` license, supplying a `dataset_scope` of `ORGANIZATION_PROFILES`, `FILING_FINANCIALS`, `GRANT_HISTORY` or `LEADERSHIP_COMPENSATION`, a `record_count` of at least 1, and a free-text `purpose_code`. Three gates apply, in order: a `record_count` below 1 is refused with `ERR_INVALID_REQUEST` (HTTP 400); a logical clock outside the license's `[term_start, term_end)` window is refused with `ERR_LICENSE_TERM_CLOSED` (HTTP 409); and a posting that would push `records_accessed` above `included_records` multiplied by 4 is refused with `ERR_QUOTA_EXCEEDED` (HTTP 402). That hard cap of four times the included allowance is a ceiling on consumption, not a pricing tier — the overage rate applies to consumption up to the cap, and beyond the cap there is no sale at all. On success a `LicenseUsageEvent` is created in `POSTED` status with `occurred_at` set to the logical-clock instant, the license's `records_accessed` increases by `record_count`, its `overage_records` and `final_annual_fee_cents` are recomputed, and the license's `version` is incremented by 1.

`records_accessed` is a conserved quantity: it equals the sum of `record_count` over the license's `POSTED` usage events and nothing else, which is what makes voiding meaningful. A `PlatformAdmin` may void a posted event by naming its `event_id` within the owning license, which moves that event to `VOIDED`, subtracts its `record_count` from `records_accessed`, recomputes `overage_records`, `overage_flag` and `final_annual_fee_cents`, and increments the license's `version` by 1. The `final_annual_fee_cents` is the read-time figure: the tier's base fee plus the count of records beyond `included_records`, floored at zero, multiplied by the tier's overage rate. The `RESEARCHER` license that quoted 700000 cents from a 50000-record forecast reports 510000 cents once its posted events total 12000 records actually read — a 500000-cent base plus 2000 overage records at 5 cents each. `overage_flag` is true exactly when `records_accessed` exceeds `included_records`. A license expires automatically when the logical clock reaches `term_end`, and also when the licensee organization finalizes a `MERGE` or a `DISSOLUTION` identity case; in both cases the licensee organization's `active_license_count` is recomputed. `EXPIRED` is terminal.

**Grant records.** A `DataConsumer` or `PlatformAdmin` records a grant made to a recipient organization, supplying the `funder_organization_id`, the funder's name exactly as it appeared in the feed as `funder_name_raw`, the grantee's name as `recipient_name_raw`, the `amount_cents`, the funder's `fiscal_year`, and optionally the grantee's `recipient_ein` and a `subject_code`. The row is created in `RECORDED` status with `taxonomy_source` set to `FUNDER_SUPPLIED` when a `subject_code` was supplied and to `UNCODED` when it was not; no operation in this version moves a grant to `VOIDED`, and only `RECORDED` grants count toward any aggregate. Creating a grant recomputes the `distinct_funder_count` of both the recipient organization and the funder organization.

Every grant is scored for recipient match at creation. The score accumulates points from four comparisons. If `recipient_ein` is present and equals the recipient organization's `ein`, 60 points are added. Both names are then normalized: uppercased, every character that is not a letter A through Z or a digit 0 through 9 replaced by a space, runs of spaces collapsed, the result trimmed, a leading token `THE` dropped, and any trailing token from the set `INC`, `INCORPORATED`, `CORP`, `CORPORATION`, `LLC`, `LTD`, `FOUNDATION`, `FUND`, `TRUST`, `ASSOCIATION`, `SOCIETY` dropped. If the normalized `recipient_name_raw` equals the normalized `legal_name`, 30 points are added; otherwise, if both normalized strings are at least 12 characters long and their first 12 characters are identical, 18 points are added instead. If `subject_code` is present and equals the recipient organization's `ntee_code`, 10 points are added. The `match_score` is the accumulated total capped at 100. A grant matching only on EIN scores 60; the same grant additionally matching on subject code scores 70. The `recipient_match_status` follows the score: `MATCHED` at 70 or above, `AMBIGUOUS` from 40 through 69 inclusive, and `UNMATCHED` below 40.

Matching can be re-run when the funder obtains better identifying data. The re-run accepts an optional `recipient_ein` and an optional `subject_code`. A supplied `recipient_ein` replaces the grant's stored `recipient_ein`; a supplied `subject_code` replaces the grant's stored `subject_code` and sets `taxonomy_source` to `FUNDER_SUPPLIED`. When no `subject_code` is supplied, and the recomputed `recipient_match_status` is `MATCHED`, and the recipient organization has a non-null `ntee_code`, the grant's `subject_code` is set to that `ntee_code` and `taxonomy_source` becomes `AUTO_CODED`. The `match_score` and `recipient_match_status` are recomputed and the grant's `version` is incremented by 1.

**Prospect research.** A funder can ask the platform to rank candidate grantees. The request names the `funder_organization_id` and may carry a `subject_code`, a `min_score` floor that restricts the returned prospects to those whose match score is at least the supplied value, and the usual `limit` and `offset`. The candidate set is every organization whose `profile_status` is `ACTIVE`, excluding the funder itself and excluding any organization that is the subject or the surviving organization of an `OPEN` identity resolution case involving the funder.

Each candidate is scored out of 100. If the candidate's `state_code` equals the funder's `state_code`, 25 points are added. If the request supplied a `subject_code` and the candidate's `ntee_code` equals it, 35 points are added. The funder's mean recorded grant amount is computed across its `RECORDED` grants — and is zero when it has none — and the size band runs from half that mean, rounded half up to a whole number of cents, to twice that mean, rounded the same way; a candidate whose `total_revenue_cents` falls within that band inclusive at both ends scores 20 points. A candidate that has at least one `RECORDED` grant from this funder scores a further 20 points. The `match_score` is the total capped at 100.

The response reports the `funder_organization_id`, the `mean_grant_amount_cents` that anchored the size band, and a `prospects` array. Each prospect is the candidate organization's own profile object — the same representation `GET /nonprofits/organizations/{id}` returns, identified by the organization's `id` — augmented with its `match_score` and its `historical_giving_cents`, the exact sum of `amount_cents` over the funder's `RECORDED` grants to that candidate. The ranking is a deterministic total order: `match_score` descending, then `historical_giving_cents` descending, then the candidate's `created_at` ascending. No identifier value ever participates in the ranking, so two candidates identical on all three keys cannot be ordered by chance. A funder with no eligible candidates receives an empty `prospects` array with `total_count` 0 and `has_more` false — an empty result is a valid answer, not an error.

## 4. Endpoint Definitions
