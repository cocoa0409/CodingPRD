# Food Bank Load Allocation API — Product Requirements Document

## 1. Introduction

The National Food Bank Network receives food in truckload quantities from manufacturers, retailers and distributors who donate at the national level rather than store by store or city by city. That scale creates a distribution problem the network has never solved cleanly: a single donated trailer of frozen protein may be pledged in Ohio, landed in a region with no member able to store it, and claimed by three food banks that all believe they asked for it first. This document specifies the API that replaces the informal phone-and-spreadsheet allocation process with a governed, auditable marketplace.

The system introduces a **share currency** that members earn through the size of the food-insecure population they serve and through the poundage they have actually moved, and it lets members bid that currency against posted loads. Because share currency is scarce, allocation is a bidding problem rather than a queue; because donated product is food, allocation is also a safety problem, and a recall must be able to reach every load, hold and pending bid that touches an affected lot within seconds. Freight is the third pressure: rural members with the greatest need are frequently the ones furthest from a donor's distribution center, so the network subsidizes haulage from a per-agreement pool and must decide, load by load, whether a remote member can realistically accept.

Three operational realities shape the requirements that follow. Members must meet network standards — storage, distribution and reporting — before they may bid at all, and their posture can be degraded automatically when an audit fails or when their share balance falls too low. Retail store donation programs run locally under a member's own certification and must be scheduled, collected and missed on a cadence the network can audit. And every pound that is delivered must be convertible into meals for donor reporting, using a factor that belongs to the donor agreement rather than to the network.

## 2. Global Specifications & System-Wide Principles

This section defines the cross-cutting rules that apply to every resource and every operation in the API.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names its operational capacity. Three roles exist, spelled exactly `NetworkAdmin`, `MemberFoodBank` and `NetworkAuditor`. A request missing either header, or carrying a role string that is not one of those three, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is valid but is not authorized for the operation it targets is rejected with `ERR_FORBIDDEN` (HTTP 403).

The three roles differ in how `X-User-ID` relates to persisted data, and this difference governs every ownership comparison in the system. When `X-User-Role` is `MemberFoodBank`, `X-User-ID` is the `id` of the acting member food bank; ownership checks on any resource that references a member food bank compare the resource's member foreign-key field to `X-User-ID`, so a member may only bid, schedule, collect and withdraw as itself, and acting on another member's bid is rejected with `ERR_FORBIDDEN`. When `X-User-Role` is `NetworkAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but never compares it to any entity's `id`. When `X-User-Role` is `NetworkAuditor`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity.

Two operational asymmetries are worth stating plainly. The `NetworkAuditor` role exists for exactly one purpose — completing member standards audits — and shares only the member read and the member's audit listing with the other roles. The `NetworkAdmin` role owns every national-level action: donor agreements, load posting and award, freight decisions, dispatch and delivery, share grants, recalls, member certification and reinstatement, and the test-driving clock. The `MemberFoodBank` role owns the bid lifecycle and the retail store program lifecycle. Section 4 states, per endpoint, which roles are authorized.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint in this API is paginated. The `limit` query parameter caps the number of items returned and defaults to 10 when omitted; it must be at least 1 and at most 100, and a value outside that range is rejected as a malformed request. The `offset` query parameter skips that many items from the front of the result set and defaults to 0; a negative offset is rejected as a malformed request just as an out-of-range limit is. Unless a section states otherwise, list endpoints return resources ordered by their creation timestamp ascending — oldest first.

List responses place `limit`, `offset`, `total_count` and `has_more` in the `meta` object alongside the standard request identifiers, where `total_count` is the size of the full result set ignoring pagination and `has_more` indicates whether further items remain beyond the returned window. The paginated collections in this system are the network-wide bid list and recall hold list, a member's audits, share ledger entries and store programs, an agreement's loads and recalls, and a program's pickups.

### 2.4. Common Resource Properties and Identifiers

Every first-class resource in the system — `MemberFoodBank`, `DonorAgreement`, `DonatedLoad`, `LoadBid`, `ProductRecall`, `MemberAudit`, `StoreDonationProgram` and `StorePickup` — carries the same four system-managed properties in addition to its own fields:

- `id` (string): a server-minted UUID that uniquely addresses the resource. The identifier carries no type prefix and no embedded meaning; clients must treat it as opaque.
- `created_at` (string): an ISO 8601 UTC timestamp with exactly three fractional digits (for example `2025-05-24T10:30:00.123Z`) recording when the resource was first created. It never changes.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed to the current logical clock value whenever any property of the resource changes.
- `version` (integer): a system-managed counter that begins at 1 and is incremented by exactly one on every mutation of the resource, whether the mutation came from a direct client request or from one of the cascades described in §2.8.

Two resource types are deliberately outside that convention. `ShareLedgerEntry` and `RecallHold` are append-only records: each carries only `id` and `created_at`, and neither carries `updated_at` nor `version`, because neither is ever modified after it is written. A share ledger row is never edited and never deleted — corrections are made by appending a compensating entry, not by rewriting history — and a recall hold moves between its states without acquiring a version counter.

The canonical rendering is not limited to `created_at` and `updated_at`. Every other timestamp the API emits for a resource is normalized the same way — UTC, exactly three fractional digits, trailing `Z` — however the client supplied it: a load's `delivery_window_start` and `delivery_window_end`, a pickup's `scheduled_date`, `window_start` and `window_end`, and a recall's `opened_at`. A delivery window endpoint sent as `2026-09-10T12:00:00Z`, for instance, is echoed back as `2026-09-10T12:00:00.000Z`.

### 2.5. The Share Currency Ledger and Derived Balances

Share currency is the network's allocation medium and it exists only as an append-only ledger. Every movement of share currency is recorded as one `ShareLedgerEntry` row whose `entry_type` names the reason and whose `amount` is the signed delta applied to the member's balance. Exactly seven entry types exist: `GRANT`, `BID_HOLD`, `BID_RELEASE`, `AWARD_DEBIT`, `AWARD_REFUND`, `ACTIVITY_BONUS` and `RECALL_REFUND`. A `GRANT`, an `ACTIVITY_BONUS` and a `RECALL_REFUND` carry a positive amount, except that a computed grant or activity bonus of zero is still appended as a zero-amount row rather than skipped; a `BID_HOLD` and an `AWARD_DEBIT` carry a negative amount; a `BID_RELEASE` and an `AWARD_REFUND` carry a positive amount that returns previously committed currency to the member. Each row also records the `balance_after` value — the member's `share_balance` immediately after that row was appended — the `epoch` label the row belongs to, formatted as a four-digit year, a hyphen and a two-digit month, and a `reference_id`, which is a plain reference rather than a foreign key to the load or bid that caused the movement and which is null on grant rows.

Three derived values on the member are always reconciled from the ledger and from the member's live bids rather than being adjusted by hand. The member's `share_balance` is the sum of the `amount` column across all of that member's ledger rows taken in the order they were appended — ordered by `created_at` ascending, with the append sequence itself breaking ties between rows stamped at the same instant. The member's `share_reserved` is the sum of `shares_offered` across that member's bids that are currently `SUBMITTED`. The member's `active_bid_count` is the number of those same `SUBMITTED` bids. Every append to the ledger triggers a reconciliation of all three values for the affected member, and the reconciliation is exact integer arithmetic.

The stored `share_balance` is always the plain ledger sum and is not netted against reservations, which means it is already reduced by every `BID_HOLD` the member's live bids have appended. When a caller asks for `available_for_bidding`, the server reports that balance minus the reserved amount, because share currency committed to a live bid is not spendable a second time; no endpoint or response field exposes this derived value, and the member resource never carries it. Two thresholds on this balance carry consequences beyond arithmetic. A `CERTIFIED` member whose recomputed balance falls below 50 shares is moved down to `PROBATION`, a demotion performed by the award cascade's reconciliation and not by every movement of the balance, so a member that merely holds a large bid below that figure keeps its posture (see §3.5.1); and a member already on `PROBATION` may only be reinstated to `CERTIFIED` once it holds at least 100 shares. Because `share_balance` and `share_reserved` are derived properties of the member, any change to them is a mutation of the member, and therefore refreshes the member's `updated_at` and increments the member's `version`.

### 2.6. Precision and Arithmetic Conventions

Four different arithmetic regimes coexist in this system, and mixing them is the most common source of drift.

Share currency is integer-only. Every division in the share economy — the population term, the activity term, the weighted demand, the proportional grant and the residual step — floors to a whole number of shares, and no fractional share is ever stored or transferred. Freight money is integer cents, and the freight calculation rounds each component upward independently before combining them: the network's share of the haul and the remote uplift are each rounded up to the next whole cent, and only then summed and capped. Meal equivalency is integer meals computed by flooring, and the canonical donor-reporting variant floors each load's meal count before summing across loads. Audit scoring is the single decimal regime: the weighted standards score is computed to one decimal place and rounded half up, so a value exactly at a half rounds to the larger number.

Currency amounts are transmitted as plain integers in cents — `freight_estimate_cents`, `freight_subsidy_cents`, `member_freight_due_cents`, `freight_subsidy_pool_cents` and `freight_subsidy_used_cents` are all integer cents and are never rendered as decimals or strings. Rate constants that are conceptually monetary, such as the per-mile haulage rate, are applied in cents so that every intermediate product stays integral.

### 2.7. Optimistic Concurrency Control

Two write operations in this API are guarded by optimistic concurrency control, and both take a mandatory expected-version field that must be present on every request to that endpoint. The two guarded operations are bid creation at `POST /network/loads/{id}/bids` and epoch share grants at `POST /network/share-ledger/grants`; no other endpoint in the system accepts a version field of any kind.

Submitting a new bid against a posted load requires `expected_load_version` carrying the client's last observed `version` of the target load. If the load's `version` has advanced past that value, the create is rejected with `ERR_STALE_VERSION` (HTTP 412) rather than being applied against a load state the client has not seen. This matters because a bid is not the only thing that moves a load's version: every accepted bid on the load, every award, and every safety hold placed on it also increments it, so a client that read the load before those writes holds a stale view and must be told so. A member's own new bid legitimately supersedes its own earlier bid on the same load — the earlier one must have left `SUBMITTED` first, by withdrawal or rejection — and the superseding create is validated against the load's current version like any other.

Applying an epoch share grant to a member requires `expected_member_version` carrying the client's last observed `version` of that member. If the member's `version` has advanced past that value, the grant is rejected with `ERR_STALE_VERSION` (HTTP 412). A new grant for the same epoch legitimately supersedes the member's earlier provisional grant for that epoch, but any ledger movement — a hold, a release, an award debit, an activity bonus — also increments the member's version, so a client holding a stale view of the member must be rejected instead of having its grant applied on top of movements it never observed.

Both checks sit high in the validation order (§2.9) and are evaluated before any state check or business rule, so a stale request never produces a state-related error code.

### 2.8. Cascading Effects and Posture Gating

A single accepted operation in this network frequently mutates more than one resource. The convention throughout is that a cascade is executed in the order stated in the business narrative, and that every resource touched by a cascade — including the member whose derived balances are recomputed — has its `updated_at` refreshed and its `version` incremented by one for that mutation. Cascades are immediate and transactional: the originating request either completes with every hop applied or fails with none of them applied.

Three properties of cascades deserve emphasis because they are easy to miss. First, cascades chain: releasing a losing bid's hold is caused by the award, and the release itself causes the member's balance to be recomputed, and that recomputation can in turn demote the member and withdraw its other bids. Second, a cascade never silently discards value — every share that was held is released by an explicit ledger row, so the sum of a member's ledger always reconstructs its balance. Third, some cascades are negative for the member: an award that drains a member below 50 shares demotes a `CERTIFIED` member to `PROBATION`, and a member that enters `PROBATION` or `SUSPENDED` has its retail programs suspended and, at the `SUSPENDED` step, its live bids withdrawn.

Member posture — the member's `certification_status` — gates nearly every member-initiated operation, and the gate is finer than a simple certified-or-not test. A member in `PENDING_CERTIFICATION` may not bid and may not schedule pickups, and is rejected with `ERR_MEMBER_NOT_CERTIFIED` (HTTP 403). A member in `PROBATION` may still bid, but may not schedule retail pickups, and is likewise rejected with `ERR_MEMBER_NOT_CERTIFIED`. A member in `SUSPENDED` may not bid, may not register a store program and may not schedule a pickup, and is rejected with `ERR_MEMBER_SUSPENDED` (HTTP 403). Registering a retail program is the one member action open to a member in `PENDING_CERTIFICATION` or `PROBATION`: the program is created in `PENDING` posture and only becomes operational once the member itself is certified.

### 2.9. Validation Order and Failure Precedence

When a request fails several rules at once, the error returned is determined by a fixed precedence order. The order below is authoritative: a check is evaluated only after every check with a lower number has passed, and the first failure produces its error. Read it as a single ranked list, not as independent checks.

1. `ERR_UNAUTHENTICATED` (HTTP 401) guards every endpoint. `X-User-Role` and `X-User-ID` must both be present, and `X-User-Role` must name one of the three declared roles.
2. `ERR_INVALID_REQUEST` (HTTP 400) guards every endpoint that takes a request body. The body must parse, every required input field for that endpoint must be present with its declared type, and every enumerated input must be a member of its declared enumeration. Malformed JSON, unknown enum members and missing required fields are all rejected here, before any existence check, state check or business rule is evaluated. The award and recall-trace endpoints treat their body as optional, so a request to either with no body at all, or with a body that does not parse as JSON, is read as carrying no selectors rather than being rejected here; a body that parses to something other than a JSON object is still rejected. The optional selector values this API accepts — `ranking_basis` on an award, `scope` on a recall or a trace, `activity_basis` on a grant and `rounding_basis` on a poundage summary — are not closed enumerations: a value other than the one named in §3, including an unrecognized string, selects the default behavior instead of being rejected here.
3. `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) guards member audit completion. The operator completing an audit must differ from the operator recorded in that audit's `opened_by_user_id`; the same operator may not create and complete the same audit even when both calls carry an authorized role.
4. `ERR_FORBIDDEN` (HTTP 403) guards every endpoint. The acting role must be listed among the endpoint's authorized roles, and for `MemberFoodBank` callers the acting `X-User-ID` must own the resource being acted on — a member may only withdraw its own bid, and acting on another member's bid is rejected here. The ownership comparison of this rank and the segregation-of-duties comparison of rank 3 both need their target resource loaded before they can be applied, so where that target is the resource named in the path — a bid, an audit, a program or a pickup — an unknown identifier reports the not-found error of rank 8, 10, 11 or 12 rather than this rank's error.
5. `ERR_MEMBER_NOT_FOUND` (HTTP 404) guards member read, member certification, member reinstatement, bid creation, audit creation, store program creation and share grants: the member named by the path or by `member_id` in the body must exist.
6. `ERR_AGREEMENT_NOT_FOUND` (HTTP 404) guards agreement read, agreement activation, the poundage summary, load creation and recall creation: the agreement named by the path or by `donor_agreement_id` in the body must exist.
7. `ERR_LOAD_NOT_FOUND` (HTTP 404) guards load read, load posting, award, freight decision, dispatch, delivery, cancellation and bid creation: the load named by the path must exist.
8. `ERR_BID_NOT_FOUND` (HTTP 404) guards bid withdrawal: the bid named by the path must exist.
9. `ERR_RECALL_NOT_FOUND` (HTTP 404) guards recall tracing and recall resolution: the recall named by the path must exist. The same identifier is returned by a read aimed at an unknown recall hold, because the catalogue has no separate hold-not-found error.
10. `ERR_AUDIT_NOT_FOUND` (HTTP 404) guards audit completion: the audit named by the path must exist.
11. `ERR_PROGRAM_NOT_FOUND` (HTTP 404) guards store program read and pickup scheduling: the program named by the path or by `program_id` in the body must exist.
12. `ERR_PICKUP_NOT_FOUND` (HTTP 404) guards pickup completion and pickup missing: the pickup named by the path must exist.
13. `ERR_STALE_VERSION` (HTTP 412) guards bid creation and share grants, as described in §2.7. A version mismatch is rejected here, before any state or business rule is evaluated.
14. The load-state errors (HTTP 409) guard the six load lifecycle operations: `ERR_LOAD_NOT_POSTED` when posting a load that is not `POSTED` and when cancelling a load that is neither `POSTED` nor `BIDDING`; `ERR_LOAD_NOT_BIDDING` when awarding or bidding on a load that is not `BIDDING`; `ERR_LOAD_NOT_AWARDED` when recording a freight decision or dispatching a load that is not `AWARDED`; `ERR_LOAD_NOT_IN_TRANSIT` when confirming delivery of a load that is not `IN_TRANSIT`.
15. `ERR_FREIGHT_DECISION_ALREADY_MADE` (HTTP 409) guards the freight decision: the load's `freight_decision` must still be `PENDING`.
16. `ERR_BID_NOT_SUBMITTED` (HTTP 409) guards bid withdrawal: the bid's `bid_status` must be `SUBMITTED`.
17. `ERR_RECALL_NOT_TRACING` (HTTP 409) guards recall tracing and resolution: tracing requires a recall in `OPEN` or `REOPENED`, and resolution requires a recall in `TRACING`.
18. `ERR_AUDIT_NOT_IN_PROGRESS` (HTTP 409) guards audit completion on an audit whose `audit_status` is not `IN_PROGRESS`; `ERR_PICKUP_NOT_SCHEDULED` (HTTP 409) guards pickup completion and pickup missing on a pickup whose `pickup_status` is not `SCHEDULED`.
19. `ERR_MEMBER_NOT_PENDING` (HTTP 409) guards member certification, which requires `PENDING_CERTIFICATION`, and member reinstatement, which requires `PROBATION` or `SUSPENDED`.
20. `ERR_LOAD_SAFETY_HOLD` (HTTP 409) guards posting, bid creation, award and dispatch: the load's `safety_status` must be `CLEAR`, and a `HELD` load is rejected here even when every other rule would pass. A `RECALLED` load is rejected by rank 21 rather than here, because the `RECALLED` test is evaluated before this one; a load is only ever marked `RECALLED` after it has been delivered, so at these four operations the `RECALLED` case can never arise.
21. `ERR_LOAD_RECALLED` (HTTP 409) guards dispatch and delivery of a load whose `safety_status` is `RECALLED`. Because `RECALLED` is set only on a load that has already been delivered, no load can be both `RECALLED` and in a state that dispatch or delivery accepts; the check is defensive and is evaluated before rank 20 wherever both could apply.
22. `ERR_DUPLICATE_BID` (HTTP 409) guards bid creation: the member must have no other `SUBMITTED` bid on the same load.
23. `ERR_STORAGE_CAPACITY_EXCEEDED` (HTTP 409) guards bid creation and award: the load's `weight_lbs` must fit the candidate member's storage for the load's `storage_type`.
24. `ERR_MEMBER_NOT_CERTIFIED` (HTTP 403) guards bid creation, store program registration and pickup scheduling for a member in `PENDING_CERTIFICATION` or `PROBATION`; `ERR_MEMBER_SUSPENDED` (HTTP 403) guards the same three operations for a member in `SUSPENDED`. The exact posture gate per operation is stated in §2.8. The same certified-posture identifier also covers two paths outside that list, each stated where it arises: dispatching a load whose awarded member is no longer certified (§3.7), and scheduling a pickup against a program that is not `ACTIVE` (§3.9).
25. `ERR_AGREEMENT_NOT_ACTIVE` (HTTP 409) guards load creation: the agreement must be `ACTIVE`.
26. `ERR_NO_ELIGIBLE_BIDS` (HTTP 409) guards the award: the selector's candidate set must be non-empty.
27. `ERR_AUDIT_SCORE_OUT_OF_RANGE` (HTTP 400) guards audit creation: `storage_score`, `distribution_score` and `reporting_score` must each be integers between 0 and 100 inclusive. This band test is applied together with the body validation of rank 2 and therefore before the member existence check of rank 5, so a request that names an unknown member and carries an out-of-band score reports this error rather than `ERR_MEMBER_NOT_FOUND`.
28. `ERR_CATEGORY_MISMATCH` (HTTP 409) guards load creation and recall creation: the product category must equal the category recorded on the referenced agreement.
29. `ERR_DELIVERY_WINDOW_INVALID` (HTTP 400) and `ERR_DELIVERY_WINDOW_OVERLAP` (HTTP 409) guard dispatch, as described in §2.12.
30. `ERR_PICKUP_WINDOW_INVALID` (HTTP 400) and `ERR_PICKUP_WINDOW_OVERLAP` (HTTP 409) guard pickup scheduling, as described in §2.12.
31. `ERR_INSUFFICIENT_SHARES` (HTTP 409) guards bid creation and award: the member's `share_balance` must be at least `shares_offered`, and equality is allowed — a member may commit its exact balance.
32. `ERR_SUBSIDY_POOL_EXHAUSTED` (HTTP 409) guards the freight decision: when a subsidy is requested for a member that cannot self-transport, the agreement's remaining subsidy pool must be at least the minimum grantable subsidy.

### 2.10. Nested Resource Retrieval and Reverse Reachability

Paths in this API nest a resource under its context, and the system validates the identifiers left to right. When a path contains more than one identifier, the leftmost identifier is resolved first, and a failure there is reported before the system even attempts to resolve the next one — so a request for a pickup under a program that does not exist yields `ERR_PROGRAM_NOT_FOUND`, never a pickup error. The same left-to-right discipline applies to the member-scoped and agreement-scoped collections, where the member or agreement segment is resolved before the query parameters are applied. Identifiers supplied in the request body are resolved under the same precedence ladder as path identifiers, at the ranks listed in §2.9: a member named in a body is resolved at rank 5, an agreement at rank 6, a load at rank 7 and a program at rank 11, regardless of which of them appears first in the JSON.

Several collections exist purely so that a parent's children can be reached without scanning the whole network: a member's audits, a member's share ledger entries, a member's store donation programs, an agreement's donated loads, an agreement's recalls, and a program's pickups. These are the reverse-reachability views of the corresponding foreign-key fields, they return the same resource shape as the network-wide read of that resource, and they support the optional filters named in §3 — `audit_status`, `epoch`, `program_status`, `status`, `recall_status` and `pickup_status` respectively — in addition to pagination.

### 2.11. Product Safety Containment

A donated load carries two independent dimensions of state. Its allocation `status` describes where the load sits in the bidding and delivery pipeline. Its `safety_status` describes whether the product is fit to move at all, and it takes exactly one of `CLEAR`, `HELD` or `RECALLED`. The two dimensions are orthogonal: a load can be `IN_TRANSIT` and `HELD`, and a load can be `DELIVERED` and `RECALLED`. Every lifecycle operation on a load is guarded by both dimensions.

`safety_status` begins at `CLEAR` for every load. A recall trace moves a matched load to `HELD` when the load has not yet been delivered, and to `RECALLED` when it has — `RECALLED` is terminal and is never left. A `HELD` load may not be posted for bidding, may not be bid on, may not be awarded and may not be dispatched; each of those attempts is rejected with `ERR_LOAD_SAFETY_HOLD`. A `RECALLED` load may not be dispatched or delivered and is rejected with `ERR_LOAD_RECALLED`, a test evaluated before the hold test; because `RECALLED` is set only on a load that has already been delivered, no load that dispatch or delivery would otherwise accept is ever `RECALLED`, so that guard is defensive. Delivery is the one operation a hold does not block: a `HELD` load may still be physically delivered, because the receiving member takes it directly into quarantine, and that delivery is recorded normally. A hold is lifted only when the recall that placed it resolves and no other open recall still holds the load, at which point the load returns to `CLEAR`.

### 2.12. The Logical Clock and Temporal Windows

The server does not read wall-clock time. It runs on a logical clock whose startup default is `2026-09-01T00:00:00Z`, and it must not fall back to the host clock before that default is overridden. An administrator sets the clock through a test-driving capability that accepts a `current_utc` instant, and from that point on every window comparison, expiry test and scheduled-date test in the system uses the logical clock value. This includes delivery appointment windows, retail pickup windows, the pickup completion tolerance, the `scheduled_date` floor on new pickups, and the timestamp stamped on a newly opened recall.

Delivery appointment windows and retail pickup windows are both half-open intervals. A window runs from its `window_start` up to but not including its `window_end`, which means two windows that merely touch — one ending exactly where the next begins — do not overlap and are both legal. A window whose start is not strictly before its end is malformed. A delivery window must also lie at or after the current logical clock time, and a pickup window must fall on its `scheduled_date`, which itself may not be in the past. Retail pickups carry one additional spacing rule beyond non-overlap: the same program's next pickup may not begin less than 24 hours after the previous pickup's window ends. The distinction between a malformed window and a colliding one matters, because the two produce different error codes with different HTTP statuses, as listed in §2.9.

## 3. Business Logic & Workflows

### 3.1. Member Food Bank Onboarding, Standards Audits, and Certification Posture

A member food bank enters the network through a registration request submitted by a national administrator with the member's legal `name`, the two-letter `state_code` of the territory it serves, its `food_insecure_population`, its `storage_capacity_lbs`, its `refrigerated_capacity_lbs` and its `transport_ability`. The name must be non-empty and unique within its state among members that are `PENDING_CERTIFICATION`, `CERTIFIED` or `PROBATION` — a suspended member's name does not reserve the slot, and a duplicate is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The state code must be exactly two uppercase letters. The food-insecure population may be zero but not negative. Total storage must be strictly positive, and the refrigerated figure — which covers both refrigerated and frozen space — may be zero but may never exceed total storage. `transport_ability` records the furthest reach the member can haul on its own and is one of `NONE`, `LOCAL`, `REGIONAL` or `NATIONAL`. Registration produces a member whose `certification_status` is `PENDING_CERTIFICATION` with a zero `share_balance`, a zero `share_reserved`, a zero `audit_score`, a zero `active_bid_count` and a null `last_grant_epoch`.

Standards are assessed through audits. An administrator opens an audit against a member, naming the `audit_type` — `STORAGE`, `DISTRIBUTION`, `REPORTING` or `COMPREHENSIVE` — and supplying three component scores: `storage_score`, `distribution_score` and `reporting_score`, each an integer from 0 to 100 inclusive. A score outside that band is rejected as `ERR_AUDIT_SCORE_OUT_OF_RANGE` before the audit row is created, and a member in `SUSPENDED` posture may not be audited at all, that rejection carrying `ERR_MEMBER_SUSPENDED` (HTTP 403). Opening an audit stamps `opened_by_user_id` from the caller's `X-User-ID`, sets the row to `IN_PROGRESS`, and computes its `weighted_score` immediately using the audit-type weighting described in §3.1.1. The `weighted_score` is the audit's headline number: it is a value between 0 and 100 expressed to one decimal place, rounded half up, and it is recomputed at completion as well as at creation.

Completion is the auditor's act, and it is deliberately separated from opening. The completing operator's `X-User-ID` must differ from the audit's recorded `opened_by_user_id`, or the request is rejected with `ERR_SEGREGATION_OF_DUTIES`; this is enforced even when the caller holds the auditor role, and it is the only operation in the system that the auditor role may perform. Completion is only possible while the audit is `IN_PROGRESS`, otherwise `ERR_AUDIT_NOT_IN_PROGRESS`. A weighted score of 85 or above passes the audit and sets the audit to `PASSED`; anything below 85 fails it and sets the audit to `FAILED`. Either way, the member's `audit_score` is overwritten with this audit's `weighted_score`. The member's `audit_score` is always the floor of the most recently completed audit's weighted score, clamped at zero, and it is zero while no audit has completed.

#### 3.1.1. Audit Weighting

The three component scores are combined into a single weighted score according to the audit's type. A `STORAGE` audit weights storage at 60 percent, distribution at 20 percent and reporting at 20 percent. A `DISTRIBUTION` audit weights storage at 20 percent, distribution at 60 percent and reporting at 20 percent. A `REPORTING` audit weights storage at 20 percent, distribution at 20 percent and reporting at 60 percent. A `COMPREHENSIVE` audit weights storage at 40 percent, distribution at 30 percent and reporting at 30 percent. Each component is multiplied by its weight and divided by 100, the three terms are added, and the sum is rounded half up to one decimal place. The result is compared against the pass mark of 85: at or above passes, below fails.

One variant modifies this weighting, and it applies only when the audit being scored is itself a `STORAGE` audit. When the member under audit has any `FAILED` `STORAGE` audit within the preceding 12 months — a window of 365 days back from the current logical clock, tested against the earlier audit's `created_at` — the storage weight is raised to 70 percent and the distribution and reporting weights drop to 15 percent each. A `COMPREHENSIVE`, `DISTRIBUTION` or `REPORTING` audit always uses its own table weights however recent the member's failed storage audit. The same three component scores can therefore cross the pass mark in opposite directions depending on the member's recent history, so the weighting must be selected before the score is computed, not after.

#### 3.1.2. Certification, Probation, Suspension and Reinstatement

A member may be certified only from `PENDING_CERTIFICATION`, and only after it has completed a `COMPREHENSIVE` audit that `PASSED`; its total storage capacity must also be strictly positive, a condition registration already guarantees. A certification attempt that finds no passed `COMPREHENSIVE` audit on record is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Certification sets the member to `CERTIFIED`, sets the member's `audit_score` to the weighted score of that latest passed comprehensive audit, and immediately activates the member's retail store programs: every one of its programs sitting in `PENDING` becomes `ACTIVE`, and those programs become eligible for new pickups while the pickup windows they already hold are left untouched. A certification attempt on a member that is not in `PENDING_CERTIFICATION` is rejected with `ERR_MEMBER_NOT_PENDING`.

Posture degrades automatically in two ways. A completed audit whose weighted score falls below 85 demotes a `CERTIFIED` member to `PROBATION`; if the member is already on `PROBATION`, the same failure moves it to `SUSPENDED`. The award cascade can also demote: a `CERTIFIED` member whose recomputed `share_balance` falls below 50 shares as a result of winning a load drops to `PROBATION` (see §3.5). When a member enters `PROBATION`, every one of its `ACTIVE` retail programs is suspended, and each of those programs' pickups that is still `SCHEDULED` for today or a later date is marked `MISSED`. When a member enters `SUSPENDED`, the same program suspension applies, and in addition every one of the member's `SUBMITTED` bids is withdrawn with `rejection_reason` `MEMBER_SUSPENDED`, each withdrawal releasing the held shares through a `BID_RELEASE` ledger entry and recomputing the member's `share_balance`, `share_reserved` and `active_bid_count`.

Reinstatement runs in the opposite direction and is deliberately asymmetric. A member on `PROBATION` is reinstated to `CERTIFIED` only when its `audit_score` is at least 85 and it holds at least 100 shares. A member that is `SUSPENDED` is reinstated only to `PROBATION` — never directly to `CERTIFIED` — and needs only an `audit_score` of at least 85, with no share-balance requirement. Reinstatement to `CERTIFIED` reactivates every `SUSPENDED` retail program belonging to the member. An attempt to reinstate a member that is `PENDING_CERTIFICATION` or already `CERTIFIED` is rejected with `ERR_MEMBER_NOT_PENDING`, while a member that is in the right posture but fails either floor — an `audit_score` below 85, or, for a `PROBATION` member, a `share_balance` below 100 — is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Because a member reaches `SUSPENDED` only through a completed audit that failed, which leaves its `audit_score` below 85, and because a `SUSPENDED` member may not be audited at all, that `audit_score` floor is never met in practice and reinstatement out of `SUSPENDED` is unreachable by construction; the floor is nonetheless enforced for every reinstatement request. Both certification and reinstatement increment the member's `version`.

### 3.2. The Share Currency Economy: Epoch Grants and the Ledger

Share currency enters the network through epoch grants. A grant request names the `member_id`, an `epoch` label of the form year-month, an optional `activity_basis`, and the mandatory `expected_member_version` described in §2.7. Although the request addresses a single member, the calculation behind it is network-wide: the granted amount is the member's proportional slice of a fixed epoch pool of 100,000 shares, so a grant cannot be computed for one member without reference to every other eligible member's demand.

The eligible set is the members currently in `CERTIFIED` or `PROBATION` posture. Each eligible member's demand is built in three steps. First, a base term: the member's `food_insecure_population` divided by one thousand, rounded down to a whole number of thousands, multiplied by 120 shares. Second, an activity term: the pounds that member delivered in the epoch immediately preceding the one being granted, divided by ten thousand, rounded down to a whole number of ten-thousand-pound blocks, multiplied by 15 shares. The activity term counts loads that reached `DELIVERED` with a positive `delivered_lbs` figure and whose delivery fell in that prior epoch. Third, a posture weight: a `CERTIFIED` member's combined base and activity total is multiplied by 100 and divided by 100 — that is, taken whole — while a member on `PROBATION` is weighted at 50 percent, so the combined total is multiplied by 50 and divided by 100. That third step floors as well, so a probationary member's fractional share is discarded rather than carried.

The member's resulting demand is then divided by the sum of every eligible member's demand, multiplied by the pool of 100,000 shares, and floored to a whole number of shares. Because flooring discards a fraction for each member independently, the grants will usually sum to less than the pool; the difference is the residual. Residual shares are handed out one share at a time, in descending order of the fractional part that was discarded — the fractional part of the exact proportional entitlement before flooring — with the earliest member `created_at` breaking ties between equal fractions. Ties are never broken by identifier. The distribution continues until the residual is exhausted, so a member may receive more than one residual share if its fraction stays at the top of the remaining order.

Two evaluation-order rules are part of the specification, not implementation detail. Every member's demand is computed from the pre-grant state in a single pass: applying one member's grant never feeds back into another member's demand within the same epoch. And the residual is assigned in a single pass over the frozen fractional parts, in the descending order described above, so the ordering cannot shift as shares are handed out. Each grant then appends one ledger entry of type `GRANT` whose `amount` is the member's grant, tagged with the epoch label, and sets the member's `last_grant_epoch` to that epoch; a member that is not in the eligible set, or whose computed grant is zero, still gets its row — with an `amount` of zero — and still has `last_grant_epoch` set. The endpoint returns `201 Created`, and the response data is that newly appended ledger entry rather than the member. The member's balance is reconciled from the ledger as described in §2.5, and the member's `version` increments.

One variant changes the activity term. When the grant request carries `activity_basis` set to `FORWARD_LOOKING`, the activity term counts prior-epoch loads whose status is `AWARDED`, `IN_TRANSIT` or `DELIVERED` rather than `DELIVERED` alone. A load that has been delivered is still attributed to the epoch of its delivery and contributes its `delivered_lbs`; an undelivered load is attributed to the epoch of its award, or of its dispatch once dispatched, and contributes its full `weight_lbs`. A member with committed but undelivered poundage therefore receives a strictly larger activity term, and therefore a larger grant, than the same member would receive from identical delivered data under the default basis.

The ledger itself is readable per member as an append-ordered list, optionally filtered to a single `epoch`. The listing preserves the order in which entries were appended, which is the same order used to reconstruct the balance.

### 3.3. Donor Agreements and the Truckload Pipeline

A donor agreement is the national instrument under which product is pledged. An administrator creates one with the `donor_name`, a `donor_type` of `MANUFACTURER`, `RETAILER` or `DISTRIBUTOR`, a `product_category` of `DRY_GOODS`, `PRODUCE`, `DAIRY`, `FROZEN_PROTEIN` or `BAKERY`, the `committed_lbs` pledged for the year — strictly positive — and the `freight_subsidy_pool_cents` the agreement makes available for haulage in the current program year, which may be zero but not negative. The `meal_equivalency_factor`, the pounds-per-meal divisor used for that donor's reporting, is optional and defaults to 1.2; when supplied it must be strictly positive. An agreement's `status` is always exactly one of `DRAFT`, `ACTIVE`, `SUSPENDED` or `CLOSED`, and only `ACTIVE` is operational. A new agreement starts in `DRAFT` with `freight_subsidy_used_cents` at zero, and only becomes usable when an administrator activates it: activation moves any agreement that is not already `ACTIVE` — `DRAFT`, `SUSPENDED` or `CLOSED` — to `ACTIVE` and increments its `version`, while activating one that is already `ACTIVE` returns it unchanged and leaves its `version` alone. Until then it accepts no loads at all, and an attempt to create a load against a non-active agreement is rejected with `ERR_AGREEMENT_NOT_ACTIVE`.

Loads are the truckloads drawn against an agreement. Creating one requires the `donor_agreement_id`, a `product_category` that must equal the agreement's own category — a mismatch is rejected with `ERR_CATEGORY_MISMATCH` — a `storage_type` of `DRY`, `REFRIGERATED` or `FROZEN`, a strictly positive `weight_lbs`, the manufacturer's `lot_code` which is the trace key used later by recalls, an `origin_zip` of exactly five digits, a `destination_region` of `NORTHEAST`, `SOUTHEAST`, `MIDWEST`, `SOUTHWEST` or `WEST`, and the one-way `distance_miles` from the donor's distribution center to whoever eventually wins the load, which must be strictly positive.

A newly created load starts in `POSTED` with `safety_status` `CLEAR`, `freight_decision` `PENDING`, `delivered_lbs` zero, `meal_equivalent` zero, `delivery_window_start` and `delivery_window_end` null, and both `awarded_bid_id` and `awarded_member_id` null. A load in `POSTED` is visible but not yet open for bids. An administrator opens it by posting it, which requires that the load is still `POSTED`, that its `safety_status` is `CLEAR`, and that the agreement it was drawn from is `ACTIVE`; posting moves the load to `BIDDING`, refreshes its `updated_at` and increments its `version`, and makes it discoverable in the load listings filtered to `BIDDING`. The agreement's loads can be listed through the reverse-reachability view, optionally filtered by `status`.

Cancellation is the network's exit for a load that will not move. It is available only while the load is still `POSTED` or still `BIDDING`; a load that has been awarded, dispatched, delivered or already cancelled cannot be cancelled, and such an attempt is rejected with `ERR_LOAD_NOT_POSTED`. Cancelling a load releases every commitment made against it. Every bid still `SUBMITTED` on that load becomes `REJECTED` with `rejection_reason` `LOAD_CANCELLED`; each of those rejections appends a `BID_RELEASE` ledger entry for the positive `shares_offered` amount and recomputes the affected member's `share_balance`, `share_reserved` and `active_bid_count`. The load itself moves to `CANCELLED`, which is terminal, and its `version` increments.

### 3.4. Bidding: Claiming a Posted Load with Share Currency

Bidding is the member's only route to product. A member food bank submits a bid carrying its own `member_id`, the `shares_offered` it commits — strictly positive — its own `preference_rank` for the load, a value of at least 1 where 1 means most preferred, a `can_self_transport` flag recording whether it can perform the haul without a network-subsidized carrier, and the mandatory `expected_load_version` described in §2.7 — a bid whose `expected_load_version` no longer matches the load's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412) before any state check or business rule is evaluated.

Six gates stand in front of a new bid, and they are evaluated in the order set out in §2.9. The load must exist and be in `BIDDING` status — bidding on a load that has not been posted, or on one that has already been awarded, is rejected with `ERR_LOAD_NOT_BIDDING`. Its `safety_status` must be `CLEAR`, so a load under a recall hold cannot attract new commitments and is rejected with `ERR_LOAD_SAFETY_HOLD`. The bidding member must be in `CERTIFIED` or `PROBATION` posture: a member in `PENDING_CERTIFICATION` is rejected with `ERR_MEMBER_NOT_CERTIFIED`, and a member in `SUSPENDED` is rejected with `ERR_MEMBER_SUSPENDED`. The member's `share_balance` must be at least the `shares_offered` amount, with equality permitted — a member may commit its exact balance and end at zero — and a shortfall is rejected with `ERR_INSUFFICIENT_SHARES`; this gate reads the balance as it stands before the new bid's own hold is appended, which is what makes that equality possible, and it is therefore not the same test the award selector applies later. The member may hold only one live bid per load, so a second `SUBMITTED` bid on the same load is rejected with `ERR_DUPLICATE_BID`. Finally the load must physically fit: a `REFRIGERATED` or `FROZEN` load requires the member's `refrigerated_capacity_lbs` to be at least the load's `weight_lbs`, and a `DRY` load requires the member's total `storage_capacity_lbs` to be at least that weight; a load that does not fit is rejected with `ERR_STORAGE_CAPACITY_EXCEEDED`. Where that enumeration departs from the §2.9 ranking, the ranking governs: a duplicate live bid is reported before a storage-capacity failure, a storage-capacity failure before a posture failure, and a posture failure before a shortfall in shares, so a member that is both uncertified and short of shares is told it is uncertified.

An accepted bid is created in `SUBMITTED` status with a `submitted_round` equal to one plus the number of bids this member has previously placed on this load, so a member that withdraws and re-bids is visibly on its second round. The commitment is real money: the create appends a `BID_HOLD` ledger entry whose `amount` is the negative of `shares_offered`, which reduces the member's `share_balance` by that amount, raises the member's `share_reserved` by the same amount, and increments the member's `active_bid_count`. The bid itself also bumps the load's `version`, because the load's bidding state has changed.

A member may withdraw a bid it owns at any time while the bid is `SUBMITTED`; a bid that is already `AWARDED`, `REJECTED` or `WITHDRAWN` cannot be withdrawn and yields `ERR_BID_NOT_SUBMITTED`. Withdrawal by the member records `rejection_reason` `WITHDRAWN_BY_MEMBER`, releases the hold with a `BID_RELEASE` entry of the positive `shares_offered` amount, and recomputes the member's `share_balance`, `share_reserved` and `active_bid_count`. Withdrawal is a shared operation: a national administrator may also withdraw a bid, though the member ownership rule in §2.1 still applies to member callers, who may only touch their own bids. An administrator-initiated withdrawal writes the same `WITHDRAWN_BY_MEMBER` reason as a member's own, since the field records how the bid left the pool rather than who ended it. The bid is resolved before ownership can be compared, so withdrawing an unknown bid id returns `ERR_BID_NOT_FOUND` even for a member caller who could not have owned it.

Bids are readable network-wide through a paginated list that accepts optional `load_id`, `member_id` and `bid_status` filters, and individually by identifier. The `rejection_reason` field carries the reason a bid left the active pool: it is populated when the bid is `REJECTED` or `WITHDRAWN`, and it is null while the bid is `SUBMITTED` or `AWARDED`.

### 3.5. Awarding a Load and the Ranking Selector

Awarding is where the network's transport economics meet the members' stated preferences, and it is performed by a national administrator against a load in `BIDDING` status whose `safety_status` is `CLEAR`. The award first assembles a candidate set from the load's bids. A bid qualifies as a candidate only if it is still `SUBMITTED`, if its member is in `CERTIFIED` or `PROBATION` posture, if that member's `share_balance` is at least the bid's `shares_offered`, and if the load physically fits that member under the same storage rule the bid was required to satisfy at submission time. That balance is the stored ledger sum of §2.5, which the bid's own `BID_HOLD` has already reduced by the shares it offered, so the comparison is made against the hold-reduced figure and not against the balance the member held before bidding; a bid is therefore awardable only while the member's balance after its own hold still covers the shares offered, and a member that committed its entire balance at submission can never be a candidate. A bid that fails any of those conditions is not a candidate and is simply left out of the ranking rather than raising an error of its own. If the filter leaves no candidate at all — whether because no bid was ever submitted or because every submitted bid was filtered out — the award is rejected with `ERR_NO_ELIGIBLE_BIDS`. Two of those conditions are the same rules that guard bid creation, where they surface as `ERR_STORAGE_CAPACITY_EXCEEDED` and `ERR_INSUFFICIENT_SHARES`; at award time they take effect through this eligibility filter, so a member whose storage posture or share balance has fallen away since it bid is not awardable and cannot win the load.

Candidates are ranked by a weighted score. The score adds 100 points for every share offered — the share commitment is by far the dominant term — plus 40 points when the bidder declared it can self-transport the haul, plus a transport bonus based on the member's `transport_ability`: 30 points for `NATIONAL`, 20 for `REGIONAL`, 10 for `LOCAL` and nothing for `NONE`. From that total the selector subtracts two points for every full 100 miles of the load's `distance_miles` — the mileage term is floored to whole hundreds before the penalty is applied — and subtracts a further 25 points when the member is on `PROBATION`. The score is an integer and requires no rounding. The bid with the highest score wins.

Ties are resolved in two steps, in order: the earliest bid `created_at` wins, and if two bids were created at the same instant, the earliest member `created_at` wins. The `preference_rank` the member supplied is not part of the default ranking at all.

One variant inverts the priority. When the award request carries `ranking_basis` set to `PREFERENCE_FIRST`, the candidate set is ordered by `preference_rank` ascending first, and the weighted score is used only to break ties between candidates that declared the same preference rank. Under that basis a member's own stated priority outranks the network's transport-efficiency calculation, which is the point of the variant: a member that most wants a particular load can say so and be taken at its word.

#### 3.5.1. The Award Cascade

Selecting a winner triggers a cascade that touches the winning bid, every losing bid, every affected member and the load itself, in a fixed order.

The selected bid becomes `AWARDED`, and the load records the winner through `awarded_bid_id` and `awarded_member_id`. Every other bid still `SUBMITTED` on that load becomes `REJECTED` with `rejection_reason` `LOSING_BID`; each of those rejections releases the losing member's hold by appending a `BID_RELEASE` entry for the positive `shares_offered` amount and recomputing that member's `share_balance`, `share_reserved` and `active_bid_count`.

The winner's own hold is then unwound in two steps that must both appear in the ledger: first a `BID_RELEASE` entry returning the held `shares_offered`, then an `AWARD_DEBIT` entry of the negative `shares_offered` amount that actually spends the currency on the load. The winner's balance therefore ends where it began in net terms, while its `share_reserved` falls by the released hold and its `active_bid_count` drops by one, because the bid is no longer `SUBMITTED`. All three derived values are reconciled from the ledger and the live bids after both entries are appended.

That reconciliation can demote the winner. The release and the debit cancel out in the balance, so the figure the demotion test reads is the same hold-reduced balance the member carried into the award. If the winner's recomputed `share_balance` is below 50 shares and the winner is `CERTIFIED`, its posture drops to `PROBATION`. When that happens, a further hop fires: every other bid that member still holds in `SUBMITTED` status anywhere in the network is withdrawn — `bid_status` `WITHDRAWN` with `rejection_reason` `MEMBER_PROBATION` — and each withdrawal appends a `BID_RELEASE` entry for the positive `shares_offered` amount and recomputes that member's `share_balance`, `share_reserved` and `active_bid_count`. The same demotion also suspends the member's `ACTIVE` retail programs under the rules in §3.1.2.

Finally the load's freight position is reset for the new award. The load's `freight_estimate_cents` is recomputed from the haul distance and the winner's `transport_ability`, the `freight_decision` is set back to `PENDING`, `freight_subsidy_cents` is set to zero, and `member_freight_due_cents` is set equal to the full estimate, since no subsidy has yet been granted. The load moves to `AWARDED` and its `version` increments.

### 3.6. Freight Coverage Decisions and the Cost of Reaching Remote Members

Freight is the network's answer to a geographic mismatch: the members serving the largest food-insecure populations are often the ones furthest from a donor's dock, and an unsubsidized haul can cost more than the load is worth to them. Each agreement carries its own `freight_subsidy_pool_cents` budget, and each load carries a `freight_decision` that is `PENDING` from award until the network rules on coverage.

The cost of the haul is built from a base amount: the load's `distance_miles` plus any recorded `detour_miles`, multiplied by the network's standard haulage rate of 185 cents per mile. Against that base, the network's share depends on how far the awarded member can haul by itself. A member that declared `can_self_transport` on its winning bid receives no network share at all, because it is bearing the haul itself. Otherwise the share is set by the member's `transport_ability`: 30 percent for a `NATIONAL` carrier, 55 percent for `REGIONAL`, 75 percent for `LOCAL` and the full 100 percent for a member with `NONE`. The network's share of the base is rounded up to the next whole cent.

A remote uplift applies on top, and only to the members least able to absorb the cost. When the member cannot self-transport, the haul is at least 400 miles — a threshold tested against the load's `distance_miles` alone, ignoring any recorded `detour_miles` — and the member's `transport_ability` is `NONE` or `LOCAL`, an additional uplift of 15 percent of the base is computed and rounded up to the next whole cent. A `REGIONAL` or `NATIONAL` carrier never receives the uplift however long the haul, and a member that can self-transport never receives it either.

The two components are added, and the sum is then capped by two independent ceilings: the agreement's remaining pool, which is the `freight_subsidy_pool_cents` minus the `freight_subsidy_used_cents` already committed, and a per-load maximum of 250,000 cents. The lower of the three governs. A resulting subsidy below 5,000 cents is then collapsed to zero — the network does not write small cheques, and a subsidy that cannot reach 50 dollars is treated as no subsidy at all. Whatever survives becomes `freight_subsidy_cents`, and the member's `member_freight_due_cents` is the base minus that subsidy, a difference that is not clamped at zero: a subsidy larger than the base, which the remote uplift can produce, leaves the due amount negative.

The decision the network records follows from the computed subsidy. A positive subsidy means the load is `COVERED`. A subsidy that collapsed to zero means `DECLINED` for a member that cannot self-transport, and `COVERED` for a member that can — a self-transporting member is covered in the sense that it bears the haul itself, with a zero subsidy and a due amount equal to the full base. The request's own `decision` is honoured when it asks for `DECLINED`: for a member that can self-transport that is recorded as `DECLINED`, with a zero subsidy and a due amount equal to the full base recomputed with any `detour_miles` supplied, and the agreement's pool is not touched. The `freight_decision` field is zero-valued on subsidy until it becomes `COVERED`, and recording a `COVERED` decision immediately commits that subsidy against the agreement's freight budget: the agreement's `freight_subsidy_used_cents` is increased by the load's `freight_subsidy_cents`, so that field always equals the sum of `freight_subsidy_cents` across the agreement's loads whose `freight_decision` is `COVERED`.

Two rounds of computation exist, and they can disagree. The provisional computation happens at award time and fixes `detour_miles` at zero, so it uses the straight-line haul distance only; it therefore always produces a subsidy less than or equal to what the final computation will produce once a detour is recorded. The final computation happens when the administrator records the decision, taking the `decision` and the optional `detour_miles` from the request and recomputing the subsidy against the full base. The request must name a load that is `AWARDED`, or it is rejected with `ERR_LOAD_NOT_AWARDED`, and the load's `freight_decision` must still be `PENDING`, or it is rejected with `ERR_FREIGHT_DECISION_ALREADY_MADE`; the decision is a single irreversible act per award. When the request asks the network to cover a member that cannot self-transport, the agreement's remaining pool must be at least the 5,000-cent minimum grantable subsidy, or the request is rejected with `ERR_SUBSIDY_POOL_EXHAUSTED`. That pool test fires only for a `COVERED` request aimed at a member that cannot self-transport, it is evaluated before the subsidy is computed and before anything is written, so a rejected request leaves the load, the agreement and the member untouched, and it does not apply to a `DECLINED` request however small the pool. A `COVERED` request whose computed subsidy then collapses below the 5,000-cent minimum is not an error: it is treated exactly as a `DECLINED` outcome for a member that cannot self-transport, and the award unwinds as described below.

A `DECLINED` outcome for a member that cannot self-transport does not merely record a refusal; it unwinds the award. The load returns to `BIDDING`, `awarded_bid_id` and `awarded_member_id` are cleared to null, `freight_decision` returns to `PENDING`, `freight_subsidy_cents` is zeroed, and `member_freight_due_cents` is zeroed — a zero due amount signals that no member currently owes freight on this load — while `freight_estimate_cents` is not reset and keeps the provisional award-time estimate it already carried. The winning bid becomes `REJECTED` with `rejection_reason` `FREIGHT_DECLINED`, and the member's spend is returned by an `AWARD_REFUND` ledger entry of the positive `shares_offered` amount, which restores the balance to its pre-award value and decrements the member's `active_bid_count`. The load's `version` increments again. A load that has been unwound this way is back in the bidding pool and may be awarded afresh to a different member.

### 3.7. Dispatch, Delivery Confirmation, and Donor Poundage Reporting

A load that has been awarded and whose freight position is settled — `freight_decision` at `COVERED` or at `DECLINED` — may be dispatched. Dispatch requires the load to be `AWARDED` — a load that is awarded but whose freight decision has not yet been recorded is refused with `ERR_LOAD_NOT_AWARDED`, the error the status test itself returns — its `safety_status` to be `CLEAR`, and the awarded member to still be in `CERTIFIED` or `PROBATION` posture, an awarded member whose posture has fallen away being refused with `ERR_MEMBER_NOT_CERTIFIED` (HTTP 403). It also requires a delivery appointment window, supplied as `delivery_window_start` and `delivery_window_end`. The window must be properly ordered, with the start strictly before the end, and both endpoints must be at or after the current logical clock time; a window that is malformed in either respect is rejected with `ERR_DELIVERY_WINDOW_INVALID`. The window must also not collide with the same member's existing commitments: no other load of that same awarded member that is currently `IN_TRANSIT` may hold a delivery window that overlaps the new one, and a collision is rejected with `ERR_DELIVERY_WINDOW_OVERLAP`. Because the intervals are half-open, a window that begins exactly when another ends is legal. A load under a recall hold cannot be dispatched, and a load that has been recalled outright cannot be dispatched at all.

Dispatch moves the load to `IN_TRANSIT` and increments its `version`. A covered load's subsidy is carried on the agreement's books through dispatch: the agreement's `freight_subsidy_used_cents` is by definition the sum of `freight_subsidy_cents` across the agreement's loads whose `freight_decision` is `COVERED`, so it already reflects this load's subsidy from the moment the coverage decision was recorded, and dispatching the load leaves that figure standing at the same total rather than charging the pool a second time. A load that is never dispatched still holds its covered subsidy against the agreement's budget, because the commitment was made when the decision was recorded.

Delivery confirmation closes the haul. It requires a load in `IN_TRANSIT` — anything else is `ERR_LOAD_NOT_IN_TRANSIT` — and permits the load's `safety_status` to be either `CLEAR` or `HELD`, because a load that came under a hold while in transit may still be physically delivered, straight into the receiving member's quarantine. A load whose `safety_status` is `RECALLED` may not be delivered and is rejected with `ERR_LOAD_RECALLED`. On delivery, `delivered_lbs` is set to the load's full `weight_lbs` and the load's `meal_equivalent` is computed as the delivered pounds divided by the agreement's `meal_equivalency_factor`, floored to a whole number of meals.

Delivery also pays the member. An `ACTIVITY_BONUS` ledger entry is appended for the awarded member, worth 15 shares for every full ten thousand pounds delivered — the delivered poundage is divided by ten thousand and floored before the multiplier is applied. The member's `share_balance` is then reconciled, and that reconciliation deliberately does not reinstate anybody: a member on `PROBATION` whose new balance has reached 100 shares or more and whose `audit_score` is at least 85 stays on `PROBATION`, because reinstatement is a deliberate administrative act performed through the member reinstatement operation and never an automatic side effect of earning shares back. The load moves to `DELIVERED` and its `version` increments.

#### 3.7.1. Donor Poundage and Meal Equivalency Reporting

Donors are told what their product became, and the poundage summary is the instrument. It reports the agreement's `donor_agreement_id`, the `total_lbs` delivered under it, the `total_meals` those pounds represent, and the `delivered_load_count` behind both figures. The population it summarizes is the agreement's loads that reached `DELIVERED` with a positive `delivered_lbs`; loads that were cancelled, and loads whose product was recalled, are excluded from the rollup entirely.

The canonical computation floors each load's meals before summing: for every qualifying load, `delivered_lbs` is divided by the agreement's `meal_equivalency_factor` and floored to a whole number of meals, and those per-load meal counts are then added together. The poundage total is the plain sum of the same set's `delivered_lbs`. The request accepts an optional `rounding_basis`; when it is set to `SUM_THEN_DIVIDE`, the computation instead sums the pounds first and divides once — `total_lbs` divided by the agreement's factor, floored — so that the remainders discarded by the canonical per-load flooring are preserved. For identical loads the two bases produce different meal totals, usually with the sum-then-divide variant reporting more meals, because per-load remainders accumulate rather than being dropped.

### 3.8. Product Safety: Recall Tracing and Network-Wide Holds

A recall begins with a donor's report. An administrator opens one against a `donor_agreement_id` with the affected `lot_code`, the `product_category` of the recalled product — which must match the agreement's own category or the request is rejected with `ERR_CATEGORY_MISMATCH` — the `affected_lbs` the donor reports, which may be zero but not negative, and an optional `scope`. The `scope` supplied at creation is remembered on the recall even though it is never returned in the response, and it governs any later trace that does not carry a scope of its own; a trace request may carry its own `scope`, which overrides the stored one for that trace without changing what the recall remembers. The recall is stamped with `opened_at` from the logical clock and starts with a `traced_load_count` of zero and a `held_lbs` of zero.

Whether the recall opens as `OPEN` or as `REOPENED` is decided by the network, not by the caller, and it depends on history: if no recall for the same agreement and the same lot code exists, the new row opens in `OPEN`; if a recall for that agreement and lot already exists in any state — including one that was already resolved — the new row is created directly in `REOPENED` and the earlier row is left completely untouched. A reopened recall is the network's way of saying the same lot has come back to haunt it, and it re-enters the tracing workflow immediately.

Tracing is the containment act. It may be run on a recall in `OPEN` or in `REOPENED` — a recall that has already been resolved is rejected with `ERR_RECALL_NOT_TRACING` — and both starting states execute the identical cascade. The trace matches the loads of the recall's agreement whose `lot_code` equals the recall's `lot_code`, considering loads in any status except `CANCELLED`; a `scope` of `DONOR_WIDE` matches every such load regardless of lot code, and a `scope` of `CATEGORY` matches every such load whose `product_category` equals the recall's own category, while any other value — including an absent one — falls back to the lot-code match. The number of matched loads becomes the recall's `traced_load_count`.

Each matched load is then handled according to what has already happened to it. A matched load that has not yet been delivered and weighs at least 500 pounds receives a `RecallHold` row in `ACTIVE` status; a matched load that has not been delivered and weighs less than 500 pounds is counted as traced but is not held, because the network does not open a quarantine case over a partial pallet. A matched load that has already been `DELIVERED` cannot be held at all — the product is out in the field — and instead has its `safety_status` set to `RECALLED`, which is terminal. Every load whose `safety_status` is moved to `HELD` in this pass also has its `version` incremented — a load already `HELD` by an earlier recall gains the new hold but is otherwise left alone, so its `version` does not move — and if that load was in `BIDDING` status, every one of its `SUBMITTED` bids is rejected with `rejection_reason` `LOAD_SAFETY_HOLD`, each rejection appending a `BID_RELEASE` entry of the positive `shares_offered` amount and recomputing the affected member's `share_balance`, `share_reserved` and `active_bid_count`. Finally the recall's `held_lbs` is set to the sum of `weight_lbs` across all of its `ACTIVE` holds, and the recall moves to `TRACING`.

One variant widens the net. When the recall request carries `scope` set to `DONOR_WIDE`, the trace matches every load of the donor agreement regardless of lot code, so both `traced_load_count` and `held_lbs` are strictly larger for the same recall row than they would be under the default lot-scoped trace. The holds created by a trace record which scope matched them through their `hold_reason` field, which takes the value `LOT_MATCH` for a lot-code match, `CATEGORY_MATCH` for a category-scoped match and `DONOR_WIDE_TRACE` for a donor-wide trace.

Resolution releases the network's grip. A recall may be resolved only from `TRACING` — anything else is `ERR_RECALL_NOT_TRACING` — and only when it has either held something or found nothing: the recall's `held_lbs` must be greater than zero, or its `traced_load_count` must be zero, so an unresolved trace that found product but somehow holds none cannot be closed, that refusal carrying `ERR_RECALL_NOT_TRACING` (HTTP 409), the same error the state test returns. Every `ACTIVE` hold belonging to the recall is set to `RELEASED`, and each affected load that was `HELD` and has no other recall's `ACTIVE` hold upon it returns to `CLEAR`. The recall's `held_lbs` drops to zero and its `recall_status` becomes `RESOLVED`.

Holds are readable network-wide through a paginated list that accepts optional `recall_id`, `load_id` and `hold_status` filters, and individually by identifier; a read aimed at an unknown hold identifier is rejected with `ERR_RECALL_NOT_FOUND` (HTTP 404), because the catalogue has no separate hold-not-found identifier. A hold's `hold_status` is always exactly one of `ACTIVE`, `RELEASED` or `DESTROYED`, and a hold that has been `RELEASED` or `DESTROYED` remains visible in that list, because the record of what was quarantined is part of the audit trail.

### 3.9. Retail Store Donation Programs and Pickup Logistics

Local retail donation is the network's second supply channel, and it runs under a member's own certification rather than under a national agreement. A member — or a national administrator acting on a member's behalf — registers a program with the `member_id`, the `store_name` and `store_chain`, a `pickup_frequency` of `DAILY`, `WEEKLY` or `BIWEEKLY`, and the `expected_weekly_lbs` contracted from that store, which may be zero but not negative. The program's posture is derived from the owning member's at registration time: a member already `CERTIFIED` gets an `ACTIVE` program immediately, while a member in `PENDING_CERTIFICATION` or `PROBATION` gets a `PENDING` program that becomes `ACTIVE` later, when the member is certified. A member in `SUSPENDED` posture may not register a program at all and is rejected with `ERR_MEMBER_SUSPENDED`. No pickup may be scheduled against a program that is not `ACTIVE`, and such an attempt is rejected with `ERR_MEMBER_NOT_CERTIFIED` (HTTP 403) — the identifier the posture gate also uses — even when the owning member is itself `CERTIFIED` and the program was suspended by the consecutive-miss rule.

Scheduling a pickup supplies a `scheduled_date` and a window bounded by `window_start` and `window_end`. The window must be properly ordered and must fall on the `scheduled_date`, and the `scheduled_date` may not be earlier than the current logical clock date; a window that violates either rule is rejected with `ERR_PICKUP_WINDOW_INVALID`. The window must not overlap another `SCHEDULED` pickup of the same program, and it must also respect the network's route-spacing rule — the same program's next pickup may not begin less than 24 hours after this pickup's window ends, so a program cannot be scheduled for two back-to-back runs on the same day; both collisions are rejected with `ERR_PICKUP_WINDOW_OVERLAP`. Both tests are applied only against pickups that are still `SCHEDULED` — a completed or missed pickup no longer constrains a new window — and the spacing test is symmetric, holding in both directions however the two windows were ordered when they were scheduled. A successful schedule creates the pickup in `SCHEDULED` status with `collected_lbs` at zero. A program's pickups are readable through the reverse-reachability list, optionally filtered by `pickup_status`.

Completing a pickup records what was actually collected. The pickup must still be `SCHEDULED` — otherwise `ERR_PICKUP_NOT_SCHEDULED` — and the supplied `collected_lbs` must be zero or greater. Completion is only accepted while the current logical clock time is no more than 48 hours past the window's end — a test that also admits a pickup completed before its window opens, so the only way to be refused is to be more than 48 hours late — which gives a driver two days of slack after a late run but no ability to close out a pickup from last month; a refusal carries `ERR_PICKUP_WINDOW_INVALID` (HTTP 400). On completion, `collected_lbs` is stored and the pickup's `meal_equivalent` is computed as the collected pounds divided by the network standard factor of 1.2, floored to a whole number of meals — note that retail pickups use the fixed network factor rather than the donor agreement's own factor, because a store donation is not tied to an agreement. The pickup becomes `COMPLETED`.

A pickup that does not happen is marked missed, either by the member or by the program-suspension cascade. Marking a `SCHEDULED` pickup missed sets it to `MISSED` and then re-evaluates the program's reliability: the program's consecutive-missed count is recomputed over its pickups taken in `scheduled_date` ascending order, with `created_at` ascending breaking ties between pickups scheduled for the same date, counting the run of consecutive `MISSED` pickups that ends at the last `MISSED` pickup in that order — a pickup that is still `SCHEDULED` for a later date sits after that run and does not reset the count. If that run reaches three, the program's `program_status` becomes `SUSPENDED` and every one of the program's remaining `SCHEDULED` pickups is marked `MISSED` as well. A suspended program can only be revived when its owning member is reinstated to `CERTIFIED`, at which point the program returns to `ACTIVE`; a program suspended by this rule while its member is already `CERTIFIED` therefore has no route back, because reinstatement is open only to a member in `PROBATION` or `SUSPENDED`. A `MISSED` pickup is never reopened; the program recovers by scheduling a fresh pickup on a later date.
