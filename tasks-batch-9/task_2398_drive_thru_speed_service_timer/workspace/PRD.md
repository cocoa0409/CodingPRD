# Drive-Thru Speed-Of-Service API — Product Requirements Document

## 1. Introduction

A drive-thru lane is the highest-throughput piece of equipment a restaurant owns, and it is measured in seconds. Operators run a **timer program**: every car that breaks the lane sensor opens a timer loop that is segmented into a greet interval, an order interval, a pull-forward interval and a window interval, each of which is judged against a target that depends on the daypart and on how busy the lane actually is. When volume climbs, targets are deliberately relaxed and outside order-takers are pushed into the lane; when order accuracy degrades, the same volume signal has to be traded off against remakes. This API is the system of record for that program.

The product problem is that these signals interact. A car that departs raises the trailing car rate, which may lift the store into a higher volume tier, which raises the number of outside order-takers the staffing model demands, which may flip the store into a surge posture — all from one departure. A wrong order logged against a car that has already departed retroactively changes what a "final" throughput number looks like, and can strand a car that was already holding a post-merge lane position. Coaching a team member on a slow window interval is only defensible if the report it rests on is published and has not been superseded. The API therefore models each of these as an explicit, individually addressable resource with an explicit state machine, and it pins the evaluation order of every rollup so that two servers processing the same request sequence agree on every derived number.

This document specifies the complete contract: the response envelope and pagination mechanics, the five operating roles and how each one's identity is resolved, the store-level posture gate, the pinned rollup chain, the twelve calculations, the thirty-three ordered validations, the sixty-four endpoints and the fifty-seven error codes. Every resource in the API is mounted under the `/drive-thru` prefix.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contract: authentication, envelope shape, pagination, the logical clock, common resource properties, the store posture gate, the rollup chain, rounding discipline, concurrency control and the order in which any request is validated.

### 2.1. Operating Roles and Access Scoping

Every request — including every read — must carry two mandatory HTTP headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which they act. Exactly five roles exist, and their spelling is part of the contract: `ProgramAdmin`, `Operator`, `ShiftLeader`, `AccuracyAuditor` and `MarketCoach`. If either header is absent, or if `X-User-Role` is not one of those five strings, the request is rejected with `ERR_UNAUTHENTICATED` (401). If the headers are well formed but the acting role does not appear on the endpoint's authorized-role list in §4, the request is rejected with `ERR_UNAUTHORIZED` (403).

Two of the five roles are entity-backed, which means `X-User-ID` is a resource identifier and ownership is checked against it.

- When `X-User-Role` is `Operator`, `X-User-ID` is the `id` of the acting `Restaurant`; ownership checks on any resource that references a `Restaurant` compare the resource's `restaurant_id` (or, for store-scoped paths, the store identifier in the path) to `X-User-ID`. Any `Operator` mutation whose target store is not the store named by `X-User-ID` is rejected with `ERR_RESTAURANT_SCOPE_MISMATCH` (403). The target store is determined as the store in the path when the path names one, otherwise the `restaurant_id` in the request body, otherwise the `restaurant_id` of the path-addressed resource.
- When `X-User-Role` is `ShiftLeader`, `X-User-ID` is the `id` of the acting `StaffMember`; ownership checks on any resource that references a `StaffMember` compare the resource's staff foreign-key field to `X-User-ID`. For every `ShiftLeader` mutation, `X-User-ID` must be an existing `StaffMember` whose `restaurant_id` equals the target store; otherwise the request is rejected with `ERR_STAFF_SCOPE_MISMATCH` (403).

The remaining three roles are opaque. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque chain-level operator identifier not tied to any persisted entity; the server records it where a transition writes it (for example, as `approved_by_user_id` on `ForecastOverride`) but never compares it to any entity's `id`. When `X-User-Role` is `AccuracyAuditor`, `X-User-ID` is likewise an opaque market-auditor identifier that the server does not compare to any entity's `id`. When `X-User-Role` is `MarketCoach`, `X-User-ID` is an opaque coach identifier; the server records it as `issued_by_user_id` on `CoachingIntervention` so that the segregation-of-duties rule can later compare a closing coach's header value against it, but it is never resolved to an entity.

Responsibilities divide as follows. A `ProgramAdmin` owns the chain: registering stores, publishing the volume-tier band table, adjudicating forecast overrides and driving the logical clock. An `Operator` owns one store's configuration, roster, staffing and posture. A `ShiftLeader` runs the pad in real time: timer loops, the merge lane, pull-forwards and incident logging. An `AccuracyAuditor` settles remakes. A `MarketCoach` computes throughput reports and authors coaching. Every `GET` endpoint is readable by all five roles.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated with two query parameters. `limit` caps the number of items returned; it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. A `limit` outside the inclusive range 1 through 100 is a schema failure and is rejected with `ERR_INVALID_REQUEST` (400). `offset` is the number of items to skip and defaults to 0.

Unless a specific endpoint states otherwise, every list endpoint returns its rows sorted by `created_at` in ascending order.

List responses carry four pagination fields inside the envelope's `meta` object: `limit`, `offset`, `total_count` and `has_more`.

### 2.4. The Logical Clock

Nothing in this system reads wall-clock time. Every timestamp the server stamps — a car's arrival, a greet, an order completion, a merge, a window arrival, a departure, a deployment activation, a slot award, an incident, a pull-forward clear — is taken from a single server-held **logical clock**. That clock starts at the fixed instant `2026-08-01T00:00:00Z` and never falls back to wall-clock time under any circumstance.

A `ProgramAdmin` moves the clock forward through an administrative test-driving capability that accepts a single field, `to_iso8601`, carrying the instant to move to. The clock is only ever set to whole seconds, and it never moves backwards: if `to_iso8601` is earlier than the clock's current value the request is rejected with `ERR_CLOCK_REGRESSION` (422). Setting the clock to exactly its current value is permitted. The successful response reports the resulting clock as `current_utc`.

Advancing the clock is not inert. Because the trailing car-rate window is measured relative to "now", every store's rollup chain is re-run after the clock moves, which ages closed cars out of the trailing window and can therefore lower the car rate, drop the volume tier, lower the outside order-taker requirement and change the posture — for every registered store, without any client touching those stores.

All datetimes accepted in request bodies are ISO 8601 UTC with whole seconds; a malformed or sub-second timestamp is rejected with `ERR_INVALID_REQUEST` (400). All timestamp comparisons throughout this specification are exact comparisons on those stored whole-second values.

### 2.5. Common Resource Properties and Store Versioning

Every resource in this API — stores, volume-tier bands, daypart profiles, team members, deployments, timer loops, merge slots, pull-forward orders, accuracy incidents, throughput reports, coaching interventions and forecast overrides — carries the same four system-managed properties:

- `id` (string): a server-minted UUID. It carries no type prefix and is never supplied by the client.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the row was first created.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the resource.
- `version` (integer): a monotonically increasing integer that starts at 1 on creation and increments by exactly 1 on every mutation of that resource.

There are no exceptions to this rule in this domain: no entity omits `updated_at` or `version`.

`Restaurant.version` deserves special attention because it is the concurrency anchor for the whole store. Five operations increment it explicitly: adjusting the store's staffing basis or labor budget, freezing the store, unfreezing the store, proposing a forecast override and creating a throughput report. In addition, whenever a system-driven recompute lands the store on a different `service_posture`, that is itself a mutation of the store row: `updated_at` is refreshed and `version` increments by 1. Clients that intend to write against a store are therefore expected to re-read it immediately beforehand (see §2.10).

### 2.6. Service Posture: The Store-Level Master Gate

Each store exposes a computed `service_posture` with exactly four values — `OPEN`, `SURGE`, `ACCURACY_HOLD` and `FROZEN` — and that single field gates most of the child mutations in the API. A newly registered store starts at `OPEN`. `service_posture` is never written directly by a client; it is derived, and only ever by the pinned rollup chain described in §2.7, whose final step applies an absolute precedence: `FROZEN` outranks `ACCURACY_HOLD`, which outranks `SURGE`, which outranks `OPEN`.

`FROZEN` is the one posture an operator can command. It is backed by a separate stored flag, `posture_override`, whose two values are `NONE` (the default) and `FROZEN`. An `Operator` freezing their store must supply a `freeze_reason`, which is stored on the store; `posture_override` becomes `FROZEN`, and the store's `version` increments by 1. Freezing requires `posture_override` to currently be `NONE`, and is available from `OPEN`, `SURGE` and `ACCURACY_HOLD` alike. Unfreezing requires `posture_override` to currently be `FROZEN`; it sets `posture_override` back to `NONE`, sets `freeze_reason` back to null, increments `version` by 1, and then re-runs the rollup chain — so unfreezing does not necessarily land on `OPEN`. If the recompute finds two or more open remakes the store lands on `ACCURACY_HOLD`; if it finds fewer than two open remakes but more outside order-takers required than deployed, it lands on `SURGE`; otherwise it lands on `OPEN`.

While `service_posture` is `FROZEN`, every mutating operation is rejected with `ERR_POSTURE_FROZEN` (409) except these eight: `POST /drive-thru/restaurants`, `PATCH /drive-thru/restaurants/{restaurantId}`, `POST /drive-thru/restaurants/{restaurantId}/unfreeze`, `POST /drive-thru/volume-tier-policies`, `POST /drive-thru/forecast-overrides`, `POST /drive-thru/forecast-overrides/{overrideId}/approve`, `POST /drive-thru/forecast-overrides/{overrideId}/reject` and `POST /drive-thru/_clock/set_current_utc`. Everything else — including a second freeze attempt and including putting an approved override into force — is blocked.

`ACCURACY_HOLD` is narrower. It blocks exactly one operation, `POST /drive-thru/restaurants/{restaurantId}/merge-award`, with `ERR_POSTURE_ACCURACY_HOLD` (409), and it does so for as long as the store carries two or more open remakes. `SURGE` blocks nothing; it is a staffing signal that the store is short of outside order-takers.

The system may move a store between `OPEN`, `SURGE` and `ACCURACY_HOLD` without any client having requested a change on the store resource, because those three are pure functions of the store's children. Every such reconciliation is a mutation of the store row and independently refreshes `updated_at` and increments `version` by 1. There are exactly six such system-driven reconciliations, and all six require `posture_override` to be `NONE`: `OPEN → SURGE` and `SURGE → OPEN` when the outside order-taker requirement rises above or falls back to the deployed count while the open-remake count is below two; `OPEN → ACCURACY_HOLD` and `SURGE → ACCURACY_HOLD` when the open-remake count reaches two or more, from either of those postures; and `ACCURACY_HOLD → SURGE` or `ACCURACY_HOLD → OPEN` when the open-remake count falls back below two, choosing between the two according to whether the requirement still exceeds the deployed count.

### 2.7. The Store Rollup Recompute Chain

Twelve derived numbers hang off each store, and they are recomputed together by a single named routine whose **evaluation order is pinned**. Each step runs exactly once, in the order given, and each step may read the results of the steps above it. The routine runs after any of the following: a timer loop departs or is abandoned; a merge slot changes state; an accuracy incident is created, remade, closed or waived; a deployment is activated, released or aborted; a forecast override is put into force; the store's staffing basis or labor budget is adjusted; the store is frozen or unfrozen; the logical clock is advanced.

1. **Trailing closed cars.** `cars_closed_trailing` is the number of the store's own timer loops whose `timing_state` is `CLOSED` and whose `depart_at` is strictly later than the instant ten minutes (600 seconds) before the current clock reading and no later than the current clock reading. The window is therefore half-open on its older edge and closed on the "now" edge.
2. **Observed car rate.** `cars_per_hour_observed` is `cars_closed_trailing` multiplied by 3600 and divided by the 600-second trailing window length, rounded half up to one decimal place.
3. **Effective car rate.** `cars_per_hour_effective` equals `cars_per_hour_observed` when the store's `staffing_basis` is `OBSERVED`. When `staffing_basis` is `FORECAST_ADJUSTED` and a forecast override is in force at the current clock reading, it is instead `cars_per_hour_observed` multiplied by one plus that override's `projected_cars_delta_pct`, rounded half up to one decimal place. When `staffing_basis` is `FORECAST_ADJUSTED` but no override is in force, it again equals `cars_per_hour_observed`.
4. **Volume tier.** `volume_tier` is the `tier` of the volume-tier band whose `cars_per_hour_floor` is less than or equal to `cars_per_hour_effective` and whose `cars_per_hour_ceiling` is either null or strictly greater than `cars_per_hour_effective`. If no band matches, the entire request that triggered the recompute is aborted with `ERR_TIER_POLICY_INCOMPLETE` (422).
5. **Deployed outside order-takers.** `deployed_oot_count` is the number of the store's deployments whose `deployment_state` is `ACTIVE` and whose `position` is either `OOT_LANE_A` or `OOT_LANE_B`. Deployments at `EXPEDITER` or `RUNNER` do not count.
6. **Open remakes.** `open_remake_count` is the number of the store's accuracy incidents whose `incident_state` is either `LOGGED` or `REMADE`.
7. **Required outside order-takers.** `required_oot_count` is produced by the staffing model described in §3.2, using the tier selected in step 4 together with the store's `lane_config` and the open-remake count from step 6.
8. **Capacity and ledger figures.** `merge_slots_free` is `merge_slots_capacity` minus the number of the store's merge slots whose `slot_state` is either `RESERVED` or `COMMITTED`. `labor_minutes_committed` is the sum of `planned_minutes` over the store's deployments in `ACTIVE` plus the sum of `labor_minutes_charged` over the store's deployments in `RELEASED`. `labor_minutes_available` is `labor_minutes_budget` minus `labor_minutes_committed`. `remake_cost_accrued_cents` is the sum of `remake_cost_cents` over the store's accuracy incidents whose `settlement_state` is either `ACCRUED` or `CHARGED`.
9. **Posture.** `service_posture` becomes `FROZEN` if `posture_override` is `FROZEN`; otherwise `ACCURACY_HOLD` if `open_remake_count` is two or more; otherwise `SURGE` if `required_oot_count` is strictly greater than `deployed_oot_count`; otherwise `OPEN`.

All rows considered by the chain are those foreign-key-linked to the store in question, with the status filters spelled out per step above. Because the chain is ordered, a single departure can propagate five hops deep — from slot release, through the trailing car count, into the tier, into the outside order-taker requirement, into the posture — and the implementer must not short-circuit any hop.

### 2.8. Volume-Tier Bands and Target Relief

The chain-level **volume-tier band table** is the bridge between how busy a lane is and how the program treats it. It is a flat, chain-wide table (not per store) of at most four rows, one per `tier`, whose values are exactly `TIER_1`, `TIER_2`, `TIER_3` and `TIER_4`. Each band declares the car-rate interval it covers, how much target relief it grants, how many outside order-takers it demands and which ranking rule the merge selector should use at that volume.

Band lookup is used in three distinct places and always with the same interval semantics — the floor is inclusive, the ceiling is exclusive, and a null ceiling means unbounded above: when the rollup chain selects a store's `volume_tier` from `cars_per_hour_effective`; when a throughput report selects its own `window_tier` from that window's `cars_per_hour`; and when a newly registered store selects the band containing a car rate of 0.0. If the value in play falls in no band, the request needing the lookup fails with `ERR_TIER_POLICY_INCOMPLETE` (422). This applies to timer-loop creation, timer-loop departure, throughput-report creation and merge awards.

Bands are chain-configuration and are therefore declared and read but never mutated or deleted.

### 2.9. Numeric Precision and Rounding Discipline

Every rounding operation in this system is **round half up**, performed on decimal arithmetic — never on binary floating point. The precision differs by quantity and is part of the contract:

- Car-rate figures (`cars_per_hour_observed`, `cars_per_hour_effective` on a store, and `cars_per_hour` on a report) carry **one** decimal place.
- Average metric figures (`avg_metric_seconds`) carry **one** decimal place.
- Attainment percentages (`attainment_pct`) and coaching priority scores (`priority_score`) carry **two** decimal places.
- Pinned segment targets, `target_total_seconds_effective` and every measured segment duration are **whole seconds**.
- `mean_pinned_target_seconds` is held **exactly**, unrounded, as a decimal; it is an intermediate that feeds a later rounding step and must not be rounded itself.
- Counts, minute figures and cent figures are integers. Partial minutes in the labor ledger are rounded **up** to the next whole minute.
- Points figures (`coaching_pool_points`) are integers.

Where a chain of arithmetic is specified, the rounding points are exactly where this document places them and nowhere else. Rounding earlier or later than specified produces different stored values and is incorrect.

### 2.10. Reading the Store Before Writing: Version Preconditions

Two write operations require the client to prove it has read the store recently, using optimistic concurrency control anchored on `Restaurant.version`. Both take a non-optional body field named `expected_restaurant_version`, carrying the `version` the client last observed on the target store — the store read endpoint is the read-before-write channel that supplies it.

- `POST /drive-thru/forecast-overrides` must carry `expected_restaurant_version` matching the target store's current `version`. If the store's `version` has advanced since the client last read it, the proposal is rejected with `ERR_STALE_RESTAURANT_VERSION` (412). Several proposed overrides on overlapping windows are perfectly legitimate — the aggregate cap in §3.7 counts only overrides already in force — so nothing about the override itself precludes the write; the stale `expected_restaurant_version` is the only thing that identifies a writer whose view of `volume_tier`, `service_posture` and the in-force override set is out of date.
- `POST /drive-thru/throughput-reports` must likewise carry `expected_restaurant_version` matching the target store's current `version`, and a mismatch is rejected with `ERR_STALE_RESTAURANT_VERSION` (412). A second report over the same window is legitimate — it supersedes the earlier one — so the report's own state never blocks it; the stale version is what marks the writer as having computed its window from an out-of-date view of the store.

No other endpoint accepts a version field, and no other endpoint performs a version check. Both of these operations, on success, increment the store's `version` by 1.

### 2.11. The Order in Which a Request Is Checked

When a single request violates more than one rule, the response is determined by a **fixed priority ladder**, not by the order in which an implementation happens to evaluate its guards. The first violated rule in this list wins, and its error is the one returned. This ordering is observable and is part of the contract: a request that is both unauthorized and malformed returns the authorization error; a request that is both posture-blocked and in the wrong resource state returns the posture error; a request that would both exceed the labor budget and be in the wrong state returns the state error.

1. **Authentication** — both headers present and `X-User-Role` among the five declared roles. Applies to every endpoint. Rejection: `ERR_UNAUTHENTICATED` (401).
2. **Endpoint authorization** — the acting role appears on the endpoint's role list. Applies to every endpoint. Rejection: `ERR_UNAUTHORIZED` (403).
3. **Path-resource existence** — every path-templated resource exists, validated strictly left to right. Applies to every endpoint with a path parameter. Rejection is the 404 code matching the first path segment that fails to resolve: `ERR_RESTAURANT_NOT_FOUND`, `ERR_PROFILE_NOT_FOUND`, `ERR_STAFF_NOT_FOUND`, `ERR_DEPLOYMENT_NOT_FOUND`, `ERR_LOOP_NOT_FOUND`, `ERR_SLOT_NOT_FOUND`, `ERR_PULL_FORWARD_NOT_FOUND`, `ERR_INCIDENT_NOT_FOUND`, `ERR_REPORT_NOT_FOUND`, `ERR_COACHING_NOT_FOUND` or `ERR_OVERRIDE_NOT_FOUND` (all 404).
4. **Operator store scope** — as described in §2.1. Applies to every `Operator` mutation. Rejection: `ERR_RESTAURANT_SCOPE_MISMATCH` (403).
5. **ShiftLeader staff scope** — as described in §2.1. Applies to every `ShiftLeader` mutation. Rejection: `ERR_STAFF_SCOPE_MISMATCH` (403).
6. **Request schema** — required fields present, enum members recognized, numbers inside their declared ranges, datetimes ISO 8601 UTC with whole seconds, and `limit` inside 1 through 100. Applies to every endpoint with a body or query parameters. Rejection: `ERR_INVALID_REQUEST` (400).
7. **Body foreign-key existence** — every foreign key named in the body resolves to a row. Applies to `POST /drive-thru/daypart-profiles`, `POST /drive-thru/staff-members`, `POST /drive-thru/order-taker-deployments`, `POST /drive-thru/timer-loops`, `POST /drive-thru/pull-forward-orders`, `POST /drive-thru/accuracy-incidents`, `POST /drive-thru/accuracy-incidents/{incidentId}/deliver-remake`, `POST /drive-thru/throughput-reports`, `POST /drive-thru/coaching-interventions` and `POST /drive-thru/forecast-overrides`. Rejection: `ERR_RESTAURANT_NOT_FOUND`, `ERR_PROFILE_NOT_FOUND`, `ERR_STAFF_NOT_FOUND`, `ERR_LOOP_NOT_FOUND` or `ERR_REPORT_NOT_FOUND` (all 404).
8. **Same-store referential integrity** — every body foreign key belongs to the same store as the operation's target. Concretely: a daypart profile's `restaurant_id` must equal the body's `restaurant_id`; a team member's `restaurant_id` must equal the loop's `restaurant_id`; a report's `restaurant_id` must equal the coachee's `restaurant_id`; and the store of the report named in `supersedes_report_id` must equal the body's `restaurant_id`. Applies to `POST /drive-thru/order-taker-deployments`, `POST /drive-thru/timer-loops`, `POST /drive-thru/accuracy-incidents`, `POST /drive-thru/accuracy-incidents/{incidentId}/deliver-remake`, `POST /drive-thru/throughput-reports` and `POST /drive-thru/coaching-interventions`. Rejection: `ERR_RESTAURANT_MISMATCH` (409).
9. **Store version precondition** — `expected_restaurant_version` equals the store's current `version`. Applies to `POST /drive-thru/forecast-overrides` and `POST /drive-thru/throughput-reports`. Rejection: `ERR_STALE_RESTAURANT_VERSION` (412).
10. **Frozen posture gate** — as enumerated in §2.6. Rejection: `ERR_POSTURE_FROZEN` (409).
11. **Accuracy-hold gate** — the store is not in `ACCURACY_HOLD`. Applies to `POST /drive-thru/restaurants/{restaurantId}/merge-award` only. Rejection: `ERR_POSTURE_ACCURACY_HOLD` (409).
12. **Declared transition** — the target resource is in a state from which the requested transition is declared. Applies to every action endpoint. Rejection is the code matching the resource: `ERR_INVALID_PROFILE_STATE`, `ERR_INVALID_DEPLOYMENT_STATE`, `ERR_INVALID_TIMER_STATE`, `ERR_INVALID_SLOT_STATE`, `ERR_INVALID_PULL_FORWARD_STATE`, `ERR_INVALID_INCIDENT_STATE`, `ERR_INVALID_REPORT_STATE`, `ERR_INVALID_COACHING_STATE` or `ERR_INVALID_OVERRIDE_STATE` (all 409).
13. **Cross-entity state gates** — timer-loop creation needs the referenced profile in `ACTIVE` (`ERR_PROFILE_NOT_ACTIVE`); coaching creation needs the referenced report in `PUBLISHED` (`ERR_REPORT_NOT_PUBLISHED`); deployment activation needs the team member in `AVAILABLE` (`ERR_STAFF_NOT_AVAILABLE`); a merge commit needs the awarded loop in `ORDERED` (`ERR_LOOP_NOT_MERGEABLE`); logging an accuracy incident needs the loop's `timing_state` to be one of `ORDERED`, `MERGED`, `AT_WINDOW` or `CLOSED` (`ERR_LOOP_HAS_NO_ORDER`); and a loop may carry only one non-terminal remake (`ERR_REMAKE_ALREADY_OPEN`). Applies to `POST /drive-thru/timer-loops`, `POST /drive-thru/coaching-interventions`, `POST /drive-thru/order-taker-deployments/{deploymentId}/activate`, `POST /drive-thru/merge-slots/{slotId}/commit` and `POST /drive-thru/accuracy-incidents`. All six codes are 409.
14. **Outside-order-taker certification** — a deployment at `OOT_LANE_A` or `OOT_LANE_B` requires the team member's `oot_certified` to be true. Applies to `POST /drive-thru/order-taker-deployments`. Rejection: `ERR_STAFF_NOT_OOT_CERTIFIED` (422).
15. **Allergen waiver ban** — an incident whose `severity` is `CRITICAL` can never be waived. Applies to `POST /drive-thru/accuracy-incidents/{incidentId}/waive`. Rejection: `ERR_ALLERGEN_WAIVER_FORBIDDEN` (422).
16. **Segregation of duties** — `remade_by_staff_id` must differ from the incident's `logged_by_staff_id`, and a closing coach's `X-User-ID` must differ from the intervention's `issued_by_user_id`. Applies to `POST /drive-thru/accuracy-incidents/{incidentId}/deliver-remake` and `POST /drive-thru/coaching-interventions/{coachingId}/close`. Rejection: `ERR_SEGREGATION_OF_DUTIES` (409).
17. **Clock monotonicity** — `to_iso8601` is at or after the current logical clock. Applies to `POST /drive-thru/_clock/set_current_utc`. Rejection: `ERR_CLOCK_REGRESSION` (422).
18. **Interval bound ordering** — `end_minute` strictly greater than `start_minute`; `planned_end_at` strictly after `planned_start_at`; `window_end_at` strictly after `window_start_at`; `effective_end_at` strictly after `effective_start_at`. Applies to `POST /drive-thru/daypart-profiles`, `POST /drive-thru/order-taker-deployments`, `POST /drive-thru/throughput-reports` and `POST /drive-thru/forecast-overrides`. Rejection: `ERR_WINDOW_BOUNDS_INVALID` (422).
19. **Daypart containment** — the logical clock's minute-of-day at loop creation is at or after the profile's `start_minute` and strictly before its `end_minute`. Applies to `POST /drive-thru/timer-loops`. Rejection: `ERR_DAYPART_WINDOW_MISMATCH` (422).
20. **No future reporting** — `window_end_at` is at or before the logical clock. Applies to `POST /drive-thru/throughput-reports`. Rejection: `ERR_REPORT_WINDOW_FUTURE` (422).
21. **Daypart overlap** — see §3.1. Applies to `POST /drive-thru/daypart-profiles/{profileId}/activate`. Rejection: `ERR_DAYPART_WINDOW_OVERLAP` (409).
22. **Deployment changeover buffer** — see §3.2. Applies to `POST /drive-thru/order-taker-deployments`. Rejection: `ERR_DEPLOYMENT_BUFFER_VIOLATION` (409).
23. **Override aggregate cap** — see §3.7. Applies to `POST /drive-thru/forecast-overrides/{overrideId}/apply`. Rejection: `ERR_OVERRIDE_AGGREGATE_CAP` (422).
24. **Uniqueness** — the pair of store and `daypart` is unique among profiles whose `profile_state` is `DRAFT` or `ACTIVE` (`ERR_DUPLICATE_DAYPART`); `tier` is globally unique across volume-tier bands (`ERR_DUPLICATE_TIER_POLICY`); `store_number` is globally unique across stores (`ERR_DUPLICATE_STORE_NUMBER`). Applies to `POST /drive-thru/daypart-profiles`, `POST /drive-thru/volume-tier-policies` and `POST /drive-thru/restaurants`. All three codes are 409.
25. **Tier band coverage** — a band must contain the car-rate figure the request needs. Applies to `POST /drive-thru/timer-loops`, `POST /drive-thru/timer-loops/{loopId}/depart`, `POST /drive-thru/throughput-reports` and `POST /drive-thru/restaurants/{restaurantId}/merge-award`. Rejection: `ERR_TIER_POLICY_INCOMPLETE` (422).
26. **One live pull-forward per loop** — no pull-forward order for this loop is in `ISSUED` or `PARKED`. Applies to `POST /drive-thru/pull-forward-orders`. Rejection: `ERR_PULL_FORWARD_ALREADY_OPEN` (409).
27. **Escalation limit** — `escalation_count` is at most 1 before a reissue, so a pull-forward can be reissued at most twice. Applies to `POST /drive-thru/pull-forward-orders/{pullForwardId}/reissue`. Rejection: `ERR_PULL_FORWARD_ESCALATION_LIMIT` (422).
28. **Revision limit** — `revision_count` is at most 1 before a contest, so an intervention can go round the revision loop at most twice. Applies to `POST /drive-thru/coaching-interventions/{coachingId}/contest`. Rejection: `ERR_COACHING_REVISION_LIMIT` (422).
29. **Consecutive-minutes cap** — `planned_minutes` is at most the team member's `max_consecutive_deployment_minutes`. Applies to `POST /drive-thru/order-taker-deployments`. Rejection: `ERR_STAFF_CONSECUTIVE_LIMIT` (422).
30. **Merge candidate availability** — the merge selector's eligible candidate set is non-empty. Applies to `POST /drive-thru/restaurants/{restaurantId}/merge-award`. Rejection: `ERR_NO_MERGE_CANDIDATE` (409).
31. **Non-empty report** — the report being published has a `cars_served` of at least 1. Applies to `POST /drive-thru/throughput-reports/{reportId}/publish`. Rejection: `ERR_REPORT_WINDOW_EMPTY` (422).
32. **Merge capacity** — `merge_slots_free` is at least 1. Applies to `POST /drive-thru/restaurants/{restaurantId}/merge-award`. Rejection: `ERR_MERGE_CAPACITY_EXHAUSTED` (409).
33. **Labor budget** — `labor_minutes_available` is at least the deployment's `planned_minutes`. Applies to `POST /drive-thru/order-taker-deployments/{deploymentId}/activate`. Rejection: `ERR_LABOR_BUDGET_EXCEEDED` (402).

Note the consequences of the ladder's shape for the merge award, which is guarded four times: the accuracy-hold posture (11) outranks tier coverage (25), which outranks candidate availability (30), which outranks free capacity (32). A store in `ACCURACY_HOLD` with an exhausted merge lane reports the posture error, not the capacity error.

### 2.12. Path Resolution and Cross-Store Referential Integrity

Resource collections in this API are flat. Every collection lives directly at `/drive-thru/<collection>` and every instance at `/drive-thru/<collection>/{id}`; where a path continues past the instance identifier, the continuation is always an action verb such as `/depart` or `/merge-award`, never a child collection. Relationships between resources are expressed by explicit identifier fields in request bodies, not by nesting.

Path identifiers are nevertheless resolved strictly left to right, and the first identifier that fails to resolve determines the 404 that comes back — the server does not attempt to locate anything further right in the path. Body-level identifiers are resolved after the whole path resolves, and a body identifier that resolves to a row belonging to a *different* store than the operation's target is a conflict rather than a not-found: it is rejected with `ERR_RESTAURANT_MISMATCH` (409). Existence therefore always precedes ownership, and ownership always precedes business rules.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Store: Registration, Bands and Dayparts

A `ProgramAdmin` registers a store by supplying its `name` (the display name shown to operators), its `store_number` (the operator-facing identifier, which must not collide with any store already registered), its `lane_config`, its `merge_slots_capacity` and its `labor_minutes_budget`. `staffing_basis` is optional at registration and defaults to `OBSERVED`. `lane_config` is one of `SINGLE`, `DUAL_TANDEM` or `DUAL_PARALLEL`; a `SINGLE` store has no second lane and therefore skips the merge step entirely, which changes the shape of its timer loop as described in §3.3. `merge_slots_capacity` is the number of post-merge lane positions that may be held at one time and must be between 1 and 12 inclusive. `labor_minutes_budget` is the deployment labor available for the operating day, between 0 and 5000 inclusive.

Registration initialises the store's derived state without running the full recompute chain: `merge_slots_free` is set equal to `merge_slots_capacity`, `labor_minutes_available` is set equal to `labor_minutes_budget` with `labor_minutes_committed` at 0, `cars_per_hour_observed` and `cars_per_hour_effective` are both 0.0, `volume_tier` is read off the band containing a car rate of 0.0, `posture_override` is `NONE`, and `service_posture` is `OPEN`. `cars_closed_trailing`, `required_oot_count`, `deployed_oot_count`, `open_remake_count` and `remake_cost_accrued_cents` all start at 0, and `freeze_reason` starts null.

Later, an `Operator` may adjust two store settings: `staffing_basis` (switching between `OBSERVED` and `FORECAST_ADJUSTED`) and `labor_minutes_budget`. Both fields are optional on that adjustment, and it re-runs the rollup chain end to end — the effective car rate, the volume tier, the outside order-taker requirement and the posture — and increments the store's `version` by 1. Switching the basis is the single most consequential store-level setting in the program, because it changes which car rate the staffing model reads.

Before any car can be timed, the chain-level band table must exist. A `ProgramAdmin` declares each band with its `tier`, its `cars_per_hour_floor` (which must be at least 0), an optional `cars_per_hour_ceiling` (omitted or null for the topmost band; otherwise strictly greater than the floor), its `target_relief_pct` (between 0.00 and 0.25 inclusive — the fraction by which daypart segment targets are relaxed at this volume), its `min_oot_count` (between 0 and 4 inclusive — the outside order-takers the staffing model requires at this tier) and its `merge_award_bias`, which selects the ranking mode the merge selector uses at this volume from `ALTERNATE`, `LONGEST_WAIT` and `ACCURACY_FIRST`. Bands can be listed and may be filtered by `tier`.

Each store then declares its dayparts. An `Operator` drafts a daypart profile against a `restaurant_id`, naming the `daypart` — one of `BREAKFAST`, `LUNCH`, `AFTERNOON`, `DINNER` or `LATE` — together with a minute-of-day window and the four segment targets that define what "on time" means during that period. `start_minute` is the inclusive start, expressed in minutes since UTC midnight, between 0 and 1439 inclusive. `end_minute` is the exclusive end, between 1 and 1440 inclusive, and must be strictly greater than `start_minute`. The four targets are `greet_target_seconds` (arrival to greet), `order_target_seconds` (greet to order completion), `pull_forward_target_seconds` (order completion to window arrival) and `window_target_seconds` (window arrival to departure); each must be between 1 and 600 seconds inclusive. The server derives `total_target_seconds` as the plain, unrelieved sum of those four values. A newly drafted profile has `profile_state` of `DRAFT`, and a store may hold only one profile per `daypart` whose `profile_state` is `DRAFT` or `ACTIVE`.

Activation moves a profile `DRAFT → ACTIVE` and is the point at which minute-of-day geometry is enforced. Activation requires the profile to be in `DRAFT` and the store not to be frozen, and it requires that the profile's half-open minute window from `start_minute` up to but excluding `end_minute` does not overlap the window of any other profile of the same store whose `profile_state` is `ACTIVE`. The geometry is genuinely half-open: two dayparts that merely touch — where the earlier profile's `end_minute` equals this profile's `start_minute` — do not overlap and both may be active. Activation recomputes `total_target_seconds` and makes the profile usable for timer-loop creation.

Retirement moves a profile to `RETIRED`, which is terminal, and is reachable from both `ACTIVE` and `DRAFT`. Either way it requires the store not to be frozen, and either way it frees the store-and-daypart uniqueness slot so a replacement profile can be drafted. Retiring an `ACTIVE` profile additionally means that timer-loop creation naming that profile now fails with `ERR_PROFILE_NOT_ACTIVE`. Profiles may be listed with filters on `restaurant_id`, `daypart` and `profile_state`, and read individually.

### 3.2. The Roster and the Outside Order-Taker Staffing Model

An `Operator` adds each team member to the roster with a `restaurant_id` (their home store) and a `full_name`. Three optional attributes shape what they may be asked to do: `oot_certified`, which defaults to false and marks them cleared to take orders outside the building; `window_certified`, which also defaults to false and marks them cleared to hand off at the window; and `max_consecutive_deployment_minutes`, which defaults to 90 and must be between 15 and 240 inclusive — the longest single stretch this member may be planned for. A new member's `staff_state` is `AVAILABLE`; the other two values are `DEPLOYED` and `INACTIVE`. The server also tracks `deployed_minutes_today`, which starts at 0 and accumulates the labor actually charged across the member's released deployments. Team members can be listed with filters on `restaurant_id` and `staff_state`, and read individually.

Planning a deployment names the `restaurant_id`, the `staff_member_id` being deployed, the `daypart_profile_id` the deployment serves, the `position` and the interval. `position` is one of `OOT_LANE_A`, `OOT_LANE_B`, `EXPEDITER` or `RUNNER`; only the first two count as outside order-takers for staffing purposes. `planned_start_at` and `planned_end_at` describe a **closed** interval, inclusive at both ends, with the end strictly after the start. From those the server derives `planned_minutes` as the interval's length in seconds divided by 60 and rounded **up** to the next whole minute — a 61-second plan therefore costs two minutes, not one. A freshly planned deployment has `deployment_state` of `PLANNED`, its `activated_at` and `released_at` are null, its `labor_minutes_charged` is 0, and — importantly — no labor has been committed against the store yet.

Two safety rules bite at planning time. First, a deployment at `OOT_LANE_A` or `OOT_LANE_B` requires the named member's `oot_certified` to be true; otherwise the plan is rejected with `ERR_STAFF_NOT_OOT_CERTIFIED`. Second, `planned_minutes` may not exceed the member's `max_consecutive_deployment_minutes`, or the plan is rejected with `ERR_STAFF_CONSECUTIVE_LIMIT`. A third rule is geometric: one team member's deployments must be separated by a ten-minute changeover buffer. For every *other* deployment of the same member whose `deployment_state` is `PLANNED` or `ACTIVE`, the new deployment must satisfy one of two conditions — either its `planned_start_at` is at or after that other deployment's `planned_end_at` plus 600 seconds, or its `planned_end_at` plus 600 seconds is at or before that other deployment's `planned_start_at`. Because these intervals are closed and the buffer is additive, back-to-back deployments that merely touch are rejected, with `ERR_DEPLOYMENT_BUFFER_VIOLATION`. Deployments already in `RELEASED` or `ABORTED` are invisible to this check.

The labor ledger is a four-state accounting story, and each state moves money differently. Planning commits nothing. Activation — moving `PLANNED → ACTIVE`, available to both an `Operator` and a `ShiftLeader` — requires the deployment to be in `PLANNED`, the store not to be frozen, the member's `staff_state` to be `AVAILABLE`, and the store's `labor_minutes_available` to be at least this deployment's `planned_minutes`; a shortfall is `ERR_LABOR_BUDGET_EXCEEDED` (402). On success `activated_at` is stamped from the logical clock, the member moves to `DEPLOYED`, the deployment's full `planned_minutes` join `labor_minutes_committed`, `labor_minutes_available` is re-derived, and the rollup chain runs — recomputing `deployed_oot_count` and then `service_posture`, which is how putting an outside order-taker on position can clear a `SURGE`.

Release — `ACTIVE → RELEASED`, again available to an `Operator` or a `ShiftLeader` — requires the deployment to be `ACTIVE` and the store not to be frozen. It stamps `released_at` from the logical clock and sets `labor_minutes_charged` to the lesser of `planned_minutes` and the elapsed activation time in seconds divided by 60 rounded up to the next whole minute. A member released early is therefore charged less than planned, and a member released late is never charged more than planned. The member returns to `AVAILABLE`, `labor_minutes_charged` is added to their `deployed_minutes_today`, and because the deployment has left `ACTIVE` it stops contributing `planned_minutes` to the store ledger and starts contributing `labor_minutes_charged` instead. The rollup chain then runs.

Abort is the compensating action, and it is reachable from two states. From `ACTIVE`, an `Operator` abort — requiring the store not to be frozen — stores the supplied `abort_reason`, leaves `labor_minutes_charged` at 0, returns the member to `AVAILABLE` with `deployed_minutes_today` untouched, and drops the full `planned_minutes` back out of `labor_minutes_committed`, restoring `labor_minutes_available` to exactly the value it had before activation. From `PLANNED`, an `Operator` abort — likewise requiring an unfrozen store — stores the `abort_reason` and moves nothing in the ledger, because nothing had been committed. Both `RELEASED` and `ABORTED` are terminal. Across all four states the invariant that must hold after every request is that `labor_minutes_budget` equals `labor_minutes_committed` plus `labor_minutes_available`; deployments in `PLANNED` and `ABORTED` contribute zero to the committed side. Deployments may be listed with filters on `restaurant_id`, `staff_member_id`, `daypart_profile_id`, `position` and `deployment_state`, and read individually.

How many outside order-takers the store *should* have is the staffing model, and it is recomputed as step 7 of the rollup chain. It starts from `min_oot_count` on the band matching the store's freshly selected `volume_tier`, then adds two conditional bumps. A **lane bump** of 1 applies when the store's `lane_config` is `DUAL_PARALLEL` *and* `cars_per_hour_effective` is at least 12 cars per hour; otherwise the lane bump is 0. An **accuracy bump** of 1 applies when `open_remake_count` is at least 1; otherwise it is 0. `required_oot_count` is the sum of the band's minimum and the two bumps, capped at 4 — no store ever demands a fifth outside order-taker. Whenever `required_oot_count` exceeds `deployed_oot_count`, and no higher-precedence posture applies, the store reads `SURGE`.

The model has two variants, selected by the store's `staffing_basis`, and they can disagree on identical timer-loop data. Under `OBSERVED`, `cars_per_hour_effective` equals `cars_per_hour_observed`, so the tier, the lane bump and therefore `required_oot_count` are read off the trailing ten-minute closed-car count alone and forecast overrides in force are ignored entirely. Under `FORECAST_ADJUSTED`, `cars_per_hour_effective` is first scaled by one plus the in-force override's `projected_cars_delta_pct` and re-rounded to one decimal place before tier selection, so the very same trailing car count can select a lower or higher band, can flip the lane bump across the 12-cars-per-hour boundary, and can therefore yield a different `required_oot_count` — and a different `service_posture` — from the observed variant.

### 3.3. The Timer Loop from Arrival to Departure

Each car gets a **timer loop**, and a loop carries two state dimensions that evolve independently. `timing_state` tracks where the car physically is: `OPEN`, `GREETED`, `ORDERED`, `MERGED`, `AT_WINDOW`, `CLOSED` or `ABANDONED`, with `CLOSED` and `ABANDONED` terminal. `accuracy_state` tracks whether the order was right: `PENDING`, `VERIFIED`, `REMAKE_OPEN`, `REMADE` or `WAIVED`, none of which is terminal. The independence is deliberate and load-bearing: an incident can move `accuracy_state` while `timing_state` stays `CLOSED`, and a departure can move `timing_state` while `accuracy_state` stays `REMAKE_OPEN`.

A `ShiftLeader` opens a loop when a car breaks the lane sensor, supplying the `restaurant_id`, the `daypart_profile_id` whose targets should govern this car, and the `lane`. `lane` is `SINGLE` only at a store whose `lane_config` is `SINGLE`, and is `LANE_A` or `LANE_B` only at a store whose `lane_config` is `DUAL_TANDEM` or `DUAL_PARALLEL`. Creation requires the named profile to be in `ACTIVE`, and it requires the logical clock's minute-of-day to fall inside that profile's half-open window — at or after `start_minute` and strictly before `end_minute` — or the request fails with `ERR_DAYPART_WINDOW_MISMATCH`. The server stamps `arrive_at` from the logical clock and assigns `car_sequence`, a per-store monotone integer starting at 1 that becomes the pinned tie-break for every order-sensitive rule downstream. A new loop begins at `timing_state` `OPEN` and `accuracy_state` `PENDING`, with `served_after_loop_id` null.

Creation is also when the loop's targets are **pinned**, once and for ever. Two reliefs combine. The **tier relief** is `target_relief_pct` on the band matching the store's current `volume_tier`. The **override relief** is 0.00 when no forecast override is in force at the current clock reading; otherwise, when the in-force override supplies an explicit `target_relief_pct_override`, that value is used verbatim; otherwise it is that override's `projected_cars_delta_pct` multiplied by one half, floored at 0.00 and then capped at 0.20 — so a negative forecast delta contributes no relief and a very large positive one contributes at most a fifth. The combined relief is the sum of tier relief and override relief, capped at 0.30.

The **rounding order here is pinned and matters**. Each of the four profile targets is multiplied by one plus the combined relief and rounded half up to a whole second *individually*, producing `greet_target_pinned`, `order_target_pinned`, `pull_forward_target_pinned` and `window_target_pinned`. Only then are those four already-rounded whole-second values summed to give `target_total_seconds_pinned`. Summing the relieved targets first and rounding once at the end yields a different number and is wrong. Once pinned, these five values never change: a later tier shift, a later override coming into force, or a later profile edit leaves already-created loops exactly as they were.

The timing dimension then advances one stamp at a time, and every one of these transitions requires the store not to be frozen. Greeting a car moves it `OPEN → GREETED`, stamping `greet_at` and computing `greet_seconds` as `greet_at` minus `arrive_at` in whole seconds. Completing the order moves it `GREETED → ORDERED`, stamping `order_complete_at`, storing the `order_items_count` captured at the counter (between 1 and 40 inclusive), computing `order_seconds` as `order_complete_at` minus `greet_at`, and — critically — making the loop eligible for the merge selector.

From `ORDERED` the path forks on lane configuration. At a store whose `lane_config` is `DUAL_TANDEM` or `DUAL_PARALLEL`, the car must first be awarded and committed into a post-merge position, taking it `ORDERED → MERGED` (see §3.4) and stamping `merge_at` and `merge_wait_seconds`, which is `merge_at` minus `order_complete_at`. Window arrival then moves it `MERGED → AT_WINDOW`. At a store whose `lane_config` is `SINGLE` there is no merge step at all, and window arrival moves the car directly `ORDERED → AT_WINDOW` with `merge_wait_seconds` left null. Either way, window arrival stamps `window_arrive_at` and computes `pull_forward_seconds` as `window_arrive_at` minus `order_complete_at` — note that this segment deliberately *includes* any merge wait, so `merge_wait_seconds` is a component of `pull_forward_seconds` rather than a separate charge.

Departure moves the car `AT_WINDOW → CLOSED` and is the busiest single operation in the API. It stamps `depart_at`, computes `window_seconds` as `depart_at` minus `window_arrive_at`, computes `total_seconds` as `depart_at` minus `arrive_at`, and computes `adjusted_total_seconds`. It then runs a five-hop cascade. **Hop one:** because the loop reached `CLOSED`, its merge slot in `COMMITTED` becomes `RELEASED`. **Hop two:** because that slot has left the occupied set, the store's `merge_slots_free` is recomputed, rising by one. **Hop three:** because a car closed, the rollup chain raises `cars_closed_trailing`, then `cars_per_hour_observed` and `cars_per_hour_effective`, then `volume_tier`. **Hop four:** because the tier may have changed, `required_oot_count` is recomputed from the new band's `min_oot_count`. **Hop five:** because the requirement may have changed, `service_posture` is recomputed, which is how a single departure flips a store from `OPEN` to `SURGE`. Departure also auto-advances the accuracy dimension: if `accuracy_state` is `PENDING` at that moment it becomes `VERIFIED`, and if any pull-forward order of this loop is in `ISSUED` or `PARKED` it becomes `CLEARED` with `cleared_at` stamped.

Breach detection is a **strict** comparison, and it is evaluated as each stamp lands. `breach_flags` is the subset of `[GREET, ORDER, PULL_FORWARD, WINDOW]` — always reported in exactly that order — whose measured seconds are *strictly greater* than the corresponding pinned target: `GREET` when `greet_seconds` exceeds `greet_target_pinned`, `ORDER` when `order_seconds` exceeds `order_target_pinned`, `PULL_FORWARD` when `pull_forward_seconds` exceeds `pull_forward_target_pinned`, `WINDOW` when `window_seconds` exceeds `window_target_pinned`. Measuring exactly the target is *not* a breach. A segment whose endpoint has not been stamped yet contributes neither a duration nor a flag, so flags accumulate as the loop progresses: `GREET` at greet, `ORDER` at order completion, `PULL_FORWARD` at window arrival and `WINDOW` at departure.

`adjusted_total_seconds` is the number the program actually coaches against, and it is `total_seconds` plus two penalties. The **accuracy penalty** is the sum of `penalty_seconds` over this loop's accuracy incidents whose `incident_state` is `LOGGED`, `REMADE` or `CLOSED` — incidents in `WAIVED` are excluded, which is precisely why waiving is a genuine reversal. The **escalation penalty** is 15 seconds multiplied by the sum of `escalation_count` over this loop's pull-forward orders whose `pf_state` is anything other than `CANCELLED`. While `total_seconds` is null, `adjusted_total_seconds` is null too. It is recomputed on departure, on incident creation, closure and waiver, and on pull-forward reissue and cancellation.

A drive-off is recorded by abandoning the loop, which supplies an `abandon_reason` and is reachable from `OPEN`, `GREETED`, `ORDERED`, `MERGED` and `AT_WINDOW`, always requiring an unfrozen store. `ABANDONED` is terminal, `total_seconds` stays null, and an abandoned car is emphatically **not** a served car — the rollup chain's trailing count does not move, so abandoning changes no tier and no posture. The cleanup differs by the state abandoned from. From `OPEN` or `GREETED` there is nothing to clean up. From `ORDERED`, any merge slot of this loop in `RESERVED` becomes `FORFEITED` and `merge_slots_free` is then recomputed upward by one, and any pull-forward order of this loop in `ISSUED` or `PARKED` becomes `CANCELLED`. From `MERGED`, the loop's slot in `COMMITTED` becomes `FORFEITED` with the same capacity recompute, and live pull-forward orders likewise become `CANCELLED`. From `AT_WINDOW`, the `COMMITTED` slot becomes `FORFEITED` and capacity is recomputed. Cancelling a pull-forward removes its escalation penalty from the loop's `adjusted_total_seconds`.

Loops can be listed with filters on `restaurant_id`, `daypart_profile_id`, `served_after_loop_id`, `lane`, `timing_state` and `accuracy_state`, and read individually with all their durations, pinned targets and flags.

### 3.4. Merge Sequencing on Double-Lane Pads

At a double-lane store two order points feed one window, and the order in which cars are merged into the single post-merge lane is the operator's main throughput lever. The API models each post-merge position as a **merge slot** whose `slot_state` is `RESERVED`, `COMMITTED`, `RELEASED` or `FORFEITED`, the last two terminal. A store may hold `merge_slots_capacity` positions at once; both `RESERVED` and `COMMITTED` slots occupy capacity, so `merge_slots_free` counts the capacity not currently held in either of those two states.

A `ShiftLeader` does not choose which car merges next. Instead they ask the store for the next award, and the **server** selects a winner. Eligibility comes first: a candidate is a loop of this store whose `timing_state` is `ORDERED`, whose `accuracy_state` is either `PENDING` or `VERIFIED`, for which no merge slot is currently in `RESERVED` or `COMMITTED`, and for which no pull-forward order is currently in `ISSUED` or `PARKED`. If that candidate set is empty the award fails with `ERR_NO_MERGE_CANDIDATE` (409); if `merge_slots_free` is below 1 it fails with `ERR_MERGE_CAPACITY_EXHAUSTED` (409).

The ranking rule is not fixed — it is the `merge_award_bias` on the band matching the store's current `volume_tier`, so the same lane behaves differently at different volumes. Under `ALTERNATE`, the selector honours lane fairness: it looks up the store's merge slot with the greatest `sequence_index` regardless of that slot's `slot_state` (null if the store has none yet), and derives a preferred lane from it — `LANE_B` if that last slot's `source_lane` was `LANE_A`, `LANE_A` if it was `LANE_B`, and no preference at all if there is no last slot or its `source_lane` was `SINGLE`. Candidates in the preferred lane rank ahead of candidates that are not, and within each of those two groups the earliest `order_complete_at` ranks first; when there is no preferred lane, all candidates rank purely by earliest `order_complete_at`. The resulting `award_reason` is `ALTERNATE`. Under `LONGEST_WAIT`, the selector simply takes the earliest `order_complete_at`, since the longest wait since ordering is the earliest completion, and `award_reason` is `LONGEST_WAIT`. Under `ACCURACY_FIRST`, candidates whose `accuracy_state` is `VERIFIED` rank ahead of all others, and within each group the earliest `order_complete_at` ranks first; `award_reason` is `ACCURACY_FIRST`.

When the entire ranking key ties, the winner is the candidate with the lowest `car_sequence` — never the lowest `id`. If it was that tie-break rather than the ranking rule that decided the winner, `award_reason` is recorded as `CAR_SEQUENCE_TIE_BREAK` instead of the bias name, which makes the audit trail honest about why a car went next.

The award creates a merge slot in `RESERVED` against the winning loop's `timer_loop_id`, copies the winner's `lane` into `source_lane`, stamps `awarded_at` from the logical clock, records `award_reason`, and assigns `sequence_index` as one more than the greatest `sequence_index` among the store's existing slots (or 1 when the store has no slots yet). The store's `restaurant_id` is copied onto the slot by the server rather than supplied. At the same moment the winning loop's `served_after_loop_id` is set to the `timer_loop_id` of whichever slot held the greatest `sequence_index` *before* this award, or null if this is the store's first award — that self-reference is the re-sequencing audit trail showing which car this one merged behind. Finally `merge_slots_free` is recomputed downward by one. A successful award returns 201 Created.

Committing the awarded car moves the slot `RESERVED → COMMITTED` and, in the same operation, moves the loop `ORDERED → MERGED`. It requires the slot to be in `RESERVED`, the slot's `timer_loop_id` to name the loop being merged, that loop's `timing_state` to be `ORDERED`, and the store not to be frozen; a commit attempted from any other `slot_state` is `ERR_INVALID_SLOT_STATE`, while a commit whose awarded loop is no longer `ORDERED` is `ERR_LOOP_NOT_MERGEABLE`. The commit stamps `merge_at` and computes `merge_wait_seconds`, and it leaves `merge_slots_free` unchanged, because `RESERVED` and `COMMITTED` occupy capacity equally.

A slot can leave the occupied set in three ways, and all three return capacity. It becomes `RELEASED` when its awarded loop departs and reaches `CLOSED` — the well-behaved path. It becomes `FORFEITED` from `RESERVED` when a pull-forward order for its awarded loop enters `ISSUED`, whether the operator issued that pull-forward directly or the system auto-issued it; in that case the awarded loop *keeps* its `timing_state` of `ORDERED` and re-enters the merge candidate pool once its pull-forward is cleared, so a forfeited reservation costs the car its place in line but not its progress. And it becomes `FORFEITED` from `COMMITTED` when its awarded loop is abandoned. In every one of these cases the store's `merge_slots_free` is recomputed upward by one — capacity is conserved across award and abandonment exactly. Merge slots can be listed with filters on `restaurant_id`, `timer_loop_id` and `slot_state`, and read individually to see the `award_reason` that selected them.

### 3.5. Pulling Lagging Cars Forward

When a car's items are not ready, holding it at the window stalls every car behind it. A `ShiftLeader` therefore issues a **pull-forward order** naming the `timer_loop_id` of the lagging car and a `reason` drawn from `ITEM_LAG`, `REMAKE_OPEN` and `MERGE_CONFLICT`, optionally recording `lag_seconds` — the operator-observed lag behind the loop's pinned pull-forward target, defaulting to 0 and accepted between 0 and 900 inclusive. The server copies the loop's `restaurant_id` onto the order rather than taking it from the client, stamps `issued_at` from the logical clock, sets `escalation_count` to 0, leaves `reissued_at` and `cleared_at` null, and sets `pf_state` to `ISSUED`. A loop may carry only one live pull-forward at a time: if any pull-forward order for that loop is already in `ISSUED` or `PARKED`, the request is rejected with `ERR_PULL_FORWARD_ALREADY_OPEN` (409). Issuing also has an immediate structural consequence — any merge slot the loop holds in `RESERVED` becomes `FORFEITED` and `merge_slots_free` is recomputed upward by one.

The lifecycle is deliberately **cyclic**. Parking moves the order `ISSUED → PARKED`, which records that the car has been pulled into a numbered parking spot. Reissuing moves it back `PARKED → ISSUED` when the items still are not ready; it stamps `reissued_at` from the logical clock, increments `escalation_count` by 1, and adds a further 15 seconds of escalation penalty to the loop's `adjusted_total_seconds` for each escalation accumulated. Reissue requires `escalation_count` to be at most 1 beforehand, which caps a pull-forward at two reissues in total; a third attempt is rejected with `ERR_PULL_FORWARD_ESCALATION_LIMIT` (422). Both park and reissue require the store not to be frozen.

Clearing moves the order to `CLEARED` and is reachable from both `ISSUED` and `PARKED`, in each case requiring an unfrozen store. It stamps `cleared_at` from the logical clock, and — because the loop no longer has a live pull-forward — the loop becomes eligible for the merge selector again, still in `timing_state` `ORDERED`. Clearing also happens without an operator asking: when a loop departs and reaches `CLOSED`, any of its pull-forward orders in `ISSUED` is moved to `CLEARED` with `cleared_at` stamped, as is one in `PARKED`.

Cancellation is the other terminal outcome and is always system-driven: when a loop is abandoned, its pull-forward orders in `ISSUED` and in `PARKED` alike become `CANCELLED`, and the escalation penalty that order contributed leaves the loop's `adjusted_total_seconds` — which is why the adjusted-total formula counts escalations only on orders whose `pf_state` is not `CANCELLED`. `CLEARED` and `CANCELLED` are both terminal. Pull-forward orders can be listed with filters on `restaurant_id`, `timer_loop_id` and `pf_state`, and read individually to inspect the escalation count.

### 3.6. Order Accuracy: Incidents, Remakes and Settlement

An **accuracy incident** records that a car got the wrong food. A `ShiftLeader` logs one against a `timer_loop_id`, naming the reporter in `logged_by_staff_id` and the defect in `incident_type`, chosen from `WRONG_ITEM`, `MISSING_ITEM`, `WRONG_SIZE` and `ALLERGEN`. The server copies the loop's `restaurant_id` onto the incident, leaves `remade_by_staff_id` and `waiver_reason` null, and sets `incident_state` to `LOGGED`. Logging is only possible once the car has actually ordered: the loop's `timing_state` must be `ORDERED`, `MERGED`, `AT_WINDOW` or `CLOSED`, and a loop still in `OPEN` or `GREETED` is rejected with `ERR_LOOP_HAS_NO_ORDER`. The loop's `accuracy_state` must be `PENDING` or `VERIFIED`; a loop already carrying an unresolved remake — `accuracy_state` of `REMAKE_OPEN` or `REMADE` — is rejected with `ERR_REMAKE_ALREADY_OPEN`.

Severity, penalty and cost are all derived, never supplied. An `ALLERGEN` defect is `CRITICAL`; a `WRONG_ITEM` or `MISSING_ITEM` defect is `MAJOR`; a `WRONG_SIZE` defect is `MINOR`. `penalty_seconds` follows from `severity` alone: 20 seconds for `MINOR`, 45 for `MAJOR`, 90 for `CRITICAL`. `remake_cost_cents` likewise: 350 cents for `MINOR`, 750 for `MAJOR`, 1200 for `CRITICAL`. No rounding is involved — both are integers. `settlement_state` starts at `ACCRUED`, and because the store's accrued figure counts both `ACCRUED` and `CHARGED` incidents, the food cost enters `remake_cost_accrued_cents` the moment the defect is logged rather than when it is settled.

Logging drives a three-hop cascade. The loop's `accuracy_state` moves to `REMAKE_OPEN` — from `PENDING` for a defect caught in the lane, or from `VERIFIED` for a late guest complaint about a car that has already departed — and its `adjusted_total_seconds` is recomputed as soon as `total_seconds` is known, gaining the new `penalty_seconds`. The `timing_state` is not touched at all: a `CLOSED` car stays `CLOSED`. **Hop one:** because the loop's accuracy dimension became `REMAKE_OPEN`, a pull-forward order with `reason` `REMAKE_OPEN` is auto-issued whenever that loop is holding a merge slot in `RESERVED`. **Hop two:** because that pull-forward entered `ISSUED`, the held slot becomes `FORFEITED` and `merge_slots_free` is recomputed upward by one. **Hop three:** because `open_remake_count` rose, the rollup chain re-derives `required_oot_count` — remember the accuracy bump adds an outside order-taker as soon as a single remake is open — and then `service_posture`, which reaches `ACCURACY_HOLD` at two or more open remakes and thereby blocks further merge awards. The late-complaint case, from `VERIFIED`, is the reason a `FINAL` report can diverge from a `PROVISIONAL` one that was published earlier over the same window.

Delivering the remake moves the incident `LOGGED → REMADE` and the loop's `accuracy_state` to `REMADE`. It requires an unfrozen store, the incident to be in `LOGGED`, and — the segregation-of-duties rule — the `remade_by_staff_id` supplied in the request to be a *different* team member from `logged_by_staff_id`, who must belong to the same store as the incident. Crediting the reporter with their own remake is rejected with `ERR_SEGREGATION_OF_DUTIES` (409). `settlement_state` stays `ACCRUED`; delivering food does not settle money.

Settlement belongs to an `AccuracyAuditor`, and the two branches are deliberately opposite. **Closing** moves the incident `REMADE → CLOSED` and `settlement_state` `ACCRUED → CHARGED`; it requires the incident to be in `REMADE` and the store not to be frozen. The loop's `accuracy_state` returns to `VERIFIED`, but the incident's `penalty_seconds` **stay inside** `adjusted_total_seconds`, because the defect really did happen and really did cost the guest time. The store's `remake_cost_accrued_cents` is unchanged by closing — moving from `ACCRUED` to `CHARGED` keeps the money in the ledger, since the accrued figure sums both states. What does change is `open_remake_count`, which drops, and therefore `service_posture`, which is recomputed and may leave `ACCURACY_HOLD`.

**Waiving** moves the incident `LOGGED → WAIVED` and `settlement_state` `ACCRUED → REVERSED`, storing the supplied `waiver_reason`. It requires the incident to be in `LOGGED`, the store not to be frozen, and the incident's `severity` not to be `CRITICAL` — an `ALLERGEN` defect can never be waived, and the attempt is rejected with `ERR_ALLERGEN_WAIVER_FORBIDDEN` (422). Waiving is the true compensating action: the loop's `accuracy_state` becomes `WAIVED`, the incident's `penalty_seconds` **leave** `adjusted_total_seconds`, and the store's `remake_cost_accrued_cents` drops by exactly this incident's `remake_cost_cents`, restoring the ledger to the value it held before the incident was logged. `open_remake_count` drops and `service_posture` is recomputed. Both `CLOSED` and `WAIVED` are terminal for the incident. Incidents can be listed with filters on `restaurant_id`, `timer_loop_id`, `logged_by_staff_id`, `remade_by_staff_id` and `incident_state`, and read individually.

### 3.7. Weather and Event Forecast Overrides

Rain, a stadium letting out, or a point-of-sale outage all change what a lane will do in the next hour in ways the trailing ten-minute car count cannot see yet. A **forecast override** lets a store say so in advance, and it is deliberately a three-party workflow: the store proposes, the chain adjudicates, and the store puts the decision into force.

An `Operator` proposes an override against a `restaurant_id`, naming its `source` — one of `WEATHER`, `LOCAL_EVENT` or `SYSTEM_OUTAGE` — and its effective window. `effective_start_at` and `effective_end_at` describe a **closed** interval, inclusive at both ends, with the end strictly after the start. `projected_cars_delta_pct` is a signed fraction between -0.50 and 1.00 inclusive, describing how much the car rate is expected to move; it is applied to `cars_per_hour_observed` only when the store's `staffing_basis` is `FORECAST_ADJUSTED`. `target_relief_pct_override` is optional and defaults to null; when supplied it must lie between 0.00 and 0.20 inclusive and it sets the override relief explicitly, and when null the override relief is derived from `projected_cars_delta_pct` as described in §3.3. The proposal must also carry `expected_restaurant_version` per §2.10. A proposed override starts at `fo_state` `PROPOSED`, with `approved_by_user_id` and `rejection_reason` null, and it has **no effect whatsoever** on any store rollup — proposing changes no target and no tier.

Adjudication is a `ProgramAdmin` fork with two disjoint outcomes, both requiring the override to be in `PROPOSED`, and neither gated by the store's posture. Approval moves it `PROPOSED → APPROVED` and stamps the approving admin's opaque `X-User-ID` into `approved_by_user_id`; approval alone still changes no target and no rollup. Rejection moves it `PROPOSED → REJECTED`, stores the supplied `rejection_reason`, and leaves `approved_by_user_id` null; `REJECTED` is terminal and a rejected override can never be applied.

Putting an approved override into force is the `Operator`'s act, moving it `APPROVED → APPLIED`. It requires the override to be in `APPROVED`, the store not to be frozen, and it enforces an **aggregate capacity cap** across the store's already-applied overrides: take every override of this store whose `fo_state` is `APPLIED` and whose closed interval intersects this one — touching endpoints count as intersecting — sum the absolute values of their `projected_cars_delta_pct`, add the absolute value of this override's own `projected_cars_delta_pct`, and the total must not exceed 0.50. A total above that is rejected with `ERR_OVERRIDE_AGGREGATE_CAP` (422). Note that the cap counts only overrides already in force, which is exactly why several `PROPOSED` overrides on overlapping windows are legitimate.

Once applied, the override becomes visible to two calculations, and `APPLIED` is terminal. It feeds the effective car rate whenever the store's `staffing_basis` is `FORECAST_ADJUSTED`, and it feeds the override relief that gets pinned onto newly created timer loops. Applying immediately re-runs the rollup chain — `cars_per_hour_effective`, then `volume_tier`, then `required_oot_count`, then `service_posture` — and from that moment newly created loops pin relieved targets that include this override's relief, while loops created earlier keep the targets they already pinned.

Only overrides in `APPLIED` are visible to any calculation at all; `PROPOSED`, `APPROVED` and `REJECTED` overrides are invisible everywhere. When more than one applied override covers the instant in question, exactly one is selected as the one in force: candidates are the store's applied overrides whose closed interval contains that instant, both ends inclusive; they are ranked by `projected_cars_delta_pct` descending, and ties are broken by the earlier `created_at` — never by `id`. The first candidate under that ranking is the override in force. When there are no candidates at all, there is no override in force, and both the relief contribution and the delta contribution are 0.00. Overrides can be listed with filters on `restaurant_id`, `fo_state` and `source`, and read individually.

### 3.8. Peak-Hour Throughput Reporting

A **throughput report** scores a closed past window of lane performance, and its central design property is that the same stored rows yield materially different numbers under its two variants. A `MarketCoach` creates one naming the `restaurant_id`, the window as `window_start_at` and `window_end_at`, the `variant`, the required `expected_restaurant_version`, and optionally `supersedes_report_id` — the identifier of a published report over comparable ground that this one is intended to replace. The window's end must be strictly after its start, and it must not reach into the future: `window_end_at` at or before the logical clock, or the request fails with `ERR_REPORT_WINDOW_FUTURE`. Every metric is computed **once, at creation**, from the state visible at that moment; publishing never recomputes anything. A new report has `report_state` `DRAFT` and `retraction_reason` null, and creating it increments the store's `version` by 1.

`variant` selects both the input set and the metric, and `metric_basis` records the choice: it is `TOTAL` for a `PROVISIONAL` report and `ADJUSTED_TOTAL` for a `FINAL` one.

- A **`PROVISIONAL`** report's input set is the store's timer loops whose `timing_state` is `CLOSED` and whose **`depart_at`** falls at or after `window_start_at` and strictly before `window_end_at`, *excluding* any loop whose `accuracy_state` is `REMAKE_OPEN`. Its metric per loop is the raw `total_seconds`. Loops still carrying an open remake, and loops that arrived inside the window but departed after it, are invisible to this variant.
- A **`FINAL`** report's input set is the store's timer loops whose `timing_state` is `CLOSED` or `ABANDONED` and whose **`arrive_at`** — arrival, not departure — falls at or after `window_start_at` and strictly before `window_end_at`, *including* loops whose `accuracy_state` is `REMAKE_OPEN`. Its metric per loop is `adjusted_total_seconds`, with the accuracy and escalation penalties folded in, and each `ABANDONED` loop in the set contributes a flat 300 seconds as its metric instead. On identical stored rows this yields a different `cars_served`, a different `window_tier` and a different `attainment_band` from the provisional variant.

`cars_served` is the size of whichever input set the variant selected. `avg_metric_seconds` is the sum of the variant's metric across the input set divided by `cars_served`, rounded half up to one decimal place. `mean_pinned_target_seconds` is the sum of `target_total_seconds_pinned` across the same input set divided by `cars_served`, held **exactly and unrounded** — it is an intermediate, and rounding it here would corrupt the attainment figure. `open_remake_incident_count` is computed independently of the variant's input set: it counts the accuracy incidents whose `incident_state` is `LOGGED` or `REMADE` and whose loop's `arrive_at` falls at or after `window_start_at` and strictly before `window_end_at`.

The remaining figures are produced by a chain whose **evaluation order is pinned** and which only *looks* circular — the relief that sets the target comes from a tier, the tier comes from the window's own car rate, and the rate comes from the very input set whose attainment is being scored. Each step runs exactly once, in this order:

1. `cars_served` is already known from the input set.
2. `cars_per_hour` is `cars_served` multiplied by 3600 and divided by the window's length in seconds, rounded half up to one decimal place.
3. `window_tier` is the `tier` of the band whose `cars_per_hour_floor` is at or below `cars_per_hour` and whose `cars_per_hour_ceiling` is null or strictly above it. This is **this window's** tier, derived from the window's own rate — it is emphatically **not** the store's `volume_tier`, which reflects the trailing ten minutes at request time and is frequently a different band.
4. The relief in play is `target_relief_pct` on the band selected in step 3.
5. `target_total_seconds_effective` is `mean_pinned_target_seconds` multiplied by one plus that relief, rounded half up to a whole second.
6. `attainment_pct` is 100 multiplied by `target_total_seconds_effective` and divided by `avg_metric_seconds`, rounded half up to two decimal places. A window that beat its effective target therefore scores above 100.
7. `attainment_band` is `GOLD` when `attainment_pct` is at least 110, otherwise `GREEN` when it is at least 100, otherwise `AMBER` when it is at least 90, otherwise `RED`.
8. `coaching_pool_points` is the coaching budget the window earned: take the band award — 10 points for `GOLD`, 6 for `GREEN`, 3 for `AMBER`, 0 for `RED` — add a volume award equal to `cars_served` divided by 25 and rounded **down** to a whole number but capped at 6 points, then subtract 2 points for each incident counted in `open_remake_incident_count`. The result is floored at 0, so the pool can never go negative.

An empty window is handled explicitly rather than by division: when `cars_served` is 0, `avg_metric_seconds`, `mean_pinned_target_seconds`, `target_total_seconds_effective`, `attainment_pct` and `attainment_band` are all null, `cars_per_hour` is 0.0, `window_tier` is the tier of the band containing a car rate of 0.0, and `coaching_pool_points` is 0. Such a report may be created — it is a legitimate statement that nothing happened — but it may not be published, and the publish attempt is rejected with `ERR_REPORT_WINDOW_EMPTY`.

Publishing moves the report `DRAFT → PUBLISHED` and requires the report to be in `DRAFT`, `cars_served` to be at least 1, and the store not to be frozen. If the report names a `supersedes_report_id` and that predecessor is currently `PUBLISHED`, the predecessor moves `PUBLISHED → SUPERSEDED` as part of the same operation; existing coaching interventions keep pointing at the superseded report through their `throughput_report_id`, but no new intervention may be created against it. Publishing is what makes coaching possible at all.

Retraction moves a report to `RETRACTED`, is reachable from both `PUBLISHED` and `DRAFT`, requires an unfrozen store, and stores the supplied `retraction_reason`. `SUPERSEDED` and `RETRACTED` are both terminal, and creating a coaching intervention against a retracted report fails with `ERR_REPORT_NOT_PUBLISHED`. Reports can be listed with filters on `restaurant_id`, `supersedes_report_id`, `variant` and `report_state`, and read individually with all their computed metrics.

### 3.9. Coaching Interventions

Coaching is the program's output, and it must be traceable to a published number. A `MarketCoach` drafts a **coaching intervention** naming the `throughput_report_id` that justifies it, the `staff_member_id` of the coachee, and the `focus_segment` under discussion — one of `GREET`, `ORDER`, `PULL_FORWARD`, `WINDOW` or `ACCURACY`. The referenced report must be in `PUBLISHED`, or the draft is rejected with `ERR_REPORT_NOT_PUBLISHED`, and the report's store must match the coachee's store. The server copies the report's `restaurant_id` onto the intervention, sets `ci_state` to `DRAFT`, sets `revision_count` to 0, and leaves `issued_by_user_id`, `contest_reason` and `closure_note` null.

Two figures are scored at draft time, and both are recomputed on every `DRAFT → ISSUED` transition from the report's then-current stored figures. `segment_gap_seconds` measures how far behind target the focus segment ran, over the referenced report's own stored input set — whichever loops that report's `variant` selected. For the four timing segments it is the mean of the matching measured duration across the input set (`greet_seconds` for `GREET`, `order_seconds` for `ORDER`, `pull_forward_seconds` for `PULL_FORWARD`, `window_seconds` for `WINDOW`) minus the mean of the matching pinned target across the same input set (`greet_target_pinned`, `order_target_pinned`, `pull_forward_target_pinned` and `window_target_pinned` respectively), floored at 0 so a segment that beat its target contributes no gap. For a `focus_segment` of `ACCURACY` it is instead the sum of `penalty_seconds` over the accuracy incidents whose `incident_state` is `LOGGED`, `REMADE` or `CLOSED` and whose loop is in that input set, divided by the report's `cars_served`. Both means are computed exactly, before any rounding.

`priority_score` then combines three saturating components on a 0-to-100 scale. The gap component is worth up to 60 points and is 60 multiplied by the smaller of 1.0 and `segment_gap_seconds` divided by 30 seconds — a segment running half a minute or more behind target saturates it. The accuracy component is worth up to 25 points and is 25 multiplied by the smaller of 1.0 and the report's `open_remake_incident_count` divided by 3 — three or more open remakes in the window saturate it. The band component is worth up to 15 points and is 15 multiplied by a band weight of 0.0 for `GOLD`, 0.2 for `GREEN`, 0.6 for `AMBER` and 1.0 for `RED`. The three components are added, the sum is capped at 100, and the result is rounded half up to two decimal places. The intervention's `tier` follows from the score: `TIER_C_RETRAIN` when `priority_score` is at least 70, otherwise `TIER_B_COACH` when it is at least 40, otherwise `TIER_A_OBSERVE`.

Issuing moves the intervention `DRAFT → ISSUED`, requires it to be in `DRAFT`, requires the referenced report to still be in `PUBLISHED`, and requires the store not to be frozen. It stamps the issuing coach's opaque `X-User-ID` into `issued_by_user_id`, overwriting whatever was there from a previous issue, and recomputes `segment_gap_seconds`, `priority_score` and `tier` in full from the report's stored figures as they now stand — so an intervention that goes round the revision loop can come back with a different score and a different `tier`.

Only the coachee responds. Acknowledging moves the intervention `ISSUED → ACKNOWLEDGED` and requires it to be in `ISSUED`, the acting `X-User-ID` to equal the intervention's `staff_member_id`, and the store not to be frozen. Contesting also starts from `ISSUED` under the same ownership and posture conditions, requires `revision_count` to be at most 1 beforehand, and stores the supplied `contest_reason`. Contesting is a **cyclic** two-step that completes inside a single request: the intervention passes through `ISSUED → CONTESTED` and then, as an automatic follow-through of that same request, `CONTESTED → DRAFT` with `revision_count` incremented by 1. The intervention therefore re-enters the authoring loop and must be issued again. Because `revision_count` must be at most 1 to contest, an intervention can go round that loop at most twice; a third contest is rejected with `ERR_COACHING_REVISION_LIMIT`.

Closure is where segregation of duties bites a second time. Moving the intervention `ACKNOWLEDGED → CLOSED` requires it to be in `ACKNOWLEDGED`, requires the store not to be frozen, requires a `closure_note`, and requires the closing `MarketCoach`'s `X-User-ID` to be **different** from the `issued_by_user_id` recorded at issue time — the coach who issued an intervention may not be the coach who closes it, and an attempt to do so is rejected with `ERR_SEGREGATION_OF_DUTIES`. `CLOSED` is terminal. Interventions can be listed with filters on `restaurant_id`, `throughput_report_id`, `staff_member_id` and `ci_state`, and read individually with their score, tier and revision count.
