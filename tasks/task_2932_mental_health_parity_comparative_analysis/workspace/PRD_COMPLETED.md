# Mental Health Parity Comparative Analysis API — Product Requirements Document

## 1. Introduction

Employer group health plans that cover mental-health and substance-use-disorder benefits must be able to demonstrate, on demand and in writing, that the limitations they impose on those benefits are no more restrictive than the limitations imposed on comparable medical and surgical benefits. In practice that demonstration is assembled by two organisations working from different records: the employer plan sponsor, who owns the plan design and answers to the regulator, and the third-party administrator (TPA), who actually adjudicates the claims and therefore holds the only evidence of how a limitation behaves in operation. Today that evidence arrives late, in inconsistent formats, and often only after a regulator has already asked for it. The comparative analyses that result are narrative documents whose arithmetic nobody can reproduce.

This service replaces that process with a system of record. It carries the plan's benefit classifications and the quantitative limitation levels attached to them; it runs the substantially-all and predominant tests over those levels and stores the verdicts; it maintains an inventory of nonquantitative treatment limitations (NQTLs) together with the comparative analysis documenting each one; it tracks the contractual production requests issued to the TPA and the as-applied data the TPA produces against them; and it converts that as-applied data into a reproducible stringency-in-operation index that a compliance officer must agree with before recording a parity determination. When a determination finds a violation, the system issues the participant notice, opens the remediation posture on the plan year, books the corrective plan's reprocessing liability against a board-approved cap, and releases that liability again when the plan closes.

Two design commitments run through everything below. First, every derived number is reproducible: each calculation names its input set, its evaluation order, its constants and its rounding step, and a second run over unchanged inputs must return the identical value. Second, nothing is silently overwritten. The whole surface is mounted under `/parity`, with one out-of-band logical-clock endpoint used to drive deadline behaviour deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors and Role-Based Access Control

Every request to the API — including every read — must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the capability set that user is acting under. If either header is absent, or is present but sent as an empty string, the request is rejected with `ERR_MISSING_IDENTITY_HEADERS` (HTTP 401); an empty-string header is treated exactly as an absent one. Only a wholly empty value counts as empty: a header whose value is one or more space characters is a present, non-empty value and is carried forward verbatim, so a whitespace-only `X-User-Role` is rejected as an unrecognised role rather than as a missing header. If `X-User-Role` carries a value that is not one of the four recognised roles, the request is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401). A recognised role that is not permitted to invoke the requested operation is rejected with `ERR_UNAUTHORIZED` (HTTP 403). The four roles, spelled exactly as they must appear in the header, are `PlanSponsor`, `Administrator`, `ComplianceOfficer` and `Regulator`.

A `PlanSponsor` is employer plan-sponsor staff. The sponsor owns the plan-design surface — registering the servicing TPA, opening plan years, classifying benefits and recording limitation levels — issues contractual production requests to the TPA and escalates them when they go unanswered, drafts comparative analyses, and answers the regulator. An `Administrator` is third-party-administrator staff: it produces the requested as-applied data sets, records the limitation levels it administers, and may draft, submit and reopen comparative analyses on the sponsor's behalf. A `ComplianceOfficer` is the independent compliance reviewer who certifies comparative analyses, records parity determinations on NQTL items, and decides and closes corrective action plans. A `Regulator` is state or federal regulatory staff: it opens requests for a plan year's comparative analyses and adjudicates the sponsor's response, and it may read every resource in the system but may not author plan data.

The two headers relate to persisted data differently depending on the role. When `X-User-Role` is `Administrator`, `X-User-ID` is the `id` of the acting `Administrator` record — the TPA itself is a first-class resource in this system, so the acting identity is entity-backed. That binding is documentary only: the server never resolves the header value against the administrator collection, so an `Administrator` request whose `X-User-ID` names no registered administrator authenticates and authorises exactly as any other and never yields `ERR_ADMINISTRATOR_NOT_FOUND` on account of the header. No endpoint in this specification narrows a result set or rejects a request by comparing a resource's `administrator_id` to `X-User-ID`; the binding matters because it names which TPA is acting, not because it filters access. When `X-User-Role` is `PlanSponsor`, `ComplianceOfficer` or `Regulator`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against any entity's `id`. The server does, however, record those opaque identifiers where a transition captures an actor: the author of a comparative analysis is stamped into `authored_by_user_id`, the officer who certifies it into `certified_by_user_id`, the officer whose determination moves an NQTL item into `determination_recorded_by_user_id`, and the officer who approves a corrective action plan into `approved_by_user_id`. Each of those four fields is null until the action that stamps it occurs: `authored_by_user_id` is written at analysis creation and is therefore always populated, while `certified_by_user_id` stays null until the analysis reaches `CERTIFIED`, `determination_recorded_by_user_id` stays null until a determination first moves the item to `COMPLIANT` or `VIOLATION`, and `approved_by_user_id` stays null until the corrective action plan reaches `APPROVED`. Those stamped values are later compared against a *subsequent* actor's `X-User-ID` to enforce segregation of duties (§2.9), which is the only place user identifiers carry behavioural weight.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the upper-case letters `A`–`Z` and the digits `0`–`9`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. The free-text annotations that the transition endpoints accept — `review_note`, `rationale`, `decision_note`, `closure_note`, `response_note` and `adjudication_note` — are validated on the way in but are not resource fields: they are neither persisted nor echoed, and appear in no response payload. `rationale` on a determination is required and must be a string of at least one character; the other five are optional, and when supplied must likewise be non-empty strings, with no upper bound on their length.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses follow this standard envelope format, whether the status is one of the 4xx codes the catalogue of §5 assigns or the 500 raised by an unexpected server fault:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two query parameters. `limit` bounds how many items come back; when it is not supplied it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` says how many items to skip and defaults to 0; negative values are not accepted. A `limit` outside the range 1 to 100 inclusive, or a negative `offset`, is a payload-shape failure and is rejected with `ERR_VALIDATION` (HTTP 422); so is a value that is not a whole number at all — an empty, fractional or otherwise non-numeric `limit` or `offset` is rejected the same way, while whitespace surrounding an otherwise valid integer is tolerated. Supplying the parameter with no value at all is therefore not the same as omitting it: an omitted parameter takes its default, whereas an empty one is a validation failure.

Unless a specific endpoint states otherwise, list results are ordered by the resource's creation timestamp, `created_at`, in ascending order, and rows sharing an identical `created_at` — which a millisecond-resolution stamp makes routine when several rows are written in quick succession — are ordered by the sequence in which the server wrote them, earliest write first. Ordering is therefore total and stable rather than dependent on the timestamp alone.

List responses populate four fields in the envelope's `meta` object: `limit` and `offset` echo the effective values used for the page, `total_count` reports how many rows match the filters before the page window is applied, and `has_more` is true when rows remain beyond the current window. Those four fields appear only on list endpoints; a single-resource or inline-object response carries `api_request_id` and `api_request_timestamp` alone. Every list filter named in §3 and §4 is an exact-match comparison against the stored value, applied before the ordering and before the page window, so `total_count` counts the filtered rows; a filter whose value lies outside the field's declared set is not a validation failure but simply matches no row, a filter naming a value a nullable field does not hold matches no row either, boolean fields are matched against the literals `true` and `false`, an omitted filter constrains nothing, and query parameters the endpoint does not declare are ignored rather than rejected.

### 2.4. Common Resource Properties

Every resource in this system carries a server-minted `id`: a UUID string with no type prefix and no embedded meaning. Clients never supply an `id`. The system also starts empty: no administrator, plan year, classification or any other row is seeded or preloaded at start-up, so every resource this document describes comes into existence through the operations of §4, and a list endpoint called against a fresh system returns an empty `data` array with `total_count` 0.

Eleven of the twelve resource kinds — administrators, plan years, benefit classifications, treatment limitations, parity tests, NQTL items, comparative analyses, vendor data requests, data submissions, corrective action plans and regulator requests — also carry the full system-managed property set:

- `created_at` (string): an ISO 8601 UTC timestamp with exactly three fractional digits, recording when the row was first written.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row, including mutations the server performs on its own initiative as part of a cascade.
- `version` (integer): a system-managed counter that starts at 1 on creation and increments by exactly 1 on every mutation of the row. A recomputation that rewrites a derived field — a counter, a score, a posture — is a mutation for this purpose and therefore both refreshes `updated_at` and increments `version`.

Participant notices are the single exception. A `ParticipantNotice` is append-only: it is created by a cascade, is never updated afterwards, and therefore carries only `id` and `created_at`. It has neither `updated_at` nor `version`, and neither field appears in its response payload.

### 2.5. The Logical Compliance Clock

Deadlines drive a large part of this domain, so the server does not read wall-clock time for any business decision. It maintains a single logical clock that begins at exactly `2026-08-01T00:00:00Z` and moves only when a client advances it. Every stamped instant — `issued_at` on a vendor data request and on a participant notice, `opened_at` on a regulator request — and every derived deadline — `due_at`, `regulatory_due_at`, `response_due_at` — is taken from this clock, as is every overdue or window-expiry comparison. Wherever this document advances an instant by a number of calendar days, that means adding exactly that many periods of twenty-four hours to the instant in UTC, so the time of day is preserved and no calendar or daylight-saving adjustment is applied. Instants are rendered as ISO 8601 UTC with three fractional digits, truncated rather than rounded to that width. The logical clock governs business instants only: the envelope's `api_request_timestamp` and every row's `created_at` and `updated_at` are wall-clock values, move independently of the logical clock, and are never compared against a deadline. Date-valued fields the client supplies — `measurement_period_start`, `measurement_period_end` and `target_completion_date` — are stored and returned as the client wrote them, which for a `YYYY-MM-DD` date is the only admissible form.

A test-driving capability, available to all four roles, sets the clock to a supplied `current_utc` instant. The clock is monotonic: `current_utc` must be strictly later than the clock's present value, and a value equal to or earlier than the present value is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422). Because moving the clock forward can turn an on-time production request late without the TPA doing anything at all, advancing the clock also re-derives `is_overdue` on every vendor data request, re-derives `late_request_count`, `regulator_reportable_late_count` and both cooperation-score variants on every administrator, and recomputes the compliance posture of every plan year. `is_overdue` is not a stored column but a value evaluated afresh from the clock each time a vendor data request is rendered, so it is always current and a clock move on its own neither refreshes a request's `updated_at` nor increments its `version`; only administrators and plan years are re-stamped by the sweep, and each of those only when one of its derived values actually moves. The response to a successful clock move is not a stored resource but an inline object reporting the new `current_utc` — re-rendered in the canonical three-fractional-digit form rather than echoed back exactly as the client wrote it — together with a `recomputed_administrator_count` and a `recomputed_plan_year_count`, which report how many administrator and plan-year rows the sweep visited, that is every such row in existence, rather than how many of them changed. Both counts are 0 while no administrator or plan year has been registered, and a successful clock move returns HTTP 200.

### 2.6. Numeric Precision and Rounding

All arithmetic in this system is performed in exact decimal arithmetic, never in binary floating point, and every rounding step uses the round-half-up convention. The rounding step is part of each calculation's contract, not an afterthought, and the specification pins where in the sequence it happens; rounding earlier or later than specified produces different published numbers and is wrong even when the difference is one unit in the last place.

The published precisions are: the substantially-all ratio on a parity test, and the two denial rates on a data submission, are reported to six decimal places; the denial-rate disparity ratio and the network-composition gap are reported to four decimal places; the stringency-in-operation index, both administrator cooperation scores and the regulator response completeness score are reported to two decimal places; and every liability amount is a whole number of cents. Weight sums used by the quantitative tests are exact integers and are never rounded. A predominant level is reported exactly as the stored level value, with no rounding at all.

Money is carried in integer cents throughout — `remediation_liability_cap_cents`, `remediation_liability_cents`, `average_claim_cents`, `reprocessing_liability_cents`, `projected_plan_payments_cents`, `total_ms_payments_cents` and `subject_payments_cents` are all integers — so no monetary field is ever a decimal string. The non-monetary decimal fields are likewise transmitted as JSON numbers and never as strings. The stated precision fixes the scale a value is rounded *to*, not the way it is printed: a score rounded to two places and standing at one hundred is transmitted as the JSON number `100.0`, a ratio of exactly two is transmitted as `2.0`, and a `level_value` or `predominant_level` recorded as a whole number is transmitted with a fractional part of zero. Trailing zeros are therefore not significant, and a value must be compared numerically rather than by its printed form.

### 2.7. Plan-Year Gating

A plan year is the container that everything else ultimately hangs from, and its `status` gates which child mutations the server will accept. Two distinct gates apply, and they are not the same rule.

The broad gate is closure. Once a plan year reaches `CLOSED`, every write that reaches it — whether the plan year is named in the path or reached through a chain of foreign keys, and whatever the resource being written is — is rejected with `ERR_PLAN_YEAR_CLOSED` (HTTP 409). The only writes exempt from this gate are the three that do not reach a plan year at all: registering an administrator, opening a plan year, and moving the logical clock.

The narrow gate protects the plan-design surface only. Creating a benefit classification or a treatment-limitation level additionally requires the owning plan year to be exactly `OPEN`; if it sits in `UNDER_REGULATOR_REVIEW` or `REMEDIATION` the write is rejected with `ERR_PLAN_YEAR_NOT_OPEN` (HTTP 409). The reasoning is documentary: once a regulator has demanded the analyses, or once a violation has been found, the plan design those analyses describe must stop moving. Every other child mutation — inventorying an NQTL, drafting or reviewing an analysis, issuing or answering a production request, running a parity test, deciding a corrective plan — remains available in `UNDER_REGULATOR_REVIEW` and `REMEDIATION` and is stopped only by `CLOSED`.

### 2.8. Cascade Propagation and Derived Values

A single client request in this system routinely mutates several rows. When it does, every row the request actually changes has its `updated_at` refreshed and its `version` incremented — the qualification below settles which rows a pure recomputation counts as having changed — and the cascade runs to completion inside the same request — there is no deferred or eventual reconciliation anywhere in this specification. A client that reads a resource immediately after a write observes every consequence of that write.

Derived fields are never client-supplied and are never trusted from a previous computation when their inputs may have moved. The administrator's obligation counters (`outstanding_request_count`, `late_request_count`, `breach_count`, `regulator_reportable_late_count`), its two cooperation scores and its `cooperation_status`; the plan year's `compliance_posture`, `open_violation_count`, `notified_violation_count`, `failing_parity_test_count` and `remediation_liability_cents`; an NQTL item's `stringency_in_operation_index` and `stringency_flag`; a vendor request's `validated_submission_count` and `is_overdue`; and a regulator request's `requested_item_count`, `covered_item_count`, `completeness_score` and `response_sufficient` are all recomputed from their input sets at each of the trigger points named in §3.

A recomputation performed on an already-existing row is a mutation of that row only when it actually moves one of those values: re-deriving them refreshes that row's `updated_at` and increments its `version` when at least one of them changes, and leaves both exactly as they were when the recomputation finds every one of them already correct. Where §3 states outright that an operation increments a named row's `version` by 1, that increment is unconditional and happens even if the recomputation it accompanies changed nothing — recording a parity determination, approving a corrective action plan and closing one all re-stamp the plan year outright, and a validated data submission re-stamps every NQTL item of its classification outright. Everywhere else the conditional rule governs, so a write whose only effect on a parent would have been a recomputation that moved nothing leaves that parent's `updated_at` and `version` where they stood. The initial derivation the server performs while writing a brand-new row is not covered by either rule: it is part of the creation, so a freshly created row is always returned with `version` 1 however many derived fields it arrived carrying.

Cascades run in a fixed order, deepest fact first. A determination that finds a violation, for example, first stamps the item and moves its status, then creates the participant notice, then re-derives the plan year's counters and posture from the new facts, and only then applies the plan-year status change that the new posture implies. Reversing those steps produces a plan year whose counters disagree with its status.

### 2.9. Segregation of Duties

Two independence rules are absolute, and both compare the current actor's `X-User-ID` against an identifier persisted earlier by a different action.

The author of a comparative analysis may never review it. On review, the acting `ComplianceOfficer`'s `X-User-ID` must differ from the analysis's `authored_by_user_id`; when they are equal the request is rejected with `ERR_SELF_CERTIFICATION` (HTTP 409). This applies on both review outcomes — sending an analysis back as insufficient is a review decision too, and self-review is refused there just as it is on certification.

Whoever finds a violation may not approve the plan that remedies it. On a corrective-action decision, the acting officer's `X-User-ID` must differ from the owning NQTL item's `determination_recorded_by_user_id`; when they are equal the request is rejected with `ERR_APPROVER_IS_DETERMINER` (HTTP 409).

### 2.10. Stale-Version Guards

Two write operations are guarded by optimistic concurrency control against a *parent* resource's version. In both cases the version field is a required input, not an optional one, and it carries the `version` value the client last observed on that parent.

Recording a parity determination on an NQTL item requires `expected_plan_year_version` in the request body, matching the current `version` of the plan year that owns the item. A determination is written on the basis of the plan year's posture, its `open_violation_count` and its `failing_parity_test_count`; any earlier accepted determination, superseding parity test, validated data submission or corrective-action decision has already rewritten those fields and advanced the plan year's version. An officer holding the older number is therefore deciding from a superseded record, and the request is rejected with `ERR_STALE_PLAN_YEAR_VERSION` (HTTP 412) so that the officer re-reads before deciding.

Creating a comparative analysis requires `expected_nqtl_item_version` in the request body, matching the current `version` of the NQTL item named by `nqtl_item_id`. This covers the create-with-supersede case in particular: a previously created analysis, or a validated as-applied data submission for the item's classification, has already moved the item's status and recomputed its stringency index, so the author's view of what the analysis must document is stale. A mismatch is rejected with `ERR_STALE_NQTL_ITEM_VERSION` (HTTP 412).

No other endpoint in this specification takes a version field, and none may be rejected for a version reason. Both guards are evaluated after existence and after state checks, so a caller who is both stale and acting on a wrongly-stated resource learns the state problem first.

### 2.11. Request Validation Order

When a request would fail more than one rule, the server reports the first failure in the following order and stops. The order is normative: a client that fixes failures one at a time must be able to walk this ladder from the top.

1. Identity headers present and non-empty — otherwise `ERR_MISSING_IDENTITY_HEADERS`.
2. `X-User-Role` is one of the four recognised roles — otherwise `ERR_UNKNOWN_ROLE`.
3. The role is permitted on this endpoint — otherwise `ERR_UNAUTHORIZED`.
4. Every identifier in the request path exists, checked left to right, each reported with the 404 code specific to the entity that identifier addresses.
5. Every foreign-key identifier in the request body exists, checked in the order the fields are listed on the owning resource in §3, and reported with the same entity-specific 404 codes.
6. Payload shape: every required field present, types as specified, enum values inside their declared sets, numeric ranges honoured, string lengths honoured, arrays non-empty and free of duplicates, dates written as `YYYY-MM-DD`, instants written as ISO 8601 UTC, and pagination values in range — otherwise `ERR_VALIDATION`. Five conventions settle the edges of this step. A request body that is absent, empty or unparseable is treated as an empty JSON object, so its required fields are reported missing in the ordinary way; a body that parses to something other than a JSON object — an array, a string, a number — is itself an `ERR_VALIDATION`. An optional field sent as JSON `null` is treated exactly as absent and takes its declared default, whereas a *required* field sent as `null` is present but ill-typed and fails its type check. Fields the endpoint does not declare, including any client-supplied `id`, are ignored rather than rejected. Types are strict: an integer field rejects a boolean, a fractional number and a numeric string alike; a decimal field accepts any finite JSON number, integral or fractional, but never a string and never a boolean; a boolean field accepts only `true` or `false`; and an enum, date or instant field accepts only a string. And a UTC instant may be written with either `T` or `t` as the separator, with any number of fractional-second digits or with none at all, and with `Z`, `z` or a zero UTC offset such as `+00:00` as its designator — a non-zero offset is not accepted, because every instant in this system is UTC.
7. Network-tier agreement with the benefit category (`ERR_NETWORK_TIER_MISMATCH`).
8. Sub-classification agreement with the benefit category (`ERR_SUB_CLASSIFICATION_MISMATCH`).
9. Measurement-period internal consistency, before any cross-row comparison (`ERR_MEASUREMENT_PERIOD_INVALID`).
10. Denial counts within adjudicated-claim counts (`ERR_DENIALS_EXCEED_CLAIMS`).
11. Submission type actually requested (`ERR_SUBMISSION_TYPE_NOT_REQUESTED`).
12. Cross-aggregate coherence of foreign-key combinations (`ERR_CROSS_PLAN_YEAR_REFERENCE`).
13. The analysis being superseded is still supersedable (`ERR_ANALYSIS_ALREADY_SUPERSEDED`).
14. The owning plan year is not `CLOSED` (`ERR_PLAN_YEAR_CLOSED`).
15. For plan-design writes only, the owning plan year is exactly `OPEN` (`ERR_PLAN_YEAR_NOT_OPEN`).
16. The target resource is in a state the requested transition departs from, reported with the transition-specific code: `ERR_ANALYSIS_NOT_DRAFT`, `ERR_ANALYSIS_NOT_SUBMITTED`, `ERR_ANALYSIS_NOT_INSUFFICIENT`, `ERR_ITEM_NOT_AWAITING_DETERMINATION`, `ERR_ITEM_NOT_IN_VIOLATION`, `ERR_CAP_NOT_DRAFT`, `ERR_CAP_NOT_APPROVED`, `ERR_REGULATOR_REQUEST_NOT_OPEN`, `ERR_REGULATOR_REQUEST_NOT_RESPONDED`, `ERR_ESCALATION_ALREADY_DECLARED`, `ERR_REQUEST_ALREADY_FULFILLED` or `ERR_PRODUCTION_WINDOW_CLOSED`.
17. The stale-version guards of §2.10 (`ERR_STALE_PLAN_YEAR_VERSION`, `ERR_STALE_NQTL_ITEM_VERSION`).
18. Self-review of a comparative analysis (`ERR_SELF_CERTIFICATION`).
19. Approver independence from the determiner (`ERR_APPROVER_IS_DETERMINER`).
20. As-applied evidence present before certification (`ERR_IN_OPERATION_DATA_MISSING`).
21. Documentation sufficiency at submission (`ERR_INSUFFICIENT_COMPARATIVE_ANALYSIS`).
22. A certified analysis behind a compliant determination (`ERR_ANALYSIS_NOT_CERTIFIED`).
23. Agreement between the determination outcome and the recomputed evidence (`ERR_STRINGENCY_CONTRADICTS_EVIDENCE`).
24. MH/SUD benefits covered in the classification being inventoried (`ERR_MH_BENEFITS_NOT_COVERED`).
25. No live duplicate NQTL item (`ERR_DUPLICATE_NQTL_ITEM`).
26. The revision loop has rounds left (`ERR_REVISION_LIMIT_REACHED`).
27. A non-zero substantially-all denominator (`ERR_EMPTY_TEST_POPULATION`).
28. Measurement periods do not collide (`ERR_MEASUREMENT_PERIOD_OVERLAP`).
29. Production windows do not collide (`ERR_PRODUCTION_WINDOW_OVERLAP`).
30. Escalation is ripe (`ERR_NOT_YET_OVERDUE`).
31. The regulator response window is still open (`ERR_RESPONSE_WINDOW_EXPIRED`).
32. The regulator's demand matches at least one inventoried item (`ERR_NO_REQUESTED_ITEMS`).
33. The logical clock moves forward (`ERR_CLOCK_NOT_MONOTONIC`).
34. The liability cap is respected (`ERR_LIABILITY_CAP_EXCEEDED`). This is evaluated last, so a corrective plan that would both breach the cap and violate approver independence reports the independence failure first.

The nine entity-specific 404 codes used by steps 4 and 5 are `ERR_ADMINISTRATOR_NOT_FOUND`, `ERR_PLAN_YEAR_NOT_FOUND`, `ERR_CLASSIFICATION_NOT_FOUND`, `ERR_NQTL_ITEM_NOT_FOUND`, `ERR_ANALYSIS_NOT_FOUND`, `ERR_VENDOR_REQUEST_NOT_FOUND`, `ERR_DATA_SUBMISSION_NOT_FOUND`, `ERR_CAP_NOT_FOUND` and `ERR_REGULATOR_REQUEST_NOT_FOUND`. Left-to-right path resolution means a nested read under a non-existent parent reports the parent's code and never reaches the child: asking for the treatment limitations of a classification that does not exist reports `ERR_CLASSIFICATION_NOT_FOUND`, and asking for the participant notices of a non-existent NQTL item reports `ERR_NQTL_ITEM_NOT_FOUND`. The same precedence applies to body foreign keys — when a payload names both a missing plan year and a missing classification, the plan year is reported first, because it is listed first on the resource being created. Step 5 can only judge an identifier it can read: a body foreign key that is absent, sent as `null`, sent as an empty string, or sent as some type other than a string is not checked for existence at all and is reported instead by step 6 as `ERR_VALIDATION`, so the nine 404 codes are reserved for well-formed identifiers that name nothing. An *optional* body foreign key left absent or null — `nqtl_item_id` on a vendor data request, `supersedes_analysis_id` on a comparative analysis — is skipped by both steps and takes its null default.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Review: the Servicing TPA and the Plan Year

Before anything can be reviewed, the sponsor registers the third-party administrator that services the plan. Registration is a `PlanSponsor` capability and captures the TPA's `legal_name` — between 1 and 120 characters — and a `contact_email` that must contain an `@` character, because that address is the contract-notice address used when a production obligation is escalated; the address must be at least one character long, carries no maximum length, and one lacking an `@` is a payload-shape failure reported as `ERR_VALIDATION` (HTTP 422). The sponsor also states `contractual_production_days`: the number of calendar days the contract allows the TPA to produce a requested analysis or data set. That value must be at least 1 and at most 120, and when the payload omits it the server applies a default of 45 days. A freshly registered administrator starts with all four obligation counters — `outstanding_request_count`, `late_request_count`, `breach_count` and `regulator_reportable_late_count` — at 0, with both `cooperation_score` and `regulatory_basis_cooperation_score` at 100.00, and with `cooperation_status` at `COOPERATIVE`. Any role may read an administrator afterwards to see both cooperation-score variants and the live obligation counters.

With a TPA on file, a `PlanSponsor` opens a plan year. The payload carries a `plan_name` of 1 to 120 characters for the employer group health plan under review, a `plan_year_label` of 1 to 16 characters as the human label of the year (for example, "2026"), the `administrator_id` of the registered TPA that is contractually obligated to produce this year's analyses, a `funding_arrangement` of either `SELF_FUNDED` or `INSURED`, a `covered_participant_count` of at least 1, and a `remediation_liability_cap_cents` of at least 0 — the board-approved ceiling on aggregate approved corrective-action liability for the year. A new plan year is written with `status` `OPEN`, with `open_violation_count`, `notified_violation_count`, `failing_parity_test_count` and `remediation_liability_cents` all at 0, and with `compliance_posture` computed immediately: an empty plan year under a `COOPERATIVE` administrator is `COMPLIANT`. Plan years can be read one at a time or listed, and the list can be narrowed by `administrator_id`, by lifecycle `status` and by `compliance_posture`.

**Compliance posture** is the plan year's summary verdict and the pivot on which most of the rest of this document turns. It is one of `COMPLIANT`, `AT_RISK` or `VIOLATION`, and it is derived — never supplied — from four inputs: `open_violation_count`, which counts the NQTL items of this plan year whose status is `VIOLATION`; `failing_parity_test_count`, which counts the parity tests still in status `COMPUTED` whose `basis` is `PLAN_PAYMENTS`, whose `result` is `FAIL`, and whose classification belongs to this plan year; the number of NQTL items of this plan year still sitting in status `INVENTORIED`; and the `cooperation_status` of the plan year's administrator. Superseded parity tests, advisory tests run on the `CLAIMS_COUNT` basis, and items that have reached `REMEDIATED` are all excluded from those counts. The verdict is an ordered ladder and the first matching clause wins:

1. If `open_violation_count` is at least 1, or `failing_parity_test_count` is at least 1, the posture is `VIOLATION`.
2. Otherwise, if the administrator's `cooperation_status` is `DELINQUENT` or `ESCALATED`, or at least one NQTL item is still `INVENTORIED`, the posture is `AT_RISK`.
3. Otherwise the posture is `COMPLIANT`.

The ladder is strictly ordered and must not be evaluated as a blend or a maximum over severities: an item in `VIOLATION` outranks a delinquent vendor even when both conditions hold at once, and the posture reported is `VIOLATION`. The posture is recomputed on every NQTL item status change, on every parity test creation or supersession, on every validated data submission, on every vendor-request fulfilment or breach declaration, on every corrective-action decision or closure, and on every advance of the logical clock.

Posture drives the plan year's own lifecycle, which the server moves on its own initiative — no client ever writes `status` on a plan year directly. From `OPEN`, a regulator opening a request for the year's analyses moves it to `UNDER_REGULATOR_REVIEW`, which freezes the plan-design surface as described in §2.7. From either `OPEN` or `UNDER_REGULATOR_REVIEW`, a recomputation that yields `VIOLATION` sets `compliance_posture` to `VIOLATION` and moves `status` to `REMEDIATION`. From `REMEDIATION`, a recomputation that yields something other than `VIOLATION` — which requires `open_violation_count` to be 0 and `failing_parity_test_count` to be 0 — sets `compliance_posture` to `COMPLIANT` or `AT_RISK` per the ladder above and returns `status` to `OPEN`. That loop is not one-shot: `OPEN` to `REMEDIATION` and back to `OPEN` is reachable more than once inside a single plan year. The one terminal move is from `UNDER_REGULATOR_REVIEW` to `CLOSED`, which happens when a regulator accepts the response while `compliance_posture` is `COMPLIANT`; after that, the plan year keeps recomputing its posture but never changes `status` again, and every child write against it is refused with `ERR_PLAN_YEAR_CLOSED`. Each of these plan-year moves refreshes `updated_at` and increments `version` by 1.

### 3.2. Describing the Plan: Benefit Classifications and Limitation Levels

Parity is tested inside a classification, never across classifications, so the sponsor's first substantive act is to split the plan's benefits into permitted categories. A `PlanSponsor` creates a benefit classification under a plan year — `plan_year_id` is taken from the path, not from the body — stating a `benefit_category` of `INPATIENT`, `OUTPATIENT`, `EMERGENCY_CARE` or `PRESCRIPTION_DRUGS`, a `network_tier` of `IN_NETWORK`, `OUT_OF_NETWORK` or `NOT_APPLICABLE`, an optional `sub_classification` of `NONE`, `OFFICE_VISITS` or `ALL_OTHER_OUTPATIENT` that defaults to `NONE`, the inclusive first and last dates of the claims measurement period the row covers as `measurement_period_start` and `measurement_period_end` (both written `YYYY-MM-DD`), and an optional `mh_su_benefits_covered` boolean that defaults to true and records whether mental-health and substance-use-disorder benefits are offered at all in this slice of the plan. Classifications may be read individually, and the classifications of one plan year may be listed with optional `benefit_category` and `network_tier` filters.

Three agreement rules bind those enumerations together, and they are checked in this order. First, network tiering applies exactly to the two categories that have a network: `network_tier` must be `NOT_APPLICABLE` when `benefit_category` is `EMERGENCY_CARE` or `PRESCRIPTION_DRUGS`, and must be either `IN_NETWORK` or `OUT_OF_NETWORK` for `INPATIENT` or `OUTPATIENT`. A row that gets this backwards — `NOT_APPLICABLE` on an inpatient or outpatient classification, or a real tier on emergency care or prescription drugs — is rejected with `ERR_NETWORK_TIER_MISMATCH` (HTTP 422). Second, the outpatient split is only meaningful for outpatient benefits: `sub_classification` may be `OFFICE_VISITS` or `ALL_OTHER_OUTPATIENT` only when `benefit_category` is `OUTPATIENT`, and must be `NONE` for every other category; otherwise the row is rejected with `ERR_SUB_CLASSIFICATION_MISMATCH` (HTTP 422). Third, the period must make sense on its own terms: `measurement_period_end` must be the same date as or a later date than `measurement_period_start`, and a reversed pair is rejected with `ERR_MEASUREMENT_PERIOD_INVALID` (HTTP 422). This single-row check runs before any comparison against other rows, so a row that is both internally reversed and colliding with a neighbour reports the reversal.

Measurement periods for the same slice of the plan must not collide, and the separation demanded here is deliberately generous. For a fixed combination of `plan_year_id`, `benefit_category`, `network_tier` and `sub_classification`, each existing row occupies the **closed** interval running from its `measurement_period_start` through its `measurement_period_end` inclusive, and a new row must additionally stand clear of that interval by at least one full day. Concretely, the new row is refused when its start date is on or before one day after an existing row's end date **and** its end date is on or after one day before that existing row's start date; the rejection is `ERR_MEASUREMENT_PERIOD_OVERLAP` (HTTP 409). Two periods that merely touch are refused, and two periods exactly one day apart are also refused; a two-day gap is accepted. Rows in a different category, a different tier, a different sub-classification or a different plan year never collide with each other.

Inside a classification, a `PlanSponsor` or an `Administrator` records the individual financial requirements and quantitative treatment limitations that the plan imposes. Each such row is created against a classification taken from the path, which becomes its `classification_id`, and states a `limitation_type` of `COPAY`, `COINSURANCE`, `DEDUCTIBLE`, `OUT_OF_POCKET_MAX`, `DAY_LIMIT` or `VISIT_LIMIT`; a `benefit_side` of either `MEDICAL_SURGICAL` — the baseline the parity test measures against — or `MENTAL_HEALTH_SUD` — the side under test; a `level_value` of at least 0, being the level of the requirement, whether that is a dollar copay, a coinsurance fraction or a day or visit count; a `projected_plan_payments_cents` of at least 0, being the plan payments in cents expected for the benefits subject to that level during the measurement period; and a `projected_claims_count` of at least 0, being the number of claims expected for the same benefits. A `level_value` of 0 is meaningful rather than empty: it records the slice of benefits on which the requirement is not imposed at all.

Limitation rows are versioned by supersession rather than edited. Every row is written with `status` `ACTIVE`, and the `ACTIVE` rows of a classification form the population that the quantitative tests read. When a new row arrives carrying the same `classification_id`, `limitation_type`, `benefit_side` **and** `level_value` as an existing `ACTIVE` row, that existing row moves `ACTIVE` to `SUPERSEDED`, has its `updated_at` refreshed and its `version` incremented by 1, and is excluded from every calculation input set from that moment on. Two rows that differ in any one of those four attributes coexist as `ACTIVE`, and `level_value` is compared numerically for this purpose, so a level written `20` and a level written `20.0` are the same level. Recording a limitation level re-stamps nothing beyond the superseded row itself: the classification is not touched, the plan year's counters and `compliance_posture` are not recomputed, and no parity test is re-run. A test computed before the supersession keeps exactly the numbers it computed and stays in `COMPUTED`; only a freshly created test reads the new `ACTIVE` population. Limitation rows may be listed per classification with optional `limitation_type`, `benefit_side` and `status` filters. Both classification creation and limitation-level creation are plan-design writes and therefore require the owning plan year to be exactly `OPEN`.

### 3.3. Quantitative Testing: the Substantially-All and Predominant Standards

A quantitative parity test is run on one classification, for one `limitation_type`, under one weighting `basis`. Either a `PlanSponsor` or a `ComplianceOfficer` may run it; the classification comes from the path and becomes the test's `classification_id`, and the payload names only the `limitation_type` under test and the `basis`, which is either `PLAN_PAYMENTS` or `CLAIMS_COUNT`. The two bases are the same algorithm weighted by different quantities: under `PLAN_PAYMENTS` each limitation row contributes its `projected_plan_payments_cents`, and under `CLAIMS_COUNT` it contributes its `projected_claims_count`. Running a test writes a new record rather than editing an old one, so the history of every test ever run is retained; the tests of one classification are listed with optional `limitation_type`, `basis` and `status` filters, and that list is the only way to read a test — no endpoint addresses a single parity test by its own identifier.

**Step one — the substantially-all standard.** The test population is drawn only from the medical/surgical baseline: every treatment-limitation row whose `classification_id` is the classification in the path, whose `status` is `ACTIVE`, whose `benefit_side` is `MEDICAL_SURGICAL` and whose `limitation_type` matches the requested type. Superseded rows are excluded, and `MENTAL_HEALTH_SUD` rows never enter either sum. The denominator, called the total weight, is the sum of the basis's weight field over every row in that population. The numerator, called the subject weight, is the same sum restricted to rows whose `level_value` is greater than 0 — the benefits on which the requirement is actually imposed. Regardless of which basis was requested, `total_ms_payments_cents` and `subject_payments_cents` always report the `projected_plan_payments_cents` sums, so that the two variants of one classification stay comparable on the record.

The requirement satisfies the substantially-all standard when the subject weight is at least two-thirds of the total weight. That comparison is made by integer cross-multiplication and never by division: `substantially_all_met` is true exactly when the subject weight multiplied by 3 is greater than or equal to the total weight multiplied by 2. Separately, and for the record only, `substantially_all_ratio` reports the subject weight divided by the total weight, rounded half up to six decimal places. The rounded ratio must never be used for the threshold decision — a ratio that rounds up to 0.666667 can still fail the two-thirds standard, and only the cross-multiplication gets the boundary right. When the total weight under the requested basis is 0 there is nothing to test and no ratio to compute, and the request is rejected with `ERR_EMPTY_TEST_POPULATION` (HTTP 422) rather than dividing by zero; at least one `ACTIVE` `MEDICAL_SURGICAL` row of the requested `limitation_type` must carry a positive weight under the requested basis.

**Step two — the predominant level.** This step runs only when `substantially_all_met` is true; when it is false, `predominant_level` is null and the step is skipped entirely. The input set narrows to the same `ACTIVE` `MEDICAL_SURGICAL` rows of the requested `limitation_type` that carry a `level_value` greater than 0 — the benefits actually subject to the limitation. The denominator for this step is the sum of the basis's weight field over that narrowed set. Rows that share a `level_value` are merged into a single level, carrying the summed weight, before anything else happens; that merge is what keeps `created_at` from influencing the outcome.

The predominant level is then found in two branches, in this order. The single-level branch fires when some level's merged weight, multiplied by 2, is strictly greater than the denominator — that is, when one level alone covers more than one half of the subject benefits. `predominant_level` is that level's `level_value`. Strictness matters: a level sitting at exactly one half does not qualify, and because more than one half can only be claimed once, at most one level can satisfy this branch and no ordering is needed. If no level qualifies alone, the combination branch runs: walk the distinct levels in descending `level_value` order, most restrictive first, since a higher `level_value` is the more restrictive requirement; keep a running cumulative weight as each level is added; and stop at the first level at which the cumulative weight multiplied by 2 becomes strictly greater than the denominator. `predominant_level` is the `level_value` of that last-added level — the least restrictive level inside the combination that together covers more than one half. The descending order is pinned; walking ascending returns a different level and is forbidden. `predominant_level` is reported exactly as the stored `level_value`, with no rounding.

**Step three — the MH/SUD level and the verdict.** The level actually imposed on mental-health and substance-use-disorder benefits is selected from the treatment-limitation rows of the same classification whose `status` is `ACTIVE`, whose `benefit_side` is `MENTAL_HEALTH_SUD`, whose `limitation_type` matches, and whose `level_value` is greater than 0. Those rows are ranked by `level_value` descending — the most restrictive requirement actually imposed — with `created_at` ascending as the deterministic tie-break, and the first row is taken. `mh_level_value` is that row's `level_value`, or null when the set is empty. The `result` then follows a fixed four-step ladder: if `substantially_all_met` is false the result is `NOT_APPLICABLE`, because the limitation may not be applied to MH/SUD benefits at all and no predominant level exists to compare against; otherwise, if `mh_level_value` is null the result is again `NOT_APPLICABLE`, because nothing is imposed on the MH/SUD side; otherwise, if `mh_level_value` is strictly greater than `predominant_level` the result is `FAIL`; otherwise the result is `PASS`.

Only plan-payment-weighted tests carry compliance weight. `advisory_only` is true exactly when `basis` is `CLAIMS_COUNT`, and an advisory test never feeds `failing_parity_test_count`; the same classification can therefore hold a `PASS` on the `PLAN_PAYMENTS` basis and a `FAIL` on the `CLAIMS_COUNT` basis without the plan year's posture moving at all. Because the two bases can take different branches of the predominant algorithm, that divergence is expected rather than anomalous.

Each new test is written with `status` `COMPUTED`. When a test already exists in status `COMPUTED` for the same `classification_id`, `limitation_type` and `basis`, that earlier test moves `COMPUTED` to `SUPERSEDED` and has its `version` incremented by 1 — and because a superseded failure stops counting, the plan year's `failing_parity_test_count` is recomputed and `compliance_posture` re-derived, with the plan year's `version` incremented whenever the posture or the count actually changes. That recomputation runs on every test creation, not only on the ones that supersede something, so the very first `FAIL` on the `PLAN_PAYMENTS` basis is what drives an otherwise clean plan year into `VIOLATION` and on into `REMEDIATION`; supersession is evaluated after the arithmetic, so a create that is refused with `ERR_EMPTY_TEST_POPULATION` leaves the earlier test standing in `COMPUTED`. A plan year that had been pushed into `VIOLATION` solely by a failing plan-payments test can therefore be brought back out of it by re-running that test against corrected limitation levels.

### 3.4. The NQTL Inventory and Its Comparative Analyses

Nonquantitative limitations are the harder half of parity, and they are handled as an inventory. A `PlanSponsor` or a `ComplianceOfficer` inventories one limitation at a time, naming the `plan_year_id` whose inventory it joins, the `classification_id` in which the limitation is applied, an `nqtl_type` of `PRIOR_AUTHORIZATION`, `NETWORK_ADMISSION`, `REIMBURSEMENT_RATE`, `MEDICAL_NECESSITY_CRITERIA`, `CONCURRENT_REVIEW` or `STEP_THERAPY`, an `applied_to` of `MENTAL_HEALTH_SUD_ONLY`, `MEDICAL_SURGICAL_ONLY` or `BOTH` recording which benefit side the limitation is applied to as written, and a `description` of 1 to 400 characters giving the plain-language wording from the plan documents. The named classification must belong to the named plan year; a payload that pairs a classification from one plan year with another plan year's identifier is rejected with `ERR_CROSS_PLAN_YEAR_REFERENCE` (HTTP 409). The classification must also actually offer the benefits being protected: when its `mh_su_benefits_covered` is false, inventorying an NQTL there is rejected with `ERR_MH_BENEFITS_NOT_COVERED` (HTTP 409). And the inventory holds one live row per limitation: when an NQTL item whose `status` is anything other than `REMEDIATED` already exists for the same `plan_year_id`, `classification_id` and `nqtl_type`, the create is rejected with `ERR_DUPLICATE_NQTL_ITEM` (HTTP 409) — a remediated item does not block re-inventorying the same limitation later.

A new item is written with `status` `INVENTORIED`, and its `stringency_in_operation_index` is computed straight away from whatever as-applied evidence already exists for its classification, which for a fresh classification means 0.00 — and where validated evidence already exists the item is returned carrying a non-zero index, and possibly a true `stringency_flag`, on the spot, still with `version` 1, because that first computation is part of writing the row. Because an item sitting in `INVENTORIED` is an un-analysed limitation, its arrival forces the plan year's posture to at least `AT_RISK` through the ladder in §3.1. Items may be read one at a time — the read is also how a client obtains the `version` value it must later pass as `expected_nqtl_item_version` — and listed with optional `plan_year_id`, `classification_id`, `nqtl_type` and `status` filters. The item's lifecycle runs `INVENTORIED` to `ANALYSIS_DRAFTED` to `ANALYSIS_SUBMITTED`, then to either `COMPLIANT` or `VIOLATION`, and finally, for a violation that has been remedied, to the terminal `REMEDIATED`.

A **comparative analysis** is the document that justifies one NQTL. Either a `PlanSponsor` or an `Administrator` drafts it, naming the `nqtl_item_id` it documents, the `factor_count` — how many factors were documented, such as excessive utilisation, provider supply or claim-type mix, at least 0 — the `evidentiary_standard_count` — how many evidentiary standards were relied upon for those factors, at least 0 — a `stringency_written_finding` and a `stringency_operation_finding`, each one of `COMPARABLE`, `MORE_STRINGENT_MH` or `MORE_STRINGENT_MS`, being the comparative finding for the limitation as written and the comparative finding for the limitation in operation respectively, and the mandatory `expected_nqtl_item_version` described in §2.10. The payload may also carry `supersedes_analysis_id`, pointing at an earlier analysis for the same NQTL that this one replaces; it is absent or null on a first analysis. The row is written with `status` `DRAFT`, `revision_round` 0, and `authored_by_user_id` stamped from the acting `X-User-ID`. Creating an analysis moves the owning item `INVENTORIED` to `ANALYSIS_DRAFTED`, increments the item's `version` by 1, recomputes the item's stringency index, and recomputes the plan year's posture — an item leaving `INVENTORIED` can clear an `AT_RISK` that existed only because of it. The item's `version` increment is unconditional and does not depend on its status having moved: `INVENTORIED` is the only status the create cascade advances on its own initiative, apart from the superseded-`SUBMITTED` leg described next, so an item already in `ANALYSIS_DRAFTED`, `ANALYSIS_SUBMITTED`, `COMPLIANT`, `VIOLATION` or `REMEDIATED` keeps the status it had and is re-stamped anyway. The newly written `DRAFT` is itself the analysis that recomputed index reads, because from the instant it is written it is the item's most recent non-`WITHDRAWN` analysis; its `factor_count` and `evidentiary_standard_count` therefore begin earning the documentation credit of §3.7 while the analysis is still an unsubmitted draft.

Supersession is how a bad draft is replaced. When `supersedes_analysis_id` is supplied it must name an analysis for the same `nqtl_item_id`; pointing at an analysis belonging to a different item is rejected with `ERR_CROSS_PLAN_YEAR_REFERENCE`. The named analysis must also still be supersedable — its `status` must be `DRAFT`, `SUBMITTED` or `INSUFFICIENT` — and a `CERTIFIED` or already `WITHDRAWN` analysis cannot be superseded, which is refused with `ERR_ANALYSIS_ALREADY_SUPERSEDED` (HTTP 409). A successful supersession moves the named row from whichever of `DRAFT`, `SUBMITTED` or `INSUFFICIENT` it occupied to `WITHDRAWN`, increments that row's `version` by 1, and removes it from the latest-analysis selector. The three legs are otherwise identical, with one extra consequence on the `SUBMITTED` leg: because the item had already advanced to `ANALYSIS_SUBMITTED` behind that analysis, the creation cascade resets the owning item to `ANALYSIS_DRAFTED`. That reset requires both conditions to hold at once — the superseded row must have been in `SUBMITTED` and the item must still be standing in `ANALYSIS_SUBMITTED` — so superseding a submitted analysis on an item that has since been determined `COMPLIANT` or `VIOLATION`, or remediated, leaves the item's status alone and only re-stamps it. Analyses may be read individually and listed with optional `nqtl_item_id`, `supersedes_analysis_id` and `status` filters, so the supersession chain is fully traversable.

**Submission** is performed by a `PlanSponsor` or an `Administrator` and moves the analysis `DRAFT` to `SUBMITTED`. It requires the analysis to be in `DRAFT` — anything else is refused with `ERR_ANALYSIS_NOT_DRAFT` (HTTP 409) — and the owning plan year not to be `CLOSED`. The owning item's status is deliberately *not* a precondition and is never checked: the analysis's own `DRAFT` status is the whole state gate. It also requires the documentation to be minimally complete: `factor_count` must be at least 2 and `evidentiary_standard_count` at least 1, and an analysis short of either is refused with `ERR_INSUFFICIENT_COMPARATIVE_ANALYSIS` (HTTP 422). A successful submission sets the owning item's `status` to `ANALYSIS_SUBMITTED` from whatever status it held — normally `ANALYSIS_DRAFTED`, but an item that had already reached `COMPLIANT`, `VIOLATION` or `REMEDIATED` behind an earlier analysis is pulled back to `ANALYSIS_SUBMITTED` just the same — increments the item's `version` by 1, recomputes the item's stringency index, recomputes the plan year's posture, and increments the analysis's own `version` by 1.

**Review** is exclusive to a `ComplianceOfficer`, applies only to an analysis in `SUBMITTED` — anything else is refused with `ERR_ANALYSIS_NOT_SUBMITTED` (HTTP 409) — and takes an `outcome` of either `CERTIFIED` or `INSUFFICIENT` plus an optional `review_note`. Both branches enforce the self-review prohibition of §2.9 and both increment the analysis's `version` by 1, but they diverge in what else they require and cause. The certifying branch moves `SUBMITTED` to `CERTIFIED`, stamps `certified_by_user_id` from the acting `X-User-ID`, leaves the owning item's status untouched, and additionally requires as-applied evidence to exist: at least one data submission in status `VALIDATED` with `submission_type` `DENIAL_RATES` must exist for the owning item's `classification_id`, because an analysis may not be certified on paper alone. Absent such evidence the request is refused with `ERR_IN_OPERATION_DATA_MISSING` (HTTP 409), and a `REJECTED` submission does not satisfy the rule. Certification also has a downstream effect: from that moment the owning item counts as covered at the next regulator response. The insufficient branch moves `SUBMITTED` to `INSUFFICIENT`, imposes no evidence requirement at all, and moves the owning item back from `ANALYSIS_SUBMITTED` to `ANALYSIS_DRAFTED`, incrementing the item's `version` by 1, so that the author can revise; that reset is conditional on the item actually standing in `ANALYSIS_SUBMITTED`, whereas the item's `version` increment is not — an item that had moved on to `COMPLIANT`, `VIOLATION` or `REMEDIATED` keeps that status and is re-stamped anyway. Either branch recomputes the owning item's stringency index and `stringency_flag`, but only the insufficient branch also recomputes the plan year's counters and `compliance_posture`. Certification, by contrast, touches nothing beyond the analysis row unless the recomputation actually moves the index or the flag: because certifying changes neither the item's as-applied evidence nor the counts on its latest analysis, the recomputed index is normally identical to the stored one and the item's `updated_at` and `version` are left exactly where they were.

**Reopening** closes the revision cycle. A `PlanSponsor` or an `Administrator` reopens an analysis that is in `INSUFFICIENT` — anything else is refused with `ERR_ANALYSIS_NOT_INSUFFICIENT` (HTTP 409) — which moves it back to `DRAFT` and increments both `revision_round` and `version` by 1. The loop `DRAFT` to `SUBMITTED` to `INSUFFICIENT` to `DRAFT` is therefore traversable repeatedly, but it is bounded: `revision_round` must be strictly less than 3 for a reopen to be accepted, so the fourth reopen of the same analysis is refused with `ERR_REVISION_LIMIT_REACHED` (HTTP 409). At that point the only way forward is a fresh analysis that supersedes the exhausted one. `CERTIFIED` and `WITHDRAWN` are the two terminal states for an analysis.

### 3.5. Vendor Production: Requests, Deadlines and Escalation

The sponsor cannot analyse what it cannot see, so the contractual production obligation is modelled explicitly. A `PlanSponsor` issues a production request to a TPA, naming the `administrator_id` obligated to produce the material, the `plan_year_id` the request is scoped to, an optional `nqtl_item_id` when the material relates to one specific limitation (left null for plan-wide data pulls), a `requested_item_count` between 1 and 10 inclusive stating how many validated submissions must arrive before the request is satisfied, and a `requested_submission_types` array naming which kinds of material the TPA must produce. That array must be non-empty, free of duplicates, and drawn from `DENIAL_RATES`, `NETWORK_COMPOSITION` and `REIMBURSEMENT_BENCHMARK`. When `nqtl_item_id` is supplied, the item it names must belong to the request's `plan_year_id`; a mismatch is rejected with `ERR_CROSS_PLAN_YEAR_REFERENCE`.

Issuance stamps `issued_at` from the logical clock and derives two deadlines from it, once, at issuance, never to be re-derived afterwards. The contractual deadline, `due_at`, is `issued_at` advanced by the administrator's `contractual_production_days` calendar days — so a TPA registered with the default terms gets 45 days. The regulatory deadline, `regulatory_due_at`, is `issued_at` advanced by a fixed 30 calendar days regardless of what the contract says, because a regulator is not bound by the sponsor's contract. Where the two disagree, both are reported and both are scored, but only one of them has contractual force. A new request begins with `fulfillment_status` `OPEN`, `escalation_status` `NONE` and `validated_submission_count` 0; it increments the administrator's `outstanding_request_count` and triggers a recomputation of the cooperation scores. The derived `is_overdue` flag on a request is true exactly when the logical clock now stands strictly later than `due_at` and `fulfillment_status` is not yet `FULFILLED`. Requests can be read individually — the read shows both status dimensions and both deadlines — and listed with optional `administrator_id`, `plan_year_id`, `nqtl_item_id`, `fulfillment_status` and `escalation_status` filters.

Overlapping production windows against the same TPA for the same plan year are refused, and the interval convention here is deliberately the opposite of the measurement-period rule in §3.2. A live request — one whose `fulfillment_status` is `OPEN` or `PARTIAL` — occupies the **half-open** window that begins at its `issued_at` and runs up to but does not include its `due_at`, with no buffer of any kind. For a fixed `administrator_id` and `plan_year_id`, a new request is refused with `ERR_PRODUCTION_WINDOW_OVERLAP` (HTTP 409) when the new window's `issued_at` falls strictly before an existing live window's `due_at` **and** that existing window's `issued_at` falls strictly before the new window's `due_at`. A request issued at exactly the instant a previous window's `due_at` falls is therefore accepted — back-to-back production windows are legitimate — and a request whose predecessor has already reached `FULFILLED` never collides at all.

A production request carries **two independent status dimensions**, and this is central to how it behaves. `fulfillment_status` tracks production and advances only on validated submissions; `escalation_status` tracks contract enforcement and advances only when the sponsor escalates. Neither dimension touches the other. A request that has had a breach declared is still recorded with whatever `fulfillment_status` it had reached, and a request under a notice can still be produced against and fulfilled normally. The fully terminal combination is a `FULFILLED` request against which a breach was declared.

**Escalation** is a `PlanSponsor` capability with two rungs, and both require the request to still be live: escalating a request whose `fulfillment_status` is `FULFILLED` is refused with `ERR_REQUEST_ALREADY_FULFILLED` (HTTP 409), and escalating one whose `escalation_status` has already reached `BREACH_DECLARED` is refused with `ERR_ESCALATION_ALREADY_DECLARED` (HTTP 409). Of those two the declared breach is examined first, so escalating the fully terminal combination described above — a `FULFILLED` request against which a breach was already declared — reports `ERR_ESCALATION_ALREADY_DECLARED`. The first rung moves `escalation_status` from `NONE` to `NOTICE_SENT` and requires the logical clock to stand strictly later than `due_at`. The second rung moves `NOTICE_SENT` to `BREACH_DECLARED` and requires the clock to stand strictly later than `due_at` advanced by a grace period of seven calendar days. Strictness applies on both rungs — a clock standing exactly at `due_at`, or exactly at the end of the grace period, is not yet overdue — and a premature escalation is refused with `ERR_NOT_YET_OVERDUE` (HTTP 409). The first rung's only effect is to increment the request's own `version` by 1.

Declaring a breach, by contrast, sets off a three-hop cascade. First, the request's `escalation_status` becomes `BREACH_DECLARED` and its `version` increments by 1. Second, the administrator's `breach_count` is incremented, both `cooperation_score` and `regulatory_basis_cooperation_score` are recomputed, `cooperation_status` is re-derived, and the administrator's `version` increments by 1. Third — because `cooperation_status` has now fallen to `DELINQUENT` or `ESCALATED` — the compliance posture of **every** plan year whose `administrator_id` is this administrator is recomputed, which by the second rung of the posture ladder yields `AT_RISK` for each plan year that has no violation of its own, and each such plan year's `version` increments by 1 on the conditional rule of §2.8 — a plan year the recomputation leaves untouched, because it already stood in `VIOLATION` on its own account or was already `AT_RISK` behind an earlier breach, keeps its `updated_at` and `version` exactly as they were. A vendor breach therefore reaches plan years the escalated request was never scoped to. From that point the production window is shut: any further data submission against that request is refused with `ERR_PRODUCTION_WINDOW_CLOSED` (HTTP 409).

**Vendor cooperation** is scored twice from the same shape of arithmetic, on two different deadlines. The input set for both is every production request whose `administrator_id` is this administrator. A request counts as late only while it is still live — that is, while its `fulfillment_status` is `OPEN` or `PARTIAL` — and only when the logical clock stands strictly later than the relevant deadline; a request that was eventually produced in full stops being late even if it was produced after its deadline. On the contractual basis the deadline is `due_at`, and the resulting late tally is published as `late_request_count`. On the regulatory basis the deadline is `regulatory_due_at`, and that tally is published as `regulator_reportable_late_count`. Breaches count on both bases: `breach_count` is the number of this administrator's requests whose `escalation_status` is `BREACH_DECLARED`, counted regardless of fulfilment. `outstanding_request_count`, meanwhile, is simply the number of this administrator's requests whose `fulfillment_status` is `OPEN` or `PARTIAL`.

Each score starts from a perfect 100, subtracts 15 points for every late request on that basis, subtracts 25 points for every declared breach, and is floored at 0 before rounding, so the score never goes negative however many breaches accumulate; the result is then rounded half up to two decimal places and can never exceed 100.00. The contractual result is published as `cooperation_score`; the regulatory result is published as `regulatory_basis_cooperation_score`, is reported to the regulator, and never drives anything else. `cooperation_status` is derived from `cooperation_score` alone: `COOPERATIVE` when the score is at least 80, `DELINQUENT` when the score is at least 50 but below 80, and `ESCALATED` when the score is below 50. Consider a TPA registered on the default 45-day terms with two requests issued on the same day and both still `OPEN`, with the clock advanced 40 days past issuance: nothing is late on the contractual basis, so `cooperation_score` stands at 100.00 and `cooperation_status` is `COOPERATIVE`, while both requests are already past the 30-day regulatory deadline, so `regulatory_basis_cooperation_score` reads 70.00. One late request plus one declared breach gives 60.00 and `DELINQUENT`; three late requests plus one declared breach gives 30.00 and `ESCALATED`. Both scores and all four counters are recomputed at request issuance, at every escalation, on the validated submission that fulfils a request, and on every advance of the logical clock.

### 3.6. As-Applied Evidence: Data Submissions and Automatic Validation

Producing material against an open production window is the `Administrator`'s exclusive capability. The request comes from the path and becomes the submission's `vendor_request_id`; the payload names the `classification_id` the data describes and a `submission_type` of `DENIAL_RATES`, `NETWORK_COMPOSITION` or `REIMBURSEMENT_BENCHMARK`. The type must be one the sponsor actually asked for: a `submission_type` absent from the owning request's `requested_submission_types` is refused with `ERR_SUBMISSION_TYPE_NOT_REQUESTED` (HTTP 422). The classification must belong to the owning request's `plan_year_id`, or the submission is refused with `ERR_CROSS_PLAN_YEAR_REFERENCE`. A submission against a request that has already reached `FULFILLED` is refused with `ERR_REQUEST_ALREADY_FULFILLED`, and one against a request whose `escalation_status` is `BREACH_DECLARED` is refused with `ERR_PRODUCTION_WINDOW_CLOSED`. Here the precedence runs the opposite way round from escalation: fulfilment is examined first, so producing against a request that is both `FULFILLED` and in `BREACH_DECLARED` reports `ERR_REQUEST_ALREADY_FULFILLED`.

The rest of the payload carries the numbers, all optional and all defaulting where the type does not need them. Denial-rate material supplies four integer counters for the measurement period: `mh_denials`, the mental-health and substance-use-disorder adverse benefit determinations; `mh_adjudicated_claims`, the MH/SUD claims adjudicated; `ms_denials`, the medical/surgical adverse benefit determinations; and `ms_adjudicated_claims`, the medical/surgical claims adjudicated. Each defaults to 0 and none may be negative. Denials cannot exceed the claims they are drawn from: `mh_denials` must be at most `mh_adjudicated_claims`, and `ms_denials` at most `ms_adjudicated_claims`, or the submission is refused with `ERR_DENIALS_EXCEED_CLAIMS` (HTTP 422). That comparison is not scoped to the denial-rate type: the four counters are checked against each other on every submission whatever its `submission_type`, so a network-composition or reimbursement-benchmark payload that carries more denials than claims is refused the same way. Network-composition material supplies `mh_in_network_provider_pct` and `ms_in_network_provider_pct`, each either null or a value from 0.0 through 1.0 inclusive, being the share of MH/SUD providers and of medical/surgical providers in the service area that were admitted to the network. Reimbursement-benchmark material may carry a `benchmark_note`, either null or free text of 1 to 200 characters referencing the benchmark relied upon.

Every submission is validated automatically inside the same request that creates it, moving from `RECEIVED` to either `VALIDATED` or `REJECTED` before the response is written; there is no separate validation step and no submission stays in `RECEIVED`. A denial-rate submission validates when `mh_adjudicated_claims` is at least 1, `ms_adjudicated_claims` is at least 1 and `ms_denials` is at least 1 — the comparator side must have denied something, or the disparity has no denominator. A network-composition submission validates when both provider-percentage fields are non-null. A reimbursement-benchmark submission always validates. Otherwise the submission is written as `REJECTED` with a `rejection_reason` that says which gate it failed: `ZERO_ADJUDICATED_CLAIMS` when a denial-rate submission carries `mh_adjudicated_claims` of 0 or `ms_adjudicated_claims` of 0, `ZERO_COMPARATOR_DENIALS` when the claim counts are both positive but `ms_denials` is 0, and `MISSING_NETWORK_PCT` when a network-composition submission leaves either percentage null. A validated submission carries `rejection_reason` `NONE`, which is also the field's default. A rejected submission is still persisted, because the TPA's production attempt belongs on the record, but it leaves every computed rate, ratio and gap null, and it advances neither `validated_submission_count` nor `fulfillment_status`. A rejection sets off no cascade whatsoever: the owning request, the administrator, the NQTL items of the submission's classification and the plan year are all left with their `updated_at` and `version` exactly where they stood. Submissions may be read individually and listed with optional `vendor_request_id`, `classification_id`, `submission_type` and `status` filters.

**Denial-rate scoring** runs on every validated denial-rate submission and is scored entirely from that one submission's own four counters; no other submission contributes. The raw MH/SUD rate is `mh_denials` divided by `mh_adjudicated_claims`, and the raw medical/surgical rate is `ms_denials` divided by `ms_adjudicated_claims`. Both raw rates are published for the record, rounded half up to six decimal places, as `mh_denial_rate` and `ms_denial_rate`. The `disparity_ratio` is then the raw MH/SUD rate divided by the raw medical/surgical rate, rounded half up to four decimal places. The rounding order is pinned and consequential: the ratio is taken from the two **unrounded** quotients and rounded exactly once, at the end, to four places. Dividing the two already-rounded six-place rates is forbidden and produces a different fourth decimal — 263 MH/SUD denials out of 3,491 claims against 71 medical/surgical denials out of 1,913 claims publish rates of 0.075337 and 0.037114, and the correct ratio is 2.0298, where the forbidden order yields 2.0299. `as_applied_flag` is then true exactly when `disparity_ratio` is not null and stands at or above 2.0: the same counters at 137 out of 1,919 against 71 out of 1,913 give 1.9235 and a false flag, 200 out of 1,000 against 100 out of 1,000 give exactly 2.0000 and a true flag because the threshold is inclusive, and 1,999 out of 10,000 against 1,000 out of 10,000 give 1.9990 and a false flag. Division by zero cannot arise, because a submission with a zero denominator, or with no comparator denials, has already been rejected before this scoring runs. `mh_denial_rate`, `ms_denial_rate` and `disparity_ratio` are null on any submission that is not both `VALIDATED` and of type `DENIAL_RATES`.

**Network-composition scoring** is simpler: `network_composition_gap` is `ms_in_network_provider_pct` minus `mh_in_network_provider_pct`, rounded half up to four decimal places, and is null on any submission that is not both `VALIDATED` and of type `NETWORK_COMPOSITION`. A positive gap means a larger share of medical/surgical providers than of MH/SUD providers was admitted to the network, which is the direction that indicates a parity problem.

A validated submission also drives the fulfilment dimension and a cascade beyond it. `validated_submission_count` — the count of this request's submissions in status `VALIDATED` — is incremented, and the request's `version` increments by 1. While the incremented count remains below `requested_item_count`, `fulfillment_status` advances from `OPEN` to `PARTIAL`, and `escalation_status` is untouched; a request already in `PARTIAL` stays there. When the arriving submission is the one that brings the count up to exactly `requested_item_count`, `fulfillment_status` moves from `OPEN` or `PARTIAL` to `FULFILLED`, and that fulfilment is what closes the obligation: the administrator's `outstanding_request_count` is decremented by exactly 1, and `late_request_count`, `regulator_reportable_late_count`, both cooperation-score variants and `cooperation_status` are all recomputed. Neither rung of fulfilment is available once `escalation_status` has reached `BREACH_DECLARED`. Every validated submission additionally recomputes the stringency-in-operation index of every NQTL item whose `classification_id` matches this submission's, incrementing each such item's `version` by 1, and recomputes the owning plan year's `compliance_posture`.

### 3.7. Stringency in Operation and the Parity Determination

Written comparability is not enough; parity has to hold in operation. The **stringency-in-operation index** is the single number that summarises how an NQTL is behaving in practice, and it is what a compliance officer's determination must agree with. It is published on every NQTL item as `stringency_in_operation_index`, a value from 0.00 through 10.00 inclusive carried to two decimal places, and it reads 0.00 before any evidence exists. Alongside it, `stringency_flag` is true exactly when the index stands at or above 5.0.

The index draws on three inputs, all scoped to the item. The denial-rate evidence term, referred to below as the disparity input, is the largest `disparity_ratio` found among data submissions whose `status` is `VALIDATED`, whose `submission_type` is `DENIAL_RATES` and whose `classification_id` matches the item's `classification_id`; when that set is empty the disparity input is 0. The network evidence term, the network-gap input, is the largest `network_composition_gap` found among submissions whose `status` is `VALIDATED`, whose `submission_type` is `NETWORK_COMPOSITION` and whose `classification_id` matches; when that set is empty it is 0. Submissions in `RECEIVED` or `REJECTED` are excluded from both. The documentation credit comes from a single analysis: the most recent comparative analysis for this `nqtl_item_id` whose `status` is not `WITHDRAWN`, ranked by `created_at` descending, then by `version` descending, and finally — because a millisecond-resolution stamp lets two analyses of one item share a `created_at` — by the order in which the server wrote them, the later write ranking first, contributing its `factor_count` and its `evidentiary_standard_count`; when no such analysis exists both counts are treated as 0. Status plays no part in that ranking beyond the exclusion of `WITHDRAWN`: a `DRAFT`, `SUBMITTED` or `INSUFFICIENT` analysis earns the documentation credit exactly as a `CERTIFIED` one does, and a newer draft displaces an older certified analysis as the credit's source.

The two evidence weights depend on what kind of limitation is being measured. Utilisation-management limitations — `PRIOR_AUTHORIZATION`, `MEDICAL_NECESSITY_CRITERIA`, `CONCURRENT_REVIEW` and `STEP_THERAPY` — weight the disparity input at 0.6 and the network-gap input at 0.4, because denial behaviour is the primary signal for them. Network-facing limitations — `NETWORK_ADMISSION` and `REIMBURSEMENT_RATE` — reverse the emphasis, weighting the disparity input at 0.3 and the network-gap input at 0.7.

The computation proceeds in six pinned steps, and every one of them matters.

1. Weight and sum the two evidence terms into a base. The disparity input contributes the greater of 0 and the disparity input minus 1, multiplied by its weight — a disparity ratio of 1 means the two sides deny at identical rates and therefore contributes nothing, and a ratio below 1 (the MH/SUD side denying less often) also contributes nothing rather than a credit. The network-gap input contributes the greater of 0 and the network-gap input itself, multiplied by its weight, so a negative gap likewise contributes nothing.
2. If the item's `applied_to` is `MENTAL_HEALTH_SUD_ONLY`, multiply the summed base by 1.5. A limitation imposed on the MH/SUD side alone is inherently more suspect. The multiplier is applied to the summed base, never to the individual weighted terms.
3. Compute the documentation credit as the smaller of 0.25 and the sum of 0.05 for each documented factor plus 0.03 for each evidentiary standard. The cap is applied here, before the credit is scaled.
4. Scale both the base and the capped credit by 10, and subtract the scaled credit from the scaled base.
5. Clamp the result into the range 0 through 10 inclusive — after the subtraction, never before it.
6. Round the clamped result half up to two decimal places, once. Intermediate terms keep full decimal precision throughout.

Two shortcuts produce different numbers and are both wrong: clamping before subtracting the credit, and subtracting an uncapped credit. A worked case makes the difference concrete. Take a `PRIOR_AUTHORIZATION` item, `applied_to` `MENTAL_HEALTH_SUD_ONLY`, with a disparity input of 2.0298, a network-gap input of 0.2800, and a latest analysis documenting 4 factors and 5 evidentiary standards. The base is 0.6 multiplied by 1.0298 plus 0.4 multiplied by 0.2800, which is 0.61788 plus 0.112, or 0.72988. The asymmetry multiplier takes it to 1.09482, and scaling by 10 gives 10.9482. The credit is the smaller of 0.25 and 0.35, so 0.25, and scaling by 10 gives 2.5. Subtracting gives 8.4482, which is already inside the range, and rounding gives an index of 8.45 and a true `stringency_flag`. Clamping first would have given 10.00 minus 2.5, or 7.50; leaving the credit uncapped would have given 7.45. For contrast, a `NETWORK_ADMISSION` item with `applied_to` `BOTH`, a disparity input of 1.9235, no network submission at all, and a latest analysis documenting 2 factors and 1 evidentiary standard has a base of 0.3 multiplied by 0.9235, or 0.27705, scaling to 2.7705, against a credit of 0.13 scaling to 1.3 — an index of 1.47 and a false flag.

The index is recomputed at five points: when a comparative analysis is created, when one is submitted, when one is reviewed on either outcome, when a data submission for the item's classification reaches `VALIDATED`, and immediately before every determination check. Those five are besides the first computation performed while the item itself is being inventoried, and they are exhaustive: nothing else re-derives the index. In particular reopening an insufficient analysis does not, a rejected data submission does not, and advancing the logical clock does not — the clock sweep of §2.5 re-derives vendor deadlines, cooperation scores and plan-year postures and leaves every NQTL item's index and `stringency_flag` exactly as they stood.

**Recording the determination** is exclusive to a `ComplianceOfficer`. The payload carries an `outcome` of either `COMPLIANT` or `VIOLATION`, a `rationale` explaining the decision, and the mandatory `expected_plan_year_version` of §2.10. Only two starting states admit a determination: an item in `ANALYSIS_SUBMITTED` and an item already in `COMPLIANT`. Both outcomes are available from both of those states. The `COMPLIANT` starting state exists chiefly so that an item can be re-determined to `VIOLATION` when fresh as-applied evidence arrives, but re-affirming `COMPLIANT` from `COMPLIANT` is accepted too: it re-stamps `determination_recorded_by_user_id` with the current actor and still increments the item's and the plan year's `version` by 1 even though no status moves. An item in `INVENTORIED`, `ANALYSIS_DRAFTED`, `VIOLATION` or the terminal `REMEDIATED` is refused with `ERR_ITEM_NOT_AWAITING_DETERMINATION` (HTTP 409).

Before deciding anything, the server recomputes the item's stringency index from current evidence, and the outcome must agree with what it finds. A `COMPLIANT` outcome requires the recomputed index to be strictly below 5.0; a `VIOLATION` outcome requires it to be at or above 5.0. An outcome that contradicts the recomputed evidence is refused with `ERR_STRINGENCY_CONTRADICTS_EVIDENCE` (HTTP 409) — an officer may not certify parity in the face of a disparity the data shows, nor declare a violation the data does not support. A `COMPLIANT` outcome carries one further requirement: the item's latest non-`WITHDRAWN` comparative analysis — selected by exactly the ranking the documentation credit uses above, `created_at` descending, then `version` descending, then latest write first — must be in status `CERTIFIED`, and a determination of compliance behind a draft, submitted, insufficient or missing analysis is refused with `ERR_ANALYSIS_NOT_CERTIFIED` (HTTP 409). Only that single latest analysis is consulted, so an item whose certified analysis has since been overtaken by a newer draft can no longer be determined compliant. Although this paragraph describes the evidence-agreement rule first, the two are evaluated in the order §2.11 gives them — the documentation check at step 22, the agreement check at step 23 — so a `COMPLIANT` outcome that both stands behind an uncertified analysis and contradicts a recomputed index at or above 5.0 reports `ERR_ANALYSIS_NOT_CERTIFIED`. A `VIOLATION` outcome imposes no such documentation requirement, because a violation can be found on the evidence alone.

An accepted `COMPLIANT` determination moves the item from `ANALYSIS_SUBMITTED` to `COMPLIANT`, stamps `determination_recorded_by_user_id` with the acting `X-User-ID`, increments the item's `version` by 1, recomputes the plan year's posture, and increments the plan year's `version` by 1.

An accepted `VIOLATION` determination — whether it comes from `ANALYSIS_SUBMITTED` or from `COMPLIANT`, since both legs behave identically from here — runs a four-hop cascade. The item moves to `VIOLATION`, `determination_recorded_by_user_id` is stamped with the acting `X-User-ID`, and the item's `version` increments by 1. Then exactly one participant notice is created, disclosing the violation to covered participants. Then the plan year's `notified_violation_count` — the number of violation-disclosure notices raised against its items — and its `open_violation_count` are both re-derived from the new facts, and `compliance_posture` is recomputed, which by the first rung of the ladder yields `VIOLATION`. Finally that posture drives the plan year from `OPEN` or `UNDER_REGULATOR_REVIEW` into `REMEDIATION`, and the plan year's `version` increments by 1. The order is not interchangeable: the notice must exist before the notified count is derived, and the counts must be current before the status change is applied.

A **participant notice** is the disclosure artefact and is never created by a client directly. Each notice records the `nqtl_item_id` it concerns, a `notice_type` of either `VIOLATION_DISCLOSURE` or `CORRECTION_COMPLETED` naming which cascade produced it, a `source` of either `DETERMINATION_CASCADE` or `CAP_CLOSURE_CASCADE` naming the cascade itself, a `recipient_count` copied from the owning plan year's `covered_participant_count` at the moment of issuance, an `issued_at` instant taken from the logical clock, and a system-composed `disclosure_summary` built from the item and its classification as the item's `nqtl_type`, then the word "in", then the classification's `benefit_category` and `network_tier` separated by a forward slash, then a colon and a space, then the `notice_type` — for example, `PRIOR_AUTHORIZATION in OUTPATIENT/IN_NETWORK: VIOLATION_DISCLOSURE`. A violation determination always produces a notice with `notice_type` `VIOLATION_DISCLOSURE` and `source` `DETERMINATION_CASCADE`. Because cascade-created notices have no other discovery channel, the notices of one NQTL item can be listed, filtered optionally by `notice_type`. Notices are append-only and, as stated in §2.4, carry no `updated_at` and no `version`.

### 3.8. Corrective Action and the Remediation Liability Ledger

A violation has to be remedied, and remedies cost money the employer's board has already capped. Either a `PlanSponsor` or a `ComplianceOfficer` drafts a corrective action plan, naming the `nqtl_item_id` in violation that the plan remedies, a `remedy_type` of `DESIGN_CHANGE`, `PROCESS_CHANGE` or `RETROSPECTIVE_CLAIMS_REPROCESSING`, an `affected_claims_count` of at least 0 being the number of participant claims within the remedy's scope, an `average_claim_cents` of at least 0 being the average allowed amount per affected claim in cents, and a `target_completion_date` written as `YYYY-MM-DD` recording the committed completion date. The owning item must actually be in `VIOLATION`; drafting a plan for an item in any other state is refused with `ERR_ITEM_NOT_IN_VIOLATION` (HTTP 409). Plans may be read individually and listed with optional `nqtl_item_id`, `status` and `remedy_type` filters.

The plan's exposure is frozen at creation. Each remedy type carries a reprocessing rate: retrospective claims reprocessing is charged at the full allowed amount, a rate of 1.00, because every affected claim is genuinely reworked; a design change is charged at one quarter of the allowed amount, a rate of 0.25; and a process change is charged at one tenth, a rate of 0.10. `reprocessing_liability_cents` is the product of `affected_claims_count`, `average_claim_cents` and the rate for the chosen `remedy_type`, rounded half up to a whole number of cents. A design change covering 1,327 affected claims at an average of 4,990 cents produces 1,655,432.50 cents before rounding and freezes at 1,655,433 cents; the same inputs under retrospective claims reprocessing freeze at 6,621,730 cents. Once written, that number never moves again — later clock advances, re-approvals or reopened analyses do not re-derive it. Creating a plan does **not** touch the plan year's `remediation_liability_cents`; drafting an expensive remedy costs the plan year nothing until somebody approves it.

`remediation_liability_cents` on a plan year is the sum of `reprocessing_liability_cents` over the corrective action plans whose `status` is `APPROVED` and whose owning NQTL item belongs to that plan year, and it is 0 when no such plan exists. Plans in `DRAFT`, `REJECTED`, `COMPLETED` or `ABANDONED` contribute nothing. The aggregation order is pinned: each plan's amount is rounded to whole cents at its own creation, and the already-rounded amounts are then summed. Summing unrounded products and rounding once at the end is forbidden and drifts from the frozen amounts the individual plans report.

**Deciding a plan** is exclusive to a `ComplianceOfficer`, takes an `outcome` of either `APPROVED` or `REJECTED` plus an optional `decision_note`, and requires the plan to be in `DRAFT` — anything else is refused with `ERR_CAP_NOT_DRAFT` (HTTP 409) — and the owning item to still be in `VIOLATION`, or the decision is refused with `ERR_ITEM_NOT_IN_VIOLATION`. The plan's own status is examined before the item's, so a plan that has already been decided and whose item has since been remediated reports `ERR_CAP_NOT_DRAFT`. Both outcomes are subject to the approver-independence rule of §2.9: an officer whose `X-User-ID` equals the owning item's `determination_recorded_by_user_id` may not decide the plan on either branch, and the attempt is refused with `ERR_APPROVER_IS_DETERMINER`. Beyond that the two branches diverge sharply. Approval moves the plan `DRAFT` to `APPROVED`, stamps `approved_by_user_id` from the acting `X-User-ID`, increments the plan's `version` by 1, adds exactly the plan's frozen `reprocessing_liability_cents` to the plan year's `remediation_liability_cents`, and increments the plan year's `version` by 1. Rejection moves the plan `DRAFT` to `REJECTED` and increments only the plan's own `version` by 1; the liability ledger is never touched on that leg.

Approval is also where the board's ceiling bites. The plan year's current `remediation_liability_cents` plus the plan's frozen `reprocessing_liability_cents` must be less than or equal to that plan year's `remediation_liability_cap_cents`, and an approval that would push the total above the ceiling is refused with `ERR_LIABILITY_CAP_EXCEEDED` (HTTP 409). Because this fiscal check is the last thing evaluated, a plan that would both breach the cap and be decided by the determining officer reports the independence failure instead, as §2.11 sets out.

**Closing a plan** is likewise exclusive to a `ComplianceOfficer` and takes an `outcome` of either `COMPLETED` or `ABANDONED` plus an optional `closure_note`. The plan must be in `APPROVED`; closing a plan in any other status, including a second closure of one already `COMPLETED` or `ABANDONED`, is refused with `ERR_CAP_NOT_APPROVED` (HTTP 409). Both outcomes reduce the plan year's `remediation_liability_cents` by exactly the plan's frozen `reprocessing_liability_cents` and increment the plan's own `version` by 1 — this is the compensating leg of the money invariant, and it is what makes an approve-then-abandon round trip return the plan year to precisely its previous total with zero drift.

The two closing outcomes differ in what happens to the violation. Completion is the remedy actually landing: it additionally requires the owning item to still be in `VIOLATION`, refusing otherwise with `ERR_ITEM_NOT_IN_VIOLATION`, and moves that item from `VIOLATION` to the terminal `REMEDIATED`, incrementing the item's `version` by 1. That move creates exactly one participant notice with `notice_type` `CORRECTION_COMPLETED` and `source` `CAP_CLOSURE_CASCADE`, again stamped with the plan year's `covered_participant_count` as `recipient_count` and the logical clock as `issued_at`. The plan year's `open_violation_count` then falls, `compliance_posture` is recomputed, and if no violation and no failing plan-payments parity test remains, the plan year returns from `REMEDIATION` to `OPEN`. Abandonment is the remedy being called off: the owning item keeps `status` `VIOLATION`, no participant notice is created at all, and the plan year's `version` increments by 1 for the ledger reduction alone. A plan year with one abandoned remedy therefore stays in `REMEDIATION` with its violation intact and its booked liability released — which is exactly the state a fresh corrective plan should be drafted against.

### 3.9. Answering the Regulator

A regulator opens a request for a plan year's comparative analyses, naming the `plan_year_id` whose analyses are demanded, a `requested_nqtl_types` array of the NQTL types analyses are demanded for — non-empty, free of duplicates, and drawn from the same six values an NQTL item's `nqtl_type` may take — and a `request_reference` of 1 to 64 characters carrying the regulator's own docket reference. Opening a request is exclusive to the `Regulator` role. It stamps `opened_at` from the logical clock, sets `response_due_at` to `opened_at` advanced by 30 calendar days, writes `status` `OPEN` and `regulator_round` 0, sets `requested_item_count` and `covered_item_count` to 0, leaves `completeness_score` and `response_sufficient` null until the first response, and — because the analyses produced must describe a fixed plan design — moves the plan year from `OPEN` to `UNDER_REGULATOR_REVIEW`, refreshing its `updated_at` and incrementing its `version` by 1. That move is conditional on the plan year actually standing in `OPEN`, and nothing prevents a regulator opening a second, concurrent request for the same plan year: a year already in `UNDER_REGULATOR_REVIEW`, or one sitting in `REMEDIATION`, keeps the status it had and is not re-stamped at all, so neither its `updated_at` nor its `version` moves. From that moment no further benefit classification or treatment-limitation level may be created for the year, as §2.7 describes. Requests may be read individually, showing the completeness score and the current deadline, and listed with optional `plan_year_id` and `status` filters.

**Responding** is the sponsor's act. A `PlanSponsor` produces the demanded analyses, optionally attaching a `response_note`, which moves the request to `RESPONDED` from either `OPEN` or `INSUFFICIENT_RESPONSE`; a request already in `RESPONDED`, or one in `CLOSED`, is refused with `ERR_REGULATOR_REQUEST_NOT_OPEN` (HTTP 409). The logical clock must stand at or before `response_due_at`, including any extension already granted, and a late response is refused with `ERR_RESPONSE_WINDOW_EXPIRED` (HTTP 409). The demand must also match something: `requested_item_count` must be at least 1 at the moment of responding, and a request whose demanded NQTL types match no inventoried item cannot be scored and is refused with `ERR_NO_REQUESTED_ITEMS` (HTTP 409) rather than dividing by zero.

Each response is scored fresh. `requested_item_count` is the number of NQTL items whose `plan_year_id` is the request's plan year and whose `nqtl_type` appears in `requested_nqtl_types`, counted at this response and not carried over from the last one. `covered_item_count` is the subset of those items having at least one comparative analysis in status `CERTIFIED`; analyses in `WITHDRAWN`, `DRAFT`, `SUBMITTED` or `INSUFFICIENT` do not cover an item. The evidentiary total behind the response is the sum of `evidentiary_standard_count` taken over one certified analysis per covered item — where an item has more than one certified analysis, the one that contributes is the most recent by `created_at` descending, and when two of them carry the same `created_at` it is the one the server wrote later, `version` playing no part in this particular ranking.

The score itself is a base coverage figure plus a tiered evidentiary credit. The base is 100 multiplied by `covered_item_count` and divided by `requested_item_count`. The tier is then selected from that base alone: tier A when the base is at least 80, tier B when it is at least 60 but below 80, and tier C otherwise. Each tier carries a maximum credit — 10 points for tier A, 6 for tier B and 2 for tier C — and the credit actually granted is that maximum multiplied by the smaller of 1 and the evidentiary total divided by 8, so a response reaches its tier's full credit once it musters eight evidentiary standards across its covered items and is scaled down proportionally below that. `completeness_score` is the smaller of 100 and the base plus the credit, rounded half up to two decimal places, and `response_sufficient` is true exactly when `completeness_score` stands at or above 85.0. The tier must be read from the base before any credit is added; re-deriving the tier from the credited figure, or iterating to a fixed point, is forbidden and can promote a response across the sufficiency threshold that should have failed it. Four demanded items of which three are covered by certified analyses carrying 3, 3 and 2 evidentiary standards give a base of 75.00, which lands in tier B because 75 is below 80, a full credit of 6, and a `completeness_score` of 81.00 with `response_sufficient` false. The forbidden iterated order would have read 81 as tier A and returned 85.00 with `response_sufficient` true.

**Adjudicating** is the regulator's act and requires the request to be in `RESPONDED`; a request in `OPEN`, `INSUFFICIENT_RESPONSE` or `CLOSED` is refused with `ERR_REGULATOR_REQUEST_NOT_RESPONDED` (HTTP 409). The payload carries an `outcome` of either `ACCEPTED` or `INSUFFICIENT` plus an optional `adjudication_note`, and both outcomes increment the request's `version` by 1. An `INSUFFICIENT` adjudication moves `RESPONDED` to `INSUFFICIENT_RESPONSE`, increments `regulator_round` by 1, and extends `response_due_at` by a further 14 calendar days — every insufficient adjudication grants that extension, so a request adjudicated insufficient twice has had 28 days added to its original 30. The figures the last response produced — `requested_item_count`, `covered_item_count`, `completeness_score` and `response_sufficient` — are left standing on the record rather than cleared back to 0 and null, and are overwritten only when the next response is scored. That closes the regulator cycle: `RESPONDED` to `INSUFFICIENT_RESPONSE` and back to `RESPONDED` is traversable as often as the regulator is unsatisfied, with each round scored against the certified analyses that exist at that moment.

An `ACCEPTED` adjudication moves the request to the terminal `CLOSED`. What it does to the plan year depends on the plan year's own posture at that instant: when `compliance_posture` is `COMPLIANT` **and** the plan year is standing in `UNDER_REGULATOR_REVIEW`, it moves to `CLOSED`, refreshing `updated_at` and incrementing `version` by 1, and every subsequent child mutation against it is refused with `ERR_PLAN_YEAR_CLOSED`. Both conditions are required: a compliant plan year that is standing in `OPEN` — where a year whose violation cleared after the request was opened lands, since a recomputation returns `REMEDIATION` to `OPEN` and never to `UNDER_REGULATOR_REVIEW` — is left alone too. When the posture is `AT_RISK` or `VIOLATION`, the request closes but the plan year's `status` is left exactly as it was — a regulator may accept the paperwork for this docket without absolving a plan year that still has an open violation or a delinquent vendor.

## 5. Error Code Catalogue

Every failure response carries one of the identifiers below in `data.error_id`, together with the HTTP status shown. The conditions that trigger each identifier are stated where the rule they guard is described — in the ordered ladder of §2.11 and in the workflow narratives of §3 — and are deliberately not repeated here.

Three further identifiers sit outside the catalogue because they answer requests that never reach a rule: a path matching no route in this specification is answered with `ERR_NOT_FOUND` (HTTP 404), a path that exists but is addressed with a method it does not accept with `ERR_METHOD_NOT_ALLOWED` (HTTP 405), and an unexpected server fault with `ERR_INTERNAL` (HTTP 500). All three use the ordinary error envelope of §2.2. The routing pair is decided before the identity headers are examined, so a request to an unrouted path, or to a known path under an unsupported method, reports the routing failure even when it carries no identity headers at all — the ladder of §2.11 governs only requests that reach a declared operation. A trailing slash is not significant in routing: `/parity/plan-years/` addresses the same route as `/parity/plan-years`.
