# Stroke Center Certification & Telestroke Network API — Product Requirements Document

## 1. Introduction

Acute ischaemic stroke is a disease of minutes, and the certification bodies that accredit primary stroke centers know it: a facility keeps its designation by proving, period after period, that it moved patients from the emergency-department door to imaging and to thrombolytic therapy inside published time targets. The operational problem is that no single facility can do this alone. A small spoke hospital has a CT scanner and an emergency physician but no vascular neurologist on site; a hub facility has the neurologists but not the patients; a thrombectomy-capable center has the interventional suite but sits an ambulance ride away. The network that stitches these three together — telestroke coverage agreements, credentialing by proxy, video consult sessions, drip-and-ship transfers — is today held together by phone calls, paper checklists and retrospective chart abstraction, which means that the very time intervals a certification body will audit are reconstructed months after the fact from handwritten notes.

This document specifies the Stroke Center Certification & Telestroke Network API: a single system of record for the clinical clock, the telestroke consult, the thrombolytic eligibility decision, the transfer handoff, the protocol-deviation review and the certification report that rolls all of it up. Every endpoint is mounted under `/stroke-network`, with one exception: the logical-clock control endpoint described in §2.4. The system is deliberately opinionated about arithmetic and about ordering. Where two plausible ways exist to compute a door-to-needle interval, to round a compliance percentage, or to sequence the release of two facilities' open-case counters, exactly one is specified here and the others are wrong. This is not pedantry — a certification decision is read off a single composite number, and two implementations that disagree by one hundredth of a point can disagree about whether a hospital keeps its accreditation.

Readers should treat the document as a whole. The clinical workflow in §3 is written as a narrative because that is how the work is actually done, and the rules that govern a given operation are stated where that operation is described rather than gathered into a schema appendix. §2 carries the cross-cutting contracts — authentication, envelope shape, pagination, precision, stale-version rejection, cascade discipline and validation precedence — that every §3 workflow assumes without restating.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API, including every read, must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user is acting. If either header is missing or empty, or if `X-User-Role` carries a value outside the six role names declared below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). When the headers are well formed but the named role is not authorised for the endpoint being called, the rejection is `ERR_FORBIDDEN_ROLE` (HTTP 403). The six roles are `EdPhysician`, `Neurologist`, `TransferCoordinator`, `QualityAbstractor`, `ProgramCoordinator`, and `CertificationReviewer`.

`Neurologist` is the only entity-backed role in the system. When `X-User-Role` is `Neurologist`, `X-User-ID` is the `id` of the acting `Neurologist` record; ownership checks on any resource that references a `Neurologist` compare the resource's foreign-key field to `X-User-ID`. Concretely, every consult lifecycle action — accepting, declining, appending a video session, completing — and the eligibility determination on that case's checklist require that the consult's `assigned_neurologist_id` equal the caller's `X-User-ID`. A `Neurologist` who is not the assignee is rejected with `ERR_NOT_CONSULT_OWNER` (HTTP 403), and it is this same identity resolution that lets the system read the acting neurologist's `board_certified` flag when scoring an attestation.

The remaining five roles are opaque. When `X-User-Role` is `EdPhysician`, `TransferCoordinator`, `QualityAbstractor`, `ProgramCoordinator`, or `CertificationReviewer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where an audit trail is required — as `activated_by_user_id` on a code stroke, as `recorded_by_user_id` inside a documented contraindication, as `opened_by_user_id` and `reviewed_by_user_id` on a protocol deviation, as `abstracted_by_user_id` and `attested_by_user_id` on a quality measure abstraction, and as `submitted_by_user_id` and `decided_by_user_id` on a certification report — but it never compares that identifier to any entity's `id`. Two of those recorded identifiers are compared to each other rather than to an entity: a certification report may not be decided by the same `X-User-ID` that submitted it, and an abstraction may not be attested by the same `X-User-ID` that abstracted it. Both violations return `ERR_SEGREGATION_OF_DUTIES` (HTTP 403); see §2.10.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint in this API is paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10 when omitted, and an explicitly supplied value must be an integer no smaller than 1 and no larger than 100. `offset` is the number of records to skip before the page begins; it defaults to 0 and an explicitly supplied value must be an integer no smaller than 0. A `limit` or `offset` outside those bounds, or one that is not an integer, is rejected with `ERR_INVALID_PAGINATION` (HTTP 422).

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending. List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the size of the full filtered result set before the page window is applied and `has_more` indicates whether records remain beyond the current window. Filter parameters offered by a list endpoint combine conjunctively — a request that supplies two filters returns only records matching both.

### 2.4. The Logical Clock

Nothing in this system reads wall-clock time. Every system-assigned timestamp, every window comparison, every expiry check and every cooldown buffer reads a server-held **logical UTC clock**, and that clock is set explicitly by test-driving callers. A capability available to all six roles sets the clock to a supplied `current_utc` instant; it is the one endpoint outside the `/stroke-network` mount, exposed at `POST /_clock/set_current_utc`, it returns HTTP 200, and it mutates no entity. There is a mandatory startup default: before any call to that endpoint the logical clock reads exactly `2026-08-01T00:00:00Z`, and the server never falls back to the host's wall clock at any point.

Every datetime accepted in a request body and every datetime returned in a response is an ISO 8601 UTC instant. Caller-supplied instants such as a case's `door_at`, a checklist-independent last-known-well capture, an agreement's `effective_from` and `effective_until`, a report's `period_start` and `period_end`, a proxy credential's `expires_at` and a video session's `started_at` and `ended_at` are taken as given; server-assigned instants such as `activation_at`, `imaging_at`, `needle_at`, `requested_at`, `assigned_at`, `accepted_at`, `completed_at`, `determined_at`, `proposed_at`, `handoff_completed_at`, `submitted_at`, `decided_at`, `published_at`, `granted_at`, `recorded_at` and `public_report_published_at` are always the logical clock as it stands at the moment the write is applied. A malformed instant is a request-shape failure and returns `ERR_INVALID_REQUEST` (HTTP 422).

### 2.5. Common Resource Properties

All ten addressable resources in this system — stroke centers, spoke agreements, neurologists, code stroke cases, telestroke consults, thrombolytic checklists, transfer decisions, protocol deviations, quality measure abstractions and certification reports — carry the same four system-managed properties:

- `id` (string): a server-minted UUID. It carries no type prefix and no embedded meaning; nothing in this specification ever parses, orders by, or derives behaviour from an `id` value.
- `created_at` (string): an ISO 8601 UTC instant with three fractional digits, recording when the record was first created, read from the logical clock.
- `updated_at` (string): an ISO 8601 UTC instant with three fractional digits, refreshed on every mutation of the record — including mutations the server performs on its own initiative as a cascade, and including mutations that only change a derived counter.
- `version` (integer): a monotonically increasing counter that begins at 1 on creation and increments by exactly 1 on every mutation of that record. A cascade that touches three records increments three separate `version` counters. `version` is the value the stale-version checks in §2.7 compare against.

Embedded objects are not addressable resources and do not carry these four properties. A proxy credential grant inside an agreement's `proxy_credentials`, a video session record inside a consult's `video_sessions`, and a documented contraindication inside a checklist's `contraindications` are all plain objects whose fields are exactly those enumerated in the §3 narratives that create them; they have no `id`, no `updated_at` and no `version` of their own. Appending one of them mutates the owning record, which is what bumps the owner's `updated_at` and `version`.

### 2.6. Numeric Precision, Rounding and Clock Arithmetic

Three distinct numeric regimes coexist in this system and they must not be conflated.

**Money-style decimal quantities** — the two eligibility scores `screening_eligibility_score` and `attested_eligibility_score`, the three measure rates `dtn_60_compliance_pct`, `dti_45_compliance_pct` and `telestroke_response_compliance_pct`, the report's `mean_dtn_excess_pct`, the `composite_certification_score`, and a transfer's `congestion_factor` — are carried to exactly 2 decimal places, rounded half up. Where a formula both clamps and rounds, the clamp is applied first and the rounding once at the very end; intermediate products and sums are kept at full precision in between. The single exception in the whole system is a facility's `public_dtn_compliance_pct`, which is published at 1 decimal place, rounded half up, and derived from an already-rounded 2-decimal input.

**Elapsed-time quantities** are whole integers obtained by floor division. To measure the minutes between two logical-clock instants, take the elapsed count of whole seconds between them and divide by 60, discarding any remainder — never round to the nearest minute, and never subtract calendar minute fields. Zero elapsed seconds therefore yields 0 minutes rather than null; 59 seconds yields 0 minutes; 60 seconds yields 1 minute; 119 seconds yields 1 minute. `door_to_imaging_minutes`, `door_to_needle_minutes`, `lkw_to_needle_minutes`, `door_in_door_out_minutes` and every window-classification comparison are computed this way. One elapsed quantity is deliberately not floored to minutes: a consult's `response_latency_seconds` is the elapsed count of whole seconds between the request and the acceptance, kept at second resolution.

**Projection arithmetic** rounds upward rather than half up. A transfer's `adjusted_transport_minutes` is the product of the raw transport estimate and the congestion multiplier taken to the next whole minute if the product is not already whole, and the fixed overheads added afterwards are never multiplied by the multiplier. §3.7 pins the exact order.

All numeric values are returned in JSON as numbers, never as strings. A quantity documented as null-until-first-computed is returned as JSON null, and a null is always distinguishable from a zero: a center whose `public_dtn_compliance_pct` is null has never published a report, which is a different fact from a center that published `0.0`, and a report whose `mean_dtn_excess_pct` is null had no eligible cases at all, which is a different fact from a report whose mean excess was `0.00`.

### 2.7. Stale-Version Rejection on Case and Center Writes

Two create operations in this system can silently destroy work that another writer has already committed, and both are therefore guarded by an explicit stale-version check against the parent record's `version`.

The first is the consult request. `POST /stroke-network/consults` requires a non-optional input field `expected_case_version`, carrying the `version` of the target `CodeStrokeCase` as the client last observed it. If that value does not equal the case's current `version`, the request is rejected with `ERR_STALE_CASE_VERSION` (HTTP 412) and nothing is written. The reason this matters is that a new consult request legitimately supersedes the case's earlier consult activity; a requester holding a stale view of the case would otherwise discard a routing assignment another writer had already produced, and the version check converts that hazard into a deterministic rejection.

The second is the report create. `POST /stroke-network/certification-reports` requires a non-optional input field `expected_center_version`, carrying the `version` of the target `StrokeCenter` as the client last observed it. A mismatch against the center's current `version` is rejected with `ERR_STALE_CENTER_VERSION` (HTTP 412). Here the destructive act is the supersede: creating a report moves the center's existing `DRAFT` report to `SUPERSEDED` and detaches every abstraction attached to it, so a coordinator working from a stale view of the center would silently discard a reporting period another writer had just opened. Note that a successful report create itself increments the center's `version`, which is what makes a second create carrying the same `expected_center_version` fail; the descriptive update operation on a facility also bumps that `version`, so an unrelated rename is enough to invalidate a coordinator's cached value.

No other endpoint in this API accepts a version field. Endpoints not named above do not take one, and supplying one to them is an unknown field, rejected as a request-shape failure.

### 2.8. Cascade Discipline and Derived Aggregates

Writes in this system are rarely local. A single action routinely mutates two, three or four records, and the specification treats every one of those secondary mutations as part of the operation's contract rather than as an implementation detail. Three principles govern them.

**Cascades are hop-ordered and complete.** Where §3 describes an operation as cascading in hops, each hop is caused by the hop before it, and a hop is never skipped because it appears to be a no-op. Suspending a hub facility, for example, is a four-hop cascade: the facility's routing advisory drops to `BYPASS`, every `ACTIVE` agreement hubbed at it moves to `SUSPENDED`, every live consult on those agreements moves to `CANCELLED`, and every neurologist released by those cancellations has their load recomputed and a system-detected deviation is opened on the affected case. Each record touched anywhere in the chain has its own `updated_at` refreshed and its own `version` incremented by 1.

**Derived aggregates are recomputed, not incremented blindly.** Several fields are defined as counts over other records and must always agree with those records. A facility's `open_case_count` is the number of `CodeStrokeCase` records whose `center_id` names that facility and whose `status` is anything other than `CLOSED` or `ABORTED`, plus the number of `TransferDecision` records whose `destination_center_id` names that facility and whose `status` is `ACCEPTED`. An agreement's `active_consult_count` is the number of `TelestrokeConsult` records on that agreement whose `status` is `REQUESTED`, `ASSIGNED` or `IN_SESSION`. A neurologist's `active_consult_count` is the number of consults whose `assigned_neurologist_id` names them and whose `status` is `ASSIGNED` or `IN_SESSION`. A case's `deviation_count` is the number of `ProtocolDeviation` records on that case whose `status` is anything other than `DISMISSED` — which is why dismissing a deviation lowers the count. A report's `included_abstraction_count` is the number of abstractions whose `report_id` names it and whose `status` is `FINALIZED`, and its `closed_case_count_in_period` is the number of `CodeStrokeCase` records at the report's facility whose `status` is `CLOSED` and whose `door_at` falls inside the report's reporting interval. A checklist's `confirmed_inclusion_item_count` is the length of `confirmed_inclusion_item_codes`; its `absolute_contraindication_count` and `relative_contraindication_count` are the numbers of elements of `contraindications` whose `severity` is `ABSOLUTE` and `RELATIVE` respectively. A consult's `valid_video_session_count` is the number of elements of `video_sessions` whose `session_valid` is true. A neurologist's `completed_consult_count`, by contrast, is a lifetime tally rather than a live count: it increments only when that neurologist drives a consult to `COMPLETED` and it is never decremented.

**Reversals restore the counter, not the history.** Where an operation compensates for an earlier one — declining a proposed transfer, aborting a case, retracting an abstraction, amending a checklist — the derived counters and rates return to the values they would have held had the compensated action never happened, while the audit fields that record what happened (a cancelled consult's `assigned_neurologist_id`, a retracted abstraction's `retraction_reason`) are retained.

### 2.9. Equipment Readiness and the EMS Routing Advisory

Each facility publishes two derived postures that emergency medical services consume when deciding where to take a patient, and both are recomputed by the server rather than set by a caller.

`equipment_readiness_posture` is derived from the two readiness flags `ct_scanner_ready` and `video_cart_ready`, both of which begin true when a facility is registered and are set by readiness attestations. The posture is `READY` when both flags are true, `DEGRADED` when exactly one is true, and `OFFLINE` when neither is true.

`ems_routing_posture` is derived by an ordered three-clause rule in which the first matching clause wins outright, evaluated against the facility as it stands after every other side effect of the triggering write has been applied:

1. The posture is `BYPASS` if the facility's `certification_status` is `SUSPENDED` or `WITHDRAWN`, or if its `equipment_readiness_posture` is `OFFLINE`.
2. Otherwise the posture is `DIVERT_ADVISORY` if its `equipment_readiness_posture` is `DEGRADED`, or its `open_case_count` is 3 or greater, or its `certification_status` is `CONDITIONAL`.
3. Otherwise the posture is `ROUTINE`.

Because the clauses are ordered, a suspended facility carrying zero open cases with both flags true is still `BYPASS`, and a facility whose certification is `CONDITIONAL` is at best `DIVERT_ADVISORY` no matter how quiet and well-equipped it is. Because the open-case threshold is inclusive at 3, a certified and fully ready facility holding exactly 2 open cases is `ROUTINE` and the same facility holding exactly 3 is `DIVERT_ADVISORY`; closing the third case drops the count back to 2 and returns the posture to `ROUTINE` inside the very same request. A certified facility with exactly one readiness flag false is `DIVERT_ADVISORY`, and with both false it is `BYPASS`.

The advisory is re-derived at the end of every write that can change `certification_status`, either readiness flag, or `open_case_count` — facility registration, a readiness attestation, a suspension, a certification decision, a code stroke activation, a case close, a case abort, a transfer acceptance, a transfer cancellation and a handoff settlement all recompute it.

### 2.10. Segregation of Duties

Two attestations in this system may not be self-attested, and both barriers compare two opaque operator identifiers rather than consulting any entity.

A certification report's deciding `X-User-ID` must differ from the `submitted_by_user_id` recorded on that report at its most recent submission. A quality measure abstraction's attesting `X-User-ID` must differ from the `abstracted_by_user_id` recorded when the abstraction was created. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The barriers apply to exactly two operations — the certification-report decision and the abstraction finalisation — and to no others; in particular a coordinator may resubmit a report they previously submitted, and an abstractor may retract an abstraction they created.

### 2.11. Validation Precedence

When a single request violates more than one rule, the response is determined by the highest-precedence rule violated, not by the order in which an implementation happens to run its checks. The ladder below is exhaustive and strictly ordered from highest precedence to lowest.

1. **Header presence.** `X-User-ID` and `X-User-Role` must both be present and non-empty on every request — `ERR_UNAUTHENTICATED` (401).
2. **Role recognition.** `X-User-Role` must name one of the six declared roles — `ERR_UNAUTHENTICATED` (401).
3. **Role authorisation.** The caller's role must appear in the endpoint's authorised-role list — `ERR_FORBIDDEN_ROLE` (403).
4. **Consult ownership.** For consult acceptance, decline, video-session append and completion, and for checklist determination, the acting `Neurologist` resolved from `X-User-ID` must equal the consult's `assigned_neurologist_id` — `ERR_NOT_CONSULT_OWNER` (403).
5. **Request shape.** The body must contain every required input field of the endpoint with the declared JSON type, must not contain unknown fields, and every datetime field must be a well-formed ISO 8601 UTC instant — `ERR_INVALID_REQUEST` (422).
6. **Pagination bounds.** On every list endpoint, `limit` must be an integer between 1 and 100 inclusive and `offset` an integer of 0 or greater — `ERR_INVALID_PAGINATION` (422).
7. **Enum membership.** Every enum-typed input field must carry one of that field's declared values — `ERR_INVALID_ENUM_VALUE` (422).
8. **Path existence.** Every `id` appearing in a URL path must reference an existing record of the addressed collection, returning that collection's own not-found code: `ERR_CENTER_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_NEUROLOGIST_NOT_FOUND`, `ERR_CASE_NOT_FOUND`, `ERR_CONSULT_NOT_FOUND`, `ERR_CHECKLIST_NOT_FOUND`, `ERR_TRANSFER_NOT_FOUND`, `ERR_DEVIATION_NOT_FOUND`, `ERR_ABSTRACTION_NOT_FOUND` or `ERR_REPORT_NOT_FOUND` (all 404).
9. **Body reference existence.** Every foreign-key field in a request body must reference an existing record of the target entity, returning that entity's not-found code from the same list, and checked in the order the fields are declared in the endpoint's input list. This applies to the creation of agreements, neurologists, code strokes, consults, checklists, transfer decisions, deviations, abstractions and certification reports, and to the granting of a proxy credential.
10. **Stale case version.** `expected_case_version` must equal the referenced case's current `version` — `ERR_STALE_CASE_VERSION` (412).
11. **Stale center version.** `expected_center_version` must equal the referenced facility's current `version` — `ERR_STALE_CENTER_VERSION` (412).
12. **Declared transition.** The addressed record must be in a state from which the requested transition is declared, otherwise the per-entity invalid-state code applies: `ERR_INVALID_CENTER_STATE`, `ERR_INVALID_AGREEMENT_STATE`, `ERR_INVALID_ONCALL_TRANSITION`, `ERR_INVALID_CONSULT_STATE`, `ERR_INVALID_TRANSFER_STATE`, `ERR_INVALID_DEVIATION_STATE`, `ERR_INVALID_ABSTRACTION_STATE` or `ERR_INVALID_REPORT_STATE` (all 409). Action endpoints on a code stroke case are governed by rule 13 instead of this one.
13. **Case still active.** The `CodeStrokeCase` referenced by a consult request, a checklist creation or any checklist sub-action, a checklist determination, a transfer proposal, a thrombolytic administration or an abstraction creation must not be `CLOSED` or `ABORTED` — `ERR_CASE_NOT_ACTIVE` (409). The same code covers a case action attempted from a status for which no transition is declared.
14. **Segregation of duties**, as specified in §2.10 — `ERR_SEGREGATION_OF_DUTIES` (403).
15. **Valid video session on completion** — `ERR_NO_VALID_VIDEO_SESSION` (409).
16. **Absolute contraindication blocks thrombolysis** — `ERR_ABSOLUTE_CONTRAINDICATION` (422). This is the highest-precedence clinical safety rule, and it deliberately sits below rule 13, so a request to treat a closed case that also carries an absolute contraindication returns `ERR_CASE_NOT_ACTIVE`.
17. **Eligibility must have been determined before thrombolysis** — `ERR_ELIGIBILITY_NOT_DETERMINED` (409).
18. **Checklist documentation must be complete before determination** — `ERR_CHECKLIST_INCOMPLETE` (422). The eligibility score is only meaningful once this passes, so the check runs before the score is computed.
19. **Override justification conditionality** — `ERR_OVERRIDE_JUSTIFICATION_REQUIRED` (422).
20. **Absolute contraindications require documented evidence** — `ERR_CONTRAINDICATION_EVIDENCE_REQUIRED` (422).
21. **Thrombolytic window must not have expired**, re-evaluated against the logical clock before the guard is applied — `ERR_THROMBOLYTIC_WINDOW_EXPIRED` (422).
22. **Last-known-well capture consistency** — `ERR_LKW_REQUIRED` (422).
23. **Transfer mode must match the case's treatment history** — `ERR_TRANSFER_MODE_MISMATCH` (422).
24. **Equipment gate** — `ERR_CENTER_EQUIPMENT_OFFLINE` (409). This sits above rule 27, so an offline facility with a not-yet-effective agreement returns the equipment code, and below rule 13, so a closed case at an offline facility returns `ERR_CASE_NOT_ACTIVE`.
25. **Transfer destination must be thrombectomy-capable** — `ERR_DESTINATION_NOT_THROMBECTOMY_CAPABLE` (422).
26. **Transfer destination must not be bypassed** — `ERR_DESTINATION_BYPASS` (409).
27. In descending order after that: no self-referral on a transfer (`ERR_SELF_REFERRAL_TRANSFER`, 409); no self-paired agreement and a hub that really is a hub (`ERR_SPOKE_AGREEMENT_SELF_PAIR`, 409); the agreement's spoke must be the case's facility (`ERR_AGREEMENT_CENTER_MISMATCH`, 409); proxy credential validity (`ERR_PROXY_CREDENTIAL_INVALID`, 422); the agreement must already be in effect (`ERR_AGREEMENT_WINDOW_CLOSED`, 409); the agreement must be `ACTIVE`, evaluated after the automatic expiry check (`ERR_AGREEMENT_NOT_ACTIVE`, 409); interval endpoints must be strictly ordered (`ERR_INVALID_PERIOD_RANGE`, 422); reporting periods must not overlap (`ERR_REPORT_PERIOD_OVERLAP`, 409); the neurologist cooldown buffer (`ERR_NEUROLOGIST_COOLDOWN_ACTIVE`, 409); the agreement's concurrent-consult ceiling (`ERR_AGREEMENT_CONSULT_CAPACITY`, 409); one checklist per case (`ERR_DUPLICATE_CHECKLIST`, 409); one live abstraction per case-and-measure pair (`ERR_DUPLICATE_ABSTRACTION`, 409); no duplicate or unrecognised inclusion item (`ERR_DUPLICATE_INCLUSION_ITEM`, 409); a report needs at least one finalised abstraction (`ERR_NO_FINALIZED_ABSTRACTIONS`, 422); a report needs a minimum closed-case volume (`ERR_INSUFFICIENT_CASE_VOLUME`, 422); the review-round ceiling (`ERR_REVIEW_ROUND_LIMIT`, 409); a debrief before substantiating a sentinel deviation (`ERR_DEBRIEF_REQUIRED`, 422); a complete handoff packet (`ERR_HANDOFF_PACKET_INCOMPLETE`, 422); and a facility that is not suspended or withdrawn at publication (`ERR_CENTER_NOT_CERTIFIED`, 409). A readiness attestation whose component or result falls outside its declared set is an enum failure and returns `ERR_INVALID_ENUM_VALUE` (422) under rule 7.

The trigger conditions for each of these codes are stated where the corresponding workflow is described in §3; the catalogue in §5 lists only the codes and their HTTP statuses.

### 2.12. Flat Addressing and Path Identifier Resolution

Every entity in this system is a peer. There is no nesting: a consult is addressed at `/stroke-network/consults/{id}` and not underneath the case it serves, a checklist at `/stroke-network/checklists/{id}` and not underneath its case, an abstraction at `/stroke-network/abstractions/{id}` and not underneath its report. Relationships travel in request bodies as foreign-key fields and are read back through the corresponding list-endpoint filters, which are the only reverse-reachability channel the API offers. This matters most for system-detected deviations, which no caller creates and which are discoverable only by listing deviations filtered by their case.

Because collections are flat, every action path carries exactly one identifier, and that identifier is resolved before any body field is inspected: a request naming a non-existent record is rejected with that collection's not-found code regardless of what else the body gets wrong. Where a path identifier and a body foreign key are both present, the path identifier is resolved first, then the body references in the order the endpoint declares them. A request that names a non-existent checklist and also a non-existent neurologist in its body reports the checklist.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Network: Facilities, Agreements and Credentialing by Proxy

Before a single patient can be routed, a `ProgramCoordinator` populates the registry. Registering a facility supplies four attributes: a `name` (non-empty, at most 120 characters), a `facility_type` of `HUB_PRIMARY`, `SPOKE` or `THROMBECTOMY_CAPABLE`, a `state_code` of exactly two uppercase letters naming the licensure jurisdiction, and an `ems_region_code` (non-empty, at most 16 characters) identifying the EMS routing region into which the facility publishes its posture. Everything else about a new facility is server-assigned: `certification_status` begins at `PROVISIONAL`, both `ct_scanner_ready` and `video_cart_ready` begin true, `equipment_readiness_posture` therefore begins `READY`, `open_case_count` begins 0, and `ems_routing_posture` is derived on the spot — which for a provisional, fully ready facility with no open cases is `ROUTINE`. Three fields begin null: `public_dtn_compliance_pct`, `public_report_published_at` and `suspension_reason`. The `consecutive_denied_report_count` begins 0. A facility's `name` and `ems_region_code` may later be revised by the same coordinator role; nothing else about the registration is editable, and the revision increments the facility's `version`, which is precisely why a coordinator who renames a facility must re-read it before opening a reporting period.

Equipment readiness is maintained by attestation rather than by direct field assignment. An attestation names a `component` — either `CT_SCANNER` or `VIDEO_CART` — and a `result` of either `PASS` or `FAIL`, optionally accompanied by a free-text `note`. The named component's flag is set to true when the result is `PASS` and false when it is `FAIL`, after which `equipment_readiness_posture` is re-derived from the pair of flags and `ems_routing_posture` is re-derived from the posture per §2.9. Posting `FAIL` for a component whose flag is already false is accepted and has no further effect beyond the ordinary `updated_at` refresh and `version` increment; there is no error for a redundant attestation. A `component` or `result` outside those declared sets is an enum failure returning `ERR_INVALID_ENUM_VALUE`.

Telestroke coverage is contractual. A **spoke agreement** binds one hub to one spoke and is created with a `hub_center_id`, a `spoke_center_id`, a `coverage_tier` of `TIER_1_FULL` or `TIER_2_CONSULT_ONLY`, a `max_concurrent_consults` ceiling between 1 and 20 inclusive, and the two ends of its coverage window: `effective_from`, which is inclusive, and `effective_until`, which is exclusive. `effective_from` must be strictly earlier than `effective_until` or the create is rejected with `ERR_INVALID_PERIOD_RANGE`. The hub and the spoke must be different facilities and the hub must genuinely be a facility whose `facility_type` is `HUB_PRIMARY`; either violation returns `ERR_SPOKE_AGREEMENT_SELF_PAIR`. A newly created agreement lands in `DRAFT` with an empty `proxy_credentials` array, an `active_consult_count` of 0 and a null `suspension_reason`.

Activation is what makes an agreement usable, and it serves both the `DRAFT` and the `SUSPENDED` starting states: `DRAFT → ACTIVE` and `SUSPENDED → ACTIVE` are both declared. In either direction the hub facility's `certification_status` must be neither `SUSPENDED` nor `WITHDRAWN`, and the logical clock must still be strictly before the agreement's `effective_until`; activating out of `DRAFT` additionally requires that the spoke facility's `certification_status` not be `WITHDRAWN`. Activation sets the `status` to `ACTIVE` and clears `suspension_reason` to null. Any activation attempted from a state or against a hub for which no transition is declared — activating an already `ACTIVE` agreement, or a `TERMINATED` one, or one whose hub is suspended — is rejected with `ERR_INVALID_AGREEMENT_STATE`.

Suspension runs the other way and is available to both a `ProgramCoordinator` and a `CertificationReviewer`. It applies only from `ACTIVE`, requires a `suspension_reason` in the body, and does considerably more than flip a flag: every `TelestrokeConsult` on the agreement whose `status` is `REQUESTED`, `ASSIGNED` or `IN_SESSION` moves to `CANCELLED`, the agreement's `active_consult_count` is recomputed to 0, and each neurologist released by those cancellations has their `active_consult_count` recomputed and their `on_call_state` returned from `IN_CONSULT` to `ON_CALL`. Each cancelled consult also opens a system-detected deviation on its case, as described in §3.8. Suspending a `DRAFT` agreement is not a declared transition and returns `ERR_INVALID_AGREEMENT_STATE`. `TERMINATED` is the agreement's only terminal state, and it is reached in three ways: by the automatic expiry check described in §3.3, or by the withdrawal of the hub facility, which drives every agreement hubbed there out of `DRAFT`, `ACTIVE` or `SUSPENDED` straight to `TERMINATED`.

**Credentialing by proxy** is the mechanism by which a hub neurologist becomes authorised to practise into a spoke. A coordinator grants a credential on a specific agreement, supplying a `neurologist_id`, a `privilege_scope` of either `CONSULT_ONLY` or `CONSULT_AND_THROMBOLYSIS`, and an `expires_at` instant. The grant is appended to the agreement's `proxy_credentials` array as an object carrying that `neurologist_id`, that `privilege_scope`, that `expires_at`, a `status` of `GRANTED`, and a `granted_at` set to the logical clock; the other possible value of a grant's `status` is `EXPIRED`. Because a grant is an embedded object rather than an addressable record, the operation returns the updated agreement, and it returns 201 because a new grant is a new thing in a collection. Two conditions guard it: the named neurologist's `home_center_id` must equal the agreement's `hub_center_id`, and there may be at most one grant per combination of `neurologist_id` and `privilege_scope` while an existing grant for that combination is still `GRANTED`. Either violation returns `ERR_PROXY_CREDENTIAL_INVALID`.

Neurologists themselves are registered by the coordinator with a `full_name` (non-empty, at most 120 characters), a `home_center_id` naming the `HUB_PRIMARY` facility that employs them, a non-empty `licensed_state_codes` array of two-uppercase-letter jurisdiction codes, a `board_certified` boolean recording vascular-neurology board certification, a `roster_rank` between 1 and 999 inclusive that orders the on-call roster with lower values considered first, and a `concurrent_consult_limit` between 1 and 5 inclusive that caps how many consults they may hold at once, defaulting to 2 when omitted. A new neurologist starts `OFF_DUTY` with `active_consult_count` and `completed_consult_count` both 0 and `last_consult_completed_at` null.

Availability is a small state machine on `on_call_state` with exactly four declared moves, and either the neurologist themselves or a `ProgramCoordinator` may drive it. `OFF_DUTY → ON_CALL` requires that the neurologist's home facility have a `certification_status` that is neither `SUSPENDED` nor `WITHDRAWN`. `ON_CALL → OFF_DUTY` requires `active_consult_count` to be exactly 0, so a neurologist cannot walk away from live work. `ON_CALL → UNAVAILABLE` and `UNAVAILABLE → ON_CALL` are unconditional. `IN_CONSULT` is not settable here at all — it is reached only by accepting a consult and left only by completing or losing one — so requesting `IN_CONSULT` directly is rejected, as is any move with no declared edge such as `OFF_DUTY → UNAVAILABLE`; all such rejections carry `ERR_INVALID_ONCALL_TRANSITION`.

### 3.2. The Code Stroke: Activation, Last Known Well, and the Time Window

A code stroke is activated by an `EdPhysician` at the bedside. The activation payload names the facility through `center_id`, carries a de-identified `patient_ref` (non-empty, at most 40 characters), the ED arrival instant `door_at` that anchors both clinical clocks, an `arrival_mode` of `EMS`, `WALK_IN` or `INTERFACILITY_TRANSFER`, and the two fields that together capture symptom onset: `lkw_precision` and `last_known_well_at`. The server stamps `activation_at` from the logical clock, records the acting operator as `activated_by_user_id`, sets `status` to `ACTIVATED`, sets `disposition` to `PENDING`, sets `deviation_count` to 0, and classifies the case's `thrombolytic_window_class` immediately. It then cascades to the facility: `open_case_count` rises by 1 and `ems_routing_posture` is re-derived, which is how a busy emergency department starts diverting ambulances on its own.

Last-known-well capture is conditional and strictly policed. `lkw_precision` is one of `EXACT`, `ESTIMATED` or `UNKNOWN_WAKE_UP`. When the precision is `EXACT` or `ESTIMATED`, `last_known_well_at` is required; when the precision is `UNKNOWN_WAKE_UP` — the wake-up stroke whose onset nobody witnessed — `last_known_well_at` must be omitted and remains null. In addition, a supplied `last_known_well_at` must never be later than `door_at`: a patient cannot have been last known well after they arrived. Any of those three violations is rejected with `ERR_LKW_REQUIRED`. A code stroke may not be activated at all at a facility whose `equipment_readiness_posture` is `OFFLINE`, which is rejected with `ERR_CENTER_EQUIPMENT_OFFLINE`.

The **thrombolytic window classification** is the single most consequential derived value on a case, and it is re-derived from scratch at every checklist determination and again at thrombolytic administration, always against the logical clock as it stands at that moment. Three precision regimes feed one classifier, and they do not share an axis.

For a case whose `lkw_precision` is `UNKNOWN_WAKE_UP`, the last-known-well axis is abandoned entirely and the classification is made on door elapsed time instead. Take the whole minutes elapsed from `door_at` to the evaluation instant. If that is 120 minutes or fewer, `thrombolytic_window_class` is `EXTENDED_UNKNOWN`; if it is more than 120 minutes, the class is `OUT_OF_WINDOW`. Exactly 120 minutes yields `EXTENDED_UNKNOWN` and exactly 121 yields `OUT_OF_WINDOW`. A wake-up case never yields `WITHIN_3H` or `WITHIN_4_5H`, no matter how recently the patient arrived.

For every other case, take the whole minutes elapsed from `last_known_well_at` to the evaluation instant as the raw elapsed minutes. When `lkw_precision` is `EXACT`, the effective elapsed minutes are exactly those raw minutes. When `lkw_precision` is `ESTIMATED`, a fixed safety margin of 30 minutes is added to the raw minutes before any comparison is made, because an estimated onset time is systematically optimistic. The effective elapsed minutes are then classified against two boundaries, each inclusive on the lower-numbered class: 180 minutes or fewer is `WITHIN_3H`; more than 180 and up to and including 270 minutes is `WITHIN_4_5H`; more than 270 minutes is `OUT_OF_WINDOW`. Exactly 180 is `WITHIN_3H`, exactly 181 is `WITHIN_4_5H`, exactly 270 is still `WITHIN_4_5H`, and exactly 271 is `OUT_OF_WINDOW`. The margin is where the two precision regimes visibly diverge: an `ESTIMATED` case whose raw elapsed time is 150 minutes has an effective elapsed time of exactly 180 and is `WITHIN_3H`, while a raw 151 becomes an effective 181 and drops to `WITHIN_4_5H` — the same raw figures under `EXACT` would both classify as `WITHIN_3H`.

Because the class is a function of the clock, it is not stable. A case that classified as `WITHIN_3H` when the checklist was first attested can classify as `OUT_OF_WINDOW` when it is attested again after an amendment, and §3.6 explains why that is a hard stop on treatment rather than a warning.

A case's `status` walks the eight values `ACTIVATED`, `IMAGING_COMPLETE`, `CONSULT_IN_PROGRESS`, `ELIGIBILITY_DETERMINED`, `THROMBOLYSIS_ADMINISTERED`, `TRANSFER_INITIATED`, `CLOSED` and `ABORTED`, of which `CLOSED` and `ABORTED` are terminal. The shape is a fork and a join: once eligibility has been determined, a case either receives thrombolysis locally or is shipped without it, and a drip-and-ship patient traverses both branch nodes in sequence — treated first, then shipped. Both branches rejoin at `CLOSED`, and which branch was taken is preserved in `disposition`, one of `PENDING`, `TREATED_LOCAL`, `DRIP_AND_SHIP`, `TRANSFER_ONLY` or `NO_TREATMENT`. That distinction is not cosmetic: it decides whether the case counts towards a published measure at all, as §3.9 makes plain.

Almost every downstream write refuses to touch a case that has already finished. Requesting a consult, opening a checklist, writing an inclusion item or a contraindication, determining eligibility, proposing a transfer, administering a thrombolytic and creating an abstraction all require the case's `status` to be neither `CLOSED` nor `ABORTED`, and all report `ERR_CASE_NOT_ACTIVE` when it is.

### 3.3. Routing a Telestroke Consult to an On-Call Neurologist

When the bedside team needs a neurologist, an `EdPhysician` requests a **telestroke consult**. The request names the case through `case_id`, the coverage contract through `agreement_id`, and the privilege the requester needs through `requested_privilege_scope`, which is either `CONSULT_ONLY` or `CONSULT_AND_THROMBOLYSIS`. It also carries `expected_case_version` per §2.7. A newly created consult is stamped with `requested_at` from the logical clock, a `status` of `REQUESTED`, a null `assigned_neurologist_id`, a `decline_count` of 0, a `routing_attempt_count` of 1, an empty `excluded_neurologist_ids` array, an empty `video_sessions` array and a `valid_video_session_count` of 0. Its `assigned_at`, `accepted_at`, `completed_at`, `response_latency_seconds`, `recommendation`, `nihss_score`, `last_decline_reason` and `cancellation_reason` all begin null. The create returns 201 whichever way routing turns out.

Several gates run before routing does. The very first thing the request does is check the named agreement for expiry: if the logical clock has reached or passed the agreement's `effective_until`, the agreement transitions `ACTIVE → TERMINATED` there and then, and the consult request that triggered it is subsequently rejected because the agreement is no longer `ACTIVE`, carrying `ERR_AGREEMENT_NOT_ACTIVE`. A request made before the agreement's `effective_from` has arrived is rejected earlier and differently, with `ERR_AGREEMENT_WINDOW_CLOSED`. A consult may not be requested for a case at a facility whose `equipment_readiness_posture` is `OFFLINE` (`ERR_CENTER_EQUIPMENT_OFFLINE`), the named agreement's `spoke_center_id` must equal the case's `center_id` (`ERR_AGREEMENT_CENTER_MISMATCH`), and the agreement must have room: the count of consults already on it whose `status` is `REQUESTED`, `ASSIGNED` or `IN_SESSION` must be strictly fewer than its `max_concurrent_consults`, otherwise `ERR_AGREEMENT_CONSULT_CAPACITY`. §2.11 fixes the precedence among all of these.

**The routing selector** then chooses the neurologist. It runs on the initial request and again on every re-route triggered by a decline, and it is specified end to end — the eligibility filter, the ranking, the tie-breaks and the empty-pool behaviour are all fixed, and a candidate's `id` value is never consulted for any purpose. A neurologist is a candidate if and only if every one of the following holds, evaluated against the consult's agreement and the consult's case:

1. Their `home_center_id` equals the agreement's `hub_center_id`.
2. Their `on_call_state` is exactly `ON_CALL`.
3. Their `active_consult_count` is strictly less than their `concurrent_consult_limit`.
4. The `state_code` of the facility named by the case's `center_id` appears in their `licensed_state_codes`.
5. The agreement's `proxy_credentials` array contains a grant whose `neurologist_id` is theirs, whose `status` is `GRANTED`, whose `expires_at` is strictly later than the logical clock, and whose `privilege_scope` either equals the consult's `requested_privilege_scope` or is `CONSULT_AND_THROMBOLYSIS`. A grant expiring at exactly the current instant is not eligible, because the comparison is strict. A `CONSULT_ONLY` grant therefore cannot satisfy a `CONSULT_AND_THROMBOLYSIS` request, while a `CONSULT_AND_THROMBOLYSIS` grant satisfies a `CONSULT_ONLY` request.
6. Their `id` does not appear in the consult's `excluded_neurologist_ids`.
7. Their `board_certified` flag is true — unless the agreement's `coverage_tier` is `TIER_2_CONSULT_ONLY`, in which case this clause is waived entirely. All else equal, a neurologist who is not board certified is eligible on a consult-only-tier agreement and ineligible on a `TIER_1_FULL` one.
8. Either their `last_consult_completed_at` is null, or the whole minutes elapsed from that instant to the logical clock are 10 or greater. A neurologist who completed a consult exactly 10 minutes ago is eligible; one who completed 9 minutes ago is not.

The surviving candidates are ordered by `roster_rank` ascending, then by `active_consult_count` ascending, then by `completed_consult_count` ascending, and finally by `created_at` ascending, and the first is taken. Two candidates sharing a `roster_rank` are separated by the lighter live load; if load and lifetime completions also tie, the earlier-registered neurologist wins. The winner is written to `assigned_neurologist_id`, `assigned_at` is stamped from the logical clock, the consult's `status` becomes `ASSIGNED`, `routing_attempt_count` reflects the pass just executed, and both the winner's `active_consult_count` and the agreement's `active_consult_count` are recomputed.

If the candidate pool is empty, the request is **not** an error. The consult's `status` becomes `ESCALATED_UNFILLED`, `assigned_neurologist_id` stays null, `routing_attempt_count` is still incremented, and a system-detected `ProtocolDeviation` of type `CONSULT_UNFILLED` and severity `MAJOR` is opened on the case, raising the case's `deviation_count` by 1. The response is still 201 with the consult in `ESCALATED_UNFILLED`; escalating an unfillable consult is the designed behaviour, not a failure of the request.

Either outcome moves the case forward. A case sitting in `ACTIVATED` or in `IMAGING_COMPLETE` transitions to `CONSULT_IN_PROGRESS`, and that transition increments the case's `version` — which is the very bump a second requester holding a stale `expected_case_version` will trip over.

**Declining** is the assigned neurologist's prerogative and it is cyclic. A decline supplies a `last_decline_reason`, raises `decline_count` by 1, appends the declining neurologist's id to `excluded_neurologist_ids` *before* anything else happens so the selector cannot pick them again, and lowers that neurologist's `active_consult_count` back to its pre-assignment value. What happens next depends on the count: if the decline just recorded is the third on this consult, the loop exits — `status` becomes `ESCALATED_UNFILLED`, `assigned_neurologist_id` is cleared to null, and a system-detected `CONSULT_UNFILLED` deviation of severity `MAJOR` is opened on the case with `deviation_count` raised by 1. Otherwise `assigned_neurologist_id` is cleared, the consult returns to `REQUESTED`, `routing_attempt_count` rises by 1, and the selector runs again inside the same request: a non-empty pool puts the consult back into `ASSIGNED` with a new assignee, a fresh `assigned_at` and that neurologist's `active_consult_count` raised, while an empty pool lands it in `ESCALATED_UNFILLED` with the same deviation as above. The agreement's `active_consult_count` is recomputed either way. Declining a consult that is not `ASSIGNED` — an `ESCALATED_UNFILLED` one, for instance — returns `ERR_INVALID_CONSULT_STATE`.

**Accepting** opens the session. The assignee must be the caller, their `on_call_state` must be `ON_CALL`, no other consult assigned to them may be `IN_SESSION`, and — where their `last_consult_completed_at` is not null — the logical clock must be at least 10 whole minutes past it. That buffer rejects adjacency: accepting exactly 9 minutes after completing another consult fails with `ERR_NEUROLOGIST_COOLDOWN_ACTIVE`, and exactly 10 minutes after succeeds. On acceptance the consult's `status` becomes `IN_SESSION`, `accepted_at` is stamped from the logical clock, `response_latency_seconds` is computed as the whole seconds elapsed from `requested_at` to `accepted_at`, and the neurologist transitions `ON_CALL → IN_CONSULT`. Nothing is raised when the latency is long; a slow response surfaces later through the telestroke-response measure rather than as a deviation here. Accepting a consult that is already `COMPLETED`, or one still in `REQUESTED`, is rejected with `ERR_INVALID_CONSULT_STATE`.

### 3.4. Video Sessions and Closing Out a Consult

A telestroke consult is only as good as the video link it ran over, so each link attempt is recorded against the consult and each one is judged. A session record supplies `started_at`, `ended_at`, `video_quality` and `disconnect_count`, and is appended to the consult's `video_sessions` array as an object carrying `started_at`, `ended_at`, `video_quality`, `disconnect_count`, `duration_seconds` and `session_valid`. The append returns 201 and, per §2.5, the appended object has no identity of its own — it is addressed only as part of its parent consult. `video_quality` is one of `HD`, `SD` or `AUDIO_ONLY`; anything else is `ERR_INVALID_ENUM_VALUE`.

`duration_seconds` is the whole number of seconds from `started_at` to `ended_at`. A session is valid — `session_valid` true — when, and only when, all three of these hold: `duration_seconds` is 180 or greater, `video_quality` is **not** `AUDIO_ONLY`, and `disconnect_count` is 2 or fewer. Each threshold is inclusive on the passing side. A three-minute `HD` session with no disconnects, at exactly 180 seconds, is valid; the same session one second shorter, at 179 seconds, is not. A ten-minute `AUDIO_ONLY` session is invalid however long it ran and however stable it was, because audio-only contact cannot support a stroke examination. A ten-minute `SD` session that dropped twice is valid; the same session with a third drop is not.

Each valid session raises the consult's `valid_video_session_count`, which is the count of appended sessions with `session_valid` true and never anything else. It is monotonic in practice: appending an invalid session after a valid one leaves the count where it was rather than reducing it, because the count is a tally of the valid ones, not a verdict on the latest one. An invalid session is not rejected — it is recorded, and it opens a system-detected `ProtocolDeviation` of type `INVALID_VIDEO_SESSION` and severity `MINOR` on the consult's case, raising that case's `deviation_count` by 1. A consult can therefore accumulate a valid session, an invalid session and a deviation all at once, and still be completable.

**Completion** ends the consult and hands the case back to the bedside. The completing neurologist supplies a `recommendation` — one of `THROMBOLYSIS`, `TRANSFER_THROMBECTOMY`, `BOTH_DRIP_AND_SHIP` or `NO_INTERVENTION` — and an `nihss_score` between 0 and 42 inclusive. The consult must be `IN_SESSION` and the caller must be its assignee. Two documentation conditions gate it: the consult's `valid_video_session_count` must be 1 or more (`ERR_NO_VALID_VIDEO_SESSION`), and no element of `video_sessions` may still have a null `ended_at`, because an unterminated link means the encounter is not over. A consult with three sessions, all invalid, cannot be completed no matter how many were recorded.

Completion writes `completed_at` from the logical clock and moves the consult to `COMPLETED`. It then unwinds the neurologist: `IN_CONSULT → ON_CALL`, `last_consult_completed_at` set to the logical clock — which starts the 10-minute cooldown of §3.3 — `completed_consult_count` raised by 1, and `active_consult_count` recomputed. The agreement's `active_consult_count` is recomputed too. Note what completion does *not* do: it does not touch the case's `status`, which stays in `CONSULT_IN_PROGRESS` until the eligibility determination of §3.5 advances it, and it does not set the case's `disposition`.

The contrast with cancellation matters. When a consult is cancelled out from under its neurologist by a cascade — an agreement suspension, a facility suspension, or the case being aborted — the neurologist is released from `IN_CONSULT` back to `ON_CALL` and their `active_consult_count` is recomputed, but `last_consult_completed_at` is **not** set and `completed_consult_count` is **not** raised. A cancelled consult was not work performed: the neurologist becomes immediately routable again with no cooldown, and their lifetime completion tally, which is a routing tie-break, is untouched. A cancelled consult records a `cancellation_reason` and retains its `assigned_neurologist_id` for audit rather than clearing it, so it remains visible who was in the room when the plug was pulled. A declined consult, by contrast, does clear that field, because there is no longer anyone assigned.

### 3.5. The Thrombolytic Checklist: Two Dimensions, Two Scores

Before clot-busting drug can be given, the team works a **thrombolytic checklist**. One is opened per case, naming it through `case_id`, and a second attempt on the same case is `ERR_DUPLICATE_CHECKLIST`. A fresh checklist has `documentation_status` `NOT_STARTED`, `determination_status` `PENDING`, an empty `confirmed_inclusion_item_codes` array with `confirmed_inclusion_item_count` 0, an empty `contraindications` array with `absolute_contraindication_count` and `relative_contraindication_count` both 0, an `amendment_count` of 0, a `screening_eligibility_score` of 0.00, and a null `attested_eligibility_score`, `override_justification`, `determined_at`, `overridden_by_neurologist_id` and `last_amendment_note`. The create returns 201.

The checklist carries **two independent state dimensions on the one row**. `documentation_status` — `NOT_STARTED`, `IN_PROGRESS`, `DOCUMENTED` or `AMENDED` — tracks what has been written down. `determination_status` — `PENDING`, `ELIGIBLE`, `INELIGIBLE` or `ELIGIBLE_WITH_RELATIVE_OVERRIDE` — tracks the clinical verdict. They move on different triggers and are not ordered against each other: an amendment pushes the documentation dimension forward to `AMENDED` while pulling the verdict dimension backward to `PENDING`, and the combination is perfectly legal.

**Inclusion items** are confirmed one at a time. The `item_code` must be one of `INC_ONSET_CONFIRMED`, `INC_NIHSS_RECORDED`, `INC_BP_CONTROLLED` or `INC_ANTICOAG_REVIEWED`, and must not already be present in `confirmed_inclusion_item_codes`; either an unknown code or a repeat is `ERR_DUPLICATE_INCLUSION_ITEM`. The code is appended, `confirmed_inclusion_item_count` is recomputed as the array's length, and `documentation_status` moves from `NOT_STARTED` to `IN_PROGRESS`. A checklist already at `AMENDED` stays at `AMENDED` — documenting more after an amendment does not fall back to `IN_PROGRESS`.

**Contraindications** are documented as objects appended to `contraindications`, each holding the supplied `code`, the `severity` (`ABSOLUTE` or `RELATIVE`), the optional `documented_evidence`, the `recorded_by_user_id` taken from the caller's identity header and a `recorded_at` from the logical clock. The append returns 201 with the updated checklist. `absolute_contraindication_count` and `relative_contraindication_count` are recomputed from the array. An `ABSOLUTE` entry must carry non-empty `documented_evidence` — a `RELATIVE` one need not — and a bare `ABSOLUTE` entry is rejected with `ERR_CONTRAINDICATION_EVIDENCE_REQUIRED` **before any mutation happens**: nothing is appended, no count moves, and in particular no `MISSING_CONTRAINDICATION_DOC` deviation is created. That deviation type exists for an abstractor to raise by hand later, not as an automatic consequence of a rejected write. Like inclusion items, documenting a contraindication moves `NOT_STARTED` to `IN_PROGRESS` and leaves `AMENDED` alone, and neither kind of write ever touches `determination_status`.

**The eligibility score has two variants, and both live on the row at once.** They share one arithmetic core and differ in what they include:

- The **screening** variant is 15.0 points for each confirmed inclusion item, minus 12.0 for each relative contraindication, minus 100.0 for each absolute contraindication. It is recomputed on every inclusion-item and contraindication write and stored in `screening_eligibility_score`.
- The **attested** variant takes that same expression and adds two further terms: it subtracts a window penalty read off the case's `thrombolytic_window_class` — 0.0 for `WITHIN_3H`, 8.0 for `WITHIN_4_5H`, 15.0 for `EXTENDED_UNKNOWN`, 100.0 for `OUT_OF_WINDOW` — and adds 6.0 of board-certification credit when, and only when, the neurologist performing the determination has `board_certified` true. It is computed only at determination and stored in `attested_eligibility_score`.

Both variants clamp the result into the range 0 through 100 and then round to two decimals half up, per §2.6. The two fields never overwrite each other: a determination writes `attested_eligibility_score` and leaves `screening_eligibility_score` exactly as the last documentation write left it, so the bedside screening figure and the attested figure can be read side by side and will legitimately differ. Four inclusion items and no contraindications screen at 60.00; if the case is `WITHIN_4_5H` and the attesting neurologist is board certified, the attested figure is 60.00 − 8.00 + 6.00 = 58.00. A single absolute contraindication drives the raw expression to −40.0 and the stored value clamps to 0.00 in both variants.

**The determination** is the neurologist's attestation and it reads the attested variant only. Its outcome follows a strictly ordered ladder, first match winning: if `absolute_contraindication_count` is greater than 0 the verdict is `INELIGIBLE` regardless of the score; otherwise if the attested score is below 40.0 the verdict is `INELIGIBLE`; otherwise if `relative_contraindication_count` is 0 and the attested score is 55.0 or higher the verdict is `ELIGIBLE`; otherwise if `relative_contraindication_count` is 1 or more, the attested score is 40.0 or higher and an `override_justification` was supplied, the verdict is `ELIGIBLE_WITH_RELATIVE_OVERRIDE`; otherwise `INELIGIBLE`. Both thresholds are inclusive at the boundary: an attested 55.00 with no relative contraindications is `ELIGIBLE` and 54.99 is `INELIGIBLE`; an attested 40.00 with one relative contraindication and a justification is `ELIGIBLE_WITH_RELATIVE_OVERRIDE` and 39.99 is `INELIGIBLE`.

Several conditions gate the determination. The case's `thrombolytic_window_class` is recomputed against the logical clock **first**, before the score, because the window penalty depends on it. `confirmed_inclusion_item_count` must equal 4, otherwise `ERR_CHECKLIST_INCOMPLETE` — and this check runs before the score is computed at all, since a score over incomplete documentation is meaningless. `override_justification` is required if and only if `relative_contraindication_count` is greater than 0: omitting it with relative contraindications present and supplying it with none are both `ERR_OVERRIDE_JUSTIFICATION_REQUIRED`. The caller must be the neurologist assigned to a consult on this case whose `status` is `IN_SESSION` or `COMPLETED` and whose `valid_video_session_count` is 1 or more; anyone else gets `ERR_NOT_CONSULT_OWNER`. The `determination_status` must be `PENDING`, so a second determination without an intervening amendment has no declared transition and is rejected with `ERR_CASE_NOT_ACTIVE`.

A successful determination sets `documentation_status` to `DOCUMENTED`, writes the verdict into `determination_status`, stamps `determined_at` from the logical clock, and — on an override outcome only — records `overridden_by_neurologist_id` as the acting neurologist along with the `override_justification`; on any other outcome both stay null. It then cascades to the case: `CONSULT_IN_PROGRESS → ELIGIBILITY_DETERMINED`, with the case's `disposition` set to `NO_TREATMENT` when the verdict was `INELIGIBLE`.

**Amendment** reopens the record. It requires `documentation_status` `DOCUMENTED` and a case sitting at `ELIGIBILITY_DETERMINED` — amending after the drug has been given is rejected. It supplies a `last_amendment_note`, sets `documentation_status` to `AMENDED`, raises `amendment_count` by 1, and compensates the verdict dimension all the way back: `determination_status` to `PENDING`, `attested_eligibility_score` to null, `determined_at` to null, `overridden_by_neurologist_id` to null and `override_justification` to null. The case's `disposition` resets to `PENDING` but its `status` is **not** rewound — it stays at `ELIGIBILITY_DETERMINED`, which is precisely why a fresh determination is required before another thrombolytic attempt can pass its eligibility gate. The re-determination from `AMENDED` applies the same preconditions and the same ladder, and because it recomputes the window class against the current clock, a case that was `WITHIN_3H` at the first determination can come back `OUT_OF_WINDOW` at the second and flip a previously eligible patient to `INELIGIBLE` on a 100.0-point window penalty. An eligible re-determination leaves the case in `ELIGIBILITY_DETERMINED` with its `disposition` recomputed.

### 3.6. Stopping the Imaging Clock and Giving the Drug

Imaging completion is recorded with an `imaging_modality` and does two things: it stamps `imaging_at` from the logical clock and computes `door_to_imaging_minutes` from the case's `door_at` to that instant. The facility's `ct_scanner_ready` must be true — and note that this gate reads the individual flag, not the aggregate posture, so a `DEGRADED` facility whose video cart is the broken half still permits imaging while a `DEGRADED` facility whose scanner is down does not. Either way a false `ct_scanner_ready` yields `ERR_CENTER_EQUIPMENT_OFFLINE`.

The transition depends on where the case is. From `ACTIVATED` the case moves to `IMAGING_COMPLETE`. From `CONSULT_IN_PROGRESS` the call is a self-loop: the imaging clock and the consult workflow are independent tracks, so the case's `status` is left exactly where it was while `imaging_at` and `door_to_imaging_minutes` are written. Recording imaging a second time on a case already in `CONSULT_IN_PROGRESS` replaces the earlier instant with the later one and recomputes `door_to_imaging_minutes` against it — the most recent scan is the one that counts. A case sitting in `IMAGING_COMPLETE` has no declared imaging transition of its own, and a case that is `CLOSED` or `ABORTED` has none either; both are `ERR_CASE_NOT_ACTIVE`.

Whenever `door_to_imaging_minutes` comes out greater than 45, a system-detected `ProtocolDeviation` of type `DTI_EXCEEDED` and severity `MINOR` is opened on the case and its `deviation_count` rises by 1. Exactly 45 minutes raises nothing; 46 does. The 45-minute target is the same figure the `STK_DTI_45` quality measure scores against later, which is why a case can carry both a minor deviation and a failed measure numerator from a single slow scan.

**Administering the thrombolytic** is the most heavily guarded write in the system, and the order of its guards is deliberate. The caller supplies a `thrombolytic_agent` — `ALTEPLASE` or `TENECTEPLASE` — and a `thrombolytic_dose_mg` carried to one decimal place. The case must be at `ELIGIBILITY_DETERMINED`. Then, in the precedence of §2.11: the case's checklist must have `determination_status` of `ELIGIBLE` or `ELIGIBLE_WITH_RELATIVE_OVERRIDE` **and** `documentation_status` of `DOCUMENTED`, otherwise `ERR_ELIGIBILITY_NOT_DETERMINED` — which is exactly what an amended-but-not-yet-re-determined checklist trips. The checklist's `absolute_contraindication_count` must be 0, otherwise `ERR_ABSOLUTE_CONTRAINDICATION`. The case's `imaging_at` must not be null; you cannot lyse a patient who has not been scanned. The `thrombolytic_window_class` is recomputed against the logical clock as it now stands, before the guard is applied, and the drug is refused with `ERR_THROMBOLYTIC_WINDOW_EXPIRED` when that fresh classification is `OUT_OF_WINDOW` — even if the determination minutes earlier said `ELIGIBLE`, because the window is a property of the passing clock and not of the paperwork. And the facility's `equipment_readiness_posture` must not be `OFFLINE`.

On success `needle_at` is stamped from the logical clock, `thrombolytic_agent` and `thrombolytic_dose_mg` are recorded, `door_to_needle_minutes` is computed from `door_at` and `lkw_to_needle_minutes` from `last_known_well_at` — the latter staying null for an `UNKNOWN_WAKE_UP` capture, which has no last-known-well instant to measure from. The case moves to `THROMBOLYSIS_ADMINISTERED` and its `disposition` becomes `TREATED_LOCAL`. When `door_to_needle_minutes` exceeds 60 a system-detected `ProtocolDeviation` of type `DTN_EXCEEDED` and severity `MAJOR` is opened on the case with `deviation_count` raised by 1; exactly 60 minutes is on target and raises nothing, 61 does. The severity gap between the imaging miss and the needle miss is intentional — a `MINOR` deviation carries no weight in the composite certification score of §3.9, while a substantiated `MAJOR` one costs 8.0 points.

The `LKW_WINDOW_VIOLATION` and `MISSING_CONTRAINDICATION_DOC` deviation types are never raised automatically anywhere in this API. They exist for a quality abstractor to raise by hand against a case whose last-known-well capture or contraindication documentation looks wrong in retrospect.

### 3.7. Shipping the Patient: Transfer Proposals, Congestion and the Handoff

A patient who needs a clot pulled out mechanically has to travel, and the travel is negotiated as a **transfer decision**. The coordinator names the `case_id`, the receiving facility through `destination_center_id`, a `mode` of either `DRIP_AND_SHIP` or `TRANSFER_ONLY`, and a raw `transport_eta_minutes` between 1 and 600 inclusive. The proposal is created with `origin_center_id` copied from the case's `center_id`, a `status` of `PROPOSED`, `proposed_at` from the logical clock, an empty `handoff_packet_items` array and `handoff_packet_complete` false; `accepted_at`, `handoff_completed_at`, `door_in_door_out_minutes`, `decline_reason` and `cancellation_reason` all start null. The create returns 201.

The mode must match the treatment already given: `DRIP_AND_SHIP` means lysis was started locally and requires the case's `needle_at` to be set, while `TRANSFER_ONLY` means the patient is shipped unlysed and requires `needle_at` to be null. Getting this backwards is `ERR_TRANSFER_MODE_MISMATCH`. The destination must have `facility_type` `THROMBECTOMY_CAPABLE` (`ERR_DESTINATION_NOT_THROMBECTOMY_CAPABLE`), must not be the origin facility itself (`ERR_SELF_REFERRAL_TRANSFER`), and must not currently be on `BYPASS` (`ERR_DESTINATION_BYPASS`). The case moves accordingly: `ELIGIBILITY_DETERMINED → TRANSFER_INITIATED` with `disposition` `TRANSFER_ONLY` for a transfer-only proposal, or `THROMBOLYSIS_ADMINISTERED → TRANSFER_INITIATED` with `disposition` `DRIP_AND_SHIP` for the drip-and-ship path — which is how a single case traverses both treatment branches in sequence. No `open_case_count` moves at proposal time; a proposal is not yet a commitment.

**The projection is computed in a pinned order, and the order is observable.**

- **Step 1** reads the destination facility's `ems_routing_posture` as it stands *before this proposal exists* and freezes it into `destination_posture_at_proposal`. Because a destination on `BYPASS` is rejected outright by the guard above, this snapshot can only ever hold `ROUTINE` or `DIVERT_ADVISORY`.
- **Step 2** picks `congestion_factor` from that snapshot: 1.00 for `ROUTINE`, 1.25 for `DIVERT_ADVISORY`.
- **Step 3** sets `adjusted_transport_minutes` to `transport_eta_minutes` multiplied by `congestion_factor`, taken up to the next whole minute — a partial minute always rounds up, since you cannot arrive in a fraction of a minute. The multiplier applies to the transport leg and to nothing else.
- **Step 4** sets `projected_door_in_door_out_minutes` to `adjusted_transport_minutes` plus 20 minutes of handoff preparation, plus a further 10 minutes when the `mode` is `DRIP_AND_SHIP` to account for the infusion being managed in transit. The two overhead terms are added after the multiplication and are never themselves multiplied.

Worked through: a `ROUTINE` destination with a 35-minute estimate on a drip-and-ship transfer gives a factor of 1.00, `adjusted_transport_minutes` of 35 and a projection of 35 + 20 + 10 = 65. The same destination on `DIVERT_ADVISORY` gives 35 × 1.25 = 43.75, which rounds up to an `adjusted_transport_minutes` of 44, and a projection of 44 + 20 + 10 = 74. That same congested destination on a transfer-only proposal projects 44 + 20 = 64. And a 40-minute estimate at 1.25 lands on exactly 50.0, needing no rounding up, for a transfer-only projection of 70.

The snapshot never refreshes. **Acceptance** re-checks the destination against its *live* state — `ems_routing_posture` must not be `BYPASS` and `certification_status` must not be `SUSPENDED` or `WITHDRAWN`, so a destination that degrades or loses its certification between proposal and acceptance blocks the acceptance with `ERR_DESTINATION_BYPASS` — but `destination_posture_at_proposal` keeps the value it was frozen with, and `congestion_factor`, `adjusted_transport_minutes` and `projected_door_in_door_out_minutes` all keep the figures derived from it. Acceptance is the moment the destination starts carrying the patient: it stamps `accepted_at`, raises the destination's `open_case_count` by 1 and recomputes that facility's `ems_routing_posture`, which can itself flip the destination to `DIVERT_ADVISORY` at the three-open-case threshold. **Declining** records a `decline_reason` and unwinds the case to the node it came from — back to `THROMBOLYSIS_ADMINISTERED` with `disposition` restored to `TREATED_LOCAL` for a drip-and-ship proposal, or back to `ELIGIBILITY_DETERMINED` with `disposition` restored to `PENDING` for a transfer-only one — leaving the coordinator free to propose elsewhere. No `open_case_count` moves on a decline, because a proposed transfer was never counted.

**The handoff settles the case, and its seven steps run in this order:**

1. `door_in_door_out_minutes` is measured as the whole minutes from the case's `door_at` to the logical clock, taken while the case is still `TRANSFER_INITIATED`.
2. The supplied `handoff_packet_items` are recorded and `handoff_packet_complete` is derived against the mode-conditional required set: `HP_IMAGING_DISC`, `HP_LYTIC_RECORD`, `HP_NIHSS` and `HP_CONSENT` are all required for a `DRIP_AND_SHIP` transfer, while a `TRANSFER_ONLY` transfer requires that set minus `HP_LYTIC_RECORD` — there is no lytic record to hand over when no lytic was given. A missing required item is `ERR_HANDOFF_PACKET_INCOMPLETE`, so a settled handoff always ends with `handoff_packet_complete` true.
3. The transfer's `status` becomes `HANDOFF_COMPLETE` and `handoff_completed_at` is stamped from the logical clock.
4. The case is closed, retaining the `disposition` its mode gave it — `DRIP_AND_SHIP` or `TRANSFER_ONLY`.
5. Both facilities release the patient: the origin's `open_case_count` and the destination's `open_case_count` are each lowered by 1, and both decrements land before any posture is re-derived.
6. `ems_routing_posture` is then recomputed on the origin facility and then on the destination facility, so each sees the fully settled counts rather than a half-applied pair.
7. Finally, when the `door_in_door_out_minutes` measured in step 1 exceeds 120, a system-detected `ProtocolDeviation` of type `DIDO_EXCEEDED` and severity `MAJOR` is opened on the case with `deviation_count` raised by 1. Exactly 120 minutes raises nothing; 121 does. The comparison uses the step-1 value, not the projection made at proposal time — a transfer whose projection was optimistic and whose realisation was slow is judged on the realisation.

Only an `ACCEPTED` transfer can be handed off; attempting it on a `PROPOSED` or `DECLINED` one is `ERR_INVALID_TRANSFER_STATE`. And when the case is aborted underneath the transfer, both `PROPOSED` and `ACCEPTED` decisions are cancelled with a `cancellation_reason` of 'case aborted' — but only the `ACCEPTED` ones give the destination's `open_case_count` back, since only they ever took it.

### 3.8. Closing a Case, Aborting One, and Reviewing What Went Wrong

A case that never travelled is closed directly, and the close takes no request body. Two routes reach it: from `THROMBOLYSIS_ADMINISTERED`, where the `disposition` stays `TREATED_LOCAL`, and from `ELIGIBILITY_DETERMINED` where the case's checklist landed on `INELIGIBLE`, in which case the `disposition` stays `NO_TREATMENT`. Closing from `ELIGIBILITY_DETERMINED` with an eligible checklist has no declared transition — an eligible patient is either treated or transferred, not quietly closed — and neither does closing a case that is `TRANSFER_INITIATED`, since transfer-bound cases close through the handoff of §3.7. Both are `ERR_CASE_NOT_ACTIVE`. One further condition applies: every consult on the case must already be settled, meaning its `status` is `COMPLETED`, `ESCALATED_UNFILLED` or `CANCELLED`. A live consult holds the case open. On success the origin facility's `open_case_count` drops by 1 and its `ems_routing_posture` is recomputed, in that order.

**Aborting** is the escape hatch and it is reachable from every live node — `ACTIVATED`, `IMAGING_COMPLETE`, `CONSULT_IN_PROGRESS`, `ELIGIBILITY_DETERMINED` and `TRANSFER_INITIATED` — with an `abort_reason` recorded. The case's `status` becomes `ABORTED` and its `disposition` `NO_TREATMENT`, and then the cascade unwinds everything the case set in motion, hop by hop. First, every consult on the case in `REQUESTED`, `ASSIGNED` or `IN_SESSION` is cancelled and every transfer decision in `PROPOSED` or `ACCEPTED` is cancelled. Second, and caused by the first, each released neurologist has `active_consult_count` lowered and returns from `IN_CONSULT` to `ON_CALL`, and each affected agreement's `active_consult_count` is recomputed. Third, the origin facility's `open_case_count` drops by 1 — exactly compensating the increment the activation made — and for each cancelled `ACCEPTED` transfer the destination facility's `open_case_count` drops by 1 as well. Fourth, and caused by the third, `ems_routing_posture` is recomputed on the origin facility and on every affected destination. Consults cancelled by the case's own abort do **not** get a `CONSULT_UNFILLED` deviation: the consult was not unfillable, the case simply stopped existing, and adding a deviation to an aborted case would penalise the facility for its own good judgement.

**Deviations** are the quality record. A manual one names its `case_id`, a `deviation_type`, a `severity` and a `narrative` that must be non-empty and at most 500 characters, and is created with `source` `MANUAL`, `status` `OPEN`, `opened_by_user_id` from the caller's identity header, `review_round` 0 and `debrief_completed` false, returning 201 and raising the case's `deviation_count` by 1. The `deviation_type` is one of `DTI_EXCEEDED`, `DTN_EXCEEDED`, `DIDO_EXCEEDED`, `CONSULT_UNFILLED`, `MISSING_CONTRAINDICATION_DOC`, `INVALID_VIDEO_SESSION` or `LKW_WINDOW_VIOLATION`; the `severity` is `MINOR`, `MAJOR` or `SENTINEL`. Deviations synthesised by the cascades described throughout §3 are identical rows except that their `source` is `SYSTEM_DETECTED` and their `opened_by_user_id` is the literal string `system`. Those rows are not returned by any create call, so listing deviations filtered by case is the only way to discover them.

The review cycle is a bounded loop. A reviewer starts the review of an `OPEN` deviation, which moves it to `UNDER_REVIEW`, raises `review_round` to 1 and records `reviewed_by_user_id`. From `UNDER_REVIEW` the reviewer may return it for more information with an `info_request`, moving it to `RETURNED_FOR_INFO`; the abstractor then supplies `additional_info` to push it back to `UNDER_REVIEW`, raising `review_round` by 1 each time. The loop terminates because entering review requires `review_round` to be below 3: the fourth entry attempt is refused with `ERR_REVIEW_ROUND_LIMIT`, and so is a return-for-info once `review_round` has already reached 3.

Two writes are deliberately kept apart. The **debrief** records a `debrief_summary` and sets `debrief_completed` true, and it is the only thing that ever writes those two fields — the decision never does, however thorough the reviewer's note. The **decision** supplies an `outcome` of `SUBSTANTIATE` or `DISMISS` and is available only from `UNDER_REVIEW`, moving the deviation to `SUBSTANTIATED` or `DISMISSED` and recording `reviewed_by_user_id`. Substantiating a deviation whose `severity` is `SENTINEL` requires `debrief_completed` to be true, otherwise `ERR_DEBRIEF_REQUIRED`; `MINOR` and `MAJOR` deviations may be substantiated without one. Deciding an `OPEN` deviation, or resubmitting one that is already `UNDER_REVIEW`, is `ERR_INVALID_DEVIATION_STATE`.

The two outcomes reach in different directions. Substantiation recomputes `substantiated_major_count` and `substantiated_sentinel_count` on every certification report whose `status` is `DRAFT` or `RETURNED`, whose facility is the case's facility and whose reporting period contains the case's `door_at` — but it pointedly does **not** recompute `composite_certification_score`, which is only ever produced at submission (§3.9). Substantiating a deviation against an already-submitted report therefore leaves that report's composite untouched. Dismissal instead lowers the case's `deviation_count`, because a dismissed deviation is no longer a deviation the case is carrying.

### 3.9. Abstraction, Reporting and the Certification Decision

Certification is earned from the record, and the record is built one abstraction at a time. A **quality measure abstraction** names its `case_id` and a `measure_code` of `STK_4_THROMBOLYTIC_THERAPY`, `STK_DTI_45`, `STK_DTN_60` or `STK_TELESTROKE_RESPONSE`, and is created with `status` `DRAFT`, `variant` `PROVISIONAL`, `abstracted_by_user_id` from the caller's identity header, and a null `attested_by_user_id`, `attestation_note` and `retraction_reason`. The create returns 201. At most one non-`RETRACTED` abstraction may exist per case-and-measure pair (`ERR_DUPLICATE_ABSTRACTION`), and the case must not yet be `CLOSED` or `ABORTED` when the draft is opened — abstraction begins while the case is live and is attested only after it has finished, which is the whole point of the two-step.

**The numerator rules are per measure**, evaluated against the abstraction's case:

- `STK_DTI_45` requires `door_to_imaging_minutes` to be non-null and 45 or less. Exactly 45 counts; 46 does not.
- `STK_DTN_60` requires `door_to_needle_minutes` to be non-null and 60 or less. Exactly 60 counts; 61 does not.
- `STK_4_THROMBOLYTIC_THERAPY` requires only that `needle_at` is not null — the patient was lysed at all.
- `STK_TELESTROKE_RESPONSE` requires some consult on the case whose `status` is `COMPLETED`, whose `response_latency_seconds` is non-null and 300 or less, and whose `valid_video_session_count` is 1 or more. The video gate is part of the numerator, not a side condition: a consult answered in 120 seconds with no valid session fails the measure. Exactly 300 seconds with a valid session passes; 301 fails.

**The exclusion clauses are ordered and the first match wins**, evaluated against the case and its checklist — where a case with no checklist at all is treated as having an `absolute_contraindication_count` of 0:

1. `ABORTED_CASE`, when the case's `status` is `ABORTED`.
2. `DOCUMENTED_ABSOLUTE_CONTRAINDICATION`, when the checklist's `absolute_contraindication_count` is greater than 0.
3. `OUT_OF_WINDOW`, when the case's `thrombolytic_window_class` is `OUT_OF_WINDOW`.
4. `TRANSFER_ONLY`, when the case's `disposition` is `TRANSFER_ONLY`.
5. `NONE`, when nothing above matched.

The order is observable and it matters: an aborted case that also documented an absolute contraindication reports `ABORTED_CASE`, and a transfer-only case that is also out of window reports `OUT_OF_WINDOW`. `exclusion_reason` records whichever clause fired.

**This evaluation has two variants and the difference is the whole reason the row has a lifecycle.** Under the `PROVISIONAL` variant — which applies at create and for as long as the row stays `DRAFT` — `numerator_flag` and `exclusion_reason` are computed as above, but `denominator_included` is set true **unconditionally**. A draft abstraction on a transfer-only case therefore reports `exclusion_reason` `TRANSFER_ONLY` while still counting itself in the denominator: the exclusion is *recorded but not applied*, so the abstractor can see what will happen without it happening yet. Under the `CERTIFIED` variant — which applies at finalisation — everything is re-evaluated against the case as it now stands and `denominator_included` becomes true only when `exclusion_reason` is `NONE`. Finalising that same transfer-only row flips `denominator_included` to false without changing `exclusion_reason`.

A new draft attaches itself to a report if it can. Its `report_id` is set to the id of the `DRAFT` certification report for the case's facility whose reporting period contains the case's `door_at`, when exactly one such report exists, and to null otherwise; when it does attach, that report's `included_abstraction_count`, its three rate fields under its current `PROVISIONAL` variant, and its `mean_dtn_excess_pct` are all recomputed on the spot.

**Finalising** supplies an `attestation_note` and requires three things: the row must be `DRAFT`, the case must have reached `CLOSED` or `ABORTED`, and the caller's identity must differ from `abstracted_by_user_id` (§2.10). It sets `status` `FINALIZED`, `variant` `CERTIFIED` and `attested_by_user_id`, re-evaluates the numerator, exclusion and denominator under the certified variant, and — when the row is attached — recomputes the report's `included_abstraction_count` and three rates under whichever variant that report's `rate_variant` currently names. Finalising an already-`FINALIZED` row is `ERR_INVALID_ABSTRACTION_STATE`.

**Retracting** supplies a `retraction_reason` and is the compensating action: every counter and rate the abstraction contributed to is restored to the value it would have had if the row had never existed. It is available from `DRAFT`, and from `FINALIZED` only while the attached report is still `DRAFT` or `RETURNED` — retracting out from under a report that has been submitted, accepted or published is `ERR_INVALID_ABSTRACTION_STATE`, as is retracting an already-`RETRACTED` row. On success the row becomes `RETRACTED`, its `report_id` is cleared to null, and the report it was attached to has its `included_abstraction_count`, `dtn_60_compliance_pct`, `dti_45_compliance_pct`, `telestroke_response_compliance_pct` and `mean_dtn_excess_pct` recomputed from the abstractions that remain. Retraction also frees the case-and-measure pair, so a fresh abstraction for the same measure on the same case may then be created.

**A certification report** covers one facility over one period. It names `center_id`, a `period_start` and a `period_end` forming the half-open interval that begins at `period_start` and stops just before `period_end`, and the `expected_center_version` of §2.7. `period_start` must be strictly earlier than `period_end` (`ERR_INVALID_PERIOD_RANGE`), and the interval must not intersect the interval of any existing report for the same facility whose `status` is not `SUPERSEDED` (`ERR_REPORT_PERIOD_OVERLAP`). Adjacency is explicitly allowed: a period beginning at exactly an existing period's `period_end` is accepted, because the existing period never included that instant. The create returns 201 with `status` `DRAFT`, `rate_variant` `PROVISIONAL`, `decision` `PENDING`, and null `submitted_by_user_id`, `decided_by_user_id`, `superseded_by_report_id`, `submitted_at`, `decided_at` and `published_at`.

Creation also supersedes and gathers. Any existing `DRAFT` report for the same facility moves to `SUPERSEDED` with its `superseded_by_report_id` pointing at the new report, and every abstraction attached to it is detached by having `report_id` cleared to null. The new report then attaches every abstraction whose `status` is `DRAFT` or `FINALIZED` sitting on a case at this facility that is `CLOSED` and whose `door_at` falls inside the period. It computes `closed_case_count_in_period` and `included_abstraction_count`, computes its three rates under the `PROVISIONAL` variant along with `mean_dtn_excess_pct`, computes `substantiated_major_count` and `substantiated_sentinel_count`, and leaves `composite_certification_score` at 0.00 — the composite is produced at submission and nowhere else. Finally it raises the facility's `version` by 1, which is the bump that makes a second create holding the same `expected_center_version` fail.

**The three compliance rates share one definition with two variants.** They are computed over `STK_DTN_60` into `dtn_60_compliance_pct`, over `STK_DTI_45` into `dti_45_compliance_pct`, and over `STK_TELESTROKE_RESPONSE` into `telestroke_response_compliance_pct`. `STK_4_THROMBOLYTIC_THERAPY` abstractions are attached and counted in `included_abstraction_count` like any other, but they feed no rate field and therefore no composite — the network scores itself on speed and reachability, not on treatment volume. For each measure, the pool is the abstractions attached to this report with that `measure_code`: under the `PROVISIONAL` variant, those whose `status` is `DRAFT` or `FINALIZED`; under the `CERTIFIED` variant, only those whose `status` is `FINALIZED`. The denominator is the pool members with `denominator_included` true; the numerator is those denominator members that also have `numerator_flag` true. When the denominator is 0 the rate is **0.00** — never null, and never 100.00 on the reasoning that nothing failed. Otherwise the rate is 100 multiplied by the numerator and divided by the denominator, rounded to two decimals half up: 1 of 3 gives 33.33, and 2 of 3 gives 66.67. `rate_variant` records which variant produced the three stored figures, and it is `PROVISIONAL` while the report is `DRAFT` and `CERTIFIED` from submission onward.

**`mean_dtn_excess_pct` measures how badly the misses missed.** Its population is the cases referenced by `FINALIZED` `STK_DTN_60` abstractions attached to this report whose `door_to_needle_minutes` is not null. For each such case, take the amount by which `door_to_needle_minutes` exceeds 60 — treating anything at or under 60 as zero excess rather than a negative — divide by 60, express as a percentage, and round that per-case figure to a **whole** percent half up. Then average those whole percents and round the average to two decimals half up. A single case at 70 minutes yields 10 over 60, which is 16.67 percent, rounding to a per-case 17, and a mean of 17.00. Two cases at 70 and 50 minutes yield 17 and 0, and a mean of 8.50. A case at exactly 60 contributes 0. When the population is empty the field is null, not 0.00 — there is a real difference between "nobody was late" and "nobody was measured", and §2.6 requires the two to be distinguishable.

**Submission** takes no request body and requires the report to be `DRAFT` or `RETURNED`, `included_abstraction_count` to be 1 or more (`ERR_NO_FINALIZED_ABSTRACTIONS`, since a report with nothing finalised attached carries no signal), and `closed_case_count_in_period` to be 2 or more (`ERR_INSUFFICIENT_CASE_VOLUME`, since two closed cases is the minimum volume from which a rate means anything). It first re-gathers: every attached abstraction still in `DRAFT` is detached with `report_id` cleared to null, every `FINALIZED` abstraction on an in-period closed case is attached, and `included_abstraction_count` is recomputed. Then `rate_variant` becomes `CERTIFIED` and the three rates are recomputed under that variant, `mean_dtn_excess_pct` is recomputed, `substantiated_major_count` and `substantiated_sentinel_count` are recomputed, and `composite_certification_score` is computed. `submitted_at` is stamped from the logical clock and `submitted_by_user_id` recorded. On a resubmission from `RETURNED`, `decision` is reset to `PENDING` and `decided_by_user_id` to null *before* any of that recomputation runs, so a returned report is judged fresh rather than against its previous verdict. Submitting a `SUPERSEDED` report is `ERR_INVALID_REPORT_STATE`.

**The composite certification score** is assembled in four parts and then clamped:

- The **weighted base** is 0.40 of `dtn_60_compliance_pct` plus 0.35 of `dti_45_compliance_pct` plus 0.25 of `telestroke_response_compliance_pct`, using the stored rounded rates exactly as they sit on the report rather than any unrounded intermediates.
- The **deviation penalty** is 8.0 for each substantiated `MAJOR` deviation plus 18.0 for each substantiated `SENTINEL` one, capped at 24.0 in total. The cap is a real ceiling: once it is reached, further substantiated deviations cost nothing more.
- The **volume credit** is 5.0 when `included_abstraction_count` is 20 or more, otherwise 2.0 when it is 10 or more, otherwise 0.0.
- The **tier multiplier** is 1.00 for a `HUB_PRIMARY` facility, 0.95 for a `SPOKE`, and 1.05 for a `THROMBECTOMY_CAPABLE` one.

The raw figure is the base minus the penalty plus the credit, all multiplied by the tier multiplier; the multiplier applies to the whole bracket, not to the base alone. The raw figure is then clamped into 0 through 100 and rounded to two decimals half up exactly once, per §2.6.

Worked through: a `SPOKE` facility with `dtn_60_compliance_pct` 100.00, `dti_45_compliance_pct` 50.00, `telestroke_response_compliance_pct` 100.00, no substantiated deviations and 4 attached abstractions has a base of 40.00 + 17.50 + 25.00 = 82.50, no penalty, no credit, and a raw figure of 82.50 × 0.95 = 78.375, which stores as 78.38. Give that same facility one substantiated `MAJOR` and one substantiated `SENTINEL` deviation and the penalty is 8.0 + 18.0 = 26.0, capped to 24.0, so the raw figure is (82.50 − 24.00) × 0.95 = 55.575 and the composite is 55.58 — and adding a third substantiated `MAJOR` deviation leaves it at 55.58, because the cap was already binding. A `THROMBECTOMY_CAPABLE` facility with all three rates at 100.00 and no penalties has a raw figure of 100.00 × 1.05 = 105.0, which clamps to a stored 100.00.

**The decision** is the reviewer's, it accepts an optional `reviewer_note`, and it requires a `SUBMITTED` report decided by someone other than its submitter (§2.10). It **re-reads** `composite_certification_score` rather than recomputing it: whatever the submission produced is what the decision judges, even if abstractions or deviations have moved since. The `decision` follows the score — `CERTIFIED` at 85.00 or above, `CONDITIONAL` from 70.00 up to but not including 85.00, and `DENIED` below 70.00. Both thresholds are inclusive at the bottom: 85.00 is `CERTIFIED` and 84.99 `CONDITIONAL`; 70.00 is `CONDITIONAL` and 69.99 `DENIED`. `decided_at` is stamped from the logical clock and `decided_by_user_id` recorded. A `CERTIFIED` or `CONDITIONAL` decision moves the report's `status` to `ACCEPTED`; a `DENIED` one moves it to `RETURNED`, from where it can be resubmitted. Deciding a `DRAFT` report is `ERR_INVALID_REPORT_STATE`.

Acceptance flows straight into the facility: its `certification_status` is set from the `decision` — so `CERTIFIED` or `CONDITIONAL` — its `consecutive_denied_report_count` is reset to 0, its `suspension_reason` is cleared to null, and its `ems_routing_posture` is recomputed, which is where a `CONDITIONAL` facility acquires its standing `DIVERT_ADVISORY` posture per §2.9.

Denial escalates, in hops. First, the facility's `consecutive_denied_report_count` rises by 1 and its `certification_status` moves to `SUSPENDED` — or all the way to `WITHDRAWN` when the facility was already `SUSPENDED` with a `consecutive_denied_report_count` of 1, which also carries that counter to 2 and, `WITHDRAWN` being terminal, terminates every agreement hubbed at that facility for good. Second, and caused by the first, the facility's `ems_routing_posture` becomes `BYPASS`. Third, and also caused by the first, every `ACTIVE` agreement hubbed at that facility moves to `SUSPENDED`, which cancels each of their live consults and releases the assigned neurologists exactly as §3.1 describes. Two consecutive denials therefore take a facility out of the network entirely, and the second denial's cascade reaches patients who were mid-consult when it landed.

**Publication** takes no request body and requires an `ACCEPTED` report whose `decision` is `CERTIFIED` or `CONDITIONAL`, and a facility whose `certification_status` is not `SUSPENDED` or `WITHDRAWN` (`ERR_CENTER_NOT_CERTIFIED`) — a facility can be accepted on one report and suspended on the strength of a later one before the first is published, and in that case the publication is refused. On success the report's `status` becomes `PUBLISHED` and `published_at` is stamped from the logical clock. The facility's public figure is then refreshed: `public_dtn_compliance_pct` is set to this report's stored `dtn_60_compliance_pct` rounded to **one** decimal place half up, and `public_report_published_at` is set to the logical clock. The rollup overwrites outright — it is the most recently published report's figure, never an average across published reports — so 100.00 publishes as 100.0, 66.67 as 66.7, and 33.33 as 33.3. Publishing a `SUBMITTED` report is `ERR_INVALID_REPORT_STATE`.

**A reviewer may also suspend a facility directly**, supplying a `suspension_reason`, from `PROVISIONAL`, `CERTIFIED` or `CONDITIONAL`. Suspending a facility that is already `SUSPENDED`, or one that is `WITHDRAWN`, is `ERR_INVALID_CENTER_STATE`. The cascade runs four hops deep and is the widest in the system. The facility's `certification_status` becomes `SUSPENDED` with the reason recorded, and its `ems_routing_posture` becomes `BYPASS`. Then every `ACTIVE` agreement hubbed at that facility moves to `SUSPENDED` with a `suspension_reason` of 'hub certification suspended'. Then every consult on those agreements whose `status` is `REQUESTED`, `ASSIGNED` or `IN_SESSION` moves to `CANCELLED` with a `cancellation_reason` of 'agreement suspended'. Then each affected agreement's `active_consult_count` is recomputed to 0, each released neurologist has `active_consult_count` lowered and returns from `IN_CONSULT` to `ON_CALL` without any cooldown being started, and a system-detected `ProtocolDeviation` of type `CONSULT_UNFILLED` and severity `MAJOR` is opened against each affected case — because unlike a case abort, a hub going dark leaves a real patient without a neurologist, and that is a protocol deviation worth recording.

Recovery is deliberately incomplete. A `SUSPENDED` facility can be brought back to `CONDITIONAL` by an accepted report, which clears its `suspension_reason` and resets `consecutive_denied_report_count` to 0 — but it does **not** automatically reactivate the agreements the suspension cascade knocked down. Each of those must be activated again by hand, and only then can consults route under it. Restoring a facility's certification and restoring its coverage are two separate acts of administration.
