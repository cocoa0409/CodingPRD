# Title IX Case Management API — Product Requirements Document

## 1. Introduction

Universities that receive federal funding carry a non-delegable obligation to respond to reports of sex-based misconduct through a prompt, equitable, and meticulously documented process. This document specifies the API for a Student Conduct & Title IX Case Management system operated by a university's Title IX office. The platform covers the full life of a case: report intake and the jurisdiction/scope determination that decides whether Title IX applies at all; supportive measures and no-contact directives that protect the parties while a matter is pending; investigation assignment and evidence gathering; the advisor and notice rights that due process guarantees both parties; the live hearing with advisor-conducted cross-examination; a deterministic sanctioning matrix; an appeal track with remand; an informal resolution option; and the recordkeeping and annual statistical reporting that federal compliance demands.

Two design commitments shape everything that follows. First, **due process is structural, not aspirational**: the same person may never occupy two official functions on one case, the complainant and respondent receive mirrored notice rights, evidence review windows and appeal deadlines have exact, inclusive boundaries, and every consequential action is appended to an immutable audit trail. Second, **time is deterministic**: the server runs on a logical clock rather than wall-clock time, so deadlines, expiries, and retention sweeps are reproducible and testable. All resources are mounted under `/api`, and all endpoints speak the single response envelope defined in §2.2.

## 2. Global Specifications & System-Wide Principles

This section fixes the system-wide contract: identity and roles, response envelopes, pagination, the logical clock, audit and retention, segregation of duties, scoring and sanctioning mathematics, concurrency control, and the order in which validations fire.

### 2.1. User and Role-Based Access Control

Every request must carry two HTTP headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the capacity in which they act. The system recognizes exactly seven roles, spelled precisely as follows: `TitleIXCoordinator`, `Investigator`, `DecisionMaker`, `AppealOfficer`, `Party`, `Advisor`, and `CaseAdministrator`. A request whose role header is missing, malformed, or names no declared role — or whose `X-User-ID` is missing — is rejected with `ERR_UNAUTHENTICATED` (401). When the role is valid but not on the endpoint's declared roles list, the request is rejected with `ERR_FORBIDDEN_ROLE` (403).

Six of the seven roles are **entity-backed**. When `X-User-Role` is `TitleIXCoordinator`, `Investigator`, `DecisionMaker`, `AppealOfficer`, `Party`, or `Advisor`, `X-User-ID` is the `id` of the acting `PartyProfile`; ownership and identity checks on any resource that references a `PartyProfile` compare the resource's foreign-key field to `X-User-ID`, and an entity-backed `X-User-ID` that does not resolve to an existing `PartyProfile` is itself an `ERR_UNAUTHENTICATED` failure. When `X-User-Role` is `CaseAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example, as `actor_id` on a `CaseEvent`) but never compares it to any entity's `id`.

The roles partition as follows. A `TitleIXCoordinator` owns triage: jurisdiction review, dismissal, supportive measures, directives, investigator and appeal-officer assignment, informal-resolution oversight, and statistics publication. An `Investigator` gathers and rules on evidence and builds the evidence packet. A `DecisionMaker` runs the live hearing, rules on cross-examination relevance, and drafts and issues the determination. An `AppealOfficer` decides appeals. A `Party` is the complainant or respondent on a case, identity-bound to that case's party fields. An `Advisor` serves a party — chosen by the party or appointed by the university — and conducts cross-examination. A `CaseAdministrator` performs operational duties: directory registration, the logical clock, the retention purge, and reconciliation runs.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints paginate through two query parameters. The `limit` parameter caps the number of returned items; it defaults to 10, with a minimum of 1 and a maximum of 100. The `offset` parameter skips a number of items and defaults to 0. Unless otherwise specified, every list endpoint returns resources sorted by `created_at` in ascending order; ties on `created_at` are broken by insertion order (the server's monotonic record sequence), and the same insertion-order fallback closes any remaining tie in every timestamp-pinned ordering this document defines. A `limit` or `offset` that does not parse as an integer, a `limit` outside 1 through 100, or a negative `offset` is rejected with `ERR_INVALID_REQUEST` (400) rather than clamped. Paginated list responses include `limit`, `offset`, `total_count`, and `has_more` in the `meta` object of the envelope.

### 2.4. The Logical Clock and Common Resource Properties

All temporal semantics in the system — intake timestamps, notice send times, deadlines, review windows, expiries, retention — read a single **logical clock**, never the host wall clock. At server startup the logical clock is exactly `2026-08-01T00:00:00Z`, and it must not fall back to wall-clock time under any circumstance. A `CaseAdministrator` may advance or set the clock through a test-driving capability that accepts a `to_iso8601` instant and echoes the new `current_utc` in its response. Setting the clock does not by itself fire any state transitions; clock-gated changes are applied per case by the reconciliation run described in §3.8.

Every primary resource carries a standard set of system-managed fields. The `id` is a server-minted UUID with no type prefix. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording creation; `updated_at` is the same kind of timestamp refreshed on every mutation. These two bookkeeping fields — and the envelope's `api_request_timestamp` — are stamped from the host wall clock, not the logical clock; the logical clock drives only the business instants (intake, notice send times, deadlines, windows, expiries, retention), which are rendered at whole-second precision, and every instant the server parses or compares is truncated to whole seconds. `version` is an integer that starts at 1 and increments by one on every mutation of the resource — including mutations the server applies automatically through cascades — and it anchors the optimistic-concurrency rules of §2.10. Two resources are deliberately thinner: a `Notice` and a `CaseEvent` are immutable records that carry only `id` and `created_at`; both `updated_at` and `version` are absent on them.

### 2.5. The Case Audit Trail and Records Retention

Every consequential mutation on a case or one of its descendants appends a row to that case's **audit trail**. Each audit row records an `event_type` drawn from a fixed vocabulary of fifty-seven event names (each is introduced in §3 next to the workflow that emits it), the acting `actor_role` and `actor_id` taken from the request headers — or the literal string `system` when a cascade or clock-driven transition fired the event — a `details` payload capturing the changed fields and their values, and an `occurred_at` logical-clock timestamp. Workflow-emitted auto-notices (§3.4) are not cascades in this sense: their `NOTICE_SENT` rows record the triggering request's actor, while supersession, dismissal-cascade, review-close, and expiry rows record `system`. The trail is append-only: nothing updates or deletes individual rows outside the retention sweep. Reading the audit log is a staff privilege extended to `TitleIXCoordinator`, `CaseAdministrator`, `Investigator`, `DecisionMaker`, and `AppealOfficer`; parties and advisors may not read it. The log can be filtered by `event_type`.

Retention is deliberate and narrow. A retention sweep, run by a `CaseAdministrator`, permanently deletes audit-trail rows belonging to cases in a terminal state — or in `DISMISSED`, which carries a `closed_at` and is included in the sweep — whose closure is at least seven years old: a case whose `closed_at` plus seven years is on or before the current logical clock qualifies, the boundary included. The seven-year addition is calendrical, with a February 29 `closed_at` clamping to February 28 of the target year. The sweep returns the `purged_event_count` and the list of `purged_case_ids`; a qualifying case appears in `purged_case_ids` only when at least one of its event rows was actually purged. Cases themselves and all annual statistics are preserved; only event rows are purged.

### 2.6. Segregation of Duties, Party Binding, and Confidentiality

A single case may involve up to five **official functions**: the coordinator named at intake, an investigator, a hearing decision-maker, an appeal officer, and an informal-resolution facilitator. Segregation of duties forbids any one person from holding more than one of those functions on the same case. The bar is deliberately strict in two directions. First, investigator history never washes out: any investigator assignment on the case in `PROPOSED`, `ACTIVE`, or `COMPLETED` status counts as holding the investigator function, so having once served as investigator permanently bars that person from the decision-maker, appeal-officer, or facilitator functions on that case even after the assignment completes. Second, recusal is permanent: a person recused on a case may never be re-proposed to any official function on that case. The remaining functions fix their holding scopes as follows: the decision-maker function is held by the named `decision_maker_id` of every hearing on the case whatever the hearing's status (even `CANCELLED`); the appeal-officer function by the assigned `appeal_officer_id` of every appeal on the case, decided or not; and the facilitator function only while its informal resolution is live (`PROPOSED` or `IN_PROGRESS`) — a withdrawn, terminated, or resolved resolution releases the facilitator function, so the same person may be proposed as facilitator again on a later resolution of the same case. A violation of these rules is rejected with `ERR_SEGREGATION_OF_DUTIES` (422). Independently, no official may be the case's complainant or respondent; that more specific failure is rejected with `ERR_OFFICIAL_IS_CASE_PARTY` (422). The party-specific check fires on proposing an investigator, scheduling a hearing, beginning appeal review, and proposing informal resolution; the broader segregation check fires on those same four operations and additionally when the proposed investigator accepts an assignment, where the re-check compares against the case coordinator, every other assignment's investigator in `PROPOSED`, `ACTIVE`, or `COMPLETED` status, every hearing decision-maker, every appeal officer, and every facilitator on the case, and confirms the acceptor is neither party.

Read access has its own perimeter. A `Party` reader may read only cases where the actor's identity equals the case's `complainant_id` or `respondent_id`, together with the descendants of such cases; an `Advisor` reader may read only cases where the actor holds an advisor appointment of any status. An unaffiliated read is rejected with `ERR_CASE_ACCESS_DENIED` (403) and is deliberately indistinguishable from ordinary authorization failure — the reader learns nothing about the case's existence beyond what an authorization denial reveals. Staff roles (`TitleIXCoordinator`, `CaseAdministrator`, `Investigator`, `DecisionMaker`, `AppealOfficer`) read without affiliation restrictions.

Supportive measures carry a stricter confidentiality scope. Every measure's `is_confidential` flag is always true: the other party must not learn the measure exists. A `Party` single-read of a measure is limited to measures whose `party_side` covers the reader — a complainant reads `COMPLAINANT` measures, a respondent reads `RESPONDENT` measures, and a `BOTH` measure is visible to both parties. Reading a measure scoped only to the other party is rejected with `ERR_SUPPORTIVE_MEASURE_CONFIDENTIAL` (403). Notices follow the party-visibility convention as well: a party sees notices addressed to their own side or to `BOTH`.

### 2.7. Case Exposure Scoring and Interim Suspension Eligibility

Each case carries a continuously maintained **exposure score** that feeds the interim-suspension eligibility flag. The score is recomputed on four occasions: when the case is created (producing the initial value), when a directive violation on the case is substantiated, and when a no-contact directive on the case is created, lifted, or expires — the latter three because they change whether any directive on the case is `ACTIVE`. The most recently computed value is stored on the case as `exposure_score`.

The score is integer arithmetic with no rounding and has four components. The first is a **category base**: take the alleged-conduct category in the case's `categories` with the highest hierarchy priority and score it by the fixed base table — `SEXUAL_ASSAULT` 40, `DATING_VIOLENCE` 35, `DOMESTIC_VIOLENCE` 35, `STALKING` 30, `SEXUAL_HARASSMENT` 25, `OTHER_SEX_BASED` 15, `NON_TITLE_IX_MISCONDUCT` 0. Hierarchy priority descends in exactly that order: `SEXUAL_ASSAULT` has priority 7, then `DATING_VIOLENCE` 6, `DOMESTIC_VIOLENCE` 5, `STALKING` 4, `SEXUAL_HARASSMENT` 3, `OTHER_SEX_BASED` 2, and `NON_TITLE_IX_MISCONDUCT` 1. The second component is **prior findings**: 15 points for each *other* case — any case whose id differs from this case's — on which the same `respondent_id` has a determination in `ISSUED`, `FINAL`, or `SUPERSEDED` status with a `responsibility_finding` of `RESPONSIBLE`; determinations in `REVERSED` status are excluded from the count. The third component is **violation history**: 10 points for each substantiated directive violation on the case's directives whose `substantiated_at` falls within the rolling window from 365 days before the evaluation instant through the evaluation instant itself — both window bounds are inclusive. (For audit output the violations are processed in `substantiated_at` ascending order with ties broken by `created_at` ascending; the order affects only audit presentation, never the count.) The fourth component is a flat 10 points when any no-contact directive on the case currently has `ACTIVE` status, and zero otherwise.

A case becomes **interim-suspension eligible** when its score reaches the threshold of 70, and that boundary is inclusive: a score of exactly 70 confers eligibility, 69 does not. The flag `interim_suspension_eligible` reflects the most recent computation — it is true precisely when the last computed score was at least 70. Worked example: a case with `categories` of `SEXUAL_ASSAULT` and `STALKING` takes the `SEXUAL_ASSAULT` base of 40 (priority 7 beats 4). The respondent has one prior responsible finding on another case, adding 15. Two substantiated violations fall inside the rolling 365-day window, adding 20. One directive on the case is `ACTIVE`, adding 10. The total, 40 + 15 + 20 + 10 = 85, is at least 70, so `interim_suspension_eligible` becomes true.

### 2.8. Procedural Deadlines, Lead Times, and Window Boundaries

Federal process lives and dies on exact timing, so every window in the system has a stated length and an explicit inclusivity rule.

**Notice lead times.** An `INTERVIEW` notice must give at least 5 days of lead and a `HEARING` notice at least 10 days: the gap between the notice's `scheduled_event_at` and its `sent_at` must be at least the required lead days expressed in seconds (86,400 seconds per day), and a gap of exactly the required lead passes — the comparison is inclusive. Non-event notice types (`ALLEGATIONS`, `EVIDENCE_RELEASE`, `DETERMINATION`, `DISMISSAL`, `APPEAL_FILED`, `APPEAL_OUTCOME`, `INFORMAL_PROPOSAL`) always have `lead_time_sufficient` set to true. The hearing lead rule is re-checked at hearing scheduling: the hearing's `scheduled_at` must be at least 10 days after the scheduling instant, in addition to being strictly in the future. A shortfall is rejected with `ERR_NOTICE_LEAD_TIME_INSUFFICIENT` (422); a `scheduled_at` that is not strictly in the future is rejected with `ERR_HEARING_TIME_CONFLICT` (422).

**Evidence review window.** A released evidence packet gives both parties 10 days to respond: `review_closes_at` is exactly `released_at` plus 10 days. A review response submitted at a logical instant on or before `review_closes_at` is timely — the close instant itself is inclusive — and a response even one second later is rejected with `ERR_REVIEW_RESPONSE_LATE` (422). The packet closes its review at the *earlier* of two moments: the instant both parties' responses have been recorded, or a reconciliation observing the clock at or past `review_closes_at`.

**Appeal window.** An issued determination sets its `appeal_deadline` to `issued_at` plus 5 days; a dismissal's deadline is the case's `closed_at` plus 5 days. An appeal filed at exactly the deadline instant is timely — the boundary is inclusive — and a filing strictly after it is rejected with `ERR_APPEAL_WINDOW_EXPIRED` (422). Closing a case without appeal requires the stronger comparison: the logical clock must be *strictly later* than the appeal deadline, so the full window has elapsed.

**Measure and directive windows** are half-open intervals: the window includes its `effective_from` instant and excludes its `effective_to` instant. A null `effective_to` means the window is open-ended and never auto-expires. When `effective_to` is set, expiry fires as soon as the logical clock reaches that instant. Two `ACTIVE` no-contact directives on the same case and a shared party scope — where a `MUTUAL` directive shares both party scopes — must not overlap as half-open intervals unless the new directive is created with supersession (only `ACTIVE` directives participate in the overlap test; `LIFTED`, `EXPIRED`, and `SUPERSEDED` windows never block creation); adjacency is allowed, meaning a new directive whose `effective_from` equals an existing directive's `effective_to` (zero gap) does not overlap. An improper overlap is rejected with `ERR_DIRECTIVE_WINDOW_OVERLAP` (422).

**Hearing calendar.** A hearing occupies the half-open interval from its `scheduled_at` through `scheduled_at` plus its `estimated_duration_minutes`. For any one decision-maker, the occupancy intervals of that person's non-cancelled hearings must neither overlap nor sit closer than a 60-minute buffer on either side: a gap of exactly 60 minutes passes, and a gap of 59 minutes fails. Conflicts are rejected with `ERR_HEARING_TIME_CONFLICT` (422).

**Rolling violation window.** The rolling substantiated-violation count of §2.7 covers the interval from 365 days before the evaluation instant through the instant itself, both ends inclusive.

**Statistics window.** Annual statistics include cases whose `received_at` falls on or after January 1 of the statistics year at 00:00:00 UTC and strictly before January 1 of the following year at 00:00:00 UTC — lower bound inclusive, upper bound exclusive. The resolved-case set used for average resolution days additionally requires `closed_at` to be strictly before that following January 1 boundary.

**Retention boundary.** The retention sweep of §2.5 purges an event row when the owning case's `closed_at` plus seven years is on or before the logical clock — an inclusive boundary.

**Sanction duration boundary.** A duration-bearing sanction completes when the logical clock reaches `effective_from` plus `duration_days` — again inclusive.

### 2.9. Severity Scoring, the Sanctioning Matrix, and Restitution

Sanctioning is deterministic. A determination's **severity score** is computed twice under two named variants, and the final computation — combined with restitution points in a pinned evaluation order — places the case in one of four tiers that bound every sanction selection.

The score uses the same category base table as the exposure score (`SEXUAL_ASSAULT` 40, `DATING_VIOLENCE` 35, `DOMESTIC_VIOLENCE` 35, `STALKING` 30, `SEXUAL_HARASSMENT` 25, `OTHER_SEX_BASED` 15, `NON_TITLE_IX_MISCONDUCT` 0), again choosing the single category in the case's `categories` with the highest hierarchy priority per the §2.7 ordering. To that base the formula adds 15 points per entry of the determination's `prior_responsible_findings`, 10 points per entry of its `aggravating_factor_count`, and 10 points for each substantiated directive violation on the case *counted all-time* — unlike the exposure score's rolling window, every violation ever substantiated on the case contributes. Finally the formula subtracts 5 points per entry of `mitigating_factor_count`, but only under the FINAL variant. Under the PROVISIONAL variant — computed at determination-draft creation and stored as `provisional_severity_score` — the mitigating contribution is zero, because mitigations are unverified until issue. A consequence implementers must honor: for otherwise identical inputs, `provisional_severity_score` can be strictly greater than `final_severity_score`. The FINAL variant runs at issue and produces `final_severity_score`. All arithmetic is integer arithmetic.

Worked example: a case whose sole category is `SEXUAL_HARASSMENT` starts at 25. The draft attests `prior_responsible_findings` 1, `aggravating_factor_count` 2, and `mitigating_factor_count` 1, and the case has one substantiated violation all-time. The provisional score is 25 + 15 + 20 − 0 + 10 = 70; the final score is 25 + 15 + 20 − 5 + 10 = 65.

**Tier bands** have inclusive lower bounds: a score from 0 through 24 is `TIER_1`; 25 through 49 is `TIER_2`; 50 through 74 is `TIER_3`; 75 and above is `TIER_4`. The final tier governs which sanction types may be selected and the inclusive duration bounds for each:

- `TIER_1` allows `WARNING`, `EDUCATIONAL_PROGRAM` from 1 to 30 days, and `PROBATION` from 1 to 90 days.
- `TIER_2` allows `EDUCATIONAL_PROGRAM` from 1 to 60 days, `PROBATION` from 30 to 180 days, `SUSPENSION` from 1 to 90 days, and `NO_CONTACT_CONTINUATION` from 1 to 180 days.
- `TIER_3` allows `PROBATION` from 91 to 365 days, `SUSPENSION` from 91 to 365 days, `RESTITUTION`, and `NO_CONTACT_CONTINUATION` from 1 to 365 days.
- `TIER_4` allows `SUSPENSION` from 180 to 730 days, `EXPULSION`, `RESTITUTION`, and `NO_CONTACT_CONTINUATION` from 1 to 730 days.

A selection whose type is not offered by the final tier, or whose `duration_days` falls outside the tier's inclusive bounds for that type, is rejected with `ERR_SANCTION_OUTSIDE_MATRIX` (422).

**Restitution** participates in the score through a pinned, seven-step evaluation order that resolves what would otherwise be a circular dependency (the cap depends on the tier, but restitution points move the tier). Step 1: compute the matrix score under the FINAL variant — mitigating factors included. Step 2: round each restitution item *first*, individually: each item's `amount_dollars` is multiplied by 100 and rounded half-up to whole cents, and only then are the per-item cent values summed. The alternative order — summing raw dollars and rounding once — is forbidden because it yields different cents: two items of 1.005 dollars each produce 101 + 101 = 202 cents per-item, versus 201 cents when summed first. Step 3: determine the **cap tier** from the matrix score alone, without restitution points, and look up the restitution cap: `TIER_1` 0 cents, `TIER_2` 0 cents, `TIER_3` 50,000 cents (500 dollars), `TIER_4` 250,000 cents (2,500 dollars). Step 4: the sanction's `applied_restitution_cents` is the smaller of the summed cents and the cap — except that when the cap is zero (cap tier `TIER_1` or `TIER_2`), a `RESTITUTION` selection is rejected with `ERR_SANCTION_OUTSIDE_MATRIX` rather than clamped to zero. Step 5: restitution points are the applied cents divided by 100 (one point per full dollar) rounded down to a whole number. Step 6: total points are the matrix score plus the restitution points. Step 7: `final_tier` is the tier band of that total, and it governs the duration bounds for *all* sanction selections on the determination. Two consequences are deliberate: the restitution cap remains the cap-tier cap from step 3 even when `final_tier` lands above the cap tier, and `applied_restitution_cents` is zero for every non-`RESTITUTION` sanction.

Worked example continued: the final matrix score of 65 lands in `TIER_3`, so the cap tier is `TIER_3` with a 50,000-cent cap. A restitution selection listing one item — a 450-dollar replacement — converts to 45,000 cents per item (450.00 × 100, already whole), sums to 45,000, clamps under the cap unchanged, and earns 450 restitution points (45,000 divided by 100, floored). Total points are 65 + 450 = 515, so `final_tier` is `TIER_4` even though the cap remains the `TIER_3` value of 50,000 cents. Duration bounds for every selection on that determination now come from `TIER_4`.

Monetary precision: restitution amounts enter in dollars as `amount_dollars`, convert to integer cents by the per-item round-half-up rule above, and all downstream arithmetic (caps, floors, point conversion) is integer-cent arithmetic. The one non-integer statistic in the system, `avg_resolution_days` of §3.8, rounds half-up to a single decimal place as its final step.

### 2.10. Optimistic Concurrency Control on Create-With-Supersede Writes

Exactly three write endpoints take part in optimistic concurrency control, and each requires the non-optional request field `expected_case_version`, carrying the client's last observed `version` of the parent case. If that value does not equal the case's current `version` at write time — because another writer has advanced the case's version since the client last read it — the request is rejected with `ERR_STALE_CASE_VERSION` (HTTP 412), forcing the client to re-read the case before writing.

The three guarded creates, and the reason each deserves protection:

- **Creating an evidence packet** against a case legitimately supersedes a `FINALIZED` predecessor packet (§3.3); a second create based on a pre-supersede view of the case would otherwise double-supersede.
- **Creating a determination draft** legitimately supersedes an existing `DRAFT`, and on a remanded case continues a lineage whose prior determinations were superseded by the remand (§3.5); a writer working from a pre-remand view of the case must restart from the current version.
- **Creating a no-contact directive** with `supersede_existing` legitimately truncates the overlapping `ACTIVE` directive (§3.2); a writer whose view of the directive set is stale must re-read the case first.

No other endpoint takes a version field: endpoints absent from this list process mutations without an OCC check.

### 2.11. Validation Order and Nested Resource Resolution

Every request is evaluated against the validation tiers in a fixed ascending priority order, and the first failing tier short-circuits the remainder. When several failures exist in one request, the error the client sees is the one from the earliest tier:

1. **Authentication** — the headers and identity rules of §2.1, failing as `ERR_UNAUTHENTICATED`.
2. **Role authorization** — the acting role must appear in the endpoint's declared roles list, failing as `ERR_FORBIDDEN_ROLE`.
3. **Existence** — path-template identifiers are resolved strictly left to right: the case id before any nested child id, the directive id before a violation under it, the hearing id before a question under it; the first unresolvable identifier in the path fails as `ERR_NOT_FOUND` (404). Body foreign-key fields that name people — `complainant_id`, `respondent_id`, `coordinator_id`, `investigator_id`, `advisor_id`, `decision_maker_id`, `appeal_officer_id`, `facilitator_id`, `asked_by_advisor_id` — must likewise resolve to existing `PartyProfile` rows, failing as `ERR_NOT_FOUND`.
4. **State** — the target entity must be in a from-state from which the requested transition exists in its machine, with terminal states rejecting all further transitions (`ERR_INVALID_STATE_TRANSITION`, 409); and, for child-mutation endpoints nested under a case, the case must not be in `CLOSED`, `REFERRED_TO_CONDUCT`, or `RESOLVED_INFORMAL` (`ERR_CASE_ALREADY_TERMINAL`, 409). Terminal cases therefore admit no case-nested creates and no case-level transitions, with only the audit-trail listing, annual statistics, and the retention purge reaching them, and filing an appeal on a `DISMISSED` case is expressly exempt from this guard (§3.6). Mutations addressed directly to a child resource rather than nested under the case path — terminating a measure, lifting a directive, reporting a violation, withdrawing an advisor appointment, marking a duration-less sanction complete, accepting, declining, or recusing an investigator assignment, adjourning, reconvening, or cancelling a hearing — carry no terminal-case guard at all and are governed by the resource's own state machine even when the owning case is terminal; among child-addressed mutations only the two violation-decision endpoints add their own terminal-case check (§3.2). On case-nested endpoints this terminal guard, and the target's own from-state gate, fire immediately after the path target resolves — ahead of the tier-3 request-body foreign-key checks; the one exception is cross-exam-question creation, which resolves `asked_by_advisor_id` before the hearing's from-state gate.
5. **Safety** — segregation of duties and the party-as-official bar (§2.6), the employee-respondent/student-complainant informal-resolution prohibition, the complainant-only formal-complaint rule, jurisdiction facts, advisor presence at convene, cross-examiner eligibility, supportive-measure confidentiality, advisor eligibility, the standard-of-evidence pin, and party/advisor affiliation scoping.
6. **Temporal** — notice lead times, the allegations-before-interview notice ordering, evidence-review timeliness and premature finalization, the appeal filing window, the hearing calendar and buffer, and directive window overlap (all §2.8).
7. **Constraint** — the one-live-packet, one-live-hearing, one-live-informal-resolution, and one-active-investigator singletons; the signed-complaint prerequisite for informal resolution; the active-investigator prerequisite for evidence and packet work; the zero-pending-questions gate; the sanctioning matrix; duplicate-advisor, duplicate-response, duplicate-resource, and empty-advisor-pool rejections.
8. **Referential** — appeal target appealability, appeal outcome compatibility, remand-scope consistency, party binding, hearing decision-maker identity, and assigned appeal-officer identity.
9. **Fiscal** — restitution item presence and positivity, and statistics-year validity.
10. **OCC staleness** — the `expected_case_version` comparison of §2.10, failing as `ERR_STALE_CASE_VERSION`.
11. **Request schema** — missing required fields, wrong types, unknown enum members, empty arrays where a non-empty array is required, and malformed datetimes, failing as `ERR_INVALID_REQUEST` (400). Schema conformance is deliberately evaluated *last*: a request that violates both a business rule and the request schema receives the business-rule error.

## 3. Business Logic & Workflows

This section walks the life of a case in business order — intake, interim safety, investigation, hearing, determination, appeal, informal resolution, and recordkeeping — with each rule stated next to the workflow that needs it. Every state name in backticks is an exact enumeration value.

### 3.1. Report Intake, Jurisdiction Review, and Dismissal

Before any case exists, people must exist. Registering a person in the university directory — an operation open to `CaseAdministrator` and `TitleIXCoordinator` — records a `full_name`, a university-issued `university_id`, a `role_type` of `STUDENT`, `EMPLOYEE`, `FACULTY`, `STAFF`, or `EXTERNAL`, a contact `email`, and an optional `advisor_eligible` flag that defaults to false and marks whether the person may serve as a university-appointed advisor. The `university_id` must be unique across the directory; a duplicate registration is rejected with `ERR_DUPLICATE_RESOURCE` (409). The directory can be listed with `role_type` and `advisor_eligible` filters, and any role — including `Party` and `Advisor` — may read a single directory entry.

A case begins when a `TitleIXCoordinator` or `CaseAdministrator` records a report. The intake payload names the `complainant_id`, the `respondent_id`, and the `coordinator_id` of the coordinator who will own the matter — each resolving to a directory entry — plus a non-empty `categories` array drawn from `SEXUAL_HARASSMENT`, `SEXUAL_ASSAULT`, `DATING_VIOLENCE`, `DOMESTIC_VIOLENCE`, `STALKING`, `OTHER_SEX_BASED`, and `NON_TITLE_IX_MISCONDUCT`; the alleged incident time `occurred_at`; the two jurisdiction facts `occurred_in_program_activity` and `occurred_in_united_states`; the `received_via` channel (`ONLINE_FORM`, `IN_PERSON`, `EMAIL`, `THIRD_PARTY`, or `ANONYMOUS`); and an optional `standard_of_evidence` of `PREPONDERANCE` or `CLEAR_AND_CONVINCING`, defaulting to `PREPONDERANCE`. That standard is **pinned at intake and immutable** for the life of the case, and the same standard applies to both parties. At intake the server mints the human reference `report_number` in the form RPT-<received year>-<sequence within that received year, zero-padded to four digits>, stamps `received_at` from the logical clock, computes the initial exposure score per §2.7, appends `REPORT_RECEIVED` to the audit trail, and lands the case in `RECEIVED`. Intake imposes no distinctness check among `complainant_id`, `respondent_id`, and `coordinator_id`. The case register is staff-only and can be filtered by `status`, `category`, `complainant_id`, `respondent_id`, `coordinator_id`, or `received_year`; the `category` filter matches any case whose `categories` array contains the given value, and a non-integer `received_year` is rejected with `ERR_INVALID_REQUEST` (400). The directory's `advisor_eligible` filter treats the query value `true` (case-insensitively) as true and any other supplied value as false. Every record nested under a case — supportive measures, directives and their violation reports, investigator assignments, evidence items and packets, notices, advisor appointments, hearings, determinations, appeals, informal resolutions, and audit events — carries the owning case's `case_id`.

From `RECEIVED`, the only way forward is jurisdiction review. The coordinator — whose `X-User-ID` must equal the case's `coordinator_id`, failing as `ERR_FORBIDDEN_ROLE` (403) — begins it, moving the case `RECEIVED → JURISDICTION_REVIEW`, appending `JURISDICTION_REVIEW_STARTED`, and incrementing the case's `version` by 1.

Confirming jurisdiction is the fork that decides whether Title IX governs the matter at all. It succeeds only when both jurisdiction facts are true — the incident occurred within an education program or activity *and* the complainant was in the United States — *and* the `categories` contain at least one Title IX category among `SEXUAL_HARASSMENT`, `SEXUAL_ASSAULT`, `DATING_VIOLENCE`, `DOMESTIC_VIOLENCE`, `STALKING`, and `OTHER_SEX_BASED`; a report carrying only `NON_TITLE_IX_MISCONDUCT` can never be confirmed. A confirmation attempt that fails any leg is rejected with `ERR_JURISDICTION_REQUIREMENTS_UNMET` (422). Confirmation is not ownership-bound: any `TitleIXCoordinator` may confirm. On success the case moves `JURISDICTION_REVIEW → AWAITING_FORMAL_COMPLAINT`, appends `JURISDICTION_CONFIRMED`, and increments `version`.

While the case awaits, only the complainant may set the formal process in motion. Filing the signed formal complaint requires the actor's identity to equal the case's `complainant_id`; anyone else's attempt is rejected with `ERR_ONLY_COMPLAINANT_MAY_FILE` (422). Filing moves the case `AWAITING_FORMAL_COMPLAINT → INVESTIGATION`, sets `formal_complaint_signed` to true, stamps `formal_complaint_filed_at` from the logical clock, automatically issues an `ALLEGATIONS` notice to `BOTH` parties — this auto-notice is the prerequisite for any later `INTERVIEW` notice — appends `FORMAL_COMPLAINT_FILED`, and increments `version`.

**Dismissal** is available to the coordinator from several stages — any `TitleIXCoordinator` may dismiss, not only the case's owning coordinator — always with a `dismissal_reason` of `MANDATORY_NO_JURISDICTION`, `DISCRETIONARY_COMPLAINANT_WITHDRAWN`, `DISCRETIONARY_RESPONDENT_DEPARTED`, or `DISCRETIONARY_EVIDENCE_UNAVAILABLE` and a required boolean `refer_to_conduct`, and always ending in the `DISMISSED` status — except at the jurisdiction stage, where the referral flag changes the destination. From `JURISDICTION_REVIEW`, dismissal with `refer_to_conduct` false lands in `DISMISSED` and appends `CASE_DISMISSED`; dismissal with `refer_to_conduct` true instead lands in `REFERRED_TO_CONDUCT` and appends `CASE_REFERRED`. From `AWAITING_FORMAL_COMPLAINT`, only the plain form exists — a referral request from that state matches no transition and is rejected with `ERR_INVALID_STATE_TRANSITION` (409). Dismissal is also available from `INVESTIGATION`, `EVIDENCE_REVIEW`, `HEARING_PREPARATION`, and `INFORMAL_RESOLUTION_IN_PROGRESS`, always into `DISMISSED` and always with `refer_to_conduct` false. Every dismissal, from every stage, sets `dismissal_reason`, stamps `closed_at` from the logical clock, issues a `DISMISSAL` notice to `BOTH` parties, and increments `version`. Two stages add cascades: dismissing from `INVESTIGATION` or `HEARING_PREPARATION` cancels any hearing of the case in `SCHEDULED` or `ADJOURNED` status (each appending `HEARING_CANCELLED`), and dismissing from `INFORMAL_RESOLUTION_IN_PROGRESS` terminates the live resolution — a resolution in `PROPOSED` or `IN_PROGRESS` moves to `TERMINATED` with `INFORMAL_TERMINATED` appended. `DISMISSED` is not an ordinary terminal state: it is appealable, and reinstatement on appeal returns the case to `AWAITING_FORMAL_COMPLAINT` with `dismissal_reason` and `closed_at` cleared (§3.6). The genuinely terminal statuses are `CLOSED`, `REFERRED_TO_CONDUCT`, and `RESOLVED_INFORMAL`.

Three deliberate cycles exist in the case machine: a remand loop (`REMANDED` back into `INVESTIGATION` or `HEARING_PREPARATION` and forward again to `APPEAL_REVIEW`), an informal-resolution withdrawal loop (`INVESTIGATION` or `EVIDENCE_REVIEW` into `INFORMAL_RESOLUTION_IN_PROGRESS` and back to `INVESTIGATION`), and the reinstatement loop (`DISMISSED → AWAITING_FORMAL_COMPLAINT`).

### 3.2. Supportive Measures, No-Contact Directives, and Violations

Supportive measures are available from `RECEIVED` onward — they do not wait for a formal complaint. The coordinator creates one with a `measure_type` of `COUNSELING`, `COURSE_ADJUSTMENT`, `HOUSING_CHANGE`, `SCHEDULE_CHANGE`, `EXTENSION`, `ESCORT`, `SAFETY_PLAN`, or `OTHER`; a `party_side` of `COMPLAINANT`, `RESPONDENT`, or `BOTH` fixing its confidentiality scope per §2.6; a free-text `description`; an inclusive `effective_from`; and an optional exclusive `effective_to` whose absence leaves the measure open-ended and exempt from auto-expiry. Creation lands the measure in `ACTIVE`, raises the owning case's `active_supportive_measure_count` by one, appends `MEASURE_CREATED`, and increments the case's `version`. Terminating an `ACTIVE` measure early moves it to `TERMINATED`, lowers `active_supportive_measure_count` by one, appends `MEASURE_TERMINATED`, and increments the case `version`. Reconciliation (§3.8) expires any `ACTIVE` measure whose `effective_to` is set and reached by the clock, moving it to `EXPIRED` with the same count decrement and a `MEASURE_EXPIRED` event. The count is maintained on every measure mutation, so it always equals the number of `ACTIVE` measures on the case. Measures on a case can be listed with `status` and `party_side` filters; party readers see only the measures covering their own side plus `BOTH`, and the single-measure read enforces §2.6's confidentiality rejection.

A no-contact directive is the case's restraining instrument, and its creation is one of the three OCC-guarded writes of §2.10: the request must carry `expected_case_version` equal to the case's current `version`, failing as `ERR_STALE_CASE_VERSION` (412). The coordinator supplies a `party_side` of `COMPLAINANT`, `RESPONDENT`, or `MUTUAL` — a `MUTUAL` directive restrains both parties and occupies both party scopes for overlap purposes — a non-empty `restrictions` array drawn from `IN_PERSON`, `ELECTRONIC`, `THIRD_PARTY`, and `PROXIMITY`, a `proximity_feet` minimum physical separation that is required when `PROXIMITY` appears in the restrictions and is otherwise optional — stored when supplied, null when absent — an inclusive `effective_from`, and an optional exclusive `effective_to`. Window overlap is policed per §2.8: on the same case and a shared scope, overlapping half-open windows are rejected with `ERR_DIRECTIVE_WINDOW_OVERLAP` — unless the creation sets `supersede_existing` true, in which case each overlapping `ACTIVE` directive is superseded: its `effective_to` is truncated to the new directive's `effective_from`, its `superseded_by_directive_id` points at the new directive, it lands in `SUPERSEDED`, and `DIRECTIVE_SUPERSEDED` is appended. Creation lands the directive in `ACTIVE`, recomputes the case exposure score (the 10-point active-directive component now contributes), appends `DIRECTIVE_CREATED`, and increments the case `version`. Lifting an `ACTIVE` directive moves it to `LIFTED`, recomputes the exposure score with the active-directive points removed, appends `DIRECTIVE_LIFTED`, and increments `version`. Reconciliation expires a directive whose `effective_to` is set and reached, moving it to `EXPIRED`, recomputing the score, appending `DIRECTIVE_EXPIRED`, and incrementing `version`. Each directive also carries the computed `substantiated_violation_count`, the number of its violation rows in `SUBSTANTIATED` status. Beyond the per-case list (filters `status`, `party_side`), a staff-only filtered list supports reverse reachability through `superseded_by_directive_id` and `status` — for example, finding every directive a given directive superseded.

Anyone on the staff side, or a party, may report an alleged violation of a directive: the report carries `reported_by_side` (`COMPLAINANT`, `RESPONDENT`, or `STAFF`), the alleged `occurred_at`, and a `description`, and lands in `PENDING` with `VIOLATION_REPORTED` appended. The reporter is not identity-checked: any `Party`-role user — affiliated with the case or not — may file, and `reported_by_side` is asserted by the request without comparison to the actor's identity or role; reporting carries no terminal-case guard. Each report is bound to its parent directive through `directive_id`. Substantiation is a coordinator act on a `PENDING` report; the parent directive may be in any status — even `LIFTED`, `EXPIRED`, or `SUPERSEDED` — but the owning case must not be terminal. Substantiating moves the report `PENDING → SUBSTANTIATED`, stamps `substantiated_at` from the logical clock (this timestamp drives the rolling 365-day window of §2.7), raises the directive's `substantiated_violation_count` by one, recomputes the case exposure score — flipping `interim_suspension_eligible` to true if the score crosses to at least 70 — appends `VIOLATION_SUBSTANTIATED`, and increments the case `version`. Marking a `PENDING` report unsubstantiated — likewise only while the case is not terminal — moves it to `UNSUBSTANTIATED`, appends `VIOLATION_UNSUBSTANTIATED`, and increments `version`. Both outcomes are terminal for the report. Violation lists filter by `status`.

### 3.3. Investigation: Assignments, Evidence Items, and the Evidence Packet

Once a case reaches `INVESTIGATION`, the coordinator proposes an investigator by naming an `investigator_id`. The proposal lands in `PROPOSED` with `INVESTIGATOR_PROPOSED` appended. Two guards fire at proposal: the §2.6 segregation and party bars (`ERR_SEGREGATION_OF_DUTIES`, `ERR_OFFICIAL_IS_CASE_PARTY`), and the singleton rule — while any assignment on the case is `ACTIVE`, a new proposal is rejected with `ERR_INVESTIGATOR_ALREADY_ACTIVE` (409); a recusal must come first.

The proposed investigator answers for themself: the actor's identity must equal the assignment's `investigator_id`, failing as `ERR_FORBIDDEN_ROLE` (403). **Accepting** re-runs the full segregation check at acceptance time — the acceptor must differ from the case coordinator, from every other assignment's investigator in `PROPOSED`, `ACTIVE`, or `COMPLETED` status, from every hearing decision-maker, every appeal officer, and every informal facilitator on the case, and must be neither complainant nor respondent — and it also requires that no other assignment on the case is `ACTIVE` and that the acceptor holds no *other* live (`PROPOSED` or `ACTIVE`) assignment of their own on the case, both failing as `ERR_INVESTIGATOR_ALREADY_ACTIVE` (409) and `ERR_SEGREGATION_OF_DUTIES` (422) respectively; a `COMPLETED` prior assignment of the same person does not bar re-service, which is what lets the remand cycle re-engage a prior investigator. Acceptance moves the assignment `PROPOSED → ACTIVE`, appends `INVESTIGATOR_ACCEPTED`, and increments the case `version`. **Declining** moves it `PROPOSED → DECLINED` with `INVESTIGATOR_DECLINED` and a version increment. **Recusal** applies to the `ACTIVE` assignment and may be invoked by the assigned investigator or by the case coordinator — any other actor fails as `ERR_FORBIDDEN_ROLE` (403); it requires a non-empty `recusal_reason`, which is recorded on the assignment. Recusal moves the assignment `ACTIVE → RECUSED`, appends `INVESTIGATOR_RECUSED`, increments the case `version`, and leaves the case without an active investigator: from that moment, evidence begin-review, relevance ruling, and every packet write on the case (attach-report, release, finalize, withdraw) fail with `ERR_NO_ACTIVE_INVESTIGATOR` (422) until a replacement accepts. The replacement forms a case-level cycle — a new assignment is proposed and accepted — but the recused person may never be re-proposed on this case. Finally, an `ACTIVE` assignment moves to `COMPLETED` automatically when the investigator's packet finalizes (below); `DECLINED`, `RECUSED`, and `COMPLETED` are the assignment's terminal states. Assignments on a case list with a `status` filter, and a staff-only filtered list searches by `investigator_id` and `status`.

Evidence enters from both sides. While the case is in `INVESTIGATION`, a party or the active investigator submits an item with `submitted_by_side` (`COMPLAINANT`, `RESPONDENT`, or `INVESTIGATOR`), an `evidence_type` of `DOCUMENT`, `PHOTO`, `VIDEO`, `MESSAGE_RECORD`, `TESTIMONY_SUMMARY`, or `OTHER`, and a `description`. The item lands in `SUBMITTED`, its `collected_at` stamps from the logical clock, and `EVIDENCE_SUBMITTED` is appended. A `Party` submitter must be a party of the case and name their own side as `submitted_by_side`, failing as `ERR_PARTY_BINDING_MISMATCH` (422); an `Investigator` submitter must hold the case's `ACTIVE` assignment but may name any `submitted_by_side`. Both parties may inspect all evidence on their case; the list filters by `status` and `submitted_by_side`.

Reviewing evidence is the active investigator's exclusive province: the actor must hold the case's `ACTIVE` assignment, failing as `ERR_NO_ACTIVE_INVESTIGATOR`. Beginning review — valid while the case is in `INVESTIGATION` or `EVIDENCE_REVIEW` — moves an item `SUBMITTED → UNDER_REVIEW` with `EVIDENCE_REVIEW_STARTED`. Ruling on relevance takes a `ruling` of `ACCEPTED` or `EXCLUDED`. An `ACCEPTED` ruling clears any prior `exclusion_reason`, appends `EVIDENCE_RULED`, and — if the case has a `DRAFT` packet — makes the item eligible for that packet's pin snapshot at release. An `EXCLUDED` ruling requires a non-empty `exclusion_reason`, records it, and appends `EVIDENCE_RULED`. The item machine is cyclic with no terminal states: an `EXCLUDED` item can be reconsidered through begin-review (`EXCLUDED → UNDER_REVIEW`), and an `ACCEPTED` item returns to `UNDER_REVIEW` by cascade when the packet that pinned it is superseded — one `EVIDENCE_REVIEW_STARTED` per pinned item.

The **evidence packet** is the investigation's deliverable, and creating one is the second OCC-guarded write: `expected_case_version` must equal the case's current `version`, failing as `ERR_STALE_CASE_VERSION`. Only one packet per case may be live — in `DRAFT`, `RELEASED_FOR_REVIEW`, or `REVIEW_CLOSED` — at a time; creating while one is live is rejected with `ERR_ACTIVE_PACKET_EXISTS` (409). Creation lands in `DRAFT`, assigns the 1-based `packet_sequence` in creation order across the case, appends `PACKET_CREATED`, and increments the case `version`; if the case already has a `FINALIZED` packet, that packet is superseded (moving to `SUPERSEDED` with `PACKET_SUPERSEDED` appended) and each of its pinned `ACCEPTED` items cascades back to `UNDER_REVIEW`. Before release, the investigator attaches the investigative report: supplying `investigative_report_summary` stamps `report_attached_at` from the clock and appends `REPORT_ATTACHED`.

Releasing the packet to the parties requires the actor to be the case's active investigator, the report attached (`report_attached_at` set), and the case in `INVESTIGATION` — a missing report or a wrong packet or case state is rejected with `ERR_INVALID_STATE_TRANSITION` (409). Release moves the packet `DRAFT → RELEASED_FOR_REVIEW`, stamps `released_at`, sets `review_closes_at` to `released_at` plus the 10-day review window of §2.8, and freezes `pinned_item_ids`: the snapshot of the case's `ACCEPTED` evidence items, ordered by `collected_at` ascending with ties broken by `created_at` ascending, immutable once released — and legitimately empty when nothing has been accepted. Release also issues an `EVIDENCE_RELEASE` notice to `BOTH` parties, moves the case `INVESTIGATION → EVIDENCE_REVIEW`, appends `PACKET_RELEASED`, and increments the case `version`.

Each party then files a review response naming its `party_side` and a `response_text`. The response is accepted only while the packet is `RELEASED_FOR_REVIEW` and the logical instant is on or before `review_closes_at` (inclusive); a later response is `ERR_REVIEW_RESPONSE_LATE`. A second response from the same side on the same packet is `ERR_DUPLICATE_RESPONSE` (409), and a side that does not match the case's party binding is `ERR_PARTY_BINDING_MISMATCH` (422). Each accepted response stamps `complainant_responded_at` or `respondent_responded_at` as appropriate and appends `REVIEW_RESPONSE_RECORDED`; the moment the second party's response lands, the packet auto-closes `RELEASED_FOR_REVIEW → REVIEW_CLOSED` with `PACKET_REVIEW_CLOSED`. Reconciliation closes the window the same way once the clock reaches `review_closes_at`. A review response is not itself a persisted resource: the create call returns `201` with the updated packet object in `data`.

Finalizing is the active investigator's last act on the case. It requires the packet in `REVIEW_CLOSED` — with one shortcut: finalizing a packet still in `RELEASED_FOR_REVIEW` succeeds once the logical clock has reached `review_closes_at`, moving the packet through `REVIEW_CLOSED` (appending `PACKET_REVIEW_CLOSED`) in the same act, whereas finalizing while the window is still open with responses outstanding is premature and rejected with `ERR_REVIEW_WINDOW_OPEN` (422) — and the report attached, its absence failing as `ERR_INVALID_STATE_TRANSITION` (409). Finalization moves the packet `REVIEW_CLOSED → FINALIZED`, moves the case `EVIDENCE_REVIEW → HEARING_PREPARATION`, moves the case's `ACTIVE` investigator assignment to `COMPLETED`, appends `PACKET_FINALIZED`, and increments the case `version`. A packet still in `DRAFT` may instead be withdrawn by the active investigator, moving to `WITHDRAWN` with `PACKET_WITHDRAWN`. The packet list on a case filters by `status`.

### 3.4. Advisors, Notices, Hearings, and Cross-Examination

Every party is entitled to an advisor throughout, and appointments are per-side. Appointing a party-selected advisor names a `party_side` (`COMPLAINANT` or `RESPONDENT`) and an `advisor_id`; a `Party` actor may appoint only for their own side, otherwise `ERR_PARTY_BINDING_MISMATCH`, while the coordinator may appoint for either side. The new appointment lands in `ACTIVE` with `source` set to `PARTY_SELECTED`, appends `ADVISOR_APPOINTED`, and increments the case `version`; any prior `ACTIVE` appointment for the same case and side is automatically replaced — moved to `REPLACED` with its `replaced_by_appointment_id` pointing at the newcomer and `ADVISOR_REPLACED` appended. Re-appointing the very same `advisor_id` for a side that already actively holds that advisor is a no-op rejection, `ERR_DUPLICATE_ADVISOR` (409). Eligibility is checked per §2.6 in spirit and precisely here: the advisor must not be the opposing party of the same case and must not hold any official function on it, failing as `ERR_ADVISOR_INELIGIBLE` (422); the `advisor_eligible` directory flag is *not* required for party-selected advisors.

When a party has no advisor of their own, the coordinator requests a university-appointed advisor for a `party_side`. A deterministic selector builds the pool: every directory profile with `advisor_eligible` true, excluding the case's two parties and everyone holding an official function on the case. The pool is ranked by fewest `ACTIVE` appointments across *all* cases, ascending, with ties broken by earliest `created_at` ascending and then by insertion order, and the top profile is appointed with `source` set to `UNIVERSITY_APPOINTED`; the same replacement cascade as above applies, and for this path `advisor_eligible` is mandatory — its absence is an `ERR_ADVISOR_INELIGIBLE` failure by construction of the pool. An empty pool is rejected with `ERR_NO_ADVISOR_AVAILABLE` (422). Withdrawal of an `ACTIVE` appointment — by the appointed advisor themself, the served party, or the case coordinator — moves it to `WITHDRAWN` with `ADVISOR_WITHDRAWN` and a version increment; a withdrawal by any other actor is rejected as `ERR_PARTY_BINDING_MISMATCH` (422). Appointments list on a case with `party_side` and `status` filters, and a staff-only directory filters by `advisor_id`, `replaced_by_appointment_id`, and `status`.

**Notices** are the system's process record to the parties. A coordinator, investigator, or decision-maker sends one with a `notice_type` of `ALLEGATIONS`, `INTERVIEW`, `EVIDENCE_RELEASE`, `HEARING`, `DETERMINATION`, `DISMISSAL`, `APPEAL_FILED`, `APPEAL_OUTCOME`, or `INFORMAL_PROPOSAL`; a `recipient_side` of `COMPLAINANT`, `RESPONDENT`, or `BOTH`; a `body`; and — required for `INTERVIEW` and `HEARING` notices, optional and simply stored for all other types — the `scheduled_event_at` of the event being noticed. Sending stamps `sent_at` from the clock, computes `lead_time_sufficient` per §2.8 for event notices (true for all other types), and appends `NOTICE_SENT`; insufficient lead is `ERR_NOTICE_LEAD_TIME_INSUFFICIENT`. A `Party` single-read of a notice addressed only to the other side is rejected with `ERR_CASE_ACCESS_DENIED` (403). Ordering matters too: an `INTERVIEW` notice may only be created after an `ALLEGATIONS` notice exists for the case — parties must receive the allegations before any interview — failing as `ERR_NOTICE_ORDER_VIOLATION` (422). Several notice types are emitted automatically by workflows elsewhere: `ALLEGATIONS` on formal-complaint filing, `EVIDENCE_RELEASE` on packet release, `HEARING` on hearing scheduling, `DETERMINATION` on issuance, `DISMISSAL` on dismissal, `APPEAL_FILED` to the non-filing party when appeal review begins, `APPEAL_OUTCOME` when an appeal is decided, and `INFORMAL_PROPOSAL` when informal resolution is proposed. The per-case notice list filters by `notice_type` and `recipient_side`, with party visibility per §2.6.

**Scheduling the live hearing** is a coordinator act with four requirements, evaluated in §2.11 tier order. The case must be in `HEARING_PREPARATION` — a state only packet finalization produces, so a `FINALIZED` packet necessarily exists. The named `decision_maker_id` must be segregation-clean per §2.6. The calendar rules of §2.8 bind next: `scheduled_at` strictly in the future (`ERR_HEARING_TIME_CONFLICT`) and at least 10 days out (`ERR_NOTICE_LEAD_TIME_INSUFFICIENT`), then no overlap and 60-minute buffers against the decision-maker's other non-cancelled hearings (`ERR_HEARING_TIME_CONFLICT`), with the hearing's occupancy defined by its positive integer `estimated_duration_minutes`. Only after the calendar checks does the singleton gate fire: one hearing per case may be live — `SCHEDULED`, `IN_SESSION`, `ADJOURNED`, or `DELIBERATION` — failing as `ERR_ACTIVE_HEARING_EXISTS` (409). The request also carries a `modality` of `IN_PERSON` or `VIRTUAL`. A scheduled hearing lands in `SCHEDULED`, automatically issues the `HEARING` notice to `BOTH` parties with the hearing time as its `scheduled_event_at`, appends `HEARING_SCHEDULED`, and increments the case `version`. Hearings list per case with a `status` filter, and a filtered calendar list by `decision_maker_id` and `status` supports occupancy discovery.

The decision-maker — and only that person; anyone else is rejected with `ERR_NOT_HEARING_DECISION_MAKER` (422) — **convenes** the hearing once the clock has reached `scheduled_at` (convening earlier is rejected with `ERR_INVALID_STATE_TRANSITION` (409), the scheduled instant itself inclusive) and both parties each hold an `ACTIVE` advisor appointment on the case, the latter failing as `ERR_ADVISOR_REQUIRED` (422). Convening moves `SCHEDULED → IN_SESSION`, stamps `convened_at`, moves the case `HEARING_PREPARATION → HEARING_IN_PROGRESS` — the case now sits in `HEARING_IN_PROGRESS` until deliberation — appends `HEARING_CONVENED`, and increments the case `version`. In session, the hearing may **adjourn** — requiring a non-empty `adjourn_reason`, which is recorded — moving `IN_SESSION → ADJOURNED` with `HEARING_ADJOURNED`, and later **reconvene**, moving `ADJOURNED → IN_SESSION`, clearing `adjourn_reason`, and appending `HEARING_RECONVENED`; the adjourn/reconvene loop may repeat any number of times while questions accumulate and are ruled. A `SCHEDULED` hearing may be cancelled by the decision-maker or the coordinator (`SCHEDULED → CANCELLED`, `HEARING_CANCELLED`), and dismissal of the case cascades a cancellation onto hearings in `SCHEDULED` or `ADJOURNED` (§3.1); `COMPLETED` and `CANCELLED` are the hearing's terminal states. Adjourn, reconvene, and cancel check the acting role only — unlike convening, closing cross-examination, and ruling, they do not bind the actor's identity to the hearing's `decision_maker_id`. When cross-examination is complete, the decision-maker closes it — again, anyone else is `ERR_NOT_HEARING_DECISION_MAKER` — and the hearing must have **zero** questions still `PENDING`, failing as `ERR_PENDING_QUESTIONS_REMAIN` (422). Closing moves the hearing `IN_SESSION → DELIBERATION`, moves the case `HEARING_IN_PROGRESS → DELIBERATION`, appends `CROSS_EXAM_CLOSED`, and increments the case `version`. The hearing's own `DELIBERATION → COMPLETED` step arrives as a cascade of determination issuance (§3.5).

While the hearing is `IN_SESSION`, cross-examination runs through the advisors — never the parties directly. An `Advisor` submits a question with `asked_by_advisor_id`, a `target_side` of `COMPLAINANT` or `RESPONDENT`, and the `question_text`. The asker must hold an `ACTIVE` appointment on the hearing's case, and the `target_side` must be the *opposing* side of the asker's appointment — advisors cross-examine the other party, never their own — failing as `ERR_QUESTIONER_NOT_CASE_ADVISOR` (422). The question lands in `PENDING` with a 1-based `sequence` in submission order within the hearing and `QUESTION_ASKED` appended; every question is bound to its hearing through `hearing_id`. Ruling belongs to the hearing's decision-maker alone (`ERR_NOT_HEARING_DECISION_MAKER` otherwise) and only while the hearing is `IN_SESSION`: a `ruling` of `ALLOWED` moves the question `PENDING → ALLOWED` with `QUESTION_RULED`; a ruling of `DISALLOWED` — the relevance exclusion — requires a non-empty `ruling_reason` explaining it on the record, records the reason, moves the question `PENDING → DISALLOWED`, and appends `QUESTION_RULED`. Both rulings are terminal. Questions list per hearing with a `ruling` filter, and a staff-only filtered list searches by `asked_by_advisor_id` and `ruling`.

### 3.5. Determination Drafting, Issuance, and Sanctions

With the case in `DELIBERATION`, the hearing's decision-maker drafts the determination. Drafting is the third OCC-guarded write: `expected_case_version` must equal the case's current `version`, failing as `ERR_STALE_CASE_VERSION`. The draft records a `responsibility_finding` of `RESPONSIBLE`, `NOT_RESPONSIBLE`, or `INSUFFICIENT_EVIDENCE`; the `standard_of_evidence` applied — recorded as supplied and not compared against the case's pinned standard until issuance; a written `rationale`; and three attested counts, each a non-negative integer defaulting to zero — `aggravating_factor_count`, `mitigating_factor_count`, and `prior_responsible_findings`. At creation the PROVISIONAL severity variant of §2.9 runs (mitigating excluded) and its result is stored as `provisional_severity_score`. A case holds at most one draft at a time by supersession: creating a new `DRAFT` moves any existing `DRAFT` on the case to `SUPERSEDED`. On a `REMANDED` case, the new draft legitimately continues the lineage whose prior determinations the remand already superseded (§3.6). Drafting appends `DETERMINATION_DRAFTED` and increments the case `version`. Only the decision-maker of the case's completed hearing may draft or issue; anyone else is `ERR_NOT_HEARING_DECISION_MAKER`.

**Issuance** is the heaviest transaction in the system. Its preconditions: the actor's identity equals the completed hearing's `decision_maker_id`; the case is in `DELIBERATION`; the issued `standard_of_evidence` — taken from the payload, defaulting to the draft's recorded value when the payload omits it — equals the case's intake-pinned `standard_of_evidence`, a mismatch being `ERR_STANDARD_OF_EVIDENCE_MISMATCH` (422), because the same standard must apply to both parties; and the `sanction_selections` conform to the sanctioning matrix — non-empty exactly when the finding is `RESPONSIBLE` (for `NOT_RESPONSIBLE` or `INSUFFICIENT_EVIDENCE` the selections must be empty), every selection's type and duration inside the computed final-tier bounds, and any `RESTITUTION` selection backed by a cap tier of `TIER_3` or `TIER_4` — failing as `ERR_SANCTION_OUTSIDE_MATRIX`. Restitution selections additionally require a non-empty `restitution_items` array whose every item carries a `description` and an `amount_dollars` strictly greater than zero, failing as `ERR_RESTITUTION_ITEMS_REQUIRED` (422); `restitution_items` is forbidden on non-`RESTITUTION` selections, just as `duration_days` is required on `PROBATION`, `SUSPENSION`, `EDUCATIONAL_PROGRAM`, and `NO_CONTACT_CONTINUATION` (within the tier's inclusive bounds) and forbidden on `WARNING`, `EXPULSION`, and `RESTITUTION`.

On issuance the pinned evaluation order of §2.9 runs: the FINAL severity variant (mitigating included) computes `final_severity_score`, restitution amounts resolve to `applied_restitution_cents` per selection, and `final_tier` falls out of the total points. Each selection becomes a `Sanction` row in `ACTIVE` status, bound to the issuing determination through `determination_id`, with `effective_from` equal to the determination's `issued_at` and `applied_restitution_cents` zero for non-restitution types. The determination itself moves `DRAFT → ISSUED`, stamps `issued_at` from the logical clock, computes `appeal_deadline` as `issued_at` plus the 5-day appeal window (filings at exactly that instant are timely), and records `issued_by_id` as the decision-maker taken from the completed hearing. The case moves `DELIBERATION → DETERMINATION_ISSUED`, the hearing cascades `DELIBERATION → COMPLETED`, a `DETERMINATION` notice goes to `BOTH` parties, `DETERMINATION_ISSUED` is appended, and the case `version` increments.

Sanctions then run their course. A duration-bearing sanction completes automatically: reconciliation (§3.8) moves it `ACTIVE → COMPLETED` once the clock reaches `effective_from` plus `duration_days`, appending `SANCTION_COMPLETED` and incrementing the case `version`. The duration-less types — `WARNING`, `EXPULSION`, `RESTITUTION` — complete manually when the coordinator marks them complete, with the same transition, event, and version increment; marking a duration-bearing sanction complete by hand is rejected with `ERR_INVALID_STATE_TRANSITION` (409). Appeal outcomes can interrupt this: a remand moves `ACTIVE` sanctions to `STAYED`, while a reversal or sanction modification moves them to `LIFTED_ON_APPEAL` (§3.6). All three of `COMPLETED`, `STAYED`, and `LIFTED_ON_APPEAL` are terminal.

When no appeal comes, the coordinator closes the case — but only after the full appeal window has elapsed: the logical clock must be strictly later than the `appeal_deadline` of the case's `ISSUED` determination, and no appeal on the case may be in `FILED` or `UNDER_REVIEW`. Finalizing closure moves the `ISSUED` determination to `FINAL` (appending `DETERMINATION_FINALIZED`), stamps `closed_at`, moves the case `DETERMINATION_ISSUED → CLOSED`, appends `CASE_CLOSED`, and increments `version`; a premature or appeal-blocked closure attempt is rejected with `ERR_INVALID_STATE_TRANSITION` (409). Determinations list per case with a `status` filter — the remand lineage is visible there — and a staff-only list filters by `issued_by_id` and `status`; sanctions list per determination with `status` and `sanction_type` filters.

### 3.6. Appeals, Remand, and Case Resumption

Either party may appeal. Filing names the `filed_by_side` (which must match the case's party binding, failing as `ERR_PARTY_BINDING_MISMATCH`), an `appeal_target` of `DETERMINATION` or `DISMISSAL`, a non-empty `grounds` array drawn from `PROCEDURAL_IRREGULARITY`, `NEW_EVIDENCE`, `CONFLICT_OF_INTEREST`, and `DISPROPORTIONATE_SANCTION`, and a supporting `statement`. The filing stamps `filed_at` from the logical clock and records `filed_by_id` from the actor's identity. Timeliness follows §2.8: `filed_at` must fall on or before the target's deadline — `issued_at` plus 5 days for a determination, `closed_at` plus 5 days for a dismissal, both inclusive — failing as `ERR_APPEAL_WINDOW_EXPIRED`. The target must also exist and be appealable: a `DETERMINATION` appeal requires a determination in `ISSUED` status on the case, and a `DISMISSAL` appeal requires the case in `DISMISSED`; `RESOLVED_INFORMAL` cases are never appealable, and determinations already `FINAL`, `REVERSED`, or `SUPERSEDED` are not either. Violations are `ERR_APPEAL_TARGET_INVALID` (422). The filing lands in `FILED`, appends `APPEAL_FILED`, and increments the case `version`; a determination-target filing also moves the case `DETERMINATION_ISSUED → APPEAL_REVIEW`, making the determination track single-shot — a second determination-target filing while the case already sits in `APPEAL_REVIEW` is rejected with `ERR_INVALID_STATE_TRANSITION` (409) — while dismissal-target filings carry no such gate and several may be filed within the window. Dismissal appeals are the sanctioned exception to the terminal-case guard: filing one on a `DISMISSED` case is expressly permitted. Appeals list per case with `status` and `appeal_target` filters, and a filtered staff list searches by `filed_by_id`, `appeal_officer_id`, and `status`.

The coordinator begins review by assigning the `appeal_officer_id`, who must pass the §2.6 segregation bar — differing from the case coordinator, the `ACTIVE` or `COMPLETED` investigator, the hearing decision-maker, any facilitator, and both parties, failing as `ERR_SEGREGATION_OF_DUTIES` or `ERR_OFFICIAL_IS_CASE_PARTY` as applicable. Beginning review moves the appeal `FILED → UNDER_REVIEW`, issues the `APPEAL_FILED` notice to the **non-filing** party, appends `APPEAL_REVIEW_STARTED`, and increments the case `version`.

Deciding belongs exclusively to the assigned officer: any other actor is rejected with `ERR_NOT_ASSIGNED_APPEAL_OFFICER` (422). The appeal decides from `UNDER_REVIEW`, moving `UNDER_REVIEW → <outcome>`. The decision carries an `outcome`, and compatibility with the `appeal_target` is enforced — `AFFIRMED` is allowed for both targets; `REVERSED`, `REMANDED`, and `SANCTION_MODIFIED` only for `DETERMINATION`; `REINSTATED` only for `DISMISSAL` — failing as `ERR_APPEAL_OUTCOME_INCOMPATIBLE` (422). Every decision stamps `decided_at`, issues the `APPEAL_OUTCOME` notice to `BOTH` parties, and increments the case `version`. The five outcomes cascade differently:

- **AFFIRMED** — the determination (when the target is `DETERMINATION`) moves `ISSUED → FINAL` with `DETERMINATION_FINALIZED`, and the case leaves `APPEAL_REVIEW` for `CLOSED` with `closed_at` stamped and `CASE_CLOSED` appended; an affirmed dismissal-target appeal instead leaves the case untouched in `DISMISSED`, with no `CASE_CLOSED` and no change to `closed_at`. `APPEAL_DECIDED` is appended either way.
- **REVERSED** — the determination moves `ISSUED → REVERSED`, and its `ACTIVE` sanctions move to `LIFTED_ON_APPEAL` as compensation so no discipline is double-counted; the case closes as under affirmance; `APPEAL_DECIDED` and `CASE_CLOSED` are appended.
- **REMANDED** — the payload's `remand_scope` must be present and ground-compatible: `INVESTIGATION` is required whenever `grounds` includes `NEW_EVIDENCE`; grounds that are a subset of `PROCEDURAL_IRREGULARITY` and `CONFLICT_OF_INTEREST` (without `NEW_EVIDENCE`) require `HEARING_PREPARATION` exactly; and any other grounds composition — for example `DISPROPORTIONATE_SANCTION` alone — accepts either scope; a mismatch is `ERR_REMAND_SCOPE_MISMATCH` (422). The determination moves `ISSUED → SUPERSEDED`, its `ACTIVE` sanctions move to `STAYED`, and the case leaves `APPEAL_REVIEW` for `REMANDED` with its `remand_target` set to the appeal's `remand_scope`; `APPEAL_DECIDED` is appended.
- **SANCTION_MODIFIED** — the payload's `modified_sanction_selections` must be non-empty, each selection within the determination's final-tier matrix bounds, failing as `ERR_SANCTION_OUTSIDE_MATRIX`; a restitution selection among them is subject to the §2.9 item and cap rules, with missing or non-positive items failing as `ERR_RESTITUTION_ITEMS_REQUIRED`. The determination's `ACTIVE` sanctions move to `LIFTED_ON_APPEAL`, replacement sanction rows are created `ACTIVE` under the same determination per the modified selections — each with `effective_from` equal to the determination's original `issued_at` — and the determination moves to `FINAL`; the case closes as under affirmance; `APPEAL_DECIDED` and `CASE_CLOSED` are appended.
- **REINSTATED** — available only against a dismissal: the case moves `DISMISSED → AWAITING_FORMAL_COMPLAINT` with `dismissal_reason` and `closed_at` cleared; `APPEAL_DECIDED` and `CASE_RESUMED` are appended.

A `REMANDED` case resumes by coordinator action, and the destination is whatever the remanding appeal recorded in `remand_target`; the request may carry an optional `remand_target` field (also accepted under the key `target`) naming the requested destination — present and unequal to the recorded target is `ERR_REMAND_SCOPE_MISMATCH`, while an absent field simply resumes to the recorded target — and a successful resume clears the case's `remand_target` to null. Resuming into `INVESTIGATION` reopens the evidence base: the case's most recent `FINALIZED` packet moves to `SUPERSEDED` (appending `PACKET_SUPERSEDED`), each of that packet's pinned `ACCEPTED` evidence items returns to `UNDER_REVIEW` (one `EVIDENCE_REVIEW_STARTED` per item), `CASE_RESUMED` is appended, and the case `version` increments. Resuming into `HEARING_PREPARATION` touches neither packet nor items: the case simply moves `REMANDED → HEARING_PREPARATION` with `CASE_RESUMED` and a version increment. Either way the remand loop of §3.1 is closed and the case runs forward again.

### 3.7. Informal Resolution

At any point while a case is in `INVESTIGATION` or `EVIDENCE_REVIEW`, the coordinator may propose informal resolution by naming a `facilitator_id` — a neutral who must pass the same §2.6 segregation bar as every other official. Three gates guard the proposal. The case must carry a signed formal complaint: `formal_complaint_signed` true, failing as `ERR_FORMAL_COMPLAINT_REQUIRED` (422). Informal resolution is categorically prohibited when the respondent's `role_type` is `EMPLOYEE` and the complainant's is `STUDENT` — employee-on-student allegations may never resolve informally — failing as `ERR_INFORMAL_RESOLUTION_PROHIBITED` (422). And only one informal resolution per case may be live — in `PROPOSED` or `IN_PROGRESS` — failing as `ERR_ACTIVE_INFORMAL_RESOLUTION_EXISTS` (409). On this endpoint the from-state gate — the case must be in `INVESTIGATION` or `EVIDENCE_REVIEW`, failing as `ERR_INVALID_STATE_TRANSITION` — is evaluated after the facilitator safety gates, the singleton, and the signed-complaint gate, not in the usual tier-4 position. A successful proposal lands in `PROPOSED`, moves the case into `INFORMAL_RESOLUTION_IN_PROGRESS`, issues the `INFORMAL_PROPOSAL` notice to `BOTH` parties, appends `INFORMAL_PROPOSED`, and increments the case `version`.

Consent is voluntary, written, and per party. A `Party` records consent with their `party_side` (binding-checked per §3.6's rule, failing as `ERR_PARTY_BINDING_MISMATCH`) and a boolean `consent`. A true consent stamps `complainant_consent_at` or `respondent_consent_at` from the logical clock and appends `INFORMAL_CONSENT_RECORDED` with a version increment; the same party consenting affirmatively twice is rejected with `ERR_DUPLICATE_RESOURCE` (409) — though a party that has consented may still record a decline while the resolution remains `PROPOSED`, which terminates it. The instant the **second** party consents — both consent timestamps now set — the resolution auto-fires `PROPOSED → IN_PROGRESS`. A false consent is a decline, available only from `PROPOSED` — from `IN_PROGRESS` it fails as `ERR_INVALID_STATE_TRANSITION` (409), and a party wishing to leave an in-progress resolution withdraws instead: the resolution moves `PROPOSED → TERMINATED`, the case returns to `INVESTIGATION`, and `INFORMAL_TERMINATED` plus `CASE_RESUMED` are appended with a version increment.

Either party may also withdraw outright, from `PROPOSED` or `IN_PROGRESS` alike — a non-party's attempt is `ERR_PARTY_BINDING_MISMATCH`. Withdrawal records the `withdrawn_by_side`, moves the resolution to `WITHDRAWN`, returns the case to `INVESTIGATION`, and appends `INFORMAL_WITHDRAWN` plus `CASE_RESUMED` with a version increment. This withdrawal loop is the second of the §3.1 cycles: a case may leave the informal track and, conditions permitting, re-enter it later under a fresh proposal.

Resolution itself belongs to the coordinator — identity-bound: a `TitleIXCoordinator` whose id differs from the case's `coordinator_id` is rejected with `ERR_FORBIDDEN_ROLE` (403) — who records the non-empty `agreed_terms`. Resolving moves the resolution `IN_PROGRESS → RESOLVED` — `RESOLVED`, `WITHDRAWN`, and `TERMINATED` are the resolution's terminal states — moves the case to `RESOLVED_INFORMAL` with `closed_at` stamped, and appends `INFORMAL_RESOLVED` plus `CASE_CLOSED` with a version increment. `RESOLVED_INFORMAL` is terminal and, per §3.6, not appealable — appeal creation on such a case fails `ERR_APPEAL_TARGET_INVALID`. A case dismissed while its informal resolution is live (§3.1) terminates that resolution — `PROPOSED` or `IN_PROGRESS` moving to `TERMINATED` with `INFORMAL_TERMINATED` — without the return-to-investigation step, since the case is closing instead. Resolutions list per case with a `status` filter, and a staff-only list filters by `facilitator_id` and `status`.

### 3.8. Reconciliation, Annual Statistics, and Retention

Clock-gated transitions do not fire on their own: a `TitleIXCoordinator` or `CaseAdministrator` runs a per-case **reconcile**, which sweeps the case and applies every pending clock-driven change in one checkpoint. Measures in `ACTIVE` with a set `effective_to` at or before the clock move to `EXPIRED` (each decrementing `active_supportive_measure_count` and appending `MEASURE_EXPIRED`); directives in `ACTIVE` with a set `effective_to` at or before the clock move to `EXPIRED` (appending `DIRECTIVE_EXPIRED`, and recomputing the case exposure score if any directive expired); packets in `RELEASED_FOR_REVIEW` whose `review_closes_at` is at or before the clock move to `REVIEW_CLOSED` (appending `PACKET_REVIEW_CLOSED`); and sanctions in `ACTIVE` with a `duration_days` set whose `effective_from` plus `duration_days` is at or before the clock move to `COMPLETED` (appending `SANCTION_COMPLETED`). The reconcile response enumerates exactly what fired: `expired_measure_ids`, `expired_directive_ids`, `review_closed_packet_ids`, and `completed_sanction_ids`, each list ordered by the fired resources' `created_at` ascending. When at least one transition fired, the case's `version` increments by 1. Recall from §2.4 that setting the clock fires nothing by itself — reconcile is the application point.

**Annual statistics** serve the federal reporting obligation. The computation always runs over the §2.8 inclusion window — cases whose `received_at` falls within the calendar year — and produces a fixed shape: `reports_received` (count of included cases), `formal_complaints_filed` (included cases with `formal_complaint_signed` true), `dismissed` (included cases in `DISMISSED`), `referred` (included cases in `REFERRED_TO_CONDUCT`), `hearings_completed` (hearings in `COMPLETED` whose *case* is included — case inclusion governs, so the hearing's own completion date may fall outside the window), `informal_resolved` (included cases in `RESOLVED_INFORMAL`), `determinations_responsible`, a `per_category` object mapping each category to a count, and `avg_resolution_days`. Two rules deserve emphasis. The **hierarchy rule** counts every included case in exactly one category bucket: the case's assigned category is the member of its `categories` with the highest §2.7 hierarchy priority, so a case alleging both `STALKING` and `SEXUAL_ASSAULT` counts toward `SEXUAL_ASSAULT` (priority 7 over 4) — and the `per_category` counts sum exactly to `reports_received`. `per_category` carries an entry only for buckets at least one included case maps to; empty categories are omitted rather than zeroed. The **responsible-determination rule** looks at each included case's *latest* determination — latest by `issued_at` ascending, ties broken by `created_at` ascending — and counts the case only when that determination's `responsibility_finding` is `RESPONSIBLE` and its status is `ISSUED`, `FINAL`, or `SUPERSEDED`; a case whose latest determination is `REVERSED` is excluded.

`avg_resolution_days` has its own pinned rounding order, and the order is load-bearing. First, per resolved case — included cases with `closed_at` set and `closed_at` strictly before the following January 1 boundary — compute whole days as the floor of the elapsed seconds between `closed_at` and `received_at` divided by 86,400. Second, take the exact rational mean of those per-case integers. Third, round the mean half-up to one decimal place — a single rounding, last. If the resolved set is empty, `avg_resolution_days` is null, never zero. Worked example: two included cases resolve in the window, one 64 whole days after intake and one 19; the exact mean of 64 and 19 is 41.5, which rounds half-up to one decimal as 41.5, and the published statistic reads 41.5. Reversing the rounding order (rounding before averaging) is forbidden.

The statistics for a year come in two variants. Before publication, reading a year returns the **LIVE** view: the computation reflects the database as of the current logical clock, including cases still in flight, and the response carries `year`, `status` reading `LIVE`, the computation under `counts`, and null `snapshot_counts`, `amended_counts`, `published_at`, and `amended_at` — with no `id`, `created_at`, `updated_at`, or `version` until a row exists. Once a row exists, the read returns the stored row's fields (`id`, `created_at`, `updated_at`, `version`, `year`, `status`, the frozen `snapshot_counts`, `amended_counts`, `published_at`, `amended_at`) plus a `counts` field that still holds the live recomputation. The year validity rule applies to all three statistics endpoints — reading included — with the `year` required to lie within 2000 through 2100 inclusive, failing as `ERR_STATISTICS_YEAR_INVALID` (422). Publishing — a coordinator act — freezes the live computation into `snapshot_counts` on a new `AnnualStatistic` row in `PUBLISHED` status with `published_at` stamped; a year row that already exists makes the publish a duplicate, `ERR_DUPLICATE_RESOURCE`. Thereafter the frozen snapshot never moves: later case mutations — dismissals, reversals, new findings — do not touch it, so the same underlying cases can yield different numbers under the live and published views. Amending recomputes: against an existing `PUBLISHED` or `AMENDED` row (amending a year with no published row fails `ERR_STATISTICS_YEAR_INVALID`), the coordinator's amendment stores a fresh live recomputation into `amended_counts`, refreshes `amended_at`, and moves `PUBLISHED → AMENDED`; re-amending an `AMENDED` year is a self-loop that recomputes `amended_counts` and refreshes `amended_at` again, with `snapshot_counts` remaining frozen throughout.

Finally, the retention sweep of §2.5 — a `CaseAdministrator` capability — permanently deletes audit-trail rows of terminal cases at the seven-year inclusive boundary, returning `purged_event_count` and `purged_case_ids`, while cases and statistics are preserved.
