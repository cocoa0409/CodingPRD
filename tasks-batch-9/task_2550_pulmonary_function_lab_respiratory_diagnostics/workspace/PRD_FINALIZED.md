# Pulmonary Function Lab API — Product Requirements Document

## 1. Introduction

A hospital pulmonary function laboratory is one of the few diagnostic services where the credibility of a number depends almost entirely on the discipline that surrounded its measurement. A forced expiratory volume is only interpretable if the device that recorded it was volume-calibrated against a certified syringe that same day, if a healthy biologic control subject reproduced their own known values on that device, if the bacterial filter was changed and the mouthpiece circuit disinfected since the previous patient, if the patient actually withheld their bronchodilators for the required number of hours, and if the effort itself satisfied the start-of-test, end-of-test and artifact criteria that the ATS/ERS standards define. When any one of those conditions silently fails, the laboratory does not produce a wrong result — it produces a result that looks entirely normal and is nevertheless inadmissible.

This document specifies the Pulmonary Function Lab API, the system of record for that discipline. Every endpoint is mounted under the `/pft-lab` prefix. The API governs the complete arc of a pulmonary study: an ordering clinician drafts and submits an order whose clinical indication is validated against the modalities it is allowed to justify; a technologist issues pre-test medication hold instructions and records the patient's attestation against them; the same technologist runs the day's calibration, leak-check and biologic-control program on the device, schedules the study into a device occupancy window, coaches the patient through repeated forced expiratory maneuvers, and — where bronchoprovocation was ordered — arms a methacholine or mannitol challenge only after rescue bronchodilator has been physically reserved from an unexpired lot; and finally an interpreting physician who did not conduct the study signs a templated report against a turnaround deadline scaled to the laboratory's current queue load.

Two commitments run through the whole specification and shape almost every rule in it. The first is that quality failures propagate rather than sit still: a single failing biologic control on a device quarantines that device, aborts every live study standing on it, hands each of those studies back to its order for rescheduling, terminates any armed bronchoprovocation run and reconciles the rescue-dose ledger, all in one request. The second is that the same measured numbers may legitimately yield different verdicts depending on which published criterion the laboratory has pinned for that context — a biologic control deviation is judged against either a fixed enrolment baseline or a rolling mean of the subject's own recent efforts, and a bronchodilator response is judged either as a percentage of the patient's own pre-drug value or as a percentage of their predicted value. Implementations must select the criterion by rule, never by preference.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across every endpoint: authentication, response shape, pagination, the logical clock, common resource properties, numeric precision, concurrency guarding, cascade semantics, the strict order in which validations run, segregation of duties, the rescue-dose ledger invariants, and the deterministic behaviour required of the two selector policies.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. If either header is absent, or if `X-User-Role` is not one of the five role names the laboratory recognises, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The five roles are `LabManager`, `Technologist`, `OrderingPhysician`, `InterpretingPhysician` and `ComplianceAuditor`, spelled exactly as written. When the acting role is not among the roles authorised for the target operation, the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

Three of the five roles are backed by a persisted `Staff` record, and for those three the header pair is also an identity assertion. When `X-User-Role` is `Technologist`, `X-User-ID` is the `id` of the acting `Staff` row, and that row's `role_type` must be `TECHNOLOGIST`; ownership checks on any resource that references a `Staff` row — for example the `technologist_staff_id` recorded on a study, or the `ordering_staff_id` recorded on an order — compare that foreign-key field to `X-User-ID`. When `X-User-Role` is `OrderingPhysician`, `X-User-ID` is likewise the `id` of the acting `Staff` row and that row's `role_type` must be `ORDERING_PHYSICIAN`. When `X-User-Role` is `InterpretingPhysician`, `X-User-ID` is the `id` of the acting `Staff` row and that row's `role_type` must be `INTERPRETING_PHYSICIAN`; the report-level ownership check compares `interpreter_staff_id` to `X-User-ID`. In all three cases, an `X-User-ID` that does not resolve to a `Staff` row at all, or that resolves to a `Staff` row whose `role_type` does not match the asserted role, is rejected with `ERR_STAFF_IDENTITY_MISMATCH` (HTTP 403), and that rejection happens before any existence check on identifiers appearing in the URL path.

The remaining two roles are opaque. When `X-User-Role` is `LabManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. This is deliberate: the laboratory manager is the role that registers the very first `Staff` row, so manager authentication must succeed on an empty database. When `X-User-Role` is `ComplianceAuditor`, `X-User-ID` is likewise an opaque identifier belonging to an external witness rather than a laboratory employee. The server does record it — a compliance witness attestation stores the raw header value in `actor_user_id` and the asserted role in `actor_role` on the custody record it appends — but it never resolves it against `Staff`. Because `actor_user_id` holds a `Staff` identifier for technologist-authored custody records and an opaque operator identifier for auditor-authored ones, it is deliberately not a foreign key.

Authority is divided along segregation-of-duties lines. `LabManager` owns the configuration surface — registering devices, staff, reference equation sets and rescue medication lots — plus clearing quarantined devices back into service, assigning accepted studies to interpreting physicians, and driving the logical clock. `Technologist` owns the testing floor: the daily quality program, medication hold issuance and attestation, study scheduling, maneuver recording, quality finalization, and the arming, stepping and aborting of bronchoprovocation runs. `OrderingPhysician` drafts, revises, submits and cancels orders, and may register patients. `InterpretingPhysician` signs and amends the reports assigned to them and does nothing else; an interpreting physician cannot assign work to themselves, because assignment belongs exclusively to `LabManager` and the interpreter is chosen by a selector rather than nominated. `ComplianceAuditor` is read-only across the entire API with exactly one write: the witness attestation that a disability report cannot be signed without. Patient registration is shared between `LabManager` and `OrderingPhysician`; order cancellation is shared between `OrderingPhysician` and `LabManager`; read access is broad but not uniform, and the authoritative per-endpoint role list is the table in §4 — in particular `OrderingPhysician` is not granted the staff, device-quality-event, maneuver, custody-event, challenge-run or rescue-lot read surfaces, and the rescue-lot read surface is further limited to `LabManager`, `Technologist` and `ComplianceAuditor`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10 when omitted, may not be smaller than 1 and may not be larger than 100. `offset` is the number of records to skip and defaults to 0.

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending — which, for the append-only event collections in this API, is also their append order.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope described in §2.2.

### 2.4. The Logical Laboratory Clock

Nothing in this API reads wall-clock time. Every timestamp the server mints, every deadline it computes, every expiry it evaluates and every staleness rule it applies is measured against a server-held **logical UTC clock**. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time.

A `LabManager` moves the clock by supplying a target instant in the `to_iso8601` field; the response body is an object carrying the resulting `current_utc` value. Moving the clock is what makes medication-hold elapse windows, annual competency expiry, rescue lot expiry, biologic-control baseline staleness, same-day calibration validity and report turnaround breaches deterministically testable.

Advancing the clock has exactly one side effect on stored data: every rescue medication lot whose `status` is `STOCKED` and whose `expires_on` date falls strictly before the new logical date moves to `status` `EXPIRED`, and each such transition increments that lot's `version`. This is the only producer of the `EXPIRED` status anywhere in the system. The transition leaves `doses_remaining` and `doses_reserved` exactly as they were, so the ledger invariants of §2.11 continue to reconcile on an expired lot. No other entity is mutated and no other state machine advances when the clock moves.

### 2.5. Common Resource Properties and Append-Only Records

Most resources in this API — `Device`, `Staff`, `Patient`, `ReferenceEquationSet`, `RescueMedicationLot`, `TestOrder`, `MedicationHold`, `TestSession`, `ChallengeRun` and `InterpretationReport` — carry the same four system-managed properties:

- **`id`** (string): a server-minted UUID. It carries no type prefix of any kind.
- **`created_at`** (string): an ISO 8601 UTC timestamp with three fractional digits (for example `2026-08-01T09:15:00.000Z`), recorded from the logical clock at the moment the record was created.
- **`updated_at`** (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the record — including mutations the server performs on its own initiative as a consequence of some other request.
- **`version`** (integer): starts at 1 on creation and increments by exactly 1 on every mutation, again including server-initiated ones. A recomputation of a derived field is a mutation for this purpose: when appending a maneuver refreshes a study's best values and quality grade, or when signing a report copies a turnaround figure onto the study, the study's `version` increments and its `updated_at` is refreshed.

Every other instant-valued field this API stores is rendered in exactly that same form — ISO 8601 UTC with three fractional digits and a trailing `Z` — whether the server minted it from the logical clock or a client supplied it in the request body in some other ISO 8601 notation, in which case it is converted to UTC and re-rendered in this form before being stored and returned. That covers, among others, a quality event's `performed_at`, a device's `last_calibration_at`, `last_session_end_at` and `quarantined_at`, a medication hold's `instructed_at`, `release_at` and `attested_at`, an order's `hold_release_at`, a study's `scheduled_start_at` and `scheduled_end_at`, a maneuver's and a custody record's `performed_at`, a report's `assigned_at`, `due_at` and `signed_at`, and the `current_utc` the clock endpoint reports. Fields that carry a calendar date rather than an instant keep their plain `YYYY-MM-DD` form.

Three collections are append-only event logs rather than mutable resources, and they deliberately carry a reduced property set: `DeviceQualityEvent`, `Maneuver` and `CustodyEvent` each expose only `id` and `created_at`. For these three, both `updated_at` and `version` are absent from the record entirely — they are never written, never returned, and never incremented. An event row, once appended, is never edited; the way to correct the record is to append another event.

### 2.6. Numeric Precision, Rounding and Chained Derivation

Every rounded quantity in this specification uses the **round-half-up** convention: a value exactly on the midpoint rounds away from zero, so 159.5 millilitres becomes 160 and 3.0035 becomes 3.004 at three decimal places. There is no banker's rounding anywhere in the API.

Each derived quantity has a fixed number of decimal places. Four decimal places: the BTPS correction factor `btps_factor`. Three decimal places: `corrected_volume_l`, `rolling_mean_fev1_l`, the predicted values `predicted_fev1_l` and `predicted_fvc_l`, the lower limit of normal `lln_fev1_l`, the ratio `fev1_fvc_ratio`, and the interpolated provocative dose `pc20_dose_units`. Two decimal places: `error_pct`, `deviation_pct`, the per-step FEV1 drop percentage, `max_fev1_drop_pct` and `queue_load_pct`. One decimal place: `fev1_pct_predicted`, `fvc_pct_predicted` and `bd_response_pct`. Whole integers, rounded half-up at zero decimal places: `bev_limit_ml`, `repeatability_delta_ml`, `fvc_repeatability_delta_ml` and `bd_response_ml`. `cumulative_dose_units` accumulates at three decimal places. A report's `turnaround_minutes` is not rounded but truncated downward to whole minutes.

Where one rounded quantity feeds another, the intermediate rounding is **normative and observable**, not an implementation detail. Two places in particular must be implemented in the stated order. The corrected calibration volume is rounded to three decimal places *first*, and the calibration error percentage is then derived from that already-rounded volume rather than from the unrounded product. The residual standard deviation of a predicted FEV1 is rounded to three decimal places *first*, and the lower limit of normal is then derived from that already-rounded residual. Deriving either downstream value from an unrounded input produces a different answer at the boundaries and is incorrect.

### 2.7. Version Guarding on Parent Records

Two write operations in this API are guarded by optimistic concurrency control against the current `version` of their **parent** record. In both cases the version field is a required, non-optional member of the request body; omitting it is a malformed request.

Issuing a pre-test medication hold against a test order requires the body field `expected_order_version`, carrying the `version` of that `TestOrder` as the client last observed it. If the value does not equal the order's current `version`, the request is rejected with `ERR_STALE_ORDER_VERSION` (HTTP 412) and no hold is created. The guard is essential here precisely because the write is otherwise unblocked: a new hold for a medication class that already has a `PENDING` or `VIOLATED` hold legitimately supersedes its predecessor, so no state precondition would stop it, and the version check is what resolves which view of the order the instruction was actually written against.

Assigning an interpretation report to an accepted study requires the body field `expected_session_version`, carrying the `version` of that `TestSession` as the client last observed it. If the value does not equal the study's current `version`, the request is rejected with `ERR_STALE_SESSION_VERSION` (HTTP 412) and no report is created. Again the guard is doing real work: a fresh assignment is allowed to supersede a still-`ASSIGNED` report, driving the earlier one to `REASSIGNED`, so a client working from a stale read of the study would otherwise silently displace an assignment it had never seen.

No other endpoint in this API accepts a version field of any kind, and no endpoint outside these two performs a version comparison.

### 2.8. Cascade Semantics Across the Device–Study–Order Graph

The laboratory's records form a graph rather than a tree, and a single request routinely mutates records several hops away from the one it addressed. Cascades in this API are **immediate and complete**: they are applied inside the originating request, before its response is returned, and each affected record independently refreshes its own `updated_at` and increments its own `version`.

Four propagation chains matter enough to state globally. First, when a device becomes `QUARANTINED`, every study standing on that device whose `session_status` is `SCHEDULED` or `IN_PROGRESS` is driven to `ABORTED`; those studies are processed in ascending `created_at` order, so the outcome of a multi-study quarantine is deterministic. Second, when a study becomes `ABORTED`, its order steps back from `IN_TESTING` to `READY` and the order's `abort_count` rises by one — skipped when the order is itself the cause and already `CANCELLED` — every bronchoprovocation run on that study whose `status` is `ARMED` or `IN_PROGRESS` terminates as `ABORTED_SAFETY` with its rescue-lot ledger settled, every interpretation report on that study whose `status` is `ASSIGNED` becomes `REASSIGNED` with that interpreter's `open_report_count` decremented, and, when the study was `IN_PROGRESS`, the device becomes `SOILED` unless it is currently `QUARANTINED`, in which case it stays `QUARANTINED` and only `last_session_end_at` and `sessions_since_filter_change` are updated. Third, when a study becomes `REPORTED`, its order advances from `IN_TESTING` to `COMPLETED` and the patient's `completed_order_count` rises by one. Fourth, when an order is cancelled, every one of its `PENDING` medication holds becomes `SUPERSEDED` and every one of its live studies aborts.

A cascade never stops halfway and never skips a hop. A single failing biologic control submitted against one device therefore travels four hops inside one request: the device is quarantined, every live study on it aborts, each of those studies hands its order back to `READY`, and each aborted study's live challenge run terminates and settles the rescue lot it had reserved doses from.

### 2.9. Path Resolution and the Order of Validation

Requests whose URL contains more than one identifier are resolved strictly left to right, and the first identifier that fails to resolve determines the response. The path identifiers this API uses are `{device_id}`, `{staff_id}`, `{patient_id}`, `{order_id}`, `{hold_id}`, `{session_id}`, `{run_id}`, `{report_id}`, `{lot_id}`, `{maneuver_id}` and `{event_id}` — the last of which appears in two distinct collections, resolving to a device quality record on the quality-event read route and to a custody record on the custody-event read route.

Identifiers arriving in the **request body** are resolved after path identifiers, and among themselves in the fixed left-to-right order in which they are declared for that operation: `patient_id`, then `order_id`, then `device_id`, then `rescue_lot_id`, then `subject_staff_id`. Each resolves to its own not-found code: `ERR_PATIENT_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_DEVICE_NOT_FOUND`, `ERR_LOT_NOT_FOUND` and `ERR_STAFF_NOT_FOUND` respectively, all HTTP 404.

Beyond resolution, every request runs a single fixed ladder of checks. **The ladder is evaluated in ascending order and the first rule that is violated determines the entire response; no later rule is evaluated.** This ordering is part of the contract, because many requests can fail several rules at once and only one code may be returned. The ladder, in order:

1. **Header presence and role validity** — `ERR_UNAUTHENTICATED` (401), on every endpoint.
2. **Role authorisation for the target operation** — `ERR_ROLE_NOT_PERMITTED` (403), on every endpoint.
3. **Staff identity resolution for the three entity-backed roles** — `ERR_STAFF_IDENTITY_MISMATCH` (403), on every endpoint whose authorised roles include `Technologist`, `OrderingPhysician` or `InterpretingPhysician`.
4. **`{device_id}` resolves** — `ERR_DEVICE_NOT_FOUND` (404), on the single-device read, quality-event submission and return-to-service.
5. **`{staff_id}` resolves** — `ERR_STAFF_NOT_FOUND` (404), on the single-staff read.
6. **`{patient_id}` resolves** — `ERR_PATIENT_NOT_FOUND` (404), on the single-patient read.
7. **`{order_id}` resolves** — `ERR_ORDER_NOT_FOUND` (404), on every order route and every order sub-resource route.
8. **`{hold_id}` resolves** — `ERR_HOLD_NOT_FOUND` (404), on hold attestation.
9. **`{session_id}` resolves** — `ERR_SESSION_NOT_FOUND` (404), on every study route and every study sub-resource route.
10. **`{run_id}` resolves** — `ERR_RUN_NOT_FOUND` (404), on every challenge-run route.
11. **`{report_id}` resolves** — `ERR_REPORT_NOT_FOUND` (404), on every interpretation-report route.
12. **`{event_id}` resolves to a device quality record** — `ERR_QUALITY_EVENT_NOT_FOUND` (404), on the single quality-event read.
13. **`{lot_id}` resolves** — `ERR_LOT_NOT_FOUND` (404), on the single rescue-lot read.
14. **Body foreign keys resolve**, in the declared order given above — the corresponding 404 code. This applies to order drafting, study scheduling, challenge-run arming and quality-event submission.
15. **Request shape** — `ERR_INVALID_REQUEST` (400), on every creating or modifying operation. The body must parse; every required field must be present and non-null; enum fields must carry declared values; numeric fields must lie in range (`height_cm` between 90.0 and 220.0 inclusive, `weight_kg` between 10.0 and 300.0 inclusive, `fvc_l`, `fev1_l` and `measured_volume_l` greater than 0, `dose_units` greater than 0, `expiratory_time_s` greater than 0, `scheduled_end_at` strictly later than `scheduled_start_at`, `applicable_age_min` no greater than `applicable_age_max`); and array fields must be non-empty with no duplicated member.
16. **Conditional field set for a device quality record** — `ERR_MISSING_EVENT_FIELDS` (422), on quality-event submission. The set required by `event_type` must be both complete and exclusive: any field belonging to a different `event_type` must be absent.
17. **Conditional field set for a custody record** — `ERR_MISSING_EVENT_FIELDS` (422), on custody-event submission.
18. **Ambient conditions in range** — `ERR_AMBIENT_OUT_OF_RANGE` (422), on quality-event submission whose `event_type` is `VOLUME_CALIBRATION` or `LEAK_CHECK`. `ambient_temp_c` must be a whole number from 20 through 27 inclusive, and `barometric_pressure_kpa` must lie between 80.00 and 110.00 inclusive.
19. **Natural-key uniqueness** — `ERR_DUPLICATE_IDENTIFIER` (409), on device registration (`device_code`), staff registration (`employee_code`), patient registration (`mrn`) and rescue-lot receipt (`lot_number`).
20. **Filter serial is genuinely new** — `ERR_FILTER_SERIAL_REUSED` (409), on quality-event submission whose `event_type` is `FILTER_REPLACEMENT`.
21. **`expected_order_version` matches the order's `version`** — `ERR_STALE_ORDER_VERSION` (412), on medication-hold issuance.
22. **`expected_session_version` matches the study's `version`** — `ERR_STALE_SESSION_VERSION` (412), on report assignment.
23. **Order state admits the operation** — `ERR_ORDER_STATE_INVALID` (409). Submission requires `DRAFT` or `INDICATION_REJECTED`; revision requires `DRAFT` or `INDICATION_REJECTED`; cancellation requires any non-terminal status; hold issuance requires `SUBMITTED`, `MED_HOLD_ISSUED` or `READY`; study scheduling requires `READY`.
24. **Hold state admits the operation** — `ERR_HOLD_STATE_INVALID` (409): attestation requires `PENDING`.
25. **Study execution state admits the operation** — `ERR_SESSION_STATE_INVALID` (409), on every study sub-resource write. Appending a maneuver requires `SCHEDULED`, `IN_PROGRESS` or `REJECTED`; quality finalization requires `IN_PROGRESS`; arming a challenge run requires `IN_PROGRESS`; assigning a report requires `ACCEPTED`; appending a custody record requires a non-terminal `session_status`.
26. **Challenge-run state admits the operation** — `ERR_RUN_STATE_INVALID` (409): both stepping and aborting require `ARMED` or `IN_PROGRESS`.
27. **Report state admits the operation** — `ERR_REPORT_STATE_INVALID` (409): signing requires `ASSIGNED` or `AMENDED`; amendment requires `SIGNED`.
28. **Device state admits the operation** — `ERR_DEVICE_NOT_AVAILABLE` (409): study scheduling and maneuver appending require `AVAILABLE`; return-to-service requires `QUARANTINED`.
29. **Coaching rounds not exhausted** — `ERR_MAX_REJECTION_ROUNDS_EXCEEDED` (409), when a maneuver is appended to a study whose `session_status` is `REJECTED`.
30. **Indication belongs to the administrative context** — `ERR_INDICATION_CONTEXT_MISMATCH` (422), on order submission.
31. **Bronchoprovocation is not contraindicated by airflow** — `ERR_CHALLENGE_CONTRAINDICATED` (422), on challenge-run arming.
32. **Device modality was actually requested** — `ERR_DEVICE_MODALITY_MISMATCH` (422), on study scheduling.
33. **Acting technologist is qualified and current** — `ERR_TECH_NOT_QUALIFIED` (403), on study scheduling and maneuver appending.
34. **Same-day volume calibration exists** — `ERR_CALIBRATION_STALE` (422), on study scheduling.
35. **Same-day biologic control exists and no failure streak is open** — `ERR_BIOLOGIC_CONTROL_MISSING` (422), on study scheduling.
36. **Between-patient infection control is complete** — `ERR_INFECTION_CONTROL_INCOMPLETE` (422), on both study scheduling and return-to-service.
37. **Same-day leak check exists where the modality demands one** — `ERR_LEAK_CHECK_MISSING` (422), on study scheduling.
38. **Biologic control subject is a valid third party** — `ERR_SELF_BIOLOGIC_CONTROL` (422), on quality-event submission whose `event_type` is `BIOLOGIC_CONTROL`.
39. **No medication hold is violated or still pending** — `ERR_MED_HOLD_VIOLATED` (422), on study scheduling.
40. **The withholding window has elapsed** — `ERR_MED_HOLD_NOT_ELAPSED` (422), on study scheduling.
41. **An unacceptable maneuver carries a coaching note** — `ERR_COACHING_NOTE_REQUIRED` (422), on maneuver appending.
42. **Segregation of duties** — `ERR_SEGREGATION_OF_DUTIES` (403), on report signing and on return-to-service.
43. **The ordered challenge agent matches** — `ERR_CHALLENGE_NOT_REQUESTED` (422), on challenge-run arming.
44. **Rescue medication is ready** — `ERR_RESCUE_NOT_READY` (422), on challenge-run arming.
45. **The cumulative dose ceiling is respected** — `ERR_MAX_DOSE_EXCEEDED` (422), on recording a challenge step.
46. **Custody tracking applies to this study at all** — `ERR_CUSTODY_NOT_APPLICABLE` (422), on custody-event submission.
47. **The custody act is the legal successor of the current custody state** — `ERR_CUSTODY_SEQUENCE_INVALID` (409), on custody-event submission.
48. **The custody chain is sealed** — `ERR_CUSTODY_NOT_SEALED` (422), on report signing.
49. **A witness attestation exists** — `ERR_WITNESS_ATTESTATION_MISSING` (422), on report signing.
50. **The device occupancy window is free** — `ERR_DEVICE_WINDOW_CONFLICT` (409), on study scheduling.
51. **The technologist is not over-committed in that window** — `ERR_TECHNOLOGIST_WINDOW_CONFLICT` (409), on study scheduling.
52. **An eligible interpreter exists** — `ERR_NO_ELIGIBLE_INTERPRETER` (422), on report assignment.
53. **An applicable reference equation set exists** — `ERR_NO_REFERENCE_EQUATION` (422), on study scheduling.
54. **The rescue lot has enough unreserved doses** — `ERR_RESCUE_DOSES_INSUFFICIENT` (409), on challenge-run arming. This stock check is deliberately last, after every safety gate, so that a lot which is simultaneously expired and short-stocked reports the safety failure rather than the stock failure.

Two consequences of this ordering deserve emphasis because they are easy to get backwards. A study scheduled onto a device that is not `AVAILABLE` reports the device-state conflict at rung 28, long before the quality gates at rungs 34 through 37 are consulted. And an order whose indication does not belong to its administrative context reports the hard context failure at rung 30, which pre-empts the softer modality-approval decision described in §3.4 entirely — so that order is never parked in `INDICATION_REJECTED`, because nothing about it is persisted at all.

### 2.10. Segregation of Duties on the Laboratory Floor

The laboratory's compliance posture rests on the principle that nobody clears their own work. Four rules implement it, and all four are enforced by the server rather than by procedure.

A technologist may never interpret a study they conducted. At signing time the acting `Staff` identifier is compared against the study's `technologist_staff_id`, and a match is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) even when that person genuinely holds an interpreting credential. The same exclusion is applied one step earlier, inside the interpreter selector, so that the study's own technologist is filtered out of the candidate pool before ranking rather than discovered at signing.

A technologist may never prove healthy a device their own failing measurement condemned. Returning a quarantined device to service requires two clearing quality records recorded after the quarantine, and each of them must have been performed by somebody other than the `quarantine_trigger_staff_id` the device is carrying; a violation is again `ERR_SEGREGATION_OF_DUTIES`.

A technologist may never serve as their own biologic control subject: the acting `Staff` identifier must differ from the `subject_staff_id` nominated on the measurement, and the nominated subject must genuinely be enrolled as a control with a stored baseline. Violations report `ERR_SELF_BIOLOGIC_CONTROL`.

Finally, the compliance witness attestation on a chain-of-custody record is reserved to `ComplianceAuditor`. A technologist who submits it — even one working on a study they otherwise own end to end — is rejected with `ERR_ROLE_NOT_PERMITTED`.

### 2.11. The Rescue-Dose Ledger

Bronchoprovocation testing is only safe if rescue bronchodilator is physically set aside before the provoking agent is given, and the API models that set-aside as a two-column ledger on each rescue medication lot. `doses_at_receipt` is fixed at receipt and never changes; it is the conserved total. `doses_remaining` counts doses physically still in the lot and falls only when rescue is actually administered. `doses_reserved` counts doses held against live commitments and moves in both directions.

Two invariants must hold after every single operation that touches a lot, without exception:

- **Conservation.** `doses_remaining`, plus the sum of `rescue_doses_administered` across every challenge run that has ever drawn on the lot, equals `doses_at_receipt`.
- **Reservation.** `doses_reserved` equals 4 multiplied by the number of challenge runs on that lot whose `status` is currently `ARMED` or `IN_PROGRESS` — a reservation of four doses per live run.

Both the reservation size and the administered quantity are four doses. When a lot's `doses_remaining` reaches exactly 0 after a debit, the lot moves from `status` `STOCKED` to `DEPLETED`.

### 2.12. Deterministic Selector Policy

Two operations in this API choose a record out of a candidate pool rather than accepting a client's nomination: the reference equation set pinned onto a new study, and the interpreting physician assigned to an accepted one. Both follow the same discipline. An eligibility filter is applied first, and if it leaves the pool empty the request fails with that selector's own error code rather than falling back to a default. The surviving candidates are then ranked by the selector's declared keys, and `created_at` ascending is always the final key, so the ranking is total. Entity identifiers never participate in ranking, and no selector consults `id` as a tie-break under any circumstances.

## 3. Business Logic & Workflows

### 3.1. The Laboratory Registry: Staff, Patients, Reference Equations and Rescue Stock

Before any testing can happen, a `LabManager` populates the registry. **Staff** rows are the laboratory's people. Each is registered with an `employee_code`, which is the payroll identifier and must be non-empty and unique across all staff — a collision reports `ERR_DUPLICATE_IDENTIFIER` — together with a `full_name` that is printed on reports and chain-of-custody records. The `role_type` decides which header role that person may authenticate as and is one of `TECHNOLOGIST`, `ORDERING_PHYSICIAN` or `INTERPRETING_PHYSICIAN`. The highest pulmonary credential held is recorded in `credential`, one of `CPFT`, `RPFT` or `MD`. Annual competency is tracked by `competency_expires_on`, a UTC calendar date in `YYYY-MM-DD` form whose last valid day is that date **inclusive**, so a technologist whose competency expires on the current logical date is still current. `credentialed_modalities` is a non-empty array of distinct modality values drawn from `SPIROMETRY`, `DLCO` and `PLETHYSMOGRAPHY`, and it governs both what that person may operate and what they may interpret.

Duty posture and interpreting capacity are also registry facts. A staff member's `status` is either `ON_DUTY` or `OFF_DUTY` and defaults to `ON_DUTY`; only `ON_DUTY` staff enter the interpreter candidate pool. `max_concurrent_reports` is that person's declared interpreting capacity, an integer of at least 1 defaulting to 1, and it is consulted twice — once by the candidate filter and once, summed across the roster, by the turnaround load tier. Alongside it the server maintains `open_report_count`, which is the number of interpretation reports naming that person as interpreter whose `status` is `ASSIGNED` or `AMENDED`. It starts at 0 and is recomputed on every report assignment, signature, amendment and supersession.

A subset of staff also serve as the laboratory's daily quality subjects. Setting `is_biologic_control` to true — it defaults to false — marks such a person, and for them three further fields are required: `baseline_fev1_l` and `baseline_fvc_l` record the established control baseline in litres, and `baseline_established_on` records the UTC calendar date on which that baseline was established. That last date is not decorative: it is what decides which of the two biologic-control comparison variants is used, as §3.2 explains.

**Patients** may be registered by either a `LabManager` or an `OrderingPhysician`. A patient carries an `mrn` — the medical record number, non-empty and unique across patients, again with `ERR_DUPLICATE_IDENTIFIER` on collision — a `full_name`, a `birth_date` as a `YYYY-MM-DD` UTC calendar date, a `sex` of either `MALE` or `FEMALE`, a `height_cm` between 90.0 and 220.0 centimetres, a `weight_kg` between 10.0 and 300.0 kilograms, and a `smoking_status` of `NEVER`, `FORMER` or `CURRENT`. Height is the dominant regressor of every predicted value in the system; weight and smoking history are recorded for the report header and the interpretation template and feed no computation. The server derives `age_years` as the number of completed whole years from `birth_date` to the current logical clock date: the difference in calendar years, reduced by one when the current month-and-day pair falls earlier than the birth month-and-day pair. It also maintains `completed_order_count`, the number of that patient's orders whose `status` is `COMPLETED`, starting at 0.

**Reference equation sets** are the published regressions the laboratory interprets against, and only a `LabManager` publishes them. A set is identified by its `equation_code` — a non-empty published identifier such as `GLI_2012_CAUCASIAN` or `NHANES_III` — and scoped by three eligibility facts: `modality_scope`, a non-empty array of distinct modality values naming the modalities the set may be selected for; `sex_scope`, one of `MALE`, `FEMALE` or `ANY`; and the inclusive age band `applicable_age_min` through `applicable_age_max`. The set carries the published lower-limit-of-normal percentile in `lln_percentile` (for example 5.0), which serves as the selector's secondary ranking key, and `ratio_lln`, the lower limit of normal for the FEV1-over-FVC ratio (for example 0.700), which drives the interpretation pattern decision. Six regression coefficients define the predicted values: `a_fev1`, `b_fev1` and `c_fev1` are respectively the intercept in litres, the height coefficient in litres per centimetre, and the age coefficient in litres per decade for predicted FEV1, and `a_fvc`, `b_fvc` and `c_fvc` are the corresponding three for predicted FVC. `rsd_frac` is the residual standard deviation expressed as a fraction of the predicted value, for example 0.130. Finally `bd_criterion`, one of `PCT_BASELINE_2005` or `PCT_PREDICTED_2021`, decides which bronchodilator-response variant every study bound to this set must use.

Publication posture lives in `status`, which is `ACTIVE` on creation and may later become `SUPERSEDED`; only `ACTIVE` sets enter the selector pool. Publishing a new set whose `equation_code` matches an existing `ACTIVE` set moves that earlier set to `SUPERSEDED`, and it immediately leaves the candidate pool. Supersession is forward-looking only: a study that already pinned the older set keeps interpreting against the snapshot it took, which is why the study stores both `reference_equation_code` and `ratio_lln` as copies rather than following the link.

**Rescue medication lots** are the laboratory's physical safety stock. Each is received with a `lot_number` — manufacturer lot, non-empty, unique, `ERR_DUPLICATE_IDENTIFIER` on collision — a `drug` of either `ALBUTEROL_MDI` or `ALBUTEROL_NEB`, an integer `doses_at_receipt` of at least 0, and an `expires_on` UTC calendar date whose last usable day is that date inclusive. On receipt, `doses_remaining` is initialised to `doses_at_receipt`, `doses_reserved` is 0 and `status` is `STOCKED`. The three lot statuses are `STOCKED`, `EXPIRED` and `DEPLETED`; the readiness gate that guards bronchoprovocation consults `status` before it ever looks at a dose count.

### 3.2. Devices and the Daily Quality Program

A **device** is registered by a `LabManager` with just two facts: a `device_code`, the laboratory asset tag, non-empty and unique across devices with `ERR_DUPLICATE_IDENTIFIER` on collision, and a `modality` naming which pulmonary measurement the instrument performs — `SPIROMETRY`, `DLCO` or `PLETHYSMOGRAPHY`. It begins life in `status` `NEW`, with `sessions_since_filter_change` at 0 and `version` at 1. The four device statuses are `NEW`, `AVAILABLE`, `SOILED` and `QUARANTINED`, and the status gates every study created against that device.

Around that status the server maintains a quality dossier, every field of which is derived from the device's append-only quality log rather than supplied by a client. `last_calibration_at` holds the instant of the most recent volume calibration on this device **that passed**, and is null until one exists. `last_calibration_error_pct` holds the error percentage of the most recent volume calibration whether it passed or failed, and is likewise null until one exists — the asymmetry between those two fields is deliberate and load-bearing. `last_biologic_control_date` holds the UTC calendar date of the most recent biologic control whose verdict was either a pass or a warning, and `consecutive_biologic_failures` counts biologic-control failures accumulated since the last passing one. `last_session_end_at` holds the scheduled end of the most recent study on this device that has left the live states — that is, the most recent study to reach an accepted, rejected, reported or aborted execution state — and is null until one exists. `current_filter_serial` holds the serial of the filter most recently fitted, and `sessions_since_filter_change` counts the studies that have reached an accepted, rejected or reported execution state since that fitting. Three further fields describe an active quarantine: `quarantined_at` is the logical instant at which the status last became `QUARANTINED`, `quarantine_reason` is either `CALIBRATION_FAILED` or `BIOLOGIC_CONTROL_FAILED`, and `quarantine_trigger_staff_id` names the technologist whose failing measurement caused it. All three are null whenever the device is not quarantined.

Only a `Technologist` may append to a device's quality log, and each appended record names its `device_id` from the URL path, its `performed_by_staff_id` from the acting technologist's `X-User-ID` header, and its `performed_at` from the logical clock. Every record carries an `event_type` — one of `VOLUME_CALIBRATION`, `LEAK_CHECK`, `BIOLOGIC_CONTROL`, `FILTER_REPLACEMENT` or `HIGH_LEVEL_DISINFECT` — and an optional free-text `note` that is accepted for every type. The remaining input fields are conditional on the type, and the conditional set must be both complete and exclusive: `VOLUME_CALIBRATION` requires `measured_volume_l`, `ambient_temp_c` and `barometric_pressure_kpa`; `LEAK_CHECK` requires `ambient_temp_c` and `barometric_pressure_kpa`; `BIOLOGIC_CONTROL` requires `subject_staff_id`, `measured_fev1_l` and `measured_fvc_l`; `FILTER_REPLACEMENT` requires `filter_serial`; and `HIGH_LEVEL_DISINFECT` requires `dwell_minutes`. Supplying a field that belongs to a different type, or omitting one the declared type needs, reports `ERR_MISSING_EVENT_FIELDS`. Each record ends with an `outcome` — one of `PASS`, `WARN`, `FAIL`, `COMPLETE` or `INCOMPLETE` — and, where the verdict is adverse, a `failure_reason` of `CAL_TOLERANCE_EXCEEDED`, `BCS_DEVIATION_EXCEEDED` or `DWELL_TIME_SHORT`. `failure_reason` is null whenever the outcome is `PASS`, `WARN` or `COMPLETE`.

**Volume calibration** is the day's first act and the one with the most arithmetic behind it. The technologist discharges a certified 3.000-litre calibration syringe into the device and reports the uncorrected volume the device read back in `measured_volume_l`, along with the ambient temperature in whole degrees Celsius and the station barometric pressure in kilopascals. Ambient temperature must be a whole number from 20 through 27 inclusive and pressure must fall between 80.00 and 110.00 kilopascals inclusive; anything else is `ERR_AMBIENT_OUT_OF_RANGE`. Those bounds exist so that the saturated water-vapour pressure table can be exhaustive over the accepted domain. The table is keyed by the whole-degree ambient temperature and gives, in kilopascals: 2.34 at 20 degrees, 2.49 at 21, 2.64 at 22, 2.81 at 23, 2.98 at 24, 3.17 at 25, 3.36 at 26 and 3.57 at 27.

From those three inputs the server derives `btps_factor`, the correction from ambient conditions to body temperature and pressure, saturated. It is the product of two ratios. The first ratio is body temperature in kelvin, 310.15, divided by the ambient temperature converted to kelvin by adding 273.15 to the reported whole-degree value. The second ratio is the barometric pressure minus the water-vapour pressure looked up for that temperature, divided by the barometric pressure minus 6.27, which is the water-vapour pressure at body temperature. The product is rounded to four decimal places. Next, `corrected_volume_l` is `measured_volume_l` multiplied by `btps_factor`, rounded to three decimal places — and that rounding happens before anything else consumes the value. Then `error_pct` is the absolute difference between `corrected_volume_l` and the 3.000-litre syringe volume, divided by 3.000 and multiplied by 100, rounded to two decimal places. Deriving `error_pct` from the unrounded product instead of from the rounded `corrected_volume_l` yields a different answer near the tolerance boundary and is wrong.

The verdict is a strict comparison against a tolerance of 3.00 percent: the calibration fails when `error_pct` is **strictly greater than** 3.00, and passes when it is exactly 3.00 or less. A passing calibration sets `failure_reason` to null, refreshes `last_calibration_at` to the record's `performed_at`, and stores `error_pct` into `last_calibration_error_pct`. It also promotes the device from `NEW` to `AVAILABLE` — but only from `NEW`. A quarantined device is cleared exclusively by an explicit return-to-service action, and a soiled device exclusively by completing the infection-control pair described in §3.3, so neither is promoted by a passing calibration however good the numbers are. A failing calibration sets `failure_reason` to `CAL_TOLERANCE_EXCEEDED`, stores `error_pct` into `last_calibration_error_pct` while pointedly **not** advancing `last_calibration_at` — only a pass refreshes calibration currency — and drives the device to `QUARANTINED`, stamping `quarantined_at` with the record's `performed_at`, `quarantine_reason` with `CALIBRATION_FAILED` and `quarantine_trigger_staff_id` with the acting technologist. A device failing calibration out of `NEW` simply becomes quarantined; a device failing out of `AVAILABLE` becomes quarantined and drags every live study on it down with it, as §3.3 details. Either way the device's `version` increments.

**Leak checks** are the simpler ritual: they record `ambient_temp_c` and `barometric_pressure_kpa` and nothing else, their `outcome` is always `COMPLETE` and their `failure_reason` always null, and no device field changes. Their only consequence is that the record now satisfies the same-day leak-check requirement that closed-circuit modalities carry — a requirement that binds `DLCO` and `PLETHYSMOGRAPHY` devices and does not exist at all for `SPIROMETRY` devices, so the identical scheduling request is legal on one instrument and refused with `ERR_LEAK_CHECK_MISSING` on another.

**Biologic control** is where the same numbers can yield two different verdicts. A healthy enrolled subject blows on the device, and the technologist submits the subject's identifier in `subject_staff_id` together with `measured_fev1_l` and `measured_fvc_l`. The acting technologist's own identifier must differ from `subject_staff_id`, and the nominated subject must have `is_biologic_control` true with a non-null `baseline_fev1_l`; otherwise the submission is refused with `ERR_SELF_BIOLOGIC_CONTROL`. The measured FVC is stored for the record but the deviation computation consumes only the FEV1.

Which comparator that FEV1 is measured against depends on how stale the subject's stored baseline has become, counted in whole days from `baseline_established_on` to the current logical clock date. When that age is 180 days or fewer, the variant is `ABSOLUTE_BASELINE` and the comparator is the subject's stored `baseline_fev1_l` — a value fixed at enrolment. When the age exceeds 180 days, the variant is `ROLLING_MEAN`: the server assembles the three most recent prior biologic-control records for this same device and this same subject whose `outcome` was `PASS` or `WARN`, ordered by `performed_at` descending with `created_at` descending as the tie-break, and takes the mean of their `measured_fev1_l` values rounded to three decimal places as the comparator. Failed records never enter that window. If fewer than three qualifying prior records exist, the variant falls back to `ABSOLUTE_BASELINE` and the stored baseline is used after all. Whichever path was taken is recorded in `deviation_variant`, and `rolling_mean_fev1_l` holds the computed mean under the rolling variant and is null under the absolute one.

`deviation_pct` is then the absolute difference between the submitted `measured_fev1_l` and the comparator, divided by the comparator, multiplied by 100 and rounded to two decimal places. The verdict is banded with inclusive upper edges: a deviation of 5.00 percent or less is `PASS`, a deviation above 5.00 but not above 10.00 percent is `WARN`, and anything above 10.00 percent is `FAIL`. A `PASS` advances `last_biologic_control_date` to the date part of the record's `performed_at` and resets `consecutive_biologic_failures` to 0. A `WARN` also advances `last_biologic_control_date` but leaves `consecutive_biologic_failures` exactly as it was. A `FAIL` does neither — it stamps `failure_reason` with `BCS_DEVIATION_EXCEEDED`, increments `consecutive_biologic_failures` by one, and quarantines the device with `quarantine_reason` `BIOLOGIC_CONTROL_FAILED`, `quarantined_at` set to the record's `performed_at` and `quarantine_trigger_staff_id` set to the acting technologist. Because a failure never advances `last_biologic_control_date`, the daily-quality gate on study scheduling stays unsatisfied, and the device's `version` increments.

Because the drift-tolerant rolling comparator and the fixed enrolment comparator disagree, an identical `measured_fev1_l` can pass under one variant and warn or fail under the other. That is intended behaviour, not a defect: the variant is selected by baseline age, and an implementation may not choose whichever comparator it finds more convenient.

### 3.3. Quarantine, Return to Service and Between-Patient Infection Control

A quarantined device is out of the laboratory's hands until a `LabManager` explicitly returns it to service, supplying a `clearance_note` that records the engineering or clinical judgement behind the decision. Four conditions must all hold, and the endpoint refuses a device whose `status` is anything other than `QUARANTINED` with `ERR_DEVICE_NOT_AVAILABLE`. First, at least one volume calibration on this device must have `outcome` `PASS` and a `performed_at` strictly later than `quarantined_at`. Second, at least one biologic control on this device must have `outcome` `PASS` — and here a `WARN` explicitly does not qualify, even though a warning is enough to advance `last_biologic_control_date` for daily-quality purposes — again with `performed_at` strictly later than `quarantined_at`. Third, `consecutive_biologic_failures` must be exactly 0. Fourth, neither of those two clearing measurements may have been performed by the technologist recorded in `quarantine_trigger_staff_id`; the person whose measurement condemned the device may not be the person whose measurement redeems it, and a violation reports `ERR_SEGREGATION_OF_DUTIES`. When all four hold, the `status` returns to `AVAILABLE` and `quarantined_at`, `quarantine_reason` and `quarantine_trigger_staff_id` are all cleared to null. Failing any of the evidence conditions reports `ERR_QUARANTINE_CLEARANCE_INCOMPLETE`. Requests that satisfy every gate leave the device's `version` one higher than before.

Between patients the device follows a different and shorter arc. A device that has just been used is soiled, and the laboratory's infection-control protocol requires two distinct acts before another patient may breathe into it: a new filter must be fitted and the instrument must be high-level disinfected. **Filter replacement** carries a single input, `filter_serial`, the serial of the filter being fitted. It must not equal the device's `current_filter_serial`, because refitting the filter that is already installed is not a filter change; that reports `ERR_FILTER_SERIAL_REUSED`. A filter replacement always computes `outcome` `COMPLETE`, sets `current_filter_serial` to the supplied serial and resets `sessions_since_filter_change` to 0. **High-level disinfection** carries `dwell_minutes`, the number of whole minutes the instrument sat in disinfectant. A dwell of at least 20 minutes computes `outcome` `COMPLETE` with `failure_reason` null; a shorter dwell computes `outcome` `INCOMPLETE` with `failure_reason` `DWELL_TIME_SHORT`, and an incomplete disinfection is worth nothing to the protocol — the device stays `SOILED` and the disinfection must be repeated in full.

Whichever of the two events is appended second is the one that clears the device, and it clears it only when both qualifying events postdate the study that soiled it. Concretely, after appending the event, the device must carry at least one filter replacement with `outcome` `COMPLETE` and at least one high-level disinfection with `outcome` `COMPLETE`, both with `performed_at` strictly later than `last_session_end_at`. When that pair exists the `status` returns from `SOILED` to `AVAILABLE`; otherwise the device stays soiled and waits for its partner event. Because the comparison is against `last_session_end_at`, hygiene performed before the last patient never counts toward the next one. That same pair test is what the infection-control gate of §2.9 rung 36 evaluates on study scheduling and on return-to-service, and it always reads whatever `last_session_end_at` the device is carrying: when the field is null — a device that has never hosted a study — the pair must nonetheless exist, with hygiene recorded at any time qualifying, so a device carrying no `COMPLETE` filter replacement or no `COMPLETE` high-level disinfection at all fails that gate.

Devices become soiled automatically rather than by request. Whenever a study leaves the live `IN_PROGRESS` execution state for `ACCEPTED` or `ABORTED`, the device moves from `AVAILABLE` to `SOILED`, `last_session_end_at` is set to that study's `scheduled_end_at` and `sessions_since_filter_change` increases by one. A study finalized as `REJECTED` is the interesting case: it soils the device only when the post-increment `rejection_round` has reached the ceiling of 2, because below that ceiling the same patient is still standing at the same instrument for another coaching round and the device must stay `AVAILABLE` for them. One further subtlety attaches to abort: when a study is aborted because its device was just quarantined, the device is already `QUARANTINED`, and quarantine outranks soiling — the device keeps `status` `QUARANTINED`, and only `last_session_end_at` and `sessions_since_filter_change` are updated.

Quarantine also propagates outward. The moment a device becomes `QUARANTINED`, every study on that device whose `session_status` is `SCHEDULED` or `IN_PROGRESS` is aborted with `abort_reason` `DEVICE_QUARANTINED`, oldest study first by `created_at`, and each of those aborts then drives its own downstream consequences — the parent order back from `IN_TESTING` to `READY` with `abort_count` incremented, every live challenge run on the study to `ABORTED_SAFETY` with `stop_reason` `SESSION_ABORTED`, the corresponding rescue-lot ledger movements, and any report still `ASSIGNED` on that study to `REASSIGNED` with its interpreter's `open_report_count` decremented.

### 3.4. The Test Order: Indication Gates, Revision and Pre-Test Medication Holds

An `OrderingPhysician` opens an order for a patient. The request supplies `patient_id` naming the subject, an `indication_code` drawn from `DYSPNEA_EVALUATION`, `ASTHMA_DIAGNOSIS`, `COPD_STAGING`, `PREOP_ASSESSMENT`, `DISABILITY_ASSESSMENT`, `OCCUPATIONAL_SURVEILLANCE_ANNUAL` and `RESTRICTIVE_DISEASE_EVALUATION`, a non-empty `requested_modalities` array of distinct modality values, and a `test_context` of `ROUTINE_CLINICAL`, `DISABILITY_EVALUATION` or `OCCUPATIONAL_SURVEILLANCE`. Three optional inputs complete the picture: `bronchodilator_requested`, a boolean defaulting to false, states whether post-bronchodilator spirometry is wanted; `challenge_type`, defaulting to `NONE` and otherwise `METHACHOLINE` or `MANNITOL`, names the bronchoprovocation agent; and `current_medication_classes`, defaulting to the empty array, lists the respiratory medications the patient is currently taking as distinct values from `SABA`, `SAMA`, `LABA`, `LAMA`, `ICS_LABA`, `ANTIHISTAMINE` and `CAFFEINE`. The server records `ordering_staff_id` from the acting physician's `X-User-ID` header, sets `status` to `DRAFT`, `abort_count` to 0, and leaves `rejection_reason`, `hold_release_at` and `cancellation_reason` null. While the order is a draft the physician who owns it may revise `indication_code`, `requested_modalities`, `bronchodilator_requested` and `challenge_type`, supplying any subset of the four; supplied fields replace their stored values and omitted fields are left untouched.

Submission runs two gates that differ sharply in character, and the order in which they run is the whole point. The **first gate is hard and administrative**: `indication_code` must belong to the order's `test_context`. A `test_context` of `DISABILITY_EVALUATION` admits only `DISABILITY_ASSESSMENT`; a `test_context` of `OCCUPATIONAL_SURVEILLANCE` admits only `OCCUPATIONAL_SURVEILLANCE_ANNUAL`; and a `test_context` of `ROUTINE_CLINICAL` admits `DYSPNEA_EVALUATION`, `ASTHMA_DIAGNOSIS`, `COPD_STAGING`, `PREOP_ASSESSMENT` or `RESTRICTIVE_DISEASE_EVALUATION`. A mismatch is `ERR_INDICATION_CONTEXT_MISMATCH` at HTTP 422 and nothing whatsoever is persisted — the order stays exactly as it was.

The **second gate is soft and clinical**, and it is checked only once the first has passed. Every entry in `requested_modalities` must appear in the approved list for the order's `indication_code`, where the fixed table reads: `DYSPNEA_EVALUATION` admits `SPIROMETRY` and `DLCO`; `ASTHMA_DIAGNOSIS` admits `SPIROMETRY` alone; `COPD_STAGING` admits `SPIROMETRY`, `DLCO` and `PLETHYSMOGRAPHY`; `PREOP_ASSESSMENT` admits `SPIROMETRY` and `DLCO`; `DISABILITY_ASSESSMENT` admits `SPIROMETRY`, `DLCO` and `PLETHYSMOGRAPHY`; `OCCUPATIONAL_SURVEILLANCE_ANNUAL` admits `SPIROMETRY` alone; and `RESTRICTIVE_DISEASE_EVALUATION` admits `SPIROMETRY`, `PLETHYSMOGRAPHY` and `DLCO`. In addition, a `challenge_type` other than `NONE` is permitted only when `indication_code` is `ASTHMA_DIAGNOSIS`. Failing either of those two clinical conditions is **not** a client error: the order moves to `INDICATION_REJECTED` and the response is **HTTP 200 carrying the order body**, because an unapproved indication is a laboratory workflow state that the ordering physician is expected to see and correct. `rejection_reason` records which condition failed — `MODALITY_NOT_APPROVED_FOR_INDICATION` when a modality is unapproved, and `CHALLENGE_INDICATION_MISMATCH` otherwise. Because the hard gate pre-empts the soft one, an order that is wrong in both ways never reaches `INDICATION_REJECTED`; it is refused outright with 422.

An order sitting in `INDICATION_REJECTED` is revised through the same update operation the draft used, and applying a revision returns it to `DRAFT` and clears `rejection_reason` to null. That closes the revision cycle `DRAFT` → `INDICATION_REJECTED` → `DRAFT` → `SUBMITTED`, which may be traversed as many times as the physician needs. Only the physician recorded in `ordering_staff_id` may submit, revise or cancel the order; anyone else, including a different `OrderingPhysician`, is refused.

Where a clean submission lands depends on the patient's medication list. When `current_medication_classes` is non-empty the order becomes `SUBMITTED` and waits for the laboratory to issue withholding instructions. When `current_medication_classes` is the empty array there is nothing to withhold, so submission takes the order directly to `READY` with `hold_release_at` remaining null. Either way `rejection_reason` is cleared.

**Medication holds** are the technologist's instrument for enforcing the pre-test withholding window, and each hold covers exactly one `medication_class`. Issuing one requires the class to be a member of the order's `current_medication_classes` — instructing a patient to withhold a drug they are not taking is refused — and requires the client to state which version of the order it read, in the mandatory `expected_order_version` body field described in §2.7. The server stamps `instructed_at` from the logical clock, reads `required_hold_hours` from the fixed per-class table (`SABA` 6 hours, `SAMA` 8, `LABA` 24, `LAMA` 36, `ICS_LABA` 24, `ANTIHISTAMINE` 72 and `CAFFEINE` 8) and computes that hold's own `release_at` as `instructed_at` plus `required_hold_hours` hours. The new hold's `status` is `PENDING`, `attestation_result` and `attested_at` are null, and its `order_id` is taken from the path. Any earlier hold on the same order for the same `medication_class` whose `status` is `PENDING` or `VIOLATED` is moved to `SUPERSEDED`, so a class never has two live instructions.

The order's own `hold_release_at` is then recomputed as the **maximum** of `instructed_at` plus that class's hold hours, taken over every hold on the order whose `status` is `PENDING` or `ATTESTED`. Superseded holds drop out of that set entirely, and so does a violated one. When the participating set is empty, `hold_release_at` is null. Because each hold keeps the `instructed_at` it was originally issued with, replacing one class's hold restarts only that class's window and leaves the others exactly where they were; and because the aggregate is a maximum, the single longest-acting class governs the whole order. The first hold on a `SUBMITTED` order takes it to `MED_HOLD_ISSUED`; a second or later hold leaves it there.

At check-in the technologist attests what the patient actually did, supplying `attestation_result` as either `WITHHELD` or `TAKEN`. The hold must still be `PENDING` — attesting an already-resolved hold reports `ERR_HOLD_STATE_INVALID` — and `attested_at` is stamped from the logical clock. `WITHHELD` moves the hold to `ATTESTED`; `TAKEN` moves it to `VIOLATED`, and because a violated hold leaves the participating set, `hold_release_at` is recomputed over the remaining `PENDING` and `ATTESTED` holds. Once no non-superseded hold on the order is still `PENDING`, the order advances from `MED_HOLD_ISSUED` to `READY` — and this happens for either attestation result, which is the trap worth stating plainly: **`READY` does not mean the patient complied.** A `VIOLATED` hold leaves the order `READY` while independently blocking study creation with `ERR_MED_HOLD_VIOLATED`. The remediation loop is to issue a replacement hold for that class, which supersedes the violation and pushes the order from `READY` back to `MED_HOLD_ISSUED` — deliberately removing it from the schedulable set — and then to attest the replacement `WITHHELD`, which returns it to `READY` with the violation superseded and the block lifted.

Cancellation is available from any non-terminal order state — `DRAFT`, `SUBMITTED`, `INDICATION_REJECTED`, `MED_HOLD_ISSUED`, `READY` or `IN_TESTING` — and records the supplied `cancellation_reason`. From `COMPLETED` or `CANCELLED` the call is refused with `ERR_ORDER_STATE_INVALID`. A cancellation moves every `PENDING` hold on the order to `SUPERSEDED`, sets the order's `hold_release_at` to null, and aborts every study for that order whose `session_status` is `SCHEDULED` or `IN_PROGRESS` with `abort_reason` `ORDER_CANCELLED`, oldest first by `created_at`. Those aborts do not bounce the order back to `READY`, since it is already cancelled.

The order's two remaining system-managed transitions close the loop with the laboratory floor. When a study for the order is aborted for any reason, the order returns from `IN_TESTING` to `READY` and `abort_count` increases by one, so the study can be rescheduled onto another instrument. When a study for the order reaches `REPORTED`, the order becomes `COMPLETED` and the patient's `completed_order_count` increases by one.

### 3.5. Scheduling a Study onto a Device

A `Technologist` schedules a study by naming the `order_id` to be executed, the `device_id` that will be occupied, and the occupancy window as `scheduled_start_at` and `scheduled_end_at`, where the end must be strictly after the start. The server records `technologist_staff_id` from the acting technologist's `X-User-ID` header, sets `session_status` to `SCHEDULED`, `rejection_round` to 0 and `quality_grade` to its default of `F`, and initialises `custody_status` to `NOT_APPLICABLE` when the order's `test_context` is `ROUTINE_CLINICAL` and to `CUSTODY_OPEN` otherwise. It also drives the order from `READY` to `IN_TESTING`. Everything else about the new study — the best values, the repeatability deltas, `abort_reason`, `turnaround_minutes`, `technologist_comment` and the whole bronchodilator group — begins null or at its default.

Scheduling is the most heavily gated operation in the system, and the gates are checked in the priority order given in §2.9. The order must be `READY`. The device must be `AVAILABLE`. The device's `modality` must be a member of the order's `requested_modalities`, since occupying a plethysmograph for a study that never asked for plethysmography is a booking error. The acting technologist's `credentialed_modalities` must contain the device's `modality` and their `competency_expires_on` must be on or after the current logical date. The device must carry a volume calibration with `outcome` `PASS` whose `performed_at` falls on or after the start of the current logical UTC day. `last_biologic_control_date` must equal the current logical UTC date — meaning a biologic control with `outcome` `PASS` or `WARN` was recorded today — and `consecutive_biologic_failures` must be 0. The infection-control pair must be satisfied: a filter replacement with `outcome` `COMPLETE` and a high-level disinfection with `outcome` `COMPLETE` both performed strictly after `last_session_end_at`, or, when `last_session_end_at` is null because the device has never been used, at any time since registration. Conditionally on modality, a `DLCO` or `PLETHYSMOGRAPHY` device additionally needs a leak check with `outcome` `COMPLETE` performed on or after the start of the current logical UTC day, while a `SPIROMETRY` device has no leak-check requirement whatsoever. Every non-superseded hold on the order must be `ATTESTED`, since a `VIOLATED` hold blocks the study outright. And the current logical clock must be at or after the order's `hold_release_at`, with the comparison inclusive so that a study beginning at exactly `hold_release_at` is permitted.

Two temporal gates then examine the calendar, and they use **deliberately different interval conventions**. The **device occupancy** gate treats the requested window as the half-open interval from `scheduled_start_at` up to but not including `scheduled_end_at`, extends its end by a 20-minute turnaround allowance for cleaning and warm-up, and compares it against the identically extended window of every other study on the same device whose `session_status` is `SCHEDULED` or `IN_PROGRESS`. Overlap is `ERR_DEVICE_WINDOW_CONFLICT`; intervals that merely touch — one study's extended end landing exactly on another's start — are accepted, because the turnaround allowance has already done its work. The **technologist workload** gate treats the requested window as the closed interval from `scheduled_start_at` through `scheduled_end_at` inclusive, applies no turnaround extension, and counts the acting technologist's other `SCHEDULED` or `IN_PROGRESS` studies whose closed intervals intersect it. Here touching endpoints **do** count as an intersection, because a person cannot be in two rooms at one instant. The count must be strictly below 2, and exceeding it reports `ERR_TECHNOLOGIST_WINDOW_CONFLICT`. These two conventions are not a redundancy to be unified; a request may pass one and fail the other on exactly the same timestamps.

Scheduling is also the moment at which the study's reference frame is fixed forever. The selector considers every `ReferenceEquationSet` whose `status` is `ACTIVE`, whose `modality_scope` contains the device's `modality`, whose inclusive age band from `applicable_age_min` through `applicable_age_max` contains the patient's `age_years`, and whose `sex_scope` either equals the patient's `sex` or is `ANY`. An empty pool reports `ERR_NO_REFERENCE_EQUATION`. The surviving candidates are ranked by the width of the age band, computed as `applicable_age_max` minus `applicable_age_min`, ascending — a narrower band is the better-fitting reference — then by `lln_percentile` ascending, which breaks ties toward the more conservative lower limit, and finally by `created_at` ascending. The first candidate wins.

From the chosen set the server computes `predicted_fev1_l` as `a_fev1` plus `b_fev1` times the patient's `height_cm`, minus `c_fev1` times `age_years` divided by ten, rounded to three decimal places; and `predicted_fvc_l` by the same expression with `a_fvc`, `b_fvc` and `c_fvc`. It then derives the residual standard deviation for FEV1 as `predicted_fev1_l` multiplied by `rsd_frac`, **rounded to three decimal places first**, and computes `lln_fev1_l` as `predicted_fev1_l` minus 1.645 times that rounded residual standard deviation, again rounded to three decimal places. Finally it snapshots the chosen set's identifier into `reference_equation_id`, its `equation_code` into `reference_equation_code`, and its `ratio_lln` into the study's own `ratio_lln`.

Those snapshots are the reason interpretation is reproducible. The equation is pinned once at scheduling and never re-selected, so publishing a newer set for the same `equation_code` afterwards — which moves the old set to `SUPERSEDED` and drops it from every future pool — cannot retroactively change how an already-scheduled study is interpreted. The pattern decision table compares the study's `fev1_fvc_ratio` against the study's own copied `ratio_lln`, not against whatever the currently active equation happens to say.

### 3.6. Maneuver Collection, Acceptability and the Coaching Cycle

Each forced expiratory blow is appended to the study as a `Maneuver`, an append-only record carrying only `id` and `created_at` from the common properties. The technologist supplies the `phase` in which the blow was performed — `PRE_BD`, `POST_BD`, `CHALLENGE_BASELINE` or `POST_CHALLENGE` — together with the measured `fvc_l` and `fev1_l` in litres, each of which must be greater than 0 and no more than 10.000 with `fev1_l` no greater than `fvc_l`, the peak expiratory flow `pef_l_s` in litres per second, the `back_extrapolated_volume_ml` in whole millilitres, the `expiratory_time_s` in seconds, and three booleans describing the trace: `plateau_reached`, meaning a volume plateau was observed at end of test; `cough_in_first_second`, meaning a cough occurred during the first second; and `glottic_closure`, meaning glottic closure was observed. An optional `coaching_note` records what the technologist told the patient. The server assigns `maneuver_index`, which is the prior count of maneuvers on this study plus one, so indices run 1, 2, 3 and upward within the study, and records `session_id` from the path and `performed_at` from the logical clock. Unacceptable blows are stored and do occupy a `maneuver_index`, so the index sequence never has gaps.

The back-extrapolated volume is judged against a **relative** limit, not a fixed one. `bev_limit_ml` is the greater of 100 millilitres and 5 percent of the maneuver's own `fvc_l` expressed in millilitres, rounded to the nearest whole millilitre. That means the limit is 100 millilitres for a small vital capacity and rises with a large one, so the same `back_extrapolated_volume_ml` can be acceptable on a big blow and disqualifying on a small one. A start-of-test failure occurs when `back_extrapolated_volume_ml` exceeds `bev_limit_ml`. An end-of-test failure occurs when neither of the two satisfactory endings is present — that is, when `expiratory_time_s` is below 15.0 seconds **and** `plateau_reached` is false; either a long enough exhalation or an observed plateau is sufficient on its own. An artifact failure occurs when `cough_in_first_second` is true or `glottic_closure` is true.

Those three findings resolve to one of three verdicts in `acceptability`. A blow with no findings at all is `ACCEPTABLE`. A blow whose only finding is the end-of-test failure is `USABLE_FEV1_ONLY`: the first second of the trace is trustworthy even though the patient stopped early, so the FEV1 may be used while the FVC may not. Every other combination is `UNACCEPTABLE`. The findings are also listed in `rejection_reasons`, an array whose entries are drawn from `BEV_EXCEEDED`, `EARLY_TERMINATION`, `COUGH_ARTIFACT` and `GLOTTIC_CLOSURE` and which is emitted in that fixed order regardless of how the checks were evaluated; an `ACCEPTABLE` maneuver carries the empty array. Because an unacceptable blow must leave a coaching record, `coaching_note` is required and must be non-empty whenever the computed `acceptability` is `UNACCEPTABLE`, and its absence reports `ERR_COACHING_NOTE_REQUIRED`. A `USABLE_FEV1_ONLY` blow does not require one.

Every append recomputes the study's aggregate picture from **two different pools**, and the difference between them is the crux of the calculation. The FEV1 pool is the study's `PRE_BD` maneuvers whose `acceptability` is `ACCEPTABLE` **or** `USABLE_FEV1_ONLY`; the FVC pool is the study's `PRE_BD` maneuvers whose `acceptability` is `ACCEPTABLE` only. `best_fev1_l` is the largest `fev1_l` in the FEV1 pool and `best_fvc_l` is the largest `fvc_l` in the FVC pool, each null while its pool is empty. `best_fev1_post_l` is the largest `fev1_l` among the study's `POST_BD` maneuvers whose `acceptability` is `ACCEPTABLE` or `USABLE_FEV1_ONLY`, null until one exists. `acceptable_maneuver_count` counts only the `PRE_BD` maneuvers whose `acceptability` is exactly `ACCEPTABLE`. Ties on a best value are broken by earlier `performed_at`, then by earlier `created_at`; since the values are equal the tie-break cannot change the number, but it fixes which maneuver is regarded as the best one. Maneuvers whose `phase` is `CHALLENGE_BASELINE` or `POST_CHALLENGE` are excluded from every one of these pools — bronchoprovocation traces never contribute to the diagnostic best values or the quality grade.

Two repeatability figures follow. `repeatability_delta_ml` is the whole-millilitre difference between the largest and second-largest `fev1_l` in the FEV1 pool, and is null while that pool holds fewer than two maneuvers. `fvc_repeatability_delta_ml` is the whole-millilitre difference between the largest and second-largest `fvc_l` in the FVC pool, and is null while that pool holds fewer than two. Because the pools differ, a study can have a defined FEV1 delta and a null FVC delta at the same time.

`quality_grade` is then recomputed as one of `A`, `B`, `C`, `D` or `F`, descending through the ladder and stopping at the first grade whose conditions hold. Grade `A` requires `acceptable_maneuver_count` of at least 3 with `repeatability_delta_ml` at or below 150 millilitres **and** `fvc_repeatability_delta_ml` at or below 150 millilitres. Grade `B` requires `acceptable_maneuver_count` of at least 3 with `repeatability_delta_ml` at or below 200 millilitres, and consults the FVC delta not at all. Grade `C` requires `acceptable_maneuver_count` of exactly 2 — not "two or more" — with `repeatability_delta_ml` at or below 150 millilitres, and likewise ignores the FVC delta. Grade `D` applies whenever at least 1 acceptable maneuver exists and none of the three conditions above matched. Grade `F` applies when no acceptable maneuver exists at all, which is also the grade a study carries before its first blow. Three asymmetries in that ladder are load-bearing: only grade `A` consults `fvc_repeatability_delta_ml`, the loose 200-millilitre tolerance belongs to grade `B` alone while `A` and `C` share the tight 150-millilitre one, and grade `C` tests the count for equality with 2 rather than for a minimum. A null delta never satisfies a threshold, so a study with only one maneuver in a pool cannot reach `A`, `B` or `C` through that pool.

Finally the derived percentages are refreshed against the values pinned at scheduling: `fev1_pct_predicted` is `best_fev1_l` divided by `predicted_fev1_l` times 100 to one decimal place, `fvc_pct_predicted` is `best_fvc_l` divided by `predicted_fvc_l` times 100 to one decimal place, and `fev1_fvc_ratio` is `best_fev1_l` divided by `best_fvc_l` to three decimal places. Each is null while any input it needs is null, so a study consisting solely of `USABLE_FEV1_ONLY` blows has a defined `fev1_pct_predicted` and a null `fvc_pct_predicted` and a null `fev1_fvc_ratio`.

The first maneuver moves the study from `SCHEDULED` to `IN_PROGRESS`; later maneuvers leave it there. Appending requires the acting technologist to be the one named in `technologist_staff_id`, requires the device to be `AVAILABLE`, and requires the same credential and competency check that scheduling applied. Maneuvers may be appended while `session_status` is `SCHEDULED`, `IN_PROGRESS` or `REJECTED`.

**Quality finalization** closes the collection phase. The technologist may supply an optional `technologist_comment`, which stays null when omitted, and the server reads the current `quality_grade`. A grade of `A`, `B` or `C` accepts the study: `session_status` becomes `ACCEPTED`, and the device is soiled with `last_session_end_at` set to the study's `scheduled_end_at` and `sessions_since_filter_change` incremented. A grade of `D` or `F` rejects it: `rejection_round` increases by one and `session_status` becomes `REJECTED`, and the device is soiled **only** when the post-increment `rejection_round` has reached 2, because below that the patient is still at the instrument. Finalization requires `session_status` to be `IN_PROGRESS`, and it additionally requires that no challenge run on the study is still `ARMED` or `IN_PROGRESS`; attempting to close a study over a live provocation is a session-state conflict reported as `ERR_SESSION_STATE_INVALID`.

A rejected study reopens for another coaching round by appending a further maneuver, which returns `session_status` to `IN_PROGRESS`, provided `rejection_round` is still strictly below 2 and the device is `AVAILABLE`. Once `rejection_round` has reached 2 the cycle is closed and a further append reports `ERR_MAX_REJECTION_ROUNDS_EXCEEDED`. That bound is what makes the coaching loop `IN_PROGRESS` → `REJECTED` → `IN_PROGRESS` terminate.

Acceptance is also where the **bronchodilator response** is computed, and only then — when the order's `bronchodilator_requested` is true and `best_fev1_post_l` is not null. `bd_response_ml` is the whole-millilitre gain from `best_fev1_l` to `best_fev1_post_l`. Which percentage accompanies it depends on the `bd_criterion` of the equation set pinned to this study, and that choice is recorded in `bd_response_variant`. Under `PCT_BASELINE_2005` the older convention applies: `bd_response_pct` is the gain divided by `best_fev1_l`, times 100, to one decimal place, and `bd_response_positive` is true only when that percentage is at least 12.0 **and** `bd_response_ml` is at least 200. Under `PCT_PREDICTED_2021` the newer convention applies: `bd_response_pct` is the gain divided by `predicted_fev1_l`, times 100, to one decimal place, and `bd_response_positive` is true when that percentage is at least 10.0, with no accompanying absolute-volume requirement. The two variants disagree in both directions — a small-lunged patient can be positive under the baseline convention and negative under the predicted one, and a large-lunged patient the reverse — so the variant must be read from the pinned equation set rather than assumed. All four fields stay null when the order did not request a bronchodilator or no post-bronchodilator best exists.

### 3.7. Bronchoprovocation Testing and the Rescue-Dose Ledger

Bronchoprovocation deliberately narrows a patient's airways, so the laboratory arms a run only when the order asked for it, the patient's airflow can tolerate it, and rescue medication is physically at hand. A `Technologist` arms a run against an in-progress study by naming the `agent` — `METHACHOLINE` or `MANNITOL` — and the `rescue_lot_id` of the lot whose doses are set aside for this patient.

Four gates guard arming, and their order is itself a safety statement. The study's `session_status` must be `IN_PROGRESS`. The order's `challenge_type` must be something other than `NONE` and the supplied `agent` must equal it, otherwise `ERR_CHALLENGE_NOT_REQUESTED`; a technologist may not provoke a patient with an agent nobody ordered, nor substitute one agent for another. The study's `fev1_pct_predicted` must be at least 60.0 percent, and a study whose best pre-bronchodilator FEV1 sits below that may never be provoked whatever the order asked for, reporting `ERR_CHALLENGE_CONTRAINDICATED`. The nominated lot must then pass a **readiness** check — `status` exactly `STOCKED` and `expires_on` on or after the current logical date, otherwise `ERR_RESCUE_NOT_READY` — and only after that passes is the **stock** check made, requiring `doses_remaining` minus `doses_reserved` to be at least 4, otherwise `ERR_RESCUE_DOSES_INSUFFICIENT`. Because readiness is checked first, a lot that is both expired and short-stocked reports the safety failure rather than the fiscal one; the clinician is told the drug is unusable, not merely that there is not much of it.

Arming creates the run with `status` `ARMED`, `current_step_index` 0, `cumulative_dose_units` 0, `last_step_dose_units` 0, `last_step_drop_pct` 0, `max_fev1_drop_pct` 0.00, `rescue_doses_administered` 0, and `pc20_dose_units`, `stop_reason` and `abort_reason` all null. It also pins `baseline_fev1_l` from the study's current `best_fev1_l`, and that snapshot is never re-read: every subsequent fall is measured against the airflow the patient had when the run was armed, even if further pre-bronchodilator maneuvers later change the study's `best_fev1_l`. Finally it adds 4 to the lot's `doses_reserved` while leaving `doses_remaining` untouched, which is the reservation half of the ledger described in §2.11.

Each provocation step is recorded with two inputs: `dose_units`, the units of agent just delivered, and `post_step_fev1_l`, the FEV1 measured after that dose. Before anything is accumulated the server checks that `cumulative_dose_units` plus `dose_units` does not exceed the ceiling of 400 units; the comparison is strict, so landing exactly on 400 is permitted and only overshooting it reports `ERR_MAX_DOSE_EXCEEDED`. The step then captures its two interpolation anchors before mutating the totals: `last_step_dose_units` takes `cumulative_dose_units` as it stood before this step, which is 0 before the first step, and `last_step_drop_pct` takes the drop percent as it stood before this step — that is, the largest fall observed on earlier steps, which is 0 before the first step. Then `current_step_index` increases by one, `cumulative_dose_units` increases by `dose_units` and is carried to three decimal places, and this step's own fall is computed as `baseline_fev1_l` minus `post_step_fev1_l`, divided by `baseline_fev1_l`, times 100, rounded to two decimal places, with `max_fev1_drop_pct` becoming the greater of its prior value and that fall.

Where the run goes next has exactly three outcomes. When the computed fall is **at or above** 20.00 percent the patient has reacted and the run stops: `status` becomes `STOPPED_PC20` with `stop_reason` `PC20_REACHED`. The provocative dose is then found by linear interpolation between the two anchors, in dose units: take the pre-step cumulative dose, and add the increment of this step multiplied by the fraction of the way from the pre-step fall to this step's fall that the 20.00 percent threshold sits — that is, 20.00 minus the pre-step fall, divided by this step's fall minus the pre-step fall. The result is stored in `pc20_dose_units` rounded to three decimal places. When the threshold is crossed on the very first step both anchors are 0, and the interpolation reduces to this step's dose scaled by 20.00 divided by the observed fall. When instead the fall is below 20.00 percent and the post-step `cumulative_dose_units` has reached exactly 400, the patient has taken the full protocol without reacting: `status` becomes `COMPLETED_NEGATIVE` with `stop_reason` `MAX_CUMULATIVE_DOSE_REACHED` and `pc20_dose_units` stays null. Otherwise the run continues, moving to or remaining at `IN_PROGRESS`, and awaits the next dose. Steps require the run's `status` to be `ARMED` or `IN_PROGRESS`; recording a step against a terminated run reports `ERR_RUN_STATE_INVALID`.

A technologist may abort a run at any time while it is `ARMED` or `IN_PROGRESS`, supplying a free-text `abort_reason` describing the safety concern. In every abort, `status` becomes `ABORTED_SAFETY` and `stop_reason` becomes `TECHNOLOGIST_ABORT` — note that `stop_reason` and `abort_reason` are distinct fields serving distinct purposes, the former an enumerated cause and the latter the operator's own words. What differs is whether any agent reached the patient. An abort with `current_step_index` still 0 means nothing was administered, so `rescue_doses_administered` stays 0, the lot's `doses_reserved` drops by 4 with `doses_remaining` untouched — a clean release of the whole reservation — and the study's `session_status` is left entirely alone, because the patient was never provoked. An abort after at least one step means the agent did reach the patient, so `rescue_doses_administered` becomes 4, the lot's `doses_remaining` drops by 4 and its `doses_reserved` drops by 4, and the study is aborted with `abort_reason` `CHALLENGE_SAFETY_ABORT`, which in turn drives the order back from `IN_TESTING` to `READY` with `abort_count` incremented.

Both non-abort terminal branches spend the allotment in the same way: `rescue_doses_administered` becomes 4, `doses_remaining` drops by 4 and `doses_reserved` drops by 4. The general rule is that any run which reached at least one step consumes the full rescue allotment, because the provocation agent reached the patient, while a run that never dosed releases its reservation intact. Whenever a debit brings `doses_remaining` to exactly 0 the lot moves from `STOCKED` to `DEPLETED`. And when a study is aborted from outside — by a device quarantine or an order cancellation — every run on it whose `status` is `ARMED` or `IN_PROGRESS` is driven to `ABORTED_SAFETY` with `stop_reason` `SESSION_ABORTED`, each one settling its own ledger movement by the same step-count rule.

### 3.8. Chain of Custody for Occupational and Disability Testing

Testing performed for an employer or a disability adjudicator carries evidentiary weight, so those studies are wrapped in a chain of custody that runs alongside the clinical work rather than inside it. The custody dimension of a study is initialised at scheduling: `NOT_APPLICABLE` when the order's `test_context` is `ROUTINE_CLINICAL`, and `CUSTODY_OPEN` when it is `OCCUPATIONAL_SURVEILLANCE` or `DISABILITY_EVALUATION`. A study whose `custody_status` is `NOT_APPLICABLE` accepts no custody events at all, reporting `ERR_CUSTODY_NOT_APPLICABLE`, and that value never changes for the life of the study.

Custody events are append-only records carrying only `id` and `created_at` from the common properties, plus `session_id` from the path, the `event_type`, the `actor_user_id` and `actor_role` copied from the acting request's `X-User-ID` and `X-User-Role` headers, a `performed_at` stamped from the logical clock, and an optional free-text `note`. As §2.1 explains, `actor_user_id` is recorded as an opaque header value and is not a foreign key, precisely so that an auditor with no `Staff` row can witness. Two conditional fields complete the record, and each is required for its own event types and forbidden for all the others: `id_document_type` — one of `PHOTO_ID`, `PASSPORT` or `EMPLOYEE_BADGE` — is required when `event_type` is `ID_VERIFIED` and must be absent otherwise, and `seal_serial`, the tamper-evident seal serial, is required when `event_type` is `SEAL_APPLIED` or `SEAL_BROKEN` and must be absent otherwise. A witness attestation therefore carries neither. `actor_role` records the acting role and is always either `Technologist` or `ComplianceAuditor`, those being the only two roles that may append.

The four `event_type` values fall into two groups. Three of them advance the custody dimension along a strict sequence and each is legal from exactly one predecessor: `ID_VERIFIED` is accepted only from `CUSTODY_OPEN` and moves the study to `CUSTODY_ID_VERIFIED`; `SEAL_APPLIED` is accepted only from `CUSTODY_ID_VERIFIED` and moves it to `CUSTODY_SEALED`; and `SEAL_BROKEN` is accepted only from `CUSTODY_SEALED` and moves it to `CUSTODY_BROKEN`. Submitting one out of turn — sealing before verifying identity, verifying identity twice, or breaking a seal that was never applied — reports `ERR_CUSTODY_SEQUENCE_INVALID`. The sequence is one-way: `CUSTODY_BROKEN` has no successor, so breaking a seal permanently forecloses signing the report for any non-routine study, and the only remedy is to run the study again.

The fourth type, `WITNESS_SIGNED`, behaves differently in three respects. It is legal from any applicable custody state — `CUSTODY_OPEN`, `CUSTODY_ID_VERIFIED`, `CUSTODY_SEALED` or `CUSTODY_BROKEN` — it leaves `custody_status` exactly where it was, and it is reserved to the `ComplianceAuditor` role; a `Technologist` submitting a witness attestation is refused with `ERR_ROLE_NOT_PERMITTED`. The other three types are the technologist's to submit. A witness attestation is nonetheless a prerequisite for signing a disability report, so it is consequential without being sequential.

Every custody event, including a witness attestation that changes no state, increments the study's `version`. That is what makes the two dimensions genuinely parallel: `session_status` is untouched by custody activity, and `custody_status` is untouched by maneuvers, quality finalization and reporting, yet both share one optimistic-concurrency counter. A client that read the study, then had a custody event land underneath it, will find its `expected_session_version` stale on a report assignment even though nothing about the clinical picture moved.

The two dimensions meet at exactly one place: report signing. For a study whose order `test_context` is anything other than `ROUTINE_CLINICAL`, `custody_status` must be exactly `CUSTODY_SEALED` at signing time, and any other value — including `CUSTODY_BROKEN` and including a chain that simply never got as far as sealing — reports `ERR_CUSTODY_NOT_SEALED`. For a study whose `test_context` is specifically `DISABILITY_EVALUATION`, at least one custody event with `event_type` `WITNESS_SIGNED` must additionally exist on that study, otherwise `ERR_WITNESS_ATTESTATION_MISSING`. A `ROUTINE_CLINICAL` study is subject to neither requirement.

### 3.9. Interpreter Assignment, Signing and Report Turnaround

An accepted study is handed to an interpreting physician by a `LabManager`. The assignment request carries exactly one body field, the mandatory `expected_session_version` described in §2.7, because who interprets the study is decided by the server rather than nominated by the manager. The study's `session_status` must be `ACCEPTED`.

The candidate pool is every `Staff` row whose `role_type` is `INTERPRETING_PHYSICIAN`, whose `status` is `ON_DUTY`, whose `credentialed_modalities` contains the modality of the device the study ran on, whose `open_report_count` is strictly below their own `max_concurrent_reports`, and whose `id` differs from the study's `technologist_staff_id`. That last clause is a segregation-of-duties guard applied as a **pre-filter rather than a post-hoc rejection**: the technologist who coached the maneuvers is removed from the pool before ranking, so the selector picks the best remaining candidate instead of selecting that person and then failing. An empty pool reports `ERR_NO_ELIGIBLE_INTERPRETER`, and it does so uniformly — a roster that is entirely off duty, entirely uncredentialed for this modality, or entirely at capacity all surface as the same error, with no capacity-specific variant. The survivors are ranked by `open_report_count` ascending, so the least-loaded interpreter wins, with `created_at` ascending as the final tie-break; entity identifiers never participate. The chosen candidate's `id` is stored in `interpreter_staff_id` and their `open_report_count` rises by one.

The turnaround deadline is then computed, and **the order of the five steps that produce it is normative**. First the report is inserted with `status` `ASSIGNED` and `assigned_at` set to the current logical clock, which is the origin of the turnaround clock. Second, the laboratory-wide open workload is counted as the number of reports anywhere in the system whose `status` is `ASSIGNED` or `AMENDED` — **including the row just inserted**. Reports that are `SIGNED` or `REASSIGNED` are excluded. When this assignment supersedes an earlier report on the same study, that earlier report is still `ASSIGNED` at the moment the count is taken and is therefore counted as well, because the demotion described below is applied only after all five steps have produced the new report's deadline. Third, that count is expressed against the roster's declared capacity, which is the sum of `max_concurrent_reports` over every `Staff` row whose `role_type` is `INTERPRETING_PHYSICIAN` and whose `status` is `ON_DUTY`; `queue_load_pct` is the open count divided by that capacity, times 100, rounded to two decimal places. Fourth, the load is tiered with inclusive lower boundaries: a `queue_load_pct` at or below 50.00 is `load_tier` `NORMAL` with a multiplier of 1.00, a value above 50.00 but at or below 80.00 is `ELEVATED` with a multiplier of 1.50, and anything above 80.00 is `SURGE` with a multiplier of 2.00. Fifth, `sla_minutes` is the integer product of the base allowance for the order's `test_context` and that multiplier, where the base is 1440 minutes for `ROUTINE_CLINICAL`, 2880 minutes for `OCCUPATIONAL_SURVEILLANCE` and 4320 minutes for `DISABILITY_EVALUATION`, and `due_at` is `assigned_at` plus `sla_minutes` minutes.

Counting the new report inside its own load measurement is not an accident of implementation; it is the rule. A single on-duty interpreter with `max_concurrent_reports` of 1 and no other open work yields an open count of 1 against a capacity of 1, a `queue_load_pct` of 100.00, a `load_tier` of `SURGE` and, for a routine study, an `sla_minutes` of 2880. Measuring the load before insertion would have produced 0.00, `NORMAL` and 1440 — a different deadline for the same request.

Assignment also copies the study's `reference_equation_code` onto the report, so a signed report cites the equation actually used, and leaves `template_version`, `signed_at`, `turnaround_minutes`, `sla_breached`, `pattern`, `severity`, `clinical_comment`, `amendment_reason` and `superseded_by_report_id` null with `amendment_count` at 0. A second assignment on the same study is legitimate: any prior report on that study whose `status` is `ASSIGNED` moves to `REASSIGNED` with `superseded_by_report_id` pointing at the new report, and the losing interpreter's `open_report_count` drops by one while the winning interpreter's rises by one, so the laboratory-wide open total is unchanged. That is precisely why the operation is version-guarded: both writers would otherwise succeed on their own product semantics, and the guard is what makes the outcome deterministic.

Signing is the interpreting physician's act, and only the physician named in `interpreter_staff_id` may perform it; anyone else, including another `InterpretingPhysician`, is refused with `ERR_ROLE_NOT_PERMITTED`. The report's `status` must be `ASSIGNED` or `AMENDED`, else `ERR_REPORT_STATE_INVALID`. The signer's `id` must differ from the study's `technologist_staff_id`, else `ERR_SEGREGATION_OF_DUTIES` — a second line of defence behind the selector's pre-filter, and the rule that makes it impossible for one person to both coach and interpret a study. The custody conditions of §3.8 then apply. The physician supplies a `clinical_comment`, the free-text interpretation narrative.

At signing the server stamps `signed_at` from the logical clock and derives the interpretation from the study's already-rounded aggregates. `pattern` comes from a two-by-two decision table crossing the ratio against its lower limit with the FVC percentage against normal: a `fev1_fvc_ratio` **below** the study's pinned `ratio_lln` together with an `fvc_pct_predicted` **below** 80.0 gives `MIXED`; a ratio below its limit with an FVC percentage at or above 80.0 gives `OBSTRUCTION`; a ratio at or above its limit with an FVC percentage below 80.0 gives `RESTRICTION`; and a ratio at or above its limit with an FVC percentage at or above 80.0 gives `NORMAL`. Both comparisons put the boundary on the normal side, so a ratio exactly equal to `ratio_lln` and an `fvc_pct_predicted` of exactly 80.0 are both normal and together yield `NORMAL`.

`severity` is then graded on `fev1_pct_predicted`, except that a `NORMAL` pattern always carries `severity` `NONE` regardless of the number. Otherwise the bands are: 70.0 percent or above is `MILD`, at least 60.0 but below 70.0 is `MODERATE`, at least 50.0 but below 60.0 is `MODERATELY_SEVERE`, at least 35.0 but below 50.0 is `SEVERE`, and below 35.0 is `VERY_SEVERE`. `template_version` is set to the constant `PFT-2026.1`.

Two timing figures complete the signature. `turnaround_minutes` is the elapsed time from `assigned_at` to `signed_at` in whole minutes, **truncated downward** rather than rounded, so 1439 minutes and 59 seconds is 1439. `sla_breached` is true when `signed_at` is **strictly after** `due_at`, so signing at exactly the deadline is not a breach. Signing also cascades: the interpreter's `open_report_count` drops by one because the report has left the open set, the study moves from `ACCEPTED` to `REPORTED` and copies `turnaround_minutes` onto its own field of the same name, and the order moves from `IN_TESTING` to `COMPLETED`, which raises the patient's `completed_order_count` by one.

A signed report may be amended by the same physician, supplying an `amendment_reason`. Amendment raises `amendment_count` by one, moves `status` to `AMENDED`, and raises that interpreter's `open_report_count` by one again because `AMENDED` is an open status — which means an amendment also raises the laboratory-wide queue load that future assignments will measure. The study stays `REPORTED` and the order stays `COMPLETED`; an amendment never rewinds the workflow. Crucially, **an amendment does not reopen the deadline**: `assigned_at` and `due_at` keep their original values, and re-signing the amended report recomputes `turnaround_minutes` against that original `assigned_at` and re-evaluates `sla_breached` against that original `due_at`. Those recomputed figures live on the report: the interpreter's `open_report_count` still drops by one as the report leaves the open set, but the study is already `REPORTED`, so the rest of the signing cascade does not run a second time — the study's own `turnaround_minutes` keeps the figure the first signature copied and the study's `version` and `updated_at` are not refreshed, the order stays `COMPLETED`, and the patient's `completed_order_count` is not raised again. A report amended and re-signed a week late is therefore breached, and the `SIGNED` → `AMENDED` → `SIGNED` cycle may repeat without bound.

## 4. Endpoint Definitions

Every endpoint is mounted under the `/pft-lab` prefix and every one of them speaks the envelope defined in §2.2. An operation that brings a new resource into existence answers with HTTP 201 and the created resource in `data`: registering a device, appending a device quality event, registering a staff member or a patient, publishing a reference equation set, receiving a rescue lot, drafting a test order, issuing a medication hold, scheduling a study, appending a maneuver, appending a custody event, arming a challenge run and assigning an interpretation report. Every other operation answers with HTTP 200 — the state transitions that modify an existing resource (submit, revise, cancel, attest, return-to-service, finalize-quality, record a challenge step, abort a run, sign, amend), every read, and the logical clock. Note in particular that recording a challenge step answers 200 with the updated `ChallengeRun` rather than 201, because a step is an accumulator update on the run rather than a resource of its own, and that a submission which lands in `INDICATION_REJECTED` still answers 200 with the order body.

Single-resource reads return the resource in `data` with `response_type` `"object"`. Collection reads return an array with `response_type` `"array"` and the pagination `meta` of §2.3, and each accepts `limit` and `offset` alongside its own filters: the device list filters on `status`, `modality` and `quarantine_trigger_staff_id`; the quality-event list on `device_id`, `subject_staff_id`, `performed_by_staff_id`, `event_type` and `outcome`; the order list on `patient_id`, `ordering_staff_id` and `status`; the per-order hold list on `status` and the cross-order hold list on `order_id`, `medication_class` and `status`; the study list on `order_id`, `device_id`, `technologist_staff_id`, `reference_equation_id`, `session_status` and `custody_status`; the per-study maneuver list on `phase` and `acceptability` and the cross-study maneuver list on `session_id`, `phase` and `acceptability`; the per-study custody list on `event_type` and the cross-study custody list on `session_id`, `event_type` and `actor_user_id`; the challenge-run list on `session_id`, `rescue_lot_id` and `status`; and the report list on `session_id`, `interpreter_staff_id`, `superseded_by_report_id` and `status`.
