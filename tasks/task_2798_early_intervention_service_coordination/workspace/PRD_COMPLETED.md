# Early Intervention Service Coordination API — Product Requirements Document

## 1. Introduction

A state early intervention program is answerable to two audiences at once. Families need help quickly, in the places where their children actually live and play; federal and state auditors need proof that every mandated step happened inside its statutory window, that every dollar of family cost participation was assessed on a published sliding scale, and that every child left the program with a measured developmental outcome. Today those two obligations are met by different systems and reconciled by hand: intake staff track the 45-day clock on spreadsheets, service coordinators estimate their own caseloads, providers submit visit notes that the fiscal office re-prices weeks later, and transition notifications to school districts are discovered late — sometimes after the child has already turned three.

This document specifies the backend service that replaces that patchwork. The service owns the whole case record: the referral and its statutory clock, the multidisciplinary evaluation and family assessment, the individualized family service plan (**IFSP**) and its service lines, the authorization of providers against a conserved pool of service units, the documentation of each delivered session, the family's sliding-scale fee and running balance, the monthly contact requirement, transition planning to preschool services, and the entry and exit child-outcome ratings that feed federal reporting. Every one of those objects is a first-class resource with an auditable state history, and every derived number — elapsed days, weighted caseload points, committed units, accrued cents — is recomputed by the server rather than supplied by a client.

Two design commitments run through the whole specification and should be read as constraints on every section that follows. First, **time is explicit**: the service evaluates every deadline, window, month bucket and "not in the future" rule against a logical clock that the program's own administrators set, never against wall-clock time, so that a compliance scenario can be reproduced exactly. Second, **nothing conserved may leak**: a service line's authorized units and a family's assessed cents each obey an arithmetic identity that the server re-checks after every write, and a write that would break either identity is refused rather than partially applied. All business resources are mounted under the `/ei` prefix; a single administrative clock endpoint sits outside it.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the service must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. A request that omits either header, or that names a role the system does not recognise, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose headers are well formed but whose role is not among the roles authorised for the target endpoint is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). These two checks run before any other consideration — before the request body is parsed, before path identifiers are resolved, and before any business rule is evaluated.

Seven roles exist, spelled exactly as follows: `IntakeSpecialist`, `ProgramAdmin`, `Evaluator`, `FiscalOfficer`, `ServiceCoordinator`, `Provider`, and `FamilyRepresentative`.

`IntakeSpecialist` is front-door intake staff, and is the only role that may register a child or open a referral. `ProgramAdmin` runs program operations: the coordinator roster, caseload assignment, eligibility determination, plan authoring, service-line authoring, the provider network, provider suspension, authorizations and their revocation, voiding a documented visit, and the logical clock. `Evaluator` is multidisciplinary evaluation staff: scheduling and completing assessments, and recording the three entry outcome ratings. `FiscalOfficer` owns family cost participation: determining the sliding scale, finalizing verified income, recording or withdrawing insurance consent, and waiving balances. `ServiceCoordinator` is the assigned coordinator for a case and owns that case's monthly contacts, transition planning, the local education agency notification, and case exit. `Provider` is the delivering agency and documents its own sessions. `FamilyRepresentative` is the parent or guardian and records parental consent on a plan. Visit scheduling is shared: `ProgramAdmin` and `ServiceCoordinator` may both schedule a session.

Four of the seven roles carry an **opaque** identity. When `X-User-Role` is `IntakeSpecialist`, `ProgramAdmin`, `Evaluator`, or `FiscalOfficer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to an entity's `id`. It may still be recorded where a scaffold rule says so — an `Evaluator`'s identifier is stored as `evaluator_user_id` on the assessment they create, and a `FiscalOfficer`'s identifier is stored as `determined_by_user_id` on the cost-share determination they create — but such a value is a provenance record, not a foreign key.

The remaining three roles are **entity-backed**, and their identity drives ownership checks. When `X-User-Role` is `ServiceCoordinator`, `X-User-ID` is the `id` of the acting `ServiceCoordinator`; ownership checks on any resource that references a `ServiceCoordinator` compare the resource's coordinator foreign-key field to `X-User-ID` — concretely, the referral's `coordinator_id`. When `X-User-Role` is `Provider`, `X-User-ID` is the `id` of the acting `Provider`; ownership checks compare the target visit's authorization `provider_id` to `X-User-ID`. When `X-User-Role` is `FamilyRepresentative`, `X-User-ID` is the `id` of the acting `Child`; ownership checks compare the referral's `child_id` to `X-User-ID`. An entity-backed role acting on a resource it does not own is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

Ownership scoping constrains **writes** only. The five staff roles — `IntakeSpecialist`, `ProgramAdmin`, `Evaluator`, `FiscalOfficer`, and `ServiceCoordinator` — share read access across the entire program, so a coordinator may read another coordinator's cases even though they may not write to them. `Provider` and `FamilyRepresentative` have no read access under `/ei` at all: their sole capabilities are, respectively, documenting their own visits and consenting to their own child's plan.

One further access rule is not about roles but about identities within a role. Family cost participation is subject to **segregation of duties**: the `FiscalOfficer` whose identifier is recorded in a determination's `determined_by_user_id` may not waive that same determination's balance. A different `FiscalOfficer` identity must act, and an attempt by the determining officer is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits; it is read from the logical clock of §2.5 rather than from host wall-clock time, so every response served while the clock sits at one instant carries that same timestamp.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All list endpoints are paginated with two query parameters. `limit` defaults to 10 when omitted, has a minimum of 1 and a maximum of 100. `offset` defaults to 0 when omitted and has a minimum of 0. A `limit` or `offset` that is not an integer, or that falls outside the accepted range for the parameter, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400); for the purposes of this check the service accepts `limit` values from 1 through 200 and `offset` values of 0 or greater as syntactically valid integers, while the effective page size ceiling remains 100. A parameter is an integer only if it is written as an optionally signed run of decimal digits — a decimal fraction such as `10.0`, an empty value, or any other non-digit text is rejected. A `limit` between 101 and 200 is accepted and echoed back verbatim in `meta.limit`, while the page itself is truncated to at most 100 rows; `meta.limit` always reports the submitted (or defaulted) value rather than the truncated page size.

Every list endpoint returns its rows sorted by `created_at` in ascending order, so that a stable page boundary is guaranteed across successive reads; because `created_at` is stamped from the logical clock, rows created while the clock stood still share an identical `created_at`, and such ties are broken by the order in which the rows were inserted, oldest insertion first. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` is true when the count of rows already skipped plus the count of rows on this page is still below `total_count`.

Filters, where a list endpoint offers them, are combined conjunctively and are applied before pagination. Every filter is matched as an exact string equality against the stored field, and a filter value is never itself validated: a status or method filter naming something outside that field's enumeration is accepted and simply matches no row, yielding an empty page with `total_count` 0 rather than an error. Query parameters other than `limit`, `offset` and the filters listed below are ignored. Referral listing filters on `child_id`, `coordinator_id` and `status`. Assessment listing filters on `referral_id`, `assessment_type` and `status`. Plan listing filters on `referral_id`, `supersedes_ifsp_id`, `authoring_coordinator_id` and `status`. Service-line listing filters on `ifsp_id` and `status`. Authorization listing filters on `ifsp_service_id`, `provider_id` and `status`. Visit listing filters on `provider_authorization_id`, `makeup_for_visit_id`, `visit_status` and `billing_status` — both status dimensions are independently filterable. Cost-share listing filters on `referral_id` and `status`. Contact-log listing filters on `referral_id` and `contact_method`. Transition-plan listing filters on `ifsp_id` and `status`.

### 2.4. Record Identity, Audit Fields, and the One Append-Only Register

Every resource the service persists carries a server-minted `id` that is a UUID string with no type prefix; clients never supply an `id`. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was inserted, read — like every other timestamp the service writes — from the logical clock of §2.5 and not from host wall-clock time.

Most resources are mutable and therefore carry two more common properties. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the row. `version` is an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row — including mutations that arrive as the secondary effect of a write aimed at a different resource. "Mutation" means that at least one stored field of the row actually took a new value: a write that recomputes a derived field to the value it already held, or that stores a field identical to the one already there, leaves both `updated_at` and `version` untouched. Conversely a single request that changes several fields of one row, or that touches the same row along several branches of a cascade, still advances that row's `version` by exactly 1 and stamps `updated_at` once. A row created by the request that then goes on to mutate it is exempt: it is returned with `version` 1 and `updated_at` equal to its `created_at`. `Child`, `Referral`, `ServiceCoordinator`, `Assessment`, `IFSP`, `IFSPService`, `Provider`, `ProviderAuthorization`, `ServiceVisit`, `CostShare` and `TransitionPlan` all carry `id`, `created_at`, `updated_at` and `version`.

`ContactLog` is the single exception. Contact entries are an append-only register: once written, a contact log row is never mutated, corrected or deleted. A `ContactLog` therefore carries only `id` and `created_at` — it has **no** `updated_at` field and **no** `version` field, and neither should appear in its representation.

### 2.5. The Logical Clock and Date Discipline

The service keeps a **logical clock**. Before an administrator sets it for the first time, the logical clock reads exactly `2026-08-01T00:00:00Z`; it must never fall back to the host's wall-clock time. An administrative capability sets the clock to an explicit instant supplied as `current_utc`, and every deadline, authorization window, credential expiry, calendar-month bucket and "not in the future" rule in this specification is evaluated against that clock and nothing else. The clock may be set to any instant, earlier or later than the one it currently reads, and the cascade below runs either way. The capability answers HTTP 200 with a `data` object carrying the single field `current_utc`, the newly set instant rendered in the canonical three-fractional-digit form; it does not return a persisted resource.

Advancing the clock is not a passive act; it is a write with consequences, enumerated in §2.7 and in the workflow narratives.

Dates that record something that has already happened may not be in the future relative to the logical clock date. This applies to `referral_received_date`, an assessment's `completion_date`, an eligibility `determination_date`, an entry-outcome `measurement_date`, an IFSP `meeting_date`, a `consent_signed_date`, an `opt_out_signed_date`, a `notification_date`, a `verification_date`, a `contact_date`, an `exit_date`, and the `effective_date` recorded when a provider leaves active standing. A violation is rejected with `ERR_DATE_IN_FUTURE` (HTTP 422). Forward-looking dates are deliberately exempt: an authorization window's `start_date` and `end_date`, an assessment's `scheduled_date`, a transition plan's `target_conference_date`, and a visit's `scheduled_start` and `scheduled_end` may all be future-dated. A transition plan's `conference_held_date` is exempt too, despite recording something already done: it is accepted exactly as supplied when the transition plan is opened, without any comparison against the logical clock date.

Ordered date pairs must be coherent, or the request is rejected with `ERR_INVALID_DATE_RANGE` (HTTP 422). An authorization's `end_date` must be on or after its `start_date`. An assessment's `completion_date` must be on or after the referral's `referral_received_date`. An eligibility `determination_date` must be on or after `referral_received_date`. An entry-outcome `measurement_date` must be on or after the referral's `eligibility_determination_date`. An `exit_date` must be on or after `services_start_date` whenever services have started.

Calendar dates are written `YYYY-MM-DD` and must be real calendar dates; a cost-share month is written `YYYY-MM` with a month part from `01` through `12`; visit instants are ISO 8601 UTC timestamps and three fractional digits are tolerated on input. Instant parsing is deliberately liberal: between one and nine fractional digits are accepted and normalised to three, the seconds component may be omitted, a space may stand in for the `T` separator, and a trailing numeric UTC offset such as `+02:00` is accepted and converted to UTC before storage, as is an absent offset, which is read as UTC. Every instant the service stores or returns is rendered back in the canonical `YYYY-MM-DDTHH:MM:SS.mmmZ` form regardless of the form it arrived in. Day counts throughout this specification are whole-day integer arithmetic with the earlier date exclusive and the later date inclusive unless a rule says otherwise.

### 2.6. Optimistic Concurrency Control on the Case Record

Exactly one write in this system is guarded by optimistic concurrency control: authoring an IFSP against a referral. A `POST /ei/ifsps` request must carry `expected_referral_version` as a required, non-optional input field whose value is the `version` of the target `Referral` as the client last observed it; it must be an integer of at least 1, and a submitted 0 or a negative value is a payload-shape failure reported as `ERR_INVALID_REQUEST` at rung 3 rather than as a stale-version refusal. If the referral's stored `version` no longer equals the submitted `expected_referral_version` at the moment the write would be applied, the request is rejected with `ERR_STALE_REFERRAL_VERSION` (HTTP 412): no `IFSP` row is created, no counter on any entity is touched, and the referral's own `version` is left unchanged.

The purpose of the guard is that a plan can never be authored against a case whose eligibility, coordinator, or statutory-timeline state has moved on since the client read it. Every request that mutates the referral aggregate advances `Referral.version` by 1 — coordinator assignment, eligibility determination, entry-outcome recording, case exit, and plan authoring itself. That list is illustrative rather than exhaustive: the rule is the general one of §2.4, so any request that leaves at least one stored field of the referral row holding a new value bumps the version by exactly 1, including writes aimed elsewhere that reach the referral as a cascade — scheduling a supplemental evaluation that reverts the case, logging a contact that moves `monthly_contact_status` or `last_qualifying_contact_date`, consenting to an initial plan, or any cascade that flips `service_gap_flag` or recomputes `case_weight_points` to a different figure. A client that reads a referral, watches another writer determine eligibility on it, and then submits its remembered version is holding a stale value and will be refused.

No other endpoint accepts a version field. Consent, authorization creation, visit documentation, cost-share finalization and every other write in this specification take no `expected_*_version` input and must not require one.

### 2.7. Cascade Discipline: One Write, Many Rows

This system is strongly coupled by design, and the service applies every consequence of a write inside that same request, immediately and atomically. There is no deferred reconciliation, no background sweep and no eventual consistency: when a request returns 200 or 201, every derived counter, aggregate and dependent state named in the workflow narratives has already been updated. Conversely, when a request fails any validation, **nothing** is written — not the primary row, not a partial cascade, not a counter.

Three cascades in particular reach four or five hops deep, and each is described in full in its §3 subsection: provider suspension or termination, plan supersession at consent, and case exit. Their shape is the same. The primary row changes state; every dependent authorization changes state and, where the branch calls for it, releases units; every scheduled session on those authorizations is cancelled; each affected service line's unit-pool and makeup counters are recomputed and may change the line's own state; and finally the referral-level flags and the assigned coordinator's caseload aggregates are recomputed. Every row touched anywhere along the chain has its `updated_at` refreshed and its `version` incremented by 1.

Advancing the logical clock is itself a cascade head. On every clock set: `gross_elapsed_days`, `net_elapsed_days` and `initial_timeline_status` are recomputed for every non-terminal referral; `case_weight_points` is recomputed for every non-terminal referral, whether or not the transition-window term itself has moved, and the affected coordinators' aggregates are recomputed after it; `monthly_contact_status` and `last_qualifying_contact_date` are recomputed for every non-terminal referral too, a case outside `ACTIVE_SERVICES` simply reconfirming `NOT_APPLICABLE`; and every `ACTIVE` authorization whose `end_date` now lies in the past transitions to `EXPIRED`, releasing its unspent units back to its service line's pool.

### 2.8. Validation Order

When several rules could reject the same request, the service evaluates them in a fixed order and reports the **first** violated rule. The order is normative because it determines which error identifier a client sees, and a mid-flight state change must surface as its own error rather than being masked by a later check. No state is written on any failure.

The ladder is, in ascending order:

1. Authentication — `ERR_UNAUTHENTICATED` (401): `X-User-Role` is present and names a declared role, and `X-User-ID` is present and non-empty. Both header requirements hold for every role, opaque as well as entity-backed, exactly as §2.1 states: an opaque role that omits `X-User-ID` is refused here just as an entity-backed one is. Applies to every endpoint.
2. Authorization — `ERR_ROLE_NOT_PERMITTED` (403): the named role appears in the target endpoint's authorised role list. Applies to every endpoint.
3. Payload shape — `ERR_INVALID_REQUEST` (400): the body parses, contains every required input field, contains no unknown field, and every value matches its declared type, enum domain and numeric range. An explicit JSON `null` is treated as an absent field, so a required field sent as `null` is reported as missing while an optional field sent as `null` simply takes its documented default. A missing or empty body on a write whose every field is optional is equivalent to `{}`, and a body that is valid JSON but not an object is refused. A string field must be non-empty once surrounding whitespace is trimmed, and any declared minimum length is measured against the trimmed text; an integer field rejects booleans and fractional numbers; an array field rejects duplicate entries as well as entries outside the item domain. A handful of cross-field shape rules are enforced at this same rung rather than later, and therefore report `ERR_INVALID_REQUEST` in preference to any existence or business error: a `date_of_birth` later than the logical clock date on child registration; a missing `natural_environment_justification` on an assessment or a service line whose `setting_code` is `CLINIC` or `PROGRAM_OFFICE`; and, on `POST /ei/transition-plans/{transitionPlanId}/notify-lea`, the either/or pairing of `lea_code` and `opt_out_signed_date` against the branch named by `family_opt_out`, as §3.9 describes — so a malformed pairing addressed to a `transitionPlanId` that does not exist reports `ERR_INVALID_REQUEST` and not `ERR_TRANSITION_PLAN_NOT_FOUND`. Applies to every endpoint.
4. Pagination — `ERR_INVALID_PAGINATION` (400): applies to the nine list endpoints `GET /ei/referrals`, `GET /ei/assessments`, `GET /ei/ifsps`, `GET /ei/ifsp-services`, `GET /ei/provider-authorizations`, `GET /ei/service-visits`, `GET /ei/cost-shares`, `GET /ei/contact-logs` and `GET /ei/transition-plans`.
5. Existence of referenced rows, resolved **left to right along the URL path first and then across body foreign keys in declaration order**. A `child_id` in path or body must resolve to a `Child` or the request fails with `ERR_CHILD_NOT_FOUND` (404) — this applies to `GET /ei/children/{childId}` and `POST /ei/referrals`. A `referralId` in the path or a `referral_id` in the body must resolve to a `Referral` or the request fails with `ERR_REFERRAL_NOT_FOUND` (404) — this applies to every endpoint under `/ei/referrals/{referralId}/` plus `POST /ei/assessments`, `POST /ei/ifsps` and `POST /ei/cost-shares`. A `coordinatorId` in the path or a `coordinator_id` in the body must resolve to a `ServiceCoordinator` or the request fails with `ERR_COORDINATOR_NOT_FOUND` (404) — applying to `GET /ei/service-coordinators/{coordinatorId}`, `GET /ei/service-coordinators/{coordinatorId}/caseload-summary` and `POST /ei/referrals/{referralId}/assign-coordinator`. An `assessmentId` must resolve to an `Assessment` or the request fails with `ERR_ASSESSMENT_NOT_FOUND` (404) on `POST /ei/assessments/{assessmentId}/complete`. An `ifspId` in the path, an `ifsp_id` in the body, and a `supersedes_ifsp_id` when supplied must each resolve to an `IFSP` or the request fails with `ERR_IFSP_NOT_FOUND` (404) — applying to `GET /ei/ifsps/{ifspId}`, `POST /ei/ifsps/{ifspId}/consent`, `POST /ei/ifsp-services` and `POST /ei/transition-plans`. A `serviceId` in the path or an `ifsp_service_id` in the body must resolve to an `IFSPService` or the request fails with `ERR_IFSP_SERVICE_NOT_FOUND` (404) — applying to `GET /ei/ifsp-services/{serviceId}` and `POST /ei/provider-authorizations`. A `providerId` in the path or a `provider_id` in the body must resolve to a `Provider` or the request fails with `ERR_PROVIDER_NOT_FOUND` (404) — applying to `GET /ei/providers/{providerId}`, `POST /ei/providers/{providerId}/suspend` and `POST /ei/provider-authorizations`. An `authorizationId` in the path or a `provider_authorization_id` in the body must resolve to a `ProviderAuthorization` or the request fails with `ERR_AUTHORIZATION_NOT_FOUND` (404) — applying to `GET /ei/provider-authorizations/{authorizationId}`, `POST /ei/provider-authorizations/{authorizationId}/revoke` and `POST /ei/service-visits`. A `visitId` in the path and a `makeup_for_visit_id` when supplied must each resolve to a `ServiceVisit` or the request fails with `ERR_VISIT_NOT_FOUND` (404) — applying to `GET /ei/service-visits/{visitId}`, `POST /ei/service-visits/{visitId}/document`, `POST /ei/service-visits/{visitId}/void` and `POST /ei/service-visits`. A `costShareId` must resolve to a `CostShare` or the request fails with `ERR_COST_SHARE_NOT_FOUND` (404) — applying to `GET /ei/cost-shares/{costShareId}`, `POST /ei/cost-shares/{costShareId}/finalize`, `POST /ei/cost-shares/{costShareId}/waive` and `POST /ei/cost-shares/{costShareId}/insurance-consent`. A `transitionPlanId` must resolve to a `TransitionPlan` or the request fails with `ERR_TRANSITION_PLAN_NOT_FOUND` (404) on `POST /ei/transition-plans/{transitionPlanId}/notify-lea`. A `contactLogId` must likewise resolve to a `ContactLog` for `GET /ei/contact-logs/{contactLogId}`, or the request fails with `ERR_CONTACT_LOG_NOT_FOUND` (404).
6. Ownership — `ERR_NOT_RESOURCE_OWNER` (403), for entity-backed roles, on the six write endpoints `POST /ei/referrals/{referralId}/contact-logs`, `POST /ei/referrals/{referralId}/exit`, `POST /ei/ifsps/{ifspId}/consent`, `POST /ei/service-visits/{visitId}/document`, `POST /ei/transition-plans` and `POST /ei/transition-plans/{transitionPlanId}/notify-lea`.
7. Segregation of duties — `ERR_SEGREGATION_OF_DUTIES` (403), on `POST /ei/cost-shares/{costShareId}/waive`.
8. Optimistic concurrency — `ERR_STALE_REFERRAL_VERSION` (412), on `POST /ei/ifsps` only.
9. State preconditions, one error per aggregate: `ERR_REFERRAL_STATE_INVALID` (409) on `POST /ei/referrals/{referralId}/assign-coordinator`, `/eligibility-determination`, `/entry-outcomes`, `/exit`, `/contact-logs`, plus `POST /ei/assessments`, `POST /ei/ifsps` and `POST /ei/cost-shares`; `ERR_IFSP_STATE_INVALID` (409) on `POST /ei/ifsps/{ifspId}/consent`, `POST /ei/ifsp-services`, `POST /ei/provider-authorizations` and `POST /ei/transition-plans`; `ERR_ASSESSMENT_NOT_SCHEDULED` (409) on `POST /ei/assessments/{assessmentId}/complete`; `ERR_PROVIDER_NOT_ACTIVE` (409) on `POST /ei/provider-authorizations` and `POST /ei/providers/{providerId}/suspend`; `ERR_AUTHORIZATION_NOT_ACTIVE` (409) on `POST /ei/service-visits` and `POST /ei/provider-authorizations/{authorizationId}/revoke`; `ERR_VISIT_NOT_SCHEDULED` (409) on `POST /ei/service-visits/{visitId}/document`; `ERR_VISIT_NOT_VOIDABLE` (409) on `POST /ei/service-visits/{visitId}/void`; `ERR_SERVICE_NOT_DELIVERABLE` (409) on `POST /ei/provider-authorizations`; `ERR_COST_SHARE_NOT_PROVISIONAL` (409) on `POST /ei/cost-shares/{costShareId}/finalize`, `/insurance-consent` and `/waive`; and `ERR_TRANSITION_PLAN_STATE_INVALID` (409) on `POST /ei/transition-plans/{transitionPlanId}/notify-lea`.
10. Child-protection and regulatory-compliance rules: `ERR_CHILD_AGE_INELIGIBLE` (422) and `ERR_DUPLICATE_REFERRAL` (409) on `POST /ei/referrals`, in that order; `ERR_PROVIDER_CREDENTIAL_EXPIRED` (422) on `POST /ei/provider-authorizations`; `ERR_NATURAL_ENVIRONMENT_JUSTIFICATION_REQUIRED` (422) on `POST /ei/ifsps/{ifspId}/consent`; `ERR_REQUIRED_ASSESSMENTS_INCOMPLETE` (422) on `POST /ei/referrals/{referralId}/eligibility-determination`; `ERR_EVALUATION_DOMAINS_INCOMPLETE` (422) on `POST /ei/assessments`; `ERR_TRANSITION_PLAN_INCOMPLETE` (422) on `POST /ei/transition-plans/{transitionPlanId}/notify-lea`; and `ERR_EXIT_OUTCOMES_REQUIRED` (422) on `POST /ei/referrals/{referralId}/exit`.
11. Referential business rules: `ERR_MAKEUP_TARGET_INVALID` (422) then `ERR_MAKEUP_ALREADY_SCHEDULED` (409) on `POST /ei/service-visits`; `ERR_SUPERSEDE_TARGET_INVALID` (422) on `POST /ei/ifsps`; `ERR_INSURANCE_POLICY_REQUIRED` (422) on `POST /ei/cost-shares/{costShareId}/insurance-consent` and `POST /ei/cost-shares/{costShareId}/finalize`; `ERR_PROVIDER_SERVICE_TYPE_MISMATCH` (422) on `POST /ei/provider-authorizations`; and `ERR_ALL_SERVICES_DECLINED` (422) on `POST /ei/ifsps/{ifspId}/consent`.
12. Constraint rules: `ERR_AUTHORIZATION_WINDOW_OVERLAP` (409) on `POST /ei/provider-authorizations`; `ERR_PROVIDER_SCHEDULE_CONFLICT` (409) on `POST /ei/service-visits`; `ERR_COST_SHARE_DUPLICATE` (409) on `POST /ei/cost-shares`; `ERR_TRANSITION_PLAN_DUPLICATE` (409) on `POST /ei/transition-plans`; and, on `POST /ei/referrals/{referralId}/assign-coordinator`, `ERR_COORDINATOR_NOT_ELIGIBLE` (422) before `ERR_NO_ELIGIBLE_COORDINATOR` (409) before `ERR_CASELOAD_CAP_EXCEEDED` (409).
13. Temporal rules, in this order: `ERR_DATE_IN_FUTURE` (422), `ERR_INVALID_DATE_RANGE` (422), `ERR_INVALID_VISIT_DURATION` (422), `ERR_MAKEUP_WINDOW_EXPIRED` (422), `ERR_TRANSITION_WINDOW_NOT_OPEN` (422), `ERR_NOTIFICATION_AFTER_THIRD_BIRTHDAY` (422), `ERR_VISIT_OUTSIDE_AUTHORIZATION_WINDOW` (422), and `ERR_VISIT_NOT_YET_OCCURRED` (422).
14. Capacity and money last: `ERR_UNITS_EXCEED_SERVICE_POOL` (422) on `POST /ei/provider-authorizations`; `ERR_UNITS_EXCEED_AUTHORIZATION` (422) on `POST /ei/service-visits` and `POST /ei/service-visits/{visitId}/document`; `ERR_ACTUAL_UNITS_EXCEED_SCHEDULED` (422) on `POST /ei/service-visits/{visitId}/document`; `ERR_WAIVE_EXCEEDS_BALANCE` (422) on `POST /ei/cost-shares/{costShareId}/waive`; and `ERR_LEDGER_WOULD_UNBALANCE` (409) on `POST /ei/service-visits/{visitId}/void`, `POST /ei/cost-shares/{costShareId}/waive` and `POST /ei/cost-shares/{costShareId}/finalize`.

The practical consequence worth internalising is that identity and shape come before existence, existence before ownership, ownership before concurrency, concurrency before state, state before regulatory safety, safety before referential integrity, referential integrity before constraints, constraints before dates, and dates before capacity and money. A request that is both mis-scoped and fiscally impossible reports the access error, never the fiscal one.

### 2.9. Rounding, Money and Unit Arithmetic

All money in this system is carried as an integer number of cents; there are no floating-point currency amounts anywhere in a request or a response. All service quantities are carried as whole 15-minute units.

Where a monetary computation requires rounding, the method is **round half up** to whole cents. Where a ratio is stored, the number of decimal places is fixed per field and the method is again round half up: `fpl_percent` is stored to 1 decimal place; `case_weight_points`, `weighted_caseload_points` and `max_weighted_caseload_points` to 2 decimal places; and `utilization_ratio` to 4 decimal places. Elapsed-day counts, unit counts and outcome ratings are integers computed with integer arithmetic and no rounding at all.

One rounding rule is more consequential than the others and is stated here so that it cannot be missed: in the sliding-scale fee computation, **each eligible service line is rounded to whole cents before the lines are summed**, never after. A sum-then-round implementation will differ from the specified result by a cent or more on many inputs, and that difference is a defect.

### 2.10. Conserved Quantities: the Unit Pool and the Family Ledger

Two arithmetic identities hold at all times and are re-checked after every write that could disturb them.

The **unit-pool invariant** belongs to a service line. A line's `units_committed` plus its `units_pool_remaining` always equals its `planned_units_total`, and `units_pool_remaining` is always between 0 and `planned_units_total` inclusive. Authorizing a provider moves units out of the pool; revoking or expiring an authorization hands the unspent remainder back. Because the identity is checked rather than assumed, a request that would commit more units than the line has left is refused with `ERR_UNITS_EXCEED_SERVICE_POOL` (HTTP 422) rather than driving the pool negative.

The **family-ledger invariant** belongs to a cost-share determination. A determination's `total_assessed_cents` always equals its `family_balance_cents` plus its `family_waived_cents`, and neither component is ever negative. A waiver moves cents from balance to waived and leaves the assessed total untouched; voiding a delivered visit removes that visit's contribution from the balance and reduces the assessed total by exactly the same amount, so the identity holds on both sides of the compensation. Any write that would leave the identity broken, or either component below zero, is refused with `ERR_LEDGER_WOULD_UNBALANCE` (HTTP 409).

### 2.11. Natural Environments and Service Settings

Federal early intervention policy prefers that evaluation and service happen where the child ordinarily spends time. The service encodes that preference through a single enumeration used by assessments, service lines and individual sessions alike: `setting_code` is one of `HOME`, `COMMUNITY_CHILDCARE`, `COMMUNITY_OTHER`, `CLINIC` or `PROGRAM_OFFICE`. The first three are natural environments; `CLINIC` and `PROGRAM_OFFICE` are not.

Choosing a non-natural setting is permitted but never silent. An assessment or service line whose `setting_code` is `CLINIC` or `PROGRAM_OFFICE` must carry a written `natural_environment_justification`, and wherever a justification is present — at assessment level, at service-line level, or at plan level — it must be at least 20 characters long, the count being taken after surrounding whitespace is trimmed away. The plan-level obligation is enforced at consent time rather than at authoring time, as §3.5 describes.

## 3. Business Logic & Workflows

The nine subsections below follow a case from the moment a physician picks up the phone to the month the child turns three and moves on to preschool services. They are written as a narrative rather than as a schema, because the coupling between objects is the substance of this system: a provider suspension is not a provider fact, it is a family fact, a fiscal fact, and a caseload fact. Where a rule belongs to more than one stage it is stated where it first bites and reinforced where it matters again.

### 3.1. The Front Door: Registering a Child and Opening a Case

Intake begins with the child, not the case. An `IntakeSpecialist` registers a child record carrying the child's `first_name`, `last_name`, `date_of_birth`, the `county_code` of residence, and the family's `primary_language` as an uppercase code such as `EN` or `ES`. Both `county_code` and `primary_language` must be non-empty uppercase tokens carrying no whitespace at all, and `date_of_birth` must be a real calendar date that is not later than the logical clock date — a child cannot be registered before they are born. A future `date_of_birth` is a payload-shape violation reported as `ERR_INVALID_REQUEST` (400), not as `ERR_DATE_IN_FUTURE`, which is why `date_of_birth` is absent from the list of dates §2.5 governs.

From the birth date the server derives `third_birthday_date`: the same month and day three calendar years later, except that a child born on 29 February takes 28 February as the anniversary. That single derived date anchors two later rules — the transition-window weight bonus in caseload scoring and the notification deadline for preschool transition — so it is worth getting right at registration. The child's `active_referral_count` starts at 0 and thereafter always reports how many referral records for that child are in a non-terminal status, that is, any status other than `NOT_ELIGIBLE` or `EXITED`.

Opening a case is the second act, and the same intake role performs it. A referral is opened with the `child_id` of the registered child, the `primary_referral_source` that federal reporting requires — one of `PHYSICIAN`, `HOSPITAL`, `PARENT`, `CHILD_CARE`, `SOCIAL_SERVICES`, `PUBLIC_HEALTH`, `EARLY_HEAD_START` or `OTHER` — the `referral_received_date` on which the program actually received the referral, the serving `county_code` for the case — an uppercase whitespace-free token on the same footing as the child's — and a narrative `presenting_concern` explaining why the child was referred. An optional `interpreter_required` flag defaults to false; when true it both raises the case's weight and narrows the set of coordinators who may take it.

The `referral_received_date` is day zero of the statutory clock. On creation the server computes `statutory_deadline_date` as that date plus 45 calendar days, sets `status` to `INTAKE`, sets `eligibility_status` to `PENDING`, sets `initial_timeline_status` to `IN_PROGRESS`, and recomputes the child's `active_referral_count`. Everything that will later be filled in — `coordinator_id`, `assignment_date`, `eligibility_determination_date`, `initial_ifsp_meeting_date`, `services_start_date`, `exit_date`, `exit_reason`, the six outcome ratings, `entry_outcomes_date` — begins as null, and the derived counters `excluded_delay_days`, `gross_elapsed_days`, `net_elapsed_days`, `service_duration_days` and `case_weight_points` begin at zero, with `monthly_contact_status` at `NOT_APPLICABLE` and `service_gap_flag` false.

Two child-protection rules guard intake, and they are evaluated in this order. First, the program serves children under three: the child's `third_birthday_date` must fall strictly after `referral_received_date`, and a referral for a child who has already reached the third birthday on the received date is rejected with `ERR_CHILD_AGE_INELIGIBLE`. Second, a child may hold only one open case at a time: if any other referral for the same child sits in a status other than `NOT_ELIGIBLE` or `EXITED`, the request is rejected with `ERR_DUPLICATE_REFERRAL`. A case that ended in either terminal status frees the child for a fresh referral.

### 3.2. Coordinator Assignment and the Weighted Caseload Standard

Before a case can move, someone must own it. A `ProgramAdmin` registers each service coordinator with a `full_name`, the `county_code` they serve, the `language_codes` they can serve families in directly (a non-empty array of uppercase tokens), and `max_weighted_caseload_points` — the state caseload standard expressed as a ceiling in weighted points, between 1.00 and 40.00 inclusive with two decimals. The ceiling is accepted as any number in that closed range, an integer as readily as a decimal, and is stored rounded half up to two decimal places, so a submitted 12.345 is persisted and reported as 12.35. An optional `status` defaults to `ACTIVE` and may be set to `INACTIVE`; only an `ACTIVE` coordinator ever enters the assignment candidate pool. A freshly registered coordinator has `weighted_caseload_points`, `active_case_count` and `utilization_ratio` all at zero.

Assignment moves the case from `INTAKE` to `EVALUATION_PENDING`. It is a `ProgramAdmin` action and takes a single optional input, `coordinator_id`. Supplying it names the coordinator the program wants; omitting it asks the server to choose. Either way the case's `coordinator_id` and its `assignment_date` — the logical clock date on which assignment happened — are stored, the case's `case_weight_points` is computed, the chosen coordinator's three aggregates are recomputed, and `Referral.version` is incremented by 1. Assignment is refused with `ERR_REFERRAL_STATE_INVALID` unless the case is in `INTAKE`.

**How a case is weighted.** A case's `case_weight_points` is not a headcount of 1; it is a scored estimate of how much coordinator effort the case consumes, recomputed on assignment, on every referral status transition, on the creation or discontinuation of a service line, on parental consent to a plan, on the provider suspension or termination cascade of §3.6, whenever the logical clock is advanced, and at exit. The computation starts from a stage base. A case in `NOT_ELIGIBLE` or `EXITED` weighs exactly 0.00 and drops out of every caseload total. A case in any pre-plan stage — `INTAKE`, `EVALUATION_PENDING`, `ELIGIBILITY_DETERMINED` or `IFSP_PENDING` — takes a base of 1.50 points, because pre-plan work is the heavier part of the job. A case in `ACTIVE_SERVICES` takes a base of 1.00 point.

Three complexity additions are then summed onto that base. When the case's `interpreter_required` flag is true, add 0.50 points. When the child's third birthday is close — specifically when the whole number of days from the logical clock date to `third_birthday_date` is at most 180, which is the final six months before the child ages out, add 0.75 points, which is why simply advancing the clock can raise a case's weight without anyone touching the case. When the plan carries at least four live service lines, add 0.50 points. Finally, and only after the additions have all been summed, the total is clamped into the range from 1.00 to 3.00 points inclusive: a total below 1.00 is raised to 1.00, a total above 3.00 is lowered to 3.00, and the clamp is never applied to an intermediate value. The result is stored to two decimal places, rounded half up.

For the four-line test, a live service line is one whose own `status` is `PLANNED`, `AUTHORIZED`, `IN_DELIVERY` or `AT_RISK` on **any** plan of the case, whatever that plan's own status — so the `PLANNED` lines of a `DRAFT` successor plan are counted alongside the live lines of the `ACTIVE` plan it will replace; `DISCONTINUED` and `COMPLETED` lines are not counted. A case that crosses from three live lines to four gains the 0.50, and one that falls back from four to three loses it again — but only when one of the triggers listed above actually recomputes the weight: a line that leaves the live set by reaching `COMPLETED` through documented delivery is not itself a trigger, so the stored `case_weight_points` keeps the bonus until the next recomputation reaches the case.

**Who is eligible.** A coordinator is a candidate for a case when four clauses all hold: the coordinator's `status` is `ACTIVE`; the coordinator's `county_code` equals the referral's `county_code`; either the case does not require an interpreter, or the case's family `primary_language` appears in the coordinator's `language_codes`; and the coordinator's current `weighted_caseload_points` plus the case's projected `case_weight_points` is less than or equal to the coordinator's `max_weighted_caseload_points`. The capacity comparison is inclusive: a coordinator who would land exactly on their ceiling is eligible, and one who would exceed it by any amount is not. The projected weight used here is the weight the case will carry once assigned, not the zero it carries beforehand.

When the request names a coordinator explicitly, the server validates that coordinator against the three non-capacity clauses — active standing, county match, and language coverage when an interpreter is needed — and rejects a coordinator who fails any of them with `ERR_COORDINATOR_NOT_ELIGIBLE`. When the request omits the coordinator, the server builds the candidate set from every coordinator on the roster who satisfies all four clauses — the three non-capacity clauses **and** the capacity clause — and, if that set is empty, rejects the assignment with `ERR_NO_ELIGIBLE_COORDINATOR` without writing anything. The capacity clause is reported separately only on the named path: a coordinator named in the request who clears the three non-capacity clauses but whose points plus the projected weight would exceed the ceiling produces `ERR_CASELOAD_CAP_EXCEEDED`. On the auto-selection path capacity is folded into candidacy instead, so a roster whose every otherwise-eligible coordinator is out of headroom reports `ERR_NO_ELIGIBLE_COORDINATOR` and never `ERR_CASELOAD_CAP_EXCEEDED`.

**How the server chooses.** Auto-selection is deterministic. Each candidate is ranked by its **projected utilization** — the coordinator's current `weighted_caseload_points` plus the case's projected weight, divided by that coordinator's `max_weighted_caseload_points`, rounded half up to four decimal places — and the candidate with the lowest projected utilization wins. Ranking on a percentage rather than on raw points is deliberate, so that coordinators with different ceilings compete fairly. When two candidates tie on the rounded ratio, the earlier `created_at` wins, and when they also share an identical `created_at` — routine, since timestamps come from the logical clock — the one registered first wins. Record identifiers are never a decision input.

**Caseload aggregates.** A coordinator's `active_case_count` is the number of referrals assigned to them whose status is neither `NOT_ELIGIBLE` nor `EXITED`, and their `weighted_caseload_points` is the sum of `case_weight_points` over exactly that same set of referrals, held to two decimal places rounded half up. Both drop a case in the very request that closes it. `utilization_ratio` is `weighted_caseload_points` divided by `max_weighted_caseload_points`, rounded half up to four decimal places. A computed caseload read exposes those numbers together with the coordinator's own identifier as `coordinator_id`, the ceiling as `max_weighted_caseload_points`, a `headroom_points` figure giving the ceiling minus the current weighted points to two decimal places, and a `caseload_posture` verdict. The posture is `OVER` when weighted points exceed the ceiling, `AT_CAP` when they equal it exactly, `NEAR_CAP` when neither of those holds but the utilization ratio is at least 0.9000, and `OPEN` otherwise — the tests are applied in that order, so an over-cap coordinator never reports `NEAR_CAP`.

### 3.3. Evaluation, Family Assessment, and the Statutory 45-Day Timeline

An `Evaluator` schedules each piece of evaluation work as its own record against a case, supplying the `referral_id`, the `assessment_type`, a `scheduled_date`, and the `setting_code` where the work will happen. The type is one of `INITIAL_EVALUATION` — the multidisciplinary evaluation that establishes eligibility — `FAMILY_ASSESSMENT`, the family-directed assessment of concerns, priorities and resources, or `SUPPLEMENTAL_EVALUATION`, additional evaluation ordered after the fact. A `natural_environment_justification` explains a `CLINIC` or `PROGRAM_OFFICE` setting and must run to at least 20 characters whenever it is supplied; it is optional for a natural setting but, as §2.11 requires, mandatory for `CLINIC` or `PROGRAM_OFFICE`, and omitting it there is a payload-shape failure reported as `ERR_INVALID_REQUEST` (400) — a check made before the `referral_id` is resolved, so it outranks `ERR_REFERRAL_NOT_FOUND`. An optional `domains_assessed` array records which developmental domains the work covers, drawn from `PHYSICAL`, `COGNITIVE`, `COMMUNICATION`, `SOCIAL_EMOTIONAL` and `ADAPTIVE`, with no repeats; when it is omitted the record stores `domains_assessed` as null rather than as an empty array. A new record is created with `status` `SCHEDULED`, `completion_date`, `eligibility_recommendation` null, `family_unavailable_days` at 0, and the acting evaluator's identifier captured as `evaluator_user_id`.

An initial evaluation is held to a stricter standard than the others: its `domains_assessed` must list all five developmental domains, and one that omits any domain is rejected with `ERR_EVALUATION_DOMAINS_INCOMPLETE`. Family and supplemental assessments may cover any subset, and an initial evaluation that omits `domains_assessed` altogether fails the same way. Scheduling is permitted from every non-terminal case status — `INTAKE`, `EVALUATION_PENDING`, `ELIGIBILITY_DETERMINED`, `IFSP_PENDING` and `ACTIVE_SERVICES` alike — and refused only against a case already in `NOT_ELIGIBLE` or `EXITED`, which fails with `ERR_REFERRAL_STATE_INVALID`.

Completing an assessment is a separate `Evaluator` action that advances the record `SCHEDULED → COMPLETED` and takes three inputs: the `completion_date`, the `eligibility_recommendation` — `ELIGIBLE`, `NOT_ELIGIBLE` or `INCONCLUSIVE` — and an optional `family_unavailable_days` count that defaults to 0 and must be an integer from 0 through 120. Only a `SCHEDULED` record may be completed; anything else is refused with `ERR_ASSESSMENT_NOT_SCHEDULED`. The `completion_date` must be on or after the case's `referral_received_date` and must not be after the logical clock date.

That `family_unavailable_days` figure is the only documented excuse the statutory clock recognises, and it exists because a program cannot be held to a deadline it was prevented from meeting. Completing an assessment therefore reaches beyond the assessment row: the case's `excluded_delay_days` is recomputed as the sum of `family_unavailable_days` across every assessment on the case whose `status` is `COMPLETED`, and from that new figure the case's `gross_elapsed_days`, `net_elapsed_days` and `initial_timeline_status` are all recomputed in the same request. Records still `SCHEDULED`, and records that were `CANCELLED` without ever being completed, contribute nothing.

**The timeline computation.** The initial IFSP meeting must occur on or before the case's `statutory_deadline_date`, which is `referral_received_date` plus 45 calendar days. To decide where the clock currently stands the server first fixes a stop date. If the case has an initial plan — a plan whose `ifsp_type` is `INITIAL` and whose `status` is `PENDING_CONSENT`, `ACTIVE`, `AMENDMENT_PENDING`, `SUPERSEDED` or `CLOSED` — with a recorded `meeting_date`, that meeting date is the stop date and the clock has stopped; should the case carry more than one such initial plan, the most recently authored of them supplies the stop date. Otherwise the stop date is the current logical clock date and the clock is still running. A `WITHDRAWN` initial plan never stops the clock, so a case whose only initial plan has been withdrawn falls back to the logical clock date.

`gross_elapsed_days` is then the whole number of days from `referral_received_date`, exclusive, to the stop date, inclusive. `excluded_delay_days` is the documented-unavailability total described above. `net_elapsed_days` is the gross count minus the excluded total, floored at zero so that it never goes negative. Both counts are reported, and the difference between them is the point of the design: the gross count is the raw wall-clock span the state reports federally, while the net count is the only figure that determines compliance. The same case can be over 45 days on the gross count and inside 45 days on the net count.

`initial_timeline_status` follows from the net count alone. When `net_elapsed_days` is at most 45, the status is `MET` if the stop date came from an initial plan's meeting date and `IN_PROGRESS` if the stop date is merely today's logical clock date. When `net_elapsed_days` exceeds 45, the status is `MISSED`. All of this is integer day arithmetic; no rounding is involved. The verdict is recomputed whenever an assessment on the case is completed, whenever the eligibility determination is recorded, whenever an initial plan's meeting date is recorded, and on every advance of the logical clock — and it is also recomputed on demand when the compliance read is served.

A computed compliance read gathers the whole statutory picture for one case in a single response: the case's own identifier as `referral_id`, its `referral_received_date`, its `statutory_deadline_date`, the `stop_date` the computation used, `gross_elapsed_days`, `excluded_delay_days`, `net_elapsed_days`, `initial_timeline_status`, and — because auditors ask both questions together — the case's `monthly_contact_status` and `last_qualifying_contact_date`. The recomputation this read performs is pure: the four timeline figures it reports are derived afresh for the response but are not written back to the referral, so serving the read never refreshes `updated_at` or advances `version`, and the two contact fields it echoes are simply the stored ones. A case whose stored counters were last written before the clock moved can therefore report a fresher verdict here than the referral resource itself shows.

### 3.4. Eligibility, Entry Child Outcomes, and the Supplemental-Evaluation Revert

Eligibility is a `ProgramAdmin` determination, and it is the fork in the road for the whole case. The request carries a boolean `is_eligible` and a `determination_date`. Three preconditions guard it. The case must be in `EVALUATION_PENDING`, or the request is refused with `ERR_REFERRAL_STATE_INVALID`. The case must have at least one `COMPLETED` assessment of type `INITIAL_EVALUATION` **and** at least one `COMPLETED` assessment of type `FAMILY_ASSESSMENT` — a case with only one of the two, or with both still merely scheduled, is refused with `ERR_REQUIRED_ASSESSMENTS_INCOMPLETE`. And the `determination_date` must be on or after `referral_received_date` and not after the logical clock date.

When `is_eligible` is true the case moves `EVALUATION_PENDING → ELIGIBILITY_DETERMINED`. Its `eligibility_status` becomes `ELIGIBLE`, its `eligibility_determination_date` records the supplied date, and the statutory counters — `excluded_delay_days`, `gross_elapsed_days`, `net_elapsed_days` and `initial_timeline_status` — are recomputed. `Referral.version` is incremented by 1.

When `is_eligible` is false the case moves `EVALUATION_PENDING → NOT_ELIGIBLE`, which is terminal, and the consequences are broader rather than narrower. Its `eligibility_status` becomes `NOT_ELIGIBLE` and `eligibility_determination_date` is stored exactly as in the eligible branch. Beyond that: every assessment on the case still in `SCHEDULED` transitions to `CANCELLED`, and a cancelled record is frozen — it can never be completed and never contributes `family_unavailable_days` to the excluded total. The case's `case_weight_points` is set to 0, and because the case has left the non-terminal population the assigned coordinator's `weighted_caseload_points`, `active_case_count` and `utilization_ratio` are all recomputed in the same request. The child's `active_referral_count` is recomputed too, which is what frees the child to be referred again later. `Referral.version` is incremented by 1 on this branch as well.

**Entry outcomes.** An eligible case cannot proceed to plan development until the child's starting point has been measured. An `Evaluator` records the three federal child-outcome entry ratings — `rating_social` for positive social relationships, `rating_knowledge` for acquiring and using knowledge and skills, and `rating_needs` for taking action to meet needs — together with a `measurement_date`. Each rating must be an integer from 1 through 7 inclusive. The `measurement_date` must be on or after the case's `eligibility_determination_date` and must not be after the logical clock date. The three values are stored as `entry_rating_social`, `entry_rating_knowledge` and `entry_rating_needs`, the date as `entry_outcomes_date`, the case advances `ELIGIBILITY_DETERMINED → IFSP_PENDING`, and `Referral.version` is incremented by 1. Because this step is mandatory, a case can never reach `ACTIVE_SERVICES` — and therefore can never exit from it — without entry ratings on file.

**The revert.** Occasionally the IFSP team convenes and concludes that the evaluation record is simply not good enough to plan from. The remedy is to schedule a `SUPPLEMENTAL_EVALUATION`, and doing so while the case sits in `IFSP_PENDING` cycles the case backwards: `IFSP_PENDING → EVALUATION_PENDING`. The revert is permitted only when no plan on the case has reached `ACTIVE` or `AMENDMENT_PENDING`; once services are live, additional evaluation is scheduled without disturbing the case status.

The revert drags a four-hop cascade behind it. Every plan on the case whose `status` is `DRAFT` or `PENDING_CONSENT` transitions to `WITHDRAWN`. Every service line on each withdrawn plan whose `status` is not already `DISCONTINUED` transitions to `DISCONTINUED`. Each withdrawn plan then has its `service_line_count` and `non_natural_setting_line_count` recomputed. The case's `initial_ifsp_meeting_date` is re-derived from whatever initial plans survive — it falls back to null when the withdrawn plan was the only initial plan on the case — and the statutory counters `gross_elapsed_days`, `net_elapsed_days` and `initial_timeline_status` are recomputed against the restored running clock, which typically returns the verdict to `IN_PROGRESS`. And because the number of live service lines on the case has just collapsed, the case's `case_weight_points` is recomputed — the four-line bonus is lost if it was held — after which the assigned coordinator's caseload aggregates are recomputed from the new case weight, `monthly_contact_status` is recomputed, and `Referral.version` advances by 1 like any other write that changes the case row. A supplemental evaluation on a case in any other status, or on an `IFSP_PENDING` case that already carries a plan in `ACTIVE` or `AMENDMENT_PENDING`, simply creates a scheduled record and changes nothing else.

### 3.5. Plan Authoring, Service Lines, and Parental Consent

A plan is authored by a `ProgramAdmin` against a case. The request carries the `referral_id`, the `ifsp_type`, the `meeting_date` on which the IFSP team met, the `authoring_coordinator_id` of the coordinator credited with authoring the plan — normally, though not necessarily, the case's assigned coordinator, and recorded as provenance only: the value is never resolved against the coordinator roster, so an identifier matching no coordinator is stored as submitted and never produces `ERR_COORDINATOR_NOT_FOUND` — and the concurrency token `expected_referral_version` described in §2.6. Two optional inputs complete the payload: `supersedes_ifsp_id`, naming the plan this one replaces, and a plan-level `natural_environment_justification` which, when present, must run to at least 20 characters.

`ifsp_type` is either `INITIAL`, the first plan on a case, or `ANNUAL`, a plan that replaces a live one. The distinction is enforced through `supersedes_ifsp_id`: it is **required** for an `ANNUAL` plan and **forbidden** on an `INITIAL` plan, and when supplied it must name a plan whose `status` is `ACTIVE`, on the same case, that no other plan outside `WITHDRAWN` already supersedes. Any violation of that cluster of conditions — missing when required, present when forbidden, pointing at a plan that is not active, pointing at another case's plan, or pointing at a plan already claimed by a second successor — is rejected with `ERR_SUPERSEDE_TARGET_INVALID`. The `meeting_date` must not be after the logical clock date.

A new plan is created in `DRAFT`. For an `INITIAL` plan authoring writes `Referral.initial_ifsp_meeting_date` — that field is re-derived from the most recently authored `INITIAL` plan on the case in any status other than `WITHDRAWN`, `DRAFT` included, which is a wider set than the stop-clock statuses of §3.3 — and recomputes the case's `gross_elapsed_days`, `net_elapsed_days` and `initial_timeline_status`. Because the plan is still in `DRAFT` at that moment, and `DRAFT` is not a stop-clock status, the recomputation still measures to the logical clock date and leaves the verdict where it stood: the meeting date becomes the stop date only once the plan has reached `PENDING_CONSENT`, and adding a service line is not itself a timeline trigger, so the stored verdict flips to `MET` or `MISSED` at the next trigger from the list in §3.3 while the computed compliance read shows the flip immediately. Authoring increments `Referral.version` by 1 regardless of type, and is refused with `ERR_REFERRAL_STATE_INVALID` unless the case is in `IFSP_PENDING` or `ACTIVE_SERVICES` — the only two statuses from which plan authoring is declared.

**Service lines.** A plan's substance is its service lines, each added by a `ProgramAdmin` with the `ifsp_id` of the plan, the `service_type` to be delivered, the `setting_code` where delivery will happen, a `frequency_per_month` of 1 to 30 planned sessions, `units_per_session` of 1 to 8 fifteen-minute units, a `unit_rate_cents` state rate per unit between 1 and 100000 cents, and a `planned_units_total` between 1 and 4000 units that fixes how many units the plan authorizes for this line in total. An optional `natural_environment_justification` of at least 20 characters accompanies a `CLINIC` or `PROGRAM_OFFICE` setting.

`service_type` is one of `SPEECH_THERAPY`, `OCCUPATIONAL_THERAPY`, `PHYSICAL_THERAPY`, `DEVELOPMENTAL_INSTRUCTION`, `SOCIAL_WORK`, `SERVICE_COORDINATION` or `EVALUATION_ASSESSMENT`. Two of those seven are services the family may never be charged for: the server computes `family_fee_exempt` as true exactly when `service_type` is `SERVICE_COORDINATION` or `EVALUATION_ASSESSMENT`, and an exempt line never enters the sliding-scale fee computation and never accrues a family share on any of its sessions. Every other type is computed as false.

A new line is created in `PLANNED` with `units_committed` at 0, `units_pool_remaining` equal to `planned_units_total`, `units_delivered` at 0, `makeup_owed_units` at 0 and `declined_by_family` false. Adding the line recomputes the plan's `service_line_count` — the number of lines on the plan whose status is not `DISCONTINUED` — and its `non_natural_setting_line_count`, the number of those same non-discontinued lines whose `setting_code` is `CLINIC` or `PROGRAM_OFFICE`. It then recomputes the case's `case_weight_points` if the live-line count has crossed the four-line threshold, and the assigned coordinator's aggregates after that.

Adding a line also moves the plan itself, and which way it moves depends on where the plan already is. The **first** non-discontinued line on a `DRAFT` plan advances it `DRAFT → PENDING_CONSENT`: a plan with no services is not something a parent can be asked to sign. A line added to a plan already in `ACTIVE` moves it `ACTIVE → AMENDMENT_PENDING`, and while a plan sits in `AMENDMENT_PENDING` **no new provider authorization may be created for any of its lines** until the family has re-consented and the plan has returned to `ACTIVE`. Lines may be added while a plan is in `DRAFT`, `PENDING_CONSENT`, `ACTIVE` or `AMENDMENT_PENDING`; an attempt against a plan in any other status is refused with `ERR_IFSP_STATE_INVALID`.

**Consent.** Only a `FamilyRepresentative` records consent, and only for their own child: the acting `X-User-ID` must equal the case's `child_id`, or the request is refused with `ERR_NOT_RESOURCE_OWNER`. The plan must be in `PENDING_CONSENT` or `AMENDMENT_PENDING`, or the request is refused with `ERR_IFSP_STATE_INVALID`. The payload carries a `consent_scope` of either `FULL` or `PARTIAL`, the `consent_signed_date` on which the parent signed, and — for a partial consent — a `declined_service_ids` array naming the lines the family does not accept. Whenever that array is supplied it must be a non-empty array of unique identifier strings; an explicitly submitted empty array is a payload-shape failure reported as `ERR_INVALID_REQUEST`, not as a declined-services error. On a `FULL` consent the array is accepted and then ignored outright, so no line is declined however it is populated.

Two consent-time guards apply. First, the natural-environment obligation lands here rather than at authoring: when the plan's `non_natural_setting_line_count` is greater than zero, the plan's own `natural_environment_justification` must be present and at least 20 characters long, and a consent attempt on a plan that offers clinic or office services without that plan-level justification is refused with `ERR_NATURAL_ENVIRONMENT_JUSTIFICATION_REQUIRED`. Second, a partial consent must leave something behind: `declined_service_ids` must actually be present, every identifier in it must belong to this plan, and at least one line on the plan whose `status` is not already `DISCONTINUED` must remain undeclined — an already-`DISCONTINUED` line may be named, since it does belong to the plan, but it does not count towards what remains. A partial consent that omits the array altogether, that names a line from another plan, or that leaves no undiscontinued line undeclined, is refused with `ERR_ALL_SERVICES_DECLINED`.

Consent advances the plan `PENDING_CONSENT → ACTIVE` or, closing the amendment cycle, `AMENDMENT_PENDING → ACTIVE`. It stores `consent_scope`, `consent_signed_date`, the acting family identifier as `consent_user_id`, and `activated_date` — the date the plan most recently reached `ACTIVE`. On an amendment consent those same four fields are overwritten with the new consent, and a single plan row may traverse `ACTIVE → AMENDMENT_PENDING → ACTIVE` any number of times over its life. Each line named in `declined_service_ids` has `declined_by_family` set to true and transitions to `DISCONTINUED`, and its unit-pool fields are recomputed over an authorization set that consent leaves entirely alone: declining a line at an amendment consent neither revokes its existing authorizations nor hands their committed units back to the line's pool, and it cancels none of their scheduled sessions. The plan's `service_line_count` and `non_natural_setting_line_count` are recomputed after that. Every consent, whichever branch it takes, then recomputes the case's `case_weight_points`, `monthly_contact_status` and `service_gap_flag` and the assigned coordinator's caseload aggregates.

Consenting to an `INITIAL` plan is the moment services begin, and it moves the case as well as the plan. The case transitions `IFSP_PENDING → ACTIVE_SERVICES`, its `services_start_date` is set to the plan's `consent_signed_date`, its `case_weight_points` is recomputed — the stage base drops from 1.50 to 1.00, which usually lowers the coordinator's load even as the case becomes busier — the coordinator's aggregates are recomputed after it, and `monthly_contact_status` is recomputed for the first time, leaving `NOT_APPLICABLE` behind.

Consenting to an `ANNUAL` plan retires the plan it replaces, and that is the second of the system's five-hop cascades. In the same request in which the successor reaches `ACTIVE`, the prior plan transitions `ACTIVE → SUPERSEDED`. Every service line on the superseded plan that is not already `DISCONTINUED` transitions to `DISCONTINUED` — the four live statuses `PLANNED`, `AUTHORIZED`, `IN_DELIVERY` and `AT_RISK`, and a line already `COMPLETED` along with them, since the retired plan keeps no line of its own alive. Every provider authorization on those lines whose `status` is `ACTIVE`, `EXHAUSTED` or `SUSPENDED` transitions to `REVOKED`, with `units_released` set to that authorization's `units_remaining` and `revocation_reason_code` recorded as `PLAN_SUPERSEDED`. Each affected line then has `units_committed` and `units_pool_remaining` recomputed, which is what restores the unit-pool identity of §2.10. And every session still in `SCHEDULED` on those authorizations transitions to `CANCELLED_PROGRAM` with its `billing_status` set to `CANCELLED_NO_CHARGE`. The superseded plan's own `service_line_count` and `non_natural_setting_line_count` are recomputed once its lines have been discontinued, and both therefore fall to 0. A transition plan still in `DRAFT` against the superseded plan transitions to `CANCELLED`, leaving the family free to open a fresh transition plan against the successor.

Plans can also die without being replaced. When a case reverts to `EVALUATION_PENDING`, or exits before services ever started, every plan on it in `DRAFT` or `PENDING_CONSENT` transitions to `WITHDRAWN` and every service line on that plan transitions to `DISCONTINUED`. `SUPERSEDED`, `CLOSED` and `WITHDRAWN` are all terminal plan statuses; a plan in any of them accepts no further consent, no further lines and no further authorizations.

### 3.6. The Provider Network, Authorizations, and the Service-Unit Pool

A `ProgramAdmin` registers each provider agency or independent practitioner with an `agency_name`, a `qualified_service_types` array listing the service types the provider is credentialed to deliver — a non-empty subset of the seven service types — and a `credential_expiry_date` recording when that credential lapses. That date is unconstrained in either direction: a `credential_expiry_date` already in the past relative to the logical clock is accepted at registration without complaint and simply blocks every authorization written afterwards. A new provider is created with `status` `ACTIVE` and `active_authorization_count` at 0, the latter always reporting how many of that provider's authorizations are currently in `ACTIVE`. Provider standing is one of `ACTIVE`, `SUSPENDED` or `TERMINATED`, and `TERMINATED` is terminal.

**Authorizing delivery.** An authorization is the funding instrument that lets one provider deliver one service line over one date window. A `ProgramAdmin` creates it with the `ifsp_service_id` of the line, the `provider_id` of the provider, a `start_date` and an `end_date` bounding the window inclusively at both ends, and the `authorized_units` to be drawn from the line's pool, between 1 and 4000 units. On creation the authorization's `status` is `ACTIVE`, its `unit_rate_cents` is copied from the service line's `unit_rate_cents` and **pinned for the life of the authorization** so that a later rate change on the plan cannot retroactively re-price sessions already funded, its `units_consumed` and `units_released` are 0, and its `units_remaining` equals `authorized_units`. The line moves `PLANNED → AUTHORIZED` when its `status` is still `PLANNED` — a line already past that point, including one whose every earlier authorization has since been revoked, keeps whatever status it holds — its `units_committed`, `units_pool_remaining` and `units_delivered` are recomputed, and the provider's `active_authorization_count` is recomputed. Nothing above the line moves: authorizing recomputes neither the case's `case_weight_points` nor its `service_gap_flag`, and touches no coordinator aggregate.

Authorizing is the most heavily guarded write in the system, and the checks are worth enumerating in the order they are applied. The parent plan must be in `ACTIVE` — a plan in `DRAFT`, `PENDING_CONSENT` or, importantly, `AMENDMENT_PENDING` cannot have new authorizations written against it, and the attempt is refused with `ERR_IFSP_STATE_INVALID`. The provider must be in `ACTIVE` standing, or the request is refused with `ERR_PROVIDER_NOT_ACTIVE`. The service line must still be deliverable — its `status` must be `PLANNED`, `AUTHORIZED`, `IN_DELIVERY` or `AT_RISK`; a `DISCONTINUED` or `COMPLETED` line accepts no new authorization and produces `ERR_SERVICE_NOT_DELIVERABLE`. The provider's `credential_expiry_date` must be on or after the requested `end_date`, so that no authorization can extend past the credential that justifies it; an over-reaching window is refused with `ERR_PROVIDER_CREDENTIAL_EXPIRED`. The line's `service_type` must then appear in the provider's `qualified_service_types`, or the request is refused with `ERR_PROVIDER_SERVICE_TYPE_MISMATCH`. The window must not collide with another window on the same line. Only then is the window itself checked for order, with `end_date` on or after `start_date`, or the request fails with `ERR_INVALID_DATE_RANGE` — the collision test runs first, exactly as §2.8 ranks it, so a reversed window that nonetheless collides reports the overlap and not the range error. And finally `authorized_units` must be less than or equal to the line's current `units_pool_remaining`, or the request is refused with `ERR_UNITS_EXCEED_SERVICE_POOL`.

**Window collision is closed-interval.** Two authorization windows on the same service line are treated as closed intervals that include both endpoints. A new window conflicts with an existing one when the new `start_date` is on or before the existing `end_date` **and** the existing `start_date` is on or before the new `end_date`; a conflict is refused with `ERR_AUTHORIZATION_WINDOW_OVERLAP`. The practical consequence is that windows may not even touch: a new window starting exactly on an existing window's end date conflicts, while one starting a single day later does not. Only windows whose authorization is in `ACTIVE`, `SUSPENDED` or `EXHAUSTED` are considered; `REVOKED` and `EXPIRED` windows are ignored entirely, so a revoked window's dates may be re-covered by a fresh authorization.

**The pool arithmetic.** A line's `units_committed` is the sum of `authorized_units` over its authorizations in `ACTIVE`, `EXHAUSTED` or `SUSPENDED`, plus, for each authorization in `REVOKED`, that authorization's `authorized_units` minus its `units_released`, plus the same quantity for each authorization in `EXPIRED`. `units_pool_remaining` is then the line's `planned_units_total` minus `units_committed`. A revoked authorization therefore keeps whatever it already spent as committed and hands the rest back, which is why revoking an untouched authorization returns exactly what it took. Both figures are recomputed on authorization creation, revocation and expiry, on plan supersession, on plan withdrawal and on case exit, and the identity of §2.10 is re-checked each time. An authorization's own `units_remaining` is derived in the same spirit rather than maintained independently: it is that authorization's `authorized_units` minus its `units_consumed` minus its `units_released`, recomputed immediately after any write that moves either counter.

**The authorization lifecycle.** An authorization advances `ACTIVE → EXHAUSTED` automatically at the moment its `units_consumed` equals its `authorized_units`, that is, when `units_remaining` reaches 0; no further session may be created against an `EXHAUSTED` authorization. It moves `ACTIVE → SUSPENDED` when its provider is suspended. It moves `ACTIVE → EXPIRED` when the logical clock is advanced past its `end_date` — strictly past, so an authorization whose `end_date` is the current logical date is left `ACTIVE` — at which point `units_released` is set to `units_remaining` and the parent line's pool fields are recomputed. Expiry cancels nothing: a session still `SCHEDULED` on an expired authorization stays `SCHEDULED`, no makeup obligation is created, and neither the line's `makeup_owed_units` nor the case's `service_gap_flag` is recomputed by the expiry hop. And it can be revoked outright by a `ProgramAdmin`, who supplies a `revocation_reason_code` from `PROVIDER_SUSPENDED`, `PROVIDER_TERMINATED`, `PLAN_SUPERSEDED`, `CASE_EXITED`, `ADMIN_CORRECTION`, `FAMILY_REQUEST` or `WINDOW_EXPIRED`. Revocation is available from `ACTIVE`, `EXHAUSTED` and `SUSPENDED`; an authorization already in `REVOKED` or `EXPIRED` is not revocable and the attempt is refused with `ERR_AUTHORIZATION_NOT_ACTIVE`. Revoking sets `units_released` to the authorization's `units_remaining`, records `revoked_date` as the logical clock date and stores the `revocation_reason_code`; every session still in `SCHEDULED` on that authorization transitions to `CANCELLED_PROGRAM` with `billing_status` `CANCELLED_NO_CHARGE`; the line's `units_committed` and `units_pool_remaining` are recomputed, restoring the pool; the line's `makeup_owed_units` and the case's `service_gap_flag` are recomputed after them, though a revocation cancels its sessions as `CANCELLED_PROGRAM` and therefore adds no makeup obligation of its own; and the provider's `active_authorization_count` is recomputed. Every revocation reached through a cascade — plan supersession, provider termination or case exit — writes the same three fields as an explicit revocation does: `units_released`, `revoked_date` at the logical clock date, and the `revocation_reason_code` that cascade carries. Revoking an `EXHAUSTED` authorization releases exactly 0 units, because its `units_remaining` is already 0, and the line's committed total is therefore unchanged. One reverse edge exists: an `EXHAUSTED` authorization returns to `ACTIVE` when a delivered session on it is voided, as §3.7 describes.

**Suspension and termination.** Removing a provider from service is a `ProgramAdmin` action carrying a `suspension_reason_code` and an `effective_date`. The reason code is one of `CREDENTIAL_LAPSE`, `QUALITY_CONCERN`, `BILLING_AUDIT`, `VOLUNTARY_WITHDRAWAL` or `CONTRACT_ENDED`, and the code itself selects the branch: `CONTRACT_ENDED` terminates the provider, moving it `ACTIVE → TERMINATED`, while every other code suspends it, moving it `ACTIVE → SUSPENDED`. Either branch requires the provider to be in `ACTIVE` standing, refusing anything else with `ERR_PROVIDER_NOT_ACTIVE`, and requires the `effective_date` not to be after the logical clock date. Both branches store `suspension_reason_code` and record `suspended_date` as the supplied `effective_date`.

From there the two branches run the same five-hop cascade with one difference, and the difference is the whole point of having two branches. On the suspension branch, every authorization for that provider whose `status` is `ACTIVE` transitions to `SUSPENDED` and keeps its units committed, because the program expects the provider back. On the termination branch, those same authorizations transition to `REVOKED` instead, each with `units_released` set to its `units_remaining` and `revocation_reason_code` recorded as `PROVIDER_TERMINATED`, so the units flow back to their lines' pools and the affected lines have `units_committed` and `units_pool_remaining` recomputed.

The remaining three hops are identical on both branches. Every session still in `SCHEDULED` on an affected authorization transitions to `CANCELLED_PROVIDER` with `billing_status` set to `CANCELLED_NO_CHARGE`. Each affected service line has its `makeup_owed_units` increased by the `scheduled_units` of the sessions just cancelled, and where the resulting owed total strictly exceeds 4 units — one full hour of missed service — the line transitions to `AT_RISK`. And finally each affected case has its `service_gap_flag` recomputed rather than simply asserted — it comes out true exactly when at least one line on the case now stands in `AT_RISK`, and stays false when the cancelled sessions left every line's owed total at 4 units or below — after which that case's `case_weight_points` and then the assigned coordinator's caseload aggregates are recomputed. The flag is the signal a program manager watches for, and a single suspension of a busy provider can therefore raise it on a dozen unrelated families in one request.

### 3.7. Scheduling Sessions, Documenting Delivery, Makeup Obligations, and Voids

Either a `ProgramAdmin` or a `ServiceCoordinator` may schedule a session. The payload names the `provider_authorization_id` the session draws from, the `scheduled_start` and `scheduled_end` instants bounding it, and the `setting_code` where it will happen. An optional `makeup_for_visit_id` marks the session as the makeup for an earlier provider cancellation. A new session is created with `visit_status` `SCHEDULED` and `billing_status` `PENDING`, and the server computes `scheduled_units` as the length of the interval in minutes divided by 15. Everything that documentation or a void will later write begins null rather than zero: `actual_units`, `actual_start`, `actual_end`, `session_note`, `documented_by_user_id`, `documented_at_utc`, `family_share_cents` and `void_reason_code`. No units are consumed and no family money accrues at scheduling time; both happen only at documentation.

The interval is treated as **half-open**: it includes `scheduled_start` and excludes `scheduled_end`. Its length must be strictly positive, a whole multiple of 15 minutes, and at most 240 minutes — four hours, or 16 units — with both endpoints falling on a 15-minute boundary; anything else is refused with `ERR_INVALID_VISIT_DURATION`. The target authorization must be in `ACTIVE`, or the request is refused with `ERR_AUTHORIZATION_NOT_ACTIVE`. The calendar date of the session's `scheduled_start` must fall inside the authorization's window, inclusive of both `start_date` and `end_date`, or it is refused with `ERR_VISIT_OUTSIDE_AUTHORIZATION_WINDOW`; `scheduled_end` is not itself tested against the window, so a session that begins on the window's last day and runs past midnight is accepted. And the session's `scheduled_units` must not exceed the authorization's current `units_remaining`, or it is refused with `ERR_UNITS_EXCEED_AUTHORIZATION`. Sessions may be scheduled in the future; the future-date prohibition of §2.5 does not apply to them.

**Provider schedule conflict.** A provider cannot be in two places at once, and travelling between places takes time. When a session is scheduled, the server compares its half-open interval against every other session for the same provider — reached through the authorization's `provider_id` — whose `visit_status` is `SCHEDULED` or `DELIVERED`. When the two sessions share the same `setting_code`, no buffer is applied and the comparison is the plain half-open one, so two same-setting sessions may touch exactly: 09:00–09:30 followed by 09:30–10:00 is legal. When the two sessions have different `setting_code` values, a travel buffer of 30 minutes is applied, and the sessions conflict when the new start falls before the existing end extended by the buffer **and** the existing start falls before the new end extended by the buffer. Concretely, a 09:30–10:00 session in a different setting conflicts with an existing 09:00–09:30 session, while a 10:00–10:30 session in a different setting does not. A conflict is refused with `ERR_PROVIDER_SCHEDULE_CONFLICT`. Sessions that were cancelled, marked as a no-show, or voided free their slot and are never considered.

**Makeup targeting.** When `makeup_for_visit_id` is supplied it must name a session whose `visit_status` is `CANCELLED_PROVIDER` and whose authorization belongs to the same service line as the new session; anything else — a family cancellation, a no-show, a delivered session, or a provider cancellation on a different line — is refused with `ERR_MAKEUP_TARGET_INVALID`. A cancellation may be made up only once: if any other session whose `visit_status` is neither `VOIDED` nor `CANCELLED_PROGRAM` already names the same `makeup_for_visit_id`, the request is refused with `ERR_MAKEUP_ALREADY_SCHEDULED`. And the repair must be prompt: the makeup session must be scheduled within 30 days of the cancelled session it repairs, the deadline being the calendar date of the target's `scheduled_start` plus 30 days, and a later attempt is refused with `ERR_MAKEUP_WINDOW_EXPIRED`.

**Documentation.** Only the delivering `Provider` documents a session, and only its own: the acting `X-User-ID` must equal the `provider_id` on the session's authorization, or the request is refused with `ERR_NOT_RESOURCE_OWNER`. The session must be in `SCHEDULED`, or the request is refused with `ERR_VISIT_NOT_SCHEDULED`. And a session may not be documented before it has begun: its `scheduled_start` must be at or before the logical clock instant, or the request is refused with `ERR_VISIT_NOT_YET_OCCURRED`. The payload carries the outcome as `visit_status` plus, for a delivered session, `actual_units`, `actual_start`, `actual_end` and a `session_note`. All four of those are declared optional and only `actual_units` is conditionally mandatory: a `DELIVERED` outcome that omits it is refused with `ERR_INVALID_REQUEST`, and that single shape check is deliberately evaluated after the ownership and `SCHEDULED` checks just described rather than at the payload rung of §2.8. `actual_start`, `actual_end` and `session_note` are recorded verbatim and are validated against nothing at all — not against each other, not against the scheduled interval, not against the 15-minute grid and not against the logical clock; only `actual_units` feeds any arithmetic.

Documenting `DELIVERED` is the productive path and touches five aggregates. The authorization's standing is **not** re-checked here: a session left `SCHEDULED` on an authorization that has since reached `EXHAUSTED` or `EXPIRED` may still be documented, and only the unit test below stops a delivery against it, since such an authorization has no `units_remaining`. `actual_units` must not exceed the authorization's `units_remaining`, or the request is refused with `ERR_UNITS_EXCEED_AUTHORIZATION`, and it must be an integer of at least 1 and at most the session's `scheduled_units`, or the request is refused with `ERR_ACTUAL_UNITS_EXCEED_SCHEDULED`; the authorization test is applied first, so a figure that breaks both reports `ERR_UNITS_EXCEED_AUTHORIZATION`, while a zero or negative `actual_units` — which the payload rung does not bound — surfaces as `ERR_ACTUAL_UNITS_EXCEED_SCHEDULED`. On success the session moves `SCHEDULED → DELIVERED`; `actual_units`, `actual_start`, `actual_end` and `session_note` are stored, together with `documented_by_user_id` capturing the acting provider identity and `documented_at_utc` recording the logical-clock instant at which the documentation was accepted, in the canonical three-fractional-digit form. A later void never clears either documentation field. The authorization's `units_consumed` rises by `actual_units` and its `units_remaining` is recomputed. The line's `units_delivered` rises by the same amount, and a line in `AUTHORIZED` advances `AUTHORIZED → IN_DELIVERY`. If the authorization's `units_consumed` now equals its `authorized_units` it advances `ACTIVE → EXHAUSTED`. And if the line's `units_delivered` has reached or passed its `planned_units_total` while its `makeup_owed_units` stands at exactly 0, the line advances `IN_DELIVERY → COMPLETED` and every authorization on it still in `ACTIVE` transitions to `EXHAUSTED`. A line carrying an outstanding makeup obligation is never completed, however many units it has delivered. The fifth aggregate is the family's, and §3.8 covers it: `family_share_cents` is computed, `billing_status` is set, and the selected cost-share row's running totals move.

The four non-delivery outcomes all set `actual_units` to 0, `family_share_cents` to 0 and `billing_status` to `CANCELLED_NO_CHARGE`, and they differ only in whether they create a makeup obligation. A provider-documented non-delivery stamps `documented_by_user_id` and `documented_at_utc` exactly as a delivery does; a session the server cancels through a cascade zeroes the same two money-and-unit fields and sets the same `billing_status`, but leaves both documentation fields null, because no provider documented it. `CANCELLED_PROVIDER` — the provider could not attend — moves the session `SCHEDULED → CANCELLED_PROVIDER`, consumes no authorization units, and increases the line's `makeup_owed_units` by the session's `scheduled_units`. `FAMILY_CANCELLED` moves the session `SCHEDULED → FAMILY_CANCELLED` and explicitly does **not** increase `makeup_owed_units`: only a provider's failure creates a makeup obligation. `NO_SHOW` moves the session `SCHEDULED → NO_SHOW`, likewise with no makeup obligation. `CANCELLED_PROGRAM` is not a provider-supplied outcome at all; the server writes it when an authorization is revoked, a plan is superseded or closed, or a case exits, and it carries no makeup obligation either.

**The makeup obligation.** A line's `makeup_owed_units` is the sum of `scheduled_units` across every session on the line whose `visit_status` is `CANCELLED_PROVIDER`, minus the sum of `actual_units` across every session on the line that was `DELIVERED` and carries a non-null `makeup_for_visit_id`, with the result floored at 0. A line is at risk when that owed figure is **strictly greater than** 4 units, so a line owing exactly 4 units is not at risk while a line owing 5 is. When a provider cancellation pushes the owed total past the threshold the line transitions `IN_DELIVERY → AT_RISK` (a line still in `AUTHORIZED` may make the same move), and the case's `service_gap_flag` is set to true. A case's `service_gap_flag` is true exactly when at least one service line belonging to **any** plan of the case is in `AT_RISK`, whatever that plan's own status: an at-risk line on a plan that has since moved to `AMENDMENT_PENDING`, or on one already `SUPERSEDED`, keeps the flag raised just as an at-risk line on the `ACTIVE` plan does.

The cycle closes when the makeup is delivered. Documenting a `DELIVERED` session that carries a non-null `makeup_for_visit_id` reduces the line's `makeup_owed_units` by that session's `actual_units`, floored at 0, and when the resulting owed figure is at most 4 units the line transitions `AT_RISK → IN_DELIVERY`. The case's `service_gap_flag` is then recomputed and becomes false when no other line on the case remains `AT_RISK`. A line may oscillate `IN_DELIVERY → AT_RISK → IN_DELIVERY` any number of times over the life of a plan. Note too that voiding a delivered makeup session stops it discharging the obligation, so the owed total rises back and the line can return to `AT_RISK`.

**Voiding.** A void is the system's only compensating action, reserved for a `ProgramAdmin` and carrying a `void_reason_code` of `DOCUMENTATION_ERROR`, `DUPLICATE_ENTRY` or `AUDIT_REVERSAL`. Only a session whose `visit_status` is `DELIVERED` may be voided; anything else is refused with `ERR_VISIT_NOT_VOIDABLE`. A void that would drive the selected cost-share row's `family_balance_cents` below 0 is refused with `ERR_LEDGER_WOULD_UNBALANCE`. On success the session moves `DELIVERED → VOIDED`, its `billing_status` moves to `REVERSED`, and the `void_reason_code` is stored. The authorization's `units_consumed` and the line's `units_delivered` are each decreased by the session's `actual_units`; the selected cost-share row's `month_accrued_cents`, `total_assessed_cents` and `family_balance_cents` are each decreased by the session's `family_share_cents`. An authorization sitting in `EXHAUSTED` returns `EXHAUSTED → ACTIVE`, provided the voided session had actually delivered more than 0 units and the authorization's window has not already ended relative to the logical clock date. The provider's `active_authorization_count` is recomputed on every void, whether or not the authorization's status actually moved. The row whose money is reversed is the very determination the session recorded at documentation time, not a determination re-selected for the session's month at void time: if that determination has since been superseded by a later one, or has left `PROVISIONAL`/`VERIFIED` standing altogether, the reversal still lands on it, so the accrual is always undone against the row that carried it. After the money is returned, the line's `units_committed`/`units_pool_remaining`, the line's `makeup_owed_units` and the case's `service_gap_flag` are recomputed in that order; a line that had already reached `COMPLETED` is never reopened by a void, so it stays `COMPLETED` even though its `units_delivered` has fallen back below its `planned_units_total`.

The two status dimensions on a session move independently, and that independence is deliberate. `visit_status` is the operational dimension — `SCHEDULED`, `DELIVERED`, `FAMILY_CANCELLED`, `NO_SHOW`, `CANCELLED_PROVIDER`, `CANCELLED_PROGRAM` or `VOIDED` — while `billing_status` is the fiscal one — `PENDING`, `ACCRUED`, `EXEMPT`, `CAPPED`, `REVERSED` or `CANCELLED_NO_CHARGE`. A void therefore pairs the operational move `DELIVERED → VOIDED` with a fiscal move to `REVERSED` from whichever of `ACCRUED`, `EXEMPT` or `CAPPED` the session was in. Reversing from `ACCRUED` moves real money: the cost-share row's `month_accrued_cents` and `family_balance_cents` both fall by the session's `family_share_cents`. Reversing from `EXEMPT` or from `CAPPED` moves only the unit counters, because in both of those cases `family_share_cents` was 0 and no cost-share money field ever changed.

### 3.8. Family Cost Participation: the Sliding Scale, Insurance, and the Family Ledger

Family cost participation is determined one month at a time by a `FiscalOfficer`. A determination is created against a case with the `referral_id`, the `effective_month` it governs written as a year and month, the `household_size` used for the federal poverty level threshold (an integer from 1 through 12), the family's `declared_annual_gross_income_cents` as a non-negative integer, an `insurance_use_consent` boolean, and — where the family consents — an `insurance_policy_id` naming the private policy. The new row is created in `PROVISIONAL`, and the acting officer's identifier is captured as `determined_by_user_id`, which is what makes the later segregation-of-duties check possible. Creation never enforces the policy-identifier obligation: a determination may be created with `insurance_use_consent` true and no `insurance_policy_id` at all, and it is accepted, because that obligation bites only at finalization and on the standalone consent capability below. Everything finalization, accrual and waiver will later write begins empty: `verified_annual_gross_income_cents`, `verification_date` and `waiver_reason_code` are null, and `total_assessed_cents`, `family_balance_cents`, `family_waived_cents` and `month_accrued_cents` all start at 0. A case may hold only one live determination per month: if another determination on the same case already governs the same `effective_month` in `PROVISIONAL` or `VERIFIED`, the request is refused with `ERR_COST_SHARE_DUPLICATE`. Determination is refused with `ERR_REFERRAL_STATE_INVALID` only when the case has reached one of the two terminal statuses `NOT_ELIGIBLE` or `EXITED`; every other case status permits a determination, `INTAKE` included, so a case need neither be eligible nor carry an active plan to be assessed.

Creating a determination for a **later** month supersedes the case's earlier live determinations. Any determination on the case in `PROVISIONAL` or `VERIFIED` whose `effective_month` is strictly earlier than the new row's transitions to `SUPERSEDED`; it stops being selected for new sessions, but the balances already accrued against it stay exactly where they are and are never migrated.

**The sliding scale.** The threshold comes first. A household's `fpl_threshold_cents` is the base of 1,580,000 cents — 15,800 dollars for a household of one — plus 555,000 cents, that is 5,550 dollars, for each household member beyond the first. `fpl_percent` is the family's income expressed as a percentage of that threshold: the income in cents multiplied by 100, divided by `fpl_threshold_cents`, rounded half up to one decimal place. Which income is used is the difference between the two variants, and is stated below.

The tier is then selected by `fpl_percent` using **inclusive** upper bounds, taking the first tier whose ceiling the percentage does not exceed. A percentage of at most 250.0 selects `tier_code` `TIER_0`, with a `coinsurance_rate` of 0.00 and a `monthly_cap_cents` of 0 — no family in this band pays anything. A percentage above 250.0 but at most 400.0 selects `TIER_1`, rate 0.05, monthly cap 12,000 cents, that is 120 dollars. Above 400.0 but at most 600.0 selects `TIER_2`, rate 0.10, cap 30,000 cents or 300 dollars. Anything above 600.0 selects `TIER_3`, rate 0.15, cap 60,000 cents or 600 dollars. A percentage of exactly 250.0 is therefore `TIER_0`, not `TIER_1`, and a percentage of exactly 600.0 is `TIER_2`, not `TIER_3`.

**The monthly fee.** The fee is built from the plan's chargeable service lines. The eligible set is the service lines belonging to the case's plan whose own status is `ACTIVE`, where each line's own `status` is `PLANNED`, `AUTHORIZED`, `IN_DELIVERY` or `AT_RISK`, whose `declined_by_family` is false, and whose `family_fee_exempt` is false — so discontinued and completed lines, family-declined lines, and service-coordination or evaluation lines are all excluded. Those lines are taken in ascending `created_at` order and each contributes its own rounded amount: the line's `frequency_per_month` multiplied by its `units_per_session` multiplied by its `unit_rate_cents` multiplied by the selected `coinsurance_rate`, rounded half up to whole cents. **The per-line rounding happens before the summation, never after** — this ordering is normative, and a sum-then-round implementation will disagree with the specification by a cent or more. The rounded line amounts are added together to give the raw assessed amount, and the raw amount is then capped at the tier's `monthly_cap_cents`, the capped figure being the lesser of the two. When the eligible set is empty the raw amount is 0 and the tier fields are still computed and stored.

**The provisional variant.** At determination time the computation runs from `declared_annual_gross_income_cents`, and the capped figure is stored as `assessed_monthly_fee_cents`. `effective_coinsurance_rate` is set to the selected tier's `coinsurance_rate`, and it is this field that per-session accrual reads. The provisional variant **never** applies the insurance offset, even when `insurance_use_consent` is true and a policy is on file: `insurance_offset_cents` stays at 0 and `final_monthly_fee_cents` stays null.

**The final variant.** Finalization is a separate `FiscalOfficer` action carrying the `verified_annual_gross_income_cents` established by income documentation and the `verification_date` on which it was verified. It requires the row to be in `PROVISIONAL`, refusing anything else with `ERR_COST_SHARE_NOT_PROVISIONAL`; requires the verified income to be non-negative and the verification date not to be after the logical clock date; and, when `insurance_use_consent` is true, requires `insurance_policy_id` to be present, refusing a consented row without a policy identifier with `ERR_INSURANCE_POLICY_REQUIRED`. The row moves `PROVISIONAL → VERIFIED`, storing `verified_annual_gross_income_cents` and `verification_date`.

The whole scale is then re-run from the verified income, which can move the family across a tier boundary in either direction: `fpl_percent`, `tier_code`, `coinsurance_rate`, `monthly_cap_cents` and `effective_coinsurance_rate` are all recomputed, the latter now carrying the verified tier's rate. `assessed_monthly_fee_cents` is **not** among the fields finalization recomputes: it is written once, at determination time, from the declared income, and finalization leaves the stored figure exactly as it was — even when the verified income moves the family to a different tier. The monthly fee is nevertheless re-derived from the verified tier in order to produce the two final-variant fields: the eligible chargeable lines described above are re-priced, as they stand at finalization, at the recomputed `coinsurance_rate` with the same per-line rounding before summation, and the raw total is capped at the recomputed `monthly_cap_cents`. It is that freshly capped figure — not the stored `assessed_monthly_fee_cents` — that the offset and the final fee below are computed from. The insurance offset is applied here and only here: when `insurance_use_consent` is true **and** an `insurance_policy_id` is on file, `insurance_offset_cents` is 60 percent of the capped monthly figure, rounded half up to whole cents; otherwise it is 0. `final_monthly_fee_cents` is then the capped figure minus `insurance_offset_cents`. The tier is never re-derived from the post-offset amount — the offset reduces what the family owes, not the band the family sits in.

Finalization deliberately does **not** re-price history. Sessions already accrued keep the share they accrued: `total_assessed_cents`, `family_balance_cents` and `month_accrued_cents` all retain their pre-finalization values, which is precisely why the ledger identity of §2.10 continues to hold across the transition. A finalization that would break that identity is refused with `ERR_LEDGER_WOULD_UNBALANCE`.

**Insurance consent on its own.** A family may record or withdraw consent to bill private insurance without waiting for finalization. That capability takes `insurance_use_consent` and an optional `insurance_policy_id`, and updates both on the determination while it is still in `PROVISIONAL` — a row in any other status is refused with `ERR_COST_SHARE_NOT_PROVISIONAL`. Both fields are written from the request rather than merged into what was there, so an omitted `insurance_policy_id` is stored as null and withdrawing consent without naming a policy therefore also clears any identifier previously on file. Setting consent to true without supplying a policy identifier is refused with `ERR_INSURANCE_POLICY_REQUIRED`. No fee is recomputed by this capability: the offset belongs to the final variant alone.

**Per-session accrual.** When a session is documented as `DELIVERED`, the server must decide which determination governs it and how much the family owes for it. Selection first gathers every determination on the case whose `status` is `PROVISIONAL` or `VERIFIED` and whose `effective_month` is at or before the calendar month of the session's `scheduled_start` — that month being the `YYYY-MM` prefix of the instant as the service stores it, in the canonical UTC form of §2.5, so a `scheduled_start` submitted with a numeric offset is bucketed by its converted UTC month rather than by the month it appeared to name; `SUPERSEDED` and `CLOSED` rows are never candidates. If that candidate set is empty, the session's `family_share_cents` is 0 and its `billing_status` is set to `EXEMPT`. Otherwise the server selects the candidate with the latest `effective_month`, breaking a tie by the latest `created_at`.

With a determination selected, two conditions still yield an exempt session: the delivering line's `family_fee_exempt` being true, or the selected determination's `effective_coinsurance_rate` being exactly 0.00. In either case `family_share_cents` is 0, `billing_status` is `EXEMPT`, and no field on the determination changes at all. Otherwise the raw share is the session's `actual_units` multiplied by the authorization's pinned `unit_rate_cents` multiplied by the determination's `effective_coinsurance_rate`, rounded half up to whole cents on that single multiplication.

The monthly cap is then applied, after rounding. The cap remainder is the determination's `monthly_cap_cents` minus its `month_accrued_cents`. `month_accrued_cents` is a running total belonging to the determination and is never reset by the arrival of a new calendar month: a determination governs every month from its `effective_month` onward until a later determination supersedes it, and its cap remainder keeps shrinking across all of those months instead of replenishing on the first of each. If that remainder is zero or below, the session's `family_share_cents` is 0, its `billing_status` is `CAPPED`, and `month_accrued_cents` is left unchanged — the family has already paid its ceiling for the month and further sessions cost them nothing. Otherwise `family_share_cents` is the lesser of the raw share and the cap remainder, and `billing_status` is `ACCRUED` when the full raw share was charged or `CAPPED` when the remainder truncated it. Whatever is charged is added to the determination's `month_accrued_cents`, to its `total_assessed_cents` and to its `family_balance_cents`.

The ledger view of the same numbers is worth stating separately, because it is the definition the invariant checks against. A determination's `family_balance_cents` equals the sum of `family_share_cents` over the case's sessions whose `billing_status` is `ACCRUED` or `CAPPED` and whose `visit_status` is `DELIVERED`, minus that determination's `family_waived_cents`. Sessions in `REVERSED`, `EXEMPT`, `PENDING` or `CANCELLED_NO_CHARGE` contribute nothing, and only the determination selected for a session's month carries that session's accrual. The three totals are nevertheless maintained incrementally rather than rebuilt from the sessions: documenting a delivery adds the charged share to `month_accrued_cents`, `total_assessed_cents` and `family_balance_cents` alike, a void subtracts it from the same three, and a waiver moves cents from balance to waived. Finalization changes none of them. What happens on all four of session documentation, session void, finalization and waiver is that the identity above is re-checked; the check is what refuses a void, a waiver or a finalization with `ERR_LEDGER_WOULD_UNBALANCE`, and on documentation it is a guard that an accrual can never trip, since accrual only ever adds the same non-negative amount to the assessed total and the balance together.

**Waivers.** A waiver reduces what the family owes without pretending the service was never assessed. A `FiscalOfficer` supplies `waive_amount_cents` and a `waiver_reason_code` of `HARDSHIP`, `ADMIN_ERROR` or `PROGRAM_POLICY`. The amount must be at least 1 cent and at most the determination's current `family_balance_cents`, or the request is refused with `ERR_WAIVE_EXCEEDS_BALANCE`. Waiving is permitted while the determination is in `PROVISIONAL` or `VERIFIED`, and refused with `ERR_COST_SHARE_NOT_PROVISIONAL` in any other status. And the officer recorded in `determined_by_user_id` may not be the officer waiving: that attempt is refused with `ERR_SEGREGATION_OF_DUTIES`. On success `family_waived_cents` rises by the waived amount, `family_balance_cents` falls by the same amount, the `waiver_reason_code` is stored, and `total_assessed_cents` is deliberately left untouched — which is exactly how the identity `total_assessed_cents` equals `family_balance_cents` plus `family_waived_cents` survives the waiver. A waiver that would break it is refused with `ERR_LEDGER_WOULD_UNBALANCE`. A determination may be waived repeatedly for as long as a balance remains, each waiver moving a further slice of what is left and overwriting `waiver_reason_code` with the reason given for the most recent one: the field records the latest waiver rather than a history of them.

`SUPERSEDED` and `CLOSED` are the terminal determination statuses. When a case exits, every determination on it in `PROVISIONAL` or `VERIFIED` transitions to `CLOSED`, after which no further accrual and no further waiver is permitted against that row.

### 3.9. Monthly Contact, Transition to Preschool, and Case Closure

**The monthly contact requirement.** A case in active services must be touched by its coordinator at least once each calendar month. The assigned `ServiceCoordinator` — and only the assigned coordinator, since the case's `coordinator_id` must equal the acting `X-User-ID` or the request is refused with `ERR_NOT_RESOURCE_OWNER` — logs each contact against the case with a `contact_date`, a `contact_method`, a `contact_type` and a narrative `summary`. The case identifier is taken from the request path and stored as `referral_id`; the contact's `contact_date` must not be after the logical clock date. The server derives `contact_month` as the year-and-month prefix of `contact_date`, and derives `qualifies_for_monthly_requirement` as true exactly when the `contact_method` is `HOME_VISIT`, `PHONE` or `VIDEO`. The five available methods are `HOME_VISIT`, `PHONE`, `VIDEO`, `EMAIL` and `LETTER`, and the last two are logged faithfully but never satisfy the requirement. `contact_type` records the purpose of the contact as `MONTHLY_CHECK_IN`, `SERVICE_REVIEW`, `CRISIS` or `TRANSITION_PLANNING`, and does not affect whether the contact qualifies. Logging is refused with `ERR_REFERRAL_STATE_INVALID` only when the case has reached one of the two terminal statuses `NOT_ELIGIBLE` or `EXITED`; every other case status accepts a contact entry, even though only a case in `ACTIVE_SERVICES` has a monthly requirement for the entry to satisfy. As stated in §2.4, a contact entry is never mutated once written.

Each logged contact refreshes two derived fields on the case. `last_qualifying_contact_date` is the latest `contact_date` among the case's contacts whose `qualifies_for_monthly_requirement` is true. `monthly_contact_status` is `NOT_APPLICABLE` whenever the case is not in `ACTIVE_SERVICES`. For a case that is in `ACTIVE_SERVICES`, the server looks for qualifying contacts whose `contact_date` falls in the same calendar month as the logical clock date: if at least one exists the status is `COMPLIANT`; if none exists and the logical clock's day of month is 20 or earlier the status is `DUE`, giving the coordinator the rest of a grace period to act; and if none exists after the twentieth of the month the status is `DELINQUENT`. A contact in a prior month never satisfies the current month. This verdict is recomputed when a contact is logged, when the logical clock is advanced, and on every referral status transition.

**Opening transition planning.** As a child approaches three, the case must plan the handoff to preschool services. The assigned `ServiceCoordinator` opens a transition plan against the case's plan with the `ifsp_id`, the `target_conference_date` on which the transition conference is intended to happen, and optionally the `conference_held_date` and a `transition_steps_count` of documented transition steps and services (an integer from 0 through 20, defaulting to 0). The new plan is created in `DRAFT` with every notification field left null: no `lea_code`, no `notification_date`, `family_opt_out` false, no `opt_out_signed_date`, no `notification_lead_days`, no `notification_compliance`.

Two gates apply. The window must be open: the whole number of days from the logical clock date to the child's `third_birthday_date` must be at most 270 — the final nine months before the child ages out — and an earlier attempt is refused with `ERR_TRANSITION_WINDOW_NOT_OPEN`. And a plan may carry at most one transition plan: if the plan already has one in `DRAFT`, `NOTIFIED`, `OPT_OUT` or `COMPLETE`, the request is refused with `ERR_TRANSITION_PLAN_DUPLICATE`. A transition plan that was `CANCELLED` because its plan was superseded or withdrawn does not block a fresh one against the successor plan. The parent plan must itself be in `ACTIVE`, or the request is refused with `ERR_IFSP_STATE_INVALID`, and the acting coordinator must own the case.

**Notifying the local education agency, or waiving it.** The notification is the statutory obligation the whole transition plan exists to discharge, and it is recorded by the assigned coordinator with a `notification_date`, a `family_opt_out` boolean, and — depending on the branch — either a `lea_code` naming the district notified or an `opt_out_signed_date` recording when the family signed the declination. `lea_code`, where it is supplied, must be a non-empty uppercase token carrying no whitespace. The either/or pairing itself is a payload-shape rule of the kind §2.8 places at rung 3, not a business rule: whichever branch `family_opt_out` names, supplying the wrong combination — a missing `lea_code` or a stray `opt_out_signed_date` on a notification, a missing `opt_out_signed_date` or a stray `lea_code` on an opt-out — is refused with `ERR_INVALID_REQUEST`, and the check runs before the transition plan is looked up at all. The transition plan must be in `DRAFT`, or the request is refused with `ERR_TRANSITION_PLAN_STATE_INVALID`; the parent plan's own status is not re-examined here, so a transition plan opened against an `ACTIVE` plan that has since moved to `AMENDMENT_PENDING` because a service line was added may still record its notification.

When `family_opt_out` is false the plan moves `DRAFT → NOTIFIED`. That branch requires the transition work to have actually happened: `conference_held_date` must be present and `transition_steps_count` must be at least 1, and a plan missing either is refused with `ERR_TRANSITION_PLAN_INCOMPLETE`. It also requires `lea_code` to be present and `opt_out_signed_date` to be absent. On success `lea_code`, `notification_date`, `notification_lead_days` and `notification_compliance` are all stored.

When `family_opt_out` is true the plan moves `DRAFT → OPT_OUT` instead. That branch requires `opt_out_signed_date` to be present and `lea_code` to be absent — a family that declined notification cannot also have a district recorded as notified. `notification_compliance` is set to `WAIVED_OPT_OUT`, and `notification_lead_days` is still computed and stored so that the audit record shows how close to the deadline the family's decision landed.

**Grading the notification.** `notification_lead_days` is the whole number of days from `notification_date` to the child's `third_birthday_date`. A negative lead — a notification dated after the third birthday — is refused with `ERR_NOTIFICATION_AFTER_THIRD_BIRTHDAY`. Given a non-negative lead, the verdict follows in this order: an opted-out plan is `WAIVED_OPT_OUT`; otherwise a lead of more than 270 days is `EARLY`; otherwise a lead of at least 90 days is `TIMELY`; otherwise the notification is `LATE`. Both boundaries are inclusive on the timely side: a lead of exactly 90 days is `TIMELY` while 89 days is `LATE`, and a lead of exactly 270 days is `TIMELY` while 271 days is `EARLY`.

**Exiting the case.** Exit is the assigned coordinator's act, and the case's `coordinator_id` must equal the acting `X-User-ID`. The payload carries the `exit_date`, an `exit_reason` of `REACHED_AGE_THREE`, `FAMILY_WITHDREW`, `MOVED_OUT_OF_STATE` or `NO_LONGER_ELIGIBLE`, and optionally the three exit outcome ratings `exit_rating_social`, `exit_rating_knowledge` and `exit_rating_needs`. The `exit_date` must not be after the logical clock date, and when services had started it must be on or after `services_start_date`. Exit increments `Referral.version` by 1 on every path.

Exiting from `ACTIVE_SERVICES` is the demanding case. All three exit ratings are required and each must be an integer from 1 through 7, and when the `exit_reason` is `REACHED_AGE_THREE` the case must additionally carry a transition plan on its `ACTIVE` plan whose status is `NOTIFIED` or `OPT_OUT` — a child cannot age out of the program without the district having been notified or the family having formally declined. A violation of either requirement is refused with `ERR_EXIT_OUTCOMES_REQUIRED`. The case moves `ACTIVE_SERVICES → EXITED`, storing `exit_date`, `exit_reason` and the three exit ratings, and recomputing `service_duration_days`.

Exiting before services ever started is the lighter case, and it is available from `EVALUATION_PENDING`, `ELIGIBILITY_DETERMINED` and `IFSP_PENDING` with an `exit_reason` of `FAMILY_WITHDREW` or `MOVED_OUT_OF_STATE`; naming `REACHED_AGE_THREE` or `NO_LONGER_ELIGIBLE` from one of those three statuses is refused with `ERR_REFERRAL_STATE_INVALID`, as is any attempt to exit a case in `INTAKE`, `NOT_ELIGIBLE` or `EXITED`. Exit ratings are not required on any of those three edges, because there is no measured service period to compare, and the three progress categories remain null; ratings supplied anyway are still stored on the case, but no progress category is derived from them and `service_duration_days` stays 0. On the `EVALUATION_PENDING → EXITED` and `ELIGIBILITY_DETERMINED → EXITED` edges every assessment still in `SCHEDULED` transitions to `CANCELLED`; on all three edges the case's `case_weight_points` is set to 0 and the coordinator's aggregates are recomputed; and on the `IFSP_PENDING → EXITED` edge every plan on the case in `DRAFT` or `PENDING_CONSENT` additionally transitions to `WITHDRAWN` with each of its service lines not already `DISCONTINUED` transitioning to `DISCONTINUED`, that plan's line and unit counts recomputed, and any transition plan still in `DRAFT` against it transitioning to `CANCELLED`.

**Child outcome progress categories.** `service_duration_days` is the whole number of days from `services_start_date` to `exit_date`, and it is 0 for as long as `services_start_date` is null. If a case received services for fewer than 180 days, no meaningful comparison is possible and all three of `progress_category_social`, `progress_category_knowledge` and `progress_category_needs` are recorded as `NOT_COMPARABLE`, whatever the ratings say. Otherwise each of the three areas is graded independently by comparing that area's entry rating with its exit rating, using 6 as the age-expected level. When the exit rating is lower than the entry rating the category is `a`, a regression. When the exit rating equals the entry rating and is below 6, the category is `b`: no progress, still below age level. When the exit rating is higher than the entry rating but still below 6, the category is `c`: progress made, still below age level. When the exit rating is at least 6 while the entry rating was below 6, the category is `d`: the child reached the age-expected level. In every remaining case — which is to say when both ratings are at least 6 — the category is `e`, the child maintained the age-expected level. A rating of exactly 6 counts as age-expected. The comparison uses `entry_rating_social` against `exit_rating_social`, `entry_rating_knowledge` against `exit_rating_knowledge`, and `entry_rating_needs` against `exit_rating_needs`.

**The closure cascade.** Exit from `ACTIVE_SERVICES` is the deepest cascade in the system, and it runs to completion inside the exit request. The case's plan in `ACTIVE` or `AMENDMENT_PENDING` transitions to `CLOSED`. Every service line on that closed plan that is not already `DISCONTINUED` transitions to `DISCONTINUED`, which means the four live statuses `PLANNED`, `AUTHORIZED`, `IN_DELIVERY` and `AT_RISK` and equally a line that had reached `COMPLETED`. Every provider authorization on those discontinued lines whose status is `ACTIVE`, `EXHAUSTED` or `SUSPENDED` transitions to `REVOKED`, each with `units_released` set to its `units_remaining` and `revocation_reason_code` recorded as `CASE_EXITED`. Each affected line then has `units_committed` and `units_pool_remaining` recomputed, restoring the unit-pool identity, and the closed plan's `service_line_count` and `non_natural_setting_line_count` are recomputed down to 0. Every session still in `SCHEDULED` on those authorizations transitions to `CANCELLED_PROGRAM` with `billing_status` `CANCELLED_NO_CHARGE`, and its `actual_units` and `family_share_cents` are set to 0. The case's transition plan, if it is in `NOTIFIED` or `OPT_OUT`, transitions to `COMPLETE` and is frozen as the audit record of the transition; a transition plan still in `DRAFT` at exit transitions instead to `CANCELLED`, because the transition it was preparing will never happen, and a transition plan in any other status is left untouched. Every cost-share determination on the case in `PROVISIONAL` or `VERIFIED` transitions to `CLOSED`. And finally the case's own derived state is cleared: `case_weight_points` is set to 0, the coordinator's `weighted_caseload_points`, `active_case_count` and `utilization_ratio` are recomputed without it, `service_gap_flag` is set to false, and `monthly_contact_status` returns to `NOT_APPLICABLE`. `NOT_ELIGIBLE` and `EXITED` are the two terminal case statuses, and neither accepts any further write.

## 4. API Endpoint Specifications

The API is served under the `/ei` prefix, with the single exception of the clock control endpoint described in §2.5. Every endpoint requires the `X-User-ID` and `X-User-Role` headers of §2.1. Creation endpoints return HTTP 201 with the newly created resource in `data`; every other successful operation returns HTTP 200 with the affected resource, the computed read structure, or the requested collection. All error responses use the envelope of §2.2 and carry one of the error identifiers catalogued in §5. The `Authorized Role(s)` column is exhaustive: a syntactically valid request from any role not listed is refused with `ERR_ROLE_NOT_PERMITTED`. ## 5. Error Handling

Every failed request returns the error envelope of §2.2 with the `error_id` set to one of the identifiers below and the documented HTTP status code. Where several rules would fail one request, the identifier reported is the one selected by the validation order of §2.8. Three further identifiers sit outside the business catalogue and answer requests that never reach an endpoint at all, still in the same envelope: `ERR_NOT_FOUND` (404) for a path that matches no declared route, `ERR_METHOD_NOT_ALLOWED` (405) for a declared path addressed with the wrong HTTP method, and `ERR_INTERNAL` (500) for an unanticipated server fault.
