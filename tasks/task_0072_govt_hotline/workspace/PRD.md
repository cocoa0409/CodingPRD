# Government Hotline API — Product Requirements Document

## 1. Introduction

A municipal government hotline receives thousands of citizen calls every business day — complaints, requests for service, reports of public-safety issues, and questions that span dozens of categories from road repair to noise enforcement. The work that follows a call is rarely owned by a single office: a noisy construction complaint may belong jointly to environmental enforcement and the local district authority, a flooded roadway involves drainage and traffic, and a hazardous-materials report touches three or four agencies at once. The system described here is the back-office record of every such call, from the moment a hotline operator picks up the phone to the moment a satisfaction survey is recorded and the case is finally closed.

Three concerns dominate the design. First, **routing must be unambiguous**: every case is mapped to exactly one lead department and zero or more supporting departments, derived from a stable (category, sub-category) routing table and a geographic-jurisdiction overlay. Second, **time limits must be auditable**: statutory and committed deadlines, business-hours arithmetic, clarification pauses, warning escalations, and breach reporting must all reconcile under a single deterministic model. Third, **citizen satisfaction must be measured and acted upon**: every resolved case receives a follow-up survey through an appropriate channel, dissatisfied callers can trigger a bounded reopening window, and aggregate satisfaction informs department-level and handler-level performance reporting.

This document defines the API contract that ties those concerns together — the resource shapes, the lifecycle transitions, the calculations, the validations, the role-based permissions, and the error catalogue that downstream implementations and test suites must agree upon byte-for-byte.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-Role`, naming the role making the call, and `X-User-ID`, naming the specific actor. Either header missing — or `X-User-Role` carrying a string that is not one of the recognised roles — is rejected with `ERR_AUTH_MISSING` (401). A recognised role acting on an endpoint outside its permitted set is rejected with `ERR_FORBIDDEN` (403).

The recognised roles are exactly six: `PlatformAdmin`, `HotlineOperator`, `Dispatcher`, `DepartmentHandler`, `Supervisor`, and `SurveyAgent`. `PlatformAdmin` is the configuration role — it registers departments, handlers, and category rules, and operates the test-harness clock and sweep endpoints. `HotlineOperator` is the front-line role that registers calls and may manually trigger satisfaction surveys or reopen a follow-up case. `Dispatcher` is the routing role that classifies, dispatches, rejects, reassigns, and closes cases. `DepartmentHandler` is the worker inside a department who accepts assignments, submits opinions, pauses and resumes the clock, and writes the final resolution. `Supervisor` watches supervision tasks, acknowledges and closes them, and reads cross-department statistics. `SurveyAgent` records caller responses to dispatched satisfaction surveys.

When `X-User-Role` is `DepartmentHandler`, `X-User-ID` is the `id` of the acting `Handler`; ownership checks on any resource that references a `Handler` (notably whether the caller is the LEAD assignment's `handler_id` when resuming or resolving) compare the resource's foreign-key field to `X-User-ID`. When `X-User-Role` is `PlatformAdmin`, `HotlineOperator`, `Dispatcher`, `Supervisor`, or `SurveyAgent`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it on `AuditLog.actor_id` (and on `AuditLog.actor_role`) when the corresponding action is committed but does not compare it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All list endpoints accept `limit` and `offset` query parameters. `limit` defaults to 10, has a minimum of 1, and a maximum of 100; values outside this range fail field validation. `offset` defaults to 0 and has no upper bound apart from the integer domain. List endpoints sort their results by `created_at` ascending unless explicitly overridden in §3. The `meta` block on a list response always carries `limit`, `offset`, `total_count`, and `has_more`, where `has_more` is true precisely when `offset + limit < total_count`.

### 2.4. Common Resource Properties and Optimistic Concurrency

Every persisted resource carries a server-minted `id` that is a UUID string with no type prefix. Most resources additionally carry `created_at`, `updated_at`, and `version`, where the two timestamps are ISO 8601 UTC strings with three fractional digits and `version` is a non-negative integer that starts at 1 on creation and increments by 1 on every mutation. The exceptions are `ClarificationPause`, `AuditLog`, and `SyncEvent`: these three are append-only log-style records and therefore expose only `id` and `created_at` — both `updated_at` and `version` are absent.

Optimistic concurrency control applies to every `PATCH` endpoint. A request body may optionally include a `version` field; when supplied, the server compares it to the current resource's `version` and rejects a mismatch with `ERR_VERSION_CONFLICT` (409). When `version` is omitted from the body, the check is skipped and the update proceeds against whatever the current state happens to be.

### 2.5. Nested Resources and Path Validation

Several endpoints sit beneath multi-segment paths — for instance, an assignment is addressed under `/work-orders/{id}/assignments/{assignment_id}`. Path segments are validated left-to-right: a missing `WorkOrder` yields `ERR_WORK_ORDER_NOT_FOUND` (404) before any check on the trailing segments runs, and an assignment that exists but belongs to a different work order than the one in the path yields `ERR_ASSIGNMENT_NOT_FOUND` (404) — the latter is also the error when the assignment id itself is unknown. A missing `Department`, `Handler`, `SatisfactionSurvey`, `SupervisionTask`, or `CategoryRule` referenced directly through a top-level path segment yields the generic `ERR_RESOURCE_NOT_FOUND` (404). Body-referenced foreign keys (such as `department_id`, `handler_id`, `target_department_id`, or a `category_code` / `sub_category_code` pair) that fail to resolve yield `ERR_REFERENCE_NOT_FOUND` (422).

### 2.6. Validation Ordering

When more than one validation could fire on the same request, they are evaluated in a fixed priority order so that the returned `error_id` is deterministic. Authentication runs first — the `X-User-Role` header presence and recognition is priority 1, the `X-User-ID` presence is priority 2, and the role-vs-endpoint RBAC check is priority 3, all surfacing as authentication or forbidden errors before any payload is inspected. Existence checks come next, in the order: path-referenced work order, path-referenced assignment scoped to its parent work order, other path-referenced entities under their generic `ERR_RESOURCE_NOT_FOUND`, then body-referenced foreign keys under `ERR_REFERENCE_NOT_FOUND`. State checks follow: the work-order state-permission check is priority 8 (and surfaces as `ERR_INVALID_STATE`), the assignment-state check is priority 9 (surfacing as `ERR_ASSIGNMENT_NOT_PENDING`), and the symmetrical pause/resume preconditions are priorities 10 and 11, yielding `ERR_NOT_PAUSED` and `ERR_ALREADY_PAUSED` respectively. Business-safety checks for anonymous PII (priority 12, `ERR_ANONYMOUS_PII_LEAK`) and survey-channel forbidden (priority 13, `ERR_SURVEY_CHANNEL_FORBIDDEN`) run after state. Business-referential checks for jurisdiction at classify time (priority 14, `ERR_JURISDICTION_NO_DEPARTMENT`) and at reassign time (priority 15, `ERR_JURISDICTION_MISMATCH`) come next. Business-constraint checks then run in this order: opinions-incomplete at resolve (priority 16, `ERR_OPINIONS_INCOMPLETE`), disagreement-unresolved at resolve (priority 17, `ERR_DISAGREEMENT_UNRESOLVED`), supervision-open at close (priority 18, `ERR_SUPERVISION_OPEN`), reopen-window expiry (priority 19, `ERR_REOPEN_WINDOW_EXPIRED`), survey expiry (priority 20, `ERR_SURVEY_EXPIRED`), category-pair existence (priority 21, `ERR_CATEGORY_UNKNOWN`), the OCC check on PATCH (priority 22, `ERR_VERSION_CONFLICT`), and finally field-shape validation (priority 23, `ERR_VALIDATION`) and duplicate-call detection (priority 24, `ERR_DUPLICATE_LINKED`). This ordering is the contract: a request that violates several checks at once receives the `error_id` corresponding to the lowest priority number above.

### 2.7. Business-Hours Time and the Clarification-Pause Clock

Time-limit arithmetic is the system's most consequential domain rule and deserves its own contract. Business days are Monday through Friday inclusive; the business day runs from 09:00 to 17:00 UTC, yielding eight business hours per day with no overnight or weekend window. When a deadline is computed as "registered time plus N business hours", the implementation walks N business hours forward from the base instant, skipping any portion of wall-clock time that falls outside a business interval. Statutory time-limit hours and committed time-limit hours, defined on a `CategoryRule`, are integers in the closed range 1 to 1440, and the committed value must be less than or equal to the statutory value (so the committed deadline always lands at or before the statutory deadline for the same case). Clarification pauses are different in kind: a paused interval is added back to both deadlines as raw wall-clock seconds — not converted to business hours — when the pause resumes, because the explicit intent is that any clarification time-out extends the wall-clock deadline by the exact wall-clock duration of the pause.

### 2.8. Precision and Rounding

The satisfaction index is rounded half-up to two decimal places, where the division is performed at full float precision and rounding is applied once at the end (never per-row before averaging). The two breach-rate variants are produced by computing a 4-decimal fraction, multiplying by 100, and rounding the resulting percentage half-up to two decimal places. Difficulty scores are integer-valued in the closed range 1 to 10 with a pinned round-half-up step that is a no-op on integer inputs but is part of the contract for symmetry with the other calculations. All `pause_accumulated_seconds`, `ClarificationPause.duration_seconds`, and other duration quantities are whole seconds; the pause invariant tolerates exactly zero deviation.

### 2.9. Auditing and Downstream Event Synchronization

Every state-changing action writes an `AuditLog` row whose `action` is one of a fixed catalogue — `REGISTER`, `CLASSIFY`, `DISPATCH`, `ACCEPT`, `REJECT`, `REASSIGN`, `OPINION_SUBMIT`, `ESCALATE`, `PAUSE`, `RESUME`, `RESOLVE`, `SURVEY_DISPATCH`, `SURVEY_RESPOND`, `REOPEN`, `CLOSE`, `SUPERVISION_CREATE`, `SUPERVISION_ACK`, and `EVENT_SYNC`. Each audit row stamps the acting `actor_role` and `actor_id` (taken from the request headers), the affected `work_order_id` when one is in scope, a structured `payload` snapshot of the inputs and the resulting state diff, and an `occurred_at` server timestamp. Separately, a fixed set of state transitions emits a `SyncEvent` to three downstream platforms — `IM`, `GOVT_AFFAIRS`, and `INTER_DEPT` — namely the events `DISPATCHED`, `RESOLVED`, `CLOSED`, `REOPENED`, and `ESCALATED`. Each `SyncEvent` carries a `target_platform`, an `event_type`, a `payload` snapshot, an `emitted_at` timestamp, and a `delivery_status` of `PENDING`, `DELIVERED`, or `FAILED`. Audit and sync queries support filtering: `/audit-logs` accepts `work_order_id` and `action` filters, while `/sync-events` accepts `work_order_id`, `event_type`, `target_platform`, and `delivery_status` filters.

### 2.10. Test-Harness Capabilities

Two test-only endpoints are reserved for `PlatformAdmin`. A clock-advance capability accepts a `seconds` body field and walks the server's logical clock forward by that many seconds — every deadline check, every business-hour arithmetic, every warning-state recompute references this clock. A sweep capability iterates the time-gated work that would otherwise be performed by a background job: surveys past their expiry move from `DISPATCHED` to `EXPIRED`; supervision tasks whose inactivity exceeds the reminder interval escalate (subject to the escalation cap); and every work order's `warning_state` is recomputed. Both capabilities are reachable only by `PlatformAdmin`.

## 3. Business Logic & Workflows

### 3.1. Configuring the Routing World — Departments, Handlers, and Category Rules

Before any call can be processed the platform must be seeded. A `Department` is created with a `name`, a stable kebab-case `code` (matching the pattern of a leading lowercase letter followed by lowercase letters, digits, and hyphens, total length 2 to 40 characters, unique across the table), a list of `jurisdiction_codes` (each matching the pattern of a literal `J` followed by exactly four digits; the list may be empty for citywide departments and is deduplicated), and a list of `category_codes` it is responsible for (each value referencing an existing `CategoryRule.category_code`, deduplicated). The department's `status` defaults to `ACTIVE`; the alternative value is `SUSPENDED`, which removes the department from any future dispatch consideration. A computed `pending_work_count` tracks how many assignments the department currently holds in `DISPATCHED` or `ACCEPTED`; it starts at zero and is maintained by the work-order side effects described below. `name` is non-empty with length between 1 and 120 inclusive.

A `Handler` is bound to a department at creation time through the `department_id` field; the target department must exist and have `status` equal to `ACTIVE`. The handler's `full_name` is non-empty with length between 1 and 80 inclusive. A handler's own `status` is one of `ACTIVE`, `ON_LEAVE`, or `DISABLED`; only `ACTIVE` handlers are eligible to accept assignments. The computed `open_assignment_count` is the number of `DepartmentAssignment` rows where this handler is assigned and whose `stage_status` is not terminal — it starts at 0 and is maintained by accept, opinion-submit, and resolve flows. Handler status updates are permitted via PATCH and may also pass a `version` for the optimistic-concurrency check.

A `CategoryRule` ties a (`category_code`, `sub_category_code`) pair — both uppercase identifiers matching a leading uppercase letter followed by uppercase letters, digits, and underscores, total length 2 to 30 characters — to a `lead_department_code` and a list of `supporting_department_codes`. The pair is unique. The lead code must reference a department whose `status` is `ACTIVE` at creation time. Supporting codes must each reference an existing department, must not include the lead code, and are deduplicated. The rule also pins `statutory_time_limit_hours` and `committed_time_limit_hours` (each an integer in the closed range 1 to 1440, with committed less than or equal to statutory) and an optional `difficulty_base` that defaults to 1 and is an integer in the closed range 1 to 5. Listing category rules supports a `category_code` filter alongside `limit` and `offset`. Listing departments supports `status` and `jurisdiction_code` filters.

### 3.2. Receiving a Call — Registration, Anonymity, and Duplicate Detection

A hotline operator registers an incoming call by submitting `caller_name`, `caller_phone`, `anonymous`, `jurisdiction_code`, `category_code`, `sub_category_code`, `content_text`, optionally `audio_url`, and optionally `urgency`. `anonymous` defaults to false. When `anonymous` is true, both `caller_name` and `caller_phone` must be omitted or null; when `anonymous` is false, `caller_phone` is required. Either violation is rejected with `ERR_ANONYMOUS_PII_LEAK` (422). `caller_name` is between 1 and 80 characters when present. `caller_phone` matches a pattern of digits, the plus sign, and hyphens, of total length 6 to 20, when present. `jurisdiction_code` matches the J-plus-four-digits pattern. `content_text` is between 1 and 4000 characters. `audio_url` is between 0 and 500 characters and is either an http(s) URL or the empty string. `urgency` is one of `LOW`, `NORMAL`, `HIGH`, or `CRITICAL` and defaults to `NORMAL` when omitted.

The (`category_code`, `sub_category_code`) pair must together resolve to an existing `CategoryRule`; otherwise the registration is rejected with `ERR_CATEGORY_UNKNOWN` (422). Provided the pair resolves and the anonymity rule is satisfied, the system creates the work order in state `REGISTERED`, server-stamps `registered_at` (which equals `created_at` to the millisecond), and immediately evaluates the difficulty calculation in its registration form: an urgency weight of 0 for `LOW`, 1 for `NORMAL`, 3 for `HIGH`, and 5 for `CRITICAL`, plus the `CategoryRule.difficulty_base` for the matched pair (defaulting to 1 if for any reason the pair fails to match, though it will already have been rejected by the category check above), plus a joint factor of 0 (because at registration the case has not yet been classified and `joint_handling` therefore defaults to false). The intermediate sum is clamped to the closed range 1 to 10 by taking the larger of 1 and the smaller of 10 and the sum, then rounded half-up to the nearest integer; on integer-valued inputs the rounding step is a no-op but remains part of the contract. The resulting integer is written to `difficulty_score`. `classification_mode` is initialised to `PENDING`. `lead_department_id`, `supporting_department_ids`, `joint_handling`, `statutory_deadline_at`, `committed_deadline_at`, `duplicate_of_id`, and `closed_at` are all left null or empty pending later transitions. `pause_accumulated_seconds` starts at 0, `pause_started_at` is null, `warning_state` is `NONE`, and `priority_flag` is recomputed (it is true precisely when the urgency is at least `HIGH` or the difficulty score is at least 7). An `AuditLog` row with action `REGISTER` is written.

Duplicate-call detection runs against the just-registered row before the operator's response is returned. If a non-terminal work order already exists with the same `caller_phone` (or, when `anonymous` is true, the same `content_text` hash) and the same `category_code`, and was registered within the last 600 seconds (the duplicate-detection window), the new row is forcibly linked: its `duplicate_of_id` is set to the matching prior work order's id, its `content_text` is appended to the prior work order's `content_text` via a system note, and the response carries the 409 status with `ERR_DUPLICATE_LINKED` and the linked work-order id embedded in the error message. The linked row persists for audit but stays in `REGISTERED` and cannot be classified independently — only the original handles the substantive flow. Two operators racing the same registration within the window observe first-writer-wins on the work-order id: the loser's row is still created but is the one that carries the `duplicate_of_id` pointer to the winner.

A registered case still in `REGISTERED` may be amended by the operator with PATCH against `content_text`, `category_code`, `sub_category_code`, `urgency`, or `audio_url`, optionally with a `version` for the OCC check. If `category_code`, `sub_category_code`, or `urgency` is changed, the difficulty score is recomputed under the same registration formula.

### 3.3. Classification — Resolving the Routing World

Classification by a `Dispatcher` advances the case from `REGISTERED` to `CLASSIFIED`. The request body carries a `mode` value indicating whether the operator believes the (category, sub-category) pair has an exact match in `CategoryRule` (in which case `classification_mode` is set to `RULE_BASED`) or whether AI assistance is needed (in which case `classification_mode` is set to `AI_ASSISTED`). The transition is permitted only when `duplicate_of_id` is null, the (`category_code`, `sub_category_code`) pair resolves to an existing rule, and `lead_department_id` is still null; otherwise the work-order state-permission check fires with `ERR_INVALID_STATE`.

The first side effect is jurisdiction-aware resolution of the lead department. The matched `CategoryRule.lead_department_code` is the starting point. If the department mapped from that code lists the work order's `jurisdiction_code` in its `jurisdiction_codes`, that department is the lead. If it does not, and a citywide peer (a department also mapped to the same lead code whose `jurisdiction_codes` list is empty) exists, the citywide peer takes the lead role. If neither holds — the mapped lead does not serve the jurisdiction and no citywide fallback exists — classification is rejected with `ERR_JURISDICTION_NO_DEPARTMENT` (422). When jurisdiction resolves, `lead_department_id` is set; `supporting_department_ids` is populated by mapping each entry of `CategoryRule.supporting_department_codes` to its corresponding department id; `joint_handling` becomes true precisely when at least one supporting department was mapped (the list size is greater than zero).

Deadlines are then computed. The statutory deadline is set to the registration timestamp advanced forward by the `CategoryRule.statutory_time_limit_hours` interpreted as business hours; the committed deadline is set the same way using `committed_time_limit_hours`. Business-hours addition walks forward hour by hour, skipping intervals outside the Monday-through-Friday 09:00-to-17:00 UTC window, until the target number of business hours has elapsed; the result is a precise instant on the wall clock. The difficulty score is then recomputed under the post-classification form: the same formula as registration, but with the joint factor set to 2 when `joint_handling` is now true and 0 when it is still false. The clamp to the closed range 1 to 10 still applies, so a case with a category-base difficulty of 5 and an urgency weight of 5 (`CRITICAL`) and joint handling will land at 10, not 12. `priority_flag` is recomputed against the new score and the existing urgency. An `AuditLog` row with action `CLASSIFY` is written.

If, after attempting classification, no department can serve the jurisdiction, the dispatcher may instead take the explicit `CLASSIFIED → REJECTED` branch by submitting a `rejection_reason` (between 1 and 500 characters); the work order moves to `REJECTED` (a terminal state) and an audit row is written. A reject with a missing reason or out-of-range reason length fails the generic field-validation check with `ERR_VALIDATION`. Note this reject endpoint may also be entered from the `CLASSIFIED` state when the lead department is null or the jurisdiction never resolves.

### 3.4. Dispatch — Creating the Assignment Fan-Out

Dispatch by a `Dispatcher` advances `CLASSIFIED` to `DISPATCHED`, provided `lead_department_id` is not null, the lead department's `status` is `ACTIVE`, and every supporting department referenced has `status` equal to `ACTIVE`. The transition creates one `DepartmentAssignment` row with `role` equal to `LEAD` and `department_id` equal to `lead_department_id`, in `stage_status` equal to `DISPATCHED`, and one further `DepartmentAssignment` row with `role` equal to `SUPPORTING` for each supporting department, each in `stage_status` equal to `DISPATCHED`. Each new assignment stamps `dispatched_at` to the current server time; `handler_id`, `accepted_at`, `rejection_reason`, `opinion_text`, `opinion_decision`, and `opinion_submitted_at` are null until the corresponding later transitions populate them. For every department touched (lead and every supporting) the department's `pending_work_count` is incremented by 1 — these are the increments that the department-pending invariant later asserts must each be paired with exactly one decrement.

Dispatch emits a `SyncEvent` with `event_type` equal to `DISPATCHED` to each of the three downstream platforms — `IM`, `GOVT_AFFAIRS`, and `INTER_DEPT`. If `priority_flag` is true at dispatch time (recall that the flag is set when `urgency` is `HIGH` or higher, or `difficulty_score` is at least 7), the system creates a `SupervisionTask` with `reason` equal to `HIGH_PRIORITY_AUTO`, `status` equal to `OPEN`, and `escalation_level` equal to 0. An `AuditLog` row with action `DISPATCH` is written.

### 3.5. Department Pickup — Accept, Reject, Reassign

A `DepartmentHandler` accepts an assignment by addressing the assignment under its parent work order. The acceptance succeeds only when the assignment's current `stage_status` is `DISPATCHED`, the acting handler's `department_id` equals the assignment's `department_id`, and the handler's own `status` is `ACTIVE`. Two handlers within the same department racing the same acceptance are serialized by a first-writer-wins guarantee on the assignment's `stage_status` moving out of `DISPATCHED`; the loser receives `ERR_ASSIGNMENT_NOT_PENDING` (409). The successful accept side-effects set the assignment's `stage_status` to `ACCEPTED`, stamp `handler_id` to the acting handler, set `accepted_at` to the current time, and increment `Handler.open_assignment_count` by 1. When the accepted assignment is the lead assignment and the parent work order's `status` is `DISPATCHED` or `REOPENED`, the work-order status is advanced to `IN_PROGRESS` (supporting acceptances do not change the parent's status). An `AuditLog` row with action `ACCEPT` is written.

A handler may also reject an assignment back to the dispatcher when the assignment is still `DISPATCHED` and a `rejection_reason` (between 1 and 500 characters) is provided. The assignment's `stage_status` moves to `REJECTED`, the `rejection_reason` is recorded on the row, and the department's `pending_work_count` is decremented by 1 — this is one of the decrement obligations the pending invariant tracks. If the rejected assignment was the lead, the work order then requires a dispatcher reassignment; the system does not move the work-order status itself on a rejected supporting assignment. An `AuditLog` row with action `REJECT` is written.

Reassignment is a `Dispatcher` action. It is permitted either when the original assignment is still `DISPATCHED`, or when the original assignment is the lead and is currently `REJECTED` (the latter is the rebound after a handler rejected the lead). The request supplies `target_department_id`; the target department must exist and have `status` equal to `ACTIVE`. When the role being reassigned is the lead, the target department must also serve the work order's `jurisdiction_code` — either its `jurisdiction_codes` contains the work order's jurisdiction, or its `jurisdiction_codes` list is empty (the citywide marker). Otherwise the reassignment is rejected with `ERR_JURISDICTION_MISMATCH` (422). The side-effects move the original assignment's `stage_status` to `REASSIGNED`, decrement the source department's `pending_work_count` by 1 (but only when it was not already decremented by a prior reject — the contract is that each dispatch's increment must be paired with exactly one decrement), create a new `DepartmentAssignment` with the same `role`, the new `department_id`, and `stage_status` set to `DISPATCHED`, increment the target department's `pending_work_count` by 1, and — when the role is `LEAD` — update the work order's `lead_department_id` to the target. An `AuditLog` row with action `REASSIGN` is written. The dispatcher reassigning while a handler in the original department is concurrently accepting is the second concurrency scenario: first-writer-wins on `stage_status`, with the loser receiving `ERR_ASSIGNMENT_NOT_PENDING`.

### 3.6. Pause and Resume — Stretching the Clock

While the lead has accepted and the case is `IN_PROGRESS`, the lead's handler may pause the time-limit clock for a clarification period. The pause endpoint expects a `reason` (between 1 and 500 characters) and is permitted only when the work order's `pause_started_at` is null (the case is not already paused) and the acting handler is the lead assignment's current `handler_id`. The side-effects create a `ClarificationPause` row carrying the parent's `work_order_id`, the `reason`, and a `paused_at` set to the current time (`resumed_at` and `duration_seconds` remain null until resume), and they set the work order's `pause_started_at` to the same instant. An `AuditLog` row with action `PAUSE` is written. A pause attempted while the work order is already paused fails priority-11 with `ERR_ALREADY_PAUSED`; two operators racing to pause the same work order are serialized by first-writer-wins on `pause_started_at` transitioning out of null, with the loser receiving `ERR_ALREADY_PAUSED`.

Resume is the inverse — also restricted to the lead's handler — and requires `pause_started_at` to be non-null. If the work order is not currently paused, resume fails priority-10 with `ERR_NOT_PAUSED`. On success, the latest open `ClarificationPause` for the work order has its `resumed_at` set to the current time and its `duration_seconds` set to the whole-seconds difference between `resumed_at` and `paused_at`. The work order's `pause_accumulated_seconds` is increased by that same duration (the global invariant is that, when no pause is open, every work order's `pause_accumulated_seconds` equals exactly the sum of `duration_seconds` across its `ClarificationPause` rows whose `resumed_at` is not null; the system-wide tolerance on that equality is zero whole seconds). Both `statutory_deadline_at` and `committed_deadline_at` are then advanced by exactly that same whole-seconds duration — wall-clock seconds, not business hours, because clarification time literally stretches the wall clock for the case. `pause_started_at` is reset to null. An `AuditLog` row with action `RESUME` is written.

### 3.7. Opinions, Aggregation, and Resolution

When the case is joint-handling, every supporting assignment must travel `DISPATCHED → ACCEPTED → OPINION_SUBMITTED` before the lead can resolve. A supporting handler submits an opinion against their own assignment, providing an `opinion_text` (between 1 and 2000 characters) and an `opinion_decision` of `AGREE`, `DISAGREE`, or `ABSTAIN`. The transition is permitted only when the assignment's `role` is `SUPPORTING` and its `stage_status` is `ACCEPTED`. The side-effects move `stage_status` to `OPINION_SUBMITTED`, stamp `opinion_submitted_at` to the current time, decrement the department's `pending_work_count` by 1, and decrement the handler's `open_assignment_count` by 1. The parent work order's aggregated opinion decision is recomputed at this point. An `AuditLog` row with action `OPINION_SUBMIT` is written.

The aggregation rule is as follows. Let N be the count of `SUPPORTING` assignments on the parent work order that are currently in `OPINION_SUBMITTED`, let A be the count whose `opinion_decision` is `AGREE`, let D be the count whose `opinion_decision` is `DISAGREE`, and let X be the count whose `opinion_decision` is `ABSTAIN`. If the work order's `joint_handling` is false, the aggregated decision is trivially `AGREE` (there are no supporting departments to dissent). Otherwise, if N is strictly less than the total count of all `SUPPORTING` assignments on the work order (i.e., at least one supporting opinion is still outstanding), the aggregated decision is `PENDING`. Once every supporting opinion has been submitted, the rule is: if D is zero the aggregated decision is `AGREE`; if D is greater than or equal to the ceiling of N divided by 2 the aggregated decision is `DISAGREE_BLOCKING`; otherwise the aggregated decision is `DISAGREE_OUTVOTED`. Note that when N is even and D equals exactly N divided by 2, the ceiling of N divided by 2 equals N divided by 2, so the inequality holds and ties resolve to `DISAGREE_BLOCKING` — the more conservative outcome. The aggregation produces a discrete label, not a numeric score.

A supporting handler facing deadlock — either because the aggregation has gone to `DISAGREE_BLOCKING`, or because they have declared deadlock with another department on the same work order — may escalate their assignment from `ACCEPTED` to `ESCALATED`. The side-effects move the `stage_status` to `ESCALATED`, and if the parent work order already has a `SupervisionTask` in `status` equal to `OPEN`, its `escalation_level` is incremented by 1; otherwise a fresh `SupervisionTask` is created with `reason` equal to `MANUAL`, `status` equal to `ESCALATED`, and `escalation_level` equal to 1. The system emits a `SyncEvent` with `event_type` equal to `ESCALATED` to each of `IM`, `GOVT_AFFAIRS`, and `INTER_DEPT`. An `AuditLog` row with action `ESCALATE` is written.

Resolution by the lead's handler advances `IN_PROGRESS` to `RESOLVED`. The request body carries a `resolution_summary` of length between 1 and 4000 characters. The preconditions are five: the acting handler must be the lead assignment's current `handler_id`; the work order must not currently be paused (`pause_started_at` must be null — a paused case must resume before it can resolve); the `resolution_summary` must be in range; when `joint_handling` is true every supporting assignment must be in `OPINION_SUBMITTED` (otherwise priority-16 fires with `ERR_OPINIONS_INCOMPLETE`); and the current aggregated opinion decision must not be `DISAGREE_BLOCKING` (otherwise priority-17 fires with `ERR_DISAGREEMENT_UNRESOLVED`). On success, the work-order `status` becomes `RESOLVED`, `resolution_summary` is written, `warning_state` is recomputed, the lead department's `pending_work_count` is decremented by 1, the lead handler's `open_assignment_count` is decremented by 1, and the same `pending_work_count` decrement is applied to any supporting department that has not yet decremented (in practice all of them will already have decremented on `OPINION_SUBMITTED`, but the contract preserves the symmetry).

Resolution also auto-dispatches a `SatisfactionSurvey` when the caller is reachable. The auto-dispatched survey's `channel` is `CALL` when the parent is not anonymous and `caller_phone` is present; otherwise, when the parent is anonymous and an IM contact handle has been recorded on file via input, the channel is `IM`; otherwise no survey is created at all (the work order still reaches `RESOLVED` and the satisfaction calculation treats it as having no response). The work order also emits a `SyncEvent` with `event_type` equal to `RESOLVED` to each of the three downstream platforms. An `AuditLog` row with action `RESOLVE` is written.

### 3.8. Warning State — The Read-Time Monitor

A work order's `warning_state` is the single field that summarises how close the case is to breaching its deadline; it is recomputed on read by the retrieval endpoint and again on every sweep. Let "remaining" be the whole-seconds difference between the committed deadline and the current server time, let "total" be the whole-seconds difference between the committed deadline and the registration time (after pause shifts have been applied to the committed deadline), and let "pct" be remaining divided by total when total is strictly positive, and zero otherwise. The state is determined in the following cascade. When the current server time is strictly greater than the statutory deadline, the state is `BREACHED`. Otherwise, when pct is less than or equal to zero, the state is `RED` (the committed deadline has passed but the statutory deadline has not yet). Otherwise, when pct is less than or equal to 0.25 — meaning 25% or less of the committed window remains — the state is `YELLOW`. Otherwise the state is `NONE`. The boundary semantics are deliberate: a case with pct exactly equal to 0.25 is `YELLOW` (not `NONE`), and a case where the server time is exactly equal to the committed deadline has pct equal to 0 and lands in `RED` (not `BREACHED` — `BREACHED` requires the strict greater-than past the statutory deadline).

### 3.9. Satisfaction Survey Lifecycle

A `SatisfactionSurvey` may be auto-dispatched on resolution as described above, or manually dispatched by a `HotlineOperator` against a `RESOLVED` or `FOLLOWED_UP` parent. The manual dispatch endpoint accepts a `channel` of `CALL`, `SMS`, or `IM`. When the parent work order has `anonymous` equal to true, `CALL` and `SMS` are forbidden (both as a manual choice and during auto-dispatch); attempting either yields `ERR_SURVEY_CHANNEL_FORBIDDEN` (422). A newly created survey starts in `status` equal to `DISPATCHED` and stamps `dispatched_at`; `score`, `comment`, and `responded_at` are null.

A `SurveyAgent` records the caller's response by supplying a `score` (an integer between 1 and 5 inclusive, where 1 is very dissatisfied and 5 is very satisfied) and an optional `comment` (between 0 and 2000 characters). The transition from `DISPATCHED` to `RESPONDED` is permitted only when the survey is still in `DISPATCHED` and the response arrives within 48 business hours after the survey's `dispatched_at` — the survey-expiry window. A response submitted past the window is rejected with `ERR_SURVEY_EXPIRED` (422); a response against a survey not in `DISPATCHED` is rejected with `ERR_SURVEY_NOT_PENDING` (409). Two responses racing the same survey are serialized by first-writer-wins on `SatisfactionSurvey.status` moving out of `DISPATCHED`; the loser receives `ERR_SURVEY_NOT_PENDING`. On success, the survey's `status` becomes `RESPONDED`, the `score` and `comment` are written, `responded_at` is stamped, the parent work order's `status` is advanced from `RESOLVED` to `FOLLOWED_UP`, and an `AuditLog` row with action `SURVEY_RESPOND` is written.

Surveys that go unanswered eventually expire. When the sweep capability runs and the current server time is strictly later than `dispatched_at` plus 48 business hours, every still-dispatched survey is moved to `EXPIRED`. No further state transitions are possible from `EXPIRED` or from `RESPONDED` — both are terminal.

### 3.10. Dissatisfaction, Reopening, and Closing

When the latest survey on a `FOLLOWED_UP` work order returns a `score` less than or equal to 2 (the dissatisfaction threshold), a `HotlineOperator` may reopen the case. The reopen is permitted only when the latest `SatisfactionSurvey` is in `RESPONDED`, its score is at most 2, and the reopen request arrives within 72 business hours of that survey's `responded_at` — the reopen window. A reopen with a score above the threshold or outside the window is rejected with `ERR_REOPEN_WINDOW_EXPIRED` (422). The side-effects move the work order's `status` to `REOPENED`, reset the existing lead `DepartmentAssignment` back to `stage_status` equal to `DISPATCHED` while clearing its `handler_id` and `accepted_at` to null (a re-dispatch to the same lead department), and increment the lead department's `pending_work_count` by 1 (re-establishing the lead's outstanding work counter). A `SyncEvent` with `event_type` equal to `REOPENED` is emitted to each of the three downstream platforms. An `AuditLog` row with action `REOPEN` is written. A subsequent accept on the lead assignment moves the assignment back to `ACCEPTED` and the work order back to `IN_PROGRESS` via the same accept transition as before.

Closing the case is the role of the `Dispatcher`. There are two valid entry paths into `CLOSED`. The first applies when the case is in `FOLLOWED_UP` and either the latest survey is `RESPONDED` with a score of at least 3, or the latest survey is `EXPIRED`, or no survey was ever created (the no-channel path at resolve time). The second applies when the case is still in `RESOLVED` and no survey exists because resolve could not pick a channel. In both paths the close additionally requires that no `SupervisionTask` for this work order is currently in `OPEN` or `ESCALATED`; otherwise priority-18 fires with `ERR_SUPERVISION_OPEN`. Two operators racing reopen and close on the same `FOLLOWED_UP` work order are serialized by first-writer-wins on the work-order `status`; the loser receives `ERR_INVALID_STATE`. On success the work order's `status` becomes `CLOSED`, `closed_at` is stamped, a `SyncEvent` with `event_type` equal to `CLOSED` is emitted to the three platforms, and an `AuditLog` row with action `CLOSE` is written. `CLOSED` is terminal.

### 3.11. Supervision Tasks and Inactivity Escalation

Two pathways create `SupervisionTask` rows. The first is automatic at dispatch: a work order with `priority_flag` true at the moment of dispatch produces a task with `reason` equal to `HIGH_PRIORITY_AUTO`, `status` equal to `OPEN`, and `escalation_level` equal to 0, stamped against the work order. The second is on handler escalation as described in section 3.7: an existing open task is escalated in place, or a fresh task is created with `reason` equal to `MANUAL`. The other recognised `reason` values are `INACTIVITY_REMINDER` and `DEADLINE_WARNING`; both originate from the sweep flow described next.

Inactivity escalation works as follows. When the sweep runs against a supervision task in `OPEN` whose `escalation_level` is strictly less than 3, and the time since the most recent activity (the latest of the task's `created_at`, its `last_reminder_at`, and the latest activity timestamp on the parent work order via `AuditLog` actions `ACCEPT`, `OPINION_SUBMIT`, or `RESOLVE`) is at least 24 business hours, the task transitions to `ESCALATED`, its `escalation_level` is incremented by 1, and its `last_reminder_at` is stamped to the sweep instant. The symmetric rule applies to a task already in `ACKNOWLEDGED`: if there has still been no progress for at least 24 business hours since `last_reminder_at`, and the `escalation_level` is below 3, the task escalates to `ESCALATED` with the same increment and stamp. A `Supervisor` may acknowledge an open task — moving its `status` from `OPEN` to `ACKNOWLEDGED` and stamping `last_reminder_at`. A `Supervisor` may close any supervision task (from `OPEN`, `ACKNOWLEDGED`, or `ESCALATED`) once the parent work order's `status` is one of `RESOLVED`, `FOLLOWED_UP`, or `CLOSED`. Closing sets `status` to `CLOSED`.

### 3.12. Difficulty, Priority, and Why the Score Can Grow at Classification

The difficulty score is computed at two distinct moments and the two results can differ for the same caller-reported inputs. At registration, the formula's joint factor is fixed at 0 — the system does not yet know which supporting departments, if any, will be involved. At classification, after `joint_handling` has been resolved, the same formula is evaluated again but the joint factor is 2 whenever `joint_handling` is true. The shared formula adds the urgency weight (0 for `LOW`, 1 for `NORMAL`, 3 for `HIGH`, 5 for `CRITICAL`), the matched category's `difficulty_base` (defaulting to 1 if for any reason the rule cannot be matched, though in practice the category check has rejected that case earlier), and the joint factor. The unclamped sum is then constrained to the closed range 1 to 10 by the larger of 1 and the smaller of 10 and the raw sum, and a round-half-up to the nearest integer is applied (a no-op on integer inputs). The `priority_flag` derived from the score is true precisely when `urgency` is at least `HIGH` or `difficulty_score` is at least 7 at the moment of evaluation — note the disjunction, not a conjunction.

### 3.13. Cross-Aggregate Invariants

Two cross-aggregate invariants must hold at every moment when the system is at rest (i.e., no in-flight pause). The pause invariant requires that for every work order, the field `pause_accumulated_seconds` is exactly equal to the sum of `duration_seconds` across its `ClarificationPause` rows whose `resumed_at` is not null; if the work order is currently paused, the equality must still hold when the open pause is excluded. The global form of the same invariant is that the sum of `pause_accumulated_seconds` across every work order minus the sum of `duration_seconds` across every resolved `ClarificationPause` row equals zero whole seconds at every moment when no pause is open. The tolerance is exactly zero seconds — neither rounding slack nor stale-cache compensation is permitted. The department-pending invariant requires that every department's `pending_work_count` is exactly equal to the count of `DepartmentAssignment` rows where `department_id` is that department's id and `stage_status` is in `DISPATCHED` or `ACCEPTED`. Globally this means the sum of `pending_work_count` across every department minus the count of `DepartmentAssignment` rows in `DISPATCHED` or `ACCEPTED` must equal zero at every moment. Each dispatch's increment is paired with exactly one decrement: a handler reject, a dispatcher reassign on the source department, a supporting opinion-submit, or — on the lead — a resolve.

### 3.14. Statistics — Satisfaction, Breach Rate, and Trend

Three statistics endpoints are read by `PlatformAdmin` and `Supervisor`. The satisfaction index aggregates over the universe of work orders whose `status` is one of `FOLLOWED_UP`, `CLOSED`, or `REOPENED`, optionally constrained by a `period_start` and `period_end` filter. The endpoint may also be grouped by department or by handler via a `group_by` query value of `department` or `handler`, and individual `department_id` or `handler_id` filters may further narrow the universe. For each work order in the universe the latest `SatisfactionSurvey` by `dispatched_at` (tie-break: higher id) is selected. If that latest survey is in `RESPONDED`, the work order contributes its survey `score`. If the latest survey is in `EXPIRED`, or no survey exists at all, the work order contributes 3 — the neutral baseline. The contributions are summed, divided by the count of work orders in the universe at full float precision, and rounded half-up to 2 decimal places at the very end. The order of operations is divide-then-round, never round-per-row-then-divide. When grouped by department, the universe is narrowed to work orders whose `lead_department_id` matches the grouping key; when grouped by handler, the universe is narrowed to work orders whose lead `DepartmentAssignment.handler_id` matches — the two variants can yield genuinely different numbers because a handler typically holds only a slice of their department's work orders.

The breach-rate endpoint accepts `period_start`, `period_end`, optional `group_by` (department or category), `department_id`, and `category_code` filters and produces two rates. The universe is work orders whose `status` is in `RESOLVED`, `FOLLOWED_UP`, `CLOSED`, or `REOPENED` and whose registration falls inside the period. For each work order the actual resolve instant is the latest `AuditLog.occurred_at` whose `action` is `RESOLVE`. The statutory breach indicator is 1 when the work order's `statutory_deadline_at` is strictly earlier than that actual resolve instant, and 0 otherwise; the committed breach indicator is the same formula against `committed_deadline_at`. Each rate is computed by summing the indicator across the universe, dividing by the count of work orders in the universe at full float precision rounded half-up to 4 decimals (the fractional rate), then multiplying by 100 to produce a percentage with 2 decimal places. The pinned order is divide-first (to a 4-decimal fraction), then multiply by 100; reversing the order — rounding per-percentage first and averaging afterwards — produces a different number, and that is not the contract. The statutory variant is used for public-disclosure compliance reporting and reflects regulatory time limits; the committed variant is used for internal department performance and is always greater than or equal to the statutory variant for identical input data because committed deadlines are tighter than statutory deadlines.

The trend endpoint accepts `period_start`, `period_end`, and a `bucket` size, and returns counts of work orders in each bucket for the lifecycle marker events `REGISTERED`, `RESOLVED`, `CLOSED`, and `REOPENED` — these are the public-disclosure aggregates the platform reports out.
