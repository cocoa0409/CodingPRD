# Fund Sales And Clearing API — Product Requirements Document

## 1. Introduction

The Fund Sales and Clearing platform is the back-office system of record for a multi-channel mutual-fund distributor. A single integrated service handles product onboarding (drafting funds, classifying them by fund type and risk rating, and gating them through a compliance review before they reach investors), the daily flow of subscription, redemption, and conversion orders coming from investor channels, the T+1 net asset value calculation that depends on portfolio data attested by the custodian, the dividend lifecycle from announcement through ex-dividend snapshotting to cash or reinvestment payout, and the end-of-day reconciliation that confronts the Transfer Agent's internal ledger against custodian, channel, and bank statements before settlement instructions are emitted to downstream systems.

Three structural concerns drive the design. First, the system is regulated: every state change that affects an investor's economic position must produce an audit trail, and several lifecycle steps are gated by segregation-of-duties constraints between the operator who proposes a change and the operator who approves it. Second, the system is financial: every cash and share number lives in minor units (cents and ten-thousandths of a share respectively), every fee, NAV, and dividend computation has a pinned rounding order so that two correct implementations produce identical integers, and every reconciliation must close on a conserved-quantity invariant before settlement instructions are dispatched. Third, the system is event-driven: NAV publication triggers a deferred confirmation pass over yesterday's open orders, large redemptions are deferred to the next NAV cycle, dividend ex-date snapshots holdings, and reconciliation closure fans out instructions to BANK, CUSTODIAN, TA, and REGULATOR consumers. The API exposed below is mounted under `/funds` and adjacent siblings (`/investors`, `/orders`, `/dividend-plans`, `/reconciliations`, `/audit-logs`, `/_clock`) and provides the primitives required to drive each of these concerns.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID` (the caller's identifier) and `X-User-Role` (the caller's role). When either header is missing or empty, the request is rejected with `ERR_AUTH_HEADERS_MISSING` (HTTP 401). When both headers are present but the role is not authorized for the targeted endpoint per the RBAC matrix in §4, the request is rejected with `ERR_FORBIDDEN` (HTTP 403).

Six roles participate in the system, each with a fixed spelling that the auth layer matches case-sensitively:

- `PlatformAdmin` — system operator handling provisioning (investor onboarding, cash credits, clock control). When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it in `AuditLog.actor_user_id` for any audited action initiated by this role but does not compare it to any entity's `id`.
- `ProductOperator` — designs fund products and dividend plans, submits funds for compliance review. When `X-User-Role` is `ProductOperator`, `X-User-ID` is an opaque operator identifier; the server stamps it onto `Fund.shelf_creator_actor_id` when this role submits a fund for review, but otherwise does not compare it to any entity's `id`.
- `ComplianceReviewer` — approves or rejects fund shelf review, suspends and resumes funds, takes funds off-shelf, adjusts published NAVs, approves investor KYC, and cancels announced dividends. When `X-User-Role` is `ComplianceReviewer`, `X-User-ID` is an opaque operator identifier; the server stamps it onto `Fund.shelf_review_actor_id` on shelf approval, and uses that stored identifier for the NAV-publisher segregation-of-duties check, but does not compare it to any entity's `id` for ownership.
- `NavOperator` — publishes T+1 NAV snapshots, marks dividend plans ex-dividend, and executes dividend payments. When `X-User-Role` is `NavOperator`, `X-User-ID` is an opaque operator identifier; it is recorded in `AuditLog` for `NAV_PUBLISHED` and `DIVIDEND_EXECUTED` actions and is compared against `Fund.shelf_review_actor_id` for the NAV segregation-of-duties check, but is not tied to any persisted entity's `id`.
- `ClearingOperator` — opens reconciliation runs, resolves exceptions, finalizes runs, and closes runs to emit settlement instructions. When `X-User-Role` is `ClearingOperator`, `X-User-ID` is an opaque operator identifier; the server records it as the run's creator on opening and compares the closer's `X-User-ID` against the recorded creator for the reconciliation segregation-of-duties check, but does not compare it to any entity's `id` for ownership.
- `Investor` — end user who submits orders, picks dividend options, and views own holdings. When `X-User-Role` is `Investor`, `X-User-ID` is the `id` of the acting `Investor` entity; ownership checks on any resource that references an `Investor` (such as an `Order`, a `Holding`, or a `DividendDistribution`) compare the resource's `investor_id` field to `X-User-ID`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two optional query parameters: `limit` and `offset`. The default `limit` is 10, its minimum is 1, and its maximum is 100. The default `offset` is 0. Results are sorted by `created_at` in ascending order. The `meta` envelope on every list response includes the four pagination fields `limit`, `offset`, `total_count`, and `has_more`, where `total_count` is the unfiltered match count for the query and `has_more` is true when `offset + limit < total_count`.

### 2.4. Common Resource Properties

Every entity carrying common fields (specifically `Investor`, `Fund`, `Order`, `Holding`, `DividendPlan`, and `ReconciliationRun`) exposes four system-managed properties on every response payload: `id`, `created_at`, `updated_at`, and `version`. The `id` is a server-minted UUID with no domain prefix. The `created_at` and `updated_at` fields are ISO 8601 UTC timestamps with three fractional digits; `created_at` is set once at insertion and never changes, `updated_at` is refreshed on every server-side mutation of the resource. The `version` field is a non-negative integer that begins at 1 on creation and increments by exactly 1 on every successful mutation. The remaining entities — `NavSnapshot`, `LotEntry`, `DividendDistribution`, `ReconciliationException`, `SettlementInstruction`, `AuditLog`, and the singleton `Clock` — carry only `id` and `created_at`; they do not expose `updated_at` or `version`. The `Clock` resource has the fixed `id` `"clock"` and the single field `now`.

### 2.5. Optimistic Concurrency Control

State-changing endpoints (any POST that mutates an existing resource) accept an optional `version` field in the request body. When the client supplies a `version` whose value does not equal the resource's current `version`, the request is rejected with `ERR_VERSION_CONFLICT` (HTTP 409). When the client omits `version` from the request body, the server skips the check and applies the mutation against whatever the current version is. Successful mutations always increment `version` by exactly 1 in the response body.

### 2.6. Monetary, Share, and NAV Units

All monetary amounts are integers in minor units (CNY fen, i.e., cents): `gross_amount_cents`, `confirmed_amount_cents`, `subscription_fee_cents`, `redemption_fee_cents`, `back_end_load_fee_cents`, `conversion_fee_cents`, `cash_balance_cents`, `gross_assets_cents`, `management_fee_accrued_cents`, `custodian_fee_accrued_cents`, `sales_service_fee_accrued_cents`, `net_assets_cents`, `portfolio_market_value_cents`, `portfolio_accrued_income_cents`, `gross_dividend_cents`, `tax_withheld_cents`, `net_dividend_cents`, `cost_basis_cents`, `cost_cents`, `total_internal_amount_cents`, `total_external_amount_cents`, `net_break_cents`, `adjustment_amount_cents`, `internal_amount_cents`, `external_amount_cents`, `min_subscription_amount_cents`, `max_subscription_amount_cents`, and `amount_cents` are all integer cents. All share quantities (`shares`, `requested_shares`, `confirmed_shares`, `eligible_shares`, `reinvested_shares`, `total_outstanding_shares`, `shares_outstanding_at_nav`, `min_redemption_shares`) are integers in 1e-4 share units, meaning the integer value 10000 represents one whole share. NAV per share (`nav_per_share_micros` and `dividend_per_share_micros`) is an integer in micros, where 1,000,000 represents one whole CNY per share. Annualized fee rates (`management_fee_bps_annual`, `custodian_fee_bps_annual`, `sales_service_fee_bps_annual`) and per-event fee rates (`conversion_fee_bps`, `tax_rate_bps_domestic`, `tax_rate_bps_foreign`, the per-tier `rate_bps` values inside `subscription_fee_tiers` and `redemption_fee_tiers`, `large_redemption_threshold_pct_bps`, and `large_redemption_pct_bps`) are integer basis points where 10000 bps equals 100%.

### 2.7. Precision and Rounding

All financial calculations follow a half-up rounding rule at the precision indicated below — half-up meaning the standard banker's tie-breaker is *not* used, ties always round away from zero. The one exception is reinvested-dividend share computation, which uses half-down to ensure no over-issuance of shares. Per-step precision: cents-denominated intermediates round half-up at cents; `nav_per_share_micros` rounds half-up at micros; per-tier and per-lot fee components round half-up at cents *first*, then sum (never sum-then-round); reinvested shares round half-down at the 1e-4 share unit. The `reconciliation_invariant` uses exact integer arithmetic with no rounding.

### 2.8. Hierarchical Consistency, Cascades, And Audit

Any operation that mutates a resource refreshes the resource's `updated_at` timestamp and increments its `version` by 1. Several state transitions cascade across multiple aggregates: NAV publication advances open orders for that trade date through their confirmation lifecycle, mutating `Holding.shares`, `Holding.cost_basis_cents`, `LotEntry.shares`, `LotEntry.status`, `Fund.total_outstanding_shares`, and `Investor.cash_balance_cents` in lockstep with the order's confirmation; dividend payment cascades into `Investor.cash_balance_cents` for `CASH` recipients and into new `LotEntry` rows plus the same chain of holding and fund-share aggregates for `REINVEST` recipients; fund suspension cascades into rejection of all pending submitted orders for that fund. Every cascade hop refreshes the touched resource's `updated_at` and bumps its `version`. Every cascade also writes one `AuditLog` row per affected aggregate, populating `actor_user_id`, `actor_role`, `action`, `subject_entity`, `subject_id`, `from_state`, `to_state`, and `payload_json`; for system-driven cascades (deferred order confirmation, dividend payout, suspension cascade), the actor fields reflect the operator who initiated the triggering call. The valid `action` values are `ORDER_STATUS_CHANGE`, `NAV_PUBLISHED`, `NAV_ADJUSTED`, `DIVIDEND_EXECUTED`, `RECONCILIATION_RESOLVED`, and `FUND_SHELF_CHANGE`.

### 2.9. Nested Resource Path Validation

Path parameters on nested endpoints are validated left-to-right: when a request targets a resource expressed as a path of identifiers, the server first verifies the outermost path segment exists, then the next, and so on, returning `ERR_NOT_FOUND` (HTTP 404) for the first missing segment encountered. This applies to nested NAV reads (where the fund must exist before its NAV snapshot is looked up), to nested dividend distribution operations (where the dividend plan must exist before the distribution under it), and to nested reconciliation exception operations (where the reconciliation run must exist before the exception under it — the exception path parameter is named `eid`, distinct from the run's `id`).

### 2.10. Validation Ordering

Within a single request, validations are evaluated in a fixed priority order so that error precedence is deterministic. The ordering, from highest priority (evaluated first) to lowest, is: (1) presence of `X-User-ID` and `X-User-Role` headers (else `ERR_AUTH_HEADERS_MISSING`); (2) role permitted for endpoint per RBAC (else `ERR_FORBIDDEN`); (3) every path resource exists, left-to-right (else `ERR_NOT_FOUND`); (4) for new-order submission, idempotency replay detection — when an order with the same `investor_id` and `idempotency_key` already exists, the server returns the original `Order` body (200) for an identical replay, or `ERR_IDEMPOTENCY_REPLAY` (409) when the body differs; (5) target resource is in a valid state for the operation (else `ERR_INVALID_STATE`); (6) segregation of duties on shelf review — approver and rejecter must differ from the creator (else `ERR_SOD_VIOLATION_SHELF`); (7) segregation of duties on NAV publication — publisher must differ from the fund's stored shelf reviewer (else `ERR_SOD_VIOLATION_NAV`); (8) segregation of duties on reconciliation closure — closer must differ from the run's creator (else `ERR_SOD_VIOLATION_RECON`); (9) investor KYC is approved before any order (else `ERR_KYC_NOT_APPROVED`); (10) suitability match — investor risk tolerance is at least the fund's risk rating on the C-vs-R index (else `ERR_SUITABILITY_MISMATCH`); (11) sales region — the investor's country code is in the fund's allowed-country-codes list, or that list is empty, meaning unrestricted (else `ERR_REGION_RESTRICTED`); (12) conversion target validity — for a CONVERT order, the target fund differs from the source, both are `ON_SHELF`, and the investor is suitable for the target (else `ERR_CONVERSION_INVALID_TARGET`); (13) cancel cutoff temporal check (else `ERR_CANCEL_WINDOW_CLOSED`); (14) NAV T+1 temporal check (else `ERR_NAV_T_PLUS_1_NOT_ELAPSED`); (15) dividend date ordering check (else `ERR_DIVIDEND_DATE_INVALID`); (16) order amount/share within fund min/max bounds (else `ERR_ORDER_LIMIT_VIOLATED`); (17) fee tiers non-overlapping and ascending (else `ERR_FEE_TIERS_INVALID`); (18) sufficient cash for subscribe (else `ERR_INSUFFICIENT_CASH`); (19) sufficient shares for redeem or convert (else `ERR_INSUFFICIENT_SHARES`); (20) reconciliation finalize invariant (else `ERR_RECONCILIATION_INVARIANT_BROKEN`); (21) off-shelf only when no holders remain (else `ERR_FUND_HAS_HOLDERS`); (22) waive prohibited on amount-mismatch exception (else `ERR_WAIVE_NOT_ALLOWED`).

### 2.11. Concurrency Guarantees

Six concurrent-operation scenarios serialize at the resource boundary with deterministic loser semantics. (a) Two operators that simultaneously approve and reject the same fund's shelf review serialize first-writer-wins on `Fund.status`; the loser observes the fund has already moved out of `UNDER_REVIEW` and receives `ERR_INVALID_STATE` (409). (b) Two simultaneous order submissions with identical `investor_id` and `idempotency_key` serialize first-writer-wins on the (`investor_id`, `idempotency_key`) tuple; the server creates exactly one `Order`, and a replay with the same key returns the original `Order` body with HTTP 200, while a replay whose body differs from the stored order receives `ERR_IDEMPOTENCY_REPLAY` (409). (c) An investor cancel racing the system NAV-publication confirmation pass on the same order serializes first-writer-wins on `Order.status`; cancel is valid only while the order remains `ACCEPTED`, and the loser receives `ERR_INVALID_STATE` (409) because the order has already moved into a terminal status. (d) Two NAV operators that simultaneously publish for the same fund and `nav_date` serialize first-writer-wins on `NavSnapshot.status`; at most one transitions to `PUBLISHED`, and the loser receives `ERR_NAV_ALREADY_PUBLISHED` (409). (e) Two clearing operators that simultaneously close the same reconciliation run serialize first-writer-wins on `ReconciliationRun.status`; at most one closes, and the loser receives `ERR_INVALID_STATE` (409). (f) Two cancel attempts on the same order serialize first-writer-wins on `Order.status`; exactly one succeeds, and the loser receives `ERR_INVALID_STATE` (409) because the order has already become `CANCELLED`.

### 2.12. The Authoritative Server Clock

Time-sensitive computations (acceptance window, cancel cutoff, T+1 NAV gating, dividend date checks, settlement timing) read from a single authoritative server clock exposed as a singleton resource with `id` `"clock"` and field `now`. The clock advances monotonically through an admin-only test-driving capability that accepts a target `now` ISO 8601 timestamp. An advance call with a `now` value at or before the current clock value is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422).

## 3. Business Logic & Workflows

### 3.1. Investor Onboarding And Cash Provisioning

A `PlatformAdmin` creates an investor record by supplying `legal_name`, `investor_type` (`INDIVIDUAL` or `INSTITUTIONAL`), `country_code` (the ISO-3166 alpha-2 code that drives sales-region restriction), `risk_tolerance` (`C1`, `C2`, `C3`, `C4`, or `C5`, with `C1` being the lowest tolerance and `C5` the highest), `tax_resident_status` (`DOMESTIC`, `FOREIGN`, or `EXEMPT`, which drives dividend tax withholding), and `bank_account_number` (used by the bank-side reconciliation pair). The new investor starts with `kyc_status` set to `PENDING` and `cash_balance_cents` set to 0. KYC approval by a `ComplianceReviewer` flips `kyc_status` from `PENDING` to `APPROVED`; until that approval has happened, no order may be submitted for this investor. A test-driving capability available to `PlatformAdmin` lets the operator credit a positive integer `amount_cents` to an investor's `cash_balance_cents`, simulating an inbound bank deposit; this is the only path through which `cash_balance_cents` increases without coming from a confirmed redemption or a cash dividend.

### 3.2. Fund Drafting, Compliance Review, And Shelf Lifecycle

Fund products go through a four-stage shelf lifecycle: `DRAFT`, `UNDER_REVIEW`, `ON_SHELF`, and either `SUSPENDED` (a temporary pause that can return to `ON_SHELF`) or `OFF_SHELF` (terminal). A `ProductOperator` drafts a fund by supplying its `fund_code` (a six-digit string matching the pattern `^[0-9]{6}$` and unique across all funds), human-readable `fund_name`, `fund_type` (one of `EQUITY`, `BOND`, `HYBRID`, `MONEY_MARKET`, or `QDII`), `risk_rating` (one of `R1`, `R2`, `R3`, `R4`, or `R5`, with `R1` lowest and `R5` highest), `allowed_country_codes` (an array of ISO-3166 alpha-2 codes; an empty array means the fund is unrestricted geographically), the three annualized fee bps inputs `management_fee_bps_annual`, `custodian_fee_bps_annual`, and `sales_service_fee_bps_annual`, the `subscription_fee_tiers` and `redemption_fee_tiers` arrays described below, the `back_end_load_enabled` boolean toggle (defaulting to false), the flat `conversion_fee_bps`, the `large_redemption_threshold_pct_bps` (defaulting to 1000 bps, i.e., ten percent of the fund's outstanding shares), and the order-size limits `min_subscription_amount_cents`, `max_subscription_amount_cents` (which may be omitted to mean unlimited), and `min_redemption_shares`. Each `subscription_fee_tier` entry carries `min_amount_cents`, `max_amount_cents` (which may be null to mean the tier is open-ended at the top), and `rate_bps`; the array must be ordered ascending by `min_amount_cents` and the tiers must not overlap. Each `redemption_fee_tier` entry carries `min_holding_days`, `max_holding_days` (which may be null to mean open-ended), and `rate_bps`; the array must be ordered ascending by `min_holding_days` and the tiers must not overlap. A submission that includes overlapping or non-ascending tiers is rejected with `ERR_FEE_TIERS_INVALID`. The tier validity check applies both at fund creation and at shelf approval, so a fund whose tiers were tampered with between drafting and approval is caught at the approval gate too.

When the operator who drafted the fund subsequently submits it for review, the fund advances `DRAFT → UNDER_REVIEW`, and the server stamps `Fund.shelf_creator_actor_id` with the submitter's `X-User-ID`, locking the creator identity for the segregation-of-duties check that follows. All required fields (`fund_code`, `fund_type`, `risk_rating`, the three fee bps, and both tier arrays) must be populated before the fund can advance out of `DRAFT`.

A `ComplianceReviewer` then approves the fund. Approval requires that the reviewer's `X-User-ID` differs from the stored `Fund.shelf_creator_actor_id` (otherwise `ERR_SOD_VIOLATION_SHELF`), and that both fee-tier arrays remain non-empty and non-overlapping. On approval, the fund advances `UNDER_REVIEW → ON_SHELF`, the reviewer's `X-User-ID` is stamped onto `Fund.shelf_review_actor_id` (locked for the subsequent NAV-publisher segregation check), and `Fund.confirmation_cycle_days` is computed from `Fund.fund_type` according to the table: `MONEY_MARKET` is 0 days, `BOND` is 1 day, `EQUITY` is 2 days, `HYBRID` is 2 days, and `QDII` is 3 days. An `AuditLog` row is written with `action` `FUND_SHELF_CHANGE` and the `from_state` / `to_state` pair `UNDER_REVIEW` / `ON_SHELF`. Symmetrically, the reviewer can reject the fund: rejection also requires the same segregation-of-duties check, advances the fund `UNDER_REVIEW → DRAFT`, clears `Fund.shelf_creator_actor_id` back to null so a different operator may resubmit, and writes an `AuditLog` `FUND_SHELF_CHANGE` row with `from_state` / `to_state` pair `UNDER_REVIEW` / `DRAFT`.

Once on shelf, the same `ComplianceReviewer` role manages the fund's operational status. Suspending an `ON_SHELF` fund advances it to `SUSPENDED` and triggers a cascade: every `Order` for this fund whose `status` is `SUBMITTED` transitions to `REJECTED` with `rejection_error_id` set to `ERR_FUND_SUSPENDED`. The fund's own `updated_at` and `version` advance, and an `AuditLog` `FUND_SHELF_CHANGE` row records the `ON_SHELF → SUSPENDED` transition. Resuming a `SUSPENDED` fund reverses the lifecycle without cascading, advancing `SUSPENDED → ON_SHELF` and writing a matching `FUND_SHELF_CHANGE` audit row. Permanent de-listing — taking the fund `OFF_SHELF` from either `ON_SHELF` or `SUSPENDED` — requires `Fund.total_outstanding_shares` to equal exactly 0, otherwise `ERR_FUND_HAS_HOLDERS` is returned; a successful de-listing writes an audit row with the corresponding `from_state → OFF_SHELF` pair. `OFF_SHELF` is terminal.

### 3.3. Order Submission, Acceptance, And Idempotency

An `Investor` submits a subscription, redemption, or conversion order through a single endpoint by supplying `fund_id`, `order_type` (`SUBSCRIBE`, `REDEEM`, or `CONVERT`), an optional `target_fund_id` (which must be present and must differ from `fund_id` for `CONVERT`, and is null for the other two), an optional `gross_amount_cents` (the investor-supplied gross cash for `SUBSCRIBE`, null for the other two), an optional `requested_shares` (the investor-supplied shares in 1e-4 share units for `REDEEM` and `CONVERT`, null for `SUBSCRIBE`), and a client-supplied `idempotency_key` that uniquely identifies this submission per investor. Server time at order creation is captured as `submitted_at`.

Idempotency is enforced on the (`investor_id`, `idempotency_key`) tuple. A repeat submission with the identical key and an identical body returns the originally created `Order` with HTTP 200; a repeat submission with the same key but a different body yields `ERR_IDEMPOTENCY_REPLAY` with HTTP 409. The system creates exactly one `Order` per tuple regardless of how many concurrent submissions arrive.

When the order passes idempotency, the server runs synchronous acceptance validation in a single atomic transition from `SUBMITTED` to `ACCEPTED`. All of the following must hold: the source `Fund.status` equals `ON_SHELF`, the `Investor.kyc_status` equals `APPROVED`, the suitability index test holds (the investor's `risk_tolerance` index is at least the fund's `risk_rating` index, where `C1`<`C2`<`C3`<`C4`<`C5` and `R1`<`R2`<`R3`<`R4`<`R5`, so an `R3` fund admits a `C3`, `C4`, or `C5` investor but rejects a `C1` or `C2`), the fund's `allowed_country_codes` array either is empty or contains the investor's `country_code`, and the order's amount or share input falls within the fund's per-order limits — for `SUBSCRIBE`, `gross_amount_cents` must lie in the inclusive range from `min_subscription_amount_cents` up to `max_subscription_amount_cents` (unlimited if that field is null); for `REDEEM`, `requested_shares` must be at least `min_redemption_shares`; for `CONVERT`, the same minimum-share rule applies on the source side and the target fund must also be `ON_SHELF` and pass the suitability check for the investor. A `SUBSCRIBE` additionally requires that the investor's `cash_balance_cents` be at least the order's `gross_amount_cents` (the cash is conceptually reserved at acceptance), and a `REDEEM` or `CONVERT` requires that the investor's `Holding.shares` for the source fund be at least `requested_shares`. If any check fails, the order is captured with `status` `REJECTED` and the corresponding error id is stored on `Order.rejection_error_id`. If every check passes, the order's `trade_date` is assigned by the acceptance-window rule, `confirm_date` is set to `trade_date` plus the fund's `confirmation_cycle_days` measured in calendar days, `status` becomes `ACCEPTED`, and an `AuditLog` row with `action` `ORDER_STATUS_CHANGE` and `from_state`/`to_state` pair `SUBMITTED` / `ACCEPTED` is written. (When validation fails, the matching audit row records the `SUBMITTED → REJECTED` pair instead.)

The acceptance-window rule that sets `trade_date` is a single 15:00 UTC cutoff applied to `submitted_at`. Form the cutoff as the calendar date of `submitted_at` combined with 15:00 UTC. If `submitted_at` is strictly before that cutoff instant, `trade_date` is the calendar date of `submitted_at`. If `submitted_at` is at or after the cutoff (the boundary at exactly 15:00 inclusive shifts to next day), `trade_date` is the calendar date of `submitted_at` plus one calendar day. The system uses calendar days throughout; there is no business-day calendar.

An `Investor` may cancel an `ACCEPTED` order — but only if the server clock is strictly before the order's `trade_date` combined with 15:00 UTC, otherwise `ERR_CANCEL_WINDOW_CLOSED`. Cancel by anyone other than the investor who owns the order is rejected (the `X-User-ID` must equal `Order.investor_id`). A successful cancel advances the order `ACCEPTED → CANCELLED`, refreshes its `updated_at` and `version`, and writes an `AuditLog` `ORDER_STATUS_CHANGE` row for the `ACCEPTED → CANCELLED` pair.

### 3.4. NAV Publication, Confirmation Cascade, And Adjustment

Each trade date's net-asset-value snapshot is published exactly once on T+1. A `NavOperator` initiates publication by supplying the `nav_date` being valued, the custodian-attested `portfolio_market_value_cents` for end-of-T-day, and the `portfolio_accrued_income_cents` (bond coupons and dividend receivables) for the same day. Three preconditions must hold: the operator's `X-User-ID` must differ from the fund's `Fund.shelf_review_actor_id` (otherwise `ERR_SOD_VIOLATION_NAV`), the server clock must be at or after `nav_date` plus one calendar day (the T+1 rule, otherwise `ERR_NAV_T_PLUS_1_NOT_ELAPSED`), and all input fields must be supplied. The publication is one-shot: a second publish attempt for the same fund and `nav_date` after a `NavSnapshot` already exists in `PUBLISHED` status is rejected with `ERR_NAV_ALREADY_PUBLISHED`.

The NAV per share computation runs in this pinned order. First, gross assets in cents is the sum of `portfolio_market_value_cents` and `portfolio_accrued_income_cents`. Second, the three daily fee accruals are each computed as the daily-prorated bps charge against gross assets: `management_fee_accrued_cents` is the gross-assets value multiplied by the fund's `management_fee_bps_annual`, divided by 10,000 (the basis-point denominator), divided by 365 (days per year), and rounded half-up at cents; `custodian_fee_accrued_cents` follows the same formula with `custodian_fee_bps_annual`; `sales_service_fee_accrued_cents` follows the same formula with `sales_service_fee_bps_annual`. Third, `net_assets_cents` is the gross assets minus the three accrued fees (each already rounded). Fourth, `shares_outstanding_at_nav` is the snapshot of `Fund.total_outstanding_shares` at T-day end. Fifth, when `shares_outstanding_at_nav` equals 0, `nav_per_share_micros` is the initial NAV constant 1,000,000 (i.e., one CNY per share). Otherwise, `nav_per_share_micros` is computed as `net_assets_cents` multiplied by 100,000,000 then divided by `shares_outstanding_at_nav`, with the final result rounded half-up at micros. The intermediate NAV value is held as `gross_assets_cents` on the snapshot together with the three fee accrual fields, the resulting `net_assets_cents`, and the chosen `shares_outstanding_at_nav`.

A successful publication writes the snapshot with `status` `PUBLISHED`, sets `published_at` to the server clock at publication time, and writes an `AuditLog` `NAV_PUBLISHED` row with the `PROVISIONAL → PUBLISHED` pair. Publication then triggers a confirmation pass over every `ACCEPTED` order whose `trade_date` equals the just-published `nav_date` and whose `confirm_date` has been reached on the server clock. Each such order is evaluated; for `REDEEM` orders, the large-redemption test runs first — the order's `large_redemption_pct_bps` is computed as `requested_shares` multiplied by 10,000 divided by `Fund.total_outstanding_shares` at trade-date end, rounded half-up to integer bps. When that ratio is at or above the fund's `large_redemption_threshold_pct_bps` (the boundary is inclusive: equality triggers deferral), the order moves `ACCEPTED → LARGE_REDEMPTION_DEFERRED` instead of confirming, the computed `large_redemption_pct_bps` is captured on the order, and `Order.confirm_date` is pushed forward by exactly one calendar day so that the deferred order will be re-evaluated against the next NAV publication. An `AuditLog` `ORDER_STATUS_CHANGE` row records the `ACCEPTED → LARGE_REDEMPTION_DEFERRED` pair. When the next NAV publication arrives and the new `confirm_date` has been reached on the server clock, the deferred order advances `LARGE_REDEMPTION_DEFERRED → CONFIRMED` using the deferred trade date's NAV.

For `REDEEM` orders below the threshold and for all other order types, confirmation runs from `ACCEPTED → CONFIRMED` directly. The order's `confirmed_nav_per_share_micros` is set to the snapshot's `nav_per_share_micros`, fees and amounts are computed (see §3.5), and the cascade follows: for `SUBSCRIBE`, a new `LotEntry` is created with `holding_id` referencing the investor's holding for the fund, `order_id` referencing the originating `Order`, that lot's `shares` and `cost_cents` (the post-fee net amount), `acquired_at` set to the confirmation date, and `status` `OPEN`; the investor's `Holding.shares` and `Holding.cost_basis_cents` are recomputed by re-aggregating the open lots; `Fund.total_outstanding_shares` is increased by the confirmed shares; and the investor's `cash_balance_cents` is decreased by the order's `gross_amount_cents`. For `REDEEM`, lots are consumed FIFO (oldest `acquired_at` first), each affected lot's `shares` decreases by the consumed take and its `cost_cents` decreases proportionally, lots whose `shares` reach zero flip `OPEN → DEPLETED`, the investor's `Holding.shares` and `Holding.cost_basis_cents` are recomputed, `Fund.total_outstanding_shares` decreases by the confirmed shares, and the investor's `cash_balance_cents` is increased by `confirmed_amount_cents` (the net redemption proceeds). For `CONVERT`, the source fund's lots are FIFO-burned exactly as in the redeem path, and a new `LotEntry` is created against the target fund with the proceeds (a cross-aggregate hop); the `Holding` and `total_outstanding_shares` aggregates of both source and target funds are recomputed. Every aggregate touched by the cascade has its `updated_at` refreshed and `version` incremented, and one `AuditLog` `ORDER_STATUS_CHANGE` row is written per order transition.

A published NAV may be adjusted later by a `ComplianceReviewer`, who supplies the corrected `portfolio_market_value_cents`, `portfolio_accrued_income_cents`, and a non-empty `adjustment_reason`. The snapshot recomputes through the same NAV formula, transitions `PUBLISHED → ADJUSTED`, and writes an `AuditLog` `NAV_ADJUSTED` row. To preserve dividend integrity, an adjustment is forbidden when any `DividendPlan` whose `ex_dividend_date` equals the snapshot's `nav_date` is currently in `EX_DIVIDEND` or `PAID` status (otherwise `ERR_INVALID_STATE`).

### 3.5. Fee Calculation: Front-End, Back-End, Redemption, And Conversion

Subscription fees vary with the fund's `back_end_load_enabled` toggle. When the toggle is false (front-end model), the server first locates the applicable subscription tier by walking `subscription_fee_tiers` in ascending order until it finds the first tier whose `min_amount_cents` is at most `gross_amount_cents` and whose `max_amount_cents` is either null or strictly greater than `gross_amount_cents`. The chosen tier's `rate_bps` produces `subscription_fee_cents` as `gross_amount_cents` multiplied by `rate_bps`, divided by 10,000, rounded half-up at cents. The net amount available for share minting is `gross_amount_cents` minus `subscription_fee_cents`, and `confirmed_shares` is the net amount multiplied by 100,000,000 then divided by the confirmation NAV (`nav_per_share_micros`), rounded half-up at the 1e-4 share unit. When `back_end_load_enabled` is true (back-end model), `subscription_fee_cents` is 0 at confirmation and `confirmed_shares` is `gross_amount_cents` multiplied by 100,000,000 divided by the confirmation NAV, rounded half-up at the 1e-4 share unit; the back-end fee is deferred and collected at the eventual redemption. For both variants, `confirmed_amount_cents` equals the original `gross_amount_cents` — that is the cash the investor's account is actually debited. The same gross amount produces strictly more shares under the back-end variant than under the front-end variant because no fee is removed from the net before share minting. Pinned rounding order: fee first (when applicable), then net, then shares.

Redemption fees are computed FIFO over the investor's `OPEN` lot entries in the fund, sorted by `acquired_at` ascending. The redemption first computes a gross redemption amount in cents as `requested_shares` multiplied by `nav_per_share_micros` divided by 100,000,000, rounded half-up at cents. It then walks the lots in order, drawing `take` shares from each lot equal to the smaller of that lot's remaining `shares` and the still-needed redemption shares. For each lot consumed, `holding_days` is computed as the floor of the calendar-day difference between the order's `trade_date` and the lot's `acquired_at`. The redemption tier for that lot is the first entry of `redemption_fee_tiers` (in ascending `min_holding_days` order) whose `min_holding_days` is at most `holding_days` and whose `max_holding_days` is either null or strictly greater than `holding_days`. The lot's amount is `take` multiplied by `nav_per_share_micros` divided by 100,000,000, rounded half-up at cents; the lot's fee is the lot amount multiplied by the chosen tier's `rate_bps` divided by 10,000, rounded half-up at cents. Per-lot fees are rounded *first* and then summed, never sum-then-round; the resulting sum is `redemption_fee_cents`. When the fund's `back_end_load_enabled` is true, each lot also accrues a back-end load equal to that lot's proportional original cost — `cost_cents` multiplied by `take` divided by the lot's original `shares`, rounded half-up at cents — multiplied by the subscription-tier `rate_bps` whose tier the lot's proportional cost falls into (looked up against `subscription_fee_tiers` using the same band-test logic as the subscription path), with each per-lot back-end load rounded half-up at cents and then summed into `back_end_load_fee_cents`. When the fund is not back-end-loaded, `back_end_load_fee_cents` is 0. The order's `confirmed_amount_cents` is the gross redemption amount minus `redemption_fee_cents` minus `back_end_load_fee_cents`, and `confirmed_shares` equals the original `requested_shares`. The back-end load is computed against the lot's *original* cost basis, not against its current value.

For a `CONVERT` order, the source-side burn follows the same FIFO redemption path described above — the source fund's redemption tier and (where enabled) back-end load are applied — and additionally a `conversion_fee_cents` is charged equal to the source-side gross redemption amount multiplied by the source fund's `conversion_fee_bps`, divided by 10,000, rounded half-up at cents. The net proceeds (gross minus redemption fee minus back-end load minus conversion fee) feed the target fund's lot creation under that fund's confirmation NAV. The pinned rounding order on every fee path is: per-lot rounding first, then sum.

### 3.6. Dividend Lifecycle: Announcement, Ex-Dividend Snapshot, Payment

A `ProductOperator` announces a dividend plan against an `ON_SHELF` fund by supplying `announcement_date`, `record_date`, `ex_dividend_date`, `payment_date`, `dividend_per_share_micros` (the gross dividend per share in micros), `tax_rate_bps_domestic` (the withholding rate in bps applied to gross dividend for `DOMESTIC` investors), and `tax_rate_bps_foreign` (the same for `FOREIGN` investors). The four dates must satisfy `record_date >= announcement_date`, `ex_dividend_date == record_date + 1` calendar day, and `payment_date >= ex_dividend_date`; any deviation yields `ERR_DIVIDEND_DATE_INVALID`. The plan is created in status `ANNOUNCED`.

When the server clock has reached or passed the date portion of `ex_dividend_date` and the fund's status is `ON_SHELF`, marking ex-dividend transitions the plan `ANNOUNCED → EX_DIVIDEND`. The transition snapshots, for each investor whose `Holding.shares` for the fund is greater than zero at record-date end, a `DividendDistribution` row populated with `dividend_plan_id`, `investor_id`, the `eligible_shares` snapshot (the `Holding.shares` at record-date end, in 1e-4 share units), and the computed `gross_dividend_cents`, `tax_withheld_cents`, and `net_dividend_cents`. Gross dividend in cents for an investor is `eligible_shares` multiplied by `dividend_per_share_micros`, divided by 100,000,000, rounded half-up at cents. Tax withholding depends on the investor's `tax_resident_status`: `EXEMPT` produces `tax_withheld_cents` 0; `DOMESTIC` produces `tax_withheld_cents` equal to `gross_dividend_cents` multiplied by `tax_rate_bps_domestic`, divided by 10,000, rounded half-up at cents; `FOREIGN` produces the same with `tax_rate_bps_foreign`. The pinned rule is that tax is computed *from the gross*, not from the net. Net dividend is gross minus tax. Each created row defaults its `option` to `CASH` and `reinvested_shares` to 0. An `AuditLog` `DIVIDEND_EXECUTED` row records the `ANNOUNCED → EX_DIVIDEND` pair.

Between ex-dividend and payment, an `Investor` may set the distribution `option` to `CASH` or `REINVEST` for the row tied to that investor. Once payment_date has been reached on the server clock and the NAV snapshot for the plan's `ex_dividend_date` is `PUBLISHED`, a `NavOperator` executes payment, transitioning the plan `EX_DIVIDEND → PAID`. The cascade per distribution row depends on `option`: when `option` is `CASH`, the investor's `cash_balance_cents` is increased by `net_dividend_cents`; when `option` is `REINVEST`, `reinvested_shares` is computed as `net_dividend_cents` multiplied by 100,000,000 divided by the ex-dividend-date NAV's `nav_per_share_micros`, rounded *half-down* at the 1e-4 share unit (specifically half-down so that no over-issuance occurs), and a new `LotEntry` is created with that `shares` count, `cost_cents` equal to `net_dividend_cents`, `acquired_at` set to the ex-dividend date, and `status` `OPEN`; the investor's `Holding.shares` and `Holding.cost_basis_cents` are recomputed; and `Fund.total_outstanding_shares` increases by the reinvested shares. Each cascade hop refreshes the touched aggregate's `updated_at` and `version`. An `AuditLog` `DIVIDEND_EXECUTED` row records the `EX_DIVIDEND → PAID` pair.

A `ComplianceReviewer` may cancel a plan that is still in `ANNOUNCED` status as long as the server clock is strictly before `ex_dividend_date`; the plan transitions `ANNOUNCED → CANCELLED` (a terminal state alongside `PAID`), no holdings cascade is performed, and an `AuditLog` `DIVIDEND_EXECUTED` row records the `ANNOUNCED → CANCELLED` pair.

### 3.7. Reconciliation, Exception Resolution, And Settlement Dispatch

A `ClearingOperator` opens a reconciliation run for an `as_of_date` and a `scope` selecting which counterparty pair the run covers (`TA_VS_CUSTODIAN`, `TA_VS_CHANNEL`, or `TA_VS_BANK`), supplying an array of `external_records` attested by the counterparty for the as-of date. Each external record carries a `ref_id` that matches the `id` of an `Order` or `DividendDistribution`, plus a `side`, an `amount_cents`, and a `shares` count. The run starts in status `OPEN` and stamps the operator as the run's creator for the closer-segregation check.

Running the match compares the internal SETTLED ledger entries for the run's scope and `as_of_date` against the supplied `external_records` and updates the run's `total_internal_amount_cents`, `total_external_amount_cents`, and `net_break_cents` (the signed difference, internal minus external). When every internal SETTLED record matches one external record one-to-one (amounts equal, and shares equal where shares apply) and there are no unmatched records on either side, the run transitions `OPEN → RESOLVED` directly with `net_break_cents` equal to 0. Otherwise the run transitions `OPEN → EXCEPTIONS_FOUND`, and one `ReconciliationException` row is created per discrepancy with the appropriate `kind` selected from `MISSING_INTERNAL` (an external record with no matching internal entry), `MISSING_EXTERNAL` (an internal entry with no matching external record), `AMOUNT_MISMATCH` (matched records with different `amount_cents`), or `SHARE_MISMATCH` (matched records with different `shares`). For each exception, `internal_amount_cents` is null when `kind` is `MISSING_INTERNAL` and otherwise carries the internal value; `external_amount_cents` is null when `kind` is `MISSING_EXTERNAL` and otherwise carries the external value. Each exception starts in `resolution_status` `OPEN`.

The clearing operator then resolves each exception. Adjusting an exception requires the parent run's status to be `EXCEPTIONS_FOUND` and a non-null `adjustment_amount_cents` supplied; the exception transitions `OPEN → ADJUSTED`, and the parent run's `net_break_cents` is updated by the adjustment delta (the adjustment amount represents the correction added to the internal side). Waiving an exception likewise requires the parent run to be `EXCEPTIONS_FOUND`, but is forbidden when the exception's `kind` is `AMOUNT_MISMATCH` (otherwise `ERR_WAIVE_NOT_ALLOWED`); a waive transitions `OPEN → WAIVED`, is logged for auditability, and does not affect `net_break_cents` — that asymmetry is the reason amount mismatches must be fixed by adjustment rather than by waiver.

Finalizing the run requires every exception to be in `ADJUSTED` or `WAIVED` and the conserved-quantity invariant to hold: the original `net_break_cents` (as observed at the moment the run first found exceptions) minus the sum of `adjustment_amount_cents` across all `ADJUSTED` exceptions must equal exactly 0 (using exact integer arithmetic, no rounding). When that holds, the run advances `EXCEPTIONS_FOUND → RESOLVED`. When it does not, the finalize is rejected with `ERR_RECONCILIATION_INVARIANT_BROKEN`. `WAIVED` exceptions deliberately do not contribute to the adjustment sum, which is what forces `AMOUNT_MISMATCH` exceptions to take the adjustment path.

Closing the run dispatches downstream. The closer's `X-User-ID` must differ from the run's recorded creator (otherwise `ERR_SOD_VIOLATION_RECON`). On success, the run transitions `RESOLVED → CLOSED`, one `SettlementInstruction` row is generated per net position to be settled (each row carrying its parent `reconciliation_run_id`, a `target_system` selected from `BANK`, `CUSTODIAN`, `TA`, or `REGULATOR`, an `instruction_type` of `DEBIT`, `CREDIT`, `TRANSFER`, or `REPORT`, the `amount_cents` to settle, and a `dispatched_at` stamped at emit time), and an `AuditLog` `RECONCILIATION_RESOLVED` row records the `RESOLVED → CLOSED` pair. The same closure also emits remote synchronization events to the four downstream systems for bank, custodian, TA, and regulatory consumers.

### 3.8. Audit Log Retrieval And Test-Driving Capabilities

Every state transition described above writes an `AuditLog` row. Compliance and platform-administration roles can query the log filtered by `action` (one of `ORDER_STATUS_CHANGE`, `NAV_PUBLISHED`, `NAV_ADJUSTED`, `DIVIDEND_EXECUTED`, `RECONCILIATION_RESOLVED`, `FUND_SHELF_CHANGE`), by `subject_entity` (the entity name affected), and by `subject_id` (the id of the affected entity), with pagination via `limit` and `offset`. Each row records `actor_user_id`, `actor_role`, the `action`, the `subject_entity` and `subject_id`, the `from_state` and `to_state` strings (which capture either the prior/new state values for state machines or the prior/new numeric strings for adjustments), and a free-form `payload_json` that carries deltas, reasons, and any other structured context relevant to the action.

For deterministic tests, the system exposes an admin-only test-driving capability that advances the authoritative server clock to a supplied `now` ISO 8601 timestamp; the clock is monotonic and any advance whose `now` is at or before the current `Clock.now` is rejected with `ERR_CLOCK_NOT_MONOTONIC`. A separate read of the clock returns the current `now` to any authorized role.
