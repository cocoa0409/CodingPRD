# Refurbished Device Marketplace — Seller Grading & Warranty Administration API — Product Requirements Document

## 1. Introduction

A refurbished-device marketplace lives or dies on one promise: that a device advertised as `GOOD` with 88% battery health really is one, and that when it is not, somebody pays. This document specifies the API that underwrites that promise end to end. It covers the onboarding of the businesses that refurbish the devices, the on-site audits that certify their processes, the grading definitions that convert a scratch score and a diagnostic pass rate into a defensible `FLAWLESS`/`GOOD`/`FAIR`/`POOR` label, and the mystery-shop programme that checks whether sellers actually honour the labels they sell under.

The commercial heart of the system is the warranty reservation and the seller exposure floor. Every listed device carries a reservation, every buyer claim opens an obligation against the seller of record, and the marketplace tracks how much live warranty exposure each seller is carrying so that it can price buy-box placement and, when a seller's conduct is bad enough, suspend its catalogue. Because the actors here have conflicting incentives, the specification is deliberately heavy on segregation of duties, blocklists, and immutability: a seller may not overwrite the identity of the seller that originally put a device on the market, an auditor may not rubber-stamp the listing of the seller it audited, and a claim's routed seller may never be reassigned.

Finally, the platform operates a trade-in channel that prices devices it buys *into* the refurbishment pool. That channel has its own pricing engine, its own intranet inspection step, its own post-inspection revision rules, and its own auto-rejection deadline handling. All time-dependent behaviour in the whole system is evaluated against a single logical clock rather than wall-clock time, so that periodic scoring sections, warranty expiries and acceptance windows can all be driven deterministically.

## 2. Global Specifications & System-Wide Principles

This section collects the rules that bind every endpoint of the API: who may call it, what a response looks like, and the invariants that no workflow may violate.

### 2.1. User and Role-Based Access Control

Every request that requires credentials must carry two HTTP headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the capacity in which the principal acts. A request that omits either header on an endpoint that requires credentials is refused with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is not listed against the target endpoint is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403); the same code covers a role that is barred from the operation by the segregation-of-duties matrix described in §2.9, and the narrower `ERR_SOD_VIOLATION` (also HTTP 403) is raised in the specific barring cases enumerated there.

The marketplace recognises eight roles, spelled exactly as follows: `PlatformAdmin`, `ComplianceReviewer`, `ClaimAdjudicator`, `TradeInInspector`, `Seller`, `Consumer`, `System`, and `Anonymous`.

Identity resolution differs by role. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it where a scaffold transition writes an operator identifier, but it does not compare it to any entity's `id`. The same is true of `ComplianceReviewer`, `ClaimAdjudicator`, `TradeInInspector`, `Consumer`, `System` and `Anonymous` — all six of these are opaque operator or caller identifiers, and none is matched against a persisted row.

The one exception is `Seller`. When `X-User-Role` is `Seller`, `X-User-ID` is the `id` of the acting `Seller`; ownership checks on any resource that references a `Seller` compare the resource's foreign-key field — `seller_id` on a listing — to `X-User-ID`. `Anonymous` exists solely as the actor marker on the two endpoints that admit no credentials at all (seller registration and trade-in submission); it holds no exclusive or shared operations.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list-bearing endpoint accepts `limit` and `offset` as query parameters. `limit` caps how many items are returned, defaults to 10, and is constrained to a minimum of 1 and a maximum of 100; a value outside that range is a malformed request. `offset` selects how many items to skip and defaults to 0. Unless a rule elsewhere in this document says otherwise, list responses are ordered by creation timestamp ascending, and the `meta` block of a list response carries `limit`, `offset`, `total_count`, and `has_more` alongside the standard `api_request_id` and `api_request_timestamp`.

Individual list endpoints accept narrowing filters in addition to the pagination pair. Seller lists may be narrowed by `onboarding_state`, by `performance_tier`, and by `latest_score_id`. Listing lists may be narrowed by `listing_state`, by `model_code`, by `servicing_seller_id`, and by `servicing_reservation_id`. Verification lists may be narrowed by `seller_id`, by `listing_id`, and by `verification_state`. Reservation lists may be narrowed by `warranty_state` and by `originated_claim_id`. Claim lists may be narrowed by `routed_seller_id`, by `claim_state`, by `resolution_type`, and by `replacement_listing_id`. Grading-definition lists may be narrowed by `definition_state`; trade-in lists by `submission_state`; and service-score lists by `seller_id` and by `section_state`. All filters are optional.

### 2.4. Common Resource Properties, the Logical Clock, and Mutation Semantics

Every top-level resource in this API — `Seller`, `SellerAuditRecord`, `DeviceListing`, `MysteryShopVerification`, `WarrantyReservation`, `WarrantyClaim`, `SellerServiceScore`, `TradeInSubmission`, and `GradingDefinition` — carries the same four system-managed properties. `id` is a server-minted UUID string with no type prefix. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording first persistence. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits recording the last modification. `version` is a system-managed integer that increments by exactly one on every mutation of the row, including mutations performed by cascades rather than by direct client request, and is the basis of the optimistic concurrency checks in §2.10. No entity in this system is configured to omit `updated_at` or `version`; all nine carry the full common set.

That three-fractional-digit rendering is a property of every instant the API persists or returns, not of the two common fields alone: `activated_on`, `expired_on`, `acceptance_deadline`, `section_opened_on`, `section_closed_on`, `audit_scheduled_for`, `verification_start`, `verification_end`, `effective_from` and `retired_on` all carry the same `...Z` shape with exactly three fractional digits. An instant supplied by a client is parsed and re-rendered into that shape rather than echoed back verbatim.

All time-dependent behaviour is evaluated against a mutable logical clock, exposed through an administrative test-driving capability and described in §3.9. The clock starts fixed at `2026-09-01T00:00:00Z` and never falls back to wall-clock time. Section windows, warranty expiries, acceptance deadlines, and validity checks on scheduled instants are all evaluated against this clock rather than against the host's system time.

### 2.5. Seller Identity, Service of Record, and Ownership Boundaries

A `DeviceListing` distinguishes two seller references, and the distinction is load-bearing. The `serving_seller_id` is set from the submitting `seller_id` when the listing is created and is thereafter immutable; it names the seller that originally placed the device on the market and must never be overwritten when the servicing relationship changes. The `servicing_seller_id` is the seller currently responsible for warranty servicing the device; it also starts equal to `seller_id` at creation, but it changes as warranty returns are routed, and the buy-box and claim-routing logic reads it when deciding who funds an outcome.

`WarrantyClaim.routed_seller_id` is likewise a pinned pointer. It is null while a claim is merely `FILED`, and it is pinned to the listing's `servicing_seller_id` at the moment the claim first enters `UNDER_REVIEW`. From that point the binding is immutable: a claim whose `routed_seller_id` differs from the value it carried when it entered `UNDER_REVIEW` is refused with `ERR_ROUTED_SELLER_IMMUTABLE` (HTTP 422), and that rule guards both the return-routing capability and the adjudication capability. A `Seller`'s own state is summarised by `onboarding_state` (`APPLICANT`, `DOCUMENT_VERIFIED`, `AUDIT_SCHEDULED`, `APPROVED`, `REJECTED`), `performance_tier` (`ELITE`, `STANDARD`, `PROBATION`, `SUSPENDED`), `latest_score_id` (the most recent closed service-score section, which may legally be null when none has been finalised), `exposure_floor_cents`, `suspension_trigger_count`, and `blocklisted`.

### 2.6. Grading Definition Binding and Effective-Dated Policy

Marketplace grading policy is versioned through `GradingDefinition`. A definition carries `definition_state` (`DRAFT`, `ACTIVE`, `RETIRED`), `cosmetic_thresholds` (a mapping whose keys must be exactly `FLAWLESS`, `GOOD`, `FAIR`, `POOR`, each giving the minimum accepted scratch score for that grade), `functional_thresholds` (a mapping whose keys must be exactly `FULLY_FUNCTIONAL`, `MINOR_FAULTS`, `MAJOR_FAULTS`, each giving the minimum accepted diagnostic pass rate), `battery_floor_pct` (the minimum battery health a device may carry and still be graded at all, between 1 and 100 inclusive), `effective_from` (the instant from which a definition becomes binding for listings submitted after it), `retired_on` (null while the definition is `DRAFT` or `ACTIVE`), and `binding_definition_id`. Creating a draft definition requires a `definition_code` alongside the threshold mappings, the floor and the effective date. Retiring a definition carries a `retirement_note` describing the reason. Activation and reinstatement each accept an optional `expected_definition_version` when the caller wishes to guard against re-activating a definition it has not re-read.

The binding rule is capture-once. When a listing enters `UNDER_REVIEW`, the server records the identifier of whichever `GradingDefinition` was `ACTIVE` at that instant on the listing's review record, and that captured value is never re-resolved afterwards. The review decision then re-checks that the captured definition is *still* `ACTIVE`; if it has since been retired, the decision is refused with `ERR_GRADING_DEFINITION_NOT_ACTIVE` (HTTP 409). Publishing a definition — that is, moving one from `DRAFT` to `ACTIVE` — sets `binding_definition_id` to its own `id` and re-flags every listing currently `UNDER_REVIEW` that was bound to the previously `ACTIVE` definition, because those listings must be re-reviewed against the new policy.

### 2.7. The Warranty Exposure Ledger

`Seller.exposure_floor_cents` is the marketplace's running estimate of the warranty exposure a seller is carrying. It is rebuilt from two additive terms and is defined as the greater of zero and the sum of the seller's constraint exposure and its carried repair exposure. The constraint term expresses marketplace risk appetite, not money already spent; the repair term is a per-day amortisation of live warranty commitments. It is recomputed on section close, on a disclosure against one of the seller's listings, when a claim acquires evidence, when a return is routed, and when a reservation is remediated. `Seller.suspension_trigger_count` tallies the suspension transitions that section scoring drives, and it is never raised by blocklisting. It is incremented by the suspension transition that fires on section close when a closed section's recomputed score has breached the suspension threshold, and equally by the §3.9 transition that fires when a component-source change recomputes an `OPEN` section to or below that threshold — the same transition that also flips the seller's state, so a seller suspended by an open-section recompute has its count raised by that act rather than only by some later close.

A seller's reserve for approved-but-unresolved claims is exposed on the exposure read as `reserved_claim_cents`, and consumers of this API should note that it is *not* netted out of the published floor — an approved claim that has not yet been resolved remains a live obligation, so subtracting it would understate the seller's position.

### 2.8. Monetary Precision and Rounding Discipline

All monetary quantities in this API are integer cents. There are no fractional cents anywhere in storage or in a response body. Where a computation produces a fractional intermediate, the rounding method is round-half-up and the rounding point is pinned per calculation, because where a rounding is applied is as much a part of the specification as whether it rounds at all: several of the calculations below specify a per-item rounding followed by a sum, and an implementation that sums the raw values and rounds once at the end will produce a different total whenever two items' fractional parts cross the halfway point together. The service score and its four percentage components carry two decimal places, also round-half-up, and the tier and suspension thresholds compare against the rounded value — a score of exactly 55.00 breaches the suspension threshold and 55.01 does not.

### 2.9. Segregation of Duties and Operator Barring

Two barring rules are enforced against the acting operator identifier. An auditor who recorded the outcome of a seller's refurbishment process audit may not record the review decision on a listing belonging to that same audited seller. An operator who recorded the diagnostic evidence on a claim may not adjudicate that same claim. Both are refused with `ERR_SOD_VIOLATION` (HTTP 403), and both checks are evaluated after the general role check of §2.1, so a caller lacking the role outright sees `ERR_FORBIDDEN_ROLE` rather than the duty-separation code.

### 2.10. Optimistic Concurrency Control

Two write operations in this system are guarded by an optimistic concurrency check against the parent seller's version. Re-submitting a listing for review, and closing a service-score section, each carry a non-optional `expected_seller_version` input field in the request body. When the supplied value does not equal the referenced seller's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412). These two operations are the only ones governed by the version-check mechanism; the other action endpoints do not take a version field of this kind, and the optional version-shaped inputs that appear on some other endpoints are documented where the relevant workflow is described.

The reason the seller's version is the currency of freshness for these two operations is that a seller's version legitimately advances for reasons invisible to a client watching the listing: a closed service-score section remaps `performance_tier`, and an exposure-floor recompute mutates the seller row. A client holding a pre-recompute view of the seller is stale even though no listing field it can see has changed, so the seller's version, not the listing's, is the correct freshness token for a re-submission.

### 2.11. Validation Precedence and Nested Retrieval

Validations are evaluated in a fixed priority order, and the order is observable because a request that violates two rules reports the higher-priority error. Priority 1 is the credential check described in §2.1 (`ERR_UNAUTHENTICATED`, 401). Priority 2 is request-shape validation — every required input field present and type-conformant, every enum-valued field carrying a declared member, every numeric field inside its declared range (`ERR_INVALID_REQUEST`, 400). Priority 3 is the role check against the endpoint's authorised set, including existence of the backing entity for entity-backed roles (`ERR_FORBIDDEN_ROLE`, 403). Priority 4 is path-resource existence, validated left to right so that a non-existent parent identifier fails before the child identifier is examined (`ERR_RESOURCE_NOT_FOUND`, 404). Priority 5 is foreign-key resolution for body-supplied references — `seller_id`, `listing_id`, `originated_claim_id`, and `replacement_listing_id` must each resolve to an existing row (`ERR_REFERENCED_ENTITY_NOT_FOUND`, 404).

The business-safety band follows: blocklist screening of the device IMEI (`ERR_DEVICE_BLOCKLISTED`, 422) at priority 6; the battery floor (`ERR_BATTERY_BELOW_FLOOR`, 422) at 7; the uninsurable post-inspection battery measurement (`ERR_INSPECTION_BATTERY_UNINSURABLE`, 422) at 8; counterfeit price-pattern screening (`ERR_COUNTERFEIT_PRICE_SIGNAL`, 422) at 9; part-provenance documentation (`ERR_PART_PROVENANCE_UNDOCUMENTED`, 422) at 10; model-catalogue eligibility (`ERR_MODEL_NOT_ELIGIBLE`, 422) at 11; and seller approval standing (`ERR_SELLER_NOT_APPROVED`, 422) at 12. The referential band follows: routed-seller immutability (`ERR_ROUTED_SELLER_IMMUTABLE`, 422) at 13, and diagnostic-evidence completeness (`ERR_DIAGNOSTIC_EVIDENCE_REQUIRED`, 422) at 14. Temporal scheduling conflicts occupy 15 and 16, with return-slot collision (`ERR_RETURN_SLOT_COLLISION`, 409) evaluated before verification-window overlap (`ERR_VERIFICATION_OVERLAP`, 409). State checks occupy 17 through 19 in the order `ERR_INVALID_STATE` (409), then the terminal-state check `ERR_CLAIM_TERMINAL` (409), then the already-upheld check `ERR_CLAIM_ALREADY_UPHELD` (409); the ordering of the last two matters because a terminal claim and an approved-but-unrouted claim are both non-mutable, and the code tells the caller which situation it is in. Duty separation (`ERR_SOD_VIOLATION`, 403) is priority 20, deliberately after the state band.

The fiscal and governance band closes the catalogue at priorities 21 to 23: the resolution cap check `ERR_OBLIGATION_EXCEEDS_CAP` (422), then the blocklist trigger ceiling `ERR_TRIGGER_CEILING_REACHED` (422), then the human-review floor `ERR_HUMAN_REVIEW_REQUIRED` (422). Priority 24 is the stale-version check of §2.10 (`ERR_STALE_VERSION`, 412). Priority 25 is reservation-selector exhaustion (`ERR_RESERVATION_NOT_FOUND`, 404), priority 26 duplicate audit booking (`ERR_AUDIT_ALREADY_SCHEDULED`, 409), priority 27 double blocklisting (`ERR_SELLER_ALREADY_BLOCKLISTED`, 409), priority 28 a too-young scoring section (`ERR_SECTION_TOO_YOUNG`, 409), priority 29 IMEI reuse (`ERR_IMEI_ALREADY_LISTED`, 422), priority 30 a lapsed grading binding (`ERR_GRADING_DEFINITION_NOT_ACTIVE`, 409), and priority 31 withdrawal blocked by an open claim or a repairing reservation (`ERR_WITHDRAW_BLOCKED_BY_OPEN_CLAIM`, 409).

For nested retrieval the left-to-right rule deserves emphasis: a request carrying two identifiers in its path is rejected immediately against the *first* identifier that does not resolve, so a child-scoped request under a non-existent parent reports the parent's absence and never reaches the child lookup.

### 2.12. Governance Safeguards: Blocklists, Capacity, and Trigger Ceilings

Two blocklists — a stolen-device list and a counterfeit list — are consulted whenever an IMEI is submitted or re-submitted. A seller may be blocklisted only while `blocklisted` is false, and only with a `finding` of `CONFIRMED_COUNTERFEIT` or `CONFIRMED_STOLEN`; a second blocklisting attempt is refused with `ERR_SELLER_ALREADY_BLOCKLISTED` (409). Blocklisting is further gated by the seller's `suspension_trigger_count`: at or above the ceiling of 99 the blocklisting is refused with `ERR_TRIGGER_CEILING_REACHED` (422), and at or above the documented minimum of 5 but below the ceiling it is refused with `ERR_HUMAN_REVIEW_REQUIRED` (422), so that a repeatedly suspended seller requires human sign-off before it can be taken off the marketplace outright. Both comparisons are inclusive, so a count of exactly 5 raises the review error and a count of exactly 99 raises the ceiling error.

Refurbishment capacity is the other governance lever. Sellers declare a `refurbishment_capacity_units` figure at registration and a `declared_monthly_throughput` figure when booking an audit, and the two are cross-checked. That cross-check outranks the audit score band, as §3.1 sets out.

## 3. Business Logic & Workflows

### 3.1. Seller Onboarding: From Applicant to Approved

A refurbishing business enters the marketplace through a registration capability reserved to `PlatformAdmin`, supplying its `legal_name`, its `country_code` (an ISO 3166-1 alpha-2 code of exactly two uppercase letters) and its `refurbishment_capacity_units`, the maximum number of devices it can refurbish per calendar month. The `legal_name` must be unique across all sellers, compared case-insensitively, and the capacity must be at least 1. A registered seller lands in `APPLICANT` with `performance_tier` set to `PROBATION` and `exposure_floor_cents` set to 0. Registration is one of only two endpoints that admit no credentials, so an `Anonymous` caller is accepted here.

A `ComplianceReviewer` moves the applicant forward by verifying its incorporation documents, which advances `onboarding_state` from `APPLICANT` to `DOCUMENT_VERIFIED`. Two conditions gate that step: the seller must genuinely be in `APPLICANT`, and its `blocklisted` flag must be false — a seller already linked to a confirmed counterfeit or stolen-device finding cannot be verified.

Booking the on-site refurbishment process audit is the next step, and it is only legal from `DOCUMENT_VERIFIED`. The reviewer supplies `audit_scheduled_for`, the date the visit is booked for, which must be strictly later than the current logical clock instant; an `audit_scope_note` of between 1 and 500 characters describing the refurbishment steps the visit will cover; and `declared_monthly_throughput`, the throughput the applicant claims, which must be at least 1. A second audit cannot be booked while a first is outstanding: a seller that already holds an audit record in `IN_PROGRESS` is refused with `ERR_AUDIT_ALREADY_SCHEDULED` (HTTP 409). On success the seller advances to `AUDIT_SCHEDULED`.

Note the shape of the audit record itself. It is created *already* `IN_PROGRESS` — there is no resting `SCHEDULED` state, so an on-site audit is never parked in a state that nothing can advance. The record's `audit_state` accepts `IN_PROGRESS`, `PASSED` and `FAILED`, and `FAILED` is terminal. The `audit_score`, an integer from 0 to 100, and the `auditor_user_id` of the operator recording the outcome are both optional at creation but required to move the record out of `IN_PROGRESS`.

The outcome is recorded by a `ComplianceReviewer` through the audit-transition capability, which takes `target_state`, `audit_score` and `auditor_user_id`. Three branches hang off that single act, and the first one to match wins. If the audit record's `declared_monthly_throughput` exceeds the seller's `refurbishment_capacity_units`, the applicant is rejected outright: the seller moves to `REJECTED`, the audit record is marked `FAILED`, and no score band is consulted at all. This capacity cross-check deliberately outranks the score band, so an over-capacity applicant is rejected before the pass-or-rework question is ever answered. If capacity is within bounds and the recorded `audit_score` is 70 or above, the seller is approved: `onboarding_state` becomes `APPROVED`, `performance_tier` is set to `PROBATION`, `exposure_floor_cents` is reset to 0, and the audit record becomes `PASSED`. If capacity is within bounds and the `audit_score` is 69 or below, the audit record becomes `FAILED` and the seller loops back to `APPLICANT`, free to be re-audited later.

That rework loop is bounded rather than open-ended, and for a structural reason worth stating plainly: an audit record row is single-use, so the next attempt requires a brand-new record, which in turn requires the seller to be re-verified and re-booked. Because `REJECTED` and `SUSPENDED` are the seller's terminal states, a rejected applicant cannot be resurrected by any capability in this API.

### 3.2. Listing Submission and the Eligibility Ladder

A `Seller` puts a device on the marketplace by submitting it with `model_code`, `imei`, `cosmetic_grade`, `functional_grade`, `battery_health_pct`, `carrier_lock_status`, `part_provenance`, `list_price_cents`, and, when required, `provenance_doc_digest`. The `imei` is exactly fifteen digits and must be unique across all listings that have not been withdrawn; the `cosmetic_grade` is one of `FLAWLESS`, `GOOD`, `FAIR`, `POOR`; the `functional_grade` is one of `FULLY_FUNCTIONAL`, `MINOR_FAULTS`, `MAJOR_FAULTS`; `battery_health_pct` runs from 1 to 100 inclusive; `carrier_lock_status` is one of `UNLOCKED`, `LOCKED`, `UNKNOWN`; `part_provenance` is one of `OEM_ONLY`, `OEM_EQUIVALENT`, `AFTERMARKET`; and `list_price_cents` must be at least 0. Submission lands the listing in `UNDER_REVIEW`, and the `serving_seller_id` and `servicing_seller_id` are both seeded from the submitting `seller_id`. This is the only creation path for a listing; `servicing_reservation_id` stays null until the listing later reaches `LISTED`.

The eligibility ladder is long, and its ordering follows §2.11 rather than the order in which the rules are described here. Nine conditions must hold together. The owning seller must be `APPROVED` — an `APPLICANT`, `DOCUMENT_VERIFIED`, `AUDIT_SCHEDULED` or `REJECTED` seller may neither hold nor submit listings, and such an attempt is refused with `ERR_SELLER_NOT_APPROVED`. The `model_code` must be present in the marketplace supported-model catalog and must not be subject to an active restricted-model restriction effective at the current logical clock instant, or the submission fails with `ERR_MODEL_NOT_ELIGIBLE`. The `imei` must appear on neither the stolen-device blocklist nor the counterfeit blocklist, or the submission fails with `ERR_DEVICE_BLOCKLISTED`. No other non-withdrawn listing belonging to the same seller may already carry the same `imei`, or the submission fails with `ERR_IMEI_ALREADY_LISTED`. The `battery_health_pct` must be at least 80, and it must also be at least the `battery_floor_pct` of whichever `GradingDefinition` is `ACTIVE`; when no definition is `ACTIVE`, the hard floor of 80 stands alone. A shortfall is refused with `ERR_BATTERY_BELOW_FLOOR`.

Part provenance carries a documentation obligation: `OEM_ONLY` needs no document, whereas `OEM_EQUIVALENT` and `AFTERMARKET` both require a `provenance_doc_digest`, which must be exactly 64 lowercase hexadecimal characters. A missing or malformed digest under either of those provenances is refused with `ERR_PART_PROVENANCE_UNDOCUMENTED`. Finally, `carrier_lock_status` must not be `LOCKED`, because a carrier-locked device cannot be sold as refurbished.

One further screen sits slightly apart from eligibility proper and is worth separating out, because it targets fraud rather than fitness. When a listing's `list_price_cents` is more than 50 percent below the model's catalogue floor — the `price_deviation_pct` tolerance — the submission is refused with `ERR_COUNTERFEIT_PRICE_SIGNAL`. This is the counterfeit-pricing signal: a price that far adrift of the catalogue floor is treated as evidence of a counterfeit device rather than as a bargain. The same screen is applied again later, against a live listing, when a reviewer delists it.

Re-submission exists for listings that failed review or were delisted or suspended. The seller supplies `expected_seller_version` alongside the re-submission, the full eligibility ladder is re-run from scratch, and the then-`ACTIVE` grading definition is re-captured onto the listing. Because the seller's version is the freshness token (§2.10), a client that holds a pre-recompute view of the seller is refused with `ERR_STALE_VERSION` (HTTP 412) rather than allowed to re-submit against stale assumptions; this is the intended serialization point between seller-level recomputes and listing re-submission. Withdrawal is a separate, terminal act: a `Seller` may withdraw a listing carrying a `withdrawal_reason` while it is `DRAFT`, `UNDER_REVIEW` or `DELISTED`, but not while any claim against it sits in `FILED`, `UNDER_REVIEW` or `APPROVED`, and not while its reservation is `REPAIRING`; either condition raises `ERR_WITHDRAW_BLOCKED_BY_OPEN_CLAIM` (409). Withdrawal releases the IMEI for reuse, because the uniqueness filter excludes withdrawn rows.

### 3.3. The Review Decision and the Warranty Reservation It Opens

A `ComplianceReviewer` rules on a listing that is `UNDER_REVIEW` by supplying a `decision` and a `reviewer_user_id`. A listing's `listing_state` accepts `DRAFT`, `UNDER_REVIEW`, `LISTED`, `DELISTED`, `SUSPENDED` and `WITHDRAWN`, the last of which is terminal. Before the decision is honoured, the server re-reads the grading definition captured at submission time and confirms it is still `ACTIVE`; a definition retired in the interim produces `ERR_GRADING_DEFINITION_NOT_ACTIVE` (409). An approval moves the listing to `LISTED` and, in the same transaction, opens a warranty reservation against it: the reservation starts in `ACTIVE`, its `activated_on` is the current logical clock instant, its `warranty_period_days` is the default 180, its `reserved_units` is 1, and its `unit_reserve_per_day_cents` is the default 1800. The listing's `servicing_reservation_id` is pointed at that reservation. A rejection sends the listing back to `DRAFT`.

Reservations are not only created as a side effect of approval. A `ComplianceReviewer` or `ClaimAdjudicator` may open a second reservation against a listing explicitly, supplying `activated_on`, `warranty_period_days`, `reserved_units` and `unit_reserve_per_day_cents`. The `activated_on` instant must not be later than the current logical clock instant, and `warranty_period_days` must be at least 1. Whichever path created it, a reservation's `expired_on` is its activation date plus its warranty period, and it is recomputed whenever `activated_on` or `warranty_period_days` changes.

Because a listing may accumulate more than one reservation over its life, the system needs a deterministic answer to "which reservation is servicing this listing right now". That selector is specified in §3.5, and it matters earlier than one might expect: the reservation is looked up on claim evidence, on buy-box computation, and on every exposure-floor recompute.

Two listing-level actions rewrite the reservation's life. Delisting a `LISTED` listing — available to a `ComplianceReviewer` with a `reason_code` drawn from `BATTERY_DEGRADED`, `MYSTERY_SHOP_FINDING`, `PART_PROVENANCE_UNVERIFIED`, and an optional `extended_reservation_days` — moves the listing to `DELISTED`, flips its servicing reservation to `SUSPENDED`, and advances the listing's `active_reservation_days` by one. Blocklisting the owning seller cascades in a second direction: every listed device of that seller becomes `SUSPENDED` and every reservation servicing those devices has its `reserved_units` zeroed, with the owning seller's `exposure_floor_cents` recomputed as a consequence.

### 3.4. Mystery-Shop Verification and Grading Compliance

Because a self-declared grade is only as good as the seller's honesty, the marketplace runs an undercover purchase programme. A `ComplianceReviewer` opens a verification against a seller's listing by supplying the `seller_id`, the `listing_id`, a `rationale_code` — one of `GRADE_GHOST`, `PART_PROVENANCE`, `BATTERY_MISMATCH` — the `ordered_cosmetic_grade` the listing was sold under, and a scheduled window given by `verification_start` and `verification_end`. The window is half-open: `verification_end` must be strictly later than `verification_start` and is exclusive. The new verification opens in state `OPEN`, and its windows may not strictly overlap another still-`OPEN` verification for the same listing; two windows that merely abut end-to-start do not collide, and a genuine overlap is refused with `ERR_VERIFICATION_OVERLAP` (HTTP 409).

Recording the findings is the disclosure act, and it is where the programme acquires teeth. The verifier supplies `received_cosmetic_grade` (the cosmetic grade actually observed on the delivered device), `measured_battery_health_pct` (1 to 100 inclusive), and a `verifier_user_id`. The verification moves from `OPEN` to `DISCLOSED`, and the effects fan out across three resources. The listing's `mystery_shop_disclosed` flag is set to true. On the verification row itself, `value_at_risk` is set to 1, `reserved_units_delta` is set to 1, and `exposure_floor_delta_cents` is set to 9600 — the `grading_constraint_violation_unit_cents` value. Then the seller's constraint exposure is raised accordingly and the seller's `exposure_floor_cents` is recomputed, which in turn re-derives `performance_tier` and re-ranks the seller's buy-box position.

Disclosure is emphatically not idempotent. A listing that already carries a `DISCLOSED` verification cannot be disclosed against a second time; the attempt is refused with `ERR_VERIFICATION_ALREADY_DISCLOSED` (HTTP 409). A verification that produces no finding may instead be voided with a `void_reason`, moving it from `OPEN` to `VOIDED`; a void mutates neither the listing nor the seller's score, so the programme can close out a clean shop without leaving a mark. `DISCLOSED` and `VOIDED` are both terminal.

### 3.5. Warranty Reservations, the Repair Cycle, and Exposure Accounting

The selector that answers "which reservation is servicing this listing" is specified precisely, because its answer is observable in several other computations. The candidate set is every reservation belonging to the listing whose `warranty_state` is `ACTIVE`, `REPAIRING` or `REPLACED`; reservations in `COMPLETED` are excluded. Candidates are ranked by `activated_on` descending, and ties on that instant are broken by `created_at` ascending. The first row under that ranking wins. Two prohibitions are absolute: the row `id` may serve neither as the primary key nor as the tie-break, because it is a random identifier and would make an otherwise deterministic result non-deterministic; and the winning row's `servicing_seller_id` must equal the listing's `servicing_seller_id`. An empty candidate set is never represented as a null winner — it raises `ERR_RESERVATION_NOT_FOUND` (HTTP 404). When exactly one candidate exists the ranking is vacuous and that row is returned; when several exist, `activated_on` decides and `created_at` settles any tie.

A reservation's `warranty_state` is the field that carries all of this, and it accepts `ACTIVE`, `REPAIRING`, `REPLACED`, `SUSPENDED` and `COMPLETED`. Reservations move through `ACTIVE`, `REPAIRING`, `REPLACED`, `SUSPENDED` and `COMPLETED`. A `ClaimAdjudicator` upholding a claim with a `REPAIR` resolution — legal only while both the reservation is `ACTIVE` and the claim is `UNDER_REVIEW` — moves the reservation to `REPAIRING` and advances the owning listing's `active_reservation_days` by one. The same adjudication with a `REPLACE` resolution moves it to `REPLACED` and likewise advances `active_reservation_days` by one. Remediation returns either state to `ACTIVE`: a `ClaimAdjudicator` remediating a `REPAIRING` reservation supplies `repair_estimate_cents` and may supply a `replacement_listing_id`, while remediating a `REPLACED` reservation supplies `replacement_listing_id`; an optional `expected_reservation_version` may be carried on the remediation request. In both cases the listing's `active_reservation_days` resets to 0, the released cell is subtracted from the seller's `exposure_floor_cents`, the seller's `performance_tier` is re-derived, and the buy-box rank is recomputed.

Reservations also expire on their own. When the logical clock advances strictly past a reservation's `expired_on` while the reservation is `ACTIVE`, the system moves it to `COMPLETED` without any client request. `COMPLETED` is terminal, and a completed reservation contributes nothing to exposure.

The carried repair exposure term is built cell by cell. A live exposure cell exists for every reservation that is its listing's servicing reservation and is in `REPAIRING` or `REPLACED`; a reservation that has returned to `ACTIVE` through remediation, or has reached `COMPLETED`, contributes zero, because its obligation has been discharged. For each live cell the system computes the remaining days as the calendar days from the current logical clock instant to the cell's expiry date — its `activated_on` plus its `warranty_period_days` — clamped at zero, and the remaining fraction as those remaining days divided by the warranty period. The cell's value is its `reserved_units` multiplied by its `unit_reserve_per_day_cents` multiplied by that remaining fraction, rounded half-up to integer cents. Crucially, each cell is rounded *individually* and only then are the cells summed; rounding once over the combined total is the non-conforming order and yields different cents whenever two cells' fractional parts cross the halfway point together. As a worked illustration, two live cells of 1855 cents per day over a 180-day period, evaluated at a clock instant where one cell has 143 days remaining and the other 138, yield 1473 cents and 1422 cents respectively, summing to 2895 cents, whereas a single rounding over the combined total would give 2896. Live reservations in `REPAIRING` or `REPLACED` contribute; reservations in `ACTIVE` or `COMPLETED` contribute zero. Claims are not netted into this term.

The constraint exposure term expresses marketplace risk appetite and is derived from the seller's most recent closed scoring section. The section-scoped claim count is the number of claims routed to the seller within the closed section window, and the raw violation unit count is one hundred times that figure. The unit count then depends on where the raw figure falls. At or above a denominator of 300 units, the raw figure is used unchanged. Between the door of 100 units inclusive and the denominator of 300 exclusive, the raw figure is divided by 300 and *floored*, never rounded, so any remainder is discarded and the result is strictly smaller than the raw count. Below the door of 100 units, the contribution is zero. The unit count is multiplied by 9600 cents to give the constraint exposure. Worked boundaries: a section with 4 claims routed to the seller has a raw figure of 400, which is at or above the denominator, so the exposure is 4 times 9600, or 38400 cents; a section with exactly 3 claims has a raw figure of exactly 300, which the inclusive comparison still places in the top branch, giving 3 times 9600, or 28800 cents; a section with 1 claim has a raw figure of exactly 100, which is below the denominator but at the door, so the division yields zero and the contribution is zero. Sellers with no closed section contribute zero.

The published floor composes the two terms in a pinned order: constraint exposure first, carried repair exposure second, the sum clamped at zero third, and publication last. Remediation illustrates the first term's behaviour — the remediated reservation stops contributing a cell, so the repair term falls by exactly that cell and the published floor falls by the same amount. A seller whose every servicing reservation has been suspended by a blocklisting illustrates the other: with every cell removed the repair term is zero and the published floor equals the constraint term alone.

### 3.6. Buyer Claim Adjudication and Return Routing

A `Consumer` files a claim against one of a seller's listings, supplying the `listing_id`, a `claim_reason_code` — one of `BATTERY_SWELL`, `TOUCH_FAILURE`, `CAMERA_FAILURE`, `UNLOCKED_PROMISE_BREACH` — and an `evidence_included` flag that records whether a diagnostic bundle accompanied the claim at filing. The claim lands in `FILED` with its `routed_seller_id` seeded from the listing's `servicing_seller_id`, and `on_time_flag` starts false. Filing is one of the two credential-free endpoints, so an `Anonymous` caller is accepted.

The claim then acquires its evidence, which is the act that pins routing; `claim_state` is the field that carries the lifecycle and accepts `FILED`, `UNDER_REVIEW`, `APPROVED`, `REJECTED` and `RESOLVED`. A `ClaimAdjudicator` attaches a `diagnostic_evidence_digest`, which must be exactly 64 lowercase hexadecimal characters; the digest and its format are checked before the claim may enter `UNDER_REVIEW`, and a claim whose digest is absent or malformed is refused with `ERR_DIAGNOSTIC_EVIDENCE_REQUIRED` (HTTP 422) rather than allowed to reach the transition at all. On success the claim moves to `UNDER_REVIEW`, its `routed_seller_id` is pinned to the listing's `servicing_seller_id` for the remainder of its life, the servicing reservation's `claims_filed_count` is incremented by one, and the seller's exposure floor is recomputed. The claim additionally takes a reserve, `claim_reserve_cents`, computed as the smaller of 90000 and the sum of 25000 and 151 times the reservation's `unit_reserve_per_day_cents` — so a reservation earning the default 1800 cents per day caps out at 90000 cents.

Adjudication is where the resolution branch is chosen. A `ClaimAdjudicator` supplies a `decision`, and when upholding, additionally a `resolution_type` of `REPAIR` or `REPLACE`, a `resolution_obligation_cents`, and an `adjudicator_user_id`. The obligation is checked against the resolution cap — 25000 cents for a `REPAIR` and 90000 cents for a `REPLACE` — and an over-cap request is refused with `ERR_OBLIGATION_EXCEEDS_CAP` (HTTP 422). A claim may only be adjudicated while it is `UNDER_REVIEW` and only while it carries a `diagnostic_evidence_digest`. On an uphold, `seller_funded_amount_cents` is set to the `resolution_obligation_cents` plus the `return_shipment_cents` supplied, the reservation's `repair_obligation_cents` is increased by the obligation when the resolution is `REPAIR`, or its `replacement_obligation_cents` is increased by it when the resolution is `REPLACE`, and the cascade described in §3.5 fires: the reservation flips to `REPAIRING` or `REPLACED` and the listing's `active_reservation_days` advances by one. A rejection sets the claim to `REJECTED`, zeroes `claim_reserve_cents`, decrements the reservation's `claims_filed_count`, and is otherwise free of financial effect.

A second uphold of a claim that is already `APPROVED` and awaiting return routing is refused with `ERR_CLAIM_ALREADY_UPHELD` (HTTP 409) — the claim remains legally non-terminal at that point, so the marketplace chooses to answer on the already-upheld ground rather than the terminal ground. Once the claim reaches `RESOLVED` or `REJECTED`, any further mutation is refused with `ERR_CLAIM_TERMINAL` (409). The two codes therefore make the claim's polarity observable from the error alone.

Routing the return closes the claim out. The `ClaimAdjudicator` supplies a `return_shipment_cents` of at least 0 and may supply a `return_carrier` of `CARRIER_A`, `CARRIER_B` or `CARRIER_C`, together with an optional `expected_claim_version`; when a carrier is named, `return_shipment_cents` is required and must be at least 0. The return occupies a one-day slot beginning at `return_shipment_start`, and that half-open interval — from the start instant to 86400 seconds later — may not touch either boundary of an already-booked return on the same carrier; a collision is refused with `ERR_RETURN_SLOT_COLLISION` (HTTP 409). On success the claim moves to `RESOLVED`, the `return_shipment_cents` is added to `seller_funded_amount_cents`, `claim_reserve_cents` is zeroed, and the seller's exposure floor is recomputed. The released reserve is not netted out of that floor when it is released — consistent with §2.7, a held reserve sits alongside the published balance rather than inside it, so subtracting it on release would double-count an obligation that was never part of the balance. What the release does move is the seller's `reserved_claim_cents` reading, which drops by the released amount the moment the claim leaves `APPROVED`.

Two edge branches deserve naming explicitly. First, a return routed to any seller other than the one pinned when the claim entered `UNDER_REVIEW` is refused with `ERR_ROUTED_SELLER_IMMUTABLE` (422) — the binding is immutable, and it is immutable even when the marketplace's own reclamation policy would otherwise have been willing to absorb a carrier-less return. That is the essence of the reclaim-route conflict: the absence of carrier data would be admissible under the reclamation policy, but the policy cannot lawfully rewrite the routed seller, so the outcome is a rejection rather than a silent reassignment. Second, `on_time_flag` is a read-mostly terminal observation: it becomes true when the claim reached `RESOLVED` within 21 calendar days of its `created_at`, counting the twenty-first day as inside the window, and stays false otherwise, including for claims that never resolve at all. `resolution_type` is null while a claim is `FILED` or `UNDER_REVIEW`, and `replacement_listing_id` records the replacement device issued when the resolution was `REPLACE`.

A replacement claim carries two separate money figures that travel on the same claim and are never netted into one field. The buyer payout is what the marketplace sends the buyer, and it is the claim's held reserve plus a goodwill component of 30 percent of the listing's `list_price_cents` rounded half-up to integer cents, with the sum then rounded half-up to integer cents once more. Its companion is the seller chargeback, which is a distinct quantity: it charges the routed seller only the pro-rated share of the refused funded cost, where the refused funded cost is a fixed 90000 cents — the warranty repair or replacement expense the marketplace advanced — multiplied by the number of calendar days from the replacement listing's activation to the replacement claim's resolution, capped at the replacement warranty class period of 180 days, divided by that same 180 days, rounded half-up to integer cents and clamped at zero. The gross is rounded first and the net subtraction is rounded in its turn, both half-up. Two further figures belong to the same settlement picture even though the payout formula does not consume them: the marketplace's own commission on the transaction is 9 percent of the sold price rounded half-up to integer cents, and the routed seller's inbound shipping allowance is a flat 5600 cents. A worked replacement illustrates the magnitudes — a device sold at 45000 cents carries a 4050-cent marketplace commission, and a claim holding a 90000-cent reserve against it pays the buyer 103500 cents while charging the seller 45000 cents, because the replacement claim resolved 90 days into its 180-day period.

### 3.7. Service-Score Sections and Buy-Box Placement

Seller performance is measured in scoring sections. A `PlatformAdmin` opens one for a seller by supplying the `seller_id` and `section_opened_on`, which must not be later than the current logical clock instant. The section's `section_state` accepts `OPEN` and `CLOSED`; it opens in `OPEN`, and a section is scored continuously — while it is open, its four components are re-derived on every read, using the current logical clock instant as the window's upper bound so that a score is always defined for a section that has opened.

Closing a section is what fixes its numbers. A section may close only once it is at least 90 calendar days old, measured from `section_opened_on`, and only when no claim routed to that seller is `APPROVED` and unresolved; the closed-state guard ordering matters here, because the open-approved-claim guard fires *before* the section-age guard, so a section that is both too young and blocked by an open approved claim reports `ERR_SECTION_BLOCKED_BY_OPEN_CLAIM` (HTTP 409) rather than `ERR_SECTION_TOO_YOUNG` (409). A section closed sooner than 90 days after it opened reports the too-young code.

The closed section's window is half-open in a specific direction: it runs from the `section_opened_on` instant *exclusive* to the `section_closed_on` instant *inclusive*. A claim created exactly at the opening instant is therefore excluded from the section, and one created exactly at the closing instant is included. Within that window the system counts claims routed to the seller, and among those counts how many were `REJECTED` and how many carry `on_time_flag` true; it counts mystery-shop verifications recorded against the seller and sums their `value_at_risk` as violations; and it counts listings created by the seller in the window, among which it counts how many have a reservation in `REPAIRING` at the moment of close.

Four components follow, each rounded half-up to two decimals *before* it is weighted — this ordering is the only conforming one. The component `claim_failure_rate_pct` is one hundred times the rejected count divided by the greater of one and the routed count. The component `on_time_resolution_pct` is one hundred times the on-time count divided by the greater of one and the routed count. The component `grading_compliance_pct` is one hundred times the quantity of shops minus violations, divided by the greater of one and the shop count. The component `return_rate_pct` is one hundred times the returned count divided by the greater of one and the listed count. The service score is then 0.35 times the complement of the claim failure rate, plus 0.30 times the on-time resolution rate, plus 0.25 times the grading compliance rate, plus 0.10 times the complement of the return rate, with the weighted sum rounded half-up to two decimals once more. The non-conforming alternative — weighting the raw unrounded ratios and rounding only the final sum — produces different results for identical data: with three claims routed, one rejected, two on time, two shops, one violation, four listings and one return, the conforming order yields a score of 63.34 while the non-conforming order yields 63.33.

The score drives two things. `threshold_breached` is true exactly when the score is at or below 55.00, and a breach at or below that figure while the seller is `APPROVED` suspends it (§3.9). Otherwise the seller's `performance_tier` is remapped: `ELITE` at 85.00 or above, `STANDARD` at 70.00 or above, `PROBATION` while the score is strictly above 55.00, and `SUSPENDED` otherwise. Because a seller closing a section carries the same freshness risk described in §2.10, the close request must carry `expected_seller_version`; a mismatch is refused with `ERR_STALE_VERSION` (412), since the section's aggregates and the seller's exposure floor are read from one instant and a stale seller view would pin the floor to a superseded value.

Buy-box placement is the commercial consequence of the tier. The candidate set for a model is every listing that is `LISTED`, whose `model_code` equals the queried listing's model code, and whose owning seller is `APPROVED`; withdrawn, delisted, suspended and draft rows are excluded, as are listings whose seller has never closed a scoring section, because no rank score exists for them. Each candidate's rank score is the `service_score` of its seller's latest closed section, and only sellers whose `performance_tier` is `ELITE`, `STANDARD` or `PROBATION` contribute candidates at all — a `SUSPENDED`-tier seller contributes nothing. The winner is the first candidate under a pinned sort key: the negation of the candidate's `list_price_cents` rounded half-up to two decimals, with `created_at` ascending as the tie-break. Neither a random identifier nor the row `id` participates in either the sort key or the tie-break.

The buy-box price the winner displays is computed in a pinned evaluation order — score, then tier, then price, then rounding, then clamp. A rank score of 95.00 or above takes a multiplier of 1.00; from 85.00 inclusive up to but excluding 95.00 takes 0.70; from 70.00 inclusive up to but excluding 85.00 takes 0.40; and below 70.00 takes 0.00. The competitor average is the integer floor of the arithmetic mean of `list_price_cents` over the *other* candidates; when exactly one candidate exists the mean is undefined and that row's own `list_price_cents` substitutes for it. The buy-box price is the multiplier applied to the competitor average, rounded half-up to integer cents once, after the multiplier — rounding is applied last and only once. If that result is at or below zero, the buy-box price falls back to the `list_price_cents` of the highest-ranked candidate. The response for a buy-box query carries `winner_listing_id`, `winner_seller_id`, `winner_rank_score`, `buy_box_price_cents` and `ranked_listing_ids`.

A worked placement makes the interaction concrete. Suppose seller D has a latest closed section score of 75.84 and seller C has 31.66. D's tier is `PROBATION` and takes a 0.40 multiplier; C's tier is `SUSPENDED` and C therefore contributes no candidate at all. Two listings compete for the same model: D's at 160000 cents and seller A's at 150000 cents, with A's score at exactly 70.00 and therefore also a 0.40 multiplier. A's listing wins the ranking, because the sort key for 150000 beats the sort key for 160000. A's competitor average is 160000 cents, so A's buy-box price is 0.40 times 160000 rounded half-up, which is 64000 cents. Should D's listing have been the sole candidate, its own price would have substituted for the competitor average and the multiplier would still have applied to it, giving the same 64000 cents — a coincidence arising from the multiplier being identical, and not a rule to generalise from.

### 3.8. Trade-In Intake and Post-Inspection Revision

The trade-in channel prices devices the marketplace buys in. A `Consumer` submits a device by declaring, before any inspection, a `customer_ref`, a `submitted_model_code`, a `self_declared_cosmetic_grade`, a `self_declared_functional_grade`, a `self_declared_battery_health_pct` between 1 and 100 inclusive, and a `self_declared_carrier_lock_status`. The submission lands in `SUBMITTED` — its `submission_state` accepting `SUBMITTED`, `INSPECTED`, `PRICE_REVISED`, `ACCEPTED` and `REJECTED` — and receives a `provisional_quote_cents` computed once, at creation, from the declaration alone. That provisional figure is never revised in place, so a submission that later receives an inspection retains both numbers side by side.

The provisional quote starts from a base of 38000 cents and subtracts four deductions. The cosmetic deduction is read from the two lower grades directly: `FLAWLESS` costs nothing, `GOOD` 1800 cents, `FAIR` 5200 cents and `POOR` 11000 cents. The functional deduction is likewise tabled: `FULLY_FUNCTIONAL` costs nothing, `MINOR_FAULTS` 4200 cents and `MAJOR_FAULTS` 13500 cents. The battery deduction is banded by declared health: 85 or above costs nothing, 80 through 84 inclusive costs 2500 cents, 70 through 79 inclusive costs 6000 cents, and below 70 would cost 12000 cents were such a device ever valued. The carrier-lock deduction is zero for `UNLOCKED`, 4500 cents for `UNKNOWN` and 9000 cents for `LOCKED`. The provisional quote is the base minus all four deductions, clamped at zero.

Inspection is performed by a `TradeInInspector`, who supplies the `inspected_cosmetic_grade`, `inspected_functional_grade`, `inspected_battery_health_pct` and `inspected_carrier_lock_status` actually measured on the device. All four are optional at submission but all four must be present to complete an inspection. The measured battery health governs the submission's fate at this step: a device measured at exactly 70 percent or above proceeds to `INSPECTED`, while one measured strictly below 70 is rejected outright and moves to `REJECTED`, refused with `ERR_INSPECTION_BATTERY_UNINSURABLE` (HTTP 422). The boundary is deliberate — 70 is insurable and 69 is not. A submission that proceeds has its `final_quote_cents` set to zero pending the revision step.

The revision step is where the final quote is struck, and it is available once. A submission in `INSPECTED` with a `revision_count` of zero may be revised: the inspector supplies the same four inspected measurements, and the submission moves to `PRICE_REVISED` with `revision_count` incremented to one, `inspection_fee_cents` set to 1500 cents, and `acceptance_deadline` set to the current logical clock instant plus seven calendar days. A revision attempted when `revision_count` is already one is refused with `ERR_REVISION_LIMIT_REACHED` (HTTP 409). A submission in `PRICE_REVISED` may, however, be revised *back* to `INSPECTED` provided the clock is at or before its `acceptance_deadline` and its `revision_count` is exactly one — the one free revision round runs in both directions and is exhausted by the second attempt. The reverse revision moves only the state: it leaves `revision_count` at one and does not recompute the struck final quote, so the submission rests in `INSPECTED` having already spent its round.

The final quote is computed in a pinned order: base, then deductions, then the step penalty, then a clamp at zero, then the fee, then the rounding, then a final clamp at zero. It begins from the same 38000-cent base, minus the cosmetic, functional, battery and carrier-lock deductions evaluated against the *inspected* measurements rather than the declaration. Then a step penalty is applied: the inspector's grades are converted to ordinal positions — cosmetic `FLAWLESS` at 0, `GOOD` at 1, `FAIR` at 2 and `POOR` at 3; functional `FULLY_FUNCTIONAL` at 0, `MINOR_FAULTS` at 1 and `MAJOR_FAULTS` at 2 — and the number of grade steps worse than the declaration is the sum of two clamped differences: the excess, if any, of the inspected cosmetic position over the declared cosmetic position, plus the excess, if any, of the inspected functional position over the declared functional position. A device that measured equal to or better than declared on an axis contributes nothing on that axis. Each step costs 2500 cents, and the step penalty is that rate times the step count, subtracted from the inspected value, with the result clamped at zero. The inspection fee is then seven percent of that clamped figure, rounded half-up to integer cents, and the final quote is that figure minus the fee, rounded half-up to integer cents and clamped at zero once more. For identical underlying measurements, the provisional and final variants differ by exactly the step penalty plus the fee.

A `Consumer` accepts the revised quote by presenting no further input at all, and the submission moves from `PRICE_REVISED` to `ACCEPTED`. Acceptance is legal while the clock reads at or before `acceptance_deadline` and while the `final_quote_cents` is strictly greater than zero. Acceptance exactly at the deadline succeeds; the same request one day later is refused with `ERR_ACCEPTANCE_WINDOW_CLOSED` (HTTP 409). The other way out of `PRICE_REVISED` requires no client at all: when the logical clock advances strictly past the `acceptance_deadline`, the system moves the submission to `REJECTED`. `ACCEPTED` and `REJECTED` are both terminal for a submission.

### 3.9. Enforcement, Blocklisting, Reinstatement, and the Logical Clock

When a closed scoring section takes an `APPROVED` seller's score to or below 55.00, the system suspends the seller without any client request: `onboarding_state` becomes `SUSPENDED`, `performance_tier` becomes `SUSPENDED`, `suspension_trigger_count` is incremented by one, and the seller's version advances. The same transition fires whenever a component-source change — a claim transitioning, a disclosure being recorded, a listing or reservation being created — recomputes an open section's score to or below that threshold. The seller then has a tier of `SUSPENDED` and, per §3.7, contributes no buy-box candidates at all.

A lighter seller-level remedy sits alongside the listing-level delisting of §3.3. A `ComplianceReviewer` may suspend an approved seller directly on a `reason_code`, optionally guarded by an `expected_seller_version`; the seller's catalogue is then delisted, the servicing reservation that covers the affected device flips so that the seller's repair exposure begins to accrue, the listing's `active_reservation_days` advances by one, and the seller's exposure floor is recomputed before the seller's version is advanced. The distinction between this seller-level act and the blocklisting remedy below is one of severity and of evidence: the blocklist requires a confirmed counterfeit or stolen-device finding, whereas this suspension responds to a counterfeit-pricing or grading signal.

Blocklisting is the harsher remedy. A `ComplianceReviewer` records a finding against a seller by supplying a `finding` of `CONFIRMED_COUNTERFEIT` or `CONFIRMED_STOLEN`, an `evidence_digest`, and an optional `suspension_trigger_units`. The seller's `blocklisted` flag is set true, `onboarding_state` and `performance_tier` both become `SUSPENDED`, and the cascade runs: every listing of that seller that is `LISTED` becomes `SUSPENDED`, and every warranty reservation servicing those listings has its `reserved_units` zeroed, with the owner's `exposure_floor_cents` recomputed from the now-empty repair term. The seller's own suspension through section scoring and its suspension through blocklisting are distinct triggers that share a destination state.

Because a suspended seller may eventually be reinstated, the system models a reinstatement ramp. The ramp counts the calendar days of service the seller has contributed, taken from the archived exposure cells that the carried-repair-exposure rule already uses; a seller with no archived cells has a service-day count of zero. The number of ramp steps is the service-day count divided by the reinstatement window of one day, floored — neither a partial window nor a partial tier is ever credited. The escalation score is the seller's latest score percentage minus twenty points per ramp step, floored and then clamped at zero. A seller that has never closed a scoring section has a latest score of 100.00, so an un-scored seller starts at the very top of the ramp. The tier is then read off the usual bands: `ELITE` at 85.00 or above, `STANDARD` at 70.00 or above, `PROBATION` while the score is strictly above 55.00, and `SUSPENDED` otherwise. Worked: a seller with three service days and a latest score of 100.00 has three ramp steps, an escalation score of 100.00 minus 60.00, or 40.00, and therefore a tier of `SUSPENDED`. An un-scored seller has an escalation score of 80.00 after one window (a `PROBATION` tier), 40.00 after three windows, and the clamp pins the score at zero thereafter so it can never be driven negative.

The exposure-floor read exposes the tension between two defensible roundings rather than hiding it. Alongside the published balance, the read returns a trace computed over the same live cells but rounded only once over the combined total, plus `cell_count`. `published_exposure_floor_cents` is the per-cell-rounded balance carried on the seller row, and `traced_exposure_cents` is the single-rounding recomputation; the two are returned side by side and may legitimately differ by one cent when two or more live cells have fractional parts that cross the halfway point together. When the seller has exactly one live cell the two orders coincide and the values agree exactly, and a seller with no live cell returns a trace of zero with a cell count of zero. `reserved_claim_cents` is returned on the same read and is not netted into either figure.

Finally, the logical clock itself is driven by an administrative capability reserved to `PlatformAdmin`, which moves the clock to a supplied `to_iso8601` instant. Moving the clock is not inert: the call evaluates every system transition whose guard depends on time, so warranty reservations whose `expired_on` has been passed while `ACTIVE` become `COMPLETED`, and trade-in submissions whose `acceptance_deadline` has been passed while `PRICE_REVISED` become `REJECTED`. Because the clock never falls back to wall-clock time, an implementation that reads the host's system time anywhere in this API will diverge from the specified behaviour.
