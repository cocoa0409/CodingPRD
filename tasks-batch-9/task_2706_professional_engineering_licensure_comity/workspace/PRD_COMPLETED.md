# Professional Engineering Licensure & Comity API — Product Requirements Document

## 1. Introduction

A state board of professional engineers is the single legal gate between an engineering graduate and the right to place a seal on a set of construction drawings. Today that gate is administered as a pile of loosely-coupled clerical processes: transcripts are evaluated in one office, supervising-engineer reference letters accumulate in another, the national testing service transmits scores by spreadsheet, out-of-state applicants arrive with credential packets from a national records program that nobody can reconcile against the board's own roster, and continuing-competency audits are drawn by hand from whatever list of renewals happens to be current. The consequences are not merely administrative. A licence that should have lapsed keeps a firm in nominal responsible charge; a plan set gets stamped by an engineer whose seal privileges were suspended three weeks earlier; a disciplinary penalty is computed two different ways by two different staff members on the same set of statutory factors.

This document specifies the API for a single system of record that closes those gaps. It covers the full licensure lifecycle — application intake with education, examination and progressive-experience verification; reference evaluation and board determination of experience credit; examination approval, seating at a national testing centre and score reporting; comity licensure for engineers already licensed elsewhere; firm registration with responsible-charge and seal requirements; biennial continuing professional competency reporting with audit sampling; and the enforcement track that runs from complaint intake through investigative finding, civil penalty assessment, negotiated consent order and eventual reinstatement.

Two design commitments run through every requirement that follows. The first is **arithmetic determinism**: every fee, every month of experience credit, every professional development hour and every civil penalty is computed by a pinned sequence of steps with pinned rounding points, so that two independent implementations of this specification produce byte-identical numbers on identical data. The second is **segregation of duties enforced on identity, not on job title**: the board officer who approves an examination must not be the reviewer who determined the experience credit on that same file, the secretary who adjudicates a competency audit must not be the one who drew the sample, and the officer who executes a consent order must not be the investigator who worked the case. Both commitments are contract-level, not aspirational, and both are visible in the error catalogue.

## 2. Global Specifications & System-Wide Principles

### 2.1. Board Identities and Role-Based Access Control

Every request to this API carries two headers: `X-User-ID`, identifying the acting party, and `X-User-Role`, naming the capacity in which that party is acting. If either header is absent — a header present but empty, or holding nothing but whitespace, counts as absent — or if `X-User-Role` is not one of the nine role names enumerated below, matched exactly and case-sensitively once surrounding whitespace is trimmed, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not among the roles authorised for the endpoint being called — the authorisation column of the endpoint table in §4 is the definitive list — the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). These two checks run before anything else the system does, in that order.

The nine roles, spelled exactly as they must appear in `X-User-Role`, are `Applicant`, `SupervisingEngineer`, `Licensee`, `FirmAdmin`, `BoardReviewer`, `BoardLicensingOfficer`, `BoardInvestigator`, `BoardSecretary` and `TestingService`.

Four of these roles are **entity-backed**, meaning `X-User-ID` is not an arbitrary operator string but the primary key of a persisted row, and ownership is decided by comparing that key against a foreign-key field on the target resource:

- When `X-User-Role` is `Applicant`, `X-User-ID` is the `id` of the acting `Engineer`; ownership checks on any resource that references an `Engineer` compare the resource's foreign-key field to `X-User-ID`. An applicant acting on an application, an experience record, a verification request, an exam authorization or an appointment must resolve, through the chain of parents, to an `Application` whose `engineer_id` equals `X-User-ID`.
- When `X-User-Role` is `SupervisingEngineer`, `X-User-ID` is the `id` of the acting `Engineer`; ownership checks on any resource that references an `Engineer` compare the resource's foreign-key field to `X-User-ID`. Concretely, the referee acting on a verification request must be the engineer named in that request's `referee_engineer_id`.
- When `X-User-Role` is `Licensee`, `X-User-ID` is the `id` of the acting `Engineer`; ownership checks on any resource that references an `Engineer` compare the resource's foreign-key field to `X-User-ID`. A licensee renewing a licence, filing a competency report or affixing a seal must be the engineer named in the relevant `License`'s `engineer_id`.
- When `X-User-Role` is `FirmAdmin`, `X-User-ID` is the `id` of the acting `FirmRegistration`; ownership checks on any resource that references a `FirmRegistration` compare the resource's foreign-key field to `X-User-ID`. A firm administrator filing a plan set must supply a `firm_registration_id` equal to `X-User-ID`, and may only nominate a replacement responsible-charge licence on the firm registration whose `id` is `X-User-ID`.

The remaining five roles are **opaque operator identities**. When `X-User-Role` is `BoardReviewer`, `BoardLicensingOfficer`, `BoardInvestigator`, `BoardSecretary` or `TestingService`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it wherever a transition writes an actor stamp — as `reviewer_user_id` and `credit_determined_by_user_id` on an `Application`, as `created_by_user_id` and `audit_decided_by_user_id` on the competency-audit records, as `assigned_investigator_user_id` on a `Case`, and as `executed_by_user_id` on a `ConsentOrder` — but it never compares that identifier to any entity's `id`. It is compared only to other recorded operator stamps, which is precisely how segregation of duties is enforced (see §2.11).

An entity-backed role acting on a resource it does not own is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Ownership is checked after the path and body identifiers have been resolved to real rows, so a nonexistent target reports its own not-found code rather than an ownership failure. Ownership gates the write and transition endpoints only: no read endpoint applies it, so a single-resource read returns the row to any role its authorisation column admits — an `Applicant` may read another applicant's file — and a filtered list is never narrowed to the acting identity's own rows.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one value in this API taken from real wall-clock time rather than from the logical clock of §2.5; it is regenerated on every response, and no rule in this specification ever reads it.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. The keys of a resource object are emitted in the fixed order that resource's field list declares — `id` first, then the entity's own fields, then `created_at` and, on the entities that carry them, `updated_at` and `version` last — and are never sorted alphabetically.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint is paginated by two optional query parameters. `limit` defaults to 10 when omitted, may be no smaller than 1 and no larger than 100. `offset` defaults to 0 and may be no smaller than 0. A `limit` outside the inclusive range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending — oldest row first. Because the logical clock of §2.5 stands still until it is explicitly moved, many rows share the same `created_at`; rows that do are ordered among themselves by the sequence in which the server persisted them, earliest first. The `meta` block of a list response carries `limit` and `offset` echoing the effective values used, `total_count` giving the number of rows that match the filter before the window is applied, and `has_more` set true when rows remain beyond the current window. Single-resource responses omit all four.

### 2.4. Record Identity, Timestamps and the Revision Counter

Every resource this API mints carries an `id` that is a server-generated UUID. Identifiers are never prefixed by type, never client-supplied, and never reused. Alongside it, every resource carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional-second digits, stamped once when the row is first persisted — read from the current value of the logical board clock of §2.5, never from system time — and never modified thereafter.

Most resources additionally carry `updated_at`, in the same ISO 8601 UTC three-fractional-digit format, and `version`, an integer that starts at 1 on creation and increases by exactly 1 on every mutation of that row. `updated_at` is stamped equal to `created_at` when the row is first persisted. Any operation that writes a field of a row, including a mutation the row receives as the downstream effect of a cascade begun elsewhere, refreshes that row's `updated_at` to the logical clock's current value and increments its `version`. `version` therefore counts writes rather than requests: a write that resolves to the value every field it names already held is not a mutation and moves neither `updated_at` nor `version`, while a single request that writes the same row in two distinct steps — a status transition followed by the recomputation of a derived total on that same row — moves both twice. The two parent-`version` bumps of §2.6 are the exception: they are unconditional, and they move the parent's `version` even though no field of the parent changes. This applies to `Engineer`, `License`, `Application`, `ExperienceRecord`, `Reference`, `TestCenter`, `ExamAuthorization`, `ExamAppointment`, `FirmRegistration`, `PlanSubmission`, `CPCAudit`, `CPCReport`, `Case` and `ConsentOrder`.

`PDHRecord` is the one exception. A professional-development-hour line item is immutable once filed: it carries `id` and `created_at` only. Both `updated_at` and `version` are absent from a `PDHRecord` representation, and there is no endpoint that edits one. The board's documentation review does not rewrite the hours claimed; it records a separate review verdict in `documentation_status` on that same line item, which is the sole field of a `PDHRecord` the board may set after filing.

### 2.5. The Logical Board Clock

Every temporal rule in this specification — renewal windows, deficiency response deadlines, authorization validity envelopes, retake waiting periods, national-records-packet staleness, reinstatement grace, suspension expiry and seat-window collision arithmetic — is evaluated against a **logical clock** maintained by the server, never against real wall-clock time. On a freshly started server the logical clock reads exactly `2026-08-01T00:00:00Z`, and it continues to read that value until it is explicitly moved. Implementations must not fall back to system time at any point, the envelope's `api_request_timestamp` of §2.2 — which no rule of this specification reads — being the sole exception.

A `BoardSecretary` moves the clock by supplying a `to_iso8601` instant; the field may equivalently be sent as `current_utc`, `to_iso8601` winning when both are present, and a request carrying neither name is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The clock may only move forward or stand still: a requested value earlier than the current logical clock is rejected with `ERR_CLOCK_REWIND_FORBIDDEN` (HTTP 409). Moving the clock forward performs a single-pass time sweep in three stages, in this order.

First, every `ExamAuthorization` in `APPROVED_TO_SIT`, `SCHEDULED` or `FAILED` whose `authorization_expires_at` falls before the new clock value transitions to `EXPIRED`; each such authorization's `SCHEDULED` `ExamAppointment` transitions to `CANCELLED_BY_BOARD` and its seat is returned to the owning `TestCenter`. Second, every `License` in `ACTIVE` whose `current_period_end` falls before the new clock value transitions to `EXPIRED`, has its `reinstatement_eligible_until` stamped, and drags every `FirmRegistration` that names it in `responsible_charge_license_id` from `ACTIVE` into `LAPSED_NO_RESPONSIBLE_CHARGE`. Third, every `FirmRegistration` in `ACTIVE` or `LAPSED_NO_RESPONSIBLE_CHARGE` whose `registration_expires_at` falls before the new clock value transitions to `EXPIRED`.

The clock response is a summary object rather than an entity: `current_utc` holding the new logical clock value, `expired_authorization_count`, `expired_license_count`, `expired_firm_count`, `cancelled_appointment_count` and `lapsed_firm_count`, each an integer count of rows the sweep touched in the corresponding stage. Every row the sweep mutates has its `version` incremented and `updated_at` refreshed exactly as a directly-requested mutation would; the new clock value is installed before the sweep begins, so every such `updated_at` reads the new value rather than the value the clock held on the way in.

### 2.6. Optimistic Concurrency on Parent Records

Two write endpoints in this system deliberately permit a second, superseding write where a naive state-machine guard would have blocked it — filing a replacement competency report for a period that already has one, and proposing a renegotiated consent order that displaces an outstanding proposal. Because those supersede paths are legitimate, the state machine alone cannot distinguish a deliberate replacement from a writer acting on an outdated view of the parent record. Optimistic concurrency control on the parent's `version` is the mechanism that draws that line, and it is the only sanctioned concurrency mechanism in this specification.

A `POST /cpc-reports` request must carry `expected_license_version` — a required, non-optional input field — holding the client's last observed `version` of the `License` named in `license_id`. If that value does not equal the licence's current `version`, the create is rejected with `ERR_STALE_LICENSE_VERSION` (HTTP 412), preventing the client from superseding a report it never observed. On success the licence's `version` is itself incremented by 1, so a client filing two reports in sequence must re-read the licence between them.

A `POST /consent-orders` request must carry `expected_case_version` — likewise required and non-optional — holding the client's last observed `version` of the `Case` named in `case_id`. If that value does not equal the case's current `version`, the create is rejected with `ERR_STALE_CASE_VERSION` (HTTP 412). Because the sanction axis of a case permits a `PROPOSED` order to be replaced by another `PROPOSED` order, this stale-version check is the only thing that separates a deliberate renegotiation from a writer overwriting a proposal it has not seen. On success the case's `version` is incremented by 1.

No other endpoint in this API takes a version field. Requests to endpoints outside these two carry no `expected_license_version`, no `expected_case_version` and no equivalent, and must not be rejected for the absence of one.

### 2.7. Order of Rejection

When a single request violates several rules at once, exactly one error is returned, and which one is not a matter of implementation convenience. The board's rejection ladder is fixed, and it is walked from the top; the first rule that fails determines the response. Rules 1 through 10 are structural and apply broadly; rules 11 onward are domain rules and apply to the specific operations named in the narrative of §3.

1. Header presence and role validity — `ERR_UNAUTHENTICATED`, 401.
2. Role authorisation for the endpoint — `ERR_UNAUTHORIZED`, 403.
3. Request well-formedness — `ERR_INVALID_REQUEST`, 400. Every required input present; every enum value a declared member; every number inside its declared range; every ISO 8601 datetime parseable; `limit` between 1 and 100 and `offset` at least 0; a professional-development line item's `completed_on` inside its report's period; the `seat_labels` of a test centre all distinct; and `suspension_months` equal to 0 unless the order's `sanction_type` is `SUSPENSION`. An absent or empty request body is read as an empty JSON object, so the first required field it lacks is the one reported; a body that is not valid JSON, or that is valid JSON but not an object, is itself `ERR_INVALID_REQUEST`. A field present with a JSON `null` is treated exactly as if it had been omitted — an optional field falls back to its declared default and a required field is reported missing. A string input must be non-empty once surrounding whitespace is discounted, while any declared maximum length is measured on the value exactly as sent, and the value is stored as sent rather than trimmed. A field declared a whole number accepts `5.0` and reads it as 5 but rejects `5.5`, and a JSON boolean is never accepted where a number is declared. Body fields and query parameters the endpoint does not declare are ignored rather than rejected.
4. Path identifier existence — the matching per-entity not-found code at HTTP 404, resolved strictly left to right along the URL. Applies to every endpoint carrying a path parameter.
5. Body foreign-key existence — the matching per-entity not-found code at HTTP 404, resolved in the field order the endpoint declares its inputs. Applies to every endpoint whose input carries an identifier field.
6. Entity-backed ownership — `ERR_NOT_RESOURCE_OWNER`, 403.
7. Segregation of duties on `X-User-ID` — `ERR_SEGREGATION_OF_DUTIES`, 403.
8. Optimistic-concurrency parent version match — `ERR_STALE_LICENSE_VERSION` or `ERR_STALE_CASE_VERSION`, 412.
9. The target row's own state permits the requested transition — the matching per-entity state code at HTTP 409.
10. Cross-entity guard states hold — HTTP 409 with the code named by the guard.

Rules 11 through 46 then run in the order given here: seal-licence activity (11), referee licence activity (12), responsible-charge licence activity (13), responsible-charge identity of the sealing licence (14), self-reference prohibition (15), respondent-target well-formedness (16), education evaluated (17), experience-period overlap (18), examination window length (19), buffered seat collision (20), seat availability (21), authorization validity envelope (22), retake waiting period (23), attempt limit (24), deficiency-cycle limit (25), deficiency response window (26), pathway match (27), national-records match (28), national-records staleness (29), comity years licensed (30), verifications all adjudicated (31), sufficient verified experience (32), duplicate active licence (33), renewal window (34), competency shortfall (35), self-certification reconciliation (36), report under audit (37), audit pool non-empty (38), reinstatement window (39), reinstatement makeup hours (40), seal attestation (41), sanction axis resolved before close (42), clock monotonicity (43), application fee paid (44), penalty and reinstatement fee paid (45) and closed-audit-cycle re-draw (46). Each of these is stated in prose, together with the error it raises, in the §3 subsection that governs the operation it guards.

### 2.8. Precision and Rounding Discipline

Money is integer cents throughout; no monetary field is ever a decimal. Wherever a percentage or factor is applied to a cent amount, the product is rounded **half up** to a whole cent at the point the formula names, and at no other point. Where a formula applies a rate to a per-unit quantity and then multiplies by a count, the rounding happens on the per-unit amount **before** the multiplication; rounding the product instead produces different totals and is not acceptable.

Professional development hours are numbers carried to **one decimal place**, rounded half up. Experience credit is expressed in **whole months**, and every intermediate per-record value is truncated downward to a whole month — never rounded, never rounded up — with the sole exception of a record's stored `credit_multiplier`, which is a number to **two decimal places** rounded half up. Aggregation happens after truncation, never before.

All instants are ISO 8601 UTC with three fractional-second digits, and an instant is emitted with exactly three such digits whatever precision it was received at, any finer precision being truncated rather than rounded on the way out while the value retained for comparison keeps it. An inbound instant is accepted with a trailing `Z`, with an explicit numeric offset, or with no offset at all: an offset-bearing value is normalised to UTC before any comparison, and an offset-free value is read as already UTC. Month arithmetic on an instant preserves the time of day and, when the target month has fewer days than the source day-of-month, clamps to the last day of the target month. Day arithmetic is whole days.

### 2.9. Cascades, Postures and Conserved Ledgers

Several operations in this system mutate more than one row. Where they do, the downstream effects are not incidental bookkeeping — they are part of the operation's contract, they occur inside the same request, and they are observable immediately afterwards. This system is **immediately consistent**: there is no deferred queue, no eventual reconciliation and no background worker. When a request returns, every cascaded row already reflects its new state, with `version` incremented and `updated_at` refreshed.

Two cascade chains run deep enough to deserve naming up front, and both are specified link by link in §3. The **verification-withdrawal chain** runs from a supervising engineer's withdrawal of an accepted verification, through the experience record, the application, the exam authorization, the appointment, and finally the test centre's seat ledger — five links. The **consent-order chain** runs from the execution of a negotiated order, through the respondent's licence, the firms that licence holds in responsible charge, and the draft plan sets under those firms — four links, from a different origin.

A firm's registration status is not set by a firm-side command; it is a **derived posture**, recomputed synchronously inside whichever request changed the licence it depends on. Given the licence a firm names in `responsible_charge_license_id`, the posture is evaluated top-down in this pinned order and the first matching clause wins: if that licence is `REVOKED`, the firm is `REVOKED`; otherwise if that licence is `SUSPENDED` or `EXPIRED`, the firm is `LAPSED_NO_RESPONSIBLE_CHARGE`; otherwise if the logical clock has passed the firm's `registration_expires_at`, the firm is `EXPIRED`; otherwise the firm is `ACTIVE`. The order matters: a firm whose responsible-charge licence has been revoked is `REVOKED` even when its own registration has also run past `registration_expires_at`. A recomputation that lands on the posture the firm already held writes nothing; where it does move the firm, entry into `LAPSED_NO_RESPONSIBLE_CHARGE` stamps `lapsed_at` from the logical clock, a return to `ACTIVE` clears `lapsed_at` back to `null`, and entry into any of `LAPSED_NO_RESPONSIBLE_CHARGE`, `EXPIRED` or `REVOKED` voids every `DRAFT` plan set beneath that firm. Once a firm reads `REVOKED` the test is never applied to it again. The one departure from the test is the clock sweep of §2.5, whose three stages move firms by their own pinned rules: the sweep never moves a firm out of `EXPIRED` or `REVOKED`, and its third stage moves a firm whose `registration_expires_at` has passed to `EXPIRED` even where the licence it holds in responsible charge is suspended, or has just been expired by the second stage — a combination this test would have left at `LAPSED_NO_RESPONSIBLE_CHARGE`.

Two quantities in this system are **conserved**, meaning a forward action and its compensating action must return the world to exactly where it started. The first is a test centre's seat capacity: at the end of every single request, `seats_available` plus `seats_committed` must equal the number of entries in `seat_labels`. Booking a seat and then cancelling that booking must restore both `seats_committed` and `seats_available` to their exact pre-booking values, and every path that releases a seat — candidate cancellation, board cancellation, score reporting, the verification-withdrawal cascade, and the clock sweep — must release it identically, with no drift. The second is the experience-credit ledger: an application's `verified_experience_months` must always equal the smaller of 96 and the sum of `credited_months` across that application's experience records whose `verification_status` is `VERIFIED`. Accepting a verification and then withdrawing it must leave the affected record's `credited_months` at 0 and the application's `verified_experience_months` back at its value before the acceptance. That equality must hold after every verification evaluation, every withdrawal and every application abandonment.

### 2.10. Nested Paths, Filtered Reads and Referential Navigation

The resource topology is flat: every collection is addressed at a top-level path segment, and no URL carries more than one identifier placeholder except where a child collection is created or read beneath its parent. Where a path does carry a parent identifier followed by a child segment, the identifiers are resolved **strictly left to right**, and the first one that fails to resolve determines the 404 code returned. A request naming a nonexistent application and a nonexistent experience record reports the application's absence, not the record's.

Because parentage is expressed through foreign-key fields rather than through deep URLs, every child collection offers a filtered list form so that a caller holding a parent's `id` can find its children. `application_id` filters experience records; `experience_record_id` and `referee_engineer_id` filter verification requests; `engineer_id` filters licences and applications; `exam_authorization_id` and `test_center_id` filter appointments; `license_id`, `audit_id` and `supersedes_report_id` filter competency reports; `cpc_report_id` filters professional-development line items; `responsible_charge_license_id` filters firm registrations; `firm_registration_id` and `sealing_license_id` filter plan sets; `respondent_license_id` and `subject_plan_submission_id` filter cases; and `case_id` filters consent orders. Each of these list forms additionally accepts a `status` filter where the entity has a status field, and the domain-specific narrowing filters named in §3 — `home_jurisdiction` and `email` on the roster, `license_type` on licences, `pathway` on applications, `responsibility_level` and `verification_status` on experience records, `exam_code` on authorizations, `state_code` on test centres and firms, `activity_type` and `documentation_status` on professional-development line items, `investigation_status` and `allegation_type` on cases, and `sanction_type` on consent orders. A filter value naming a row that does not exist yields an empty page, not a 404; a malformed filter value yields `ERR_INVALID_REQUEST`. Only the filters drawn from a declared enumeration — every `status` filter and the `license_type`, `pathway`, `responsibility_level`, `verification_status`, `exam_code`, `activity_type`, `documentation_status`, `investigation_status`, `allegation_type` and `sanction_type` filters — are validated against their members and can be malformed. The identifier and free-text filters, `state_code` and `home_jurisdiction` among them, are compared verbatim and are never validated, so a value that could not possibly match — a jurisdiction written out in full, or an identifier that is not even a UUID — yields an empty page rather than a rejection. All filters supplied on one request are conjunctive, and every one of them is an exact equality comparison, never a prefix or case-insensitive match.

### 2.11. Segregation of Duties

Three pairs of board actions are statutorily incompatible, and in each case the bar is drawn on the acting `X-User-ID`, not on `X-User-Role`. Because all five board and integration roles are opaque identities, two different officers holding the same role are distinguishable, and that is exactly the distinction being enforced.

An audit decision on a competency report may not be taken by the operator whose `X-User-ID` was recorded as the deciding audit's `created_by_user_id`. Execution of a consent order may not be taken by the operator whose `X-User-ID` was recorded as the case's `assigned_investigator_user_id`. And neither examination approval nor licence issuance on an application may be taken by the operator whose `X-User-ID` was recorded as that application's `credit_determined_by_user_id`. Each bar compares the acting identity against a stamp that may not have been written yet, and a stamp still standing at `null` can never collide: the bar is simply vacuous until the stamping operation has run, and the request falls through to the rungs below it. Any of the three, violated, yields `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), and the check runs at rung 7 of the ladder — after ownership, before any version or state check — so a segregation failure is reported in preference to a stale-version or wrong-state failure on the same request.

## 3. Business Logic & Workflows

### 3.1. The Board Roster, Direct Licensure and the Testing Inventory

Before any licensure workflow can begin, the natural persons the board deals with must exist on its roster. A `BoardSecretary` registers an engineer by supplying `full_name` — a non-empty string of at most 120 characters — `email`, which must contain an `@` character — no further format is imposed on it and it carries no maximum length — and must be unique across the roster, compared as an exact case-sensitive string so that `a@b.com` and `A@B.com` are two different addresses (a repeat address is refused with `ERR_DUPLICATE_EMAIL`, HTTP 409), and `home_jurisdiction`, which must be exactly two uppercase letters denoting the USPS code of the engineer's primary jurisdiction. Where the engineer already participates in the national records program, the secretary may also supply `ncees_record_id`, an identifier between 8 and 20 characters long; it defaults to `null` and stays `null` when omitted. The identifier the board mints for the resulting roster row is the value that person will send as `X-User-ID` when acting as an `Applicant`, a `SupervisingEngineer` or a `Licensee`. A path or body identifier naming no such row is answered with `ERR_ENGINEER_NOT_FOUND` (HTTP 404).

Two roster attributes are never written directly. `active_license_number` mirrors the `license_number` of whichever licence held by that engineer currently sits in `ACTIVE`, and is `null` when the engineer holds none; it is recomputed on every licence mutation that touches that engineer, so it falls back to `null` the moment an only licence expires, is suspended or is revoked, and is restored on reinstatement. `open_case_count` holds the number of complaint records whose respondent licence belongs to that engineer and whose investigation axis stands in `RECEIVED`, `INVESTIGATING` or `PROBABLE_CAUSE`; it starts at 0 and is recomputed whenever a complaint against that engineer is opened or its investigation axis reaches a terminal close. The roster is readable one row at a time by every role in the system, and as a paginated list — narrowable by `home_jurisdiction` or `email` — by the four board roles.

Not every licence in the register arrives through an application. A `BoardLicensingOfficer` may issue one directly, which is how referee licences, firm responsible-charge licences and pre-existing licensees are seeded. Direct issuance takes `engineer_id`, a `license_type` of either `STANDARD` or `COMITY`, an `issued_on` instant — which may fall before, on or after the logical clock and is never checked against it, so a licence whose resulting period has already closed is created in `ACTIVE` and simply expires on the next clock advance — and optionally `pdh_requirement` — the professional development hours the holder owes for the current period, a number at least 0 carried to at most one decimal place, defaulting to 30 when omitted. The board mints `license_number` itself as the literal prefix `PE-` followed by a zero-padded six-digit sequence number assigned in ascending order of creation, so the first licence ever issued is `PE-000001`; the value is unique across the register. The new licence opens in `ACTIVE` with `reinstatement_eligible_until` and `suspension_ends_at` both `null` and `discipline_flag` false. An engineer may hold only one live registration: if any licence with the same `engineer_id` already stands in `ACTIVE`, issuance is refused with `ERR_DUPLICATE_ACTIVE_LICENSE` (HTTP 409). A licence identifier — whether it arrives as `license_id`, `sealing_license_id`, `responsible_charge_license_id` or `respondent_license_id` — that matches no register row yields `ERR_LICENSE_NOT_FOUND` (HTTP 404).

The first biennium is laid down at issuance. `current_period_start` is set to `issued_on`, `current_period_end` to the instant 24 months after `issued_on`, and `renewal_window_opens_at` to 90 days before `current_period_end` — so the renewal window is the last quarter-year of every two-year period. Month arithmetic keeps the time of day and, where the target month is shorter than the source day-of-month, lands on the target month's final day; a licence issued on 31 August therefore ends its period on the last day of the corresponding August two years later. These three fields are always recomputed together, and `issued_on`, `license_type`, `license_number` and the period window are the substance of what a licence read returns alongside `status` and `discipline_flag`.

Seating for the discipline examinations lives in a separate inventory that a `BoardSecretary` maintains. A test centre is registered with `name` — non-empty, at most 120 characters — `state_code`, again exactly two uppercase letters, and `seat_labels`: an ordered array of between 1 and 20 distinct non-empty workstation labels such as `S1` and `S2`. Twenty labels is the hard ceiling, and repeated labels within one array make the request malformed. An optional `status` of `OPEN` or `SUSPENDED` may be supplied, defaulting to `OPEN`; a suspended centre accepts no new bookings. The centre's `seat_count` is simply the number of entries in `seat_labels` and is never supplied by the caller; `seats_committed` starts at 0 and `seats_available` starts equal to `seat_count`. Both counters are always derived by counting the centre's appointments rather than by incremental patching (see §3.5). A `test_center_id` naming no centre answers `ERR_TEST_CENTER_NOT_FOUND` (HTTP 404). Centres are readable individually and as a list narrowable by `state_code` and `status`.

### 3.2. Opening an Application: Pathway, Education, the National Records Packet and the Assessed Fee

An `Applicant` opens a file by declaring which of the two routes to licensure they are taking. The payload carries `engineer_id`, which must be equal to the acting `X-User-ID` — an applicant may not open a file on another person's behalf, and a mismatch here is an ownership failure reported as `ERR_NOT_RESOURCE_OWNER` — together with `pathway`, either `STANDARD_EXAM` for an examination candidate or `COMITY` for an engineer already licensed in another jurisdiction. Both routes require `exam_code`, naming the discipline examination as `PE_CIVIL`, `PE_MECHANICAL` or `PE_ELECTRICAL`; the comity route needs it because the national records program's confirmation is matched against a discipline. The payload also carries `degree_level`, a required enum of `BS`, `MS` or `PHD`, and may carry `expedite_requested`, a boolean defaulting to false that buys accelerated review at a price. Once chosen, `pathway` is immutable for the life of the file. The new application opens in `DRAFT` with `education_status` at `NOT_EVALUATED`, `ncees_record_status` at `NOT_REQUESTED`, `ncees_verified_exam_pass` false, `ncees_verified_years_licensed` and `ncees_disciplinary_history_count` both 0, `ncees_record_expires_on` `null`, `provisional_experience_months` and `verified_experience_months` both 0, `deficiency_cycle_count` 0, `fee_paid_cents` 0, and `submitted_at`, `deficiency_reason`, `deficiency_due_at`, `denial_reason`, `reviewer_user_id` and `credit_determined_by_user_id` all `null`. The stored `degree_level` remains `null` until an education evaluation records it; the value on the create payload is the applicant's own claim, and the board's evaluation is the authoritative write. An `application_id` matching no file yields `ERR_APPLICATION_NOT_FOUND` (HTTP 404). Applications are readable individually and as a list narrowable by `engineer_id`, `status` and `pathway`.

A `BoardReviewer` records the transcript finding, supplying `degree_level` — one of `BS`, `MS` or `PHD` — and `accreditation_finding`, which is one of `EABET_ACCREDITED`, `NON_ACCREDITED_EVALUATED` or `REJECTED` and is written straight through to `education_status`. A `REJECTED` finding is fatal on the spot, but only out of `DRAFT`: from `DRAFT` the application moves `DRAFT → DENIED` with `denial_reason` set to the string `EDUCATION_REJECTED`, whereas the same finding recorded against a file that has already moved on writes `education_status` and `degree_level` and leaves the file's `status` exactly where it stands. The evaluation carries no state precondition of its own — it may be recorded, and re-recorded, whatever status the file is in, each recording overwriting both fields. Recording a `degree_level` re-derives every experience block's `raw_months` and `credit_multiplier` and re-runs the provisional experience-credit computation described in §3.3; in practice that recomputation leaves those figures where they stand, because a block's multiplier is derived from its own `responsibility_level` and its own `post_degree` flag rather than from the file's `degree_level`, and `post_degree` is the applicant's own assertion which the evaluation never rewrites.

For the comity route the national records program transmits the applicant's out-of-state credential packet under the `TestingService` identity. That transmission carries `ncees_record_id`, a non-empty string of at most 20 characters, `source_jurisdiction` naming the jurisdiction the credential came from — required and non-empty but of no prescribed shape, not a two-letter code, and recorded nowhere on the file — `verified_exam_pass` stating whether a passing discipline examination was confirmed elsewhere, `verified_years_licensed` giving the full years the applicant has held a licence elsewhere, `disciplinary_history_count` reporting how many disciplinary actions the program knows of, and `record_expires_on`, after which the transmitted packet is stale. Reconciliation is a straight identity comparison: `ncees_record_status` becomes `MATCHED` when the transmitted `ncees_record_id` equals the value on the applicant's roster row, and `MISMATCH` otherwise. The four transmitted facts land on the application as `ncees_verified_exam_pass`, `ncees_verified_years_licensed`, `ncees_disciplinary_history_count` and `ncees_record_expires_on`. A packet that arrives while the application is still `DRAFT` re-runs the fee assessment, because a matched national record adds a verification charge; a packet that arrives after submission has frozen the assessment never changes it. The transmission itself carries no state precondition and is accepted whatever status the file stands in, a later packet overwriting the facts an earlier one left.

The fee an applicant owes is computed by a pinned eight-step sequence, and it is worth understanding why the order is pinned. The comity discount tier looks as though it should key off the amount finally owed, but that amount already nets the discount out, which would be circular; the board's rule keys the tier off the pre-discount total instead. Step one selects the base charge: 25,000 cents for a `STANDARD_EXAM` file, 37,500 cents for a `COMITY` file. Step two prices verification work: the number of experience blocks attached to the file, multiplied by 2,500 cents apiece, plus a flat 7,500 cents when `ncees_record_status` is `MATCHED` and nothing when it is not. Step three sums the base charge and the verification charge into a subtotal. Step four adds the expedite surcharge, which is 18 percent of that subtotal rounded half up to whole cents when `expedite_requested` is true, and zero otherwise. Step five sums the subtotal and the surcharge into the pre-discount total. Step six picks the comity discount rate from that pre-discount total: 0 percent for any file whose `pathway` is not `COMITY`; otherwise 15 percent when the pre-discount total is at least 50,000 cents, 10 percent when it is at least 30,000 cents, and 5 percent below that. The thresholds are inclusive, so a pre-discount total of exactly 50,000 cents takes the 15 percent rate while 49,999 cents takes 10 percent. Step seven multiplies the pre-discount total by the chosen rate and rounds half up to whole cents. Step eight subtracts that discount from the pre-discount total, yielding `fee_assessment_cents`. Rounding happens at steps four and seven and never on the final total.

Every experience block attached to the file at evaluation time is billable regardless of its verification state — including blocks whose verification has been withdrawn, because the verification work was already performed. The assessment is recomputed when the file is created, when an experience block is added and when a national records packet arrives on a `DRAFT` file; it is recomputed once more and then permanently frozen at submission, so blocks added later never move it. Because staff and applicants both need to see how the number was reached, a read is available that exposes every intermediate: `base_fee_cents`, `records_verification_fee_cents`, `ncees_record_fee_cents`, `expedite_surcharge_cents`, `pre_credit_total_cents`, `comity_credit_tier_pct`, `comity_credit_cents` and `assessment_total_cents`. In that payload `comity_credit_tier_pct` carries the rate itself as a fraction — 0.15, 0.1, 0.05 or 0 — rather than a whole-number percentage. That read is a live recomputation from the file's current state and persists nothing, so on a file whose assessment has already been frozen its `assessment_total_cents` may differ from the stored `fee_assessment_cents`; it is available whatever status the file stands in, and its `data` is this summary object rather than an application.

Payments are recorded one at a time by the applicant, each supplying `amount_cents`, a whole number of at least 0, which is added to the running `fee_paid_cents`. A payment carries no state precondition beyond the applicant's ownership of the file: it is accepted whatever status that file stands in, including after submission and after denial, and a remittance of 0 is a legitimate no-op. Nothing prevents overpayment; the rule at submission is a floor, not an equality.

Submitting a `DRAFT` file advances it `DRAFT → SUBMITTED` and is the point at which the board's intake requirements bite. The applicant must own the file. The education evaluation must have landed on either `EABET_ACCREDITED` or `NON_ACCREDITED_EVALUATED`; a file still at `NOT_EVALUATED`, or one whose evaluation came back `REJECTED`, is refused with `ERR_EDUCATION_NOT_EVALUATED` (HTTP 422). At least one experience block must be attached; a file carrying none is refused with `ERR_APPLICATION_STATE_INVALID` (HTTP 409), and that check sits between the education gate and the fee gate. And `fee_paid_cents` must be at least `fee_assessment_cents` as it stands on the way in — the recomputation below happens only after this comparison has passed; underpayment is refused with `ERR_FEE_UNPAID` (HTTP 402), which sits at the very bottom of the rejection ladder so that every structural and eligibility problem surfaces before the money question. On success the assessment is recomputed one final time and frozen, `submitted_at` is stamped from the logical clock, every experience block still in `UNVERIFIED` that already carries at least one verification request moves to `PENDING_VERIFICATION`, and `provisional_experience_months` is recomputed.

An applicant may abandon a file that stands in `DRAFT`, `SUBMITTED`, `UNDER_REVIEW` or `DEFICIENT`, moving it to the terminal `WITHDRAWN`. Every verification request still sitting in `REQUESTED` is closed out as `REJECTED`, and when the abandonment happens out of `UNDER_REVIEW`, every experience block in `PENDING_VERIFICATION` reverts to `UNVERIFIED` — the board's verification work is unwound, and the credit ledger equality of §2.9 must still hold afterwards. Any application transition requested from a status that does not declare it — abandoning an already-issued file, submitting a file that is not `DRAFT`, or a dependent operation demanding a status the file is not in — is refused with `ERR_APPLICATION_STATE_INVALID` (HTTP 409).

### 3.3. Progressive Experience, Supervising-Engineer Verification and the Credit Ledger

Experience is claimed in blocks, each one a period of employment under a single employer at a single level of responsibility. An `Applicant` adds a block to their own file by supplying `employer_name` and `position_title` — each non-empty and at most 120 characters — `period_start_month` and `period_end_month`, both written as a four-digit year, a hyphen and a two-digit month between `01` and `12`, with the end month no earlier than the start month and both endpoints inclusive. The payload also carries `responsibility_level`, one of `SUBORDINATE`, `PROGRESSIVE` or `RESPONSIBLE_CHARGE`, and `post_degree`, a boolean asserting that the whole period falls after the qualifying degree was conferred. The claim carries no state precondition of its own beyond the applicant's ownership of the file: a block may be attached whatever status that file stands in, including after submission and after a terminal denial or withdrawal, and it always opens in `UNVERIFIED`. A block identifier matching nothing is answered with `ERR_EXPERIENCE_RECORD_NOT_FOUND` (HTTP 404); blocks are readable individually and as a list narrowable by `application_id`, `verification_status` and `responsibility_level`.

An applicant's timeline cannot be double-claimed. The claimed months of a new block are compared against the months of every existing block on the same file whose `verification_status` is not `RECANTED`, using closed inclusive month intervals with no buffer: the two sets of months are the full inclusive ranges from each block's start month through its end month, and any month appearing in both is a collision, refused with `ERR_EXPERIENCE_PERIOD_OVERLAP` (HTTP 409). Two blocks running January through June and July through December of the same year are merely adjacent and both stand; a block running January through June and a second running June through November share the month of June, and the second is refused. A block whose verification has been withdrawn is excluded from the comparison, which deliberately frees its months so the applicant can re-claim the same period under a different supervisor.

Each block carries three derived numbers. `raw_months` is the inclusive span of the claimed period: twelve times the difference in years between the end and start months, plus the difference in months, plus one — so January through June is six months, not five. `credit_multiplier` is the product of two factors, stored to two decimal places rounded half up. The first factor is the responsibility weight: 1.00 for `RESPONSIBLE_CHARGE`, 0.75 for `PROGRESSIVE` and 0.50 for `SUBORDINATE`. The second is the degree factor: 1.00 when `post_degree` is true, and 0.50 when it is false, which is the board's haircut on pre-degree work. `credited_months` is the number of months this block finally contributes to the file's verified total, and it stays at 0 for as long as the block's `verification_status` is anything other than `VERIFIED`. Adding a block to a file still in `DRAFT` also re-runs the fee assessment of §3.2, because the per-block verification charge scales with the number of blocks on the file; on a file whose assessment has already been frozen at submission the addition leaves `fee_assessment_cents` untouched, while `provisional_experience_months` is recomputed either way.

Credit is aggregated the same way in both of the two contexts where it is computed, and the rounding order within that aggregation is pinned. For each included block, multiply `raw_months` by that block's `credit_multiplier` and truncate the product downward to a whole month. Cap that truncated figure at 48 months, which is the most any single block may contribute. Multiply the capped figure by the block's weighting for the variant in force and truncate downward again. Sum those per-block contributions across every included block, and cap the sum at 96 months, which is the programme ceiling. Truncation happens per block, before summation — truncating only the sum produces different totals and is not acceptable. Blocks whose `verification_status` is `RECANTED` are excluded in both contexts, and because overlapping periods cannot coexist, no month is ever counted twice.

The two contexts differ in which blocks they include and how heavily they weight each one. The **self-reported** figure, written to `provisional_experience_months`, includes every block whose `verification_status` is `UNVERIFIED`, `PENDING_VERIFICATION`, `VERIFIED` or `DISPUTED`, and weights each at 1.00 regardless of who attested it — the applicant's own claim taken at face value. It is written when the file is submitted, when the applicant cures a deficiency, when a block is added, and when an education evaluation changes the degree level. The **board-determined** figure, written to `verified_experience_months`, includes only blocks whose `verification_status` is `VERIFIED`, and weights each block at 1.00 when the accepted verification on it came from a `DIRECT_SUPERVISOR` and at 0.50 when it came from a `PROJECT_MANAGER` or a `PEER`. Where more than one accepted verification stands on the same block, the earliest-created of them supplies the weight, and a block included under this figure carrying no accepted verification at all is weighted 1.00. Under this figure, each included block's `credited_months` is set to its own contribution, and every excluded block's `credited_months` is forced to 0. It is written when the reviewer determines credit and re-written on every verification acceptance, rejection and withdrawal. The divergence is real and observable on identical data: a `PROGRESSIVE` post-degree block spanning January 2019 through December 2022 has 48 raw months and a multiplier of 0.75, contributing 36 months provisionally — inside the single-block cap — but only 18 months finally if the accepted verification on it came from a project manager rather than a direct supervisor.

Verification is solicited by the applicant and answered by the supervising engineer. Requesting one takes `referee_engineer_id`, naming the engineer asked to attest, and `relationship`, one of `DIRECT_SUPERVISOR`, `PROJECT_MANAGER` or `PEER`. An applicant may not vouch for themselves: a `referee_engineer_id` equal to the file's own `engineer_id` is refused with `ERR_SELF_REFERENCE_FORBIDDEN` (HTTP 422). The request opens in `REQUESTED` with `evaluation_score`, `months_confirmed`, `responsibility_confirmed`, `submitted_at` and `recant_reason` all `null`. If the parent file has already been submitted, attaching the request also moves its block from `UNVERIFIED` to `PENDING_VERIFICATION`. Soliciting a verification carries no state precondition of its own: it may be attached whatever status the block or its file stands in, and a block may carry more than one. A `reference_id` matching nothing yields `ERR_REFERENCE_NOT_FOUND` (HTTP 404); verification requests are readable individually and as a list narrowable by `experience_record_id`, `referee_engineer_id` and `status`.

A `SupervisingEngineer` answers a request that names them, advancing it `REQUESTED → SUBMITTED` and supplying `evaluation_score` — an integer competency rating from 1 at the lowest to 5 at the highest — `months_confirmed`, the number of months of the claimed period the referee personally confirms, which must be at least 0 and is recorded for the board's information alone — no credit computation ever reads it, the arithmetic of the credit ledger resting on the block's own claimed span — and `responsibility_confirmed`, a boolean stating whether the referee endorses the claimed responsibility level. Two guards stand in front of this. The referee must hold a licence in `ACTIVE` at the moment of answering — an expired, suspended or revoked supervisor cannot attest, and the attempt is refused with `ERR_REFEREE_LICENSE_INACTIVE` (HTTP 422). And the block being attested must stand in `PENDING_VERIFICATION`, meaning the file has been submitted; answering against a block still in `UNVERIFIED` or already resolved is refused with `ERR_REFERENCE_STATE_INVALID` (HTTP 409). On success `submitted_at` is stamped from the logical clock.

A `BoardReviewer` then adjudicates, supplying a `decision` of either `ACCEPT` or `REJECT`, and the two branches diverge in what they leave behind. Acceptance is available only when the referee's `evaluation_score` is at least 3 and `responsibility_confirmed` is true; an `ACCEPT` decision on a verification failing either test is refused as a state conflict with `ERR_REFERENCE_STATE_INVALID` (HTTP 409). Accepting moves the request `SUBMITTED → ACCEPTED`, moves its block `PENDING_VERIFICATION → VERIFIED`, recomputes that block's `raw_months`, `credit_multiplier` and `credited_months`, and recomputes the file's `verified_experience_months` under the board-determined figure. Rejecting moves the request `SUBMITTED → REJECTED` and takes the other path entirely: the block moves `PENDING_VERIFICATION → DISPUTED`, its `credited_months` is forced to 0, and the file's `verified_experience_months` is recomputed — which will now be lower. Both branches increment the verification request's `version`. Neither branch carries a precondition on the file's own status, and the block moves only out of `PENDING_VERIFICATION`: a second verification adjudicated on a block that has already reached `VERIFIED` or `DISPUTED` records the decision on the request and recomputes the file's `verified_experience_months` but leaves the block's `verification_status` exactly where it stands. Acceptance is the forward half of the credit-ledger conservation rule of §2.9.

Withdrawal is the compensating half, and it is the deepest cascade in the system. A `SupervisingEngineer` may withdraw a verification that stands in `ACCEPTED`, supplying `recant_reason`, provided the parent file is in `UNDER_REVIEW`, `DEFICIENT` or `EXAM_APPROVED` — a withdrawal against an already-issued or denied file has no purchase and is refused as a state conflict with `ERR_APPLICATION_STATE_INVALID` (HTTP 409). Five links then fire inside that one request. First, the verification request itself moves `ACCEPTED → RECANTED` with `recant_reason` stored. Second, its block moves `VERIFIED → RECANTED` and its `credited_months` is reset to 0. Third, caused by the second link, the file's `verified_experience_months` is recomputed; and if the file was standing in `EXAM_APPROVED` and the recomputed total has fallen below 48 months, the file moves `EXAM_APPROVED → DEFICIENT`, which increments `deficiency_cycle_count` by 1, sets `deficiency_reason` to the string `EXPERIENCE_CREDIT_WITHDRAWN` and sets `deficiency_due_at` to 30 days after the logical clock's current value — the three-cycle limit of §3.4 is not tested on this path, so the counter is incremented even where it already stands at 3. Fourth, caused by the third link and not by the withdrawal itself, the file's exam authorization — if it stands in `APPROVED_TO_SIT` or `SCHEDULED` — moves to `CANCELLED`. Fifth, caused by the fourth link, every appointment under that authorization still in `SCHEDULED` moves to `CANCELLED_BY_BOARD`, and each such move decrements the owning centre's `seats_committed` by 1 and increments its `seats_available` by 1. Links four and five fire only where the third link actually demoted the file: a withdrawal out of `UNDER_REVIEW` or `DEFICIENT`, or one out of `EXAM_APPROVED` that leaves `verified_experience_months` at 48 or above, stops the chain at the third link and leaves every authorization and appointment exactly where it stands. Every row touched along the chain has its `version` incremented and its `updated_at` refreshed. Afterwards, the withdrawn block's `credited_months` must read 0 and the file's `verified_experience_months` must read exactly what it read before the acceptance being undone.

### 3.4. Board Review, Deficiency Cycles and the Licensure Fork

A `BoardReviewer` takes possession of a `SUBMITTED` file, advancing it `SUBMITTED → UNDER_REVIEW` and stamping `reviewer_user_id` with the acting `X-User-ID`. That stamp is a record of who holds the file; it is not the stamp the segregation-of-duties bar reads, which is a different field written by a different operation later in this subsection.

Review is a loop, not a straight line. When the reviewer finds the file wanting, they issue a deficiency notice with a `deficiency_reason`, moving the file `UNDER_REVIEW → DEFICIENT`. That increments `deficiency_cycle_count` by 1, stores the reason, and sets `deficiency_due_at` to 30 days after the logical clock's current value. The board tolerates three deficiency cycles in total: a notice attempted on a file whose `deficiency_cycle_count` already stands at 3 is refused with `ERR_DEFICIENCY_LIMIT_REACHED` (HTTP 409). Note that this counter is never decremented — curing a deficiency does not buy the applicant a fresh allowance.

The applicant cures a deficiency by responding inside the window, supplying a `response_note` and moving the file `DEFICIENT → UNDER_REVIEW`. The response must arrive at or before `deficiency_due_at`; a response arriving after that instant is refused with `ERR_DEFICIENCY_RESPONSE_WINDOW_CLOSED` (HTTP 409). A successful response clears both `deficiency_reason` and `deficiency_due_at` back to `null`, leaves `deficiency_cycle_count` where it stands, and re-runs the self-reported experience figure so that any blocks added during the deficiency period are reflected.

Denial is the terminal that a `BoardLicensingOfficer` reaches for when the file cannot be saved, and it always carries a `denial_reason`. It is available from `DEFICIENT`, from `UNDER_REVIEW` and from `EXAM_APPROVED`. Out of `DEFICIENT`, it requires either that the logical clock has passed `deficiency_due_at` or that `deficiency_cycle_count` has reached 3 — the officer may not short-circuit a live cure window. Out of `UNDER_REVIEW`, it requires either that `ncees_record_status` is `MISMATCH` or that `education_status` is `REJECTED`. Denial also tears down any examination arrangements: every authorization on the file standing in `APPROVED_TO_SIT` or `SCHEDULED` moves to `CANCELLED`, each such authorization's `SCHEDULED` appointment moves to `CANCELLED_BY_BOARD`, and each released seat is returned to its centre.

Before either fork of the licensure decision can be reached, somebody must convert the accepted verifications into a number the board stands behind. That is the credit determination, which either a `BoardReviewer` or a `BoardLicensingOfficer` may perform: it runs the board-determined experience figure of §3.3, writes the result to `verified_experience_months`, and stamps `credit_determined_by_user_id` with the acting `X-User-ID`. That stamp is the segregation-of-duties bar — the same operator may not later approve the examination or issue the licence on that file, and an attempt to do so is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Until the determination has run, `credit_determined_by_user_id` is `null` and neither fork is available. The determination itself carries no state precondition: it may be run, and re-run, whatever status the file stands in, and every run re-stamps `credit_determined_by_user_id` with the acting `X-User-ID`, so a second officer who re-runs it displaces the first stamp and takes the bar onto themselves — which is also how a file blocked by the bar can be unblocked.

The fork itself is the structural heart of the review workflow. A `STANDARD_EXAM` file leaves `UNDER_REVIEW` for `EXAM_APPROVED`; a `COMITY` file leaves `UNDER_REVIEW` for `LICENSE_ISSUED` directly, never receiving an examination authorization at all. Requesting the wrong one for the file's `pathway` — examination approval on a comity file, or direct comity issuance on an examination file — is refused with `ERR_PATHWAY_MISMATCH` (HTTP 409).

Examination approval, taken by a `BoardLicensingOfficer`, requires four things beyond the pathway match. The credit determination must have run and must have been run by a different operator. No verification request anywhere on the file may be left hanging: every one of them must have reached `ACCEPTED` or `REJECTED`, and one still sitting in `REQUESTED` or `SUBMITTED` — or a missing credit determination — is refused with `ERR_REFERENCE_NOT_ACCEPTED` (HTTP 422). And `verified_experience_months` must be at least 48; a file at 47 months is refused with `ERR_EXPERIENCE_INSUFFICIENT` (HTTP 422), while a file at exactly 48 passes. On success the file moves `UNDER_REVIEW → EXAM_APPROVED` and the board mints one examination authorization, opening in `APPROVED_TO_SIT` with `exam_code` copied from the file, `attempt_number` at 1, `result` at `PENDING`, `raw_score` and `retake_eligible_at` and `ncees_transmission_id` all `null`, and `authorization_expires_at` set to 365 days after the logical clock's current value. The response body is that authorization, and the status code is 201 because a new resource was created.

Comity issuance out of `UNDER_REVIEW` is guarded much more heavily, because the board is accepting another jurisdiction's judgement in place of its own examination. Beyond the pathway match, the credit determination stamp and the segregation-of-duties bar, it requires that `ncees_record_status` be `MATCHED` and `ncees_verified_exam_pass` be true — an absent, mismatched or examination-silent packet is refused with `ERR_NCEES_RECORD_NOT_MATCHED` (HTTP 422); that the logical clock has not passed `ncees_record_expires_on`, a stale packet being refused with `ERR_NCEES_RECORD_EXPIRED` (HTTP 422); that `ncees_verified_years_licensed` be at least 4, fewer years being refused with `ERR_COMITY_YEARS_INSUFFICIENT` (HTTP 422); that `verified_experience_months` be at least 48; and that the engineer hold no licence already standing in `ACTIVE`, a duplicate being refused with `ERR_DUPLICATE_ACTIVE_LICENSE` (HTTP 409).

The examination route rejoins at the same terminal but through a different door and with different preconditions. From `EXAM_APPROVED`, issuance requires the file's `pathway` to be `STANDARD_EXAM`, the authorization on the file to stand in `PASSED`, `verified_experience_months` to be at least 48, and again no existing `ACTIVE` licence for that engineer. Both doors lead to `LICENSE_ISSUED`, and both mint a licence in `ACTIVE` with `issued_on` set to the logical clock's current value, `pdh_requirement` at 30, and the first biennium laid down exactly as in §3.1 — but the comity door writes `license_type` `COMITY` and the examination door writes `license_type` `STANDARD`. Both doors recompute the engineer's `active_license_number`. The response is the new licence and the status code is 201.

### 3.5. Examination Authorization, Seat Booking and Score Reporting

An authorization is the candidate's standing permission to sit a discipline examination, and its 365-day envelope from `authorization_expires_at` is absolute. Authorizations are readable individually and as a list narrowable by `application_id`, `status` and `exam_code`; an `exam_authorization_id` matching nothing answers `ERR_EXAM_AUTHORIZATION_NOT_FOUND` (HTTP 404), and any authorization or appointment transition requested from a status that does not declare it is refused with `ERR_EXAM_STATE_INVALID` (HTTP 409).

Booking a seat is the applicant's move, and it advances the authorization `APPROVED_TO_SIT → SCHEDULED` while creating an appointment in `SCHEDULED`. The payload carries `exam_authorization_id`, `test_center_id`, `seat_label` naming the workstation to reserve, and `window_start` and `window_end` bounding the sitting as a half-open interval — the start instant is inside the reservation and the end instant is not. The candidate must own the authorization, by way of the file it belongs to, and that file must stand in `EXAM_APPROVED`; a booking against a file in any other status is refused with `ERR_APPLICATION_STATE_INVALID` (HTTP 409). The `seat_label` must be one of the centre's declared `seat_labels`; a label the centre does not offer answers `ERR_SEAT_LABEL_NOT_FOUND` (HTTP 404), and because that is an existence check it is tested at rung 5 of the ladder — ahead of the ownership and state failures just described, so a candidate booking somebody else's authorization onto a label the centre does not offer is told the label is unknown rather than that the authorization is not theirs.

Three domain checks then run in a fixed order, and the order determines which error a badly-formed booking sees. The window length is checked first: `window_end` must be exactly 480 minutes — eight hours — after `window_start`, and any other span is refused with `ERR_EXAM_WINDOW_LENGTH_INVALID` (HTTP 422). Only then is the seat's own calendar consulted, and only then is aggregate capacity consulted. A booking whose window is 479 minutes long against a full centre therefore reports the window error, not the capacity error. Neither window endpoint is ever compared against the logical clock or against the authorization's `authorization_expires_at`: a window lying wholly in the past, or one running out beyond the envelope, is bookable so long as the clock itself is still inside the envelope when the booking is taken.

Seat collision is evaluated per labelled seat, at minute granularity, with an asymmetric trailing turnover buffer. Each existing appointment on the same centre and the same `seat_label` that still stands in `SCHEDULED` is inflated by appending 45 minutes to its `window_end`; the new booking collides with it when the new `window_start` falls strictly before that inflated end **and** the new booking's own inflated end falls strictly after the existing `window_start`. Any collision is refused with `ERR_SEAT_WINDOW_CONFLICT` (HTTP 409). Because both comparisons are strict, a booking starting exactly 45 minutes after an existing window's end does not collide, while one starting 44 minutes after it does. Appointments on different `seat_labels` of the same centre never collide with one another; they compete only through the capacity dimension below.

Capacity is the third check and the coarsest. The centre must have `seats_available` of at least 1 and must stand in `OPEN`; a full centre or a `SUSPENDED` one is refused with `ERR_NO_SEAT_AVAILABLE` (HTTP 409). Finally, the logical clock must be strictly before the authorization's `authorization_expires_at`; a lapsed envelope is refused with `ERR_AUTHORIZATION_EXPIRED` (HTTP 409). On success, the owning centre's `seats_committed` rises by 1 and its `seats_available` falls by 1, and both the authorization's and the centre's `version` are incremented. This is the forward half of the seat-capacity conservation rule. The centre's counters are always derived by counting that centre's appointments still in `SCHEDULED` — appointments in `COMPLETED`, `CANCELLED_BY_CANDIDATE` or `CANCELLED_BY_BOARD` never occupy a seat — and are never patched incrementally. Appointments are readable individually and as a list narrowable by `exam_authorization_id`, `test_center_id` and `status`; an `exam_appointment_id` matching nothing answers `ERR_EXAM_APPOINTMENT_NOT_FOUND` (HTTP 404).

Cancellation is the compensating half, and who cancels determines which terminal the appointment lands in. An `Applicant` cancelling their own booking sends it to `CANCELLED_BY_CANDIDATE`; a `BoardSecretary` cancelling on the board's behalf sends it to `CANCELLED_BY_BOARD`. Either way an optional `reason` may accompany the request — validated as a non-empty string when present, of no maximum length, and recorded on no row — the appointment must still stand in `SCHEDULED`, and the logical clock must be strictly before `window_start`: a sitting already begun cannot be cancelled, and either objection is refused with `ERR_EXAM_STATE_INVALID` (HTTP 409). The authorization returns `SCHEDULED → APPROVED_TO_SIT`, which is the cyclic edge that lets the candidate re-book, and the seat is released: `seats_committed` falls by 1 and `seats_available` rises by 1, restoring both counters to exactly their pre-booking values.

Scores arrive from the `TestingService` identity against a `SCHEDULED` authorization, carrying `raw_score` — an integer between 0 and 100 — `administered_at` naming the instant the sitting was held, and `ncees_transmission_id`, the opaque transmission handle the testing service supplies. The authorization must have an appointment standing in `SCHEDULED` whose `window_end` is at or before the logical clock's current value; the board does not accept a score for a sitting that has not finished, and an authorization with no such appointment is refused with `ERR_EXAM_STATE_INVALID` (HTTP 409). The reported `administered_at` is never compared against the logical clock or against the sitting's own window and is stored on no row: it serves solely as the base instant for the retake clock below. The passing mark is 70, and the two outcomes diverge. A `raw_score` of 70 or above moves the authorization `SCHEDULED → PASSED` and sets `result` to `PASS`. A `raw_score` below 70 moves it `SCHEDULED → FAILED`, sets `result` to `FAIL`, and additionally sets `retake_eligible_at` to 90 days after the reported `administered_at` instant. Both outcomes store `raw_score` and `ncees_transmission_id`, move the linked appointment `SCHEDULED → COMPLETED`, and release its seat by decrementing `seats_committed` and incrementing `seats_available` — the scoring path and the cancellation path must release a seat identically, with no drift.

A failed candidate re-arms the same authorization rather than obtaining a new one. Retaking consults the authorization alone — the status of the file it belongs to is never tested, so a file that has since fallen back to `DEFICIENT` may still re-arm its `FAILED` authorization even though it could not then book a seat with it. Retaking moves it `FAILED → APPROVED_TO_SIT`, increments `attempt_number` by 1, resets `raw_score` to `null`, `result` to `PENDING` and `retake_eligible_at` to `null`; `ncees_transmission_id` is not reset, and goes on holding the handle the failed sitting's score report wrote until the next report overwrites it. Three conditions gate it: the logical clock must have reached `retake_eligible_at`, an early attempt being refused with `ERR_RETAKE_WAITING_PERIOD` (HTTP 409); `attempt_number` must be below 3, a fourth sitting being refused with `ERR_ATTEMPT_LIMIT_REACHED` (HTTP 409); and the logical clock must still be before `authorization_expires_at`. That last condition matters because `authorization_expires_at` is never extended by a retake — the original 365-day envelope caps the whole retake loop, and a candidate who fails late in the envelope may find the waiting period runs past it. When the clock sweep of §2.5 finds an authorization in `APPROVED_TO_SIT`, `SCHEDULED` or `FAILED` whose envelope has lapsed, it moves that authorization to the terminal `EXPIRED`.

### 3.6. Continuing Professional Competency: Reporting, Hour Valuation and Audit Sampling

Every biennium a `Licensee` accounts for their continuing professional competency by filing a report against their own licence. The filing carries `license_id`, `period_start` and `period_end` bounding the renewal period being reported — `period_end` must equal that licence's `current_period_end`, and although a mismatch is reported as `ERR_INVALID_REQUEST` (HTTP 400) it is tested only after the ownership and stale-version rungs, so a wrong-period filing that is also unowned or stale reports the ownership or version failure in preference; `period_start` is never compared against `period_end` at all, and a start standing after the end is accepted — `self_certified_pdh`, the total hours the licensee declares for the period as a number at least 0 carried to at most one decimal place, and optionally `carryover_pdh_claimed`, hours brought forward from the previous period, defaulting to 0 and likewise at most one decimal place. It must also carry `expected_license_version`, the concurrency guard described in §2.6. The report opens in `SUBMITTED` with `audit_id` and `audit_decided_by_user_id` at `null` — and `supersedes_report_id` at `null` too, except on the supersede path described in the next paragraph. Only the self-certified side is computed at filing time, and over an empty set of line items that reduces to the capped carryover alone: `self_certified_total_pdh` opens at the smaller of `carryover_pdh_claimed` and 15 rounded to one decimal place, and `shortfall_pdh` opens at the self-certified shortfall that follows from it, carrying the whole 2-hour ethics floor because no ethics hours have been claimed yet. `audit_verified_total_pdh` opens at exactly 0 however much carryover was claimed, and stays there until an audit context first touches the report. Both totals are part of the creation rather than a second write, so the new report reads `version` 1. Filing increments the licence's `version` by 1.

Re-filing for a period that already has a report is legitimate and deliberate: the earlier report moves `SUBMITTED → SUPERSEDED` and the new report's `supersedes_report_id` is pointed at it. Only a predecessor still standing in `SUBMITTED` is displaced this way, and where more than one somehow qualifies it is the most recently created of them; a predecessor for the same period that has already reached `ACCEPTED`, `UNDER_AUDIT`, `AUDIT_CLEARED`, `AUDIT_DEFICIENT` or `SUPERSEDED` is left exactly as it stands and the new report's `supersedes_report_id` stays `null`, so a licence may legitimately carry a fresh `SUBMITTED` report alongside an older accepted or audited one for the very same period. That is exactly why the concurrency guard exists — no state precondition would have blocked the second filing, so the stale-version check is the only thing preventing a client from displacing a report it never read. A `cpc_report_id` in the path matching nothing answers `ERR_CPC_REPORT_NOT_FOUND` (HTTP 404) — a `supersedes_report_id` supplied as a list filter is compared verbatim and yields an empty page rather than a 404, exactly as §2.10 requires — and a report transition requested from a status that does not declare it — accepting a `SUPERSEDED` report, for instance — is refused with `ERR_CPC_REPORT_STATE_INVALID` (HTTP 409). Reports are readable individually and as a list narrowable by `license_id`, `audit_id`, `supersedes_report_id` and `status`.

Hours are claimed one activity at a time as line items beneath the report. Each carries `activity_type` — one of `COURSE`, `SEMINAR`, `TEACHING`, `PUBLICATION`, `PATENT` or `SELF_STUDY` — `pdh_hours`, a number strictly greater than 0 and no greater than 40 carried to at most one decimal place, `completed_on`, the instant the activity was finished, which must fall inside the report's period from `period_start` through `period_end` inclusive, and optionally `ethics_flag`, a boolean defaulting to false marking the activity as carrying professional-ethics content. Each line item opens with `documentation_status` at `NONE`. No precondition is placed on the owning report's own status: a line item may be filed beneath a report standing in any status at all — one already `ACCEPTED`, one drawn `UNDER_AUDIT`, one that has reached `AUDIT_CLEARED` or `AUDIT_DEFICIENT`, or one long `SUPERSEDED`. Every filing re-runs the totals for whichever context matches that status, so adding an item beneath an `ACCEPTED` report rewrites its `self_certified_total_pdh` and `shortfall_pdh` after the fact — the declared `self_certified_pdh` is not touched and no longer reconciles with the recomputed figure — and can therefore cure or create the shortfall the renewal gate of §3.7 reads without any further board action. Line items are immutable, as §2.4 explains; a `pdh_record_id` matching nothing answers `ERR_PDH_RECORD_NOT_FOUND` (HTTP 404). They are readable individually and as a list narrowable by `cpc_report_id`, `activity_type` and `documentation_status`.

The hour total is computed in five steps, and each activity category is capped independently before anything is summed. Step one, for each of the six categories in turn, sums the `pdh_hours` of the report's included line items in that category and takes the smaller of that sum and the category's ceiling: 30 hours for `COURSE`, 30 for `SEMINAR`, 10 for `TEACHING`, 10 for `PUBLICATION`, 10 for `PATENT`, and for `SELF_STUDY` a ceiling that depends on the context in force. Step two sums the six capped figures into an activity subtotal. Step three takes the smaller of `carryover_pdh_claimed` and 15 hours, which is the board's carryover ceiling. Step four adds the activity subtotal and the capped carryover and rounds the result half up to one decimal place, giving the report's total.

Step five treats ethics as a **separate floor rather than part of the hour count**, and the two deficiencies are **additive**. Sum the `pdh_hours` of every included line item whose `ethics_flag` is true. The hour deficiency is the licence's `pdh_requirement` minus the report's total, or 0 if that difference would be negative. The ethics deficiency is 2 hours minus the ethics hours just summed, or 0 if that difference would be negative. `shortfall_pdh` is the sum of those two deficiencies, rounded half up to one decimal place. A licensee who logged 30 hours but none of them on ethics therefore carries a shortfall of 2.0, not 0.

Two contexts compute this total, and they differ in exactly two places. The **self-certified** context governs while a report stands in `SUBMITTED` or `ACCEPTED`, takes the licensee's attestation at face value, includes every line item whose `documentation_status` is `NONE` or `ACCEPTED` — only `REJECTED` documentation is dropped — allows `SELF_STUDY` a ceiling of 8 hours, and writes its result to `self_certified_total_pdh`. The **audit-verified** context governs while a report stands in `UNDER_AUDIT`, `AUDIT_CLEARED` or `AUDIT_DEFICIENT`, demands proof, includes only line items whose `documentation_status` is `ACCEPTED`, allows `SELF_STUDY` a ceiling of 0 hours — unproctored self study earns nothing under audit — and writes its result to `audit_verified_total_pdh`. Both contexts write `shortfall_pdh`, each under its own inclusion rule; the field always reflects whichever context matches the report's current status. A report standing in `SUPERSEDED` matches neither context: its `self_certified_total_pdh` and `shortfall_pdh` stand frozen at the values they last held, even where a line item is added beneath it, though a documentation review on one of its line items still rewrites `audit_verified_total_pdh`. On identical line items the divergence is stark: a report whose 30 declared hours include 8 hours of self study and whose documentation was never submitted reads 30.0 self-certified and 14.0 audit-verified.

Routine acceptance is a `BoardReviewer` action on a `SUBMITTED` report that has not been drawn into an audit, moving it `SUBMITTED → ACCEPTED`. It requires the licensee's arithmetic to reconcile: `self_certified_pdh` as declared must equal the recomputed `self_certified_total_pdh`, and a discrepancy is refused with `ERR_PDH_SELF_CERT_MISMATCH` (HTTP 422). Acceptance also recomputes `shortfall_pdh` under the self-certified context, which is the figure the renewal gate of §3.7 will read.

Audit sampling is drawn by a `BoardSecretary` or a `BoardReviewer` over one renewal period at a time. The draw carries `audit_cycle_label`, a human label of at most 40 characters that must be unique across all draws — a repeat is refused with `ERR_DUPLICATE_AUDIT_CYCLE` (HTTP 409) — `sample_pct`, the fraction of the eligible pool to draw, which must be greater than 0 and no greater than 1, and `as_of_period_end`, the renewal-period end date that defines the pool. A period whose audit cycle has already been closed can never be re-drawn: if any draw with status `CLOSED` already exists for the requested `as_of_period_end`, the request is refused with `ERR_AUDIT_STATE_INVALID` (HTTP 409). That bar is tested before the eligible pool is assembled at all — ahead of the pool-non-empty test, notwithstanding its later position in the ladder of §2.7 — so a re-draw against a closed cycle is refused as a state conflict even where the pool would have come back empty as well. A `cpc_audit_id` in the path matching nothing answers `ERR_CPC_AUDIT_NOT_FOUND` (HTTP 404); an `audit_id` supplied as a list filter yields an empty page instead.

Eligibility is an explicit predicate. A report enters the pool when it stands in `ACCEPTED`, its `period_end` equals the draw's `as_of_period_end`, its `audit_id` is still `null`, and the licence it covers stands in `ACTIVE` or `EXPIRED` — suspended and revoked licensees are handled through the disciplinary track instead. The count of qualifying reports is recorded as `pool_size`. If nothing qualifies, the draw is refused with `ERR_AUDIT_POOL_EMPTY` (HTTP 409) and no audit row is persisted at all.

Ranking audits the thinnest margins first. Each pooled report's margin is its `self_certified_total_pdh` minus the `pdh_requirement` of the licence it covers, and the pool is ordered by that margin ascending. Ties break first on `created_at` ascending and then on the licence's `license_number` ascending; the report's own `id` is never a decision input. The number drawn is the larger of 1 and the pool size multiplied by `sample_pct` rounded up to a whole number, then reduced if necessary to no more than the pool size — so a non-empty pool always yields at least one report, and a pool of one report at a 10 percent rate still yields exactly one. That count is recorded as `sampled_count`, the draw opens in `SAMPLED`, and `created_by_user_id` is stamped with the acting `X-User-ID`, which is the bar that later prevents that same operator from deciding any report in this sample. Each selected report, taken from the head of the ordering, moves `ACCEPTED → UNDER_AUDIT`, has its `audit_id` pointed at the new draw, and has both `audit_verified_total_pdh` and `shortfall_pdh` recomputed under the audit-verified context, all in one write.

Documentation review is where the audit-verified figure earns its name. A `BoardReviewer` reviews the evidence behind one line item at a time, supplying a `decision` of `ACCEPT` or `REJECT`, which sets that line item's `documentation_status` to `ACCEPTED` or `REJECTED` respectively and re-runs the audit-verified total on the owning report. The owning report's status is never tested here: any line item may be reviewed at any time, one already reviewed may be reviewed again with the opposite verdict, and `audit_verified_total_pdh` is rewritten on every such review whatever status the report stands in. Where that report stands in `SUBMITTED` or `ACCEPTED`, the review additionally rewrites `self_certified_total_pdh` and `shortfall_pdh` under the self-certified context, because a `REJECTED` line item drops out of that context too — so rejecting the documentation behind an accepted report's hours can open a shortfall that blocks its renewal, and the report is written twice inside the one request, moving its `version` twice where both writes land on something new.

Adjudication closes out one `UNDER_AUDIT` report, again by a `BoardReviewer`, with a `decision` of `CLEAR` or `DEFICIENT`. The report must actually stand in `UNDER_AUDIT`; an attempt against a report in any other status is refused with `ERR_REPORT_NOT_UNDER_AUDIT` (HTTP 409). The acting `X-User-ID` must differ from the `created_by_user_id` of the draw that selected the report. Both totals are recomputed under the audit-verified context first, and the recomputed `shortfall_pdh` decides which terminal is legitimate: a shortfall of exactly 0 supports `CLEAR`, sending the report to `AUDIT_CLEARED`, and a shortfall above 0 supports `DEFICIENT`, sending it to `AUDIT_DEFICIENT`. A decision contradicting the recomputed shortfall is refused as a state conflict with `ERR_CPC_REPORT_STATE_INVALID` (HTTP 409). Either terminal stamps `audit_decided_by_user_id` with the acting `X-User-ID`, and the `AUDIT_DEFICIENT` branch additionally sets the covered licence's `discipline_flag` to true. When the decision leaves no report of that draw still standing in `UNDER_AUDIT`, the draw itself bubbles up `SAMPLED → CLOSED`. The consequence of the deficient branch reaches into the next subsection: because renewal demands a report in `ACCEPTED` or `AUDIT_CLEARED`, a licence whose current-period report lands in `AUDIT_DEFICIENT` can no longer be renewed at all.

### 3.7. Renewal, Expiry and Reinstatement

Renewal is a self-loop: a licence in `ACTIVE` stays in `ACTIVE`, and only its period window moves. A `Licensee` renews their own licence, and two gates stand in front of it. The logical clock must fall at or after `renewal_window_opens_at` and at or before `current_period_end`; a request outside that 90-day window at either end is refused with `ERR_RENEWAL_WINDOW_CLOSED` (HTTP 409). And a competency report must exist for that licence whose `period_end` equals the licence's `current_period_end`, whose status is either `ACCEPTED` or `AUDIT_CLEARED`, and whose `shortfall_pdh` is exactly 0; anything else — no report, a superseded report, an `AUDIT_DEFICIENT` report, or a cleared report still carrying a shortfall — is refused with `ERR_CPC_SHORTFALL` (HTTP 422).

The period roll on renewal chains off the **old** period end rather than off the renewal instant, so renewing early never shortens the biennium. `current_period_start` becomes the old `current_period_end`, the new `current_period_end` becomes 24 months after the old one, and `renewal_window_opens_at` is recomputed as 90 days before the new period end.

Expiry is not a command; it happens to a licence when the clock sweep of §2.5 finds it in `ACTIVE` with a `current_period_end` behind the new clock value. The licence moves `ACTIVE → EXPIRED`, and at that instant — and only at that instant — `reinstatement_eligible_until` is stamped at 730 days after `current_period_end`, giving a two-year grace window. The engineer's `active_license_number` is recomputed, falling to `null` when this was their only live licence, and every firm holding this licence in responsible charge is dragged from `ACTIVE` into `LAPSED_NO_RESPONSIBLE_CHARGE`.

Reinstatement is a `BoardLicensingOfficer` action and serves two quite different postures. It carries `makeup_pdh`, the remedial hours the holder has completed as a number at least 0 carried to at most one decimal place, and `reinstatement_fee_cents`, the money remitted as a number at least 0. `makeup_pdh` must be at least 15, and a lesser figure is refused with `ERR_REINSTATEMENT_MAKEUP_INSUFFICIENT` (HTTP 422); `reinstatement_fee_cents` must be at least 45,000 cents, and underpayment is refused with `ERR_PENALTY_UNPAID` (HTTP 402). The temporal gate differs by posture: an `EXPIRED` licence may be reinstated only while the logical clock stands at or before `reinstatement_eligible_until`, whereas a `SUSPENDED` licence may be reinstated only once the logical clock has reached `suspension_ends_at`. Either gate failing — a lapsed grace window, or a suspension that has not yet run its course — is refused with `ERR_REINSTATEMENT_WINDOW_EXPIRED` (HTTP 409).

The disciplinary gates differ by posture too, and both must be stated. An `EXPIRED` licence cannot be reinstated at all if any consent order against it has reached `EXECUTED` with a `sanction_type` of `REVOCATION` — revocation is permanent, and that objection is reported as `ERR_LICENSE_STATE_INVALID` (HTTP 409), tested immediately after the licence's own status and therefore ahead of the temporal gate. A `SUSPENDED` licence additionally requires that every consent order against it standing in `EXECUTED` has `penalty_paid_cents` at least equal to its `penalty_cents`; an unpaid penalty blocks the return with `ERR_PENALTY_UNPAID` (HTTP 402).

Both postures return the licence to `ACTIVE` and open a **fresh** biennium measured from the reinstatement instant rather than from the old period end: `current_period_start` becomes the logical clock's current value, `current_period_end` becomes 24 months later, and `renewal_window_opens_at` is recomputed accordingly. Reinstating from `EXPIRED` clears `reinstatement_eligible_until` back to `null`; reinstating from `SUSPENDED` clears `suspension_ends_at` back to `null`. Either way the engineer's `active_license_number` is restored, and every firm holding this licence in responsible charge has its posture recomputed by the four-clause test of §2.9 rather than being moved by fiat: such a firm returns from `LAPSED_NO_RESPONSIBLE_CHARGE` to `ACTIVE` with its `lapsed_at` cleared to `null`, unless the logical clock has already run past its own `registration_expires_at`, in which case the recomputation lands it in `EXPIRED` instead, and a firm already standing in `REVOKED` is left there. The duplicate-active-licence bar of §3.1 is not re-tested on this path: reinstatement returns the licence to `ACTIVE` even where the same engineer already holds another `ACTIVE` licence, and `active_license_number` then mirrors whichever of them the register reaches first in creation order. What is never cleared is `discipline_flag`: once any consent order against a licence has been executed, that flag reads true permanently, because the disciplinary record survives the reinstatement. A licence transition requested from a status that does not declare it — renewing an `EXPIRED` licence, reinstating an `ACTIVE` one, or anything at all against a `REVOKED` one — is refused with `ERR_LICENSE_STATE_INVALID` (HTTP 409).

### 3.8. Firm Registration, Responsible Charge and Plan Sealing

A firm may not practise engineering on its own authority; it practises through a single licensee held in responsible charge, and the firm's standing in the register is nothing more than a projection of that licensee's standing. A `BoardLicensingOfficer` registers a firm with `firm_name`, a non-empty business name of at most 160 characters that must be unique across the register — the comparison is exact and case-sensitive and it spans every firm row whatever its status, so a lapsed, expired or revoked registration goes on holding its name, and a repeat is refused with `ERR_DUPLICATE_FIRM_NAME` (HTTP 409), tested before the nominated licence's own status is examined — `state_code`, exactly two uppercase letters giving the USPS code of the registered office, and `responsible_charge_license_id`, the licence taking responsible charge. That licence must stand in `ACTIVE`; anything else is refused with `ERR_RESPONSIBLE_CHARGE_LICENSE_INACTIVE` (HTTP 422). Nothing bars one licence from standing in responsible charge of several firms at once, and where it does, every one of those firms tracks that licence's fate together. The firm opens in `ACTIVE` with `lapsed_at` at `null` and `registration_expires_at` at 365 days after the logical clock's current value, and answers HTTP 201. The `id` of the row returned is the identifier the firm's administrator presents as `X-User-ID` under the `FirmAdmin` role, so that role's ownership check is simply that the firm being acted on is the firm the caller is. A `firm_registration_id` matching nothing answers `ERR_FIRM_REGISTRATION_NOT_FOUND` (HTTP 404). Firms are readable individually and as a list narrowable by `responsible_charge_license_id`, `status` and `state_code`.

The firm's `status` is never set by hand. It is recomputed from the responsible-charge licence at firm creation, at every nomination, on every licence status transition touching a licence held in responsible charge, and on every clock advance, by the four-clause test pinned in §2.9 — subject to the sweep's own departure from that test recorded there: revocation of the responsible-charge licence makes the firm `REVOKED`; suspension or expiry of that licence makes the firm `LAPSED_NO_RESPONSIBLE_CHARGE`; a clock past `registration_expires_at` makes the firm `EXPIRED`; otherwise the firm is `ACTIVE`. Because the clauses are tested in that order, a firm whose responsible-charge licence has been revoked reads `REVOKED` even when its own registration has also run past `registration_expires_at`.

A firm that has lost its responsible charge cures itself by nominating a replacement. The `FirmAdmin` of that firm supplies a new `responsible_charge_license_id`, which must itself stand in `ACTIVE` — the same `ERR_RESPONSIBLE_CHARGE_LICENSE_INACTIVE` (HTTP 422) applies — and the logical clock must stand at or before `registration_expires_at`, a registration that has already run out being refused with `ERR_FIRM_STATE_INVALID` (HTTP 409). That expiry gate is tested only after the nominated licence's status, so a firm past its own registration end that nominates an inactive licence is told the licence is inactive rather than that the registration has expired. On success the firm moves `LAPSED_NO_RESPONSIBLE_CHARGE → ACTIVE`, `responsible_charge_license_id` is replaced with the nominated licence, and `lapsed_at` is cleared to `null`; all three fields move in a single write, so the firm's `version` advances by exactly 1 and the posture recomputation is not a second, separately counted write of that row. This is a compensating edge, but it is deliberately **not** a full undo: plan sets that were voided while the firm was lapsed stay voided and are never resurrected. A firm transition requested from a status that does not declare it, or an operation demanding an `ACTIVE` firm that finds one in any other posture, is refused with `ERR_FIRM_STATE_INVALID` (HTTP 409). `REVOKED` is terminal.

Plan sets are filed by the `FirmAdmin` under its own firm, carrying `firm_registration_id`, `project_name`, a non-empty project title of at most 160 characters, and `sheet_count`, the number of drawing sheets in the set as a whole number from 1 through 500. Filing demands nothing of the firm's own posture: a `DRAFT` set may be filed beneath a firm standing in `LAPSED_NO_RESPONSIBLE_CHARGE`, `EXPIRED` or `REVOKED` just as readily as beneath an `ACTIVE` one, and because the voiding of §2.9 fires only where a firm's posture actually moves, such a set is not voided on filing and survives every later recomputation that lands the firm back on the posture it already held. The set opens in `DRAFT` with `sealing_license_id` at `null`, `responsible_charge_attested` at false and `seal_affixed_at` at `null`, and answers HTTP 201. The sheet count matters far beyond the filing: it is the multiplier of the per-sheet component of the civil penalty should the set later be found improperly stamped. A `plan_submission_id` in the path, or a `subject_plan_submission_id` naming the subject of a new case, matching nothing answers `ERR_PLAN_SUBMISSION_NOT_FOUND` (HTTP 404); the `firm_registration_id`, `sealing_license_id` and `subject_plan_submission_id` list filters, by contrast, are compared verbatim, and a value matching nothing yields an empty page rather than a 404, exactly as §2.10 requires. Plan sets are readable individually and as a list narrowable by `firm_registration_id`, `sealing_license_id` and `status`.

Sealing is the act that puts a licensee's professional liability behind the drawings, and it is guarded four times over. A `Licensee` seals a `DRAFT` set by supplying `sealing_license_id`, the licence whose seal is affixed, and `responsible_charge_attested`, the sealer's attestation that they were personally in responsible charge of the work. The nominated licence must belong to the caller. Beyond that, the order of the remaining checks is deliberately chosen and observable. First the firm must stand in `ACTIVE`, otherwise `ERR_FIRM_STATE_INVALID` (HTTP 409). Then, at rung 11, the sealing licence itself must stand in `ACTIVE`, otherwise `ERR_SEAL_LICENSE_NOT_ACTIVE` (HTTP 422). Only then, at rung 14, must the sealing licence be the very licence the firm holds in responsible charge, otherwise `ERR_NOT_RESPONSIBLE_CHARGE` (HTTP 422). And last, at rung 41, `responsible_charge_attested` must be true, otherwise `ERR_ATTESTATION_MISSING` (HTTP 422). The consequence is that a revoked outsider who tries to stamp a firm's drawings is told their licence is not active — the public-safety objection — rather than that they are not the firm's responsible charge, even though both statements are true. On success the set moves `DRAFT → SEALED`, both supplied fields are written, and `seal_affixed_at` is stamped from the logical clock.

Two exits leave `DRAFT` and `SEALED` behind, and both are terminal. A `BoardInvestigator` may flag a `SEALED` set as suspect stamping by supplying a `reason`, moving it `SEALED → FLAGGED`; the same transition also occurs as a side effect of a probable-cause finding on a case whose `subject_plan_submission_id` names the set. And a `DRAFT` set is voided — `DRAFT → VOIDED` — whenever its firm falls into `LAPSED_NO_RESPONSIBLE_CHARGE`, `EXPIRED` or `REVOKED`, whether that happened through the consent-order cascade, through either firm-touching stage of the clock sweep — the expiry of the licence it holds in responsible charge, or the lapse of its own `registration_expires_at` — or through revocation of the responsible-charge licence. Sets that had already reached `SEALED` are left untouched by every one of those firm-level events: a seal that was validly affixed is a matter of record, and the firm's later collapse does not retract it. Sealing an already sealed or voided set, or flagging a set still in `DRAFT`, is refused with `ERR_PLAN_STATE_INVALID` (HTTP 409).

### 3.9. Complaints, Findings, Civil Penalties and Consent Orders

Enforcement is the one part of the register where two questions must be answered at once and neither waits for the other: *what did the respondent do*, and *what is the board going to do about it*. A case therefore carries two independent status axes on the same row. `investigation_status` runs `RECEIVED`, `INVESTIGATING`, then either `PROBABLE_CAUSE` or `NO_CAUSE`, then `CLOSED`. `sanction_status` runs `NONE`, then `PROPOSED` or `HEARING_REFERRED`, and `PROPOSED` may go on to `CONSENT_EXECUTED`. Each axis advances on its own transitions, and the two are coupled only by the explicit cross-axis guards named below. A `case_id` matching nothing answers `ERR_CASE_NOT_FOUND` (HTTP 404), and a transition requested on either axis from a value that does not declare it is refused with `ERR_CASE_STATE_INVALID` (HTTP 409). `CLOSED` is terminal.

A `BoardInvestigator` opens a complaint with `allegation_type` — one of `NEGLIGENCE`, `UNLICENSED_PRACTICE`, `PLAN_STAMPING` or `CPC_FRAUD` — `complainant_name`, a non-empty name of at most 120 characters, and `received_on`, the instant the board took the complaint in. The respondent is identified by exactly one of two mutually exclusive means: `respondent_license_id` naming a licensed respondent, or `unlicensed_respondent_name` naming someone practising without a licence. Supplying both, or neither, is refused with `ERR_RESPONDENT_TARGET_INVALID` (HTTP 422), as is an `UNLICENSED_PRACTICE` allegation without `unlicensed_respondent_name` or a `PLAN_STAMPING` allegation without `subject_plan_submission_id`. `subject_plan_submission_id`, optional in general, names the plan set at issue. The case opens with `investigation_status` at `RECEIVED`, `sanction_status` at `NONE`, `assigned_investigator_user_id` at `null`, all three factor counts at 0, `penalty_factor` at 0 and `assessed_penalty_cents` at 0, and answers HTTP 201. When `respondent_license_id` was supplied, the respondent engineer's `open_case_count` is recomputed from the register rather than incremented, exactly as §3.1 describes, so any count left standing by an earlier finding is corrected on the way through. Cases are readable individually and as a list narrowable by `respondent_license_id`, `subject_plan_submission_id`, `investigation_status` and `allegation_type`.

Opening the investigation moves `RECEIVED → INVESTIGATING` and stamps `assigned_investigator_user_id` with the acting `X-User-ID`. That stamp is the whole point of the transition: it is the bar that will later prevent the investigator who built the case from also executing the order that settles it.

The finding closes the investigative question. A `BoardInvestigator` supplies `finding`, either `PROBABLE_CAUSE` or `NO_CAUSE`, together with `aggravating_factor_count` and `mitigating_factor_count`, whole numbers from 0 through 8, and `violation_count`, a whole number from 0 through 20. All three counts are written onto the case whichever way the finding goes, but the two branches then diverge sharply. A finding of `PROBABLE_CAUSE` requires `violation_count` of at least 1, moves the case `INVESTIGATING → PROBABLE_CAUSE`, recomputes `penalty_factor` and `assessed_penalty_cents` through the assessment below, and — when `subject_plan_submission_id` is set and that plan set stands in `SEALED` — drags the plan set `SEALED → FLAGGED`. A finding of `NO_CAUSE` requires `violation_count` of exactly 0, moves the case `INVESTIGATING → NO_CAUSE`, and sets both `penalty_factor` and `assessed_penalty_cents` to 0 outright: no assessment is run and no plan set is flagged. A finding whose `violation_count` contradicts the branch requested is refused with `ERR_CASE_STATE_INVALID` (HTTP 409). Neither branch touches the respondent engineer's `open_case_count`: a `NO_CAUSE` finding takes the case off the open list of §3.1 without recomputing that counter, which therefore goes on reading the value it already held until the next complaint against that engineer is opened or the next one is closed.

The civil penalty is assessed in five steps, and its rounding order is pinned because a different order produces a different number of cents. Step one computes the aggravation/mitigation factor: start at 1.00, add 0.25 for each aggravating factor found, subtract 0.15 for each mitigating factor found, round that raw figure half up to two decimal places, and then clamp the result to no less than 0.50 and no more than 2.00. That clamped value is `penalty_factor`. Step two computes the conduct component from the statutory base for the allegation — 150,000 cents for `NEGLIGENCE`, 250,000 for `UNLICENSED_PRACTICE`, 200,000 for `PLAN_STAMPING` and 100,000 for `CPC_FRAUD` — by multiplying that base by `penalty_factor`, **rounding the per-violation amount half up to a whole cent first**, and only then multiplying by `violation_count`. Step three computes the per-sheet stamping component, and only when `subject_plan_submission_id` is set: multiply 1,725 cents by `penalty_factor`, **round that per-sheet amount half up to a whole cent first**, and only then multiply by the plan set's `sheet_count` as it stands at finding time. When no plan set is named the stamping component is 0. Step four computes cost recovery as 48,000 cents multiplied by `penalty_factor`, rounded half up to a whole cent. Step five adds the three already-rounded components and takes the smaller of that sum and the statutory cap of 1,000,000 cents; the sum itself is never rounded again. `assessed_penalty_cents` is that capped figure. The order sensitivity is real rather than theoretical: with a `penalty_factor` of 0.85 and a `sheet_count` of 7, rounding per sheet first gives 1,466 cents per sheet and 10,262 cents for the component, whereas multiplying everything before rounding would give 10,264 — a two-cent divergence, and the pinned order is the correct one.

A negotiated settlement is proposed by a `BoardInvestigator` against a case that has reached probable cause. The proposal carries `case_id`, `sanction_type` — one of `REPRIMAND`, `SUSPENSION` or `REVOCATION` — optionally `suspension_months`, a whole number from 0 through 60 that must be 0 unless `sanction_type` is `SUSPENSION`, optionally `penalty_paid_cents`, the cents remitted so far as a whole number of at least 0 defaulting to 0, and `expected_case_version`, the concurrency guard of §2.6. The case's `investigation_status` must be `PROBABLE_CAUSE`; proposing against a case still under investigation, or one found to have no cause, is refused with `ERR_PROBABLE_CAUSE_REQUIRED` (HTTP 409). Nothing at all is asked of the sanction axis: so long as `investigation_status` still reads `PROBABLE_CAUSE`, a fresh proposal is accepted even against a case whose sanction axis has already moved on to `HEARING_REFERRED` or to `CONSENT_EXECUTED`, and `sanction_status` is written to `PROPOSED` whichever of those values it held. Only orders standing in `PROPOSED` are displaced by the new one; an order already `EXECUTED` or `SUPERSEDED` is left exactly as it stands. `penalty_cents` is never supplied by the client — it is copied from the case's `assessed_penalty_cents` at proposal time, freezing the assessment as it then stood. The order opens in `PROPOSED` with `executed_on` and `executed_by_user_id` at `null`, the case's `sanction_status` is written to `PROPOSED` — `NONE → PROPOSED` in the ordinary case — and the response is HTTP 201. A second proposal on the same case is legitimate and is exactly why the concurrency guard exists: the outstanding order moves `PROPOSED → SUPERSEDED`, a replacement order is created in `PROPOSED`, and the sanction axis takes the `PROPOSED → PROPOSED` self-loop. A `consent_order_id` matching nothing answers `ERR_CONSENT_ORDER_NOT_FOUND` (HTTP 404); orders are readable individually and as a list narrowable by `case_id`, `status` and `sanction_type`.

Referral to a formal hearing is the alternative to settlement, taken when the respondent declines the proposed order. From `NONE` or from `PROPOSED`, and only while `investigation_status` is `PROBABLE_CAUSE`, the sanction axis moves to `HEARING_REFERRED`; when it was standing at `PROPOSED`, the outstanding order is dragged `PROPOSED → SUPERSEDED` on the way. `HEARING_REFERRED` and `CONSENT_EXECUTED` are both resolved postures as far as closing the case is concerned.

Execution is where the discipline actually bites, and it is the entry point of the four-link cascade. Either a `BoardInvestigator` or a `BoardLicensingOfficer` may execute, supplying `executed_on`, the instant the board executed the order. The order must stand in `PROPOSED` and the case's `sanction_status` must stand at `PROPOSED`; otherwise the request is refused with `ERR_CONSENT_ORDER_STATE_INVALID` (HTTP 409). The acting `X-User-ID` must differ from the case's `assigned_investigator_user_id`, and `penalty_paid_cents` must be at least `penalty_cents` — an unpaid penalty is refused with `ERR_PENALTY_UNPAID` (HTTP 402), which is the last rung of the ladder and therefore the error a request sees only once everything else about it is in order.

The cascade then runs to completion inside the same request, in link order. Link one moves the order `PROPOSED → EXECUTED`, stamps `executed_on` from the request and `executed_by_user_id` with the acting `X-User-ID`, and moves the case's `sanction_status` `PROPOSED → CONSENT_EXECUTED`. Link two, caused by link one, reaches the respondent's licence when `respondent_license_id` is set: `SUSPENSION` moves it `ACTIVE → SUSPENDED` and stamps `suspension_ends_at` at `executed_on` plus `suspension_months` months; `REVOCATION` moves it `ACTIVE → REVOKED`; and `REPRIMAND` moves the licence nowhere at all, setting only `discipline_flag` to true. `discipline_flag` is in fact set to true by all three sanction types, and never cleared thereafter. Whenever the licence leaves `ACTIVE`, the holder's `active_license_number` is recomputed by the rule of §3.1 — falling to `null` unless the holder still holds some other licence in `ACTIVE`, whose number it then takes. Link three, caused by link two, reaches every firm holding that licence in responsible charge, lapsing it into `LAPSED_NO_RESPONSIBLE_CHARGE` on a suspension and moving it to `REVOKED` on a revocation, exactly as the posture rule dictates. Link four, caused by link three, reaches every `DRAFT` plan set beneath those firms and voids it; sets already `SEALED` are untouched. A `REPRIMAND` stops the chain at link two, because the licence never leaves `ACTIVE` and therefore no firm posture changes. A licence that was not standing in `ACTIVE` when the order was executed stops the chain there too, whatever the sanction says: an already suspended, expired or revoked licence takes `discipline_flag` and nothing else — a `REVOCATION` executed against an `EXPIRED` licence leaves it `EXPIRED`, though §3.7 then bars its reinstatement for good — and neither `active_license_number` nor any firm posture is recomputed. `executed_on` is taken as supplied and is never compared against the logical clock, so `suspension_ends_at` may land behind the clock the moment it is stamped.

Closing the case is the last act on the investigative axis, and it is guarded across the axes. From `PROBABLE_CAUSE` the sanction axis must have resolved to `CONSENT_EXECUTED` or `HEARING_REFERRED`; from `NO_CAUSE` the sanction axis must still be `NONE`. A close attempted while the sanction axis sits at `NONE` behind a probable-cause finding, or at `PROPOSED`, is refused with `ERR_OPEN_SANCTION_BLOCKS_CLOSE` (HTTP 409) — the board does not close a case with an outstanding proposal on the table. On success `investigation_status` becomes `CLOSED` and, when `respondent_license_id` is set, the respondent engineer's `open_case_count` is recomputed so that the closed case no longer counts against them.

## 5. Error Code Catalogue

Every error response carries one of the identifiers below in `error_id`, with the HTTP status shown. When more than one condition is violated by the same request, the identifier reported is the one belonging to the earliest rung of the ladder in §2.7. Three identifiers outside this catalogue belong to the transport rather than to the domain, and they are answered before the header checks of §2.1 ever run: a request to a path this API does not route answers `ERR_NOT_FOUND` (HTTP 404), a request to a routed path under a method that path does not serve answers `ERR_METHOD_NOT_ALLOWED` (HTTP 405), and an unhandled server fault answers `ERR_INTERNAL` (HTTP 500). Any other transport-level rejection is reported as `ERR_INVALID_REQUEST` under the status the transport chose. A trailing slash on any path is tolerated and resolves to the same endpoint as the path without one.
