# Playground Equipment Manufacturing & Installation API — Product Requirements Document

## 1. Introduction

Commercial playground equipment is one of the few products where a design error is simultaneously a safety incident, a regulatory finding and a warranty liability. Our manufacturing business begins long before the first post is extruded: a design consultant sits with a school district, a municipality or a homeowners' association, measures a site, learns which age bands the finished playground must serve, discovers that the subgrade is clay rather than sandy loam, and is told the budget ceiling and the date on which the community's fundraising drive closes. From that conversation the business must produce a rendering the community can vote on, a quote that is defensible to the cent, a manufacturing order that can be kitted and bagged on the plant floor, a booking with a certified installer whose crew calendar is genuinely free, and finally an independent post-installation safety audit. Today that chain lives in spreadsheets, PDF renderings emailed around a school board, and a warranty binder in a filing cabinet, and the seams between those artefacts are exactly where compliance failures hide.

This document specifies the API that replaces that chain with a single system of record. Its central organising idea is that a **playground safety standard edition** governs everything: exactly one edition is ACTIVE at any moment, component models are certified against that edition, renderings pin the edition they were drawn under, and when a new edition supersedes the old one the system must automatically walk the consequences outward — decertifying models, demoting the placements that used them, reopening the designs that contained those placements, and expiring the renderings and quotes that were built on them. A second organising idea is that money and geometry are both computed, never asserted: use-zone intervals, critical fall heights, required surfacing depths, quote subtotals, fundraising allocations, crew-day commitments, warranty coverage percentages and retrofit prices are all derived by the server from rules written here, so that two readers of the same design cannot disagree about them.

The API is mounted under the `/playground` prefix. It is designed for six distinct operator populations — plant administration, design consultancy, compliance, the commissioning community, the installer network and independent safety auditors — whose duties deliberately do not overlap. Where a segregation-of-duties boundary exists in the real business (a consultant may not certify their own design; the auditor who inspected an installation may not also audit it), the API enforces that boundary rather than trusting policy.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint — reads, writes and the test-driving clock endpoint alike — must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. If either header is absent, or present but empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); "empty" means the zero-length string, so a header carrying only whitespace counts as present and is then matched against the role names like any other value. The same rejection applies when `X-User-Role` carries a value that is not one of the six roles defined below: an unrecognised role name is an authentication failure, not an authorisation failure. Header presence is settled before role recognition, and both are settled before the endpoint's authorised-role list is consulted.

Six roles exist, and their names must be spelled exactly as follows:

- `ManufacturerAdmin` — plant administration. Owns the component catalogue, registers standard editions, drives the production floor and manages membership of the installer network.
- `DesignConsultant` — runs the design consultation. Owns projects, play areas, placements, renderings, quotes, manufacturing orders and installer bookings.
- `ComplianceOfficer` — owns safety certification. Activates and supersedes standard editions, certifies component models and finished designs, and decides warranty claims.
- `ClientRepresentative` — acts for the commissioning community. Runs fundraising, records community input, accepts quotes, buys replacement parts and files warranty claims.
- `InstallerOperator` — a company in the certified installer network, acting on its own bookings only.
- `SafetyAuditor` — an independent inspector who files installation inspections and post-installation safety audits.

Once the headers are accepted, the acting role must appear in the authorised-role list of the endpoint being called, as tabulated in §4. A role that is legitimate but not authorised for that endpoint receives `ERR_FORBIDDEN_ROLE` (HTTP 403).

Identity semantics differ between the roles, and this difference matters because it decides what ownership means. When `X-User-Role` is `InstallerOperator`, `X-User-ID` is the `id` of the acting `CertifiedInstaller`; ownership checks on any resource that references a `CertifiedInstaller` compare the resource's foreign-key field to `X-User-ID`. Concretely, an `InstallerOperator` may start, complete or drive the rework loop of a job only when that job's `installer_id` equals its own `X-User-ID`; acting on another company's booking is rejected with `ERR_NOT_JOB_OWNER` (HTTP 403). For the other five roles — `ManufacturerAdmin`, `DesignConsultant`, `ComplianceOfficer`, `ClientRepresentative` and `SafetyAuditor` — `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record such an identifier (for example as `consultant_user_id` on a `DesignProject` when a `DesignConsultant` opens it, as `performed_by_user_id` on every inspection record a `SafetyAuditor` files, or as `install_inspector_user_id` on an `InstallationJob`) but it never compares those opaque identifiers to any entity's `id`.

Two segregation-of-duties rules ride on those recorded identifiers, and both reject with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). First, the `ComplianceOfficer` who certifies a project's compliance must not be the `DesignConsultant` who created it: the acting `X-User-ID` must differ from the project's stored `consultant_user_id`. Second, the `SafetyAuditor` who files a post-installation audit must not be the auditor recorded in the job's `install_inspector_user_id` — that is, the auditor who filed the job's installation inspection is permanently barred from auditing the same job.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request. It is the literal prefix `req_` followed by exactly 20 characters drawn at random from the uppercase letters `A`–`Z` and the digits `0`–`9`, so the whole value is always 24 characters long and carries no lower-case letters, hyphens or other punctuation.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with exactly three fractional digits and a literal `Z` suffix — the shape `YYYY-MM-DDTHH:MM:SS.mmmZ`, always 24 characters, never an offset such as `+00:00`. This single value is read from real wall-clock time rather than from the logical clock of §2.5, because it describes the transport rather than any business fact.
- The `response_type` is either "object" for a single resource or "array" for a list of resources; error envelopes use the third value "error", as shown below.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. The one HTTP 204 operation in this API — placement removal (§3.3) — is the exception to the envelope itself: it answers with a completely empty body, carrying no `meta`, no `response_type` and no `data` at all.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and only for list endpoints: the `meta` of a single-resource 2xx response carries `api_request_id` and `api_request_timestamp` and nothing else.

#### Standard Error Response Format

All error API responses (4xx and 5xx status codes alike) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. Its wording is free text: no client behaviour depends on it, and only `error_id` and the HTTP status are contractual.
- Two transport-level rejections use this same envelope. A request whose path matches no route defined in §4 answers HTTP 404, and a request whose path matches a defined route but whose HTTP method does not answers HTTP 405. Both carry `error_id` `ERR_INVALID_REQUEST`, which is therefore the one identifier in the §5 catalogue that is also returned with statuses other than the 422 tabulated there.
- An unhandled server fault answers HTTP 500 with this envelope and `error_id` `ERR_INTERNAL_ERROR`. That identifier is deliberately absent from the §5 catalogue, which enumerates only the client-caused rejections a well-behaved caller can provoke.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0, with no upper bound. A `limit` that is not an integer, or is below 1, or above 100, and an `offset` that is not an integer or is below 0, are both rejected with `ERR_INVALID_PAGINATION` (HTTP 422). "Not an integer" means anything that is not an optionally-signed run of base-ten digits, so `abc`, `1.5`, `10x` and the empty string all fail exactly as `0` and `101` do; surrounding whitespace is trimmed before the check. `limit` is validated before `offset`, so a request that breaks both reports the `limit` failure. An `offset` at or beyond `total_count` is perfectly legal and yields an empty `data` array rather than an error. Both parameters are validated after the path segments of the endpoint have been resolved, so a list under a nonexistent parent reports that parent's not-found code rather than `ERR_INVALID_PAGINATION`.

Unless a specific endpoint's narrative says otherwise, list results are ordered by `created_at` ascending, and rows that share a `created_at` value — which is possible because the instant is only millisecond-resolved — are ordered among themselves by the order in which the server inserted them, so the sort is total and stable. The inspection log of an installation job is the one place where an additional ordering guarantee is stated explicitly: its records come back in `sequence_number` order, which for an append-only log is the same ordering as `created_at` ascending.

The `meta` block of a list response carries `limit` and `offset` echoing the effective values used, `total_count` giving the number of rows matching the filter before pagination was applied, and `has_more` indicating whether any row remains beyond the current page — derived as `offset` plus the number of rows actually returned on this page being strictly less than `total_count`, which is why a short final page reports `false`. Filter query parameters listed for an endpoint in §4 narrow `total_count` accordingly; they never change the sort order. Filter matching is exact and case-sensitive against the string form of the stored value: a boolean field is matched against the literals `true` and `false`, an integer field against its decimal digits, and a row whose filtered field is null matches no supplied value at all, so null cannot be selected for. A filter parameter that is omitted narrows nothing, and any query parameter an endpoint does not list is ignored rather than rejected.

### 2.4. Resource Identity, Timestamps and Revision Counters

Every resource the API creates is assigned an `id` that is a server-minted UUID. Identifiers carry no type prefix and no embedded semantics — a caller must never parse an `id` to learn what kind of resource it points at. Clients never supply an `id`; a body field that happens to end in `_id` is always a reference to an already-existing row, never a request to mint one.

Most resources also carry three common properties. `created_at` is the ISO 8601 UTC instant at which the row was inserted, rendered with exactly three fractional digits and a literal `Z` suffix — the same `YYYY-MM-DDTHH:MM:SS.mmmZ` shape as `api_request_timestamp`. `updated_at` is the ISO 8601 UTC instant of the row's most recent mutation, in the same format; on a freshly created row it equals `created_at`. Both instants are read from **real wall-clock UTC time, not from the logical clock of §2.5**: the logical clock governs business dates, deadlines, expiries and effective dates, while row bookkeeping records when the write physically happened. A consequence worth stating is that moving the logical clock does not move any `created_at` or `updated_at`, and rows created while the clock sits in 2026 still stamp the wall-clock instant of the request. `version` is an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row — including mutations the caller did not directly request, such as those a cascade performs. When a narrative in §3 says an operation "bumps" or "increments" a row's version, it means exactly this: one increment per row actually mutated by that operation, and `updated_at` refreshed at the same time.

`InstallationInspection` is the single exception. Inspection records are immutable append-only evidence, so they carry only `id` and `created_at`; they have neither `updated_at` nor `version`, and neither field appears in their JSON representation. Every other entity — `PlaygroundStandard`, `ComponentModel`, `DesignProject`, `PlayArea`, `ComponentPlacement`, `DesignRendering`, `Quote`, `FundraisingPledge`, `ManufacturingOrder`, `CertifiedInstaller`, `InstallationJob` and `WarrantyClaim` — carries all four of `id`, `created_at`, `updated_at` and `version`.

### 2.5. The Logical Plant Clock

Nothing in this system reads wall-clock time for business purposes. Instead the server keeps a single **logical clock**, and every deadline, expiry, elapsed-warranty, effective-date and booking-window rule in this document reads it. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; this startup default is mandatory, and the server must not fall back to real time under any circumstance. An administrative test-driving capability moves the clock to an explicit ISO-8601 UTC instant supplied as `current_utc`, which is a required non-empty string and which reports `ERR_INVALID_REQUEST` when it is not a parseable ISO-8601 instant. The response body reports the clock's new `current_utc` value rather than a business row: the `data` object of that response holds the single field `current_utc` and nothing else — no `id`, no `created_at`, no `updated_at` and no `version`, because no row was written — and its value is the caller's own string **echoed back verbatim**, exactly as it was supplied rather than normalised, so an instant named with a trailing offset such as `+02:00`, with no seconds part, or with six fractional digits is answered with that same spelling and not with a `YYYY-MM-DDTHH:MM:SS.mmmZ` rendering. The instant is nevertheless converted to UTC for internal use, so every date comparison afterwards reads the UTC date of the instant supplied, whatever spelling the caller chose.

Time may be moved forward freely, but it may not be rewound past history the system has already written down: if the requested instant is earlier than any `installed_on` date already recorded on any project, the request is rejected with `ERR_CLOCK_REWIND_FORBIDDEN` (HTTP 422). That comparison is made at **calendar-date granularity, and against `installed_on` alone**. The UTC date of the requested instant is compared against each project's recorded `installed_on`, so any instant falling on that same calendar day is accepted — including `00:00:00Z` of it, and including an instant earlier in the day than the one at which the installation was actually recorded — and only a strictly earlier calendar date is refused. No other recorded date participates: a `pledged_at`, a quote's `valid_until`, a booking window, a scheduled job date and every row's `created_at` are all irrelevant to the check, and a project whose `installed_on` is still null constrains nothing. Setting the clock mutates no business rows and bumps no versions.

Where a rule compares against a calendar date rather than an instant — a fundraising deadline, a quote's last acceptable acceptance day, an installer's certification expiry, a job's first startable day, a pledge date, a failure date — the comparison uses the date portion of the logical clock in UTC. Where a rule compares against a calendar year — the last year in which replacement parts for a model are sold — it uses the year portion of that same date.

### 2.6. Nested Path Resolution and Referential Integrity

Several resources are addressed through nested paths — a project's play areas, a play area's placements, a job's inspection log. Path segments are resolved strictly left to right, and the first segment that fails to resolve determines the error. Asking for the placements of a play area that does not exist yields `ERR_PLAY_AREA_NOT_FOUND` (HTTP 404) even when the placement identifier further right is also nonsense; asking for a rendering under a project that does not exist yields `ERR_PROJECT_NOT_FOUND` before the rendering is ever looked up. Each entity has its own not-found code, and all of them are HTTP 404: `ERR_STANDARD_NOT_FOUND`, `ERR_MODEL_NOT_FOUND`, `ERR_PROJECT_NOT_FOUND`, `ERR_PLAY_AREA_NOT_FOUND`, `ERR_PLACEMENT_NOT_FOUND`, `ERR_RENDERING_NOT_FOUND`, `ERR_QUOTE_NOT_FOUND`, `ERR_PLEDGE_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_INSTALLER_NOT_FOUND`, `ERR_JOB_NOT_FOUND` and `ERR_CLAIM_NOT_FOUND`.

The same catalogue governs references supplied in a request body rather than in the path. Every foreign key a caller sends must resolve to an existing row, and an unresolvable reference produces the not-found code of the referenced entity's type: `component_model_id`, `supersedes_model_id` and `replacement_model_id` produce `ERR_MODEL_NOT_FOUND`; `attached_to_placement_id` and `placement_id` produce `ERR_PLACEMENT_NOT_FOUND`; `pinned_standard_id` and `successor_standard_id` produce `ERR_STANDARD_NOT_FOUND`; `rendering_id` produces `ERR_RENDERING_NOT_FOUND`; `project_id` produces `ERR_PROJECT_NOT_FOUND`; `quote_id` produces `ERR_QUOTE_NOT_FOUND`; `installer_id` produces `ERR_INSTALLER_NOT_FOUND`; and `order_id` produces `ERR_ORDER_NOT_FOUND`. Where one request body carries more than one foreign key, the references are resolved in a fixed order declared per endpoint and the **first** unresolvable one determines the error: on placement creation that order is `component_model_id` before `attached_to_placement_id`, so a body in which both are nonsense reports `ERR_MODEL_NOT_FOUND`. A field that is absent, or explicitly `null`, is not a reference at all and is passed straight to the shape pass; so is a field whose value is not a string, which is why a numeric or object-valued `_id` yields `ERR_INVALID_REQUEST` rather than a not-found code.

Beyond existence, request bodies are checked for shape. Required fields must be present, values must be of the declared type, enum-typed values must be members of their declared set, strings must respect their declared length limits and numbers their declared ranges. Any failure of that kind is reported as `ERR_INVALID_REQUEST` (HTTP 422). Fields the endpoint does not recognise are ignored rather than rejected. Four conventions settle the edges of that pass. A field explicitly set to `null` is treated exactly as if it were absent, so an optional field takes its documented default and a required field reports the same missing-field `ERR_INVALID_REQUEST`. A JSON boolean is never an acceptable integer, so `true` where a count is declared is a shape failure. A request body that is absent or empty is read as the empty object, while a body that is syntactically invalid JSON, or is valid JSON but not an object — an array, a bare string, a bare number — is refused with `ERR_INVALID_REQUEST`. And an endpoint that declares no body fields at all never parses the request body, so whatever is sent to it, well-formed or not, is simply ignored.

### 2.7. Money, Geometry and Rounding Discipline

All monetary amounts in this system are integer counts of cents. There are no floating-point money fields, no currency codes and no fractional cents in stored data. Where a calculation multiplies an amount by a percentage and the exact product is not a whole number of cents, the result is rounded **half up** — a value whose fractional part is exactly one half rounds away from zero to the next higher cent. Rounding happens only at the points this document names; intermediate products are carried exactly, as rational arithmetic, until such a point is reached. The distinction is not cosmetic: §3.5 describes two quote variants that differ *only* in where the single rounding point sits, and on the same placement data they can legitimately produce subtotals that differ by up to one cent per priced line less one.

All geometry — site extents, play-area intervals, anchor coordinates, use-zone extents, deck heights, surfacing depths, clearances — is expressed in whole centimetres. Those calculations never round because every term in them is already an integer. Percentages that are exposed as data rather than used as a multiplier follow their own stated precision: the community approval percentage is carried to exactly one decimal place, rounded half up, while a warranty coverage percentage is a whole percent, also rounded half up.

Crew-day figures are whole numbers, and every date interval in this system that is described as a booking window is **closed on both ends**: both the first and the last calendar day count, so a window whose start and end are the same day is one day long. Use-zone intervals are likewise closed on both ends. Play-area axis intervals, by contrast, are **half-open**: the origin coordinate is inside the interval and the coordinate one past the interval's length is outside it. Mixing these two conventions up is the most common source of off-by-one geometry defects, so §3.3 and §3.4 restate them where they bite.

### 2.8. Stale-Version Protection on Quoting and Rescheduling

Two write operations require the client to declare which revision of a *parent* row it was looking at when it decided to write, and both reject a mismatch with HTTP 412.

A `POST /playground/quotes` request must carry `expected_project_version`, an integer holding the client's last observed `version` of the `DesignProject` named by `project_id`. If that value does not equal the project's current `version`, the request is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). The reason is that issuing a quote legitimately expires the project's prior ISSUED quote; a writer whose view of the project predates another writer's successful issuance would therefore silently expire a quote it had never seen. `expected_project_version` is a required field of that request, not an optional one.

A `POST /playground/installation-jobs/{id}/reschedule` request must carry `expected_installer_version`, an integer holding the client's last observed `version` of the `CertifiedInstaller` the job is booked with. If that value does not equal the installer's current `version`, the request is rejected with `ERR_STALE_INSTALLER_VERSION` (HTTP 412). A reschedule supersedes the job's previous booking window and re-derives the installer's committed crew days, so a writer holding a stale view of the installer's booking book would evaluate the overlap, travel-buffer and crew-capacity checks against calendar occupancy that no longer exists. `expected_installer_version` is likewise required.

No other endpoint in this API takes a version field. In particular, quote acceptance, placement validation, order progression, inspection filing and warranty decisions carry no `expected_*_version` input, and supplying one has no effect.

### 2.9. One Governing Edition, and How Cascades Propagate

At most one `PlaygroundStandard` row may be in status `ACTIVE` at any instant. That invariant is what makes the phrase "the ACTIVE edition" a deterministic singleton everywhere else in this document: operations that must resolve it never have to choose between candidates, and if there is no candidate at all they fail rather than guess, with `ERR_NO_ACTIVE_STANDARD` (HTTP 409). The operations that must resolve the ACTIVE edition, and therefore fail with `ERR_NO_ACTIVE_STANDARD` when none exists, are model certification, taking a project into consultation, placement creation and rendering issuance. Three further operations consult it opportunistically and do not fail without it: placement validation, whose cross-area separation check is skipped when no edition is `ACTIVE`; the compliance retrofit of §3.9, whose fall-height test is skipped on the same condition; and the issuance of a `FIRM` quote (§3.5), whose accessible-route re-check then falls back to the project's own `accessible_route_required` flag alone.

Cascades in this system are **immediate and complete**. When an operation's side effects include changes to rows other than the one addressed, those changes land inside the same request, before the response is written; there is no deferred queue and no eventual reconciliation. Two cascades are large enough to be described hop by hop in §3 — the supersession of a standard edition (§3.1) and the failure of a post-installation audit (§3.8) — and two more are structural (project cancellation in §3.9, installer revocation in §3.7). In all of them, every row actually mutated has its `version` incremented by exactly 1 and its `updated_at` refreshed, including rows the caller never named. Rows that a cascade examines but does not change are not bumped — unless the operation's own narrative in §3 declares an unconditional bump for a particular row, which several of them do, each such carve-out being stated at the point it applies.

Derived fields are always **recomputed from their inputs**, never patched incrementally. A play area's `critical_fall_height_cm` and `required_surfacing_depth_cm` are re-derived from the area's current placement set every time that set or its members change. A project's `funds_collected_cents` and its four allocation buckets are re-derived from the project's collected pledges on every collection and on every refund of a pledge that had actually been collected — a refund of a merely `PLEDGED` pledge triggers no recompute at all, as §3.6 spells out. An installer's `committed_crew_days` is re-derived from the installer's current non-excluded job set on every event that could change it. This rule is what makes compensating actions exact: refunding a collected pledge restores the buckets to precisely their pre-collection values, and cancelling a job restores `committed_crew_days` to precisely its pre-booking value, with no accumulated drift.

### 2.10. Order of Rejection

When a request violates more than one rule, the response must carry the error of the **highest-priority** violated rule, evaluated in the following order. This ordering is normative; a fair implementation that checks rules in a different order will report the wrong code on requests that break several rules at once.

1. **Header presence and role recognition.** Missing or empty `X-User-ID` or `X-User-Role` first, then an `X-User-Role` outside the six declared roles — both `ERR_UNAUTHENTICATED`.
2. **Endpoint authorisation.** The acting role must be listed for the endpoint — `ERR_FORBIDDEN_ROLE`.
3. **Ownership and duty separation.** Job ownership for installer-driven job operations (`ERR_NOT_JOB_OWNER`) is checked next; then the consultant-versus-officer separation on compliance certification, and then the inspector-versus-auditor separation on a post-installation audit (both `ERR_SEGREGATION_OF_DUTIES`). One documented exception applies to that last check: because the server cannot know it is looking at a post-installation audit until it has read `kind` out of the request body, the inspector-versus-auditor separation is evaluated **after** the request-shape pass of item 5 rather than ahead of it, so an audit filed by the barred auditor with a malformed body reports `ERR_INVALID_REQUEST`. It still precedes everything from item 7 onwards, including the job's own phase gate.
4. **Path existence,** left to right, then **body foreign-key existence** — the not-found codes of §2.6.
5. **Request shape,** then **pagination bounds** — `ERR_INVALID_REQUEST`, then `ERR_INVALID_PAGINATION`. On the inspection-filing endpoint alone this shape pass also runs **ahead of** the inspector-versus-auditor separation of item 3, for the reason item 3 records.
6. **Stale parent version** — `ERR_STALE_PROJECT_VERSION` or `ERR_STALE_INSTALLER_VERSION`.
7. **State admissibility of the transition itself:** whether the target row's state field permits the requested move at all. A trigger fired from a state that declares no such transition — including firing the same trigger twice — is rejected here with that entity's state error: `ERR_STANDARD_NOT_DRAFT`, `ERR_STANDARD_NOT_ACTIVE`, `ERR_MODEL_NOT_CERTIFIABLE`, `ERR_PROJECT_INVALID_STATE`, `ERR_PROJECT_NOT_EDITABLE`, `ERR_PLACEMENT_INVALID_STATE`, `ERR_RENDERING_NOT_ISSUED`, `ERR_QUOTE_NOT_ACCEPTED`, `ERR_ORDER_INVALID_STATE`, `ERR_ORDER_NOT_IN_PRODUCTION`, `ERR_JOB_INVALID_STATE`, `ERR_PLEDGE_INVALID_STATE`, `ERR_CLAIM_INVALID_STATE` or `ERR_INSTALLER_INVALID_STATE`.
8. **Editability and locking of design content:** design content may be mutated only while the owning project's `design_status` is `CONSULTATION` or `REVISION_REQUESTED` (`ERR_PROJECT_NOT_EDITABLE`), and a `LOCKED` play area accepts no further placement writes (`ERR_PLAY_AREA_LOCKED`). Rendering issuance gates on that same pair of statuses but is not itself a mutation of design content, and it reports `ERR_PROJECT_INVALID_STATE` at item 7 instead, exactly as §3.4 states.
9. **Cross-entity state gates:** the placed model must be certified and not discontinued, an attachment parent must be validated, a quote's rendering must be ISSUED, an order's quote must be an ACCEPTED FIRM quote, a job's installer must be ACTIVE, and a rendering's pinned edition must still be ACTIVE when compliance is certified.
10. **Standard-registry invariants:** at most one ACTIVE edition (`ERR_ACTIVE_STANDARD_EXISTS`), an ACTIVE edition must exist where one is required (`ERR_NO_ACTIVE_STANDARD`), and a supersession's successor must be DRAFT and already effective (`ERR_SUCCESSOR_NOT_DRAFT`, then `ERR_SUCCESSOR_NOT_EFFECTIVE`).
11. **Design-completeness gates for rendering issuance:** every required age band must have a play area (`ERR_AGE_GROUP_COVERAGE_INCOMPLETE`) and every play area must hold at least one placement in `DRAFT` or `VALIDATED` (`ERR_PLAY_AREA_EMPTY`).
12. **Safety checks,** in this order: fall height against the ACTIVE edition's ceiling for the area's age band (`ERR_FALL_HEIGHT_EXCEEDS_STANDARD`), age-group use-zone separation (`ERR_AGE_GROUP_SEPARATION_VIOLATION`), model-to-area age-band agreement (`ERR_AGE_GROUP_MISMATCH`), surfacing depth sufficiency (`ERR_SURFACING_DEPTH_INSUFFICIENT`), and accessible-route provision (`ERR_ACCESSIBLE_ROUTE_MISSING`).
13. **Business constraints,** in this order: the rework ceiling (`ERR_REWORK_LIMIT_EXCEEDED`), use-zone overlap inside an area (`ERR_USE_ZONE_OVERLAP`), use-zone containment inside the area's axis interval (`ERR_USE_ZONE_OUT_OF_BOUNDS`), attachment direction (`ERR_INVALID_ATTACHMENT_TARGET`), installer booking conflicts (`ERR_INSTALLER_BOOKING_CONFLICT`), crew capacity (`ERR_CREW_CAPACITY_EXCEEDED`), installer category coverage (`ERR_INSTALLER_CATEGORY_NOT_CERTIFIED`) and the minimum community turnout (`ERR_INSUFFICIENT_COMMUNITY_INPUT`).
14. **Temporal and referential business rules,** in this order: the fundraising deadline (`ERR_FUNDRAISING_DEADLINE_PASSED`), quote validity (`ERR_QUOTE_EXPIRED`), parts availability (`ERR_PARTS_NO_LONGER_AVAILABLE`), installer certification expiry and job start eligibility (`ERR_INSTALLER_CERTIFICATION_EXPIRED`, then `ERR_JOB_NOT_YET_STARTABLE`), retrofit model eligibility (`ERR_RETROFIT_MODEL_MISMATCH`), warranty claim placement ownership and project installation (`ERR_WARRANTY_PLACEMENT_MISMATCH`, then `ERR_PROJECT_NOT_INSTALLED`), failure-date bounds (`ERR_INVALID_FAILURE_DATE`), rendering-to-project agreement on a quote (`ERR_RENDERING_PROJECT_MISMATCH`), an empty pricing scope (`ERR_QUOTE_EMPTY_SCOPE`) and the requirement that every placement an order's quote priced is still validated (`ERR_PLACEMENTS_NOT_VALIDATED`). One documented exception applies to that last code: on compliance certification the all-placements-validated gate is evaluated **ahead of** the item-12 surfacing-depth and accessible-route checks, in the order §3.7 states, because a design whose placements are not settled has nothing meaningful to measure surfacing against.
15. **Fiscal checks last.** Only after every safety and constraint check has passed does the system look at money: a FIRM quote against the client's budget ceiling (`ERR_QUOTE_EXCEEDS_BUDGET`), funding sufficiency when an order is raised (`ERR_FUNDING_SHORTFALL`), committed funds blocking a refund (`ERR_FUNDS_ALREADY_COMMITTED`) and decayed warranty coverage blocking an approval (`ERR_WARRANTY_EXPIRED`).
16. **Standalone rules that guard a single operation** sit at the end of their own operation's chain: an installer may not be reinstated while audit failures remain open (`ERR_AUDIT_FAILURES_OPEN`), a project may be cancelled only from a cancellable status and may accept pledges only while fundable (`ERR_PROJECT_NOT_CANCELLABLE`, `ERR_PROJECT_NOT_FUNDABLE`), a model whose commercial lifecycle has ended may not be placed (`ERR_MODEL_DISCONTINUED`), a model that is not certified may not be placed, validated or used as a retrofit replacement (`ERR_MODEL_NOT_CERTIFIED`), a placement's attachment parent must itself be validated (`ERR_PARENT_PLACEMENT_NOT_VALIDATED`), a PROVISIONAL quote may not be accepted (`ERR_PROVISIONAL_QUOTE_NOT_ACCEPTABLE`), an inactive installer may not be booked or started (`ERR_INSTALLER_NOT_ACTIVE`) and the logical clock may not be rewound past a recorded installation date (`ERR_CLOCK_REWIND_FORBIDDEN`).

## 3. Business Logic & Workflows

### 3.1. Governing Safety Editions and the Component Catalogue

Everything the plant builds is measured against a **playground safety standard edition**. Registering one is a records-keeping act, open to both `ManufacturerAdmin` and `ComplianceOfficer` operators, and it captures the edition's family `code` — a string of 1 to 40 characters restricted to uppercase letters, digits and the underscore character, such as the family that governs public playground equipment — together with the `edition_year` of this particular revision, an integer between 2000 and 2100 inclusive. The pair of `code` and `edition_year` must be globally unique: the same family may be registered many times, but never twice for the same revision year, and a repeat registration of the same pair is refused with `ERR_INVALID_REQUEST` (HTTP 422) — a uniqueness collision is reported as a shape failure, and it is tested only after every declared field of the body has passed its own type and range validation. The edition also carries `effective_from`, a calendar date in `YYYY-MM-DD` form marking the earliest day on which the revision may take effect, and four numeric requirements: `min_use_zone_clearance_cm`, the minimum number of clear centimetres the edition demands between use zones belonging to different age bands, which may be zero or more; and three fall-height ceilings, `max_fall_height_cm_toddler`, `max_fall_height_cm_preschool` and `max_fall_height_cm_school_age`, each of which must be greater than zero and each of which caps the designated play surface height permitted for the age band named in its field. Finally the boolean `requires_accessible_route` records whether the edition mandates an accessible transfer point in every play area; when the registrant omits it, it defaults to true. A newly registered edition is born in `DRAFT` status with `superseded_by_standard_id` null, and governs nothing at all until it is activated. Registry listings may be narrowed by `status` and by `code`, and — because `superseded_by_standard_id` doubles as a reverse lookup — by the identifier of the edition that superseded them.

Activation is a `ComplianceOfficer` privilege and moves an edition `DRAFT → ACTIVE`. Two things can go wrong. Activating an edition whose status is anything other than `DRAFT` is rejected with `ERR_STANDARD_NOT_DRAFT`, and activating a genuine `DRAFT` while some other edition already sits in `ACTIVE` is rejected with `ERR_ACTIVE_STANDARD_EXISTS` — the registry admits at most one `ACTIVE` edition at any instant, and that invariant is load-bearing throughout §3. A successful activation sets `status` to `ACTIVE` and bumps the edition's `version` by one.

**Supersession is the largest single operation in this API.** A `ComplianceOfficer` retires the `ACTIVE` edition by nominating a `successor_standard_id` in the request body. The edition being retired must itself be `ACTIVE`, or the request fails with `ERR_STANDARD_NOT_ACTIVE`; the nominated successor must be in `DRAFT`, or the request fails with `ERR_SUCCESSOR_NOT_DRAFT`; and the successor's `effective_from` must be on or before the logical clock's current date, or the request fails with `ERR_SUCCESSOR_NOT_EFFECTIVE` — a revision that has not yet come into force cannot be pressed into service early. When all three hold, the retiring edition takes `status` `ACTIVE → SUPERSEDED` and records the successor in its `superseded_by_standard_id`, while the successor is atomically promoted to `ACTIVE`, so the single-`ACTIVE` invariant never lapses even momentarily. The `successor_standard_id` reference is resolved for existence before the three state gates run, so nominating a nonexistent successor reports `ERR_STANDARD_NOT_FOUND` even when the addressed edition is not `ACTIVE`. The response body of a supersession is the **retired** edition — now reading `status` `SUPERSEDED` with `superseded_by_standard_id` filled in — not the newly promoted successor.

The consequences then propagate outward in four hops, all inside the same request. **Hop one:** because the retired edition no longer governs, every `ComponentModel` whose `certified_against_standard_id` points at it and whose `certification_status` is `CERTIFIED` moves `CERTIFIED → DECERTIFIED`; the historical pin in `certified_against_standard_id` is deliberately retained, so the record of what the model was once certified against survives. **Hop two:** because those models are now decertified, every `ComponentPlacement` whose `component_model_id` is one of them moves to `NEEDS_RECERTIFICATION`, provided its own `status` was `DRAFT` or `VALIDATED` and its owning project's `design_status` is one of `CONSULTATION`, `RENDERED`, `COMMUNITY_REVIEW`, `REVISION_REQUESTED`, `DESIGN_APPROVED`, `CERTIFIED` or `ORDERED`. **Hop three:** because those placements now need recertification, each owning `DesignProject` has its `compliance_status` set to `RETROFIT_REQUIRED`; and additionally, any such project whose `design_status` is `RENDERED`, `COMMUNITY_REVIEW` or `CERTIFIED` is reverted to `REVISION_REQUESTED`. A project already sitting in `DESIGN_APPROVED` is a deliberate exception: its community sign-off is preserved and its `design_status` is *not* reverted, though its `compliance_status` still becomes `RETROFIT_REQUIRED`. **Hop four:** for exactly those projects whose `design_status` hop three reverted to `REVISION_REQUESTED`, every `DesignRendering` of theirs in `ISSUED` status moves to `SUPERSEDED` and every `Quote` of theirs in `ISSUED` status moves to `EXPIRED`. The `DESIGN_APPROVED` project keeps its `ISSUED` rendering — which now pins an edition that is no longer `ACTIVE`, so its later attempt at compliance certification will fail with `ERR_STANDARD_NOT_ACTIVE`. That is the intended trap, not an oversight.

After the hops, every play area touched by hop two has its `critical_fall_height_cm` and `required_surfacing_depth_cm` recomputed, because placements that have left `DRAFT` and `VALIDATED` also leave the input set of those two derived numbers. That recomputation is the **non-raising** form described in §3.3: it records whatever the shrunken placement set yields, even a critical fall height above the absolute 305-centimetre ceiling, so no hop of this cascade can fail on that ceiling. The cascade as a whole therefore never fails partway — once the three state gates above have passed, all four hops and the recomputation land, and there is no half-applied outcome to reason about. Version counters are incremented by one on the retired edition, on the promoted successor, and on every model, placement, rendering and quote the four hops actually mutated; the projects hop three reaches and the play areas hop two touched are bumped **unconditionally**, the project's counter moving even when its `compliance_status` already read `RETROFIT_REQUIRED` and its `design_status` was not among the three hop three reverts, and the area's counter moving even when the recomputation left both derived numbers exactly where they were. Those two are carve-outs of exactly the kind §2.9 reserves to an operation's own narrative, standing against its general rule that a row a cascade examines but does not change is not bumped.

Turning to the catalogue: a `ManufacturerAdmin` adds a component model with a `sku` of 1 to 40 characters that must be globally unique — a duplicate `sku` is refused with `ERR_INVALID_REQUEST` (HTTP 422), tested after the rest of the body has passed shape validation, and matched exactly and case-sensitively — a `category` drawn from `POST`, `DECK`, `PLASTIC_SLIDE`, `METAL_CLIMBER` and `HARDWARE_KIT`, and an `age_group` drawn from `TODDLER_6_23M`, `PRESCHOOL_2_5` and `SCHOOL_AGE_5_12`. Geometry comes from two integers: `deck_height_cm`, the designated play surface height this model contributes, which ranges from 0 (for ground-level components) to 400 inclusive; and `use_zone_footprint_cm`, the half-extent of the model's use zone measured outward from its anchor point along the site axis, which must be zero or more. Commercial terms come from `unit_price_cents`, a list price greater than zero that excludes both colour uplift and freight; `hardware_bag_count`, the number of fastener bags shipped per unit, zero or more; `warranty_years`, a term between 1 and 50 inclusive; and `parts_support_until_year`, the last calendar year between 2000 and 2200 inclusive in which replacement parts for the model are still sold. The `color_options` array holds between 1 and 8 distinct strings, each of which must be non-empty and must already be uppercase — a string that is empty, or that contains any character with a distinct lower-case form, is refused with `ERR_INVALID_REQUEST` — and its **first element is the no-cost default colour** — any other selection is chargeable, as §3.5 explains. The boolean `accessible_transfer_ready` records whether the model provides a compliant accessible transfer point and defaults to false. Where the model replaces an older one for retrofit purposes, `supersedes_model_id` names that predecessor; for a new family it is omitted and stored as null, and it doubles as a reverse-lookup filter on catalogue listings. A newly added model is `UNCERTIFIED` with `certified_against_standard_id` null and `lifecycle_status` `ACTIVE`. Catalogue listings may be filtered by `category`, `age_group`, `certification_status`, `lifecycle_status`, `supersedes_model_id` and `certified_against_standard_id`.

Certification of a model is a `ComplianceOfficer` act that resolves the single `ACTIVE` edition itself — the caller supplies no body. A model may be certified from `UNCERTIFIED` and re-certified from `DECERTIFIED`; attempting it on a model that is already `CERTIFIED`, or on one whose `lifecycle_status` has reached `DISCONTINUED`, fails with `ERR_MODEL_NOT_CERTIFIABLE`. Those two admissibility tests come first, in the order just given and in keeping with §2.10 items 7 and 10: only once the model's own `certification_status` and `lifecycle_status` permit the move does the server look for a governing edition, and if none is `ACTIVE` the attempt then fails with `ERR_NO_ACTIVE_STANDARD`. An already-`CERTIFIED` model therefore reports `ERR_MODEL_NOT_CERTIFIABLE` even when the registry holds no `ACTIVE` edition at all. The substantive check is dimensional: the model's `deck_height_cm` must not exceed the resolved edition's ceiling for the model's own `age_group` — `max_fall_height_cm_toddler` for `TODDLER_6_23M`, `max_fall_height_cm_preschool` for `PRESCHOOL_2_5`, `max_fall_height_cm_school_age` for `SCHOOL_AGE_5_12` — and a model that stands taller than its band permits is refused with `ERR_FALL_HEIGHT_EXCEEDS_STANDARD`. On success the model's `certification_status` becomes `CERTIFIED`, `certified_against_standard_id` is set to the resolved edition, and `version` is incremented by one. Re-certification after a supersession closes the `DECERTIFIED → CERTIFIED` half of the model's certification cycle, and its new pin points at the new edition.

A model's commercial availability is a second, independent dimension. A `ManufacturerAdmin` moves it along by supplying a `lifecycle_status` value: `ACTIVE → LEGACY` marks the model as an older-system part, after which every replacement-part sale of it prices in an eighteen-percent surcharge (§3.9); `LEGACY → DISCONTINUED` retires it from new designs altogether, and a placement attempt against a discontinued model is refused with `ERR_MODEL_DISCONTINUED`. `DISCONTINUED` is terminal, and a lifecycle move that no transition declares — jumping from `ACTIVE` straight to `DISCONTINUED`, restating a model's current value, or moving a model that is already `DISCONTINUED` — is rejected as an inadmissible transition with `ERR_MODEL_NOT_CERTIFIABLE` (HTTP 409): the model-state code of §2.10 item 7 does double duty for the lifecycle axis, there being no separate lifecycle code in the catalogue. A `lifecycle_status` value outside `ACTIVE`, `LEGACY` and `DISCONTINUED` is a shape failure and reports `ERR_INVALID_REQUEST` instead. Certification status and lifecycle status never affect one another: a `LEGACY` model can be perfectly `CERTIFIED`, which is exactly what makes compliance retrofits to legacy parts possible.

### 3.2. Opening a Consultation: Site Constraints, Age Bands and Play Areas

A `DesignConsultant` opens the engagement by creating a project for the commissioning `client_name`, a string of 1 to 120 characters naming the school, municipality or homeowners' association footing the bill. The site is described by two extents, both greater than zero and both no larger than 100000 centimetres: `site_length_cm` along the layout axis, inside which every play area must fit, and `site_width_cm` perpendicular to it, which is recorded for the record but never enters a geometric check in this specification. Subgrade classification arrives as `site_soil_type`, one of `SANDY_LOAM`, `GRAVEL` or `CLAY`, and clay subgrade carries a surfacing consequence described in §3.3. Commercial and calendar boundaries arrive as `budget_cents`, a hard ceiling greater than zero that a contractual quote may not breach, and `fundraising_deadline`, a `YYYY-MM-DD` date after which pledges may no longer be collected. The `required_age_groups` array names between 1 and 3 distinct age bands drawn from `TODDLER_6_23M`, `PRESCHOOL_2_5` and `SCHOOL_AGE_5_12` that the finished playground must serve. The optional boolean `accessible_route_required` records whether the client's contract independently mandates an accessible transfer point in every play area and defaults to true when omitted.

The created project starts with `design_status` `DRAFT` and `compliance_status` `NOT_ASSESSED`, and it stores the acting consultant's `X-User-ID` in `consultant_user_id` — the value the segregation-of-duties check in §3.7 later compares against. Its counters start at zero: `revision_rounds` is 0, `funds_collected_cents` is 0, and all four allocation buckets — `alloc_permit_freight_cents`, `alloc_surfacing_cents`, `alloc_structure_cents` and `alloc_contingency_cents` — are 0. Its `installed_on` is null and stays null until the day the installation passes inspection. Project listings can be narrowed by `design_status` and by `compliance_status`, and a single project's representation exposes `funds_collected_cents` alongside those four buckets.

Two state dimensions run on a project and they are genuinely independent. `design_status` walks the design lifecycle through `DRAFT`, `CONSULTATION`, `RENDERED`, `COMMUNITY_REVIEW`, `REVISION_REQUESTED`, `DESIGN_APPROVED`, `CERTIFIED`, `ORDERED`, `INSTALLED`, `AUDITED` and `CANCELLED`, of which `AUDITED` and `CANCELLED` are terminal. `compliance_status` tracks regulatory posture through `NOT_ASSESSED`, `COMPLIANT`, `RETROFIT_REQUIRED` and `NON_COMPLIANT`, and it advances on its own triggers. Because they are independent, combinations that look contradictory are legal and expected: a project can sit at `design_status` `DESIGN_APPROVED` while its `compliance_status` reads `RETROFIT_REQUIRED`, which is precisely the state hop three of a supersession leaves behind.

Starting the consultation moves the project `DRAFT → CONSULTATION` and is what makes design content editable at all. It requires exactly one edition to be in `ACTIVE` status; with no `ACTIVE` edition the attempt is refused with `ERR_NO_ACTIVE_STANDARD`. On success `design_status` becomes `CONSULTATION` and the project's `version` is incremented by one. Firing the same trigger a second time, or firing it from any status other than `DRAFT`, is rejected with `ERR_PROJECT_INVALID_STATE`.

**Design content is editable only in two statuses.** Creating a play area, creating a placement, validating a placement and removing a placement are all permitted only while the owning project's `design_status` is `CONSULTATION` or `REVISION_REQUESTED`; in any other status they are refused with `ERR_PROJECT_NOT_EDITABLE`. That second permitted status is what lets a project reopened by a below-threshold community review, or by hop three of a supersession, actually be repaired.

Inside an editable project, a consultant carves out play areas. Each area serves a single `age_group` from the same three bands, and a project may hold at most one area per band — the combination of owning project and `age_group` is unique, a second area for a band already carved out being refused with `ERR_INVALID_REQUEST` (HTTP 422), and the area's `project_id` is taken from the request path rather than the body. The area occupies a **half-open** interval on the site axis: `axis_origin_cm`, which must be zero or more, is inside the interval, and the interval runs for `axis_length_cm` centimetres, which must be greater than zero, with the coordinate at origin plus length lying outside it. The sum of `axis_origin_cm` and `axis_length_cm` must not exceed the project's `site_length_cm`, and an area that would run off the site is refused with `ERR_INVALID_REQUEST` (HTTP 422). Both of these body-level tests — the site-length fit and the one-area-per-band uniqueness, in that order — are evaluated **before** the editability gate of §2.10 item 8, so an attempt that duplicates a band on a project that is not editable reports `ERR_INVALID_REQUEST` rather than `ERR_PROJECT_NOT_EDITABLE`. Protective surfacing is specified per area by `surfacing_material`, either `ENGINEERED_WOOD_FIBER` or `POURED_RUBBER`, and by `surfacing_depth_cm`, the depth the design commits to, between 0 and 120 centimetres inclusive. A newly created area is `PLANNED`, with `critical_fall_height_cm` at 0 and `required_surfacing_depth_cm` at the absolute floor of 15 centimetres; creating it increments the owning project's `version` by one, and the area row itself is returned with HTTP 201. Area listings under a project may be filtered by `age_group` and by `status`.

An area's own lifecycle has three states. `PLANNED` becomes `ZONED` automatically the moment the area's first placement reaches `VALIDATED`, and `ZONED` becomes `LOCKED` automatically when the owning project is ordered. `LOCKED` is terminal: a locked area accepts no further placement creation, validation or removal, and such attempts are refused with `ERR_PLAY_AREA_LOCKED`. A single area's representation exposes both derived numbers, `critical_fall_height_cm` and `required_surfacing_depth_cm`, so a consultant can see the surfacing obligation the design has accumulated.

### 3.3. Placing Components: Use Zones, the Attachment Graph and Validation

Placing a catalogue component inside a play area is the atom of design work. The consultant names the `component_model_id` being placed, picks a `color_choice`, anchors it at `x_start_cm` — a coordinate on the site axis that must be zero or more — and states a `quantity` of identical units between 1 and 50 inclusive. Where the component bolts onto another, `attached_to_placement_id` names the parent placement; free-standing components omit it and it is stored as null. The `color_choice` must be a member of the model's `color_options`, and a value outside that array is refused with `ERR_INVALID_REQUEST` (HTTP 422) as part of reading the body, therefore ahead of the editability and lock gates and ahead of every safety check below; any value other than the first element of that array incurs the colour uplift when the design is priced. A placement's `play_area_id` is taken from the request path, never from the body, and the placement is born in `DRAFT`.

Creation is gated by a run of checks in a fixed order. The project must be editable and the area must not be `LOCKED`. The model must then be `CERTIFIED`, or the placement is refused with `ERR_MODEL_NOT_CERTIFIED`; it must not have reached `DISCONTINUED`, or the placement is refused with `ERR_MODEL_DISCONTINUED`. The remaining checks read the single `ACTIVE` edition — if none is `ACTIVE`, the attempt fails with `ERR_NO_ACTIVE_STANDARD`. The model's `deck_height_cm` must not exceed the `ACTIVE` edition's ceiling for the area's age band, otherwise `ERR_FALL_HEIGHT_EXCEEDS_STANDARD` (HTTP 422); the same code is returned when the placement would push the area's `critical_fall_height_cm` past the absolute 305-centimetre ceiling described below. **Only once both fall-height tests have passed does the band-agreement test run:** the model's `age_group` must equal the owning area's `age_group`, otherwise `ERR_AGE_GROUP_MISMATCH` (HTTP 422) — a preschool slide cannot be dropped into a toddler area. That precedence is normative and is the same one §2.10 item 12 states: a placement that is simultaneously too tall for the band's ceiling *and* drawn from the wrong band reports `ERR_FALL_HEIGHT_EXCEEDS_STANDARD`, never `ERR_AGE_GROUP_MISMATCH`.

**Use-zone geometry** is derived, never supplied. For the placement being written, `use_zone_start_cm` is the anchor coordinate `x_start_cm` less the model's `use_zone_footprint_cm`. `use_zone_end_cm` is the anchor coordinate plus the model's `use_zone_footprint_cm`, plus a further 122 centimetres when and only when the model's `category` is `PLASTIC_SLIDE` — a slide needs clear run-out past its exit that a post or a deck does not. The resulting interval from `use_zone_start_cm` to `use_zone_end_cm` is **closed at both ends**. That whole interval must lie inside the owning area's half-open axis interval, meaning the start must be at or after `axis_origin_cm` and the end must be strictly before `axis_origin_cm` plus `axis_length_cm`; a zone that pokes outside its area is refused with `ERR_USE_ZONE_OUT_OF_BOUNDS` (HTTP 422).

Attachment direction follows the catalogue, and violating it yields `ERR_INVALID_ATTACHMENT_TARGET` (HTTP 422). A `PLASTIC_SLIDE` and a `METAL_CLIMBER` may attach only to a placement whose model `category` is `DECK`. A `DECK` may attach only to a `POST`. A `POST` and a `HARDWARE_KIT` attach to nothing at all, so supplying a parent for either of them is a violation. Because decks hang off posts and slides hang off decks, the placements of a project form a directed acyclic graph through `attached_to_placement_id`, and the attachment parent must be a placement in the same play area — a parent living in a different area of the same project is refused with that same code. The parent's own `status` is *not* examined at creation time: a `DRAFT` parent is an acceptable attachment target, and the requirement that the parent be `VALIDATED` bites only at validation. Sending `attached_to_placement_id` explicitly as `null` is identical to omitting it and yields a free-standing placement.

Validating a `DRAFT` placement is the consultant's assertion that it is buildable, and it is where the expensive geometry runs. The placement itself must be in `DRAFT`; validating one that is already `VALIDATED`, or one that has been demoted to `NEEDS_RECERTIFICATION`, is refused with `ERR_PLACEMENT_INVALID_STATE`. The project must be editable and the area must not be `LOCKED`. The model must still be `CERTIFIED`, or the attempt fails with `ERR_MODEL_NOT_CERTIFIED` — a model decertified by a supersession blocks validation even though the placement was created while it was fine. If the placement declares an attachment parent, that parent must itself already be `VALIDATED`, otherwise `ERR_PARENT_PLACEMENT_NOT_VALIDATED`; the practical consequence is that a structure must be validated bottom-up, posts before decks before slides.

Two spatial checks then run, and both are deliberately restricted to placements already in `VALIDATED` status — `DRAFT` and `NEEDS_RECERTIFICATION` placements are invisible to them, which is why **the order in which a consultant validates placements changes the outcome**. Of the two, the cross-area separation check is evaluated **first** and the in-area overlap check second — the precedence §2.10 items 12 and 13 also imply — so a placement that simultaneously crowds a different band's zone and overlaps a neighbour inside its own area reports `ERR_AGE_GROUP_SEPARATION_VIOLATION`, never `ERR_USE_ZONE_OVERLAP`. Described in the order they are written rather than the order they run: the in-area check is overlap inside the area: two closed use-zone intervals overlap when the first's start is at or before the second's end *and* the second's start is at or before the first's end. Two zones that merely touch at a single coordinate — where one interval's end equals the other's start — therefore *do* overlap, while a one-centimetre gap between them does not. Any overlap with another `VALIDATED` placement in the same area is refused with `ERR_USE_ZONE_OVERLAP` (HTTP 409), with exactly one exemption: a pair is exempt when one of the two is the other's attachment parent, because a slide bolted to its deck must by construction overlap that deck's zone. The second check reaches across areas: for every `VALIDATED` placement sitting in a *different* play area of the same project — therefore serving a different age band — the two zones must be separated by at least the `ACTIVE` edition's `min_use_zone_clearance_cm` clear centimetres. Clear separation is counted as the number of whole centimetres strictly between the two intervals: take the later interval's start, subtract the earlier interval's end, subtract one more, and the result must be greater than or equal to `min_use_zone_clearance_cm`; when the two intervals themselves overlap, the clear separation is taken to be negative and therefore always falls short. Falling short is refused with `ERR_AGE_GROUP_SEPARATION_VIOLATION` (HTTP 409). Unlike placement creation, validation does **not** require a governing edition: when no edition is `ACTIVE` at all the separation check is skipped outright rather than failing, since there is no `min_use_zone_clearance_cm` to read, and the in-area overlap check — which reads no edition — still runs.

A successful validation sets the placement's `status` to `VALIDATED`, promotes the owning area from `PLANNED` to `ZONED` if it was still `PLANNED`, recomputes the area's `critical_fall_height_cm` and `required_surfacing_depth_cm`, and increments both the placement's and the area's `version` by one.

**The two derived numbers on a play area** deserve their own statement, because five different operations read them. `critical_fall_height_cm` is the largest `deck_height_cm` among the models of the area's placements whose `status` is `DRAFT` or `VALIDATED`; when that set is empty the value is 0. Placement creation is the **one** operation that enforces an absolute ceiling on it: if the placement being written would carry that maximum past 305 centimetres, the creation is refused with `ERR_FALL_HEIGHT_EXCEEDS_STANDARD`. The recomputations triggered by validation, removal, retrofit and the supersession cascade deliberately never raise on that ceiling — they simply record whatever the area's current placement set yields, so a value above 305 can persist on an area whose contents changed underneath it. `required_surfacing_depth_cm` is then derived from the critical fall height, the area's surfacing product and two independent uplifts. Start with a base attenuation depth. When the critical fall height is 0 there is nothing to fall from and the base is 0. Otherwise, for `ENGINEERED_WOOD_FIBER` the base is 23 centimetres when the critical fall height is at most 150 centimetres, 30 centimetres when it is at most 200, and 38 centimetres above that; for `POURED_RUBBER` the base is 5 centimetres at or below 150, 8 centimetres at or below 200, and 13 centimetres above that. Two uplifts then apply, and **they are not additive**: each is applied to the base on its own to form a candidate, and the requirement is the largest candidate. The first candidate is the base plus 5 centimetres when the area's `age_group` is `TODDLER_6_23M`, and the base unchanged otherwise. The second candidate is the base plus 3 centimetres when the owning project's `site_soil_type` is `CLAY`, and the base unchanged otherwise. `required_surfacing_depth_cm` is the greatest of those two candidates and the absolute minimum of 15 centimetres — which is why an area with no placements at all still reads 15. All terms are whole centimetres and nothing is rounded. Both numbers are recomputed on every placement creation, every validation, every removal and every retrofit under the area. The area's own `version` follows two different rules depending on the trigger: **on placement creation it is incremented only when the recomputation actually changes one of the two derived numbers**, so placing a component no taller than what the area already holds leaves the area's counter alone; on placement validation, placement removal and retrofit it is incremented unconditionally, whether or not either number moved.

Removing a placement is available to a `DesignConsultant` while the project is editable and the area is not `LOCKED`, and it returns HTTP 204 with no body. Removal deletes the placement, clears `attached_to_placement_id` on any child placement that pointed at it — the children survive as free-standing placements rather than being deleted, and each child so reparented has its own `version` incremented by one — recomputes the area's two derived numbers, and increments the area's `version` by one. A placement may be removed from any of its three statuses: there is no placement-state gate on removal, so a `VALIDATED` or `NEEDS_RECERTIFICATION` placement is as removable as a `DRAFT` one.

A placement's `status` takes one of three values, `DRAFT`, `VALIDATED` and `NEEDS_RECERTIFICATION`, and its representation also carries the pricing of the most recent replacement-part or retrofit purchase made against it: `retrofit_model_id`, `retrofit_quantity`, `retrofit_unit_price_cents`, `retrofit_handling_cents`, `retrofit_total_cents` and the boolean `legacy_surcharge_applied`, all of which start at null, zero, zero, zero, zero and false respectively and are explained in §3.9. Placement listings across the catalogue may be filtered by `play_area_id`, `component_model_id`, `attached_to_placement_id`, `retrofit_model_id` and `status`; listings scoped to one area may be filtered by `status`.

### 3.4. Renderings, Community Input and Revision Rounds

Issuing a design rendering is how a consultant freezes a design for the community to look at. The request carries a single field, `pinned_standard_id`, and it must name the edition that is currently `ACTIVE`; pinning anything else — a `DRAFT` edition, or one already `SUPERSEDED` — is refused with `ERR_STANDARD_NOT_ACTIVE`, and issuing while no edition is `ACTIVE` at all is refused with `ERR_NO_ACTIVE_STANDARD`. The project must be in `CONSULTATION` or `REVISION_REQUESTED`; from any other `design_status` the attempt fails with `ERR_PROJECT_INVALID_STATE`.

Three completeness gates then run in this order. Every age band listed in the project's `required_age_groups` must have a play area of that `age_group`, or the request is refused with `ERR_AGE_GROUP_COVERAGE_INCOMPLETE`. Every play area of the project — including any extra area beyond the required bands — must hold at least one placement whose `status` is `DRAFT` or `VALIDATED`, or the request is refused with `ERR_PLAY_AREA_EMPTY`. And accessibility: when either the project's `accessible_route_required` is true **or** the `ACTIVE` edition's `requires_accessible_route` is true, every play area must hold at least one placement in `DRAFT` or `VALIDATED` whose model has `accessible_transfer_ready` set to true; a shortfall is refused with `ERR_ACCESSIBLE_ROUTE_MISSING` (HTTP 422). Note the disjunction: a client contract that waives the accessible route cannot override an edition that mandates one.

A successful issuance creates a rendering in `ISSUED` status whose `round_number` is one greater than the highest `round_number` any previous rendering of the project holds, or 1 when this is the project's first. It freezes `use_zone_snapshot`, a map keyed by each play area's identifier whose value records that area's `critical_fall_height_cm`, its `required_surfacing_depth_cm`, its specified `surfacing_depth_cm` and its `placement_count` as they stood at issue time. It freezes `pinned_standard_id`, and that pin is never rewritten afterwards even when the pinned edition is later superseded. Any other rendering of the same project still in `ISSUED` moves to `SUPERSEDED`. The project's `design_status` becomes `RENDERED` and its `version` is incremented by one. Renderings are returned with HTTP 201 and their vote tallies start at zero: `yes_votes` 0, `no_votes` 0 and `community_approval_pct` 0.0. Rendering listings may be filtered by `project_id`, `pinned_standard_id` and `status`; the project-scoped listing accepts `pinned_standard_id` and `status` only, `project_id` being already fixed by the path. A rendering's own representation exposes the frozen `use_zone_snapshot` alongside the tallies.

Community input arrives from a `ClientRepresentative` as batches rather than individual ballots. Each batch supplies `yes_votes` and `no_votes` — both are required integers of zero or more, and a batch of two zeros is perfectly admissible and simply leaves the tallies where they stand — and the values are **added to** the rendering's running `yes_votes` and `no_votes` rather than replacing them. The rendering must be in `ISSUED` status, or the batch is refused with `ERR_RENDERING_NOT_ISSUED`, and the owning project must be in `RENDERED` or `COMMUNITY_REVIEW`. After the batch is absorbed, `community_approval_pct` is re-derived: with no votes at all it is 0.0; otherwise it is one hundred multiplied by the accumulated `yes_votes`, divided by the sum of `yes_votes` and `no_votes`, rounded half up to exactly one decimal place. Recording a batch also sets the project's `design_status` to `COMMUNITY_REVIEW`, which is idempotent when the project is already there, and increments both the rendering's and the project's `version` by one — the project's counter moves on that write even when its `design_status` was already `COMMUNITY_REVIEW`. The response body of a vote batch is the **rendering**, carrying its new tallies and `community_approval_pct`, not the project.

Closing the review is a `DesignConsultant` act, and it is a **branch, not a pass/fail gate**. The rendering must still be `ISSUED` (otherwise `ERR_RENDERING_NOT_ISSUED`) and the project must be in `COMMUNITY_REVIEW`. Turnout is checked first: the sum of `yes_votes` and `no_votes` must be at least 25, and a review closed on thinner participation is refused with `ERR_INSUFFICIENT_COMMUNITY_INPUT` (HTTP 422). Once turnout clears, `community_approval_pct` selects the branch and never itself raises an error, and the comparison is **inclusive** — exactly 60.0 percent approves. The value compared is the stored field itself, already rounded to one decimal place by the last vote batch, not a freshly recomputed exact ratio: a tally whose exact approval is 59.95 percent stores 60.0 and therefore takes the approve branch.

The two branches have deliberately unequal consequences, and both must be implemented in full. On the **approve branch**, where `community_approval_pct` is greater than or equal to 60.0, the project's `design_status` moves `COMMUNITY_REVIEW → DESIGN_APPROVED` and the rendering is left in `ISSUED` status precisely so that it can go on to back a quote; `revision_rounds` is not touched, no quote is expired, and the rendering is not withdrawn. On the **revise branch**, where `community_approval_pct` is below 60.0, three further things happen beyond the status move: the rendering's `status` becomes `WITHDRAWN`, the project's `design_status` becomes `REVISION_REQUESTED` and its `revision_rounds` counter is incremented by one, and every `Quote` of the project still in `ISSUED` status is moved to `EXPIRED`. Either way, every row actually touched has its `version` incremented by one, and the operation's response body is the project rather than the rendering.

Because a project in `REVISION_REQUESTED` is editable again and may have a new rendering issued from it, the cycle `RENDERED → COMMUNITY_REVIEW → REVISION_REQUESTED → RENDERED` may run as many times as the community demands, each pass minting a rendering whose `round_number` is one higher than the last and incrementing `revision_rounds` once per completed round that ended in revision. A rendering's own lifecycle has two terminal outcomes, `SUPERSEDED` when a newer rendering displaces it or a supersession cascade retires it, and `WITHDRAWN` when a review closes below threshold.

### 3.5. Quoting: Two Pricing Variants, Budget Discipline and Acceptance

A quote is a `DesignConsultant`'s priced offer against a specific rendering, and it is computed once at issue time and frozen thereafter. The request identifies the `project_id` being quoted and the `rendering_id` being priced, selects a `variant` of either `PROVISIONAL` or `FIRM`, sets `valid_until` — the last `YYYY-MM-DD` calendar day on which the quote may still be accepted, on which no lower bound is imposed at issue time, so a quote may legitimately be issued carrying a `valid_until` that already lies behind the logical clock and is then simply unacceptable from birth — and carries the `expected_project_version` described in §2.8. The named rendering must belong to the named project, or the request is refused with `ERR_RENDERING_PROJECT_MISMATCH` (HTTP 422), and it must be in `ISSUED` status, or refused with `ERR_RENDERING_NOT_ISSUED`.

Pricing proceeds in six steps, and the first and third of them depend on the variant.

**Step one, the input set.** Gather every `ComponentPlacement` whose owning play area belongs to the quoted project and whose `status` is included by the variant, ordered by `created_at` ascending, with placements sharing a `created_at` instant ordered among themselves by insertion order exactly as §2.3 requires — that ordering is the only sanctioned one and identifier ordering must never be substituted for it, though because both variants' subtotals are order-independent sums the tie-break never shows up in the frozen amounts. A `PROVISIONAL` quote includes placements in `DRAFT` *and* `VALIDATED`, because an early budgetary number is meant to price a design that is still being validated. A `FIRM` quote includes only placements in `VALIDATED`. Placements demoted to `NEEDS_RECERTIFICATION` are priced by neither variant. If the resulting set is empty there is nothing to price, and the request is refused with `ERR_QUOTE_EMPTY_SCOPE` (HTTP 422).

**Step two, the per-line raw amount.** For each placement in that ascending order, take its model's `unit_price_cents`, multiply by the placement's `quantity`, and call the product the base line. When the placement's `color_choice` differs from the first element of the model's `color_options`, the raw line is the base line increased by seven percent — that is, the base line multiplied by one plus seven hundredths. When the colour choice is the default first element, the raw line is the base line unchanged. These raw amounts are carried exactly, with no rounding, into step three.

**Step three, the subtotal — and this is the only place the two variants differ arithmetically.** For a `PROVISIONAL` quote, each raw line is rounded half up to whole cents first, and `subtotal_cents` is the sum of those rounded lines. For a `FIRM` quote, the exact unrounded raw lines are summed first and the single total is rounded half up to whole cents once, at the end. On identical placement data the two orders can differ by as much as one cent for every priced line beyond the first: three lines whose exact values each end in half a cent give the `PROVISIONAL` order a subtotal one cent above the `FIRM` order's. Both behaviours are required; neither is an approximation of the other.

**Step four, freight.** `priced_unit_count` is the sum of `quantity` over the placements the variant included. `freight_cents` is a flat base of 48000 cents plus 1250 cents for every priced unit.

**Step five, the volume discount.** The tier is selected on `subtotal_cents` **alone** — never on the subtotal plus freight — and freight itself is never discounted. When `subtotal_cents` is at least 5000000 cents the rate is six percent; otherwise, when it is at least 2000000 cents the rate is three percent; otherwise the rate is zero. `discount_cents` is `subtotal_cents` multiplied by that rate, rounded half up to whole cents.

**Step six.** `total_cents` is `subtotal_cents` plus `freight_cents` less `discount_cents`.

A `FIRM` quote carries three additional obligations that a `PROVISIONAL` quote does not, because a firm quote is the contractual instrument a manufacturing order may be raised against. Every play area of the project must have a specified `surfacing_depth_cm` greater than or equal to its `required_surfacing_depth_cm`, or the issuance is refused with `ERR_SURFACING_DEPTH_INSUFFICIENT` (HTTP 422). The accessible-route provision of §3.4 is re-checked: with either the project's `accessible_route_required` or the `ACTIVE` edition's `requires_accessible_route` true, every play area must hold an accessible-transfer-ready placement in `DRAFT` or `VALIDATED`, or the issuance is refused with `ERR_ACCESSIBLE_ROUTE_MISSING`. Unlike rendering issuance, this re-check does **not** require a governing edition: when no edition is `ACTIVE` the demand is read from the project's own `accessible_route_required` alone rather than failing with `ERR_NO_ACTIVE_STANDARD`. And the resulting `total_cents` must not exceed the project's `budget_cents`, or the issuance is refused with `ERR_QUOTE_EXCEEDS_BUDGET` (HTTP 422) — fiscal checks of this kind run only after every safety and constraint check has already passed.

Issuing a quote creates it in `ISSUED` status with `subtotal_cents`, `freight_cents`, `discount_cents`, `total_cents` and `priced_unit_count` all frozen, moves every other `Quote` of the project still in `ISSUED` to `EXPIRED`, and increments the project's `version` by one. That sibling sweep runs after the new quote row already exists and **exempts the new quote by identifier**, so a freshly issued quote never expires itself; and because it only looks at `ISSUED` rows, a quote of the same project already sitting in `ACCEPTED` survives the issuance untouched, which is how two live candidates can coexist for the purposes of §3.6. That version bump is exactly why the stale-version guard of §2.8 exists on this operation. Quotes are returned with HTTP 201, and quote listings may be filtered by `project_id`, `rendering_id`, `status` and `variant`.

Acceptance belongs to the `ClientRepresentative`, and its four gates run in this order, which is the §2.10 ordering applied to this one operation and is normative. First the quote must be in `ISSUED` status, or the attempt is refused with `ERR_QUOTE_NOT_ACCEPTED` — that code covers an already-`ACCEPTED`, `EXPIRED` quote as much as a second acceptance of the same one. Second the rendering backing the quote must still be in `ISSUED` status, or the attempt is refused with `ERR_RENDERING_NOT_ISSUED`. Third the logical clock's date must be on or before `valid_until`, or the attempt is refused with `ERR_QUOTE_EXPIRED`. Fourth and last its `variant` must be `FIRM`, since a budgetary number is not contractually acceptable and attempting it is refused with `ERR_PROVISIONAL_QUOTE_NOT_ACCEPTABLE` — so a `PROVISIONAL` quote whose `valid_until` has also passed reports `ERR_QUOTE_EXPIRED`, the expiry check being the earlier of the two. On success the quote's `status` becomes `ACCEPTED`, every other quote of the same project still in `ISSUED` becomes `EXPIRED` — the accepted quote is again exempted from that sweep by identifier, though it has already left `ISSUED` in any case — and the `version` of every quote touched, the accepted one and each expired sibling, is incremented by one. The project row is not written at all by an acceptance: its `version` does not move, which is why §2.8 asks for no `expected_project_version` here. `ACCEPTED` and `EXPIRED` are both terminal, so a quote is never revived; a project that needs a different number needs a new quote.

Quotes expire from `ISSUED` for five distinct reasons, and all five must be implemented: a newer quote is issued for the same project, a sibling quote is accepted, a community review closes below threshold, the project is cancelled, or hop four of a standard supersession fires. Each of those expirations increments the expired quote's `version` by one.

### 3.6. Community Fundraising and the Allocation Waterfall

Community playgrounds are paid for by pledge drives, and the API models the drive explicitly so that ordering can be gated on money actually in hand. A pledge is recorded against a project by either a `ClientRepresentative` or a `DesignConsultant`, carrying `amount_cents` greater than zero and `pledged_at`, the `YYYY-MM-DD` date on which the pledge was made, which must not be later than the logical clock's current date — a future-dated pledge is refused with `ERR_INVALID_REQUEST` (HTTP 422), and that test runs before the fundability gate below. The pledge's `project_id` comes from the request path. The project's `fundraising_deadline` is **not** consulted at pledge time: a pledge may be recorded after the deadline has passed, and the deadline gates only collection. A project accepts pledges only while its `design_status` is outside `CANCELLED`, `INSTALLED` and `AUDITED`; in any of those three it is refused with `ERR_PROJECT_NOT_FUNDABLE`. A recorded pledge is born `PLEDGED` and returned with HTTP 201, and — importantly — it contributes nothing to the project's money until it is collected. Recording a pledge mutates no field of the project and bumps no project `version`; the project row is read only to check fundability. Pledge listings under a project may be filtered by `status`.

Collecting a pledge is a `ClientRepresentative` act. The pledge must be in `PLEDGED` status, and collecting one that is not is refused with `ERR_PLEDGE_INVALID_STATE`. The logical clock's date must be on or before the project's `fundraising_deadline`, or the collection is refused with `ERR_FUNDRAISING_DEADLINE_PASSED`. The owning project's `design_status` must not be `CANCELLED` or `AUDITED`, or the collection is refused with `ERR_PROJECT_NOT_FUNDABLE`. On success the pledge's `status` becomes `COLLECTED`, the project's `funds_collected_cents` and all four allocation buckets are recomputed from scratch, and both the pledge's and the project's `version` are incremented by one.

**The allocation waterfall** is recomputed in full on every collection and every refund, never patched incrementally. Begin by summing `amount_cents` over every pledge of the project whose `status` is `COLLECTED`; that sum is `funds_collected_cents`. Then find the project's most recently created `Quote` whose `status` is `ISSUED` or `ACCEPTED` — order the candidates by `created_at` ascending, breaking a tie between candidates that share a `created_at` instant by the order in which the server inserted them, exactly the total ordering §2.3 lays down, and take the last one. Two candidates genuinely can coexist, because issuance and acceptance both expire only `ISSUED` siblings and therefore leave an `ACCEPTED` quote standing, so this tie-break is load-bearing rather than decorative: the governing quote is always the latest-inserted of the surviving candidates, never the `ACCEPTED` one merely because it is the accepted one. When no such quote exists, all three targeted buckets are zero and `alloc_contingency_cents` absorbs the entire collected amount. When one does exist, it supplies three targets in strict fill order. The first target, for permits and freight, is the quote's `freight_cents`. The second target, for surfacing, is the quote's `subtotal_cents` multiplied by twenty percent, rounded half up to whole cents. The third target, for structure, is the quote's `subtotal_cents` less that surfacing target — defined by subtraction precisely so that the surfacing and structure targets sum to `subtotal_cents` exactly, with no rounding remainder left stranded. Contingency has no target and absorbs whatever survives the first three.

Fill the buckets in that order. `alloc_permit_freight_cents` receives the smaller of the remaining funds and the first target, and that amount leaves the remaining funds. `alloc_surfacing_cents` receives the smaller of what now remains and the second target, and that amount leaves the remainder. `alloc_structure_cents` receives the smaller of what now remains and the third target, and that amount leaves the remainder. `alloc_contingency_cents` receives every cent still remaining. The invariant that must hold after every collection and every refund is that the four buckets sum to exactly `funds_collected_cents` — no cent is created and none is lost.

Refunding is the compensating action, available to a `ClientRepresentative` on a pledge whose `status` is `PLEDGED` or `COLLECTED`; attempting it on one already `REFUNDED` is refused with `ERR_PLEDGE_INVALID_STATE`. Money that has already been committed to production cannot be clawed back: once the project's `design_status` has reached `ORDERED`, `INSTALLED` or `AUDITED`, a refund is refused with `ERR_FUNDS_ALREADY_COMMITTED`. A successful refund sets the pledge's `status` to `REFUNDED`, and **only a refund of a pledge that was actually `COLLECTED` recomputes** `funds_collected_cents` and the four buckets from scratch. Because the recompute is total rather than incremental, refunding a collected pledge restores the buckets to exactly their pre-collection values — the buckets drain in reverse fill order purely as a consequence of the recompute, with no drift. Refunding a pledge that was still merely `PLEDGED` runs no recompute whatsoever: the project row is not written, `funds_collected_cents` and all four buckets keep the exact values they already held — even where a quote issued since the last recompute has changed the targets and the stored buckets are therefore stale against it — and only the pledge's own `version` is incremented. Refunding a `COLLECTED` pledge, by contrast, recomputes the whole waterfall and increments both the pledge's and the project's `version` by one. `REFUNDED` is terminal.

### 3.7. Compliance Certification, Ordering, and the Production Floor

Compliance certification is the checkpoint between a design the community likes and a design the business is willing to build. Only a `ComplianceOfficer` may perform it, and the officer must not be the project's own consultant: the acting `X-User-ID` is compared against the project's stored `consultant_user_id`, and a match is refused with `ERR_SEGREGATION_OF_DUTIES`. The project must be in `design_status` `DESIGN_APPROVED`; from anywhere else the attempt is refused with `ERR_PROJECT_INVALID_STATE`. Four substantive gates then run, in the order written here. The project's **most recently created** rendering still in `ISSUED` status — ordering the candidates by `created_at` ascending, breaking a tie between candidates that share a `created_at` instant by the order in which the server inserted them, exactly the total ordering §2.3 lays down, and taking the last — must have a `pinned_standard_id` whose edition is *still* `ACTIVE`; if a supersession has moved on since the rendering was drawn, certification is refused with `ERR_STANDARD_NOT_ACTIVE`, which is the mechanism that catches the `DESIGN_APPROVED` project hop three deliberately spared. A project holding **no** `ISSUED` rendering at all fails this very gate with the same `ERR_STANDARD_NOT_ACTIVE`, there being no live pin to check. Every `ComponentPlacement` of the project must be in `VALIDATED` status; one left in `DRAFT`, or demoted to `NEEDS_RECERTIFICATION`, is refused with `ERR_PLACEMENTS_NOT_VALIDATED`. Every play area's specified `surfacing_depth_cm` must be greater than or equal to its `required_surfacing_depth_cm`, or the attempt is refused with `ERR_SURFACING_DEPTH_INSUFFICIENT`. And the accessible-route provision is checked once more: with either the project's `accessible_route_required` or the `ACTIVE` edition's `requires_accessible_route` true, each play area must hold at least one placement in `DRAFT` or `VALIDATED` whose model is `accessible_transfer_ready`, or the attempt is refused with `ERR_ACCESSIBLE_ROUTE_MISSING` — the same test §3.4 and §3.5 apply, though the all-placements-validated gate just above has already forced every placement of the project to `VALIDATED` by the time it runs here.

A successful certification advances both project dimensions at once: `design_status` moves `DESIGN_APPROVED → CERTIFIED` and `compliance_status` moves to `COMPLIANT`, and the project's `version` is incremented by one. The `compliance_status` axis is entered from either `NOT_ASSESSED` or `RETROFIT_REQUIRED`, so a project whose compliance posture was spoiled by a supersession and then repaired is certifiable again. For completeness, that axis has five moves in total and only the first is client-driven: `NOT_ASSESSED → COMPLIANT` on certification; `COMPLIANT → RETROFIT_REQUIRED` when hop three of a supersession demotes at least one of the project's placements; `RETROFIT_REQUIRED → COMPLIANT` when a retrofit clears the project's last `NEEDS_RECERTIFICATION` placement; `COMPLIANT → NON_COMPLIANT` when a post-installation audit fails; and `NON_COMPLIANT → COMPLIANT` when a subsequent post-installation audit passes.

Raising the manufacturing order is the consultant's final design act. The request names a single `quote_id`, and the owning project is resolved from that quote's own `project_id` rather than named by the caller, so there is no quote-to-project agreement check here to fail. Four gates then run, in the order written. The project must be in `CERTIFIED` status, or the request is refused with `ERR_PROJECT_INVALID_STATE`; the named quote must be in `ACCEPTED` status and have `variant` `FIRM`, or the request is refused with `ERR_QUOTE_NOT_ACCEPTED`; every `ComponentPlacement` of that project — the whole set, not merely the subset the quote priced — must still be `VALIDATED`, with any demotion refused as `ERR_PLACEMENTS_NOT_VALIDATED`; and the money must actually be in hand — the project's `funds_collected_cents` must be greater than or equal to the quote's `total_cents`, and a shortfall is refused with `ERR_FUNDING_SHORTFALL`, the one HTTP 402 in this API. On success a `ManufacturingOrder` is created with HTTP 201 in `production_status` `CREATED`, `kitting_status` `PENDING` and `bagging_status` `PENDING`, with `kit_line_count`, `hardware_bag_total` and `instruction_package_revision` all at 0. The project's `design_status` becomes `ORDERED`, and every play area of the project is driven `ZONED → LOCKED`, after which placements can no longer be created, validated or removed there. The project's `version` and each locked area's `version` are incremented by one.

The plant floor runs on three parallel state dimensions of the same order row, and `ManufacturerAdmin` drives all of them. `production_status` is the primary axis and walks `CREATED`, `IN_PRODUCTION`, `READY_TO_SHIP`, `SHIPPED` and `CANCELLED`, of which `SHIPPED` and `CANCELLED` are terminal. Starting production moves the order `CREATED → IN_PRODUCTION` and additionally requires that the backing quote's project is still in `design_status` `ORDERED`; firing it from any other `production_status` is refused with `ERR_ORDER_INVALID_STATE`. The order's own axis is tested first and the project's second, so an order that has already left `CREATED` reports `ERR_ORDER_INVALID_STATE` even when the backing project has also left `ORDERED`. **That transition is the fork**: only once the order is `IN_PRODUCTION` do the two prep dimensions become writable, and advancing either of them while `production_status` is anything else is refused with `ERR_ORDER_NOT_IN_PRODUCTION`. That fork gate is evaluated **ahead of** the requested prep dimension's own transition validity, so an order that is not `IN_PRODUCTION` reports `ERR_ORDER_NOT_IN_PRODUCTION` even when the prep move asked for would itself have been inadmissible — which is also why, once the join below has carried the order to `READY_TO_SHIP`, a repeated prep advance reports `ERR_ORDER_NOT_IN_PRODUCTION` rather than `ERR_ORDER_INVALID_STATE`.

The two prep dimensions are genuinely independent — either may be advanced first, in any interleaving, and advancing one never mutates the other. Kitting is driven by supplying a `kitting_status` value and walks `PENDING → IN_PROGRESS → DONE`, with a fast path straight from `PENDING → DONE` for an order where no partial kitting was ever recorded. Reaching `DONE` writes exactly one derived field and no other: `kit_line_count` becomes the count of distinct placement lines the backing quote priced — that is, the number of placements under the ordered quote's project that read `VALIDATED` at the moment the branch reaches `DONE`, one per placement row however large its `quantity`. Hardware bagging is driven by supplying a `bagging_status` value over the same three states, with the same fast path, and reaching `DONE` writes exactly one derived field and no other: `hardware_bag_total` becomes the sum, over every `VALIDATED` placement under the ordered quote's project taken in `created_at` ascending order, of that placement's model's `hardware_bag_count` multiplied by the placement's `quantity`. Both counts read that `VALIDATED` set **live at the moment the branch reaches `DONE`**, from the project itself, rather than replaying the quote's own frozen `line_count` or its frozen line amounts. At the instant the order was raised the two coincided, since order creation demands that every placement of the project be `VALIDATED`; they can nevertheless come apart afterwards, because an `ORDERED` project is still within reach of the supersession cascade of §3.1 — a demotion of one of its placements to `NEEDS_RECERTIFICATION` drops that line out of both counts, and a subsequent retrofit that restores the placement under a superseding model brings it back with the *new* model's `hardware_bag_count`. Whichever set the branch finds at that moment is the set it counts, and neither count is ever recomputed again. Whole bags only; nothing is rounded. The two branches thus touch disjoint fields — kitting never writes `hardware_bag_total`, bagging never writes `kit_line_count` — and each advance increments the order's `version` by one.

**The join** is a system transition rather than a client call: the moment the second of `kitting_status` and `bagging_status` reaches `DONE`, and only then, the order's `production_status` moves `IN_PRODUCTION → READY_TO_SHIP` and `instruction_package_revision` is set to the backing rendering's `round_number`. That field is written nowhere else — not on order creation, not by either prep branch on its own — so an order that ships against the third rendering of a much-revised design carries revision 3 in its installation instruction package. Whichever branch happens to complete second carries out the join inside the same request, so a caller sees `production_status` already `READY_TO_SHIP` in that response. **The join rides on that same single increment** rather than adding one of its own: the second branch writes its own prep dimension, its own derived count, `production_status` and `instruction_package_revision` and still bumps the order's `version` by exactly one, so walking an `IN_PRODUCTION` order to `READY_TO_SHIP` through two prep advances costs exactly two increments, never three. Shipping then moves the order `READY_TO_SHIP → SHIPPED`, dispatching the kit together with its instruction package, and increments `version` by one; that single status test is its only precondition — no installation job need exist, the two prep dimensions are not re-examined, and neither the backing project's `design_status` nor its compliance posture is consulted. Order listings may be filtered by `quote_id`, `production_status`, `kitting_status` and `bagging_status`, and a single order's representation exposes both prep dimensions alongside `kit_line_count`, `hardware_bag_total` and `instruction_package_revision`.

### 3.8. The Installer Network, Installation, Inspection and the Post-Installation Audit

Admission to the certified installer network is a `ManufacturerAdmin` act. The company's `company_name` is 1 to 120 characters and must be globally unique — a repeat of a name already in the network is refused with `ERR_INVALID_REQUEST` (HTTP 422), matched exactly and case-sensitively, and tested only after every declared field of the body has passed its own type and range validation. Its `certification_level` is one of `APPRENTICE`, `CERTIFIED` or `MASTER`. Its `certified_categories` array names between 1 and 5 distinct component categories drawn from `POST`, `DECK`, `PLASTIC_SLIDE`, `METAL_CLIMBER` and `HARDWARE_KIT` — the categories the company is qualified to erect. Its `crew_capacity_per_day` is the maximum number of crew members it can field on any single calendar day, between 1 and 200 inclusive. Its `certification_expires_on` is the last `YYYY-MM-DD` date on which its certification remains valid, and its `region_code` is exactly two uppercase letters. A newly admitted installer is `ACTIVE` with `committed_crew_days` at 0 and `open_audit_failures` at 0, and is returned with HTTP 201. Installer listings may be filtered by `status`, `region_code` and `certification_level`, and a single installer's representation exposes both `committed_crew_days` and `open_audit_failures`.

**The crew-day ledger** is derived, never asserted. Each job contributes `booked_crew_days`, which is its `crew_size` multiplied by the inclusive day count of its booking window — the number of calendar days from `scheduled_start_date` to `scheduled_end_date` counting both ends, so a window whose two dates are equal counts as one day. An installer's `committed_crew_days` is the sum of `booked_crew_days` over every job booked with that installer whose `status` is **not** one of `AUDIT_PASSED`, `AUDIT_FAILED` or `CANCELLED`; a finished or cancelled job no longer occupies the calendar. That total is recomputed from scratch whenever a job is created, rescheduled, cancelled or started, whenever an inspection outcome changes a job's status, and on any change to the installer's own `status`. Because it is a full recompute, cancelling a job restores `committed_crew_days` to exactly the value it held before that job was created.

Booking a job is a `DesignConsultant` act. The request names the `order_id` whose kit is being installed and the `installer_id` doing the work, and sets `scheduled_start_date`, `scheduled_end_date` — which must not be earlier than the start date — and `crew_size`, an integer of at least 1 committed for every day of the window. An order may carry several phased jobs. The two body references are resolved for existence in the fixed order `order_id` before `installer_id`, so a request in which both are nonsense reports `ERR_ORDER_NOT_FOUND`. The order's own `production_status` is not gated at all: a job may be booked against an order still sitting in `CREATED`, and nothing here consults the order's project either. Four admission checks then run against the installer's **other** jobs whose status is not one of the three excluded ones, in the order written, which is the order §2.10 item 13 lays down. First, the installer must be in `ACTIVE` status; booking a `SUSPENDED` or `REVOKED` company is refused with `ERR_INSTALLER_NOT_ACTIVE`. Second, the requested closed date interval must not intersect any of those other bookings, **and** it must leave one fully clear calendar day of travel buffer between consecutive bookings: the new window's first day must fall on or after the earlier booking's last day plus one day plus the one-day buffer — so a booking that ends on the tenth of a month admits a next booking starting no earlier than the twelfth — and symmetrically, the new window's last day must sit at least that same clear day before any later booking's first day. Either an intersection or an insufficient gap is refused with `ERR_INSTALLER_BOOKING_CONFLICT` (HTTP 409). Third, `crew_size` must not exceed the installer's `crew_capacity_per_day`, or the booking is refused with `ERR_CREW_CAPACITY_EXCEEDED` (HTTP 422). Fourth and last, the installer's `certified_categories` must cover every component `category` appearing among the models of the placements the order's quote priced — read live off the project's current `VALIDATED` set exactly as §3.7's two prep counts are, and deduplicated — with a gap refused as `ERR_INSTALLER_CATEGORY_NOT_CERTIFIED` (HTTP 409). That places the category test *last of the four*, after both the calendar test and the capacity test, so a booking that both clashes with an existing window and reaches outside the company's certified categories reports `ERR_INSTALLER_BOOKING_CONFLICT`, and one that both overruns the daily crew capacity and misses a category reports `ERR_CREW_CAPACITY_EXCEEDED`. A successful booking creates the job with HTTP 201 in `SCHEDULED` status with `rework_cycles` at 0, `last_failed_inspection_kind` null and `install_inspector_user_id` null, writes its `booked_crew_days`, recomputes the installer's `committed_crew_days`, and increments the installer's `version` by one. The order row and the project row are not written at all, and neither of their `version` counters moves.

Rescheduling moves a `SCHEDULED` job to a new window. Besides the `expected_installer_version` of §2.8, it carries a new `scheduled_start_date` and `scheduled_end_date`, and optionally a new `crew_size`; when `crew_size` is omitted the existing crew size is retained. Firing it against a job in any other status is refused with `ERR_JOB_INVALID_STATE`. The same overlap, travel-buffer and crew-capacity checks re-run against the installer's other non-excluded jobs, with the same three error codes. On success the booking window and `booked_crew_days` are rewritten, `committed_crew_days` is recomputed, and both the job's and the installer's `version` are incremented by one — the installer's **unconditionally**, even when the recomputed `committed_crew_days` comes back identical because the new window is the same length and the crew size unchanged. Cancelling a job is the exact compensating action for creating one: it is a `DesignConsultant` act carrying no ownership check of its own, it is permitted while the job's `status` is `SCHEDULED` or `IN_PROGRESS`, it sets `status` to `CANCELLED`, recomputes `committed_crew_days` back to its pre-booking value, and increments both the job's and the installer's `version` by one, the installer's again unconditionally. Job listings may be filtered by `order_id`, `installer_id` and `status`.

Membership status is its own axis with three values, `ACTIVE`, `SUSPENDED` and `REVOKED`, and the `ManufacturerAdmin` drives it by supplying a `status` value. `REVOKED` is terminal to every client-driven status call — no `status` value a caller can supply moves an installer out of it — but it is not absolutely terminal: the audit-failure cascade described below writes a `REVOKED` installer back down to `SUSPENDED`, and that cascade is the single exception. **The two kinds of suspension differ, and the difference is deliberate.** An *administrative* suspension moves the installer `ACTIVE → SUSPENDED` and does **not** cancel any existing booking; it only blocks the creation of new jobs and blocks a `SCHEDULED` job from being started. A *compliance* suspension, driven by the audit-failure cascade described below, moves the installer to `SUSPENDED` and **does** cancel that installer's other `SCHEDULED` and `IN_PROGRESS` jobs. Reinstatement moves `SUSPENDED → ACTIVE` but only while `open_audit_failures` is 0; while any audit failure remains open the reinstatement is refused with `ERR_AUDIT_FAILURES_OPEN`. Reinstatement does not resurrect jobs a prior compliance suspension cancelled. Revocation moves the installer to `REVOKED` from either `ACTIVE` or `SUSPENDED`, cancels every job of that installer whose `status` is `SCHEDULED` or `IN_PROGRESS`, and then recomputes `committed_crew_days`; the installer's `version` and each cancelled job's `version` are each incremented by one. That recomputation does not necessarily zero the ledger, and neither does a compliance suspension: a job already past `IN_PROGRESS` — awaiting inspection, awaiting audit, failed, or in rework — is not cancellable by either of them and goes on occupying its `booked_crew_days` until an audit outcome or a cancellation takes it out. The ledger reaches 0 only when every one of the installer's jobs has landed in `AUDIT_PASSED`, `AUDIT_FAILED` or `CANCELLED`. A status change that no transition declares — attempting to move a `REVOKED` installer anywhere at all, or restating the installer's current value, such as suspending a company that is already `SUSPENDED` — is refused with `ERR_INSTALLER_INVALID_STATE`, and that transition test precedes the open-audit-failures gate, so re-reinstating an already-`ACTIVE` installer reports `ERR_INSTALLER_INVALID_STATE` rather than `ERR_AUDIT_FAILURES_OPEN`.

On site, the `InstallerOperator` drives its own job and nobody else's; every one of the three operator-driven job triggers compares the acting `X-User-ID` against the job's `installer_id` and refuses a mismatch with `ERR_NOT_JOB_OWNER`. Starting the job moves it `SCHEDULED → IN_PROGRESS` under three further conditions: the installer's own `status` must be `ACTIVE`, or the start is refused with `ERR_INSTALLER_NOT_ACTIVE`; the installer's `certification_expires_on` must be on or after the logical clock's date, or the start is refused with `ERR_INSTALLER_CERTIFICATION_EXPIRED`; and the logical clock's date must be on or after the job's `scheduled_start_date`, since a crew cannot start early, with a premature attempt refused as `ERR_JOB_NOT_YET_STARTABLE`. Those three conditions are tested in the order just written, and all of them after the job's own `SCHEDULED` gate. A start bumps the job's `version` by one and re-derives the installer's `committed_crew_days`, but it does **not** bump the installer's `version`: `SCHEDULED` and `IN_PROGRESS` are both non-excluded statuses, so the ledger cannot move, and the installer row is left unwritten. Reporting the work finished moves the job `IN_PROGRESS → INSPECTION_PENDING`, increments the job's `version` by one, touches nothing else, and hands the job to the auditors.

Inspection records are filed by a `SafetyAuditor` and form an immutable append-only log per job. Each record states its `kind`, either `INSTALL_INSPECTION` or `POST_INSTALL_AUDIT`, and its `result`, either `PASS` or `FAIL`, along with three measurements: `deficiency_count`, the number of deficiencies noted, zero or more; `fall_height_measured_cm`, the highest designated play surface height actually measured on site, zero or more; and `surfacing_depth_measured_cm`, the shallowest protective surfacing depth actually measured on site, zero or more. The record's `job_id` comes from the request path, its `performed_by_user_id` is set from the acting `X-User-ID`, and its `sequence_number` is 1 for the job's first record and one greater than the highest existing sequence number thereafter. Records are returned with HTTP 201, and a job's log is listed in `sequence_number` order with optional filters on `kind` and `result`. Because these records are evidence rather than working state, they carry only `id` and `created_at` and are never updated. Of the three measurements, `surfacing_depth_measured_cm` is the one that gates: on an `INSTALL_INSPECTION` it must be greater than or equal to the largest `required_surfacing_depth_cm` across the project's play areas — the **maximum** over those areas, not the minimum and not the requirement of any one area — and a shallower measurement is refused with `ERR_SURFACING_DEPTH_INSUFFICIENT` before any record is written. The gate is indifferent to the `result` being filed: a `FAIL` record is refused for a too-shallow measurement exactly as a `PASS` record is, so an inspector cannot log the shortfall as evidence and must deepen the surfacing first. A `POST_INSTALL_AUDIT` is not gated on the measurement at all, whichever way it goes. `deficiency_count` and `fall_height_measured_cm` are recorded for the audit trail and gate nothing.

An `INSTALL_INSPECTION` may only be filed while the job is in `INSPECTION_PENDING`, and a `POST_INSTALL_AUDIT` only while it is in `AUDIT_PENDING`; filing in the wrong phase is refused with `ERR_JOB_INVALID_STATE`. Filing a post-installation audit additionally requires that the acting `X-User-ID` differ from the job's recorded `install_inspector_user_id`, with a match refused as `ERR_SEGREGATION_OF_DUTIES`. That separation test is evaluated **before** the phase gate — the barred auditor is turned away with `ERR_SEGREGATION_OF_DUTIES` even when the job is in the wrong phase for an audit — but, as the exception in §2.10 item 3 records, **after** the body has been read and shape-checked, since `kind` is what reveals the request to be an audit in the first place. The four outcomes have sharply different consequences, and each must be implemented in full.

An **installation inspection that passes** creates the record, sets the job's `install_inspector_user_id` to the acting `X-User-ID` if it is still null, moves the job `INSPECTION_PENDING → AUDIT_PENDING`, and reaches across into the design: the owning project's `design_status` moves `ORDERED → INSTALLED` and its `installed_on` is set to the logical clock's current date in `YYYY-MM-DD` form — the date from which every warranty term is later measured. Both the job's and the project's `version` are incremented by one. That reach into the design is **guarded on the project still reading `ORDERED`**, and the guard is load-bearing because an order may carry several phased jobs: the second such job's passing installation inspection finds the project already `INSTALLED`, leaves both its `design_status` and its original `installed_on` exactly as the first job set them, does not write the project row at all and therefore bumps only the job's `version`. The installation date of a phased build is thus the date the *first* job passed its inspection.

An **installation inspection that fails** creates the record, likewise sets `install_inspector_user_id` if it is still null — so the auditor who first touched the job is barred from the eventual audit whichever way the inspection went — moves the job `INSPECTION_PENDING → INSPECTION_FAILED`, and records `last_failed_inspection_kind` as `INSTALL_INSPECTION`. The job's `version` is incremented by one; the project is not touched.

A **post-installation audit that passes** creates the record, moves the job `AUDIT_PENDING → AUDIT_PASSED`, and advances the project on both axes at once: `design_status` becomes `AUDITED` and `compliance_status` becomes `COMPLIANT`. Unlike the installation-inspection branch above, this project write is **not** guarded on the project's current values — a second phased job's passing audit rewrites `AUDITED` and `COMPLIANT` over the values they already held and bumps the project's `version` again all the same. Because `AUDIT_PASSED` is one of the excluded statuses, the installer's `committed_crew_days` is recomputed — the job releases the calendar — and `open_audit_failures` is recomputed as well. The job's, the project's and the installer's `version` are each incremented by one. `AUDITED` is terminal for the project and `AUDIT_PASSED` terminal for the job.

A **post-installation audit that fails** fires a four-hop cascade. Hop one: the record is created and the job moves `AUDIT_PENDING → AUDIT_FAILED` with `last_failed_inspection_kind` set to `POST_INSTALL_AUDIT`. Hop two: because the job has failed its audit, the owning project's `compliance_status` becomes `NON_COMPLIANT` — note that its `design_status` is left alone, so a project can be `AUDITED`-bound yet non-compliant — and the project's `version` is bumped by this hop unconditionally, even when its `compliance_status` already read `NON_COMPLIANT` from an earlier failed audit on another job of the same order. Hop three: because that project is now non-compliant, the installer's `open_audit_failures` is incremented, and the suspension threshold is **one** — a single failed post-installation audit is enough — so the installer's `status` becomes `SUSPENDED` as a compliance suspension. This hop writes `SUSPENDED` unconditionally and consults no membership transition table: an installer already `SUSPENDED` simply stays there, and one that had been driven all the way to `REVOKED` while this job still sat in `AUDIT_PENDING` — revocation cancels only `SCHEDULED` and `IN_PROGRESS` jobs, so an awaiting-audit job survives it — is written back down to `SUSPENDED`. That cascade write is the single documented exception to `REVOKED` being terminal; no client-driven status call can leave it. Hop four: because the installer is now compliance-suspended, every *other* job of that installer whose `status` is `SCHEDULED` or `IN_PROGRESS` moves to `CANCELLED`, and `committed_crew_days` is then recomputed over what remains. Version counters are incremented by one on the job, the project, the installer and every cancelled sibling job. The installer's `open_audit_failures` is the count of its own jobs currently sitting in `AUDIT_FAILED`, which is what makes reinstatement contingent on those jobs being worked back out of that status.

The rework loop is how a failed job recovers, and it is driven by the `InstallerOperator` supplying an `action` of either `START` or `COMPLETE`. `START` is admissible while the job's `status` is `INSPECTION_FAILED` or `AUDIT_FAILED` and moves it to `REWORK_IN_PROGRESS`, but only while `rework_cycles` is strictly less than 2; at two completed cycles the loop is closed and a further attempt is refused with `ERR_REWORK_LIMIT_EXCEEDED`. `COMPLETE` is admissible only from `REWORK_IN_PROGRESS`, increments `rework_cycles` by one, and **returns the job to whichever check it failed**: when `last_failed_inspection_kind` is `INSTALL_INSPECTION` the job lands back in `INSPECTION_PENDING`, closing the cycle `INSPECTION_PENDING → INSPECTION_FAILED → REWORK_IN_PROGRESS → INSPECTION_PENDING`; when it is `POST_INSTALL_AUDIT` the same trigger lands the job in `AUDIT_PENDING` instead. Completing a rework does **not** clear `last_failed_inspection_kind`: the field keeps the value the last failure wrote until a later failure overwrites it, so a job that has been reworked back into `INSPECTION_PENDING` still reports `INSTALL_INSPECTION` there. Each rework transition increments the job's `version` by one and writes nothing outside the job row — neither the installer's ledger nor its `version` moves, both `INSPECTION_FAILED` and `REWORK_IN_PROGRESS` being non-excluded statuses.

### 3.9. Warranty, Replacement Parts, Compliance Retrofits and Cancellation

Warranty runs by component category, not by system, and a claim is filed by either a `ClientRepresentative` or a `ComplianceOfficer` once a playground is in the ground. The request names the `project_id` the failure occurred on, the `placement_id` that failed, the `quantity` of failed units claimed — at least 1, with no upper bound and no comparison against the failed placement's own `quantity` — and the `failure_date` on which the failure occurred. The two body references are resolved for existence in the fixed order `project_id` before `placement_id`, so a claim naming two nonexistent rows reports `ERR_PROJECT_NOT_FOUND`. Three referential and temporal gates then run, in the order written, and nothing else gates a claim: the project's `design_status` is never consulted, so a claim may be filed against a project that is merely `INSTALLED` as readily as against an `AUDITED` one. The named placement must belong to a play area of the named project, or the claim is refused with `ERR_WARRANTY_PLACEMENT_MISMATCH` (HTTP 422). The project must actually have been installed, meaning its `installed_on` is non-null; a claim against an uninstalled project is refused with `ERR_PROJECT_NOT_INSTALLED` (HTTP 422). And `failure_date` must fall on or after the project's `installed_on` and on or before the logical clock's current date, with anything outside that window refused as `ERR_INVALID_FAILURE_DATE` (HTTP 422).

At claim time the claim freezes its own copy of the commercial facts so that later catalogue edits cannot rewrite history. `component_model_id` is copied from the placement's current `component_model_id` and frozen; `claim_category` is copied from that model's `category` and is what selects the coverage variant. `elapsed_years` is the whole number of years between installation and failure: take the number of days from the project's `installed_on` to the claim's `failure_date`, divide by 365, and discard any fraction, rounding down.

**Coverage then follows one of two variants, selected purely by category.** For a `POST`, a `DECK` or a `METAL_CLIMBER` — structural steel and lumber, which depreciate continuously — the variant is `PRORATED`. `covered_pct` is 0 when `elapsed_years` has reached or passed the model's `warranty_years`; otherwise it is one hundred multiplied by the model's `warranty_years` less `elapsed_years`, divided by that same `warranty_years`, rounded half up to a whole percent. Coverage therefore declines by one warranty-term fraction per elapsed year: a ten-year model claimed in elapsed year 3 covers 70 percent. For a `PLASTIC_SLIDE` or a `HARDWARE_KIT` — rotomoulded plastics and fasteners — the variant is `STEP`. Take half the model's `warranty_years`, rounded **up** to a whole number of years. `covered_pct` is 100 when `elapsed_years` is at or below that halfway point; otherwise it is 50 while `elapsed_years` is still strictly less than `warranty_years`; otherwise it is 0. Coverage is thus a step function rather than a ramp, and on identical inputs the two variants genuinely diverge: the same ten-year term at elapsed year 3 pays 70 percent under `PRORATED` and 100 percent under `STEP`. The chosen variant is recorded on the claim in `coverage_variant`, whose value is either `PRORATED` or `STEP`.

`reimbursement_cents` is then the model's `unit_price_cents` multiplied by the claim's `quantity` multiplied by `covered_pct`, divided by one hundred, rounded half up to whole cents. All four of `elapsed_years`, `coverage_variant`, `covered_pct` and `reimbursement_cents` are computed once and frozen. A claim whose `covered_pct` computes to 0 is still created and returned with HTTP 201 in `SUBMITTED` status — the record of an out-of-warranty failure has value in its own right. Claim listings may be filtered by `project_id`, `placement_id`, `component_model_id` and `status`.

Deciding a claim belongs to the `ComplianceOfficer`, who supplies a `decision` of either `APPROVED` or `DENIED`. The claim must be in `SUBMITTED` status; deciding one already decided is refused with `ERR_CLAIM_INVALID_STATE`. Approval is refused when coverage has decayed away entirely — a `covered_pct` of 0 cannot be approved and yields `ERR_WARRANTY_EXPIRED` — whereas denial is always available regardless of coverage. Either decision sets `status` accordingly and increments the claim's `version` by one; `APPROVED` and `DENIED` are both terminal.

**Buying a replacement part and performing a compliance retrofit are the same operation**, available to a `ClientRepresentative` or a `DesignConsultant`, and it names a `replacement_model_id` and a `quantity` of at least 1, with no upper bound. Unlike the design operations of §3.3 this one is deliberately **not** gated on the owning project's editability or on the play area's lock, and it imposes no gate on the placement's own `status` either: a replacement part may be bought against a `LOCKED` area of an `ORDERED`, `INSTALLED` or `AUDITED` project, and against a placement in `DRAFT`, `VALIDATED` or `NEEDS_RECERTIFICATION`.

The eligibility gates run before any pricing, in this order. **First**, when and only when the placement being repaired is in `NEEDS_RECERTIFICATION`, the stricter compliance form runs: the replacement must itself be in `certification_status` `CERTIFIED`, or the request is refused with `ERR_MODEL_NOT_CERTIFIED`; then its `deck_height_cm` must not exceed the `ACTIVE` edition's ceiling for the owning area's band, or the request is refused with `ERR_FALL_HEIGHT_EXCEEDS_STANDARD`, that one test being skipped outright when no edition is `ACTIVE` since there is then no ceiling to read; then its `age_group` must still match the area's band, with a mismatch refused as `ERR_AGE_GROUP_MISMATCH` — the same fall-height-before-band precedence §3.3 and §2.10 item 12 lay down. **Second**, for every purchase alike, the logical clock's current year must be no later than the replacement model's `parts_support_until_year`, since the plant stops sourcing parts for a family after that year, and a late purchase is refused with `ERR_PARTS_NO_LONGER_AVAILABLE`. **Third**, the replacement must be either the placement's own current model or a model whose `supersedes_model_id` points at the placement's current model; anything else is refused with `ERR_RETROFIT_MODEL_MISMATCH` (HTTP 422) — and on a `NEEDS_RECERTIFICATION` placement only the superseding form will do, so naming the placement's own current model is refused with that same code.

Pricing the purchase has three steps. First the surcharge: when the replacement model's `lifecycle_status` is `LEGACY`, `retrofit_unit_price_cents` is the model's `unit_price_cents` plus eighteen percent of that `unit_price_cents` rounded half up to whole cents, and `legacy_surcharge_applied` is set true; otherwise `retrofit_unit_price_cents` is simply the model's `unit_price_cents` and `legacy_surcharge_applied` is false. Second the line: the line amount is `retrofit_unit_price_cents` multiplied by the requested `quantity`. Third the handling waiver, and its evaluation point is the subtle part — **the waiver is decided on the line amount, before handling is added, and never on the resulting total.** When the line amount is greater than or equal to 250000 cents, `retrofit_handling_cents` is 0; otherwise it is a flat 3500 cents. A line of exactly 250000 cents therefore waives handling, while a line of 247000 cents attracts the 3500-cent charge and totals 250500 cents — above the threshold, yet handling still applies, because the decision was made on 247000. `retrofit_total_cents` is the line amount plus `retrofit_handling_cents`. The purchase also records `retrofit_model_id` as the replacement model and `retrofit_quantity` as the requested quantity.

Where the placement was in `NEEDS_RECERTIFICATION` and the replacement supersedes its model, the placement's `component_model_id` is rewritten to the replacement and its `status` moves `NEEDS_RECERTIFICATION → VALIDATED`. The owning area's `critical_fall_height_cm` and `required_surfacing_depth_cm` are recomputed in every case, since the model behind the placement may have changed height. And there is a cascade upward: once the owning project holds no remaining placement in `NEEDS_RECERTIFICATION`, its `compliance_status` returns to `COMPLIANT` — but only if it was reading `RETROFIT_REQUIRED` at the time; a project already `COMPLIANT`, still `NOT_ASSESSED`, or gone `NON_COMPLIANT` after a failed audit keeps whatever value it holds. The placement's, the area's and the project's `version` are each incremented by one **unconditionally**, on every successful purchase: the area's counter moves even when neither derived number changed, and the project's counter moves even when its `compliance_status` did not.

Cancellation is the project-level compensating action, driven by the `DesignConsultant`. It is available from any of `DRAFT`, `CONSULTATION`, `RENDERED`, `COMMUNITY_REVIEW`, `REVISION_REQUESTED`, `DESIGN_APPROVED`, `CERTIFIED` and `ORDERED`; a project already `INSTALLED`, `AUDITED` or `CANCELLED` cannot be cancelled and the attempt is refused with `ERR_PROJECT_NOT_CANCELLABLE`. On success the project's `design_status` becomes `CANCELLED`, and the consequences fan out inside the same request. Hop one: the project's `ManufacturingOrder`, if it has one and its `production_status` is `CREATED` or `IN_PRODUCTION`, moves to `CANCELLED`. Hop two: because that order is cancelled, every `InstallationJob` of the order whose `status` is `SCHEDULED` or `IN_PROGRESS` moves to `CANCELLED`. Hop three: because those jobs are cancelled, each affected installer has its `committed_crew_days` recomputed. Alongside the hops, every `FundraisingPledge` of the project whose `status` is `PLEDGED` or `COLLECTED` moves to `REFUNDED`, after which `funds_collected_cents` and all four allocation buckets are recomputed and therefore all become 0; and every `Quote` of the project still in `ISSUED` moves to `EXPIRED`. Version counters are incremented by one on the project and on every order, job, installer, pledge and quote the cancellation actually mutated. `CANCELLED` is terminal on the project's design axis.

## 4. Endpoint Definitions

Every path below is mounted under the `/playground` prefix exactly as written. Creation operations answer HTTP 201; every other successful operation answers HTTP 200, with the single exception of placement removal, which answers HTTP 204 with a completely empty body — no envelope at all, and therefore no `meta`, no `response_type` and no `data`. A request to a path this table does not define answers HTTP 404, and a request to a defined path with an undefined method answers HTTP 405; both carry the standard error envelope with `error_id` `ERR_INVALID_REQUEST` (§2.2). List operations return an array in `data` together with the pagination `meta` fields described in section 2.3, and single-resource operations return the resource object. Operations that mutate a resource return the updated resource. The Authorized Role(s) column is exhaustive: a caller presenting a valid but unlisted role is refused with `ERR_FORBIDDEN_ROLE`, and role membership is checked before any payload validation, existence check or state check.
