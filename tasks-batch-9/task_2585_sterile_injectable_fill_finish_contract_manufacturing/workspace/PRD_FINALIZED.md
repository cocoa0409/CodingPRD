# Sterile Fill-Finish CMO API — Product Requirements Document

## 1. Introduction

A sterile injectable contract manufacturing organisation sells one thing above all others: the defensible certainty that a vial or a pre-filled syringe leaving its filling suite was made under aseptic conditions that can be reconstructed, line by line, years later, in front of an inspector. Today that certainty lives in binders, spreadsheets and the institutional memory of a handful of people. When a media fill turns turbid, somebody has to remember which batches were in the suite, which operators had been qualified on the strength of that simulation, and which component reservations must be handed back to inventory. When a Qualified Person signs a release, somebody has to be sure that the person who reviewed the batch record was not the same person now certifying it. Those chains of consequence are exactly what this system exists to make mechanical.

This document specifies the API for that system. It covers the whole commercial and GMP arc of a contract fill-finish programme: taking in a sponsor's molecule and driving technology transfer and analytical method transfer to completion; qualifying a shared filling suite through aseptic process simulation and cleaning validation; qualifying, lapsing and revoking the operators who gown into that suite; receiving and sterilisation-validating primary packaging components and reserving them against specific batches; scheduling batches into shared suites with directional changeover buffers and a hard occupancy ceiling; running the fill and capturing in-process controls for fill weight, container closure integrity and visual inspection; monitoring the environment against grade-specific alert and action limits and investigating every excursion; raising, classifying and closing deviations through a CAPA loop; reviewing the executed batch record; certifying or rejecting the batch through a segregated Qualified Person; and hosting sponsor audits and internal inspection-readiness rehearsals.

Two design commitments run through everything that follows. The first is that derived state is genuinely derived: a suite's operational posture, a project's committed unit ledger, a lot's available quantity and a batch's releasable-unit figures are all recomputed from their inputs rather than carried forward by hand, and every cascade that a single write triggers is specified here in full. The second is that time is explicit. The server keeps a **logical clock** that every expiry, validity window and timestamp rule reads, and that clock only moves when an operator moves it. Nothing in this system consults real wall-clock time.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint — including the read-only computed endpoints and the clock endpoint — must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role that user is acting under. If either header is absent or present but empty, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). If `X-User-Role` carries a value that is not one of the six roles below, the request is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401). Only once the role has resolved does the server test it against the target endpoint's authorised role list; a role that is not on that list yields `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are exactly `ProgramManager`, `ProductionSupervisor`, `MicrobiologyAnalyst`, `QaReviewer`, `QualifiedPerson` and `ClientRepresentative`.

- A `ProgramManager` is the CMO-side technical project owner. They intake client projects, drive technology transfer, register filling suites and receive component lots, schedule batches into shared suites, cancel batches, and host audit engagements.
- A `ProductionSupervisor` is the filling-suite production lead. They drive a batch through setup, aseptic fill and fill completion, and they record in-process controls.
- A `MicrobiologyAnalyst` owns sterility assurance. They schedule, execute and read out media fills, qualify and revoke operators, record cleaning-validation and component sterilisation-validation verdicts, and record and investigate environmental monitoring excursions.
- A `QaReviewer` owns quality assurance. They adjudicate investigated media fills, raise and classify deviations, decide CAPAs, review the executed batch record, and release a project from hold. A `QaReviewer` explicitly cannot certify a batch.
- A `QualifiedPerson` holds the sole authority to certify, reject or quarantine a finished batch. They read everything the release rests on but perform no production or QA step, which is what makes the release signature genuinely segregated.
- A `ClientRepresentative` is the sponsor-side contact for exactly one client project. They may request audit engagements and read only their own project's records.

When `X-User-Role` is `ProgramManager`, `ProductionSupervisor`, `MicrobiologyAnalyst`, `QaReviewer` or `QualifiedPerson`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it — it stamps `opened_by_user_id` on a `Deviation`, `reviewer_user_id` on a `BatchRecordReview` and `qp_user_id` on a `QpReleaseDecision` — but it never compares it to any entity's `id`.

When `X-User-Role` is `ClientRepresentative`, `X-User-ID` is the `id` of the acting `ClientProject`; ownership checks compare the owning project of the addressed resource to `X-User-ID`. For `GET /client-projects/{id}`, `GET /client-projects/{id}/readiness-assessment` and `GET /client-projects/{id}/audit-engagements` the comparison is against the path `id` directly. For `POST /audit-engagements` it is against the `client_project_id` in the body. For `GET /batch-orders/{id}` and `GET /batch-orders/{id}/unit-accounting` it is against the addressed batch's `client_project_id`. A mismatch on any of those six operations is rejected with `ERR_PROJECT_ACCESS_DENIED` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` is an integer between 1 and 100 inclusive and defaults to 10 when omitted. `offset` is an integer of at least 0 and defaults to 0 when omitted. A `limit` below 1 or above 100, or a negative `offset`, or a non-integer value for either, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

List responses set `response_type` to `"array"` and populate four pagination fields in `meta`: `limit` and `offset` echo the effective values, `total_count` reports the number of rows matching the filters before the window is applied, and `has_more` is true when rows remain beyond the current window. Unless a specific endpoint says otherwise, every list is ordered by `created_at` ascending — this includes the two append-only sub-resource reads, the audit-engagement list under a project and the Qualified-Person decision list under a batch.

Filters on a list are combined with logical conjunction, and any filter that is omitted places no restriction. The available filters are: `status` and `primary_suite_id` on the client-project list; `posture` and `grade` on the filling-suite list; `suite_id` and `status` on the media-fill list; `suite_id`, `media_fill_id`, `status` and `operator_name` on the personnel-qualification list; `client_project_id`, `component_type` and `status` on the component-lot list; `client_project_id`, `suite_id`, `lead_operator_qualification_id`, `production_status` and `quality_status` on the batch-order list; `batch_order_id`, `component_lot_id` and `status` on the component-reservation list; `batch_order_id`, `check_type` and `result` on the in-process-check list; `suite_id`, `batch_order_id`, `classification`, `investigation_status` and `sample_type` on the environmental-monitoring list; `batch_order_id`, `em_sample_id`, `status` and `classification` on the deviation list; `batch_order_id` and `status` on the batch-record-review list; and `status` on the per-project audit-engagement list.

### 2.4. Record Identity, Audit Stamps and the Logical Clock

Every persisted resource carries an `id` that is a server-minted UUID with no type prefix; clients never supply it. Every resource also carries a `created_at` timestamp, formatted as an ISO 8601 UTC instant with exactly three fractional digits.

Fourteen of the fifteen resource types additionally carry an `updated_at` timestamp in the same format and an integer `version`. `version` begins at 1 when the row is created and increases by exactly 1 on every mutation of that row, and `updated_at` is refreshed to the same instant. The single exception is the Qualified-Person release decision: it is an append-only evidential record that is never modified after it is written, so it carries only `id` and `created_at` — it has no `updated_at` field and no `version` field at all.

Timestamps written by the server, and every expiry or validity comparison in this specification, read the **logical clock** rather than real time. The clock's startup value is exactly `2026-08-01T00:00:00Z`, and it must never fall back to wall-clock time, not even before the first clock call of a server's life. An operator moves the clock by supplying a `to_iso8601` instant to the clock endpoint, which answers with the resulting `current_utc` together with `lapsed_qualification_count` and `expired_component_lot_count` — the number of operator qualifications and component lots the move retired. All five CMO-side roles may move the clock; a `ClientRepresentative` may not.

Moving the clock is not a passive act. Every operator qualification whose `status` is `QUALIFIED` and whose `expires_on` is at or before the new clock value becomes `LAPSED`, processed in ascending `expires_on` order with ties broken by ascending `created_at`. Every component lot whose `status` is `RELEASED` or `EXHAUSTED` and whose `sterilization_expiry` is at or before the new clock value becomes `EXPIRED` with its `quantity_available` set to 0, processed in ascending `sterilization_expiry` order with ties broken by ascending `created_at`; reservations already held against such a lot are deliberately left untouched so that the component-unit ledger still balances against `quantity_received`. Every filling suite touched by a lapse then has its `qualified_operator_count` and its `posture` recomputed.

### 2.5. Suite Posture: The Derived Aseptic Gate

Every filling suite exposes a computed `posture` that is the single gate every filling operation consults. It is one of `OPEN`, `RESTRICTED` or `FROZEN`, and it is recomputed after every mutation that touches the suite's `aseptic_qualification_status` or `cleaning_validation_status`, any environmental sample's `classification` or `investigation_status` in that suite, any operator qualification in that suite, or the logical clock. A brand-new suite computes to `RESTRICTED`.

The three branches are tested in order and the first match wins, so a suite that qualifies for more than one branch always takes the most severe. First: if `aseptic_qualification_status` is `INVALIDATED`, or `cleaning_validation_status` is `FAILED`, the posture is `FROZEN`. Otherwise, if any one of four conditions holds — `open_action_excursion_count` is at least 1, or `media_fill_valid_until` is null, or `media_fill_valid_until` is earlier than the current logical clock, or `qualified_operator_count` is below two — the posture is `RESTRICTED`. Otherwise the posture is `OPEN`.

Two of those inputs are themselves derived counts. `open_action_excursion_count` is the number of environmental monitoring samples in this suite whose `classification` is `ACTION` and whose `investigation_status` is either `OPEN` or `INVESTIGATING`; samples classified `ALERT` or `WITHIN_LIMIT` never restrict a suite, and neither does an `ACTION` sample whose investigation has reached `CLOSED`. `qualified_operator_count` is the number of operator qualifications in this suite whose `status` is `QUALIFIED` and whose `expires_on` is at or after the current logical clock. The roster threshold is two effective operators, and it is a strict shortfall test: a count of one restricts the suite, a count of exactly two does not.

### 2.6. Cascade Discipline and Compensating Ledgers

Several fields in this system are ledgers: they are maintained as running totals but they must always equal the aggregate they claim to represent, and every action that adds to one has an inverse that removes exactly what was added. A project's `committed_demand_units` is the sum of `component_demand_units` over that project's batches whose `production_status` is `SCHEDULED`, `SETUP`, `FILLING` or `FILLED`. A suite's `committed_minutes` is the corresponding occupancy total described in section 3.5. A project's `open_deviation_risk_total` is the sum of `risk_score` over the deviations written against that project's batches whose `status` is not `CLOSED`. A project's `last_client_audit_finding_count` is the `finding_count` of the most recently hosted audit engagement for that project, ranked by `hosted_at` descending with ties broken by `created_at` descending, and 0 when no engagement has been hosted. A lot's `quantity_available` is the portion of `quantity_received` not currently held by a `RESERVED` or `CONSUMED` reservation.

Cascades in this system are transitive: a hop is caused by the mutation the previous hop performed, not by the originating call, and every intermediate row is written. The deepest chain runs five levels. A failed aseptic process simulation invalidates its suite's aseptic qualification; the invalidation drives the suite's posture to `FROZEN`; the freeze suspends and quarantines that suite's live batches; the suspension releases those batches' held component reservations back to their lots; and the restored availability un-exhausts any lot that had been fully drawn down. Whenever a cascade mutates a row, that row's own `version` increases by 1 and its `updated_at` is refreshed, exactly as if it had been written directly.

### 2.7. Optimistic Concurrency on Shared Parents

Two write operations commit against a parent whose derived state the client must have observed first, and both are protected by an optimistic concurrency token. In both cases the product semantics legitimately allow a second write against the same parent, so no state precondition excludes it — the token exists purely to reject a write computed from a stale read.

A request to `POST /batch-orders` must carry `expected_suite_version` as a required, non-optional field holding the client's last observed `version` of the target `FillingSuite`. If it does not equal that suite's current `version`, the create is rejected with `ERR_STALE_SUITE_VERSION` (HTTP 412). The reason is concrete: scheduling on an out-of-date view of the suite's `committed_minutes`, `posture` and `last_cleaned_molecule` would silently mis-derive `changeover_minutes_applied`.

A request to `POST /component-reservations` must carry `expected_component_lot_version` as a required, non-optional field holding the client's last observed `version` of the target `ComponentLot`. If it does not equal that lot's current `version`, the create is rejected with `ERR_STALE_COMPONENT_LOT_VERSION` (HTTP 412), because the client's `quantity_reserved` was computed from a `quantity_available` that has since moved.

No other endpoint in this specification accepts an expected-version field, and none may be required to.

### 2.8. Segregation of Duties

Two decisions in this system must be signed by somebody other than the person who prepared them, and the rule is enforced on `X-User-ID` rather than on role alone. The `X-User-ID` signing a Qualified-Person release must differ from the `reviewer_user_id` recorded on that batch's batch record review. The `X-User-ID` deciding a CAPA must differ from the `opened_by_user_id` recorded on that deviation. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Note that the second rule bites even though both actions are performed by the same role: two distinct `QaReviewer` users are required to open a deviation and to decide its CAPA.

### 2.9. Numeric Precision and Pinned Evaluation Order

Nearly every quantity in this domain is an integer: colony-forming units, component units, occupancy minutes, releasable containers, risk points and money in cents. Where a computation produces a fractional intermediate, the specification names both the rounding operation and the point in the computation at which it is applied, and implementations must apply it there and nowhere else. Two rounding operations are used. **Round half up** means round to the stated number of decimal places (or to a whole number where no decimal places are stated) with a tie at exactly one half going away from zero. **Ceiling** means round up to the next whole number, with a value that is already whole left unchanged.

The places where the ordering matters are these. The environmental excursion risk index rounds its scaled core term to a whole number half-up *before* the sample-type and batch-exposure surcharges are added, and those surcharges are never themselves rounded. A deviation's risk score rounds the escalation-multiplied base half-up to a whole number *before* the environmental-linkage bonus is added, and the ceiling on the score is applied last of all. The Qualified-Person release fee applies round-half-up independently at its surcharge step and again at its discount step, never once across a composed expression. The component demand figure applies its pack-size ceiling once per component line and only then sums the lines; summing the gross requirements first and applying a single ceiling to the total is wrong and yields a different integer. The provisional releasable-unit figure uses a ceiling on its expected-reject term, never round-half-up. The operator component of a project readiness score is rounded half-up to a whole number before it is added to the other three components. The only field in the system carried at more than whole-number precision is `max_absolute_deviation_pct`, which is held at four decimal places and rounded half-up to those four places *before* it is compared against any tolerance.

### 2.10. Request Evaluation Order

When a single request violates several rules, exactly one error is returned, and which one is fixed. The server evaluates rules in the following order and returns the first failure it finds. This ordering is part of the contract: it is what lets a caller trust that a 404 means "the thing you named does not exist" rather than "the thing you named exists but you are not allowed to see it".

1. **Header presence** — `ERR_MISSING_AUTH_HEADERS`, on every endpoint.
2. **Role recognition** — `ERR_UNKNOWN_ROLE`, on every endpoint.
3. **Endpoint authorisation** — `ERR_ROLE_NOT_PERMITTED`, on every endpoint.
4. **Project ownership for a `ClientRepresentative`** — `ERR_PROJECT_ACCESS_DENIED`, on the six operations enumerated in section 2.1.
5. **Path existence** — the resource-specific 404 for each path segment, resolved left to right, on every endpoint that has a path `id`.
6. **Request shape** — `ERR_INVALID_REQUEST`, on every POST: a required field absent or null, a field of the wrong JSON type, an array field that is not an array, or a numeric field outside its declared range.
7. **Enum membership** — `ERR_INVALID_ENUM_VALUE`, on every POST carrying an enum-typed input and additionally on the two computed reads `GET /client-projects/{id}/readiness-assessment` and `GET /batch-orders/{id}/unit-accounting`.
8. **Pagination bounds** — `ERR_INVALID_PAGINATION`, on every list read.
9. **Body foreign-key existence** — the resource-specific 404, on `POST /client-projects`, `POST /media-fills`, `POST /personnel-qualifications`, `POST /batch-orders`, `POST /component-lots`, `POST /component-reservations`, `POST /in-process-checks`, `POST /em-samples`, `POST /deviations`, `POST /batch-record-reviews` and `POST /audit-engagements`.
10. **Optimistic concurrency** — `ERR_STALE_SUITE_VERSION` on `POST /batch-orders`, then `ERR_STALE_COMPONENT_LOT_VERSION` on `POST /component-reservations`.
11. **Batch record review closure at release** — `ERR_BR_REVIEW_NOT_CLOSED` on `POST /batch-orders/{id}/qp-release`. This check is deliberately ordered ahead of the quality-axis state check that follows it: a Qualified Person who signs against a batch whose record has never been reviewed and closed must be told precisely that, rather than being told only that the state machine disagrees. The consequence is symmetric and intended — a batch whose review *is* closed and clean but whose `quality_status` has already reached a terminal disposition still fails at the next rung with `ERR_BATCH_QUALITY_STATE_INVALID`.
12. **State-machine guards**, in this order: `ERR_BATCH_PRODUCTION_STATE_INVALID`; `ERR_BATCH_QUALITY_STATE_INVALID`; `ERR_MEDIA_FILL_STATE_INVALID`; `ERR_QUALIFICATION_STATE_INVALID`; `ERR_COMPONENT_LOT_STATE_INVALID`; `ERR_EXCURSION_STATE_INVALID`; `ERR_DEVIATION_STATE_INVALID`; `ERR_BR_REVIEW_STATE_INVALID`; `ERR_AUDIT_ENGAGEMENT_STATE_INVALID`; and finally `ERR_PROJECT_STATE_INVALID`.
13. **Aseptic and GMP safety rules**, in this order: `ERR_MEDIA_FILL_QUALIFICATION_EXPIRED`; `ERR_SUITE_NOT_OPEN`; `ERR_CLEANING_VALIDATION_REQUIRED`; `ERR_OPERATOR_NOT_QUALIFIED`; `ERR_MEDIA_FILL_NOT_PASSED`; `ERR_MEDIA_FILL_UNDERSIZED`; `ERR_REQUIRED_IPC_MISSING`; `ERR_IPC_FAILED`; `ERR_OPEN_CRITICAL_DEVIATION`; `ERR_COMPONENT_STERILIZATION_INVALID`; and `ERR_SEGREGATION_OF_DUTIES`.
14. **Temporal rules**, in this order: `ERR_INVALID_WINDOW`; then the suite occupancy conflict `ERR_SUITE_CHANGEOVER_CONFLICT`; then the lead-operator conflict `ERR_OPERATOR_DOUBLE_BOOKED`.
15. **Referential coherence**, in this order: `ERR_COMPONENT_LOT_PROJECT_MISMATCH`; `ERR_EM_SAMPLE_SUITE_MISMATCH`; `ERR_COMPONENTS_NOT_RESERVED`.
16. **Uniqueness and payload coherence**, in this order: `ERR_DUPLICATE_BATCH_NUMBER`; `ERR_DUPLICATE_LOT_CODE`; `ERR_DUPLICATE_SUITE_CODE`; `ERR_BR_REVIEW_ALREADY_EXISTS`; `ERR_COMPONENT_LOT_INSUFFICIENT`; `ERR_IPC_PAYLOAD_INCONSISTENT`.
17. **Fiscal and capacity ceilings, evaluated last of all** — `ERR_PROJECT_UNIT_BUDGET_EXCEEDED`, then `ERR_SUITE_CAPACITY_EXCEEDED`. Both are money-shaped rejections and both carry HTTP 402. Placing them last means a scheduling request that is simultaneously ill-formed and over budget reports the ill-formedness, and a request that is over both ceilings reports the project unit budget first.

Which of these rungs apply to a given endpoint is determined by the endpoint. The state-machine rungs each guard a named set of operations: the production-axis check guards batch setup, fill start, fill completion and cancellation; the quality-axis check guards opening a batch record review, closing one, and Qualified-Person release; the media-fill check guards execution, read-out and adjudication; the operator-qualification check guards granting and revoking; the component-lot check guards the sterilisation-validation verdict and reservation creation; the excursion check guards opening and closing an environmental investigation; the deviation check guards classification, CAPA submission and the CAPA decision; the batch-record-review check guards recording findings and closing; the audit-engagement check guards hosting; and the project-status check guards technology-transfer advancement, hold release, batch scheduling, batch setup and audit hosting.

### 2.11. Path Resolution and Sub-Resource Reads

Path identifiers are resolved strictly left to right, and the first segment that fails to resolve determines the error. Each resource type has its own not-found code: `ERR_CLIENT_PROJECT_NOT_FOUND`, `ERR_FILLING_SUITE_NOT_FOUND`, `ERR_MEDIA_FILL_NOT_FOUND`, `ERR_QUALIFICATION_NOT_FOUND`, `ERR_BATCH_ORDER_NOT_FOUND`, `ERR_COMPONENT_LOT_NOT_FOUND`, `ERR_RESERVATION_NOT_FOUND`, `ERR_IN_PROCESS_CHECK_NOT_FOUND`, `ERR_EM_SAMPLE_NOT_FOUND`, `ERR_DEVIATION_NOT_FOUND`, `ERR_BR_REVIEW_NOT_FOUND` and `ERR_AUDIT_ENGAGEMENT_NOT_FOUND`, all at HTTP 404.

The same codes are reused when a foreign key supplied in a request body fails to resolve. A `primary_suite_id` or `suite_id` that names no suite yields `ERR_FILLING_SUITE_NOT_FOUND`; a `client_project_id` that names no project yields `ERR_CLIENT_PROJECT_NOT_FOUND`; a `media_fill_id` yields `ERR_MEDIA_FILL_NOT_FOUND`; a `lead_operator_qualification_id` yields `ERR_QUALIFICATION_NOT_FOUND`; a `batch_order_id` yields `ERR_BATCH_ORDER_NOT_FOUND`; a `component_lot_id` yields `ERR_COMPONENT_LOT_NOT_FOUND`; and an `em_sample_id` yields `ERR_EM_SAMPLE_NOT_FOUND`.

Most relationships in this system are addressed by filtered collection reads rather than by nesting. There are exactly two nested reads, and both are append-only evidence trails whose members have no independent addressability: the audit engagements raised against a project, and the Qualified-Person decisions signed against a batch. Both resolve their parent first and both order by `created_at` ascending.

## 3. Business Logic & Workflows

### 3.1. Taking On a Sponsor: Project Intake and Technology Transfer

A programme begins when a `ProgramManager` intakes the sponsor. The intake payload names the sponsor in `client_name` (a string of 1 to 120 characters), the drug substance in `molecule_name` (1 to 80 characters), and the presentation being filled in `dosage_form`, which is either `VIAL` or `PRESYRINGE`. It nominates the suite the programme will run in through `primary_suite_id`, which must reference a suite that already exists — this is the suite whose aseptic qualification and operator roster later feed the project's readiness assessment. It records the nominal fill weight per container in `target_fill_weight_mg`, which must be greater than zero and from which the fill-weight in-process tolerance band is derived. Finally it carries the two contractual figures: `historical_reject_rate_ppm`, the sponsor's own declared historical visual reject rate in parts per million, an integer of at least 0 and at most 100000; and `reserved_unit_budget`, an integer of at least 0 setting the ceiling on the total component units the CMO may commit across all of that project's live batches.

A freshly intaken project starts with `status` set to `INTAKE`, `tech_transfer_stage` set to `NOT_STARTED`, `analytical_method_transfer_status` set to `NOT_STARTED`, and all three derived ledgers — `committed_demand_units`, `open_deviation_risk_total` and `last_client_audit_finding_count` — at 0.

Technology transfer then advances one step at a time, and only while the project is still in `INTAKE`. Each advance supplies `to_stage` and `analytical_method_transfer_status`. `to_stage` must be the immediate successor of the project's current `tech_transfer_stage` in the ordered progression `NOT_STARTED`, `GAP_ASSESSMENT`, `ENGINEERING_RUN`, `COMPLETE` — skipping a stage or naming the current stage again is refused with `ERR_PROJECT_STATE_INVALID` (HTTP 409), as is any advance attempted on a project whose `status` is no longer `INTAKE`. The supplied `analytical_method_transfer_status` may hold or advance but never regress: it must not be earlier than the stored value in the ordered progression `NOT_STARTED`, `IN_TRANSFER`, `VALIDATED`. Each successful advance writes `tech_transfer_stage` and `analytical_method_transfer_status` to the supplied values and bumps the project's `version`. The intermediate advances — to `GAP_ASSESSMENT` and to `ENGINEERING_RUN` — move only those two fields and leave `status` at `INTAKE`. The advance that reaches `to_stage` of `COMPLETE` with an `analytical_method_transfer_status` of `VALIDATED` additionally flips the project `INTAKE → ACTIVE`, and that is the only way a project becomes `ACTIVE`.

An `ACTIVE` project can be pulled back to `ON_HOLD`, but never by a direct call: the only entry into `ON_HOLD` is the critical-deviation cascade described in section 3.7. The only exit is a `QaReviewer` releasing the hold, supplying a `release_rationale`. That release requires the project to actually be in `ON_HOLD` — otherwise `ERR_PROJECT_STATE_INVALID` — and requires that no deviation written against any of the project's batches still carries a `classification` of `CRITICAL` with a `status` other than `CLOSED`; if one does, the release is refused with `ERR_OPEN_CRITICAL_DEVIATION` (HTTP 409). A successful release returns `status` to `ACTIVE`, restores every batch of the project whose `production_status` is `SUSPENDED` and whose suite's `posture` is not `FROZEN` to `SCHEDULED`, recomputes the project's `committed_demand_units` and each affected suite's `committed_minutes`, and bumps the project's `version`. Because the hold can be taken and released repeatedly, `ACTIVE → ON_HOLD → ACTIVE` is a genuine loop with no terminal state on the project axis.

### 3.2. Making a Suite Fit to Fill: Cleaning Validation and Aseptic Process Simulation

A shared filling suite is registered by a `ProgramManager` with a `suite_code` of 1 to 20 characters that must be unique across every suite — a collision is refused with `ERR_DUPLICATE_SUITE_CODE` (HTTP 409). The suite declares the EU GMP cleanroom `grade` of its critical zone as `A`, `B` or `C`, which selects the environmental monitoring limit table used for every sample taken in it. It declares two changeover buffers in minutes: `changeover_minutes_same_product`, an integer of at least 0, is the buffer that must elapse after a batch's `planned_end` before the next batch of the *same* molecule may start; `changeover_minutes_product_change` is the buffer required before the next batch of a *different* molecule may start, and it must be at least as large as `changeover_minutes_same_product`. It also declares `max_committed_minutes`, an integer greater than 0, capping the suite's total committed occupancy. A new suite is born with `aseptic_qualification_status` of `NOT_QUALIFIED`, `cleaning_validation_status` of `NOT_VALIDATED`, `media_fill_valid_until` and `last_cleaned_molecule` both null, and `committed_minutes`, `open_action_excursion_count` and `qualified_operator_count` all 0 — which, per section 2.5, computes an initial `posture` of `RESTRICTED`.

Cross-contamination control is the first of the suite's two independent qualification axes, and it evolves without any reference to the aseptic axis. A `MicrobiologyAnalyst` records a cleaning-validation swab result naming the `molecule_name` the suite was just cleaned down from together with the measured `residue_ug_per_swab`. The acceptance limit is 100 micrograms per swab, and it is inclusive: a residue at or below 100 sets `cleaning_validation_status` to `VALIDATED` and writes the supplied `molecule_name` into `last_cleaned_molecule`, while a residue above 100 sets `cleaning_validation_status` to `FAILED` and leaves `last_cleaned_molecule` exactly as it was. Either verdict recomputes the suite's `posture` and bumps the suite's `version`; a `FAILED` verdict necessarily drives that posture to `FROZEN`. All four movements on this axis are legal — `NOT_VALIDATED → VALIDATED`, `NOT_VALIDATED → FAILED`, `VALIDATED → FAILED` and `FAILED → VALIDATED` — and re-validating an already `VALIDATED` suite for a new molecule is a normal, expected event. What is not permitted is running a cleaning validation while a batch in that suite has `production_status` of `FILLING`; such an attempt is refused as a state conflict (HTTP 409).

The aseptic axis is qualified by **media fills** — aseptic process simulations in which sterile growth medium is filled instead of product. A `MicrobiologyAnalyst` schedules one against a `suite_id` with a `scheduled_run_date`, and it is born with `status` of `SCHEDULED`, `units_filled` and `contaminated_units` both null, and `participating_operator_names` an empty list. Executing the simulation advances `SCHEDULED → INCUBATING` and records how large the run was in `units_filled` and which operators performed aseptic interventions in `participating_operator_names`. The run must be at least 5000 units — exactly 5000 is acceptable, 4999 is not, and an undersized run is refused with `ERR_MEDIA_FILL_UNDERSIZED` (HTTP 422). The supplied `participating_operator_names` list must not be empty, and, as with cleaning validation, execution is refused as a state conflict while any batch in the suite is in `FILLING`. Attempting to execute a simulation whose `status` is anything other than `SCHEDULED` yields `ERR_MEDIA_FILL_STATE_INVALID` (HTTP 409).

Incubation read-out is where the fork lives. Reading out an `INCUBATING` simulation supplies `contaminated_units`, the number of turbid units found, and the server stamps `read_at` from the logical clock. A read-out is refused with `ERR_MEDIA_FILL_UNDERSIZED` when the recorded `units_filled` is below 5000, and with `ERR_MEDIA_FILL_STATE_INVALID` from any `status` other than `INCUBATING`. Three outcomes are possible and they are decided purely by the count.

**Zero contaminated units passes.** `status` becomes `PASSED` and `outcome_reason` is pinned to `ZERO_CONTAMINANT_PASS`. The suite's `aseptic_qualification_status` moves to `QUALIFIED` — legally from either `NOT_QUALIFIED` or `INVALIDATED` — and `media_fill_valid_until` is stamped as the simulation's `read_at` plus 183 days, which is the validity period of an aseptic process simulation (just over six months). The suite's `posture` is recomputed. When the pass is the requalification of a previously `INVALIDATED` suite, it additionally returns every batch in that suite whose `production_status` is `SUSPENDED` and whose owning project's `status` is `ACTIVE` to `SCHEDULED`; a requalifying simulation must be one whose `scheduled_run_date` is strictly after the `read_at` of the simulation that invalidated the suite. The simulation's own `version` is bumped.

**Exactly one contaminated unit forks to investigation.** `status` becomes `INVESTIGATION_REQUIRED` and `outcome_reason` is pinned to `SINGLE_UNIT_INVESTIGATION`. This branch deliberately carries no suite-level qualification change at all: `aseptic_qualification_status` is left exactly as it was, `media_fill_valid_until` is untouched, no batch is suspended and no reservation is released. The suite's `posture` is recomputed and therefore stays `RESTRICTED` or `FROZEN` if it already was. The simulation's `version` is bumped.

**Two or more contaminated units fails.** `status` becomes `FAILED` and `outcome_reason` is pinned to `MULTI_UNIT_FAILURE`, and this branch carries the full depth-five cascade. The suite's `aseptic_qualification_status` moves to `INVALIDATED` and its `media_fill_valid_until` is set back to null; the invalidation drives `posture` to `FROZEN`; the freeze sets every batch in that suite whose `production_status` is `SCHEDULED` or `SETUP` to `SUSPENDED` and, for each such batch whose `quality_status` is neither `RELEASED` nor `REJECTED`, sets `quality_status` to `QUARANTINED`; the quarantine sets every reservation of each such batch whose `status` is `RESERVED` to `RELEASED` with `released_reason` of `SUITE_FREEZE_SUSPENSION`, increasing that reservation's lot's `quantity_available` by its `quantity_reserved`; and the restored availability returns any such lot whose `status` was `EXHAUSTED` to `RELEASED`. Separately, every operator qualification that cites this simulation through its `media_fill_id` and whose `status` is `QUALIFIED` is set to `REVOKED`. The suite's `version` and the simulation's `version` are both bumped, as is the `version` of every row the cascade touches.

An `INVESTIGATION_REQUIRED` simulation is resolved by a `QaReviewer` adjudicating it, supplying an `outcome` of either `PASSED` or `FAILED` together with a mandatory `adjudication_rationale`. Adjudication from any other `status` yields `ERR_MEDIA_FILL_STATE_INVALID`. The two adjudication branches are exactly as consequential as the corresponding direct read branches and their side-effect sets are disjoint. An adjudicated pass pins `outcome_reason` to `ADJUDICATED_PASS`, sets `status` to `PASSED`, moves the suite to `QUALIFIED` and stamps `media_fill_valid_until` as the simulation's already-recorded `read_at` plus 183 days, then recomputes `posture` and bumps the simulation's `version`. An adjudicated failure pins `outcome_reason` to `ADJUDICATED_FAILURE`, sets `status` to `FAILED`, moves the suite to `INVALIDATED` with the identical depth-five cascade described above, revokes every `QUALIFIED` qualification citing this simulation, and bumps the simulation's `version`. `PASSED` and `FAILED` are terminal for a media fill.

### 3.3. The Operator Roster: Qualification, Lapse and Revocation

Aseptic filling is only as good as the people who gown into the room, so operator competence is tracked per suite rather than per person. A `MicrobiologyAnalyst` opens a qualification record naming the operator in `operator_name` (a string of 1 to 40 characters), the suite it is scoped to in `suite_id`, and the scope of the competence in `qualification_type`, which is `GOWNING`, `ASEPTIC_INTERVENTION` or `VISUAL_INSPECTION`. Because qualifications are suite-scoped, one operator holds one record per suite. The record declares `expires_on`, the instant at or after which the competence is no longer effective, and that instant must be strictly later than the logical clock at the moment of creation — an `expires_on` at or before the clock is refused with `ERR_INVALID_WINDOW` (HTTP 422). A record may optionally cite the aseptic process simulation it is evidenced by through `media_fill_id`. New records begin with `status` of `PENDING` and `qualified_at` null.

Granting the qualification moves it `PENDING → QUALIFIED`, stamps `qualified_at` from the logical clock, recomputes the suite's `qualified_operator_count` and its `posture`, and bumps the record's `version`. A grant attempted from any status other than `PENDING` is refused with `ERR_QUALIFICATION_STATE_INVALID` (HTTP 409). The grant also re-checks that `expires_on` is still later than the logical clock. Where `qualification_type` is `ASEPTIC_INTERVENTION` the grant carries an extra evidential burden: `media_fill_id` must be non-null, the cited simulation must have `status` of `PASSED`, and the record's `operator_name` must be a member of that simulation's `participating_operator_names`. Any of those three failing is refused with `ERR_MEDIA_FILL_NOT_PASSED` (HTTP 409). The other two qualification types carry no such requirement, and for them `media_fill_id` may be left null.

Qualifications rot with time rather than with use. When the logical clock advances to an instant at or after a `QUALIFIED` record's `expires_on`, that record moves `QUALIFIED → LAPSED` automatically, and each lapse recomputes its suite's `qualified_operator_count` and `posture` and bumps the record's `version`. Because lapses are processed in ascending `expires_on` order with ties broken by ascending `created_at`, the sequence of posture recomputations a single clock move produces is deterministic.

Revocation is the disciplinary path and it is available from three states. A `MicrobiologyAnalyst` may revoke a record whose `status` is `PENDING`, `QUALIFIED` or `LAPSED`, supplying a `revoke_reason`; the record moves to `REVOKED` and its `version` is bumped. Revoking a record that was `QUALIFIED` additionally recomputes the suite's `qualified_operator_count` and `posture`, because that record was counted; revoking a `PENDING` or `LAPSED` record does not, because it was not. `REVOKED` is terminal, and a revoke attempted against an already-`REVOKED` record is refused with `ERR_QUALIFICATION_STATE_INVALID`. Revocation also happens without anyone asking for it: when an aseptic process simulation ends in `FAILED`, whether by direct read-out or by adjudication, every `QUALIFIED` record citing it through `media_fill_id` is revoked as part of that failure.

### 3.4. Component Supply: Receipt, Sterilisation Validation and Reservation

Primary packaging is project-dedicated, never pooled. A `ProgramManager` receives a lot naming its owning `client_project_id`, its `component_type` — one of `VIAL`, `STOPPER`, `SYRINGE` or `PLUNGER` — and the vendor's `lot_code`, a string of 1 to 30 characters that must be unique within that `component_type`; a collision is refused with `ERR_DUPLICATE_LOT_CODE` (HTTP 409). The lot declares `quantity_received`, an integer greater than 0 which is immutable for the life of the row and is the conserved total against which the component-unit ledger always balances, and `sterilization_expiry`, the instant at or after which the depyrogenation and sterilisation hold time lapses. A received lot begins with `status` of `QUARANTINE`, `sterilization_validation_status` of `PENDING`, and `quantity_available` of 0 — nothing may be drawn from a lot that has not yet cleared its dossier.

A `MicrobiologyAnalyst` clears it by recording the sterilisation-validation verdict, supplying an `outcome` of either `RELEASED` or `REJECTED` together with the achieved lethality in `f0_minutes`. The verdict is only accepted while the lot's `sterilization_validation_status` is still `PENDING`; a second verdict on the same lot is refused with `ERR_COMPONENT_LOT_STATE_INVALID` (HTTP 409). A `RELEASED` outcome sets both `sterilization_validation_status` and `status` to `RELEASED` and opens `quantity_available` to the full `quantity_received`; it additionally requires that `sterilization_expiry` is still strictly later than the logical clock, and a lot whose hold time has already lapsed is refused as a state conflict (HTTP 409). A `REJECTED` outcome sets both fields to `REJECTED` and zeroes `quantity_available`. Either way the lot's `version` is bumped. `REJECTED` is terminal, as is `EXPIRED`.

Drawing units from a lot creates a reservation, which either a `ProgramManager` or a `ProductionSupervisor` may do. The payload names the `batch_order_id` holding the components, the `component_lot_id` they are drawn from, the `quantity_reserved` (an integer greater than 0) being withheld, and `expected_component_lot_version` as described in section 2.7. Four coherence rules guard the create. The lot's `status` must be `RELEASED` — a lot in `QUARANTINE`, `REJECTED`, `EXPIRED` or `EXHAUSTED` cannot be drawn from, and the attempt is refused with `ERR_COMPONENT_LOT_STATE_INVALID`. Beyond that status arm, the lot's sterility must cover the whole planned fill: `sterilization_validation_status` must be `RELEASED`, `sterilization_expiry` must be strictly later than the logical clock, *and* `sterilization_expiry` must be at or after the owning batch's `planned_end`, since a sterilised component has to remain inside its hold time through the entire window it will be used in. A failure of any of those three yields `ERR_COMPONENT_STERILIZATION_INVALID` (HTTP 409). The lot must belong to the same programme and the right presentation: its `client_project_id` must equal the batch's `client_project_id`, and its `component_type` must be one of the lines the project's `dosage_form` actually calls for — a `VIAL` project consumes `VIAL` and `STOPPER` lots, a `PRESYRINGE` project consumes `SYRINGE` and `PLUNGER` lots — with any mismatch refused as `ERR_COMPONENT_LOT_PROJECT_MISMATCH` (HTTP 409). And the lot must actually have the units: `quantity_reserved` must be at most the lot's current `quantity_available`, or the create is refused with `ERR_COMPONENT_LOT_INSUFFICIENT` (HTTP 409).

A successful reservation is born with `status` of `RESERVED` and `released_reason` null, decreases the lot's `quantity_available` by `quantity_reserved`, and bumps the lot's `version`. When that decrease brings `quantity_available` to exactly 0, the lot moves `RELEASED → EXHAUSTED`. Exhaustion is deliberately reversible: whenever a reservation against an exhausted lot is handed back and `quantity_available` rises above 0 again, the lot returns `EXHAUSTED → RELEASED`.

A reservation leaves `RESERVED` down one of exactly two paths, and the difference between them is what happens to the lot. When the owning batch completes its fill, moving `FILLING → FILLED`, every one of its `RESERVED` reservations becomes `CONSUMED` and the lot's `quantity_available` is deliberately *not* changed, because those units were already withheld at reservation time and consuming them merely retires them permanently. When the owning batch is cancelled, or is suspended by a suite freeze or a project hold, every one of its `RESERVED` reservations becomes `RELEASED` with `released_reason` recorded as either `BATCH_CANCELLED` or `SUITE_FREEZE_SUSPENSION` according to the cause, and the lot's `quantity_available` is increased by that reservation's `quantity_reserved`. Both `CONSUMED` and `RELEASED` are terminal, and every such transition bumps the reservation's own `version`. One consequence deserves stating plainly: when the logical clock expires a lot that still has `RESERVED` reservations against it, `quantity_available` drops to 0 but those reservations are left exactly as they are, so the sum of held units plus available units continues to balance against `quantity_received`.

### 3.5. Booking Time in a Shared Suite

Scheduling is the most heavily guarded write in the system, because a suite is a scarce shared asset and a mis-booked window is discovered only when two crews arrive at the same door. A `ProgramManager` schedules a batch by naming its owning `client_project_id`, the `suite_id` it will occupy, the `lead_operator_qualification_id` of the lead aseptic operator, a sponsor `batch_number` of 1 to 30 characters, the occupancy window as `planned_start` and `planned_end`, the planned container count in `target_fill_units` (an integer greater than 0), and `expected_suite_version`. The window is half-open: `planned_start` is inclusive, `planned_end` is exclusive, and `planned_end` must be strictly after `planned_start` or the request is refused with `ERR_INVALID_WINDOW` (HTTP 422). The owning project must be `ACTIVE`; scheduling against an `INTAKE` or `ON_HOLD` project is refused with `ERR_PROJECT_STATE_INVALID`. The `batch_number` must be unused by any non-`CANCELLED` batch of the same project, or the request is refused with `ERR_DUPLICATE_BATCH_NUMBER` (HTTP 409).

Two suite-fitness rules apply at scheduling time. The suite's aseptic qualification must cover the *whole* requested window, so `media_fill_valid_until` must be non-null and at or after the batch's `planned_end`; a suite with no valid simulation, or one whose validity lapses inside the window, is refused with `ERR_MEDIA_FILL_QUALIFICATION_EXPIRED` (HTTP 409). And the nominated lead operator must be genuinely effective: the qualification named by `lead_operator_qualification_id` must be an `ASEPTIC_INTERVENTION` qualification for this very suite — its `suite_id` equal to the batch's `suite_id` — with `status` of `QUALIFIED` and `expires_on` at or after the logical clock. Otherwise the request is refused with `ERR_OPERATOR_NOT_QUALIFIED` (HTTP 409).

**Suite occupancy conflicts** treat the window as half-open *and extend it by a directional changeover buffer*. A live batch, for the purposes of both occupancy rules, is any batch whose `production_status` is `SCHEDULED`, `SETUP`, `FILLING` or `FILLED`; `SUSPENDED` and `CANCELLED` batches release their claim on the suite entirely. The applicable buffer between two batches is the suite's `changeover_minutes_same_product` when the two batches' owning projects carry the same `molecule_name`, and the suite's `changeover_minutes_product_change` when they carry different molecules — a full product changeover demands the longer clean-down. The new batch is rejected when there exists a live batch in the same suite such that the new batch's `planned_start` falls strictly earlier than that batch's `planned_end` advanced by the applicable buffer, *and* that batch's `planned_start` falls strictly earlier than the new batch's `planned_end` advanced by the applicable buffer. Both comparisons are strict, so a new batch that starts at exactly the instant a previous batch's `planned_end` plus buffer falls is accepted. The rejection carries `ERR_SUITE_CHANGEOVER_CONFLICT` (HTTP 409).

**Lead-operator conflicts** are treated the opposite way on purpose. Here the interval is closed at both ends, no buffer is applied at all, and the check spans every suite in the plant rather than just this one — a human being cannot lead two aseptic fills at once no matter which rooms they are in. The operator resource is resolved by taking the `operator_name` of the qualification named by `lead_operator_qualification_id`, and grouping live batches by that name. The new batch is rejected when there exists a live batch whose resolved `operator_name` equals the new batch's, such that the new batch's `planned_start` is at or before that batch's `planned_end` *and* that batch's `planned_start` is at or before the new batch's `planned_end`. Both comparisons are non-strict, so windows that merely touch at an endpoint do collide — the exact opposite adjacency treatment from the suite rule above. The rejection carries `ERR_OPERATOR_DOUBLE_BOOKED` (HTTP 409).

Two figures are computed once at creation and then frozen for the life of the row. The first is `changeover_minutes_applied`. The server looks at the live batches in the same suite whose `planned_end` is at or before the new batch's `planned_start`, and picks the single one with the greatest `planned_end`, breaking a tie by the greatest `created_at`. When that candidate set is empty — the new batch is the first thing this suite will run — `changeover_minutes_applied` is the standing initial-setup allowance of 60 minutes, a full hour of room preparation. Otherwise, if the preceding batch's project carries the same `molecule_name` as the new batch's project, `changeover_minutes_applied` is the suite's `changeover_minutes_same_product`; if the molecules differ, it is the suite's `changeover_minutes_product_change`.

The second frozen figure is `component_demand_units`, the contractual count of primary-packaging units the batch commits. It depends on nothing but the new batch's `target_fill_units` and its project's `dosage_form`; no lot participates, because demand is a contractual figure rather than an availability figure. A `VIAL` presentation calls for two component lines in this order: `VIAL`, then `STOPPER`. A `PRESYRINGE` presentation calls for `SYRINGE`, then `PLUNGER`. Each line carries an overage allowance and a vendor pack size: vials carry 3 percent overage and ship in packs of 480; stoppers carry 5 percent overage and ship in packs of 1000; syringes carry 3 percent overage and ship in packs of 500; plungers carry 5 percent overage and ship in packs of 1000. For each line in the order listed, the gross requirement is `target_fill_units` multiplied by one plus that line's overage fraction; the line's committed units are then the gross requirement divided by that line's pack size, rounded *up* to a whole number of packs, multiplied back by the pack size. `component_demand_units` is the sum of the line figures. The order of operations is pinned and it matters: the pack-size ceiling is applied per line *first* and the rounded lines are summed *afterwards*. Summing the gross requirements of both lines and then applying a single pack-size ceiling to the total is explicitly wrong and yields a different integer. For a `VIAL` batch of 10000 containers, the vial line grosses 10300 units and rounds up to 22 packs of 480, or 10560 units; the stopper line grosses 10500 and rounds up to 11 packs of 1000, or 11000 units; `component_demand_units` is therefore 21560 — not the 21000 that the forbidden sum-then-round order would produce.

Both ceilings are checked last, after everything else has passed, and both answer with HTTP 402. The project's contractual unit ceiling is tested by adding the new batch's `component_demand_units` to the project's current `committed_demand_units`: if that sum exceeds `reserved_unit_budget`, the request is refused with `ERR_PROJECT_UNIT_BUDGET_EXCEEDED`. Then the suite's occupancy ceiling is tested by adding the requested window length in minutes and the newly derived `changeover_minutes_applied` to the suite's current `committed_minutes`: if that sum exceeds the suite's `max_committed_minutes`, the request is refused with `ERR_SUITE_CAPACITY_EXCEEDED`. A suite's `committed_minutes` is itself the sum, over every live batch in that suite, of the number of whole minutes between that batch's `planned_start` and `planned_end` plus that batch's `changeover_minutes_applied`; the summation runs in ascending `planned_start` order with ties broken by ascending `created_at`, and every window is a whole number of minutes so no truncation arises.

A batch that survives all of the above is born with `production_status` of `SCHEDULED` and `quality_status` of `PENDING` on the two independent axes it will travel. Its project's `committed_demand_units` increases by the new `component_demand_units`, its suite's `committed_minutes` increases by the window length plus `changeover_minutes_applied`, and the suite's `version` is bumped — which is precisely why the next client to schedule into that suite must have read the suite again.

### 3.6. Running the Fill and Proving It: Setup, Aseptic Fill and In-Process Controls

The physical progress of a batch travels the production axis, and it moves independently of the quality axis on the same row: neither is a function of the other. A `ProductionSupervisor` first moves the batch `SCHEDULED → SETUP`. That requires the batch to actually be `SCHEDULED` — otherwise `ERR_BATCH_PRODUCTION_STATE_INVALID` (HTTP 409) — the suite's `posture` to be anything other than `FROZEN`, or else `ERR_SUITE_NOT_OPEN` (HTTP 409), and the owning project's `status` to be `ACTIVE`, or else `ERR_PROJECT_STATE_INVALID`. Note the asymmetry with the next step: setup tolerates a `RESTRICTED` suite, and only a hard freeze blocks it.

Starting the aseptic fill advances `SETUP → FILLING` and is the single most gated operation in the production axis, because it is the moment sterile product is exposed. Five conditions must all hold. The suite's `posture` must be exactly `OPEN` — `RESTRICTED` is not good enough here, and a suite that is merely restricted yields `ERR_SUITE_NOT_OPEN`. The suite's `media_fill_valid_until` must be non-null and at or after the current logical clock, or the attempt is refused with `ERR_MEDIA_FILL_QUALIFICATION_EXPIRED`. The suite's cross-contamination state must match the product: `cleaning_validation_status` must be `VALIDATED` *and* `last_cleaned_molecule` must equal the owning project's `molecule_name`, or the attempt is refused with `ERR_CLEANING_VALIDATION_REQUIRED` (HTTP 409) — cleaning down for a different molecule than the one about to be filled is exactly the failure this rule exists to prevent. The qualification behind `lead_operator_qualification_id` must still have `status` of `QUALIFIED` with `expires_on` at or after the logical clock, or the attempt is refused with `ERR_OPERATOR_NOT_QUALIFIED`; a qualification that lapsed between scheduling and filling stops the fill. And the components must actually be in the room: the sum of `quantity_reserved` over the batch's reservations whose `status` is `RESERVED` must be at least the batch's `component_demand_units`, or the attempt is refused with `ERR_COMPONENTS_NOT_RESERVED` (HTTP 409). A successful start writes `production_status` of `FILLING` and, on the quality axis, advances `quality_status` from `PENDING` to `IN_PROCESS_REVIEW` — the one place where a production event drives the quality axis directly.

Closing the fill advances `FILLING → FILLED` and records `filled_unit_count`, the containers actually filled, which must be greater than 0 and at most `target_fill_units`. Completion turns every `RESERVED` reservation of the batch into `CONSUMED` without touching any lot's `quantity_available`, and it stamps the forward-looking `provisional_releasable_units` figure described below. `CANCELLED` is the production axis's only terminal state, and cancellation is available to a `ProgramManager` from `SCHEDULED`, `SETUP` or `SUSPENDED` with a `cancellation_reason`; a cancel attempted while the batch is `FILLING`, `FILLED` or already `CANCELLED` is refused with `ERR_BATCH_PRODUCTION_STATE_INVALID`. Cancellation is a compensating action and unwinds exactly what scheduling added: every `RESERVED` reservation of the batch becomes `RELEASED` with `released_reason` of `BATCH_CANCELLED` and its lot's `quantity_available` rises by its `quantity_reserved`; any lot thereby lifted above 0 returns `EXHAUSTED → RELEASED`; the project's `committed_demand_units` falls by exactly the batch's `component_demand_units`; the suite's `committed_minutes` falls by exactly the window length in minutes plus `changeover_minutes_applied`; and, unless the quality axis has already reached `RELEASED` or `REJECTED`, `quality_status` is set to `REJECTED`. Cancelling a batch that was already `SUSPENDED` behaves identically except that its reservations were released by the suspension, so no further lot restoration takes place.

Suspension is never requested; it is inflicted. When a suite's `posture` becomes `FROZEN`, or when the owning project moves `ACTIVE → ON_HOLD`, every batch of the affected scope whose `production_status` is `SCHEDULED` or `SETUP` moves to `SUSPENDED`. Each such suspension sets `quality_status` to `QUARANTINED` unless that axis had already reached `RELEASED` or `REJECTED`, releases every `RESERVED` reservation of the batch back to its lot, and triggers a recomputation of the project's `committed_demand_units` and the suite's `committed_minutes`, since a suspended batch no longer commits either resource. The reverse edge, `SUSPENDED → SCHEDULED`, fires when the suite requalifies from `INVALIDATED` back to `QUALIFIED` or when a `QaReviewer` releases the project hold; it requires the suite's `posture` to be something other than `FROZEN` and the project's `status` to be `ACTIVE`, and it recomputes both ledgers again. Restoration is deliberately asymmetric: `production_status` returns to `SCHEDULED`, but `quality_status` is *not* restored automatically and remains `QUARANTINED` until the deviation-closure path in section 3.7 moves it.

In-process controls are the evidence the batch record will later be reviewed against, and either a `ProductionSupervisor` or a `QaReviewer` may record one. Each record names the `batch_order_id` under control, the `check_type` performed — `FILL_WEIGHT`, `CCI` (container closure integrity) or `VISUAL_INSPECTION` — the number of containers inspected in `sample_size` (greater than 0), the number rejected by the control in `reject_unit_count`, the number destroyed by the control itself in `destructive_sample_units`, and, for fill-weight checks only, the individual measurements in milligrams in `measured_fill_weights_mg`. Both counts default to 0 and the measurement array defaults to empty. Payload coherence is strict: `measured_fill_weights_mg` must be present and non-empty when `check_type` is `FILL_WEIGHT` and must be empty for `CCI` and `VISUAL_INSPECTION`, and `reject_unit_count` must be at most `sample_size`; any violation is refused with `ERR_IPC_PAYLOAD_INCONSISTENT` (HTTP 422).

The verdict is computed by the server, never supplied, and lands in `result` as `PASS`, `ALERT` or `FAIL`, alongside `max_absolute_deviation_pct`. For a `FILL_WEIGHT` check the server reaches the owning project's `target_fill_weight_mg` through the batch, computes for each measurement in `measured_fill_weights_mg` the absolute difference between that measurement and the target divided by the target, takes the largest such relative deviation, and rounds it half up to four decimal places into `max_absolute_deviation_pct`. That rounded figure is then compared against two tolerances, and the comparison happens *after* the rounding: a deviation strictly greater than 0.0500 gives a `result` of `FAIL`, a deviation of at least 0.0300 but not greater than 0.0500 gives `ALERT`, and anything below 0.0300 gives `PASS`. For a `CCI` check, `max_absolute_deviation_pct` is 0 and the control is zero-defect: a `reject_unit_count` of at least 1 gives `FAIL`, and only a `reject_unit_count` of 0 gives `PASS` — there is no `ALERT` band for container closure integrity. For a `VISUAL_INSPECTION` check, `max_absolute_deviation_pct` is likewise 0 and the defect rate is `reject_unit_count` divided by `sample_size`, evaluated as an exact ratio and deliberately *not* pre-rounded: a defect rate at or above the acceptable quality limit of 0.0250 gives `FAIL`, and anything below it gives `PASS`.

### 3.7. Watching the Room and Answering for It: Excursions, Deviations and CAPA

Environmental monitoring is continuous, and a `MicrobiologyAnalyst` records each result against a `suite_id` with a `sample_type` of `VIABLE_AIR`, `SURFACE` or `PERSONNEL_GLOVE` and a `cfu_count` — the colony-forming units recovered, an integer of at least 0. A sample taken while a batch was in progress may name that batch through `batch_order_id`, and when it does, that batch's `suite_id` must equal the sample's own `suite_id`, or the record is refused with `ERR_EM_SAMPLE_SUITE_MISMATCH` (HTTP 409). Omitting `batch_order_id` marks the sample as non-production.

The limits a sample is judged against are stamped onto the row at creation from the monitored suite's `grade` and the sample's `sample_type`, and they never move afterwards even if the suite is later re-graded. In a grade `A` critical zone the standard is absolute: `alert_limit` and `action_limit` are both 1 for all three sample types, so a single colony anywhere in grade A is an action-level excursion. In grade `B`, viable air carries an `alert_limit` of 5 and an `action_limit` of 10, surfaces carry 3 and 5, and personnel gloves carry 1 and 5. In grade `C`, viable air carries 50 and 100, surfaces carry 15 and 25, and personnel gloves carry 5 and 10.

`classification` is then decided against the stamped limits, and the action test is evaluated *first*: a `cfu_count` at or above `action_limit` classifies the sample `ACTION`; otherwise a `cfu_count` at or above `alert_limit` classifies it `ALERT`; otherwise it is `WITHIN_LIMIT`. Both boundaries are inclusive. The consequence of the ordering is the grade A case just described — because alert and action coincide at 1 there, a grade A colony is never merely an `ALERT`. A `WITHIN_LIMIT` sample is stamped with an `investigation_status` of `NOT_REQUIRED`, which is already terminal; an `ALERT` or `ACTION` sample is stamped `OPEN`.

Every excursion also receives a `risk_index`, which is 0 for a `WITHIN_LIMIT` sample and otherwise combines four inputs non-linearly. The ratio term is `cfu_count` divided by the stamped `action_limit`, held as an exact fraction. The grade weight is 3 for a grade `A` suite, 2 for grade `B` and 1 for grade `C`. The sample-type surcharge is 25 points for a `PERSONNEL_GLOVE` sample, 10 points for a `SURFACE` sample and 0 for `VIABLE_AIR` — a contaminated glove print is the most damning finding available. The batch-exposure term is 20 points when the sample names a `batch_order_id` whose batch had `production_status` of `FILLING` at the instant the sample was recorded, and 0 otherwise. From these, the core term is the ratio multiplied by 20 and then by the grade weight, clamped so that it is never below 0 and never above 100, and then rounded half up to a whole number. The surcharges are added to that rounded core, and `risk_index` is the smaller of 150 and that sum. The rounding happens on the core term alone and before the surcharges join it; the surcharges are never rounded and the overall cap is applied last.

An `ACTION` classification is not just a number — it reaches into the quality axis. Recording one raises the suite's `open_action_excursion_count`, which per section 2.5 recomputes the suite's `posture` to `RESTRICTED`; the restriction demotes every batch of that suite whose `quality_status` is `QP_REVIEW` back to `BR_REVIEW`; and each such demotion reopens that batch's batch record review, setting its `status` from `CLOSED` to `COMPLETE_WITH_FINDINGS`, increasing its `open_findings_count` by 1 and setting `closed_at` back to null. A demoted batch keeps its previously stamped `final_releasable_units` untouched; that figure is recomputed only when the review closes again. Recording an `ACTION` sample bumps the suite's `version` as well as writing the sample.

Investigating an excursion moves it `OPEN → INVESTIGATING` with an `investigator_note`, and deliberately does *not* relieve the suite: `INVESTIGATING` is still not closed, so `open_action_excursion_count` is unchanged and the suite stays restricted. Closing the investigation moves it `INVESTIGATING → CLOSED` and requires a non-empty `root_cause`, which is written onto the sample. For a sample classified `ACTION` there is an additional gate: every deviation that cites this sample through its `em_sample_id` must already have `status` of `CLOSED`, and an attempt to close the excursion while any linked deviation is still open is refused as a state conflict (HTTP 409). Closing recomputes the suite's `open_action_excursion_count`, which recomputes `posture` and can return the suite to `OPEN` — the only route back from an excursion-driven restriction — and bumps both the sample's `version` and the suite's `version`. An investigate or close attempted from a status that does not permit it is refused with `ERR_EXCURSION_STATE_INVALID` (HTTP 409).

Deviations are the formal GMP record of something having gone wrong, and only a `QaReviewer` may raise one. A deviation names the `batch_order_id` it is written against, a one-line `summary` of 1 to 200 characters, and optionally the `em_sample_id` of the environmental excursion that spawned it — that link is what makes a deviation polymorphic, attaching always to a batch and sometimes also to a sample. A new deviation is born with `status` of `OPEN`, `classification` null, `risk_score` 0, `capa_rejection_count` 0, `capa_summary` null, and `opened_by_user_id` stamped from the raising user's `X-User-ID`.

Classification moves the deviation `OPEN → UNDER_INVESTIGATION` and requires a `classification` of `MINOR`, `MAJOR` or `CRITICAL` together with a `classification_rationale`; classify from any other status is refused with `ERR_DEVIATION_STATE_INVALID` (HTTP 409). Classification computes `risk_score` and posts it to the owning project's `open_deviation_risk_total`, which increases by exactly the new score. The score starts from a base of 5 points for `MINOR`, 20 for `MAJOR` and 50 for `CRITICAL`. That base is multiplied by an escalation multiplier of one plus one half for each CAPA rejection the deviation has accumulated — so a deviation with no rejections is multiplied by 1, one rejection by 1.5, two rejections by 2, and so on. The product is rounded half up to a whole number. Then, and only then, an environmental-linkage bonus of 15 points is added when the deviation names an `em_sample_id` whose sample carries a `classification` of `ACTION`; a linkage to an `ALERT` or `WITHIN_LIMIT` sample earns no bonus. Finally the result is capped at 120 points. As an illustration, a `MAJOR` deviation with one CAPA rejection linked to an `ACTION` sample scores 20 multiplied by 1.5, which rounds to 30, plus the 15-point linkage bonus, for 45 points.

A `CRITICAL` classification is the trigger of the system's other multi-hop cascade. The owning batch's `quality_status` becomes `QUARANTINED`; the quarantine puts the owning project `ACTIVE → ON_HOLD`; the hold suspends every batch of that project whose `production_status` is `SCHEDULED` or `SETUP`; and each suspension releases that batch's `RESERVED` reservations back to their lots. When the quarantined batch was in `BR_REVIEW` at the time, its batch record review is additionally reopened — a `CLOSED` review returns to `COMPLETE_WITH_FINDINGS` with `open_findings_count` increased by 1 and `closed_at` set to null. A batch whose `quality_status` has already reached `RELEASED` or `REJECTED` is not quarantined by this cascade.

Corrective action follows. A `QaReviewer` submits the remedy by supplying a non-empty `capa_summary`, moving the deviation `UNDER_INVESTIGATION → CAPA_PENDING`. The decision on that submission is where segregation of duties bites: whoever decides must not be the user recorded in `opened_by_user_id`, and a self-decision is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The decision supplies an `outcome` of `APPROVED` or `REJECTED` and a `decision_note`, and it is only accepted from `CAPA_PENDING`.

A rejected CAPA loops the deviation back: `capa_rejection_count` increases by 1, `risk_score` is recomputed with the higher rejection count, the project's `open_deviation_risk_total` is adjusted by exactly the difference between the new score and the previous one, and `status` returns to `UNDER_INVESTIGATION`. The loop may run any number of times and each pass raises the score, until the 120-point cap absorbs further escalation. An approved CAPA closes the deviation: `status` becomes `CLOSED` and the project's `open_deviation_risk_total` decreases by exactly this deviation's current `risk_score`, which returns the ledger to precisely the value it held before this deviation was classified. When that approval closes the last deviation of the batch that was not already `CLOSED`, and the batch's `quality_status` is `QUARANTINED`, and its `production_status` is `FILLED`, and its suite's `posture` is not `FROZEN`, the batch's `quality_status` returns `QUARANTINED → BR_REVIEW`, closing the quarantine loop. `CLOSED` is terminal for a deviation, and every one of these transitions bumps the deviation's `version`.

### 3.8. Reviewing the Record and Certifying the Batch

The quality axis of a batch begins at `PENDING`, is moved to `IN_PROCESS_REVIEW` by the start of the fill, and from there travels through `BR_REVIEW` and `QP_REVIEW` to one of the two terminal dispositions, `RELEASED` or `REJECTED`, with `QUARANTINED` sitting off to the side as a recoverable holding state.

Opening the executed batch record review is a `QaReviewer`'s act and it names only the `batch_order_id`. Four gates guard it and their error codes are distinct on purpose. The batch's `quality_status` must be `IN_PROCESS_REVIEW`, or the request is refused with `ERR_BATCH_QUALITY_STATE_INVALID` (HTTP 409), and the batch must have finished filling with a `production_status` of `FILLED`, or the request is refused as a state conflict (HTTP 409). The batch must carry at least one in-process control of *each* of the three required kinds — `FILL_WEIGHT`, `CCI` and `VISUAL_INSPECTION` — and a batch missing any one of them is refused with `ERR_REQUIRED_IPC_MISSING` (HTTP 422). No in-process control of the batch may carry a `result` of `FAIL`; one that does is refused with `ERR_IPC_FAILED` (HTTP 409), and note that an `ALERT` result does not block the review. And at most one review row may ever exist per batch, so a second attempt is refused with `ERR_BR_REVIEW_ALREADY_EXISTS` (HTTP 409); that uniqueness gate sits at rung 16 of section 2.10, however, so it is reached only once the state gates above it have passed, and the ordinary second-attempt case — where opening the first review has itself already advanced the batch's `quality_status` to `BR_REVIEW` — is therefore refused one rung earlier with `ERR_BATCH_QUALITY_STATE_INVALID` (HTTP 409). The uniqueness gate ignores the status of the existing review row; it answers the case of a batch that already carries a review while its `quality_status` still reads `IN_PROCESS_REVIEW`.

The review is created with `status` of `IN_PROGRESS`, `closed_at` null, and `reviewer_user_id` stamped from the opening user's `X-User-ID` — the value the Qualified Person will later be measured against. Its `open_findings_count` is seeded rather than starting at zero: it is set to the number of deviations of this batch whose `classification` is `MAJOR` and whose `status` is not `CLOSED`, so every unresolved major deviation is one finding the reviewer must dispose of. Opening the review advances the batch `IN_PROCESS_REVIEW → BR_REVIEW` and bumps the batch's `version`.

Findings are driven down by recording them. A `QaReviewer` supplies an `open_findings_count` of at least 0 together with a `findings_note`; the supplied value overwrites the stored one and the review's `version` is bumped. From `IN_PROGRESS` this moves the review to `COMPLETE_WITH_FINDINGS`, and from `COMPLETE_WITH_FINDINGS` it is a self-loop that leaves the status where it is — which is exactly how a reviewer walks the count down to zero across several passes. Closing the review is permitted from either `IN_PROGRESS` or `COMPLETE_WITH_FINDINGS`, requires `open_findings_count` to be exactly 0, and requires the owning batch to still be in `BR_REVIEW`; a close attempted with findings outstanding, or from a status that does not permit it, is refused with `ERR_BR_REVIEW_STATE_INVALID` (HTTP 409). A successful close sets `status` to `CLOSED`, stamps `closed_at` from the logical clock, advances the batch `BR_REVIEW → QP_REVIEW`, stamps the batch's `final_releasable_units`, and bumps both the review's `version` and the batch's `version`. The review is never terminal: the `ACTION`-excursion demotion of section 3.7 and the quarantine of a batch in `BR_REVIEW` both push a `CLOSED` review back to `COMPLETE_WITH_FINDINGS`.

**Two releasable-unit figures exist and they are computed differently, at different moments, from different evidence.** Both begin from the same destructive total: the sum of `destructive_sample_units` over every in-process control recorded against the batch, accumulated in ascending `created_at` order.

The forward-looking figure, `provisional_releasable_units`, is stamped when the batch advances `FILLING → FILLED`, before any visual inspection result necessarily exists. It projects rejects from the sponsor's own contractual figure: the expected reject count is `filled_unit_count` multiplied by the project's `historical_reject_rate_ppm` divided by one million, rounded *up* to a whole number — a ceiling, never a half-up rounding. `provisional_releasable_units` is then `filled_unit_count` less that expected reject count less the destructive total. It ignores `quarantined_unit_count` entirely, which makes it systematically optimistic whenever the actual visual reject rate turns out worse than the sponsor's history suggested.

The chronological figure, `final_releasable_units`, is stamped when the batch advances `BR_REVIEW → QP_REVIEW`, and it replays what actually happened. Its reject term is the sum of `reject_unit_count` over the batch's in-process controls whose `check_type` is `VISUAL_INSPECTION`, accumulated in ascending `created_at` order; rejects recorded by fill-weight or container-closure controls do not count here. `final_releasable_units` is `filled_unit_count` less that actual visual reject total, less the destructive total, less `quarantined_unit_count` — the containers segregated during batch record review, which defaults to 0 and is subtracted by this variant alone. `historical_reject_rate_ppm` is not consulted at all. For identical stored data the two figures differ, and `provisional_releasable_units` is never overwritten by the final computation: a batch that filled 8500 containers under a declared historical rate of 2500 parts per million, with 60 destructively sampled units and 166 units rejected at visual inspection and nothing quarantined, carries a provisional figure of 8418 and a final figure of 8274 side by side.

Certification is the `QualifiedPerson`'s exclusive act, and it is the only operation in the system whose success creates a second resource: an immutable Qualified-Person decision record, returned with HTTP 201. The signer supplies a `decision` of `RELEASE`, `REJECT` or `QUARANTINE` and a mandatory written `rationale` of 1 to 300 characters. Four gates guard all three decisions alike. The batch must have a batch record review, that review's `status` must be `CLOSED` and its `open_findings_count` must be 0, or the request is refused with `ERR_BR_REVIEW_NOT_CLOSED` (HTTP 409) — and this check is evaluated *before* the state check, so a Qualified Person signing against an unreviewed batch learns that fact rather than merely being told the state machine disagrees. The batch's `quality_status` must be `QP_REVIEW`, or the request is refused with `ERR_BATCH_QUALITY_STATE_INVALID`; a batch that has been demoted back to `BR_REVIEW`, quarantined, or already dispositioned fails here even if its review is closed and clean. No deviation of the batch may carry a `classification` of `CRITICAL` with a `status` other than `CLOSED`, or the request is refused with `ERR_OPEN_CRITICAL_DEVIATION` (HTTP 409). And the signing `X-User-ID` must differ from the review's `reviewer_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

Each of the three decisions writes an appended record carrying `batch_order_id`, `qp_user_id` stamped from the signer's `X-User-ID`, `decision`, `rationale`, `released_unit_count` and `fee_cents`, and each bumps the batch's `version`.

- A `RELEASE` sets the batch's `quality_status` to `RELEASED`, stamps `release_fee_cents` on the batch from the fee formula below, and appends a decision whose `released_unit_count` copies the batch's `final_releasable_units` and whose `fee_cents` copies `release_fee_cents`. The batch's `production_status` must be `FILLED` for a release to be signed.
- A `REJECT` sets the batch's `quality_status` to `REJECTED`, leaves `release_fee_cents` null on the batch, and appends a decision whose `released_unit_count` is 0 and whose `fee_cents` is 0.
- A `QUARANTINE` sets the batch's `quality_status` to `QUARANTINED`, leaves `release_fee_cents` null on the batch, and appends a decision whose `released_unit_count` is 0 and whose `fee_cents` is 0. Unlike the other two, this disposition is not terminal — the quarantined batch can be brought back to `BR_REVIEW` once its deviations are closed.

The release fee is computed in five pinned steps and, although the discount tier depends on a total that itself looks as though it should depend on the discount, the tier is selected exactly once and is never re-derived. **Step one:** the subtotal in cents is a base release fee of 150000 cents plus 40 cents for each unit of `final_releasable_units`. **Step two:** a deviation surcharge is the subtotal multiplied by the surcharge percentage for the most severe open deviation class on this batch, rounded half up to whole cents. That class is the greatest `classification`, ranked with `CRITICAL` above `MAJOR` above `MINOR`, over the batch's deviations whose `status` is not `CLOSED` and whose `classification` is not null; when no such deviation exists the class is none. The percentages are 0 for none, 5 percent for `MINOR`, 12 percent for `MAJOR` and 25 percent for `CRITICAL` — the last of which cannot in practice arise, since an open critical deviation blocks the release outright. **Step three:** the pre-discount total is the subtotal plus the surcharge. **Step four:** the volume discount percentage is chosen from the first matching tier evaluated against the *pre-discount total*: 10 percent for a pre-discount total of at least 2000000 cents, otherwise 6 percent at or above 1000000 cents, otherwise 3 percent at or above 500000 cents, otherwise 0 percent. **Step five:** `release_fee_cents` is the pre-discount total less the pre-discount total multiplied by that chosen percentage, rounded half up to whole cents. Round-half-up is applied independently at step two and at step five and never once over a composed expression. Worked through: a batch with `final_releasable_units` of 8274 and one open `MINOR` deviation has a subtotal of 480960 cents, a surcharge of 24048 cents, a pre-discount total of 505008 cents which selects the 3 percent tier, a discount of 15150 cents, and a `release_fee_cents` of 489858. Re-deriving the tier from that final 489858 would have selected 0 percent and produced 505008, and that is forbidden.

### 3.9. Facing the Outside World: Audits, Readiness Scoring and Unit Accounting

Sponsors audit their contract manufacturers, and regulators inspect them. Both are handled by the same engagement record, which either a `ClientRepresentative` or a `ProgramManager` may raise against a `client_project_id`. The `audit_kind` distinguishes them: `CLIENT_AUDIT` when the sponsor is auditing the CMO, `INSPECTION_READINESS` when the CMO is rehearsing a regulatory inspection on itself. The requester declares the earliest instant they can attend in `requested_window_start`, which must be strictly later than the logical clock or the request is refused with `ERR_INVALID_WINDOW` (HTTP 422). A new engagement is born with `status` of `REQUESTED`, `finding_count` of 0 and `hosted_at` null.

A `ProgramManager` then resolves the engagement, supplying an `outcome` of either `HOSTED` or `DEFERRED` together with the `finding_count` raised. Hosting is permitted from `REQUESTED` and also from `DEFERRED` — a deferred engagement is re-hostable later, which is what makes the deferral loop worth having — but hosting an engagement whose `status` is already `HOSTED` is refused with `ERR_AUDIT_ENGAGEMENT_STATE_INVALID` (HTTP 409). Hosting additionally requires that the project's `status` is `ACTIVE`, or else `ERR_PROJECT_STATE_INVALID` (HTTP 409), and that the project's nominated `primary_suite_id` has a `posture` other than `FROZEN`, or else `ERR_SUITE_NOT_OPEN` (HTTP 409) — you do not walk a sponsor through a frozen suite. A successful hosting writes the supplied `finding_count`, stamps `hosted_at` from the logical clock, sets `status` to `HOSTED`, recomputes the project's `last_client_audit_finding_count`, and bumps the engagement's `version`. A deferral instead sets `status` to `DEFERRED`, leaves `hosted_at` null and leaves `finding_count` at 0 regardless of what was supplied, and bumps the engagement's `version`. `HOSTED` is terminal.

Inspection readiness is also scored, through a read-only assessment of a project that computes nothing persistent. The caller must supply a `variant` of either `INTAKE_FORECAST` or `GMP_AUDIT`; the parameter is required and a value outside that set is refused with `ERR_INVALID_ENUM_VALUE` (HTTP 422). The response echoes `client_project_id` and `variant` and reports `readiness_score` together with each weighted component — `tech_points`, `analytical_points`, `aseptic_points` and `operator_points` — plus `counted_operator_count`, the operator population the variant actually counted, and `assessed_at`, the logical-clock instant of the assessment. The score is an integer between 0 and 100 and it draws only on the project row, the suite named by `primary_suite_id`, and that suite's operator qualifications; no batch and no deviation participates. Both variants weight the same four concerns — technology transfer up to 30 points, analytical method transfer up to 25, aseptic qualification up to 25, and the operator roster up to 20 — and both compute the operator component identically: 20 points when the counted operator population is at least two, and otherwise 20 multiplied by that count divided by two, rounded half up to a whole number. The operator component is the only rounded term and it is rounded before the four components are summed.

The `INTAKE_FORECAST` variant is the commercial view used while a project is still being sold, and it is generous with anything in flight. Technology transfer scores the full 30 points when `tech_transfer_stage` is `ENGINEERING_RUN` or `COMPLETE`, 15 points at `GAP_ASSESSMENT`, and 0 at `NOT_STARTED`. Analytical method transfer scores the full 25 points when `analytical_method_transfer_status` is `IN_TRANSFER` or `VALIDATED`, and 0 at `NOT_STARTED`. Aseptic qualification scores the full 25 points whenever the suite's `aseptic_qualification_status` is `QUALIFIED`, and `media_fill_valid_until` is ignored completely — a lapsed simulation costs this variant nothing. The counted operator population is every qualification of that suite whose `status` is `PENDING`, `QUALIFIED` or `LAPSED`, with `expires_on` ignored; only `REVOKED` records are excluded.

The `GMP_AUDIT` variant is the inspection view and it credits only what is effective as of the logical clock. Technology transfer scores by an explicit table: 0 points at `NOT_STARTED`, 0 points at `GAP_ASSESSMENT`, 15 points at `ENGINEERING_RUN` and 30 points at `COMPLETE`. Analytical method transfer scores 0 at `NOT_STARTED`, 12 at `IN_TRANSFER` and 25 at `VALIDATED`. Aseptic qualification scores 0 when the suite's `aseptic_qualification_status` is anything other than `QUALIFIED`; 10 points when it is `QUALIFIED` but `media_fill_valid_until` is null or falls earlier than the current logical clock; and the full 25 points only when it is `QUALIFIED` with a `media_fill_valid_until` at or after the clock. The counted operator population is only those qualifications whose `status` is `QUALIFIED` and whose `expires_on` is at or after the logical clock. The gap between the two views is the point of having both: a project at `ENGINEERING_RUN` with an `IN_TRANSFER` method, a `QUALIFIED` suite whose simulation validity has lapsed, and a roster of one effective operator plus one lapsed and one pending, scores 100 under `INTAKE_FORECAST` and 47 under `GMP_AUDIT`.

The second computed read exposes the two releasable-unit variants side by side so that a sponsor or a Qualified Person can see exactly where the difference came from. Addressed at a batch, it returns `batch_order_id`, the `filled_unit_count` both variants start from, the forward-looking `expected_reject_units` derived from the sponsor's historical rate, the `actual_visual_reject_units` actually recorded by visual inspection controls, the `destructive_total_units` both variants subtract, the `quarantined_unit_count` only the final variant subtracts, the stored `provisional_releasable_units` and `final_releasable_units`, and `variant_delta_units`, which is `provisional_releasable_units` minus `final_releasable_units` — positive whenever the sponsor's declared history flattered the batch. This read computes nothing persistent and mutates nothing.

## 4. Endpoint Definitions

The table below is the complete surface of the API. Every path is rooted at the server origin with no version or namespace prefix, and `{id}` is always the UUID primary key of the addressed resource. Every endpoint that brings a new resource into existence answers `201 Created` on success — that is `POST /client-projects`, `POST /filling-suites`, `POST /media-fills`, `POST /personnel-qualifications`, `POST /component-lots`, `POST /batch-orders`, `POST /component-reservations`, `POST /in-process-checks`, `POST /em-samples`, `POST /deviations`, `POST /batch-record-reviews`, `POST /audit-engagements` and `POST /batch-orders/{id}/qp-release`, the last of which appends a new immutable decision record. Every other endpoint — every read, every list, every state-transition action that mutates an existing resource, and the clock control — answers `200 OK` on success. Transition endpoints return the updated principal resource in `data`; the two computed reads and the two sub-resource lists return the computed or listed payload described in section 3.
