# Public Land Grazing Permit Administration API — Product Requirements Document

## 1. Introduction

Federal rangeland is a finite forage resource that the agency must allocate, meter, bill and defend, year after year, against a shifting backdrop of drought, wildfire, ecological decline and litigation. The unit of that allocation is the **animal unit month** (AUM) — the forage one mature cow consumes in a month — and every allotment in the inventory carries a permitted AUM ceiling that must never be over-committed. Around that ceiling sits a dense administrative apparatus: qualifying base property that entitles a rancher to preference, term permits that carry that preference, annual operating instructions that commit a single grazing year's slice of the ceiling, actual-use reports that reconcile what was planned against what was grazed, bills computed at the statutory grazing fee rate, monitoring that measures whether the land is meeting rangeland health standards, emergency orders that shrink the ceiling underneath commitments that have already been made, and an appeals process that can freeze or unwind any of it.

This service is the system of record for that apparatus. Field staff author the technical record; deciding officials sign it; an independent adjudicator hears challenges to it; and permittees report their use and pay their bills against it. The recurring engineering challenge is not any single workflow but the interaction between them: an emergency drought order issued in July reduces an allotment's effective capacity, which re-authorizes every operating instruction already in force for that year, which supersedes the unpaid bills raised from those instructions, which moves each affected rancher's outstanding balance, which in turn re-derives whether their permits are current or delinquent. Reversing that same order on appeal must restore every one of those figures exactly, with no arithmetic drift and no compounding.

Accordingly, this document specifies the whole chain and not merely its endpoints. It fixes the arithmetic (including where a value is floored, where it is rounded, and in what order), the state machines and their side effects, the order in which a malformed or unauthorized or premature request is rejected, and the concurrency rule that protects an allotment record from being written against a stale view of its capacity. Where a rule is stated in one section and reinforced in another, the two statements agree; where a number appears, it is exact.

## 2. Global Specifications & System-Wide Principles

Resources are mounted at the root of the service; there is no version or product path segment in front of the collection names. A path is matched with or without a trailing slash, so `/allotments` and `/allotments/` name the same resource. A request for a path this document does not define is answered with `error_id` `ERR_NOT_FOUND` and HTTP 404, and a request that names a defined path with a method that path does not support is answered with `ERR_METHOD_NOT_ALLOWED` and HTTP 405; both carry the ordinary error envelope of §2.2.

### 2.1. Actors, Identity Headers and Role-Based Access Control

Every request — reads included — must carry two headers. `X-User-ID` identifies the acting individual or system identity, and `X-User-Role` names the capacity in which that individual is acting. If `X-User-ID` is absent or empty — a header holding nothing but whitespace counts as empty — the request fails with `ERR_UNAUTHORIZED` (HTTP 403). The same code and status are returned when `X-User-Role` is absent or empty, when it holds a string that is not one of the five roles named below, when the role it names is not among the roles authorised for the requested operation, and when a rancher reaches for a record that belongs to somebody else. Resolution against a persisted record is demanded of the `Permittee` role alone: a `Permittee` whose `X-User-ID` is not the `id` of a registered permittee fails this gate, while the four other roles carry opaque identifiers that are never looked up in any collection. Within this one gate the conditions are evaluated in the order just given — `X-User-ID` presence, `X-User-Role` presence, role recognisability, role authorisation, then permittee resolution — so a caller who omits both headers is told about `X-User-ID` first.

Five roles exist, spelled exactly as follows: `Permittee`, `RangeSpecialist`, `AuthorizedOfficer`, `AppealsAdjudicator`, and `SystemAdmin`.

A `Permittee` is the rancher or operator who holds — or is applying for — grazing preference. When `X-User-Role` is `Permittee`, `X-User-ID` is the `id` of the acting `Permittee` record itself; ownership checks on any resource that references a permittee compare that resource's permittee reference to `X-User-ID`. Concretely, a `Permittee` actor may read and act only on its own permits, its own annual operating instructions, the use records beneath them, its own bills, the trespass incidents attributed to it and its own appeals; touching another permittee's row is the same `ERR_UNAUTHORIZED` failure as presenting an unknown identity. Appeal filing is exclusive to this role, and the `appellant_permittee_id` carried in the filing payload must equal the acting `X-User-ID` — the server never infers the appellant silently, and a mismatch is `ERR_UNAUTHORIZED`. A `Permittee` also reports actual use on its own scheduled windows (shared with `RangeSpecialist`) and records payments against its own bills (shared with `AuthorizedOfficer`).

A `RangeSpecialist` is field and resource staff who author the technical record: rangeland health assessments, decision documents, trespass detections and range improvement proposals, plus the drafting and scheduling of annual operating instructions. This role authors but never approves. When `X-User-Role` is `RangeSpecialist`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a workflow calls for authorship attribution — as `author_user_id` on a rangeland health assessment and as `authoring_officer_id` on a permit decision — but never compares it to any entity's `id`.

An `AuthorizedOfficer` is the deciding official: this role registers allotments, pastures, permittees and base properties, issues and renews and transfers permits, issues and reduces and voids operating instructions, signs and effectuates decisions, issues and lifts closure orders, bills trespass, and approves and allocates range improvement projects. When `X-User-Role` is `AuthorizedOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as `deciding_officer_id` on a decision it signs and as `issuing_officer_id` on a closure order it issues, but never compares it to any entity's `id`.

An `AppealsAdjudicator` is the independent administrative judge who dockets and decides appeals. When `X-User-Role` is `AppealsAdjudicator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as `adjudicator_id` on the case it dockets, but never compares it to any entity's `id`.

A `SystemAdmin` exists solely to drive the service's logical clock and holds no business authority whatsoever. When `X-User-Role` is `SystemAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is not recorded on any resource.

Read access is broad: `Permittee`, `RangeSpecialist`, `AuthorizedOfficer` and `AppealsAdjudicator` may all call every retrieval and listing operation, subject to the ownership narrowing described above for `Permittee`. Write access is narrow and is enumerated per operation in §4. Because the acting capacity comes from `X-User-Role` while the acting person comes from `X-User-ID`, one operator identifier may legitimately present under two different roles — a small field office where the same person is both the range specialist and an authorised officer is an ordinary arrangement — and the segregation-of-duties rules in §2.10 therefore compare identifiers, never roles.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` and continues with exactly 20 further characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`, so the whole string is 24 characters long.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits and a trailing `Z`. It is read from the host's real-time clock, **not** from the logical clock of §2.5, and successive stamps minted by a running process never repeat and never move backwards.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes, and the 5xx response an unexpected server fault produces) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every listing operation is paginated by the same two query parameters. `limit` controls page size: it defaults to `10` when omitted, may be no smaller than `1`, and may be no larger than `100`. `offset` controls the starting position: it defaults to `0` and may be no smaller than `0`. A `limit` or `offset` outside those bounds is a request-shape failure and is rejected with `ERR_VALIDATION` (HTTP 400). A parameter that is omitted altogether, or sent as an empty string, takes its default; surrounding whitespace around a value is ignored; and a value that is not a whole number at all — `abc`, `2.5`, or a string of nothing but spaces — is that same `ERR_VALIDATION` failure. `limit` is the only one of the two with an upper bound: `offset` may be arbitrarily large, and an `offset` at or beyond `total_count` is a perfectly legitimate request that returns an empty `data` array with `has_more` false. Both parameters are validated ahead of the identity gate of §2.1 on every listing operation, so a malformed `limit` presented with no headers at all still reports `ERR_VALIDATION` rather than `ERR_UNAUTHORIZED`.

Listing responses carry `response_type` of `"array"` and place the array of resource objects directly in `data`. The `meta` object of a listing response additionally carries `limit` (the effective page size), `offset` (the effective starting position), `total_count` (the number of records matching the filters before pagination is applied) and `has_more` (true exactly when records matching the filters remain beyond the current page). Single-resource responses carry `response_type` of `"object"` and omit those four pagination fields from `meta`.

Unless a listing operation's description in §4 states otherwise, results are ordered by `created_at` ascending — oldest record first. The listing of an allotment's pastures is presented in rotation order, that is by `sequence_order` ascending. Because the timestamps of §2.4 are strictly increasing within a running process, that default ordering is total; should two records nevertheless carry the same `created_at`, the earlier-inserted record still sorts first. All other filter parameters named in §4 narrow the result set by exact equality on the named field, and combining several filters narrows by conjunction. Filtering is applied after ordering and never disturbs it. A filter parameter that is omitted or sent as an empty string is ignored entirely. A filter value that cannot be read as the filtered field's type — a non-numeric value for an integer filter such as `grazing_year` or `assessment_year`, or anything other than `true`, `false`, `1` or `0` (compared case-insensitively, whitespace trimmed) for a boolean filter such as `rest_required` or `stay_granted` — is **not** a validation failure: it simply matches no record, and the response is an empty `data` array with `total_count` 0 and `has_more` false. Every other filter compares the raw query string to the stored value verbatim, so an identifier filter naming a row that does not exist likewise returns an empty page rather than a 404.

### 2.4. Resource Identity, Timestamps and Record Versioning

Every persisted resource in this service carries four common properties. `id` is a server-minted UUID string in the canonical lower-case hyphenated 36-character form, unique across the whole service and never containing a type prefix or any other decoration; clients never supply it, and a client-supplied `id` in a request body is ignored rather than honoured. `created_at` is the ISO 8601 UTC instant at which the resource was first persisted, rendered with exactly three fractional-second digits and a trailing `Z`, and taken from the host's real-time clock rather than from the logical clock of §2.5. These stamps are strictly increasing across a running process: no two resources ever share a `created_at`, and a mutation always writes an `updated_at` strictly later than the value it replaces. `updated_at` is the ISO 8601 UTC instant of the most recent mutation of that resource, in the same format, and equals `created_at` on a resource that has never been mutated since creation. `version` is an integer that starts at 1 when the resource is created and increases by exactly 1 on every mutation of that resource, whether the mutation was requested directly by a client or applied as a side effect of an operation on some other resource. No entity in this service is exempt: allotments, pastures, permittees, base properties, grazing permits, annual operating instructions, pasture use records, grazing bills, rangeland health assessments, permit decisions, appeal cases, closure orders, trespass incidents and range improvement projects all expose `id`, `created_at`, `updated_at` and `version`.

Because `version` moves on side-effect mutations as well as direct ones, an allotment's `version` advances on exactly the following events and on no others: when a closure order over it is issued, lifted, or expired by a clock advance; when a health assessment on it is finalized with a concurrence; when a decision document is authored against it; when a decision on it is made effective or vacated; and when an annual operating instruction on one of its permits is issued. The last two of those need not rewrite any allotment field to count — instruction issuance writes none at all, and a suspension or cancellation decision taking effect writes none either — yet each bumps the version once for the event. The converse is equally firm: an event that moves only the allotment's *derived* capacity ledger of §2.9 is not an allotment mutation, so approving non-use, voiding an operating instruction, transferring a permit, issuing a permit, and raising, paying or voiding a bill all leave `version` exactly where it was. §2.9 states the same rule from the ledger's side, and §2.7 turns this behaviour into a concurrency guarantee.

### 2.5. The Logical Range Calendar

The service does not read the host's wall clock for business purposes. It maintains a **logical clock**, an ISO 8601 UTC instant that begins at exactly `2026-08-01T00:00:00Z` at server start and thereafter moves only when a `SystemAdmin` sets it. The setting payload carries a single field, `current_utc`, holding the new instant; the requested value must be strictly after the present logical clock value, and a value equal to or earlier than the present one is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422). A successful clock set returns 200 with an empty `data` object.

Everything date-derived in this specification reads the logical clock: the calendar date on which a bill becomes due, the `effective_date` stamped on a decision when it takes effect, and each allotment's `current_grazing_year`, which is the calendar year (in UTC) of the logical clock at the moment of evaluation. Advancing the clock is therefore an eventful operation, and it has exactly three consequences, applied in this fixed order after the new instant has been stored: bill delinquency as §3.6 describes, then closure-order expiry with the reallocation cascade each expiry drags behind it as §3.10 describes, then permit term expiry as §3.3 describes. The order is observable, because a bill that the first sweep has just carried to `DELINQUENT` is still a candidate for the supersession the second sweep performs.

### 2.6. Path Resolution and the Order in Which a Request Is Rejected

Nested paths are resolved strictly left to right, so the outermost missing identifier wins: a request naming an allotment that does not exist and, beneath it, a pasture that also does not exist, reports the allotment failure. Each entity has its own not-found code: an allotment yields `ERR_ALLOTMENT_NOT_FOUND`, a pasture `ERR_PASTURE_NOT_FOUND`, a permittee `ERR_PERMITTEE_NOT_FOUND`, a base property `ERR_BASE_PROPERTY_NOT_FOUND`, a grazing permit `ERR_PERMIT_NOT_FOUND`, an annual operating instruction `ERR_AOI_NOT_FOUND`, a pasture use record `ERR_USE_RECORD_NOT_FOUND`, a grazing bill `ERR_BILL_NOT_FOUND`, a rangeland health assessment `ERR_ASSESSMENT_NOT_FOUND`, a permit decision `ERR_DECISION_NOT_FOUND`, an appeal case `ERR_APPEAL_NOT_FOUND`, a closure order `ERR_CLOSURE_ORDER_NOT_FOUND`, a trespass incident `ERR_TRESPASS_NOT_FOUND` and a range improvement project `ERR_PROJECT_NOT_FOUND`. All fourteen carry HTTP 404. Foreign keys sent in a request **body** are resolved with the same fourteen-code mapping, in the order in which the fields are listed for that operation in §4's request description and in §3's narrative.

When a single request violates more than one rule, exactly one error is returned, and which one is fully determined. The checks below are evaluated in ascending order of the numbers given, the first violated check short-circuits the request, and its code is the code the client sees. This ordering is normative — a client that fixes the reported problem and retries will then see the next-highest violated check, and never the reverse.

1. **Request shape** — `ERR_VALIDATION`, HTTP 400. Every field marked as required for the operation is present and non-null; every enumerated field holds one of its declared members; every field whose name ends in `_aums`, `_cents`, `_count`, `_days`, together with `acres`, is an integer that is not negative, with head counts (`planned_head_count`, `actual_head_count`, `head_count`) and `unauthorized_days` required to be at least 1; every field whose name ends in `_pct` is a number between 0.0 and 1.0 inclusive; every field whose name ends in `_score` is an integer between 0 and 100 inclusive; `observed_utilization_pct` is an integer between 1 and 100 inclusive; date-valued fields are ISO 8601 calendar dates in `YYYY-MM-DD` form; the allotment's `season_start` and `season_end` are `MM-DD` strings with no year; and instant-valued fields (`detected_at`, `current_utc`) are ISO 8601 UTC instants with a trailing `Z` — the accepted spellings are `YYYY-MM-DDTHH:MM`, `YYYY-MM-DDTHH:MM:SS` and `YYYY-MM-DDTHH:MM:SS` followed by a fractional part, each closed by the literal `Z` and nothing else, so a numeric offset such as `+00:00`, a missing `Z` and a non-string value are all `ERR_VALIDATION`, and an instant accepted in a shorter spelling is stored re-rendered to exactly three fractional digits. Six cross-field shape rules join this check: on a range improvement project proposal, `agency_share_pct` and `permittee_share_pct` must add up to exactly 1.0; on a stocking-adjustment decision, both `assessment_id` and `adjustment_pct` are required and `adjustment_pct` must be greater than 0 and no greater than 0.9; on a decision of any other `decision_type`, `permit_id` is required instead and `adjustment_pct` must be omitted or null; on a closure order, `reduction_pct` is required for a drought reduction and must be greater than 0.0 and no greater than 0.9; a wildfire closure or a full closure must either omit `reduction_pct` altogether or send exactly 1.0 — the server records 1.0 in either case; and on a rangeland health assessment whose `monitoring_method` is `UTILIZATION_MAPPING`, `observed_utilization_pct` must be supplied and non-null even though that field is optional for every other method. Each of these cross-field rules is evaluated ahead of the identity gate of priority 3, so a request that trips one of them reports `ERR_VALIDATION` even when its credentials are also wrong. This check applies to every write operation, and the `limit`/`offset` clause of §2.3 extends it to every listing operation. Four further conventions fix which shape failure a client sees. A write request that carries no body at all is read as an empty JSON object, so the first required field of the operation is what the message names; a body that is not valid JSON, or that parses to anything other than a JSON object, is this same failure. The declared fields of an operation are checked in the order this document lists them, so when several are malformed at once the first-listed one is reported, and that is the same order priority 6 uses to resolve body foreign keys. A field that is present but `null` fails exactly as an absent required field does, unless this document expressly permits null for it; an optional field that is omitted takes its documented default. And the JSON types are read leniently in exactly one direction: where an integer is required a JSON number with a zero fractional part such as `5.0` is accepted, while a boolean is never accepted for an integer or a number field, nor a number for a boolean field; a string field is rejected when it is empty or holds nothing but whitespace.
2. **Date-range coherence** — `ERR_INVALID_DATE_RANGE`, HTTP 400, checked before any record is looked up. A permit's `term_start_date` must be strictly before its `term_end_date`; an operating instruction's `season_start_date` must be on or before its `season_end_date`; a use record's `planned_entry_date` must be strictly before its `planned_exit_date` and, when actual use is reported, its `actual_entry_date` must be strictly before its `actual_exit_date`, because a grazing window is half-open and a zero-length window is never valid; and a closure order's `effective_start_date` must be on or before its `effective_end_date`. This check applies to permit application, permit renewal, permit transfer, operating-instruction creation, use-record scheduling, actual-use reporting and closure-order issuance. A range whose earlier or later endpoint is absent or null is not examined here at all, so an optional window is tested only once both of its dates have been supplied.
3. **Identity and role** — `ERR_UNAUTHORIZED`, HTTP 403, on every operation without exception. The rules are those of §2.1: `X-User-ID` present, non-empty and resolvable; the acting role listed for the operation; and a `Permittee` actor confined to rows belonging to its own permittee record, including the requirement that a filed appeal's `appellant_permittee_id` equal the acting `X-User-ID`.
4. **Segregation of duties** — `ERR_SEGREGATION_OF_DUTIES`, HTTP 403, on assessment review, decision signature and appeal decision, exactly as specified in §2.10.
5. **Path-parameter existence** — HTTP 404 with the entity-specific code, resolved left to right as described at the top of this subsection. Applies to every operation that carries a path parameter.
6. **Body foreign-key existence** — HTTP 404 with the entity-specific code, in the declared field order. Applies to every write operation that carries foreign keys in its body.
7. **Optimistic concurrency** — `ERR_STALE_ALLOTMENT_VERSION`, HTTP 412, on authoring a permit decision, exactly as specified in §2.7. It is deliberately checked after existence and before any state or business rule, so a stale version on a request that would have failed a later business check still surfaces as the concurrency error.
8. **Transition legality** — HTTP 409 with the entity-specific state code. The subject record must be in a state from which the requested transition is declared, and every same-entity precondition of that transition must hold. Because §3.3 declares transfer to be the `ISSUED → TRANSFERRED` transition, a transfer whose source permit sits in any other `permit_status` fails here, at this priority, with `ERR_PERMIT_STATE_INVALID`, ahead of the posture, standards, ownership and preference-chain checks numbered below; renewal is the deliberate exception, its own source-state failure being reported at priority 15 instead. A grazing permit yields `ERR_PERMIT_STATE_INVALID`, an operating instruction `ERR_AOI_STATE_INVALID`, a use record `ERR_USE_RECORD_STATE_INVALID`, a bill `ERR_BILL_STATE_INVALID`, an assessment `ERR_ASSESSMENT_STATE_INVALID`, a decision `ERR_DECISION_STATE_INVALID`, an appeal `ERR_APPEAL_STATE_INVALID`, a closure order `ERR_CLOSURE_ORDER_STATE_INVALID`, a trespass incident `ERR_TRESPASS_STATE_INVALID` and a project `ERR_PROJECT_STATE_INVALID`. This priority also covers the cross-entity state preconditions that name the subject's own parent chain: drafting an operating instruction requires the named permit to be `ISSUED`, so a permit in `PENDING_REVIEW`, `SUSPENDED`, `CANCELLED`, `EXPIRED` or `TRANSFERRED` yields `ERR_PERMIT_STATE_INVALID`; scheduling a use record requires the owning instruction to be in `DRAFT`; reporting actual use requires it to be in `ISSUED`; and paying a bill requires the bill to be in `ISSUED` or `DELINQUENT`. Applies to every action operation and every nested create.
9. **Rangeland posture gate** — `ERR_ALLOTMENT_CLOSED`, HTTP 409. When the governing allotment's `allotment_status` is `CLOSED`, no permit may be issued, renewed or transferred onto it, no operating instruction may be created or issued for any of its permits, no use record may be scheduled on such an instruction, and no range improvement project on it may be approved. Those are the seven operations this gate guards. A `RESTRICTED` allotment still permits all seven — only its reduced capacity applies.
10. **Rangeland standards gate** — `ERR_HEALTH_STANDARDS_NOT_MET`, HTTP 409, on permit issuance, permit renewal and permit transfer. A permit may not be issued, renewed or transferred onto an allotment whose `health_determination` is `NOT_MEETING` unless a permit decision of `decision_type` `STOCKING_ADJUSTMENT` on that allotment has already reached `decision_status` `EFFECTIVE`.
11. **Environmental review gate** — `ERR_ENVIRONMENTAL_REVIEW_INCOMPLETE`, HTTP 409, on decision signature only. Signing requires `nepa_status` to be `COMPLETE` and `nepa_findings_summary` to be non-empty; a decision whose `nepa_level` is `EA` or `EIS` additionally requires a `rationale` of at least 20 characters.
12. **Appeal stay gate** — `ERR_DECISION_STAYED`, HTTP 409, on two operations: making a decision effective, and authoring a new decision. A decision whose `decision_status` is `STAYED` may not be made effective, and while that stay stands the allotment it targets may not receive a further decision of the same `decision_type`. The stay is released only when the appeal case leaves `FILED` and `UNDER_REVIEW`. On making a decision effective this gate is the one deliberate departure from the ascending order: the stay is tested **before** the priority 8 requirement that the decision be `FINAL`, so a `STAYED` decision reports `ERR_DECISION_STAYED` and never `ERR_DECISION_STATE_INVALID`, while the reserved-identity rule of §2.10 still precedes both.
13. **Base-property ownership** — `ERR_BASE_PROPERTY_NOT_OWNED`, HTTP 422, on permit application, permit renewal and permit transfer. The `base_property_id` carried by the request must belong to the permittee who will hold the resulting permit. On a transfer the transferee's own base property is required, and reusing the transferor's base property is precisely this violation.
14. **Pasture locality** — `ERR_PASTURE_NOT_IN_ALLOTMENT`, HTTP 422, on use-record scheduling. The `pasture_id` must name a pasture whose `allotment_id` equals the allotment of the instruction's permit.
15. **Preference chain** — `ERR_PREDECESSOR_PERMIT_INVALID`, HTTP 422, on permit renewal and permit transfer. On either operation the permit named by the path must not already have a successor (no other permit may carry the same `predecessor_permit_id`). On renewal it must additionally be in `permit_status` `ISSUED`, and the new `term_start_date` must fall on or after the predecessor's `term_end_date`. On transfer that source-state requirement is instead the priority 8 transition-legality failure `ERR_PERMIT_STATE_INVALID`, so this code covers only the successor clash there.
16. **Preference qualification** — `ERR_INSUFFICIENT_QUALIFIED_AUMS`, HTTP 422, on permit application, permit issuance, permit renewal and permit transfer. On permit application the `requested_aums` carried by the payload must not exceed the `qualified_aums` of the named base property; a permittee with no base property of the required kind cannot hold preference at all. On permit issuance, permit renewal and permit transfer the same comparison is re-run against the permit's **stored** `permitted_aums` and never against a payload figure — renewal and transfer both send a `requested_aums` that this check ignores — which is why the issuance transition has an error mapping even though a conforming application can never fail it.
17. **One instruction per permit-year** — `ERR_DUPLICATE_AOI_FOR_YEAR`, HTTP 409, on operating-instruction creation. At most one instruction per permit and `grazing_year` may exist in an `aoi_status` other than `VOIDED`; voiding an instruction frees the slot so that a replacement may be created for the same year.
18. **One assessment per allotment-year** — `ERR_DUPLICATE_ASSESSMENT_FOR_YEAR`, HTTP 409, on assessment creation and on assessment review. At most one assessment per allotment and `assessment_year` may reach `FINALIZED`, and at most one may sit in `DRAFT` or `FIELD_REVIEW` at a time. The two clauses are not both checked on both operations: creation checks both, while review checks only the `FINALIZED` clause, and it checks it only on a `CONCUR` outcome.
19. **Rotation sequence integrity** — `ERR_PASTURE_SEQUENCE_CONFLICT`, HTTP 409, on pasture creation. `sequence_order` is unique within its allotment and the sequence must be dense from 1: creating position N requires that position N−1 already exists on that allotment.
20. **Rotation requirement** — `ERR_ROTATION_REQUIREMENT_NOT_MET`, HTTP 422, on operating-instruction issuance. The instruction's `distinct_pasture_count` must be at least the allotment's `required_pasture_rotation_count`, and every pasture of that allotment whose `rest_required` is true must be absent from the instruction's use records.
21. **Non-use ceiling** — `ERR_NONUSE_LIMIT_EXCEEDED`, HTTP 409, on permit renewal. A permit whose `consecutive_nonuse_years` has reached three may not be renewed, because the preference has lapsed; at two the renewal still succeeds. Only `RESOURCE_CONSERVATION` and `PERSONAL_CONVENIENCE` years count toward the run, so `DROUGHT` and `WILDFIRE` non-use never bars renewal.
22. **Appeal remand ceiling** — `ERR_APPEAL_REMAND_LIMIT_EXCEEDED`, HTTP 409, on appeal decision. An appeal may be remanded at most twice; a third remand outcome is refused and the adjudicator must instead affirm, reverse or dismiss.
23. **Assessment remand ceiling** — `ERR_ASSESSMENT_REMAND_LIMIT_EXCEEDED`, HTTP 409, on assessment review. A review that sends the assessment back to `DRAFT` may happen at most twice per assessment; the third such rejection is refused, and the reviewer must concur or the assessment must be abandoned.
24. **Use-report completeness** — `ERR_ACTUAL_USE_INCOMPLETE`, HTTP 409, on use-report acceptance. The instruction must have at least one use record, and no record may still be in `record_status` `SCHEDULED`.
25. **Season of use** — `ERR_SEASON_OF_USE_VIOLATION`, HTTP 422, on operating-instruction creation, use-record scheduling and actual-use reporting. A use record's planned window, treated as half-open from `planned_entry_date` up to but excluding `planned_exit_date`, must fall entirely inside the closed interval from its instruction's `season_start_date` to its `season_end_date`; that instruction season must itself fall inside the allotment's recurring `season_start`-to-`season_end` window resolved against the instruction's `grazing_year`, which is checked once, at instruction creation, and is not re-checked when a use record is scheduled beneath it; and an actual window reported outside the instruction season is the same violation. The planned and reported tests are deliberately not symmetric, because only the planned window is half-open: a `planned_exit_date` may land one day past `season_end_date` and still be inside the season, whereas the reported window is tested with both endpoints inclusive, so `actual_entry_date` must be on or after `season_start_date` and `actual_exit_date` must be on or before `season_end_date` itself.
26. **Closure-order spacing** — `ERR_CLOSURE_ORDER_OVERLAP`, HTTP 409, on closure-order issuance. A new order's closed interval from `effective_start_date` through `effective_end_date` must neither overlap, nor begin within seven days after the end of, any order on the same allotment that is still in `order_status` `ACTIVE`. Formally the new order is refused whenever its `effective_start_date` falls on or before the existing order's `effective_end_date` plus seven days; a start on the eighth day after that end is accepted. Both endpoints of both intervals are inclusive, so intervals that merely touch do overlap.
27. **Clock monotonicity** — `ERR_CLOCK_NOT_MONOTONIC`, HTTP 422, on the clock-setting operation, as described in §2.5.
28. **Debt gate** — `ERR_OUTSTANDING_BALANCE`, HTTP 402, on permit issuance, permit renewal, permit transfer and operating-instruction creation. None of those four may proceed while the permittee who would hold the permit has an `outstanding_balance_cents` greater than zero, evaluated against the live permittee aggregate. On a transfer the check runs against the **transferee**, not the transferor.
29. **Pasture capacity** — `ERR_PASTURE_CAPACITY_EXCEEDED`, HTTP 422, on use-record scheduling and on actual-use reporting. Evaluated as a temporal aggregate, as specified in §3.4.
30. **Allotment capacity** — `ERR_ALLOTMENT_CAPACITY_EXCEEDED`, HTTP 422, on operating-instruction creation, operating-instruction issuance, permit issuance, permit renewal and permit transfer. At instruction creation the requested `authorized_aums` must not exceed the allotment's `open_aums` at that moment, and the same comparison is re-run at issuance against the then-current `open_aums`, so a capacity that shrank between draft and issue makes the issue fail even though the draft was accepted. At permit issuance, renewal and transfer the same rule applies to the permit's `permitted_aums`, which must not exceed `open_aums` at that moment.
31. **Non-use bounds** — `ERR_NONUSE_EXCEEDS_AUTHORIZED`, HTTP 422, on non-use approval. The requested `nonuse_aums` must be at least 1 and no greater than the instruction's current `authorized_aums`, and a `nonuse_reason` of `DROUGHT` or `WILDFIRE` is accepted only while a closure order of the matching `order_type` is `ACTIVE` on the allotment.
32. **Overpayment** — `ERR_OVERPAYMENT`, HTTP 422, on payment recording. The `amount_cents` must be at least 1 and must not exceed the bill's `total_amount_cents` less its `amount_paid_cents`; overpayment is refused outright rather than credited.
33. **Cost-share preconditions** — `ERR_PROJECT_STATE_INVALID`, HTTP 409, on cost-share allocation. The project's `total_cost_cents` must be at least 1 and the project must be in `project_status` `APPROVED`. An allotment with no `ISSUED` permits is expressly **not** an error here — see §3.12.

### 2.7. Optimistic Concurrency on Allotment Writes

Authoring a permit decision is the one write in this service that is guarded by optimistic concurrency, because it is the one write that acts on an allotment's contested capacity while superseding a sibling document. A decision-authoring request must therefore carry `expected_allotment_version`, a non-optional integer field holding the `version` of the target allotment as the client last observed it. If that value does not equal the allotment's current `version`, the request is rejected with `ERR_STALE_ALLOTMENT_VERSION` and HTTP 412, and nothing is written.

The guarantee this buys is concrete. A newly authored draft decision legitimately vacates any earlier decision of the same `decision_type` on the same allotment that is still in `DRAFT` or `PROPOSED`. Without the version check, a specialist working from an out-of-date view of the allotment could overwrite a colleague's pending document while the allotment's capacity, posture or health determination had already moved underneath them — because a closure order was issued, an assessment was finalized with a concurrence, or an earlier decision was authored, each of which advances the allotment's `version`. The version comparison reduces that whole class of hazard to a single stale-read rejection.

No other operation in this service accepts a version field. Requests to issue, renew or transfer a permit, to create, issue, reduce, accept or void an operating instruction, to schedule or report a use record, to pay or void a bill, to submit or review an assessment, to complete environmental review, to sign or effectuate a decision, to file, docket or decide an appeal, to issue or lift a closure order, to bill trespass, or to approve or allocate a project carry no expected-version field at all, and any write-write hazard they present is expressed instead as a state precondition in §2.6 and §3. Underneath both, the service serialises requests: one request runs to completion before the next begins, so a version check and the write it guards are indivisible, no two requests ever interleave their mutations of the same record, and a cascade is never observed half-applied.

### 2.8. Animal-Unit-Month Arithmetic, Rounding and Money Precision

Three numeric conventions run through the whole specification, and they are not interchangeable.

**Rounding.** Wherever this document says a value is *rounded*, the method is round-half-up: a value exactly halfway between two representable results goes to the larger magnitude. Wherever it says a value is *floored*, the value is truncated downward to the next whole number. Wherever it says a value is taken to a *ceiling*, it is raised to the next whole number, and a value that is already whole is unchanged. Capacity arithmetic floors; forage quantities round; the unauthorized-use quantity is the one place a ceiling is used.

**Fractional AUMs.** A quantity of grazed or scheduled forage is a number carried to exactly 2 decimal places: `planned_aums`, `actual_aums`, `planned_aums_total`, `actual_aums_total`, `scheduled_aums`, `unauthorized_aums` and a bill's `billed_aums` all follow that rule. Rounding to 2 decimal places happens once, per record, at the moment the record's quantity is computed; aggregates are then formed by adding the already-rounded per-record values and are **not** rounded again. Capacity quantities, by contrast, are whole AUMs: `total_permitted_aums`, `effective_capacity_aums`, `allocated_aums`, `open_aums`, `permitted_aums`, `authorized_aums`, `authorized_aums_at_issue`, `nonuse_aums`, `billable_aums`, `pasture_aum_capacity`, `carrying_capacity_aums` and `qualified_aums` are all integers.

**Adjustment fractions.** A stocking or cost-share fraction is a number carried to exactly 4 decimal places and rounded to that width: `stocking_adjustment_pct`, `adjustment_pct`, `pre_decision_adjustment_pct`, `reduction_pct`, `recommended_reduction_pct`, `agency_share_pct` and `permittee_share_pct`. A health score is carried to 2 decimal places: `composite_score`.

**Money.** All monetary amounts are integer cents and are never fractional: `outstanding_balance_cents`, `base_amount_cents`, `admin_fee_cents`, `penalty_amount_cents`, `total_amount_cents`, `amount_paid_cents`, `amount_cents`, `total_cost_cents`, `permittee_share_cents`, `allocated_share_cents` and `fee_rate_cents_per_aum`. Two amounts may be negative and no others: an `ADJUSTMENT_CREDIT` bill carries a negative `total_amount_cents`, and a permittee's `outstanding_balance_cents` may be negative when credits exceed charges. Rounding a money figure is done once, at the step this document names, and the result is an integer number of cents.

Every field named anywhere in this subsection is rendered in a JSON response as a bare number and never as a quoted string. The decimal-place rules above therefore constrain the *value* a field may take, not the textual width it is printed at: a 2-decimal forage quantity that happens to land on a whole number renders as `40.0` rather than `40.00`, a 4-decimal fraction of four tenths renders as `0.4`, and money and whole-AUM capacity fields render as bare integers with no decimal point at all. A quantity that is genuinely absent renders as JSON `null` — `actual_aums` before its leg is reported, and `composite_score` on an assessment that has not been finalized — rather than as 0.

### 2.9. The Allotment Capacity Ledger and Its Conservation Invariants

Each allotment publishes a live three-line capacity ledger that must be recomputed after every event that can move it, and that is the single arbiter of whether a further commitment fits.

The first line is **effective capacity**: `effective_capacity_aums` is the allotment's `total_permitted_aums` multiplied by one minus its `stocking_adjustment_pct`, with the product floored to a whole AUM. With no adjustment in force the effective capacity equals the permitted ceiling exactly. The second line is **allocation**: `allocated_aums` is the sum, over every annual operating instruction whose permit belongs to this allotment, whose `grazing_year` equals the allotment's `current_grazing_year`, and whose `aoi_status` is one of `ISSUED`, `USE_REPORTED`, `BILLED` or `CLOSED`, of that instruction's `authorized_aums` less its `nonuse_aums`. Instructions in `DRAFT` or `VOIDED` contribute nothing, and instructions for any other grazing year contribute nothing; the window is exactly the allotment's `current_grazing_year`, inclusive of both ends of that calendar year. The sum is order-insensitive, so no tie-break is needed. The third line is **the remainder**: `open_aums` is `effective_capacity_aums` less `allocated_aums`, and it is the uncommitted forage a new commitment may draw on. `current_grazing_year` itself is the calendar year, in UTC, of the logical clock. All three lines, and `current_grazing_year` with them, are derived afresh on every read from the allotment's stored `total_permitted_aums` and `stocking_adjustment_pct` and from the live instructions; not one of them is a stored column, and none is ever written directly. Two consequences follow. `open_aums` is a plain difference and is **not** clamped at zero: because instructions that have reached `aoi_status` `BILLED` or `CLOSED` still occupy allocation while the re-authorization hop of §3.10 declines to touch them, a reduction can leave `effective_capacity_aums` below `allocated_aums`, and `open_aums` is then negative — the AUM invariant below still holds exactly, and priority 30 simply refuses every further commitment until the year turns over. And an event that moves only these derived figures does not by itself write the allotment row: approving non-use, voiding an operating instruction, transferring a permit, issuing a permit, and raising, paying or voiding a bill all shift the ledger without advancing the allotment's `version`, which moves only when one of the allotment's own stored fields is rewritten or where this document expressly says otherwise — namely on the issuance of an operating instruction (§3.4) and on the authorship, effectuation or vacatur of a permit decision (§3.8), none of which need write an allotment field yet each of which bumps the version once for the event. Cancelling a permit is not a separate ledger-only event: a permit reaches `CANCELLED` only as the cascade of a cancellation decision taking effect, and that event bumps the version once, as the effectuation clause just given requires. §2.4 states the same trigger list from the versioning side, and the two lists agree exactly.

Two conservation invariants hold at all times and are the acceptance criterion for every cascade in §3. The AUM invariant: an allotment's `open_aums` plus its `allocated_aums` always equals its `effective_capacity_aums`. The compensation invariant: if an allotment's `allocated_aums` is A before an operating instruction is issued, then after issuance it is A plus that instruction's `billable_aums`, and after that same instruction is voided it is A again — exactly A, with no drift — while `open_aums` returns to `effective_capacity_aums` less A.

The money side carries the mirror-image invariant. A permittee's `outstanding_balance_cents` always equals the sum, over that permittee's bills whose `bill_status` is `ISSUED` or `DELINQUENT`, of each bill's `total_amount_cents` less its `amount_paid_cents`; bills in `PAID` or `VOIDED` contribute nothing, and an `ADJUSTMENT_CREDIT` bill contributes its negative total and so reduces the balance. If the balance is B before a bill is issued, it is B plus that bill's `total_amount_cents` afterwards, and voiding that bill returns it to exactly B with no residue. When one operation voids a bill and issues a replacement, the balance ends at B less the voided bill's `total_amount_cents` plus the replacement's `total_amount_cents`. A permittee's `permittee_status` is derived from the same aggregate: it is `DEBT_FLAGGED` exactly when `outstanding_balance_cents` is greater than zero **and** at least one of the contributing bills is in `bill_status` `DELINQUENT`, and `IN_GOOD_STANDING` in every other case — so an unpaid bill that is not yet overdue leaves the permittee `IN_GOOD_STANDING`. A permit's `account_status` is re-derived from the same live bills rather than nudged in one direction. Every event that touches one of a permittee's bills — raising it, paying it, or voiding it, whether directly or as part of a cascade — recomputes a single target for that permittee, `DELINQUENT` when it still holds at least one bill in `bill_status` `DELINQUENT` and `CURRENT` otherwise, and writes that target onto every permit of the permittee whose `permit_status` is `PENDING_REVIEW`, `ISSUED` or `SUSPENDED` and whose stored value differs from it. The refresh is therefore genuinely two-way: a permit that was filed while a delinquent bill already stood, and so landed on the `CURRENT` default of §3.3, is carried to `DELINQUENT` by the next billing event that touches that permittee rather than at filing time. Permits in `CANCELLED`, `EXPIRED` or `TRANSFERRED` are never rewritten by this refresh and keep whichever `account_status` they held when they reached that terminal state.

### 2.10. Segregation of Duties Across Authorship, Decision and Adjudication

Authorship, decision and adjudication are three separate hands, and the same person may never occupy two of them on the same document. Three operations enforce this, each comparing `X-User-ID` values only and never roles, and each failing with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). On assessment review, the reviewing officer's `X-User-ID` must not equal the assessment's `author_user_id`. On decision signature, the deciding officer's `X-User-ID` must not equal the decision's `authoring_officer_id`. On appeal decision, the adjudicator's `X-User-ID` must equal neither the appealed decision's `deciding_officer_id` nor its `authoring_officer_id`. Each of these comparisons bites only once the identifier it names exists: while the named field is still null — as `deciding_officer_id` is on a decision that has not yet been signed, or on one whose signature a remand has stripped — there is nothing to collide with and the check passes.

Two consequences follow from the fact that this check runs at priority 4, after the role gate at priority 3, and inspects identifiers alone. An identifier whose `X-User-Role` is not listed for the operation fails at priority 3 with `ERR_UNAUTHORIZED` even when that identifier is also the authoring hand — the role gate simply gets there first. And an identifier whose `X-User-Role` **is** listed for the operation fails here with `ERR_SEGREGATION_OF_DUTIES` even though its role is impeccable, because the person, not the capacity, is what disqualifies it.

One further identity rule sits outside the segregation family and is not a segregation failure: only the range specialist who created an assessment may submit it for field review, and a submission attempt by any other identifier is `ERR_UNAUTHORIZED`. Likewise, an appeal may be decided only by the adjudicator who docketed it — the acting `X-User-ID` must equal the case's `adjudicator_id` — and a mismatch is `ERR_UNAUTHORIZED`. Making a decision effective is reserved to the officer who signed it, so the acting `X-User-ID` must equal the decision's `deciding_officer_id`, and a mismatch is likewise `ERR_UNAUTHORIZED`. Each rule in this paragraph is a positive match against a stored identifier and therefore, like the segregation checks above, holds vacuously while that identifier is still null.

### 2.11. Cascade Discipline: Snapshots, Supersession and Restoration

Because capacity moves underneath commitments that have already been made, three disciplines govern every cascade in this specification, and departing from any of them produces wrong numbers rather than a visible failure.

**Reductions are recomputed from a snapshot, never applied on top of the current value.** When an operating instruction is issued, its `authorized_aums` at that instant is copied into `authorized_aums_at_issue`, and that snapshot is never mutated afterwards. Every subsequent re-authorization — from an emergency order, from a stocking adjustment, from lifting an order, from vacating a decision — recomputes `authorized_aums` from the snapshot and the currently prevailing adjustment fraction. Reductions therefore never compound, and restoring the original figure is exact rather than approximate. The same discipline applies one level up: a decision that is about to take effect first copies the allotment's `stocking_adjustment_pct` into its own `pre_decision_adjustment_pct` before changing anything, so that vacating the decision can restore the prior fraction verbatim.

**Reduction sources are combined by taking the strongest, never by adding.** An allotment's `stocking_adjustment_pct` is the maximum over the `reduction_pct` of every closure order on that allotment in `order_status` `ACTIVE` and the `adjustment_pct` of every permit decision on that allotment of `decision_type` `STOCKING_ADJUSTMENT` in `decision_status` `EFFECTIVE`. Orders that are `LIFTED` or `EXPIRED` contribute nothing, and decisions in `DRAFT`, `PROPOSED`, `FINAL`, `STAYED` or `VACATED` contribute nothing. Two overlapping 30-percent reductions leave the allotment at 30 percent, not 51 or 60.

**An unpaid bill is superseded; a partly paid bill is adjusted.** When a recomputation changes what a bill should have charged, the outcome depends on whether money has been received. A bill whose `amount_paid_cents` is zero is voided and replaced by a new bill carrying `superseded_bill_id` pointing at the voided one. A bill that has received any payment at all is left untouched, and the difference is settled by a separate adjustment bill. Both paths leave the money conservation invariant of §2.9 intact.

Every mutation these cascades perform is a real mutation: the affected resource's `updated_at` is refreshed and its `version` increases by 1, including on rows the client never named. The converse is equally binding, and it is what keeps a cascade's version arithmetic predictable: a recomputation that lands a stored field on the value it already held is not a mutation at all, so an operating instruction whose re-authorized `authorized_aums` comes back identical to the figure it carried, a permit whose re-derived `account_status` already equals the target value, and a permit whose recomputed `consecutive_nonuse_years` has not moved are each left with their `updated_at` and `version` completely untouched. The allotment at the head of a reallocation is the deliberate exception: its row is written once for the event whether or not its `stocking_adjustment_pct` or `allotment_status` actually changed. A cascade completes in a single pass and reaches its fixed point without feeding back on itself — recomputing instruction authorizations never re-enters the computation of the allotment's adjustment fraction.

## 3. Business Logic & Workflows

### 3.1. The Allotment Inventory, Its Pastures and the Season of Use

Everything in this service hangs off an **allotment** — a bounded tract of public land with a forage ceiling. An `AuthorizedOfficer` registers one by supplying its `name` (between 1 and 120 characters, and not blank), the administering field office's `admin_unit_code` (two uppercase letters, a hyphen, then three digits, as in `NV-042`), the `acres` of public land inside the boundary (at least 1), and the `total_permitted_aums` the inventory carries before any adjustment (also at least 1). The season of use is recurring rather than dated: `season_start` and `season_end` are month-and-day strings with no year, and `season_end` must fall strictly after `season_start` inside the same calendar year, so a season that wraps around New Year's Day cannot be expressed; because these two are `MM-DD` strings rather than dates, that ordering rule is a request-shape failure reported as `ERR_VALIDATION` at priority 1 and never the `ERR_INVALID_DATE_RANGE` of priority 2, whose remit §2.6 confines to the dated windows it enumerates. The `MM-DD` test is a calendar-shape test only, and it is performed against a leap year, so `02-29` is an accepted `season_start` or `season_end`: accepting the shape asserts that the month-and-day pair is a real calendar day somewhere, not that it exists in every grazing year the recurring window is later resolved against. This document therefore does not define what resolving a `02-29` season boundary against a non-leap grazing year produces, and no client behaviour may be built on that combination. The officer may also supply `required_pasture_rotation_count`, the minimum number of distinct pastures an operating instruction must schedule before it may be issued; when omitted it defaults to 2, and it must be at least 1.

A freshly registered allotment starts in a fully permissive posture. Its `allotment_status` is `OPEN`, its `health_determination` is `NOT_ASSESSED`, its `stocking_adjustment_pct` is 0, and its capacity ledger reads `effective_capacity_aums` equal to `total_permitted_aums`, `allocated_aums` of 0 and `open_aums` equal to `total_permitted_aums`. Its `current_grazing_year` is set to the calendar year of the logical clock. Over its life the posture takes exactly three values — `OPEN`, `RESTRICTED` and `CLOSED` — and the health determination takes exactly four: `NOT_ASSESSED`, `MEETING`, `MEETING_WITH_PROBLEMS` and `NOT_MEETING`. Neither field is ever written directly by a client: posture follows from the reduction sources described in §3.10 and §3.8, and the determination follows from the monitoring record described in §3.7. Officers and specialists can therefore browse the inventory filtered by `allotment_status`, by `health_determination` or by `admin_unit_code`, and read a single allotment to see its live ledger and its current `version`.

Pastures give the allotment its rotation structure. An `AuthorizedOfficer` adds one by naming it — `name`, between 1 and 80 characters, which the service does **not** require to be unique within the allotment, so two pastures of one allotment may legitimately share a name and only `sequence_order` is checked for collision — and stating its `pasture_aum_capacity`, the maximum concurrent scheduled AUMs the unit may carry at any single instant, which must be at least 1. The `sequence_order` fixes the pasture's position in the required rotation sequence: it must be at least 1, must be unique within the allotment, and the sequence must be dense from 1, so creating position 4 on an allotment that has only positions 1, 2 and 3 succeeds while creating position 5 on that same allotment is `ERR_PASTURE_SEQUENCE_CONFLICT`. A pasture may be flagged `rest_required`, which defaults to false; a rested pasture may not be scheduled in any operating instruction at all, and the `allotment_id` the pasture belongs to is taken from the path rather than the body.

Each pasture also publishes a live utilisation roll-up. Its `scheduled_aums` is the sum of `planned_aums` over every use record naming that pasture whose owning operating instruction has a `grazing_year` equal to the allotment's `current_grazing_year` and an `aoi_status` of `ISSUED`, `USE_REPORTED`, `BILLED` or `CLOSED`; the figure is carried to 2 decimal places and starts at 0. Records belonging to draft or voided instructions, and records for any other grazing year, contribute nothing. Pastures are listed either beneath their allotment in rotation order or across the whole inventory, narrowed by `allotment_id` or by `rest_required`.

### 3.2. Permittee Standing, Base Property and Preference Qualification

A **permittee** is a ranch or operator on the agency's books. Registration takes only a `name` of 1 to 120 characters and a `contact_email`, which must contain an at-sign; the resulting record starts `IN_GOOD_STANDING` with an `outstanding_balance_cents` of 0 and a `billed_trespass_incident_count` of 0. The `permittee_status` field takes exactly two values, `IN_GOOD_STANDING` and `DEBT_FLAGGED`, derived as described in §2.9, and the trespass counter is itself derived: it is the number of trespass incidents attributed to this permittee whose `incident_status` is `BILLED` or `RESOLVED`. Anyone with a role may read a permittee's aggregates, a `Permittee` actor being confined to its own record.

Preference to graze does not arise from the permit; it arises from **base property** — deeded land or controlled livestock that the operator commits to the operation. An `AuthorizedOfficer` records one against a permittee by supplying `base_property_type`, which is either `LAND` or `LIVESTOCK`; a `legal_description` of 1 to 200 characters giving the township-range-section description; the `carrying_capacity_aums` the property can produce, which must not be negative; and the `controlled_since_date` on which the operator took control, as a calendar date. The owning `permittee_id` comes from the path.

The commensurability arithmetic runs at that moment and again on any read of the property. Deeded land qualifies at full strength: the qualification factor for a `LAND` property is 1.0. Controlled livestock qualifies at three-quarters strength: the factor for a `LIVESTOCK` property is 0.75. The property's `qualified_aums` is its `carrying_capacity_aums` multiplied by that factor, floored to a whole AUM. A `LAND` property producing 400 AUMs therefore qualifies 400; a `LIVESTOCK` property producing the same 400 qualifies 300, and one producing 401 qualifies 300 as well, because the product 300.75 is floored rather than rounded. `qualified_aums` is the ceiling on how much preference the property can support on a permit, and it is what priority 16 compares `requested_aums` against.

The kind of base property also ranks a permit's preference. A permit's `preference_priority` is 1 when its qualifying base property is of type `LAND` and 2 when it is of type `LIVESTOCK`, a lower number winning any qualification comparison. This field is never client-supplied and, importantly, is not computed when the application is filed: it is stamped on the transition that moves the permit from `PENDING_REVIEW` to `ISSUED`. An unissued application backed by deeded land therefore still reads its default of 2 for the whole of its `PENDING_REVIEW` period. Base properties are listed beneath their permittee or across the register: the register-wide listing narrows by `permittee_id` or by `base_property_type`, while the nested listing takes its permittee from the path and narrows by `base_property_type` alone. On both listings the query parameter `qualification_basis` is accepted as an exact alias of `base_property_type` and filters that identical stored field with the identical verbatim string comparison; there is no separate `qualification_basis` attribute stored on or returned by a base property, and a request that sends both parameters simply narrows by each in turn, so disagreeing values match nothing. Neither listing is narrowed by ownership — the `Permittee` confinement of §2.1 does not reach base properties, so any operational role may list and read any permittee's.

### 3.3. The Term Permit Lifecycle: Application, Issuance, Renewal and Transfer

A **grazing permit** carries one permittee's preference on one allotment for one term, and it is the only entity in this service with two independent state dimensions on the same row. The authorization dimension, `permit_status`, takes the values `PENDING_REVIEW`, `ISSUED`, `SUSPENDED`, `CANCELLED`, `EXPIRED` and `TRANSFERRED`, of which the last three are terminal, and it is moved only by decisions and permit actions. The billing dimension, `account_status`, takes the values `CURRENT` and `DELINQUENT`, and it is moved only by billing events. The two axes never constrain one another: a permit may legitimately be `ISSUED` and `DELINQUENT`, or `SUSPENDED` and `CURRENT`, or any other pairing, and an operation that moves one dimension leaves the other exactly where it was.

An application is filed by an `AuthorizedOfficer` naming the `allotment_id` the preference attaches to, the `permittee_id` who will hold it, the `base_property_id` that qualifies it, the `requested_aums` of preference sought (at least 1), the `term_start_date` and `term_end_date` bounding the term, and the `livestock_kind`, which is `CATTLE`, `SHEEP` or `HORSES`. The request-body figure is named `requested_aums`, and the value it carries is stored on the permit as `permitted_aums`; the two names refer to the same quantity seen from the client side and the server side respectively. The application lands in `permit_status` `PENDING_REVIEW` and `account_status` `CURRENT`, with `suspension_reason` null, `consecutive_nonuse_years` 0, `predecessor_permit_id` null — that self-reference is populated only on a permit born of a renewal or a transfer — and `preference_priority` at its default of 2. A `PENDING_REVIEW` application consumes no capacity whatsoever; the ledger of §2.9 does not see it. At this stage the named base property must belong to the named permittee, on pain of `ERR_BASE_PROPERTY_NOT_OWNED`, and `requested_aums` must fit within that property's `qualified_aums`, on pain of `ERR_INSUFFICIENT_QUALIFIED_AUMS`.

Issuance is the transition `PENDING_REVIEW → ISSUED`, performed by an `AuthorizedOfficer` with no request body at all: the `permitted_aums` stored at application time is the figure that governs, and it is not re-read from the request. Five gates guard the transition and, per §2.6, they are evaluated in that fixed order. The allotment's `allotment_status` must be `OPEN` or `RESTRICTED`, a `CLOSED` allotment yielding `ERR_ALLOTMENT_CLOSED` at priority 9. The allotment's `health_determination` must not be `NOT_MEETING` unless a `STOCKING_ADJUSTMENT` decision on that allotment is already `EFFECTIVE`, failing which the officer sees `ERR_HEALTH_STANDARDS_NOT_MET` at priority 10. The permit's `permitted_aums` must not exceed the qualifying base property's `qualified_aums`, re-checked here and reported as `ERR_INSUFFICIENT_QUALIFIED_AUMS` at priority 16. The holding permittee's `outstanding_balance_cents` must be zero, failing which the answer is `ERR_OUTSTANDING_BALANCE` at priority 28. And the `permitted_aums` must not exceed the allotment's `open_aums` at that moment, failing which it is `ERR_ALLOTMENT_CAPACITY_EXCEEDED` at priority 30. When all five hold, `permit_status` becomes `ISSUED` and `preference_priority` is recomputed from the qualifying base property's `base_property_type` — 1 for `LAND`, 2 for `LIVESTOCK`. Those two fields on the permit row are the entire footprint of the transition, and the response is HTTP 200 carrying that updated permit. In particular the priority 30 comparison only *reads* the allotment's `open_aums`; it reserves nothing against it, so an `ISSUED` permit, exactly like the `PENDING_REVIEW` application it grew out of, contributes nothing to `allocated_aums` — which §2.9 draws from operating instructions alone — and neither the allotment row nor its `version` is written by an issuance. No permit decision of any kind is required to reach `ISSUED`: an `ISSUANCE` decision, described in §3.8, is the formal appealable record of the authorization and neither gates nor performs this transition.

Renewal is the `ISSUED → EXPIRED` transition on the predecessor coupled with the birth of a successor. The `AuthorizedOfficer` supplies the successor's `term_start_date` and `term_end_date`, its `requested_aums`, and the `base_property_id` that will qualify it. The predecessor must be in `permit_status` `ISSUED`, must not already have a successor, and the new `term_start_date` must fall on or after the predecessor's `term_end_date`, all three failures reporting `ERR_PREDECESSOR_PERMIT_INVALID`. The permittee's `outstanding_balance_cents` must be at most zero, the named base property's `qualified_aums` must be at least the permit's `permitted_aums`, and the allotment's `allotment_status` must be `OPEN` or `RESTRICTED`. The non-use ceiling described in §3.5 also bites here. On success the predecessor moves to `permit_status` `EXPIRED`, and a successor permit is created carrying `predecessor_permit_id` pointing at the predecessor, `permit_status` `ISSUED`, `account_status` `CURRENT`, the same `permittee_id`, `allotment_id`, `base_property_id`, `permitted_aums` and `livestock_kind` as the predecessor, and the supplied term dates. The `requested_aums` in the payload is validated for shape and then ignored: the successor's `permitted_aums` is the predecessor's stored figure, and it is that stored figure — never the payload's — that priorities 16 and 30 compare. The supplied `base_property_id` is likewise consulted only for the ownership check of priority 13 and the qualification check of priority 16; the successor's own `base_property_id` is inherited from the predecessor, and its `preference_priority` is stamped from that *inherited* property's `base_property_type` rather than from the property just supplied. The successor's `suspension_reason` is null. The call answers HTTP 201 with the newly created successor in `data`; the predecessor, now `EXPIRED`, is not what is returned. The predecessor's `consecutive_nonuse_years` is recomputed and copied onto the successor. The allotment's `allocated_aums` is recomputed and, because the successor inherits the predecessor's commitments only for future years, comes back unchanged.

Transfer is the `ISSUED → TRANSFERRED` transition, and it differs from renewal in three ways that matter. Because that is the declared transition, a source permit in any other `permit_status` is refused as a transition-legality failure — `ERR_PERMIT_STATE_INVALID` at priority 8, evaluated before the allotment-posture, rangeland-standards, base-property-ownership and preference-chain checks — rather than as the `ERR_PREDECESSOR_PERMIT_INVALID` that the same situation earns on renewal; a source permit that is `ISSUED` but already carries a successor is still `ERR_PREDECESSOR_PERMIT_INVALID` at priority 15. The `AuthorizedOfficer` supplies `transferee_permittee_id` — the operator receiving the preference — together with the `base_property_id`, `term_start_date`, `term_end_date` and `requested_aums` of the successor. The base property must belong to the **transferee**, so reusing the transferor's property is `ERR_BASE_PROPERTY_NOT_OWNED`, and its `qualified_aums` must be at least the permit's `permitted_aums`. The debt gate runs against the transferee rather than the transferor. And unlike renewal, transfer does not let the transferor's year run on: the source permit moves to `permit_status` `TRANSFERRED`, a successor is created for `transferee_permittee_id` with `predecessor_permit_id` set to the source permit, `permit_status` `ISSUED`, `account_status` `CURRENT` and the source permit's `permitted_aums`, `livestock_kind`, `term_start_date` and `term_end_date`, and **every** operating instruction of the **source permit itself** in `aoi_status` `DRAFT` or `ISSUED` is voided — the sweep is keyed on the source permit and not on the transferor as a party, so instructions the transferor holds under any *other* permit are left standing, and each instruction the sweep does catch is voided with a null `void_reason` and drags its own `ISSUED` or `DELINQUENT` bills to `VOIDED` exactly as §3.5 describes. The allotment's `allocated_aums` and `open_aums` are then recomputed, releasing what those voided instructions held. The successor's `base_property_id` is the property supplied on the request rather than the source permit's, and its `preference_priority` is stamped from that supplied property's `base_property_type`; the payload's `term_start_date`, `term_end_date` and `requested_aums` are validated for shape and for date-range coherence and then ignored, the successor taking the source permit's term dates and `permitted_aums` instead. Unlike renewal, the successor's `consecutive_nonuse_years` starts at 0 rather than inheriting the source's run, its `suspension_reason` is null, and the source permit's `suspension_reason` is cleared to null as it moves to `TRANSFERRED`. The call answers HTTP 201 with the newly created successor in `data`.

Two further movements of the authorization dimension are driven from elsewhere. Advancing the logical clock past a permit's `term_end_date` moves an `ISSUED` permit to `EXPIRED` — specifically, every `ISSUED` permit whose `term_end_date` is earlier than the new clock date expires — while leaving `account_status` untouched. And an effective decision suspends or cancels, as §3.8 sets out. Suspension records why in `suspension_reason`, which is `NONPAYMENT`, `DECISION`, or null; the field is null whenever `permit_status` is anything other than `SUSPENDED`. The enumeration declares both reasons, but only one of them is ever produced. The single operation in this service that suspends a permit is a `SUSPENSION` decision taking effect, and it always records `DECISION`; no operation writes `NONPAYMENT` at all, because delinquency moves the billing dimension alone and never the authorization dimension. The `NONPAYMENT` reinstatement rule stated in §3.6 is therefore a declared conditional that no reachable state satisfies, and it is retained as the specification of what a `NONPAYMENT` suspension would mean rather than as a path a client can exercise. A permit is listed and filtered by `allotment_id`, `permittee_id`, `base_property_id`, `predecessor_permit_id`, `permit_status` and `account_status`, and a single read exposes both dimensions along with `suspension_reason` and `consecutive_nonuse_years`.

### 3.4. The Grazing Year: Drafting, Scheduling and Issuing Annual Operating Instructions

Each grazing year on each permit is governed by one **annual operating instruction**, and its `aoi_status` runs through `DRAFT`, `ISSUED`, `USE_REPORTED`, `BILLED` and `CLOSED`, with `VOIDED` available as an alternative ending; `CLOSED` and `VOIDED` are terminal. A `RangeSpecialist` or an `AuthorizedOfficer` drafts one by naming the `permit_id` it belongs to, the `grazing_year` it governs (a calendar year between 2020 and 2060 inclusive), the `authorized_aums` for that year (at least 1), and the `season_start_date` and `season_end_date` bounding the authorised turnout and off-dates. The named permit must be in `permit_status` `ISSUED` — a permit in `PENDING_REVIEW`, `SUSPENDED`, `CANCELLED`, `EXPIRED` or `TRANSFERRED` yields `ERR_PERMIT_STATE_INVALID` — the allotment must not be `CLOSED`, no other non-voided instruction may already exist for that permit and year (`ERR_DUPLICATE_AOI_FOR_YEAR`), the declared season must sit inside the allotment's recurring season window resolved against the `grazing_year` (`ERR_SEASON_OF_USE_VIOLATION`), the permittee must carry no outstanding balance (`ERR_OUTSTANDING_BALANCE`), and the requested `authorized_aums` must not exceed the allotment's `open_aums` at that instant (`ERR_ALLOTMENT_CAPACITY_EXCEEDED`).

The new instruction lands in `aoi_status` `DRAFT`. Its `authorized_aums_at_issue` is stamped with the `authorized_aums` just supplied and is never mutated afterwards — it is re-stamped, to the same value, on the issuance transition, and every later re-authorization reads it rather than the live figure. Its `nonuse_aums` is 0 and its `nonuse_reason` is null, which makes its `billable_aums` — always `authorized_aums` less `nonuse_aums` — equal to the `authorized_aums` supplied. Its `planned_aums_total`, `actual_aums_total` and `distinct_pasture_count` all start at 0, and its `void_reason` starts null and stays null unless a void supplies one. Crucially, a `DRAFT` instruction consumes nothing: capacity was checked against `open_aums` but not taken, and the allotment's `allocated_aums` does not move until the instruction is issued.

Scheduling the rotation is the next step, and it is only possible while the instruction is in `DRAFT` — adding a window to an instruction in any other status is `ERR_AOI_STATE_INVALID`. A `RangeSpecialist` or `AuthorizedOfficer` schedules one leg at a time by naming the `pasture_id`, the `planned_entry_date` on which livestock turn out, the `planned_exit_date` on which they come off, the `planned_head_count` (at least 1) and the `livestock_kind` for that leg. The window is **half-open**: grazing is counted from `planned_entry_date` up to but not including `planned_exit_date`, so the exit day itself is not grazed and a window whose exit equals its entry is never valid. The pasture must belong to the allotment of the instruction's permit, failing which the answer is `ERR_PASTURE_NOT_IN_ALLOTMENT`, and the leg's `livestock_kind` must equal the `livestock_kind` of the instruction's permit — a mismatch is a request-shape failure reported as `ERR_VALIDATION`. That one rule is the documented exception to where priority 1 sits in the ordering of §2.6, because the comparison cannot be made until the instruction's permit has been fetched: it is evaluated after the role gate of priority 3 and after the path instruction has been resolved at priority 5, so a mismatched `livestock_kind` presented by an unauthorised caller, or against an instruction that does not exist, reports `ERR_UNAUTHORIZED` or `ERR_AOI_NOT_FOUND` instead. It is nevertheless evaluated before the body's `pasture_id` is resolved at priority 6 and before every state, locality, season and capacity gate below, so once the caller and the path instruction are both good, the mismatch is what the client sees.

The forage a leg represents is computed the moment it is scheduled. Take the number of whole days in the half-open window — that is, the count of days from the entry date up to but excluding the exit date. Multiply the head count by the animal-unit equivalent of the livestock kind, which is 1.0 for `CATTLE`, 0.2 for `SHEEP` and 1.25 for `HORSES`. Multiply that by the day count, then divide by 30, the number of grazing days that make up one animal unit month. Round the result half-up to 2 decimal places, exactly once. That value is the record's `planned_aums`. A leg of 40 head of cattle turned out on the 1st and taken off on the 31st spans 30 days and therefore carries 40.00 planned AUMs; the same 40 head of sheep over the same window carries 8.00. Once the leg is stored, the instruction's `planned_aums_total` is recomputed as the sum of `planned_aums` over **all** of its use records regardless of `record_status`, its `distinct_pasture_count` as the number of distinct `pasture_id` values across all of those records, and the named pasture's `scheduled_aums` roll-up is refreshed.

Pasture capacity is enforced as a temporal aggregate rather than a running total, and this is where the half-open convention earns its keep. For the pasture named by a new or newly reported leg, sum `planned_aums` over every use record on that pasture whose half-open planned window **intersects** the window of the leg under evaluation — records belonging to any operating instruction of the same `grazing_year` count, and the leg under evaluation is included in its own sum. If that sum exceeds the pasture's `pasture_aum_capacity`, the request is refused with `ERR_PASTURE_CAPACITY_EXCEEDED`. Two legs that merely touch, where one's exit date equals the other's entry date, do not intersect and are never aggregated together; two legs that overlap by even a single day are. No `record_status` and no `aoi_status` filter narrows the contributors: a leg on an instruction still in `DRAFT` counts here, which is exactly where this aggregate parts company with the `scheduled_aums` roll-up of §3.1 that admits only issued-or-later instructions. The same aggregate is re-evaluated when actual use is reported, and the substitution is confined to the one leg being reported: that leg contributes its newly reported **actual** window and its freshly computed `actual_aums`, its own scheduled row being excluded from the sum so that it is never counted twice, while every other record on the pasture contributes its `planned_aums` over its **planned** window — including records that have themselves already been reported, whose actual figures play no part in anybody else's check.

Issuing the instruction is the transition `DRAFT → ISSUED`, reserved to an `AuthorizedOfficer` and taking no request body. Five conditions must hold: the permit is still `ISSUED`, the allotment's `allotment_status` is `OPEN` or `RESTRICTED` (otherwise `ERR_ALLOTMENT_CLOSED`), the instruction's `distinct_pasture_count` is at least the allotment's `required_pasture_rotation_count` and no pasture flagged `rest_required` appears among its use records (otherwise `ERR_ROTATION_REQUIREMENT_NOT_MET`), the instruction's `planned_aums_total` does not exceed its `authorized_aums` (a same-entity precondition, so a schedule that plans more forage than the year authorises is `ERR_AOI_STATE_INVALID`), and the instruction's `billable_aums` — which for an unreduced draft equals its `authorized_aums` — does not exceed the allotment's `open_aums` as of that moment, a capacity that shrank between draft and issue therefore producing `ERR_ALLOTMENT_CAPACITY_EXCEEDED` even though the draft was accepted. Those five are enumerated here for readability and not in the order they run; per §2.6 they are evaluated by priority, which puts the instruction's own `DRAFT` requirement first, then the permit's `ISSUED` requirement, then the `planned_aums_total` ceiling — all three being priority 8 failures, the first and third `ERR_AOI_STATE_INVALID` and the second `ERR_PERMIT_STATE_INVALID` — then `ERR_ALLOTMENT_CLOSED` at priority 9, then the rotation requirement at priority 20 (its distinct-pasture count checked before its rested-pasture scan, though both report the one code), and the capacity comparison last at priority 30.

Issuance is where the year's forage is actually committed and the first bill is raised. The `aoi_status` becomes `ISSUED`, `authorized_aums_at_issue` is re-stamped from `authorized_aums`, the allotment's `allocated_aums` and `open_aums` are recomputed by the ledger of §2.9 — `allocated_aums` rising by exactly this instruction's `billable_aums` — the allotment's `version` is bumped, and `scheduled_aums` is refreshed on every pasture the instruction's use records name. When `billable_aums` is greater than zero, a preliminary bill of `bill_type` `PRELIMINARY_USE` is raised, computed by the preliminary variant of the use-bill arithmetic in §3.6, and the permittee's `outstanding_balance_cents` is recomputed to include it. When `billable_aums` is exactly zero, **no** bill at all is created.

### 3.5. Temporary Non-Use, Reporting Actual Use and Final Settlement

Not every authorised AUM is grazed, and the agency recognises **temporary non-use** for four reasons: `DROUGHT`, `WILDFIRE`, `RESOURCE_CONSERVATION` and `PERSONAL_CONVENIENCE`. An `AuthorizedOfficer` approves it against an operating instruction by supplying `nonuse_aums` and `nonuse_reason`. No `aoi_status` precondition guards the operation at all — which is why priority 8 does not list it: non-use may be approved against an instruction in any status whatsoever, `DRAFT`, `ISSUED`, `BILLED`, `CLOSED` and `VOIDED` alike. A second approval on the same instruction **replaces** the stored `nonuse_aums` and `nonuse_reason` rather than adding to them, so the bound below is always measured against the instruction's `authorized_aums` and never against a running total, and lowering a previously approved figure is an ordinary approval. The requested `nonuse_aums` must be at least 1 and no greater than the instruction's current `authorized_aums`, and the two agency-directed reasons are conditional: `DROUGHT` is accepted only while a closure order of `order_type` `DROUGHT_REDUCTION` is `ACTIVE` on the allotment, and `WILDFIRE` only while an order of `order_type` `WILDFIRE_CLOSURE` is `ACTIVE` on it. Every one of those failures is `ERR_NONUSE_EXCEEDS_AUTHORIZED`. Whenever `nonuse_aums` is 0, `nonuse_reason` is null.

Approving non-use releases capacity and re-prices the year. The instruction's `billable_aums` becomes its `authorized_aums` less the approved `nonuse_aums`, the allotment's ledger is recomputed so that the released AUMs reappear in `open_aums`, any still-unpaid preliminary bill for that instruction is superseded by a revised bill at the lower figure — or, where that bill has already received money, is left standing beside an `ADJUSTMENT_CREDIT` for the difference, and where the instruction has no live use bill at all nothing is raised, exactly the three-way branch of §3.6 — the permit's `consecutive_nonuse_years` is recomputed, and the permittee's `outstanding_balance_cents` is brought back into line.

The non-use counter is deliberately narrow, because it is what forfeits preference. Consider the permit's operating instructions in `aoi_status` `ISSUED`, `USE_REPORTED`, `BILLED` or `CLOSED`, arranged by `grazing_year` in ascending order — creation order is irrelevant, so an instruction drafted late for an earlier year still lands in its chronological slot, and instructions in `DRAFT` or `VOIDED` are invisible to the exercise. A year **counts** toward the run when its instruction has a `nonuse_aums` greater than 0 **and** a `nonuse_reason` of either `RESOURCE_CONSERVATION` or `PERSONAL_CONVENIENCE`. A year **breaks** the run when its instruction has `nonuse_aums` of 0, when its `nonuse_reason` is `DROUGHT` or `WILDFIRE` — agency-directed non-use is never held against the permittee — or when that grazing year has no qualifying instruction at all, a gap being as good as a break. The permit's `consecutive_nonuse_years` is the length of the unbroken run of counting years that **ends at the most recent counting year** — the run is anchored on the latest year that counts, not on the latest year that merely has a qualifying instruction. Two consequences of that anchoring are pinned. A breaking year, or a gap, that falls *after* the last counting year leaves the run standing rather than resetting it to 0: a permit that took conservation non-use in 2024 and 2025 and then grazed its full authorization in 2026 still reads 2. And an earlier run that has since been broken never revives: with counting years 2020, 2021 and 2022, a breaking 2023 and a counting 2024, the figure is 1, not 3, because only the run touching the most recent counting year is measured. Once it reaches 3, the preference has lapsed and renewal is barred with `ERR_NONUSE_LIMIT_EXCEEDED`; at 2 a renewal still succeeds.

Reporting what actually happened belongs to the rancher, and a `RangeSpecialist` may do it on their behalf. The reporting call names a single scheduled leg and supplies `actual_entry_date`, `actual_exit_date` and `actual_head_count`. When the caller is a `Permittee`, their `X-User-ID` must be the `permittee_id` of the instruction's permit. The owning instruction must be in `aoi_status` `ISSUED`; the leg must still be in `record_status` `SCHEDULED`, since reporting against a record already in `ACTUAL_REPORTED` or `ACCEPTED` is `ERR_USE_RECORD_STATE_INVALID`; `actual_exit_date` must be strictly after `actual_entry_date`; and the reported window must sit inside the instruction's declared season, so `actual_entry_date` must be on or after `season_start_date` and `actual_exit_date` on or before `season_end_date`, failing which the answer is `ERR_SEASON_OF_USE_VIOLATION`. The pasture-capacity aggregate of §3.4 is re-evaluated for the reported window.

On success the three reported values are stored, the leg's `actual_aums` is computed by exactly the same forage arithmetic as `planned_aums` — head count times animal-unit equivalent times whole days in the half-open window, divided by 30, rounded half-up to 2 decimal places once — and the leg moves `SCHEDULED → ACTUAL_REPORTED`. The instruction's `actual_aums_total` is then recomputed as the sum of `actual_aums` over its records whose `record_status` is `ACTUAL_REPORTED` or `ACCEPTED`; records still `SCHEDULED` contribute nothing, and `actual_aums` is null until the leg is reported. The rounding order here is pinned: each record's quantity is rounded to 2 decimal places first and the already-rounded values are then added, because summing raw quotients and rounding once at the end produces a different figure and therefore a different bill. Reporting a leg does **not** move the instruction's own `aoi_status`; the officer's acceptance does that.

Acceptance is a single atomic operation performed by an `AuthorizedOfficer` that carries the instruction from `ISSUED` straight to `BILLED`. The intermediate `aoi_status` value `USE_REPORTED` is a declared member of the enumeration that this transition — and, in fact, every operation in this service — never actually persists: acceptance writes the instruction's `aoi_status` exactly once, landing on `BILLED`, so the instruction's own `version` advances by exactly 1 across the whole acceptance and no read ever observes an instruction sitting in `USE_REPORTED`. Wherever `USE_REPORTED` appears in a status set elsewhere in this document — among the allocating statuses of §2.9 and §3.1, or among the statuses from which §3.5 permits a void — that membership is therefore satisfied vacuously and narrows nothing. Before the transition the instruction must have at least one use record and no record may still be in `record_status` `SCHEDULED`; otherwise the request is refused with `ERR_ACTUAL_USE_INCOMPLETE`. The operation then moves every use record of the instruction from `ACTUAL_REPORTED` to `ACCEPTED`, recomputes `actual_aums_total`, computes the final charge by the final variant of §3.6, settles the difference against the preliminary bill, sets `aoi_status` to `BILLED`, and recomputes the permittee's `outstanding_balance_cents`. The instruction reaches `CLOSED` later and indirectly: when a payment brings every non-voided bill of that instruction to `bill_status` `PAID`, the instruction moves `BILLED → CLOSED`.

Voiding is the escape hatch. An `AuthorizedOfficer` may void an instruction while it is in `DRAFT`, `ISSUED` or `USE_REPORTED`, optionally recording a `void_reason`; attempting it on an instruction already `BILLED`, `CLOSED` or `VOIDED` is `ERR_AOI_STATE_INVALID`, and an instruction any of whose bills has an `amount_paid_cents` greater than zero may not be voided either. Voiding a `DRAFT` instruction simply marks it `VOIDED`: it held no allocation, so the allotment's `allocated_aums` and `open_aums` are recomputed and come back unchanged. Voiding an instruction that had been issued does more: `aoi_status` becomes `VOIDED`, every bill of that instruction in `bill_status` `ISSUED` or `DELINQUENT` moves to `VOIDED`, the allotment's `allocated_aums` decreases by exactly that instruction's `billable_aums` while `open_aums` increases by the same amount — restoring the compensation invariant of §2.9 to the cent-exact AUM figure it held before issuance — `scheduled_aums` is refreshed on every pasture the instruction's records name, and the permittee's `outstanding_balance_cents` and the permit's `account_status` are re-derived. Because a voided instruction frees its permit-year slot, a replacement instruction may then be drafted for the same `grazing_year`.

### 3.6. Grazing Bills: Computation, Payment, Delinquency and Voiding

A **grazing bill** is never created directly by a client; it is always raised as the side effect of some other act. Its `bill_type` records the basis of the charge and takes exactly seven values: `PRELIMINARY_USE`, raised when an operating instruction is issued; `FINAL_USE`, raised when an accepted use report replaces an unpaid preliminary bill; `REVISED_USE`, raised when a capacity movement supersedes an unpaid use bill; `UNAUTHORIZED_USE`, raised when a trespass incident is billed; `PROJECT_COST_SHARE`, raised when a range improvement project's permittee share is allocated; and `ADJUSTMENT_DEBIT` and `ADJUSTMENT_CREDIT`, raised to settle a difference against a bill that has already received money. Every bill names the `permittee_id` it charges. A bill arising from a grazing year names its `aoi_id`; bills that do not arise from a grazing year leave it null. `trespass_incident_id` is populated only on an `UNAUTHORIZED_USE` bill and `project_id` only on a `PROJECT_COST_SHARE` bill. `superseded_bill_id` is a self-reference to the bill this one replaces, set whenever a recomputation voids an unpaid bill and issues a replacement, and null otherwise. An `ADJUSTMENT_DEBIT` or `ADJUSTMENT_CREDIT` bill carries the whole signed difference on a single line: its `base_amount_cents` and its `total_amount_cents` are both exactly that difference, its `billed_aums` is 0.00 because an adjustment re-prices no forage, and its `admin_fee_cents` and `penalty_amount_cents` are both 0 — the tiered administrative fee is levied once on the bill being adjusted and is deliberately never re-levied on the adjustment. Its `fee_rate_cents_per_aum` nevertheless still records the grazing fee rate of 172, its `superseded_bill_id` is null because it supersedes nothing and leaves the adjusted bill standing, and its `aoi_id` names the operating instruction whose recomputation produced it while its `trespass_incident_id` and `project_id` are null.

The **use-bill arithmetic** runs in five pinned steps, and the step order is not negotiable. Step one establishes `billed_aums`, which depends on the variant and is described below. Step two computes `base_amount_cents` as `billed_aums` multiplied by the grazing fee rate of 172 cents per AUM, rounded half-up to a whole cent; that same 172 is recorded on the bill as its `fee_rate_cents_per_aum`. Step three selects the tiered administrative fee **from `base_amount_cents`, never from the total**: `admin_fee_cents` is 0 when `base_amount_cents` is below 50,000 cents, 2,500 cents when `base_amount_cents` is at least 50,000 and below 200,000 cents, and 6,000 cents when `base_amount_cents` is 200,000 cents or more. Reading the tier off the total is the circular reading and produces the wrong fee, because the total already contains the fee. Step four sets `total_amount_cents` to `base_amount_cents` plus `admin_fee_cents`; `penalty_amount_cents` is 0 on every use bill. Step five, which applies only to the final variant, settles the difference against the preliminary bill. Every use bill is raised in `bill_status` `ISSUED` with `amount_paid_cents` of 0 and a `due_date` of the logical-clock date at issuance plus 30 days.

Three variants differ only in step one, and the difference between the first two is the whole point of the reconciliation. The **preliminary** variant, used when an operating instruction is issued, sets `billed_aums` to the instruction's `authorized_aums` less its `nonuse_aums` — an integer, so step two is exact — and applies no minimum-charge floor. The **final** variant, used when an accepted use report is billed, sets `billed_aums` to whichever is larger of the instruction's `actual_aums_total` and one quarter of the instruction's `authorized_aums` less its `nonuse_aums`, that quarter being floored to a whole AUM; because `actual_aums_total` carries two decimal places, step two genuinely rounds here, so identical instruction data yields a different total under the two variants and the difference is settled in step five. The **revised** variant, used when an emergency reduction, a stocking adjustment or a vacatur moves `authorized_aums` while a use bill is still unpaid, sets `billed_aums` to the recomputed `authorized_aums` less `nonuse_aums`, voids the superseded bill and records `superseded_bill_id` on the replacement, and likewise applies no minimum-charge floor.

Step five branches on whether money has already been received against the preliminary bill, and the two branches are equally binding. When the preliminary bill's `amount_paid_cents` is exactly 0, that bill moves to `bill_status` `VOIDED` and a bill of `bill_type` `FINAL_USE` is issued for the final total with `superseded_bill_id` set to the voided bill's `id`. When its `amount_paid_cents` is greater than 0, the preliminary bill is left untouched and the difference between the final total and the preliminary total is issued as a separate bill: `ADJUSTMENT_DEBIT` when that difference is positive, `ADJUSTMENT_CREDIT` when it is negative — in which case the new bill's `total_amount_cents` is itself negative — and **no bill at all** when the difference is exactly zero. A third case completes the branch, because the settlement needs a live bill to settle against and there may be none. When the instruction has no use bill in `bill_status` `ISSUED` or `DELINQUENT` at acceptance time — because `billable_aums` was 0 at issuance so no preliminary bill was ever raised, or because the preliminary bill has since reached `PAID` or `VOIDED` — there is nothing to void and nothing to compare against, so the final total is simply charged outright: a bill of `bill_type` `FINAL_USE` is raised for it with `superseded_bill_id` null whenever that total is greater than 0, and nothing at all is raised when the total is exactly 0. A preliminary bill already paid in full is therefore never credited back by this step.

Payment is recorded by the `Permittee` who owes the bill or by an `AuthorizedOfficer`, and the payload carries a single `amount_cents`. The target bill must be in `bill_status` `ISSUED` or `DELINQUENT`; paying one already `PAID` or `VOIDED` is `ERR_BILL_STATE_INVALID`. The `amount_cents` must be at least 1 and must not exceed the bill's `total_amount_cents` less its `amount_paid_cents`, because overpayment is refused rather than credited and yields `ERR_OVERPAYMENT`. A successful payment increases `amount_paid_cents` by `amount_cents`, and when the accumulated `amount_paid_cents` reaches or exceeds `total_amount_cents` the bill moves to `bill_status` `PAID`. The permittee's `outstanding_balance_cents` and `permittee_status` are then recomputed, and four consequential effects follow in turn. The first two fire only on the payment that carries this bill all the way to `bill_status` `PAID`, and a partial payment therefore triggers neither: when that fully paid bill was an `UNAUTHORIZED_USE` bill, its linked trespass incident moves `BILLED → RESOLVED`; when every non-voided bill of the linked operating instruction has likewise reached `PAID` and that instruction is sitting in `aoi_status` `BILLED`, it moves `BILLED → CLOSED`. The remaining two are re-derivations that run after every successful payment, full or partial: when the permittee is left with no bill in `bill_status` `DELINQUENT`, every permit of that permittee whose `permit_status` is `PENDING_REVIEW`, `ISSUED` or `SUSPENDED` moves `account_status` `DELINQUENT → CURRENT`; and a permit that was `SUSPENDED` with `suspension_reason` `NONPAYMENT` then moves `SUSPENDED → ISSUED` with its `suspension_reason` cleared to null. That fourth effect is conditional on a `NONPAYMENT` suspension and, as §3.3 records, no operation in this service ever produces one, so it never fires in practice: a permit suspended by decision keeps its `DECISION` reason and its `SUSPENDED` status through any payment, and is restored only by the vacatur of the decision that suspended it.

Delinquency is driven purely by the logical clock. When the clock advances, every bill in `bill_status` `ISSUED` whose `due_date` falls **strictly before** the new clock date and whose `total_amount_cents` still exceeds its `amount_paid_cents` moves to `bill_status` `DELINQUENT`; a bill whose `due_date` equals the new clock date is not yet delinquent. Each such bill flips its permittee's `permittee_status` to `DEBT_FLAGGED` and moves `account_status` from `CURRENT` to `DELINQUENT` on every permit of that permittee whose `permit_status` is `PENDING_REVIEW`, `ISSUED` or `SUSPENDED`. The authorization dimension is untouched: an `ISSUED` permit stays `ISSUED` while becoming `DELINQUENT` on its billing axis.

Voiding a bill is reserved to an `AuthorizedOfficer`, who may optionally record a `void_reason`, and it is permitted only while the bill's `amount_paid_cents` is exactly 0 — a bill that has received any money at all, or that is already `PAID` or `VOIDED`, yields `ERR_BILL_STATE_INVALID`. A void may be requested directly or performed by the system as part of a supersession during an emergency reduction, a stocking adjustment, a use-report acceptance or an instruction void. Either way the bill's `bill_status` becomes `VOIDED`, the permittee's `outstanding_balance_cents` is recomputed so that it returns to exactly the figure it held before the bill was raised, and two conditional effects follow: when the voided bill was an `UNAUTHORIZED_USE` bill, its linked trespass incident cycles `BILLED → DETECTED`; and when the void leaves the permittee with no `DELINQUENT` bill, every permit of that permittee whose `permit_status` is `PENDING_REVIEW`, `ISSUED` or `SUSPENDED` moves `account_status` `DELINQUENT → CURRENT`. Bills are read individually with their full money breakdown, and listed with filters on `permittee_id`, `aoi_id`, `trespass_incident_id`, `project_id`, `superseded_bill_id`, `bill_type` and `bill_status`.

### 3.7. Rangeland Health Monitoring and Stocking Determinations

Monitoring is the evidentiary engine behind every permanent capacity reduction, and the record it produces is a **rangeland health assessment**. A `RangeSpecialist` opens one against an allotment for a monitoring year, supplying `allotment_id`, `assessment_year` (between 2020 and 2060 inclusive), `monitoring_method` — either `INDICATOR_ASSESSMENT` or `UTILIZATION_MAPPING` — and the three standard indicator scores `upland_score`, `riparian_score` and `water_quality_score`, each an integer from 0 through 100. Three further inputs are optional at creation: `observed_utilization_pct`, the measured forage utilisation percentage, an integer from 1 through 100, which is required when `monitoring_method` is `UTILIZATION_MAPPING` and otherwise null; `standards_not_met`, an array of rangeland health standard codes drawn without duplicates from `UPLAND_HEALTH`, `RIPARIAN_FUNCTION`, `WATER_QUALITY` and `HABITAT`; and `causal_factor_is_livestock`, a boolean recording whether current livestock grazing is a significant causal factor for the unmet standards. All three may be sent as an explicit `null` as well as omitted altogether, and their stored defaults are fixed: an absent or null `observed_utilization_pct` is stored as null, an absent or null `standards_not_met` is stored as the **empty array** rather than as null, and an absent or null `causal_factor_is_livestock` is stored as false. The new row lands in `assessment_status` `DRAFT` with `remand_count` 0, `review_notes` null, `composite_score`, `determination` and `recommended_reduction_pct` all still unwritten — `recommended_reduction_pct` reading its default of 0 — and `author_user_id` set to the creating specialist's `X-User-ID`. At most one assessment per allotment and `assessment_year` may ever reach `FINALIZED`, and at most one may sit in `DRAFT` or `FIELD_REVIEW` at a time, either violation being `ERR_DUPLICATE_ASSESSMENT_FOR_YEAR`.

Submitting for field review is the transition `DRAFT → FIELD_REVIEW`, and only the authoring specialist may perform it: the acting `X-User-ID` must equal `author_user_id`, and anyone else is `ERR_UNAUTHORIZED`. Submitting an assessment that is not in `DRAFT` is `ERR_ASSESSMENT_STATE_INVALID`, and a `UTILIZATION_MAPPING` assessment whose `observed_utilization_pct` is still null cannot be submitted either — that second refusal is the same `ERR_ASSESSMENT_STATE_INVALID` at priority 8, not the `ERR_VALIDATION` the identically worded rule earns at creation time, and it is tested after the `DRAFT` requirement, so an assessment that fails both reports its status rather than its missing measurement. The transition writes `assessment_status` alone; no score, determination or recommendation is computed at submission.

Review is the fork, performed by an `AuthorizedOfficer` who supplies `review_outcome` — either `CONCUR` or `REMAND` — and may attach `review_notes`, an optional and nullable free-text field. The assessment must be in `FIELD_REVIEW`, and the reviewer's `X-User-ID` must differ from `author_user_id` on pain of `ERR_SEGREGATION_OF_DUTIES`, that segregation check running at priority 4 and so ahead of the status requirement. The two outcome-specific refusals are then tested, each on its own branch and only there: a `CONCUR` is refused with `ERR_DUPLICATE_ASSESSMENT_FOR_YEAR` when some **other** assessment on the same allotment and `assessment_year` has already reached `FINALIZED`, while a `REMAND` is refused with `ERR_ASSESSMENT_REMAND_LIMIT_EXCEEDED` when `remand_count` has already reached 2 — so a remand is never blocked by a finalized sibling, and a concurrence is never blocked by the remand ceiling. Whichever branch is taken, a non-null `review_notes` is written onto the assessment before the branch's own effects run; an omitted or null `review_notes` writes nothing and therefore leaves any note a previous review left in place rather than clearing it. The two branches carry deliberately disjoint side-effect sets otherwise, which is what makes the fork observable. A `CONCUR` outcome moves `FIELD_REVIEW → FINALIZED`, computes `composite_score` and `determination`, computes `recommended_reduction_pct`, writes the resulting `determination` onto the allotment's `health_determination`, and bumps the allotment's `version`. A `REMAND` outcome moves `FIELD_REVIEW → DRAFT` and increments the assessment's `remand_count` by 1; beyond those two fields and the `review_notes` described above it does **nothing else at all** — no score is computed, no determination is written, and the allotment is not touched in any way. A remand is permitted at most twice per assessment; a third remand is refused with `ERR_ASSESSMENT_REMAND_LIMIT_EXCEEDED`, leaving the reviewer to concur or the assessment to be abandoned.

The **composite score** is a weighted average of the three indicator scores. Multiply `upland_score` by 0.40, `riparian_score` by 0.35 and `water_quality_score` by 0.25, add the three products, and round the sum half-up to 2 decimal places; the result is `composite_score`. The weights add to exactly 1.00, so a uniform score maps to itself. The `determination` follows by band: `MEETING` when `composite_score` is at least 70, `MEETING_WITH_PROBLEMS` when `composite_score` is at least 50 but less than 70, and `NOT_MEETING` in every remaining case, that is when it is below 50. The top band is inclusive at its threshold, so an assessment scoring 70, 70 and 70 lands exactly on 70 and is `MEETING`. On finalization the allotment's `health_determination` takes this value, which is how a `NOT_MEETING` finding comes to bar new issuance, renewal and transfer under priority 10 until a corrective stocking-adjustment decision is effective.

The **recommended reduction** is computed by whichever of two variants the `monitoring_method` selects, and the two ignore different inputs, so the same underlying observations yield different recommendations under the two protocols. Under `INDICATOR_ASSESSMENT`, take 0.10 for each standard code listed in `standards_not_met`, add a further 0.10 when `causal_factor_is_livestock` is true, cap the result at 0.50, and round half-up to 4 decimal places; `observed_utilization_pct` is ignored entirely. Three unmet standards with livestock causation therefore recommend 0.4000, and four unmet standards with livestock causation reach exactly 0.5000 by arithmetic — 0.40 for the standards plus 0.10 for causation — landing on the cap rather than being truncated by it; because only four standard codes exist and duplicates are rejected, 0.5000 is the largest figure this variant can produce at all, so the cap is a stated ceiling that never actually cuts a sum down. Under `UTILIZATION_MAPPING`, the recommendation is exactly 0.0 when `observed_utilization_pct` is at most the target utilisation of 50 percent; otherwise subtract 50 from `observed_utilization_pct`, divide that difference by `observed_utilization_pct` itself, cap the quotient at 0.50, and round half-up to 4 decimal places. `standards_not_met` and `causal_factor_is_livestock` are ignored entirely by this variant. The value is never negative and never exceeds 0.50, and it is 0 whenever the `determination` is anything other than `NOT_MEETING`. The recommendation is advisory: it becomes binding only when an officer carries it into a stocking-adjustment decision, as §3.8 describes. Assessments are listed with filters on `allotment_id`, `assessment_year`, `monitoring_method`, `assessment_status` and `determination`.

### 3.8. Permit Decisions: Authorship, Environmental Review, Signature and Effect

Every permanent change to what a permittee is authorized to graze is made through a **permit decision** — a formal, appealable document that is authored, reviewed for environmental compliance, signed by a different officer, and only then put into effect. A `RangeSpecialist` authors one, supplying `decision_type`, `allotment_id`, `expected_allotment_version`, `nepa_level` and, as the type requires, `permit_id`, `assessment_id`, `adjustment_pct`, `effective_date` and `rationale`. The `decision_type` takes exactly four values — `ISSUANCE`, `STOCKING_ADJUSTMENT`, `SUSPENSION` and `CANCELLATION` — and it governs which of the optional inputs are permitted. A `STOCKING_ADJUSTMENT` decision is allotment-wide, so its `permit_id` may be null, but it requires a non-null `assessment_id` naming the assessment that justifies it and a non-null `adjustment_pct` strictly greater than 0 and at most 0.9, rounded to 4 decimal places on storage per §2.8 rather than refused for carrying more. Both `assessment_id` and `permit_id` are checked for existence alone, at priority 6: the named assessment need not be `FINALIZED`, need not carry any particular `determination`, and need not even belong to the allotment the decision names, and the named permit is likewise only required to exist. Nothing in this service ties a stocking adjustment's `adjustment_pct` to the `recommended_reduction_pct` of the assessment it cites. Every other `decision_type` requires a `permit_id` and must leave `adjustment_pct` null; supplying `adjustment_pct` on an `ISSUANCE`, `SUSPENSION` or `CANCELLATION` decision, or omitting it on a `STOCKING_ADJUSTMENT`, is a shape failure reported as `ERR_VALIDATION`. The `nepa_level` records the depth of environmental review the action demands and is one of `CX` for a categorical exclusion, `CATEGORICAL_EXCLUSION` as an accepted long spelling of that same level, `EA` for an environmental assessment or `EIS` for an impact statement; any other string is `ERR_VALIDATION`. The level is documentary and changes the workflow in one place only: at signature, where the longer rationale of §2.6 priority 11 is demanded of `EA` and `EIS` alone, `CATEGORICAL_EXCLUSION` behaving in every respect exactly as `CX` does and demanding nothing.

Authorship has three consequences beyond creating the row. The new decision lands in `decision_status` `DRAFT` with `nepa_status` `PENDING`, `nepa_findings_summary` null, `pre_decision_adjustment_pct` null, `deciding_officer_id` null and `effective_date` null unless supplied, and its `authoring_officer_id` is stamped with the authoring specialist's `X-User-ID`. It is written against a specific `expected_allotment_version` and is refused with `ERR_STALE_ALLOTMENT_VERSION` when that figure does not match the allotment's current `version`, exactly as §2.7 requires. And it **supersedes** any earlier decision of the same `decision_type` on the same allotment that is still in `decision_status` `DRAFT` or `PROPOSED`: each such predecessor moves straight to `VACATED`. That supersession is deliberately effect-free — a decision that has not yet become effective never applied a cascade, so nothing is unwound, no bill is superseded, and the predecessor's `pre_decision_adjustment_pct`, still null, is simply discarded. Authorship itself bumps the allotment's `version`, which means two decisions authored back to back against the same allotment cannot both quote the same `expected_allotment_version`; the second author must re-read the allotment first.

Environmental review is completed by a `RangeSpecialist`, who supplies `nepa_findings_summary`. The decision must be in `decision_status` `DRAFT` with `nepa_status` `PENDING`; calling it on a decision that is already `PROPOSED` or later is `ERR_DECISION_STATE_INVALID`. On success the `nepa_findings_summary` is stored, `nepa_status` becomes `COMPLETE`, and the decision moves `DRAFT → PROPOSED` in the same operation, so completing the review and proposing the decision are one act rather than two.

Signature is performed by an `AuthorizedOfficer`, who may attach a `rationale`. Three conditions gate it, and their order matters because they carry different statuses; it is the order of §2.6 rather than the order of exposition. The signing officer's `X-User-ID` must differ from `authoring_officer_id`, else `ERR_SEGREGATION_OF_DUTIES` at priority 4 — so an author who signs their own `DRAFT` decision sees the segregation failure and not the status failure. The decision must then be in `decision_status` `PROPOSED`, else `ERR_DECISION_STATE_INVALID`. And `nepa_status` must be `COMPLETE` with a non-blank `nepa_findings_summary`, else `ERR_ENVIRONMENTAL_REVIEW_INCOMPLETE`; because the proposal transition is the only way to set `nepa_status` to `COMPLETE`, a `PROPOSED` decision always satisfies this in practice, but the rule stands on its own. The `rationale` on this payload is optional and falls back rather than overwriting: when it is omitted or null the decision's existing `rationale`, as the author supplied it, is the rationale that both the `EA`/`EIS` length rule of priority 11 and the stored result use, so signing without a rationale never blanks one that was already there. On success `decision_status` becomes `FINAL`, `deciding_officer_id` is stamped with the signing officer's `X-User-ID`, and that resolved `rationale` is stored. Signature has one cross-entity effect: **every** appeal on this decision sitting in `appeal_status` `REMANDED` is returned to `UNDER_REVIEW`, closing the remand loop described in §3.9.

Putting a decision into effect is the moment its consequences reach the rangeland, and it is reserved to the same `AuthorizedOfficer` who signed it: the acting `X-User-ID` must equal `deciding_officer_id`, and any other officer is refused with `ERR_UNAUTHORIZED`. The three gates run in this fixed order: the reserved-identity match just described, then the appeal freeze — a decision in `decision_status` `STAYED` yields `ERR_DECISION_STAYED` — and only then the requirement that the decision be in `decision_status` `FINAL`, else `ERR_DECISION_STATE_INVALID`. Because the freeze is tested first, a stayed decision always reports `ERR_DECISION_STAYED` and never the state error, which is the priority 12 carve-out §2.6 records. Two fields are stamped **before** any cascade runs: `effective_date` takes the logical-clock date in `YYYY-MM-DD` form, and `pre_decision_adjustment_pct` takes a snapshot of the allotment's `stocking_adjustment_pct` **as it stands before the adjustment is applied**. Taking that snapshot first is what makes a later vacatur exactly reversible; taking it afterwards would record the new figure and make restoration a no-op. Then `decision_status` becomes `EFFECTIVE`, the type-specific cascade runs, and the allotment's `version` is bumped once.

The four cascades are deliberately unequal in reach. A `STOCKING_ADJUSTMENT` decision runs the complete five-hop reallocation of §3.10 from the top: the allotment's `stocking_adjustment_pct` is recomputed as the strongest active source rather than the sum of sources, so a decision imposing an `adjustment_pct` of 0.30 on an allotment already carrying a 0.40 drought reduction leaves the allotment at 0.40 and changes nothing downstream; the allotment's `effective_capacity_aums` and `allotment_status` are recomputed; every operating instruction of the allotment in the current grazing year and in `aoi_status` `ISSUED` or `USE_REPORTED` is re-authorized from its `authorized_aums_at_issue` snapshot; each such instruction's unpaid use bill is superseded; and each affected permittee's `outstanding_balance_cents` and each affected permit's `account_status` are recomputed. A `SUSPENSION` decision moves the named permit `permit_status` `ISSUED → SUSPENDED` with `suspension_reason` `DECISION` — the authorization dimension is written only when the permit is actually `ISSUED` at that moment, so a permit that has since been suspended, cancelled, expired or transferred keeps the `permit_status` and `suspension_reason` it already carries — and voids that permit's current-year instructions still in `aoi_status` `DRAFT`, which it does whatever the permit's status turned out to be. A `CANCELLATION` decision moves the named permit to `permit_status` `CANCELLED` from whatever status it held, with its `suspension_reason` cleared to null, and voids that permit's instructions in `aoi_status` `DRAFT` or `ISSUED` — in **every** grazing year rather than only the current one, which is where it differs from the suspension cascade. What that returns to the allotment ledger is exactly what those voided instructions held, namely the sum of their `billable_aums`, so `allocated_aums` falls by that figure and `open_aums` rises by it; the permit's own `permitted_aums` releases nothing, because a permit is never itself an entry in `allocated_aums` and cancelling one whose instructions were all `DRAFT` therefore moves the ledger not at all. An `ISSUANCE` decision runs **no cascade whatsoever**: it is the formal, appealable record that an authorization exists, it neither gates nor performs permit issuance, and the only observable change is its own `decision_status` together with the allotment `version` bump. An implementation that makes issuance a precondition of permit issuance, or that has an `ISSUANCE` decision touch capacity, is wrong.

A decision may also reach `EFFECTIVE` by a second route. When an appeal has frozen it in `decision_status` `STAYED` and the adjudicator then affirms or dismisses that appeal, the decision moves `STAYED → EFFECTIVE`, `effective_date` takes the clock date **at that later moment** rather than the date the officer first attempted it, and the full `decision_type` cascade runs then and only then. The mirror image is vacatur. When an adjudicator reverses an appeal against a decision in `decision_status` `EFFECTIVE`, the decision moves `EFFECTIVE → VACATED` and the four-hop restoration runs: for a `STOCKING_ADJUSTMENT`, the allotment's `stocking_adjustment_pct` is restored verbatim from `pre_decision_adjustment_pct` and `effective_capacity_aums` recomputed; then, because capacity moved, every current-year instruction in `aoi_status` `ISSUED` or `USE_REPORTED` has its `authorized_aums` recomputed from its own snapshot; then, because `billable_aums` moved, each such instruction's unpaid use bill is superseded by a `REVISED_USE` bill; then each affected permittee's `outstanding_balance_cents` is recomputed and each affected permit's `account_status` re-evaluated. For a `SUSPENSION`, the named permit moves `permit_status` `SUSPENDED → ISSUED` with `suspension_reason` cleared to null. In both cases the allotment's `allotment_status` is recomputed — returning `RESTRICTED → OPEN` when `stocking_adjustment_pct` falls to 0 and no closure order remains active — and the allotment's `version` is incremented by 1. A vacated `CANCELLATION` does not resurrect the cancelled permit and a vacated `ISSUANCE` unwinds nothing, because neither `permit_status` `CANCELLED` nor an effect-free issuance leaves anything to restore. Reversing an appeal against a decision that is merely `STAYED` moves it `STAYED → VACATED` and runs **no** cascade at all, because a stayed decision never applied its effects. The allotment `version` bump is nevertheless unconditional across the whole family: every vacatur writes the allotment row exactly once, whether or not a cascade ran and whether or not any allotment field moved, so the cascade-free `STAYED → VACATED` path and the vacatur of a `CANCELLATION` or an `ISSUANCE` each still advance the `version` by 1. One reversal case moves nothing at all: a `REVERSE` outcome against a decision that is merely `FINAL` — signed, unstayed and never put into effect — records the appeal as `REVERSED` but leaves the decision in `decision_status` `FINAL`, touching neither the decision nor the allotment, because vacatur reaches only the `EFFECTIVE` and `STAYED` statuses. `VACATED` is terminal in every case.

Decisions are fetched individually with their `nepa_status`, `adjustment_pct`, `pre_decision_adjustment_pct` and both officer identifiers visible, and listed with filters on `allotment_id`, `permit_id`, `assessment_id`, `decision_type`, `decision_status` and `nepa_status`.

### 3.9. Administrative Appeals: Filing, Stays, Remands and Adjudication

An **appeal case** is the permittee's remedy against a decision, and it is filed by a `Permittee` alone, in that permittee's own name. The filing payload carries `appellant_permittee_id`, `stay_requested` and `statement_of_reasons`, the last being between 10 and 1,000 characters inclusive. The `appellant_permittee_id` is client-supplied but never trusted: it must equal the acting `X-User-ID`, and a mismatch is `ERR_UNAUTHORIZED`, so the server neither infers the appellant silently nor lets one permittee appeal in another's name. That role gate and that identity match are the whole of the appellant test: the server never derives which permittee a decision affects, and imposes no further relationship between the appellant and the appealed decision, so any registered `Permittee` filing in its own name is accepted on any decision whose status allows an appeal. The appealed decision, identified by `decision_id` from the path, must be in `decision_status` `FINAL` or `EFFECTIVE`; appealing a decision that is still `DRAFT` or `PROPOSED`, or one already `STAYED` or `VACATED`, is `ERR_DECISION_STATE_INVALID`. The new case lands in `appeal_status` `FILED` with `remand_count` 0 and `adjudicator_id` null.

Whether a stay bites depends entirely on how far the decision had already travelled, and the two branches are genuinely different outcomes for the same `stay_requested` value. When `stay_requested` is true **and** the decision is in `decision_status` `FINAL` — signed but not yet in effect — the petition is granted at filing: `stay_granted` becomes true and the decision moves `FINAL → STAYED`, which freezes it completely. No allotment, permit, instruction or bill field is written by the stay; it is a pure hold. While the decision is `STAYED`, an attempt to put it into effect is refused with `ERR_DECISION_STAYED`. When the decision is already `EFFECTIVE`, a stay cannot un-ring the bell: `stay_granted` is false, the decision is untouched, and the appeal proceeds against a decision whose cascade has already run. When `stay_requested` is false the outcome is the same as the second branch regardless of `decision_status`.

Docketing is the `AppealsAdjudicator`'s act of taking the case up, and it moves `appeal_status` `FILED → UNDER_REVIEW` while stamping `adjudicator_id` with the docketing adjudicator's `X-User-ID`. Docketing does **not** touch `stay_granted`: the stay was granted or refused at filing time and is not revisited here. Docketing a case that is not in `appeal_status` `FILED` is `ERR_APPEAL_STATE_INVALID`, and in particular a `REMANDED` case is never returned to review through this endpoint — it returns only when the deciding officer re-signs the remanded decision.

Adjudication carries an `appeal_outcome` of `AFFIRM`, `REVERSE`, `REMAND` or `DISMISS`, and may attach a `decision_rationale`. Three gates run, in this order. The acting `X-User-ID` must equal `adjudicator_id` — the adjudicator who docketed the case is the only one who may decide it, and anyone else is `ERR_UNAUTHORIZED`. The adjudicator must then be neither the officer who signed the appealed decision nor the specialist who authored it, either collision being `ERR_SEGREGATION_OF_DUTIES`; the `deciding_officer_id` is compared first, so an identity that occupies both hands reports the signing collision. Only then must the case be in `appeal_status` `UNDER_REVIEW`, else `ERR_APPEAL_STATE_INVALID`. Both identity comparisons hold vacuously while the identifier they name is still null, as §2.10 requires, so a decision whose signature a remand has stripped presents no `deciding_officer_id` to collide with.

Each outcome carries its own consequences. `AFFIRM` moves the case to `appeal_status` `AFFIRMED`, sets `stay_granted` to false, and — if the appealed decision is `STAYED` — releases it into effect, running its full cascade at that moment. `DISMISS` moves the case to `DISMISSED` and behaves identically to `AFFIRM` in every respect other than the status recorded, which matters because dismissal on procedural grounds and affirmance on the merits leave the same footprint on the rangeland. `REVERSE` moves the case to `REVERSED`, sets `stay_granted` to false, and vacates the appealed decision: an `EFFECTIVE` decision runs the four-hop restoration of §3.8, while a `STAYED` decision is simply vacated with no cascade. `REMAND` moves the case to `REMANDED`, increments `remand_count` by 1, and pushes the appealed decision back down the chain to `PROPOSED` with `deciding_officer_id` and `rationale` both nulled — so the decision must be signed again, by an officer who still may not be its author, and the re-signature is what returns this same appeal to `UNDER_REVIEW` with its `remand_count` preserved. That push-down reaches exactly two statuses, `FINAL` and `STAYED`, both of which land on `PROPOSED`; a decision already `EFFECTIVE` is left in `EFFECTIVE` untouched, its cascade standing, and the remand then bears on the case alone. `REMAND` is also the one outcome that does **not** clear `stay_granted`: the flag keeps whatever value filing gave it, even though the decision it froze has been carried back to `PROPOSED`, whereas `AFFIRM`, `REVERSE` and `DISMISS` all set it to false. The optional `decision_rationale` behaves the same way on every outcome: a non-null value is stored and an omitted or null one leaves the field as it stood rather than clearing it. That loop is bounded: a remand is refused with `ERR_APPEAL_REMAND_LIMIT_EXCEEDED` once `remand_count` has reached 2, leaving the adjudicator to affirm, reverse or dismiss. `AFFIRMED`, `REVERSED` and `DISMISSED` are terminal. Appeals are fetched individually with their `stay_granted`, `remand_count` and `adjudicator_id` visible, and listed with filters on `decision_id`, `appellant_permittee_id`, `appeal_status` and `stay_granted`.

### 3.10. Drought and Wildfire Response: Closure Orders and the Reallocation Cascade

A **closure order** is the fast instrument. Where a stocking-adjustment decision takes weeks of authorship, review, signature and appeal, an `AuthorizedOfficer` issues a closure order in one call and the rangeland responds immediately. The payload carries `allotment_id`, `order_type`, `effective_start_date`, `effective_end_date`, a `justification` of between 10 and 500 characters recording the drought indicators or fire perimeter relied on, and, conditionally, `reduction_pct`. The `order_type` takes exactly three values. A `DROUGHT_REDUCTION` order is a partial cut and requires a `reduction_pct` strictly greater than 0.0 and at most 0.9. A `WILDFIRE_CLOSURE` order and a `FULL_CLOSURE` order are total: `reduction_pct` should be omitted, or sent as exactly 1.0, and the server records 1.0 in either case. Supplying a `reduction_pct` other than 1.0 on a total closure, or omitting it on a `DROUGHT_REDUCTION`, is a shape failure reported as `ERR_VALIDATION`. The order's date interval is **closed at both ends**, in force from `effective_start_date` through `effective_end_date` inclusive, and `effective_end_date` must not precede `effective_start_date`, which is `ERR_INVALID_DATE_RANGE`. The order lands in `order_status` `ACTIVE` with `issuing_officer_id` stamped from the issuing officer's `X-User-ID`.

Closure orders must be spaced. A new order is refused with `ERR_CLOSURE_ORDER_OVERLAP` when its `effective_start_date` falls on or before the `effective_end_date` of any existing order on the same allotment in `order_status` `ACTIVE`, plus a buffer of 7 days. Concretely: with an active order ending on a given day, a new order starting on that day itself overlaps, because both intervals are inclusive and touching ends collide; a new order starting on any of the following 7 days is inside the buffer and is refused; a new order starting on the eighth day after that end date is accepted. Orders in `order_status` `LIFTED` or `EXPIRED` constrain nothing, so a lifted order's interval may be immediately re-covered. The test is stated on the new order's start date alone and has no lower bound, which has one consequence worth spelling out: an interval lying wholly **earlier** than the active order is refused by this same rule, because its `effective_start_date` is necessarily on or before that order's `effective_end_date` plus seven days. While an order is active on an allotment, the only accepted start dates are those from the eighth day after its end onward.

Issuing an order runs the **five-hop reallocation cascade** in strict order, and each hop's input is the previous hop's output. Hop one recomputes the allotment's `stocking_adjustment_pct`. It is exactly 1.0 when any closure order on the allotment in `order_status` `ACTIVE` has `order_type` `WILDFIRE_CLOSURE` or `FULL_CLOSURE`. Otherwise it is the **maximum** over two families of contributors: the `reduction_pct` of every closure order on the allotment in `order_status` `ACTIVE`, and the `adjustment_pct` of every permit decision on the allotment with `decision_type` `STOCKING_ADJUSTMENT` and `decision_status` `EFFECTIVE`. That maximum is capped at 0.9 and rounded half-up to 4 decimal places. When neither family has a member the figure is exactly 0.0. Contributors are **never summed**: a 0.40 drought reduction standing beside a 0.30 effective stocking adjustment yields 0.40, not 0.70. Orders in `order_status` `LIFTED` or `EXPIRED` contribute nothing, and decisions in `decision_status` `DRAFT`, `PROPOSED`, `FINAL`, `STAYED` or `VACATED` contribute nothing.

Hop two recomputes the allotment's posture from that fraction. The `effective_capacity_aums` becomes the allotment's own `total_permitted_aums` multiplied by one minus `stocking_adjustment_pct`, floored to a whole AUM — exactly the first line of the capacity ledger of §2.9, and never the `carrying_capacity_aums` of any base property, which is a preference-qualification input and plays no part in allotment capacity — so a 0.40 reduction on a permitted ceiling of 1,000 AUMs yields 600, and a total closure yields 0. The `allotment_status` becomes `CLOSED` when `stocking_adjustment_pct` is exactly 1.0, `RESTRICTED` when it is strictly between 0 and 1, and `OPEN` when it is exactly 0. The 0.9 cap therefore has a precise meaning: partial sources can never close an allotment, because 0.9 leaves a tenth of the capacity standing and the posture stays `RESTRICTED`; only a wildfire or full closure order, whose 1.0 bypasses the cap, moves the allotment to `CLOSED`. When this hop carries the allotment into `CLOSED` from any other posture, it also fires the project termination of §3.12 — every project of the allotment still in `project_status` `APPROVED` moves to `TERMINATED` — and it fires that only on the transition, so a recomputation that leaves an already-`CLOSED` allotment closed terminates nothing further.

Hop three re-authorizes the grazing year. For every operating instruction of the allotment whose `grazing_year` equals the allotment's `current_grazing_year` and whose `aoi_status` is `ISSUED` or `USE_REPORTED`, the `authorized_aums` becomes the instruction's own `authorized_aums_at_issue` snapshot multiplied by one minus `stocking_adjustment_pct`, floored to a whole AUM, and `billable_aums` becomes the new `authorized_aums` less `nonuse_aums`. Recomputing from the snapshot rather than from the current `authorized_aums` is what makes successive reductions non-compounding: two 0.40 events in a season leave the instruction at 60 percent of its issue-time authorization, not 36 percent, and lifting the second event restores it exactly. Instructions in `aoi_status` `DRAFT`, `BILLED`, `CLOSED` or `VOIDED` are **not** re-authorized, and instructions of any other `grazing_year` are untouched.

Hop four settles the money. Each re-authorized instruction's outstanding use bill is superseded at the new `billable_aums` by a bill of `bill_type` `REVISED_USE` carrying `superseded_bill_id`, provided the old bill's `amount_paid_cents` is exactly 0; a bill that has already received money is left standing and the difference is issued as an `ADJUSTMENT_CREDIT`, or an `ADJUSTMENT_DEBIT` were the movement upward, exactly as §3.6 prescribes. Only a bill of `bill_type` `PRELIMINARY_USE`, `FINAL_USE` or `REVISED_USE` sitting in `bill_status` `ISSUED` or `DELINQUENT` is a candidate for that settlement — an `ADJUSTMENT_DEBIT` or `ADJUSTMENT_CREDIT` bill is never itself superseded or re-adjusted, and where more than one candidate somehow exists the most recently raised one is the subject. Three further consequences of the branch are pinned. When the candidate is unpaid the supersession is unconditional and is not gated on the figure having moved: the old bill is voided, with its `void_reason` left null because the system supplies none, and a `REVISED_USE` replacement is raised even when its total is identical to the voided one, and even when the new total is exactly 0 — so a total closure that drives `billable_aums` to 0 leaves a zero-amount `REVISED_USE` bill behind rather than no bill, the zero-bill suppression of §3.4 applying to instruction issuance alone. When the candidate has already received money the reverse holds, and a difference of exactly 0 raises **no** bill at all. And when the instruction has no candidate at all — because none was ever raised, or because the only one has already reached `PAID` or `VOIDED` — hop four does nothing whatsoever for that instruction: no bill is created, no adjustment is issued, and money already settled is not revisited. Hop five closes the ledger: each affected permittee's `outstanding_balance_cents` and `permittee_status` are recomputed and each of their permits' `account_status` is re-derived. The allotment's `version` is bumped once for the whole cascade. The cascade is a **single pass**: hop three's changes to instruction authorizations never feed back into hop one, so the fixed point is reached in one traversal and an implementation that iterates to convergence will produce different, wrong figures. Hops one and two always run; hops three, four and five run only when hop one's recomputed fraction actually differs from the fraction the allotment already carried. Adding a source no stronger than the strongest one already in force therefore rewrites `stocking_adjustment_pct` and `allotment_status` to the same values and stops there — no instruction is re-authorized, no bill is superseded and no balance is recomputed — while the allotment's own `version` is still bumped once for the event.

Lifting is the reverse instrument. An `AuthorizedOfficer` lifts an order that is in `order_status` `ACTIVE`, optionally recording a fresh `justification`; lifting one already `LIFTED` or `EXPIRED` is `ERR_CLOSURE_ORDER_STATE_INVALID`. The lift payload's `justification` is optional and nullable but keeps the issuing shape when it is supplied — between 10 and 500 characters, on pain of `ERR_VALIDATION` — and when it is omitted or null the order keeps the justification it was issued with rather than having it cleared. The order moves `ACTIVE → LIFTED` and the identical five-hop cascade re-runs over the **remaining** sources, so a lift recomputes rather than subtracts: lifting a 0.40 drought order while a 0.30 effective stocking adjustment survives leaves the allotment at 0.30 and `RESTRICTED`, not at 0.0 and `OPEN`. Because hop three works from `authorized_aums_at_issue`, instruction authorizations are restored to precisely their pre-reduction figures, and hop four supersedes the unpaid `REVISED_USE` bills again at the restored amounts.

Expiry is the same movement driven by the clock rather than by an officer. When the logical clock advances, every closure order in `order_status` `ACTIVE` whose `effective_end_date` falls **strictly before** the new clock date moves to `order_status` `EXPIRED` and runs the same recomputation chain — allotment posture, capacity, instruction authorizations, bill supersession and permittee balances. An order whose `effective_end_date` equals the new clock date is still in force, because the interval's end is inclusive. The sweep expires every qualifying order first and then recomputes once per **distinct** affected allotment, so when several orders on one allotment expire in the same clock advance that allotment's chain runs a single time and its `version` is bumped once for the advance rather than once per order; each expired order's own row is written once, of course. This expiry sweep is the second of the three the clock advance performs, and §2.5 fixes its position: bill delinquency has already run, permit term expiry has not yet run. Both `LIFTED` and `EXPIRED` are terminal. Closure orders are fetched individually and listed either across all allotments — narrowed there by `allotment_id`, `order_status` and `order_type` — or beneath one allotment, where the allotment comes from the path and the only filters accepted are `order_status` and `order_type`.

### 3.11. Trespass Detection and Unauthorized-Use Billing

Livestock found on public range without authorization is recorded as a **trespass incident**, and the charge for it is computed on a wholly different basis from a grazing bill: the permittee pays the full commercial forage value rather than the subsidised federal fee, plus a penalty scaled by intent and by history. A `RangeSpecialist` records the incident with `allotment_id`, `permittee_id`, `detected_at`, `head_count`, `livestock_kind`, `unauthorized_days` and `willfulness`. The `detected_at` is an ISO 8601 UTC instant; `head_count` is at least 1; `unauthorized_days` is at least 1; `livestock_kind` is `CATTLE`, `SHEEP` or `HORSES`; and `willfulness` is `NON_WILLFUL`, `WILLFUL` or `REPEATED_WILLFUL`. The `permittee_id` may be null when ownership of the livestock is undetermined, which is the ordinary case for a fresh detection. The incident lands in `incident_status` `DETECTED`.

Two figures are established at detection. The `unauthorized_aums` is computed immediately as `head_count` multiplied by the animal-unit equivalent of `livestock_kind` — 1.0 for `CATTLE`, 0.2 for `SHEEP`, 1.25 for `HORSES` — multiplied by `unauthorized_days` and divided by 30 days per AUM, rounded half-up to 2 decimal places. The `prior_billed_incident_count` is **snapshotted at detection time and never recomputed**: it is the count of other incidents of the same `permittee_id` whose `incident_status` is `BILLED` or `RESOLVED` and whose `detected_at` is strictly earlier than this incident's `detected_at`. Because it is a snapshot, an incident detected before an earlier incident is billed carries the count as it stood when this incident was detected, which is why the field lives on the incident rather than being read from the permittee's running `billed_trespass_incident_count` at billing time.

Billing the incident is an `AuthorizedOfficer`'s act. The incident must be in `incident_status` `DETECTED`, else `ERR_TRESPASS_STATE_INVALID`, and its `permittee_id` must be non-null — an incident whose owner is still undetermined cannot be billed, and attempting it is `ERR_TRESPASS_STATE_INVALID`. The charge is then computed in seven steps whose order is binding. Step one recomputes `unauthorized_aums` as at detection, to 2 decimal places. Step two sets `billed_aums` to `unauthorized_aums` rounded **up** to the next whole AUM, so 12.01 unauthorized AUMs are billed as 13; unlike a use bill, an unauthorized-use charge is never billed in fractional AUMs. Step three sets `base_amount_cents` to `billed_aums` multiplied by the full forage value of 2,340 cents per AUM, which is also recorded as the bill's `fee_rate_cents_per_aum`; because `billed_aums` is a whole number the product is exact. Step four selects the willfulness multiplier: 1.0 for `NON_WILLFUL`, 2.0 for `WILLFUL` and 3.0 for `REPEATED_WILLFUL`. Step five computes the repeat factor as 1.0 plus 0.25 for each prior billed incident recorded in `prior_billed_incident_count`, capped at 2.0 — so the factor climbs 1.0, 1.25, 1.50, 1.75, 2.0 and then stops, a fifth and any later prior incident adding nothing. Step six sets `penalty_amount_cents` to `base_amount_cents` multiplied by the willfulness multiplier less 1.0, multiplied by the repeat factor, rounded half-up to a whole cent. Subtracting 1.0 from the multiplier before applying the repeat factor is what makes a `NON_WILLFUL` incident penalty-free: its multiplier is exactly 1.0, so the penalty is 0 no matter how many prior incidents the permittee has, and an implementation that multiplies the base by the multiplier and treats the excess as the penalty will levy a repeat-factor-inflated charge on an unwilful trespasser. Step seven sets `total_amount_cents` to `base_amount_cents` plus `penalty_amount_cents`, and sets `admin_fee_cents` to exactly 0 — the tiered administrative fee of §3.6 does **not** apply to an unauthorized-use bill, whatever the size of the base amount.

On success a bill of `bill_type` `UNAUTHORIZED_USE` is issued against the incident's `permittee_id` with `trespass_incident_id` naming the incident, `aoi_id` and `project_id` null, a `due_date` of the clock date plus 30 days, and `bill_status` `ISSUED`; the incident moves `DETECTED → BILLED`; and the permittee's `outstanding_balance_cents` and `billed_trespass_incident_count` are recomputed. The incident's life is cyclic rather than linear. Paying that bill in full moves the incident `BILLED → RESOLVED`, which is terminal. Voiding that bill instead cycles the incident `BILLED → DETECTED` and recomputes both the permittee's `outstanding_balance_cents` and its `billed_trespass_incident_count`, restoring the money-conservation invariant of §2.9 exactly; the incident is then billable again, and a re-bill recomputes the charge from the incident's stored inputs and its unchanged `prior_billed_incident_count` snapshot. Incidents are fetched individually with their `unauthorized_aums`, `billed_aums` and `prior_billed_incident_count` visible, and listed with filters on `allotment_id`, `permittee_id`, `willfulness` and `incident_status`. Both reads are row-scoped for a `Permittee` actor exactly as §2.1 requires, and the scoping key is the incident's own `permittee_id` rather than the allotment it names: a `Permittee` sees only the incidents attributed to it, and because an undetermined incident's `permittee_id` is null it belongs to nobody — it is filtered out of every `Permittee` listing, and a `Permittee` reading it directly is refused with `ERR_UNAUTHORIZED`, while every other operational role sees it normally.

### 3.12. Range Improvement Projects and Pro-Rata Cost-Share Allocation

A **range improvement project** builds infrastructure that benefits every operator on an allotment — a fence, a water development or a seeding — and its cost is split between the agency and the permittees who graze there. A `RangeSpecialist` proposes one with `allotment_id`, `project_type` — one of `FENCE`, `WATER_DEVELOPMENT`, `SEEDING`, `VEGETATION_TREATMENT` or `EROSION_CONTROL`, any other string being `ERR_VALIDATION` — `total_cost_cents` of at least 1, the two fractions `agency_share_pct` and `permittee_share_pct`, each between 0 and 1 inclusive and rounded to 4 decimal places on storage per §2.8 rather than refused for carrying more, and a `maintenance_responsibility` of `AGENCY`, `PERMITTEE` or `SHARED` recording who keeps the improvement in repair thereafter. The two fractions must add to **exactly** 1.0; any other sum is `ERR_VALIDATION`. That sum is tested on the two values exactly as submitted, before the 4-decimal rounding is applied, so a pair that sums to 1.0 at greater precision is accepted and the two figures the project then stores need not themselves sum to exactly 1.0. The project lands in `project_status` `PROPOSED` with `permittee_share_cents` and `allocated_share_cents` both 0.

Approval is an `AuthorizedOfficer`'s act and does one arithmetic thing: it fixes the pot. The project must be in `project_status` `PROPOSED`, else `ERR_PROJECT_STATE_INVALID`, and the allotment must not be in `allotment_status` `CLOSED`, else `ERR_ALLOTMENT_CLOSED` — there is no point contracting improvements on range no livestock may enter. On success `project_status` becomes `APPROVED` and `permittee_share_cents` is set to `total_cost_cents` multiplied by `permittee_share_pct`, rounded half-up to a whole cent. Fixing the figure at approval rather than at allocation matters, because `total_cost_cents` and `permittee_share_pct` are frozen from that moment as far as the allocation is concerned.

Allocation distributes that pot across the operators and is likewise an `AuthorizedOfficer`'s act, requiring `project_status` `APPROVED` on pain of `ERR_PROJECT_STATE_INVALID`. The eligible pool is every grazing permit on the project's allotment whose `permit_status` is exactly `ISSUED`; permits in `permit_status` `PENDING_REVIEW`, `SUSPENDED`, `CANCELLED`, `EXPIRED` or `TRANSFERRED` — that is, every other member of the enumeration — are excluded, and a permit's `account_status` is irrelevant to eligibility, so a delinquent but issued permit still takes its share. The pool's total is the sum of `permitted_aums` over the eligible permits.

An **empty pool is a success, not a failure**. When the allotment has no permit in `permit_status` `ISSUED`, or when the eligible permits' `permitted_aums` sum to 0, the allocation still completes: nothing is distributed, `allocated_share_cents` is set to 0, `project_status` becomes `COST_ALLOCATED`, and no bill of any kind is raised. There is deliberately no error for this case, and returning one is wrong.

Otherwise the distribution runs in three passes and must land on the pot exactly, to the cent. Pass one computes each permit's provisional share as `permittee_share_cents` multiplied by that permit's `permitted_aums` divided by the pool total, **floored** to a whole cent. Flooring every share necessarily leaves a remainder, so pass two computes that remainder as `permittee_share_cents` less the sum of the floored shares, ranks the eligible permits by `permitted_aums` **descending** and then, for ties, by `created_at` **ascending**, and adds exactly one cent to each of the first as many permits as there are remainder cents. The permit `id` is **never** used as a tie-break; where `permitted_aums` and `created_at` are both equal the ordering is whatever the two preceding keys establish. Pass three raises one bill of `bill_type` `PROJECT_COST_SHARE` per eligible permit whose final share is greater than 0, charged to that permit's `permittee_id`, with `project_id` naming the project, `aoi_id` and `trespass_incident_id` null, `billed_aums` of 0 and `fee_rate_cents_per_aum` of 0 because a cost share is not forage, `base_amount_cents` and `total_amount_cents` both equal to the share, `admin_fee_cents` and `penalty_amount_cents` both 0, a `due_date` of the clock date plus 30 days, and `bill_status` `ISSUED`. A permit whose final share is 0 receives no bill. Then `allocated_share_cents` is set to `permittee_share_cents` exactly, `project_status` becomes `COST_ALLOCATED`, and each billed permittee's `outstanding_balance_cents` is recomputed. The invariant is unconditional: the sum of `total_amount_cents` over the project's non-voided `PROJECT_COST_SHARE` bills equals `permittee_share_cents`, so no cent is created and none is lost in the rounding.

A project may also end without ever being allocated. When the allotment moves to `allotment_status` `CLOSED` — which happens when a `WILDFIRE_CLOSURE` or `FULL_CLOSURE` order takes effect — every project of that allotment still in `project_status` `APPROVED` moves to `project_status` `TERMINATED` as a side effect, with no bill raised and `allocated_share_cents` left at 0. Projects still in `project_status` `PROPOSED` are not terminated; they simply cannot be approved while the allotment stays closed. Both `COST_ALLOCATED` and `TERMINATED` are terminal. Projects are fetched individually with their `permittee_share_cents` and `allocated_share_cents` visible, and listed with filters on `allotment_id`, `project_type`, `maintenance_responsibility` and `project_status`.

## 5. Error Code Catalogue

Every failure the service can return is listed below with the HTTP status code it must carry. The `error_id` string in the response body's `data` object must match the identifier in this table exactly, character for character, and the accompanying `message` is a human-readable explanation whose wording is not constrained. When more than one failure applies to a single request, the one reported is the one that comes first in the priority ordering of §2.6. Three further identifiers belong to the request framework rather than to any workflow above and so are deliberately absent from the table: `ERR_NOT_FOUND` with HTTP 404 for a path the service does not route at all, `ERR_METHOD_NOT_ALLOWED` with HTTP 405 for a routed path called with a method it does not support, and `ERR_INTERNAL` with HTTP 500 for an unexpected server fault.
