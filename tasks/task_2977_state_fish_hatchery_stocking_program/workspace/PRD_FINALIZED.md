# Fish Hatchery Stocking API — Product Requirements Document

## 1. Introduction

A state fish and wildlife agency runs its hatchery program as one continuous production line that begins with a ripe brood female and ends with a tanker truck backing down a boat ramp. Between those two points the agency must answer questions that today live in spreadsheets, radio traffic and a filing cabinet of paper certificates: how many acre-feet of adjudicated water an egg take will actually consume, whether a lot of fingerlings still carries a valid fish-health certificate on the morning the truck is loaded, how a finite production pool should be divided between a regional biologist's management-plan target and a member of the public asking for trout in a local pond, and whether the station's discharge is inside the limits of its NPDES permit. Each of those questions is individually tractable. What breaks the paper system is that they are coupled: a second effluent exceedance inside a quarter can freeze the station, and freezing the station has to unwind spawning windows and planned egg takes that were scheduled weeks earlier.

This document specifies the API for the program of record. The service owns brood stock and spawning windows, rearing lots and their feed-conversion arithmetic, fish-health inspections and the treatment-and-retest cycle that precedes certification, the allocation of finished production across waters, the transport trips that deliver it, and the marking programs that later measure what the release contributed to the fishery. It is deliberately a ledger-first design: water rights, standing crop, appropriated budget and fish counts are all tracked as conserved quantities, so that every reservation has an exact compensating release and no operator action can silently lose a resource.

Two design commitments run through everything that follows. First, the service is the single point of refusal for every biological, fiscal and regulatory constraint — an operator cannot load a truck past its oxygen rating or ship fish out of a quarantined lot, because the server declines. Second, every temporal rule reads a logical clock the service itself maintains rather than wall-clock time, which makes seasons, withdrawal periods, certificate expiry and rest buffers all reproducible.

## 2. Global Specifications & System-Wide Principles

Every collection described here is mounted at the root of the service. The topology is flat: records reference one another through identifier fields carried in request bodies rather than through nested URL hierarchies, with the single exception of a station's discharge-monitoring record, which is read as a sub-resource of the station.

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. A request whose `X-User-ID` header is absent, empty, or consists only of whitespace is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This is the very first thing the server checks — it precedes role authorisation, existence lookups, and request-shape validation alike. Once the caller is identified, the server checks whether the role named in `X-User-ID`'s companion header is permitted to invoke the operation at all; if it is not, the answer is `ERR_FORBIDDEN_ROLE` (HTTP 403).

There are exactly five roles, spelled as follows: `ProgramAdmin`, `HatcheryManager`, `FishHealthVeterinarian`, `RegionalBiologist`, and `PublicRequester`.

A `ProgramAdmin` is the statewide program administrator. The role owns the reference data — stations, waters, allocation plans, the transport fleet — plus the allocation selector and the logical clock. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any record's `id`, and a `ProgramAdmin` is never scoped to a single station.

A `HatcheryManager` runs exactly one station, and the role is the one entity-backed identity in the system. When `X-User-Role` is `HatcheryManager`, `X-User-ID` is the `id` of the acting `Hatchery`; ownership checks on any resource that references a `Hatchery` compare the resource's `hatchery_id` to `X-User-ID`. Where the target record does not carry `hatchery_id` directly, the server follows the chain to one that does — a spawn event through its brood group, a health inspection or a stocking trip through its rearing lot, an allocation plan or a transport unit through its own `hatchery_id`. A manager who addresses an existing record belonging to another station is refused with `ERR_HATCHERY_SCOPE_VIOLATION` (HTTP 403). Scope is evaluated only on a record that was actually found, so an identifier in the URL that resolves to nothing yields that collection's 404 instead; and a manager acting on another station's existing record always sees `ERR_HATCHERY_SCOPE_VIOLATION` — never a 404, and never a request-shape complaint. Scope applies to every `HatcheryManager` write, and additionally to two reads: reading a station, and listing a station's discharge samples.

A `FishHealthVeterinarian` is the fish-health professional who samples lots, records laboratory results, prescribes treatment, and signs certificates. When `X-User-Role` is `FishHealthVeterinarian`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it — as `sampled_by_user_id` when an inspection is opened and as `certified_by_user_id` when a certificate is signed — but never compares it to any record's `id`. Those two recorded values exist to enforce segregation of duties: the veterinarian who sampled a lot may not be the one who signs its certificate, and an attempt to do so is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Because both principals hold the same role, this is not a role check; it is the same role refused because it is the same person. The certifying veterinarian needs no other relationship to the lot.

A `RegionalBiologist` authors stocking requests on behalf of the waters in a region and evaluates tag recoveries. A `PublicRequester` is a member of the public submitting a stocking request. For both, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as `requested_by_user_id` on the request the principal submits, but does not compare it to any record's `id`. Ownership of a request is decided against that recorded value: withdrawing a request, and attaching a request to an allocation plan, act only on requests whose `requested_by_user_id` equals the caller's `X-User-ID`, and otherwise return `ERR_NOT_REQUEST_OWNER` (HTTP 403). A `ProgramAdmin` is exempt from that ownership test and may withdraw or attach any requester's request.

The role boundaries are strict in both directions. Production writes — opening a spawning window, planning and recording an egg take, recording a feeding, advancing a rearing stage, scheduling a trip, loading it and releasing it — belong to `HatcheryManager` alone, and a `ProgramAdmin` attempting one is refused. Every fish-health write belongs to `FishHealthVeterinarian` alone. Registering a station, registering or retiring a water, creating an allocation plan, running one, and advancing the logical clock belong to `ProgramAdmin` alone. Authoring a stocking request belongs to `RegionalBiologist` and `PublicRequester`; neither a `ProgramAdmin` nor a `HatcheryManager` may author demand. Reporting tag recoveries is shared between `ProgramAdmin` and `RegionalBiologist`. Registering a brood group, registering a transport unit, and logging a discharge sample are shared between `HatcheryManager` (own station only) and `ProgramAdmin` (unscoped); cancelling a planned take and aborting a trip are shared the same way. A `PublicRequester` may read waters and stocking requests and nothing else — reads of stations, brood groups, spawn events, rearing lots, inspections, allocation plans, transport units and stocking events all return `ERR_FORBIDDEN_ROLE` for that role. A `PublicRequester` also may not attach a request to a plan, because queueing demand onto a production pool is a program decision rather than a requester's.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Ordering and Filtering

Every list endpoint accepts two optional pagination parameters. `limit` controls page size: it defaults to 10 when omitted, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls how many records are skipped before the page begins: it defaults to 0 and its minimum accepted value is 0. A `limit` or `offset` outside those bounds, or of the wrong type, is a request-shape failure and yields `ERR_INVALID_REQUEST` (HTTP 400) rather than being silently clamped.

List responses carry four pagination fields inside `meta`: `limit` and `offset` echoing the values in force, `total_count` giving the number of records matching the filters before paging, and `has_more` indicating whether any matching record remains beyond the current page. Unless a specific endpoint says otherwise, list endpoints return records in ascending `created_at` order — oldest first. The one documented departure is the discharge-monitoring record of a station, which is returned newest sample first.

Beyond paging, lists accept the domain filters that make them useful, and an unrecognised value for any of them is likewise `ERR_INVALID_REQUEST`. Waters may be filtered by `status`, `plan_species` and `county`. Brood groups accept `hatchery_id`, `species` and `status`. Spawn events accept `brood_stock_id` and `status`. Rearing lots accept `hatchery_id`, `spawn_event_id`, `rearing_stage`, `health_status` and `species` — this is how a lot brought into existence by a recorded egg take is discovered, since lots have no creation endpoint of their own. Health inspections accept `lot_id`, `status` and `inspection_type`. Stocking requests accept `water_id`, `allocation_plan_id`, `status`, `requester_kind` and `species`. Allocation plans accept `hatchery_id`, `status` and `fiscal_year`. Transport units accept `hatchery_id`, `status` and `current_event_id`. Stocking events accept `lot_id`, `stocking_request_id`, `transport_unit_id` and `status`. A station's discharge samples accept `status`.

### 2.4. The Logical Clock

Nothing in this service reads wall-clock time for a business decision. Spawning windows, health-certificate validity, drug-withdrawal periods, transport-certification lapse, the rolling effluent window and a water's rest buffer are all evaluated against a single logical clock the service maintains, which a `ProgramAdmin` sets by supplying a `current_utc` instant. Until it is ever set, the clock reads `2026-08-01T00:00:00Z`. The clock may be moved forward or backward freely; there is no monotonicity requirement.

Advancing the clock is not a passive assignment. On every clock set, and in this order, the service re-evaluates the whole world: it recomputes each station's `exceedance_count_rolling` and then its `operating_posture`, which may freeze a station and suspend its spawning groups, or thaw a station and resume them; it lapses every health certificate whose expiry the clock has now passed, moving the affected rearing lot's `health_status` from `CERTIFIED` back to `UNSCREENED`; it closes every brood group whose `spawning_window_end` the clock has reached or passed; and it takes every available transport unit `OUT_OF_SERVICE` once the clock reaches or passes that unit's `certification_expires_at`. Each of these consequences is spelled out in the workflow section that owns it.

Two temporal inputs are validated against the clock rather than against each other. A discharge sample's `sampled_at` and a health inspection's `sampled_at` must not be after the clock — you cannot log a sample from the future. Likewise the `taken_at` instant recorded with an egg take must not be after the clock. All instants in this API, whether supplied by the caller or minted by the server, are ISO 8601 UTC timestamps with three fractional digits.

### 2.5. Station Ledgers as Conserved Quantities

A hatchery station is, for the purposes of this API, three ledgers and a standing-crop meter. Each ledger is a strict three-way split, and the split must hold after every single write. The service is expected to maintain these identities rather than merely to report them.

The **water-right ledger** splits the station's adjudicated `annual_water_right_af` into `water_reserved_af`, `water_used_af` and `water_available_af`, where `water_available_af` is the `annual_water_right_af` minus `water_reserved_af` minus `water_used_af`, carried to four decimal places. `water_reserved_af` is the sum of the acre-feet held by that station's spawn events still in `PLANNED` status; `water_used_af` is the sum of the acre-feet consumed by spawn events that reached `TAKEN`, plus the `flow_af` of every discharge sample logged against the station. Planning a take reserves acre-feet; cancelling that planned take returns exactly the same acre-feet; recording the take converts reserved acre-feet into used acre-feet. The identity — adjudicated right equals available plus reserved plus used — holds after the reservation, after the cancellation, and after the conversion.

The **appropriation ledger** splits `annual_budget_cents` into `budget_committed_cents`, `budget_spent_cents` and `budget_available_cents`, where `budget_available_cents` is `annual_budget_cents` minus `budget_committed_cents` minus `budget_spent_cents`. `budget_committed_cents` is the total transport cost of the station's stocking events in `SCHEDULED` or `IN_TRANSIT` status; `budget_spent_cents` is the total transport cost of those that reached `RELEASED`. Scheduling a trip commits its cost; aborting the trip releases exactly the same cents back to available; releasing the fish moves exactly the same cents from committed to spent. The identity never drifts.

The **standing-crop meter** is `biomass_on_hand_lbs`, the sum of `biomass_lbs` across the station's rearing lots whose `rearing_stage` is neither `RELEASED` nor `TERMINATED`, and `density_index`, that biomass divided by the station's permitted `rearing_capacity_lbs`. The station also declares an `oxygen_supply_lpm` — the bulk liquid-oxygen delivery rate available to loading operations — an `effluent_permit_number`, and a `tss_permit_limit_mg_l` ceiling, together with a `name`, a `station_code` and a `water_source_type`.

Fish are conserved too, at the level of a single rearing lot: a lot's `initial_count` always equals its `count_on_hand`, plus its `reserved_count`, plus its `cumulative_mortality_count`, plus the fish already released out of it. This is why aborting a stocking trip is specified as an exact restoration rather than an approximation: after an abort, the lot's `count_on_hand` and `reserved_count` read exactly as they did before the trip was created, and the granting request's `allocated_count` together with the destination water's `allocated_count_ytd` are restored as well.

### 2.6. Operating Posture: How Compliance Gates Production

Every station carries a derived compliance dimension called `operating_posture`, which takes one of three values — `OPEN`, `RESTRICTED` or `FROZEN` — and which is never set directly by a caller. A newly registered station is `OPEN`. The posture is recomputed from three inputs whenever any of them can have changed: the station's `exceedance_count_rolling`, its `water_available_af` and its `density_index`.

The recomputation is ordered worst-first, so that a frozen station never reads as merely restricted. The service first tests the freeze conditions: if `exceedance_count_rolling` is two or more, or `water_available_af` is zero or below, the posture becomes `FROZEN`. Only if neither freeze condition holds does the service test the restriction conditions: if `exceedance_count_rolling` is exactly one, or `density_index` is at or above 0.90, the posture becomes `RESTRICTED`. If none of those conditions hold, the posture is `OPEN`. The boundaries are exact: a `density_index` of precisely 0.90 is `RESTRICTED` while 0.8999 is `OPEN`, and `water_available_af` of precisely 0 is `FROZEN` because that comparison includes equality. Because the freeze test runs first, a station with two exceedances inside the rolling window is `FROZEN` even when its density is comfortable and its water right untouched.

Posture is cyclic — there is no terminal posture, and a station recovers on its own as its exceedances age out of the rolling window, its density falls back, or acre-feet are returned to it. All six edges are real and all six are reachable. A station moves from `OPEN` to `RESTRICTED` when a restriction condition becomes true while no freeze condition is true; that recomputation follows a recorded feeding, a logged discharge sample, a recorded egg take, or a clock advance. It moves from `OPEN` to `FROZEN`, or from `RESTRICTED` to `FROZEN`, when a freeze condition becomes true; that recomputation follows a logged discharge sample or a planned egg take. It moves from `RESTRICTED` back to `OPEN` when `exceedance_count_rolling` is zero and `density_index` is below 0.90 and `water_available_af` is above zero; that recomputation follows a recorded feeding, a released trip, or a clock advance. It moves from `FROZEN` to `RESTRICTED` when `exceedance_count_rolling` has fallen to exactly one and `water_available_af` is above zero, which happens on a clock advance that pushes an exceedance sample out of the rolling window. And it moves from `FROZEN` straight to `OPEN` when `exceedance_count_rolling` has fallen to zero, `density_index` is below 0.90 and `water_available_af` is above zero, which happens on a clock advance that ages out every exceedance at once.

What the posture gates differs by value, and the difference is deliberate. At `RESTRICTED`, only new intake is refused: planning a new egg take is rejected with `ERR_HATCHERY_RESTRICTED` (HTTP 409), while loading trucks and releasing fish stay perfectly legal, because those are precisely the operations that lower standing crop and let a restricted station recover. At `FROZEN`, five operations are refused with `ERR_HATCHERY_FROZEN` (HTTP 409): opening a spawning window, planning an egg take, recording an egg take, running an allocation plan, and loading a truck.

Entering `FROZEN` also triggers a cascade, and leaving it triggers the partial reverse. When a station becomes `FROZEN` — whether from `OPEN` or from `RESTRICTED` — every brood group of that station in `SPAWNING` status transitions to `SUSPENDED`, and because each of those groups is now suspended, each of its spawn events still in `PLANNED` status transitions to `CANCELLED`, returning that event's committed females to the group's available pool and that event's reserved acre-feet to the station's available water. When a station leaves `FROZEN` — whether to `RESTRICTED` or to `OPEN` — every brood group of that station in `SUSPENDED` status whose spawning window still contains the clock transitions back to `SPAWNING`. Spawn events cancelled by the freeze are not resurrected; the females and acre-feet they returned stay returned, and a manager who wants those takes back must plan them again.

### 2.7. Common Record Properties and Revision Semantics

Every record in this service carries a server-minted `id`, which is a UUID with no type prefix of any kind. Every record carries a `created_at` timestamp, an ISO 8601 UTC instant with three fractional digits, recorded when the record is first written.

Almost every record additionally carries an `updated_at` timestamp of the same format and a `version` integer. `version` begins at 1 when the record is created and increments by exactly one on every mutation of that record, whether the mutation came from a caller acting on it directly or from a cascade reaching it from elsewhere. `updated_at` is refreshed on the same occasions. There is exactly one exception: a discharge sample carries only `id` and `created_at`. Discharge samples have neither `updated_at` nor `version`, because they are immutable once written — there is no endpoint that modifies one, and the record's classification is decided at the instant it is logged.

Because cascades cross record boundaries, revision bookkeeping does too. When recording a laboratory result quarantines a lot and unwinds its scheduled trips, the inspection's `version` advances, and so does the `version` of the rearing lot, of each aborted stocking event, of each transport unit released back to the fleet, of each stocking request pushed back into the queue, and of each affected water and station. The rule to hold onto is that every record the service actually changes gets a `version` bump and a fresh `updated_at`, and no record the service merely reads does.

### 2.8. Optimistic Concurrency: Writing Against a Revision You Have Read

Three writes in this API change a shared parent record in a way that only makes sense relative to the state the caller believes that parent is in. Those three carry a mandatory optimistic-concurrency token: a non-optional input field naming the `version` the caller last observed on the parent. If the value does not match the parent's current `version`, the write is refused and nothing is mutated. This is not a race-detection mechanism and does not depend on requests overlapping in time — it is a staleness test against a value the caller read at some earlier point.

Scheduling a stocking trip must carry `expected_lot_version`, matching the current `version` of the `RearingLot` named by `lot_id`. Scheduling a trip reserves fish out of that lot's `count_on_hand`, so the caller has to prove it reserved against the count it actually read. Any earlier write that touched the lot — a recorded feeding, a stage advance, a health cascade, another trip scheduled against the same lot — has advanced the lot's `version`, and a mismatch is rejected with `ERR_STALE_LOT_VERSION` (HTTP 412). The version check is evaluated before the state checks, before the health and capacity gates, and before the reservation itself. On success the lot's `version` advances by one.

Running an allocation plan must carry `expected_plan_version`, matching the current `version` of the `AllocationPlan` addressed in the URL. A run resolves the entire queued candidate set at once, so the caller must prove it read the plan after the last attach. Every attach advances the plan's `version`, so a run built from an older read is refused with `ERR_STALE_PLAN_VERSION` (HTTP 412) rather than silently allocating against a candidate set that has changed underneath it. The version check is evaluated before `ERR_NO_ELIGIBLE_REQUESTS` and before every per-request eligibility test. On success the plan's `version` advances by one.

Attaching a stocking request to a plan must likewise carry `expected_plan_version`, matching the current `version` of the plan named by `allocation_plan_id` in the body. Attaching enlarges the plan's candidate set, and because two different requests attaching to one plan both advance that plan's `version`, the second caller has to re-read the plan before it may attach; otherwise `ERR_STALE_PLAN_VERSION` (HTTP 412). This check is evaluated before the plan's own status checks and before `ERR_SIZE_CLASS_MISMATCH`. On success the plan's `version` advances by one.

No other endpoint accepts a version field. In particular, recording a feeding, advancing a stage, opening or resulting or certifying an inspection, loading, releasing or aborting a trip, and withdrawing a request all take no concurrency token at all.

### 2.9. Numeric Precision, Rounding and Units

Unless a rule below says otherwise, every rounding operation in this specification rounds half up. Where a value is described as floored or ceilinged, that is stated explicitly and half-up rounding does not apply.

Money is handled exclusively in integer cents; there are no fractional cents anywhere in the appropriation ledger, and the one place a fractional cent could arise — the per-pound term of a transport cost — is ceilinged so that a partial cent always rounds up to the next whole cent.

Weights, volumes and rates each carry their own scale. Pounds of fish and pounds of feed are carried to two decimal places: a lot's `biomass_lbs`, its `initial_biomass_lbs`, its `cumulative_mortality_biomass_lbs`, a trip's `planned_load_lbs`, and the intermediate volume and oxygen limits of a load plan. The conversion between grams and pounds uses 453.592 grams to the pound throughout. A station's `density_index` is carried to four decimal places, as is every acre-foot figure in the water-right ledger and a spawn event's `water_reserved_af`. Feed-conversion ratios — both `fcr_biological` and `fcr_economic` — are carried to three decimal places. A lot's `growth_rate_g_per_day` is carried to four decimal places. A trip's `oxygen_flow_lpm` is carried to three decimal places. A discharge sample's `exceedance_margin_mg_l` is carried to three decimal places. A spawn event's `cumulative_survival` is carried to four decimal places, and both contribution indices on a released trip are carried to four decimal places. Percentages — a water's `plan_fill_pct` and the plan-gap term inside a request's priority score — are carried to two decimal places, and a request's `priority_score` is likewise two decimal places. A temperature delta is carried to two decimal places.

Counts are integers, always. A spawn event's `required_eggs_for_target` is ceilinged to a whole egg while its `projected_release_count` is floored to a whole fish; a load plan's `max_fish_allowed` is floored to a whole fish; acclimation minutes are whole minutes and always a multiple of six; and every allocation grant is a whole multiple of 25 fish.

### 2.10. The Order of Refusal

A single request can violate several rules at once. When it does, the error the caller sees must be a deterministic function of the request rather than of the order in which the server happened to evaluate its checks. Every write endpoint therefore evaluates its rules against one total ladder and returns the **first** violation it meets. The ladder, from first evaluated to last, is:

1. **Authentication** — the `X-User-ID` header is present and not blank.
2. **Role authorisation** — the acting role may invoke this operation at all.
3. **Ownership and station scope** — the acting principal may touch this particular record. This is where `ERR_HATCHERY_SCOPE_VIOLATION` and `ERR_NOT_REQUEST_OWNER` live.
4. **Path record existence** — the identifier in the URL resolves to a record of the addressed collection.
5. **Body foreign-key existence** — each identifier carried in the body resolves, checked left to right in the order the endpoint declares its inputs.
6. **Request shape** — required fields present and non-null, types correct, enum values recognised, numbers inside their declared ranges, strings matching their declared patterns, and interval field pairs not inverted.
7. **Optimistic concurrency** — the supplied expected parent version matches.
8. **Own-record state** — the target record is in a status that has a transition for this operation.
9. **Cross-record state** — a related record is in a status that permits this operation.
10. **Business safety** — the health, certification and drug-withdrawal gates, plus the release temperature and tempering gates.
11. **Segregation of duties** — the acting user is not the user who performed the prior step.
12. **Temporal conflicts** — trip-interval overlap, the water rest buffer, and the station's shared oxygen supply.
13. **Capacity and count ceilings** — density, transport load, lot fish availability, brood females, allocation ceiling and stage weight.
14. **Referential agreement** — species and size-class agreement between related records.
15. **Fiscal ceilings** — the water right and the appropriation.

Because the ladder is total, whenever two rules are both violated the one with the lower number always wins. Three consequences of that are worth stating explicitly, because they are easy to get backwards. Loading a stocking trip that has already been aborted, on a lot that has since been quarantined, violates both the own-record state rule and the quarantine safety rule; the answer is `ERR_INVALID_STATE` (HTTP 409) and never `ERR_LOT_QUARANTINED` (HTTP 422), because state sits at level 8 and safety at level 10. A load whose trip interval overlaps another trip on the same truck **and** whose `fish_count` exceeds the warm-water load plan answers `ERR_TRANSPORT_UNIT_UNAVAILABLE` (HTTP 409) and never `ERR_TRANSPORT_CAPACITY_EXCEEDED` (HTTP 422), because temporal conflicts sit at level 12 and capacity ceilings at level 13. And scheduling a trip against a quarantined lot with a transport cost the appropriation cannot absorb answers `ERR_LOT_QUARANTINED` (HTTP 422) and never `ERR_BUDGET_EXCEEDED`, because safety sits at level 10 and fiscal ceilings at level 15.

Level 10 has internal ordering of its own on the load operation, and it matters because three different findings all describe "this lot may not be shipped". Quarantine is checked first, because it is the most specific and most serious finding, and reports `ERR_LOT_QUARANTINED`. An expired certificate is checked next and reports `ERR_HEALTH_CERTIFICATE_EXPIRED`; a lot that has never been certified at all reports `ERR_LOT_NOT_CERTIFIED`. An unelapsed drug-withdrawal window is checked last within the level and reports `ERR_WITHDRAWAL_PERIOD_ACTIVE`. The distinction between the expired and never-certified findings is possible precisely because a lapsed certificate leaves its expiry instant on the lot rather than clearing it — see the certificate-lapse rule in the fish-health workflow.

There is exactly one carve-out from the ladder. Recording a treatment against an inspection that has reached `FAILED_REPORTABLE` reports `ERR_PATHOGEN_NOT_TREATABLE` (HTTP 422) rather than the generic `ERR_INVALID_STATE` (HTTP 409), because the reason no transition exists is exactly the reportable finding itself. Every other illegal originating status for that operation — `SAMPLED`, `RETEST_DUE`, `PASSED` or `CERTIFIED` — reports `ERR_INVALID_STATE` as usual.

### 2.11. Resolving Identifiers

Identifiers reach the service in two places, and each has its own failure code. An identifier in the URL path is resolved against the collection the path addresses, and a value that resolves to nothing produces that collection's own 404: `ERR_HATCHERY_NOT_FOUND`, `ERR_WATER_NOT_FOUND`, `ERR_BROOD_STOCK_NOT_FOUND`, `ERR_SPAWN_EVENT_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND`, `ERR_REQUEST_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_TRANSPORT_UNIT_NOT_FOUND` or `ERR_EVENT_NOT_FOUND`. Where a path nests one collection inside another — a station's discharge-monitoring record is the only such path — the segments are validated left to right, so an unknown station is reported before anything about the sub-resource is considered.

Identifiers carried in a request body are resolved the same way, against the collection each one names, and they too report the referenced collection's own 404. Body keys are resolved strictly left to right in the order the endpoint declares its inputs, which makes the reported error predictable when a caller sends several bad identifiers at once. Scheduling a stocking trip, for example, declares `stocking_request_id` first, then `lot_id`, then `transport_unit_id`; a body in which all three are unknown reports `ERR_REQUEST_NOT_FOUND`. Existence of the body's identifiers is settled before the remaining scalar fields are shape-validated, so a body with both an unknown identifier and a malformed number reports the 404, not `ERR_INVALID_REQUEST`.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Station and Keeping Its Discharge Record

A `ProgramAdmin` brings a station into the system by registering it with a `name`, a `station_code`, a `water_source_type`, an `annual_water_right_af` figure, a permitted `rearing_capacity_lbs`, an `oxygen_supply_lpm` rating, an `effluent_permit_number`, a `tss_permit_limit_mg_l` ceiling and an `annual_budget_cents` appropriation. The `station_code` is a four-character code drawn only from uppercase letters and digits, and it must be unique across every station on file — a duplicate is refused with `ERR_DUPLICATE_STATION_CODE` (HTTP 409). The `water_source_type` describes where the rearing water comes from and is one of `SPRING`, `WELL` or `SURFACE`.

Registration seeds all three ledgers at rest. `water_reserved_af` and `water_used_af` both start at zero, so `water_available_af` starts equal to `annual_water_right_af`. `biomass_on_hand_lbs` starts at zero and `density_index` at zero. `exceedance_count_rolling` starts at zero and `operating_posture` at `OPEN`. `budget_committed_cents` and `budget_spent_cents` both start at zero, so `budget_available_cents` starts equal to `annual_budget_cents`. One consequence of registration deserves emphasis because it is how station scoping works at all: the new station's `id` is the value a `HatcheryManager` must present as `X-User-ID` in order to act on that station's records.

Discharge monitoring is the compliance spine of the whole system. Either the station's own manager or a `ProgramAdmin` logs a sample by naming the `hatchery_id` it belongs to, the `sampled_at` instant it was drawn, the `tss_mg_l` total-suspended-solids concentration, the `total_phosphorus_mg_l` concentration and the `flow_af` discharge volume for the reporting period in acre-feet. All three measurements must be zero or greater, and `sampled_at` must not be after the logical clock. The sample classifies itself: its `status` becomes `EXCEEDANCE` if the `tss_mg_l` figure is strictly above the station's `tss_permit_limit_mg_l`, or if `total_phosphorus_mg_l` is strictly above the statewide total-phosphorus limit of 0.10 mg/L; otherwise it is `COMPLIANT`. A sample landing exactly on either limit is `COMPLIANT`, because both comparisons are strictly greater. Alongside the classification the service records `exceedance_margin_mg_l`, which is the amount by which `tss_mg_l` overshot the station's ceiling, floored at zero so that a compliant sample records a margin of zero, and rounded to three decimal places.

Logging a sample has three further consequences. The sample's `flow_af` is added to the station's `water_used_af`, and `water_available_af` is recomputed — a station can therefore drink its own water right dry through discharge alone, which is one of the two ways `water_available_af` can reach zero and freeze it. The station's `exceedance_count_rolling` is recomputed as the number of that station's discharge samples whose `status` is `EXCEEDANCE` and whose `sampled_at` falls strictly after the instant ninety days before the clock; a sample drawn exactly ninety days ago has aged out and no longer counts, because the old edge of the window is exclusive. Finally the station's `operating_posture` is recomputed from the new count, the new available water and the current density. A second `EXCEEDANCE` inside the ninety-day window drives `exceedance_count_rolling` to two, which freezes the station and cascades into its `SPAWNING` brood groups and their `PLANNED` egg takes exactly as described in the operating-posture rules.

A discharge sample is a permanent record. There is no operation that edits or deletes one, it carries no `version` and no `updated_at`, and its classification is final at the moment it is written. The station's own manager and a `ProgramAdmin` may read a station's samples back as a list, newest sample first, optionally filtered by `status`; a manager reading another station's samples is refused with `ERR_HATCHERY_SCOPE_VIOLATION`.

### 3.2. Brood Groups and the Spawning Window

A brood group is a holding of ripe adults of one species and one genetic line, registered either by the station's own manager or by a `ProgramAdmin`. Registration names the `hatchery_id` holding the group, the `species`, the `strain` label, the `female_count` and `male_count` of ripe adults held, the planning `expected_fecundity_per_female` in eggs per spawned female, the `spawning_window_start` and `spawning_window_end` instants, and the season's `egg_take_target` in eggs. The `species` value is one of `RAINBOW_TROUT`, `BROWN_TROUT`, `KOKANEE`, `WALLEYE` or `CHINOOK` — the same five-species vocabulary used by waters, allocation plans, requests and rearing lots. Each of `female_count`, `male_count` and `expected_fecundity_per_female` must be at least 1, and `spawning_window_end` must fall strictly after `spawning_window_start`; an inverted window is a request-shape failure.

A newly registered group opens in `READY` status with its female ledger at rest: `females_reserved` and `females_spent` both zero, so `females_available` — the `female_count` less the reserved and the spent — equals the whole `female_count`, and `cumulative_eggs_taken` is zero.

Only the station's own manager may declare the group ripe, moving it from `READY` to `SPAWNING`; a manager whose `X-User-ID` is not the group's `hatchery_id` is refused with `ERR_HATCHERY_SCOPE_VIOLATION`. Two conditions guard the transition. The logical clock must lie inside the group's spawning window — at or after `spawning_window_start` and strictly before `spawning_window_end` — and a clock outside that range is refused with `ERR_SPAWN_WINDOW_CLOSED` (HTTP 409). The station's `operating_posture` must not be `FROZEN`, and a frozen station is refused with `ERR_HATCHERY_FROZEN` (HTTP 409). Note the asymmetry with new egg takes: opening a window is permitted at `RESTRICTED`, because the window itself consumes nothing. Attempting to open a group that is not in `READY` status at all — one already `SPAWNING`, one `SUSPENDED`, or one `CLOSED` — is `ERR_INVALID_STATE` (HTTP 409). A group that reaches `SPAWNING` is the only kind of group against which egg takes may be planned.

The `SPAWNING` status is not permanent, and it can be lost in two very different ways. A compliance freeze at the station drives every `SPAWNING` group there to `SUSPENDED`, and that suspension cancels each of the group's `PLANNED` egg takes, returning their committed females and their reserved acre-feet. When the station later leaves `FROZEN`, a `SUSPENDED` group whose spawning window still contains the clock returns to `SPAWNING` — but a group whose window has meanwhile closed does not, and its cancelled takes are never restored. Separately, the group closes for the season. The end of a recorded egg take evaluates whether `cumulative_eggs_taken` has reached or passed `egg_take_target`, and a `SPAWNING` group that has met its target transitions to `CLOSED`. A clock advance closes any group, `SPAWNING` or `SUSPENDED`, whose `spawning_window_end` the clock has reached or passed.

`CLOSED` is terminal. A group in `READY`, `SUSPENDED` or `CLOSED` status is not a legal parent for a new egg take or for a recorded take, and both operations refuse it with `ERR_BROOD_STOCK_NOT_SPAWNING` (HTTP 409). Every role except `PublicRequester` may read a single group with its female ledger, or list groups filtered by `hatchery_id`, `species` and `status`; a manager reading another station's group is refused with `ERR_HATCHERY_SCOPE_VIOLATION`.

### 3.3. Planning an Egg Take, and Recording What Was Actually Taken

An egg take is planned before it happens and reconciled afterwards, and the two halves of that story are what make the water-right ledger work. Only the station's own manager may plan a take, by naming the `brood_stock_id` of the group to be spawned, the `planned_take_date` on which the crew intends to strip it, the `females_spawned` count committed to this take, and the `target_release_count` — the number of fish this one take is meant to deliver to the stocking program at release size. `females_spawned` must be at least 1. A planned take opens in `PLANNED` status.

Planning immediately computes a survival-chained projection from eggs in the tray to fish at the truck. The eggs the take can expect to yield, `planned_eggs`, is the `females_spawned` count multiplied by the group's `expected_fecundity_per_female`. Three fixed stage survivals then chain together: 0.80 of eggs reach fry, 0.90 of fry reach fingerling, and 0.95 of fingerlings reach release. That chained product is then derated by how crowded the station already is, using a density tier read from the station's `density_index` **as it stands at the moment the take is planned** — a factor of 1.00 when `density_index` is below 0.50, 0.95 when it is at or above 0.50 but below 0.90, and 0.85 when it is at or above 0.90. The take's `cumulative_survival` is the product of the three stage survivals and the derate factor, rounded to four decimal places. From it the service derives two planning numbers: `required_eggs_for_target`, the `target_release_count` divided by `cumulative_survival` and rounded **up** to a whole egg, telling the crew how many eggs they need to hit the target; and `projected_release_count`, the `planned_eggs` figure multiplied by `cumulative_survival` and rounded **down** to a whole fish, telling the program what this take will actually deliver. The derate tier is resolved once and never revisited: a station sitting at a `density_index` of 0.4999 projects on the 1.00 tier even though the incoming eggs will push it past 0.50, and a later feeding that changes the station's density does not re-project an existing take.

Planning also reserves two scarce resources. Water is reserved at the rate of 0.05 acre-feet per thousand eggs, so the take's `water_reserved_af` is `planned_eggs` divided by one thousand, multiplied by 0.05, rounded to four decimal places; that figure is added to the station's `water_reserved_af`, and the station's `water_available_af` is recomputed. Females are reserved by adding `females_spawned` to the group's `females_reserved`, which lowers `females_available` correspondingly and advances the group's `version`. If the take asks for more females than the group has available, it is refused with `ERR_BROOD_FEMALES_INSUFFICIENT` (HTTP 422); if the acre-feet it would reserve exceed the station's `water_available_af`, it is refused with `ERR_WATER_RIGHT_EXCEEDED` (HTTP 422). Planning is also the operation most tightly gated on compliance: the parent group must be in `SPAWNING` status or the answer is `ERR_BROOD_STOCK_NOT_SPAWNING`, the station must not be `FROZEN` or the answer is `ERR_HATCHERY_FROZEN`, and — uniquely among all operations — the station must not be `RESTRICTED` either, or the answer is `ERR_HATCHERY_RESTRICTED`. Because the reservation can drive `water_available_af` to zero or below, planning a take is itself one of the two operations after which the station's posture is recomputed and may freeze.

Recording the take closes the loop. The station's own manager supplies the `eggs_taken` actually collected and the `taken_at` instant of collection, and the take moves from `PLANNED` to `TAKEN`. The group must still be `SPAWNING` and the station must still not be `FROZEN`. `taken_at` must not be after the logical clock and `eggs_taken` must be at least 1; either failure is `ERR_INVALID_REQUEST`. The fiscal gate is evaluated against the actual count rather than the planned one: the acre-feet the actual `eggs_taken` will consume — that count divided by one thousand, multiplied by 0.05, rounded to four decimal places — must not exceed the station's `water_available_af` plus the reservation this very take already holds, and otherwise the answer is `ERR_WATER_RIGHT_EXCEEDED`. Adding the take's own reservation back in is what lets a take that comes in exactly as planned always succeed.

On success the take's `eggs_taken` and `taken_at` are persisted and every ledger settles. The group's `females_reserved` falls by `females_spawned` while its `females_spent` rises by the same amount, its `cumulative_eggs_taken` rises by `eggs_taken`, and its `version` advances. The station's `water_reserved_af` falls by this take's `water_reserved_af` while its `water_used_af` rises by the acre-feet the actual egg count consumed — reserved water becoming used water, with the adjudicated total untouched. If `cumulative_eggs_taken` has now reached or passed the group's `egg_take_target`, the group transitions to `CLOSED`.

The recorded take is also the only way a rearing lot comes into existence; there is no operation that creates one directly. The new lot copies the station as its `hatchery_id` and the group's `species` as its own `species`, records the originating take as its `spawn_event_id`, opens at `rearing_stage` `EGG` and `health_status` `UNSCREENED` with a null `certificate_expires_at`, and takes `initial_count` and `count_on_hand` both equal to `eggs_taken`. Its `avg_weight_g` starts at the standard egg weight of 0.1 grams. Its `initial_biomass_lbs` — `initial_count` multiplied by that 0.1-gram egg weight, converted to pounds at 453.592 grams per pound and rounded to two decimal places — is frozen at creation and never recomputed thereafter; its `biomass_lbs` is computed the same way from the live `count_on_hand` and `avg_weight_g` and is recomputed for the rest of the lot's life. `reserved_count`, `cumulative_mortality_count`, `cumulative_mortality_biomass_lbs` and `cumulative_feed_lbs` all start at zero, and `growth_rate_g_per_day`, `fcr_biological` and `fcr_economic` all start null. Finally the station's `biomass_on_hand_lbs`, `density_index`, `water_available_af` and `operating_posture` are recomputed, which is how a large take can restrict the station it was taken at.

A planned take that will not happen is unwound rather than left to rot, and the unwinding is exact. Either the station's own manager or an unscoped `ProgramAdmin` may cancel a take in `PLANNED` status, moving it to `CANCELLED`. Cancellation subtracts `females_spawned` from the group's `females_reserved`, returning those females to `females_available`, and subtracts the take's `water_reserved_af` from the station's `water_reserved_af`, returning those acre-feet to `water_available_af`; the station's `water_available_af` and `operating_posture` are then recomputed, so cancelling a take can thaw a station that a reservation had frozen. The same cancellation, with the same two restorations, is what a compliance freeze performs on every `PLANNED` take of a suspended group. Both `TAKEN` and `CANCELLED` are terminal: recording a take against a cancelled event, cancelling one that has already been taken, or cancelling one twice all answer `ERR_INVALID_STATE`. Every role except `PublicRequester` may read a take with its survival projection, or list takes filtered by `brood_stock_id` and `status`.

### 3.4. Rearing: Feedings, Growth, Feed Conversion and Stage Gates

A rearing lot carries two entirely independent state dimensions on the same record, and keeping them separate is essential to reading the rest of this document correctly. The growth dimension, `rearing_stage`, runs `EGG` to `FRY` to `FINGERLING` to `YEARLING` and then to one of the two terminal values `RELEASED` or `TERMINATED`. The disease dimension, `health_status`, runs `UNSCREENED`, `UNDER_INSPECTION`, and then `CERTIFIED`, `RESTRICTED` or `QUARANTINED`, with `CERTIFIED` falling back to `UNSCREENED` when a certificate lapses. The two advance on their own triggers: a lot may perfectly well be `YEARLING` and `QUARANTINED`, or `FRY` and `CERTIFIED`. Only the pair together decides whether the lot can be shipped.

Feeding is where the growth dimension actually gets its numbers. The station's own manager records a feeding period by supplying the `fed_at` instant the period ended, the `feed_lbs` of feed delivered during it, the new mean individual weight `avg_weight_g_after`, and optionally the `mortality_count` observed since the previous feeding. When `mortality_count` is omitted it is treated as zero. A feeding is not itself a resource of this service — it has no `id` of its own, no read endpoint and no list filter — so recording one is a modification of the rearing lot rather than a creation: a successful feeding answers HTTP 200 with the updated rearing lot in `data`, not HTTP 201.

The arithmetic of a feeding runs in a fixed order. The dead fish leave first: `count_on_hand` falls by `mortality_count` and `cumulative_mortality_count` rises by the same number. The lot's `avg_weight_g` is then replaced by the supplied `avg_weight_g_after`, and `growth_rate_g_per_day` is recorded as the increase in mean weight over this period — the supplied `avg_weight_g_after` less the `avg_weight_g` the lot carried immediately before this feeding — divided by the number of whole days between this feeding's `fed_at` and the previous feeding's `fed_at`, or, for the lot's very first feeding, between `fed_at` and the lot's `created_at`. The result is rounded to four decimal places, and when that span works out to zero whole days the rate is recorded as null rather than as any number. The pounds lost to mortality in this period — `mortality_count` multiplied by `avg_weight_g_after`, converted to pounds at 453.592 grams per pound and rounded to two decimal places — are added to the lot's running `cumulative_mortality_biomass_lbs`. The lot's `biomass_lbs` is then recomputed from the surviving `count_on_hand` and the new `avg_weight_g`, and `feed_lbs` is added to `cumulative_feed_lbs`.

Feed conversion is reported under both industry conventions, on every feeding, always. `fcr_biological` credits only the fish still standing: it is `cumulative_feed_lbs` divided by the lot's current `biomass_lbs` less its frozen `initial_biomass_lbs`, rounded to three decimal places. `fcr_economic` credits the pounds that died as well: it is `cumulative_feed_lbs` divided by the sum of `biomass_lbs` and `cumulative_mortality_biomass_lbs`, less `initial_biomass_lbs`, again rounded to three decimal places. There is no selector between them — both are computed and both are stored, and the two are the lot's current cumulative figures. Because the economic denominator is the biological one plus the mortality pounds, `fcr_economic` is always at or below `fcr_biological`, and the two coincide only for a lot that has recorded no mortality at all. Whenever a denominator works out to zero or below, that variant is recorded as null rather than as any number.

Two consequences of a feeding reach beyond the lot. First, the station's `biomass_on_hand_lbs`, `density_index` and `operating_posture` are all recomputed, which is how feeding a growing lot restricts a station and how the mortality in a feeding relaxes it. Second, a feeding is refused outright — with nothing written at all, not even the feed — when the `density_index` the station would carry afterwards would exceed the hard cap of 1.0000; that refusal is `ERR_DENSITY_CAP_EXCEEDED` (HTTP 422). The cap boundary is inclusive on the legal side: a feeding that lands the station at exactly 1.0000 is accepted, while one that would land it at 1.0100 is refused and nothing is written. Note that this hard cap sits above the 0.90 restriction threshold, so there is a band in which a station is `RESTRICTED` but feeding still works — deliberately, because the fish on hand still have to eat.

The end of a feeding also asks whether the lot has run out. A lot whose `count_on_hand` has fallen to zero, whose `reserved_count` is zero, and whose `cumulative_mortality_count` has reached its `initial_count` — that is, a lot whose entire cohort died — transitions to `rearing_stage` `TERMINATED` and leaves the station's `biomass_on_hand_lbs` for good.

Advancing the growth dimension is a separate, deliberate act by the station's own manager, who names the `to_stage` being advanced into. Advancement is strictly one step at a time: from `EGG` the only legal target is `FRY`, from `FRY` only `FINGERLING`, and from `FINGERLING` only `YEARLING`. Any non-adjacent target, and any attempt to advance a lot that is already at `YEARLING`, `RELEASED` or `TERMINATED`, is `ERR_INVALID_STATE`. Each target carries a minimum mean weight the lot must have reached, and the gate is inclusive: `FRY` requires an `avg_weight_g` of at least 1.0 grams, `FINGERLING` at least 4.0 grams, and `YEARLING` at least 45.0 grams. A lot at exactly 4.0 grams may advance to `FINGERLING`; one at 3.99 grams may not, and is refused with `ERR_STAGE_WEIGHT_NOT_MET` (HTTP 422). Advancing a stage touches `health_status` not at all — a lot that was `RESTRICTED` before the advance is still `RESTRICTED` after it — and it advances the lot's `version`. Because the set of lots counted into a station's standing crop is defined by `rearing_stage`, a stage advance also triggers a recomputation of the station's `biomass_on_hand_lbs` and `density_index`.

The remaining growth transition belongs to the trip workflow rather than to rearing: a lot at `FRY`, `FINGERLING` or `YEARLING` whose `count_on_hand` and `reserved_count` have both reached zero transitions to `rearing_stage` `RELEASED`, evaluated at the end of a released trip, and that lot's biomass then leaves the station's `biomass_on_hand_lbs` with `density_index` and `operating_posture` recomputed accordingly. Every role except `PublicRequester` may read a lot — including the `version` a trip creation must quote — or list lots by `hatchery_id`, `spawn_event_id`, `rearing_stage`, `health_status` and `species`.

### 3.5. Fish Health: Sampling, Treatment, Retesting and Certification

No lot leaves a hatchery without a current health certificate signed by a veterinarian who did not draw the sample. Getting there is a small state machine of its own, and it is deliberately cyclic: a treatable finding can be treated and retested, twice, before the program gives up and declares the lot unshippable.

A `FishHealthVeterinarian` opens an inspection by naming the `lot_id` sampled, the `inspection_type` — `PRE_TRANSFER` for a pre-shipment screen or `ROUTINE` for surveillance — the `sample_size` of fish sacrificed for the assay, and the `sampled_at` instant of sampling. At least 30 fish must be sacrificed, and `sampled_at` must not be after the logical clock. Only one inspection may be open on a lot at a time: if another inspection on the same lot is still in `SAMPLED` or `RETEST_DUE` status, the new one is refused with `ERR_INVALID_STATE` (HTTP 409). A lot already under quarantine cannot be sampled at all, and is refused with `ERR_LOT_QUARANTINED` (HTTP 422). The new inspection opens in `SAMPLED` status with `retest_count` zero, no `result` and no `pathogen_code` yet, and the acting veterinarian recorded as `sampled_by_user_id`. Opening an inspection also drives the lot's `health_status` to `UNDER_INSPECTION` and clears the lot's `certificate_expires_at` to null, advancing the lot's `version`. That is worth dwelling on: re-inspecting a lot that was `CERTIFIED` withdraws its standing certificate outright, immediately, before any result is known — a lot under inspection is not shippable.

Recording a laboratory result supplies the `result` value and, with a positive finding, the `pathogen_code` observed. The recognised results are `NEGATIVE`, `POSITIVE_TREATABLE` and `POSITIVE_REPORTABLE`; anything else is `ERR_INVALID_REQUEST`. A quarantined lot cannot have results recorded against it and answers `ERR_LOT_QUARANTINED`. From `SAMPLED`, the three results branch three ways, and each branch carries the same weight of consequence. A `NEGATIVE` result moves the inspection to `PASSED`, with `certificate_expires_at` staying null until the certificate is actually signed. A `POSITIVE_TREATABLE` result moves the inspection to `FAILED_TREATABLE`, persists the `pathogen_code`, and drives the lot's `health_status` to `RESTRICTED` with its `certificate_expires_at` cleared to null — a `RESTRICTED` lot may still be fed and still be advanced through rearing stages, but it may not be shipped, and an attempt to load it answers `ERR_LOT_NOT_CERTIFIED`. A `POSITIVE_REPORTABLE` result moves the inspection to `FAILED_REPORTABLE`, persists the `pathogen_code`, and quarantines the lot with the full unwind cascade described at the end of this subsection.

A treatable finding opens the treatment-and-retest cycle. The veterinarian records the therapeutant applied by supplying the `treatment_code`, the mandatory `withdrawal_days` period in days, and the `treatment_completed_at` instant the course finished; the inspection moves from `FAILED_TREATABLE` to `RETEST_DUE` and its `retest_count` rises by one. The `treatment_code` must be one of the recognised therapeutant codes and `withdrawal_days` must be zero or greater, and either failure is `ERR_INVALID_REQUEST`. The service then computes `withdrawal_clears_at` as the `treatment_completed_at` instant advanced by `withdrawal_days` days. That instant is a hard gate on shipping: while the logical clock is before it, loading a truck from this lot is refused with `ERR_WITHDRAWAL_PERIOD_ACTIVE` (HTTP 422). Attempting to record a treatment against an inspection that has reached `FAILED_REPORTABLE` answers `ERR_PATHOGEN_NOT_TREATABLE` (HTTP 422) — a reportable pathogen may not be treated out — while every other illegal originating status answers `ERR_INVALID_STATE`.

From `RETEST_DUE` the retest result branches three ways as well, and the branches mirror the ones out of `SAMPLED` with two additions. A `NEGATIVE` retest moves the inspection to `PASSED`, but only once the drug-withdrawal window has cleared: if the clock is still before `withdrawal_clears_at`, the retest is refused with `ERR_WITHDRAWAL_PERIOD_ACTIVE`. A `POSITIVE_TREATABLE` retest, while `retest_count` is still below the ceiling of two, cycles the inspection back to `FAILED_TREATABLE` and drives the lot's `health_status` back to `RESTRICTED` — this is the loop, and it may run twice. A `POSITIVE_REPORTABLE` retest goes straight to `FAILED_REPORTABLE`. The addition is the escalation: a `POSITIVE_TREATABLE` retest arriving when `retest_count` has already reached two does **not** cycle again — the third positive escalates the inspection to `FAILED_REPORTABLE`, and in exactly that case the service sets `escalated_from_retests` to true on the inspection, recording that the lot got there because a treatable pathogen persisted through both permitted treatment rounds rather than because a reportable pathogen was found. A reportable finding reached any other way leaves `escalated_from_retests` false.

Certification is the last step and it is the segregation-of-duties gate. A `FishHealthVeterinarian` signs the certificate on an inspection in `PASSED` status, and the acting `X-User-ID` must differ from the inspection's `sampled_by_user_id`; the sampling veterinarian signing their own certificate is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). A quarantined lot cannot be certified and answers `ERR_LOT_QUARANTINED`. On success the inspection moves to `CERTIFIED`, records the signer as `certified_by_user_id`, stamps `certified_at` with the logical clock, and computes `certificate_expires_at` as `certified_at` advanced by 30 days. The certificate is then pushed onto the lot: the lot's `health_status` becomes `CERTIFIED`, the lot's own `certificate_expires_at` is set to the certificate's expiry, and the lot's `version` advances. Both `CERTIFIED` and `FAILED_REPORTABLE` are terminal statuses for an inspection.

Certificates lapse rather than being revoked. On a clock advance, any lot whose `health_status` is `CERTIFIED` and whose `certificate_expires_at` the clock has moved strictly past falls back to `health_status` `UNSCREENED`. Crucially, the lapsed expiry instant is **retained** on the lot rather than cleared — that retained value is exactly what lets a load attempt distinguish a lot whose certificate ran out, which answers `ERR_HEALTH_CERTIFICATE_EXPIRED`, from a lot that was never certified at all and carries a null `certificate_expires_at`, which answers `ERR_LOT_NOT_CERTIFIED`. The inspection record itself stays `CERTIFIED` as the historical document of what was signed and when.

A reportable finding sets off the longest cascade in the system, and every link of it is mandatory. The inspection reaches `FAILED_REPORTABLE`. Because of that, the lot's `health_status` becomes `QUARANTINED` and its `certificate_expires_at` is cleared to null — and quarantine can be entered from `UNSCREENED`, `UNDER_INSPECTION`, `RESTRICTED` or `CERTIFIED` alike. Because the lot is quarantined, every stocking event on that lot in `SCHEDULED` or `IN_TRANSIT` status transitions to `ABORTED`, stamping `aborted_at` with the logical clock, setting `abort_reason` to `LOT_QUARANTINED` and `released_count` to zero, returning that event's `fish_count` out of the lot's `reserved_count`, releasing that event's `transport_cost_cents` from the station's `budget_committed_cents`, and returning the truck to `AVAILABLE` with its `current_event_id` cleared to null. Because each of those events is aborted, its granting stocking request falls from `ALLOCATED` back to `DEFERRED` with `allocated_count` reset to zero and `deferral_reason` set to `EVENT_ABORTED`. And because each of those grants is surrendered, each affected water has the surrendered grant subtracted from its `allocated_count_ytd`, with `plan_shortfall_count` and `plan_fill_pct` recomputed. Every record the cascade touches — inspection, lot, each event, each truck, each request, each water, and the station — has its `version` advanced. Every role except `PublicRequester` may read an inspection with its retest history, withdrawal window and certificate, or list inspections filtered by `lot_id`, `status` and `inspection_type`.

### 3.6. Destinations, Demand Intake and the Priority Score

A stocking destination is registered by a `ProgramAdmin` with a `name`, the `county` of record, a `water_class` — one of `COLDWATER_LAKE`, `COLDWATER_STREAM` or `WARMWATER_LAKE` — a `habitat_suitability_score` and an `angler_demand_index` each expressed on a 0-to-100 scale, the `plan_species` named in the water's management plan, the annual `plan_target_count` in fish, and an `access_type` of `PUBLIC_BOAT`, `SHORE_ONLY` or `REMOTE`. Both scores must fall between 0 and 100 inclusive, and `plan_target_count` must be at least 1. A new water opens `ACTIVE` with `allocated_count_ytd` and `released_count_ytd` at zero, `last_release_at` null, `plan_shortfall_count` equal to the full `plan_target_count`, and `plan_fill_pct` at zero.

Those last two figures are the water's progress against its management plan, and both are maintained continuously. `plan_shortfall_count` is the `plan_target_count` less `released_count_ytd` less `allocated_count_ytd`, floored at zero so that an over-subscribed water reports a shortfall of zero rather than a negative number. `plan_fill_pct` is the sum of `released_count_ytd` and `allocated_count_ytd`, divided by `plan_target_count`, expressed as a percentage and rounded to two decimal places — and it is deliberately not capped, so a water with a `plan_target_count` of 2000 carrying 2400 allocated and nothing yet released reports a `plan_shortfall_count` of 0 and a `plan_fill_pct` of 120.00. Both are recomputed whenever an allocation run raises `allocated_count_ytd`, whenever a release raises `released_count_ytd` while lowering `allocated_count_ytd` by the fulfilled grant, and whenever an abort lowers `allocated_count_ytd`. `released_count_ytd` is the sum of the `released_count` figures of every trip that reached `RELEASED` at this water; `allocated_count_ytd` is the sum of the `allocated_count` figures of this water's requests currently in `ALLOCATED` status, and a grant that is actually fulfilled moves out of that counter and into `released_count_ytd` rather than being counted twice.

A `ProgramAdmin` may retire a water, moving it from `ACTIVE` to `CLOSED`; `CLOSED` is terminal and closing an already-closed water is `ERR_INVALID_STATE`. Retirement has two downstream effects and, importantly, one non-effect. Releasing fish into a closed water is refused with `ERR_WATER_CLOSED` (HTTP 409). Queued requests naming a closed water become ineligible and are `DENIED` by the next allocation run that considers them. But trips already `SCHEDULED` against the water are deliberately left alone rather than mass-aborted, so that an operator can abort each one consciously.

Demand arrives from two very different quarters. A `RegionalBiologist` or a `PublicRequester` submits a request naming the `water_id` asked to be stocked, the `species` requested, the `requested_count` of fish, the `size_class` — one of `FRY`, `FINGERLING` or `YEARLING` — and a narrative `justification`. `requested_count` must be at least 1. The `requester_kind` is **never** accepted from the body: the service derives it from the acting role, recording `BIOLOGIST` for a `RegionalBiologist` and `PUBLIC` for a `PublicRequester`, and it records the caller's `X-User-ID` as `requested_by_user_id`. A new request opens in `SUBMITTED` status with `allocated_count` zero, `allocation_plan_id` null, and `deferral_reason`, `allocated_at` and `fulfilled_at` all null.

Intake is also where the request is scored, once and for good. The `priority_score` is a single figure on a 0-to-100 scale, computed from the destination water's counters as they stand at that moment and then frozen on the request; a later change to the water's counters does not re-score an existing request. It is built in four steps, and the order of the last two is the part that is easy to get wrong. First the service computes a plan-gap percentage: the `plan_target_count` less `released_count_ytd` less `allocated_count_ytd`, floored at zero, divided by `plan_target_count`, expressed as a percentage and rounded to two decimal places. Second it forms a base score by weighting three terms — 0.45 of the water's `habitat_suitability_score`, plus 0.35 of the water's `angler_demand_index`, plus 0.20 of that plan-gap percentage. Third it multiplies that base by the requester weight, which is 1.00 for a `BIOLOGIST` request and 0.80 for a `PUBLIC` one. Fourth, and only after the multiplier has been applied, it adjusts by two flat terms: 10 points are added when the request's `species` equals the water's `plan_species`, and 5 points are subtracted when the water's `access_type` is `REMOTE`. Because the flat terms come after the multiplier, a public request never has its species bonus discounted. The result is clamped into the range 0 through 100 and rounded to two decimal places.

A requester may withdraw a request that has not yet been shipped, moving it to `WITHDRAWN` from `SUBMITTED`, from `QUEUED` or from `DEFERRED`. A `RegionalBiologist` or a `PublicRequester` may withdraw only their own request — the caller's `X-User-ID` must equal the request's `requested_by_user_id` — while a `ProgramAdmin` may withdraw anyone's; a mismatch is `ERR_NOT_REQUEST_OWNER`. Withdrawal from `QUEUED` retains the `allocation_plan_id` for audit but removes the request from that plan's candidate set, so the plan's next run will not consider it. `WITHDRAWN` is terminal, as are `DENIED` and `FULFILLED`, and withdrawing a request in any of those, or one already `ALLOCATED`, is `ERR_INVALID_STATE`. A `ProgramAdmin`, a `HatcheryManager`, a `RegionalBiologist` or a `PublicRequester` may read a single request with its score, grant and status, or list requests filtered by `water_id`, `allocation_plan_id`, `status`, `requester_kind` and `species`; waters may be read and listed by every role, with filters on `status`, `plan_species` and `county`.

### 3.7. Allocation Plans and the Distribution Run

An allocation plan is a pool of finished production offered up for distribution. A `ProgramAdmin` opens one by naming the `hatchery_id` whose production it distributes, the `fiscal_year` it allocates, the `species` and `size_class` it covers, the `available_count` of fish in the pool, the `public_request_cap_pct` share of that pool reachable by public requesters, and optionally an `allocation_mode`. `available_count` must be zero or greater and `public_request_cap_pct` must fall between 0.00 and 1.00 inclusive. `allocation_mode` is either `PRIORITY_WATERFALL` or `PROPORTIONAL`, and it defaults to `PRIORITY_WATERFALL` when omitted. A new plan opens in `DRAFT` status with `allocated_total_count`, `unmet_demand_count`, `public_allocated_count` and `run_count` all at zero.

Requests reach a plan by being attached to it, which is how they enter the queue. A `RegionalBiologist` may attach their own request and a `ProgramAdmin` may attach anyone's; a `PublicRequester` may not attach at all, because deciding which demand competes for a production pool is a program judgement. The caller supplies the `allocation_plan_id` of the target plan and the `expected_plan_version` it last read on that plan. Two originating statuses are legal, and they are guarded slightly differently. A request in `SUBMITTED` status attaches to any plan that is not `CLOSED`. A request in `DEFERRED` status — one that a previous run could not fill — re-enters the queue the same way, with the extra condition that the target plan must be a **different** plan from the one already recorded in its `allocation_plan_id`; re-attaching a deferred request to the very plan that deferred it is `ERR_INVALID_STATE`. In both cases a `CLOSED` plan is refused with `ERR_INVALID_STATE`, and in both cases the request's `size_class` must equal the plan's `size_class` or the attach is refused with `ERR_SIZE_CLASS_MISMATCH` (HTTP 422). On success the request moves to `QUEUED`, its `allocation_plan_id` is set to the target plan, its `deferral_reason` is cleared to null, its `version` advances, and the plan's `version` advances too.

Attaching to a plan that has **already run** is permitted, and it is the mechanism by which the plan machine cycles. Such an attach sends the plan from `ALLOCATED` back to `DRAFT`, resets `allocated_total_count`, `unmet_demand_count` and `public_allocated_count` to zero while `run_count` keeps its historical value, advances the plan's `version`, and returns every request the plan had previously resolved to `ALLOCATED` or `DEFERRED` back to `QUEUED` with `allocated_count` reset to zero — releasing the corresponding `allocated_count_ytd` on each of those requests' waters. The selector must then be re-run. There is one condition on that cycle: it is refused with `ERR_INVALID_STATE` if any stocking event has already been created against a request this plan allocated, because production that has begun cannot be silently un-allocated.

Running the plan is the selector, and it belongs to `ProgramAdmin` alone. The caller supplies `expected_plan_version`; the plan must be in `DRAFT` status, so running an `ALLOCATED` plan or a `CLOSED` one is `ERR_INVALID_STATE`; and the plan's station must not be `FROZEN`, or the answer is `ERR_HATCHERY_FROZEN`. The run considers exactly the requests attached to this plan that are currently in `QUEUED` status.

Eligibility is settled first, and ineligible requests never consume any of the pool. A queued request is eligible when its `species` equals the plan's `species` and its destination water is `ACTIVE`. A queued request that fails either test is resolved to `DENIED` with `allocated_count` zero and `deferral_reason` set to `INELIGIBLE`. If no queued request survives eligibility at all — whether because none is queued, or because every queued one is ineligible on species or on a closed water — the whole run is refused with `ERR_NO_ELIGIBLE_REQUESTS` (HTTP 422), and nothing at all is written: the plan stays `DRAFT`, its `version` does not advance, and no request changes status.

The eligible set is then ordered deterministically, by `priority_score` descending, then by `requested_count` ascending as the first tie-break, then by `created_at` ascending as the final tie-break. Before the walk begins the service reserves a sub-pool for public requesters: the public pool is the plan's `available_count` multiplied by `public_request_cap_pct`, rounded **down** to a whole fish. A running remainder starts at the full `available_count`.

Each request is then served in order, in four steps. First a raw entitlement is computed, and this is the one place the two modes differ. Under `PRIORITY_WATERFALL` the raw entitlement is the smaller of the request's `requested_count` and the running remainder — each request in priority order takes everything it asked for that the pool can still cover. Under `PROPORTIONAL` the raw entitlement is the smallest of three quantities: the request's `requested_count`; the plan's `available_count` multiplied by this request's `requested_count` and divided by the total `requested_count` across the whole eligible set, rounded down to a whole fish; and the running remainder. Second, if the request's `requester_kind` is `PUBLIC`, the raw entitlement is further capped at whatever is left of the public pool. Third the entitlement is rounded down to a whole multiple of the 25-fish transport unit, because fish ship in whole units — that rounded figure is the grant. Fourth the bookkeeping: a `PUBLIC` grant is subtracted from the public pool, and every grant is subtracted from the running remainder.

The order of the third and fourth steps matters and is the single most consequential detail of this algorithm: the unit rounding happens **before** the remainder is decremented, so the fish rounded away stay available to the next request in line. A request asking for 640 fish against a 1000-fish pool is granted 625 and leaves 375 behind, not 360. `PROPORTIONAL` mode deliberately leaves its rounding remainder unallocated — it is a fair-share mode rather than a fill mode, and no second pass redistributes what the pro-rata shares did not reach.

Each served request is then resolved. A request whose grant is greater than zero moves to `ALLOCATED`, records the grant as its `allocated_count`, stamps `allocated_at` with the logical clock, and has its `deferral_reason` cleared to null; its destination water has the grant added to `allocated_count_ytd`, with `plan_shortfall_count` and `plan_fill_pct` recomputed. A request that was eligible but whose grant came out at zero moves to `DEFERRED` with `allocated_count` zero, `deferral_reason` set to `POOL_EXHAUSTED` and `allocated_at` left null — and, because a deferred request may be attached to a different plan later, that is a loop rather than a dead end.

The plan itself then settles. Its `status` moves from `DRAFT` to `ALLOCATED`, its `run_count` rises by one and its `version` advances. Its `allocated_total_count` is the `available_count` less whatever remains of the running remainder. Its `unmet_demand_count` is the total, across the whole eligible set, of each request's `requested_count` less its `allocated_count` — so it counts the shortfall of granted requests as well as the whole ask of deferred ones. Its `public_allocated_count` is the total `allocated_count` across the eligible requests whose `requester_kind` is `PUBLIC`.

A plan reaches the end of its life when its work is done: at the close of a released trip, a plan in `ALLOCATED` status every one of whose attached requests has reached a terminal status — `FULFILLED`, `DENIED` or `WITHDRAWN` — transitions to `CLOSED`. A `CLOSED` plan can neither be re-run nor re-attached to. A `ProgramAdmin`, a `HatcheryManager` or a `RegionalBiologist` may read a plan with its allocation totals and the `version` a run must quote, or list plans filtered by `hatchery_id`, `status` and `fiscal_year`.

### 3.8. The Stocking Trip: Booking the Truck, Loading It, and Releasing the Fish

The fleet comes first. Either a `ProgramAdmin` or the station's own manager registers a tank truck by naming its home `hatchery_id`, its fleet `unit_code`, its usable `tank_gallons`, its mechanical payload ceiling `max_load_lbs`, the `oxygen_lpm` delivery rate of its diffuser bank, and the `certification_expires_at` instant at which its hauling certification lapses. `tank_gallons`, `max_load_lbs` and `oxygen_lpm` must each be strictly greater than zero. A new unit opens `AVAILABLE` with `current_event_id` null. A unit cycles between `AVAILABLE` and `IN_USE` for as long as it is certified: loading a trip takes the unit to `IN_USE` and records the loading trip as its `current_event_id`, and either releasing or aborting that trip returns the unit to `AVAILABLE` with `current_event_id` cleared to null. Certification lapse is the exit: on a clock advance, an `AVAILABLE` unit whose `certification_expires_at` the clock has reached or passed goes `OUT_OF_SERVICE`, which is terminal — such a unit can no longer be booked, and an attempt to load with it is refused with `ERR_TRANSPORT_UNIT_UNAVAILABLE` (HTTP 409). A `ProgramAdmin`, a `HatcheryManager` or a `RegionalBiologist` may read a unit with its availability and the trip currently holding it, or list the fleet filtered by `hatchery_id`, `status` and `current_event_id`.

Scheduling a trip is the station manager's act, and it is the most heavily gated creation in the API because it commits three separate scarce resources at once. The manager supplies the `stocking_request_id` of the granted request the trip fills, the `lot_id` of the lot being drawn down, the `transport_unit_id` of the truck reserved for the trip, the `fish_count` committed, the `scheduled_depart_at` and `scheduled_return_at` instants bounding the trip, and the `expected_lot_version` the manager last read on the lot. Optionally the manager declares the marking programme: a `mark_type` of `NONE`, `AD_CLIP`, `CWT` or `PIT`, defaulting to `NONE`, and a `marked_count` of fish carrying the mark, defaulting to 0. `fish_count` must be at least 1 and `scheduled_return_at` must fall strictly after `scheduled_depart_at`. `marked_count` must be exactly 0 when `mark_type` is `NONE`, and otherwise must not exceed `fish_count`; a violation is a request-shape failure.

The gates on scheduling, in the order the ladder imposes them, are these. The three body identifiers are resolved left to right — `stocking_request_id`, then `lot_id`, then `transport_unit_id` — so a body with several unknown identifiers reports `ERR_REQUEST_NOT_FOUND` first. The `expected_lot_version` must match the lot's current `version` or the answer is `ERR_STALE_LOT_VERSION` (HTTP 412). The request must be in `ALLOCATED` status — scheduling against a request that is merely `SUBMITTED` or `QUEUED`, or one already `FULFILLED`, `DEFERRED`, `DENIED` or `WITHDRAWN`, is `ERR_INVALID_STATE`. The lot must not be `QUARANTINED`, or the answer is `ERR_LOT_QUARANTINED`. The `fish_count` must not exceed the lot's unreserved stock — its `count_on_hand` less its `reserved_count` — or the answer is `ERR_LOT_INSUFFICIENT_FISH` (HTTP 422). The `fish_count` must not exceed the request's `allocated_count`, or the answer is `ERR_ALLOCATION_EXCEEDED` (HTTP 422): a trip may not ship more fish than the request was granted. The lot's `species` must equal the request's `species`, or the answer is `ERR_SPECIES_MISMATCH` (HTTP 422). And finally the trip's computed transport cost must not exceed the station's `budget_available_cents`, or the answer is `ERR_BUDGET_EXCEEDED` (HTTP 422).

Scheduling computes three figures and commits two resources. The trip's `planned_load_lbs` is the `fish_count` multiplied by the lot's current `avg_weight_g`, converted to pounds at 453.592 grams per pound and rounded to two decimal places. Its `transport_cost_cents` is a flat 45000-cent base plus the `planned_load_lbs` figure multiplied by 150 cents per pound, that per-pound term rounded **up** to a whole cent, so a load of 240.00 pounds costs 45000 plus 36000, or 81000 cents in total. Its `oxygen_flow_lpm` is the `planned_load_lbs` figure multiplied by an oxygen demand of 0.015 litres per minute per pound of fish, rounded to three decimal places. On success the trip opens in `SCHEDULED` status, the `fish_count` is added to the lot's `reserved_count` and the lot's `version` advances, and the `transport_cost_cents` is added to the station's `budget_committed_cents` with `budget_available_cents` recomputed. Nothing yet leaves `count_on_hand`; the fish are reserved, not gone.

Loading the truck is the safety checkpoint of the whole program. The station's own manager supplies the `loaded_at` instant loading finished, the `load_water_temp_c` hatchery water temperature at loading in degrees Celsius, and optionally the `measured_load_lbs` scale weight of the load. The trip moves from `SCHEDULED` to `IN_TRANSIT`. The station must not be `FROZEN`. Then come the health gates, in the level-10 order set out earlier: a `QUARANTINED` lot answers `ERR_LOT_QUARANTINED`; a lot whose retained `certificate_expires_at` the clock has moved past answers `ERR_HEALTH_CERTIFICATE_EXPIRED` (HTTP 422), with loading exactly at `certificate_expires_at` still legal and one second later not; a lot whose `health_status` is `UNDER_INSPECTION` or `RESTRICTED`, or `UNSCREENED` with a null `certificate_expires_at` because it was never certified, answers `ERR_LOT_NOT_CERTIFIED` (HTTP 422); and a lot whose latest inspection has a `withdrawal_clears_at` the clock has not yet reached answers `ERR_WITHDRAWAL_PERIOD_ACTIVE` (HTTP 422). Only a lot whose `health_status` is `CERTIFIED`, with a certificate the clock has not passed and no unelapsed withdrawal window, may be loaded.

Two temporal conflicts are then checked. The truck's calendar must be free: the trip is compared against every other trip on the same transport unit in `SCHEDULED`, `IN_TRANSIT` or `RELEASED` status, and two trips intersect exactly when this trip's `scheduled_depart_at` falls strictly before the other's `scheduled_return_at` **and** the other's `scheduled_depart_at` falls strictly before this trip's `scheduled_return_at`. Trips that merely touch — one returning at exactly the instant the next departs — do not intersect. An intersection, or a unit that has gone `OUT_OF_SERVICE`, is `ERR_TRANSPORT_UNIT_UNAVAILABLE`. Note that terminal trips keep their intervals on record for exactly this comparison, so a released trip still blocks the same slot. Separately, the station's bulk oxygen supply is shared across every truck that is out at the same time: the total `oxygen_flow_lpm` of this station's trips that are currently `IN_TRANSIT` with an intersecting trip interval, plus this trip's own `oxygen_flow_lpm`, must not exceed the station's `oxygen_supply_lpm`, and an overrun is `ERR_OXYGEN_SUPPLY_EXCEEDED` (HTTP 422). Each individual load can be well inside its own truck's rating and the station can still fail this aggregate test.

The last gate at loading is the truck's real, temperature-adjusted carrying capacity, which the system computes fresh at loading time from the water temperature actually reported. First the average fish weight is converted to pounds: the lot's `avg_weight_g` divided by 453.592. Next the safe loading density is set: a baseline of 0.50 pounds of fish per gallon of water, multiplied by a derating factor of 0.80 when the reported `load_water_temp_c` is strictly warmer than 15.0 degrees Celsius, and left at the full baseline otherwise. Water at exactly 15.0 degrees carries the full 0.50 density; water at 15.1 degrees carries only 0.40. Three separate ceilings are then computed in pounds. The volume ceiling is the truck's `tank_gallons` multiplied by that density, rounded to two decimal places. The oxygen ceiling is the truck's `oxygen_lpm` divided by the 0.015 litres-per-minute-per-pound demand, rounded to two decimal places. The mechanical ceiling is the truck's `max_load_lbs` as registered. The trip's gross capacity is the smallest of those three figures, and the trip's `max_fish_allowed` is that gross capacity divided by the average fish weight in pounds, rounded **down** to a whole fish. If the trip's `fish_count` exceeds `max_fish_allowed`, loading is refused with `ERR_TRANSPORT_CAPACITY_EXCEEDED` (HTTP 422). Which of the three ceilings binds is entirely a matter of how the particular truck is specified and how warm the water is, and the refusal names only the fish count, never the binding ceiling — a truck that is volume-limited in cold water can become oxygen-limited in warm water without anything about the truck changing.

A successful load records the supplied `loaded_at`, `load_water_temp_c` and `measured_load_lbs` on the trip alongside the freshly computed `oxygen_flow_lpm` and `max_fish_allowed`, moves the trip to `IN_TRANSIT`, moves the transport unit to `IN_USE` with this trip as its `current_event_id`, and advances the `version` of both the trip and the unit. The fish remain counted in the lot's `reserved_count` and are still counted in `count_on_hand`: they have left the raceway physically but not yet on the books.

Release closes the trip and is where every reservation in the system finally settles. The station's manager supplies the `arrived_at` instant the truck reached the water, the `site_water_temp_c` receiving-water temperature in degrees Celsius, the `tempering_minutes` actually spent tempering the load before release, and optionally the `transport_mortality_count` of fish that died in transit, defaulting to 0. The trip moves from `IN_TRANSIT` to `RELEASED`, and four conditions must hold.

First, the receiving water must still be `ACTIVE`; a water closed since the trip was scheduled answers `ERR_WATER_CLOSED` (HTTP 409). Second, the thermal shock must be within tolerance: the temperature delta is the absolute difference between `site_water_temp_c` and the trip's recorded `load_water_temp_c`, rounded to two decimal places, and it must not exceed 10.0 degrees Celsius or the answer is `ERR_TEMP_DELTA_EXCEEDED` (HTTP 422). A delta of exactly 10.0 degrees is releasable; a delta of 10.01 degrees is not, no matter how long the crew tempers. Third, the tempering must have been long enough: the trip's `tempering_minutes_required` is the temperature delta divided by a 1.0-degree step, that quotient rounded **up** to a whole step, multiplied by 6 minutes per step, and the supplied `tempering_minutes` must be at least that figure or the answer is `ERR_ACCLIMATION_INSUFFICIENT` (HTTP 422). Because the step count is rounded up, a partial degree costs a whole step: a delta of 7.5 degrees requires the same 48 minutes as a delta of 8.0 degrees, while a delta of 8.01 degrees requires 54. A zero delta requires zero minutes, and the maximum releasable delta of 10.0 degrees requires 60. Fourth, the receiving water must have had its rest: when the water carries a `last_release_at` from an earlier trip, the clock must stand at or after that instant plus 48 hours, or the answer is `ERR_WATER_REST_BUFFER` (HTTP 409). Exactly 48 hours after the previous release is permitted; 47 hours and 59 minutes is not. A water that has never been stocked has no `last_release_at` and imposes no buffer.

A successful release settles the books in six places. On the trip, `released_at` is stamped with the clock, `arrived_at`, `site_water_temp_c` and `tempering_minutes` are recorded, and `released_count` is set to the `fish_count` less the `transport_mortality_count`. On the lot, the `fish_count` is subtracted from both `reserved_count` and `count_on_hand`, the `transport_mortality_count` is added to `cumulative_mortality_count`, `biomass_lbs` is recomputed, and a lot emptied by the trip may reach the `RELEASED` stage. On the receiving water, the `released_count` is added to `released_count_ytd`, the filled request's `allocated_count` is subtracted from `allocated_count_ytd` because that grant is no longer merely promised, `last_release_at` is set to the clock, and `plan_shortfall_count` and `plan_fill_pct` are recomputed against the water's `stocking_plan_count`. On the station, the trip's `transport_cost_cents` moves out of `budget_committed_cents` and into `budget_spent_cents`, and because inventory has left the raceways `biomass_on_hand_lbs`, `density_index` and `operating_posture` are all recomputed — a release is one of the ways a `RESTRICTED` station returns to `NORMAL`. On the fleet, the transport unit returns to `AVAILABLE` with `current_event_id` cleared to null. And on the demand side the filled request moves to `FULFILLED` with `fulfilled_at` stamped from the clock, which in turn may close the last open request on an allocation plan and take that plan to `CLOSED`. Transport mortality reduces the `released_count` but never blocks fulfilment: a request whose trip lost fish in transit is still `FULFILLED`, and the shortfall shows up as a smaller `released_count_ytd` on the water, not as an unfilled request.

Abort is the exact inverse of scheduling, and it takes no request body. Either the station's own manager or a `ProgramAdmin` may abort a trip that is still `SCHEDULED` or already `IN_TRANSIT`; a `ProgramAdmin` is not confined to one station. Aborting stamps `aborted_at` from the clock, sets `abort_reason` to `OPERATOR_ABORT`, and sets `released_count` to 0. It returns the fish by subtracting the `fish_count` from the lot's `reserved_count` while leaving `count_on_hand` untouched — the fish were never shipped, so they are simply unreserved — and advances the lot's `version`. It returns the money by subtracting the `transport_cost_cents` from the station's `budget_committed_cents`, with nothing added to `budget_spent_cents`. It returns the grant by moving the request to `DEFERRED` with its `allocated_count` reset to 0 and its `deferral_reason` set to `EVENT_ABORTED`, and by subtracting that surrendered grant from the receiving water's `allocated_count_ytd`, with the water's `plan_shortfall_count` and `plan_fill_pct` recomputed. And it returns the truck, moving the transport unit back to `AVAILABLE` with `current_event_id` cleared, when the unit was `IN_USE` for this trip; a trip aborted before it was ever loaded never held the unit and leaves it as it found it. Both `RELEASED` and `ABORTED` are terminal: neither can be loaded, released or aborted again.

### 3.9. Marking Programmes and Evaluating Contribution

Marked fish are how the program learns whether stocking works. A trip declares its marking programme when it is scheduled, through the `mark_type` and `marked_count` fields: an adipose fin clip (`AD_CLIP`), a coded wire tag (`CWT`), a passive integrated transponder (`PIT`), or `NONE` for an unmarked trip. The declared `marked_count` is the number of fish that were handled for marking, not the number that will still be identifiable when they are caught, because every marking method loses some marks between release and recovery. The system therefore derives the trip's `effective_marked_count` when the trip is scheduled — both of its inputs are declared at that moment — by discounting the declared `marked_count` by a method-specific tag-loss rate: 2 percent for `AD_CLIP`, 5 percent for `CWT`, and 1 percent for `PIT`, with the survivor count rounded to a whole fish. A scheduled trip therefore reads back its `effective_marked_count` immediately, rather than only once a recovery has been reported, and an unmarked trip — `mark_type` `NONE`, whose `marked_count` is necessarily 0 — reads 0. A `CWT` programme is the least durable of the three, so the same declared `marked_count` yields a smaller `effective_marked_count` under `CWT` than under `PIT`.

Recoveries are reported against a released trip by a `ProgramAdmin` or a `RegionalBiologist`, who supplies the `recovered_count` of marked fish recovered and the `creel_sample_fraction` describing what share of the fishery's catch the creel survey actually sampled. The `creel_sample_fraction` must be strictly greater than 0 and no greater than 1; a fraction of 1 means the survey covered the entire catch. Recoveries can only be reported against a trip that has reached `RELEASED` — a trip still `SCHEDULED`, `IN_TRANSIT` or `ABORTED` answers `ERR_INVALID_STATE`, an unknown trip answers `ERR_EVENT_NOT_FOUND`, and a malformed or out-of-range body answers `ERR_INVALID_REQUEST`.

Reporting a recovery computes two different contribution measures, and the system computes and stores **both** of them side by side on every recovery, always, with no mode flag and no selector deciding between them. The cohort measure, `contribution_index_cohort`, is the `recovered_count` divided by the trip's `effective_marked_count`, rounded to four decimal places: it answers what fraction of the durably marked fish came back, and it is the measure a hatchery evaluator cares about. The harvest measure, `contribution_index_harvest`, first expands the observed recoveries to the whole fishery by dividing the `recovered_count` by the `creel_sample_fraction`, then divides that expanded figure by the trip's `released_count`, again rounded to four decimal places: it answers what fraction of everything released is estimated to have entered the harvest, and it is the measure a fishery manager cares about. The two indices answer different questions from the same observation and will ordinarily disagree, sometimes by a wide margin, because one is scaled by durably marked fish and the other by total fish released and expanded by survey coverage. Both are rounded half-up at the fourth decimal place. Both indices remain null on a trip until a recovery with a `recovered_count` strictly greater than zero has been reported, and a recovery report advances the trip's `version`. The trip's own `recovered_count` is not among the fields that start null: it opens at 0 when the trip is scheduled and is replaced by the figure a recovery report supplies. Consumers that need one measure read that field; the API never withholds the other.

## 4. Endpoint Definitions

Every endpoint below is mounted at the root of the API. Endpoints that create a new resource answer HTTP 201 on success; every other successful operation, including the state-transition operations and all reads, answers HTTP 200. Unless a section above says otherwise, a successful create or modify returns the created or updated resource in the `data` field of the envelope described in section 2.2, and a successful list returns an array in `data` together with the pagination fields in `meta`. All endpoints require authentication, and the roles named in the last column are the only roles permitted; a caller holding some other role receives `ERR_FORBIDDEN_ROLE`, and a caller whose role is permitted but whose station or ownership scope does not cover the target receives `ERR_HATCHERY_SCOPE_VIOLATION` or `ERR_NOT_REQUEST_OWNER` as described in section 2.1.
