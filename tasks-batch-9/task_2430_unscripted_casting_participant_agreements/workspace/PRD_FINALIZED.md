# Unscripted Casting & Participant Agreements API — Product Requirements Document

## 1. Introduction

Unscripted television lives or dies on the people in front of the camera, and the paperwork that stands behind them. A single docusoap season can put hundreds of members of the public through an open call, screen them for suitability, negotiate individual participation terms with each one, satisfy state-by-state minor employment law, insure them on set, and then chase them for a press junket eight months after wrap. Today that work is spread across casting spreadsheets, a business-affairs mailbox, a welfare officer's notebook and a location manager's clipboard. Nothing reconciles: a participant can be called to a stage before their medical clearance has been recorded, a minor's blocked trust can be short-funded because the deposit was rounded the wrong way, and a duty-of-care complaint can be closed without anyone noticing that the production's welfare spend has quietly overrun its budget.

This document specifies the Unscripted Casting & Participant Agreements API, a single system of record for the whole participant journey — casting call distribution, applicant screening, participant agreement negotiation, minor protections, on-set welfare, incidental release management, post-production obligations and participant aftercare. Every resource is mounted under the `/casting` prefix, with the sole exception of an administrative clock control described later. The API's governing design idea is that **the production is the gate**: money committed to stipends, money committed to welfare, the number of minors on the books and the number of substantiated welfare incidents are all rolled up onto the production record, and a single derived posture field decides whether casting may continue at all.

The system is deliberately conservative. Where a rule can be checked before an irreversible act, it is checked; where a commitment has been made, a compensating action exists that unwinds it exactly, leaving no drift in any conserved figure. Where two humans must be involved for a decision to be trustworthy — recording a background check and a psychological evaluation on the same applicant, or proposing terms and then executing them — the API enforces that separation rather than trusting process discipline.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts, conventions and cross-cutting principles that hold everywhere in the API. Where §3 narrates business workflows, this section fixes the mechanics those workflows rely on.

### 2.1. User and Role-Based Access Control

Every request, without exception, must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. If either header is absent or empty, or if `X-User-Role` is not one of the six recognised roles, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the header pair is well formed but the declared role is not permitted to invoke the addressed operation, the rejection is `ERR_ROLE_FORBIDDEN` (HTTP 403).

The six roles are `ProductionAdmin`, `CastingDirector`, `ComplianceOfficer`, `BusinessAffairs`, `WelfareOfficer` and `Applicant`. A `ProductionAdmin` owns productions, venues, shooting blocks, incidental releases and the welfare epoch sweep. A `CastingDirector` distributes casting calls and records applications. A `ComplianceOfficer` runs screening instruments, medical clearance and minor-protection packets. `BusinessAffairs` drafts, negotiates, executes and voids participant agreements, funds minors' trusts and closes out post-production obligations. A `WelfareOfficer` plans and manages welfare protocols and handles complaint triage, aftercare and escalation. The `Applicant` role belongs to the participant themselves.

Identity semantics differ between the operator roles and the participant role, and the difference matters for every ownership check in the system. When `X-User-Role` is `ProductionAdmin`, `CastingDirector`, `ComplianceOfficer`, `BusinessAffairs` or `WelfareOfficer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server records it where a transition demands an audit key — as `recorded_by_user_id` on a screening item, as `proposer_user_id` on a negotiation round, as `last_production_proposer_user_id` and `executed_by_user_id` on an agreement, and as `triaged_by_user_id` and `routed_by_user_id` on a complaint — but it is never compared against any entity's `id`. When `X-User-Role` is `Applicant`, by contrast, `X-User-ID` is the `id` of the acting `Applicant` record; ownership checks on any resource that references an applicant compare the resource's applicant reference to `X-User-ID`. Concretely, a participant may read only their own applicant record, may withdraw only themselves, and may read, counter-offer against, or file a complaint against only an agreement whose `applicant_id` equals their own `X-User-ID`. A mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10, may be no smaller than 1 and no larger than 100. `offset` is the number of records skipped before the page begins; it defaults to 0 and may not be negative. A `limit` outside the range 1 through 100 inclusive, or a negative `offset`, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the number of records matching the filters before pagination is applied and `has_more` states whether any matching record remains beyond the returned page.

### 2.4. Resource Identity, Audit Fields and Record Versioning

Every resource in the system is addressed by an `id`, a server-minted UUID carrying no type prefix and no embedded meaning. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the record was first written.

Most resources — productions, locations, casting calls, applicants, screening items, minor-protection packets, participant agreements, welfare protocols, shoot blocks and post-production obligations, together with complaints — additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that begins at 1 when the record is created and increases by exactly one on every mutation. A write to a derived field counts as a mutation for both purposes: when a rollup rewrites a production's committed figures, or a cascade flips an agreement's welfare flag, that production or agreement has its `updated_at` refreshed and its `version` incremented just as if a client had edited it directly.

Two record types are deliberately exempt. Negotiation rounds and incidental releases are append-only evidence, not editable state: each carries only `id` and `created_at`, and both `updated_at` and `version` are absent from those records entirely. A negotiation round's `recorded_at` and a release's `collected_at` are stamped once at creation and never mutated thereafter.

### 2.5. The Logical Production Clock

Every deadline, expiry, intake window, coverage interval and age determination in this specification is evaluated against the server's **logical clock**, never against real wall-clock time. On start-up the logical clock reads exactly `2026-08-01T00:00:00Z`, and it continues to read that instant until an administrator moves it; under no circumstance does it fall back to the host's real time.

An administrative test-driving capability, reserved to `ProductionAdmin` and mounted outside the `/casting` prefix, sets the logical clock to a supplied instant carried in the request field `to_iso8601`. Setting the clock mutates no entity and fires no sweep of any kind: expiries, lapses and breaches are only ever applied by the welfare epoch sweep described in §3.7, which an operator must invoke explicitly.

### 2.6. Request Admission Order

Because most operations in this API are guarded by several independent rules at once, the order in which those rules are evaluated is part of the contract: the first rule that fails determines the response, and no later rule is evaluated. A client that fixes the reported problem and retries may then encounter the next rule down the ladder. The ladder below is exhaustive and is evaluated strictly top to bottom.

1. Both `X-User-ID` and `X-User-Role` are present and non-empty on every endpoint, otherwise `ERR_UNAUTHENTICATED` (401).
2. `X-User-Role` names one of the six roles listed in §2.1, otherwise `ERR_UNAUTHENTICATED` (401).
3. The declared role appears in the addressed endpoint's authorised-role list, otherwise `ERR_ROLE_FORBIDDEN` (403).
4. When the declared role is `Applicant`, `X-User-ID` equals the applicant that owns the addressed resource — the applicant record itself, or the `applicant_id` of the addressed agreement or of the agreement under which the addressed complaint was filed. This ownership rung guards exactly five operations: reading one applicant, participant withdrawal, agreement counter-offer, filing a complaint against an agreement, and reading one agreement. A mismatch yields `ERR_NOT_RESOURCE_OWNER` (403).
5. Every identifier appearing in the URL path exists, validated left to right, with the failure reported as the 404 error naming the missing kind: `ERR_PRODUCTION_NOT_FOUND`, `ERR_CASTING_CALL_NOT_FOUND`, `ERR_APPLICANT_NOT_FOUND`, `ERR_SCREENING_ITEM_NOT_FOUND`, `ERR_MINOR_PROTECTION_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_WELFARE_PROTOCOL_NOT_FOUND`, `ERR_SHOOT_BLOCK_NOT_FOUND`, `ERR_POST_OBLIGATION_NOT_FOUND` or `ERR_COMPLAINT_NOT_FOUND`.
6. Every foreign key carried in a request body exists — `production_id`, `venue_location_id`, `casting_call_id`, `applicant_id`, `location_id`, `supersedes_agreement_id`, and every entry of `participant_agreement_ids` — reported as `ERR_PRODUCTION_NOT_FOUND`, `ERR_LOCATION_NOT_FOUND`, `ERR_CASTING_CALL_NOT_FOUND`, `ERR_APPLICANT_NOT_FOUND` or `ERR_AGREEMENT_NOT_FOUND` (404). This rung applies to the four body-referencing creates: casting-call draft, applicant intake, agreement draft and shoot-block scheduling.
7. The request body is well shaped: every required field present, every enum value a declared member, every number inside its declared range, every datetime pair correctly ordered (`photography_end_utc` strictly after `photography_start_utc`, `coverage_end_utc` strictly after `coverage_start_utc`, `end_utc` strictly after `start_utc`, `open_call_window_end_utc` strictly after `open_call_window_start_utc`, and `max_age` no smaller than `min_age`), and `participant_agreement_ids` free of duplicate entries. Any breach is `ERR_INVALID_REQUEST` (400). This rung applies to every creating and amending operation.
8. Pagination parameters are inside their bounds on every list endpoint, otherwise `ERR_INVALID_PAGINATION` (400).
9. On agreement drafting, `expected_applicant_version` equals the applicant's current `version`, otherwise `ERR_STALE_APPLICANT_VERSION` (412).
10. On a participant counter-offer, `expected_agreement_version` equals the agreement's current `version`, otherwise `ERR_STALE_AGREEMENT_VERSION` (412).
11. The owning production's `casting_posture` is not `FROZEN` on the seven posture-gated write operations — casting-call publish, applicant intake, agreement drafting, agreement send, agreement execution, shoot-block scheduling and shoot-block roll — otherwise `ERR_CASTING_FROZEN` (409).
12. The owning production's `casting_posture` is not `RESTRICTED` on casting-call publish, and not `RESTRICTED` on applicant intake when the receiving call's `channel` is `OPEN_CALL`, otherwise `ERR_CASTING_RESTRICTED` (409).
13. The addressed entity is in a state from which the requested transition is declared, otherwise `ERR_INVALID_STATE_TRANSITION` (409). This rung applies to every action endpoint.
14. The addressed agreement's `welfare_hold` is false. This guards all four negotiation writes — send, counter-offer, revise and execute — and a held agreement is rejected with `ERR_WELFARE_HOLD_ACTIVE` (409).
15. On applicant intake, the receiving casting call's `status` is `PUBLISHED`, otherwise `ERR_CASTING_CALL_NOT_OPEN` (409).
16. On applicant intake through a call whose `channel` is `OPEN_CALL`, the logical clock lies inside the closed intake window bounded inclusively by `open_call_window_start_utc` and `open_call_window_end_utc`, otherwise `ERR_OPEN_CALL_WINDOW_CLOSED` (409).
17. On a trust deposit, the packet's applicant has an agreement in `EXECUTED` status, otherwise `ERR_AGREEMENT_NOT_EXECUTED` (409).
18. On filing a complaint, the addressed agreement's `status` is either `EXECUTED` or `VOIDED`, otherwise `ERR_COMPLAINT_TARGET_INVALID` (409).
19. The four-eyes screening rule holds on both screening-outcome paths — opening a screening item with an outcome supplied, and recording the outcome of an existing item — otherwise `ERR_SEGREGATION_OF_DUTIES` (403).
20. The four-eyes execution rule holds on agreement execution, otherwise `ERR_SEGREGATION_OF_DUTIES` (403).
21. On agreement send and agreement execution, the applicant's `screening_status` is `CLEARED`, otherwise `ERR_SCREENING_INCOMPLETE` (422).
22. On agreement send and agreement execution, the applicant's `medical_status` is `CLEARED`, otherwise `ERR_MEDICAL_CLEARANCE_MISSING` (422).
23. On agreement send, when the applicant's `psych_eval_required` is true, a `PSYCH_EVAL` item exists whose `outcome` is `PASS` or `CONDITIONAL` and whose `expires_at` is either absent or strictly later than the logical clock, otherwise `ERR_PSYCH_EVAL_REQUIRED` (422).
24. On agreement send, when the applicant's `enhanced_support_required` is true, the production has an `ACTIVE` `ONSET_PSYCH_SUPPORT` protocol whose coverage spans the entire photography window, otherwise `ERR_ENHANCED_SUPPORT_MISSING` (422).
25. On agreement send, when the applicant's `is_minor` is true, that applicant has a minor-protection packet in `COMPLETE` status, otherwise `ERR_MINOR_PROTECTION_INCOMPLETE` (422).
26. Minor work permits are unexpired: on agreement send for a minor applicant, and on shoot-block scheduling for every minor called to the block, `permit_expires_on` is strictly after the logical clock's date, otherwise `ERR_WORK_PERMIT_EXPIRED` (422).
27. On minor-protection filing and on minor-protection amendment, `education_hours_scheduled_weekly` is at least the jurisdiction minimum, otherwise `ERR_EDUCATION_HOURS_SHORTFALL` (422).
28. On shoot-block roll, no minor called to the block exceeds the daily on-set hours cap, otherwise `ERR_MINOR_DAILY_HOURS_EXCEEDED` (422).
29. On shoot-block roll, an `ACTIVE` `DUTY_OF_CARE_OFFICER` protocol covers the whole block interval, otherwise `ERR_DUTY_OF_CARE_UNCOVERED` (422).
30. On shoot-block roll, no called participant's applicant has a `medical_status` of `EXPIRED` or `DEFERRED`, otherwise `ERR_MEDICAL_CLEARANCE_EXPIRED` (422).
31. On release collection, a release whose `subject_kind` is `MINOR_INCIDENTAL` carries `guardian_signature` set to true, otherwise `ERR_GUARDIAN_SIGNATURE_REQUIRED` (422).
32. On shoot-block wrap, the block's `release_coverage_complete` is true, otherwise `ERR_RELEASE_COVERAGE_INCOMPLETE` (422).
33. On applicant intake, the applicant is eligible for the call: their completed age at the production's `photography_start_utc` lies between `min_age` and `max_age` inclusive, and when the call's `residency_state_code` is set, the applicant's `residency_state_code` equals it. Otherwise `ERR_ELIGIBILITY_NOT_MET` (422).
34. On applicant intake, a minor applicant supplies `guardian_name`, otherwise `ERR_GUARDIAN_REQUIRED` (422).
35. On agreement drafting, the applicant has no other agreement whose `status` is `DRAFTED`, `SENT`, `COUNTERED`, `REVISED` or `EXECUTED`, unless `supersedes_agreement_id` names exactly that agreement. Otherwise `ERR_DUPLICATE_AGREEMENT` (409).
36. On agreement drafting, `supersedes_agreement_id`, when supplied, references an agreement of the same applicant whose `status` is `DRAFTED`, `SENT`, `COUNTERED` or `REVISED`, otherwise `ERR_SUPERSEDE_TARGET_INVALID` (422).
37. On agreement execution for a minor applicant, one more minor still fits under the production's cap, otherwise `ERR_MINOR_CAP_EXCEEDED` (409).
38. On welfare-protocol planning and on welfare-protocol activation, a protocol whose `kind` is `INSURANCE_RIDER` carries `carrier_certificate_number`, otherwise `ERR_INSURANCE_CERTIFICATE_MISSING` (422).
39. On shoot-block scheduling, a block whose `block_kind` is `LOCATION_EXTERIOR` or `PUBLIC_SPACE` sits at a venue whose `filming_permit_number` is present, otherwise `ERR_LOCATION_PERMIT_MISSING` (422).
40. On shoot-block scheduling, every entry of `participant_agreement_ids` belongs to the named `production_id` and has `status` `EXECUTED`, otherwise `ERR_PARTICIPANT_NOT_EXECUTED` (422).
41. On shoot-block scheduling, the block interval lies inside the production's photography window, otherwise `ERR_OUTSIDE_PHOTOGRAPHY_WINDOW` (422).
42. On shoot-block scheduling, the block does not collide with another block at the same venue, otherwise `ERR_LOCATION_BLOCK_CONFLICT` (409).
43. On casting-call publish, the venue's aggregate expected attendance stays within capacity, otherwise `ERR_VENUE_CAPACITY_EXCEEDED` (409).
44. On agreement send and agreement execution, the stipend pool guard holds, otherwise `ERR_STIPEND_POOL_EXCEEDED` (409).
45. On welfare-protocol planning and on welfare-protocol activation, the welfare budget guard holds, otherwise `ERR_WELFARE_BUDGET_EXCEEDED` (409).
46. On minor-protection filing and on minor-protection amendment, `trust_deposit_pct` is at least the jurisdiction minimum, otherwise `ERR_TRUST_DEPOSIT_SHORTFALL` (422).

Path resolution deserves separate emphasis. Where an endpoint's URL nests one collection beneath another — a production's welfare protocols, an applicant's screening items, an agreement's negotiation rounds — the identifiers are resolved strictly left to right, and the first identifier that names no existing record produces its own 404 before any identifier to its right is examined. A request for the screening items of a non-existent applicant therefore yields `ERR_APPLICANT_NOT_FOUND`, never a screening-item error, and never an empty list.

### 2.7. Casting Posture: the Production-Level Gate

Each production carries `casting_posture`, a derived field taking one of `OPEN`, `RESTRICTED` or `FROZEN`. It is never set directly by a client. It is recomputed immediately after any write that changes `stipend_committed_cents`, `welfare_committed_cents`, `minor_participant_count`, `welfare_incident_count` or `duty_of_care_tier`, and again at the end of every welfare epoch sweep. The derivation reads only the production's own computed figures — no child scan beyond the rollups that have already written them — and its clauses are evaluated in a pinned precedence where the first matching clause wins and no lower clause is considered:

- The posture is `FROZEN` when `welfare_committed_cents` is strictly greater than `welfare_budget_cents`, or when `welfare_incident_count` has reached 2 or more.
- Otherwise the posture is `RESTRICTED` when committed stipend has reached ninety percent of the pool, or when the production admits minors at all and its minor headcount has caught up with its cap. The utilisation test is performed by integer cross-multiplication: `stipend_committed_cents` multiplied by 100 is compared against `stipend_pool_cents` multiplied by 90, and the posture restricts when the former is greater than or equal to the latter. Exactly ninety percent restricts; anything below it, however narrowly, does not. The minor clause reads: `minor_participant_cap` is strictly greater than 0 and `minor_participant_count` is greater than or equal to `minor_participant_cap`. The guard on the cap matters — a production that admits no minors at all, with a cap of 0, is never restricted by the minor clause, because a minor's agreement could never have been executed there in the first place.
- Otherwise the posture is `OPEN`.

Posture is a gate in two directions. Prospectively it blocks work: a `FROZEN` production rejects casting-call publication, applicant intake, agreement drafting, agreement send, agreement execution, shoot-block scheduling and shoot-block roll with `ERR_CASTING_FROZEN`, while a `RESTRICTED` production rejects casting-call publication outright and rejects applicant intake through an `OPEN_CALL` channel with `ERR_CASTING_RESTRICTED`. Retrospectively it cascades: the moment a production's posture becomes `RESTRICTED`, every casting call of that production that is `PUBLISHED` **and** whose `channel` is `OPEN_CALL` moves to `CLOSED` with `closed_reason` set to `POSTURE_RESTRICTED`, its `version` incremented by one; calls on the `DIGITAL_SUBMISSION` and `REFERRAL` channels are left `PUBLISHED`. The moment a posture becomes `FROZEN`, the cascade is wider and channel-blind: every `PUBLISHED` casting call of the production moves to `CLOSED` with `closed_reason` set to `POSTURE_FROZEN` and its `version` incremented, every shoot block still in `SCHEDULED` status moves to `CANCELLED` with its `version` incremented, and every participant agreement whose `status` is `DRAFTED`, `SENT`, `COUNTERED` or `REVISED` has `welfare_hold` set to true.

### 2.8. Arithmetic, Rounding and Comparison Conventions

Monetary amounts are integers of whole cents throughout; the API never returns a fractional cent. Wherever an intermediate product or quotient is not a whole number of cents it is rounded half up — a value exactly on the half-cent rounds away from zero, upward. Three rounding orders are pinned because a different order gives a different answer, and implementations that follow the wrong order will be off by a few cents:

- In the stipend commitment computation, each component is rounded to whole cents **before** the components are summed, and the depiction adjustment is then applied to the already-rounded subtotal rather than to any individual component.
- In the minor trust deposit schedule, the per-installment amount is rounded half up **first** and the total is then obtained by multiplying that rounded installment by the installment count. The resulting total is never re-rounded, and the alternative order — round the target, then divide — is incorrect.
- In aftercare session authorisation, the session count is rounded half up to a whole number of sessions **before** the ceiling is applied, not after.

Risk scores are decimals carried to two decimal places, rounded half up once at the end, applied to the final sum and never to individual contributions. On-set hours are carried to one decimal place, and the daily-hours violation test is a strict comparison: a total of exactly the cap is permitted, only a total above it is a violation. The welfare surcharge is whole cents, rounded half up. The posture utilisation test uses integer cross-multiplication only, with no floating-point division anywhere in its evaluation. Release coverage is compared with integer head counts, and exact equality between coverage and expectation counts as complete.

### 2.9. Optimistic Concurrency Control

Two write operations require the client to state the version of a parent record it believes it is working against. Both are non-optional inputs on their endpoints, and no other endpoint in the API accepts a version field of any kind.

Drafting a participant agreement requires `expected_applicant_version`, carrying the client's last observed `version` of the target `Applicant`. If the applicant's current `version` differs from the supplied value — most typically because another `BusinessAffairs` writer has already drafted an agreement for that applicant, an act that legitimately supersedes the earlier one when `supersedes_agreement_id` names it — then the drafting client's view of the applicant, including its `screening_status` and its existing agreements, is stale, and the request is rejected with `ERR_STALE_APPLICANT_VERSION` (HTTP 412).

A participant counter-offer requires `expected_agreement_version`, carrying the participant's last observed `version` of the `ParticipantAgreement` being countered. If the agreement's current `version` differs, the terms the participant is countering have already been replaced by a newer round or a production-side revision, and accepting the counter would negotiate against text the participant never saw; the request is rejected with `ERR_STALE_AGREEMENT_VERSION` (HTTP 412).

### 2.10. Segregation of Duties

Two decisions in this system are too consequential to leave with a single operator, and both are enforced by comparing `X-User-ID` against a previously recorded user identifier. Neither rule can be waived.

The first is the four-eyes screening rule. The `ComplianceOfficer` who records a `BACKGROUND_CHECK` outcome for an applicant may not also record a `PSYCH_EVAL` outcome for that same applicant, and the converse holds as well: recording a `PSYCH_EVAL` outcome is refused when any `BACKGROUND_CHECK` item of the same applicant carries a `recorded_by_user_id` equal to the caller's `X-User-ID`, and recording a `BACKGROUND_CHECK` outcome is refused when any `PSYCH_EVAL` item of the same applicant does. The rule applies on both paths that can record an outcome — opening a screening item with an outcome supplied in the same request, and recording the outcome of an item that was left pending — and the rejection is `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

The second is the four-eyes execution rule. The `BusinessAffairs` user who authored the most recent production-side negotiation round on an agreement, recorded on the agreement as `last_production_proposer_user_id`, may not be the user who executes it. Execution is permitted when `last_production_proposer_user_id` is absent — an agreement executed straight out of its first send has no production-side round — and otherwise only when the caller's `X-User-ID` differs from it. A caller who proposed the standing terms and then attempts to execute them is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.11. Conserved Quantities and Compensating Actions

Three figures on the production record are **conserved quantities**: `stipend_committed_cents`, `welfare_committed_cents` and `trust_escrow_balance_cents`. Each is defined as a full recomputation over its contributing child records, never as an incremental delta applied to the previous value, and each is recomputed in the same request as the write that changed its inputs. The invariant this buys is exact: for every forward action there is a compensating action, and after the compensating action the figure returns to precisely the value it held before, with no drift of even one cent.

Committed stipend is the sum of `total_stipend_commitment_cents` over the production's participant agreements whose `status` is `EXECUTED`. Agreements in `DRAFTED`, `SENT`, `COUNTERED` or `REVISED` status contribute nothing, and `VOIDED` agreements both fall outside the summed set and carry a zeroed `total_stipend_commitment_cents`, so voiding is an exact reversal of executing. Trust escrow is the sum of `trust_deposited_cents` over the minor-protection packets reachable from the production through its applicants' agreements whose packet `status` is `INCOMPLETE`, `COMPLETE` or `LAPSED`; `RELEASED` packets are excluded from the sum and also have their deposit figures zeroed, so a trust refund likewise leaves zero residue. Committed welfare is described in §3.7, and cancelling a protocol is the exact compensating action for planning one.

### 2.12. Jurisdictional Minimums for Minor Participants

A production declares its employment jurisdiction once, as `jurisdiction_code`, drawn from `CA`, `NY`, `GA` and `IL`; venues carry the same four-member enumeration as `state_code`, and applicants declare residency as `residency_state_code` from the same set. The jurisdiction selects two statutory minimums that every minor-protection packet of that production's applicants must satisfy.

The weekly on-set tutoring minimum is 15 hours in `CA`, 12 hours in `NY`, 10 hours in `GA` and 12 hours in `IL`; a packet whose `education_hours_scheduled_weekly` is below the applicable figure is refused with `ERR_EDUCATION_HOURS_SHORTFALL`. The blocked-trust minimum is fifteen hundredths of the executed stipend in `CA` and in `NY`, and ten hundredths in `GA` and in `IL`; a packet whose `trust_deposit_pct` is below the applicable fraction is refused with `ERR_TRUST_DEPOSIT_SHORTFALL`. Both minimums are inclusive floors — a packet exactly at the minimum satisfies it — and both are enforced identically when a packet is first filed and when it is later amended.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Production and Its Venues

Everything begins with a production record, created by a `ProductionAdmin`. The payload names the show by `title`, between 1 and 200 characters, and declares its `format_type` as one of `COMPETITION_HIGH_STRESS`, `DOCUSOAP`, `DATING_FORMAT` or `TALENT_SEARCH`. Format is not cosmetic: it drives the hazard uplift in the stipend computation, it forces psychological evaluation on every applicant, and it sets the opening duty-of-care posture. The record also carries `jurisdiction_code`, the `season_number` as an ordinal of at least 1, and `episode_order`, the season's ordered episode count, between 1 and 40 inclusive. Photography is bounded by `photography_start_utc` and `photography_end_utc`, the latter strictly after the former; the start instant is the reference point for every minor-age determination in the system, and the end instant anchors every post-production due date. Finally the payload declares three budget figures — `stipend_pool_cents` and `welfare_budget_cents`, each zero or greater, and `minor_participant_cap`, also zero or greater, being the maximum number of minor participants the production may carry under executed agreements.

At creation the server derives the production's opening welfare stance. A `COMPETITION_HIGH_STRESS` production opens at a `duty_of_care_tier` of `ENHANCED`; every other format opens at `STANDARD`. The posture opens at `OPEN`, and every rolled-up figure opens at zero: `stipend_committed_cents`, `welfare_committed_cents`, `trust_escrow_balance_cents`, `welfare_incident_count`, `breached_obligation_count` and `minor_participant_count`. Reading a production back returns all of those figures alongside the derived posture, and it is the read every role in the system is permitted to perform, participants included.

Venues are registered separately and are shared across productions. A venue carries a `name`, a `state_code`, a `capacity` of at least 1 describing how many heads it can hold at once, and `turnaround_buffer_minutes` — the strike and turnaround time reserved *after* each shoot block's end at that venue, defaulting to 60 minutes and permitted anywhere from 0 to 480. A venue may also carry `filming_permit_number`, its municipal filming permit; when that field is absent the venue may host studio work only, and any attempt to schedule exterior or public-space shooting there is refused.

### 3.2. Distributing Casting Calls and Open-Call Logistics

A `CastingDirector` drafts a casting call against a production by supplying the `production_id`, a `channel` of `OPEN_CALL`, `DIGITAL_SUBMISSION` or `REFERRAL`, an age band of `min_age` between 13 and 80 and `max_age` no smaller than `min_age` and no greater than 99, and `exclusivity_window_days` between 0 and 730 — the default exclusivity term the production intends to offer applicants recruited through this call. Optionally the draft narrows the recruiting pool with `residency_state_code`, in which case an applicant's own residency must equal it exactly. Open calls additionally need logistics: `venue_location_id` names the venue, `open_call_window_start_utc` and `open_call_window_end_utc` bound the intake window inclusively at both ends, and `expected_attendance` forecasts the head count, defaulting to 0 and never negative. A freshly drafted call sits in `DRAFT` status, has never been published, and carries no closing reason.

Publication moves the call `DRAFT → PUBLISHED` and is the point where open-call logistics become binding. Publication is refused unless the call is genuinely in `DRAFT`; unless the owning production's posture is `OPEN`, since both `RESTRICTED` and `FROZEN` productions reject publication; and, when the `channel` is `OPEN_CALL`, unless the venue, both window bounds and the expected attendance are all present. The venue capacity check then runs: the expected attendances of every other casting call at the same venue that is already `PUBLISHED`, has channel `OPEN_CALL`, and whose inclusive intake window intersects this one, are summed together with this call's own `expected_attendance`, and if that aggregate exceeds the venue's `capacity` the publication is refused with `ERR_VENUE_CAPACITY_EXCEEDED`. Two inclusive windows intersect when neither one's start falls after the other's end. On success the call's status becomes `PUBLISHED` and `published_at` is stamped with the logical clock's current instant.

A director may retire a live call at any time, moving it `PUBLISHED → CLOSED` with `closed_reason` recorded as `DIRECTOR_CLOSED`. The other two closing reasons are never chosen by a human: `POSTURE_RESTRICTED` and `POSTURE_FROZEN` are written by the posture cascades of §2.7, and a call carrying either of them was closed by the production's own finances or welfare record rather than by its director. Alongside its lifecycle fields each call maintains `screened_pass_count`, the number of applicants arriving through it whose `screening_status` has reached `CLEARED` or `CAST`; the counter is incremented by one each time one of the call's applicants clears screening. Calls can be listed and filtered by `production_id`, by `venue_location_id`, by `status` and by `channel`, and the applicants received through a single call can be listed and filtered by `screening_status` and `medical_status`.

### 3.3. Applicant Intake, Eligibility and Withdrawal

An application is recorded by a `CastingDirector` against a live call. The payload names the `casting_call_id`, the applicant's `legal_name` as it will appear on the participant agreement, their `date_of_birth` as an ISO 8601 calendar date in `YYYY-MM-DD` form, and their `residency_state_code`. When the applicant is a minor the payload must also name the parent or guardian of record as `guardian_name`; omitting it for a minor is refused with `ERR_GUARDIAN_REQUIRED`.

Intake is admitted only into a call whose `status` is `PUBLISHED` — an application against a draft or closed call is refused with `ERR_CASTING_CALL_NOT_OPEN` — and, when the call's channel is `OPEN_CALL`, only while the logical clock lies inside the inclusive intake window, failing which the answer is `ERR_OPEN_CALL_WINDOW_CLOSED`. Eligibility is then checked against the call's own criteria: the applicant's completed age at the production's `photography_start_utc` must lie inside the band bounded inclusively by `min_age` and `max_age`, and where the call demands a residency state the applicant's `residency_state_code` must equal it. Either failure is `ERR_ELIGIBILITY_NOT_MET`.

Three derived facts are settled at intake and shape everything that follows. `is_minor` is true when the applicant's completed age at `photography_start_utc` is under 18 — minority is judged as of the first day of principal photography, not as of the application date, so an applicant who turns 18 between applying and shooting is not a minor for this production's purposes. `psych_eval_required` is true when the production's `format_type` is `COMPETITION_HIGH_STRESS` or when `is_minor` is true; high-stress formats and minors both attract mandatory psychological evaluation. And the applicant's two independent state dimensions open at their initial values: `screening_status` at `SUBMITTED` and `medical_status` at `NOT_STARTED`. Both risk figures, `provisional_risk_score` and `final_risk_score`, open at 0, and `enhanced_support_required` opens false.

Withdrawal is the participant's own act, permitted only to the `Applicant` role and only against their own record — `X-User-ID` must equal the applicant's `id` — and only while `screening_status` is not already `WITHDRAWN` or `REJECTED`; the withdrawal payload carries a free-text `reason`. Withdrawal is by far the widest cascade in the system, and every link fires in order. First, the applicant's `screening_status` becomes `WITHDRAWN`, reachable from `SUBMITTED`, `SCREENING`, `CLEARED` or `CAST`. Second, because the applicant has withdrawn, every participant agreement of that applicant whose `status` is `DRAFTED`, `SENT`, `COUNTERED`, `REVISED` or `EXECUTED` moves to `VOIDED` with `void_reason` set to `APPLICANT_WITHDRAWN`. Third, because an executed agreement has been voided, that agreement's `total_stipend_commitment_cents` is zeroed, the production's `stipend_committed_cents` is recomputed by full re-summation, the production's `minor_participant_count` is recomputed, and every post-production obligation of that agreement still in `SCHEDULED` status moves to `EXCUSED`. Fourth, because the agreement was voided, every minor-protection packet of that applicant whose `status` is `INCOMPLETE`, `COMPLETE` or `LAPSED` moves to `RELEASED`, its `trust_deposited_cents` and `per_installment_cents` are zeroed, and the production's `trust_escrow_balance_cents` is recomputed. Fifth and last, because committed stipend changed, the production's `casting_posture` is re-derived.

### 3.4. Screening Instruments, Risk Scoring and Medical Clearance

Screening is conducted by a `ComplianceOfficer`, one instrument at a time, each recorded as its own item against an applicant. The item declares its `kind` — `INTERVIEW`, `BACKGROUND_CHECK`, `PSYCH_EVAL` or `MEDICAL_EXAM` — and may optionally carry its result in the same request. Supplying `outcome` records the result immediately; omitting it leaves the item's `outcome` at `PENDING` for later completion. Where a result is supplied the officer also supplies `severity_flags`, the count of adverse findings on that instrument from 0 to 5 with a default of 0, and, where the result is `CONDITIONAL`, may attach the free-text `conditional_conditions`. Opening any screening item while the applicant's `screening_status` is `SUBMITTED` or `SCREENING` advances that dimension `SUBMITTED → SCREENING` and refreshes the provisional risk figure.

Recording the outcome of an item that was left pending is the other path to the same place. It is admitted only while that item's `outcome` is still `PENDING`, and only while the applicant's `screening_status` is neither `WITHDRAWN` nor `REJECTED`; the payload carries `outcome`, `severity_flags` and optionally `conditional_conditions`, and the four-eyes screening rule of §2.10 is enforced on the way in. On success the item's `outcome` and `severity_flags` are written, `recorded_by_user_id` is stamped with the caller's `X-User-ID`, `recorded_at` is stamped with the logical clock, and `expires_at` is derived from the kind's validity window: a `MEDICAL_EXAM` clearance is valid for 30 days from `recorded_at`, a `PSYCH_EVAL` for 60 days, a `BACKGROUND_CHECK` for 180 days, and an `INTERVIEW` never expires, so its `expires_at` remains absent. Both risk figures are then refreshed and both applicant dimensions re-evaluated.

Risk is scored by weighted contribution. Each instrument kind carries a weight — 1.5 for an `INTERVIEW`, 3.0 for a `BACKGROUND_CHECK`, 4.0 for a `PSYCH_EVAL` and 2.0 for a `MEDICAL_EXAM` — and each recorded outcome carries a factor: `PASS` contributes a factor of zero, `CONDITIONAL` one half, and `FAIL` one. A recorded item's points are its `severity_flags` multiplied by its kind weight multiplied by its outcome factor, so a passing item contributes nothing however many flags it carries. The set of **required kinds** for an applicant is `INTERVIEW`, `BACKGROUND_CHECK` and `MEDICAL_EXAM`, plus `PSYCH_EVAL` when the applicant's `psych_eval_required` is true.

Two variants of that score exist side by side on the applicant, and they answer different questions. The **provisional ceiling** variant is written to `provisional_risk_score` on every screening-item write, and it charges every item that has not yet been recorded — every item whose `recorded_at` is still absent — at the pessimistic ceiling: 5 severity flags multiplied by that item's kind weight multiplied by a factor of one. Items that have been recorded contribute their own points at full weight, with no recency decay applied. The sum of the two groups is rounded half up to two decimal places once, at the end. The **final decayed** variant is written to `final_risk_score` only once every required kind has an item whose `recorded_at` is present; pending items contribute nothing at all to it. Its recorded items are ordered by `recorded_at` descending, with ties broken by `created_at` descending, and each item is then multiplied by a decay factor determined by its one-based position in that ordering: the first item keeps its full points, the second is multiplied by eight tenths, the third by six tenths, the fourth by one half, and every item from the fifth onward is also multiplied by one half. The decayed products are summed and the sum is rounded half up to two decimal places once. Because the two variants weight the same evidence differently, they disagree for identical data whenever any decayed item carries points at all, and every threshold in the screening pipeline reads the final decayed figure, never the provisional one.

The screening dimension resolves on those thresholds. An applicant advances `SCREENING → CLEARED` when every required kind has an item whose outcome is `PASS` or `CONDITIONAL`, no item of the applicant has outcome `FAIL`, and the final risk figure is strictly below 12.00. Clearing recomputes both risk figures, sets `enhanced_support_required` to true exactly when `final_risk_score` is 8.00 or above, and increments the originating casting call's `screened_pass_count` by one. An applicant instead advances `SCREENING → REJECTED` when the outcome just recorded is `FAIL`, or when every required kind is now recorded and the final risk figure has reached 12.00 or more; rejection likewise recomputes both risk figures before writing the status. Much later, execution of an agreement moves a cleared applicant `CLEARED → CAST` and increments the applicant's `version` by one.

Medical clearance runs on its own dimension and neither gates nor is gated by the screening dimension — only the agreement send gate reads both together. Opening a `MEDICAL_EXAM` item without an outcome moves `medical_status` `NOT_STARTED → PENDING`. Recording a `MEDICAL_EXAM` item with outcome `PASS` moves `medical_status` to `CLEARED` from any of `NOT_STARTED`, `PENDING`, `DEFERRED` or `EXPIRED`, and stamps that item's `expires_at` 30 days after its `recorded_at`. Recording a `MEDICAL_EXAM` item with outcome `CONDITIONAL` moves `medical_status` to `DEFERRED` from either `NOT_STARTED` or `PENDING`, and a deferred applicant cannot have an agreement sent to them until a passing exam is recorded. Finally, the welfare epoch sweep moves `medical_status` `CLEARED → EXPIRED` when the applicant's latest `MEDICAL_EXAM` item has an `expires_at` at or before the logical clock, incrementing the applicant's `version` by one as it does so.

### 3.5. Minor Participant Protections and the Blocked Trust

Where an applicant is a minor, a `ComplianceOfficer` files a protection packet for them before any agreement can be sent. The packet carries the state-issued `work_permit_number`, the `permit_expires_on` date on which that permit lapses as an ISO 8601 calendar date, the `education_hours_scheduled_weekly` of on-set tutoring from 0 to 40 hours, and `trust_deposit_pct`, the fraction of the executed stipend commitment that will be deposited into the blocked trust account, expressed from 0 to 1 with two decimals.

A packet's `status` is derived, never supplied. It becomes `COMPLETE` when all three of its conditions hold together — the permit's expiry date is strictly after the logical clock's date, the scheduled education hours are at least the jurisdiction's weekly minimum, and the trust percentage is at least the jurisdiction's minimum fraction — and `INCOMPLETE` otherwise. Amendment re-derives the status in both directions with equal force: a packet may be patched with any of `work_permit_number`, `permit_expires_on`, `education_hours_scheduled_weekly` or `trust_deposit_pct`, and where the amended packet satisfies all three conditions it moves `INCOMPLETE → COMPLETE`, while where the amended packet no longer satisfies all three it moves `COMPLETE → INCOMPLETE`. Note the asymmetry between the derivation and the guards of §2.6: a shortfall in education hours or trust percentage is refused outright at filing and amendment time with its own error, so the `INCOMPLETE` derivation is reached in practice through an expired or expiring permit.

Two further transitions are driven by the system rather than by the officer. The welfare epoch sweep moves a `COMPLETE` packet to `LAPSED` when `permit_expires_on` falls at or before the logical clock, and that lapse is not silent: every participant agreement of the same applicant whose `status` is `SENT`, `COUNTERED`, `REVISED` or `EXECUTED` has `welfare_hold` set to true, freezing further negotiation on it. And whenever the applicant's agreement moves to `VOIDED`, every packet of that applicant that is not already `RELEASED` — that is, any packet in `INCOMPLETE`, `COMPLETE` or `LAPSED` — moves to `RELEASED` with `trust_deposited_cents` and `per_installment_cents` zeroed and the production's `trust_escrow_balance_cents` recomputed. Releasing the trust is a refund, and because both the packet's deposit figure and the escrow rollup are recomputed from scratch, the refund leaves the production's escrow figure exactly where it stood before the deposit.

Funding the trust is a `BusinessAffairs` act, and it is admitted only once the applicant's agreement has reached `EXECUTED` — a deposit requested any earlier is refused with `ERR_AGREEMENT_NOT_EXECUTED`. The only input is `installment_count`, the number of equal installments requested, from 1 to 24 inclusive. The target amount is the executed agreement's `total_stipend_commitment_cents` multiplied by the packet's `trust_deposit_pct`. That target is divided by the installment count and the quotient is rounded half up to whole cents to give `per_installment_cents`; `trust_deposited_cents` is then that rounded installment multiplied by the installment count, and it is not rounded again. The single executed agreement used here is the applicant's only agreement that is not voided. Once the packet's figures are written, the production's `trust_escrow_balance_cents` is recomputed as described in §2.11. A deposit brings no deposit record of its own into existence — there is no such record type in this system, as §2.4's enumeration shows: funding is an amendment of the minor-protection packet itself, which has the requested `installment_count` recorded on it alongside the two derived figures and is refreshed and version-incremented as any other mutation. The response therefore carries the amended packet in `data` under the uniform `200 OK` of §4, not a `201`.

### 3.6. Drafting, Negotiating and Executing Participant Agreements

Negotiation is where the API earns its keep. A `BusinessAffairs` user drafts an agreement by naming the `applicant_id` and the `production_id`, the `exclusivity_window_days` from 0 to 730 during which the participant may not appear on a competing programme after wrap, the `confidentiality_tier` as `STANDARD`, `ENHANCED` or `PERPETUAL`, the `depiction_rights_scope` as `FULL`, `LIMITED` or `PSEUDONYMIZED`, the `stipend_structure` as `FLAT`, `PER_EPISODE` or `TIERED` — the shape the money takes as agreed with the participant, recorded on the agreement as part of its terms — the `base_stipend_cents` per episode, and `episodes_committed` from 1 to 40. The draft may also carry `press_appearance_obligation_count`, the number of contracted press-junket appearances from 0 to 6 with a default of 0, and `reunion_obligation`, defaulting to false, stating whether the participant owes a reunion taping. `expected_applicant_version` is mandatory, as §2.9 requires. A draft may finally name `supersedes_agreement_id`, the same applicant's prior non-terminal agreement that this one replaces; when supplied, that prior agreement — which must belong to the same applicant and be in `DRAFTED`, `SENT`, `COUNTERED` or `REVISED` status — moves to `VOIDED` with `void_reason` set to `SUPERSEDED` and its `version` incremented by one. A first agreement leaves the field absent. Drafting opens the agreement at `status` `DRAFTED` with `round_number` at 0, both stipend figures at 0, `welfare_hold` false, and it increments the applicant's `version` by one.

Sending the agreement to the participant is the system's most heavily guarded transition, reachable from `DRAFTED → SENT` and again from `REVISED → SENT`, with identical preconditions on both paths. Sending requires that the agreement be in `DRAFTED` or `REVISED` status, that its `welfare_hold` be false, that the production's posture not be `FROZEN`, that the applicant's `screening_status` be `CLEARED` and their `medical_status` be `CLEARED`, that where `psych_eval_required` is true the applicant hold a `PSYCH_EVAL` item whose outcome is `PASS` or `CONDITIONAL` and whose `expires_at` is either absent or later than the logical clock, that where `enhanced_support_required` is true the production hold a welfare protocol of kind `ONSET_PSYCH_SUPPORT` in `ACTIVE` status whose coverage interval contains the whole span from `photography_start_utc` to `photography_end_utc`, that where the applicant `is_minor` they hold a minor-protection packet in `COMPLETE` status whose `permit_expires_on` is later than the logical clock, and finally that the production's `stipend_committed_cents` plus this agreement's provisional stipend figure stay within `stipend_pool_cents`, failing which the answer is `ERR_STIPEND_POOL_EXCEEDED`. On success the provisional stipend variant is written to `provisional_stipend_cents` — recomputed from the revised terms when the send follows a revision — and the status becomes `SENT`. Sending never changes `round_number`.

A participant who wants better terms counters, moving the agreement `SENT → COUNTERED`. The counter is admitted only from `SENT`, only while `welfare_hold` is false, only when `X-User-ID` equals the agreement's `applicant_id`, and only when `expected_agreement_version` matches the agreement's current `version`. The payload proposes `requested_base_stipend_cents`, `requested_exclusivity_window_days` and `requested_depiction_rights_scope`. A negotiation round is appended against the `agreement_id` of the agreement under negotiation, recording `proposed_by` as `PARTICIPANT`, `disposition` as `COUNTERED`, `proposer_user_id` as the caller's `X-User-ID`, `recorded_at` at the logical clock, and `round_number` as one more than the agreement's current round count; the agreement's own `round_number` is incremented by one, its `status` becomes `COUNTERED`, and its `version` is incremented by one. The append-only negotiation log of an agreement can be read back and filtered by `proposed_by`.

The production answers a counter by revising, moving the agreement `COUNTERED → REVISED`. Revision is admitted only from `COUNTERED` and only while `welfare_hold` is false. It overwrites the agreement's `base_stipend_cents`, `exclusivity_window_days` and `depiction_rights_scope`, together with `episodes_committed`, `press_appearance_obligation_count` and `reunion_obligation` where those are supplied. A negotiation round is appended with `proposed_by` as `PRODUCTION` and `disposition` as `REVISED`, carrying the revised terms and a `round_number` one greater than the current count; `last_production_proposer_user_id` is set to the revising user's `X-User-ID`, the agreement's `round_number` is incremented by one, and the status becomes `REVISED`. From `REVISED` the agreement is sent again, and the cycle `SENT → COUNTERED → REVISED → SENT` may repeat without any bound on the number of rounds. Note what the cycle implies for the stipend computation: negotiation history is never re-read, because each revision has already overwritten the agreement's own term fields, and those current fields are the sole authority.

Execution moves the agreement `SENT → EXECUTED` and is admitted only from `SENT`, only while `welfare_hold` is false, only while the production's posture is not `FROZEN`, only when the four-eyes execution rule of §2.10 is satisfied, only while the applicant's `screening_status` and `medical_status` are both `CLEARED`, only when a minor applicant still fits under the cap — the production's `minor_participant_count` plus one must be no greater than `minor_participant_cap`, failing which the answer is `ERR_MINOR_CAP_EXCEEDED` — and only when `stipend_committed_cents` plus this agreement's final stipend figure stay within `stipend_pool_cents`. The execution cascade then runs in a fixed order. First, the final stipend variant is written to `total_stipend_commitment_cents`, the status becomes `EXECUTED`, `executed_by_user_id` is stamped with the caller's `X-User-ID`, `executed_at` is stamped with the logical clock, and the applicant's `screening_status` moves to `CAST`. Second, because the final commitment was written, the production's `stipend_committed_cents` is recomputed by full re-summation over executed agreements and its `minor_participant_count` is recomputed as the count of executed agreements whose applicant is a minor. Third, because committed stipend changed, the production's `casting_posture` is re-derived and may become `RESTRICTED`. Fourth, if the posture did become `RESTRICTED`, every casting call of that production that is `PUBLISHED` with channel `OPEN_CALL` moves to `CLOSED` with `closed_reason` `POSTURE_RESTRICTED`. Alongside those four links, execution auto-creates the agreement's post-production obligations, as described in §3.9.

Voiding is the compensating action for executing, and it is reachable from `DRAFTED`, `SENT`, `COUNTERED`, `REVISED` or `EXECUTED` — from any status except `VOIDED` itself. The caller supplies `void_reason`, one of `WELFARE_BREACH`, `APPLICANT_WITHDRAWN`, `BUSINESS_AFFAIRS_VOID` or `SUPERSEDED`, and the status becomes `VOIDED`. Where the prior status was `EXECUTED` the full unwind follows: `total_stipend_commitment_cents` is zeroed, the production's `stipend_committed_cents` is recomputed by full re-summation, `minor_participant_count` is recomputed, every post-production obligation of the agreement still in `SCHEDULED` status moves to `EXCUSED`, every minor-protection packet of the applicant moves to `RELEASED` with its `trust_deposited_cents` zeroed, and the production's `trust_escrow_balance_cents` is recomputed. In every case, executed or not, the production's `casting_posture` is re-derived at the end. Voiding conserves both committed stipend and trust escrow exactly.

The stipend commitment itself is computed from a single agreement row plus its production's `format_type` and `episode_order`, and it is computed twice in the life of an agreement under two variants that differ in their assumptions. The common shape is a tiered per-episode base, a hazard uplift, an exclusivity premium, press and reunion components, and finally a depiction adjustment. The tier multiplier is selected by the episode count used: a count of 4 or fewer takes a multiplier of 1.00, a count from 5 to 8 inclusive takes 1.15, and a count of 9 or more takes 1.30. The **base component** is `base_stipend_cents` multiplied by the episode count used, multiplied by that tier multiplier, rounded half up to whole cents. The **hazard component** applies only to a production whose `format_type` is `COMPETITION_HIGH_STRESS`, where it is one tenth of the rounded base component, itself rounded half up to whole cents; for every other format it is zero. The **exclusivity component** charges a premium of 40,000 cents for each 30-day block of exclusivity, where the number of blocks is `exclusivity_window_days` divided by 30 and rounded *up* to a whole number — a 31-day window is charged as two blocks, a 60-day window as two, a 61-day window as three. The **press component** is a rate of 25,000 cents for each contracted press appearance. The **reunion component** is a flat 150,000 cents when a reunion is owed and zero when it is not. Those five rounded components are then summed into a subtotal, and the **depiction adjustment** is that subtotal multiplied by the percentage for the agreement's `depiction_rights_scope` — nothing at all for `FULL`, a reduction of five hundredths for `LIMITED`, and a reduction of twelve hundredths for `PSEUDONYMIZED` — rounded half up to whole cents. The total is the subtotal plus that adjustment, which for a limited or pseudonymised licence is a discount.

The **provisional** variant, written to `provisional_stipend_cents` on every send transition and read by the send-time pool guard, is a deliberately forward-looking worst case over that same row. It uses as its episode count the larger of `episodes_committed` and the production's `episode_order`, on the assumption that the participant is retained for the full season — and because that larger count can cross a tier boundary, the tier multiplier itself may differ from the final variant's. It charges the press component against `press_appearance_obligation_count` plus a reserve of 2 further appearances. It charges the reunion flat amount unconditionally, whether or not a reunion is actually owed. And it applies no depiction adjustment at all, assuming no discount. The **final** variant, written to `total_stipend_commitment_cents` on execution and zeroed on voiding, uses `episodes_committed` exactly as agreed, the contracted press count without any reserve, the actual `reunion_obligation` flag, and it does apply the depiction adjustment. The final variant is the only one that enters the production's committed-stipend rollup; the provisional figure never does.

Agreements may be listed and filtered by `production_id`, by `applicant_id`, by `supersedes_agreement_id` and by `status`, and a single agreement read back exposes both stipend variants alongside `round_number` and the negotiation audit keys.

### 3.7. Welfare Protocols, Duty of Care and the Welfare Epoch

A `WelfareOfficer` plans welfare instruments against a production. Each protocol declares its `kind` — `DUTY_OF_CARE_OFFICER`, `ONSET_PSYCH_SUPPORT`, `INSURANCE_RIDER` or `AFTERCARE_PROGRAM` — its inclusive `coverage_start_utc` and `coverage_end_utc`, the latter strictly after the former, and its committed `cost_cents`, zero or greater. A protocol whose kind is `INSURANCE_RIDER` must also carry `carrier_certificate_number`, both when it is planned and when it is later activated; without it the answer is `ERR_INSURANCE_CERTIFICATE_MISSING`. A newly planned protocol sits at `status` `PLANNED`.

Activation moves a protocol `PLANNED → ACTIVE` and is admitted only from `PLANNED`, only when an insurance rider carries its certificate, and only while `coverage_end_utc` is still later than the logical clock — coverage that is already over cannot be activated. Cancellation moves a protocol to `CANCELLED` from either `PLANNED` or `ACTIVE`, and it is the exact compensating action for planning one. The welfare epoch sweep moves an `ACTIVE` protocol to `EXPIRED` once its `coverage_end_utc` falls at or before the logical clock. Protocols can be listed per production and filtered by `status` and by `kind`.

Committed welfare is recomputed after any protocol is planned, activated or cancelled, after the epoch sweep, and whenever the production's `duty_of_care_tier` changes. Its evaluation order is pinned in four steps, which breaks an apparent circularity between the surcharge and the band that sets the surcharge rate. Step one sums `cost_cents` over the production's protocols whose `status` is `PLANNED` or `ACTIVE`, excluding both `EXPIRED` and `CANCELLED` rows, to give the protocol subtotal; coverage dates play no part in membership, only the sweep's expiry transition does. Notably, because `PLANNED` and `ACTIVE` rows both count, activating a protocol leaves the subtotal unchanged, and because cancelled rows drop out, cancelling one removes its cost exactly. Step two selects the band rate from that pre-surcharge subtotal: four hundredths when the subtotal is below 5,000,000 cents, seven hundredths when it is at least 5,000,000 cents and below 20,000,000 cents, and nine hundredths when it is 20,000,000 cents or more. Step three multiplies the subtotal by that band rate and again by the tier factor for the production's current `duty_of_care_tier` — one for `STANDARD`, one and a half for `ENHANCED`, two for `CRITICAL` — rounding the product half up to whole cents to give the duty-of-care surcharge. Step four sets `welfare_committed_cents` to the protocol subtotal plus that surcharge. Planning or activating a protocol whose effect would push the recomputed `welfare_committed_cents` above `welfare_budget_cents` is refused with `ERR_WELFARE_BUDGET_EXCEEDED`. Each of the three protocol writes — planning, activation and cancellation — rewrites the production's committed-welfare figure and re-derives its posture, and therefore refreshes the production's `updated_at` and increments the production's `version` by one.

The duty-of-care tier is therefore a cost multiplier as well as a welfare stance. It opens at `ENHANCED` for a high-stress format and at `STANDARD` otherwise, and it escalates one level — `STANDARD` to `ENHANCED`, `ENHANCED` to `CRITICAL` — for each escalated complaint that constitutes a duty-of-care breach, with `CRITICAL` as a hard ceiling that no further breach can exceed.

The welfare epoch sweep is an operator-driven checkpoint, invoked by a `ProductionAdmin` against one production, that applies everything the passage of the logical clock has made true. Its work runs in order. Every `ACTIVE` welfare protocol whose `coverage_end_utc` is at or before the logical clock becomes `EXPIRED`. Every `COMPLETE` minor-protection packet whose `permit_expires_on` is at or before the logical clock becomes `LAPSED`, and sets `welfare_hold` on that applicant's agreements in `SENT`, `COUNTERED`, `REVISED` or `EXECUTED` status. Every applicant whose latest `MEDICAL_EXAM` item has an `expires_at` at or before the logical clock moves `medical_status` from `CLEARED` to `EXPIRED`. Every `SCHEDULED` post-production obligation whose `due_utc` is at or before the logical clock becomes `BREACHED`, incrementing the production's `breached_obligation_count` and setting `welfare_hold` on its agreement once that agreement holds two or more breached obligations. Finally the sweep recomputes `welfare_committed_cents` and re-derives `casting_posture`, and increments the production's `version` by one. The sweep is the only mechanism that applies expiry, lapse and breach; moving the logical clock alone changes nothing.

### 3.8. Shooting Blocks, Incidental Releases and Minor Hour Caps

A `ProductionAdmin` schedules a shooting block by naming the `production_id`, the `location_id` of the occupied venue, the `block_kind` as `STUDIO`, `LOCATION_EXTERIOR` or `PUBLIC_SPACE`, the inclusive `start_utc` and the exclusive `end_utc` strictly after it, and `participant_agreement_ids`, the array of executed agreements called to the block, holding from 0 to 40 entries with no duplicates. Two optional figures complete the payload: `expected_crowd_headcount`, the forecast incidental crowd size from 0 to 5,000 with a default of 0, where 0 means no incidental appearances are expected at all; and `onset_minor_hours`, the number of on-set hours each minor participant of the block is called for, from 0 to 12 with one decimal place and a default of 0. A newly scheduled block opens at `status` `SCHEDULED`, with `minor_participant_count` computed as the number of called agreements whose applicant is a minor, `covered_head_count` at 0 and `release_coverage_complete` false.

Scheduling is guarded by five business rules beyond body shape, and the ladder of §2.6 fixes which one a client hears first. Every entry of `participant_agreement_ids` must belong to the named production and be in `EXECUTED` status, failing which the answer is `ERR_PARTICIPANT_NOT_EXECUTED`. A block whose kind is `LOCATION_EXTERIOR` or `PUBLIC_SPACE` must sit at a venue carrying a `filming_permit_number`; a permit-less venue may host `STUDIO` work only, and any other kind there is refused with `ERR_LOCATION_PERMIT_MISSING`. Every minor called to the block must hold an unexpired work permit, checked as `permit_expires_on` strictly after the logical clock's date. The block interval must lie inside the production's window from `photography_start_utc` to `photography_end_utc`. And the block must not collide with another block at the same venue: each block occupies the half-open interval that begins at its `start_utc` and ends at its `end_utc` extended by the venue's `turnaround_buffer_minutes`, and if that extended interval intersects the extended interval of any other block at the same location whose `status` is `SCHEDULED` or `ROLLING`, the scheduling is refused with `ERR_LOCATION_BLOCK_CONFLICT`. Because the interval is half-open, a block beginning exactly when the previous block's buffer ends does not collide.

Rolling moves a block `SCHEDULED → ROLLING` and is the on-set safety gate. It is admitted only from `SCHEDULED`, only while the production's posture is not `FROZEN`, and only when three welfare conditions hold. The production must hold a welfare protocol of kind `DUTY_OF_CARE_OFFICER` in `ACTIVE` status whose `coverage_start_utc` is at or before the block's `start_utc` and whose `coverage_end_utc` is at or after the block's `end_utc`; partial coverage is not coverage, and the failure is `ERR_DUTY_OF_CARE_UNCOVERED`. Every called participant's applicant must have `medical_status` `CLEARED`; a participant whose clearance has gone `EXPIRED` or has been left `DEFERRED` blocks the roll with `ERR_MEDICAL_CLEARANCE_EXPIRED`. And no minor may be over-scheduled for the day.

The minor daily-hours rule deserves care, because it is aggregate-capacity semantics over a calendar-date bucket rather than a pairwise interval intersection: two blocks falling on the same UTC calendar date collide on the cap even when their clock intervals do not overlap at all. For each minor called to the block being rolled, the bucket is the UTC calendar date of that block's `start_utc`. The minor's on-set hours for that bucket are this block's `onset_minor_hours` plus the `onset_minor_hours` of every other shoot block of the same production whose `status` is `ROLLING` or `WRAPPED`, that lists the same agreement in its `participant_agreement_ids`, and whose `start_utc` falls on the same UTC calendar date; blocks still `SCHEDULED` and blocks already `CANCELLED` are excluded from that sum. The minor's education hours for the day are their packet's `education_hours_scheduled_weekly` divided by 5, the number of tutoring days in a week. If the sum of on-set hours and education hours for any called minor exceeds a total daily cap of 8.0 hours, the roll is refused with `ERR_MINOR_DAILY_HOURS_EXCEEDED`; a total of exactly 8.0 hours is permitted, since only a total above the cap is a violation.

Incidental appearances are covered by releases collected on the block. Each release declares its `subject_kind` as `INCIDENTAL_CROWD`, `BYSTANDER_IDENTIFIABLE`, `PROPERTY_OWNER` or `MINOR_INCIDENTAL`, a `head_count` from 1 to 5,000 covering however many heads the paper covers, and a `disposition` of `COLLECTED`, `REFUSED` or `BLURRED_WAIVER`. It may name the subject as `subject_name`, which is absent for blanket crowd releases, and it carries `guardian_signature`, defaulting to false; a release whose subject kind is `MINOR_INCIDENTAL` must carry that counter-signature set to true or it is refused with `ERR_GUARDIAN_SIGNATURE_REQUIRED`. Each release is filed against the `shoot_block_id` of the block it was collected on, which the request path supplies rather than the payload. Collection stamps `collected_at` with the logical clock and is never mutated afterwards. Releases on a block can be listed and filtered by `subject_kind` and by `disposition`.

Every release write, and again the start of every wrap attempt, recomputes the block's coverage. `covered_head_count` is the sum of `head_count` over the block's releases whose `disposition` is `COLLECTED` or `BLURRED_WAIVER`; a `REFUSED` release contributes nothing. `release_coverage_complete` is true when `covered_head_count` is greater than or equal to `expected_crowd_headcount` **and** every release of the block whose `subject_kind` is `MINOR_INCIDENTAL` carries `guardian_signature` true. A block expecting no crowd at all, with no releases collected, is vacuously complete, because the sum over an empty set is 0 and 0 is not less than 0. Wrapping moves a block `ROLLING → WRAPPED`, is admitted only from `ROLLING`, and re-evaluates coverage at wrap time; incomplete coverage is refused with `ERR_RELEASE_COVERAGE_INCOMPLETE`. Blocks can be listed and filtered by `production_id`, by `location_id` and by `status`, and a single block read back exposes its coverage rollup.

### 3.9. Post-Production Obligations, Complaints and Aftercare

Executing an agreement automatically creates the participant's post-production obligations, in a pinned creation order and with fees drawn from the same rate constants the stipend computation uses, so that the obligations always reconcile with the components the participant was paid for. For each ordinal from 1 up to `press_appearance_obligation_count`, a press obligation is created with `kind` `PRESS_JUNKET`, its `sequence_ordinal` set to that ordinal, its `fee_cents` set to the press appearance rate of 25,000 cents, and its `due_utc` set to the production's `photography_end_utc` advanced by 30 days multiplied by the ordinal — so the first junket falls 30 days after wrap, the second 60 days after, the third 90 days after, and so on. Then, and only when `reunion_obligation` is true, a single reunion obligation is created with `kind` `REUNION_TAPING`, `sequence_ordinal` 1, `fee_cents` of 150,000 cents, and `due_utc` set to `photography_end_utc` advanced by 180 days. All press rows are created first in ascending ordinal order, and the reunion row last. Every obligation records the `agreement_id` that owes the appearance and opens at `status` `SCHEDULED` with `fulfilled_at` absent. Complaints likewise hang off the `agreement_id` they arise under.

`BusinessAffairs` closes an obligation out by recording the appearance, moving it `SCHEDULED → FULFILLED` and stamping `fulfilled_at` with the logical clock. Fulfilment is admitted only while the obligation is `SCHEDULED` and only while the owning agreement is still `EXECUTED`. An obligation left unfulfilled past its due date is caught by the welfare epoch sweep, which moves it `SCHEDULED → BREACHED` when `due_utc` falls at or before the logical clock, increments the production's `breached_obligation_count`, and — once the owning agreement carries two or more breached obligations — sets that agreement's `welfare_hold` to true, so that repeat non-appearance freezes the participant's contractual position. An obligation is instead moved `SCHEDULED → EXCUSED`, with its `version` incremented by one, when the owning agreement is voided for any reason. Obligations can be listed per agreement and filtered by `status` and by `kind`.

A participant files a complaint against their own agreement, permitted only while that agreement's `status` is `EXECUTED` or `VOIDED`; a complaint against an agreement still in negotiation is refused with `ERR_COMPLAINT_TARGET_INVALID`. The filing carries a `category` of `WELFARE`, `MISREPRESENTATION`, `HARASSMENT` or `PAYMENT`, a reporter-assessed `severity` from 1 to 5, and a `narrative` of between 1 and 2,000 characters. The complaint opens at `status` `OPEN` with `duty_of_care_breach` false and `aftercare_sessions_authorized` at 0. Complaints filed under one agreement can be listed and filtered by `status` and by `category`.

A `WelfareOfficer` then triages, moving the complaint `OPEN → TRIAGED` and stamping `triaged_by_user_id` with the caller's `X-User-ID`. From `TRIAGED` the complaint forks, and the fork is chosen by the `route` field of the routing request: a value of `AFTERCARE` takes the aftercare branch and a value of `ESCALATION` takes the escalation branch. Both branches stamp `routed_by_user_id`, and both write `aftercare_sessions_authorized` using the same authorisation rule — but their side-effect sets diverge sharply.

Session authorisation reads the complaint's severity and the production's duty-of-care tier **as of the start of the routing transition**, that is, before any escalation performed by the very same request. The base session count is 2 sessions at severity 1, 4 at severity 2, 8 at severity 3, 12 at severity 4 and 16 at severity 5. That base is multiplied by the tier factor — one for `STANDARD`, one and a half for `ENHANCED`, two for `CRITICAL` — and the product is rounded half up to a whole number of sessions. The authorised figure is then the smaller of that rounded number and a hard ceiling of 24 sessions.

The aftercare branch is the quiet one. It moves the complaint `TRIAGED → AFTERCARE_ACTIVE`, stamps `routed_by_user_id`, writes `aftercare_sessions_authorized` from the pre-transition tier, leaves `duty_of_care_breach` false, and mutates no field on the production whatsoever. No incident is counted, no tier escalates, no budget is re-evaluated and no posture moves.

The escalation branch moves the complaint `TRIAGED → ESCALATED`, stamps `routed_by_user_id`, writes `aftercare_sessions_authorized` from the pre-escalation tier, and derives `duty_of_care_breach` as true exactly when the complaint's `category` is `WELFARE` or `HARASSMENT` **and** its `severity` is 4 or more. Where that derivation is true, four further links fire in order, each only while its own precondition still holds. Because the escalation is a duty-of-care breach, the production's `welfare_incident_count` is incremented and its `duty_of_care_tier` escalates one level, `STANDARD` to `ENHANCED` or `ENHANCED` to `CRITICAL`, capped at `CRITICAL`. Because the tier changed, the production's `welfare_committed_cents` is recomputed with the higher tier factor. Because the recomputed commitment can now exceed `welfare_budget_cents`, the posture derivation may set `casting_posture` to `FROZEN` — and note that a second breach alone freezes the production regardless of budget, since the incident-count clause fires at 2. Because the posture became `FROZEN`, every `PUBLISHED` casting call of the production moves to `CLOSED` with `closed_reason` `POSTURE_FROZEN`, every `SCHEDULED` shoot block moves to `CANCELLED`, and every participant agreement in `DRAFTED`, `SENT`, `COUNTERED` or `REVISED` status has `welfare_hold` set to true. An escalation that is *not* a duty-of-care breach stops after the first link: the complaint is `ESCALATED`, sessions are authorised, and nothing on the production changes.

Both branches join at resolution. A `WelfareOfficer` moves the complaint to `RESOLVED` from either `AFTERCARE_ACTIVE` or `ESCALATED`, recording a closing `resolution_note`. Resolution is deliberately not a reversal: `welfare_incident_count` is never decremented, and `duty_of_care_tier` never steps back down, so a production that has sustained an escalated breach keeps its escalated tier — and therefore its higher welfare surcharge — for the remainder of the season.
