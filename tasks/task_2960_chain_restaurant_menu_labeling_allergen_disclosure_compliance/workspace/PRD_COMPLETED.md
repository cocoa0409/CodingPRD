# Chain Menu Labeling API — Product Requirements Document

## 1. Introduction

Restaurant chains that operate twenty or more units under the same public-facing name are required to declare calorie content for the standard items on their menus and menu boards, to keep additional written nutrition information available to any guest who asks for it, and to publish an allergen matrix with an honest cross-contact statement. In practice the burden is not the arithmetic — it is the bookkeeping. A single supplier substitution changes one recipe, which changes one item's declared calorie range, which invalidates the printed line on every board in every store that lists it, which starts a reprint clock whose length depends on the state or local authority that governs each individual store. Compliance teams today track this in spreadsheets, and the failure they report most often is not a miscalculated calorie figure but a board that quietly went stale and was still hanging above a counter when an inspector walked in.

This document specifies the Chain Menu Labeling API, the system of record that replaces those spreadsheets. It holds the chain's brand register, its unit estate, its menu, its versioned recipe sheets and laboratory certifications, its menu boards and the individual printed lines on them, its allergen disclosure packets, its variance filings with state and local authorities, and the enforcement files those authorities open against it. Every derived compliance figure — whether a brand is a covered establishment, whether a menu board's printed declarations still match the certified recipes, how much a brand owes on an assessed penalty — is computed and stored by the server rather than asserted by the client, so that two operators reading the same brand never disagree about its standing.

The service is deliberately opinionated about two things. First, **segregation of duties**: the laboratory analyst who submits a recipe for nutrition analysis may not be the analyst who certifies it, and the brand side, the store side and the regulator side own disjoint write surfaces. Second, **derived gating**: a brand whose compliance record has slipped past a hard line is frozen out of expanding its menu or its board estate until it recovers, and that freeze is a consequence the system computes, never a flag an operator sets. Everything that follows elaborates those two commitments into a concrete HTTP contract. All resources are mounted at the root of the service; no resource path nests one identifier inside another.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint — reads included — must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names the role it acts in. A request that omits `X-User-ID`, sends it with no value, sends it as an empty string, or sends it as a value made up entirely of whitespace is rejected with `ERR_MISSING_AUTH` (HTTP 401) before anything else about the request is examined, including before `X-User-Role` is looked at. A request whose `X-User-Role` is absent, empty, whitespace-only, or not exactly one of the five recognised role names is rejected with `ERR_INVALID_ROLE`, also HTTP 401; the role header is matched against the five names without being trimmed first, so a role name padded with surrounding whitespace is not a recognised role. Only after both headers are known good does the service ask whether that role is permitted on the requested operation; a recognised role attempting an operation it does not hold receives `ERR_UNAUTHORIZED` (HTTP 403).

The five roles are `PlatformAdmin`, `BrandComplianceOfficer`, `NutritionAnalyst`, `MenuboardPublisher` and `StateRegulator`. Their names are case-sensitive and are the only accepted values of `X-User-Role`.

- **`PlatformAdmin`** is the program operator. It registers chain brands, registers state and local authorities, registers and re-statuses units, runs coverage determinations on demand, and controls the service's logical clock. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any row's `id`, and no write by this role is ownership-scoped.
- **`BrandComplianceOfficer`** acts for exactly one chain brand. When `X-User-Role` is `BrandComplianceOfficer`, `X-User-ID` is the `id` of the acting `Brand`; ownership checks on any resource that references a `Brand` compare the resource's brand foreign key to `X-User-ID`. This role owns the menu, the disclosure packet, variance filings and citation responses.
- **`NutritionAnalyst`** is an independent laboratory analyst who owns recipe versions, their components, and the certification decision. When `X-User-Role` is `NutritionAnalyst`, `X-User-ID` is an opaque analyst identifier not tied to any persisted entity. The server records it — as `submitted_by_user_id` when a recipe is sent into analysis and as `decided_by_user_id` when the analysis is decided — but never compares it to any entity's `id`. It is recorded precisely so that two distinct analysts can be told apart for segregation of duties.
- **`MenuboardPublisher`** acts for exactly one unit. When `X-User-Role` is `MenuboardPublisher`, `X-User-ID` is the `id` of the acting `Establishment`; ownership checks on any resource that references an `Establishment` compare the resource's establishment foreign key to `X-User-ID`. This role owns menu boards, the lines printed on them, publication and reprints.
- **`StateRegulator`** acts for exactly one state or local authority. When `X-User-Role` is `StateRegulator`, `X-User-ID` is the `id` of the acting `Jurisdiction`; ownership checks on any resource that references a `Jurisdiction` compare the resource's jurisdiction foreign key to `X-User-ID`. This role decides variance requests and drives enforcement.

Ownership scoping applies to writes only. Every read endpoint in this specification is open to all five roles and is never ownership-scoped: a `StateRegulator` may read a brand it has never cited, and a `BrandComplianceOfficer` may read a competitor's menu. A write by one of the three entity-backed roles against a resource that belongs to a different entity than the one `X-User-ID` names is rejected with `ERR_FORBIDDEN_SCOPE` (HTTP 403). Because role authorization is decided before ownership, a caller holding the wrong role for an operation *and* pointing at somebody else's resource receives `ERR_UNAUTHORIZED`, not `ERR_FORBIDDEN_SCOPE`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`: the literal prefix `req_` followed by exactly twenty characters drawn from the uppercase letters `A` through `Z` and the digits `0` through `9`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. Like `created_at` and `updated_at`, it is read from the service's real wall-clock time and never from the logical clock of §2.4, so it does not move when a `PlatformAdmin` sets the clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size; it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls how many rows are skipped before the page begins; it defaults to 0 and its minimum accepted value is 0. A supplied `limit` below 1 or above 100, or a supplied `offset` below 0, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400) — so `limit` of 0 and `limit` of 101 are both refused while `limit` of 1 and `limit` of 100 are both accepted. A supplied value that is not a base-ten integer at all — an empty value, a decimal such as `10.5`, or any other non-numeric text — is refused with the same `ERR_INVALID_PAGINATION`, while whitespace surrounding an otherwise valid integer is tolerated. A parameter that is simply omitted takes its default and is never an error, and neither parameter has an upper bound on `offset`: an `offset` past the end of the result set is accepted and returns an empty page with the true `total_count`.

Unless a specific list endpoint states otherwise, list results are ordered by `created_at` ascending. The one documented exception is the brand's disclosure-packet listing, which is ordered by `packet_version` descending so that the newest packet appears first. Because `created_at` is stamped only to millisecond precision, two rows inserted by the same request routinely carry an identical `created_at`; such ties are broken by insertion order, so the row inserted first is listed first.

For list responses the `meta` object carries the four pagination fields — `limit` and `offset` echoing the effective values in force for the request, `total_count` giving the number of rows that match the filter before the page window is applied, and `has_more` set to true when rows matching the filter remain beyond the current window. Single-resource responses omit all four.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource is keyed by `id`, a server-minted UUID string carrying no type prefix and no embedded meaning. Clients never supply an `id`; a client-supplied `id` in a request body is not honoured. The entire store lives in the service process's memory and comes up completely empty on every boot: no brands, authorities, units, reference rows or demonstration data of any kind are seeded, so the first read of any collection returns an empty page and every scenario must build the rows it needs through the write operations of §4.

Most resources also carry three common properties. `created_at` is the ISO 8601 UTC timestamp at which the row was inserted, rendered with exactly three fractional-second digits and a trailing `Z`. `updated_at` follows the same format and is refreshed on every mutation of the row, including mutations caused by a cascade rather than by a direct request against that row. Both `created_at` and `updated_at` are stamped from the service's real wall-clock time rather than from the logical clock described below, so neither field is derived from the logical instant in force. `version` is an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of the row, again including cascade-driven mutations; it is the value the optimistic-concurrency machinery of §2.8 compares against. `RecipeComponent` is the single exception: a component row carries only `id` and `created_at`. It has no `updated_at` and no `version`, and neither field appears in its representation. Beyond that one exception, a resource representation always carries every property this document names for its type, on reads and on write responses alike: a property that has no value yet is rendered as JSON `null` rather than omitted, list-valued properties that are empty are rendered as empty arrays, and no property is ever conditionally absent from a representation.

Timestamps that record when a business event happened — `approved_at`, `certified_at`, `published_at`, `opened_at`, `closed_at`, `effective_from`, `effective_to`, `reprint_deadline` — are read from the service's **logical clock**, not from wall-clock time. The logical clock starts at `2026-08-01T00:00:00Z` when the process starts and only moves when a `PlatformAdmin` sets it, supplying the new instant as `to_iso8601`. Every instant-valued field a client supplies — `to_iso8601` and the board display window included — is accepted in the shape `YYYY-MM-DDTHH:MM:SS`, optionally followed by a fractional-second part of any number of digits, with either `T` or a single space as the date-time separator, and carrying either a trailing `Z`, an explicit `+HH:MM` or `-HH:MM` offset (also accepted without the colon) that is normalised to UTC before it is stored, or no zone designator at all, in which case the value is read as already being UTC; a value in any other shape — a bare `YYYY-MM-DD` date with no time part included — is rejected with `ERR_VALIDATION`. Stored instants are always rendered back in UTC with exactly three fractional digits and a trailing `Z`, whatever offset they arrived in. Advancing the clock is not a passive act: it sweeps the estate for deadlines that the new instant has crossed, and the response reports how much work the sweep did as `current_utc`, `boards_marked_overdue` and `variances_expired`. Fields that hold a calendar date rather than an instant — `first_offered_on`, `start_date`, `end_date`, `requested_start_date`, `requested_end_date`, `effective_start_date`, `effective_end_date` — are plain `YYYY-MM-DD` strings, and comparisons against the clock for those fields use the clock's calendar date in UTC.

### 2.5. The Operation Vocabulary and Left-to-Right Path Resolution

Section 3 describes business behaviour without quoting URLs; section 4 supplies the HTTP contract. The two are joined by a fixed vocabulary of operation names used consistently throughout this document: *brand registration*, *authority registration*, *unit registration*, *unit batch registration*, *unit status change*, *coverage determination*, *menu-item creation*, *offer-window append*, *exemption review*, *recipe-version creation*, *component addition*, *analysis submission*, *analysis decision*, *certification withdrawal*, *packet drafting*, *packet publication*, *board creation*, *listing creation*, *board publication*, *board reprint*, *variance filing*, *variance decision*, *citation opening*, *brand response*, *regulator action* and *clock set*. Each name corresponds to exactly one row of the endpoint table in section 4.

Path identifiers are resolved strictly left to right. Every templated segment must name an existing row, and the not-found error reported is the one belonging to the resource type of the *leftmost* unresolved segment: `ERR_BRAND_NOT_FOUND`, `ERR_JURISDICTION_NOT_FOUND`, `ERR_ESTABLISHMENT_NOT_FOUND`, `ERR_MENU_ITEM_NOT_FOUND`, `ERR_RECIPE_NOT_FOUND`, `ERR_NUTRITION_ANALYSIS_NOT_FOUND`, `ERR_MENU_BOARD_NOT_FOUND`, `ERR_DISCLOSURE_PACKET_NOT_FOUND`, `ERR_VARIANCE_REQUEST_NOT_FOUND` or `ERR_ENFORCEMENT_ACTION_NOT_FOUND`, each with HTTP 404. Foreign keys carried in a request body are resolved only after the path has fully resolved, and they report the not-found error of the entity they reference. Consequently a request that names a non-existent path resource *and* a non-existent body foreign key reports the path resource's error, never the body's.

Filters on list endpoints are exact-match equality filters on the named field, and several lists accept more than one, in which case all supplied filters must hold. The establishment list filters on `brand_id`, `jurisdiction_id` and `unit_status`; the menu-item list on `brand_id`, `item_class` and `labeling_status`; the recipe list on `menu_item_id`, `supersedes_recipe_id` and `status`; the component list on `role` and `choice_group`; the board list on `establishment_id`, `board_type`, `publication_status` and `calorie_compliance_status`; the listing lists on `listing_status`; the packet, analysis and enforcement lists on `status`; the brand's variance list on `status` and `requirement_code`; and an authority's variance list on `status` and `brand_id`. A filter is only ever compared for equality against the stored value, so a filter value that is not a member of the filtered field's enum domain — or is an empty string, or is otherwise malformed — is never itself an error: it simply matches no row, and the endpoint answers 200 with an empty `data` array and a `total_count` of 0. Filters are likewise applied after the list's own scoping and before the page window, so `total_count` counts the filtered population rather than the whole collection.

### 2.6. The Order in Which a Request Is Refused

Many operations in this system are guarded by several conditions at once, and a compliance team debugging a rejection needs to know *which* condition fired. The service therefore evaluates its checks in one fixed, strictly ordered ladder. The first condition that fails ends the request immediately with that condition's error; no later condition is consulted, and no partial write is retained. The ladder is universal — a check simply does not apply to operations outside its scope — and it runs in exactly this order:

1. `X-User-ID` present and non-empty, else `ERR_MISSING_AUTH`. Applies to every endpoint.
2. `X-User-Role` present and equal to one of the five role names, else `ERR_INVALID_ROLE`. Applies to every endpoint. Because this rung precedes endpoint authorization, an unknown role never produces `ERR_UNAUTHORIZED`.
3. The role is authorized for the requested operation, else `ERR_UNAUTHORIZED`. Applies to every endpoint.
4. For the entity-backed roles, `X-User-ID` equals the `id` of the entity the write targets — the `Brand` for a `BrandComplianceOfficer`, the `Establishment` for a `MenuboardPublisher`, the `Jurisdiction` for a `StateRegulator` — else `ERR_FORBIDDEN_SCOPE`. Applies to every write; reads are never ownership-scoped. The value the rung compares the caller's `X-User-ID` against comes in three shapes, and the shape decides when the rung is able to fire at all. First, it may be a field of the row the path identifier names, or of a row reached by dereferencing onwards from it; because that row must be in hand before the comparison is possible, the rung is skipped outright when any link in that walk resolves to nothing, and the request is refused instead as a malformed body when it is one and otherwise with the relevant not-found error, never with `ERR_FORBIDDEN_SCOPE`. Second, it may be a foreign key carried in the request body, in which case this rung reads that key straight out of the raw body ahead of validation; if the key is missing, null, blank or not a string at all, there is nothing to compare and the rung is skipped rather than failed, so the request proceeds to rung 5 and is refused there as a malformed body. Third — and this shape is easy to miss — it may be a field of the row that a request-body foreign key *refers to* rather than the key's own value: citation opening compares the acting `StateRegulator` against the cited unit's own stored `jurisdiction_id`, a value the payload never carries. That shape needs the referent row, so the rung is skipped whenever the body key names no existing row, and the request is refused later at rung 8 with that entity's not-found error rather than with `ERR_FORBIDDEN_SCOPE`, however unrelated the acting authority. `PlatformAdmin` and `NutritionAnalyst` never fail this rung, since neither role's `X-User-ID` names a persisted row.
5. The request body is well-formed: every required field present, every field of its declared type, every enum-valued field carrying a value inside its declared domain, every integer non-negative where declared so, every decimal within its stated precision, and every date well-formed. Otherwise `ERR_VALIDATION`. Applies to every write. Four conventions make this rung precise. First, a body that is absent or empty is read as an empty JSON object, so a write sent with no body at all fails this rung on its first missing required field; a body that is present but is not a JSON object — an array, a bare string or number, or text that does not parse as JSON — is itself `ERR_VALIDATION`, and the request's declared `Content-Type` is never consulted either way. Second, a field supplied as JSON `null` counts as absent rather than as a value: a required field sent as `null` is refused as missing, and an optional field sent as `null` falls back to its documented default instead of storing a null the caller asked for. Third, fields the operation does not name are ignored rather than refused, so an unrecognised key never by itself fails a request. Fourth, declared types are checked strictly with no coercion in either direction — an integer-valued field accepts only a JSON integer and refuses both a boolean and a real number such as `5.0`; a decimal-valued field accepts a JSON integer or a JSON real but never a numeric string such as `"12.50"`; a boolean-valued field accepts only `true` or `false` and never the strings `"true"` and `"false"` nor `0` and `1`; and enum-, date-, instant- and identifier-valued fields accept only strings, so a foreign key sent as a number fails here rather than at rung 8. String values are neither trimmed nor otherwise rewritten before they are stored, and a declared character-length range counts the characters exactly as supplied; a value that is non-empty but consists only of whitespace satisfies the length range and is then refused by the non-blank rule. Because this rung precedes existence lookup, a malformed body sent against a path identifier that does not exist yields `ERR_VALIDATION` rather than a not-found error.
6. `limit` inside 1 through 100 and `offset` at least 0 when supplied, else `ERR_INVALID_PAGINATION`. Applies to every list endpoint.
7. Every templated path identifier resolves to an existing row, else that resource type's not-found error.
8. Every foreign key supplied in the request body resolves to an existing row, else the referenced entity's not-found error. Applies to unit registration, unit batch registration, menu-item creation, board creation, listing creation, variance filing and citation opening.
9. The supplied optimistic-concurrency field equals the parent row's current `version`, else the stale-version error of §2.8. Because this rung sits after existence and before every state precondition, a stale version against an already-terminal parent reports the stale-version error, not a state error.
10. The row the request would move is not already in a terminal state for the state field being moved, else `ERR_ALREADY_TERMINAL`. Applies to every transition operation. `SUPERSEDED` recipes, `SUPERSEDED` packets, `WITHDRAWN` boards, `REMOVED` listings, `DENIED` and `EXPIRED` variance requests, `CLOSED_COMPLIANT` and `CLOSED_PENALTY` enforcement files, and `PERMANENTLY_CLOSED` units accept no further transitions. For a recipe, which terminal statuses this rung consults depends on the operation. Analysis submission consults `SUPERSEDED`, `REJECTED` and `WITHDRAWN` alike and refuses all three here with `ERR_ALREADY_TERMINAL`, never reaching rung 12. Certification withdrawal consults only `SUPERSEDED` here; a `REJECTED` or `WITHDRAWN` recipe is instead refused at rung 14 with `ERR_RECIPE_NOT_APPROVED`, as is any other non-`APPROVED` status. Component addition is not a transition operation and so is not guarded by this rung at all: it is refused at rung 12 with `ERR_RECIPE_NOT_DRAFT` for every status other than `DRAFT`, the terminal ones included.
11. The board's `publication_status` is `DRAFT`, else `ERR_BOARD_NOT_DRAFT`. Applies to listing creation and board publication. Re-publishing an already `PUBLISHED` board therefore fails here, before any display-window arithmetic is attempted.
12. The recipe's `status` is `DRAFT`, else `ERR_RECIPE_NOT_DRAFT`. Applies to component addition and analysis submission.
13. The nutrition analysis `status` is `SUBMITTED`, else `ERR_ANALYSIS_ALREADY_DECIDED`. Applies to the analysis decision.
14. The recipe's `status` is `APPROVED`, else `ERR_RECIPE_NOT_APPROVED`. Applies to certification withdrawal.
15. The enforcement file is in a state from which the requested regulator action or brand response is defined, and a compliant closure additionally requires the recorded `last_response_type` to be either `REPRINT_COMPLETED` or `VARIANCE_CITED`. Otherwise `ERR_ACTION_STATE_INVALID`. Applies to brand responses and regulator actions.
16. The variance request is in the state the requested decision expects, else `ERR_VARIANCE_STATE_INVALID`. Applies to the variance decision.
17. The packet's `status` is `DRAFT`, else `ERR_PACKET_NOT_DRAFT`. Applies to packet publication.
18. On a certification decision the acting analyst's `X-User-ID` differs from the analysis's `submitted_by_user_id`, else `ERR_SAME_USER_CERTIFICATION`. Applies to the analysis decision.
19. The owning brand's `compliance_posture` is not `FROZEN`, else `ERR_BRAND_POSTURE_FROZEN`. Applies to five operations: menu-item creation, recipe-version creation, board creation, listing creation and board publication.
20. The owning brand's `coverage_status` is `COVERED`, else `ERR_BRAND_NOT_COVERED`. Applies to packet drafting and board publication.
21. The listed item's `brand_id` equals the `brand_id` of the board's establishment, else `ERR_ITEM_BRAND_MISMATCH`. Applies to listing creation.
22. The board-and-item pair is not already carried by a listing whose `listing_status` is `LISTED` or `STALE`, else `ERR_DUPLICATE_LISTING`. Applies to listing creation.
23. The component's choice-group metadata is internally consistent, else `ERR_CHOICE_GROUP_INCONSISTENT`. Applies to component addition.
24. The recipe holds at least one component whose `role` is `BASE`, else `ERR_RECIPE_HAS_NO_BASE_COMPONENT`. Applies to analysis submission.
25. The brand holds a disclosure packet whose `status` is `PUBLISHED`, else `ERR_NO_PUBLISHED_PACKET`. Applies to board publication and brand responses.
26. The packet's `allergen_matrix_complete` is true, else `ERR_ALLERGEN_MATRIX_INCOMPLETE`. Applies to packet publication and board publication, and *which* value this rung reads differs between the two. On board publication it is the stored flag of the brand's `PUBLISHED` packet, believed exactly as that packet is carrying it and never re-derived. On packet publication it is the flag that publication's own re-synthesis has just written: as §3.5 sets out, clearing the status gate of rung 17 re-runs the whole matrix synthesis and overwrites all four synthesised fields immediately before this rung is tried, so the value compared here is the freshly derived one and not the one drafting stored.
27. `cross_contact_statement` is non-empty whenever the packet's `cross_contact_statement_required` is true, else `ERR_CROSS_CONTACT_STATEMENT_REQUIRED`. Applies to packet publication, and — like rung 26 above it — the flag consulted is the one publication's re-synthesis has just written rather than the one drafting stored.
28. The board's `succinct_statement_variant` matches what its jurisdiction requires, or a granted variance covers it, else `ERR_SUCCINCT_STATEMENT_MISMATCH`. Applies to board publication, and is checked before any per-listing declaration check.
29. Every listing that needs the sodium warning icon carries it, else `ERR_SODIUM_WARNING_ICON_REQUIRED`. Applies to board publication.
30. The board carries at least one line — `listing_count` of at least 1 — **and** every listed item either carries a certified calorie declaration or is exempt, else `ERR_ITEM_CALORIES_UNDECLARED`. Applies to board publication. Both limbs raise that same one error and the empty-board limb is tried first, so taking a board live with no lines printed on it at all is refused here rather than by any error of its own.
31. On every supplied date or instant pair the start is not after the end, else `ERR_INVALID_DATE_RANGE`. Applies to offer-window append, variance filing, the variance decision, and board publication when an end instant is supplied. A single range's own ordering is checked before it is compared against any other row's range.
32. The requested display window does not overlap the window of another published board of the same establishment and board type, else `ERR_BOARD_WINDOW_CONFLICT`. Applies to board publication.
33. The target authority's `preemption_mode` is `VARIANCE_ALLOWED`, else `ERR_VARIANCE_NOT_ALLOWED`. Applies to the variance decision.
34. The granted window clears the cooling buffer against every other granted variance for the same brand, authority and requirement, else `ERR_VARIANCE_WINDOW_CONFLICT`. Applies to the variance decision.
35. The enforcement file's `info_round_count` is at least 1, else `ERR_INFO_ROUND_REQUIRED`. Applies to an escalating regulator action.
36. No granted variance shields the citation on the current logical date, else `ERR_CITATION_SHIELDED_BY_VARIANCE`. Applies to an escalating regulator action.
37. The cited unit's `outstanding_penalty_cents` is 0, else `ERR_OUTSTANDING_PENALTY` (HTTP 402). Applies to a brand response whose `response_type` is `REPRINT_COMPLETED`.
38. The board's `publication_status` is `PUBLISHED` **and** its `stale_listing_count` is at least 1, else `ERR_NO_STALE_LISTINGS`. Applies to board reprint. The two limbs are one condition raising one error, so a reprint filed against a board still in `DRAFT` — whatever its stale count — is refused here with `ERR_NO_STALE_LISTINGS` and never at rung 11 with `ERR_BOARD_NOT_DRAFT`, which does not apply to this operation at all.
39. The item's `item_class` is `TEMPORARY` or `TEST_MARKET`, else `ERR_ITEM_NOT_TEMPORARY`. Applies to offer-window append and exemption review.
40. When the requested `new_unit_status` is `PERMANENTLY_CLOSED`, no enforcement file of that unit is in `OPEN`, `RESPONSE_SUBMITTED`, `INFO_REQUESTED`, `ESCALATED` or `PENALTY_ASSESSED`, else `ERR_UNIT_HAS_OPEN_ENFORCEMENT`. Applies to the unit status change, and only for the `PERMANENTLY_CLOSED` target — moves to `OPERATING` and `TEMPORARILY_CLOSED` are not gated by it.

The consequence worth internalising is that a compliance-posture freeze (rung 19) outranks coverage (rung 20), which outranks every referential and per-listing check on board publication, which in turn outrank the temporal window checks (rungs 31 and 32). A frozen brand attempting to publish a board with an overlapping window and a wrong succinct statement is told only that it is frozen.

### 2.7. Declaration Arithmetic, Rounding Ladders and Money Precision

Three separate rounding disciplines coexist in this system and must not be conflated.

**Component-level arithmetic** works to two decimal places, rounding half up. A component's calorie contribution, `component_calories`, is its `calories_per_100g` multiplied by its `grams` and divided by 100, with the result rounded half up to two decimal places. Its sodium contribution, `component_sodium_mg`, is its `sodium_mg_per_100g` multiplied by its `grams` and divided by 100, likewise rounded half up to two decimal places. Sums of component contributions are also held at two decimal places, rounded half up.

**Declaration rounding** turns a two-decimal nutrient total into the integer figure that is actually printed. Calories and sodium use *different* ladders, and each ladder is applied exactly once, to a total that has already been summed at full component precision. The calorie ladder reads: a total strictly below 5 calories declares as 0; a total from 5 up to and including 50 calories declares as the total divided by 5, rounded half up to a whole number, then multiplied by 5; a total above 50 calories declares as the total divided by 10, rounded half up to a whole number, then multiplied by 10. The sodium ladder has the same three-step shape with different breakpoints: a total strictly below 5 milligrams declares as 0; a total from 5 up to and including 140 milligrams declares as the total divided by 5, rounded half up, then multiplied by 5; a total above 140 milligrams declares as the total divided by 10, rounded half up, then multiplied by 10. Declaration rounding always produces an integer.

The order of operations is mandatory and is the single most commonly botched part of this specification: **sum first at two-decimal precision, then apply the declaration ladder once to the total.** Rounding each component to its declared figure and then adding the declared figures produces a different and wrong answer. Two components of 2.60 calories each sum to 5.20 and declare as 5; declaring each component first would give 0 plus 0, which is 0.

**Money** is held exclusively in whole cents, as integers, with every intermediate product rounded half up to a whole cent. There are no fractional cents anywhere in the system, and no monetary value is ever expressed in dollars.

Every numeric field of every representation — the integer money and count fields, the integer declaration figures, and the two-decimal component and recipe figures alike — is serialised as a JSON number and never as a string. A two-decimal figure whose value happens to be integral is rendered with no fractional part at all and a trailing zero is not preserved, so a contribution of 13.00 appears as `13` and one of 12.50 appears as `12.5`.

**Counts and days** are plain integers with no rounding. Calendar-day arithmetic treats offer windows and variance windows as closed intervals inclusive of both endpoints, while board display windows are half-open intervals that include their start instant and exclude their end instant — a deliberate asymmetry described in §3.6 and §3.8.

### 2.8. Optimistic Concurrency on Parent Rows

Two operations in this system create a child row whose meaning depends on the parent's state at the moment of creation, and both are guarded by optimistic concurrency control on the parent's `version`. In each case the guarding field is a **required, non-optional** member of the request body.

Recipe-version creation against a menu item requires `expected_menu_item_version`, carrying the `version` of the `MenuItem` that the client last observed. If it does not equal the item's current `version`, the request is rejected with `ERR_STALE_MENU_ITEM_VERSION` and HTTP 412. The rule exists because a new recipe version legitimately supersedes the item's prior certified declaration once it is certified; a writer holding a stale view of the item would otherwise branch the version chain from an outdated baseline.

Packet drafting against a brand requires `expected_brand_version`, carrying the `version` of the `Brand` that the client last observed. If it does not equal the brand's current `version`, the request is rejected with `ERR_STALE_BRAND_VERSION` and HTTP 412. Publishing a packet legitimately supersedes the brand's prior published packet, so a writer whose view of the brand predates the latest allergen-affecting mutation would publish a matrix synthesised from an outdated item set.

Neither field carries a range constraint, and that is deliberate. Both are validated at rung 5 as plain JSON integers and nothing more — strictly typed, so a boolean, a real such as `3.0` and the string `"3"` are each refused there as they are anywhere else — but 0 and negative integers are perfectly well-formed integers and clear that rung untouched. Since every row is born at `version` 1 and only ever increments, no such value can ever match a live row, so `expected_menu_item_version` sent as 0 or as -1 is refused at rung 9 with `ERR_STALE_MENU_ITEM_VERSION` and HTTP 412, and `expected_brand_version` sent as 0 or as -1 with `ERR_STALE_BRAND_VERSION` and HTTP 412 — never with `ERR_VALIDATION`. The one thing that outranks the refusal is existence: because rung 7 precedes rung 9, a nonsensical version supplied against a path identifier that names no row still reports that resource's not-found error rather than the stale-version error.

No other operation in this specification takes a version field, and no other operation may reject on version grounds. Note the interaction with §2.4: because `version` increments on cascade-driven mutations as well as direct ones, a client that read a brand, then certified a recipe that rewrote that brand's counters, holds a stale `expected_brand_version` even though it never wrote to the brand itself.

### 2.9. The Brand Compliance Posture Ladder

`compliance_posture` on a `Brand` is a **derived** value. It is never supplied in a request body and never set directly. It is recomputed at the end of every mutation that changes the brand's `coverage_status`, `open_reprint_obligation_count`, `overdue_board_count` or `open_enforcement_escalated_count`, by evaluating four rungs top to bottom and taking the first that matches:

- `FROZEN` — when `coverage_status` is `COVERED` and either `overdue_board_count` is at least 1 or `open_enforcement_escalated_count` is at least 1.
- `RESTRICTED` — when `coverage_status` is `COVERED` and `open_reprint_obligation_count` is at least 1.
- `COMPLIANT` — when `coverage_status` is `COVERED`.
- `EXEMPT` — when `coverage_status` is `NOT_COVERED`.

A newly registered brand is `NOT_COVERED` and therefore `EXEMPT`. Whenever the ladder's outcome changes the stored value, the brand's `updated_at` is refreshed and its `version` increments by 1. The transitions that this ladder produces are, in full: `EXEMPT` to `COMPLIANT` when coverage becomes `COVERED` with all three counters at zero; `COMPLIANT` to `EXEMPT` when coverage falls back to `NOT_COVERED`; `COMPLIANT` to `RESTRICTED` when a published board of the brand acquires a reprint obligation while no board is overdue and no case is escalated; `RESTRICTED` to `COMPLIANT` when the last outstanding reprint obligation clears — whether by a reprint being filed, a board being withdrawn, or a certification being withdrawn — with no overdue board and no escalated case remaining; `RESTRICTED` to `FROZEN` when a board with a reprint obligation passes its `reprint_deadline` during a clock set, or when an enforcement file against one of the brand's units is escalated; `COMPLIANT` to `FROZEN` directly, when an enforcement file is escalated while the brand carried no reprint obligation; `FROZEN` to `RESTRICTED` when nothing is overdue and nothing is escalated but at least one reprint obligation remains; and `FROZEN` to `COMPLIANT` when every overdue board has been reprinted, no case remains escalated, and no reprint obligation remains. There is no terminal posture — a brand can cycle through all four indefinitely.

The posture is not decoration. `FROZEN` is the gate named in rung 19 of §2.6: a brand that has let a board go overdue, or that is carrying an escalated citation, cannot add a menu item, open a new recipe version, create a board, add a line to a board, or take a board live. What deliberately stays open is the recovery path — filing a reprint and responding to a citation are never blocked by the freeze, because blocking them would trap the brand permanently.

### 2.10. Conserved Counters and Cascade Discipline

A handful of integer fields are **conserved quantities**: the system guarantees that each equals, at all times, a count or sum over the rows it summarises, and every operation that could change that population must adjust the counter in the same request.

- `Brand.counted_unit_count` equals the number of the brand's units that count under the coverage basis in force; `Brand.standard_item_count` equals the number of the brand's menu items whose `labeling_exempt` is false.
- `Brand.open_reprint_obligation_count` equals the number of the brand's boards whose `publication_status` is `PUBLISHED` and whose `calorie_compliance_status` is either `REPRINT_REQUIRED` or `OVERDUE`. `Brand.overdue_board_count` equals the number of the brand's boards whose `publication_status` is `PUBLISHED` and whose `calorie_compliance_status` is `OVERDUE` — it carries the same `PUBLISHED` restriction as the reprint counter above it, so a board that is withdrawn while overdue leaves both counters even though it keeps its own `OVERDUE` marking.
- `Brand.open_enforcement_escalated_count` equals the number of enforcement files against the brand's units whose `status` is `ESCALATED`. `Brand.has_published_disclosure_packet` is true exactly when at least one of the brand's packets has `status` `PUBLISHED`.
- A unit's `board_count` equals the number of the unit's boards whose `publication_status` is not `WITHDRAWN`; `Establishment.outstanding_penalty_cents` equals the sum of `penalty_total_cents` over the unit's enforcement files whose `status` is `PENALTY_ASSESSED` or `CLOSED_PENALTY`.
- `Jurisdiction.assessed_penalty_cents_total` equals the sum of `penalty_total_cents` over that authority's enforcement files whose `status` is `PENALTY_ASSESSED` or `CLOSED_PENALTY`.
- `MenuBoard.listing_count` equals the number of the board's lines whose `listing_status` is not `REMOVED`; `MenuBoard.stale_listing_count` equals the number whose `listing_status` is `STALE`. `Recipe.component_count` equals the number of components attached to the recipe version.
- `DisclosurePacket.covered_item_count` is a *snapshot*, not a live count. It is written when the matrix is synthesised, and the matrix is synthesised at exactly two moments: when the packet is drafted, and again when the packet is published, where the re-synthesis described in §3.5 overwrites `covered_item_count` together with `allergen_rows`, `allergen_matrix_complete` and `cross_contact_statement_required`. It is not re-derived at any other moment: it does not track the creation of a menu item, the certification of a recipe or an exemption review, so a stored `covered_item_count` may legitimately lag the brand's current rows in between — and a `PUBLISHED` or `SUPERSEDED` packet's figure stays frozen at whatever its publication computed, for good.

Several operations propagate through more than one entity in a single request. Where that happens, this document names the hops explicitly and in order, and every hop lands atomically: either all of them are applied or the request is rejected and none are. Every row a hop touches has its `updated_at` refreshed and its `version` incremented by 1, exactly as if it had been written directly. That bookkeeping is settled once, at the very end of the request, and it is counted per row rather than per hop: a row that several hops of one request touch is stamped and incremented exactly once, not once per hop, and every row bumped by a single request shares one identical `updated_at` value. A hop that leaves every stored field of a row exactly as it found it is not a mutation and bumps nothing — which is why an exemption review that flips no flag changes nothing — whereas an increment this document states outright for a named operation is unconditional and lands even when the operation leaves every other field of that row untouched. **The coverage determination is the one carve-out from the no-op rule worth naming here.** Every run of it, whether the explicit determination of §3.1 or the automatic `OPERATING_ONLY` re-determination that fires after unit registration, bulk unit registration, a unit status change, menu-item creation and an exemption review's flip, overwrites all four of the brand's stored coverage fields — `counted_unit_count`, `standard_item_count`, `coverage_status` and `coverage_reason` — and refreshes the brand's `updated_at` and increments its `version` **unconditionally**, even when all four recomputed values are identical to the ones already stored. A unit registration that leaves the brand well short of the threshold, the creation of an exempt menu item, a unit status change that re-asserts the status the unit already held, and the same explicit determination re-run twice on the same basis therefore each bump the brand exactly once even though coverage did not move an inch. That force belongs to the coverage determination alone: `compliance_posture`, every conserved counter listed above and every snapshot field follow the ordinary no-op rule and bump the row only where the stored value genuinely changes. A row the request itself created is born at `version` 1 with `updated_at` equal to `created_at` and is never additionally bumped by the same request's later hops. The response body of the request that caused the bumps already carries the post-bump `version` and `updated_at` of every row it echoes, so a client never has to re-read a row to learn the version its own write produced. Two of these cascades have exact inverses — certification withdrawal reverses certification, and penalty rescission reverses assessment — and in both cases the reversal restores the affected counters to precisely their pre-cascade values, not to a recomputed approximation of them.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Register: Brands, Authorities and the Unit Estate

A `PlatformAdmin` seeds the register. Brand registration records the chain's `legal_name` — between 1 and 120 characters and not blank — and, optionally, its `doing_business_as`, the public-facing chain name that carries the same-name limb of covered-establishment determination and is likewise between 1 and 120 non-blank characters; when `doing_business_as` is omitted or sent as `null`, the brand's stored and serialised `doing_business_as` is a verbatim copy of the supplied `legal_name` rather than null, so the public-facing name is never empty on a brand representation. A freshly registered brand is deliberately inert: `coverage_status` is seeded to `NOT_COVERED` with `coverage_reason` `NO_STANDARD_MENU_ITEMS`, `counted_unit_count` and `standard_item_count` are 0, `open_reprint_obligation_count`, `overdue_board_count` and `open_enforcement_escalated_count` are 0, `has_published_disclosure_packet` is false, and the posture ladder of §2.9 therefore lands on `EXEMPT`.

Authority registration describes one state or local labeling regime. The authority's `code` is its identifier in enforcement correspondence: 2 to 12 characters drawn only from uppercase letters, digits and the hyphen, and unique across all authorities — a `code` already registered by another authority is refused with `ERR_VALIDATION`. Its `name` is a human-readable label of 1 to 120 non-blank characters. `preemption_mode` decides whether the authority may grant labeling relief at all and is either `PREEMPTED` or `VARIANCE_ALLOWED`. `extra_requirement` names the state or local rule layered on top of the federal one and is `NONE`, `SODIUM_WARNING` or `ADDED_SUGAR_ICON`, defaulting to `NONE`. `enforcement_tier` selects the penalty multiplier tier and is `FEDERAL_ALIGNED` or `ENHANCED`, defaulting to `FEDERAL_ALIGNED`. `sodium_warning_threshold_mg` is the declared-sodium level at or above which a printed line must carry the sodium warning icon; it accepts any integer from 0 through 10000 and defaults to 2300. `required_succinct_statement_variant` fixes the succinct-statement wording that boards in this authority must carry and is `FEDERAL_DEFAULT` or `STATE_EXTENDED`, defaulting to `FEDERAL_DEFAULT`. Two figures are derived rather than supplied: `assessed_penalty_cents_total` starts at 0, and `reprint_grace_days` is 30 when `extra_requirement` is `NONE` and 14 for every other value — so an authority that layers a sodium warning or an added-sugar icon onto the federal rule also grants a shorter reprint window, and boards of one brand sitting in two authorities receive different deadlines from a single recipe certification.

Units are registered either one at a time or in bulk, and either a `PlatformAdmin` or the brand's own `BrandComplianceOfficer` may do it. A single unit registration carries the `brand_id` of the owning chain, the `jurisdiction_id` of the authority whose labeling rules bind it, a `unit_label` of 1 to 40 non-blank characters that must be unique within the brand, an optional `unit_status`, and an optional `operates_under_brand_name`. A `unit_label` already held by another unit of the same brand is refused with `ERR_VALIDATION`, and that comparison is made before either supplied foreign key is resolved, so a registration that duplicates a label *and* names a non-existent `jurisdiction_id` reports `ERR_VALIDATION` rather than `ERR_JURISDICTION_NOT_FOUND`. `unit_status` defaults to `PLANNED` when omitted but may be supplied as `OPERATING` outright, so an estate that is already trading can be entered without a second call per store; any one of the four status values is in fact accepted at registration, `TEMPORARILY_CLOSED` and even `PERMANENTLY_CLOSED` included, and a unit registered straight into `PERMANENTLY_CLOSED` is born terminal and accepts no status change afterwards. `operates_under_brand_name` defaults to true and records whether the unit actually does business under the brand's `doing_business_as`; a unit for which it is false never counts toward the federal unit threshold under any counting basis. Registering a single unit re-runs the coverage determination on the `OPERATING_ONLY` basis and increments the brand's `version` once.

Bulk registration exists because a covered estate is twenty units deep and nobody wants twenty round trips. It is addressed at a brand and takes the `jurisdiction_id` all the created units share, a `unit_count` of how many to create — a required integer of at least 1, with no upper bound imposed on it — an optional `unit_status` and `operates_under_brand_name` applied uniformly to all of them and each defaulting exactly as it does in a single registration, and an optional `unit_label_prefix` of 1 to 40 non-blank characters. The created units are inserted in `created_at` ascending order and labelled with the prefix, a hyphen, and a four-digit zero-padded sequence number beginning at `0001`; when `unit_label_prefix` is omitted the literal prefix `UNIT` is used. The labels a batch generates carry the same brand-wide uniqueness obligation as a single registration's `unit_label`: when any generated label matches the `unit_label` of a unit the brand already holds, the batch is refused with `ERR_VALIDATION` and none of its units are created. Unlike a single registration's label check, the batch's runs only after both the path `brand_id` and the body `jurisdiction_id` have resolved, so a batch that names a non-existent authority reports `ERR_JURISDICTION_NOT_FOUND` even when its generated labels would also have collided. The response summarises the batch rather than echoing every row: `brand_id`, `created_count`, the `unit_status` the batch was created in, `first_created_establishment_id`, and the brand's resulting `brand_coverage_status` and `brand_counted_unit_count`. Coverage is re-determined exactly once after the whole batch lands, and the brand's `version` increments exactly once — not once per unit.

Once registered, a unit moves through `PLANNED`, `OPERATING`, `TEMPORARILY_CLOSED` and `PERMANENTLY_CLOSED` by a unit status change, which carries the target `new_unit_status` and an optional `effective_note` of 1 to 400 non-blank characters that is validated and then discarded — no field of the unit records it, and it is absent from the unit's representation. The defined moves are `PLANNED` to `OPERATING`, `OPERATING` to `TEMPORARILY_CLOSED`, `TEMPORARILY_CLOSED` back to `OPERATING` — a genuine reopening cycle — and `OPERATING` or `TEMPORARILY_CLOSED` to `PERMANENTLY_CLOSED`. Those are the moves the workflow expects rather than a validated whitelist: `new_unit_status` is accepted for any one of the four status values, so a change that repeats the unit's current status, or that runs the sequence backwards from `OPERATING` to `PLANNED`, is carried out rather than refused, and `PERMANENTLY_CLOSED` may be reached from `PLANNED` just as it is from `OPERATING`, closure cascade and open-enforcement gate included. `PERMANENTLY_CLOSED` is terminal; a request that would move a unit already in it fails on the terminal-lockdown rung. When a `BrandComplianceOfficer` drives the change, its `X-User-ID` must equal the unit's `brand_id`. Because that comparison needs the unit's own stored `brand_id`, it is skipped outright when the path identifier names no existing unit: such a request is refused as a malformed body when it is one and otherwise with `ERR_ESTABLISHMENT_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`. Each of the first three moves recomputes `Brand.counted_unit_count`, re-runs the coverage determination on the `OPERATING_ONLY` basis, and recomputes `compliance_posture` — and that automatic re-determination overwrites all four stored coverage fields and increments the brand's `version` unconditionally, even when every recomputed value is identical to the one already stored, so a change that leaves coverage exactly where it was still bumps the brand; a temporary closure explicitly leaves the unit's boards alone, because closing a store for a refit does not withdraw its menu boards.

Permanent closure is a different animal, and it is gated. If any enforcement file of the unit is in `OPEN`, `RESPONSE_SUBMITTED`, `INFO_REQUESTED`, `ESCALATED` or `PENALTY_ASSESSED`, the request is refused with `ERR_UNIT_HAS_OPEN_ENFORCEMENT`: a unit may not be closed out of the register while a live citation is pending, and the enforcement file must first reach `CLOSED_COMPLIANT` or `CLOSED_PENALTY`. When it is allowed, four hops run in order. **Hop 1:** every board of the unit whose `publication_status` is `DRAFT` or `PUBLISHED` moves to `WITHDRAWN`, processed in `created_at` ascending order. **Hop 2**, caused by hop 1: each withdrawn board sets its lines whose `listing_status` is `LISTED` or `STALE` to `REMOVED`, and where the board left `PUBLISHED` with `calorie_compliance_status` of `REPRINT_REQUIRED` or `OVERDUE`, `Brand.open_reprint_obligation_count` drops by 1 for that board, together with `Brand.overdue_board_count` when the board was `OVERDUE`. **Hop 3**, caused by hop 2: every menu item that no longer has any `STALE` line anywhere returns from `labeling_status` `RELABEL_REQUIRED` to `DECLARED`. **Hop 4**, caused by hops 1 through 3: `Brand.counted_unit_count` is recomputed, the coverage determination re-runs on the `OPERATING_ONLY` basis, and `compliance_posture` is recomputed. `Establishment.board_count` ends at 0.

Coverage determination itself answers one question — is this brand a covered establishment — and it can be run explicitly by a `PlatformAdmin` or a `BrandComplianceOfficer` under a stated `basis`, or it runs automatically. **Automatic re-determination always uses the `OPERATING_ONLY` basis**, and it fires after unit registration, after bulk unit registration, after a unit status change, after menu-item creation, and after an exemption review that actually flips the item's `labeling_exempt` — a review that leaves that flag exactly where it stood re-determines nothing and bumps nothing, as §3.2 sets out. Where it does fire it is unconditional in the sense §2.10 gives that word: it rewrites all four stored coverage fields and bumps the brand even when every recomputed value is the one already there. Whichever basis is in force, the determination first counts units, then counts items, then decides. Under the `OPERATING_ONLY` basis, `counted_unit_count` is the number of the brand's units whose `unit_status` is `OPERATING` and whose `operates_under_brand_name` is true. Under the `REGISTERED_ALL` basis, `counted_unit_count` is the number of the brand's units whose `unit_status` is either `OPERATING` or `TEMPORARILY_CLOSED` and whose `operates_under_brand_name` is true. Units in `PLANNED` or `PERMANENTLY_CLOSED`, and units whose `operates_under_brand_name` is false, are excluded under both bases. `standard_item_count` is, under both bases, the number of the brand's menu items whose `labeling_exempt` is false.

The decision then reads as follows, in this order. If `standard_item_count` is 0, `coverage_status` is `NOT_COVERED` and `coverage_reason` is `NO_STANDARD_MENU_ITEMS`. Otherwise, if `counted_unit_count` is at least twenty, `coverage_status` is `COVERED` and `coverage_reason` is `COVERED_BY_UNIT_COUNT`. Otherwise `coverage_status` is `NOT_COVERED` and `coverage_reason` is `BELOW_UNIT_THRESHOLD`. The zero-item branch outranks the unit branch, so a brand with fifty operating units and not one non-exempt item reports `NO_STANDARD_MENU_ITEMS` and never `BELOW_UNIT_THRESHOLD`. The two bases are the interesting part: a brand with nineteen `OPERATING` units and one `TEMPORARILY_CLOSED` unit counts nineteen on the `OPERATING_ONLY` basis and is `NOT_COVERED` for `BELOW_UNIT_THRESHOLD`, but counts twenty on the `REGISTERED_ALL` basis and is `COVERED` for `COVERED_BY_UNIT_COUNT` — the same rows, two answers. An explicit determination overwrites the brand's stored `coverage_status`, `coverage_reason`, `counted_unit_count` and `standard_item_count` with the chosen basis's result, increments the brand's `version`, and reports `brand_id`, the `basis` used, `counted_unit_count`, `standard_item_count`, `coverage_status`, `coverage_reason` and a `persisted` flag, which is always `true` because an explicit determination always writes the result it reports. Counts and thresholds are integers throughout; nothing here rounds.

For operators who want the whole picture in one read, a brand's compliance summary is recomputed from current rows at read time rather than served from stored counters. It returns `brand_id`, `coverage_status`, `coverage_reason`, `counted_unit_count`, `standard_item_count`, `compliance_posture`, `open_reprint_obligation_count`, `overdue_board_count`, `open_enforcement_escalated_count`, `has_published_disclosure_packet`, and `outstanding_penalty_cents_total` — the sum of `outstanding_penalty_cents` across every unit of the brand. **The summary's coverage limb always runs on the `OPERATING_ONLY` basis**: the endpoint takes no `basis` query parameter and the `REGISTERED_ALL` basis is not reachable through it, so `counted_unit_count`, `standard_item_count`, `coverage_status` and `coverage_reason` are the `OPERATING_ONLY` answer recomputed from current rows, which may differ from the values stored on the brand when the last explicit determination ran on the other basis. `compliance_posture` is likewise derived on the spot by applying the ladder of §2.9 to those recomputed figures rather than echoed from the brand's stored posture, and `open_reprint_obligation_count` and `overdue_board_count` carry exactly the same `PUBLISHED` board restriction as the stored counters of §2.10 — a withdrawn board that is still marked `OVERDUE` is counted by neither. The summary is a pure read: it writes nothing back to the brand and never bumps its `version`, even where a recomputed figure disagrees with the stored one.

### 3.2. The Menu: Item Classes, Offer Windows and the Temporary-Item Exemption

Only a `BrandComplianceOfficer` may add to a brand's menu, and only to its own brand's. Menu-item creation carries the `brand_id`, the item's `name` as printed on menus — 1 to 120 non-blank characters, unique within the brand, a name already used by another item of the same brand being refused with `ERR_VALIDATION` — its `item_class`, an optional `variable_type`, and `first_offered_on`, the ISO 8601 calendar date on which the item first appeared on a menu. Any well-formed `YYYY-MM-DD` value is accepted for `first_offered_on`, in the past or in the future; it is never compared against the logical clock and never against the item's offer windows. `item_class` is the FDA classification that drives every exclusion rule and is one of `STANDARD`, `TEMPORARY`, `TEST_MARKET`, `DAILY_SPECIAL`, `CUSTOM_ORDER` or `SELF_SERVICE`. `variable_type` describes the shape of the item's declaration and is one of `NONE`, `SIZE_VARIANTS`, `FLAVOR_VARIANTS`, `COMBINATION_MEAL` or `TOPPING_BASED`, defaulting to `NONE`; an item whose `variable_type` is `NONE` declares a single calorie value, while every other value declares a minimum-to-maximum range.

Creation seeds the item's two derived flags from `item_class` alone. A `STANDARD` item gets `labeling_exempt` false and `labeling_status` `DECLARATION_PENDING`. An item of any other class gets `labeling_exempt` true and `labeling_status` `NOT_REQUIRED`. The item's `offer_windows` starts as an empty list, `cumulative_offered_days` at 0, and `declared_calorie_min`, `declared_calorie_max`, `declared_sodium_mg` and `approved_recipe_version_no` all null, with `allergen_groups` and `cross_contact_groups` empty until a recipe is certified. Because a new non-exempt item changes `standard_item_count`, creation re-runs the coverage determination on the `OPERATING_ONLY` basis and increments the brand's `version` — and it does so for an item of every class, an exempt one included, the re-determination being unconditional rather than contingent on the count actually moving. Creation is one of the five operations gated by a `FROZEN` posture.

Temporary and test-market items are the only items that carry offer windows, and the only items whose exemption can be reviewed. An offer-window append supplies a `start_date` and an `end_date` and adds one entry to the end of the item's append-only `offer_windows` list, each entry being a JSON object carrying exactly two members — `start_date` and `end_date`, both plain `YYYY-MM-DD` strings — that hold that pair of whole calendar days as a closed interval inclusive of both ends; the list is stored and serialised in append order, oldest append first. Entries are never removed and never edited. A window whose `start_date` is after its `end_date` is refused with `ERR_INVALID_DATE_RANGE`, and an append against an item whose `item_class` is anything other than `TEMPORARY` or `TEST_MARKET` is refused with `ERR_ITEM_NOT_TEMPORARY`. Each append immediately recomputes `cumulative_offered_days` by the same merge described next, scoped to the calendar year of the appended window's own `start_date` — not to the year the logical clock is in, and never to every year at once, so appending a window that opens in a different year than the last one rewrites the figure onto that new year's basis. An append recomputes nothing else: however many days the total now reaches, it never re-decides `labeling_exempt` or `labeling_status` and never re-runs the coverage determination — only an exemption review does that. On this operation and on the exemption review alike the ownership comparison needs the item's own stored `brand_id`, so it is skipped outright when the path identifier names no existing item: such a request is refused as a malformed body when it is one and otherwise with `ERR_MENU_ITEM_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`.

An exemption review names a single `review_year` — a required integer from 1 through 9999, with no relation to the logical clock's own year — and re-decides the item's exemption for that year. It is likewise restricted to `TEMPORARY` and `TEST_MARKET` items, on pain of `ERR_ITEM_NOT_TEMPORARY`. The review considers only the entries of `offer_windows` whose `start_date` falls in the reviewed year, sorted by `start_date` ascending and, where two share a start, by `end_date` ascending. It then merges them: walking the sorted list, a window is appended as a new span when nothing has been accumulated yet or when its `start_date` falls more than one day after the end of the span accumulated so far; otherwise it is absorbed into that span, whose end becomes the later of the span's current end and the window's `end_date`. The adjacency rule is exact — a window that starts on the very next day after the previous span ends merges into it, while a window that leaves a two-day gap starts a fresh span. `cumulative_offered_days` is then the sum, over the merged spans, of the number of whole calendar days each covers counting both endpoints. A window is selected by its `start_date` alone and is then counted in full: a window that opens inside the reviewed year and closes inside the following one contributes every one of its days, because the merged spans are never clipped back to the reviewed year's boundary. Because of the merge, twelve overlapping fortnights do not count as one hundred and sixty-eight days.

The exemption itself is decided by class first and day count second. A `STANDARD` item is never exempt, whatever the day count. `DAILY_SPECIAL`, `CUSTOM_ORDER` and `SELF_SERVICE` items are always exempt, whatever the day count. Only `TEMPORARY` and `TEST_MARKET` items depend on the arithmetic: such an item is exempt while `cumulative_offered_days` is strictly below sixty days for the reviewed year, and loses its exemption the moment the merged total reaches sixty. Sixty days on the nose is not exempt.

When the review flips `labeling_exempt`, `labeling_status` follows. A flip to true sets `labeling_status` to `NOT_REQUIRED`. A flip to false sets it to `DECLARATION_PENDING` when the item has no `APPROVED` recipe, and to `DECLARED` when exactly one recipe of the item is already `APPROVED` — so an item that quietly outgrew its test-market exemption while its recipe was already certified arrives at `DECLARED` directly, without passing through `DECLARATION_PENDING`. Either way the flip recomputes `Brand.standard_item_count`, re-runs the coverage determination on the `OPERATING_ONLY` basis, recomputes `compliance_posture`, and — because the brand's covered item set just changed — turns every `PUBLISHED` disclosure packet of the brand `STALE`, since `allergen_matrix_complete` can no longer be trusted. A review that changes nothing changes nothing.

### 3.3. Recipe Versions, Components and the Shape of a Choice Group

Recipe sheets belong to the laboratory, not to the brand: only a `NutritionAnalyst` may open, populate, submit, certify or withdraw one. Opening a new recipe version for a menu item requires `expected_menu_item_version` — the optimistic-concurrency guard of §2.8 — and a `change_note` of 1 to 240 non-blank characters describing what changed against the prior version. The new row starts with `status` `DRAFT`, `revision_round` 0, `supersedes_recipe_id` null, `component_count` 0, `computed_base_calories` 0, `computed_declared_min`, `computed_declared_max`, `computed_sodium_mg` and `approved_at` all null, and `version_no` set to 1 for the item's first recipe or to the item's highest existing `version_no` plus 1 thereafter. Recipe-version creation is one of the five operations a `FROZEN` posture blocks. The recipe's own `menu_item_id` names the item it specifies, and the self-referential chain of `supersedes_recipe_id` can be walked backwards through the recipe list to reconstruct an item's full certification history.

Components may be added only while the recipe is `DRAFT`; an attempt against any other status is refused with `ERR_RECIPE_NOT_DRAFT`. A component addition carries a `component_name` of 1 to 80 non-blank characters that must be unique within the recipe, a name already carried by another component of the same recipe being refused with `ERR_VALIDATION`, a `role`, the as-served portion weight `grams`, the supplier-specification energy density `calories_per_100g` and sodium figure `sodium_mg_per_100g`, optionally `added_sugar_g_per_100g`, optionally an `allergen_group` and a `cross_contact_risk`, and — where the component is part of a selectable group — `choice_group`, `selection_mode` and `selection_limit`. `grams` must be strictly greater than 0 and carry at most two decimal places. `calories_per_100g`, `sodium_mg_per_100g` and `added_sugar_g_per_100g` must each be at least 0 with at most two decimal places, and `added_sugar_g_per_100g` defaults to 0. `allergen_group` names the major food allergen the component contributes and is one of `NONE`, `MILK`, `EGG`, `FISH`, `CRUSTACEAN_SHELLFISH`, `TREE_NUT`, `PEANUT`, `WHEAT`, `SOY` or `SESAME`, defaulting to `NONE`. `cross_contact_risk` records shared-equipment exposure and is one of `NONE`, `SHARED_FRYER`, `SHARED_LINE` or `SHARED_EQUIPMENT`, defaulting to `NONE`; any value other than `NONE` on any component of a covered item's approved recipe forces a cross-contact statement onto the brand's disclosure packet.

`role` is either `BASE` or `CHOICE`. A `BASE` component is always served. A `CHOICE` component belongs to a selectable group identified by `choice_group`, a label of 1 to 40 non-blank characters shared by the mutually exclusive or additive options in that group. `selection_mode` says how many members of the group a guest actually receives and is one of `EXACTLY_ONE`, `UP_TO_N` or `UNLIMITED`. `selection_limit` supplies the N of `UP_TO_N` and accepts an integer from 1 through 10. The consistency rules on these three fields are strict and are enforced together, with `ERR_CHOICE_GROUP_INCONSISTENT` (HTTP 400) as the single rejection: a component whose `role` is `CHOICE` must supply a non-null `choice_group` and a non-null `selection_mode`; a component whose `role` is `BASE` must leave all three of `choice_group`, `selection_mode` and `selection_limit` null; `selection_mode` of `UP_TO_N` requires a `selection_limit` of at least 1; `selection_mode` of `EXACTLY_ONE` or `UNLIMITED` forbids `selection_limit` entirely; and every component sharing one `choice_group` must declare the identical `selection_mode` and the identical `selection_limit` as the components already stored in that group. That last clause makes the check contextual — the same payload is valid against an empty recipe and invalid against a recipe whose group already declared a different mode.

Each addition computes the component's own two figures and then rebuilds the recipe's. `component_calories` is `calories_per_100g` multiplied by `grams` divided by 100, rounded half up to two decimal places; `component_sodium_mg` is `sodium_mg_per_100g` multiplied by `grams` divided by 100, rounded half up to two decimal places. The recipe's `component_count`, `computed_base_calories`, `computed_declared_min`, `computed_declared_max` and `computed_sodium_mg` are then all recomputed from scratch.

`computed_base_calories` is the sum of `component_calories` over the recipe's components whose `role` is `BASE`, held at two decimal places rounded half up. For an item whose `variable_type` is `NONE` there is nothing else to consider: `computed_declared_min` is the calorie declaration ladder of §2.7 applied once to `computed_base_calories`, and `computed_declared_max` equals `computed_declared_min`. This is the case where the order of operations bites, and it bears repeating in situ: the components are summed at two-decimal precision first and the ladder is applied exactly once to that total.

For a variable item the non-`BASE` components are partitioned by `choice_group` and each group is asked for the least and the most it can contribute. Within a group the members are considered in descending `component_calories` order, ties broken by ascending `created_at`. A group whose `selection_mode` is `EXACTLY_ONE` contributes, as its minimum, the smallest `component_calories` among its members, and as its maximum, the largest. A group whose `selection_mode` is `UP_TO_N` contributes a minimum of 0 — the guest may take nothing — and as its maximum the sum of the `selection_limit` largest `component_calories` in the group, or the sum of all of its members when the group holds fewer members than `selection_limit`. A group whose `selection_mode` is `UNLIMITED` contributes a minimum of 0 and, as its maximum, the largest `component_calories` in the group multiplied by three, three being the repeat cap the program applies to an unbounded self-serve option.

The raw minimum is `computed_base_calories` plus the sum of every group's minimum; the raw maximum is `computed_base_calories` plus the sum of every group's maximum. `computed_declared_min` is the calorie ladder applied once to the raw minimum and `computed_declared_max` is the calorie ladder applied once to the raw maximum. The ladder is never applied to an individual group's contribution, and never to an individual component. Two `variable_type` values shape the outcome in recognisably different ways. Under `TOPPING_BASED` the groups are optional add-ons, so every group contributes a minimum of 0 and the declared minimum is simply the ladder applied to `computed_base_calories`. Under `COMBINATION_MEAL` every group is `EXACTLY_ONE`, so every group pushes its cheapest member into the minimum, and the declared minimum strictly exceeds the ladder applied to `computed_base_calories` whenever any group's cheapest member is non-zero.

Sodium follows its own path. The raw sodium total is the sum of `component_sodium_mg` over the components whose `role` is `BASE`, at two decimal places rounded half up, and `computed_sodium_mg` is the sodium declaration ladder of §2.7 applied once to that total. That single figure is what the state and local sodium warning icon is later judged against, and it describes the maximum-calorie configuration of the item.

The printed text is derived, not typed. `display_calorie_text` on a board line is the item's `declared_calorie_min` followed by a space and the word `Cal` when `declared_calorie_min` and `declared_calorie_max` are equal, and otherwise `declared_calorie_min`, a hyphen, `declared_calorie_max`, a space and `Cal` — so a fixed item prints `320 Cal` while a range prints `320-540 Cal`. Where only one of the two endpoints is null the other stands in for both and the text reads as the single-value form; where both are null — the case of an exempt item printed on a board without ever having been certified — `display_calorie_text` is null too, never a placeholder string.

### 3.4. Analysis Submission, Certification, and the Withdrawal that Undoes It

Sending a recipe into analysis moves it from `DRAFT` to `ANALYSIS_PENDING`, and the request supplies only `method`, the basis of the nutrient figures, which is either `DATABASE` or `LAB_ANALYSIS`. Four things must hold. The recipe's `component_count` must be at least 1 — a recipe holding no components at all is caught by the base-component rule that follows rather than by any error of its own. It must hold at least one component whose `role` is `BASE`, or the submission is refused with `ERR_RECIPE_HAS_NO_BASE_COMPONENT` — a recipe with no base component has no computable base calorie figure. Every `choice_group` of the recipe must already declare one consistent `selection_mode` and `selection_limit`, an invariant the component-addition rule of §3.3 already guarantees and which submission therefore does not re-test. And no other recipe of the same menu item may currently be in `ANALYSIS_PENDING`, so an item cannot have two competing versions in the laboratory at once; a competing version is refused with `ERR_VALIDATION`, and that check is the last of the four to be tried — after the base-component rule, never before it. Submission creates a nutrition-analysis row with `status` `SUBMITTED`, its `recipe_id` pointing at the recipe version under analysis, `submitted_by_user_id` recorded from the acting `X-User-ID`, and `decided_by_user_id`, `decision_note`, `certified_at`, `declared_calorie_min`, `declared_calorie_max` and `declared_sodium_mg` all null. It also recomputes the recipe's derived figures in full, exactly as a component addition does — `component_count`, `computed_base_calories`, `computed_declared_min`, `computed_declared_max` and `computed_sodium_mg` alike — rather than `computed_base_calories` alone; because every component addition already recomputed all five, the recomputation is a confirmation and leaves the stored figures where they stood. The created analysis is discoverable through the recipe's analysis list.

The decision on a pending analysis carries `decision` — either `CERTIFY` or `REJECT` — and an optional `decision_note` of at most 400 characters, the empty string included and the blank string with it; omitted or sent as `null` it is recorded on the analysis as null. A decision against an analysis whose `status` is no longer `SUBMITTED` is refused with `ERR_ANALYSIS_ALREADY_DECIDED`. **Segregation of duties applies to `CERTIFY` only**: the analyst whose `X-User-ID` was recorded in `submitted_by_user_id` may not certify that analysis and is turned away with `ERR_SAME_USER_CERTIFICATION` (HTTP 403), while a `REJECT` from that same analyst is entirely permitted.

A rejection writes `decided_by_user_id` and `decision_note` on the analysis, moves the analysis to `REJECTED`, and then branches on how many rejections the recipe has already absorbed. While `revision_round` is below 3, the recipe returns from `ANALYSIS_PENDING` to `DRAFT` with `revision_round` incremented by 1 and becomes editable again so further components can be added — a genuine revision cycle from `DRAFT` to `ANALYSIS_PENDING` and back. When `revision_round` is already exactly 3, the recipe goes instead to `REJECTED`, which is terminal: that version can never be resubmitted, and a fresh version must be opened.

A certification is the heaviest operation in the system. The analysis moves to `CERTIFIED` with `certified_at` stamped from the logical clock, `decided_by_user_id` and `decision_note` written, and the declared figures `declared_calorie_min`, `declared_calorie_max` and `declared_sodium_mg` snapshotted onto the analysis row so that the certified numbers survive later recipe churn. The recipe moves from `ANALYSIS_PENDING` to `APPROVED` with `approved_at` stamped from the logical clock and its `computed_declared_min`, `computed_declared_max` and `computed_sodium_mg` written. Then four hops run in order. **Hop 1:** the menu item's previously `APPROVED` recipe, if there was one, moves from `APPROVED` to `SUPERSEDED`, and the newly certified recipe's `supersedes_recipe_id` is set to that row's `id`; on a first certification `supersedes_recipe_id` stays null. **Hop 2**, caused by hop 1: the item's `declared_calorie_min`, `declared_calorie_max`, `declared_sodium_mg`, `allergen_groups`, `cross_contact_groups` and `approved_recipe_version_no` are all rewritten from the newly approved recipe, and `labeling_status` moves from `DECLARATION_PENDING` to `DECLARED` on a first declaration, or from `DECLARED` to `RELABEL_REQUIRED` when the calorie change is large enough to force a reprint. Both of those moves are conditional. The move into `DECLARED` happens only for an item whose `labeling_exempt` is false and only when the certified recipe has a `component_count` of at least 1; an exempt item sits in `NOT_REQUIRED` and stays there even when a recipe of it is certified, though its declared figures and allergen sets are still refreshed. The move into `RELABEL_REQUIRED` happens only for an item whose `labeling_exempt` is false that actually has at least one line whose `listing_status` is `LISTED` on a board whose `publication_status` is `PUBLISHED` — a certification that shifts the calorie figure of an item nobody has printed yet leaves the item in `DECLARED` and creates no reprint obligation anywhere. Neither move ever runs backwards. An item already sitting in `RELABEL_REQUIRED` stays in `RELABEL_REQUIRED` when a further certification's calorie change falls inside the tolerance, and stays there as well when every line that prints it is already `STALE` — in that second case the certification finds no `LISTED` line to stale, so hop 3 does not fire, no fresh deadline is set and no second obligation is opened. Certification is never the operation that returns an item from `RELABEL_REQUIRED` to `DECLARED`. **Hop 3**, caused by hop 2 landing in `RELABEL_REQUIRED`: every line of the item whose `listing_status` is `LISTED` *and* whose holding board's `publication_status` is `PUBLISHED` becomes `STALE` — a `LISTED` line on a board still in `DRAFT` is left exactly as it stands, because nothing has been printed for a guest to read — and every board holding a line so staled moves `calorie_compliance_status` from `CURRENT` to `REPRINT_REQUIRED` with `reprint_deadline` set to the logical clock plus that board's authority's `reprint_grace_days` days. A board that is already `REPRINT_REQUIRED`, or already `OVERDUE`, keeps that status and keeps the `reprint_deadline` it is already carrying: an obligation that is already open is never reopened and its deadline is never extended by a second certification. **Hop 4**, caused by hop 3: `Brand.open_reprint_obligation_count` rises by one for each newly `REPRINT_REQUIRED` board, `MenuBoard.stale_listing_count` is recomputed on each, and `compliance_posture` is recomputed — typically carrying the brand from `COMPLIANT` to `RESTRICTED`. Independently of the reprint question, every `PUBLISHED` disclosure packet of the brand turns `STALE` if the item's `allergen_groups` or `cross_contact_groups` changed.

Whether hop 3 fires at all is decided by a tolerance band around the item's previously declared maximum. The prior maximum is the item's `declared_calorie_max` as it stood before this certification, and the new maximum is the newly approved recipe's `computed_declared_max`. On a first certification the prior maximum is null and no reprint is required. Otherwise the change is the absolute difference between the new maximum and the prior maximum, and the tolerance is the larger of twenty calories and the prior maximum multiplied by twenty per cent then rounded half up to a whole calorie. **A change equal to the tolerance does require a reprint** — the comparison is at-or-above, not strictly-above. So an item previously declared at 400 calories has a tolerance of 80 and survives a move to 470 untouched, while a move to 480 stales every published line that prints it. An item previously declared at 60 calories has a tolerance of 20, because the twenty-calorie floor beats twelve. A deadline is the logical instant in force at the moment of certification advanced by that whole number of days, so it inherits that instant's time of day rather than being truncated to a midnight boundary, and it is stored and rendered in UTC like every other instant; and because `reprint_grace_days` is 30 in an authority with no extra requirement and 14 in every other authority, one certification can hand two boards of the same brand two different deadlines.

Certification withdrawal is the compensating action that undoes all of it, and it is the only way an item's declaration walks backwards. It carries a `reason` of 1 to 400 non-blank characters, which is validated and then discarded — no row of the system records it — and is available only on a recipe whose `status` is `APPROVED` — anything else is refused with `ERR_RECIPE_NOT_APPROVED` — and only when that recipe's `supersedes_recipe_id` is not null, since there must be a prior version to restore; an `APPROVED` first certification, whose `supersedes_recipe_id` is null, is refused with that same `ERR_RECIPE_NOT_APPROVED` and not with an error of its own. The withdrawn recipe moves from `APPROVED` to `WITHDRAWN`, which is terminal, and four compensation hops run. Nothing else on the withdrawn row is rewritten: it keeps its own `computed_base_calories`, `computed_declared_min`, `computed_declared_max`, `computed_sodium_mg` and `approved_at`, and it keeps `supersedes_recipe_id` pointing at the very recipe it has just handed the certification back to, so the version chain stays walkable after the withdrawal exactly as it was before. **Hop 1:** the recipe named by `supersedes_recipe_id` moves from `SUPERSEDED` back to `APPROVED`, with its `approved_at` refreshed to the logical clock of the restoration. **Hop 2**, caused by hop 1: the item's `declared_calorie_min`, `declared_calorie_max`, `declared_sodium_mg`, `allergen_groups`, `cross_contact_groups` and `approved_recipe_version_no` are rewritten from the restored recipe. **Hop 3**, caused by hop 2: every line of the item whose `listing_status` is `STALE` returns to `LISTED` with `display_calorie_text`, `declared_min_snapshot` and `declared_max_snapshot` rebuilt from the restored declaration, and every board whose `stale_listing_count` thereby reaches 0 returns `calorie_compliance_status` from `REPRINT_REQUIRED` to `CURRENT`, or from `OVERDUE` to `CURRENT`, with `reprint_deadline` cleared to null. **Hop 4**, caused by hop 3: `Brand.open_reprint_obligation_count` and `Brand.overdue_board_count` are decremented back to exactly their pre-certification values, the item's `labeling_status` returns from `RELABEL_REQUIRED` to `DECLARED`, and `compliance_posture` is recomputed. Because the restored recipe re-enters `APPROVED`, the certification cycle from `APPROVED` to `SUPERSEDED` and back to `APPROVED` is a real cycle in this system, not a one-way street.

### 3.5. The Allergen Matrix and Written Nutrition Information

Two of the program's obligations sit outside the menu board itself: the allergen matrix and the promise that additional written nutrition information is available to any guest who asks. Both live on the `DisclosurePacket`, which a `BrandComplianceOfficer` drafts for its own brand. Drafting requires `expected_brand_version` — the brand-side optimistic-concurrency guard of §2.8 — the `cross_contact_statement` wording that will be printed alongside the matrix, and `written_info_channels`, the list of channels through which the written information can be had. `cross_contact_statement` may be between 0 and 400 characters, and the empty string is legitimate only when no covered item of the brand has a component with a `cross_contact_risk` other than `NONE`; unlike most free-text fields in this document it carries no non-blank rule, so a value made up entirely of whitespace is accepted at drafting and stored verbatim — publication, described below, then treats such a value as if it were empty. `written_info_channels` must carry between 1 and 4 distinct entries drawn from `IN_STORE_BINDER`, `WEBSITE`, `QR_HANDOUT` and `PHONE_LINE`, and the list is stored and serialised in exactly the order the client supplied: it is never sorted into the domain's order and never otherwise rewritten, a repeated entry being refused outright as non-distinct rather than silently collapsed. Drafting is refused with `ERR_BRAND_NOT_COVERED` unless the brand's `coverage_status` is `COVERED` — a chain that is not a covered establishment has nothing to disclose under this program. The new packet takes `status` `DRAFT`, `published_at` null, and `packet_version` set to 1 for the brand's first packet or to the brand's highest existing `packet_version` plus 1 thereafter.

Drafting is also when the matrix is synthesised, and the synthesis is deterministic. The matrix items are the brand's menu items whose `labeling_exempt` is false, ordered by `name` ascending. `covered_item_count` is the number of those items that actually have a recipe in `APPROVED` — a non-exempt item still waiting on certification is in the matrix's population but does not count as covered. `allergen_rows` then holds one entry per matrix item, ordered by `item_name` ascending, each entry carrying the item's `menu_item_id`, its `item_name`, its `allergen_groups` and its `cross_contact_groups`. An item's `allergen_groups` is the alphabetically ascending list of distinct `allergen_group` values across the components of that item's `APPROVED` recipe, with `NONE` excluded; its `cross_contact_groups` is the alphabetically ascending list of distinct `allergen_group` values across the same components restricted to those whose `cross_contact_risk` is not `NONE`, again with `NONE` excluded. A matrix item that has no `APPROVED` recipe behind it still gets its row, and that row carries `allergen_groups` and `cross_contact_groups` as empty arrays — never as null and never as a leftover from an earlier certification. Sorting alphabetically is what makes the matrix reproducible rather than insertion-ordered.

Two flags come out of the synthesis. `allergen_matrix_complete` is true when `covered_item_count` is at least 1 **and** `covered_item_count` equals the brand's `standard_item_count` — that is, when every non-exempt item on the menu has a certified recipe behind it. A brand with four non-exempt items and three certifications has an incomplete matrix, and so does a brand with no non-exempt items at all. `cross_contact_statement_required` is true when any component of any `APPROVED` recipe of any non-exempt item of the brand has a `cross_contact_risk` other than `NONE`. Both are stored on the packet, and — this matters — where `allergen_matrix_complete` is consulted by some *later* operation it is read from the stored flag rather than re-derived on the spot: board publication of §3.6 believes whatever value the brand's `PUBLISHED` packet is carrying. All four synthesised fields — `covered_item_count` and `allergen_rows` as much as `allergen_matrix_complete` and `cross_contact_statement_required` — are computed when the packet is drafted and refreshed together when the packet is published, and at no other moment; no third occasion re-derives any of them.

Publication takes a `DRAFT` packet live and carries no request body. Because the ownership comparison needs the packet's own stored `brand_id`, it is skipped outright when the path identifier names no existing packet: such a request is refused as a malformed body when it is one and otherwise with `ERR_DISCLOSURE_PACKET_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`. It requires the packet's `status` to be `DRAFT`, on pain of `ERR_PACKET_NOT_DRAFT` — an already `PUBLISHED` or `STALE` packet cannot be republished, and a fresh packet must be drafted instead. Once the status gate is cleared, and before any of the remaining conditions is tried, **publication re-runs the whole synthesis just described against the brand's rows as they now stand**, overwriting all four synthesised fields of the packet — `covered_item_count` and `allergen_rows` as well as `allergen_matrix_complete` and `cross_contact_statement_required` — so a packet drafted before a certification landed publishes the matrix as it is at the moment of publication rather than the one drafting captured. It then requires that refreshed `allergen_matrix_complete` to be true, else `ERR_ALLERGEN_MATRIX_INCOMPLETE`; the check reads the value the re-synthesis just wrote, not the value drafting stored, so a packet that was drafted incomplete and has since had its last item certified publishes successfully, and one drafted complete whose brand has since gained an uncertified non-exempt item is refused. It requires `cross_contact_statement` to be non-empty whenever the refreshed `cross_contact_statement_required` is true, else `ERR_CROSS_CONTACT_STATEMENT_REQUIRED` — a conditional requirement that simply does not apply to a brand whose components are all free of shared-equipment exposure. "Non-empty" here means non-blank: the stored statement is compared with its surrounding whitespace stripped away, so a statement of one space or a run of tabs is refused exactly as the empty string is, and the field itself is left stored verbatim either way. And it requires `written_info_channels` to hold at least one entry, else `ERR_VALIDATION` — this last condition is a belt-and-braces restatement of the drafting rule and can only fail for a packet whose channel list was somehow emptied after drafting. On success the packet moves from `DRAFT` to `PUBLISHED`, `published_at` is stamped from the logical clock, `Brand.has_published_disclosure_packet` becomes true, and any other packet of the same brand whose `status` was `PUBLISHED` or `STALE` moves to `SUPERSEDED` with its `version` incremented by 1. `SUPERSEDED` is terminal.

A published packet does not stay fresh forever, and the set of things that spoil it is deliberately narrow. Exactly two triggers move a packet from `PUBLISHED` to `STALE`: a certification decision that changed the `allergen_groups` or `cross_contact_groups` recorded in `allergen_rows` for a covered item, and an exemption review that flipped a covered item's `labeling_exempt`. Nothing else does. In particular, creating a new menu item does not stale a published packet, and neither does registering a new unit — the matrix is not re-derived outside those two triggers. When a packet does go `STALE`, `Brand.has_published_disclosure_packet` returns to false, which in turn blocks board publication for that brand until a fresh packet is drafted and published. A `STALE` packet can still be superseded by a newer published packet, again with its `version` incremented by 1.

### 3.6. Menu Boards: Drafting a Panel, Printing Lines, and Going Live

A `MenuboardPublisher` owns the boards of exactly one unit, and every board operation checks that its `X-User-ID` equals the board's `establishment_id`. On the three operations addressed at an existing board — listing creation, board publication and board reprint — that comparison needs the board's own stored `establishment_id`, so it is skipped outright when the path identifier names no existing board: such a request is refused as a malformed body when it is one and otherwise with `ERR_MENU_BOARD_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`. Board creation is the exception, because there the unit is named by a request-body foreign key that the ownership rung can read straight out of the raw body ahead of validation. Board creation names the `establishment_id` of the unit that will display the board, the `board_type` — the surface the declaration appears on, one of `PRIMARY_MENU_BOARD`, `DRIVE_THRU_BOARD`, `PRINTED_MENU` or `THIRD_PARTY_DELIVERY` — and the `succinct_statement_variant` the board will carry, one of `FEDERAL_DEFAULT`, `STATE_EXTENDED` or `OMITTED`. A new board is seeded with `publication_status` `DRAFT` and `calorie_compliance_status` `CURRENT`, `effective_from`, `effective_to` and `reprint_deadline` null, and `reprint_count`, `listing_count` and `stale_listing_count` at 0. `Establishment.board_count` is recomputed. Board creation is blocked while the brand's posture is `FROZEN`.

**A board carries two independent state dimensions on one row.** `publication_status` tracks whether the board is drafted, live or retired, and advances only on publication and on the withdrawal cascade of a permanently closing unit. `calorie_compliance_status` tracks whether the declarations printed on the board still match the certified recipes behind them, and advances only on recipe-certification cascades, on clock advances, and on reprints — never on a publication action. The two never gate each other and every combination of the two is reachable: a `DRAFT` board can be `REPRINT_REQUIRED` in principle, and a `PUBLISHED` board can be `CURRENT`, `REPRINT_REQUIRED` or `OVERDUE`. `WITHDRAWN` is terminal for `publication_status`; `calorie_compliance_status` has no terminal value.

Lines are printed onto a board while it is still `DRAFT`; an attempt against a board whose `publication_status` is anything else is refused with `ERR_BOARD_NOT_DRAFT`. A listing creation supplies the `menu_item_id` of the item to print and, optionally, `sodium_warning_icon`, which defaults to false and records whether the printed line actually carries the state or local sodium warning icon. Three referential rules apply in the order of §2.6. The item's `brand_id` must equal the `brand_id` of the board's establishment, else `ERR_ITEM_BRAND_MISMATCH` — a board cannot print another chain's item even when both chains are covered. The board-and-item pair must not already be carried by a line whose `listing_status` is `LISTED` or `STALE`, else `ERR_DUPLICATE_LISTING`; a line that has been `REMOVED` does not block re-listing the same item. And the brand's posture must not be `FROZEN`. On success the line starts at `listing_status` `LISTED` with its `menu_board_id` pointing at the board, and `display_calorie_text`, `declared_min_snapshot` and `declared_max_snapshot` captured from the item's `declared_calorie_min` and `declared_calorie_max` as they stand at that moment. `MenuBoard.listing_count` is recomputed.

Taking a board live is the most heavily guarded operation in the specification. The request supplies `effective_from`, the instant the display window opens, and optionally `effective_to`, the instant it closes; a null or omitted `effective_to` means an open-ended window, and once such a window exists no later window can be published on the same `establishment_id` and `board_type`. **Display windows are half-open**: a window includes its `effective_from` instant and excludes its `effective_to` instant, so a window that begins exactly at another window's `effective_to` is accepted, with no buffer required between them. If `effective_to` is supplied and is earlier than `effective_from`, the request fails with `ERR_INVALID_DATE_RANGE`; if the resulting window overlaps the window of another board of the same establishment and the same `board_type` whose `publication_status` is `PUBLISHED`, it fails with `ERR_BOARD_WINDOW_CONFLICT`.

Beyond the window arithmetic, seven conditions must hold, and §2.6 fixes the order in which they are tried. The board must be `DRAFT`, else `ERR_BOARD_NOT_DRAFT`. The brand's posture must not be `FROZEN`, else `ERR_BRAND_POSTURE_FROZEN`. The brand's `coverage_status` must be `COVERED`, else `ERR_BRAND_NOT_COVERED`. The brand must hold a disclosure packet whose `status` is `PUBLISHED`, else `ERR_NO_PUBLISHED_PACKET` — which is precisely why a packet turning `STALE` locks a brand out of publishing new boards. That packet's stored `allergen_matrix_complete` must be true, else `ERR_ALLERGEN_MATRIX_INCOMPLETE`. The board's `succinct_statement_variant` must equal the establishment's authority's `required_succinct_statement_variant`, unless a variance request of that brand in that authority for `requirement_code` `SUCCINCT_STATEMENT` is `GRANTED` and its covered interval contains the publication date; otherwise the request fails with `ERR_SUCCINCT_STATEMENT_MISMATCH`, and this check runs before any per-listing check. **The publication date this shield is tested against is the UTC calendar date of the `effective_from` instant the request supplies**, not the calendar date of the logical clock in force at the moment of the call: a board whose window opens inside a granted interval is released even when the clock currently sits outside that interval, and a board whose window opens after the granted interval has closed is refused even when the clock still sits inside it. Then, where the authority's `extra_requirement` is `SODIUM_WARNING`, every line whose item's `declared_sodium_mg` is at or above that authority's `sodium_warning_threshold_mg` must carry `sodium_warning_icon` true, else `ERR_SODIUM_WARNING_ICON_REQUIRED`; exactly at the threshold the icon **is** required, and the whole check is inapplicable in an authority whose `extra_requirement` is `NONE` or `ADDED_SUGAR_ICON`. A line whose item carries no `declared_sodium_mg` at all is passed over rather than read as a zero, so it never requires the icon — not even in an authority whose `sodium_warning_threshold_mg` is 0, where a zero would have tripped the at-or-above comparison. Finally the board must carry at least one line — `listing_count` of at least 1 — and every listed item must either have `labeling_status` of `DECLARED` or `RELABEL_REQUIRED` with a non-null `declared_calorie_max`, or have `labeling_exempt` true; otherwise `ERR_ITEM_CALORIES_UNDECLARED`. Exempt temporary and test-market items are welcome on a live board with no declaration at all; a non-exempt item that has never been certified is not.

Publication moves `publication_status` from `DRAFT` to `PUBLISHED`, writes `effective_from` and `effective_to` from the request, refreshes every line's `declared_min_snapshot`, `declared_max_snapshot` and `display_calorie_text` from its item's current declaration, and recomputes `Establishment.board_count`. It does not touch `calorie_compliance_status`, which stays wherever it was.

### 3.7. When a Line Goes Stale: Reprints, Overdue Boards and the Clock Sweep

The life of a printed line is short and has three states. A line begins `LISTED`. It becomes `STALE` when the item it prints enters `labeling_status` `RELABEL_REQUIRED` after a recipe certification, which can only happen while the holding board's `publication_status` is `PUBLISHED`; the board's `stale_listing_count` is recomputed as each line flips. A `STALE` line returns to `LISTED` in exactly two ways — through a board reprint, or through the compensation cascade of a certification withdrawal — and on the way back its `display_calorie_text`, `declared_min_snapshot` and `declared_max_snapshot` are rebuilt from the item's current declaration. That is a genuine cycle from `LISTED` to `STALE` and back. A line in either state becomes `REMOVED` when its holding board reaches `WITHDRAWN`; `REMOVED` is terminal. When a `LISTED` line is removed the board's `listing_count` is recomputed; when a `STALE` line is removed both `listing_count` and `stale_listing_count` are recomputed, and `Brand.open_reprint_obligation_count` is decremented once for the board — once for the board, not once per stale line on it.

A board reprint is how a store discharges the obligation. Filed by the board's own `MenuboardPublisher` with an optional `reprint_note` of 0 to 400 characters — the empty string and the blank string included — which is validated and then discarded, no field of any row recording it, it requires the board's `publication_status` to be `PUBLISHED` and its `stale_listing_count` to be at least 1; a reprint on a board with nothing stale on it is refused with `ERR_NO_STALE_LISTINGS`, which is what stops `reprint_count` from being inflated by empty filings. Those two requirements are read as one condition raising one error: a reprint filed against a board still in `DRAFT` is refused with that same `ERR_NO_STALE_LISTINGS` and never with `ERR_BOARD_NOT_DRAFT`, which does not apply to this operation at all, while a `WITHDRAWN` board is already refused earlier on the terminal-lockdown rung. Reprinting is deliberately *not* blocked by a `FROZEN` posture, because it is the brand's route out of a freeze. Three hops follow. **Hop 1:** every `STALE` line of the board returns to `LISTED` with `declared_min_snapshot`, `declared_max_snapshot` and `display_calorie_text` rebuilt from its item's current declaration. **Hop 2**, caused by hop 1: each affected menu item that is left with no remaining `STALE` line anywhere returns `labeling_status` from `RELABEL_REQUIRED` to `DECLARED`. **Hop 3**, caused by hops 1 and 2: `Brand.open_reprint_obligation_count` is decremented by 1 and `compliance_posture` is recomputed. Alongside the hops, `reprint_deadline` is cleared to null, `reprint_count` increments by 1, and `stale_listing_count` resets to 0. A reprint filed while `calorie_compliance_status` was `REPRINT_REQUIRED` returns it to `CURRENT`. A reprint filed while it was `OVERDUE` returns it to `CURRENT` too, and additionally decrements `Brand.overdue_board_count` by 1 before the posture is recomputed — which is how a brand walks back from `FROZEN` to `RESTRICTED`, or all the way to `COMPLIANT` when nothing else is outstanding. The full compliance cycle is therefore `CURRENT` to `REPRINT_REQUIRED` to `OVERDUE` and back to `CURRENT`.

Deadlines only bite when the clock moves, and the clock only moves when a `PlatformAdmin` sets it, supplying the new instant as `to_iso8601`. The clock set is a sweep as much as an assignment. Every board whose `publication_status` is `PUBLISHED`, whose `calorie_compliance_status` is `REPRINT_REQUIRED`, and whose `reprint_deadline` is strictly earlier than the new clock instant moves to `OVERDUE`, incrementing `Brand.overdue_board_count` by 1 and recomputing `compliance_posture` — which carries the brand from `RESTRICTED` to `FROZEN`. A board whose `reprint_deadline` is exactly the new instant is not yet overdue. A board that does move to `OVERDUE` keeps the `reprint_deadline` it missed: going overdue neither clears that field nor rewrites it, and the sweep is one-directional — it never returns an `OVERDUE` board to `REPRINT_REQUIRED`, whatever instant the clock is subsequently set to. Every variance request whose `status` is `GRANTED` and whose `effective_end_date` falls before the calendar date of the new clock moves to `EXPIRED`, and stops shielding citations from the moment it does. The response reports the resulting `current_utc` along with `boards_marked_overdue` and `variances_expired`, the counts of rows the sweep moved in each population.

### 3.8. Asking a State or Local Authority for Relief

State and local labeling requirements sit on top of the federal rule, and a chain that cannot meet one of them in one authority may ask that authority for relief. A `BrandComplianceOfficer` files a variance request for its own brand, naming the `brand_id`, the `jurisdiction_id` of the authority being asked, the `requirement_code` it wants relief from — one of `SUCCINCT_STATEMENT`, `SODIUM_WARNING`, `ADDED_SUGAR_ICON` or `WRITTEN_INFO_FORMAT` — a written `justification` of 1 to 400 non-blank characters, and the closed interval of relief it is asking for as `requested_start_date` and `requested_end_date`. The filing's two body foreign keys are resolved in the order this paragraph names them — `brand_id` first, then `jurisdiction_id` — so a filing that names neither an existing brand nor an existing authority reports `ERR_BRAND_NOT_FOUND` rather than `ERR_JURISDICTION_NOT_FOUND`. Both resolve before the requested interval is examined: the requested end may not precede the requested start, on pain of `ERR_INVALID_DATE_RANGE`. A filed request starts at `status` `SUBMITTED` with `effective_start_date`, `effective_end_date`, `decision_note` and `decided_by_user_id` all null.

Only the `StateRegulator` of the addressed authority may decide it, and its `X-User-ID` must equal the request's `jurisdiction_id`. Because that comparison needs the request's own stored `jurisdiction_id`, it is skipped outright when the path identifier names no existing variance request: such a call is refused as a malformed body when it is one and otherwise with `ERR_VARIANCE_REQUEST_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`. The decision carries a `decision` of `OPEN_REVIEW`, `GRANTED` or `DENIED`, an optional `decision_note` of at most 400 characters — the empty string included and the blank string with it, and recorded as null when it is omitted or sent as `null` — and optionally `effective_start_date` and `effective_end_date`. Every decision, `OPEN_REVIEW` included, writes both `decided_by_user_id` from the acting `X-User-ID` and `decision_note` from the payload, and writes them unconditionally: a later decision that omits `decision_note` overwrites the note an earlier one recorded back to null rather than preserving it. Where both `effective_start_date` and `effective_end_date` are supplied, the pair's own ordering is tested once the state machine has accepted the requested decision and before any date is written, whatever that decision is — so a reversed pair sent alongside `OPEN_REVIEW` or `DENIED`, neither of which will store either date anywhere, is still refused with `ERR_INVALID_DATE_RANGE`. The state machine is deliberately two-step: `OPEN_REVIEW` is defined only from `SUBMITTED` and moves the request to `UNDER_REVIEW`, while `GRANTED` and `DENIED` are defined only from `UNDER_REVIEW`. A regulator therefore cannot grant straight out of `SUBMITTED`, and any decision requested from the wrong state is refused with `ERR_VARIANCE_STATE_INVALID`. `DENIED` and `EXPIRED` are terminal states; a decision against a request already in one of them fails on the terminal-lockdown rung.

Granting is where the constraints live. The authority's `preemption_mode` must be `VARIANCE_ALLOWED`; an authority whose `preemption_mode` is `PREEMPTED` may open a review and may deny, but a grant from it is refused with `ERR_VARIANCE_NOT_ALLOWED`. The granted window is written from `effective_start_date` and `effective_end_date` in the decision payload, each defaulting to the corresponding `requested_start_date` or `requested_end_date` when omitted, and the resulting `effective_start_date` may not fall after the resulting `effective_end_date`. **The covered interval is a closed interval** inclusive of both `effective_start_date` and `effective_end_date` — pointedly unlike the half-open display windows of §3.6 — and consecutive grants must be separated by a cooling buffer. Concretely: for every other variance request of the same `brand_id`, the same `jurisdiction_id` and the same `requirement_code` whose `status` is `GRANTED`, the new grant's `effective_start_date` must fall **more than seven days** after that request's `effective_end_date`. A start exactly seven days after an existing grant's end is refused with `ERR_VARIANCE_WINDOW_CONFLICT`; eight days after is accepted. Where a denial is issued instead, `decision_note` is recorded and both effective dates stay null.

A granted variance does two things. Within its covered interval it releases a board from matching its authority's `required_succinct_statement_variant`, where the granted `requirement_code` is `SUCCINCT_STATEMENT`. And it shields matching citations from escalation for as long as the covered interval contains the logical clock's calendar date, as described next. Both effects end the instant the clock pushes the grant to `EXPIRED`.

### 3.9. Enforcement: Citations, Responses, Escalation and the Money

A `StateRegulator` opens a citation against a single unit, supplying the `establishment_id` of the cited unit, the `citation_code` naming the labeling requirement cited — one of `CALORIES_NOT_DECLARED`, `SUCCINCT_STATEMENT_MISSING`, `WRITTEN_INFO_UNAVAILABLE`, `ALLERGEN_MATRIX_MISSING` or `SODIUM_WARNING_MISSING` — and an optional `inspection_note` of up to 400 characters — the empty string and the blank string included — recording what the inspector saw. The ownership rung here compares the acting `X-User-ID` against the cited establishment's own stored `jurisdiction_id` rather than against anything the payload carries, so it cannot fire until that establishment has been located: a citation whose `establishment_id` matches no unit is refused with `ERR_ESTABLISHMENT_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`, however unrelated the acting authority. The new file copies its `jurisdiction_id` from the cited establishment at opening time rather than taking it from the request, stamps `opened_at` from the logical clock, and starts at `status` `OPEN` with `info_round_count` and `response_count` at 0, `last_response_type`, `penalty_basis`, `violation_unit_count`, `base_penalty_cents`, `admin_fee_cents` and `closed_at` all null, and `penalty_total_cents` at 0.

The brand answers through its `BrandComplianceOfficer`, whose `X-User-ID` must equal the cited establishment's `brand_id`; because that comparison has to walk from the file through to its establishment to reach that `brand_id`, it is skipped outright when the path identifier names no existing enforcement file, and such a call is refused as a malformed body when it is one and otherwise with `ERR_ENFORCEMENT_ACTION_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`. A response supplies a `response_type` of `REPRINT_COMPLETED`, `VARIANCE_CITED` or `DISPUTED` and an optional `response_note` of up to 400 characters, the empty string and the blank string included, which is validated and then discarded — no field of the file records it and it is absent from the file's representation. A response is defined only from `OPEN` and from `INFO_REQUESTED`, and both land in `RESPONSE_SUBMITTED` with `response_count` incremented by 1 and `last_response_type` recorded; a response requested from any other state is refused with `ERR_ACTION_STATE_INVALID`. Two further conditions apply. The brand must hold a disclosure packet whose `status` is `PUBLISHED`, else `ERR_NO_PUBLISHED_PACKET` — written nutrition and allergen information must be on file before a chain answers a citation at all. And where `response_type` is `REPRINT_COMPLETED`, the cited unit's `outstanding_penalty_cents` must be 0, else `ERR_OUTSTANDING_PENALTY` with HTTP 402: a chain may not certify a reprint as complete for a unit that still owes an assessed penalty, though rescinding that penalty clears the block. A `VARIANCE_CITED` or `DISPUTED` response is not subject to the money check.

The regulator side of the file moves through a single operation carrying an `action_type`, an optional `penalty_basis` and an optional `action_note` of up to 400 characters — the empty string and the blank string included — which is validated and then discarded exactly as the brand's `response_note` is; the acting `X-User-ID` must equal the file's own stored `jurisdiction_id` throughout, a comparison that is skipped outright when the path identifier names no existing file, so such a call is refused as a malformed body when it is one and otherwise with `ERR_ENFORCEMENT_ACTION_NOT_FOUND`, never with `ERR_FORBIDDEN_SCOPE`. `REQUEST_INFO` is defined only from `RESPONSE_SUBMITTED`, moves the file to `INFO_REQUESTED` and increments `info_round_count` by 1 — and because a response from `INFO_REQUESTED` comes straight back to `RESPONSE_SUBMITTED`, information rounds are a real cycle that can run as many times as the regulator wants. `CLOSE_COMPLIANT` is defined only from `RESPONSE_SUBMITTED` and additionally demands that `last_response_type` be `REPRINT_COMPLETED` or `VARIANCE_CITED`; a file whose most recent response was `DISPUTED` cannot be closed as compliant and is refused with `ERR_ACTION_STATE_INVALID`. A compliant closure stamps `closed_at` from the logical clock and is terminal.

`ESCALATE` is also defined only from `RESPONSE_SUBMITTED`, and it has two extra gates. The file's `info_round_count` must be at least 1 — a regulator must have asked for information at least once before escalating — else `ERR_INFO_ROUND_REQUIRED`. And no variance request of the cited brand in the citing authority whose `status` is `GRANTED` and whose `requirement_code` maps to the file's `citation_code` may cover the logical clock's calendar date, else `ERR_CITATION_SHIELDED_BY_VARIANCE`. The citation-to-requirement map is fixed and total: `SUCCINCT_STATEMENT_MISSING` maps to `SUCCINCT_STATEMENT`, `SODIUM_WARNING_MISSING` maps to `SODIUM_WARNING`, and `WRITTEN_INFO_UNAVAILABLE` maps to `WRITTEN_INFO_FORMAT`, while `CALORIES_NOT_DECLARED` and `ALLERGEN_MATRIX_MISSING` map to no `requirement_code` at all and can therefore never be shielded — note in particular that a grant for `ADDED_SUGAR_ICON` shields nothing, because no citation code maps to it. The shield lifts as soon as the clock pushes the grant to `EXPIRED`. A successful escalation moves the file to `ESCALATED`, increments `Brand.open_enforcement_escalated_count` by 1, and recomputes `compliance_posture` to `FROZEN`.

`ASSESS_PENALTY` is defined only from `ESCALATED` and requires `penalty_basis` to be supplied in the request, as either `PER_BOARD` or `PER_ESTABLISHMENT`. That requirement is enforced at the body-validation rung rather than as a state or referential check: an `ASSESS_PENALTY` that omits `penalty_basis` or sends it as `null` is refused with `ERR_VALIDATION`, and because that rung outranks existence, terminal-lockdown and state checks alike, the same `ERR_VALIDATION` is what such a call receives even when the `action_id` names no file at all, names a closed one, or names one that is not `ESCALATED`. On every other `action_type` `penalty_basis` is accepted and then ignored, a value outside those two being refused with `ERR_VALIDATION` there as well. The basis decides `violation_unit_count`. Under `PER_BOARD`, `violation_unit_count` is the number of the cited establishment's boards whose `publication_status` is `PUBLISHED` and whose `calorie_compliance_status` is either `REPRINT_REQUIRED` or `OVERDUE` — one violation unit per board that is out of step. Under `PER_ESTABLISHMENT`, `violation_unit_count` is exactly 1 regardless of how many boards are out of step. A `PER_BOARD` assessment against a unit that has no out-of-step published board at all is not an error and has no floor of one: `violation_unit_count` lands at 0, `base_penalty_cents`, `admin_fee_cents` and `penalty_total_cents` all land at 0, and the file still moves to `PENALTY_ASSESSED` — leaving a unit whose `outstanding_penalty_cents` is 0 while a penalty is formally on the record. From there the arithmetic is shared. The tier multiplier is one and a half when the citing authority's `enforcement_tier` is `ENHANCED` and plain one when it is `FEDERAL_ALIGNED`. `base_penalty_cents` is fifty thousand cents per violation unit — that is, five hundred dollars a unit expressed in whole cents — multiplied by `violation_unit_count`, multiplied by the tier multiplier, rounded half up to a whole cent. The administrative fee rate is then read **off `base_penalty_cents`, never off the fee-inclusive total**: five per cent when `base_penalty_cents` is at or below one hundred thousand cents, eight per cent when it is above that but at or below two hundred and fifty thousand cents, and twelve per cent above that. `admin_fee_cents` is `base_penalty_cents` multiplied by that rate, rounded half up to a whole cent, and `penalty_total_cents` is `base_penalty_cents` plus `admin_fee_cents`.

The two bases can produce different fee tiers from identical data, which is the point of asking the regulator to choose one. A unit with three non-current published boards in an `ENHANCED` authority assessed `PER_BOARD` yields a base of 225000 cents, lands in the eight-per-cent tier for a fee of 18000 cents, and totals 243000 cents. The same unit assessed `PER_ESTABLISHMENT` yields a base of 75000 cents, lands in the five-per-cent tier for a fee of 3750 cents, and totals 78750 cents. An assessment moves the file to `PENALTY_ASSESSED`, adds `penalty_total_cents` to the cited `Establishment.outstanding_penalty_cents` and to the citing `Jurisdiction.assessed_penalty_cents_total`, decrements `Brand.open_enforcement_escalated_count` by 1, and recomputes `compliance_posture` — so assessing a penalty can actually thaw a brand that was frozen only by that escalation, while leaving the unit owing money.

Two moves are defined from `PENALTY_ASSESSED`. `RESCIND_PENALTY` is the compensating action: it subtracts **exactly** `penalty_total_cents` from both `Establishment.outstanding_penalty_cents` and `Jurisdiction.assessed_penalty_cents_total`, clears `penalty_basis`, `violation_unit_count`, `base_penalty_cents` and `admin_fee_cents` back to null, resets `penalty_total_cents` to 0, and returns the file to `RESPONSE_SUBMITTED` — from which the brand can respond again, the regulator can request more information, escalate again, or close. That is the penalty cycle: `RESPONSE_SUBMITTED` to `ESCALATED` to `PENALTY_ASSESSED` and back to `RESPONSE_SUBMITTED`. `CLOSE_PENALTY` instead stamps `closed_at` from the logical clock and moves the file to `CLOSED_PENALTY`, which is terminal; the assessed money stays on both ledgers, because `CLOSED_PENALTY` remains inside the set of statuses those ledgers sum over. Every regulator action requested from a state in which it is undefined is refused with `ERR_ACTION_STATE_INVALID`.

## 4. Endpoint Definitions

All resources are mounted at the root of the service; no path nests one resource identifier inside another. An operation that brings a new resource row into existence answers **201 Created** and returns that row; an operation that modifies, transitions or reads an existing resource answers **200 OK**. Note that two operations which look like creations are in fact modifications and answer 200: an offer-window append and an exemption review both return the modified `MenuItem`, and a coverage determination returns a computed summary of the brand it updated. Every response body follows the envelope of §2.2, and the request body of each write is reconstructed from the narratives of §3 rather than restated here. "All five roles" below means `PlatformAdmin`, `BrandComplianceOfficer`, `NutritionAnalyst`, `MenuboardPublisher` and `StateRegulator`.

## 5. Error Code Catalogue

Every error response carries the envelope of §2.2 with `response_type` set to `error` and the identifier below in `data.error_id`. The conditions that raise each identifier are stated in the narratives of §2 and §3, at the point where the rule they enforce is described; §2.6 fixes the order in which competing conditions are evaluated.

A request that never reaches one of the operations of §4 is answered outside this catalogue, in the same error envelope: a path that matches no operation yields `ERR_NOT_FOUND` with HTTP 404, a path that exists only under a different method yields `ERR_METHOD_NOT_ALLOWED` with HTTP 405, a request the HTTP layer itself rejects as malformed yields `ERR_VALIDATION` with HTTP 400, any other HTTP-level refusal yields `ERR_REQUEST_FAILED` with that refusal's own status, and an unhandled server fault yields `ERR_INTERNAL` with HTTP 500. A trailing slash on any path of §4 is tolerated and resolves to the same operation as the slashless form.
