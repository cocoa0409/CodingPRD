# Per-Diem Healthcare Staffing API — Product Requirements Document

## 1. Introduction

Hospitals and clinics rarely staff every shift from their permanent roster. When a unit is short a nurse for a night, or a respiratory therapist calls out, the gap is filled from a *float pool* of per-diem clinicians who pick up individual shifts on demand. This document specifies the backend API for a marketplace that runs that float pool end to end: facilities publish their demand as staffing orders and individual shift slots, credentialed clinicians self-schedule by claiming those slots, a scheduler awards each slot to the best eligible bidder, attendance is tracked, worked hours are punched and verified into pay, and the money is closed out through invoices that carry the platform's markup.

The system exists to reconcile two competing pressures. On one side, a facility must never place a clinician who lacks a current licence or the certifications its unit requires, must never double-book someone, and must respect rest and weekly-hour limits that keep care safe. On the other side, clinicians who cancel late or fail to appear degrade the pool, so the platform maintains a reliability score that feeds directly back into who is eligible to be awarded future work. Between those two poles sits a money layer that keeps a clean separation between what a clinician is paid and what a facility is billed, and enforces segregation of duties so that no single operator can both fill a shift and sign off its hours, or both issue an invoice and record its payment.

Everything below is written for the engineer building the service. Section 2 fixes the system-wide contracts — envelopes, pagination, identity, concurrency, precision — that every endpoint obeys. Section 3 narrates the business workflows, where the detailed rules for each entity live. Sections 4 and 5 summarize the endpoint surface and the error catalogue.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role under which it acts. If either header is missing, or if `X-User-Role` is not one of the six roles defined by this system, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The six roles are `PlatformAdmin`, `ComplianceOfficer`, `FacilityScheduler`, `FacilityVerifier`, `Clinician`, and `BillingAgent`. When a request is authenticated but the acting role is not among the roles permitted on the target endpoint, it is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Roles differ in how `X-User-ID` binds to persisted data. When `X-User-Role` is `FacilityScheduler`, `X-User-ID` is the `id` of the acting `Facility`; ownership checks on any resource that reaches a facility (an order directly, or a shift, assignment, or timesheet traced back through its order) compare that facility `id` to `X-User-ID`. When `X-User-Role` is `FacilityVerifier`, `X-User-ID` is likewise the `id` of the acting `Facility`, and the same ownership tracing applies — the two facility roles are deliberately split so that the person who fills a slot is never the person who signs off the hours worked in it. When `X-User-Role` is `Clinician`, `X-User-ID` is the `id` of the acting `Clinician`; ownership checks on any credential, claim, assignment, or timesheet compare the owning clinician `id` to `X-User-ID`. A facility principal acting on a resource belonging to a different facility is rejected with `ERR_ROLE_SCOPE_VIOLATION` (HTTP 403); a clinician acting on a resource belonging to a different clinician is rejected with `ERR_NOT_OWNER` (HTTP 403).

When `X-User-Role` is `PlatformAdmin`, `ComplianceOfficer`, or `BillingAgent`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record such an identifier — for example a `ComplianceOfficer`'s id is written to `verified_by_user_id` on the credential they accept, and a `BillingAgent`'s id is written to `issued_by_user_id` and `settled_by_user_id` on the invoices they act on — but it never compares an opaque id to any entity's `id`. The opaqueness of the `BillingAgent` identity is exactly what makes the invoice segregation-of-duties rule enforceable: a settlement whose `X-User-ID` equals the invoice's `issued_by_user_id` is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, with a minimum of 1 and a maximum of 100; a supplied `limit` below 1 is clamped up to 1, a `limit` above 100 is clamped down to 100, and a non-integer `limit` falls back to the default of 10, rather than any of these being rejected. `offset` defaults to 0 and has no upper bound beyond the size of the result set; a negative or non-integer `offset` falls back to 0. Results are ordered by `created_at` ascending unless a specific workflow states otherwise. Each list response carries `limit`, `offset`, `total_count` (the number of records matching the query before the page window is applied), and `has_more` (true when records remain beyond the current page) inside `meta`.

### 2.4. Common Resource Properties, Timestamps, and the Logical Clock

Every persisted resource carries a server-minted `id` — a UUID with no type prefix — and a `created_at` timestamp. All entities in this system also carry an `updated_at` timestamp and an integer `version`. `version` starts at 1 on creation and increments by exactly 1 on every mutation that the workflows below describe; `updated_at` is refreshed to the current instant on each such mutation while `created_at` never changes. Path-nested resources are validated left to right: for a path that names a facility and then one of its rate cards, the facility `id` is resolved first, and only if it resolves is the nested `id` checked, so that the error reflects the first unresolved segment.

Time in this system is driven entirely by a logical clock, never by wall-clock time. Before the clock is ever set it reads exactly `2026-05-01T00:00:00Z`. An administrative test-driving capability advances the clock to a supplied instant, and from that point every temporal rule — the claim window, credential expiry, cancellation lead, reliability decay, timesheet windows, and invoice due dates — reads the new instant. Every server-stamped timestamp is rendered from this logical clock in ISO 8601 UTC with exactly three fractional digits (for example `2026-05-01T00:00:00.000Z`). This applies to `created_at`, `updated_at`, and every event instant the system records: `claimed_at`, `awarded_at`, `confirmed_at`, `verified_at`, `occurred_at`, `adjudicated_at`, `issued_at`, and `due_at`. Client-supplied timestamp inputs, by contrast, are never renormalized: values a caller sends in a request body — including `issued_on` and `expires_on` on credentials, `scheduled_start` and `scheduled_end` on shifts, `window_start` and `window_end` on orders, `effective_from` and `effective_to` on rate cards, `clock_in` and `clock_out` on timesheets, and `period_start` and `period_end` on invoices — are stored and echoed back in the exact string form supplied, not reformatted to three fractional digits.

### 2.5. Optimistic Concurrency Control

Two write operations guard against acting on a stale view of a parent resource, and both use the parent's `version` as the concurrency token.

Awarding a shift requires the client to send `expected_shift_version` carrying the `version` of the target `Shift` as the scheduler last observed it. A shift's `version` advances every time its `claim_count` is recomputed — that is, whenever a new claim lands on it or an existing claim is withdrawn — so a mismatch means the candidate pool changed since the scheduler formed its ranking decision. When `expected_shift_version` does not equal the shift's current `version`, the award is rejected with `ERR_STALE_SHIFT_VERSION` (HTTP 412), and the scheduler must re-read the shift and re-decide.

Generating an invoice requires the client to send `expected_facility_version` carrying the `version` of the target `Facility` as the biller last observed it. A facility's `version` advances whenever `pending_pay_cents` changes — that is, whenever another timesheet is verified into the billable pool — so a mismatch means the set of billable work moved under the biller's feet. When `expected_facility_version` does not equal the facility's current `version`, generation is rejected with `ERR_STALE_FACILITY_VERSION` (HTTP 412), and the biller must re-read the facility first. No other endpoint takes a version field.

### 2.6. Monetary and Temporal Precision

All money is stored and computed in integer cents. Hour quantities — `scheduled_hours`, `worked_hours`, `night_hours`, `weekend_hours`, `regular_hours`, `overtime_hours`, and `cancellation_lead_hours` — are carried to two decimal places using round-half-up. Wherever rounding is applied to a money amount it is round-half-up to whole cents. A recurring and load-bearing rule in the pay and billing math is *where* the rounding happens: pay is assembled from separately rounded components rather than by rounding a single grand total, and a facility's bill is assembled by rounding each invoice line to whole cents first and then summing the rounded lines. The alternative of summing exact products and rounding once is explicitly not used and would produce different totals whenever two lines each carry a half-cent remainder. The individual formulas in Section 3 state exactly which quantities are rounded and in what order.

### 2.7. Validation Order and Error Precedence

When a request could fail more than one check, the checks are evaluated in a fixed priority order and the first failure determines the response. The ordering, from earliest to latest, is: authentication of the headers (`ERR_UNAUTHENTICATED`); role authorization for the endpoint (`ERR_UNAUTHORIZED`); existence of every `id` named in the path, resolved left to right (the not-found errors for facility, clinician, credential, order, shift, claim, assignment, timesheet, invoice, and reliability event); existence of every `id` named in the body (facility, clinician, or claim not-found); facility ownership scope for the two facility roles (`ERR_ROLE_SCOPE_VIOLATION`); clinician ownership (`ERR_NOT_OWNER`); billing segregation of duties on settlement (`ERR_SEGREGATION_OF_DUTIES`); body schema and field-range validation (`ERR_VALIDATION`); punch-interval validity (`ERR_INVALID_PUNCH_INTERVAL`); shift-duration validity (`ERR_SHIFT_DURATION_INVALID`); shift-within-order-window validity (`ERR_SHIFT_OUTSIDE_ORDER_WINDOW`); invoice-period validity (`ERR_INVOICE_PERIOD_INVALID`); the current-state gate for the requested transition (the various not-in-state errors); the timesheet single-submission gate (`ERR_ASSIGNMENT_NOT_CONFIRMED`); the clinician-active gate (`ERR_CLINICIAN_SUSPENDED`); the optimistic-concurrency check (`ERR_STALE_SHIFT_VERSION` or `ERR_STALE_FACILITY_VERSION`); then the domain-specific business gates described in Section 3, in the order they appear there — credential presence, credential expiry, claim window, shift-ended, timesheet window, duplicate claim, shift overlap, rest period, unit capacity, headcount, weekly hours, claim limit, rate-card availability, billable-timesheet availability, invoice-period overlap, eligible-claim availability, dispute limit, and payment-amount match. Each of these is described where its workflow lives; the point of this subsection is that they are strictly ordered, not independent.

### 2.8. Body Schema Validation

Every create or transition request is checked against its input schema after the auth and existence checks and before the state and business gates. A missing required field, a value of the wrong type, an invalid enum member, or an out-of-range number all raise `ERR_VALIDATION` (HTTP 400). The numeric bounds enforced here are: `unit_capacity` is an integer from 1 through 20; `headcount` is an integer from 1 through 20; `break_minutes` is an integer from 0 through 240; `base_pay_rate_cents_per_hour` is an integer from 1000 through 50000; and `required_credential_types` must be a non-empty array whose members come from the credential-type enumeration. A clinician's `email` must be unique across all clinicians, and a `(clinician_id, credential_type)` pair must be unique among that clinician's credentials that are not in the `REVOKED` state; a duplicate of either kind also raises `ERR_VALIDATION`.

### 2.9. Money Conservation Invariants

Three computed counters on each facility mirror the money moving through the system and must stay consistent with the events that drive them. `pending_pay_cents` is the sum of `gross_pay_cents` over the facility's timesheets that are `VERIFIED` — billable but not yet placed on an invoice. `outstanding_balance_cents` is the sum of `bill_total_cents` over the facility's invoices that are `ISSUED`; it is the conserved quantity behind the issue/void/settle compensating logic. `lifetime_billed_cents` is the sum of `bill_total_cents` over the facility's invoices that are `ISSUED` or `SETTLED`, and it is the sole input to the billing markup tier. Every workflow that issues, settles, or voids an invoice, and every verification that adds billable pay, adjusts these counters exactly as described in Section 3 so that they always equal the aggregate they represent.

## 3. Business Logic & Workflows

### 3.1. Facilities, Units, and Rate Cards

A `PlatformAdmin` registers a facility by supplying its display `name` (1 to 120 characters), the single staffed `unit_name` it schedules through the float pool (1 to 60 characters), the `unit_capacity` of that unit, and the `required_credential_types` a clinician must hold to work there. `unit_capacity` is the maximum number of the facility's shifts whose intervals may overlap at any instant, and it must be from 1 through 20. `required_credential_types` is a non-empty list drawn from the credential types `RN_LICENSE`, `BLS`, `ACLS`, `TB_SCREENING`, and `FIT_TEST`. On registration the three money counters `pending_pay_cents`, `outstanding_balance_cents`, and `lifetime_billed_cents` all start at 0.

Pay rates live on rate cards, which either a `PlatformAdmin` or the owning `FacilityScheduler` publishes against a facility. A rate card names the `specialty` it covers — one of `RN`, `LPN`, `CNA`, `RT`, or `PT` — a `base_pay_rate_cents_per_hour` between 1000 and 50000 inclusive, an inclusive `effective_from` instant, and an optional `effective_to` instant that, when omitted, leaves the card open-ended. `effective_from` is the inclusive start and `effective_to`, when present, is the exclusive end of the window in which the card is selectable. When a shift is later posted, the system chooses among the facility's cards for that specialty whose `effective_from` is at or before the shift's start and whose `effective_to` is either absent or strictly after the shift's start; of those, it takes the card with the greatest `effective_from`, breaking a tie by the greatest `created_at`. If no card qualifies, shift posting fails with `ERR_RATE_CARD_NOT_FOUND`.

### 3.2. Clinician Onboarding and the Credential Lifecycle

A `PlatformAdmin` registers a per-diem clinician with a `full_name` (1 to 120 characters), a unique `email`, and a `specialty` from the same five-member enumeration used by rate cards. A new clinician begins with `status` `ACTIVE`, a `reliability_score` of 100, and a `provisional_reliability_score` of 100; the derived `no_show_count` and `completed_shift_count` both start at 0.

A clinician (or a `PlatformAdmin` acting for them) attaches a credential by supplying its `credential_type`, a `license_number` (1 to 40 characters) identifying the issuing body, an `issued_on` instant, and an `expires_on` instant that must be strictly after `issued_on`. A newly attached credential enters `PENDING_VERIFICATION` and confers no eligibility; its `status`, `verified_at`, `verified_by_user_id`, and `decision_note` remain at their initial values (the last three null) until a `ComplianceOfficer` acts. Only a `ComplianceOfficer` may verify, reject, or revoke a credential.

Verification carries a `decision`, an optional replacement `expires_on`, and an optional `note`. When a `ComplianceOfficer` verifies a credential that is in `PENDING_VERIFICATION` with a decision of `VERIFIED`, the credential moves `PENDING_VERIFICATION → VERIFIED` provided its expiry lies in the future: if the call supplies a new `expires_on` it must be strictly after the current clock instant, otherwise the stored `expires_on` must be strictly after the current clock instant. The transition sets `status` to `VERIFIED`, records `verified_at` as the current instant and `verified_by_user_id` as the officer's opaque id, applies the supplied `expires_on` when one was sent, and bumps the credential's `version`. A decision of `REJECTED` from `PENDING_VERIFICATION` moves the credential `PENDING_VERIFICATION → REJECTED`, storing the `note` into `decision_note` and bumping `version`; `REJECTED` is terminal, so a clinician who wants to retry must attach a fresh credential row. Verifying or rejecting a credential that is not in `PENDING_VERIFICATION` (and not, per the renewal case below, in `EXPIRED`) is refused with `ERR_CREDENTIAL_NOT_PENDING`.

A verified credential lapses on its own timeline. Whenever a credential is read or consulted during a compliance check and the current clock instant is at or after its `expires_on`, it is lazily moved `VERIFIED → EXPIRED`, setting `status` to `EXPIRED` and bumping `version`. This materialization happens both when a clinician's credentials are listed and on every compliance evaluation, so expiry is observable without any batch job. An `EXPIRED` credential is renewed in place rather than replaced: a `ComplianceOfficer` verifying it with a decision of `VERIFIED` and a supplied `expires_on` strictly after the current instant moves it `EXPIRED → VERIFIED`, updating `expires_on`, `verified_at`, and `verified_by_user_id` and bumping `version`. This VERIFIED → EXPIRED → VERIFIED loop is the credential renewal cycle.

Revocation carries a `reason`. A `ComplianceOfficer` may revoke a credential whose `status` is either `VERIFIED` or `EXPIRED`, moving it to `REVOKED`, writing the `reason` into `decision_note`, and bumping `version`; `REVOKED` is terminal and immediately removes eligibility everywhere that credential type is required. Attempting to revoke a credential that is neither `VERIFIED` nor `EXPIRED` is refused with `ERR_CREDENTIAL_NOT_PENDING`.

### 3.3. Staffing Orders and Posting Shift Slots

A `FacilityScheduler` opens a staffing order against its own facility. The request carries the `facility_id` (which must equal the scheduler's `X-User-ID`), the `specialty` requested, a `headcount` of slots to authorize, an `urgency` of either `STANDARD` or `CRISIS`, and the `window_start` and `window_end` bounding when shifts may be scheduled. `headcount` must be from 1 through 20. A new order is created in `status` `OPEN` with all five of its counters — `shift_count`, `open_count`, `filled_count`, `completed_count`, and `cancelled_count` — at 0. `urgency` of `CRISIS` will later multiply the base pay rate; `STANDARD` will not.

Each shift slot is posted under an order by the scheduler and carries a `scheduled_start` and a `scheduled_end`. The interval `[scheduled_start, scheduled_end)` is treated as inclusive of the start and exclusive of the end. Several checks guard the post, in the order given. The shift's duration — the span from `scheduled_start` to `scheduled_end` — must be at least 4 hours and at most 16 hours, and `scheduled_end` must be strictly after `scheduled_start`; a violation raises `ERR_SHIFT_DURATION_INVALID`. The shift must sit inside the order's window, meaning `scheduled_start` is at or after `window_start` and `scheduled_end` is at or before `window_end`; otherwise `ERR_SHIFT_OUTSIDE_ORDER_WINDOW`. A unit-capacity check then counts, including the shift being created, how many of the facility's shifts in `OPEN`, `ASSIGNED`, or `COMPLETED` status have a closed interval `[scheduled_start, scheduled_end]` that intersects the new shift's closed interval; if that count exceeds the facility's `unit_capacity`, it fails with `ERR_UNIT_CAPACITY_EXCEEDED`. Note that under this capacity rule, touching endpoints — where one shift ends exactly when another begins — do count as intersecting. Finally, the order's `shift_count` excluding cancelled shifts, plus the shift being created, must not exceed the order's `headcount`, or the post fails with `ERR_HEADCOUNT_EXCEEDED`. Posting a shift under an order that is `CLOSED` or `CANCELLED` is refused with `ERR_ORDER_NOT_OPEN`.

Posting a shift also freezes its economics. The system selects the rate card for the facility, the order's specialty, and the shift's start as described in 3.1, snapshots that card's `base_pay_rate_cents_per_hour` onto the shift's own `base_pay_rate_cents_per_hour`, and computes the frozen `effective_rate_cents_per_hour`: when the order's urgency is `CRISIS`, the effective rate is the base rate multiplied by 1.25 and rounded half-up to whole cents once; otherwise the effective rate equals the base rate. Later edits to rate cards never re-rate an existing shift. The shift's `scheduled_hours` is the span from `scheduled_start` to `scheduled_end` expressed in hours to two decimals. Its `estimated_hours` is the scheduled hours minus the deemed unpaid break. Its `estimated_pay_cents` is the estimated pay computed over the scheduled interval (described in 3.6 as the estimated variant, with no overtime). A newly posted shift enters `status` `OPEN` with `claim_count` at 0, records its parent through `order_id`, and the parent order's fill posture is recomputed.

The parent order's fill posture is a derived aggregate recomputed after every award, every assignment release, every shift completion, and every order cancel. It recounts `shift_count` (all shifts of the order), `open_count` (shifts in `OPEN`), `filled_count` (shifts in `ASSIGNED` or `COMPLETED`), `completed_count` (shifts in `COMPLETED`), and `cancelled_count` (shifts in `CANCELLED`); these counters always satisfy `shift_count` equals `open_count` plus `filled_count` plus `cancelled_count`. The order's `status` is then derived: it is `CANCELLED` if the order was explicitly cancelled; otherwise `CLOSED` when it has at least one shift, no open shifts remain, every filled shift is completed, and completed plus cancelled shifts account for all of them; otherwise `FILLED` when the filled count equals the `headcount`; otherwise `PARTIALLY_FILLED` when the filled count is above 0; otherwise `OPEN`. This is why an order cycles `OPEN → PARTIALLY_FILLED → FILLED` as slots fill, can return `FILLED → PARTIALLY_FILLED → OPEN` as assignments are released, and settles into `CLOSED` once every shift is terminal. Each recompute that changes the counters bumps the order's `version`.

### 3.4. Self-Scheduling: Claims and the Eligibility Gate Stack

A clinician self-schedules by claiming an open shift, supplying their own `clinician_id` (which must equal the acting clinician's `X-User-ID`) and an optional free-text `note`. A claim is only accepted on a shift whose `status` is `OPEN`; a claim against any other shift state is refused with `ERR_SHIFT_NOT_OPEN`. The claiming clinician must be `ACTIVE`; a suspended clinician is refused with `ERR_CLINICIAN_SUSPENDED`. Beyond those, a stack of eligibility gates runs in a fixed order, and the accepted claim records `claimed_at` as the current instant and snapshots the clinician's current `reliability_score` into `reliability_snapshot` (retained for audit only — it is not used to rank the claim later). A new claim enters `status` `PENDING`, then `Shift.claim_count` is recomputed and the shift's `version` is bumped.

The gates, in evaluation order, are as follows. The credential compliance gate has two legs: the clinician must hold, for every credential type in the facility's `required_credential_types`, a credential of that type in `VERIFIED` status, or the claim fails with `ERR_CREDENTIAL_MISSING`; and each such required credential must remain valid through the shift, meaning its `expires_on` is at or after the shift's `scheduled_end` plus a one-day buffer, or the claim fails with `ERR_CREDENTIAL_EXPIRED`. A credential whose `expires_on` is at or before the current instant is first materialized to `EXPIRED` and then fails the expiry leg. Next, the claim window must be open: the current instant must be at or before the shift's `scheduled_start` minus 2 hours; exactly at that lock instant a claim is still accepted, but one second later it is refused with `ERR_CLAIM_WINDOW_CLOSED`. Next, the clinician must not already hold a claim on this shift in `PENDING` or `AWARDED` status, or it fails with `ERR_DUPLICATE_CLAIM`. Next comes the shift-overlap gate: the target shift's half-open interval `[scheduled_start, scheduled_end)` must not intersect the half-open interval of any other shift the clinician already occupies through an assignment whose `work_status` is `PENDING_CONFIRMATION`, `CONFIRMED`, or `WORKED`; a violation raises `ERR_SHIFT_OVERLAP`. Back-to-back shifts, where one ends exactly when the next starts, do not intersect under this overlap rule. Next, the rest gate: the gap between the target shift and every adjacent occupied shift of the same clinician (again, occupied means an assignment in `PENDING_CONFIRMATION`, `CONFIRMED`, or `WORKED`) must be at least 8 hours; a gap of exactly 8.00 hours passes, and anything less raises `ERR_REST_PERIOD_VIOLATION`. Next, the weekly-hours gate: the clinician's total `scheduled_hours` across occupied shifts falling in the target shift's ISO week, plus the target shift's own `scheduled_hours`, must not exceed 60 hours; exactly 60.00 passes, and more raises `ERR_WEEKLY_HOURS_EXCEEDED`. Finally, the claim-quota gate: the clinician must currently hold fewer than 5 claims in `PENDING` status, or the claim is refused with `ERR_CLAIM_LIMIT_EXCEEDED`.

A clinician may withdraw one of their own pending claims. Withdrawal is permitted only on a claim in `PENDING` status and only by the owning clinician; it moves the claim `PENDING → WITHDRAWN`, bumps the claim's `version`, then recomputes `Shift.claim_count` and bumps the shift's `version`. Withdrawing a claim that is not `PENDING` is refused with `ERR_CLAIM_NOT_PENDING`. A withdrawn, declined, or awarded claim never re-enters the candidate pool.

### 3.5. Awarding, Confirmation, and the Assignment Lifecycle

A `FacilityScheduler` fills a slot by awarding it. Because the award decision is made against a candidate pool that other claims and withdrawals can shift, the request must carry `expected_shift_version` matching the shift's current `version`, failing with `ERR_STALE_SHIFT_VERSION` when the shift has advanced (see 2.5). An award is only valid on a shift in `OPEN` status whose parent order is `OPEN` or `PARTIALLY_FILLED`; an award on any other shift state raises `ERR_SHIFT_NOT_OPEN`. The award may optionally name a `claim_id`. When `claim_id` is supplied, that single named claim is the pool: it must be `PENDING`, belong to this shift, and individually pass every eligibility predicate (the credential presence and expiry legs, the overlap gate, the rest gate, and the weekly-hours gate), and if any predicate fails the corresponding gate error is raised rather than a generic one. When `claim_id` is omitted, the server evaluates the whole pool: it filters to the shift's `PENDING` claims whose clinician is `ACTIVE` and passes the credential, overlap, rest, and weekly-hours gates, then ranks the survivors by live `reliability_score` descending, breaking ties by earliest `claimed_at` and then earliest `created_at`, and takes the top candidate. Note that the ranking reads the clinician's live `reliability_score`, not the `reliability_snapshot` frozen on the claim. If the filtered pool is empty, the award fails with `ERR_NO_ELIGIBLE_CLAIM`. A suspended clinician's claim is never eligible, and an award naming such a clinician's claim is refused with `ERR_CLINICIAN_SUSPENDED`.

A successful award creates an `Assignment` on the shift. The assignment records its `shift_id`, the winning claim's `clinician_id`, and the winning `claim_id`, enters `work_status` `PENDING_CONFIRMATION` and `pay_status` `UNBILLED`, records `awarded_at` as the current instant, and copies the shift's `estimated_pay_cents` onto its own `estimated_pay_cents` (its `final_pay_cents` stays null and its `confirmed_at`, `cancellation_lead_hours`, and `cancellation_reason` remain unset). When the slot being awarded had previously carried an assignment that was released back to `OPEN`, the new assignment's `replaces_assignment_id` is set to that prior assignment; on a first fill it stays null. The award sets the winning claim `PENDING → AWARDED` and every other `PENDING` claim on the shift `PENDING → DECLINED`, recomputes `Shift.claim_count`, moves the shift `OPEN → ASSIGNED`, bumps the shift's `version`, and triggers the parent order's fill-posture recompute.

The two axes of an assignment evolve independently. The `work_status` axis captures attendance, running from `PENDING_CONFIRMATION` through `CONFIRMED` to the terminal `WORKED`, or into one of the terminal cancellation outcomes `CANCELLED_BY_CLINICIAN`, `CANCELLED_BY_FACILITY`, or `NO_SHOW`. The `pay_status` axis captures money, running `UNBILLED → TIMESHEET_PENDING → PAYABLE → INVOICED → PAID`, with `WAIVED` as the terminal reached when the work axis is cancelled or no-showed. The pay axis is also cyclic between `INVOICED` and `PAYABLE`: voiding an invoice returns `INVOICED → PAYABLE`.

The awarded clinician confirms attendance before the shift starts. Confirmation is permitted only by the assigned clinician, only while the assignment is in `PENDING_CONFIRMATION`, only while the clinician is `ACTIVE`, and only before the shift's `scheduled_start`; it moves `work_status` `PENDING_CONFIRMATION → CONFIRMED`, records `confirmed_at`, bumps the assignment's `version`, and leaves the pay axis untouched. Confirming a suspended clinician's assignment raises `ERR_CLINICIAN_SUSPENDED`; confirming an assignment whose work axis is anything other than `PENDING_CONFIRMATION` — whether an already-terminal outcome or an already-`CONFIRMED` assignment — raises `ERR_ASSIGNMENT_NOT_CANCELLABLE`. This work-axis state gate is checked before the clinician-active gate, so a non-`PENDING_CONFIRMATION` assignment yields `ERR_ASSIGNMENT_NOT_CANCELLABLE` even when the clinician is suspended.

Either the assigned clinician or the owning facility scheduler may cancel an assignment, supplying a `reason`. Cancellation is permitted while the work axis is `PENDING_CONFIRMATION` or `CONFIRMED`; attempting it once that axis is terminal raises `ERR_ASSIGNMENT_NOT_CANCELLABLE`. A cancellation computes `cancellation_lead_hours` as the span from the current instant to the shift's `scheduled_start`, expressed in hours to two decimals, and sets `pay_status` to `WAIVED` and `cancellation_reason` to the supplied `reason`. When the assigned clinician cancels, the work axis moves to `CANCELLED_BY_CLINICIAN`, and the reliability consequence follows the cancellation tier: if the lead is at least 72 hours, no reliability event is recorded at all; if the lead is at least 24 hours but under 72, a `LATE_CANCELLATION` penalty event worth 5 points is appended in `PENDING`; if the lead is under 24 hours, including any negative lead, a `VERY_LATE_CANCELLATION` penalty event worth 15 points is appended in `PENDING`. These boundaries fall on the cheaper side: a lead of exactly 72.00 hours is free, exactly 24.00 hours is the 5-point tier, and 23.99 hours is the 15-point tier. When the facility scheduler cancels, the work axis moves to `CANCELLED_BY_FACILITY`, and instead of a penalty, a `FACILITY_CANCELLATION_CREDIT` event worth 2 credit points is appended already `CONFIRMED` regardless of the lead. In both cancellation cases the affected clinician's reliability is then recomputed, the shift returns `ASSIGNED → OPEN` so the slot can be backfilled, the order's fill posture is recomputed, and the assignment's `version` is bumped.

A `FacilityVerifier` records a no-show when a confirmed clinician fails to appear, optionally supplying a `note`. A no-show is only valid on an assignment whose `work_status` is `CONFIRMED` and only once the current instant is at or after the shift's `scheduled_start`; a no-show against an assignment not in `CONFIRMED` raises `ERR_ASSIGNMENT_NOT_CONFIRMED`. The no-show cascade sets `work_status` to `NO_SHOW` and `pay_status` to `WAIVED`; appends a `NO_SHOW` penalty event worth 30 points in `PENDING`; recomputes the clinician's reliability, which — because the provisional score may now fall below the suspension threshold — can move the clinician `ACTIVE → SUSPENDED` and, on suspension, decline all of that clinician's `PENDING` claims (recomputing `Shift.claim_count` on each affected shift); returns the shift `ASSIGNED → OPEN`; recomputes the order's fill posture; and bumps the assignment's `version`.

### 3.6. Timesheets: Submission, Dispute, Verification, and Pay

After a shift has ended, the assigned clinician submits a timesheet with the actual `clock_in`, `clock_out`, and reported `break_minutes` (from 0 through 240). A timesheet may be submitted only once per assignment, and only when the assignment's `work_status` is `CONFIRMED` and its `pay_status` is `UNBILLED`; a second submission or a submission against an unconfirmed assignment raises `ERR_ASSIGNMENT_NOT_CONFIRMED`. Submission is also gated temporally: the current instant must be at or after the shift's `scheduled_end`, or it fails with `ERR_SHIFT_NOT_ENDED`, and it must be within 7 days after the shift's `scheduled_end`, or it fails with `ERR_TIMESHEET_WINDOW_CLOSED`. The punch interval itself is validated: `clock_out` must be strictly after `clock_in`, and the punched interval must lie within the shift's scheduled interval widened by 4 hours on each side — that is, no earlier than `scheduled_start` minus 4 hours and no later than `scheduled_end` plus 4 hours — or the request fails with `ERR_INVALID_PUNCH_INTERVAL`.

On submission the system normalizes the hours. `raw_minutes` is the whole number of minutes between `clock_in` and `clock_out`. The deemed unpaid break, `unpaid_break_minutes`, is 30 minutes when `raw_minutes` is at least 360 and the reported `break_minutes` is under 30; otherwise it equals the reported `break_minutes`. In effect, a short shift under 360 raw minutes with a reported break of 0 keeps a zero break, while a long shift with an under-reported break is force-deducted to 30 minutes. `worked_hours` is then `raw_minutes` minus `unpaid_break_minutes`, divided by 60, to two decimals. The differential hours are measured over the raw clocked interval `[clock_in, clock_out)` — the unpaid break is deliberately not deducted from differential hours. `night_hours` is the count of minutes of that interval whose UTC wall time falls in the night window, which runs from 19:00 up to midnight and from midnight up to 07:00, divided by 60 to two decimals. `weekend_hours` is the count of minutes of that interval whose UTC calendar day is Saturday or Sunday, divided by 60 to two decimals. The two windows can overlap: a minute at, say, 22:00 on a Saturday counts toward both and earns both differentials. Because the interval is half-open, a shift ending exactly at 19:00 contributes zero night minutes for that boundary. On submission the assignment moves `work_status` `CONFIRMED → WORKED`, the clinician's `completed_shift_count` increments by 1, and the assignment's `pay_status` moves `UNBILLED → TIMESHEET_PENDING`. A new timesheet enters `status` `SUBMITTED` with `dispute_count` at 0.

A `FacilityVerifier` for the owning facility can dispute a submitted timesheet, supplying a `reason`. A dispute is valid only on a timesheet in `SUBMITTED` status and only while `dispute_count` is below 2; it moves the timesheet `SUBMITTED → DISPUTED`, stores the `reason` into `dispute_reason`, increments `dispute_count` by 1, and bumps `version`. Disputing a timesheet that is not `SUBMITTED` raises `ERR_TIMESHEET_NOT_DISPUTABLE`, and a third dispute attempt — one made when `dispute_count` has already reached 2 — is refused with `ERR_DISPUTE_LIMIT_REACHED`. The disputed timesheet is bounced back to the clinician, who resubmits corrected `clock_in`, `clock_out`, and `break_minutes`. Resubmission is valid only on a timesheet in `DISPUTED` status and only by the timesheet's own clinician; it overwrites the three punch inputs, recomputes `raw_minutes`, `unpaid_break_minutes`, `worked_hours`, `night_hours`, and `weekend_hours`, and moves the timesheet `DISPUTED → SUBMITTED`, bumping `version`. Crucially, `dispute_count` is not reset on resubmission — that is what bounds the dispute/resubmit loop to at most two rounds. Resubmitting a timesheet that is not `DISPUTED` raises `ERR_TIMESHEET_NOT_RESUBMITTABLE`.

A `FacilityVerifier` for the owning facility verifies a submitted timesheet, which is where final pay is computed. Verification is valid only on a timesheet in `SUBMITTED` status whose assignment's `work_status` is `WORKED`; a verify against a timesheet not in `SUBMITTED` raises `ERR_TIMESHEET_NOT_VERIFIABLE`. Verification first allocates weekly overtime, then computes final pay. The overtime allocation finds the ISO week of the shift — the week starting at the most recent Monday 00:00:00Z at or before the shift's `scheduled_start` and running seven days as a half-open interval — and sums the `worked_hours` of the same clinician's *other* timesheets that are already `VERIFIED`, `INVOICED`, or `PAID` at this instant and whose own shift's `scheduled_start` falls in that week. Call that sum the prior cumulative. This timesheet's `overtime_hours` is the portion of its `worked_hours` that pushes the running weekly total past 40 hours: it is the smaller of this timesheet's `worked_hours` and (the prior cumulative plus this timesheet's `worked_hours` minus 40), floored at zero, to two decimals. Its `regular_hours` is `worked_hours` minus `overtime_hours`, to two decimals. The 40-hour boundary is strict: when the prior cumulative plus this timesheet's `worked_hours` equals exactly 40.00, `overtime_hours` is 0.00, and at 40.01 it is 0.01. Only already-verified siblings count toward the prior cumulative — `SUBMITTED` and `DISPUTED` siblings are excluded — so the accumulator advances in verification order, and once written, `overtime_hours` and `regular_hours` are frozen and not retro-adjusted when a later sibling is verified.

Final pay, written to the timesheet's `gross_pay_cents`, is the sum of three separately rounded components computed from the frozen `effective_rate_cents_per_hour` of the shift. The regular component is `regular_hours` times the effective rate, rounded half-up to whole cents. The overtime component is `overtime_hours` times the effective rate times 1.5, rounded half-up to whole cents. The differential component is the sum of two independently rounded pieces: `night_hours` times 450 cents per hour rounded half-up, plus `weekend_hours` times 300 cents per hour rounded half-up. `gross_pay_cents` is the sum of the regular, overtime, and differential components; the rounding is applied per component and never to the final sum. This is the final variant of the pay calculation. The estimated variant, computed at shift posting and carried onto the assignment at award, is the same formula applied to the scheduled interval with the unpaid break deemed the same way from the scheduled duration, with `overtime_hours` forced to 0.00 because a shift is estimated standalone with no knowledge of the week, and with differential hours drawn from the scheduled interval. When the scheduled and actual intervals coincide and no weekly overtime applies, the two variants agree; any punch drift or weekly overtime makes them diverge.

Verification then fires its cascade. The timesheet moves `SUBMITTED → VERIFIED`, recording `verified_at`. Because the timesheet became verified, the assignment's pay axis moves `TIMESHEET_PENDING → PAYABLE`, the assignment's `final_pay_cents` is set to the timesheet's `gross_pay_cents`, and the facility's `pending_pay_cents` grows by `gross_pay_cents` while the facility's `version` bumps. Because the assignment reached `PAYABLE`, its shift moves `ASSIGNED → COMPLETED`, which triggers the parent order's fill-posture recompute and can move the order to `CLOSED` once every sibling shift is terminal. Verification also appends a `SHIFT_COMPLETED` credit event worth 2 points already `CONFIRMED` and recomputes the clinician's reliability. The timesheet's `version` is bumped.

### 3.7. Reliability Scoring and Adjudication

Every clinician carries a reliability score that decays with time and is recomputed whenever a reliability event is appended (by a late cancellation, a no-show, a facility-cancellation credit, or a shift completion) and whenever a `ComplianceOfficer` adjudicates an event. Each `ReliabilityEvent` records the `clinician_id` it scores, the `assignment_id` that produced it, its `event_type`, its `penalty_points` and `credit_points` (one of which is non-zero, the other 0), the `occurred_at` instant it was appended, its `adjudication_status`, an `adjudicated_at` instant, and a human-readable `reason`. Penalty events (`LATE_CANCELLATION`, `VERY_LATE_CANCELLATION`, `NO_SHOW`) are appended in `PENDING`; credit events (`SHIFT_COMPLETED`, `FACILITY_CANCELLATION_CREDIT`) are appended directly in `CONFIRMED` and never pass through adjudication.

The recompute weights each in-window event by age. The age of an event in whole days is the floor of the span from the event's `occurred_at` to the current instant divided by one day. An event aged 30 days or fewer carries full weight 1.0; aged 60 days or fewer, weight 0.6; aged 90 days or fewer, weight 0.3; older than 90 days, it is excluded entirely. Two variants of the score are produced from a base of 100. Starting from 100, for each of the clinician's events whose `occurred_at` falls in the trailing 90-day window (inclusive at both ends — at or after the current instant minus 90 days and at or before the current instant), the score is reduced by the event's `penalty_points` times its weight and increased by its `credit_points` times its weight; the result is rounded half-up and then clamped between 0 and 100. The adjudicated variant, written to `reliability_score`, counts only `CONFIRMED` events; this is also the value snapshotted onto a claim's `reliability_snapshot`. The provisional variant, written to `provisional_reliability_score`, counts both `PENDING` and `CONFIRMED` events, so a freshly recorded, still-pending no-show immediately depresses it. Immediately after a first no-show on an otherwise clean clinician, the adjudicated score reads 100 and the provisional score reads 70. `OVERTURNED` events are excluded from both variants. The clinician's `no_show_count` is the count of in-window events whose `event_type` is `NO_SHOW` and whose `adjudication_status` is `CONFIRMED`.

The provisional score drives suspension. When a recompute leaves the provisional score below 60, an `ACTIVE` clinician moves `ACTIVE → SUSPENDED`, all of that clinician's `PENDING` claims are set to `DECLINED` (with `Shift.claim_count` recomputed on each affected shift), and the clinician's `version` bumps. When a later recompute returns the provisional score to 60 or above, a `SUSPENDED` clinician moves `SUSPENDED → ACTIVE` and the `version` bumps; reinstatement does not resurrect the claims declined at suspension time, so the clinician must claim again.

A `ComplianceOfficer` adjudicates a pending penalty event with a `decision`. A decision of `CONFIRMED` moves the event `PENDING → CONFIRMED`, records `adjudicated_at`, and recomputes the clinician's reliability (rewriting `reliability_score`, `provisional_reliability_score`, and `no_show_count`, and possibly moving the clinician's status). A decision of `OVERTURNED` moves the event `PENDING → OVERTURNED`, records `adjudicated_at`, and recomputes reliability with that event now excluded from both variants, so the provisional score returns exactly to its pre-event value and any suspension the event caused is reversed. Adjudicating an event whose `adjudication_status` is not `PENDING` is refused with `ERR_EVENT_ALREADY_ADJUDICATED`.

The four-link order-cancel cascade ties this section back to 3.3. When a `FacilityScheduler` cancels an order whose `status` is `OPEN`, `PARTIALLY_FILLED`, or `FILLED` (and whose `facility_id` matches the scheduler's `X-User-ID`), the first link sets every shift under the order whose `status` is `OPEN` or `ASSIGNED` to `CANCELLED`. The second link, because those shifts became cancelled, moves every assignment on them whose `work_status` is `PENDING_CONFIRMATION` or `CONFIRMED` to `CANCELLED_BY_FACILITY` and its pay axis to `WAIVED`. The third link, because those assignments were facility-cancelled, appends one `FACILITY_CANCELLATION_CREDIT` event worth 2 credit points already `CONFIRMED` per cancelled assignment. The fourth link, because those events were appended, runs the reliability recompute for each affected clinician, rewriting both score variants and, when the provisional score crosses back to 60 or above, reinstating a suspended clinician. Every remaining `PENDING` claim on the cancelled shifts is set to `DECLINED` with `Shift.claim_count` recomputed, the order moves to `CANCELLED` with its five counters refreshed, and its `version` bumps. Cancelling an order that is already `CLOSED` or `CANCELLED` is refused with `ERR_ORDER_NOT_OPEN`.

### 3.8. Billing: Invoice Generation, Issue, Settlement, and Void

A `BillingAgent` generates a draft invoice for a facility over a billing period, supplying the `facility_id`, the `period_start`, the `period_end`, and `expected_facility_version` (the concurrency token of 2.5). The period is half-open, inclusive of `period_start` and exclusive of `period_end`. `period_end` must be strictly after `period_start` and the span must be at most 31 days, or the request fails with `ERR_INVOICE_PERIOD_INVALID`. The requested period must not intersect the period of any existing invoice of the facility in `DRAFT`, `ISSUED`, or `SETTLED` status, or it fails with `ERR_INVOICE_PERIOD_OVERLAP`. At least one billable timesheet must fall in the period, or it fails with `ERR_NO_BILLABLE_TIMESHEETS`.

Generation first freezes the markup. The tier is chosen once from the facility's `lifetime_billed_cents` as it stands *before* this invoice contributes to it — draft invoices contribute nothing, and the invoice being generated has not yet been issued. When that basis is under 200000 cents, the invoice's `markup_tier` is `TIER_1` and its `markup_multiplier` is 1.45; when the basis is from 200000 through 499999 cents, the tier is `TIER_2` and the multiplier is 1.38; when the basis is 500000 cents or more, the tier is `TIER_3` and the multiplier is 1.32. The tier boundaries are half-open, so a basis of exactly 200000 selects `TIER_2` and exactly 500000 selects `TIER_3`. The frozen `markup_tier` and `markup_multiplier` are never re-derived at issue or settle time.

Generation then builds the lines. The billable set is the facility's timesheets in `VERIFIED` status whose shift's `scheduled_start` falls in the half-open period; `SUBMITTED`, `DISPUTED`, `INVOICED`, and `PAID` timesheets are excluded. The billable set is ordered by the line's shift `scheduled_start` ascending, breaking ties by the timesheet's `created_at` ascending. Each line is an object `{ timesheet_id, worked_hours, pay_cents, bill_cents }`, where `pay_cents` is the timesheet's `gross_pay_cents` and `bill_cents` is `pay_cents` times the frozen `markup_multiplier`, rounded half-up to whole cents *per line*. The invoice's `lines` holds these objects, `line_count` is their number, `pay_total_cents` is the sum of the lines' `pay_cents`, and `bill_total_cents` is the sum of the lines' already-rounded `bill_cents` — rounding each line first and then summing, not summing exact products and rounding once. `margin_cents` is `bill_total_cents` minus `pay_total_cents`. As part of generation, each swept timesheet moves `VERIFIED → INVOICED` with its `invoice_id` set to the new invoice, each corresponding assignment's pay axis moves `PAYABLE → INVOICED`, the facility's `pending_pay_cents` decreases by `pay_total_cents`, and the facility's `version` bumps. A new invoice enters `status` `DRAFT` with `issued_by_user_id`, `issued_at`, `due_at`, `settled_by_user_id`, `paid_amount_cents`, and `void_reason` all null.

A `BillingAgent` issues a draft invoice that has at least one line. Issuing a draft with no lines, or issuing anything not in `DRAFT` status, is refused with `ERR_INVOICE_NOT_DRAFT`. Issuance moves the invoice `DRAFT → ISSUED`, records `issued_at` as the current instant, `issued_by_user_id` as the agent's opaque id, and `due_at` as the issue instant plus 30 days, then increases the facility's `outstanding_balance_cents` and `lifetime_billed_cents` each by `bill_total_cents` and bumps both the facility's and the invoice's `version`.

Settlement records payment on an issued invoice and enforces segregation of duties. A `BillingAgent` settles by supplying `paid_amount_cents`. The settling agent's `X-User-ID` must differ from the invoice's `issued_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. The invoice must be in `ISSUED` status, or the request is refused with `ERR_INVOICE_NOT_ISSUED`. The supplied `paid_amount_cents` must equal the invoice's `bill_total_cents` exactly, or it is refused with `ERR_PAYMENT_AMOUNT_MISMATCH`. Settlement moves the invoice `ISSUED → SETTLED`, records `settled_by_user_id` and `paid_amount_cents`, decreases the facility's `outstanding_balance_cents` by `bill_total_cents` (its `lifetime_billed_cents` is unchanged), moves every line's timesheet `INVOICED → PAID` and every corresponding assignment's pay axis `INVOICED → PAID`, and bumps the facility's and the invoice's `version`.

Voiding reverses an invoice. A `BillingAgent` voids an invoice in `DRAFT` or `ISSUED` status, supplying a `reason`; voiding a `SETTLED` or already-`VOID` invoice is refused with `ERR_INVOICE_NOT_VOIDABLE`. A void moves the invoice to `VOID`, storing the `reason` into `void_reason`, returns every line's timesheet `INVOICED → VERIFIED` with its `invoice_id` cleared, returns every corresponding assignment's pay axis `INVOICED → PAYABLE`, increases the facility's `pending_pay_cents` by `pay_total_cents`, and bumps the facility's and the invoice's `version`. When the invoice being voided had already been issued, the void additionally decreases the facility's `outstanding_balance_cents` and `lifetime_billed_cents` each by `bill_total_cents`, restoring both to their pre-issue values.

Timesheet submission and resubmission accept `clock_in`, `clock_out`, and `break_minutes`; dispute accepts a `reason`; verify takes no body. Credential verification accepts `decision`, an optional `expires_on`, and an optional `note`; revocation accepts a `reason`; adjudication accepts a `decision`. Invoice generation accepts `facility_id`, `period_start`, `period_end`, and `expected_facility_version`; settlement accepts `paid_amount_cents`; void accepts a `reason`. The clock endpoint accepts `to_iso8601` and returns the new `current_utc`. List endpoints accept `limit` and `offset`; additionally, rate-card listing accepts `specialty`; credential, order, shift, timesheet, and invoice listings accept `status`; claim listing accepts `shift_id`, `clinician_id`, and `status`; assignment listing accepts `shift_id`, `clinician_id`, `claim_id`, `replaces_assignment_id`, `work_status`, and `pay_status`; and the clinician reliability-events listing accepts `event_type` and `adjudication_status`.
