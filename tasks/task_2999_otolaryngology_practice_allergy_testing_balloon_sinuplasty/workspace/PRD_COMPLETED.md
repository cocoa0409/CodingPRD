# Ent Practice Ops API — Product Requirements Document

## 1. Introduction

A modern otolaryngology practice is really five businesses sharing one waiting room. The allergy clinic mixes and administers patient-specific extract, and every millilitre it draws has to be accounted for. The endoscopy suite runs in-office balloon sinuplasty, which no payer will cover without a documented history of failed medical management. The audiology and sleep service dispenses hearing aids and oral appliances on trial, and money flows back out of the practice when a patient returns one. Sterile processing owns the flexible scopes, and a scope that fails two disinfection runs in a row has to disappear from the schedule before it touches another patient. Pediatric tube and tonsil cases have to be pushed out to a partner surgery center when the child is too young for the office suite. Today each of these lives in a different spreadsheet, and the seams between them are where patients get hurt and claims get denied.

This document specifies the **ENT Practice Operations API**, a single service that holds all five workflows and, more importantly, holds the couplings between them. A grade-3 systemic reaction recorded during an immunotherapy visit must not merely be filed: it has to roll the patient's escalation schedule back, re-price the observation window on every panel that patient still has open, and force a physician into the room for procedures that were booked weeks earlier. An amendment to a payer plan must not silently reprice an authorization that was already granted. A returned hearing aid must move exactly one unit from the "consumed" bucket to the "written off" bucket, never back onto the shelf. The API's job is to make those consequences mechanical rather than remembered.

Two design commitments run through everything that follows. First, **the practice is time-driven and the time is ours**: every window, expiry, washout and shelf life is measured against a server-held logical clock rather than wall-clock time, so the same scenario is reproducible. Second, **rejection is ordered, not arbitrary**: when a single request violates several rules at once, the API always reports the one that matters most clinically, and the ordering is published in §2.8 rather than left to implementation accident. The whole surface is mounted at the server root, and every collection is addressed as a top-level path; parents are named by identifier inside request bodies rather than by nested URL segments.

## 2. Global Specifications & System-Wide Principles

### 2.1. Staff Identity and Role-Based Access Control

Every request to every endpoint — reads included — must carry two headers: `X-User-ID`, identifying the staff member acting, and `X-User-Role`, naming the capacity in which they act. If either header is missing, supplied as an empty string, or supplied as whitespace only, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A header present and non-blank but naming something that is not one of the six declared roles, or naming a role that the target endpoint does not list, is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

Six roles exist, spelled exactly as follows:

- `PracticeAdmin` — the practice manager. Owns payer-plan configuration, the patient and asset registries, inventory, surgery-center blocks, refund settlement, and the logical clock.
- `Otolaryngologist` — the treating physician. Orders panels and studies, documents sinuplasty candidacy, interprets studies, and runs procedures.
- `AllergyNurse` — the allergy clinic nurse. Administers panels, records reactions, compounds and verifies extract vials, and gives immunotherapy doses.
- `Audiologist` — audiology and sleep services. Records study results and dispenses, adjusts, accepts back and finalizes hearing aids and oral appliances.
- `SterileProcessingTech` — the endoscopy suite reprocessing technician. Owns high-level-disinfection runs from start to documented completion.
- `PayerLiaison` — the prior-authorization coordinator. Submits and resubmits cases to payers and records payer decisions.

All six roles carry an **opaque** identity. When `X-User-Role` is `PracticeAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it on rows where a workflow step demands attribution, but never compares it to any entity's `id`. The same holds, in exactly the same form, for `Otolaryngologist`, for `AllergyNurse`, for `Audiologist`, for `SterileProcessingTech`, and for `PayerLiaison`: none of these six is entity-backed, so no endpoint performs an ownership check of the form "the acting user's identifier must equal a resource's primary key". What the server does instead is store the acting identifier at the moment of an action — as `ordered_by_user_id`, `administered_by_user_id`, `recorded_by_user_id`, `mixed_by_user_id`, `verified_by_user_id`, `supervising_user_id`, `documented_by_user_id`, `submitted_by_user_id`, `performed_by_user_id`, `interpreted_by_user_id`, `dispensed_by_user_id`, `settled_by_user_id`, `reprocessing_started_by_user_id`, `last_used_by_user_id`, `physician_user_id` or `attending_physician_user_id`, depending on the workflow — purely so that the segregation-of-duties and run-continuity comparisons described in §2.9 have two identifiers to compare.

Every read endpoint in the service is available to all six roles. Write endpoints are narrower, and §4 is authoritative on which roles may call which.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`: the literal prefix `req_` followed by exactly twenty characters drawn from uppercase letters and digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. Like every other instant in the service it is read from the logical clock of §2.5 and never from wall-clock time, so two responses produced without an intervening clock move carry the same `api_request_timestamp`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- A request that cannot be routed at all is answered in this same error envelope: an unknown path, or a method the path does not implement, carries `error_id` `ERR_INVALID_REQUEST` with the transport status the router itself selected — 404 for a path that matches no endpoint, 405 for a path that exists under a different method — rather than the 400 that the same identifier carries when a routed request fails the shape gate.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may be no smaller than 1, and may be no larger than 100. `offset` controls how many matching rows are skipped before the page begins: it defaults to 0 and may never be negative. A `limit` outside the range 1 through 100 inclusive, or a negative `offset`, is a shape failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

List results are ordered by `created_at` ascending. Where two rows share a `created_at` — which the logical clock makes common, since every row created without an intervening clock move shares one instant — the tie is broken by the order in which the rows were created, so the ordering is stable across repeated identical requests and rows created later never sort ahead of rows created earlier.

For list responses, the `meta` object carries four pagination fields in addition to the request identifier and timestamp: `limit` (the effective page size actually applied), `offset` (the effective offset actually applied), `total_count` (the number of rows matching the filters, before the page window is applied), and `has_more` (true when the sum of `offset` and the number of rows returned in this page is strictly less than `total_count`, otherwise false). Single-resource reads omit all four; they nonetheless tolerate `limit` and `offset` as query parameters — the two names are accepted on every read endpoint in the service — and simply ignore them, still returning the bare two-field `meta`. An `offset` at or beyond `total_count` is not an error: the page comes back as an empty `data` array with `has_more` false.

Filter parameters on list endpoints are combined conjunctively: a request that supplies both a `patient_id` filter and a `status` filter returns only rows matching both. An omitted filter constrains nothing. A filter is matched by exact equality against the stored field, and a filter that names an identifier no row carries — or that names an identifier belonging to no entity at all — is never a 404: it simply matches nothing and the response is an empty page with a `total_count` of 0. Identifier-valued filters are accepted as free strings and are not pattern-checked, whereas an enum-valued filter must name a declared member of that enum, a numeric filter must be a well-formed integer, and a boolean filter must be spelled exactly `true` or exactly `false` — `TRUE`, `False`, `1`, `0` and `yes` are all rejected — every one of the three failing the shape gate otherwise. The service declares boolean filters on two list endpoints only, a scope's `mec_test_due` in §3.8 and a block's `overnight_capable` in §3.9, but the spelling rule is general and would govern any other.

### 2.4. Resource Identity, Timestamps and the Version Counter

Every resource the service stores carries a server-minted `id`: a UUID, rendered as a plain UUID string with no type prefix and no domain flavouring. Clients never supply an `id`, and a request body that contains one fails the shape gate.

Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional-second digits, stamped from the logical clock at the instant the row is created. The exactly-three-digit guarantee is a guarantee about instants the *server* stamps. An instant a *client* supplies — `antihistamine_last_dose_at`, the clock setter's `current_utc`, and every other client-supplied instant field — is stored and echoed back in precisely the spelling the client sent, character for character, and is never renormalised into the three-digit form: a client that sends `2026-08-01T00:00:00Z` reads that same string back, and one that sends `2026-08-01T00:00:00.000000Z` reads that back instead. Calendar-date fields are stored as spelled in the same way. Comparisons and arithmetic are of course performed on the parsed instant, so two different spellings of one instant behave identically in every gate. Twelve of the thirteen resource kinds additionally carry `updated_at`, of identical format, refreshed to the current logical-clock instant on every mutation of that row, and `version`, an integer that begins at 1 when the row is created and increments by exactly 1 on every mutation of that row. Those twelve are: `PayerPolicy`, `Patient`, `AllergyTestOrder`, `ImmunotherapyVial`, `ImmunotherapyDose`, `SinuplastyCase`, `DiagnosticStudy`, `DeviceDispense`, `EndoscopeAsset`, `SupplyLot`, `SurgeryCenterBlock` and `ProcedureBooking`.

The one exception is the reaction event. A recorded reaction is append-only clinical evidence: it is never edited and never withdrawn. A reaction event therefore carries only `id` and `created_at` — it has **no** `updated_at` field and **no** `version` field at all, and neither appears in its representation. Its own clinical timestamp, `occurred_at`, is stamped from the logical clock when the event is recorded and is likewise never rewritten.

When a request's path contains more than one identifier, the identifiers are resolved strictly left to right, and the first one that fails to resolve determines the error. In this service almost every path carries a single identifier — `policyId`, `patientId`, `orderId`, `eventId`, `vialId`, `doseId`, `caseId`, `studyId`, `dispenseId`, `scopeId`, `lotId`, `blockId` or `bookingId` — and each resolves against its own collection, producing the entity-specific 404 named in §5. Identifiers supplied inside a request body are resolved after every path identifier has resolved, and in the order the endpoint's own input list declares them, so a body naming two unknown parents reports the one declared first.

### 2.5. The Logical Clock and Temporal Arithmetic

Nothing in this service consults wall-clock time. A server-held **logical clock** supplies the instant used for every `created_at`, every `updated_at`, every administration stamp, every window comparison, every expiry test and every elapsed-time subtraction. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. A `PracticeAdmin` may move it by supplying a `current_utc` instant to the clock-setting capability; the response echoes back a single `current_utc` field, carrying the caller's own spelling of the instant, and nothing else — the clock is not a stored resource and its response object has no `id`, no `created_at` and no `version`. The clock may be set to any well-formed UTC instant, and it may be moved backwards as freely as forwards: an instant earlier than the clock's current reading is accepted without complaint, and no row already stamped is revisited.

Moving the clock moves nothing else. There is no sweep, no background job and no lazy scan triggered by a clock change. An authorization whose validity window has elapsed still reads `AUTHORIZED` until a scheduling attempt observes it, and a scope whose disinfection shelf life has elapsed still reads `READY` with its old `hld_expires_at` until a procedure start attempts to use it. Expiry in this system is always **observed**, never swept, and the two places where observation has a durable consequence are called out explicitly in §3.6 and §3.9.

Elapsed-time arithmetic follows three conventions used consistently throughout. Comparisons against a deadline are made on the raw instants, so "the window has elapsed" means the current logical-clock instant is greater than or equal to the deadline. Conversions from an interval to whole days discard any partial day — a subtraction of two instants yielding two days and twenty-three hours counts as two whole days. Conversions from an interval to whole minutes likewise discard the remainder. Calendar-date fields such as `date_of_birth`, `ct_study_date`, and the `start_date` and `end_date` of a documented therapy carry no time of day, and arithmetic on them is pure calendar arithmetic.

### 2.6. Cents, Millilitres, Basis Points and Rounding

Money never appears as a decimal in this API. Every monetary field — `practice_charge_cents`, `patient_responsibility_cents`, `price_cents`, `restock_fee_cents`, `restock_fee_floor_cents` and `refund_cents` — is an integer count of cents. Wherever a monetary computation produces a fractional cent, the result is rounded **half up** to a whole cent: a value whose fractional part is exactly one half rounds away from zero, upward.

Proportions are expressed in **basis points**, integers where 10000 represents one hundred percent. `covered_pct_bps` is the share of a billed allergy unit the plan pays, `restock_fee_bps` is the restocking fee expressed as a fraction of the device price, and `utilization_bps` is a surgery-center block's booked share of its own capacity. All three are integers, and any derived basis-point figure is rounded half up.

Extract volumes are millilitres carried to exactly two decimal places. `volume_ml_initial`, `volume_ml_remaining`, `volume_ml_dispensed_total`, `volume_ml_wasted` and a dose's `volume_ml` are all two-decimal quantities, and because every scheduled dose is a whole multiple of 0.05 mL, no rounding is ever required inside the volume ledger; the arithmetic closes exactly. Two decimal places is a statement about the *value* and not about its spelling on the wire: each of these five fields is emitted as a JSON **number**, and a JSON number does not preserve trailing zeros, so a bucket holding 5.00 mL renders as `5.0`, an empty bucket renders as `0.0`, and a 0.30 mL figure renders as `0.3`, while 0.05 mL — needing both places — renders as `0.05`. Wherever this document writes a millilitre figure as `5.00` or `0.00` it is naming the quantised value, not promising those characters in a response body; §3.5 works the renderings through.

Two clinical measures carry at most a single decimal place — one decimal place is the *ceiling* the shape gate enforces, not a minimum, so an integral value is perfectly well formed and, per §3.7, is echoed back integral rather than re-rendered with a `.0`: a reaction's `local_wheal_mm` (0 through 80 inclusive) and the audiometric and sleep metrics `pta_db_hl` (0 through 120 inclusive), `word_recognition_pct` (0 through 100 inclusive) and `ahi` (0 through 120 inclusive). Everything else that is numeric in this API — counts, minutes, days, months, units, points, steps and basis points — is an integer, and where a formula divides, the quotient is taken downward to a whole number unless the formula explicitly says otherwise.

One rounding rule deserves emphasis because getting it backwards changes published totals: in allergy panel billing, the per-unit price is rounded **before** it is multiplied by the number of billed units, never after. §3.3 states the sequence in full.

### 2.7. Version Pinning and Stale-Read Rejection

Two write operations in this service can legitimately supersede work a colleague has already done, which makes them impossible to guard by state alone. Both are therefore guarded by **optimistic concurrency control** on a parent resource's `version` counter, and both take a mandatory version field in their request body. No other endpoint in this service accepts a version field of any kind, and supplying one where it is not declared is a shape failure.

A request to compound a new extract vial must carry `expected_patient_version`, an integer holding the `version` the client last read from the target `Patient` row. The check is not optional and the field has no default. If `expected_patient_version` does not equal that patient's current `version`, the request is rejected with `ERR_STALE_PATIENT_VERSION` (HTTP 412) and no vial is created. This matters because compounding a fresh vial silently discards the patient's existing verified or in-use vial as `SUPERSEDED`, and because the dilution the new vial must carry is decided by the patient's current escalation step — a step that a cleared dose or a recorded reaction may have moved since the compounder last looked. Rejecting a stale read stops a nurse from superseding a vial they never saw, and from mixing against a schedule position that no longer exists.

A request to dispense a hearing aid or oral appliance must carry `expected_study_version`, an integer holding the `version` the client last read from the target `DiagnosticStudy` row. If `expected_study_version` does not equal that study's current `version`, the request is rejected with `ERR_STALE_STUDY_VERSION` (HTTP 412) and no dispense is created. A second dispense against the same interpreted study is a legitimate operation — it supersedes the earlier unit and increments the study's `superseded_dispense_count` — so state cannot be the gate here either. The stale-version check is what stops an audiologist from superseding a dispense that is not in their view of the study.

Both checks are evaluated *after* the referenced parent has been proven to exist, so a stale version quoted against an identifier that resolves to nothing still reports the 404, not the 412. Both are evaluated *before* any lifecycle-state precondition, so a stale version quoted against a parent in the wrong state reports the 412. §2.8 fixes that ordering formally.

### 2.8. Rejection Precedence: The Fourteen-Rung Ladder

Clinical requests fail for several reasons at once far more often than they fail for one. A nurse can present an unauthenticated request, for an endpoint her role could not call anyway, with a malformed body, naming a patient who does not exist, against an order in the wrong state. The API must always answer with the *same* error for the *same* multiply-invalid request, so the fourteen families of validation are arranged in a strict ladder and evaluated in ascending rung order. **The first rung that finds a violation produces the response; every higher-numbered rung is armed but never reached.** The shape of the ladder is: identity before shape, shape before existence, existence before concurrency, concurrency before lifecycle state, and then, inside the business band, patient safety before temporal scheduling, temporal scheduling before referential coherence, referential coherence before contractual constraints, and contractual constraints before money and inventory.

**Rung 1 — authentication.** Both `X-User-ID` and `X-User-Role` present and non-blank, as described in §2.1. Applies to every endpoint. Violation: `ERR_UNAUTHENTICATED`, HTTP 401.

**Rung 2 — authorization.** `X-User-Role` is one of the six declared roles and is listed among the target endpoint's permitted roles. Applies to every endpoint. Violation: `ERR_ROLE_NOT_PERMITTED`, HTTP 403.

**Rung 3 — request shape.** The body and query conform to the endpoint's declared input: every required field is present; no unknown field is present; every value has the declared type; every enum-typed value is a declared member; every integer lies inside its declared range; every ISO-8601 instant is well formed and expressed in UTC — the accepted spelling is a `YYYY-MM-DDThh:mm:ss` core (the date-time separator may be upper or lower case), optionally followed by a fractional-second part of one or more digits, closed either by `Z` or by an explicitly zero UTC offset written `+00:00`, `+0000`, `-00:00` or `-0000`, with surrounding whitespace trimmed before the value is judged, so an instant bearing any non-zero offset, or omitting its seconds, or omitting a zone marker altogether, fails here; every calendar date is well formed as `YYYY-MM-DD`; every regex-constrained string matches its pattern (`mrn` matches an `MRN-` prefix followed by exactly five digits; `plan_code` is three to twenty characters drawn only from uppercase letters, digits and hyphens; `serial_number` matches an `SC-` prefix followed by exactly four digits; `lot_number` matches a `LOT-` prefix followed by exactly four digits; `device_serial` is exactly two uppercase letters followed by exactly six digits); array fields declared non-empty are non-empty; a documented therapy item never has a `start_date` later than its `end_date`; a reaction event carries exactly one of `allergy_test_order_id` and `immunotherapy_dose_id`, so supplying both or neither fails here; a study-results payload carries exactly the metric set its `study_type` demands; `limit` lies between 1 and 100 inclusive and `offset` is not negative. Three conventions complete this rung. A request body, where one is declared, must be a JSON object: a body that is not parseable JSON, or that parses to an array, a string or a number, fails here. An endpoint that declares no request body — every action that carries none — treats an absent body, an empty body and the empty object `{}` as equivalent and accepts all three, while rejecting any field whatsoever inside the body. And query-string policing belongs to the read endpoints: every `GET` rejects a query parameter it does not declare, always tolerating `limit` and `offset`, whereas the creating and mutating endpoints declare no query parameters at all and ignore whatever query string a caller appends to their path. Applies to every endpoint. Violation: `ERR_INVALID_REQUEST`, HTTP 400.

The ladder's "shape before existence" clause admits exactly three exceptions, and each exists for the same reason: the shape the payload must take is itself read off a stored row, so the check has nothing to judge until that row has been fetched. They are the vial `label_text` composition of §3.5, which is measured against the referenced patient's `mrn` and therefore waits on a *body* reference and sits behind rung 5; the study metric set of §3.7, which is fixed by the target study's `study_type`; and the reading count of §3.3, which is bounded by the target order's `antigen_count` — the last two waiting on their endpoint's *path* identifier and therefore sitting behind rung 4. All three still emit `ERR_INVALID_REQUEST` at rung 3, and each still outranks every rung that follows the one identifier it had to wait for, so each of them beats its endpoint's concurrency and lifecycle gates; each subsection states its own ordering in full. Every other rung-3 check in the service is judged before any identifier is resolved and beats every 404.

**Rung 4 — path existence.** Every identifier in the path resolves to a stored row, resolved left to right. Applies to every endpoint carrying a path parameter. Violation: the entity-specific 404 — `ERR_PAYER_POLICY_NOT_FOUND`, `ERR_PATIENT_NOT_FOUND`, `ERR_ALLERGY_TEST_ORDER_NOT_FOUND`, `ERR_REACTION_EVENT_NOT_FOUND`, `ERR_IMMUNOTHERAPY_VIAL_NOT_FOUND`, `ERR_IMMUNOTHERAPY_DOSE_NOT_FOUND`, `ERR_SINUPLASTY_CASE_NOT_FOUND`, `ERR_DIAGNOSTIC_STUDY_NOT_FOUND`, `ERR_DEVICE_DISPENSE_NOT_FOUND`, `ERR_ENDOSCOPE_ASSET_NOT_FOUND`, `ERR_SUPPLY_LOT_NOT_FOUND`, `ERR_SURGERY_CENTER_BLOCK_NOT_FOUND` or `ERR_PROCEDURE_BOOKING_NOT_FOUND` — all HTTP 404.

**Rung 5 — body-reference existence.** Every identifier supplied inside the request body resolves to a stored row, resolved in the order the endpoint's input list declares them. This rung guards the nine creation operations: patient creation, allergy-order creation, reaction-event creation, vial compounding, dose administration, sinuplasty-case creation, diagnostic-study creation, device dispensing, and procedure-booking creation. The error is drawn from the same 404 catalogue as rung 4, selected by whichever referenced entity failed to resolve. Note the division of labour on a reaction event: carrying both or neither of `allergy_test_order_id` and `immunotherapy_dose_id` was already rejected at rung 3, whereas carrying exactly one that resolves to nothing is a 404 here. A body identifier supplied as an empty or whitespace-only string does not reach this rung at all: every identifier field is required to be a non-blank string to clear rung 3, so a blank identifier is an `ERR_INVALID_REQUEST` and not a 404. Identifiers are otherwise unconstrained strings — they are never pattern-checked as UUIDs — so any non-blank value that matches no stored row produces the entity-specific 404 here.

**Rung 6 — optimistic concurrency.** `expected_patient_version` equals the referenced patient's current `version`, and `expected_study_version` equals the referenced study's current `version`. Applies to vial compounding and to device dispensing only. Violation: `ERR_STALE_PATIENT_VERSION` or `ERR_STALE_STUDY_VERSION`, HTTP 412. Because this rung sits above rung 4 and 5, a stale version quoted against a nonexistent parent still reports the 404.

**Rung 7 — lifecycle state.** The entity named by the path — or, for a creation, the primary parent that owns the new row's lifecycle — is in one of the states the requested transition declares as a legal origin. Applies to every action endpoint and to every creation whose parent has a lifecycle. The error identifies the entity whose *own* lifecycle blocked the request: `ERR_ORDER_STATE_INVALID`, `ERR_VIAL_STATE_INVALID`, `ERR_DOSE_STATE_INVALID`, `ERR_CASE_STATE_INVALID`, `ERR_STUDY_STATE_INVALID`, `ERR_DISPENSE_STATE_INVALID`, `ERR_SCOPE_STATE_INVALID`, `ERR_BOOKING_STATE_INVALID`, `ERR_LOT_STATE_INVALID` or `ERR_BLOCK_STATE_INVALID`, all HTTP 409. Concretely this rung covers: an order not `ORDERED` at administration or at serum conversion; an order in neither `ADMINISTERED` nor `SERUM_PENDING` when readings are recorded; a vial not `MIXED` at label verification; a vial outside `MIXED`, `LABEL_VERIFIED` and `IN_USE` at discard; a dose not `ADMINISTERED`, or already carrying a non-null `observation_cleared_at`, at observation clearance or at void, and at clearance additionally a dose whose `reaction_grade` exceeds 1 — all three of those sub-checks emitting `ERR_DOSE_STATE_INVALID` from this rung, so the grade is judged as a lifecycle matter ahead of the observation window rather than as a safety gate; a case not `DRAFT` at documentation, a case outside `DOCUMENTED`, `INFO_REQUESTED` and `AUTH_EXPIRED` at an authorization submission, a case not `AUTH_SUBMITTED` at a payer decision, and a case outside `AUTHORIZED` and `DOCUMENTED` when a balloon-sinuplasty booking references it; a study not `ORDERED` when results are recorded and not `PERFORMED` at interpretation; a study not `INTERPRETED` when a dispense is created against it; a dispense whose `fit_status` is already `FINALIZED` or `RETURNED` at adjustment, finalization or trial return, or whose `billing_status` is not `REFUND_PENDING` at refund settlement; a scope outside `SOILED` and `QUARANTINED` at reprocessing start and not `REPROCESSING` at reprocessing completion, or a scope that is `RETIRED`; a booking not `SCHEDULED` at start or cancellation and not `IN_PROGRESS` at completion; a block that is already `CLOSED` when a close is requested; and a lot that is `QUARANTINED` when a booking or a dispense tries to draw from it.

**Rung 8 — practice-wide uniqueness.** Five string fields are unique across all rows of their entity, including rows that have reached a terminal state: a plan's `plan_code`, a patient's `mrn`, an endoscope's `serial_number`, a supply lot's `lot_number`, and a device dispense's `device_serial`. Applies to plan registration, patient registration, endoscope registration, supply-lot receipt and device dispensing. Violation: `ERR_DUPLICATE_PLAN_CODE`, `ERR_DUPLICATE_MRN`, `ERR_DUPLICATE_SCOPE_SERIAL`, `ERR_DUPLICATE_LOT_NUMBER` or `ERR_DUPLICATE_DEVICE_SERIAL`, all HTTP 409. A retired scope still owns its serial; a returned device still owns its serial.

**Rung 9 — segregation of duties.** The six identity comparisons enumerated in §2.9. This rung sits deliberately *below* rung 7 so that a request arriving in the wrong lifecycle state is told about the state and is never told who performed the earlier step. Violations: `ERR_SELF_VERIFICATION_FORBIDDEN`, `ERR_SELF_DECISION_FORBIDDEN`, `ERR_SELF_INTERPRETATION_FORBIDDEN`, `ERR_SELF_SETTLEMENT_FORBIDDEN`, `ERR_REPROCESSING_TECH_MISMATCH` or `ERR_PHYSICIAN_MISMATCH`, all HTTP 409. Applies to label verification, payer decisions, study interpretation, refund settlement, reprocessing completion and booking start.

**Rung 10 — patient safety.** Eight gates, all HTTP 409, checked before any scheduling or temporal rule: epinephrine must be on file whenever the patient's `risk_score` is at least 45 and a skin-method panel or an immunotherapy dose is being administered (`ERR_EPINEPHRINE_NOT_ON_FILE`); a patient whose `dermatographism` flag is true may not receive a skin-method administration (`ERR_DERMATOGRAPHISM_BLOCKS_SKIN_TEST`); a vial's `label_text_confirmation` must equal its stored `label_text` (`ERR_VIAL_LABEL_MISMATCH`); a vial whose beyond-use instant the clock has reached may be neither verified nor drawn from (`ERR_VIAL_EXPIRED`); a vial's `dilution_code` must equal the dilution the patient's pre-rollback escalation step demands (`ERR_DILUTION_MISMATCH`); a dose drawn from a vial whose `requires_supervised_administration` is true must supply `supervising_user_id` (`ERR_SUPERVISION_REQUIRED`); a booking whose `requires_physician_presence` is true must supply `attending_physician_user_id` at start (`ERR_ATTENDING_PHYSICIAN_REQUIRED`); and a booking whose `overnight_observation_required` is true, *when it names a surgery-center block at all*, must name one whose `overnight_capable` is true (`ERR_OVERNIGHT_CAPABILITY_REQUIRED`) — an office-suite booking names no block, so this gate finds nothing to judge there and the pediatric venue rule of rung 13 stops it instead. This rung applies to exactly five operations: panel administration, vial label verification, dose administration, booking creation and booking start.

**Rung 11 — temporal windows.** Nine clock-relative gates, all HTTP 409: the antihistamine washout must be complete before a skin administration (`ERR_WASHOUT_NOT_COMPLETE`); the observation window must have elapsed before readings are recorded or a dose's observation is cleared (`ERR_OBSERVATION_NOT_COMPLETE`); a dose may be voided only inside its fifteen-minute window (`ERR_VOID_WINDOW_CLOSED`); a scope's live booking intervals may not overlap (`ERR_SCOPE_INTERVAL_CONFLICT`); consecutive bookings on one scope must leave the reprocessing turnaround (`ERR_REPROCESSING_BUFFER_VIOLATION`); a booking must lie entirely inside its block's half-open window (`ERR_BLOCK_WINDOW_EXCEEDED`); a scope whose disinfection shelf life has lapsed may not be used (`ERR_HLD_EXPIRED`); a case whose authorization validity the clock has reached may not be scheduled, and the case is durably moved to `AUTH_EXPIRED` before the rejection is emitted (`ERR_AUTHORIZATION_EXPIRED`); and a dispense may not be finalized before its trial window has elapsed (`ERR_TRIAL_NOT_COMPLETE`). This rung applies to exactly seven operations: panel administration, panel readings, dose observation clearance, dose void, booking creation, booking start and dispense finalization.

**Rung 12 — referential coherence.** Four checks about the relationship *between* two referenced rows, or about the state of a secondary, non-owning referenced row, all HTTP 409: a dispense's `device_type` must be the device type the study's `recommendation` calls for (`ERR_DEVICE_TYPE_NOT_RECOMMENDED`); a supply lot's `item_type` must match what is being drawn from it, whether that is a dispense's `device_type` or a booking's `procedure_type` (`ERR_LOT_ITEM_TYPE_MISMATCH`); a booking's `sinuplasty_case_id` must reference a case whose `patient_id` equals the booking's own `patient_id` (`ERR_CASE_PATIENT_MISMATCH`); and a booking's endoscope must be `READY` at start (`ERR_SCOPE_NOT_READY`). The scope check here covers only scopes that are *still serviceable* — `IN_USE`, `SOILED`, `REPROCESSING` or `QUARANTINED`. A `RETIRED` scope is deliberately excluded from this rung and falls through to rung 13, one rung *lower*, where the `scope_reassignment_required` flag its retirement cascade raised reports `ERR_SCOPE_REASSIGNMENT_REQUIRED` — so the operator is told to reassign rather than told to wait. That fall-through is a property of booking *start* only; a booking *creation* naming a `RETIRED` scope is stopped far earlier, at rung 7, with `ERR_SCOPE_STATE_INVALID`. This rung applies to device dispensing, booking creation and booking start.

**Rung 13 — contractual and configuration constraints.** Eight checks, all HTTP 409: a balloon-sinuplasty booking may not start while the case's `pinned_policy_version` differs from the plan's current `version` (`ERR_POLICY_VERSION_DRIFT`); a case may not be resubmitted once its `revision_round` has reached 2 (`ERR_REVISION_LIMIT_REACHED`); a case whose `candidacy_status` is not `ELIGIBLE` may be neither submitted nor scheduled (`ERR_CANDIDACY_NOT_ELIGIBLE`); a serum conversion is refused when the plan's `allergy_serum_covered` is false (`ERR_SERUM_NOT_COVERED`); an oral-appliance dispense is refused when the plan's `appliance_covered` is false (`ERR_APPLIANCE_NOT_COVERED`); a fourth adjustment on one dispense is refused (`ERR_ADJUSTMENT_LIMIT_REACHED`); a booking whose `scope_reassignment_required` is true may not start (`ERR_SCOPE_REASSIGNMENT_REQUIRED`); and a tonsillectomy or tympanostomy-tube booking for a patient younger than thirty-six whole months may not be venued in the office suite (`ERR_PEDIATRIC_VENUE_REQUIRED`). This rung applies to serum conversion, authorization submission, device dispensing, dispense adjustment, booking creation and booking start.

**Rung 14 — money, volume and inventory ceilings.** Five checks, all HTTP 409, evaluated last: a booking may not reserve from a lot whose `available_quantity` is 0, nor reserve more units than the lot has available (`ERR_SUPPLY_EXHAUSTED`); a dose may not be drawn when the vial's `volume_ml_remaining` is less than the computed dose `volume_ml` (`ERR_INSUFFICIENT_VIAL_VOLUME`); a balloon-sinuplasty booking's `planned_device_count` may not exceed the case's `authorized_device_count` (`ERR_DEVICE_COUNT_EXCEEDS_AUTHORIZATION`); a booking may neither push a block's `booked_minutes` beyond its `capacity_minutes` nor exceed the block's `max_concurrent_cases` at any instant inside its own interval (`ERR_BLOCK_CAPACITY_EXCEEDED`); and no booking may be created against a block whose status is `FULL` or `CLOSED` (`ERR_BLOCK_NOT_OPEN`). This rung applies to dose administration and booking creation.

Two consequences of this ordering are worth spelling out because they are easy to implement backwards. **First**, on booking creation, a lifecycle failure beats a supply failure: if the referenced sinuplasty case is `DENIED` — not `AUTHORIZED` and not `DOCUMENTED` — while the referenced supply lot simultaneously has an `available_quantity` of 0, the response is `ERR_CASE_STATE_INVALID` from rung 7, not `ERR_SUPPLY_EXHAUSTED` from rung 14. A denied case is not schedulable at all, so inventory is never consulted. **Second**, on panel administration, a safety failure beats a temporal failure: if the patient's `risk_score` is at least 45 with `epinephrine_on_file` false while the seventy-two-hour antihistamine washout is simultaneously incomplete, the response is `ERR_EPINEPHRINE_NOT_ON_FILE` from rung 10, not `ERR_WASHOUT_NOT_COMPLETE` from rung 11. A missing rescue medication is a hard stop; an incomplete washout is a scheduling defect that a later appointment cures.

### 2.9. Segregation of Duties

Five paired workflows in this practice require two different people, and one requires the *same* person. All six comparisons operate on `X-User-ID` and all six live at rung 9.

Four of them are "not the same person" rules. The staff member who verifies a vial's label must differ from the `mixed_by_user_id` recorded when the vial was compounded, or the verification is refused with `ERR_SELF_VERIFICATION_FORBIDDEN`. The staff member who records a payer decision must differ from the `submitted_by_user_id` recorded on the case's current submission, or the decision is refused with `ERR_SELF_DECISION_FORBIDDEN`. The staff member who interprets a study must differ from the `performed_by_user_id` recorded when the results were entered, or the interpretation is refused with `ERR_SELF_INTERPRETATION_FORBIDDEN`. The staff member who settles a refund must differ from the `dispensed_by_user_id` recorded when the device went out, or the settlement is refused with `ERR_SELF_SETTLEMENT_FORBIDDEN`.

The fifth is the inverse. A disinfection run must be closed by the same technician who opened it: the identifier on the completion must **equal** the scope's `reprocessing_started_by_user_id`, and a mismatch is refused with `ERR_REPROCESSING_TECH_MISMATCH`. Continuity, not independence, is the point — a technician may not document a run they did not personally perform.

The sixth is an identity rule rather than a duty-splitting rule: a booking may be started only by the physician of record, so the acting identifier must equal the booking's `physician_user_id`, and any other identifier is refused with `ERR_PHYSICIAN_MISMATCH`. The optional `attending_physician_user_id` supplied on the same request is a *different* person's identifier and is never compared with `physician_user_id`.

### 2.10. Conserved Ledgers

Two quantities in this practice are conserved, and every operation that appears to create or destroy them is really moving them between buckets. Implementations that treat either as a free-running counter will drift, and the drift is observable through the read endpoints.

**The supply lot has four buckets.** `quantity_on_hand` counts units physically present, reserved units included; `quantity_consumed` counts units permanently implanted or dispensed; `quantity_wasted` counts units written off; and `quantity_received` is the running total ever booked in. After **every** mutation of a lot, `quantity_received` must equal the sum of `quantity_on_hand`, `quantity_consumed` and `quantity_wasted`. A fifth figure, `quantity_reserved`, is not a bucket but a claim against `quantity_on_hand`: it is the sum of `planned_device_count` over the lot's bookings in status `SCHEDULED` or `IN_PROGRESS`, and a booking that has been `CANCELLED` or `COMPLETED` holds no reservation at all. What the practice can actually commit is `available_quantity`, defined as `quantity_on_hand` minus `quantity_reserved`; it is never negative, and a lot may not be reserved from unless at least one unit is available.

**The extract vial has four volume buckets**, and the same discipline applies. `volume_ml_dispensed_total` is the sum of `volume_ml` over the vial's doses in status `ADMINISTERED`, `CLEARED` or `REACTION_HELD`, taken in ascending `administered_at` order with ascending `created_at` as the tie-break; `volume_ml_wasted` is what a discard wrote off; and `volume_ml_remaining` is `volume_ml_initial` less `volume_ml_dispensed_total` less `volume_ml_wasted`. After every mutation, `volume_ml_initial` must equal the sum of `volume_ml_remaining`, `volume_ml_dispensed_total` and `volume_ml_wasted`. A dose in status `VOIDED` is excluded from `volume_ml_dispensed_total` entirely, which is exactly how a void compensates its own draw and leaves no residue. A draw that would drive `volume_ml_remaining` below zero is refused with `ERR_INSUFFICIENT_VIAL_VOLUME` before any bucket moves. The reference compounded volume for a new vial is 5.00 mL.

### 2.11. Cascade Discipline and Derived-Field Freshness

Many operations in this service mutate more than one row, and several mutate rows two, three or four steps away from the one named in the request. The rule is that a cascade is **transitive**: each hop is caused by the mutation the previous hop made, not by the original request, so a hop whose triggering condition is not met simply does not fire and the hops beyond it do not fire either. §3.4 walks the longest chain in the system — four hops, from a recorded reaction all the way out to procedure bookings made weeks earlier — hop by hop.

Every row a cascade touches is a mutation of that row for the purposes of §2.4: its `updated_at` is refreshed to the current logical-clock instant and its `version` increments by one, exactly as if it had been written directly. A cascade that flips a patient's `supervision_tier` therefore advances that patient's `version`, and that advance is precisely what a client's previously-read `expected_patient_version` will fail against.

Derived fields are recomputed eagerly, at the moment their inputs move, and are stored so that a read never has to recompute them — with two deliberate exceptions. A patient's `age_months` is recomputed on every read of that patient row as well as on every mutation of it, because its only other input is the clock, and the clock moves without touching the row. A supply lot's `quantity_reserved`, and the `available_quantity` derived from it, are likewise refreshed on every read of the lot as well as whenever the lot itself is written, because their input is the set of reservations held by *other* rows and a booking that changes its own status does not necessarily write the lot. Every other computed field on every entity — `risk_score`, `supervision_tier`, `sensitized_antigen_count`, `billed_units`, `practice_charge_cents`, `patient_responsibility_cents`, `observation_required_minutes`, `worst_systemic_grade`, `volume_ml_remaining`, `volume_ml_dispensed_total`, `volume_ml_wasted`, `reaction_grade`, `gap_days_at_dose`, `criteria_met_count`, `contiguous_management_days`, `cumulative_management_days`, `candidacy_status`, `authorized_device_count`, `auth_expires_at`, `cycle_count`, `hld_expires_at`, `mec_test_due`, `consecutive_mec_failures`, `booked_case_count`, `booked_minutes`, `capacity_minutes`, `utilization_bps`, `duration_minutes` on a booking — a `SurgeryCenterBlock` carries no `duration_minutes` of its own, its window length surviving only inside the `capacity_minutes` it was multiplied into — `planned_device_count` on a case, `superseded_dispense_count`, `adjustment_count`, `days_used`, `refund_variant`, `restock_fee_cents`, `refund_cents`, `evaluation_variant`, `revision_round`, `pinned_policy_version`, `escalation_step_at_dose`, `volume_ml`, `immunotherapy_escalation_step`, `immunotherapy_status`, `last_dose_administered_at`, `risk_score_variant`, `overnight_observation_required`, `requires_physician_presence`, `requires_supervised_administration`, `scope_reassignment_required`, `supply_shortfall_flag`, `last_reprocessed_at`, `last_used_by_user_id` and `reprocessing_started_by_user_id` — is written at the moment the operation or cascade that owns it runs.

Fields whose `source` is computed or system are never accepted from a request body. A client that supplies one is rejected at rung 3 as an unknown field. This is why, for example, a `dermatographism` flag can only ever be raised by the abort cascade in §3.3, and why a dose's `volume_ml` is whatever the schedule says it is regardless of what the caller believes.

## 3. Business Logic & Workflows

### 3.1. Payer Plans and the Patient Chart

Everything in this practice is priced, gated and timed by a **payer plan**. A `PracticeAdmin` registers one by supplying a `payer_name` of one to one hundred and twenty characters and a `plan_code`, which must be unique across every plan the practice has ever registered. Thirteen further terms may be supplied, and each has a default that applies when the field is omitted: `requires_prior_auth` defaults to true; `min_medical_management_days` defaults to 28 and must lie between 0 and 180 inclusive; `requires_ct_within_months` defaults to 12 and must lie between 1 and 60 inclusive; `min_documented_criteria` defaults to 3 and must lie between 1 and 6 inclusive; `max_balloon_devices` defaults to 2 and must lie between 1 and 6 inclusive; `covered_pct_bps` defaults to 8000 — that is, the plan pays eight tenths of each billed allergy unit — and must lie between 0 and 10000 inclusive; `allergy_serum_covered` defaults to true; `observation_floor_minutes` defaults to 20 and must lie between 0 and 120 inclusive; `device_trial_days` defaults to 30 and must lie between 1 and 120 inclusive; `restock_fee_bps` defaults to 1500 — fifteen hundredths of the device price — and must lie between 0 and 10000 inclusive; `restock_fee_floor_cents` defaults to 12500, that is one hundred and twenty-five dollars, and must lie between 0 and 500000 inclusive; `auth_validity_days` defaults to 90 and must lie between 1 and 365 inclusive; and `appliance_covered` defaults to true. The new plan is created with `version` 1. A `plan_code` that already exists on another plan is refused with `ERR_DUPLICATE_PLAN_CODE`.

Plans get amended, and amendment is the engine behind two of this system's most interesting failures. A `PracticeAdmin` may amend any of the thirteen optional terms — `plan_code` and `payer_name` are not amendable and are not accepted on an amendment — and every amendment increments the plan's `version` by one, an amendment that supplies no terms at all included: an empty amendment body is a legitimate request, refreshes `updated_at` and still advances `version`, which is the cheapest way to make an authorization's pinned version drift. Critically, an amendment is **not** retroactive. A device dispense that has already stamped its `trial_end_at`, and a sinuplasty case that has already stamped its `auth_expires_at`, keep those instants unchanged forever; lengthening `device_trial_days` does not extend a trial already running, and shortening `auth_validity_days` does not shorten an authorization already granted. What an amendment *does* do is move the plan's `version`, and since an authorization pins the version it observed, the amendment is exactly what makes `ERR_POLICY_VERSION_DRIFT` reachable (§3.6 pins the version, §3.9 enforces it).

A `PracticeAdmin` registers a patient by naming the governing plan with `payer_policy_id`, supplying an `mrn` unique across every patient row, a `full_name` of one to one hundred and twenty characters, and a `date_of_birth` given as a calendar date that must fall on or before the logical clock's current date. A `date_of_birth` after the clock's current date is a shape failure reported as `ERR_INVALID_REQUEST`, and it is judged before `payer_policy_id` is resolved, so a future birth date quoted alongside an unknown plan reports the 400 and not the 404. Three intake facts are optional: `antihistamine_last_dose_at`, an instant that defaults to null when the patient reports no recent antihistamine; `epinephrine_on_file`, a flag defaulting to false; and `prior_systemic_reaction_count`, an integer between 0 and 10 inclusive that defaults to 0. A duplicate `mrn` is refused with `ERR_DUPLICATE_MRN`. On creation the chart is seeded with `sensitized_antigen_count` 0, `dermatographism` false, `immunotherapy_escalation_step` 1, `immunotherapy_status` `NONE`, `last_dose_administered_at` null, `risk_score_variant` `PROVISIONAL`, and a `risk_score` and `supervision_tier` computed immediately.

**Age in whole months.** The patient's `age_months` is derived from `date_of_birth` against the logical clock's date, and because the clock moves independently of the row, it is recomputed on every read of the patient as well as on every mutation. Take the difference in years between the clock's year and the birth year and multiply by twelve; add the difference between the clock's month number and the birth month number; then, if the clock's day of month is strictly less than the birth day of month, subtract one. No rounding of any kind is applied — the day-of-month borrow is the only truncation. A child born on 2024-03-15 observed at `2026-08-01T00:00:00Z` is 28 months old, because the day borrow applies (1 is less than 15). A child born on 2023-08-01 observed at the same instant is exactly 36 months old, with no borrow. Two age thresholds matter downstream: a patient under 72 whole months attracts pediatric risk points, and a patient under 36 whole months triggers the overnight-observation and venue rules of §3.9. Both boundaries are exclusive on the low side, so exactly 36 months does *not* require overnight observation, and exactly 72 months does *not* attract the pediatric points.

**The anaphylaxis risk score.** A patient's `risk_score` is an integer from 0 to 100 that governs observation sizing and supervision. Its base is assembled from five terms. Start with a base of 5 points. Add 15 points for each historical systemic reaction in `prior_systemic_reaction_count`, counting no more than 3 of them, so this term contributes at most 45. Add the patient's `sensitized_antigen_count`, counting no more than 20, so this term contributes at most 20. Add 8 points when `age_months` is strictly below 72, and nothing otherwise. Add 10 points when `epinephrine_on_file` is false, and nothing when it is true. To that base add the event term described below, then clamp the total to the range 0 through 100 inclusive. A newly registered adult with no prior reactions, no sensitizations and epinephrine on file therefore scores 5; the same patient at 28 months of age scores 13; and a patient with two prior reactions, ten sensitized antigens, adult age and epinephrine on file scores exactly 45.

The **event term** depends on which of two variants the patient is in, recorded in `risk_score_variant`. A patient begins life in `PROVISIONAL`, meaning no grade-2-or-worse systemic reaction has ever been recorded for them against a parent the safety cascade arms, and under `PROVISIONAL` the event term is exactly 0 — recorded grade-0 and grade-1 events contribute nothing at all and only the five base terms apply. The variant flips permanently to `POST_REACTION` the first time a reaction of grade 2 or higher is recorded against a parent that the cascade of §3.4 actually arms: an allergy test order standing in `ADMINISTERED`, or an immunotherapy dose standing in `ADMINISTERED`. The flip is a hop of that cascade rather than a property of the grade alone, so a grade-2-or-higher event filed against a parent in any other status is recorded and rolls that parent up but leaves `risk_score_variant`, `risk_score` and `supervision_tier` exactly where they were — the patient remains `PROVISIONAL` with an event term of 0. Once the variant has flipped, the event term is the sum, over **every** reaction event that resolves to this patient through either an allergy test order or an immunotherapy dose, of twenty points multiplied by that event's `systemic_grade` multiplied by a decay factor, each individual product rounded half up to a whole number *before* being added in so that rounding cannot accumulate across events. The decay factor is read from the whole number of days between the event's `occurred_at` and the current clock instant, taken downward: 1.00 when that age is 30 days or fewer; 0.60 when it is 31 through 90 days inclusive; 0.30 when it is 91 through 180 days inclusive; and 0.00 beyond 180 days, at which point the event stops contributing entirely. Events are summed in ascending `occurred_at` order with ascending `created_at` as the tie-break, and a row's `id` is never consulted for ordering. A `POST_REACTION` patient with base 45 and a single grade-1 event 61 days old therefore scores 57, because twenty times one times six tenths rounds to 12. The same patient with a single grade-3 event recorded today reaches 105 before the clamp and is stored as 100. Because reaction events are append-only, this input set never shrinks.

**Supervision follows the score.** A patient's `supervision_tier` is `STANDARD` while `risk_score` is 59 or lower, and becomes `PHYSICIAN_PRESENT` as soon as `risk_score` reaches 60 or more. A separate, lower threshold of 45 governs observation escalation and the epinephrine gate. Both thresholds are inclusive at the boundary: a score of exactly 45 escalates observation, and a score of exactly 60 escalates supervision.

The tier is **re-derived, not latched**, wherever it is derived at all, and the derivation reads nothing but the fresh score — so it moves in both directions. Three operations re-derive it: patient registration, the chart revision described below, and the readings roll-up of §3.3. Any of the latter two may therefore **demote** a patient from `PHYSICIAN_PRESENT` back to `STANDARD` if the recomputed score has fallen below 60 — because an epinephrine prescription was recorded, because `prior_systemic_reaction_count` was corrected downward, because the patient crossed 72 months and lost the pediatric points, or because a `POST_REACTION` patient's event term decayed as the clock advanced past the 30-, 90- and 180-day boundaries. The safety cascade of §3.4 is the deliberate exception: it only ever raises the tier, and never lowers it. A demotion is also strictly a change of tier and nothing more — it does **not** unwind the work an earlier promotion's cascade did, so `requires_supervised_administration` stays true on the patient's vials, `requires_physician_presence` stays true on their `SCHEDULED` bookings, and any `observation_required_minutes` that hop three of §3.4 had raised to 90 stays at 90 until that order is administered or converted. Those flags are cleared by no operation in this service.

A `PracticeAdmin` or an `AllergyNurse` may revise the three patient-reported intake facts — `antihistamine_last_dose_at`, `epinephrine_on_file` and `prior_systemic_reaction_count` — at any time. Of the three, `antihistamine_last_dose_at` is the only one that accepts an explicit null, which clears a previously recorded antihistamine dose and thereby satisfies the washout gate outright; a null offered for `epinephrine_on_file` or for `prior_systemic_reaction_count` is a shape failure. Any such revision re-derives `age_months` against the current clock, recomputes `risk_score` under the patient's *current* `risk_score_variant`, whatever that is, re-derives `supervision_tier` from that fresh score, and increments the patient's `version` by one. A revision that supplies none of the three fields is accepted and does all of that work anyway, so an empty update body is a legitimate way to advance the patient's `version`. That version bump is a real event for the concurrency rule of §2.7: a nurse who read the patient before an admin corrected the epinephrine flag will find their vial compounding refused. Patients can be listed and filtered by `payer_policy_id`, by `immunotherapy_status` and by `supervision_tier`.

### 3.2. Ordering an Allergy Panel: the Skin Arm and the Serum Arm

An `Otolaryngologist` or an `AllergyNurse` opens a panel by naming the `patient_id`, choosing a `panel_code` from `ENV_36`, `FOOD_24`, `MOLD_12` and `VENOM_5`, and choosing a `method` from `SKIN_PRICK`, `INTRADERMAL` and `SERUM_IGE`. The panel code alone fixes the order's `antigen_count`: `ENV_36` carries 36 antigens, `FOOD_24` carries 24, `MOLD_12` carries 12, and `VENOM_5` carries 5. The new order enters status `ORDERED` with `billed_units` 0, `practice_charge_cents` 0, `patient_responsibility_cents` 0, `positive_antigen_count` 0, `worst_systemic_grade` 0, `abort_reason` null, `administered_at` null, `administered_by_user_id` null, and `ordered_by_user_id` stamped from the acting identifier. Its `observation_required_minutes` is sized at creation from the requested method, so an `ORDERED` order always advertises a current figure — exactly 0 for a `SERUM_IGE` order — and that figure is re-derived at administration, is rewritten to 0 by a serum conversion, and is re-derived on every one of the patient's still-`ORDERED` orders by exactly one cascade hop: hop three of the *dose-branch* chain in §3.4, which fires only when a reaction on an immunotherapy dose pushes the patient's `supervision_tier` to `PHYSICIAN_PRESENT`. Nothing else moves it. A plain chart revision under §3.1, a reading on some other order, and the order-branch chain of §3.4 all leave an `ORDERED` order's `observation_required_minutes` untouched even when they move the patient's `risk_score`, so an `ORDERED` order may legitimately advertise a figure that is stale with respect to the patient's current score until it is administered or until that one hop reaches it. Orders may be listed and filtered by `patient_id`, by `status`, by `method` and by `panel_code`.

From `ORDERED` the order forks. The **skin arm** takes it to `ADMINISTERED`; the **serum arm** takes it to `SERUM_PENDING`; and both arms rejoin at `READ`. The two arms have genuinely different side-effect sets, and the difference is the point.

Administering the panel is an `AllergyNurse` action carrying no request body, and it is only available on the skin arm: the order must still be `ORDERED` and its `method` must be either `SKIN_PRICK` or `INTRADERMAL`, or the request is refused with `ERR_ORDER_STATE_INVALID`. Three clinical gates then apply, in the precedence order §2.8 fixes and, where two of them share rung 10, in the order stated here. The patient's `dermatographism` flag must be false, or the administration is refused with `ERR_DERMATOGRAPHISM_BLOCKS_SKIN_TEST` — this gate is evaluated first, so a patient who is both dermatographic and unprotected by an epinephrine prescription is told about the dermatographism and not about the missing epinephrine. A patient whose skin weals on contact cannot produce an interpretable skin result, ever. Whenever the patient's `risk_score` is 45 or higher, `epinephrine_on_file` must be true, or the administration is refused with `ERR_EPINEPHRINE_NOT_ON_FILE`; below 45 no epinephrine prescription is demanded. And the antihistamine washout must be complete: if `antihistamine_last_dose_at` is null the gate is satisfied outright, and otherwise at least seventy-two hours must have elapsed between that instant and the current clock, or the administration is refused with `ERR_WASHOUT_NOT_COMPLETE`. Seventy-two hours is the washout for both skin methods alike. On success the order moves `ORDERED → ADMINISTERED`, `administered_at` is stamped from the logical clock, `administered_by_user_id` is stamped from the acting identifier, and `observation_required_minutes` is re-derived from the order's own method.

**Sizing the observation window.** The observation requirement is computed the same way for a skin panel and for an immunotherapy dose, from a context that is the order's `method` for a panel and the immunotherapy-dose context for a dose. If the context is `SERUM_IGE`, the answer is exactly 0 and nothing further applies — in particular, the plan's `observation_floor_minutes` is **bypassed entirely** on that path, which is the one hard exception to the floor in this whole specification. Otherwise begin with a base of 30 minutes for `SKIN_PRICK`, 40 minutes for `INTRADERMAL`, or 30 minutes for an immunotherapy dose. If the patient's `risk_score` is 45 or higher, raise the candidate to at least 60 minutes. If the context is an immunotherapy dose and the effective schedule step is 9 or higher, raise the candidate to at least 45 minutes. If the patient's `supervision_tier` is `PHYSICIAN_PRESENT`, raise the candidate to at least 90 minutes. Finally, raise the candidate to at least the plan's `observation_floor_minutes`. Each of those four steps takes whichever value is larger, so the result is always either one of the four declared figures or the plan floor, never a sum. A `SKIN_PRICK` order for a patient scoring 44 under a plan whose floor is 20 therefore requires 30 minutes; the same order for a patient scoring exactly 45 requires 60; an `INTRADERMAL` order for a low-risk patient under a plan whose floor is 45 requires 45, because the plan floor dominates the 40-minute base; and a serum conversion for a `PHYSICIAN_PRESENT` patient scoring 100 under a plan whose floor is 120 still requires 0.

The **serum arm** is a different `AllergyNurse` action, again with no request body. The order must be `ORDERED` and its `method` must not already be `SERUM_IGE`, or the conversion is refused with `ERR_ORDER_STATE_INVALID`. The governing plan must have `allergy_serum_covered` true, or the conversion is refused with `ERR_SERUM_NOT_COVERED`. On success the order moves `ORDERED → SERUM_PENDING`, its `method` is rewritten to `SERUM_IGE`, its `billed_units` is set to the antigen count divided by four and rounded **up** to a whole number, and its `observation_required_minutes` is set to 0. Nothing is administered on this arm, so `administered_at` and `administered_by_user_id` stay null, no observation wait accrues, and — because the dermatographism abort of §3.3 is triggered by a wheal pattern that only a skin test can produce — a serum order can never abort for that reason. One consequence of the two gates above deserves stating plainly: an order *opened* with `method` `SERUM_IGE` has no transition available to it at all. It cannot be administered, because its method is not a skin method, and it cannot be converted, because its method is already `SERUM_IGE`; both refusals are `ERR_ORDER_STATE_INVALID`. Such an order therefore stays in `ORDERED` permanently, advertising an `observation_required_minutes` of 0, and can never be read or billed. `SERUM_PENDING` — and with it the serum arm's route to `READ` — is reachable only by converting an order that was opened on `SKIN_PRICK` or `INTRADERMAL`.

### 3.3. Reading a Panel, Billing It, and the Dermatographism Abort

Recording readings is the join node of the fork, and either an `AllergyNurse` or an `Otolaryngologist` may do it. The payload carries `positive_antigen_count`, the number of antigens that read positive, and may optionally carry `max_wheal_mm`, the largest wheal the reader measured, a figure from 0 through 80 inclusive carried to one decimal place. `max_wheal_mm` is validated and then discarded: it is never persisted on the order, never appears in any representation, and has no bearing on the billing figures, on the abort branch or on the chart — an out-of-range or badly typed value still fails the shape gate, but a well-formed one leaves no trace. `positive_antigen_count` is a non-negative integer and may never exceed the order's `antigen_count`; a larger figure fails the shape gate with `ERR_INVALID_REQUEST`. Because that comparison is against the order's own `antigen_count`, it is necessarily made once the order has been resolved, and it outranks the order's lifecycle gate: an over-large count quoted against an order that is still `ORDERED` reports the 400, not `ERR_ORDER_STATE_INVALID`.

Arriving from `ADMINISTERED`, the reading is subject to the observation wait: at least `observation_required_minutes` whole minutes must have elapsed since `administered_at`, or the reading is refused with `ERR_OBSERVATION_NOT_COMPLETE`. Arriving from `SERUM_PENDING`, there is no wait at all — the serum arm's window is 0 minutes by construction — and that absence of a wait is precisely what distinguishes the two arms at the join. In either case, an order in any other status is refused with `ERR_ORDER_STATE_INVALID`.

A reading in which *every* antigen came back positive is not a result. On the skin arm, when `positive_antigen_count` equals the order's `antigen_count`, the order does not reach `READ` at all: it takes the branch `ADMINISTERED → ABORTED` with `abort_reason` set to `DERMATOGRAPHISM_DETECTED`, and both `practice_charge_cents` and `patient_responsibility_cents` are forced to 0, because an all-positive skin panel is a mechanical artefact of reactive skin rather than evidence of sensitization and the practice does not bill for it. The reading itself is still recorded — the aborted order keeps a `positive_antigen_count` equal to its `antigen_count` — while `billed_units` is left exactly as it stood, which on the skin arm is the 0 the order was created with, and the abort neither recomputes the patient's `sensitized_antigen_count` nor rescores the patient. A second hop follows, caused by the abort rather than by the request: the patient's `dermatographism` flag is set to true, which permanently forecloses the skin arm of every future panel that patient will ever have — administration will be refused from then on with `ERR_DERMATOGRAPHISM_BLOCKS_SKIN_TEST`. That flag is never accepted from a request body; this cascade is the only way it can ever become true. On the serum arm this branch does not exist: an all-positive `SERUM_PENDING` order proceeds to `READ` and is billed normally.

Otherwise the order moves to `READ` — `ADMINISTERED → READ` on the skin arm, `SERUM_PENDING → READ` on the serum arm — and is priced. **The pricing sequence is fixed and its order is not negotiable.** First read the antigen count from the panel code. Second read the per-unit price from the method: 1775 cents for `SKIN_PRICK`, 2240 cents for `INTRADERMAL`, 3310 cents for `SERUM_IGE`. Third select the volume tier factor from the antigen count: a factor of exactly 1.0000 when the antigen count is 12 or fewer, exactly 0.9250 when it is 13 through 30 inclusive, and exactly 0.8500 when it is 31 or more. Fourth multiply the per-unit price by that tier factor and round the product half up to a whole number of cents — **this per-unit rounding happens before any multiplication by the unit count**. Fifth determine `billed_units`: for `SKIN_PRICK` and `INTRADERMAL` it is the antigen count itself; for `SERUM_IGE` it is the antigen count divided by four and rounded up to a whole number, because serum assays are batched four antigens at a time. Sixth set `practice_charge_cents` to the rounded per-unit gross multiplied by `billed_units`. Seventh compute the patient's per-unit share: multiply the rounded per-unit gross by ten thousand less the plan's `covered_pct_bps`, divide by ten thousand, and round that half up to a whole number of cents. Eighth set `patient_responsibility_cents` to that per-unit patient share multiplied by `billed_units`.

Rounding the extended amount instead of the per-unit amount produces different published totals, so the sequence is worth checking against worked figures. An `ENV_36` panel by `SKIN_PRICK` under a plan covering 8000 basis points takes the 0.8500 tier, giving a per-unit gross of 1509 cents, 36 billed units, a `practice_charge_cents` of 54324, a per-unit patient share of 302 cents and a `patient_responsibility_cents` of 10872. The same panel by `SERUM_IGE` under the same plan yields 9 billed units, a `practice_charge_cents` of 25326 and a `patient_responsibility_cents` of 5067. A `FOOD_24` panel by `SERUM_IGE` under a plan covering 5000 basis points takes the 0.9250 tier for a per-unit gross of 3062 cents, 6 billed units, a charge of 18372 and a patient share of 9186. A `MOLD_12` panel by `INTRADERMAL` under a plan covering 7000 basis points takes the 1.0000 tier, a per-unit gross of 2240, 12 units, a charge of 26880 and a patient share of 8064. A `VENOM_5` panel by `SKIN_PRICK` under a plan covering nothing at all charges 8875 and leaves the whole 8875 with the patient. Orders that have not reached `READ` — those still `ORDERED`, `ADMINISTERED` or `SERUM_PENDING` — and orders that reached `ABORTED` contribute nothing to either money field.

Reaching `READ` also refreshes the patient. The chart's `sensitized_antigen_count` is recomputed as the sum of `positive_antigen_count` across all of that patient's orders in status `READ`, capped at 20; the `risk_score` is recomputed under the patient's current `risk_score_variant`; and `supervision_tier` is re-derived from the new score. Both `READ` and `ABORTED` are terminal: nothing further can be done to the order.

### 3.4. Reactions and the Four-Hop Safety Cascade

Only an `AllergyNurse` records a reaction, and a reaction is attached to **exactly one** parent: either an allergy test order, named with `allergy_test_order_id`, or an immunotherapy dose, named with `immunotherapy_dose_id`. Supplying both, or supplying neither, is a shape failure rejected with `ERR_INVALID_REQUEST`; supplying exactly one that resolves to nothing is a 404 naming the missing parent. The payload carries a mandatory `systemic_grade` between 0 and 4 inclusive on the World Allergy Organization scale, a mandatory `onset_minutes` between 0 and 240 inclusive giving the minutes between administration and onset, an optional `local_wheal_mm` between 0 and 80 inclusive to one decimal place defaulting to 0, and an optional `epinephrine_given` flag defaulting to false. The server stamps `occurred_at` from the logical clock and `recorded_by_user_id` from the acting identifier. The stored event carries **both** parent identifier fields in its representation, the unused one explicitly null, so a reaction attached to a dose still shows an `allergy_test_order_id` of null rather than omitting the key. Reaction events are append-only evidence: they are never edited, never withdrawn, and — as §2.4 states — carry neither an `updated_at` nor a `version`.

Recording any reaction, of any grade, refreshes the parent's roll-up: an order's `worst_systemic_grade` becomes the largest `systemic_grade` among the events attached to it, and a dose's `reaction_grade` becomes the largest `systemic_grade` among the events attached to *it*. Both start at 0 and both are bounded by 4. Grades 0 and 1 stop there — they are documented, they raise the roll-up, and under the `PROVISIONAL` variant they contribute nothing to the risk score. The roll-up is a mutation of the parent row in the full sense of §2.4 whether or not it changes anything: a grade-0 event filed against an order whose `worst_systemic_grade` is already 0 still refreshes that order's `updated_at` and still advances its `version` by one. The same holds for an event of any grade whose parent is not in the status the cascade arms — the parent is rolled up and versioned, and nothing else happens.

A grade of **2 or higher** is a different animal, and what follows depends on which parent the event names.

**On an allergy test order** that is currently `ADMINISTERED`, the order takes the branch `ADMINISTERED → ABORTED` with `abort_reason` set to `SYSTEMIC_REACTION`, and its `practice_charge_cents` and `patient_responsibility_cents` are forced to 0 — a panel that put the patient into a systemic reaction is not billed. A second hop, caused by that abort rather than by the request, flips the patient's `risk_score_variant` to `POST_REACTION` and recomputes `risk_score` under that variant, which now includes the decayed event term of §3.1. A third hop, caused by the second hop's new score reaching 60 or more, sets the patient's `supervision_tier` to `PHYSICIAN_PRESENT`. If the new score does not reach 60, the third hop does not fire. The order branch stops there, and stopping is deliberate: the tier flip on this branch does **not** re-derive `observation_required_minutes` on the patient's `ORDERED` orders and does **not** raise `requires_supervised_administration` on their vials or `requires_physician_presence` on their bookings. Those two further hops exist only on the dose branch described next. The patient's `version` advances exactly once across this whole branch, and the tier flip rides on that single advance rather than adding a second one.

**On an immunotherapy dose** that is currently `ADMINISTERED`, the chain is longer and each link is caused by the link before it. Hop one moves the dose `ADMINISTERED → REACTION_HELD` and raises its `reaction_grade` to the larger of its previous value and the event's grade. Hop two, caused by hop one, does three things to the patient: `immunotherapy_escalation_step` is rolled back to the dose's own `escalation_step_at_dose` less two, floored at 1; `immunotherapy_status` is set to `HELD`; and `risk_score_variant` is set to `POST_REACTION` with `risk_score` recomputed under that variant. Hop three fires only if hop two's new score reached 60 or more: the patient's `supervision_tier` becomes `PHYSICIAN_PRESENT`, and every allergy test order of that patient still sitting in status `ORDERED` has its `observation_required_minutes` re-derived — which, under the new `PHYSICIAN_PRESENT` tier, raises each of them to at least 90 minutes. Each such order is re-derived from **its own `method`**, exactly as it was at creation, with no schedule step in play, and that has one consequence worth stating because it looks like an omission: an order whose `method` is `SERUM_IGE` — the dead end of §3.2, which sits in `ORDERED` for ever — is re-derived along with the rest and comes back to exactly 0, because the `SERUM_IGE` context of §3.2 short-circuits ahead of both the tier rule and the plan floor. So the hop reaches every `ORDERED` order of that patient, but it raises only the skin-method ones to 90; the serum ones are touched, versioned and left at 0. Hop four fires only because hop three changed the tier, and it reaches across two more aggregates: every extract vial of that patient in status `LABEL_VERIFIED` or `IN_USE` has `requires_supervised_administration` set to true, and every procedure booking of that patient in status `SCHEDULED` has `requires_physician_presence` set to true. A booking made three weeks ago therefore acquires, without anyone touching it, a hard requirement that an attending physician be named when it starts.

Each of the rows those four hops touch is mutated in the full sense of §2.11 — `updated_at` refreshed, `version` incremented — and the patient's version bump in particular is what a stale `expected_patient_version` will collide with. The patient's `version` advances exactly once for the whole chain — one bump, not one per hop, however many hops fire — while each allergy test order, each extract vial and each procedure booking that the later hops reach advances its own `version` by one. Reaction events can be listed and filtered by `allergy_test_order_id` or by `immunotherapy_dose_id`, which is how the practice walks from either parent to its reaction history.

### 3.5. Immunotherapy: Compounding, Verification, Dosing and Escalation

Immunotherapy is the part of the practice where a clerical slip is a patient-safety event, so it is built as a chain of small, individually gated steps owned entirely by the `AllergyNurse` role.

**Compounding a vial.** A nurse compounds a patient-specific extract vial by naming the `patient_id`, naming the `supply_lot_id` of the concentrate it is drawn from, choosing a `dilution_code`, supplying the `label_text` and the beyond-use instant `expires_at`, optionally supplying a `volume_ml_initial` between 1.00 and 10.00 millilitres to two decimal places (defaulting to 5.00 when the key is omitted altogether, while an explicitly null `volume_ml_initial` is a shape failure rather than a request for the default), and supplying `expected_patient_version` as described in §2.7. The referenced lot must hold allergen concentrate — a lot whose `item_type` is anything other than `ALLERGEN_CONCENTRATE` is refused with `ERR_LOT_ITEM_TYPE_MISMATCH`, and a lot in status `QUARANTINED` is refused with `ERR_LOT_STATE_INVALID`. The beyond-use instant must fall strictly after the current logical clock and no more than three hundred and sixty-five days after it. The four colour-coded dilutions are `YELLOW_1_10`, `BLUE_1_100`, `GREEN_1_1000` and `SILVER_1_10000`; only the first two are ever demanded by the escalation schedule, so a vial compounded at `GREEN_1_1000` or `SILVER_1_10000` will never satisfy a dose draw. The `label_text` must be composed exactly as the patient's `mrn`, then a vertical bar, then the `dilution_code`, then a vertical bar, then the year-month-day date portion of `expires_at` — three parts, two separators, no spaces. A `label_text` that does not match that composition fails the shape gate with `ERR_INVALID_REQUEST`. Because the composition is measured against the patient's own `mrn`, this is the one rung-3 check in the service that cannot be judged before a **body** reference has been resolved — two further rung-3 checks wait on a resolved row as well, the study metric set of §3.7 and the reading count of §3.3, but each of those waits only on its endpoint's *path* identifier, so this remains the only place where rung 3 sits behind rung 5: it is evaluated after `patient_id` has been proven to exist but before `supply_lot_id` is looked up, so a request that both misspells its label and names a `patient_id` resolving to nothing reports `ERR_PATIENT_NOT_FOUND`, whereas one that misspells its label and names a `supply_lot_id` resolving to nothing reports `ERR_INVALID_REQUEST`. The two `expires_at` window checks, by contrast, are judged before any reference is resolved at all, so either of them beats every 404 on this endpoint; both of them report `ERR_INVALID_REQUEST` at rung 3 and never `ERR_VIAL_EXPIRED`, which belongs to verification and dosing alone. The date portion the label must carry is taken from the *trimmed* spelling of `expires_at`, so leading or trailing whitespace in the submitted instant — tolerated at rung 3 and preserved in the stored `expires_at` per §2.4 — need not be reproduced inside `label_text`.

The new vial is created in status `MIXED` with `mixed_by_user_id` stamped from the acting identifier, `verified_by_user_id` null, `volume_ml_remaining` equal to `volume_ml_initial`, `volume_ml_dispensed_total` 0.00, `volume_ml_wasted` 0.00, `requires_supervised_administration` false and `discard_reason` null. Every millilitre figure this section discusses — a vial's `volume_ml_initial`, `volume_ml_remaining`, `volume_ml_dispensed_total` and `volume_ml_wasted`, and a dose's `volume_ml` — is carried to two decimal places per §2.6 and is emitted as a JSON **number**, never as a string, and a JSON number does not preserve trailing zeros: a bucket holding 5.00 mL therefore renders as `5.0`, an empty bucket renders as `0.0`, a 0.30 mL figure renders as `0.3`, and a 0.05 mL draw renders as `0.05`. Compounding also **supersedes**: if that patient already holds one or more vials in status `LABEL_VERIFIED` or `IN_USE`, every one of them is moved to `DISCARDED` with `discard_reason` `SUPERSEDED`, each one's `volume_ml_remaining` is moved into its `volume_ml_wasted` and its `volume_ml_remaining` is set to 0.00, leaving the ledger identity of §2.10 intact. Only those two statuses are swept: a vial of the same patient still sitting in `MIXED` is left exactly as it stands, as is one already `EXHAUSTED` or `DISCARDED`, and the vial being compounded never supersedes itself. Finally the patient's own `version` increments by one, which is the observation point the next compounder's `expected_patient_version` will be measured against. Vials can be listed and filtered by `patient_id`, by `supply_lot_id`, by `status` and by `dilution_code`.

**Verifying the label.** No vial may be drawn from until a *second* nurse has verified its label. The verifier submits `label_text_confirmation`, retyped by hand. The vial must be in status `MIXED`, or the verification is refused with `ERR_VIAL_STATE_INVALID`. The acting identifier must differ from `mixed_by_user_id`, or the verification is refused with `ERR_SELF_VERIFICATION_FORBIDDEN`. The retyped `label_text_confirmation` must equal the stored `label_text` character for character, or the verification is refused with `ERR_VIAL_LABEL_MISMATCH`. And the logical clock must still be strictly before `expires_at`, or the verification is refused with `ERR_VIAL_EXPIRED`. On success the vial moves `MIXED → LABEL_VERIFIED`, `verified_by_user_id` is stamped, and the patient's `immunotherapy_status` is re-derived from the patient's `immunotherapy_escalation_step`: it becomes `BUILD_UP` when that step is 6 or lower, and `MAINTENANCE` when that step is 7 or higher. This is normally where the status leaves `NONE` for the first time, but the re-derivation is unconditional and does not consult the previous status: a verification for a patient already at `BUILD_UP` or `MAINTENANCE` simply rewrites the posture the step already implies, and a verification for a patient sitting at `HELD` lifts that hold. The escalation step itself is never moved by a verification, and the patient row is mutated in the full sense of §2.11 — its `updated_at` refreshed and its `version` incremented — on every successful verification.

**Discarding a vial.** A nurse may discard a vial in status `MIXED`, `LABEL_VERIFIED` or `IN_USE` — the three arcs `MIXED → DISCARDED`, `LABEL_VERIFIED → DISCARDED` and `IN_USE → DISCARDED`, which have identical effects — by supplying a `discard_reason` of either `BEYOND_USE_DATE` or `CONTAMINATION`; the third reason, `SUPERSEDED`, is reserved for the supersession cascade above and is never accepted from a request body. A vial already `EXHAUSTED` or `DISCARDED` is refused with `ERR_VIAL_STATE_INVALID`. The discard moves the whole of `volume_ml_remaining` into `volume_ml_wasted` and sets `volume_ml_remaining` to 0.00, so a vial of 5.00 mL that had dispensed 4.70 mL before a contamination discard ends with 0.30 mL wasted, 0.00 remaining, and the identity still closing. A discard touches the vial and nothing else: the patient's row is not mutated at all, so neither `immunotherapy_status` nor `immunotherapy_escalation_step` moves and the patient's `version` does not advance, and the doses already drawn from that vial keep their statuses and their recorded `volume_ml`. `EXHAUSTED` and `DISCARDED` are the vial's two terminal states.

**Sizing the next dose.** Every dose volume is computed by the server, and a client-supplied volume is never honoured. The computation reads the patient's `immunotherapy_escalation_step` — call it the *pre-rollback* step — together with `last_dose_administered_at`, and proceeds in three stages whose order matters. Stage one fixes the **required dilution from the pre-rollback step**: `BLUE_1_100` when that step is 6 or lower, `YELLOW_1_10` when it is 7 or higher. Stage two computes the gap: if `last_dose_administered_at` is null the gap is 0 whole days, and otherwise it is the number of whole days between that instant and the current clock, taken downward. The gap rollback is then applied **exactly once**, and which rollback applies is also decided on the pre-rollback step: when that step is 6 or lower and the gap is 14 whole days or more, the effective step becomes the pre-rollback step less two, floored at 1; when the pre-rollback step is 7 or higher and the gap is 28 whole days or more, the effective step becomes the pre-rollback step less three, floored at 1; otherwise the effective step is the pre-rollback step unchanged. Stage three reads the volume from the **post-rollback** effective step, using this schedule: step 1 draws 0.05 mL, step 2 draws 0.10, step 3 draws 0.20, step 4 draws 0.30, step 5 draws 0.40, step 6 draws 0.50, and the maintenance half of the schedule repeats the same ladder — step 7 draws 0.05, step 8 draws 0.10, step 9 draws 0.20, step 10 draws 0.30, step 11 draws 0.40, step 12 draws 0.50. Every scheduled figure is already a whole multiple of 0.05 mL, and the volume is taken down to the nearest 0.05 mL increment as a matter of form. The effective step is recorded on the dose as `escalation_step_at_dose` and the gap as `gap_days_at_dose`.

Deciding the band on the pre-rollback step and the volume on the post-rollback step is not a stylistic choice; evaluating both on the same step gives the wrong answer whenever a rollback crosses the seam between step 6 and step 7. A patient at pre-rollback step 8 returning after a 30-day gap requires a `YELLOW_1_10` vial, because the maintenance band is read from step 8, but draws 0.40 mL, because the rollback of three steps lands on step 5. Reading the band after the rollback would have demanded `BLUE_1_100` and rejected a perfectly correct vial. The same patient returning after 27 days stays at step 8 and draws 0.10 mL, because 27 is short of 28. A patient at step 2 returning after exactly 14 days rolls back to step 1 and draws 0.05 mL, floored at the bottom of the schedule. A patient at step 6 returning after 21 days rolls back to step 4 and draws 0.30 mL. A patient at step 7 returning the same day stays at step 7 and draws 0.05 mL. The schedule never exceeds step 12.

**Administering the dose.** A nurse names the `immunotherapy_vial_id` and, when supervision is in force, a `supervising_user_id` — the identifier of the supervising `Otolaryngologist`. The dose inherits its patient from the vial; there is no patient field on the request. The vial must be in status `LABEL_VERIFIED` or `IN_USE`, or the draw is refused with `ERR_VIAL_STATE_INVALID`. The clock must still be strictly before the vial's `expires_at`, or it is refused with `ERR_VIAL_EXPIRED`. Whenever the patient's `risk_score` is 45 or higher, `epinephrine_on_file` must be true, or it is refused with `ERR_EPINEPHRINE_NOT_ON_FILE`. The vial's `dilution_code` must equal the required dilution derived from the pre-rollback step, or it is refused with `ERR_DILUTION_MISMATCH`. If the vial's `requires_supervised_administration` is true, `supervising_user_id` must be supplied, or it is refused with `ERR_SUPERVISION_REQUIRED`; an explicitly null `supervising_user_id` clears the shape gate but counts as *not supplied* for this test. When that flag is false the field may be omitted and defaults to null, and a `supervising_user_id` volunteered anyway is simply stored as given. Whatever is stored is an opaque string of one to a hundred and twenty characters, taken verbatim and never trimmed: it is never resolved against the staff directory and never role-checked, so the requirement is that a supervisor be *named*, not that the name resolve to an existing user or to one holding the `Otolaryngologist` role. Last of all, the vial's `volume_ml_remaining` must be at least the computed `volume_ml`, or the draw is refused with `ERR_INSUFFICIENT_VIAL_VOLUME` before any volume moves. Three things that might be expected to gate a draw do not. The patient's `immunotherapy_status` is never consulted, so a patient sitting at `HELD` after a systemic reaction may still be dosed — the hold is a posture the chart advertises, not a lock on this endpoint. Nothing bars a second draw while an earlier dose of the same patient is still `ADMINISTERED` and awaiting clearance, so several uncleared doses may legitimately coexist, each carrying its own `escalation_step_at_dose`. And no version field is accepted here at all, so a draw against a patient whose chart has moved since the client last read it is never refused for staleness.

On success the dose is created in status `ADMINISTERED` with `observation_cleared_at` null and `reaction_grade` 0, `administered_at` stamped from the logical clock and `administered_by_user_id` from the acting identifier, and `observation_required_minutes` sized by the immunotherapy-dose context of §3.2 — which is where the late-step rule bites: an effective step of 9 or higher raises the window to at least 45 minutes. That test reads the **post-rollback** effective step — the very figure recorded as `escalation_step_at_dose` — and never the patient's stored `immunotherapy_escalation_step`: a patient stored at step 10 who rolls back to step 7 on a 28-day gap is sized *without* the 45-minute bump, while a patient stored at step 12 who rolls back to step 9 still receives it. The vial moves `LABEL_VERIFIED → IN_USE` on the first draw; its `volume_ml_remaining` decreases and its `volume_ml_dispensed_total` increases by the drawn volume; and if the remaining volume then falls below 0.05 mL the vial moves `IN_USE → EXHAUSTED` and stops being a valid dose source, with no volume moving on that transition. The patient's `last_dose_administered_at` is set to this dose's `administered_at`, and that write is a mutation of the patient row in the full sense of §2.11 — `updated_at` refreshed, `version` advanced by one — so every administration moves the counter a later compounder's `expected_patient_version` is measured against, while `immunotherapy_status` and `immunotherapy_escalation_step` are left exactly where they stood. Doses can be listed and filtered by `immunotherapy_vial_id`, by `status` and by `patient_id`; the last of those is resolved *through* the dose's vial, because a dose stores no patient identifier of its own and its representation carries none.

**Clearing observation.** Once the window has elapsed, the nurse discharges the patient. The request carries no body. The dose must be `ADMINISTERED` with `observation_cleared_at` still null, or the clearance is refused with `ERR_DOSE_STATE_INVALID`. The dose's `reaction_grade` must then be 1 or lower, or the clearance is refused with that same `ERR_DOSE_STATE_INVALID` — the grade is treated as a lifecycle matter and judged at rung 7, *ahead* of the window, so a dose that is simultaneously grade-2-or-worse and short of its window reports `ERR_DOSE_STATE_INVALID` and never `ERR_OBSERVATION_NOT_COMPLETE`. In practice a dose that produced a grade-2-or-worse reaction has already left `ADMINISTERED` for `REACTION_HELD` and can never be cleared. Only then is the clock consulted: at least `observation_required_minutes` whole minutes must have elapsed since `administered_at`, or it is refused with `ERR_OBSERVATION_NOT_COMPLETE`. On success the dose moves `ADMINISTERED → CLEARED`, `observation_cleared_at` is stamped, the patient's `immunotherapy_escalation_step` advances to the dose's `escalation_step_at_dose` plus one but never beyond 12, and `immunotherapy_status` is re-derived from the new step: `BUILD_UP` when the new step is 6 or lower, `MAINTENANCE` when it is 7 or higher. Clearing a dose is also the moment at which a patient who was `HELD` after a systemic reaction re-enters the build-up or maintenance posture. If the vial's remaining volume is below 0.05 mL it moves `IN_USE → EXHAUSTED` here as well, and the vial row is versioned only when that move actually fires: a clearance moves no volume — a dose counts as dispensed under `ADMINISTERED` and under `CLEARED` alike — so in the ordinary case a clearance leaves the vial completely untouched, its `updated_at` and `version` unchanged.

**Voiding a dose.** A dose drawn in error can be undone, but only briefly. The nurse supplies a mandatory `void_reason` of `DRAWN_IN_ERROR`, `WRONG_VIAL` or `PATIENT_DEFERRED`; the value is validated against those three members and then discarded — unlike a booking's `cancel_reason` or a vial's `discard_reason`, a dose carries no `void_reason` field at all, so the reason is not stored and never appears in any dose representation. The dose must still be `ADMINISTERED` with `observation_cleared_at` null, or the void is refused with `ERR_DOSE_STATE_INVALID` at rung 7; only then is the window measured, and no more than fifteen minutes may have elapsed since `administered_at`, or the void is refused with `ERR_VOID_WINDOW_CLOSED`. That elapsed figure is whole minutes taken downward, exactly as the observation window measures its own, so a void attempted fifteen minutes and fifty-nine seconds after administration is still inside the window while one attempted at sixteen minutes flat is not. The void moves the dose `ADMINISTERED → VOIDED`, returns its `volume_ml` to the vial's `volume_ml_remaining` and subtracts the same figure from the vial's `volume_ml_dispensed_total`, so the ledger closes with no residue at all. A vial that had gone `EXHAUSTED` returns `EXHAUSTED → IN_USE` when the returned volume brings its remaining volume back to 0.05 mL or more; the vial row is mutated in the full sense of §2.11 on every void whether or not its status moved, because a void genuinely rewrites its volume buckets. The patient's `last_dose_administered_at` is recomputed as the `administered_at` of that patient's most recent remaining dose in status `ADMINISTERED`, `CLEARED` or `REACTION_HELD`, or null when none remains. The patient's `immunotherapy_escalation_step` is deliberately **left untouched** — a void neither advances the schedule nor rolls it back, and because a `VOIDED` dose never contributes to `last_dose_administered_at`, it also does not reset the gap clock. The patient's `immunotherapy_status` is left untouched along with it and is never re-derived here, so whatever posture the last verification or clearance wrote — including a `HELD` posture — survives a void exactly as it stood. `CLEARED` and `VOIDED` are the dose's terminal states; `REACTION_HELD` is not terminal in name but nothing further can be done to a held dose.

### 3.6. Balloon Sinuplasty: Candidacy, Authorization and Two Revision Loops

An `Otolaryngologist` opens a balloon sinuplasty case by naming the `patient_id`, choosing a `laterality` of `LEFT`, `RIGHT` or `BILATERAL`, and listing the `sinuses` planned for dilation as a non-empty array of distinct members drawn from `MAXILLARY`, `FRONTAL` and `SPHENOID`. From those two inputs the server derives `planned_device_count`: the number of sinuses listed, doubled when `laterality` is `BILATERAL` and taken as-is otherwise. A bilateral case on the maxillary and frontal sinuses therefore plans four devices. The `sinuses` array is stored and echoed back exactly as submitted, in the order submitted and never sorted or normalised. The new case is created in status `DRAFT` with `candidacy_status` `UNDETERMINED`, `revision_round` 0, `authorized_device_count` 0, `criteria_met_count` 0, `contiguous_management_days` 0, `cumulative_management_days` 0, and `pinned_policy_version`, `auth_expires_at`, `payer_reference`, `submitted_by_user_id` and `documented_by_user_id` all null. Its `evaluation_variant` is fixed from the patient's plan at creation: `POLICY_STRICT` when the plan's `requires_prior_auth` is true, `CLINICAL_BROAD` when it is false. That choice is made once and never revisited: a later plan amendment that flips `requires_prior_auth`, or a chart revision that moves the patient onto a different plan, leaves an existing case's `evaluation_variant` exactly where creation put it — even though the plan's *numeric* thresholds are re-read live at every evaluation. Opening a case does not touch the patient row: the endpoint accepts no version field and the patient's `version` does not move. Cases can be listed and filtered by `patient_id`, by `status` and by `candidacy_status`.

**Documenting the case.** A `DRAFT` case carries no clinical evidence, and a case that is not `DRAFT` refuses documentation with `ERR_CASE_STATE_INVALID`. The documenting physician supplies three things. `documented_therapies` is the medical-management history and must be a non-empty array; each item is an object carrying a `therapy_code` of `INCS`, `ABX`, `SALINE` or `ORAL_STEROID`, a `start_date` and an `end_date`, both calendar dates, and no item may have a `start_date` later than its `end_date`. `documented_criteria_codes` is the array of candidacy criteria the physician asserts, with members drawn from `CT_OPACIFICATION`, `SNOT22_GE_20`, `FAILED_INCS`, `FAILED_ABX`, `FAILED_SALINE` and `ENDOSCOPY_FINDING`; the key is mandatory, but unlike `documented_therapies` the array **may be empty**, and its members need not be distinct — a repeated code clears the shape gate untouched and is collapsed only later, inside the evaluation. And `ct_study_date` is the calendar date of the CT sinus study, or null when no CT is on file; the key itself is mandatory even so, so an explicit null is accepted while omitting the key altogether fails the shape gate. Nothing constrains `ct_study_date` to the past. On success the case moves `DRAFT → DOCUMENTED`, `documented_by_user_id` is stamped from the acting identifier, and the candidacy evaluation runs. The case stores both submitted arrays **verbatim** — `documented_therapies` in the order submitted, `documented_criteria_codes` with any duplicates intact — and the evaluation writes back only four derived figures: `criteria_met_count`, `contiguous_management_days`, `cumulative_management_days` and `candidacy_status`. The admissible-code list itself is never stored on the case and is visible only through the candidacy read described below. Documentation is a once-only act, because `DRAFT` is its sole legal origin and the same request leaves `DRAFT` behind, and it leaves the patient row untouched.

**Evaluating candidacy.** The evaluation produces four figures and a verdict. Begin by sorting the documented therapies by `start_date` ascending, using `end_date` ascending as the tie-break. The span of one therapy is the number of days from its `start_date` to its `end_date` counting **both endpoints**, so a course from the 1st to the 14th of a month spans 14 days. `cumulative_management_days` is the sum of every therapy's span, whether or not the courses overlap or leave gaps. `contiguous_management_days` comes from a merge pass over the sorted list: walk the therapies in order, and start a new merged interval whenever the therapy's `start_date` falls more than one calendar day after the running interval's end date; otherwise extend the running interval's end date to the later of its current end and the therapy's `end_date`. Adjacency counts as contiguous — a course ending on the 14th and a course starting on the 15th leave a gap of zero days and merge into one span. `contiguous_management_days` is then the span of the longest merged interval, or 0 when no therapies were documented at all.

Next decide which criteria codes are **admissible**, after deduplicating the submitted list — each code is kept at the position of its **first** appearance and later repeats are dropped, so the surviving sequence is first-appearance order and never the declaration order of the enum — and set `criteria_met_count` to the number that survive. That same first-appearance order is what `admissible_criteria_codes` reports wherever it is returned. Here the two variants diverge, and so does the management-days figure the verdict consults.

Under **`POLICY_STRICT`**, the variant a case acquires whenever the plan's `requires_prior_auth` was true at the moment the case was opened, the verdict consults `contiguous_management_days` — the longest single merged span only, so separate courses do not add up. Admissibility is cross-checked: `FAILED_INCS` counts only when at least one documented therapy carries `therapy_code` `INCS`; `FAILED_ABX` counts only when at least one carries `ABX`; `FAILED_SALINE` counts only when at least one carries `SALINE`; and `CT_OPACIFICATION` counts only when `ct_study_date` is no more than the plan's `requires_ct_within_months` multiplied by thirty days old, measured against the logical clock's current date. That age is the whole count of days from `ct_study_date` to the clock's current date and the comparison is inclusive, so an age exactly equal to the allowance still counts; a `ct_study_date` lying in the *future* yields a negative age and is therefore trivially inside the allowance, while a null `ct_study_date` strikes the code out for want of any CT at all. `requires_ct_within_months`, like the plan's two numeric thresholds, is read live at each evaluation and never from a pinned plan revision. `SNOT22_GE_20` and `ENDOSCOPY_FINDING` carry no cross-check and always count when asserted, and the therapy cross-checks look only at the `therapy_code` values present in `documented_therapies`, paying no attention to how long those courses ran or when.

Under **`CLINICAL_BROAD`**, the variant a case acquires whenever the plan's `requires_prior_auth` was false at the moment the case was opened, the verdict consults `cumulative_management_days` — every documented course adds up regardless of the gaps between them. Every asserted code that is a declared member counts, with no therapy cross-check whatsoever and no CT recency test at all.

The verdict itself is the same expression under both variants: `candidacy_status` becomes `ELIGIBLE` when `criteria_met_count` is at least the plan's `min_documented_criteria` **and** the variant's management-days figure is at least the plan's `min_medical_management_days`, and `INELIGIBLE` otherwise. A case still in `DRAFT` has `candidacy_status` `UNDETERMINED` and takes part in no evaluation.

The divergence between the variants is easiest to see on one worked history. A patient documented with an `INCS` course running 2026-06-01 to 2026-06-14 and an `ABX` course running 2026-06-20 to 2026-07-03, asserting `CT_OPACIFICATION`, `FAILED_INCS` and `FAILED_ABX`, with a `ct_study_date` of 2026-05-01, observed at a clock date of 2026-08-01, under a plan demanding 28 management days and 3 criteria: `cumulative_management_days` is 28 and `contiguous_management_days` is 14, because the six-day gap prevents a merge. Under `POLICY_STRICT` all three criteria are admissible but 14 falls short of 28, so the case is `INELIGIBLE`. Under `CLINICAL_BROAD` the same three criteria count and 28 meets 28 exactly, so the case is `ELIGIBLE`. Change the second course to `INCS` running 2026-06-15 to 2026-06-28 and the two courses merge into one span of 28 days, so `contiguous_management_days` becomes 28 rather than 14. Separately, a `POLICY_STRICT` case asserting `CT_OPACIFICATION`, `SNOT22_GE_20` and `FAILED_ABX` while documenting only an `INCS` course has `FAILED_ABX` struck out for want of a matching therapy, leaving `criteria_met_count` at 2 and the case `INELIGIBLE`. And a `POLICY_STRICT` case with a `ct_study_date` of 2025-06-01 observed at 2026-08-01 under a plan whose `requires_ct_within_months` is 12 — that is, a 360-day allowance — has a CT that is 426 days old, so `CT_OPACIFICATION` is struck out.

**Reading candidacy without touching the case.** A `PracticeAdmin`, an `Otolaryngologist` or a `PayerLiaison` may recompute and read the determination without mutating anything. This read is the tool the practice uses to compare the two variants side by side, and it returns exactly nine fields: `evaluation_variant`, `criteria_met_count`, `admissible_criteria_codes` (the array of codes that survived the admissibility test), `contiguous_management_days`, `cumulative_management_days`, `management_days_metric` (the figure the active variant actually consults), `min_documented_criteria_required` and `min_medical_management_days_required` (the plan's two thresholds as read at this instant), and `candidacy_status`. The read recomputes from the case's stored documentation and from the patient's plan **as both stand at this instant**, but it takes `evaluation_variant` from the case rather than re-deriving it from the plan, so the side-by-side comparison it supports is between the two variants' *formulas*, not a way to move a case onto the other variant. A case still in `DRAFT` is put through exactly the same arithmetic: because it carries no documentation, `criteria_met_count` comes back 0, `admissible_criteria_codes` comes back empty and all three day figures come back 0, alongside the plan's two live thresholds, and `candidacy_status` is then forced to `UNDETERMINED` whatever the arithmetic produced. It performs no state transition and increments no `version`.

**Submitting to the payer.** A `PayerLiaison` files an authorization submission with no request body. Three origins are legal, and all three end in `AUTH_SUBMITTED`: `DOCUMENTED → AUTH_SUBMITTED`, `INFO_REQUESTED → AUTH_SUBMITTED` and `AUTH_EXPIRED → AUTH_SUBMITTED`. From `DOCUMENTED`, the plan must require prior authorization — a case whose plan has `requires_prior_auth` false has no payer pathway at all and its submission is refused with `ERR_CASE_STATE_INVALID` — and the case's `candidacy_status` must be `ELIGIBLE`, or the submission is refused with `ERR_CANDIDACY_NOT_ELIGIBLE`. From `INFO_REQUESTED`, the case's `revision_round` must be strictly below 2; the submission then increments `revision_round` by one, and a third attempt made when `revision_round` already stands at 2 is refused with `ERR_REVISION_LIMIT_REACHED`. From `AUTH_EXPIRED`, the submission resets `revision_round` to 0, `authorized_device_count` to 0 and `auth_expires_at` to null, giving an expired authorization a fresh revision budget as it re-enters the loop. A submission from any other status is refused with `ERR_CASE_STATE_INVALID`. Neither re-entry origin repeats the `DOCUMENTED` gates: an `INFO_REQUESTED` or `AUTH_EXPIRED` case is resubmitted without re-testing the plan's `requires_prior_auth` and without re-testing `candidacy_status`, so a case whose plan has since dropped its prior-authorization requirement, and a case whose stored verdict a later threshold amendment would now overturn, both resubmit unimpeded. No submission of any origin re-runs the candidacy evaluation either: `criteria_met_count`, the two management-day figures and `candidacy_status` stay exactly as the case's single documentation left them, however stale they have become. A resubmission likewise leaves `payer_reference` holding whatever the previous round wrote, for the next decision to overwrite.

Every submission, whichever origin it came from, stamps `submitted_by_user_id` from the acting identifier and stamps `pinned_policy_version` with the plan's `version` **as read at that instant**. That pin is then frozen for the life of the authorization: later plan amendments move the plan's `version` but never the pin, and the divergence between the two is what §3.9 detects at procedure start. Each fresh submission re-stamps the pin, so a resubmission taken after an amendment pins the amended `version` and overwrites the earlier value — which is exactly how a case that has drifted out of §3.9's version check is brought back into line — while between two submissions nothing moves the pin. Nothing ever returns it to null: neither a payer decision of any kind nor the `AUTH_EXPIRED` reset clears `pinned_policy_version`, even though that reset does clear `authorized_device_count` and `auth_expires_at`.

**Recording the payer's answer.** A `PayerLiaison` records the decision by supplying a `decision` of `APPROVED`, `DENIED` or `INFO_REQUESTED` together with the payer's `payer_reference` number, a string of one to sixty characters stored verbatim — it is never trimmed, never pattern-checked and never required to be unique across cases. The case must be `AUTH_SUBMITTED`, or the decision is refused with `ERR_CASE_STATE_INVALID`, and the acting identifier must differ from `submitted_by_user_id`, or it is refused with `ERR_SELF_DECISION_FORBIDDEN` — the person who filed a submission may not also be the person who records what the payer said about it. All three decisions store `payer_reference`. `APPROVED` moves the case `AUTH_SUBMITTED → AUTHORIZED`, sets `authorized_device_count` to whichever is smaller of the case's `planned_device_count` and the plan's `max_balloon_devices`, and sets `auth_expires_at` to the current logical-clock instant advanced by the plan's `auth_validity_days` whole days. Both of those figures are read from the plan **as it stands when the decision is recorded**, never from the plan revision the submission pinned: `pinned_policy_version` records only what the case was submitted against and never governs the numbers written here, so an amendment landing between the submission and the decision genuinely changes the device ceiling and the validity window this approval grants. An approval does not reset `revision_round` either — it keeps whatever count the revision loop had reached. `DENIED` moves the case `AUTH_SUBMITTED → DENIED` and sets `authorized_device_count` to 0 while leaving `auth_expires_at` exactly as it stood; `DENIED` is terminal, and a denied case can never be scheduled or resubmitted. `INFO_REQUESTED` moves the case `AUTH_SUBMITTED → INFO_REQUESTED` and leaves `revision_round` alone, for the next submission to increment; it leaves `authorized_device_count`, `auth_expires_at` and `pinned_policy_version` untouched as well.

Two loops therefore exist in this lifecycle. The short one runs `AUTH_SUBMITTED → INFO_REQUESTED → AUTH_SUBMITTED` and may be traversed at most twice before the revision cap bites. The long one runs `AUTHORIZED → AUTH_EXPIRED → AUTH_SUBMITTED` and reopens the whole payer conversation from scratch. Beyond the payer conversation the case still has scheduling states: `AUTHORIZED → SCHEDULED` and, on the self-pay path, `DOCUMENTED → SCHEDULED`; then `SCHEDULED → COMPLETED`, which is terminal; and, when a booking is cancelled, the compensating returns `SCHEDULED → AUTHORIZED` for an authorized case or `SCHEDULED → DOCUMENTED` for a self-pay one. All of those are driven by the booking lifecycle of §3.9 rather than by any case endpoint of their own.

### 3.7. Audiology, Sleep Studies and the Device Trial Economy

An `Otolaryngologist` orders a diagnostic study by naming the `patient_id` and a `study_type` of `AUDIOMETRY`, `SLEEP_HSAT` or `SLEEP_PSG`. The study is created in status `ORDERED` with `superseded_dispense_count` 0, `version` 1, and `pta_db_hl`, `word_recognition_pct`, `ahi`, `recommendation`, `performed_at`, `performed_by_user_id` and `interpreted_by_user_id` all null. Studies may be listed and filtered by `patient_id`, by `study_type`, by `status` and by `recommendation`.

**Recording results.** An `Audiologist` records the measurements, and the metric set the payload must carry is fixed entirely by the study's `study_type`. An `AUDIOMETRY` study requires both `pta_db_hl` and `word_recognition_pct` and forbids `ahi`. A `SLEEP_HSAT` or `SLEEP_PSG` study requires `ahi` and forbids both `pta_db_hl` and `word_recognition_pct`. Supplying the wrong metric set — a missing required metric or a forbidden one present — is a shape failure and returns `ERR_INVALID_REQUEST` at rung 3, before the study's own state is even consulted. That one check is the exception to this rung's usual precedence over rung 4: because the demanded metric set is fixed by the study's own `study_type`, it cannot be judged until the path identifier has been resolved, so a wrong metric set aimed at a `studyId` matching no row reports `ERR_DIAGNOSTIC_STUDY_NOT_FOUND`, whereas every other rung-3 violation on this endpoint — an unknown field, a non-numeric metric, a metric outside its range or one carrying two decimal places — is judged before the path is resolved and beats the 404. Each metric is a number carried to at most one decimal place: `pta_db_hl` lies between 0 and 120 inclusive, `word_recognition_pct` between 0 and 100 inclusive, and `ahi` between 0 and 120 inclusive. Each supplied metric is stored and echoed back in exactly the numeric form it arrived in, so an integral `40` is never re-rendered as `40.0`, and an explicit null offered for any of the three is a shape failure rather than a request to leave that metric unset. The metrics the study's type forbids are never written and remain null for ever. The study must be `ORDERED`, or the request is refused with `ERR_STUDY_STATE_INVALID`. On success the study moves `ORDERED → PERFORMED`, `performed_at` is stamped from the logical clock, `performed_by_user_id` is stamped from the acting identifier, and the study's `version` increments by one.

**Interpreting.** Either an `Otolaryngologist` or an `Audiologist` interprets a `PERFORMED` study, with no request body. A study in any other status is refused with `ERR_STUDY_STATE_INVALID`, and the acting identifier must differ from `performed_by_user_id`, or the interpretation is refused with `ERR_SELF_INTERPRETATION_FORBIDDEN` — the clinician who measured may not also be the clinician who reads. On success the study moves `PERFORMED → INTERPRETED`, which is terminal; `interpreted_by_user_id` is stamped; `recommendation` is computed; and `version` increments by one.

**The recommendation.** For an `AUDIOMETRY` study the recommendation is `HEARING_AID` when `pta_db_hl` is 40 or greater, and `OBSERVATION` otherwise; `word_recognition_pct` is recorded for the chart and never enters the decision. For a `SLEEP_HSAT` or `SLEEP_PSG` study — the two sleep types are treated identically — the recommendation is read from `ahi` in three bands: `OBSERVATION` when `ahi` is strictly below 5; `ORAL_APPLIANCE` when `ahi` is at least 5 and at most 30; and `CPAP` when `ahi` is strictly above 30. Both band bounds are inclusive on the `ORAL_APPLIANCE` band, so an `ahi` of exactly 5 recommends an oral appliance rather than observation, and an `ahi` of exactly 30 recommends an oral appliance rather than CPAP, while 30.1 recommends CPAP. A `pta_db_hl` of exactly 40 recommends a hearing aid; 39.9 recommends observation. Only two of the four recommendations lead to a dispensable device: a `HEARING_AID` recommendation admits a `HEARING_AID` device, and an `ORAL_APPLIANCE` recommendation admits an `ORAL_APPLIANCE` device. A `CPAP` recommendation and an `OBSERVATION` recommendation admit no device at all, so any dispense attempted against them is refused with `ERR_DEVICE_TYPE_NOT_RECOMMENDED`.

**Dispensing a device.** An `Audiologist` dispenses a unit by naming the `diagnostic_study_id` it is justified by, the `supply_lot_id` it came out of, the `device_type`, the `device_serial`, the fitted `ear` (`LEFT`, `RIGHT`, `BOTH`, or `NA` for an oral appliance — the value is never cross-checked against `device_type`, so any of the four is accepted for either device), the retail `price_cents` between 1 and 2000000 inclusive, and the `expected_study_version`. The gates run in ladder order. The study and the lot must exist. The `expected_study_version` must equal the study's current `version`, or the dispense is refused with `ERR_STALE_STUDY_VERSION`, HTTP 412. The study must be `INTERPRETED`, or the dispense is refused with `ERR_STUDY_STATE_INVALID`; a lot that is `QUARANTINED`, or whose `expires_at` the logical clock has reached, is refused with `ERR_LOT_STATE_INVALID` — the same two lot conditions, and only those two, that block a booking in §3.9; an `EXHAUSTED` lot is *not* blocked here and falls through instead to the inventory rung below. The `device_serial` must be exactly two uppercase letters followed by six digits and must not already exist on any other dispense row — including on a `RETURNED` one — or the dispense is refused with `ERR_DUPLICATE_DEVICE_SERIAL`. The `device_type` must be the one the study's `recommendation` admits, or the dispense is refused with `ERR_DEVICE_TYPE_NOT_RECOMMENDED`; the lot's `item_type` must equal the `device_type`, or it is refused with `ERR_LOT_ITEM_TYPE_MISMATCH`. An `ORAL_APPLIANCE` dispense additionally requires the patient's plan to have `appliance_covered` true, or it is refused with `ERR_APPLIANCE_NOT_COVERED`. Finally the lot's `available_quantity` must be at least 1, or the dispense is refused with `ERR_SUPPLY_EXHAUSTED`.

On success the dispense is created with `fit_status` `FITTED`, `billing_status` `INVOICED`, `adjustment_count` 0, `days_used` 0, `restock_fee_cents` 0, `refund_cents` 0, `refund_variant` null, `settled_by_user_id` null, `dispensed_by_user_id` stamped from the acting identifier, `dispensed_at` stamped from the logical clock, and `trial_end_at` set to `dispensed_at` advanced by the plan's `device_trial_days` whole days. That trial window is **frozen at creation**: a later amendment to the plan's `device_trial_days` never moves an existing `trial_end_at`. One unit leaves the lot immediately — `quantity_on_hand` falls by one and `quantity_consumed` rises by one, conserving `quantity_received` — and the lot flips `ACTIVE → EXHAUSTED` if that draw takes its `available_quantity` to zero, with the shortfall-flag hop of §3.8 following, so a dispense that empties a lot raises `supply_shortfall_flag` on that lot's `SCHEDULED` bookings exactly as a write-off would. If an earlier dispense already existed against the same study, this one supersedes it and the study's `superseded_dispense_count` increments by one; every earlier dispense row against that study counts for this test whatever its own `fit_status` or `billing_status`, so a study whose first unit was returned and refunded still has its second dispense recorded as a supersession. Either way the study's `version` increments by one, which is what makes a second concurrent dispense holding the older version fail the stale-version check. Dispenses may be listed and filtered by `diagnostic_study_id`, by `supply_lot_id`, by `fit_status` and by `billing_status`.

**Two independent dimensions.** A dispense carries two state dimensions that advance on different triggers and are owned by different roles. `fit_status` is the fitting dimension and runs `FITTED`, `ADJUSTED`, `FINALIZED` or `RETURNED`, with `FINALIZED` and `RETURNED` terminal. `billing_status` is the financial dimension and runs `INVOICED`, `REFUND_PENDING`, `REFUNDED` or `RETAINED`. Most transitions move exactly one of the two, and understanding which is which is the whole point of the design: the refund settlement moves only the financial dimension, leaving `fit_status` at `RETURNED`, while an adjustment moves only the fitting dimension and leaves `billing_status` untouched at `INVOICED`.

**Adjustments.** An `Audiologist` records a fitting adjustment, optionally supplying an `adjustment_note` of free text between 1 and 200 characters. The note is length-checked and then discarded: a dispense carries no `adjustment_note` field, so the text is never stored and never appears in any dispense representation, and an explicitly null `adjustment_note` is a shape failure rather than an accepted absence. The dispense's `fit_status` must be `FITTED` or `ADJUSTED`, or the adjustment is refused with `ERR_DISPENSE_STATE_INVALID`; a dispense already `FINALIZED` or `RETURNED` is closed to further fitting work, and so is one whose trial window has already elapsed, which is reported with the same `ERR_DISPENSE_STATE_INVALID`. That second test is measured after the `fit_status` test and closes at the boundary: an adjustment is permitted only while the logical clock is **strictly before** `trial_end_at`, so one attempted at exactly `trial_end_at` is already too late — the same instant at which a return becomes `POST_TRIAL` and a finalization becomes permissible. The `adjustment_count` must be strictly below three, or the adjustment is refused with `ERR_ADJUSTMENT_LIMIT_REACHED`. On success the dispense moves to `ADJUSTED` — `FITTED → ADJUSTED` on the first adjustment, and `ADJUSTED → ADJUSTED` on the second and third, so `ADJUSTED` carries a self-loop — and `adjustment_count` increments by one. Three adjustments are permitted; the fourth is refused.

**Returning a device.** An `Audiologist` accepts a unit back, supplying a mandatory `return_reason` of `DISSATISFIED`, `POOR_FIT` or `MEDICAL_CHANGE`; the value is validated against those three members and then discarded — exactly as a dose's `void_reason` is in §3.5, and unlike a booking's `cancel_reason` or a vial's `discard_reason`, a dispense carries no `return_reason` field at all, so the reason is not stored and never appears in any dispense representation. The `fit_status` must be `FITTED` or `ADJUSTED` and the `billing_status` must be `INVOICED`, or the return is refused with `ERR_DISPENSE_STATE_INVALID`; unlike an adjustment, a return is accepted at any point on either side of `trial_end_at`, the instant merely selecting which refund variant applies. On success the dispense moves to `RETURNED` — `FITTED → RETURNED` or `ADJUSTED → RETURNED`, with identical effects from either origin, and with `adjustment_count` preserved in the refund record — and the refund computation runs. The return itself leaves the lot entirely alone: all four buckets stand exactly where the dispense left them, and the unit is written off only later, if and when a refund is settled.

The refund computation begins with `days_used`, which counts the elapsed whole 24-hour periods between `dispensed_at` and the return instant and then adds one, so the day of dispensing is day one. A return 10 days and 19.5 hours after a dispensing at 2026-08-05T14:00:00Z — that is, at 2026-08-16T09:30:00Z — yields 11, because ten complete 24-hour periods have elapsed and the day of dispensing itself counts as the eleventh. The figure is recorded on the dispense under both variants, so a `POST_TRIAL` return stores its `days_used` too even though no wear charge is assessed against it. The `refund_variant` is then `IN_TRIAL` when the return instant is **strictly** before `trial_end_at`, and `POST_TRIAL` otherwise; the boundary is half-open, so a return at exactly `trial_end_at` is `POST_TRIAL`.

Under `POST_TRIAL` the practice keeps the money: `restock_fee_cents` is 0, `refund_cents` is 0, and `billing_status` becomes `RETAINED`, which is financially terminal and needs no settlement. Under `IN_TRIAL` the practice owes money. The `restock_fee_cents` is the larger of the plan's `restock_fee_floor_cents` and the `price_cents` multiplied by the plan's `restock_fee_bps` divided by ten thousand, that quotient rounded half up to a whole number of cents. A wear charge is then assessed at 350 cents for each day of `days_used`. The `refund_cents` is `price_cents` less `restock_fee_cents` less the wear charge, floored at zero so a refund is never negative, and `billing_status` becomes `REFUND_PENDING`.

Three worked returns fix the arithmetic. A unit priced at 289000 cents under a plan whose `restock_fee_bps` is 1500 and whose `restock_fee_floor_cents` is 12500, returned `IN_TRIAL` with `days_used` 12: the proportional fee is 43350, which exceeds the floor and stands; wear is 4200; the refund is 241450. The same unit returned `POST_TRIAL` with `days_used` 30: `restock_fee_cents` 0 and `refund_cents` 0, with no wear charge at all. A unit priced at 60000 cents returned `IN_TRIAL` with `days_used` 40 under the same plan: the proportional fee computes to 9000, which is below the floor and is therefore raised to 12500; wear is 14000; the refund is 33500.

**Finalizing a kept device.** An `Audiologist` closes out a unit the patient keeps. The `fit_status` must be `FITTED` or `ADJUSTED` and the `billing_status` must be `INVOICED`, or the finalization is refused with `ERR_DISPENSE_STATE_INVALID`; and the logical clock must have reached `trial_end_at`, or it is refused with `ERR_TRIAL_NOT_COMPLETE`. Here the boundary is inclusive: a finalization at exactly `trial_end_at` succeeds, which is the exact complement of the return boundary — at that one instant a return is `POST_TRIAL` and a finalization is permitted. On success the fitting dimension moves `FITTED → FINALIZED` or `ADJUSTED → FINALIZED` and `billing_status` becomes `RETAINED`. This is the single transition on which the two dimensions advance together. No unit is returned to the lot, because the patient kept it.

**Settling a refund.** A `PracticeAdmin`, not the audiologist, settles the money. The dispense's `billing_status` must be `REFUND_PENDING`, or the settlement is refused with `ERR_DISPENSE_STATE_INVALID`, and the acting identifier must differ from `dispensed_by_user_id`, or it is refused with `ERR_SELF_SETTLEMENT_FORBIDDEN`. On success `billing_status` moves `REFUND_PENDING → REFUNDED` and `settled_by_user_id` is stamped, while the fitting dimension self-loops `RETURNED → RETURNED` and stays exactly where it was — this transition is purely financial, which is what proves the two dimensions independent. The returned unit is then written off rather than restocked: the lot's `quantity_consumed` falls by one and its `quantity_wasted` rises by one, leaving `quantity_received` equal to the sum of `quantity_on_hand`, `quantity_consumed` and `quantity_wasted` exactly as before. Because `quantity_on_hand` does not rise, a settlement never revives an `EXHAUSTED` lot. A `POST_TRIAL` return, having gone straight to `RETAINED`, has no settlement to perform and any attempt at one is refused with `ERR_DISPENSE_STATE_INVALID`.

### 3.8. The Endoscopy Suite: Reprocessing Cycles and Supply Inventory

**The scope register.** A `PracticeAdmin` registers a flexible endoscope by supplying its `serial_number` — an `SC-` prefix followed by exactly four digits, unique across every scope ever registered, duplicates refused with `ERR_DUPLICATE_SCOPE_SERIAL` — and its `model`, free text of 1 to 60 characters. A new scope is created in status `READY` with `cycle_count` 0, `consecutive_mec_failures` 0, `mec_test_due` false, and `last_reprocessed_at`, `hld_expires_at`, `reprocessing_started_by_user_id` and `last_used_by_user_id` all null. A scope that has never been reprocessed is treated as shelf-valid until its first use, which is what makes a freshly registered scope usable. Scopes may be listed and filtered by `status` and by `mec_test_due`, the latter being how the sterile-processing team finds the scopes whose next run must carry a concentration test; a boolean filter is spelled exactly `true` or `false`, and any other spelling — `TRUE`, `1`, `yes` — is a shape failure.

**The cycle.** A scope's life is a loop: `READY → IN_USE → SOILED → REPROCESSING → READY`, with a `QUARANTINED` branch hanging off the reprocessing node and a single terminal exit at `RETIRED`. Two of those arcs have no endpoint of their own and are driven by the booking lifecycle of §3.9: a scope moves `READY → IN_USE` when a booking that references it starts, recording `last_used_by_user_id` from that booking's `physician_user_id`; and it moves `IN_USE → SOILED` when that booking completes, at which point `hld_expires_at` is set back to null because the previous disinfection is void the moment the scope enters a patient.

**Shelf life, cycle counting and the concentration test.** Three derived quantities govern a scope. Its `hld_expires_at` is `last_reprocessed_at` advanced by 168 hours — seven days — or null while `last_reprocessed_at` is null. A scope is shelf-valid when `last_reprocessed_at` is null, or when `hld_expires_at` is null, or when the logical clock is **strictly before** `hld_expires_at`; the boundary is exclusive, so a scope reprocessed at 2026-08-01T00:00:00Z expires at 2026-08-08T00:00:00Z, is still usable at 2026-08-07T23:59:00Z, and is no longer usable at exactly 2026-08-08T00:00:00Z. The middle limb is not redundant: a completion in §3.9 clears `hld_expires_at` to null while leaving `last_reprocessed_at` standing, so a `SOILED` scope still counts as shelf-valid and a start against it is refused by the readiness rung with `ERR_SCOPE_NOT_READY` rather than by the shelf-life rung with `ERR_HLD_EXPIRED`. A quarantined or retired scope, by contrast, keeps whatever `hld_expires_at` its last passing run wrote, so it can genuinely fail the shelf-life rung first. Its `mec_test_due` is true exactly when `cycle_count` plus one is an exact multiple of ten, so a scope with a `cycle_count` of 9 has a concentration test due on its next completion — that completion will be cycle ten — while a `cycle_count` of 8 does not. And consecutive scope bookings must leave a reprocessing turnaround: a candidate booking may start only at or after 45 minutes past the end of the scope's immediately prior booking, inclusive at the boundary, so if a prior booking ends at 10:00 a next start at 10:30 is refused with `ERR_REPROCESSING_BUFFER_VIOLATION` while a next start at exactly 10:45 is accepted.

**Starting a run.** A `SterileProcessingTech` opens a disinfection run with no request body. The scope must be `SOILED` or `QUARANTINED`, or the request is refused with `ERR_SCOPE_STATE_INVALID`; and when the scope is `QUARANTINED`, its `consecutive_mec_failures` must be strictly below 2, which is what makes a retired scope's quarantine irreversible rather than retryable. On success the scope moves to `REPROCESSING` and `reprocessing_started_by_user_id` is stamped from the acting identifier. The `QUARANTINED → REPROCESSING` arc is the retry that closes the loop from the failure branch.

**Closing a run.** The same `SterileProcessingTech` closes the run, supplying `leak_test_passed` as a boolean and optionally `mec_test_passed` as a boolean. The scope must be `REPROCESSING`, or the completion is refused with `ERR_SCOPE_STATE_INVALID`, and the acting identifier must equal `reprocessing_started_by_user_id`, or the completion is refused with `ERR_REPROCESSING_TECH_MISMATCH`. Note the direction of this comparison: every other segregation-of-duties rule in the service demands that two identifiers **differ**, and this one alone demands that they **match**, because a disinfection run is a single continuous responsibility rather than a two-person check. Both booleans are read for the pass/fail decision and then discarded: a scope carries neither a `leak_test_passed` nor an `mec_test_passed` field, so neither value is stored anywhere and neither ever appears in a scope representation, and an explicitly null `mec_test_passed` is a shape failure rather than an accepted absence.

A run **passes** when `leak_test_passed` is true and, whenever the scope's `mec_test_due` is true, `mec_test_passed` is also true. When `mec_test_due` is false the `mec_test_passed` value is not consulted at all, so a run may pass on a false `mec_test_passed` on any cycle that demands no concentration test. On a pass the scope moves `REPROCESSING → READY`; `cycle_count` increments by one; `last_reprocessed_at` is stamped from the logical clock; `hld_expires_at` is set to that instant advanced by 168 hours; `consecutive_mec_failures` is reset to 0; `mec_test_due` is re-derived from the new `cycle_count`; and `reprocessing_started_by_user_id` is cleared to null.

A run **fails** when `leak_test_passed` is false, or when `mec_test_due` is true and `mec_test_passed` is not true — a missing `mec_test_passed` on a cycle that demands one is a failure, not a shape error. Failure is a three-hop cascade. Hop one: the scope moves `REPROCESSING → QUARANTINED`, `consecutive_mec_failures` increments by one, `reprocessing_started_by_user_id` is cleared to null, and `cycle_count` is deliberately **not** incremented, because a failed run disinfected nothing. Nor are `last_reprocessed_at`, `hld_expires_at` or `mec_test_due` rewritten: the scope keeps the shelf-life expiry its last passing run left behind, and a cycle that demanded a concentration test still demands one on the retry. Hop two, caused by hop one and only when `consecutive_mec_failures` has thereby reached 2: the scope moves `QUARANTINED → RETIRED`, which is terminal and admits no further transition of any kind. Hop three, caused by hop two: every `ProcedureBooking` referencing this scope whose status is `SCHEDULED` has `scope_reassignment_required` set to true, which blocks its start until the operator reassigns it. Each hop writes its row in the full sense of §2.11, so a failing completion that merely quarantines advances the scope's `version` by one, while one that goes on to retire it advances that same scope's `version` by two. One failure quarantines a scope and leaves it retryable; the second consecutive failure retires it and reaches out to the schedule. A single passing run in between resets the counter to 0, so two failures separated by a pass never retire anything.

**Receiving a lot.** A `PracticeAdmin` books in a supply or implant lot by supplying its `item_type` — one of `BALLOON_DEVICE`, `TYMPANOSTOMY_TUBE`, `ALLERGEN_CONCENTRATE`, `HEARING_AID` or `ORAL_APPLIANCE`, which fixes for ever which workflow may draw from it — its `lot_number` as a `LOT-` prefix followed by exactly four digits and unique across all lots, duplicates refused with `ERR_DUPLICATE_LOT_NUMBER`, its `quantity_received` between 1 and 1000 inclusive, and its expiry instant `expires_at`, which is stored exactly as spelled and is **not** required to lie in the future — a lot may be booked in already expired, and nothing objects until the first attempt to draw from it. The lot is created with `quantity_on_hand` equal to `quantity_received`, `quantity_reserved` 0, `quantity_consumed` 0, `quantity_wasted` 0 and status `ACTIVE`. A lot may be neither reserved nor consumed at or after its `expires_at`; an attempt to draw from an expired lot is refused with `ERR_LOT_STATE_INVALID`, the same error a `QUARANTINED` lot produces, because in both cases it is the lot's own condition that blocks the request. Lots may be listed and filtered by `item_type` and by `status`.

**What the buckets mean.** A lot's `available_quantity` is `quantity_on_hand` less `quantity_reserved`, and `quantity_reserved` is the sum of `planned_device_count` over the lot's bookings whose status is `SCHEDULED` or `IN_PROGRESS`. Both figures appear as fields on every lot representation, but neither is an independently maintained counter: both are re-derived from that set of bookings on every read of the lot as well as on every write of it, so the pair a read returns is always live — even when the event that moved it wrote only a booking row and never touched the lot at all — and `available_quantity` is floored at zero and never reported negative. The conserved identity `quantity_received` equals `quantity_on_hand` plus `quantity_consumed` plus `quantity_wasted` holds after **every** mutation without exception. At least one unit must be available to reserve. A lot with `quantity_received` 2, `quantity_on_hand` 2 and two units reserved therefore has an `available_quantity` of 0, is `EXHAUSTED`, and refuses a further booking with `ERR_SUPPLY_EXHAUSTED` even though two units are still physically on the shelf.

**Adjusting a lot.** A `PracticeAdmin` adjusts a lot by supplying a `reason` of `RECEIVE`, `WRITE_OFF` or `QUARANTINE`. A `quantity` between 1 and 1000 inclusive is required for `RECEIVE` and for `WRITE_OFF`, and is ignored entirely for `QUARANTINE` — supplying it there is harmless and changes nothing, while omitting it for either of the first two reasons is a shape failure returning `ERR_INVALID_REQUEST`, judged before the path `lotId` is resolved, so a `RECEIVE` without a `quantity` aimed at a lot that does not exist reports `ERR_INVALID_REQUEST` rather than `ERR_SUPPLY_LOT_NOT_FOUND`. An explicitly null `quantity` is a shape failure under every reason. Neither the `reason` nor the `quantity` is retained as a field of its own: a lot records no adjustment history, so the only trace an adjustment leaves is the movement of its buckets, its status and its `version`. The lot must be `ACTIVE` or `EXHAUSTED`; an already `QUARANTINED` lot is terminal and refuses every adjustment with `ERR_LOT_STATE_INVALID`.

`RECEIVE` raises both `quantity_received` and `quantity_on_hand` by the `quantity`, preserving the identity. If that lifts `available_quantity` above zero the lot flips `EXHAUSTED → ACTIVE`, and every `SCHEDULED` booking on the lot has its `supply_shortfall_flag` set back to false.

`WRITE_OFF` is the supply cascade's origin and runs in three hops. Hop one: `quantity_on_hand` falls by the `quantity` and `quantity_wasted` rises by the same amount, so nothing is created or destroyed and the identity holds. The written-off `quantity` may not exceed the lot's `available_quantity` — a write-off may never consume units another booking has reserved, nor drive a bucket negative — and an attempt to do so is refused with `ERR_SUPPLY_EXHAUSTED`. Hop two, caused by hop one: if `available_quantity` has reached zero the lot flips `ACTIVE → EXHAUSTED`. Hop three, caused by hop two: every booking on this lot whose status is `SCHEDULED` and whose `planned_device_count` is greater than zero has `supply_shortfall_flag` set to true. Bookings with a `planned_device_count` of zero are untouched, because they were never going to draw a unit.

`QUARANTINE` moves the lot's **whole available remainder** from `quantity_on_hand` to `quantity_wasted` in one step and takes the arc `ACTIVE → QUARANTINED`, or `EXHAUSTED → QUARANTINED` from the exhausted posture. Existing reservations are deliberately left intact, so in-flight bookings keep the units they had already claimed and can still complete; what the quarantine removes is only the uncommitted balance. No `supply_shortfall_flag` is raised by a quarantine even though it drives `available_quantity` to zero, because the lot leaves the `ACTIVE ↔ EXHAUSTED` pair for `QUARANTINED` instead of becoming `EXHAUSTED`, and the flag hop hangs off that one transition alone; any flags an earlier exhaustion had already set are likewise left standing. `QUARANTINED` is terminal for a lot: there is no path back to `ACTIVE`.

The `ACTIVE ↔ EXHAUSTED` pair is a genuine loop, and the `supply_shortfall_flag` it drives is always reversed rather than merely set, so repeated exhaustion and replenishment accumulate no drift. Only three operations can ever lower a lot's `available_quantity`: a booking reservation, a device dispense drawing a unit, and a `WRITE_OFF` or `QUARANTINE` adjustment. Only three can raise it: a booking cancellation releasing its reservation, a booking completion — which releases a reservation of `planned_device_count` while consuming only `devices_used_count`, and so lifts availability by the difference whenever fewer devices were used than planned, exactly as §3.9 describes — and a `RECEIVE` adjustment. A refund settlement moves a unit from `quantity_consumed` to `quantity_wasted` and so raises nothing, because `quantity_on_hand` does not move.

### 3.9. The Surgical Schedule: Blocks, Bookings, Start, Completion and Cancellation

**Publishing a block.** A `PracticeAdmin` publishes a surgery-center block by supplying the `center_name` as free text of 1 to 120 characters, the inclusive `block_start_at`, the exclusive `block_end_at` — which must be strictly after `block_start_at` — and optionally `max_concurrent_cases`, the number of rooms the center staffs, an integer from 1 to 6 inclusive defaulting to 2, and `overnight_capable`, a boolean defaulting to false. The block window is half-open: the interval it offers is `block_start_at` up to but not including `block_end_at`. The block is created in status `OPEN` with `booked_case_count` 0, `booked_minutes` 0, `utilization_bps` 0, and `capacity_minutes` fixed as the whole minutes between the two instants multiplied by `max_concurrent_cases`. Nothing whatever is checked between one block and another: `center_name` is free text bearing no uniqueness rule, and two blocks may overlap in time, at the same centre or at different ones, so the room ceiling is enforced inside each block and never across them. Blocks may be listed and filtered by `status` and by `overnight_capable`, the latter being how a pediatric tonsillectomy finds a venue that can hold the child overnight and, like every boolean filter in the service, spelled exactly `true` or `false`.

**Utilization and posture.** A block's own duration is the whole minutes between `block_start_at` and `block_end_at`, taken downward, but that duration is an intermediate figure only: a block stores no `duration_minutes` field and never reports one — the name belongs to bookings alone — and the duration surfaces solely inside `capacity_minutes`, which is that figure multiplied by `max_concurrent_cases`, computed once at publication and never recomputed thereafter. Its `booked_minutes` is the sum of `duration_minutes` over the block's bookings whose status is `SCHEDULED`, `IN_PROGRESS` or `COMPLETED`, and its `booked_case_count` is the number of those bookings. `CANCELLED` bookings are excluded from both, which is exactly what makes a full block reopenable. The `utilization_bps` is 0 when `capacity_minutes` is 0, and otherwise `booked_minutes` multiplied by ten thousand, divided by `capacity_minutes`, rounded half up to a whole number of basis points. A block running 08:00 to 12:00 with two rooms therefore has a duration of 240 minutes and a `capacity_minutes` of 480: 90 booked minutes read 1875 basis points, 180 read 3750, 240 read 5000, and 480 read exactly 10000. The posture follows the number: a block flips `OPEN → FULL` the moment `utilization_bps` reaches 10000 or more, and flips `FULL → OPEN` again the moment a cancellation brings it back below 10000. That pair is a genuine loop, re-evaluated after every booking creation and every booking cancellation that touches the block — and after those two events only. A completion re-evaluates nothing at all, because a `COMPLETED` booking counts toward `booked_minutes` and `booked_case_count` exactly as its `SCHEDULED` self did, so neither figure, neither `utilization_bps` nor the posture can move when a case finishes. The posture itself is what gates new bookings.

**Closing a block.** A `PracticeAdmin` closes a block with no request body. The block must be `OPEN` or `FULL` — the two arcs `OPEN → CLOSED` and `FULL → CLOSED` have identical effects — or the close is refused with `ERR_BLOCK_STATE_INVALID`. `CLOSED` is terminal: no booking may be created against a closed block, but bookings already `SCHEDULED` inside it keep their slots and may still be started and completed normally.

**Scheduling a procedure.** A `PracticeAdmin` or an `Otolaryngologist` schedules a procedure by supplying the `patient_id`, the `procedure_type` (`BALLOON_SINUPLASTY`, `DIAGNOSTIC_ENDOSCOPY`, `TYMPANOSTOMY_TUBES` or `TONSILLECTOMY`), the `venue` (`IN_OFFICE_SUITE` or `SURGERY_CENTER`), the `start_at` and `end_at` instants with `end_at` strictly after `start_at`, and the `physician_user_id` of the otolaryngologist of record — an opaque string of one to a hundred and twenty characters, stored verbatim and never trimmed, which is neither resolved against the staff directory nor role-checked, so what the booking demands is that a physician be *named*, not that the name belong to an existing user holding the `Otolaryngologist` role. Neither `start_at` nor `end_at` is ever compared with the logical clock — not at creation, not at start and not at completion — so a booking may be scheduled wholly in the past and may be started and completed at any clock position at all; the only temporal comparisons the schedule makes are between one booking and another, between a booking and its block's window, and between the clock and the authorization and disinfection expiries. Four optional references are conditionally required, and each is required in one circumstance and forbidden in the complement of it: `sinuplasty_case_id` is required when `procedure_type` is `BALLOON_SINUPLASTY` and must be null otherwise; `endoscope_asset_id` is required when `procedure_type` is `BALLOON_SINUPLASTY` or `DIAGNOSTIC_ENDOSCOPY` and must be null otherwise; `surgery_center_block_id` is required when `venue` is `SURGERY_CENTER` and must be null otherwise; and `supply_lot_id` is required when `planned_device_count` is greater than zero and must be null otherwise. `planned_device_count` is an integer from 0 to 6 inclusive defaulting to 0. Every one of those conditional presence rules is a shape rule, so a missing-when-required or present-when-forbidden reference returns `ERR_INVALID_REQUEST` at rung 3. Each of the four conditional references accepts an explicit null as exactly equivalent to omitting the key — which is what "must be null otherwise" means literally, and it also means an explicit null supplied where the reference is required still fails as a missing reference. `planned_device_count` behaves the other way: an explicit null is a shape failure rather than a request for its default, exactly as an explicit null is for a block's `max_concurrent_cases` and `overnight_capable`.

The gates then run in ladder order. Every supplied reference must resolve, each to its own 404, and they are resolved in the order the input list declares them — `patient_id` first, then `sinuplasty_case_id`, then `endoscope_asset_id`, then `surgery_center_block_id`, then `supply_lot_id` — so a request naming two rows that do not exist always reports whichever comes earlier in that order. The referenced sinuplasty case must be `AUTHORIZED` or `DOCUMENTED`, or the booking is refused with `ERR_CASE_STATE_INVALID`, and a `DOCUMENTED` case qualifies only on the self-pay path — a `DOCUMENTED` case under a plan whose `requires_prior_auth` is true has not been authorized yet and is refused with the same `ERR_CASE_STATE_INVALID`. A `QUARANTINED` or expired lot is refused with `ERR_LOT_STATE_INVALID`, and a `RETIRED` scope with `ERR_SCOPE_STATE_INVALID` — the only scope posture a booking creation objects to. A scope that is `IN_USE`, `SOILED`, `REPROCESSING` or `QUARANTINED` may be booked against freely, and its disinfection shelf life is not consulted here at all: readiness and shelf-life currency are demanded only at start, because a scope has until then to come back round its loop. Next, at the safety rung, a booking whose `overnight_observation_required` is true and which names a block whose `overnight_capable` is false is refused with `ERR_OVERNIGHT_CAPABILITY_REQUIRED`. Then the temporal rung: the requested interval may not overlap any existing `SCHEDULED` or `IN_PROGRESS` booking on the same endoscope, treating both endpoints as inclusive so two bookings that merely touch already conflict, or the booking is refused with `ERR_SCOPE_INTERVAL_CONFLICT`; the requested `start_at` must be at least 45 minutes after the `end_at` of the scope's preceding booking and the requested `end_at` must be at least 45 minutes before the `start_at` of the scope's following booking, or the booking is refused with `ERR_REPROCESSING_BUFFER_VIOLATION` — both that test and the overlap test before it consider only the scope's `SCHEDULED` and `IN_PROGRESS` bookings, so a `COMPLETED` or `CANCELLED` booking imposes neither a conflict nor a turnaround, and on each side only the single nearest live booking is measured; a booking naming a block must lie entirely inside that block's half-open window, so it may begin at exactly `block_start_at` but must end at or before `block_end_at`, or it is refused with `ERR_BLOCK_WINDOW_EXCEEDED`; and a `BALLOON_SINUPLASTY` booking whose case is `AUTHORIZED` but whose `auth_expires_at` the logical clock has reached is refused with `ERR_AUTHORIZATION_EXPIRED`. Then the referential rung: the lot's `item_type` must match the `procedure_type` — a `BALLOON_SINUPLASTY` draws `BALLOON_DEVICE` and a `TYMPANOSTOMY_TUBES` draws `TYMPANOSTOMY_TUBE` — or the booking is refused with `ERR_LOT_ITEM_TYPE_MISMATCH`; those two procedure types are the only pairings the check knows, so a `DIAGNOSTIC_ENDOSCOPY` or `TONSILLECTOMY` booking may name a lot of any `item_type` at all and is never refused here; and the referenced case's `patient_id` must equal the booking's own `patient_id`, or it is refused with `ERR_CASE_PATIENT_MISMATCH`. Then the contractual rung: a case whose `candidacy_status` is `UNDETERMINED` or `INELIGIBLE` may not be scheduled and is refused with `ERR_CANDIDACY_NOT_ELIGIBLE`; and a `TONSILLECTOMY` or `TYMPANOSTOMY_TUBES` booking for a patient whose `age_months` is below 36 may not be venued `IN_OFFICE_SUITE` and is refused with `ERR_PEDIATRIC_VENUE_REQUIRED`.

The fiscal rung is last, and inside it the four checks are evaluated in the order the catalogue declares them. The lot must have at least `planned_device_count` units available, or the booking is refused with `ERR_SUPPLY_EXHAUSTED`. A `BALLOON_SINUPLASTY` booking's `planned_device_count` may not exceed the case's `authorized_device_count`, or it is refused with `ERR_DEVICE_COUNT_EXCEEDS_AUTHORIZATION` — which is how a plan's `max_balloon_devices` ceiling, applied at approval, reaches forward into the schedule. The booking may not push the block's `booked_minutes` past its `capacity_minutes`, nor cause more than `max_concurrent_cases` bookings to be live at any instant inside its half-open interval — a count taken over the same three statuses `booked_minutes` uses, `SCHEDULED`, `IN_PROGRESS` and `COMPLETED`, so a case that has already finished still holds its room for the remainder of its interval — or it is refused with `ERR_BLOCK_CAPACITY_EXCEEDED`. And a booking against a block whose status is `FULL` or `CLOSED` is refused with `ERR_BLOCK_NOT_OPEN`.

**The expiry that writes before it refuses.** The authorization-expiry check is the one place in this service where a rejection leaves a durable trace. When a `BALLOON_SINUPLASTY` booking is created against an `AUTHORIZED` case whose `auth_expires_at` the logical clock has reached, the case is **first persisted** as `AUTH_EXPIRED` and only then is the request rejected with `ERR_AUTHORIZATION_EXPIRED`. The caller receives a 409, and a subsequent read of the case shows it in `AUTH_EXPIRED` rather than `AUTHORIZED`. Expiry is observed lazily and never swept: moving the logical clock past an `auth_expires_at` changes nothing on its own, and the case continues to read `AUTHORIZED` until some booking attempt observes it. The same laziness governs a scope's shelf life — an expired `hld_expires_at` is plainly visible on the scope row and the scope still reads `READY` until a start attempt observes it — but the scope case differs in that no state is written on the rejection.

**What a successful booking does.** The booking is created in status `SCHEDULED` with `devices_used_count` 0, `scope_reassignment_required` false, `supply_shortfall_flag` false, `cancel_reason` null, `attending_physician_user_id` null, and `duration_minutes` fixed as the whole minutes between `start_at` and `end_at`, taken downward. Two flags are derived at creation: `overnight_observation_required` is true exactly when `procedure_type` is `TONSILLECTOMY` and the patient's `age_months` is below 36, and `requires_physician_presence` is true when the patient's `supervision_tier` is already `PHYSICIAN_PRESENT` — and is also set true later, on an existing `SCHEDULED` booking, by the reaction cascade of §3.4 whenever that tier is raised. `planned_device_count` units are reserved on the lot, which flips `ACTIVE → EXHAUSTED` if that takes its `available_quantity` to zero, with the sibling-flag cascade of §3.8 following. The booking's `duration_minutes` is added to the block's `booked_minutes`, its `booked_case_count` rises by one, `utilization_bps` is recomputed, and the block flips `OPEN → FULL` if the result reaches 10000 basis points. A `BALLOON_SINUPLASTY` booking moves its case `AUTHORIZED → SCHEDULED`, or `DOCUMENTED → SCHEDULED` on the self-pay path. Bookings may be listed and filtered by `patient_id`, by `sinuplasty_case_id`, by `endoscope_asset_id`, by `surgery_center_block_id`, by `supply_lot_id`, by `status` and by `procedure_type`.

**Starting.** Only an `Otolaryngologist` starts a procedure, optionally supplying `attending_physician_user_id`. The booking must be `SCHEDULED`, or the start is refused with `ERR_BOOKING_STATE_INVALID`. The acting identifier must equal the booking's `physician_user_id`, or the start is refused with `ERR_PHYSICIAN_MISMATCH` — this is the second of the two run-continuity rules that demand a match rather than a difference, and it means a colleague cannot start another physician's case even though the role is identical. When `requires_physician_presence` is true, `attending_physician_user_id` must be present, or the start is refused with `ERR_ATTENDING_PHYSICIAN_REQUIRED`; when it is false the field may be supplied and is simply recorded. A start that omits `attending_physician_user_id` leaves the field at the null it was created with, and a start never populates it from the acting identifier — which §2.9 has in any case already required to equal the booking's own `physician_user_id`. An explicitly null `attending_physician_user_id` clears the shape gate and then counts as *not supplied* for both purposes at once: it satisfies nothing when presence is demanded, and it writes nothing when presence is optional. Then, when the booking names an endoscope: the scope's high-level-disinfection shelf life must not have lapsed — that is, `last_reprocessed_at` is null, or `hld_expires_at` is null, or the clock is strictly before `hld_expires_at`, exactly the three-limbed test §3.8 defines — or the start is refused with `ERR_HLD_EXPIRED`; and the scope must be in status `READY`, or the start is refused with `ERR_SCOPE_NOT_READY`. That second error deliberately covers only the still-serviceable postures `IN_USE`, `SOILED`, `REPROCESSING` and `QUARANTINED`, because each of those resolves with time and the operator should wait. A `RETIRED` scope is excluded from it precisely so the next rung can tell the operator something different: a booking whose `scope_reassignment_required` is true is refused with `ERR_SCOPE_REASSIGNMENT_REQUIRED`, meaning the scope is gone for good and the booking needs a different one. Finally, a `BALLOON_SINUPLASTY` booking may only start while its case's `pinned_policy_version` still equals the plan's current `version`; if the plan was amended after authorization the two have diverged and the start is refused with `ERR_POLICY_VERSION_DRIFT`. The `supply_shortfall_flag` is advisory and blocks nothing: a booking whose lot ran dry may still be started, and the shortfall becomes visible only in what the completion can consume.

On success the booking moves `SCHEDULED → IN_PROGRESS`, and the scope moves `READY → IN_USE` with `last_used_by_user_id` set to the booking's `physician_user_id` — note that it records the physician of record from the booking, not the acting identifier, though the identity check has just guaranteed the two are equal.

**Completing.** An `Otolaryngologist` completes the procedure by supplying `devices_used_count`, an integer from 0 to 6 inclusive. The booking must be `IN_PROGRESS`, and the `devices_used_count` may not exceed the booking's `planned_device_count`; either failure is refused with `ERR_BOOKING_STATE_INVALID`. On success the booking moves `IN_PROGRESS → COMPLETED`, which is terminal, and three ledgers settle. On the lot, the reservation of `planned_device_count` units is released while `quantity_consumed` rises by `devices_used_count` and `quantity_on_hand` falls by the same amount, so `quantity_received` still equals the sum of `quantity_on_hand`, `quantity_consumed` and `quantity_wasted`. A lot's `available_quantity` can never fall on a completion, because the released reservation is always at least as large as the count consumed; consequently no `ACTIVE → EXHAUSTED` transition and no `supply_shortfall_flag` can ever originate here. The reverse arc, however, both can and does fire: if releasing the reservation lifts `available_quantity` above zero the lot flips `EXHAUSTED → ACTIVE` and `supply_shortfall_flag` is cleared on the lot's remaining `SCHEDULED` bookings, so a completion is one of the events that heals a lot rather than one that strains it. The scope moves `IN_USE → SOILED` and its `hld_expires_at` is cleared to null, which is what forces a fresh reprocessing run before its next use. And a `BALLOON_SINUPLASTY` booking's case moves `SCHEDULED → COMPLETED`, terminal — a hop conditioned on the case still standing at `SCHEDULED`, so a case sitting in any other status is left exactly as it is and no error is raised on its account. The block's `booked_minutes` and `booked_case_count` are unchanged by a completion, because a `COMPLETED` booking still counts toward utilization.

**Cancelling.** A `PracticeAdmin` or an `Otolaryngologist` cancels a booking by supplying a `cancel_reason` of `PATIENT_REQUEST`, `CLINICAL_HOLD`, `SUPPLY_SHORTAGE` or `SCOPE_UNAVAILABLE`. The booking must be `SCHEDULED`, or the cancellation is refused with `ERR_BOOKING_STATE_INVALID` — an `IN_PROGRESS` procedure cannot be cancelled, only completed. On success the booking moves `SCHEDULED → CANCELLED`, terminal, `cancel_reason` is stored, and every resource the booking held is released in one atomic step. The lot's reservation of `planned_device_count` units is released, so `available_quantity` rises while all four buckets stay exactly where they were and the conserved identity is untouched; if that lifts `available_quantity` above zero the lot flips `EXHAUSTED → ACTIVE` and the `supply_shortfall_flag` is cleared on the lot's `SCHEDULED` bookings. The scope's claimed interval is released together with its 45-minute turnaround buffer, so a replacement booking may immediately occupy the freed slot; the scope's own status is untouched, because a cancelled booking never started and never put it `IN_USE`. The block's `booked_case_count` falls by one, its `booked_minutes` falls by the booking's `duration_minutes`, `utilization_bps` is recomputed, and the block flips `FULL → OPEN` if the result falls below 10000 basis points. And the compensation reaches the case, though only while that case still stands at `SCHEDULED` — a case in any other status is left untouched and no error is raised. The status restored is the one the case held at the instant it was scheduled, which the scheduling step recorded for this purpose in a private field that no case representation exposes and no request may supply: a `BALLOON_SINUPLASTY` booking's case therefore returns `SCHEDULED → AUTHORIZED`, or `SCHEDULED → DOCUMENTED` on the self-pay path. Should that record be missing or hold anything other than `AUTHORIZED` or `DOCUMENTED`, the origin is derived from the plan instead — `DOCUMENTED` when the plan's `requires_prior_auth` is false, `AUTHORIZED` when it is true — which lands on the same answer for every case that reached `SCHEDULED` by the ordinary route. The case keeps its `authorized_device_count`, `auth_expires_at`, `pinned_policy_version` and `revision_round` exactly as they were, so a case can be rescheduled without any fresh trip to the payer — provided its authorization has not expired in the meantime.

**Driving the clock.** A `PracticeAdmin` sets the server's logical clock by supplying `current_utc`, and the response body carries that single field `current_utc` rather than a domain resource. Every window, expiry, elapsed-time and shelf-life rule in this specification reads that clock and nothing else. Before any call to this endpoint the clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time. Moving the clock runs no sweep of any kind: nothing is expired, retired, exhausted or escalated as a side effect of time passing. Every derived consequence of the clock is observed at the moment some request consults it, which is what makes the whole surface reproducible.
