# Player Transactions & Roster Compliance API — Product Requirements Document

## 1. Introduction

A professional league's transactions office sits between thirty-odd clubs that all want to move players and a rulebook that says when, how and at what price they may. Every club front office runs the same daily gauntlet: keep the active, reserve, injured-reserve and practice-squad headcounts inside their published limits, get paperwork filed before a deadline that the league itself computes, get a player through a physical before a signing can be approved, and keep the whole payroll under a hard salary cap whose arithmetic changes depending on whether you are asking "what have we promised?" or "what have we actually incurred?". Today this work is done on spreadsheets and phone calls, which means a club discovers it is over the cap a week after the transaction that put it there, and the league discovers a missing injury filing only when a grievance is filed.

This document specifies the service that replaces that process. It is a compliance-and-audit system first: every club carries a **compliance posture** that is recomputed from its own child records, and that posture gates whether the club may transact at all. Layered on top is a quota-allocation system — roster designations and salary-cap dollars are the two scarce quantities, and almost every business rule in this document is ultimately about admitting or refusing a write because one of those two quotas would be breached. Around that core sit the league's transactional instruments: filings that must be approved by someone other than their author, waiver wires with revocability and claiming order, trades with cap compatibility and medical contingencies, tenders with response deadlines, and injury designations with minimum stays and return-to-play windows.

Two design commitments run through everything that follows. First, **time is explicit and server-owned**: the service reads a logical UTC clock that tests drive directly, and every deadline, window, expiry and service-day accrual is derived from that clock rather than from wall time. Second, **derived state is never accepted as input**: roster counts, cap totals, service-time totals, dead money, proration schedules, compliance postures and eligibility flags are all computed by the server from the records it holds, so a client cannot assert its way into compliance.

## 2. Global Specifications & System-Wide Principles

### 2.1. Front-Office Identity and Role-Based Access Control

Every request to every endpoint — reads included — must carry two headers: `X-User-ID`, identifying who is acting, and `X-User-Role`, naming the capacity in which they act. If either header is absent or blank — and a value consisting only of whitespace counts as blank — the request fails with `ERR_UNAUTHENTICATED` (HTTP 401). Both header values are trimmed of surrounding whitespace before they are compared or used as a lookup key. The same 401 with the same error identifier is returned when `X-User-Role` carries a value outside the four roles this system recognises, which are, spelled exactly: `LeagueOfficer`, `TeamCapAnalyst`, `TeamMedicalOfficer`, and `PlayerAgent`.

Authentication and authorisation are separate steps. Once the headers are present and the role is one of the four, the service asks whether that role appears in the acting endpoint's authorised-role list (see §4). If it does not, the answer is `ERR_UNAUTHORIZED` (HTTP 403).

The four roles divide the league's work along a strict segregation-of-duties line:

- **`LeagueOfficer`** is the league transactions office. It registers clubs and players, decides filings, processes waiver wires, executes trades, marks bonus allocations earned, adjusts club limits, drives the logical clock and runs the compliance sweep. It never prepares a club's paperwork. When `X-User-Role` is `LeagueOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — it is stored as `decided_by_user_id` on a filing the officer decides — but it never compares that value to any entity's `id`.
- **`TeamCapAnalyst`** is a club's cap and transactions analyst. It prepares, files and revises its own club's filings, places and withdraws waiver placements, claims players off the wire, constructs trades, decides team options and issues tenders — but it approves nothing and never touches the medical dimension. When `X-User-Role` is `TeamCapAnalyst`, `X-User-ID` is the `id` of the acting `Team`; ownership checks on any resource that references a `Team` compare the resource's club-reference field to `X-User-ID`. A filing's `filed_by_user_id` is therefore the same value as its `team_id`.
- **`TeamMedicalOfficer`** is a club's medical officer. When `X-User-Role` is `TeamMedicalOfficer`, `X-User-ID` is likewise the `id` of the acting `Team`, and ownership is checked the same way — but the role is confined to the medical dimension: injury designations, league injury paperwork, and physical examinations. It cannot file, claim, trade or tender.
- **`PlayerAgent`** is a certified agent acting for exactly one player. When `X-User-Role` is `PlayerAgent`, `X-User-ID` is the `id` of the acting `Player`; ownership checks on any resource that references a `Player` compare the resource's player-reference field to `X-User-ID`. An agent responds to tenders and decides player options, and reads the club and contract records that concern its player.

For all three of the entity-backed roles — `TeamCapAnalyst`, `TeamMedicalOfficer` and `PlayerAgent` — the identifier in `X-User-ID` must be the `id` of an existing instance of the backing entity (a `Team` for the two club roles, a `Player` for the agent). A syntactically fine but unknown identifier is an authorisation failure, `ERR_UNAUTHORIZED` (HTTP 403), not a not-found.

Beyond "may this role act at all", the service enforces **actor scope**: the acting club must be the club that owns the resource, and the acting player must be the player the resource concerns. Concretely, the acting club's identifier is compared against the filing's `team_id`, the waiver placement's `from_team_id`, the claim's `claiming_team_id`, the contract's `team_id`, the injury designation's `team_id` and the physical exam's `team_id`; for trade actions the acting club must be whichever of the two clubs the negotiation currently expects to respond. The acting player's identifier is compared against the contract's `player_id` or the tender's `player_id`. A mismatch is `ERR_ACTOR_SCOPE_VIOLATION` (HTTP 403).

Finally, the segregation of duties is enforced at the decision point itself: the `X-User-ID` that decides a filing must differ from the `filed_by_user_id` recorded when that filing was submitted. If the two coincide, the decision is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters `A` through `Z` and the digits `0` through `9`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. Like every other instant this service emits, it is read from the logical clock of §2.5 rather than from wall time, so two requests made at the same logical instant carry the identical timestamp.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- This same envelope is also what the service returns for a request that never reaches an endpoint at all: an unknown path answers `ERR_INVALID_REQUEST` with HTTP 404, a known path addressed with an unsupported method answers `ERR_INVALID_REQUEST` with HTTP 405, and an unexpected server fault answers `ERR_INVALID_REQUEST` with HTTP 500. Those are the only cases in which `ERR_INVALID_REQUEST` is paired with a status other than the 400 that §5 records for it; a body that is not parseable JSON is an ordinary 400.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0. A value outside those bounds — a `limit` of 0, a `limit` of 101, a negative `offset` — is a request-shape failure and yields `ERR_INVALID_REQUEST` (HTTP 400), and so is a value that is not an integer at all, such as `limit=abc` or `limit=2.5`. A parameter that is absent, or present but empty as in `?limit=`, takes its default rather than failing. `offset` carries no upper bound: an `offset` beyond `total_count` is accepted and simply returns an empty page. Those bounds are checked at request-shape precedence on the flat collection endpoints and on a club's sweep history; on a list nested beneath a path identifier — a contract's bonus allocations, a contract's trade assets, a trade's assets — the identifier resolves first, so an unknown parent answers its own 404 even when `limit` or `offset` is out of bounds as well.

Unless a specific endpoint's description in §4 says otherwise, list results are ordered by `created_at` ascending. The one deliberate exception is a club's sweep history, which is returned newest first by `checked_at`. Because the logical clock lets many records share a single `created_at`, ties are broken by the order in which the server created the records, earliest first; the sweep history reverses that ordering whole, so of two rows sharing a `checked_at` the later-created one comes first.

List responses carry all four pagination fields in `meta`: `limit` and `offset` echo the values actually applied, `total_count` is the number of records matching the filter before the page window is applied, and `has_more` is true exactly when records remain beyond the current page. Single-resource responses omit all four.

Collection endpoints additionally accept the domain filters named in their §4 descriptions; a filter narrows `total_count` as well as the page. Clubs may be filtered by `compliance_status`. Players may be filtered by `current_team_id` (which is how a club retrieves its own roster view), `roster_designation`, `medical_status` and `contract_rights_class`. Contracts may be filtered by `team_id`, `player_id`, `signed_via_transaction_id` and `status`. Filings may be filtered by `team_id`, `player_id`, `contract_id`, `injury_designation_id`, `transaction_type` and `status`. Waiver placements may be filtered by `player_id`, `from_team_id`, `awarded_to_team_id`, `transaction_id`, `contract_id` and `status`; claims by `waiver_request_id`, `claiming_team_id` and `status`. Trades may be filtered by `initiating_team_id`, `counterparty_team_id` and `status`. Tenders may be filtered by `player_id`, `team_id`, `resulting_transaction_id` and `status`. Injury designations may be filtered by `player_id`, `team_id`, `designation_type` and `status`. Physicals may be filtered by `player_id`, `team_id`, `transaction_id`, `trade_id`, `exam_type` and `status`. Every filter is matched as an exact, case-sensitive string against the value of the field it names — including `contract_rights_class`, which is matched against the derived class rather than a stored column — so a well-formed but unmatched or unrecognised filter value narrows the result to nothing and returns an empty page with a `total_count` of 0 rather than an error. A filter supplied empty is ignored, as is any query parameter other than `limit`, `offset` and the filters named here.

### 2.4. Resource Identity, Timestamps and the Version Counter

Every resource this service creates is identified by a server-minted UUID exposed as `id`. Identifiers carry no type prefix — a filing's identifier and a trade's identifier are indistinguishable by shape — and clients never supply them on creation.

Most resources also carry three bookkeeping fields. `created_at` is the ISO 8601 UTC instant of creation, rendered with exactly three fractional-second digits. `updated_at` is the same format and marks the last mutation; at creation it equals `created_at`. That rendering is universal: **every** instant-valued field this service returns — not only `created_at` and `updated_at`, but every deadline, window bound, validity expiry, effective/decision/placement/processing stamp, the sweep's `checked_at`, and the envelope's `api_request_timestamp` — is emitted in the identical shape `YYYY-MM-DDTHH:MM:SS.mmmZ`, with exactly three fractional-second digits and a trailing `Z`; instants the client supplied are normalised to UTC before being rendered that way — a supplied instant may carry a trailing `Z` or an explicit numeric UTC offset, one that carries no zone designator at all is read as already being UTC, and precision finer than a millisecond is truncated toward the past rather than rounded. A value whose sub-second part happens to be zero is still rendered with those three digits, as `2026-08-13T13:00:00.000Z`, and wherever this document writes an instant without fractional digits it is naming the instant itself rather than its rendering. An instant-valued field that is not set is rendered as JSON `null`, and that is the general shape of every representation in this document: each field named for a resource is present in every representation of that resource, never omitted, and a field holding no value is rendered as JSON `null` rather than dropped. `version` is an integer that starts at 1 and increases by exactly 1 on every mutation of that resource. Any write that changes a resource refreshes its `updated_at` and advances its `version` together — the two never move independently.

`ComplianceCheck` is the single exception. A sweep record is an immutable audit event, so it carries only `id` and `created_at`: it has no `updated_at` and no `version` field at all, and neither should appear in its representation.

Two consequences of the version counter deserve stating up front, because they are easy to get wrong. First, a club's `version` advances on writes that the client did not aim at the club directly: opening a filing, submitting a claim, adjusting limits, deciding a filing, revising one, placing a waiver, responding to a tender with an acceptance, and running a compliance sweep all bump the owning `Team`'s `version`, and no other write does — a waiver withdrawal, a processed wire, an accepted or executed trade, an issued tender, an exercised or declined option and an earned bonus allocation each recompute and re-evaluate the club in place while leaving its `version` exactly where it was. Second, a purely computed read never bumps anything — the cap-ledger read recomputes both cap variants from live contract and allocation rows and returns them, but leaves `Team.version` exactly where it was.

### 2.5. The Logical League Clock and the Daily Processing Window

Nothing in this system reads the host machine's wall clock. Instead the service maintains a **logical UTC clock**, and every deadline, processing window, validity expiry, minimum stay and service-day accrual is derived from it. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; that is the fixed startup default and the service never falls back to real time. Note that this default instant sits deliberately outside the daily processing window described below, so a test that expects a window-gated operation to succeed must move the clock first.

A league officer moves the clock by supplying a `current_utc` instant; the clock jumps to that instant, no entity is mutated, and no sweep is performed as a side effect. The clock may be moved backwards as freely as forwards, and the reply is the ordinary 200 envelope of §2.2 carrying an empty `data` object rather than the new clock value.

The league transactions office is open on a **daily processing window** running from 13:00:00 UTC up to but not including 21:00:00 UTC. The interval is half-open: an operation attempted at exactly 13:00:00 UTC is inside the window, and an operation attempted at exactly 21:00:00 UTC is outside it. Four operations are gated on this window — submitting a filing to the league, deciding a filing, processing a waiver wire, and executing a trade — and each is refused with `ERR_OUTSIDE_PROCESSING_WINDOW` (HTTP 422) when the logical clock's time of day falls outside it.

The same window also **snaps** computed deadlines onto office hours. Whenever this document says a deadline is "snapped into the processing window", the rule is: take the raw instant; if its UTC time of day is earlier than 13:00:00, the deadline becomes 13:00:00 UTC on that same calendar date; if its time of day is 13:00:00 or later but earlier than 21:00:00, the raw instant is kept unchanged; otherwise — that is, at 21:00:00 or later — the deadline becomes 13:00:00 UTC on the following calendar date. Snapped deadlines are produced at whole-second resolution and never carry a sub-second component: the raw instant's sub-second part is discarded on every branch, including the middle branch that otherwise keeps the raw instant unchanged. That is a property of the *stored* value; the rendering rule of §2.4 still applies unchanged to it, so a snapped 13:00 deadline is returned as `2026-08-13T13:00:00.000Z`. This single rule is reused by the filing deadline, the waiver clearance deadline and the tender response deadline.

### 2.6. Stale-Version Guards on Club, Trade and Contract Writes

Three families of write are protected by optimistic concurrency control. Each protected endpoint takes a non-optional version field naming the client's last observed `version` of the *parent* record, and a mismatch against that parent's current `version` is rejected outright. Endpoints not named below take no version field at all.

**Opening a filing.** A `POST /transactions` request must carry `expected_team_version` matching the target club's current `Team.version`. A club may legitimately hold several `DRAFT` filings for the same player and the same designation at once — the second create observes no state field that the first create changed, so no state-machine or business rule would refuse it. The stale team version is the only signal distinguishing a writer who has not yet seen the roster counts and cap totals the earlier filing moved. If `expected_team_version` does not equal the club's current `version`, the request is rejected with `ERR_STALE_TEAM_VERSION` (HTTP 412).

**Submitting a waiver claim.** A `POST /waiver-requests/{id}/claims` request must likewise carry `expected_team_version` matching the claiming club's current `Team.version`. The claim captures a snapshot of that club's waiver priority rank and cap space, and a club may legitimately hold claims on several wires simultaneously, so a repeated submit sees identical waiver-request state and would otherwise succeed. Rejecting on a stale team version is what prevents a claim from being ranked and cap-tested against a club snapshot that has since been superseded. The rejection is `ERR_STALE_TEAM_VERSION` (HTTP 412).

**Adding a trade asset.** A `POST /trades/{id}/assets` request must carry `expected_trade_version` matching the trade's current `Trade.version`. A trade accepts any number of assets on either side, so a second add observes the same trade status and would legitimately succeed; the stale version is the only signal that the writer has not seen the cap deltas recomputed by the previously added asset, or the counter that has since advanced the negotiation. Which club may add a given asset turns on that asset's `direction` alone and never on whose turn it is to respond, so both parties may keep adding while the trade is `PROPOSED` or `COUNTERED`. The rejection is `ERR_STALE_TRADE_VERSION` (HTTP 412). The same `expected_trade_version` field, checked the same way against the same error identifier and status, is also required when countering a trade.

**Deciding a contract option.** A `POST /contracts/{id}/option-decision` request must carry `expected_contract_version` matching the contract's current `Contract.version`; a mismatch is `ERR_STALE_CONTRACT_VERSION` (HTTP 412).

### 2.7. Money, Days and Rounding Conventions

All money in this system is expressed in **integer cents** — there are no fractional amounts anywhere in a request or a response, and every field whose name ends in `_cents` is an integer. Because the inputs are integers, most cap arithmetic requires no rounding at all: sums of contract charges and bonus allocations are exact.

Where a division or a multiplier does appear, the rounding rule is stated once here and referenced by the workflows that use it. Signing-bonus proration divides the bonus across seasons and takes the **floor** of the per-season quotient, pushing the entire remainder into the last prorated season, so the per-season charges always sum back to the bonus exactly. Tender amounts apply a decimal multiplier and are then rounded **half up** to whole cents before any ceiling is applied. Day counts derived from two instants — service-time accrual, injured-reserve service credit — are computed as the elapsed seconds divided by 86,400 and then **floored** to whole days, discarding any partial day; such a count is never negative, so an interval whose end is not strictly later than its start — the two instants coincide, or the logical clock has since been moved back behind the baseline — contributes 0 days rather than a negative figure. The injured-reserve half-weight credit used by one service-time variant is also floored. Service years are the floor of a day count divided by a fixed per-season day budget.

Cap space is reported, not clamped: a club whose commitments exceed its cap limit reports a negative `cap_space_cents` rather than zero.

### 2.8. Validation Precedence: The Order in Which a Request Is Refused

Many requests in this system violate more than one rule at once, and the benchmark cares which error the client sees. Validation is therefore strictly ordered, and **the first rule violated decides the response**; no later rule can mask an earlier one. The ordering follows the way a league office actually reads a submission: who are you, is the paperwork well-formed, do the things you reference exist, are you looking at current data, is the record in the right state, is this safe and medically documented, do the cross-references line up, are we inside the deadlines, do the constraints hold, and only last, does the money work.

The full ladder, in ascending precedence:

1. Both `X-User-Role` and `X-User-ID` are present and non-blank — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. `X-User-Role` is one of `LeagueOfficer`, `TeamCapAnalyst`, `TeamMedicalOfficer`, `PlayerAgent` — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
3. The role is listed among the endpoint's authorised roles — otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
4. For an entity-backed role, `X-User-ID` is the `id` of an existing instance of its backing entity — a `Team` for `TeamCapAnalyst` and `TeamMedicalOfficer`, a `Player` for `PlayerAgent` — otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint whose authorised roles include any of those three.
5. Actor scope: the acting club owns the resource (compared against `Transaction.team_id`, `WaiverRequest.from_team_id`, `WaiverClaim.claiming_team_id`, `Contract.team_id`, `InjuryDesignation.team_id` or `PhysicalExam.team_id`) or, for trade actions, is the club whose turn the negotiation assigns; the acting player is the contract's `player_id` or the tender's `player_id` — otherwise `ERR_ACTOR_SCOPE_VIOLATION` (403). Applies to every team-scoped and player-scoped write.
6. Segregation of duties: the deciding `X-User-ID` differs from the filing's `filed_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to `POST /transactions/{id}/decide`.
7. Request shape: the body parses, every required field is present, enums carry known values, integers fall in their declared ranges, datetimes are well-formed, money amounts are non-negative, `window_end_at` is strictly later than `window_start_at`, and the conditional companion fields demanded by a polymorphic `asset_kind` are supplied — otherwise `ERR_INVALID_REQUEST` (400). Applies to every endpoint. A request carrying no body at all is read as an empty JSON object, so it fails on the first required field it lacks, while a body that parses to anything other than a JSON object fails outright. An optional field supplied as an explicit `null` counts as absent and takes its documented default. String inputs are trimmed of surrounding whitespace before their blank and length checks, and the trimmed value is what is stored. An integer-valued field must be a JSON integer — `true` and `3.0` are both refused — and an enum must match one of its declared values exactly, case included.
8. Every identifier in the URL path exists, validated left to right — otherwise the matching 404 from the not-found catalogue (`ERR_TEAM_NOT_FOUND`, `ERR_PLAYER_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_BONUS_ALLOCATION_NOT_FOUND`, `ERR_TRANSACTION_NOT_FOUND`, `ERR_WAIVER_REQUEST_NOT_FOUND`, `ERR_WAIVER_CLAIM_NOT_FOUND`, `ERR_TRADE_NOT_FOUND`, `ERR_TENDER_NOT_FOUND`, `ERR_INJURY_DESIGNATION_NOT_FOUND`, `ERR_PHYSICAL_EXAM_NOT_FOUND`). Applies to every endpoint with a path parameter.
9. Every foreign key in the request body exists, validated in the order the fields are declared for that endpoint — otherwise the same 404 catalogue. Applies to `POST /transactions`, `POST /transactions/{id}/revise` (for the `injury_designation_id` it may carry), `POST /waiver-requests`, `POST /waiver-requests/{id}/claims`, `POST /trades`, `POST /trades/{id}/assets`, `POST /qualifying-offers`, `POST /injury-designations`, `POST /physical-exams` and `POST /compliance-checks/run`.
10. `expected_team_version` equals the club's current `version` — otherwise `ERR_STALE_TEAM_VERSION` (412). Applies to `POST /transactions` and `POST /waiver-requests/{id}/claims`.
11. `expected_trade_version` equals the trade's current `version` — otherwise `ERR_STALE_TRADE_VERSION` (412). Applies to `POST /trades/{id}/assets` and `POST /trades/{id}/counter`.
12. `expected_contract_version` equals the contract's current `version` — otherwise `ERR_STALE_CONTRACT_VERSION` (412). Applies to `POST /contracts/{id}/option-decision`.
13. The target record is in a state that has an outgoing transition for this trigger, including the parallel dimension the trigger writes — otherwise the matching 409 state error (`ERR_INVALID_TRANSACTION_STATE`, `ERR_INVALID_CONTRACT_STATE`, `ERR_INVALID_OPTION_STATE`, `ERR_INVALID_WAIVER_STATE`, `ERR_INVALID_TRADE_STATE`, `ERR_INVALID_TENDER_STATE`, `ERR_INVALID_DESIGNATION_STATE`, `ERR_INVALID_EXAM_STATE`). Applies to every action endpoint. One deliberate carve-out: a revision aimed at a filing that is already `VOIDED` and whose `revision_count` has reached the revision limit is **not** reported here — that case is deferred to the next rule, which owns the more specific diagnosis.
14. A revision aimed at a filing already voided by the revision limit — that is, a filing whose `status` is `VOIDED` and whose `revision_count` equals the maximum of 2 — is rejected with `ERR_REVISION_LIMIT_EXCEEDED` (409). Applies to `POST /transactions/{id}/revise`. A revision on a `REJECTED` filing below the limit passes this rule; a revision on a `REJECTED` filing exactly at the limit does not error here either — it voids the filing, as described in §3.3.
15. The acting or affected club's `compliance_status` is neither `NON_COMPLIANT` nor `TRANSACTION_FROZEN` — otherwise `ERR_TEAM_TRANSACTIONS_FROZEN` (409). Applies to nine operations: `POST /transactions`, `POST /transactions/{id}/file`, `POST /transactions/{id}/decide`, `POST /waiver-requests`, `POST /waiver-requests/{id}/claims`, `POST /trades`, `POST /trades/{id}/accept`, `POST /trades/{id}/execute` and `POST /qualifying-offers`.
16. The subject player's `medical_status` is not `FAILED_PHYSICAL` — otherwise `ERR_PLAYER_FAILED_PHYSICAL` (422). Applies to `POST /transactions/{id}/decide` with an approving decision, `POST /trades/{id}/execute` and `POST /qualifying-offers`.
17. When the filing's `requires_physical` is true, a physical exam for that filing's player — one whose own `transaction_id` either names that filing or is null — exists whose `status` is `PASSED` and whose `expires_at` is strictly later than the logical clock — otherwise `ERR_PHYSICAL_NOT_PASSED` (422). Applies to `POST /transactions/{id}/decide` with an approving decision. The same identifier also guards `POST /trades/{id}/execute`, but in a different shape and at a lower rung: for a trade in `MEDICAL_REVIEW`, every exam booked against that trade must be `PASSED` with an `expires_at` strictly later than the clock, and that test is read immediately after rule 28 rather than here.
18. An `IR_PLACEMENT` filing's cited injury designation is in `PAPERWORK_FILED`, and an `IR_ACTIVATION` filing's cited designation is in `RETURN_WINDOW_OPEN` — otherwise `ERR_INJURY_PAPERWORK_MISSING` (422). Applies to `POST /transactions/{id}/decide` with an approving decision.
19. A filing's `injury_designation_id` references a designation whose `player_id` and `team_id` both match the filing — otherwise `ERR_DESIGNATION_PLAYER_MISMATCH` (422). Applies to `POST /transactions` and `POST /transactions/{id}/revise`.
20. A waiver placement's `transaction_id` references an `APPROVED` filing of type `RELEASE` for the same player and the same club — otherwise `ERR_RELEASE_FILING_MISMATCH` (422). Applies to `POST /waiver-requests`.
21. A `CONTRACT` trade asset references a contract whose `status` is `ACTIVE` and whose `team_id` is the club sending the asset — otherwise `ERR_ASSET_NOT_OWNED` (422). Applies to both `POST /trades/{id}/assets` and `POST /trades/{id}/execute`.
22. The logical clock's time of day is inside the half-open processing window — otherwise `ERR_OUTSIDE_PROCESSING_WINDOW` (422). Applies to `POST /transactions/{id}/file`, `POST /transactions/{id}/decide`, `POST /waiver-requests/{id}/process` and `POST /trades/{id}/execute`.
23. The logical clock is no later than the filing's `filing_deadline_at` — otherwise `ERR_FILING_DEADLINE_PASSED` (422). Applies to `POST /transactions/{id}/file` and `POST /transactions/{id}/revise`.
24. The logical clock has reached the wire's `clearance_deadline_at` — otherwise `ERR_CLEARANCE_NOT_REACHED` (422). Applies to `POST /waiver-requests/{id}/process`.
25. The logical clock is no later than the tender's `deadline_at` — otherwise `ERR_TENDER_DEADLINE_PASSED` (422). Applies to `POST /qualifying-offers/{id}/respond`.
26. The logical clock is no later than the contract's `option_deadline_at` — otherwise `ERR_OPTION_DEADLINE_PASSED` (422). Applies to `POST /contracts/{id}/option-decision`.
27. The logical clock lies inside the closed interval from the cited designation's `return_window_opens_at` through its `return_window_closes_at` — otherwise `ERR_RETURN_WINDOW_CLOSED` (422). Applies to `POST /transactions/{id}/decide` on an `IR_ACTIVATION` filing.
28. For a trade in `MEDICAL_REVIEW`, the logical clock is no later than `medical_review_deadline_at` — otherwise `ERR_MEDICAL_WINDOW_EXPIRED` (422). Applies to `POST /trades/{id}/execute`.
29. `performed_at` falls inside the half-open exam window that begins at `window_start_at` and ends before `window_end_at` — otherwise `ERR_RESULT_OUTSIDE_EXAM_WINDOW` (422). Applies to `POST /physical-exams/{id}/record-result`.
30. The requested exam window does not collide with another scheduled window for the same player under half-open semantics — otherwise `ERR_EXAM_WINDOW_OVERLAP` (409). Applies to `POST /physical-exams`.
31. Neither club's medical-review capacity is already occupied by an interval that overlaps the new one under closed semantics — otherwise `ERR_MEDICAL_REVIEW_SLOT_TAKEN` (409). Applies to `POST /trades/{id}/accept`.
32. Uniqueness of open records: the player has no `PENDING` waiver placement (`ERR_WAIVER_ALREADY_PENDING`), the player has no open injury designation (`ERR_INJURY_DESIGNATION_ALREADY_OPEN`), the player-and-club pair has no `ISSUED` tender (`ERR_TENDER_ALREADY_ISSUED`), the claiming club has no `SUBMITTED` claim already on this wire (`ERR_CLAIM_ALREADY_SUBMITTED`), and a club's `market_code` (`ERR_DUPLICATE_MARKET_CODE`) and `waiver_priority_rank` (`ERR_DUPLICATE_WAIVER_PRIORITY`) are unique across all clubs. All six carry HTTP 409. Applies to `POST /waiver-requests`, `POST /injury-designations`, `POST /qualifying-offers`, `POST /waiver-requests/{id}/claims`, `POST /teams` and — for `waiver_priority_rank` alone — `PATCH /teams/{id}/limits`.
33. The two clubs named on a trade are distinct — otherwise `ERR_TRADE_SAME_TEAM` (422). Applies to `POST /trades`.
34. A player being placed onto or elevated off the practice squad has `practice_squad_eligible` true — otherwise `ERR_PRACTICE_SQUAD_INELIGIBLE` (422). The two halves of that requirement are tested at different moments: a filing whose destination designation is `PRACTICE_SQUAD` is tested at this rung when the approving decision is made, whereas an elevation *off* the squad is tested once, at `POST /transactions`, when the `PRACTICE_SQUAD_ELEVATION` filing is opened, and is never revisited afterwards. Applies to `POST /transactions` for a `PRACTICE_SQUAD_ELEVATION` and `POST /transactions/{id}/decide` with an approving decision for a filing bound for the practice squad.
35. A tender targets a player whose `contract_rights_class` is `RESTRICTED` or `ARBITRATION_ELIGIBLE`, and an `ARBITRATION_TENDER` targets only a player who is `ARBITRATION_ELIGIBLE` — otherwise `ERR_RESTRICTED_RIGHTS_REQUIRED` (422). Applies to `POST /qualifying-offers`.
36. The resulting headcounts stay within the club's corresponding limits — otherwise `ERR_ROSTER_LIMIT_EXCEEDED` (409). How wide the test is depends on the operation. Submitting a filing, deciding one approvingly and awarding a claim each rehearse the move and then compare **all four** projected designation headcounts against their own limits, so a club that is already over an unrelated quota is refused here as well. Executing a trade compares only each affected club's projected `active_roster_count` against `active_roster_limit`. Withdrawing a waiver compares only the `origin_designation` being restored against its own limit. Applies to `POST /transactions/{id}/file`, `POST /transactions/{id}/decide` with an approving decision, `POST /trades/{id}/execute`, `POST /waiver-requests/{id}/process` and `POST /waiver-requests/{id}/withdraw`.
37. The club's provisional cap commitment fits under `salary_cap_limit_cents` — otherwise `ERR_CAP_LIMIT_EXCEEDED` (409). Opening a `SIGNING` filing is the one prospective test: the club's provisional commitment plus the new contract's `current_season_cap_charge_cents` must not exceed the limit. The other two read the commitment exactly as it already stands and so refuse only a club that is *already* over its limit — which for an approving decision is not a weaker test than it looks, because the pending contract has been counted in the provisional variant since the filing was opened. Applies to `POST /transactions`, `POST /transactions/{id}/decide` with an approving decision, and `POST /qualifying-offers`.
38. Trade cap compatibility holds for both clubs — otherwise `ERR_TRADE_CAP_INCOMPATIBLE` (409). Applies to `POST /trades/{id}/execute`.

Two consequences worth naming: because the frozen-club check sits at precedence 15, a club that has been frozen sees `ERR_TEAM_TRANSACTIONS_FROZEN` rather than a downstream cap or roster error even when both would apply; and because the medical checks at 16 through 18 sit above every temporal and fiscal check, an unsafe or undocumented approval is refused before the league ever looks at deadlines or arithmetic.

### 2.9. Nested Path Resolution and Cascade Discipline

Path identifiers are resolved **left to right**, and the first one that does not resolve determines the 404. A request naming a contract and then a bonus allocation beneath it fails with `ERR_CONTRACT_NOT_FOUND` when the contract is unknown, even if the allocation identifier is also nonsense; only once the contract resolves does an unknown allocation produce `ERR_BONUS_ALLOCATION_NOT_FOUND`. Where a child is addressed beneath a parent, the child must genuinely belong to that parent; a mismatch is reported as a not-found on the child.

Every write in this system is applied **immediately and completely** — there is no deferred settlement. When an operation touches more than one record, all of the consequences described in §3 land within the same request: the primary state change, the derived recomputations on the affected clubs (their four designation headcounts, both cap totals, dead money and cap space), the re-evaluation of the affected clubs' compliance posture, and the `updated_at` and `version` bumps on each mutated record. If any precondition fails, nothing is written at all — with the single exception §3.6 records for the waiver award pipeline, whose elimination stage writes before the last roster gate is read.

Compliance re-evaluation runs in two distinct modes, and the difference is observable. **Event mode** runs inline, immediately after any write that changed rosters, cap totals or designations. It persists no sweep record, never advances a club's consecutive-violation counter beyond 1, and can only move a club from `COMPLIANT` to `GRACE` (arming the grace expiry) or leave the posture where it was — it never freezes a club, and it never lapses tenders, expires injury windows, voids medical reviews or expires physicals. **Sweep mode** runs only when the league explicitly runs a compliance check; it persists a sweep record, walks the full posture ladder using the consecutive-violation counter, and additionally performs five clock-driven steps described in §3.9. Identical club data therefore yields the same violation list in both modes but can yield a different resulting posture.

## 3. Business Logic & Workflows

### 3.1. Clubs, Roster Quotas and the Cap Ledger

A club enters the system when the league office registers it. Registration carries the club's `name` — between 1 and 80 characters, and not blank — and its `market_code`, which is exactly three uppercase letters A through Z and must be unique across every club in the league; a collision is refused with `ERR_DUPLICATE_MARKET_CODE`. Registration also fixes the club's `salary_cap_limit_cents`, which may not be negative and which the league conventionally sets to its standard figure of 500,000,000 cents, and its `waiver_priority_rank`, an integer of at least 1 that must likewise be unique league-wide — rank 1 claims ahead of rank 2, and a duplicate is refused with `ERR_DUPLICATE_WAIVER_PRIORITY`. A registration that collides on both at once reports the market code: `ERR_DUPLICATE_MARKET_CODE` is evaluated ahead of `ERR_DUPLICATE_WAIVER_PRIORITY`.

The four roster quotas may be supplied at registration and otherwise take league defaults: `active_roster_limit` defaults to 26 and must be at least 1; `reserve_roster_limit` defaults to 4; `injured_reserve_limit` defaults to 3; `practice_squad_limit` defaults to 6; and the latter three must each be at least 0. A freshly registered club starts with every headcount and every money total at zero, `cap_space_cents` equal to its `salary_cap_limit_cents`, and a `compliance_status` of `COMPLIANT`.

Against each quota sits a matching server-maintained headcount: `active_roster_count`, `reserve_roster_count`, `injured_reserve_count` and `practice_squad_count`. Each is recomputed, never asserted, as the number of players whose owning club is this club and whose `roster_designation` is respectively `ACTIVE`, `RESERVE`, `INJURED_RESERVE` and `PRACTICE_SQUAD`. The four counts partition only those four rostered designations: a player who is `WAIVED_PENDING` or `UNROSTERED` counts toward none of them. That asymmetry is deliberate and observable — a club whose release has been approved but whose waiver has not yet resolved sits *below* its own active headcount even though it is still paying the player.

The club record also carries `open_medical_review_count`, the number of trades currently in medical review on which this club is either the initiating or the counterparty side, and three posture fields: `compliance_status`, `grace_expires_at` (the instant the current grace window ends, and null unless the posture is `GRACE`), and `consecutive_noncompliant_checks` (how many consecutive sweeps have found violations, reset to zero by the first violation-free sweep).

The money side of the club record is a two-variant ledger, and the distinction between the variants is the single most consequential piece of arithmetic in this document. **`provisional_cap_committed_cents`** — the *provisional* variant — is what every admission gate compares against `salary_cap_limit_cents`. It sums the current-season cap charge of every contract of this club whose `status` is either `PENDING_APPROVAL` or `ACTIVE`; adds every current-season bonus allocation of those contracts whose `counts_against_provisional` flag is true (that is, whose `bonus_type` is `ROSTER_BONUS` or `PERFORMANCE_LTBE`), whose `season_year` is the current season of 2026, and whose `allocation_status` is either `SCHEDULED` or `EARNED`; and finally adds the club's `dead_money_cents`. **`final_cap_committed_cents`** — the *final* variant, used for compliance reporting and for the season-settlement view — sums the current-season cap charge of only those contracts whose `status` is `ACTIVE`; adds only those current-season bonus allocations of those contracts whose `allocation_status` is `EARNED`, and here the eligible kinds are `ROSTER_BONUS`, `PERFORMANCE_LTBE` **and** `PERFORMANCE_NLTBE`; and again adds `dead_money_cents`.

Neither variant ever counts a `SIGNING_PRORATION` allocation row. That money already sits inside each contract's `current_season_cap_charge_cents`, so counting the row again would double-charge the proration; the proration rows exist as an amortisation ledger that dead-money acceleration consumes, not as an extra charge. The two variants therefore disagree on identical data in two specific ways: a not-yet-approved contract raises the provisional total while never touching the final total, and an earned not-likely-to-be-earned performance bonus raises the final total while never having touched the provisional one. Consider a club holding one `ACTIVE` contract whose current-season charge is 83,333,333 cents, carrying a `SCHEDULED` `PERFORMANCE_LTBE` allocation of 5,000,000 cents and an `EARNED` `PERFORMANCE_NLTBE` allocation of 7,000,000 cents, plus a `PENDING_APPROVAL` contract whose current-season charge is 40,000,000 cents, with no dead money: the provisional total is 128,333,333 cents, the final total is 90,333,333 cents, and against the standard cap the club's `cap_space_cents` is 371,666,667 cents.

`cap_space_cents` is always the club's `salary_cap_limit_cents` less its **provisional** commitment, and it is permitted to go negative. The sweep record's own `cap_space_cents` is computed differently — from the *final* total — and §3.9 spells that out. `dead_money_cents` is the sum of the current-season dead-money charge of every `TERMINATED` contract owned by this club plus the dead money booked against this club as the releasing side of every `CLAIMED` waiver placement.

Both variants are recomputed by every write that creates, terminates, transfers or re-values a contract or a bonus allocation, and they are also available as a computed read: the cap-ledger view recomputes both totals from the club's live contract and allocation rows and returns them side by side with `dead_money_cents` and `cap_space_cents`. That view is strictly read-only and does not advance the club's `version`.

The league office may adjust an existing club's quotas after the fact, supplying any subset of `active_roster_limit`, `reserve_roster_limit`, `injured_reserve_limit`, `practice_squad_limit`, `salary_cap_limit_cents` and `waiver_priority_rank`. The league-wide uniqueness of `waiver_priority_rank` is enforced here too: a rank another club already holds is refused with `ERR_DUPLICATE_WAIVER_PRIORITY`, while a club re-supplying the rank it already holds is accepted. Adjustments take effect immediately, which means the league can legitimately shrink a limit below a club's current headcount. Such an adjustment is **not** refused: the club's `cap_space_cents` is recomputed from the new limit, its compliance posture is re-evaluated in event mode, its `version` is incremented, and the resulting over-limit condition surfaces as a violation at the next evaluation rather than as an error on the adjustment itself.

### 3.2. Players, Service Accrual and Future Contract Rights

The league office registers each player with a `full_name` of 1 to 80 non-blank characters and a `position` drawn from `QB`, `RB`, `WR`, `OL`, `DL`, `LB`, `DB` and `K`. Registration also seeds the four career day buckets the league already has on file — `accrued_active_days`, `accrued_reserve_days`, `accrued_ir_days` and `accrued_practice_days`, each defaulting to 0 and never negative — together with `practice_squad_seasons_used`, also defaulting to 0 and likewise never negative — a figure no later workflow ever moves, so a practice-squad signing or an elevation leaves it exactly as registration seeded it. Everything else about the player is derived: a freshly registered player has `roster_designation` `UNROSTERED`, `medical_status` `CLEARED`, a `current_team_id` of null, and a `designation_effective_at` set to the logical clock at registration.

A player carries **two independent state dimensions**, and this is a point implementers routinely collapse by mistake. `roster_designation` is dimension A, moving through `UNROSTERED`, `ACTIVE`, `RESERVE`, `INJURED_RESERVE`, `PRACTICE_SQUAD` and `WAIVED_PENDING`; it changes only as a side effect of an approved filing or a resolved waiver placement, and it is never accepted as input. `medical_status` is dimension B, moving through `CLEARED`, `PHYSICAL_PENDING`, `REHAB` and `FAILED_PHYSICAL`; it advances on examination and injury-paperwork events that have nothing to do with dimension A. Any combination of the two is legal — a player may be `INJURED_RESERVE` and `PHYSICAL_PENDING`, or `ACTIVE` and `FAILED_PHYSICAL` — and `current_team_id` is null exactly when `roster_designation` is `UNROSTERED`.

`designation_effective_at` is the accrual baseline. Whenever a player's `roster_designation` changes, the server first computes the elapsed whole days since `designation_effective_at` — the elapsed seconds divided by 86,400 and floored — and adds that number to the bucket of the **outgoing** designation, and only then resets `designation_effective_at` to the logical clock. Days spent `ACTIVE` land in `accrued_active_days`, days on reserve in `accrued_reserve_days`, days on injured reserve in `accrued_ir_days`, and days on the practice squad in `accrued_practice_days`.

From those buckets the server derives two different service totals on every accrual event, and they deliberately disagree. **`pension_credit_days`** is the sum of `accrued_active_days`, `accrued_reserve_days` and `accrued_ir_days` — injured-reserve days at full weight, practice-squad days excluded entirely. **`roster_service_days`** is `accrued_active_days` plus `accrued_reserve_days` plus the floor of `accrued_ir_days` multiplied by one half — injured-reserve days at half weight, practice-squad days again excluded. Whenever a player has any injured-reserve days at all, the roster-service total is strictly the smaller of the two.

`service_years` is the floor of `pension_credit_days` divided by 170 days per season, and it selects the player's `contract_rights_class`: `UNRESTRICTED` at 4 or more service years, `ARBITRATION_ELIGIBLE` at exactly 3, `RESTRICTED` at 1 or 2, and `NONE` at 0. Separately, `practice_squad_eligible` is true only when both of two conditions hold: `roster_service_days` is at most 340, and `practice_squad_seasons_used` is strictly less than 2. Take a player with 500 active days, 100 reserve days, 80 injured-reserve days and 200 practice-squad days: pension credit is 680 days, which is 4 service years, so the rights class is `UNRESTRICTED`; roster service is 640 days, so the player is not practice-squad eligible. Shift the injured-reserve figure to 79 days and the outcome moves: pension credit becomes 679 days, which is still only 3 service years, so the rights class drops to `ARBITRATION_ELIGIBLE`, and roster service becomes 639 days.

Two more derived flags ride on the player record. `waiver_revocability_class` reports which revocability a waiver placement would receive if the player were placed on the wire at the current logical clock — `REVOCABLE` or `IRREVOCABLE`, computed by the rule §3.6 describes. `last_physical_passed_at` is resolved the same way, at read time: it is the latest `performed_at` among this player's physicals that stand at `PASSED` at that moment, and null when the player has none — so once the sweep of §3.9 has moved the last passing exam to `EXPIRED`, the field reads null again.

The designation dimension moves only along declared edges, and each edge both accrues the outgoing bucket and re-checks the destination club's quota. A signing takes a player from `UNROSTERED` to `ACTIVE` when the club's active headcount is strictly below its active limit, or from `UNROSTERED` to `PRACTICE_SQUAD` when the contract is a practice-squad contract, the player is practice-squad eligible and the club's practice-squad headcount is strictly below its practice-squad limit. A designation change moves a player `ACTIVE → RESERVE` when the reserve headcount is strictly below the reserve limit, or `RESERVE → ACTIVE` when the active headcount is strictly below the active limit. An elevation moves `PRACTICE_SQUAD → ACTIVE` when the active headcount is strictly below the active limit and the player was practice-squad eligible at the moment the filing was opened — eligibility is settled there and not re-examined when the elevation is approved. An injured-reserve placement moves `ACTIVE → INJURED_RESERVE` when the cited designation is in `PAPERWORK_FILED` and the injured-reserve headcount is strictly below the injured-reserve limit; an activation moves `INJURED_RESERVE → ACTIVE` when the cited designation is in `RETURN_WINDOW_OPEN` and the active headcount is strictly below the active limit. A release moves the player to `WAIVED_PENDING` from whichever of the four rostered designations they held, decrementing that designation's own headcount and accruing that designation's own bucket, while leaving `current_team_id` untouched — the club keeps carrying the cap charge until the wire resolves. From `WAIVED_PENDING` the player either returns to `ACTIVE` at the winning club when a claim is awarded (that club's active headcount must be strictly below its active limit), falls to `UNROSTERED` with a null `current_team_id` when the wire clears, or is restored to the snapshotted pre-release designation when the placement is withdrawn. Finally, a declined or lapsed contract option sends the player to `UNROSTERED` from whichever designation they were holding — ordinarily `ACTIVE` — accruing that designation's own bucket, clearing `current_team_id` and decrementing that designation's own headcount.

### 3.3. The Filing Cycle: Draft, Submission, Decision and Revision

Every roster move in this league is a **filing**, and a filing's life is a small state machine: `DRAFT` at birth, `FILED` once submitted, then either `APPROVED` or `REJECTED`, with `REJECTED` looping back to `DRAFT` through a revision. `APPROVED` and `VOIDED` are the terminal states.

A club's cap analyst opens a filing by naming the filing club as `team_id`, the subject player as `player_id`, and a `transaction_type` drawn from `SIGNING`, `RELEASE`, `DESIGNATION_CHANGE`, `IR_PLACEMENT`, `IR_ACTIVATION` and `PRACTICE_SQUAD_ELEVATION`. The acting analyst's identifier must equal the named `team_id`, and the club's posture must be neither `NON_COMPLIANT` nor `TRANSACTION_FROZEN`. The type then determines which further inputs are required and which preconditions the create must satisfy. A `SIGNING` requires `years` and `base_salary_cents`, and the subject player must currently be `UNROSTERED`. A `RELEASE` requires that the player's owning club is already the filing club and that the player holds one of the four rostered designations `ACTIVE`, `RESERVE`, `INJURED_RESERVE` or `PRACTICE_SQUAD`. A `DESIGNATION_CHANGE` or a `PRACTICE_SQUAD_ELEVATION` requires a `target_designation` — one of `ACTIVE`, `RESERVE`, `INJURED_RESERVE`, `PRACTICE_SQUAD` — that differs from the player's current designation, with the player already owned by the filing club; a `PRACTICE_SQUAD_ELEVATION` additionally requires that the player is practice-squad eligible at create time. Neither type constrains the designation the player is coming *from*, so an elevation opened for a player who is not on the practice squad is accepted and behaves exactly like a designation change apart from that eligibility test; and a `target_designation` or an `injury_designation_id` supplied on a type that has no use for it is stored on the filing verbatim and rendered back unchanged — a cited designation is still held to the ownership test above, but nothing else in the cascade ever reads either field. An `IR_PLACEMENT` or `IR_ACTIVATION` requires an `injury_designation_id` whose designation belongs to both the filing club and the subject player — a mismatch on either is `ERR_DESIGNATION_PLAYER_MISMATCH`, and the same check is re-applied on every revision.

Alongside the type-specific inputs, a `SIGNING` filing carries the whole contract offer: `base_guaranteed` (defaulting to false), `signing_bonus_cents` (defaulting to 0 and never negative), `start_season_year` (defaulting to 2026 and confined to the range 2026 through 2030), `is_practice_squad_contract` (defaulting to false), the option triple `option_type` (defaulting to `NONE`), `option_deadline_at` and `option_salary_cents`, and the two bonus figures `performance_ltbe_cents` and `performance_nltbe_cents`, each of which produces a bonus allocation row at approval when it is greater than zero. `years` must fall between 1 and 7 inclusive, and `base_salary_cents` may not be negative. All of that is read only when the `transaction_type` is `SIGNING`: on any other type these fields are not examined at all, so values that would be refused on a signing pass unnoticed and unstored. Those contract terms are inputs to the filing rather than fields of it: besides the `id` and the three bookkeeping fields of §2.4, a filing's representation carries only `team_id`, `player_id`, `transaction_type`, `status`, `target_designation`, `injury_designation_id`, `contract_id`, `requires_physical`, `filing_deadline_at`, `filed_at`, `filed_by_user_id`, `decided_at`, `decided_by_user_id`, `effective_at`, `rejection_reason`, `revision_count` and `prior_designation`, and the terms themselves are read off the linked contract.

On creation the filing lands in `DRAFT` and the server derives two things. `requires_physical` is true exactly when the `transaction_type` is `SIGNING` or `IR_ACTIVATION`, and false for all four other types. And `filing_deadline_at` is fixed once, at creation, and never recomputed: it is the filing's `created_at` plus 48 hours, snapped into the daily processing window per §2.5. A filing created at 2026-08-10T22:00:00Z therefore has a raw deadline of 2026-08-12T22:00:00Z, whose time of day is at or past the 21:00 close, so the stored `filing_deadline_at` becomes 2026-08-13T13:00:00Z. Creating any filing increments the club's `version` by 1. A `SIGNING` create additionally builds the offered contract immediately — a `PENDING_APPROVAL` contract linked back through `signed_via_transaction_id`, with the filing's own `contract_id` pointing forward at it — computes that contract's proration schedule and current-season charge as §3.4 describes, and re-derives the club's provisional commitment and cap space. That is the moment a not-yet-approved contract begins consuming provisional cap space, which is why a `SIGNING` create is itself subject to the provisional cap ceiling and can be refused with `ERR_CAP_LIMIT_EXCEEDED`.

**Submission** advances a filing `DRAFT → FILED`. It may be performed only by the filing club's own analyst, only while the club is not frozen, only inside the daily processing window, and only while the logical clock is at or before `filing_deadline_at` — the deadline instant itself is still on time, and only a clock strictly later than the deadline is late, at which point the answer is `ERR_FILING_DEADLINE_PASSED`. Submission additionally rehearses the outcome: the designation headcounts the club would hold *after* this filing were approved must satisfy every one of the club's four quotas, and a projection that would breach one is refused with `ERR_ROSTER_LIMIT_EXCEEDED`. What submission does *not* do is re-test the type-specific preconditions the create already satisfied: a filing whose player has since been rostered elsewhere, or has since left the club, still submits and can still be approved. That is how a player can come to hold two `ACTIVE` contracts — two `SIGNING` filings opened while they were `UNROSTERED` may each be carried to approval — and the system tolerates it rather than refusing it. On success the server records `filed_at` as the logical clock and `filed_by_user_id` as the acting identifier, and the filing alone is written: submission advances no club `version`.

**Decision** is the league's, and only the league's. The officer supplies a `decision` of either `APPROVE` or `REJECT`, may supply a `rejection_reason`, and must not be the same identifier that filed. A `rejection_reason` sent alongside an `APPROVE` is neither validated nor stored — approval leaves the field null. Both branches require the logical clock's time of day to be inside the processing window.

An approving decision is the largest cascade in the system. Before anything is written the league re-checks that the club is not frozen, that the subject player's `medical_status` is not `FAILED_PHYSICAL`, and — when `requires_physical` is true — that a physical exists for this player whose `status` is `PASSED`, whose `expires_at` is strictly later than the logical clock, and whose own `transaction_id` either names this very filing or is null: an exam booked against a *different* filing does not clear this one, while an exam booked against no filing at all does. An `IR_PLACEMENT` requires its cited designation to be in `PAPERWORK_FILED`; an `IR_ACTIVATION` requires its cited designation to be in `RETURN_WINDOW_OPEN` **and** the logical clock to lie inside the closed interval from `return_window_opens_at` through `return_window_closes_at`, both endpoints accepted. The projected designation headcounts must satisfy every club quota. Any filing whose destination designation is `PRACTICE_SQUAD` — a `SIGNING` whose contract is a practice-squad contract, or a `DESIGNATION_CHANGE` or `PRACTICE_SQUAD_ELEVATION` naming that target — must find the player still practice-squad eligible, or the approval fails with `ERR_PRACTICE_SQUAD_INELIGIBLE`; an elevation *off* the squad is not re-tested here, its eligibility having been settled when the filing was opened. And every approval, whatever the type, requires the club's provisional commitment — which for a `SIGNING` has counted this contract since the filing was opened — to stand at or below `salary_cap_limit_cents`, so a club already over its cap can have no filing approved at all.

Once those hold, the approval writes: `status` becomes `APPROVED`; `decided_at` and `effective_at` are both set to the logical clock; `decided_by_user_id` records the deciding officer; and `prior_designation` snapshots the player's `roster_designation` as observed immediately *before* the designation side effects below run. The player's outgoing designation bucket then accrues its elapsed days and `designation_effective_at` is reset, after which `pension_credit_days`, `roster_service_days`, `service_years`, `contract_rights_class`, `practice_squad_eligible` and `waiver_revocability_class` are all re-derived. Then the type-specific cascade runs:

- **`SIGNING`**: the linked contract moves `PENDING_APPROVAL → ACTIVE`; its bonus allocation rows are created; `option_status` becomes `PENDING` when the contract carries an option and stays `NOT_APPLICABLE` otherwise; the player's designation becomes `PRACTICE_SQUAD` for a practice-squad contract and `ACTIVE` otherwise; and `current_team_id` becomes the filing club.
- **`RELEASE`**: the player's designation becomes `WAIVED_PENDING`. The contract stays `ACTIVE` and keeps its full cap charge, and `current_team_id` is left alone — the release only authorises a waiver placement, it does not by itself end the club's obligation.
- **`DESIGNATION_CHANGE`** and **`PRACTICE_SQUAD_ELEVATION`**: the player's designation becomes the filing's `target_designation`.
- **`IR_PLACEMENT`**: the player's designation becomes `INJURED_RESERVE`; the cited designation moves `PAPERWORK_FILED → ACTIVE` with `activated_at` set to the logical clock; and its `return_window_opens_at` and `return_window_closes_at` are computed.
- **`IR_ACTIVATION`**: the player's designation becomes `ACTIVE` and their `medical_status` returns to `CLEARED`; the cited designation moves `RETURN_WINDOW_OPEN → CLOSED` with `closed_at` set to the logical clock and `ir_service_credit_days` computed as the floored whole days between `activated_at` and `closed_at`.

Finally the club's four headcounts, both cap totals, `dead_money_cents` and `cap_space_cents` are recomputed, the club's compliance posture is re-evaluated in event mode — where a fresh violation may move the club from `COMPLIANT` to `GRACE` but can never freeze it — and the club's `version` is incremented.

A rejecting decision requires a `rejection_reason` that is present and non-blank. It sets `status` to `REJECTED`, records `decided_at` and `decided_by_user_id`, stores the reason, and increments the club's `version`. When the rejected filing was a `SIGNING`, its contract moves `PENDING_APPROVAL → VOIDED` and the club's provisional commitment and cap space are recomputed. The invariant here is exact, not approximate: after a signing rejection the club's provisional commitment and cap space return to precisely the values they held before the filing was created, cent for cent.

**Revision** is the club's remedy for a rejection, and it is budgeted. A filing may be revised at most twice. A revision on a `REJECTED` filing whose `revision_count` is strictly less than 2 returns it `REJECTED → DRAFT`, increments `revision_count` by 1, clears `rejection_reason` and `decided_at` (along with `decided_by_user_id`, `filed_at` and `filed_by_user_id`), and leaves `filing_deadline_at` exactly as it was — a revision never buys more time, and a revision attempted after the deadline has passed is refused with `ERR_FILING_DEADLINE_PASSED`. A revision may amend `target_designation`, `injury_designation_id`, `years`, `base_salary_cents`, `base_guaranteed`, `signing_bonus_cents`, `option_type`, `option_deadline_at`, `option_salary_cents`, `performance_ltbe_cents` and `performance_nltbe_cents`; every one of them is optional, and a field left out — or supplied as an explicit `null` — keeps the value it already carries rather than being cleared. Two contract terms sit outside that set: `start_season_year` and `is_practice_squad_contract` are still shape-validated when supplied and then ignored, so a revision cannot turn a practice-squad contract into a standard one or move its season. On a filing that is not a `SIGNING` the contract terms are not read at all — neither validated nor stored — so nonsense sent in those fields is simply ignored there. A revision that names an `option_type` of `TEAM_OPTION` or `PLAYER_OPTION` must re-supply both `option_deadline_at` and `option_salary_cents` in the same request, even when the contract already carries them, or the answer is `ERR_INVALID_REQUEST`. For a `SIGNING`, the contract is revived `VOIDED → PENDING_APPROVAL` with the amended terms, re-prorated, and the club's provisional total rises again. Only a `REJECTED` filing may be revised at all; a revision aimed at a filing in any other state is refused with `ERR_INVALID_TRANSACTION_STATE`, save that a filing already carrying the voided-at-the-limit signature reports `ERR_REVISION_LIMIT_EXCEEDED` ahead of it, as rule 14 orders. The acting analyst must own the filing and the club must not be frozen. Either branch increments the club's `version`.

When a revision is attempted on a `REJECTED` filing whose `revision_count` already equals 2, the filing is not returned to draft — it moves `REJECTED → VOIDED` instead, and any linked contract stays `VOIDED` permanently. Note carefully that the void does **not** itself consume a revision: `revision_count` stays at 2, so the pair of a `VOIDED` status with a `revision_count` of 2 is the stable signature the system later recognises. A *further* revision aimed at that already-voided filing is the one case that reports `ERR_REVISION_LIMIT_EXCEEDED`.

Two filings can also be voided without anyone asking. A `DRAFT` filing whose `filing_deadline_at` has passed is voided by the daily sweep, and if it was a `SIGNING` its contract moves `PENDING_APPROVAL → VOIDED` and the club's provisional commitment is recomputed downward. And an `APPROVED` `RELEASE` filing is voided when the waiver placement it authorised is withdrawn — in that case `effective_at` is cleared back to null, because the authorised release never took hold.

### 3.4. Contract Economics: Proration, Bonus Allocations, Options and Dead Money

A contract is never created directly; it is always born from a `SIGNING` filing, which is why it carries `signed_via_transaction_id` pointing at the filing that produced it, a `player_id` naming the signing player, and a `team_id` naming the owning club. The owning club is not immutable — a waiver award and a trade execution both reassign it. A contract's `status` runs `PENDING_APPROVAL` at birth, `ACTIVE` once the filing is approved, `VOIDED` if the filing is rejected or voided (and back to `PENDING_APPROVAL` if the filing is revised), and `TERMINATED` as its one terminal state. `total_value_cents` is simply `base_salary_cents` multiplied by `years`, plus `signing_bonus_cents`.

**Proration.** A signing bonus is paid up front but charged against the cap over several seasons, and the league caps that spread at five seasons. `proration_years` is therefore the lesser of `years` and 5. `annual_proration_cents` is the floor of `signing_bonus_cents` divided by `proration_years`, and it is the charge every prorated season carries except the last. `final_season_proration_cents` absorbs the whole rounding remainder: it is `signing_bonus_cents` less `annual_proration_cents` multiplied by one fewer than `proration_years`. The consequence is that the season charges always sum back to the bonus exactly. A 10,000,000-cent bonus on a three-year deal gives an annual proration of 3,333,333 cents and a final-season proration of 3,333,334 cents, and twice 3,333,333 plus 3,333,334 is exactly 10,000,000. When `years` is at most 5 every contract season carries a share; when `years` exceeds 5 the spread is clamped to five seasons, so each annual charge is larger than a simple division by `years` would give and seasons six onward carry no proration at all.

**Current-season charge.** Each contract's `current_season_cap_charge_cents` is derived for the current season, which for this system is 2026. Let the elapsed season count be 2026 less `start_season_year`, and let the proration span again be the lesser of `years` and 5. If the elapsed season count equals one less than the proration span, the season's proration share is `final_season_proration_cents`; if the elapsed season count is smaller than one less than the proration span, the share is `annual_proration_cents`; and if it is larger, the share is zero. The contract's current-season charge is then `base_salary_cents` plus that share. A contract with an 80,000,000-cent base salary, a 10,000,000-cent signing bonus, three years and a 2026 start has an elapsed season count of zero, a proration share of 3,333,333 cents, and a current-season charge of 83,333,333 cents.

**Bonus allocations.** Approving a `SIGNING` materialises the contract's cap allocation rows, each linked by `contract_id` and each carrying a `bonus_type`, the `season_year` it is charged against, an `amount_cents` that may not be negative, an `allocation_status` and a derived `counts_against_provisional` flag. One `SIGNING_PRORATION` row is created per prorated season — exactly `proration_years` rows, created even when the signing bonus is zero, in which case each simply carries an `amount_cents` of 0 — carrying `annual_proration_cents` except for the final prorated season, which carries `final_season_proration_cents`; the flag on these rows is false, because that money already lives inside the contract's current-season charge and these rows exist only as the amortisation ledger that dead-money acceleration later consumes. One `PERFORMANCE_LTBE` row is created when the filing carried a `performance_ltbe_cents` greater than zero, charged against `start_season_year`, with the flag true. One `PERFORMANCE_NLTBE` row is created when the filing carried a `performance_nltbe_cents` greater than zero, also charged against `start_season_year`, with the flag false. A `ROSTER_BONUS` row, should one exist, likewise carries the flag as true. Every row is born `SCHEDULED`. A club or agent reading a contract's allocations receives them in creation order: the `SIGNING_PRORATION` rows first in ascending `season_year`, then the `PERFORMANCE_LTBE` row, then the `PERFORMANCE_NLTBE` row.

A league officer may mark a `SCHEDULED` allocation **earned**, which requires the parent contract to be `ACTIVE`. A row that is no longer `SCHEDULED`, or one whose parent contract is not `ACTIVE`, is refused with `ERR_INVALID_CONTRACT_STATE`, and where both are wrong at once the row's own status is the one diagnosed. Earning stamps `earned_at` with the logical clock and moves `allocation_status` to `EARNED`, then recomputes the owning club's `provisional_cap_committed_cents`, `final_cap_committed_cents` and `cap_space_cents` and re-evaluates the club's posture in event mode. The two performance kinds behave asymmetrically here, and both halves matter: a `PERFORMANCE_NLTBE` row enters the final cap variant for the first time at this moment while never having entered the provisional variant, whereas a `PERFORMANCE_LTBE` row leaves the provisional variant unchanged — it was already counted there — and raises only the final variant. An `EARNED` row is terminal: it is never subsequently forfeited.

**Termination and dead money.** A contract reaches `TERMINATED` by exactly three routes, each recording its own `termination_reason`: `RELEASE_CLEARED` when a waiver placement clears, `OPTION_DECLINED` when an option is declined, and `OPTION_LAPSED` when an option deadline passes unanswered. All three run the same allocation cascade. Every unamortised `SIGNING_PRORATION` row — the current season's row and every later one, that is every such row whose `season_year` is 2026 or beyond — moves `SCHEDULED → ACCELERATED`, meaning it stops counting as a live cap charge and its money is folded into the dead-money split below. Every still-`SCHEDULED` `ROSTER_BONUS`, `PERFORMANCE_LTBE` and `PERFORMANCE_NLTBE` row moves `SCHEDULED → FORFEITED`, leaving both cap variants and contributing nothing to dead money — a declined option forfeits unearned performance money outright. Rows already `EARNED` are untouched. The cascade itself leaves the option dimension alone: it is whichever route reached termination that has already set `option_status`, so a contract terminated on a cleared release keeps the `PENDING` option it was carrying until the sweep lapses it.

The dead-money split itself turns on a single date. Let the elapsed season count again be 2026 less `start_season_year` and the proration span be the lesser of `years` and 5, and let the unamortised balance be `signing_bonus_cents` less `annual_proration_cents` multiplied by the elapsed season count. The league's **acceleration cutoff** is 2026-09-01T00:00:00Z, and the comparison against it is strict. If the release instant is strictly earlier than the cutoff, the current season keeps only its own share: `dead_money_current_season_cents` is `annual_proration_cents` and `dead_money_next_season_cents` is the unamortised balance less `annual_proration_cents`. If the release instant is at or after the cutoff, the whole balance accelerates: `dead_money_current_season_cents` is the full unamortised balance and `dead_money_next_season_cents` is zero. Either way the two components sum to the unamortised balance, and the current-season component is added to the club's `dead_money_cents`. The contract's base salary leaves the books entirely — only bonus money survives as dead money — except that `base_guaranteed`, when true, means the current-season base salary is fully guaranteed and does enter dead money on a release that goes unclaimed. Concretely, on a 10,000,000-cent bonus over three years starting in 2026, with an annual proration of 3,333,333 cents and nothing yet amortised: a release at 2026-08-20T14:00:00Z charges 3,333,333 cents this season and 6,666,667 cents next, while a release at 2026-09-02T14:00:00Z charges the full 10,000,000 cents this season and nothing next. A release at exactly 2026-09-01T00:00:00Z accelerates.

**The option dimension.** `option_status` is a second, parallel dimension on the contract that advances independently of `status`. It begins `NOT_APPLICABLE`, and moves to `PENDING` at the moment the contract activates *if* the contract carries an option — that is, if `option_type` is `TEAM_OPTION` or `PLAYER_OPTION`, in which case both `option_deadline_at` and `option_salary_cents` are required and the latter may not be negative. An `option_type` of `NONE` leaves the dimension at `NOT_APPLICABLE` forever — even when the filing volunteered an `option_deadline_at` or an `option_salary_cents` anyway, which are stored on the contract and rendered back verbatim but arm nothing: no sweep ever lapses such a contract, because lapsing looks only at contracts whose `option_status` is `PENDING`. An attempt to decide an option that is not `PENDING` — never applicable, or already resolved — is refused with `ERR_INVALID_OPTION_STATE`.

Who may decide is determined by which party holds the option. A `TEAM_OPTION` may be decided only by the owning club's cap analyst, whose identifier must equal the contract's `team_id`; a `PLAYER_OPTION` may be decided only by the player's agent, whose identifier must equal the contract's `player_id`. Reaching for the other party's option is an `ERR_ACTOR_SCOPE_VIOLATION` in its own right even when the caller is the right club or the right player for that contract — an analyst answering a `PLAYER_OPTION`, an agent answering a `TEAM_OPTION` — and both scope refusals are settled before the request body is examined at all, so they outrank the request-shape, version, state and deadline checks that follow. In both cases the contract's `status` must be `ACTIVE`, the logical clock must be at or before `option_deadline_at` — a decision landing exactly on the deadline instant is accepted, and only a clock strictly later is refused with `ERR_OPTION_DEADLINE_PASSED` — and the request must carry `expected_contract_version` matching the contract's current `version`. Where the option dimension and the contract's `status` are both wrong at once — a `LAPSED` option on a contract already `TERMINATED`, say — the option dimension is the one diagnosed, so the answer is `ERR_INVALID_OPTION_STATE` rather than `ERR_INVALID_CONTRACT_STATE`. Either branch increments the contract's `version` by 1.

An `EXERCISE` decision moves `option_status` `PENDING → EXERCISED`, replaces `base_salary_cents` with `option_salary_cents`, adds one to `years`, then recomputes the contract's current-season charge and `total_value_cents` from those amended terms together with the owning club's cap fields. The bonus schedule is deliberately *not* re-derived: `proration_years`, `annual_proration_cents` and `final_season_proration_cents` stay exactly as the signing fixed them even though `years` has grown, and the exercise is subject to no cap ceiling of its own — it may push the club over its limit, to be caught later as a violation. A `DECLINE` decision moves `option_status` `PENDING → DECLINED` and simultaneously terminates the contract `ACTIVE → TERMINATED` with `termination_reason` `OPTION_DECLINED`, running the full dead-money and allocation cascade, sending the player to `UNROSTERED` with a null `current_team_id`, and recomputing the club's headcounts and cap fields. If nobody decides at all, the daily sweep moves `option_status` `PENDING → LAPSED` once the logical clock passes `option_deadline_at`, terminating the contract with `termination_reason` `OPTION_LAPSED` and applying exactly the same dead-money and roster consequences as the decline path.

A contract also keeps a backward view of its trade history: every trade asset that has ever referenced this contract, across all trades, is retrievable as a list.

### 3.5. The Medical Dimension: Injury Designations, Return Windows and Physicals

The medical dimension belongs entirely to the club medical officer, and it is the one part of the system a cap analyst cannot touch. It comprises two record types — injury designations, which govern a player's stay on injured reserve, and physical examinations, which gate signings, activations and physically contingent trades.

**Opening a designation.** A medical officer opens an injury designation for one of their own club's rostered players, naming the `player_id`, the `team_id` (which must equal the acting officer's identifier), and a `designation_type` of `INJURED_RESERVE`, `INJURED_RESERVE_RETURN_ELIGIBLE` or `NON_ROSTER_INJURY`. The player must already be owned by that club and must currently be either `ACTIVE` or `RESERVE` — an injured-reserve or practice-squad player cannot be freshly designated. Either failure is `ERR_INVALID_DESIGNATION_STATE`, and both are read before the one-open-designation test below. A player may hold only one open designation at a time; if any designation for that player is currently in `PENDING_PAPERWORK`, `PAPERWORK_FILED`, `ACTIVE` or `RETURN_WINDOW_OPEN`, the request is refused with `ERR_INJURY_DESIGNATION_ALREADY_OPEN`. On creation the designation records `placed_at` as the logical clock, lands in `PENDING_PAPERWORK`, and fixes `minimum_stay_days` from the type: 21 days for `INJURED_RESERVE`, 14 days for `INJURED_RESERVE_RETURN_ELIGIBLE` and 28 days for `NON_ROSTER_INJURY`. The return window is *not* computed yet.

**Filing the paperwork.** The designation advances `PENDING_PAPERWORK → PAPERWORK_FILED` when the club's medical officer files the league paperwork, supplying a `paperwork_reference` that is present and non-blank. The server stamps `paperwork_filed_at` with the logical clock and, in the same write, sets the player's `medical_status` to `REHAB` and advances that player's own `version`. The move is unconditional in the origin state: `REHAB` is written over whatever the player held, so a `PHYSICAL_PENDING` or even a `FAILED_PHYSICAL` player emerges from this step in `REHAB`. Filing paperwork twice is refused with `ERR_INVALID_DESIGNATION_STATE`. Until the paperwork is on file the club cannot get its `IR_PLACEMENT` filing approved — that approval demands the `PAPERWORK_FILED` state and otherwise answers `ERR_INJURY_PAPERWORK_MISSING` — and an unfiled designation that has been sitting for more than a day becomes a compliance violation in its own right, as §3.9 sets out.

**Activation and the return window.** The designation reaches `ACTIVE` only as a side effect of the league approving the `IR_PLACEMENT` filing that cites it, and only when the club's injured-reserve headcount is strictly below its `injured_reserve_limit`. At that moment `activated_at` is stamped with the logical clock and the return window is derived: `return_window_opens_at` is `activated_at` plus `minimum_stay_days` days, and `return_window_closes_at` is `return_window_opens_at` plus a further 21 days. Both are null until activation. A designation of type `INJURED_RESERVE_RETURN_ELIGIBLE` activated at 2026-08-12T14:00:00Z therefore opens on 2026-08-26T14:00:00Z and closes on 2026-09-16T14:00:00Z.

The window opens on the clock, not on request: the daily sweep moves a designation `ACTIVE → RETURN_WINDOW_OPEN` once the logical clock has reached `return_window_opens_at` and has not yet passed `return_window_closes_at`, and that step changes no roster or cap value — it merely makes the `IR_ACTIVATION` filing approvable. The return window is a **closed** interval: an activation landing exactly on `return_window_opens_at` or exactly on `return_window_closes_at` is on time, and only an instant outside that inclusive span draws `ERR_RETURN_WINDOW_CLOSED`. An approved `IR_ACTIVATION` moves the designation `RETURN_WINDOW_OPEN → CLOSED`, which additionally requires a passed, unexpired return physical for the player; it stamps `closed_at` with the logical clock and computes `ir_service_credit_days` as the floored whole days between `activated_at` and `closed_at`, which is the figure that feeds the player's `accrued_ir_days` and is then weighted differently by the two service-time totals.

If nobody activates in time, the sweep closes the door. A designation still in `ACTIVE` when the logical clock passes `return_window_closes_at` moves `ACTIVE → EXPIRED`, and a designation in `RETURN_WINDOW_OPEN` when the clock passes the same instant moves `RETURN_WINDOW_OPEN → EXPIRED`. Both stamp `closed_at` and compute `ir_service_credit_days` by the same floored-days rule, and in the expiry case the player simply stays on injured reserve for the balance of the season. Attempting to activate from `ACTIVE` rather than from `RETURN_WINDOW_OPEN` is refused with `ERR_INVALID_DESIGNATION_STATE`.

**Scheduling a physical.** A club's medical officer schedules a physical for a player, naming `player_id`, `team_id` (again equal to the acting identifier), an `exam_type` of `ENTRY_PHYSICAL`, `TRADE_PHYSICAL` or `RETURN_PHYSICAL`, and the examination window bounded by `window_start_at` and `window_end_at`, where the end must be strictly later than the start. Optional back-references tie the exam to what it satisfies: `transaction_id` names the filing the exam is meant to clear, and `trade_id` names a trade — the latter is required when `exam_type` is `TRADE_PHYSICAL`, and that trade must be in `MEDICAL_REVIEW` with a `PHYSICAL_CONTINGENT` clause, or the request is refused with `ERR_INVALID_TRADE_STATE`. A `RETURN_PHYSICAL` requires the player to hold an injury designation in `ACTIVE` or `RETURN_WINDOW_OPEN`, and answers `ERR_INVALID_DESIGNATION_STATE` when they hold none. Both of those tests precede the window-collision test below.

A player may hold **one** scheduled examination window at a time, and the collision test uses **half-open** interval semantics: the requested window, treated as starting at `window_start_at` and ending strictly before `window_end_at`, collides with an existing window of another `SCHEDULED` exam for the same player exactly when the requested start is strictly earlier than the existing end and the existing start is strictly earlier than the requested end. Touching endpoints therefore do *not* collide — a new window beginning exactly at an existing window's `window_end_at` is accepted. Exams whose status is `PASSED`, `FAILED` or `EXPIRED` free their window and are ignored by the test. A genuine collision is refused with `ERR_EXAM_WINDOW_OVERLAP`. Scheduling an exam sets the player's `medical_status` to `PHYSICAL_PENDING` and advances the player's `version`, and it does so unconditionally — out of `CLEARED`, out of `REHAB`, or out of `FAILED_PHYSICAL` when the club is re-examining a player who previously failed — whatever the `exam_type` happens to be.

**Recording the result.** The medical officer who owns the exam records a `result` of either `PASSED` or `FAILED` together with the `performed_at` instant at which the examination actually took place. `performed_at` must fall inside the **half-open** window — at or after `window_start_at` and strictly before `window_end_at` — and anything else is `ERR_RESULT_OUTSIDE_EXAM_WINDOW`. Recording a result on an exam that is not `SCHEDULED` is `ERR_INVALID_EXAM_STATE`. Either outcome stamps `result_recorded_at` with the logical clock and advances the subject player's own `version`, whether or not the outcome actually changed that player's `medical_status`. `result` is an input to this request only: a physical exam's own representation carries no `result` field of its own, and the outcome it recorded is read off the exam's `status` instead.

A passed result moves the exam `SCHEDULED → PASSED` and sets `expires_at` to `performed_at` plus 14 days. Validity is tested strictly: an approval may cite an exam only while that exam is `PASSED` and its `expires_at` is strictly later than the logical clock, so an exam performed at 2026-08-10T14:00:00Z may still be cited at 2026-08-24T13:59:59Z but no longer at 2026-08-24T14:00:00Z, at which point the sweep moves it `PASSED → EXPIRED`. A pass also becomes the instant the player's derived `last_physical_passed_at` reports, resolved at read time as §3.2 describes rather than stored, and returns the player's `medical_status` to `CLEARED`, provided no other scheduled exam remains outstanding — where "outstanding" counts only exams still in `SCHEDULED`, so a player with a second booking keeps `PHYSICAL_PENDING`. Separately, when an `IR_ACTIVATION` is approved on the strength of a passed, unexpired return physical, that approval itself moves the player's `medical_status` `PHYSICAL_PENDING → CLEARED`.

A failed result moves the exam `SCHEDULED → FAILED` and the player's `medical_status` to `FAILED_PHYSICAL`, which immediately blocks the player from being approved on any filing, from riding on an executed trade, and from being tendered — all three answer `ERR_PLAYER_FAILED_PHYSICAL`. When the failed exam was a `TRADE_PHYSICAL` whose named trade is still in `MEDICAL_REVIEW`, the failure cascades through three further steps in order: the linked trade moves `MEDICAL_REVIEW → VOIDED` with `void_reason` `FAILED_PHYSICAL`; every one of that trade's assets moves `PROPOSED → RETURNED`; and because the medical-review interval is thereby released, both clubs' `open_medical_review_count` is decremented by 1. A trade that has already left `MEDICAL_REVIEW` by the time the failure is recorded — voided by the sweep, say — is left exactly as it stands, and only the exam and the player are written. A club may re-examine a failed player by scheduling a fresh exam, which returns `medical_status` `FAILED_PHYSICAL → PHYSICAL_PENDING`.

### 3.6. The Waiver Wire: Placement, Revocability, Claims and the Award Pipeline

A release does not by itself free a player. Once the league has approved a `RELEASE` filing, the releasing club's analyst places the player on the **waiver wire** by citing that filing: the placement names the `player_id`, the releasing club as `from_team_id`, and the authorising filing as `transaction_id`. The acting analyst's identifier must equal `from_team_id`, the cited filing must be an `APPROVED` filing of type `RELEASE` for the same player and the same club (otherwise `ERR_RELEASE_FILING_MISMATCH`), the player must currently be `WAIVED_PENDING` — otherwise `ERR_INVALID_WAIVER_STATE`, read after the filing-mismatch test and before the uniqueness test — and no other placement for that player may still be `PENDING` — a second one is refused with `ERR_WAIVER_ALREADY_PENDING`.

Placement freezes three things that never move again. `contract_id` captures the player's `ACTIVE` contract — the earliest-created one, in the unusual case that the player holds more than one, and null if the player somehow holds none — which rides along on the wire. `origin_designation` copies the authorising filing's `prior_designation` — the designation the player held immediately before the release took hold, one of `ACTIVE`, `RESERVE`, `INJURED_RESERVE` or `PRACTICE_SQUAD` — and it is the value a withdrawal restores verbatim. And `revocability` is evaluated once, at `placed_at`, and frozen: a placement made strictly before 2026-08-25T16:00:00Z is `REVOCABLE`, and a placement made at or after that instant is `IRREVOCABLE`. The same rule, evaluated against the current clock rather than a placement, is what the player record reports as `waiver_revocability_class`.

Revocability also sets the clearance clock. `clearance_deadline_at` is `placed_at` plus 24 hours for a `REVOCABLE` placement or plus 48 hours for an `IRREVOCABLE` one, snapped into the daily processing window per §2.5. A placement made at 2026-08-10T09:00:00Z is `REVOCABLE`, giving a raw deadline of 2026-08-11T09:00:00Z, which snaps forward to 2026-08-11T13:00:00Z. A placement made at exactly 2026-08-25T16:00:00Z is `IRREVOCABLE`, giving a raw deadline of 2026-08-27T16:00:00Z, which already sits inside the window and is kept unchanged. Placement stamps `placed_at` with the logical clock, leaves the wire in `PENDING`, and increments the releasing club's `version`.

**Claiming.** While a wire is `PENDING` and the logical clock is strictly before `clearance_deadline_at`, any *other* club's analyst may lodge a claim, naming their own club as `claiming_team_id`. The acting identifier must equal that club, the claiming club may not be the releasing club — an attempt by the releasing club is `ERR_ACTOR_SCOPE_VIOLATION`, settled before that club's own `expected_team_version` has even been read — the claiming club must not be `NON_COMPLIANT` or `TRANSACTION_FROZEN`, and the same club may not claim the same wire twice — a repeat is `ERR_CLAIM_ALREADY_SUBMITTED`. A claim aimed at a wire that has already resolved, or lodged once the clock has reached `clearance_deadline_at`, is refused with `ERR_INVALID_WAIVER_STATE`, and both readings precede the posture and duplicate tests. The claim is born `SUBMITTED`, stamps `submitted_at` with the logical clock, links back through `waiver_request_id`, and captures three figures. `priority_rank_snapshot` copies the claiming club's `waiver_priority_rank` and is the ranking key the award pipeline uses. `cap_space_snapshot_cents` copies the claiming club's `cap_space_cents` — this value is retained for audit only and is **never** the eligibility input. `required_cap_charge_cents` is the `base_salary_cents` of the wired contract, that is, the charge the claiming club would assume, and 0 when the wire carries no contract at all. Submitting a claim increments the wire's `claim_count` and the claiming club's `version` by 1. `claim_count` itself is maintained as the number of claims on this wire whose status is any of `SUBMITTED`, `AWARDED`, `LOST` or `INVALIDATED`.

**Withdrawal.** The releasing club may pull a player back off the wire, but only under four conditions: the acting analyst owns the releasing club, the placement's `revocability` is `REVOCABLE`, the wire is still `PENDING`, and the logical clock is strictly before `clearance_deadline_at`. A withdrawal attempt on an `IRREVOCABLE` placement, or on a wire that has already resolved, is refused with `ERR_INVALID_WAIVER_STATE`. The releasing club must also have room: its headcount for the `origin_designation` being restored must be strictly below the matching quota. A withdrawal moves the wire `PENDING → WITHDRAWN`, stamps `processed_at`, restores the player's `roster_designation` from `WAIVED_PENDING` back to `origin_designation` with `current_team_id` restored to `from_team_id`, increments the releasing club's headcount for that designation by 1, re-evaluates the club's posture in event mode, voids the authorising `RELEASE` filing `APPROVED → VOIDED`, and moves every still-`SUBMITTED` claim on the wire to `INVALIDATED`. `releasing_team_dead_money_cents` stays at 0 and the contract keeps its `ACTIVE` status — a withdrawal is fiscally and numerically a no-op, and the club's roster headcount ends up exactly where it began before the release.

**Processing.** Once the logical clock has reached `clearance_deadline_at` — the boundary instant itself is enough, and a request made strictly earlier is refused with `ERR_CLEARANCE_NOT_REACHED` — a league officer processes the wire from inside the daily processing window. A wire that has already resolved — `CLAIMED`, `CLEARED` or `WITHDRAWN` — cannot be processed a second time; that refusal is `ERR_INVALID_WAIVER_STATE`, and it is read ahead of both the window test and the clearance test. Processing runs an **ordered elimination pipeline followed by a single ranking step**, and the order is observable rather than cosmetic.

The candidate set is every claim on this wire whose status is `SUBMITTED`; claims already `INVALIDATED`, `AWARDED` or `LOST` from an earlier attempt are excluded. The pipeline then applies three filters, in this sequence. First the **cap filter** drops every claim whose `required_cap_charge_cents` is greater than the claiming club's `cap_space_cents` *read live at processing time* — not the audit snapshot captured at submission. Second the **posture filter** drops every claim whose claiming club's `compliance_status` is `NON_COMPLIANT` or `TRANSACTION_FROZEN` at processing time. Third the **roster filter** drops every claim whose claiming club's `active_roster_count` has reached or exceeded its `active_roster_limit` at processing time. Every dropped claim moves `SUBMITTED → INVALIDATED` and is never ranked. Only then does the **ranking step** run: the surviving claims are sorted by `priority_rank_snapshot` ascending, ties broken by the claim's own `created_at` ascending, and the first survivor moves `SUBMITTED → AWARDED` while every other survivor moves `SUBMITTED → LOST`. Because the cap filter runs *before* the ranking step, a rank-1 claim that fails the cap test is eliminated outright and a rank-9 claim wins the player; applying the same three tests after ranking would instead award the rank-1 claim and then have to reject the award, so the sequence genuinely decides the outcome.

If at least one claim survives, the wire moves `PENDING → CLAIMED`. `awarded_to_team_id` records the winner and `processed_at` records the logical clock. Because a winner exists, the player's `current_team_id` becomes the winning club and their `roster_designation` moves `WAIVED_PENDING → ACTIVE`. Because the player changed clubs, the contract's `team_id` becomes the winning club and that club's `active_roster_count`, `provisional_cap_committed_cents`, `final_cap_committed_cents` and `cap_space_cents` are all recomputed. Because the winner's committed cap changed, the winner's `compliance_status` is re-evaluated in event mode. On the releasing side, `releasing_team_dead_money_cents` is charged to `from_team_id` and is the dead-money split applied to the **unamortised signing bonus only** — the base salary travels with the contract to the claiming club, so the releasing club keeps no base charge — after which the releasing club's cap fields and posture are likewise recomputed.

If no claim survives the three filters, the wire moves `PENDING → CLEARED` instead. `processed_at` is stamped, every `SUBMITTED` claim is moved to `INVALIDATED`, the player's `roster_designation` moves `WAIVED_PENDING → UNROSTERED` with `current_team_id` set to null, and the contract moves `ACTIVE → TERMINATED` with `termination_reason` `RELEASE_CLEARED`, running the full acceleration-and-forfeiture cascade of §3.4. `releasing_team_dead_money_cents` is then the contract's `dead_money_current_season_cents`, and the releasing club's `dead_money_cents`, cap fields and posture are all recomputed. While a wire is `PENDING` or after it is `WITHDRAWN`, `releasing_team_dead_money_cents` is 0.

Processing is also subject to the roster quota in its own right, and the test is read only once the winner is known: the award is rehearsed on the winning club and refused with `ERR_ROSTER_LIMIT_EXCEEDED` when any one of that club's four projected designation headcounts — its active count raised by one, the other three exactly as they stand — would exceed its own limit. Because the elimination pipeline has already written by the time that gate is read, this is the one operation where the all-or-nothing rule of §2.9 does not hold end to end: a processing attempt refused here leaves the claims it eliminated at `INVALIDATED` and leaves `processed_at` stamped on a wire that is still `PENDING`, and the league may attempt the processing again. Each claim can be read individually, complete with the snapshots the pipeline consulted.

### 3.7. Trade Construction, Negotiation Rounds, Medical Review and Execution

A trade is a negotiation between exactly two clubs, and it is the only place in this system where two clubs act on the same record in alternation. One club's analyst opens it, naming itself as `initiating_team_id` and the other club as `counterparty_team_id`. The acting identifier must equal `initiating_team_id`, both clubs must exist, both must have a posture that is neither `NON_COMPLIANT` nor `TRANSACTION_FROZEN`, and the two must be distinct — naming the same club twice is `ERR_TRADE_SAME_TEAM`. A `conditional_clause_type` may be attached: `NONE` is the default, `PICK_CONDITIONAL` records a pick-based contingency, and `PHYSICAL_CONTINGENT` routes acceptance through a medical review instead of straight to execution. Either non-`NONE` clause requires a non-blank `condition_note` describing the term. A new trade lands in `PROPOSED` with `round_count` at 1.

**Assets.** A trade carries assets, each linked by `trade_id` and each polymorphic on `asset_kind`. A `CONTRACT` asset requires a `contract_id` and forbids the other companion fields; a `DRAFT_PICK` asset requires `draft_pick_year`, confined to 2027 through 2031, and `draft_pick_round`, confined to 1 through 7; a `CASH_CONSIDERATION` asset requires a `cash_amount_cents` greater than zero. Missing or mismatched companion fields are a request-shape failure, `ERR_INVALID_REQUEST`. Every asset also carries a `direction` of either `TO_COUNTERPARTY` or `TO_INITIATOR`, naming which club receives it, and **only the sending club may add it**: a `TO_COUNTERPARTY` asset may be added only by the initiating club's analyst, and a `TO_INITIATOR` asset only by the counterparty club's analyst. Those two scope tests sit on either side of the body: membership in the trade is settled before the body is read at all, so a club that is not a party to the trade draws `ERR_ACTOR_SCOPE_VIOLATION` whatever it sent, whereas the direction test can only follow the parse — a party sending from the wrong side of a malformed body sees `ERR_INVALID_REQUEST` first. Assets may be added only while the trade is `PROPOSED` or `COUNTERED`; adding one to an accepted, executed or voided trade is `ERR_INVALID_TRADE_STATE`. A `CONTRACT` asset must reference a contract whose `status` is `ACTIVE` and whose `team_id` is the sending club, or the request fails with `ERR_ASSET_NOT_OWNED` — and that same ownership test is applied again at execution time, because a contract can change hands in between.

Adding an asset stores its `cap_charge_snapshot_cents`: for a `CONTRACT` asset that is the referenced contract's `current_season_cap_charge_cents` as it stands at the moment of the addition; for a `CASH_CONSIDERATION` asset it is the `cash_amount_cents`; and for a `DRAFT_PICK` asset it is 0. The asset is born `PROPOSED` and every addition re-derives both clubs' cap deltas and increments the trade's `version`. An asset's representation always carries all four companion fields whatever its kind, per §2.4: `contract_id`, `draft_pick_year` and `draft_pick_round` read `null` on a kind that does not use them, while `cash_amount_cents` reads 0 rather than null on a `CONTRACT` or a `DRAFT_PICK` asset.

**Cap deltas and compatibility.** For each club, the incoming total is the sum of `cap_charge_snapshot_cents` over the trade's still-`PROPOSED` assets directed *at* that club, and the outgoing total is the same sum over the still-`PROPOSED` assets directed *away from* it; `RETURNED` and `TRANSFERRED` assets are excluded. `cap_delta_initiating_cents` is the initiating club's incoming total less its outgoing total, and `cap_delta_counterparty_cents` is the counterparty club's incoming total less its outgoing total. Because every asset is directed at exactly one club, the two deltas are always exact negations of one another. The compatibility test, applied at execution, requires that for **both** clubs the club's `provisional_cap_committed_cents` plus its own delta is at or below its `salary_cap_limit_cents`; a failure is reported for the offending club as `ERR_TRADE_CAP_INCOMPATIBLE`. Draft picks contribute nothing to either side, while cash consideration behaves exactly like a contract charge — a cost to the paying club and a credit to the receiving one.

**Countering.** The negotiation alternates strictly. From `PROPOSED`, only the counterparty club may counter, moving the trade `PROPOSED → COUNTERED`; from `COUNTERED`, only the initiating club may counter back, moving it `COUNTERED → PROPOSED` and closing the cycle. A counter from the wrong club is `ERR_ACTOR_SCOPE_VIOLATION`. In a state that owes no response at all — `ACCEPTED`, `MEDICAL_REVIEW`, `EXECUTED` or `VOIDED` — there is no club whose turn it is, so only membership in the trade is tested: either party countering or accepting there is refused with `ERR_INVALID_TRADE_STATE`, while an outsider still draws `ERR_ACTOR_SCOPE_VIOLATION`. Each counter must carry `expected_trade_version` matching the trade's current `version`, increments `round_count` by 1 and increments `version` by 1. The round budget is 3: since a trade is created with `round_count` at 1, exactly two counters are permitted (taking `round_count` to 2 and then to 3), and the third counter does not flip the trade at all. Once `round_count` has reached 3, a counter — by the counterparty from `PROPOSED`, or by the initiator from `COUNTERED`, symmetrically on both edges — instead moves the trade to `VOIDED` with `void_reason` `ROUND_LIMIT_EXCEEDED`, still increments `round_count`, and moves every `PROPOSED` asset to `RETURNED`. Whichever club owes the response when the budget is exhausted is the club whose counter kills the deal.

**Acceptance.** Acceptance is the mirror of countering: from `PROPOSED` only the counterparty may accept, and from `COUNTERED` only the initiator may. Either way the trade must carry at least one still-`PROPOSED` asset: an empty trade is refused with `ERR_INVALID_TRADE_STATE`, read before either club's posture is examined. Where the trade has no physical contingency — a `conditional_clause_type` of `NONE` or `PICK_CONDITIONAL` — acceptance moves the trade to `ACCEPTED`, stamps `accepted_at` with the logical clock, and awaits league execution.

Where the clause is `PHYSICAL_CONTINGENT`, acceptance instead moves the trade to `MEDICAL_REVIEW` and occupies a **medical-review slot on both clubs**. Each club has capacity for exactly one concurrent medical review, and the occupied interval runs from a trade's `accepted_at` through its `medical_review_deadline_at` as a **closed** interval — touching endpoints *do* collide, which is deliberately the opposite of the half-open rule governing examination windows. The candidate interval runs from the logical clock through the logical clock plus 72 hours, and it overlaps an existing occupied interval exactly when the candidate's start is at or before the existing interval's end and the existing interval's start is at or before the candidate's end. A club is available only when the number of its overlapping occupied intervals is strictly less than 1, that is, when it has none; both clubs must be available, and otherwise the acceptance is refused with `ERR_MEDICAL_REVIEW_SLOT_TAKEN`. Only trades currently in `MEDICAL_REVIEW` occupy a slot — voided and executed trades release theirs. A successful contingent acceptance stamps `accepted_at`, sets `medical_review_deadline_at` to `accepted_at` plus 72 hours, and increments both clubs' `open_medical_review_count` by 1. Every acceptance increments the trade's `version`.

**Execution.** Only the league office executes, and only from inside the daily processing window. An `ACCEPTED` trade may be executed when both clubs' postures are neither `NON_COMPLIANT` nor `TRANSACTION_FROZEN`, every `CONTRACT` asset still references an `ACTIVE` contract owned by its sending club, no player riding on a `CONTRACT` asset has a `medical_status` of `FAILED_PHYSICAL`, the cap compatibility test holds for both clubs, and each receiving club's `active_roster_count` after the transfer remains at or below its `active_roster_limit`. A `MEDICAL_REVIEW` trade must satisfy all of those and two more: the logical clock must be at or before `medical_review_deadline_at`, or the answer is `ERR_MEDICAL_WINDOW_EXPIRED`; and every physical exam tied to this trade must be `PASSED` with an `expires_at` strictly later than the logical clock, any exam still `SCHEDULED`, or `FAILED`, or `EXPIRED` drawing `ERR_PHYSICAL_NOT_PASSED`. That last test is read after the window test and is satisfied vacuously by a contingent trade against which no exam was ever booked, which therefore executes.

Execution moves the trade to `EXECUTED`, stamps `executed_at`, and stores both `cap_delta_initiating_cents` and `cap_delta_counterparty_cents`. Every `PROPOSED` asset moves `PROPOSED → TRANSFERRED`. For each `CONTRACT` asset the underlying contract's `team_id` and the player's `current_team_id` move to the receiving club, the player's `roster_designation` becomes `ACTIVE`, and their outgoing designation bucket accrues its elapsed days before `designation_effective_at` is reset to the logical clock. Both clubs' four designation headcounts and both cap variants are then recomputed and both clubs' postures re-evaluated in event mode, and the trade's `version` is incremented. When the trade came from `MEDICAL_REVIEW`, both clubs' `open_medical_review_count` is additionally decremented by 1.

A trade dies in exactly three ways, each with its own `void_reason`. `ROUND_LIMIT_EXCEEDED` covers the exhausted-negotiation case above. `FAILED_PHYSICAL` covers a trade in `MEDICAL_REVIEW` whose trade physical is recorded as failed, as §3.5 sets out. And `MEDICAL_WINDOW_EXPIRED` covers a trade still in `MEDICAL_REVIEW` when the daily sweep finds the logical clock past `medical_review_deadline_at`. All three void paths move every `PROPOSED` asset to `RETURNED`, and the two medical-review paths additionally decrement both clubs' `open_medical_review_count` by 1. A returned asset changes no contract and no player — it never moved.

### 3.8. Tenders, Qualifying Offers and Restricted Free Agency

When a player's rights are restricted rather than unrestricted, the club that holds them keeps them by issuing a **tender**. A cap analyst issues one for their own club, naming the `player_id`, their own club as `team_id`, an `offer_type` of `QUALIFYING_OFFER`, `RESTRICTED_TENDER` or `ARBITRATION_TENDER`, a `tender_level` of `FIRST_ROUND`, `SECOND_ROUND`, `ORIGINAL_ROUND` or `RIGHT_OF_FIRST_REFUSAL`, and the player's `prior_base_salary_cents` — the base salary from the season just completed, which may not be negative and which serves as the raise base.

Eligibility is narrow, and its tests are read in the precedence order of §2.8, which is worth spelling out because several of them can fail at once. The player must currently be `UNROSTERED`, or the answer is `ERR_INVALID_TENDER_STATE`. Then the club must not be `NON_COMPLIANT` or `TRANSACTION_FROZEN`. Then the player's `medical_status` must not be `FAILED_PHYSICAL`. Then the same club-and-player pair may not already hold an `ISSUED` tender, which would be `ERR_TENDER_ALREADY_ISSUED`. Only then is the player's `contract_rights_class` required to be `RESTRICTED` or `ARBITRATION_ELIGIBLE`, with an `ARBITRATION_TENDER` specifically requiring `ARBITRATION_ELIGIBLE` and any other rights class refused as `ERR_RESTRICTED_RIGHTS_REQUIRED`. Issuing a tender is finally subject to the provisional cap ceiling and can be refused with `ERR_CAP_LIMIT_EXCEEDED` — a ceiling read as the club's commitment already stands, since the tender itself adds nothing to it, so only a club that is *already* over its limit is turned away.

The tender's `amount_cents` is derived, never supplied, and it is built in two steps. First a **floor** is established as the largest of three figures: the player's `prior_base_salary_cents`; the minimum for the chosen `tender_level`, which is 60,000,000 cents for `FIRST_ROUND`, 45,000,000 cents for `SECOND_ROUND`, 30,000,000 cents for `ORIGINAL_ROUND` and 25,000,000 cents for `RIGHT_OF_FIRST_REFUSAL`; and the league minimum for the player's service years, which is 12,000,000 cents at zero service years, 15,000,000 at one, 18,000,000 at two, 21,000,000 at three, and 24,000,000 at four or more — a player with more than four service years is treated as having four for this lookup. Second, the `offer_type` selects a multiplier applied to that floor: a `RESTRICTED_TENDER` multiplies the floor by 1.10, an `ARBITRATION_TENDER` multiplies it by 1.20, and a plain `QUALIFYING_OFFER` applies no multiplier at all. The result is rounded half up to whole cents, and the final `amount_cents` is the lesser of that rounded figure and the league's tender ceiling of 150,000,000 cents. Three worked cases: a prior base of 50,000,000 cents at `FIRST_ROUND` for a player with two service years, issued as a `RESTRICTED_TENDER`, has a floor of 60,000,000 cents and an amount of 66,000,000 cents; the same prior base at `ORIGINAL_ROUND` for a player with three service years, issued as an `ARBITRATION_TENDER`, has a floor of 50,000,000 cents and an amount of 60,000,000 cents; and the same inputs issued as a plain `QUALIFYING_OFFER` have a floor of 50,000,000 cents and an amount of 50,000,000 cents.

Issuance stamps `issued_at` with the logical clock, leaves the tender `ISSUED`, and computes `deadline_at` as `issued_at` plus 72 hours, snapped into the daily processing window per §2.5.

**Responding.** Only the player's own agent may answer, supplying a `response` of either `ACCEPT` or `DECLINE`, and only while the logical clock is at or before `deadline_at` — a response strictly later is refused with `ERR_TENDER_DEADLINE_PASSED`. An accept additionally requires the tendering club not to be `NON_COMPLIANT` or `TRANSACTION_FROZEN`. Answering a tender that is not `ISSUED` is `ERR_INVALID_TENDER_STATE`. Either answer stamps `responded_at` with the logical clock.

A decline moves the tender `ISSUED → DECLINED` and changes nothing else — no filing is created. An accept moves the tender `ISSUED → ACCEPTED` and cascades in three further steps. Because the tender was accepted, a filing of type `SIGNING` is created for that club and player in `DRAFT` status, and `resulting_transaction_id` is set to point at it. Because that filing exists, a contract is created in `PENDING_APPROVAL` for one year, with `base_salary_cents` equal to the tender's `amount_cents` and `signing_bonus_cents` of 0, linked to the filing. And because a `PENDING_APPROVAL` contract now exists, the tendering club's `provisional_cap_committed_cents` and `cap_space_cents` are recomputed and its `version` incremented. Note that the accept produces a *draft* filing, not an approved one — the club still has to submit it and the league still has to approve it, on the ordinary filing cycle of §3.3. That filing is built exactly as §3.3 would build a `SIGNING`: `requires_physical` is true, `filing_deadline_at` is the logical clock plus 48 hours snapped into the processing window, `target_designation` and `injury_designation_id` are null, and `revision_count` starts at 0. The contract it points at takes `start_season_year` 2026, `base_guaranteed` false, `is_practice_squad_contract` false, an `option_type` of `NONE` with `option_status` `NOT_APPLICABLE`, and no performance bonuses. And unlike opening a `SIGNING` by hand, the accept is subject to **no** cap ceiling of its own: the resulting `PENDING_APPROVAL` contract may carry the club past `salary_cap_limit_cents`, in which case the club simply becomes a cap violator on the spot — the club's posture is re-evaluated in event mode with the rest of the cascade — and its own approval later fails on the ceiling of §3.3.

If no answer arrives, the daily sweep moves the tender `ISSUED → LAPSED` once the logical clock passes `deadline_at`, and a lapse creates no filing.

### 3.9. The Daily Compliance Sweep and the Posture Ladder

Compliance is the spine of this system. Every club carries a `compliance_status` posture, and that posture is what gates whether the club may transact at all: a club in `NON_COMPLIANT` or `TRANSACTION_FROZEN` has nine team-scoped operations closed to it, each answering `ERR_TEAM_TRANSACTIONS_FROZEN`, as §2.8 precedence 15 enumerates.

**What counts as a violation.** Evaluating a club produces an ordered list of `violation_codes`, appended in exactly this fixed order so that the first code is always deterministic:

1. `ACTIVE_ROSTER_OVER_LIMIT`, when `active_roster_count` is strictly greater than `active_roster_limit`.
2. `RESERVE_OVER_LIMIT`, when `reserve_roster_count` is strictly greater than `reserve_roster_limit`.
3. `IR_OVER_LIMIT`, when `injured_reserve_count` is strictly greater than `injured_reserve_limit`.
4. `PRACTICE_SQUAD_OVER_LIMIT`, when `practice_squad_count` is strictly greater than `practice_squad_limit`.
5. `CAP_OVER_LIMIT`, when `provisional_cap_committed_cents` is strictly greater than `salary_cap_limit_cents`.
6. `INELIGIBLE_PRACTICE_SQUAD_PLAYER`, when any player of this club whose `roster_designation` is `PRACTICE_SQUAD` has `practice_squad_eligible` false.
7. `UNFILED_INJURY_PAPERWORK`, when any injury designation of this club is still in `PENDING_PAPERWORK` and the logical clock has reached or passed that designation's `created_at` plus a 24-hour paperwork grace period.

An empty list means the club is compliant. A non-empty list means the club is in violation, and what happens next depends on the posture ladder and on which mode the evaluation ran in.

**The posture ladder.** From `COMPLIANT`, a non-empty violation list moves the club to `GRACE`, arming `grace_expires_at` at the evaluation instant plus a 24-hour grace period and setting `consecutive_noncompliant_checks` to 1. This edge is the one an event-mode evaluation can take — any approved filing, executed trade, processed waiver, earned bonus or limit adjustment that leaves a violation behind arms grace inline.

Every subsequent step belongs to the sweep. A sweep that finds violations while the club is in `GRACE` and the logical clock is still strictly before `grace_expires_at` leaves the club in `GRACE`, with `grace_expires_at` and `consecutive_noncompliant_checks` both unchanged. A sweep that finds violations while the club is in `GRACE` and the logical clock has reached or passed `grace_expires_at` moves the club `GRACE → NON_COMPLIANT` — the boundary instant already counts as expired — clears `grace_expires_at` to null, and sets `consecutive_noncompliant_checks` to 2; from this point every team-scoped write is refused. A sweep that finds violations while the club is `NON_COMPLIANT` moves it `NON_COMPLIANT → TRANSACTION_FROZEN` when the counter incremented by one reaches or exceeds the freeze threshold of 3, and it increments `consecutive_noncompliant_checks`. A sweep that finds violations while the club is already `TRANSACTION_FROZEN` leaves it frozen and increments the counter again.

There is exactly **one** way out, and it is the same edge from all three violation postures: a sweep that finds an empty violation list returns the club to `COMPLIANT`, clears `grace_expires_at` to null and resets `consecutive_noncompliant_checks` to 0. `GRACE → COMPLIANT`, `NON_COMPLIANT → COMPLIANT` and `TRANSACTION_FROZEN → COMPLIANT` all travel this single violation-free edge; there is no other unfreeze path.

**The sweep record.** A league officer runs a sweep for one club at a time, naming the `team_id`. The sweep writes an immutable audit row that captures what it saw: `team_id`, `checked_at` as the logical clock of the sweep, the four observed headcounts `active_roster_count`, `reserve_roster_count`, `injured_reserve_count` and `practice_squad_count`, the club's `final_cap_committed_cents`, a `cap_space_cents` figure, the ordered `violation_codes`, a `result` of `COMPLIANT`, `GRACE` or `NON_COMPLIANT`, the club's `grace_expires_at` as it stands once the sweep has applied — null unless the `result` was `GRACE`, and on a sweep that merely leaves an unexpired club in `GRACE` it is the expiry the *earlier* evaluation armed rather than a fresh one — and a `resulting_compliance_status` of `COMPLIANT`, `GRACE`, `NON_COMPLIANT` or `TRANSACTION_FROZEN` recording the posture the club holds after the sweep applied. One subtlety deserves emphasis: the sweep row's `cap_space_cents` is the club's `salary_cap_limit_cents` less its **final** committed total, because the audit view reports settled money — unlike the club record's own `cap_space_cents`, which is measured against the *provisional* total. Identical data therefore yields two different cap-space figures depending on which record you read. Sweep rows are immutable audit events and carry no `updated_at` and no `version`; a club's sweep history is returned newest first. Running a sweep increments the club's `version` by 1. Everything the row reports is read *after* the five clock-driven steps below have run, so a sweep always describes the club as those steps left it: a tender the same sweep lapsed, or a stale draft it voided, is already reflected in the headcounts, the cap figure and the violation list of the row it writes.

**The five clock-driven steps.** Beyond posture, a sweep is the only mechanism that lets time itself change state, and it performs five steps, each cascading into its own record's lifecycle. Those steps are **not** confined to the club the sweep names: each one runs across every club's records league-wide, in `created_at` order within each collection, and any other club they touch has its four headcounts, both cap totals, dead money and cap space recomputed in place. What such a club does *not* get is a posture re-evaluation, an audit row or a `version` bump — only the named club is walked up the ladder, and only the named club's `version` moves. Step one voids every `DRAFT` filing whose `filing_deadline_at` the logical clock has passed, voiding a `SIGNING` filing's `PENDING_APPROVAL` contract along with it and recomputing the club's provisional commitment. Step two lapses time-expired decisions: every `ISSUED` tender whose `deadline_at` has passed moves to `LAPSED`, and every `PENDING` contract option whose `option_deadline_at` has passed moves to `LAPSED`. Where that contract is still `ACTIVE`, the lapse terminates it with `termination_reason` `OPTION_LAPSED` and applies the dead-money and roster consequences of §3.4, sending the player to `UNROSTERED` with a null `current_team_id`; where the contract has already been terminated by another route, the option is marked `LAPSED` and nothing else moves — the earlier `termination_reason` stands and the player's designation is left alone. Within this step every tender is lapsed before any option is. Step three voids every `MEDICAL_REVIEW` trade whose `medical_review_deadline_at` has passed, with `void_reason` `MEDICAL_WINDOW_EXPIRED`, returning its assets and releasing both clubs' medical-review slots. Step four opens or expires injury return windows: an `ACTIVE` designation whose `return_window_opens_at` the clock has reached, and whose `return_window_closes_at` it has not yet passed, moves to `RETURN_WINDOW_OPEN`, while any designation in `ACTIVE` or `RETURN_WINDOW_OPEN` whose `return_window_closes_at` the clock has passed moves to `EXPIRED`. Step five expires every `PASSED` physical whose `expires_at` the clock has passed, moving it to `EXPIRED` so that no approval can cite it again.

Event-mode evaluation performs **none** of those five steps and never freezes a club — it evaluates violations, may arm grace, and stops there. That asymmetry is the reason a club can hold a stale `DRAFT` filing, an unanswered tender or an over-run medical review indefinitely until somebody runs a sweep.

## 4. API Endpoint Definitions

Every endpoint below is rooted at the service origin — there is no version prefix and no resource namespace above the collection name. A request that successfully creates a new record returns HTTP 201 with the created record in `data`; a request that modifies, transitions or recomputes an existing record returns HTTP 200 with the updated record in `data`; a read returns HTTP 200. Sub-resource creation endpoints — adding a claim to a wire, adding an asset to a trade, running a compliance sweep — return 201 with the newly created child record, while action endpoints that transition an existing record — filing, deciding, revising, withdrawing, processing, countering, accepting, executing, responding, filing paperwork, recording a result, earning a bonus, deciding an option — return 200 with the transitioned parent record. The logical-clock endpoint returns 200. All list endpoints honour the pagination and filtering contract of §2.3. All endpoints require the `X-User-ID` and `X-User-Role` headers of §2.1.
