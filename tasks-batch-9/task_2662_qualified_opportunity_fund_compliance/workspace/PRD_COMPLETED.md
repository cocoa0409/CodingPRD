# Qualified Opportunity Fund Compliance API — Product Requirements Document

## 1. Introduction

A Qualified Opportunity Fund (QOF) manager lives inside a set of statutory clocks that never stop. A taxpayer who realizes a capital gain has a fixed window to move those dollars into a fund; the fund must self-certify before it can accept them; twice a year it must prove that at least ninety percent of its holdings are qualified property; each operating business it invests in must clear a three-prong test on gross income, intangibles and nonqualified financial property; every building it buys used must be substantially improved inside thirty months; and every dollar of working capital it wants sheltered from nonqualified treatment must sit behind a written plan with a month-by-month spend schedule. Miss one measurement date and the consequences are not a warning email — they are penalty months, cure filings, and, on a second consecutive failure, decertification that pulls every investor's deferred gain into income at once.

This document specifies the API for the compliance system that tracks all of it. The system is a system of record and a calculator in equal measure: it holds investor gains, fund self-certifications, asset inventories, semiannual test measurements, improvement projects, working-capital plans, penalty assessments, basis step-up elections and inclusion events, and it derives — inside the same request that changes the underlying data — every ratio, shortfall, penalty figure and rollup that a compliance officer would otherwise recompute by hand in a spreadsheet. There are no background jobs and no eventual consistency: if a working-capital plan blows its pacing, the operating business's nonqualified financial property figure, the business's qualification posture, the fund's qualified-asset aggregates and the affected asset test are all corrected before the response is written.

Two design commitments shape everything that follows. First, **measurement and certification are separated**: the operator who runs a measurement may never be the operator who certifies it, and a fund manager may never certify at all. Second, **money and months are conserved**: the dollars on an eligible gain always split exactly into elected and unelected halves, and a fund's cumulative noncompliance-month count always equals the sum of the months carried by its live penalty assessments. Every compensating action in the API — revoking an election, approving a cure — exists to restore one of those two identities exactly, to the cent or to the whole month, with no tolerance.

All endpoints are mounted under the `/qof` prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, declaring the capacity in which the caller acts. If either header is absent or blank, the request is rejected with `ERR_MISSING_AUTH_HEADER` (HTTP 401). If `X-User-Role` carries any value other than the four recognized roles — `FundManager`, `ComplianceOfficer`, `Investor`, and `PlatformAdmin` — the request is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401). A syntactically valid role that is simply not authorized for the endpoint being called is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The authorized roles for each endpoint are listed in §4.

The four roles differ in how `X-User-ID` is interpreted, and that difference is the whole of the ownership model:

- When `X-User-Role` is `Investor`, `X-User-ID` is the `id` of the acting Investor resource. Ownership checks on any resource that references an investor compare the resource's investor reference to `X-User-ID`: an eligible gain's `investor_id`, a deferral election's `investor_id`, and the investor identifier in the path of the single-investor read and statement endpoints. A mismatch is rejected with `ERR_INVESTOR_SCOPE_VIOLATION` (HTTP 403). An `Investor` caller may register gains, make and revoke elections, record inclusion events, and file step-up elections, but only against its own gains and elections.
- When `X-User-Role` is `FundManager`, `X-User-ID` is an opaque operator handle and is **not** the `id` of any persisted entity. It is compared against the `manager_user_id` recorded on the fund that owns the target resource; a mismatch is rejected with `ERR_FUND_MANAGER_MISMATCH` (HTTP 403). The server also records the handle on resources the manager creates through action endpoints — for example as `requested_by_user_id` on a penalty assessment and as `measured_by_user_id` on a test the manager measured — but it never compares it to any entity's `id`. A `FundManager` may measure a test and may never certify one.
- When `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is likewise an opaque operator handle tied to no persisted entity. The server records it as `measured_by_user_id` when the officer runs a measurement, as `certified_by_user_id` when the officer certifies a test, and as `decided_by_user_id` when the officer decides a cure request; it is never compared to any entity's `id`. The `ComplianceOfficer` role holds the certification, decertification and cure-decision authority.
- When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator handle tied to no persisted entity. The platform administrator owns investor onboarding, the attestation switch, the logical clock and the batch sweep, and may stand in for an investor or a manager on creation endpoints. It is recorded where a transition writes an operator handle, but never compared to any entity's `id`, and it confers no certification or cure-decision authority.

Ownership and role checks are not interchangeable, and they run in a fixed order relative to each other and to every other check in the system; §2.11 gives the complete precedence ladder.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly 20 characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is stamped from the host clock at the moment the response is written, not from the logical clock of §2.4, so it is unaffected by any clock the platform administrator sets.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. Every field a resource declares is always present on every representation of that resource: a field described anywhere in this document as "empty" is emitted as JSON `null` rather than omitted, and that includes a foreign key that this particular row does not use — a capital expenditure filed against an improvement project reports `wcsh_plan_id` as `null`, and one filed against a working-capital plan reports `improvement_project_id` as `null`. The only fields ever absent from a representation are `updated_at` and `version` on a capital expenditure (§2.5).
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and only for list endpoints: the `meta` object of a single-resource response carries `api_request_id` and `api_request_timestamp` alone.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two query parameters. `limit` sets the maximum number of resources returned; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` sets how many resources are skipped before the page begins; it defaults to 0 and may not be negative. A `limit` outside 1 through 100, a non-integer `limit` or `offset`, or a negative `offset` is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

Unless a specific endpoint says otherwise, list results are ordered by the resource's creation timestamp, ascending. This applies equally to the paginated collection endpoints and to the reverse-lookup endpoints that walk a foreign key (a fund's asset tests, a business's tests, an election's inclusion events and step-up elections, a project's expenditures, a plan's expenditures, an investor's gains and elections).

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope. `total_count` counts every resource matching the request's filters, not just the ones on the returned page. `has_more` is true exactly when the returned window stops short of the end of the filtered set — that is, when `offset` plus the number of resources actually returned is strictly less than `total_count` — so it is false on the final page and false for any `offset` at or beyond `total_count`, where the page comes back as an empty `data` array rather than an error. `limit` and `offset` are echoed back as the effective values the server used, including the defaults it supplied.

Collection endpoints additionally accept domain filters, and a filter narrows the result set without changing the ordering or the meaning of `total_count`. The fund list filters on `certification_status`, `compliance_posture` and `manager_user_id`; the investor list filters on `compliance_attestation_status`; the eligible-gain list filters on `investor_id`, `status` and `deadline_basis`; the deferral-election list filters on `fund_id`, `investor_id`, `eligible_gain_id` and `status`; the fund-asset list filters on `fund_id`, `qoz_business_id`, `status` and `qualification`; the operating-business list filters on `fund_id` and `qualification_status`; the improvement-project list filters on `fund_asset_id`, `status`, `group_key` and `aggregation_method`; the working-capital-plan list filters on `qoz_business_id` and `status`; the penalty-assessment list filters on `fund_id`, `asset_test_id` and `status`; the expenditure lists filter on `expenditure_kind`; the inclusion-event list filters on `event_type`; and the reverse-lookup lists for tests, gains, elections and step-up elections filter on `status`. Every filter is a case-sensitive exact-equality match against the stored value rendered as a string, and a resource whose filtered field is empty never matches any supplied filter value. A filter is applied only when the query parameter is actually present; a query parameter the endpoint does not declare is ignored rather than rejected, so an unrecognized or misspelled filter name narrows nothing and produces no error.

### 2.4. The Logical Clock

No *domain* instant in this system reads the host machine's wall clock; the only two things that do are the envelope's `api_request_timestamp` and the row-bookkeeping stamps `created_at` and `updated_at` of §2.5, which are host-clock stamps at millisecond resolution, forced to be strictly increasing across the life of the process so that creation order and insertion order can never disagree — which is what makes the default "creation timestamp ascending" ordering of §2.3 total. Everything else comes from the clock below. The server keeps a **logical clock**, and every instant the system computes for itself is stamped from it: a deferral election's `investment_date`, a capital expenditure's `spend_date`, an inclusion event's `event_date`, a step-up election's `election_date`, a fund asset's `disposed_at`, an eligible gain's `expired_at`, an improvement project's `evaluated_at`, a fund's `self_certification_date`, and the sweep's `swept_at`. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`. A `PlatformAdmin` moves it by supplying a `current_utc` instant; the response reports both the new `current_utc` and the `previous_utc` it replaced, and no entity is mutated by the move — subsequent writes simply stamp their computed instants from the new value. Any caller may read the clock, which returns the current `current_utc`.

Instants supplied by clients — `realization_date`, `pass_through_year_end`, `acquisition_date`, `measurement_date`, `period_start`, `period_end`, `testing_date`, `window_start`, `first_taxable_month_iso8601` — are ISO 8601 UTC timestamps and are compared at millisecond resolution. Parsing is forgiving in three specific ways and strict everywhere else: a trailing `Z` and an explicit `+HH:MM` offset are both accepted and normalized to UTC, a timestamp carrying no zone designator at all is read as already being UTC, and a bare calendar date `YYYY-MM-DD` is accepted as the first instant of that day. Any other shape — a non-string, a blank string, or text that parses as neither of those two forms — is a schema violation and yields `ERR_INVALID_REQUEST` (400) under §2.11 rule 4. Day arithmetic (the 180-day window, the holding-period tiers) counts whole elapsed days: the number of complete 24-hour days between two instants, with any partial day discarded. Month arithmetic (the 30-month improvement window of §3.6, the 31-month safe-harbor window of §3.7) advances an instant by whole calendar months, carrying the time of day and the day-of-month across unchanged but clamping the day **down** to the last day of the target month whenever the target month is the shorter one: a `window_start` of 2026-07-31T00:00:00.000Z advanced by 31 months lands on 2029-02-28T00:00:00.000Z, not on any instant in March.

### 2.5. Common Resource Properties

Investors, funds, eligible gains, deferral elections, fund assets, operating businesses, business tests, asset tests, improvement projects, working-capital plans, penalty assessments, inclusion events and step-up elections all carry the same four system-managed properties:

- `id` — a server-minted UUID string with no type prefix.
- `created_at` — an ISO 8601 UTC timestamp with three fractional digits, recording when the row was first written.
- `updated_at` — an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the resource, including mutations caused by a cascade rather than by a direct client call on that resource.
- `version` — an integer that starts at 1 on creation and increases by exactly 1 on every mutation of the resource, cascaded mutations included. The unit of mutation is the **request**, not the individual write: however many times one request touches the same row — directly, and then again through one or several cascade links — that row's `version` rises by exactly 1 and its `updated_at` is stamped exactly once for the whole request. A row created by a request is likewise returned at `version` 1 even when a cascade inside that same request recomputes one of its derived fields.

Capital expenditures are the one exception. A `CapitalExpenditure` row is immutable once written and therefore carries only `id` and `created_at`: it has **no** `updated_at` and **no** `version` field. When a later expenditure or a checkpoint re-runs the allocation waterfall and rewrites an earlier expenditure's `schedule_month_index`, that rewrite does not create an `updated_at` or a `version` on the row.

Recomputation counts as mutation. When a deferral election is created, the fund's committed-capital total changes, so the fund's `updated_at` and `version` both move even though the client never addressed the fund directly. The same is true of an investor's three rollups, an eligible gain's elected/unelected split, an operating business's netted nonqualified figure, and a fund's four asset aggregates.

### 2.6. Path Resolution and Referential Integrity

Path identifiers are resolved strictly left to right, and the first identifier that does not resolve determines the error. The error is the one belonging to the entity that owns the path segment: `ERR_FUND_NOT_FOUND`, `ERR_INVESTOR_NOT_FOUND`, `ERR_ELIGIBLE_GAIN_NOT_FOUND`, `ERR_DEFERRAL_ELECTION_NOT_FOUND`, `ERR_FUND_ASSET_NOT_FOUND`, `ERR_QOZ_BUSINESS_NOT_FOUND`, `ERR_BUSINESS_TEST_NOT_FOUND`, `ERR_ASSET_TEST_NOT_FOUND`, `ERR_IMPROVEMENT_PROJECT_NOT_FOUND`, `ERR_WCSH_PLAN_NOT_FOUND` or `ERR_PENALTY_ASSESSMENT_NOT_FOUND` — each HTTP 404. Path resolution happens before any state, ownership or business check on the resource, so a call against a nonexistent fund reports the missing fund rather than a permission or state problem.

Routing itself sits above all of that. A trailing slash is insignificant: `/qof/funds/` and `/qof/funds` address the same endpoint. A request whose path matches no declared route at all is rejected with `ERR_INVALID_REQUEST` at HTTP 404, and a request whose path matches a declared route under a method that route does not declare is rejected with `ERR_INVALID_REQUEST` at HTTP 405. Both carry the ordinary error envelope of §2.2, and neither is reported as one of the entity not-found errors above, because no path identifier was ever reached.

Foreign keys arriving in a request **body** are a separate check with a single error. When `investor_id`, `eligible_gain_id`, `fund_id`, `qoz_business_id`, `fund_asset_id`, or any element of a supplied disposition sequence fails to resolve to an existing row, the response is `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404).

Resources in this domain are addressed as peers: a business test, an asset test, an improvement project, a working-capital plan, an inclusion event, a step-up election and a capital expenditure are all discovered through the parent path that created them, but each one is identified by its own foreign key on the row rather than by a nested identity path. The creation and reverse-lookup sub-paths exist as channels only.

### 2.7. Money, Percentages and Rounding Discipline

Two numeric families run through this domain and they round differently.

**Money** — every dollar field, whether supplied by a client or derived by the server — is carried to exactly 2 decimal places and rounded half up. This covers `eligible_amount`, `elected_amount`, `unelected_amount`, `included_amount`, `deferred_remaining`, `unadjusted_cost_basis`, `afs_fair_value`, `adjusted_basis`, `proceeds_amount`, `basis_at_acquisition`, `qualified_additions_total`, `covered_amount`, `spent_total`, `unspent_amount`, `pacing_shortfall`, `overspill_amount`, `declared_nqfp_amount`, `total_asset_value`, `total_tangible_property_basis`, `total_asset_value_measured`, `wcsh_protected_amount`, `blown_unspent_amount`, `nqfp_amount`, `nqfp_amount_measured`, `qualified_numerator`, `total_denominator`, `shortfall_amount`, `monthly_penalty_amount`, `gross_penalty_amount`, `cure_credit_amount`, `net_penalty_amount`, `gross_inclusion_amount`, `basis_offset_amount`, `net_inclusion_amount`, `claimed_fmv`, `stepped_up_basis`, `initial_basis`, `current_basis`, `amount`, and every `planned_amount` inside a spend schedule. Money is represented in JSON as a number, never as a string; a client that sends a money field as a string, as a boolean, or as a non-finite number is rejected with `ERR_INVALID_REQUEST` (400).

A client-supplied money figure carrying more than two decimal places is **not** rejected. It is quantized to two places, half up, at the moment it is read out of the request body, and every subsequent check — the declared bound, the conservation identity, the comparison against another amount — is applied to the quantized value and never to what the client literally sent. This is observable at the bounds: an `eligible_amount` of `0.004` quantizes to `0.00` and therefore fails the "strictly greater than 0.00" bound with `ERR_INVALID_REQUEST`, while `0.005` quantizes to `0.01` and is accepted as one cent. Client-supplied percentages and fractions are quantized the same way to four places before their bounds are checked.

**Percentages and fractions** are carried to exactly 4 decimal places and rounded half up: `ratio_pct`, `improvement_ratio_pct`, `gross_income_pct`, `intangibles_pct`, `nqfp_pct`, `hours_zone_pct`, `amounts_paid_zone_pct`, `included_fraction`, `included_fraction_total`, and `step_up_applied_pct`. Like money, these are JSON numbers and never strings, and the scale each one is expressed on — out of 100 for the ratio and prong percentages, out of 1 for `included_fraction`, `included_fraction_total` and `step_up_applied_pct` — is fixed by the workflow that defines it in §3.

Where a threshold is compared against a percentage, the comparison uses the **rounded** 4-decimal value, not an unrounded intermediate. A ratio that computes to 89.99996 rounds to 90.0000 and therefore passes the ninety-percent test.

Where a formula rounds more than once, the order of rounding is part of the contract and is spelled out at the point of use. The penalty calculation in §3.8 is the sharpest case: the per-month figure is rounded to the cent **before** it is multiplied out over the failed months, and summing unrounded monthly figures and rounding once at the end is explicitly the wrong answer.

Whole-number quantities — `failed_month_count`, `cumulative_penalty_months`, `consecutive_failed_tests`, `consecutive_failed_business_tests`, `included_asset_count`, `cure_attempt_count`, `days_from_basis`, `holding_days`, `holding_period_days`, `schedule_month_count`, `schedule_month_index`, `last_checkpoint_month_index`, `disposition_sequence_index`, `tax_year_end_month` and `month_index` — are exact integers and are never rounded.

### 2.8. Optimistic Concurrency on Shared Aggregates

Two write operations in this system change a parent's ledger without changing any state that a precondition could guard, and both of them therefore require the client to prove it was looking at a current parent when it decided to write.

Creating a deferral election requires `expected_fund_version` in the request body. The field is **not** optional. It must carry the `version` the client last observed on the fund named by `fund_id`. Two elections against the same `SELF_CERTIFIED` fund are both perfectly legal — any number of investors may invest — so no state check can catch a client whose picture of the fund's `deferred_gain_committed` predates someone else's election. The fund's `version` is the only observable that reveals it. If `expected_fund_version` does not equal the fund's current `version`, the create is rejected with `ERR_STALE_FUND_VERSION` (HTTP 412), and no election is written.

Recording a capital expenditure against a substantial-improvement project requires `expected_project_version`, again as a mandatory body field, carrying the `version` the client last observed on that project. A second expenditure against an `OPEN` project is always legitimate, so nothing but the version reveals a writer whose view of `qualified_additions_total` and `improvement_ratio_pct` predates another expenditure. A mismatch with the project's current `version` is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412), and no expenditure is written.

No other endpoint in this API accepts a version field. Plan expenditures, checkpoints, measurements, certifications, disposals, revocations, inclusion events, step-up filings and cure actions take no expected-version input, and supplying one is an unknown field.

### 2.9. Conserved Quantities

Two quantities in this system are conserved by construction, and every compensating action exists to restore one of them exactly.

**Gain dollars on one eligible gain.** At all times, `eligible_amount` equals `unelected_amount` plus the sum of `elected_amount` over every deferral election on that gain whose `status` is anything other than `REVOKED`, with the sum taken to 2 decimal places. Creating an election is the forward action: it reduces `unelected_amount` and raises the gain's own `elected_amount` rollup by exactly the elected figure. Revoking an election is the compensating action: it raises `unelected_amount` and lowers the gain's `elected_amount` rollup by exactly the same figure. After a create-then-revoke pair the gain's `unelected_amount` is identical to its value before the create, and the gain's `status` has cycled back to the value it held before.

**Noncompliance months on one fund.** At all times, `cumulative_penalty_months` on a fund equals the sum of `failed_month_count` over every penalty assessment of that fund whose `status` is `ASSESSED`, `CURE_REQUESTED` or `UPHELD`. Certifying a failed asset test is the forward action: it creates an assessment in `ASSESSED` and raises the fund's month count by that assessment's `failed_month_count`. Approving a cure is the compensating action: the assessment moves to `CURED` and the fund's month count falls by exactly that same `failed_month_count`. A **denied** cure is not a compensating action — the assessment cycles back to `ASSESSED` or terminates at `UPHELD`, and the month count does not move, because a denied or upheld penalty still counts.

### 2.10. Segregation of Duties

Measurement and certification are two-person operations. On either certification call — the asset test's or the business test's — the caller's `X-User-ID` must differ from the `measured_by_user_id` recorded on the target test when it was measured. If they are equal, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), even when the caller holds the `ComplianceOfficer` role. This is why both roles that may measure (`FundManager` and `ComplianceOfficer`) are recorded on the test, and why only `ComplianceOfficer` may certify: a fund manager who measures cannot later certify their own work, and a fund manager who did not measure still cannot certify, because the certification endpoints do not admit that role at all.

### 2.11. Order of Evaluation

Requests are validated in a fixed order, and the **first** check that fails determines the response. The ordering matters because several checks can fail at once on the same request and only one error is returned. From highest precedence to lowest:

1. Auth headers present and non-blank — `ERR_MISSING_AUTH_HEADER` (401).
2. `X-User-Role` is one of the four recognized roles — `ERR_UNKNOWN_ROLE` (401).
3. The caller's role is authorized for the endpoint — `ERR_ROLE_NOT_PERMITTED` (403).
4. Request-body and query schema on every write endpoint: all required fields present, no unknown fields, correct types, legal enum members, and each number inside its declared bounds — `ERR_INVALID_REQUEST` (400). The bounded cases include `eligible_amount` strictly greater than 0.00, `included_fraction` strictly greater than 0.0000 and at most 1.0000, `zone_tract_code` exactly 11 characters, a spend schedule each of whose `month_index` values is an integer from 1 through 31 with no duplicates — the agreement between the indices actually present and `schedule_month_count` is **not** checked here and instead feeds `documentation_complete` (§3.7) — and `first_taxable_month_iso8601` falling exactly on a month boundary (day 1 at `00:00:00.000Z`). The shape of the body itself is part of this rule: an absent body, an all-whitespace body, and a literal `null` body are all read as the empty JSON object `{}`, which satisfies any endpoint that declares no required field and fails the required-field check on any endpoint that does; a body that is syntactically invalid JSON, or that is valid JSON but not an object — an array, a bare number, a bare string, a bare boolean — is `ERR_INVALID_REQUEST` (400). The body is parsed as JSON regardless of the `Content-Type` the client declares, so a well-formed JSON object sent without `application/json` is accepted on its contents alone. An optional field the client omits is simply not applied, and takes whatever default the workflow in §3 declares for it; an optional field the client sends is validated exactly as a required one would be.
5. Pagination bounds on any endpoint that accepts `limit` and `offset` — `ERR_INVALID_PAGINATION` (400).
6. Path identifiers resolve, left to right — the owning entity's not-found error (404).
7. Foreign keys in the request body resolve — `ERR_REFERENCED_ENTITY_NOT_FOUND` (404). This guards gain intake, election create, asset record, business registration, plan filing, project creation, and step-up filing.
8. Investor ownership scope — `ERR_INVESTOR_SCOPE_VIOLATION` (403). This guards gain intake, the single-gain read, election create, election revoke, inclusion-event recording, step-up filing, the single-investor read and the investor statement read.
9. Fund-manager ownership — `ERR_FUND_MANAGER_MISMATCH` (403). This guards self-certification, asset record, asset disposal, asset-test creation, business registration, project creation, project expenditure, plan filing, plan activation, plan expenditure and cure request.
10. Segregation of duties on a certification — `ERR_SEGREGATION_OF_DUTIES` (403), on both the asset-test and business-test certifications.
11. Fund certification gate: the owning fund's `certification_status` must be `SELF_CERTIFIED` — `ERR_FUND_NOT_CERTIFIED` (409). This guards election create, asset-test measurement, business registration and asset record.
12. Fund decertification lockout: the owning fund's `certification_status` must not be `DECERTIFIED` — `ERR_FUND_DECERTIFIED` (409). This guards election create, self-certification, decertification, asset-test creation and asset record. On the two endpoints that carry both this rule and rule 11 — election create and asset record — the lockout is the check written first, so a `DECERTIFIED` fund, which fails both conditions at once, always reports `ERR_FUND_DECERTIFIED` and never `ERR_FUND_NOT_CERTIFIED`; the numbering of the two rules does not reorder them.
13. The target is in a non-terminal state from which the requested transition is declared — `ERR_INVALID_STATE_TRANSITION` (409). This covers requests such as measuring an already-`MEASURED` test, running a checkpoint on a `DRAFT` plan, or deciding a cure on an assessment still in `ASSESSED`. It deliberately never fires when the target is already terminal; that case belongs to the next rule even though this one is evaluated first.
14. The target is already in a terminal state for its machine — `ERR_ALREADY_TERMINAL` (409): an `INCLUDED_FULL` or `REVOKED` election, a `PASSED` or `FAILED` business test, a `CERTIFIED_PASS` or `CERTIFIED_FAIL` asset test, a `SATISFIED` or `LAPSED` project, a `COMPLETED` or `BLOWN` plan, a `CURED` or `UPHELD` assessment, and a `DISPOSED` asset. Two terminal states of this system never reach this rule. A `DECERTIFIED` fund is instead reported by rule 12 as `ERR_FUND_DECERTIFIED`, on every endpoint that names a fund. And an `EXPIRED` gain is never guarded at all, because no endpoint takes a gain as the target of a transition — see §3.11. One endpoint is carved out: filing a step-up election is exempt, because an investor is entitled to a written denial on file rather than a rejected request. A step-up filing against an `INCLUDED_FULL` election is accepted and recorded as a `DENIED` step-up election.
15. Optimistic concurrency: the supplied expected parent version equals the parent's current `version` — `ERR_STALE_FUND_VERSION` (412) on election create and `ERR_STALE_PROJECT_VERSION` (412) on project expenditure.
16. Investor attestation: `compliance_attestation_status` must be `ATTESTED` — `ERR_INVESTOR_NOT_ATTESTED` (422), on election create and step-up filing.
17. Gain character: `gain_character` must not be `ORDINARY`, and `deadline_basis` of `SECTION_1231_YEAR_END` is legal only on a gain whose `gain_character` is `SECTION_1231_NET` — `ERR_GAIN_NOT_ELIGIBLE` (422), on gain intake and election create.
18. Related-party bar — `ERR_RELATED_PARTY_ACQUISITION` (422), on asset record.
19. The 180-day window has not closed — `ERR_180_DAY_WINDOW_CLOSED` (422), on election create.
20. The 180-day window has opened — `ERR_180_DAY_WINDOW_NOT_OPEN` (422), on election create.
21. Asset-test period overlap — `ERR_TESTING_PERIOD_OVERLAP` (409), on asset-test creation.
22. Improvement-window overlap — `ERR_IMPROVEMENT_WINDOW_OVERLAP` (409), on project creation.
23. Expenditure inside the improvement window — `ERR_EXPENDITURE_OUTSIDE_WINDOW` (422), on project expenditure.
24. Safe-harbor window still open — `ERR_WCSH_WINDOW_CLOSED` (422), on plan expenditure and plan activation.
25. Plan documentation complete — `ERR_WCSH_PLAN_INCOMPLETE` (422), on plan activation.
26. Spend-schedule arithmetic — `ERR_WCSH_SCHEDULE_MISMATCH` (422), on plan filing.
27. Checkpoint index bounds — `ERR_CHECKPOINT_INDEX_INVALID` (422), on plan checkpoint.
28. Safe-harbor input completeness — `ERR_SAFE_HARBOR_INPUT_MISSING` (422), on business-test measurement.
29. Operating-business linkage on an asset — `ERR_QOZB_LINK_REQUIRED` (422), on asset record.
30. Aggregation grouping — `ERR_AGGREGATION_GROUP_INVALID` (422), on project creation.
31. The ten-year hold can be evaluated at all — `ERR_TEN_YEAR_HOLD_NOT_MET` (422), on step-up filing.
32. Disposition-sequence integrity — `ERR_DISPOSITION_SEQUENCE_INVALID` (422), on step-up filing.
33. The election is not revoked — `ERR_ELECTION_REVOKED` (409), on step-up filing.
34. Disposition ordering — `ERR_DISPOSITION_ORDER_VIOLATION` (409), on asset disposal.
35. Election amount ceiling — `ERR_ELECTED_AMOUNT_EXCEEDS_GAIN` (422), on election create.
36. Aggregate safe-harbor capacity — `ERR_WCSH_AGGREGATE_CAP_EXCEEDED` (422), on plan filing.
37. Inclusion-fraction ceiling — `ERR_INCLUSION_FRACTION_EXCEEDS_REMAINING` (422), on inclusion-event recording.
38. Cure attempts remaining — `ERR_CURE_ATTEMPTS_EXHAUSTED` (409), on cure request.
39. Cure basis approvable — `ERR_CURE_BASIS_NOT_APPROVABLE` (422), on cure decision.

The precise condition behind each of rules 7 through 39 is stated in §3 alongside the workflow it guards. Two consequences of this ladder are worth stating outright: a stale expected version is reported only after every state check has passed, so a client that is both stale and attempting an undeclared transition sees the state error; and a step-up filing against a revoked election is reported as `ERR_ELECTION_REVOKED` rather than as a terminal-state rejection, because the terminal-state rule is carved out for that endpoint.

### 2.12. Cascade and Recomputation Discipline

Every derived field in this system is recomputed inside the request that invalidated it and is observable in that request's response. There is no deferred reconciliation. When a change propagates, it propagates completely along the chain the change implies, and each resource touched along the chain has its `updated_at` refreshed and its `version` incremented.

Four chains recur throughout §3 and are worth naming once:

- **Asset qualification to fund aggregates.** Any change to a fund asset's `qualification` or `status` recomputes the fund's `aggregate_asset_basis`, `aggregate_qualified_basis`, `aggregate_afs_value` and `aggregate_qualified_afs_value`. The unqualified aggregates sum over assets whose `status` is `HELD` or `IMPROVING`; the qualified aggregates additionally require `qualification` to be `QUALIFIED`. A `DISPOSED` asset leaves all four.
- **Operating-business disqualification to the fund's live test.** Disqualifying an operating business flips every equity asset pointing at it to `NONQUALIFIED`, recomputes the fund's aggregates, re-measures the fund's latest `MEASURED` asset test in place, and can move the fund's `compliance_posture`.
- **Election changes to investor rollups.** Any change to a deferral election's dollars recomputes the owning investor's `deferred_gain_outstanding` and `included_gain_total`, and any change to a gain's dollars recomputes that investor's `eligible_gain_total`.
- **Working-capital plan changes to the nonqualified figure.** Activating, spending against, completing or blowing a plan recomputes the operating business's `wcsh_protected_amount`, `blown_unspent_amount` and `nqfp_amount`, in that order, and a blown plan carries the change onward into the business's prong verdicts.

A cascade never skips a link because the client did not ask for it, and a cascade that fires as part of a rejected request does not happen at all: a request that fails any check in §2.11 mutates nothing.

## 3. Business Logic & Workflows

### 3.1. Taxpayer Onboarding and the Intake of Eligible Gain

A `PlatformAdmin` registers each taxpayer that may participate. Registration takes the taxpayer's `legal_name` — between 1 and 200 characters and not blank — and its `taxpayer_type`, one of `INDIVIDUAL`, `PARTNERSHIP`, `C_CORPORATION` or `TRUST`, which determines later on which deadline bases are legal for that taxpayer's gains. Two further inputs are optional: `tax_year_end_month`, an integer from 1 through 12 naming the calendar month in which the taxpayer's tax year ends, which defaults to 12; and `compliance_attestation_status`, which defaults to `PENDING` and may be supplied as `PENDING`, `ATTESTED` or `BLOCKED`. A freshly registered investor carries `eligible_gain_total`, `deferred_gain_outstanding` and `included_gain_total` all at 0.00.

The attestation posture is the anti-abuse gate, and it is the platform administrator's to move. A separate administrative call sets `compliance_attestation_status` to any of the three values after KYC review, incrementing the investor's `version`. Only an `ATTESTED` investor may make a deferral election or file a step-up election; a `PENDING` or `BLOCKED` investor attempting either is rejected with `ERR_INVESTOR_NOT_ATTESTED`. Moving an investor to `BLOCKED` does not disturb elections already made — it only closes the door on new ones.

The three investor rollups are derived, never supplied. `eligible_gain_total` is the sum of `eligible_amount` across that investor's gains in any of the four gain states `ELIGIBLE`, `PARTIALLY_INVESTED`, `FULLY_INVESTED` and `EXPIRED`, taken to two decimal places. `deferred_gain_outstanding` is the sum of `deferred_remaining` across that investor's elections whose `status` is `DEFERRED`, `STEPPED_UP` or `INCLUDED_PARTIAL`. `included_gain_total` is the sum of `included_amount` across that investor's elections whose `status` is `INCLUDED_PARTIAL` or `INCLUDED_FULL`. All three are refreshed whenever an underlying gain or election changes.

Gain intake is where the statutory clock starts. An `Investor` (or a `PlatformAdmin` acting for one) submits a realized gain with the owning `investor_id`, the `gain_character`, the `eligible_amount` in dollars — strictly greater than 0.00 — the `realization_date` on which the underlying sale or exchange closed, and the `deadline_basis` that selects which 180-day window variant applies. `gain_character` is one of `SHORT_TERM_CAPITAL`, `LONG_TERM_CAPITAL`, `SECTION_1231_NET` or `ORDINARY`, and `deadline_basis` is one of `SALE_DATE`, `PARTNERSHIP_YEAR_END` or `SECTION_1231_YEAR_END`. A sixth input, `pass_through_year_end`, carries the pass-through entity's or Section 1231 tax-year-end instant; it is **required** whenever `deadline_basis` is anything other than `SALE_DATE`, and **forbidden** when `deadline_basis` is `SALE_DATE`. Ordinary income is never deferrable: a gain whose `gain_character` is `ORDINARY` is rejected with `ERR_GAIN_NOT_ELIGIBLE`, and so is a gain that asks for the `SECTION_1231_YEAR_END` basis without being `SECTION_1231_NET`. That same check is re-applied when an election is made against the gain.

Intake resolves the window in two steps. First, the `window_basis_date` is set: when `deadline_basis` is `SALE_DATE`, it is the `realization_date`; when `deadline_basis` is `PARTNERSHIP_YEAR_END` or `SECTION_1231_YEAR_END`, it is the `pass_through_year_end`. This is the only point at which the two variants diverge, and they diverge on identical realization data. Second, the `investment_deadline` is the `window_basis_date` advanced by exactly 180 calendar days. The gain is created with `status` `ELIGIBLE`, `elected_amount` at 0.00, `unelected_amount` equal to `eligible_amount`, and `expired_at` empty; the owning investor's `eligible_gain_total` is recomputed immediately.

Consider a gain realized on 2026-03-15T00:00:00.000Z. Under the sale-date variant its `investment_deadline` falls on 2026-09-11T00:00:00.000Z. Change nothing about the gain except electing the pass-through basis with a `pass_through_year_end` of 2026-12-31T00:00:00.000Z, and the deadline moves to 2027-06-29T00:00:00.000Z — 292 days later on identical gain data. Choosing the basis is therefore a substantive election, not a formality.

### 3.2. Fund Formation, Self-Certification, and Decertification

A fund is created — by a `FundManager` or a `PlatformAdmin` — from four inputs: the fund's `name` (1 to 200 characters, non-blank), its `entity_type`, either `CORPORATION` or `PARTNERSHIP`, for the federal self-certification filing; the `manager_user_id` that will own it, a non-blank handle of 1 to 64 characters that is compared against `X-User-ID` on later manager calls and is deliberately **not** a foreign key to any entity; and optionally `asset_test_valuation_method`, either `APPLICABLE_FINANCIAL_STATEMENT` or `UNADJUSTED_COST_BASIS`, defaulting to `UNADJUSTED_COST_BASIS`. A new fund has `certification_status` `DRAFT`, `compliance_posture` `UNTESTED`, all four of `aggregate_asset_basis`, `aggregate_qualified_basis`, `aggregate_afs_value` and `aggregate_qualified_afs_value` at 0.00, `deferred_gain_committed` at 0.00, `cumulative_penalty_months` at 0, `consecutive_failed_tests` at 0, and `first_taxable_month_iso8601`, `self_certification_date` and `last_test_measurement_date` all empty.

A fund carries **two independent state dimensions**, and this is the single most easily mis-modelled part of the domain. `certification_status` tracks the self-certification lifecycle across `DRAFT`, `SELF_CERTIFIED` and `DECERTIFIED`, with `DECERTIFIED` terminal. `compliance_posture` tracks the rolling ninety-percent asset-test posture across `UNTESTED`, `COMPLIANT`, `DEFICIENT`, `CURE_PENDING` and `FAILED_FINAL`, with `FAILED_FINAL` terminal. Neither value constrains the other, and they advance on entirely different triggers. There is exactly one coupling: moving `certification_status` to `DECERTIFIED` forces `compliance_posture` to `FAILED_FINAL` as an explicit side effect.

Self-certification is the manager's own act and is available only from `DRAFT`. The caller must be the `FundManager` whose `X-User-ID` equals the fund's `manager_user_id`, and must supply `first_taxable_month_iso8601` — the first month the fund elects to be treated as a QOF — as the first instant of a calendar month, meaning day 1 at `00:00:00.000Z` exactly. A value anywhere else inside a month is a schema violation and yields `ERR_INVALID_REQUEST`. On success the `DRAFT → SELF_CERTIFIED` transition stamps `self_certification_date` with the logical clock's current instant, records `first_taxable_month_iso8601` from the request, leaves `compliance_posture` exactly where it was — `UNTESTED` on a fresh fund — and increments the fund's `version` by 1. Self-certifying a fund that is already `SELF_CERTIFIED` is an undeclared transition from a non-terminal state and yields `ERR_INVALID_STATE_TRANSITION`; self-certifying a `DECERTIFIED` fund yields `ERR_FUND_DECERTIFIED`.

Decertification belongs to the `ComplianceOfficer` and accepts an optional `reason_note` of at most 500 characters for the file — a value the server validates and then discards, because no field of the fund records it and the fund the call returns therefore looks exactly as it would have without the note. It is declared from both `DRAFT` and `SELF_CERTIFIED`, so both `DRAFT → DECERTIFIED` and `SELF_CERTIFIED → DECERTIFIED` are legal, and in both cases it sets `certification_status` to `DECERTIFIED`, sets `compliance_posture` to `FAILED_FINAL`, and increments the fund's `version` by 1. Decertifying an already-`DECERTIFIED` fund is rejected with `ERR_FUND_DECERTIFIED`.

The difference between the two decertification paths is the cascade. Decertifying a `SELF_CERTIFIED` fund fires a three-link chain. First, every deferral election on that fund whose `status` is `DEFERRED`, `STEPPED_UP` or `INCLUDED_PARTIAL` receives a system-generated inclusion event with `event_type` `FUND_DECERTIFICATION` and an `included_fraction` equal to 1.0000 minus that election's current `included_fraction_total`, rounded half up to four decimal places — that is, exactly the fraction still outstanding. Second, because those inclusion events now exist, each affected election's `included_amount`, `included_fraction_total` and `deferred_remaining` are recomputed and its `status` becomes `INCLUDED_FULL`. Third, because those elections changed, every owning investor's `deferred_gain_outstanding` and `included_gain_total` are recomputed. Decertifying a `DRAFT` fund fires none of this, and not by omission: a `DRAFT` fund cannot hold a single deferral election, because election creation requires a `SELF_CERTIFIED` fund.

The `compliance_posture` dimension is never moved by a direct client call on the fund. Every one of its transitions is a system event driven from somewhere else: asset-test certifications move it to `COMPLIANT`, `DEFICIENT` or `FAILED_FINAL`; cure requests move it to `CURE_PENDING`; cure decisions move it back to `DEFICIENT` or forward to `COMPLIANT`; and the operating-business disqualification cascade can move it from `COMPLIANT` to `DEFICIENT` without any certification occurring at all. Each of those transitions is specified with the workflow that fires it, in §3.4, §3.5 and §3.8.

### 3.3. Deferral Elections and the Conserved Gain Ledger

An `Investor` (or a `PlatformAdmin` acting for one) invests gain dollars into a fund by creating a **deferral election**. Four inputs are required and none is optional: the `eligible_gain_id` whose dollars are being deferred, the `fund_id` of the receiving QOF, the `elected_amount` in dollars — strictly greater than 0.00 at two decimal places — and `expected_fund_version`, the fund `version` the client last observed (§2.8). The server copies `investor_id` from the gain onto the election and treats it as immutable thereafter; it stamps `investment_date` with the logical clock's current instant; it computes `days_from_basis`; and it initializes `initial_basis` and `current_basis` at 0.00, `step_up_applied_pct` at 0.0000, `holding_tier` at `UNDER_FIVE`, `included_amount` at 0.00, `included_fraction_total` at 0.0000, `revoked_reason_code` at `NONE`, `deferred_remaining` at the full `elected_amount`, and `status` at `DEFERRED`. The statutory basis in a qualifying investment starts at zero, which is why `initial_basis` is always 0.00 and never derived from the amount invested.

Timeliness is decided by `days_from_basis`, the number of whole elapsed days from the gain's `window_basis_date` to the election's `investment_date`, with any partial day discarded. An election is timely when `days_from_basis` is at least 0 and at most 180. The boundary is inclusive on both ends: a `days_from_basis` of exactly 180 is timely, 181 is rejected with `ERR_180_DAY_WINDOW_CLOSED`, and a negative value — an election dated before the window even opened, which happens readily when the pass-through basis puts `window_basis_date` months after the sale — is rejected with `ERR_180_DAY_WINDOW_NOT_OPEN`.

Several gates stand between a request and a written election, and §2.11 fixes their order. The receiving fund's `certification_status` must be `SELF_CERTIFIED`, or the request is rejected with `ERR_FUND_NOT_CERTIFIED`; a `DECERTIFIED` fund is rejected with `ERR_FUND_DECERTIFIED`. The investor must be `ATTESTED`. The gain's character must still be deferrable. The `expected_fund_version` must match. And the amount must fit: `elected_amount` may not exceed the gain's current `unelected_amount`, or the request is rejected with `ERR_ELECTED_AMOUNT_EXCEEDS_GAIN`.

Writing the election moves the gain along its own cyclic lifecycle, and the branch depends on how much of the gain is left. From `ELIGIBLE`, an election for strictly less than the whole `unelected_amount` produces `ELIGIBLE → PARTIALLY_INVESTED`; an election for exactly the whole `unelected_amount` produces `ELIGIBLE → FULLY_INVESTED` and sets `unelected_amount` to 0.00. From `PARTIALLY_INVESTED`, a further election for strictly less than the remaining `unelected_amount` is a self-loop `PARTIALLY_INVESTED → PARTIALLY_INVESTED` in which `elected_amount` grows and `unelected_amount` falls by exactly the elected figure, while an election for exactly the remainder produces `PARTIALLY_INVESTED → FULLY_INVESTED` with `unelected_amount` set to 0.00. Each of these bumps the gain's `version` by 1. The gain's `elected_amount` rollup is the sum of `elected_amount` over its elections whose `status` is not `REVOKED`; `unelected_amount` is the conserved remainder, `eligible_amount` less that rollup, and it is never negative.

Two ledgers outside the gain also move on every election: the fund's `deferred_gain_committed`, which is the sum of `elected_amount` over that fund's elections whose `status` is not `REVOKED`, and the investor's `deferred_gain_outstanding`. The fund's `version` is incremented by 1 as part of the same request — which is precisely why the next client to create an election must have re-read the fund.

Revocation is the compensating action, and it is tightly fenced. Only the investor who owns the election may revoke it: `X-User-ID` must equal the election's `investor_id`. The election must be in `DEFERRED`, and **no** inclusion event may exist against it — once any gain has been included, the election's dollars have already moved into income and cannot be handed back. That second bar is tested after the `DEFERRED` state guard and is reported as `ERR_INVALID_STATE_TRANSITION` in its own right, so an election that is still `DEFERRED` yet carries an event is refused with the same error id as one whose status was never revocable. The request carries `revoked_reason_code`, one of `INVESTOR_WITHDRAWAL`, `FUND_REJECTED` or `ADMIN_CORRECTION`; the field reads `NONE` on every election that has not been revoked. On success, `DEFERRED → REVOKED` sets `deferred_remaining` to 0.00 and records the reason code, then cascades in three links: the gain's `elected_amount` falls and its `unelected_amount` rises by exactly the revoked election's `elected_amount`; because the gain's elected total changed, its `status` is re-derived and walks back down — `FULLY_INVESTED → PARTIALLY_INVESTED` when other non-revoked elections remain against the gain, `FULLY_INVESTED → ELIGIBLE` when the revoked election was the only non-revoked one, and `PARTIALLY_INVESTED → ELIGIBLE` likewise when it was the only one; and because the election no longer counts, the fund's `deferred_gain_committed` and the investor's `deferred_gain_outstanding` are recomputed. After the pair of actions the gain's `unelected_amount` is identical to its value before the election was ever created.

An election's `holding_tier` is a cached view of how long the investment has been held, resolved from the logical clock at the most recent mutation that affects how the election reads; it moves through `UNDER_FIVE`, `FIVE_YEAR`, `SEVEN_YEAR` and `TEN_YEAR` and is forced to `TEN_YEAR` when a step-up election is granted. Exactly three requests re-resolve it: recording an inclusion event against the election, filing a step-up election that is granted, and the full-inclusion cascade of a fund decertification or of a second consecutive certified asset-test failure. Nothing else does. An election is created at `UNDER_FIVE`, and advancing the logical clock, revoking the election, or merely reading it back all leave the cached tier exactly where it stood — so an election whose investment is ten years old still reads `UNDER_FIVE` until one of those three requests touches it. The authoritative tier for any money calculation is always the one resolved at the moment of the event, as described in §3.9.

### 3.4. The Asset Ledger and the Ninety-Percent Asset Test

A `SELF_CERTIFIED` fund records what it holds. Each holding is registered by a `FundManager` who owns the fund (or by a `PlatformAdmin`) with the `fund_id`, the `asset_class`, the `acquisition_date`, the `unadjusted_cost_basis` in dollars and the `afs_fair_value` in dollars, both at least 0.00. Three inputs are optional: `qoz_business_id`, which links the holding to an operating business; `acquired_from_related_party`, defaulting to false; and `original_use_in_zone`, defaulting to false, which asserts that original use of the property in the zone commenced with the fund. `asset_class` is one of `QOZ_BUSINESS_PROPERTY`, `QOZB_EQUITY`, `NONQUALIFIED_FINANCIAL_PROPERTY` or `CASH`. Registering an asset against a fund that is not `SELF_CERTIFIED` yields `ERR_FUND_NOT_CERTIFIED`, and against a `DECERTIFIED` fund, `ERR_FUND_DECERTIFIED`.

Two referential rules bite at registration. Property bought from a related party can never be qualified zone business property, so an asset with `acquired_from_related_party` true and `asset_class` `QOZ_BUSINESS_PROPERTY` is rejected outright with `ERR_RELATED_PARTY_ACQUISITION`. And the operating-business link is exclusive to equity: `asset_class` `QOZB_EQUITY` **requires** a `qoz_business_id` whose business belongs to the same `fund_id` as the asset, while every other asset class must omit `qoz_business_id` entirely. A missing link, a link supplied on the wrong class, or a link pointing at a business of a different fund all yield `ERR_QOZB_LINK_REQUIRED`.

A new asset is created with `status` `HELD`, `adjusted_basis` equal to its `unadjusted_cost_basis`, `disposed_at` empty, `proceeds_amount` at 0.00, and `disposition_sequence_index` empty. Its initial `qualification` is derived, not supplied, and there are four cases: `QOZ_BUSINESS_PROPERTY` with `original_use_in_zone` true is `QUALIFIED` immediately; `QOZ_BUSINESS_PROPERTY` with `original_use_in_zone` false is `IMPROVEMENT_PENDING`, because used property only qualifies once it has been substantially improved; `QOZB_EQUITY` tracks the linked business's `qualification_status`, so it is `QUALIFIED` exactly when that business is `QUALIFIED` and `NONQUALIFIED` otherwise; and `NONQUALIFIED_FINANCIAL_PROPERTY` and `CASH` are always `NONQUALIFIED`. Registration then recomputes all four fund aggregates. An asset's `adjusted_basis` is its `unadjusted_cost_basis` plus the sum of `amount` over every capital expenditure booked to an improvement project on that asset whose `counts_toward_basis` flag is true, to two decimal places.

Disposal ends an asset's life. A `FundManager` who owns the fund (or a `PlatformAdmin`) disposes an asset that is `HELD` by supplying the gross `proceeds_amount` — `HELD` is the only state disposal is declared from, so an asset that is still `IMPROVING` cannot be disposed of and is refused with `ERR_INVALID_STATE_TRANSITION`; the improvement project must reach `SATISFIED` or `LAPSED` first and return the asset to `HELD`. The `HELD → DISPOSED` transition stamps `disposed_at` from the logical clock, records the proceeds, and recomputes `aggregate_asset_basis`, `aggregate_qualified_basis`, `aggregate_afs_value` and `aggregate_qualified_afs_value` so that the basis ledger again describes only the fund's remaining `HELD` and `IMPROVING` assets. Disposal respects any order pinned by a granted step-up election: when the asset carries a non-empty `disposition_sequence_index`, every asset of the same fund with a non-empty index strictly smaller than this asset's index must already be `DISPOSED`, or the request is rejected with `ERR_DISPOSITION_ORDER_VIOLATION`. `disposition_sequence_index` itself is the asset's 1-based position inside the disposition sequence of the most recently granted step-up election belonging to that fund, and is empty for any asset the sequence does not list. Disposal leaves already-certified asset tests untouched; only tests still in `DRAFT` or `MEASURED` will see the change, and only at their next measurement.

Asset tests are opened per testing period by a `FundManager` who owns the fund or by a `ComplianceOfficer`. The request supplies the `measurement_date` the ratio is attributed to, the `period_start` that inclusively opens the testing period, the `period_end` that exclusively closes it, and optionally a `valuation_method_override`. The test's own `valuation_method` is resolved once at creation: the override when one is supplied, otherwise the fund's `asset_test_valuation_method` as of that moment. The test is created in `status` `DRAFT` with `result` `PENDING`, `qualified_numerator` and `total_denominator` at 0.00, `ratio_pct` at 0.0000, `included_asset_count` at 0, `shortfall_amount` at 0.00 and `failed_month_count` at 0.

Testing periods for one fund may not overlap, and the interval arithmetic is **half-open**: the new period `[period_start, period_end)` must not intersect the half-open period of any existing asset test of the same fund, and `period_start` must be strictly before `period_end`. Adjacency is legal here — a new period whose `period_start` equals an existing period's `period_end` is accepted, because back-to-back semiannual periods share that instant. A genuine intersection, or a period whose start is not strictly before its end, is rejected with `ERR_TESTING_PERIOD_OVERLAP`.

Measuring a test moves it `DRAFT → MEASURED`, requires the owning fund to be `SELF_CERTIFIED`, records the caller's handle as `measured_by_user_id`, and sets the fund's `last_test_measurement_date` to this test's `measurement_date`. It takes no request body at all — every input comes from the stored test and the fund's live asset ledger. The measurement proceeds as follows. The included set is every asset of the test's fund whose `status` is `HELD` or `IMPROVING`, whose `acquisition_date` is strictly before `period_end`, and which either has no `disposed_at` at all or has a `disposed_at` on or after `period_end`; an asset disposed before `period_end` is excluded from **both** the numerator and the denominator. `included_asset_count` is the number of assets in that set. Each included asset contributes a value chosen by the test's `valuation_method`: its `unadjusted_cost_basis` under `UNADJUSTED_COST_BASIS`, its `afs_fair_value` under `APPLICABLE_FINANCIAL_STATEMENT`. `total_denominator` is the sum of those values over the whole included set, rounded half up to two decimal places; `qualified_numerator` is the same sum restricted to included assets whose `qualification` is `QUALIFIED`. `ratio_pct` is the numerator divided by the denominator, multiplied by 100 and rounded half up to four decimal places — and exactly 0.0000 when `total_denominator` is 0.00, which is the case a fund with no included assets must not divide its way into. `result` is `PASS` when `ratio_pct` is at least 90.0000 and `FAIL` otherwise, compared against the rounded four-decimal figure. The degenerate test is not a vacuous pass: an included set that is empty, or one whose values all sum to 0.00, reads `ratio_pct` 0.0000 and therefore `result` `FAIL`, with a `shortfall_amount` of 0.00 and a `failed_month_count` computed by the month arithmetic below exactly as on any other failure. On a pass, `shortfall_amount` is 0.00; on a fail it is `total_denominator` multiplied by 0.90, less `qualified_numerator`, rounded half up to two decimal places. On a pass, `failed_month_count` is 0; on a fail it is the whole months of noncompliance attributed to the period, computed as twelve times the difference in years between `measurement_date` and `period_start`, plus the difference in their months, plus one more month when the day-of-month of `measurement_date` is greater than or equal to the day-of-month of `period_start`. Nothing constrains `measurement_date` to fall inside the testing period — creation checks the period's own endpoints and its overlap against sibling tests, never the measurement date against them — and this count is not floored at 0. A `measurement_date` earlier than `period_start` therefore yields a **negative** `failed_month_count`, which is stored on the test as computed and flows unchanged into the fund's `cumulative_penalty_months` and into a negative `gross_penalty_amount` and `net_penalty_amount` on the assessment a certified failure creates.

The valuation variant is not cosmetic. Take a fund holding one `QUALIFIED` asset and one `NONQUALIFIED` asset. Carried at cost, 850000.00 qualified against 150000.00 nonqualified, the ratio is 85.0000 and the test **fails** with a `shortfall_amount` of 50000.00. Carried on the applicable financial statement, the same two rows at 950000.00 and 50000.00 produce 95.0000 and the test **passes** with a `shortfall_amount` of 0.00. Identical asset rows, opposite compliance outcome, decided entirely by which variant the fund elected or the test overrode.

Certification is the `ComplianceOfficer`'s, and the certifier's `X-User-ID` must differ from `measured_by_user_id`. From `MEASURED` the test forks on its stored `result`. A `PASS` produces `MEASURED → CERTIFIED_PASS`, records `certified_by_user_id`, drives the fund's `compliance_posture` to `COMPLIANT` — `UNTESTED → COMPLIANT` on a fund that has never been tested — and resets `consecutive_failed_tests` to 0. A `FAIL` produces `MEASURED → CERTIFIED_FAIL` and a three-link cascade: first `consecutive_failed_tests` increments by 1; second, because the test is now `CERTIFIED_FAIL`, a penalty assessment is created in `ASSESSED` with the fund, the test, the `failed_month_count` and the `shortfall_amount` snapshotted onto it and the penalty figures computed as in §3.8, and the fund's `cumulative_penalty_months` rises by that `failed_month_count`; third, because a live assessment now exists, `compliance_posture` becomes `DEFICIENT`, whether by `UNTESTED → DEFICIENT` on a first-ever test or by `COMPLIANT → DEFICIENT` on a fund that had been passing. Both branches increment the test's `version` and the fund's `version`.

The second consecutive failure is different in kind. When a failing certification lands on a fund whose `consecutive_failed_tests` stands at 1, that count becomes 2 and the cascade grows a fourth link: a second penalty assessment is still created and `cumulative_penalty_months` still rises by its `failed_month_count`, but `compliance_posture` goes `DEFICIENT → FAILED_FINAL` and `certification_status` goes `SELF_CERTIFIED → DECERTIFIED`, and because the fund is now decertified, the full fund-decertification inclusion cascade of §3.2 fires — a `FUND_DECERTIFICATION` inclusion event on every election in `DEFERRED`, `STEPPED_UP` or `INCLUDED_PARTIAL`, those elections moving to `INCLUDED_FULL`, and every owning investor's `deferred_gain_outstanding` and `included_gain_total` recomputed. The trigger for that fourth link is the counter alone — `consecutive_failed_tests` standing at 2 or more once this failure has been counted — and it does not consult the fund's `compliance_posture`, so a fund sitting in `CURE_PENDING` with the counter at 1 decertifies on its next certified failure exactly as a `DEFICIENT` one does. `consecutive_failed_tests` is itself a counter carried on the fund rather than a figure re-derived from the test history: certifying a test `CERTIFIED_FAIL` raises it by exactly 1 from whatever it held, certifying one `CERTIFIED_PASS` resets it to 0, and approving a cure (§3.8) also resets it to 0 even though no test changed state. `last_test_measurement_date` is likewise a stamp written by the measurement call rather than a figure re-derived from the test history: each measurement overwrites it with that test's `measurement_date` unconditionally and bumps the fund's `version` in the same request, so measuring an older test after a newer one moves the field backwards to the older date. It is empty until the fund's first measurement, and no other call — certification included — ever changes it.

### 3.5. Operating Businesses and the Three-Prong Zone Test

Where a fund holds equity rather than property directly, it registers the operating business. A `FundManager` who owns the fund (or a `PlatformAdmin`) supplies the `fund_id`, the business's `legal_name` (1 to 200 characters, non-blank), the `zone_tract_code` of the designated opportunity-zone census tract it operates in — exactly 11 characters, no more and no fewer — its self-reported `declared_nqfp_amount` of nonqualified financial property, its `total_asset_value`, which must be strictly greater than 0.00 and serves as the nonqualified-property denominator whenever no measurement figure overrides it, and its `total_tangible_property_basis`, the aggregate basis of tangible property it holds, at least 0.00. The business is created `UNTESTED` with `consecutive_failed_business_tests` at 0, `wcsh_protected_amount` and `blown_unspent_amount` at 0.00, and `nqfp_amount` equal to `declared_nqfp_amount`, since no safe-harbor plan yet shelters or releases anything. Registration requires the fund to be `SELF_CERTIFIED`.

The `nqfp_amount` is the figure the test actually measures, and it is never the raw declaration. It is `declared_nqfp_amount`, plus `blown_unspent_amount`, minus `wcsh_protected_amount`, rounded half up to two decimal places and floored at 0.00 so it can never go negative. `wcsh_protected_amount` is the sum, over that business's working-capital plans whose `status` is `ACTIVE`, of each plan's `covered_amount` less its `spent_total`, each such difference rounded half up to two decimal places before it enters the sum and deliberately **not** floored at 0.00 — so a plan that has spent past what it covers contributes a negative term and shrinks the shelter the other plans provide, which is why this figure is not the sum of the plans' `unspent_amount` values, those being floored. `blown_unspent_amount` is the sum of `unspent_amount` over that business's plans whose `status` is `BLOWN`. Plans in `DRAFT` and plans in `COMPLETED` enter neither sum. Sheltered dollars are therefore netted out while the shelter holds and thrown back in the moment it fails.

The self-reported figures can be corrected. A manager or platform administrator may update any of `declared_nqfp_amount`, `total_asset_value` and `total_tangible_property_basis`, each independently optional in the request; the update recomputes `nqfp_amount` from the live shelter and release and increments the business's `version`. It deliberately does **not** re-derive any prong of any business test: prongs are only ever re-derived by a fresh measurement or by the plan-blowout cascade described in §3.7.

A test is opened for a `testing_date` by any `FundManager` or `ComplianceOfficer` — unlike asset-test creation this call is **not** fenced by the fund-manager ownership check of §2.11 rule 9, and it does not consult the owning fund's `certification_status` either, so a manager of another fund may open a test and a test may be opened against a business of a `DECERTIFIED` fund. The test arrives in `status` `DRAFT` with `gross_income_prong`, `intangibles_prong` and `nqfp_prong` all `PENDING`, the three percentages at 0.0000, and `nqfp_amount_measured` at 0.00. The measurement inputs come later, at the measure call, which is what makes the safe-harbor election a measurement-time decision rather than a filing-time one.

Measuring the test moves it `DRAFT → MEASURED` and records the caller's handle as `measured_by_user_id`. The request declares `safe_harbor_used` — one of `FIFTY_PCT_HOURS`, `FIFTY_PCT_AMOUNTS_PAID`, `MANAGEMENT_AND_TANGIBLE` or `GROSS_INCOME_ACTUAL` — and supplies `gross_income_zone_amount`, `gross_income_total_amount`, `intangibles_zone_use_amount`, `intangibles_total_amount` and `total_asset_value_measured`, the last of which must be strictly greater than 0.00. Two further inputs are conditional and are the subject of a dedicated check: `FIFTY_PCT_HOURS` requires `hours_zone_pct` and `FIFTY_PCT_AMOUNTS_PAID` requires `amounts_paid_zone_pct`, each a percentage from 0.0000 through 100.0000; `MANAGEMENT_AND_TANGIBLE` and `GROSS_INCOME_ACTUAL` require neither and **reject both**. A missing required percentage, or a percentage supplied for a branch that does not consume it, yields `ERR_SAFE_HARBOR_INPUT_MISSING`.

The measurement computes three prong percentages. `gross_income_pct` follows four mutually exclusive branches. Under `FIFTY_PCT_HOURS` it is `hours_zone_pct` rounded half up to four decimal places. Under `FIFTY_PCT_AMOUNTS_PAID` it is `amounts_paid_zone_pct` rounded the same way. Under `GROSS_INCOME_ACTUAL` it is `gross_income_zone_amount` divided by `gross_income_total_amount`, multiplied by 100 and rounded half up to four decimal places, and exactly 0.0000 when `gross_income_total_amount` is 0.00. Under `MANAGEMENT_AND_TANGIBLE` it is a composite of three inputs: a management component equal to `intangibles_zone_use_amount` divided by `intangibles_total_amount` times 100 rounded half up to four decimal places (0.0000 when `intangibles_total_amount` is 0.00); a tangible component equal to `total_asset_value_measured` less `nqfp_amount_measured`, divided by `total_asset_value_measured`, times 100 and rounded half up to four decimal places, a component that is **not** floored at 0.0000 — the measurement enforces only that `total_asset_value_measured` be strictly greater than 0.00 and never that the snapshotted `nqfp_amount_measured` be no larger than it, so a business whose sheltered-and-released nonqualified property exceeds its reported asset total drives this component, and through it `gross_income_pct`, negative; and then the **smaller** of those two components multiplied by a safe-harbor credit of 1.25, rounded half up to four decimal places, and finally capped so the result can never exceed 100.0000. `intangibles_pct` is `intangibles_zone_use_amount` divided by `intangibles_total_amount` times 100, rounded half up to four decimal places, and 0.0000 when `intangibles_total_amount` is 0.00. `nqfp_amount_measured` snapshots the business's live `nqfp_amount`, and `nqfp_pct` is that snapshot divided by `total_asset_value_measured` times 100, rounded half up to four decimal places; unlike the composite above, `nqfp_pct` carries no cap and reads whatever the ratio produces, above 100.0000 included.

The three verdicts follow from the rounded percentages. `gross_income_prong` is `PASS` when `gross_income_pct` is at least 50.0000 and `FAIL` otherwise. `intangibles_prong` is `PASS` when `intangibles_pct` is at least 40.0000 and `FAIL` otherwise. `nqfp_prong` is `PASS` when `nqfp_pct` is at most 5.0000 and `FAIL` otherwise — note the direction: this prong is a ceiling, not a floor, and nonqualified financial property above five percent of measured assets fails it.

Certification is again the `ComplianceOfficer`'s, again requires `X-User-ID` to differ from `measured_by_user_id`, and forks from `MEASURED` into two terminal states with deliberately different consequences. When all three prong verdicts are `PASS`, the test goes `MEASURED → PASSED`, records `certified_by_user_id`, drives the business `UNTESTED → QUALIFIED` with `consecutive_failed_business_tests` reset to 0, and promotes every `QOZB_EQUITY` asset pointing at that business whose `status` is `HELD` to `qualification` `QUALIFIED`, after which the fund's `aggregate_qualified_basis` and `aggregate_qualified_afs_value` are recomputed. When at least one prong verdict is `FAIL`, the test goes `MEASURED → FAILED`, also records `certified_by_user_id`, and then splits again on which prong failed. The `PASSED` branch fires neither of the two failure paths.

The failure paths are these. If `nqfp_prong` is `PASS` but at least one of `gross_income_prong` and `intangibles_prong` is `FAIL`, and the business's `consecutive_failed_business_tests` stood at 0 before this certification, the business moves `UNTESTED → AT_RISK` (or `AT_RISK → DISQUALIFIED` on a second failure, below) with the counter set to 1. `AT_RISK` is a warning posture only: **no** asset's `qualification` changes and no fund aggregate moves. If instead `nqfp_prong` is `FAIL`, the business is disqualified outright — `UNTESTED → DISQUALIFIED` from a first test, `AT_RISK → DISQUALIFIED` from a warned business — and a four-link cascade runs. First, `qualification_status` becomes `DISQUALIFIED` and `consecutive_failed_business_tests` is set — to 1 from `UNTESTED`, to 2 from `AT_RISK`. Second, because the business is disqualified, every asset pointing at it whose `status` is `HELD` or `IMPROVING` gets `qualification` `NONQUALIFIED`, and the fund's `aggregate_qualified_basis` and `aggregate_qualified_afs_value` are recomputed. Third, because the fund's qualified aggregates changed, the fund's asset test that is still in `MEASURED` with the greatest `measurement_date` — ties broken on the later creation timestamp — is re-measured in place, recomputing its `qualified_numerator`, `total_denominator`, `ratio_pct`, `result`, `shortfall_amount` and `failed_month_count`; when the fund holds no asset test in `MEASURED` at all, links three and four are simply absent and nothing on the fund but its aggregates moves. Fourth, because that re-measured test now reads `FAIL`, the fund's `compliance_posture` moves to `DEFICIENT` — including directly from `COMPLIANT`, and regardless of which posture the fund held before, the move being unconditional once the re-measured test reads `FAIL` and not firing at all when that test re-reads `PASS`. This last path creates **no** penalty assessment, because no certification of an asset test occurred — only a re-measurement.

A business in `AT_RISK` that later certifies a test with all three prongs `PASS` goes `AT_RISK → QUALIFIED` with `consecutive_failed_business_tests` reset to 0. A business in `AT_RISK` whose next certification has any prong `FAIL` goes `AT_RISK → DISQUALIFIED` with the same four-link cascade and the counter at 2. `consecutive_failed_business_tests` is, like the fund's counter, carried on the business rather than re-derived from the test history: a certification that fails raises it by exactly 1 from whatever it held, except that the certification which disqualifies an already-`AT_RISK` business sets it to 2 outright; a certification in which all three prongs pass resets it to 0; and the plan-blowout cascade of §3.7 raises it by 1 as well, even though no business test failed in that request at all. `DISQUALIFIED` is terminal for the business.

### 3.6. Substantial Improvement Projects

Used property has to be substantially improved before it counts, and the improvement has a thirty-month clock. A `FundManager` who owns the fund (or a `PlatformAdmin`) opens a project against a `fund_asset_id` with a `window_start`, an `aggregation_method` of either `ASSET_BY_ASSET` or `AGGREGATED_GROUP`, and — only under the group variant — a `group_key`. `window_end` is computed as `window_start` advanced by exactly 30 calendar months and is an exclusive upper bound. Opening the project snapshots `basis_at_acquisition` from the asset's current `unadjusted_cost_basis`, creates the project `OPEN` with `qualified_additions_total` at 0.00, `improvement_ratio_pct` at 0.0000 and `evaluated_at` empty, and moves the owning asset `HELD → IMPROVING` with `qualification` `IMPROVEMENT_PENDING`. Only property whose `original_use_in_zone` is false may enter improvement — property whose original use in the zone began with the fund needs no improvement to qualify, and a project opened against such an asset is refused with `ERR_INVALID_STATE_TRANSITION`, a bar tested after the terminal-state check that turns a `DISPOSED` asset away with `ERR_ALREADY_TERMINAL` and before the window-collision check below. Being `HELD` is not itself a precondition, only the trigger for the side effect: an asset already `IMPROVING` under an earlier project may take another one whenever the two windows do not collide, and both writes — the `IMPROVING` status and the `IMPROVEMENT_PENDING` qualification — are applied only when the asset is actually `HELD` at the moment of filing and are skipped entirely otherwise, leaving such an asset's `qualification` exactly as it stood. Because an `IMPROVEMENT_PENDING` asset leaves the qualified numerator, opening a project immediately recomputes the fund's `aggregate_qualified_basis` and `aggregate_qualified_afs_value`.

The `group_key` is a self-referential handle that links sibling projects into one aggregation group, and it is 1 to 40 characters when present. It is **required** when `aggregation_method` is `AGGREGATED_GROUP` and **forbidden** when it is `ASSET_BY_ASSET`; furthermore, every project sharing a `group_key` must sit on assets belonging to the same fund. A missing key, a key on an asset-by-asset project, or a key shared across funds yields `ERR_AGGREGATION_GROUP_INVALID`.

Improvement windows on one asset may not collide, and here the interval arithmetic is **closed**, deliberately unlike the asset-test rule. The new project's closed window runs from `window_start` through `window_end` minus one day, inclusive at both ends, and it must not intersect the equally closed window of any existing project on the same `fund_asset_id` whose `status` is `OPEN` or `SATISFIED`. Because both endpoints are inclusive, adjacency is **rejected**: a new window whose `window_start` equals an existing window's last day collides. Any such collision yields `ERR_IMPROVEMENT_WINDOW_OVERLAP`. Setting the two geometries side by side: back-to-back asset-test periods may touch, back-to-back improvement windows may not.

Spending is recorded against the project by the owning `FundManager` with an `amount` strictly greater than 0.00, an `expenditure_kind` of `CAPITALIZED_IMPROVEMENT`, `OPERATING_WORKING_CAPITAL` or `LAND_ACQUISITION`, and the mandatory `expected_project_version` of §2.8. The server stamps `spend_date` from the logical clock, sets the expenditure's `improvement_project_id` from the project it was filed against and leaves its `wcsh_plan_id` empty, and leaves `schedule_month_index` empty as well — that field belongs only to plan-attached spending. `counts_toward_basis` is set true exactly when `expenditure_kind` is `CAPITALIZED_IMPROVEMENT` **and** `spend_date` falls inside the container's window; every other combination leaves it false. Recording the spend recomputes the project's `qualified_additions_total` and `improvement_ratio_pct` and the asset's `adjusted_basis`, and increments the project's `version` by 1. The logical clock must itself be inside the project's window — at or after `window_start` and strictly before `window_end` — or the request is rejected with `ERR_EXPENDITURE_OUTSIDE_WINDOW`.

The ratio is where the two aggregation variants part company. A project's own additions are the sum of `amount` over its capital expenditures whose `expenditure_kind` is `CAPITALIZED_IMPROVEMENT` and whose `spend_date` lies at or after that project's `window_start` and strictly before its `window_end`, rounded half up to two decimal places. Under `ASSET_BY_ASSET`, `qualified_additions_total` is just that figure and the denominator is the project's own `basis_at_acquisition`. Under `AGGREGATED_GROUP`, the group is every project sharing this project's `group_key` whose `aggregation_method` is also `AGGREGATED_GROUP` and whose `status` is `OPEN` or `SATISFIED` — `LAPSED` siblings are excluded from both sides of the ratio — processed in order of `window_start` ascending and then creation timestamp ascending; `qualified_additions_total` is the sum of each member's own additions, rounded half up to two decimal places, and the denominator is the sum of each member's `basis_at_acquisition`, likewise rounded. In both variants `improvement_ratio_pct` is `qualified_additions_total` divided by the denominator, multiplied by 100 and rounded half up to four decimal places, and exactly 0.0000 when the denominator is 0.00.

Pooling changes outcomes, not just presentation. Project A with a `basis_at_acquisition` of 500000.00 and additions of 600000.00 reaches 120.0000 percent and satisfies the requirement on its own; project B with a `basis_at_acquisition` of 500000.00 and additions of 450000.00 reaches only 90.0000 percent and lapses when its window closes. Pool the identical expenditure rows under one `group_key` and both projects read 1050000.00 over 1000000.00, or 105.0000 percent, so project B is satisfied instead of lapsed.

Evaluation is the deciding call, made by any `FundManager` or `ComplianceOfficer` — like the checkpoint of §3.7, and unlike the expenditure call above it, this one is **not** fenced by the fund-manager ownership check of §2.11 rule 9 — and it re-runs the ratio under the project's active `aggregation_method` before deciding. It stamps `evaluated_at` from the logical clock. `OPEN → SATISFIED` requires `improvement_ratio_pct` of at least 100.0000, a logical clock strictly before `window_end`, and the owning asset still `IMPROVING`; it drives that asset `IMPROVING → HELD` with `qualification` `QUALIFIED`, which recomputes the fund's `aggregate_qualified_basis` and `aggregate_qualified_afs_value`. Under `AGGREGATED_GROUP`, satisfaction is collective: every sibling project sharing the `group_key` that is still `OPEN` is also set to `SATISFIED`, and each of their assets is promoted the same way. Only the project the call names has its `evaluated_at` stamped, however; a sibling carried to `SATISFIED` by the group keeps whatever `evaluated_at` it already held, which is empty for a sibling never evaluated on its own. `OPEN → LAPSED` applies once the logical clock has reached or passed `window_end` with `improvement_ratio_pct` still below 100.0000; it drives the owning asset `IMPROVING → HELD` with `qualification` `NONQUALIFIED` and recomputes the same two aggregates. Promotion rewrites the asset's `qualification` unconditionally but moves its `status` only when the asset is actually `IMPROVING`: an asset that has since been disposed of, or that an earlier project already returned to `HELD`, takes the new `qualification` and keeps the `status` it has. That describes the lapse branch, and every sibling an aggregation group carries to `SATISFIED` alongside the named project. The satisfaction branch of the named project itself is different, because there the asset still being `IMPROVING` is a precondition of entering the branch rather than a condition on one write inside it: a project whose ratio has reached 100.0000 inside its window while its **own** asset is no longer `IMPROVING` matches neither outcome branch, so it stays `OPEN` with its refreshed ratio and its freshly stamped `evaluated_at`, and that asset's `qualification` is not rewritten at all. A project that is neither satisfied nor out of time simply stays `OPEN`, with its refreshed ratio and `evaluated_at` recorded. The two outcome branches are tested independently and neither is the other's fallback, so a project that only crossed 100.0000 percent after its window had already closed matches neither — the clock is not strictly before `window_end`, and the ratio is not below 100.0000 — and it too stays `OPEN`. Both `SATISFIED` and `LAPSED` are terminal, so a second evaluation of either yields `ERR_ALREADY_TERMINAL`.

### 3.7. The Working Capital Safe Harbor

A business may shelter working capital from nonqualified-property treatment for thirty-one months provided it has a written plan and spends to schedule. A `FundManager` who owns the fund behind the business, or a `PlatformAdmin`, files the plan with a `qoz_business_id`, a `window_start`, a `covered_amount` strictly greater than 0.00, a `written_plan_reference` of 1 to 80 non-blank characters documenting the written designation, a `schedule_month_count` from 1 through 31, and a `spend_schedule` of monthly buckets. Each bucket is an object carrying a `month_index` from 1 through 31 and a `planned_amount` of at least 0.00, and no two buckets may carry the same `month_index`; a bucket that is not an object, one carrying an unknown key or missing either key, an index outside 1 through 31 or not an integer, a negative `planned_amount`, and a repeated index are all `ERR_INVALID_REQUEST`. Filing does **not** require the indices present to be exactly 1 through `schedule_month_count`, and gaps are not rejected: a gapped schedule — months 1, 2 and 5 under a `schedule_month_count` of 3 — is accepted and, because it carries as many buckets as the count declares, is even fully documented, while a schedule carrying fewer or more buckets than the count is accepted too and simply never becomes documented. `window_end` is `window_start` advanced by exactly 31 calendar months and is an exclusive upper bound.

Filing computes `documentation_complete`, which is true only when `written_plan_reference` is non-blank, the number of buckets in `spend_schedule` equals `schedule_month_count`, and the sum of every `planned_amount`, rounded half up to two decimal places, equals `covered_amount`. That last equality is separately enforced at filing time: a schedule whose planned amounts do not sum to the covered amount is rejected with `ERR_WCSH_SCHEDULE_MISMATCH`. The plan is created `DRAFT` with `spent_total` at 0.00, `unspent_amount` equal to `covered_amount`, `last_checkpoint_month_index` at 0, `pacing_shortfall` at 0.00 and `overspill_amount` at 0.00. No shelter is granted yet, because only `ACTIVE` plans count toward `wcsh_protected_amount`.

Plans may overlap, but their combined shelter is capped, and this is the third and most permissive interval geometry in the domain. It is an **aggregate-capacity** rule rather than a pairwise one: for every month covered by the new plan's window, the sum of `covered_amount` over that business's plans whose `status` is `DRAFT` or `ACTIVE` and whose window covers that same month, plus the new plan's own `covered_amount`, must be no greater than the business's `total_asset_value` multiplied by 0.31 and rounded half up to two decimal places. A breach in any covered month yields `ERR_WCSH_AGGREGATE_CAP_EXCEEDED`. Because the test is a per-month sum rather than a pair test, a single overlapping pair can be perfectly legal while the addition of a third overlapping plan breaches the cap — unlike the asset-test rule, where any half-open intersection is fatal, and unlike the improvement rule, where any closed intersection is fatal.

Activation is the owning `FundManager`'s alone. It moves the plan `DRAFT → ACTIVE`, requires `documentation_complete` to be true — otherwise `ERR_WCSH_PLAN_INCOMPLETE` — and requires the logical clock to sit at or after `window_start` and strictly before `window_end`, otherwise `ERR_WCSH_WINDOW_CLOSED`. Activation raises the business's `wcsh_protected_amount` by `covered_amount` less `spent_total` and therefore recomputes `nqfp_amount` downward, which is the whole point of the harbor.

Spending against an active plan is likewise the owning `FundManager`'s, and takes an `amount` strictly greater than 0.00 and an `expenditure_kind`. The expenditure's `wcsh_plan_id` is set from the plan it was filed against and its `improvement_project_id` is left empty. The same in-window rule applies, again with `ERR_WCSH_WINDOW_CLOSED`. Logging a spend refreshes the plan's `spent_total`, `unspent_amount` and `overspill_amount` and every attached expenditure's `schedule_month_index`, and recomputes the business's `wcsh_protected_amount` and `nqfp_amount`; it never moves the plan's `status`. Nor does it touch `pacing_shortfall` or `last_checkpoint_month_index`: those two are written only by a checkpoint, so between checkpoints a plan's reported `pacing_shortfall` is a stale figure describing where the plan stood when it was last evaluated, and a spend that closes the gap does not lower it until the next checkpoint recomputes it. A spend the waterfall excludes — that is, a `LAND_ACQUISITION` one, the out-of-window case having already been refused — moves none of the plan's figures, and because nothing changed the plan's `version` does not move either, though the expenditure itself is still written and returned. Only the checkpoint evaluation may complete or blow a plan.

The pacing figures come from a waterfall allocation, and the order is pinned. The eligible spends are the plan's expenditures whose `expenditure_kind` is `OPERATING_WORKING_CAPITAL` or `CAPITALIZED_IMPROVEMENT` and whose `spend_date` lies at or after `window_start` and strictly before `window_end`; `LAND_ACQUISITION` spends and out-of-window spends are excluded from both `spent_total` and the waterfall entirely. Those spends are sorted by `spend_date` ascending, ties broken on creation timestamp ascending and never on identifier. Buckets are taken in `month_index` ascending order. Each spend is poured into the earliest bucket that still has room — room being that bucket's `planned_amount` less what has already been filled into it, at two decimal places — and continues into successive buckets until the spend is exhausted or the buckets run out. The `schedule_month_index` recorded on the expenditure is the highest `month_index` its dollars actually reached. A spend that no bucket could absorb at all — because every bucket was already filled to its `planned_amount` by the time this spend was poured — records `schedule_month_index` as empty, and a bucket whose `planned_amount` is 0.00, or one already full, is never counted as reached. Whatever cannot be absorbed by any bucket accumulates into the plan's `overspill_amount` at two decimal places.

The checkpoint is evaluated by any `FundManager` or `ComplianceOfficer` — again outside the fund-manager ownership fence of §2.11 rule 9, unlike activation and plan spending, which are the owning manager's alone — at a `checkpoint_month_index`, which must be an integer from 1 through `schedule_month_count` and must be at least the plan's current `last_checkpoint_month_index` — checkpoints may repeat an index but may never walk backwards, and a violation yields `ERR_CHECKPOINT_INDEX_INVALID`. At that index, `required_cumulative` is the sum of `planned_amount` over buckets whose `month_index` is at most the index, and `actual_cumulative` is the sum of what the waterfall filled into those same buckets, each rounded half up to two decimal places. `pacing_shortfall` is `required_cumulative` less `actual_cumulative`, rounded half up to two decimal places and floored at 0.00. `spent_total` is the sum of `amount` over the eligible spends at two decimal places, `unspent_amount` is `covered_amount` less `spent_total`, floored at 0.00, and `last_checkpoint_month_index` is set to the evaluated index.

The tolerance is 10 percent of `required_cumulative`, rounded half up to two decimal places, and the comparison is **strictly greater than**: a plan whose shortfall lands exactly on the tolerance survives, and only a shortfall above it fails. When `pacing_shortfall` exceeds the tolerance, the plan moves `ACTIVE → BLOWN` and a three-link cascade runs. First, the business's `wcsh_protected_amount` falls to exclude this plan while its `blown_unspent_amount` rises by the plan's `unspent_amount`, so `nqfp_amount` is recomputed upward. Second, because `nqfp_amount` rose, the business's latest `MEASURED` business test — the one with the greatest `testing_date`, ties broken on the later creation timestamp — has its `nqfp_amount_measured`, `nqfp_pct` and `nqfp_prong` re-derived, and only those three: `gross_income_pct`, `intangibles_pct`, the other two prong verdicts and the test's own `MEASURED` status all stand as they were measured. If the recomputed `nqfp_pct` exceeds 5.0000 the business is disqualified — from `QUALIFIED`, and equally from `UNTESTED` or `AT_RISK`, the sole exception being a business already `DISQUALIFIED`, which is left where it stands — with `consecutive_failed_business_tests` raised by 1. If instead the business has no test in `MEASURED` to re-derive at all it moves `QUALIFIED → AT_RISK` with its counter left alone, and a business not currently `QUALIFIED` is left untouched on that path, on the ground that the sheltered working capital has re-entered `nqfp_amount` but no measurement yet proves a breach. Third, on the disqualifying branch only, every asset pointing at that business whose `status` is `HELD` or `IMPROVING` gets `qualification` `NONQUALIFIED` and the fund's `aggregate_qualified_basis` and `aggregate_qualified_afs_value` are recomputed.

When instead `checkpoint_month_index` has reached or passed `schedule_month_count` and `pacing_shortfall` is exactly 0.00, the plan moves `ACTIVE → COMPLETED`. The shelter drops — `wcsh_protected_amount` falls to exclude the plan — but `blown_unspent_amount` is **not** increased, so `nqfp_amount` rises only by whatever `unspent_amount` remained, which is 0.00 whenever the schedule was fully funded on time. A completed plan therefore never disqualifies a business, and this is exactly where the completed and blown branches diverge. A checkpoint that neither blows nor completes the plan leaves it `ACTIVE` with its refreshed pacing figures, and moves the plan's `version` only when one of those figures actually changed value — so a checkpoint repeated at the same index with no spending in between returns the plan byte-for-byte as it stood, `version` and `updated_at` included. Both `COMPLETED` and `BLOWN` are terminal.

### 3.8. Penalty Assessment, Cure Requests and Cure Decisions

A penalty assessment is never created by a client. It exists only as link two of the certified-failure cascade in §3.4, where it is born snapshotting `fund_id` and `asset_test_id` from the failing test along with that test's `failed_month_count` and `shortfall_amount`. It arrives with `cure_credit_amount` at 0.00, `cure_attempt_count` at 0, `cure_basis` `NONE`, `narrative_reference` empty, `requested_by_user_id` and `decided_by_user_id` empty, and `status` `ASSESSED`. Assessments are discoverable only by reading them back individually or through the assessment list, which is the sole discovery channel for rows the cascade created.

The penalty arithmetic has a pinned rounding order and getting it wrong is off by cents. `monthly_penalty_amount` is `shortfall_amount` multiplied by an annual underpayment rate of 0.08 and divided by 12, rounded half up to the cent **first**. `gross_penalty_amount` is that already-rounded per-month figure summed over `failed_month_count` months, rounded half up to two decimal places. `net_penalty_amount` is `gross_penalty_amount` less `cure_credit_amount`, which is 0.00 at assessment time, so net equals gross until a cure is approved. Worked through: a `shortfall_amount` of 50000.00 over a `failed_month_count` of 6 gives a monthly figure of 333.33 and a gross of 1999.98. Multiplying first and rounding once at the end would give 2000.00; that is explicitly not the contract.

The owning `FundManager` may file a cure request against an `ASSESSED` assessment, supplying a `cure_basis` of either `REASONABLE_CAUSE` or `TREATED_AS_FAILURE` and a `narrative_reference` of 1 to 200 non-blank characters documenting the argument. The request is permitted only while `cure_attempt_count` is below 2; a third filing is rejected with `ERR_CURE_ATTEMPTS_EXHAUSTED` and leaves the assessment `ASSESSED`. Filing moves the assessment `ASSESSED → CURE_REQUESTED`, increments `cure_attempt_count` by 1, records `cure_basis`, `narrative_reference` and `requested_by_user_id` from the caller, and moves the fund's `compliance_posture` `DEFICIENT → CURE_PENDING` — but only out of `DEFICIENT`: a fund whose posture reads anything else when the request is filed keeps the posture it has, and the assessment still moves.

A `ComplianceOfficer` decides the pending request with a `decision` of `APPROVE` or `DENY`. Approval requires the asserted basis to be approvable: only `REASONABLE_CAUSE` may be approved, and approving a `TREATED_AS_FAILURE` basis is rejected with `ERR_CURE_BASIS_NOT_APPROVABLE`, because that basis is a concession of the failure rather than a defence of it. The decision records `decided_by_user_id`.

Approval moves the assessment `CURE_REQUESTED → CURED` and computes the credit through a tiered netting whose definition only looks circular. The tier basis is the **gross** penalty, never the net figure. The cap percentage is 0.60 when the gross is at least 1000.00 and 0.40 otherwise. The credit is that cap percentage multiplied by the gross and rounded half up to two decimal places, then raised to a floor of 250.00 if it falls below it, then capped so it can never exceed the gross itself, and rounded half up to two decimal places again. `net_penalty_amount` is the gross less that credit. There is no second pass: the cap percentage is never re-derived from the resulting net figure even when the net falls below the tier break as a consequence of the credit. Worked through on a gross of 1999.98: the gross is at least 1000.00, so the cap is 0.60; 0.60 of 1999.98 is 1199.988, which rounds to 1199.99; the floor of 250.00 does not bind and the cap at gross does not bind, so the credit is 1199.99 and the net is 799.99. Re-deriving the tier from the net, seeing 799.99 below 1000.00 and applying 0.40 would produce a credit of 800.00 and a net of 1199.98, which is the wrong answer.

Approval is also the compensating action for the second conserved quantity. It decrements the fund's `cumulative_penalty_months` by exactly this assessment's `failed_month_count`, returning that count to its pre-assessment value and flooring it at 0 so it can never go negative, moves the fund's `compliance_posture` to `COMPLIANT` — the declared path being `CURE_PENDING → COMPLIANT`, though the write is unconditional and lands on `COMPLIANT` from whatever posture the fund held — and resets the fund's `consecutive_failed_tests` to 0.

Denial is not a compensating action, and it forks on the asserted basis. Denying a `REASONABLE_CAUSE` request cycles the assessment `CURE_REQUESTED → ASSESSED`: `cure_credit_amount` stays 0.00, the fund's `cumulative_penalty_months` is unchanged, and `compliance_posture` moves `CURE_PENDING → DEFICIENT`. Because the assessment is `ASSESSED` again rather than terminal, a second request may be filed — which is what makes the two-attempt cap meaningful. Denying a `TREATED_AS_FAILURE` request instead moves the assessment `CURE_REQUESTED → UPHELD`, which is terminal: `net_penalty_amount` remains equal to `gross_penalty_amount`, `compliance_posture` still moves `CURE_PENDING → DEFICIENT`, and `cumulative_penalty_months` is unchanged because an upheld penalty's months keep counting. Both `CURED` and `UPHELD` are terminal, so a further decision on either yields `ERR_ALREADY_TERMINAL`, and a decision filed against an assessment that is merely `ASSESSED` yields `ERR_INVALID_STATE_TRANSITION`.

### 3.9. Ten-Year Step-Up Elections and the Disposition Sequence

An investor who has held a qualifying investment for ten years may elect to step its basis up to fair market value, and the same filing pins the order in which the fund will dispose of its assets. The investor who owns the election, or a `PlatformAdmin`, files it with a `claimed_fmv` strictly greater than 0.00 and an optional `disposition_sequence`, an ordered list of asset identifiers. The server sets the step-up election's `deferral_election_id` from the deferral election it was filed against, stamps `election_date` from the logical clock, and computes `holding_period_days` as the whole days from the election's `investment_date` to `election_date`.

The outcome is decided synchronously at filing time — the filing always succeeds and is always recorded, either `GRANTED` or `DENIED`, and the denial reasons are evaluated in a fixed order. If `holding_period_days` is below 3653 the election is `DENIED` with `denial_reason` `HOLD_UNDER_TEN_YEARS`. Otherwise, if the fund's `certification_status` is `DECERTIFIED` the election is `DENIED` with `denial_reason` `FUND_DECERTIFIED`. Otherwise, if any inclusion event on this election has `is_full` true the election is `DENIED` with `denial_reason` `PRIOR_FULL_INCLUSION`. Otherwise it is `GRANTED` with `denial_reason` `NONE`. `stepped_up_basis` is `claimed_fmv` when granted and 0.00 when denied. The ten-year boundary is inclusive at 3653: a `holding_period_days` of exactly 3653 grants, and 3652 denies with `HOLD_UNDER_TEN_YEARS`.

Because a shorter hold produces a recorded denial rather than a rejection, `ERR_TEN_YEAR_HOLD_NOT_MET` covers only the filing whose hold cannot be evaluated at all: an election whose `investment_date` lies strictly after the logical clock. Similarly, the terminal-state bar of §2.11 is carved out for this one filing: a step-up election filed against an `INCLUDED_FULL` deferral election is accepted and comes back as a `DENIED` step-up election with `denial_reason` `PRIOR_FULL_INCLUSION`, or `FUND_DECERTIFIED` when that reason is reached first, because the investor is entitled to a written denial on file rather than a bare rejection. The one deferral-election status that bars a filing outright is `REVOKED`, which yields `ERR_ELECTION_REVOKED`: a revoked election has no qualifying investment left to step up.

A granted election drives the deferral election `DEFERRED → STEPPED_UP`, setting its `current_basis` to the `claimed_fmv`, its `step_up_applied_pct` to 1.0000 and its `holding_tier` to `TEN_YEAR`. Only the status write is conditioned on the election standing in `DEFERRED`; the other three are unconditional. A grant landing on an election in any other status the filing admits — `INCLUDED_PARTIAL`, or `STEPPED_UP` from an earlier grant — still rewrites `current_basis`, `step_up_applied_pct` and `holding_tier`, and leaves the status exactly where it stands. When a `disposition_sequence` was supplied, position `i` of the list, counting from 1, is written to the `disposition_sequence_index` of the asset named at that position. The list is authoritative: there is no server-side ranking, no tie-break, and no dependence on identifier ordering. Every listed asset must belong to the election's fund, must be `HELD`, must appear at most once, and the list must be non-empty when supplied, or the filing is rejected with `ERR_DISPOSITION_SEQUENCE_INVALID`; an identifier naming no asset at all is rejected earlier as a referenced-entity failure. Disposition indices are what §3.4's disposal ordering rule reads: an asset carrying a non-empty `disposition_sequence_index` may be disposed only once every asset of the same fund with a strictly smaller non-empty index is already `DISPOSED`, and jumping the queue yields `ERR_DISPOSITION_ORDER_VIOLATION`.

### 3.10. Inclusion Events and the Holding-Tier Basis Step

Deferred gain comes back into income on an inclusion event. The owning investor, a `FundManager` or a `PlatformAdmin` records one against the election with an `event_type` of `SALE_OF_INTEREST`, `GIFT_TRANSFER`, `FUND_DECERTIFICATION`, `PARTIAL_REDEMPTION` or `DEC_31_2026_STATUTORY`, and an `included_fraction` strictly greater than 0.0000 and at most 1.0000 expressed to four decimal places, being the fraction of the election's original `elected_amount` that this event includes. The server sets the event's `deferral_election_id` from the deferral election it was recorded against, stamps `event_date` from the logical clock, and computes `holding_days` as the whole days from the election's `investment_date` to `event_date`.

The tier follows from `holding_days` against three thresholds, tested from the longest hold down: at least 3653 days is `TEN_YEAR`, otherwise at least 2557 days is `SEVEN_YEAR`, otherwise at least 1826 days is `FIVE_YEAR`, otherwise `UNDER_FIVE`. The result is stored as `holding_tier_applied`. The five-year boundary is inclusive: exactly 1826 days is `FIVE_YEAR`, and 1825 days is `UNDER_FIVE`. The basis step that follows from the tier is 0.15 for `SEVEN_YEAR` and `TEN_YEAR`, 0.10 for `FIVE_YEAR`, and 0.00 for `UNDER_FIVE`.

`gross_inclusion_amount` is the election's `elected_amount` multiplied by `included_fraction`, rounded half up to two decimal places. `basis_offset_amount` is `elected_amount` multiplied by `included_fraction` and by the tier's step, rounded half up to two decimal places. `net_inclusion_amount` is the gross less the offset, rounded half up to two decimal places. `is_full` is true exactly when the election's `included_fraction_total` plus this event's `included_fraction`, rounded half up to four decimal places, reaches 1.0000. The election may never be over-included: that same sum must be at most 1.0000, and a request that would exceed the remaining fraction is rejected with `ERR_INCLUSION_FRACTION_EXCEEDS_REMAINING`.

Recording the event recomputes the election's `included_amount` — the sum of `net_inclusion_amount`, and never of `gross_inclusion_amount`, over every inclusion event recorded against that election, client-recorded and system-generated events alike, rounded half up to two decimal places, so the tier's basis step is already netted out of the figure the investor's `included_gain_total` rolls up — together with its `included_fraction_total`, the sum of `included_fraction` over those same events rounded half up to four decimal places and capped at 1.0000, and its `deferred_remaining`, which is the election's `elected_amount` multiplied by one less `included_fraction_total`, rounded half up to two decimal places and floored at 0.00 — deliberately **not** `elected_amount` less `included_amount`, so the tier's basis step never enlarges what stays deferred — and then recomputes the investor's `deferred_gain_outstanding` and `included_gain_total`. A `REVOKED` election reads `deferred_remaining` 0.00 outright, whatever its `elected_amount` and whatever fraction was ever included against it. Five election transitions are driven from here. From `DEFERRED`, an event leaving the running fraction total below 1.0000 moves the election `DEFERRED → INCLUDED_PARTIAL`; an event closing it exactly at 1.0000 moves it `DEFERRED → INCLUDED_FULL` with `deferred_remaining` set to 0.00 and the event's `is_full` true. From `INCLUDED_PARTIAL`, a further event still short of 1.0000 is a self-loop `INCLUDED_PARTIAL → INCLUDED_PARTIAL` in which `included_amount` and `included_fraction_total` grow while `deferred_remaining` shrinks, and an event closing the remaining fraction moves it `INCLUDED_PARTIAL → INCLUDED_FULL`, again zeroing `deferred_remaining` and marking the event full. From `STEPPED_UP`, an event with an `included_fraction` of 1.0000 moves the election `STEPPED_UP → INCLUDED_FULL`, and 1.0000 is the only fraction that machine accepts — an event for anything less against a `STEPPED_UP` election is refused with `ERR_INVALID_STATE_TRANSITION`, a bar tested after the state guard and before the over-inclusion ceiling, on the ground that a stepped-up investment is included whole or not at all; because a stepped-up election carries `holding_tier` `TEN_YEAR`, that event's `basis_offset_amount` uses the 0.15 step. `INCLUDED_FULL` is terminal, and the two branches out of `DEFERRED` — the step-up branch, which rewrites basis and writes disposition indices, and the inclusion branch, which moves gain dollars into the investor's `included_gain_total` — converge there.

Inclusion events also arrive without a client request, as the system events of the fund-decertification cascade in §3.2. Those carry `event_type` `FUND_DECERTIFICATION` and an `included_fraction` covering the whole remaining fraction, and they are computed by the identical tier and offset arithmetic. The inclusion-event list for an election is the only channel through which those system-created rows can be discovered.

The investor statement is the reporting view over all of this. It returns the `investor_id` together with `eligible_gain_total`, `deferred_gain_outstanding` and `included_gain_total` as defined in §3.1, plus `election_count`, the number of deferral elections belonging to that investor, and `inclusion_event_count`, the number of inclusion events recorded against those elections. It is readable by the investor itself, by a `ComplianceOfficer` and by a `PlatformAdmin`, with the investor's own reads subject to the ownership scope of §2.1.

### 3.11. The Deadline Sweep

Three of the domain's clocks expire without anybody filing anything, and a single operator batch pass — a `PlatformAdmin` capability — applies all three against the logical clock. It takes no input and mutates every row that qualifies.

First, every eligible gain whose `status` is `ELIGIBLE` or `PARTIALLY_INVESTED` and whose `investment_deadline` the logical clock has moved **strictly past** is expired with `expired_at` stamped from the clock, by `ELIGIBLE → EXPIRED` and `PARTIALLY_INVESTED → EXPIRED` respectively. A gain sitting exactly on its deadline is not swept — the 180-day window is inclusive of its final instant, consistent with the election gate of §3.3. Expiry freezes the gain's `status` and nothing else: an `EXPIRED` gain never re-derives that field again however its elections move, while its `elected_amount` and `unelected_amount` split is still recomputed on every change to those elections. So the dollars left in `unelected_amount` at expiry are in practice unreachable, but not by any terminal-state check: election create never inspects the gain's `status` at all, and what turns a late election away is the 180-day gate of §3.3, which an expired gain has by construction already crossed. The two rules are not quite coextensive, because expiry needs the clock strictly past the deadline while the gate needs the whole days from `window_basis_date` to exceed 180 — so during the single day that follows the deadline instant an election against an `EXPIRED` gain is still written, against the gain's remaining `unelected_amount`, and the gain's frozen `status` stays `EXPIRED` while its `elected_amount` rises. Revoking one of that gain's still-`DEFERRED` elections after expiry lowers the gain's `elected_amount` rollup and raises `unelected_amount` by exactly the revoked figure, just as it would have before. `EXPIRED` is terminal for a gain.

Second, every improvement project that is still `OPEN` whose `window_end` the logical clock has reached or passed, and whose stored `improvement_ratio_pct` is still below 100.0000 — the figure exactly as the last expenditure or evaluation left it, because the sweep does not re-run the ratio before deciding, so a project whose group has since crossed the threshold through a sibling's spending still lapses on its own stale figure — moves `OPEN → LAPSED` with the same effects as an operator-driven evaluation: `evaluated_at` is stamped and the owning asset returns `IMPROVING → HELD` with `qualification` `NONQUALIFIED`, which recomputes the fund's `aggregate_qualified_basis` and `aggregate_qualified_afs_value`. The sweep simply applies that transition to every matching project at once rather than one at a time.

Third, every working-capital plan that is still `ACTIVE` whose `window_end` the logical clock has reached or passed and whose `unspent_amount` is strictly greater than 0.00 moves `ACTIVE → BLOWN`, with the identical three-link cascade as the checkpoint-driven blowout: the shelter is withdrawn from `wcsh_protected_amount`, `blown_unspent_amount` rises by the plan's `unspent_amount`, `nqfp_amount` is recomputed upward, the latest `MEASURED` business test's nonqualified-property prong is re-derived, and the business moves to `DISQUALIFIED` or `AT_RISK` accordingly with the asset and aggregate consequences that follow. A plan whose window has closed with `unspent_amount` at exactly 0.00 is left alone, because every sheltered dollar was in fact spent.

The response reports what the pass did: `expired_gain_count`, `lapsed_project_count` and `blown_plan_count` as integers, and `swept_at`, the logical-clock instant the pass ran at. The counts are of rows actually transitioned, so a sweep on an unchanged ledger reports three zeros, and a second immediate sweep after a first reports zeros as well because every qualifying row has already left its pre-sweep state.

## 5. Error Codes

The table below lists every error identifier this API may return in the `error_id` field of the error envelope described in §2.2, together with its HTTP status code. When more than one condition holds simultaneously, the identifier returned is the one belonging to the lowest-numbered rule in the order of evaluation given in §2.11.

The status shown against each identifier is the status it carries for the condition described in §2.11. `ERR_INVALID_REQUEST` is the one identifier the server reuses outside that ladder, and there its status differs: HTTP 404 for a path that matches no route and HTTP 405 for a method a matching route does not declare (§2.6), and HTTP 500 should the server fault unexpectedly.
