# ADA Workplace Accommodation API — Product Requirements Document

## 1. Introduction

Employers subject to the Americans with Disabilities Act do not fail their accommodation obligations by refusing outright. They fail by drifting: a documentation request that asks for a diagnosis nobody was entitled to see, a manager's essential-function analysis that was never completed before options were priced, an undue-hardship verdict computed against a department budget when the statute contemplates the employer's whole balance sheet, an appeal decided by the same person who issued the denial. Each of those is a small procedural slip. Together they are the record an enforcement agency reads. This service exists to make the interactive process auditable while it is happening rather than reconstructable afterwards.

The product is a records-of-authority backend for the entire accommodation lifecycle. It carries the job architecture that defines what a role actually requires, the intake of an accommodation request through whichever channel it arrived, a bounded medical-documentation budget that the employer may not exceed, a manager-signed analysis of each essential duty, an exploration phase in which either party may propose accommodations, a finance-run undue-hardship score computed under one of two statutory budget bases, a trial period with structured effectiveness check-ins, a denial-and-appeal track with strict segregation of duties, and a recurring renewal review that re-arms itself for as long as the accommodation remains in force. Crossing all of that is a confidentiality dimension that evolves on its own axis: medical information hardens the case as soon as it exists, and an impermissible disclosure seals the case permanently against further process activity until an auditor intervenes.

Two design commitments shape everything downstream. First, **every number the service reports is reproducible** — costs, coverage fractions, hardship scores, effectiveness scores and integrity scores are all computed by pinned formulas with pinned evaluation order and pinned rounding, so two runs over the same facts never disagree. Second, **the process is scored, not merely recorded**. Each case carries an interactive-process integrity score that decays when the employer over-requests documentation, lets a response window lapse, discloses medical information to someone not entitled to it, or misses a renewal deadline. That score is not decorative: below a fixed threshold, an appeal officer is forbidden from upholding the denial and must remand the case back into option exploration.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API — including reads, including the operational endpoints — must carry two headers. `X-User-ID` identifies the actor and `X-User-Role` names the capacity in which that actor is acting. If either header is absent, if `X-User-ID` is present but empty, or if `X-User-Role` is not exactly one of the seven role names below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This check runs before anything else, ahead of body parsing and ahead of any lookup.

The seven roles are `Employee`, `Manager`, `AccommodationCoordinator`, `MedicalReviewOfficer`, `FinanceOfficer`, `AppealOfficer` and `ComplianceAuditor`. Their spelling is exact and case-sensitive.

- An `Employee` is the worker who is asking for an accommodation, and acts only on their own case.
- A `Manager` is the people manager who performs the essential-function analysis and participates in effectiveness check-ins.
- An `AccommodationCoordinator` is the ADA coordinator who runs the interactive process from intake through renewal.
- A `MedicalReviewOfficer` is the confidentiality firewall: the only role allowed to rule on whether submitted medical documentation is sufficient.
- A `FinanceOfficer` runs the undue-hardship assessment against a department or employer-wide budget.
- An `AppealOfficer` decides appeals, and is bound by segregation-of-duties rules described later.
- A `ComplianceAuditor` is the read-everything oversight role that additionally owns the confidentiality override, the logical clock and the operational sweep.

Two of these roles are **entity-backed**. When `X-User-Role` is `Employee`, `X-User-ID` is the `id` of the acting `Employee` row; ownership checks on any case-scoped resource compare that resource's owning case's `employee_id` against `X-User-ID`. When `X-User-Role` is `Manager`, `X-User-ID` is likewise the `id` of an acting `Employee` row, and scope checks compare that row's `department_code` against the case employee's `department_code`. For both of these roles, if `X-User-ID` does not resolve to an existing `Employee`, the request is rejected with `ERR_UNKNOWN_ACTOR` (HTTP 401). Acting as `Manager` additionally requires that the resolved `Employee` row carries `is_people_manager` set to true; a resolved employee without that flag is rejected with `ERR_NOT_A_PEOPLE_MANAGER` (HTTP 403).

The remaining five roles — `AccommodationCoordinator`, `MedicalReviewOfficer`, `FinanceOfficer`, `AppealOfficer` and `ComplianceAuditor` — carry **opaque** identity. For these, `X-User-ID` is an operator identifier that is not tied to any persisted entity and is never compared against any row's `id`. The server does record it where the workflow demands an audit trail — as `issued_by_user_id` on a denial issued by a coordinator, as `assessor_user_id` on an assessment run by a finance officer, as `appeal_officer_user_id` on an appeal taken under review, as `reviewer_user_id` on an effectiveness check-in, and as `logged_by_user_id` on a disclosure log row — but it is treated as a string token, not as a foreign key.

Each endpoint declares the set of roles permitted to invoke it (see §4). An authenticated actor whose role is not in that set is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query-string parameters. `limit` controls page size: it defaults to 10 when omitted, may be no smaller than 1, and may be no larger than 100. `offset` controls the starting position within the result set: it defaults to 0 and may be no smaller than 0. A supplied `limit` or `offset` outside those bounds, or one that is not an integer, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400); this check runs before the parent path identifier of a nested listing is resolved, so a bad `limit` aimed at a non-existent parent reports `ERR_INVALID_REQUEST` rather than that parent's not-found code.

Unless a subsection below says otherwise, list results are ordered by `created_at` ascending, and because the logical clock only moves when it is explicitly set, ties on that stamp are the common case rather than the exception: they are broken by insertion order, so rows sharing a `created_at` come back in the order they were created. All four pagination fields — `limit`, `offset`, `total_count` and `has_more` — appear in the `meta` object of every list response. `total_count` reports the number of rows matching the filters before the page window is applied, and `has_more` is true exactly when rows remain beyond the current window.

List endpoints also accept the domain filters named in §4's description column; those filters are applied before pagination, and `total_count` reflects the filtered population. Filter values themselves are never validated: a value matching no row simply yields an empty page rather than an error, a boolean filter (`is_essential`, `authorized`) given anything but `true`, `false`, `1` or `0` is ignored outright, and an unrecognised query parameter is ignored.

### 2.4. Resource Identity, Timestamps and Version Semantics

Every resource this API mints carries a server-generated `id`. It is a UUID string with no type prefix — no `emp_`, no `req_`, nothing but the UUID itself. Clients never supply an `id`; a body that contains one has it ignored.

Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional-second digits (for example `2026-08-01T00:00:00.000Z`), stamped from the logical clock of §2.5 when the row is first persisted and never altered afterwards.

Most resources additionally carry `updated_at` — same format, refreshed from that same logical clock on every mutation of that row — and `version`, an integer that begins at 1 when the row is created and increases by exactly 1 on every mutation of that row. **Two entity types are exceptions.** `EffectivenessReview` rows and `MedicalDisclosure` rows are append-only journal entries: they carry `id` and `created_at` only, and both `updated_at` and `version` are absent from their representations entirely. Every other entity type — `Employee`, `JobProfile`, `EssentialFunction`, `AccommodationRequest`, `MedicalDocumentationRequest`, `FunctionAnalysis`, `AccommodationOption`, `UndueHardshipAssessment`, `TrialPeriod`, `DenialRecord`, `Appeal` and `AbsenceRecord` — carries all four common properties.

The primary row that a successful mutating call addresses always advances by exactly 1, even when the supplied values happen to leave every field unchanged — an amendment that rewrites a field with the value it already held, or a `PATCH` body carrying none of its optional fields at all, still moves that row's `version` and `updated_at`. A cascade counts as a mutation, but only where it actually changes something: a row a cascade reaches and leaves identical does not move. When a decision on a case shelves three sibling options, all three of those option rows have their `updated_at` refreshed and their `version` incremented, exactly as the selected option does. When a cascade recomputes a counter on the parent case, the case row's `version` moves too. Version numbers are per-row; nothing in this system maintains a global sequence. Because both stamps read the logical clock rather than real time, a row created and then mutated while the clock still reads the creation instant ends up with `updated_at` exactly equal to `created_at` even though its `version` has moved; `updated_at` differs from `created_at` only when the clock has been moved in between.

### 2.5. The Logical Clock and Deferred Operations

Nothing in this service reads the host machine's wall clock for any domain purpose; the single exception is the envelope's `api_request_timestamp` of §2.2, which is stamped from host wall-clock time and bears no relation to the logical clock. All date and time comparisons — documentation-window expiry, appeal deadlines, trial start and end, renewal due dates, the `issued_at` / `responded_at` / `filed_at` / `review_date` stamps — read a **logical clock** maintained by the server. At process startup that clock reads exactly `2026-08-01T00:00:00Z`, and it holds that value until it is explicitly moved. There is no fallback to real time under any circumstance, including before the first clock write.

A `ComplianceAuditor` moves the clock by supplying `to_iso8601`; the response reports the newly effective instant as `current_utc`. The clock carries no monotonicity guard: an instant earlier than the current reading is accepted exactly like a later one and simply becomes the new reading. Moving the clock does not, by itself, advance any state machine. Clock-gated transitions are applied only by the **daily sweep**, a separate `ComplianceAuditor`-only operation that walks every deferred transition in a pinned phase order and reports what it did. The sweep response carries `swept_at` plus seven counters: `doc_requests_expired`, `absence_records_activated`, `absence_records_exhausted`, `trials_activated`, `trials_moved_to_review`, `requests_moved_to_renewal_due` and `denials_finalized`.

The phase order is normative and is never permuted:

1. Every `MedicalDocumentationRequest` still in status `ISSUED` whose `due_date` is at or before the current logical instant moves to `EXPIRED`.
2. Every `AbsenceRecord` in status `SCHEDULED` whose `start_date` is at or before the current logical date moves to `ACTIVE`.
3. Every `AbsenceRecord` in status `ACTIVE` whose `record_type` is `FMLA_CONTINUOUS`, `FMLA_INTERMITTENT` or `STATE_LEAVE`, and whose `end_date` is at or before the current logical date, moves to `EXHAUSTED`.
4. Every `TrialPeriod` in status `SCHEDULED` whose `start_date` is at or before the current logical date moves to `ACTIVE`.
5. Every `TrialPeriod` in status `ACTIVE` whose `end_date` is at or before the current logical date moves to `UNDER_REVIEW`.
6. Every `AccommodationRequest` in stage `GRANTED_PERMANENT` whose `review_due_date` is non-null and is at or before the current logical date moves to stage `RENEWAL_DUE`.
7. Every `DenialRecord` in status `ISSUED` with `appeal_count` equal to zero whose `appeal_deadline_date` is strictly earlier than the current logical date moves to `FINAL`, and its case moves to stage `DENIED_FINAL`.
8. The interactive-process integrity score is recomputed for every case touched by phase 1 or phase 6.

Within a phase, rows are processed in `created_at` ascending order; no random identifier participates in any ordering decision. **Phases never re-run within one sweep.** A trial promoted from `SCHEDULED` to `ACTIVE` in phase 4 is not eligible for phase 5 in the same sweep — it needs a second sweep to reach `UNDER_REVIEW`.

### 2.6. Rejection Ordering: How the Server Chooses an Error

When a request violates more than one rule, exactly one error is returned, and which one is fully determined. Checks are evaluated in the strict ascending order below, and **the first check that fails ends the request**. No later check is consulted, and no earlier check can be skipped because a later one looks more specific. This ordering is a contract in its own right: a caller that trips two rules must see the earlier one.

1. **Headers present and role recognised** — otherwise `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. **Entity-backed actor resolves** — when the acting role is `Employee` or `Manager`, `X-User-ID` must name an existing `Employee`; otherwise `ERR_UNKNOWN_ACTOR`. Applies to every endpoint whose permitted roles include `Employee` or `Manager`.
3. **Role permitted on this endpoint** — otherwise `ERR_ROLE_NOT_PERMITTED`. Applies to every endpoint.
4. **People-manager flag** — when acting as `Manager`, the resolved employee must carry `is_people_manager` true; otherwise `ERR_NOT_A_PEOPLE_MANAGER`. Applies to every endpoint whose permitted roles include `Manager`.
5. **Body well-formed** — the request body must parse, must carry every required field, and every supplied value must satisfy its declared type, its enum membership and its numeric range; otherwise `ERR_INVALID_REQUEST`. This rung also carries every cross-field and conditional body constraint — a string-length bound, an `end_date` that may not precede its `start_date`, a `due_date` that must be strictly after the moment of issuance, and a field that is required only for a particular `decision` value — so each of those is reported as `ERR_INVALID_REQUEST` ahead of any path or body identifier lookup. Applies to every endpoint that takes a body.
6. **Path identifiers resolve** — every id templated into the URL must name an existing row, checked strictly left to right, each yielding the not-found code for its own resource type. Applies to every endpoint with a path parameter.
7. **Body identifiers resolve** — every id carried in the body must name an existing row: `employee_id`, `job_profile_id`, `essential_function_id`, `request_id`, `option_id`, `absence_record_id`, `alternative_option_id`, `selected_option_id`, and each member of `coverage_function_ids`. The applicable not-found code is the one for the referenced resource type. Applies to every endpoint carrying an id in the body.
8. **Case ownership for employees** — when acting as `Employee` on a case-scoped resource, `X-User-ID` must equal the case's `employee_id`; otherwise `ERR_NOT_CASE_OWNER`. This guard covers exactly eight operations: opening an accommodation case, driving a case's stage, proposing an option on a case, responding to a documentation round, filing an appeal against a denial, performing a non-terminal appeal action, recording an effectiveness check-in on a trial, and amending a function analysis.
9. **Manager department scope** — when acting as `Manager` on a case-scoped resource, the acting employee's `department_code` must equal the case employee's `department_code`; otherwise `ERR_MANAGER_SCOPE_VIOLATION`. This guard covers exactly five operations: recording a function analysis on a case, amending a function analysis, recording an effectiveness check-in on a trial, authoring an essential function on a job profile, and revising an essential function. The last two are addressed through a job profile rather than a case, and no case exists anywhere on those paths; there the comparison is made instead against the owning `JobProfile`'s own `department_code`.
10. **Transition is declared** — the target resource must be in a state from which the requested transition exists, otherwise the state-machine rejection for that resource type: `ERR_INVALID_STAGE_TRANSITION`, `ERR_DOC_REQUEST_NOT_OPEN`, `ERR_OPTION_NOT_ASSESSABLE`, `ERR_TRIAL_NOT_RESOLVABLE`, `ERR_DENIAL_NOT_APPEALABLE`, `ERR_APPEAL_NOT_ACTIONABLE`, `ERR_ABSENCE_TRANSITION_INVALID` or `ERR_PROFILE_NOT_DRAFT`, each HTTP 409. Applies to every state-changing endpoint.
11. **Optimistic concurrency token matches** — see §2.7; otherwise `ERR_STALE_VERSION`.
12. **Case is not sealed** — see §2.10; otherwise `ERR_CASE_SEALED`.
13. **Segregation of duties on appeals** — see §3.8; otherwise `ERR_SEGREGATION_OF_DUTIES`.
14. **Medical scope is not overbroad** — otherwise `ERR_MEDICAL_SCOPE_OVERBROAD`.
15. **Documentation is permitted at all on this case** — otherwise `ERR_DOCUMENTATION_NOT_PERMITTED`.
16. **The option being granted covers enough essential weight** — otherwise `ERR_ESSENTIAL_FUNCTION_UNCOVERED`.
17. **The requesting employee's job profile is published** — otherwise `ERR_PROFILE_NOT_PUBLISHED`.
18. **Referenced essential functions belong to the pinned profile and are live** — otherwise `ERR_FUNCTION_NOT_IN_PINNED_PROFILE`.
19. **Documentation budget remains** — otherwise `ERR_DOC_REQUEST_LIMIT_EXCEEDED`.
20. **Function analysis is complete** — otherwise `ERR_FUNCTION_ANALYSIS_INCOMPLETE`.
21. **At least one option has been proposed** — otherwise `ERR_NO_OPTIONS_PROPOSED`.
22. **No option is still awaiting assessment** — otherwise `ERR_OPTION_ASSESSMENT_PENDING`.
23. **No duplicate function analysis for the same duty** — otherwise `ERR_DUPLICATE_FUNCTION_ANALYSIS`.
24. **Business keys are unique** — otherwise `ERR_DUPLICATE_RESOURCE_KEY`.
25. **The appeal window is still open** — otherwise `ERR_APPEAL_WINDOW_CLOSED`.
26. **No documentation window overlap** — otherwise `ERR_DOC_WINDOW_OVERLAP`.
27. **No trial window conflict** — otherwise `ERR_TRIAL_WINDOW_CONFLICT`.
28. **No blocking absence over the trial interval** — otherwise `ERR_TRIAL_BLOCKED_BY_ABSENCE`.
29. **Intermittent weekly capacity is not exceeded** — otherwise `ERR_INTERMITTENT_CAP_EXCEEDED`.
30. **A cross-referenced workers'-compensation restriction is on modified duty** — otherwise `ERR_WC_MODIFIED_DUTY_REQUIRED`.
31. **The selected option is not hardship-blocked** — otherwise `ERR_OPTION_HARDSHIP_BLOCKED`.
32. **An appeal with a degraded process score must be remanded, not upheld** — otherwise `ERR_APPEAL_MUST_REMAND`.
33. **The appeal supplement allowance is not exhausted** — otherwise `ERR_APPEAL_SUPPLEMENT_LIMIT`.
34. **The interactive-round allowance is not exhausted** — otherwise `ERR_INTERACTIVE_ROUND_LIMIT`.
35. **Enough trial reviews exist to resolve** — otherwise `ERR_INSUFFICIENT_TRIAL_REVIEWS`.
36. **The requested trial outcome agrees with the computed score** — otherwise `ERR_TRIAL_OUTCOME_MISMATCH`.
37. **The trial extension allowance is not exhausted** — otherwise `ERR_TRIAL_EXTENSION_LIMIT`.
38. **The employee's open-case allowance is not exhausted** — otherwise `ERR_OPEN_CASE_LIMIT`.

The specific conditions attached to checks 12 through 38 are stated in the workflow narratives of §3, alongside the business rule each one protects.

### 2.7. Optimistic Concurrency on Contested Records

Three write operations are guarded by optimistic concurrency control against a parent row's `version`. In each case the guard field is **required, not optional** — omitting it is a malformed body and fails the body-well-formedness check with `ERR_INVALID_REQUEST` long before the concurrency comparison is reached. No other endpoint in this API accepts a version field, and supplying one where it is not declared has no effect.

- **Issuing a medical documentation round** on an accommodation case requires `expected_request_version` carrying the client's last observed `version` of that `AccommodationRequest`. A new round legitimately supersedes an earlier `REJECTED_INSUFFICIENT` round and consumes one unit of the case's documentation budget, so a writer whose view of `medical_doc_request_count` and `medical_doc_request_limit` has gone stale must re-read first. If the supplied value differs from the case's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412).
- **Recording an undue-hardship assessment** on an accommodation option requires `expected_option_version` carrying the client's last observed `version` of that `AccommodationOption`. A new assessment supersedes the option's prior current assessment, so a finance officer whose view of the option's costs or coverage has gone stale would otherwise overwrite a verdict it never saw. A mismatch against the option's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412).
- **Completing a recurring renewal review** on a case requires `expected_request_version` carrying the client's last observed `version` of that `AccommodationRequest`. A renewal review writes a new `review_due_date` over the standing cadence, so a stale writer would overwrite a cadence it never observed. A mismatch against the case's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412).

Note the interaction the option guard is designed to catch: revising an option's costs advances that option's `version` even when the revision leaves the option's `status` unchanged at `PROPOSED`. Any concurrency token a finance officer was already holding is invalidated by that revision.

### 2.8. Nested Path Resolution and Reverse Lookups

Several resources are addressed through their parent. Path identifiers are resolved strictly left to right, and the leftmost failure determines the error: on a path naming a job profile and then an essential function, a non-existent profile yields `ERR_JOB_PROFILE_NOT_FOUND` even if the function id is also bogus. The eleven not-found codes map one-to-one onto resource types: `ERR_EMPLOYEE_NOT_FOUND`, `ERR_JOB_PROFILE_NOT_FOUND`, `ERR_ESSENTIAL_FUNCTION_NOT_FOUND`, `ERR_REQUEST_NOT_FOUND`, `ERR_DOC_REQUEST_NOT_FOUND`, `ERR_FUNCTION_ANALYSIS_NOT_FOUND`, `ERR_OPTION_NOT_FOUND`, `ERR_TRIAL_NOT_FOUND`, `ERR_DENIAL_NOT_FOUND`, `ERR_APPEAL_NOT_FOUND` and `ERR_ABSENCE_RECORD_NOT_FOUND`, all HTTP 404.

Once a child collection is addressed through a parent, the collection is scoped to that parent: listing the documentation rounds of one case never returns a round belonging to another. Where a relationship is not expressed in the URL, it is reachable as a query filter on the corresponding top-level list, which is how a caller performs a reverse lookup from a foreign key back to the rows that reference it.

### 2.9. Money, Weights, Ratios and Rounding

All monetary amounts in this system are **whole cents held as integers**. There are no fractional cents and no floating-point currency anywhere in a stored value or a response. Wherever a monetary computation produces a fraction, it is rounded **half up** to the nearest whole cent — a value ending in exactly half a cent rounds away from zero.

Non-monetary computed quantities carry declared decimal precision, always with half-up rounding: coverage fractions and budget ratios are held to six decimal places; the three normalised hardship components are held to four decimal places; the pre-credit and post-credit hardship scores and the trial effectiveness score are held to two decimal places; a per-review composite is held to four decimal places. Counters, weights, day counts and integrity scores are exact integers with no rounding at all.

One rounding rule deserves separate emphasis because it is easy to get wrong: where a formula below says that two components are each rounded and only then added, that order is mandatory. Adding first and rounding once produces a different cent value whenever the two fractional parts are each below half a cent but sum to half a cent or more, and that divergence is a defect, not a tolerance.

### 2.10. Confidentiality as a Parallel Dimension

Every accommodation case carries two independent state dimensions. `stage` tracks where the case sits in the interactive process. `confidentiality_posture` tracks how tightly the case's medical information is held, and it moves on its own axis: nothing about the `stage` value constrains the posture value, and a posture change never by itself advances or rewinds `stage`. The posture begins at `STANDARD` and may be `RESTRICTED` or `SEALED`.

Once a case is `SEALED`, mutating operations scoped to that case are refused with `ERR_CASE_SEALED` (HTTP 409). Exactly three families of operation remain available on a sealed case: every read operation, appending a new row to the case's medical-disclosure log, and the auditor's posture override. Everything else — issuing documentation, advancing the stage, proposing options, deciding, scheduling trials, filing appeals, running a renewal review — is blocked while the seal stands.

### 2.11. The Committed-Cost Ledger and Its Zero-Drift Rule

Each job profile carries `committed_accommodation_cost_cents`, a running ledger of accommodation spend committed against that profile's department budget. The ledger is not a free-form counter; it is bound by an invariant that must hold after every request completes: **the profile's ledger equals the sum of `committed_cost_cents` over every accommodation option in status `SELECTED` or `IMPLEMENTED` whose case pins that profile.** Options in `PROPOSED`, `CLEARED`, `HARDSHIP_BLOCKED`, `SHELVED`, `TRIAL_FAILED` or `WITHDRAWN` contribute exactly zero.

The ledger moves through matched pairs. The forward action fires when an option enters `SELECTED` or `IMPLEMENTED`: the option's `committed_cost_cents` is set to its `option_net_cost_cents`, and that same amount is added to the profile's ledger. The compensating action fires when an option leaves that set — through a failed trial or through a case closing out of renewal review: the option's currently held `committed_cost_cents` is subtracted from the profile's ledger, and the option's `committed_cost_cents` is then set to zero.

The pair must leave the ledger at exactly the value it held before the forward action. **Zero drift is required**, and it is required even when `option_net_cost_cents` has been recomputed in the interim: the release always subtracts the amount actually held in `committed_cost_cents`, never a freshly recomputed net cost.

## 3. Business Logic & Workflows

### 3.1. Job Architecture: Profiles, Duties and Publication

Nothing in the interactive process can be evaluated without an agreed statement of what the job actually requires, so the job architecture is authored first. An `AccommodationCoordinator` creates a **job profile** by supplying its business key `job_code`, a human-readable `title`, the owning `department_code`, and two budget figures in whole cents: `department_annual_budget_cents`, the owning department's annual accommodation budget, and `employer_annual_budget_cents`, the employer-wide annual accommodation budget. Both budgets must be strictly greater than zero. A profile is born in `status` `DRAFT` with `essential_function_count` at zero, `total_essential_weight` at zero, `committed_accommodation_cost_cents` at zero and `profile_version_label` null. The `job_code` must be unique across all profiles; a collision is rejected with `ERR_DUPLICATE_RESOURCE_KEY`.

While a profile is `DRAFT`, duties are authored onto it. Either an `AccommodationCoordinator` or a `Manager` may add an **essential function**, supplying `function_code`, a business key that must be unique within that profile and whose collision is refused with `ERR_DUPLICATE_RESOURCE_KEY`, a narrative `description` of the duty, a `criticality_weight` between 1 and 10 inclusive that expresses how important the duty is relative to its siblings, and a `frequency_per_week` between 0 and 40 inclusive. Two optional flags round it out: `is_essential`, which defaults to true, and `marginal_reassignable`, which defaults to false and is meaningful only for duties that are *not* essential — it marks a marginal duty as one a coworker may absorb. The duty's owning `job_profile_id` is taken from the address, never from the body, and the duty is born with `status` `ACTIVE`. Authoring a duty onto a profile that has already left `DRAFT` is refused with `ERR_PROFILE_NOT_DRAFT`.

Each duty write refreshes two roll-ups on the owning profile. `essential_function_count` is the number of duties on the profile whose `status` is `ACTIVE`, regardless of whether they are essential or marginal. `total_essential_weight` is the sum of `criticality_weight` over the profile's duties that are simultaneously `is_essential` true and `status` `ACTIVE`; marginal duties and retired duties contribute nothing to it.

Duties can be revised after authoring, by either an `AccommodationCoordinator` or a `Manager`, adjusting any of `criticality_weight`, `frequency_per_week`, `is_essential`, `marginal_reassignable` and `status`. Revision carries no `DRAFT` precondition of its own — unlike authoring, it stays available once the profile is `PUBLISHED`, which is the only reason the cascade described next ever has live accommodation work to act on. Revision is where the graph gets interesting, because a duty is referenced by live accommodation work elsewhere. Three consequences follow every revision. The profile's `essential_function_count` and `total_essential_weight` are recomputed. Then the coverage fraction is recomputed for **every** accommodation option belonging to a case pinned to this profile whose option `status` is `PROPOSED`, `CLEARED` or `HARDSHIP_BLOCKED` — retiring a heavily weighted duty silently reshapes the coverage arithmetic of options that were priced before the retirement. And when the revision drives `status` to `RETIRED`, every function analysis anywhere in the system that analysed this duty and currently sits in `RECORDED` or `DISPUTED` is moved to `SUPERSEDED`, which removes it from every completeness count that referenced it.

Publication freezes the architecture. An `AccommodationCoordinator` publishes a `DRAFT` profile by supplying `profile_version_label`, a label stamped onto the profile at that moment; the profile's `status` becomes `PUBLISHED`. Publishing anything that is not currently `DRAFT` is refused with `ERR_PROFILE_NOT_DRAFT`. A published profile is never reopened — when the job changes materially, a successor profile is created under a new `job_code` rather than the published one being edited back to draft.

Both duty listings and profile reads are open to all seven roles; the duty listing narrows by `status` and by `is_essential`.

### 3.2. Workforce Records: Employees, Leave and Workers' Compensation

An employee is registered by an `AccommodationCoordinator` or a `ComplianceAuditor` with `employee_number` (a payroll identifier unique across all employees, between 1 and 32 characters), `full_name`, `department_code`, `job_title`, `hire_date` as an ISO 8601 calendar date in `YYYY-MM-DD` form, `job_profile_id` naming the profile whose duties will govern this person's analyses, an optional `is_people_manager` flag defaulting to false, and `annual_salary_cents`, a whole-cent figure that may not be negative. A duplicate `employee_number` is refused with `ERR_DUPLICATE_RESOURCE_KEY`. Three roll-ups start at their base values: `employment_status` at `ACTIVE`, `open_case_count` at zero and `lifetime_denial_count` at zero.

Those three roll-ups are derived, not client-supplied. `employment_status` is one of `ACTIVE`, `ON_LEAVE` and `RESTRICTED_DUTY`, and it is driven entirely by the employee's absence records. `open_case_count` is the number of accommodation cases for this employee whose stage is anything other than `CLOSED`, `WITHDRAWN` or `DENIED_FINAL`. `lifetime_denial_count` is the number of denial records on this employee's cases whose `status` is `ISSUED`, `APPEALED` or `FINAL`; a denial that has been `VACATED` is excluded, which is why vacating a denial decrements the count. Employees can be listed with filters on `job_profile_id`, `department_code` and `employment_status`.

Leave and workers' compensation reach this system as **absence records**, a single polymorphic table discriminated by `record_type`. An `AccommodationCoordinator` records one with `employee_id`, `record_type` (one of `FMLA_CONTINUOUS`, `FMLA_INTERMITTENT`, `STATE_LEAVE` and `WC_RESTRICTION`), an inclusive `start_date` and an **exclusive** `end_date` that must be strictly after the start, plus four optional fields: `weekly_intermittent_days` between 0 and 7 inclusive (defaulting to 0, meaningful only for intermittent leave), `restriction_severity` between 0 and 5 inclusive (defaulting to 0, meaningful only for a workers'-compensation restriction), `modified_duty_available` defaulting to false, and `claim_reference`, the external carrier claim number, defaulting to null. Every new record starts in `status` `SCHEDULED`.

Intermittent leave is the one absence type with a capacity rule, and it is an *aggregate* rule rather than an exclusion rule: overlapping intermittent records are perfectly legal, but their combined weekly draw is capped. When an intermittent record is being created, the server gathers every other intermittent record for the same employee whose `status` is `SCHEDULED` or `ACTIVE` and whose interval overlaps the candidate's under half-open comparison — that is, the candidate's start is strictly before the existing record's end and the candidate's end is strictly after the existing record's start. It then adds the candidate's `weekly_intermittent_days` to the sum of `weekly_intermittent_days` across those overlapping records. If that total exceeds **five days per week**, the create is refused with `ERR_INTERMITTENT_CAP_EXCEEDED`. Records that have reached `EXHAUSTED` or `CLOSED` release their capacity and are not counted. Continuous and state-leave records are never counted in this sum; they are policed by the trial-blocking rule instead.

An absence record moves through its own lifecycle, driven either by an `AccommodationCoordinator` supplying a `to_status` of `ACTIVE`, `MODIFIED_DUTY` or `CLOSED`, or by the daily sweep. From `SCHEDULED` the record becomes `ACTIVE` — the sweep does this automatically once the logical date reaches `start_date`, and the coordinator may do it directly. Activation drives the employee's `employment_status`: to `RESTRICTED_DUTY` when the record is a `WC_RESTRICTION`, and to `ON_LEAVE` for every other type. From `ACTIVE`, a workers'-compensation restriction whose `modified_duty_available` is true may move to `MODIFIED_DUTY`, which again sets the employee's `employment_status` to `RESTRICTED_DUTY`; requesting that move on a record that is not a workers'-compensation restriction, or on one where modified duty is not available, is refused with `ERR_ABSENCE_TRANSITION_INVALID`, as is any `to_status` that is not reachable from the record's current status. From `ACTIVE`, a leave-type record — `FMLA_CONTINUOUS`, `FMLA_INTERMITTENT` or `STATE_LEAVE` — is moved to `EXHAUSTED` by the sweep once the logical date reaches `end_date`. Both `ACTIVE` and `MODIFIED_DUTY` may be closed outright to `CLOSED`, and `EXHAUSTED` may also be closed. Whenever a record reaches `EXHAUSTED`, or is closed from `ACTIVE` or `MODIFIED_DUTY`, the employee's `employment_status` returns to `ACTIVE` provided the employee has no other absence record still sitting in `ACTIVE` or `MODIFIED_DUTY`; closing an already-`EXHAUSTED` record is a bookkeeping move that leaves `employment_status` alone. Absence records are readable individually and listable with filters on `employee_id`, `record_type` and `status`.

### 3.3. Intake and the Bounded Medical Documentation Budget

An accommodation case is opened by the `Employee` themselves, by an `AccommodationCoordinator`, or by a `Manager` who observed the need. The opener supplies `employee_id`, a `request_channel` describing how the request arrived — `WRITTEN`, `VERBAL`, `MANAGER_OBSERVED` or `HR_INITIATED` — and `requested_accommodation_text`, the accommodation as the employee described it. Two optional inputs shape the case from the outset: `disability_obvious`, which defaults to false, and `absence_record_id`, which defaults to null and cross-references an existing leave or workers'-compensation record. An `Employee` opening a case for anyone but themselves is refused with `ERR_NOT_CASE_OWNER`.

Intake **pins** the job architecture. The case copies the requesting employee's `job_profile_id` and copies that profile's `profile_version_label` into the case's own `pinned_profile_version_label`. The pinned label is a snapshot: it is never refreshed afterwards, even if the profile is later superseded. The pin is only legal against a profile that is `PUBLISHED` at that moment; a case opened for an employee whose profile is still `DRAFT` is refused with `ERR_PROFILE_NOT_PUBLISHED`. Opening also increments the employee's `open_case_count`, and an employee may not hold more than **two** cases open simultaneously — an intake that would push the count past two is refused with `ERR_OPEN_CASE_LIMIT`.

A new case is born in stage `INTAKE` with `confidentiality_posture` `STANDARD`, `decision` `PENDING`, `interactive_round_count` at zero, `cleared_option_count` at zero, `blocked_option_count` at zero, `review_cycle_index` at zero, `interactive_process_integrity_score` at 100, and `selected_option_id`, `renewal_of_request_id`, `review_cadence_days` and `review_due_date` all null. An `AccommodationCoordinator` may later amend `requested_accommodation_text`, `disability_obvious` and `absence_record_id` on a case, and that amendment carries no stage precondition whatsoever — only the seal of §2.10 blocks it, so it remains available even on a `CLOSED`, `WITHDRAWN` or `DENIED_FINAL` case; linking an absence record after the fact is the ordinary way a leave or workers'-compensation matter gets cross-referenced, and it later shortens the renewal cadence. Cases are readable by every role and listable with filters on `employee_id`, `job_profile_id`, `renewal_of_request_id`, `absence_record_id`, `selected_option_id` and `stage`.

**The documentation budget.** The employer may not interrogate an employee's medical circumstances without limit, so each case carries a hard ceiling on how many documentation rounds it may issue. The ceiling is computed rather than stored by hand. Start from a base allowance of **two** rounds. Add **one** further round if any trial period on this case has concluded ineffective — an accommodation that failed in practice legitimately reopens the medical question. Add **one** further round if the case was itself created as the successor of an earlier case, that is, if `renewal_of_request_id` is non-null. The resulting raw allowance is then capped: `medical_doc_request_limit` is the smaller of that raw allowance and an absolute ceiling of **four** rounds, so no case can ever issue a fifth round however many bonuses accrue. Against that ceiling, `medical_doc_request_count` is the number of documentation rounds on the case in any status **other than** `WITHDRAWN` — an expired round and a round rejected as insufficient both still consume budget. `documentation_budget_remaining` is the ceiling minus the count, floored at zero so it is never negative.

**Issuing a round.** Only an `AccommodationCoordinator` may issue medical documentation. The issue is declared only out of stages `INTAKE` and `DOC_PENDING` — from any other stage it is refused with `ERR_INVALID_STAGE_TRANSITION`, and because that is a transition-declared check it is evaluated ahead of the version token, ahead of the seal, and ahead of all three substantive guards below. It is otherwise guarded by the case-version concurrency token described in §2.7. The coordinator supplies `scope_fields_requested`, a non-empty array whose members are drawn from `functional_limitations`, `work_restrictions`, `restriction_duration`, `prognosis`, `accommodation_needed`, `diagnosis` and `treatment_plan`; a `due_date`, the logical instant at which the response window closes, which must be strictly after the moment of issuance; an optional `is_second_opinion` flag defaulting to false, marking a round where the employer is seeking a second opinion at its own expense; and `expected_request_version`.

Three substantive guards apply, and their relative order matters when a single request trips more than one. The **scope** guard comes first: the employer is entitled to functional information only, so `scope_fields_requested` may not include `diagnosis` and may not include `treatment_plan`, and a round that asks for either is refused with `ERR_MEDICAL_SCOPE_OVERBROAD`. The **permission** guard comes next: when the case's `disability_obvious` is true, the limitation is obvious or already known and no medical documentation may be requested at all, so any round on such a case is refused with `ERR_DOCUMENTATION_NOT_PERMITTED`. The **budget** guard comes after both: `documentation_budget_remaining` must be at least 1, and a round issued against an exhausted budget is refused with `ERR_DOC_REQUEST_LIMIT_EXCEEDED`. Later still comes the **window** guard, described next.

Documentation windows are **half-open** on the case: a round occupies the interval from its `issued_at` up to but excluding its `due_date`, and only rounds still in `ISSUED` occupy anything. A new round's `issued_at` is always the current logical instant, so it can never begin before an existing window; the collision test is therefore simply whether the new `issued_at` falls strictly before the `due_date` of some round still in `ISSUED`. If so, the issue is refused with `ERR_DOC_WINDOW_OVERLAP`. Because the endpoint is exclusive, a round issued at exactly the prior round's `due_date` does **not** collide. Rounds in `RESPONDED`, `ACCEPTED_SUFFICIENT`, `REJECTED_INSUFFICIENT`, `EXPIRED` or `WITHDRAWN` impose no window whatsoever.

A successful issue creates the round in `status` `ISSUED` with `issued_at` read from the logical clock and `round_index` set to the case's `medical_doc_request_count` plus one — a 1-based ordinal assigned in issuance order. It then increments the case's `medical_doc_request_count`, recomputes `documentation_budget_remaining`, recomputes the case's `interactive_process_integrity_score`, and increments the case's `version`. The first such round moves the case from `INTAKE` to `DOC_PENDING`; every subsequent round is a self-loop that leaves the case in `DOC_PENDING`, because the interactive process may legitimately need more than one round.

**Responding, adjudicating, withdrawing and expiring.** Only the case's own `Employee` may respond, supplying `response_summary`, and only while the logical instant is strictly before the round's `due_date`; a response offered once the clock has reached that `due_date` is refused with `ERR_DOC_REQUEST_NOT_OPEN`, the same code a wrong-status attempt draws. Responding moves the round `ISSUED → RESPONDED`, stamps `responded_at` from the clock, and — this is the parallel-dimension side effect — moves the case's `confidentiality_posture` from `STANDARD` to `RESTRICTED`. Once real medical content exists on a case, the posture hardens and never returns to `STANDARD`. A `MedicalReviewOfficer`, and no other role, then adjudicates a `RESPONDED` round by supplying a `verdict` of `SUFFICIENT` or `INSUFFICIENT`, together with an optional `adjudication_note`; the round moves to `ACCEPTED_SUFFICIENT` or to `REJECTED_INSUFFICIENT` accordingly and the note is recorded. An `AccommodationCoordinator` may withdraw a round from either `ISSUED` or `RESPONDED`, which moves it to `WITHDRAWN`, decrements the case's `medical_doc_request_count`, recomputes `documentation_budget_remaining` — returning that budget unit to the case — and recomputes the integrity score. Withdrawal is the only compensating action that returns budget. Any of these three moves attempted from a status that does not permit it is refused with `ERR_DOC_REQUEST_NOT_OPEN`. Finally, the daily sweep expires any round still in `ISSUED` whose `due_date` the logical clock has reached, moving it to `EXPIRED` and recomputing the case's integrity score with the expired-window penalty applied. Rounds on a case are listable, filtered by `status`.

**Leaving the documentation stage.** A case whose `disability_obvious` is true may skip documentation entirely: an `AccommodationCoordinator` advances it straight from `INTAKE` to `FUNCTION_ANALYSIS` by naming that `target_stage`, and that advance is legal only when `disability_obvious` is true. From `DOC_PENDING`, the same advance to `FUNCTION_ANALYSIS` requires that at least one round on the case has reached `ACCEPTED_SUFFICIENT`. A `DOC_PENDING` case that has burned its whole budget without ever obtaining a sufficient response is a dead end for the ordinary path, and the coordinator may instead record a denial: from `DOC_PENDING` a `DENY` decision is permitted only when `documentation_budget_remaining` has reached zero, no round on the case is in `ACCEPTED_SUFFICIENT`, and the recorded `denial_basis` is either `INSUFFICIENT_DOCUMENTATION` or `FAILURE_TO_COOPERATE`. Any advance or decision that is not declared out of the case's current stage is refused with `ERR_INVALID_STAGE_TRANSITION`, and so is any advance or decision whose stage-specific precondition is unmet: a skip from `INTAKE` to `FUNCTION_ANALYSIS` on a case whose `disability_obvious` is false, an advance from `DOC_PENDING` with no round yet `ACCEPTED_SUFFICIENT`, a `DENY` from `DOC_PENDING` with budget still remaining or a sufficient round on file or a `denial_basis` outside those two, and a return from `HARDSHIP_REVIEW` to `OPTION_EXPLORATION` while an option is still `PROPOSED` or `cleared_option_count` is non-zero all draw that same code.

**Withdrawal by the employee.** At any point from `INTAKE`, `DOC_PENDING`, `FUNCTION_ANALYSIS`, `OPTION_EXPLORATION`, `HARDSHIP_REVIEW`, `DECISION_PENDING`, `TRIAL_SETUP` or `TRIAL_ACTIVE`, the case's own `Employee` may abandon the process by naming `WITHDRAWN` as the `target_stage`; the guard is simply that `X-User-ID` equals the case's `employee_id`. `WITHDRAWN` is the only `target_stage` an `Employee` may name — every other stage advance is the `AccommodationCoordinator`'s move — and conversely, because the guard compares `X-User-ID` against the case's `employee_id`, a coordinator's opaque identifier can never satisfy it. Both mismatches are transition-declared failures rather than authorisation failures: an `Employee` naming any stage other than `WITHDRAWN`, and a coordinator naming `WITHDRAWN`, are each refused with `ERR_INVALID_STAGE_TRANSITION`. The preconditions and the cascade are identical from all eight origin stages. Withdrawal sets the case's stage to `WITHDRAWN`; sets every accommodation option on the case that is in `PROPOSED`, `CLEARED` or `HARDSHIP_BLOCKED` to `WITHDRAWN`, adjusting `cleared_option_count` and `blocked_option_count` to match; sets every documentation round on the case in `ISSUED` or `RESPONDED` to `WITHDRAWN` and recomputes `medical_doc_request_count`; sets every trial period on the case in `SCHEDULED`, `ACTIVE` or `UNDER_REVIEW` to `ABORTED`; and decrements the employee's `open_case_count`.

### 3.4. Essential-Function Analysis with the Manager

Before anyone prices an accommodation, the people manager must state, duty by duty, what the employee can and cannot do. Recording that analysis is the `Manager` role's exclusive act — no coordinator, officer or auditor may sign one. The manager names the `essential_function_id` under analysis, states `can_perform_unaided` (whether the employee can perform this duty with no accommodation at all), gives a `limitation_severity` rating between 0 and 5 inclusive, and chooses a `proposed_treatment` from `NOT_LIMITED`, `PERFORM_WITH_AID`, `RESTRUCTURE`, `REASSIGN_MARGINAL` and `CANNOT_PERFORM`. The analysis takes its `request_id` from the case being addressed and stamps `manager_id` from the acting `X-User-ID`; both are server-set and cannot be supplied. Recording carries no stage precondition: an analysis may be signed against a case sitting in any stage, and only the seal of §2.10 stands in the way. Every new analysis is born in `status` `RECORDED` with `employee_dispute_note` null.

Two referential guards protect the analysis. The duty named by `essential_function_id` must be `ACTIVE`, must be flagged `is_essential`, and must belong to the case's pinned `job_profile_id`; a duty that is retired, marginal, or drawn from some other profile is refused with `ERR_FUNCTION_NOT_IN_PINNED_PROFILE`. And a case may hold only one live analysis per duty: if an analysis for the same `essential_function_id` already exists on this case in `RECORDED` or in `DISPUTED`, the attempt is refused with `ERR_DUPLICATE_FUNCTION_ANALYSIS`. Note that a `SUPERSEDED` analysis does not block a fresh one — that is precisely what makes re-analysis possible after a duty has been revised.

Analyses are revisable, and by two different parties with two different intents. A `Manager` in scope may amend `can_perform_unaided`, `limitation_severity` or `proposed_treatment`. The case's own `Employee` may instead register disagreement by supplying `employee_dispute_note`; setting that note moves the analysis from `RECORDED` to `DISPUTED`. Each party's writes are confined to its own fields, and a field supplied by the party that does not own it is silently ignored rather than rejected. The amendment carries no precondition on the analysis's own `status` either, so even a `SUPERSEDED` analysis can be amended — and the row's `version` advances on any such call, including one that changes nothing. The consequence is procedural rather than cosmetic: a `DISPUTED` analysis no longer counts toward completeness, so a dispute genuinely blocks the case from moving on until the manager and employee reconcile. The third status, `SUPERSEDED`, is never set by hand — it arrives only through the cascade fired when the analysed duty is retired, as described in §3.1. Analyses are readable individually and listable with filters on `request_id`, `essential_function_id`, `manager_id` and `status`.

Completeness is the gate out of the analysis stage. An `AccommodationCoordinator` advances the case from `FUNCTION_ANALYSIS` to `OPTION_EXPLORATION` by naming that `target_stage`, and the advance succeeds only when **every** duty on the pinned profile that is simultaneously `is_essential` true and `status` `ACTIVE` has exactly one analysis on this case in `status` `RECORDED`. A missing analysis, a duplicate, or a lone disputed analysis all leave the requirement unmet, and the advance is refused with `ERR_FUNCTION_ANALYSIS_INCOMPLETE`.

### 3.5. Option Exploration, Costing and Coverage

Option exploration is the part of the process the statute actually calls *interactive*, so both sides get to propose. Either an `AccommodationCoordinator` or the case's own `Employee` may put forward an **accommodation option**, and the case must be sitting in stage `OPTION_EXPLORATION` at that moment — proposing from any other stage is refused with `ERR_INVALID_STAGE_TRANSITION`. The proposer supplies `option_code`, a business key that must be unique within the case (a collision yields `ERR_DUPLICATE_RESOURCE_KEY`); a `category` drawn from `EQUIPMENT`, `SCHEDULE_MODIFICATION`, `TELEWORK`, `JOB_RESTRUCTURING`, `REASSIGNMENT`, `LEAVE_AS_ACCOMMODATION` and `POLICY_EXCEPTION`; an optional `one_time_cost_cents` and an optional `recurring_monthly_cost_cents`, each defaulting to 0 and neither permitted to be negative; an `implementation_days` figure between 0 and 365 inclusive, counting calendar days from selection to the accommodation actually being in place; and `coverage_function_ids`, an array naming the duties this option would make performable, which may be empty. The option is stamped with `proposed_by_role` taken from the acting `X-User-Role` — either `Employee` or `AccommodationCoordinator` — is born in `status` `PROPOSED` with `committed_cost_cents` at zero, and takes its `request_id` from the case being addressed.

**Net cost.** Federal tax relief for accommodation spending means the employer's real exposure is not the sticker price. Each option's `option_net_cost_cents` is computed from its two cost inputs and a **26 percent ADA tax credit**, with recurring spend amortised over **24 months**. The order of operations is pinned and is not negotiable. First, the one-time component: multiply `one_time_cost_cents` by the credit-adjusted fraction — that is, by one minus 0.26 — and round the product half up to a whole number of cents. Second, the recurring component: multiply `recurring_monthly_cost_cents` by 24 and then by that same credit-adjusted fraction, and round *that* product half up to a whole number of cents. Only then are the two rounded components added together to give `option_net_cost_cents`. Rounding each component independently before summing them is mandatory; summing the two unrounded components and rounding once is a different computation that yields a different cent figure whenever both fractional parts sit below half a cent yet add to half a cent or more. Only the two cost fields of the single option being written enter this math — no sibling option and no historical value participates.

**Coverage.** An option's `coverage_ratio` measures how much of the job it actually rescues, expressed as a fraction of essential weight. The denominator is the set of duties on the case's pinned job profile that are simultaneously `is_essential` true and `status` `ACTIVE`; the numerator is the subset of *those* duties whose ids appear in the option's `coverage_function_ids`. Sum `criticality_weight` over each set, divide the covered sum by the total sum, and round the quotient half up to six decimal places. Marginal duties and retired duties are excluded from **both** numerator and denominator, and an id listed in `coverage_function_ids` that falls outside the filtered denominator set contributes nothing at all. That tolerance is arithmetic only. At the moment an option is proposed or revised, every id supplied in `coverage_function_ids` must itself name a duty that is `ACTIVE`, is flagged `is_essential`, and belongs to the case's pinned profile; one that does not is refused with `ERR_FUNCTION_NOT_IN_PINNED_PROFILE`. The tolerance therefore bites only for a duty that was legitimately covered when it was named and has since been retired or made marginal — which is also why the assessment-time re-check of §3.6 tests only `ACTIVE` and profile ownership and deliberately does not re-test `is_essential`. When the denominator set is empty — a pinned profile with no live essential duties — the ratio is exactly `1.000000` rather than an error or a zero. This same computation runs on option creation, on option revision, and again on every case-pinned option whenever a duty on the profile is revised.

The threshold that gives `coverage_ratio` teeth is **0.60**: an accommodation that covers less than sixty percent of pinned essential weight may not be granted, as §3.7 spells out.

**Revising an option.** An `AccommodationCoordinator`, and only a coordinator, may revise an option's `one_time_cost_cents`, `recurring_monthly_cost_cents`, `implementation_days` or `coverage_function_ids`. Revision is permitted only while the case is in stage `HARDSHIP_REVIEW` and only against an option whose own status is `PROPOSED` or `HARDSHIP_BLOCKED`; an attempt while the case sits elsewhere, or against an option in any other status, is refused with `ERR_OPTION_NOT_ASSESSABLE`. Whatever the option's starting status, revision recomputes both `option_net_cost_cents` and `coverage_ratio` and increments the option's `version`. From `PROPOSED` the revision is a self-loop: the status stays `PROPOSED`, but the version still advances, which is exactly what invalidates a concurrency token a finance officer may already be holding. From `HARDSHIP_BLOCKED` the revision is a genuine cycle back into the assessment queue: the option returns to `PROPOSED`, the case's `blocked_option_count` is decremented, and the option's current undue-hardship assessment is moved to `SUPERSEDED`. Options on a case are listable with a `status` filter, and any option is readable individually together with its net cost, coverage ratio and committed amount.

Exploration ends when the coordinator advances the case from `OPTION_EXPLORATION` to `HARDSHIP_REVIEW`, which requires at least one option on the case in `PROPOSED` or `CLEARED`. A case with nothing on the table is refused with `ERR_NO_OPTIONS_PROPOSED`.

### 3.6. Undue Hardship and the Clearing Fork

Only a `FinanceOfficer` may assess undue hardship, and doing so is that role's exclusive act. The officer names the option and supplies just two inputs: `assessment_basis`, which is either `EMPLOYER_WIDE` or `SITE_LOCAL`, and `expected_option_version`, the concurrency token from §2.7. The assessment stamps `assessor_user_id` from the acting `X-User-ID` and takes its `option_id` from the option being addressed. Three preconditions gate the write: the case must be in stage `HARDSHIP_REVIEW`, every duty referenced by the option's `coverage_function_ids` must still be `ACTIVE` and must still belong to the case's pinned `job_profile_id` (otherwise `ERR_FUNCTION_NOT_IN_PINNED_PROFILE`), and the supplied version must match. An assessment against an option whose status does not admit one, or against a case outside `HARDSHIP_REVIEW`, is refused with `ERR_OPTION_NOT_ASSESSABLE`.

The score is a weighted blend of three normalised pressures, computed in a pinned order over exactly one option and the job profile pinned on its case. Sibling options and other cases never enter the arithmetic.

1. **Snapshot the cost.** `assessed_net_cost_cents` is a copy of the option's `option_net_cost_cents` taken at assessment time; a later revision of the option never rewrites it.
2. **Choose the denominator.** `denominator_cents` is the pinned profile's `employer_annual_budget_cents` when `assessment_basis` is `EMPLOYER_WIDE`, and the pinned profile's `department_annual_budget_cents` when it is `SITE_LOCAL`.
3. **Budget ratio.** `budget_ratio` is `assessed_net_cost_cents` divided by `denominator_cents`, rounded half up to six decimal places.
4. **Normalise the budget pressure.** Divide `budget_ratio` by a cap of **0.05** — five percent of the applicable budget is treated as the point of maximum cost pressure — multiply by 100, round half up to four decimal places, and then take the smaller of that figure and `100.0000`. The result is `budget_ratio_norm`.
5. **Disruption.** `disruption_index` is the uncovered share of essential weight on the same scale: subtract the option's `coverage_ratio` from 1, multiply by 100, and round half up to four decimal places.
6. **Lag.** Divide the option's `implementation_days` by a cap of **60 days**, multiply by 100, round half up to four decimal places, and take the smaller of that figure and `100.0000`. The result is `lag_norm`.
7. **Pre-credit score.** `raw_hardship_score` is `budget_ratio_norm` multiplied by **0.65**, plus `disruption_index` multiplied by **0.20**, plus `lag_norm` multiplied by **0.15**, with the sum rounded half up to two decimal places.
8. **Mitigation credit.** `mitigation_credit_rate` is selected from a band read off `raw_hardship_score`. When `raw_hardship_score` is below `40.00` the rate is `0.00`. When it is at least `40.00` but below `65.00` the rate is `0.10`. When it is at least `65.00` but below `85.00` the rate is `0.05`. When it is `85.00` or above the rate is `0.00`. The tier is read from the **pre-credit** figure, always; it is never re-selected from the post-credit figure even when the credit pushes the score down into a lower band, and the credit is applied exactly once.
9. **Final score.** `hardship_score` is `raw_hardship_score` multiplied by one minus `mitigation_credit_rate`, rounded half up to two decimal places.
10. **Verdict.** `hardship_verdict` is `UNDUE` when `hardship_score` is at least `70.00`; otherwise `BORDERLINE` when `hardship_score` is at least `45.00`; otherwise `NOT_UNDUE`.

The two bases are not cosmetic variants. Under `SITE_LOCAL` the accommodation is charged against the owning department alone, and because `department_annual_budget_cents` is the far smaller figure, `budget_ratio_norm` frequently saturates at the `100.0000` cap and the option scores `UNDUE`. Under `EMPLOYER_WIDE` — the basis the ADA generally contemplates for a large employer, because the employer's total resources are what count — the identical option divided by `employer_annual_budget_cents` collapses toward zero on the cost dimension and routinely scores `NOT_UNDUE`. Same option, same coverage, same lead time: divergent verdict, and divergent option status.

Every assessment is created in `status` `CURRENT` and moves any prior `CURRENT` assessment on the same option to `SUPERSEDED`; assessments on an option are listable with a `status` filter. The verdict then drives a two-way fork on the option, and the two branches are deliberately asymmetric in which counter they move:

- **Branch A — cleared.** A verdict of `NOT_UNDUE` or of `BORDERLINE` moves the option `PROPOSED → CLEARED`, increments the case's `cleared_option_count` by one, and increments the option's `version` by one. The case's `blocked_option_count` does not move.
- **Branch B — blocked.** A verdict of `UNDUE` moves the option `PROPOSED → HARDSHIP_BLOCKED`, increments the case's `blocked_option_count` by one, and increments the option's `version` by one. The case's `cleared_option_count` does not move, and the case can no longer reach `DECISION_PENDING` through this option.

Hardship review resolves in one of two directions. When no option on the case remains `PROPOSED` and `cleared_option_count` is at least 1, an `AccommodationCoordinator` advances the case from `HARDSHIP_REVIEW` to `DECISION_PENDING`; an advance attempted while an option is still awaiting assessment, or with `cleared_option_count` at zero, is refused with `ERR_OPTION_ASSESSMENT_PENDING`. When instead no option remains `PROPOSED` and `cleared_option_count` is zero — every proposal was ruled an undue hardship — the parties must keep talking: the coordinator advances the case back from `HARDSHIP_REVIEW` to `OPTION_EXPLORATION`, which increments `interactive_round_count` by one. That re-entry is capped. A case may re-enter `OPTION_EXPLORATION` at most **twice** over its lifetime; a transition that would push `interactive_round_count` past two is refused with `ERR_INTERACTIVE_ROUND_LIMIT`. The same cap governs every other re-entry into `OPTION_EXPLORATION` described later in this document.

### 3.7. The Decision, the Trial Period and Effectiveness Review

Recording the outcome of the interactive process belongs to the `AccommodationCoordinator` alone. The coordinator supplies a `decision` of `GRANT_WITH_TRIAL`, `GRANT_PERMANENT` or `DENY`, together with whichever of `selected_option_id`, `denial_basis`, `rationale_text` and `alternative_option_id` the chosen outcome requires.

**Granting.** Both grant outcomes are reachable only from stage `DECISION_PENDING`, and both require that `selected_option_id` names an option on this case whose status is `CLEARED` and whose `coverage_ratio` is at least 0.60. An option that leaves too much essential weight uncovered is refused with `ERR_ESSENTIAL_FUNCTION_UNCOVERED`; an option that sits in `HARDSHIP_BLOCKED` is refused with `ERR_OPTION_HARDSHIP_BLOCKED`. Those two codes are reserved for exactly those two faults: a `selected_option_id` naming an option that belongs to some other case, or one whose status is neither `CLEARED` nor `HARDSHIP_BLOCKED`, never reaches either check and is refused earlier as `ERR_INVALID_STAGE_TRANSITION`. When both faults are present on the same request, the coverage failure is the one reported, because it is evaluated first.

A `GRANT_WITH_TRIAL` decision moves the chosen option `CLEARED → SELECTED`; a `GRANT_PERMANENT` decision moves it `CLEARED → IMPLEMENTED`. In both branches the identical fiscal cascade runs: the option's `committed_cost_cents` is set to its `option_net_cost_cents`, and that amount is added to the pinned profile's `committed_accommodation_cost_cents`. In both branches every *other* option on the case still sitting in `CLEARED` is moved to `SHELVED`, and the case's `cleared_option_count` is recomputed to match. In both branches the case's `decision` and `selected_option_id` are written, and the renewal cadence is computed. The two branches differ only in the option status and in where the case lands: `GRANT_WITH_TRIAL` moves the case `DECISION_PENDING → TRIAL_SETUP`, while `GRANT_PERMANENT` moves it `DECISION_PENDING → GRANTED_PERMANENT`.

**The renewal cadence.** Every grant fixes how often the accommodation will be revisited, and the rule is *shortest applicable interval wins*. Begin with a baseline of **365 days** — one review a year. If the selected option's current undue-hardship assessment carries a `hardship_verdict` of `BORDERLINE`, a **180-day** interval also applies. If the case's `absence_record_id` is non-null and that absence record's `status` is anything other than `CLOSED`, a **90-day** interval also applies. If the recorded `decision` is `GRANT_WITH_TRIAL`, a **120-day** interval also applies. `review_cadence_days` is the smallest of whichever intervals apply, and `review_due_date` is the current logical-clock date plus that many days. This computation runs on the grant that creates the trial, on the grant that goes straight to permanent, on the conclusion of an effective trial, and on a reversal at appeal.

**Denying.** A `DENY` decision from `DECISION_PENDING` requires a `denial_basis` — one of `UNDUE_HARDSHIP`, `DIRECT_THREAT`, `NOT_QUALIFIED`, `NO_DISABILITY_NEXUS`, `INSUFFICIENT_DOCUMENTATION` and `FAILURE_TO_COOPERATE` — and a non-empty `rationale_text`. An `alternative_option_id` may optionally be supplied to record an alternative accommodation offered alongside the denial; when supplied it must name an option on this case whose status is `CLEARED`, and one that does not is refused with `ERR_INVALID_STAGE_TRANSITION`. The denial creates a denial record in `status` `ISSUED`, carrying `issued_by_user_id` from the acting `X-User-ID` (which is the comparand the segregation-of-duties rule later uses), `issued_at` from the logical clock, `appeal_count` at zero, and `rejected_option_ids` listing, in `created_at` ascending order, the ids of every option on the case whose status was `CLEARED` or `HARDSHIP_BLOCKED` at that moment. `appeal_deadline_date` is set to the issuance date plus **30 days**; appeals must be filed on or before that date. The case moves to stage `DENIED` with `decision` `DENY`, and the employee's `lifetime_denial_count` is incremented by one. Like every other outcome of this endpoint, a denial answers with HTTP 200 carrying the updated `AccommodationRequest` — never the freshly minted denial record, which is read back from `/denial-records`. Denials are readable individually and listable with filters on `request_id`, `alternative_option_id` and `status`.

**Scheduling the trial.** Only an `AccommodationCoordinator` schedules a trial period, naming `request_id` and `option_id` and giving an inclusive `start_date` and an inclusive `end_date` that must not fall before the start. Two optional inputs tune the trial: `checkin_cadence_days`, the nominal spacing between effectiveness check-ins, defaulting to 14 and constrained to 1 through 90 inclusive; and `scoring_mode`, which is `CUMULATIVE_MEAN` or `LATEST_WEIGHTED` and defaults to `LATEST_WEIGHTED`. The trial copies `employee_id` from the case — that employee, not the case, is the resource against which trial windows are deconflicted — and is created in `status` `SCHEDULED` with `review_count` at zero, `extension_count` at zero, `outcome` `PENDING` and `effectiveness_score` null. The case moves `TRIAL_SETUP → TRIAL_ACTIVE`. The named `option_id` must be the case's own `selected_option_id` and that option's status must be `SELECTED`; a case outside `TRIAL_SETUP`, an `option_id` that is not the case's selected option, and a selected option in any other status are all refused with `ERR_INVALID_STAGE_TRANSITION`, checked before the three deconfliction rules below.

Three deconfliction rules guard the schedule, and they are evaluated in this order. First, **trial windows are closed intervals with a mandatory washout gap of 7 days**. The server gathers every trial period belonging to the same `employee_id` in *any* status — `SCHEDULED`, `ACTIVE`, `UNDER_REVIEW`, `CONCLUDED_EFFECTIVE`, `CONCLUDED_INEFFECTIVE` and `ABORTED` alike, no status is exempt — and the candidate collides with such a trial when the candidate's `start_date` is on or before that trial's `end_date` plus seven days **and** the candidate's `end_date` is on or after that trial's `start_date` minus seven days. Because both comparisons are inclusive, a candidate starting exactly seven days after a prior trial's `end_date` still collides; the earliest legal start is eight days after the prior end. A collision is refused with `ERR_TRIAL_WINDOW_CONFLICT`. Second, **continuous leave blocks a trial outright**: if any absence record for that employee whose `record_type` is `FMLA_CONTINUOUS` or `STATE_LEAVE` is in `status` `ACTIVE` and overlaps the candidate interval, the schedule is refused with `ERR_TRIAL_BLOCKED_BY_ABSENCE`. The overlap test honours each side's own endpoint convention — the absence's `end_date` is exclusive while the trial's is inclusive — so the two collide exactly when the candidate's `start_date` is strictly before the absence's `end_date` and the candidate's `end_date` is on or after the absence's `start_date`. Third, **a workers'-compensation cross-reference must be on modified duty**: if the case's `absence_record_id` names a `WC_RESTRICTION` record, that record's `status` must be `MODIFIED_DUTY` before any trial may begin, and otherwise the schedule is refused with `ERR_WC_MODIFIED_DUTY_REQUIRED`. Trials are readable individually and listable with filters on `request_id`, `option_id`, `employee_id` and `status`.

Once scheduled, a trial is activated by the daily sweep as soon as the logical date reaches its `start_date`, moving it `SCHEDULED → ACTIVE`.

**Effectiveness check-ins.** A `Manager`, the case's own `Employee`, or an `AccommodationCoordinator` may record a check-in against a trial that is in `ACTIVE` or `UNDER_REVIEW` — any other status is refused with `ERR_TRIAL_NOT_RESOLVABLE`, the same state-machine code the resolve endpoint uses — supplying `employee_rating` and `manager_rating`, each an integer from 0 to 10 inclusive, and `objective_metric_pct`, an integer from 0 to 100 inclusive representing productivity attainment. The check-in stamps `trial_period_id` from the trial being addressed, `reviewer_user_id` from the acting `X-User-ID`, `review_date` as the calendar date read from the logical clock, and `review_index`, a 1-based ordinal assigned in recording order within the trial. Check-ins are append-only journal rows: as noted in §2.4, they carry `id` and `created_at` and nothing else from the common set. They are listable per trial.

Each check-in immediately computes its own `review_composite`, a blended score on a 0-to-10 scale: average `employee_rating` and `manager_rating`, multiply that average by **0.6**, then add `objective_metric_pct` divided by 10 and multiplied by **0.4**, and round the total half up to four decimal places.

The trial's `effectiveness_score` is then recomputed from the whole set of that trial's check-ins, ordered by `review_date` ascending with ties broken by `created_at` ascending. With no check-ins at all the score is null. With at least one, the two `scoring_mode` variants diverge:

- Under **`CUMULATIVE_MEAN`**, the score is the unweighted mean of `review_composite` across every check-in on the trial — their sum divided by their count — rounded half up to two decimal places. An improving trial is dragged down by its early poor scores under this mode and can land below the effectiveness bar.
- Under **`LATEST_WEIGHTED`**, only the three most recent check-ins count. Take the last three in the ordering above (or all of them if fewer than three exist) and re-index them so that position one is the latest check-in, position two the next-latest and position three the third-latest. The nominal recency weights are **0.5, 0.3 and 0.2** in that order. Take as many of those weights as there are check-ins in the tail and renormalise them by dividing each by their own sum, so that with two check-ins the weights become 0.5 and 0.3 each divided by 0.8, and with a single check-in the weight is 1. Multiply each check-in's `review_composite` by its renormalised weight, add the products, and round half up to two decimal places. The identical set of check-ins on an improving trial can land at or above the bar under this mode while falling below it under the other — same reviews, divergent score, divergent permitted outcome.

Every check-in on this trial participates, including check-ins recorded before an extension; an extension never discards reviews, and reviews from other trials never intrude.

A trial reaches `UNDER_REVIEW` in one of two ways: recording the **third** check-in moves it `ACTIVE → UNDER_REVIEW`, and so does the daily sweep once the logical date reaches its `end_date`. Either way `effectiveness_score` is recomputed under the trial's `scoring_mode` at that moment.

**Resolving the trial.** An `AccommodationCoordinator` closes out or extends a trial by supplying an `outcome` of `EFFECTIVE`, `INEFFECTIVE`, `EXTEND` or `ABORT`. Any outcome requested from a status that does not admit it is refused with `ERR_TRIAL_NOT_RESOLVABLE`. Three shared guards then apply to the two terminal judgements: the trial must be in `UNDER_REVIEW`; `review_count` must be at least **3**, and fewer is refused with `ERR_INSUFFICIENT_TRIAL_REVIEWS`; and the requested outcome must agree with the computed score against a bar of **7.00** — `EFFECTIVE` requires `effectiveness_score` at or above 7.00, `INEFFECTIVE` requires it strictly below 7.00 — with disagreement refused as `ERR_TRIAL_OUTCOME_MISMATCH`.

An `EFFECTIVE` resolution sets the trial to `CONCLUDED_EFFECTIVE` with `outcome` `EFFECTIVE`, moves the trialed option `SELECTED → IMPLEMENTED` while **leaving its `committed_cost_cents` untouched** — the money was already committed at selection and stays committed — moves the case `TRIAL_ACTIVE → GRANTED_PERMANENT`, and recomputes `review_cadence_days` and `review_due_date` under the cadence rule above.

An `INEFFECTIVE` resolution additionally requires that the case's `interactive_round_count` can absorb one more re-entry into option exploration, and otherwise fails with `ERR_INTERACTIVE_ROUND_LIMIT`. It then triggers a five-hop transitive cascade, where each hop is caused by the hop above it rather than by the resolve request itself. Hop one sets the trial to `CONCLUDED_INEFFECTIVE` with `outcome` `INEFFECTIVE`. Hop two, caused by hop one, moves the trialed option `SELECTED → TRIAL_FAILED` and releases its `committed_cost_cents` to zero. Hop three, caused by hop two, subtracts that released amount from the pinned profile's `committed_accommodation_cost_cents`. Hop four, also caused by hop two, moves the case `TRIAL_ACTIVE → OPTION_EXPLORATION`, increments `interactive_round_count` by one, and raises the case's `medical_doc_request_limit` by the ineffective-trial bonus of one round — still subject to the absolute ceiling of four. Hop five, caused by hop four, recomputes `documentation_budget_remaining` from the raised limit.

An `EXTEND` resolution is available only from `UNDER_REVIEW` and only while `extension_count` can absorb one more; a trial may be extended at most **once**, and a second attempt is refused with `ERR_TRIAL_EXTENSION_LIMIT`. Extension increments `extension_count`, pushes `end_date` out by **30 days**, and returns the trial `UNDER_REVIEW → ACTIVE` so that further check-ins can be recorded.

An `ABORT` resolution is available from `SCHEDULED`, from `ACTIVE` and from `UNDER_REVIEW`, with identical effects from all three: the trial becomes `ABORTED` with `outcome` `ABORTED`, and the case returns from `TRIAL_ACTIVE` to `TRIAL_SETUP` with the selected option left in `SELECTED` and its `committed_cost_cents` intact, ready for a fresh trial to be scheduled. Note that an aborted trial still occupies its calendar interval for washout purposes, so the replacement trial must clear the seven-day gap around it.

### 3.8. Denial, Appeal and Remand

A denied employee has thirty days to contest, counted by the `appeal_deadline_date` stamped on the denial record. Filing is the `Employee` role's exclusive act and only the case's own employee may file. The filer supplies `grounds_text`, their stated grounds. Three conditions gate the filing: the denial record's `status` must still be `ISSUED`, otherwise `ERR_DENIAL_NOT_APPEALABLE`; the current logical-clock date must be on or before `appeal_deadline_date`, otherwise `ERR_APPEAL_WINDOW_CLOSED`; and the case must not be sealed. A successful filing creates an appeal in `status` `FILED` with `outcome` `PENDING`, `supplement_count` at zero, `stay_count` at zero, `appeal_officer_user_id` null, `filed_by_user_id` taken from the acting `X-User-ID`, `filed_at` read from the logical clock, and `denial_record_id` taken from the denial being addressed. The denial record moves `ISSUED → APPEALED` with `appeal_count` incremented by one, and the case moves `DENIED → UNDER_APPEAL`. Appeals are readable individually and listable per denial with a `status` filter.

If nobody appeals, the denial becomes permanent on its own. The daily sweep finalises any denial record still in `ISSUED` whose `appeal_count` is zero once the logical date has passed strictly beyond `appeal_deadline_date`: the record moves `ISSUED → FINAL`, the case moves `DENIED → DENIED_FINAL`, and the employee's `open_case_count` is decremented by one.

**Segregation of duties.** An `AppealOfficer` may not review their own handiwork. On every appeal action and every appeal decision, the acting officer's `X-User-ID` must differ from the `issued_by_user_id` recorded on the denial under appeal, **and** must differ from every `manager_id` that signed an analysis in `status` `RECORDED` on the underlying case. A violation of either comparison is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

**Non-terminal appeal moves.** An appeal progresses through an `action` of `START_REVIEW`, `REQUEST_SUPPLEMENT` or `SUBMIT_SUPPLEMENT`, and any action not reachable from the appeal's current status is refused with `ERR_APPEAL_NOT_ACTIONABLE`. Each action also belongs to exactly one of this endpoint's two permitted roles — `START_REVIEW` and `REQUEST_SUPPLEMENT` to the `AppealOfficer`, `SUBMIT_SUPPLEMENT` to the `Employee` — and an action attempted by the other permitted role draws that same `ERR_APPEAL_NOT_ACTIONABLE` rather than a role or ownership code. An `AppealOfficer` takes an appeal in `FILED` under review with `START_REVIEW`, which requires that the case's `confidentiality_posture` is not `SEALED` and that the officer is not the coordinator who issued the denial; the appeal moves `FILED → UNDER_REVIEW` and `appeal_officer_user_id` is stamped from the acting `X-User-ID`. From `UNDER_REVIEW` the same officer may ask for more material with `REQUEST_SUPPLEMENT`, moving the appeal `UNDER_REVIEW → SUPPLEMENT_REQUESTED`; this is allowed only while `supplement_count` is still below the ceiling of **two**. The case's own `Employee` then answers with `SUBMIT_SUPPLEMENT`, which requires that `X-User-ID` equals the case's `employee_id` and that `supplement_count` can absorb one more round; it increments `supplement_count` by one and returns the appeal `SUPPLEMENT_REQUESTED → UNDER_REVIEW`. That loop is the negotiation inside the appeal, and it may run at most twice; a third supplement round in either direction is refused with `ERR_APPEAL_SUPPLEMENT_LIMIT`.

**Terminal appeal decisions.** An `AppealOfficer` closes an appeal with an `outcome` of `UPHOLD`, `REVERSE`, `REMAND` or `DISMISS`. The first three are reachable only from `UNDER_REVIEW` and only by the officer whose `X-User-ID` matches the appeal's own `appeal_officer_user_id`; `DISMISS` is additionally reachable from `FILED`, and is not bound to the stamped officer at all. A decision taken from a status that does not admit it, one of the first three taken by an officer other than the stamped one, and a `REVERSE` whose denial carries no `alternative_option_id` or names one outside `CLEARED` and `SHELVED` are all refused with `ERR_APPEAL_NOT_ACTIONABLE`.

`UPHOLD` is the outcome the integrity score can veto. It requires that the case's `interactive_process_integrity_score` is at least **60**; when the score has fallen below that threshold, the employer's own process failed and the appeal must be remanded rather than upheld, so the request is refused with `ERR_APPEAL_MUST_REMAND`. A permitted `UPHOLD` sets the appeal to `UPHELD` with `outcome` `UPHELD`, moves the denial record `APPEALED → FINAL`, moves the case `UNDER_APPEAL → DENIED_FINAL`, and decrements the employee's `open_case_count` by one.

`DISMISS` requires only that the acting officer is not the coordinator who issued the denial. It sets the appeal to `DISMISSED` with `outcome` `DISMISSED`, moves the denial record to `FINAL`, and returns the case from `UNDER_APPEAL` to stage `DENIED` — note that it lands on `DENIED`, not on `DENIED_FINAL`, so the sweep's finalisation path is what eventually retires the case.

`REVERSE` requires that the denial's `alternative_option_id` is non-null and that the option it names is currently in `CLEARED` or in `SHELVED`. It sets the appeal to `REVERSED` with `outcome` `REVERSED`; moves the denial record `APPEALED → VACATED` and decrements the employee's `lifetime_denial_count` by one; moves the alternative option to `IMPLEMENTED`, sets that option's `committed_cost_cents` to its `option_net_cost_cents` and adds that amount to the pinned profile's `committed_accommodation_cost_cents`; moves the case `UNDER_APPEAL → GRANTED_PERMANENT` with `decision` `GRANT_PERMANENT` and `selected_option_id` set to the alternative option; and computes `review_cadence_days` and `review_due_date` under the cadence rule of §3.7.

`REMAND` requires that the case's `interactive_round_count` can absorb one more re-entry into option exploration, and otherwise fails with `ERR_INTERACTIVE_ROUND_LIMIT`. It then triggers a five-hop transitive cascade in which each hop is caused by the hop above it rather than by the decision itself. Hop one sets the appeal to `REMANDED` with `outcome` `REMANDED`. Hop two, caused by hop one, moves the denial record `APPEALED → VACATED`. Hop three, caused by hop two, decrements the employee's `lifetime_denial_count` by one and moves the case `UNDER_APPEAL → OPTION_EXPLORATION` with `interactive_round_count` incremented by one. Hop four, caused by hop three, resets every option on the case currently in `HARDSHIP_BLOCKED` back to `PROPOSED` and sets the case's `blocked_option_count` to zero. Hop five, caused by hop four, moves every undue-hardship assessment belonging to one of those reset options and currently in `status` `CURRENT` to `SUPERSEDED` — the case returns to exploration with its financial verdicts wiped, so the options must be assessed afresh.

### 3.9. Renewal Cadence, Disclosure Logging and the Integrity Score

An accommodation in force is not finished business. Once the daily sweep observes that a case in `GRANTED_PERMANENT` has reached its `review_due_date`, it moves the case to stage `RENEWAL_DUE`, and an `AccommodationCoordinator` must work it. The coordinator supplies an `outcome` of `CONTINUE`, `MODIFY`, `CLOSE` or `RENEW_SUCCESSOR`, together with `expected_request_version` as described in §2.7. The case must be sitting in `RENEWAL_DUE`, and one that is not is refused with `ERR_INVALID_STAGE_TRANSITION` ahead of the version token; the seal of §2.10 then blocks all four outcomes alike. All four outcomes increment `review_cycle_index` by one and increment the case's `version` by one, and all four answer with HTTP 200 carrying this case — `RENEW_SUCCESSOR` included, which returns the predecessor rather than the successor it minted; they differ in everything else.

- **`CONTINUE`** re-arms the cadence: the accommodation stands as it is, `review_due_date` is set to the current logical-clock date plus the standing `review_cadence_days`, and the case returns `RENEWAL_DUE → GRANTED_PERMANENT`. As with the other three outcomes, the case must not be sealed.
- **`MODIFY`** reopens the negotiation: the case moves `RENEWAL_DUE → OPTION_EXPLORATION` and `interactive_round_count` is incremented by one, subject as always to the two-round ceiling and otherwise refused with `ERR_INTERACTIVE_ROUND_LIMIT`.
- **`CLOSE`** retires the matter, with no precondition of its own. The case moves `RENEWAL_DUE → CLOSED`; the selected option is set to `IMPLEMENTED` with its `committed_cost_cents` released to zero and that released amount subtracted from the pinned profile's `committed_accommodation_cost_cents`; and the employee's `open_case_count` is decremented by one.
- **`RENEW_SUCCESSOR`** keeps the current case in `RENEWAL_DUE` — this outcome is a self-loop — while opening a fresh case for the next period. The successor is created in stage `INTAKE` with its `renewal_of_request_id` pointing back at this case, and because it is a renewal it starts with a documentation ceiling of the base two rounds plus the renewal bonus of one, giving `medical_doc_request_limit` of three. It carries `request_channel`, `requested_accommodation_text`, `disability_obvious` and `absence_record_id` forward unchanged from the case it succeeds, and takes the ordinary intake birth values of §3.3 for everything else. Its job architecture is pinned afresh rather than inherited: the successor pins the employee's current `job_profile_id` and that profile's `profile_version_label` when that profile is `PUBLISHED`, and falls back to the predecessor's own pinned profile and label when it is not — `ERR_PROFILE_NOT_PUBLISHED` is never raised on this path. The employee's `open_case_count` is incremented by one, so this outcome is available only while the employee has room under the two-open-case ceiling; otherwise it is refused with `ERR_OPEN_CASE_LIMIT`.

**The disclosure log.** Every time medical information about a case leaves the medical-review firewall, a row is appended to that case's disclosure log by an `AccommodationCoordinator`, a `MedicalReviewOfficer` or a `ComplianceAuditor`. The logger supplies `disclosed_to_role` — one of `Manager`, `AccommodationCoordinator`, `MedicalReviewOfficer`, `FinanceOfficer`, `AppealOfficer`, `ComplianceAuditor` and `EXTERNAL` — plus `disclosed_to_user_id` identifying the recipient, a `disclosure_purpose` drawn from `FUNCTION_ANALYSIS`, `HARDSHIP_ASSESSMENT`, `APPEAL_REVIEW`, `AUDIT`, `SAFETY_EMERGENCY` and `OTHER`, and `fields_disclosed`, a non-empty array whose members come from the same seven medical categories used for documentation scope. The row records `logged_by_user_id` from the acting `X-User-ID` and takes its `request_id` from the case being addressed. Like effectiveness check-ins, disclosure rows are append-only and carry only `id` and `created_at` from the common property set.

The log **always accepts the row**, and always with HTTP 201. An impermissible disclosure is not rejected; it is recorded, because a breach that the system refuses to write down is a breach nobody can audit. What the server computes is `authorized`, a boolean judged from exactly two inputs — `disclosed_to_role` and `fields_disclosed` — and from nothing else:

- Disclosure to a `MedicalReviewOfficer` or to a `ComplianceAuditor` is always authorized; these two roles see everything.
- Disclosure to an `AccommodationCoordinator` is authorized when every member of `fields_disclosed` is drawn from `functional_limitations`, `work_restrictions`, `restriction_duration`, `prognosis` and `accommodation_needed`.
- Disclosure to a `Manager` is authorized when every member of `fields_disclosed` is drawn from the narrower set of `work_restrictions`, `restriction_duration` and `accommodation_needed`.
- Disclosure to a `FinanceOfficer` is authorized only when `fields_disclosed` contains nothing beyond `accommodation_needed`.
- Disclosure to an `AppealOfficer` is authorized under the same five-category set permitted to an `AccommodationCoordinator`.
- Disclosure to `EXTERNAL` is never authorized.

Whenever `authorized` comes out false, the seal cascade fires. Hop one is the appended log row itself. Hop two, caused by hop one, drives the case's `confidentiality_posture` to `SEALED` — from `STANDARD` or from `RESTRICTED` alike — and recomputes the case's `interactive_process_integrity_score`. Hop three, caused by hop two, stays the appeal track: every appeal on this case currently in `UNDER_REVIEW` is moved to `SUPPLEMENT_REQUESTED` and has its `stay_count` incremented by one. From that point every mutating case-scoped operation is refused with `ERR_CASE_SEALED` until an auditor intervenes. The log is readable by the same three roles and filterable on `authorized`.

**Unsealing.** A `ComplianceAuditor`, exclusively, may override the posture by supplying a `to_posture` of `RESTRICTED`, which is permitted only while the case is currently `SEALED` and moves it `SEALED → RESTRICTED`; an override aimed at a case that is `STANDARD` or already `RESTRICTED` is refused with `ERR_INVALID_STAGE_TRANSITION`. Unsealing restores the ability to work the case. It does **not** restore the integrity score: disclosure penalties are permanent.

**The integrity score.** `interactive_process_integrity_score` is the case's compliance grade for how the employer conducted the interactive process. It starts from a base of **100** and subtracts four penalties, then floors the result at **0** so it can never go negative. The four penalties are computed as follows over all documentation rounds and all disclosure rows on the case, in every status:

- **Documentation overreach.** Count the case's `medical_doc_request_count` and subtract the base allowance of two, taking zero if the difference is negative. Each such excess round costs **25 points** — so a case that issued three rounds loses 25, and a case at the absolute ceiling of four loses 50.
- **Unauthorized disclosure.** Count the disclosure rows on the case whose `authorized` is false. Each one costs **30 points**.
- **Lapsed documentation window.** Count the documentation rounds on the case whose `status` is `EXPIRED`. Each one costs **10 points**.
- **Missed renewal.** If the case is currently in stage `RENEWAL_DUE` and the current logical-clock date is strictly later than `review_due_date` plus a grace period of **30 days**, a single flat penalty of **15 points** applies; otherwise this penalty is zero.

Subtract the sum of those penalties from 100 and take the larger of the result and 0. The score is recomputed whenever a documentation round is created, withdrawn or expired, whenever an *unauthorized* disclosure row is appended — the recomputation rides on the seal cascade, so an authorized row, which by construction changes none of the four penalty inputs, does not trigger one and does not pick up a missed-renewal penalty that has accrued since the last recomputation — and in the sweep's final phase for every case touched by documentation expiry or by a renewal-due promotion. Penalties are permanent in a strong sense: unsealing the case, withdrawing an already-expired round, or closing the case out entirely never restores points that were deducted for an unauthorized disclosure or a lapsed window. This is what gives the score its authority at appeal — a case whose score has fallen below 60 cannot have its denial upheld.
