# Clinical Decision Support Governance API — Product Requirements Document

## 1. Introduction

A health system's clinical informatics committee sits at an uncomfortable intersection. On one side are clinicians who want an order set or an interruptive alert built quickly, because they have just watched a preventable harm event. On the other side is the accumulated weight of everything the committee has already published: hundreds of order sets pinned to drug-interaction content that a vendor refreshes every quarter, and alerts that fire tens of thousands of times a year and are overridden almost every time. Today that governance runs on spreadsheets, meeting minutes and institutional memory. Nobody can answer, on demand, which published order sets are pinned to superseded interaction content, which alerts have earned retirement, or whether the clinician who approved a build was the same person who wrote it.

This document specifies the Clinical Decision Support Governance API, mounted under `/cds`, which turns that committee process into an auditable system of record. The API carries a content request from intake — with a named clinical sponsor and graded evidence citations — through committee triage, order set and alert construction, peer review and specialty approval under an explicit quorum, publication or activation, post-implementation adherence measurement, and finally annual re-attestation, expiration and archival. Alongside that spine it governs the vendor content update cycle for drug-interaction and dosing rules, monitors alert burden in closed measurement windows so that low-value firings can be retired on evidence rather than anecdote, and models scheduled downtime so that decision support content behaves predictably read-only when the EHR is unavailable.

Two design commitments run through everything that follows. First, **segregation of duties is enforced by data, not by policy**: a clinician may legitimately hold several committee roles, so every governance step compares the caller's identity against the identities already recorded on the artifact. Second, **every derived number is reproducible**: priority scores, quorum thresholds, burden indices, adherence percentages and review dates are all computed from stored inputs by the rules in this document, with the rounding discipline stated exactly, so that two implementations of this specification agree to the last decimal place.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contracts: authentication, response shape, pagination, common properties, precision, concurrency control, the order in which rejections are evaluated, and the cross-cutting governance principles that no single workflow owns.

### 2.1. Committee Identity and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, naming the acting principal, and `X-User-Role`, declaring the capacity in which that principal is acting. A request that omits either header, or whose `X-User-ID` names no registered clinician, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This check runs before everything else — before path resolution included — so an unauthenticated call against an identifier that does not exist returns 401 and never 404.

The system recognises exactly seven roles: `ClinicalSponsor`, `InformaticsBuilder`, `PeerReviewer`, `SpecialtyApprover`, `CommitteeChair`, `PharmacyInformaticist`, and `SystemAdmin`. Once the caller is authenticated, the declared role is checked against the roles permitted for the endpoint; a caller whose committee roles contain nothing permitted for that endpoint is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Role authorization likewise precedes path resolution, so a wrong-role call against a non-existent identifier returns 403 and not 404. Where the endpoint table in §4 lists "Any role" it means all seven roles are permitted.

Six of the seven roles are backed by a persisted clinician record. When `X-User-Role` is `ClinicalSponsor`, `InformaticsBuilder`, `PeerReviewer`, `SpecialtyApprover`, `CommitteeChair`, or `PharmacyInformaticist`, the `X-User-ID` header is the `id` of the acting `Clinician`; ownership checks on any resource that references a `Clinician` compare that resource's clinician-reference field to `X-User-ID`. Concretely, a sponsor resubmission compares `X-User-ID` to the request's `clinical_sponsor_id`, a vote cast compares it to the assignment's `reviewer_id`, and an annual attestation compares it to the `clinical_sponsor_id` of the content request that governs the artifact. Furthermore, a clinician may only act in a capacity their record grants: the role in `X-User-Role` must be a member of that clinician's `authorized_roles` array, and a clinician whose `authorized_roles` does not include the declared role is rejected with `ERR_UNAUTHORIZED`. Because one clinician may legitimately hold several of these roles, passing the role check is never sufficient on its own — see §2.10.

`SystemAdmin` is different. When `X-User-Role` is `SystemAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the literal principal `SYSTEM_ADMIN` is accepted for the `SystemAdmin`-only endpoints. The server may record that opaque value — it is stored as `declared_by_user_id` on a `DowntimeEvent` when the operator schedules one — but it never compares it to any clinician's `id`, and `SystemAdmin` never appears in any clinician's `authorized_roles`.

Where an endpoint binds the actor to a stored identity and the two do not agree, the rejection is `ERR_ROLE_IDENTITY_MISMATCH` (HTTP 403) — distinct from a plain role failure, because the caller holds the right role but is the wrong person.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; when it is omitted it defaults to 10, and a supplied value must be at least 1 and at most 100. `offset` is the number of matching records to skip before the page begins and defaults to 0. Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the number of records matching the filters before pagination is applied and `has_more` indicates whether any matching record remains beyond the current page.

Unless a specific endpoint says otherwise, list endpoints return records sorted by `created_at` in ascending order. Three endpoints override that default because the committee reads them as worklists rather than as journals: the content request list is sorted by `priority_score` descending with `created_at` ascending as the tie-break, the order set item list is sorted by `sequence_index` ascending, and an alert's burden window list is sorted by `window_start` descending so the most recent monitoring window comes first.

### 2.4. Common Artifact Properties and the Logical Clock

Most resources in the system carry the same four system-managed properties. `id` is a server-minted UUID with no type prefix. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the record was first written. `updated_at` is an ISO 8601 UTC timestamp in the same format recording the most recent mutation. `version` is an integer that starts at 1 on creation and increments by exactly 1 on every mutation of the resource, including mutations the server performs on its own initiative when a cascade reaches the resource; it is the value the concurrency guards in §2.6 compare against. `Clinician`, `ContentRequest`, `OrderSet`, `Alert`, `AlertBurdenWindow`, `ReviewAssignment`, `VendorContentRelease`, `VendorRuleDelta`, `DowntimeEvent`, `AdherenceMeasurement` and `AnnualReviewTask` all carry all four.

Two record types are append-only observations rather than governed artifacts, and they carry only `id` and `created_at`: an `OrderSetItem` line and an `OverrideEvent` firing record have no `updated_at` field and no `version` field at all.

Every instant the system compares against — the moment a review becomes due, the moment a downtime window may be activated, the moment a burden window closes — is read from a single **logical clock** rather than from wall time. The clock starts at `2026-08-01T00:00:00Z` and is only ever moved by the administrative clock capability described in §3.9. Whenever this document says "the current instant", it means the logical clock's current value. Setting the clock never itself performs any transition; the expiration sweep must be invoked explicitly.

### 2.5. Governance Precision and Rounding Discipline

Every computed number in this system is produced by decimal arithmetic and rounded half-up. The precision differs by quantity and the intermediate rounding steps are load-bearing, so they are specified once here and referenced by the workflows in §3.

- `priority_score` is stored with two decimal places. Inside the committee-calibrated variant the backlog age bonus is rounded to four decimal places *before* it is used as a multiplier.
- `override_rate` and `volume_factor` on a burden window are each rounded to four decimal places before they are multiplied together; `burden_index` and `burden_index_clinician_weighted` are then rounded to two decimal places.
- `peer_approve_ratio`, `specialty_approve_ratio` and every approval ratio used by the quorum rules are rounded to four decimal places, and the threshold comparison is made against the *rounded* ratio. This matters at the boundary: two approvals out of three rounds to 0.6667 and therefore meets the 0.6667 standard-risk threshold, while one approval out of two rounds to 0.5000 and does not.
- `adherence_pct_per_protocol`, `adherence_pct_intention_to_treat`, `latest_adherence_pct` and `unintended_event_rate_per_100` are stored with two decimal places, and the per-unit rates that feed the per-protocol average are each rounded to four decimal places before being averaged.
- `estimated_minutes`, the three workload counters on a clinician, `impact_score` and every count field are whole integers and are never rounded.
- Date arithmetic adds whole UTC days to an anchor instant and preserves the anchor's time-of-day component exactly.

All numeric values are returned in response bodies as JSON numbers, not strings.

### 2.6. Stale-Version Guards on Parent Artifacts

Two creation endpoints attach a child record to a parent whose state the client must have observed first, and both are protected by an optimistic-concurrency guard expressed as a mandatory version field in the request body.

Creating an order set build under a content request requires `expected_content_request_version`, carrying the `version` of the target `ContentRequest` as the client last read it. If that value does not equal the content request's current `version`, the request is rejected with `ERR_STALE_CONTENT_REQUEST_VERSION` and HTTP 412. The guard exists because another builder may already have created a build on the same request — a build the current builder may legitimately intend to supersede — in which case the caller's picture of the request, including its `status` and its calibrated `priority_score`, is out of date.

Opening a burden window on an alert requires `expected_alert_version`, carrying the `version` of the target `Alert` as the client last read it. A mismatch with the alert's current `version` is rejected with `ERR_STALE_ALERT_VERSION` and HTTP 412. Opening a window legitimately supersedes whichever window is currently open, closing it and computing its burden index, so a stale view of the alert's version means the caller is reasoning about a firing ledger and a window chain that have already moved on.

Both fields are required, not optional; omitting one is a schema failure. No other endpoint in the system accepts a version field, and no other endpoint performs a version comparison.

### 2.7. The Order of Rejection

Many requests can fail for several reasons at once, and which error surfaces is part of the contract. Checks are evaluated in the following precedence; the first check that fails determines the response, and no later check is consulted.

1. **Authentication** — `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorization** — `ERR_UNAUTHORIZED` (403). Applies to every endpoint. Steps 1 and 2 both precede path resolution.
3. **Identity binding** — `ERR_ROLE_IDENTITY_MISMATCH` (403), on sponsor resubmission, vote casting and annual attestation. Because this comparison reads the stored artifact, an identifier in the path that names nothing still produces the 404 of step 4.
4. **Path existence**, evaluated left to right across the path (see §2.8) — the 404 family.
5. **Request-body foreign keys**, evaluated in the order the endpoint declares its input fields — the 404 family again. An unknown clinician reference such as `clinical_sponsor_id`, `built_by_clinician_id`, `designed_by_clinician_id`, `reviewer_id` or `pharmacy_signoff_by_clinician_id` yields `ERR_CLINICIAN_NOT_FOUND`; an unknown `supersedes_order_set_id`, `linked_order_set_id` or `order_set_id` yields `ERR_ORDER_SET_NOT_FOUND`; an unknown `pinned_vendor_release_id` or `supersedes_release_id` yields `ERR_VENDOR_RELEASE_NOT_FOUND`; an unknown `alert_id` yields `ERR_ALERT_NOT_FOUND`.
6. **Schema** — `ERR_INVALID_REQUEST` (400): a missing required field, an unknown enum member, a wrong JSON type, an empty array where at least one element is required, or a negative count.
7. **Interval bounds** — `ERR_INVALID_WINDOW_BOUNDS` (422) when an interval's start is not strictly before its end.
8. **Observation counts** — `ERR_INVALID_OBSERVATION_COUNTS` (422) on adherence unit observations.
9. **Stale parent version** — the 412 guards of §2.6. Concurrency is checked after schema and existence but *before* any state precondition, so a stale version against an artifact that is also in the wrong state returns 412.
10. **The primary artifact's own state** — the 409 family, one code per endpoint, listed in §5 and named in the workflows of §3.
11. **The state of a second entity the caller did not name in the path** — a reviewer whose `employment_status` is not `ACTIVE` yields `ERR_CLINICIAN_NOT_ACTIVE` (409); an assignment that is no longer outstanding yields `ERR_ASSIGNMENT_NOT_ASSIGNED` (409); reopening a window while a different window of the same alert is open yields `ERR_ANOTHER_WINDOW_OPEN` (409).
12. **Downtime freeze** — `ERR_CDS_CONTENT_FROZEN` or `ERR_CDS_UNAVAILABLE` (409), per §2.11. The freeze is evaluated after the stale-version guard and after the primary state precondition, so a frozen system still reports 412 for a stale version and 409 for an impossible transition before it reports the freeze.
13. **Segregation of duties** — `ERR_SEGREGATION_OF_DUTIES` (403).
14. **Self-review** — `ERR_SELF_REVIEW_FORBIDDEN` (403). Step 13 is evaluated before step 14, so a builder who is also the sponsor of the request receives `ERR_SEGREGATION_OF_DUTIES`.
15. **Evidence sufficiency** — `ERR_EVIDENCE_INSUFFICIENT` (422).
16. **Hard-stop justification** — `ERR_TIER1_JUSTIFICATION_REQUIRED` (422).
17. **Override reason capture** — `ERR_OVERRIDE_REASON_REQUIRED` (422).
18. **High-alert pharmacy sign-off** — `ERR_HIGH_ALERT_PHARMACY_SIGNOFF_REQUIRED` (409).
19. **Burden window overlap** — `ERR_BURDEN_WINDOW_OVERLAP` (409).
20. **Downtime window overlap** — `ERR_DOWNTIME_WINDOW_OVERLAP` (409).
21. **Adherence verdict support** — `ERR_ADHERENCE_VERDICT_UNSUPPORTED` (422).
22. **Pinned vendor release activated** — `ERR_VENDOR_RELEASE_NOT_ACTIVATED` (409).
23. **Linked order set published** — `ERR_LINKED_ORDER_SET_NOT_PUBLISHED` (409).
24. **Duplicate review assignment** — `ERR_DUPLICATE_REVIEW_ASSIGNMENT` (409).
25. **Complete delta disposition** — `ERR_DELTA_DISPOSITION_INCOMPLETE` (409).
26. **Suppression justification** — `ERR_SUPPRESSION_JUSTIFICATION_REQUIRED` (422).
27. **Retirement criteria** — `ERR_RETIREMENT_CRITERIA_NOT_MET` (409).
28. **Reviewer capacity** — `ERR_REVIEWER_CAPACITY_EXCEEDED` (422). This is evaluated last of all, so a reviewer who is simultaneously duplicated and over capacity receives `ERR_DUPLICATE_REVIEW_ASSIGNMENT` from step 24.

### 2.8. Path Resolution and Nested Artifact Addressing

When a path carries more than one identifier, the identifiers are resolved strictly left to right and the first one that resolves to nothing determines the 404. Each collection has its own not-found code: a content request path yields `ERR_CONTENT_REQUEST_NOT_FOUND`, an order set path `ERR_ORDER_SET_NOT_FOUND`, an alert path `ERR_ALERT_NOT_FOUND`, a nested burden window `ERR_BURDEN_WINDOW_NOT_FOUND`, a review assignment `ERR_REVIEW_ASSIGNMENT_NOT_FOUND`, a vendor release `ERR_VENDOR_RELEASE_NOT_FOUND`, a vendor rule delta `ERR_VENDOR_RULE_DELTA_NOT_FOUND`, a downtime event `ERR_DOWNTIME_EVENT_NOT_FOUND`, an adherence measurement `ERR_ADHERENCE_MEASUREMENT_NOT_FOUND`, an annual review task `ERR_ANNUAL_REVIEW_TASK_NOT_FOUND`, and a clinician `ERR_CLINICIAN_NOT_FOUND`.

Nesting also implies ownership. A burden window addressed under an alert must belong to that alert: a `window_id` that exists but whose `alert_id` names a different alert is treated as not found for the alert in the path and yields `ERR_BURDEN_WINDOW_NOT_FOUND`, never a window from someone else's alert.

### 2.9. Two-Dimensional Governance State and Cascade Discipline

Order sets and alerts each carry **two independent state dimensions**, and the system never collapses them. An `OrderSet` has a `review_state` covering governance (`DRAFT`, `PEER_REVIEW`, `SPECIALTY_APPROVAL`, `APPROVED`) and a `publication_state` covering its life in production (`UNPUBLISHED`, `PUBLISHED`, `EXPIRING`, `EXPIRED`, `ARCHIVED`, `SUPERSEDED`), of which `ARCHIVED` and `SUPERSEDED` are terminal. An `Alert` has a `review_state` (`DRAFT`, `SPECIALTY_APPROVAL`, `APPROVED`) and a `lifecycle_state` (`UNPUBLISHED`, `ACTIVE`, `SUSPENDED`, `RETIRED`), of which `RETIRED` is terminal. Both review dimensions are cyclic — a revision vote sends an artifact back to `DRAFT` and it may climb again — and an alert may cycle between `ACTIVE` and `SUSPENDED` indefinitely.

Because these artifacts reference each other, a single request routinely mutates more than one record. The governing principles are:

- **Every touched record is a mutation.** When a cascade reaches a record, that record's `updated_at` is refreshed and its `version` increments by 1, exactly as if a client had written to it directly. This applies to derived-field refreshes too: recomputing `item_count` on an order set, or `windowed_fire_count` on an alert, increments that artifact's `version`.
- **Cascades run to completion inside the triggering request.** Consistency is immediate; there is no deferred reconciliation queue. If a specialty vote returns an order set to `DRAFT`, the sibling assignments are voided, the reviewers' workload ledgers are credited, and the dependent alerts are re-staged before the response is written.
- **Votes are never deleted.** An assignment that a cascade invalidates moves to `VOIDED` and keeps its recorded `vote`, `comment` and `evidence_concern` for audit; only the artifact's aggregate counters change.
- **Ledgers are conserved, not recomputed from scratch.** Reversals must restore the prior value exactly — see §2.12.

### 2.10. Segregation of Duties Across the Governance Chain

Authorization answers "may this role do this?"; segregation of duties answers "may this *person* do this, given what they have already done to this artifact?" A clinician may hold several roles in `authorized_roles`, so the second question is always asked separately, and it is asked by comparing `X-User-ID` and stored identity fields on the artifact.

Four constraints are enforced with `ERR_SEGREGATION_OF_DUTIES` (403). The clinician recorded as an order set's `built_by_clinician_id` may not be assigned to review that order set. The clinician recorded as an alert's `designed_by_clinician_id` may not be assigned to review that alert. The same clinician may not hold both a `PEER_REVIEW` assignment and a `SPECIALTY_APPROVAL` assignment on one order set. And the approver who cast the deciding specialty vote on an artifact may not then be the one who publishes that order set or activates that alert.

Two further constraints are enforced with `ERR_SELF_REVIEW_FORBIDDEN` (403), both at assignment time: the `clinical_sponsor_id` of a content request may not review any artifact built from that request, and the clinician recorded in `pharmacy_signoff_by_clinician_id` on an order set may not review that order set.

Only a `CommitteeChair` may triage a request, create or withdraw a review assignment, publish an order set, activate, suspend, resume or retire an alert, or finalize a measurement. Only an `InformaticsBuilder` may create an order set build, design an alert, or submit an order set for peer review. Only a `PharmacyInformaticist` may record pharmacy sign-off or run a vendor release impact analysis. Only a `ClinicalSponsor` may resubmit a returned request or attest an annual review task. A `SystemAdmin` may never triage, review, publish, activate, retire or attest clinical content; a `CommitteeChair` may never cast a review vote and may never reopen a burden window.

### 2.11. Downtime, Read-Only Mode and the Content Freeze

Decision support content must degrade predictably when the EHR is down. A `DowntimeEvent` declares a `scope` — one of `SYSTEM_WIDE`, `ORDER_SETS_ONLY`, `ALERTS_ONLY` — and a `mode`, either `READ_ONLY` or `FULL_UNAVAILABLE`. While the event's `state` is `ACTIVE`, every in-scope content mutation is refused: with `mode` `READ_ONLY` the refusal is `ERR_CDS_CONTENT_FROZEN` (409), and with `mode` `FULL_UNAVAILABLE` both mutations *and* reads of in-scope content are refused with `ERR_CDS_UNAVAILABLE` (409).

Scope determines what "in-scope" means. `ORDER_SETS_ONLY` covers writes to order sets, to order set items, and to review assignments whose target is an order set. `ALERTS_ONLY` covers writes to alerts, to alert burden windows, and to review assignments whose target is an alert. `SYSTEM_WIDE` covers all of the above and additionally covers vendor content releases and vendor rule deltas, which no narrower scope covers. Regardless of scope or mode, the freeze never blocks closing a downtime event, running the expiration sweep, ingesting alert firings, or setting the logical clock, and it never blocks writes to content requests, adherence measurements or annual review tasks.

Each in-scope mutation the freeze rejects increments that active event's `blocked_mutation_count` by 1, giving the committee an after-action count of the clinical work the downtime displaced.

### 2.12. Conservation Invariants on the Two Ledgers

The system keeps two running ledgers, and both must survive reversal without drift.

The **reviewer workload ledger** lives on each `Clinician` as `review_workload_capacity_minutes`, `review_workload_assigned_minutes`, `review_workload_remaining_minutes` and `open_assignment_count`. After every write that touches assignments, two identities must hold: `review_workload_capacity_minutes` equals `review_workload_assigned_minutes` plus `review_workload_remaining_minutes`; and `review_workload_assigned_minutes` equals the sum of `estimated_minutes` over that clinician's assignments in state `ASSIGNED` or `CAST`. A withdrawal followed by an identical re-assignment must restore both sides to exactly their prior values, and `open_assignment_count` must return to exactly its prior value.

The **alert firing ledger** lives on each `Alert` as `lifetime_fire_count`, `windowed_fire_count` and `unwindowed_fire_count`. `lifetime_fire_count` counts every firing record ever ingested for the alert and never decreases. `windowed_fire_count` is the sum of `fire_count` over that alert's burden windows in state `CLOSED` or `FINALIZED`. `unwindowed_fire_count` is always `lifetime_fire_count` minus `windowed_fire_count` — the firings not yet attributed to a closed window. Reopening a closed window discards that window's counts and subtracts them back out of `windowed_fire_count`, leaving `lifetime_fire_count` untouched, so the three numbers stay consistent across arbitrarily many close-and-reopen cycles.

## 3. Business Logic & Workflows

### 3.1. Content Request Intake and Committee Triage

Governance begins when a clinician asks for something to be built. A `ClinicalSponsor` — or a `CommitteeChair` filing on a sponsor's behalf — submits a **content request** carrying a short `title`, a `request_type` of `ORDER_SET`, `ALERT` or `BOTH`, the `clinical_domain` that will own the content, an `urgency` of `ROUTINE`, `EXPEDITED` or `SAFETY_URGENT`, a self-declared `evidence_grade` of `A`, `B`, `C` or `EXPERT_OPINION`, the `clinical_sponsor_id` of the sponsoring clinician, and an `evidence_citations` array. Each citation object carries a required `citation` string and a required `peer_reviewed` boolean, plus an optional `doi` string and an optional `publication_year` integer; the array must contain at least one entry, and an empty array is an `ERR_INVALID_REQUEST` schema failure. Optionally the sponsor may set `patient_safety_flag` to assert that the content mitigates a patient-safety event — it defaults to `false` — and may supply an advisory `requested_go_live_at`, which is purely a hint: the chair sets the binding `go_live_at` at publication. The named sponsor must be a clinician whose committee roles include `ClinicalSponsor` and whose `employment_status` is `ACTIVE`.

Creation lands the request in `status` `INTAKE_SUBMITTED`. The server derives `peer_reviewed_citation_count` as the number of `evidence_citations` entries whose `peer_reviewed` is true, sets `return_count` to 0, leaves `triage_note` null, and computes the **intake-provisional priority score**. That variant trusts the sponsor's own grading and nothing else: it awards 40 points for evidence grade `A`, 30 for `B`, 18 for `C` and 8 for `EXPERT_OPINION`; adds 0 points for urgency `ROUTINE`, 12 for `EXPEDITED` and 25 for `SAFETY_URGENT`; adds a further 15 points when `patient_safety_flag` is true and nothing when it is false; sums those three components; rounds the sum half-up to two decimal places; and stores the lesser of that figure and the score ceiling of 100.00 as `priority_score`. The provisional variant deliberately ignores `peer_reviewed_citation_count` and ignores how long the request has waited, and it applies no multiplier of any kind. `priority_score_basis` is set to `INTAKE_PROVISIONAL` to record which variant produced the stored number.

Triage is the `CommitteeChair`'s exclusive step and takes a `decision` of `ACCEPT`, `RETURN` or `DECLINE` together with an optional `triage_note`. A request may only be triaged out of `INTAKE_SUBMITTED`; any other `status` is rejected with `ERR_CONTENT_REQUEST_NOT_TRIAGEABLE`. All three decisions store the `triage_note`.

Accepting a request advances `INTAKE_SUBMITTED → TRIAGE_ACCEPTED`, but only if the evidence clears the acceptance bar. A request must carry at least two citations, of which at least one is peer reviewed; and a request whose `patient_safety_flag` is true or whose `urgency` is `SAFETY_URGENT` must carry at least two peer-reviewed citations. Evidence that falls short of any applicable threshold is rejected with `ERR_EVIDENCE_INSUFFICIENT`. On acceptance the score is recomputed with the **committee-calibrated** variant, which replaces the sponsor's self-declared grade with verified citations and then rewards patience. The citation component is 6 points for each peer-reviewed citation, capped at 40 points however many there are. The urgency and safety components are the same as before — 0, 12 or 25 points for urgency, and 15 points when `patient_safety_flag` is true. Those three form the base. The backlog age in whole days is the number of elapsed seconds between the request's `created_at` and the current instant divided by 86400 with the fractional part discarded. The age bonus is 0.02 per whole day of backlog age, rounded half-up to four decimal places, then capped at 0.30. The base is multiplied by one plus that age bonus, the product is rounded half-up to two decimal places, and `priority_score` becomes the lesser of that result and 100.00. `priority_score_basis` is set to `COMMITTEE_CALIBRATED`. Because the two variants use a different first term and only the calibrated one multiplies, the same stored data legitimately yields two different scores.

Returning a request advances `INTAKE_SUBMITTED → RETURNED_TO_SPONSOR` and increments `return_count` by 1; both `priority_score` and `priority_score_basis` are left exactly as they were. Declining a request advances `INTAKE_SUBMITTED → DECLINED`, which is terminal. Resubmission is the sponsor's own step: only the clinician whose id equals the request's `clinical_sponsor_id` may resubmit, and only from `RETURNED_TO_SPONSOR` — any other `status` is `ERR_CONTENT_REQUEST_NOT_RETURNED`, and the wrong clinician is `ERR_ROLE_IDENTITY_MISMATCH`. A resubmission supplies a fresh `evidence_citations` array, optionally revising `evidence_grade` and `urgency`; the array replaces the stored one wholesale, `peer_reviewed_citation_count` is recomputed from it, `priority_score` is recomputed with the intake-provisional variant, `priority_score_basis` returns to `INTAKE_PROVISIONAL`, and `status` returns to `INTAKE_SUBMITTED`. A request may travel this loop any number of times.

Once builders begin work the request advances `TRIAGE_ACCEPTED → BUILD_IN_PROGRESS`, and it closes as `CLOSED_IMPLEMENTED` — which is terminal — only when the build it asked for actually reached production: for `request_type` `ORDER_SET`, at least one child order set has `publication_state` `PUBLISHED`; for `ALERT`, at least one child alert has `lifecycle_state` `ACTIVE`; and for `BOTH`, both conditions must hold. That closure is performed by the server as part of publication or activation, never as a request of its own. Requests may be listed with filters on `clinical_sponsor_id`, `status`, `urgency`, `request_type`, `clinical_domain` and `patient_safety_flag`.

### 3.2. Order Set Construction, the Item Catalogue and Pharmacy Sign-off

An `InformaticsBuilder` opens a build against a request that has been accepted. The payload names the order set's `name`, its owning `specialty`, the `pinned_vendor_release_id` identifying the drug-interaction and dosing content version the build is pinned to, and `built_by_clinician_id` — the builder of record, which must equal the `X-User-ID` of the builder issuing the call. It also carries the mandatory `expected_content_request_version` guard described in §2.6, and it may carry `supersedes_order_set_id` naming the build this one legitimately replaces. The `content_request_id` is taken from the path and never from the body. A build may only be opened against a request whose `status` is `TRIAGE_ACCEPTED` or already `BUILD_IN_PROGRESS`; anything else is `ERR_CONTENT_REQUEST_NOT_ACCEPTED`.

The new order set starts with `review_state` `DRAFT`, `publication_state` `UNPUBLISHED`, `item_count` and `high_alert_item_count` at 0, `revision_round`, `votes_cast_count` and `votes_voided_count` at 0, `peer_cast_count` and `specialty_cast_count` at 0, `peer_required_votes`, `specialty_required_votes`, `peer_approve_ratio` and `specialty_approve_ratio` all null, `pharmacy_signoff_at`, `pharmacy_signoff_by_clinician_id`, `go_live_at`, `review_due_date`, `expiration_at`, `archive_eligible_at`, `latest_adherence_pct` and `archived_at` all null, and `pinned_content_stale` false. Its `risk_class` is seeded from the parent request's `patient_safety_flag`: `HIGH` when that flag is true, `STANDARD` otherwise. Creating the first build artifact on a request — order set or alert — advances that request `TRIAGE_ACCEPTED → BUILD_IN_PROGRESS` and increments the request's `version`. If `supersedes_order_set_id` was supplied and names an order set whose `publication_state` is `UNPUBLISHED`, that predecessor transitions `UNPUBLISHED → SUPERSEDED` and every review assignment on it in state `ASSIGNED` or `CAST` is voided with `void_reason` `ARTIFACT_SUPERSEDED`, crediting each reviewer's minutes back per §2.12.

Content is added one orderable at a time, by the builder or by a `PharmacyInformaticist`, and only while `review_state` is `DRAFT` — adding to an order set in any other review state is `ERR_ORDER_SET_NOT_DRAFT`. Each line carries an `orderable_code` from the catalogue, a `display_name`, an `item_category` of `MEDICATION`, `LAB`, `IMAGING`, `NURSING` or `CONSULT`, and optionally `default_selected` (whether the line is pre-checked when a clinician opens the order set, default `false`), `default_dose` (a pre-populated dose string such as 40 mg, meaningful for medication lines and null by default), `route`, `frequency`, `high_alert_medication` (default `false`), and `sequence_index`. The `sequence_index` controls display order within the order set, must be at least 1, and must be unique within its `order_set_id`; when the builder omits it the server assigns the order set's current `item_count` plus 1. The `order_set_id` itself is taken from the path. Every added line increments the order set's `item_count`, and a line whose `high_alert_medication` is true also increments `high_alert_item_count`.

`risk_class` is recomputed whenever items change and again when the order set enters review: it is `HIGH` when `high_alert_item_count` is at least 1 **or** the parent request's `patient_safety_flag` is true, and `STANDARD` otherwise. Adding a single high-alert medication therefore promotes a standard build to high risk, which raises its quorum bar, lengthens the review minutes charged to its reviewers, and shortens its review interval. Items may be listed filtered by `item_category` and `high_alert_medication`.

High-alert content requires a pharmacist's eyes before it reaches production. A `PharmacyInformaticist` records sign-off by supplying `pharmacy_signoff_by_clinician_id` and an optional `signoff_note`; the server stores that clinician reference and sets `pharmacy_signoff_at` to the current instant. Sign-off has a governance consequence: the clinician who signed becomes permanently ineligible to review that order set, and any later attempt to assign them is refused with `ERR_SELF_REVIEW_FORBIDDEN`.

Order sets may be listed filtered by `content_request_id`, `built_by_clinician_id`, `pinned_vendor_release_id`, `supersedes_order_set_id`, `pharmacy_signoff_by_clinician_id`, `review_state`, `publication_state`, `risk_class`, `specialty` and `pinned_content_stale`.

### 3.3. Alert Design, Severity Tiering and Override Reason Capture

Alerts are designed by an `InformaticsBuilder` against the same accepted request, and the request's `status` gate and its `TRIAGE_ACCEPTED → BUILD_IN_PROGRESS` advance work identically to an order set build; the alert's `content_request_id` comes from the path. The payload carries the alert's `name`, its `firing_criteria` — an object with a `trigger_event` string naming the EHR event that evaluates the rule and an `expression` string carrying the rule itself — a `designed_by_clinician_id` snapshotting the designer, and a `severity_tier` of `TIER_1_HARD_STOP`, `TIER_2_INTERRUPTIVE` or `TIER_3_PASSIVE`. Optionally it carries `override_reason_codes` (the allowed override reason code strings, an empty array by default), `override_reason_required`, `hard_stop_justification`, and `linked_order_set_id` naming an order set whose publication gates this alert's activation.

Severity tier is the alert's single most consequential attribute. It fixes how many approval votes the alert needs, how many minutes its review costs a reviewer, how heavily its firings weigh in the burden index, and how soon it must be reviewed again. It also constrains override capture: `override_reason_required` is forced to true for `TIER_1_HARD_STOP` and `TIER_2_INTERRUPTIVE` regardless of what the designer submitted, and only a `TIER_3_PASSIVE` alert may leave it false. When `override_reason_required` is true, the alert must declare at least two entries in `override_reason_codes` before it can be activated, and a shortfall is `ERR_OVERRIDE_REASON_REQUIRED`. A `TIER_1_HARD_STOP` alert additionally requires a non-empty `hard_stop_justification` narrative before it may enter review or be activated; without it the request is refused with `ERR_TIER1_JUSTIFICATION_REQUIRED`.

A newly designed alert starts with `review_state` `DRAFT` and `lifecycle_state` `UNPUBLISHED`, with `required_approval_votes`, `latest_burden_index`, `latest_burden_classification`, `review_due_date`, `expiration_at`, `retired_at` and `suspension_reason` all null, and with `approval_cast_count`, `lifetime_fire_count`, `windowed_fire_count`, `unwindowed_fire_count`, `lifetime_override_count`, `suspension_count` and `restage_count` all at 0. `lifetime_override_count` accumulates the number of firing records for this alert whose `accepted` is false, across the alert's whole life. Alerts may be listed filtered by `content_request_id`, `designed_by_clinician_id`, `linked_order_set_id`, `severity_tier`, `review_state`, `lifecycle_state` and `latest_burden_classification`.

### 3.4. Reviewer Assignment, Vote Casting and Quorum Evaluation

Reviewers are registered as clinicians by a `SystemAdmin`, who supplies a `full_name`, a `specialty` drawn from the clinical taxonomy (`INTERNAL_MEDICINE`, `HOSPITAL_MEDICINE`, `CRITICAL_CARE`, `CARDIOLOGY`, `NEPHROLOGY`, `ENDOCRINOLOGY`, `GERIATRICS`, `ONCOLOGY`, `PEDIATRICS`, `EMERGENCY`, `ORTHOPEDICS`, `PHARMACY`, `NURSING`, `INFORMATICS`) that is also the taxonomy used for a request's `clinical_domain` and an order set's own `specialty`, and a non-empty `authorized_roles` array of committee role tokens. Optionally the admin supplies an `npi` national provider identifier (null by default), a `credential` of `MD`, `DO`, `PHARMD`, `RN` or `NP`, an `employment_status` of `ACTIVE` or `INACTIVE` (defaulting to `ACTIVE`), and a `review_workload_capacity_minutes` review-time budget, which must be at least 0 and defaults to 480 minutes — eight hours of committee reading per cycle. A freshly registered clinician starts with `review_workload_assigned_minutes` at 0, `review_workload_remaining_minutes` equal to the full capacity, and `open_assignment_count` at 0. Only a clinician whose `employment_status` is `ACTIVE` may act or be assigned; assigning or casting as an inactive clinician is `ERR_CLINICIAN_NOT_ACTIVE`.

The `CommitteeChair` creates each **review assignment**, naming the `reviewer_id`, a `review_kind` of `PEER_REVIEW` or `SPECIALTY_APPROVAL`, exactly one of `order_set_id` or `alert_id`, and an optional advisory `due_at` that is recorded but never enforced as a gate. Supplying neither target or both is `ERR_INVALID_REQUEST`. The assignment opens in state `ASSIGNED` with `vote`, `comment`, `cast_at`, `withdrawal_reason` and `void_reason` null and `evidence_concern` false.

Creating an assignment debits the reviewer's time budget. The server first snapshots `risk_class_snapshot`: for an order-set assignment it is the order set's current `risk_class`; for an alert assignment it is `HIGH` when the alert's `severity_tier` is `TIER_1_HARD_STOP` and `STANDARD` otherwise. From that it computes `estimated_minutes`. An order-set peer review costs 20 minutes on a `STANDARD` build and 35 on a `HIGH` one; an order-set specialty approval costs 15 minutes on a `STANDARD` build and 25 on a `HIGH` one. An alert review is priced by tier instead: 30 minutes for `TIER_1_HARD_STOP`, 18 for `TIER_2_INTERRUPTIVE` and 10 for `TIER_3_PASSIVE`. Those minutes are added to the reviewer's `review_workload_assigned_minutes`, `open_assignment_count` is increased by 1, and `review_workload_remaining_minutes` is recomputed as `review_workload_capacity_minutes` minus `review_workload_assigned_minutes`. An assignment that would push `review_workload_assigned_minutes` above `review_workload_capacity_minutes` is refused with `ERR_REVIEWER_CAPACITY_EXCEEDED`; the test is on the aggregate, so several individually modest assignments can collectively breach the cap. A clinician may hold at most one assignment in state `ASSIGNED` or `CAST` per artifact-and-`review_kind` pair, and a second one is `ERR_DUPLICATE_REVIEW_ASSIGNMENT`; assignments already in `VOIDED` or `WITHDRAWN` do not block a fresh assignment. The segregation and self-review constraints of §2.10 are enforced here too.

The first assignment created against an alert also opens that alert's single approval stage, advancing its `review_state` `DRAFT → SPECIALTY_APPROVAL` and seeding `required_approval_votes` from the tier: 3 votes for `TIER_1_HARD_STOP`, 2 for `TIER_2_INTERRUPTIVE`, 1 for `TIER_3_PASSIVE`. Assigning a reviewer to a `TIER_1_HARD_STOP` alert also requires that the alert already carry a non-empty `hard_stop_justification`; without it the assignment is refused with `ERR_TIER1_JUSTIFICATION_REQUIRED`, so a hard-stop alert cannot enter review unjustified. Order sets enter review by a different door: the builder submits the draft, which requires `review_state` `DRAFT` (otherwise `ERR_ORDER_SET_NOT_DRAFT`), at least one item, and a `publication_state` of `UNPUBLISHED`, `EXPIRING` or `EXPIRED`. Submission takes an optional `submission_note`, recomputes `risk_class`, seeds `peer_required_votes`, and advances `review_state` `DRAFT → PEER_REVIEW`.

A reviewer casts a vote of `APPROVE`, `REVISE` or `REJECT`, optionally flagging `evidence_concern` and attaching a `comment`. Only the clinician whose id equals the assignment's `reviewer_id` may cast, and only from state `ASSIGNED`; a `CAST`, `WITHDRAWN` or `VOIDED` assignment yields `ERR_ASSIGNMENT_NOT_ASSIGNED`. The stage must also match: a `PEER_REVIEW` assignment may only be cast while the target order set's `review_state` is `PEER_REVIEW`; a `SPECIALTY_APPROVAL` assignment on an order set requires that order set's `review_state` to be `SPECIALTY_APPROVAL`; a `SPECIALTY_APPROVAL` assignment on an alert requires that alert's `review_state` to be `SPECIALTY_APPROVAL`. Casting moves the assignment `ASSIGNED → CAST`, stores `vote`, `comment`, `evidence_concern` and `cast_at`, and leaves the workload debit in place — the minutes were consumed by doing the work, so casting never credits the ledger.

Every cast re-runs the **quorum evaluation** on the target artifact, and the seven steps run in exactly this order because each step consumes the output of the ones before it — the evidence-concern count of step 3 feeds the required vote count of step 4, which in turn feeds the quorum test. Step one determines `risk_class`: `HIGH` when the order set's `high_alert_item_count` is at least 1 or the parent request's `patient_safety_flag` is true, `STANDARD` otherwise. Step two takes the base vote requirement from that class — 3 votes for `HIGH`, 2 for `STANDARD`. Step three counts the assignments on this artifact and this stage that are in state `CAST` with `evidence_concern` true, *including the vote being cast in this very request*. Step four sets the required vote count to the base plus 1 when that concern count is at least 1, plus nothing when it is 0, and then caps the result at 4. Step five recomputes, over the `CAST` assignments on this artifact and stage, the cast count, the approve count, the reject count, and the approve ratio as approve count divided by cast count rounded half-up to four decimal places. Step six declares quorum met only when all three of the following hold: the cast count is at least the required vote count; the approve ratio is at least the required approval ratio for the risk class, which is 0.8000 for `HIGH` and 0.6667 for `STANDARD`; and the reject count is exactly 0. Step seven advances the artifact's review state when quorum is met.

Those counters are persisted so the committee can read them: `peer_required_votes`, `peer_cast_count` and `peer_approve_ratio` for the peer stage, `specialty_required_votes`, `specialty_cast_count` and `specialty_approve_ratio` for the specialty stage, plus `votes_cast_count` and `votes_voided_count` counting all assignments on the order set in state `CAST` and `VOIDED` respectively. When the peer stage reaches quorum the order set advances `PEER_REVIEW → SPECIALTY_APPROVAL` and `specialty_required_votes` is seeded by re-running the same evaluation for the specialty stage. When the specialty stage reaches quorum the order set advances `SPECIALTY_APPROVAL → APPROVED`.

Alerts run the same skeleton with one stage and a stricter bar. `required_approval_votes` comes from the tier table and there is no risk class and no evidence-concern bump; `approval_cast_count` counts the alert's `CAST` assignments; and the approve ratio must be exactly 1.0000 — unanimity. Meeting that advances the alert `SPECIALTY_APPROVAL → APPROVED`.

Non-approving votes drive the revision loops, and the two artifact kinds differ. On an order set, a `PEER_REVIEW` vote of `REVISE` does **not** revert the stage; it merely lowers `peer_approve_ratio` and so may keep quorum out of reach. A `PEER_REVIEW` vote of `REJECT`, cast while the order set is in `PEER_REVIEW` from an assignment in state `ASSIGNED`, sends the order set `PEER_REVIEW → DRAFT`, increments `revision_round` by 1, and voids every *other* assignment on that order set in state `ASSIGNED` or `CAST` with `void_reason` `ARTIFACT_RETURNED_TO_DRAFT`, crediting each of those reviewers' minutes back. On the specialty stage, a vote of either `REVISE` or `REJECT`, cast while the order set is in `SPECIALTY_APPROVAL` from an assignment in state `ASSIGNED`, triggers a four-link cascade. First, `review_state` returns `SPECIALTY_APPROVAL → DRAFT` and `revision_round` increments by 1. Second, because the order set returned to `DRAFT`, every *other* assignment on it in state `ASSIGNED` or `CAST` moves to `VOIDED` with `void_reason` `ARTIFACT_RETURNED_TO_DRAFT`. Third, because each of those assignments was voided, its reviewer's `review_workload_assigned_minutes` is reduced by that assignment's `estimated_minutes` and `review_workload_remaining_minutes` is recomputed. Fourth, because the order set is no longer in approval, every alert whose `linked_order_set_id` names it, whose `lifecycle_state` is `UNPUBLISHED` and whose `review_state` is `SPECIALTY_APPROVAL` or `APPROVED`, has its `review_state` forced back to `DRAFT` and its `restage_count` incremented by 1. Afterwards `peer_cast_count`, `specialty_cast_count`, `votes_cast_count` and `votes_voided_count` are all recomputed. The triggering assignment itself stays `CAST` with its vote intact. An alert's own revision loop is simpler: a `REVISE` or `REJECT` vote cast while the alert is in `SPECIALTY_APPROVAL` returns it to `DRAFT` and voids every other assignment on that alert in state `ASSIGNED` or `CAST` with `void_reason` `ARTIFACT_RETURNED_TO_DRAFT`, crediting those reviewers' minutes back.

Voiding is always a system act, never a client request; it happens whenever a target artifact returns to `DRAFT` or is superseded. Voiding an assignment that was still `ASSIGNED` credits its minutes back exactly as a withdrawal does. Voiding one that had already reached `CAST` also credits the minutes back, keeps the recorded vote for audit, and additionally decreases the target artifact's `votes_cast_count` by 1 while increasing `votes_voided_count` by 1.

Withdrawal, by contrast, is the chair's compensating action on an assignment still in state `ASSIGNED`. It supplies a `withdrawal_reason`, moves the assignment `ASSIGNED → WITHDRAWN`, reduces the reviewer's `review_workload_assigned_minutes` by that assignment's `estimated_minutes`, decreases `open_assignment_count` by 1, and recomputes `review_workload_remaining_minutes` — restoring the pre-assignment ledger exactly, with no drift. Both `WITHDRAWN` and `VOIDED` are terminal. Assignments may be listed filtered by `order_set_id`, `alert_id`, `reviewer_id`, `review_kind`, `state`, `vote` and `evidence_concern`.

### 3.5. Publication, Activation and the Content Review Schedule

Publication is the `CommitteeChair`'s exclusive act, and it is where the governance dimension finally meets the production dimension. The chair supplies the binding `go_live_at` instant. Five conditions must hold: the order set's `publication_state` must be `UNPUBLISHED` and its `review_state` must be `APPROVED`, and a failure of either is `ERR_ORDER_SET_NOT_APPROVED`; the release named by `pinned_vendor_release_id` must be in `review_cycle_state` `ACTIVATED`, or the request is refused with `ERR_VENDOR_RELEASE_NOT_ACTIVATED`; if `high_alert_item_count` is at least 1 then `pharmacy_signoff_at` must not be null, or the request is refused with `ERR_HIGH_ALERT_PHARMACY_SIGNOFF_REQUIRED`; and no active downtime event may cover order sets, per §2.11. The specialty approver who cast the deciding vote may not be the one publishing, per §2.10.

On success `publication_state` advances `UNPUBLISHED → PUBLISHED`, `go_live_at` is stored from the request, and the **review schedule** is computed from it. The review interval depends on risk: a `STANDARD` artifact is reviewed 365 days after its anchor instant, a `HIGH` artifact after 180 days. So `review_due_date` is the anchor plus the interval for the artifact's `risk_class`, `expiration_at` is `review_due_date` plus a 30-day grace period, and `archive_eligible_at` is `expiration_at` plus a further 90 days. All three are whole-day additions that preserve the anchor's time of day exactly. The server also creates one annual review task governing this order set, with `artifact_kind` `ORDER_SET`, `state` `PENDING`, `cycle_index` 1, and the same three dates mirrored onto it. Finally, if the parent request's `status` is `BUILD_IN_PROGRESS` and its `request_type` is now satisfied, that request closes as `CLOSED_IMPLEMENTED`.

Publication can also retire a predecessor. When the order set being published names a predecessor in `supersedes_order_set_id` and that predecessor's `publication_state` is `PUBLISHED`, the predecessor transitions `PUBLISHED → SUPERSEDED`. Its governing annual review task is *not* attested — it transitions to `EXPIRED`, with `stale_content_triggered` left exactly as it was — and every alert whose `linked_order_set_id` named the predecessor and whose `lifecycle_state` is `ACTIVE` is re-linked to the successor order set so that live alerting is never orphaned.

Alert activation is the parallel step and is likewise the chair's alone. It takes an optional `activation_note`, and requires `lifecycle_state` `UNPUBLISHED` and `review_state` `APPROVED` — a failure of either is `ERR_ALERT_NOT_APPROVED`. If `linked_order_set_id` is not null, that order set's `publication_state` must be `PUBLISHED`, or activation is refused with `ERR_LINKED_ORDER_SET_NOT_PUBLISHED`. A `TIER_1_HARD_STOP` alert must carry its `hard_stop_justification`, and an alert with `override_reason_required` true must declare at least two `override_reason_codes`. No active downtime event may cover alerts, and — exactly as at publication — the specialty approver who cast the deciding vote on the alert may not be the one activating it, which is refused with `ERR_SEGREGATION_OF_DUTIES`. On success `lifecycle_state` advances `UNPUBLISHED → ACTIVE`; `review_due_date` is the current instant plus the review interval for the alert's risk class, where an alert counts as `HIGH` risk when its `severity_tier` is `TIER_1_HARD_STOP` and `STANDARD` otherwise; `expiration_at` is that date plus the 30-day grace period. Alerts have no `archive_eligible_at`. An annual review task with `artifact_kind` `ALERT`, `state` `PENDING` and `cycle_index` 1 is created, and the parent request closes as `CLOSED_IMPLEMENTED` if its `request_type` is now satisfied.

### 3.6. Vendor Content Release Review Cycles

Drug-interaction and dosing knowledge arrives from a vendor on its own cadence, and the committee must decide how much local scrutiny each drop deserves. A `PharmacyInformaticist` or a `SystemAdmin` records a release with a `vendor_name`, a `release_label` unique within that vendor, and a `content_domain` of `DRUG_INTERACTION`, `DOSING`, `ALLERGY` or `DUPLICATE_THERAPY`. Optionally the payload carries `received_at` — the instant the health system took delivery, defaulting to the current instant when omitted — an `effective_at` before which the release may not be activated, and `supersedes_release_id` naming the release this one replaces on activation. A new release opens in `review_cycle_state` `RECEIVED` with `delta_count` and `contraindicated_delta_count` and `dispositioned_delta_count` and `restaged_order_set_count` all at 0, and with `impact_score` and `activated_at` null.

Each individual rule change is then recorded as a **delta** against the release, whose `vendor_release_id` comes from the path. A delta carries a `rule_code` unique within its release, a `change_type` of `NEW_INTERACTION`, `SEVERITY_INCREASED`, `SEVERITY_DECREASED`, `RETIRED_INTERACTION` or `DOSING_BOUND_CHANGED`, a vendor-supplied `description`, and optionally a `drug_pair` naming the interacting pair or dosing target, a `prior_severity` as carried by the superseded release, and a `new_severity` asserted by the vendor; both severities are drawn from `CONTRAINDICATED`, `MAJOR`, `MODERATE`, `MINOR` and both default to null. On creation the server assigns the delta's `weight` from its `change_type` — 5 for `SEVERITY_INCREASED`, 3 for `NEW_INTERACTION`, 3 for `DOSING_BOUND_CHANGED`, 2 for `RETIRED_INTERACTION`, 1 for `SEVERITY_DECREASED` — plus a bonus of 4 when `new_severity` is `CONTRAINDICATED`. The release's `delta_count` increments, and `contraindicated_delta_count` increments too when `new_severity` is `CONTRAINDICATED`. A delta's `disposition`, `suppression_justification` and `dispositioned_at` all start null. Deltas may be listed filtered by `change_type`, `disposition` and `new_severity`; releases may be listed filtered by `supersedes_release_id`, `review_cycle_state`, `vendor_name` and `content_domain`.

Impact analysis is the `PharmacyInformaticist`'s exclusive step, takes an optional `analysis_note`, and may run only on a release whose `review_cycle_state` is `RECEIVED` and which carries at least one delta; otherwise it is refused with `ERR_VENDOR_RELEASE_NOT_RECEIVED`. `impact_score` is the sum, over every delta of the release, of that delta's weight — the `change_type` weight plus the 4-point contraindication bonus where it applies — and it is a whole integer that is never rounded. The score then **forks the release permanently**. A score below 25 routes it `RECEIVED → IMPACT_ANALYZED_FAST_TRACK`; a score of 25 or more routes it `RECEIVED → IMPACT_ANALYZED_CLINICAL_REVIEW`. One delta can decide the branch, and the branches differ in who may activate the release and in what activation does downstream.

Before either branch may be activated, every delta must be dispositioned. A `PharmacyInformaticist` or a `CommitteeChair` records a `disposition` of `ACCEPT`, `SUPPRESS` or `CUSTOMIZE` on an individual delta, with an optional `suppression_justification` narrative that is required when the disposition is `SUPPRESS`; the server sets `dispositioned_at` and increments the release's `dispositioned_delta_count` on that delta's first disposition. Dispositioning against a release still in `RECEIVED`, or one already `ACTIVATED` or `SUPERSEDED`, is refused with `ERR_VENDOR_RELEASE_NOT_ANALYZED`.

Activation takes an optional `activation_note` and requires that `dispositioned_delta_count` equal `delta_count` — a shortfall is `ERR_DELTA_DISPOSITION_INCOMPLETE` — and that `effective_at` be null or already reached by the current instant. A release still in `RECEIVED`, or already `ACTIVATED` or `SUPERSEDED`, is refused with `ERR_VENDOR_RELEASE_NOT_ANALYZED`.

The fast-track branch is deliberately inert. Either a `PharmacyInformaticist` or a `CommitteeChair` may take a release `IMPACT_ANALYZED_FAST_TRACK → ACTIVATED`; `activated_at` is set to the current instant, and the release named by `supersedes_release_id`, if any, transitions to `SUPERSEDED` — a terminal state. `restaged_order_set_count` stays at 0: the fast-track branch does not mark any pinned order set stale and does not touch any annual review task.

The clinical-review branch is the chair's alone — a `PharmacyInformaticist` attempting it is refused with `ERR_UNAUTHORIZED` — and it also requires that every delta dispositioned `SUPPRESS` carry a non-empty `suppression_justification`, failing which the activation is refused with `ERR_SUPPRESSION_JUSTIFICATION_REQUIRED`. That requirement does not exist on the fast-track branch. Taking a release `IMPACT_ANALYZED_CLINICAL_REVIEW → ACTIVATED` drives a three-link cascade. First, `activated_at` is set to the current instant and the release named by `supersedes_release_id` transitions to `SUPERSEDED`. Second, because that predecessor became `SUPERSEDED`, every order set whose `pinned_vendor_release_id` names the predecessor and whose `publication_state` is `PUBLISHED` has `pinned_content_stale` set to true, and `restaged_order_set_count` is set to the number of order sets so marked. Third, because each of those order sets now carries stale pinned content, its annual review task in state `PENDING` or `OVERDUE` has its `review_due_date` pulled forward to the current instant plus 30 days, with `expiration_at` and `archive_eligible_at` recomputed from that new due date by the usual 30-day grace and 90-day archive offsets, and `stale_content_triggered` set to true; the same three dates are mirrored back onto the order set. Note that `pinned_content_stale` on an order set is precisely the statement that its `pinned_vendor_release_id` points at a release whose `review_cycle_state` is `SUPERSEDED`.

### 3.7. Firing Ingestion, Burden Monitoring and Low-Value Retirement

Once an alert is `ACTIVE` it starts firing, and the committee's obligation shifts from designing it to proving it still earns its interruption. Firings arrive as **override events**, each recording the `alert_id` that fired, an opaque EHR-supplied `firing_clinician_ref` in the style `SYN-001` that is used only for distinct-clinician counting and is never a clinician's `id`, the `fired_at` instant, an `accepted` boolean that is true when the clinician took the advice and false when they overrode it, an `override_reason_code` recorded when `accepted` is false and null otherwise, a `severity_tier_snapshot` capturing the alert's `severity_tier` at ingest time, and an `ingest_batch_seq` giving the firing's 0-based index inside its ingest batch so that ordering is deterministic.

Firings are produced in bulk by an administrative ingest capability, so that burden windows have data to score. It takes the target `alert_id`, a `fired_at_start` instant, an `interval_seconds` spacing, a `fire_count`, an `override_count`, a `distinct_clinician_count`, and an optional `override_reason_code`. It creates exactly `fire_count` firing records whose `fired_at` values are `fired_at_start` plus the interval multiplied by the record's 0-based index, running from 0 up to one less than `fire_count`. The first `override_count` of those records are created with `accepted` false and the supplied `override_reason_code`; every remaining record is created with `accepted` true and a null reason code. Each record's `firing_clinician_ref` is assigned round-robin as `SYN-001` through `SYN-` followed by the `distinct_clinician_count`, zero-padded to three digits. The alert's `lifetime_fire_count` increases by `fire_count` and `unwindowed_fire_count` is recomputed; per-window counters are not touched, because a window's counts are only computed when it closes. The capability reports back a `created_event_count`, the `first_fired_at` and `last_fired_at` instants, an `override_event_count`, and the `distinct_clinician_count` it actually used. For an alert whose `override_reason_required` is true, an ingested firing with `accepted` false must carry an `override_reason_code` drawn from that alert's declared `override_reason_codes`; a missing or undeclared code is refused with `ERR_OVERRIDE_REASON_REQUIRED`. Raw firings may be listed for an alert filtered by `accepted`, `override_reason_code`, `fired_at_from` and `fired_at_to`.

A `SystemAdmin` or a `CommitteeChair` opens an **alert burden window** over a monitoring interval, supplying `window_start` and `window_end` alongside the mandatory `expected_alert_version` guard of §2.6. The interval is half-open: `window_start` is inclusive, `window_end` is exclusive, and a firing whose `fired_at` equals `window_end` belongs to the *next* window. `window_end` must be strictly after `window_start`, or the request is refused with `ERR_INVALID_WINDOW_BOUNDS`. A new window may not overlap any window of the same alert in state `CLOSED` or `FINALIZED`; because overlap is computed on half-open intervals, a new window whose `window_start` equals an existing window's `window_end` is merely adjacent and is allowed, while a genuine intersection is refused with `ERR_BURDEN_WINDOW_OVERLAP`. An existing `OPEN` window is never an overlap conflict — opening a new window legitimately supersedes it, closing that predecessor with `closure_reason` `SUPERSEDED_BY_NEW_WINDOW` and computing its burden index in the process. The window opens in `state` `OPEN` with `severity_tier_snapshot` copied from the alert, `reopen_count` at 0, `closure_reason` and `closed_at` null, every count at 0 and every rate, factor, index and classification null.

Closing a window is where the measurement happens. The close may be requested explicitly by a `SystemAdmin` or `CommitteeChair` with an optional `closure_reason`, or performed by the server when a new window supersedes it, when the alert is suspended, or when the alert is retired; closing a window that is already `CLOSED` or `FINALIZED` is refused with `ERR_BURDEN_WINDOW_NOT_OPEN`. `closure_reason` records why the window closed and is one of `MANUAL_CLOSE`, `SUPERSEDED_BY_NEW_WINDOW`, `SOURCE_SUSPENDED` or `ALERT_RETIRED`, and `closed_at` records the instant of the most recent close.

The input set for every computation is the alert's firing records whose `fired_at` is at or after `window_start` and strictly before `window_end`; firings of the same alert outside that interval are excluded. From that set the server computes `fire_count` as the number of firings, `override_count` as the number with `accepted` false, `accept_count` as the number with `accepted` true, `distinct_fired_clinician_count` as the number of distinct `firing_clinician_ref` values, and `distinct_overriding_clinician_count` as the number of distinct `firing_clinician_ref` values among the firings with `accepted` false.

Two burden indices are then produced from the same window, and the difference between them is the whole point of the measurement. The **fire-weighted** index is the one stored in `burden_index` and mirrored to the alert. Its `override_rate` is `override_count` divided by `fire_count`, rounded half-up to four decimal places, and is 0.0000 when `fire_count` is 0. Its `volume_factor` is `fire_count` divided by an expected 50 firings per window, rounded half-up to four decimal places, then capped at 2.0. The tier multiplier comes from `severity_tier_snapshot`: 1.6 for `TIER_1_HARD_STOP`, 1.0 for `TIER_2_INTERRUPTIVE`, 0.4 for `TIER_3_PASSIVE`. `burden_index` is then `override_rate` multiplied by the tier multiplier multiplied by `volume_factor` multiplied by 100, rounded half-up to two decimal places, and finally capped at 100.00. The stored `override_rate` and `volume_factor` fields hold these fire-weighted quantities.

The **clinician-weighted** index, stored in `burden_index_clinician_weighted`, counts people instead of interruptions. Its rate is `distinct_overriding_clinician_count` divided by `distinct_fired_clinician_count`, rounded half-up to four decimal places, and is 0.0000 when `distinct_fired_clinician_count` is 0. Its volume factor is `distinct_fired_clinician_count` divided by an expected 20 clinicians per window, rounded half-up to four decimal places, then capped at 2.0. `burden_index_clinician_weighted` is that rate multiplied by the same tier multiplier multiplied by that volume factor multiplied by 100, rounded half-up to two decimal places and capped at 100.00. A high-volume alert that annoys only a handful of clinicians scores far lower here, which is exactly why the retirement gate is pinned to the fire-weighted figure and never consults this one.

`burden_classification` is derived from the fire-weighted `burden_index` alone, and the tests run in this order: if `fire_count` is 0 the classification is `NO_SIGNAL`; otherwise if `burden_index` is at least 65.00 it is `LOW_VALUE`; otherwise if `burden_index` is at most 25.00 it is `HIGH_VALUE`; otherwise it is `MONITOR`. Because the zero-firing test runs first, a window with no firings is `NO_SIGNAL` and not `HIGH_VALUE`, even though its index of 0.00 would otherwise qualify.

Closing a window also updates the alert's ledger: `windowed_fire_count` increases by the window's `fire_count`, `unwindowed_fire_count` becomes `lifetime_fire_count` minus `windowed_fire_count`, and `latest_burden_index` and `latest_burden_classification` are set from the most recently closed window, taken in order of `window_start` descending with `created_at` descending as the tie-break.

Reopening is the `SystemAdmin`'s compensating action, requested with a `reopen_reason`. A window may only be reopened from `CLOSED` — `OPEN` or `FINALIZED` yields `ERR_BURDEN_WINDOW_NOT_CLOSED` — and only while no other window of the same alert is `OPEN`, or the request is refused with `ERR_ANOTHER_WINDOW_OPEN`. Reopening moves the window `CLOSED → OPEN`, resets `fire_count`, `override_count`, `accept_count`, `distinct_fired_clinician_count` and `distinct_overriding_clinician_count` to 0, resets `override_rate`, `volume_factor`, `burden_index`, `burden_index_clinician_weighted`, `burden_classification`, `closure_reason` and `closed_at` to null, and increments `reopen_count` by 1. On the alert, `windowed_fire_count` is reduced by exactly the `fire_count` just discarded, `unwindowed_fire_count` is recomputed as `lifetime_fire_count` minus `windowed_fire_count`, and `lifetime_fire_count` is left unchanged; `latest_burden_index` and `latest_burden_classification` are recomputed from whatever `CLOSED` or `FINALIZED` windows remain, or set to null when none remain. A window may be closed and reopened repeatedly and the firing ledger must not drift. Windows may be listed for an alert filtered by `state` and `burden_classification`.

Suspension pauses a firing alert. The chair supplies a `suspension_reason`, which is stored, and `suspension_count` increments by 1 as `lifecycle_state` moves `ACTIVE → SUSPENDED`; suspending an alert that is not `ACTIVE` is `ERR_ALERT_NOT_ACTIVE`. Because the alert suspended, any burden window of that alert still in state `OPEN` is closed with `closure_reason` `SOURCE_SUSPENDED`, which computes that window's `fire_count`, `override_count`, `accept_count`, `distinct_fired_clinician_count`, `distinct_overriding_clinician_count`, `override_rate`, `volume_factor`, `burden_index`, `burden_index_clinician_weighted` and `burden_classification`; and because that window closed, the alert's `windowed_fire_count`, `unwindowed_fire_count`, `latest_burden_index` and `latest_burden_classification` are all recomputed. Resuming reverses the pause: with an optional `resume_note`, an alert moves `SUSPENDED → ACTIVE` and `suspension_reason` is cleared, provided `lifecycle_state` is `SUSPENDED` (otherwise `ERR_ALERT_NOT_SUSPENDED`), `review_state` is `APPROVED`, and — where `linked_order_set_id` is not null — that order set's `publication_state` is `PUBLISHED`, failing which resumption is refused with `ERR_LINKED_ORDER_SET_NOT_PUBLISHED`. An alert may cycle through suspension and resumption any number of times and `suspension_count` keeps accumulating.

Retirement must be earned. The chair supplies a `retirement_rationale` and may retire an alert from `ACTIVE` or from `SUSPENDED` — any other `lifecycle_state` is `ERR_ALERT_NOT_ACTIVE` — but only when the **low-value retirement gate** is satisfied. The candidate set is the two most recent burden windows of the alert in state `CLOSED` or `FINALIZED`, ordered by `window_start` descending with `created_at` descending as the tie-break; windows still `OPEN` are never considered. The gate passes only when exactly two such candidate windows exist **and** every one of them satisfies all three of these conditions: its `override_rate` is at least 0.9000, its `fire_count` is at least 40, and its fire-weighted `burden_index` is at least 65.00. All comparisons are inclusive, `override_rate` is compared at four decimal places and `burden_index` at two decimal places as stored, and the clinician-weighted index is never consulted. When the gate fails — because fewer than two closed windows exist, or because either candidate window falls short on any one of the three criteria — the request is refused with `ERR_RETIREMENT_CRITERIA_NOT_MET` and the alert stays in its current `lifecycle_state`.

When retirement succeeds, `lifecycle_state` becomes `RETIRED` — a terminal state — and `retired_at` is set to the current instant. Every burden window of the alert still in state `OPEN` is closed with `closure_reason` `ALERT_RETIRED`, and then every window of the alert in state `CLOSED` transitions to `FINALIZED`, which is terminal for a window. The alert's governing annual review task, if it is in state `PENDING` or `OVERDUE`, transitions to `EXPIRED`.

### 3.8. Post-Implementation Adherence Measurement

Publishing an order set is a hypothesis; measurement tests it. A `CommitteeChair`, an `InformaticsBuilder` or a `ClinicalSponsor` records an observation set against a published order set, whose `order_set_id` is taken from the path, supplying `measurement_period_start` and `measurement_period_end` — the period is half-open, with the start inclusive and the end exclusive, and the end must be strictly after the start or the request is refused with `ERR_INVALID_WINDOW_BOUNDS` — plus a `unit_observations` array with at least one row. Each row carries a `unit_code`, an `eligible_orders` count, an `adherent_orders` count and an `unintended_events` count. Every row must satisfy three conditions: `eligible_orders` is at least 0, `adherent_orders` is at least 0 and no greater than `eligible_orders`, and `unintended_events` is at least 0. A row violating any of these is refused with `ERR_INVALID_OBSERVATION_COUNTS`.

A unit whose `eligible_orders` is 0 contributed no denominator and is **excluded** from the adherence arithmetic, though it is retained in `unit_observations` for audit. `included_unit_count` is the number of rows whose `eligible_orders` is greater than 0 and `excluded_unit_count` is the number of rows whose `eligible_orders` is 0. When at least one unit is included the measurement opens in `measurement_state` `PROVISIONAL`; when `included_unit_count` is 0 the measurement is created directly in the terminal state `INSUFFICIENT_DATA`. `unintended_event_count` is the sum of `unintended_events` across *all* rows of `unit_observations`, included and excluded alike. `verdict`, `finalized_at`, `adherence_pct_intention_to_treat` and `unintended_event_rate_per_100` all start null.

At creation the server computes the **per-protocol** adherence figure, which treats every included unit as one equal vote regardless of its volume. For each included row it divides `adherent_orders` by `eligible_orders` and rounds that rate half-up to four decimal places; it sums those per-unit rates and divides the sum by `included_unit_count` to obtain an unweighted mean; it multiplies that mean by 100 and rounds half-up to two decimal places, storing the result in `adherence_pct_per_protocol`.

Finalization is the chair's exclusive step and requires `measurement_state` `PROVISIONAL`; a measurement already `FINALIZED` or `INSUFFICIENT_DATA` is refused with `ERR_MEASUREMENT_NOT_PROVISIONAL`. The chair supplies a `verdict` of `SUSTAIN`, `REVISE` or `RETIRE`, with an optional `finalization_note`. Finalization computes the **intention-to-treat** figure, which pools volume instead of averaging rates: it sums `adherent_orders` over the included rows, sums `eligible_orders` over the included rows, divides the first total by the second, multiplies by 100, rounds half-up to two decimal places, and stores the result in `adherence_pct_intention_to_treat`. Because the per-protocol variant averages rounded per-unit rates while the intention-to-treat variant pools raw numerators and denominators, an observation set whose units have very different volumes legitimately yields two materially different percentages from the identical array. Alongside it the server computes `unintended_event_rate_per_100` as 100 multiplied by the sum of `unintended_events` over the *included* rows, divided by the sum of `eligible_orders` over the included rows, rounded half-up to two decimal places; this rate is always pooled and never averaged.

The submitted verdict must be supported by those computed numbers, and the check runs against the intention-to-treat value computed in this very request, never against the per-protocol value stored at creation. `SUSTAIN` requires `adherence_pct_intention_to_treat` to be at least 70.00 **and** `unintended_event_rate_per_100` to be at most 5.00. `RETIRE` requires `adherence_pct_intention_to_treat` to be below 70.00 **or** `unintended_event_rate_per_100` to be above 5.00. `REVISE` is always permitted. An unsupported verdict is refused with `ERR_ADHERENCE_VERDICT_UNSUPPORTED`.

On success `measurement_state` advances `PROVISIONAL → FINALIZED`, `verdict` and `finalized_at` are stored, and the governed order set's `latest_adherence_pct` is set to this measurement's `adherence_pct_intention_to_treat` — that field always mirrors the most recently finalized measurement for the order set. A verdict of `RETIRE` additionally reopens the governance clock: the governed order set moves `publication_state` `PUBLISHED → EXPIRING` and its annual review task in state `PENDING` transitions to `OVERDUE`. Measurements may be listed for an order set filtered by `measurement_state` and `verdict`.

### 3.9. The Annual Review Cycle, Expiration Sweep and Operational Control

Every published order set and every active alert is governed by an **annual review task**, created automatically at publication or activation. The task records which artifact it governs through `artifact_kind` — `ORDER_SET` or `ALERT` — together with `order_set_id` set for an order-set task and `alert_id` set for an alert task, mirrors the governed artifact's `review_due_date`, `expiration_at` and `archive_eligible_at` for the current cycle, carries a `cycle_index` that is 1 for the first cycle and increments with every attestation that opens a new one, and opens in `state` `PENDING` with `stale_content_triggered` false, `evidence_citations` an empty array, and `attested_at`, `attestation_note` and `attested_by_clinician_id` all null. Tasks may be listed filtered by `order_set_id`, `alert_id`, `attested_by_clinician_id`, `artifact_kind`, `state`, `stale_content_triggered` and `cycle_index`.

**Attestation** is the sponsor's obligation and their exclusive step: only the clinician whose id equals the `clinical_sponsor_id` of the content request governing the artifact may attest, and any other caller is refused with `ERR_ROLE_IDENTITY_MISMATCH`. A task may be attested from `PENDING` or from `OVERDUE`; a task already `ATTESTED` or `EXPIRED` — both terminal — is refused with `ERR_REVIEW_TASK_NOT_OPEN`. The sponsor submits an `evidence_citations` array in the same shape as intake, with a required `citation` string and required `peer_reviewed` boolean per entry plus optional `doi` and `publication_year`, together with an optional `attestation_note`. That array must be non-empty, and an empty array is refused with `ERR_EVIDENCE_INSUFFICIENT`. Attestation sets `attested_at` to the current instant, stores the `attestation_note`, and records `attested_by_clinician_id`. It then recomputes the governed artifact's `review_due_date` as the current instant plus the review interval for the artifact's `risk_class` — 365 days for `STANDARD`, 180 days for `HIGH` — with `expiration_at` 30 days after that and `archive_eligible_at` a further 90 days after that, and it creates a fresh annual review task in state `PENDING` whose `cycle_index` is the attested task's `cycle_index` plus 1, mirroring the new dates. When the governed order set's `publication_state` was `EXPIRING`, attestation returns it to `PUBLISHED` for the new cycle.

The **expiration sweep** is an operational capability available to a `SystemAdmin` or a `CommitteeChair`. It compares the logical clock against the stored schedule dates and drives the whole expiration chain in one pass; every comparison is inclusive, so a sweep run at exactly the due instant does flip the record while a sweep run one second earlier does not. An optional `dry_run` flag makes the sweep report what it would do while applying no transition at all. Its response reports `swept_at` together with the counts `tasks_marked_overdue`, `tasks_expired`, `order_sets_marked_expiring`, `order_sets_expired`, `order_sets_archived`, `alerts_suspended`, `alerts_retired`, `burden_windows_closed` and `downtime_events_closed`.

The chain runs as follows. A task in state `PENDING` whose `review_due_date` the clock has reached moves `PENDING → OVERDUE`, and because that task became overdue, the order set it governs moves `publication_state` `PUBLISHED → EXPIRING` — for a task whose `artifact_kind` is `ALERT` there is no publication change at this step. A task whose `expiration_at` the clock has reached moves to `EXPIRED`, either `OVERDUE → EXPIRED` or, when the sweep never saw the intermediate step, `PENDING → EXPIRED`; and because that task expired, the order set it governs moves to `publication_state` `EXPIRED`, while for an alert task the governed alert moves `lifecycle_state` `ACTIVE → SUSPENDED` directly. An order set reaching `EXPIRED` — whether from `EXPIRING` or straight from `PUBLISHED` when the sweep skipped the intermediate step — cascades onward: every alert whose `linked_order_set_id` names it and whose `lifecycle_state` is `ACTIVE` moves to `SUSPENDED` with `suspension_reason` recorded as `SOURCE_CONTENT_EXPIRED` and `suspension_count` incremented by 1. An order set in `publication_state` `EXPIRED` whose `archive_eligible_at` the clock has reached moves `EXPIRED → ARCHIVED` with `archived_at` set to the current instant; because it archived, every alert linked to it whose `lifecycle_state` is `SUSPENDED` moves to `RETIRED` with `retired_at` set to the current instant; and because each such alert retired, every burden window of that alert in state `CLOSED` moves to `FINALIZED` while every window still `OPEN` is first closed with `closure_reason` `ALERT_RETIRED` and then finalized. The same sweep also closes any downtime event whose `state` is `ACTIVE` and whose `window_end` the clock has passed.

**Downtime** is declared by a `SystemAdmin`, who supplies the `scope` and `mode` described in §2.11, a `window_start` and a `window_end`, an optional `planned` boolean defaulting to true, and an optional free-text `reason` recording the operational cause. `window_end` must be strictly after `window_start`, or the request is refused with `ERR_INVALID_WINDOW_BOUNDS`. A new downtime event may not overlap any existing event whose `state` is `SCHEDULED` or `ACTIVE` and whose scope intersects the new one, where `SYSTEM_WIDE` intersects every other scope; unlike burden windows, downtime intervals are treated as **closed**, so events whose endpoints merely touch do conflict, and the rejection is `ERR_DOWNTIME_WINDOW_OVERLAP`. The event opens in `state` `SCHEDULED` with `blocked_mutation_count` 0, `activated_at` and `closed_at` null, and `declared_by_user_id` holding the declaring operator's opaque identifier.

Activation, with an optional `activation_note`, requires `state` `SCHEDULED` and requires the clock to be at or after `window_start` and at or before `window_end`; any other state, or a clock outside that span, is refused with `ERR_DOWNTIME_EVENT_NOT_SCHEDULED`. On activation `activated_at` is set to the current instant and `state` moves `SCHEDULED → ACTIVE`, at which point the freeze of §2.11 begins. Closing, with an optional `closure_note`, sets `closed_at` to the current instant and takes an `ACTIVE` event to `CLOSED` — which resumes in-scope mutations — or a `SCHEDULED` event to `CANCELLED`; both are terminal, and closing an event already `CLOSED` or `CANCELLED` is refused with `ERR_DOWNTIME_EVENT_NOT_CLOSEABLE`.

Finally, an administrative clock capability sets the logical clock to a supplied `to_iso8601` instant and reports the resulting `current_utc`. The clock starts at `2026-08-01T00:00:00Z`, and moving it never itself performs a transition: the expiration sweep must always be invoked explicitly.
