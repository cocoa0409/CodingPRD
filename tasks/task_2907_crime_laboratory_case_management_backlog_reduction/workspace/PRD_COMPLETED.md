# Forensic Laboratory Casework API — Product Requirements Document

## 1. Introduction

A state forensic laboratory lives and dies by its backlog. Evidence arrives faster than examiners can work it, statutory speedy-trial deadlines run against submissions that nobody has yet triaged, and every hour an examiner spends on the wrong case is an hour stolen from a homicide with a suspect in custody. The laboratory's existing paper-and-spreadsheet workflow cannot answer the three questions the director is asked every week: which cases are late, who is over capacity, and what should be sent out to a vendor laboratory. This document specifies the REST service that answers those questions and enforces the quality-system rules that make the answers defensible in court.

The service covers the whole custody-to-courtroom arc. Front-counter staff submit cases and log physical evidence into the vault; an intake decision either accepts the submission into the laboratory's workload or refuses it and returns the property. Accepted work is decomposed into examination requests, each binding one evidence item to one accredited analytical method, and each landing in that method's discipline queue. Casework coordinators staff those queues either by naming an examiner or by letting the workload balancer pick the least-utilised eligible one, and they may instead award the work to an accredited vendor laboratory under a priced, capacity-limited custody window. Completed bench work passes a technical review by a second examiner and an administrative review by a coordinator before any report is released, with a quality-managed path for resolving technical disagreements.

Wrapped around that flow is an accreditation quality system that the API treats as first-class business logic rather than paperwork: method validation studies with expiry, periodic proficiency testing that can put an examiner on probation, suspend them or decertify them outright, nonconformance findings with severity-driven corrective-action deadlines and escalation on repeated rejection, discovery-request response clocks, and a testimony calendar that refuses to double-book an examiner. Two hard segregation-of-duties principles run through the entire specification: the examiner who performed an examination may never sign its technical review, and the party that submits a corrective-action root cause may never close the finding. Every rule below is written to be deterministic, because the laboratory's turnaround statistics and its accreditation audit trail both depend on the same numbers being reproducible.

All endpoints are mounted under the `/lab` path prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operator Identity and Role Authority

Every request to every endpoint, read or write, must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the authority under which they act. If either header is absent, or is supplied as an empty string, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A header consisting only of an empty value counts as absent for this purpose; only a literally empty value counts as such, so a header carrying nothing but whitespace is a present, non-empty value that passes this rule and is then judged on its own merits — a whitespace-only `X-User-Role` is an unrecognised role string and lands on `ERR_UNAUTHORIZED`, while a whitespace-only `X-User-ID` is simply accepted as the acting operator's identifier.

Five roles exist, spelled exactly as follows: `EvidenceTechnician`, `CaseManager`, `Analyst`, `QualityManager`, and `LabDirector`. If `X-User-Role` carries a value that is not one of those five strings, or carries a recognised role that the requested endpoint does not authorise, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Authorisation outranks payload validity, so an unrecognised role never produces a 400 — it produces the 403.

The roles divide the laboratory's duties deliberately. An `EvidenceTechnician` is front-counter custody staff: they submit cases, log and release physical evidence, and make the intake accept-or-reject decision. A `CaseManager` coordinates casework: raising and routing examination requests, assigning and reassigning examiners, awarding and administering vendor engagements, performing administrative review, reporting cases, handling discovery, owning corrective-action plans, and managing the testimony calendar. An `Analyst` is a bench examiner who performs and completes casework on their own assignments, technically reviews a peer's casework, and sits proficiency tests. A `QualityManager` owns the quality system: validating and retiring methods, running proficiency testing, resolving technical disagreements, opening findings, deciding corrective-action plans, and reinstating suspended examiners — and never performs or administratively releases casework. A `LabDirector` owns the personnel and vendor registries, sets queue-class overrides, and drives the logical clock; the director is deliberately not authorised for administrative review, technical review or corrective-action decisions, so that no single role can both create and release casework.

Identity binds to persisted rows for exactly one role. When `X-User-Role` is `Analyst`, `X-User-ID` is the `id` of the acting `Analyst` row; ownership and segregation-of-duties checks on any resource that references an `Analyst` compare the resource's analyst reference to `X-User-ID` — the `assigned_analyst_id` of an examination request when starting or completing analysis, and the `analyst_id` of a proficiency test when submitting it. When `X-User-Role` is `EvidenceTechnician`, `CaseManager`, `QualityManager` or `LabDirector`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record such an identifier — for example as `reviewer_operator_id` on the immutable review record written by an administrative review or a disagreement resolution — but it never compares it to any entity's `id`.

Two mirror-image identity rules apply to `Analyst` callers and to nobody else. On starting analysis and on completing analysis, the acting `X-User-ID` must equal the request's `assigned_analyst_id`; on submitting a proficiency test, it must equal that test's `analyst_id`. A mismatch is `ERR_ANALYST_IDENTITY_MISMATCH` (HTTP 403). On technical review the comparison is inverted: the acting `X-User-ID` must **not** equal the `assigned_analyst_id`, and a violation is a segregation-of-duties conflict rather than an identity mismatch. Callers acting as `CaseManager`, `QualityManager`, `EvidenceTechnician` or `LabDirector` are never subject to the identity-binding rule.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one instant in the whole service taken from the host's wall clock rather than from the logical clock of §2.5, so it advances between two calls made at the same logical instant and never has to agree with any persisted `_at_utc` stamp.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Default Ordering

List endpoints are paginated with two query parameters. The `limit` parameter caps how many rows are returned; it defaults to 10, has a minimum of 1 and a maximum of 100. The `offset` parameter is the number of rows to skip and defaults to 0, with a minimum of 0. A value outside those bounds is a schema violation and is rejected with `ERR_INVALID_REQUEST`, and so is a value that is not an integer at all: an empty, non-numeric or fractional `limit` or `offset` earns the same 400. Surrounding whitespace is stripped before the value is read, so ` 5 ` is the integer 5. Beyond those two, each list endpoint declares in §3 the query parameters it may be narrowed by, and every one of them is a plain exact-equality filter on the stored field of the same name, compared against the string the client supplied; several supplied together must all match. A filter value is never validated against the field's enum domain: a value that matches no row simply narrows the page to nothing, so a `status`, `severity` or `discipline` filter carrying a value the domain does not contain answers 200 with an empty `data` array and `total_count` 0 rather than `ERR_INVALID_REQUEST`. A query parameter a list endpoint does not declare is ignored rather than rejected.

Unless a list endpoint declares otherwise, rows are returned sorted by their creation timestamp `created_at` in ascending order. Because the logical clock of §2.5 moves only when the director moves it, every row written under one logical instant carries an identical `created_at`; such a tie is broken by insertion order, the row created first coming first. Four list endpoints declare a different order because the laboratory reads them as queues rather than as registries. The case list is ordered by `priority_score` descending, then by `received_at_utc` ascending. The examination-request list — the discipline queue view — is ordered by the owning case's `priority_score` descending, then by `requested_at_utc` ascending. The review-record list is ordered by `recorded_at_utc` ascending. The court-event list is ordered by `start_utc` ascending. In all four, any tie surviving the declared keys is broken by insertion order exactly as it is for the default ordering — the row created first coming first — so two cases carrying both the same `priority_score` and the same `received_at_utc` are returned in the order they were submitted, and `id` is never a tie-break on any list.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` is true exactly when `offset` plus the number of rows actually returned in `data` is still less than `total_count` — so an `offset` at or beyond `total_count` returns an empty `data` array with `has_more` false. The four pagination fields appear only on list responses; the `meta` of a single-resource or computed-document response carries `api_request_id` and `api_request_timestamp` alone.

### 2.4. Record Identity, Audit Stamps and Versioning

Every resource the service persists carries a server-minted `id` formatted as a UUID, with no type prefix of any kind, and a `created_at` timestamp: an ISO 8601 UTC instant rendered with exactly three fractional-second digits, for example `2026-08-01T00:00:00.000Z`. Clients never supply an `id`. That same three-digit rendering is applied to every instant the service emits, including one a client supplied: a client-supplied instant must carry a date, a time of day and a zone designator — either `Z` or a numeric UTC offset such as `+02:00`, which is converted to UTC before the value is stored — while a date-only string, or one with no zone designator at all, is `ERR_INVALID_REQUEST`. Precision finer than a millisecond is accepted on input and truncated, not rounded, to three fractional digits when the value is rendered back.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, a system-managed integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row. This holds for `Analyst`, `Method`, `Case`, `EvidenceItem`, `ExaminationRequest`, `Assignment`, `ProficiencyTest`, `Vendor`, `VendorEngagement`, `Nonconformance` and `CourtEvent` records. Note that a mutation includes a server-initiated one: when a cascade refreshes a case's rolled-up counters, releases an examiner's committed hours or de-encumbers a vendor's contract authority, the affected row's `updated_at` moves and its `version` increments exactly as it would for a client-driven write.

The review record is the one exception. A `ReviewRecord` is immutable once written: it carries only `id` and `created_at`. It has no `updated_at` field and no `version` field at all, and no operation ever modifies one after it has been signed.

### 2.5. The Logical Laboratory Clock

Statutory deadlines, method-validation expiry, backlog aging, vendor custody windows, corrective-action deadlines and testimony notice periods are all time-dependent, so the service does not read wall-clock time. It maintains a **logical clock** that starts at exactly `2026-08-01T00:00:00Z` and only ever moves when a `LabDirector` sets it, by supplying a `current_utc` instant to the clock-setting capability at `POST /lab/_clock/set_current_utc`. The server must not fall back to wall-clock time either before or after that call; the single exception is the envelope's own `api_request_timestamp` of §2.2, which is a transport stamp rather than a business instant. The clock may be driven in either direction: an instant earlier than the one currently in force is accepted and winds the clock back, and setting it to the instant already in force is equally admissible. The call answers 200 and its `data` is not a persisted resource but a one-field document, `current_utc`, rendering the instant now in force.

Every system-sourced instant — every field whose name ends in `_at_utc` and whose value the server assigns rather than the client — is stamped from the logical clock at the moment of the write. So are every derived `notice_days`, every `overdue` recomputation, every `custody_days` figure and every aging computation. Advancing the clock does not itself mutate any row; it changes what the next write stamps and what the next computed read returns.

### 2.6. Numeric Precision: Hours, Days, Percentages and Cents

Hours, day counts, percentages and ratios are decimal numbers carried to exactly 2 decimal places, and every rounding step uses the round-half-up convention. A client that supplies such a figure with more than two decimal places is not refused for that reason: the field's declared range is tested against the value exactly as supplied, and the value is then rounded half up to two places as it is written. All of these figures are emitted as JSON numbers rather than as strings, and the JSON rendering carries no trailing zeros — a stored 43.50 appears as `43.5`, and a stored 0.00 appears as `0.0`. Where a formula in §3 specifies more than one rounding step, the steps are performed in the stated order and each intermediate result is rounded before it feeds the next step; collapsing two rounding steps into one final rounding produces a different, incorrect answer.

Day counts derived from two instants come in two flavours and the difference matters. A **whole-day floor** divides the difference in whole seconds between the two instants by 86400 and discards the remainder, yielding an integer — the quotient is taken toward negative infinity, so an instant that already lies in the past yields a negative figure rather than zero; this is how the priority scorer measures the distance to a statutory deadline or a court date and how testimony notice is measured. A **fractional-day figure** divides the same whole-second difference by 86400 and rounds the quotient half up to 2 decimal places; this is how turnaround, vendor custody and backlog age are measured.

Money is carried exclusively as integer cents. There are no fractional cents anywhere in the vendor ledger: every price, surcharge, discount, award, invoice and variance is an integer, and the only rounding in the pricing chain happens where §3.7 says it happens. Percentage-style rates such as a vendor's `rush_surcharge_pct` and the derived `volume_discount_pct` are decimal fractions — a rate of `0.12` means twelve percent — while utilisation figures such as `projected_utilization_pct` are expressed on a 0-to-100 scale.

### 2.7. Stale-Record Protection on Parent Records

Two write endpoints supersede something a client may not have observed, and both therefore demand that the client prove which version of the parent record it was looking at. This is optimistic concurrency control, and the required field is not optional.

Creating or replacing an assignment on an examination request requires `expected_examination_request_version` in the request body, carrying the client's last observed `version` of that `ExaminationRequest`. If the value does not equal the request's current `version`, the write is refused with `ERR_STALE_EXAM_REQUEST_VERSION` (HTTP 412) and nothing is created. Because a reassignment legitimately supersedes the incumbent holder, a writer working from a stale view of the request would otherwise silently displace a holder it never saw.

Recording a priority override on a case requires `expected_case_version` in the request body, carrying the client's last observed `version` of that `Case`. A mismatch with the case's current `version` is refused with `ERR_STALE_CASE_VERSION` (HTTP 412). Each override supersedes the prior override, and the derived queue class it replaces may have moved through intake, request creation or an earlier override, so the check is what makes the supersede deterministic.

No other endpoint in the service accepts a version field. Supplying `expected_examination_request_version` or `expected_case_version` anywhere else is an unknown field and is rejected with `ERR_INVALID_REQUEST`.

### 2.8. The Normative Rule Evaluation Order

Many write endpoints can fail for several reasons at once, and an accreditation audit trail is only useful if the reported reason is predictable. The service therefore evaluates checks in one fixed order on every write endpoint. When a single request violates two rules, the earlier rule in this list determines the response, and no side effect belonging to any later rule is applied. The order is normative, not advisory:

1. **Headers.** Both `X-User-ID` and `X-User-Role` are present and non-empty, else `ERR_UNAUTHENTICATED` (401).
2. **Role authority.** `X-User-Role` is one of the five declared roles and that role is authorised for this endpoint, else `ERR_UNAUTHORIZED` (403). An unrecognised role string lands here, never at the schema check.
3. **Path identifiers.** Every identifier segment in the URL resolves to an existing row of its declared entity, checked left to right, else the entity's own not-found code (404).
4. **Body schema.** The body parses, carries every required field, carries no unknown field, and every value matches its declared type, enum domain and numeric range, else `ERR_INVALID_REQUEST` (400). A malformed ISO 8601 instant, a negative `item_count`, a `competency_level` outside 1 through 5, and a `score_pct` outside 0.00 through 100.00 all land here. The body is read as JSON whatever `Content-Type` the request declares, and an absent body, an empty body and a body of literal `null` are all treated as an empty JSON object — so an endpoint whose every field is optional, or which declares no body at all, succeeds on a request that sends nothing. A body that parses to anything that is not a JSON object is a 400. An explicit `null` satisfies only a field §3 describes as nullable; supplying `null` for any other field, including an optional one carrying a documented default, is a 400 rather than a request for that default. A JSON boolean never satisfies a declared integer or number, and a number carrying a fractional part never satisfies a declared integer. Where §3 declares a character range for a text field that range is enforced; where it declares none, any string satisfies the schema, the empty string included, unless §3 separately demands a non-empty value as it does for the `response_note` of a discovery denial.
5. **Body foreign keys.** Every identifier carried in the body resolves to an existing row of its declared entity, else that entity's not-found code (404). Body foreign keys are resolved after the schema check so that a syntactically invalid identifier yields 400 rather than 404. Where one body carries more than one such identifier they are resolved in the order §3 lists them for that endpoint, so a body naming two rows that neither exist reports the not-found code of the earlier identifier in that written order — `analyst_id` before `method_id` when a proficiency test is assigned, and `examination_request_id` before `analyst_id` when a finding is opened or a testimony block is scheduled.
6. **Analyst identity binding.** For an `Analyst` caller, `X-User-ID` equals the analyst the operation acts as, else `ERR_ANALYST_IDENTITY_MISMATCH` (403). Only three operations apply this binding — starting bench work, completing bench work and submitting a proficiency test — and no read applies it at all: an `Analyst` caller may read any examiner's record, workload document or proficiency test, not merely their own.
7. **Scoped uniqueness.** No scoped uniqueness key is already taken, else `ERR_DUPLICATE_RESOURCE` (409).
8. **State guard.** The target row is in a state from which the requested transition is declared, else that entity's own invalid-state code (409): `ERR_CASE_INVALID_STATE` for a case's `workflow_status`, `ERR_EVIDENCE_CUSTODY_INVALID_STATE` for an evidence item's custody position — which is also the code for the custody-position guard requiring `IN_VAULT` before a checkout, `IN_ANALYSIS` before a check-in, and refusing any re-checkout of a `CONSUMED` item — `ERR_EXAM_REQUEST_INVALID_STATE` for an examination request, `ERR_METHOD_INVALID_STATE` for a method's `validation_status`, `ERR_PT_INVALID_STATE` for a proficiency test, `ERR_VENDOR_ENGAGEMENT_INVALID_STATE` for a vendor engagement, `ERR_NONCONFORMANCE_INVALID_STATE` for a quality finding, `ERR_COURT_EVENT_INVALID_STATE` for a testimony block, and `ERR_ANALYST_INVALID_QUALIFICATION_STATE` for an examiner's `qualification_state`. This is the general non-linear-state-machine guard and it outranks every temporal, capacity and fiscal check below it.
9. **Stale-record check.** Where the endpoint declares an expected-version field, its value equals the parent row's current `version`, else that parent's stale-version code (412) — `ERR_STALE_EXAM_REQUEST_VERSION` when the parent is an examination request and `ERR_STALE_CASE_VERSION` when it is a case. Only the two operations named in §2.7 declare such a field; no other endpoint accepts one.
10. **Cross-entity referential coherence.** Named rows that all exist nonetheless belong together, else `ERR_REFERENTIAL_MISMATCH` (409).
11. **Evidence seal integrity.** Chain-of-custody seal integrity holds — every evidence item of a case being accepted has `seal_intact` true, and no item is ever checked out of the vault with a broken seal — else `ERR_EVIDENCE_SEAL_BROKEN` (409). This is the highest-ranked business rule in the laboratory; it outranks the per-method item cap at rule 24, so an item with a broken seal and an over-cap request count reports the seal defect.
12. **Method validation.** The named method is `VALIDATED` and, where analysis is starting, its validation has not lapsed against the logical clock, else `ERR_METHOD_NOT_VALIDATED` (409) for a `DRAFT` or `RETIRED` method and the distinct `ERR_METHOD_VALIDATION_EXPIRED` (409) for a validated method whose expiry instant is at or before the clock.
13. **Analyst standing.** The subject analyst has `employment_status` `ACTIVE` and `qualification_state` `QUALIFIED` or `PROBATION`. An `employment_status` other than `ACTIVE` yields `ERR_ANALYST_NOT_ACTIVE` (409) and a `DECERTIFIED` analyst yields `ERR_ANALYST_DECERTIFIED` (409); both of those are tested before the qualified-or-probation test, whose own failure yields `ERR_ANALYST_NOT_QUALIFIED` (409). This rule concerns the *subject* analyst of the operation, not the caller identity, which was rule 6.
14. **Segregation of duties.** The acting reviewer is not a party they may not review, else `ERR_SEGREGATION_OF_DUTIES` (409).
15. **Vendor accreditation.** The named vendor is accredited for the discipline and its accreditation outlasts the custody window, else `ERR_VENDOR_NOT_ACCREDITED` (409). Accreditation is a safety gate and deliberately outranks the fiscal ceiling at rule 27, so an unaccredited vendor whose award would also breach the contract ceiling reports the accreditation defect.
16. **Vendor availability.** The named vendor's `status` is `ACTIVE`, else `ERR_VENDOR_SUSPENDED` (409). Checked after accreditation, so a vendor that is both suspended and unaccredited reports the accreditation defect.
17. **Vendor concurrent capacity.** The vendor's concurrent custody capacity is not exceeded, else `ERR_VENDOR_CAPACITY_EXCEEDED` (409).
18. **Testimony non-overlap.** The examiner's testimony calendar has no conflicting block, else `ERR_TESTIMONY_SCHEDULE_CONFLICT` (409). This is deliberately ranked below the state guard at rule 8.
19. **Testimony notice.** The notice period is sufficient or a subpoena has been served, else `ERR_INSUFFICIENT_TESTIMONY_NOTICE` (422).
20. **Probation priority restriction.** A probationary examiner is offered only routine-class work, else `ERR_PROBATION_PRIORITY_RESTRICTED` (409). Evaluated against the case's effective queue class, so a director override down to routine class makes an otherwise blocked assignment admissible.
21. **Remediation training minimum.** A probationary examiner meets the standing training minimum, else `ERR_TRAINING_MINIMUM_NOT_MET` (409). Checked after the priority restriction, so a probationary examiner offered statutory-class work reports the restriction rather than the training shortfall.
22. **Discipline match.** The subject analyst's `disciplines` contains the method's `discipline`, else `ERR_ANALYST_DISCIPLINE_MISMATCH` (409).
23. **Competency floor.** The subject analyst's `competency_level` is at least the method's `min_competency_level`, else `ERR_ANALYST_COMPETENCY_INSUFFICIENT` (409). Checked after the discipline test, so an out-of-discipline junior examiner reports the discipline defect.
24. **Per-method item cap.** The request's `item_count` does not exceed the method's `max_items_per_request`, else `ERR_ITEM_COUNT_EXCEEDS_METHOD_LIMIT` (422).
25. **Examiner capacity.** The subject analyst's post-assignment projected utilisation does not exceed the utilisation ceiling, else `ERR_ANALYST_CAPACITY_EXCEEDED` (409).
26. **Candidate pool.** On automatic balancing, at least one eligible candidate exists, else `ERR_NO_ELIGIBLE_ANALYST` (409).
27. **Contract ceiling.** The vendor's committed and spent authority plus the newly priced award does not exceed the contract ceiling, else `ERR_VENDOR_CEILING_EXCEEDED` (402). This is the lowest-ranked gate of all: the award is priced in full, tier discount included, and every safety gate above it has already passed, before the money is tested.

Two additional checks sit outside that battery because they are properties of a single submitted field pair rather than of the laboratory's state. An interval whose endpoints are not strictly increasing — a vendor custody window whose `window_end_utc` is at or before its `window_start_utc`, or a testimony block whose `end_utc` is at or before its `start_utc` — is refused with `ERR_INVALID_INTERVAL` (HTTP 422), and this is established before any capacity arithmetic that would consume the interval. A method-validation study that falls short of the accreditation minima is refused with `ERR_METHOD_VALIDATION_INSUFFICIENT` (HTTP 422).

### 2.9. Path Identifier Resolution

Where a URL carries more than one identifier segment, the service resolves them strictly left to right and rejects on the first segment that does not name an existing row, returning that entity's own not-found code. A vendor engagement addressed under a non-existent examination request therefore reports `ERR_EXAM_REQUEST_NOT_FOUND` and never attempts to look further. The same left-to-right discipline governs creation: a parent segment's existence is established before any child-level or body-level rule is consulted, and a child row that exists but belongs to a different parent than the path declares is reported as not found for that path rather than as a mismatch. Matching the request against the set of paths this document declares happens earlier still, ahead of the header check of §2.8 rule 1: a request to a path that is not declared here answers HTTP 404 carrying `error_id` `ERR_INVALID_REQUEST`, and a request to a declared path under an HTTP method that path does not declare answers HTTP 405 carrying the same `error_id` — these two routing failures are the only occasions on which `ERR_INVALID_REQUEST` is returned under a status other than the 400 tabulated in §5, and they are reported whether or not the request carried identity headers. A trailing slash is insignificant in routing: `/lab/cases` and `/lab/cases/` address the same endpoint.

Each entity has its own not-found code: `ERR_ANALYST_NOT_FOUND`, `ERR_METHOD_NOT_FOUND`, `ERR_CASE_NOT_FOUND`, `ERR_EVIDENCE_ITEM_NOT_FOUND`, `ERR_EXAM_REQUEST_NOT_FOUND`, `ERR_ASSIGNMENT_NOT_FOUND`, `ERR_REVIEW_RECORD_NOT_FOUND`, `ERR_PROFICIENCY_TEST_NOT_FOUND`, `ERR_VENDOR_NOT_FOUND`, `ERR_VENDOR_ENGAGEMENT_NOT_FOUND`, `ERR_NONCONFORMANCE_NOT_FOUND` and `ERR_COURT_EVENT_NOT_FOUND`. Each is returned with HTTP 404, and each covers both a path segment and a body reference naming that entity — so an `analyst_id` supplied in a request body that resolves to nothing is also `ERR_ANALYST_NOT_FOUND`. The addressable path identifiers are `analyst_id`, `method_id`, `vendor_id`, `case_id`, `evidence_item_id`, `examination_request_id`, `assignment_id`, `review_record_id`, `proficiency_test_id`, `vendor_engagement_id`, `nonconformance_id` and `court_event_id`.

### 2.10. Cascading Reconciliation: Case Rollup, Hour Release and Hold Reopening

Three named reconciliations recur throughout §3. They are described once here, in full, and referred to by name later; each is a server-initiated mutation of the rows it touches, so each refreshes `updated_at` and increments `version` on every row it changes.

Before describing them, three groupings of examination-request status are worth naming, because the reconciliations key off them. The **active casework states** are `ASSIGNED`, `IN_ANALYSIS`, `TECH_REVIEW`, `DISAGREEMENT`, `ADMIN_REVIEW` and `OUTSOURCED`. The **terminal states** are `RELEASED` and `CANCELLED`. The **hold states** — the only two states in which an examiner's assignment is `ACTIVE` and their hours are encumbered — are `ASSIGNED` and `IN_ANALYSIS`.

**Case rollup.** Whenever an examination request of a case is created, changes status, or is cancelled, the owning case is reconciled. The rollup applies only while the case's `workflow_status` is `ACCEPTED`, `IN_PROGRESS` or `AWAITING_ASSIGNMENT`; a case that is `SUBMITTED`, `REPORTED` or `REJECTED` is left entirely alone. Within those three statuses the rollup decides the new `workflow_status` as follows: if the case has no examination requests at all, the `workflow_status` is left as it is; otherwise, if at least one of the case's requests is in an active casework state the case becomes `IN_PROGRESS`; otherwise, if at least one is `QUEUED` the case becomes `AWAITING_ASSIGNMENT`; otherwise — every request is terminal — the case becomes `IN_PROGRESS`. In every invocation, whether or not the status changed, the rollup refreshes `open_examination_request_count` to the number of the case's requests whose status is neither `RELEASED` nor `CANCELLED`, refreshes `released_examination_request_count` to the number whose status is `RELEASED`, refreshes `updated_at` and increments the case's `version` by 1.

**Probation release.** When an examiner enters `PROBATION`, every `ACTIVE` assignment they hold whose request belongs to a case whose effective `priority_class` is `P1_STATUTORY` or `P2_VIOLENT` is released: the assignment's `status` becomes `RELEASED` with `closed_at_utc` stamped from the logical clock, the assignment's snapshotted `estimated_hours` is subtracted from the examiner's `assigned_casework_hours`, the request's `assigned_analyst_id` is cleared to null, the request's `status` falls back to `QUEUED`, and the case rollup then runs on each affected case. Routine-class work is left in the examiner's hands.

**Full release.** When an examiner is suspended or decertified, the identical release runs with no queue-class filter at all: every `ACTIVE` assignment they hold is released, every affected request falls back to `QUEUED` with its `assigned_analyst_id` cleared, the hours come off `assigned_casework_hours`, and the case rollup runs per affected case.

Released assignments are never restored. When an examiner later returns to `QUALIFIED` or is reinstated from suspension, the work that was taken from them stays in the queue for someone else to pick up; this is what keeps the committed-hours ledger consistent with hold-state membership.

**Hold reopening.** Two revision paths — an administrative review that returns the file, and a disagreement resolved in the reviewer's favour — send a request back to bench work, and both must decide whether the original examiner can pick it up again. The decision procedure is identical in both cases. Let the candidate assignment be the request's `Assignment` row whose `status` is `COMPLETED` and whose `assigned_at_utc` is the greatest, breaking a tie by the earlier `created_at` and any tie remaining after that by insertion order, the row created first winning — because the logical clock stands still between writes, both stamps are routinely identical on a file that has been round the loop more than once, so insertion order is the key that actually decides. The *reopen branch* is taken when the request's `assigned_analyst_id` is not null and that examiner's `employment_status` is `ACTIVE` and either their `qualification_state` is `QUALIFIED`, or their `qualification_state` is `PROBATION` while the case's effective `priority_class` is `P3_ROUTINE` and their `training_hours_per_week` is at least 8.00. On the reopen branch the candidate assignment's `status` returns to `ACTIVE`, its `closed_at_utc` is cleared to null, its snapshotted `estimated_hours` is added back to the examiner's `assigned_casework_hours`, the request returns to `IN_ANALYSIS`, and the evidence item is checked out of the vault again. That re-checkout is unconditional: the cascade writes `custody_status` `IN_ANALYSIS` and increases `checkout_count` by 1 from whatever custody position the item currently holds, a `CONSUMED` item included, because the custody-position guard of §2.8 rule 8 governs client-driven checkouts and not this server-initiated movement. Otherwise the *requeue branch* is taken: the candidate assignment stays `COMPLETED`, the request's `assigned_analyst_id` is cleared to null, the request returns to `QUEUED`, no hours are re-encumbered, and the case rollup runs.

### 2.11. Standing Ledger Invariants

Two accumulator fields exist purely so that a reader does not have to re-aggregate the whole database, and both must agree with their aggregate definition exactly, with no drift, after every forward action and after every compensating action.

The **committed casework hours** invariant fixes each examiner's `assigned_casework_hours` at the sum of the snapshotted `estimated_hours` of that examiner's assignments whose `status` is `ACTIVE`, rounded half up to 2 decimal places. Assignments that are `SUPERSEDED`, `RELEASED` or `COMPLETED` contribute nothing. Equivalently, summed across the whole laboratory, the total of every examiner's `assigned_casework_hours` equals the total `estimated_hours` of the examination requests that are in a hold state with a non-null `assigned_analyst_id`, rounded half up to 2 decimal places. This identity is checked after every assignment mutation — creation, supersede, release, completion and reopening — and is exposed through the examiner workload read.

The **vendor encumbrance** invariant fixes each vendor's `encumbered_cents` at the sum of `award_amount_cents` over that vendor's engagements whose `status` is `AWARDED` or `AT_VENDOR`, and their `spent_cents` at the sum of `final_invoice_cents` over that vendor's engagements whose `status` is `RETURNED`. A `CANCELLED` engagement contributes to neither sum. Cancellation is the exact compensating action of an award: after cancelling, the vendor's `encumbered_cents` equals what it was before the award was made and their `spent_cents` is likewise untouched, leaving zero residue in either counter.

## 3. Business Logic & Workflows

### 3.1. Intake: Case Submission, Priority Scoring and Evidence Custody

Casework begins at the front counter. An `EvidenceTechnician` submits a **Case** by supplying the submitting agency's own `agency_case_number` (1 to 40 characters), the `submitting_agency` itself (1 to 80 characters), and the charged `offense_category`, which is one of `HOMICIDE`, `SEXUAL_ASSAULT`, `AGG_ASSAULT`, `ROBBERY`, `BURGLARY`, `DRUG_OFFENSE`, `PROPERTY_CRIME` or `OTHER`. Three optional facts sharpen the triage: `suspect_in_custody`, a boolean that defaults to false when omitted, and the two nullable instants `statutory_deadline_utc` (the speedy-trial deadline, null when the submission carries none) and `court_date_utc` (the scheduled trial date, null when unscheduled). The agency's case number must be unique within the submitting agency; a repeat is refused with `ERR_DUPLICATE_RESOURCE`. That pair is checked against every case the service holds, whatever its `workflow_status`, so refusing a submission at intake does not free its number for resubmission. On acceptance of the submission the server stamps `received_at_utc` from the logical clock — this instant is the baseline for priority tiers, backlog aging and turnaround alike — and sets `workflow_status` to `SUBMITTED` and `discovery_status` to `NONE`.

Two derived facts are computed at that same moment. The `violent_crime_flag` is true exactly when the `offense_category` is one of `HOMICIDE`, `SEXUAL_ASSAULT`, `AGG_ASSAULT` or `ROBBERY`, and false for the other four categories. The `priority_score` and `priority_class` follow from the scoring model described next.

The scoring model runs in a pinned order, and the order is what makes the arithmetic reproducible. **First**, two whole-day distances are measured from `received_at_utc`. The days-to-deadline figure is null when `statutory_deadline_utc` is null, and otherwise the whole-day floor of the interval from `received_at_utc` to `statutory_deadline_utc`. The days-to-court figure is null when `court_date_utc` is null, and otherwise the whole-day floor of the interval from `received_at_utc` to `court_date_utc`. **Second**, each distance earns points on a descending band. Deadline points are 0 when the distance is null, 30 when the deadline is 14 days away or nearer, 22 when it is more than 14 and at most 30 days away, 14 when it is more than 30 and at most 60 days away, 6 when it is more than 60 and at most 120 days away, and 0 beyond 120 days. Court points are 0 when the distance is null, 10 when the trial date is 30 days away or nearer, 5 when it is more than 30 and at most 60 days away, and 0 beyond 60 days. **Third**, severity and custody combine into a base: each offence category carries its own weight — 40 for `HOMICIDE`, 36 for `SEXUAL_ASSAULT`, 30 for `AGG_ASSAULT`, 26 for `ROBBERY`, 16 for `BURGLARY`, 12 for `DRUG_OFFENSE`, 8 for `PROPERTY_CRIME` and 4 for `OTHER` — and a further 15 points are added when `suspect_in_custody` is true. That base is then multiplied by 1.10 when the `violent_crime_flag` is true and by 1.00 when it is not, and the product is rounded half up to 2 decimal places to give the weighted base. The violence multiplier applies to the severity-plus-custody subtotal only; it never touches the temporal points. **Fourth**, the two temporal signals blend non-linearly: the larger of the deadline points and the court points counts in full, the smaller counts at half its value, and the sum is rounded half up to 2 decimal places. **Fifth and last**, the weighted base and the blended temporal points are added, rounded half up to 2 decimal places, and capped at 100.00 — the cap is applied after the addition, never before it. The result is `priority_score`, and it is computed once at intake and never recomputed thereafter.

The queue class is derived separately and answers a different question: not "how urgent is this" but "which queue does it sit in". A director's `priority_override_class`, when one is in force, wins outright. Absent an override, the class is `P1_STATUTORY` when the days-to-deadline figure is not null and is at most 30 days; otherwise `P2_VIOLENT` when the `violent_crime_flag` is true; otherwise `P3_ROUTINE`. A `LabDirector` records an override by supplying a `priority_override_class` of `P1_STATUTORY`, `P2_VIOLENT` or `P3_ROUTINE`, a `priority_override_reason` justifying it, and the `expected_case_version` described in §2.7. An override is admissible whatever the case's `workflow_status` — a case still `SUBMITTED`, one already `REPORTED` and even a `REJECTED` one may be overridden, the version check of §2.7 being the only gate beyond role and schema. Each override replaces both fields outright and re-derives `priority_class` with the override winning; the `priority_score` is deliberately left untouched, and the case's open examination requests are simply re-weighted in the backlog index the next time it is read.

Physical property is logged separately from the case that owns it. An `EvidenceTechnician` logs an **EvidenceItem** by naming its `case_id`, the agency's `item_number` label (1 to 20 characters, unique within that case, a repeat being `ERR_DUPLICATE_RESOURCE`), a free-text `item_description`, the physical `item_type` — one of `BIOLOGICAL`, `CHEMICAL`, `FIREARM`, `LATENT_LIFT`, `DIGITAL_DEVICE` or `TRACE_MEDIA` — and the boolean `seal_intact` recording chain-of-custody seal integrity as observed at the counter. Items may only be logged while the case is still `SUBMITTED`; logging against a case in any other `workflow_status` is `ERR_CASE_INVALID_STATE`. A newly logged item has `custody_status` `IN_VAULT`, a `checkout_count` of 0 and a `logged_at_utc` stamped from the logical clock.

The intake decision closes the counter's involvement. Accepting a submission moves `workflow_status` from `SUBMITTED` to `ACCEPTED` and stamps `accepted_at_utc`; the technician may attach an optional `acceptance_note`. Acceptance demands two things of the evidence: the case must carry at least one logged item, else `ERR_CASE_HAS_NO_EVIDENCE`, and every one of those items must have `seal_intact` true, else `ERR_EVIDENCE_SEAL_BROKEN`. Both are tested after the `SUBMITTED` state guard of §2.8 rule 8 and in the order written, so a case that is not `SUBMITTED` reports `ERR_CASE_INVALID_STATE` even when it also carries no logged evidence. Refusing a submission instead requires a `rejection_reason` and moves `workflow_status` from `SUBMITTED` to `REJECTED`, which is terminal — no examination request may ever be raised on a rejected case. Refusal cascades to the property: every one of the case's items still `IN_VAULT` moves to `RETURNED`.

Property leaves the vault for good once its case is closed out. An `EvidenceTechnician` releases an item back to the submitting agency, optionally recording a `return_note`, moving `custody_status` from `IN_VAULT` to the terminal `RETURNED`. This is admissible only while the item is genuinely `IN_VAULT` — an item that is `IN_ANALYSIS`, already `RETURNED` or `CONSUMED` yields `ERR_EVIDENCE_CUSTODY_INVALID_STATE` — and only when the owning case's `workflow_status` is `REPORTED` or `REJECTED`, else `ERR_CASE_INVALID_STATE`.

### 3.2. Accreditation Scope: Methods, Validation Studies and Retirement

Nothing may be examined by a method the laboratory is not accredited to run, so the **Method** catalogue is owned by the `QualityManager`. Registering a method requires a `name` (1 to 160 characters), the owning `discipline` — one of `BIOLOGY`, `CHEMISTRY`, `LATENT_PRINTS`, `TRACE` or `DIGITAL`, which is what drives queue routing and examiner eligibility — the accredited `standard_hours_per_item` (greater than 0.00, at most 40.00, 2 decimal places), the `min_competency_level` an examiner must hold to perform or technically review the method (an integer from 1 to 5), and the `accreditation_scope_code` (1 to 40 characters) that audit findings cite. Three inputs are optional: `max_items_per_request`, the accreditation-scope cap on items examined under one request, an integer from 1 to 200 that defaults to 20; `is_consumptive`, a boolean defaulting to false that declares whether the method destroys the item it examines; and the intended `validation_expires_at_utc`. A method may also be registered with its `validation_study_item_count` and `precision_cv_pct` already known. Those three optional figures are recorded exactly as supplied and may each be sent as null: registration applies neither the study minima nor any comparison of `validation_expires_at_utc` against the clock, and `validated_at_utc`, `retired_at_utc` and `retirement_reason` all start null. Every method is born with `validation_status` `DRAFT`, and no examination request may name it until it is `VALIDATED`.

Validation is the gate. The `QualityManager` records a completed validation study by supplying the `validation_study_item_count` actually examined, the `precision_cv_pct` — the coefficient of variation the study reported, in percent, at least 0.00 and carried to 2 decimal places — and an `expires_at_utc` instant at which the validation will lapse. The study is accepted only if it examined at least 12 items and its coefficient of variation is at most 5.00 percent; a study that examined fewer items or reported a higher coefficient is refused with `ERR_METHOD_VALIDATION_INSUFFICIENT`. The supplied `expires_at_utc` must be strictly after the logical clock, else `ERR_INVALID_REQUEST`. On success `validation_status` moves `DRAFT` → `VALIDATED`, `validated_at_utc` is stamped from the logical clock, and `validation_expires_at_utc` takes the supplied instant. Validating a method that is not `DRAFT` is `ERR_METHOD_INVALID_STATE`. Once the body has passed its schema these three conditions are evaluated in a fixed order: the `DRAFT` state guard first, then the study minima, then the `expires_at_utc` comparison against the clock. A `RETIRED` method presented with a two-item study therefore reports the invalid state, and a `DRAFT` method presented with a two-item study *and* an already-lapsed `expires_at_utc` reports `ERR_METHOD_VALIDATION_INSUFFICIENT`.

Withdrawal from scope is the mirror image. Retiring a method requires a `retirement_reason` and moves `validation_status` `VALIDATED` → `RETIRED`, which is terminal, stamping `retired_at_utc`. Retiring anything that is not `VALIDATED` is `ERR_METHOD_INVALID_STATE`. Retirement cascades in two hops: first, every examination request naming the retired method whose status is still `QUEUED` moves to `CANCELLED`; second, because those requests just became terminal, the case rollup of §2.10 runs on each affected case, refreshing its `open_examination_request_count`. Requests already past `QUEUED` are untouched by retirement and may run to completion — retirement withdraws the method from *future* work, not from work in flight.

Validation also lapses on its own. Because expiry is evaluated against the logical clock rather than against the instant of queuing, a request raised under a live method is blocked from starting once the validation lapses: the method is still `VALIDATED`, but its `validation_expires_at_utc` is at or before the clock, and bench work is refused with the distinct `ERR_METHOD_VALIDATION_EXPIRED` rather than with `ERR_METHOD_NOT_VALIDATED`.

### 3.3. Raising Examination Requests into the Discipline Queues

An **ExaminationRequest** is the unit of laboratory work: one evidence item, one accredited method, one queue. A `CaseManager` raises one by naming the `case_id`, the `evidence_item_id` to be examined, the `method_id` to apply, and the `item_count` — the number of items examined under this request, an integer of at least 1 at the schema layer. The three body references are resolved in exactly that written order — `case_id`, then `evidence_item_id`, then `method_id` — so a body naming two rows that do not exist reports the not-found code of the earlier one by that order.

Four coherence rules guard the pairing. The named item must belong to the named case: an `evidence_item_id` whose own `case_id` is some other case is `ERR_REFERENTIAL_MISMATCH`. The method's `discipline` must be admissible for the item's `item_type`, and the admissible pairings are exactly these: `BIOLOGY` examines `BIOLOGICAL` items, `CHEMISTRY` examines `CHEMICAL` items, `LATENT_PRINTS` examines `LATENT_LIFT` or `FIREARM` items, `TRACE` examines `TRACE_MEDIA` items, and `DIGITAL` examines `DIGITAL_DEVICE` items; any other combination is `ERR_REFERENTIAL_MISMATCH`. The named method must be `VALIDATED` — a `DRAFT` or `RETIRED` method is `ERR_METHOD_NOT_VALIDATED`. And the owning case must be past intake and not closed out: requests may be raised only while its `workflow_status` is `ACCEPTED`, `IN_PROGRESS` or `AWAITING_ASSIGNMENT`, else `ERR_CASE_INVALID_STATE`. Separately, the same evidence item may not be sent to the same method twice: the pair of `evidence_item_id` and `method_id` must be unique across all requests whose status is not `CANCELLED`, a repeat being `ERR_DUPLICATE_RESOURCE`. A cancelled request frees its pair for reuse.

The `item_count` also faces the accreditation-scope cap: a count exceeding the method's `max_items_per_request` is refused with `ERR_ITEM_COUNT_EXCEEDS_METHOD_LIMIT` (HTTP 422). Note where this sits in the order of §2.8 — a request naming a broken-seal item *and* an over-cap count reports the seal defect, not the cap.

On success the request copies its `discipline` from the method — that copy is the queue it will sit in for the rest of its life, unaffected by any later method edit — and computes its `estimated_hours` as the method's `standard_hours_per_item` multiplied by the `item_count`, rounded half up to 2 decimal places. That estimate is never recomputed: a later change to the method's standard hours cannot retroactively re-price an encumbered estimate. The new request has `status` `QUEUED`, `revision_round` 0, `assigned_analyst_id` null, `actual_hours_logged` null, `released_at_utc` null, `vendor_custody_days` 0.00 and a `requested_at_utc` stamped from the logical clock, which becomes its aging baseline. The case rollup of §2.10 then runs: a case that was `ACCEPTED` becomes `AWAITING_ASSIGNMENT` on its first request, and `open_examination_request_count` is refreshed.

The queue itself is read as a list, narrowable by `case_id`, `evidence_item_id`, `method_id`, `assigned_analyst_id`, `discipline` or `status`, and ordered as §2.3 specifies so that the most urgent case's oldest request appears first. A request's `status` takes one of nine values across its life: `QUEUED`, `ASSIGNED`, `IN_ANALYSIS`, `TECH_REVIEW`, `DISAGREEMENT`, `ADMIN_REVIEW`, `OUTSOURCED`, `RELEASED` and `CANCELLED`.

### 3.4. Staffing the Bench: Assignment, Reassignment and Automatic Balancing

Examiners are personnel records owned by the `LabDirector`. Registering an **Analyst** requires a `full_name` (1 to 120 characters), a non-empty `disciplines` array drawn from `BIOLOGY`, `CHEMISTRY`, `LATENT_PRINTS`, `TRACE` and `DIGITAL`, and a `weekly_capacity_hours` figure greater than 0.00 and at most 60.00, carried to 2 decimal places, being the contracted weekly hours available for laboratory duties. Three inputs are optional. The `competency_level` is an integer on the closed range 1 through 5, where 1 is a trainee and 5 a technical lead, and defaults to 1; any integer outside that range is a schema violation. The `training_hours_per_week` figure is the standing weekly commitment reserved for training and competency maintenance; it defaults to 0.00, must be at least 0.00, and may not exceed the examiner's own `weekly_capacity_hours`. The `employment_status` is one of `ACTIVE`, `ON_LEAVE` or `SEPARATED` and defaults to `ACTIVE`; it is a staffing-availability dimension entirely independent of the quality-system standing described in §3.8. A newly registered examiner starts with `qualification_state` `QUALIFIED`, `consecutive_pt_failures` 0, `assigned_casework_hours` 0.00, and both `probation_entered_at_utc` and `suspended_at_utc` null.

The director may later adjust an examiner's `weekly_capacity_hours`, `training_hours_per_week`, `competency_level`, `disciplines` set or `employment_status`. Such an adjustment re-derives the availability and utilisation figures on the next read, but it deliberately has no retroactive force: no existing assignment is released by it, and no snapshotted `estimated_hours` is re-priced by it. Every field of the adjustment is optional, and the call counts as a mutation whatever it carries: an adjustment that supplies no field at all, or one that supplies a field's existing value, still refreshes `updated_at` and increments `version` by 1. The training-versus-capacity ceiling is enforced against the values the row will hold after the adjustment, so a supplied `training_hours_per_week` is compared with a supplied `weekly_capacity_hours` when both are present and with the stored one otherwise, a breach being `ERR_INVALID_REQUEST`.

**Availability and utilisation.** An examiner's available hours are their `weekly_capacity_hours` minus their `training_hours_per_week`, floored at 0.00 and rounded half up to 2 decimal places — training time is carved out of capacity before casework is considered. Two utilisation variants are then computed over that denominator, and they differ deliberately. The **projected** variant answers "what is encumbered right now": its numerator, `projected_load_hours`, is the sum of the snapshotted `estimated_hours` of the examiner's assignments whose `status` is `ACTIVE`, rounded half up to 2 decimal places, and `projected_utilization_pct` is that numerator divided by the available hours, multiplied by 100 and rounded half up to 2 decimal places — or exactly 0.00 when the available hours are 0.00. The **realized** variant answers "what did the work actually consume": its numerator, `realized_load_hours`, ranges over the examiner's assignments whose `status` is `ACTIVE` or `COMPLETED` and takes, for each one, the owning request's `actual_hours_logged` whenever that figure is not null and the assignment's snapshotted `estimated_hours` otherwise, summing and rounding half up to 2 decimal places; `realized_utilization_pct` is derived from it in the same way, and is likewise 0.00 when the available hours are 0.00. Assignments that are `SUPERSEDED` or `RELEASED` are excluded from both variants entirely. Because the realized variant adds completed work back in and substitutes reported hours, an identical assignment history yields a different utilisation figure under each variant — that difference is the point of exposing both. A third figure, `casework_training_ratio`, is 0.00 when `training_hours_per_week` is 0.00 and otherwise `projected_load_hours` divided by `training_hours_per_week`, rounded half up to 2 decimal places. The workload read exposes all of it side by side: `analyst_id`, `available_hours`, `projected_load_hours`, `projected_utilization_pct`, `realized_load_hours`, `realized_utilization_pct`, `casework_training_ratio`, `active_assignment_count` — the number of the examiner's `ACTIVE` assignments — and the stored `assigned_casework_hours`.

**The capacity gate.** Before any assignment is admitted, the projected variant is recomputed as though the new work were already encumbered: the examiner's current `projected_load_hours` plus the request's `estimated_hours`, divided by their available hours, multiplied by 100 and rounded half up to 2 decimal places. The assignment is admitted only when that post-assignment figure is at most 100.00 percent. Exactly 100.00 is admitted; 100.01 is refused with `ERR_ANALYST_CAPACITY_EXCEEDED`. An examiner whose available hours are 0.00 — one whose whole contracted week is committed to training — is refused every assignment under this same code.

**Naming an examiner.** A `CaseManager` staffs a queued request by naming the `analyst_id` of the incoming holder, supplying the `expected_examination_request_version` of §2.7, and optionally an `assignment_reason` of `MANUAL` or `AUTO_BALANCED`, which defaults to `MANUAL`. The request moves `QUEUED` → `ASSIGNED`. The incoming examiner must clear an eligibility battery, evaluated in the order §2.8 fixes: their `employment_status` must be `ACTIVE`, else `ERR_ANALYST_NOT_ACTIVE`; their `qualification_state` must be `QUALIFIED`, or `PROBATION` under the remediation window described below, a `SUSPENDED` examiner yielding `ERR_ANALYST_NOT_QUALIFIED` and a `DECERTIFIED` one `ERR_ANALYST_DECERTIFIED`; a probationary examiner may hold work only on a case whose effective `priority_class` is `P3_ROUTINE`, else `ERR_PROBATION_PRIORITY_RESTRICTED`; a probationary examiner must additionally carry `training_hours_per_week` of at least 8.00, else `ERR_TRAINING_MINIMUM_NOT_MET`; their `disciplines` must contain the method's `discipline`, else `ERR_ANALYST_DISCIPLINE_MISMATCH`; their `competency_level` must be at least the method's `min_competency_level`, else `ERR_ANALYST_COMPETENCY_INSUFFICIENT`; and finally the capacity gate above must admit them. That battery is exhaustive, on this operation and on the balancer below alike: neither re-tests the method's `validation_status` or its expiry against the clock, and neither consults the evidence item's custody position or its seal — a request whose method was retired after it was raised may still be reassigned, and it is only the bench-work step of §3.5 that re-tests the method and the property.

Creating the assignment writes an **Assignment** row with `status` `ACTIVE`, its own `estimated_hours` snapshotted from the request, `assigned_at_utc` stamped from the logical clock, `closed_at_utc` null and `superseded_by_assignment_id` null. The examiner's `assigned_casework_hours` is increased by the request's `estimated_hours`, which is itself a mutation of the examiner's record and increments their `version`. The request's `assigned_analyst_id` is set to the incoming examiner, its own `version` increments, and the case rollup runs — a case that was `ACCEPTED` or `AWAITING_ASSIGNMENT` becomes `IN_PROGRESS`.

**Reassignment** uses the same operation against a request that is already `ASSIGNED`, and the request's status stays `ASSIGNED` — a self-loop rather than a new state. The stale-version check and the whole eligibility battery apply to the incoming examiner exactly as above; once those pass, the named examiner must not be the one who already holds the request, else `ERR_ANALYST_ALREADY_ASSIGNED`. On success the incumbent's `ACTIVE` assignment moves to `SUPERSEDED` with `closed_at_utc` stamped and `superseded_by_assignment_id` pointing at the newly created row, and the outgoing examiner's `assigned_casework_hours` is decreased by exactly that superseded assignment's snapshotted `estimated_hours` — not by the request's current estimate. The incoming examiner receives a fresh `ACTIVE` assignment and their `assigned_casework_hours` rises by the request's `estimated_hours`. The request's `assigned_analyst_id` becomes the incoming examiner.

**Automatic balancing.** Rather than naming a holder, a `CaseManager` may let the workload balancer choose one; that operation takes no request body at all. Automatic balancing is admissible only from `QUEUED`: a request that is already `ASSIGNED` is refused with `ERR_EXAM_REQUEST_INVALID_STATE`, so rebalancing an assigned request has to go through the naming operation above. The balancer first filters candidates over the whole examiner roster with an explicit predicate: `employment_status` is `ACTIVE`; and either `qualification_state` is `QUALIFIED`, or `qualification_state` is `PROBATION` while the case's effective `priority_class` is `P3_ROUTINE` and the examiner's `training_hours_per_week` is at least 8.00; and the examiner's `disciplines` contains the method's `discipline`; and their `competency_level` is at least the method's `min_competency_level`; and their post-assignment projected utilisation, computed exactly as the capacity gate computes it, is at most 100.00 percent. Surviving candidates are ordered by post-assignment projected utilisation ascending, compared at 2 decimal places. Ties fall through to three further keys in order: the number of the examiner's `ACTIVE` assignments, ascending; then their `created_at`, ascending; then, because the logical clock stands still between writes and a roster registered under one instant carries identical `created_at` stamps throughout, insertion order — the examiner registered first wins. Examiner identifiers are never a tie-break — random identifiers decide nothing. The first candidate after ordering is selected, receives a new `ACTIVE` assignment with `assignment_reason` `AUTO_BALANCED`, and the request moves `QUEUED` → `ASSIGNED` with the same hour encumbrance, `assigned_analyst_id` write and case rollup as a manual assignment. If the filter yields no candidate at all, nothing is created, the request is left `QUEUED`, and the call is refused with `ERR_NO_ELIGIBLE_ANALYST`.

An assignment's `status` is one of `ACTIVE`, `SUPERSEDED`, `RELEASED` or `COMPLETED`, and the supersede chain is self-referential — `superseded_by_assignment_id` on a displaced row names the row that replaced it, so the full history of holders on a request is walkable. Assignments are readable individually and as a list narrowable by `examination_request_id`, `analyst_id`, `superseded_by_assignment_id` or `status`.

### 3.5. Bench Work: Custody Movement, Reported Hours and Revision Rounds

Bench work is performed by the holder and nobody else. The holding examiner begins by advancing the request from `ASSIGNED` to `IN_ANALYSIS`; the operation takes no request body. Starting is admissible only from `ASSIGNED` — anything else is `ERR_EXAM_REQUEST_INVALID_STATE` — and only for the holder, the acting `X-User-ID` having to equal `assigned_analyst_id` on pain of `ERR_ANALYST_IDENTITY_MISMATCH`. The holder's standing is re-checked at this moment rather than trusted from assignment time: their `qualification_state` must still be `QUALIFIED`, or still `PROBATION` with the case's effective `priority_class` `P3_ROUTINE` and `training_hours_per_week` of at least 8.00, else `ERR_ANALYST_NOT_QUALIFIED`. So is the method: its `validation_status` must be `VALIDATED`, else `ERR_METHOD_NOT_VALIDATED`, and its `validation_expires_at_utc` must either be null or lie strictly after the logical clock, else `ERR_METHOD_VALIDATION_EXPIRED`. The property itself must be available too — and by the normative order of §2.8 this pair is in fact tested *before* the method and standing checks just described, the item's custody position falling under the rule 8 state guard and its seal under rule 11, so a request whose item has left the vault reports the custody position even when the method has also lapsed: the item's `custody_status` must be `IN_VAULT`, else `ERR_EVIDENCE_CUSTODY_INVALID_STATE`, and its `seal_intact` must be true, else `ERR_EVIDENCE_SEAL_BROKEN`.

Starting analysis checks the property out of the vault. The item moves `IN_VAULT` → `IN_ANALYSIS` and its `checkout_count` increases by 1 — that counter records how many times the item has been checked out over its whole life, which is exactly once per revision round of the work performed on it.

Completing bench work advances the request `IN_ANALYSIS` → `TECH_REVIEW` and is likewise restricted to the holder by the same identity comparison. The examiner reports `actual_hours`, a figure greater than 0.00, at most 400.00 and carried to 2 decimal places, which is stored on the request as `actual_hours_logged`; because that field feeds only the realized utilisation variant, reporting hours changes what §3.4's realized figures say and leaves the projected figures alone. The examiner also dispositions the property with the optional boolean `evidence_consumed`, which defaults to false. When it is false the item is checked back in, `IN_ANALYSIS` → `IN_VAULT`. When it is true the item is destroyed by the examination, `IN_ANALYSIS` → `CONSUMED`, which is terminal as far as client-driven custody movement goes, the hold-reopening cascade of §2.10 being the one server-initiated exception that moves an item out of it — and that is admissible only if the method's `is_consumptive` is true, else the call is refused with `ERR_METHOD_NOT_CONSUMPTIVE`.

Completion also settles the hours ledger in the same transaction. The holder's `ACTIVE` assignment moves to `COMPLETED` with `closed_at_utc` stamped from the logical clock, and the holder's `assigned_casework_hours` is decreased by exactly that assignment's snapshotted `estimated_hours`. This is not an accounting quirk: the request has just left the hold states, so removing the encumbrance is precisely what keeps the committed-hours invariant of §2.11 balanced. Both bench-work calls — starting and completing — answer 200 with the updated `ExaminationRequest` as their `data`, never with the evidence item or the assignment, whose movements are observed through their own reads.

Casework in this laboratory is cyclic, and the cycle is deliberate. A file may leave `IN_ANALYSIS` for review and come straight back to it, either because administrative review returned it or because a technical disagreement was resolved in the reviewer's favour. Each such return increments `revision_round` by 1, and each is arbitrated by the hold-reopening procedure of §2.10 — either the original examiner re-encumbers the same assignment row and the item is checked out again, or the request is requeued with its `assigned_analyst_id` cleared for someone else to pick up. A single request may therefore run `ADMIN_REVIEW` → `IN_ANALYSIS` → `TECH_REVIEW` → `ADMIN_REVIEW` any number of times, and likewise `DISAGREEMENT` → `IN_ANALYSIS` → `TECH_REVIEW` → `DISAGREEMENT`, with `revision_round` counting the passes and `checkout_count` on the item tracking them from the custody side. A revision round does not reset the work already reported: `actual_hours_logged` keeps the figure the previous completion wrote, is never cleared back to null when the file returns to `IN_ANALYSIS`, and is simply overwritten by the next completion — so the realized utilisation figures of §3.4 go on reading the superseded figure while the file is back on the bench.

### 3.6. The Review Gates: Technical, Disagreement and Administrative

No report leaves the laboratory without passing two review gates, and each gate writes an immutable **ReviewRecord** that is the accreditation audit trail. Every review record names the `examination_request_id` it concerns, its `review_type` — one of `TECHNICAL`, `ADMINISTRATIVE` or `DISAGREEMENT_RESOLUTION` — the `decision` recorded, a mandatory `rationale` of 1 to 500 characters, a `revision_round_snapshot` copying the request's `revision_round` at the instant of signing, and a `recorded_at_utc` stamped from the logical clock. A technical record carries the reviewing examiner in `reviewer_analyst_id` and leaves `reviewer_operator_id` null; an administrative record and a disagreement-resolution record carry the acting operator's opaque identifier in `reviewer_operator_id` and leave `reviewer_analyst_id` null. Review records are readable individually and as a list narrowable by `examination_request_id`, `reviewer_analyst_id` or `review_type`.

**Technical review** is performed by a second `Analyst` on a request in `TECH_REVIEW`, with a `decision` of either `AGREE` or `DISAGREE` and a `rationale`. The acting `X-User-ID` must itself name a registered examiner: an `Analyst` caller whose identifier resolves to no `Analyst` row is `ERR_ANALYST_NOT_FOUND` (404), resolved after the body schema check of §2.8 rule 4 and ahead of the request's own state guard, so an unregistered reviewer signing a request that is not in `TECH_REVIEW` reports the missing examiner. The reviewer must not be the holder: an acting `X-User-ID` equal to `assigned_analyst_id` is refused with `ERR_SEGREGATION_OF_DUTIES`. The reviewer must also be competent to sign — and their standing, being rule 13, is tested ahead of the segregation conflict just described: their `employment_status` must be `ACTIVE`, else `ERR_ANALYST_NOT_ACTIVE`, a `DECERTIFIED` reviewer being `ERR_ANALYST_DECERTIFIED`; their `qualification_state` must be `QUALIFIED` — probationary standing is not enough for a review signature, and a shortfall is `ERR_ANALYST_NOT_QUALIFIED` — their `disciplines` must contain the method's `discipline`, else `ERR_ANALYST_DISCIPLINE_MISMATCH`, and their `competency_level` must be at least the method's `min_competency_level`, else `ERR_ANALYST_COMPETENCY_INSUFFICIENT`.

A decision of `AGREE` writes the record and advances the request `TECH_REVIEW` → `ADMIN_REVIEW`. A decision of `DISAGREE` writes the record with the identical field set and touches off a four-hop cascade that is the most consequential chain in the service. Hop one: the record is written and the request enters `DISAGREEMENT`. Hop two, caused by that `DISAGREEMENT` state rather than by anything in the request body: a **Nonconformance** is opened with `source` `TECHNICAL_DISAGREEMENT`, `severity` `MAJOR`, its `examination_request_id` set to this request, its `analyst_id` set to the request's `assigned_analyst_id`, `opened_at_utc` stamped from the logical clock, `due_utc` set 30 days after that instant and a server-generated `description` naming this request rather than any client-supplied text. Hop three, caused by that `MAJOR` finding carrying an `analyst_id`: the implicated examiner moves `QUALIFIED` → `PROBATION` with `probation_entered_at_utc` stamped. Hops three and four are conditional on that examiner standing `QUALIFIED` when the finding is opened: an examiner already on `PROBATION` is left exactly as they are, with `probation_entered_at_utc` not re-stamped and no second release cascade; one who is `SUSPENDED` or `DECERTIFIED` is likewise untouched; and a request with no holder at all — as after a vendor return under §3.7 — yields a finding whose `analyst_id` is null and implicates nobody, so both hops fall away entirely. Hop four, caused by that `PROBATION` state: the probation release of §2.10 runs, so every `ACTIVE` assignment that examiner holds on a `P1_STATUTORY` or `P2_VIOLENT` case is released, each affected request falls back to `QUEUED`, the hours come off their `assigned_casework_hours`, and the case rollup runs on each affected case.

**Disagreement resolution** belongs to the `QualityManager`, who records a `decision` of `UPHOLD_ANALYST` or `UPHOLD_REVIEWER` with a `rationale` against a request in `DISAGREEMENT`. Upholding the analyst is a compensating action: the request advances `DISAGREEMENT` → `ADMIN_REVIEW`, and every finding of this request whose `source` is `TECHNICAL_DISAGREEMENT` — a file that has been round the revision loop more than once may carry several, and one the `QualityManager` opened directly under §3.8 counts as much as one raised by the cascade — moves to `VOIDED` with `closed_at_utc` stamped if its status is `OPEN` or `ROOT_CAUSE_SUBMITTED`, while one already `CAPA_APPROVED`, `CLOSED` or `VOIDED` is left untouched. Because that finding is gone, the examiner named by each voided finding's own `analyst_id` returns `PROBATION` → `QUALIFIED`, but only when that examiner has no remaining nonconformance whose status is `OPEN`, `ROOT_CAUSE_SUBMITTED` or `CAPA_APPROVED`. The assignments taken from them by the earlier probation release are *not* restored — the hours ledger stays consistent with hold-state membership, and the requeued work is picked up afresh.

Upholding the reviewer instead sends the file back to the bench. The review record is written before anything else moves, so its `revision_round_snapshot` carries the round that is closing rather than the one about to open; the `revision_round` then increments by 1 and the hold-reopening procedure of §2.10 decides between two outcomes: `DISAGREEMENT` → `IN_ANALYSIS` when the incumbent examiner is still eligible, in which case their `COMPLETED` assignment returns to `ACTIVE`, its snapshotted `estimated_hours` is re-added to their `assigned_casework_hours` and the item is checked out of the vault again; or `DISAGREEMENT` → `QUEUED` when the incumbent is `SUSPENDED`, `DECERTIFIED`, not employment-`ACTIVE`, probationary on a `P1_STATUTORY` or `P2_VIOLENT` case, probationary below the 8.00-hour training minimum, or absent altogether — a request that reached review through a vendor return under §3.7 has no `assigned_analyst_id` to reinstate and always requeues — in which case `assigned_analyst_id` is cleared, the assignment is left `COMPLETED`, no hours are re-encumbered and the case rollup runs. On this branch the `TECHNICAL_DISAGREEMENT` finding stays `OPEN` — the reviewer was right, so the finding stands.

**Administrative review** is the release gate and belongs to the `CaseManager`, who records a `decision` of `APPROVE` or `RETURN` with a `rationale` against a request in `ADMIN_REVIEW`. Approval writes the administrative record, advances the request `ADMIN_REVIEW` → `RELEASED`, stamps `released_at_utc` from the logical clock and runs the case rollup, which is what moves `open_examination_request_count` down and `released_examination_request_count` up. A return writes the record, increments `revision_round` by 1, and hands the outcome to the same hold-reopening procedure: `ADMIN_REVIEW` → `IN_ANALYSIS` on the reopen branch, with the completed assignment reactivated, its hours re-encumbered and the item checked out again; or `ADMIN_REVIEW` → `QUEUED` on the requeue branch, with `assigned_analyst_id` cleared, no hours re-encumbered and the case rollup run.

Segregation of duties is enforced across all three gates and is compared on both `reviewer_analyst_id` and `reviewer_operator_id`, so that a director or manager acting under a personal user identifier cannot review their own casework. The technical reviewer may be neither the assigned analyst nor the same acting identifier that completed the analysis. The administrative reviewer may be neither the assigned analyst nor the technical reviewer of the same `revision_round`. A disagreement resolver may be none of those three. Every violation is `ERR_SEGREGATION_OF_DUTIES`.

### 3.7. Outsourcing to Vendor Laboratories

When a discipline queue outruns the bench, work goes out. The **Vendor** registry belongs to the `LabDirector`, who registers a vendor laboratory with its `name` (1 to 120 characters), a non-empty `accredited_disciplines` array drawn from `BIOLOGY`, `CHEMISTRY`, `LATENT_PRINTS`, `TRACE` and `DIGITAL`, the `accreditation_expires_at_utc` instant at which that accreditation lapses, a `concurrent_case_capacity` from 1 to 50 being the maximum number of engagements whose custody windows may cover any one instant, a `unit_price_cents` of at least 1 being the contract price per examined item in integer cents, a `contract_ceiling_cents` of at least 1 being the total contract authority in cents, and optionally a `rush_surcharge_pct` between 0.00 and 0.50 inclusive at 2 decimal places, defaulting to 0.00. A newly registered vendor has `status` `ACTIVE` and both `encumbered_cents` and `spent_cents` at 0. The director may later set a vendor's `status` to `SUSPENDED`, optionally recording a `suspension_reason`, or set it back to `ACTIVE`. The `suspension_reason` moves only when the call supplies it, so returning a vendor to `ACTIVE` without naming one leaves the reason recorded at suspension standing in the field; and setting a vendor to the `status` it already holds is admissible, simply re-stamping the row. Suspension bars *new* awards only: engagements already `AWARDED` or `AT_VENDOR` are untouched and keep occupying both the vendor's concurrent capacity and their encumbrance.

Awarding work is a `CaseManager` action against a `QUEUED` request. The coordinator names the `vendor_id`, the contracted custody window's `window_start_utc` and `window_end_utc`, and optionally `rush_flag`, a boolean defaulting to false that buys the vendor's rush surcharge. On success the request moves `QUEUED` → `OUTSOURCED` and a **VendorEngagement** is created with `status` `AWARDED`, `awarded_at_utc` stamped from the logical clock — that instant is the custody-day baseline — and the request's `item_count` snapshotted onto the engagement, while `shipped_at_utc`, `returned_at_utc`, `custody_days`, `final_invoice_cents`, `variance_cents` and `cancellation_reason` all start null and stay null until the step that fills them. The case rollup then runs, so a case that was `AWAITING_ASSIGNMENT` becomes `IN_PROGRESS`; outsourced work counts as active casework. Every engagement operation — award, shipment, return and withdrawal — answers with the `VendorEngagement` itself as its `data`, never with the examination request or the vendor, whose movements are observed through their own reads.

Four gates guard an award, and their relative order is the one §2.8 fixes. The strictly-increasing custody window of §2.8's interval rule is established ahead of all four of them but behind the request's own state guard, so an inverted window offered against a request that is not `QUEUED` reports `ERR_EXAM_REQUEST_INVALID_STATE`, while an inverted window offered to a suspended or unaccredited vendor reports `ERR_INVALID_INTERVAL`. The vendor must be accredited for the work: their `accredited_disciplines` must contain the request's `discipline`, and their `accreditation_expires_at_utc` must lie strictly after the engagement's `window_end_utc`, else `ERR_VENDOR_NOT_ACCREDITED` — a vendor whose accreditation lapses part-way through the contracted window may not be given the work at all. The vendor's `status` must be `ACTIVE`, else `ERR_VENDOR_SUSPENDED`. The vendor's concurrent capacity must accommodate one more window: count the vendor's engagements whose `status` is `AWARDED` or `AT_VENDOR` and whose own window intersects the requested window, add one for the new engagement, and refuse with `ERR_VENDOR_CAPACITY_EXCEEDED` if that total exceeds `concurrent_case_capacity`. Custody windows are **closed at both ends** for this arithmetic, so a new window whose `window_start_utc` falls exactly on an existing window's `window_end_utc` does intersect it and is refused, while a window starting one second later is admitted. Engagements that are `CANCELLED` or `RETURNED` never occupy capacity. And last of all the money must fit: the vendor's `encumbered_cents` plus their `spent_cents` plus the newly computed `award_amount_cents` may not exceed their `contract_ceiling_cents`, else `ERR_VENDOR_CEILING_EXCEEDED` (HTTP 402).

Pricing an award is a six-step chain, and the order is pinned because the volume tier depends on the total while the rush surcharge feeds the total. **Step one:** `base_amount_cents` is the vendor's `unit_price_cents` multiplied by the snapshotted `item_count`. **Step two:** `rush_surcharge_cents` is the `base_amount_cents` multiplied by the vendor's `rush_surcharge_pct`, rounded half up to whole cents, when `rush_flag` is true, and exactly 0 when it is false. **Step three:** `tier_basis_cents` is `base_amount_cents` plus `rush_surcharge_cents` — this rush-inclusive figure, and never the bare base, is the basis the tier is chosen from, and it is pinned onto the engagement so the choice is auditable. **Step four:** `volume_discount_pct` is 0.12 when `tier_basis_cents` is at least 500000 cents, otherwise 0.08 when it is at least 250000 cents, otherwise 0.04 when it is at least 100000 cents, otherwise 0.00. **Step five:** `discount_amount_cents` is `tier_basis_cents` multiplied by `volume_discount_pct`, rounded half up to whole cents. **Step six:** `award_amount_cents` is `tier_basis_cents` minus `discount_amount_cents`, and that is the figure the vendor's encumbrance carries. Do not discount before surcharging, and do not compute the surcharge on a discounted amount; rounding happens at step two and step five and nowhere else in the chain. The award then increments the vendor's `encumbered_cents` by `award_amount_cents`.

Shipment is confirmed separately, because the money moves at award time but the property moves later. Confirming shipment, optionally with a `shipment_note` — accepted for the operator's convenience but neither persisted on the engagement nor echoed anywhere in the response — advances the engagement `AWARDED` → `AT_VENDOR`, stamps `shipped_at_utc`, and checks the property out of the vault: the item moves `IN_VAULT` → `IN_ANALYSIS` with `checkout_count` increased by 1. The item must genuinely be `IN_VAULT`, else `ERR_EVIDENCE_CUSTODY_INVALID_STATE`, and its seal must be intact, else `ERR_EVIDENCE_SEAL_BROKEN`. Confirming shipment on an engagement that is not `AWARDED` is `ERR_VENDOR_ENGAGEMENT_INVALID_STATE`, and the engagement's own state guard is tested before the item's custody position, so confirming a second time — the property being `IN_ANALYSIS` at the vendor by then — reports the engagement state rather than the custody position. Neither encumbrance nor capacity occupation changes at this step.

Recording the vendor's return closes the fiscal and custodial loops together and is admissible only from `AT_VENDOR`. The coordinator supplies `final_invoice_cents`, an integer of at least 0. The engagement moves to the terminal `RETURNED` with `returned_at_utc` stamped; its `custody_days` is the interval from `awarded_at_utc` to `returned_at_utc` expressed as a fractional-day figure — whole seconds divided by 86400, rounded half up to 2 decimal places — and its `variance_cents` is `final_invoice_cents` minus `award_amount_cents`, which is negative when the vendor under-billed. The vendor's ledger then settles: `encumbered_cents` decreases by `award_amount_cents` and `spent_cents` increases by `final_invoice_cents`. The contract ceiling is not re-tested here: an invoice larger than the award is recorded even when it carries the vendor's `encumbered_cents` plus `spent_cents` past their `contract_ceiling_cents`, the ceiling being an award-time gate and nothing else. The request rejoins the internal path, moving `OUTSOURCED` → `TECH_REVIEW`, and its own `vendor_custody_days` is refreshed to the sum of `custody_days` over that request's `RETURNED` engagements — 0.00 for a request that was never outsourced. The property is checked back in, `IN_ANALYSIS` → `IN_VAULT`. Finally, invoicing discipline is enforced: when the absolute value of `variance_cents` exceeds ten percent of `award_amount_cents` — that tolerance being `award_amount_cents` multiplied by 0.10 and rounded half up to whole cents — a nonconformance is opened with `source` `VENDOR_VARIANCE`, `severity` `MINOR`, a server-generated `description` naming the engagement, its `examination_request_id` set to this request and its `analyst_id` null, because no individual examiner is implicated by a vendor's billing.

Withdrawing an award is the exact compensating action of making one, and is admissible from either `AWARDED` or `AT_VENDOR` with a `cancellation_reason`. The engagement moves to the terminal `CANCELLED`, the vendor's `encumbered_cents` decreases by exactly `award_amount_cents` — restoring the pre-award value with zero residue — and `spent_cents` is not touched at all. The closed window stops occupying capacity, freeing it for another award. The request returns `OUTSOURCED` → `QUEUED` and the case rollup runs; cancelling an engagement that was already `AT_VENDOR` additionally brings the property home, `IN_ANALYSIS` → `IN_VAULT`. Cancelling an engagement that is already `RETURNED` or `CANCELLED` is `ERR_VENDOR_ENGAGEMENT_INVALID_STATE`.

Engagements are readable individually — exposing every pricing field, `custody_days` and `variance_cents` — and as a list narrowable by `examination_request_id`, `vendor_id` or `status`, which is the view used to reconcile a vendor's encumbrance against the ledger invariant of §2.11.

### 3.8. The Quality System: Proficiency Testing, Findings and Corrective Action

Competence in a forensic laboratory is not asserted once; it is re-demonstrated on a cycle. The `QualityManager` assigns a **ProficiencyTest** to an examiner by naming the `analyst_id`, the `method_id` the test exercises, a `test_cycle` label of 1 to 20 characters identifying the round, and the `due_utc` deadline. The triple of `analyst_id`, `method_id` and `test_cycle` must be unique; a second test for the same examiner, method and cycle is `ERR_DUPLICATE_RESOURCE`. A new test has `status` `ASSIGNED`, `late_submission` false and no `submitted_at_utc`, `score_pct`, `result` or `scored_at_utc`. Note deliberately that assignment applies no gate beyond the existence of the two named rows and the uniqueness of the triple: an examiner who is `SUSPENDED` or even `DECERTIFIED`, and one whose `employment_status` is `ON_LEAVE` or `SEPARATED`, may still be assigned a proficiency test, and so may a method still in `DRAFT` or already `RETIRED` be named — neither the standing battery nor the method-validation gate of §2.8 is consulted here. The test is precisely the instrument by which a suspended examiner produces the evidence needed for reinstatement, so the qualification gates that guard casework do not guard testing.

The examiner submits their own test. Submission carries no body, requires `status` `ASSIGNED` else `ERR_PT_INVALID_STATE`, and requires the `X-User-ID` of the caller to equal the test's `analyst_id` else `ERR_ANALYST_IDENTITY_MISMATCH`. It advances the test to `SUBMITTED`, stamps `submitted_at_utc` from the logical clock, and sets `late_submission` to true when that instant is strictly after `due_utc` — a submission landing exactly on `due_utc` is on time.

Scoring is the `QualityManager`'s act, admissible only from `SUBMITTED` else `ERR_PT_INVALID_STATE`. The manager supplies `score_pct` between 0.00 and 100.00 inclusive at 2 decimal places; the test advances to the terminal `SCORED`, `scored_at_utc` is stamped, and `result` is graded. Per §2.6 the mark is rounded half up to 2 decimal places as it is stored, and it is that rounded figure — not the figure as supplied — that grading reads, so a supplied 89.995 is stored as 90.00 and grades as `PASS`. Grading has a hard precedence: a `late_submission` is a `FAIL` whatever the mark, because a proficiency test that misses its deadline has failed as an exercise regardless of the answers. Otherwise a `score_pct` of at least 90.00 is `PASS`, a `score_pct` of at least 70.00 is `INCONCLUSIVE`, and anything below 70.00 is `FAIL`. Both thresholds are inclusive at the boundary: 90.00 passes while 89.99 is inconclusive, and 70.00 is inconclusive while 69.99 fails.

The score then cascades into the examiner's standing, and the two stages run in this order. First the failure counter moves: a `FAIL` increases `consecutive_pt_failures` by 1, a `PASS` resets it to 0, and an `INCONCLUSIVE` leaves it exactly as it was — an inconclusive result neither punishes nor absolves. Second the qualification state moves against the updated counter. An examiner who was `QUALIFIED` and has just failed moves to `PROBATION`, `probation_entered_at_utc` is stamped, and the probation release of §2.10 sheds their priority-restricted work. An examiner already on `PROBATION` whose `consecutive_pt_failures` has reached 2 moves to `SUSPENDED`, `suspended_at_utc` is stamped, and the full release sheds all of their open work. An examiner already `SUSPENDED` who fails again moves to the terminal `DECERTIFIED`, with a full release once more. An examiner on `PROBATION` who passes returns to `QUALIFIED` — but only if they carry no nonconformance whose `status` is `OPEN`, `ROOT_CAUSE_SUBMITTED` or `CAPA_APPROVED`; a passing mark does not clear probation while a finding against that examiner is still live. Restoration to `QUALIFIED` sets `consecutive_pt_failures` to 0 and `probation_entered_at_utc` to null, and it does **not** return any previously released assignment to the examiner: released work stays released and must be reassigned deliberately. Each request requeued by a release is followed by the case rollup for its case. An examiner already `DECERTIFIED` who fails again has `consecutive_pt_failures` incremented like anyone else but moves nowhere and sheds nothing, `DECERTIFIED` being terminal on the qualification axis. Each of the two stages writes to the examiner's row only when it actually changes something, and each write that happens refreshes `updated_at` and increments `version` by exactly 1: an `INCONCLUSIVE` mark, and a `PASS` for an examiner who is already `QUALIFIED` with a zero counter, leave the examiner's `updated_at` and `version` untouched, whereas a `PASS` that both clears a non-zero counter and then restores qualification increments `version` twice, and a `FAIL` from `QUALIFIED` increments it once for the counter and again for the move to `PROBATION`.

Scoring also opens findings of its own. An `INCONCLUSIVE` result creates a nonconformance with `source` `PT_INCONCLUSIVE` and `severity` `MINOR` naming that `analyst_id`; being `MINOR`, it never itself moves a qualification state, which is why an inconclusive mark leaves the examiner exactly where they were while still creating a documented finding. A `FAIL` creates a nonconformance with `source` `PT_FAILURE` and `severity` `MAJOR` naming that `analyst_id`, alongside the counter and qualification movements above. Either finding is opened with `examination_request_id` null — a proficiency finding attaches to the examiner, not to a piece of casework — and is opened after the standing cascade has run, taking `status` `OPEN`, `capa_rejection_count` 0 and the severity-derived `due_utc` exactly as a finding opened by hand does. The finding the `FAIL` opens is not itself a second trigger of the probation move: the qualification movement is the cascade's alone, so an examiner is never advanced two states by one mark.

Reinstatement lifts a suspension and is the `QualityManager`'s decision, recorded with a required `rationale` of 1 to 500 characters. It is admissible only from `SUSPENDED`: an examiner who is `QUALIFIED` or on `PROBATION` yields `ERR_ANALYST_INVALID_QUALIFICATION_STATE`, and one who is `DECERTIFIED` yields the more specific `ERR_ANALYST_DECERTIFIED`, decertification being irreversible. Two substantive conditions then apply. The examiner must carry no nonconformance whose `status` is `OPEN`, `ROOT_CAUSE_SUBMITTED` or `CAPA_APPROVED`, else `ERR_OPEN_NONCONFORMANCE_BLOCKS_REINSTATEMENT` — every finding against them must be `CLOSED` or `VOIDED`. And they must have at least one `SCORED` proficiency test whose `result` is `PASS` and whose `scored_at_utc` lies strictly after their `suspended_at_utc`, else `ERR_REINSTATEMENT_PT_REQUIRED`; a pass earned before the suspension proves nothing about the competence that was suspended. On success the examiner moves `SUSPENDED` → `PROBATION` rather than straight to `QUALIFIED`, `consecutive_pt_failures` resets to 0, `suspended_at_utc` is cleared to null, and `probation_entered_at_utc` is set to the current logical instant, starting a fresh probation. Reinstatement does not restore any assignment shed by the earlier release.

A **Nonconformance** is the laboratory's quality finding. Beyond those raised automatically by technical disagreement, proficiency results, vendor billing variance and missed discovery deadlines, the `QualityManager` may open one directly, supplying its `source` — one of `TECHNICAL_DISAGREEMENT`, `PT_FAILURE`, `PT_INCONCLUSIVE`, `ACCREDITATION_AUDIT`, `INTERNAL_QA`, `DEADLINE_MISS` or `VENDOR_VARIANCE` — its `severity` of `MINOR`, `MAJOR` or `CRITICAL`, a `description` of 1 to 500 characters, and optionally an `examination_request_id` and an `analyst_id` to attribute it to a piece of work, an examiner, both or neither. Each of those two identifiers, when supplied, must resolve, else `ERR_EXAM_REQUEST_NOT_FOUND` or `ERR_ANALYST_NOT_FOUND`. A new finding has `status` `OPEN`, `capa_rejection_count` 0, `overdue` false, `opened_at_utc` stamped from the logical clock, and no `root_cause_category`, `corrective_action_plan` or `closed_at_utc`. Opening a `MAJOR` or `CRITICAL` finding that names an `analyst_id` moves that examiner `QUALIFIED` → `PROBATION` immediately, with the probation release running; a `MINOR` finding never moves a qualification state. That move fires only from `QUALIFIED`: an examiner already on `PROBATION` is left exactly as they are, with `probation_entered_at_utc` retaining its original instant rather than being re-stamped, and one who is `SUSPENDED` or `DECERTIFIED` is not moved back up to `PROBATION` either. The finding is written first and the standing move follows it, so the new finding is already live when the move lands, and the finding is created and returned whether or not any state moved.

Every finding carries a corrective-action deadline. Its `due_utc` is its `opened_at_utc` advanced by the service-level allowance for its severity: 60 days for `MINOR`, 30 days for `MAJOR`, 10 days for `CRITICAL`. Its `overdue` flag is true exactly when the current logical instant is strictly after `due_utc` and its `status` is neither `CLOSED` nor `VOIDED`; the comparison is strict, so a finding read at precisely its `due_utc` is not yet overdue, and a closed finding is never overdue however long it took.

Remediation runs in three moves with the responsibility deliberately split. First, the `CaseManager` submits the root cause, naming a `root_cause_category` of `TRAINING`, `METHOD_DEFICIENCY`, `EQUIPMENT`, `DOCUMENTATION`, `WORKLOAD` or `VENDOR`, together with a `corrective_action_plan` of 1 to 500 characters. This is admissible only from `OPEN`, else `ERR_NONCONFORMANCE_INVALID_STATE`, and it advances the finding to `ROOT_CAUSE_SUBMITTED` while leaving `due_utc` untouched — submitting an analysis does not buy more time.

Second, the `QualityManager` renders a corrective-action decision, supplying a `decision` of `APPROVE` or `REJECT` and a `rationale`; this is admissible only from `ROOT_CAUSE_SUBMITTED`, else `ERR_NONCONFORMANCE_INVALID_STATE`. `APPROVE` advances the finding to `CAPA_APPROVED`. `REJECT` sends it back to `OPEN`, increases `capa_rejection_count` by 1, and clears both `root_cause_category` and `corrective_action_plan` to null so the next submission starts clean. A second rejection escalates: when `capa_rejection_count` reaches 2, the `severity` steps up one tier — `MINOR` becomes `MAJOR`, `MAJOR` becomes `CRITICAL`, and `CRITICAL` stays `CRITICAL` because there is no higher tier — and `due_utc` is recomputed from the **original** `opened_at_utc` using the new tier's allowance, never from the rejection instant. A `MINOR` finding rejected twice therefore has its deadline recomputed as `opened_at_utc` plus 30 days, which for a finding rejected late in its original 60-day window means the escalated deadline is already in the past and the finding reads as `overdue` the moment the escalation lands. That is intended: escalation tightens the clock retroactively. Escalation fires on exactly the second rejection and never again: a third or later rejection still increases `capa_rejection_count` and still clears the analysis, but leaves `severity` and `due_utc` where the second rejection left them.

Third, the `QualityManager` verifies and closes, optionally recording a `closure_note` — a string of any length, carried for the operator's benefit and not persisted on the finding, which has no field for it. Closure is admissible only from `CAPA_APPROVED`, else `ERR_NONCONFORMANCE_INVALID_STATE`; the finding moves to the terminal `CLOSED`, `closed_at_utc` is stamped, and `overdue` is recomputed to false. Closure can also restore an examiner: when the finding names an `analyst_id`, that examiner is on `PROBATION`, and no other nonconformance against them remains with `status` `OPEN`, `ROOT_CAUSE_SUBMITTED` or `CAPA_APPROVED`, they move `PROBATION` → `QUALIFIED`, `consecutive_pt_failures` resets to 0 and `probation_entered_at_utc` is cleared. Because a `CaseManager` submits the root cause and only a `QualityManager` may approve and close it, no single operator can both diagnose and sign off on the same finding.

Proficiency tests are readable individually and as a list narrowable by `analyst_id`, `method_id`, `test_cycle`, `status` and `result`. Findings are readable individually and as a list narrowable by `examination_request_id`, `analyst_id`, `source`, `severity` and `status` — the list that answers whether an examiner is clear to be reinstated.

### 3.9. Closing Out: Reporting, Turnaround Metrics, Backlog Aging, Discovery and Testimony

A case is reported once, by the `CaseManager`, optionally with a `report_note`. The case must be `IN_PROGRESS`, else `ERR_CASE_INVALID_STATE`. Its `open_examination_request_count` must be exactly 0, else `ERR_CASE_HAS_OPEN_REQUESTS` — nothing may still be in a queue, on a bench, at a vendor or in review. And its `released_examination_request_count` must be at least 1, else `ERR_CASE_HAS_NO_RELEASED_REQUEST`; a case whose every request was cancelled has produced no findings and cannot be reported. On success the case moves `IN_PROGRESS` → `REPORTED`, which is terminal on the workflow axis, `reported_at_utc` is stamped from the logical clock, and both turnaround figures are computed and frozen onto the case.

The two turnaround figures answer two different questions and are computed differently on purpose. `gross_turnaround_days` is the elapsed calendar time the agency waited: the interval from the case's `received_at_utc` to its `reported_at_utc`, taken in whole seconds, divided by 86400, rounded half up to 2 decimal places. `net_turnaround_days` is the time the laboratory itself is accountable for, and it excludes the days the property spent in a vendor's custody. Compute it by collecting, for every examination request belonging to this case, the custody window from `awarded_at_utc` to `returned_at_utc` of each of that request's engagements whose `status` is `RETURNED`; engagements that are `AWARDED`, `AT_VENDOR` or `CANCELLED` contribute nothing, since an award that never came back is not a completed period of vendor custody. Sort those windows by start instant ascending, breaking ties by `created_at` ascending. Merge them as closed intervals: windows that overlap merge, and windows that merely touch — one ending at the exact instant the next begins — also merge into a single continuous period, because the property was in vendor hands throughout. Sum the merged durations in whole seconds, divide by 86400 and round half up to 2 decimal places to obtain the case's total vendor custody in days. Then `net_turnaround_days` is `gross_turnaround_days` minus that figure, rounded half up to 2 decimal places, and floored at 0.00 so it is never negative. The merge is what makes the figure honest: two requests of the same case sent to vendors over overlapping windows spent one shared stretch of calendar out of house, and that stretch is subtracted once, never twice. Merging is performed on the whole-second instants before any rounding, so that rounding each window separately can never inflate the deduction.

Backlog aging is the director's instrument for deciding whether to outsource, and it is readable by the `LabDirector`, the `QualityManager` and the `CaseManager`. The reader may supply `as_of_utc` to age the backlog as at an arbitrary instant; when it is absent the current logical instant is used, and either way the instant actually used is echoed back as `as_of_utc`. A supplied `as_of_utc` that is not a well-formed ISO 8601 instant of the shape §2.4 requires is refused with `ERR_INVALID_REQUEST` (HTTP 400). The reader may also supply `discipline` to narrow the report to one discipline; like every other list filter it is an exact-equality match that is never checked against the discipline enumeration, so a `discipline` the laboratory does not run simply empties the population and the report answers 200 with `open_request_count` 0, `backlog_index` 0.00, four zero buckets and `outsourcing_recommended` false. The population is every examination request whose `status` is not `RELEASED` and not `CANCELLED` — that is, every request still owed to somebody, including those sitting at a vendor — restricted to the named discipline when one is given, and its size is reported as `open_request_count`.

Each open request is aged from the instant it was raised: its age in days is the interval from its `requested_at_utc` to the as-of instant in whole seconds, divided by 86400, rounded half up to 2 decimal places. That rounded age is then weighted by the urgency of its case: 1.50 for `P1_STATUTORY`, 1.25 for `P2_VIOLENT` and 1.00 for `P3_ROUTINE`, and the product is itself rounded half up to 2 decimal places. The `backlog_index` is the mean of those weighted ages — their sum divided by `open_request_count`, rounded half up to 2 decimal places — and is exactly 0.00 when there are no open requests at all, with no division attempted. Both rounding steps are required and neither may be skipped: age is rounded before weighting, each weighted age is rounded before summing, and the mean is rounded at the end. Carrying full precision through and rounding only once at the end is a different number and is not what this report returns. An age is never clamped: when the as-of instant precedes a request's `requested_at_utc` the age is negative, and that negative figure is weighted, summed and averaged exactly like any other — it can pull `backlog_index` below zero — while the request itself counts in the first bucket, whose lower edge of 0.00 is a label rather than a floor.

The same rounded ages populate four aging buckets, each half-open at its upper edge so every request falls in exactly one: `bucket_0_29_count` for ages from 0.00 up to but excluding 30.00, `bucket_30_59_count` for 30.00 up to but excluding 60.00, `bucket_60_89_count` for 60.00 up to but excluding 90.00, and `bucket_90_plus_count` for 90.00 and above. A request whose rounded age is exactly 30.00 therefore lands in the 30-to-59 bucket, not the first one, and the four counts always sum to `open_request_count`. Alongside them, `p1_open_count` counts the open requests whose case `priority_class` is `P1_STATUTORY`, and `outsourcing_recommended` is true exactly when `backlog_index` is at least 45.00 — at exactly 45.00 the recommendation is already true. The report returns `as_of_utc`, `open_request_count`, `backlog_index`, the four bucket counts, `p1_open_count` and `outsourcing_recommended`.

Discovery runs on a second, independent axis of the case. A case's `discovery_status` starts at `NONE` and moves through `RECEIVED` to either `FULFILLED` or `DENIED` without ever disturbing the case's `workflow_status`; the two axes are orthogonal, so a case can be answering a discovery demand while its examinations are still in progress, and reporting a case does not resolve an outstanding demand. The `CaseManager` records an incoming demand by naming the `discovery_requesting_party` — defence counsel, prosecutor or court. The case's `discovery_status` must be `NONE`, else `ERR_DISCOVERY_ALREADY_RECEIVED`, since a second demand on the same case is a duplicate rather than a new obligation, and the case's `workflow_status` must be one of `ACCEPTED`, `AWAITING_ASSIGNMENT`, `IN_PROGRESS` or `REPORTED`, else `ERR_CASE_INVALID_STATE`. On success `discovery_status` becomes `RECEIVED`, `discovery_requested_at_utc` is stamped from the logical clock, and `discovery_due_utc` is set to that instant advanced by 30 days.

Answering the demand is likewise the `CaseManager`'s act and requires `discovery_status` to be `RECEIVED`, else `ERR_DISCOVERY_NOT_PENDING`. The manager supplies a `decision` of `FULFILL` or `DENY` and optionally a `response_note`; a `DENY` must carry a present, non-empty `response_note` justifying the refusal, else `ERR_INVALID_REQUEST`, while a `FULFILL` may omit it. That note requirement is a schema-class check and is settled ahead of the `RECEIVED` guard, so a denial carrying no note against a case whose `discovery_status` is still `NONE` reports `ERR_INVALID_REQUEST` rather than `ERR_DISCOVERY_NOT_PENDING`. `FULFILL` moves `discovery_status` to `FULFILLED` and requires the case to have at least one `RELEASED` examination request, else `ERR_CASE_HAS_NO_RELEASED_REQUEST` — there is nothing to disclose from a case that has released no findings. `DENY` moves it to `DENIED`. Either way, if the current logical instant is strictly after `discovery_due_utc`, the laboratory has missed a statutory response deadline, and a nonconformance is opened with `source` `DEADLINE_MISS` and `severity` `MAJOR`, with both `examination_request_id` and `analyst_id` null and a `description` citing the case, because a missed disclosure deadline is an institutional failure rather than an individual examiner's. Answering exactly at `discovery_due_utc` is on time and raises no finding.

Testimony closes the arc. A **CourtEvent** blocks an examiner's calendar for a hearing, and the `CaseManager` schedules it by naming the `examination_request_id` being testified to, the `analyst_id` who will testify, the `court_name` of 1 to 120 characters, the `docket_number` of 1 to 40 characters, the hearing's `start_utc` and `end_utc`, and optionally `subpoena_received`, a boolean defaulting to false. The `end_utc` must lie strictly after `start_utc`, else `ERR_INVALID_INTERVAL`. The named request must be `RELEASED` — only released findings are testified to — and the named examiner must be that request's assigned analyst, else `ERR_REFERENTIAL_MISMATCH`; a colleague cannot be put on the stand for work they did not perform. Among that examiner's non-cancelled events, the `docket_number` must not already be used, else `ERR_DUPLICATE_RESOURCE`. A new event has `status` `SCHEDULED`, both `testimony_note` and `cancellation_reason` null, and its `notice_days` computed once at creation as the whole number of complete days from the current logical instant to `start_utc` — the interval in seconds divided by 86400, discarding any fraction, so a hearing already in the past carries a negative `notice_days`. Where one scheduling request breaks more than one of these rules the reported reason is settled in a fixed order: the docket-number uniqueness check first, then the named request's `RELEASED` state guard, then the strictly-increasing interval check, then the assigned-analyst coherence check, then the calendar guard below, and the notice floor last. An `end_utc` at or before `start_utc` on a request that is not `RELEASED` therefore reports `ERR_EXAM_REQUEST_INVALID_STATE`, while that same interval named against an examiner who is not the request's holder reports `ERR_INVALID_INTERVAL`. Scheduling consults no standing battery whatever: an examiner on `PROBATION`, `SUSPENDED` or even `DECERTIFIED`, and one whose `employment_status` is no longer `ACTIVE`, may still be booked, confirmed and recorded as having testified, because testimony concerns work the laboratory has already released.

Two independent guards apply. The calendar guard treats a hearing as the half-open interval from `start_utc` up to but excluding `end_utc`, then extends every existing block by a 60-minute travel buffer at each end: the new hearing may not intersect any of that examiner's events whose `status` is `SCHEDULED` or `CONFIRMED` once those are so extended, else `ERR_TESTIMONY_SCHEDULE_CONFLICT`. An examiner cannot be in two courthouses at once, and cannot be in the second one without an hour to get there, so a hearing beginning exactly 60 minutes after an earlier one ends is admissible while one beginning a single second earlier is refused. Events that are `TESTIFIED` or `CANCELLED` occupy nothing. The notice guard requires `notice_days` to be at least 7, else `ERR_INSUFFICIENT_TESTIMONY_NOTICE` — unless `subpoena_received` is true, in which case the notice floor is waived entirely, because a served subpoena compels attendance whatever the notice. A served subpoena waives only the notice floor; it never waives the calendar guard, so a subpoena for a slot the examiner is already booked into is still `ERR_TESTIMONY_SCHEDULE_CONFLICT`.

An event is then confirmed, completed or cancelled. Confirmation carries no body, requires `status` `SCHEDULED` else `ERR_COURT_EVENT_INVALID_STATE`, moves the event to `CONFIRMED` and sets `subpoena_received` to true, service being what confirmation records; the block's occupation of the calendar is unchanged, since both `SCHEDULED` and `CONFIRMED` occupy. Completion carries a `testimony_note`, is admissible only from `CONFIRMED` else `ERR_COURT_EVENT_INVALID_STATE`, and additionally requires the current logical instant to be at or after `end_utc`, else `ERR_COURT_EVENT_NOT_ELAPSED` — testimony cannot be recorded as given before the hearing has finished, though recording it at exactly `end_utc` is allowed. It moves the event to the terminal `TESTIFIED`, after which the block no longer occupies the calendar and the slot may be rebooked. Cancellation carries a `cancellation_reason`, is admissible from `SCHEDULED` or `CONFIRMED`, and moves the event to the terminal `CANCELLED`; the block is released from the calendar immediately and its `docket_number` is freed for that examiner, so the same docket may be rescheduled.

Court events are readable individually and as a list narrowable by `examination_request_id`, `analyst_id` and `status`, which together with the workload read of §3.4 is how a coordinator sees what a given examiner owes the court and the bench at the same time.
