# Retirement Plan 401K API — Product Requirements Document

## 1. Introduction

This document specifies the requirements for a 401(k) Retirement Plan Management API. The system administers the full lifecycle of a defined-contribution retirement plan: it onboards participants, records bi-weekly contribution periods, computes employer matching under either a tiered or safe-harbor formula, tracks vesting under cliff or graded schedules, originates and services participant loans, processes hardship withdrawals against IRS safe-harbor categories, and administers age-based Required Minimum Distributions.

The system is designed around two complementary concerns. On one side, every monetary movement is an auditable, integer-cent operation whose precision and rounding order are pinned — a 401(k) plan administrator and the plan's custodian must be able to reconstruct every balance from its underlying contribution, match, vesting, withdrawal, and distribution events. On the other side, every operator action must respect the federal regulatory envelope: contribution deferral caps, vesting cliffs, hardship safe-harbor categories, the one-loan-at-a-time rule, and the age-73 RMD trigger are not advisory — they reject offending requests outright. The API is the system of record that reconciles these two perspectives across a plan's lifetime.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and contract structure that apply across every endpoint described in §4.

### 2.1. User and Role-Based Access Control

Every request must carry two HTTP headers: `X-User-ID`, which identifies the acting user, and `X-User-Role`, which declares the operational capacity under which the request is made. The system recognizes exactly three roles, each spelled as `PlanAdmin`, `Participant`, and `Custodian`. A request that omits either header — or carries a header value the server cannot parse — is rejected with `ERR_UNAUTHENTICATED`. A request that authenticates successfully but whose declared role is not permitted to perform the requested operation per the authorization rules of §4 is rejected with `ERR_FORBIDDEN`.

The two header values stand for fundamentally different things depending on the declared role. When `X-User-Role` is `PlanAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server treats it as the actor of record for plan administration actions but never compares it to any entity's `id`. When `X-User-Role` is `Custodian`, `X-User-ID` is likewise an opaque identifier for a third-party custodian or auditor with read-only access, and the server never compares it to any entity's `id`. When `X-User-Role` is `Participant`, `X-User-ID` is the `id` of the acting `Participant` entity; ownership checks on any resource that references a `Participant` compare the resource's participant foreign-key field to `X-User-ID`, and read or write attempts against resources belonging to a different participant are rejected with `ERR_FORBIDDEN`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

---

### 2.3. Pagination

List endpoints expose two query parameters that govern paging: `limit`, the maximum number of items returned, which defaults to 10 and is bounded by a minimum of 1 and a maximum of 100; and `offset`, the number of items to skip, which defaults to 0. Unless an endpoint says otherwise, list responses are sorted by `created_at` in ascending order. The pagination metadata fields — `limit`, `offset`, `total_count`, and `has_more` — appear in the `meta` block of every list response envelope.

### 2.4. Common Resource Properties

Every primary resource — `Plan`, `Participant`, `ContributionPeriod`, `Loan`, `HardshipWithdrawal`, and `RMDDistribution` — carries the same four system-managed fields, alongside a domain `status` field whose enumeration is fixed per entity (see §3). The `id` is a server-minted UUID with no type prefix. The `created_at` field is an ISO 8601 UTC timestamp with three fractional digits, set once at creation. The `updated_at` field is an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation. The `version` field is a non-negative integer that begins at 1 on creation and increments by exactly one with every mutation, including mutations that arise from cascade reconciliation rather than from a direct write against the resource. The `VestingEvent` resource is the single exception: it is an immutable, append-only audit row, so it carries only `id` and `created_at` — neither `updated_at` nor `version` is present on a `VestingEvent`.

### 2.5. Monetary Precision and Rounding Discipline

All monetary fields are stored and exchanged as integer cents — there are no floating-point dollar values anywhere in the system, and the API never returns decimal currency. Computations follow precision rules pinned per calculation: each multiplication is followed by a `floor` to integer cents, and tiered formulas sum **after** each tier's individual floor (the floor must not be deferred to the end of the tiered sum). The two places that diverge from `floor` are deliberate: the loan amortization computes a per-payment value via `ceil` so the loan repays fully across its term, and the hardship maximum is clamped to zero through a max-with-zero so that an exhausted vested-balance cap can never produce a negative approved amount. The chosen rounding order is part of the contract — reversing it (for instance, summing raw amortization values before rounding) yields a different total and is forbidden.

### 2.6. Hierarchical Consistency and Cascade Discipline

The plan, the participant, the contribution period, and the loan are arranged in a hierarchy where a transition on a parent can cascade derived state down through its children. Every cascade mutates the affected child as a first-class write: the child's `updated_at` is refreshed and its `version` is incremented by one, the same as if a direct request had targeted it. When a plan is terminated, the cascade reaches participants (depth 2), and from each terminated participant onward to any disbursed loan (depth 3); each distinct affected row gets exactly one version bump per triggering cascade event — derived-field reconciliation that fires on the same row as a result of the same triggering event (for example, `vested_employer_balance_cents` and `outstanding_loan_principal_cents` being recomputed on a participant whose `employer_balance_cents` and `enrollment_status` were just updated by the same cascade) is absorbed into that single version bump and does not produce an additional increment. Similarly, closing a contribution period rolls forward the participant's `employee_balance_cents` and `employer_balance_cents` (depth 2), which in turn forces a recomputation of `vested_employer_balance_cents` (depth 3) — derived-field reconciliation is always strictly downstream of the field that triggered it but shares the same version increment. The participant's `outstanding_loan_principal_cents` is itself a derived field: it equals the sum of `outstanding_principal_cents` across all of the participant's loans whose status is `DISBURSED`, and it is refreshed on every loan state change.

A conservation invariant binds contribution periods to participant balances at all times: the participant's `employee_balance_cents` equals the sum of `employee_contribution_cents` across that participant's contribution periods whose status is `CLOSED`. Reversing a closed period (transition `CLOSED → REVERSED`) is a compensating action that subtracts the period's employee and employer contributions back out of the participant's balances and recomputes the vested employer balance; the invariant therefore holds before, after, and through the close-reverse pair.

### 2.7. Optimistic Concurrency Control on Plan Termination

Terminating a plan is the one administrative operation guarded by an optimistic-concurrency check on the parent `Plan` resource. The request body must include `expected_plan_version` — a non-optional integer field that carries the client's last observed `version` of the target plan. If `expected_plan_version` does not equal the plan's current `version`, the request is rejected with `ERR_STALE_VERSION` and an HTTP 412 status. The protection covers the case where another administrator has, since the terminator last observed the plan, legitimately changed it — most commonly by freezing or unfreezing it — and the terminator's view is therefore stale; rejecting on stale version forces the terminator to re-read the plan and re-confirm intent rather than overwrite an out-of-date posture. No other endpoint in the system accepts `expected_plan_version` or any other version field: termination is the sole concurrency-guarded write, and endpoints not listed under this rule do not take a version field.

### 2.8. Nested Resource Retrieval and Referential Integrity

Where a request carries multiple identifiers in its URL or its body, the server validates them left-to-right. If a path identifier or a foreign-key identifier in the request body — `plan_id` on a `Participant` creation, `participant_id` on a `ContributionPeriod`, a `Loan`, a `HardshipWithdrawal`, an `RMDDistribution`, or a `VestingEvent` — does not resolve to an existing entity, the request is rejected with `ERR_NOT_FOUND`. Existence checks precede state, authorization-scope, and business-rule checks, so a missing parent surfaces before any downstream rule can mask it.

### 2.9. Vesting Discipline

The participant's `years_of_service` is a derived field computed as the floor of the number of days between the system clock and `hire_date` divided by 365. It is recomputed lazily on any read or any vesting-relevant operation, and on every system year-tick. Vesting itself depends on the plan's chosen schedule. Under the `CLIFF_3` schedule the participant's vested percentage is zero while years of service is below 3 and is 100% once years of service reaches 3 or more. Under the `GRADED_6` schedule the participant gains vesting in 20-percentage-point increments per year of service: 0% at less than one full year, 20% at one full year, 40% at two, 60% at three, 80% at four, and 100% at five or more (six full years confirms full vesting and any year beyond that remains fully vested). The vested employer balance is then the participant's `employer_balance_cents` multiplied by the vested percentage expressed as basis points and divided by ten thousand, with a floor applied at the multiplication. The recomputation always reads the participant's most recent `employer_balance_cents` — the trigger event (a contribution close, a loan default, a hardship payment) updates the raw employer balance first and the derived vested balance reconciles strictly afterward.

### 2.10. Validation Ordering and Error Precedence

When more than one validation rule applies to the same endpoint, the server evaluates them in a fixed priority order, returning the first violated rule and not continuing. Authentication runs first; an absent or unparseable `X-User-ID`/`X-User-Role` header pair returns `ERR_UNAUTHENTICATED` before any other check. Authorization runs second; a role not permitted for the endpoint returns `ERR_FORBIDDEN`. Existence of every path-templated parent runs third and returns `ERR_NOT_FOUND` on the first identifier in the path that does not resolve. State eligibility runs fourth; a transition attempted against a resource whose current state does not permit it returns `ERR_INVALID_STATE`. The plan-termination optimistic-concurrency check runs fifth (only on that endpoint) and returns `ERR_STALE_VERSION`. Business-safety, business-constraint, business-fiscal, business-temporal, and business-referential checks follow in that order, with the body-level type and field-presence sweep — `ERR_INVALID_REQUEST` — applying as a low-priority backstop across all endpoints. This precedence is deliberate: a state-illegal transition surfaces with `ERR_INVALID_STATE` before any fiscal limit can mask it, and a missing parent surfaces with `ERR_NOT_FOUND` before any state check is even attempted.

## 3. Business Logic & Workflows

### 3.1. Plan Configuration and Lifecycle

A plan administrator initiates a new retirement plan by creating a `Plan` resource. Creation requires a display `name`, a `plan_year` between 1900 and 2999 inclusive that identifies the calendar year the plan operates in, the employer's chosen `match_formula` — one of `TIERED` or `SAFE_HARBOR_ENHANCED` — and the chosen `vesting_schedule` — one of `CLIFF_3` or `GRADED_6`. Two regulatory caps are configurable per plan but default to currently-pinned federal values: `annual_compensation_limit_cents`, the IRC §401(a)(17) compensation ceiling that bounds the compensation slice used in match calculations, defaults to 34,500,000 cents; and `annual_deferral_limit_cents`, the IRC §402(g) elective deferral cap for participants under age 50, defaults to 2,300,000 cents. A newly created plan begins in `DRAFT` status with `version = 1`.

The plan progresses through four states. Activation by a plan administrator advances `DRAFT → ACTIVE` and is only permitted once the plan has its `match_formula` and `vesting_schedule` set; it bumps the plan's `version` and refreshes `updated_at`. A live plan can be frozen by transitioning `ACTIVE → FROZEN`, and unfrozen back via `FROZEN → ACTIVE`; both are version-bumping mutations. While the plan is frozen, any attempt to open a new contribution period is rejected because contribution-period creation requires the plan to be in `ACTIVE` status. The terminal transition `ACTIVE → TERMINATED` is the version-guarded operation described in §2.7: it requires `expected_plan_version` and, on success, performs three cascading mutations. The plan's own status moves to `TERMINATED` and its `version` increments. Every participant of the plan whose `enrollment_status` is `ENROLLED` or `SUSPENDED` is moved to `TERMINATED` (depth 2) with its own `version` bump. For every such terminated participant, any loan in `DISBURSED` status is cascaded to `DEFAULTED` (depth 3), the loan's `version` is bumped, and the participant's `outstanding_loan_principal_cents` is reduced to zero as the derived-field reconciliation downstream of the loan defaults.

### 3.2. Participant Onboarding and Enrollment

A participant is brought into a plan by creating a `Participant` resource scoped to a `plan_id`, carrying a legal `full_name`, an ISO 8601 `date_of_birth`, an ISO 8601 `hire_date`, the participant's reported annual gross compensation in integer cents via `annual_compensation_cents` (which must be strictly positive), and optionally an initial elective deferral expressed in basis points via `deferral_rate_bps` (defaulting to 0, bounded between 0 and 10000 inclusive — for example, 600 means 6.00% of compensation). On creation the participant's enrollment is `PENDING`, their computed balances `employee_balance_cents` and `employer_balance_cents` are 0, their derived `years_of_service` is 0, their `vested_employer_balance_cents` is 0, and their `outstanding_loan_principal_cents` is 0.

A participant cannot post contributions until enrolled, and enrollment requires two preconditions. Moving the participant from `PENDING` to `ENROLLED` requires the participant's plan to be in `ACTIVE` status (a cross-entity check) and the participant's `deferral_rate_bps` to be set to a strictly positive value; the transition bumps the participant's `version`. A participant may then be suspended (`ENROLLED → SUSPENDED`) and resumed (`SUSPENDED → ENROLLED`); resumption is also gated on the plan being `ACTIVE`. While the participant is suspended, future contribution-period creations against that participant are rejected because contribution-period creation requires the participant to be in `ENROLLED` status. A participant may be terminated from either `ENROLLED` or `SUSPENDED`; from `ENROLLED`, the transition cascades any disbursed loan on the participant to `DEFAULTED` (depth 2, with a loan version bump) and reconciles the participant's `outstanding_loan_principal_cents` (depth 3). Termination from `SUSPENDED` does not carry the loan-default cascade because no loans should remain disbursed on a suspended participant, but the participant's own status and version still progress.

A participant can self-service their elective deferral by submitting a new `deferral_rate_bps`; the same operation may also be performed by a plan administrator on a participant's behalf. The update bumps the participant's `version`.

### 3.3. Pay-Period Contributions and the Employer Match

A `ContributionPeriod` records a single pay-period's compensation and the resulting employee deferral and employer match for one participant. Creation requires `participant_id`, an ISO 8601 `period_end_date`, and the strictly positive `gross_compensation_cents` paid in that period; the period is created in `OPEN` status with `employee_contribution_cents` and `employer_match_cents` both at 0. The period is finalized by a plan administrator closing it, transitioning `OPEN → CLOSED`. Closing requires the plan to be `ACTIVE` and the participant to be `ENROLLED` (cross-entity preconditions), and on success it runs the matching calculation and applies four cascades.

The matching calculation first determines a per-period capped compensation as the smaller of the period's `gross_compensation_cents` and the per-period compensation slice, which is the plan's `annual_compensation_limit_cents` divided by 26 with a floor applied — i.e., a bi-weekly slice of the annual §401(a)(17) ceiling. The employee deferral amount for this period equals the capped compensation multiplied by the participant's `deferral_rate_bps` and divided by 10000, with a floor applied. That amount becomes `employee_contribution_cents`, and closing is rejected with `ERR_DEFERRAL_LIMIT_EXCEEDED` if it would breach the §402(g) cap. The cap test is evaluated as follows: the year-to-date already-closed total equals the sum of `employee_contribution_cents` across the same participant's contribution periods that are currently in `CLOSED` status and whose `period_end_date` falls in the same calendar year as the plan's `plan_year`; closing this period is rejected whenever that already-closed total plus the deferral computed for the period being closed strictly exceeds `annual_deferral_limit_cents`. The deferral computed for the period being closed is the raw value from the matching calculation above — closing does not auto-shrink the deferral to fit beneath the cap; an over-cap period is refused outright.

The employer match is then computed under the plan's chosen formula. When the plan's `match_formula` is `TIERED`, the match is the sum of two tiers, each floored independently before summation: the first tier matches 100% on the first 3% of compensation deferred — its tier rate is 10000 basis points (full match) and its tier cap is 300 basis points of deferral — and equals the capped compensation multiplied by the smaller of the participant's `deferral_rate_bps` and 300, divided by 10000, with a floor applied; the second tier matches 50% on the next 2% of compensation deferred — its tier rate is 5000 basis points (half match) and its tier cap is 200 basis points of additional deferral — and equals the capped compensation multiplied by the smaller of 200 and the participant's `deferral_rate_bps` reduced by 300 (or zero if that subtraction would be negative), divided by 10000 with a floor applied, and then divided by 2 with a second floor applied (i.e., integer-divide the floored intermediate by 2). Under the tiered formula the maximum effective employer cost is 4% of compensation — reached once the participant defers at least 5% — but the schedule is curved: at a 4% deferral the participant earns only 3.5% of compensation in match (the full first tier plus half of one remaining deferral percentage point).

When the plan's `match_formula` is `SAFE_HARBOR_ENHANCED`, the match is a single-tier full-rate cap: the effective matched deferral basis points are the smaller of the participant's `deferral_rate_bps` and 400, and the match equals the capped compensation multiplied by that effective basis-point value, divided by 10000, with a floor applied. The safe-harbor curve is flat-and-cliff at 4%: at a 4% deferral the participant earns the full 4% of compensation in match, identical to a 5% deferral — but **different** from the tiered formula's 3.5% at the same inputs. The two formulas produce divergent results from identical inputs and the system never substitutes one for the other.

On a successful close, the participant's `employee_balance_cents` is increased by the period's `employee_contribution_cents` (depth-2 cascade), the participant's `employer_balance_cents` is increased by the period's `employer_match_cents` (depth-2 cascade), the participant's `vested_employer_balance_cents` is recomputed (depth-3 derived-field reconciliation, against the new `employer_balance_cents`), and the period itself moves to `CLOSED` with its `version` bumped.

A closed period may be reversed by a plan administrator transitioning `CLOSED → REVERSED`, provided the plan is still `ACTIVE`. The reversal is a compensating action: the participant's `employee_balance_cents` is reduced by that period's `employee_contribution_cents`, the participant's `employer_balance_cents` is reduced by that period's `employer_match_cents`, the participant's `vested_employer_balance_cents` is recomputed, and the period itself moves to `REVERSED` with a version bump. The close-then-reverse pair leaves the participant's balances unchanged, preserving the conservation invariant described in §2.6.

### 3.4. Plan Loans

A participant — or a plan administrator acting on the participant's behalf — may originate a `Loan` against the participant's vested savings. Creation requires `participant_id`, the requested `principal_cents` (strictly positive), a `term_months` between 1 and 180 inclusive (the broader primary-residence upper bound; the `Loan` resource does not carry a loan-category discriminator, so the same `term_months` range applies uniformly to every loan), and an `annual_interest_rate_bps` strictly greater than 0 and at most 2500 (i.e., up to 25.00%). The loan begins in `REQUESTED` status with `monthly_payment_cents` and `outstanding_principal_cents` both at 0.

Disbursement — transitioning the loan from `REQUESTED` to `DISBURSED` — is the credit decision and runs the amortization calculation. Disbursement requires the plan to be `ACTIVE` and the participant to be `ENROLLED` (cross-entity preconditions). It also enforces two hard constraints. First, the participant must have no other loan whose status is `DISBURSED` — the one-loan-at-a-time rule — and a violation is rejected with `ERR_LOAN_ALREADY_OUTSTANDING`. This rule also encodes a temporal semantic: a loan's active interval runs from disbursement (inclusive) to terminal state (exclusive, where terminal means `REPAID` or `DEFAULTED`), and any overlap of two active intervals for the same participant is forbidden. Second, the loan's `principal_cents` must not exceed the smaller of half the participant's vested savings — explicitly the floor of (`employee_balance_cents` + `vested_employer_balance_cents`) divided by 2 in integer arithmetic — and the absolute statutory cap of 5,000,000 cents. A loan that exceeds this borrowing limit is rejected with `ERR_LOAN_EXCEEDS_LIMIT`.

The amortization calculation determines the standard monthly payment. The monthly interest rate is the loan's `annual_interest_rate_bps` divided by 10000 and again divided by 12, the number of months per year. The raw monthly payment then equals the principal multiplied by the monthly rate multiplied by one-plus-the-monthly-rate raised to the term in months, all divided by the same one-plus-the-monthly-rate raised to the term minus one. The result is rounded up (`ceil`) to the next whole cent to produce `monthly_payment_cents`, so that the payment schedule fully repays the loan rather than leaving a sub-cent residual. The rounding order is pinned at the per-payment scalar — never on a sum of raw values; reversing the order would change the total interest and is forbidden. On a successful disbursement the loan's `outstanding_principal_cents` is set equal to `principal_cents`, the participant's `outstanding_loan_principal_cents` is increased by the principal (depth-2 derived-field reconciliation), and the loan moves to `DISBURSED` with a version bump.

A disbursed loan settles in one of two ways. A repayment — transitioning `DISBURSED → REPAID` — accepts a body field `amount_cents` that must be strictly positive (a missing or non-positive `amount_cents` is a shape failure surfaced as `ERR_INVALID_REQUEST`) and must be at least the loan's current `outstanding_principal_cents` (a strictly positive amount that is nevertheless less than the outstanding is rejected with `ERR_INVALID_STATE`); the participant or the plan administrator submits the payoff. On success the loan's `outstanding_principal_cents` is zeroed, the participant's `outstanding_loan_principal_cents` is reduced by the prior outstanding (depth-2 reconciliation), and the loan moves to `REPAID` with a version bump. Alternatively, a default — transitioning `DISBURSED → DEFAULTED`, initiated either by a plan administrator or as a cascaded consequence of the participant being terminated — treats the unpaid principal as a deemed distribution against the participant's vested employer match: the participant's `employer_balance_cents` is reduced by the loan's prior `outstanding_principal_cents` (depth-2 cascade, employee balance unaffected), the participant's `vested_employer_balance_cents` is recomputed (depth-3 derived-field reconciliation against the new employer balance), the participant's `outstanding_loan_principal_cents` is reduced by the prior outstanding (depth-2 reconciliation), and the loan moves to `DEFAULTED` with a version bump.

### 3.5. Hardship Withdrawals

A participant — or a plan administrator on the participant's behalf — may request a `HardshipWithdrawal` to access savings before retirement age. Creation requires `participant_id`, a strictly positive `requested_amount_cents`, and a `hardship_category` drawn from the IRS safe-harbor enumeration: `MEDICAL_EXPENSES`, `PRIMARY_RESIDENCE_PURCHASE`, `TUITION_PAYMENT`, `EVICTION_PREVENTION`, or `FUNERAL_EXPENSES`. The withdrawal begins in `REQUESTED` status with `approved_amount_cents` and `ten_percent_penalty_cents` both at 0.

A plan administrator either approves or denies the request. The denial transition `REQUESTED → DENIED` is unconditional and simply records the rejection with a version bump. The approval transition `REQUESTED → APPROVED` is gated on the plan being `ACTIVE`, the participant being in either `ENROLLED` or `SUSPENDED` status (cross-entity preconditions), and the maximum hardship amount computation producing a strictly positive value — if it does not, the request is rejected with `ERR_NO_HARDSHIP_HEADROOM`.

The maximum hardship amount is the greater of zero and the smallest of three candidates. The first candidate, the vested-savings cap, is computed in this fixed order: take the integer floor of (`employee_balance_cents` + `vested_employer_balance_cents`) divided by 2 (the integer-arithmetic half-of-vested figure), then subtract the participant's current `outstanding_loan_principal_cents` from that floored half — i.e., loans already drawn against the participant's vested balance reduce hardship headroom one-for-one, and the subtraction is applied AFTER the divide-and-floor so this candidate may legitimately be negative for an over-loaned participant (the outer max-with-zero in the formula below then clamps a negative cap_a away). The second candidate is the absolute hard cap of 5,000,000 cents. The third candidate is the participant's own `requested_amount_cents`. The approved amount is set to the maximum of zero and the smallest of those three values, so an exhausted or over-loaned participant whose first cap is negative still produces an approved amount of zero rather than a negative number; in that case the approval is itself rejected because the rule that gates approval requires the maximum hardship amount to be strictly positive. On approval the approved amount is written to `approved_amount_cents`, and a 10% early-withdrawal penalty is assessed only if the participant is younger than the age penalty threshold of 59 full years (the IRS age 59.5 threshold rounded down to whole years per the integer-arithmetic precision rule in §2.5): the participant's age in whole years is computed as the floor of the number of days between the system clock and `date_of_birth` divided by 365, and the penalty `ten_percent_penalty_cents` is set to ten percent of `approved_amount_cents` with a floor applied; otherwise the penalty is 0. The withdrawal moves to `APPROVED` with a version bump.

An approved hardship is finally paid by a plan administrator transitioning `APPROVED → PAID`. Payment debits the participant's balances in a fixed order: employee deferrals first — the participant's `employee_balance_cents` is reduced by the approved amount, and any shortfall (the portion of the approved amount that exceeds the participant's employee deferrals) is then taken from the participant's `employer_balance_cents`. Both of these are depth-2 cascades; the participant's `vested_employer_balance_cents` is recomputed (depth 3, derived-field reconciliation) and the withdrawal moves to `PAID` with a version bump.

### 3.6. Required Minimum Distributions

Once a participant reaches age 73, the IRS requires an annual minimum distribution from the plan account. An `RMDDistribution` is the system's record of one such required payment for one participant in one calendar year. Creation requires `participant_id`, the integer `distribution_year` identifying the calendar year the RMD is required for, a strictly positive `prior_year_end_balance_cents` snapshotting the plan-account balance as of December 31 of the prior year, and the `rmd_variant` selecting which life-expectancy table to apply — either `UNIFORM_LIFETIME` (indexed by the participant's age alone) or `JOINT_LIFE` (indexed by both the participant's age and a spouse's age). When the variant is `JOINT_LIFE`, the `spouse_date_of_birth` field carries the spouse's ISO 8601 date of birth; for `UNIFORM_LIFETIME` the field is null. The distribution begins in `PENDING` status with `required_amount_cents` set by the RMD calculation and `distributed_amount_cents` set to 0.

The RMD calculation begins by computing the participant's age at the end of `distribution_year` as the floor of the number of days between December 31 of `distribution_year` and the participant's `date_of_birth` divided by 365. If that age is less than the age trigger of 73, the creation is rejected with `ERR_RMD_NOT_REQUIRED` — the participant is not yet subject to RMDs and the system refuses to manufacture a distribution. Under the `UNIFORM_LIFETIME` variant, the life-expectancy factor is read from the IRS Uniform Lifetime Table indexed by the participant's age at year-end. The table is pinned for every integer age from 73 through 120 as the following exact factor values: 73→26.5, 74→25.5, 75→24.6, 76→23.7, 77→22.9, 78→22.0, 79→21.1, 80→20.2, 81→19.4, 82→18.5, 83→17.7, 84→16.8, 85→16.0, 86→15.2, 87→14.4, 88→13.7, 89→12.9, 90→12.2, 91→11.5, 92→10.8, 93→10.1, 94→9.5, 95→8.9, 96→8.4, 97→7.8, 98→7.3, 99→6.8, 100→6.4, 101→6.0, 102→5.6, 103→5.2, 104→4.9, 105→4.6, 106→4.3, 107→4.1, 108→3.9, 109→3.7, 110→3.5, 111→3.4, 112→3.3, 113→3.1, 114→3.0, 115→2.9, 116→2.8, 117→2.7, 118→2.5, 119→2.3, 120→2.0. For any participant age strictly greater than 120 the factor used is 2.0 (the age-120 entry); ages below 73 are gated out by the trigger check above. Under the `JOINT_LIFE` variant, the spouse's age at the same year-end is computed the same way from `spouse_date_of_birth`, and the variant is only eligible if the spouse is more than 10 years younger than the participant — i.e., the participant's age minus the spouse's age must be strictly greater than 10; if the age gap is 10 years or less, the request is rejected with `ERR_JOINT_LIFE_INELIGIBLE`. When eligible, the factor is read from the Joint Life Table indexed by the pair (participant_age, spouse_age). The Joint Life Table is pinned for the following (participant_age, spouse_age) keys with these exact factor values: (73,60)→27.4, (73,55)→30.7, (73,50)→34.2, (73,45)→37.9, (73,40)→41.7, (74,60)→27.0, (74,55)→30.3, (75,60)→26.7, (75,55)→30.0, (80,65)→22.6, (80,60)→24.8, (80,55)→28.0, (85,70)→17.9, (85,65)→19.7, (85,60)→22.4. For any eligible (participant_age, spouse_age) pair not present in the pinned table, the factor is computed deterministically as the Uniform Lifetime factor for `participant_age` (looked up by the rule above, with the age-120 clamp for ages beyond 120) plus 0.5 multiplied by (age_gap − 10), where age_gap is participant_age − spouse_age. This fallback guarantees the Joint Life factor strictly exceeds the Uniform Lifetime factor for the same participant age whenever the spouse is more than 10 years younger, so for the same `prior_year_end_balance_cents` the joint-life variant yields a strictly smaller `required_amount_cents` — the system never substitutes one variant for the other.

The required amount is then `prior_year_end_balance_cents` divided by the chosen life-expectancy factor, with a floor applied. To keep the arithmetic in integer cents, the factor is held as a fixed-point value scaled by one million during the multiply-and-divide: the prior-year-end balance multiplied by one million is divided by the factor multiplied by one million (each with a floor applied), and the final divide is floored. A second uniqueness rule prevents two distributions covering the same year: the pair (`participant_id`, `distribution_year`) is a closed, discrete bucket and must be unique across all `RMDDistribution` rows — an attempt to create a second distribution for the same participant in the same year is rejected with `ERR_DUPLICATE_RMD_YEAR`. (Unlike the loan's half-open continuous interval, the year bucket is the inclusive discrete unit; both interval semantics coexist in this system.)

A pending RMD is settled by a plan administrator transitioning `PENDING → PAID` and supplying the `distributed_amount_cents` actually paid. Payment requires that the participant's current age (computed from the system clock against `date_of_birth`) is at least 73 years, and that `distributed_amount_cents` equals `required_amount_cents` — partial payments are not accepted on this transition. On success the participant's `employee_balance_cents` and `employer_balance_cents` are reduced pro-rata by the distributed amount (depth-2 cascade). The pro-rata split is pinned in integer cents as follows: let `total = employee_balance_cents + employer_balance_cents` measured immediately before the deduction; if `total > 0`, the employee share equals `floor(distributed_amount_cents * employee_balance_cents / total)` and the employer share equals `distributed_amount_cents − employee_share` (the rounding residual lands on the employer side, so the employee balance never goes negative on the rounding edge); if `total == 0`, both shares are 0. The participant's `vested_employer_balance_cents` is recomputed (depth-3 reconciliation), and the distribution moves to `PAID` with a version bump. Alternatively, a pending RMD can be marked missed by transitioning `PENDING → MISSED`, either directly by a plan administrator or automatically by the system's annual year-tick once the distribution year has closed without payment — the status simply moves to `MISSED` with a version bump.

### 3.7. Vesting Audit Trail

The `VestingEvent` resource is the immutable, append-only audit row that records each service-anniversary tick for a participant. Creation requires `participant_id`, the service-anniversary `as_of_date`, the snapshot of the participant's years of service immediately after the tick via `years_of_service_after`, and the snapshot of the vested percentage in basis points immediately after the tick via `vested_pct_bps_after` (for example, 6000 means 60.00%). Because the row is immutable, it carries no `updated_at` and no `version` (see §2.4). A vesting event is appended naturally as part of the system's annual year-tick: for every enrolled or suspended participant whose `vested_pct_bps` value under the plan's vesting schedule differs between its prior `years_of_service` and its recomputed `years_of_service` at the tick — this is the precise sense of "crosses a vesting boundary" — the year-tick recomputes that participant's `vested_employer_balance_cents` (against the participant's current `employer_balance_cents`) and appends a `VestingEvent` snapshotting the new years-of-service and the new vested percentage. The appended `VestingEvent`'s `as_of_date` is set by the system to the current system-clock instant at the moment the tick is processed (formatted as the standard ISO 8601 UTC millisecond string), not to a derived hire-date anniversary.

### 3.8. Test-Driving Capabilities

Two administrative capabilities exist to drive the system's logical clock and year roll-over for evaluation purposes. The first sets the system clock to a supplied `to_iso8601` instant — used for age calculations across RMD, hardship penalty, and vesting, and for the derivation of `years_of_service`; on success the clock is advanced and `years_of_service` is recomputed lazily on the next read of any participant. The second simulates the annual year-tick at a supplied `as_of_year`: for each enrolled or suspended participant whose `years_of_service` crosses a vesting boundary, the year-tick recomputes that participant's `vested_employer_balance_cents` and appends the corresponding `VestingEvent` per §3.7; and for each pending RMD whose `distribution_year` is strictly less than `as_of_year`, the RMD's status is set to `MISSED`. Both capabilities are restricted to a plan administrator.
