# Standards Development Consensus API — Product Requirements Document

## 1. Introduction

A standards developing organization does not publish documents; it publishes *agreements*. The value of a published standard rests entirely on the defensibility of the process that produced it — that a technical committee was balanced across competing interests, that every negative vote was individually considered and answered before the document advanced, that the public was given a real opportunity to comment and that each comment received a written disposition, that anyone holding a patent essential to the text disclosed it and committed to license it, and that a party who believes the procedure was violated has somewhere to complain. Today that entire chain of evidence lives in spreadsheets, mailing-list archives and the institutional memory of a secretariat. When a losing party challenges a standard, the organization cannot reconstruct who was eligible to vote on which revision, or prove that a particular objection was ever read.

This document specifies the API for a system that makes the consensus process itself the system of record. Every artefact in the pipeline — the participant roster, the technical committee and its interest-category composition, the work item, each draft revision, each ballot and each vote cast on it, each comment and its disposition, each patent disclosure and licensing commitment, each appeal, and each post-publication interpretation or erratum — is a first-class addressable resource whose state transitions are governed by rules the server enforces rather than rules a chair remembers. The system is mounted under the `/sdo` path prefix, plus a single administrative namespace beginning with `/_` used only to drive the logical clock in tests.

Two design commitments run through everything that follows. The first is that **procedural arithmetic is computed, never asserted**: balance verdicts, quorum and approval percentages, disposition completeness, review schedules and appeal deadlines are all derived by the server from the underlying rows, and a client may never supply them. The second is that **advancement is gated, not merely discouraged**: a work item carries a derived procedural gate that a live appeal, an unresolved objection or an out-of-balance committee holds shut, and the endpoints that advance a standard refuse to run while it is shut. Engineers implementing this specification should read §2 as the invariant contract and §3 as the domain narrative that determines when each rule fires.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint — including the administrative clock endpoint — must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the capacity in which the caller is acting. Both header values are stripped of surrounding whitespace before anything is done with them, and the stripped value is what is matched against the role names and compared to stored identifiers. If either header is absent, or is empty or blank once stripped, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This check runs before anything else the server does, ahead even of deciding whether the requested path resolves to a stored row, so an unauthenticated request naming a nonexistent identifier still returns 401 rather than 404.

Exactly six roles exist, and their names are spelled `Proposer`, `CommitteeMember`, `CommitteeChair`, `PublicCommenter`, `StandardsStaff` and `AppealsBoard`. If `X-User-Role` carries any other string, or carries one of the six but that role is not listed for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Role admission is decided from the header alone, before any resource is loaded from storage.

Four of the six roles are participant-backed. When `X-User-Role` is `Proposer`, `X-User-ID` is the `id` of the acting `Participant`; ownership checks on any resource that references a `Participant` compare the resource's participant-typed field to `X-User-ID`. The same holds for `CommitteeMember`, for `CommitteeChair` and for `PublicCommenter`: in each of those three cases `X-User-ID` is likewise the `id` of the acting `Participant`, and ownership is decided by comparing the resource's participant-typed field to it. Concretely, a caller in one of these four roles must resolve to a stored participant, and any submitter-identity field carried in a request body — `proposer_participant_id`, `submitter_participant_id`, `disclosing_participant_id`, `appellant_participant_id` or `requester_participant_id` — must equal `X-User-ID`; a mismatch, or a `X-User-ID` that resolves to no participant at all, is `ERR_ACTOR_IDENTITY_MISMATCH` (HTTP 403). The same error covers the case where the `membership_id` supplied when casting a vote belongs to a different participant.

`Proposer` is the capacity in which any participant submits work item proposals, comments on drafts, discloses patents, files appeals and requests interpretations. `CommitteeMember` is the capacity of a participant who holds a seat: it is the only role, alongside `CommitteeChair`, that may cast, change or withdraw a vote, and it is the only role that may withdraw its own pending negative during adjudication. `CommitteeChair` is the participant recorded as a committee's `chair_participant_id`; the chair alone opens ballots, dispositions comments and rules a negative persuasive or non-persuasive. Because the chair is also a seated member and may therefore vote, two segregation-of-duties errors exist specifically to police the chair: `ERR_SELF_ADJUDICATION` and `ERR_DISPOSITION_APPROVER_CONFLICT`. `PublicCommenter` is the capacity of a participant with no committee seat, taking part through the public review period, patent disclosure, appeals and maintenance requests.

The remaining two roles are operational rather than personal. When `X-User-Role` is `StandardsStaff`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it (for example, as `disposition_approved_by_participant_id` on `PublicReview` where a transition writes an approver) but does not compare it to any entity's `id`; where an opaque operator approves a disposition record, that field is left null rather than being populated with the operator string. `StandardsStaff` is the secretariat: it registers participants, forms and activates committees, appoints and suspends seats, approves scopes, announces and closes public reviews, publishes standards, runs periodic review, issues errata and drives the logical clock. Likewise, when `X-User-Role` is `AppealsBoard`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but never compares it to any entity's `id`. The appeals board is the independent panel that decides appeals, and it is deliberately barred from every other mutation in the system so that a body able to vacate a ballot can never have participated in it. Both opaque roles retain read access to every collection.

Two further identity checks are narrower than role admission and are described where they bite. Chair-restricted operations require that `X-User-ID` equal the `chair_participant_id` of the governing committee, failing with `ERR_NOT_COMMITTEE_CHAIR` (HTTP 403). Vote-owner operations require that `X-User-ID` equal the `participant_id` of the `CommitteeMembership` behind the target vote, failing with `ERR_NOT_VOTE_OWNER` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly 20 characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the **logical clock** of §2.4 rather than from wall-clock time — so it is exactly the clock's current instant, and every response issued while the clock sits at one instant carries the same value.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, may not be smaller than 1 and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A `limit` outside the inclusive range from 1 to 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400); both must be integers, and a parameter that is present but empty is likewise malformed; `limit` is validated before `offset`. The filters each list endpoint declares are applied as **exact, case-sensitive equality** against the stored field of the same name — never as a substring or prefix match — and are conjunctive when several are supplied; a declared filter that is present but empty is treated as absent and narrows nothing, and a query parameter the endpoint does not declare is ignored rather than rejected. Filtering happens before pagination, so `total_count` counts the filtered rows.

Results are returned in ascending `created_at` order unless a specific endpoint states otherwise, so paging through a collection walks it in the order the rows were created. Because `created_at` is taken from the logical clock, rows created while the clock stands still share one `created_at`; ties are broken by insertion order, so the ordering is always the order the rows were created even when their timestamps are identical. The `meta` block of a list response carries `limit` and `offset` as they were applied, `total_count` as the number of rows matching the filters before pagination, and `has_more` as a boolean that is true when rows remain beyond the current page.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource in this system carries four common properties. `id` is a server-minted UUID with no type prefix — clients never supply it and never derive meaning from its shape. `created_at` and `updated_at` are ISO 8601 UTC timestamps with three fractional digits; `created_at` is written once at insertion and `updated_at` is refreshed on every mutation that touches the row. `version` is an integer that starts at 1 and increments by exactly 1 on each mutation of that row. All twelve resource types — participants, technical committees, committee memberships, work items, drafts, ballots, votes, comments, public reviews, patent disclosures, appeals and maintenance items — carry all four properties; none is exempt.

Because so many operations in this domain cascade across entities, the version discipline deserves an explicit statement: when one request mutates several rows, **each** mutated row's `version` advances by 1 and its `updated_at` is refreshed. A ballot close, for example, advances the ballot, the affected votes, the draft, the work item and any suspended memberships, all in the same request. Two refinements make that discipline exact. First, a row advances **at most once per request**, however many hops of a cascade write it, and a row *created* by the request is never additionally advanced by a later hop of the same request — a freshly created row is always observable at `version` 1. Second, a re-derivation that turns out to change nothing does not advance a version: recomputing a committee's balance fields, a work item's `consensus_gate`, `unresolved_negative_count` and `ip_status`, or a public review's disposition counters and status advances that row only when it actually writes a different stored value. Endpoints whose own description says they write the row advance it regardless.

Time in this system is a **logical clock**, not wall-clock time. Its startup value is exactly `2026-08-01T00:00:00Z`, and until an operator moves it the server reads that instant; the server must never fall back on real system time. Every deadline, window, expiry and due-date rule specified in this document is evaluated against the logical clock. `StandardsStaff` may set the clock to any ISO 8601 UTC instant by supplying `to_iso8601`; the response reports the new `current_utc`, rendered in the same three-fractional-digit form as every other instant, together with `promoted_public_review_ids`, the identifiers of public reviews that the clock movement promoted from a scheduled state to an open one, listed in ascending creation order. Those two keys are the whole of the response `data`; no resource row is echoed. Setting the clock mutates nothing else — in particular, it never auto-closes a ballot and never auto-closes a review.

### 2.5. Order of Precedence Among Validations

When a single request violates more than one rule, the response must name the violation with the **lowest precedence number** in the ordered ladder below. This ordering is normative and is the single most important cross-cutting contract in this specification: two implementations that both detect all violations but report them in different orders will disagree on the majority of error responses.

1. **10 — Authentication.** Both headers present and non-empty, else `ERR_UNAUTHENTICATED` (401). Precedes path resolution.
2. **20 — Role admission.** `X-User-Role` is one of the six declared roles and is listed for the target endpoint, else `ERR_UNAUTHORIZED` (403). Decided from the header alone.
3. **30 — Path existence.** Every identifier templated into the path resolves to a stored row, checked left to right in the order the segments appear. Appointing a member to an unknown committee returns `ERR_COMMITTEE_NOT_FOUND` before any body field is examined. The applicable error is the one for the missing type: `ERR_PARTICIPANT_NOT_FOUND`, `ERR_COMMITTEE_NOT_FOUND`, `ERR_MEMBERSHIP_NOT_FOUND`, `ERR_WORK_ITEM_NOT_FOUND`, `ERR_DRAFT_NOT_FOUND`, `ERR_BALLOT_NOT_FOUND`, `ERR_VOTE_NOT_FOUND`, `ERR_COMMENT_NOT_FOUND`, `ERR_PUBLIC_REVIEW_NOT_FOUND`, `ERR_PATENT_DISCLOSURE_NOT_FOUND`, `ERR_APPEAL_NOT_FOUND` or `ERR_MAINTENANCE_ITEM_NOT_FOUND`, each HTTP 404.
4. **40 — Request shape.** Required fields present; enum fields carrying a declared member; integer fields non-negative integers; date fields parsing as ISO 8601 calendar dates and datetime fields as ISO 8601 UTC instants; text fields that must be non-empty being non-empty after trimming, though their length bounds are measured on the string exactly as supplied — surrounding whitespace included — and the string is stored exactly as supplied rather than trimmed; identifier-valued body fields being non-blank strings, so a blank or non-string identifier is caught here at 400 rather than at precedence 50 as a 404; `limit` an integer from 1 to 100 and `offset` a non-negative integer; unknown body fields rejected; and any field this document describes as computed or server-maintained rejected when a client supplies it — which is also how a `version`-pinning field is refused on the endpoints of §2.7 that do not declare one. Two consequences of this ladder are worth spelling out, because they are the cases most likely to be implemented backwards. First, consider a committee whose `max_concurrent_ballots` is 1 and which already holds one ballot in `OPEN` status; a second ballot request aimed at that same already-balloting draft with an overlapping window violates two rules at once — the draft is in `SUBCOMMITTEE_BALLOT` rather than `DRAFTING`, and the overlap occupancy has reached capacity. The response is `ERR_INVALID_DRAFT_STATE` (409), because the draft-state check at precedence 70 outranks the capacity check at precedence 106, and no ballot row is created. Second, an appeal filed by a participant who holds no membership, authored no comment and did not propose the work item, submitted after the filing window has already elapsed, likewise violates two rules; the response is `ERR_APPELLANT_NOT_INTERESTED_PARTY` (403), because standing at precedence 97 is decided before timeliness at precedence 117, and no appeal row is created.

### 2.6. Interest-Category Balance Arithmetic

Balance is the organization's central legitimacy claim, and it is computed — twice, on two different bases — every time a committee's composition could have changed. The inputs are the `CommitteeMembership` rows whose `committee_id` is the committee in question. Participants themselves are never counted; only seats are, so a participant appointed to two committees contributes independently to each. Crucially, the category used in the arithmetic is the `interest_category` **snapshotted onto the membership** at appointment, never the participant's current `interest_category`: re-categorising a participant does not retroactively rebalance the committees they already sit on.

For a given set of seats, the arithmetic proceeds in a fixed order. First, count the seats in the set. Second, build `category_counts`, a map from each `interest_category` value to the number of seats in the set holding that category, omitting any key whose count would be zero. Third, set `distinct_category_count` to the number of keys in that map whose count is at least 1. Fourth, take the largest single count in the map — zero if the set is empty. Fifth, compute the dominance share: it is 0.0 when the set is empty, and otherwise 100 multiplied by the largest category count, divided by the number of seats in the set, rounded half up to one decimal place.

The verdict is then one of three labels, chosen by the first matching condition. The set is **`BALANCED`** when it holds at least 3 seats, spans at least 3 distinct interest categories, and its dominance share is no greater than 50.0 percent. Failing that, it is **`PROVISIONAL`** when it holds at least 3 seats, spans at least 2 distinct interest categories, and its dominance share is no greater than 66.7 percent. Failing both, it is **`UNBALANCED`**. All comparisons on the dominance share are inclusive, so a committee sitting exactly at 50.0 percent is `BALANCED` rather than merely provisional. The rounding happens *before* the comparison, which is why two seats out of three in one category yields 66.7 and not 66.666…: that value is above the 50.0 limit and exactly at the 66.7 provisional limit, and equality passes.

The two bases differ only in which seats enter the set, and they are written to two independent groups of fields. The **voting basis** counts only seats whose `status` is `ACTIVE` and whose `voting_rights` is true; suspended seats, withdrawn seats, and active seats that are observers because `voting_rights` is false are excluded entirely. Its outputs are `balance_status`, `active_member_count`, `dominance_pct`, `distinct_category_count` and `category_counts`. This is the label that gates opening a ballot and gates committee activation, and it is the label whose failure is reported as `ERR_COMMITTEE_NOT_BALANCED`. The **roster basis** counts seats whose `status` is either `ACTIVE` or `SUSPENDED`, regardless of `voting_rights`, excluding only withdrawn seats. Its outputs are `roster_balance_status`, `roster_member_count` and `roster_dominance_pct`. The roster basis is consulted by exactly one consumer — the adjudication of an appeal asserting a balance violation — because that appellant's complaint concerns who was appointed, not who happened to be able to vote on the day.

Identical underlying data therefore routinely produces two different labels. Three `ACTIVE` seats in three distinct categories, plus two `SUSPENDED` seats both in the `PRODUCER` category, gives a voting-basis dominance of 33.3 percent with a `BALANCED` verdict, while the roster basis sees five seats with three of them `PRODUCER`, a dominance of 60.0 percent, a `distinct_category_count` of 3 and a `PROVISIONAL` verdict — because 60.0 exceeds the 50.0 balanced limit but does not exceed the 66.7 provisional limit. Both label groups, together with `active_member_count`, `roster_member_count`, `dominance_pct`, `roster_dominance_pct`, `distinct_category_count` and `category_counts`, are recomputed and persisted whenever a seat is appointed, whenever a seat's `status` or `voting_rights` is edited, whenever a committee is activated, and whenever a seat is suspended by the system for repeated non-return at a ballot close.

### 2.7. Version Pinning on Contended Writes

Two write operations in this system read the state of a parent resource, decide what to do based on rows already attached to it, and then mutate that parent. Both therefore require the client to pin the parent's `version` — the value the client last observed — so the server can refuse to act on a stale view. Every other endpoint in this specification takes no version field at all, and supplying one is a malformed body.

The first is announcing a public review, `POST /sdo/public-reviews`, whose body must carry `expected_draft_version` as a required, non-optional field holding the `Draft.version` the client last read. Announcing a review supersedes any still-scheduled announcement on the same draft — the earlier review is cancelled and the draft's `version` advances — so a second announcement must prove it observed the draft as it now stands. When `expected_draft_version` does not equal the draft's stored `version`, the request is rejected with `ERR_STALE_DRAFT_VERSION` (HTTP 412), no public review row is created, and nothing is cancelled, so a stale announcement can never cancel a review its caller never saw. Because a draft's `version` is advanced by every write that reaches it — announcement, review close, ballot creation, ballot evaluation and appeal cascades alike — a caller must re-read the draft to obtain a usable value.

The second is recording a patent disclosure, `POST /sdo/patent-disclosures`, whose body must carry `expected_work_item_version` as a required, non-optional field holding the `WorkItem.version` the client last read. Recording a disclosure re-evaluates patent clearance and can move the work item's `ip_status` to `IP_BLOCKED`, which in turn changes what publication will accept; because that outcome depends on the disclosures already on file, the caller must present the version it read. A mismatch is rejected with `ERR_STALE_WORK_ITEM_VERSION` (HTTP 412), leaving no patent disclosure row and no change to `ip_status`. A work item's `version` is advanced by scope approval, draft creation, ballot cascades, disclosure recording, commitment recording, publication, periodic-review actions and maintenance resolutions.

### 2.8. Percentages, Rounding and Threshold Comparison

Every percentage this system stores — `dominance_pct`, `roster_dominance_pct`, `return_rate_pct`, `provisional_approval_pct`, `final_approval_pct` and `disposition_completeness_pct` — is carried to **one decimal place, rounded half up**. The one non-percentage ratio, a draft's `substantive_change_ratio`, is carried to **four decimal places, rounded half up**.

The order of operations is normative and is not an implementation detail: **each value is rounded first, and only the rounded value is ever compared to a threshold.** Comparing the unrounded quotient changes verdicts. Two returns out of three seats is 66.666… percent, which sits below a 66.7 percent quorum bar when left unrounded but is exactly equal to it once rounded — and every threshold comparison in this specification is inclusive, so equality passes. An implementation that defers rounding to presentation time will disagree with this specification on real ballots.

### 2.9. The Consensus Gate and Cascade Discipline

Each work item carries a derived procedural gate, `consensus_gate`, whose value is either `OPEN` or `BLOCKED`. It is a fixed point over three independent blockers living on other resources, and it is recomputed from scratch on every request that touches one of them rather than being incrementally toggled — so clearing one blocker while another still holds leaves the gate `BLOCKED`. The gate is `BLOCKED` when any of the following holds: some appeal on the work item has `status` `FILED` or `ACCEPTED_FOR_REVIEW`; some draft of the work item has `status` `COMMENT_RESOLUTION`; or the sponsoring committee's `status` is anything other than `ACTIVE`, or its `balance_status` is anything other than `BALANCED`. When none of the three holds, the gate is `OPEN`. A work item that has no `sponsoring_committee_id` at all — one still `PROPOSED`, or one whose scope was rejected — has no committee for the third condition to read, so that condition simply does not fire: a brand-new proposal is born with `consensus_gate` `OPEN`.

Recomputed alongside the gate, from the same walk, is the work item's `unresolved_negative_count`: the number of votes reachable through the work item's drafts' ballots that are cast, hold the `NEGATIVE` position, and whose `adjudication_status` is still `PENDING`. This gate is what makes "all negatives must be considered before advancement" observable rather than aspirational: a draft holding even one pending negative sits in `COMMENT_RESOLUTION`, which holds the gate shut no matter how favourable the ballot arithmetic was. The recomputation runs at the end of every ballot creation, ballot close, adjudication, appeal filing, appeal decision, membership edit and committee activation, and also at every scope decision, publication and periodic-review action. It does *not* run when a seat is appointed — that request recomputes the committee's balance bases only — nor when a comment is dispositioned or a public review is closed.

Cascades in this system are described in this document as numbered hops, and the numbering is meaningful: a hop's precondition is the state the previous hop just wrote, and all hops of a cascade complete inside the request that triggered the first one. There is no deferred or eventually-consistent settlement anywhere in this specification. Where a cascade suspends a committee, that suspension in turn gates the committee's work items and places a procedural hold on the committee's open ballots, all in the same request. Where a cascade advances a draft, the parent work item's dimension and gate are recomputed in the same request. Every row a cascade writes has its `version` advanced and its `updated_at` refreshed.

### 2.10. Two Conserved Quantities

The system maintains two counting invariants that must hold at every observable instant, and the tests that matter most for this specification are the ones that perform an action and then its compensating action and check that every counter returned to its earlier value.

The first conserved quantity is **voter seats**. For every ballot, `affirmative_count` plus `negative_count` plus `abstain_count` always equals `returned_count`, and `returned_count` plus `not_returned_count` always equals `eligible_voter_count`. Equivalently: the three position buckets plus `not_returned_count` sum to `eligible_voter_count`. The `eligible_voter_count` itself is frozen when the ballot is created and is never rewritten by any later request — not by a membership suspension, not by a withdrawal, not by a re-appointment. Casting a vote moves one seat out of `not_returned_count` into exactly one position bucket. Withdrawing that vote moves the seat back and removes it from its bucket, so after a cast followed by its withdrawal all four counters equal their pre-cast values exactly. Changing a position moves the seat between buckets without ever changing `returned_count`. Adjudication also rewrites positions and therefore moves seats between buckets, but must never change `returned_count` or `eligible_voter_count`.

The second conserved quantity is the **comment disposition ledger**. For every public review, `disposed_count` plus `unresolved_comment_count` always equals `comment_count`, and `comment_count` always equals the number of comment rows whose `public_review_id` is that review. Dispositioning a comment increments `disposed_count`, decrements `unresolved_comment_count`, and may bubble the review's status forward; reopening that comment decrements `disposed_count`, increments `unresolved_comment_count`, clears the recorded rationale, and reverses the bubble-up. After a disposition followed by a reopening, all three counters, the review's `status` and its `disposition_completeness_pct` equal their pre-disposition values exactly. `comment_count` is touched by neither direction — it moves only when a comment row is created.

### 2.11. Two Interval Disciplines

This domain uses two deliberately different interval conventions, and conflating them is the most common source of off-by-one behaviour.

A **ballot window** is a half-open interval running from `opens_at` inclusive to `closes_at` exclusive. Two ballot windows overlap when each one's start is strictly before the other's end; adjacency is therefore explicitly permitted, and a ballot opening at exactly the instant another closes does not overlap it. Overlap alone is not fatal: a committee may run several overlapping ballots at once, up to a per-committee cap. A vote is admissible when the clock is at or after `opens_at` and strictly before `closes_at`; a vote at exactly `closes_at` is refused.

A **public review window** is a closed inclusive interval running from `start_date` through `end_date`, both days counted, and its `duration_days` is therefore the whole-day difference between the two dates plus one. Public review windows carry a symmetric buffer that widens each occupied interval on both sides before collision is tested, adjacency is *forbidden* rather than permitted, and the capacity is exactly one: a single collision is fatal, because a work item may never have two live public review periods.

## 3. Business Logic & Workflows

### 3.1. The Participant Registry and the Formation of a Technical Committee

Nothing in this system happens without participants, and only the secretariat may create them. Registering a participant records their `full_name` (a non-blank string of 1 to 120 characters), their `organization` (a non-blank string of 1 to 160 characters, free text naming the employer or represented body), their `interest_category` — one of `PRODUCER`, `USER`, `GENERAL_INTEREST`, `REGULATORY` or `ACADEMIC` — and optionally their `employer_affiliation_code`, a group code of 1 to 32 characters that defaults to null when omitted. The affiliation code exists to stop a single employer from packing an interest category through multiple people, and the interest category is what the balance arithmetic in §2.6 counts.

A technical committee is created by the secretariat with a `designation` such as TC-14 (a non-blank string of 1 to 32 characters), a `scope_text` statement of 1 to 600 non-blank characters, a `chair_participant_id` naming the presiding chair, and optionally `max_concurrent_ballots`, an integer of at least 1 that defaults to 2 and caps how many of the committee's ballot windows may overlap. A new committee is born in `status` `FORMING`. Balance is computed immediately on its empty roster, which means a brand-new committee reports `balance_status` `UNBALANCED`, `roster_balance_status` `UNBALANCED`, `dominance_pct` and `roster_dominance_pct` 0.0, `active_member_count`, `roster_member_count` and `distinct_category_count` 0, an empty `category_counts` map and an `open_ballot_count` of 0 before anyone is appointed to it.

Appointing a seat is likewise a secretariat action and is addressed through the committee that will hold the seat, so the committee identifier comes from the path and becomes the membership's `committee_id`. The body names the `participant_id` being appointed and may carry `voting_rights`, which defaults to true; a seat created with `voting_rights` false is an **observer** — it is excluded from every ballot's eligible set and from both balance bases. At the moment of appointment the server snapshots the participant's `interest_category` and `employer_affiliation_code` onto the membership, records `appointed_at` from the logical clock, sets `missed_ballot_streak` to 0, and puts the seat in `status` `ACTIVE`. Those snapshots never track later edits to the participant. Two constraints guard the roster: if the participant already holds a seat on this committee in `status` `ACTIVE` or `SUSPENDED`, the appointment is refused with `ERR_DUPLICATE_MEMBERSHIP` — a `WITHDRAWN` seat, by contrast, may be re-appointed; and if the participant carries a non-null `employer_affiliation_code` that some other `ACTIVE` or `SUSPENDED` seat on this same committee already carries, the appointment is refused with `ERR_AFFILIATION_ALREADY_REPRESENTED`, because one employer gets one seat. Those two are the whole of the guard: the appointment imposes no condition on the committee's own `status`, so a seat may be added to a `FORMING`, an `ACTIVE` or a `SUSPENDED` committee alike, and a participant whose `employer_affiliation_code` is null is never caught by the affiliation rule however many other unaffiliated seats the committee already holds. Both bases of the balance arithmetic are recomputed on the parent committee as part of the appointment.

Activation is the moment a committee becomes able to do work, and the secretariat drives it. A committee moves from `FORMING` to `ACTIVE`, or from `SUSPENDED` back to `ACTIVE`, only when three things hold in this order: the committee is currently in `FORMING` or `SUSPENDED` — activating a committee that is already `ACTIVE` is *not* idempotent and is refused with `ERR_INVALID_COMMITTEE_STATE`; the participant named as `chair_participant_id` holds a seat on this very committee whose `status` is `ACTIVE` and whose `voting_rights` is true, failing which the request is refused with `ERR_CHAIR_NOT_MEMBER`; and the freshly recomputed voting-basis verdict is `BALANCED`, failing which the request is refused with `ERR_COMMITTEE_NOT_BALANCED`. Both balance bases are recomputed and persisted before that verdict is read, so `balance_status`, `roster_balance_status`, `dominance_pct`, `roster_dominance_pct`, `distinct_category_count`, `category_counts`, `active_member_count` and `roster_member_count` are all current when activation succeeds. A successful activation also re-derives the procedural gate of every work item this committee sponsors, and — when the committee was coming back from `SUSPENDED` — releases the procedural hold on its ballots, resetting every `hold_reason` of `COMMITTEE_UNBALANCED` back to `NONE`. Re-activation is a loop the committee may traverse any number of times: a committee can be suspended and restored repeatedly over its life.

Seats are edited, never deleted. The secretariat may move a seat's `status` from `ACTIVE` to `SUSPENDED`, from `SUSPENDED` back to `ACTIVE`, or from either `ACTIVE` or `SUSPENDED` to `WITHDRAWN`, which is terminal and cannot be restored. Those four are the only status edges the endpoint admits: any other move between two different statuses — a restoration out of `WITHDRAWN` above all — is refused with `ERR_INVALID_REQUEST` (HTTP 400), and nothing at all of the request is applied, not even an accompanying `voting_rights` flip. The same operation may also flip `voting_rights` to re-enfranchise or disenfranchise a seat, and that flip stays available even on a `WITHDRAWN` seat, which is excluded from both balance bases either way. Restoring a suspended seat to `ACTIVE` also resets its `missed_ballot_streak` to 0. Every one of these edits recomputes both balance bases on the parent committee and re-derives the gate on every work item the committee sponsors, and every one of them leaves already-created ballots' `eligible_voter_count` untouched. An edit counts as an edit only when it changes something: a request that restates the `status` and `voting_rights` the seat already holds advances no `version`, refreshes no `updated_at` and runs no cascade at all, and neither field is required, so a body naming neither of them is that same lawful no-op rather than a malformed request, and the committee's own `version` advances only where the recomputation actually wrote a different balance value or moved the committee's `status`. A withdrawal decrements `active_member_count` and rebuilds `category_counts`, but votes the departing seat had already cast on open ballots remain cast and keep counting — a withdrawal never rewrites a ballot already returned.

When a seat change drops the voting-basis verdict below `BALANCED`, a four-hop cascade runs inside the same request. Hop one recomputes the committee's counters. Hop two moves the committee from `ACTIVE` to `SUSPENDED`. Hop three, because the committee is now suspended, re-derives the procedural gate of every work item whose sponsoring committee is this one — the whole sponsored set, whatever each work item's `progress_status`, so a `PUBLISHED` or `REAFFIRMED` standard of this committee is gated `BLOCKED` alongside the ones still in development — setting each to `BLOCKED`. Hop four, because those work items are now gated, sets `hold_reason` to `COMMITTEE_UNBALANCED` on every ballot of this committee whose `status` is `OPEN` — and a ballot bearing a hold cannot be closed. That stamp overwrites whatever hold the ballot already carried, an `APPEAL_PENDING` hold included; because the denial of an appeal releases only the holds still reading `APPEAL_PENDING`, an overwritten hold outlives the appeal that placed it and is cleared only by the committee's re-activation. Hops one and three in fact run on *every* edit of an existing seat, whatever the resulting verdict, which is how a recomputation that leaves the committee balanced still refreshes the sponsored work items' gates; the appointment of a *new* seat is not such an edit and runs hop one alone — it re-derives no work item's gate and never suspends the committee, even where the seat it adds is what drops the voting-basis verdict below `BALANCED`. Hops two and four fire only on the drop, and only where the committee was `ACTIVE` at the time — a committee already `SUSPENDED` takes no second suspension and stamps no fresh holds. The reverse trip is the activation described above.

### 3.2. Proposing Work and Developing Draft Revisions

A work item proposal may be submitted by any participant acting as a `Proposer`, `CommitteeMember` or `CommitteeChair`, and it carries the proposed `title` (1 to 200 non-blank characters), the proposed `scope_text` (1 to 1200 non-blank characters), the `work_item_type` — one of `NEW_STANDARD`, `REVISION` or `AMENDMENT` — the `proposer_participant_id`, which must equal the caller's own identifier, and a `target_completion_date` expressed as an ISO 8601 calendar date in year-month-day form. A new proposal is born with `progress_status` `PROPOSED` and `ip_status` `IP_PENDING`; its `sponsoring_committee_id` and `designation` are both null, as are `scope_approved_at`, `edition`, `published_at`, `periodic_review_due_date` and `last_periodic_action_at`, and its `errata_count`, `interpretation_count` and `unresolved_negative_count` all start at 0.

Each work item carries **two independent state dimensions**. `progress_status` tracks development and runs over `PROPOSED`, `SCOPE_APPROVED`, `SCOPE_REJECTED`, `IN_DEVELOPMENT`, `CONSENSUS_APPROVED`, `PUBLISHED`, `UNDER_PERIODIC_REVIEW`, `REAFFIRMED`, `WITHDRAWN` and `SUSPENDED`, with `SCOPE_REJECTED` and `WITHDRAWN` terminal. `ip_status` tracks intellectual property and runs over `IP_PENDING`, `IP_DISCLOSED`, `IP_BLOCKED` and `IP_CLEARED`. The two evolve independently — a work item can sit in `IP_BLOCKED` while its development dimension advances all the way to `CONSENSUS_APPROVED` — and publication is the single point at which both dimensions are read together.

The secretariat decides a scope proposal by supplying a `decision` of either APPROVE or REJECT, and only while the work item is still `PROPOSED`: any other `progress_status` — a second decision on an already-decided work item included — is refused with `ERR_INVALID_WORK_ITEM_STATE`, ahead of the committee-status check below. An approval requires `sponsoring_committee_id` and a `designation` of 1 to 32 non-blank characters, and it is refused with `ERR_COMMITTEE_NOT_ACTIVE` when the nominated committee's `status` is not `ACTIVE`. On approval the server persists the sponsoring committee and the standard's `designation`, writes `scope_approved_at` from the logical clock, sets `edition` to 1, and advances `progress_status` from `PROPOSED` through `SCOPE_APPROVED` and onward to `IN_DEVELOPMENT` within that same request — the step out of `SCOPE_APPROVED` is a system step, not a second call, and draft creation is thereafter permitted because it requires `IN_DEVELOPMENT` — attempted against a work item in any other `progress_status` it is refused with `ERR_INVALID_WORK_ITEM_STATE`. A rejection requires a `rationale` of 1 to 2000 non-blank characters, moves `progress_status` to the terminal `SCOPE_REJECTED`, and leaves both `sponsoring_committee_id` and `designation` null; on a rejection those two fields remain optional, and one supplied anyway is still shape-checked and still resolved against storage — an unknown `sponsoring_committee_id` is `ERR_COMMITTEE_NOT_FOUND` even on a rejection — but neither value is persisted. Either way the work item's `version` advances by 1, and the procedural gate is re-derived — so a work item whose sponsoring committee is not currently active and balanced starts life gated `BLOCKED`.

Draft revisions are created by a caller acting as `CommitteeChair` — the role alone admits the caller, and the server does not check that the caller is in fact the `chair_participant_id` of the sponsoring committee — or by the secretariat, addressed through the work item they belong to, so the work item identifier arrives from the path and becomes the draft's `work_item_id`. The body carries `total_clause_count` (an integer of at least 1), optionally `changed_clause_count` (an integer that defaults to 0, may not be negative and may not exceed `total_clause_count`), optionally `prior_draft_id` naming the revision this one supersedes, and optionally a `summary` written by the editor. A draft with no `prior_draft_id` is revision 1 and its `revision_number` is 1; a draft that supersedes another carries a `revision_number` one greater than its predecessor's. At creation the server computes `substantive_change_ratio` as `changed_clause_count` divided by `total_clause_count`, rounded half up to four decimal places, taking the value 0.0000 when `total_clause_count` is zero. A new draft opens in `status` `DRAFTING`, with `unresolved_negative_count` and `ballot_round_count` at 0 — the latter being simply how many ballot rows have ever been created against this revision, counting any that were later `VACATED`, and refreshed only when a ballot is opened on the draft — and with `recirculation_required` false.

Superseding a predecessor is where the "consider every negative" principle first bites. A predecessor may be superseded only from `DRAFTING`, `COMMENT_RESOLUTION` or `PUBLIC_REVIEW_CLOSED`; any other status, and `ABANDONED` in particular, is refused with `ERR_INVALID_DRAFT_STATE`. From `COMMENT_RESOLUTION` or from `PUBLIC_REVIEW_CLOSED`, the predecessor may be superseded only when no vote on any of its ballots still has `adjudication_status` `PENDING`; a draft holding unconsidered negatives cannot be quietly replaced, and the attempt is refused with `ERR_NEGATIVES_NOT_CONSIDERED`. When the supersession succeeds, the predecessor moves to the terminal `ABANDONED`, its `recirculation_required` is cleared to false, and its `carryover_unresolved_negative_count` is copied forward onto the successor. Creating a draft, with or without a predecessor, advances the parent work item's `version` but does *not* re-derive its `consensus_gate` or its `unresolved_negative_count`: both keep whatever an earlier request left them holding until the next request that does re-derive them, so abandoning a predecessor that was sitting in `COMMENT_RESOLUTION` does not by itself reopen the gate. Nor is a predecessor required to belong to the same work item as its successor — `prior_draft_id` is resolved and status-checked, never cross-checked against the path's work item. Where the predecessor was in `PUBLIC_REVIEW_CLOSED`, every public review already recorded against it keeps its own status and continues to occupy the work item's review calendar — a draft may be revised after its public review has closed, but the closed review still counts as an occupant when the next review window is tested.

That carried-forward figure, `carryover_unresolved_negative_count`, is a penalty ledger. It is written when an upheld appeal reaches a draft — whether by vacating the cited ballot or by remanding to the committee — taking the value of every negative that had been cast on the cited ballot. Any value greater than zero raises the approval bar of the draft's next ballot, as §3.5 describes. It is reset to 0 only when a successor draft is created without a carryover to inherit.

### 3.3. Opening a Ballot: the Effective Kind, the Eligible Set and the Window

Only a committee chair opens a ballot, and only on their own committee: the caller's identifier must equal the `chair_participant_id` of the committee named in the request, or the request is refused with `ERR_NOT_COMMITTEE_CHAIR`. The request names the `draft_id` being balloted, the `committee_id` that will run it — which is the `sponsoring_committee_id` of that draft's work item — the `ballot_kind` the chair intends, the `opens_at` instant at which voting becomes admissible and the `closes_at` instant at which it ceases, and optionally a `predecessor_ballot_id` naming the ballot this one re-runs. A first-round ballot leaves `predecessor_ballot_id` null.

The chair's `ballot_kind` is a request, not a verdict. It may be `SUBCOMMITTEE`, `CONSENSUS_BODY`, `RECIRCULATION` or `REAFFIRMATION`, and it is the draft's own `status` — not the kind submitted — that decides both admissibility and the transition the draft takes: a draft in `DRAFTING` is admitted and transitions to `SUBCOMMITTEE_BALLOT`; a draft in `PUBLIC_REVIEW_CLOSED` is admitted and transitions to `CONSENSUS_BALLOT`; and a draft in `APPROVED` is admitted only where the submitted `ballot_kind` is `REAFFIRMATION`, staying in `APPROVED` through a self-loop, which is the only way a published standard can ever be re-confirmed. Any other draft status — and `ABANDONED` under all circumstances — is refused with `ERR_INVALID_DRAFT_STATE`. Apart from that one restriction on `APPROVED`, the expected pairing of kind to draft status is a convention the server does not police: a `CONSENSUS_BODY` ballot submitted on a `DRAFTING` draft is accepted and the draft still moves to `SUBCOMMITTEE_BALLOT`, and a `SUBCOMMITTEE` ballot submitted on a `PUBLIC_REVIEW_CLOSED` draft is accepted and the draft still moves to `CONSENSUS_BALLOT`. A reaffirmation ballot additionally requires the parent work item's `progress_status` to be `UNDER_PERIODIC_REVIEW`, failing which the response is `ERR_INVALID_WORK_ITEM_STATE`. After those two status checks rather than before them, the sponsoring committee must be `ACTIVE` (else `ERR_COMMITTEE_NOT_ACTIVE`) and, further down the ladder, its voting-basis `balance_status` must be `BALANCED` (else `ERR_COMMITTEE_NOT_BALANCED`). A ballot opened on a draft in `PUBLIC_REVIEW_CLOSED` — whatever kind was submitted, since the gate keys off the draft's status and not off the requested or effective kind — carries one further gate: the most recently created public review on that draft must have reached `DISPOSITION_APPROVED`, or the request is refused with `ERR_PUBLIC_REVIEW_NOT_APPROVED` — the consensus body may not vote on a text whose public comments have not been formally disposed of.

What the ballot will actually be judged as is recorded in `effective_ballot_kind`, and every threshold in this system reads that field rather than the submitted `ballot_kind`. It is derived in a strict order, and the order is normative because each step feeds the next: the eligible voter set depends on the effective kind, the effective kind depends on the draft's change ratio, and the change ratio is a property of the draft the ballot is being opened on. Evaluating the eligible set before the kind, or the kind before the ratio, produces a different `eligible_voter_count` and therefore a different quorum verdict weeks later.

**Step one** is the ratio, already computed when the draft was created: `changed_clause_count` divided by `total_clause_count`, rounded half up to four decimal places. **Step two** selects the effective kind by the first matching condition. If the draft has no `prior_draft_id`, the effective kind is exactly the submitted `ballot_kind`. Otherwise, if the draft's `substantive_change_ratio` is greater than or equal to 0.1000, the effective kind is forced to `RECIRCULATION`, overriding whatever the chair submitted. Otherwise, if the draft's `recirculation_required` flag is true — which a persuasive negative sets, as §3.5 explains — the effective kind is likewise forced to `RECIRCULATION`. Otherwise, the submitted kind is discarded in favour of the predecessor ballot's own `effective_ballot_kind`, so an editorial revision is re-balloted under exactly the rules that applied to the draft it replaces. The predecessor ballot for this purpose is the most recently created ballot on the predecessor draft whose `status` is `EVALUATED` or `VACATED`, taking them in descending order of creation. When the predecessor draft carries no such ballot, the ballot named by the request's own `predecessor_ballot_id` stands in for it — whatever that ballot's own status — and when the request named none either there is no predecessor kind to inherit, so the submitted `ballot_kind` stands after all. To make the boundary concrete: on a revision with 40 clauses in total, 4 changed clauses gives a ratio of exactly 0.1000 and forces recirculation, while 3 changed clauses gives 0.0750 and inherits the predecessor's kind.

**Step three** freezes the eligible voter set. For any effective kind other than `RECIRCULATION`, the eligible set is every seat on the committee whose `status` is `ACTIVE` and whose `voting_rights` is true — the full active voting roster. For a recirculation, the eligible set is narrower and is the union of two groups: every seat that holds a cast vote on the predecessor ballot, plus every seat that is currently `ACTIVE` with `voting_rights` true and whose `appointed_at` is later than the predecessor ballot's `closes_at`. A seat enters the first group on the strength of its cast vote alone, whatever its `status` and `voting_rights` happen to be now, so a seat since suspended or withdrawn is still re-polled; the `appointed_at` comparison is strict, so a seat appointed at exactly the predecessor's `closes_at` is not added. Where no predecessor ballot could be resolved at all, there is nothing to narrow against and the recirculation set falls back to the full active voting roster. A member who let the previous ballot lapse is deliberately not re-polled; a member appointed after the previous ballot closed never had a chance to vote and is therefore added. The size of that set is written to `eligible_voter_count` and is frozen for the life of the ballot, together with the identities of the seats in it — which is the set the attendance sweep of §3.5 later walks. **Step four** is simply the consequence: because thresholds read the effective kind, a forced recirculation raises the approval bar to 75.0 percent while leaving the return-rate bar at 66.7 percent.

The window is validated against the effective kind, and therefore only after the effective kind has been derived. The span from `opens_at` to `closes_at` must be at least 14 days for a subcommittee or recirculation ballot and at least 30 days for a consensus-body or reaffirmation ballot, and `opens_at` must be strictly earlier than `closes_at`; the boundary is inclusive, so a span of exactly the minimum passes. The span is the exact elapsed interval between the two instants expressed in days with its fraction retained, not truncated to whole days, so a window of 14 days and one hour also clears a 14-day minimum while one of 13 days and 23 hours does not. Both failures — a span below the minimum and an `opens_at` at or after `closes_at` — are reported as `ERR_BALLOT_WINDOW_TOO_SHORT`. A window from `2026-08-01T00:00:00Z` to `2026-08-15T00:00:00Z` is 14 days and is acceptable for a subcommittee ballot, while a window ending `2026-08-14T00:00:00Z` is 13 days and is refused with `ERR_BALLOT_WINDOW_TOO_SHORT`.

Capacity is measured over the committee, not the draft. The occupants of the candidate window are the ballot rows on this same committee whose `status` is `OPEN` or `CLOSED` and whose half-open window overlaps the candidate's — two windows overlapping exactly when each one's start is strictly earlier than the other's end, so a ballot opening at the instant another closes is not an occupant. Evaluated ballots and vacated ballots free their slot. If the number of occupants is already equal to or greater than the committee's `max_concurrent_ballots`, the request is refused with `ERR_BALLOT_CAPACITY_EXCEEDED`. Ballots on other committees never contend, even when they target drafts of the same work item. A successful creation refreshes the committee's `open_ballot_count` to the number of its ballots in `status` `OPEN` or `CLOSED`; because a close evaluates in the same request, no ballot is ever externally observable as `CLOSED`, so that figure is in practice the count of open ballots. A ballot close refreshes the same figure; but where a creation also advances the committee's `version`, a close leaves the committee's `version` alone unless the attendance sweep of §3.5 independently changed the committee's balance fields or its `status`.

The new ballot is created in `status` `OPEN` with `hold_reason` `NONE`, `closed_at` null, `consensus_result` `PENDING`, `affirmative_count`, `negative_count`, `abstain_count` and `returned_count` at 0, `not_returned_count` equal to `eligible_voter_count`, `return_rate_pct` 0.0, `pending_negative_count` 0, and both `provisional_approval_pct` and `final_approval_pct` null. Its `opens_at` and `closes_at` are stored and echoed back exactly as the client supplied them rather than renormalised to the three-fractional-digit form of §2.4, while the window arithmetic itself works on the parsed instants. Its `required_return_rate_pct` and `required_approval_pct` are seeded at creation from the effective kind and the carryover escalation described in §3.5, so a chair can see the bar before the first vote arrives. The parent draft takes its transition, the parent work item's procedural gate is re-derived, and the draft, the committee and the work item each have their `version` advanced by 1.

### 3.4. Casting, Changing and Withdrawing a Vote

A vote is cast against an open ballot by a participant acting as a `CommitteeMember` or a `CommitteeChair`. The request identifies the ballot in the path and carries the `membership_id` of the seat casting the vote, the `position` — one of `AFFIRMATIVE`, `NEGATIVE` or `ABSTAIN` — and, when the position is `NEGATIVE`, a `comment_text` explaining the objection, optionally accompanied by a `clause_reference` naming the clause at issue. The seat named by `membership_id` must belong to the calling participant, or the request is refused with `ERR_ACTOR_IDENTITY_MISMATCH`.

Four conditions govern admissibility, and §2.5 fixes the order in which they are reported. The ballot's `status` must be `OPEN`, else `ERR_BALLOT_NOT_OPEN`. The acting seat must not already hold a vote on this ballot whose `status` is `CAST`, else `ERR_DUPLICATE_VOTE` — a vote previously withdrawn does not block a fresh cast, so a member who retracted may vote again. The acting seat must be eligible: its `status` must be `ACTIVE` with `voting_rights` true on the ballot's committee, and when the ballot's `effective_ballot_kind` is `RECIRCULATION` the seat must additionally fall inside the narrowed recirculation eligible set described in §3.3; otherwise the response is `ERR_VOTER_NOT_ELIGIBLE`. And the logical clock must lie inside the half-open voting window — at or after `opens_at` and strictly before `closes_at` — else `ERR_BALLOT_NOT_IN_VOTING_WINDOW`; a vote arriving at exactly `closes_at` is too late.

An unexplained negative is not admissible. A vote cast with `position` `NEGATIVE` must supply a non-empty `comment_text`, or the request is rejected with `ERR_NEGATIVE_REQUIRES_COMMENT` (HTTP 400). When it does, the server itself creates the objection on file as a comment against the ballot's draft: that comment's `source_type` is `BALLOT_NEGATIVE`, its `source_vote_id` points back at the vote, its `ballot_id` names the ballot, its `draft_id` is the ballot's own draft, its `submitter_participant_id` is the objecting caller, its `comment_type` is `TECHNICAL` and its `is_substantive` therefore true, its `comment_text` and `clause_reference` are the ones carried on the vote, it opens in `status` `OPEN` with a null `disposition_rationale`, and its `public_review_id` is null — which is precisely why a ballot objection never enters any public review's disposition ledger. Clients may never post a comment with `source_type` `BALLOT_NEGATIVE` themselves; that value is reserved for the server, and supplying it is `ERR_INVALID_REQUEST`.

The accepted vote is stored with `status` `CAST`, `adjudication_status` `NOT_APPLICABLE`, `cast_at` taken from the logical clock, `position_change_count` at 0, and `adjudicated_by_participant_id` and `adjudication_rationale` both null. Casting moves one seat out of `not_returned_count` into exactly one position bucket, the ballot's tallies are recomputed, the seat's `missed_ballot_streak` is reset to 0, and the ballot's `version` advances. The seat's own `version` advances too, unconditionally — the reset is written whether or not the streak already stood at 0 — while the draft, the work item and its `consensus_gate` are left entirely alone by a cast vote.

A voter may revise their own vote while the ballot's `status` is `OPEN`, else `ERR_BALLOT_NOT_OPEN`, and while the clock is inside the same half-open window, else `ERR_BALLOT_NOT_IN_VOTING_WINDOW` — and only their own: the caller's identifier must equal the `participant_id` of the seat behind the vote, else `ERR_NOT_VOTE_OWNER`. Supplying a different `position` takes the vote around a self-loop — it stays `CAST` — increments `position_change_count`, and moves the seat between position buckets without ever changing `returned_count`; a member may do this any number of times while the ballot is open. Changing a position to `NEGATIVE` again demands an explanation: either a comment is already linked to this vote or a non-empty `comment_text` accompanies the change, failing which the response is `ERR_NEGATIVE_REQUIRES_COMMENT`. Where that change goes through and no comment is yet linked to the vote, the server files the objection itself, exactly as it does on a fresh negative cast and reading the `comment_text` and `clause_reference` the vote now carries. The body of this request accepts only `position`, `status` and `comment_text` — a `clause_reference`, like any other field, is `ERR_INVALID_REQUEST` — and supplying only a `comment_text` that differs from the stored one, with no position change, rewrites the vote's own `comment_text` and nothing else: `position_change_count` does not move and the linked comment's text stays as it was first filed. A request that changes nothing at all, whether by restating the position the vote already holds or by naming `status` `CAST`, advances no `version`, refreshes no `updated_at` and leaves the ballot's tallies untouched, answering 200 with the vote unchanged.

Supplying `status` `WITHDRAWN` retracts the vote instead, moving the vote's return dimension from `CAST` to `WITHDRAWN`. A withdrawn vote contributes to nothing: it leaves every position bucket, its seat returns to `not_returned_count`, and the four seat counters return to exactly the values they held before the vote was cast. `WITHDRAWN` is terminal for the return dimension of a vote: a further revision of a vote already `WITHDRAWN` is refused with `ERR_INVALID_REQUEST` (400), and that refusal is deliberately evaluated *after* the ballot-open and voting-window checks, so a caller poking a withdrawn vote on a ballot that has since left its window learns about the window first. The comment behind a withdrawn negative is *not* deleted — it stays on file in `status` `OPEN` as the historical record of the objection, still carrying a null `public_review_id` and therefore still outside every disposition ledger. Both the vote's and the ballot's `version` advance by 1.

### 3.5. Closing a Ballot, Evaluating Consensus, and Considering Every Negative

Either a caller acting as `CommitteeChair` — the role alone admits the caller here, with no check that they are the `chair_participant_id` of the ballot's own committee — or the secretariat may close a ballot, and the close is where the arithmetic of consensus happens. Three preconditions apply: the ballot's `status` must be `OPEN`, else `ERR_BALLOT_NOT_OPEN`; the ballot's `hold_reason` must be `NONE`, since a ballot held because its committee fell out of balance or because an appeal is pending may not be closed, and the attempt is refused with `ERR_COMMITTEE_NOT_BALANCED`; and the ballot must have ended — the logical clock must be at or after `closes_at`, *or* `returned_count` must already equal `eligible_voter_count`, which lets a fully-returned ballot close early. Otherwise the response is `ERR_BALLOT_NOT_ENDED`.

The close runs a four-hop cascade inside a single request. **Hop one** freezes the tallies, records `closed_at` from the logical clock, and moves the ballot from `OPEN` to `CLOSED`; the system immediately follows with the step from `CLOSED` to `EVALUATED` in the same request, so `CLOSED` is never externally observable.

Evaluation itself proceeds in four steps and only ever counts votes whose `status` is `CAST`. First the tally: `affirmative_count`, `negative_count` and `abstain_count` are the numbers of cast votes holding each position, `returned_count` is their sum, and `not_returned_count` is `eligible_voter_count` less `returned_count`. Second the percentages: `return_rate_pct` is 0.0 when `eligible_voter_count` is zero and otherwise 100 multiplied by `returned_count`, divided by `eligible_voter_count`, rounded half up to one decimal place; the approval base is `affirmative_count` plus `negative_count`, with abstentions deliberately excluded, and the approval percentage is 0.0 when that base is zero and otherwise 100 multiplied by `affirmative_count`, divided by the base, rounded half up to one decimal place. Third the thresholds, selected by `effective_ballot_kind`: `required_return_rate_pct` is 50.0 percent for a subcommittee ballot and 66.7 percent for a consensus-body, recirculation or reaffirmation ballot, while the base approval bar is 50.1 percent for a subcommittee ballot, 66.7 percent for a consensus-body ballot, 75.0 percent for a recirculation and 66.7 percent for a reaffirmation. If the draft's `carryover_unresolved_negative_count` is greater than zero, the ballot is penalised: `required_approval_pct` becomes that base bar plus 5.0 percentage points, but never more than a ceiling of 90.0 percent — whichever of those two is smaller. With no carryover, `required_approval_pct` is simply the base bar.

Fourth, the verdict, written to `consensus_result`. The `pending_negative_count` is first computed as the number of cast negative votes whose `adjudication_status` is either `NOT_APPLICABLE` or `PENDING`. Then the **first** matching branch wins, and the order is normative: if `return_rate_pct` is below `required_return_rate_pct` the result is `FAILED_QUORUM`; otherwise if the approval percentage is below `required_approval_pct` the result is `FAILED_THRESHOLD`; otherwise if `pending_negative_count` is greater than zero the result is `APPROVED_PENDING_NEGATIVES`; otherwise the result is `APPROVED`. A quorum failure therefore masks a threshold failure: a ballot that misses both bars reports `FAILED_QUORUM` only.

Closing uses the **provisional** reading of the ballot: positions are taken exactly as cast, every cast negative counts toward `pending_negative_count`, so an otherwise-passing ballot lands on `APPROVED_PENDING_NEGATIVES` rather than `APPROVED`. The result of that reading is written to `provisional_approval_pct`, and `final_approval_pct` is left null.

**Hop two** moves every cast negative vote on the ballot from `adjudication_status` `NOT_APPLICABLE` to `PENDING`. **Hop three**, because those votes are now pending, recomputes the draft's `unresolved_negative_count` and moves the draft. Edge precedence here is strict and catches implementers out: **if the evaluated ballot leaves any pending negative, the draft goes to `COMMENT_RESOLUTION` regardless of `consensus_result`** — from `SUBCOMMITTEE_BALLOT` or from `CONSENSUS_BALLOT` alike. Only when zero negatives are pending do the other edges apply. A subcommittee ballot with `consensus_result` `APPROVED` and no pending negatives advances the draft from `SUBCOMMITTEE_BALLOT` to `PUBLIC_REVIEW_READY`. A subcommittee ballot resulting in `FAILED_QUORUM` or `FAILED_THRESHOLD` with no pending negatives returns the draft from `SUBCOMMITTEE_BALLOT` to `DRAFTING` — a failed ballot sends the text back for work with no adjudication step at all. A consensus ballot with `consensus_result` `APPROVED` and no pending negatives, on a draft whose most recent public review has reached `DISPOSITION_APPROVED`, moves the draft from `CONSENSUS_BALLOT` to `APPROVED`. A consensus ballot resulting in `FAILED_QUORUM` or `FAILED_THRESHOLD` returns the draft from `CONSENSUS_BALLOT` to `PUBLIC_REVIEW_CLOSED`, leaving it eligible for another consensus ballot without a second public review. A reaffirmation ballot is different again: the draft is sitting in `APPROVED`, no edge out of `APPROVED` is declared for a close, so hop three merely recomputes `unresolved_negative_count` and the draft stays `APPROVED`.

Alongside the cascade, the close enforces attendance. Every eligible seat — meaning every seat in the set frozen onto the ballot when it was created, read as it stands now — that returned no cast vote has its `missed_ballot_streak` incremented and its own `version` advanced, whether or not the increment goes on to suspend it; a seat whose streak reaches 2 is additionally suspended by the system, moving from `ACTIVE` to `SUSPENDED`, while a seat that is already `SUSPENDED` or `WITHDRAWN` takes the increment without any status change. That suspension recomputes both balance bases on the committee, and a drop below `BALANCED` drives the committee's own suspension and the gating cascade of §3.1; the recomputation and that cascade run once, and only where the sweep actually suspended at least one seat. Critically, this suspension is computed from the closing ballot's raw tallies and **never** alters that ballot's `eligible_voter_count`: seats suspended by the very close being processed do not shrink the denominator of the ballot being closed. The sweep runs after hop three and before hop four, and that ordering is observable: where the sweep suspends enough seats to unbalance and suspend the committee, the work item's gate is already `BLOCKED` by the time hop four reads it, so a consensus ballot that would otherwise have carried the work item to `CONSENSUS_APPROVED` in this same request does not — the advancement requires an `OPEN` gate, and the close itself has just shut it.

**Hop four** re-derives the parent work item's `consensus_gate` and `unresolved_negative_count`. Where the draft reached `APPROVED`, the work item moves from `IN_DEVELOPMENT` to `CONSENSUS_APPROVED`, which requires that the ballot's `consensus_result` be `APPROVED` with `pending_negative_count` zero, that the draft's latest public review be `DISPOSITION_APPROVED`, and that the work item's gate be `OPEN`. The order in which that advancement writes is itself specified: `progress_status` is written to `CONSENSUS_APPROVED` **first**, and only then is patent clearance re-evaluated — at which point the call for patents is closed, so the work item moves from `IP_PENDING` or from `IP_DISCLOSED` to `IP_CLEARED`, unless a blocking disclosure holds `ip_status` at `IP_BLOCKED`. The close advances the `version` of the ballot, of each affected vote, of the draft, of the work item and of every membership the attendance sweep touched, whether or not that seat was suspended.

Adjudication is how a pending negative is answered, and until every one has been answered the draft cannot advance. The target vote must have `adjudication_status` `PENDING` and `status` `CAST`, else `ERR_VOTE_NOT_ADJUDICABLE`; those two conditions are the whole of the test and the ballot's own `status` is never consulted, so a pending negative left behind on a ballot that has since been `VACATED` stays adjudicable, and the final reading described below re-reads and rewrites that vacated ballot's tallies, percentages and `consensus_result` exactly as it would any other — the preservation of a vacated ballot's figures in §3.8 is a property of the vacating act itself, not a permanent freeze. The request carries a `resolution` and a mandatory `adjudication_rationale`, and the server records the acting identifier as `adjudicated_by_participant_id`. Two of the three resolutions are the chair's call and one is the voter's. `PERSUASIVE` and `NON_PERSUASIVE` require that the caller's identifier equal the `chair_participant_id` of the committee sponsoring the draft's work item, else `ERR_NOT_COMMITTEE_CHAIR`, and further require that the caller not be the participant behind the vote's own seat: a chair who cast a negative may not rule on it, and the attempt is refused with `ERR_SELF_ADJUDICATION`. `WITHDRAWN_BY_VOTER` is the opposite — only the participant who cast the negative may choose it, and anyone else, the chair included, is refused with `ERR_NOT_VOTE_OWNER`.

Each resolution rewrites the vote differently, and each rewrite is what the **final** reading of the ballot then tallies. `PERSUASIVE` moves the vote's `adjudication_status` to `PERSUASIVE` and rewrites its `position` from `NEGATIVE` to `AFFIRMATIVE`, and sets the linked comment behind that vote to `ACCEPTED`. `NON_PERSUASIVE` moves `adjudication_status` to `NON_PERSUASIVE`, leaves `position` at `NEGATIVE`, and sets the linked comment to `REJECTED`; on this path `final_approval_pct` comes out equal to `provisional_approval_pct`. `WITHDRAWN_BY_VOTER` moves `adjudication_status` to `WITHDRAWN_BY_VOTER` and rewrites `position` from `NEGATIVE` to `ABSTAIN`, so the objection leaves the approval base entirely. All three are terminal for the adjudication dimension.

The final reading re-runs the same four evaluation steps over the rewritten positions, writes the outcome to `final_approval_pct`, and preserves `provisional_approval_pct` untouched as the historical record of what the ballot looked like as cast. It also refreshes `pending_negative_count` and `consensus_result` — and `consensus_result` moves from `APPROVED_PENDING_NEGATIVES` to `APPROVED` only when the refreshed tally still clears `required_approval_pct`. Because the re-run is the whole four-step verdict rather than a patch, it also re-seeds `required_return_rate_pct` and `required_approval_pct` from the effective kind and the draft's carryover as they then stand, and a ballot that closed `FAILED_THRESHOLD` may be lifted out of that result: rewriting a negative into an affirmative or an abstention can only raise the approval percentage, never lower it, so no ballot ever moves backwards through the verdict ladder. `return_rate_pct` is never touched by an adjudication, because adjudication moves no seat in or out of `returned_count`, so a `FAILED_QUORUM` ballot can never be rescued. Consider a three-seat consensus-body ballot with two affirmatives and one negative: at close, `provisional_approval_pct` is 66.7 and `consensus_result` is `APPROVED_PENDING_NEGATIVES`. Ruling that negative `PERSUASIVE` gives `final_approval_pct` 100.0 and `consensus_result` `APPROVED`; ruling it `NON_PERSUASIVE` gives `final_approval_pct` 66.7 instead.

When an adjudication clears the **last** pending negative, the draft ordinarily leaves `COMMENT_RESOLUTION`, and which edge it takes depends on what happened during resolution. It returns to `DRAFTING` when at least one vote on the draft's ballots was ruled `PERSUASIVE`, or when the draft's most recently evaluated ballot — the most recently created ballot on the draft whose `status` is `EVALUATED` — carries a `consensus_result` of `FAILED_QUORUM` or `FAILED_THRESHOLD` **as the final reading just refreshed it**, not as it stood at close; on that edge, `recirculation_required` is set to true only when the edge was taken because of a persuasive ruling, and is left exactly as it was when the edge was taken because the ballot had failed its quorum or threshold. It moves to `PUBLIC_REVIEW_READY` when no vote on the draft was ruled `PERSUASIVE`, the refreshed `consensus_result` of the most recently evaluated ballot is `APPROVED` or `APPROVED_PENDING_NEGATIVES`, and no public review on this draft has yet reached `DISPOSITION_APPROVED` — the next step is to announce one. And it moves straight to `APPROVED` when no vote was ruled `PERSUASIVE`, the draft's latest public review is already `DISPOSITION_APPROVED`, and the refreshed `consensus_result` is `APPROVED`; on that edge the parent work item takes its step from `IN_DEVELOPMENT` to `CONSENSUS_APPROVED`. Those three edges are exhaustive rather than merely illustrative, and none of them fires where the draft carries no ballot in `status` `EVALUATED` at all — the ballot that was evaluated having since been vacated, so that there is no refreshed `consensus_result` to read: the persuasive-ruling edge is then the only one available, and a draft on which nothing was ruled `PERSUASIVE` keeps `COMMENT_RESOLUTION` and keeps the work item's gate shut. This last edge is what makes "mandatory consideration of all negatives before advancement" observable on the consensus body: the draft cannot reach `APPROVED` while a negative is pending, only afterwards, and only if the refreshed tally still clears the bar. Whichever edge is taken, the work item's gate is re-derived — returning to `OPEN` once no draft of the work item sits in `COMMENT_RESOLUTION` and nothing else blocks it — and the vote, the ballot, the draft and the work item each have their `version` advanced by 1, joined by the linked comment on the two rulings that rewrite it: `WITHDRAWN_BY_VOTER` leaves that comment in `OPEN` and does not advance it at all. Those advances happen on **every** adjudication, not only on the one that clears the last pending negative — an adjudication that leaves other negatives still pending moves no draft, but still advances the draft's and the work item's `version` alongside the vote's and the ballot's. A persuasive negative therefore forces a substantive revision and the draft re-enters development, which is exactly the loop the change-ratio rule of §3.3 then re-prices.

### 3.6. Public Review and the Comment Disposition Record

A public review is announced by the secretariat against a specific draft, naming the `draft_id`, the inclusive `start_date` and `end_date` of the review period as ISO 8601 calendar dates, and the `expected_draft_version` required by §2.7. The draft must be in `PUBLIC_REVIEW_READY`, or else in `PUBLIC_REVIEW` provided every review already recorded against it is in `SCHEDULED` or `CANCELLED` — that second case is the supersession path, where a replacement announcement takes over from one that has not yet started. Any other draft status is `ERR_INVALID_DRAFT_STATE`.

The review period must be long enough. Its `duration_days` is the whole-day difference from `start_date` to `end_date` plus one, counting both endpoints, and it must be at least 45 days; `start_date` may not fall after `end_date`, and that inversion draws the same `ERR_REVIEW_PERIOD_TOO_SHORT` (409) rather than being treated as a malformed body. A window from 2026-08-01 to 2026-09-14 is 45 days inclusive and is accepted, while the same window ending 2026-09-13 is 44 days and is refused with `ERR_REVIEW_PERIOD_TOO_SHORT`.

The period must also stand clear of every other review the work item has already run, on any of its draft revisions. The occupants of the calendar are the public reviews reachable from the candidate draft's work item through every one of its drafts whose `status` is `OPEN`, `CLOSED`, `DISPOSITION_DRAFTED` or `DISPOSITION_APPROVED`. Each occupant is widened by 15 days on both sides before collision is tested: the candidate collides with an occupant when the candidate's `start_date` is on or before the occupant's `end_date` advanced by 15 days **and** the occupant's `start_date` is on or before the candidate's `end_date` advanced by 15 days. A single collision is fatal and is refused with `ERR_REVIEW_WINDOW_BUFFER_CONFLICT`, because a work item may never carry two live review periods. Concretely, an existing review ending 2026-09-14 pushes its buffered edge out to 2026-09-29, so a candidate beginning 2026-09-29 collides while one beginning 2026-09-30 does not. Reviews in `SCHEDULED` are deliberately *not* occupants — they are superseded rather than avoided.

On success, any still-`SCHEDULED` review on the same draft is moved to the terminal `CANCELLED`, keeping its own `comment_count` as the historical record, and the draft advances from `PUBLIC_REVIEW_READY` to `PUBLIC_REVIEW` or takes the `PUBLIC_REVIEW` self-loop, with the draft's `version` advancing either way. The new review records `announced_at` from the logical clock, leaves `closed_at`, `disposition_approved_by_participant_id` and `disposition_approved_at` null, and starts with `comment_count`, `disposed_count` and `unresolved_comment_count` at 0 and `disposition_completeness_pct` at 100.0. Its `status` is `OPEN` when `start_date` is on or before the logical clock's current date, and `SCHEDULED` otherwise. A review left `SCHEDULED` is promoted to `OPEN` when the logical clock is later moved to an instant at or after its `start_date`, and the identifiers of every review promoted that way are reported back in `promoted_public_review_ids`, each promoted review's `version` advancing by 1.

Comments arrive from two quite different directions and the `source_type` field distinguishes them. A member of the public — or any participant acting as `PublicCommenter`, `CommitteeMember`, `CommitteeChair` or `Proposer` — submits a comment carrying `source_type`, `comment_type`, a `comment_text` body of 1 to 2000 non-blank characters, the `submitter_participant_id` (which must equal the caller's own identifier), and a `clause_reference` of 1 to 40 non-blank characters naming the clause addressed. `source_type` `PUBLIC_REVIEW` requires a `public_review_id` and a review whose `status` is `OPEN`; `source_type` `COMMITTEE` requires a `draft_id` instead and attaches the comment directly to the revision. Each of the two leaves the *other* identifier optional rather than forbidden: one supplied anyway is still resolved against storage — an unknown `draft_id` is `ERR_DRAFT_NOT_FOUND` even on a `PUBLIC_REVIEW` comment, and the `draft_id` is resolved before the `public_review_id` and both before the `submitter_participant_id` — and is then ignored, so a `PUBLIC_REVIEW` comment always records the review's own `draft_id` and a `COMMITTEE` comment always records a null `public_review_id` and therefore never joins any disposition ledger. `source_type` `BALLOT_NEGATIVE` is reserved for the server's own record of a negative vote and is rejected as client input with `ERR_INVALID_REQUEST`. The `comment_type` is `GENERAL`, `TECHNICAL` or `EDITORIAL`, and the server derives `is_substantive` from it: general and technical comments are substantive, editorial comments are not. A new comment opens in `status` `OPEN` with `disposition_rationale` null, and, when it belongs to a public review, the review's counters are recomputed on the spot.

Closing a review is the secretariat's act, and it may not be premature: the review's `status` must be `OPEN`, else `ERR_INVALID_PUBLIC_REVIEW_STATE`, and the logical clock must be **strictly after** the review's `end_date`, since the last day of an inclusive window must be fully elapsed; otherwise the response is `ERR_REVIEW_NOT_ENDED`. The close records `closed_at`, freezes `comment_count`, recomputes the disposition counters, moves the review from `OPEN` to `CLOSED`, and moves the parent draft from `PUBLIC_REVIEW` to `PUBLIC_REVIEW_CLOSED`, advancing both `version` values. Closing recomputes the counters but does not itself apply the bubble edge of the disposition record: a review whose every comment had already been dispositioned while it was still `OPEN` — which nothing forbids — closes to `CLOSED` carrying `disposition_completeness_pct` 100.0 and an `unresolved_comment_count` of 0, and it waits there until some later disposition action moves it on to `DISPOSITION_DRAFTED`. A review that drew no comments takes a fast path: because a review with no comments is 100.0 percent disposed **by definition** — not 0.0 and not null — it moves from `CLOSED` straight to the terminal `DISPOSITION_APPROVED` inside that same close request, skipping `DISPOSITION_DRAFTED` entirely, with `disposition_completeness_pct` at 100.0, `disposition_approved_at` set from the logical clock, and `disposition_approved_by_participant_id` left null because nobody approved it.

The disposition counters themselves are simple and are recomputed whenever a comment is created against a review, whenever a comment on it is dispositioned in either direction, and whenever the review is closed. `comment_count` is the number of comment rows whose `public_review_id` is this review, in every status. `disposed_count` is how many of those are in `ACCEPTED`, `ACCEPTED_WITH_MODIFICATION` or `REJECTED`. `unresolved_comment_count` is `comment_count` less `disposed_count`. And `disposition_completeness_pct` is 100.0 when `comment_count` is zero, and otherwise 100 multiplied by `disposed_count`, divided by `comment_count`, rounded half up to one decimal place. Objections raised on a ballot never enter this count: a comment whose `public_review_id` is null is outside the ledger.

Dispositioning a comment is the chair's exclusive act — the caller's identifier must equal the `chair_participant_id` of the committee sponsoring the reviewed draft's work item, else `ERR_NOT_COMMITTEE_CHAIR`. Any comment may be dispositioned whatever its `source_type`: a `COMMITTEE` comment and the server-filed `BALLOT_NEGATIVE` objection pass through the very same request as a public review comment, and because their `public_review_id` is null the disposition moves the comment alone and touches no ledger. The request supplies a `disposition` of `ACCEPTED`, `ACCEPTED_WITH_MODIFICATION`, `REJECTED` or `REOPENED`. The first three each move an `OPEN` comment to the matching status and each require a non-empty `disposition_rationale`, which is recorded on the comment — a rejected comment in particular must carry a written reason, and omitting the rationale is `ERR_INVALID_REQUEST`. A comment that is not `OPEN` cannot be dispositioned, and a comment that *is* `OPEN` cannot be reopened; both mismatches are `ERR_INVALID_COMMENT_STATE`. Every one of the three disposing outcomes has identical downstream effects: the parent review's `disposed_count`, `unresolved_comment_count` and `disposition_completeness_pct` are recomputed, and when the recomputed `unresolved_comment_count` reaches 0 on a review that has at least one comment, the review bubbles up from `CLOSED` to `DISPOSITION_DRAFTED` with `disposition_completeness_pct` at 100.0. Both the comment's and the review's `version` advance.

`REOPENED` is the exact compensation for all three. It returns a comment in `ACCEPTED`, `ACCEPTED_WITH_MODIFICATION` or `REJECTED` back to `OPEN`, clears its `disposition_rationale` to null, decrements the review's `disposed_count`, increments its `unresolved_comment_count`, recomputes `disposition_completeness_pct`, and reverses the earlier bubble-up by moving the review from `DISPOSITION_DRAFTED` back to `CLOSED` if it had already bubbled. A `disposition_rationale` is optional on this branch rather than forbidden: one that is supplied is still shape-checked as a 1-to-2000-character string, but it is neither stored nor otherwise consulted, the comment's rationale being cleared regardless. Reopening is forbidden once the review has reached `DISPOSITION_APPROVED`, and the attempt is refused with `ERR_INVALID_PUBLIC_REVIEW_STATE`. After a disposition followed by a reopening there must be no counter drift whatsoever.

Approving the disposition record is where segregation of duties bites hardest. Either the secretariat or a committee chair may approve, the review must be in `DISPOSITION_DRAFTED` (else `ERR_INVALID_PUBLIC_REVIEW_STATE`), its `disposition_completeness_pct` must be exactly 100.0 (else `ERR_DISPOSITION_INCOMPLETE`), and the caller's identifier must **differ** from the `chair_participant_id` of the committee sponsoring the reviewed draft's work item — whoever wrote the dispositions may not sign them off, and a chair who tries is refused with `ERR_DISPOSITION_APPROVER_CONFLICT`. On success the review moves from `DISPOSITION_DRAFTED` to the terminal `DISPOSITION_APPROVED`, `disposition_approved_at` is taken from the logical clock, and `disposition_approved_by_participant_id` records the caller's identifier when the caller is a chair and stays null when the caller is the opaque secretariat role. Only then does the draft become eligible for a consensus-body ballot.

### 3.7. Patent Disclosure, Licensing Commitments and the Call for Patents

Any participant taking part in the process — acting as `CommitteeMember`, `CommitteeChair`, `PublicCommenter` or `Proposer` — may record a patent disclosure against a work item. The submission names the `work_item_id` the patent reads on, the `disclosing_participant_id` (which must equal the caller's own identifier), the `patent_number` as a non-blank string of 1 to 40 characters, the claimed `essentiality`, and the `expected_work_item_version` required by §2.7. `essentiality` is one of `ESSENTIAL`, `POTENTIALLY_ESSENTIAL` or `NON_ESSENTIAL`. A new disclosure is stored with `status` `DISCLOSED_NO_COMMITMENT`, `disclosed_at` from the logical clock, and `commitment_letter_ref` and `committed_at` both null. Nothing else constrains the filing: the work item's `progress_status` is never examined, so a disclosure may be recorded at any stage of the life cycle from `PROPOSED` through `WITHDRAWN`, and `patent_number` carries no uniqueness constraint of any kind — the same number may be disclosed twice on one work item, by the same party or by different ones, and each filing is an independent row that is counted independently by the derivation below.

The disclosing party is expected to follow up with a licensing commitment, recorded against the disclosure itself. The `commitment` value maps one-to-one onto the disclosure's `status`: `RAND` yields `RAND_COMMITTED`, `RAND_ZERO` yields `RAND_ZERO_COMMITTED`, `REFUSE` yields `REFUSED`, and `WITHDRAW` yields `WITHDRAWN`. A `commitment_letter_ref` naming the filed licensing letter, a non-blank string of 1 to 80 characters, is required for `RAND` and for `RAND_ZERO`, and `committed_at` is taken from the logical clock for those two. "Expected" is the operative word: the endpoint enforces no identity at all beyond role admission — the body carries no participant identifier to re-assert, and any caller in one of the four participating roles may record the commitment on any disclosure, whoever filed it. Nor is there any status precondition. A commitment may be recorded on a disclosure that already carries one, and the last write wins, which makes the four values freely interchangeable in any order and any number of times; the disclosure's `version` advances on every such call, a call that merely restates the status it already had included. Because `commitment_letter_ref` and `committed_at` are written only on the two reasonable-and-non-discriminatory branches, they are never cleared: a `REFUSE` or `WITHDRAW` following a `RAND` leaves the earlier letter reference and commitment instant standing beside the new status, and a `commitment_letter_ref` supplied alongside `REFUSE` or `WITHDRAW` is shape-checked against the same bounds and then discarded. Recording a disclosure and recording a commitment both count, in the sense of §2.7's closing proviso, as endpoints that write the parent work item: each advances that work item's `version` by exactly 1 whether or not the clearance derivation running inside it actually moves `ip_status`.

Whether a particular patent stands in the way of publication is recorded on the disclosure as `blocks_publication`, and the rule has exactly two conjuncts: the disclosure's `essentiality` is `ESSENTIAL` or `POTENTIALLY_ESSENTIAL`, **and** its `status` is `DISCLOSED_NO_COMMITMENT` or `REFUSED`. A withdrawn disclosure therefore never blocks. A disclosure declared `NON_ESSENTIAL` never blocks, whatever its licensing status. And a reasonable-and-non-discriminatory commitment, whether royalty-bearing or royalty-free, lifts the block on an essential patent — though lifting a block is not by itself clearance. Storing the verdict per disclosure means a blocked work item's blockage is always attributable to a specific patent. Every re-derivation of the work item's `ip_status` refreshes `blocks_publication` on all of that work item's disclosures before reading them, and does so without advancing those disclosures' `version`: the flag is a pure function of the disclosure's own `essentiality` and `status`, so outside the request that changed one of those two the refresh is only ever confirmatory.

The work item's `ip_status` is then derived from all of its disclosures together, by the first matching branch of a four-way rule. The **call for patents** is deemed closed once the work item's `progress_status` is `CONSENSUS_APPROVED`, `PUBLISHED`, `UNDER_PERIODIC_REVIEW` or `REAFFIRMED`; before that instant an empty disclosure set means only that nobody has spoken yet, and afterwards it means the field is clear. So: if any disclosure on the work item has `blocks_publication` true, `ip_status` is `IP_BLOCKED`; otherwise, if the call for patents has closed, `ip_status` is `IP_CLEARED`; otherwise, if the work item has no disclosures at all, `ip_status` is `IP_PENDING`; otherwise `ip_status` is `IP_DISCLOSED`. This derivation runs when a disclosure is recorded, when a commitment is recorded, at the consensus-approval moment inside a ballot close and inside the adjudication that clears the last pending negative, again inside the upholding of an appeal at the moment that upholding returns a work item from `CONSENSUS_APPROVED` to `IN_DEVELOPMENT`, and once more as a precondition of publication.

Reading that rule against the four `ip_status` values produces the full set of edges, and each is worth stating on its own because they are what the tests exercise. A first disclosure whose `blocks_publication` is false, on a work item with no blocking disclosure on file, moves `IP_PENDING` to `IP_DISCLOSED`. A disclosure whose `blocks_publication` is true moves `IP_PENDING` to `IP_BLOCKED`. A later blocking disclosure, or a commitment of `REFUSE`, moves `IP_DISCLOSED` to `IP_BLOCKED`. A commitment of `RAND`, `RAND_ZERO` or `WITHDRAW` that leaves no blocking disclosure on the work item moves `IP_BLOCKED` back to `IP_DISCLOSED` **while the call for patents is still open** — that is, while `progress_status` is none of `CONSENSUS_APPROVED`, `PUBLISHED`, `UNDER_PERIODIC_REVIEW` or `REAFFIRMED`. The very same commitment, on a work item whose call for patents has already closed, moves `IP_BLOCKED` directly to `IP_CLEARED` instead: unblocking a late essential patent on an already consensus-approved standard clears intellectual property outright rather than dropping back to `IP_DISCLOSED`, and that is precisely what lets publication resume. Consensus approval itself clears the field: a work item with zero disclosures moves `IP_PENDING` to `IP_CLEARED`, and a work item all of whose disclosures are non-blocking moves `IP_DISCLOSED` to `IP_CLEARED`. Clearance is not a one-way latch in either direction. A late blocking disclosure filed after consensus approval moves `IP_CLEARED` to `IP_BLOCKED` — the edge that makes intellectual property a real gate, since publication is then refused with `ERR_IP_NOT_CLEARED`. And when an upheld appeal has returned a work item to `IN_DEVELOPMENT`, a recomputation on a work item that has no disclosures at all moves `IP_CLEARED` back to `IP_PENDING`, because reopening development reopens the call for patents.

### 3.8. Appeals of Procedural Violations and Their Remedies

Any participant with standing may file an appeal alleging that the procedure was violated, acting as `Proposer`, `CommitteeMember`, `CommitteeChair` or `PublicCommenter`. The filing names the `work_item_id` whose procedure is challenged, the `appellant_participant_id` (which must equal the caller's own identifier), the `grounds` asserted — one of `BALANCE_VIOLATION`, `NEGATIVE_NOT_CONSIDERED`, `PUBLIC_REVIEW_DEFECT`, `IP_DISCLOSURE_DEFECT` or `VOTING_PROCEDURE_DEFECT` — a `statement` of 1 to 2000 non-blank characters, and optionally a `cited_ballot_id` naming the ballot whose conduct is challenged.

Standing is checked first, ahead of timeliness. The caller must be an interested party, which means one of three things: the caller is the work item's `proposer_participant_id`; or the caller is the `participant_id` of a committee membership on the sponsoring committee whose `status` is `ACTIVE` or `SUSPENDED`; or the caller is the `submitter_participant_id` of at least one comment on one of the work item's drafts. A caller who is none of the three is refused with `ERR_APPELLANT_NOT_INTERESTED_PARTY`.

Timeliness needs an anchor. When `cited_ballot_id` is supplied, the anchor is that ballot's `closed_at`; when it is omitted, the anchor is the work item's `published_at`. If the cited ballot has no `closed_at` — which is the case for a ballot still `OPEN`, and for one vacated while it was still `OPEN`, though *not* for one vacated after it had been evaluated, since vacating leaves the `closed_at` the close stamped on it intact and such a ballot still anchors a filing — or if no ballot was cited and the work item has never been published, there is nothing to count from and the filing is refused with `ERR_APPEAL_ANCHOR_MISSING`. Given an anchor, `filing_deadline_at` is that anchor instant advanced by 30 days, and a filing is timely when the logical clock is at or before that deadline — the deadline instant itself is timely. A ballot that closed at `2026-09-15T00:00:00Z` therefore yields a `filing_deadline_at` of `2026-10-15T00:00:00Z`; a filing at exactly that instant is accepted, and a filing one second later is refused with `ERR_APPEAL_UNTIMELY`.

An accepted filing is stored with `status` `FILED`, `remedy` `NONE`, `filed_at` from the logical clock, and `decided_at` and `decision_rationale` null. Merely filing it shuts the work item's procedural gate to `BLOCKED`, and the work item's `version` advances — an appeal is a stop-work order until it is decided.

Deciding an appeal belongs exclusively to the `AppealsBoard`, which is barred from every other mutation precisely so that the body able to vacate a ballot can never have participated in it. The decision carries a `decision`, a non-empty `decision_rationale`, and, on an upholding, a `remedy`. A `decision` of ACCEPT_FOR_REVIEW moves an appeal from `FILED` to `ACCEPTED_FOR_REVIEW`; it requires the appeal to be in `FILED`, else `ERR_INVALID_APPEAL_STATE`. Acceptance keeps the work item's gate `BLOCKED`, because an appeal in either `FILED` or `ACCEPTED_FOR_REVIEW` blocks advancement, and where the appeal cites a ballot that is still `OPEN`, that ballot's `hold_reason` becomes `APPEAL_PENDING` — which is what stops the ballot being closed while the challenge is live. An acceptance records the `decision_rationale` on the appeal but leaves `decided_at` null, an acceptance not yet being a decision, and leaves `remedy` at `NONE`: a `remedy` supplied alongside an ACCEPT_FOR_REVIEW or a DENY is checked as an enum member and then ignored. It advances the appeal's own `version`, and the cited ballot's where a hold was stamped, but advances the work item's `version` only where the re-derivation actually writes a different `consensus_gate` or `unresolved_negative_count` — which, the gate already standing `BLOCKED` from the filing, it ordinarily does not. `UPHELD` and `DENIED` are terminal; a further decision on either is refused with `ERR_INVALID_APPEAL_STATE`.

A `decision` of UPHOLD requires a `remedy` of `VACATE_BALLOT`, `REMAND_TO_COMMITTEE` or `SUSPEND_STANDARD`; a remedy of `NONE` on an upholding is rejected with `ERR_INVALID_REQUEST`. It also requires the appeal to be in `ACCEPTED_FOR_REVIEW`: an appeal still in `FILED` must be accepted for review first, and an upholding taken directly from `FILED` is refused with `ERR_INVALID_APPEAL_STATE`. Upholding runs a four-hop cascade. Hop one writes the appeal's `status` to `UPHELD`, records the `remedy` and the `decision_rationale`, and sets `decided_at` from the logical clock. Hop two, under the `VACATE_BALLOT` remedy, moves the cited ballot from `EVALUATED` to `VACATED` — the tallies and percentages are preserved untouched as the historical record, and `consensus_result` is left exactly as it was — or, when the cited ballot is still `OPEN`, from `OPEN` to `VACATED`, in which case no tallies are frozen at all and `provisional_approval_pct` stays null; either way the vacated ballot's `hold_reason` is released to `NONE`. Where the remedy is `VACATE_BALLOT` but the appeal cited no ballot at all, or cited one whose `status` is neither `OPEN` nor `EVALUATED`, nothing is vacated and hops three and four do not run either: only the appeal itself is written. Hop three, because the ballot was vacated, reaches the cited ballot's own draft — or, where no ballot was cited, the work item's latest revision — and moves it from `APPROVED` back to `DRAFTING`, or from `CONSENSUS_BALLOT` to `PUBLIC_REVIEW_CLOSED` when the draft was still balloting, a draft in any other status keeping the status it holds; the draft inherits a `carryover_unresolved_negative_count` equal to the cited ballot's `negative_count`, meaning every negative that had been cast on it whether or not it was later adjudicated, and where no ballot was cited the carryover is left exactly as it stood. The draft's `version` advances on this hop whichever of those branches applied. Hop four, because the draft returned to development, moves the work item from `CONSENSUS_APPROVED` back to `IN_DEVELOPMENT` and re-derives its gate, so the consensus cycle can run again — this time with the approval bar raised by 5.0 percentage points on account of the carryover; a work item in any other `progress_status` keeps it, while still taking a `version` advance and a fresh gate derivation. Under the `REMAND_TO_COMMITTEE` remedy the ballot is left entirely intact — an `APPEAL_PENDING` hold already stamped on it is *not* released, since only a denial and a vacating clear a hold — and only hops three and four run. Under the `SUSPEND_STANDARD` remedy a work item in `PUBLISHED` or `REAFFIRMED` moves to `SUSPENDED` instead of the draft and consensus hops running, and a work item in any other state keeps its `progress_status` while still taking a `version` advance and a fresh gate derivation. An upholding advances the `version` of the appeal always, of the ballot where it was vacated, and of the draft and the work item wherever hops three and four ran.

A `decision` of DENY is the divergent branch, and it does very little by design. It may be taken from `ACCEPTED_FOR_REVIEW` or directly from `FILED` — a procedurally deficient appeal may be denied without a substantive review — and in both cases it requires a non-empty `decision_rationale` and behaves identically. `remedy` stays `NONE`. The cited ballot, the draft and the work item's `progress_status` are all left untouched. Any ballot `hold_reason` of `APPEAL_PENDING` is released back to `NONE` — on the cited ballot and on every other ballot reachable through the work item's drafts, whichever appeal had stamped it. And the work item's gate is re-derived, returning to `OPEN` when no other appeal is live and no draft of the work item sits in `COMMENT_RESOLUTION`. A denial advances the `version` of the appeal and, unconditionally, of the work item — the re-derivation bumps it even where the gate comes out unchanged — together with the `version` of every ballot whose hold it released; nothing else in the graph is written.

One asymmetry deserves a note, because it is the sole consumer of the roster-basis arithmetic in §2.6: an appeal whose `grounds` are `BALANCE_VIOLATION` is adjudicated against the committee's `roster_balance_status` and `roster_dominance_pct`, not against `balance_status` — the appellant's complaint concerns who was appointed to the committee, not who happened to be entitled to vote on the day the ballot ran.

### 3.9. Publication and the Five-Year Maintenance Cycle

Publication is the secretariat's act, reserved to `StandardsStaff`, and it takes no body at all: every one of its conditions is read from stored state, so there is nothing for the caller to assert. Five preconditions must hold together. The work item's `progress_status` must be `CONSENSUS_APPROVED`. Its sponsoring committee's `status` must still be `ACTIVE`, since a standard may not be published out of a committee that has been dissolved or put on hold. No vote on any of its ballots may still carry an `adjudication_status` of `PENDING`, else `ERR_NEGATIVES_NOT_CONSIDERED`. Its `consensus_gate` must be `OPEN`, else `ERR_CONSENSUS_GATE_BLOCKED` — and like the clearance check below, the gate is derived afresh inside this request from the appeals, the drafts and the sponsoring committee as they now stand, rather than read out of the stored field, which an earlier request may have left behind. Its `ip_status`, after the clearance derivation of §3.7 has been re-run inside this same request, must be `IP_CLEARED`, else `ERR_IP_NOT_CLEARED` — re-running rather than trusting the stored value is what catches a patent disclosed between consensus approval and publication. And the latest public review on the `APPROVED` draft must have reached `DISPOSITION_APPROVED`, else `ERR_PUBLIC_REVIEW_NOT_APPROVED`: publication may never outrun the disposition of the public review comments. The draft read for that last condition is the most recently created draft of the work item whose `status` is `APPROVED`, and a work item carrying no `APPROVED` draft at all draws that very same `ERR_PUBLIC_REVIEW_NOT_APPROVED` rather than a draft-state error.

On success `progress_status` moves from `CONSENSUS_APPROVED` to `PUBLISHED`, the `edition` label assigned at scope approval is persisted as the published edition, `published_at` is taken from the logical clock, `periodic_review_due_date` is written by the schedule rule below, and the work item's `version` advances.

Every published standard carries a standing obligation to be revisited, and `periodic_review_due_date` is where that obligation lives. The due date is anchored on a **calendar date**, not on a timestamp of convenience: the anchor is the date part of `published_at` at publication, and the date part of `last_periodic_action_at` at a reaffirmation. The due date is that anchor date advanced by 5 calendar years, keeping the same month and day, with the single exception that a 29 February anchor falls back to 28 February. Two further bounds are derived from it and are never stored: the review window opens 180 days before the due date, and the reaffirmation grace period ends 90 days after it. A periodic-review action is in-window when the calendar date of the logical clock falls at or after the window opening and at or before the end of grace, both bounds inclusive. So a standard published on 2026-09-15 is due for review on 2031-09-15, may be opened for review from 2031-03-19, and may be reaffirmed up to and including 2031-12-14.

A periodic-review action supplies an `action` of OPEN_REVIEW, REAFFIRM or WITHDRAW, and optionally a `rationale` of 1 to 2000 non-blank characters, which is shape-checked and then discarded — no field of the work item records it. It too is reserved to `StandardsStaff`, and it requires the work item's `consensus_gate` to be `OPEN` (else `ERR_CONSENSUS_GATE_BLOCKED`), derived afresh inside the request exactly as publication derives it and checked only after the per-action `progress_status` check has passed. In all three branches it writes `last_periodic_action_at` from the logical clock and advances the work item's `version`.

OPEN_REVIEW requires `progress_status` to be `PUBLISHED` or `REAFFIRMED` and moves it to `UNDER_PERIODIC_REVIEW`. It requires the logical clock to have reached the window opening — that is, the date of the logical clock at or after the due date less 180 days — else `ERR_PERIODIC_REVIEW_NOT_DUE`. The edge out of `REAFFIRMED` is what makes the cycle a genuine loop: a reaffirmed standard becomes due again five years after its reaffirmation and may be opened for review again, without limit.

REAFFIRM is taken only from `UNDER_PERIODIC_REVIEW` and moves the work item to `REAFFIRMED`. It carries the process's one purely evidentiary precondition: the work item's latest draft — the one with the highest `revision_number`, and where two drafts tie on that number the most recently created of them — must carry at least one ballot whose `effective_ballot_kind` is `REAFFIRMATION`, whose `status` is `EVALUATED` and whose `consensus_result` is `APPROVED`, else `ERR_REAFFIRMATION_BALLOT_REQUIRED`. No ballot identifier is passed in; the check is a lookup over the work item's own ballots. A ballot left at `APPROVED_PENDING_NEGATIVES` does not satisfy it, because reaffirmation on the strength of a ballot whose negatives were never considered would defeat the whole point. Reaffirmation must also fall within grace: the date of the logical clock at or before the due date plus 90 days, else `ERR_REAFFIRMATION_WINDOW_EXPIRED`. A successful reaffirmation rewrites `periodic_review_due_date` to the date of the current logical clock advanced by 5 calendar years, re-anchoring the cycle on the reaffirmation rather than on the original publication.

WITHDRAW moves the work item to the terminal `WITHDRAWN`, and may be taken either from `UNDER_PERIODIC_REVIEW` or from `SUSPENDED` — a standard suspended by an upheld appeal is retired by the same act. Withdrawal sets `periodic_review_due_date` to null. It is also the one periodic-review action never barred by the grace deadline: an overdue standard must always remain withdrawable, so `ERR_REAFFIRMATION_WINDOW_EXPIRED` applies to REAFFIRM alone, while `ERR_PERIODIC_REVIEW_NOT_DUE` guards the window opening for both. Any maintenance request against a withdrawn standard that is still sitting in `RECEIVED` stays in `RECEIVED` — nothing is cascaded onto it — but its resolution is refused from that moment on with `ERR_INVALID_WORK_ITEM_STATE`.

A published standard attracts two kinds of maintenance traffic, and both enter through a single request. Any participant acting as `PublicCommenter`, `CommitteeMember`, `CommitteeChair` or `Proposer` may submit one, naming the `work_item_id` the request concerns, the `requester_participant_id` (which must equal the caller's own identifier), the `item_kind` — either `INTERPRETATION_REQUEST` or `ERRATUM_REPORT` — the `question_text` stating the question or the defect as 1 to 2000 non-blank characters, and optionally the `clause_reference` the request concerns, a non-blank string of 1 to 40 characters when supplied and null when not. Submission imposes no condition whatsoever on the target work item's `progress_status` — the phrase "a published standard" describes the expected traffic, not a gate. A request may be filed against a work item that is still `IN_DEVELOPMENT`, that was never published, or that has already been `WITHDRAWN`, and it is stored in `RECEIVED` in every such case; every state test in this area lives at resolution instead. The stored item begins with `status` `RECEIVED`, `received_at` from the logical clock, and `response_text`, `erratum_clause_reference` and `resolved_at` all null.

Resolving a maintenance item is where the two kinds diverge sharply, though they share a request shape: an `action`, a `response_text` of 1 to 2000 non-blank characters that is required on all three actions alike, and optionally an `erratum_clause_reference` of 1 to 40 non-blank characters, which becomes required on `ISSUE_ERRATUM` and, on the other two actions, is shape-checked against those same bounds and then discarded — the field is written to the item on the erratum branch alone. The item must be in `RECEIVED`, else `ERR_INVALID_MAINTENANCE_STATE`; a resolved item cannot be re-resolved. The chair-identity test keys off the **caller's role rather than the action**: a caller presenting `CommitteeChair` must equal the `chair_participant_id` of the committee sponsoring the target work item on all three actions — `DECLINE` and `ISSUE_ERRATUM` included, and unsatisfiably so where the work item has no sponsoring committee, which yields `ERR_NOT_COMMITTEE_CHAIR` for a chair on such an item whatever the action — while a caller presenting `StandardsStaff` is never subject to the test at all. In all three branches `resolved_at` is taken from the logical clock, the `response_text` is stored, and the item's `version` advances; on the two issuing branches the parent work item's `version` advances as well, since its counters are rebuilt from the maintenance record and written back, while `DECLINE` leaves the parent's `version` where it stood.

ISSUE_INTERPRETATION is conventionally the chair's branch, though the server does not police that pairing — either admitted role may take either issuing action, so the secretariat may issue an interpretation just as a chair may issue an erratum — and is available only where `item_kind` is `INTERPRETATION_REQUEST`; asking for it on an erratum report is refused with `ERR_MAINTENANCE_ACTION_MISMATCH`. It moves the item from `RECEIVED` to `INTERPRETATION_ISSUED` and increments the parent work item's `interpretation_count` by 1, leaving `errata_count` untouched.

ISSUE_ERRATUM is conventionally the secretariat's branch, again as a convention rather than an enforced restriction, and is available only where `item_kind` is `ERRATUM_REPORT`, again refused with `ERR_MAINTENANCE_ACTION_MISMATCH` otherwise. It additionally requires a non-empty `erratum_clause_reference` naming the clause being corrected, which is stored on the item, and it requires the parent work item's `progress_status` to be `PUBLISHED`, `REAFFIRMED` or `UNDER_PERIODIC_REVIEW`, else `ERR_STANDARD_NOT_PUBLISHED` — an erratum cannot be issued against text that was never published. It moves the item from `RECEIVED` to `ERRATUM_ISSUED` and increments the parent's `errata_count` by 1, leaving `interpretation_count` untouched. Note the asymmetry: an interpretation may be issued against a standard in any state short of `WITHDRAWN` — including one that has no sponsoring committee at all, which the secretariat can resolve although a chair cannot — while an erratum is confined to published text.

DECLINE is available for either kind and to either role, requires only a non-empty `response_text`, and moves the item from `RECEIVED` to `DECLINED`. It is the branch that touches nothing else: neither `errata_count` nor `interpretation_count` changes, and only the maintenance item's own `version` advances — the parent work item is left entirely alone.

Both counters are, by definition, the number of maintenance items on the work item that have reached `ERRATUM_ISSUED` and `INTERPRETATION_ISSUED` respectively, so they are always reconstructible from the maintenance record. And neither branch ever touches `edition` or `published_at`: an interpretation clarifies the published text and an erratum corrects a defect in it, but only a full revision cycle — a new work item of `work_item_type` `REVISION` carried through balloting, public review and publication — produces a new edition. That is the whole reason `edition` is written once at publication and never again.

## 4. API Endpoint Specifications

Every endpoint below is mounted under the `/sdo` prefix, except the logical-clock control endpoint described in §2.4. Endpoints that create a new resource respond with HTTP status code 201; endpoints that read, modify or advance an existing resource respond with HTTP status code 200. Every response body follows the envelope of §2.2, and every list endpoint honours the pagination rules of §2.3. The role column lists the values of `X-User-Role` admitted by that endpoint; any other value is refused with `ERR_UNAUTHORIZED`, as described in §2.1. A request whose path matches no endpoint at all, or whose method that path does not support, never reaches the ladder of §2.5: it is answered with the error envelope of §2.2 carrying `error_id` `ERR_INVALID_REQUEST` under HTTP 404 and HTTP 405 respectively — the only two places in this specification where `ERR_INVALID_REQUEST` is returned under a status other than 400. A body that is not parseable JSON, or that parses to something other than a JSON object, is `ERR_INVALID_REQUEST` (400); an absent or empty body is read as the empty object, so endpoints with no required fields accept a request with no body at all.
