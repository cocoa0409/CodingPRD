# Single-Family Rental Portfolio Operations API — Product Requirements Document

## 1. Introduction

A scattered-site single-family rental operator does not own a building; it owns thousands of individual houses, each one an independent asset with its own underwriting case, its own renovation history, its own insurance binder, its own homeowner-association covenants and its own tax assessment. The operational consequence is that almost nothing can be managed as a batch. A home can be simultaneously stabilized on the acquisition axis and occupied on the leasing axis, or approved for a portfolio-lot sale while a resident is still living in it. Every decision — pass or acquire, in-house crew or vendor network, approve or conditionally approve an applicant, hold or sell — is taken per address, against market-level policy that must nonetheless stay standardized across the whole portfolio.

This document specifies the API that carries that work. It covers acquisition underwriting on individual homes with planned renovation scope and rent estimates; renovation and turn project management across a certified vendor network with cost benchmarking; leasing through self-showing technology with identity verification and fraud controls; resident screening with a risk-adjusted deposit stack; standardized pet policy and lease terms; maintenance dispatch that forks between in-house technicians and vendor crews; make-ready cycle-time measurement with vendor holdbacks; property tax appeals, insurance and HOA compliance; and disposition decisions on individual assets versus portfolio lots.

Two properties of the design deserve emphasis up front, because they shape nearly every endpoint. First, the same underwriting case is priced twice — once forward-looking from planned scope and an estimated rent, and once again from what actually happened, using invoiced renovation costs and the executed lease rent — and the divergence between the two figures is what drives the hold-or-sell recommendation. Second, a home's entire leasing funnel is gated by a single derived value, the **leasing posture**, that is recomputed from the home's acquisition state, its insurance binder and its live compliance obligations; when that posture changes, published showing windows are blocked or released as a side effect rather than by any explicit operator action. Implementers should treat the posture recomputation and its slot cascade as a first-class concern, not an afterthought.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operator Identity and Role-Based Access Control

Every request carries two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names the capacity in which the principal is acting. Segregation of duties and peer-ownership checks are always resolved against `X-User-ID`; `X-User-Role` never participates in an ownership comparison, only in permission checks.

Twelve roles exist, spelled exactly as follows: `System`, `PortfolioAdmin`, `AcquisitionAnalyst`, `InvestmentCommittee`, `OperationsManager`, `VendorManager`, `Vendor`, `LeasingAgent`, `Prospect`, `Anonymous`, `ComplianceOfficer`, `RegionalDirector`.

If `X-User-Role` is absent, or carries any value outside that list of twelve, the request is rejected with `ERR_INVALID_ROLE` (HTTP 400). If `X-User-ID` is absent or is an empty string, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); the single exception is the logical-clock setter, which is exempt from the `X-User-ID` requirement. When both headers are well-formed but the named role is not among the roles authorised for the requested operation, the rejection is `ERR_UNAUTHORIZED` (HTTP 403).

Ownership semantics differ by role, and they must be implemented literally:

- When `X-User-Role` is `Vendor`, `X-User-ID` is the `id` of the acting vendor row. Ownership checks on a work order compare the work order's `vendor_id` to `X-User-ID`: a vendor may accept or complete only work orders whose `vendor_id` equals its own identifier, and a mismatch is `ERR_NOT_ASSIGNED_VENDOR` (HTTP 403).
- When `X-User-Role` is `Prospect`, `X-User-ID` is the `id` of the acting prospect row. Exactly two operations compare it: slot booking compares it to the `prospect_id` named in the booking payload — the slot itself carries none yet — and slot cancellation compares it to the showing slot's stored `prospect_id`. Either mismatch is `ERR_NOT_SLOT_OWNER` (HTTP 403). Nothing else is ownership-checked against a prospect: a rental application's `prospect_id` is never compared to `X-User-ID`, on creation or on screening, and neither is the prospect named in an identity-verification path.
- When `X-User-Role` is `AcquisitionAnalyst`, `X-User-ID` is an opaque analyst identifier not tied to any persisted entity. The server records it as `submitted_by_user_id` on the underwriting case at submit time, but never compares it to any entity's `id`.
- When `X-User-Role` is `InvestmentCommittee`, `X-User-ID` is an opaque committee-member identifier not tied to any persisted entity. The server records it as `decided_by_user_id` on the underwriting case at decision time, and compares it only against the case's stored `submitted_by_user_id`.
- When `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is an opaque officer identifier not tied to any persisted entity. The server records it as `submitted_by_user_id` on a compliance obligation when a resolution is submitted, and compares it only against that stored value when the resolution is reviewed.
- When `X-User-Role` is `System`, `X-User-ID` is an opaque identifier that the server ignores entirely; the role exists only to drive the logical clock.
- When `X-User-Role` is `PortfolioAdmin`, `OperationsManager`, `VendorManager`, `LeasingAgent` or `RegionalDirector`, `X-User-ID` is an opaque staff identifier not tied to any persisted entity. The server may record it, but it is never compared to any entity's `id`.
- When `X-User-Role` is `Anonymous`, `X-User-ID` is an opaque device-scoped token not tied to any persisted entity. It must still be present and non-empty, but it is never matched against a stored row.

Two roles hold override authority worth naming here. A `RegionalDirector` is the only role permitted to draft a lease whose `term_months` differs from the market's standardized term, and it shares budget revision with `OperationsManager` and compliance review with `ComplianceOfficer`. A `PortfolioAdmin` is the only role that may register markets and publish scope templates.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection read accepts two query parameters. `limit` defaults to 10 when omitted, with a minimum accepted value of 1 and a maximum accepted value of 100. `offset` defaults to 0 and counts rows to skip from the beginning of the ordered result set. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400); `offset` carries no upper bound. Either parameter supplied as an empty string falls back to its default, and either supplied as anything that is not a base-10 integer is likewise rejected with `ERR_INVALID_REQUEST`. Both parameters, and the filter parameters described below, are examined only after the role and principal checks of §2.1 have passed, so an unauthorised caller who also supplies an out-of-range `limit` is answered with `ERR_UNAUTHORIZED`.

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending, with rows sharing the same `created_at` value ordered by the sequence in which the server created them. The four pagination fields reported in `meta` are `limit` (the effective page size actually applied), `offset` (the effective offset actually applied), `total_count` (the number of rows matching the filters before pagination) and `has_more` (true when rows remain beyond this page). Filter query parameters, where an endpoint offers them, narrow the matched set before `total_count` is computed. A filter over a boolean field accepts `true`, `false`, `1` or `0` and rejects any other value with `ERR_INVALID_REQUEST`; a filter over a string or enum field is matched by exact equality, so a value matching no row simply yields an empty page rather than an error.

### 2.4. Resource Identity, Common Properties and the Logical Clock

Every stored resource carries an `id` that is a server-minted UUID string with no type prefix; clients never supply an `id`. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits, fixed at creation. All twelve persisted entity types in this system — markets, scope templates, homes, underwriting cases, vendors, vendor certifications, renovation projects, work orders, prospects, showing slots, rental applications, leases and compliance obligations — additionally carry `updated_at`, an ISO 8601 UTC timestamp with three fractional digits refreshed on every mutation, and `version`, an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row, including mutations reached as a cascade side effect of an operation on a different resource. The `created_at` and `updated_at` stamps are taken from real server time; the logical clock described below governs comparisons only and never these two stamps.

Date fields such as `due_on`, `effective_on`, `expires_on`, `scheduled_start_date`, `scheduled_end_date`, `completed_on`, `signed_on`, `start_date`, `turn_started_on`, `rent_ready_on`, `planned_resolution_on`, `requested_move_in_date`, `insurance_binder_expires_on` and `insurance_expires_on` are plain calendar dates in `YYYY-MM-DD` form. Instant fields — `starts_at` and `ends_at` on a showing window — are full ISO 8601 UTC timestamps with three fractional digits. On input, any valid ISO 8601 instant is accepted for an instant field — a trailing `Z` or a numeric UTC offset, with or without fractional digits — and is normalised to UTC before any comparison; a date field, by contrast, is accepted only in exactly `YYYY-MM-DD` form.

Every date and instant comparison in this API reads a **logical clock** rather than wall-clock time. The clock boots at `2026-08-01T00:00:00Z`. A `System` caller may set it to any instant by supplying `current_utc`; a read of the clock returns the same field name, whose value is the instant text exactly as the most recent accepted set supplied it, not re-rendered — and, before any set has been accepted, the literal boot text `2026-08-01T00:00:00Z`. The setter itself responds with HTTP 200 carrying that same `current_utc` field and value. Setting the clock never rewrites values already stored: it only changes what subsequent comparisons see. That matters in three places in particular — the derived leasing posture of every home (because an insurance binder is judged expired relative to the clock), vendor dispatch eligibility (because vendor insurance and trade certifications are dated), and the rejection of showing windows that start in the past.

### 2.5. Money, Basis Points and Rounding Discipline

All monetary amounts are integers in cents; no field in this API carries a fractional currency value. All rates, ratios, scores, tolerances and yields are integers in **basis points**, where 10,000 basis points is exactly 1. A basis-point field outside the inclusive range 0 through 1,000,000 is a malformed request.

Wherever a computation divides, the result is rounded **half up** to the nearest whole unit — whole cents for money, whole basis points for rates. There is exactly one rounding convention in this system and no computation ever truncates. Two consequences are load-bearing and are restated in the workflow sections below: a benchmark total is rounded once **per scope line** and only the already-rounded per-line figures are summed, and the fraud risk score is rounded exactly **once** at the very end after all four weighted factors have been summed as raw integers.

Basis-point arithmetic always uses 10,000 as the denominator. So "a percentage of X in basis points" means X multiplied by the basis-point figure, divided by 10,000, rounded half up.

"Half up" is measured **away from zero**, so a quotient whose fractional part is exactly one half always rounds to the larger magnitude in whichever direction it already sits: 2.5 becomes 3 and −2.5 becomes −3, never −2. That matters wherever a divided figure is allowed to be negative — a work order's `variance_bps` when the quote comes in below benchmark, and a yield in basis points computed off a negative net operating income. Every division is exact integer arithmetic on the numerator and denominator named in the formula, never floating point.

### 2.6. Optimistic Concurrency Control on Home and Prospect Writes

Two write operations require the client to prove it has observed the current state of a parent resource before it writes.

Opening an underwriting case requires `expected_home_version` in the request body. This field is mandatory, not optional, and it must carry the `version` of the target `Home` as the client last read it. If it does not equal the home's current `version`, the create is rejected with `ERR_STALE_HOME_VERSION` (HTTP 412) and nothing is written. This check exists because re-underwriting a scattered-site home is legitimate at any time, and a newly created case supersedes the prior non-terminal case for that home; on product semantics alone a second create observing the same stored state would succeed, so the stale-version comparison is what makes the supersede deterministic.

Recording an identity verification against a prospect requires `expected_prospect_version` in the request body, again mandatory, carrying the `version` of the target `Prospect` as the client last read it. A mismatch with the prospect's current `version` is rejected with `ERR_STALE_PROSPECT_VERSION` (HTTP 412). Re-verification is always permitted and legitimately supersedes the stored document, device and income signals, so the guard is expressed purely as a stale-version comparison against `Prospect.version` and never against any workflow status.

No other endpoint in this API accepts a version field. Requests to endpoints outside these two must not be required to carry one, and a supplied version field elsewhere carries no meaning.

### 2.7. Validation Precedence

Path parameters are resolved strictly left to right. A request to a nested path validates the outer identifier before the inner one, so a request naming a home that does not exist reports the missing home even when the inner identifier is also unknown.

More generally, every request is evaluated against an ordered ladder of checks. **Evaluation stops at the first violated rule, and only that rule's error is reported.** The ladder, in ascending order of the rank at which each check runs, is:

1. **Rank 10 — malformed payload.** A required input field is absent; an input field has the wrong JSON type; an enum-typed field carries a value outside its declared set; a money or count field is negative; a basis-point field falls outside the inclusive range 0 through 1,000,000; a field violates the numeric range declared for it in this document; or a date or timestamp field is not a valid ISO 8601 value. Reported as `ERR_INVALID_REQUEST` (400). Applies to every write endpoint. A field supplied as JSON `null` is treated exactly as if it were absent — it fails this rank when the field is required and takes the field's documented default when the field is optional — and a field this document does not declare for the endpoint is ignored rather than rejected, as is a request body that is absent entirely on an endpoint whose every field is optional.
2. **Rank 12 — inverted or degenerate interval.** A work-order window whose `scheduled_start_date` is later than its `scheduled_end_date`; a showing window whose `starts_at` is at or after its `ends_at`; a lease `term_months` below 1; or a certification whose `effective_on` is later than its `expires_on`. Reported as `ERR_INVALID_REQUEST` (400). Applies to work-order creation, showing-slot creation, lease drafting, vendor-certification creation and project scope-lock.
3. **Rank 20 — unrecognised role.** `ERR_INVALID_ROLE` (400), on every endpoint.
4. **Rank 30 — missing principal.** `ERR_UNAUTHENTICATED` (401), on every endpoint except the logical-clock setter.
5. **Rank 40 — role not permitted.** `ERR_UNAUTHORIZED` (403), on every endpoint.

### 2.8. The Two-Dimensional Home and the Leasing Posture Gate

A home carries **two independent state dimensions** that advance separately and must never be collapsed into one. `asset_status` tracks the acquisition and disposition axis and takes one of `PIPELINE`, `PASSED`, `ACQUIRED`, `RENOVATING`, `STABILIZED`, `DISPOSITION_APPROVED` or `DISPOSED`; it starts at `PIPELINE`, and `PASSED` and `DISPOSED` are terminal. `occupancy_status` tracks the leasing axis and takes one of `VACANT`, `RESERVED` or `OCCUPIED`; it starts at `VACANT`, and `OCCUPIED` is terminal. A transition on one dimension never implicitly moves the other. A `RESERVED` home may still be `STABILIZED` or `DISPOSITION_APPROVED`, and a portfolio-lot sale of an `OCCUPIED` home is a legitimate, supported case.

On top of those two dimensions sits a third, derived value: `leasing_posture`, which is one of `OPEN`, `RESTRICTED` or `FROZEN`. It is never supplied by a client and never stored independently of its inputs — it is recomputed at the end of every mutation that changes the home's `asset_status`, changes the home's `insurance_binder_expires_on`, or changes the status or severity set of the home's compliance obligations, and it is re-derived at read time so that a logical-clock change is visible without any write. Its inputs are the home's `asset_status`, the home's `insurance_binder_expires_on`, the `status` and `severity` of every compliance obligation attached to the home, and the current logical-clock date.

The posture is decided by the **first matching clause** in this exact order:

1. If `asset_status` is `PASSED`, `RENOVATING` or `DISPOSED`, the posture is `FROZEN`.
2. Otherwise, if `insurance_binder_expires_on` is earlier than the current logical-clock date, the posture is `FROZEN`.
3. Otherwise, if the home has at least one compliance obligation whose `severity` is `CRITICAL` and whose `status` is one of `OPEN`, `PLANNED`, `RESOLUTION_SUBMITTED` or `RESOLUTION_REJECTED`, the posture is `FROZEN`.
4. Otherwise, if the home has at least one compliance obligation whose `severity` is `MAJOR` and whose `status` is one of `OPEN`, `PLANNED`, `RESOLUTION_SUBMITTED` or `RESOLUTION_REJECTED`, the posture is `RESTRICTED`.
5. Otherwise, if `asset_status` is `PIPELINE` or `ACQUIRED`, the posture is `RESTRICTED`.
6. Otherwise — which is to say when `asset_status` is `STABILIZED` or `DISPOSITION_APPROVED` and none of the earlier clauses matched — the posture is `OPEN`.

Obligations whose `severity` is `MINOR` never affect posture, in any status. Obligations whose `status` is `RESOLVED` or `WAIVED` never affect posture, at any severity. That the first clause outranks the second matters: a `DISPOSED` home with a live binder is still `FROZEN`, and a `RENOVATING` home is `FROZEN` for the whole make-ready window regardless of how clean its obligation set is — which is precisely what makes the unblock cascade at stabilization observable. That the third clause outranks the fourth also matters: a home carrying both a `CRITICAL` and a `MAJOR` blocking obligation is `FROZEN`, not `RESTRICTED`, and resolving only the `MAJOR` one leaves it `FROZEN`.

The posture gates the funnel in three graduated steps. A showing window may be booked when the posture is `OPEN` or `RESTRICTED`. An application may be screened when the posture is `OPEN` or `RESTRICTED`. A lease may be executed **only** when the posture is exactly `OPEN` — `RESTRICTED` is not sufficient. A booking or screening attempt against a `FROZEN` home is refused with `ERR_HOME_SHOWINGS_BLOCKED`; an execution attempt against a home whose posture is anything other than `OPEN` is refused with `ERR_HOME_LEASING_FROZEN`.

Recomputation also drives showing-window state. Whenever a recomputation lands the posture on `FROZEN`, every showing window on that home whose `status` is `AVAILABLE` moves `AVAILABLE` → `BLOCKED_BY_POSTURE`. Whenever a recomputation returns the posture to `OPEN` or `RESTRICTED`, every window whose `status` is `BLOCKED_BY_POSTURE` moves back `BLOCKED_BY_POSTURE` → `AVAILABLE`. Windows whose `status` is `BOOKED` are never touched by posture recomputation, so a tour a prospect has already scheduled is never silently cancelled.

A dedicated computed read exposes the whole decision for a single home: it returns `home_id`, the resulting `leasing_posture`, `deciding_clause` as the integer number (1 through 6) of the clause that produced it, `blocking_obligation_ids` as the identifiers of the obligations that contributed to the decision, and `binder_expired` as a boolean stating whether the second clause's condition currently holds. `blocking_obligation_ids` is populated only by the two obligation clauses, and only at the severity of the clause that actually decided: clause 3 lists the home's blocking `CRITICAL` obligations and nothing else — its blocking `MAJOR` obligations are omitted even though they are present — clause 4 lists its blocking `MAJOR` obligations, and clauses 1, 2, 5 and 6 return an empty array even when the home is in fact carrying blocking obligations that a lower clause would have reported. Within the array the identifiers appear in obligation creation order. `binder_expired` is reported independently of which clause won, so it can be true while `deciding_clause` is 1.

### 2.9. Cascade Discipline and Conserved Quantities

Several operations in this system mutate more than one row. The rule is that every cascade completes inside the originating request — consistency is immediate, never eventual — and every row the cascade touches has its `updated_at` refreshed and its `version` incremented by 1, a row the cascade reaches by more than one hop inside the same request still being incremented by exactly 1 in total. There is no partial cascade: if a guard rejects the operation, nothing at all is written, including the cascade targets.

Three quantities are **conserved** and must reconcile after every operation:

- **The renovation money ledger.** For every renovation project, `committed_cost_cents` plus `budget_remaining_cents` always equals `approved_budget_cents`. Creating a work order inside a project adds the work order's `quoted_cost_cents` to `committed_cost_cents` and subtracts the same amount from `budget_remaining_cents`; voiding that work order subtracts it back out of `committed_cost_cents` and returns it to `budget_remaining_cents`. `committed_cost_cents` is by definition the sum of `quoted_cost_cents` over the project's work orders whose `status` is one of `PENDING_DISPATCH`, `DISPATCHED`, `ACCEPTED`, `IN_PROGRESS` or `COMPLETED`.
- **The vendor labour ledger.** For every vendor, `committed_crew_days` always equals the sum of `crew_days` over that vendor's work orders whose `status` is `DISPATCHED` or `ACCEPTED`. A successful vendor-channel dispatch adds the work order's `crew_days`; completing or voiding a dispatched or accepted work order subtracts it. In-house work never touches this figure.
- **The booking count.** For every home, `booked_showing_count` always equals the number of showing windows on that home whose `status` is `BOOKED`. Booking increments it by 1; releasing a booked window back to the calendar, or losing a booking because the prospect's identity verification failed, decrements it by 1.

### 2.10. Market Policy Standardization

A `Market` is the policy container that standardizes operations across thousands of homes, and almost every threshold in this document is read from it rather than hard-coded. A market is identified to operators by `code` — a 2-to-6-character uppercase-letter token such as `ATL`, unique across all markets — and carries a human-readable `name` plus the `tax_jurisdiction_code` of the authority that hears its property-tax appeals.

Its policy fields fall into five families. **Pricing and tax:** `millage_bps` is the annual property-tax rate in basis points of a home's assessed value and must fall between 1 and 3000 inclusive; `rent_index_cents` is the market median monthly rent in cents, at least 1, and serves both as the default asking rent for a new home and as the basis of the income-coverage denominator in fraud scoring; `cost_index_bps` is the market cost multiplier applied to national scope benchmarks and must fall between 5000 and 20000 inclusive. **Cost control and turn management:** `cost_variance_tolerance_bps` is the maximum variance above benchmark a work-order quote may carry, between 0 and 10000 inclusive; `make_ready_target_days` is the target make-ready cycle time in whole days, at least 1; `turn_holdback_cap_bps` caps the vendor holdback as a share of gross turn cost, between 0 and 10000 inclusive. **Self-showing:** `showing_buffer_minutes` is the lockbox re-code buffer appended after every showing window, between 0 and 240 inclusive, and `min_showing_duration_minutes` is the shortest permitted window, at least 5 minutes. **Standardized resident policy:** `pet_deposit_per_pet_cents` and `pet_deposit_cap_cents` set the per-pet charge and its hard ceiling; `max_pets` is the per-application pet limit, at least 0; `restricted_breeds` is an array of uppercase breed tokens the market forbids, stored exactly as supplied with no casing normalisation and later matched against a declared breed by exact equality; `standard_lease_term_months` is the standardized term in months, at least 1; `fraud_block_threshold_bps` and `rent_to_income_max_bps` are the fraud and affordability ceilings, each between 0 and 10000 inclusive. **Investment policy:** `vacancy_loss_bps`, `bad_debt_bps` and `mgmt_fee_bps` are the three deductions applied when a home's income is modelled, each between 0 and 10000 inclusive; `underwriting_yield_floor_bps` is the minimum underwritten yield an acquisition must clear; `disposition_yield_floor_bps` is the realized-yield line below which a home is flagged for disposition review; and `max_rent_concession_bps` is the deepest discount, in basis points of asking rent, that a lease's monthly rent may sit below the published asking rent. Each of those five is between 0 and 10000 inclusive.

Markets are readable individually and as a filterable list; the list read accepts a `code` filter alongside the standard pagination parameters.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Market, the Scope Catalogue and the Home Register

Before any home can be underwritten, a `PortfolioAdmin` registers the market whose policy will govern it, supplying every field described in the market policy section above. A second registration reusing an existing `code` is refused with `ERR_DUPLICATE_MARKET_CODE`.

The renovation programme is standardized through a catalogue of scope templates, also published by a `PortfolioAdmin`. Each template carries a `code` such as `PAINT_INT` or `HVAC_REPLACE` that must be unique across the catalogue — a duplicate is refused with `ERR_DUPLICATE_SCOPE_TEMPLATE_CODE` — plus a human-readable `name` and a `certification_code`, which is the trade certification token a vendor must hold before it can receive work of that kind. The template's `unit` states what the quantity means and is one of `HOME`, `SYSTEM`, `SQFT` or `EACH`. Its `benchmark_unit_cost_cents` is the national benchmark cost per unit in cents, at least 1, quoted *before* any market cost index is applied. `default_crew_size` and `default_crew_days` record the typical crew profile for the scope, each at least 1. Finally, `safety_critical` is a boolean that defaults to false; when it is true, the scope may never be fulfilled by the in-house technician bench and requires a certified vendor. Scope templates are immutable once published: there is no update capability, and correcting a benchmark means publishing a new template. The catalogue is readable individually and as a list filterable by `code`, by `certification_code` and by `safety_critical`.

Homes enter the register from the acquisition pipeline, added by an `AcquisitionAnalyst` or a `PortfolioAdmin`. The payload names the governing market through `market_id`, locates the property with `address_line1`, `city`, `state_code`, `postal_code`, and describes it with `bedrooms`, `bathrooms` (halves are permitted, so this is a numeric rather than an integer field, and it may not be negative), `square_feet` and `year_built`. The financial intake consists of `assessed_value_cents`, the current assessment used for property tax; `asking_rent_cents`, the published asking rent, which may be omitted and then defaults to the market's `rent_index_cents`; `insurance_carrier_name`, `insurance_annual_premium_cents` and `insurance_binder_expires_on` for the property insurance position; and the optional pair `hoa_name`, which defaults to the empty string when the home sits in no association, and `hoa_annual_cents`, which defaults to 0. A `market_id` that names no stored market is refused with `ERR_MARKET_NOT_FOUND`.

A newly registered home starts with `asset_status` `PIPELINE`, `occupancy_status` `VACANT`, `booked_showing_count` 0, `disposition_mode` `NONE`, `lot_code` the empty string, `bpo_value_cents` 0, `net_sale_proceeds_cents` 0, `realized_gain_cents` 0, `hold_sell_score_bps` 0 and `disposition_flagged` false. Its `property_tax_annual_cents` is computed immediately as the home's `assessed_value_cents` multiplied by the market's `millage_bps`, divided by 10,000 and rounded half up, and it is recomputed whenever `assessed_value_cents` changes for any reason. Its `leasing_posture` is derived at once, which for a pipeline home with a live binder and no blocking obligation yields `RESTRICTED`.

The mutable facts of a home can be revised later by an `AcquisitionAnalyst` or `PortfolioAdmin`: `asking_rent_cents`, `assessed_value_cents`, `insurance_carrier_name`, `insurance_annual_premium_cents`, `insurance_binder_expires_on`, `hoa_name` and `hoa_annual_cents` are each optional in that payload and only the supplied fields are overwritten. Neither state dimension nor any computed field may be written this way; `asset_status`, `occupancy_status` and every derived figure are ignored if a client sends them. Revising `assessed_value_cents` recomputes `property_tax_annual_cents`. Revising `insurance_binder_expires_on` recomputes `leasing_posture`, which is the quiet path by which an administrative correction can freeze a home and push its `AVAILABLE` showing windows to `BLOCKED_BY_POSTURE`, or renew a binder and release them back to `AVAILABLE`. Either way the home's `version` increments by 1 — an accepted revision always increments it by exactly 1, even when the payload supplies no field at all and nothing on the row actually changes. The register is readable one home at a time and as a list filterable by `market_id`, by `asset_status`, by `occupancy_status`, by `leasing_posture`, by `disposition_flagged` and by `lot_code` — the last of these being how a portfolio-lot buyer's asset list is assembled.

One further capability exists purely so that dated behaviour can be driven deterministically in testing: a `System` caller may advance or rewind the logical clock to a supplied `current_utc` instant, and any role may read the clock's present value. This is the only operation in the system exempt from the `X-User-ID` requirement.

### 3.2. Acquisition Underwriting and the Committee Cycle

An `AcquisitionAnalyst` opens an underwriting case against a home by naming it through `home_id`, proving it has observed the home's current state through `expected_home_version`, and supplying the deal terms: `purchase_price_cents` (at least 1), `acquisition_closing_costs_cents` (at least 0, covering title, transfer and diligence costs capitalized into basis), `estimated_monthly_rent_cents` (at least 1, the analyst's rent estimate), `turn_reserve_annual_cents` (at least 0, an annual make-ready reserve treated as an operating expense), and `planned_scope_lines`. That last field is an ordered array of at least one object, each object carrying a `scope_template_id` and a `quantity`; every `scope_template_id` must resolve to a published scope template or the create fails with `ERR_SCOPE_TEMPLATE_NOT_FOUND`. **The array order supplied by the analyst is significant** — it fixes the per-line rounding sequence described below.

Opening a case is also the supersede point. Every prior underwriting case on the same home whose `status` is `DRAFT`, `SUBMITTED` or `REVISION_REQUESTED` is moved to `SUPERSEDED` — the transitions `DRAFT` → `SUPERSEDED`, `SUBMITTED` → `SUPERSEDED` and `REVISION_REQUESTED` → `SUPERSEDED` — so a home has at most one live case at a time. The new case is created in `DRAFT` with `revision_round` 0 and both `submitted_by_user_id` and `decided_by_user_id` the empty string, and `decision_note` the empty string.

**Pricing the planned scope.** The planned renovation budget is produced by walking `planned_scope_lines` in the order supplied. For each line, the referenced scope template's `benchmark_unit_cost_cents` is multiplied by that line's `quantity` and by the home's market `cost_index_bps`, divided by 10,000, and rounded half up to whole cents. That per-line result is the line benchmark. `planned_renovation_budget_cents` is the sum of those already-rounded per-line results. The evaluation order here is mandatory and is not a matter of taste: applying the market cost index once to the sum of the raw unindexed line costs produces a different number, sometimes off by a single cent, and that figure is wrong. Consider a market whose `cost_index_bps` is 10250, with three lines — a floor scope at 475 cents per unit for 1150 units, an HVAC replacement at 612450 cents for one unit, and an interior paint at 285050 cents for one unit. Rounding per line gives 559906, 627761 and 292176 for a total of 1479843. Summing first and indexing once gives 1479844. The first figure is the one this API stores.

**The two yield variants.** A case is priced twice, by two variants of the same ten-step skeleton, each writing its own disjoint group of fields on the same row. The skeleton, evaluated in exactly this order, is: (1) the all-in basis is `purchase_price_cents` plus `acquisition_closing_costs_cents` plus a renovation figure; (2) gross potential rent is a monthly rent basis multiplied by twelve months; (3) the vacancy loss is gross potential rent multiplied by the market's `vacancy_loss_bps`, divided by 10,000, rounded half up; (4) the bad-debt loss is gross potential rent multiplied by the market's `bad_debt_bps`, divided by 10,000, rounded half up; (5) effective gross income is gross potential rent less the vacancy loss and less the bad-debt loss; (6) the management fee is effective gross income multiplied by the market's `mgmt_fee_bps`, divided by 10,000, rounded half up; (7) the annual property tax is the home's `assessed_value_cents` multiplied by the market's `millage_bps`, divided by 10,000, rounded half up; (8) total operating expenses are the management fee plus that property tax plus the home's `insurance_annual_premium_cents` plus the home's `hoa_annual_cents` plus the case's `turn_reserve_annual_cents`; (9) net operating income is effective gross income less total operating expenses; and (10) the yield on cost in basis points is net operating income multiplied by 10,000, divided by the all-in basis, rounded half up.

The **underwritten** variant is the forward-looking one. Its renovation figure is `planned_renovation_budget_cents` and its monthly rent basis is `estimated_monthly_rent_cents`. It writes `underwritten_all_in_basis_cents`, `underwritten_effective_gross_income_cents`, `underwritten_noi_cents` and `underwritten_yield_on_cost_bps`. It runs when a case is created, when a case is revised, and again when a case is submitted.

The **realized** variant is the retrospective one, and it applies only once the home has an `APPROVED` case and post-acquisition facts exist. Should a re-underwritten home end up carrying more than one `APPROVED` case, every recomputation of this variant — and the hold/sell refresh below — reads the **earliest-created** one, and only that case's realized group is ever written. Its renovation figure is the sum of `actual_cost_cents` over every work order whose `status` is `COMPLETED` and whose `project_id` names any renovation project of that home; work orders sitting in `VOIDED`, `PENDING_DISPATCH`, `DISPATCHED`, `ACCEPTED` or `IN_PROGRESS` contribute nothing to that sum. Its monthly rent basis is the `monthly_rent_cents` of the home's lease whose `status` is `EXECUTED`, falling back to the case's `estimated_monthly_rent_cents` when the home has no executed lease. Because step (7) reads `assessed_value_cents` at recomputation time, a resolved property-tax appeal that lowered the assessment feeds straight through into the realized yield. This variant writes `realized_renovation_cost_cents`, `realized_all_in_basis_cents`, `realized_noi_cents` and `realized_yield_on_cost_bps`. All four remain null until at least one work order on the home has reached `COMPLETED`; `realized_renovation_cost_cents` is the gate, and while it is null the other three are null too. The realized variant is re-run at exactly three kinds of moment: when the make-ready cascade of §3.5 reaches its fifth hop — which happens both when a work order completes and drives its project to rent-ready **and** when a void drains the project's live queue and drives it to rent-ready — when a lease is executed, and when a property-tax appeal resolution is accepted.

Downstream of the realized variant, two fields on the home are refreshed. `hold_sell_score_bps` is the case's `realized_yield_on_cost_bps` — or its `underwritten_yield_on_cost_bps` if the case has never yet been realized — minus the market's `disposition_yield_floor_bps`; it stays at its creation value of 0, with `disposition_flagged` false, while the home has no `APPROVED` case at all, because nothing refreshes the pair until an approved case exists. `disposition_flagged` is true exactly when that score is below zero, which is to say when the approved case's realized yield sits strictly below the market's disposition floor.

To make the divergence concrete: a home assessed at 28000000 cents with 180000 of annual insurance and 60000 of HOA dues, in a market with `vacancy_loss_bps` 500, `bad_debt_bps` 100, `mgmt_fee_bps` 800 and `millage_bps` 125, underwritten at a purchase price of 25000000, closing costs of 750000, a turn reserve of 120000, an estimated rent of 215000 and a planned budget of 1479843, yields a basis of 27229843, gross potential rent of 2580000, a vacancy loss of 129000, bad debt of 25800, effective gross income of 2425200, a management fee of 194016, property tax of 350000, operating expenses of 904016, net operating income of 1521184 and an underwritten yield of 559 basis points. The same case realized against three completed work orders costing 310000, 640000 and 570000 and an executed lease at 208000 a month yields a basis of 27270000 and a realized yield of 531 basis points — twenty-eight basis points below the underwritten figure on the same home.

**The submission and decision cycle.** A case sits in `DRAFT` until its analyst submits it, which requires the case to be in `DRAFT` and to carry at least one planned scope line — an empty scope set would be refused with `ERR_PROJECT_SCOPE_EMPTY`, which the create and rework payload rules make unreachable in practice — and which moves it `DRAFT → SUBMITTED` while stamping `submitted_by_user_id` from the caller's `X-User-ID`. Submission recomputes `planned_renovation_budget_cents` and the whole underwritten group *before* checking the yield floor, so a stale draft is never approved on stale numbers. If the recomputed `underwritten_yield_on_cost_bps` falls below the market's `underwriting_yield_floor_bps`, submission is refused with `ERR_YIELD_BELOW_FLOOR`. Continuing the example above, moving the purchase price to 30000000 and closing costs to 900000 against the same scope and rent gives a basis of 32379843 and a yield of 470 basis points, below a floor of 500, so the submission is refused.

The committee then records one of three decisions through a `decision` field carrying `APPROVE`, `REJECT` or `REQUEST_REVISION`, with an optional `decision_note` stored on the case. All three require the case to be in `SUBMITTED`, and all three require that the deciding `InvestmentCommittee` member's `X-User-ID` differs from the case's `submitted_by_user_id`; a self-decision is refused with `ERR_SEGREGATION_OF_DUTIES`. `APPROVE` additionally re-checks the yield floor and is refused with `ERR_YIELD_BELOW_FLOOR` if the underwritten yield sits below it.

An approval moves the case `SUBMITTED → APPROVED`, stamps `decided_by_user_id`, and cascades: the home advances `PIPELINE → ACQUIRED` and its `leasing_posture` is recomputed, which for both `PIPELINE` and `ACQUIRED` leaves it `RESTRICTED` unless some freezing input applies. The home's `occupancy_status` is untouched — the two dimensions advance independently. A rejection moves the case `SUBMITTED → REJECTED`, stamps `decided_by_user_id`, and cascades further: the home advances `PIPELINE → PASSED`, its posture becomes `FROZEN` because `PASSED` is a freezing asset state, and every showing window on that home whose `status` is `AVAILABLE` moves to `BLOCKED_BY_POSTURE`. Both of those asset hops are conditional on the home still sitting in `PIPELINE`: when the home of a re-underwritten case has already moved past `PIPELINE`, the decision leaves its `asset_status` and its `version` untouched and merely recomputes the posture. A revision request moves the case `SUBMITTED → REVISION_REQUESTED`, stores the `decision_note`, leaves `decided_by_user_id` at the empty string, and deliberately leaves the home's `asset_status`, its posture and its showing calendar alone. It is permitted only while `revision_round` is at most 1; once `revision_round` has reached 2 a third revision request is refused with `ERR_REVISION_LIMIT_EXCEEDED`.

Reworking a returned case moves it `REVISION_REQUESTED → DRAFT`, increments `revision_round` by 1, and clears `submitted_by_user_id` back to the empty string so the next submission re-stamps it. The rework payload may carry any of `purchase_price_cents`, `acquisition_closing_costs_cents`, `estimated_monthly_rent_cents`, `turn_reserve_annual_cents` and `planned_scope_lines`; each field present overwrites its stored counterpart and absent fields are left alone, after which `planned_renovation_budget_cents` and the entire underwritten group are recomputed immediately. This closes the cycle `SUBMITTED → REVISION_REQUESTED → DRAFT → SUBMITTED`, bounded to two loops.

`APPROVED`, `REJECTED` and `SUPERSEDED` are terminal: any submit, decision or rework attempted against a case in one of those states is refused with `ERR_INVALID_STATE`, as is a rework of a case that is not in `REVISION_REQUESTED` or a submit of a case that is not in `DRAFT`. Cases are readable individually — the read exposes both the underwritten and realized field groups — and as a list filterable by `home_id` and `status`.

### 3.3. Renovation and Turn Projects, the Budget Ledger and Work Orders

Once a home has been acquired, an `OperationsManager` opens the project that will make it rent-ready. The payload names the home through `home_id`, declares a `project_type` of either `ACQUISITION_RENOVATION` or `TURN`, and sets `approved_budget_cents`, a hard ceiling of at least 1 cent against which every work-order quote will be committed. A project can only be opened for a home that already has an underwriting case in `APPROVED`; if it has none, the request is refused with `ERR_CASE_NOT_APPROVED`. A home may not carry two live projects at once: if it already has a project whose `status` is `SCOPING` or `IN_PROGRESS`, the request is refused with `ERR_DUPLICATE_PROJECT_FOR_HOME`. A home whose earlier project already reached `RENT_READY` may, however, open a later `TURN` project — which will then have to satisfy the acquired-state check when its scope is locked.

A new project is created in `SCOPING` with `committed_cost_cents` 0, `budget_remaining_cents` equal to `approved_budget_cents`, `turn_started_on` and `rent_ready_on` the empty string, and every turn metric and holdback figure — `turn_days`, `overage_days`, `gross_turn_cost_cents`, `holdback_rate_bps`, `vendor_holdback_cents` and `net_turn_cost_cents` — carried as `null` until the project reaches rent-ready. A project's `approved_budget_cents` may be revised later by an `OperationsManager` or a `RegionalDirector`, which resets `budget_remaining_cents` to the new `approved_budget_cents` less the current `committed_cost_cents` and increments the project's `version` by 1. Lowering the budget below money already committed would break the conserved money identity, so a revision whose `approved_budget_cents` is less than `committed_cost_cents` is refused with `ERR_BUDGET_BELOW_COMMITTED`. A budget revision is otherwise accepted from any project status, `RENT_READY` included, because it moves no state dimension. Projects are readable individually and as a list filterable by `home_id`, `status` and `project_type`.

**Creating work.** Work orders are created by an `OperationsManager` and are the unit of field execution. Each names the property through `home_id` and the standardized scope through `scope_template_id`, and declares which programme it belongs to via `work_type`, one of `RENOVATION`, `TURN` or `RESIDENT_MAINTENANCE`. The `quantity` is expressed in the scope template's own unit and is at least 1. `crew_size` is the number of crew members required on each scheduled date and is at least 1. `scheduled_start_date` and `scheduled_end_date` bound the work window, inclusive at both ends, and the end may not precede the start. `fulfillment_channel` chooses between `IN_HOUSE` and `VENDOR`. `quoted_cost_cents`, at least 1, is the amount committed against the project budget. `project_id` is optional: standalone resident-maintenance work that is not part of any project leaves it as the empty string, and a `project_id` that names no stored project is refused with `ERR_RENOVATION_PROJECT_NOT_FOUND`. No consistency check couples the two references: the named project need not belong to the home named by `home_id`, and a work order that crosses them is accepted and commits against that project's budget just the same.

A new work order is created in `PENDING_DISPATCH` with `vendor_id` the empty string, `actual_cost_cents` 0, `completed_on` the empty string and `void_reason` the empty string. Two figures are computed at creation. `benchmark_total_cents` is the single-line benchmark for this work order's scope and quantity, computed exactly as a planned scope line is: the template's `benchmark_unit_cost_cents` multiplied by `quantity` and by the market's `cost_index_bps`, divided by 10,000, rounded half up. `variance_bps` is then the quoted cost less that benchmark, multiplied by 10,000, divided by the benchmark and rounded half up; it may be negative when the quote comes in below benchmark. `crew_days` is the conserved labour figure and equals `crew_size` multiplied by the number of whole days in the window counted inclusively at both ends — so a single-day work order has one window day, and two work orders sharing a single boundary date do overlap on that date.

Three fiscal and structural gates guard creation; they are numbered here for exposition only, and their relative precedence is the §2.7 ladder, in which the scope-lock check at rank 304 runs **ahead of** the variance check at rank 604 and the budget check at rank 606. A quote whose `variance_bps` is **strictly greater** than the market's `cost_variance_tolerance_bps` is refused with `ERR_COST_VARIANCE_EXCEEDED`; a variance landing exactly on the tolerance is accepted. Continuing the interior-paint example whose benchmark was 292176, a quote of 300000 gives 268 basis points and is accepted against a tolerance of 1000; a quote of 321394 gives exactly 1000 basis points and is still accepted; a quote of 330000 gives 1295 basis points and is refused. Second, when a `project_id` is supplied, the quote is added to the project's `committed_cost_cents` and subtracted from `budget_remaining_cents`; if the resulting committed total would be **strictly greater** than the project's `approved_budget_cents` the work order is refused with `ERR_PROJECT_BUDGET_EXCEEDED`, while landing exactly on the approved budget is allowed. Third, a project that has already reached `RENT_READY` accepts no further work orders and refuses them with `ERR_PROJECT_SCOPE_LOCKED`.

**Locking the scope.** When the scope set is complete, the `OperationsManager` locks it and starts the make-ready clock by supplying `turn_started_on`. Locking requires the project to be in `SCOPING`, requires at least one work order on the project whose `status` is one of `PENDING_DISPATCH`, `DISPATCHED`, `ACCEPTED`, `IN_PROGRESS` or `COMPLETED` — an empty or fully-voided scope set is refused with `ERR_PROJECT_SCOPE_EMPTY` — and requires the home's `asset_status` to be exactly `ACQUIRED`, otherwise `ERR_HOME_NOT_ACQUIRED`. A successful lock moves the project `SCOPING → IN_PROGRESS` and stores `turn_started_on`, then cascades in two further hops: the home advances `ACQUIRED → RENOVATING`, which recomputes its `leasing_posture` to `FROZEN` because `RENOVATING` is a freezing asset state; and because the recomputed posture is `FROZEN`, every showing window on that home whose `status` is `AVAILABLE` moves to `BLOCKED_BY_POSTURE`. Windows already `BOOKED` are left untouched.

A computed read exposes the project's benchmark arithmetic side by side with its naive alternative, so an operations manager can see exactly what the per-line rounding discipline costs or saves. It returns the `project_id`, a `line_count`, a `per_line_benchmark_cents` array holding each contributing work order's own benchmark in creation order, `scope_benchmark_total_cents` as the sum of those already-rounded per-line figures, `index_the_sum_total_cents` as the figure that would result from summing the raw unindexed line costs first and applying the market cost index once at the end, `quoted_total_cents` as the sum of `quoted_cost_cents` over the same contributing work orders, and the project's current `committed_cost_cents` and `budget_remaining_cents`. Work orders whose `status` is `VOIDED` do not contribute.

Work orders are readable individually and as a list filterable by `home_id`, `project_id`, `vendor_id`, `scope_template_id`, `status`, `work_type` and `fulfillment_channel`.

### 3.4. The Vendor Network, Trade Certification and Dispatch Selection

A `VendorManager` onboards each vendor into exactly one market. The payload carries `legal_name`, the serving `market_id`, `daily_crew_capacity` (at least 1 — the maximum number of crew members the vendor can field on any single calendar date across all of its non-terminal work), `cost_index_bps` (the vendor's price multiplier, between 5000 and 20000 inclusive), `quality_score_bps` (between 0 and 10000 inclusive) and `insurance_expires_on`, the date on which its general liability coverage lapses. A vendor is created with `status` `ACTIVE`, `committed_crew_days` 0 and `suspension_reason` the empty string.

Commercial terms move over time, so `daily_crew_capacity`, `cost_index_bps`, `quality_score_bps` and `insurance_expires_on` are each individually revisable by the `VendorManager`; only supplied fields are overwritten, `committed_crew_days` and `status` are never writable through that path, and the vendor's `version` increments by exactly 1 — even when the payload supplies no field at all and nothing on the row actually changes. Lowering `daily_crew_capacity` never retroactively invalidates work already dispatched or accepted — it only constrains the next dispatch. Suspension and reactivation are a separate capability that sets `status` to `ACTIVE` or `SUSPENDED` and stores a `suspension_reason`. That reason is itself optional: when it is supplied it is stored verbatim under either status, and when it is omitted a move to `ACTIVE` clears the stored reason back to the empty string while a move to `SUSPENDED` leaves whatever was already there untouched. The capability carries no state guard of its own — setting the `status` the vendor already holds is accepted and still increments its `version` by 1. A suspended vendor is excluded from automatic selection and may not be named explicitly on a dispatch, but work it has already accepted may still be completed. Vendors are readable individually — the read exposes the live `committed_crew_days` — and as a list filterable by `market_id` and `status`.

Trade qualification is recorded as dated certifications. A `VendorManager` creates one by naming `vendor_id` and the `certification_code`, and bounding it with `effective_on`, the first date on which it is honoured, and `expires_on`, the last date on which it is honoured; both bounds are inclusive and `expires_on` may not precede `effective_on`. A certification is created with `status` `ACTIVE`, and a vendor may not hold two active certifications for the same `certification_code` — a second attempt is refused with `ERR_DUPLICATE_CERTIFICATION`. Revoking a certification requires a `reason` and sets its `status` to `REVOKED`, which immediately disqualifies the vendor for that trade on future dispatches while leaving work already dispatched or accepted undisturbed. Certifications are readable individually and as a list filterable by `vendor_id`, `certification_code` and `status`.

**Dispatch.** The `OperationsManager` dispatches each work order, and the dispatch forks by channel. `vendor_id` is optional in the payload: supplying it names the vendor explicitly, while omitting it — or supplying it as the empty string, which is treated identically to omission and so is never looked up and never reported as `ERR_VENDOR_NOT_FOUND` — asks the system to select one.

On the `IN_HOUSE` branch the work order moves `PENDING_DISPATCH → IN_PROGRESS` directly, `vendor_id` stays the empty string, and no vendor capacity whatsoever is consumed. The branch requires that no `vendor_id` is supplied in the payload — one that is supplied anyway is refused with `ERR_INVALID_REQUEST` (400), naming the offending field — and requires that the work order's scope template is not `safety_critical`, a safety-critical scope on the in-house bench being refused with `ERR_IN_HOUSE_SAFETY_CRITICAL`. Those two are checked in that order, and both are branch checks reached only after the work order's own `PENDING_DISPATCH` state guard has passed, so an in-house dispatch attempted from any other status reports `ERR_INVALID_STATE` even when it also names a vendor or carries a safety-critical scope.

On the `VENDOR` branch the work order moves `PENDING_DISPATCH → DISPATCHED`, its `vendor_id` is set to the selected vendor, and that vendor's `committed_crew_days` increases by this work order's `crew_days`. Whether the vendor was named explicitly or selected automatically, it must satisfy **four** eligibility clauses, evaluated in exactly this order with only the first failure reported: its `status` must be `ACTIVE`, or the dispatch fails with `ERR_VENDOR_INACTIVE`; its `insurance_expires_on` must be on or after the current logical-clock date, or `ERR_VENDOR_INSURANCE_EXPIRED`; it must hold a certification whose `certification_code` equals the work order's scope template `certification_code`, whose `status` is `ACTIVE`, whose `effective_on` is on or before the clock date and whose `expires_on` is on or after the clock date, or `ERR_VENDOR_NOT_CERTIFIED`; and it must have room on every date of the work window, or `ERR_VENDOR_CAPACITY_EXCEEDED`. The market check is deliberately **not** one of those four. An explicitly supplied `vendor_id` whose vendor's `market_id` differs from the home's `market_id` is refused with `ERR_MARKET_MISMATCH` at rank 160, which sits ahead of the work order's own `PENDING_DISPATCH` state guard, ahead of the channel fork and ahead of all four eligibility clauses — so a cross-market vendor that is also suspended, or named on an `IN_HOUSE` work order, or named on a work order that has already left `PENDING_DISPATCH`, reports `ERR_MARKET_MISMATCH` and nothing else. Automatic selection can never raise it, because the candidate set is drawn from the home's market to begin with.

That last clause is a per-date capacity test, not an aggregate one. For **every** calendar date in the closed-inclusive window from `scheduled_start_date` through `scheduled_end_date`, the sum of `crew_size` over that vendor's **other** work orders whose `status` is `DISPATCHED` or `ACCEPTED` and whose own closed-inclusive windows contain that date, plus this work order's `crew_size`, must not exceed the vendor's `daily_crew_capacity`. The work order under test is always excluded from that sum — including the case where it is itself already `DISPATCHED` or `ACCEPTED` to the very vendor being tested, which is reachable through the computed ranking read below — so no row is ever counted against itself. If even one date fails, the dispatch is refused with `ERR_VENDOR_CAPACITY_EXCEEDED`. Because the windows are inclusive at both ends, a single shared boundary date is enough to cause a conflict: a vendor with a `daily_crew_capacity` of 4 already carrying a three-crew job from the 10th through the 12th cannot take a two-crew job running the 12th through the 14th, since the 12th would need 5. Rescoped to one crew member, the same job fits exactly at 4 and succeeds, taking `committed_crew_days` from 9 to 12; voiding it returns `committed_crew_days` to 9.

**Automatic selection.** When the payload omits `vendor_id`, the system builds the eligible set from every vendor in the home's market that passes all of the clauses above, then prices each one: the bid is this work order's `benchmark_total_cents` multiplied by that vendor's `cost_index_bps`, divided by 10,000, rounded half up. Ranking is applied in exactly this order — ascending bid first, then descending `quality_score_bps`, then ascending `created_at`, and finally, should two vendors carry the identical `created_at` instant, ascending order of insertion into the vendor register — and the first row wins. That fourth key makes the ranking total, so the winner is never left to chance. Price beats quality here: a cheaper vendor with a worse quality score is selected over a pricier vendor with a better one. Take a paint work order whose `benchmark_total_cents` is 292176: a vendor with `cost_index_bps` 9800 and `quality_score_bps` 8600 bids 286332, while a vendor with `cost_index_bps` 10100 and `quality_score_bps` 9400 bids 295098, and the first wins despite scoring 800 basis points worse on quality. Add a third vendor also at `cost_index_bps` 9800 but with `quality_score_bps` 9500 and its bid ties at 286332, so the quality tiebreak hands it the win; a fourth vendor with the same index and the same quality score created later loses on `created_at`. If the eligible set is empty, the dispatch is refused with `ERR_NO_ELIGIBLE_VENDOR`.

The same ranking is exposed read-only so an operations manager can inspect a dispatch before making it. That computed read returns the `work_order_id`, `eligible_vendor_ids` ordered by the ranking above, `bid_cents` positionally aligned with that array, `excluded_vendor_ids` listing every same-market vendor that failed the eligibility filter in vendor-register scan order — ascending `created_at` and then ascending insertion order, which is the order the candidate set is walked in, not any ranking order — `exclusion_reasons` positionally aligned with the exclusions where each entry is the error identifier of the **first** eligibility clause that vendor failed — one of `ERR_VENDOR_INACTIVE`, `ERR_VENDOR_INSURANCE_EXPIRED`, `ERR_VENDOR_NOT_CERTIFIED` or `ERR_VENDOR_CAPACITY_EXCEEDED` — and `winning_vendor_id`, which is the first eligible identifier or the empty string when the eligible set is empty. The read imposes no state or channel precondition of its own: it is answered for a work order in any `status`, it never consults `fulfillment_channel` and so will rank vendors for an `IN_HOUSE` work order that would never use them, and it reports the eligibility failures only inside `exclusion_reasons` rather than raising any of them as an error.

### 3.5. Work Execution, Voids, and the Make-Ready Cascade

A dispatched vendor accepts its assignment itself: the acting role is `Vendor` and its `X-User-ID` must equal the work order's `vendor_id`, otherwise the request is refused with `ERR_NOT_ASSIGNED_VENDOR`. Acceptance moves the work order `DISPATCHED → ACCEPTED` and changes no money and no capacity — the crew days were already committed at dispatch.

Completion is reported with `actual_cost_cents`, the amount actually incurred, and `completed_on`, the date the crew finished, which may not precede `scheduled_start_date` — an earlier date is refused with `ERR_COMPLETION_DATE_INVALID`. Completion is reachable from exactly two states, and `fulfillment_channel` alone decides which one is demanded: a vendor-channel work order is completed from `ACCEPTED`, and an in-house work order from `IN_PROGRESS`. Any other originating status is refused with `ERR_INVALID_STATE`. Both `Vendor` and `OperationsManager` are authorized on the endpoint, and the assigned-vendor identity check at rank 352 is applied **only when the acting role is `Vendor`**. Two consequences follow. An `OperationsManager` may close out a vendor-channel work order on the crew's behalf without being — and without needing to name — the assigned vendor, and the crew-day release below still runs on that completion. Conversely a `Vendor` calling against an in-house work order is always refused with `ERR_NOT_ASSIGNED_VENDOR`, because such a row's `vendor_id` is the empty string and can never equal an authenticated `X-User-ID`. The work order moves `ACCEPTED` → `COMPLETED` on the vendor channel or `IN_PROGRESS` → `COMPLETED` on the in-house channel, and stores both reported values. Crew capacity is released only on the vendor channel: the assigned vendor's `committed_crew_days` decreases by this work order's `crew_days`, restoring its availability for future dates. An in-house completion releases nothing, because nothing was ever committed. Note that money is **not** released on completion — the quoted amount stays committed against the project for the life of the work order, and `actual_cost_cents` is recorded alongside it rather than replacing it in the ledger.

**The make-ready cascade.** Completion is the trigger for the longest side-effect chain in the system, and it fires only when the completed work order belongs to a project and that completion drains the project's live queue. The condition has three parts: the project's own `status` must still be `IN_PROGRESS`, no work order on the project may remain in `PENDING_DISPATCH`, `DISPATCHED`, `ACCEPTED` or `IN_PROGRESS`, and at least one work order on the project must be `COMPLETED`. That first part is load-bearing in both directions. A project still in `SCOPING` — whose work orders may already have been dispatched, because dispatch never consults the project — does **not** cascade when its queue drains, since the make-ready clock was never started; and a project already in `RENT_READY` never cascades a second time. When all three parts hold, five hops run in order as one atomic unit:

1. The project moves `IN_PROGRESS → RENT_READY` and its `rent_ready_on` is stamped with the current logical-clock date.
2. The turn-holdback settlement runs, populating the project's `gross_turn_cost_cents`, `turn_days`, `overage_days`, `holdback_rate_bps`, `vendor_holdback_cents` and `net_turn_cost_cents` as described below.
3. The home advances `RENOVATING → STABILIZED`, which is the state in which it can be leased or sold. This hop is conditional on the home still sitting in `RENOVATING`: a home whose `asset_status` has since moved elsewhere keeps the status it has, and the two hops below still run.
4. The home's `leasing_posture` is recomputed. `STABILIZED` is not a freezing asset state, so — absent any blocking compliance obligation and with an insurance binder that has not expired — the posture leaves `FROZEN`, and every showing window on that home whose `status` is `BLOCKED_BY_POSTURE` returns to `AVAILABLE`. Windows that were `CANCELLED` stay cancelled, and windows that were `BOOKED` are untouched.
5. The `APPROVED` underwriting case of the home has its realized yield group recomputed off actual spend, which then refreshes `hold_sell_score_bps` and `disposition_flagged` — both of which, per §3.2, live on the **home** row rather than on the case. If the home carries no `APPROVED` case, this hop writes nothing at all.

If the project still has live work, only the work order itself changes; the project, the home, the calendar and the case are all untouched.

**The turn-holdback settlement.** This is the vendor-performance chargeback for a slow turn, and its eight steps run strictly in order.

1. `gross_turn_cost_cents` is the sum of `actual_cost_cents` over every work order on the project whose `status` is `COMPLETED`. Voided work orders contribute nothing.
2. `turn_days` is the number of whole days from `turn_started_on` inclusive to `rent_ready_on` exclusive — so a turn that starts and finishes on the same date is zero days.
3. `overage_days` is `turn_days` less the market's `make_ready_target_days`, floored at zero: a turn at or inside the target has no overage.
4. `holdback_rate_bps` is a flat tier selected by the overage band, not a per-day accrual. Zero overage days give a rate of 0. One, two or three overage days give 1000. Four, five, six or seven overage days give 2000. Eight or more overage days give 3000.
5. The raw holdback is `gross_turn_cost_cents` multiplied by `holdback_rate_bps`, divided by 10,000, rounded half up.
6. The cap is `gross_turn_cost_cents` multiplied by the market's `turn_holdback_cap_bps`, divided by 10,000, rounded half up. The cap is always computed against the **gross** turn cost, never against the raw holdback.
7. `vendor_holdback_cents` is the lesser of the raw holdback and the cap.
8. `net_turn_cost_cents` is `gross_turn_cost_cents` less `vendor_holdback_cents`.

Three worked settlements make the tiering and the cap concrete. Take a project whose completed work orders total a `gross_turn_cost_cents` of 1520000 in a market with a `make_ready_target_days` of 30 and a `turn_holdback_cap_bps` of 1500. If the turn ran 32 days, the overage is 2, which falls in the 1-to-3 band for a `holdback_rate_bps` of 1000; the raw holdback is 152000 and the cap is 228000, so the raw figure stands as `vendor_holdback_cents` and `net_turn_cost_cents` is 1368000. If instead the turn ran 34 days, the overage is 4, which crosses into the 4-to-7 band for a rate of 2000; the raw holdback is 304000, which exceeds the cap of 228000, so the cap binds — `vendor_holdback_cents` is 228000 and `net_turn_cost_cents` is 1292000. If the turn ran exactly 30 days, the overage is 0, the rate is 0, `vendor_holdback_cents` is 0 and `net_turn_cost_cents` equals the gross 1520000 untouched.

**Voiding work.** An `OperationsManager` may void a work order with a `void_reason` from any of `PENDING_DISPATCH`, `DISPATCHED`, `ACCEPTED` or `IN_PROGRESS`; a work order already `COMPLETED` or already `VOIDED` refuses the void with `ERR_INVALID_STATE`. A void moves the work order `PENDING_DISPATCH` → `VOIDED`, `DISPATCHED` → `VOIDED`, `ACCEPTED` → `VOIDED` or `IN_PROGRESS` → `VOIDED` as the case may be, and reverses its commitments asymmetrically. Money is always restored: if the work order named a `project_id`, that project's `committed_cost_cents` decreases by `quoted_cost_cents` and its `budget_remaining_cents` increases by the same amount, which is what makes the conserved money identity hold across voids. Crew days are restored only if they were ever taken — that is, only when the void happens from `DISPATCHED` or `ACCEPTED`, in which case the assigned vendor's `committed_crew_days` decreases by `crew_days`. A void from `PENDING_DISPATCH` releases no capacity because none was committed, and a void from `IN_PROGRESS` releases none because the in-house channel never consumes any. Finally, a void can itself drain the project's live queue: if after the void no work order on the project remains in `PENDING_DISPATCH`, `DISPATCHED`, `ACCEPTED` or `IN_PROGRESS` and at least one is `COMPLETED`, the full five-hop make-ready cascade above fires from the void just as it would from a completion.

### 3.6. Prospect Registration, Identity Verification and Dual-Variant Fraud Scoring

A prospect registers itself from the self-service portal — the acting role may be `Anonymous` or `LeasingAgent` — supplying `email` (which must be unique across all prospects, compared against every stored prospect by exact string equality with no case folding, trimming or other normalisation, a collision being refused with `ERR_DUPLICATE_PROSPECT_EMAIL`), `full_name`, `phone`, the governing `market_id`, `declared_monthly_income_cents` (at least 0), a `credit_tier` of `A`, `B`, `C` or `D`, and `prior_eviction_count`, which defaults to 0. Nothing has been proven at this point, so a new prospect is created with `identity_status` `UNVERIFIED`, `verification_attempt_count` 0, `verified_monthly_income_cents` 0, `document_type` `NONE`, `document_match_score_bps` 0, `selfie_liveness_pass` false, `device_reputation_bps` 0 and `ip_geo_distance_km` 0. Its `fraud_risk_score_bps` is nevertheless computed immediately, by the pre-verification variant described below, and `fraud_score_variant` is stamped `PRE_VERIFICATION`. Prospects are readable individually — the read exposes the live score and the variant that produced it — and as a list filterable by `market_id`, `identity_status` and `credit_tier`.

**Identity verification.** A verification attempt is submitted by `Anonymous` or by the `Prospect` itself — the endpoint runs no ownership comparison, so the acting `X-User-ID`, while it must still be present and non-empty, need not equal the `prospectId` in the path — and carries `expected_prospect_version` for the concurrency check described in §2.6, plus the full signal set: `document_type` (`NONE`, `DRIVERS_LICENSE`, `PASSPORT` or `STATE_ID`), `document_match_score_bps` and `device_reputation_bps`, each of which must fall inside the inclusive range 0 through 10000 rather than the wider basis-point range of §2.5, `selfie_liveness_pass`, `verified_monthly_income_cents` (at least 0) and `ip_geo_distance_km`, a whole non-negative count of kilometres. Every one of those six signals is mandatory — none is optional or defaulted — as is `expected_prospect_version`. Every supplied signal overwrites the stored one, `verification_attempt_count` increases by 1, and the prospect's `version` increases by 1. The outcome is a two-clause conjunction: `identity_status` becomes `VERIFIED` when `selfie_liveness_pass` is true **and** `document_match_score_bps` is at or above 5000, and becomes `REJECTED` otherwise. No separate verification-attempt resource is persisted — the attempt modifies the prospect row in place, so it is one of the modifying endpoints of §4 and responds with HTTP 200 carrying the updated prospect, rescored signals and all.

This dimension is deliberately cyclic and has no terminal state. The permitted transitions are `UNVERIFIED` → `VERIFIED`, `UNVERIFIED` → `REJECTED`, `REJECTED` → `VERIFIED` on a retry, `VERIFIED` → `REJECTED` when a later attempt fails, the self-loop `REJECTED` → `REJECTED` when a retry fails again, and the self-loop `VERIFIED` → `VERIFIED` when an already-verified prospect submits another passing attempt — the re-verification supersede case the version check guards. Every starting status therefore admits every outcome, and no verification attempt is ever refused with `ERR_INVALID_STATE`. Every one of those attempts rescores the prospect with the post-verification variant and stamps `fraud_score_variant` `POST_VERIFICATION`.

One transition carries a cascade. On a `VERIFIED → REJECTED` fall-back, every showing window whose `prospect_id` is this prospect and whose `status` is `BOOKED` returns to `AVAILABLE` with its `prospect_id` cleared, and each affected home's `booked_showing_count` decreases by 1 — one decrement per released window, so the count invariant continues to hold. No other verification outcome touches the calendar.

**The fraud score.** `fraud_risk_score_bps` is a weighted score in which higher means riskier, built from four factors whose weights sum to exactly 10,000: identity at 3500, income at 3000, history at 2000 and device at 1500. Every factor is clamped into the range 0 through 10,000 **before** it is weighted, the four weighted products are summed as raw integers, and the sum is divided by 10,000 and rounded half up exactly **once** at the very end — never per factor.

Two factors are shared by both variants. The income coverage denominator is the market's `rent_index_cents` multiplied by 3, and the income factor is 10,000 less the quantity (income multiplied by 10,000, divided by that denominator, rounded half up), floored at zero — so an applicant earning three times the market rent index or more scores a risk-free zero on income. The history factor is the credit-tier risk points — 500 for `A`, 1500 for `B`, 3000 for `C`, 5000 for `D` — plus `prior_eviction_count` multiplied by 2500, capped at 10,000.

The two variants differ in which income figure they trust and in how much they can say about identity and device. The **pre-verification** variant applies when `verification_attempt_count` is 0 — that is, at registration. It uses `declared_monthly_income_cents` as the income, and because nothing has been proven it hard-codes the identity factor at 10,000 and the device factor at 7000. The **post-verification** variant applies once `verification_attempt_count` is 1 or more, at every verification attempt. It uses `verified_monthly_income_cents` as the income. Its identity factor is 10,000 whenever `selfie_liveness_pass` is false — a liveness failure overrides the document score entirely, however good that score is — and otherwise is 10,000 less `document_match_score_bps`, floored at zero. Its device factor is 10,000 less `device_reputation_bps`, floored at zero, plus a penalty of 2000 when `ip_geo_distance_km` is **strictly greater** than 100, the whole sum capped at 10,000.

Worked through, in a market whose `rent_index_cents` is 210000 the income coverage denominator is 630000 and the `fraud_block_threshold_bps` is 6000. A prospect declaring 700000 with credit `B` and no evictions scores identity 10000, income 0 (since the raw coverage figure of 11111 exceeds 10,000 and the factor floors), history 1500 and device 7000, which weighs out to 35000000 plus 0 plus 3000000 plus 10500000, or 48500000, and after the single final division 4850 basis points. The same prospect then verifies with a document score of 9200, liveness true, a verified income of 560000, a device reputation of 8800 and 15 km of geo distance: identity becomes 800, income becomes 1111, history stays 1500, device becomes 1200, and the score falls to 1093 basis points — 3757 basis points of divergence between the two variants for the same person in the same market, which is exactly why the variant that produced a score is recorded alongside it.

A second prospect declaring 250000 with credit `D` and one eviction scores identity 10000, income 6032, history 7500 and device 7000, weighing out to 78596000, which divided by 10,000 gives 7859.6 and rounds half up to 7860. After verifying with a document score of 6000, liveness true, a verified income of 240000, a device reputation of 3000 and 400 km of distance, its factors are identity 4000, income 6190, history 7500 and device 9000 (7000 plus the 2000 geo penalty), for 6107 basis points — a prospect that is genuinely `VERIFIED` and yet still above the market's threshold of 6000, so its bookings are refused with `ERR_PROSPECT_FRAUD_BLOCKED`. Verification and fraud are independent gates. A third prospect, verified with a document score of 6000, liveness true, a verified income of 157500, credit `D`, no evictions, a device reputation of 3000 and 400 km, has factors identity 4000, income 7500, history 5000 and device 9000, weighing out to 14000000 plus 22500000 plus 10000000 plus 13500000 and giving exactly 6000 basis points — landing exactly on the threshold, which is allowed. A fourth, verified with a document score of 9600, liveness true, a verified income of 800000, credit `A`, no evictions, a device reputation of 9200 and 5 km, has identity 400, income 0 (clamped up from a raw negative), history 500 and device 800, for 360 basis points. And a fifth, submitting a document score of 9200 but a failed liveness check with a verified income of 560000, credit `B`, no evictions, a device reputation of 8800 and 15 km, has identity 10000 by the liveness override rather than 800, income 1111, history 1500 and device 1200, for 4313 basis points — and an `identity_status` of `REJECTED`.

### 3.7. The Self-Showing Calendar

A `LeasingAgent` publishes each self-showing window on a home's access calendar, naming `home_id`, bounding the window with `starts_at`, which is inclusive, and `ends_at`, which is exclusive, and choosing the `access_mode` a prospect will use to enter: `SMART_LOCK`, `LOCKBOX` or `AGENT_ESCORT`. A window is created with `status` `AVAILABLE` and both `prospect_id` and `cancel_reason` the empty string.

Three calendar rules guard publication, and they are checked in this order. A window whose length in whole minutes is less than the market's `min_showing_duration_minutes` is refused with `ERR_SLOT_DURATION_INVALID`. A window whose `starts_at` is before the current logical-clock instant is refused with `ERR_SLOT_IN_PAST`. And a window that collides with the existing calendar is refused with `ERR_SHOWING_SLOT_OVERLAP`. The collision test considers, on the same `home_id`, every existing window whose `status` is `AVAILABLE`, `BOOKED` or `BLOCKED_BY_POSTURE`, and fails if that window's half-open interval from `starts_at` inclusive to `ends_at` exclusive either overlaps the new interval, or is separated from it by **strictly fewer** than `showing_buffer_minutes` whole minutes on either side — the buffer being the lockbox re-code interval that must follow and precede every tour. Because the intervals are half-open, a new window beginning exactly when an existing one ends does not overlap, though it must still clear the buffer. Windows whose `status` is `CANCELLED` are ignored entirely, which is what lets a withdrawn window's interval be reused.

**Booking.** A prospect books for itself: the acting role is `Prospect`, the payload names `prospect_id`, and `X-User-ID` must equal that identifier or the request is refused with `ERR_NOT_SLOT_OWNER`. Booking requires the window's `status` to be `AVAILABLE`, and a window that is `BOOKED`, `BLOCKED_BY_POSTURE` or `CANCELLED` is refused with `ERR_SHOWING_SLOT_NOT_AVAILABLE`. It requires the prospect's `market_id` to equal the home's `market_id`, otherwise `ERR_MARKET_MISMATCH`. It requires the prospect's `identity_status` to be exactly `VERIFIED`, otherwise `ERR_PROSPECT_IDENTITY_UNVERIFIED`, and its `fraud_risk_score_bps` to be at or below the market's `fraud_block_threshold_bps`, a strictly greater score being refused with `ERR_PROSPECT_FRAUD_BLOCKED`. Finally it requires the home's `leasing_posture` to be `OPEN` or `RESTRICTED`; a `FROZEN` home refuses the booking with `ERR_HOME_SHOWINGS_BLOCKED`. Those six guards are evaluated in the rank order of §2.7 rather than the order narrated here — market mismatch first, then the slot state, then slot ownership, then identity, then fraud, then posture — so a booking placed by the wrong prospect on a slot that is already `BOOKED` reports `ERR_SHOWING_SLOT_NOT_AVAILABLE`, and one placed into the wrong market reports `ERR_MARKET_MISMATCH` whatever else is wrong with it. A successful booking moves the window `AVAILABLE → BOOKED`, stores the `prospect_id`, and increases the home's `booked_showing_count` by 1.

**Cancelling.** Cancellation takes a `reason` and behaves differently depending on where it starts from and who calls it. From `BOOKED` the window returns `BOOKED` → `AVAILABLE`, its `prospect_id` is cleared, the `reason` is stored in `cancel_reason`, and the home's `booked_showing_count` decreases by 1, restoring the count invariant; the acting role may be the booking `Prospect`, whose `X-User-ID` must equal the stored `prospect_id`, or a `LeasingAgent`. From `AVAILABLE` only a `LeasingAgent` may act — a `Prospect` reaching that branch is refused with `ERR_NOT_SLOT_OWNER`, because an unbooked window carries no `prospect_id` for its `X-User-ID` to match — and the window goes `AVAILABLE` → `CANCELLED` with the `reason` stored — a terminal withdrawal after which the interval no longer occupies the home's showing calendar, so a new window may be published over it. `CANCELLED` is the only terminal state on this dimension; `AVAILABLE` and `BLOCKED_BY_POSTURE` cycle back and forth as the home's posture changes, as described in §2.8.

Windows are readable individually and as a list filterable by `home_id`, `prospect_id`, `status` and `access_mode`.

### 3.8. Screening, the Deposit Stack and Lease Execution

An application is submitted by the `Prospect` itself or by a `LeasingAgent` and names `prospect_id`, `home_id` and `requested_move_in_date`. `lease_term_months` carries the requested term, must be at least 1 when it is supplied, and defaults to the market's `standard_lease_term_months` when omitted. `pet_count` defaults to 0, and `pet_breeds` is an array of uppercase breed tokens that defaults to empty. The application is created in `SUBMITTED` with `rent_to_income_bps`, `security_deposit_cents`, `pet_deposit_cents`, `total_move_in_deposit_cents` and `risk_multiplier_bps` all 0 and `adverse_action_reason` `NONE`.

Four intake rules guard submission. The prospect's `identity_status` must be exactly `VERIFIED`, otherwise `ERR_PROSPECT_IDENTITY_UNVERIFIED`. The prospect's `market_id` must equal the home's `market_id`, otherwise `ERR_MARKET_MISMATCH`. No declared breed may appear in the market's `restricted_breeds` list, otherwise `ERR_RESTRICTED_BREED`. And the pet declaration must be internally consistent and within policy: `ERR_PET_COUNT_EXCEEDED` is raised when `pet_count` is greater than the market's `max_pets` **or** when the length of `pet_breeds` is not equal to `pet_count`, so two pets must be named by two breed tokens. Those four run in the rank order of §2.7 rather than the order narrated here — market mismatch first, then identity, then breed, then pet count. Ahead of all four, immediately after the home and prospect lookups, comes the duplicate guard: the same prospect may not have two live applications on the same home, so a second application for the same `prospect_id` and `home_id` while one is still `SUBMITTED` is refused with `ERR_DUPLICATE_APPLICATION` at rank 158 — a duplicate submitted by an unverified prospect, into the wrong market, with a restricted breed still reports `ERR_DUPLICATE_APPLICATION`. Applications are readable individually and as a list filterable by `prospect_id`, `home_id`, `status` and `adverse_action_reason`.

**Screening.** A `LeasingAgent` runs screening on a `SUBMITTED` application; the call carries no payload because every input is already stored. Screening requires the home's `occupancy_status` to be exactly `VACANT`, otherwise `ERR_HOME_NOT_VACANT`, and the home's `leasing_posture` not to be `FROZEN`, a frozen home being refused with `ERR_HOME_SHOWINGS_BLOCKED`.

First, `rent_to_income_bps` is computed as the home's `asking_rent_cents` multiplied by 10,000, divided by the prospect's `verified_monthly_income_cents`, rounded half up. A `VERIFIED` prospect may still carry a `verified_monthly_income_cents` of 0, since a passing liveness check and a document score at or above 5000 say nothing about income; rather than divide by zero, the ratio in that case is pinned at the sentinel value 1000000000 and stored on the application as such. Being far above any permitted `rent_to_income_max_bps`, that sentinel fires clause 3 below unless clause 1 or clause 2 fires first. Then the decision is taken by the **first matching clause** of five, and that order is load-bearing:

1. If the prospect's `fraud_risk_score_bps` is **strictly greater** than the market's `fraud_block_threshold_bps`, the application is `DENIED` with `adverse_action_reason` `FRAUD_RISK`.
2. Otherwise, if the prospect's `prior_eviction_count` is 2 or more, it is `DENIED` with `adverse_action_reason` `EVICTION_HISTORY`.
3. Otherwise, if `rent_to_income_bps` is **strictly greater** than the market's `rent_to_income_max_bps`, it is `DENIED` with `adverse_action_reason` `RENT_TO_INCOME`. A ratio landing exactly on the ceiling does not fire this clause and falls through.
4. Otherwise, if the `credit_tier` is `A` **and** `prior_eviction_count` is 0 **and** `rent_to_income_bps` is at or below 3000, the application is `APPROVED` with a `risk_multiplier_bps` of 10000.
5. Otherwise the application is `CONDITIONAL_APPROVED` with a `risk_multiplier_bps` selected by credit tier: 15000 for `A`, 15000 for `B`, 20000 for `C` and 25000 for `D`.

Because clause 1 precedes clause 3, an applicant who is both over the fraud threshold and over the rent-to-income ceiling is denied for `FRAUD_RISK`, never for `RENT_TO_INCOME`.

The side-effect sets of the three outcomes diverge sharply. On `DENIED`, `security_deposit_cents`, `pet_deposit_cents`, `total_move_in_deposit_cents` and `risk_multiplier_bps` are all set to 0 and the **home is not touched at all** — its `occupancy_status` stays `VACANT` and remains available to the next applicant. On `APPROVED` or `CONDITIONAL_APPROVED` the deposit stack is built: `security_deposit_cents` is the home's `asking_rent_cents` multiplied by `risk_multiplier_bps`, divided by 10,000, rounded half up; `pet_deposit_cents` is the lesser of `pet_count` multiplied by the market's `pet_deposit_per_pet_cents` and the market's `pet_deposit_cap_cents`; and `total_move_in_deposit_cents` is their sum, which is the amount a lease must collect before it can be executed. Both approval outcomes then cascade the home's `occupancy_status` `VACANT` → `RESERVED`. The application itself moves `SUBMITTED` → `APPROVED`, `SUBMITTED` → `CONDITIONAL_APPROVED` or `SUBMITTED` → `DENIED` according to the clause that fired.

Worked through in a market whose `rent_to_income_max_bps` is 4000, `fraud_block_threshold_bps` is 6000, `pet_deposit_per_pet_cents` is 30000 and `pet_deposit_cap_cents` is 50000, against a home whose `asking_rent_cents` is 215000: an applicant with a verified income of 560000, credit `B`, no evictions, a fraud score of 1093 and one pet has a `rent_to_income_bps` of 3839, misses clauses 1 through 4 on the credit tier alone, and lands in clause 5 as `CONDITIONAL_APPROVED` with a multiplier of 15000, a `security_deposit_cents` of 322500, a `pet_deposit_cents` of 30000 and a `total_move_in_deposit_cents` of 352500. The same applicant declaring two pets has a raw pet deposit of 60000, which the cap pulls down to 50000, for a total of 372500. An applicant with a verified income of 800000, credit `A`, no evictions, a fraud score of 360 and no pets has a `rent_to_income_bps` of 2688 — the raw quotient being 2687.5 and rounding half up — and satisfies clause 4, so it is `APPROVED` with a multiplier of 10000, a `security_deposit_cents` of 215000, no pet deposit and a total of 215000. On the boundary, a verified income of 537500 gives a ratio of exactly 4000, which does not fire clause 3 and so lands in clause 5 as `CONDITIONAL_APPROVED`, whereas a verified income of 537000 gives 4004 and is `DENIED` for `RENT_TO_INCOME`.

**Drafting the lease.** A `LeasingAgent` or a `RegionalDirector` drafts the lease, naming the `application_id` and supplying `start_date`, `term_months` and `monthly_rent_cents`, which must be at least 1. The lease is created in `DRAFT` with its `home_id` copied from the application, its `required_deposit_cents` copied from the application's `total_move_in_deposit_cents`, `deposit_paid_cents` 0, and `signed_on` and `void_reason` the empty string. The referenced application's `status` must be `APPROVED` or `CONDITIONAL_APPROVED`, otherwise `ERR_APPLICATION_NOT_APPROVED`; the application's home must not already carry a lease whose `status` is `DRAFT` or `EXECUTED`, otherwise `ERR_LEASE_ALREADY_EXISTS`; the `monthly_rent_cents` must not fall below the market's concession floor, which is the home's `asking_rent_cents` less the quantity (`asking_rent_cents` multiplied by the market's `max_rent_concession_bps`, divided by 10,000, rounded half up), a deeper discount being refused with `ERR_RENT_CONCESSION_EXCEEDED`; and `term_months` must equal the market's `standard_lease_term_months` unless the acting role is `RegionalDirector`, who alone may write a non-standard term — anyone else attempting one is refused with `ERR_LEASE_TERM_INVALID`. Leases are readable individually — the read exposes the deposit funding position — and as a list filterable by `application_id`, `home_id` and `status`.

**Funding the deposit.** A `LeasingAgent` records each move-in deposit payment as an `amount_cents` figure of at least 1 that accumulates into `deposit_paid_cents` and increments the lease's `version` by 1. This is a funding ledger entry only: the lease stays in `DRAFT` no matter how much has been paid, and reaching the required amount never executes it. A payment that would take `deposit_paid_cents` plus `amount_cents` **strictly above** `required_deposit_cents` is refused with `ERR_DEPOSIT_OVERPAYMENT`, so the funding position can land exactly on the requirement but never overshoot it.

**Executing the lease.** A `LeasingAgent` executes the lease with a `signed_on` date, moving it `DRAFT → EXECUTED`. Execution demands the strictest gate in the system: the home's `leasing_posture` must be exactly `OPEN`, and anything else — including merely `RESTRICTED` — is refused with `ERR_HOME_LEASING_FROZEN`. It also demands full funding: `deposit_paid_cents` must be at or above `required_deposit_cents`, otherwise `ERR_DEPOSIT_NOT_FUNDED`. When both conditions fail at once, the posture failure is reported: a lease on a `RESTRICTED` home that is also short on deposit reports `ERR_HOME_LEASING_FROZEN`. Execution cascades three ways: the home's `occupancy_status` moves `RESERVED → OCCUPIED`; every showing window on that home whose `status` is `AVAILABLE` moves `AVAILABLE` → `CANCELLED` with `cancel_reason` set to `HOME_LEASED`, since a leased home holds no more tours; and the home's `APPROVED` underwriting case has its realized field group recomputed off the executed `monthly_rent_cents` rather than the home's `asking_rent_cents`, which in turn refreshes `hold_sell_score_bps` and `disposition_flagged`.

**Voiding a draft.** A `LeasingAgent` or a `RegionalDirector` may void a lease that is still in `DRAFT` by supplying a `reason`, which is stored in `void_reason` and moves the lease to `VOIDED`. That is the transition `DRAFT` → `VOIDED`, and its compensating cascade returns the home's `occupancy_status` `RESERVED` → `VACANT`, so the home can be re-reserved by another application. `EXECUTED` and `VOIDED` are both terminal: neither a void nor an execution may be applied to a lease already in either state, and such an attempt is refused with `ERR_INVALID_STATE`.

### 3.9. Compliance Obligations, Property Tax Appeals and Disposition

A `ComplianceOfficer` opens an obligation against a home, naming `home_id`, an `obligation_type` of `HOA_VIOLATION`, `INSURANCE_DEFICIENCY` or `PROPERTY_TAX_APPEAL`, a `severity` of `MINOR`, `MAJOR` or `CRITICAL`, a narrative `description`, and the `due_on` date by which it must be resolved. Three fields are supplied only for tax appeals: `assessed_value_cents`, the appeal's starting basis, which is required for `PROPERTY_TAX_APPEAL` and 0 for the other two types — it is recorded for the file only, since the savings computation at acceptance reads the home's own `assessed_value_cents` rather than this copy; `target_value_cents`, the value the appeal seeks, likewise required for `PROPERTY_TAX_APPEAL` and 0 otherwise; and `consultant_fee_bps`, the contingency fee in basis points that the appeal consultant will take from the annual savings, defaulting to 0 and, unlike the two value fields, stored exactly as supplied whatever the obligation type. Those two conditional requirements are enforced at rank 10, so an appeal that omits either value is refused with `ERR_INVALID_REQUEST` before the role and principal checks of §2.1 are reached; a value supplied on an obligation of either other type is discarded and stored as 0 rather than rejected. `supersedes_obligation_id` optionally names the prior-cycle obligation this one renews and is the empty string on a first cycle. The obligation is created in `OPEN` with `resolution_round` 0, `submitted_by_user_id`, `planned_resolution_on` and `evidence_ref` the empty string, and `settled_value_cents`, `annual_tax_savings_cents`, `consultant_fee_cents` and `net_tax_benefit_cents` all 0.

Creation immediately recomputes the home's `leasing_posture`: a `CRITICAL` obligation drives the posture to `FROZEN` and therefore moves every `AVAILABLE` showing window on that home to `BLOCKED_BY_POSTURE`; a `MAJOR` obligation drives it to `RESTRICTED`, which leaves the calendar alone; and a `MINOR` obligation changes nothing at all. Obligations are readable individually — the read exposes the tax-appeal economics — and as a list filterable by `home_id`, `supersedes_obligation_id`, `work_order_id`, `obligation_type`, `severity` and `status`.

**Planning the cure.** A `ComplianceOfficer` commits a cure plan by supplying `planned_resolution_on` and optionally `work_order_id`, the remediation work order that will do the field work; it stays the empty string when the cure needs none, and an omitted `work_order_id` on a re-plan leaves whatever work order is already linked in place rather than clearing it. Planning moves the obligation `OPEN → PLANNED`, or `RESOLUTION_REJECTED → PLANNED` with `resolution_round` increased by 1 — that counter records how many rejected-and-replanned cure rounds the obligation has been through. A `planned_resolution_on` after the `due_on` is refused with `ERR_OBLIGATION_PAST_DUE`, and a `work_order_id` naming a work order that belongs to a different home or whose `status` is `VOIDED` is refused with `ERR_OBLIGATION_WORK_ORDER_MISMATCH`.

**Submitting the resolution.** A `ComplianceOfficer` submits for review with `evidence_ref` and `settled_value_cents`, both optional in the payload because which one is mandatory depends on the type. The obligation moves `PLANNED → RESOLUTION_SUBMITTED` and its `submitted_by_user_id` is stamped from the caller's `X-User-ID`, which is what the segregation-of-duties check will read at review. A `PROPERTY_TAX_APPEAL` requires a `settled_value_cents` that is present, at least 1, and no greater than the home's `assessed_value_cents`; anything else is refused with `ERR_SETTLED_VALUE_INVALID`. A settlement exactly equal to the home's `assessed_value_cents` is accepted and simply yields zero savings and a zero fee. An obligation whose type is `HOA_VIOLATION` or `INSURANCE_DEFICIENCY` instead requires a non-empty `evidence_ref`, and an absent or empty one is refused with `ERR_EVIDENCE_REQUIRED`. The field each type does not require is still accepted when supplied: an `evidence_ref` sent with an appeal is stored on the obligation, while a `settled_value_cents` sent with either other type is ignored and `settled_value_cents` stays 0.

**Reviewing the resolution.** Review is performed by a `ComplianceOfficer` or a `RegionalDirector` and carries a `decision` of `ACCEPT`, `REJECT` or `WAIVE` plus an optional `review_note`, which is accepted for the reviewer's narrative but is not persisted on the obligation and appears in no response field. Because this is the segregation-of-duties control, the reviewer may not be the submitter: a caller whose `X-User-ID` equals the obligation's `submitted_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES`.

`REJECT` moves the obligation `RESOLUTION_SUBMITTED` → `RESOLUTION_REJECTED` and clears `submitted_by_user_id`, reopening the cure cycle so it can be planned again for another round. `WAIVE` moves it `RESOLUTION_SUBMITTED` → `WAIVED` and is permitted only for an obligation whose `obligation_type` is `HOA_VIOLATION` and whose `severity` is `MINOR` or `MAJOR`; a `CRITICAL` obligation of any type, or an obligation of any severity whose type is `INSURANCE_DEFICIENCY` or `PROPERTY_TAX_APPEAL`, is refused with `ERR_CRITICAL_OBLIGATION_NOT_WAIVABLE`. `ACCEPT` moves it `RESOLUTION_SUBMITTED` → `RESOLVED`. Only `REJECT` clears `submitted_by_user_id`; `ACCEPT` and `WAIVE` leave it on the row as the audit record of who submitted. Every one of the three branches recomputes the home's `leasing_posture`, since `RESOLVED` and `WAIVED` obligations both stop blocking, and may therefore move `BLOCKED_BY_POSTURE` windows back to `AVAILABLE`.

**The tax-appeal cascade.** When the accepted obligation's `obligation_type` is `PROPERTY_TAX_APPEAL`, acceptance runs four further hops in order.

1. `annual_tax_savings_cents` is the home's `assessed_value_cents` **as it stands at the moment of acceptance** less the obligation's `settled_value_cents`, multiplied by the market's `millage_bps`, divided by 10,000, rounded half up. `consultant_fee_cents` is `annual_tax_savings_cents` multiplied by `consultant_fee_bps`, divided by 10,000, rounded half up — the fee is a share of the **savings**, not of the assessment reduction. `net_tax_benefit_cents` is `annual_tax_savings_cents` less `consultant_fee_cents`.
2. The home's `assessed_value_cents` is overwritten with the obligation's `settled_value_cents`, and its `property_tax_annual_cents` is recomputed as the new `assessed_value_cents` multiplied by `millage_bps`, divided by 10,000, rounded half up.
3. Because the tax line moved, the home's `APPROVED` underwriting case has its `realized_noi_cents` and `realized_yield_on_cost_bps` recomputed.
4. Because the realized yield moved, the home's `hold_sell_score_bps` and `disposition_flagged` are recomputed against the market's `disposition_yield_floor_bps`.

Worked through: a home assessed at 28000000 in a market whose `millage_bps` is 125 carries a `property_tax_annual_cents` of 350000. The appeal settles at 24800000 with a `consultant_fee_bps` of 3000, so the reduction is 3200000, the `annual_tax_savings_cents` is 40000, the `consultant_fee_cents` is 12000 and the `net_tax_benefit_cents` is 28000. The home's `assessed_value_cents` becomes 24800000 and its `property_tax_annual_cents` becomes 310000. The case's `realized_noi_cents` rises from 1448541 to 1488541 and its `realized_yield_on_cost_bps` from 531 to 546, so against a `disposition_yield_floor_bps` of 540 the home's `hold_sell_score_bps` moves from −9 to 6 and its `disposition_flagged` flips from true to false — a successful tax appeal is what takes a home off the disposition watch list.

**Disposition.** The `InvestmentCommittee` decides disposition in two steps, both through the same capability, distinguished by a `decision` of `APPROVE_SALE` or `CLOSE_SALE`, with `disposition_mode`, `bpo_value_cents`, `lot_code` and `net_sale_proceeds_cents` all optional in the payload because each belongs to only one of the two steps.

`APPROVE_SALE` moves the home `STABILIZED → DISPOSITION_APPROVED` and stores the payload's `disposition_mode` (`NONE`, `INDIVIDUAL` or `PORTFOLIO_LOT`), `bpo_value_cents` and `lot_code`, the last being the empty string for an `INDIVIDUAL` sale — an omitted `disposition_mode` is stored as `NONE`, an omitted `bpo_value_cents` leaves the stored figure as it stands, and a `lot_code` that is actually supplied is stored verbatim whatever the mode. It requires the home's `leasing_posture` not to be `FROZEN`, a frozen home being refused with `ERR_DISPOSITION_NOT_ELIGIBLE`, and that posture test runs before the occupancy test that follows. Its occupancy requirement depends on the mode and is the clearest expression of the two dimensions being independent: an `INDIVIDUAL` sale requires the home's `occupancy_status` to be `VACANT`, and anything else is refused with `ERR_DISPOSITION_NOT_ELIGIBLE`, whereas a `PORTFOLIO_LOT` sale is permitted at any `occupancy_status` including `RESERVED` and `OCCUPIED`, because an investor buying a lot of houses is buying the leases with them. Approval deliberately leaves `occupancy_status` alone — an occupied home in a portfolio lot stays occupied.

`CLOSE_SALE` moves the home `DISPOSITION_APPROVED → DISPOSED` and requires `net_sale_proceeds_cents` to be present in the payload. It stores that figure and computes `realized_gain_cents` as `net_sale_proceeds_cents` less the basis, where the basis is the `APPROVED` underwriting case's `realized_all_in_basis_cents` when that field is non-null and its `underwritten_all_in_basis_cents` otherwise — so a home sold out of the pipeline before any renovation actually happened is measured against its underwritten basis, and a home carrying no `APPROVED` case at all is measured against a basis of 0 so that its `realized_gain_cents` is simply the proceeds. `CLOSE_SALE` imposes no posture and no occupancy requirement of its own, and leaves `occupancy_status`, `disposition_mode`, `bpo_value_cents` and `lot_code` exactly as `APPROVE_SALE` left them. `DISPOSED` is a freezing asset state, so the home's `leasing_posture` becomes `FROZEN` and every showing window on the home whose `status` is `AVAILABLE` moves to `BLOCKED_BY_POSTURE`. `PASSED` and `DISPOSED` are both terminal on the asset dimension: no further asset transition is accepted from either, and an attempt is refused with `ERR_INVALID_STATE`.

## 4. API Endpoints

Every endpoint is rooted at the API root and every request carries the `X-User-ID` and `X-User-Role` headers described in §2.1, with the single exception of the clock-setting endpoint, which is exempt from the `X-User-ID` requirement. Endpoints that create a new resource return HTTP 201 with the created resource in the `data` field. Endpoints that read, list or modify an existing resource return HTTP 200 with the resource, the array of resources, or the computed object in the `data` field. Failures return the error envelope of §2.2 with the status code listed for that error identifier in §5. A request to a path this table does not declare, or to a declared path under a method that path does not offer, is answered with the same error envelope carrying `error_id` `ERR_INVALID_REQUEST` under the status the transport failure produced — 404 for the unknown path and 405 for the unsupported method — rather than under the 400 listed for that identifier in §5. List endpoints accept the `limit` and `offset` query parameters of §2.3 in addition to the filters named in their descriptions.
