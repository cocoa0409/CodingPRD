# Fiber Route Engineering & Permitting API — Product Requirements Document

## 1. Introduction

Building an outside-plant fiber route is not primarily a cable-pulling exercise; it is an exercise in reconciling four adversarial pressures. Construction cost pushes the design toward the cheapest terrain. Network topology objectives push it toward whichever geometry closes a ring or reaches a backbone hand-off. Permitting reality — a city right-of-way office, a railroad's engineering department, a state highway district, a waterway authority — pushes it toward whatever corridor can actually be approved inside the in-service date. And the physical field pushes back on all three: poles rot, communication space fills up, spare conduit turns out to be occupied, and a street resurfaced eighteen months ago is under a paving moratorium that forbids open-cut trenching outright.

This document specifies the API for the system our fiber construction group uses to carry a route from a line on a map to a certified network record. The system is deliberately opinionated about sequencing. A route's segment set must be frozen before permits are filed, because a permitting-complexity score computed against a moving segment list is worthless. A field walkout must be accepted by an engineer before a segment can be costed, because a cost estimate built on an unverified obstruction count is a cost estimate that will be wrong at bid time. A design package must be stamped by an engineer other than the one who submitted it, and the as-built produced from that design must be certified by an engineer other than the one who stamped it. When an authority denies a permit late in the process, the system does not merely record the denial — it walks backwards through every downstream artifact that the denial invalidated, releases the segment from its locked design state, voids the affected stamp, and returns the route to permitting.

Two design commitments run through everything that follows. First, **every monetary amount is an integer count of cents and every ratio is an integer count of basis points** — there are no floating-point money fields anywhere in this API. Second, **time is a logical clock**, not the host's wall clock: review deadlines, moratorium containment tests and lapsed-window claims are all evaluated against a server-held instant that tests advance explicitly. Implementers who treat either commitment as a suggestion will produce numbers that disagree with the field.

## 2. Global Specifications & System-Wide Principles

### 2.1. Personnel, Agencies and Role-Based Access Control

Every request to this API, without exception, carries two headers. `X-User-ID` identifies the acting individual and `X-User-Role` names the capacity in which that individual is acting. If either header is absent, is present but blank, or if `X-User-Role` holds a string that is not one of the six roles declared below, the request is rejected with `ERR_UNAUTHENTICATED` and HTTP 401. Role names are matched exactly and case-sensitively, a header whose value is only whitespace counts as blank, and `X-User-ID` is otherwise unconstrained — any non-blank text is accepted, and it is recorded verbatim, without trimming, wherever the system stores an acting individual. This check precedes every other check in the system, including whether the addressed resource exists. The one class of failure that reports ahead of it is a routing failure resolved before any handler runs: a path matching no declared route answers `ERR_NOT_FOUND` with HTTP 404, and a declared path addressed with an undeclared HTTP method answers `ERR_METHOD_NOT_ALLOWED` with HTTP 405, in both cases even when the two headers are absent.

Six roles exist, spelled exactly as follows:

- **`RouteEngineer`** — owns route definition, segment engineering, construction-method selection, design production and as-built certification.
- **`FieldSurveyor`** — performs field walkouts, documents pole condition, conduit availability and obstructions, and files as-built documentation.
- **`PermitCoordinator`** — files pole attachment applications and right-of-way permits, accepts make-ready estimates, and claims lapsed-review outcomes.
- **`AuthorityReviewer`** — acts for the municipal, railroad, highway or waterway agency reviewing a permit application.
- **`PoleOwner`** — acts for the utility that owns the poles, returning make-ready estimates, revision requests or denials.
- **`NetworkRecordsAdmin`** — maintains municipal moratorium records, route budget authorizations, and the server's logical clock.

Once the headers are accepted, the system checks that the acting `X-User-Role` appears in the authorized-role list for the addressed operation. A role that is authenticated but not authorized for that operation receives `ERR_UNAUTHORIZED` and HTTP 403. All six roles are authorized for every read operation in the system; write operations are partitioned as shown in the endpoint table of section 4.

All six roles carry an **opaque** identity. That is: when `X-User-Role` is `RouteEngineer`, when it is `FieldSurveyor`, when it is `PermitCoordinator`, when it is `AuthorityReviewer`, when it is `PoleOwner`, and when it is `NetworkRecordsAdmin`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity in this system. The server never compares `X-User-ID` against any resource's `id`, and there is no "ownership" relationship between an operator and a route, segment, walkout, application, permit, design or as-built record. There is no entity-backed role here at all.

The server does, however, **record** `X-User-ID` at the points where accountability matters, and it compares those recorded values against each other. A walkout review stores the reviewing engineer in `reviewed_by_user_id`. A permit decision made by a person stores that person in `decided_by_user_id`. A design submission stores the submitter in `submitted_by_user_id` and a stamp stores the stamping engineer in `stamped_by_user_id`. An as-built filing stores the surveyor in `submitted_by_user_id` and a certification stores the certifying engineer in `certified_by_user_id`. **Segregation of duties in this system is enforced on `X-User-ID`, never on the role**: two different individuals both holding the `RouteEngineer` role are what the rule requires, and a single individual holding that role cannot satisfy both sides of it. Violations surface as `ERR_SEGREGATION_OF_DUTIES` with HTTP 403.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`; the prefix is followed by exactly 20 characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one instant this API emits that is read from the host's real-time clock rather than from the logical clock of section 2.5, and it always carries exactly three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and are absent entirely from a single-resource envelope, whose `meta` carries only `api_request_id` and `api_request_timestamp`. The order in which the envelope's keys are serialized is not significant.

#### Standard Error Response Format

All error API responses (4xx status codes, and any 5xx response, which takes the same shape) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Ordering

Every collection-returning operation in this API accepts the same two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position within the ordered result set: it defaults to 0 and its minimum accepted value is 0. A `limit` or `offset` outside those bounds, or one that is not an integer, is a malformed request and is rejected with `ERR_INVALID_REQUEST` and HTTP 400. Both values are read with surrounding whitespace tolerated and an explicit leading `+` or `-` sign accepted, while a parameter that is present but empty is malformed. `offset` carries no upper bound, so a window beginning past the end of the result set answers an empty `data` array while `total_count` still reports the full matching population. Query parameters the operation does not declare are ignored rather than rejected.

Collections are ordered by `created_at` in ascending order — oldest record first — unless a specific operation's narrative in section 3 states a different ordering for a specific derivation. Because the logical clock makes identical `created_at` values ordinary rather than exceptional, records sharing an instant are ordered among themselves by the order in which the server created them, earliest creation first; identifiers are never used as a tie-break. Pagination is reported back to the caller through four fields inside the `meta` object: `limit` and `offset` echo the effective values actually applied, `total_count` reports how many records matched the filters before the page window was applied, and `has_more` is true exactly when records remain beyond the current window.

Filter parameters, where an operation offers them, are combined conjunctively — a listing that is filtered on both `status` and `authority_type` returns only records matching both — and `total_count` reflects the filtered population, not the unfiltered one. A filter value is compared as an exact, case-sensitive string against the stored value and is not itself validated against any enumeration, so a filter naming a value no record holds simply matches nothing rather than reporting `ERR_INVALID_REQUEST`. The route- and segment-scoped listings offer these filters and no others: `/routes` accepts `status` and `topology_objective`; `/routes/{id}/segments` accepts `engineering_status` and `permit_status`; `/routes/{id}/design-packages`, `/routes/{id}/as-built-records`, `/segments/{id}/walkouts`, `/segments/{id}/pole-attachment-applications` and `/segments/{id}/splice-points` each accept `status`; `/segments/{id}/permit-applications` accepts `status` and `authority_type`; and `/segments/{id}/downstream-segments` offers none. Turning to the listings that hang off a walkout, off a pole attachment application, or off the moratorium registry: `/walkouts/{id}/pole-observations` accepts `requires_make_ready` and no other filter, `/pole-attachment-applications/{id}/make-ready-items` accepts `work_class` and no other, `/moratorium-windows` accepts `municipality_code` and `street_name` and no others, and `/design-packages/{id}/splice-points` — the one listing that hangs off a design revision — accepts `status` and `enclosure_type` and no others. `requires_make_ready` is the API's one boolean-valued filter, and it is read more forgivingly than the exact-string filters: its value is lower-cased with surrounding whitespace stripped before it is understood, so `true`, `TRUE`, ` false ` and `False` all select the population they name, while any value that is neither of those two words — `1`, `yes`, or the empty string — is silently ignored and the listing comes back unfiltered rather than reporting `ERR_INVALID_REQUEST` or matching nothing. Where a listing hangs off a parent resource, that path parameter is resolved before the paging parameters are read, so an unresolvable parent answers its not-found identifier even when `limit` or `offset` is also malformed.

### 2.4. Resource Identity, Audit Fields and Version Counters

Every resource this API mints receives an `id` that is a server-generated UUID. There is no type prefix on an identifier: a design package's `id` and a splice point's `id` are indistinguishable by inspection, and clients must not attempt to infer a resource's type from the shape of its identifier. Identifiers are never supplied by the client.

Nine of the eleven resource types are versioned resources and carry the full audit set: `id`, `created_at`, `updated_at` and `version`. `created_at` records the instant the record was first persisted. `updated_at` records the instant of the most recent mutation and is refreshed on every mutation, including mutations that touch only computed rollup fields. `version` is an integer that begins at 1 on creation and increments by exactly 1 on every mutation of that record — again including mutations confined to computed rollups, and including mutations applied by a cascade rather than by a direct request against that record. These nine are `Route`, `RouteSegment`, `FieldWalkout`, `PoleAttachmentApplication`, `PermitApplication`, `MoratoriumWindow`, `DesignPackage`, `SplicePoint` and `AsBuiltRecord`. A single request advances a given record's `version` by exactly 1 no matter how many times that one request touches it: a direct write together with any number of cascade hops that reach the same record count as one mutation, not several. The increment and the `updated_at` refresh are applied before the response is serialized, so the record a write returns already carries its new `version` and `updated_at`.

Two resource types are append-only observations and are deliberately **not** versioned: a `PoleObservation` and a `MakeReadyItem` each carry only `id` and `created_at`. Neither carries `updated_at` and neither carries `version`; those two fields are absent from their response payloads entirely rather than present-and-null. Those two absences are the only ones in the API: on every resource, every other field the resource declares is always present in its payload, carrying `null` where it holds no value, and a nullable field is never omitted. This is intentional — a pole observation is a field measurement that is never edited, and a make-ready line is replaced wholesale rather than amended.

The version counters are load-bearing far beyond auditing. Because so many operations in this system cascade into the owning `Route`, the route's `version` advances frequently and from many directions, and section 2.7 makes that counter the basis of the system's concurrency protection.

### 2.5. The Logical Clock and Instant Representation

This API does not read the host's wall clock. It holds a **logical clock** whose value is `2026-08-01T00:00:00Z` before any client has set it, and which never falls back to real time regardless of how long the process has been running. Every instant the system writes — `created_at`, `updated_at`, `scope_locked_at`, `submitted_at`, `decision_due_at`, `decided_at`, `stamped_at`, `stamp_voided_at` and `voided_at` — is read from that logical clock at the moment of the write. Every temporal comparison the system performs — whether a review window has lapsed, whether a moratorium contains a planned work date — is evaluated against that logical clock.

A `NetworkRecordsAdmin` moves the clock forward or backward by supplying a `to_iso8601` instant — the single body field that capability declares, and a required one — to the clock-setting capability, which answers HTTP 200 with an object whose only key is `current_utc`, carrying the newly effective instant in the whole-second emitted form. A fractional part supplied on input is truncated away rather than echoed back or rounded, so setting the clock to `2026-09-24T00:00:00.500Z` leaves it standing at, and answers with, `2026-09-24T00:00:00Z`. Setting the clock mutates no entity and evaluates no automatic transition: nothing becomes overdue merely because the clock passed a deadline. Deadline consequences are always claimed by an explicit request, never applied in the background.

Instants are exchanged in a single fixed form: **ISO 8601 UTC at whole-second precision with a trailing `Z` and no fractional-second digits** — for example `2026-09-24T00:00:00Z`. That form is what the API emits and that same form is what it accepts on input. The input parser is fractionally wider than the emitted form in exactly one respect: a supplied instant may carry one to six fractional-second digits, which are accepted and then discarded, the value being truncated to whole seconds before it is stored or compared. Every other deviation — a missing `Z`, a numeric offset such as `+00:00`, a space in place of the `T`, or a date-only string — is rejected with `ERR_INVALID_REQUEST`. Calendar dates, which are a distinct concept in this domain, are exchanged as `YYYY-MM-DD` strings with no time component at all: `target_in_service_date`, `planned_work_start_on`, `planned_work_end_on`, `walked_on`, `work_window_start_on`, `work_window_end_on`, `resurfaced_on`, `starts_on` and `ends_on` are all plain calendar dates. A value that cannot be parsed in the form its field requires is rejected with `ERR_INVALID_REQUEST`.

### 2.6. Integer Cents, Basis Points and Rounding Discipline

All money in this system is an integer number of cents. All ratios are integer numbers of **basis points**, where one basis point is one ten-thousandth, so 10,000 basis points is unity and 2,000 basis points is twenty percent. Permitting complexity is scored in integer **centipoints**, where one point is 100 centipoints. No field in this API is a decimal or floating-point number.

Wherever a division or a proportional multiplication cannot land exactly on an integer, the result is rounded **half up** — a value whose fractional part is exactly one half rounds away from zero, to the larger magnitude. There is no banker's rounding anywhere in this specification.

The subtle part is not the rounding rule but the **rounding sites**. Several of this system's calculations round more than once, and the number of roundings and their position in the evaluation order are part of the specification, not an implementation detail. Two calculations in particular round each term of a summation to a whole integer *before* summing, and computing the same sum with a single rounding at the end produces a different, wrong number. Where section 3 pins an evaluation order, that order is mandatory.

### 2.7. Optimistic Concurrency on the Owning Route

Two write operations in this system are guarded by optimistic concurrency control against the owning `Route`, and both guard on the route's `version` counter described in section 2.4. In each case the client must supply `expected_route_version` in the request body as a **required, non-optional** field carrying the `version` value the client last observed on that route. If the supplied value does not equal the route's current `version`, the request is rejected with `ERR_STALE_ROUTE_VERSION` and HTTP 412, and no field anywhere is written.

The two guarded operations are:

1. **`POST /segments/{id}/construction-method`** — selecting or re-selecting a segment's construction method requires `expected_route_version` to equal the current `version` of the route that owns the addressed segment. A mismatch is `ERR_STALE_ROUTE_VERSION` (HTTP 412). This guard exists because method selection is a legitimate supersede: a segment already in `METHOD_SELECTED` may be re-selected, and the later selection overwrites `construction_method`, `moratorium_class`, `restoration_cost_cents` and `preliminary_cost_cents` and re-derives the route's cost rollups. A caller whose view of the route has gone stale would therefore overwrite cost figures derived from route state it never observed. The comparison is a stale-version comparison on the route's `version` only; nothing else about the route is inspected by this guard.

2. **`POST /design-packages`** — creating the next design revision on a route requires `expected_route_version` to equal that route's current `version`. A mismatch is `ERR_STALE_ROUTE_VERSION` (HTTP 412). A newly stamped revision legitimately supersedes the previously stamped one, so the create itself is always permitted by the product's semantics; the stale-version comparison is what prevents a caller from minting revision N+1 from an outdated view of the route's segment set, permit posture and cost rollups.

No other operation in this API takes a version field. Endpoints not named in the two clauses above must not accept `expected_route_version`, and supplying it to them is an unknown body field, rejected with `ERR_INVALID_REQUEST`.

### 2.8. Flat Addressing and Referential Resolution Order

Every collection in this system is mounted as a top-level path segment. There are no nested creation paths: a segment is not created under a route's URL, a splice point is not created under a design package's URL. Parentage travels instead in the **request body**, through foreign-key fields such as `route_id`, `segment_id`, `walkout_id`, `application_id` and `design_id`. Reverse navigation is offered as a set of read-only listing operations hanging off the parent — the route's segments, the route's design packages, the route's as-built records, a segment's downstream segments, a segment's walkouts, a segment's pole attachment applications, a segment's permit applications, a segment's splice points, a walkout's pole observations, an application's make-ready items, and a design package's splice points.

Where an operation's URL carries a path parameter, that parameter is resolved before the body is inspected, and where several path parameters appear they are resolved strictly **left to right**, with the first unresolvable identifier determining the error. The 404-bearing identifiers are `ERR_ROUTE_NOT_FOUND`, `ERR_SEGMENT_NOT_FOUND`, `ERR_WALKOUT_NOT_FOUND`, `ERR_POLE_APPLICATION_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_DESIGN_NOT_FOUND`, `ERR_SPLICE_POINT_NOT_FOUND` and `ERR_AS_BUILT_NOT_FOUND`.

Body foreign keys are resolved after path parameters, and among themselves they are resolved **in the order the owning resource declares them**. On a segment create that means `route_id` is resolved before `predecessor_segment_id`, so a create naming both a nonexistent route and a nonexistent predecessor answers `ERR_ROUTE_NOT_FOUND`. On a splice-point create it means `design_id` is resolved before `segment_id`, so that combination answers `ERR_DESIGN_NOT_FOUND`. A `walkout_id` on a pole-observation create, an `application_id` where one appears, and a lone `segment_id` on a walkout, pole attachment application or permit application create each resolve as the single key they are. A nonexistent `walkout_id` is `ERR_WALKOUT_NOT_FOUND`; a nonexistent `segment_id` or `predecessor_segment_id` is `ERR_SEGMENT_NOT_FOUND`; a nonexistent `route_id` is `ERR_ROUTE_NOT_FOUND`; a nonexistent `design_id` is `ERR_DESIGN_NOT_FOUND`. Body-key resolution applies to the eight creation operations that carry foreign keys: segment create, walkout create, pole-observation create, pole-attachment-application create, permit-application create, design-package create, splice-point create and as-built-record create.

### 2.9. Validation Precedence

When a single request could fail several checks, the check that reports is fixed by the following precedence, evaluated top to bottom. This ordering is normative: a request that violates both a later and an earlier rule must report the **earlier** rule's error identifier. The rationale is that a caller should learn about the cheapest and most structural defect first, and that a business-rule rejection should never mask an authentication or shape problem.

1. **Header authentication** — both headers present and non-blank, and `X-User-Role` naming one of the six declared roles. Applies to every operation in the system. → `ERR_UNAUTHENTICATED` (401)
2. **Role authorization** — the acting role appears in the addressed operation's authorized-role list. Applies to every operation in the system. → `ERR_UNAUTHORIZED` (403)
3. **Body shape** — every required field present; no unknown field; every enum value inside its declared set; every integer inside its declared constraint; dates parseable as `YYYY-MM-DD`; instants parseable as ISO 8601 UTC; and every ordering constraint between a pair of body fields satisfied, namely `planned_work_end_on` on or after `planned_work_start_on`, `work_window_end_on` on or after `work_window_start_on`, `ends_on` on or after `starts_on`, `express_fiber_count` strictly less than `fiber_count_allocated`, and `station_feet` no greater than the addressed segment's `length_feet` — this last being the one shape rule that has to read a body foreign key's target, so it is evaluated only where the body's `segment_id` actually resolves to a segment: a splice-point create whose `segment_id` names nothing at all skips the ceiling entirely and reports its foreign-key failure instead, while one whose `segment_id` does resolve reports the ceiling ahead of an unresolvable `design_id`. A request body that is absent, empty or the JSON literal `null` is read as the empty JSON object, so an action operation declaring no body fields accepts any of them, while a body that parses to anything other than a JSON object — an array, a string, a number — is malformed. An explicitly `null` optional field is treated exactly as an omitted one and takes that field's stated default; an explicitly `null` required field is a shape error. A required string field must further be non-blank — an empty or whitespace-only value is a shape error — except where a section 3 narrative explicitly permits a blank one, while an optional free-text field imposes no such floor and accepts any string at all, the empty and the whitespace-only included, storing it verbatim without trimming. A field whose requirement is conditional on another body field's value, such as the `rejection_reason` that a walkout rejection demands, is evaluated at this priority like any other shape rule, so it reports `ERR_INVALID_REQUEST` ahead of the addressed record's existence and ahead of that record's status gate. A JSON boolean is never accepted where an integer is declared. Enum members are matched case-sensitively, and a calendar date must be a real date, so `2026-02-30` is rejected even though it matches the `YYYY-MM-DD` shape. An unknown body field is rejected on the strength of its name alone, whatever value it carries, `null` included. Applies to every write operation. → `ERR_INVALID_REQUEST` (400)
4. **Path-parameter existence**, resolved left to right. Applies to every operation carrying a path parameter. → the matching not-found identifier (404)
5. **Body foreign-key existence**, resolved in declaration order. Applies to the eight creation operations that carry foreign keys. → the matching not-found identifier (404)
6. **Predecessor coherence** on a segment create. → `ERR_PREDECESSOR_SEGMENT_MISMATCH` (422)
7. **Sequence-index uniqueness** on a segment create. → `ERR_SEQUENCE_INDEX_TAKEN` (409)
8. **Route stale-version check** on construction-method selection and on design-package creation. → `ERR_STALE_ROUTE_VERSION` (412)
9. **Route status gate** — segment creation requires the route in `PLANNING`; permit-application creation and permit submission require `SCOPE_LOCKED`, `PERMITTING` or `CONSTRUCTION_READY`, since a supplemental permit may legitimately be filed after the design is construction-ready; design-package creation requires `SCOPE_LOCKED`, `PERMITTING` or `CONSTRUCTION_READY`; as-built filing requires `CONSTRUCTION_READY`; scope locking requires `PLANNING`. Applies to those six operations. → `ERR_SCOPE_LOCKED` (409) where a segment create is refused because its route has left `PLANNING`, and `ERR_INVALID_ROUTE_STATE` (409) in every other case
10. **Segment engineering-status gate** — construction-method selection requires `WALKED` or `METHOD_SELECTED`; bid-ready estimation requires `METHOD_SELECTED`. Applies to those two operations. → `ERR_INVALID_SEGMENT_ENGINEERING_STATE` (409)
11. **Child-resource status gate** on every action operation that drives a state machine other than the route's — walkout submission requires `OPEN` or `REJECTED` and walkout review requires `SUBMITTED`; pole-attachment submission requires `DRAFT` or `REVISION_REQUESTED`, owner response requires `SUBMITTED`, make-ready acceptance requires `MAKE_READY_ESTIMATED`, and withdrawal requires any non-terminal status; permit submission requires `DRAFT` or `REVISION_REQUESTED` while permit review and the lapsed-window claim both require `UNDER_REVIEW`; design submission for review requires `DRAFT`, stamping requires `IN_REVIEW`, return-to-draft requires `IN_REVIEW`, and splice-point placement requires the owning design in `DRAFT`; splice-point voiding requires `PLACED`; as-built certification requires `SUBMITTED`. → `ERR_INVALID_WALKOUT_STATE`, `ERR_INVALID_POLE_APPLICATION_STATE`, `ERR_INVALID_PERMIT_STATE`, `ERR_INVALID_DESIGN_STATE`, `ERR_INVALID_SPLICE_POINT_STATE` or `ERR_INVALID_AS_BUILT_STATE` respectively (409)
12. **Segregation of duties** — on design stamping and on as-built certification. → `ERR_SEGREGATION_OF_DUTIES` (403)
13. **Open-cut prohibition** — on construction-method selection. → `ERR_OPEN_CUT_PROHIBITED` (422)
14. **Grade-D make-ready requirement** — on make-ready acceptance. → `ERR_MAKE_READY_REQUIRED` (422)
15. **Moratorium containment of the permit work window** — on permit submission. → `ERR_MORATORIUM_WINDOW_CONFLICT` (409)
16. **Moratorium window non-overlap** — on moratorium-window registration. → `ERR_MORATORIUM_WINDOW_OVERLAP` (409)
17. **Review window has actually lapsed** — on the lapsed-window claim. → `ERR_REVIEW_WINDOW_OPEN` (409)
18. **Splice spacing buffer** — on splice-point placement. → `ERR_SPLICE_SPACING_VIOLATION` (422)
19. **Empty-collection gates** — scope locking requires at least one segment, walkout submission requires at least one pole observation, and design submission for review requires at least one placed splice point. Applies to those three operations. → `ERR_ROUTE_HAS_NO_SEGMENTS`, `ERR_WALKOUT_HAS_NO_OBSERVATIONS` or `ERR_DESIGN_HAS_NO_SPLICE_POINTS` respectively (422)
20. **Walkout readiness** — scope locking requires every segment on the route to have left `DRAFT`, and pole-attachment submission requires the same of its own segment. Applies to those two operations. → `ERR_WALKOUT_NOT_ACCEPTED` (422)
21. **Route-wide permit clearance** — on design stamping. → `ERR_PERMIT_NOT_CLEARED` (422)
22. **Spare-fiber floor** — on design stamping. → `ERR_SPARE_RATIO_BELOW_MINIMUM` (422)
23. **Fiber conservation** — on splice-point placement. → `ERR_FIBER_ALLOCATION_EXCEEDED` (422)
24. **Stamped-revision existence** — on as-built filing. → `ERR_DESIGN_NOT_STAMPED` (422)
25. **As-built length variance ceiling** — on as-built certification where the decision is acceptance. → `ERR_AS_BUILT_VARIANCE_EXCEEDED` (422)
26. **Budget sufficiency** — on make-ready acceptance and on budget adjustment. → `ERR_BUDGET_EXCEEDED` (402)

Note the practical consequences of this ordering. Design stamping runs four business checks after its status gate, and they fire in this sequence: segregation of duties first, then route-wide permit clearance, then the spare-fiber floor. An engineer who submitted a package and then tries to stamp it on a route whose permits are not cleared learns about the duty conflict, not the permit posture. Likewise, make-ready acceptance evaluates the grade-D make-ready requirement (priority 14) **before** budget sufficiency (priority 26), so an application missing its pole-replacement line reports `ERR_MAKE_READY_REQUIRED` even when it also exceeds the route's available budget. And a segment create that names an unusable predecessor reports `ERR_PREDECESSOR_SEGMENT_MISMATCH` even when its `sequence_index` is also taken.

### 2.10. Cascade Propagation and Rollup Integrity

Three named cascades exist in this system, and each one is a multi-hop chain in which every hop is caused by the hop above it. A cascade is atomic: either every hop it reaches is applied, or the triggering request fails and nothing is written. Each resource a cascade touches has its `updated_at` refreshed and its `version` incremented, exactly as if it had been mutated directly. The hop sequences given below are the full chains, not the chains that always run: several individual hops are conditional on the state the cascade finds when it arrives, and where a hop's condition fails, that hop and every hop caused by it simply do not run — no field is written and no record is touched on their account. The narratives of section 3 pin each of those conditions exactly, and a hop that does not run is a normal outcome rather than an error.

- **The re-walk rejection cascade** has depth 5 and fires when an engineer rejects a submitted walkout. Hop 1 rejects the walkout itself; hop 2 drives the walked segment back to `DRAFT` engineering status; hop 3 clears that segment's derived construction figures; hop 4 recomputes the route's two cost rollups; hop 5 returns the route to `PLANNING`.
- **The permit denial cascade** also has depth 5 and fires when a permit reaches `DENIED`, whether by an authority's decision or by a lapsed non-municipal review window. Hop 1 denies the permit; hop 2 blocks the segment's permit dimension; hop 3 releases that segment from `DESIGN_LOCKED`; hop 4 voids the stamp on every stamped design package that had placed work on that segment; hop 5 returns the route from `CONSTRUCTION_READY` to `PERMITTING`.
- **The attachment withdrawal cascade** has depth 4 and fires when a pole attachment application is withdrawn. Hop 1 withdraws the application and clears its commitment flag; hop 2 releases the committed budget on the route; hop 3 re-derives the segment's bid-ready cost without that application's make-ready contribution; hop 4 recomputes the route's bid-ready cost rollup.

Rollup fields on a parent are never stale. `segment_count`, `design_total_length_feet`, `total_preliminary_cost_cents`, `total_bid_ready_cost_cents`, `budget_committed_cents` and `budget_available_cents` on a route, and `assigned_drop_fiber_count`, `reserve_fiber_count`, `spare_ratio_bp`, `splice_point_count` and `handhole_count` on a design package, are recomputed synchronously inside the request that changed their inputs and are readable at their new values in that request's own response. Where a rollup sums a nullable child field — `preliminary_cost_cents` and `bid_ready_cost_cents` are both nullable — a null contributes zero to the sum rather than making the sum null.

### 2.11. Conserved Quantities: The Budget Ledger and the Fiber Ledger

Two invariants hold after every forward action and after every compensating action in this system, and an implementation that lets either drift is incorrect regardless of how any individual request behaved.

The **budget invariant** is that a route's `budget_authorized_cents` always equals `budget_committed_cents` plus `budget_available_cents`. Committed budget is not a running counter that operations nudge; it is defined as the sum of `make_ready_cost_cents` over every pole attachment application filed against a segment of this route whose status is `GRANTED` — and nothing else. Applications in `DRAFT`, `SUBMITTED`, `REVISION_REQUESTED`, `MAKE_READY_ESTIMATED`, `DENIED` or `WITHDRAWN` contribute nothing, even when they carry a fully computed `make_ready_cost_cents`. Available budget is authorized minus committed. Because withdrawal simply removes a row from the `GRANTED` population while retaining its cost figures on the row for audit, withdrawal is an exact compensating action for acceptance. All addends are integers, so the sum is order-insensitive and needs no rounding.

The **fiber invariant** is that a design package's `fiber_count_allocated` always equals `express_fiber_count` plus `assigned_drop_fiber_count` plus `reserve_fiber_count`. Assigned drop fiber is defined as the sum of `fiber_count_dropped` over the splice points on this design whose status is `PLACED`; splice points in `VOIDED` are excluded, and splice points belonging to a different design revision on the same route never enter the sum. Voiding a placed splice point is therefore an exact compensating action for placing it: the dropped fibers return to the future-customer reserve without residue.

## 3. Business Logic & Workflows

### 3.1. Establishing a Route and Building Its Segment Chain

A `RouteEngineer` opens the work by creating a **Route**, supplying a human-readable `name` of between 1 and 120 characters that is not blank or whitespace-only, a `topology_objective` that is one of `RING_CLOSURE`, `SPUR` or `EXPRESS_BACKBONE`, a `target_in_service_date` as a calendar date, and a `budget_authorized_cents` of at least 1 cent covering construction and make-ready together. The route is born in `PLANNING` with `segment_count` and `design_total_length_feet` at zero, `total_preliminary_cost_cents` and `total_bid_ready_cost_cents` at zero, `budget_committed_cents` at zero and `budget_available_cents` equal to the authorized figure, `scope_locked_at` null, and both complexity indices — `planned_complexity_index` and `live_complexity_index` — null. The `topology_objective` is not decoration: `RING_CLOSURE` is the only objective that earns an expedited permit review cycle later, and section 3.5 explains where that discount lands.

Route status advances through `PLANNING`, `SCOPE_LOCKED`, `PERMITTING` and `CONSTRUCTION_READY` to the terminal `RECORDS_UPDATED`. Two of those hops can run backwards, and both are described where the operations that cause them are described. `RECORDS_UPDATED` is genuinely terminal: no further route transition is permitted from it, and attempts to add a segment, file a permit application, or create a design package on a records-updated route are refused with `ERR_INVALID_ROUTE_STATE`.

While the route is in `PLANNING`, the engineer builds its **segment chain**. Each `RouteSegment` is created with a `route_id` naming its route, a `sequence_index` of at least 1 giving its position along the route, a `street_name` and a `municipality_code` identifying the right-of-way, a `length_feet` of at least 1, a `terrain_class`, and the pair of planned construction dates `planned_work_start_on` and `planned_work_end_on`, the latter falling on or after the former. Two further inputs are optional: `predecessor_segment_id`, which names the immediately upstream segment on the same route and is null for the head segment, and `existing_conduit_available`, a boolean that defaults to false and records whether spare conduit is believed to run along the segment. The `sequence_index` must be unused by any other segment on the same route; a collision is `ERR_SEQUENCE_INDEX_TAKEN`. When `predecessor_segment_id` is supplied non-null, the named segment must belong to the *same* route and must carry a `sequence_index` strictly lower than the new segment's; a predecessor on a different route, or one whose index is equal to or higher than the new segment's, is `ERR_PREDECESSOR_SEGMENT_MISMATCH`.

`terrain_class` is the most consequential field on a segment because it drives three separate things. It is one of `URBAN_PAVED`, `URBAN_UNPAVED`, `RURAL_SHOULDER`, `RAIL_CROSSING`, `HIGHWAY_CROSSING` or `WATER_CROSSING`. From it the system immediately derives `required_authority_type`, the permitting authority class that will have to be dealt with: paved urban, unpaved urban and rural shoulder terrain all fall to `MUNICIPAL_ROW`, a highway crossing falls to `STATE_HIGHWAY`, a rail crossing falls to `RAILROAD`, and a water crossing falls to `WATERWAY`. The same mapping drives the planned complexity score at scope lock, and terrain also supplies the cost multiplier described in section 3.3. A new segment is born with `engineering_status` at `DRAFT`, `permit_status` at `NOT_REQUIRED`, `construction_method` null, `moratorium_class` at `NONE`, `restoration_cost_cents` at zero, `accepted_obstruction_count` at zero, and both `preliminary_cost_cents` and `bid_ready_cost_cents` null. Creating it raises the route's `segment_count` by one, adds the new `length_feet` to the route's `design_total_length_feet`, and increments the route's `version`.

A segment carries **two independent state dimensions on the same row**. `engineering_status` walks `DRAFT`, `WALKED`, `METHOD_SELECTED` and `DESIGN_LOCKED`; `permit_status` walks `NOT_REQUIRED`, `PENDING`, `CLEARED` and `BLOCKED`. Neither dimension is a function of the other, and a segment can perfectly well sit at `DESIGN_LOCKED` with a `permit_status` of `PENDING`, or at `WALKED` with a `permit_status` of `CLEARED`. The one place the dimensions interact is the permit denial cascade, and even there the interaction is narrow: a denial blocks the permit dimension unconditionally, but it disturbs the engineering dimension only when that dimension had reached `DESIGN_LOCKED`.

The engineer freezes the scope once the segment chain is complete; the lock operation declares no body fields at all, so any field supplied in its body is an unknown field. Scope locking demands that the route be in `PLANNING`, that its `segment_count` be at least 1 — a route with no segments is `ERR_ROUTE_HAS_NO_SEGMENTS` — that its `budget_authorized_cents` be at least 1 — a route whose authorization has been driven to zero is refused with `ERR_BUDGET_EXCEEDED` and HTTP 402 — and that **every** segment on the route have progressed past `DRAFT` into `WALKED`, `METHOD_SELECTED` or `DESIGN_LOCKED`. A single still-`DRAFT` segment refuses the whole lock with `ERR_WALKOUT_NOT_ACCEPTED`. On success the route moves `PLANNING → SCOPE_LOCKED`, `scope_locked_at` is stamped from the logical clock, the planned permitting-complexity index is computed and written to `planned_complexity_index`, `live_complexity_index` is seeded with that identical value, and the route's `version` increments. From that moment the segment set is closed: an attempt to add another segment to the route is refused with `ERR_SCOPE_LOCKED`.

The **planned permitting-complexity index** scores the authority mix that the terrain implies, and it ignores entirely whether any permit has ever been filed. Its input set is every segment whose `route_id` is this route, with no status filter, evaluated at the instant of the lock. Each segment contributes the authority weight of the authority its terrain implies: a municipal right-of-way weighs 10, a state highway weighs 25, a railroad weighs 40 and a waterway weighs 50. Those integer weights are summed across the segments — the sum is order-insensitive — the total is multiplied by 100 to convert points into centipoints, that product is divided by the route's `segment_count`, and the quotient is rounded half up to a whole number of centipoints. There is exactly **one** rounding in this calculation and it is the last step: the authority weights are whole points, so no term is rounded before the summation, which is precisely what distinguishes the planned index from the live index of section 3.5, where every term rounds before it is summed. For a three-segment route made of one `URBAN_PAVED`, one `RAIL_CROSSING` and one `HIGHWAY_CROSSING` segment, the weights are 10, 40 and 25 for a sum of 75, giving 7,500 centipoints over three segments and a `planned_complexity_index` of 2500. Once written, this value is never recomputed; the only thing that ever changes it again is the re-walk rejection cascade, which resets it to null.

### 3.2. Field Walkout, Pole Condition, and the Re-Walk Cascade

A `FieldSurveyor` opens a **FieldWalkout** against a segment by supplying the `segment_id` and the `walked_on` date on which the walk was performed. Three inputs are optional: `obstruction_count`, a count of at least zero that defaults to 0 and records documented obstructions found along the segment; `conduit_available_confirmed`, a boolean defaulting to false recording whether the surveyor actually confirmed usable spare conduit; and `surveyor_note`, free text defaulting to null. A new walkout begins at `OPEN` with `review_round` at 0, `worst_pole_condition_grade` at `NONE`, `make_ready_flagged_pole_count` at 0, and `reviewed_by_user_id` and `rejection_reason` both null.

Onto a walkout the surveyor appends **PoleObservation** records, one per utility pole encountered. Appending one carries no walkout-status gate whatever: an observation is accepted while its walkout stands at `OPEN`, at `SUBMITTED`, at `ACCEPTED` or at `REJECTED`, and in each case the walkout's two derived rollups are recomputed and its `version` increments. A late observation appended to an already-accepted walkout does not, however, re-copy anything onto the segment; that copy happens only at review time. Each observation names its `walkout_id`, the `pole_tag` as stencilled in the field, the `pole_owner` — one of `ELECTRIC_UTILITY`, `TELCO` or `MUNICIPAL_LIGHT` — a `condition_grade` of `A`, `B`, `C` or `D`, an `available_vertical_clearance_in` of at least zero inches of usable communication space, and an `existing_attachment_count` of at least zero attachments already on the pole. Observations are immutable field measurements; there is no operation to edit or delete one.

Each observation derives one field and updates two rollups on its walkout. The derived field is `requires_make_ready`, which is true when either the pole's `condition_grade` is `C` or `D`, or the pole's `available_vertical_clearance_in` is strictly less than 40 inches — that is, less than three feet four inches of usable space. Either condition alone is sufficient. The two rollups are `make_ready_flagged_pole_count`, which counts the observations on this walkout whose `requires_make_ready` is true, and `worst_pole_condition_grade`, which is the single worst grade among this walkout's observations under the severity order in which `D` is worse than `C`, `C` is worse than `B`, and `B` is worse than `A`; when a walkout has no observations at all the value is `NONE`. Recording an observation increments the walkout's `version`.

The surveyor then submits the walkout for engineering review. Submission requires at least one pole observation on the walkout — a walkout with none is refused with `ERR_WALKOUT_HAS_NO_OBSERVATIONS` — and drives `OPEN → SUBMITTED`. The same submission operation also serves the revision loop: a walkout sitting at `REJECTED` is submitted again, which passes it through `OPEN` and immediately re-evaluates the `OPEN → SUBMITTED` transition inside the same request, so the response the surveyor receives shows the walkout at `SUBMITTED` rather than at `OPEN`. `review_round` retains whatever value the earlier rejection gave it. Submitting a walkout from any other status is `ERR_INVALID_WALKOUT_STATE`.

A `RouteEngineer` reviews a submitted walkout by supplying a `decision`, with `rejection_reason` as an accompanying optional field. Any route engineer may review; there is no constraint tying the reviewer to the surveyor. Both outcomes stamp the reviewing engineer's `X-User-ID` into `reviewed_by_user_id` and increment the walkout's `version`. A `rejection_reason` supplied alongside an `ACCEPTED` decision is read for shape and then ignored, stored nowhere; and any `rejection_reason` an earlier rejection left on the row survives a later acceptance rather than being cleared back to null.

**Acceptance** moves the walkout `SUBMITTED → ACCEPTED`, which is its terminal state, and drives the walked segment's engineering dimension `DRAFT → WALKED`. That advance fires from `DRAFT` only: accepting a further walkout on a segment that has already reached `WALKED`, `METHOD_SELECTED` or `DESIGN_LOCKED` leaves the engineering dimension exactly where it stands, while still refreshing the field data described next. Acceptance is also the moment the field data lands on the segment: the walkout's `obstruction_count` is copied onto the segment as `accepted_obstruction_count`, and the walkout's `conduit_available_confirmed` is copied onto the segment as `existing_conduit_available`, overwriting whatever the engineer guessed at segment-creation time. The segment's `version` increments. Where a segment has accumulated several `ACCEPTED` walkouts over its life, **both** copied fields are read off the walkout at `ACCEPTED` with the newest `created_at` — that is, the most recently created accepted walkout, ranked by `created_at` descending and taking the first row, and where two accepted walkouts share a `created_at` the later-created of the two wins — rather than off whichever walkout this particular review happened to accept. Accepting an older-created walkout after a newer-created one has already been accepted therefore rewrites the segment from the *newer* row's figures and leaves both values standing exactly where they were, even though the review itself still advances the segment's `version`. A segment with no `ACCEPTED` walkout at all reads zero for `accepted_obstruction_count`, while `existing_conduit_available` keeps whatever value segment creation gave it: this copy is the only thing in the system that ever writes that flag, and nothing — the re-walk rejection cascade included — ever resets it.

**Rejection** moves the walkout `SUBMITTED → REJECTED` and requires a `rejection_reason` that is present and non-blank; a rejection submitted without one is `ERR_INVALID_REQUEST`. Rejection then runs the five-hop re-walk rejection cascade. Hop 1 always applies, but hops 2 through 5 are gated on the segment's engineering dimension standing at `WALKED`, `METHOD_SELECTED` or `DESIGN_LOCKED` at the moment the rejection arrives — the three statuses hop 2 has something to undo. Where that dimension already stands at `DRAFT`, which is the ordinary case for a segment whose very first walkout is rejected, the cascade stops after hop 1: the segment is not touched and its `version` does not move, its derived figures are not rewritten, neither route cost rollup is recomputed, the route is not touched either, and the route's `status`, `scope_locked_at` and `planned_complexity_index` are all left exactly as they stood. When the gate does open, every remaining hop runs:

- **Hop 1** sets the walkout's `status` to `REJECTED`, stores the supplied text in `rejection_reason`, raises `review_round` by 1, and records `reviewed_by_user_id`.
- **Hop 2**, caused by hop 1, drives the walkout's segment back to `DRAFT` engineering status from whichever of `WALKED`, `METHOD_SELECTED` or `DESIGN_LOCKED` it had reached.
- **Hop 3**, caused by hop 2, erases every engineering derivation on that segment: `construction_method` becomes null, `moratorium_class` returns to `NONE`, `restoration_cost_cents` returns to 0, and `preliminary_cost_cents` and `bid_ready_cost_cents` both become null. Those five fields are the whole of the erasure: the field data the walkout review copied down — `accepted_obstruction_count` and `existing_conduit_available` — is **not** disturbed by this hop and survives the rejection intact, as do the segment's `permit_status`, its `sequence_index` and its derived `required_authority_type`. The segment's `version` increments, and it does so unconditionally: a segment that had reached only `WALKED`, and whose five figures therefore already stood at null, `NONE` and 0, is still counted as mutated by this hop.
- **Hop 4**, caused by hop 3, recomputes the owning route's `total_preliminary_cost_cents` and `total_bid_ready_cost_cents` over the segment set as it now stands. The route is touched at this hop unconditionally — its `version` advances and its `updated_at` refreshes whether or not either rollup's value actually moved, and whether or not hop 5 goes on to fire at all.
- **Hop 5**, caused by hop 4, drives the route's status to `PLANNING`, sets `scope_locked_at` back to null, and sets `planned_complexity_index` back to null. The route's `version` increments.

Hop 5 fires from any of `SCOPE_LOCKED`, `PERMITTING` or `CONSTRUCTION_READY`, and from those three only: a route already sitting in `PLANNING` keeps its status, and its `scope_locked_at` and `planned_complexity_index` are left as they are rather than being re-nulled — though hop 4 has already advanced that route's `version` regardless. The destination is always `PLANNING` — a late field rejection unwinds a route that had already reached construction readiness just as thoroughly as it unwinds one that had merely locked its scope. Note that `live_complexity_index` is *not* reset by this cascade; only the planned figure is.

### 3.3. Choosing How to Build: Method Selection, Moratoria and Restoration

Once a segment has been field-verified, a `RouteEngineer` selects how it will be built by supplying a `method` — one of `AERIAL`, `DIRECTIONAL_BORE` or `TRENCH` — together with `expected_route_version`, the concurrency token described in section 2.7. Selection is legal from `WALKED` and it is legal again from `METHOD_SELECTED`, which makes it a **self-loop**: re-selection is an ordinary, expected act that supersedes the earlier choice, and the whole reason the operation is version-guarded is that a superseding write from a stale view of the route would silently replace cost figures derived from route state the writer never saw. Selection from `DRAFT` or from `DESIGN_LOCKED` is refused with `ERR_INVALID_SEGMENT_ENGINEERING_STATE`. A successful selection advances the segment's engineering dimension to `METHOD_SELECTED` — from `WALKED` on the first selection, and from `METHOD_SELECTED` to `METHOD_SELECTED` on any later one — writes `construction_method`, resolves the moratorium and restoration figures, recomputes the preliminary cost, **discards any bid-ready cost by setting `bid_ready_cost_cents` back to null**, recomputes both route cost rollups, and increments the route's `version`.

Moratorium resolution runs **first**, before any cost is computed, because it can veto the selection outright. A `NetworkRecordsAdmin` registers each **MoratoriumWindow** with the `municipality_code` that enacted it, the `street_name` it covers, the `resurfaced_on` date on which the street was last resurfaced, the inclusive first date `starts_on` and inclusive last date `ends_on` of the restriction, a `moratorium_class` of either `NO_OPEN_CUT` or `FULL_RESTORATION`, and the `ordinance_reference` citing the municipal ordinance. Registration is refused with `ERR_MORATORIUM_WINDOW_OVERLAP` when the new window's closed date interval intersects an existing window on the same `municipality_code` and `street_name`; because both intervals are closed, windows that merely touch at an endpoint do collide.

To resolve a segment's moratorium the system gathers every registered window whose `municipality_code` equals the segment's `municipality_code`, whose `street_name` equals the segment's `street_name`, and whose date interval **contains the segment's `planned_work_start_on`** — that is, where `starts_on` is on or before the planned start and `ends_on` is on or after it, both endpoints inclusive. The segment's planned start date, not its planned end date and not the current logical clock, is the probe. Every registered window is eligible for consideration regardless of when it was registered; there is no recency filter on the candidate set beyond that containment test. If no window matches, the segment's `moratorium_class` resolves to `NONE`. If one or more match, they are ranked by severity descending, where `FULL_RESTORATION` outranks `NO_OPEN_CUT` and `NO_OPEN_CUT` outranks `NONE`, and ties on severity are broken by `created_at` ascending — the earliest-registered window wins a tie, and identifiers are never used as a tie-break. The winning window's `moratorium_class` becomes the segment's `moratorium_class`.

With the moratorium resolved, the **open-cut prohibition** applies: a `method` of `TRENCH` on a segment whose resolved `moratorium_class` is `NO_OPEN_CUT` is refused with `ERR_OPEN_CUT_PROHIBITED`, and the request writes nothing at all — not the method, not the moratorium class, not the restoration figure. The city has forbidden cutting that pavement, and a boring machine or an aerial build is the only lawful answer.

Otherwise the pavement restoration obligation is computed as the segment's `length_feet` multiplied by a per-foot restoration rate looked up on the pair of construction method and moratorium class, and the product is written to `restoration_cost_cents`. Both operands are integers, so the product is exact and no rounding occurs. An aerial build disturbs no pavement and therefore carries a restoration rate of 0 cents per foot under all three moratorium classes. A directional bore carries 260 cents per foot with no moratorium in force, 480 cents per foot under a no-open-cut moratorium, and 720 cents per foot under a full-restoration moratorium. Open trenching carries 940 cents per foot with no moratorium in force and 2,150 cents per foot under a full-restoration moratorium; the no-open-cut combination does not exist because the prohibition above already rejected it.

**Construction cost is estimated twice over a segment's life, by two variants of the same calculation that deliberately disagree.** Both variants begin from the same two lookups: a base rate in cents per foot keyed on `construction_method` — 1,237 for `AERIAL`, 4,615 for `DIRECTIONAL_BORE` and 2,845 for `TRENCH` — and a terrain multiplier in basis points keyed on `terrain_class`: 12,750 for `URBAN_PAVED`, 10,850 for `URBAN_UNPAVED`, 9,250 for `RURAL_SHOULDER`, 22,500 for `RAIL_CROSSING`, 18,250 for `HIGHWAY_CROSSING` and 24,750 for `WATER_CROSSING`.

The **preliminary variant** is written into `preliminary_cost_cents` at the moment of method selection, before anything is known about make-ready commitments or the accepted obstruction count. It is a single product with a single rounding: the segment's `length_feet` multiplied by the base rate, multiplied by the terrain multiplier in basis points, divided by 10,000, and the quotient rounded half up to whole cents. Nothing else enters it — no obstruction surcharge, no restoration obligation, no make-ready cost whatsoever.

The **bid-ready variant** is written into `bid_ready_cost_cents` when the engineer requests a bid-ready estimate for the segment, which requires the segment to be at `METHOD_SELECTED` with a non-null `construction_method` and which advances the engineering dimension `METHOD_SELECTED → DESIGN_LOCKED`. Requesting it from any other engineering status is `ERR_INVALID_SEGMENT_ENGINEERING_STATE`. This variant is materially different in two ways. First, **it prices the segment in 100-foot station blocks and rounds every block before summing them.** The segment's `length_feet` is divided by 100 with integer floor division to give the number of full station blocks, and the remainder of that division gives the leftover feet. One full block's cost is 100 multiplied by the base rate, multiplied by the terrain multiplier in basis points, divided by 10,000, rounded half up to whole cents. The leftover feet's cost is the leftover foot count multiplied by the base rate, multiplied by the terrain multiplier in basis points, divided by 10,000, rounded half up to whole cents. The construction subtotal is then the number of full blocks multiplied by one block's rounded cost, plus the leftover cost. **Summing unrounded block values and rounding once at the end is forbidden and yields a different number.** For an aerial build on urban paved terrain over 250 feet, the block-wise construction subtotal is 394,295 cents while the preliminary figure for the same segment is 394,294 cents — the one-cent gap is the specification working correctly, not an error to be smoothed away.

Second, the bid-ready variant adds three components the preliminary variant excludes. An **obstruction surcharge** of 750 dollars for each accepted obstruction — that is, 75,000 cents multiplied by the segment's `accepted_obstruction_count`. The segment's `restoration_cost_cents` as resolved above. And the **granted make-ready contribution**: the sum of `make_ready_cost_cents` over the pole attachment applications on this segment whose status is `GRANTED`, and only those — applications in `DRAFT`, `SUBMITTED`, `REVISION_REQUESTED`, `MAKE_READY_ESTIMATED`, `DENIED` or `WITHDRAWN` are excluded from the sum. Every addend is an integer, so the make-ready sum is order-insensitive. The bid-ready figure is the construction subtotal plus the obstruction surcharge plus the restoration obligation plus the granted make-ready sum.

Because the granted make-ready sum can move after a segment is design-locked, the bid-ready figure is re-derived whenever that sum changes — specifically, when a make-ready estimate is accepted and when an application is withdrawn — but **only while the segment is still at `DESIGN_LOCKED`**. A segment sitting at `WALKED` or `METHOD_SELECTED` has a null `bid_ready_cost_cents` and those events leave it null. The route's `total_preliminary_cost_cents` is the sum of `preliminary_cost_cents` across its segments and its `total_bid_ready_cost_cents` is the sum of `bid_ready_cost_cents` across its segments, in both cases counting a null child value as zero.

### 3.4. Pole Attachment Applications and Make-Ready Engineering

Where a route is built aerially it must hang on somebody else's poles, and that requires an application to the pole's owner. A `PermitCoordinator` drafts a **PoleAttachmentApplication** naming the `segment_id` whose poles are at issue, the `pole_owner` the application is filed with — `ELECTRIC_UTILITY`, `TELCO` or `MUNICIPAL_LIGHT` — and a `pole_count` of at least one pole. The application starts at `DRAFT` with `revision_round` at 0, `committed` false, `submitted_at` and `owner_note` null, and all five make-ready figures — `make_ready_items_subtotal_cents`, `make_ready_admin_fee_bp`, `make_ready_admin_fee_cents`, `make_ready_cost_cents` and `make_ready_days` — null.

Submission is permitted from `DRAFT` and from `REVISION_REQUESTED`, and both paths require the application's segment to have left `DRAFT` engineering status: a segment that has not yet had a walkout accepted refuses the submission with `ERR_WALKOUT_NOT_ACCEPTED`, since there is no point asking a utility to price make-ready on poles nobody has looked at. Submission drives the application to `SUBMITTED` and stamps `submitted_at` from the logical clock. Where the submission comes from `REVISION_REQUESTED` the `revision_round` value already incremented by the owner's revision request is retained, not reset. Submitting from any other status is `ERR_INVALID_POLE_APPLICATION_STATE`.

The `PoleOwner` answers a submitted application with an `outcome`, accompanied optionally by `owner_note` and, in one case, by `make_ready_items`. Three outcomes exist and each is a distinct transition out of `SUBMITTED`. An `owner_note` that is omitted, or supplied as an explicit `null`, leaves whatever note the row already carries untouched rather than clearing it back to null, so a note written in an earlier revision round survives a later response that supplies none.

An outcome of `REVISION_REQUESTED` moves the application `SUBMITTED → REVISION_REQUESTED`, raises `revision_round` by 1, and stores the supplied `owner_note` on the application. The coordinator may then resubmit.

An outcome of `DENIED` moves the application `SUBMITTED → DENIED`, which is terminal, and stores the supplied `owner_note`.

An outcome of `ESTIMATED` moves the application `SUBMITTED → MAKE_READY_ESTIMATED` and requires `make_ready_items` to be present with at least one element; an estimate with an absent or empty item array is `ERR_INVALID_REQUEST`. Each element of `make_ready_items` is an object carrying exactly three fields — a non-blank `pole_tag`, a `work_class` drawn from the five classes listed below, and a `quantity` of at least 1 — and an element that is not a JSON object, that omits one of the three, or that carries any further key of its own is `ERR_INVALID_REQUEST`. The array is inspected on this outcome alone: supplied alongside a `REVISION_REQUESTED` or `DENIED` outcome it is neither validated nor stored but simply ignored, however malformed its contents. From it the system creates one **MakeReadyItem** row whose `application_id` is this application, and any make-ready rows created by an earlier estimate on the same application are **deleted and replaced**, so the item set is exactly the payload's set and never an accumulation across rounds.

The make-ready cost and schedule are then derived, and **the evaluation order below is mandatory** because the administrative fee tier is keyed on an amount that superficially resembles the total but is not it.

**Step one — per-item pricing, rounded per item, then summed.** Each item's `unit_cost_cents` is looked up on its `work_class`: a `TRANSFER` costs 425 dollars per unit, a `POLE_REPLACEMENT` 5,850 dollars, a `GUYING` 780 dollars, a `RISER` 965 dollars and a `CLEARANCE_TRIM` 312 dollars and 50 cents. Each item's `lead_days` is likewise looked up on its `work_class`: 30 days for a `TRANSFER`, 90 for a `POLE_REPLACEMENT`, 45 for a `GUYING`, 25 for a `RISER` and 15 for a `CLEARANCE_TRIM`. Each item's `extended_cost_cents` is that item's `quantity` multiplied by its `unit_cost_cents`, multiplied by the owner multiplier in basis points for the application's `pole_owner` — 11,500 basis points for an `ELECTRIC_UTILITY`, 10,000 for a `TELCO` and 9,500 for a `MUNICIPAL_LIGHT` — divided by 10,000, and rounded half up to whole cents. The application's `make_ready_items_subtotal_cents` is the sum of those already-rounded per-item extended costs; the addends are integers, so the sum is order-insensitive.

**Step two — the fee tier, keyed on the pre-fee subtotal.** The administrative fee rate `make_ready_admin_fee_bp` is chosen by comparing `make_ready_items_subtotal_cents` against two ceilings: a subtotal strictly below 5,000 dollars takes 1,200 basis points; a subtotal that is at least 5,000 dollars but strictly below 20,000 dollars takes 900 basis points; a subtotal of 20,000 dollars or more takes 600 basis points. The tier is keyed on the subtotal and **never** on the final total; re-deriving the tier from `make_ready_cost_cents` is forbidden and does not converge.

**Step three — the fee itself.** `make_ready_admin_fee_cents` is `make_ready_items_subtotal_cents` multiplied by `make_ready_admin_fee_bp`, divided by 10,000, rounded half up to whole cents.

**Step four — the total.** `make_ready_cost_cents` is `make_ready_items_subtotal_cents` plus `make_ready_admin_fee_cents`.

**The schedule.** `make_ready_days` is the sum of two considerations, then capped. Take the greatest `lead_days` among the application's items — the longest single piece of work on the critical path — and add two days of pole-handling labour for each pole in the application, that is, twice the application's `pole_count`. The resulting day count is then capped at 120 days: `make_ready_days` is the lesser of that sum and 120. Note that `pole_count` is read from the application row itself, not counted from the item lines, so an application for twelve poles with a single transfer line still carries twenty-four days of handling.

Accepting the estimate is what actually grants the attachment and spends money. Acceptance requires the application at `MAKE_READY_ESTIMATED` and enforces two business rules in the order given. First, the **grade-D pole rule**: if any pole observation recorded on any walkout of that segment standing at `ACCEPTED` carries a `condition_grade` of `D` — every accepted walkout on the segment is scanned, not merely the newest one, while observations hanging off a walkout still at `OPEN`, `SUBMITTED` or `REJECTED` are ignored entirely — then this application must contain at least one make-ready item whose `work_class` is `POLE_REPLACEMENT`, because a grade-D pole cannot be climbed or loaded and must come out of the ground. An acceptance that violates this is refused with `ERR_MAKE_READY_REQUIRED`. Second, the **budget rule**: the application's `make_ready_cost_cents` must not exceed the route's `budget_available_cents`. The rejection is strict — a cost strictly greater than the available balance is refused with `ERR_BUDGET_EXCEEDED`, and an exact fit that drives `budget_available_cents` to precisely zero is allowed.

A successful acceptance moves the application `MAKE_READY_ESTIMATED → GRANTED`, sets `committed` to true, raises the route's `budget_committed_cents` by the application's `make_ready_cost_cents` and lowers its `budget_available_cents` by the same amount so that authorized always equals committed plus available, re-derives the segment's `bid_ready_cost_cents` if and only if that segment is at `DESIGN_LOCKED`, recomputes the route's `total_bid_ready_cost_cents`, and increments the versions of both the application and the route. The application's and the route's counters advance unconditionally, but the segment's own `version` advances only where that re-derivation actually changed the stored figure: a segment sitting at `WALKED` or `METHOD_SELECTED`, and equally a `DESIGN_LOCKED` segment whose recomputed bid-ready figure lands on the value already stored, is not touched at all.

Withdrawal is the compensating action, and a `PermitCoordinator` may withdraw from any non-terminal status — `DRAFT`, `SUBMITTED`, `REVISION_REQUESTED`, `MAKE_READY_ESTIMATED` or `GRANTED` — supplying an optional `reason`, which is accepted for the record of the request and then discarded: no field on the application, and no field anywhere else, persists it. Withdrawal from `DENIED` or from `WITHDRAWN` is `ERR_INVALID_POLE_APPLICATION_STATE`. It runs a four-hop cascade. Hop 1 sets `status` to `WITHDRAWN` and `committed` to false, while `make_ready_cost_cents` and the rest of the make-ready breakdown are deliberately **retained on the row for audit**. Hop 2, caused by hop 1, drops the route's `budget_committed_cents` by that application's `make_ready_cost_cents` where the application had in fact been committed, and raises `budget_available_cents` by the same amount. Hop 3, caused by hop 2, re-derives the segment's `bid_ready_cost_cents` without that application's make-ready contribution, again only while the segment is at `DESIGN_LOCKED`, and again touching the segment — and so advancing its `version` — only where the re-derived figure actually differs from the one already stored. Hop 4, caused by hop 3, recomputes the route's `total_bid_ready_cost_cents`. The application's and the route's versions both increment. Because committed budget is *defined* as a sum over granted applications rather than maintained as a running counter, this unwind is exact.

Separately, a `NetworkRecordsAdmin` may raise or lower a route's authorization by supplying a signed `delta_cents` and a `reason`. `reason` must be present as a string but may be empty or whitespace-only; `delta_cents` may be positive, negative or zero. The delta is added to `budget_authorized_cents`, the committed and available figures are re-derived so the invariant continues to hold, and the route's `version` increments — a zero delta is still a mutation and still advances the counter. Budget adjustment carries no route-status gate whatever: it is permitted from every route status, the terminal `RECORDS_UPDATED` included. A reduction that would drive `budget_authorized_cents` below the route's current `budget_committed_cents` is refused with `ERR_BUDGET_EXCEEDED` — money already committed to granted attachments cannot be de-authorized underneath them.

### 3.5. Right-of-Way Permitting Across Four Authorities

A `PermitCoordinator` drafts a **PermitApplication** against exactly one authority for exactly one segment, supplying the `segment_id`, the `authority_type` — one of `MUNICIPAL_ROW`, `RAILROAD`, `STATE_HIGHWAY` or `WATERWAY` — an `authority_name` giving the reviewing agency's actual name, and the inclusive occupancy window bounded by `work_window_start_on` and `work_window_end_on`, the latter falling on or after the former. Drafting requires the owning route to have reached `SCOPE_LOCKED`, `PERMITTING` or `CONSTRUCTION_READY`; a permit drafted against a route still in `PLANNING` is refused with `ERR_INVALID_ROUTE_STATE`, because the segment set it would be permitting is not yet frozen. A supplemental permit *may* legitimately be drafted after the route has reached `CONSTRUCTION_READY`. The application begins at `DRAFT` with `revision_round` at 0, `review_days` and `decision_due_at` null, `decided_at`, `decided_by_user_id` and `decision_note` null, and `deemed` false. Note that nothing forces the drafted `authority_type` to agree with the segment's derived `required_authority_type`; the latter is advisory and describes the authority the terrain implies, while the former records the agency actually being petitioned.

Filing the permit is a separate act, permitted from `DRAFT` and from `REVISION_REQUESTED` and requiring the route to be in `SCOPE_LOCKED`, `PERMITTING` or `CONSTRUCTION_READY`. Filing from any other permit status is `ERR_INVALID_PERMIT_STATE`. Before anything is written, the system checks the requested occupancy window against the paving moratoria: if any registered moratorium window matching the segment's `municipality_code` and `street_name` intersects the closed interval running from `work_window_start_on` to `work_window_end_on`, the filing is refused with `ERR_MORATORIUM_WINDOW_CONFLICT`. Both intervals are closed, so a work window that merely touches a moratorium at a single shared endpoint does collide. Observe that this check probes the *permit's* window, whereas the moratorium class resolved during construction-method selection probes the segment's `planned_work_start_on` — the two tests read the same registry for different purposes and can legitimately disagree.

A successful filing stamps `submitted_at` from the logical clock, computes the review schedule described below, drives the segment's permit dimension to `PENDING` from whichever of `NOT_REQUIRED`, `CLEARED` or `BLOCKED` it held — a segment already standing at `PENDING` is left exactly as it is — advances the route `SCOPE_LOCKED → PERMITTING` on the first filing anywhere on that route, recomputes the route's live complexity index, and increments the versions of the permit and the route, together with the segment's whenever that filing actually moved its permit dimension. A second permit filed against a segment already at `PENDING` therefore leaves that segment's `version` and `updated_at` untouched.

**The review schedule** is a non-linear interaction of three inputs: the authority's class, the route's topology objective, and how many revision rounds the permit has already been through. Each authority class publishes a base review cycle — 21 days for `MUNICIPAL_ROW`, 45 days for `STATE_HIGHWAY`, 90 days for `RAILROAD` and 120 days for `WATERWAY` — and each publishes a hard statutory ceiling on how long a review may run: 35 days for `MUNICIPAL_ROW`, 60 days for `STATE_HIGHWAY`, 120 days for `RAILROAD` and 150 days for `WATERWAY`. A resubmission penalty of 14 days is charged for each completed revision round, so the penalty is 14 multiplied by the permit's `revision_round`. The raw day count is the base cycle plus that penalty.

An **expedited review** is available, and it is available only when both of two conditions hold: the owning route's `topology_objective` is `RING_CLOSURE`, and the permit's `authority_type` is either `MUNICIPAL_ROW` or `STATE_HIGHWAY`. Railroad and waterway reviews are never expedited, and a spur or express-backbone route is never expedited even at a municipal counter. Where the route qualifies, the raw day count is multiplied by 7,500 basis points — a twenty-five percent reduction — and the product is **rounded up** to the next whole day. Where it does not qualify, the raw day count passes through unchanged. Either way, the result is then capped: `review_days` is the lesser of that figure and the authority's ceiling. Finally, `decision_due_at` is `submitted_at` advanced by exactly `review_days` multiplied by 24 hours of UTC instant arithmetic.

The `revision_round` value read by this calculation is the value **after** any increment applied by a prior revision request, which means the first resubmission of a permit is charged exactly one 14-day penalty. For a ring-closure route's first municipal filing, the raw count is 21 days with no penalty, the expedited figure is 21 multiplied by 7,500 basis points which is 15.75 rounded up to 16, and 16 is below the municipal ceiling of 35, so `review_days` is 16.

An `AuthorityReviewer` decides a permit under review by supplying a `decision`, optionally accompanied by a `decision_note`. Three decisions exist. All three stamp `decided_at` from the logical clock and record the deciding individual in `decided_by_user_id`, all three recompute the route's live complexity index, and all three increment the versions of the permit and the route. A `decision_note` that is omitted, or supplied as an explicit `null`, leaves any note already on the row untouched rather than clearing it, so the note a revision request left behind survives the later decision that supplies none.

**Approval** moves the permit `UNDER_REVIEW → APPROVED`, which is terminal, and sets `deemed` to false. It then drives the segment's permit dimension `PENDING → CLEARED`, but only when the segment satisfies both halves of a two-part test: at least one permit on that segment stands at `APPROVED`, and **zero** permits on that segment remain in `UNDER_REVIEW` or `REVISION_REQUESTED`. A segment with two filed permits therefore stays at `PENDING` until the second one is resolved. The transition runs out of `PENDING` and out of `PENDING` only: a segment that an earlier denial has already driven to `BLOCKED` is not rescued by a later approval on the same segment and stays `BLOCKED`, and a segment already at `CLEARED` is left as it is. When clearing the segment leaves *every* segment on the route at `CLEARED` and at least one design package on the route stands at `STAMPED`, the route advances `PERMITTING → CONSTRUCTION_READY`.

**A revision request** moves the permit `UNDER_REVIEW → REVISION_REQUESTED`, raises `revision_round` by 1, and stores the supplied `decision_note`. It deliberately leaves the segment's permit dimension at `PENDING` — the agency has asked for more paperwork, not refused the crossing — and the coordinator files the permit again, paying the resubmission penalty.

**Denial** moves the permit `UNDER_REVIEW → DENIED`, which is terminal, and runs the permit denial cascade described in section 3.6.

When an authority simply never answers, the coordinator claims the statutory outcome. This lapsed-window claim requires the permit to be at `UNDER_REVIEW` and requires the logical clock to stand **strictly after** `decision_due_at`; a claim made while the clock is at or before the deadline is refused with `ERR_REVIEW_WINDOW_OPEN`, so the deadline instant itself is still inside the window. The claim sets `deemed` to true, stamps `decided_at` from the logical clock, and leaves `decided_by_user_id` **null**, since no person decided anything. The outcome then splits on authority class, and the split is the whole point of the mechanism. For a `MUNICIPAL_ROW` permit the ordinance grants the permit when the city lets its own review window lapse: the permit moves `UNDER_REVIEW → APPROVED` with exactly the same downstream effects as an authority's approval — the same two-part segment-clearing test, the same possible route advance to `CONSTRUCTION_READY`. For a `RAILROAD`, `STATE_HIGHWAY` or `WATERWAY` permit there is no such grace: silence is refusal, the permit moves `UNDER_REVIEW → DENIED`, and hops 2 through 5 of the permit denial cascade run exactly as they would after a reviewer's denial. Either way the route's live complexity index is recomputed and both the permit's and the route's versions increment.

**The live permitting-complexity index** scores the permits actually on file, weighted by how badly each one is going, and it is recomputed on every permit status change — on filing, on an authority's decision, and on a lapsed-window claim. Its input set is every permit application whose `segment_id` belongs to a segment of this route and whose status is one of `UNDER_REVIEW`, `REVISION_REQUESTED`, `APPROVED` or `DENIED`; permits still in `DRAFT` are excluded. There is no recency window: every qualifying row counts once, at its current status, no matter how many revision rounds it has been through. The authority weights are the same as for the planned index — 10 for a municipal right-of-way, 25 for a state highway, 40 for a railroad, 50 for a waterway — and each is scaled by a status factor in basis points: 10,000 for `UNDER_REVIEW`, 15,000 for `REVISION_REQUESTED`, 2,500 for `APPROVED` and 20,000 for `DENIED`. A permit under review therefore carries its full authority weight, one in revision carries half again as much, an approved one carries a quarter of it, and a denied one carries double.

**The rounding order here is pinned.** Each permit's term is the authority weight multiplied by the status factor in basis points, multiplied by 100 to convert points into centipoints, divided by 10,000, and **rounded half up to a whole number of centipoints first**. Only then are those integer terms summed. Summing unrounded terms is forbidden. The `live_complexity_index` is that sum divided by the route's `segment_count`, rounded half up to whole centipoints; where the qualifying set is empty and the sum therefore has no addends at all, the index is 0 rather than null or an error. The index is likewise 0, rather than an arithmetic failure, in the degenerate case of a route whose `segment_count` is 0: the divisor is tested before the division is performed, so this calculation never divides by zero. Consider that same three-segment route with three filed permits: a municipal one under review contributes 1,000 centipoints, a railroad one denied contributes 8,000, and a state-highway one approved contributes 625 after its own rounding. The integer sum is 9,625, which over three segments gives 3,208.33 and a `live_complexity_index` of 3208. Because the live index counts permits rather than segments, a segment with no permit on file contributes nothing to it while a segment with two filed permits contributes twice — the divisor, however, is the route's `segment_count` in both variants.

### 3.6. Permit Denial and the Unwinding of Stamped Work

A denial is the most destructive event in this system, because a permit refusal invalidates not just the crossing but every engineering artifact that assumed the crossing. Whether the denial arrives as an `AuthorityReviewer`'s decision or as the statutory consequence of a lapsed railroad, highway or waterway review window, the same five-hop cascade runs, and every hop is caused by the hop above it.

- **Hop 1** sets the permit's `status` to `DENIED` and records `decided_at`, `decided_by_user_id` and `decision_note` — the user id being null on a lapsed-window denial.
- **Hop 2**, caused by hop 1, drives the permit's segment to `BLOCKED` in its permit dimension, from either `PENDING` or `CLEARED`. The trigger is simply that at least one permit on that segment now stands at `DENIED`. The segment's `version` increments. Those two are the only source statuses this hop acts from: a segment standing at `NOT_REQUIRED`, and equally one that an earlier denial has already driven to `BLOCKED`, is left entirely alone and is not touched at all — so a second denial on the same segment neither advances that segment's `version` nor refreshes its `updated_at`.
- **Hop 3**, caused by hop 2, releases that segment's engineering dimension `DESIGN_LOCKED → METHOD_SELECTED` and sets its `bid_ready_cost_cents` back to null, then recomputes the route's `total_bid_ready_cost_cents`. This hop is conditional on the segment having actually been at `DESIGN_LOCKED`: blocking the permit dimension does **not** by itself move the engineering dimension, and a segment sitting at `WALKED` or `METHOD_SELECTED` is left exactly where it is.
- **Hop 4**, caused by hop 3, voids the stamp on every design package on that route that stands at `STAMPED` and owns at least one `PLACED` splice point on that segment: each such package moves `STAMPED → DRAFT` with `stamp_voided_at` stamped from the logical clock. `stamped_by_user_id` and `stamped_at` are deliberately **retained** on the row for audit rather than cleared — the record that a particular engineer stamped a particular design at a particular instant survives the voiding, which is exactly what the segregation-of-duties rule at as-built certification time depends on. Each voided package's `version` increments. Being *caused by* hop 3 is a strict condition here and not merely a narrative ordering: hop 4 runs only where hop 3 actually released the segment out of `DESIGN_LOCKED`. Where the segment stood at `WALKED` or `METHOD_SELECTED` when the denial arrived, no stamp is voided at all — a package standing at `STAMPED` that holds `PLACED` work on that very segment keeps its status, keeps its null `stamp_voided_at`, and is not touched — and hop 5 consequently cannot fire either.
- **Hop 5**, caused by hop 4, drives the route `CONSTRUCTION_READY → PERMITTING`, conditional on the cascade having actually demoted at least one design package from `STAMPED` to `DRAFT` on this route. The route's `version` increments.

The route's live complexity index is recomputed as part of the same request, and the newly denied permit now contributes double its authority weight to that score.

### 3.7. Design Production: Fiber Allocation and Splice Placement

A **DesignPackage** is a numbered revision of the route's engineering drawings. A `RouteEngineer` creates one by supplying the `route_id`, the `fiber_count_allocated` giving the total fibre count of the cable assigned to this design, the `express_fiber_count` reserving fibres for pass-through traffic that is never dropped at any splice point, and `expected_route_version` as the concurrency token from section 2.7. `fiber_count_allocated` must be one of the six manufactured cable counts — 48, 96, 144, 240, 288 or 432 — and any other value is `ERR_INVALID_REQUEST`. `express_fiber_count` must be at least zero and **strictly less** than `fiber_count_allocated`; a design whose entire cable is express fibre has nothing to drop and is rejected as a malformed request. Creation requires the route to be in `SCOPE_LOCKED`, `PERMITTING` or `CONSTRUCTION_READY`; from `PLANNING` or `RECORDS_UPDATED` it is `ERR_INVALID_ROUTE_STATE`. `expected_route_version` is read as a plain integer carrying no floor of its own, so a zero or negative token is shape-valid and simply fails the comparison; and that comparison runs ahead of the route-status gate, so a stale token supplied against a route still in `PLANNING` reports `ERR_STALE_ROUTE_VERSION` rather than `ERR_INVALID_ROUTE_STATE`.

The new package's `revision` is assigned by the server as 1 plus the number of design packages that already exist on that `route_id` at creation time, so revisions number from 1 upwards per route and are never supplied by the client. The package begins at `DRAFT` with `submitted_by_user_id`, `stamped_by_user_id`, `stamped_at`, `stamp_voided_at` and `return_note` all null. Its fibre rollups are computed immediately over an empty splice-point set: `assigned_drop_fiber_count` is 0, `reserve_fiber_count` is `fiber_count_allocated` minus `express_fiber_count`, `splice_point_count` and `handhole_count` are both 0, and `spare_ratio_bp` is derived as described below. Creating the package increments the route's `version`, while the package itself is served at `version` 1: computing its opening rollups is part of the act of creating it, not a later mutation of it, so those rollups do not push a brand-new package to `version` 2.

**SplicePoint** placement is where the fibre plan actually gets built. The engineer places an enclosure by supplying the `design_id` of the revision it belongs to, the `segment_id` of the segment it sits on, the `station_feet` measuring its distance in feet from that segment's head, the `enclosure_type` — `HANDHOLE`, `AERIAL_SNOWSHOE` or `CABINET` — and the `fiber_count_dropped` giving how many fibres are dropped out of the express core there. `station_feet` must be at least 0 and no greater than the addressed segment's `length_feet`; `fiber_count_dropped` must be at least 0. Placement requires the owning design package to be at `DRAFT`; placing into a package that is in review, stamped or superseded is `ERR_INVALID_DESIGN_STATE`. A splice point is born at `PLACED` with `voided_at` null. Note that a splice point is a genuinely cross-cutting record: it belongs to a design revision and it sits on a segment, and those two parents are independent — which is precisely why a permit denial on one segment can reach a stamped design that placed work there. Those two parents are also never checked against each other: the system does **not** require the addressed segment to belong to the design package's own route, and a placement naming a segment of some entirely different route is accepted on exactly the same terms as one naming a segment of its own. There is no coherence error for that combination, and the `station_feet` ceiling, the spacing buffer and the fibre rollups all behave for it just as they do for a same-route placement.

Two constraints guard placement. The **spacing buffer** requires the new enclosure to stand at least 250 feet from every `PLACED` splice point that shares both its `design_id` and its `segment_id`: the rejection is for an absolute station separation strictly less than 250 feet, so two enclosures exactly 250 feet apart are permitted while 249 feet apart is refused with `ERR_SPLICE_SPACING_VIOLATION`. Voided siblings and siblings on other segments or other design revisions do not constrain the placement. The **fibre conservation** constraint requires that the drop not push the design's `reserve_fiber_count` below zero; a placement that would over-allocate the cable is refused with `ERR_FIBER_ALLOCATION_EXCEEDED` and writes nothing.

Every placement and every voiding re-derives the design package's five fibre rollups from the current population of `PLACED` splice points on that design. `assigned_drop_fiber_count` is the sum of `fiber_count_dropped` over those placed points, and it is 0 when none are placed. `reserve_fiber_count` — the future-customer reserve, the whole commercial point of the exercise — is `fiber_count_allocated` less `express_fiber_count` less `assigned_drop_fiber_count`. `spare_ratio_bp` is `reserve_fiber_count` multiplied by 10,000, divided by `fiber_count_allocated`, rounded half up to whole basis points. `splice_point_count` counts the placed points, and `handhole_count` counts those placed points whose `enclosure_type` is `HANDHOLE`. Rows on other design revisions of the same route never enter any of these; the addends are integers, so the sums are order-insensitive and need no tie-break. The design package's `version` increments on each placement, and that package is the only record besides the splice point itself that fibre work ever touches: neither the segment the enclosure sits on nor the owning route is mutated by a placement or a voiding, so their `version` counters and `updated_at` values do not move. A newly placed splice point is served at `version` 1, its creation and the parent's re-derivation being one act rather than two.

Voiding a placed splice point is the exact compensating action. It requires the splice point at `PLACED` — a second voiding is `ERR_INVALID_SPLICE_POINT_STATE` — and requires its owning design package to be at `DRAFT` or `IN_REVIEW`, since voiding work inside a stamped or superseded package would falsify a sealed drawing; from any other design status it is `ERR_INVALID_DESIGN_STATE`. The two gates are read in that order, so an already-`VOIDED` splice point sitting inside a `STAMPED` package reports `ERR_INVALID_SPLICE_POINT_STATE` rather than `ERR_INVALID_DESIGN_STATE`. Voiding moves the splice point `PLACED → VOIDED`, which is terminal, stamps `voided_at` from the logical clock, returns the point's `fiber_count_dropped` from `assigned_drop_fiber_count` to `reserve_fiber_count`, re-derives `spare_ratio_bp`, `splice_point_count` and `handhole_count`, and increments the versions of both the splice point and its design package.

### 3.8. Design Review, Stamping and Segregation of Duties

A design package moves through `DRAFT`, `IN_REVIEW` and `STAMPED` to the terminal `SUPERSEDED`, and two of those edges run backwards. Submitting a draft for peer review requires the package at `DRAFT` and requires it to hold at least one `PLACED` splice point; a package with none — whether because none was ever placed or because every one was voided — is refused with `ERR_DESIGN_HAS_NO_SPLICE_POINTS`. Submission moves the package `DRAFT → IN_REVIEW` and records the submitting engineer's `X-User-ID` in `submitted_by_user_id`. Submitting a package that is already in review, stamped or superseded is `ERR_INVALID_DESIGN_STATE`.

A reviewing engineer who wants changes returns the package to draft with a mandatory `return_note`; a return submitted with an absent, blank or whitespace-only note is `ERR_INVALID_REQUEST`. The return requires the package at `IN_REVIEW`, moves it `IN_REVIEW → DRAFT`, stores the text in `return_note`, and **clears `submitted_by_user_id` back to null** so that whoever resubmits the edited package becomes the new submitter of record — which in turn changes who is barred from stamping it. The package can then be edited, have splice points placed or voided, and be resubmitted. Neither the submission for review nor the return to draft reaches beyond the package itself: no segment and no route is touched by either, so the route's `version` and `updated_at` are unmoved by both operations.

Stamping is the act that seals a design, and it is guarded by three checks that fire in a fixed order after the status gate has confirmed the package is at `IN_REVIEW`.

First, **segregation of duties**: the stamping engineer's `X-User-ID` must differ from the package's `submitted_by_user_id`. An engineer who submitted a package may not stamp their own work, and the attempt is refused with `ERR_SEGREGATION_OF_DUTIES` and HTTP 403. This is a comparison of individuals, not of roles — both parties hold `RouteEngineer`.

Second, **route-wide permit clearance**: every segment whose `route_id` matches the package's `route_id` must stand at `CLEARED` in its permit dimension. One segment at `NOT_REQUIRED`, `PENDING` or `BLOCKED` refuses the stamp with `ERR_PERMIT_NOT_CLEARED`. A design is a promise that the route can be built as drawn, and a segment nobody has permission to occupy makes that promise false.

Third, the **spare-fibre floor**: the package's `spare_ratio_bp` must be at least 2,000 basis points, meaning at least twenty percent of the allocated cable must remain in the future-customer reserve after express fibre and all placed drops are accounted for. A ratio of exactly 2,000 basis points passes; anything below is refused with `ERR_SPARE_RATIO_BELOW_MINIMUM`. Over-dropping a cable today is how a route becomes unsellable in three years.

A successful stamp moves the package `IN_REVIEW → STAMPED`, records the stamping engineer's `X-User-ID` in `stamped_by_user_id`, stamps `stamped_at` from the logical clock, and clears `stamp_voided_at` back to null so that a package restamped after a cascade voiding no longer carries the stale voiding instant. `submitted_by_user_id` is deliberately **retained** rather than cleared, so a stamped row shows both individuals side by side and the duty comparison remains auditable after the fact; and any `return_note` an earlier review round left on the package survives both the resubmission and the stamp, since nothing in the system ever clears that field back to null. Every **other** design package on the same route that stood at `STAMPED` is moved to `SUPERSEDED`, which is terminal and from which no further transition exists — a route has at most one live stamped revision at any instant. Each package so demoted is itself touched, so its `version` advances and its `updated_at` refreshes, while its `stamped_by_user_id` and `stamped_at` are retained. Finally, if every segment on the route now stands at `CLEARED`, the route advances `PERMITTING → CONSTRUCTION_READY`. Both the package's and the route's `version` counters increment, and the route's does so unconditionally: a stamp that leaves the route at `PERMITTING` because some segment is not yet cleared, and equally a stamp on a route already standing at `CONSTRUCTION_READY`, still advances the route's `version` and refreshes its `updated_at` even though its `status` does not move.

The route can reach `CONSTRUCTION_READY` from either direction, and the condition is symmetric: it requires the route to be at `PERMITTING`, every segment on it to be `CLEARED`, and at least one design package on it to be `STAMPED`. Whichever of those two facts becomes true last is the one that triggers the advance — a stamp completes it when the permits were already clear, and a permit approval or a municipal lapsed-window approval completes it when the stamp was already in place. The system evaluates the condition after every authority decision, after every lapsed-window claim, and after every stamp.

### 3.9. As-Built Documentation and Closing the Network Records

Construction happens off-system; what returns is an **AsBuiltRecord**. A `FieldSurveyor` files one by supplying the `route_id`, the `design_revision` naming which stamped drawing the crew actually built from — a plain integer of at least 1, matched against the `revision` of a design package on that same route — the `as_built_length_feet` of at least 1 measuring what was really constructed, the `splice_point_count_field_verified` counting splice enclosures at least zero that were physically located and opened in the field, and the `records_system_reference` identifying the external network-records system entry under which the documentation was filed.

Filing requires the route to stand at `CONSTRUCTION_READY`; from any other route status it is `ERR_INVALID_ROUTE_STATE`. It also requires that a design package on that route with `revision` equal to the supplied `design_revision` actually be at `STAMPED` — filing against a revision number that never existed, or against one whose stamp was voided by a permit denial or superseded by a later revision, is refused with `ERR_DESIGN_NOT_STAMPED`. The record is born at `SUBMITTED` with the filing surveyor's `X-User-ID` in `submitted_by_user_id`, and with `certified_by_user_id` and `certification_note` null. Filing mutates nothing else anywhere in the system: the route it names, the segments beneath that route and the stamped design revision it cites are all left untouched, so no `version` outside the new record moves and the record itself is served at `version` 1. Nor is there any uniqueness rule — a route may carry several as-built records at once, whether against the same `design_revision` or different ones, and each is decided on its own.

The **length variance** is computed at filing time and written to `length_variance_bp`. It is the absolute difference between the record's `as_built_length_feet` and the route's `design_total_length_feet`, multiplied by 10,000, divided by that same `design_total_length_feet`, rounded half up to whole basis points. The designed total is the sum of `length_feet` over every segment whose `route_id` is this route, and every segment contributes regardless of its `engineering_status` or its `permit_status`. The variance is signless: building 200 feet short of the drawing and building 200 feet long of it score identically. Length is the only dimension scored. `splice_point_count_field_verified` is recorded for the external records hand-off and is **never** compared against the design package's own `splice_point_count`: no derivation, no gate and no error identifier in this system is keyed on it, and a filing whose field-verified count disagrees wildly with the drawing is accepted and certified on the strength of its length variance alone.

A `RouteEngineer` then certifies or rejects the filing by supplying a `decision`, optionally accompanied by a `certification_note`. Certification requires the record at `SUBMITTED`; a second decision on an already-decided record is `ERR_INVALID_AS_BUILT_STATE`, since both outcomes are terminal.

Both outcomes are guarded by the **second segregation-of-duties rule**, and it fires identically on each: the certifying engineer's `X-User-ID` must differ from the `stamped_by_user_id` of the design package on this route whose `revision` equals the record's `design_revision`. The engineer who sealed the drawing may not be the engineer who certifies that the field matched it, and the attempt is refused with `ERR_SEGREGATION_OF_DUTIES` and HTTP 403. Because a voided stamp retains `stamped_by_user_id` for exactly this purpose, the bar survives a cascade. Both outcomes record the deciding engineer's `X-User-ID` in `certified_by_user_id`, store the supplied text in `certification_note`, and increment the record's `version`.

**Acceptance** carries one further check that rejection does not: the record's `length_variance_bp` must not exceed 500 basis points, which is five percent. A variance of exactly 500 basis points is acceptable and passes; strictly above 500 is refused with `ERR_AS_BUILT_VARIANCE_EXCEEDED`. A crew that built five percent longer than the drawing has built something the drawing does not describe, and the fix is a corrected filing rather than a signature. On success the record moves `SUBMITTED → ACCEPTED` and the route makes its final hop `CONSTRUCTION_READY → RECORDS_UPDATED`, incrementing the route's `version`. That final hop is conditional on the route *still* standing at `CONSTRUCTION_READY` when the certification arrives: where a permit denial has meanwhile driven the route back to `PERMITTING`, or where an earlier as-built acceptance has already carried it to `RECORDS_UPDATED`, the acceptance is still recorded on the as-built record itself but the route is neither advanced nor touched, and its `version` and `updated_at` do not move. `RECORDS_UPDATED` is terminal: the route accepts no further transition, and segment creation, permit-application creation and design-package creation against it are all refused with `ERR_INVALID_ROUTE_STATE`.

**Rejection** moves the record `SUBMITTED → REJECTED`, which is equally terminal, and applies no variance check at all — an engineer may reject a filing whose numbers are perfectly within tolerance for reasons the numbers do not capture. Rejection explicitly leaves the route's `status` unchanged at `CONSTRUCTION_READY` and does not increment the route's `version`; the route stays open, and a rejected as-built is remedied by filing an entirely new `AsBuiltRecord` rather than by amending the rejected one.
