# Round-Trip Car Sharing Pod Assignment & Membership API — Product Requirements Document

## 1. Introduction

A round-trip car-sharing network lives or dies on two promises: that the car will be where the app said it would be, and that the member who unlocks it is allowed to drive it. This document specifies the product requirements for an API that governs both promises end to end. Membership is not a single flag but a pipeline — an applicant must be registered, screened against their driving record, and formally approved before any booking right exists. Only after that approval does a member acquire a membership that can itself be suspended, frozen, thawed, or closed, and only an approved member holding a live membership may hold a vehicle.

The physical side of the business is organised around pods. Vehicles are placed into pods, must be returned to the pod they were booked from, and are moved between pods in approved relocation bundles when neighbourhood, campus and airport demand shifts. Because a pod has a finite number of bays, every placement and relocation is capacity-checked, and the pod's derived utilization and bay accounting is recomputed after every occupancy change. Fuel and cleanliness are treated as first-class standards rather than advisory notes: members report contamination and low fuel, the network responds with cleaning orders, community signals and escalations, and repeated quality or access failures escalate into member strikes and fees.

Money is handled on a single conserved wallet ledger per member. Reservation holds are reserved into a wallet hold, late returns post tiered penalties, damage produces a member fee layered with insurance, and every charge is derived from a pinned, order-sensitive calculation so that two implementations fed identical inputs produce identical cents. Because the network is operationally parallel — two operators may screen, split and relocate at the same instant — the write paths that re-derive shared state are guarded by optimistic concurrency on the parent entity's version, and the entire system evaluates every deadline against a logical clock rather than wall-clock time.

## 2. Global Specifications & System-Wide Principles

This section collects the rules that apply across the whole API: identity and authorisation, the response envelope, pagination, the derived-value conventions, monetary precision, concurrency, and the precedence order in which validations are evaluated.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which that principal is acting. If either header is absent, or if `X-User-Role` carries a value that is not one of the declared roles below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The declared roles are spelled exactly as follows: `Anonymous`, `Member`, `PodOperator`, `UniversityAccountAdmin`, `FleetAdmin`, and `PlatformAdmin`.

A request whose role is recognised but which is not permitted for the operation being attempted is rejected with `ERR_FORBIDDEN` (HTTP 403). An `Anonymous` caller is an opaque, unauthenticated principal: `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it but never compares it to any entity's `id`. An `Anonymous` caller may file a membership application and browse public pod and vehicle listings, and nothing more.

When `X-User-Role` is `Member`, `X-User-ID` is the `id` of the acting `Member`; ownership checks on any resource that references a `Member` compare the resource's foreign-key field to `X-User-ID`. Concretely, a `Member` acting on a member-scoped resource must have `X-User-ID` equal to the owning `Member.id` of the target resource, or of the target resource's parent chain, and every such mismatch is rejected with `ERR_FORBIDDEN`. For a `Member`, the target `Member.id` in a path must equal `X-User-ID` when the acting role is `Member`, and this ownership test is evaluated immediately after the header-presence test and before any other check on the request.

When `X-User-Role` is `PodOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a workflow writes an operator identity but does not compare it to any entity's `id`. The one exception is a segregation-of-duties test described in §3.8, which compares the acting operator identifier against a member identifier recorded on an incident.

When `X-User-Role` is `UniversityAccountAdmin`, `X-User-ID` is the `id` of the acting `Account`; ownership checks on any resource that references an `Account` compare the resource's foreign-key field to `X-User-ID`.

When `X-User-Role` is `FleetAdmin` or `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. `PlatformAdmin` is a benchmark operator identity used only by the test-driving endpoints; it is never required to equal any entity `id`.

An operator who attempts to approve, split, or otherwise act on an incident they themselves raised as a member is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403); the full rule appears in §3.8.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of items returned, defaults to 10, and must be between 1 and 100 inclusive; a value below 1 or above 100 is a malformed request. `offset` is the number of items to skip and defaults to 0. Every list endpoint returns items sorted by their creation timestamp in ascending order unless a section below states otherwise, and every list response carries `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope.

### 2.4. Pod Occupancy and Bay Accounting

Pods are the network's capacity unit, and two derived values on each pod are recomputed after every occupancy-changing event: `utilization_score` and `available_bays`. Both are read-only computed fields and both are response-visible on every pod payload.

The parked count of a pod is the number of vehicles whose `home_pod_id` is that pod and whose `use_status` is anything other than `RETIRED`. The active-member count is likewise the number of vehicles whose `home_pod_id` is that pod and whose `use_status` is anything other than `RETIRED`. The periodic demand rate of a pod is the number of reservations whose `status` is `CONFIRMED` and whose `reservation_at` falls within the trailing 24 hours before the current logical clock value. From those three quantities the raw utilization is computed as the active-member count multiplied by 12, plus the periodic demand rate multiplied by 5. The pod's `utilization_score` is that raw utilization divided by the raw utilization plus 60, computed to four decimal places with round-half-up.

The pod's `available_bays` is its `capacity` minus the parked count, and it is never negative — a pod whose parked vehicles already meet or exceed its capacity reports zero available bays. A pod created with `capacity` of 0 is closed to placement and accepts no vehicle at all. On pod creation the pod reports `available_bays` equal to its `capacity` and `utilization_score` of 0.

### 2.5. Membership Posture and Booking Rights

Booking rights do not follow from registration. A member acquires them only when their `application_status` reaches `APPROVED`. The application posture is one of `APPLIED`, `SCREENING`, `APPROVED` or `DECLINED`, and a member in any posture other than `APPROVED` is refused at every booking path with `ERR_APPLICATION_NOT_APPROVED` (HTTP 409). Separately from the application posture, a membership carries a lifecycle `status` from the set `ACTIVE`, `SUSPENDED`, `FROZEN`, `CLOSED`; an operation that needs a live membership and finds none in `ACTIVE` is refused with `ERR_MEMBERSHIP_NOT_ACTIVE` (HTTP 409), and a booking attempted while the member's membership is `FROZEN` is refused with the more specific `ERR_MEMBERSHIP_FROZEN` (HTTP 409) so that the freeze is observable rather than collapsed into the generic not-active case.

A vehicle must itself be in the `AVAILABLE` posture before it will accept a reservation. Any other `use_status` freezes the vehicle to new reservations and is refused with `ERR_VEHICLE_NOT_AVAILABLE` (HTTP 409). These three gates — approval, live membership, available vehicle — are described again where each booking path is described in §3.

### 2.6. The Conserved Wallet Ledger

Each member carries exactly one cumulative wallet balance, and it is modelled as a single conserved quantity that moves between two fields rather than being created or destroyed. `wallet_credit_cents` is the member's spendable balance and `wallet_hold_cents` is the reserved-but-unspent portion held against a reservation ledger. Money moves between them; it is never deleted. When a reservation is created, the member's hold is credited with the reservation hold; when the reservation is closed, the hold is credited back to the spendable balance and the hold is zeroed, exactly once per reservation. When a reservation is resolved while overdue, the late-return penalty is posted to the member ledger and the hold that covered it is consumed first. A membership close releases a residual from the same ledger, likewise exactly once. A damage fee posted against a member is credited into the wallet, and the corresponding waiver is the conserving compensating gesture that debits it back out. Because the quantity is conserved, no operation may leave a member with a negative spendable balance, and every compensating gesture is refused when it would do so.

### 2.7. Temporal Windows and the Logical Clock

All deadlines, expiries and window comparisons are evaluated against a logical clock, not against wall-clock time. The clock's value at server startup is exactly 2026-09-01T00:00:00Z, and before any call that advances it the clock reads that default; it never falls back to real time. An operator-only test-driving capability advances the logical clock to a supplied `to_iso8601` instant, and after that call every deadline, expiry and window comparison in the system is evaluated against the new value.

Windows in this system are half-open. A window written as `[from, to)` includes its lower bound and excludes its upper bound. The practical consequence is stated where each window is used: a reservation whose `end_at` exactly equals another reservation's `start_at` does not collide with it; a maintenance window whose `scheduled_end` exactly equals another window's `scheduled_start` does not collide with it; and the early-grade revert window closes exactly at its upper bound, so the instant equal to that bound is outside the window.

### 2.8. Common Resource Properties

Every entity in this API is created by the server with a system-minted `id`: a UUID string with no type prefix, unique across the collection it belongs to. Every entity also carries a `created_at` ISO 8601 UTC timestamp with three fractional digits, recording when the row was first created.

Every entity additionally carries `updated_at` and `version` unless noted otherwise. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits that is refreshed on any change to the resource's properties, including changes to derived fields. `version` is a system-managed integer that increments by one on every mutation of the row. Every entity in this API is declared with the full common-field set, so there is no entity in this system that omits `updated_at` or `version`.

A single logical event may mutate several rows. Each such row independently refreshes its own `updated_at` and increments its own `version`; the increments are per-row and are never shared, coalesced or skipped.

### 2.9. Monetary Values and Rounding

All money in this system is held in integer cents on persisted fields, and the suffix `_cents` marks every such field. Where a calculation produces a fractional intermediate, the exact rounding instruction is given with that calculation; unless that instruction says otherwise, monetary results are computed to two decimal places using round-half-up. Two calculations in this system are deliberately order-sensitive and pin their rounding to a per-step application before summation rather than after; those pins are stated in full where the calculations appear in §3, and an implementation that rounds once at the end will produce different cents from one that rounds per step. Percentages expressed as fractions in this document are exact decimal fractions, not percentages to be divided by 100 again.

### 2.10. Optimistic Concurrency Control

Three write operations re-derive shared state and are therefore guarded by optimistic concurrency on the parent entity's version. Each requires a non-optional version field in its request payload carrying the client's last observed `version` of the named parent entity; if that value does not equal the parent entity's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412).

- Creating a reservation requires `expected_vehicle_version`, carrying the client's last observed `version` of the target `Vehicle`. A mismatch means another writer has advanced the vehicle's version since the client last read it, and the create is rejected with `ERR_STALE_VERSION`.
- Applying a relocation bundle requires `expected_pod_version_profile`, carrying the client's last observed `version` of the destination `Pod`. A mismatch means a prior approved bundle has already re-derived the destination pod's bay accounting since the client last read it, and the apply is rejected with `ERR_STALE_VERSION`.
- Splitting responsibility on an incident requires `expected_incident_version`, carrying the client's last observed `version` of the target `Incident`. A mismatch means a prior split has already re-derived the fee and the insurance layer since the client last read it, and the split is rejected with `ERR_STALE_VERSION`.

These three are the only operations in this API that accept a version field in their payload. Every other endpoint takes no version input and performs no optimistic concurrency check.

### 2.11. Nested Resource Retrieval and Path Validation

When a request targets a resource through a path that contains more than one identifier, the server resolves the identifiers from left to right and rejects the request at the first segment that does not correspond to an existing row. The error returned is the not-found error belonging to that segment's entity: `ERR_MEMBER_NOT_FOUND`, `ERR_MEMBERSHIP_NOT_FOUND`, `ERR_POD_NOT_FOUND`, `ERR_VEHICLE_NOT_FOUND`, `ERR_RESERVATION_NOT_FOUND`, `ERR_INCIDENT_NOT_FOUND`, `ERR_ACCOUNT_NOT_FOUND`, `ERR_MAINTENANCE_ORDER_NOT_FOUND`, `ERR_ACCESS_EVENT_NOT_FOUND` or `ERR_FUEL_TRANSACTION_NOT_FOUND`, each with HTTP 404. A request that names a member that does not exist is answered with `ERR_MEMBER_NOT_FOUND` before the server even attempts to resolve anything nested beneath that member.

Reverse-reachability reads follow the same discipline. A read that lists the memberships billed to an account, the vehicles whose home pod is a pod, the reservations booked at a pod, the maintenance orders raised from an incident, the access events recorded for a vehicle, or the fuel-card transactions posted against a vehicle all resolve their container segment first and return the not-found error for that container when it is missing.

### 2.12. Validation Precedence

When a request violates more than one rule, the error surfaced is the highest-precedence violation. The ordering is fixed and is stated here once, in the order in which the checks are evaluated, lowest priority number first.

The authentication checks run first: header presence and declared-role membership (`ERR_UNAUTHENTICATED`), then the role-permission and ownership test (`ERR_FORBIDDEN`). Next come the existence checks: field presence, declared type and enum membership (`ERR_INVALID_REQUEST`), then left-to-right path resolution and reference resolution for the entities named in the request. After existence comes the wallet-residual release guard (`ERR_ALREADY_RELEASED`), which is deliberately evaluated before the state preconditions of the same operation so a repeat close surfaces as a release conflict rather than as an invalid transition. Then the already-terminal guard (`ERR_ALREADY_TERMINAL`), then the declared-transition guard (`ERR_INVALID_STATE`), then segregation of duties (`ERR_SEGREGATION_OF_DUTIES`), then the screening outcome guard (`ERR_SCREENING_NOT_CLEAR`), then application approval (`ERR_APPLICATION_NOT_APPROVED`), then the frozen-membership guard (`ERR_MEMBERSHIP_FROZEN`), then the live-membership guard (`ERR_MEMBERSHIP_NOT_ACTIVE`), then vehicle availability (`ERR_VEHICLE_NOT_AVAILABLE`), then the pending-driving-record guard (`ERR_DRIVING_RECORD_PENDING`), then the duplicate-primary guard (`ERR_DUPLICATE_PRIMARY_MEMBERSHIP`), then the unique-email guard (`ERR_MEMBER_EMAIL_TAKEN`), then the return-pod guard (`ERR_WRONG_RETURN_POD`), then the odometer-regression guard (`ERR_ODOMETER_REGRESSION`), then the early-grade window guard (`ERR_REOPEN_WINDOW_CLOSED`), then the future-incident guard (`ERR_INCIDENT_IN_FUTURE`), then the fuel-reversal temporal guard (`ERR_INVALID_STATE`).

The window and capacity constraints follow: citation signature validity (`ERR_CITATION_SIGNATURE_INVALID`), then the loss-estimate guard (`ERR_LOSS_EXCEEDS_REPAIR_COST`), then the double-booking guard (`ERR_VEHICLE_DOUBLE_BOOKED`), then the maintenance-window guard (`ERR_MAINTENANCE_WINDOW_CONFLICT`), then the bundle-window guard (`ERR_BUNDLE_WINDOW_CONFLICT`), then the pod-capacity guard (`ERR_POD_CAPACITY_EXCEEDED`), then insufficient wallet credit (`ERR_INSUFFICIENT_WALLET_CREDIT`), then the wallet-adjustment validity guard (`ERR_WALLET_ADJUSTMENT_INVALID`), and finally the stale-version guard (`ERR_STALE_VERSION`), which is evaluated last of all so that a request failing an earlier check reports that earlier failure rather than the version conflict.

Two consequences of this ordering are worth calling out because they are easy to get backwards. Because the release guard sits above the state guard, a second residual release on the same membership is refused with `ERR_ALREADY_RELEASED` (HTTP 409) rather than with the generic invalid-transition error. Because the segregation-of-duties guard sits below the existence and state checks but above the business-safety gates, an operator who both raised and attempts to split an incident over which they hold no authorisation still sees `ERR_FORBIDDEN`, while an authorised operator acting on their own incident sees `ERR_SEGREGATION_OF_DUTIES`.

## 3. Business Logic & Workflows

### 3.1. Becoming a Member

An unauthenticated caller files an application by supplying a `full_name`, an `email`, a `kind`, and optionally an operator-supplied history anchor, `last_accident_fee_block`. The `kind` field is one of `INDIVIDUAL`, `STUDENT` or `EMPLOYEE`, and it determines both the damage insurance layer the member will eventually receive and the route their screening takes. `full_name` and `email` are required; `email` is the login identity and is unique across all members, so a second application carrying an email that already exists is refused with `ERR_MEMBER_EMAIL_TAKEN` (HTTP 409). On registration the new member is created in `APPLIED` with `screen_result` of `NONE`, `strikes` of 0 and `wallet_credit_cents` of 0. The optional `last_accident_fee_block` defaults to 0, where 0 means no prior at-fault damage incident; it is a 30-minute billing block index and is used only as the declared fallback when no incident row exists for the member. Registration is the only operation an `Anonymous` caller may perform.

An applicant in `APPLIED` submits their driving record by supplying a `license_state`, a `license_years_held`, and optionally a `report_decision`. Submission moves the application posture to `SCREENING` and creates a `DrivingRecordReport` with `report_status` of `SUBMITTED`. A `license_years_held` below the screening floor supports a `REFERRED` outcome rather than a `CLEAR` one. Submission is the applicant's own operation: only the member whose `id` equals `X-User-ID` may submit for themselves. The submitted report starts non-terminal, and while a report for the same member remains in `SUBMITTED` a second submission is refused with `ERR_DRIVING_RECORD_PENDING` (HTTP 409) — at most one non-terminal driving-record report may exist per member. The same rule is what governs the permitted self-loop out of `SCREENING`: once a previous report has been re-opened and is no longer awaiting a decision, the member may submit again, and the application posture remains `SCREENING` across that submission.

A screener records the outcome on a report by supplying a `report_decision`, which is one of `NONE`, `CLEAR`, `REFERRED` or `FAILED`. Recording sets the report's `report_decision` to the supplied value, sets its `report_status` to `RECORDED`, stamps `screen_completed_at` with the current logical clock value, and copies the decision onto the member as `Member.screen_result`. Only a `PodOperator` may record a decision. A report still in `SUBMITTED` is non-terminal and blocks a second submission, as described above.

With a recorded decision in hand, a `PodOperator` approves or declines the application by supplying a `decision` of `APPROVE` or `DECLINE`. Approval is the only path to booking rights. Four conditions must hold, and they are evaluated in a fixed order: first, the application posture must be `SCREENING` — any other posture is refused with `ERR_INVALID_STATE` (HTTP 409); second, the member's latest report must carry a recorded decision, meaning `Member.screen_result` is not `NONE`; third, `ERR_SCREENING_NOT_CLEAR` (HTTP 422) is returned when the recorded outcome is `REFERRED` or `FAILED`, because only a `CLEAR` outcome permits a positive decision; and fourth, the approval proceeds. Precedence between these gates follows §2.12, so a member whose screening came back `FAILED` and who is already `APPROVED` reports the invalid state rather than the screening failure.

Approval writes `Member.application_decided_at` with the current logical clock value, which is the anchor for the declared early-grade revert window, and then branches on `kind`. When `kind` is `INDIVIDUAL`, the server creates a `Membership` with `account_id` of null, `member_id` equal to the member's `id`, `tier` of `STANDARD`, `primary_flag` of true and `status` of `ACTIVE`. When `kind` is `STUDENT` or `EMPLOYEE`, no membership is created at approval — the sponsored membership is created later under the member's account by the account administrator. In both cases the member's `version` increments once.

Declining does not need a `CLEAR` screening outcome, only that a screening outcome was recorded. Declining writes `Member.application_decided_at` with the current logical clock value and closes every membership of that member whose status is `ACTIVE` or `SUSPENDED`, moving each to `CLOSED`, before incrementing the member's `version`.

### 3.2. The Early-Grade Revert Window

An approved applicant has a short window in which the approval can be unwound. The window opens at the moment of the decision — the member's `application_decided_at` — and closes 24 hours later; it is half-open, so the instant exactly equal to that close boundary is already outside the window. A `PodOperator` may invoke the revert for an `APPROVED` applicant only when four conditions hold together: the current logical clock value is strictly before `application_decided_at` plus 24 hours; the member's `screen_result` is `CLEAR`; the member's `strikes` is 0; and no membership row of that member is referenced by any reservation whose status is not `CANCELLED`. Because the window is half-open, a clock value at or past the close boundary is refused with `ERR_REOPEN_WINDOW_CLOSED` (HTTP 409). A member whose screening is `REFERRED` or `FAILED` is refused the same operation with `ERR_SCREENING_NOT_CLEAR` (HTTP 422). The revert anchor is always derived from `application_decided_at` and never from the member's `id`; when no decision timestamp is available the anchor falls back to the standard common-field ordering of `created_at` ascending.

A permitted revert performs a complete unwind. The member's `application_status` returns to `SCREENING`. Every membership of that member currently in `ACTIVE` is moved to `CLOSED`. `Member.application_decided_at` is cleared to null. The member's latest `DrivingRecordReport` is reset to `report_status` of `SUBMITTED` with `report_decision` null, so the screening must be re-recorded. The member's `version` increments once. Note that the preservation anchor for this revert is the closed membership set, not a preserved status field; there is no `status_before_*` field on the member.

### 3.3. Memberships, Tiers and the Occupancy Fee

`Membership` is the entity that carries a member's standing, their billing arrangement and their insurance layer. A membership is created either automatically at approval for an `INDIVIDUAL` applicant or explicitly by a `UniversityAccountAdmin` for a sponsored member under an account. The explicit creation supplies a `member_id`, a `tier`, a `primary_flag`, and optionally an `account_id` and a `department_code`. The `account_id` is omitted for an individual, unsponsored membership, and the `department_code` defaults to `UNSPONSORED` when it is omitted. The `tier` is one of `STANDARD`, `PLUS`, `PREMIUM` or `FROZEN`; only `PREMIUM` waves the damage deductible, as described in §3.13. The `primary_flag` defaults to false and marks whether the membership is the member's primary, billable membership — exactly one `ACTIVE` primary membership may exist per member at a time. A creation that would leave a second `ACTIVE` primary membership for the same member is refused with `ERR_DUPLICATE_PRIMARY_MEMBERSHIP` (HTTP 409). A new membership is born in `ACTIVE`.

Creating a membership runs the registration-fee-and-dues derivation. The membership dues are a flat 7000 cents. The registration fee is the 2500-cent registration base reduced by 20 percent, giving 2000 cents. The membership total is the dues plus that reduced registration fee, so 9000 cents on the default dues. The discount percentage is then selected against that post-fee total: 10 percent when the total is at least 10000 cents, and 5 percent otherwise. The billing total is the membership total minus the floor of the membership total multiplied by the selected percentage, and it is stored on the membership as `membership_billing_cents`. The 9000-cent default therefore bills 8550 cents, because the floor of 9000 multiplied by 0.05 is 450. The order of these steps is pinned: the fee is derived from the pre-fee dues and the discount is keyed on a total that already includes the fee, in a single forward pass with no fixed-point iteration. The competing reading — discounting the dues before adding the fee — is explicitly not what this system does, and it produces a different billing total from the same inputs because its discount base excludes the registration fee. `membership_billing_cents` defaults to 0 and is the raw residual from which the release in §3.4 is derived.

A membership also carries `residual_released_cents`, the cumulative wallet residual released by that membership's closes, which is the release-once anchor for the conserved quantity described below. It defaults to 0.

### 3.4. Suspension, Freezing, Thawing and Closing

Membership status moves through `ACTIVE`, `SUSPENDED`, `FROZEN` and `CLOSED`, and the cycle reopens from `CLOSED` back to `ACTIVE`. A `PodOperator` suspends an `ACTIVE` primary membership; the membership must be in `ACTIVE` and must have `primary_flag` true, and a suspension leaves every existing reservation of that member intact — `SUSPENDED` blocks new bookings only. A `PodOperator` reinstates a `SUSPENDED` membership back to `ACTIVE`. A membership can also be reinstated out of `CLOSED`, but only when the member's `application_status` is `APPROVED` and the member holds no other membership currently in `ACTIVE`; this reopen edge completes the cycle `CLOSED → ACTIVE → SUSPENDED → FROZEN → ACTIVE`.

Freezing happens as a consequence of a damage split rather than as a direct operator action. When a frozen cascade lands on a member, every membership of that member whose status is `ACTIVE` or `SUSPENDED` moves to `FROZEN`. Before the move, the status observed immediately beforehand is captured into `status_before_freeze`, which is one of `ACTIVE`, `SUSPENDED` or `NONE`, and the membership's `tier` is set to `FROZEN`. Freezing a membership is not cosmetic: every reservation belonging to that member whose status is `HELD` or `CONFIRMED` is cancelled, and the vehicle of each cancelled reservation is returned to `use_status` of `AVAILABLE`, after which the utilization and bay accounting of the affected pods is recomputed. The membership's `version` increments once. The same cascade applies whether the membership was `ACTIVE` or `SUSPENDED` going in.

`status_before_freeze` is the preservation anchor that makes thawing correct. If a membership was `ACTIVE` before it was frozen, a successful thaw returns it to `ACTIVE`; if it was `SUSPENDED`, the thaw returns it to `SUSPENDED`. The thaw target is never unconditionally `ACTIVE`. On thaw, `status_before_freeze` is reset to `NONE`.

A thaw is performed by a `PodOperator` and requires the membership to be in `FROZEN`, the incident that caused the freeze to have reached `CLOSED`, and `status_before_freeze` to hold either `ACTIVE` or `SUSPENDED`. When a membership is thawed back to `ACTIVE`, the server consults the membership's tier-restore entitlements: a `TierRestoreEntitlement` row for this membership whose `restore_status` is `PENDING` is honoured, and its `tier` is restored onto the membership, the entitlement's `restore_status` is set to `CONSUMED` and its `consumed_at` is stamped with the current logical clock value. When no pending entitlement exists, the membership's `tier` is set to `STANDARD`. Thawing back to `SUSPENDED` restores no tier and consumes no entitlement. A membership that is already in the terminal posture for this operation is refused with `ERR_ALREADY_TERMINAL` (HTTP 409), and a thaw attempted against a membership with a status other than `FROZEN` is refused with `ERR_INVALID_STATE` (HTTP 409).

Tier-restore entitlements are recorded by a `UniversityAccountAdmin` or a `PodOperator` against a membership by supplying the `tier` to restore and a `reason`. The `tier` is one of `STANDARD`, `PLUS` or `PREMIUM` — `FROZEN` is not an entitlement value. The new entitlement is born with `restore_status` of `PENDING`, and recording it increments the membership's `version`. The restore pool used at thaw time is the set of `PENDING` entitlements for that membership ordered by `created_at` ascending with ties broken by the standard common-field ordering, and the first such entitlement is the one consumed.

A `UniversityAccountAdmin` closes a membership. Closing requires the membership to be in `ACTIVE` or `SUSPENDED`; requires the member to hold no reservation whose status is `HELD`, `CONFIRMED`, `IN_USE` or `OVERDUE`; and requires that after the transition at most one membership of that member holds `ACTIVE` with `primary_flag` true. A close that would violate the primary-membership invariant is refused with `ERR_DUPLICATE_PRIMARY_MEMBERSHIP`.

Closing also releases the wallet residual, and that release is permitted exactly once per membership. The released amount is the floor of `membership_billing_cents` multiplied by 80 percent. With the default billing of 8550 cents, the released residual is 6840 cents. The released amount is credited to the member's `wallet_credit_cents`, and the membership's `residual_released_cents` accumulates what has been released. A second close of the same membership releases zero and is refused with `ERR_ALREADY_RELEASED` (HTTP 409); because of the precedence rule given in §2.12, this release guard is evaluated before the close's own state preconditions, so a repeat close surfaces as a release conflict rather than as an invalid transition. The competing reading — crediting the residual on every close call — is explicitly not what this system does, because a repeated close would double-credit a conserved quantity.

### 3.5. Pods, Vehicles and Relocation Bundles

Pods are created by a `FleetAdmin`, who supplies a `name`, a `site_type` and a `capacity`, and optionally a `fuel_floor_pct`. The `site_type` is one of `NEIGHBORHOOD`, `CAMPUS` or `AIRPORT`, and it drives the fuel-level and utilization thresholds applied at that pod. The `capacity` is the maximum number of vehicles that may concurrently call the pod home, and it defaults to 0, which means the pod is created closed to placement. The `fuel_floor_pct` is the minimum acceptable fuel level at return for that site type and defaults to 25; the network's standard floors are 25 percent for a `NEIGHBORHOOD` pod, 20 percent for a `CAMPUS` pod and 35 percent for an `AIRPORT` pod.

A pod's placement class can be revised by a `FleetAdmin` supplying a `site_type`. The revision follows the closed cycle `NEIGHBORHOOD → CAMPUS → AIRPORT → NEIGHBORHOOD`. The preamble for this cycle is that the pod must currently hold a `site_type` drawn from that same three-member set, and that the pod must have no maintenance order in `BLOCKED` or `IN_PROGRESS`. Each revision sets the new `site_type`, recomputes `utilization_score` and `available_bays` for the pod, and increments the pod's `version`.

Vehicles are placed into a pod by a `FleetAdmin` supplying a `pod_id`, a `vin`, a `model`, a `capacity_seats`, and optionally a `next_service_miles`. The `vin` is unique across all vehicles and `capacity_seats` is the vehicle's seating capacity. `next_service_miles` defaults to 0 and records the odometer value at which a completed maintenance order becomes due. The placement requires the destination pod to exist — an unknown `pod_id` is refused with `ERR_POD_NOT_FOUND` (HTTP 404) — and requires that pod's `available_bays` to be greater than 0; a pod already at capacity, or a pod created with `capacity` of 0, accepts no vehicle and the placement is refused with `ERR_POD_CAPACITY_EXCEEDED` (HTTP 409). A placed vehicle is born with `use_status` of `AVAILABLE`, `cleanliness_state` of `CLEAN`, `fuel_level_pct` of 100, `odometer_miles` of 0, and `home_pod_id` set equal to the supplied `pod_id`. Placement recomputes the pod's derived values and increments the pod's `version`.

Vehicles carry two independent posture dimensions on the same row. `use_status` is one of `AVAILABLE`, `RESERVED`, `IN_USE`, `CLEANING`, `MAINTENANCE`, `OUT_OF_SERVICE` or `RETIRED`, and only `AVAILABLE` permits a confirmed reservation; any other value freezes the vehicle to new reservations. `cleanliness_state` is a parallel dimension, independent of the use lifecycle, and is one of `CLEAN`, `REPORTED_DIRTY`, `CLEANING`, `ESCALATED` or `SUSPENDED_FOR_CLEANLINESS`. Two further computed fields make a vehicle's history visible: `odometer_miles`, the latest reported reading, advanced by each return, and `charge_total_cents`, the charged amount produced by the return charge calculation for the vehicle's most recently returned reservation. `last_known_odometer_at` is the timestamp at which the current utilization anchor period began. `home_pod_id` is set to the vehicle's `pod_id` at creation and is changed only by an approved relocation.

A `PodOperator` or a `FleetAdmin` changes a vehicle's availability by supplying an `event`. Setting the event to `OUT_OF_SERVICE` requires the vehicle's `use_status` to be `AVAILABLE` or `RESERVED` and requires that the vehicle has no reservation in `IN_USE`; it sets `use_status` to `OUT_OF_SERVICE`. Setting the event to `RETIRE` requires the vehicle to already be `OUT_OF_SERVICE` and moves it to `RETIRED`, which is the vehicle's terminal posture. Both recompute the pod's derived values and increment the vehicle's `version`.

Relocation is the mechanism by which the network rebalances vehicles across neighbourhoods, campuses and airports. A `PodOperator` applies a monthly relocation bundle by supplying a `source_pod_id`, a `dest_pod_id`, a `scheduled_start`, a `scheduled_end`, the ordered `monthly_pods` list of vehicle ids being moved, and an `expected_pod_version_profile`. The relocation window is half-open from `scheduled_start` inclusive to `scheduled_end` exclusive. Applying a bundle requires all of the following: every vehicle named in `monthly_pods` is in `use_status` of `AVAILABLE`; no vehicle named in `monthly_pods` has a reservation in `HELD`, `CONFIRMED`, `IN_USE` or `OVERDUE`; no vehicle named in `monthly_pods` has a maintenance order in `SCHEDULED`, `BLOCKED` or `IN_PROGRESS` whose window overlaps the bundle window; the destination pod has `available_bays` greater than 0; and `expected_pod_version_profile` equals the destination pod's current `version`. A bundle window that fully contains a live reservation window, or a live maintenance order window, for one of the source vehicles is a collision and is refused with `ERR_BUNDLE_WINDOW_CONFLICT` (HTTP 409); an exactly adjacent window is not a collision because the windows are half-open.

When a bundle is applied, every relocated vehicle's `pod_id` and `home_pod_id` are set to `dest_pod_id`, and both the source pod's and the destination pod's `utilization_score` and `available_bays` are recomputed. A `PodShiftBundle` row is created recording the `source_pod_id`, the `dest_pod_id` and the `monthly_pods` list, and it is born with `status` of `APPLIED` — `APPLIED` is the only value that status can take. The destination pod's `version` increments once and each relocated vehicle's `version` increments once. Relocation is a self-loop on the vehicle's posture: `use_status` is preserved unchanged while the home-pod assignment that every bay computation reads changes underneath it. If the destination pod's `available_bays` proves to be 0, or fewer than the size of the bundle, no bundle row is created and the request is refused with `ERR_POD_CAPACITY_EXCEEDED` (HTTP 409).

The bundle fee is derived in two parts, and its band selection is evaluated top-down with the first matching band winning. The bundle vehicle count is the number of entries in `monthly_pods`. The per-pod fee is 5000 cents multiplied by that count. The source available count is the number of vehicles whose `home_pod_id` is the source pod, whose `use_status` is not `RETIRED`, and which are not among the vehicles being moved. The destination available count is the number of vehicles whose `home_pod_id` is the destination pod and whose `use_status` is not `RETIRED`. The long-haul surcharge is then selected: 19600 cents when the bundle vehicle count is 0, in which case the row still registers and the fee floor applies; otherwise 3200 cents when the absolute difference between the source available count and the destination available count is at most 1; otherwise 10400 cents when the smaller of the two counts multiplied by 3 is at least the larger of the two; and otherwise 19600 cents. The `bundle_fee_cents` is the per-pod fee plus the selected surcharge. Moving 3 source-campus vehicles into an empty destination pod leaves both counts at 0, so the surcharge is 3200 and the fee is 15000 plus 3200, equal to 18200 cents.

### 3.6. Reserving a Vehicle

A reservation is placed by a `Member` and supplies a `member_id`, a `pod_id`, a `vehicle_id`, a `start_at`, an `end_at`, and an `expected_vehicle_version`, with an optional `reserved_hours`. The `reserved_hours` is the length of the booked window in hours and defaults to 0, where 0 declares a flat daily reservation rather than an hourly one. The `end_at` is the planned end of the booked window, and it is the instant from which the late-return clock is measured. Every reservation must be returned to the pod it was booked from, and the new reservation is created in the `HELD` posture before the confirmation cascade below acts on it.

Because several gates guard this single operation, their relative order matters and follows the precedence table in §2.12. Field presence, types and enum membership are checked first and are refused with `ERR_INVALID_REQUEST` (HTTP 400). The `member_id`, `pod_id` and `vehicle_id` references must then resolve, each with its own not-found error. Next comes the screening outcome check: a member whose `screen_result` is `REFERRED` or `FAILED` is refused with `ERR_SCREENING_NOT_CLEAR` (HTTP 422). Then approval: a member whose `application_status` is anything other than `APPROVED` is refused with `ERR_APPLICATION_NOT_APPROVED` (HTTP 409). Then the frozen-membership check (`ERR_MEMBERSHIP_FROZEN`), then the live-membership check, which requires a membership of that member in `ACTIVE` and is refused with `ERR_MEMBERSHIP_NOT_ACTIVE` (HTTP 409), then the vehicle-availability check (`ERR_VEHICLE_NOT_AVAILABLE`), then the double-booking check (`ERR_VEHICLE_DOUBLE_BOOKED`, HTTP 409), and finally the optimistic-concurrency check, which is refused with `ERR_STALE_VERSION` (HTTP 412). Because the stale-version guard is evaluated last, a request that also fails an earlier gate reports that earlier gate.

The double-booking check compares the requested half-open interval from `start_at` inclusive to `end_at` exclusive against every non-cancelled reservation of the same vehicle. A booked window whose `end_at` exactly equals another reservation's `start_at` is permitted and does not collide, because the interval excludes its upper bound.

Confirmation of a `HELD` reservation is a system cascade rather than a separate client action, and it is what actually takes the vehicle. It requires the member's `application_status` to be `APPROVED`, the member to hold a membership in `ACTIVE`, the requested vehicle's `use_status` to be `AVAILABLE`, and the requested vehicle's `pod_id` to equal the reservation's `pod_id`. When it fires, the reservation moves to `CONFIRMED`, the vehicle's `use_status` moves to `RESERVED`, `reservation_at` is stamped with the current logical clock value — this instant is also the anchor from which the pod's periodic demand rate is measured — the reservation's `charge_total_cents` is computed from the confirmed window using the charge calculation of §3.11, and the booking pod's `utilization_score` and `available_bays` are recomputed. The reservation's `version` increments once and the vehicle's `version` increments once.

Confirming a reservation also places a hold on the member's wallet. The member's `wallet_hold_cents` is credited by 2000 cents, with the reservation hold recorded as its named hold source. That reserved amount stays held until the reservation is closed, at which point it is returned to the spendable balance as described in §3.13.

A `Member` or a `PodOperator` may cancel a reservation that is still `HELD`, optionally supplying a `reason`. When the acting role is `Member`, the actor must be the reservation's own member, and any other member is refused with `ERR_FORBIDDEN` (HTTP 403). Cancellation requires the reservation's status to be `HELD`; a reservation that has already reached the terminal posture this operation produces is refused with `ERR_ALREADY_TERMINAL` (HTTP 409), and a reservation in any other posture is refused with `ERR_INVALID_STATE` (HTTP 409). Cancelling recomputes the booking pod's derived values and increments the reservation's `version`. The vehicle held by a cancelled reservation is released by the same posture rule that governs a no-show: a vehicle in `RESERVED` whose reservation becomes `CANCELLED` or `NO_SHOW` returns to `AVAILABLE`, the booking pod's derived values are recomputed, and the vehicle's `version` increments. `NO_SHOW` is produced by the system's own sweep rather than by a client call, and it is one of the reservation's terminal postures alongside `CLOSED` and `CANCELLED`.

### 3.7. Access, Lockouts and the Auto-Release Allowance

Access attempts are recorded by a `Member` supplying a `reservation_id`, a `member_id` and a `method`. The `method` is one of `KEY_CARD` or `APP`. The event's `vehicle_id` is derived from the reservation and its `pod_id` is derived from that vehicle's `pod_id` at creation; the attempt's `occurred_at` is stamped by the server. An attempt starts out as `FAILED` unless the cascade below promotes it. An attempt by a member who is not `APPROVED` is refused with `ERR_APPLICATION_NOT_APPROVED` (HTTP 409), and an attempt by a member with no membership in `ACTIVE` is refused with `ERR_MEMBERSHIP_NOT_ACTIVE` (HTTP 409).

A successful attempt is what starts the trip, and it advances two postures at once. For the reservation, a `CONFIRMED` reservation whose vehicle is `RESERVED` and whose member matches the event's `member_id` moves to `IN_USE`. For the vehicle, a `RESERVED` vehicle whose reservation is `CONFIRMED` and whose member matches the event's `member_id` moves to `IN_USE`. On success the event's `outcome` is set to `SUCCESS`, the reservation's `version` increments and the vehicle's `version` increments.

A failed physical attempt can be recovered in one of two ways. The first is an operator-driven auto-release cascade, invoked by a `PodOperator` against a `FAILED` event. It requires the event's reservation to be `CONFIRMED`, the event's vehicle to be `RESERVED`, and the event's member to have consumed at most one auto-release allowance. When it succeeds, the event's `outcome` becomes `SUCCESS` and its `auto_release_used` is set to true, the reservation moves to `IN_USE`, the vehicle moves to `IN_USE`, and the event's `version` increments. Only one auto-release allowance may be consumed per reservation, so a second consumption against the same reservation is refused. The second recovery path is a clean retry: a `FAILED` event whose reservation is `CONFIRMED` and whose vehicle is `RESERVED` becomes a `SUCCESS` when the previous `FAILED` event for that reservation used `KEY_CARD` and the retry is made with `method` of `APP`. A clean retry moves the reservation and vehicle to `IN_USE` and increments the event's `version`, but it consumes no auto-release allowance and leaves `auto_release_used` false.

A member who cannot get in reports a lockout rather than waiting. The report is filed by a `Member` against a `FAILED` event, and it requires the event's `outcome` to be `FAILED`, the event's reservation status to be `CONFIRMED` or `IN_USE`, and — when the acting role is `Member` — the acting member identifier to equal the event's `member_id`; any other member is refused with `ERR_FORBIDDEN` (HTTP 403). Reporting sets the event's `outcome` to `LOCKOUT_REPORTED` and stamps `lockout_reported_at` with the current logical clock value.

The report also runs the member's strike escalation and posts its fee. Strike escalation maintains a cumulative load for the member, built from the weights of the member's terminal quality and access violations. A fuel-level violation weighs 1, a cleanliness violation weighs 2 and a lockout violation weighs 3. The cumulative load is the sum of those weights over the member's terminal-violation snapshot, which is the tuple of violation types applied to the member in ascending creation-time order, with ties broken by ascending tuple-index order. That snapshot is frozen at the first quality or access strike transition: it includes every later-applied violation type, and its frozen position for each type is that type's first application position, so no violation can be counted after itself. The member's `strikes` is then the ceiling of the cumulative load divided by 2. The overage count is the member's `strikes` minus 2, floored at zero, and the violation fee is 1000 cents multiplied by that overage count. A cumulative load of 6 — one fuel-level, one fuel-level, one cleanliness and one lockout violation, weighing 1 plus 1 plus 2 plus 3 — yields `strikes` of 3, an overage count of 1 and a fee of 1000 cents. The competing reading charges each violation's weight directly with no ceiling division and would report 7 for that same load instead of 1; this system does not do that. A first lockout report additionally credits the member's `wallet_credit_cents` by 500 cents. The member's `version` increments once and the event's `version` increments once.

### 3.8. Returning the Vehicle

The return is the member's own gesture and only the booking member may perform it. Its payload carries the `returned_pod_id`, the `returned_odometer_miles`, the `returned_fuel_level_pct`, and an optional `contamination_level`. The `contamination_level` is a cleanliness severity from 0 to 3, where 0 means no contamination was reported, and it defaults to 0.

Returns are gated in the precedence order of §2.12. A reservation that already sits in the terminal posture this operation produces is refused with `ERR_ALREADY_TERMINAL` (HTTP 409) before any other business check, and a reservation whose status admits no declared return edge is refused with `ERR_INVALID_STATE` (HTTP 409). Next is the return-pod rule: the `returned_pod_id` must equal the reservation's `pod_id`, because a round-trip vehicle must come home to the pod it was booked from, and a return to any other pod is refused with `ERR_WRONG_RETURN_POD` (HTTP 422). Then the odometer rule: `ERR_ODOMETER_REGRESSION` (HTTP 422) is returned when the reported `returned_odometer_miles` is lower than the vehicle's current `odometer_miles`. Finally the loss rule: a request whose ambient loss estimate exceeds the incident's `repair_cost_cents` is refused with `ERR_LOSS_EXCEEDS_REPAIR_COST` (HTTP 422).

The declared return edge on the reservation runs from `IN_USE` to `RETURNED` and requires the reservation to be in `IN_USE`, the `returned_pod_id` to equal the reservation's `pod_id`, the reported `returned_odometer_miles` to be greater than or equal to the vehicle's `odometer_miles`, and the member to be `APPROVED` while holding a membership in `ACTIVE`. When it fires, `returned_at` is stamped with the current logical clock value, `returned_pod_id` is recorded on the reservation, and `late_minutes` is set to the greater of zero and the whole number of minutes between the reservation's `end_at` and its `returned_at` — so an early return reports zero late minutes rather than a negative count. The vehicle's `fuel_level_pct` is set to the reported `returned_fuel_level_pct` and its `odometer_miles` to the reported `returned_odometer_miles`. The reservation's `charge_total_cents` is recomputed by the return charge calculation of §3.9, and that same amount is copied onto the vehicle's own `charge_total_cents`, so the vehicle reflects whatever its latest close produced while the reservation keeps its own figure. The booking pod's `utilization_score` and `available_bays` are recomputed. The reservation's `version` increments once and the vehicle's `version` increments once.

The vehicle's posture is resolved in the same event. A vehicle in `IN_USE` whose return reports a `contamination_level` of 3 or more moves to `CLEANING`: its `cleanliness_state` is set to `CLEANING`, its fuel level and odometer take the reported readings, and a maintenance order is created with `blocking` false, `status` of `SCHEDULED` and `reason` of `CLEANING`. A vehicle in `IN_USE` whose return reports a `contamination_level` of 2 or less moves to `AVAILABLE`, taking the reported fuel level and odometer. Both branches require the `returned_pod_id` to equal the reservation's `pod_id` and the returning member to be `APPROVED` with a membership in `ACTIVE`, both recompute the booking pod's derived values, and both increment the vehicle's `version`. A vehicle left in `CLEANING` still displaces one service bay of its home pod, because the pod's parked count reads every vehicle whose `use_status` is not `RETIRED` regardless of whether that vehicle is currently in use.

Returning also raises community signals on two triggers. When the return reports a `contamination_level` of 1 or 2, a `CommunitySignal` is created with a `signal_type` of `CLEANLINESS` and a `member_id` equal to the returning member. When the reported `returned_fuel_level_pct` is below the booking pod's `fuel_floor_pct`, a `CommunitySignal` is likewise created with a `signal_type` of `CLEANLINESS` and a `member_id` equal to the returning member. These signals are how the network learns about vehicles that came back dirty or dry without an operator walking the lot.

The reservation's lateness dimension is resolved by the same event, independently of the physical return. A return that lands late carries the reservation into the `OVERDUE` dimension, and a return that is on time does not. The mechanics of that dimension, and the sweep that enforces it against elapsed windows, are described in §3.10; the important point here is that `late_minutes`, the physical `returned_at` and the overdue dimension are three separate facts, and a reservation may be physically returned while still carrying an overdue posture.

### 3.9. The Return Charge, Fuel Adjustment and Standards

One calculation produces the single `charge_total_cents` written on return, on overdue resolution and on close, and its evaluation order is pinned at every step. The hourly rate is 1150 cents. Lateness is measured in 30-minute blocks, the grace period is 10 minutes, the multiplier applied to the first late block is 1.5, and each subsequent late block is escalated by a further factor of 1.17 applied to the previous block's rate. Escalation stops after the third block: blocks beyond the third contribute nothing further.

The reference instant is `returned_at` when that value is not null, and otherwise the reservation's `end_at`. `late_minutes` is the greater of zero and the whole number of minutes between the reservation's `end_at` and that reference instant. The number of lateness blocks is zero when `late_minutes` is at most the 10-minute grace period, and otherwise the whole number of 30-minute blocks that covers `late_minutes`, rounded up. For blocks numbered 1 through 3 within the lateness count, the per-block raw rate is the hourly rate multiplied by 1.5 for block 1, and the previous block's rate multiplied by 1.17 for blocks 2 and 3; block 0 and any block numbered above 3 contribute a raw rate of zero. Each qualifying block's raw rate is individually rounded half-up to a whole number of cents before anything else happens, and the late fee is the sum of those individually rounded block rates. The rounding order here is pinned deliberately: round each block, then sum — an implementation that sums the unrounded rates and rounds once will not produce the same cents. With a 4-hour booking and a return 75 minutes past `end_at`, the lateness count is 3 blocks, the per-block late rates round to 1725, 2018 and 2361 cents, and the late fee is 6104 cents.

The fuel deficit is the greater of zero and the booking pod's `fuel_floor_pct` minus the reported `returned_fuel_level_pct`. The fuel surcharge is the deficit percentage multiplied by 12, divided by 100, multiplied by the 450-cent surcharge ceiling, rounded up to a whole cent. The fuel-level fine is 2500 cents multiplied by the greater of zero and the reported fuel level's bucket minus 1, where the bucket is 1 for a fuel percentage from 35 through 100 inclusive, 2 for a percentage from 1 through 34 inclusive, and 3 for a percentage of exactly 0. An on-time reading at the pod floor therefore carries a deficit of zero and a bucket of 1, and contributes neither a surcharge nor a fine. When the deficit is zero but the reported bucket is 3, the surcharge is the flat reduced 750-cent amount instead of the measured formula; when the deficit is zero and the bucket is 1 or 2, no surcharge is added. The competing reading applies the flat 750-cent amount to any deficit at all, which would produce 750 cents for a 15-point deficit where the measured formula produces 810 cents; this system applies the measured formula, so a 20-percent pod floor against a 35-percent reading yields a deficit of 15 points and a surcharge of the ceiling of 15 multiplied by 12 divided by 100, multiplied by 450, which is 810 cents.

The time component depends on the reservation class. For an hourly reservation the time component is the number of on-time blocks multiplied by the 1150-cent hourly rate, plus the number of billed late blocks multiplied by the hourly rate multiplied by the 1.5 late multiplier. The number of billed late blocks is the lateness block count capped at 3, and the number of on-time blocks is `reserved_hours` minus the billed late blocks, floored at zero. For a daily reservation — that is, one whose `reserved_hours` is 0 — the time component is the flat daily rate of 6450 cents. For a reservation whose `reserved_hours` is at least 1, the daily rate is read from an ordered table evaluated top-down, first match winning: 4650 cents when `reserved_hours` is at least 120, 5450 cents when it is at least 72, and 6450 cents when it is at least 24; when `reserved_hours` is below 24 in this branch the daily rate is 7450 cents.

The pre-discount amount is the time component plus the late fee plus the fuel surcharge plus the fuel-level fine. The projected vehicle charge is the vehicle's existing `charge_total_cents` plus that pre-discount amount, and it exists only to select the discount band. The discount percentage is 20 percent when the projected vehicle charge is below 100000 cents and 15 percent otherwise. The final `charge_total_cents` is the pre-discount amount minus the floor of the pre-discount amount multiplied by the selected discount percentage. The discount is keyed on the projected vehicle charge but applied to the pre-discount amount, and it is never keyed back onto the discounted amount — there is no circular re-entry. A reservation with a 4-hour window, no prior vehicle charge, an on-time reading at the pod floor and a fresh reservation therefore charges 4600 cents in the pre-discount amount and 3680 cents after the 20-percent discount, for both a zero-minute return and a 10-minute return. The same reservation returned 11 minutes late has a pre-discount amount of 6900 cents and charges 5520 cents; returned 31 minutes late it has a pre-discount amount of 9493 cents and charges 7595 cents; and returned 75 minutes late with a 6-point fuel deficit it has a late fee of 6104, a surcharge of 324 and a pre-discount amount of 12753 cents, charging 10203 cents. That last figure is the one to check rounding order against: summing the unrounded block rates before rounding would give 12754 and charge 10204 cents. An unresolved overdue reservation that is swept and then resolved carries no fuel deficit and no time adjustment beyond the lateness itself; resolved at the sample instant 2026-09-10T12:00:00Z it produces a pre-discount amount of 12429 cents and charges 9944 cents.

Because the vehicle carries its own `charge_total_cents`, and because that field feeds the projected-vehicle-charge band selection, the discount a member receives on a return depends on the charged amount left behind by the vehicle's previous close. Implementers should read the band selection as reading the vehicle's stored field at the instant the current return is evaluated.

### 3.10. The Overdue Dimension and Closing Out

The lateness dimension is a second lifecycle track that runs alongside the physical return, and it is why a reservation can be closed and still be late. A reservation whose window has elapsed without a physical return is carried into `OVERDUE` by the system's lateness sweep, which is invoked by a `PodOperator` rather than by a member. The sweep has two declared entry edges: from `CLOSED` when the current logical clock value is strictly greater than the reservation's `end_at` and the reservation's `returned_at` is null, and from `RETURNED` under the same two conditions. Before either edge fires, the status observed immediately beforehand is captured into `status_before_overdue` — one of `CONFIRMED`, `IN_USE`, `RETURNED` or `NONE` — and that capture is the preservation anchor. The sweep then sets the reservation's status to `OVERDUE`, recomputes `charge_total_cents` by the return charge calculation of §3.9, and increments the reservation's `version`.

Resolution of an overdue reservation is performed by a `PodOperator` and requires the reservation to be in `OVERDUE` and its `status_before_overdue` to hold `CONFIRMED` or `IN_USE`. The resolution moves the reservation to `CLOSED`, never to `RETURNED`, regardless of what the preserved status was; it stamps `returned_at` with the current logical clock value when that field is still null; it sets the vehicle's `use_status` to `AVAILABLE` when the preserved status was `IN_USE`; it recomputes `late_minutes` as the greater of zero and the whole minutes between `end_at` and `returned_at`; it recomputes `charge_total_cents` by the return charge calculation; and it increments the reservation's `version`.

Resolving an overdue reservation also posts the late-return penalty to the member ledger, and that penalty is a distinct calculation surface from the reservation charge. It is keyed on the vehicle's fuel-card ledger rather than on the reservation's own charge. Its qualifying set is every `FuelCardTransaction` whose `vehicle_id` equals the reservation's `vehicle_id` and whose `status` is `POSTED`, ordered by `created_at` ascending with ties broken by the standard common-field ordering — never by a random identifier. For a count `n`, the last-transaction total is the sum of `amount_cents` over the last `min(n, count)` entries of that ordered list, and the ledger delta for `n` is the last-transaction total for `n + 1` minus the last-transaction total for `n`. When the vehicle has no posted fuel-card transaction at all, every last-transaction total is zero, so the ledger delta is zero and a large overage resolves to the flat 8000-cent tier with no ledger contribution.

The penalty itself is tiered on a quantity `S` derived from the same lateness measure used above. The reference instant is `returned_at` when it is not null and otherwise the reservation's `end_at`; `late_minutes` is the greater of zero and the whole minutes between `end_at` and that instant; the lateness block count is zero when `late_minutes` is at most the 10-minute grace period and otherwise the whole number of 30-minute blocks covering `late_minutes`, rounded up; and `S` is that block count minus the grace period expressed in blocks, which is the ceiling of 10 divided by 30, namely 1, floored at zero. The tier selection uses at-least comparisons, and they are evaluated in ascending order so the highest satisfied tier wins: when `S` is 0 the member penalty is 0; when `S` is at least 1 the penalty is the flat 6000-cent tier; when `S` is at least 2 the penalty is the flat 8000-cent tier; and when `S` is at least 3 the penalty is the flat 8000-cent tier plus the ledger delta for `S - 3`. Neither the 6000-cent nor the 8000-cent tier is ever scaled by elapsed hours — a lateness that reaches exactly `S` of 1 lands on the 6000-cent tier and not on a partial or prorated amount. The competing reading multiplies a flat 6000-cent fee by the number of lateness blocks, which would charge 18000 cents for three blocks where this system charges 6000; this system scales with the ledger delta above the top tier and with nothing else.

The penalty is posted as a service credit on the member's wallet, and the hold reserved against the reservation is consumed by it.

### 3.11. Closing a Reservation

Closing is the step that returns the reservation's reserved wallet amount to the member. It is performed by the booking `Member` or by a `PodOperator`, and it requires the reservation to be in `RETURNED` with a valid `FuelCardTransaction` whose `status` is `POSTED` already posted against it — a reservation returned but not yet refuelled cannot be closed. A reservation that is already `CLOSED` is refused with `ERR_ALREADY_TERMINAL` (HTTP 409), and a reservation in any other posture is refused with `ERR_INVALID_STATE` (HTTP 409).

Closing stamps `closed_at` with the current logical clock value. It then credits the member's `wallet_credit_cents` by the member's `wallet_hold_cents` and sets `wallet_hold_cents` to 0, so the amount reserved at booking is released back to the spendable balance exactly once per reservation. The hold release is applied before any referral credit computed in the same transaction.

Closing runs one more calculation, the residual release, which is the compensating half of the utilization-service gesture. The released amount stored on the maintenance order is the sum of the return charges, measured after the membership discount, of the other reservations of that vehicle that were closed within the last 30 days. When the order is completed, that amount is credited to the member wallet of the member who owns the vehicle's most recent `CLOSED` reservation, but only when that released amount is greater than zero; otherwise no credit is posted. See §3.13 for the completion path that posts it.

Closing also triggers two automatic consequences. First, when the vehicle has at least 8 `CLOSED` reservations whose `closed_at` falls inside the last 30 days, a maintenance order is created with `blocking` true, `status` of `SCHEDULED` and `reason` of `UTILIZATION_SERVICE` — the network schedules service on vehicles that are being worked hard. Second, when the reservation's `charge_total_cents` is greater than 5000 cents and the member already has at least 2 `CLOSED` reservations within the last 180 days, the member's `wallet_credit_cents` is credited by 500 cents and the member's `referral_invites` is incremented by 10. The referral condition is evaluated against the charge as computed before any close-hop surcharge is folded in. The member's `version` increments only when a referral credit is actually issued, and the reservation's `version` always increments once.

### 3.12. Cleanliness, Community Signals and the Fuel Card

Members and operators both raise community signals by supplying a `pod_id`, a `signal_type`, a `message`, and optionally a `reservation_id` and a `vehicle_id`. The `signal_type` is one of `CAMPUS`, `CLEANLINESS` or `AVAILABILITY`. The server stamps the signal with `created_at_signal` equal to the current logical clock value and records the acting member as the signal's `member_id`; the `reservation_id` is populated when one was supplied. Campus signals are the only signal class counted toward the pod threshold; cleanliness signals are the ones that move a vehicle's cleanliness posture, and availability signals are recorded for operational visibility without changing any posture.

The cleanliness posture is a parallel track on the vehicle row, independent of `use_status`, and it advances on cleanliness signals and on cleaning orders. A vehicle in `CLEAN`, `REPORTED_DIRTY` or `CLEANING` that receives a cleanliness signal moves to `REPORTED_DIRTY`, provided the signal's `pod_id` equals the vehicle's own `pod_id`; a signal raised against a pod that is not the vehicle's home pod is refused. That transition records the acting member on the signal and increments the vehicle's `version`. A second cleanliness signal against the same vehicle within 180 days moves the vehicle from `REPORTED_DIRTY` to `ESCALATED`, provided the vehicle already has at least one earlier cleanliness signal whose `created_at_signal` is not earlier than the current logical clock value minus 180 days, and provided the acting member is not the member who raised the previous cleanliness signal for that vehicle — a member may not escalate their own earlier report. On that escalation, when the vehicle has at least three cleanliness signals created within the last 180 days, its `use_status` is additionally set to `OUT_OF_SERVICE`, and the vehicle's `version` increments.

Cleaning orders are what bring a vehicle back. Completing a maintenance order whose `reason` is `CLEANING` resolves the cleanliness posture by departure point: a vehicle in `ESCALATED` moves to `SUSPENDED_FOR_CLEANLINESS` and its `use_status` is set to `OUT_OF_SERVICE`; a vehicle in `REPORTED_DIRTY` moves to `CLEAN`; and a vehicle in `CLEANING` moves to `CLEAN`. The `ESCALATED` outcome additionally requires the vehicle's `use_status` to be `CLEANING`, recomputes the pod's derived values, and is the posture from which a vehicle must be explicitly restored. Restoration is an operator gesture against a vehicle whose cleanliness posture is `SUSPENDED_FOR_CLEANLINESS`, and it is permitted only when no cleanliness signal for that vehicle has a `created_at_signal` not earlier than the current logical clock value minus 180 days — the reporting window must have cleared. Restoration sets the cleanliness posture to `CLEAN` and, when the vehicle's `use_status` was `OUT_OF_SERVICE`, returns it to `AVAILABLE`, then recomputes the pod's derived values and increments the vehicle's `version`.

Maintenance orders are the network's service vehicle. An order is created either directly against a vehicle by a `PodOperator`, supplying the `vehicle_id`, a `reason`, a `blocking` flag, a `scheduled_start` and a `scheduled_end`, or from an incident, where a `pod_id` is supplied instead of a `vehicle_id`. On the direct path the order's `pod_id` is read from the vehicle and is never taken from the caller. The `reason` is a short reason code; the `blocking` flag defaults to true and declares whether the order freezes reservations for the vehicle; the service window runs from `scheduled_start` inclusive to `scheduled_end` exclusive; and the `incident_id` is populated when the order was raised from an incident. A new order is born in `SCHEDULED`.

The temporal overlap rule guards scheduling: the requested half-open window must not overlap any existing maintenance order for the same vehicle whose status is `SCHEDULED`, `BLOCKED` or `IN_PROGRESS`, nor any reservation of that vehicle whose status is `CONFIRMED`, `IN_USE` or `OVERDUE`. A collision is refused with `ERR_MAINTENANCE_WINDOW_CONFLICT` (HTTP 409); an adjacent window whose `scheduled_end` exactly equals the other window's `scheduled_start` does not collide.

A blocking order moves straight into `BLOCKED` and takes the vehicle with it: the order requires that no reservation of the vehicle in `CONFIRMED`, `IN_USE` or `OVERDUE` overlaps its window and that no other order in `SCHEDULED`, `BLOCKED` or `IN_PROGRESS` overlaps it, and on success the vehicle's `use_status` is set to `MAINTENANCE`, the order's pod derived values are recomputed, the vehicle's `version` increments and the order's `version` increments. A non-blocking order remains `SCHEDULED` and never displaces a bay; the same overlap rule against other orders still applies, and the permitted self-loop out of `SCHEDULED` for a non-blocking order means a repeated registration is still observable through the order's incremented `version`. A `PodOperator` starts a `BLOCKED` order, moving it to `IN_PROGRESS` and incrementing the order's `version`; a start attempted against an order in any other posture is refused with `ERR_INVALID_STATE` (HTTP 409).

Completion requires the order to be in `IN_PROGRESS`; any other posture is refused with `ERR_INVALID_STATE` (HTTP 409). Completing moves the order to `COMPLETED`, which together with `CANCELLED` is one of the order's two terminal postures, and stamps `completed_at` with the current logical clock value. When the order's `reason` is `UTILIZATION_SERVICE`, the vehicle's `next_service_miles` is set to its `odometer_miles` plus 5000, which is the distance at which the next service becomes due. When the order's `reason` is `CLEANING` and the vehicle's `use_status` is `CLEANING`, the `use_status` returns to `AVAILABLE`. The cleanliness posture is then resolved by the reason-and-departure rules given above — `ESCALATED` to `SUSPENDED_FOR_CLEANLINESS`, and either `REPORTED_DIRTY` or `CLEANING` to `CLEAN`. When the order carries an `incident_id`, the referenced incident is moved to `CLOSED`. The order's `released_cents` is set to the sum of the return charges, measured after the membership discount, of the other reservations of that vehicle that were closed within the last 30 days, and when that amount is greater than zero it is credited to the member wallet of the member who owns the vehicle's most recent `CLOSED` reservation. The order's pod derived values are recomputed, the vehicle's `version` increments and the order's `version` increments.

Cancellation is permitted by a `PodOperator` for an order in `SCHEDULED` or `BLOCKED`, optionally supplying a `reason` of `CUSTOMER_IMPACT`; cancelling moves the order to `CANCELLED`, its other terminal posture, and increments the order's `version`. When the cancellation reason is `CUSTOMER_IMPACT` and the vehicle is in `MAINTENANCE` with an active order of that same reason, the vehicle is released from `MAINTENANCE` back to `AVAILABLE`, its pod derived values are recomputed and its `version` increments. Orders never take the vehicle out of a posture that a different order is still holding.

Fuel purchases are posted against a reservation and a vehicle by a `Member` or a `PodOperator`, supplying a `reservation_id`, a `vehicle_id`, an `amount_cents` and a `gallons_hundredths`, the last being gallons in hundredths of a gallon. A new transaction is born with `status` of `POSTED`, and its `fuel_level_after_pct` starts at 0 and is set to the reported level of the transaction that follows it — the field therefore reads zero until a later purchase supplies the reading. Posted transactions are the source of the ledger deltas described in §3.10 and of the vehicle's fuel-card ledger total. A `PodOperator` reverses a posted transaction only when the transaction's status is `POSTED`, the transaction's reservation is in `RETURNED` or `CLOSED`, and the reservation carries no `returned_fuel_level_pct` greater than the transaction's `fuel_level_after_pct`. A transaction whose reservation has already progressed past the point where its reading may be unwound is refused with `ERR_INVALID_STATE` (HTTP 409). Reversal sets the transaction's status to `REVERSED`, sets the vehicle's `fuel_level_pct` to the transaction's `fuel_level_after_pct`, and increments both the transaction's and the vehicle's `version`.

### 3.13. Damage, Insurance and the Severity Fork

An incident is opened by a `Member` or a `PodOperator` against a reservation, supplying the `reservation_id`, a `vehicle_id`, a `member_id`, an `incident_type`, and optionally a `repair_cost_cents` and a `loss_estimate_cents`. The `incident_type` is one of `DAMAGE`, `MECHANICAL` or `THEFT`, and only a `DAMAGE` incident carries a member fee and insurance layers — the other two classes are recorded for operational history. The supplied `vehicle_id` and `member_id` must agree with the reservation's own `vehicle_id` and `member_id`; a disagreement is refused with `ERR_INCIDENT_REFERENCE_MISMATCH` (HTTP 422). A `loss_estimate_cents` that exceeds the incident's `repair_cost_cents` is refused with `ERR_LOSS_EXCEEDS_REPAIR_COST` (HTTP 422). A new incident is born in `OPEN`, with `damage_fee_charged` false, `fee_version` 0, `severity_score` 0 and `severity_fee_cents` 0. The `assigned_driver_member_id` — the member responsible for damage found on return and therefore charged the damage fee — stays null while the incident is `OPEN`. At most one active incident may exist per reservation.

Assessing responsibility is a `PodOperator` gesture, and it is guarded by two independent protections beyond the ordinary ones. First, segregation of duties: the acting operator identifier must not equal the incident's recorded member identifier, so the same identity cannot both raise an incident and split it; a violation is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Second, optimistic concurrency: the request must carry `expected_incident_version` equal to the incident's current `version`, and a mismatch is refused with `ERR_STALE_VERSION` (HTTP 412). An incident whose opening instant is later than the current logical clock value is refused with `ERR_INCIDENT_IN_FUTURE` (HTTP 422), because it cannot be time-ordered against the reservation window. An incident already in the terminal posture this operation produces is refused with `ERR_ALREADY_TERMINAL` (HTTP 409).

The declared edge into assessment runs from `OPEN` to `ASSESSED` and additionally requires the incident to be in `OPEN`, its `incident_type` to be `DAMAGE`, and its `repair_cost_cents` to be present. When the incident's member holds no membership in `ACTIVE`, the assessment cannot proceed and the refusal is reported as `ERR_MEMBERSHIP_NOT_ACTIVE` (HTTP 409), and the refusal is made observable by recording a secondary marker for that refusal on the incident itself.

A permitted assessment writes a family of derived values onto the incident. The `assigned_driver_member_id` becomes the member who last operated the vehicle within the booking window. The `assigned_damage_block_position` becomes the greater of 1 and the whole number of minutes between the reservation's `start_at` and the incident's creation instant divided by 30, rounded up — so an incident is always attributed to at least the first 30-minute billing block. The `damage_fee_estimate_cents` is the projection produced by the estimate variant, and the `member_damage_fee_cents` is the fee of record produced by the final variant. The `insurance_layer` is set from the insurance tier selected by the pinned selector described below. The `fee_version` is set to 1, the status is set to `ASSESSED`, and the incident's `version` increments once.

The insurance tier used for the fee of record is selected from the member's memberships as follows, and no other ordering may be substituted. Among the member's membership rows whose status is `ACTIVE`, the selector takes the row whose `tier` has the highest rank in the order `PREMIUM` above `PLUS` above `STANDARD`; among rows of equal rank it takes the earliest `created_at`; and the member's `Member.id` and the membership's `Membership.id` never participate in the selection. A membership whose `tier` is `FROZEN` is treated as the preserved base tier it was frozen from, and never as `PREMIUM`.

The member fee is a two-variant calculation whose estimate and final halves are both written, and whose tiers are keyed on that selected tier. A `STANDARD` membership — and any membership falling back to the base tier — carries a zero deductible and a member liability fraction of 1.00. A `PLUS` membership carries a 2000-cent deductible and a member liability fraction of 0.10. A `PREMIUM` membership carries a 3000-cent deductible and a member liability fraction of 0.00. The insurance amount is the member liability fraction multiplied by `repair_cost_cents`, rounded half-up to a whole cent. The final member damage fee is the deductible plus that insurance amount. The estimate half is deliberately tier-blind: `damage_fee_estimate_cents` is `repair_cost_cents` multiplied by 0.50, rounded half-up, and ignores the membership tier entirely. The two halves therefore diverge sharply for a well-insured member: a `PLUS` membership with a `repair_cost_cents` of 30000 yields an estimate of 15000 cents but a final fee of only 3000 cents, because the liability fraction of 0.10 gives 3000 and the deductible of 2000 is waived against it.

After assessment the incident forks on a severity score, and the two branches are not symmetric — one charges and freezes, the other closes and cancels. The score is built from three terms. The first term is the member's `last_accident_fee_block`, the 30-minute billing block index of the member's most recent at-fault damage incident, which is 0 when the member has no such history. The second term is 1 when the member's `strikes` is 0 and 2 otherwise. The third term is 1 when the incident's `repair_cost_cents` is at least 10000 cents and 0 otherwise. The raw severity score is the sum of the three terms, and it is stored on the incident as `severity_score`.

The high-severity branch fires when the severity score is greater than or equal to 4, and it runs from `ASSESSED` to `FEE_CHARGED`. It additionally requires `damage_fee_charged` to be false, the `fee_version` to be greater than 0, and `expected_incident_version` to equal the incident's persisted `version`. Both the at-least-4 threshold and the at-least-2 threshold below are inclusive bounds. On this branch the incident's `severity_fee_cents` is 1500 cents multiplied by the raw severity score, plus 1500 cents multiplied by the raw severity score minus the member's `last_accident_fee_block` when that difference is positive and zero otherwise — so the excess band is charged from the second point, not the first. With a `last_accident_fee_block` of 2, a `strikes` of 0 and a `repair_cost_cents` of 12000, the raw score is 4, the branch fires, and the excess fee is 1500 multiplied by 4 plus 1500 multiplied by the difference of 2, giving 9000 cents. The incident's `damage_fee_charged` is set to true, and the incident's damage fee of record together with that branch amount is posted to the member as a service credit on `wallet_credit_cents`. The branch then cascades: every membership of the incident's member whose status is `ACTIVE` or `SUSPENDED` is moved to `FROZEN`, with `status_before_freeze` capturing the status observed immediately beforehand and `tier` set to `FROZEN`. That freeze in turn cancels that member's `HELD` and `CONFIRMED` reservations and returns their vehicles to `AVAILABLE`, exactly as described in §3.4. The member's `version` increments once, each frozen membership's `version` increments once, and the incident's `version` increments once.

The low-severity branch fires when the severity score is less than or equal to 2, and it runs from `ASSESSED` straight to `CLOSED`, skipping `FEE_CHARGED` entirely. It requires the incident to be in `ASSESSED` and `expected_incident_version` to equal the persisted `version`. On this branch the incident's `severity_fee_cents` is 1500 cents multiplied by the member's `last_accident_fee_block`, plus 1500 cents multiplied by the third severity term minus 2 when that difference is positive and zero otherwise — that branch scales only the assigned block position rather than the whole score. With a `last_accident_fee_block` of 2, a `strikes` of 0 and a `repair_cost_cents` of 6000, the raw score is 1, the branch closes the incident, and the branch amount is 1500 multiplied by 2 plus zero, giving 3000 cents. The incident's `damage_fee_charged` is set to true and that branch amount is credited to the member's `wallet_credit_cents`. The incident's status becomes `CLOSED`, every maintenance order carrying this incident's `incident_id` is set to `CANCELLED`, and every membership of the incident's member that is currently `FROZEN` is returned to its preserved `status_before_freeze` with `status_before_freeze` reset to `NONE`. The member's `version` increments once and the incident's `version` increments once.

The branches rejoin at `CLOSED`. An incident sitting in `FEE_CHARGED` reaches `CLOSED` through the completion of the maintenance order that was raised from it: the order's `incident_id` must equal the incident's `id` and the order's status must be `IN_PROGRESS`. That join closes the incident and returns every membership held `FROZEN` for that incident's member to its preserved `status_before_freeze`, resetting `status_before_freeze` to `NONE`; each thawed membership's `version` increments once and the incident's `version` increments once.

A charged fee can be reversed by an operator waive. Waiving debits the member's `wallet_credit_cents` by the incident's `member_damage_fee_cents` and sets the incident's `damage_fee_charged` back to false; the member's `version` and the incident's `version` each increment once. The waiver is refused with `ERR_INSUFFICIENT_WALLET_CREDIT` (HTTP 422) when the member's `wallet_credit_cents` is strictly less than the amount being waived — a partial balance cannot cover a waiver.

### 3.14. Accounts, Department Billing, Wallet Adjustments and Citations

Organisation accounts are the billing backstop for university and business programs. An account is created by an `Anonymous` caller or by a `UniversityAccountAdmin`, supplying a `name`, a `type`, a `primary_member_id` and a `billing_email`. The `type` is one of `UNIVERSITY` or `BUSINESS` and drives the program's billing posture and its department billing. The `primary_member_id` is the program administrator member who owns the account, and the `billing_email` is the department billing destination address. Memberships created under an account carry a `department_code` naming the department charged for that membership's reservations; the code defaults to `UNSPONSORED`, which is also the value used for an individual, unsponsored membership that has no account at all.

A `PodOperator` may adjust a member's wallet outside the automatic penalty paths by supplying an `amount_cents` and a `reason`. A positive amount credits the member's `wallet_credit_cents` and a negative amount debits it. An adjustment is refused with `ERR_WALLET_ADJUSTMENT_INVALID` (HTTP 422) when the requested `amount_cents` is zero, or when a debit would take the member past their `wallet_credit_cents` — that is, a debit that exceeds the available balance is refused rather than partially applied. A permitted adjustment increments the member's `version`.

Authority citations exist so that an externally issued citation can be checked against its signer. A `PlatformAdmin` mints a citation through the test-driving surface by supplying a `recoverable_signer_address`, a `signer_address` and an `expires_at`; the minted citation is then addressable for validation. Validation is available to a `PodOperator` or a `PlatformAdmin` and takes a `signature`; when the supplied `signature` does not match the citation's recoverable signer address, the validation is refused with `ERR_CITATION_SIGNATURE_INVALID` (HTTP 422).

Two further test-driving capabilities exist for benchmark and integration use, and both are reserved to `PlatformAdmin`. One settles an out-of-band payment outcome for a membership's billing total without a real payment rail, by supplying a `membership_id` and an `outcome`; it records the simulated settlement outcome against that membership and changes no other field. The other advances the logical clock, as described in §2.7, by supplying the target instant as `to_iso8601`.

### 3.15. Reading the Network

Reads are the system's other half, and they are organised around containment. A member's own record, their memberships and their driving-record reports are readable by the member themselves and by the operational roles; an account's memberships and its enrolled members are readable by the account administrator and the fleet administrator; a pod's vehicles, its reservations, its maintenance orders, its access events, its shift bundles and its community signals are readable as container-scoped lists; a vehicle's maintenance orders, access events and fuel-card transactions are readable beneath the vehicle; and an incident's maintenance orders are readable beneath the incident. A reservation's access events are readable beneath the reservation.

The collection reads accept optional filters, and each filter is applied only when supplied. Members can be narrowed by `application_status` and by `kind`. Accounts can be narrowed by `type` and by `primary_member_id`. Memberships can be narrowed by `member_id`, by `account_id` and by `status`. Tier-restore entitlements can be narrowed by `membership_id` and by `restore_status`. Pods can be narrowed by `site_type`. Vehicles can be narrowed by `pod_id`, by `home_pod_id`, by `use_status` and by `cleanliness_state`. Reservations can be narrowed by `member_id`, by `pod_id`, by `vehicle_id`, by `returned_pod_id`, by `status` and by the window field `start_at`. Incidents can be narrowed by `reservation_id`, by `vehicle_id`, by `member_id`, by `assigned_driver_member_id` and by `status`. Maintenance orders can be narrowed by `vehicle_id`, by `pod_id`, by `incident_id` and by `status`. Access events can be narrowed by `reservation_id`, by `member_id` and by `vehicle_id`. Fuel-card transactions can be narrowed by `reservation_id`, by `vehicle_id` and by `status`. Community signals can be narrowed by `pod_id`, by `signal_type`, by `member_id` and by `reservation_id`. Shift bundles can be narrowed by `source_pod_id` and by `dest_pod_id`. Every collection read accepts `limit` and `offset` per §2.3, and every collection read is ordered by creation timestamp ascending except the single-resource reads, which return the resource itself.
