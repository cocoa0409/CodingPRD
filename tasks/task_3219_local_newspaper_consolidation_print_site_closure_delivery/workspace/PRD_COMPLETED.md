# Regional News Operations API — Product Requirements Document

## 1. Introduction

A regional newspaper group is simultaneously doing four hard things at once: it is closing and consolidating its printing base, rewriting its delivery economics around third-party contractors, shrinking print frequency while migrating subscribers to digital, and redistributing its newsroom across a smaller set of regional editing hubs. Every one of those programmes collides with a statutory obligation — the group must keep enough qualifying print circulation on time in each market to keep publishing legal notices — and with a production reality that printing farther from a market pushes publication deadlines later and later. This document specifies the API that the group runs its consolidation on.

The API models the group as a set of regional editing and distribution hubs. Under each hub live regions, print sites, print markets, delivery contractors, title closures and the newsroom positions that fund them. Print markets are the unit that actually experiences the consolidation: they are transferred from closing sites to surviving sites, they carry deadlines that must still be met after the transfer, and their subscriber contracts are renegotiated as print frequency drops. The API is expected to reconcile all of this immediately rather than in a nightly settlement, so that a market transfer, an edition dispatch, a contractor sanction or a subscriber migration leaves the whole ledger — press posture, transfer costs, route night costs, legal-notice eligibility and headcount — consistent in one write.

The sections that follow define the system-wide contract first (identity, response envelope, pagination, precision, concurrency, legal-notice gating), then the business workflows that carry the domain's real complexity, then the HTTP surface and the error catalogue.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request is authenticated by two mandatory HTTP headers: `X-User-ID` identifies the acting party and `X-User-Role` names their capacity. Seven roles exist, spelled exactly as follows: `PlatformAdmin`, `PrintOperationsDirector`, `DeliveryNetworkManager`, `NewsroomOperationsManager`, `CustomerService`, `Subscriber`, and `Auditor`. A request whose headers are absent, whose `X-User-Role` names no such role, or whose `X-User-ID` does not resolve for an entity-backed role is refused with `ERR_UNAUTHENTICATED` (HTTP 401). A request that presents a valid identity but attempts an operation that role does not hold is refused with `ERR_UNAUTHORIZED` (HTTP 403).

The roles carry no persisted identity except one. When `X-User-Role` is `PlatformAdmin`, `PrintOperationsDirector`, `DeliveryNetworkManager`, `NewsroomOperationsManager`, `CustomerService`, or `Auditor`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it where a workflow stamps an operator, but it is never compared to an entity's `id`. When `X-User-Role` is `Subscriber`, by contrast, `X-User-ID` is the `id` of the acting `SubscriberContract`; ownership checks on a subscriber contract compare the contract's own `id` to `X-User-ID`, and a subscriber may only read, cancel or migrate their own contract.

`PlatformAdmin` provisions hubs and drives the logical clock and makes no business decisions. None of the hub list, the hub read, the compliance read or hub creation moves the hub row: those reads report its `updated_at` and `version` unchanged. `PrintOperationsDirector` owns print site consolidation, market transfers, publication deadlines, edition dispatch and title closure. `DeliveryNetworkManager` owns contractor networks, route economics and delivery stops. `NewsroomOperationsManager` owns headcount allocation between regions and hubs — and is subject to a segregation-of-duties rule: no operator may approve a headcount movement that it created itself, and an attempt to do so is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). `CustomerService` owns subscriber notification, migration, retention offers and refunds. `Auditor` is read-only across every GET surface, including the hub compliance read.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of items returned; when omitted it defaults to 10, its minimum accepted value is 1 and its maximum is 100. `offset` is the number of items to skip and defaults to 0; a non-numeric or out-of-range `limit` is coerced toward the permitted band, to the default when it cannot be read as a number, to 1 when below the minimum and to 100 when above the maximum, and a negative `offset` is read as 0. Unless a specific ordering is called for by the business rules, list endpoints return resources in ascending order of their creation timestamp, with a tie on that timestamp broken by ascending `id`. The pagination fields `limit`, `offset`, `total_count` and `has_more` are carried in the `meta` object of every list response.

### 2.4. The Logical Clock and the Press-Volume Feed

The API runs on a server-side logical clock rather than real wall time. Until an operator moves it, the clock reads the fixed startup instant `2026-09-01T00:00:00Z`, and it never silently falls back to real wall-clock time. Only a `PlatformAdmin` may advance it, by supplying a `current_utc` instant, an instant that cannot be parsed as one being refused with `ERR_INVALID_REQUEST` (HTTP 400); the write returns an empty data object rather than the clock. Every temporal rule in this document — pause windows, cooling-off expiry, effective dates, notice periods, refund windows, savings windows — is evaluated against this clock, so a logical date and a calendar date mean the same thing throughout.

A separate operational feed records the physical reality that the savings ledger needs. A `PrintOperationsDirector` records one contract-day of press volume for a site by supplying the `print_site_id`, the `day` and the `charge_cents` actually incurred. Recording a day that already exists overwrites it, and a day on which the site printed no edition is recorded with a charge of zero rather than left unrecorded. Only the thirty contract-days immediately preceding the logical clock's current date enter the savings calculation, so re-recording a day older than that window changes nothing at all. The supplied `print_site_id` must resolve to a site, refused otherwise as `ERR_REFERENCE_NOT_FOUND` (HTTP 404), and each successful record recomputes the site's savings figures and bumps the site row itself; the write returns an empty data object with `201 Created`.

### 2.5. Hierarchical Consistency and Cascading Side Effects

The system is a graph of parents and children, and a transition on a parent is never a local event. When a print site leaves `active` for `closing`, every `PrintRoute` that prints out of it is orphaned, every market that had committed to one of those routes has its `route_selection_status` set to `needs_reassignment`, and each such market's transfer ledger is recomputed. When a market is withdrawn, its delivery routes and stops are terminated and every subscriber contract riding those stops is moved into retention — all in the same write. When a contractor is terminated, its routes are rescored at the terminated status factor, its stops are terminated, each affected market's boycott flag and each hub's legal-notice block are re-examined.

Two counters move every time a hub-level invariant is re-evaluated: the owning `RegionHub`'s `updated_at` is refreshed and its `version` is incremented by exactly 1. This happens on print-site closure planning and closure, on market transfer planning, redispatch and withdrawal, on delivery stop pause, resume and terminate, on contractor termination, and on newsroom change creation and reopening. Clients should treat a hub's `version` as the freshness token for everything derived from its member rows.

Every resource that carries the standard fields exposes the same core properties: `id`, a server-minted UUID with no type prefix and no embedded entity name; `created_at`, an ISO 8601 UTC timestamp with three fractional digits; `updated_at`, the same format, refreshed on any mutation; and `version`, an integer that starts at 1 on creation and increments by one on every modification. Derived quantities — a site's `capacity_remaining_copies`, a market's `net_print_site_transfer_cost_cents`, an edition's `minutes_late` — are ordinary field mutations: recomputing one refreshes `updated_at` and bumps `version` on the row that holds it. Every entity in this API uses the standard field set; none is immutable-after-creation and none omits `updated_at` or `version`.

### 2.6. Nested Resource Retrieval

Paths in this API are hierarchical, and path parameters are uniformly named `{id}` at each level. Where a path names several resources they are resolved strictly from left to right: each identifier taken for a real path segment is resolved in turn, and the first such segment that does not resolve to an existing row is the one reported, as `ERR_RESOURCE_NOT_FOUND` (HTTP 404) — never a later one. A creation endpoint whose path names only the parent — stops under a route, retention actions under a subscriber, routes under a contractor — resolves that one parent against its own collection, and the child is then required to sit under the parent it names through the body or the system stamp rather than through a second path segment; where a path does name both a parent and a child, the child must genuinely belong to that parent and a stop requested under a route it does not sit on, or an edition requested under a market it does not serve, is refused as `ERR_RESOURCE_NOT_FOUND` rather than being silently resolved from anywhere in the graph.

Identifiers supplied in a request body rather than the path are resolved separately and separately reported. When a body carries a foreign key — an `assigned_print_site_id`, a `receiving_print_site_id`, a `newsroom_position_id`, a `to_region_id`, a `from_region_id`, or a `delivery_stop_id` — and that key resolves to no row, the request is refused with `ERR_REFERENCE_NOT_FOUND` (HTTP 404). Path resolution runs before body resolution, so a request with both a bad path segment and a bad body key reports the path segment.

### 2.7. Monetary Values and Precision

Money moves through this system in cents. All monetary amounts — budgets, ceilings, credits, penalties, transport costs, route night costs — are carried as integer cents or as decimal numbers, never as floating-point currency, and no intermediate step is rounded. Values are rounded exactly once, at the end of their own calculation, using the round-half-up method, to the number of decimal places that calculation declares.

The precision of each calculated quantity is fixed and stated where the calculation is described. Transport costs, transfer costs, night costs, redispatch costs, plan-tonnage figures and severance costs round to two decimal places. The two per-copy rates — a print route's `marginal_cost_per_copy_cents` and a delivery route's `cost_per_copy_cents` — are the exception: both are round-half-up to four decimal places. Whole-copy and whole-head allocations truncate toward zero instead of rounding. A computed monetary value that would be negative before its own clamp is clamped as that calculation describes, not repaired by rounding.

### 2.8. Optimistic Concurrency Control

Two writes in this system are gated on the client's view of the owning hub, because both size their result from hub state that another writer can move. When a market is directed onto a receiving print site, the request must carry `expected_hub_version`, the client's last observed `version` of the owning `RegionHub`. When a headcount movement is proposed, the request must likewise carry `expected_hub_version`. In both cases, if the submitted value does not equal the hub's current `version`, the write is refused with `ERR_STALE_VERSION` (HTTP 412) and no side effects fire. The two gated operations are market transfer planning and newsroom change creation; no other endpoint in this API accepts a version field, and no other endpoint performs an OCC check.

### 2.9. The Legal-Notice Ratio Gate

Legal notices may only be carried by a publication with sufficient qualifying print circulation, and the API models that as a ratio gate on every hub. The gate counts the hub's `PrintMarket` rows whose `status` is `active`, `consolidation_planned` or `transfer_in_progress`; markets whose status is `withdrawn` are excluded from both the numerator and the denominator, because they no longer receive print. Among the counted markets, a market forms part of the numerator only while it still counts as receiving print: its latest edition is `is_on_time`, that edition is neither open to a correction nor reverted to digital, and every delivery stop recorded in the market is `active` — a market with no delivery stops at all is judged on its edition alone. The gate is satisfied when the number of on-time markets multiplied by 100 is at or above `min_on_time_ratio_pct` multiplied by the number of counted markets — an exact integer comparison with no floating point, and equality satisfies it. With ten counted markets and `min_on_time_ratio_pct` of 90, nine on-time markets pass: 900 is at or above 900. If there are no counted markets at all, there is no compliance basis and the gate fails.

A failed gate sets the hub's `legal_notice_block` to true. While that block is true, three operations are held across the whole hub — opening a print frequency reduction, dispatching frequency notices, and publishing a statutory title-closure notice — each refused with `ERR_LEGAL_NOTICE_HOLD` (HTTP 422). Because the block is derived rather than stored by hand, every event that can change a market's on-time status or remove a market from the count re-examines the ratio and refreshes the flag: pausing, resuming or terminating a delivery stop, terminating a contractor, correcting an edition, and withdrawing a market. A readable projection of the verdict and its inputs is exposed on the hub compliance read, which reports the boolean verdict, the `on_time_market_count`, the `counted_market_count`, the effective `min_on_time_ratio_pct`, the current `legal_notice_block`, and the hub's `press_posture`.

### 2.10. Press Posture and Slot Discipline

Each hub carries a derived `press_posture` summarizing its member print sites. It is `OPEN` while no member site is `closing` and none is `closed`; it becomes `RESTRICTED` as soon as at least one member site is `closing` and not all of them are `closed`; and it is `SUSPENDED` once every member site is `closed`. A hub with no member print sites at all is `OPEN`. A closed site is frozen: any status write against a `PrintSite` whose status is already `closed` is refused with `ERR_PRESS_POSTURE_LOCKED` (HTTP 422) and fires no side effects. That same code, at HTTP 422, also refuses any business action attempted while the owning hub's posture is `SUSPENDED` — planning a site closure, reinstating a delivery contractor, or planning a market transfer.

Dock capacity is a second kind of discipline. Each site declares how many route dispatch windows may overlap through `max_concurrent_departures`, and each route occupies a loading window of `loading_slot_minutes` starting at its `dispatch_cutoff_utc`. Windows are half-open — the interval `[dispatch_cutoff_utc, dispatch_cutoff_utc + loading_slot_minutes)` — so two departures that abut exactly do not collide, while one that starts inside another's window does. A new route whose window overlaps an existing departure at the same site is refused with `ERR_DOCK_SLOT_CONFLICT` (HTTP 409), unless the site's `max_concurrent_departures` still has room for one further overlapping departure. Every route of a site is measured against every other regardless of that route's status, and a route may not be created out of a `closed` site, which reports `ERR_PRESS_POSTURE_LOCKED` first.

### 2.11. Validation Ordering

Validation in this API runs in a fixed cascade, and the order is part of the contract because it decides which error a client sees when several conditions are violated at once. The cascade is: request shape first, then identity, then authorization and segregation of duties, then path existence, then body-reference existence, then lifecycle state, then regulatory safety, then referential integrity, then business constraints, then temporal rules, and finally fiscal ceilings.

Concretely, a malformed body is reported as `ERR_INVALID_REQUEST` (HTTP 400) before any identity check runs, while an operation that takes no body fields accepts an empty body and refuses any field it is handed — or any key an endpoint does not recognise — with that same code once identity has been established. Identity precedes authorization, so a missing header reports `ERR_UNAUTHENTICATED` (HTTP 401) rather than `ERR_UNAUTHORIZED`. Self-approval is checked at the same rank as ordinary authorization, so a newsroom change approved by its own creator reports `ERR_SEGREGATION_OF_DUTIES` rather than a generic permission failure. Where a path and a body are both in play the path is resolved first, so an operation whose path names a parent row and whose body names children — a stop created under a route, a retention action opened for a subscriber — reports a bad path segment as `ERR_RESOURCE_NOT_FOUND` ahead of any body field complaint, and a body field that is merely missing or wrongly typed is reported as `ERR_INVALID_REQUEST` only once every body key referenced here resolves. Path resolution precedes body-reference resolution, state precedes safety, safety precedes constraints, and constraints precede temporal rules. Two of the safety checks rank ahead of everything else in their band: the legal-notice hold and the suspended-posture lock are evaluated before capacity, referential and constraint checks, so a hub under a legal-notice block reports `ERR_LEGAL_NOTICE_HOLD` rather than a downstream duplicate-code or date error. Where two rules share a rank their relative order is not observable through the error code, because both produce the same class of refusal.

### 2.12. Shared Identifiers and Uniqueness

Names and codes are scoped to their container, and the API refuses reuse within that scope. A `Region`'s `name` must be unique within its hub; a `PrintSite`'s `code` must be unique within its hub; a `DeliveryContractor`'s `name` must be unique within its hub; a `DeliveryRoute`'s `route_code` must be unique within its contractor; and a `TitleClosure`'s `title_code` must be unique within its hub. A `DeliveryStop`'s `stop_code` is unique within its route, and a `PrintMarket`'s `name` is unique within its region. Any reuse is refused with `ERR_DUPLICATE_HUB_CODE` (HTTP 409), and a missing or empty required name or code is refused as `ERR_INVALID_REQUEST` (HTTP 400) before the uniqueness check is reached.

## 3. Business Logic & Workflows

### 3.1. Consolidating the Printing Base

The consolidation programme begins with a hub, which a `PlatformAdmin` provisions with its `name`, the `total_newsroom_headcount` it funds, a `max_print_tonnage_budget_cents` ceiling for aggregate print tonnage and transport, and a `transfer_cost_ceiling_cents` that caps how much cumulative print-site transfer cost any single member market may carry. On creation the hub's `press_posture` begins at `OPEN`, its `legal_notice_block` begins false, and its `min_on_time_ratio_pct` — the statutory floor described in §2.9 — defaults to 90 unless supplied. `total_newsroom_headcount`, `max_print_tonnage_budget_cents` and `transfer_cost_ceiling_cents` must each be at least 1, and `min_on_time_ratio_pct`, when supplied, must lie between 1 and 100 inclusive, a request breaching any of these being refused as `ERR_INVALID_REQUEST` (HTTP 400). The hub's `unassigned_headcount` begins equal to the whole `total_newsroom_headcount`, since no region has yet taken a share of it. Every hub child records its owner as a system field: a region carries `region_hub_id`, a print site carries `print_site_hub_id`, a delivery contractor carries `contractor_hub_id`, and a title closure carries `title_hub_id`.

A `PrintOperationsDirector` then lays out the hub's print sites. Each site carries a `code` unique within the hub, its installed `press_units`, the `shifts_per_night` it runs, a per-press throughput of `copies_per_hour_per_press`, and a `max_concurrent_departures` cap on overlapping dock windows. A site also declares how many `distinct_shifts_per_night` it runs, defaulting to 4, and a `loading_slot_minutes` dock window, defaulting to 30. Each of `press_units`, `shifts_per_night`, `copies_per_hour_per_press`, `max_concurrent_departures`, `distinct_shifts_per_night` and `loading_slot_minutes` must be at least 1, and a site may not be created in a hub whose `press_posture` is already `SUSPENDED` (refused as `ERR_PRESS_POSTURE_LOCKED`, as in §2.10); a breach of either floor is refused as `ERR_INVALID_REQUEST` (HTTP 400) with no site created. Its `allocation_method` is either `PRIORITY` or `PROPORTIONAL`, and that single choice governs how every edition printed at the site is sized. A site whose `code` is supplied but empty is refused as `ERR_INVALID_REQUEST` before any uniqueness check. From these the system derives `capacity_copies` as the number of presses multiplied by the number of shifts per night, multiplied by eight hours, multiplied by the per-press hourly throughput; sums the `allocated_print_run_copies` of every edition assigned to the site into `allocated_copies`; and reports `capacity_remaining_copies` as the difference, which is never negative.

Closing a site is a two-branch fork that both paths resolve through one join. Taking the consolidation branch moves the site from `active` to `closing`, and is permitted while the site is `active`, while the owning hub's `press_posture` is `OPEN` or `RESTRICTED`, while every market served by one of the site's print routes still passes the transfer-cost-ceiling check against the hub's `transfer_cost_ceiling_cents`, and while every latest edition on those markets has zero `minutes_late`. The ceiling is tested against each affected market's currently recorded `print_site_transfer_cost_cents` — a market the transfer route selector has not yet costed carries zero and passes — and a breach by any one market, or a late edition on any one of them, refuses the whole closure. Taking a site to `closing` orphans all of its print routes — a route that was `eligible` or `committed` becomes `orphaned` — marks every market that had selected one of those routes as needing reassignment, recomputes those markets' transfer ledger (§3.2), and recomputes the hub's `press_posture`, which in the ordinary case becomes `RESTRICTED`. Because a closure changes the markets it serves, the hub's `legal_notice_block` is re-examined under §2.9 as well. The hub's `version` increments by 1.

The second branch is the archive-continuity path: a site moves to `consolidating` while it is `active` or `closing`, once every market served by one of its routes has reached `withdrawn` and the site's own `allocated_copies` has fallen to zero. Its side effect is the savings ledger: the forward-looking and chronological figures below are recomputed. A site whose status is neither `active` nor `closing`, or one whose routes still serve a market that has not withdrawn or whose `allocated_copies` has not reached zero, is refused with `ERR_INVALID_STATE`. Whichever branch the site took, the close action is the join — moving `closing` to `closed` requires every one of the site's routes to be `orphaned`, a market having already had to reach `withdrawn` for that route to be terminated, so the withdrawal is implied by the orphan state rather than re-checked; moving `consolidating` to `closed` requires only that the archive continuity handoff has been recorded for every member hub. Either path recomputes `realized_savings_cents` and `savings_divergence_cents`, recomputes `press_posture` (which becomes `SUSPENDED` once every member site is closed), and — for every member region whose markets are all `withdrawn` — sets that region to `consolidated` and closes each of its newsroom positions. Again the hub's `version` increments by 1. Attempting any further status write against a `closed` site is refused as `ERR_PRESS_POSTURE_LOCKED`, per §2.10.

Site closure economics are deliberately dual-variant, and the pair is compared against each other rather than reconciled. Both variants run over a savings window of the thirty contract-days immediately preceding the current logical date. The forward-looking figure assumes the whole window. It first computes a flat daily rate: if the window carries no recorded charge, the rate is zero; otherwise the rate is the sum of the window's `day_charge_cents` divided by the number of days that carry a recorded charge, where a day recorded with a zero charge in fact counts as observed. The annualized figure `annualized_savings_cents` is then the fixed press cost avoided of 1,800 dollars, plus that flat daily rate multiplied by all thirty window days, rounded half up to two decimals. The chronological figure takes each day at its own observed value: `realized_savings_cents` is the same fixed press cost avoided of 1,800 dollars plus the sum of every window day's own `day_charge_cents` whose date is at or before the current logical date, rounded half up to two decimals — days that never ran add nothing. The divergence `savings_divergence_cents` is the absolute difference between the two, rounded half up to two decimals, and it is the value the closure audit pins. To make the divergence concrete: a window in which fifteen days were observed at 10,000 cents each and no other day carried a charge gives a flat daily rate of 150,000 divided by 15, that is 10,000, an annualized figure of 180,000 plus 10,000 times 30, that is 480,000.00, a realized figure of 180,000 plus 150,000, that is 330,000.00, and a divergence of exactly 150,000.00.

### 3.2. Transferring a Market and Meeting Its Deadline

Markets are the unit the consolidation actually moves. A `PrintOperationsDirector` creates one inside a region with its `name`, the `per_copy_revenue_cents` it earns per single copy sold, a `daily_route_cost_ceiling_cents` that caps its routes' combined nightly cost, a `weighted_demand_units` weight that feeds headcount allocation (§3.8), and its current `print_edition_per_week` between 1 and 7. It is stamped with its `region_id` and with the chosen `selected_print_route_id` once one is committed. It may also set the `publication_deadline_utc` wall time by which its edition must be delivery-ready (defaulting to 05:30 UTC), an `on_time_margin_minutes` slack (defaulting to 30), a `guaranteed_floor_copies` contract floor (defaulting to 0), and the `single_copy_market_rule` it follows (defaulting to `carrier`). A new market begins `active` with its `frequency_change_status` dimension `none`, its `route_selection_status` at `needs_reassignment` and no `selected_print_route_id`, and — because nothing has yet terminated a stop in it — its `delivery_boycott_active` reads true; that dimension is the parallel lifecycle described in §3.7 and runs independently of the market's consolidation status.

Directing a market onto a receiving print site is the write that carries the OCC obligation of §2.8: the payload names the `receiving_print_site_id` and must also carry `expected_hub_version`, and — because the OCC check sizes the write from the hub's observed version — it is evaluated before the suspended-posture lock and before the market's own state, so a stale version on a suspended hub or a non-active market still reports `ERR_STALE_VERSION`; a missing `expected_hub_version` is `ERR_INVALID_REQUEST` (HTTP 400) and the OCC check precedes the body-reference resolution of `receiving_print_site_id`. It is accepted only while the market is `active`, while the receiving site is `active` and not already committed to another market's in-flight transfer, and while that site's `capacity_remaining_copies` covers the market's latest edition's `requested_print_run_copies` — a market carrying no edition at all asks for nothing and satisfies that capacity test — otherwise the refusal is `ERR_SITE_NOT_RECEIVING` or `ERR_NO_PRINT_CAPACITY` (both HTTP 422). A route is then chosen by the selector below; if none qualifies the transfer is refused with `ERR_NO_ROUTE_IN_TIME` (HTTP 422) before the transfer cost is ever struck. The resulting transfer cost is computed from that chosen route's per-copy rate and the market's current allocation, and only afterwards may not push the market past the hub's `transfer_cost_ceiling_cents`, refused as `ERR_TRANSFER_COST_CEILING_EXCEEDED` (HTTP 422) — so a market with no qualifying route reports the route failure, not a ceiling breach. On success the market's `selected_print_route_id` points at the chosen route, that route becomes `committed`, the market's status becomes `consolidation_planned`, its `route_selection_status` becomes `current`, its transfer ledger is computed, the hub's `legal_notice_block` is re-examined under §2.9 because the market's editions have been re-pointed and recomputed, and the hub's `version` increments by 1.

A move onto a receiving site is only viable if a route can still clear the market's deadline, and that choice is a deterministic selector. The candidate set is the receiving site's print routes that are `eligible` and are `is_direct_hop` — only direct hops are considered — filtered further to those whose dispatch cutoff plus sixty minutes of make-ready plus the edition's press run hours plus the route's `transit_minutes` plus its `buffer_minutes` lands at or before the market's `publication_deadline_utc`. Among the survivors the shortest `transit_minutes` wins; ties break to the earliest `dispatch_cutoff_utc`; a remaining tie breaks to the earliest creation time. If no candidate survives, the selector raises `ERR_NO_ROUTE_IN_TIME`, the transfer is refused, and the market's `route_selection_status` stays `needs_reassignment`.

Once a market has been planned onto a site, and that receiving site later enters `closing`, the market moves automatically to `transfer_in_progress` — this is a system event, not a client request — and every edition of the market is re-pointed at the closing site and has its `latest_edition_ready_utc`, `minutes_late`, `late_edition_penalty_cents` and `is_on_time` recomputed. From `transfer_in_progress` a `PrintOperationsDirector` may redispatch the market: re-point it at a replacement route by naming a new `receiving_print_site_id`, requiring the selector to find a replacement whose origin site is `active`; a market that is not `transfer_in_progress` or whose `route_selection_status` is no longer `needs_reassignment` is refused with `ERR_INVALID_STATE`, and a named site that is not `active` is refused with `ERR_SITE_NOT_RECEIVING`. The replacement route becomes `committed` and is recorded as the market's `replacement_route_id`, the market returns to `active` with `route_selection_status` back at `current`, its editions are re-pointed at the replacement origin and returned to `in_production`, and the hub's `version` increments by 1.

A market leaves the print graph only by withdrawal, and only when it has become undeliverable. Withdrawal is accepted from `transfer_in_progress` when the market needs reassignment and its `delivery_boycott_active` is true; a withdrawal attempted from any other status is refused with `ERR_INVALID_STATE`, and a withdrawal attempted while no boycott is active is refused with `ERR_MARKET_NOT_WITHDRAWABLE` (HTTP 409). Withdrawing the market sets `print_site_transfer_credit_cents` to the exact negation of `print_site_transfer_cost_cents`, driving `net_print_site_transfer_cost_cents` to exactly 0.00, zeroes the market's `weighted_demand_units`, sets its status to `withdrawn`, terminates every one of its delivery routes and every `active` or `paused` stop on them, and moves every subscriber contract on those stops into retention (§3.6) with `offer_status` `offered` and `delivery_status` `terminated`, seeding the retention offer row for high-value contracts exactly as §3.6's system event describes. Any region left with all its markets withdrawn becomes `consolidated`; the hub's `legal_notice_block` is recomputed and its `version` increments by 1. A withdrawn market's `transfer_cost_disputed` flag reads true whenever its net transfer cost is non-zero while its status is `withdrawn` — which is exactly the state a market can be left in when a credit was never posted.

### 3.3. Delivery Contractors, Routes and Nightly Costing

Print delivery is outsourced to contractor networks, and their economics must reconcile every night. A `DeliveryNetworkManager` registers a contractor in a hub with its `name`, a `pay_basis` of `PER_STOP` or `PER_COPY`, the `per_copy_rate_cents` applied under the `PER_COPY` basis, a `min_stop_guarantee` of at least one stop, a `net_60_available` flag for whether it still finances a net-60 settlement term, a `cost_per_copy_ceiling_cents` on its routes, and the `last_load_claim_weight_lbs` claimed on its most recent load. A `sanction_reason_code` may be supplied or stamped later. A contractor begins `active`, its `sanction_reason_code` unset; a `min_stop_guarantee` below one is refused with `ERR_INVALID_REQUEST` (HTTP 400) and no contractor created.

Each contractor runs routes. A route is created against a `print_market_id` with a `route_code` unique within the contractor, a `stop_capacity` of at least one stop, a `per_stop_fee_cents`, an average `dist_per_stop_miles`, a route-level `cost_per_copy_ceiling_cents`, a `printed_copies_surcharge_cents` applied while the route still carries printed copies, and the `cost_run_date` it was last costed in. Each route records the `delivery_contractor_id` that operates it and the `destination_market_id` it serves. A print route is likewise anchored by its `origin_print_site_id`, the site that prints and dispatches the run. A route begins `prepared` with `last_cost_run_date` unset. A route's `print_market_id` must resolve, refused otherwise as `ERR_REFERENCE_NOT_FOUND` (HTTP 404), and a `stop_capacity` below one is refused as `ERR_INVALID_REQUEST` (HTTP 400). Stops are added under a route, each with a `print_market_id`, a `stop_code` unique within the route, the `contracted_daily_copies` it takes per night, the `contracted_daily_fee_cents` billed for it, and an optional pause window given by `pause_start_date` and `pause_end_date`; each stop carries its `delivery_route_id`. The `pause_window_days` is computed as the end date minus the start date plus one when both dates are supplied, and zero otherwise; supplying only one of the two dates, or an end date earlier than the start date, is refused with `ERR_OVERLAP_PAUSE_WINDOW` (HTTP 422). A stop begins `active`. Adding a stop that would push the route's non-terminated stop count above its `stop_capacity` is refused with `ERR_STOP_CAPACITY_EXCEEDED` (HTTP 422), and a stop whose `print_market_id` does not resolve is refused with `ERR_REFERENCE_NOT_FOUND` (HTTP 404) before that count is taken. Creating any stop, from any state, recomputes its route's night cost so the new stop enters the counted-stop term. A market's `daily_route_cost_ceiling_cents` is the ceiling a single one of the market's routes carries on its own nightly cost rather than a cap on the market's routes taken together, and no endpoint sums a market's route night costs against it.

Route transport cost is what a print route charges to carry a run out of a site, and it prices distance in bands. The route's `distance_miles` is its `transit_minutes` divided by sixty, multiplied by fifty-five miles per hour, rounded half up to two decimals. The `marginal_mileage_cost` is then built in three bands applied to that distance: the first fifty miles bill at 0.90 per mile, the next one hundred miles bill at 0.75 per mile, and every mile beyond one hundred and fifty bills at 0.60 per mile; the three band charges are added and the sum is rounded half up to two decimals. The band boundaries are exclusive in the sense that matters: at exactly fifty miles the second band contributes nothing and no 0.75 rate applies, and at exactly one hundred and fifty miles the third band contributes nothing and no 0.60 rate applies. The route's `route_transport_cost` is that marginal mileage cost plus the route's `stops_per_night` — the count of delivery stops on routes delivered into the same market — multiplied by a per-stop transport fee of 1.25, rounded half up to two decimals. The route's `marginal_cost_per_copy_cents` is the transport cost divided by `total_copies_allocated`, the summed `allocated_print_run_copies` over the destination market, rounded half up to four decimals — and it is exactly zero when `total_copies_allocated` is zero. `stops_per_night` is likewise a snapshot: it counts the delivery stops currently sitting in the destination market whose own status is `active` or `paused`, and it is refreshed whenever the route's transport cost is recomputed.

Nightly route cost is assessed by an explicit two-step recipe whose order is pinned. The copy total is the summed `allocated_print_run_copies` over the route's market for the night, counting only editions in `in_production`, `on_time_dispatch`, `late_dispatch` or `delivered_market`; that total is the route's `copies_carried_night`. Step one builds the `base_cost_cents`: a copy term, zero unless the contractor's `pay_basis` is `PER_COPY`, in which case it is `copies_carried_night` multiplied by the contractor's `per_copy_rate_cents`; plus a stop term taken over the counted stop count — delivery stops on the route whose status is `active` or `paused` — floored at the contractor's `min_stop_guarantee`, multiplied by the route's `per_stop_fee_cents`; the copy term and the stop term are added and rounded half up to two decimals. The `printed_copies_surcharge_cents` is deliberately not part of step one. Step two picks a copy-volume tier from `copies_carried_night` alone — before any sanction factor is applied, so a terminated contractor never falls into a lower tier: the tier percentage `copy_volume_tier_pct` is 0.00 for up to 7,500 copies, 0.05 above 7,500 up to 15,000, 0.10 above 15,000 up to 30,000, and 0.15 above 30,000. Exactly 7,500 copies is tier one and 7,501 is tier two. The `contractor_status_factor` is 0.85 when the contractor's status is `terminated` and 1.00 otherwise. The route's `route_night_cost` is the base cost multiplied by one plus the tier percentage, multiplied by the status factor, plus the route's `printed_copies_surcharge_cents`, rounded half up to two decimals. Finally `cost_per_copy_cents` is the night cost divided by `copies_carried_night`, rounded half up to four decimals, and exactly zero when `copies_carried_night` is zero. When the contractor's `pay_basis` is `PER_STOP` the copy term vanishes and the tier percentage multiplies only the stop term; under `PER_COPY` the copy term scales with delivered copies, so the tier applies to a base that already grows with volume.

Advancing the cost calendar is a guarded operation. A `DeliveryNetworkManager` submits a `run_date` to advance a route's nightly costing; the run date must be strictly later than the route's `last_cost_run_date`, or the request is refused with `ERR_COST_RUN_REGRESSION` (HTTP 409). On success the route's `route_night_cost` and `cost_per_copy_cents` are recomputed, its `last_cost_run_date` becomes the submitted `run_date`, and its `printed_copies_last_run` — the run size observed for the market at the most recent cost run, and the source for `copies_carried_night` — is refreshed from the market's current edition. Advancing a route from `prepared` to `contract_active` requires the route's contractor to be `active` and its non-terminated stop count to be at or below `stop_capacity`; achieving `contract_active` on the first cost run is what puts the route into service.

A contractor may be sanctioned, and sanctions cascade in both directions. Suspension is always explicit: it is admitted only against a contractor that is `active` and requires a `sanction_reason_code` to be supplied, a suspension attempted without one being refused as `ERR_INVALID_REQUEST` (HTTP 400) and one attempted against a contractor that is not `active` as `ERR_INVALID_STATE` (HTTP 409). Suspension moves every member route from `contract_active` to `suspended` and every stop on those routes from `active` to `paused`, and rescoring the routes follows. Reinstating a suspended contractor requires `net_60_available` to be true and no member route to be over its `cost_per_copy_ceiling_cents`, each failure being reported as `ERR_INVALID_STATE` (HTTP 409); a contractor that is not `suspended` at all is likewise `ERR_INVALID_STATE`, and a reinstate attempted while the owning hub's `press_posture` is `SUSPENDED` is refused with `ERR_PRESS_POSTURE_LOCKED` per §2.10 before either eligibility test. On success it returns every route to `contract_active` at a status factor of 1.00, resumes every paused stop, and replaces the contractor's factor. Termination is terminal: it requires the contractor to be `active` or `suspended` and to have no route still `prepared`, a contractor already `terminated` being refused with `ERR_CONTRACTOR_TERMINAL` (HTTP 409) and one in any other state with `ERR_INVALID_STATE`. It terminates every route, sets `contractor_status_factor` to 0.85 on each, rescoring `route_night_cost` and `cost_per_copy_cents`, terminates every stop, and recomputes each affected market's `delivery_boycott_active` — which reads true once no stop in the market is still `active`, and is the precondition a market must satisfy to be withdrawable. Every subscriber contract on the terminated stops moves to retention with `delivery_status` `terminated`, and each affected market's legal-notice ratio is re-examined per §2.9, refreshing the hub's `legal_notice_block`, whose `version` increments by 1. Two refusals guard this area: reinstating a `terminated` contractor, or creating a new route under it, is refused with `ERR_CONTRACTOR_TERMINAL` (HTTP 409); and a forward action that references a row an earlier reverse action already terminated in the same region — reinstating a contractor whose routes a withdrawal already terminated, or resuming a stop so terminally ended — is refused with `ERR_BACKED_OUT_REFERENCE` (HTTP 422).

Choosing which contractor holds the hub's sanction policy is a single-policy selection, not an aggregate. The candidate set is the hub's contractors whose status is `active` or `suspended` and whose `net_60_available` is true, excluding any contractor whose `sanction_reason_code` is `RESIDUAL_PROGRAMME`. Candidates rank by `per_copy_rate_cents` ascending, with ties broken by `name` compared as a case-sensitive ASCII string, and the lowest rate wins. When no contractor qualifies, no policy is applied: the reason code `NO_ELIGIBLE_CONTRACTOR` is recorded and every route in the hub is held at `prepared` for the next cost run.

A market may alternatively follow a single-copy assortment decision that decides whether its own rule keeps print in the market, and the two rules diverge precisely because they count different things. Under the `newsstand` rule, only what actually sells earns: the copies sold is the `allocated_print_run_copies` multiplied by the sell-through rate of 0.65 and floored to a whole number, and `newsstand_contribution_cents` is those copies multiplied by the market's `per_copy_revenue_cents`, minus the route's whole `route_transport_cost`, rounded half up to two decimals. Under the `carrier` rule the whole run counts as sold and each copy bears only its own marginal delivery cost: `carrier_contribution_cents` is `allocated_print_run_copies` multiplied by `per_copy_revenue_cents`, minus `allocated_print_run_copies` multiplied by the route's `marginal_cost_per_copy_cents`, rounded half up to two decimals. The market's `single_copy_market_rule` states which rule it follows, and `keeps_print_single_copy` reads true when that market's own rule reports a contribution at or above zero — the break-even being exactly zero under both rules, so the two can disagree on the same market: returns make the newsstand rule look far worse, while a market comfortably profitable under the carrier rule may show a thin or negative margin under the newsstand rule. The decision is taken for markets in `active`, `consolidation_planned` or `transfer_in_progress`; a `withdrawn` market is excluded from the assortment decision entirely.

### 3.4. Stops, Pause Windows and Programmed Interruptions

Delivery stops are the physical endpoints of a route, and their lifecycle is windowed by the logical clock. A `DeliveryNetworkManager` pauses an `active` stop only while the current logical date lies inside the stop's declared pause window, that is, at or after `pause_start_date` and at or before `pause_end_date` inclusive; a pause attempted outside that window — and equally a pause attempted against a stop that declares no pause window at all — is refused with `ERR_PAUSE_WINDOW_NOT_OPEN` (HTTP 422), and a pause attempted against a stop that is already `paused` or has been `terminated` is refused with `ERR_STOP_NOT_ACTIVE` (HTTP 409), the stop's own state being examined before its window. Pausing the stop pauses every subscriber contract riding it, setting their status and `delivery_status` to `paused`. Resuming is admitted only once the current logical date is strictly later than the stop's `pause_end_date`; a resume attempted while the window is still open is refused with `ERR_PAUSE_WINDOW_STILL_OPEN` (HTTP 422), and a resume attempted against a stop that is not `paused` is refused with `ERR_INVALID_STATE` (HTTP 409). Resuming returns every paused contract on the stop to `active` with `delivery_status` set to `resumed`. Terminating a stop — permitted from `active` or from `paused` — is terminal, and moves every subscriber contract on it into retention with `delivery_status` `terminated`; a terminate attempted against a stop that is already `terminated` is refused with `ERR_STOP_NOT_ACTIVE` (HTTP 409).

Every one of those three stop transitions carries the same hub-level side effect. Pausing, resuming or terminating a stop re-examines its market's legal-notice ratio under §2.9 and refreshes the owning hub's `legal_notice_block`, incrementing the hub's `version` by 1. Because a paused stop stops taking copies, a pause can push a market off time and set the block; a resume can clear it again. This makes the stop lifecycle the most common trigger for the hub-wide gating described in §2.9.

### 3.5. Press Runs, Edition Dispatch and Late Sports Coverage

An edition is the physical artefact the whole consolidation is trying to land on time. A `PrintOperationsDirector` creates one against a market by naming the `assigned_print_site_id`, a `slug` such as `2026-09-21` that is unique within the market and orders it among its stable siblings, the `page_count`, the `requested_print_run_copies`, a `late_sports_engineering_flag` for coverage that needs the adjustment slot below, and the `legal_notice_count` of statutory notices it carries. An edition may only be created against a market that is still receiving print — one whose status is `active`, `consolidation_planned` or `transfer_in_progress`; a `withdrawn` market no longer receive[s] print, so an edition created against one is refused with `ERR_INVALID_STATE` (HTTP 409). The edition begins `in_production`, with `press_run_hours`, `minutes_late` and the penalty at zero, `correction_open` false and `next_edition_slot_taken` reset, and its `is_on_time` — and, where the market already has a selected route, its ready times — immediately computed; where the market has not yet selected a route there is nothing to derive a ready time from, so those times stay null and the edition is not on time until a transfer points it at one. A `page_count` below one or a negative `requested_print_run_copies` is refused as `ERR_INVALID_REQUEST` (HTTP 400), the `assigned_print_site_id` must resolve (else `ERR_REFERENCE_NOT_FOUND`, HTTP 404), an empty or already-used `slug` is refused as `ERR_INVALID_REQUEST` or `ERR_DUPLICATE_HUB_CODE` respectively, and an assigned site that is already `closed` refuses the creation with `ERR_PRESS_POSTURE_LOCKED`; the market's own receiving-print state is examined before the assigned site is resolved or its slug checked.

How many copies the market actually gets is decided at creation by the assigned site's allocation method, which is the single lever described in §3.1. Under the `PRIORITY` method the contested pool is the site's `capacity_remaining_copies` and the competing editions are the site's other editions ordered by `slug` ascending and then by `print_market_id` ascending; each market is served its whole request up to what remains, so an early market can consume the pool before a later one is reached. In either method the market's `guaranteed_floor_copies` is applied first: the run actually requested becomes the larger of `requested_print_run_copies` and `guaranteed_floor_copies`, and the `allocated_print_run_copies` is the smaller of that and the site's remaining capacity. Under the `PROPORTIONAL` method the same floor is applied, but the run is first scaled: the `allocated_print_run_copies` is the requested run multiplied by the site's remaining capacity and divided by the summed requested runs of the edition being created together with the site's other editions, floored to a whole number of copies, and then clamped upward to the market's `guaranteed_floor_copies`, downward to the requested run, and downward again to the site's remaining capacity. When the summed requested runs are zero the allocation is zero. A market whose `guaranteed_floor_copies` exceeds the assigned site's `capacity_remaining_copies` is refused outright with `ERR_FLOOR_COPIES_EXCEED_CAPACITY` (HTTP 422) and no edition is created — the guarantee cannot be satisfied, so nothing is printed. Two further ceilings guard the same creation: a run that would push the issuing site's press load past its installed hourly capacity is refused with `ERR_PRESS_CAPACITY_EXCEEDED` (HTTP 422), and a run that would push the hub's aggregate print tonnage charge for the period past `max_print_tonnage_budget_cents` — counting partial-period consumption, never annualizing it, and measured on the run the market is actually allocated — floored at its guaranteed floor — rather than on the run requested — is refused with `ERR_PRINT_BUDGET_EXCEEDED` (HTTP 402).

The time an edition actually takes on press is computed in one pinned order. The `speed_factor` is 1.00 for a `page_count` of at most 8, 0.85 for a `page_count` above 8 up to 16, and 0.70 beyond 16. A raw hours figure is formed by dividing `requested_print_run_copies` by the site's `press_units`, then by its `shifts_per_night`, then by its `copies_per_hour_per_press`, and then by the speed factor. That single raw duration is rounded up to the next quarter hour to give `press_run_hours`. The rounding order is pinned and meaningful: the division chain collapses to one duration and is rounded once; rounding the per-press throughput first and then dividing does not produce the same figure. From there `press_ready_utc` is the selected route's `dispatch_cutoff_utc` plus sixty minutes of make-ready plus `press_run_hours`, and `latest_edition_ready_utc` is `press_ready_utc` plus the route's `transit_minutes` plus its `buffer_minutes`. This ready time is recomputed whenever the selected route's status changes — which is what a market transfer, a redispatch or a site closure sets in motion. The `minutes_late` is the whole minutes from the market's `publication_deadline_utc` to `latest_edition_ready_utc`, floored at zero, and `is_on_time` reads true only when the deadline minus the ready time is at or above the market's `on_time_margin_minutes`.

The engine may consume the pool it was never fully allocated, and this is why the pool is contested above. The transfer ledger for the market is evaluated in a pinned three-step order, because step one's own input is derived from the market's allocated copy count: first `print_site_transfer_cost_cents` is the `allocated_print_run_copies` multiplied by the selected route's `marginal_cost_per_copy_cents`, rounded half up to two decimals; then `print_site_transfer_credit_cents` is zero while the market is not `withdrawn` and no correction is open, and is exactly the negation of the cost once the market is `withdrawn` or a correction has stopped the press; and finally `net_print_site_transfer_cost_cents` is the cost plus the credit, rounded half up to two decimals. Reading a route's per-copy rate before the market's current allocation would use a stale rate, so the order is fixed. While the market is live with no correction open the credit is zero and the net equals the cost; once the market is withdrawn or a correction is open the credit is exactly the negated cost and the net is exactly 0.00.

Dispatch is where a late edition costs money. A `PrintOperationsDirector` dispatches an edition from `in_production`, and the outcome branches on whether it can still make its deadline. An edition that is `is_on_time` moves straight to `on_time_dispatch`; dispatching an `in_production` edition that is neither late nor on time, and dispatching a late edition whose site reports no open adjustment slot, are each refused with `ERR_INVALID_STATE` (HTTP 409). An edition with a positive `minutes_late` takes the late path, and that path first requires the site's slot check to report an open five-minute second-edition adjustment slot at the edition's print site: consuming the slot sets the edition's `next_edition_slot_taken` to 1, marks it `late_dispatch`, recomputes its late penalty, increments the site's consumed adjustment-slot count and decrements its available count, and recomputes the edition's `second_edition_slot_open` gate, which is set false once the site's consumed slot count equals that site's `distinct_shifts_per_night`. Each distinct dispatch shift offers exactly one such five-minute slot, so a site running four distinct shifts per night can absorb four late dispatches before the gate closes. Recording that a dispatched edition reached its market moves it from either `late_dispatch` or `on_time_dispatch` to `delivered_market`, a delivery attempted from any other status being refused with `ERR_INVALID_STATE`, re-examines the market's hub under the legal-notice ratio gate of §2.9, and, on the late path only, recomputes `savings_divergence_cents` for the edition's former print site under §3.1 — no separate check that the market's delivery run has completed stands between the two.

The late-edition penalty escalates, and the escalation is driven by flags on the same edition rather than by any global rate. `minutes_late` is the whole minutes from the deadline to the ready time, floored at zero. A penalty of exactly zero is booked when `minutes_late` is zero. Otherwise the multiplier is 3 when the edition has an open correction, 2 when it carries the `late_sports_engineering_flag`, and 1 otherwise — in that precedence, so an open correction outranks the sports flag. The penalty is `minutes_late` multiplied by 45 cents per minute, multiplied by that multiplier, truncated toward zero. A corrected edition that is already late is re-evaluated by the transfer route selector before its penalty is booked.

Late sports coverage has a second escape hatch besides the adjustment slot. From `late_dispatch`, an edition carrying `late_sports_engineering_flag` true may be reverted to digital-only when no route to the edition's market can produce an edition ready at or before that market's `publication_deadline_utc`. Reverting sets `press_run_hours` to zero, resets `next_edition_slot_taken` to 0, clears the `assigned_print_site_id`, and decrements the former site's `allocated_copies` by the edition's `allocated_print_run_copies`; because the market is no longer receiving printed copies, every delivery route of that market has its `printed_copies_surcharge_cents` set to zero and its `route_night_cost` recomputed. A reverted edition contributes no press hours at all to any downstream figure. A revert attempted from any status other than `late_dispatch`, or against a late edition that does not carry the `late_sports_engineering_flag`, is refused with `ERR_INVALID_STATE`; the flag is a required consignment on the revert itself, not merely a precondition on the route check.

Corrections are the last loop in the edition lifecycle. A delivered edition that carried at least one legal notice may be corrected: this sets `correction_open` true, computes `correction_redispatch_cost_cents`, re-examines the edition's market under the legal-notice ratio gate of §2.9, and pushes the edition to `reverted_to_digital`. The redispatch cost is the edition's `press_run_hours` multiplied by 2,500.00 dollars of reprint press cost per hour, plus the route's `route_transport_cost` multiplied by 1.40 — the whole route is re-run at that multiplier, including stops whose copies were never in error — with the total rounded half up to two decimals. A correction attempted on an edition that is not `delivered_market`, or on one that carried no legal notice, is refused with `ERR_INVALID_STATE`.

### 3.6. Subscriber Migration, Retention and Refund

Subscribers are the people the frequency reduction and the market withdrawal both land on. A `CustomerService` operator creates a subscriber contract on a delivery stop, supplying a `subscriber_ref` unique within the region hub, the `remaining_print_issues` not yet delivered, the `paid_through_utc` end of the paid term, and the `print_issue_value_cents` that one issue is worth to the subscriber. The contract begins `active`, with its `offer_status` and `delivery_status` both `none`, and its `migration_credit_cents`, its `churn_retention_credit_cents` and its `offer_recommendation` are all computed at creation. A stop that is already `terminated` takes no new contract (refused as `ERR_INVALID_STATE`), a `subscriber_ref` that is empty or a negative `remaining_print_issues` is refused as `ERR_INVALID_REQUEST` (HTTP 400), and the `subscriber_ref` is unique within the region hub rather than the stop.

Two variants of the migration credit exist and they answer different questions, so they are not interchangeable. The retained-print-margin variant asks what the publisher keeps by not printing: the per-issue print cost is the carrier labour cost of 85 cents plus 40 cents of handling, that is 125 cents, and `migration_credit_cents` is the number of `remaining_print_issues` multiplied by the difference between that 125-cent per-issue cost and the carrying market's `per_copy_revenue_cents`, truncated toward zero. A market whose per-copy revenue exceeds the per-issue cost therefore produces a non-positive credit. The refund-responsibility variant asks what the subscriber is owed back: a base refund of `remaining_print_issues` multiplied by `print_issue_value_cents` is scaled by how much term remains — one half when fewer than 30 days remain, seven tenths when between 30 and 89 days inclusive remain, and nine tenths when more than 89 days remain — the result truncated toward zero and floored at zero, and then capped at 5,000 cents whenever it reaches 5,000. This active-contract cap is deliberate and has a visible consequence: the `FULL_REFUND` recommendation is suppressed exactly at 5,000 cents, so a high-value subscriber still resolves to `PRINT_CREDIT`. For any given subscriber the refund-responsibility figure is strictly larger than the retained-print-margin figure.

The offer a subscriber sees is chosen by a threshold of its own, evaluated at the moment notices go out or migration eligibility is checked. The `remaining_contract_value_cents` is `remaining_print_issues` multiplied by `print_issue_value_cents`, rounded half up to two decimals, and `days_remaining` is the whole days from the current logical instant to `paid_through_utc`. When the remaining contract value is below 5,000 cents the recommendation is `PRINT_CREDIT` regardless of term length. Otherwise the choice is driven purely by term length: `DIGITAL_UPGRADE` when `days_remaining` is at least 180, and `FULL_REFUND` below that.

Migration itself moves an `active` contract to `migrated`, sets `offer_status` to `accepted`, and computes `migration_credit_cents` under the retained-print-margin variant; either the subscriber or `CustomerService` may perform it. Cancellation moves an `active` or `churned_pending_retention` contract to `churned` with `offer_status` set to `declined`, computing the churn credit under the refund-responsibility variant; a `migrated` contract can also be cancelled, and a subscriber or `CustomerService` may do it. A refund, available to `CustomerService` alone, moves an `active` contract to `churned`, computes the same refund-responsibility credit, and is admitted only at or before `paid_through_utc` — a refund requested after the paid-through instant is refused with `ERR_REFUND_WINDOW_CLOSED` (HTTP 409). Any cancellation, refund or migration attempted against a contract already `churned` is refused with `ERR_SUBSCRIBER_TERMINAL` (HTTP 409), because `churned` is terminal.

Churn does not always end the relationship. A contract enters `churned_pending_retention` only through a system event seeded by a market withdrawal or a stop termination — never by a client request — which sets `offer_status` to `offered`, computes the refund-responsibility credit, and, for contracts whose remaining contract value is at least 20,000 cents, creates one retention offer row for the subscriber. The offer row is opened with an `AUTO_RETENTION` code, a `STANDARD` eligibility policy and a `cooling_off_expires_utc` fourteen days after the current logical instant, but — unlike a `CustomerService` mailbox offer — carries no `churn_retention_credit_cents`, that row's own credit field remaining unset. The subscriber can then be brought back: accepting the open retention offer moves the contract from `churned_pending_retention` back to `active` with `offer_status` `accepted`, but only if its `delivery_status` is not `terminated` and only strictly before the offer's cooling-off instant. A retention action is itself a lifecycle: a `CustomerService` operator offers one with a `retention_offer_code` such as `CREDIT30` or `DIGITAL12`, a `retention_credit_cents` of at least zero, and the `eligibility_policy_id` the subscriber must satisfy, which stamps `cooling_off_expires_utc` and opens the action in status `open`. Each retention action records the `subscriber_contract_id` whose churn it is trying to retain. Accepting a retention action requires the current logical time to be strictly earlier than `cooling_off_expires_utc`; acceptance at or after it is refused with `ERR_COOLOFF_EXPIRED` (HTTP 409), and acceptance of an action that is `accepted`, `expired` or `cancelled` is refused with `ERR_RETENTION_ALREADY_SETTLED` (HTTP 409), the settled check preceding the cooling-off check. A retention action opened by a `CustomerService` operator stamps `cooling_off_expires_utc` as exactly fourteen days after the current logical instant, and a negative `retention_credit_cents` is refused as `ERR_INVALID_REQUEST` (HTTP 400). Acceptance moves the action to `accepted` and returns the parent contract to `active` with `offer_status` `accepted`; the same state change may equally be reached from the contract's own side, by the `accept-retention-offer` write, which acts on the contract's newest open action. An action whose window lapses becomes `expired`, and one whose parent contract exits — by cancellation or by refund — becomes `cancelled`; both are terminal, as is `accepted`.

### 3.7. Reducing Print Frequency and Migrating Subscribers

Reducing a market's print frequency runs on its own state dimension on the market row, in parallel with the consolidation status dimension of §3.2 — a market can be mid-transfer and mid-frequency-reduction at once, and the two do not block each other. A `PrintOperationsDirector` opens a reduction by supplying a `target_print_edition_per_week` strictly below the market's current `print_edition_per_week`; both values lie between 1 and 7. The proposal is admitted while the frequency dimension is `none` and the market's consolidation status is `active`, `consolidation_planned` or `transfer_in_progress`, and it moves the dimension to `proposed`. A target that is not strictly below the current frequency, or that falls outside the 1-to-7 band, is refused with `ERR_INVALID_REQUEST` (HTTP 400); a reduction opened while the dimension is no longer `none`, or against a market whose consolidation status is `withdrawn`, is refused with `ERR_INVALID_STATE` (HTTP 409).

Dispatching the subscriber notices is a separate step and it is the one the legal-notice gate guards. It is admitted only from `proposed` and only while the owning hub's `legal_notice_block` is false; an attempt while the hub is under a legal-notice hold is refused with `ERR_LEGAL_NOTICE_HOLD` (HTTP 422). Dispatch moves the dimension to `notices_dispatched`, stamps `notices_dispatched_at` with the current logical time, pauses every subscriber contract riding the market's currently active delivery stops, computes each such contract's `offer_recommendation` under §3.6, and raises the market's `renewals_accepted_count` above zero — the count is a server-computed field with no other writer, and the dispatched renewal solicitation itself is what first moves it. Rejecting the reduction can happen from either `proposed` or `notices_dispatched`; it moves the dimension to `rejected` and returns every paused contract to `active` with `offer_status` set to `declined`.

Applying the reduction is the step that actually lowers the print frequency, and it is doubly guarded. It requires the dimension to be `notices_dispatched`; an apply while notices have not been dispatched, or while `renewals_accepted_count` is zero, is refused with `ERR_NOTICES_NOT_DISPATCHED` (HTTP 409), that dimension being examined before the count rather than after it. It further requires at least 14 calendar days to have elapsed since the notices were dispatched; applying inside the statutory notice period is refused with `ERR_NOTICE_PERIOD_NOT_ELAPSED` (HTTP 409). On success the dimension becomes `applied`, the market's `print_edition_per_week` is set to its `target_print_edition_per_week`, every paused subscriber contract on the market's stops is migrated with `offer_status` `accepted`, and the market's `weighted_demand_units` is rescored to the former weight multiplied by the new frequency and divided by the former frequency, rounded half up to a whole number of units. `applied` and `rejected` are the dimension's terminal values, and any attempt to re-apply an already-applied reduction is refused with `ERR_INVALID_STATE` (HTTP 409); applying a reduction whose dimension has moved past `notices_dispatched` by any other route is refused with `ERR_NOTICES_NOT_DISPATCHED`, that dimension being examined before the count.

### 3.8. Newsroom Allocation Across Editing Hubs

Newsroom headcount is a scarce pool that the hub distributes among its regions in two passes, and the distribution is the model for how a shrinking newsroom keeps coverage in the markets it still serves. A `PrintOperationsDirector` creates a region inside a hub with its `name`, unique within the hub and acting as the tie-break key wherever regions are ordered, a `daily_headcount_floor` of at least zero, a `daily_headcount_cap` of at least that floor, and an `allocation_priority` rank; a floor below zero or a cap below the floor is refused with `ERR_INVALID_REQUEST` (HTTP 400). The cap bounds only the residual pass; the floor is what the region keeps in the first pass. The region's `region_need_score` is the summed `weighted_demand_units` of its member markets — counting only markets in `active`, `consolidation_planned` or `transfer_in_progress`, since a `withdrawn` market carries no demand — divided by one thousand, rounded half up to two decimals.

The first pass guarantees floors. Each region's `guaranteed_headcount` is the smaller of its `region_need_score` floored to a whole number of heads and its `daily_headcount_floor`, so the floor is the binding value whenever the need score would allow more. The second pass distributes what remains, in a fixed order: regions are ordered by `allocation_priority` ascending, and among regions sharing a priority by `name` ascending. A residual pool is formed as the hub's `total_newsroom_headcount` minus the sum of every region's `guaranteed_headcount`, and each region in that order takes a grant equal to the smaller of what the pool still holds and the headroom between its `daily_headcount_cap` and its `guaranteed_headcount`, floored at zero. Its `allocated_newsroom_headcount` is its floor plus that grant, and the pool is drawn down by the grant before the next region is served. A region reached after the pool is exhausted keeps only its floor; a region whose cap binds stops at the cap and passes the remainder along. Whatever the waterfall cannot place is the hub's `unassigned_headcount`, the difference between the hub's `total_newsroom_headcount` and the sum of `allocated_newsroom_headcount` over its regions, and it is the documented sink for headcount the residual pass could not place. Each region also reports its `member_market_count`, and it begins `active`, becoming `consolidated` once every one of its member markets has reached `withdrawn`.

Positions and movements are how a `NewsroomOperationsManager` expresses a staffing change. A position is created inside a region with a `role_code` such as `REPORTER`, `SPORTS` or `COPY`, an `expertise_code` such as `HIGH_SCHOOL_SPORTS` or `COURTS`, and a fully-loaded `monthly_cost_cents`; a `monthly_cost_cents` below one is refused as `ERR_INVALID_REQUEST` (HTTP 400). It begins `open`, its `allocated_headcount` is the summed `allocated_slots` of the changes recorded against it, and it becomes `closed` once its region is `consolidated`. A headcount movement is proposed with a `newsroom_position_id`, the `to_region_id` and `from_region_id` it moves between — the two being equal for a pure top-up — an `effective_date` strictly later than the current logical date, a `layoff_order_index` under which the smaller index is selected first when a reduction must choose, and a `requested_slots` of at least one; a `requested_slots` below one is refused with `ERR_INVALID_REQUEST` (HTTP 400) and a `newsroom_position_id`, `to_region_id` or `from_region_id` that does not resolve is refused with `ERR_REFERENCE_NOT_FOUND` (HTTP 404) before it. This creation is the second write carrying the OCC obligation of §2.8: it must supply `expected_hub_version`, and a value that no longer matches the hub's current `version` is refused with `ERR_STALE_VERSION` (HTTP 412), because the residual pool the movement would draw down can only be sized from the observed version. On creation the movement is `proposed` and the hub's `version` increments by 1.

Settling a movement moves it through `approved` to `applied`. Approval is admitted from `proposed` when the `effective_date` is strictly later than the current logical date — otherwise `ERR_EFFECTIVE_DATE_NOT_FUTURE` (HTTP 422) — and when the acting operator is not the one that created the movement, a self-approval being refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) under §2.1. Application is admitted from `approved` once the current logical date is at or later than `effective_date`. Applying computes, for every sibling movement in the hub, the `residual_headcount` left to it after the movements ahead of it in the residual pass have been served — a figure of exactly zero when every one of its slots is placed — and sets its `allocated_slots` to the smaller of its `requested_slots` and that residual headcount. A `rejected` movement is most visibly one whose `allocated_slots` fell to zero, so a movement against a hub whose `unassigned_headcount` is already exhausted is rejected and carries no severance. The pass is ordered by creation time ascending, then by `layoff_order_index`, then by identifier, and it is re-run when a movement is created and when an approved movement is reopened as well as when one is applied. It then computes `severance_cost_cents` as described below, recomputes the destination and source positions' `allocated_headcount`, recomputes the region's `allocated_newsroom_headcount` and the hub's `unassigned_headcount`, and sets the movement to `applied`. A movement may instead be rejected from `proposed`, moving it to `rejected`; or reopened from `approved` while it has not been applied, returning it to `proposed`, re-deriving its residual headcount and allocated slots and recomputing its severance cost, and incrementing the hub's `version` by 1. `applied` and `rejected` are terminal.

Severance is charged on the heads the waterfall could not place, and it steps down in scale. The severed headcount is `requested_slots` minus `allocated_slots`, so a movement whose slots are all placed carries no severance at all. When nothing is severed the cost is zero. When one or two heads are severed, the cost is the severed count multiplied by 2.15 months of severance, multiplied by a salary-load multiplier of 1.65, multiplied by the position's `monthly_cost_cents`, rounded half up to two decimals, and no mitigation factor applies. When three or four or more heads are severed, the same multiplication applies but a mitigation factor of 0.25 is inserted — the severed count, times 2.15, times 0.25, times `monthly_cost_cents`, times 1.65 — and the result is rounded half up to two decimals. The mitigation applies from the four-head boundary upward.

### 3.9. Closing and Merging Titles with Archive Continuity

A title that is being folded away follows its own small lifecycle, kept separate from the print suppression it accompanies. A `PrintOperationsDirector` announces a closure in a hub with a `title_code` unique within the hub, an `archive_retention_years` of at least one, and the `digital_replacement_url` of the title that will inherit the archive; the closure begins `announced`. An `archive_retention_years` below one is refused as `ERR_INVALID_REQUEST` (HTTP 400) and a `digital_replacement_url` left empty falls foul of the same code, both before the uniqueness check on `title_code`.

Publishing the statutory notice moves it to `notice_published`, and it is one of the operations the legal-notice gate holds: an attempt while the owning hub's `legal_notice_block` is true is refused with `ERR_LEGAL_NOTICE_HOLD` (HTTP 422) under §2.9, and — the block being a stored projection of the ratio gate — a hub whose ratio is currently failing is refused with that same code even where the stored flag has drifted, so both the flag and a freshly computed verdict must clear before the notice can go out. It is admitted only from `announced`, a publish from any other status being refused with `ERR_INVALID_STATE`. It also requires the title to retain its archive for at least one year, and requires the hub's qualifying print circulation for the title's market — measured over markets in `active`, `consolidation_planned` or `transfer_in_progress` — to be at or above the census enumeration floor. Because that floor is exactly the ratio gate of §2.9, a hub that has lost too many markets off time cannot publish a closure notice until the ratio recovers. A published closure can be halted: suspending it to `suspended` requires the hub's `legal_notice_block` to be true — suspending while the block is clear is refused with `ERR_INVALID_STATE`, as is suspending a closure that is not `notice_published` — and resuming it back to `notice_published` requires that block to be false, resuming a closure that is not `suspended` being refused with `ERR_INVALID_STATE`.

From `notice_published` or `suspended` the closure may be merged into its replacement title by naming the surviving `survivor_title_id`, which requires the `digital_replacement_url` to be non-empty; the merge sets the closure to `merged`, and the surviving closure in the same hub that shares the same `digital_replacement_url` and is itself `merged` inherits the archive, taking the larger of its own `archive_retention_years` and the merged title's as its retention period. A merge whose survivor `title_code` cannot be resolved is refused with `ERR_REFERENCE_NOT_FOUND` (HTTP 404); a survivor that resolves but sits in a different hub than the title being merged is refused as `ERR_RESOURCE_NOT_FOUND` (HTTP 404); and a merge attempted from a status other than `notice_published` or `suspended`, or by a title whose `digital_replacement_url` is empty, is refused with `ERR_INVALID_STATE`. The final step, from `merged` to `archived`, requires the archive handoff to have been recorded for the survivor chain and stamps `archive_handoff_checksum` from the survivor's checksum; an archive attempted from a status other than `merged` is refused with `ERR_INVALID_STATE`; a title whose survivor chain has not recorded a checksum is stamped with its own retained checksum, or a freshly minted placeholder when it holds none, rather than refused; and `archived` is terminal.
