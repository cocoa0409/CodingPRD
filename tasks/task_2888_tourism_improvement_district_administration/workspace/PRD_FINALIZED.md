# Tourism Improvement District Administration API — Product Requirements Document

## 1. Introduction

A tourism improvement district is a self-taxing arrangement among the lodging businesses of a destination: the operators petition to assess themselves, the assessments are collected through the operators rather than by a general tax levy, and the proceeds are spent on sales and marketing programs whose only honest measure of success is the number of room nights they actually generate. Every dollar in the system therefore belongs to somebody who can, and frequently does, challenge how it was calculated. The administration of such a district is consequently far less about marketing than about evidence: who signed the petition and how much room revenue their signature represented, which properties sit inside the boundary and which were exempt, what each operator reported versus what an independent auditor found, and whether the board spent the money inside the categories the enabling statute permits.

This document specifies the API that runs that administration end to end. It covers district formation from a revenue-weighted petition drive, boundary definition and the three alternative assessment methodologies, per-period statement generation and operator self-reporting, the collection waterfall and its exact reversibility, delinquency enforcement with penalty and interest, the annual budget and work plan the board must approve before a single program may run, execution and performance measurement of those programs in coordination with the destination marketing organization, the statutory transparency artifacts (public meetings, annual reports, financial audits) that gate renewal, the dispute proceeding an aggrieved operator may bring against a statement, and the renewal petition that must clear a higher bar than formation did.

Two design commitments run through the whole specification and should be read as constraints on every section that follows. First, **all temporal behavior is evaluated against a server-side logical clock**, never against wall-clock time, so that deadlines, grace periods, notice windows, renewal windows and stay intervals are reproducible. Second, **money is conserved and reversals are exact**: the district's collected total is at all times equal to the sum of the money buckets on its statements, and unwinding a payment restores every derived figure to the value it held beforehand rather than recomputing an approximation of it.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold everywhere in the API: identity and authorization, the response envelope, pagination, the logical clock, record metadata, rounding discipline, stale-version rejection, the order in which validations fire, and the cascade rules that let one write legitimately mutate several entities.

### 2.1. User and Role-Based Access Control

Every non-public request carries two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which it acts. Both must be present and non-empty, and `X-User-Role` must name one of exactly seven recognized roles — `DistrictAdministrator`, `BoardMember`, `LodgingOperator`, `DmoLiaison`, `HearingOfficer`, `IndependentAuditor`, and `PublicViewer`. A request that omits either header, sends either as empty, or sends a role string outside that set of seven is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). When the headers are well-formed but the declared role does not appear in the authorized-role list published for the requested operation in §4, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). The §4 table's Authorized Role(s) column is the authoritative input to that check.

Ten read operations are published for the general public and are served **with no headers at all**, because publication is the point of them: the district list, a single district, a district's financial summary, a district's petition drives, a district's annual work plans, a district's transparency records, a single petition drive, a single annual work plan, a single marketing program, and a single transparency record. On those ten the header requirement is waived entirely and `ERR_UNAUTHENTICATED` cannot arise. Every other operation in the API requires both headers.

Six of the seven roles carry an **opaque** identity. When `X-User-Role` is `DistrictAdministrator`, `BoardMember`, `DmoLiaison`, `HearingOfficer`, `IndependentAuditor` or `PublicViewer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against any entity's `id`. The server does record it where a workflow demands an audit trail or a separation-of-duties test — as `sponsor_user_id` and `approver_user_id` on a work plan, as `audited_by_user_id` on an assessment statement, as `engaged_by_user_id` on a transparency record, as `resolved_by_user_id` on a dispute, and as `verified_by_user_id` on a room-night claim — but it resolves none of those values to a stored principal.

`LodgingOperator` is the one **entity-backed** role. When `X-User-Role` is `LodgingOperator`, `X-User-ID` is the `id` of the acting lodging business, and ownership checks on any resource that references a lodging business compare that resource's `lodging_business_id` to `X-User-ID`. If the supplied `X-User-ID` matches no existing lodging business at all, the request is rejected with `ERR_OPERATOR_IDENTITY_UNKNOWN` (HTTP 403) before any path identifier is looked up; this check applies on every operation whose authorized-role list contains `LodgingOperator`. If the identity resolves but the target resource does not chain back to that business, the rejection is `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Ownership is deliberately evaluated **after** existence, so that a genuinely absent resource still yields a 404 rather than leaking, through a 403, the fact that the resource exists and belongs to somebody else. The ownership rule guards signing a petition, withdrawing a signature, filing a statement, amending a statement, remitting against a statement, filing a dispute, acting in a dispute proceeding, submitting a room-night claim, and reading a lodging business record together with all of its sub-resource lists.

Authorization is not symmetric between `DistrictAdministrator` and `LodgingOperator` on the operations they share. Signing, withdrawal, filing, amendment, remittance and dispute filing are all open to both, but the ownership comparison against `X-User-ID` is scoped to `LodgingOperator` only: a `DistrictAdministrator` acting on an operator's behalf is exempt from it. Within a dispute proceeding the split is finer still — `OPEN_REVIEW` and `REQUEST_INFO` belong to the `HearingOfficer`, while `SUBMIT_RESPONSE`, `APPEAL` and `WITHDRAW` are reserved to the owning `LodgingOperator`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.


### 2.3. Pagination

List operations are paginated through two query parameters. The `limit` parameter caps the number of records returned; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. The `offset` parameter is the number of records to skip before the page begins and defaults to 0. Unless a specific operation says otherwise, list results are ordered by `created_at` ascending; the only documented exception is the district's assessment-period list, which is ordered by `period_start` ascending.

Every list response carries four pagination fields inside the envelope's `meta` object: `limit`, `offset`, `total_count` and `has_more`. Filter parameters offered by individual list operations — for example `status`, `filing_status`, `payment_status`, `boundary_zone`, `drive_type`, `record_type`, `dispute_type`, `channel`, `fiscal_year` and `lodging_business_id` — narrow the result set before pagination is applied, so `total_count` always reflects the filtered set rather than the whole collection.

### 2.4. The Logical Clock

The server maintains a single **logical clock** that stands in for the current instant everywhere in this API. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time. Every deadline test, grace-period test, notice window, renewal window, petition window, filing window and stay-interval comparison in the sections that follow is evaluated against this clock, which is what makes the whole system's temporal behavior deterministic and independent of when the requests are actually issued.

A `DistrictAdministrator` may move the clock to an explicit instant by supplying `current_utc`. That operation returns no payload, and it charges no assessment, no penalty and no interest: delinquency is only ever assessed by an explicit sweep. It does, however, have one automatic consequence. Every transparency record still sitting in `SCHEDULED` or `NOTICED` whose `required_by` instant now lies in the past moves to the terminal state `OVERDUE`, and each such stamp re-derives the owning district's `transparency_standing`, which in turn can foreclose renewal. That chain is specified in §3.9.

### 2.5. Common Resource Properties

All twelve persisted resource types in this system — districts (`District`), lodging businesses (`LodgingBusiness`), petition drives (`PetitionDrive`), petition signatures (`PetitionSignature`), assessment periods (`AssessmentPeriod`), assessment statements (`AssessmentStatement`), remittances (`Remittance`), annual work plans (`AnnualWorkPlan`), marketing programs (`MarketingProgram`), room-night claims (`RoomNightClaim`), transparency records (`TransparencyRecord`) and assessment disputes (`AssessmentDispute`) — carry the same four system-managed properties:

- **`id`** (string): a server-minted unique identifier formatted as a UUID, with no type prefix of any kind.
- **`created_at`** (string): an ISO 8601 timestamp in UTC with three fractional digits, recording when the record was first persisted. This stamp is record metadata rather than workflow data: unlike the workflow instants that §3 explicitly stamps from the logical clock (`filed_at`, `signed_at`, `tallied_at`, `filed_on`, `reversed_on` and the rest), `created_at` is taken from the server's **real wall-clock time**, so it is neither derived from nor comparable to the logical clock's reading of §2.4.
- **`updated_at`** (string): an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the record, from the same real wall-clock source as `created_at`. A record that has not yet been mutated carries an `updated_at` exactly equal to its `created_at`.
- **`version`** (integer): a counter that starts at 1 when the record is created and increments by exactly 1 on every subsequent mutation of that record.

No entity in this system is exempt from `updated_at` or `version`; all twelve carry the full set. A mutation for these purposes includes a change to a *derived* field: when a signature recomputes a drive's `weighted_support_pct`, or a remittance recomputes a district's `collected_to_date_cents`, the drive and the district have each been mutated, and each independently refreshes its own `updated_at` and increments its own `version`. This matters because two operations in this API compare a client-supplied version against a stored one (§2.7), and a client that has not observed a cascade will hold a stale number.

### 2.6. Money, Percentages and Rounding

Every monetary quantity in this API is an **integer number of cents**, named with a `_cents` suffix, and is transported as a JSON integer rather than a string or a decimal. There is no sub-cent representation anywhere in the system.

Every rounding step in this specification uses **round half up**: a value exactly on the halfway mark rounds away from zero. Monetary results round to a whole cent. The four ratio quantities — a drive's `weighted_support_pct` and `headcount_support_pct`, a work plan's `funding_ratio`, and a marketing program's `performance_index` — round to exactly **four decimal places**. The three configurable district thresholds `formation_threshold_pct`, `renewal_threshold_pct` and `renewal_headcount_threshold_pct` are likewise carried at four decimal places, and each must lie between 0.0001 and 1.0000 inclusive.

Where a calculation applies more than one rounding step, the *number and position* of those steps is part of the contract and may not be optimized away. Two consequences are called out because they are easy to get wrong. First, support percentages perform exactly one division and exactly one rounding, at the very end; per-business shares are never rounded individually and then summed, because that ordering drifts by up to half a cent per business. Second, delinquency penalty and interest are rounded **once per statement** and only then accumulated into the district total; summing the outstanding balances of a period first and applying the rates to that aggregate produces a different total whenever any per-statement product lands on a half cent, and is therefore wrong.

### 2.7. Stale-Version Rejection on Amendment Writes

Exactly two operations in this API require the caller to declare the version of the record it last observed, and both of them are amendment writes — writes that legitimately *supersede* whatever was stored before, and which therefore cannot be protected by a state precondition.

The first is `POST /assessment-statements/{id}/amendments`. The request must carry `expected_statement_version`, a non-optional field holding the client's last observed `version` of the target assessment statement. If that number does not equal the statement's current stored `version`, the amendment is rejected with `ERR_STALE_STATEMENT_VERSION` (HTTP 412). A granted dispute resolution or a preceding amendment bumps the statement's `version` without producing any state change the operator can see from the outside, so an operator working from a cached view goes stale silently; this check is the only thing standing between that operator and the silent overwrite of an amendment it never saw.

The second is `POST /annual-work-plans/{id}/amendments`. The request must carry `expected_work_plan_version`, holding the client's last observed `version` of the target annual work plan. A mismatch against the plan's current stored `version` is rejected with `ERR_STALE_WORK_PLAN_VERSION` (HTTP 412). The automatic move into `AMENDMENT_PENDING` driven by a funding-ratio recompute is the usual reason the number moves between the read and the write.

No other operation in this API accepts a version field. Every other write is guarded by state preconditions and business rules alone, and supplying a version to one of them has no effect.

### 2.8. Validation Order

When several rules could reject the same request, the outcome is determined by a fixed priority ladder, evaluated from the top and stopping at the first rule that fails. The ladder is:

1. **Authentication** — headers present, non-empty, and naming one of the seven roles: `ERR_UNAUTHENTICATED`.
2. **Authorization** — the acting role appears in the operation's authorized-role list: `ERR_FORBIDDEN_ROLE`.
3. **Operator identity resolution** — a `LodgingOperator`'s `X-User-ID` resolves to an existing lodging business: `ERR_OPERATOR_IDENTITY_UNKNOWN`.
4. **Request shape** — every non-optional input field is present; every enum-typed field carries a declared member; every cent-valued field is an integer that is not negative; every date or instant field parses as ISO 8601; every interval field has its start strictly before its end. Any failure here is `ERR_INVALID_REQUEST` (HTTP 400). Requesting publication of a transparency record without a `document_reference` also lands here.
5. **Existence** — path identifiers are resolved left to right, and then body foreign keys in the order the fields are declared for that operation; the *first* unresolved reference decides which 404 is returned, from `ERR_DISTRICT_NOT_FOUND`, `ERR_LODGING_BUSINESS_NOT_FOUND`, `ERR_PETITION_DRIVE_NOT_FOUND`, `ERR_PETITION_SIGNATURE_NOT_FOUND`, `ERR_ASSESSMENT_PERIOD_NOT_FOUND`, `ERR_ASSESSMENT_STATEMENT_NOT_FOUND`, `ERR_REMITTANCE_NOT_FOUND`, `ERR_WORK_PLAN_NOT_FOUND`, `ERR_MARKETING_PROGRAM_NOT_FOUND`, `ERR_ROOM_NIGHT_CLAIM_NOT_FOUND`, `ERR_TRANSPARENCY_RECORD_NOT_FOUND` and `ERR_DISPUTE_NOT_FOUND`. This applies to every operation carrying a path identifier or a body foreign key. A supplied `remittance_id` that exists but belongs to a different statement than the one in the path is treated as not found and yields `ERR_REMITTANCE_NOT_FOUND`.
6. **Ownership** — `ERR_NOT_RESOURCE_OWNER`, as described in §2.1.
7. **State preconditions** — the target is in a state from which the requested transition is declared, including every cross-entity guard that transition names (district active, period open or closed, plan approved, drive open, program planned or running, dispute non-terminal). Terminal states accept nothing. The generic failure is `ERR_INVALID_STATE_TRANSITION` (HTTP 409); the specific guards `ERR_STATEMENT_ALREADY_CERTIFIED`, `ERR_DISTRICT_NOT_ACTIVE`, `ERR_PERIOD_NOT_CLOSED`, `ERR_WORK_PLAN_NOT_APPROVED`, `ERR_DMO_AGREEMENT_NOT_EXECUTED`, `ERR_PROGRAM_SPEND_FROZEN` and `ERR_CLAIMS_PENDING_VERIFICATION` sit at the same rung and are described where their workflows are.
8. **Stale-version rejection** — `ERR_STALE_STATEMENT_VERSION` and `ERR_STALE_WORK_PLAN_VERSION`, per §2.7. This rung sits below state checks, so a statement already `CERTIFIED` reports `ERR_STATEMENT_ALREADY_CERTIFIED` even when the caller also sent a stale `expected_statement_version`.
9. **Separation of duties and transparency compliance** — `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) and `ERR_TRANSPARENCY_REQUIREMENTS_UNMET` (HTTP 409). Because these sit above every temporal, referential, constraint and fiscal rule, an approval attempted by the plan's own sponsor reports the separation failure even when the plan's category mix would also have failed a cap.
10. **Temporal windows** — `ERR_PETITION_WINDOW_CLOSED`, `ERR_RENEWAL_WINDOW_NOT_OPEN`, `ERR_MEETING_NOTICE_TOO_LATE`, `ERR_CLAIM_OUTSIDE_BOOKING_WINDOW` and `ERR_FILING_WINDOW_CLOSED`.
11. **Referential rules** — `ERR_BUSINESS_OUTSIDE_BOUNDARY`, `ERR_BUSINESS_EXEMPT`, `ERR_DUPLICATE_SIGNATURE`, `ERR_STATEMENT_ALREADY_EXISTS_FOR_PERIOD`, `ERR_DISPUTE_ALREADY_OPEN` and `ERR_REMITTANCE_ALREADY_REVERSED`.
12. **Structural constraints** — `ERR_PERIOD_OVERLAP`, `ERR_MEETING_SEPARATION_VIOLATION`, `ERR_CLAIM_STAY_OVERLAP`, `ERR_CLAIM_EXCEEDS_CAPACITY`, `ERR_EXPENDITURE_CATEGORY_NOT_PERMITTED`, `ERR_ADMIN_SHARE_EXCEEDED`, `ERR_CONTINGENCY_SHARE_EXCEEDED`, `ERR_MARKETING_SHARE_BELOW_MINIMUM` and `ERR_APPEAL_LIMIT_EXCEEDED`.
13. **Fiscal rules** — `ERR_AMENDMENT_VARIANCE_EXCEEDED`, `ERR_FUNDING_RATIO_BELOW_MINIMUM`, `ERR_PROGRAM_BUDGET_EXCEEDED`, `ERR_LODGING_TAX_MATCH_CAP_EXCEEDED`, `ERR_LODGING_TAX_MATCH_EXHAUSTED`, `ERR_REMITTANCE_EXCEEDS_TOTAL_DUE`, `ERR_ADJUSTMENT_EXCEEDS_ASSESSMENT` and `ERR_PETITION_POOL_TOO_SMALL`.

Two consequences of this ordering deserve emphasis. The petition-pool floor and the funding-ratio floor sit at the bottom of the ladder, so a request that violates both a state precondition and a fiscal floor always reports the state failure. And because ownership sits below existence, an operator probing for another property's statement identifiers learns only that they do not exist as far as it is concerned — a 404, never a 403.

### 2.9. Nested Reads and Path Resolution

Several read operations address a child collection through its parent — a district's lodging businesses, a district's petition drives, a drive's signatures, a period's statements, a statement's remittances, a statement's disputes, a plan's marketing programs, a program's room-night claims, a business's signatures, statements, claims and disputes. In all of them the parent identifier in the path is resolved first and reported as its own 404 if it is unknown; only then is the child collection assembled and filtered. A district that exists but holds no assessment periods returns an empty array with `total_count` 0, not a 404. Assessment statements are never addressable as a top-level collection: they are reachable through a single-statement read, through the owning period's statement list, or through the owning business's statement list.

### 2.10. Cascade Discipline

Many writes in this system legitimately mutate more than one record, and some mutate a record whose change then causes a further mutation elsewhere. Those chains are specified explicitly in §3 as ordered hops, and the ordering is normative, because a hop is caused by the mutation the *previous* hop wrote rather than by the original call. Two long chains exist: a four-hop chain out of a delinquency sweep (§3.5), and a three-hop chain out of a granted dispute resolution (§3.6).

Every record touched anywhere in a cascade refreshes its own `updated_at` and increments its own `version`, including records the caller never named. A district whose assessable roll is recomputed because a property was revised has been mutated. A drive whose support percentages were re-scored because a signer left the boundary has been mutated. Recomputation always reaches a fixed point: a work plan's compliance recomputation reads statements and writes only the plan and its programs, and never writes back to any statement, so there is no oscillation.

### 2.11. Segregation of Duties

Three points in this system require that the principal who *proposes* something differ from the principal who *blesses* it, and all three compare opaque `X-User-ID` values. Approving an annual work plan requires an `X-User-ID` different from the one stored as `sponsor_user_id`. Certifying an assessment statement requires an `X-User-ID` different from the one stored as `audited_by_user_id`. Advancing a transparency record of type `FINANCIAL_AUDIT` to either `COMPLETED` or `PUBLISHED` requires an `X-User-ID` different from the one stored as `engaged_by_user_id` when that record was created. All three failures are reported as `ERR_SEGREGATION_OF_DUTIES` with HTTP 403. Note the asymmetry on the transparency path: the separation applies only to `FINANCIAL_AUDIT` records, and applies to *both* the completion advance and the publication advance, not just one of them.

### 2.12. The Conserved Collection Identity

At every instant, a district's `collected_to_date_cents` equals the sum, over every one of that district's assessment statements, of `interest_paid_cents` plus `penalty_paid_cents` plus `principal_paid_cents` plus `credit_balance_cents`. This identity is checked after every forward payment and after every reversal, and it is what makes the collection ledger auditable. Its companion, `delinquent_charges_cents`, is the sum over the same statements of `penalty_cents` plus `interest_cents`, accumulated from the per-statement rounded values as described in §2.6.

Two mechanisms preserve the identity under corrections. A reversal subtracts exactly the four per-bucket amounts recorded on the remittance row rather than re-running the allocation backwards, so the identity holds regardless of the order in which payments and reversals arrive. And when a downward correction leaves a statement's principal above its new assessment, the excess *migrates* from `principal_paid_cents` into `credit_balance_cents` rather than disappearing — cents move between buckets of the same statement and never leave the district.

## 3. Business Logic & Workflows

### 3.1. Proposing a District and Building the Assessable Roll

A `DistrictAdministrator` opens the whole process by proposing a district, supplying its legal `name` — non-blank, between 1 and 120 characters — and, optionally, the parameters that will govern its life. The methodology selector `assessment_method` chooses which branch of the assessment calculation the district's statements will run and takes one of `PCT_OF_ROOM_REVENUE`, `PER_OCCUPIED_ROOM_NIGHT` or `TIERED_BY_CLASSIFICATION`, defaulting to `PCT_OF_ROOM_REVENUE`. The boundary itself is expressed as `included_zones`, the set of zone codes that lie inside the district; it must be a non-empty subset of `ZONE_CORE` and `ZONE_PERIMETER`, must not repeat a code, and defaults to both zones. Three support thresholds may be tuned: `formation_threshold_pct` is the minimum revenue-weighted support a formation drive must reach and defaults to 0.6000; `renewal_threshold_pct` is the corresponding revenue-weighted minimum for a renewal drive and defaults to 0.6500; and `renewal_headcount_threshold_pct` is an *additional* headcount minimum that binds only on renewal drives, defaulting to 0.5000. `term_years`, the number of years each certification adds to the district's term, defaults to 5 and must be between 1 and 10 inclusive. `current_fiscal_year` is the year the district is presently budgeting for, defaults to 2027, and must be between 2020 and 2050 inclusive.

A newly proposed district lands in `status` `PROPOSED`. Its lifecycle `status` moves through the eight values `PROPOSED`, `PETITION_CIRCULATING`, `FORMATION_FAILED`, `FORMED`, `ACTIVE`, `RENEWAL_PENDING`, `EXPIRED` and `DISESTABLISHED`, of which `FORMATION_FAILED`, `EXPIRED` and `DISESTABLISHED` are terminal. Both `formed_on` and `expiration_date` start null; they are stamped by certification, never by proposal. `transparency_standing` starts `COMPLIANT` and only ever holds `COMPLIANT` or `DEFICIENT`. The destination-marketing fields start empty: `dmo_name` is null and `dmo_agreement_status` is `NONE`, the other members of that enumeration being `PROPOSED`, `EXECUTED`, `SUSPENDED` and `TERMINATED`. The five money and count aggregates all start at zero — `dmo_contract_cents`, `public_lodging_tax_offset_cents`, `lodging_tax_match_pool_cents`, `lodging_tax_match_committed_cents`, `collected_to_date_cents`, `delinquent_charges_cents`, `assessable_basis_cents` and `assessable_business_count` — and none of them may ever go negative.

**The assessable set** is the single most-consulted derived concept in the system, and it has exactly one definition. A lodging business belongs to its district's assessable set when its `status` is `ASSESSABLE`, its `exempt_status` is `NONE`, and its `boundary_zone` is a member of the district's `included_zones`. `assessable_basis_cents` is the sum of `prior_year_gross_room_revenue_cents` over that set, and `assessable_business_count` is the number of members of that same set. Both are recomputed whenever anything that could change membership happens: a property is added, a property is revised, the boundary is redefined, a property is closed out, or a dispute grants an exemption.

Adding a property to the roll means supplying its `district_id`, its registered `legal_name` (non-blank, 1 to 120 characters), the `boundary_zone` it physically sits in — `ZONE_CORE`, `ZONE_PERIMETER`, or `OUTSIDE` for a property in no district zone at all — its lodging `classification`, which is one of `FULL_SERVICE`, `LIMITED_SERVICE`, `BOUTIQUE` or `SHORT_TERM_RENTAL`, its rentable `room_count` (at least 1), its `prior_year_gross_room_revenue_cents` (not negative), and an `operator_contact_email` that is non-blank and contains an at-sign, which is the notice address for statements and delinquency notices. Two further inputs are optional: `exempt_status`, drawn from `NONE`, `GOVERNMENT_OWNED`, `UNDER_MINIMUM_ROOMS` and `NONPROFIT_RETREAT` and defaulting to `NONE`, and `remittance_frequency`, either `MONTHLY` or `QUARTERLY` and defaulting to `MONTHLY`.

The property's `status` is *resolved by the server at creation* rather than supplied, across the four values `ASSESSABLE`, `EXEMPT`, `OUTSIDE_BOUNDARY` and terminal `CLOSED_OUT`. A property whose asserted `exempt_status` is anything other than `NONE` is created directly in `EXEMPT`. A property whose `room_count` is below the five-room minimum is likewise created in `EXEMPT`, with its `exempt_status` forced to `UNDER_MINIMUM_ROOMS`. A property whose `boundary_zone` is not a member of the district's `included_zones` — which includes every property whose zone is `OUTSIDE` — is created in `OUTSIDE_BOUNDARY`. Only a property that clears all three tests is created `ASSESSABLE`. Creation also initialises `delinquency_strike_count` to 0 and `compliance_standing` to `GOOD`, then recomputes the district's assessable aggregates and re-scores every open petition drive of the district.

Revising a property accepts any subset of `boundary_zone`, `classification`, `room_count`, `prior_year_gross_room_revenue_cents`, `exempt_status`, `remittance_frequency` and `operator_contact_email`, plus the flag `close_out`. Assessability is re-derived from the resolved values on every revision, and the movement it produces is a genuine state transition with cascades attached. A property that was `ASSESSABLE` and now resolves to a non-`NONE` `exempt_status` — or whose `room_count` drops below five, which forces `exempt_status` to `UNDER_MINIMUM_ROOMS` — moves `ASSESSABLE → EXEMPT`. That flip recomputes the district's `assessable_basis_cents` and `assessable_business_count`, and it disqualifies every `VALID` signature this property holds on any `OPEN` drive, stamping `disqualification_reason` `BUSINESS_EXEMPT` and forcing each affected drive to recompute `signed_basis_cents`, `valid_signature_count`, `weighted_support_pct` and `headcount_support_pct`.

The exemption is not one-way. A revision that resolves `exempt_status` back to `NONE`, on a property whose `room_count` is at least five and whose `boundary_zone` is a member of `included_zones`, moves the property `EXEMPT → ASSESSABLE` and recomputes the district's two aggregates — closing the cycle `ASSESSABLE → EXEMPT → ASSESSABLE`. A revision setting `boundary_zone` to a zone outside `included_zones` moves the property `ASSESSABLE → OUTSIDE_BOUNDARY`, recomputes the district aggregates, and disqualifies that property's `VALID` signatures on `OPEN` drives with `disqualification_reason` `OUTSIDE_BOUNDARY`, that signature change itself forcing each affected drive to recompute `signed_basis_cents`, `valid_signature_count` and `weighted_support_pct`. A revision bringing the zone back inside moves the property `OUTSIDE_BOUNDARY → ASSESSABLE` provided its resolved `exempt_status` is `NONE` and its `room_count` is at least five, and recomputes the district aggregates — but **already disqualified signatures are not restored**. Disqualification is permanent; the operator must sign again.

Passing `close_out` as true retires a property permanently, moving it from `ASSESSABLE`, `EXEMPT` or `OUTSIDE_BOUNDARY` to terminal `CLOSED_OUT` and recomputing the district aggregates. Close-out is refused while the property still owes money: no statement of that property may sit in `payment_status` `UNPAID`, `PARTIALLY_PAID` or `DELINQUENT` with a positive `total_due_cents`. One further guarantee protects history — a revision changing zone or classification never rewrites a past period's audited amount, because final assessments read the snapshot the statement captured at period start rather than the property's live values.

Redefining the boundary is a district-level act. The administrator supplies a replacement `included_zones` set and an `effective_on` instant, and every property on the roll is re-evaluated against the new set in one pass: properties whose `boundary_zone` has left the set move `ASSESSABLE → OUTSIDE_BOUNDARY` and have their `VALID` signatures on `OPEN` drives disqualified with reason `OUTSIDE_BOUNDARY`, properties whose zone has re-entered move `OUTSIDE_BOUNDARY → ASSESSABLE`, the district's `assessable_basis_cents` and `assessable_business_count` are recomputed, and support is re-scored for every `OPEN` drive of the district.

Coordination with the destination marketing organization and with the city's public lodging tax programs is recorded on the district itself. The administrator supplies `dmo_name`, `dmo_agreement_status` and `dmo_contract_cents`, and may additionally set `lodging_tax_match_pool_cents` — the pool of public lodging tax dollars the city has made available to match district-funded marketing spend — and `public_lodging_tax_offset_cents`, the credit the city's lodging tax program grants against district assessments. Moving `dmo_agreement_status` to `EXECUTED` is the cross-entity gate that lets marketing programs launch at all. Lowering the pool is constrained: if the new `lodging_tax_match_pool_cents` would fall below the district's already-committed `lodging_tax_match_committed_cents`, the coordination call is refused with `ERR_LODGING_TAX_MATCH_EXHAUSTED`, and if the committed total would exceed half of the approved plan total for `current_fiscal_year`, the refusal is `ERR_LODGING_TAX_MATCH_CAP_EXCEEDED`. `lodging_tax_match_committed_cents` is itself derived — the sum of `lodging_tax_matched_cents` over the district's marketing programs whose `status` is not `CANCELLED`.

Once a district has reached a terminal state, it stops accepting new activity of any kind. A district that is `FORMATION_FAILED`, `EXPIRED` or `DISESTABLISHED` rejects the creation of assessment periods, annual work plans, marketing programs, transparency records and petition drives, in all five cases with `ERR_DISTRICT_NOT_ACTIVE`.

For transparency purposes the district also publishes a computed financial summary, derived on read from the statements themselves and never stored. Narrowed optionally by `fiscal_year`, it reports `district_id`, `fiscal_year`, `billed_total_cents`, `collected_to_date_cents`, `delinquent_charges_cents`, `outstanding_total_cents`, `credit_total_cents`, `statement_count`, `delinquent_statement_count` and `lodging_tax_match_committed_cents`, reconciling what was billed against what was collected, what remains outstanding and what is held as credit across every assessment period of the district.

### 3.2. Petition Circulation, the Tally Fork, and the District Term

Nothing about a district is real until its lodging businesses have petitioned for it. A `DistrictAdministrator` opens a drive by supplying the `district_id`, the `drive_type` — either `FORMATION`, which creates the district's term, or `RENEWAL`, which extends it — and a `closes_at` instant after which no further signature may be recorded. The drive is created with `status` `OPEN`, its `opened_on` stamped from the logical clock, and its threshold pair *snapshotted from the district at open time* so that later tuning of the district cannot move the goalposts mid-drive. For a formation drive, `required_weighted_pct` is copied from the district's `formation_threshold_pct` and `required_headcount_pct` is snapshotted as 0.0000, so that only the revenue-weighted test binds. For a renewal drive, `required_weighted_pct` is copied from `renewal_threshold_pct` and `required_headcount_pct` from `renewal_headcount_threshold_pct`, so that both tests bind. The drive also snapshots the current denominators into `assessable_basis_snapshot_cents` and `assessable_count_snapshot`, and starts with `signed_basis_cents` and `valid_signature_count` at 0, `weighted_support_pct` and `headcount_support_pct` at 0.0000, `short_reason` at `NONE` and `tallied_at` null.

Opening a formation drive is what moves the district out of proposal: it requires the district to be `PROPOSED`, requires that no drive of that district is currently `OPEN`, and requires the district's `assessable_business_count` to be **at least three** — a one- or two-property district cannot petition itself into existence. On success the district advances `PROPOSED → PETITION_CIRCULATING`. Opening a *renewal* drive instead requires the district to be inside its renewal window: the logical clock must be no more than 180 whole days before the district's `expiration_date` and must not be at or past it. Outside that half-open window the request is refused with `ERR_RENEWAL_WINDOW_NOT_OPEN`.

A signature is recorded against a drive by naming the `lodging_business_id` of the signing property. Either the property itself, acting as `LodgingOperator`, or a `DistrictAdministrator` on its behalf may record it; when the actor is the operator, its `X-User-ID` must equal the `lodging_business_id` it names. The new signature stores its `petition_drive_id`, stamps `signed_at` from the logical clock, and — critically — captures `weight_basis_revenue_cents` as a snapshot of the signer's `prior_year_gross_room_revenue_cents` **at the moment of signing**, which is never re-read afterwards. A property that grows its room revenue after signing does not thereby strengthen its own signature. The signature is created with `status` `VALID` and `disqualification_reason` `NONE`.

Four rules guard signing. The logical clock must lie inside the drive's half-open window running from `opened_on` up to but not including `closes_at`; outside it the answer is `ERR_PETITION_WINDOW_CLOSED`. The signer must belong to the same district as the drive, must have a `boundary_zone` that is a member of the district's `included_zones`, and must have `status` `ASSESSABLE`; a failure of any of those three is `ERR_BUSINESS_OUTSIDE_BOUNDARY`. A signer whose `exempt_status` is anything other than `NONE`, or whose `status` is `EXEMPT`, holds no petition standing and is refused with `ERR_BUSINESS_EXEMPT`. And at most one `VALID` signature may exist for a given drive-and-property pair, a second attempt yielding `ERR_DUPLICATE_SIGNATURE` — though a prior signature that was withdrawn or disqualified does not block a fresh one, because those signatures are no longer `VALID`.

An operator may withdraw its own signature during the window, optionally recording a `reason`, and again a `DistrictAdministrator` may do so on the operator's behalf without the ownership comparison. Withdrawal requires the signature to be `VALID`, the owning drive to be `OPEN`, and the logical clock to still be before `closes_at`; the temporal failure is again `ERR_PETITION_WINDOW_CLOSED`. The signature moves `VALID → WITHDRAWN`, the drive's `signed_basis_cents` is reduced by exactly that signature's `weight_basis_revenue_cents`, `valid_signature_count` is reduced by one, and both support percentages are recomputed — restoring, exactly, the values the drive held immediately before the signature was recorded.

Signatures can also be taken away without the operator's involvement. A `VALID` signature on an `OPEN` drive moves to `DISQUALIFIED` whenever its signer has just reached `compliance_standing` `SUSPENDED`, has just moved to `status` `OUTSIDE_BOUNDARY`, or has just moved to `status` `EXEMPT`. The `disqualification_reason` records which of the three causes applied — `COMPLIANCE_SUSPENDED`, `OUTSIDE_BOUNDARY` or `BUSINESS_EXEMPT` — and the drive's `signed_basis_cents` and `valid_signature_count` are reduced by that signature's contribution, with both support percentages recomputed. `WITHDRAWN` and `DISQUALIFIED` are both terminal for a signature.

**Computing support.** Support is recomputed on every signature recorded, every withdrawal, every cascade that disqualifies a signature, every boundary redefinition, every property revision that changes the assessable set, and once more immediately before the threshold comparison inside a tally. The recomputation proceeds in a fixed order. First the denominators: the assessable set is the district's lodging businesses whose `status` is `ASSESSABLE`, whose `exempt_status` is `NONE`, and whose `boundary_zone` is a member of the district's `included_zones`; `assessable_basis_snapshot_cents` is set to the sum of `prior_year_gross_room_revenue_cents` over that set and `assessable_count_snapshot` to the count of that set. The denominator is therefore the assessable set **as of the recompute instant**, not as of drive open. Then the numerators: the valid set is the drive's signatures whose `status` is `VALID`; `signed_basis_cents` is the sum of `weight_basis_revenue_cents` over the valid set and `valid_signature_count` is its count. Withdrawn and disqualified signatures contribute nothing to either numerator.

The two support figures then each perform **one division and one rounding**, at the very end. `weighted_support_pct` is `signed_basis_cents` divided by `assessable_basis_snapshot_cents`, rounded half up to four decimal places — or exactly 0.0000 when `assessable_basis_snapshot_cents` is zero. `headcount_support_pct` is `valid_signature_count` divided by `assessable_count_snapshot`, rounded half up to four decimal places — or exactly 0.0000 when `assessable_count_snapshot` is zero. These are the two variants of one measurement, and they diverge sharply on the same data: the revenue-weighted variant lets a single large property carry a drive on its own, while the headcount variant is indifferent to property size, which is precisely why a renewal drive can pass the revenue test and still fail on headcount.

A drive qualifies when `weighted_support_pct` is **greater than or equal to** `required_weighted_pct` *and* `headcount_support_pct` is **greater than or equal to** `required_headcount_pct`. Both comparisons are inclusive, so support landing exactly on a threshold qualifies.

**The tally fork.** A `DistrictAdministrator` tallies an `OPEN` drive; the drive recomputes support immediately before the comparison, stamps `tallied_at` from the logical clock, and then forks. On the qualifying branch the drive moves `OPEN → QUALIFIED` and `short_reason` is set to `NONE`. On the failing branch the drive moves `OPEN → SHORT_OF_THRESHOLD`, which is terminal, and `short_reason` records which test failed: the revenue-weighted test is evaluated first, so `short_reason` is `WEIGHTED_BELOW_THRESHOLD` whenever `weighted_support_pct` is below `required_weighted_pct`, and `HEADCOUNT_BELOW_MINIMUM` only when the weighted test passed and the headcount test alone failed. The two branches differ in one more respect, and the difference is not cosmetic: on the failing branch, a `FORMATION` drive additionally drives its district `PETITION_CIRCULATING → FORMATION_FAILED`, which is terminal for the district, while a `RENEWAL` drive leaves the district exactly where it was, in `RENEWAL_PENDING`. The qualifying branch touches no district status at all. Tallying is also refused with `ERR_PETITION_POOL_TOO_SMALL` when the district's eligible assessable pool holds fewer than three businesses.

**Certification** is what turns a qualified petition into a term. A `DistrictAdministrator` certifies a `QUALIFIED` drive, optionally recording a `certified_on` value, and the drive moves `QUALIFIED → CERTIFIED`, which is terminal. Certification requires the district to be in the matching state: `PETITION_CIRCULATING` for a formation drive, `RENEWAL_PENDING` for a renewal drive. It is likewise refused with `ERR_PETITION_POOL_TOO_SMALL` when fewer than three businesses remain in the eligible assessable pool. Certifying a **formation** drive advances the district `PETITION_CIRCULATING → FORMED`, stamps `formed_on` from the logical clock, and sets `expiration_date` to that same instant advanced by `term_years` years. Certifying a **renewal** drive advances the district `RENEWAL_PENDING → ACTIVE`, extends the existing `expiration_date` by a further `term_years` years, and advances `current_fiscal_year`. A renewal certification is additionally gated on transparency: the district must hold a `PUBLISHED` transparency record of type `ANNUAL_REPORT` and a `PUBLISHED` transparency record of type `FINANCIAL_AUDIT` for its `current_fiscal_year`, and its `transparency_standing` must not be `DEFICIENT`. A shortfall on any of those is `ERR_TRANSPARENCY_REQUIREMENTS_UNMET`.

**Driving the district lifecycle.** The remaining district movements are requested directly by a `DistrictAdministrator`, who names the desired `to_status` and may attach an `effective_on` instant and a `reason`. Four destinations are accepted.

Requesting `ACTIVE` activates a `FORMED` district. It requires the district to be `FORMED`, requires the district's formation drive to be `CERTIFIED`, and requires `assessable_business_count` to still be at least three — a district whose assessable roll collapsed between certification and activation may not be activated. Activation sets `status` to `ACTIVE` and deliberately leaves `formed_on` and `expiration_date` exactly as certification stamped them; nothing about activation re-dates the term.

Requesting `RENEWAL_PENDING` opens the renewal window on an `ACTIVE` district. It requires the logical clock to be at or after `expiration_date` minus 180 whole days and strictly before `expiration_date`, failing with `ERR_RENEWAL_WINDOW_NOT_OPEN` outside that range. It further requires `transparency_standing` to be `COMPLIANT`, and requires at least one `PUBLISHED` `ANNUAL_REPORT` record and at least one `PUBLISHED` `FINANCIAL_AUDIT` record for the district, failing with `ERR_TRANSPARENCY_REQUIREMENTS_UNMET` otherwise. The district cannot enter renewal while any transparency artifact stands `OVERDUE`. On success `status` becomes `RENEWAL_PENDING`, and the cycle `ACTIVE → RENEWAL_PENDING → ACTIVE` closes when the renewal drive is certified.

Requesting `EXPIRED` lets the term lapse. It is accepted from `ACTIVE` or `RENEWAL_PENDING` and requires the logical clock to be at or after `expiration_date`. The district's `status` becomes `EXPIRED`. Expiry deliberately does **not** close assessment periods — every period of the district still in `OPEN` is left untouched, remaining readable while rejecting further writes. When the district was in `RENEWAL_PENDING`, expiry additionally moves every drive of the district still in `OPEN` to `WITHDRAWN`.

Requesting `DISESTABLISHED` dissolves the district early. It is accepted from `ACTIVE` or `RENEWAL_PENDING` and requires that no assessment period of the district is still `OPEN`. On success `status` becomes `DISESTABLISHED`, every drive of the district still `OPEN` moves to `WITHDRAWN`, and every marketing program under any of the district's work plans whose `status` is `PLANNED`, `RUNNING` or `SUSPENDED_PENDING_AMENDMENT` moves to `CANCELLED`. Where a district is dissolved from `ACTIVE`, that cancellation also clears `spend_frozen` back to false on each cancelled program.

### 3.3. Assessment Periods, Statement Generation and the Filing Dimension

Assessments are billed in periods. A `DistrictAdministrator` opens one by supplying the `district_id`, a human `period_label` such as "2026-09" that is non-blank and at most 32 characters, the occupancy window as an inclusive `period_start` and an exclusive `period_end` that must fall strictly after it, a `due_date` by which remittance is due that must be at or after `period_end`, and optionally `grace_days`, the number of whole days added to `due_date` before a statement may be swept as delinquent, which defaults to 10 and must be between 0 and 60 inclusive. The period is created with `status` `OPEN` — the other two values being `CLOSED` and terminal `DELINQUENCY_SWEPT` — with `statement_count` at 0 and `billed_total_cents` and `collected_total_cents` at 0. Periods of one district are treated as half-open intervals and may not overlap; a new period starting exactly on an existing period's `period_end` is accepted, while any genuine overlap is refused with `ERR_PERIOD_OVERLAP`.

Statement generation issues one statement per eligible property in a single pass, walking the district's roll in `created_at` ascending order of the businesses. A property is eligible when its `status` is `ASSESSABLE`, its `exempt_status` is `NONE` and its `boundary_zone` is a member of the district's `included_zones` — which is exactly the assessable set of §3.1, and which is why exempt, out-of-boundary and closed-out properties are never billed at all. A property failing the boundary or district-membership arm of that test is reported as `ERR_BUSINESS_OUTSIDE_BOUNDARY`. The response is a summary rather than a list of statements: it carries the `assessment_period_id`, a `generated_count`, a `skipped_count` and the array `statement_ids`. `skipped_count` counts every member of the district's roll that received no new statement on this run — both those that already hold one for the period and those excluded by the eligibility filter. At most one statement may exist per period-and-property pair, so a re-run generates only the eligible properties still missing one; a re-run on which no eligible property is missing a statement, and where `generated_count` would therefore be 0, is refused outright with `ERR_STATEMENT_ALREADY_EXISTS_FOR_PERIOD`. Generation updates the period's `statement_count`.

Each statement records its `assessment_period_id` and its `lodging_business_id`, and captures three **period-start snapshots** that are the whole reason the two assessment variants can disagree: `zone_at_period_start` copies the property's `boundary_zone`, `classification_at_period_start` copies its `classification`, and `assessment_method_at_period_start` copies the district's `assessment_method`, pinning which formula branch both variants will use. A statement begins with `filing_status` `NOT_FILED` and `payment_status` `UNPAID`, with `reported_room_nights` and `reported_gross_room_revenue_cents` null, `audited_room_nights` and `audited_gross_room_revenue_cents` null, `provisional_assessment_cents` 0, `final_assessment_cents` null, `effective_assessment_cents` 0, `granted_adjustment_cents` 0, `delinquency_stage` `NONE`, `penalty_cents` and `interest_cents` 0, all four money buckets at 0, `total_due_cents` 0, `amendment_count` 0, and `filed_at` and `audited_by_user_id` null.

A statement carries **two entirely independent state dimensions on one row**. `filing_status` moves through `NOT_FILED`, `FILED`, `AMENDED`, `AUDITED` and terminal `CERTIFIED`, and is advanced only by filing, amendment and audit activity. `payment_status` moves among `UNPAID`, `PARTIALLY_PAID`, `PAID_IN_FULL`, `DELINQUENT` and `REFUND_DUE`, and is advanced only by remittance, reversal and delinquency events. Neither dimension reads or writes the other: a filing never touches `payment_status`, and a remittance never touches `filing_status`. The payment dimension is the subject of §3.4; the filing dimension is described here.

An operator files its period figures by supplying `reported_room_nights` and `reported_gross_room_revenue_cents`, each an integer that may not be negative. A `DistrictAdministrator` may file on the operator's behalf. Filing requires `filing_status` to be `NOT_FILED`, requires the owning period to be `OPEN`, and requires the logical clock to be at or before the period's `due_date`; there is no lower bound, so a statement may be self-reported at any instant of the open window. A period that is `CLOSED` or `DELINQUENCY_SWEPT`, or a clock already past `due_date`, is refused with `ERR_FILING_WINDOW_CLOSED`. On acceptance the reported figures are stored, `filed_at` is stamped from the logical clock, the statement moves `NOT_FILED → FILED`, the provisional variant of the assessment is computed into `provisional_assessment_cents`, `effective_assessment_cents` and `total_due_cents` are re-derived, and the owning period's `billed_total_cents` is recomputed. The change in the statement's effective assessment also re-evaluates the fiscal year's annual work plan, which may drive an approved plan into `AMENDMENT_PENDING` as described in §3.7.

An amendment replaces the reported figures. The request carries `expected_statement_version` (see §2.7), the replacement `reported_room_nights` and `reported_gross_room_revenue_cents`, and optionally an `amendment_reason`. Amendment is accepted while `filing_status` is `FILED` or `AMENDED`, moving the statement `FILED → AMENDED` on the first revision and `AMENDED → AMENDED` on each subsequent one, so the filing dimension carries a genuine revision cycle. Two preconditions constrain it beyond staleness. The amended `reported_gross_room_revenue_cents` may deviate from the value stored by the *original* filing by at most 25 percent of that original value. And a statement may take at most three revisions, so the self-loop is refused once `amendment_count` has reached 3. A violation of either precondition fails the declared transition and is reported at the state rung as `ERR_INVALID_STATE_TRANSITION`. Amendment is also subject to the same filing window as filing itself and yields `ERR_FILING_WINDOW_CLOSED` outside it. On acceptance the new figures supersede the prior revision, `amendment_count` increases by one, `filed_at` is re-stamped from the logical clock, the provisional variant is recomputed, `effective_assessment_cents` and `total_due_cents` are re-derived, the work plan is re-evaluated, and the statement's `version` increments by one. `payment_status`, `principal_paid_cents`, `penalty_paid_cents` and `interest_paid_cents` are all left untouched.

An `IndependentAuditor` closes the filing dimension in two moves, both requested by naming an `action`. With `action` `AUDIT`, the auditor may substitute `audited_room_nights` and `audited_gross_room_revenue_cents` and may attach an `audit_note`. Auditing is accepted from `FILED` or `AMENDED`, moving the statement to `AUDITED` in either case, and it requires the owning period to have left `OPEN` — the period must be `CLOSED` or `DELINQUENCY_SWEPT`, and an attempt while the period is still `OPEN` is refused with `ERR_PERIOD_NOT_CLOSED` even though the statement's own `filing_status` was perfectly eligible. The audit stores the audited figures, records `audited_by_user_id` from the acting `X-User-ID`, computes the final variant of the assessment into `final_assessment_cents`, sets `effective_assessment_cents` to that figure, recomputes the period's `billed_total_cents`, re-derives `payment_status` including the overpayment reallocation of §2.12, and re-evaluates the fiscal year's work plan. With `action` `CERTIFY`, the statement moves `AUDITED → CERTIFIED` and its amount is locked permanently. Certification requires that no dispute on the statement is still live — no dispute of that statement may be in `SUBMITTED`, `UNDER_REVIEW` or `INFO_REQUESTED` — and it requires an `X-User-ID` different from the stored `audited_by_user_id`, failing with `ERR_SEGREGATION_OF_DUTIES` otherwise. Once `CERTIFIED`, the statement accepts no filing, no amendment and no further audit action, all three being refused with `ERR_STATEMENT_ALREADY_CERTIFIED`.

Closing a period is what unlocks auditing. A `DistrictAdministrator` closes an `OPEN` period once the logical clock has reached `period_end` and at least one statement has been generated for it; the period moves `OPEN → CLOSED` and its `billed_total_cents` and `collected_total_cents` are recomputed from its statements — the former as the sum of `effective_assessment_cents` and the latter as the sum of `principal_paid_cents` over the period's statements. From that moment filings and amendments are refused with `ERR_FILING_WINDOW_CLOSED`.

**How an assessment is calculated.** The assessment computation has two variants that share one arithmetic body and differ only in which five inputs feed it. The **provisional** variant runs at filing and at every amendment, before any audit: it reads the property's `boundary_zone` and `classification` **live, at the moment of the call**, takes `reported_gross_room_revenue_cents` as the revenue basis and `reported_room_nights` as the nights basis, uses an adjustment basis of zero, and writes its output to `provisional_assessment_cents`. The **final** variant runs at audit and is recomputed on every granted dispute adjustment: it reads `zone_at_period_start` and `classification_at_period_start` instead of the live values, takes `audited_gross_room_revenue_cents` as the revenue basis when that is not null and otherwise `reported_gross_room_revenue_cents`, takes `audited_room_nights` as the nights basis when that is not null and otherwise `reported_room_nights`, uses `granted_adjustment_cents` as the adjustment basis, and writes its output to `final_assessment_cents`. Because a mid-period classification or zone revision moves the live values away from the period-start snapshot, the two variants return different integers from byte-identical reported data.

The arithmetic body branches on `assessment_method_at_period_start`, and each branch performs **exactly one rounding step**.

- Under `PCT_OF_ROOM_REVENUE`, the revenue component is the revenue basis multiplied by the zone rate for the zone basis and then by the class multiplier for the class basis, rounded half up to a whole cent. A per-night floor is computed separately as the nights basis multiplied by 150 cents, with no rounding, since it is already whole cents. The gross figure is then the **larger** of the revenue component and the floor. The zone rates are 0.0200 for `ZONE_CORE`, 0.0125 for `ZONE_PERIMETER` and 0.0000 for `OUTSIDE`. The class multipliers are 1.00 for `FULL_SERVICE`, 0.85 for `LIMITED_SERVICE`, 0.90 for `BOUTIQUE` and 1.15 for `SHORT_TERM_RENTAL`.
- Under `PER_OCCUPIED_ROOM_NIGHT`, the gross figure is the nights basis multiplied by 300 cents per occupied room night and then by the same class multiplier for the class basis, rounded half up to a whole cent. No floor applies on this branch.
- Under `TIERED_BY_CLASSIFICATION`, the gross figure is the flat fee for the class basis multiplied by the zone factor for the zone basis, rounded half up to a whole cent. The flat fees are 500000 cents for `FULL_SERVICE`, 300000 cents for `LIMITED_SERVICE`, 350000 cents for `BOUTIQUE` and 150000 cents for `SHORT_TERM_RENTAL`. The zone factors are 1.0000 for `ZONE_CORE`, 0.6250 for `ZONE_PERIMETER` and 0.0000 for `OUTSIDE`. Neither the revenue basis nor the nights basis participates on this branch.

Whichever branch ran, the gross figure is then capped: the capped figure is the **smaller** of the gross figure and a per-period ceiling of 2500000 cents. The assessment output is the capped figure less the adjustment basis, floored at zero so it can never go negative. The order of these two limits is normative — the floor comparison inside the percentage branch runs **before** the ceiling comparison, because reversing them would let a per-night floor above the ceiling escape the ceiling entirely.

### 3.4. Collections: The Remittance Waterfall and the Payment Dimension

An operator pays a statement by submitting a remittance, and a `DistrictAdministrator` may submit one on the operator's behalf. The request carries `amount_cents`, which must be at least 1, `received_on`, the instant the money arrived, which must be at or before the logical clock, and `method`, the instrument used, which must be one of `ACH`, `CHECK`, `WIRE` or `CARD`. A statement must have been filed before it can be paid: a remittance against a statement whose `filing_status` is still `NOT_FILED` is refused at the state rung with `ERR_INVALID_STATE_TRANSITION`. Overpayment is tolerated but bounded — `amount_cents` may exceed the statement's `total_due_cents` by at most 500000 cents, and a payment exceeding that tolerance is refused with `ERR_REMITTANCE_EXCEEDS_TOTAL_DUE` rather than banked. Each accepted remittance creates its own record with `status` `APPLIED`, `reversed_on` and `reversal_reason` null, and `version` 1. Both the applied and the reversed history of a statement remains readable, and a single remittance can be read on its own to see exactly how its money was split.

**The waterfall.** The allocation of a payment is a strict cascade over three debts and one overflow, and each bucket is filled to its outstanding balance before a single cent reaches the next. Begin with a working remainder equal to `amount_cents`.

1. The interest outstanding is `interest_cents` less `interest_paid_cents`. The amount applied to interest is the smaller of the remainder and that outstanding balance treated as zero if it is negative. Reduce the remainder by that amount and record it as `applied_to_interest_cents`.
2. The penalty outstanding is `penalty_cents` less `penalty_paid_cents`. The amount applied to penalty is the smaller of the now-reduced remainder and that outstanding balance treated as zero if negative. Reduce the remainder and record `applied_to_penalty_cents`.
3. The principal outstanding is `effective_assessment_cents` less `principal_paid_cents`. The amount applied to principal is the smaller of the remainder and that outstanding balance treated as zero if negative. Reduce the remainder and record `applied_to_principal_cents`.
4. Whatever remains — never discarded — is recorded as `applied_to_credit_cents`.

The statement's `interest_paid_cents`, `penalty_paid_cents`, `principal_paid_cents` and `credit_balance_cents` are then each increased by the corresponding allocation, and the district's `collected_to_date_cents` together with the period's `collected_total_cents` are increased by the full `amount_cents`. The four allocations always sum to exactly `amount_cents`. **No rounding occurs anywhere in the waterfall**, which is precisely what makes it exactly reversible. Only records whose `status` is `APPLIED` contribute to the statement's buckets.

**Reversal.** A `DistrictAdministrator` unwinds a payment — a returned bank transfer, say — by naming the `remittance_id` and supplying a `reversal_reason`. The named record must belong to the statement named in the path, must still be `APPLIED`, and its statement's `filing_status` must not be `CERTIFIED`; a second attempt on the same record is refused with `ERR_REMITTANCE_ALREADY_REVERSED`, and a reversal against a certified statement is refused at the state rung with `ERR_INVALID_STATE_TRANSITION`. The record moves `APPLIED → REVERSED`, `reversed_on` is stamped from the logical clock, and `reversal_reason` is stored. The reversal then **subtracts exactly the four per-bucket amounts recorded on that record** — it does not re-run the waterfall backwards — so `interest_paid_cents`, `penalty_paid_cents`, `principal_paid_cents` and `credit_balance_cents` are each reduced by that record's own allocation. The district's `collected_to_date_cents` and the period's `collected_total_cents` are reduced by `amount_cents`. Because subtraction is per-record rather than recomputed, every derived total returns to exactly its pre-payment value and the conserved identity of §2.12 holds no matter what order payments and reversals arrive in.

**How payment status is derived.** `payment_status` is never set directly by a caller. It is recomputed from scratch at the end of every call that changes any of the four money buckets, the effective assessment or the delinquency stage — that is, on remittances, reversals, filings, amendments, audit and certification, dispute resolutions, and the delinquency sweep. The derivation reads one statement row only and aggregates nothing across statements. It proceeds in three steps.

First, the effective assessment is fixed: `effective_assessment_cents` becomes `final_assessment_cents` when that is not null, and otherwise becomes `provisional_assessment_cents` less `granted_adjustment_cents`, floored at zero.

Second, the **reallocation step** runs. A downward revision can leave `principal_paid_cents` above the new effective assessment. The overpaid amount is `principal_paid_cents` less `effective_assessment_cents`; when that is greater than zero, the excess is added to `credit_balance_cents` and `principal_paid_cents` is reduced to equal `effective_assessment_cents`. The cents migrate rather than vanish, which is what keeps the conserved identity true after a dispute is granted.

Third, `total_due_cents` becomes the sum of `effective_assessment_cents`, `penalty_cents` and `interest_cents`, less the sum of `principal_paid_cents`, `penalty_paid_cents` and `interest_paid_cents`, floored at zero. `payment_status` is then read off the following ladder, evaluated top to bottom, stopping at the first true branch:

1. `REFUND_DUE` when `credit_balance_cents` is greater than zero **and** `total_due_cents` is zero.
2. `PAID_IN_FULL` when `total_due_cents` is zero.
3. `DELINQUENT` when `delinquency_stage` is not `NONE`.
4. `PARTIALLY_PAID` when the sum of `principal_paid_cents`, `penalty_paid_cents` and `interest_paid_cents` is greater than zero.
5. `UNPAID` otherwise.

The two orderings inside this ladder are normative: `REFUND_DUE` is tested before `PAID_IN_FULL`, so a fully retired statement holding credit reports the refund rather than the settlement; and `DELINQUENT` is tested before `PARTIALLY_PAID`, so a part-paid statement that has been swept keeps reporting its enforcement state rather than reverting to a merely part-paid one.

**The reachable payment transitions.** A first payment that leaves principal partly outstanding moves the statement from `UNPAID` to `PARTIALLY_PAID`; the same call from `DELINQUENT` is equally permitted. A payment that exactly retires `total_due_cents` moves it to `PAID_IN_FULL` with `credit_balance_cents` at zero, and is accepted from `UNPAID`, `PARTIALLY_PAID` or `DELINQUENT` alike; from `DELINQUENT` the waterfall necessarily fills interest, then penalty, then principal on the way there, and `delinquency_stage` is deliberately **left at its swept value** — payment in full does not erase the enforcement record. A payment that overflows all three buckets within the tolerance moves the statement to `REFUND_DUE`, the overflow landing simultaneously in `credit_balance_cents` and in that record's `applied_to_credit_cents`.

Reversals run the same set of moves in the opposite direction, and the two sibling pairs are equally supported. Unwinding the only applied payment of a fully paid statement returns it to `UNPAID`; unwinding the only applied payment of a part-paid statement — where no other payment of that statement is still `APPLIED`, so every bucket empties to zero — likewise returns it to `UNPAID`. Without that second move a partially paid statement could never be unwound to its filed state. Unwinding one of several applied payments on a fully paid statement, so that a positive `total_due_cents` reappears while earlier payments remain, moves it from `PAID_IN_FULL` to `PARTIALLY_PAID`. Unwinding an overpaying payment while earlier payments still retire the whole balance moves the statement from `REFUND_DUE` to `PAID_IN_FULL`, the credit alone disappearing; unwinding a payment that had filled both principal and credit — one whose `applied_to_credit_cents` and `applied_to_principal_cents` are both greater than zero — moves it from `REFUND_DUE` to `PARTIALLY_PAID`, because removing the credit also reopens a positive balance.

Two moves reach the payment dimension from outside collections entirely. A dispute resolved so as to abate the whole assessment, or an audit that revises the basis down to nothing owed, moves an `UNPAID` statement straight to `PAID_IN_FULL` when the re-derived `effective_assessment_cents` is zero and no penalty or interest has been charged: **no remittance record is created**, since a statement may be retired by abatement rather than by payment, and `REFUND_DUE` is unreachable on this path precisely because `credit_balance_cents` stays at zero when nothing was ever paid. Conversely, an audit or a granted adjustment that lowers `effective_assessment_cents` below the already-collected `principal_paid_cents` moves a `PAID_IN_FULL` statement to `REFUND_DUE`: the final variant of the assessment is recomputed, the reallocation step migrates the now-excess principal into `credit_balance_cents` so that `principal_paid_cents` equals `effective_assessment_cents` and `credit_balance_cents` equals the excess, `total_due_cents` re-derives to zero, and the district's `collected_to_date_cents` is untouched because cents moved between buckets of one statement rather than out of the district. Neither of these two moves touches `filing_status`, and no payment transition anywhere touches it either.

The delinquency moves belong to §3.5: a statement in `UNPAID` or `PARTIALLY_PAID` with `total_due_cents` greater than zero is driven to `DELINQUENT` by the sweep.

### 3.5. Delinquency Enforcement and Operator Compliance Standing

Enforcement is a single administrative act performed once per assessment period, and it is the head of the longest cascade in the system. A `DistrictAdministrator` sweeps a period for delinquency; the call takes no body and returns the period. Two preconditions gate it. The period's `status` must be `CLOSED`, so an open period can never be swept and a period already `DELINQUENCY_SWEPT` can never be swept twice. And the logical clock must be **strictly past** the grace deadline, which is the period's `due_date` advanced by `grace_days` whole days: a clock landing exactly on the grace deadline is not yet delinquent and the sweep is refused at the state rung with `ERR_INVALID_STATE_TRANSITION`. On success the period moves `CLOSED → DELINQUENCY_SWEPT`, which is terminal, and its `version` increments by one.

The sweep considers only the statements of that period whose `payment_status` is `UNPAID` or `PARTIALLY_PAID` and whose `total_due_cents` is greater than zero. Statements that are `PAID_IN_FULL`, that are `REFUND_DUE`, or that already stand `DELINQUENT` are skipped and receive no second set of charges. The selected statements are processed **in `created_at` ascending order**, and that order is observable because it determines the sequence in which strikes accumulate against a property.

For each swept statement the charges are computed as follows. The number of days late is the count of whole days from the grace deadline to the logical clock, and it is at least 1 whenever the statement is swept at all, since the clock is strictly past the deadline. The outstanding amount is `effective_assessment_cents` less `principal_paid_cents`, floored at zero — note that it is the *principal* bucket alone that offsets it, so unpaid penalty or interest from an earlier period plays no part. `penalty_cents` becomes the outstanding amount multiplied by a penalty rate of 0.10, rounded half up to a whole cent. `interest_cents` becomes the outstanding amount multiplied by a daily interest rate of 0.0005 and then by the number of days late, rounded half up to a whole cent. `delinquency_stage`, which begins at `NONE`, becomes `LIEN_REFERRED` when either the outstanding amount is at least 1000000 cents or the owning property's `compliance_standing` **already stood `SUSPENDED` when the sweep began, before this sweep's own strike increment**; otherwise it becomes `NOTICE`. A property that reaches `SUSPENDED` because of this very sweep is therefore staged `NOTICE`, not `LIEN_REFERRED`. The two charge figures are each rounded once per statement and only then accumulated into the district's `delinquent_charges_cents`; summing outstanding amounts across the period first and applying the rates to that aggregate is incorrect, because it yields a different total whenever any per-statement product lands on a half cent.

The cascade has four hops, and each hop is caused by the mutation the previous hop wrote rather than by the sweep call itself.

- **Hop one.** Each selected statement's `payment_status` flips to `DELINQUENT`.
- **Hop two.** That flip stamps the statement with its `delinquency_stage`, its `penalty_cents` and its `interest_cents` as computed above, re-derives `total_due_cents`, and adds the two per-statement rounded charges into the district's `delinquent_charges_cents`.
- **Hop three.** The delinquency stamp on the statement increments the owning property's `delinquency_strike_count` by one and re-derives its `compliance_standing` from the new count: zero strikes is `GOOD`, exactly one strike is `WATCH`, and two or more strikes is `SUSPENDED`.
- **Hop four.** A property that has *just reached* `compliance_standing` `SUSPENDED` as a result of hop three has every one of its `VALID` petition signatures on drives still `OPEN` moved to `DISQUALIFIED` with `disqualification_reason` `COMPLIANCE_SUSPENDED`, and each affected drive recomputes `signed_basis_cents`, `valid_signature_count` and `weighted_support_pct`. A suspended operator's political support for a district is withdrawn as a direct consequence of its arrears, four hops away from the call that caused it.

Two properties of this design are deliberate. A statement's `delinquency_stage` is never cleared by subsequent payment — paying in full moves `payment_status` to `PAID_IN_FULL` while the enforcement record stands — and `delinquency_strike_count` never decreases, so `compliance_standing` is monotone once earned.

### 3.6. Disputes over Assessment and Exemption

An operator who believes a statement is wrong files a dispute, and a `DistrictAdministrator` may file one on the operator's behalf. The request names the `assessment_statement_id`, a `dispute_type` that must be one of `CALCULATION_ERROR` for an arithmetic or basis objection, `EXEMPT_PROPERTY` for a claim that the property should not be assessed at all, or `BOUNDARY_MISCLASSIFICATION` for an objection to the zone determination; a `claimed_adjustment_cents` of at least 1, being the reduction asked for; and optionally a free-text `dispute_note`. The dispute is created with `status` `SUBMITTED`, `filed_on` stamped from the logical clock, `granted_adjustment_cents` 0, `appeal_count` 0, and `resolved_by_user_id` and `resolution_note` null. Its `lodging_business_id` is **copied from the referenced statement** and is never supplied by the client, so a dispute can never be attributed to a property other than the one billed. At most one non-terminal dispute may exist per statement-and-ground pair: a second `CALCULATION_ERROR` dispute on a statement that already has one live is refused with `ERR_DISPUTE_ALREADY_OPEN`, while an `EXEMPT_PROPERTY` dispute on the same statement is admissible alongside it. Disputes are readable per statement and per property, each with a `status` filter, and individually.

Proceedings advance a dispute by naming an `action`, which must be one of `OPEN_REVIEW`, `REQUEST_INFO`, `SUBMIT_RESPONSE`, `APPEAL` or `WITHDRAW`, with an optional `note`. The five actions are split between two roles, and the split is enforced as an authorization decision rather than a state check: `OPEN_REVIEW` and `REQUEST_INFO` are reserved to the `HearingOfficer`, while `SUBMIT_RESPONSE`, `APPEAL` and `WITHDRAW` are reserved to the owning `LodgingOperator`, whose `X-User-ID` must equal the dispute's `lodging_business_id`.

- `OPEN_REVIEW` moves a `SUBMITTED` dispute to `UNDER_REVIEW` and opens the hearing.
- `REQUEST_INFO` moves an `UNDER_REVIEW` dispute to `INFO_REQUESTED`, and `SUBMIT_RESPONSE` moves it back from `INFO_REQUESTED` to `UNDER_REVIEW`. This information cycle **may repeat without limit**; there is no cap on how many times a hearing officer may ask for more material.
- `APPEAL` moves a `RESOLVED_UPHELD` dispute back to `UNDER_REVIEW`, increments `appeal_count` by one and clears `resolved_by_user_id` back to null. The appeal cycle is one-shot: at most one appeal may be taken, so the action is refused with `ERR_APPEAL_LIMIT_EXCEEDED` once `appeal_count` has reached 1.
- `WITHDRAW` moves a `SUBMITTED` dispute to terminal `WITHDRAWN`. A dispute may be abandoned **only before the hearing officer opens review**; once review is open the matter runs to a resolution, and a withdrawal attempt from `UNDER_REVIEW`, `INFO_REQUESTED` or either resolved state is refused at the state rung.

A `HearingOfficer` alone resolves a dispute, and only from `UNDER_REVIEW`. The request carries an `outcome`, and optionally `granted_adjustment_cents`, an `exempt_status_granted` and a `resolution_note`. Both outcomes record `resolved_by_user_id` from the acting `X-User-ID` and store the `resolution_note` — but only once the outcome is actually reached. Neither field is written on the way in, so a resolution request that is refused by any rule, including the three bounds on the granted figure described below, leaves the dispute exactly as it stood: its `status`, `resolved_by_user_id`, `resolution_note` and `granted_adjustment_cents` are unchanged, and its `updated_at` and `version` do not move. In particular a refused `ADJUSTED` attempt must not leave the hearing officer's identifier stranded on a still-`UNDER_REVIEW` dispute.

An outcome of `UPHELD` moves the dispute to `RESOLVED_UPHELD`. `granted_adjustment_cents` stays 0, and the statement's amounts, its `payment_status` and the district's work plan forecast are all left untouched. `RESOLVED_UPHELD` is not terminal, precisely because it remains appealable once.

An outcome of `ADJUSTED` moves the dispute to terminal `RESOLVED_ADJUSTED` and is the head of a three-hop cascade. Three bounds govern the granted figure: it must be at least 1, it must not exceed the dispute's own `claimed_adjustment_cents`, and it must not exceed the statement's current `effective_assessment_cents` — the third bound failing with `ERR_ADJUSTMENT_EXCEEDS_ASSESSMENT`. Where the `dispute_type` is `EXEMPT_PROPERTY`, an `exempt_status_granted` other than `NONE` must additionally be supplied. The cascade then runs, each hop caused by the mutation the previous hop wrote:

- **Hop one.** The statement's `granted_adjustment_cents` increases by the granted figure, `final_assessment_cents` is recomputed by the final variant of the assessment when it is already non-null, `effective_assessment_cents` is re-derived, and `payment_status` is re-derived — becoming `REFUND_DUE` when `principal_paid_cents` now exceeds the reduced effective assessment, with the excess migrated into `credit_balance_cents` by the reallocation step of §3.4.
- **Hop two.** That change in the statement's `effective_assessment_cents` itself forces the district's annual work plan for its `current_fiscal_year` to recompute `assessment_revenue_forecast_cents` and `funding_ratio`. An `APPROVED` plan whose recomputed `funding_ratio` falls below 0.9000 moves `APPROVED → AMENDMENT_PENDING`.
- **Hop three.** That `AMENDMENT_PENDING` flip itself moves every `PLANNED` marketing program of the plan to `SUSPENDED_PENDING_AMENDMENT` and sets `spend_frozen` to true on every `RUNNING` marketing program of the plan.

Separately from the three hops, an `ADJUSTED` dispute whose `dispute_type` is `EXEMPT_PROPERTY` additionally moves the disputing property `ASSESSABLE → EXEMPT` and sets its `exempt_status` to the supplied `exempt_status_granted`, which removes it from every future assessable roll. Because a live dispute blocks certification (§3.3), and because `RESOLVED_ADJUSTED`, `RESOLVED_UPHELD` and `WITHDRAWN` are all outside the blocking set, a statement becomes certifiable again the moment its last dispute is decided, withdrawn or upheld — even though an upheld dispute may still be appealed afterwards.

### 3.7. The Annual Budget and Work Plan

A `DistrictAdministrator` drafts the district's annual budget by naming the `district_id`, the `fiscal_year` the budget covers — an integer between 2020 and 2050 inclusive that must be unique per district across every plan whose `status` is not `CLOSED`, so a closed year may be superseded by a fresh plan but two live plans may not claim the same year — and the `expenditure_lines`. That array must be non-empty, each element being an object with a `category`, an `amount_cents` of at least 1 and a `narrative`. `category` must be one of `SALES_AND_MARKETING`, `DESTINATION_EVENTS`, `ADMINISTRATION`, `CONTINGENCY_RESERVE` or `CAPITAL_IMPROVEMENT`, and **at most one line per category** may appear, so each category total is that single line's amount.

Creation computes `total_budget_cents` as the sum of the line amounts, then the five per-category rollups `administration_cents`, `contingency_reserve_cents`, `sales_and_marketing_cents`, `destination_events_cents` and `capital_improvement_cents`, each being the amount of the corresponding line or 0 when that category is absent. `assessment_revenue_forecast_cents` and `funding_ratio` are also computed at creation. `committed_program_cents` starts at 0 and thereafter tracks the sum of `committed_cents` over the plan's marketing programs whose `status` is not `CANCELLED`. `revision_count` starts at 0, and `sponsor_user_id`, `approver_user_id` and `approved_at` all start null. The plan is created in `DRAFT`, and **a `DRAFT` plan may hold any category mix at all**: none of the share caps is applied at draft. That is deliberate, because it is what makes the sponsor-versus-approver identity check reachable ahead of the cap checks at approval time.

The revenue forecast is the propagated quantity that ties the budget to collections. `assessment_revenue_forecast_cents` is the sum of `effective_assessment_cents` over every assessment statement belonging to a period of the plan's district whose `period_label` begins with the characters `FY` followed by the plan's `fiscal_year`, counting only statements whose `filing_status` is `FILED`, `AMENDED`, `AUDITED` or `CERTIFIED` — a statement still `NOT_FILED` contributes nothing — and counting them **regardless of `payment_status`**, because the forecast measures assessed revenue rather than cash collected. `funding_ratio` is then 0.0000 when `total_budget_cents` is 0, and otherwise the forecast divided by `total_budget_cents`, rounded half up to four decimal places. The floor the district must meet is 0.9000.

The board moves a plan through its lifecycle by naming an `action` — one of `SPONSOR`, `APPROVE`, `RETURN` or `CLOSE` — with an optional `note`. Only a `BoardMember` may act.

- `SPONSOR` moves a `DRAFT` plan to `BOARD_REVIEW`, requires `expenditure_lines` to be non-empty, and records `sponsor_user_id` from the acting `X-User-ID`.
- `RETURN` moves a `BOARD_REVIEW` plan back to `DRAFT`, clears `sponsor_user_id` to null and increments `revision_count` by one. This closes the review cycle `DRAFT → BOARD_REVIEW → DRAFT`, and a returned plan may be sponsored again by any board member, including the one who sponsored it before.
- `APPROVE` moves a `BOARD_REVIEW` plan to `APPROVED`, records `approver_user_id` from the acting `X-User-ID` and stamps `approved_at` from the logical clock, then computes `assessment_revenue_forecast_cents` and `funding_ratio`.
- `CLOSE` moves an `APPROVED` plan to terminal `CLOSED`, and requires that **every** marketing program of the plan already stands `CLOSED` or `CANCELLED`; a plan with a single `PLANNED`, `RUNNING` or `SUSPENDED_PENDING_AMENDMENT` program cannot be retired, so no live program is ever orphaned by closure.

**Approval is where the fiscal discipline bites.** The checks run in a fixed order. First, the acting `X-User-ID` must differ from the stored `sponsor_user_id`, and equality is refused with `ERR_SEGREGATION_OF_DUTIES`; this identity check is evaluated **before any category cap**, so a board member who tries to approve a plan he himself sponsored is told about the conflict of interest even when the budget mix is also non-compliant. Then the compliance tests run against the plan's own lines:

- The administration cap is `total_budget_cents` multiplied by 0.15, rounded half up to a whole cent. The `ADMINISTRATION` amount must be at or below that cap, and exceeding it yields `ERR_ADMIN_SHARE_EXCEEDED`.
- The contingency cap is `total_budget_cents` multiplied by 0.10, rounded half up. The `CONTINGENCY_RESERVE` amount must be at or below it, and exceeding it yields `ERR_CONTINGENCY_SHARE_EXCEEDED`.
- The marketing floor is `total_budget_cents` multiplied by 0.60, rounded half up. The `SALES_AND_MARKETING` amount must be at or **above** it, and falling short yields `ERR_MARKETING_SHARE_BELOW_MINIMUM`. A plan with no marketing line at all therefore fails this test whenever its budget is non-zero.
- A `CAPITAL_IMPROVEMENT` line is permitted only when the district's `assessment_method` is `PCT_OF_ROOM_REVENUE`; under either other method its presence yields `ERR_EXPENDITURE_CATEGORY_NOT_PERMITTED`.
- The lodging tax match ceiling is `total_budget_cents` multiplied by 0.50, rounded half up. The district's `lodging_tax_match_committed_cents` must be at or below the **smaller** of that ceiling and the district's `lodging_tax_match_pool_cents`, and breaching either arm yields `ERR_LODGING_TAX_MATCH_CAP_EXCEEDED`.
- Finally the recomputed `funding_ratio` must be at least 0.9000, and falling short yields `ERR_FUNDING_RATIO_BELOW_MINIMUM`. A district cannot adopt a budget its assessments do not substantially fund.

An approved plan is not frozen. Any change to the effective assessment of any statement in the plan's fiscal year — a filing, an amendment, an audit or a granted dispute adjustment — forces a re-evaluation of `assessment_revenue_forecast_cents` and `funding_ratio`. Where the plan's `fiscal_year` equals the district's `current_fiscal_year` and the recomputed `funding_ratio` falls below 0.9000, the plan moves `APPROVED → AMENDMENT_PENDING` without any caller asking for it, and that flip in turn suspends the plan's programs as described in §3.6 and §3.8. The recomputation reaches a fixed point because it touches only the plan and its programs and never writes back to any statement.

Amendment is how the district recovers. A `DistrictAdministrator` or a `BoardMember` submits `expected_work_plan_version` (see §2.7), a replacement `expenditure_lines` array and an optional `amendment_reason`. The plan's `status` must be `APPROVED` or `AMENDMENT_PENDING`. The lines are **replaced wholesale**, every derived category total and `total_budget_cents` is recomputed, and `revision_count` increases by one. Two ceilings constrain an amendment beyond the caps that approval already imposes, and both report `ERR_AMENDMENT_VARIANCE_EXCEEDED`: the absolute difference between the proposed total and the plan's currently stored `total_budget_cents` must be at or below the variance allowance, which is that stored total multiplied by 0.25 and rounded half up; and `revision_count` must still be below 3 when the submission arrives. Every compliance test listed above is then re-enforced against the revised lines, including the funding ratio floor. On success the plan's `status` becomes `APPROVED` — which is how an `AMENDMENT_PENDING` plan returns to good standing once its ratio again reaches 0.9000 — its `version` increments by one, every marketing program of the plan standing `SUSPENDED_PENDING_AMENDMENT` returns to `PLANNED`, and every `RUNNING` program has `spend_frozen` set back to false. This closes the amendment cycle `APPROVED → AMENDMENT_PENDING → APPROVED`.

### 3.8. Marketing Programs, Room-Night Claims and Performance Measurement

A `DistrictAdministrator` or a `DmoLiaison` creates a program funded by an approved plan. The request names the `annual_work_plan_id`, a non-blank `name` of 1 to 120 characters, a `channel` that must be one of `PAID_SEARCH`, `TRADE_SHOW`, `GROUP_SALES`, `OTA_CAMPAIGN` or `INFLUENCER`, a `committed_cents` of at least 1, an inclusive `booking_window_start` and an exclusive `booking_window_end` that must fall strictly after it, and optionally `lodging_tax_matched_cents`, the portion of the commitment drawn from the public lodging tax pool, which defaults to 0 and may not be negative. The funding plan's `status` must be `APPROVED`; a `DRAFT`, `BOARD_REVIEW`, `AMENDMENT_PENDING` or `CLOSED` plan funds nothing and creation is refused with `ERR_WORK_PLAN_NOT_APPROVED`. Two fiscal ceilings are then enforced: the sum of `committed_cents` over the plan's non-cancelled programs must not exceed the plan's `sales_and_marketing_cents`, exceeding it with `ERR_PROGRAM_BUDGET_EXCEEDED`; and the district's `lodging_tax_match_committed_cents` is increased by the requested match and re-checked against both the district's `lodging_tax_match_pool_cents` and the 50 percent ceiling of §3.7, exceeding either with `ERR_LODGING_TAX_MATCH_CAP_EXCEEDED` and exhausting the pool with `ERR_LODGING_TAX_MATCH_EXHAUSTED`. The program is created in `PLANNED` with `spend_frozen` false, `verified_room_nights` 0, `gross_cost_per_room_night_cents`, `efficiency_tier` and `net_cost_per_room_night_cents` all null, `dmo_cost_share_cents` and `net_district_cost_cents` 0, `performance_index` 0.0000, `performance_flag` `NOT_MEASURED`, and `launched_at` and `closed_at` null. Programs are readable per plan, filterable by `status` and `channel`, and individually.

Launching puts a planned program into market and may be requested with an optional `launch_note`. Four guards apply beyond the program's own `PLANNED` state, and they are independent of one another: the funding plan must still be `APPROVED`, the owning district's `status` must be `ACTIVE`, the district's `dmo_agreement_status` must be `EXECUTED` — a program in a perfectly valid `PLANNED` state still cannot go to market under a merely `PROPOSED` or `TERMINATED` agreement, which is refused with `ERR_DMO_AGREEMENT_NOT_EXECUTED` — and the logical clock must lie inside the half-open booking window, at or after `booking_window_start` and strictly before `booking_window_end`. The program budget is re-checked against the plan's marketing line at launch as well, so a program that was affordable at creation but has since been crowded out is refused with `ERR_PROGRAM_BUDGET_EXCEEDED`. On success the program moves `PLANNED → RUNNING` and `launched_at` is stamped from the logical clock.

An operator, or a `DmoLiaison` acting for one, claims the room nights a running program generated. The request names the `lodging_business_id`, an inclusive `stay_start`, an exclusive `stay_end` that must fall strictly after it, a `room_nights` of at least 1, and optionally an `attribution_method` of either `DIRECT_PICKUP` or `LOOKBACK_WINDOW`, defaulting to `DIRECT_PICKUP`. Three business rules govern a claim.

- The program must be `RUNNING` and the claimed stay must fall **entirely inside** the program's half-open booking window; a stay extending one hour past `booking_window_end`, or a claim against a program not yet launched, is refused with `ERR_CLAIM_OUTSIDE_BOOKING_WINDOW`.
- Stay intervals of the same program-and-property pair, treated as half-open, must not overlap. An interval starting exactly where another ends is accepted. Only claims whose `status` is `SUBMITTED` or `VERIFIED` occupy an interval; a `REJECTED` claim frees it for a new claim over the same nights. An overlap is refused with `ERR_CLAIM_STAY_OVERLAP`.
- `room_nights` must not exceed the property's `room_count` multiplied by the number of whole nights in the stay interval, since a property cannot sell more room nights than it has rooms. A claim beyond that physical capacity is refused with `ERR_CLAIM_EXCEEDS_CAPACITY`.

A claim is created in `SUBMITTED` with its `marketing_program_id` taken from the path, `verified_room_nights` null, `rejection_reason` `NONE` and `verified_by_user_id` null. Claims are readable per program — filterable by `status` and `lodging_business_id` — per property, and individually.

Verification is the destination marketing organization's audit of a claim and is performed by a `DmoLiaison` or a `DistrictAdministrator` on a claim still `SUBMITTED`. The request carries a `decision` of either `ALLOW` or `REJECT`, optionally `verified_room_nights` and optionally a `rejection_reason` drawn from `NONE`, `UNVERIFIABLE`, `DUPLICATE_STAY` and `OUTSIDE_ATTRIBUTION_WINDOW`. `ALLOW` moves the claim `SUBMITTED → VERIFIED`, storing `verified_room_nights` — which defaults to the claim's full `room_nights` when omitted, must be at least 1, and may never exceed `room_nights`, an excess being refused with `ERR_CLAIM_EXCEEDS_CAPACITY` — records `verified_by_user_id` from the acting `X-User-ID`, and recomputes the program's `verified_room_nights` as the sum over its `VERIFIED` claims only. `REJECT` moves the claim `SUBMITTED → REJECTED`, requires a `rejection_reason` other than `NONE`, leaves the claim's `verified_room_nights` null, restores the program's `verified_room_nights` to exactly its pre-claim value, and frees the stay interval. Both target states are terminal, so a decision is final. `REJECTED` nights are excluded from the performance numerator and are never restored.

Closure publishes the measurement. A `DistrictAdministrator` or a `DmoLiaison` closes a `RUNNING` program with an optional `closure_note`. Two independent refusals guard it. The program's `spend_frozen` must be false — a running program frozen because its funding plan fell into `AMENDMENT_PENDING` may not be closed, since performance may not be published against a budget that is no longer funded, and because the program's `status` is still `RUNNING` the generic state check does not fire and `ERR_PROGRAM_SPEND_FROZEN` is the only possible outcome. And no claim of the program may still be `SUBMITTED`, refused with `ERR_CLAIMS_PENDING_VERIFICATION`, because measurement reads verified nights only and an unverified claim would silently drop out of the published index. On success the program moves `RUNNING → CLOSED`, `closed_at` is stamped from the logical clock, and the performance figures are written.

**How performance is measured.** The measurement is deliberately split into two passes, and the split exists to break what would otherwise be a circular dependency: the DMO's cost share depends on the efficiency tier, the tier depends on cost per room night, and cost per room night depends on the share. The order below breaks the cycle by fixing the tier from the **gross** figure only.

*Pass one — the gross basis.* The verified night count is the sum of `verified_room_nights` over the program's claims whose `status` is `VERIFIED`. When that count is zero, `gross_cost_per_room_night_cents` is null and `efficiency_tier` is `TIER_UNPRODUCTIVE`. Otherwise `gross_cost_per_room_night_cents` is `committed_cents` divided by the verified night count, rounded half up to a whole cent, and the tier is read off that gross figure: `TIER_EFFICIENT` at 1500 cents or below, otherwise `TIER_STANDARD` at 3000 cents or below, otherwise `TIER_MARGINAL` at 6000 cents or below, otherwise `TIER_UNPRODUCTIVE`. **The tier selected in this pass is never reselected.**

*Pass two — the net basis.* Using the tier fixed in pass one, `dmo_cost_share_cents` is `committed_cents` multiplied by the tier's share percentage, rounded half up to a whole cent, where the percentages are 0.40 for `TIER_EFFICIENT`, 0.25 for `TIER_STANDARD`, 0.10 for `TIER_MARGINAL` and 0.00 for `TIER_UNPRODUCTIVE`. `net_district_cost_cents` is `committed_cents` less `dmo_cost_share_cents`. When the verified night count is zero, `net_cost_per_room_night_cents` is null and `performance_index` is 0.0000. Otherwise `net_cost_per_room_night_cents` is `net_district_cost_cents` divided by the verified night count, rounded half up to a whole cent, and `performance_index` is a benchmark of 2500 cents divided by `net_cost_per_room_night_cents`, rounded half up to four decimal places. Re-tiering on the net figure is forbidden and would change the published index.

`performance_flag` is then `UNDERPERFORMING` when the verified night count is zero; otherwise `MEETS_BENCHMARK` when `performance_index` is at least 1.0000, otherwise `BELOW_BENCHMARK` when it is at least 0.7500, otherwise `UNDERPERFORMING`. A program that closes with no verified nights therefore publishes null costs per room night, `TIER_UNPRODUCTIVE`, an index of 0.0000 and the `UNDERPERFORMING` flag.

Two moves reach a program from outside its own workflow. The funding plan entering `AMENDMENT_PENDING` moves every `PLANNED` program of that plan to `SUSPENDED_PENDING_AMENDMENT` and freezes spend on every `RUNNING` one; an accepted amendment restoring the plan to `APPROVED` returns those suspended programs to `PLANNED` and clears `spend_frozen`, closing the suspension cycle `PLANNED → SUSPENDED_PENDING_AMENDMENT → PLANNED`. And the district's disestablishment moves every program that is `PLANNED`, `RUNNING` or `SUSPENDED_PENDING_AMENDMENT` to terminal `CANCELLED` with `spend_frozen` cleared to false, after which the plan's `committed_program_cents` is recomputed excluding the cancelled program.

### 3.9. Transparency Obligations and the Public Record

A district's authority to assess is conditional on publishing what it does with the money, so transparency artifacts are first-class records with their own lifecycle. A `DistrictAdministrator` schedules one by naming the `district_id`, a `record_type` that must be one of `PUBLIC_MEETING`, `ANNUAL_REPORT` or `FINANCIAL_AUDIT`, the `fiscal_year` the artifact covers as an integer between 2020 and 2050 inclusive, a `scheduled_for` instant at which the meeting is held or the artifact is targeted, and a `required_by` instant that is the statutory deadline. The record is created in `SCHEDULED` with `noticed_on`, `completed_on`, `published_on` and `document_reference` all null, and with `engaged_by_user_id` taken from the acting `X-User-ID` — the identity that will later be barred from advancing a financial audit. One constraint applies at creation: two `PUBLIC_MEETING` records of the same district must have `scheduled_for` instants at least 10 whole days apart. A separation of exactly 10 days is accepted and 9 days is rejected with `ERR_MEETING_SEPARATION_VIOLATION`. The rule is scoped to public meetings only, so an annual report may be targeted for the same day as a meeting. Transparency records are readable by anyone with no headers at all, individually and per district with `record_type`, `status` and `fiscal_year` filters, because publication is the whole point of the record.

A record is advanced by naming a `to_status`, optionally with a `document_reference`. Only a `DistrictAdministrator` may advance one, and the three forward steps run in order.

- `NOTICED` is accepted from `SCHEDULED` and requires the logical clock to be at least 14 whole days before `scheduled_for`. Exactly 14 whole days ahead is accepted and 13 is not; a notice posted any nearer to the meeting is refused with `ERR_MEETING_NOTICE_TOO_LATE`, since a late notice is no notice. On success `noticed_on` is stamped from the logical clock.
- `COMPLETED` is accepted from `NOTICED` and requires the logical clock to be at or after `scheduled_for`, so a meeting cannot be recorded as held before its own start. On success `completed_on` is stamped from the logical clock.
- `PUBLISHED` is accepted from `COMPLETED` and requires a `document_reference` that is supplied and non-blank. On success `published_on` is stamped from the logical clock, `document_reference` is stored, and the district's `transparency_standing` is re-derived: it returns to `COMPLIANT` only when no `ANNUAL_REPORT` and no `FINANCIAL_AUDIT` record of the district remains `OVERDUE`, and stays `DEFICIENT` otherwise.

On a record whose `record_type` is `FINANCIAL_AUDIT`, **both** the `COMPLETED` and the `PUBLISHED` advances additionally require the acting `X-User-ID` to differ from the stored `engaged_by_user_id`, and equality is refused with `ERR_SEGREGATION_OF_DUTIES`. The administrator who engaged the audit may neither record its completion nor put its opinion on the public record. `PUBLIC_MEETING` and `ANNUAL_REPORT` records carry no such restriction.

The transparency dimension is the one place where merely advancing the logical clock mutates business state, and it produces a three-hop cascade. Setting the clock past a record's `required_by` while its `status` is `SCHEDULED` or `NOTICED` moves that record to terminal `OVERDUE`. That `OVERDUE` stamp itself sets the district's `transparency_standing` to `DEFICIENT` when the record's `record_type` is `ANNUAL_REPORT` or `FINANCIAL_AUDIT` — a missed public meeting is a lapse but not a disqualifying one. And that `DEFICIENT` standing in turn blocks the district's advance from `ACTIVE` to `RENEWAL_PENDING`, so a missed reporting deadline forecloses renewal without any operator or board member doing anything. A record already `COMPLETED` or `PUBLISHED` is untouched by the clock, and `OVERDUE` is terminal, so a record cannot be rescued after the deadline passes; the district recovers its standing only by publishing whatever other reports remain outstanding.

That standing is what the renewal gate reads. Before a district may enter `RENEWAL_PENDING`, and before a `RENEWAL` petition drive may be certified, the district must hold `PUBLISHED` records of `record_type` `ANNUAL_REPORT` **and** of `record_type` `FINANCIAL_AUDIT` for its `current_fiscal_year`, and its `transparency_standing` must not be `DEFICIENT`. A district failing any arm of that test is refused with `ERR_TRANSPARENCY_REQUIREMENTS_UNMET`, however strong its petition support may be.

## 4. API Endpoint Definitions

Every endpoint below is rooted at the service root, so a path shown as `/districts` is requested exactly as written. Creation endpoints return HTTP 201 with the created resource in `data`; every other successful call returns HTTP 200 with the affected resource, the requested resource, or an array of resources. A **creation endpoint** is precisely one that persists at least one brand-new record of one of the twelve types of §2.5, and there are exactly twelve of them: `POST /districts`, `POST /lodging-businesses`, `POST /petition-drives`, `POST /petition-drives/{id}/signatures`, `POST /assessment-periods`, `POST /assessment-periods/{id}/statement-generation`, `POST /assessment-statements/{id}/remittances`, `POST /assessment-disputes`, `POST /annual-work-plans`, `POST /marketing-programs`, `POST /marketing-programs/{id}/room-night-claims` and `POST /transparency-records`. Statement generation is a creation endpoint and so answers 201, but its `data` is the summary object of §3.3 rather than a resource. Every other write endpoint answers **HTTP 200**, however its path is spelled and however plural the noun at the end of it: an action that only advances, amends, revises, records against, reverses, tallies, certifies, closes, verifies, sweeps, resolves or otherwise mutates an existing record persists no new record, so `POST /assessment-statements/{id}/filings`, `POST /assessment-statements/{id}/amendments`, `POST /petition-signatures/{id}/withdrawal`, `POST /districts/{id}/boundary-revisions`, `POST /lodging-businesses/{id}/revisions` and the rest of that group all return 200 with the updated resource. `POST /_clock/set_current_utc` likewise answers 200, with the empty `data` object of §2.2 since §2.4 gives it no payload. Endpoints that mutate a resource return the updated resource, so a caller never needs a follow-up read to observe the effect of a write. The `Authorized Role(s)` column is exhaustive and is the authoritative input to the role check described in §2.1; a caller whose `X-User-Role` is absent from a row is refused with `ERR_FORBIDDEN_ROLE`, except on the public endpoints noted in §2.1, which accept requests carrying no identity headers at all.
