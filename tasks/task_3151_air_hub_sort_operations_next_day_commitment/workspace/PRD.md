# Air Hub Sort Operations API - Product Requirements Document

## 1. Introduction

An air hub is, in operational terms, a race between a fixed wall-clock window and volume that arrives from the sky whether or not the window is ready for it. This document specifies the product requirements for the Air Hub Sort Operations API, the system of record behind a major overnight package hub: inbound arrival banks, aircraft unload sequencing, package induction, primary and secondary sorting, irregular and hazardous material diversion, outbound load planning by weight, balance and destination commitment, commitment cutoff decisions under late inbound pressure, weather and mechanical contingency with alternate-hub routing, sort labor staffing across the nightly window, regional ground feeder coordination, and service failure attribution with money-back guarantee settlement.

The product exists because today's hub decisions are made with partial and inconsistent pictures. A sort supervisor cannot tell whether opening the unload face is legal, a load planner cannot tell whether the next package will breach a container or a weight floor, and a commitment controller cannot tell whether a late arrival has already invalidated a next-day promise. Every one of those questions has a single correct answer that depends on the current volume, the current posture, the current clock, and the current state of several interdependent resources. The system is therefore built as a live, posture-driven control surface: hub posture gates every induction, sort and load action; working postures on each package gate the sort, diverge and refund paths; and staffing posture gates induction and feeder staging.

The system is designed to be complete and self-consistent, not merely plausible. Every derived quantity — the live planning volume, the effective unload budget of a bank, the rated handling weight of a package, the reserve tier of a buildup, the money-back refund of a failure — is recomputed the moment its inputs move, and no derived value is ever accepted as client input. The lifecycle is immediate and strict: the system validates in a fixed order (authentication, then role permission, then path resource existence, then body-scope foreign keys, then business safety rules, then business-temporal rules, then business constraints, then fiscal capacity, then state admissibility, then optimistic concurrency), and it rejects a request at the first rule that fails.

## 2. Global Specifications & System-Wide Principles

This section fixes the contract-level behaviour of the API — who may act, what responses look like, how lists are paged, and which cross-cutting invariants hold everywhere — before §3 turns to the operational workflows themselves.

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers. `X-User-ID` identifies the acting operator and `X-User-Role` declares their capacity. The system recognizes exactly ten roles, spelled as follows: `HubOpsManager`, `SortSupervisor`, `SortOperator`, `LoadPlanner`, `CommitmentController`, `FeederCoordinator`, `GatewayCoordinator`, `HazmatCertifier`, `WeatherOfficer`, and `RefundAdjuster`. A request that omits `X-User-Role`, or that supplies a role outside this set, fails with `ERR_UNAUTHENTICATED` (HTTP 401). Because the entire role model is peer-role rather than entity-backed, **every** one of the ten roles has an opaque identity: when `X-User-Role` is `HubOpsManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity, and the same is true of `SortSupervisor`, `SortOperator`, `LoadPlanner`, `CommitmentController`, `FeederCoordinator`, `GatewayCoordinator`, `HazmatCertifier`, `WeatherOfficer`, and `RefundAdjuster`. The server may record the supplied identifier — for example as the `actor_role` stamped on a `ServiceFailureClaim` — but it never compares it to any entity's `id`, and resource ownership is never inferred from it. Consequently `X-User-ID` is technically present on every request yet constrains nothing: no ownership comparison exists anywhere in this API.

Authorization is enforced after authentication. Each role owns a disjoint set of exclusive operations, and a call to an operation outside the acting role's set is refused with `ERR_UNAUTHORIZED` (HTTP 403). The exclusive sets are: `HubOpsManager` owns the logical-clock pin, clearing a contingency, the ground-stop escalation, aircraft cancellation and reinstatement, bank abandonment, and the two ops-checkpoint dispositions; `SortSupervisor` owns opening a bank's unload face, lane creation and the lane close/reopen pair, per-aircraft unload begin and complete, irregular routing and resolution, and labor-shift creation, cancellation and completion; `SortOperator` owns package creation, induction and induction rejection, primary and secondary sort, and lane reclaim; `LoadPlanner` owns the entire load-move lifecycle, buildup creation and lifecycle, package onboarding and offboarding, buildup assignment, and both manual tier overrides; `CommitmentController` owns every commitment decision (downgrade, ground downgrade, diverge, upgrade-hold) and the clear-reroute, clear-upgrade-hold and package-void exits; `FeederCoordinator` owns feeder scheduling, staging, loading, departure and cancellation; `GatewayCoordinator` owns aircraft creation, origin departure, landing, and reassigning a package to a different inbound aircraft; `HazmatCertifier` owns hazmat routing and hazmat clearance; `WeatherOfficer` owns contingency declaration, weather-driven aircraft diversion, and may append a claim to a failure; `RefundAdjuster` owns failure recording, finalization, dispute, reopen, failure void, and the separate lost-package indemnity claim. Read endpoints across all of the resource collections are shared by all ten roles, and appending a claim to a failure is shared by `RefundAdjuster`, `HubOpsManager` and `WeatherOfficer`.

Two error identifiers govern this subsection and appear nowhere else: `ERR_UNAUTHENTICATED` for the missing-or-invalid header case, and `ERR_UNAUTHORIZED` for the permitted-role case. A malformed or incomplete request — a missing required input, an unknown field, a value of the wrong type, or an invalid enumeration member — is a distinct failure, `ERR_INVALID_REQUEST` (HTTP 400), and it is raised before any business rule is consulted.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` query parameter giving the maximum number of items to return; it defaults to 10, may not be smaller than 1, and may not exceed 100. They also accept an `offset` query parameter giving the number of items to skip; it defaults to 0. Unless a more specific ordering rule is stated for a particular resource, list endpoints return resources sorted by their creation timestamp in ascending order, so the oldest record is first. Every paginated list response carries four pagination fields in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. The Operating Day and the Logical Clock

The hub operates on its own rolling day, and the API exposes a single administrative capability that pins it: a `HubOpsManager` may set the server's logical clock to a supplied `current_utc` instant. Every hub-local minute comparison in this specification is evaluated against a value derived from that instant — never against the host's wall clock. The operating day begins at 12:00Z, and the hub-local minute is the UTC hour multiplied by sixty plus the UTC minute, plus a further 1440 when the clock's UTC time is strictly before noon. So 23:00Z reads minute 1380, 02:00Z reads minute 1560, and 06:01Z reads minute 1801. At server startup the clock stands at 2026-09-01T00:00:00Z, which reads as minute 1440 — the opening edge of a 1440-open / 1560-close window — and the server never substitutes real time for this figure. Moving the clock strictly backwards is refused with `ERR_CLOCK_OUT_OF_ORDER` (HTTP 409), because the whole evening's arithmetic depends on a monotone minute. The write mutates no entity; it merely fixes what every subsequent read observes.

Two properties of the hub's declared window follow from the same arithmetic. A hub is created with `sort_window_open_minutes` and `sort_window_close_minutes`, both hub-local minutes-of-day; the close must be strictly greater than the open, and a hub whose close is at or before its open is refused. A hub is identified by a three-letter `iata_code` that is unique across all hubs and immutable once set, and carries a display `name`; it may also name another hub as its `alternate_hub_id`, which is the destination that normal diversions reroute to while the hub's `contingency_mode` is false. It additionally carries an `ops_run_index` counter that begins at zero and advances by exactly one on every operations checkpoint. The window's length in minutes — the difference between the two — is the basis for the hub's congestion thresholds described in §2.6, and it is also the interval that must contain the current minute for a ground feeder to open its turnout. Everything downstream, from the commitment cutoff of a package to the resolve budget on an irregular routing, is expressed in this same minute-of-day coordinate, which makes the clock the single most load-bearing input in the system.

### 2.5. Posture: The Hub, the Package, and the Shift

Three derived enumerations act as gates over nearly every operation, and getting them wrong is the most common way an implementation will diverge.

**Hub posture** is one of `OPEN`, `CONGESTED`, `LOCKDOWN`, or `GROUND_STOP`. The first three are computed; the fourth is only ever set explicitly. While a hub's `contingency_mode` is false, its posture is a pure function of volume: the congestion threshold is the window length in minutes multiplied by 2000 grams per minute and floored to a whole gram, and the lockdown threshold is the same length multiplied by 5000 grams per minute and floored. Above the congestion threshold but at or below the lockdown threshold, the hub reads `CONGESTED`; at or above the lockdown threshold it reads `LOCKDOWN`; at or below the congestion threshold it reads `OPEN`. The boundaries are deliberate and asymmetric: the open-to-congested comparison is strict, so a live volume of exactly the floored congestion threshold reads `OPEN` and not `CONGESTED`, while the congested-to-lockdown comparison is inclusive, so a live volume of exactly the floored lockdown threshold reads `LOCKDOWN` and not `CONGESTED`. While `contingency_mode` is true, posture is `LOCKDOWN` for every volume, including zero, and the volume-driven branch is restored only when the contingency is cleared. `GROUND_STOP` is never produced by this computation at all; it is reachable only through the escalation described in §3.4. A hub is also created with an `alternate_hub_id`, itself a hub, which is the destination that normal diversions reroute to while `contingency_mode` is false. Its own lifecycle status is carried on a `posture` field, whose four enumerated members are `OPEN`, `CONGESTED`, `LOCKDOWN` and `GROUND_STOP`.

**Package handling posture** is one of `STANDARD`, `IRREGULAR_LANE`, or `HAZMAT_LANE`, carried on the package's `handling_posture` field, and it gates every subsequent sort, load and diverge action on the package. The underlying `handling_status` dimension it summarizes — which is what a package's record actually states — takes one of `NORMAL`, `ROUTED_TO_IRREGULAR`, `ROUTED_TO_HAZMAT`, `DIVERTED` or `HOLD_AT_HUB`.

**Package commitment posture** is one of `COMMITTED_OK`, `DOWNGRADE_PENDING`, or `REROUTE_PENDING`, carried on the package's `commitment_posture` field. A package whose commitment status is `REROUTED` or `UPGRADED_HELD` reads `REROUTE_PENDING`; a package whose commitment status is `DOWNGRADED` reads `DOWNGRADE_PENDING`; and every other package — including one that is still `COMMITTED` while loaded — reads `COMMITTED_OK`. This enumeration, not the commitment status itself, is the gate that package onboarding onto a load move reads, which is why a downgraded package is not loadable even though it has never been voided. The `commitment_status` dimension itself is one of `COMMITTED`, `DOWNGRADED`, `REROUTED`, `VOIDED` or `UPGRADED_HELD`.

**Staffing posture**, carried on a shift's `staffing_posture` field, is one of `GREEN`, `AMBER`, `RED`, or `SATURATED`, and it gates induction and feeder staging during the shift's window. Its derivation, together with the `volume_variance_pct` figure that drives it, is specified in §3.7.

### 2.6. The Live Planning Volume and its Consequences

The hub's `live_planned_package_total` is the sum of `planned_weight_grams` over every package on that hub whose `handling_status` is neither `DIVERTED` nor `HOLD_AT_HUB` and whose `commitment_status` is neither `VOIDED` nor `UPGRADED_HELD`. The inclusion set is pinned by enumeration rather than by any adjective: a package leaves the live total the instant it is diverted or parked at the hub, and it returns the instant it is cleared back. The value is recomputed on every package creation, and on every mutation the package undergoes — induction, routing, sorting, loading, commitment downgrade, divergence, upgrade-hold, void, and every clear operation — and it is also recomputed when a feeder departs with its staged volume voided. Its principal consequence is the hub posture of §2.5, but it also drives the labor variance of §3.7 and the triage classification of §3.13.

Because the value is a live projection over the rows that currently exist, it is legitimately provisional early in the night: read while a bank is still `EN_ROUTE` or `UNLOADING`, it counts only packages that have already been recorded, so a hub may read `OPEN` or `CONGESTED` before the bank's volume has landed. Read after every bank on the hub has closed, the same formula runs over a now-stable row set, and any difference against the earlier reading is an induction shortfall rather than a rounding artefact. An operator may also replace the value outright by declaring a figure; that override stands until the next package mutation recomputes the total in the ordinary way.

### 2.7. Currency, Minutes, and Weight Precision

Three numeric conventions hold across the whole API. All monetary values, of which the refund figure on a service failure is the only one, are expressed in whole cents and produced by rounding half up; no monetary value carries a fractional cent and none is padded to a fixed number of decimal places beyond that. All time quantities are whole hub-local minutes-of-day as defined in §2.4, with no sub-minute precision anywhere. All weights are whole grams, and where a weight is derived it is always a whole number of grams.

Two rounding rules are worth stating separately because they sit under rules that a reader would otherwise guess at. A package's rated handling weight is rounded half up to the nearest 100 grams, and a labor shift's volume variance is rounded half up to four decimal places. Weight thresholds are compared against floored integers, and the reserved-band comparisons of §3.6 are inclusive of their upper bound exactly as written there.

### 2.8. Resource Addressability, Hierarchy, and Validation Order

Every top-level resource in this system carries a system-managed identifier `id`, formatted as a UUID with no type prefix or other decoration, and a `created_at` timestamp in ISO 8601 UTC with three fractional digits. Every resource except `OpsRun` and `ServiceFailureClaim` additionally carries `updated_at`, refreshed whenever the resource is modified, and `version`, an integer that increments on every mutation. `OpsRun` and `ServiceFailureClaim` are the two exceptions: they are created once and never modified in place, so they carry `id` and `created_at` only, and neither `updated_at` nor `version` appears on them.

The resource hierarchy is flat. This API mounts everything under a single top-level path, and each resource declares its owning hub or parent resource through ordinary reference fields in its own body rather than through nested collection paths: a bank and an aircraft know their hub and their bank, a package knows its hub and its inbound aircraft, a lane, a move, a feeder, a shift, a failure and a buildup all know their hub, and a buildup additionally knows its load move and a claim knows the failure it speaks for. Because of that shape, the request bodies in this API list foreign keys in a fixed order everywhere: first `hub_id`, then the parent resource, then the operator-supplied content — so a package body reads `hub_id`, then `aircraft_id`, then the rest; an aircraft body reads `bank_id`; a bank body reads `hub_id`; a lane, move, feeder, shift and failure body each read `hub_id`; a buildup body reads `hub_id` then `load_move_id`; and a claim body reads `service_failure_id`. Many resources, from the bank that groups aircraft through the lane that holds a package to the feeder that stages it, are addressed by an internally derived identifier that the server furnishes and the client then names in later requests.

Validation follows a strict priority order, and a request is rejected at the first rule it violates. Authentication and request shape come first (`ERR_UNAUTHENTICATED` and `ERR_INVALID_REQUEST`, then `ERR_UNAUTHORIZED`). Next comes existence: every path resource is validated left to right — hub, then bank, then aircraft, then package, then load move, then buildup — and the first identifier that does not resolve inside the request's hub scope produces `ERR_RESOURCE_NOT_FOUND` (HTTP 404) immediately. Then every foreign key supplied in the body is validated in the order the endpoint's input list declares it, with the same error and the same hub-scope requirement. Only after existence is settled do business rules run, in this order: business safety rules (`ERR_HAZMAT_CAP_EXCEEDED`, then `ERR_POSTURE_BLOCKS_INDUCTION`), business-temporal rules (`ERR_LANE_CERTIFICATION_LAPSED`), business constraints (`ERR_LANE_NOT_AVAILABLE`, then `ERR_BUILDUP_UNDER_CAPACITY`), fiscal capacity rules (`ERR_LOAD_WEIGHT_EXCEEDED`, `ERR_FEEDER_OVER_CAPACITY`, `ERR_FEEDER_WINDOW_CONFLICT`), then state admissibility with its large family of state and posture errors — whose generic member, raised when a resource is simply not in a state that admits the requested transition, is `ERR_INVALID_STATE` — and finally optimistic concurrency (`ERR_STALE_VERSION`).

### 2.9. Optimistic Concurrency Control

Exactly two write operations in this API carry a stale-version guard, and only those two.

A commitment downgrade sent against a package must carry `expected_package_version`, the client's last observed `version` of the target package. If that value does not equal the package's current version, the requested downgrade is refused with `ERR_STALE_VERSION` (HTTP 412), because the client's view of the package is stale and the downgrade decision has to be re-derived from the current cutoff position rather than applied blindly. The guard is a genuine one rather than a state re-check: a second sequential downgrade request would observe an unchanged commitment position and would itself be legitimate, so only the version field can distinguish the stale writer.

Onboarding a package onto a load move must likewise carry `expected_load_move_version`, the client's last observed `version` of the target move, and a mismatch is refused with `ERR_STALE_VERSION` (HTTP 412). The rationale is the same: another writer has already changed the move's weight commitment, so the client's capacity arithmetic is stale and its onboarding decision would be made against a number that no longer holds. This onboarding request additionally carries `expected_package_version`, the client's last observed version of the package being onboarded, and it is validated against the package's current version with the same error and status.

No other endpoint performs a stale-version rejection. Two notes keep that statement precise. The sealing operation does carry a field named `expected_buildup_version`, but it is not one of the two OCC-guarded writes: a mismatch on it does not produce the stale-version rejection described above, and an implementer should not extend the guard to it. Equally, the manual tier overrides on a move or a buildup demand no previously observed version at all, and an implementation that requires one there will fail calls a client is entitled to make.

### 2.10. Cascading Effects and the Recompute Obligation

The system's consistency model is immediate, and the shape of the domain is deliberately cascading: a single request routinely mutates several resources at once, and one mutation routinely forces the recomputation of a value several relationships away. Three consequences deserve statement up front. First, whenever a mutation changes an input to a derived value, the derived value is recomputed in the same operation — the hub's live planning total and posture, a lane's load and saturation status, a move's weights and reserve tier, a buildup's rated weight and tier, a feeder's staged weight, a shift's variance and posture, and a failure's refund figure are all recomputed at the moment their inputs move rather than on a later read. Second, each such recomputation is an ordinary mutation: it refreshes the affected resource's `updated_at` and increments its `version`. Third, cascades propagate across relationships in defined hops, and the paradoxes of §3.6 and the cascade chains of §3.14 are exactly those hop structures written out.

## 3. Business Logic & Workflows

### 3.1. Induction, Rated Handling Weight, and the Live Volume

A `SortOperator` records each package as it is manifested, supplying a `tracking_number`, the destination represented by `destination_hub_code`, a `commodity_class`, one of the four enumerated values `GENERAL`, `IRREGULAR`, `HAZMAT` or `PERISHABLE`; a `service_level`, one of `NEXT_DAY_AIR`, `SECOND_DAY_AIR` or `GROUND`; the manifested `planned_weight_grams`; and the volumetric `dimension_weight_grams`. A package is created against the inbound aircraft that carried it into the hub, so the request names that aircraft alongside the hub. On creation the package stands at `NOT_INDUCTED` on the induction dimension, `UNSORTED` on the sort dimension, `COMMITTED` on the commitment dimension, and `NORMAL` on the handling dimension, and the system computes its `commitment_cutoff_minutes` from the service level and the hub's window close — `NEXT_DAY_AIR` is cut off exactly at the hub's `sort_window_close_minutes`, `SECOND_DAY_AIR` one full day later at that close plus 1440, and `GROUND` two days later at that close plus 2880. That figure is an absolute minute-of-day and is independent of the clock; what depends on the clock is only where the current minute sits relative to it.

Two creation rules guard the record. A hub may not hold two live packages with the same `tracking_number`: if this hub already carries a package with that number whose `commitment_status` is neither `VOIDED` nor `DIVERTED`, the creation is refused with `ERR_DUPLICATE_LIVE_PACKAGE` (HTTP 409). And a client may supply an `acknowledgement_number` — an idempotency key — whose replay on the same hub returns the original package with a `200` rather than minting a second record; but the same key replayed against a payload that differs from the original request is refused with `ERR_ACK_MISMATCH` (HTTP 409).

Physical induction is the `SortOperator`'s next act, and it is heavily gated because it is the moment the hub accepts the volume into its arithmetic. The hub must be `OPEN` or `CONGESTED` — a `LOCKDOWN` or `GROUND_STOP` hub blocks induction with `ERR_POSTURE_BLOCKS_INDUCTION` (HTTP 409) — and the labor shift whose declared window contains the current minute must not be `SATURATED`, though a `RED` posture does not block it. The package's inbound aircraft must already be `UNLOADED`, and the supplied `dimension_weight_grams` must be at least 1. When induction succeeds, the `induction_status` dimension moves to `INDUCTED`, the hub's live volume and the containing shift's variance both recompute, and the package's handling weight is established.

That handling weight is the `rated_weight_grams`, and it is worth spelling out because it silently governs every capacity comparison in the building. Take the largest of three quantities: the package's `planned_weight_grams`, its `dimension_weight_grams`, and a dimensional minimum of 2000 grams. The rated weight is that largest quantity divided by 100, rounded half up to a whole number, and multiplied back by 100 — that is, the maximum rounded half up to the nearest 100 grams. The minimum and the rounding are both applied before any lane or container comparison, so a package manifested at one gram still occupies 2000 grams of capacity. The rule has two honest readings that the system must both support: when the caller supplies a dimension weight equal to the planned weight — the manifest path — the maximum collapses to the planned weight and the rated weight is simply that weight rounded half up to the nearest 100; when the caller supplies a dimension weight above the planned weight — the volumetric path — the larger figure wins before rounding, so a light but bulky package rates well above what it was manifested at.

An operator may also refuse a package at the face, moving the induction dimension straight to `REJECTED`. That dimension is terminal: a rejected package can undertake no further sort, load or commitment action for the rest of the night.

### 3.2. The Arrival Bank, the Unload Face, and the Effective Sort Budget

Inbound volume arrives in **arrival banks** — scheduled clusters of aircraft — and the bank is the unit against which unload headroom is measured. A bank is created with a `bank_code` unique within its hub, a planned `scheduled_start_minutes` and `scheduled_end_minutes` (the end strictly later than the start), and a `hydraulic_crew_available` flag defaulting to true. It begins life with a `status` of `SCHEDULED` and a null `actual_start_minutes`, and it moves to `EN_ROUTE` automatically when the first aircraft in it reaches `IN_FLIGHT`. The bank's own status dimension walks `SCHEDULED`, `EN_ROUTE`, `UNLOADING`, `UNLOADED`, `CLOSED` and `ABANDONED`, of which `CLOSED` and `ABANDONED` are terminal.

Opening the bank's unload face is a `SortSupervisor` action, and it is refused on three grounds: the hydraulic crew must be available (`ERR_HYDRAULIC_CREW_UNAVAILABLE`), at least one aircraft in the bank must already be `LANDED`, and the hub must not be `GROUND_STOP`. When it succeeds, the bank records `actual_start_minutes` as the current hub minute and every landed aircraft in the bank moves to `UNLOADING`; the bank's own status becomes `UNLOADING`. From that moment the bank's aircraft unload strictly one at a time, because a bank has exactly one unload face: beginning an aircraft's unload while another aircraft on the same bank already holds `UNLOADING` is refused with `ERR_UNLOAD_FACE_OCCUPIED` (HTTP 409), and beginning it while the bank itself is not `UNLOADING` is refused with `ERR_BANK_NOT_UNLOADING`. The per-aircraft unload is also gated on the parent bank's hydraulic crew and on the hub not being ground-stopped.

The headroom the bank still has is the `effective_sort_budget_minutes`, and it is the bank's most consequential derived figure because a late arrival eats directly into it. The computation is a sum over the bank's live aircraft — those whose status is one of `SCHEDULED`, `IN_FLIGHT`, `LANDED`, `UNLOADING` or `UNLOADED`; a `CANCELLED` aircraft contributes nothing at all. Each live aircraft contributes a per-aircraft unload budget of 45 minutes reduced by that aircraft's slack, where the slack is the aircraft's actual arrival minute minus its scheduled arrival minute, clamped to at least zero and to at most an unload slack cap. That cap is the smaller of the 45-minute per-aircraft budget and the number of minutes between the hub's window close and the bank's actual start, itself clamped to at least zero. The resulting sum is clamped to at least zero, so a bank whose every aircraft has been cancelled reports exactly zero rather than a negative figure. The direction of the slack term is the point of the rule: a late arrival increases the slack, which decreases the bank's budget. An aircraft that has not landed, or that landed exactly on schedule, contributes its full 45 minutes; an aircraft twelve minutes late contributes thirty-three. The budget is recomputed on every aircraft unload, cancellation, maintenance diversion or reinstatement within the bank.

Aircraft themselves are identified by a `tail_number` that is unique within the hub and record their `origin_station_code` and the planned `scheduled_arrival_minutes`, and they follow a six-state life of `SCHEDULED`, `IN_FLIGHT`, `LANDED`, `UNLOADING`, `UNLOADED` and `CANCELLED` on a `status` dimension. A `GatewayCoordinator` puts one in flight, and a landing stamps the aircraft's `actual_arrival_minutes` with the current hub minute and records the `inbound_weight_grams` the landing declares; neither action is permitted while the hub is `GROUND_STOP`. Landing deliberately does **not** set the aircraft's `maintenance_hold` even when the arrival is late, because weather and mechanical contingencies in this system are declared at the hub and never at touchdown. Completing an unload requires the supplied `unload_completed_minutes` to be at or after the aircraft's `actual_arrival_minutes`; an earlier figure is refused with `ERR_LATE_UNLOAD_REGRESSION`. A bank becomes `UNLOADED` automatically once every aircraft in it is `UNLOADED` or `CANCELLED`, and an `UNLOADED` bank closes automatically during an operations checkpoint once no package on its aircraft is still `NOT_INDUCTED`.

### 3.3. Sorting, Lane Discipline, and the Handling Dimension

Sorting happens in two passes over physical lanes, and the lane a package occupies is a first-class resource with its own certification, capability and capacity. A lane carries a `lane_code` unique within the hub, a `lane_kind` of `PRIMARY`, `SECONDARY`, `IRREGULAR` or `HAZMAT`, a `commodity_capability` naming the one commodity class it is certified to handle, an hourly `capacity_weight_grams`, a `certified_until_minutes` instant, and a `turnout_start_minutes` / `turnout_end_minutes` pair describing when its face is open. A lane starts `AVAILABLE` and moves to `SATURATED` automatically once its load reaches its capacity, back to `AVAILABLE` when the load falls below capacity, and to `CLOSED` or back by explicit supervisor action. The lane's `lane_load_grams` is the sum of rated handling weights over every package assigned to it whose sort status is `PRIMARY_SORTED` or `SECONDARY_SORTED`; a package that is `UNSORTED` after a reclaim, or that has been loaded and vacated the lane, contributes nothing.

A primary sort requires the package to be `INDUCTED`, requires the hub not to be `LOCKDOWN`, and requires the target lane — named in the request by its `lane_id` — to exist on this hub, to be `AVAILABLE`, to be certified for this package's commodity class, and to be certified at the current instant — strict certification means the current minute is strictly before the lane's `certified_until_minutes`, and a lapsed certificate is refused with `ERR_LANE_CERTIFICATION_LAPSED`. A closed lane, or one whose capability does not match the package's commodity class, is refused with `ERR_LANE_NOT_AVAILABLE`; and the lane's hourly capacity must not be exceeded — if the lane's load plus this package's rated weight would exceed the lane's `capacity_weight_grams`, the sort is refused with `ERR_LANE_CAPACITY_EXCEEDED`. On success the `sort_status` dimension moves to `PRIMARY_SORTED`, the lane assignment is recorded on the package's `assigned_lane_id`, `last_sort_minutes` takes the current hub minute, and the lane's load and saturation status recompute.

The primary sort also carries the automatic diversion of commodity. This is not optional behaviour an operator may skip. A `GENERAL` package is primary-sorted and stays `NORMAL` on the handling dimension. A package whose commodity class is `IRREGULAR` or `PERISHABLE` is automatically moved to `ROUTED_TO_IRREGULAR`, and a `HAZMAT` package is automatically moved to `ROUTED_TO_HAZMAT`. A package already parked in the irregular lane cannot be primary-sorted at all until that routing is cleared — the primary sort admits handling statuses `NORMAL` and `ROUTED_TO_IRREGULAR` only, with the irregular routing being the one it tolerates because the resolution of that routing is itself handled below. Handling posture recomputes to `IRREGULAR_LANE` for the irregular case and `HAZMAT_LANE` for the hazardous case.

A secondary sort moves the package to its final lane and is governed by a tighter set of gates. It requires that the package is not `ROUTED_TO_IRREGULAR` — the irregular lane must be resolved first — that the package is not `DIVERTED`, and that the elapsed time since `last_sort_minutes` is at most 60 minutes, the secondary stage budget. An attempt past that budget is refused with `ERR_SORT_STAGE_BUDGET_EXCEEDED`. The target secondary lane must exist, be `AVAILABLE`, be certified for the candidate's commodity class, and still be certified at the current minute. And when the package is `ROUTED_TO_HAZMAT`, the target lane's `lane_kind` must be `HAZMAT`: a hazardous package may never be secondary-sorted onto a lane of any other kind. On success the `sort_status` dimension moves to `SECONDARY_SORTED`, the `assigned_lane_id` and `last_sort_minutes` update, and the lane recomputes.

Lanes are not permanent assignments. An operator may reclaim a package off a lane from either `PRIMARY_SORTED` or `SECONDARY_SORTED`, returning the `sort_status` dimension to `UNSORTED` and clearing the `assigned_lane_id` — critically, `last_sort_minutes` survives the reclaim, so the freshness and budget clocks described in §3.5 keep running rather than restarting. Coming off a primary lane also normalizes the handling dimension: both `ROUTED_TO_IRREGULAR` and `ROUTED_TO_HAZMAT` return to `NORMAL`, the handling posture returns to `STANDARD`, and the source lane releases its grams. The reclaim from a secondary lane carries the same release for the secondary lane's load.

### 3.4. Weather and Mechanical Contingency

The hub's contingency regime is a deliberate two-stage escalation, and its stages are not symmetric.

A `WeatherOfficer` declares a contingency. A hub in `OPEN` or in `CONGESTED` may be declared, and the only precondition is that the hub's `contingency_mode` flag is currently false; declaring it while it is already true is refused with `ERR_CONTINGENCY_NOT_DECLARED`. The declaration sets the mode true and, through the posture computation of §2.5, forces posture to `LOCKDOWN` regardless of volume. From that instant the ordinary induction and load paths close: `LOCKDOWN` blocks induction, loading, departure and landing with `ERR_POSTURE_BLOCKS_INDUCTION`.

Escalation from `LOCKDOWN` to `GROUND_STOP` belongs to a `HubOpsManager` and requires the contingency already be declared — a ground stop attempted on a hub that is not locked down is refused with `ERR_HUB_NOT_LOCKED`. The escalation is violent by design: every load move on the hub that is `PLANNED` or `LOADING` moves to `REWORK_REQUIRED` and returns each of its loaded packages from `LOADED` to `SECONDARY_SORTED`, and the loaded weight those moves had accumulated is released by the ordinary recomputation.

Clearing the contingency is the `HubOpsManager`'s counter-move, and it is where the system's most intricate cascade lives. Clearing sets the mode false and lets the posture recompute; with the mode false the posture returns to `OPEN` or `CONGESTED` purely as a function of live volume. But the minute the mode clears, every package on the hub that had been pushed out into the world has to be accounted for. Every package that is `DIVERTED` in handling and `REROUTED` in commitment has its commitment returned to `COMMITTED`, its `final_commitment_minutes` cleared to null, and its service level restored to the level it originally committed to; the failure recorded against that reroute is voided as well. Every package that is parked at the hub under `HOLD_AT_HUB` handling with a `COMMITTED` commitment moves instead to `UPGRADED_HELD` with its `final_commitment_minutes` set to its commitment cutoff plus 360 minutes — the guarantee-assurance extension — and this happens independently of any aircraft's state. Each package that has just become `UPGRADED_HELD` emits exactly one service failure, with a `REVENUE_PRORATE` cause, attributed to the customer, recorded at the current hub minute, in `OPEN` status and not refund-eligible. That new failure's refund figure is computed by the ordinary money-back rule, which returns zero for a customer-attributed failure. Finally, an aircraft on this hub whose `maintenance_hold` is true stays `CANCELLED` when the contingency clears: reinstatement is always an explicit act and never automatic.

The strand is the failure mode this design accepts deliberately. A hub that clears its contingency with no `alternate_hub_id` declared leaves its diverted and parked packages unable to be diverted a second time, because there is no alternate route to give them, so they take the assurance extension path instead of a genuine reroute.

Weather and mechanical trouble also arrives at the aircraft level. An in-flight aircraft may be diverted to a maintenance station by a `WeatherOfficer` under a declared contingency and while its own `maintenance_hold` is false; the diversion is a self-transition that leaves the aircraft `IN_FLIGHT` but sets its `maintenance_hold` and clears `actual_arrival_minutes` to null, so the aircraft is excluded from every unload computation while remaining nominally in the air — the bank's effective sort budget recomputes accordingly. A grounded aircraft may be cancelled by a `HubOpsManager`, but only while not one of its packages has left `UNSORTED`; a cancellation with cause `MECHANICAL` sets the maintenance hold, every package aboard moves to `UPGRADED_HELD` with a cutoff-plus-360 extension, each emits exactly one mechanical-attributed failure, and the hub's live volume and the containing shift's posture recompute because those packages have just left the live total. A `CANCELLED` aircraft may be returned to service by the duty manager once the contingency is clear and its maintenance hold has been released; reinstatement clears its arrival, unload-completion and inbound-weight figures back to null, but its packages stay `UPGRADED_HELD` and are not automatically returned to `COMMITTED` — each must be cleared individually.

A bank has its own abandonment path, restricted to a `HubOpsManager` and again available only under contingency. A bank still `EN_ROUTE` may be abandoned only when an operations checkpoint exists on this hub at `MAJOR` level with a `HELD` verdict; abandonment cancels every aircraft in it that is still `SCHEDULED` or `IN_FLIGHT`, each of which emits one weather-attributed failure, and every package aboard those aircraft moves to `DOWNGRADED` with a cutoff-plus-360 extension and a service level slipping from next-day to second-day. A bank that is already `UNLOADING` may be abandoned with only the contingency as its precondition, and every aircraft still `UNLOADING` or `LANDED` in it is cancelled with its maintenance hold set.

### 3.5. Irregular and Hazardous Routing, and the Freshness Gate

Handling diversion is the system's second dimension of state on a package, and it loops rather than merely advancing. A `SortSupervisor` may route an irregular or perishable package to the irregular lane from the normal handling state, provided the commodity class is `IRREGULAR` or `PERISHABLE`, the package is still `UNSORTED`, and the target irregular lane exists, is available, and is certified at the current minute. Resolution back to normal is also the supervisor's — or, for a hazardous routing, the `HazmatCertifier`'s — and both resolutions are bounded by an irregular resolve budget of 45 minutes measured from `last_sort_minutes`: a package may be resolved while its last sort minute is null, or while the current minute is at or before that last sort minute plus 45. A resolution attempted after the budget has closed is refused with `ERR_IRREGULAR_RESOLVE_BUDGET_EXCEEDED`.

Routing to the hazardous lane is the `HazmatCertifier`'s exclusive act and can be reached from either the normal handling state or from an irregular routing already in force. In both cases the commodity class must be `HAZMAT` and the target hazardous lane must exist, be available, and be certified at the current minute. When the route is taken from an irregular routing, two further gates apply, and the second of them is the sharpest rule in the section. The first is the same 45-minute resolve budget measured from `last_sort_minutes`. The second is a lane-freshness gate that is strictly tighter than the budget: for the irregular-to-hazardous route specifically, the package may only be moved while its last sort minute is null or while the current hub minute is at or **before** its last sort minute. Advancing the clock strictly past the last sort minute closes this gate even while the 45-minute budget window is still wide open. On a successful route the handling status becomes `ROUTED_TO_HAZMAT` and the handling posture `HAZMAT_LANE`, and any lane the package previously occupied releases its grams.

### 3.6. Load Moves, Buildups, and Two Different Capacity Truths

An outbound flight is filled through a **load move** and its destination **buildups**. A move is planned against an outbound aircraft with a `weight_limit_grams`, begins as `DRAFT`, and takes a `sequence` number at creation that is assigned monotonically within the hub and serves as the stable tie-break for gateway weight allocation within that move. It then moves through `DRAFT` to `PLANNED` (a planning act that requires the aircraft not be cancelled and not under a maintenance hold; the aircraft may still be on the ground), `PLANNED` to `LOADING` (permitted unless the hub is ground-stopped), and `LOADING` to `LOADED` upon completion. It can be forced into `REWORK_REQUIRED` — automatically when the hub's posture becomes `LOCKDOWN` or `GROUND_STOP` from `PLANNED`, or by the ground stop from `LOADING` — and it can be replanned back to `PLANNED` once the contingency has been cleared, or cancelled from `DRAFT`, from `PLANNED` while nothing on it is loaded, or from `REWORK_REQUIRED` at any time.

Within a move, a buildup consolidates volume for one destination gateway and belongs to a single move, declared by its `load_move_id`. A buildup is unique per gateway within its move and is created with a `container_limit_grams`, an optional `hazardous_cap_grams` (defaulting to zero, and a cap of zero means the buildup accepts no hazardous content at all), and an optional `requires_container` flag defaulting to false. Its `rated_weight_grams` is the sum of rated handling weights over every package assigned to it whose commitment is not voided, its `hazardous_load` flag is true when at least one such assigned package is `HAZMAT`, and its `hazardous_weight_grams` sums the rated weight of exactly those hazardous packages. Moving a package into a buildup without loading it is a separate assignment act, which sets the package's `buildup_id` and recomputes the buildup's rated and hazardous weights. The move keeps two independent weight tallies as it fills: the `planned_weight_grams` of everything committed to it that is not voided, and the `loaded_weight_grams` of the subset that has actually reached `LOADED`, so a move can show planned volume that has not yet been physically placed.

The move's own capacity arithmetic is pinned in an evaluation order that must not be reordered, because the tier label and the displayed capacity come from two different values of the same quantity. First compute the **filled weight**: the sum of `planned_weight_grams` over every package on the move whose commitment is not `VOIDED`. Second compute the **raw forward capacity**: the move's `weight_limit_grams` minus that filled weight. Third derive the **tier label from the raw value, not from the floored one**: raw capacity strictly above zero reads `UNDER_CAPACITY`, exactly zero reads `AT_CAPACITY`, and below zero reads `RESERVE_TIER`. Only fourth, and purely for the displayed field and for the onboarding guard, is the floor applied: the `forward_capacity_grams` field is the raw value floored at zero. The dependency looks circular because the tier also feeds the reserve routing described below, and the pinned order is what makes the value well defined: a move whose raw forward capacity is negative five thousand grams reads a displayed forward capacity of zero and a tier of `RESERVE_TIER` on the very same read. A move read during planning, before anything is onboard, has a filled weight of zero, so its raw forward capacity is exactly its weight limit; and a move read after a package was loaded and then unloaded returns to exactly its pre-load tier and capacity, because the row set is identical and nothing drifts.

The buildup's own tier uses a different subject and a different band. Take the buildup's `rated_weight_grams` minus its `container_limit_grams`. A difference at or below zero reads `UNDER_CAPACITY`; a difference strictly above zero and at most 25000 grams reads `AT_CAPACITY`, the decision band inside which neither sealing nor breach fires; and a difference above 25000 grams reads `RESERVE_TIER`. The boundaries are exact: a difference of exactly zero is `UNDER_CAPACITY` and not `AT_CAPACITY`, and a difference of 25 grams is `AT_CAPACITY`. Because the same function is called with two subjects, a hub can legitimately show a load move reading `RESERVE_TIER` while its buildup reads `UNDER_CAPACITY` at the same instant. The discontinuity at the band edge is what produces the dual effect: since every rated weight is a multiple of 100 grams, a 100000-gram buildup against a 100000-gram container sits exactly at `AT_CAPACITY`, while 100100 grams crosses into `RESERVE_TIER` **and** flips the buildup from `OPEN` to `WEIGHT_BREACH` at the same moment. The breach state is entered automatically whenever the difference exceeds 25000 grams, its tier is recomputed to `RESERVE_TIER`, and it returns to `OPEN` automatically when unloading brings the rated weight back to within the tolerance.

Onboarding a package onto a move is where the guards concentrate — the request names the `package_id` to onboard, and it carries the optimistic-concurrency obligations of §2.9, so it must be sent with both `expected_load_move_version` and `expected_package_version`. The package must read `COMMITTED_OK` on its commitment posture. The move must be `PLANNED` or `LOADING`. The move's aircraft must not be cancelled and must not be under a maintenance hold. The destination buildup guard then rejects the onboarding if the move already carries a buildup for this package's destination gateway whose rated weight minus its container limit is strictly inside the band from just above zero to 25000 grams inclusive — that is, any buildup sitting in its `AT_CAPACITY` decision band may not accept more volume, and the refusal is `ERR_BUILDUP_UNDER_CAPACITY`. The hazardous cap guard rejects onboarding a `HAZMAT` package whose rated weight, added to the target buildup's existing hazardous weight, would exceed that buildup's `hazardous_cap_grams`, with `ERR_HAZMAT_CAP_EXCEEDED` (HTTP 409). The fiscal floors then apply to the move's forward capacity: the forward capacity **before** onboarding must be at or below a ceiling of 350000 grams — onboarding from above that ceiling is refused — and the forward capacity **after** onboarding must be at or above a lower bound — the sort budget floor constant, which is negative 20000 grams — with a breach of that floor refused as `ERR_LOAD_WEIGHT_EXCEEDED` (HTTP 409). On success the package's sort dimension becomes `LOADED`, its lane assignment clears, and the move's loaded weight, planned weight, forward capacity and tier and the buildup's rated weight, hazardous weight, hazardous flag and tier all recompute; if the buildup has just crossed the breach tolerance it flips to `WEIGHT_BREACH`. Offboarding returns the package to `SECONDARY_SORTED` and unwinds the same recomputations, including a breached buildup returning to `OPEN` once it is back within tolerance.

Completing a load has its own pair of final gates. Every buildup on the move must satisfy a disjunction: either its rated weight is at or below its container limit, or its rated weight exceeds that limit by more than 25000 grams. A buildup stranded inside the band between those two conditions — above its limit by more than nothing and by at most 25000 grams — blocks completion with `ERR_BUILDUP_UNDER_CAPACITY`. The move's planned weight must not exceed its weight limit plus a use-it-or-lose-it tolerance of 10000 grams, with a breach reported as `ERR_LOAD_WEIGHT_EXCEEDED`. And the hub must be `OPEN` or `CONGESTED` at that moment. On success every `OPEN` buildup on the move is `SEALED` and the move's aircraft is marked ready for departure. A buildup may also be sealed or unsealed directly: sealing requires that its rated weight is at or below its container limit, and separately requires that its rated weight does not exceed that limit by more than nothing and by at most 25000 grams — the same exclusion of the tolerance band — and, when the owning move's declared `requires_container` map says true for this buildup's destination gateway, requires it be filled to at least its container limit minus a fill tolerance of 5000 grams. Sealing sends the buildup's tier through the same computation, and a sealed buildup may be reopened again by its planner. A buildup may be cancelled as well, with the gate depending on where it stands: an `OPEN` buildup may be cancelled only while no package resting in it has reached sort status `LOADED`, and a `SEALED` buildup may be cancelled only while its owning load move has not itself reached `LOADED`. A load move, for its part, may be cancelled from `PLANNED` only while nothing on it has reached sort status `LOADED`, and from `DRAFT` or `REWORK_REQUIRED` at any time.

### 3.7. Labor Staffing Across the Nightly Window

A shift is created by a `SortSupervisor` with a `shift_code` unique within the hub, a `start_minutes` and `end_minutes`, a `headcount`, a per-operator-hour `productivity_grams_per_operator_hour`, a `forecast_volume_grams`, and an optional `certified_for_hazmat` flag. The `end_minutes` must differ from the `start_minutes`; a shift whose end equals its start is invalid. A shift may cross midnight: the end minute may be numerically smaller than the start minute. Its duration in minutes is the end minus the start, plus 1440 if that difference is negative — equivalently, the difference taken modulo 1440.

Its postures derive from two comparisons against the hub's live volume, and the precedence between them is pinned. The capacity in grams is the headcount multiplied by the per-operator-hour productivity multiplied by the shift's duration in hours — that is, the duration divided by sixty. If the live volume strictly exceeds that capacity, the posture is `RED`. Otherwise, if the shift's variance is at least 0.15, the posture is `SATURATED`. Otherwise, if the absolute value of the variance is strictly less than 0.10, the posture is `GREEN`. Otherwise the posture is `AMBER`. Because the capacity rule is checked before the variance rules, a shift that is both over capacity and over variance reads `RED` and never `SATURATED` — a distinction that matters downstream, because the ground-feeder staging gate and the induction gate both test specifically for `SATURATED` and do not block on `RED`. The boundaries are exact: a variance of exactly 0.15 is `SATURATED`, and a variance of exactly 0.0999 is `GREEN`. A shortfall is not the same posture as a match: a shift whose live volume falls at least 0.10 below its forecast reads `AMBER`, and `GREEN` is reserved for a variance strictly inside plus or minus 0.10.

The variance itself is the live volume minus the shift's forecast volume, divided by the forecast volume, rounded half up to four decimal places, expressed as a signed fraction. The shift's window participates in these computations only while it contains the current hub minute; a shift whose window is open with `start_minutes` at or before the current minute and `end_minutes` strictly after it — or, for an overnight shift whose start is above its end, one whose current minute is at or after its start or strictly before its end — is the one that governs, and a shift outside its window does not participate at all. While the containing shift's window is open, a variance at or above 0.15 moves its status automatically to `OVERRUN`, and it falls back to `SCHEDULED` automatically when the variance drops below that figure. A shift may be cancelled by a supervisor while no induction is in progress against it — that is, while it is not the shift currently gating induction — and it may be closed out to its terminal `COMPLETED` state only once its posture is no longer `SATURATED`, because a shift has to be brought back under the overrun band before it can close. A supervisor may also revise the shift's `forecast_volume_grams` at the start of the night, which recomputes the variance and the posture.

Where the shift's posture surfaces as an operational decision is the hub's triage read, which classifies the next volume wave by the `verdict`-style label it returns. The system identifies the shift whose declared window contains the current hub minute. If no shift covers the current minute, the triage is `NO_SHIFT`. If the covering shift is `RED`, the triage is `SHED_TO_NEXT_WINDOW`. If it is `SATURATED`, the triage is `THROTTLE_INDUCTION`. Otherwise the triage is `ACCEPT`. The domination of `RED` over `SATURATED` holds here exactly as it does in the posture derivation, so a shift that is both over capacity and over variance sheds rather than throttles. This read is also the observable surface of the deepest contingency cascade: a cascade that drives the covering shift to `RED` shows up as `SHED_TO_NEXT_WINDOW` even though a `RED` posture blocks no endpoint.

### 3.8. Ground Feeder Coordination

Regional volume reaches the hub on **ground feeders**, and the feeder's lifecycle is a narrow, heavily gated window. A feeder is scheduled by a `FeederCoordinator` with a `feeder_code` unique within the hub, an `origin_station_code`, a `scheduled_departure_minutes` strictly above zero, a `stage_capacity_grams`, and a `window_minutes` giving the length of its turnout window.

Opening the feeder's turnout — moving it from `SCHEDULED` to `STAGING` — is bound by five preconditions at once. The current hub minute must be at or after the scheduled departure minus the window length, and strictly before the scheduled departure. The owning hub must be inside its own sort window, meaning the current minute is at or after the hub's `sort_window_open_minutes` and strictly before its `sort_window_close_minutes`. No other feeder on the hub may already be `STAGING` within one window length of this feeder's scheduled departure; a collision is refused with `ERR_FEEDER_WINDOW_CONFLICT` (HTTP 409). And the labor shift whose window contains the current minute must not be `SATURATED`; note that a `RED` shift, exactly as in §3.7, does not block staging.

Staging a package onto the feeder's turnout lane records the feeder on the package's `staged_feeder_id` and accumulates the feeder's `staged_weight_grams`, which is the sum of `planned_weight_grams` over every package staged on it whose commitment is not voided. Closing the turnout and beginning the load requires the staged weight be at or below the full `stage_capacity_grams`. Departure is where a second, tighter capacity number appears, and it is the trap of this workflow. While the feeder is `STAGING`, the compliant ceiling is the full stage capacity; at departure, the ceiling is ninety-five percent of the stage capacity, floored to a whole gram — the departure tolerance applied to the stage capacity, so the comparison is against exactly 0.95 of it. A feeder staged to exactly its full capacity is therefore perfectly compliant while staging and over its departure ceiling by five percent at the moment it leaves — refused with `ERR_FEEDER_OVER_CAPACITY` (HTTP 409), even though nothing about the load changed. Departure additionally requires the hub to be `OPEN` or `CONGESTED`. When it succeeds, every staged package has its commitment voided, its handling moved to `DIVERTED`, and its final commitment minute cleared, each emits exactly one failure with a `REVENUE_PRORATE` cause attributed to the customer, in `OPEN` status and not refund-eligible, and the hub's live volume recomputes.

Cancelling a feeder is available from `SCHEDULED`, `STAGING` and `LOADING`, so the feeder's own lifecycle states are `SCHEDULED`, `STAGING`, `LOADING` and `DEPARTED`, with `CANCELLED` as the alternative ending. A cancellation from either of the two later states releases every staged package back to the sort surface and clears its feeder reference, recomputing the staged weight to zero.

### 3.9. Commitment Cutoffs, Downgrade, and Divergence

The commitment dimension is where the night's promises are kept or broken, and it has five states: `COMMITTED`, `DOWNGRADED`, `REROUTED`, `VOIDED` and `UPGRADED_HELD`. A package's cutoff was fixed at creation by §3.1; the decisions below move the package relative to that cutoff. The downgrade window is defined by two leads around the cutoff: it opens 30 minutes before the cutoff and closes 60 minutes after it. A downgrade attempted before the package has entered that window is refused with `ERR_CUTOFF_NOT_REACHED`, and one attempted after the grace window has closed is refused with `ERR_COMMITMENT_GRACE_EXCEEDED`. Every commitment decision in this subsection also requires that the package has not already been loaded — a commitment action on a loaded package is refused with `ERR_SORT_PENDING` — and the two decisions that would strand a package at the hub require that it is not already `HOLD_AT_HUB`.

The ordinary downgrade is the `CommitmentController`'s, and it must be sent against the package's observed version as §2.9 requires. It applies while the current minute is strictly after the cutoff minus 30 and at or before the cutoff plus 60. On success the commitment becomes `DOWNGRADED`, the service level slips from next-day to second-day, the final commitment minute is set to the cutoff plus 360, and exactly one failure is emitted, with a `LATE_INBOUND` cause attributed to the carrier, in `OPEN` status and refund-eligible, carrying its provisional refund figure.

The ground downgrade is the same controller's response to a hub that has stopped moving, and it needs no clock window at all — only that the hub is `LOCKDOWN` or `GROUND_STOP` and the package is not loaded. Its extension is far longer than the ordinary one: the final commitment minute becomes the cutoff plus 1800, and the failure it emits carries a `WEATHER` cause attributed to the weather event, in `OPEN` status and not refund-eligible.

Divergence is the decision to send the package somewhere other than here. It requires a declared contingency, requires the hub to actually have an `alternate_hub_id` — diving on a hub with none is refused with `ERR_NO_ALTERNATE_HUB` — requires the package not be parked at the hub, and requires the current minute be strictly past the cutoff. It moves the commitment to `REROUTED` and the handling to `DIVERTED` together, sets the final commitment minute to the cutoff plus 240, emits exactly one failure with a `LATE_INBOUND` cause attributed to the carrier, in `OPEN` status and refund-eligible, and recomputes the hub's live volume and posture.

The upgrade hold parks the package at the hub instead. It requires the contingency to be **clear**, requires the current minute be strictly past the cutoff, and requires the package's inbound aircraft to be `CANCELLED` — a hold against a package whose aircraft is still flying is refused with `ERR_AIRCRAFT_NOT_CANCELLED`. It moves the commitment to `UPGRADED_HELD` and the handling to `HOLD_AT_HUB`, sets the final commitment minute to the cutoff plus 360, and recomputes the hub's live volume and the containing shift's posture.

Three exits unwind these decisions. A `REROUTED` package may be cleared once the contingency is clear, returning it to `COMMITTED` handling `NORMAL` with any open reroute failure voided and the live volume recomputed. An `UPGRADED_HELD` package may have its hold cleared only while its aircraft is no longer cancelled and the contingency is clear; the clear returns it to `COMMITTED` and `NORMAL` handling and additionally resets its sort dimension to `UNSORTED` with `last_sort_minutes` cleared, so it must be sorted again from scratch. And a `DOWNGRADED` package may be voided by the controller, provided it is not loaded and provided no failure on it has already been finalized — a finalized failure blocks the void with `ERR_FINALIZED_FAILURE_PRESENT` — whereupon the commitment becomes `VOIDED` and the handling `DIVERTED`, excluding the package from every load and feeder calculation.

### 3.10. Operations Checkpoints and the Dual Disposition of a Held Run

An operations checkpoint is a `HubOpsManager`'s formal judgement about the state of the night, recorded as an `OpsRun` against a declared `minute_of_day` and at a `level` of `MINOR` or `MAJOR`. Its `verdict` is one of `ADVANCED`, `HELD` or `RELEASED`, and its `run_index` is the sequential checkpoint number within the hub. Creating one takes the hub's `ops_run_index`, adds one, and uses that value as the run's own `run_index`, starting at 1 for the first checkpoint on a hub; the hub's counter increments by one, and the new checkpoint's verdict begins at `HELD`. Running a checkpoint is also when an unloaded bank whose packages are all induced is closed automatically.

A held checkpoint has two possible dispositions, and their difference is the sharpest fork in the system. Both require the checkpoint to currently be `HELD`, both leave the hub's counter incremented by one, and both advance the checkpoint's own verdict away from `HELD` — but their preconditions are opposite and their effects diverge.

Advancing a held run is the disposition taken **while the contingency is still declared**. It re-routes the night: every package on the hub in `DOWNGRADED` commitment moves to `REROUTED` with its final commitment minute set to its cutoff plus 240, and every aircraft on the hub that is `CANCELLED` with a maintenance hold is returned to `IN_FLIGHT` with its actual arrival minute cleared. Note that no failure is emitted by this disposition, and no package is parked.

Releasing a held run is the disposition taken **once the contingency has been cleared**. It parks the night: every package on the hub in `DOWNGRADED` commitment moves instead to `UPGRADED_HELD` with its final commitment minute set to its cutoff plus 360, and each such package emits exactly one failure, with a `LATE_INBOUND` cause attributed to the carrier, refund-eligible, and `OPEN`. No aircraft changes status at all under this disposition — the aircraft-level compensation belongs exclusively to the advance path.

### 3.11. Service Failures, Attribution, and the Money-Back Guarantee

A service failure records a missed commitment. It is created against the package whose commitment was missed, by naming that package alongside the hub, and with a `cause_code` and a `failure_minutes` stamped from the hub's clock, and it begins `OPEN`. Two of its fields are derived once and then frozen for the rest of its life: the `attributed_role`, and the `refund_eligible` flag. Later clock movement or a change in hub posture never re-derives either of them. Its own `status` dimension is one of `OPEN`, `FINALIZED`, `DISPUTED` or `VOIDED`, and its computed `refund_amount_cents` carries the money-back figure for the whole life of the record, moving only when the failure's own status moves or when its history is re-derived.

The attribution mapping is fixed, and its four possible values are the exact strings `CARRIER`, `CUSTOMER`, `WEATHER_EVENT` and `MECHANICAL_EVENT`. A cause of `LATE_INBOUND`, `SORT_MISS` or `NO_SCAN` attributes the failure to `CARRIER`. A cause of `BAD_ADDRESS` or `REVENUE_PRORATE` attributes it to `CUSTOMER`. A `WEATHER` cause attributes it to `WEATHER_EVENT`, and a `MECHANICAL` cause attributes it to `MECHANICAL_EVENT`. The refund eligibility is exactly the carrier attribution: a failure is refund-eligible if and only if its attributed role is `CARRIER`.

The refund figure follows the service level of the package the failure is about. A next-day package is rated at 550 cents per kilogram, a second-day package at 300, and a ground package at 140. The gross figure is the package's `planned_weight_grams` divided by 1000, multiplied by that per-kilogram rate, rounded half up to a whole cent; a package whose commodity class is `PERISHABLE` adds a further 250-cent surcharge on top, and a package that is both perishable and next-day collects both, because the rate is keyed on the service level while the surcharge is keyed on the commodity class — two independent dimensions. Three qualifications complete the rule. A failure not attributed to the carrier refunds nothing at all, which covers every weather-attributed, mechanical-attributed and customer-attributed failure and applies before any rate is considered. A failure still in `OPEN` status pays only the provisional share, seventy percent of the gross figure, rounded half up to a whole cent. And a failure that has been finalized pays the gross figure in full. To fix the magnitudes: a next-day package of 2500 grams rates 1375 cents at full value, and while open it pays 963 cents, because 1375 multiplied by 0.70 is 962.5, which rounds half up; once finalized the same package pays the full 1375. Ground failures are never eligible, so no ground rate is ever actually paid under this rule.

The failures on a hub aggregate into a refund batch total, and the evaluation order of that total is pinned because two readings of the same sentence differ by a cent. For each failure the gross figure is computed as above — the weight-times-rate term rounded half up, plus the perishable surcharge where it applies. Each failure's own value is then computed from its gross figure: seventy percent of it rounded half up while the failure is `OPEN`, and the gross figure itself when it is not. The values are **then** summed. Rounding each failure first and summing afterwards is the required order; summing first and rounding once at the end is forbidden and produces a different number. On two open next-day failures over 250050-gram general packages, the gross per failure is 137528 cents — 250.050 multiplied by 550 is 137527.5, rounding half up — and the pinned order yields 96270 per failure for a total of 192540, while the forbidden order yields 192539. Only failures attributed to the carrier on that hub contribute; failures attributed to the customer, the weather event or the mechanical event contribute zero and are excluded from the sum. The batch total is refreshed whenever a failure on the hub is created or finalized, and it also moves when a carrier-attributed failure is voided, because voiding a failure removes it from the sum.

### 3.12. Finalization, Dispute, and the Compensating Void

A failure moves between `OPEN`, `FINALIZED`, `DISPUTED` and `VOIDED` through the refund adjuster's decisions, and each transition carries its own gate.

Finalizing lifts the money-back guarantee to full value and is available only to a refund-eligible failure: a non-eligible failure cannot be finalized at all. On success the refund figure is recomputed without the provisional scaling and frozen at that value.

Disputing is the opposite motion and is available only to a failure that is **not** carrier-attributed, because a carrier-attributed failure is a refund obligation rather than a dispute candidate; the attempt is refused with `ERR_CARRIER_ATTRIBUTED_NOT_DISPUTABLE` (HTTP 409). Disputing moves the failure to `DISPUTED` and changes nothing else. Reopening a disputed failure returns it to `OPEN`, but only while the hub is `OPEN` or `CONGESTED` — a reopen attempted while the hub is `LOCKDOWN` or `GROUND_STOP` is refused with `ERR_REOPEN_POSTURE_BLOCKED`.

Voiding a failure is reserved for a carrier-attributed one, and it is the compensating invariant of the whole refund design: voiding a carrier refund restores the package's commitment. The package the failure names, if it is in `DOWNGRADED` commitment, returns to `COMMITTED` with its final commitment minute cleared to null and its service level restored to the level it originally committed to; its sort dimension is deliberately left untouched. The hub's live volume recomputes as a result, and the hub's refund batch total recomputes because the voided failure leaves the carrier sum.

Claims are a separate, append-only record of who said what about a failure. Any of the three permitted roles — the refund adjuster, the duty manager or the weather officer — may append a claim carrying an `outcome` of any of `OPEN`, `FINALIZED`, `DISPUTED` or `VOIDED` and an optional free-text `note`; the appended claim records the role that wrote it and takes the next sequential `claim_index` within its failure, counting from one. It is the claim history, not the claim itself, that decides the failure's status: the status is re-derived from the claims as the outcome of the claim that is last in the fixed order — ordered by ascending claim index, then by ascending creation timestamp, then by ascending claim identifier, so that a tie in the first two criteria is broken deterministically rather than at random — considering only claims whose index is at or below the failure's current claim sequence. A failure with no claims is `OPEN` by construction. Appending a claim also recomputes the failure's refund figure, which is why a claim can move the batch total without any refund adjuster touching the failure directly. Distinct from all of this is the lost-package indemnity path: a refund adjuster may open a separate indemnity claim on a package by declaring a `claimed_value_cents`, but the declared value is recorded and not paid — the system emits a failure with a `NO_SCAN` cause attributed to the carrier, and that failure's refund figure comes from the money-back rule of §3.11 like any other.

### 3.13. Lane Geometry, Concourse Width, and the Lane Count

Two metrics hang off the sort lanes, and they must not be confused with each other, because they differ in what they measure, in how many lanes they take as subject, and in what they do about adjacency.

The first is the lane load of §3.3: a weight metric, on a single lane, summing the rated handling weights of the packages resting on it.

The second is the concourse width rating: a **minute** metric, computed across a **pair** of lanes of the same kind on one hub. Take every non-closed lane on the hub whose kind matches the kind being asked about, and sort their turnout intervals — each a start minute and an end minute — by start minute and then by end minute. Walk adjacent pairs in that order. Where a pair's second interval begins at or before the first interval's end, the intervals merge, and the pair contributes the difference between the second interval's end and the first interval's end. The rating is the total of those merged minutes multiplied by a merge credit of four. The treatment of a single minute of separation is the whole point: two same-kind lanes whose intervals touch exactly at a point — the second beginning exactly where the first ends — merge and credit four units per merged minute, while two lanes that miss by exactly one minute do not merge at all and contribute zero, so one minute of gap disables an entire merge.

### 3.14. The Cascade Chain

Several operations in this system are chain reactions rather than single effects, and the chain has a defined length. The deepest of them begins with a late unload at hub minute M of an aircraft whose packages have already reached their commitment cutoffs. The aircraft's packages still reading `COMMITTED` move to `DOWNGRADED`, with a next-day service level slipping to second-day and a final commitment minute of the cutoff plus 360. If the hub's contingency is on at that moment, the same package is then rewritten a second time, from `DOWNGRADED` to `UPGRADED_HELD`, and its final commitment minute is overwritten to the cutoff itself — the guarantee is lost outright rather than extended, which is the whole difference between the two hops. A third hop then emits exactly one failure per such package, with a weather cause attributed to the weather event, in `OPEN` status and not refund-eligible. A parallel chain runs from the arrival bank's cancellation path: cancelling an unfinished aircraft moves each of its packages to `UPGRADED_HELD` with the cutoff-plus-360 extension, emits one mechanical-attributed failure for each, and, because every one of those packages has just left the live planning set, forces both the hub's live volume and the containing shift's posture to recompute. Clearing a contingency with no alternate declared produces a chain of the same shape through the parked packages, ending in a `REVENUE_PRORATE` failure attributed to the customer. An implementation that stops at the first hop will pass the simple cases and fail every deep one.

### 3.15. Manual Overrides and the Limits of the Derived Fields

Three derived fields can be overridden by hand, and each override has a defined lifetime. A load planner may set a move's `load_plan_tier` directly, and a load planner may set a buildup's `load_plan_tier` directly; in both cases the override stands until the next package event on that object, at which point the ordinary derivation of §3.6 recomputes the tier and the manual value is gone. Separately, a load planner may declare that a destination gateway must ship in a full container by writing to the move's `gateway_requirements` map, keyed by `destination_gateway_code` with a `requires_container` boolean; that declaration is what the sealing gate of §3.6 reads. None of these override operations changes any weight: each merely offers a tier label or a declaration in place of the derived one, and the underlying arithmetic remains the system's.
