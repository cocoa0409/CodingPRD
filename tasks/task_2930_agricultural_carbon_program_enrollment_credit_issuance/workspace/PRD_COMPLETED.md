# Agricultural Carbon Program API — Product Requirements Document

## 1. Introduction

Voluntary agricultural carbon markets fail for a boringly predictable reason: the paperwork does not reconcile. A grower adopts cover cropping, a consultant models some tonnage, a buyer retires a certificate, and three years later nobody can say which acres produced which credit, whether the practice was genuinely new, or who is liable when the field is ploughed back. This API is the programme's system of record, and it is built so that every credit ever issued can be traced backwards through a verification opinion, a quantification run, a set of quality-controlled field observations, an approved baseline, an additionality screening and a mapped field boundary — with no step optional and no step reversible by accident.

The service supports four kinds of actor working in deliberate mutual distrust. Programme administration staff onboard growers, publish methodologies, screen enrollments, adjudicate baselines, run quality control, quantify removals, commission verification, handle reversals and settle payments — but never two of the sensitive steps with the same human identity. Growers map their own land, file their own historical records and field observations, and may ask to leave a commitment early. Accredited third-party verification bodies conduct site visits and issue the opinion that unlocks issuance. A registry custodian, organisationally separate from programme administration, holds sole authority to list, retire and cancel batches on the public registry.

Two properties dominate the design. First, **conservatism is arithmetic, not attitude**: every tonnage figure carries an explicit uncertainty deduction, every issuance contributes a share of its credits to a programme buffer pool sized against reversal risk, and every grower payment withholds a permanence holdback until the commitment is nearly served. Second, **the ledgers must always reconcile**: gross credits always equal buffer credits plus issued credits; the buffer pool's balance always equals its running `contributed_total` less its `drawn_total`, a cancelled batch's contribution being taken out of both figures at once; serial numbers are handed out once and never reused, even when a batch is cancelled. Where a rule below looks pedantic about evaluation order or rounding, that pedantry is the requirement.

## 2. Global Specifications & System-Wide Principles

All paths in this document are mounted at the service root, so every business collection is a top-level path segment.

### 2.1. Actors and Role-Based Access Control

Every request other than the logical-clock endpoint must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the caller's role. Both must be present and non-empty; a header supplied as an empty string, or as whitespace only, counts as absent. If either header is missing or empty, or if `X-User-Role` is not one of the four declared role names, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the named role is not authorized for the endpoint being called, the request is refused with `ERR_UNAUTHORIZED` (HTTP 403).

The four roles are `ProgramAdmin`, `Grower`, `Verifier` and `RegistryOfficer`, spelled exactly as shown.

- **`ProgramAdmin`** — programme administration staff. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands an audit trail — as `screening_decision_admin_id` and `baseline_approval_admin_id` on an enrollment, as `approved_by_admin_id` on a baseline, and as `reported_by_admin_id` and `assessed_by_admin_id` on a reversal event — and it compares recorded values against the acting identifier to enforce segregation of duties, but it never compares it to any entity's `id`.
- **`Grower`** — the enrolled agricultural operator. When `X-User-Role` is `Grower`, `X-User-ID` is the `id` of the acting `Grower` row; ownership checks on any resource that references a `Grower` compare the resource's owning-grower field to `X-User-ID`, following the chain transitively where necessary (a data packet belongs to an enrollment, which belongs to a grower).
- **`Verifier`** — an accredited third-party verification body. When `X-User-Role` is `Verifier`, `X-User-ID` is the `id` of the acting `VerificationBody` row; ownership checks on a verification compare the verification's assigned body to `X-User-ID`.
- **`RegistryOfficer`** — the registry custodian. When `X-User-Role` is `RegistryOfficer`, `X-User-ID` is an opaque custodian identifier not tied to any persisted entity. The server may record it for audit purposes but never compares it to any entity's `id`.

An acting `Grower` that addresses a resource owned by a different grower, or an acting `Verifier` that addresses a verification assigned to a different verification body, is refused with `ERR_RESOURCE_NOT_OWNED` (HTTP 403). Ownership is evaluated after existence — so a grower probing another grower's identifiers learns that it is not permitted rather than whether the row exists — and before any state check, so a grower touching a foreign suspended enrollment still receives the ownership error rather than a state error. Ownership binds single-resource reads and writes only: list endpoints are never implicitly narrowed to the caller, so a `Grower` or `Verifier` calling a list endpoint its role may reach receives every row matching the supplied filters, including rows belonging to other growers or bodies, and must pass the relevant foreign-key filter itself to see only its own.

A `ProgramAdmin` caller is never ownership-bound. On the endpoints that both roles share — field registration, practice-history filing, enrollment creation, enrollment submission and resubmission, exit requests, data-packet filing and packet correction — a `ProgramAdmin` may act on any grower's records, while a `Grower` may act only on its own.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by 32 lower-case hexadecimal characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one timestamp in the API read from the host's real UTC clock rather than from the logical programme clock of §2.4, so it does not move when a client repositions that clock and it never appears on a stored row.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. The `limit` parameter caps the number of items returned; it defaults to 10 when omitted, must be at least 1, and may not exceed 100. The `offset` parameter is the number of items to skip and defaults to 0, and it may not be negative. Both bounds are enforced rather than clamped: a `limit` below 1 or above 100, a negative `offset`, or either parameter carrying something that is not an integer is refused with `ERR_INVALID_REQUEST` (400). A parameter supplied as an empty string is read as omitted and takes its default, and any query parameter the endpoint does not declare is ignored.

Unless a specific endpoint says otherwise, every list endpoint returns its rows ordered by creation, ascending — oldest first. Because the logical clock of §2.4 can leave many rows sharing one `created_at`, the ordering is by the server's monotonic creation sequence rather than by the timestamp string, so rows created in the same clock instant come back in the order they were written and the order is stable across calls.

List responses carry four pagination fields inside the envelope's `meta` object: `limit`, `offset`, `total_count` and `has_more`. `total_count` reports the number of rows matching the filters before the window is applied, and `has_more` is true when rows remain beyond the current window.

### 2.4. The Logical Programme Clock and Crop Years

Nothing in this API reads the host machine's wall clock. Every temporal comparison — crop-year derivation, exit-notice arithmetic, site-visit stamping, payment timestamps — reads a server-held **logical UTC clock**. Before any client repositions it, the logical clock reads exactly `2026-08-01T00:00:00Z`; this startup default is mandatory and the server never falls back to real time. Any of the four roles may reposition the clock by supplying a `current_utc` instant — the field is required, and the endpoint accepts it whether or not identity headers are sent at all — and the response `data` carries exactly two keys, the new `current_utc` echoed back byte for byte as it was supplied (a submitted `2026-08-01T00:00:00.500Z` is echoed with its three fractional digits, and a submitted `2026-08-01T00:00:00Z` is echoed with none), together with the derived `current_crop_year`. Repositioning the clock mutates no stored entity and triggers no recalculation of any previously computed figure.

The **current crop year** is the calendar year of the logical clock instant. Every rule in this document that speaks of "the current crop year" means exactly that derived integer.

### 2.5. Resource Identity, Audit Fields and the One Immutable Record Type

Every resource is addressed by an `id`, which is a server-minted UUID carrying no type prefix. Alongside it, most resources expose three system-managed fields:

- `created_at` — an ISO 8601 UTC timestamp with three fractional digits, recording when the row was first written. It renders the logical clock of §2.4 at exactly millisecond width, always with three fractional digits and a trailing `Z`; a clock positioned with a finer fraction than a millisecond has that finer part truncated away here.
- `updated_at` — an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row. On creation it equals `created_at` exactly.
- `version` — an integer that starts at 1 on creation and increments by exactly one on every mutating request, including mutations the server performs on its own initiative as part of a cascade. The unit is the request, not the assignment: where one request touches the same row more than once — a cascade that revisits a row it has already moved, or an aggregate adjusted in two hops of the same call — that row's `version` still advances by exactly one for the whole request, and its `updated_at` is refreshed once.

`PracticeHistory` is the single exception. A historical crop-year practice record is immutable once filed: it carries only `id` and `created_at`. It has neither `updated_at` nor `version`, there is no endpoint that edits or deletes it, and nothing in the system ever rewrites one. Growers correct their evidence base by filing additional records, not by amending existing ones.

Derived aggregates count as mutations. When the reversal cascade decreases an enrollment's `accrued_payment_cents`, or an issuance increases a grower's `lifetime_credits_issued`, or a cancellation decreases the buffer pool's `outstanding_issued_credits`, the affected row's `updated_at` is refreshed and its `version` increments — even though no client asked for that row to change.

### 2.6. Path Resolution and Reverse Reachability

Path parameters are resolved strictly left to right, and the leftmost identifier that does not resolve decides the response. Registering a field under an unknown grower reports `ERR_GROWER_NOT_FOUND` even when the request body is also malformed, because grower resolution precedes body validation. The path identifiers the API accepts are `grower_id`, `field_id`, `practice_history_id`, `practice_standard_id`, `enrollment_id`, `baseline_id`, `data_packet_id`, `quantification_run_id`, `verification_body_id`, `verification_id`, `credit_batch_id`, `buffer_account_id`, `reversal_event_id` and `grower_payment_id`; each has its own not-found code, listed in §5, and `practice_history_id` reports `ERR_PRACTICE_HISTORY_NOT_FOUND`.

Foreign keys supplied in a request *body* are resolved too, and they report the same not-found codes as their path counterparts. The body-borne references the API accepts are `practice_standard_id`, `field_id`, `baseline_id`, `quantification_run_id`, `verification_body_id`, `credit_batch_id` and `supersedes_batch_id`; an unresolvable `supersedes_batch_id` reports `ERR_CREDIT_BATCH_NOT_FOUND`.

Several records in this programme are created by cascades rather than by direct client calls — credit batches minted by issuance, grower payments accrued by issuance, and the baseline proposal that a newer proposal supersedes. Those records are never returned by the call that created them, so each child collection offers a filtered list endpoint carrying the relevant foreign key as an optional query parameter. That is the only discovery channel for cascade-created rows: `grower_id` on the field list, `field_id` on the practice-history list, `grower_id` / `field_id` / `practice_standard_id` on the enrollment list, `enrollment_id` on the baseline, data-packet and quantification-run lists, `baseline_id` on the quantification-run list, `quantification_run_id` and `verification_body_id` on the verification list, `enrollment_id` / `quantification_run_id` / `supersedes_batch_id` on the credit-batch list, `enrollment_id` / `credit_batch_id` on the reversal-event and grower-payment lists, and `pool_code` on the buffer-account list.

Beyond the foreign keys, list endpoints accept the obvious attribute filters: `status` and `mailing_state` for growers; `status`, `soil_group` and `county_code` for fields; `crop_year`, `practice_code` and `evidence_source` for practice history; `practice_code` and `status` for practice standards, which additionally filter on the methodology version under either of two accepted parameter names, `standard_version` or the shorter alias `version`; `status`, `permanence_status`, `payment_model` and `start_crop_year` for enrollments; `method` and `status` for baselines; `crop_year`, `source`, `qc_status` and `completeness_status` for data packets; `crop_year`, `method` and `status` for quantification runs; `status` and `practice_code` for verification bodies; `opinion` for verifications; `vintage_year`, `issuance_status`, `registry_status` and `risk_tier` for credit batches; `pool_status` for buffer accounts; `reversal_type` and `status` for reversal events; and `crop_year`, `status` and `payment_model` for grower payments. Two of those names read a differently named stored field: `status` on the verification list reads the verification's `opinion` axis, which has no separate status field of its own, and `practice_code` on the verification-body list — for which `accredited_practice` is accepted as a second name — reads the body's `accredited_practices` array. Every filter matches by exact equality against the stored value, with no case folding, no trimming and no partial matching, except the two array-valued names just given, which match when the supplied string is a member of the array; filters supplied together are combined with logical AND, and a value that matches nothing yields an empty page rather than an error. The empty-string tolerance of §2.3 governs `limit` and `offset` alone: a *filter* supplied as an empty string is matched literally and so selects no rows, while a filter whose stored counterpart is an integer — `crop_year`, `start_crop_year`, `vintage_year`, and `standard_version` under either of its two names — is parsed as an integer and refused with `ERR_INVALID_REQUEST` when it cannot be, the empty string included.

### 2.7. Numeric Precision, Rounding and Units

Every rounding operation in this API is **round half up** — a value exactly on the midpoint rounds away from zero. Where a figure has a declared scale, the server stores and returns it at that scale, as a JSON number rather than a string. "At that scale" governs the value, not its rendering: the figure is carried to the declared number of decimal places, and because it is emitted as a JSON number the trailing zeros are not preserved, so a two-place `12.50` comes back as `12.5` and a two-place zero comes back as `0.0`.

Incoming numeric fields must be JSON numbers too. A numeral wrapped in a string, a boolean, or a non-finite value in a decimal field is refused with `ERR_INVALID_REQUEST`, and so is a value carrying more decimal places than its declared scale — with the one tolerance that trailing zeros which disappear on normalisation do not count against the scale, so a two-place field accepts `12.500`. Integer fields — `crop_year`, the four boundary coordinates, `standard_version` and the methodology's year counts among them — require a JSON integer: `3.0` is not an integer and neither is `true`.

- **Acreage** is carried to 2 decimal places. This includes `gross_acres`, `mapped_acres`, `enrolled_acres`, `acres`, `reported_acres`, `verified_acres`, `payable_acres` and `affected_acres`.
- **Tonnage**, measured in tCO2e, is carried to 3 decimal places: `baseline_emissions_t`, `gross_removals_t`, `uncertainty_deduction_t`, `net_removals_t` and `restated_removals_t`.
- **Per-acre rates** are carried to 4 decimal places: `observed_emissions_per_acre`, `historical_mean_rate`, `sequestration_rate_per_acre` and `modeled_baseline_rate_per_acre`. Dimensionless factors such as `adoption_factor` are likewise carried to 4 decimal places.
- **Percentages** are carried to 2 decimal places and, except where a formula explicitly produces a larger figure, lie between 0 and 100 inclusive: `max_prior_adoption_pct`, `uncertainty_base_pct`, `buffer_base_pct`, `prior_adoption_pct`, `additionality_score`, `coverage_pct`, `qc_score`, `uncertainty_pct`, `mean_coverage_pct`, `sampling_uncertainty_pct`, `sample_pct`, `material_discrepancy_pct`, `buffer_pct`, `holdback_pct` and `per_credit_share_pct`.
- **Money** is carried as an integer number of cents throughout — `per_acre_rate_cents` is the only cents figure that accepts fractional input, at 2 decimal places, because it is a configured rate rather than a settled amount. Settled amounts (`gross_amount_cents`, `holdback_cents`, `net_amount_cents`, `exit_fee_cents`, `grower_clawback_cents`, `net_paid_cents`, `outstanding_clawback_cents`, `accrued_payment_cents`) are whole cents.
- **Credits** are integers throughout. One credit is one tonne of CO2 equivalent, so converting tonnage to credits discards the fraction: the credit count is the largest integer not greater than the tonnage.
- **Field boundaries** are integers in programme grid units, where one grid unit is one metre and 4000 square grid units make one acre.

Where a formula chains rounded terms, each intermediate term is rounded to its own declared scale *before* it feeds the next line. Where a formula both rounds and clamps, the rounding happens first and the clamp is applied to the rounded value.

### 2.8. Optimistic Concurrency on Enrollments and Batches

Three write operations require the caller to declare the version of a parent record it last observed. These are not optional fields, and no other endpoint accepts a version field at all.

- **Proposing a baseline** for an enrollment requires `expected_enrollment_version` in the request body, carrying the client's last observed `version` of that `Enrollment`. If it does not equal the enrollment's current `version`, the request is refused with `ERR_STALE_ENROLLMENT_VERSION` (HTTP 412). The state machine alone cannot protect this operation, because a second proposal is entirely legitimate on its own terms — it supersedes the incumbent proposal. The version check is what stops a client still looking at the screening-era view of the enrollment from replacing a proposal it has never seen.
- **Creating a quantification run** requires `expected_enrollment_version` in the request body, again carrying the client's last observed `version` of the `Enrollment`. A mismatch against the enrollment's current `version` is refused with `ERR_STALE_ENROLLMENT_VERSION` (HTTP 412). Repeat draft runs for the same enrollment and crop year are permitted by the product, so a client working from a fresh snapshot would succeed where a client working from a stale one must not; the version check is the only thing that distinguishes them.
- **Cancelling a credit batch** requires `expected_credit_batch_version` in the request body, carrying the client's last observed `version` of the `CreditBatch`. A mismatch against the batch's current `version` is refused with `ERR_STALE_BATCH_VERSION` (HTTP 412). Listing, retirement and reversal cascades all advance a batch's `version` without moving its `issuance_status`, so a cancellation built on an older snapshot would otherwise release buffer credits from a batch whose registry position has since changed.

### 2.9. Segregation of Duties

The programme deliberately requires two distinct human identities to walk certain paths. Two rules are enforced by comparing `X-User-ID` against a previously recorded administrator identifier:

- The `ProgramAdmin` whose `X-User-ID` was recorded as an enrollment's `screening_decision_admin_id` may not approve that enrollment's baseline.
- The `ProgramAdmin` whose `X-User-ID` was recorded as a reversal event's `reported_by_admin_id` may not assess that reversal event.

Either violation is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 409). This check runs *after* the state precondition, which has a consequence worth stating explicitly: an administrator who repeats an approval call on a baseline that is already approved receives `ERR_INVALID_STATE_TRANSITION`, not the duties error, even though that same administrator is also the one barred from approving.

Custody is separated structurally as well. Registry actions — listing, retirement and cancellation of issued batches — belong to `RegistryOfficer` alone and to no `ProgramAdmin`, so the staff who mint credits cannot also place them on the registry or take them off it. Symmetrically, a `Verifier` may issue an opinion but may not assign itself work, quantify, issue or touch the registry.

### 2.10. The Validation Ladder: One Fixed Order for Every Request

Requests are checked against an ordered ladder of rules. The rungs are evaluated in ascending order, the **first** violated rung decides the response, and no later rung runs. This ordering is part of the contract: two rules may both be violated by one request, and the response must name the earlier one. The ladder is as follows.

1. **Authentication.** `X-User-Role` and `X-User-ID` are both present and non-empty, and `X-User-Role` is one of the four declared roles → otherwise `ERR_UNAUTHENTICATED` (401). This rung applies to every endpoint except the logical-clock repositioning endpoint, which is deliberately unauthenticated so that test harnesses can position the clock before any actor exists.
2. **Authorization.** The acting role appears in the called endpoint's authorized-role list → otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Path existence.** Every path-parameter resource resolves, strictly left to right → otherwise the corresponding not-found code (404). Applies to every endpoint carrying path parameters.
4. **Ownership.** A `Grower` caller owns the addressed resource; a `Verifier` caller is the body assigned to the addressed verification → otherwise `ERR_RESOURCE_NOT_OWNED` (403). Applies to every endpoint reachable by `Grower` or `Verifier`.
5. **Request shape.** Every required body field is present and non-null; enum fields carry a declared member; decimal fields are numbers inside their declared scale; acreage, tonnage, percentage and cents fields are not negative; percentage fields lie between 0 and 100 inclusive; a `crop_year` is an integer between 2000 and 2100 inclusive, and every other crop-year-valued field shares exactly that range — `start_crop_year`, `vintage_year` and `requested_exit_year` among them; the boundary values are integers with `boundary_max_x` strictly greater than `boundary_min_x` and `boundary_max_y` strictly greater than `boundary_min_y`; instants are ISO 8601 UTC with a trailing `Z` → otherwise `ERR_INVALID_REQUEST` (400). Applies to every write endpoint that reads a body — seven action endpoints never read one at all, namely enrollment submission and resubmission, verification-body suspension and reinstatement, site-visit recording, reversal assessment and payment settlement, and on those the request body is ignored in its entirety, so even a body that is not valid JSON passes this rung untouched. Five conventions settle the edges of this rung. The body itself must be a JSON object: a body that is absent altogether, or is present but empty, is read as `{}` and so satisfies any endpoint that requires no field, while a body that parses to an array, a string or a number, or that is not valid JSON at all, is refused. A field supplied explicitly as `null` is indistinguishable from an omitted field, so it fails a required field and takes the declared default on an optional one. A string field declared non-empty is trimmed for the emptiness test only — whitespace alone is empty and is refused, but a value that survives is stored exactly as supplied, untrimmed. Body properties the endpoint does not declare are ignored rather than refused. An instant is accepted with no fractional part or with one to nine fractional digits, and its `T` and `Z` may be given in either case; anything else — a bare calendar date, a numeric offset such as `+00:00`, a missing `Z` — is refused.
6. **Body foreign keys.** Every foreign key supplied in the body resolves → otherwise the corresponding not-found code (404). Applies to enrollment creation, quantification-run creation, verification creation, reversal-event reporting and field registration.
7. **Grower standing.** The owning grower is not `SUSPENDED` → otherwise `ERR_GROWER_SUSPENDED` (409). A suspended grower may still read everything it could read before. The rung applies to exactly nine write endpoints — field registration, survey confirmation, practice-history filing, enrollment creation, enrollment submission, enrollment resubmission, the exit request, data-packet filing and packet correction — which are the writes that put new grower-supplied material into the programme. The administrator-only steps further along each workflow are deliberately *not* gated on grower standing, so staff can finish adjudicating work already in flight for a grower under sanction: the screening information request, the screening decision, exit adjudication, per-acre accrual, every baseline action, quality control, packet rejection, quantification-run creation, submission, revision and issuance all proceed unchanged while the owning grower is `SUSPENDED`.
8. **Verification-body standing.** The verification body involved in the write is `ACCREDITED` rather than `SUSPENDED` at the moment of the write → otherwise `ERR_VERIFICATION_BODY_SUSPENDED` (409). Applies to four operations: verification assignment, site-visit recording, opinion issuance and resampling.
9. **State.** The addressed resource is in a state from which the requested transition is declared, and the transition's preconditions on *other* entities also hold — quantification requires the enrollment to be `ACTIVE`, issuance requires a `POSITIVE` verification opinion, registry listing requires `issuance_status` of `ISSUED` → otherwise `ERR_INVALID_STATE_TRANSITION` (409). Applies to every action endpoint.
10. **Stale parent version.** Where the endpoint declares a version field (§2.8), the supplied value equals the parent's current `version` → otherwise `ERR_STALE_ENROLLMENT_VERSION` or `ERR_STALE_BATCH_VERSION` (412). Applies to exactly three operations: baseline proposal, quantification-run creation and batch cancellation.
11. **Segregation of duties** → `ERR_SEGREGATION_OF_DUTIES` (409), on baseline approval and reversal assessment, as described in §2.9.
12. **Methodology availability.** The pinned practice standard is `ACTIVE` rather than `RETIRED`, and its `effective_from` calendar year is not later than the enrollment's `start_crop_year` → otherwise `ERR_PRACTICE_STANDARD_RETIRED` (409). Applies to enrollment creation, submission and resubmission.
13. **Methodology version integrity.** The `pinned_standard_version` on the enrollment still equals the referenced standard's current `standard_version` → otherwise `ERR_STANDARD_VERSION_MISMATCH` (409). Applies to quantification-run creation and to issuance.
14. **Additionality gates**, evaluated as a two-step cascade: first that `documented_years` is at least the standard's `min_documented_years`, then that `prior_adoption_pct` is not greater than the standard's `max_prior_adoption_pct` → `ERR_INSUFFICIENT_PRACTICE_HISTORY` or `ERR_ADDITIONALITY_FAILED` respectively (both 422). The second check consumes figures produced while evaluating the first, so a field with too little documented history reports the history error even when its computed prior adoption would also have breached the ceiling. The two-step cascade applies to enrollment submission and resubmission only. Baseline proposal re-runs neither gate — it never reports `ERR_ADDITIONALITY_FAILED` and never compares a year count against `min_documented_years`; it borrows the first code alone, `ERR_INSUFFICIENT_PRACTICE_HISTORY`, for the narrower emptiness reason given in §3.4.
15. **Commitment terms.** `commitment_years` is at least the standard's `min_adoption_years` and at most 12; `enrolled_acres` is greater than zero and not greater than the field's `mapped_acres` → otherwise `ERR_COMMITMENT_TERMS_INVALID` (422). Applies to enrollment creation.
16. **Boundary exclusivity** → `ERR_FIELD_BOUNDARY_OVERLAP` (409), on field registration, as described in §3.1.
17. **Commitment-period exclusivity** → `ERR_COMMITMENT_PERIOD_OVERLAP` (409), on enrollment creation, as described in §3.3.
18. **Practice cooldown** → `ERR_PRACTICE_COOLDOWN_ACTIVE` (409), on enrollment creation, as described in §3.9. Rung 18 is evaluated only after rung 17, so an enrollment that both overlaps an incumbent commitment and sits inside a cooldown window reports the overlap error.
19. **Verifier workload** → `ERR_VERIFIER_CAPACITY_EXCEEDED` (409), on verification assignment and resampling, as described in §3.6.
20. **Cross-entity linkage coherence.** The baseline named on a quantification run belongs to the same enrollment and is `APPROVED`; the verification body's `accredited_practices` contains the enrollment's `practice_code`; a batch naming `supersedes_batch_id` references a batch of the same enrollment → otherwise `ERR_BASELINE_NOT_APPROVED`, `ERR_BASELINE_ENROLLMENT_MISMATCH`, `ERR_PRACTICE_NOT_ACCREDITED` or `ERR_SUPERSEDED_BATCH_MISMATCH` (all 422). Applies to quantification-run creation, verification creation and issuance. Because this rung runs after the temporal rungs, a verification assignment that is both capacity-blocked and directed at a body lacking the practice accreditation reports the capacity error.
21. **Data sufficiency and quality thresholds** → `ERR_NO_QUALIFYING_DATA`, `ERR_TELEMETRY_EVIDENCE_REQUIRED`, `ERR_COVERAGE_BELOW_MINIMUM`, `ERR_QC_SCORE_BELOW_THRESHOLD`, `ERR_MATERIAL_DISCREPANCY_EXCEEDED` or `ERR_SAMPLE_TOO_SMALL` (all 422). Applies to quantification-run creation, the quality-control decision, verification creation and opinion issuance. The individual thresholds are stated in §3.5 and §3.6; `sample_pct` must be at least 5.00 on both verification assignment and resampling, and a value below that floor reports `ERR_SAMPLE_TOO_SMALL`.
22. **Uniqueness.** Seven distinct uniqueness rules live on this rung, each with its own code (all 409): a practice standard is unique on the pair of `practice_code` and `standard_version` (`ERR_DUPLICATE_STANDARD_VERSION`); at most one non-terminal enrollment exists per field and `practice_code` (`ERR_DUPLICATE_ENROLLMENT`); at most one non-rejected data packet exists per enrollment, `crop_year` and `source` (`ERR_DUPLICATE_DATA_PACKET`); at most one non-rejected quantification run exists per enrollment and `crop_year` (`ERR_DUPLICATE_QUANTIFICATION_RUN`); at most one proposed baseline exists per enrollment and `method`, so a proposal naming a *different* method legitimately supersedes the incumbent while a repeat of the *same* method is a duplicate (`ERR_DUPLICATE_BASELINE`); at most one pending verification exists per quantification run (`ERR_DUPLICATE_VERIFICATION`); and at most one accrued payment exists per enrollment, `crop_year` and `payment_model` (`ERR_DUPLICATE_PAYMENT`). The rung applies to practice-standard publication, enrollment creation, data-packet filing, quantification-run creation, baseline proposal, verification creation and per-acre payment accrual.
23. **Exit notice window** → `ERR_EXIT_WINDOW_NOT_OPEN` (422), on the exit request, as described in §3.9. Both clauses of the rule carry this same code.
24. **Buffer pool solvency** → `ERR_BUFFER_POOL_DEFICIT` (409), on issuance, as described in §2.12.
25. **Settlement preconditions** → `ERR_CLAWBACK_OUTSTANDING`, `ERR_UNRESOLVED_REVERSAL` or `ERR_SUPERSEDED_BATCH_NOT_CANCELLED` (all 409), on payment settlement, batch retirement and batch listing respectively, as described in §3.8 and §3.9.

### 2.11. Cascade Discipline and Compensation

Many operations in this programme touch more than one entity. Where they do, the secondary effects are as much a part of the contract as the primary one, and they are stated in full alongside the workflow that triggers them. Three conventions govern all of them.

**Cascades are transitive and immediate.** Suspending a grower moves that grower's active enrollments to `SUSPENDED`, and *because* those enrollments moved, their enrolled fields move to `SUSPENDED` in turn. There is no queue and no eventual consistency: by the time the response is written, every hop has landed and every touched row has a refreshed `updated_at` and an incremented `version`.

**Compensation is explicit, and not always symmetric.** Reinstating a grower restores exactly the enrollments and fields that its suspension moved, and leaves terminal rows alone. Cancelling a credit batch unwinds the pool contribution, the outstanding-credit count, the grower's lifetime issuance and the enrollment's issued total — but not the serial counter, which never rolls back because serial numbers are never reused. Resolving a reversal returns suspended registry listings and repairs permanence standing, but does not restore cash that was clawed back. Each asymmetry is deliberate and each is stated where the operation is described.

**Aggregates that look like they should move sometimes must not.** A grower's `total_enrolled_acres` counts the `mapped_acres` of that grower's fields whose `status` is either `ENROLLED` or `SUSPENDED`. Suspension therefore leaves the acreage aggregate completely unchanged — the programme still regards the land as enrolled while the grower is under sanction. The aggregate moves only when a field enters or leaves that pair of states: it increases when baseline approval marks a field `ENROLLED`, and decreases when an exit or termination returns the field to `MAPPED`.

The grower row carries four further running aggregates. `lifetime_credits_issued` is the running total of `issued_credits` across every batch minted for that grower, decreased again only by a batch cancellation. `net_paid_cents` is the sum of `net_amount_cents` over that grower's payments whose `status` is `PAID`. `outstanding_clawback_cents` is the sum of `grower_clawback_cents` over that grower's reversal events whose `status` is `ASSESSED` or `RESOLVED` — the assessed unbacked liability, booked once per reversal event and never once per clawed-back payment. `reversal_count` is the number of reversal events on that grower's enrollments whose `status` is `ASSESSED` or `RESOLVED`. All four start at zero when the grower is registered, as does `total_enrolled_acres` at 0.00.

### 2.12. The Programme Buffer Pool

Exactly one buffer pool exists, and the server seeds it at startup with `pool_code` set to `PROGRAM_BUFFER`. Its purpose is to absorb reversals so that a buyer holding a retired credit does not lose it when a grower's field burns. The pool is a ledger with six stored running counters, a serial cursor and two derived figures.

`contributed_total` accumulates every credit ever contributed by an issuance, less any contribution that a batch cancellation has since withdrawn from it (§3.8). `drawn_total` accumulates every credit ever drawn to cover an assessed reversal. `released_total` accumulates every credit ever released back out of the pool because the batch that contributed it was cancelled. `unbacked_reversal_credits` accumulates every assessed reversal credit the pool could not cover on the occasions when the pool was consulted at all — that is, on unintentional reversals only, an intentional reversal leaving this counter and `drawn_total` alike exactly where they stood (§3.8). The pool's `balance_credits` is itself a stored running counter rather than a figure re-derived on read: it is seeded at zero and moves only through the hops named in §3.7 and §3.8 — an issuance's buffer contribution increases it, a reversal draw decreases it, and a batch cancellation decreases it by the cancelled batch's `buffer_credits`. Because a cancellation is booked twice over — `released_total` up and `contributed_total` down by that one quantity — `balance_credits` is **not** recomputed as contributions less draws less releases; the identity that holds at every moment is that `balance_credits` equals `contributed_total` less `drawn_total`.

`outstanding_issued_credits` is, like `balance_credits`, a stored running counter rather than a figure re-derived on read. It is seeded at zero and moves on exactly three hops: an issuance increases it by the minted batch's `issued_credits` (§3.7), and both the retirement and the cancellation of a batch decrease it by that batch's `issued_credits` (§3.8). Retirement is why the counter cannot be restated as a sum over the batches whose `issuance_status` is `ISSUED` — a retired batch is still `ISSUED` on the issuance axis, its credits having left the counter while that axis never moved — and cancellation is why it cannot be restated as a sum over every batch ever minted. The pool holds a `min_reserve_ratio`, seeded at 0.05, and its `required_reserve_credits` is that ratio multiplied by `outstanding_issued_credits`, rounded half up to a whole credit. The pool's `pool_status` is `HEALTHY` when `balance_credits` is greater than or equal to `required_reserve_credits`, and `DEFICIT` otherwise.

Solvency gates issuance. An issuance whose buffer contribution would still leave `balance_credits` below `required_reserve_credits` is refused with `ERR_BUFFER_POOL_DEFICIT`, and a pool already in `DEFICIT` refuses every issuance outright. The two tests run in that order — the stored `pool_status` is consulted first, so a pool already in deficit reports the code without the prospective arithmetic being evaluated at all. Both sides of that prospective comparison are taken *after* the issuance would land: the prospective balance is the current `balance_credits` plus the batch's `buffer_credits`, and the requirement it is measured against is `min_reserve_ratio` multiplied by `outstanding_issued_credits` plus the batch's `issued_credits`, rounded half up to a whole credit. Because a reversal draw is what normally pushes the pool into deficit, and because a deficit freezes registry listings programme-wide (§3.8), the pool's health is the single most consequential number in the system.

The pool also owns the programme-wide serial counter. `next_serial_number` starts at 1 and advances by the `issued_credits` of every batch minted, and it never rolls back for any reason.

## 3. Business Logic & Workflows

### 3.1. Onboarding a Grower and Mapping the Land

Programme staff register a farm operator by supplying its registered `legal_name` — non-empty and at most 200 characters — its `operator_type`, which is one of `SOLE_PROPRIETOR`, `LLC`, `PARTNERSHIP`, `CORPORATION` or `TRUST`, a `tax_id` that must be non-empty because it appears on payment remittances — the programme records it as supplied and does not enforce uniqueness across growers, so two operators may carry the same `tax_id` — and a `mailing_state` given as exactly two upper-case letters. A newly registered grower has `status` of `ACTIVE`, a null `suspension_reason`, and all five running aggregates at zero as described in §2.11.

A grower's `status` is either `ACTIVE` or `SUSPENDED`, and only programme staff move it. Suspension for programme non-compliance requires a `suspension_reason`, which is stored on the grower, and it may only be applied to a grower that is currently `ACTIVE`. Suspension then cascades in two hops: first, every enrollment of that grower whose `status` is `ACTIVE` moves to `SUSPENDED`; second, *because* those enrollments moved, each of their fields whose `status` is `ENROLLED` moves to `SUSPENDED`. The grower's `total_enrolled_acres` is deliberately left untouched by both hops. Reinstatement is the mirror image and may only be applied to a grower that is currently `SUSPENDED`: `suspension_reason` is cleared back to null, every enrollment of that grower whose `status` is `SUSPENDED` returns to `ACTIVE`, and *because* those enrollments returned, each of their fields whose `status` is `SUSPENDED` returns to `ENROLLED`. Enrollments sitting in `EXITED`, `TERMINATED` or `REJECTED` are never touched by either direction, and again `total_enrolled_acres` does not move.

Land enters the programme as a **Field**, registered under a grower. The registration payload carries a `field_name`, which must be non-empty but need not be unique — two fields of one grower may share a name, since the boundary rule below, not the label, is what stops the same ground being mapped twice; the four integers `boundary_min_x`, `boundary_min_y`, `boundary_max_x` and `boundary_max_y` describing the mapped boundary rectangle in programme grid metres, where the west and south edges must be at least zero and each maximum must be strictly greater than its corresponding minimum; a `gross_acres` figure greater than zero, which is the grower's own declared acreage from the farm plan and is retained purely for reconciliation against the surveyed figure; a `soil_group` of `LOAM`, `CLAY` or `SAND`, which later drives the modelled baseline; and an optional `county_code`, a non-empty identifier used as registry listing metadata which stays null when it is not supplied. The field's `grower_id` is taken from the path rather than the body.

The surveyed acreage is derived, never supplied. Take the rectangle's width as the east edge minus the west edge, and its height as the north edge minus the south edge, both in whole grid metres. Multiply width by height to get the enclosed area in square grid units, divide that area by the 4000 square grid units that make up one programme acre, and round the quotient half up to two decimal places. That figure is stored as `mapped_acres`, and it — not `gross_acres` — is what every downstream acreage rule reads.

One grower may not map the same ground twice. A new rectangle is refused with `ERR_FIELD_BOUNDARY_OVERLAP` when its intersection with the rectangle of any existing field of the **same** grower whose `status` is not `SUSPENDED` has positive area. Zero-area intersections are explicitly permitted: two fields may share an edge exactly, and two fields may meet at a single corner. A one-grid-unit intrusion into the interior, however, is an overlap and is refused. Fields belonging to other growers are irrelevant to this check.

A field's `status` begins at `DRAFT` with a null `surveyor_reference`, and it may take the values `DRAFT`, `MAPPED`, `ENROLLED` and `SUSPENDED`. Confirming the survey — permitted only while the field is `DRAFT` and only while the owning grower is `ACTIVE` — stores the supplied `surveyor_reference` and advances the field from `DRAFT` to `MAPPED`, which is the only state from which the field may be enrolled. The remaining field transitions are all driven by other entities: `MAPPED → ENROLLED` when a baseline approval activates an enrollment on this field, `ENROLLED → SUSPENDED` and `SUSPENDED → ENROLLED` under grower suspension and reinstatement, and `ENROLLED → MAPPED` when an approved exit or a termination releases the field. That last release only fires when no *other* enrollment on the same field has `status` of `ACTIVE` or `SUSPENDED`; a field carrying a second live commitment stays `ENROLLED`.

### 3.2. Building the Evidence Base: Practice History and Published Methodologies

Additionality is a claim about the past, so the past has to be on file. Either programme staff or the grower may file a **PracticeHistory** record against a field, describing one crop year of one practice. Each record carries a `crop_year` between 2000 and 2100 inclusive, a `practice_code` of `COVER_CROP`, `REDUCED_TILLAGE` or `NUTRIENT_MANAGEMENT`, an `adopted` boolean saying whether that practice was in place on that field in that year, an `evidence_source` of `FARM_RECORD`, `EQUIPMENT_TELEMETRY`, `REMOTE_SENSING` or `ATTESTATION` recording the provenance of the documentation, an `acres` figure of at least zero — conventionally zero when `adopted` is false, though the server does not police that pairing and files whatever non-negative acreage it is given — and an optional `observed_emissions_per_acre` giving the measured or recorded counterfactual emissions in tCO2e per acre for that crop year, which must be at least zero and which, when omitted, is stored as zero rather than left null, so the field is never null on a filed record. The record's `field_id` comes from the path. As §2.5 states, these rows are immutable: they are the sole evidence base for additionality screening and for historical-data baselines, and nothing ever rewrites one.

Provenance matters twice over, in two different ways. Screening weights the four sources differently but admits all of them. Baseline establishment admits only two of them. That asymmetry is the single most commonly misread rule in this specification and it is spelled out in §3.3 and §3.4 respectively.

A **PracticeStandard** is a published, versioned methodology governing one eligible practice. Programme staff publish it with a `practice_code` naming the practice it governs and a `standard_version` integer of at least 1 that must be unique for that `practice_code`. The methodology then declares the parameters that govern every enrollment pinned to it:

- `additionality_lookback_years`, between 3 and 10 inclusive, is how many crop years before the commitment's first year are examined for prior adoption.
- `max_prior_adoption_pct`, between 0 and 100 at two decimal places, is the **inclusive** ceiling on weighted prior adoption above which the practice is judged business-as-usual.
- `min_documented_years`, at least 1, is how many distinct crop years inside the lookback window must carry at least one historical record.
- `min_adoption_years`, at least 1, is the shortest commitment the methodology will accept.
- `uncertainty_base_pct`, between 0 and 100 at two decimal places, is the base uncertainty before the per-year reduction for evidence depth.
- `sequestration_rate_per_acre`, greater than zero at four decimal places, is the modelled removals in tCO2e per acre per crop year used by model-based quantification.
- `modeled_baseline_rate_per_acre`, greater than zero at four decimal places, is the modelled counterfactual emissions in tCO2e per acre used by the modelled baseline.
- `buffer_base_pct`, between 0 and 25 at two decimal places, is the base buffer-pool contribution before risk adders.
- `telemetry_required` is a boolean defaulting to false. When true, it does two things: quantification demands at least one quality-passed equipment-telemetry observation, and additionality screening applies a penalty when the historical evidence base contains no telemetry at all.
- `effective_from` is an ISO 8601 calendar date, formatted as year, month and day, from which the standard may be pinned.

A published standard has `status` of `ACTIVE` and may become `RETIRED`, which is terminal. Retirement, permitted only from `ACTIVE`, closes the methodology to new enrollments and changes **no** existing enrollment: every enrollment already carries a pinned copy of the version it cited, and that pinning is precisely what protects work in flight.

Revision behaves quite differently and is the trap in this subsection. A revision is a self-loop, and like retirement it is available only from `ACTIVE` — revising a `RETIRED` standard is refused with `ERR_INVALID_STATE_TRANSITION`. The standard stays `ACTIVE`, its `standard_version` advances by exactly one, and every rate and threshold field on the row is left untouched. Staff supply a `revision_note` with the revision, which is stored on the row and returned with it; it reads null on a standard that has never been revised, and a further revision overwrites it. The publication uniqueness rule is not re-applied here: a revision advances the version number even when another standard already carries that `practice_code` and that version, so `ERR_DUPLICATE_STANDARD_VERSION` guards publication alone. No enrollment is rewritten, so an enrollment that pinned the earlier version now disagrees with its own standard — and from that moment its quantification and its issuance are refused with `ERR_STANDARD_VERSION_MISMATCH`, permanently. There is no re-pinning action anywhere in this API. The grower's only route back into the pipeline is to enroll afresh under the current version.

Citing a methodology is also gated on timing and standing. An enrollment may not cite a `RETIRED` standard, and it may not cite a standard whose `effective_from` falls in a calendar year later than the enrollment's `start_crop_year`; either fault is refused with `ERR_PRACTICE_STANDARD_RETIRED`, and the same check is re-applied at submission and resubmission, not only at creation.

### 3.3. Enrollment, Additionality Screening and Adjudication

An **Enrollment** is the three-way junction of a field, a methodology and a grower, and it is the entity every downstream artefact hangs from. Either programme staff or the grower creates one by naming the `field_id` of the field to be enrolled — which must be in `MAPPED` status at that moment — the `practice_standard_id` of the methodology to pin, a `commitment_years` count, a `start_crop_year`, an `enrolled_acres` figure and a `payment_model`. Three fields are copied at creation and never re-read afterwards: `grower_id` is derived from the referenced field's owning grower, `practice_code` is copied from the standard, and `pinned_standard_version` is copied from the standard's `standard_version`. The enrollment begins with `status` of `DRAFT` and `permanence_status` of `NOT_STARTED`, and its `prior_adoption_pct`, `additionality_score` and `documented_years` are all null until screening computes them. Every other narrative field starts empty as well — `screening_decision_admin_id`, `baseline_approval_admin_id`, `rejection_reason`, `missing_items`, `exit_reason`, `requested_exit_year`, `exit_fee_cents` and `terminated_effective_year` are all null — while the two running counters `accrued_payment_cents` and `credits_issued_total` start at 0.

Because creation carries no path parameter, ownership (rung 4) is resolved through the body-borne `field_id`. Whenever that value is a string naming an existing field, a `Grower` caller whose `X-User-ID` differs from that field's owning grower is refused with `ERR_RESOURCE_NOT_OWNED` *before* the request shape is examined at all, so a foreign field paired with a malformed payload reports the ownership error rather than `ERR_INVALID_REQUEST`. When the value is absent, is not a string, or names no field, that early hop cannot fire and the request proceeds to rung 5 and then to rung 6, where the two body foreign keys resolve in a fixed order — `field_id` first, reporting `ERR_FIELD_NOT_FOUND`, then `practice_standard_id`, reporting `ERR_PRACTICE_STANDARD_NOT_FOUND` — after which the ownership check is applied once more against the resolved field.

Commitment terms are checked as a group: `commitment_years` must be at least the pinned standard's `min_adoption_years` and at most 12, `enrolled_acres` must be greater than zero and must not exceed the field's surveyed `mapped_acres`, and any breach of those three reports `ERR_COMMITMENT_TERMS_INVALID`. `commitment_years` carries no bound of its own on rung 5 beyond having to be a JSON integer, so it is judged here and nowhere else: a zero or negative count reports `ERR_COMMITMENT_TERMS_INVALID` rather than a shape error. Separately, `start_crop_year` must equal either the current crop year or the current crop year plus one — the programme accepts an enrollment for the season under way or the season next, and nothing further out. That window is a request-shape rule rather than a terms rule: a year outside it reports `ERR_INVALID_REQUEST` on rung 5, and because it is settled on rung 5 it is decided before the body foreign keys are resolved, so a payload naming an unknown `field_id` together with a start year three seasons out reports the shape error and never reaches `ERR_FIELD_NOT_FOUND`.

Compensation terms are conditional and mutually exclusive. When `payment_model` is `PER_ACRE`, the payload must carry `per_acre_rate_cents`, a figure greater than zero at two decimal places giving cents per payable acre before band multipliers, and it must **omit** `per_credit_share_pct`. When `payment_model` is `PER_CREDIT`, the payload must carry `per_credit_share_pct`, between 0 and 100 at two decimal places, giving the grower's share of credit revenue, and it must **omit** `per_acre_rate_cents`. Supplying the wrong one, or both, is a malformed request. Whichever field is not supplied stays null on the stored enrollment.

Two exclusivity rules protect a field from being double-committed, and their order matters — it is the ladder's order rather than the order in which the rules read most naturally. The temporal rule goes first, on rung 17: commitment periods on one field may not overlap in time. Treat an enrollment's occupied interval as the half-open range of crop years beginning at its `start_crop_year` and ending immediately before `start_crop_year` plus `commitment_years` — so a five-year commitment starting in 2026 occupies 2026 through 2030 inclusive and releases the field for 2031. A new enrollment on the same field — whatever its `practice_code` — whose interval intersects the interval of a non-terminal enrollment is refused with `ERR_COMMITMENT_PERIOD_OVERLAP`, while an interval that begins exactly at the incumbent's end year is accepted because the incumbent's range excludes that year. This temporal rule is evaluated before the cooldown rule of §3.9. The duplicate rule waits until rung 22: at most one non-terminal enrollment may exist per field and `practice_code`, and a second reports `ERR_DUPLICATE_ENROLLMENT`. Because the overlap rung comes first, a repeat of the same practice on the same field whose years *also* intersect the incumbent's interval reports the overlap error, and `ERR_DUPLICATE_ENROLLMENT` surfaces only for a same-practice repeat whose interval sits clear of the incumbent's. For both rules an enrollment counts as non-terminal when its `status` is none of the three terminal values `REJECTED`, `EXITED` and `TERMINATED`.

Submission runs the screening arithmetic, so a submission that fails an additionality gate never reaches `SCREENING` at all. The three computed figures are written only on success: a refused submission leaves the enrollment in `DRAFT` with `prior_adoption_pct`, `additionality_score` and `documented_years` exactly as they were, and a refused resubmission likewise leaves the enrollment in `INFO_REQUESTED` with its previous figures and its `missing_items` list intact. Submission is available to programme staff and to the owning grower, requires the enrollment to be in `DRAFT`, requires the owning grower to be `ACTIVE`, and — when the caller is a `Grower` — requires that `X-User-ID` equal the enrollment's owning grower; a `ProgramAdmin` caller is not ownership-bound. On success the enrollment advances `DRAFT → SCREENING`.

**The additionality computation.** Let the lookback length be the pinned standard's `additionality_lookback_years`. The lookback window is the run of crop years beginning at the enrollment's `start_crop_year` minus that lookback length and ending at `start_crop_year` minus one, with **both ends included**; the `start_crop_year` itself is outside the window. The input set is every historical practice record whose `field_id` is the enrolled field, whose `practice_code` equals the enrollment's `practice_code`, and whose `crop_year` falls inside that window. Records for another field, records for another practice, and records for a crop year outside the window are excluded regardless of their `evidence_source`.

From that input set, three figures are derived:

- **Weighted prior adoption.** For each record whose `adopted` is true, multiply its `acres` by the weight of its `evidence_source` — 1.0 for `FARM_RECORD`, 1.0 for `EQUIPMENT_TELEMETRY`, 0.8 for `REMOTE_SENSING` and 0.5 for `ATTESTATION` — and add the products together. Divide that weighted acreage by the product of the field's `mapped_acres` and the lookback length, multiply the quotient by 100, and round half up to two decimal places. The result is `prior_adoption_pct`.
- **Evidence depth.** Count the distinct `crop_year` values appearing anywhere in the input set, counting a year whether its records say the practice was adopted or not adopted. The result is `documented_years`.
- **Telemetry gap.** A telemetry gap exists when the pinned standard's `telemetry_required` is true **and** no record in the input set carries an `evidence_source` of `EQUIPMENT_TELEMETRY`. Otherwise there is no gap.

The score is then assembled from a base of 100: subtract one and a half points for each percentage point of `prior_adoption_pct`; subtract a flat 20 points when a telemetry gap exists and nothing when it does not; and add two points for each documented year, counting at most as many documented years as the lookback length. Round that raw total half up to two decimal places, and only then clamp it into the range 0 to 100 inclusive — values below 0 become 0 and values above 100 become 100. The clamped result is `additionality_score`.

Two gates then decide whether the submission survives, and they cascade in a fixed order. The first gate requires `documented_years` to be at least the standard's `min_documented_years`; failure reports `ERR_INSUFFICIENT_PRACTICE_HISTORY`. Only if that gate passes does the second gate run, requiring `prior_adoption_pct` to be no greater than the standard's `max_prior_adoption_pct` — equality passes, because the ceiling is inclusive — and failure reports `ERR_ADDITIONALITY_FAILED`. Because the second gate consumes figures produced while evaluating the first, a field with too little documented history reports the history error even when its computed prior adoption would also have breached the ceiling.

Screening is a conversation, not a single decision. A `ProgramAdmin` reviewing an enrollment in `SCREENING` may return it to the grower with a `missing_items` array of documentation item labels — the array itself is required and each member must be a string that is not empty, though an array carrying no members at all is accepted — which is stored on the enrollment and moves it `SCREENING → INFO_REQUESTED`. The grower then files additional historical records and resubmits. Resubmission — available to programme staff and to the owning grower under the same ownership rule and the same requirement that the grower be `ACTIVE` — requires the enrollment to be in `INFO_REQUESTED`, re-runs the entire computation above against the historical records **as they now stand**, overwrites `prior_adoption_pct`, `additionality_score` and `documented_years` with the new figures, clears `missing_items` back to null, re-applies both additionality gates, and moves the enrollment `INFO_REQUESTED → SCREENING`. This cycle may repeat without limit.

Adjudication ends the screening phase. A `ProgramAdmin` records a `decision` on an enrollment in `SCREENING`, and in **both** branches the acting `X-User-ID` is recorded as `screening_decision_admin_id`. A `decision` of `ACCEPT` moves the enrollment `SCREENING → ACCEPTED` and does nothing else. A `decision` of `REJECT` requires a `rejection_reason` in the payload, stores it, and moves the enrollment `SCREENING → REJECTED`, which is terminal; the field stays `MAPPED` and no acreage is added anywhere. The recorded `screening_decision_admin_id` is what later bars that same administrator from approving this enrollment's baseline.

### 3.4. Establishing the Baseline and Activating the Commitment

An accepted enrollment still has no counterfactual, and without a counterfactual there is nothing to subtract removals from. A **Baseline** supplies it. Only a `ProgramAdmin` may propose one, against an enrollment identified by `enrollment_id` in the path, and the payload carries just two things: the `method`, which is either `HISTORICAL_DATA` or `MODELED`, and the `expected_enrollment_version` demanded by §2.8. A proposal starts with `status` of `PROPOSED`, a null `approved_by_admin_id` and a null `rejection_note`, and proposing one increments the parent enrollment's `version`. Proposal places no state precondition on the enrollment at all: the workflow expects an `ACCEPTED` enrollment, but that requirement is enforced at approval rather than at proposal, so a proposal filed against an enrollment still in `DRAFT` or `SCREENING`, or already `ACTIVE`, is accepted on its own terms and merely yields a baseline that cannot be approved from where its enrollment stands.

Both methods read the same set of historical records, and that set is **narrower** than the one screening used. Using the same lookback window as §3.3 — from `start_crop_year` minus the standard's `additionality_lookback_years` through `start_crop_year` minus one, both ends included — the qualifying records are those for the enrolled field and the enrolled `practice_code` whose `evidence_source` is either `FARM_RECORD` or `EQUIPMENT_TELEMETRY`. Remote-sensing and attestation records count toward `documented_years` during screening but are **not** admissible baseline evidence and drop out here. The count of distinct `crop_year` values among the qualifying records is stored as `qualifying_years`, and if that count is zero the proposal is refused with `ERR_INSUFFICIENT_PRACTICE_HISTORY`.

**Under the `HISTORICAL_DATA` method**, the grower's own farm records carry the counterfactual. Add together the `observed_emissions_per_acre` values of all qualifying records, divide that sum by `qualifying_years` — note that the divisor is the count of distinct years, not the count of records — and round half up to four decimal places; that is `historical_mean_rate`. Multiply the field's `mapped_acres` by `historical_mean_rate` and round half up to three decimal places to get `baseline_emissions_t`. For the uncertainty deduction, take the standard's `uncertainty_base_pct`, subtract 2.0 percentage points for each qualifying year, round half up to two decimal places, and then raise the result to 5.00 if it fell below that floor; the outcome is `uncertainty_pct`.

**Under the `MODELED` method**, the programme's own process model supplies the counterfactual and the observed values are ignored entirely — `historical_mean_rate` is stored as null. Multiply the field's `mapped_acres` by the standard's `modeled_baseline_rate_per_acre`, then by the soil factor for the field's `soil_group`, which is 1.00 for `LOAM`, 0.90 for `CLAY` and 1.15 for `SAND`, and round half up to three decimal places to get `baseline_emissions_t`. For the uncertainty deduction, take the standard's `uncertainty_base_pct`, add a flat 10.0 percentage-point modelling adder, subtract 1.5 percentage points for each qualifying year, round half up to two decimal places, and then raise the result to 12.00 if it fell below that floor; the outcome is `uncertainty_pct`. Note that the modelled route reads the qualifying record set only for its cardinality: `qualifying_years` still shapes the uncertainty, so a modelled baseline on a field with no admissible evidence is still refused.

Proposals interact in a very specific way. At most one `PROPOSED` baseline may exist per enrollment and `method`; a second proposal naming the **same** method is refused with `ERR_DUPLICATE_BASELINE`. A proposal naming the **other** method is legitimate, and when it lands, the incumbent `PROPOSED` baseline — necessarily of the other method — moves to `SUPERSEDED`, leaving the new row as the only `PROPOSED` baseline on the enrollment. The superseded row is never returned by the call that displaced it, so the filtered baseline list carrying `enrollment_id` is the only way to observe it. A baseline's `status` may be `PROPOSED`, `APPROVED`, `REJECTED` or `SUPERSEDED`, and the last three are all terminal.

Approval is the pivot of the whole programme, and it is the most consequential cascade in the system. A `ProgramAdmin` may approve a baseline only while it is `PROPOSED`, only while its enrollment is in `ACCEPTED`, and only when the acting `X-User-ID` differs from that enrollment's `screening_decision_admin_id`; the same administrator repeating both steps is refused with `ERR_SEGREGATION_OF_DUTIES`. On success the baseline's `status` moves `PROPOSED → APPROVED` and the acting identifier is recorded as `approved_by_admin_id`. Then three hops fire in order. First, the enrollment moves `ACCEPTED → ACTIVE`, its `permanence_status` moves `NOT_STARTED → IN_COMPLIANCE`, and the acting identifier is also recorded on the enrollment as `baseline_approval_admin_id`. Second, *because* the enrollment became `ACTIVE`, its field moves `MAPPED → ENROLLED`. Third, *because* the field became `ENROLLED`, the grower's `total_enrolled_acres` increases by that field's `mapped_acres`. The second and third hops are conditional on the field actually being `MAPPED` at that moment. A field can legitimately carry a second live commitment — a later, non-overlapping enrollment on the same land — and when that second baseline is approved the field is already `ENROLLED`, so neither hop fires and the acreage is not counted a second time; the enrollment still becomes `ACTIVE` exactly as described.

Rejection does none of that. A `ProgramAdmin` rejecting a `PROPOSED` baseline supplies a `rejection_note`, which is stored, and the baseline moves `PROPOSED → REJECTED`. No cascade fires: the enrollment stays `ACCEPTED` so that a fresh baseline can be proposed, the field stays `MAPPED`, and no acreage is added to the grower.

### 3.5. Field Data Collection and Quality Control

Once a commitment is `ACTIVE`, evidence of what actually happened on the ground arrives as **DataPacket** rows, filed against an enrollment by programme staff or by the owning grower. Each packet describes one crop year through one channel and carries a `crop_year` between 2000 and 2100 inclusive, a `source` of `FARM_RECORD`, `EQUIPMENT_TELEMETRY` or `REMOTE_SENSING`, a `reported_acres` figure greater than zero stating how many acres the packet reports as under the practice, a `coverage_pct` between 0 and 100 stating what percentage of the enrolled acres the packet actually covers, and an optional `measured_value` giving the observed stock change in tCO2e per acre for those reported acres, which must be at least zero, is read only by measurement-based quantification, and — like the practice record's `observed_emissions_per_acre` — is stored as 0.0000 rather than left null when it is omitted. The packet's `enrollment_id` comes from the path, and a new packet arrives with a null `flag_reason` and a `correction_count` of 0. At most one non-rejected packet may exist for a given enrollment, `crop_year` and `source`; a second reports `ERR_DUPLICATE_DATA_PACKET`. Filing is not itself gated on the commitment's state: the enrollment's `status` is never examined when a packet is filed, so a packet may be filed against an enrollment in any status, and it is only the *correction* action below that demands an `ACTIVE` enrollment.

A packet has **two entirely independent status axes**, and confusing them is the classic implementation error here. The quality axis, `qc_status`, takes the values `PENDING`, `PASSED`, `FLAGGED` and `REJECTED`; it starts at `PENDING` and moves only through explicit quality-control actions. The coverage axis, `completeness_status`, takes the values `PARTIAL` and `COMPLETE`; it is *derived* from `coverage_pct` on arrival and on every correction, and it is never touched by any quality-control action. A packet may perfectly well be `PASSED` and `PARTIAL`, or `PENDING` and already `COMPLETE`. A packet is `COMPLETE` when its `coverage_pct` is greater than or equal to 85.00, and `PARTIAL` otherwise.

**The quality score.** On arrival, and again on every correction, the packet's `qc_score` is computed from three ratios. The completeness ratio is `coverage_pct` divided by 100, rounded half up to four decimal places, then capped at 1.0000. The acre-gap ratio is the absolute difference between the packet's `reported_acres` and the enrollment's `enrolled_acres`, divided by the enrollment's `enrolled_acres`, rounded half up to four decimal places, then capped at 1.0000. The plausibility ratio is 1 minus the acre-gap ratio, rounded half up to four decimal places. The source weight is 0.6 for `FARM_RECORD`, 1.0 for `EQUIPMENT_TELEMETRY` and 0.8 for `REMOTE_SENSING`. Weight the completeness ratio at 0.5, the plausibility ratio at 0.3 and the source weight at 0.2, add the three weighted terms together, multiply the sum by 100, and round half up to two decimal places. That is `qc_score`, and it lies between 0 and 100. No sibling packet participates in the calculation — only the packet's own `coverage_pct`, `reported_acres` and `source`, plus the enrollment's `enrolled_acres`.

Quality control belongs to programme staff alone. A `ProgramAdmin` records a `decision` against a packet whose `qc_status` is `PENDING`. A `decision` of `PASS` requires the packet's `qc_score` to be greater than or equal to 70.00 — equality passes — and moves `qc_status` from `PENDING` to `PASSED`; a score below that floor is refused with `ERR_QC_SCORE_BELOW_THRESHOLD`. A `decision` of `FLAG` requires a `flag_reason` in the payload, stores it, and moves `qc_status` from `PENDING` to `FLAGGED`. Under both decisions the `completeness_status` axis is neither recomputed nor changed.

A flagged packet can be repaired. Programme staff or the owning grower may correct one whose `qc_status` is `FLAGGED`, provided the owning enrollment is `ACTIVE` and — when the caller is a `Grower` — provided `X-User-ID` matches the enrollment's owning grower; a `ProgramAdmin` caller is not ownership-bound. The correction payload may supply any of `reported_acres`, `coverage_pct` and `measured_value`, and each supplied value overwrites the stored one; each is optional, and a correction that supplies none of the three is still a valid correction that rescores the packet against unchanged figures and returns it to the queue. The `qc_score` is then recomputed from the corrected figures, the `completeness_status` axis is re-derived from the new `coverage_pct` and may move in either direction, `correction_count` increases by one, `flag_reason` is cleared to null, and `qc_status` returns from `FLAGGED` to `PENDING`. This `PENDING → FLAGGED → PENDING` cycle may repeat as often as the evidence demands.

A flagged packet can also be abandoned. A `ProgramAdmin` may reject one whose `qc_status` is `FLAGGED`, optionally recording a `flag_reason` — supplied, it overwrites the reason recorded at flagging; omitted, it leaves that earlier reason standing rather than clearing it — which moves `qc_status` from `FLAGGED` to `REJECTED`. That state is terminal and the packet is permanently excluded from every quantification input set thereafter.

### 3.6. Quantifying Net Removals and Third-Party Verification

A **QuantificationRun** turns one crop year of one active enrollment into a tonnage figure. Only a `ProgramAdmin` creates one, naming the `enrollment_id` being quantified, the `baseline_id` of the approved baseline the run deducts against, the `crop_year` the run covers, the `method` — either `MODEL` or `MEASUREMENT` — and the `expected_enrollment_version` demanded by §2.8. The `crop_year` must lie inside the enrollment's commitment window — from `start_crop_year` through `start_crop_year` plus `commitment_years` minus one, both inclusive — and must not be later than the current crop year. Either breach is a request-shape failure reported as `ERR_INVALID_REQUEST`, and because the test needs the parent row in hand it is evaluated after both body foreign keys have resolved (the `enrollment_id` first, then the `baseline_id`) but before the enrollment's state, its version and its methodology are examined at all. The enrollment must be `ACTIVE`, its `pinned_standard_version` must still match the referenced standard's `standard_version`, the named baseline must belong to that same enrollment (otherwise `ERR_BASELINE_ENROLLMENT_MISMATCH`) and must be in `APPROVED` status (otherwise `ERR_BASELINE_NOT_APPROVED`). At most one non-rejected run may exist per enrollment and `crop_year`; a second reports `ERR_DUPLICATE_QUANTIFICATION_RUN`. A new run starts with `status` of `DRAFT` and `revision_count` of 0, and creating it increments the parent enrollment's `version`.

**The input set.** Collect every data packet whose `enrollment_id` is the run's enrollment, whose `crop_year` equals the run's `crop_year`, and whose `qc_status` is `PASSED`. Packets that are `PENDING`, `FLAGGED` or `REJECTED` are excluded, and a packet's `completeness_status` plays no part in this filter — a `PARTIAL` packet that passed quality control is admitted exactly like a `COMPLETE` one. If that collection is empty, the run is refused with `ERR_NO_QUALIFYING_DATA`. If the pinned standard's `telemetry_required` is true and no packet in the collection has a `source` of `EQUIPMENT_TELEMETRY`, the run is refused with `ERR_TELEMETRY_EVIDENCE_REQUIRED`.

**Under the `MODEL` method**, every quality-passed packet is included. Add together the `reported_acres` of the included packets and take the smaller of that sum and the enrollment's `enrolled_acres`; the result, at two decimal places, is `verified_acres`. Add together the `coverage_pct` of the included packets, divide by how many were included, and round half up to two decimal places to get `mean_coverage_pct`. Divide `mean_coverage_pct` by 100, round half up to four decimal places, and cap the result at 1.0000; that is `adoption_factor`. Multiply the pinned standard's `sequestration_rate_per_acre` by `verified_acres` and then by `adoption_factor`, rounding half up to three decimal places, to get `gross_removals_t`. For the deduction, add 5.00 percentage points to the governing baseline's `uncertainty_pct`, divide the sum by 100, multiply by `gross_removals_t`, and round half up to three decimal places; that is `uncertainty_deduction_t`. The baseline's own tonnage never enters the model arithmetic, and `sampling_uncertainty_pct` is stored as null.

**Under the `MEASUREMENT` method**, the included packets are only those quality-passed packets whose `source` is `EQUIPMENT_TELEMETRY` or `REMOTE_SENSING`; farm-record packets are inadmissible as measurement evidence and drop out. If that narrowed set is empty, the run is refused with `ERR_NO_QUALIFYING_DATA` — the same code as the wider emptiness check. `verified_acres` and `mean_coverage_pct` are computed exactly as above but over the narrowed set. `mean_coverage_pct` must then be at least 60.00, and a lower figure is refused with `ERR_COVERAGE_BELOW_MINIMUM`. For each included packet multiply its `measured_value` by its `reported_acres`, add the products together, and round half up to three decimal places to get the measured stock change; subtract the baseline's `baseline_emissions_t` from it, round half up to three decimal places, and floor the result at 0.000 to get `gross_removals_t`. For the deduction, subtract one quarter of `mean_coverage_pct` from 30.0, round half up to two decimal places, and raise the result to 5.00 if it fell below that floor; that is `sampling_uncertainty_pct`. Multiply `gross_removals_t` by `sampling_uncertainty_pct`, divide by 100, and round half up to three decimal places to get `uncertainty_deduction_t`. Here `adoption_factor` is stored as null.

Both methods then converge. Subtract `uncertainty_deduction_t` from `gross_removals_t`, round half up to three decimal places, and floor the result at 0.000; that is `net_removals_t`. `packet_count` is the number of packets the selected method actually included, which under `MEASUREMENT` is the narrowed count rather than the count of all passed packets. Because the two methods read overlapping but different packet sets and combine them with entirely different arithmetic, the very same evidence base yields two different `net_removals_t` figures depending on the `method` chosen.

A run's `status` may be `DRAFT`, `SUBMITTED`, `VERIFIED`, `REJECTED` or `ISSUED`, the last being terminal. The tonnage figures are computed once, at creation, and are never re-derived on read: a `DRAFT` run does not track later packet corrections or later quality-control decisions, so the figures are already frozen before submission ever happens. Submitting a run for third-party verification is permitted only from `DRAFT` and moves it `DRAFT → SUBMITTED`, carrying those frozen figures forward untouched. A run driven to `REJECTED` by an adverse opinion may be reopened by a `ProgramAdmin`: revision moves it `REJECTED → DRAFT`, increases `revision_count` by one, and re-runs the whole computation above against the quality-passed packet set as it now stands — the one recomputation in a run's life. The revision payload may optionally carry a fresh `method`, which overwrites the stored one before the recomputation runs; omitted, the run keeps the method it already had. Revision re-examines nothing but the run's own `status`: neither the enrollment's state, nor its `version`, nor the methodology version is re-checked. The recomputation itself is still subject to the data-sufficiency rules above, so a revision whose quality-passed packet set has since emptied out is refused with `ERR_NO_QUALIFYING_DATA` and the run stays `REJECTED`.

#### Commissioning and Conducting Verification

Verification is performed by an accredited body outside the programme. A `ProgramAdmin` accredits a **VerificationBody** with a non-empty `name`, a non-empty `accreditation_id`, which the programme records as supplied and does not check for uniqueness — as with a grower's `tax_id`, two bodies may carry the same one — an `accredited_practices` array — non-empty, drawn from `COVER_CROP`, `REDUCED_TILLAGE` and `NUTRIENT_MANAGEMENT` — naming which practices the body may verify, and a `max_concurrent_visits` integer of at least 1 capping how many pending site-visit windows may cover any single calendar day. A body's `status` is `ACCREDITED` or `SUSPENDED` and starts `ACCREDITED`.

Suspending a body, permitted only while it is `ACCREDITED`, does **not** disturb history: opinions already issued stand, no verification row is modified, and pending verifications keep their assigned windows. What suspension does is refuse every subsequent verification write naming that body — assignment, arrival recording, opinion issuance and resampling alike — with `ERR_VERIFICATION_BODY_SUSPENDED`, for as long as the suspension lasts. Reinstatement, permitted only while the body is `SUSPENDED`, returns it to `ACCREDITED` and makes its pending verifications actionable again with their original site-visit windows intact.

A `ProgramAdmin` assigns a submitted run to a body by creating a **Verification** naming the `quantification_run_id`, the `verification_body_id`, a `sample_pct` giving the share of enrolled acres to be physically sampled — greater than zero, no more than 100, at two decimal places, and at least 5.00 or else `ERR_SAMPLE_TOO_SMALL` — and a closed site-visit window given as two ISO 8601 calendar dates, `site_visit_start` for the first visit day and `site_visit_end` for the last, both inclusive, with the end not earlier than the start — a window closing before it opens is a rung-5 shape failure reported as `ERR_INVALID_REQUEST`. The body's `accredited_practices` must contain the enrollment's `practice_code`, or the assignment is refused with `ERR_PRACTICE_NOT_ACCREDITED`. At most one verification with a pending opinion may exist per run; a second reports `ERR_DUPLICATE_VERIFICATION`. The two body foreign keys resolve on rung 6 in a fixed order — `quantification_run_id` first, reporting `ERR_QUANTIFICATION_RUN_NOT_FOUND`, then `verification_body_id`, reporting `ERR_VERIFICATION_BODY_NOT_FOUND`. A new verification starts with `opinion` of `PENDING`, `resample_count` of 0 and `material_discrepancy_pct` of 0.00, and both `restated_removals_t` and `findings_note` null.

**Workload capacity.** A body cannot be in two places at once beyond its declared ceiling. Counting only that body's verifications whose `opinion` is still `PENDING`, count how many have a closed visit interval running from `site_visit_start` through `site_visit_end` inclusive that intersects the requested interval; two windows that merely share an endpoint day do intersect. That count must be strictly less than the body's `max_concurrent_visits`, or the request is refused with `ERR_VERIFIER_CAPACITY_EXCEEDED`. Each individual visit is perfectly admissible on its own; it is the aggregate overlap that fails. The same check applies both when a verification is first assigned and whenever it is reopened for resampling.

A `Verifier` records arrival on site, which resets `site_visit_start` to the current logical clock instant and leaves the `opinion` axis untouched at `PENDING`. That instant is written exactly as the clock was positioned — the same string a clock read would echo back, not re-rendered at the millisecond width of §2.5 — and it replaces the plain calendar date the field was given at commissioning, so the field is thereafter an instant rather than a date and the workload rule above reads only its leading `YYYY-MM-DD`. Acting as a `Verifier` requires that `X-User-ID` equal the `verification_body_id` recorded on the addressed verification.

**Issuing the opinion.** A `Verifier` opines on a verification whose `opinion` is `PENDING`, while its body is `ACCREDITED`, supplying an `opinion` of `POSITIVE`, `QUALIFIED` or `ADVERSE`, optionally a `restated_removals_t` figure at three decimal places giving the net removals the verifier believes correct, and optionally a `findings_note` recording the findings text, which — like every other non-empty string field — is refused when it is supplied as an empty or whitespace-only string. The `material_discrepancy_pct` is derived first: if `restated_removals_t` was omitted it is 0.00; otherwise, if the run's frozen `net_removals_t` is 0.000, it is 100.00 when the restated figure is greater than zero and 0.00 when the restated figure is zero; otherwise it is the absolute difference between `restated_removals_t` and the run's `net_removals_t`, divided by the run's `net_removals_t`, multiplied by 100 and rounded half up to two decimal places.

The tolerance gate applies to `POSITIVE` opinions only. A `POSITIVE` opinion requires `material_discrepancy_pct` to be no greater than 5.00 — equality passes — and a larger gap is refused with `ERR_MATERIAL_DISCREPANCY_EXCEEDED`. `QUALIFIED` and `ADVERSE` opinions are never gated on the discrepancy; they record it and proceed.

Each opinion carries its own cascade, and the three branches diverge sharply. A `POSITIVE` opinion moves the verification `PENDING → POSITIVE`, which is terminal, and moves the run `SUBMITTED → VERIFIED`, unlocking issuance. An `ADVERSE` opinion moves the verification `PENDING → ADVERSE`, also terminal, and moves the run `SUBMITTED → REJECTED`, from which the run can only re-enter the pipeline through revision. A `QUALIFIED` opinion moves the verification `PENDING → QUALIFIED` and leaves the run exactly where it was, still `SUBMITTED`, with issuance still blocked pending a resample. All three branches store `material_discrepancy_pct` and `findings_note`.

Resampling closes the qualified loop. A `Verifier` may reopen a verification whose `opinion` is `QUALIFIED` by supplying a fresh `sample_pct`, `site_visit_start` and `site_visit_end`, which overwrite the stored values. The new window is re-checked against the body's concurrency ceiling, `resample_count` increases by one, `restated_removals_t` and `findings_note` are cleared to null, `material_discrepancy_pct` is reset to 0.00, and the `opinion` returns `QUALIFIED → PENDING`. This cycle may repeat.

### 3.7. Credit Issuance and the Buffer Split

Minting credits is the programme's whole point, and it is the most heavily guarded action in the API. Only a `ProgramAdmin` may issue, and only from a run whose `status` is `VERIFIED`. Four further preconditions apply, and they are decided in the ladder's order rather than in the order that reads most naturally. First come two more rung-9 state tests, both reporting `ERR_INVALID_STATE_TRANSITION`: no verification of that run may carry an `opinion` of `ADVERSE`, and then the owning enrollment must be `ACTIVE`. Next, the enrollment's `pinned_standard_version` must still equal the referenced standard's current `standard_version`, or the request is refused with `ERR_STANDARD_VERSION_MISMATCH`. Last of all the buffer pool is consulted: its `pool_status` must be `HEALTHY` and its reserve must survive the contribution, or the request is refused with `ERR_BUFFER_POOL_DEFICIT` as §2.12 describes — so a deficit pool is reported only once every other guard has passed. The payload carries a `vintage_year`, which must equal the run's `crop_year` and is stamped on the credits for the registry, and optionally a `supersedes_batch_id` pointing at a cancelled batch this issuance replaces. A `vintage_year` that does not match the run's `crop_year` is a request-shape failure reported as `ERR_INVALID_REQUEST`, settled on rung 5 ahead of every precondition above. An optional `registry_account_ref` may accompany the request and is retained on the batch; it does not list anything, because the new batch always starts unlisted. The `supersedes_batch_id`, by contrast, is resolved late: it is looked up only after the run's state, the adverse-opinion guard, the enrollment's state and the methodology-version check have all passed, so an unresolvable batch reference on a run that is not `VERIFIED` reports the state error rather than `ERR_CREDIT_BATCH_NOT_FOUND`. Once resolved it must name a batch belonging to the **same** enrollment, or the request is refused with `ERR_SUPERSEDED_BATCH_MISMATCH`; issuance does not test that predecessor's own `issuance_status`, since the guard that insists the predecessor be `CANCELLED` lives on registry listing (§3.8).

Issuance produces a **CreditBatch**, whose `quantification_run_id` is taken from the addressed run and whose `enrollment_id` is copied from that run. Like a data packet, a batch carries two independent axes: `issuance_status`, which is `ISSUED` or `CANCELLED` and starts `ISSUED`, and `registry_status`, which is `UNLISTED`, `LISTED`, `SUSPENDED` or `RETIRED` and starts `UNLISTED`. Its `registry_account_ref`, `retirement_beneficiary` and `cancellation_reason` are null unless the corresponding action has recorded one.

**The split, in a pinned evaluation order.** The tier basis looks circular — the risk tier scales the buffer percentage, the buffer percentage decides how many credits are actually issued, and issued credits feed the grower's cumulative issuance, which is what tiers are keyed on. The following order breaks the loop and must not be re-entered.

1. `gross_credits` is the run's frozen `net_removals_t` reduced to the largest integer that does not exceed it, since one credit is one tonne of CO2 equivalent.
2. The tier basis is the grower's `lifetime_credits_issued` **as it stands before this issuance** plus `gross_credits`. It uses `gross_credits`, not `issued_credits`.
3. The `risk_tier` is `LOW` when the tier basis is at least 5000 credits, `MEDIUM` when it is at least 1000 but below 5000, and `HIGH` otherwise. The tier adder is 2.0 percentage points for `LOW`, 4.0 for `MEDIUM` and 8.0 for `HIGH`. A further reversal-history adder of 5.0 percentage points applies when the grower's `reversal_count` is at least 1, and nothing when it is zero. Add the pinned standard's `buffer_base_pct`, the tier adder and the reversal-history adder together, round half up to two decimal places, and cap the result at 25.00; that is `buffer_pct`.
4. `buffer_credits` is `gross_credits` multiplied by `buffer_pct`, divided by 100, and rounded **up** to the next whole credit.
5. `issued_credits` is `gross_credits` minus `buffer_credits`, an exact integer subtraction. The invariant `gross_credits` equals `buffer_credits` plus `issued_credits` holds always.
6. `serial_start` is the buffer pool's current `next_serial_number`, and `serial_end` is `serial_start` plus `issued_credits` minus one, both inclusive. The pool's `next_serial_number` then advances by `issued_credits`, and the grower's `lifetime_credits_issued` increases by `issued_credits`. A verified run whose `net_removals_t` floors to zero is still issuable and still mints a batch: `gross_credits`, `buffer_credits` and `issued_credits` all come out at zero, the serial range is empty with `serial_end` reading exactly one below `serial_start`, and the pool's cursor does not advance.

Step 6 never re-triggers step 2 for this batch: the tier decision was made against the pre-issuance figure and stands.

The rest of the issuance cascade fires in order. The run moves `VERIFIED → ISSUED`, which is terminal. The buffer pool's `contributed_total` and `balance_credits` each increase by the batch's `buffer_credits`, its `outstanding_issued_credits` increases by the batch's `issued_credits`, and its `required_reserve_credits` and `pool_status` are re-derived from the new figures. The enrollment's `credits_issued_total` increases by `issued_credits` and its `version` increments. And then, *only* when the enrollment's `payment_model` is `PER_CREDIT`, a grower payment is accrued automatically against the freshly minted batch, and *because* that payment exists the enrollment's `accrued_payment_cents` increases by that payment's `net_amount_cents`; the arithmetic is in §3.9. A batch minted this way is not returned by the issuing call, and neither is the payment; both are discovered through the filtered list endpoints described in §2.6. What the issuing call returns is the addressed run itself, now `ISSUED`, with HTTP 200.

### 3.8. Registry Custody, Reversals and the Permanence Obligation

Registry custody belongs to the `RegistryOfficer` and to nobody else. Listing a batch on the public registry requires its `registry_status` to be `UNLISTED` and its `issuance_status` to be `ISSUED`, stores the supplied `registry_account_ref` — required here, unlike the optional one §3.7 lets an issuance retain, and overwriting whatever that issuance retained — and moves the registry axis `UNLISTED → LISTED`. The issuance axis is not touched. A re-issued batch — one carrying a `supersedes_batch_id` — starts `UNLISTED` like any other and follows the same edge, but with one extra guard: the batch named by `supersedes_batch_id` must already have `issuance_status` of `CANCELLED`, and listing a superseding batch while its predecessor is still `ISSUED` is refused with `ERR_SUPERSEDED_BATCH_NOT_CANCELLED`. The predecessor itself is untouched by the successor's listing.

Retiring a batch, permitted only while its `registry_status` is `LISTED` and its `issuance_status` is `ISSUED`, stores the supplied `retirement_beneficiary` and moves the registry axis `LISTED → RETIRED`, which is terminal. Retirement permanently removes the credits from circulation, so the buffer pool's `outstanding_issued_credits` decreases by the batch's `issued_credits` and its `required_reserve_credits` and `pool_status` are both re-derived from the new figures — which means a retirement large enough to shrink the reserve requirement below the pool's balance lifts the pool out of `DEFICIT` on its own; the batch's own buffer contribution, however, stays in the pool permanently. Retirement is refused with `ERR_UNRESOLVED_REVERSAL` while any reversal event whose `status` is `REPORTED` or `ASSESSED` references the batch.

Cancelling a batch is the compensating action for an issuance, and it requires the `expected_credit_batch_version` of §2.8. It is permitted only while `issuance_status` is `ISSUED` and only while `registry_status` is not `RETIRED`. The supplied `cancellation_reason` is stored, the issuance axis moves `ISSUED → CANCELLED`, and the registry axis is left exactly where it was. Three compensation hops follow. First, the buffer pool's `released_total` increases by the batch's `buffer_credits`, its `balance_credits` and `contributed_total` each decrease by the same quantity, and its `outstanding_issued_credits` decreases by the batch's `issued_credits`, after which `required_reserve_credits` and `pool_status` are re-derived. Second, the grower's `lifetime_credits_issued` and the enrollment's `credits_issued_total` each decrease by `issued_credits`. Third, every grower payment whose `credit_batch_id` names this batch and whose `status` is `ACCRUED` moves to `VOID`, and the enrollment's `accrued_payment_cents` decreases by each such payment's `net_amount_cents`. The pool's `next_serial_number` is **not** rolled back: serial numbers are never reused.

**Reporting a reversal.** When sequestered carbon is lost, a `ProgramAdmin` reports a **ReversalEvent** against an issued batch, naming the `credit_batch_id`, a `reversal_type` of `INTENTIONAL` or `UNINTENTIONAL`, an `affected_acres` figure greater than zero and no greater than the enrollment's `enrolled_acres`, and a `detected_crop_year` that must not be earlier than the batch's `vintage_year`. Those last two bounds both read the parent rows, so they are request-shape failures reported as `ERR_INVALID_REQUEST` and evaluated after the body-borne `credit_batch_id` has resolved but before the batch's own state is examined. That state test comes last: the named batch's `issuance_status` must be `ISSUED`, or the report is refused with `ERR_INVALID_STATE_TRANSITION`. Only the issuance axis is consulted, so a batch already retired on the registry — whose `issuance_status` is still `ISSUED` — may perfectly well receive a reversal report. The event's `enrollment_id` is copied from the batch, its `status` starts at `REPORTED`, and the acting `X-User-ID` is recorded as `reported_by_admin_id`. Reporting computes nothing: `affected_credits`, `buffer_draw_credits`, `unbacked_credits` and `grower_clawback_cents` all remain at zero until assessment, and `assessed_by_admin_id` and `resolution_note` remain null.

**Assessment** is where the damage is priced, and it is the largest cascade in the system. A `ProgramAdmin` assesses an event whose `status` is `REPORTED`, and the acting `X-User-ID` must differ from the recorded `reported_by_admin_id` or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. Those are the only two preconditions: assessment re-examines neither the batch's `issuance_status` nor the owning enrollment's state, so an event reported against a batch that has since been cancelled remains assessable and still prices the loss against that batch's `issued_credits`. The arithmetic runs first. Multiply the batch's `issued_credits` by the event's `affected_acres`, divide by the enrollment's `enrolled_acres`, round the quotient **up** to a whole credit, and then take the smaller of that figure and the batch's `issued_credits`; the result is `affected_credits`. For an `UNINTENTIONAL` reversal — fire, drought, flood — `buffer_draw_credits` is the smaller of the buffer pool's current `balance_credits` and `affected_credits`, and never less than zero, so a pool whose balance has been driven negative by a cancellation draws nothing rather than a negative quantity. For an `INTENTIONAL` reversal — the grower ploughed the field or abandoned the practice — the pool is not touched at all and `buffer_draw_credits` is zero. `unbacked_credits` is `affected_credits` minus `buffer_draw_credits`. The clawback share is the enrollment's `per_credit_share_pct` when its `payment_model` is `PER_CREDIT`, and a full 100.00 percent otherwise; multiply `unbacked_credits` by the programme credit price of 2750 cents, multiply by the clawback share, divide by 100, and round half up to whole cents to get `grower_clawback_cents`.

The cascade then proceeds in seven hops. The event's `status` moves `REPORTED → ASSESSED`, the acting identifier is recorded as `assessed_by_admin_id`, and the grower's `reversal_count` increases by one. Second, the buffer pool's `drawn_total` increases by `buffer_draw_credits`, its `balance_credits` decreases by the same quantity, and its `unbacked_reversal_credits` increases by `unbacked_credits`. Third, if the resulting `balance_credits` has fallen below `required_reserve_credits`, the pool's `pool_status` becomes `DEFICIT`. Fourth — and this is the programme-wide blast radius — when the pool is in `DEFICIT`, **every** batch anywhere in the programme whose `registry_status` is `LISTED` moves to `SUSPENDED`, not merely this grower's. Fifth, *because* those batches became registry-suspended, each of their owning enrollments moves `permanence_status` to `BREACHED`. Sixth, *because* those enrollments were breached, every grower payment of theirs whose `status` is `ACCRUED` moves to `CLAWED_BACK` and the owning enrollment's `accrued_payment_cents` decreases by that payment's `net_amount_cents`. The grower's `outstanding_clawback_cents` then increases by this reversal event's `grower_clawback_cents` — booked once per reversal event, and **not** once per clawed-back payment, and booked on *every* assessment rather than only on the ones that suspended something, so a reversal that breached no permanence and clawed back no cash still books its liability in full. Seventh, when a grower's `outstanding_clawback_cents` has thereby reached 250000 cents or more, that grower moves `ACTIVE → SUSPENDED` under a server-generated `suspension_reason` naming the breached clawback threshold, which itself cascades to that grower's active enrollments and their enrolled fields exactly as §3.1 describes. A grower already `SUSPENDED` when the threshold is crossed is left as it stands, its existing `suspension_reason` intact.

For an `INTENTIONAL` reversal the divergent branch applies: the pool is not consulted at all, so not one of its counters moves — no `drawn_total`, no `balance_credits`, no `unbacked_reversal_credits` even though `unbacked_credits` on the event is the whole of `affected_credits`, and therefore no pool-status change and no programme-wide freeze — but the reversal's own batch moves `registry_status` from `LISTED` directly to `SUSPENDED`, and hops five through seven follow from there in exactly the same way. Should that batch not be `LISTED` at the time, nothing is suspended and hops five and six find nothing to do, while hops one and seven still run in full.

**Resolution** closes an assessed event once remediation is documented. A `ProgramAdmin` resolves an event whose `status` is `ASSESSED`, supplying a `resolution_note`, which is stored, and the `status` moves `ASSESSED → RESOLVED`, which is terminal. Every batch whose `registry_status` is `SUSPENDED` — including the batch this reversal event was reported against — returns to `LISTED`, but only once the pool's `pool_status` is `HEALTHY` again; while the pool is still in `DEFICIT`, resolution closes the event and leaves the suspensions standing. Each affected enrollment returns from `BREACHED` to `IN_COMPLIANCE` once no suspended batch remains on it. Cash is not returned: payments already moved to `CLAWED_BACK` stay clawed back, because the clawback is permanent. Nor is the liability: the grower's `outstanding_clawback_cents` is not reduced by a resolution, and a grower that the clawback threshold suspended stays suspended — reinstatement remains the explicit administrative act of §3.1.

An enrollment's `permanence_status` is therefore fully independent of its `status`. It is `NOT_STARTED` before activation, `IN_COMPLIANCE` from baseline approval onward, and `BREACHED` for as long as any batch of that enrollment sits registry-suspended. One breach arrives from outside the registry altogether: terminating an unserved commitment (§3.9) sets `BREACHED` directly, with no batch involved, and only the restoration of a suspended batch of that same enrollment could ever lift it.

### 3.9. Grower Compensation, Contract Exit and Termination

A **GrowerPayment** is the cash side of the ledger. Its `enrollment_id` names the enrollment it settles, its `crop_year` names the crop year it covers, and its `payment_model` is copied from the enrollment at accrual. There are exactly two ways a payment comes into existence, and they are mutually exclusive. A `PER_ACRE` enrollment is accrued once per crop year by an explicit `ProgramAdmin` action supplying the `crop_year`; the resulting payment has `credit_batch_id` null and `payable_acres` populated. The only state gate on that endpoint is the `payment_model` itself — invoking it on a `PER_CREDIT` enrollment is refused with `ERR_INVALID_STATE_TRANSITION` — and nothing else about the enrollment is examined: its `status` may be anything at all, the owning grower's standing is not consulted, and the supplied `crop_year` need only be a crop year in the 2000-to-2100 range rather than a year inside the commitment window. The call returns the newly accrued payment itself, with HTTP 201. A `PER_CREDIT` enrollment never uses that endpoint at all — its payments are minted automatically by the issuance cascade of §3.7, with `credit_batch_id` naming the batch that triggered them, `crop_year` copied from that batch's `vintage_year` and `payable_acres` left null. A second `ACCRUED` payment for the same enrollment, `crop_year` and `payment_model` is refused with `ERR_DUPLICATE_PAYMENT`; payments that have since moved out of `ACCRUED` do not block a new accrual.

**The holdback, common to both models.** The elapsed years are the current crop year minus the enrollment's `start_crop_year`, and the remaining years are its `commitment_years` minus the elapsed years. The `holdback_pct` is 20.00 when at least 3 years remain, 10.00 when at least 1 but fewer than 3 remain, and 0.00 otherwise — including when the remaining years are zero or negative, because a commitment that is fully served has nothing left to secure.

**The `PER_ACRE` waterfall.** The `payable_acres` figure is the enrollment's `enrolled_acres`. It is sliced into three bands: the first band is the acreage up to 500.00 acres, the second is the acreage above 500.00 up to 2000.00 acres, and the third is everything above 2000.00 acres — each band taken as zero when the acreage does not reach it. Each band is priced by multiplying its acreage by the enrollment's `per_acre_rate_cents` and then by that band's multiplier: 1.000 for the first band, 0.925 for the second and 0.850 for the third. **The rounding order is pinned:** round each of the three band lines to whole cents, half up, *first*, and *then* add the three rounded lines together to get `gross_amount_cents`. Adding the three raw products and rounding the single total gives a different answer by a cent or two and is wrong.

**The `PER_CREDIT` share.** Multiply the freshly minted batch's `issued_credits` by the enrollment's `per_credit_share_pct`, divide by 100, multiply by the programme credit price of 2750 cents, and round half up to whole cents; that is `gross_amount_cents`.

From there both models converge. `holdback_cents` is `gross_amount_cents` multiplied by `holdback_pct`, divided by 100, rounded half up to whole cents, and `net_amount_cents` is `gross_amount_cents` minus `holdback_cents` — an exact integer subtraction. The payment's `status` starts at `ACCRUED`, its `paid_at` is null, and the owning enrollment's `accrued_payment_cents` increases by `net_amount_cents`.

A payment has four states. `ACCRUED` is the initial state. `PAID` is reached by an explicit `ProgramAdmin` settlement, and is terminal. `CLAWED_BACK` is reached only by the reversal cascade of §3.8, and is terminal. `VOID` is reached either by the batch-cancellation compensation of §3.8 or by the termination branch below, and is terminal. Settlement requires that the payment's `status` is `ACCRUED`, that the owning enrollment's `permanence_status` is not `BREACHED`, and that the grower's `status` is `ACTIVE` — three rung-9 tests, decided in that order and all three reporting `ERR_INVALID_STATE_TRANSITION`; it is additionally refused with `ERR_CLAWBACK_OUTSTANDING` while the grower's `outstanding_clawback_cents` is above zero. On success the `status` moves `ACCRUED → PAID`, `paid_at` is stamped with the logical clock's `current_utc` exactly as that clock was positioned rather than re-rendered at the millisecond width of §2.5, and the grower's `net_paid_cents` increases by `net_amount_cents`. The enrollment's `accrued_payment_cents` is deliberately left where it stood, because settling an accrual does not retire it from that running figure.

**Requesting an exit.** A grower who wants out of a commitment, or a `ProgramAdmin` acting for one, files an exit request naming an `exit_reason` of `VOLUNTARY`, `LAND_SALE` or `FORCE_MAJEURE` and a `requested_exit_year`. The enrollment's `status` must be `ACTIVE` and the grower's `status` must be `ACTIVE`. Two independent temporal clauses both carry `ERR_EXIT_WINDOW_NOT_OPEN`: the `requested_exit_year` must be at least the current crop year plus one, so a mid-year request naming the current crop year is refused; and the current crop year minus the enrollment's `start_crop_year` must be at least one, so an enrollment cannot file an exit inside its own first crop year. On success the `status` moves `ACTIVE → EXIT_REQUESTED`, the `exit_reason` and `requested_exit_year` are stored, and the `version` increments. A `rejection_reason` left over from an earlier denial is not cleared by the fresh request: it stays on the row until some later denial overwrites it.

**Adjudicating an exit** is a three-way fork, and the branches have deliberately divergent side effects. A `ProgramAdmin` supplies a `decision` and, on a denial, a `rejection_reason`.

- **`APPROVE` with the commitment fully served** — the elapsed years are at least the `commitment_years`. The `status` moves `EXIT_REQUESTED → EXITED`, which is terminal, the `exit_fee_cents` settles at 0, and the `permanence_status` stays `IN_COMPLIANCE`. Every payment of this enrollment still sitting at `ACCRUED` moves to `PAID` as a final settlement, and each one settles exactly as an explicit settlement would: its `paid_at` is stamped with the logical clock and the grower's `net_paid_cents` rises by its `net_amount_cents`. The enrollment's `accrued_payment_cents` is left exactly where it stood, because settling an accrual does not retire it from that running figure.
- **`APPROVE` with the commitment not fully served.** The `status` moves `EXIT_REQUESTED → TERMINATED`, which is terminal, the exit fee below is charged into `exit_fee_cents`, the `permanence_status` moves to `BREACHED`, and the `terminated_effective_year` is set to the current crop year, opening the cooldown described below. Every payment still sitting at `ACCRUED` moves to `VOID` instead of `PAID` — no cash moves in either direction, and the enrollment's `accrued_payment_cents` decreases by each voided payment's `net_amount_cents`.
- **`DENY`.** The `status` returns `EXIT_REQUESTED → ACTIVE`, the supplied `rejection_reason` is stored, and both `exit_reason` and `requested_exit_year` are cleared back to null. This is a cycle, not a terminus: the grower may file a fresh exit request later, and the cleared fields make that request start from a blank slate.

Both approval branches share one cascade hop: the enrolled field moves `ENROLLED → MAPPED`, and *because* it left the enrolled set the grower's `total_enrolled_acres` decreases by that field's `mapped_acres`. Every branch increments the enrollment's `version`.

**The exit fee.** The served ratio is the elapsed years divided by the `commitment_years`, capped at 1. That quotient carries no declared scale and is not rounded: it is taken at full precision straight into the multiplication below, so the only rounding anywhere in this formula is the final half-up to whole cents. The settled figure is the sum of `net_amount_cents` over this enrollment's payments whose `status` is `PAID` — and only those; `ACCRUED`, `CLAWED_BACK` and `VOID` rows are excluded, which means the same voiding hop that runs on termination cannot retroactively change the fee, because voided rows were never in the sum. If the `exit_reason` is `FORCE_MAJEURE` the `exit_fee_cents` is 0, no matter how little of the commitment was served. Otherwise, if the elapsed years are at least the `commitment_years` the `exit_fee_cents` is 0. Otherwise multiply the settled figure by one minus the served ratio and round half up to whole cents.

**The practice cooldown.** A termination leaves scorched earth on the land it covered. After an enrollment reaches `TERMINATED`, the same field may not be re-enrolled in the **same** `practice_code` until two crop years have elapsed past the `terminated_effective_year`: a new enrollment's `start_crop_year` must be at least the `terminated_effective_year` plus 2, or creation is refused with `ERR_PRACTICE_COOLDOWN_ACTIVE`. A *different* `practice_code` on the same field is unaffected, and so is the same practice on a different field.

**The reconciliation read.** A `ProgramAdmin` or a `RegistryOfficer` may ask for a grower's ledger summary, a computed read that derives every figure from the rows that exist at read time rather than copying the stored aggregates, so that the two can be compared. It returns the `grower_id`; the `lifetime_credits_issued` exactly as stored on the grower, cancellations having already been subtracted from it by the cancel compensation; the `buffer_contributed_credits`, being the sum of `buffer_credits` over this grower's batches whose `issuance_status` is `ISSUED`, so cancelled batches drop out; the `accrued_total_cents`, `paid_total_cents` and `clawed_back_total_cents`, being the sums of `net_amount_cents` over this grower's payments whose `status` is `ACCRUED`, `PAID` and `CLAWED_BACK` respectively; and the `outstanding_clawback_cents` exactly as stored on the grower. The `paid_total_cents` figure must always equal the grower's stored `net_paid_cents`. Payments in `VOID` are counted nowhere.

## 4. Endpoint Definitions

Creation endpoints return HTTP 201 with the created resource in `data`; every other successful call returns HTTP 200 with the affected resource, or with an array of resources for a list endpoint. Every path below is relative to the service root, and a trailing slash is tolerated on any of them — `/growers/` addresses the same endpoint as `/growers`. Path parameters are resolved left to right as described in §2.6, and the validation ladder of §2.10 governs the order in which failures are reported.

Routing runs ahead of the whole ladder, authentication included. A request whose path matches no endpoint in this table is refused with `ERR_NOT_FOUND` (404) and a request whose path matches but whose method does not is refused with `ERR_METHOD_NOT_ALLOWED` (405) — in both cases regardless of whether identity headers were sent, so an unauthenticated call to a misspelled path reports the routing failure rather than `ERR_UNAUTHENTICATED`. Should the server fault unexpectedly it answers `ERR_INTERNAL` (500) in the same error envelope.
