# Executive Compensation & Say-On-Pay API — Product Requirements Document

## 1. Introduction

A public company's compensation committee operates under an unforgiving calendar. Between the close of one fiscal year and the annual meeting of the next, the committee must assemble a defensible peer group, size the chief executive's target pay against it, set goal curves that pay out neither too easily nor impossibly, certify the year's results, draft a Compensation Discussion & Analysis that survives counsel review, absorb whatever the proxy advisors publish about it, and then live with the shareholder vote. Every one of those steps depends numerically on the one before it, and any of them can be reopened by an event nobody planned for — a peer that delists, a market-data refresh that moves a size ratio, a failed vote, or an accounting restatement that retroactively invalidates a payout the company has already made.

This document specifies the API that runs that calendar. The system is mounted under `/exec-comp` and is deliberately built as a compliance-and-audit engine rather than a calculator: it records who did what, refuses to let one person occupy two seats of the same control, and re-derives every downstream number the moment an upstream input moves. The recurring theme is *supersession* — when a benchmark input changes, the benchmark that depended on it stops being a fact and becomes a stale claim, and the system's job is to say so loudly instead of quietly serving a number nobody can defend to a regulator.

The reader should expect three kinds of rule. There are **derivations** — medians, benchmark variants, payout factors, realized and realizable pay, concern scores — each of which is pinned to an exact evaluation and rounding order because two defensible orders produce two different cents. There are **gates** — state preconditions, referential guards, uniqueness constraints and segregation-of-duties checks — each with a designated error identifier and a designated place in a global precedence ladder. And there are **cascades** — the multi-level propagations that fan out from a single write, most of which terminate by invalidating a proxy-advisor screen and, through it, sending a legally cleared disclosure section back to its author.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request, without exception, must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. If either header is absent, or if `X-User-ID` is present but blank or whitespace-only, or if `X-User-Role` is not one of the five recognised role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the acting role does not appear in the authorised-role list of the endpoint being called, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The five roles are `CompConsultant`, `CompCommitteeChair`, `SecuritiesCounsel`, `InvestorRelationsLead` and `NamedExecutiveOfficer`, and the split between them is a segregation-of-duties model rather than a seniority model. The `CompConsultant` is the independent adviser: it registers companies and officers, refreshes market data, builds and screens peer groups, opens pay programs, defines metrics, submits fiscal-year achievements and administers awards — and approves nothing. The `CompCommitteeChair` is the only approver: it approves peer groups and program designs, orders goal adjustments, certifies metric results and vote outcomes, and orders and executes clawback recovery. The `SecuritiesCounsel` owns the disclosure pipeline — legal clearance and filing of every section — and also declares and analyses accounting restatements. The `InvestorRelationsLead` runs proxy-advisor screening and the shareholder outreach programme. The `NamedExecutiveOfficer` is the officer themselves, present in the system only to inspect their own awards and determinations and to acknowledge a recovery notice served on them.

For four of the five roles, identity is opaque. When `X-User-Role` is `CompConsultant`, `CompCommitteeChair`, `SecuritiesCounsel` or `InvestorRelationsLead`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it where a transition asks for it — as `approved_by_user_id` on a `PeerGroup` or a `PayProgram`, as `authored_by_user_id` or `cleared_by_user_id` on a disclosure section, as `adjusted_by_user_id` or `certified_by_user_id` on a metric — and it compares recorded identifiers against each other for segregation-of-duties purposes, but it never compares them to any entity's `id`. `NamedExecutiveOfficer` is the exception: when `X-User-Role` is `NamedExecutiveOfficer`, `X-User-ID` is the `id` of the acting `Executive` row, and ownership checks on any resource that references an `Executive` compare the resource's foreign-key field to `X-User-ID`. Concretely, an officer may read awards only where the award's `executive_id` equals their `X-User-ID`, and may read or acknowledge a clawback determination only where the determination's award has that same `executive_id`. Any other read or action by that role is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a collection accepts two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be lower than 1, and may not exceed 100. `offset` is the number of rows to skip and defaults to 0. Requests supplying values outside those ranges — or a `limit` or `offset` that is not an integer at all — are malformed requests and are rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint says otherwise, list results are ordered by the row's creation timestamp, ascending, with ties on that timestamp — which a logical clock that only moves when an operator moves it makes routine — broken by the order in which the rows were inserted. The response `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the size of the filtered result set before the window is applied.

### 2.4. Common Resource Properties and the Logical Clock

Every entity in this system — companies, executives, peer groups and their memberships, pay programs, incentive metrics, payout awards, disclosure sections, proxy-advisor screens, outreach engagements, restatement events and clawback determinations — carries the same four system-managed properties:

- **`id`** (string): a server-minted UUID. It carries no type prefix of any kind.
- **`created_at`** (string): the ISO 8601 UTC instant at which the row was first written, with three fractional digits (for example `2026-08-01T00:00:00.000Z`).
- **`updated_at`** (string): the ISO 8601 UTC instant of the most recent mutation of the row, in the same format.
- **`version`** (integer): a counter that starts at 1 on creation and increments by exactly one on every mutation of that row. Recomputing a derived field counts as a mutation: when a cascade rewrites a program's benchmark numbers or an award's realizable value, that row's `version` increments and its `updated_at` is refreshed just as if a client had written to it directly. A row reached only as a cascade level moves only when at least one stored value actually changes, though: a recomputation that reproduces the figures the row already held writes nothing and leaves both `version` and `updated_at` alone, whereas the row an endpoint is specified as advancing directly always increments. And however many cascade levels write to one row inside a single request, that row's `version` advances by exactly one for the whole request.

Time in this system is logical, not wall-clock. The server starts cold at the fixed instant `2026-08-01T00:00:00Z` and never falls back to the host clock, so every window, quiet period, lookback and freshness stamp is deterministic and reproducible. An operator-facing capability sets that clock: it takes a single field `to_iso8601` and returns the resulting `current_utc`, and every subsequent read of "the current logical time" — including `market_data_updated_at`, `screened_at`, `held_at`, `filed_at`, `noticed_at`, `acknowledged_at` and `recovered_at` — resolves to the instant last supplied. All four operator roles may drive the clock; `NamedExecutiveOfficer` may not.

### 2.5. Monetary Precision, Ratios and Rounding Discipline

Two precision families exist. **Money and percentages** — every field whose name ends in `_usd` or `_pct`, and every payout factor and score — are stored and returned as numbers rounded to exactly 2 decimal places using the round-half-up convention. **Ratios** — `revenue_ratio`, `market_cap_ratio`, `benchmark_ratio`, the size-adjustment factor used by the benchmark computation and the posture ratio used to band a program against its benchmark — are rounded to 4 decimal places, also half-up. Instant comparisons (windows, quiet periods, lookbacks) are made at second granularity.

Rounding *order* is part of the contract, not an implementation detail, because two defensible orders differ by a cent and a cent is a test failure. Three orders are pinned explicitly and are restated where each formula is described in §3: the size-adjustment factor is rounded to 4 decimal places **before** it multiplies a peer's disclosed compensation, and only then is the product rounded to 2 decimal places; each metric's weighted contribution to a vehicle's payout factor is rounded to 2 decimal places **before** the contributions are summed, and never the other way round; and the annual-incentive cap is applied **after** the uncapped amount has been rounded, so the cap compares two already-rounded figures.

### 2.6. Segregation of Duties

Three pairs of steps in the compensation calendar may never be performed by the same `X-User-ID`, and in all three cases the second step is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). First, the user recorded as a disclosure section's `authored_by_user_id` may not legally clear that same section. Second, the chair recorded as an incentive metric's `adjusted_by_user_id` may not certify the result measured against the goal it moved. Third, the user recorded as a clawback determination's `acknowledged_by_user_id` may not execute that determination's recovery. The three checks are independent of the role check: passing `ERR_ROLE_NOT_PERMITTED` does not exempt an identifier from the conflict test, and the conflict test is evaluated on the recorded identifier, not on the role.

### 2.7. Stale-Version Guards on Composition Writes

Three writes in this system change the composition of something other clients are already reading, and each of them is protected by an optimistic-concurrency guard on the parent row's `version`. In each case the guard field is a **required** input, not an optional one, and it must carry the client's last observed `version` of the parent.

Adding a peer to a peer group requires `expected_peer_group_version` to equal that `PeerGroup` row's current `version`; if it does not, the add is rejected with `ERR_STALE_PEER_GROUP_VERSION` (HTTP 412), because a membership change legitimately supersedes the group's screened medians and benchmark values and a writer holding an older view would be composing a peer set against numbers that no longer exist. Reallocating pay-mix points requires `expected_pay_program_version` to equal that `PayProgram` row's current `version`, failing with `ERR_STALE_PAY_PROGRAM_VERSION` (HTTP 412), because each reallocation supersedes the prior mix and a delta derived from a stale mix would shift different components than the client intended. Ordering a goal adjustment requires `expected_incentive_metric_version` to equal that `IncentiveMetric` row's current `version`, failing with `ERR_STALE_INCENTIVE_METRIC_VERSION` (HTTP 412), because an adjustment supersedes the locked goal curve and a stale view would measure the policy limit against a target that has already moved.

No other endpoint accepts a version field. Operations not named above are not version-guarded and must not require one; body fields an endpoint does not declare — a stray version guard among them — are ignored rather than rejected.

### 2.8. Cascade Propagation and Screen Freshness

A single accepted write in this system routinely mutates many rows, and the propagation is specified as an ordered chain rather than a set. Each level of a cascade is caused by the level above it, each mutated row increments its own `version` and refreshes its own `updated_at`, and no level is skipped because the client did not ask for it.

The chain that recurs most often terminates in the disclosure pipeline. Whenever anything the proxy advisors care about changes on a pay program — its `realized_pay_total_usd`, `realizable_pay_total_usd`, `pay_percentile_rank`, `degree_of_alignment`, `alignment_status`, `target_tdc_usd`, `performance_based_pct`, `outreach_coverage_pct` or `vote_status` is recomputed to a new value — every `ProxyAdvisorScreen` of that program that is currently `SCREENED` moves to `STALE`. A screen going `STALE` keeps its last computed `concern_score`, `concern_level` and `recommendation` verbatim: the numbers are preserved as a historical record, only their claim to currency is withdrawn. And because a legally cleared disclosure cannot rest on a withdrawn screen, a screen's move to `STALE` in turn sends every `LEGAL_CLEARED` section of that program back to `DRAFTING`, incrementing its `revision_round` and clearing its `cleared_by_user_id`.

Upstream, the same discipline applies to benchmarks. A market-data refresh recomputes the size-band fit of every affected membership; a membership that falls out of band having previously been inside it, or a membership that is excluded outright, pulls a `SCREENED` peer group back to `DRAFT` and clears every median and benchmark value on it; and a peer group that loses its benchmark clears the benchmark-derived fields of every `DRAFT` pay program that references it. Groups that have reached `APPROVED` never revert, and their composition can no longer be changed at all.

### 2.9. Path Resolution Order

Many paths in this API address a child through its parent, and identifiers are resolved strictly left to right. The first identifier in the path that does not resolve to an existing row determines the 404 that is returned, and no rule further right is evaluated. A request naming a non-existent company therefore fails with `ERR_COMPANY_NOT_FOUND` before any question about the sub-resource is asked; the same discipline yields `ERR_PEER_GROUP_NOT_FOUND`, `ERR_PEER_GROUP_MEMBER_NOT_FOUND`, `ERR_EXECUTIVE_NOT_FOUND`, `ERR_PAY_PROGRAM_NOT_FOUND`, `ERR_INCENTIVE_METRIC_NOT_FOUND`, `ERR_PAYOUT_AWARD_NOT_FOUND`, `ERR_CDA_DRAFT_NOT_FOUND`, `ERR_SCREEN_NOT_FOUND`, `ERR_ENGAGEMENT_NOT_FOUND`, `ERR_RESTATEMENT_EVENT_NOT_FOUND` and `ERR_DETERMINATION_NOT_FOUND` for their respective row types. Foreign keys supplied in a request body are resolved after every path identifier has resolved, and among themselves in the order the endpoint's input list declares them: `peer_company_id`, `peer_group_id`, `ceo_executive_id`, `executive_id` and `payout_award_id` each raise the not-found error of the entity they point at.

### 2.10. Validation Precedence

When several rules could reject the same request, the outcome is determined by a single global ladder. Lower numbers are evaluated first and the first failure is the response; a rule further down the ladder never masks a rule above it. The ladder is:

1. Authentication of the two headers — `ERR_UNAUTHENTICATED`.
2. Role authorisation against the endpoint's role list — `ERR_ROLE_NOT_PERMITTED`.
3. Path-identifier resolution, left to right — the not-found error of the first unresolved row.
4. Body foreign-key resolution, in declaration order — the not-found error of the first unresolved reference. This applies to pay-group creation, peer addition, program creation and award granting. A reference that is present but of the wrong JSON type, or that names no row, raises that entity's not-found error; a reference that is absent or explicitly null is left to step 6 instead.
5. Officer ownership: a `NamedExecutiveOfficer` may only read or act on rows whose `executive_id`, directly or via the determination's award, equals the acting `X-User-ID` — `ERR_NOT_RESOURCE_OWNER`. This applies to the two award reads, the two determination reads and the acknowledgement action.
6. Request well-formedness on every mutating endpoint — `ERR_INVALID_REQUEST`. This covers missing required fields, enum values outside their declared sets, numbers that are negative where the field's semantics forbid it, a reallocation whose `from_component` equals its `to_component`, `points` that is not strictly positive, non-integer vote tallies or tallies whose `votes_for` and `votes_against` sum to zero, `window_end` at or before `window_start`, `lookback_end` at or before `lookback_start`, and any instant that is not parseable ISO 8601. It also covers a free-text field longer than its ceiling — five hundred characters for `exclusion_reason` and `reversal_reason`, two thousand for `feedback_summary` and `result_adjustment_reason`.
7. The three stale-version guards of §2.7 — `ERR_STALE_PEER_GROUP_VERSION`, `ERR_STALE_PAY_PROGRAM_VERSION`, `ERR_STALE_INCENTIVE_METRIC_VERSION`.
8. Segregation of duties on legal clearance, result certification and recovery execution — `ERR_SEGREGATION_OF_DUTIES`.
9. Peer-group mutability: `DRAFT` for a member add and for screening, `DRAFT` or `SCREENED` for a member exclusion, `APPROVED` never — `ERR_PEER_GROUP_NOT_MUTABLE`.
10. Peer-group screened-before-approval — `ERR_PEER_GROUP_NOT_SCREENED`.
11. Program design mutability, required by mix reallocation, metric definition and committee approval — `ERR_PROGRAM_NOT_MUTABLE`.
12. Metric state, required by adjustment, result submission and certification — `ERR_METRIC_STATE_INVALID`.
13. Award state before settlement — `ERR_AWARD_NOT_GRANTED`.
14. Disclosure-section state, required by submit-for-review, revision request, legal clearance and filing — `ERR_CDA_STATE_INVALID`.
15. Engagement state, required by scheduling and by holding — `ERR_ENGAGEMENT_STATE_INVALID`.
16. Program disclosed before a vote can be certified — `ERR_PROGRAM_NOT_DISCLOSED`.
17. Vote not yet certified, required both by vote certification and by reopening a filed section — `ERR_VOTE_ALREADY_CERTIFIED`.
18. Vote failed before remediation — `ERR_VOTE_NOT_FAILED`.
19. Restatement-event state, required by analysis and by recovery ordering — `ERR_EVENT_STATE_INVALID`.
20. Determination state, required by acknowledgement, recovery and reversal — `ERR_DETERMINATION_STATE_INVALID`.
21. The pre-meeting quiet period, which outranks every scheduling-hygiene rule below it — `ERR_QUIET_PERIOD_ENGAGEMENT`.
22. Acknowledgement before recovery — `ERR_DETERMINATION_NOT_ACKNOWLEDGED`.
23. A delisted candidate peer — `ERR_PEER_COMPANY_DELISTED`.
24. A candidate peer that is the group's own issuer — `ERR_PEER_IS_ISSUER`.
25. The program's peer group approved before program approval; this referential gate outranks the fiscal cap below — `ERR_PEER_GROUP_NOT_APPROVED`.
26. A current `ISS` screen before legal clearance — `ERR_ISS_SCREEN_NOT_CURRENT`.
27. Metric certification before an award may vest — `ERR_METRIC_NOT_CERTIFIED`.
28. The `CD_AND_A` section filed before a vote may be certified — `ERR_CDA_NOT_FILED`.
29. Ticker and issuer uniqueness at company registration — `ERR_ISSUER_ALREADY_EXISTS`.
30. One membership per peer per group, counting excluded rows — `ERR_PEER_ALREADY_IN_GROUP`.
31. Metric uniqueness per program, code and vehicle — `ERR_METRIC_ALREADY_DEFINED`.
32. Section uniqueness per program and section code — `ERR_CDA_SECTION_ALREADY_EXISTS`.
33. Screen uniqueness per program and advisor — `ERR_SCREEN_ALREADY_EXISTS`.
34. An engagement window that starts in the past — `ERR_ENGAGEMENT_WINDOW_IN_PAST`.
35. A same-investor window overlap — `ERR_OUTREACH_WINDOW_OVERLAP`.
36. A colliding restatement lookback period — `ERR_LOOKBACK_PERIOD_COLLISION`.
37. A meeting date that is not in the future at program creation — `ERR_MEETING_DATE_NOT_FUTURE`.
38. A pay mix that does not total exactly 100.00 — `ERR_PAY_MIX_MUST_TOTAL_100`.
39. A mix component outside its permitted range — `ERR_MIX_COMPONENT_OUT_OF_BOUNDS`.
40. A goal curve that is not strictly monotonic in the metric's direction — `ERR_GOAL_CURVE_NOT_MONOTONIC`.
41. Metric weights that do not sum to exactly 100.00 at committee approval — `ERR_METRIC_WEIGHTS_NOT_100`.
42. A candidate peer outside the size bands without a qualifying inclusion rationale — `ERR_PEER_OUTSIDE_SIZE_BAND`.
43. Screening an empty peer group — `ERR_PEER_GROUP_EMPTY`.
44. Incomplete tabular disclosure or an under-length narrative at legal clearance — `ERR_CDA_TABLES_INCOMPLETE`.
45. A goal adjustment beyond the policy limit — `ERR_ADJUSTMENT_EXCEEDS_POLICY_LIMIT`.
46. Target compensation above the benchmark cap at committee approval — `ERR_TDC_EXCEEDS_BENCHMARK_CAP`.
47. Insufficient outreach coverage at remediation — `ERR_OUTREACH_COVERAGE_INSUFFICIENT`.

Note the two precedence pairs the ladder deliberately fixes. The quiet-period blackout at step 21 is evaluated before the same-investor overlap at step 35, so an engagement that both intrudes on the blackout and collides with an existing slot reports the blackout. And the peer-group approval gate at step 25 is evaluated before the benchmark cap at step 46, so a program whose group is still unapproved reports the referential failure even when its target compensation would also have breached the cap.

### 2.11. Status Codes

Creating a new row returns `201 Created`. Every other successful operation — including the state-advancing actions that dominate this API, and including reads — returns `200 OK`.

## 3. Business Logic & Workflows

### 3.1. The Issuer, its Peers and its Officers

Everything in this system hangs off a registry of public companies, and companies serve two purposes at once: exactly one of them is the filing issuer whose program is being designed, and the rest are candidate peers against which that issuer is measured. A `CompConsultant` registers a company with its `legal_name` (one to one hundred and twenty characters, not blank), its `ticker` (one to five uppercase letters), the `is_issuer` flag, a `gics_sector` drawn from `TECH`, `INDUSTRIALS`, `HEALTHCARE`, `FINANCIALS`, `CONSUMER` or `ENERGY`, and four market data points: trailing-twelve-month `revenue_usd` and `market_cap_usd` (both strictly positive), the current `share_price_usd` (strictly positive), and `ceo_tdc_usd`, the last disclosed chief-executive total direct compensation, which may be zero but not negative. `is_issuer` defaults to false when the field is omitted, and a `listing_status` may be supplied at registration but defaults to `ACTIVE`. Tickers are unique across the registry and at most one company may carry `is_issuer` as true; a second attempt at either is rejected with `ERR_ISSUER_ALREADY_EXISTS`. Registration stamps `market_data_updated_at` with the current logical time.

Market data goes stale faster than anything else in the compensation calendar, so refreshing it is a first-class operation rather than a generic update. A refresh may carry any subset of `revenue_usd`, `market_cap_usd`, `share_price_usd`, `ceo_tdc_usd` and `listing_status`, but it must carry at least one of them — a refresh with none of the five is malformed and is rejected with `ERR_INVALID_REQUEST`. Whatever is supplied overwrites the stored value, `market_data_updated_at` moves to the current logical time, and the company's `version` increments. A refresh that carries `listing_status` as `DELISTED` moves the company from `ACTIVE` to `DELISTED`; that transition is terminal, and only a company still in `ACTIVE` may be refreshed at all — a refresh aimed at a company already `DELISTED` is a malformed request and is rejected with `ERR_INVALID_REQUEST`. Delisting deliberately does *not* remove the company from peer groups that already reference it — existing memberships survive untouched, and only the creation of *new* memberships against a delisted peer is blocked, with `ERR_PEER_COMPANY_DELISTED`. A refresh that does not carry `listing_status` leaves the company in `ACTIVE`; it is a self-transition, and it triggers exactly the same downstream work.

That downstream work is a four-part cascade, and it is the widest fan-out in the system. First, for every `ACCEPTED` membership whose peer is this company *or* whose owning group treats this company as its issuer, and whose owning group is in `DRAFT` or `SCREENED`, the size-band fit of that membership is recomputed — `revenue_ratio`, `market_cap_ratio` and `in_size_band` are all rewritten. Second, caused by the first: any group in `SCREENED` that owns a recomputed membership whose `in_size_band` has flipped to false falls back from `SCREENED` to `DRAFT`, clearing its medians and both benchmark variants. Third, caused by the second: every pay program referencing such a group whose design is still `DRAFT` has `benchmark_ratio`, `lti_multiple`, `lti_target_usd` and `target_tdc_usd` set to null and `benchmark_posture` set back to `UNBENCHMARKED`. Fourth, independently of the peer-group chain, a refresh that carries `share_price_usd` at all — whether or not the supplied price differs from the stored one — re-marks every award of the issuer's programs that is still `GRANTED`, rewriting each award's `realizable_value_usd` and then re-deriving each of those programs' `realized_pay_total_usd`, `realizable_pay_total_usd`, `pay_percentile_rank`, `degree_of_alignment` and `alignment_status`, any movement in which flips that program's `SCREENED` screens to `STALE` and, through them, its `LEGAL_CLEARED` sections back to `DRAFTING`.

Officers are registered against their employing company, which the created row records as its `company_id`. Each officer carries a `full_name` (one to one hundred and twenty characters), a `role_title` drawn from `CEO`, `CFO`, `COO`, `CHRO` and `GC`, an `is_neo` flag marking the officer as a named executive officer for disclosure purposes (defaulting to true when omitted), an annualized `base_salary_usd` that must be strictly positive, and an `sti_target_pct` between 0.00 and 400.00 expressing the annual-incentive target as a percentage of that salary. Those last two fields anchor every cash payout formula in the system, which is why officer registration is a consultant operation performed long before any program exists.

### 3.2. Constructing, Screening and Approving the Peer Group

A peer group is opened in `DRAFT` by a `CompConsultant`, who names the `issuer_company_id` it benchmarks — which must be a company whose `is_issuer` is true, on pain of `ERR_INVALID_REQUEST` — the `fiscal_year` it supports (an integer between 2020 and 2035 inclusive), and the `benchmark_basis` that will later decide which of two benchmark variants drives the target. `benchmark_basis` is either `RAW_MEDIAN` or `SIZE_ADJUSTED`, and defaults to `RAW_MEDIAN`. A freshly opened group has `accepted_member_count` of 0 and null medians.

Peers are added one at a time, each add naming a `peer_company_id`, an `inclusion_reason` drawn from `SIZE_MATCH`, `INDUSTRY_MATCH`, `BUSINESS_MODEL_ANALOG` and `TALENT_COMPETITOR`, and the `expected_peer_group_version` guard described in §2.7. A group only accepts new peers while it is in `DRAFT`; attempting an add against a `SCREENED` or `APPROVED` group is rejected with `ERR_PEER_GROUP_NOT_MUTABLE`. A company may not appear twice in the same group even if its earlier membership has since been excluded — the second attempt is `ERR_PEER_ALREADY_IN_GROUP` — and a group's own issuer may never be added as a peer of itself, which is `ERR_PEER_IS_ISSUER`.

Each accepted membership is immediately sized against the issuer. The peer's revenue divided by the issuer's revenue, rounded half-up to four decimal places, is stored as `revenue_ratio`; the peer's market capitalisation divided by the issuer's market capitalisation, rounded the same way, is stored as `market_cap_ratio`. The membership's `in_size_band` is true only when the revenue ratio lies between 0.5 and 2.0 and the market-capitalisation ratio lies between 0.25 and 4.0. Both bands are **closed**: a ratio exactly equal to a bound is inside the band. A candidate that fails either band is still admissible, but only on a documented rationale — an `inclusion_reason` of `BUSINESS_MODEL_ANALOG` or `TALENT_COMPETITOR` permits an out-of-band peer, whereas `SIZE_MATCH` or `INDUSTRY_MATCH` does not and the add is rejected with `ERR_PEER_OUTSIDE_SIZE_BAND`. New memberships begin in `ACCEPTED` with a null `exclusion_reason`, and each add increments both the group's `accepted_member_count` and the group's `version`.

Dropping a peer is a separate action: a `CompConsultant` excludes an `ACCEPTED` membership, supplying the free-text `exclusion_reason` that is recorded on the row, and the membership moves `ACCEPTED → EXCLUDED`. Exclusion is permitted while the owning group is in `DRAFT` or in `SCREENED`, but never once it is `APPROVED`, where the answer is `ERR_PEER_GROUP_NOT_MUTABLE` — and a membership that is no longer `ACCEPTED` draws that same error, the group's own mutability being tested first. The exclusion cascade has four levels. The membership's own status and reason are written and its `version` increments. Caused by that, the owning group recomputes `accepted_member_count`, and if the group was `SCREENED` it falls back `SCREENED → DRAFT` with `median_revenue_usd`, `median_market_cap_usd`, `size_fit_score`, `screened_at`, `benchmark_target_tdc_raw_usd`, `benchmark_target_tdc_adjusted_usd` and `benchmark_target_tdc_usd` all cleared to null. Caused by that, every pay program referencing the group whose design is still `DRAFT` has `benchmark_ratio`, `lti_multiple`, `lti_target_usd` and `target_tdc_usd` cleared and `benchmark_posture` returned to `UNBENCHMARKED`. Caused by that, every `SCREENED` proxy-advisor screen of those programs becomes `STALE`.

Screening is the act that turns a list of peers into a benchmark, moving the group `DRAFT → SCREENED`. It is refused on a group that is not in `DRAFT` with `ERR_PEER_GROUP_NOT_MUTABLE`, refused on a group with zero `ACCEPTED` members with `ERR_PEER_GROUP_EMPTY`, and refused with `ERR_PEER_OUTSIDE_SIZE_BAND` unless every `ACCEPTED` member either sits inside both bands or was admitted as a `BUSINESS_MODEL_ANALOG` — note that a `TALENT_COMPETITOR` peer whose ratios have since drifted out of band does block screening even though it was admissible at add time. Only `ACCEPTED` members participate in the computation; excluded members never do, no matter when they were excluded.

The medians are computed from the peers' own figures. Sort the accepted peers' `revenue_usd` ascending, breaking ties by the membership row's `created_at` ascending; where the count is odd, `median_revenue_usd` is the middle value rounded half-up to two decimal places, and where the count is even it is the mean of the two middle values, likewise rounded to two decimal places. `median_market_cap_usd` is derived identically from the peers' `market_cap_usd`. The `size_fit_score` expresses how closely the peer set's revenue median tracks the issuer: take the absolute difference between `median_revenue_usd` and the issuer's own revenue, divide it by the issuer's revenue, cap the resulting share at 1, subtract it from 1, multiply by 100 and round half-up to two decimal places — so a median identical to the issuer's revenue scores 100.00, and a median at least twice or at most zero times the issuer's revenue scores 0.00.

The benchmark itself is computed twice, in two variants, and **both are always stored** regardless of which one the group has elected. The `RAW_MEDIAN` variant works from the list of each accepted peer's disclosed `ceo_tdc_usd`, unadjusted, so a peer set skewed toward larger companies pulls the benchmark upward. The `SIZE_ADJUSTED` variant first scales each peer's disclosed compensation for the size difference: divide the issuer's revenue by that peer's revenue, clamp the quotient to no less than 0.5 and no more than 2.0, round the clamped factor half-up to four decimal places, multiply the peer's `ceo_tdc_usd` by that rounded factor, and round the product half-up to two decimal places. The rounding order matters — the factor is rounded before it multiplies, never after.

Both variants are then collapsed to a single figure by the same pinned percentile method: sort the list ascending (ties keeping the earlier-created membership first), take the value at the position given by rounding one half of the count *up* to the next whole number, and round that value half-up to two decimal places. For an even count this selects the **lower** of the two middle values, which is why the benchmark figure does not in general equal the mean-of-middles median used for `median_revenue_usd` — the two computations are deliberately different and both are asserted. The result of the raw list is `benchmark_target_tdc_raw_usd`; the result of the adjusted list is `benchmark_target_tdc_adjusted_usd`. Finally `benchmark_target_tdc_usd` is set to whichever of the two the group's `benchmark_basis` names. Because the size adjustment reorders the list, the two variants routinely select different peers as the percentile element, not merely different values. Screening stamps `screened_at` with the current logical time and increments the group's `version`.

Committee approval by a `CompCommitteeChair` moves the group `SCREENED → APPROVED` and freezes it. Approval requires the group to be in `SCREENED` — a `DRAFT` group is rejected with `ERR_PEER_GROUP_NOT_SCREENED` — and requires a non-null `benchmark_target_tdc_usd`, which successful screening guarantees and whose absence would be reported as `ERR_PEER_GROUP_NOT_SCREENED` too. The chair's `X-User-ID` is recorded as `approved_by_user_id`, the group's `version` increments, and the frozen benchmark is then pushed through the programs that depend on it: at the first level, every pay program referencing this group whose design is still `DRAFT` recomputes `fixed_leg_usd`, `benchmark_ratio`, `lti_multiple`, `lti_target_usd`, `target_tdc_usd` and `benchmark_posture`; at the second level, caused by the first, each such program that already has a non-null `pay_percentile_rank` recomputes `pay_percentile_rank`, `degree_of_alignment` and `alignment_status`; at the third level, caused by either of the first two, every `SCREENED` proxy-advisor screen of a touched program becomes `STALE`. `APPROVED` is terminal for a peer group: it never reverts, and its membership can never change again.

### 3.3. Sizing Target Pay: the Mix and the Benchmark Tier

A pay program is the centre of gravity of the whole system, and it carries two independent lifecycles at once. Its `design_status` runs `DRAFT → COMMITTEE_APPROVED → DISCLOSED → CLOSED`, tracking the design and disclosure of the program. Its `vote_status` runs `NOT_VOTED → PASSED` or `NOT_VOTED → FAILED → REMEDIATED`, tracking the shareholder verdict. The two advance independently — approving the design never touches the vote dimension, and certifying a vote only touches the design dimension in the specific circumstances described in §3.8. A new program begins at `DRAFT` and `NOT_VOTED`.

A `CompConsultant` opens a program by naming the `issuer_company_id` (which must be the company flagged as issuer), the `peer_group_id` that benchmarks it (whose own `issuer_company_id` must equal the program's), the `ceo_executive_id` whose target pay the program sizes (whose `company_id` must equal the program's issuer), the `fiscal_year` between 2020 and 2035, the three mix shares, the performance-share split, and the `meeting_date` at which the say-on-pay vote will be held; a violation of any of those three referential conditions is `ERR_INVALID_REQUEST`. The meeting date must be strictly after the current logical time when the program is created; otherwise the creation is rejected with `ERR_MEETING_DATE_NOT_FUTURE`. Two further inputs are optional: `sti_max_multiple`, the hard cap on the annual incentive expressed as a multiple of target, which must lie between 1.0 and 3.0 and defaults to 2.0; and `tsr_percentile_rank`, the issuer's three-year total-shareholder-return percentile rank against the peer group, a value between 0.00 and 100.00 that later drives the alignment verdict and itself defaults to 0.00 when omitted. Creation also initialises `outreach_coverage_pct`, `realized_pay_total_usd` and `realizable_pay_total_usd` to 0.00 and `alignment_status` to `UNRATED`, leaves `votes_for`, `votes_against`, `abstentions` and `support_pct` null, and sets `enhanced_engagement_required` to false.

The pay mix is expressed as three percentages of target pay — `salary_pct`, `sti_pct` and `lti_pct` — each of which must lie in the closed range from 5.00 to 80.00, on pain of `ERR_MIX_COMPONENT_OUT_OF_BOUNDS`, and which together must total exactly 100.00, on pain of `ERR_PAY_MIX_MUST_TOTAL_100`. A fourth input, `lti_performance_share_pct`, states what share of the long-term-equity leg is delivered as performance shares rather than time-vested units, between 0.00 and 100.00. From those four numbers the system derives `performance_based_pct`, the share of target pay that is genuinely performance-contingent: multiply `lti_pct` by `lti_performance_share_pct`, divide by 100, round half-up to two decimal places, add `sti_pct`, and round the sum again to two decimal places.

Target compensation is then built in five pinned steps, and the pinning matters because the chain looks circular and is not. **Step one** computes the fixed leg, which is independent of equity entirely: the CEO's annual-incentive target in dollars is the officer's `base_salary_usd` multiplied by `sti_target_pct` divided by 100, rounded half-up to two decimal places, and `fixed_leg_usd` is that figure added to `base_salary_usd`, rounded again to two decimal places. If the peer group has no `benchmark_target_tdc_usd` yet, the chain stops here: `benchmark_ratio`, `lti_multiple`, `lti_target_usd` and `target_tdc_usd` are all null and `benchmark_posture` is `UNBENCHMARKED`. **Step two** sizes the benchmark's own fixed leg using the program's declared salary-plus-annual-incentive share: multiply `benchmark_target_tdc_usd` by the sum of `salary_pct` and `sti_pct`, divide by 100, round to two decimal places; then `benchmark_ratio` is the issuer's `fixed_leg_usd` divided by that benchmark fixed leg, rounded half-up to four decimal places. **Step three** looks up the equity tier from that ratio: `lti_multiple` is 4.0 when `benchmark_ratio` is below 0.80, 3.0 when it is at least 0.80 but below 1.20, and 2.0 when it is at or above 1.20. The tier is keyed on the fixed-leg ratio from step two and nothing else; it is never keyed on target compensation, which does not exist yet, and it is never re-evaluated after the later steps. There is no iteration to a fixed point. **Step four** sets `lti_target_usd` to `fixed_leg_usd` multiplied by `lti_multiple`, rounded to two decimal places. **Step five** sets `target_tdc_usd` to `fixed_leg_usd` plus `lti_target_usd`, rounded to two decimal places, then bands the result: divide `target_tdc_usd` by the group's `benchmark_target_tdc_usd` and round half-up to four decimal places, and `benchmark_posture` becomes `ABOVE_MARKET` when that posture ratio is at or above 1.20, `BELOW_MARKET` when it is at or below 0.80, and `ALIGNED` in between. The whole computation involves exactly one officer and one peer group; no other program's numbers participate.

Reallocating the mix is the one way a `DRAFT` program's shares can move after creation. The request names a `from_component` and a `to_component`, each one of `SALARY`, `STI` or `LTI` and the two necessarily different, together with the number of `points` to shift, which is taken to two decimal places and must be strictly positive, and the `expected_pay_program_version` guard. The component being drawn down is reduced by the points and the component being credited is increased by them, each result rounded to two decimal places. If either resulting component falls below 5.00 or rises above 80.00 the reallocation is rejected with `ERR_MIX_COMPONENT_OUT_OF_BOUNDS`, and if the three resulting components do not sum to exactly 100.00 it is rejected with `ERR_PAY_MIX_MUST_TOTAL_100`. The hundred-point total is a conserved quantity: it holds before and after every reallocation, and applying a reallocation and then its exact reverse restores each component to its prior value. A successful reallocation re-runs the whole five-step target computation, increments the program's `version`, and marks every `SCREENED` screen of the program `STALE`. Reallocation is only available while `design_status` is `DRAFT`; anything else is `ERR_PROGRAM_NOT_MUTABLE`.

Committee approval of the design, performed by a `CompCommitteeChair`, advances `design_status` from `DRAFT` to `COMMITTEE_APPROVED` and is the gate at which four independent conditions are checked. The program must actually be in `DRAFT`, or the answer is `ERR_PROGRAM_NOT_MUTABLE`. The referenced peer group must be `APPROVED`, or the answer is `ERR_PEER_GROUP_NOT_APPROVED` — and per §2.10 this referential gate is evaluated before the fiscal cap, so an unapproved group is reported even when the cap would also fail. The three mix shares must still total exactly 100.00. For each vehicle that has at least one metric defined, the `weight_pct` values of that vehicle's metrics must sum to exactly 100.00, or the answer is `ERR_METRIC_WEIGHTS_NOT_100`; a vehicle with no metrics at all imposes no weight requirement. And `target_tdc_usd` may not exceed one and a half times the group's `benchmark_target_tdc_usd`, that product being rounded to two decimal places before the comparison — exceeding it is `ERR_TDC_EXCEEDS_BENCHMARK_CAP`. On success the chair's `X-User-ID` is stored as the program's `approved_by_user_id`, the program's `version` increments, `vote_status` is left exactly where it was, and every metric of the program still in `DRAFT` is locked, as described next.

Programs can be listed with filters on `issuer_company_id`, `peer_group_id`, `ceo_executive_id`, `design_status` and `vote_status`, which is the practical way to find, say, every program that has been disclosed but not yet voted.

### 3.4. Goal Setting, Adjustment, Results and Certification

Incentive metrics are the instruments through which a program's variable pay is earned. A `CompConsultant` defines each one against a `DRAFT` program — a program in any later design state rejects the definition with `ERR_PROGRAM_NOT_MUTABLE` — recording the owning `pay_program_id` and choosing a `metric_code` from `ADJ_EPS`, `REVENUE_GROWTH`, `FCF`, `ROIC`, `RTSR` and `COST_RATIO`, a `vehicle` of either `ANNUAL_INCENTIVE` or `LONG_TERM_PSU`, a `direction` of `HIGHER_IS_BETTER` or `LOWER_IS_BETTER`, and a `weight_pct` between 5.00 and 100.00 expressing the metric's weight inside its own vehicle. The triple of program, `metric_code` and `vehicle` is unique; a duplicate is `ERR_METRIC_ALREADY_DEFINED`.

The goal curve itself is three goal values and three payout percentages. `threshold_value` is the achievement that pays `threshold_payout_pct` (default 50.00), `target_value` — which may not be zero — is the achievement that pays `target_payout_pct` (default 100.00), and `maximum_value` is the achievement that pays `maximum_payout_pct` (default 200.00). The `interpolation` field, either `LINEAR` or `STEP` and defaulting to `LINEAR`, decides the shape between those inflection points. The three goal values must be **strictly** ordered in the metric's direction: for `HIGHER_IS_BETTER` the threshold must be less than the target and the target less than the maximum; for `LOWER_IS_BETTER` the threshold must be greater than the target and the target greater than the maximum. A curve that violates this, whether at definition or at adjustment, is rejected with `ERR_GOAL_CURVE_NOT_MONOTONIC`. Metrics can be listed per program with an optional `vehicle` filter.

Metrics start in `DRAFT`. When the committee approves the program design, every `DRAFT` metric of that program moves `DRAFT → LOCKED` and takes a snapshot: `locked_target_value` is set to the metric's `target_value` at that instant, and the snapshot never moves again. That frozen value is the yardstick for the mid-cycle adjustment policy.

A `CompCommitteeChair` may adjust a `LOCKED` metric's goals — and only a `LOCKED` one; any other state is `ERR_METRIC_STATE_INVALID` — supplying any of `target_value`, `threshold_value` and `maximum_value` together with a mandatory `result_adjustment_reason`, recorded in the metric's field of that name, and the `expected_incentive_metric_version` guard. Before the adjustment is applied, its magnitude is measured against the snapshot: take the new target (the supplied `target_value`, or the metric's existing one if the request does not move the target), subtract `locked_target_value`, take the absolute value, divide by the absolute value of `locked_target_value`, multiply by 100 and round half-up to two decimal places; the result is stored as `goal_adjustment_pct`. A magnitude of exactly 15.00 percent is permitted; anything strictly greater is rejected with `ERR_ADJUSTMENT_EXCEEDS_POLICY_LIMIT`. The resulting curve must also remain strictly monotonic. A successful adjustment overwrites the supplied goal values, moves the metric `LOCKED → ADJUSTED`, records the ordering chair as `adjusted_by_user_id`, increments the metric's `version` — and has a lasting cost: every subsequent proxy-advisor screen of the program counts this metric against the program's goal rigor, and every `SCREENED` screen of the program is immediately marked `STALE`.

Fiscal-year achievement is submitted by a `CompConsultant` against a metric in `LOCKED` or in `ADJUSTED`; both branches behave identically and both land the metric in `RESULT_SUBMITTED`, incrementing its `version`. The submission carries the GAAP `as_reported_value`, an optional `non_gaap_adjusted_value` asserted under the program's adjustment policy, and an optional `result_adjustment_reason` justifying that assertion; a submission that omits `result_adjustment_reason` entirely leaves whatever reason the metric already carried — an ordering chair's, typically — in place. The metric's `achieved_value` is the `non_gaap_adjusted_value` whenever one has been supplied, and the `as_reported_value` otherwise; before any submission it is null. Any state other than `LOCKED` or `ADJUSTED` yields `ERR_METRIC_STATE_INVALID`.

Certification by a `CompCommitteeChair` moves the metric `RESULT_SUBMITTED → CERTIFIED` and is where the payout curve is finally evaluated. Certification is refused from any other state with `ERR_METRIC_STATE_INVALID`, and refused with `ERR_SEGREGATION_OF_DUTIES` when the acting `X-User-ID` equals the metric's `adjusted_by_user_id` — the chair who moved a goal may not certify the result measured against it.

The curve is evaluated against `achieved_value` using the metric's own three goal values and three payout percentages, and each of the four direction-by-interpolation combinations is specified separately. For a `HIGHER_IS_BETTER` metric with `LINEAR` interpolation: an achievement strictly below `threshold_value` pays 0.00; an achievement at or above the threshold but strictly below the target pays `threshold_payout_pct` plus the difference between `target_payout_pct` and `threshold_payout_pct`, prorated by how far the achievement has travelled from the threshold toward the target; an achievement at or above the target but strictly below the maximum pays `target_payout_pct` plus the difference between `maximum_payout_pct` and `target_payout_pct`, prorated by how far the achievement has travelled from the target toward the maximum; and an achievement at or above `maximum_value` pays `maximum_payout_pct`. For a `HIGHER_IS_BETTER` metric with `STEP` interpolation the curve is a staircase with no proration: at or above the maximum pays `maximum_payout_pct`, otherwise at or above the target pays `target_payout_pct`, otherwise at or above the threshold pays `threshold_payout_pct`, otherwise 0.00.

For a `LOWER_IS_BETTER` metric the curve mirrors, with the same density of specification. With `LINEAR` interpolation: an achievement strictly above `threshold_value` pays 0.00; an achievement at or below the threshold but strictly above the target pays `threshold_payout_pct` plus the difference between `target_payout_pct` and `threshold_payout_pct`, prorated by how far the achievement has travelled down from the threshold toward the target; an achievement at or below the target but strictly above the maximum pays `target_payout_pct` plus the difference between `maximum_payout_pct` and `target_payout_pct`, prorated by how far it has travelled down from the target toward the maximum; and an achievement at or below `maximum_value` pays `maximum_payout_pct`. With `STEP` interpolation: at or below the maximum pays `maximum_payout_pct`, otherwise at or below the target pays `target_payout_pct`, otherwise at or below the threshold pays `threshold_payout_pct`, otherwise 0.00. In every case the result is rounded half-up to two decimal places and stored as `payout_factor_pct`. The boundaries are inclusive in the earning direction: an achievement exactly equal to `threshold_value` pays exactly `threshold_payout_pct`, an achievement exactly equal to `maximum_value` pays exactly `maximum_payout_pct`, and one unit past the threshold in the failing direction pays 0.00. Sibling metrics never enter this formula — the curve is a function of one metric row alone.

Certification then fans out five levels. At the first level the factor is computed as above, snapshotted into `original_payout_factor_pct` — which is immutable thereafter — the certifying chair is recorded as `certified_by_user_id`, the status becomes `CERTIFIED` and the metric's `version` increments. At the second level, caused by the first: if *every* metric of this program sharing this metric's `vehicle` is now certified — or restated, which counts equally here — each award of that program with the same vehicle recomputes its `certified_factor_pct` and `earned_amount_usd`, then its `realized_value_usd` and `realizable_value_usd`. At the third level, caused by the second, the owning program recomputes `realized_pay_total_usd`, `realizable_pay_total_usd`, `pay_percentile_rank`, `degree_of_alignment` and `alignment_status`. At the fourth level, caused by the third, any movement in the program figures §2.8 watches — the two pay totals, `pay_percentile_rank`, `degree_of_alignment` or `alignment_status` — marks every `SCREENED` screen of the program `STALE`. At the fifth level, caused by the fourth, every `LEGAL_CLEARED` disclosure section of the program returns to `DRAFTING` with `revision_round` incremented by one and `cleared_by_user_id` cleared.

A certified metric has one further transition available to it, driven only by a restatement analysis: `CERTIFIED → RESTATED`, described in §3.9.

### 3.5. Granting, Settling and Valuing Awards

Awards are what actually deliver money. A `CompConsultant` grants one against a program, naming the `executive_id` of the holder — whose `company_id` must equal the program's issuer — and the `vehicle`, one of `ANNUAL_INCENTIVE`, `LONG_TERM_PSU` or `RSU`. Equity vehicles carry `units_granted`, a non-negative figure with two decimal places that must be strictly positive for `LONG_TERM_PSU` and `RSU` and exactly 0 for `ANNUAL_INCENTIVE`, where omitting the field altogether is equivalent to supplying 0. The issuer's prevailing `share_price_usd` is captured on the row as `grant_price_usd` (a supplied `grant_price_usd` overrides the captured price). New awards begin in `GRANTED`, with `settlement_date` and `vest_price_usd` null.

For an `ANNUAL_INCENTIVE` award, `target_amount_usd` is the holder's `base_salary_usd` multiplied by their `sti_target_pct` divided by 100, rounded half-up to two decimal places; for the two equity vehicles it is 0.00. Granting also computes the award's payout factor immediately whenever the award's program-and-vehicle pair carries at least one metric and every one of them is already certified or restated, so that an award granted after certification is not left permanently factorless; a pair with no metrics at all leaves the factor null, exactly as the next paragraph requires, and an `RSU` award — a vehicle no metric can be defined against — is therefore always factorless. Finally the award's realized and realizable values are computed and the program's alignment verdict is recomputed.

The weighted payout factor of a vehicle is computed as follows. Gather every metric of the award's own program sharing the award's own `vehicle`; metrics of the other vehicle and of any other program are excluded. If that set is **empty**, the award has no factor at all: `certified_factor_pct` and `earned_amount_usd` both stay null, and the computation stops there — an empty contribution list must not collapse to 0.00, because a null factor is what lets the forward-looking valuation fall back to assumed target performance. If the set is non-empty but not every member of it is in `CERTIFIED` or `RESTATED`, the factor is likewise null and the computation stops. Otherwise each metric contributes its `payout_factor_pct` multiplied by its `weight_pct` divided by 100, **each contribution rounded half-up to two decimal places individually**, and `certified_factor_pct` is the sum of those rounded contributions, rounded again to two decimal places. Summing unrounded products and rounding the total afterwards is wrong and produces a different cent.

For an `ANNUAL_INCENTIVE` award the cash follows: the uncapped amount is `target_amount_usd` multiplied by `certified_factor_pct` divided by 100, rounded to two decimal places; the cap is `target_amount_usd` multiplied by the program's `sti_max_multiple`, rounded to two decimal places; and `earned_amount_usd` is the lesser of the two, the cap being applied only after both figures have been rounded. For the equity vehicles `earned_amount_usd` remains null.

Settlement is a fork. A `CompConsultant` settles a `GRANTED` award — any other status is `ERR_AWARD_NOT_GRANTED` — supplying a `disposition` of either `VEST` or `FORFEIT` together with a `settlement_date` — required on both branches, though only the vesting branch honours the value supplied — and optionally a `vest_price_usd` override. The `VEST` branch carries a cross-entity precondition the `FORFEIT` branch does not: for the `ANNUAL_INCENTIVE` and `LONG_TERM_PSU` vehicles the award's `certified_factor_pct` must already be non-null, meaning every metric of that vehicle has been certified, and vesting without it is refused with `ERR_METRIC_NOT_CERTIFIED`. Vesting moves the award `GRANTED → VESTED`, stamps the supplied `settlement_date`, freezes `vest_price_usd` at the issuer's current `share_price_usd` unless an override was supplied, recomputes the award's two values, and increments the award's `version`. Forfeiting moves the award `GRANTED → FORFEITED` with no certification requirement whatsoever — the divergent precondition set is precisely what distinguishes the two branches — stamps `settlement_date` with the current logical time, zeroes both `realized_value_usd` and `realizable_value_usd`, and increments the award's `version`. Either branch then makes the owning program recompute `realized_pay_total_usd` and `realizable_pay_total_usd`; on the vesting branch the program additionally recomputes `pay_percentile_rank`, `degree_of_alignment` and `alignment_status`, and on either branch the program's `SCREENED` screens flip to `STALE` as soon as any figure §2.8 watches has moved — which a shift in the pay totals alone is enough to do.

The two valuations an award carries answer two different questions, and they are computed from the same row by two deliberately different rules. Where a factor is needed but none is certified, the forward-looking rule substitutes an assumed 100.00 percent of target.

The **realized** value is strictly chronological: it counts only what has actually been delivered. An award still `GRANTED` has a `realized_value_usd` of 0.00, and so does a `FORFEITED` one. A `VESTED` `ANNUAL_INCENTIVE` award realizes its `earned_amount_usd`. A `VESTED` `LONG_TERM_PSU` award first converts units at performance — `units_granted` multiplied by `certified_factor_pct` divided by 100, rounded to two decimal places — then multiplies those effective units by the frozen `vest_price_usd` and rounds to two decimal places. A `VESTED` `RSU` award simply multiplies `units_granted` by `vest_price_usd`, rounded to two decimal places. A `CLAWED_BACK` award realizes its value at vest less the determination's `recoverable_amount_usd`, rounded to two decimal places. Because it freezes delivered equity at the vest price, the realized figure is insensitive to later price moves.

The **realizable** value is forward-looking: it marks outstanding grants to today's price. For a `GRANTED` `ANNUAL_INCENTIVE` award it is `target_amount_usd` multiplied by the factor (certified if available, otherwise the assumed 100.00 percent) divided by 100, rounded to two decimal places. For a `GRANTED` `LONG_TERM_PSU` award it is `units_granted` multiplied by the issuer's **current** `share_price_usd`, multiplied by that same factor and divided by 100, rounded to two decimal places. For a `GRANTED` `RSU` award it is `units_granted` multiplied by the issuer's current `share_price_usd`, rounded to two decimal places. A `FORFEITED` award has a realizable value of 0.00. For any other status — `VESTED` or `CLAWED_BACK` — the realizable value simply equals the realized value, since nothing remains outstanding. Identical award data therefore yields two different totals, which is the entire point of the disclosure.

Awards can be listed with filters on `pay_program_id`, `executive_id` and `status`; a `NamedExecutiveOfficer` issuing that read sees only rows whose `executive_id` matches their own identifier, and an `executive_id` filter naming anybody else is rejected outright with `ERR_NOT_RESOURCE_OWNER`.

### 3.6. Pay-for-Performance Alignment and Proxy-Advisor Screening

Alignment testing asks whether the chief executive's pay percentile tracks the company's shareholder-return percentile. Its inputs are recomputed whenever any award of the program changes its realized value, its realizable value or its status, and also as the second level of the cascade that follows peer-group approval.

The program's `realized_pay_total_usd` is the sum of `realized_value_usd` over the program's awards in `GRANTED`, `VESTED` or `CLAWED_BACK`, rounded half-up to two decimal places, and `realizable_pay_total_usd` is the corresponding sum of `realizable_value_usd`. `FORFEITED` awards are excluded from both totals entirely — that is what "excluded from both program totals" means operationally. If the program's peer group has no `ACCEPTED` members, or the program has no awards in those three statuses, then `pay_percentile_rank` and `degree_of_alignment` are null and `alignment_status` is `UNRATED`. Otherwise, count the `ACCEPTED` peers whose disclosed `ceo_tdc_usd` is **strictly less** than the program's `realized_pay_total_usd`, divide that count by the number of `ACCEPTED` peers, multiply by 100 and round half-up to two decimal places to obtain `pay_percentile_rank`. `degree_of_alignment` is the program's `tsr_percentile_rank` minus `pay_percentile_rank`, rounded to two decimal places. The verdict bands that gap on inclusive floors: `alignment_status` is `ALIGNED` when the gap is at or above negative 10.00, `WATCH` when it is below that but at or above negative 30.00, and `MISALIGNED` below negative 30.00 — so exactly negative 10.00 is `ALIGNED` and exactly negative 30.00 is `WATCH`. A dedicated computed read returns this whole picture for a single program: `realized_pay_total_usd`, `realizable_pay_total_usd`, `pay_percentile_rank`, `tsr_percentile_rank`, `degree_of_alignment`, `alignment_status` and `accepted_peer_count`.

Proxy-advisor screening applies a published advisor methodology to the program and produces a vote recommendation the committee can react to before the meeting. Either an `InvestorRelationsLead` or a `CompConsultant` opens a screen naming the `advisor`, which is `ISS` or `GLASS_LEWIS`; only one screen may exist per program per advisor, and a second attempt is `ERR_SCREEN_ALREADY_EXISTS` with the instruction to re-run the existing one instead. Screens can be listed per program with an optional `advisor` filter.

Three components are common to both methodologies. The **alignment component** starts from a pivot of 50.00 and subtracts the program's `degree_of_alignment` (treating a null gap as 0.00), then clamps the result to no less than 0.00 and no more than 100.00 and rounds to two decimal places — so a badly misaligned program, whose gap is deeply negative, scores high concern. The **mix component** is 100.00 less the program's `performance_based_pct`, floored at 0.00 and rounded to two decimal places, penalising a mix that is light on performance-contingent pay. The **rigor component** counts the program's metrics that have been meddled with — every metric whose status is `ADJUSTED` or whose `goal_adjustment_pct` is non-null — charges 25.00 per such metric, caps the total at 100.00 and rounds to two decimal places; four adjusted metrics therefore saturate the rigor penalty.

The two methodologies then diverge, and the divergence is the whole reason both screens are worth running. Under `ISS`, engagement is ignored entirely: `outreach_component` is null, and `concern_score` is 0.50 of the alignment component plus 0.30 of the mix component plus 0.20 of the rigor component, rounded to two decimal places — an issuer that has done no shareholder outreach at all is not penalised. Under `GLASS_LEWIS`, engagement counts: `outreach_component` is 100.00 less the program's `outreach_coverage_pct`, floored at 0.00 and rounded to two decimal places, and `concern_score` is 0.35 of the alignment component plus 0.15 of the mix component plus 0.30 of the rigor component plus 0.20 of the outreach component, rounded to two decimal places. Because alignment is weighted lower but a fresh engagement penalty is added, identical program data yields a higher Glass Lewis score and can land in a different band.

The score is banded into `concern_level`: `LOW` below 30.00, `MEDIUM` at or above 30.00 but below 60.00, and `HIGH` at or above 60.00 — exactly 30.00 is `MEDIUM` and exactly 60.00 is `HIGH`. `recommendation` follows mechanically: `AGAINST` when the level is `HIGH`, and `FOR` otherwise. A newly created screen is `SCREENED` and stamps `screened_at` with the current logical time.

Re-running a screen is how a `STALE` one becomes current again, and either the `InvestorRelationsLead` or the `CompConsultant` may do it. A re-run is accepted from `SCREENED` as well as from `STALE`: from `STALE` it is the `STALE → SCREENED` refresh, from `SCREENED` it is a self-transition, and in both cases it recomputes `alignment_component`, `mix_component`, `rigor_component`, `outreach_component`, `concern_score`, `concern_level` and `recommendation` identically, re-stamps `screened_at` and increments the screen's `version`.

### 3.7. The Disclosure Cycle: Drafting, Clearance, Filing and Amendment

Disclosure sections are drafted per program, one row per section. Either a `SecuritiesCounsel` or a `CompConsultant` opens a section, naming its `section_code` — one of `CD_AND_A`, `SUMMARY_COMP_TABLE`, `PAY_RATIO` and `PVP_TABLE` — its drafted `word_count` (a non-negative integer) and the `required_tables_included` flag, which defaults to false when omitted. Only one row may exist per program per section code, and a duplicate is `ERR_CDA_SECTION_ALREADY_EXISTS`. A new section starts in `DRAFTING` with `revision_round` at 0, `authored_by_user_id` set to the creating user, `cleared_by_user_id` null and `filed_at` null. Sections can be listed per program with an optional `section_code` filter.

The section's lifecycle is a review loop with a filing exit. Submitting a `DRAFTING` section for review — permitted to `SecuritiesCounsel` and `CompConsultant`, and optionally revising `word_count` and `required_tables_included` on the way — moves it `DRAFTING → IN_REVIEW`, records the submitting `X-User-ID` as `authored_by_user_id` and increments the section's `version`. Submission additionally requires the owning program's `design_status` to be `COMMITTEE_APPROVED` or `DISCLOSED`; a program still in `DRAFT`, or already `CLOSED`, rejects it with `ERR_PROGRAM_NOT_MUTABLE`. Bouncing a section back — permitted to `SecuritiesCounsel` and `CompCommitteeChair`, with an optional `feedback_summary` — returns it `IN_REVIEW → DRAFTING`, increments `revision_round` by one, clears `cleared_by_user_id` and increments `version`. That loop, `DRAFTING → IN_REVIEW → DRAFTING`, may run any number of times, and `revision_round` is the count of the loops.

Legal clearance is a `SecuritiesCounsel` operation on a section in `IN_REVIEW`, moving it `IN_REVIEW → LEGAL_CLEARED`, and it is the most heavily gated step in the disclosure pipeline. The section must be in `IN_REVIEW`, or the answer is `ERR_CDA_STATE_INVALID`. The clearing `X-User-ID` must differ from the section's `authored_by_user_id`, or the answer is `ERR_SEGREGATION_OF_DUTIES`. The section's `required_tables_included` must be true, and additionally, when the section is the `CD_AND_A` narrative, its `word_count` must be at least 1500 — other section codes carry no length floor — and a failure of either condition is `ERR_CDA_TABLES_INCOMPLETE`. Finally, a cross-entity guard: the owning program must carry an `ISS` proxy-advisor screen whose status is `SCREENED`, so that counsel is clearing a disclosure against a current advisor read; a missing or `STALE` `ISS` screen is `ERR_ISS_SCREEN_NOT_CURRENT`. On success `cleared_by_user_id` is set to the clearing user and the section's `version` increments.

Filing, also a `SecuritiesCounsel` operation, moves a section `LEGAL_CLEARED → FILED` — any other state is `ERR_CDA_STATE_INVALID` — stamps `filed_at` with the current logical time and increments the section's `version`. Filing the `CD_AND_A` section has a consequence beyond the section itself: it advances the owning program's `design_status` from `COMMITTEE_APPROVED` to `DISCLOSED` and increments the program's `version`. Filing any other section code advances nothing on the program.

Two paths lead a section back into drafting without anyone asking. The amended-proxy path is deliberate: a `SecuritiesCounsel` or `CompCommitteeChair` may reopen a `FILED` section, moving it `FILED → DRAFTING`, incrementing `revision_round`, and clearing both `cleared_by_user_id` and `filed_at`. Reopening is only permitted while the program's `vote_status` is still `NOT_VOTED`; after certification the answer is `ERR_VOTE_ALREADY_CERTIFIED`. Reopening the `CD_AND_A` section leaves the program at `design_status` `DISCLOSED` — the program does not un-disclose — but it does make `ERR_CDA_NOT_FILED` reachable on vote certification until that section has been cleared and filed again. The involuntary path is the tail of the cascades: whenever a proxy-advisor screen of the program moves `SCREENED → STALE`, every `LEGAL_CLEARED` section of that program is pushed `LEGAL_CLEARED → DRAFTING` with `revision_round` incremented and `cleared_by_user_id` cleared. A section has no terminal state; it can always be reopened and re-cleared.

### 3.8. Shareholder Outreach and the Say-on-Pay Vote

Outreach is how the company earns the right to claim it listened. An `InvestorRelationsLead` requests an engagement against a program, supplying the `investor_name` as the requester knows it (one to one hundred and twenty characters, not blank), the investor's `ownership_pct` of shares outstanding (between 0.01 and 100.00), and a `channel` of `CALL`, `MEETING` or `LETTER`. The `investor_key` is not a client input at all: the server derives it from the name alone, as the `investor_name` trimmed of surrounding whitespace and upper-cased — any `investor_key` the request happens to carry is ignored — and it — not the display name — is the identity used both for window-conflict detection and for coverage de-duplication, so that "BlackRock", " blackrock " and "BLACKROCK" are one investor. New engagements begin in `REQUESTED` with `feedback_position`, `feedback_summary` and `held_at` all null. Engagements can be listed per program with an optional `engagement_status` filter.

Scheduling moves an engagement `REQUESTED → SCHEDULED` and is where the calendar rules bite. The request supplies `window_start`, the inclusive start of the slot, and `window_end`, its exclusive end, which must be strictly after the start. An engagement that is not in `REQUESTED` is refused with `ERR_ENGAGEMENT_STATE_INVALID`, and a `window_start` strictly before the current logical time is refused with `ERR_ENGAGEMENT_WINDOW_IN_PAST`.

Two interval rules then apply, in a fixed order. First the **quiet period**: the ten days immediately preceding the program's `meeting_date`, up to and including the meeting instant itself, form a closed blackout interval, and a candidate slot intersects it whenever the slot's start is at or before the meeting instant and the slot's end is strictly after the start of the blackout. An intersecting slot is refused with `ERR_QUIET_PERIOD_ENGAGEMENT`. This SEC-mandated blackout is evaluated before any scheduling-hygiene rule — the past-window check of the preceding paragraph included — so a slot that both intrudes on the blackout and either lies in the past or collides with an existing booking reports the blackout. Second the **same-investor overlap**: gather the program's other engagements sharing the candidate's `investor_key` whose status is `SCHEDULED` or `HELD` — `REQUESTED` rivals are ignored entirely — and refuse the candidate with `ERR_OUTREACH_WINDOW_OVERLAP` if the candidate's start falls strictly before a rival's end while that rival's start falls strictly before the candidate's end. Because both intervals are half-open, exact adjacency is permitted: a slot beginning at the very instant a prior slot ends does not overlap it.

Holding a `SCHEDULED` engagement — any other status is `ERR_ENGAGEMENT_STATE_INVALID` — records the investor's `feedback_position` as `SUPPORTIVE`, `CONCERNED` or `OPPOSED` together with an optional `feedback_summary`, stamps `held_at` with the current logical time, moves the engagement `SCHEDULED → HELD`, and increments its `version`. Holding then cascades twice. At the first level, the program recomputes `outreach_coverage_pct`: gather the program's `HELD` engagements, keep at most one row per distinct `investor_key` — the contributor being the row with the **earliest** `created_at`, so a second conversation with the same investor adds nothing — sum the contributors' `ownership_pct`, cap the sum at 100.00 and round half-up to two decimal places. `REQUESTED` and `SCHEDULED` engagements contribute nothing. At the second level, caused by the first, every `SCREENED` screen of the program moves to `STALE`, because coverage is a `GLASS_LEWIS` policy input.

Vote certification is the second dimension of the program's lifecycle, performed by a `CompCommitteeChair`, and it is gated three ways. The program's `vote_status` must still be `NOT_VOTED`, or the answer is `ERR_VOTE_ALREADY_CERTIFIED`. Its `design_status` must be `DISCLOSED`, or the answer is `ERR_PROGRAM_NOT_DISCLOSED`. And the program's `CD_AND_A` section must exist and be in `FILED`, or the answer is `ERR_CDA_NOT_FILED`. The request supplies three integer tallies — `votes_for`, `votes_against` and `abstentions` — all of which are stored on the program.

Support is measured on votes cast: the denominator is `votes_for` plus `votes_against`, and `abstentions` are recorded for disclosure but deliberately excluded from it. A denominator of zero is a malformed request and is rejected with `ERR_INVALID_REQUEST`. Otherwise `support_pct` is `votes_for` divided by that denominator, multiplied by 100 and rounded half-up to two decimal places. Support of at least 50.00 percent carries the vote; below that it fails. And independently of pass or fail, `enhanced_engagement_required` is set true whenever `support_pct` is strictly below 70.00 — the responsiveness trigger — and false otherwise. Exactly 50.00 passes; exactly 70.00 does *not* trigger enhanced engagement.

The two branches then diverge sharply, and the divergent side-effect sets are what distinguish them. On the **passing** branch, `vote_status` becomes `PASSED` and the program's `version` increments. If support reached 70.00 or more, the design dimension also advances `DISCLOSED → CLOSED` and the program is done. If support passed but fell short of the responsiveness trigger, `design_status` stays at `DISCLOSED` and `enhanced_engagement_required` stands as a standing obligation until the committee remediates. On the **failing** branch, `vote_status` becomes `FAILED`, `enhanced_engagement_required` is true, `design_status` stays at `DISCLOSED` — a failed vote does not close a program — and `alignment_status` is set to `MISALIGNED`. Caused by that, every `SCREENED` screen of the program moves to `STALE`, the failed vote being a new policy input in its own right. Caused by that, every `LEGAL_CLEARED` section of the program returns to `DRAFTING` with `revision_round` incremented and `cleared_by_user_id` cleared — on this branch that bounce runs whether or not the program had a `SCREENED` screen to stale in the first place; every `FILED` section other than the `CD_AND_A` narrative likewise returns to `DRAFTING` for the responsiveness rewrite, with `revision_round` incremented and both `cleared_by_user_id` and `filed_at` cleared.

Remediation closes the loop after a failure. A `CompCommitteeChair` records the program changes made in response, supplying a mandatory `feedback_summary`, and the program moves `vote_status` `FAILED → REMEDIATED` while `design_status` advances `DISCLOSED → CLOSED`, `enhanced_engagement_required` is cleared to false and the program's `version` increments. Remediation is refused on any program whose `vote_status` is not `FAILED`, with `ERR_VOTE_NOT_FAILED`, and — the substantive gate — it requires that the committee have actually engaged holders of at least 30.00 percent of shares outstanding: an `outreach_coverage_pct` below 30.00 is refused with `ERR_OUTREACH_COVERAGE_INSUFFICIENT`. `CLOSED` is the terminal design state of a pay program, reachable either through a comfortably passing vote or through remediation of a failed one.

### 3.9. Restatements, Clawback Determinations and Recovery

An accounting restatement retroactively invalidates achievements the committee has already certified and payouts the company has already made, and this last workflow is how the money comes back. A `SecuritiesCounsel` declares a restatement against a company, supplying the `restatement_date` on which the restatement was determined, the inclusive `lookback_start` and inclusive `lookback_end` bounding the three-year recovery window, and a free-text `accounting_reason` of one to five hundred characters. The lookback end must be strictly after the lookback start, and the restatement date must fall at or after the lookback end; a violation of either is `ERR_INVALID_REQUEST`. A declaration begins in `DECLARED` with `determination_count` at 0 and both `recoverable_total_usd` and `recovered_total_usd` at 0.00, and the event records the `company_id` it restates.

Two live restatements on one company may not describe near-adjacent periods. Gather the company's existing events whose status is `DECLARED`, `ANALYZED` or `RECOVERY_ORDERED` — events already `CLOSED` never block a new declaration — and reject the candidate with `ERR_LOOKBACK_PERIOD_COLLISION` when its lookback start falls at or before a rival's lookback end extended forward by one day *and* its lookback end falls at or after that rival's lookback start pulled back by one day. Both bounds are closed and the buffer is symmetric, so unlike the half-open outreach windows, exact adjacency between two lookback periods is forbidden.

Analysis moves the event `DECLARED → ANALYZED` and does the arithmetic. Any other starting state is `ERR_EVENT_STATE_INVALID`. The request carries `restated_metric_results`, an array of objects each shaped as an `incentive_metric_id` paired with a `restated_achieved_value`. Every referenced metric must resolve to a metric of a pay program of this company and must currently be in `CERTIFIED`, or the analysis is refused with `ERR_METRIC_NOT_CERTIFIED`. Each referenced metric is re-run through the payout curve of §3.4 using its restated achievement, and the result is stored as `restated_payout_factor_pct` while the metric moves `CERTIFIED → RESTATED`; the metric's original `payout_factor_pct` and `original_payout_factor_pct` are left untouched, because the audit trail must keep both readings. Any metric of the period that the request does not name keeps its current `achieved_value` and hence its current factor.

The recovery scope is then assembled. In scope are the awards whose program's issuer is this company, whose `vehicle` is `ANNUAL_INCENTIVE` or `LONG_TERM_PSU`, whose status is `VESTED`, and whose `settlement_date` falls inside the lookback window, both bounds inclusive. Awards that are still `GRANTED`, already `FORFEITED` or already `CLAWED_BACK`, and `RSU` awards of any status, are out of scope. In-scope awards are processed in ascending `settlement_date`, ties broken by ascending `created_at`.

For each in-scope award, `original_factor_pct` on the resulting determination records the award's `certified_factor_pct` as it was originally certified, and `restated_factor_pct` is the award's vehicle factor recomputed from restated achievements — the same weighted sum as in §3.5, each metric's restated-or-current factor multiplied by its `weight_pct` divided by 100 with **each contribution rounded to two decimal places before the sum**, and the sum rounded again to two decimal places. Where the original factor is 0.00, division is impossible and the guard applies: `restated_amount_usd` is set to the award's `realized_value_usd` and `recoverable_amount_usd` to 0.00. Otherwise `restated_amount_usd` is the award's `realized_value_usd` multiplied by `restated_factor_pct` divided by `original_factor_pct`, rounded half-up to two decimal places, and `recoverable_amount_usd` is the award's `realized_value_usd` less that restated amount, rounded to two decimal places and floored at 0.00 — a restatement that would have paid *more* recovers nothing. A determination row is created, in status `CALCULATED`, only for awards whose `recoverable_amount_usd` is strictly greater than 0.00; awards yielding exactly 0.00 produce no row at all. Each row records the owning `restatement_event_id` and the `payout_award_id` it targets. The event's `determination_count` is the number of rows created and its `recoverable_total_usd` is the sum of their recoverable amounts, rounded to two decimal places. Where no award yields a positive recoverable amount the event still reaches `ANALYZED`, with a count of 0 and a total of 0.00.

Ordering recovery is a `CompCommitteeChair` action on an `ANALYZED` event — any other state is `ERR_EVENT_STATE_INVALID` — which moves the event `ANALYZED → RECOVERY_ORDERED` and, as its cascade, moves every `CALCULATED` determination of the event `CALCULATED → NOTICED`, stamping each row's `noticed_at` with the current logical time and incrementing each row's `version`.

The affected officer then acknowledges. A `NamedExecutiveOfficer` acknowledges a `NOTICED` determination — a determination in any other status is `ERR_DETERMINATION_STATE_INVALID`, and one belonging to another officer's award is `ERR_NOT_RESOURCE_OWNER` — which stamps `acknowledged_at` with the current logical time and records the acknowledging identifier as `acknowledged_by_user_id`. Determinations can be listed with filters on `restatement_event_id`, `payout_award_id` and `status`, with the officer-scoped restriction applying to that read as well.

Executing recovery is a `CompCommitteeChair` action, and it is gated three ways: the determination must be in `NOTICED`, or the answer is `ERR_DETERMINATION_STATE_INVALID`; `acknowledged_at` must be non-null, or the answer is `ERR_DETERMINATION_NOT_ACKNOWLEDGED`; and the acting `X-User-ID` must differ from `acknowledged_by_user_id`, or the answer is `ERR_SEGREGATION_OF_DUTIES`. Execution then runs a five-level cascade. First, the determination moves `NOTICED → RECOVERED`, `recovered_at` is stamped with the current logical time, the owning event recomputes `recovered_total_usd` as the sum of the recoverable amounts of its `RECOVERED` determinations, and — when every determination of the event has reached `RECOVERED` — the event itself moves `RECOVERY_ORDERED → CLOSED`. Second, caused by the first, the linked award moves `VESTED → CLAWED_BACK` with its `realized_value_usd` reduced by the determination's `recoverable_amount_usd` and its `realizable_value_usd` set equal to the new realized figure. Third, caused by the second, the award's program recomputes `realized_pay_total_usd`, `realizable_pay_total_usd`, `pay_percentile_rank`, `degree_of_alignment` and `alignment_status`. Fourth, caused by the third, every `SCREENED` screen of that program becomes `STALE`. Fifth, caused by the fourth, every `LEGAL_CLEARED` section of that program returns to `DRAFTING` with `revision_round` incremented.

Recovery can be undone, and the undo is a first-class compensating action rather than a deletion. A `CompCommitteeChair` reverses a `RECOVERED` determination — any other status is `ERR_DETERMINATION_STATE_INVALID` — supplying a mandatory `reversal_reason` explaining why, for instance because the restatement itself was withdrawn. The determination moves `RECOVERED → NOTICED` with `recovered_at` cleared; the owning event recomputes `recovered_total_usd` and, if it had already closed, reverts `CLOSED → RECOVERY_ORDERED`; the linked award moves `CLAWED_BACK → VESTED` with its `realized_value_usd` increased by the same `recoverable_amount_usd`, restoring exactly the pre-recovery figure, and its `realizable_value_usd` set equal to that restored realized figure; and the award's program recomputes `realized_pay_total_usd`, `realizable_pay_total_usd`, `pay_percentile_rank`, `degree_of_alignment` and `alignment_status`, carrying the same tail as the recovery it undoes: any movement in those figures marks the program's `SCREENED` screens `STALE` and, through them, sends its `LEGAL_CLEARED` sections back to `DRAFTING`. The determination's `version` increments. The pair of actions conserves dollars: for every determination, the award's `realized_value_usd` added to the event's `recovered_total_usd` is identical before the recovery and after its reversal. The parent event's status is always a function of its children's — it is re-derived on every child transition, including the reversal that moves a child back to `NOTICED`.
