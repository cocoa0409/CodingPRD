# Dealer Territory Parts Support API — Product Requirements Document

## 1. Introduction

An independent dealer network only works when the manufacturer can guarantee, dealer by dealer and product family by product family, that machines already in the field will be fed parts and kept running. This document specifies the product requirements for the Dealer Territory Parts Support API, the system of record behind that guarantee. It governs how an independent dealer is assigned a territory, how exclusive representation is asserted and defended, what stocking levels and emergency fill windows that dealer must honour, how remanufactured and certified rebuilds are adjudicated with core return credits, how the machine population is tracked so parts and service demand can be forecast, which technicians and tooling must be certified for a product family, how equipment financing and used-machine remarketing are coordinated, and how dealer performance is reviewed against market share and customer loyalty measures.

Two structural forces shape almost every rule that follows. The first is quota and allocation: the manufacturer does not simply take an order, it measures the dealer against a mandate derived from the machines that dealer is responsible for supporting, and it settles returned cores against an arrear rather than against a price. The second is compliance and audit: territory exclusivity, technician certification, tooling completeness, rebuild specification limits and warranty-safety limits are all conditions that must be checked before work is admitted, and the network's own representation history is evidence that can be superseded.

A third, quieter force is time. Every credential expires, every coverage plan can be suspended, every core credit has a settlement threshold, and every deferred re-evaluation has an epoch in which it may or may not fire. The logical clock is therefore a first-class input rather than background noise: it is set explicitly, it never silently reverts to real wall-clock time, and it drives derived statuses across certifications, coverage and service outcomes.

## 2. Global Specifications & System-Wide Principles

This section states the cross-cutting contract: how requests are authenticated and scoped, what every response looks like, how lists are paged, how identifiers and timestamps behave, how money and percentages are rounded, and how concurrent writers are kept from clobbering one another.

### 2.1. Dealer Network Roles, Headers and Actor Identity

Every request carries two mandatory headers. `X-User-ID` names the acting party and `X-User-Role` names its capacity. A request missing either header, or naming a role that is not one of the declared roles, is rejected with `ERR_UNAUTHENTICATED` at HTTP 401.

The network recognises seven roles. `DealerNetworkManager` owns the dealer network: dealer records, dealer agreements, representation intervals and party registrations. `DealerPerformanceReviewer` measures dealer performance through reviews, market-share observations and the underperformance finding on an agreement. `PartsManager` operates the stocking commitments, parts-order batches, rebuild core credits, support agreements and the machine population. `RebuildProgramSpecialist` adjudicates remanufactured and certified rebuild claims and authorised dealer repair programmes. `ServiceTechnicianSupervisor` runs the dealer service bench: emergency fills, restriction orders and SLA outcomes. `DealerSalesManager` sells machines under the dealership's own identity. `FinancePartner` approves OEM equipment financing against a submitted order. `InputDealer` is a read-only dealer principal used for ownership-scoped reads: a dealer may read only its own agreements, commitments, reviews, claims, support agreements, population records, observations and certifications.

Two of these roles are backed by a persisted entity. When `X-User-Role` is `DealerSalesManager`, `X-User-ID` is the `id` of the acting `Dealer`; ownership checks on any resource that references a `Dealer` compare the resource's foreign-key field to `X-User-ID`. When `X-User-Role` is `InputDealer`, the same applies: `X-User-ID` is the `id` of the acting `Dealer`, and every read this role performs is scoped to that dealer's own rows. A `DealerSalesManager` of one dealership therefore cannot act on another dealership's resources, and that attempt is rejected with `ERR_UNAUTHORIZED` at HTTP 403. The remaining roles — `DealerNetworkManager`, `DealerPerformanceReviewer`, `PartsManager`, `RebuildProgramSpecialist`, `ServiceTechnicianSupervisor` and `FinancePartner` — are opaque: when `X-User-Role` is one of these, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it, but it does not compare it to any entity's `id`.

One deliberate exception to the opaque rule is worth stating plainly because it is easy to get backwards. When `X-User-Role` equals `ServiceTechnicianSupervisor`, the `X-User-ID` value is read but is **not** compared to the owning `PartsCommitment.dealer_id`, so a service order opened for one dealer may be reviewed by any technician supervisor on the network. This exception is scoped to exactly two operations: beginning service work on a service order, and recording an emergency fill against a service order. On any other operation, a role acting outside its permitted set is rejected with `ERR_UNAUTHORIZED` at HTTP 403, and an operator whose credentials cannot be resolved to a dealer scope is rejected with `ERR_DEALER_SCOPE_MISMATCH` at HTTP 403.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints. `has_more` is true exactly while `offset + limit` is less than `total_count`. A request that reaches a path the surface does not define, or that reaches a defined path under a method the path does not declare, is answered from the not-found handler with `ERR_DEALER_NOT_FOUND` at HTTP 404 rather than with a method-not-allowed status.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` query parameter that caps how many resources come back, a default of 10 when the caller omits it, a floor of 1 and a ceiling of 100. A `limit` below the floor is raised to 1 and one above the ceiling is lowered to 100 rather than refused, and a `limit` that is not an integer is refused with `ERR_INVALID_REQUEST` at HTTP 400. The `offset` query parameter skips that many resources from the front of the result set and defaults to 0; a negative `offset` is clamped to 0 and a non-integer one is refused with `ERR_INVALID_REQUEST` at HTTP 400. Unless a list endpoint's own description says otherwise, results are ordered by creation timestamp ascending. Every paged list response carries `limit`, `offset`, `total_count` and `has_more` in the `meta` object alongside the request identifier and timestamp.

### 2.4. Logical Clock and Time-Derived Status

All STAFF roles may set the logical clock via `POST /dealer-network/_clock/set_current_utc`, supplying `to_iso8601` and receiving the resulting `current_utc`. A `to_iso8601` that is not a well-formed instant is refused with `ERR_INVALID_REQUEST` at HTTP 400. The server's startup default time is exactly `2026-09-01T00:00:00Z`; before any call to the clock endpoint the logical clock reads exactly that default and must never fall back to real wall-clock time. Setting the clock recomputes every time-derived status in the system: `CertificationRecord.status`, `SupportAgreement` coverage, and `ServiceOrder` SLA outcomes.

### 2.5. Identifiers, Timestamps, Versions and Version-Bearing Endpoints

Every top-level resource carries a system-minted `id` formatted as a UUID with no type prefix, plus `created_at` as an ISO 8601 UTC timestamp. Resources declared with the common field set — `Dealer`, `DealerAgreement`, `PartsCommitment`, `PartsOrderBatch`, `CertificationRecord`, `RebuildClaim`, `EquipmentOrder`, `TradeInUnit`, `SupportAgreement`, `MarketShareObservation`, `PartyRegistration`, `MachinePopulationRecord` and `ServiceOrder` — additionally carry `updated_at`, refreshed on any change to the resource's properties, and `version`, a system-managed integer that increments with every modification and that a freshly created resource carries at 1. Mutations to derived fields are still mutations: they refresh `updated_at` and increment `version` on the owning resource. Every resource also exposes a `status` field carrying its current state value from the enumeration defined for it in §3. The server-stamped instants are drawn from the logical clock rather than from real wall-clock time — a resource created before any clock call carries the startup default — and successive stamps inside one logical tick advance by a millisecond apiece, so creation order across resources stays total and deterministic even when several are written within the same tick. An instant supplied by the caller and an instant the server stamps are both rendered in the same three-fractional-digit UTC form.

`PerformanceReview` is the one resource declared without the common field set, and this must be handled explicitly. A performance review carries only `id` and `created_at`. It has no `updated_at` and no `version` field at all.

Creation of a new, stand-alone resource returns `201 Created`. Modification of an existing resource, including the creation of a nested row that is addressed through its parent, returns `200 OK`. A certification record may be registered either stand-alone or as a nested row addressed through its parent agreement at `POST /dealer-network/dealer-agreements/{id}/certification-records`; the nested form creates a credential whose `dealer_id` and `product_family` are taken from the parent agreement, so no `dealer_id` or `product_family` is supplied in its body, triggers the same recomputation cascade as the stand-alone form, and returns `200 OK`. Creating a resource whose body carries a duplicate value the resource declares unique is not a create-time refusal in every case: a `Dealer` whose legal name is already registered for the same territory code is refused with `ERR_INVALID_REQUEST` carried at HTTP 409, and so is a second live `SupportAgreement`, `MachinePopulationRecord`, `RebuildClaim` or `EquipmentOrder` for the same machine serial, and a `MachinePopulationRecord` reinstated onto a serial another live record already holds.

Before any of the workflow rules in §3 are evaluated, every request is put through a fixed validation ladder, and the rungs are checked in order rather than independently. The ladder is not merely a set of checks that must all hold — it is a priority order, so the first rung that fails determines the error the caller sees and later rungs are never reached on that request. The rungs, in order, are:

1. **Header and identity authentication.** Both `X-User-ID` and `X-User-Role` must be present, the role must be a declared role, and the identifier must equal the `id` of an instance of that role's backing entity when the role is entity-backed. Failure gives `ERR_UNAUTHENTICATED` at HTTP 401.
2. **Role permission and actor scope.** The acting role must be permitted for the operation, and an actor backed by an entity may not act on another entity's resource. Failure gives `ERR_UNAUTHORIZED` at HTTP 403. The actor's `X-User-ID` is compared to the resource's foreign-key dealer on creation of an equipment order and on every equipment-order mutation that walks the order's own dealer, in addition to the read-side scoping §2.1 describes.
3. **Technician-supervisor dealer scope.** The narrow exception of §2.1 is evaluated here, on the two operations it covers, so that its handling is deterministic rather than incidental. Only beginning service work and recording an emergency fill consult a dealer scope at all, and on those two a technician supervisor whose scope does not cover the order's dealer is refused with `ERR_DEALER_SCOPE_MISMATCH` at HTTP 403. Because the identifier a technician supervisor presents is opaque and is never compared to the order's dealer, the rung in practice refuses only an actor whose credentials cannot be resolved to any dealer scope at all; every resolvable supervisor passes it. The remaining service-bench transitions — escalating, filling, reopening, raising or lowering a restriction, and resolving — are driven by the supervisor role as well and are checked at the role rung rather than here.
4. **Referenced-resource existence.** Referenced resources must exist, and body foreign keys are validated in the order the endpoint's own input list declares them, left to right. The first missing referent produces its own 404 identifier — `ERR_DEALER_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_COMMITMENT_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, `ERR_REVIEW_NOT_FOUND` or `ERR_POPULATION_NOT_FOUND` — at HTTP 404.
5. **State admissibility.** The target resource must be in a state that admits the operation, and every from-state not listed for a trigger is refused with that operation's invalid-state error, `ERR_INVALID_STATE` at HTTP 409. Two rungs-5-adjacent refusals are carried by the same invalid-state identifier while they rest on a condition rather than a from-state: reopening a service order whose linked commitment holds an `ORDERED` batch, and terminating a support agreement while a service order referencing its machine serial is `OPEN` or `IN_PROGRESS`.
6. **Business safety.** Certified-rebuild specification limits and warranty-safety limits are checked here: the machine's `machine_operating_weight_lb` against the specification's maximum weight, the specification's technician certification minimum against the agreement's `certified_technician_count`, and the destination of a remanufactured core. Failure gives `ERR_REBUILD_SPEC_EXCEEDED` at HTTP 422. This rung is reached on rebuild-claim approval and on rebuild delivery, and nowhere else.
7. **Business constraint.** Availability, stocking and mandate limits are checked here: the emergency availability target against the stocking mandate's hard cap, and the aggregate batch reservation condition in which `requested_units` exceeds `available_commitment_units`. Failure gives `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409. The two conditions this rung names are not the only ones that speak through that identifier, and none of them sits on this rung on every operation that can raise it: a commitment reinstated out of `PERFORMANCE_DEFICIENT` while its availability deficit persists, a core credit settled up to or past the mandate threshold, and a batch closed before the settlement has cleared all answer with the hard-cap identifier, as does a rebuild-claim approval whose supplied version reference no longer matches the claim.
8. **Fiscal limit.** The trade-in appraisal is checked against the financed list price, so that an attached trade-in whose appraised value reaches the list price is refused with `ERR_TRADE_IN_APPRAISAL_EXCEEDS_PRICE` at HTTP 409.
9. **Population and representation referential limits.** A machine's serial must be live in the dealer's population before a rebuild claim can be tied to it, and a superseded party registration blocks the decline path. Failure gives `ERR_MACHINE_NOT_IN_POPULATION` at HTTP 409.

Nothing above the rung that failed is re-checked after the fact, and a rung that passes never re-raises. A request whose body is malformed, whose required field is missing, whose field is unknown, or whose value falls outside its declared type or enum is refused earlier than any of these with `ERR_INVALID_REQUEST` at HTTP 400, because no rung in the ladder can be evaluated against a body that does not parse into the declared shape.

#### 2.5.1. Optimistic Concurrency Control

Three create operations participate in optimistic concurrency control, and only these three carry a version precondition that can reject a request.

Creating a `DealerAgreement` requires the caller to supply `expected_dealer_version` alongside `dealer_id`, `product_family`, `territory_code`, `exclusivity_level`, `start_at`, `end_at` and `performance_plan_share_pct`. The target dealer is resolved first and the supplied value must match that dealer's current `version`; an `end_at` not strictly after `start_at`, and a `performance_plan_share_pct` outside the 0-to-100 band, are refused with `ERR_INVALID_REQUEST` at HTTP 400. When another writer has advanced that dealer's version since the client last read it, the create is refused with `ERR_STALE_VERSION` at HTTP 412. This covers the case where another writer has just created an agreement for the same territory and product family — which, as §3.2 explains, legitimately supersedes the prior representation — leaving the current writer's view of the dealer stale. Creation of the agreement also increments `Dealer.version` by 1 and recomputes the new agreement's `tooling_compliance_status`.

Creating a `PartsCommitment` requires `expected_dealer_version` alongside `agreement_id`, `dealer_id`, `product_family`, `machine_population_units`, `machine_population_slope`, `planned_annual_units`, `emergency_stocking_target_pct` and `emergency_fill_window_hours`. The owning agreement is resolved before the dealer, the supplied version value must match the target dealer's current `version`, and only then are the body's own values examined: a `product_family` that does not equal the agreement's, and an `emergency_stocking_target_pct` outside the open-closed band above 0 and up to 100, are each refused with `ERR_INVALID_REQUEST` at HTTP 400. When another writer has advanced that dealer's `version` — for instance by having just created a commitment for the same product family, which supersedes the prior stocking mandate — the create is refused with `ERR_STALE_VERSION` at HTTP 412. A successful creation increments `Dealer.version` by 1 and recomputes the new commitment's `machine_population_tier`, `required_stocking_units`, `required_stocking_units_final`, `availability_target_pct` and `emergency_tier`.

Creating a `PerformanceReview` requires `expected_dealeragreement_version` alongside `dealer_id`, `agreement_id`, `period_start`, `period_end`, `actual_territory_machine_units`, `territory_market_machine_units`, `sampled_service_orders`, `met_sla_service_orders` and the optional `circumstance_note`. The dealer is resolved before the agreement, the supplied version value must match the target agreement's current `version`, and only then are the body's own values examined: a `period_end` not strictly after `period_start` and a `met_sla_service_orders` above `sampled_service_orders` are each refused with `ERR_INVALID_REQUEST` at HTTP 400. When another writer has advanced the agreement's version — for instance by having just opened a review for the same period — the create is refused with `ERR_STALE_VERSION` at HTTP 412. A successful creation increments `DealerAgreement.version` by 1 and computes the review's `actual_market_share_pct`.

No endpoint outside these three declares a stale-version precondition. In particular, the state-transition endpoints on agreements, commitments, batches, claims, orders, agreements of support, orders of service and population records accept no `expected_*_version` input that can reject the request; the version integers they increment are outputs, not preconditions. One further input the surface tolerates on any operation is a version precondition field it does not itself declare: `expected_dealer_version`, `expected_dealeragreement_version` and `expected_rebuildclaim_version` are accepted without tripping unknown-field detection wherever they are supplied, and each rejects only when a value is supplied and no longer matches. On the three creates, an omitted precondition skips the check entirely rather than failing it, and because the field is a precondition rather than a required property, omitting it on a create does not raise the missing-field error either. `expected_rebuildclaim_version` is the one further precondition, attached to rebuild-claim approval alone; when it is supplied and no longer matches the claim's current version the request is refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409, not with the stale-version error the three creates raise. The one further rejection that approval raises is the specification and priority gate described in §3.7, and a successful approval increments the claim's version by 1. Each of the three creates refuses in its own order: header and identity, then the version precondition, then the referents the body names in the order the endpoint declares them, then the body's own value checks.

### 2.6. Nested Resource Retrieval

When a request path names several resources in a chain, the system resolves each identifier strictly left to right and rejects at the first one that does not resolve, with the 404 code that belongs to that level. A read of a dealer's agreements fails with `ERR_DEALER_NOT_FOUND` at HTTP 404 if the dealer does not exist, long before any agreement is considered. A read of an agreement's parts commitments fails with `ERR_AGREEMENT_NOT_FOUND` at HTTP 404 for a missing agreement. A read of a commitment's parts-order batches fails with `ERR_COMMITMENT_NOT_FOUND` at HTTP 404 for a missing commitment. A read of a commitment's service orders likewise resolves the commitment first. A read of a dealer's rebuild claims, support agreements, market-share observations, certification records, machine population records, equipment orders or service orders resolves the dealer first and fails with `ERR_DEALER_NOT_FOUND` if it is absent. A read of a batch, a claim, a review or a population record by its own identifier fails with `ERR_COMMITMENT_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, `ERR_REVIEW_NOT_FOUND` or `ERR_POPULATION_NOT_FOUND` respectively. The remaining single-resource reads borrow the identifier of the level they sit under rather than minting their own: a service order read by its own identifier fails with `ERR_COMMITMENT_NOT_FOUND`, and a support agreement read by its own identifier fails with `ERR_AGREEMENT_NOT_FOUND`, while an equipment order, a trade-in unit, a certification record, a market-share observation and a party registration read by their own identifiers each fail with `ERR_DEALER_NOT_FOUND`, the code that stands in for a missing row at a level that declares no not-found code of its own. For writes that take foreign keys in the body rather than the path, existence is checked in the order the endpoint's own input list declares the keys, left to right, and the first missing referent produces its own 404.

### 2.7. Mandate Arithmetic, Rounding and Precision

Money in this system is stored in integer cents, but several credit and fee figures are rounded to two decimal places using the half-up rule — the digit that is exactly halfway is rounded away from zero. Percentages are rounded half-up to four decimal places unless stated otherwise: `actual_market_share_pct`, `performance_ratio_pct`, `quality_deficiency_pp`, `discrepancy_pp`, `observed_share_pct`, `availability_target_pct`, `coverage_multiplier`, `weight_class_tier_multiplier`, `tier_weighted_machine_population`, `fill_rate_pct`, `market_share_from_observations_pct` and `dealer_coverage_pct` all carry four decimal places. `loyalty_score`, `machine_lifetime_value`, `core_return_credit_cents`, `rebuild_fee_cents` and `credited_settlement_units_increment` carry two. `risk_score`, `priority_rank`, `deferral_tier`, `text_sweep_est_monthly_parts_value_cents`, `text_sweep_vendor_code_matches`, `forecast_parts_demand_units` and the two stocking-unit variants are integers with no fractional part. Each rounded figure is served in the narrowest form that carries its value: a four-place reading whose fourth decimal is zero, and a two-place reading whose second decimal is zero, is emitted as an integer rather than as a trailing-decimal float.

The stocking mandate is the pivot on which most of the quota logic turns, and it exists in two deliberately different variants. The numerator used to derive a commitment's tier is `machine_population_units` multiplied by `machine_population_slope`, rounded half-up to two decimal places, with the rounded numerator then serving every downstream reading that consumes it. The tier band follows the edges upward: a numerator below 100 is `MICRO`, 100 or more but below 500 is `SMALL`, 500 or more but below 1500 is `MEDIUM`, and 1500 or more is `LARGE`. The 100, 500 and 1500 edges belong to the higher tier — a numerator of exactly 100 is `SMALL`, exactly 1500 is `LARGE`, and exactly 99.99 is `MICRO`.

The stocking mandate itself uses a per-machine rate selected by the emergency fill window. A `BASIC` window uses a rate of 0.101 units per machine; a `STANDARD` window uses 0.127; a `PREMIUM` window uses 0.152. The `STANDARD` rate is exactly the average of the `BASIC` and `PREMIUM` rates, computed as the sum of 0.101 and 0.152 divided by two, so a reading that failed to name the middle band can only resolve to the average the two named bands imply. Two targets are then formed: one from the rate, being the tier-weighted numerator multiplied by the per-machine rate, and one from the dealer's plan, being `planned_annual_units` divided by 800. The active variant takes the larger of the ceiling of the rate target and the ceiling of the fill target, so it never rounds a term down. The final variant takes the larger of the floor of the rate target and the floor of the fill target, so it never rounds a term up, and `required_stocking_units_final` is therefore less than or equal to `required_stocking_units` on every input. Both are whole units. Recomputing the mandate also re-keys `emergency_tier`, `machine_population_tier`, `availability_target_pct` and `available_commitment_units` in the same pass, and re-keying `available_commitment_units` is not by itself the availability edge that moves a commitment to `PERFORMANCE_DEFICIENT` — that automatic move belongs to the flows §3.4 names and is not triggered by a plain recompute.

### 2.8. Emergency Fill, Restriction Priority and Service Risk

Every service order carries a `kind`, one of `EMERGENCY_FILL`, `RESTRICTION` or `SLA_AUDIT`; all three share a single response-window treatment. Its `response_window_hours` is derived from the linked commitment's `emergency_fill_window_hours` and is fixed at the moment the order is opened into active work, so opening an order copies the commitment's window immediately. A recorded response `sla_hours` meets the window when it is less than or equal to `response_window_hours`; a response landing exactly on the window is met, so the upper bound is inclusive. Setting the clock recomputes these outcomes across the surface, which re-keys `priority_rank`, `risk_score`, `emergency_filled_units` and the dealer's `deferral_tier` on every order and re-derives the window of every order still `OPEN` or `IN_PROGRESS`.

Restriction severity runs `HOURS_SPENT`, then `METER_RUNNING`, then `FULL_STOP`, in increasing order, and it is declared by `restriction_scope`. The derived `priority_rank` is 3 for `FULL_STOP`, 2 for `METER_RUNNING` and 1 for `HOURS_SPENT`. The derived `risk_score` multiplies `priority_rank` by ten, adds ten when the order's `kind` is `EMERGENCY_FILL`, and adds five more when the order's `machine_serial` is covered by an `ACTIVE` support agreement whose `plan_tier` is `PREMIUM`. `risk_score` is a plain integer. The severity ladder is the pivot the restriction rise and fall step along, and recomputing an order re-keys `priority_rank`, `risk_score` and its `emergency_filled_units` together from the order's own fields.

The deferral tier attached to a restriction is `1 + priority_rank` when the dealer's ordering target list holds at least one candidate, and 0 when it holds none. The ordering target list is the dealer's `RESTRICTION` service orders whose `status` is `OPEN` and whose `machine_serial` is on one of the dealer's `ACTIVE` machine population records. When candidates must be attributed an order, they are ranked by `sla_hours` ascending and then by `created_at` ascending, and never by `id`. The tier is a property of every service order of that dealer — each of that dealer's orders is re-keyed to the same candidate-or-no-candidate outcome when the list is recomputed, whatever the order's own kind or status.

### 2.9. Coverage, Forecast Multipliers and Population Stability

Three multiplier lookups recur throughout the system and are defined once here. Coverage is `coverage_multiplier`: 1.5 when an `ACTIVE` support agreement with `plan_tier` `PREMIUM` covers the serial, 1.25 for `PLUS`, and 1.0 otherwise; it is recorded to two decimal places, half-up. Weight class is `weight_class_tier_multiplier`, derived from `machine_operating_weight_lb`: below 40000 pounds `LIGHT`, from 40000 pounds through 100000 pounds inclusive at both edges `MIDDLE`, and above 100000 pounds `HEAVY`; the multiplier is 0.8 for `LIGHT`, 1.0 for `MIDDLE` and 1.2 for `HEAVY`, recorded to two decimal places, half-up. Family base demand is `base_annual_parts_units`, fixed per product family at 40 for `EXCAVATION`, 48 for `EARTHMOVING`, 28 for `COMPACTION`, 60 for `POWER_SYSTEMS` and 36 for `LIFT_TRUCK`.

A population record's `projected_annual_parts_units` is the family base demand multiplied by the serial's coverage multiplier and then by the weight class multiplier, with the product rounded up to the next whole unit. The record's `weight_class_tier` and its serial-bound `coverage_multiplier` are re-keyed in the same pass as that product, so `coverage_multiplier` reads 1.0 when no `ACTIVE` support agreement covers the serial and the covering plan's multiplier otherwise.

The canonical dealer forecast, served by `GET /dealer-network/machine-population-records/forecast` for a supplied `dealer_id`, is the `per_record_ceiling` variant: each `ACTIVE` record's product is rounded up to the next whole unit individually and the rounded values are then summed, with no further rounding. The response exposes `forecast_parts_demand_units` from that variant together with `per_record_total` and `sum_then_ceiling_total`. The `sum_then_ceiling` variant is the illustrative alternative used to show where the two readings diverge: it sums the per-record products exactly and rounds the total up once. `RETIRED` records contribute nothing to either variant.

The coverage snapshot for a single machine, served by `GET /dealer-network/machine-population-records/{id}/coverage-snapshot`, returns `machine_serial`, `coverage_pct` and `weight_class_tier`. Its `coverage_pct` is 100 multiplied by the serial's coverage multiplier and divided by 1.5 when the machine has an `ACTIVE` support agreement; otherwise it is 100 multiplied by `machine_population_units` and divided by the larger of 1 and the tier-weighted numerator, where the record itself carries no such count and the figure is borrowed from the dealer's commitment for the record's product family. Both readings carry four decimal places, half-up. When the dealer holds no commitment for that family the reading is 0.0. The `coverage_multiplier` the snapshot borrows is the serial's covering agreement's multiplier, which is 1.0 when no `ACTIVE` agreement covers it, so an uncovered machine whose family carries no commitment reads 0.0 while an uncovered machine whose family carries a commitment reads 100 divided by the larger of 1 and that commitment's tier-weighted numerator.

### 2.10. Core Credit, Rebuild Pricing and Settlement Constants

Core credits and rebuild fees are priced once and never repriced. The named constants below recur in §3 and are stated here so the arithmetic is unambiguous. `CORE_CREDIT_RATE` is 1.4 and `CERTIFIED_HANDLING_MARGIN` is 0.15. The labour-rate weight factor is 0.0025. The planned annual divisor is 800. The settlement arrear on a mandate is 103040 cents, and one returned core settles 1610 cents of it. The restriction unit value used when offsetting a dealer working balance is 150 cents. The service risk priority multiplier is ten, the emergency bonus is ten and the premium-coverage age bonus is five — that last being the five points the risk score adds for a machine serial covered by an `ACTIVE` support agreement at the `PREMIUM` tier. The quality spread threshold is 10.0 percentage points. The loyalty customer-satisfaction bonus is 3.0 percent. The availability surrogate base is 92.0 percent, its slope per percentage point of emergency target is 0.1, its knee sits at an emergency target of 60 percent, and its cap is 4.0 percentage points. The emergency fill denominator is 2 for a gross fill of 8.0 or less and 4 above that, and the first-tier fill max is 8.0. The middle band's inclusive weight edges are 40000 and 100000 pounds. A certification is a one-year credential: a record is `ACTIVE` while the logical clock stands before its `certified_at` plus one year, and a recurrence interval likewise runs from a certification instant up to but not including twelve months after it. The certified credit reduction applied to the final stocking variant when a rebuild is certified is one unit.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Dealership

A `DealerNetworkManager` opens a dealership by creating a `Dealer` with its `legal_name`, its two-letter `home_state_code` and its `territory_code`. The registered legal name must be unique per territory code, compared explicitly and case-sensitively, and the territory code is required and becomes immutable after creation: a dealership does not change territory. A duplicate legal name for the same territory is refused with `ERR_INVALID_REQUEST` carried at HTTP 409 rather than with the create's usual 201. The response carries `certified_family_count`, `trusted_commitment_count`, `open_backorder_units` and `market_share_pct`; the first three are initialised to 0 at creation and `market_share_pct` starts at 0.0. The new dealer's `status` begins at `PENDING_AGREEMENT`, and it stays there until the dealer holds at least one dealer agreement in `STORE_READY` standing.

The four derived counters on a dealer are worth naming together because they move for different reasons. `certified_family_count` counts the distinct product family values for which the dealer holds a certification record whose `status` is `ACTIVE`. `trusted_commitment_count` counts the dealer's agreements whose `trusted_commitment` flag is true. `open_backorder_units` sums `unfilled_units` across the parts-order batches whose commitment belongs to this dealer and whose `status` is `OPEN` or `CORE_PENDING`. `market_share_pct` reports the latest `PerformanceReview.actual_market_share_pct` across this dealer's reviews, and reads 0.0 when no review has been evaluated. The latest is taken by `created_at` ascending with no id-based tie-break, and only reviews that carry a computed share — those that have had results recorded or evaluated — are considered, so a review still in `DRAFT` has no share to contribute. Reading a single dealer by its own identifier recomputes all four counters for the caller but does not treat the read as a mutation, so the dealer's `updated_at` and `version` are left where the read found them.

### 3.2. Territory Representation, Exclusivity and Party Registration

A dealership's representation of a machine family is recorded as a `DealerAgreement`, created by a `DealerNetworkManager` in `DRAFT`. It binds a `dealer_id` and a `product_family`, one of `EXCAVATION`, `EARTHMOVING`, `COMPACTION`, `POWER_SYSTEMS` or `LIFT_TRUCK`, and it is immutable in that family after creation. It declares a `territory_code`, an `exclusivity_level` that defaults to `SHARED` and may be `EXCLUSIVE`, an inclusive `start_at`, an exclusive `end_at` that must be strictly after `start_at`, and a `performance_plan_share_pct` expressed in percent points between 0 and 100. A share outside that band, or an `end_at` not strictly after the `start_at`, is refused with `ERR_INVALID_REQUEST` at HTTP 400. An `EXCLUSIVE` agreement asserts sole representation inside the territory for that product family over the half-open interval running from `start_at` up to but not including `end_at`. An agreement's `territory_code` must equal its owning dealer's territory code when the agreement is `EXCLUSIVE`; a mismatch is refused with `ERR_AGREEMENT_EXCLUSIVITY_MISMATCH` at HTTP 409. Creating an agreement against a dealer already in `TERMINATED` is refused with `ERR_DEALER_TERMINATED` at HTTP 409 before the version precondition is examined.

The lifecycle of an agreement runs `DRAFT`, `SUBMITTED`, `ACTIVE`, and then either `SUSPENDED` or `PERFORMANCE_DEFICIENT`, with `TERMINATED` as the single terminal state reachable from either `ACTIVE` or `SUSPENDED`.

Submission moves an agreement from `DRAFT` to `SUBMITTED` and runs the exclusivity overlap determination. Three things happen in that determination. First, an `EXCLUSIVE` submission is refused with `ERR_TERRITORY_OVERLAP` at HTTP 409 when another agreement with the same `territory_code` and the same `product_family` and an `exclusivity_level` of `EXCLUSIVE` is already in `SUBMITTED` or `ACTIVE` over an interval that overlaps the submission's interval. Second, the `performance_plan_share_pct` is examined against the ceiling of 100: a value of exactly 100 is accepted and recorded verbatim, while a value above 100 is rejected with `ERR_TERRITORY_OVERLAP` at HTTP 409 — the same code that the overlap test raises. Third, when a superseded `EXCLUSIVE` row for the same territory code and product family exists in `TERMINATED` with an `end_at` not after the current instant, the oldest such row is first revived: it is reset so that its `start_at` becomes the current instant, its `end_at` becomes the current instant plus one year, and its `status` becomes `SUBMITTED`, and it then takes part in the overlap determination as a live row. The revival runs ahead of both the overlap test and the share-ceiling test, so a submission that revives a row and then fails the share ceiling leaves the revived row standing in `SUBMITTED`. Only after that revival does the submission proceed. Submission always recomputes the agreement's `certified_technician_count` and `tooling_compliance_status`, and it deactivates the default deferred shortage rule on every commitment of the agreement.

A `DealerAgreement` also carries computed operating figures that the rest of the network depends on. `certified_technician_count` counts the distinct `technician_name` values among certification records with `status` `ACTIVE` that match this dealer and this product family. `performance_actual_share_pct` reports the actual territory share from the most recently evaluated performance review for this agreement, taken in `created_at` ascending order with no id-based tie-break, and reads 0.0 before the first evaluation. `tooling_compliance_status` is `NOT_SUBMITTED` while the agreement holds no certification record at all, `PARTIAL` while `certified_technician_count` is below the product family minimum of 2, and `COMPLIANT` once it reaches 2 — with the further requirement that `COMPLIANT` also requires the product family's tooling kit registration to be present. `trusted_commitment` is true only when `tooling_compliance_status` is `COMPLIANT` and a commitment for this agreement exists in `ORDER_READY`. `closed_at` is stamped when the agreement reaches `TERMINATED`; a superseded agreement retains its terminal stamp and is superseded by the successor row rather than erased.

Activation moves `SUBMITTED` to `ACTIVE` and is gated on four conditions holding together. The agreement's `tooling_compliance_status` must be `COMPLIANT`, so a shortfall here is refused with `ERR_TOOLING_INCOMPLETE` at HTTP 409. The `certified_technician_count` must be at least 2, which is the same check seen from the head-count side and carries the same error. At least one commitment of the agreement must exist and at least one of them must not be sitting in `PLANNED`; an agreement whose commitments are all still `PLANNED` is refused with `ERR_INVALID_STATE` at HTTP 409. A final variant below one unit is refused with `ERR_STOCKING_MANDATE_UNMET` at HTTP 409. Finally, the owning dealer must not be `TERMINATED`; that case is refused with `ERR_DEALER_TERMINATED` at HTTP 409. Activation recomputes `machine_population_tier`, `required_stocking_units`, `required_stocking_units_final` and `availability_target_pct` for every commitment of the agreement, re-keys its own `trusted_commitment` and the owning dealer's `trusted_commitment_count`, increments `DealerAgreement.version` by 1, and — when the dealer's `trusted_commitment_count` is at least 1 — drives `Dealer.status` to `ACTIVE`.

The dealer's own status follows its agreements automatically. A dealer in `PENDING_AGREEMENT` becomes `ACTIVE` the moment `trusted_commitment_count` reaches 1, and that automatic move reactivates the default deferred shortage rule for every commitment of the dealer. A dealer in `PENDING_AGREEMENT` becomes `SUSPENDED` automatically when every one of its agreements is `SUSPENDED`, with no other consequence. A dealer in `ACTIVE` becomes `SUSPENDED` automatically when no agreement of that dealer is `ACTIVE`, and that move deactivates the default deferred shortage rule for every commitment of the dealer. A dealer in `SUSPENDED` returns to `ACTIVE` automatically as soon as at least one agreement of that dealer returns to `ACTIVE`, and that move reactivates the rule for every commitment of the dealer.

Termination ends an agreement, and it behaves differently depending on the state it is leaving. Leaving `ACTIVE` for `TERMINATED` carries two requirements. Every commitment of the agreement must be either `COMPLETE` or `CORE_PENDING` with a `credit_balance_cents` of 0, and no batch of the agreement's commitments may be `OPEN` or `ORDERED`; that second condition is refused with `ERR_AGREEMENT_COMMITMENT_OPEN` at HTTP 409, and a commitment that is neither `COMPLETE` nor a zero-balance `CORE_PENDING` is refused with the same identifier, so an empty-but-settled commitment is admitted while a `PLANNED` or `ORDER_READY` one is not. Leaving `SUSPENDED` for `TERMINATED` carries only the batch condition, again refused with `ERR_AGREEMENT_COMMITMENT_OPEN` at HTTP 409. In both cases `DealerAgreement.closed_at` is stamped with the server timestamp and `Dealer.certified_family_count` is recomputed. Terminating from `ACTIVE` additionally suspends every `ACTIVE` commitment of the agreement — and every `ORDER_READY` commitment with it — terminates every `ACTIVE` support agreement bound to a machine serial of this dealer, and drives `Dealer.status` to `TERMINATED` only when every agreement of the dealer is itself `TERMINATED`. Terminating an agreement that is already `TERMINATED`, or one that is still `DRAFT` or `SUBMITTED`, is refused with `ERR_DEALER_TERMINATED` or `ERR_INVALID_STATE` respectively. In every case the terminating agreement has its `trusted_commitment` re-keyed and its owning dealer's `trusted_commitment_count` recomputed.

Party registration is a separate, thinner record. A `DealerNetworkManager` registers a `PartyRegistration` with a `dealer_id`, a `territory_code` and a `registered_at`, and it starts in `REGISTERED`. A party registration becomes `SUPERSEDED` as soon as a later registration for the same `territory_code` is written; a second registration for the territory therefore supersedes the first, and every earlier registration for that territory becomes `SUPERSEDED` in the same operation. Only rows still in `REGISTERED` are superseded, so an already-`SUPERSEDED` row is left as it is.

Closing the dealership itself is the last act of the representation lifecycle, and a `DealerNetworkManager` may perform it from any non-terminal dealer state. The precondition is identical on all three: every agreement of the dealer must already be `TERMINATED`. A dealer still holding a live agreement is refused with `ERR_DEALER_TERMINATED` at HTTP 409, and so is a dealer already in `TERMINATED`, which is refused with the same identifier rather than with an invalid-state error. The consequences differ by the state being left. A dealer terminating out of `PENDING_AGREEMENT` has every certification record of the dealer revoked. A dealer terminating out of `ACTIVE` has every support agreement of the dealer terminated and every certification record of the dealer revoked. A dealer terminating out of `SUSPENDED` has every support agreement of the dealer terminated. Revocation on this path marks the credential revoked and clears the derived `ACTIVE` standing, and termination of a support agreement on this path clears the serial's coverage. `TERMINATED` is terminal, and a terminated dealer or agreement admits no further operation, so any later mutation aimed at one is refused with `ERR_DEALER_TERMINATED` at HTTP 409. A `Dealer.status` set by termination is not walked back by the automatic agreement-driven transitions, which leave a `TERMINATED` dealer where it stands.

### 3.3. Certification, Tooling and the Technician Bench

Technician credentials are recorded as `CertificationRecord` rows, created for a `dealer_id` and a `technician_name` against a `product_family`, with a `credential_code` of either `DEALER_MASTER` or `DEALER_CERTIFIED` and a `certified_at` instant that begins the credential's validity interval. The technician name is the identity key inside the dealership and is not a server-minted identifier. The product family is immutable after creation.

A credential's `recurrence_within_period` is true when another certification record that is not `REVOKED` exists for the same dealer, the same product family and the same technician name with a `certified_at` inside the interval running from this record's `certified_at` up to but not including twelve months after it. Such a recurrence keeps the credential `ACTIVE` past its nominal expiry while it is in force. The record's `status` is one of `ACTIVE`, `EXPIRED` or `REVOKED`, and for everything but an explicit revocation it is derived on read from `certified_at`, `recurrence_within_period` and the logical clock. A credential is `ACTIVE` while the clock stands before its own `certified_at` plus one year; once it is past, an overlapping recurrence that is itself still within its own year keeps it `ACTIVE`, and a credential with no such live recurrence reads `EXPIRED`. The recurrence flag on every row of the dealer, family and technician is re-keyed whenever a credential is registered, and setting the clock re-derives both the flag and the status across the surface.

Registering a credential, and revoking one, both recompute the dealer's `certified_family_count`, the agreement's `certified_technician_count` and the agreement's `tooling_compliance_status`. Revocation is the explicit `ACTIVE` to `REVOKED` step; recall that revocation of the pair that had been holding an agreement at `COMPLIANT` is what pushes it back down to `PARTIAL`. Revoking a credential whose derived status is not `ACTIVE` is refused with `ERR_INVALID_STATE` at HTTP 409, so an already-expired or already-revoked credential has nothing to revoke.

### 3.4. The Stocking Mandate

A stocking commitment is created by a `PartsManager` in `PLANNED` against an `agreement_id` and a denormalised `dealer_id`. It declares a `product_family` that must equal the agreement's product family — a mismatch is refused with `ERR_INVALID_REQUEST` at HTTP 400 — and is immutable after creation, a `machine_population_units` count of the family in the territory as declared at submission, a `machine_population_slope` trend factor that defaults to 1.0 and whose constant 1.0 absorbs a territory whose growth is not stated, a `planned_annual_units` plan, an `emergency_stocking_target_pct` in the open-closed range above 0 and up to 100 — a value outside that range is refused with `ERR_INVALID_REQUEST` at HTTP 400 — and an `emergency_fill_window_hours`.

The fill window is not just a duration, it is the selector for both the rate and the tier. A window of 8 hours or fewer is a `PREMIUM` emergency tier, a window of 24 hours or fewer is `STANDARD`, and a window above 24 hours is `BASIC`; `emergency_tier` is refreshed on every recompute of the stocking mandate. The mandate itself requires a window of 24 hours or less, and a value above 24 caps the required stocking level rather than silently extending the mandate. The rate per machine follows the tier: 0.101 for `BASIC`, 0.127 for `STANDARD` and 0.152 for `PREMIUM`, with the `STANDARD` figure being exactly the average of the other two. The same 8-hour and 24-hour edges are inclusive at the top: a window of exactly 8 hours is `PREMIUM` and one of exactly 24 is `STANDARD`, so a window strictly above 24 is the only reading that lands `BASIC`.

Two further derived figures ride alongside the mandate. `committed_units` is the sum of the outstanding, not-yet-received units of every batch of the commitment that has not been cancelled or closed, so a batch still `OPEN` or `ORDERED` contributes its whole reservation while a received, partially-returned or core-pending batch contributes only its unallocated remainder. `fill_rate_pct` is the fulfilled share of everything the commitment has taken on — `fulfilled_units` divided by the sum of `fulfilled_units` and `committed_units` — taken to four decimal places half-up, and reading 0.0 when that sum is zero. `available_commitment_units` is the larger of 0 and the final stocking variant minus `committed_units`, recomputed whenever either `required_stocking_units_final` or `committed_units` changes. `availability_target_pct` is the emergency availability surrogate: it begins at 92.0 and adds one tenth of a percentage point for every percentage point by which `emergency_stocking_target_pct` exceeds 60, but never more than 4.0 percentage points in total, so the surrogate sits at 92.0 for a target of 60 or less and tops out at 96.0, the cap being reached at a target of 100. `fulfilled_units` is likewise re-keyed from the batches: a `CLOSED` batch contributes its whole `requested_units`, while a batch in `RECEIVED`, `PARTIALLY_RETURNED` or `CORE_PENDING` contributes its `reserved_units` less its still-`unfilled_units` remainder.

Submission moves a commitment from `PLANNED` to `SUBMITTED`, requires that the owning agreement be `SUBMITTED` or `ACTIVE` — otherwise the request is refused with `ERR_INVALID_STATE` at HTTP 409 — and requires a `planned_annual_units` of at least 1, likewise refused with `ERR_INVALID_STATE`. Submission recomputes `machine_population_tier`, `required_stocking_units`, `required_stocking_units_final` and `availability_target_pct`. A commitment already in `COMPLETE` refuses every later transition, submission and order-readiness included, with `ERR_INVALID_STATE` at HTTP 409.

Becoming order-ready moves `SUBMITTED` to `ORDER_READY` and is gated on three conditions: `required_stocking_units_final` at least 1, the owning agreement's `tooling_compliance_status` equal to `COMPLIANT`, and `machine_population_tier` other than `MICRO`, the last of which is refused with `ERR_STOCKING_MANDATE_UNMET` at HTTP 409 while a shortfall in tooling compliance is refused with `ERR_TOOLING_INCOMPLETE`. It sets the owning agreement's `trusted_commitment` to true, recomputes `Dealer.trusted_commitment_count`, drives `Dealer.status` to `ACTIVE` when `trusted_commitment_count` is at least 1, and reactivates the default deferred shortage rule. A final variant under one unit is the case the network calls an unmet mandate and is refused with `ERR_STOCKING_MANDATE_UNMET` at HTTP 409.

A commitment falls into trouble automatically. The moment `available_commitment_units` drops below the final stocking variant minus `committed_units`, and the commitment is `ORDER_READY`, the system moves it to `PERFORMANCE_DEFICIENT` with no client request. That automatic transition stamps `backorder_opened_at` with the server timestamp, deactivates the default deferred shortage rule, recalculates `Dealer.open_backorder_units`, and opens a service order of kind `EMERGENCY_FILL` against the commitment. The commitment can be returned to `ORDER_READY` by a `PartsManager` once `available_commitment_units` is at least the final variant minus `committed_units`; a reinstatement that still falls short of that edge is refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409. That reinstatement reactivates the rule and clears `backorder_opened_at`. Reinstating out of `SUSPENDED` instead requires the owning agreement to be `ACTIVE` and reactivates the rule without touching the stamp. The automatic move is the only party that opens the emergency service order: a reinstatement back to `ORDER_READY` does not.

Suspension moves `ORDER_READY` to `SUSPENDED` and is refused with `ERR_COMMITMENT_BATCH_OPEN` at HTTP 409 while any parts-order batch of the commitment is `OPEN` or `ORDERED`. Suspension clears the owning agreement's `trusted_commitment` to false when no other commitment of that agreement remains `ORDER_READY`, recomputes `Dealer.trusted_commitment_count`, and deactivates the default deferred shortage rule. Reinstating a `SUSPENDED` commitment whose owning agreement is not `ACTIVE` is refused with `ERR_INVALID_STATE` at HTTP 409, and suspension itself is admitted only from `ORDER_READY`, so a commitment in any other state refuses it with `ERR_INVALID_STATE`.

### 3.5. Parts Batches, Receipts and the Core Round Trip

Part batches are created by a `PartsManager` against a `commitment_id`, declaring a `product_family` that must equal the commitment's family — a mismatch is refused with `ERR_INVALID_REQUEST` at HTTP 400 — and is immutable after creation, a `requested_units` quantity, a `core_units` count, a `core_return_required` flag, an optional `emergency` flag defaulting to false, and a `requested_at` instant. A batch starts in `OPEN`. Its `requested_units` is immutable after creation, including during the `CORE_PENDING` round trip. A batch's `unfilled_units` starts equal to its `reserved_units` and falls to 0 when the batch is received.

The `reserved_units` figure is where the allocation archetype is most visible, and it is computed at creation in three distinct ways. For an ordinary non-emergency batch the reservation is the smaller of `requested_units` and `available_commitment_units`. For an oversized non-emergency batch — one whose `requested_units` exceeds `available_commitment_units` — the reservation is exactly the active variant plus 2, an over-reservation made without confirming an allocation at the active variant, and the batch's `core_return_required` is forced true whether or not the caller asked for it. For an emergency batch the reservation is the smaller of the gap and five times the active variant, where the gap is the active variant minus `committed_units`, and the emergency branch's `core_return_required` is taken from the caller. The aggregate condition `requested_units > available_commitment_units` is itself a mandate-limit violation and is refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409, so the oversized case is a deliberate exception carved out of that rule rather than a way around it. The exception is the non-emergency branch alone: a batch that is both emergency and oversized is refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409 and does not get the over-reservation, so the emergency flag is never a route past the cap. A batch created against a commitment whose `status` is `CORE_PENDING` is forced to `core_return_required` true.

A batch's `unfilled_units` is the portion of `reserved_units` not yet received, and it feeds `Dealer.open_backorder_units` while the batch is `OPEN` or `CORE_PENDING`. Its `status` runs `OPEN`, `ORDERED`, `RECEIVED`, `PARTIALLY_RETURNED`, `CLOSED` or `CANCELLED`, and `CLOSED` and `CANCELLED` are terminal. Its `received_at` is a server-clock instant written when the batch is received and is what drives emergency fill-window measurement. Its `core_return_required` flag is set when either the aggregate over-request condition holds or the dealer is on core-pending restriction; once set it forces the core-pending round trip unless it was already set. A batch's `core_return_credit_cents` is left unset at creation and carries a value only once the batch has entered the partial-return or core-pending leg, where it is priced once and frozen. Placing an order re-keys the commitment's `committed_units` and `fill_rate_pct` in the same call, so an order placed from `OPEN` immediately moves the commitment's outstanding standing.

Placing an order moves `OPEN` to `ORDERED` and requires that `available_commitment_units` be at least 1, or that the batch be an emergency. A refusal here is `ERR_COMMITMENT_EMPTY` at HTTP 409. Placing the order recomputes the commitment's `committed_units` and `fill_rate_pct`, and — when the commitment is not emergency and `available_commitment_units` is 0 — caps the batch's `reserved_units` to the floor of `available_commitment_units` divided by two, without confirming the allocation. Since that floor is 0 whenever the available count has already fallen to zero, and the branch is reached when the batch is an emergency, the cap leaves the emergency reservation standing.

Receiving moves `ORDERED` to `RECEIVED` and carries the settlement logic. The receipt is identified by an `ordered_ref` supplied with the request, which names the vendor order the received material belongs to — this is the reference that lets the system recognise a repeat of a receipt it has already credited, and a batch records the reference of each receipt it has credited. The commitment's `fulfilled_units` is increased by the batch's `unfilled_units`. The commitment's `credit_balance_cents` is increased by exactly the batch's `core_units` multiplied by the credited settlement units increment — never by a repriced figure — whenever `core_units` is at least 1. Receipt then recomputes `fill_rate_pct`, `committed_units` and `Dealer.open_backorder_units`, and moves every service order of the commitment that is `FILLED` to `RESOLVED`, stamping each one's `resolved_at` and dropping it out of the ordering target list. Two replay guards apply. A receipt whose unreceipted quantity is already covered by this batch writes no second credit and leaves `committed_units` untouched, so a repeated receipt is idempotent; the guard matches on the batch's own unordered quantity being spent or on the supplied reference having already been credited, and in either case the request answers with the batch as it stands. And when the receipt uses only part of the batch, the unallocated remainder of `reserved_units` is carried forward into a new batch in status `OPEN` with `core_return_required` inherited from the batch being received, its `requested_units` and `reserved_units` both set to that remainder, and its `core_units` zeroed. There is one further interaction worth stating precisely: when the commitment is `PERFORMANCE_DEFICIENT` or `SUSPENDED` and the outstanding SLA claim whose kind is `SLA_AUDIT` is not resolved, the receipt suspends the deferred re-evaluation for that epoch, so that the older-performance re-evaluation the suspension discards must re-compute its deferral tier rather than replay the tier it held when it ran. A receipt colliding with a deferred re-evaluation armed for the same commitment in the same epoch is refused with `ERR_EXECUTION_EPOCH_CONFLICT` at HTTP 409. A receipt also settles the deferred shortage rule from the commitment's credited core count and re-checks the automatic completion condition, so a commitment that has met its arrear with every batch closed can complete on the same call.

Returning part of a received batch moves `RECEIVED` to `PARTIALLY_RETURNED` and requires `core_units` of at least 1. The move is repeatable: a later partial return on a batch already in `PARTIALLY_RETURNED` is accepted, and the batch's `core_return_credit_cents` — computed as `core_units` multiplied by 100 on the first partial return and frozen on the batch thereafter — is only ever priced once. The commitment's `credit_balance_cents` is increased by that frozen figure and never repriced. The return clears the commitment's default deferred shortage rule when `credit_balance_cents` reaches the final stocking variant multiplied by 100, and recomputes `fulfilled_units` and `Dealer.open_backorder_units`.

The core-return round trip has two directions and a compensating action. Moving `RECEIVED` to `CORE_PENDING` requires `core_return_required` to be true — a batch that does not require one is refused with `ERR_INVALID_STATE` at HTTP 409 — and requires that the commitment's `status` not be `PERFORMANCE_DEFICIENT`; that case is refused with `ERR_COMMITMENT_PERFORMANCE_DEFICIENT` at HTTP 409. The move sets the commitment's `status` to `CORE_PENDING` when its `credit_balance_cents` is 0, deactivates the default deferred shortage rule, sets `core_return_required` to true on every `OPEN` batch of the commitment, clears the owning agreement's `trusted_commitment` to false when no other commitment of that agreement remains `ORDER_READY`, and recomputes `Dealer.trusted_commitment_count` and `Dealer.open_backorder_units`. Moving back from `CORE_PENDING` to `RECEIVED` requires `core_units` of at least 1 and a `credit_balance_cents` of at least the final stocking variant multiplied by 100 — a shortfall in either is refused with `ERR_INVALID_STATE` at HTTP 409 — and the entry leg is admitted from `RECEIVED` or from an already-`PARTIALLY_RETURNED` batch, with every other from-state refused with `ERR_INVALID_STATE`; it increases `credit_balance_cents` by `core_units` multiplied by 100, reactivates the rule, sets the commitment's `status` to `ORDER_READY` when `credit_balance_cents` reaches the final variant multiplied by 100, and recomputes `Dealer.open_backorder_units`. The compensating action that cancels a core return decreases `credit_balance_cents` by exactly the core return credit amount the matching forward return added — never by a repriced figure — and restores the default deferred shortage rule to the activation it held before that forward return. The action is admitted on a batch sitting in `PARTIALLY_RETURNED` or `CORE_PENDING` and nowhere else; it deducts the batch's frozen `core_return_credit_cents` when one is held, and otherwise the `core_units` the core-pending leg priced at 100 cents each, never driving the balance below 0. When the reduced balance falls back under the final variant's threshold, the rule is deactivated again.

Closing a batch moves `RECEIVED` to `CLOSED` and requires the commitment's `credit_balance_cents` to be at least the final stocking variant multiplied by the credited settlement units increment, and the commitment's `status` to be `ORDER_READY`. A shortfall in the settlement is refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409, and a commitment not standing at `ORDER_READY` is refused with `ERR_INVALID_STATE`. Closing recomputes `committed_units` and `Dealer.open_backorder_units`, and when every batch of the commitment is `CLOSED` and `credit_balance_cents` meets that same threshold, the commitment's `status` becomes `COMPLETE`. When the batches have all closed but the balance still stands under the threshold, the completion hard cap is suspended for a certified rebuild's credit reduction: if the dealer holds a `CERTIFIED` rebuild claim in the commitment's product family, the balance is lifted onto the threshold so the settlement path stays reachable.

Cancelling an `OPEN` or `ORDERED` batch releases the batch's `reserved_units` back to `available_commitment_units` and recomputes the commitment's `committed_units`; when the batch was `OPEN`, `Dealer.open_backorder_units` is recomputed as well.

A commitment reaches `COMPLETE` automatically once `credit_balance_cents` is at least the final stocking variant multiplied by 100 and every batch of that commitment is `CLOSED`. That automatic move recalculates `Dealer.open_backorder_units` and deactivates the default deferred shortage rule. A commitment that holds no batch at all is left where it stands, so the automatic completion needs at least one closed batch to fire.

Core-credit suspension and settlement form their own pair. Moving `ORDER_READY` to `CORE_PENDING` requires `credit_balance_cents` to be exactly 0 — a non-zero balance is refused with `ERR_CREDIT_ALREADY_APPLIED` at HTTP 409 — and requires that no batch of the commitment be `OPEN` or `ORDERED`, which is refused with `ERR_COMMITMENT_BATCH_OPEN` at HTTP 409. It sets `core_return_required` to true on every `OPEN` batch of the commitment, clears the owning agreement's `trusted_commitment` to false when no other commitment of that agreement remains `ORDER_READY`, recomputes `Dealer.trusted_commitment_count`, deactivates the default deferred shortage rule, and moves every service order of this commitment that is `OPEN` or `IN_PROGRESS` to `ESCALATED`. Settling moves `CORE_PENDING` back to `ORDER_READY`; it requires a `credit_balance_cents` of at least the final stocking variant multiplied by 100 and accepts a supplied `credit_settlement_cents` which increases `credit_balance_cents`, with a commitment whose balance is short of that threshold refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409. The settlement is refused at the moment the settled figure reaches that threshold, with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409, and a successful settlement reactivates the default deferred shortage rule and recomputes `Dealer.trusted_commitment_count`. Every service order moved to `ESCALATED` by a suspension is re-keyed by the dealer's `deferral_tier` recompute in the same call.

### 3.6. Performance Reviews and Market Share

A `DealerPerformanceReviewer` opens a `PerformanceReview` in `DRAFT` for a `dealer_id` and an `agreement_id`, declaring an inclusive `period_start`, an exclusive `period_end` that must be strictly after the start — a `period_end` not strictly after it is refused with `ERR_INVALID_REQUEST` at HTTP 400 — the dealer's own `actual_territory_machine_units`, the `territory_market_machine_units` placed by all sellers in the territory during the period, a `sampled_service_orders` count, a `met_sla_service_orders` count that must not exceed the sampled count (likewise `ERR_INVALID_REQUEST` at HTTP 400), and an optional `circumstance_note` explaining a missed plan. The review carries `status` values `DRAFT`, `RESULTS_RECORDED`, `REMEDIATION_REQUIRED`, `CIRCUMSTANCE_PENDING` and `EVALUATED`. Opening the review computes its `actual_market_share_pct` and `performance_ratio_pct` at once rather than withholding them until results are recorded, and it increments the owning agreement's version. The review itself carries only `id` and `created_at`; the measures it holds are left unset until they are computed.

Recording results moves `DRAFT` to `RESULTS_RECORDED` and recomputes `actual_market_share_pct` and `performance_ratio_pct`. `actual_market_share_pct` is 100 multiplied by `actual_territory_machine_units` and divided by `territory_market_machine_units`, stored exactly as reported to four decimal places half-up. `performance_ratio_pct` is 100 multiplied by `actual_market_share_pct` and divided by the linked agreement's `performance_plan_share_pct`, likewise to four decimal places half-up. The ratio saturates: once the reported share reaches 100, the ratio is capped at 100.0, so a plan of 20 percent with a reported share of 120 yields a ratio of 100.0 rather than 600.0. Below a reported share of 100 the saturation never binds and the two readings agree.

From `RESULTS_RECORDED` a review may take one of two recorded outcomes. A `DealerPerformanceReviewer` can move it to `REMEDIATION_REQUIRED` with a remedy plan, which carries no computed consequence. A `DealerPerformanceReviewer` can also move it to `CIRCUMSTANCE_PENDING`, putting the agreement's validity to the dealer; the dealer principal may also request circumstances on its own review, and that move increments `DealerAgreement.version` by 1. Both are admitted only from `RESULTS_RECORDED`, refused with `ERR_INVALID_STATE` at HTTP 409 otherwise, and a dealer principal requesting circumstances on another dealer's review is refused with `ERR_UNAUTHORIZED` at HTTP 403.

Evaluation moves `RESULTS_RECORDED` or `CIRCUMSTANCE_PENDING` to `EVALUATED`, and it is the point at which the quality and loyalty measures are computed. Any other from-state, including a review still in `DRAFT`, is refused with `ERR_INVALID_STATE` at HTTP 409. The product support quality index of a review is 100 multiplied by `met_sla_service_orders` and divided by `sampled_service_orders`, and reads 0.0 when the sampled count is 0. On evaluation, `quality_deficiency_pp` is the mean of the quality index values across the whole dealer's reviews that are `EVALUATED` at that instant — including this review — minus this review's own quality index, to four decimal places half-up. `quality_deficient` is true when the spread of those quality index values, taken as the highest minus the lowest, is at least 10.00 percentage points. `discrepancy_pp` is the absolute difference between `actual_market_share_pct` and `market_share_from_observations_pct`, to four decimal places half-up, where the observed share is the one implied by this dealer's market-share observations whose `recorded_at` falls inside the review period — the half-open interval from `period_start` up to but not including `period_end`. `loyalty_score` is `performance_ratio_pct` plus the lifetime-value bonus plus a customer-satisfaction bonus of 3.0 when `performance_ratio_pct` is at least 100.0 and 0.0 otherwise, recorded to two decimal places half-up. The lifetime-value bonus is `machine_lifetime_value` expressed in dollars. Evaluation also recomputes `Dealer.market_share_pct` and increments `DealerAgreement.version` by 1.

Rider observations are recorded by a `DealerPerformanceReviewer` as `MarketShareObservation` rows carrying a `dealer_id`, a `product_family`, `observed_machine_units` recorded for this dealer and family in the observation window, `territory_machine_units` recorded for the territory in the same window, a `recorded_at` instant inside the window, and a `kind` that defaults to `MACHINE` and may be `LIGHT`. The `kind` is a weight and not a label: an observation of kind `MACHINE` weighs 1.0 and one of kind `LIGHT` weighs 0.5 when the share is aggregated. `observed_share_pct` is 100 multiplied by `observed_machine_units` and divided by `territory_machine_units`, recomputed from the summed observation values of the dealer and family, to four decimal places half-up, and reading 0.0 when the summed territory units are 0. Because the reading is an aggregate of the dealer-and-family rows, recording a later observation re-keys the ratio served on every earlier row of that dealer and family as well.

The share that feeds the review is formed the same way. The numerator is the sum over the dealer's observations whose `recorded_at` falls inside the review period of `observed_machine_units` multiplied by its kind weight; the denominator is the sum over the same rows of `territory_machine_units` multiplied by its kind weight; and the share is 100 times the numerator divided by the denominator, or 0.0 when the denominator is 0, to four decimal places half-up. For a fixture consisting of a single pair of observations the representable percentages step by 100 divided by the quantity two times the unit count plus one as the unit count runs over the integers, giving 50.0, 40.0, 33.3333, 28.5714, 25.0, 22.2222, 20.0, 18.1818, 16.6667 and 15.3846 in sequence.

The dealer's lifetime value is a projection built from core credits. When the dealer's commitment whose product family matches the serial's population record is in status `ORDER_READY`, both the core value and the core fee are zero. Otherwise the core value is the `core_purchase_value_cents` of the dealer's rebuild claim for that machine serial with the greatest `created_at`, ties broken by the larger `core_purchase_value_cents`, and is zero when no such claim exists; a claim that carries no core purchase value is skipped rather than treated as zero. The core fee is the core value multiplied by the certified handling margin, rounded half-up to two decimal places. The parts value component of the bonus is zero. The bonus is the sum of the core value, the core fee and the parts value component, divided by 100 and rounded half-up to two decimal places, so the bonus is expressed in dollars. The projection runs over each distinct serial of the dealer's `ACTIVE` population records, taking each serial once, and the per-serial reading is taken from the dealer's first commitment in the record's product family when several stand.

An agreement's performance standing is set from these reviews. A `DealerPerformanceReviewer` moves `ACTIVE` to `PERFORMANCE_DEFICIENT` only once every review of the agreement is `EVALUATED` — none in `DRAFT`, none in `RESULTS_RECORDED`, none in `REMEDIATION_REQUIRED` and none in `CIRCUMSTANCE_PENDING` — and an outstanding review is refused with `ERR_REVIEW_OUTSTANDING` at HTTP 409. That move sets the agreement's commitments to `PERFORMANCE_DEFICIENT` for every commitment not already in a terminal condition — a commitment already `COMPLETE` is left where it stands — stamps `backorder_opened_at` with the server timestamp on each affected commitment, raises each affected commitment's required stocking level to the next rung of the fine availability ladder the stocking levels themselves step along — the ladder running through 10, 25, 50, 100, 250 and 500 units, the first rung above the level being taken, with a level already at or above the last rung simply rising by one unit so the raise is never a no-op — recalculates `Dealer.open_backorder_units`, and deactivates the default deferred shortage rule on each affected commitment. The same agreement returns to `ACTIVE` by reinstatement once every review of the agreement is `EVALUATED` with a `performance_ratio_pct` of at least 80.0; a review below that floor, like an outstanding one, is refused with `ERR_REVIEW_OUTSTANDING` at HTTP 409. Reinstatement reactivates the default deferred shortage rule for each commitment of the agreement and increments the agreement's version by 1. Suspending an `ACTIVE` agreement is refused with `ERR_REVIEW_AWAITING_CIRCUMSTANCE` at HTTP 409 while any review of the agreement is `CIRCUMSTANCE_PENDING`; otherwise suspension increments the agreement's version by 1, drives `Dealer.status` to `SUSPENDED` when no other agreement of the dealer is `ACTIVE`, and deactivates the rule on each commitment of the agreement. Reinstating a `SUSPENDED` agreement requires a `tooling_compliance_status` of `COMPLIANT` — a shortfall refused with `ERR_TOOLING_INCOMPLETE` at HTTP 409 — and requires that the owning dealer not be `TERMINATED`, which is refused with `ERR_DEALER_TERMINATED`; it reactivates the rule for each commitment and increments the version by 1. Marking underperforming is admitted only from `ACTIVE`, suspending only from `ACTIVE` and reinstating only from `PERFORMANCE_DEFICIENT` or `SUSPENDED`; any other from-state is refused with `ERR_INVALID_STATE` at HTTP 409, and every one of these four operations refuses a dealer or agreement already `TERMINATED` with `ERR_DEALER_TERMINATED`.

### 3.7. Certified Rebuilds, Core Returns and Remarketing

A `RebuildProgramSpecialist` opens a `RebuildClaim` in `REQUESTED` for a `dealer_id` and a `product_family`, naming a `machine_serial`, the core machine's `machine_operating_weight_lb`, the `client_meter_hours` currently showing on the client's machine, a `requested_at` instant, an optional `core_purchase_value_cents`, the `rebuild_labor_hours` and `rebuild_labor_rate_cents`, and a `certified_rebuild_spec_code` of `CAT_CERTIFIED_1`, `CAT_CERTIFIED_2` or `CAT_CERTIFIED_3`. The machine serial must be live in the dealer's active population before a claim can be tied to it; a serial that is not produces `ERR_MACHINE_NOT_IN_POPULATION` at HTTP 409. The client meter hours matter for a reason that only becomes visible later: they identify the machine the dealer holds, so the exchange itself has nothing to ship. The operating weight is immutable after submission for approval, and the machine serial is unique among rebuild claims that are neither `DENIED` nor `DECLINED` — a second live claim on the same serial is refused with `ERR_DUPLICATE_SERIAL` at HTTP 409. Opening a claim refreshes the dealer's agreement in that product family when one stands.

Approval moves `REQUESTED` to `APPROVED` and is gated on three conditions. The dealer's agreement for that product family must be `ACTIVE`; when it is not, the refusal is `ERR_NO_ACTIVE_AGREEMENT` at HTTP 409. The dealer must hold at least one commitment in status `PERFORMANCE_DEFICIENT`, so that the rebuild carries a repair priority; without one the refusal is `ERR_NO_RESTRICTION_PRIORITY` at HTTP 409. And the machine's operating weight must not exceed the certified rebuild maximum weight for the requested specification code; exceeding it is refused with `ERR_REBUILD_SPEC_EXCEEDED` at HTTP 422. The weight ceiling is still measured by the requested `certified_rebuild_spec_code` even though approval derives `core_purchase_value_cents` from the machine: the derivation is of the claim's core value, not of its weight against the supplied specification. The maximum weight rises with the specification code: 80000 pounds for `CAT_CERTIFIED_1`, 100000 for `CAT_CERTIFIED_2` and 120000 for `CAT_CERTIFIED_3`, each compared inclusively so a machine exactly at the ceiling is admitted. Approval derives `core_purchase_value_cents` from the machine, recomputes `rebuild_fee_cents` and recomputes `core_return_credit_cents`, and it increments the claim's version by 1. The supplied `expected_rebuildclaim_version` is examined before the three gates, so a version that no longer matches is refused with `ERR_STOCKING_MANDATE_HARD_CAP` at HTTP 409 rather than reaching the priority or specification checks.

Rejection by denial moves `REQUESTED` to `DENIED` and has no precondition at all. It creates no commitment, no core credit and no rebuild fee for the claim. Declining moves `APPROVED` to `DECLINED` and requires that no party registration for the territory be `SUPERSEDED`; when one is, the refusal is `ERR_PARTY_SUPERSEDED` at HTTP 409. A `DECLINED` claim's machine serial is left out of the machine-serial uniqueness comparison on every later registration, so declining releases the serial for reuse while denying does not. Both denial and decline are admitted only from their declared from-state, and any other from-state is refused with `ERR_INVALID_STATE` at HTTP 409.

Requesting a core return moves `APPROVED` to `CORE_PENDING` and requires a `core_purchase_value_cents` of at least 1 — a shortfall is refused with `ERR_INVALID_STATE` at HTTP 409. It deactivates the default deferred shortage rule and opens a service order of kind `RESTRICTION` against the claim's dealer with the claim's `machine_serial` set, and the operation is admitted only from `APPROVED`, any other from-state being refused with `ERR_INVALID_STATE`.

Returning the core moves `CORE_PENDING` to `CORE_RETURNED` and requires that `core_returned_at` be supplied on the claim. The settlement depends on whether the dealer holds the machine. When `client_meter_hours` is set, the dealer holds the machine and the exchange settlement writes nothing: the commitment's `credit_balance_cents` is unchanged and the credit is carried on the dealer's restriction service order instead. Otherwise the commitment's `credit_balance_cents` is increased by the claim's `core_return_credit_cents`, priced on the pair frozen at approval and never recomputed. Either way, the default deferred shortage rule is reactivated when `credit_balance_cents` reaches the final stocking variant multiplied by the credited settlement units increment, and `Dealer.open_backorder_units` is recomputed. A claim whose core has not been returned under the certified return terms cannot proceed and is refused with `ERR_REBUILD_CORE_UNRETURNED` at HTTP 409, and the move is admitted only from `CORE_PENDING`.

Delivering moves `CORE_RETURNED` to `DELIVERED` and requires that the certified technician minimum for the claim's `certified_rebuild_spec_code` — 2 for `CAT_CERTIFIED_1`, 4 for `CAT_CERTIFIED_2` and 6 for `CAT_CERTIFIED_3`, rising with the specification code — be no greater than the agreement's `certified_technician_count`; a shortfall is refused with `ERR_REBUILD_SPEC_EXCEEDED` at HTTP 422, the same code that guards the weight limit, because the two are the twin halves of the specification's warranty-safety envelope. The head-count is read from the dealer's first agreement in the claim's product family, and reads 0 when no such agreement stands. Delivery creates three things: a service order of kind `SLA_AUDIT` in status `RESOLVED`, opened against the dealer's first commitment in the claim's family when one stands and stamped resolved as it is created, a `TradeInUnit` row in status `ACCEPTED` with its `machine_serial` copied from the claim's serial carrying the dealer's current client meter hours affixed and its appraised value taken from the claim's core purchase value, and a `SupportAgreement` in status `ACTIVE` for the rebuilt serial carrying the claim's specification code, created as a `PREMIUM` plan only when no live support agreement already covers that serial, and re-keying the serial's coverage and the dealer's commitments in the family when it is created.

Certification moves `DELIVERED` to `CERTIFIED` and requires that at least one service order whose `origin_rebuild_id` equals this claim is not `CANCELLED`. Certification decreases the final stocking variant by the certified credit reduction while the completion hard cap remains suspended, and recomputes `required_stocking_units` and `Dealer.open_backorder_units`. A claim reaches `COMPLETE` automatically once `credit_balance_cents` is at least the final stocking variant multiplied by 100 and no batch of the dealer is `OPEN` or `ORDERED`; that move recalculates `Dealer.open_backorder_units` and deactivates the default deferred shortage rule for the claim's commitment. Certification and delivery are each admitted only from their declared from-state, any other from-state being refused with `ERR_INVALID_STATE` at HTTP 409.

The credit arithmetic is shared by every core return in the system, whether it issues from a rebuild claim or from a batch's partial return. The core value is `core_purchase_value_cents` multiplied by the core credit rate of 1.4, rounded half-up to two decimal places. The core handling fee is that core value multiplied by the certified handling margin of 0.15, rounded half-up to two decimal places. `core_return_credit_cents` is the core value plus the core handling fee. The credited settlement units increment is the core return credit plus three times the core value, rounded half-up to two decimal places. A returned core is priced on this pair and never on a recomputed one. Where the pair is written onto a claim or settled against a commitment's balance it is carried in whole cents, rounded half-up from those two-place figures, and it is the whole-cent form that the one-core-settles-1610 rule keys from.

The rebuild fee is computed at approval and built from two components. The labour fee component is `rebuild_labor_hours` multiplied by a per-hour rate, rounded half-up to two decimal places, where that per-hour rate is itself the core value multiplied by 0.0025 and rounded half-up to two decimal places — so the rate is selected by the machine's weight class through the core value rather than chosen freely, and the supplied `rebuild_labor_rate_cents` is recorded on the claim without entering the fee. The rebuild handling component is the core value multiplied by the certified handling margin of 0.15, rounded half-up to two decimal places, evaluated from the same core value the core return credit uses. `rebuild_fee_cents` is the sum of the two components, rounded half-up to the whole cent. Approval takes `core_purchase_value_cents` as 0 when the claim carries none, so a claim opened without a core purchase value still prices a fee and a core return credit from a zero core value.

There is a further settlement offset that applies when a core return is taken against a dealer working balance. The offset is the mandate settlement arrear of 103040 cents minus 150 multiplied by the mean operating hours, where the mean operating hours are measured over the dealer's `ACTIVE` machine population records only, and read as 0 when the dealer holds none. It is recorded to two decimal places half-up.

Finally, the deferred shortage rule that all of these flows arm and disarm has its own arithmetic. The rule does nothing at all when no deferred re-evaluation is armed, and a commitment whose arrear is already met is not converted. Otherwise the shortage is the mandate settlement arrear of 103040 cents minus 1610 multiplied by the credited core units, where the credited core units are the count of cores already returned against this commitment — the cores carried by the commitment's batches sitting in `PARTIALLY_RETURNED` or `CORE_PENDING`. A returned core therefore settles 1610 cents of the arrear, and the deferred re-evaluation fires when the credited core count reaches 64, since 63 cores settle only 101430 of the 103040 arrear and fall 1610 cents short. A rule that is not armed when the receipt runs leaves no re-evaluation behind, armed or otherwise.

### 3.8. Equipment Sales, Financing and Trade-In Remarketing

A `DealerSalesManager` opens an `EquipmentOrder` in `DRAFT` for a `dealer_id` and a `product_family`, naming the `machine_serial` being delivered, the `list_price_cents`, an optional `trade_in_serial` and a `requested_at` instant. The list price is frozen at order submission, and `supportable_machine_registered` is initialised to false. An order's `status` runs `DRAFT`, `SUBMITTED`, `FINANCE_APPROVED`, then `DELIVERED` or `CANCELLED`, with `DELIVERED` and `CANCELLED` both terminal. The acting dealer sales manager must be backed by the order's own dealer, so opening an order for another dealership is refused with `ERR_UNAUTHORIZED` at HTTP 403 at the actor-scope rung.

Submission moves `DRAFT` to `SUBMITTED` and requires that the machine serial not be held by another equipment order outside `CANCELLED` and not be held by an active machine population record; either collision is refused with `ERR_DUPLICATE_SERIAL` at HTTP 409. When a `trade_in_serial` is set, a `TradeInUnit` is created in status `APPRAISED` carrying the order's trade-in serial, its operating weight and appraised value taken from the optional `trade_in_weight_lb` and `trade_in_appraised_value_cents` supplied on the submission and read as 0 when omitted, and `supportable_machine_registered` is recomputed. The order's remarketed price is likewise declared at submission through the optional `remarketed_price_cents` and left unset when it is omitted.

Financing approval moves `SUBMITTED` to `FINANCE_APPROVED` and requires a `financing_approval_reference` to be present. It also requires that the summed `appraised_value_cents` of the `ACCEPTED` trade-ins attached to this order be strictly less than the list price and not equal to it: an appraisal that reaches the list price is refused with `ERR_TRADE_IN_APPRAISAL_EXCEEDS_PRICE` at HTTP 409. Approval increases the dealer's restriction-order credit by the trade-in value while the financing approval clears the trade-in's appraised value in kind, and it recomputes `supportable_machine_registered`. The two movements are one pair: the same appraised total that was added to the dealer's restriction-order credit is then written down to 0 across the attached trade-ins, and the credit it was exchanged for is the figure a later cancellation reverses. Every attached trade-in still in `APPRAISED` is moved to `ACCEPTED` in the same call, and the credit applied is the accepted total that stood before the write-down.

Delivery moves `FINANCE_APPROVED` to `DELIVERED` and is gated on two conditions. The dealer must hold an `ACTIVE` agreement whose product family equals the order's product family, and a dealer without one is refused with `ERR_NO_ACTIVE_AGREEMENT` at HTTP 409. The machine serial must be carried by no `RETIRED` population record, which is refused with `ERR_MACHINE_POPULATION_RETIRED` at HTTP 409, and by no `ACTIVE` population record outside this dealer's own rows, which is refused with `ERR_MACHINE_ALREADY_REGISTERED` at HTTP 409. Delivery registers a machine population record in status `ACTIVE` for the serial when no record carries it at all, carrying the serial's operating weight. When the order carried a product support bundle — declared by the optional `bundle_support_plan` input — a support agreement is created in status `ACTIVE` for the serial carrying the `PREMIUM` plan tier, but only when no live support agreement already covers that serial, and its creation re-keys the serial's coverage and the dealer's commitments in the family. The attached trade-in becomes `REMARKETED` when its remarketed price is at least 70 percent of its `appraised_value_cents`, and `SCRAPPED` otherwise; a trade-in whose appraised value has been cleared to 0 and that carries no remarketed price is `SCRAPPED` rather than `REMARKETED`, since a zero appraisal is nothing for a price to reach. And when the dealer's latest restriction service order has a restriction scope of `FULL_STOP`, the delivery is charged against that restriction's deferral tier by consuming one pending deferral slot rather than opening a new re-evaluation, and a dealer already holding no pending slot simply consumes nothing.

Cancellation is available on two states with different consequences. A `SUBMITTED` order can be cancelled with no precondition, and the attached trade-in rows are released from the remarketing track — the release returns them to `APPRAISED`, dropping any appraisal the financing had accepted. A `FINANCE_APPROVED` order can be cancelled only when the dealer's restriction-order credit is at least the applied financing value, and cancellation reverses the financing credit applied to that restriction order; a dealer whose credit has since fallen below the applied value is refused with `ERR_INVALID_STATE` at HTTP 409. An order can also be cancelled before those states are reached only through its own permitted transitions; every other from-state, `DRAFT`, `DELIVERED` and `CANCELLED` included, is refused with `ERR_INVALID_STATE` at HTTP 409. The reversal subtracts exactly the credit the approval applied, so a cancel after a partial draw-down may leave the working balance at 0 rather than negative.

Remarketing rows are `TradeInUnit` records. A trade-in is attached to its order through `order_id`, which is left unset for a row that a rebuild delivery creates. Its `machine_serial` is copied from the equipment order's trade-in serial and carries the dealer's current `client_meter_hours` affixed, and it is a system-written value rather than a client input. Its `machine_operating_weight_lb` and `appraised_value_cents` are declared at appraisal. Its `status` runs `APPRAISED`, `ACCEPTED`, `REMARKETED` or `SCRAPPED`. An operation that needs a trade-in in a particular state and finds it elsewhere is refused with `ERR_TRADE_IN_NOT_ACCEPTED` at HTTP 409. A taken-in serial is matched against a machine serial both exactly and by prefix, so a serial carrying the meter-hours suffix affixed still answers a lookup by its own machine serial.

### 3.9. Product Support Agreements and Machine Population

A `PartsManager` enrolls a machine on a product support plan by creating a `SupportAgreement` for a `dealer_id`, a `machine_serial`, a `plan_tier` of `BASIC`, `PLUS` or `PREMIUM`, and an `enrolled_at` instant. The machine serial must be unique among support agreements that are not `TERMINATED`, and a second live enrollment for the same serial is refused with `ERR_DUPLICATE_SERIAL` at HTTP 409. `BASIC` keeps the standard warranty terms without adding a product support obligation; `PLUS` and `PREMIUM` add a maintenance obligation. The agreement's `coverage_multiplier` is 1.0 for `BASIC`, 1.25 for `PLUS` and 1.5 for `PREMIUM`, and that multiplier is applied to the forecast coverage whenever material is reserved. Its `status` runs `ACTIVE`, `SUSPENDED` or `TERMINATED`. Creating a support agreement recomputes the serial's `coverage_multiplier` on the machine population record and recomputes `required_stocking_units` on the dealer's commitments — enrollments are not limited to the serial's own product family, so the recomputation runs over every commitment of the dealer rather than a single family.

Suspending an active support agreement is refused with `ERR_SLA_AUDIT_PENDING` at HTTP 409 while any service order of kind `SLA_AUDIT` referencing the agreement's machine serial is `OPEN` or `IN_PROGRESS`. Otherwise the suspension stops the coverage multiplier from being applied to the coverage-backed inventory tier, recomputes `required_stocking_units` for the dealer's commitments in that product family, and deactivates the default deferred shortage rule for those commitments. Reinstatement requires that the machine population record for that serial be `ACTIVE`; it re-applies the coverage-backed inventory tier, recomputes the same stocking figures and reactivates the rule for those commitments. A serial with no population record at all cannot be reinstated and is refused with `ERR_POPULATION_NOT_FOUND` at HTTP 404. Termination requires that no service order referencing the agreement's machine serial be `OPEN` or `IN_PROGRESS`; it recomputes the population record's `coverage_multiplier` for that serial to 1.0, recomputes `required_stocking_units` for the dealer's commitments in that product family, and — for a suspended agreement that is terminated — recomputes the same `coverage_multiplier` to 1.0 without the stocking recomputation.

The machine population is the network's memory of what is actually running in the field. A `PartsManager` registers a `MachinePopulationRecord` for a `dealer_id` and `product_family` with a `machine_serial`, an `machine_operating_weight_lb` that selects the weight-class tier multiplier, and a `meter_hours` reading. The serial must be unique among records that are not `RETIRED`, and a second live registration for the same serial is refused with `ERR_DUPLICATE_SERIAL` at HTTP 409. Registration recomputes `projected_annual_parts_units` and recomputes `machine_population_tier` on the dealer's commitments — over every commitment of the dealer, since the recomputation is not narrowed to the record's family. A record's `status` is `ACTIVE` or `RETIRED`, and `RETIRED` records are excluded from every forecast and from the tier-weighted machine population. A record also carries `weight_class_tier` and a serial-bound `coverage_multiplier`.

Reading a meter has a deliberate direction: a new reading replaces the record's `meter_hours`, but a lower reading is retained in preference to a higher one, so a reading above the standing figure is accepted and leaves the record's asked-for count where it was, and the coverage-credit bands are re-keyed accordingly. Reading the meter recomputes `projected_annual_parts_units` and recomputes `required_stocking_units` on the dealer's commitments — over every commitment of the dealer rather than a single family.

Retiring a record moves `ACTIVE` to `RETIRED` and requires that the dealer carry a `TradeInUnit` with this machine serial in status `ACCEPTED`; without one the request is refused with `ERR_TRADE_IN_NOT_ACCEPTED` at HTTP 409. The trade-in is matched by the serial itself or by a serial carrying the meter-hours suffix affixed, so a taken-in row created by a rebuild delivery answers for its own machine serial. Retirement drops the record from the forecast demand, recomputes `machine_population_tier` for the dealer's commitments in that product family, and deactivates the default deferred shortage rule for those commitments. Reinstating moves `RETIRED` back to `ACTIVE` and requires that the serial not be carried by a trade-in in status `REMARKETED`; a remarketed machine cannot be brought back and is refused with `ERR_MACHINE_REMARKETED` at HTTP 409. A reinstatement that would collide with another live record for the serial is refused with `ERR_DUPLICATE_SERIAL` at HTTP 409. Reinstatement re-includes the record in forecast demand, recomputes `machine_population_tier` for those commitments, and reactivates the rule for them.

The rider sweep metrics serve a different purpose: they summarise a dealer's population as a sweep rather than as a demand forecast. The dealer's `machine_serial` values that are `ACTIVE` are ordered by `created_at` ascending, with ties broken alphabetically by `machine_serial` and never by `id`; `RETIRED` rows are excluded before ordering. If the first serial in that order has an underlying commitment in status `CORE_PENDING` or `PERFORMANCE_DEFICIENT` — where the underlying commitment is the dealer's commitment in that record's product family — the response's `text_sweep_est_monthly_parts_value_cents` is the sum over the whole ordered set of the serial's one-based position in that ordering multiplied by 100, and `text_sweep_vendor_code_matches` is left unset. Otherwise `text_sweep_vendor_code_matches` is the count of serials whose underlying commitment is in status `ORDER_READY`, and the estimated monthly value is left unset. Both figures are integer cents or integer counts with no rounding. A dealer with no `ACTIVE` population at all reads a count of 0 and no estimated value.

### 3.10. The Service Bench: Emergency Fills, Restrictions and SLA Audits

A `ServiceTechnicianSupervisor` opens a `ServiceOrder` against a `commitment_id`, naming a `dealer_id`, a `kind` of `EMERGENCY_FILL`, `RESTRICTION` or `SLA_AUDIT`, a `product_family`, an optional `machine_serial`, an optional `orderable_ref_enabled` flag defaulting to false, an optional `restriction_scope` defaulting to `HOURS_SPENT`, a logged `sla_hours`, and an optional `origin_rebuild_id`. The order starts in `OPEN`, and its `opened_at` is a server-clock instant, as is its `resolved_at` when it reaches resolution. Its `status` runs `OPEN`, `IN_PROGRESS`, `FILLED`, `ESCALATED` and `RESOLVED`, with `RESOLVED` terminal. Opening an order recomputes its `risk_score`, `priority_rank` and the dealer's `deferral_tier`, and it initialises `emergency_filled_units` from the filled-quantity rule set out below. The order's `response_window_hours` is seeded from the linked commitment's current `emergency_fill_window_hours` as it is opened, and no field of the body beyond the declared inputs is consulted.

Beginning work moves `OPEN` to `IN_PROGRESS` and fixes `response_window_hours` from the linked commitment's `emergency_fill_window_hours`. Reopening moves `IN_PROGRESS` back to `OPEN` and requires that no batch of the linked commitment be `ORDERED`; the response window is re-derived from the commitment's current emergency fill window. A batch in any other state does not block the reopening, and the requirement names `ORDERED` alone.

Filling moves an order to `FILLED` and requires `orderable_ref_enabled` to be true; the same requirement holds whether the order is coming from `IN_PROGRESS` or from `ESCALATED`. Filling deactivates the default deferred shortage rule and recomputes the commitment's `fill_rate_pct`. An order whose backing reference is not orderable cannot be filled this way and is refused with `ERR_INVALID_STATE` at HTTP 409.

Escalation moves `IN_PROGRESS` to `ESCALATED` and requires `orderable_ref_enabled` to be false, so the two branches of `IN_PROGRESS` are exact complements: an order with an orderable reference fills, and an order without one escalates. Escalating sets the commitment's `status` to `PERFORMANCE_DEFICIENT`, stamps `backorder_opened_at` with the server timestamp, recalculates `Dealer.open_backorder_units` and deactivates the default deferred shortage rule. Escalation is admitted only from `IN_PROGRESS`, and an order already `ESCALATED` or at `FILLED` or `RESOLVED` is refused with `ERR_INVALID_STATE` at HTTP 409.

Recording an emergency fill moves either `IN_PROGRESS` or `ESCALATED` to `FILLED`, requires `orderable_ref_enabled` to be true, and is idempotent in the sense that a repeat of the same recorded fill leaves the order `FILLED` and otherwise unchanged — a repeat on an already-`FILLED` order takes no second consequence of the fill, neither deactivating the rule nor re-keying the commitment's rate. Each recording deactivates the default deferred shortage rule and recomputes the commitment's `fill_rate_pct`. An order in `OPEN` or already `RESOLVED` has nothing to fill and is refused with `ERR_INVALID_STATE` at HTTP 409. Recording always re-keys the order's `emergency_filled_units` on the same call, even on the idempotent repeat.

The `emergency_filled_units` figure on an emergency order is computed from the gross filled units, and the two modes are not interchangeable. The gross filled units are the sum of `sla_hours` across the dealer's `OPEN` `RESTRICTION` service orders whose `machine_serial` sits on one of the dealer's `ACTIVE` machine population record rows; orders whose machine serial has no active population record contribute nothing. The denominator is 2 when the gross is 8.0 or less and 4 otherwise. When `orderable_ref_enabled` is false the filled quantity is the gross divided by the denominator, rounded up to the next whole unit; when `orderable_ref_enabled` is true the filled quantity is the gross divided by the denominator, rounded down to the whole unit. So the non-orderable mode breaks a tie upward and the orderable mode breaks it downward, and the resulting `emergency_filled_units` is a whole number of units. The figure is computed from the dealer's standing restriction orders rather than from the order's own history, so it is re-keyed on any recompute of any of that dealer's orders.

Resolution has several entry points. An order in `OPEN` or in `FILLED` can be resolved explicitly by a supervisor, stamping `resolved_at` with the server timestamp; a second resolve of the same order is a no-op, keeping the first stamp and reporting success. An order in any other state, `IN_PROGRESS` and `ESCALATED` included, is refused with `ERR_INVALID_STATE` at HTTP 409. An order in `FILLED` also resolves automatically the moment a batch of its linked commitment reaches `RECEIVED`; that automatic move stamps `resolved_at`, drops the order out of the ordering target list, and — when the order had already been resolved by an earlier receipt of the same batch — applies no second consequence of the batch receipt at all. Resolution re-keys the dealer's `deferral_tier` across its orders, since dropping an order out of the target list can change the dealer's candidate standing.

Restriction scope is adjusted in two directions. Raising moves `OPEN` to `OPEN` or `IN_PROGRESS` to `IN_PROGRESS`, leaving the order's status where it was, and is refused with `ERR_RESTRICTION_ALREADY_FULL_STOP` at HTTP 409 when the scope is already `FULL_STOP`; both adjustments are admitted only from `OPEN` or `IN_PROGRESS`, any other state being refused with `ERR_INVALID_STATE` at HTTP 409. A successful raise lifts the restriction scope by one severity step and recomputes `priority_rank`, `risk_score` and the `deferral_tier` of the dealer's `OPEN` restriction orders. Lowering is the compensating action: it is refused with `ERR_RESTRICTION_ALREADY_MINIMAL` at HTTP 409 when the scope is already `HOURS_SPENT`, and otherwise it lowers the restriction scope by exactly one severity step — never by a repriced figure — decreases `risk_score` by exactly the same delta the matching raise added, and recomputes `deferral_tier` for the dealer's `OPEN` restriction orders.
