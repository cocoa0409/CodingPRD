# Fresh-Cut Produce Processing API — Product Requirements Document

## 1. Introduction

A fresh-cut vegetable processor lives or dies by two numbers that pull against each other: how fast raw product moves from the field to a sealed case, and how completely the plant can prove what happened to that product if a laboratory result comes back positive three days later. Today those two numbers live in different places — the receiving log is on a clipboard at the dock, wash-water chlorine readings are in a sanitation binder, dwell times and spin speeds are chalked on the line, and the traceability link between a grower's ranch block and a pallet of retail bags is reconstructed by hand under time pressure during a recall. This document specifies the API for a single system of record that closes that gap: every load received, every gallon of flume water, every clean, every swab, every case, and every code date is one addressable resource, and the relationships between them are strong enough that a recall traversal is a query rather than an investigation.

The system governs the full plant workflow. Raw product arrives against an identified grower lot whose preharvest testing evidence is scored before the lot may be consumed at all. Loads are weighed, their pulp temperature is verified, and they are accepted or rejected with a declared trim loss. Accepted pounds are drawn onto processing runs, which occupy a trimming and cutting line and draw on a shared wash flume whose antimicrobial concentration and organic load are monitored continuously and whose water is dumped on a schedule the system computes rather than guesses. Runs are closed with their measured dwell time, spin speed, packaging atmosphere and case count, at which point the system determines shelf life, prints a code date in the format the customer's specification demands, and allocates the run's cost across the cases it packed to the exact cent. Product that must clear hold-and-release micro testing is held, tested under a bounded retest loop, and either released with a recomputed final code date or rejected and destroyed.

Two families of controls run across all of it. Food-safety controls are gates, not advisories: a line whose most recent clean has not been validated cannot start a run, an unverified corrective action keeps a line shut even after a later clean passes, a confirmed environmental positive freezes the line and reaches backwards to hold product that has already been packed, and a recalled grower lot propagates through receipts, runs, holds, cases and rework descendants in one deterministic sweep. Segregation-of-duties controls are equally hard: the technician who performed a clean may not validate it, the technician who recorded a micro result may not release the hold, and the technician who implemented a corrective action may not verify it. Because all of this is scored and audited, the specification below fixes evaluation order, rounding, boundary inclusivity and cascade extent explicitly wherever a plausible alternative reading exists.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold for every endpoint in the API, together with the plant-wide principles that individual workflows in §3 assume without restating.

### 2.1. Operator Identity and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting operator and `X-User-Role` declares the capacity in which they are acting. If either header is absent, or is present but sent as an empty string, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); an empty string is treated as an absent header, not as a valid identifier. The emptiness test is against the exact empty string and nothing else, so a header whose value is only whitespace is a genuine non-empty identifier and passes authentication rather than being refused. When both headers are present, `X-User-Role` must name one of the seven roles the plant recognises and that role must be listed for the operation being attempted; otherwise the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The seven roles are `PlantAdmin`, `ReceivingClerk`, `QATechnician`, `QAManager`, `LineOperator`, `SanitationTech`, and `ShippingClerk`. `PlantAdmin` maintains master data — products, customer specifications, lines and wash systems — and drives the plant's logical clock, but holds no quality or production authority. `ReceivingClerk` records incoming loads at the dock and cannot decide the disposition of what they receive. `QATechnician` identifies grower lots, dispositions loads within specification, validates cleans, runs the environmental monitoring programme, opens quality holds and records micro results, and implements corrective actions. `QAManager` is the approval and release authority: lot adjudication, recalls, the out-of-specification receiving override, hold release and rejection, and corrective-action verification. `LineOperator` plans runs, records wash-water readings and lot consumption, starts and closes runs. `SanitationTech` cleans and reassembles the lines and changes the wash water. `ShippingClerk` releases finished cases to customers.

Identity in this system is deliberately shallow. For all seven roles — `PlantAdmin`, `ReceivingClerk`, `QATechnician`, `QAManager`, `LineOperator`, `SanitationTech` and `ShippingClerk` — `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against any resource's `id`. The server records it where an audit trail or a segregation-of-duties comparison requires it: as `dispositioned_by_user_id` on a receipt disposition, `taken_by_user_id` on a wash-water reading, `recorded_by_user_id` on a lot consumption, `performed_by_user_id` and `validated_by_user_id` on a sanitation event, `resulted_by_user_id` and `released_by_user_id` on a hold record, `implemented_by_user_id` and `verified_by_user_id` on a corrective action, and `resulted_by_user_id` on an environmental swab. Because identity is opaque, one human being may legitimately hold two roles; the segregation-of-duties rules in §2.9 therefore compare recorded operator identifiers rather than roles.

One authorisation rule is narrower than the role list itself. The `override_justification` field on a receipt disposition may only be supplied by an operator whose `X-User-Role` is `QAManager`. Any other role that sends a non-null `override_justification` is refused with `ERR_OVERRIDE_NOT_PERMITTED` (HTTP 403), and this refusal happens before the rest of the payload is examined — so a `QATechnician` who sends both an override justification and a malformed body sees the override refusal, not a request-shape error. Exactly one thing precedes it, and it is parsing rather than validation: the body must still parse as a JSON object before the field can be read at all, so a caller whose body is syntactically invalid JSON, or is valid JSON that is not an object, sees `ERR_INVALID_REQUEST` even when the intent was to override. Sending `override_justification` as an explicit `null` does not count as supplying it and never triggers the refusal for any role.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty randomly chosen alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints and are omitted entirely from single-object responses, whose `meta` carries only `api_request_id` and `api_request_timestamp`. `has_more` is true exactly when `offset` plus the number of rows actually returned on this page is strictly less than `total_count`, so an `offset` at or past the end of the collection yields an empty `data` array with `has_more` false.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a collection is paginated through two query parameters. `limit` is the maximum number of rows to return; when it is omitted it defaults to 10, and a supplied value must be at least 1 and at most 100. `offset` is the number of rows to skip and defaults to 0. A `limit` or `offset` that is not an integer, a `limit` outside 1 through 100, or a negative `offset` is rejected with `ERR_INVALID_REQUEST` (HTTP 400); either parameter sent as an empty string is treated as absent and takes its default. Unless a specific collection declares otherwise, list results are ordered by `created_at` ascending, with the server's own creation sequence — the order in which the rows were written, regardless of collection — as the implicit tie-break whenever two rows share a `created_at`. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the number of rows matching the filters before pagination is applied.

Collections also accept domain filters, which combine with each other and with pagination. Products may be filtered by `commodity_class` and `allergen_group`; customer specification revisions by `channel` and `status`; lines by `posture`; grower lots by `status` and `grower_code`; the loads received against a grower lot by `status` and `temp_grade`; wash-water readings by `below_target`; sanitation events by `status` and `shift`; environmental swabs by `result`, `zone` and `organism`; corrective actions by `status`, `severity` and `source_type`; lot consumptions, whether viewed from the run side or from the receipt side, by `status`; finished cases by `status`; hold records by `status` and `reason`; and processing runs by `line_id`, `product_id`, `customer_spec_id`, `wash_system_id`, `rework_source_run_id`, `run_status` and `disposition_status`. Three collections override the default ordering because the plant reads them newest-first: wash-water readings are returned by `reading_at` descending, sanitation events by `scheduled_for` descending, and hold records by `opened_at` descending. Finished cases are returned in `case_sequence` ascending order, which is the pack order. Enumerated filters accept only declared members, and an unrecognised value is `ERR_INVALID_REQUEST` (HTTP 400); any filter sent as an empty string is treated as absent; the boolean `below_target` accepts only the four literals `true`, `True`, `false` and `False`; and free-text filters such as `grower_code` match the stored value exactly and case-sensitively. Where a collection hangs off a parent identifier in the path, the domain filters are validated *before* that parent is resolved while the pagination parameters are validated *after* it — so an unrecognised filter value against a parent that does not exist reports `ERR_INVALID_REQUEST`, whereas a `limit` of 0 against that same missing parent reports the parent's not-found error.

### 2.4. The Plant Logical Clock

Nothing in this system reads the host machine's wall clock. All server-stamped instants and every time-window rule read a single logical clock that an administrator sets explicitly through a test-driving capability taking a `current_utc` instant. Before that capability is ever called, the logical clock reads exactly `2026-08-01T00:00:00Z`, and in practice it only ever moves forward within a given session — but that is a convention of use rather than a rule the server polices: the capability simply adopts whatever valid `current_utc` it is handed, including an instant earlier than the current reading, and never refuses one for going backwards. Setting the clock changes no stored row and creates none; it changes what every subsequent creation, mutation and window evaluation observes as "now". The call answers HTTP 200 with a `data` object carrying the single field `current_utc`, echoing the supplied text verbatim.

The fields that read the logical clock are `created_at` and `updated_at` on every resource, plus `ProcessRun.started_at` and `closed_at`, `SanitationEvent.validated_at`, `HoldRecord.opened_at` and `closed_at`, `FinishedCase.shipped_at`, `GrowerLot.recalled_at`, `WashSystem.last_changeout_at`, `CorrectiveAction.opened_at` and `verified_at`, `EnvironmentalSwab.resulted_at`, `CustomerSpec.superseded_at` and `LotConsumption.voided_at`. Client-supplied instants — `received_at`, `harvest_datetime`, `reading_at`, `scheduled_for`, `collected_at`, `planned_start_at` and `planned_end_at` — are taken as given and are never overwritten by the clock. They are also echoed back in exactly the text the client sent, never re-rendered into the server's canonical three-fraction-digit form: an instant supplied as `2026-08-02T06:00:00Z` reads back as that same string, and one supplied with six fractional digits reads back with six. Only server-stamped instants carry the canonical three-digit rendering.

One consequence deserves emphasis. Two rows created without an intervening clock advance carry an identical `created_at`, so `created_at` alone is not a reliable ordering key. Every rule in this document that could tie on `created_at` therefore pins a second, monotonic tie-break drawn from the domain: `sequence_no` on wash-water readings, `sequence_no` on sanitation events, `case_sequence` on finished cases, and `spec_revision` on customer specifications.

### 2.5. Record Identity and Audit Fields

Every resource carries an `id` that the server mints as a UUID. Identifiers carry no type prefix, no embedded meaning, and are never used in a business decision — where a rule needs an ordering or a key, it uses a domain field, never an `id`.

Most resources also carry three system-managed audit fields: `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written; `updated_at`, an ISO 8601 UTC timestamp in the same format recording the most recent mutation; and `version`, an integer that begins at 1 and increases by exactly 1 on every mutation of that row. Recomputation of a derived field counts as a mutation: when a wash-water change-out resets a system's load figures, or a receipt disposition depresses a grower lot's trailing score, the affected row's `updated_at` is refreshed and its `version` is incremented even though no client sent a field for it.

`AntimicrobialReading` is the one exception and it is deliberate. A wash-water reading is an append-only measurement: it carries only `id` and `created_at`. It has no `updated_at` and no `version`, there is no endpoint that modifies it, and the derived values frozen onto it at the moment of recording — `organic_load_index_at_reading`, `target_free_chlorine_ppm_at_reading`, `topup_ppm_required` and `below_target` — are never revised by later activity on the wash system.

### 2.6. Measurement Precision, Rounding and Money

Rounding is half-up everywhere in this specification, and it is applied at the points named below and nowhere else. In particular it is not applied on input: the precision conventions in this section govern how figures are *compared* and how *derived* figures are computed, while a client-supplied figure is stored exactly at the value it was sent, never re-quantised on the way in. A `min_antimicrobial_ppm` submitted as `20.005` or a `pulp_temp_c` submitted as `3.35` retains that extra digit rather than being truncated or rounded to the declared precision, and only the values computed from it are rounded. All numeric fields are carried as JSON numbers in both directions, never as strings, and insignificant trailing zeros are not preserved in the rendering, so a `case_net_weight_lb` sent as `2.500` reads back as `2.5`.

- Pound quantities — `gross_weight_lb`, `tare_weight_lb`, `net_weight_lb`, `trim_loss_lb`, `accepted_lb`, `remaining_lb`, `consumed_lb`, `input_lb`, `output_lb`, `weighted_load_lb` and `case_net_weight_lb` — are carried to two decimal places.
- `yield_pct` and `min_yield_pct` are carried to two decimal places, and the yield tolerance comparison is made against the rounded `yield_pct`, never against the unrounded quotient.
- `organic_load_index` is carried to exactly three decimal places, and the tier selection that depends on it reads the rounded value.
- Free chlorine figures — `free_chlorine_ppm`, `min_antimicrobial_ppm`, `target_free_chlorine_ppm`, `target_ppm_at_start`, `min_ppm_observed` and `topup_ppm_required` — are compared and stored at one decimal place. `ph` and `turbidity_ntu` likewise carry one decimal place, and `orp_mv` is a whole number of millivolts.
- `pulp_temp_c` is recorded and compared at exactly one decimal place with no further rounding, so a temperature breakpoint is a comparison between two one-decimal figures.
- Day counts — every shelf-life figure, deduction and penalty — are integers, and any flooring or clamping a rule declares is applied in the order that rule states.
- Money is never fractional. All monetary values are whole numbers of cents: `total_run_cost_cents`, `per_case_cost_cents`, `cost_remainder_cents` and `allocated_cost_cents` are integers. Each cost component is rounded half-up to whole cents before it is added to any other component, and the allocation across cases uses integer division with an integer remainder, so no fraction of a cent is ever stored, created or destroyed.

### 2.7. Stale-Version Protection on Master-Data and Run Writes

Two writes in this API can silently overwrite work the caller never observed, and both are protected by an explicit stale-version check. In each case the check compares a client-supplied expected version against the current `version` of the *parent* resource; the check is not optional, and it is applied only where this section names it.

Publishing a customer specification revision for a product requires the request to carry `expected_product_version` holding the `version` of that `Product` as the client last read it. If the product's current `version` differs — because another writer has published a revision, or because any other mutation has advanced the product row — the request is rejected with `ERR_STALE_PRODUCT_VERSION` (HTTP 412). The field is itself a required non-negative integer, so omitting it, sending it as `null`, or sending a non-integer is a request-shape failure with `ERR_INVALID_REQUEST` (HTTP 400) rather than a stale-version refusal. The protection matters because a new revision supersedes the prior `ACTIVE` specification for the same `product_id` and `channel`: a writer holding a stale view of the product would otherwise supersede a revision it had never seen.

Recording a lot consumption against a processing run, and voiding a consumption already recorded, both require the request to carry `expected_process_run_version` holding the `version` of that `ProcessRun` as the client last read it. If the run's current `version` differs, the write is rejected with `ERR_STALE_PROCESS_RUN_VERSION` (HTTP 412). The field is itself a required integer of at least 1 — a version begins at 1 and never falls — so omitting it, sending it as `null`, sending 0 or a negative number, or sending a non-integer is a request-shape failure with `ERR_INVALID_REQUEST` (HTTP 400) rather than a stale-version refusal. Each consumption shifts both the wash system's organic load and the run's mass balance, and the caller computed the pounds it is posting from its observed view of the run; a stale view means posting pounds against a balance that no longer exists.

No other endpoint takes a version field. Requests to endpoints that this section does not name are processed without any expected-version input, and supplying one has no effect.

### 2.8. Validation Order

When a single request violates several rules, the response must be deterministic. The system therefore evaluates checks in a fixed global order and returns the first failure it finds.

1. **Authentication.** Header presence and non-emptiness first (`ERR_UNAUTHENTICATED`), then whether the declared role is a recognised role that is permitted on this operation (`ERR_UNAUTHORIZED`), then the narrower override-authority rule of §2.1 (`ERR_OVERRIDE_NOT_PERMITTED`).
2. **Request shape.** The body must be a JSON object; every required input field must be present and non-null; every enumerated field must carry a declared member; every numeric field must be a number of the permitted sign and range; and every instant field must be an ISO 8601 UTC timestamp. Any violation is `ERR_INVALID_REQUEST` (HTTP 400). Unknown fields are ignored rather than rejected. Several details of this step are fixed. An absent, empty or whitespace-only request body is treated as an empty JSON object rather than as a parse failure, so what it fails on is the first missing required field; a body that parses to anything other than an object — an array, a number, a bare string — is `ERR_INVALID_REQUEST`. A field sent as `null` counts as absent: required means `ERR_INVALID_REQUEST`, optional means the field takes its declared default. String fields must contain at least one non-whitespace character, and are stored exactly as sent without being trimmed. Integer fields accept a JSON number whose fractional part is zero, such as `5.0`, but never a boolean; numeric fields likewise reject booleans; boolean fields accept only `true` and `false` and never the strings `"true"` or `"false"`. An instant is accepted with one to nine fractional-second digits and is retained to microsecond resolution; the trailing `Z` is optional and an explicit zero offset such as `+00:00` or `-0000` is accepted, while any non-zero offset is rejected. Query-string filters and, on list endpoints hanging off a parent, only the filters rather than the pagination parameters, are validated at this stage. Cross-field arithmetic constraints that this document states as field constraints — notably a load's `tare_weight_lb` being strictly less than its `gross_weight_lb` — are checked here as well, and therefore before any body foreign key is resolved.
3. **Path existence.** Identifiers embedded in the URL are resolved left to right, and always before any body field is resolved. The first identifier that names nothing produces its own not-found error: `ERR_PRODUCT_NOT_FOUND`, `ERR_GROWER_LOT_NOT_FOUND`, `ERR_RAW_RECEIPT_NOT_FOUND`, `ERR_LINE_NOT_FOUND`, `ERR_WASH_SYSTEM_NOT_FOUND`, `ERR_PROCESS_RUN_NOT_FOUND`, `ERR_LOT_CONSUMPTION_NOT_FOUND`, `ERR_FINISHED_CASE_NOT_FOUND`, `ERR_HOLD_RECORD_NOT_FOUND`, `ERR_SANITATION_EVENT_NOT_FOUND`, `ERR_ENVIRONMENTAL_SWAB_NOT_FOUND` or `ERR_CORRECTIVE_ACTION_NOT_FOUND`, each with HTTP 404.
4. **Body foreign-key existence.** Foreign keys in the body are resolved after the path and in the order the operation declares its inputs. Recording a load resolves `grower_lot_id` (`ERR_GROWER_LOT_NOT_FOUND`). Planning a run resolves, in this exact order, `line_id` (`ERR_LINE_NOT_FOUND`), `product_id` (`ERR_PRODUCT_NOT_FOUND`), `customer_spec_id` (`ERR_CUSTOMER_SPEC_NOT_FOUND`), `wash_system_id` (`ERR_WASH_SYSTEM_NOT_FOUND`) and then, only when it is present and non-null, `rework_source_run_id` (`ERR_PROCESS_RUN_NOT_FOUND`). Recording a consumption resolves `raw_receipt_id` (`ERR_RAW_RECEIPT_NOT_FOUND`).
5. **Stale-version checks.** The two checks of §2.7 are evaluated after existence and before any state precondition, so a caller holding a stale version learns that before learning anything about the resource's lifecycle state.
6. **Lifecycle state preconditions.** Whether the target resource is in a state from which the requested action is legal, yielding `ERR_GROWER_LOT_INVALID_STATE`, `ERR_RECEIPT_NOT_PENDING`, `ERR_RUN_NOT_IN_SETUP`, `ERR_RUN_NOT_RUNNING`, `ERR_CONSUMPTION_ALREADY_VOIDED`, `ERR_SANITATION_INVALID_STATE`, `ERR_SWAB_INVALID_RESULT_TRANSITION`, `ERR_CORRECTIVE_ACTION_INVALID_STATE`, `ERR_HOLD_INVALID_STATE`, `ERR_HOLD_NOT_RELEASED` or `ERR_CASE_NOT_IN_INVENTORY` as appropriate. Within shipping specifically, the run-level cause is reported before the case-level symptom: `ERR_HOLD_NOT_RELEASED` precedes `ERR_CASE_NOT_IN_INVENTORY`.
7. **Segregation of duties.** The comparisons of §2.9, all reported as `ERR_SEGREGATION_OF_DUTIES` (HTTP 409), are evaluated after state and before any food-safety gate.
8. **Food-safety gates**, then **referential agreement** between related records, then **temporal window rules**, then the remaining **business constraints**, and finally the **balance and capacity** rules. §3 states the exact sequence for each operation that carries more than one of these.

### 2.9. Segregation of Duties

Three approvals in this plant may not be self-approvals, and in each case the comparison is between the acting `X-User-ID` and an operator identifier the system stamped earlier on the same record. Validating a sanitation event is refused when the acting `X-User-ID` equals that event's `performed_by_user_id`. Releasing a hold is refused when the acting `X-User-ID` equals that hold's `resulted_by_user_id` — the technician who recorded the micro result may not be the one who releases on it. Verifying a corrective action is refused when the acting `X-User-ID` equals that action's `implemented_by_user_id`. All three refusals carry `ERR_SEGREGATION_OF_DUTIES` (HTTP 409), and all three are role-blind: holding `QAManager` does not exempt an operator who personally performed the work.

### 2.10. Line Posture: The Derived Gate on Production

A `Line` has no state-changing operation of its own. Its `posture` is a pure projection of the sanitation events, corrective actions and environmental swabs that name that line, and it is the single gate consulted before a run may start. Its three values are `OPEN`, `RESTRICTED` and `FROZEN`, and a newly registered line begins at `RESTRICTED` because it has no validated clean yet — runs may be planned on a brand-new line, but not started. The projection is not evaluated afresh on every read: `posture` is a stored field on the line row that the server recomputes at exactly four points — when a sanitation event is validated (on the passing branch and on the failing branch alike), when an environmental swab result is recorded, when a corrective action is verified with a passing outcome, and when closing a run opens an antimicrobial-excursion corrective action. Scheduling, starting or submitting a clean, logging a swab, taking ownership of a corrective action, submitting one for verification, and failing a verification all leave the stored value exactly as it was. For all but one of those operations the omission is invisible, because they cannot change the four facts below; the exception is scheduling. Scheduling a sanitation event whose `scheduled_for` is later than every existing one makes an unvalidated event the *latest* event on the line, so the projection below would now yield `RESTRICTED` — yet the stored `posture`, and therefore the gate on starting a run, stays `OPEN` until one of the four recomputation points arrives.

The projection reads four facts about the line and nothing else. First, the **latest sanitation event** is the `SanitationEvent` for this line with the greatest `scheduled_for`, and when two events share that instant, the one with the greater `sequence_no`. Note that the key is `scheduled_for` and not `created_at`, so back-filling a clean that was scheduled earlier than an existing one does not change which event counts as latest. Second, an **open critical action** exists when some `CorrectiveAction` on this line has `severity` of `CRITICAL` and a `status` other than `VERIFIED`. Third, an **open major action** exists when some `CorrectiveAction` on this line has `severity` of `MAJOR` and a `status` other than `VERIFIED`. Fourth, an **open presumptive finding** exists when some `EnvironmentalSwab` on this line has `result` equal to `PRESUMPTIVE_POSITIVE`. Only children whose `line_id` is this line are read; rows on a different line never affect this line's posture, even when the two lines share a wash system.

The four facts are then examined in a strictly ordered sequence, and the first matching branch decides the posture:

1. If an open critical action exists, the posture is `FROZEN`.
2. Otherwise, if an open major action exists or an open presumptive finding exists, the posture is `RESTRICTED`.
3. Otherwise, if the line has no sanitation event at all, the posture is `RESTRICTED`.
4. Otherwise, if the latest sanitation event's `status` is anything other than `VALIDATED`, the posture is `RESTRICTED`.
5. Otherwise, the posture is `OPEN`.

Two consequences follow from the ordering and are intended. A line carrying both an open `CRITICAL` and an open `MAJOR` action is `FROZEN`, because the critical branch is examined first. And passing a fresh clean does not clear an unverified corrective action: a line whose latest sanitation event is `VALIDATED` but which still carries an unverified `MAJOR` action remains `RESTRICTED` until that action reaches `VERIFIED`. This is the cross-entity gate behind `ERR_LINE_NOT_OPEN`.

Posture movements carry their own consequences, but two derived line fields do not wait for a movement. *Every* recomputation, whatever posture it lands on and whether or not the posture changed, also re-derives `open_corrective_action_count` as the number of corrective actions on this line whose `status` is `OPEN`, `IN_PROGRESS` or `VERIFICATION_PENDING`, and re-derives `last_validated_sanitation_at` as the `validated_at` of this line's `VALIDATED` sanitation event with the greatest `validated_at` — tie-broken by the greater `sequence_no` — or null when the line has no validated event at all. Neither field is ever incremented or decremented in place; both are counted from scratch, so wherever this document says a cascade "increments" or "decrements" one of them, what the server actually does is re-derive it and arrive at that value. So a clean that validates on a line still carrying an unverified `MAJOR` action refreshes `last_validated_sanitation_at` even though the posture stays `RESTRICTED`. The line row's `updated_at` and `version` move only when the recomputation actually changes `posture`, `open_corrective_action_count` or `last_validated_sanitation_at`; a recomputation that finds all three already correct is not a mutation at all and leaves both audit fields where they were. When a recomputation lands on `OPEN`, run starts become possible. When it lands on `RESTRICTED` from `OPEN`, further starts are blocked while runs already `RUNNING` remain closable. Whenever it lands on `FROZEN` — including when the line was already `FROZEN` before the recomputation ran, so that the posture did not change at all — the containment propagation described in §3.5 fires: `SETUP` runs on the line are cancelled and `RUNNING` runs, together with recently closed ones, are placed on hold. When a passing corrective-action verification lifts a line out of `FROZEN` to `OPEN` or to `RESTRICTED`, nothing is undone: runs cancelled during the freeze are not un-cancelled, and holds opened during the freeze are not released. Recovery from a freeze always runs forward through hold release, never backwards through the cascade.

### 2.11. Cascade Discipline and Counter Conservation

Several operations in this plant reach far beyond the row the client named. A confirmed environmental positive and a grower-lot recall each propagate through five caused hops, a failed sanitation validation through four, and a run close creates a whole population of cases. Four principles govern all of them.

**Every touched row is a mutation.** Any row a cascade changes — a quarantined receipt, a held run, a case moved to `ON_HOLD`, a grower lot whose trailing score fell — has its `updated_at` refreshed and its `version` incremented by 1, exactly as if a client had written to it directly. The converse holds for the grower-lot risk recomputation specifically, wherever it is triggered from: when the recomputation leaves both counters, the trailing score and the lot's `status` exactly as they already were, the lot is not a touched row at all and its `updated_at` and `version` stay where they were.

**Cascades run in a declared order.** Where a hop processes a set of rows, the order is pinned by a domain field so that the result is reproducible: receipts in `received_at` ascending order with `created_at` ascending as the tie-break, runs in `planned_start_at` ascending order with `created_at` ascending as the tie-break, cases in `case_sequence` ascending order, and wash systems in `created_at` ascending order. Where even those keys tie — two receipts sharing a `received_at` and a `created_at`, two runs sharing a `planned_start_at` and a `created_at`, two wash systems sharing a `created_at` — the server's own creation sequence settles the order, so the sweep is still reproducible.

**Cascades are conditional, not blanket.** A hop skips rows that are already past the state it would impose: a run whose `disposition_status` is already `REJECTED` is not re-held, and cases already `SHIPPED` or `DESTROYED` are left untouched when their siblings move to `ON_HOLD`.

**Case counters partition the run's cases and always reconcile.** A closed run's four counters — `cases_available` counting cases with `status` of `IN_INVENTORY`, `cases_on_hold` counting `ON_HOLD`, `cases_shipped` counting `SHIPPED` and `cases_destroyed` counting `DESTROYED` — are recomputed from the run's `FinishedCase` rows on every close, every hold opening, every hold release, every hold rejection and every shipment. Cases are never deleted, only re-dispositioned, so `cases_produced` is a fixed denominator once the run has closed, and after every one of those triggers the sum of the four counters equals `cases_produced` exactly. No case is ever counted twice and none is ever dropped. Because a hold moves only the `IN_INVENTORY` cases, a hold opened after part of the run has already shipped records how much product had left the plant in the hold's own `shipped_case_count`, which is the recall-effectiveness figure the quality group reports.

## 3. Business Logic & Workflows

### 3.1. Master Data: Products, Customer Specifications, Lines and Wash Systems

Before any produce moves, a `PlantAdmin` establishes the plant's configuration. A **product** is registered with a plant product code in `code` (for example `RML-SHRED`), a human-readable `name`, and the processing envelope the product must be run within. Its `commodity_class` is one of `LEAFY`, `ROOT` or `FRUIT` and expresses the soil and organic load the commodity carries into the flume. Its `allergen_group` is one of `NONE`, `CELERY`, `SESAME`, `MUSTARD` or `SULFITE` and defaults to `NONE` when the field is omitted; it is what drives changeover sanitation between dissimilar products. The processing envelope itself is four figures: `min_dwell_seconds`, the product-specific minimum flume dwell time, at least 1 second; `min_spin_rpm`, the minimum spin-dryer speed, at least 1, below which the product is under-dried and loses a day of life; `min_antimicrobial_ppm`, the free chlorine concentration in parts per million the wash water must hold for this product, greater than zero and carried to two decimal places; and `base_shelf_life_days`, the validated shelf life in days before any customer cap or quality deduction, at least 1. Two acceptance figures complete the record: `min_yield_pct`, the lowest acceptable ratio of case weight out to raw pounds in, greater than 0 and at most 100 with two decimal places, and `hold_and_release_required`, a flag defaulting to false which, when true, causes every run of that product to be placed on hold automatically the moment it closes. The server maintains `active_spec_count` on the product, starting at 0, as the number of that product's specification revisions whose `status` is `ACTIVE`. Product codes are unique across the plant; registering a second product with an existing `code` is refused with `ERR_DUPLICATE_CODE` (HTTP 409). The comparison is an exact, case-sensitive string match — `RML-SHRED` and `rml-shred` are two distinct codes — and it is made only after the request has cleared request-shape validation, so a duplicate code sent alongside a malformed field reports `ERR_INVALID_REQUEST`.

**Customer specifications** hang off the product and describe what one customer will accept. A revision names its `product_id`, the `customer_code` of the account (for example `FSVC-NORTH`) and a `channel` of either `FOODSERVICE` or `RETAIL`. It carries `max_shelf_life_days_offered`, at least 1, which caps whatever the product's own validated life would otherwise allow; `min_remaining_shelf_life_days_at_ship`, at least 0, the days of code-date life that must still remain on the day a case leaves the plant; `atmosphere_required`, one of `AIR`, `MAP_LOW_O2` or `MAP_HIGH_CO2`; `case_net_weight_lb`, the net finished weight of one case in pounds, greater than zero with two decimal places; and `code_date_format`, either `JULIAN` or `CALENDAR`, which decides how the code date is printed on the case. Specifications are versioned by revision rather than edited. The server computes `spec_revision` as 1 plus the number of specification rows that already existed for the same `product_id` and `channel`, sets the new row's `status` to `ACTIVE` with `superseded_at` left null, and moves the previously `ACTIVE` row for that same `product_id` and `channel` to `SUPERSEDED`, stamping its `superseded_at` with the logical clock. It then recomputes the product's `active_spec_count` and increments the product's `version` by 1. Because a new revision is expected to displace its predecessor, the pair of `product_id` and `channel` is deliberately *not* unique — but the write is protected by the stale-version rule of §2.7: the request must carry `expected_product_version` equal to the product's current `version`, or it is rejected with `ERR_STALE_PRODUCT_VERSION` (HTTP 412).

A **line** is a trimming, cutting and washing line. It is registered with a `line_code` such as `L1`, unique across the plant, a `required_disassembly_component_count` — an integer of zero or greater — stating how many components must come apart before a clean may be submitted, and a `max_atp_rlu`, likewise an integer of zero or greater, giving the highest post-sanitation ATP swab reading, in relative light units, that still passes validation. Both figures are required and both accept 0: a line whose requirement is 0 accepts any disassembly count, and a line whose limit is 0 fails any ATP reading above zero. A new line starts with `posture` at `RESTRICTED`, `open_corrective_action_count` at 0, and `last_validated_sanitation_at`, `last_run_allergen_group` and `last_run_ended_at` all null. A duplicate `line_code` is refused with `ERR_DUPLICATE_CODE`, on the same terms as a product code: an exact, case-sensitive string comparison made only after the request has cleared request-shape validation.

A **wash system** is a shared flume and antimicrobial recirculation loop that runs on any line may draw on. It is registered with a `system_code` such as `W1`, unique across the plant, a `water_volume_gal` working volume greater than zero which becomes the denominator of the organic load index, and a `max_concurrent_runs` of at least 1 limiting how many runs' planned windows may overlap on it. On creation the server sets `status` to `IN_SERVICE`, `last_changeout_at` to the logical clock's current instant, `weighted_load_lb` to 0, `organic_load_index` to 0.000, `target_free_chlorine_ppm` to 20.0, `changeout_count` to 0 and `reading_sequence_high_water` to 0. A duplicate `system_code` is likewise refused with `ERR_DUPLICATE_CODE`, by the same exact, case-sensitive comparison made after request-shape validation. `status` has only the two members `IN_SERVICE` and `DUMP_REQUIRED`; there is no out-of-service state and no endpoint that sets the status directly.

### 3.2. Grower Lots: Identification, Risk Adjudication and Suspension

Traceability begins in the field. A `QATechnician` identifies a **grower lot** with the `grower_code` of the account (for example `GRW-100`), the `ranch_block` identifier of the harvested field, the `commodity_class` of the raw product as `LEAFY`, `ROOT` or `FRUIT`, and the `harvest_datetime` at which the block was cut — an instant that later anchors every harvest-lag deduction on finished product. Three fields carry the preharvest evidence: `water_source`, one of `MUNICIPAL`, `WELL` or `SURFACE`; `adjacent_animal_operation`, a flag defaulting to false that is true when a concentrated animal feeding operation adjoins the block; and `preharvest_test_result`, one of `NEGATIVE`, `PRESUMPTIVE` or `POSITIVE` from the preharvest pathogen testing programme. A fourth, `prior_rejected_receipt_count`, carries the grower's historical rejected-load count in from the scorecard; it must be zero or greater and defaults to 0 when omitted. A newly identified lot has `status` of `PENDING_APPROVAL`, `out_of_spec_receipt_count` and `env_positive_run_count` at 0, `recalled_at` null, and both `preharvest_risk_score` and `trailing_risk_score` null — a lot's risk is not scored until it is adjudicated.

Adjudication is the `QAManager`'s decision and it computes a **preharvest risk score** on a hundred-point scale where a higher score is safer. The score starts at 100. Twenty-five points are deducted when `water_source` is `SURFACE`. Fifteen points are deducted when `adjacent_animal_operation` is true. Twenty points are deducted when `preharvest_test_result` is `PRESUMPTIVE`. A prior-rejection deduction is then taken: five points for each load counted in `prior_rejected_receipt_count`, but the whole term is capped at twenty points *before* it is subtracted, so a grower with four prior rejected loads and a grower with forty prior rejected loads both lose exactly twenty points. The result is finally constrained to the range 0 through 100 inclusive. Adjudication then takes one of three branches, and each branch is a transition out of `PENDING_APPROVAL`:

- When `preharvest_test_result` is `POSITIVE`, the lot moves `PENDING_APPROVAL → REJECTED` regardless of the weighted score — a confirmed preharvest pathogen positive is a hard rejection — and both `preharvest_risk_score` and `trailing_risk_score` are set to 0.
- When the test result is anything other than `POSITIVE` and the computed score is at least 50, the lot moves `PENDING_APPROVAL → APPROVED`. The server writes the computed value into `preharvest_risk_score` and copies the identical value into `trailing_risk_score`, because no operating evidence exists yet, and refreshes `out_of_spec_receipt_count` and `env_positive_run_count` to their current counts.
- When the test result is anything other than `POSITIVE` and the computed score is below 50, the lot moves `PENDING_APPROVAL → SUSPENDED` — approved into suspension. Both `preharvest_risk_score` and `trailing_risk_score` receive the computed value, `out_of_spec_receipt_count` and `env_positive_run_count` are refreshed to their current counts exactly as in the approving branch, and the lot may not be consumed. The `POSITIVE` branch is the only one that does not refresh the counters: it writes the two zero scores and leaves both counters exactly as they stood.

Adjudication increments the lot's `version` by 1. It is legal only from `PENDING_APPROVAL`; attempting it on a lot in any other state is refused with `ERR_GROWER_LOT_INVALID_STATE` (HTTP 409).

Once a lot is approved, its risk is re-derived from operating evidence rather than from field evidence, and in the ordinary course this **trailing score** only falls. The trailing computation begins from the *frozen* `preharvest_risk_score` — never from a freshly re-derived preharvest figure — and subtracts ten points for each receipt counted in `out_of_spec_receipt_count` and twelve points for each run counted in `env_positive_run_count`, constraining the result to the range 0 through 100 inclusive. `out_of_spec_receipt_count` is the number of this lot's loads whose `temp_grade` is `OUT_OF_SPEC` and whose `status` is not `REJECTED`; a rejected load never counts against the grower, however warm it arrived. `env_positive_run_count` is the number of distinct processing runs that hold an `ACTIVE` consumption against one of this lot's loads and that carry a hold record opened for an environmental positive or for a recall. Neither counter is accumulated: both are re-derived from scratch, from those two definitions, on every recomputation, and neither is ever incremented in place. Two consequences follow and are what the implementation actually exhibits. Because a load still in `PENDING_INSPECTION` already counts toward `out_of_spec_receipt_count`, subsequently rejecting that load removes it from the count and the trailing score rises again on the next recomputation; likewise voiding the consumption that tied a run to the lot removes that run from `env_positive_run_count`. What is genuinely irreversible is the suspension, not the number: a lot driven `APPROVED → SUSPENDED` by a low trailing score is never returned to `APPROVED` by a later recomputation, however far the score recovers. The trailing score is recomputed whenever operating evidence lands: on every load disposition, on the environmental containment sweep, and on the recall sweep. Whenever the recomputation runs on a lot whose `status` is `APPROVED` and the new trailing score is strictly below 50, the lot moves `APPROVED → SUSPENDED`, and from that moment no further consumption may be drawn from any of its loads. The comparison is strict: a trailing score of exactly 50 keeps the lot `APPROVED`.

Suspension and rejection are not the end of the story. A `QAManager` may also **recall** a lot that is `APPROVED` or `SUSPENDED`, which drives it to the terminal `RECALLED` state and runs the containment sweep described in §3.9. Recall on a lot that is neither `APPROVED` nor `SUSPENDED` is refused with `ERR_GROWER_LOT_INVALID_STATE`.

### 3.3. Receiving: Temperature Verification and Load Disposition

A `ReceivingClerk` records each raw load at the dock against the grower lot it came from. The load names its `grower_lot_id`, the `received_at` instant it arrived, the verified `pulp_temp_c` pulp temperature in Celsius at one decimal place, and the two scale figures: `gross_weight_lb`, greater than zero with two decimal places, and `tare_weight_lb`, zero or greater and strictly less than the gross weight. `pulp_temp_c` carries no sign or range constraint of its own — a sub-zero reading is a legal input — and the tare-versus-gross comparison belongs to request-shape validation, reported as `ERR_INVALID_REQUEST` (HTTP 400) before `grower_lot_id` is resolved, so an impossible weight pair recorded against an unknown lot reports the shape failure rather than `ERR_GROWER_LOT_NOT_FOUND`. The server derives `net_weight_lb` as the gross weight less the tare weight, rounded half-up to two decimal places, and sets `status` to `PENDING_INSPECTION` with `trim_loss_lb`, `accepted_lb` and `remaining_lb` all left null. Nothing about the grower lot's own state is checked at receiving; a load may be recorded against a lot that has not yet been adjudicated. What the lot's state controls is whether the load can ever be *consumed*.

Temperature verification happens at the moment of recording, using two strictly-greater breakpoints against the reported pulp temperature. A pulp temperature greater than 4.4 degrees Celsius grades the load `OUT_OF_SPEC`. Otherwise, a pulp temperature greater than 3.3 degrees Celsius grades it `MARGINAL`. Otherwise the load grades `IN_SPEC`. Both comparisons are strict, so a load arriving at exactly 4.4 degrees is `MARGINAL` rather than `OUT_OF_SPEC`, and a load at exactly 3.3 degrees is `IN_SPEC` rather than `MARGINAL`. The resulting grade is written to `temp_grade` and immediately frozen onto the load as a day count in `shelf_life_deduction_days`: zero days for `IN_SPEC`, one day for `MARGINAL`, and two days for `OUT_OF_SPEC`. The grade is stored rather than recomputed on demand, because two downstream rules read it — the shelf-life deduction on finished product and the grower's trailing risk score.

Disposition is a separate decision taken by a `QATechnician` or a `QAManager`, and it accepts three inputs: a `decision` of either `ACCEPT` or `REJECT`, an optional `trim_loss_lb` declaring the trim and cull pounds, and an optional `override_justification`. The load must be `PENDING_INSPECTION`; a load already dispositioned or quarantined is refused with `ERR_RECEIPT_NOT_PENDING` (HTTP 409). On an acceptance, two further checks are made and their order matters. First, a load graded `OUT_OF_SPEC` may not be accepted at all unless the acting `X-User-Role` is `QAManager` *and* `override_justification` is supplied; a justification that is absent or explicitly `null` reaches this check and the acceptance is refused with `ERR_RECEIPT_TEMP_OUT_OF_SPEC` (HTTP 422), while a justification sent as `""` or as whitespace alone never reaches it, having already failed request-shape validation with `ERR_INVALID_REQUEST` (HTTP 400). Only then is the declared trim examined: an omitted or `null` `trim_loss_lb` is taken as zero, and the value must be zero or greater and must not exceed the load's `net_weight_lb`, or the acceptance is refused with `ERR_TRIM_LOSS_EXCEEDS_NET` (HTTP 422) — a negative declaration reports that same refusal rather than a shape error, because the field itself is declared without a sign constraint. A warm load with an impossible trim declaration therefore reports the temperature refusal, not the trim refusal.

An accepted load moves `PENDING_INSPECTION → ACCEPTED`. The server sets `accepted_lb` to the net weight less the declared trim loss, rounded half-up to two decimal places, sets `remaining_lb` to that same figure — the load's full drawable balance — and stamps `dispositioned_by_user_id` with the acting `X-User-ID`. A rejected load moves `PENDING_INSPECTION → REJECTED` and its `accepted_lb`, `remaining_lb` and `trim_loss_lb` are deliberately all left null — a rejection ignores whatever trim the client declared, and neither the temperature gate nor the trim gate is evaluated on that branch at all — which is what makes a rejected load permanently unusable rather than merely discouraged. On either branch, an `override_justification` that was supplied is persisted onto the load and returned in its representation, on a rejection and on an in-specification acceptance as readily as on a genuine override; when none was supplied the field stays null. Either decision then refreshes the parent grower lot's `out_of_spec_receipt_count` and `env_positive_run_count` and, when that lot's `preharvest_risk_score` is non-null, recomputes its trailing risk score, which may move the lot `APPROVED → SUSPENDED` in the same request; the lot's own `updated_at` and `version` move only if one of those two counters, the trailing score or the `status` actually changed value. The load's own `version` is incremented by 1.

The fourth state a load can reach is `QUARANTINED`, and no client ever asks for it: a load in `PENDING_INSPECTION` or `ACCEPTED` is driven to `QUARANTINED` by the recall sweep of §3.9. Quarantine leaves `remaining_lb` untouched — the pounds are physically still on site, they have simply become unusable — and propagates onward to the runs that already consumed the load.

### 3.4. Wash-Water Chemistry: Organic Load, Tier Targets and Change-Out

The flume is the plant's central shared resource and its chemistry is monitored continuously. A `LineOperator` or a `SanitationTech` records a **wash-water reading** against a wash system with the `reading_at` instant the sample was drawn, the measured `free_chlorine_ppm` (zero or greater, one decimal place), the measured `ph` (greater than 0 and at most 14, one decimal place), the measured `orp_mv` oxidation-reduction potential in whole millivolts, and the measured `turbidity_ntu` (zero or greater, one decimal place). All five fields are required, and `orp_mv` alone carries no sign or range constraint, so a negative potential is a legal input. Nor is there any state precondition on recording: a reading may be taken on a system that has already reached `DUMP_REQUIRED`, which is how the plant documents the state of exhausted water before it is dumped. Readings are append-only measurements: the server assigns each one the next `sequence_no` for that wash system, counting from 1, advances the system's `reading_sequence_high_water` to that number, and stamps `taken_by_user_id` from the acting `X-User-ID`. Wherever a rule needs "the latest reading" for a wash system, it means the reading with the greatest `reading_at`, and when two readings share that instant, the one with the greater `sequence_no`; the list endpoint returns readings in exactly that ordering reversed, `reading_at` descending with the greater `sequence_no` first among readings sharing an instant.

Recording a reading — and equally, recording a consumption, voiding a consumption, closing a run, or changing the water — triggers a four-step chemistry recomputation on the wash system. **The four steps are strictly ordered and each consumes the output of the one before it: load, then tier, then dwell, then top-up.** Getting the order wrong changes the answer, so each step is stated exactly. The five triggers differ in one respect only, and it is a bookkeeping one. Recording a reading and recording a change-out always refresh the wash system's `updated_at` and increment its `version`, even when the recomputation lands on exactly the three derived figures the system already carried — they are writes to the system in their own right. The other three triggers — recording a consumption, voiding one and closing a run — refresh the system's `updated_at` and `version` only when the recomputation actually changes `weighted_load_lb`, `organic_load_index`, `target_free_chlorine_ppm` or `status`; a consumption that leaves all four alone leaves the system's audit fields alone too.

**Step one — the weighted organic load since the last change-out.** The server gathers the consumptions in the current load window: every lot consumption whose `status` is `ACTIVE`, whose run draws on this wash system, whose run's `run_status` is `RUNNING` or `CLOSED`, and whose `created_at` is at or after the system's `last_changeout_at`. Consumptions on runs still in `SETUP` or already `CANCELLED` are excluded, as is any consumption whose `status` is `VOIDED`. Each surviving consumption contributes its `consumed_lb` multiplied by the load factor of the commodity class of the product its run was packing: 1.0 for `LEAFY`, 1.8 for `ROOT`, and 0.5 for `FRUIT`. Those contributions are added together and the sum, rounded half-up to two decimal places, becomes `weighted_load_lb`.

**Step two — normalise, then pick the tier.** `organic_load_index` is the two-decimal `weighted_load_lb` that step one just produced — not the unrounded sum behind it — divided by the product of the system's `water_volume_gal` and a normalising constant of 10, rounded half-up to exactly three decimal places. The rounded index — not the raw quotient — then selects the tier, and all three breakpoints are inclusive on the lower side. An index of 3.000 or greater exhausts the water: the system moves `IN_SERVICE → DUMP_REQUIRED` and `target_free_chlorine_ppm` is set to null, because no chlorine tier is defined above the change-out ceiling. Otherwise, an index of 1.500 or greater sets `target_free_chlorine_ppm` to 55.0; an index of 0.500 or greater sets it to 35.0; and anything below that sets it to 20.0. An index of exactly 0.500 therefore targets 35.0, exactly 1.500 targets 55.0, and exactly 3.000 forces a change-out. The status transition is one-way: only a system currently `IN_SERVICE` is moved to `DUMP_REQUIRED`, and no recomputation ever moves a system back the other way. A void that drops the index below 3.000 again therefore re-derives a tier target — 20.0, 35.0 or 55.0 as the new index dictates — while leaving `status` at `DUMP_REQUIRED`, so the two fields legitimately disagree until a change-out is recorded. A change-out is the only operation that returns a system to `IN_SERVICE`.

**Step three — derive the dwell requirement from the tier.** When the tier target is null, or when the system has no readings at all, the required dwell is null. Otherwise the required dwell in seconds is the greater of 90 seconds and the value obtained by multiplying 90 seconds by the tier target from step two, dividing by the latest reading's measured `free_chlorine_ppm`, and rounding that quotient *up* to the next whole second. A latest reading whose measured `free_chlorine_ppm` is exactly zero is the one case where no quotient is taken at all: the requirement is the base 90 seconds, not a division by zero and not an unbounded dwell. The numerator is the tier target chosen in step two and the denominator is the measured concentration; using the measured concentration in both places, or picking the tier before the index has been rounded to three decimals, produces a different and incorrect answer. In business terms, under-chlorinated water buys its lethality with contact time.

**Step four — derive the dosing gap.** `topup_ppm_required` is the tier target from step two less the measured `free_chlorine_ppm`, rounded half-up to one decimal place, with any negative result replaced by zero. It is written onto the reading being recorded, together with `organic_load_index_at_reading` and `target_free_chlorine_ppm_at_reading` holding the load index and tier target in force at that moment, and `below_target`, a flag that is true exactly when the reading's `free_chlorine_ppm` is less than `target_free_chlorine_ppm_at_reading`. The concentration used for the two figures frozen onto a reading is always *that reading's own* `free_chlorine_ppm`, never some other reading's: a reading posted with a `reading_at` earlier than one already on file is not the system's latest reading, yet its own `topup_ppm_required` and `below_target` are still computed from its own measurement. When the tier target is null — that is, when the load index has reached 3.000 and the water is exhausted — there is no gap to dose: `topup_ppm_required` is written as null and `below_target` as false, never as true. Those four frozen values are never revised by later activity on the system.

A `SanitationTech` restores exhausted water with a **change-out**, which is legal whether the system is `DUMP_REQUIRED` or still `IN_SERVICE` — a scheduled dump ahead of the load ceiling is good practice, not an error. The change-out sets `last_changeout_at` to the logical clock's current instant, increments `changeout_count` by 1 and sets `status` to `IN_SERVICE`, and it is legal from either status without any state precondition to fail. It does *not* reset `reading_sequence_high_water`, so reading sequence numbers keep climbing across change-outs and are unique for the life of the system rather than for the life of one water charge. Because the load window now begins at the new change-out instant, the recomputation ordinarily finds no consumption inside it and resets `weighted_load_lb` to 0, `organic_load_index` to 0.000 and `target_free_chlorine_ppm` to 20.0. The one exception follows from the window's lower bound being inclusive and from the logical clock of §2.4 standing still between calls: a consumption whose `created_at` is exactly the new `last_changeout_at` — that is, one recorded at the same logical-clock reading as the change-out, with no intervening clock advance — is still inside the window and still contributes its weighted pounds, so the reset figures are not zero. Advancing the clock before the change-out is what guarantees a clean slate. The system's `version` is incremented by 1 on every change-out. A wash system can also be forced to `DUMP_REQUIRED` without any reading at all: see the sanitation-failure propagation in §3.5.

### 3.5. Sanitation Shifts, Environmental Monitoring and Corrective Actions

Sanitation is scheduled ahead of the clean itself. A `SanitationTech` or a `QATechnician` schedules a **sanitation event** on a line with a `shift` of `FIRST`, `SECOND` or `SANITATION`, the `scheduled_for` instant it is due, and `is_allergen_changeover`, a flag defaulting to false that is set true when this clean is the documented allergen changeover clean between two products of different allergen groups. The server assigns the next `sequence_no` for that line, counting from 1 and derived as one more than the number of sanitation events already on that line, and creates the event in `SCHEDULED` with `attempt_count` at 0, with `performed_by_user_id`, `validated_by_user_id`, `disassembled_component_count`, `atp_rlu`, `allergen_swab_result`, `failed_reason` and `validated_at` all null. `scheduled_for` is a client-supplied instant and may name any point in time, past or future, relative to the logical clock. Scheduling alone does not move the line's posture; only a validated or failed outcome does — which, as §2.10 spells out, is why a freshly scheduled event that becomes the line's *latest* event does not by itself restrict an `OPEN` line. The list endpoint returns a line's events by `scheduled_for` descending, with the greater `sequence_no` first among events sharing an instant.

The clean itself runs through a four-state loop. Beginning the clean moves the event `SCHEDULED → IN_PROGRESS`, and it is the same operation that re-enters the loop after a failure, moving `FAILED → IN_PROGRESS`. An event in any other state is refused with `ERR_SANITATION_INVALID_STATE` (HTTP 409). Beginning a clean is also refused while any run on the same line has `run_status` of `RUNNING`, with `ERR_LINE_RUN_IN_PROGRESS` (HTTP 409) — equipment cannot be disassembled around moving product. On entry the server stamps `started_at` and `performed_by_user_id` from the acting `X-User-ID`, increments `attempt_count` by 1, and clears the measurement fields: `disassembled_component_count` back to 0, and `atp_rlu`, `allergen_swab_result` and `failed_reason` back to null. Because `performed_by_user_id` is re-stamped on every entry, a different technician may take over a re-clean. The two clock stamps the loop records internally, `started_at` and `completed_at`, are not part of the sanitation event's representation and appear in no response body; what a client reads back of the loop's progress is `status`, `attempt_count`, the three measurements, `failed_reason` and — once the clean is validated — `validated_at`.

Submitting the completed clean moves the event `IN_PROGRESS → AWAITING_VALIDATION` and carries three measurements, all three required: `disassembled_component_count`, the number of components actually taken apart, an integer of zero or greater; `atp_rlu`, the post-clean ATP swab reading in relative light units, likewise an integer of zero or greater; and `allergen_swab_result`, either `NEGATIVE` or `POSITIVE`. The submission is refused with `ERR_DISASSEMBLY_INCOMPLETE` (HTTP 422) unless `disassembled_component_count` is at least the line's `required_disassembly_component_count`; a count exactly equal to the requirement passes. On success the three measurements are recorded and `completed_at` is stamped from the logical clock.

Validation is a `QATechnician` decision carrying an `outcome` of `PASS` or `FAIL`, and it is where segregation of duties bites: the validating `X-User-ID` must differ from the event's `performed_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. A clean moves `AWAITING_VALIDATION → VALIDATED` only when the submitted outcome is `PASS`, `atp_rlu` is at or below the line's `max_atp_rlu`, and `allergen_swab_result` is `NEGATIVE`. A reading exactly equal to `max_atp_rlu` passes. On validation the server stamps `validated_at` and `validated_by_user_id` on the event, then recomputes the line's `posture`, which can move the line `RESTRICTED → OPEN`. That same recomputation is what writes the line's `last_validated_sanitation_at`, on the terms of §2.10: it lands on this event's `validated_at` in the ordinary case, and it is written whether or not the posture moves.

Everything else fails the clean. The event moves `AWAITING_VALIDATION → FAILED` when the outcome is `FAIL`, and equally when the outcome is `PASS` but `atp_rlu` exceeds `max_atp_rlu` or `allergen_swab_result` is `POSITIVE` — a passing verdict cannot override the measurements. The server writes `failed_reason` by examining three candidate reasons in exactly this order and taking the first that applies: `ATP_ABOVE_LIMIT` when the ATP reading exceeds the line limit, then `ALLERGEN_POSITIVE` when the allergen swab came back positive, then `MANUAL_FAIL`. A failed validation is never silently retried, and it propagates through four further consequences, each caused by the one before it. The failure opens a corrective action against the line with `source_type` of `SANITATION_FAILURE`, `source_ref_id` pointing at the failed event, `severity` of `MAJOR`, and raises the line's `open_corrective_action_count` to include it. That new open action drives the line's `posture` recomputation to `RESTRICTED` — and, unlike the environmental cascade below, the remaining hops are not conditional on where the posture landed; they fire on every failed validation. The restriction then reaches the water: the server collects the distinct wash systems referenced by the runs on this line whose `run_status` is `SETUP` or `RUNNING`, processes them in `created_at` ascending order, and moves each one that is currently `IN_SERVICE` to `DUMP_REQUIRED` while leaving one already `DUMP_REQUIRED` as it stands. And every run **on any line in the plant**, not merely on the failed line, whose `run_status` is `SETUP` and whose `wash_system_id` names one of the systems the hop just visited, moves `SETUP → CANCELLED` in `planned_start_at` ascending order. The cancellation hop keys off the whole visited set, not merely the subset whose status actually flipped: a system that was already `DUMP_REQUIRED` when the failure landed still cancels every plant-wide `SETUP` run drawing on it. Note what does *not* happen: no `RUNNING` run is cancelled or held by this cascade, no grower lot is rescored, and the line stays `RESTRICTED` even after a later clean on it passes validation, because the `MAJOR` corrective action is still unverified.

Environmental monitoring runs in parallel with sanitation. A `QATechnician` logs an **environmental swab** against a line with the `zone` of the swab site — `ZONE_1`, `ZONE_2`, `ZONE_3` or `ZONE_4`, where `ZONE_1` is product contact — the `site_code` from the environmental monitoring map, the target `organism` as `LISTERIA_SPP`, `LISTERIA_MONOCYTOGENES`, `SALMONELLA` or `APC`, and the `collected_at` instant of collection, which later anchors the lookback window over closed runs. A new swab has `result` of `PENDING`, and a pending swab does not affect the line's posture at all.

Results arrive later and each recorded `result` must be a legal advance from the swab's current one. A `PENDING` swab accepts `NEGATIVE` or `PRESUMPTIVE_POSITIVE`. A `PRESUMPTIVE_POSITIVE` swab accepts `CONFIRMED_POSITIVE` or `NEGATIVE`, the latter being confirmation testing ruling the presumptive finding out. A swab that has already reached `NEGATIVE` or `CONFIRMED_POSITIVE` accepts nothing further. Anything else is refused with `ERR_SWAB_INVALID_RESULT_TRANSITION` (HTTP 409). Every accepted result stamps `resulted_at` from the logical clock and `resulted_by_user_id` from the acting `X-User-ID`, and recomputes the line's posture. The consequences differ sharply by branch, and each branch is spelled out:

- `PENDING → NEGATIVE`: the posture recomputation runs and can clear a restriction that an earlier presumptive finding had imposed. No corrective action is opened.
- `PENDING → PRESUMPTIVE_POSITIVE`: the posture recomputation makes the line `RESTRICTED` — a presumptive finding in any zone restricts the line and never freezes it — and no corrective action is opened.
- `PRESUMPTIVE_POSITIVE → NEGATIVE`: the posture recomputation runs and can restore `OPEN`. No corrective action is opened, so nothing cascades.
- `PRESUMPTIVE_POSITIVE → CONFIRMED_POSITIVE`: the full containment sweep described next.

A confirmation is the plant's most consequential single event, and it propagates through four caused consequences after the result itself is written. First, the confirmation opens a corrective action against the swab's line with `status` of `OPEN`, `source_type` of `ENV_SWAB`, `source_ref_id` pointing at the swab, and `severity` of `CRITICAL` when the swab's `zone` is `ZONE_1` and `MAJOR` for every other zone; the line's `open_corrective_action_count` rises to include it. Second, the line's posture is recomputed, which yields `FROZEN` for a `CRITICAL` action and, on a line carrying nothing worse, `RESTRICTED` for a `MAJOR` one. Third — and **only** when that recomputation landed on `FROZEN`, which is a test of where the posture now stands rather than of whether it changed — production on the line is contained: every run on the line with `run_status` of `SETUP` moves `SETUP → CANCELLED` in `planned_start_at` ascending order, and every run on the line with `run_status` of `RUNNING`, together with every run on the line with `run_status` of `CLOSED` whose `closed_at` is at or after the swab's `collected_at` minus 24 hours, whose `disposition_status` is not already `REJECTED`, moves its disposition `UNRESTRICTED → HELD` or `RELEASED → HELD` with a new hold record whose `reason` is `ENVIRONMENTAL_POSITIVE`. Fourth, for every run just held, its cases with `status` of `IN_INVENTORY` move to `ON_HOLD` in `case_sequence` ascending order, the new hold's `cases_held_count` and `shipped_case_count` are recorded, and the run's four case counters are recomputed. Then, once every hold of this sweep has been opened and not before, each grower lot behind an `ACTIVE` consumption of any run just held is rescored: its `out_of_spec_receipt_count` and `env_positive_run_count` are re-derived from scratch by the definitions of §3.2 — the environmental counter is *not* incremented, it is recounted, and it therefore rises by one only for a run that had no environmental-positive or recall hold against it already — and its trailing risk score is recomputed, which may in turn move those lots `APPROVED → SUSPENDED`. Deferring the rescoring until every hold exists is what makes a sweep that holds several runs of the same lot arrive at one recount rather than a running total. A lot whose counters, trailing score and `status` all come back unchanged is not a touched row and keeps its `updated_at` and `version`. A `MAJOR` confirmation, by contrast, ordinarily restricts the line and stops there: no run is cancelled and no product is held. The exception follows from the third consequence testing where the posture now stands: a `MAJOR` confirmation on a line that some earlier `CRITICAL` action has already `FROZEN` leaves the posture at `FROZEN`, and the containment therefore does fire, cancelling and holding again on the strength of the new swab's own `collected_at` lookback.

Whatever opened it, a **corrective action** is the record that keeps a line shut until the finding is genuinely resolved. Beyond `line_id`, `source_type` and `severity`, it carries a polymorphic `source_ref_id` that resolves against a different table depending on the source: an environmental swab when `source_type` is `ENV_SWAB`, a sanitation event when `source_type` is `SANITATION_FAILURE`, and a wash-water reading when `source_type` is `ANTIMICROBIAL_EXCURSION`. A new action has `status` of `OPEN`, `reopen_count` at 0, `opened_at` stamped from the logical clock, and `action_taken`, `implemented_by_user_id`, `verified_by_user_id` and `verified_at` all null. A `QATechnician` takes ownership, moving the action `OPEN → IN_PROGRESS` and stamping `implemented_by_user_id` from the acting `X-User-ID`. A technician then submits the work for verification with a narrative in the required `action_taken`, moving the action `IN_PROGRESS → VERIFICATION_PENDING`; the submitter is not required to be the operator in `implemented_by_user_id` and submitting never re-stamps that field, so ownership stays with whoever took it. Neither taking ownership nor submitting recomputes the line's posture, because neither changes what §2.10 projects. Verification is a `QAManager` decision carrying an `outcome`, and the verifying `X-User-ID` must differ from `implemented_by_user_id` on both branches or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. An `outcome` of `PASS` moves the action `VERIFICATION_PENDING → VERIFIED`, stamps `verified_at` and `verified_by_user_id`, and recomputes the posture — which drops the line's re-derived `open_corrective_action_count` by one and may move the line `FROZEN → RESTRICTED` or `FROZEN → OPEN` depending on what else is still open. An `outcome` of `FAIL` moves the action `VERIFICATION_PENDING → IN_PROGRESS`, increments `reopen_count` by 1, clears `action_taken` back to null, leaves `verified_at` and `verified_by_user_id` null, and runs no posture recomputation at all, so the line's stored `posture` and `open_corrective_action_count` are left exactly as they were — which is the same value a recomputation would have produced, the action having stayed in the open set. The implement-and-verify cycle is unbounded; only a passing verification terminates the record. Any of these three operations attempted from the wrong state is refused with `ERR_CORRECTIVE_ACTION_INVALID_STATE` (HTTP 409): taking ownership requires `OPEN`, submitting requires `IN_PROGRESS`, and verifying requires `VERIFICATION_PENDING`.

### 3.6. Planning and Starting a Processing Run

A **processing run** is the unit of production, and it carries two state dimensions that advance independently of each other. `run_status` tracks production progress through `SETUP`, `RUNNING`, `CLOSED` and `CANCELLED`, with `CLOSED` and `CANCELLED` terminal. `disposition_status` tracks quality release through `UNRESTRICTED`, `HELD`, `RELEASED` and `REJECTED`, with only `REJECTED` terminal. The two never gate each other except in the two places this document says they do: a `CANCELLED` run cannot be placed on hold, and shipping reads the disposition dimension only.

A `LineOperator` plans a run by naming its `line_id`, its `product_id`, the `customer_spec_id` it will pack to, the `wash_system_id` it will draw on, the planned occupancy window as `planned_start_at` and `planned_end_at`, and `crew_size`, the crew head count of at least 1 that later multiplies the labour cost. A run reworking rejected product also names `rework_source_run_id`, the earlier run whose product is being reprocessed; the field is optional and may be omitted or sent as null. The new run begins with `run_status` of `SETUP` and `disposition_status` of `UNRESTRICTED`, and `started_at`, `closed_at`, `target_ppm_at_start` and `required_dwell_seconds_at_start` all null. Three numeric fields begin at zero rather than null — `input_lb` at 0.00, `antimicrobial_excursion_count` at 0, and all four case counters (`cases_available`, `cases_on_hold`, `cases_shipped`, `cases_destroyed`) at 0 — while every figure that only a close can produce is null on the planned run: `actual_dwell_seconds`, `spin_rpm`, `spin_seconds`, `atmosphere_actual`, `water_gal_used`, `cases_produced`, `output_lb`, `yield_pct`, `min_ppm_observed`, `provisional_shelf_life_days`, `provisional_code_date`, `final_shelf_life_days`, `final_code_date`, `total_run_cost_cents`, `per_case_cost_cents` and `cost_remainder_cents`. Every one of those fields is present in the run's representation from the moment it is planned; none is omitted merely because it is null. At planning time the server also computes `allergen_changeover_required`, which is true exactly when the line's `last_run_allergen_group` is non-null and differs from the `allergen_group` of the product this run will pack — that is, the line last ran a different allergen and has not been changed over. On a line that has never run anything, `last_run_allergen_group` is null and no changeover is required.

Planning enforces six rules, evaluated in this order after the four foreign keys have been resolved as described in §2.8:

1. The named specification must belong to the named product: its `product_id` must equal the run's `product_id`, or the request is refused with `ERR_SPEC_PRODUCT_MISMATCH` (HTTP 422).
2. The named specification's `status` must be `ACTIVE`; a `SUPERSEDED` revision cannot be packed to, and naming one is refused with `ERR_SPEC_NOT_ACTIVE` (HTTP 422).
3. When `rework_source_run_id` is supplied, the run it names must have `disposition_status` of `REJECTED` — only rejected product may be reworked — or the request is refused with `ERR_REWORK_SOURCE_NOT_REJECTED` (HTTP 422).
4. The planned window is treated as half-open: `planned_start_at` is inclusive and `planned_end_at` is exclusive, and `planned_end_at` must be strictly after `planned_start_at`. The window must not overlap the window of any other run on the same line whose `run_status` is `SETUP` or `RUNNING`. Two windows that merely touch, where one ends at exactly the instant the next begins, do not overlap. A violation of either the ordering or the exclusion is refused with `ERR_LINE_INTERVAL_CONFLICT` (HTTP 409).
5. A changeover buffer protects against allergen carry-over in the schedule. Consider the immediately preceding non-terminal run on the same line — the run with the greatest `planned_end_at` that is at or before the new run's `planned_start_at`; when two such runs share that greatest `planned_end_at`, the earlier-created of the two is the one considered. When that run packs a product whose `allergen_group` differs from the new run's product's `allergen_group`, the gap between that run's `planned_end_at` and the new `planned_start_at` must be at least 45 minutes; a gap of exactly 45 minutes passes. A shorter gap is refused with `ERR_CHANGEOVER_BUFFER_REQUIRED` (HTTP 409).
6. The wash system has an aggregate occupancy limit rather than a pairwise exclusion, because runs on different lines legitimately share a flume. Count the other runs on the same wash system whose `run_status` is `SETUP` or `RUNNING` and whose half-open planned window overlaps the new run's window; that count must be strictly less than the system's `max_concurrent_runs`, since the new run would be the next occupant after those already counted. Otherwise the request is refused with `ERR_WASH_SYSTEM_CAPACITY_EXCEEDED` (HTTP 409).

Starting the run is where every food-safety gate in the plant converges, and it moves the production dimension `SETUP → RUNNING`. The run must be in `SETUP`; any other `run_status` is refused with `ERR_RUN_NOT_IN_SETUP` (HTTP 409). The remaining gates are then evaluated in this order:

1. The line's derived `posture` must be `OPEN`. A `RESTRICTED` or `FROZEN` line is refused with `ERR_LINE_NOT_OPEN` (HTTP 409). Since posture requires the line's latest sanitation event to be `VALIDATED` and no unverified corrective action to exist, this single gate carries the whole sanitation and corrective-action programme into every start.
2. The run's wash system must have `status` of `IN_SERVICE`; a system awaiting a dump is refused with `ERR_WASH_SYSTEM_DUMP_REQUIRED` (HTTP 422).
3. At least one wash-water reading must exist for that wash system, or the start is refused with `ERR_NO_ANTIMICROBIAL_READINGS` (HTTP 422).
4. The latest reading must be fresh: its `reading_at` must be no earlier than the logical clock's current instant minus 60 minutes. A reading exactly 60 minutes old is still fresh; an older one is refused with `ERR_ANTIMICROBIAL_READING_STALE` (HTTP 422).
5. That same latest reading's `free_chlorine_ppm` must be at least the product's `min_antimicrobial_ppm`. Exactly equal passes; below the minimum is refused with `ERR_ANTIMICROBIAL_BELOW_MINIMUM` (HTTP 422).
6. When the run's `allergen_changeover_required` is true, the newest `VALIDATED` sanitation event on the line must have `is_allergen_changeover` true, `allergen_swab_result` of `NEGATIVE`, and a `validated_at` at or after the line's `last_run_ended_at`. "Newest" here is the same key §2.10 uses for `last_validated_sanitation_at` and not the `scheduled_for` key of the latest-event projection: the `VALIDATED` event with the greatest `validated_at`, tie-broken by the greater `sequence_no`. The third comparison is conditional on there being something to compare against — when the line's `last_run_ended_at` is still null, because no run has yet ended on it, that comparison is skipped and the first two conditions suffice. Any of those failing, or the line having no `VALIDATED` event at all, is refused with `ERR_ALLERGEN_CHANGEOVER_NOT_VALIDATED` (HTTP 422) — a changeover clean performed *before* the previous product finished does not count.

A successful start stamps `started_at` from the logical clock and freezes two figures onto the run by running the four-step wash-water chemistry of §3.4 in its pinned step order: `target_ppm_at_start` receives the tier target from step two and `required_dwell_seconds_at_start` receives the dwell requirement from step three. Both are frozen for the life of the run and are never revised by consumption recorded later — and since the run's own consumptions are always created after `started_at`, they never contribute to the run's own frozen figures in the first place. That evaluation is read-only on the flume: starting a run reads the four steps but writes none of the wash system's own derived fields, so `weighted_load_lb`, `organic_load_index` and `target_free_chlorine_ppm` on the system row are left exactly as the last reading or consumption left them, the system row is not a mutation and its `version` does not move, and a start can never be the event that pushes a system to `DUMP_REQUIRED`. The start also sets the line's `last_run_allergen_group` to the `allergen_group` of the product now running — and only when that field is not already that group, so a start that finds the line already carrying the right allergen group leaves the line row untouched, with its `updated_at` and `version` where they were — recomputes the run's `allergen_changeover_required` to false, and increments the run's `version` by 1.

Not every run reaches `RUNNING`. A run sitting in `SETUP` is driven `SETUP → CANCELLED` by either of two upstream events: the containment sweep that follows a `CRITICAL` environmental confirmation on its line, or the wash-system dumping that follows a failed sanitation validation on any line sharing its flume. Cancellation leaves `disposition_status` untouched at `UNRESTRICTED`, which is the clearest demonstration that the two dimensions are genuinely independent, and because no case has been packed yet, no case cascade fires.

### 3.7. Lot Consumption, the Pound Balance and Traceability

Raw pounds reach a run through **lot consumption** records, which form the many-to-many join between runs and received loads and are the backbone of traceability in both directions. A `LineOperator` records one by naming the `raw_receipt_id` of the load being drawn down and the `consumed_lb` pounds drawn, greater than zero with two decimal places, together with the `expected_process_run_version` required by §2.7. The run's own identity supplies `process_run_id`. The new record has `status` of `ACTIVE`, `voided_at` null, and `recorded_by_user_id` stamped from the acting `X-User-ID`.

Consumption is permitted while the run's `run_status` is `SETUP` or `RUNNING`; a `CLOSED` or `CANCELLED` run is refused with `ERR_RUN_NOT_RUNNING` (HTTP 409). Four business rules then apply in this order:

1. The grower lot behind the named load must have `status` of `APPROVED`. Lots that are `PENDING_APPROVAL`, `SUSPENDED`, `REJECTED` or `RECALLED` may never be consumed, and the attempt is refused with `ERR_GROWER_LOT_NOT_APPROVED` (HTTP 422).
2. The load itself must have `status` of `ACCEPTED`. Loads still `PENDING_INSPECTION`, or `REJECTED`, or `QUARANTINED` may never be consumed, and the attempt is refused with `ERR_RECEIPT_NOT_ACCEPTED` (HTTP 422). This precedes the balance rule deliberately, so an unusable load never reports a balance problem.
3. The grower lot's `commodity_class` must equal the `commodity_class` of the product the run is packing; a mismatch is refused with `ERR_COMMODITY_CLASS_MISMATCH` (HTTP 422).
4. The pounds requested must fit: `consumed_lb` must not exceed the load's `remaining_lb`, which already nets out every earlier `ACTIVE` consumption drawn from that load by *any* run. Exactly equal passes and drives the balance to zero; anything more is refused with `ERR_INSUFFICIENT_RECEIPT_BALANCE` (HTTP 422).

The two balances the system maintains are both sums over `ACTIVE` consumptions only. A load's `remaining_lb` is its `accepted_lb` less the total `consumed_lb` of every `ACTIVE` consumption naming that load, rounded half-up to two decimal places. A run's `input_lb` is the total `consumed_lb` of every `ACTIVE` consumption naming that run, rounded half-up to two decimal places, and starts at 0. Both balances are recomputed from those definitions on every write rather than adjusted in place, so the load row is a mutation only when its recomputed `remaining_lb` genuinely differs from what it already held: a draw of a fraction of a pound too small to survive the two-decimal rounding leaves the load's `remaining_lb`, `updated_at` and `version` all exactly where they were. Nothing forbids a run from drawing repeatedly on the same load either — each draw is its own consumption record, and the balance rule simply nets them all. Recording a consumption therefore lowers the load's remaining pounds and raises the run's input pounds by the same figure, recomputes the wash system's chemistry per §3.4 — which can push the system to `DUMP_REQUIRED` in the middle of production — and increments the run's `version` by 1.

Mistakes are corrected by **voiding**, never by deletion, and a void is a true compensating operation. Voiding is available to a `LineOperator` while the run's `run_status` is `SETUP` or `RUNNING`, requires `expected_process_run_version` exactly as the original write did, and requires the consumption's `status` to still be `ACTIVE`; a second void on the same record is refused with `ERR_CONSUMPTION_ALREADY_VOIDED` (HTTP 409). Those two state checks are ordered as written: the run's own state is examined first, so voiding an already-voided consumption on a run that has since closed reports `ERR_RUN_NOT_RUNNING` rather than `ERR_CONSUMPTION_ALREADY_VOIDED`. The void sets `status` to `VOIDED` and stamps `voided_at` from the logical clock, restores the load's `remaining_lb` to exactly its pre-consumption value, lowers the run's `input_lb` by exactly the same pounds, recomputes the wash system's `weighted_load_lb`, `organic_load_index` and `target_free_chlorine_ppm`, and increments the run's `version` by 1. No residue is left behind. From that moment the voided row is invisible to every aggregate in this document: it contributes no pounds to either balance, no organic load to the flume, no temperature grade to the shelf-life calculation and no harvest date to the harvest-lag calculation — though the row itself remains readable as part of the audit trail, and the consumption listings on both the run side and the load side will still return it when the `status` filter permits.

Because traceability is the whole point, the system also exposes a consolidated one-hop recall view of a run. It returns the run's own `process_run_id`, the `product_code` of the product it packed and the `customer_code` of the specification it packed to, the identifiers and grower codes of every lot that fed it as `grower_lot_ids` and `grower_codes`, the `raw_receipt_ids` of every load drawn, the `active_consumption_count` and `voided_consumption_count` of its consumption records, the `case_count` of cases it produced together with the `shipped_case_count`, `on_hold_case_count` and `destroyed_case_count` breakdown, the `effective_code_date` currently in force on the run's product, and the rework ancestry as the immediate `rework_source_run_id` plus the full chain of `rework_ancestor_run_ids`. Five details of that view are fixed. The three lineage arrays are built from the run's `ACTIVE` consumptions alone — a voided consumption contributes neither its load nor its lot nor its grower code, consistent with every other aggregate — and each array is de-duplicated in first-appearance order, walking the active consumptions in the order they were recorded. `active_consumption_count` counts the `ACTIVE` rows and `voided_consumption_count` is every other consumption on the run, so the two always sum to the run's consumption record count. `case_count` counts *all* the run's cases whatever their status, so it is 0 before the run closes and equals `cases_produced` afterwards, and the three named breakdown figures are subsets of it — there is no in-inventory figure in this view. `effective_code_date` is the run's `final_code_date` when a hold release has produced one and its `provisional_code_date` otherwise, and null on a run that has not yet closed. And `rework_ancestor_run_ids` begins with the immediate `rework_source_run_id` and then climbs one generation at a time, nearest ancestor first, stopping at the first run that names no source of its own — the climb is not depth-capped the way the recall sweep's downward walk is, it simply stops if it ever revisits a run it has already listed, and it is an empty array on a run that is not a rework. This is the view the quality group reads first when a laboratory result forces a decision under time pressure.

### 3.8. Closing a Run: Compliance, Yield, Shelf Life, Code Dates and Cost

Closing a run is the heaviest single operation in the system. A `LineOperator` reports six measured figures: `actual_dwell_seconds`, the flume dwell time actually achieved; `spin_rpm` and `spin_seconds`, the spin dryer's speed and cycle length; `atmosphere_actual`, the packaging atmosphere actually applied as `AIR`, `MAP_LOW_O2` or `MAP_HIGH_CO2`; `water_gal_used`, the wash water gallons the run consumed; and `cases_produced`, the number of cases packed, at least 1. The first three and `water_gal_used` must be zero or greater. The close moves the production dimension `RUNNING → CLOSED`; a run in any other `run_status` is refused with `ERR_RUN_NOT_RUNNING`.

The gates on a close are evaluated in this order. At least one wash-water reading must fall inside the run's window, or the close is refused with `ERR_NO_ANTIMICROBIAL_READINGS` (HTTP 422). Then `actual_dwell_seconds` must be at least the greater of the product's `min_dwell_seconds` and the run's frozen `required_dwell_seconds_at_start`; exactly equal passes, and anything short is refused with `ERR_DWELL_TIME_INSUFFICIENT` (HTTP 422). Then `atmosphere_actual` must equal the specification's `atmosphere_required`, or the close is refused with `ERR_ATMOSPHERE_MISMATCH` (HTTP 422). Then at least one consumption on the run must have `status` of `ACTIVE`, so that `input_lb` is greater than zero; a run with nothing consumed is refused with `ERR_NO_LOTS_CONSUMED` (HTTP 422). Finally the computed yield must fall within tolerance, as described below, or the close is refused with `ERR_YIELD_OUT_OF_TOLERANCE` (HTTP 422).

**Antimicrobial compliance over the run window.** The run window is the closed interval running from `started_at` to `closed_at` with both ends inclusive: a reading taken at exactly `started_at`, or at exactly `closed_at`, is inside it. Only readings on the run's own wash system count, and readings taken before the run started or after it closed are excluded even when they belong to the same wash system and the same change-out window. The lowest `free_chlorine_ppm` among the in-window readings is stored as `min_ppm_observed`, compared at one decimal place with no rounding. `antimicrobial_excursion_count` is the number of in-window readings whose `free_chlorine_ppm` is strictly below the product's `min_antimicrobial_ppm`, so a reading exactly equal to the product minimum is compliant. A non-zero excursion count does not block the close; it triggers an automatic hold and corrective action described at the end of this subsection.

**Mass balance and yield.** `output_lb` is `cases_produced` multiplied by the specification's `case_net_weight_lb`, rounded half-up to two decimal places. `yield_pct` is that stored, already-rounded `output_lb` — not the unrounded product of cases and case weight — divided by the run's `input_lb`, multiplied by 100, and the quotient rounded half-up to exactly two decimal places. The tolerance test is then made against that rounded percentage, never against the unrounded quotient: `yield_pct` must be at least the product's `min_yield_pct` and at most 100.00. A yield exactly equal to the product minimum passes, and a yield of exactly 100.00 passes; a yield above 100.00 cannot be physical, since a run cannot pack more finished pounds than the raw pounds it consumed.

**Provisional shelf life and code date.** Shelf life is computed at close in its provisional form, and the computation proceeds in a fixed order. The base window is the smaller of the product's `base_shelf_life_days` and the specification's `max_shelf_life_days_offered` — the customer's cap can shorten the validated life but never extend it. A **temperature penalty** is then taken: across the loads behind the run's `ACTIVE` consumptions, take the worst `temp_grade`, meaning the grade carrying the largest deduction, and deduct its day count — zero days for `IN_SPEC`, one day for `MARGINAL`, two days for `OUT_OF_SPEC`. A **harvest-lag penalty** follows: take the oldest `harvest_datetime` among the grower lots behind those same `ACTIVE` consumptions, measure the time from that instant to the reference instant in whole hours by discarding any partial hour, divide that hour count by 24 discarding any remainder to obtain a whole number of lag days, subtract one grace day, and treat a negative result as zero. The grace day is subtracted *after* the lag has been reduced to whole days, so 47 elapsed hours give one lag day and no penalty, while 51 elapsed hours give two lag days and a one-day penalty. A **spin penalty** of one day is taken when the reported `spin_rpm` is strictly below the product's `min_spin_rpm`, and zero otherwise. A **micro penalty** completes the list and is zero in the provisional computation, because no micro result exists yet. The shelf life in days is then the base window less all four penalties, floored at three days — and the floor is applied last, to the total, not to each term: a base of 12 with penalties totalling 11 yields 3, not 1. The result is written to `provisional_shelf_life_days`. The provisional code date is the UTC calendar date of the reference instant advanced by that many whole days, written to `provisional_code_date` as an ISO date in `YYYY-MM-DD` form. In the provisional computation the reference instant is the run's `started_at`.

**Cost allocation to the exact cent.** The run's cost is built from four components, and each is rounded half-up to whole cents *independently* before any of them are added together. The water component is `water_gal_used` multiplied by 0.37 cents per gallon. The sanitizer component is the closing top-up concentration multiplied by `water_gal_used`, multiplied by 0.0021 cents per parts-per-million-gallon, where the closing top-up concentration is the `topup_ppm_required` of the in-window reading with the greatest `reading_at`, tie-broken by the greatest `sequence_no`; a closing reading whose `topup_ppm_required` is null — one taken when the organic load had already passed the change-out ceiling and no tier target existed — is read as a concentration of zero, so the sanitizer component is zero rather than undefined. The labour component is the run's elapsed minutes — the time from `started_at` to `closed_at` in whole minutes, discarding any partial minute — multiplied by `crew_size` and by 58 cents per crew-minute; a run closed in the same logical-clock instant it started has zero elapsed minutes and therefore no labour cost. The energy component is `spin_seconds` multiplied by `cases_produced` and by 0.014 cents per spin-second-case. The four rounded components are summed into `total_run_cost_cents`. That total is then allocated so that not one cent is created or destroyed: `per_case_cost_cents` is the total divided by `cases_produced` with any fraction discarded, `cost_remainder_cents` is the total less the per-case figure multiplied by the case count, and the remainder is distributed as a waterfall over `case_sequence` ascending — each case whose `case_sequence` is less than or equal to `cost_remainder_cents` receives `per_case_cost_cents` plus one cent in its `allocated_cost_cents`, and every other case receives exactly `per_case_cost_cents`. The sum of `allocated_cost_cents` across the run's cases therefore equals `total_run_cost_cents` exactly. The waterfall key is `case_sequence` and never a case identifier.

**Case creation.** The close creates one `FinishedCase` row per case packed, numbered by `case_sequence` from 1 through `cases_produced`. Each case carries `process_run_id`, a `case_code` composed of the line's `line_code`, a hyphen, the pack date rendered as eight digits in year-month-day order, another hyphen, and the case's `case_sequence` zero-padded to four digits — where the pack date is the UTC calendar date of the run's `started_at`. Each case copies the specification's `case_net_weight_lb` into its own `net_weight_lb`, receives the run's `provisional_code_date` as its `code_date`, and receives a `code_date_label` rendering that code date in the format the specification's `code_date_format` demands: for `CALENDAR`, the ISO form `YYYY-MM-DD`; for `JULIAN`, a seven-character string of the four-digit year followed by the zero-padded three-digit day of the year. Each case also receives its `allocated_cost_cents` from the waterfall, and a `status` of `IN_INVENTORY` with `shipped_at` null. The run's `cases_available` is set to `cases_produced` and the other three case counters remain 0.

**Automatic holds.** Two branches may open a hold in the same close, and each is stated in full. When the product's `hold_and_release_required` is true, the close opens a hold record with `reason` of `HOLD_AND_RELEASE_TESTING`, moves the run's disposition `UNRESTRICTED → HELD`, and moves every newly created case `IN_INVENTORY → ON_HOLD`. When `antimicrobial_excursion_count` is greater than zero, the close opens a hold record with `reason` of `ANTIMICROBIAL_EXCURSION` and additionally opens a corrective action on the line with `source_type` of `ANTIMICROBIAL_EXCURSION`, `severity` of `MAJOR`, and `source_ref_id` pointing at the in-window reading with the lowest `free_chlorine_ppm`, tie-broken by the lowest `sequence_no`; the line's posture is then recomputed, which will restrict the line. When both branches fire in the same close the hold-and-release record is opened first, and the consequence is visible on the two records: it is the one whose `cases_held_count` equals `cases_produced`, while the excursion hold — finding every case already `ON_HOLD` and the disposition already `HELD` — records a `cases_held_count` of 0. Either way both holds record a `shipped_case_count` of 0, since no case can have shipped before the close that created it. Finally, the close stamps `closed_at` from the logical clock, sets the line's `last_run_ended_at` to that instant, recomputes the wash system's `weighted_load_lb`, `organic_load_index` and `target_free_chlorine_ppm` — because the run's consumptions now sit on a `CLOSED` run and so remain inside the load window — and increments the run's `version` by 1 when no automatic hold fired, or by 2 when either or both of them did, the move to `HELD` with its case re-disposition being a second, separate mutation of the run row rather than part of the close's own write. The line row is likewise a mutation once for the `last_run_ended_at` stamp, and a second time on the excursion branch when the posture recomputation that follows changes `posture` or `open_corrective_action_count`, so an excursion close leaves the line two versions ahead.

### 3.9. Hold-and-Release Testing, Shipping and Recall

A **hold record** is the quality dimension made concrete. It names the `process_run_id` of the run whose product is held and a `reason` drawn from `HOLD_AND_RELEASE_TESTING`, `ENVIRONMENTAL_POSITIVE`, `SANITATION_FAILURE`, `ANTIMICROBIAL_EXCURSION` or `RECALL`. A `QATechnician` may open one directly on any run whose `disposition_status` is not `REJECTED` and whose `run_status` is not `CANCELLED`, naming freely any of the five reasons — nothing reserves `ENVIRONMENTAL_POSITIVE`, `SANITATION_FAILURE`, `ANTIMICROBIAL_EXCURSION` or `RECALL` to the server's own sweeps. A violation of either state condition is refused with `ERR_HOLD_INVALID_STATE` (HTTP 409), the rejected disposition being reported before the cancelled production state, so a run that is both reports the disposition. Note that a run may be held while it is still `SETUP` or `RUNNING`, since the two dimensions advance independently. The same creation and cascade also happen without a client request, when the recall sweep, the environmental containment sweep, or the automatic branches of a run close open a hold on the system's own initiative; the only differences are the `reason` carried and that the two state refusals above are the client's alone — a sweep skips a run whose `disposition_status` is already `REJECTED`, but it holds a `CANCELLED` run just as readily as a `RUNNING` one.

However it is opened, a hold record is created with `status` of `HELD`, `test_round` at 0, `opened_at` stamped from the logical clock, and `latest_test_type`, `latest_test_result`, `latest_apc_cfu_g`, `resulted_by_user_id`, `released_by_user_id` and `closed_at` all null. Opening it moves the run's disposition to `HELD` — from `UNRESTRICTED` or, when later evidence re-implicates a run that was already cleared, from `RELEASED`, because this dimension is deliberately not monotonic. Every case of the run with `status` of `IN_INVENTORY` moves to `ON_HOLD`; cases already `SHIPPED` or `DESTROYED` are left alone. The hold's `cases_held_count` records how many cases just moved, and its `shipped_case_count` records how many of the run's cases had already shipped at that moment — the customer notification list size. Both are written as part of creating the hold rather than as a later edit of it, so a freshly opened hold record carries `version` 1 with those counts already in place. The run's four case counters are then recomputed. The run row is a mutation only when the opening actually changed something about it: on a run that is already `HELD` with all of its remaining cases already `ON_HOLD` — the second hold of a pair — the disposition and all four counters are already where this opening would put them, so the run's `updated_at` and `version` stay exactly where they were even though a new hold record now exists.

Testing runs as a bounded loop. Submitting a micro sample is legal from `HELD` or from `RETEST_REQUIRED` and carries the assay in `latest_test_type` as `APC`, `LISTERIA`, `ECOLI_O157` or `SALMONELLA`. It is refused with `ERR_MAX_RETEST_ROUNDS_EXCEEDED` (HTTP 409) unless `test_round` is strictly below 3, so a fourth sample against the same hold is never accepted. The state check comes first: a hold that is neither `HELD` nor `RETEST_REQUIRED` reports `ERR_HOLD_INVALID_STATE` (HTTP 409) even when its three rounds are also spent. A successful submission increments `test_round` by 1, records the assay, clears `latest_test_result`, `latest_apc_cfu_g` and `resulted_by_user_id` from any earlier round, and moves the hold `HELD → UNDER_TEST` or `RETEST_REQUIRED → UNDER_TEST`.

Recording the laboratory result is legal only from `UNDER_TEST` and carries `latest_test_result` as `NEGATIVE`, `POSITIVE` or `INDETERMINATE`, optionally with `latest_apc_cfu_g`, the aerobic plate count in colony-forming units per gram, which must be zero or greater. A result of `NEGATIVE` or `POSITIVE` leaves the hold in `UNDER_TEST` — a self-loop, so one round can be resulted and then acted on — while a result of `INDETERMINATE` moves the hold `UNDER_TEST → RETEST_REQUIRED` and leaves `test_round` unchanged, which means the next submission consumes one of the three rounds. Either way the server records the result fields and stamps `resulted_by_user_id` with the acting `X-User-ID`. `latest_apc_cfu_g` is written unconditionally from what the request carried, so a submission that omits it or sends it as `null` writes null and does not leave an earlier count in place: re-recording a result on the same round without the plate count clears it.

Release is a `QAManager` decision and it is guarded four ways, evaluated in this order: the hold must be in `UNDER_TEST` and every *other* hold record on the same run must already be in a terminal state of `RELEASED` or `REJECTED`, or the request is refused with `ERR_HOLD_INVALID_STATE` (HTTP 409); the releasing `X-User-ID` must differ from the hold's `resulted_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`; and the hold's `latest_test_result` must be `NEGATIVE`, since a `POSITIVE` or `INDETERMINATE` latest result cannot be released, or the request is refused with `ERR_TEST_RESULT_NOT_NEGATIVE` (HTTP 409).

A release stamps `closed_at` and `released_by_user_id`, moves the hold `UNDER_TEST → RELEASED`, and moves the run's disposition `HELD → RELEASED`. It also recomputes shelf life in its **final** form, which differs from the provisional form in exactly two respects. The reference instant becomes the run's `closed_at` rather than its `started_at`, which is later and can therefore make the harvest-lag penalty a full day larger. And the micro penalty becomes two days when the releasing hold's `latest_apc_cfu_g` is at least 1,000,000 colony-forming units per gram, and zero otherwise. Every other term is computed exactly as it was provisionally — including the spin penalty, which is evaluated in both forms from the same reported `spin_rpm` and so is never itself the source of a divergence between them. The results are written to `final_shelf_life_days` and `final_code_date`, and because both changes can only shorten the window, the final code date is never later than the provisional one. Because `closed_at` is what supplies the reference instant, a release on a run that never reached `CLOSED` — the hold having been opened while the run was still `SETUP` or `RUNNING` — has no reference instant to work from and so computes no final figures at all: `final_shelf_life_days` and `final_code_date` stay null, and no case is re-dated. Otherwise the final code date is stamped onto every case of the run that is neither `SHIPPED` nor `DESTROYED`, rewriting both `code_date` and `code_date_label`; product already in a customer's hands keeps the label it left with. A case whose `code_date` and `code_date_label` already read the final values and which was not itself on hold has nothing rewritten and is not a mutation, so its `updated_at` and `version` do not move — which is the ordinary outcome when the final window turns out identical to the provisional one. Finally, every case of the run with `status` of `ON_HOLD` moves back to `IN_INVENTORY`, restoring `cases_available` and `cases_on_hold` to exactly their pre-hold values, so that the pair round-trips precisely.

Rejection is the other terminal branch, available from `UNDER_TEST` or from `RETEST_REQUIRED` — the escape hatch once the three retest rounds are exhausted — and that state check is its *only* guard. Unlike release it is not gated on the latest result, so a hold sitting on a `NEGATIVE` result may still be rejected; it is not gated on the other holds of the run, so a run with several open holds may have one of them rejected while the rest are still under test; and it is not a segregation-of-duties decision, so the rejecting `X-User-ID` may be the very operator recorded in `resulted_by_user_id`. It stamps `closed_at` and `released_by_user_id` — the same field the release path stamps, since it records whoever closed the hold either way — moves the hold to `REJECTED`, moves the run's disposition to the terminal `REJECTED`, and moves every case of the run with `status` of `ON_HOLD` to `DESTROYED`, recomputing `cases_on_hold` and `cases_destroyed` so that the four counters still sum to `cases_produced`. It computes no final shelf life and no final code date: a rejected run keeps whatever `final_shelf_life_days` and `final_code_date` it already had, which on a run that was never released is null, and the cases it destroys keep the code date they were packed with. A rejected run becomes eligible to be named as the `rework_source_run_id` of a later run, which is the only way rejected product legitimately re-enters production.

Shipping is the `ShippingClerk`'s operation on an individual case, and it moves the case `IN_INVENTORY → SHIPPED`. Three checks are made in this order. First, the parent run's `disposition_status` must be `UNRESTRICTED` or `RELEASED`; a run that is `HELD` or `REJECTED` cannot ship and the attempt is refused with `ERR_HOLD_NOT_RELEASED` (HTTP 409). This precedes the case's own state check deliberately, so that a held case reports the run-level cause rather than the case-level symptom. Second, the case's own `status` must be `IN_INVENTORY`; an already `SHIPPED` or `DESTROYED` case on a run whose disposition permits shipping is refused with `ERR_CASE_NOT_IN_INVENTORY` (HTTP 409). Third, enough code-date life must remain: the number of whole days from the ship date — the UTC calendar date of the logical clock's current instant — to the case's `code_date` must be at least the specification's `min_remaining_shelf_life_days_at_ship`. Exactly equal passes; anything less is refused with `ERR_INSUFFICIENT_REMAINING_SHELF_LIFE` (HTTP 422). A successful shipment stamps `shipped_at` from the logical clock, decrements the run's `cases_available`, increments its `cases_shipped`, and increments the case's `version` by 1. The run row is a mutation too, so its `version` advances by 1 in the same request; the endpoint nevertheless returns the case, and a caller who wants the refreshed counters reads the run back.

**Recall.** When a grower lot must be pulled, a `QAManager` recalls it and the system performs the plant's widest sweep. The recall first drives the lot to `RECALLED` and stamps `recalled_at` from the logical clock. Caused by that, every load whose `grower_lot_id` names the lot and whose `status` is `PENDING_INSPECTION` or `ACCEPTED` moves to `QUARANTINED`, processed in `received_at` ascending order with `created_at` ascending as the tie-break. Caused by the quarantine, for every load that just became quarantined, every run holding an `ACTIVE` consumption of that load whose `disposition_status` is not already `REJECTED` moves its disposition to `HELD` and receives a new hold record with `reason` of `RECALL` and `status` of `HELD`, with runs processed in `planned_start_at` ascending order and `created_at` ascending as the tie-break. Caused by that hold, each newly held run moves its `IN_INVENTORY` cases to `ON_HOLD` in `case_sequence` ascending order, the opening hold's `cases_held_count` and `shipped_case_count` are recorded, and the run's `cases_available` and `cases_on_hold` are recomputed, while cases already `SHIPPED` or `DESTROYED` are left untouched.

The sweep then follows the rework chain, and this is the hop that is easiest to under-implement. Starting from **every** run that holds an `ACTIVE` consumption of a load quarantined in this recall — including the runs the previous hop skipped because their `disposition_status` was already `REJECTED`, which are precisely the runs a later rework run is allowed to name — the system walks downward along `rework_source_run_id` edges to a maximum depth of five hops. Every descendant reached whose `disposition_status` is not already `REJECTED` moves to `HELD` with its own hold record carrying `reason` of `RECALL`, and its cases follow the same `ON_HOLD` treatment — and that is so whether or not the descendant ever drew a pound of the recalled lot itself; being downstream of a contaminated run is the whole reason it is reached. A run already listed as a root is never held twice as its own descendant, and the walk abandons any edge that would revisit a run it has already reached. The descendants found at every depth are then held as a single batch in `planned_start_at` ascending order, not generation by generation, so the ordering is over the whole reached set rather than restarted at each hop. Finally, every grower lot consumed by any run held anywhere in this sweep has its `env_positive_run_count` and trailing risk score recomputed, which may move those lots `APPROVED → SUSPENDED` as a side effect of someone else's recall. Every row the sweep touches — the lot, the loads, the runs, the holds, the cases and the collaterally-suspended lots — has its `updated_at` refreshed and its `version` incremented by 1, with a single exception: the recalled lot itself advances by 2 whenever the sweep held at least one run that had consumed it, because that final recomputation hop runs on the recalled lot exactly as on any other and its own `env_positive_run_count` now counts the `RECALL` holds just opened, which is a second mutation on top of the transition to `RECALLED`.

One property of all this containment deserves restating, because it is the difference between a correct implementation and a plausible one: none of these sweeps is self-reversing. Verifying the corrective action that froze a line does not un-cancel the runs the freeze cancelled, and it does not release the holds the freeze opened. Product comes off hold only through the release path described above, one hold record at a time.

## 4. API Endpoints

All paths are mounted at the server root; there is no version or namespace prefix. Every collection is a flat peer of every other, and nested paths appear only where a child resource is genuinely subordinate to its parent, in which case the parent identifier in the path is authoritative and no duplicate parent identifier is accepted in the body.

Endpoints that create a new resource respond with HTTP 201 and return the created resource in `data`. Endpoints that modify an existing resource — every state transition, every disposition, every result and every void — respond with HTTP 200 and return the updated resource in `data`, so that the caller can read back the recomputed derived fields and the incremented `version` without a second request. Read endpoints respond with HTTP 200. Where a transition has effects on other resources, those effects are applied before the response is serialised, so the returned representation and every sibling collection are consistent the instant the call returns.

Every endpoint requires the `X-User-ID` and `X-User-Role` headers described in §2.1. The Authorized Roles column below is exhaustive: a syntactically valid request from a role not listed for that endpoint is refused with `ERR_UNAUTHORIZED`.

## 5. Error Codes

Three further identifiers sit outside the table because they are transport-level rather than domain outcomes, and they are returned in the same envelope: a request to a path this API does not route answers `ERR_NOT_FOUND` (HTTP 404), a request using a method the path does not support answers `ERR_METHOD_NOT_ALLOWED` (HTTP 405), and an unhandled server fault answers `ERR_INTERNAL` (HTTP 500).
