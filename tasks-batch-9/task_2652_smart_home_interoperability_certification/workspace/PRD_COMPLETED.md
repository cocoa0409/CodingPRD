# Smart Home Interoperability Certification API — Product Requirements Document

## 1. Introduction

A smart-home device only earns a consumer's trust when a lightbulb from one vendor genuinely speaks to a hub from another. Our industry consortium exists to make that promise auditable: we publish a versioned interoperability specification, we accredit the laboratories that test against it, we host multi-vendor plugfests where devices meet real peers before anybody signs a declaration of conformity, and we publish a public directory of certified devices with the exact feature set each one claims. Today that programme runs on a patchwork of spreadsheets, mailboxes and shared calendars. Specification versions drift out from under submissions that were opened months earlier; a laboratory books the same bench twice and nobody notices until a vendor's engineers are already on a plane; a member company quietly withdraws its patent commitment and its devices stay listed as certified for weeks afterwards.

This document specifies the backend service that replaces that patchwork. The service owns the full certification chain end to end: specification versioning with mandatory, optional and conditional feature sets per device class; member onboarding with intellectual-property commitments and testing-tool entitlement; the authorized laboratory network with bench scheduling, test-plan execution and result submission; the two-track review that pairs a declaration-of-conformity assessment with an independent security assessment covering device attestation, verified secure boot and firmware update capability; device attestation credential issuance; publication of the consumer-facing certification listing; recertification triggers driven by firmware revisions and specification demotion; and noncompliance investigation ending in remediation or listing withdrawal.

Three design commitments shape everything that follows. First, **version pinning**: a submission, and the test plan derived from it, freeze the specification version and the feature graph they were opened against, and a later ratified version never re-targets them. Second, **segregation of duties**: the human who signs off conformity may not also sign off security, and the officer who opens a noncompliance case may not close it. Third, **a single logical clock**: every deadline, booking window, accreditation expiry and "due in N days" computation in this service reads one server-controlled instant, never the host wall clock, so that an entire multi-month certification campaign can be replayed deterministically in a test harness. All collections are mounted directly at the API root as flat peers — `/specifications`, `/feature-sets`, `/members`, `/test-laboratories`, `/submissions`, `/test-plans`, `/test-sessions`, `/plugfests`, `/plugfest-participations`, `/listings` and `/noncompliance-cases` — with no shared prefix and no resource nested inside another resource's URL.

## 2. Global Specifications & System-Wide Principles

### 2.1. Programme Actors and Role-Based Access Control

Every request to this service carries two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the capacity in which that principal acts. Seven roles are declared, and their spelling is exact: `ProgramAdmin`, `Member`, `TestLaboratory`, `ConformanceReviewer`, `SecurityReviewer`, `ComplianceOfficer` and `PublicViewer`. If either header is absent, or if `X-User-Role` carries a string that is not one of those seven, the request is rejected with `ERR_MISSING_AUTH_HEADERS` and HTTP 401; a header that is present but empty or whitespace-only counts as absent, and surrounding whitespace is stripped from both headers before they are compared to anything. The sole exception is the logical-clock endpoint `POST /_clock/set_current_utc`, which is exempt from the header-presence requirement — omitting both headers there is accepted — although a role that *is* supplied on that endpoint is still checked against its authorized-role list, so any value other than `ProgramAdmin`, including a string that is not one of the seven declared roles, is refused there with `ERR_UNAUTHORIZED` and HTTP 403 rather than with `ERR_MISSING_AUTH_HEADERS`; every other endpoint in the service requires both headers. Once the headers are accepted, the acting role must appear in the endpoint's authorized-role list of §4; if it does not, the request is rejected with `ERR_UNAUTHORIZED` and HTTP 403.

Two of the seven roles are backed by persisted entities, and this is what ties `X-User-ID` to resource ownership:

- When `X-User-Role` is `Member`, `X-User-ID` is the `id` of the acting `Member` row. Ownership checks on any resource that references a `Member` compare the resource's `member_id` — or the `member_id` reachable through its parent chain, such as the `member_id` of the `CertificationSubmission` behind a `TestPlan`, or the `member_id` copied onto a `CertificationListing` — to `X-User-ID`.
- When `X-User-Role` is `TestLaboratory`, `X-User-ID` is the `id` of the acting `TestLaboratory` row. Session ownership compares the target `TestSession`'s `laboratory_id` to `X-User-ID`, and plugfest hosting compares the target `Plugfest`'s `host_laboratory_id` to `X-User-ID`.

The remaining five roles carry opaque identity. When `X-User-Role` is `ProgramAdmin`, `ConformanceReviewer`, `SecurityReviewer`, `ComplianceOfficer` or `PublicViewer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to an entity's `id`. It may, however, be recorded: a `ConformanceReviewer`'s identifier is written to `conformance_reviewer_user_id`, a `SecurityReviewer`'s to `security_reviewer_user_id`, and a `ComplianceOfficer`'s to `opened_by_user_id` or `closed_by_user_id`, because §2.10's segregation-of-duties rules are enforced on those recorded identifiers rather than on the role name. Where the server itself performs one of those writes as part of a cascade rather than on an operator's behalf, it records the literal string `SYSTEM` in place of a user identifier.

Ownership enforcement is not global — it applies to a fixed set of twelve write operations, and on any of them a mismatch also yields `ERR_UNAUTHORIZED` with HTTP 403. Those operations are: executing an IP commitment (`POST /members/{member_id}/ip-commitment`), withdrawing an IP commitment (`POST /members/{member_id}/ip-commitment/withdraw`), purchasing credit (`POST /members/{member_id}/credits`), opening a submission (`POST /submissions`), submitting it (`POST /submissions/{submission_id}/submit`), withdrawing it (`POST /submissions/{submission_id}/withdraw`), registering for a plugfest (`POST /plugfest-participations`), starting a test session (`POST /test-sessions/{test_session_id}/start`), appending results (`POST /test-sessions/{test_session_id}/results`), completing a session (`POST /test-sessions/{test_session_id}/complete`), cancelling a session (`POST /test-sessions/{test_session_id}/cancel`), and recording a plugfest outcome (`POST /plugfest-participations/{participation_id}/record-outcome`).

Read access is broad but not uniform. `PublicViewer` is the consumer-facing role and is read-only: it may read specifications, feature sets, laboratories, plugfests and listings, and nothing else — it can see neither member records, submissions, test plans, sessions, participations, credit ledgers nor noncompliance cases. `ComplianceOfficer` reads members, credit ledgers, laboratory competency, submissions, plugfests, listings and cases, and exclusively drives the noncompliance workflow and listing withdrawal. `ConformanceReviewer` and `SecurityReviewer` read the specification, feature-set, member, submission, plan, session, plugfest and listing surfaces, and each owns one leg of the two-track review. `ProgramAdmin` is the programme operator: it alone creates and demotes specification versions, adds feature sets, registers members and laboratories, moves testing-tool entitlement, decides accreditation, runs competency reviews, creates and issues test plans, schedules and locks and closes plugfests, issues attestation credentials, creates and publishes listings, and repositions the logical clock. §4 is the authoritative role-to-endpoint mapping.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by twenty randomly chosen uppercase-alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one timestamp in the service taken from the host wall clock rather than from the logical programme clock of §2.5, because it describes the transport rather than the domain; no domain field is ever derived from it.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.


### 2.3. Pagination, Ordering and Collection Filters

Every list endpoint in the service is paginated by two optional query parameters. `limit` defaults to 10 when omitted, and its accepted range is a minimum of 1 and a maximum of 100. `offset` defaults to 0 when omitted, and its minimum is 0 with no upper bound beyond the size of the collection. A `limit` or `offset` that is not an integer, or that falls outside those bounds, is rejected with `ERR_INVALID_REQUEST` and HTTP 400.

List responses always order the array by `created_at` ascending, oldest row first, and that ordering is stable regardless of any filter applied. Because the logical clock can stand still across several creates, `created_at` ties are common; they are broken by a monotonic store-wide insertion sequence, so rows sharing a `created_at` come back in the order they were created. The `meta` block of a list response carries `limit` and `offset` echoing the effective values used, `total_count` giving the number of rows that matched the filters before pagination was applied, and `has_more` set to true exactly when rows remain beyond the returned page.

Beyond pagination, each collection exposes a set of exact-match filters, and every foreign key declared in this specification is reverse-reachable through the filtered list form of its child collection. Specifications may be filtered by `status`, by `security_baseline_level` and by `supersedes_specification_id` (which finds the versions that supersede a given version). Feature sets accept `specification_id`, `device_type`, `obligation` and `depends_on_feature_set_id`. Members accept `tier`, `onboarding_state` and `ip_scope_specification_id`. Laboratories accept `accreditation_status` and `device_type` (matching against the laboratory's authorized device classes). Submissions accept `member_id`, `specification_id`, `state`, `dac_state` and `device_type`. Test plans accept `submission_id`, `specification_id` and `state`. Test sessions accept `test_plan_id`, `laboratory_id`, `state` and `session_type`. Plugfests accept `host_laboratory_id`, `specification_id` and `state`. Plugfest participations accept `plugfest_id`, `member_id`, `submission_id` and `state`. Listings accept `submission_id`, `member_id`, `publication_status` and `compliance_status`. Noncompliance cases accept `listing_id`, `state`, `category` and `auto_opened`. Filter values are matched exactly, and only some of them are validated: the filters named after one of §2.8's enum-typed inputs — `device_type`, `obligation`, `tier`, `security_baseline_level`, `session_type`, and the `variant` of the computed reads — are checked for enum membership and reject an unrecognised value with `ERR_INVALID_ENUM_VALUE`, whereas every other filter, including each `state`, `status`, `dac_state`, `publication_status`, `compliance_status`, `onboarding_state`, `accreditation_status` and `category` axis and every identifier filter, is compared as an opaque string, so an unrecognised value there is not an error at all: it simply matches nothing and yields an empty page with `total_count` 0. `auto_opened` is the one boolean filter and accepts only the literals `true` and `false`, anything else being rejected with `ERR_INVALID_REQUEST`. A filter supplied with an empty or whitespace-only value is treated as though it had not been supplied. Three computed-read endpoints instead accept a `variant` query parameter, which selects between the two evaluation modes of the credit ledger, the laboratory competency score and the certification readiness score respectively; each of those is described with its calculation in §3.

### 2.4. Identifiers, Audit Fields and Resource Versioning

Every one of the eleven resource families in this service — `Specification`, `FeatureSet`, `Member`, `TestLaboratory`, `CertificationSubmission`, `TestPlan`, `TestSession`, `Plugfest`, `PlugfestParticipation`, `CertificationListing` and `NoncomplianceCase` — carries the same four system-managed properties, and there are no exceptions:

- `id` — a server-minted UUID string. It carries no type prefix and no embedded meaning; clients never supply it.
- `created_at` — an ISO 8601 UTC timestamp with exactly three fractional-second digits, stamped when the row is first stored.
- `updated_at` — an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row. At creation it equals `created_at`.
- `version` — an integer that starts at 1 when the row is created and increments by one on every mutation of that row.

A mutation for these purposes is any change to any stored property, including changes to computed properties. When a laboratory's `reserved_bench_minutes` is adjusted because one of its sessions was cancelled, when a member's `credit_balance_cents` moves because a submission escrowed its fee, when a submission's `provisional_readiness_score` is refreshed by an incoming result line, or when a listing's `declared_features` is recomputed at publication, that row's `updated_at` is refreshed and its `version` increments — even though the client never named those fields in any payload. Two refinements keep the counter predictable. First, a write that leaves a property at the value it already held is not a mutation at all: nothing is stamped and nothing is incremented, so an action that recomputes a field to the figure it already carried can leave the row completely untouched. Second, a single accepted API operation advances a given row's `version` by exactly one however many internal writes, recomputations, cascade hops or fan-out effects of that one request touch it — the counter counts changing requests, not individual field assignments — and a row *created* by a request stays at `version` 1 even when a later recomputation inside that same request writes to it again. This matters directly, because §2.9's stale-view protection is evaluated against exactly that `version` counter.

Two public reference strings exist alongside `id` and are not interchangeable with it. A `CertificationListing` carries `listing_reference`, the consumer-facing handle formed from the literal prefix `LST-` followed by a six-digit zero-padded ordinal equal to one more than the number of listing rows with an earlier `created_at`; the first listing ever created is therefore `LST-000001`. A certified `CertificationSubmission` carries `dac_serial`, the serial of its issued device attestation credential, which is supplied by the programme operator at issuance and must be unique across all submissions that hold one.

### 2.5. The Logical Programme Clock

This domain is saturated with time: accreditation lapses, bench windows open and close, plugfest registration deadlines pass, remediation deadlines expire, recertification falls due a fixed number of days after a trigger, and a rolling ninety-day competency window slides forward. Every one of those computations reads a single server-held logical clock, and none of them reads the host's wall clock. Before the clock has ever been repositioned it reads exactly `2026-08-01T00:00:00.000Z`; that startup default is normative, and the service must not silently fall back to real time.

A `ProgramAdmin` repositions the clock by supplying `current_utc`, an arbitrary UTC instant carried as a required ISO 8601 string — a value that cannot be parsed as one is rejected with `ERR_INVALID_REQUEST`, a value bearing a numeric UTC offset is normalised to UTC, and a value bearing no zone designator at all is read as already being UTC — to the test-driving clock endpoint; the response answers HTTP 200 with a `data` object holding `current_utc` and nothing else, echoing the instant back in the canonical three-fractional-digit form, and every subsequent request in the service reads the new instant as "now". Whenever this document says a timestamp is *stamped* — `ratified_at`, `deprecated_at`, `ip_executed_at`, `ip_withdrawn_at`, `competency_reviewed_at`, `submitted_at`, `review_started_at`, `certified_at`, `started_at`, `completed_at`, `outcome_recorded_at`, `locked_at`, `published_at` — the value written is the logical clock's current instant. Day arithmetic is exact: "now plus N days" means the current logical instant advanced by N times 86400 seconds, with no calendar or daylight-saving adjustment. The one place where calendar dates rather than instants matter is plugfest date-overlap detection, described in §3.7, which compares UTC calendar dates and deliberately ignores clock times.

### 2.6. Path Resolution and Referential Integrity

No resource in this service is nested inside another resource's URL, but many paths still carry a templated identifier, and several carry a resource identifier followed by an action segment. Templated segments are resolved strictly left to right, and the first segment that fails to resolve decides the response: HTTP 404 carrying the error identifier for that resource family. The path variables in use are `specification_id`, `feature_set_id`, `member_id`, `laboratory_id`, `submission_id`, `test_plan_id`, `test_session_id`, `plugfest_id`, `participation_id`, `listing_id` and `case_id`, and they map to `ERR_SPECIFICATION_NOT_FOUND`, `ERR_FEATURE_SET_NOT_FOUND`, `ERR_MEMBER_NOT_FOUND`, `ERR_LABORATORY_NOT_FOUND`, `ERR_SUBMISSION_NOT_FOUND`, `ERR_TEST_PLAN_NOT_FOUND`, `ERR_TEST_SESSION_NOT_FOUND`, `ERR_PLUGFEST_NOT_FOUND`, `ERR_PARTICIPATION_NOT_FOUND`, `ERR_LISTING_NOT_FOUND` and `ERR_CASE_NOT_FOUND` respectively.

Foreign keys supplied inside a request body are resolved with the same discipline, and the same HTTP 404 error identifiers, immediately after path resolution succeeds. The order of resolution is the order in which the endpoint declares its input fields, so a create request naming two dangling references reports the first one in declaration order and never the second. This body-level resolution applies to feature-set creation, submission creation, test-plan creation, test-session creation, plugfest creation, plugfest-participation creation, listing creation, noncompliance-case creation, and IP-commitment execution.

### 2.7. Money, Ratios and Rounding Discipline

Every monetary amount in this service is an integer number of cents, and every field carrying one says so in its name: `credits_purchased_cents`, `credits_consumed_cents`, `credit_balance_cents`, `escrowed_credit_cents`, `certification_fee_cents`, `fee_escrowed_cents`, `amount_cents`, `assessment_subtotal_cents`, `surcharge_cents` and `penalty_total_cents`. There are no fractional cents anywhere and no floating-point money; sums and differences of these values are exact integer arithmetic.

Where a rate or a percentage enters a money computation, the result is rounded to a whole number of cents using round-half-up. Where a rate or a percentage enters a *score* computation, two rounding steps apply in sequence and their order is normative. First, every intermediate ratio is rounded half-up to four decimal places. Second, each weighted component — a weight multiplied by its already-rounded ratio — is itself rounded half-up to two decimal places. Only then are the rounded components added, and the final score is the exact sum of those rounded components. Rounding once at the end instead of per component produces a different number, and the two answers diverge observably at the one-hundredth of a point; the per-component rule is the one this service implements. Scores are reported with two decimal places.

Two computations round in a way worth naming explicitly. The certification fee applies its tier discount and rounds to whole cents, then applies its review-track multiplier to that already-rounded figure and rounds again — two rounding steps, not one. A test session's reserved bench minutes are obtained by taking the floor of the window duration in whole minutes; because both window bounds are validated to sit exactly on a minute boundary, the floor is exact and never discards anything.

### 2.8. The Validation Ladder

Certification is an evidentiary process, and the error a rejected request carries is itself evidence. Requests are therefore validated in one fixed, strictly ordered ladder, and the **first** rung whose condition is violated decides the response: no later rung is evaluated, and no later rung's error identifier can appear in its place. When a request violates several rules at once, the earlier rung always wins. The rungs, in ascending evaluation order:

1. **Authentication.** Both `X-User-ID` and `X-User-Role` are present and `X-User-Role` is one of the seven declared roles — otherwise `ERR_MISSING_AUTH_HEADERS` (401). Applies to every endpoint except the logical-clock endpoint.
2. **Role authorization.** The acting `X-User-Role` appears in the endpoint's authorized-role list — otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Ownership.** For a `Member` or `TestLaboratory` actor, `X-User-ID` matches the addressed resource's owner as described in §2.1 — otherwise `ERR_UNAUTHORIZED` (403). Applies to the twelve operations enumerated in §2.1, and only to those two actor roles: a `ProgramAdmin` sharing one of those endpoints, such as the credit purchase, is never ownership-checked. Because this rung sits above path existence, an actor addressing an owner identifier that is not its own is refused with `ERR_UNAUTHORIZED` even when that identifier resolves to no stored row at all.
4. **Path existence.** Every templated path segment resolves, left to right, to a stored row — otherwise the matching HTTP 404 not-found identifier from §2.6.
5. **Body reference existence.** Every foreign-key identifier in the request body resolves, in input-declaration order — otherwise the matching HTTP 404 not-found identifier.
6. **Request shape.** Every field the endpoint declares as required is present and of the declared JSON type, and every numeric field lies inside its declared range — otherwise `ERR_INVALID_REQUEST` (400). A required field supplied as JSON null counts as absent and fails here, while an *optional* field supplied as JSON null is treated exactly as though it had been omitted and therefore takes its documented default; a JSON boolean is never accepted where an integer is declared, nor a number where a string is declared; a request body that is absent or empty is read as an empty JSON object, so its missing required fields fail here, whereas a body that is present but is not a JSON object at all is itself rejected here — a rejection that can only arise on an endpoint declaring at least one body field, because an endpoint that declares none never inspects the body and therefore accepts any payload whatever, JSON object or not; and a field the endpoint does not declare is ignored rather than refused. This rung also enforces the conditional requirements: `depends_on_feature_set_id` is required when `obligation` is `CONDITIONAL` and must be null when `obligation` is `MANDATORY` or `OPTIONAL`; `remediation_days` is required when `disposition` is `ORDER_REMEDIATION` and must be absent for every other disposition; `authorized_device_types` must be a non-empty array with no duplicate entries, and, like every other array of code strings in this service, must hold non-empty strings only — with membership of the five device classes then tested at rung 7 rather than here; `result_lines` must be a non-empty array of objects each carrying `feature_set_id`, `outcome` and `evidence_hash`; and `interop_pass_count`, whose declared range is 0 through 8 for either outcome, must be at least 1 when `outcome` is `PASS`.
7. **Enumeration membership.** Every enum-typed input carries one of that field's declared values, compared exactly and case-sensitively — otherwise `ERR_INVALID_ENUM_VALUE` (422). An enum-typed input is a string before it is an enum, so a value that is absent, null or of any other JSON type fails rung 6 with `ERR_INVALID_REQUEST` and never reaches this rung; only a string that is not a declared member is answered with `ERR_INVALID_ENUM_VALUE`. The enum-typed inputs are `device_type`, `obligation`, `tier`, `review_track`, `session_type`, `decision`, `disposition`, `outcome`, `variant`, `category`, `security_baseline_level` and `ip_commitment_type`.
8. **Window bounds.** `window_end` is strictly after `window_start`, and both bounds fall exactly on a minute boundary with zero seconds and zero microseconds — otherwise `ERR_INVALID_WINDOW_BOUNDS` (422). Applies to test-session creation and plugfest creation.
9. **Date ranges.** On specification creation, a supplied `sunset_date` is strictly after `effective_date`; on plugfest creation, `registration_deadline` is at or before `window_start`; on a case advance ordering remediation, `remediation_days` is at least 1 and at most 365 — otherwise `ERR_INVALID_DATE_RANGE` (422).
10. **Credit purchase range.** `amount_cents` is at least 1000 cents and at most 100000000 cents — otherwise `ERR_CREDIT_AMOUNT_OUT_OF_RANGE` (422).
11. **Submission stale-view check.** `expected_submission_version` equals the parent submission's current `version` — otherwise `ERR_STALE_SUBMISSION_VERSION` (412). Applies to test-plan creation.
12. **Listing stale-view check.** `expected_listing_version` equals the target listing's current `version` — otherwise `ERR_STALE_LISTING_VERSION` (412). Applies to firmware-revision reporting.
13. **Specification state.** `ERR_INVALID_SPECIFICATION_STATE` (409) when the target specification's `status` does not permit the operation: ratifying or adding a feature set requires `DRAFT`; submitting a certification submission requires `RATIFIED`; executing an IP commitment requires `RATIFIED` or `DEPRECATED`, whereas creating a plugfest requires `RATIFIED` exactly and refuses a `DEPRECATED` version; naming a non-null `supersedes_specification_id` at creation requires the named version's `status` to be `RATIFIED` or `DEPRECATED`; and the demotion step from `DEPRECATED` to `RETIRED` additionally requires that no submission pinned to the version sits in a live state.
14. **Member state.** `ERR_INVALID_MEMBER_STATE` (409) when the target member's `onboarding_state` does not permit the operation: executing an IP commitment requires `REGISTERED`; a tool-access grant requires `IP_EXECUTED` or `TOOLS_REVOKED`; a tool-access revoke requires `TOOLS_GRANTED`; and a withdrawal requires that the member is not already `IP_WITHDRAWN`.
15. **Laboratory state.** `ERR_INVALID_LABORATORY_STATE` (409) when the target laboratory's `accreditation_status` does not permit the operation: authorizing requires `PROVISIONAL`; suspending requires `AUTHORIZED`; reinstating requires `SUSPENDED`; revoking requires `PROVISIONAL`, `AUTHORIZED` or `SUSPENDED`; and booking or starting a test session, or running a competency review, requires `AUTHORIZED`.
16. **Submission state.** `ERR_INVALID_SUBMISSION_STATE` (409) when the linked submission's `state` or credential posture does not permit the operation: test-plan creation requires `IN_REVIEW`; listing creation requires `REVIEW_COMPLETE` or `CERTIFIED`; listing publication requires the linked submission's `dac_state` to be `ISSUED`; and each of the submission's own lifecycle actions requires the originating state named in §3.8.
17. **Review already decided.** `ERR_REVIEW_ALREADY_DECIDED` (409) when the addressed review axis has already left `PENDING` — a conformance decision or a security decision cannot be recorded twice, and a return-for-info requires `conformance_review_state` to still be `PENDING`.
18. **Test-plan state.** `ERR_INVALID_TEST_PLAN_STATE` (409) when the target plan's `state` does not permit the operation: issuing requires `DRAFT`; starting a session requires the plan to be `ISSUED` or `IN_EXECUTION`; and booking a session requires a plan that is not `VOIDED`.
19. **Session state.** `ERR_INVALID_SESSION_STATE` (409) when the target session's `state` does not permit the operation: starting requires `SCHEDULED`; appending results and completing require `IN_PROGRESS`; disputing a line requires `IN_PROGRESS` or `COMPLETE`; cancelling requires `SCHEDULED` or `IN_PROGRESS`.
20. **Plugfest state.** `ERR_INVALID_PLUGFEST_STATE` (409) when the target event's `state` does not permit the operation: registering a participation and locking require `REGISTRATION_OPEN`; recording an outcome and closing require `LOCKED`.
21. **Participation state.** `ERR_INVALID_PARTICIPATION_STATE` (409) when the target participation has already left `REGISTERED`.
22. **Listing state.** `ERR_INVALID_LISTING_STATE` (409) when the target listing's two status axes do not permit the operation: publication requires `publication_status` to be `UNPUBLISHED` or `SUPPRESSED` and `compliance_status` to be `COMPLIANT` or `REMEDIATED`; withdrawal and firmware-revision reporting require `publication_status` not to be `WITHDRAWN`; opening a noncompliance case requires `compliance_status` to be `COMPLIANT` or `REMEDIATED`.
23. **Case state.** `ERR_INVALID_CASE_STATE` (409) when the target case's `state` does not permit the requested `disposition`: `ESCALATE` requires `OPEN`; `ORDER_REMEDIATION` and `ORDER_WITHDRAWAL` require `EVIDENCE_REVIEW`; `CONFIRM_REMEDIATION` requires `REMEDIATION_ORDERED`; and a close requires `REMEDIATED` or `WITHDRAWAL_ORDERED`.
24. **Segregation of duties.** `ERR_SEGREGATION_OF_DUTIES` (409) — see §2.10.
25. **Member good standing.** `ERR_MEMBER_NOT_IN_GOOD_STANDING` (409) when the acting member's `good_standing` is false. Applies to submitting a submission, registering a plugfest participation, and publishing a listing.
26. **IP scope.** `ERR_IP_COMMITMENT_REQUIRED` (409) when the member's `ip_scope_specification_id` does not equal the submission's pinned `specification_id`. Applies to submitting a submission.
27. **Security baseline declaration.** `ERR_SECURITY_BASELINE_NOT_MET` (422) when the pinned specification's `security_baseline_level` is `SB2` or `SB3` and the corresponding declaration falls short — at submit time, `declared_secure_boot` must be true and `declared_firmware_update_capability` must be `OTA_SIGNED`; at security-decision time, the request's `verified_firmware_update_capability` must be `OTA_SIGNED` under the same condition.
28. **Device attestation.** `ERR_SECURE_BOOT_NOT_VERIFIED` (422) when a security approval carries `secure_boot_verified` false, or when credential issuance is attempted while the stored `secure_boot_verified` is not true or the stored `verified_firmware_update_capability` is `NONE`.
29. **Accreditation currency.** `ERR_ACCREDITATION_EXPIRED` (409) when the laboratory's `accreditation_expires_at` is not strictly after the logical clock's current instant. Applies to accreditation decisions that authorize or reinstate, to booking a test session, and to starting a test session.
30. **Device-class authorization.** `ERR_DEVICE_TYPE_NOT_AUTHORIZED` (422) when the laboratory's `authorized_device_types` does not contain the `device_type` of the session's test plan. Applies to test-session creation.
31. **Feature-code uniqueness.** `ERR_DUPLICATE_FEATURE_CODE` (409) when `feature_code` already exists within the same specification and device class.
32. **Dependency edge validity.** `ERR_FEATURE_DEPENDENCY_CYCLE` (422) when a supplied `depends_on_feature_set_id` names a feature set of a different specification or a different device class, or when adding the edge would close a cycle in that specification-and-device-class dependency graph.
33. **Feature-code resolution.** `ERR_UNKNOWN_FEATURE_CODE` (422) when an entry of `declared_feature_codes` matches no feature set of the pinned specification and the submission's device class, or when an entry of `changed_feature_codes` matches no feature set of the listing's pinned specification and device class.
34. **Cross-reference coherence.** `ERR_DEVICE_TYPE_MISMATCH` (422) when a session's device class disagrees with its test plan's `device_type`, when a participation's submission is pinned to a different `specification_id` than the plugfest's, or when an operator supplies `category` `IP_WITHDRAWAL` on a noncompliance case, which only the system may open.
35. **Credential serial uniqueness.** `ERR_DUPLICATE_DAC_SERIAL` (409) when the `dac_serial` supplied at issuance is already held by another submission.
36. **One listing per submission.** `ERR_LISTING_ALREADY_EXISTS` (409) when the submission already has a listing.
37. **Result-line addressing.** `ERR_UNKNOWN_RESULT_FEATURE_SET` (422) when a result line's `feature_set_id` is not among the enclosing session's plan's `included_feature_set_ids`, or when a supplied `line_index` addresses no existing entry of `result_lines`.
38. **Bench occupancy.** `ERR_BENCH_WINDOW_CONFLICT` (409) — see §3.6.
39. **Plugfest date overlap.** `ERR_PARTICIPATION_WINDOW_CONFLICT` (409) — see §3.7.
40. **Duplicate registration.** `ERR_DUPLICATE_PARTICIPATION` (409) when the same submission is already registered for the same plugfest.
41. **Registration deadline.** `ERR_REGISTRATION_CLOSED` (409) when the logical clock's current instant is after the plugfest's `registration_deadline`.
42. **Vendor quorum.** `ERR_INSUFFICIENT_DISTINCT_VENDORS` (409) when `distinct_vendor_count` is below `min_distinct_vendors` at lock time.
43. **Coverage completeness.** `ERR_MANDATORY_COVERAGE_INCOMPLETE` (409), required in four contexts: a conformance decision requires the submission's non-`VOIDED` test plan to exist, to be `COMPLETE`, and to have every `MANDATORY` or `CONDITIONAL` feature set of `included_feature_set_ids` covered by at least one result line; issuing a plan requires its `required_case_count` to be at least 1; completing a session requires its `result_lines` to be non-empty; and ratifying a specification requires `feature_set_count` to be at least 1 and requires that, for every device class appearing among the specification's feature sets, at least one of that class's feature sets has `obligation` `MANDATORY`.
44. **Plugfest credits.** `ERR_INSUFFICIENT_PLUGFEST_CREDITS` (409) when `plugfest_credit_count` is below the pinned specification's `min_plugfest_credits` at a conformance approval.
45. **Readiness threshold.** `ERR_READINESS_BELOW_THRESHOLD` (409) when the freshly computed final readiness score is strictly below 65.00 at a conformance approval.
46. **Revision rounds.** `ERR_REVISION_LIMIT_EXCEEDED` (409) when `revision_round` has already reached 2 at a return-for-info.
47. **Reviewable history.** `ERR_NO_COMPLETED_SESSIONS` (409) when the requested competency variant's counted set contains no `COMPLETE` session.
48. **Remediation deadline.** `ERR_REMEDIATION_DEADLINE_PASSED` (409) when remediation is confirmed after the case's `remediation_deadline_at`.
49. **Bench capacity.** `ERR_LAB_CAPACITY_EXCEEDED` (409) — see §3.6.
50. **Certification credit.** `ERR_INSUFFICIENT_CREDIT` (402) when the member's `credit_balance_cents` is below the submission's pinned `certification_fee_cents` at the first submit.
51. **Collection-wide name uniqueness.** `ERR_DUPLICATE_NAME` (409) when an input-supplied scalar declared unique across its whole collection repeats a stored value: a specification's `version_label`, a member's `legal_name`, or a laboratory's `name`. Comparison is exact and case-sensitive.

Two adjacent pairs on this ladder deserve to be called out because they are the ones an implementation most often gets backwards.

**The compliance-over-money pair.** Rung 25 sits far above rung 50. A submit request from a member who has both lost good standing *and* lacks the credit to cover the pinned fee is rejected with `ERR_MEMBER_NOT_IN_GOOD_STANDING` and HTTP 409 — never with `ERR_INSUFFICIENT_CREDIT`. Compliance standing outranks the balance sheet.

**The conflict-over-capacity pair.** Rung 38 sits above rung 49. A session booking that both collides with an existing booking on the same bench *and* would push the laboratory past its capacity ceiling is rejected with `ERR_BENCH_WINDOW_CONFLICT` — never with `ERR_LAB_CAPACITY_EXCEEDED`. A booking that cannot be honoured is refused before its minutes are ever weighed against the ceiling.

Note also where `ERR_DUPLICATE_NAME` sits: dead last, deliberately. Every shape, enum, range, state and referential rule is evaluated before it, so a request that is simultaneously malformed and a duplicate reports the malformation. The three narrower uniqueness rules keep their own identifiers and their own, much higher, rungs — `ERR_DUPLICATE_FEATURE_CODE` at 31, `ERR_DUPLICATE_DAC_SERIAL` at 35 and `ERR_DUPLICATE_PARTICIPATION` at 40.

### 2.9. Stale-View Protection on Superseding Writes

Exactly two write operations in this service legitimately *overwrite* work a client may not have seen, and both are guarded by an optimistic-concurrency check against the parent resource's `version` counter. On these two endpoints the version field is a required, non-optional input; no other endpoint in the service accepts a version field of any kind, and none applies a concurrency check.

**Test-plan creation.** `POST /test-plans` requires `expected_submission_version`, carrying the client's last observed `version` of the target `CertificationSubmission`. If that value does not equal the submission's current `version`, the request is rejected with `ERR_STALE_SUBMISSION_VERSION` and HTTP 412. This guard exists because plan creation is intentionally *permitted* to supersede the submission's existing non-`VOIDED` plan, voiding it and cancelling its scheduled sessions; the submission is still `IN_REVIEW`, so no state precondition would stop a second create. The stale-view check is what makes a supersede deliberate rather than accidental: a client that has not observed the current submission cannot destroy a plan it never saw.

**Firmware-revision reporting.** `POST /listings/{listing_id}/firmware-revisions` requires `expected_listing_version`, carrying the client's last observed `version` of the target `CertificationListing`. If that value does not equal the listing's current `version`, the request is rejected with `ERR_STALE_LISTING_VERSION` and HTTP 412. Again the operation is legitimate on its face — the listing is still `PUBLISHED` and each report is entitled to replace the previous report's `recert_classification`, `recert_trigger_reason` and `recertification_due_at` — so only the version check prevents a client from overwriting a classification it never observed.

Because §2.4 counts every computed-field refresh as a mutation, a client's cached `version` can go stale without the client ever issuing a write of its own. A member who reads a listing, then has that listing's `declared_features` refreshed by an operator's publication, must re-read the listing before reporting a firmware revision.

### 2.10. Segregation of Duties

Two decisions in this programme must be made by two different people, and in both cases the rule is enforced on `X-User-ID` rather than on `X-User-Role` — two `ConformanceReviewer` operators are two different people, and one `SecurityReviewer` who also signed the conformity declaration is one person wearing two hats.

The first rule protects the two-track review: the `X-User-ID` stored in a submission's `conformance_reviewer_user_id` may not record that submission's security decision. Note that `conformance_reviewer_user_id` is written both by a conformance decision and by a return-for-info, so an operator who merely returned a submission for more information has already disqualified themselves from its security decision.

The second rule protects investigations: the `X-User-ID` stored in a case's `opened_by_user_id` may not close that case, and `closed_by_user_id` therefore always differs from `opened_by_user_id`. A case auto-opened by the system carries the literal `SYSTEM` in `opened_by_user_id`, which no operator identifier can match, so an auto-opened case is closable by any `ComplianceOfficer`.

Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` and HTTP 409, and because that check sits at rung 24 of §2.8's ladder it is evaluated *before* the security-baseline and device-attestation checks that follow it — a disqualified reviewer is turned away on identity grounds even when their findings would also have failed on substance.

### 2.11. Cascades, Fan-Outs and Compensating Adjustments

Several operations in this service reach well beyond the row they address. Two patterns recur, and this specification distinguishes them because they behave differently under partial conditions.

A **cascade** is a chain of hops in which each hop is caused by the hop before it. Deprecating a specification returns its live submissions (hop 1), which voids those submissions' test plans (hop 2), which cancels those plans' live sessions and releases the laboratory minutes they held (hop 3). Withdrawing an IP commitment recomputes the member out of good standing (hop 1), which suppresses that member's published listings and puts them under investigation (hop 2), which revokes the attestation credentials of the submissions behind those listings (hop 3), which auto-opens one noncompliance case per affected listing (hop 4). A hop that finds nothing to act on ends the chain quietly; it is not an error.

A **fan-out** is a set of effects triggered directly by the originating operation and independent of the cascade chain. Deprecating a specification also gives every published listing of that specification a recertification deadline — an effect that fires whether or not any submission was in a returnable state. Revoking a laboratory's accreditation also cancels the plugfests that laboratory hosts and marks their still-registered participations as no-shows, independently of what happened to that laboratory's test sessions.

A **compensating adjustment** restores an accumulator to exactly the value it held before the compensated event, with no drift after any number of cycles. Escrow is compensating: the cents a submission escrows at submit are returned to `credit_balance_cents` in full on rejection or withdrawal, or moved in full into `credits_consumed_cents` at credential issuance, and in every one of those three outcomes `fee_escrowed_cents` returns to 0. Bench minutes are compensating: a session's `reserved_minutes` are added to its laboratory's `reserved_bench_minutes` at booking and removed in full when the session completes, is cancelled directly, or is cancelled by any cascade — so a book-then-cancel pair restores the previous total exactly.

Every row a cascade, fan-out or compensating adjustment touches has its `updated_at` refreshed and its `version` incremented, exactly as if it had been written directly. A single deprecation request can therefore bump the `version` of one specification, several submissions, several test plans, several sessions, several laboratories and several listings.

## 3. Business Logic & Workflows

### 3.1. Specification Versions and the Device Feature Graph

Everything in this programme hangs off a **specification version**. A `ProgramAdmin` opens one by supplying a `version_label` such as `1.0` — between 1 and 32 characters, and unique across every specification version ever created, with a repeat rejected as `ERR_DUPLICATE_NAME` — together with the `security_baseline_level` the version mandates, one of `SB1`, `SB2` or `SB3`, and an `effective_date`, the ISO 8601 UTC instant from which the version may be cited by a certification submission. Three inputs are optional. A `sunset_date` records the instant after which the version is scheduled for retirement and defaults to null when unscheduled; when supplied it must be strictly after `effective_date`, and otherwise the create is rejected with `ERR_INVALID_DATE_RANGE`. A `supersedes_specification_id` names the version this one replaces and defaults to null for the first version in a chain; when supplied, the named version's `status` must already be `RATIFIED` or `DEPRECATED`, because a `DRAFT` version cannot be superseded before it has been ratified, and a violation is rejected with `ERR_INVALID_SPECIFICATION_STATE`. Specification creation is not one of the operations that resolve body-level foreign keys under §2.6, so a `supersedes_specification_id` that resolves to no stored specification at all is not reported as a 404 either: it fails this same status requirement and is likewise rejected with `ERR_INVALID_SPECIFICATION_STATE`. Finally `min_plugfest_credits`, which defaults to 0 and must be at least 0 and at most 4, records how many passed plugfest credits a submission pinned to this version must hold before its conformity declaration can be approved. A new version is stored with `status` `DRAFT`, `feature_set_count` 0, and both `ratified_at` and `deprecated_at` null. Because `supersedes_specification_id` points at another specification version, the supersession chain is self-referential, and the reverse direction — "which versions replace this one" — is reachable through the specification list filter of the same name.

Into a `DRAFT` version the `ProgramAdmin` writes **feature sets**, one row per feature per device class. A feature set names its `specification_id`, which must still be `DRAFT` at the moment the feature set is added, and a `device_type` drawn from `LIGHTING`, `THERMOSTAT`, `LOCK`, `SENSOR` and `HUB`. Its `feature_code` — a stable machine-readable identifier such as `CORE_ONOFF`, between 1 and 48 characters and composed of uppercase letters, digits and underscores, a code carrying any other character being a shape failure that yields `ERR_INVALID_REQUEST` — must be unique within its own `specification_id` and `device_type` pair; the same code may therefore legitimately appear on a lighting feature set and on a thermostat feature set of the same version, but a repeat within one pair is rejected with `ERR_DUPLICATE_FEATURE_CODE`. Each feature set declares a `test_case_count`, at least 1 and at most 500, being the number of test cases it contributes to a test plan, and a `security_relevant` flag that defaults to false and is set true when the feature set covers device attestation, secure boot or firmware update behaviour.

The `obligation` field is where the feature graph earns its complexity, and its three values behave very differently. A `MANDATORY` feature set is always in scope for its device class, whether or not any vendor mentions it. An `OPTIONAL` feature set is in scope only when a submission explicitly declares its `feature_code`. A `CONDITIONAL` feature set is in scope only when the feature set it depends on is itself in scope — and once it is in scope it is treated exactly like a `MANDATORY` one for the purpose of pass requirements. That dependency is carried by `depends_on_feature_set_id`, which is required when `obligation` is `CONDITIONAL` and must be null when `obligation` is `MANDATORY` or `OPTIONAL`. The target must share this row's `specification_id` and its `device_type`, and the resulting dependency graph — one graph per specification-and-device-class pair — must remain acyclic; a cross-specification target, a cross-device-class target, or an edge that would close a cycle is rejected with `ERR_FEATURE_DEPENDENCY_CYCLE`. Because a feature set's dependency edge is fixed at creation and no stored row is ever re-pointed at a newer one, the acyclicity requirement is in practice vacuous — nothing yet depends on the row being added, so no accepted create can close a cycle — and `ERR_FEATURE_DEPENDENCY_CYCLE` is in fact only ever reached by a cross-specification or cross-device-class target. A target identifier that resolves to nothing at all is instead an existence failure and yields `ERR_FEATURE_SET_NOT_FOUND`; and because body references are resolved at rung 5, that 404 also outranks the rung-6 requirement that the field be null, so a `MANDATORY` or `OPTIONAL` feature set submitted with a dangling `depends_on_feature_set_id` is answered with `ERR_FEATURE_SET_NOT_FOUND` rather than `ERR_INVALID_REQUEST`. Each accepted feature set increments its owning version's `feature_set_count`, which counts every feature set of that version across all device classes and all obligations.

Ratification is what turns a draft into a citable standard, and it is available to the `ProgramAdmin` only. A version moves `DRAFT → RATIFIED` when it has at least one feature set and when, for every device class that appears at all among its feature sets, at least one of that class's feature sets carries `obligation` `MANDATORY` — a version that describes only optional lighting behaviour has no baseline and cannot be ratified, and either shortfall is reported as `ERR_MANDATORY_COVERAGE_INCOMPLETE`. Ratification stamps `ratified_at` with the logical clock's current instant and freezes the feature-set population permanently: from that moment every attempt to add a feature set to the version is refused with `ERR_INVALID_SPECIFICATION_STATE`. Attempting to ratify a version that is not `DRAFT` draws the same specification-state error.

Demotion runs in two steps, and the same operator action drives both — the step taken depends on the version's current `status`. From `RATIFIED` the version moves to `DEPRECATED`, stamping `deprecated_at`. From `DEPRECATED` it moves to `RETIRED`, which is terminal, and only when no submission pinned to the version sits in any of the live states `DRAFT`, `SUBMITTED`, `IN_REVIEW`, `RETURNED_FOR_INFO` or `REVIEW_COMPLETE`; a still-live submission blocks retirement with `ERR_INVALID_SPECIFICATION_STATE`. Demoting a version that is `DRAFT` or already `RETIRED` draws the same error.

The `RATIFIED → DEPRECATED` step is the single most consequential write in the service, because a deprecated baseline invalidates work in flight. Its cascade runs in three hops. **Hop one** takes every submission pinned to this version whose `state` is `SUBMITTED`, `IN_REVIEW` or `RETURNED_FOR_INFO` and sets `conformance_review_state` to `RETURNED`, `state` to `RETURNED_FOR_INFO`, and `conformance_reviewer_user_id` to the literal `SYSTEM`; each such submission's `revision_round` is raised by one but never past the ceiling of 2, so a submission already at 2 stays at 2 rather than overflowing. **Hop two**, caused by hop one rather than by the demotion itself, takes every test plan belonging to a submission that hop one touched and whose `state` is `DRAFT`, `ISSUED`, `IN_EXECUTION` or `COMPLETE`, and sets `state` to `VOIDED` with `voided_reason` `SPECIFICATION_DEPRECATED`. **Hop three**, caused by hop two, takes every test session of a plan voided in hop two whose `state` is `SCHEDULED` or `IN_PROGRESS`, sets `state` to `CANCELLED`, and decrements the owning laboratory's `reserved_bench_minutes` by exactly that session's `reserved_minutes`. Alongside that chain, and independent of it, a **fan-out** gives every certification listing whose submission is pinned to this version and whose `publication_status` is `PUBLISHED` a `recertification_due_at` of the logical clock's current instant advanced by 180 days, with `recert_trigger_reason` set to `SPECIFICATION_DEPRECATED`. Every row touched by any hop or by the fan-out has its `updated_at` refreshed and its `version` incremented.

### 3.2. Member Onboarding, IP Commitments and Programme Credit

A device vendor joins the programme as a **member**. The `ProgramAdmin` registers one with a `legal_name` — the registered legal name of the company, between 1 and 120 characters and unique across all members, with a repeat rejected as `ERR_DUPLICATE_NAME` — a `contact_email` for programme correspondence, a required string of between 1 and 254 characters whose contents are never inspected for address syntax, and a `tier` of `ADOPTER`, `PARTICIPANT` or `PROMOTER`, which drives the certification fee discount described later in this section. A fresh member sits in `onboarding_state` `REGISTERED` with `ip_commitment_type` null, `essential_patent_count` 0, `ip_scope_specification_id` null, `ip_executed_at` and `ip_withdrawn_at` both null, `credits_purchased_cents` and `credits_consumed_cents` and `credit_balance_cents` and `escrowed_credit_cents` all 0, `good_standing` false, and `open_case_count` 0.

Onboarding proceeds in two acts. First the member executes its **intellectual-property commitment**, an action reserved to the `Member` role acting on its own record: it supplies an `ip_commitment_type` of either `RAND_ROYALTY_FREE` or `RAND_ROYALTY_BEARING`, an `essential_patent_count` recording how many essential patents it disclosed alongside the commitment, required and at least 0 with no upper bound, and a `scope_specification_id` naming the specification version the commitment covers, which must have `status` `RATIFIED` or `DEPRECATED`. The commitment moves `onboarding_state` from `REGISTERED` to `IP_EXECUTED`, copies the three supplied values onto `ip_commitment_type`, `essential_patent_count` and `ip_scope_specification_id`, and stamps `ip_executed_at`. A member that has already executed a commitment cannot execute a second one; the attempt is rejected with `ERR_INVALID_MEMBER_STATE`. Good standing is recomputed at this point and remains false, because tool access has not yet been granted.

Second, the `ProgramAdmin` moves **testing-tool entitlement** by supplying a `decision` of either `GRANT` or `REVOKE`. A grant moves `IP_EXECUTED → TOOLS_GRANTED`, and good standing becomes true. A revoke moves `TOOLS_GRANTED → TOOLS_REVOKED`, and good standing becomes false. A further grant moves `TOOLS_REVOKED → TOOLS_GRANTED` and restores good standing — this pair is cyclic and may repeat without bound, since a member whose tooling was pulled for a paperwork lapse can be reinstated as often as necessary. A grant attempted from any state other than `IP_EXECUTED` or `TOOLS_REVOKED`, or a revoke attempted from any state other than `TOOLS_GRANTED`, is rejected with `ERR_INVALID_MEMBER_STATE`.

**Good standing** is the gate that fronts three separate operations, and it is computed, never supplied. `good_standing` is true exactly when `onboarding_state` is `TOOLS_GRANTED`, `ip_commitment_type` is not null, and `ip_withdrawn_at` is null; if any one of those three fails, it is false. The member's `open_case_count` is reported for operators but does not gate good standing: it counts the noncompliance cases whose `state` is `OPEN`, `EVIDENCE_REVIEW`, `REMEDIATION_ORDERED` or `WITHDRAWAL_ORDERED` and whose `listing_id` resolves to a listing whose `member_id` is this member, and a member with three open investigations is still in good standing so long as its tooling and its commitment are intact. Where good standing is required and absent — submitting a certification submission, registering a plugfest participation, or publishing a listing — the request is rejected with `ERR_MEMBER_NOT_IN_GOOD_STANDING`.

Withdrawal of the IP commitment is terminal for onboarding and is the most destructive action a member can take on itself. It is available from `IP_EXECUTED`, from `TOOLS_GRANTED` and from `TOOLS_REVOKED`, always landing on `IP_WITHDRAWN`, and it stamps `ip_withdrawn_at`. Attempting it on a member that is already `IP_WITHDRAWN` draws `ERR_INVALID_MEMBER_STATE`. The transition body is identical from all three origins, including its full four-hop cascade. **Hop one** recomputes `good_standing` to false. **Hop two**, caused by that loss of standing, takes every listing of this member whose `publication_status` is `PUBLISHED` and sets `publication_status` to `SUPPRESSED` and `compliance_status` to `UNDER_INVESTIGATION`. **Hop three**, caused by the suppression, takes every submission behind a listing suppressed in hop two whose `dac_state` is `ISSUED` and sets `dac_state` to `REVOKED`. **Hop four**, caused by that credential revocation, creates one noncompliance case per listing whose submission lost its credential in hop three, with `category` `IP_WITHDRAWAL`, `state` `OPEN`, `auto_opened` true, `opened_by_user_id` the literal `SYSTEM`, `claimed_impact_units` 0, `evidence_summary` set to the fixed text `Auto-opened: IP commitment withdrawn by member`, and its three penalty amounts computed exactly as for an operator-filed case. Every row the cascade touches has its `updated_at` refreshed and its `version` incremented.

Certification is paid for out of a **credit account**, and the account is a strict three-way ledger. Credit is purchased either by the `ProgramAdmin` or by the member itself, by supplying `amount_cents`; a purchase must be at least 1000 cents and at most 100000000 cents, and anything outside that band is rejected with `ERR_CREDIT_AMOUNT_OUT_OF_RANGE`. An accepted purchase increases `credits_purchased_cents`, which is monotonically non-decreasing and never reduced by anything, and it answers with the updated `Member` row — not with a ledger view — its `credit_balance_cents`, `escrowed_credit_cents`, `good_standing` and `open_case_count` already recomputed. `credits_consumed_cents` is likewise monotonically non-decreasing and records credit irrevocably spent on device attestation credential issuance. Between those two sits escrow: `escrowed_credit_cents` is the total of `fee_escrowed_cents` across every submission belonging to the member, and `credit_balance_cents` — the spendable, unescrowed figure — is `credits_purchased_cents` reduced by `credits_consumed_cents` and reduced again by `escrowed_credit_cents`. The invariant that must hold after every single write, with no drift ever, is that `credits_purchased_cents` equals `credit_balance_cents` plus `credits_consumed_cents` plus `escrowed_credit_cents`.

A submission's `fee_escrowed_cents` is non-zero exactly while its `state` is `SUBMITTED`, `IN_REVIEW`, `RETURNED_FOR_INFO` or `REVIEW_COMPLETE`: no ledger event fires on the `IN_REVIEW → REVIEW_COMPLETE` bubble-up, so the escrow is carried across it unchanged, which is what lets §3.8's issuance precondition — `fee_escrowed_cents` equal to `certification_fee_cents` — still be satisfiable at issuance. A `DRAFT` submission contributes 0 because it has never escrowed; a `CERTIFIED` submission contributes 0 because its escrow was consumed into `credits_consumed_cents`; a `REJECTED` or `WITHDRAWN` submission contributes 0 because its escrow was released back into `credit_balance_cents`. The ledger is recomputed on every write that moves credit — a purchase, an escrow at first submit, an escrow release on rejection or withdrawal, and an escrow consumption at credential issuance — and it is readable without writing anything through the member credit-ledger read, which returns `member_id`, the `variant` that was evaluated, `credits_purchased_cents`, `credits_consumed_cents`, `escrowed_credit_cents` and a `balance_cents` figure.

That read has two variants, and they differ on identical stored data. The `AVAILABLE` variant is the default when `variant` is omitted; it is the figure persisted on `credit_balance_cents`, and it is the figure the first submit compares against the pinned fee, because money committed to an in-flight submission is not spendable. The `COMMITTED` variant, requested explicitly, is the finance view of everything the member still owns including money held in escrow: it does *not* subtract `escrowed_credit_cents`, so its `balance_cents` is simply `credits_purchased_cents` reduced by `credits_consumed_cents`. For a member with exactly one escrowed submission the two variants differ by precisely that submission's `fee_escrowed_cents`.

### 3.3. The Authorized Laboratory Network

Testing happens at **authorized test laboratories**, and the programme keeps a tight grip on which of them may work on what. A `ProgramAdmin` registers a laboratory with a `name` — its trading name, between 1 and 120 characters and unique across all laboratories, with a repeat rejected as `ERR_DUPLICATE_NAME` — a `bench_capacity` between 1 and 32 giving the number of independently bookable test benches, an `authorized_device_types` array listing the device classes the laboratory may test, and an `accreditation_expires_at` instant at which its accreditation lapses. The `authorized_device_types` array must be non-empty, must contain no duplicates, and must be a subset of `LIGHTING`, `THERMOSTAT`, `LOCK`, `SENSOR` and `HUB`; an empty or duplicate-bearing array is a shape failure and yields `ERR_INVALID_REQUEST`, whereas an entry that is a non-empty string outside those five values is an enumeration failure and yields `ERR_INVALID_ENUM_VALUE`, entries being checked in the order supplied. `accreditation_expires_at` is required but is not itself compared to the logical clock at registration, so a laboratory may legitimately be registered already lapsed; the currency check bites only on the accreditation decisions that authorize or reinstate and on booking or starting a session. A newly registered laboratory sits in `accreditation_status` `PROVISIONAL` with `reserved_bench_minutes` 0 and with `competency_score`, `competency_variant` and `competency_reviewed_at` all null, because no competency review has yet been run against it.

Accreditation moves on an operator's `decision`, one of `AUTHORIZE`, `SUSPEND`, `REINSTATE` or `REVOKE`. `AUTHORIZE` takes a `PROVISIONAL` laboratory to `AUTHORIZED`. `SUSPEND` takes an `AUTHORIZED` laboratory to `SUSPENDED`, and it deliberately leaves that laboratory's test sessions exactly where they are — nothing is cancelled — but no session may be started while the laboratory is suspended. `REINSTATE` takes a `SUSPENDED` laboratory back to `AUTHORIZED`, and this pair is cyclic: a laboratory may walk `AUTHORIZED → SUSPENDED → AUTHORIZED` any number of times. Both `AUTHORIZE` and `REINSTATE` additionally require that `accreditation_expires_at` is strictly after the logical clock's current instant, and a lapsed accreditation blocks either with `ERR_ACCREDITATION_EXPIRED`; a decision attempted from a status the transition table does not permit is instead rejected with `ERR_INVALID_LABORATORY_STATE`.

`REVOKE` is terminal and is accepted from `PROVISIONAL`, from `AUTHORIZED` and from `SUSPENDED`, with an identical body from all three. Its **hop one** takes every session of this laboratory whose `state` is `SCHEDULED` or `IN_PROGRESS` and sets `state` to `CANCELLED`, and then sets the laboratory's `reserved_bench_minutes` to 0 outright, since nothing remains booked. **Hop two**, caused by those cancellations, takes every test plan that lost at least one session in hop one, whose `state` is `IN_EXECUTION`, and which now retains no session in `SCHEDULED`, `IN_PROGRESS` or `COMPLETE`, and sets `state` to `VOIDED` with `voided_reason` `SPECIFICATION_DEPRECATED`; a plan that still holds a completed session survives, because its evidence survives. Separately, and independently of that chain, a **fan-out** takes every plugfest this laboratory hosts whose `state` is `REGISTRATION_OPEN` or `LOCKED` and sets `state` to `CANCELLED`, and then takes every participation of those cancelled events whose `state` is `REGISTERED` and sets `state` to `NO_SHOW`; each cancelled event's `distinct_vendor_count` is then recomputed and consequently falls, since a `NO_SHOW` participation no longer counts as a present vendor.

Laboratory quality is measured by a **competency score** on a 100-point scale, and it is measured in two ways that can disagree sharply. The score has two components. Punctuality is worth 60 points and is driven by the share of the laboratory's counted sessions that finished on time — that is, sessions whose `completed_late` is false — divided by the number of counted sessions. Dispute-freedom is worth the remaining 40 points and is driven by the counted result lines that were never challenged: take the total number of `result_lines` entries across the counted sessions, subtract the total of their `disputed_line_count` values, and divide by that same total number of lines. Each ratio is rounded half-up to four decimal places; if the counted sessions carry no result lines at all, the dispute-free ratio is taken as exactly 1.0000 rather than being undefined. Each of the two weighted components is then rounded half-up to two decimal places, and the score is the exact sum of those two rounded components.

Only sessions of the laboratory whose `state` is `COMPLETE` are ever counted. `SCHEDULED`, `IN_PROGRESS` and `CANCELLED` sessions are invisible to the calculation in both variants, which has a real consequence: cancelling a session that finished late would have erased its punctuality damage, had it not already completed. Sessions belonging to test plans that were later voided still count, provided the session itself reached `COMPLETE` — the evidence was produced and the laboratory is answerable for it. The two variants differ only in the window they look through. `ROLLING_90D` counts only sessions whose `completed_at` is at or after the logical clock's current instant reduced by 90 days, and the lower bound is inclusive, so a session completed at exactly ninety days ago is counted. `LIFETIME` counts every `COMPLETE` session the laboratory has ever produced. Because old clean history dilutes recent misconduct, `LIFETIME` is typically the higher of the two, and the same stored data can quite legitimately land the two variants on opposite sides of the suspension threshold.

A `ProgramAdmin` runs a review by naming the `variant` in the request body, where it is a required field with no default, an omitted `variant` being a shape failure rejected with `ERR_INVALID_REQUEST`; and the review both writes and may punish. It writes `competency_score`, which is stored and echoed on the laboratory row as a plain JSON number, records which `competency_variant` produced it, and stamps `competency_reviewed_at`. If the requested variant's counted set contains no `COMPLETE` session at all, no score is written and the review is refused with `ERR_NO_COMPLETED_SESSIONS`. And if the freshly computed score is *strictly* less than 70.00 while the laboratory is `AUTHORIZED`, the system itself drives `AUTHORIZED → SUSPENDED` as part of the same request; a score of exactly 70.00 leaves the laboratory `AUTHORIZED`. The same two-variant computation is available as a pure read that writes nothing, exposing its inputs so the divergence is auditable: it returns `laboratory_id`, the `variant` evaluated, `counted_session_count`, `counted_line_count`, `disputed_line_count`, `on_time_ratio`, `dispute_free_ratio` and `competency_score`. The three decimal figures of that read are rendered as JSON *strings* — each ratio at exactly four decimal places and the score at exactly two — which is the one place the read's shape departs from the laboratory row, where `competency_score` is a number; the three counts are plain integers. That read defaults to `ROLLING_90D` when `variant` is omitted, and unlike the review it neither requires an `AUTHORIZED` laboratory nor refuses an empty counted set: with no counted session it simply reports zero counts, an `on_time_ratio` of `0.0000`, a vacuous `dispute_free_ratio` of `1.0000` and a score of `40.00`.

Finally, every laboratory carries a live occupancy figure. `reserved_bench_minutes` is defined as the sum of `reserved_minutes` over the laboratory's sessions whose `state` is `SCHEDULED` or `IN_PROGRESS`, and that definition is normative: after any number of book, start, complete, cancel and cascade-cancel cycles, the stored aggregate must equal that sum exactly, with no accumulated drift. Completing a session and cancelling a session each remove exactly the session's `reserved_minutes`, so a laboratory that has finished all its work sits back at 0 no matter how much it ever booked. The aggregate is incremented at booking, decremented on completion, decremented on cancellation whether that cancellation was direct or a cascade, and zeroed outright by an accreditation revocation.

### 3.4. Opening a Certification Submission and Pinning its Fee

A **certification submission** is the unit of certification: one device model, one device class, one specification version. A `Member` opens one against its own record — the `member_id` in the payload must match the acting `X-User-ID`, a mismatch being refused with `ERR_UNAUTHORIZED` at rung 3 even when the named identifier resolves to no stored member, while a `member_id` that is absent, null, or present but not a string is left to rung 6 rather than treated as an ownership failure — naming the `specification_id` to certify against, a `device_model` designation of between 1 and 80 characters, and the `device_type` under certification. The two body foreign keys resolve in that declaration order, `member_id` before `specification_id`, so a create naming two dangling references reports `ERR_MEMBER_NOT_FOUND` and never `ERR_SPECIFICATION_NOT_FOUND`. Three security self-declarations accompany it: `declared_secure_boot`, the vendor's assertion that the device enforces verified secure boot; `declared_firmware_update_capability`, one of `OTA_SIGNED`, `OTA_UNSIGNED` or `NONE`; and `attestation_key_fingerprint`, between 1 and 64 characters, the fingerprint of the device attestation key the vendor will burn into the device. An optional `review_track` selects `STANDARD` or `EXPEDITED` and defaults to `STANDARD`.

The remaining input, `declared_feature_codes`, is the vendor's consumer-facing feature declaration: every `feature_code` the device claims, including the mandatory baseline codes. The array may be empty but must contain no duplicates, and every entry must resolve to a feature set of the pinned specification whose `device_type` equals the submission's own — a code belonging to another device class, or to no feature set at all, is rejected with `ERR_UNKNOWN_FEATURE_CODE`. Beyond that resolution requirement the obligation of the named feature sets is unconstrained, and the array has two entirely independent consequences that are easy to conflate. Each entry adds to the certification fee. And separately, entries whose feature set carries `obligation` `OPTIONAL` are the *only* mechanism by which an optional feature set enters a test plan's scope. Mandatory feature sets are seeded into the plan whether or not they were declared, so declaring a mandatory code raises the fee and changes nothing about the plan.

The **certification fee** is computed once, at creation, and pinned onto `certification_fee_cents`; it is never recomputed, so a member that later climbs from `PARTICIPANT` to `PROMOTER`, or a specification that is later amended, does not move an already-pinned fee. It draws on exactly four stored inputs and nothing else — the submission's own `device_type`, `declared_feature_codes` and `review_track`, plus the owning member's `tier`, plus the pinned specification's `security_baseline_level`. No test plan, test session or plugfest data participates.

The computation runs as a subtotal followed by two rounding steps, and the step order is normative. The subtotal is the base fee for the device class, plus 15000 cents — one hundred and fifty dollars — for each entry in `declared_feature_codes`, plus the surcharge for the specification's security baseline. The base fee is 100000 cents for a `SENSOR`, 120000 cents for `LIGHTING`, 180000 cents for a `THERMOSTAT`, 240000 cents for a `LOCK` and 300000 cents for a `HUB` — a hub costs three times what a sensor costs, reflecting the breadth of its interoperability surface. The security-baseline surcharge is nothing at `SB1`, 50000 cents at `SB2` and 125000 cents at `SB3`. In the first step, the tier discount is applied to that subtotal and the result rounded half-up to a whole number of cents: an `ADOPTER` receives no discount, a `PARTICIPANT` receives ten percent off, and a `PROMOTER` receives a quarter off. In the second step, the review-track multiplier is applied to the *already-rounded* result of the first step and rounded half-up to whole cents again: `STANDARD` multiplies by one and therefore leaves the figure untouched, while `EXPEDITED` multiplies it by 1.40, a forty-percent surcharge for jumping the queue. Discounting and multiplying with a rounding step between them is not the same arithmetic as folding the discount and the multiplier into a single factor; across the matrix of five device classes, three tiers, two tracks and three baselines there are cells where the two approaches differ by one cent, and the two-step form is the correct one.

A newly created submission sits in `state` `DRAFT` with all three review axes at their initial positions — `conformance_review_state` `PENDING`, `security_review_state` `PENDING`, `dac_state` `NOT_ISSUED` — and with `dac_serial`, `secure_boot_verified`, `verified_firmware_update_capability`, `conformance_reviewer_user_id`, `security_reviewer_user_id`, `provisional_readiness_score`, `final_readiness_score`, `submitted_at`, `review_started_at` and `certified_at` all null, and with `revision_round`, `fee_escrowed_cents` and `plugfest_credit_count` all 0.

Submitting is where the money and the compliance gates bite, and it is reachable from two states. From `DRAFT` it requires that the pinned specification's `status` is `RATIFIED`, that the member's `good_standing` is true, that the member's `ip_scope_specification_id` equals the submission's pinned `specification_id` — otherwise `ERR_IP_COMMITMENT_REQUIRED` — that when the specification's `security_baseline_level` is `SB2` or `SB3` the submission's `declared_secure_boot` is true and its `declared_firmware_update_capability` is `OTA_SIGNED`, and finally that the member's `credit_balance_cents` is at least the pinned `certification_fee_cents`. On success `state` becomes `SUBMITTED`, `submitted_at` is stamped, and the fee is escrowed: the member's `credit_balance_cents` falls by `certification_fee_cents`, the member's `escrowed_credit_cents` rises by the same amount, and the submission's `fee_escrowed_cents` is set to `certification_fee_cents`. Both the member's and the submission's `version` are bumped.

From `RETURNED_FOR_INFO` the same action re-submits, and here the checks are the same except that the credit check does not apply — the money was escrowed on the first submit and has never left. It requires `RATIFIED` status on the pinned specification, `good_standing` on the member, and the same `SB2`/`SB3` declaration pair. On success `state` becomes `SUBMITTED`, `submitted_at` is re-stamped, and `conformance_review_state` returns from `RETURNED` to `PENDING`, closing the review cycle `IN_REVIEW → RETURNED_FOR_INFO → SUBMITTED → IN_REVIEW`. Crucially the ledger is untouched: `fee_escrowed_cents` already equals `certification_fee_cents`, and no second escrow is taken. A submit attempted from any state other than `DRAFT` or `RETURNED_FOR_INFO` is rejected with `ERR_INVALID_SUBMISSION_STATE`, a non-`RATIFIED` specification with `ERR_INVALID_SPECIFICATION_STATE`, a failed baseline declaration with `ERR_SECURITY_BASELINE_NOT_MET`, and an underfunded first submit with `ERR_INSUFFICIENT_CREDIT` and HTTP 402. Recall from §2.8 that a member who is both out of good standing and short of credit hears about the standing, not the money.

Withdrawal is the member's escape hatch and is available from `DRAFT`, `SUBMITTED`, `IN_REVIEW` and `RETURNED_FOR_INFO`, with an identical body from all four; from any other state it draws `ERR_INVALID_SUBMISSION_STATE`. It sets `state` to `WITHDRAWN`, which is terminal, and releases any escrow: the member's `escrowed_credit_cents` falls by `fee_escrowed_cents`, the member's `credit_balance_cents` rises by the same amount, and `fee_escrowed_cents` is then set to 0. From `DRAFT` that release is arithmetically a no-op because `fee_escrowed_cents` was already 0; from `SUBMITTED`, `IN_REVIEW` or `RETURNED_FOR_INFO` it is fully observable, because `fee_escrowed_cents` equalled `certification_fee_cents`. Withdrawal also cleans up testing: the submission's test plan whose `state` is not `VOIDED` — at most one such plan ever exists — is set to `VOIDED` with `voided_reason` `SUPERSEDED_BY_NEW_PLAN`, and every session of that plan whose `state` is `SCHEDULED` or `IN_PROGRESS` is set to `CANCELLED` with the owning laboratory's `reserved_bench_minutes` decremented by exactly that session's `reserved_minutes`.

### 3.5. Resolving the Test Plan and its Feature-Set Closure

A **test plan** is the frozen snapshot of what a particular device must be tested against. A `ProgramAdmin` creates one for a submission that is currently `IN_REVIEW` — any other submission state is rejected with `ERR_INVALID_SUBMISSION_STATE` — by naming the `submission_id` and the `expected_submission_version` described in §2.9. That version field is a required integer carrying no declared range of its own, so a zero or negative figure is shape-valid at rung 6 and is answered by the stale-view rung with `ERR_STALE_SUBMISSION_VERSION`, never with `ERR_INVALID_REQUEST`. Nothing about the pinned specification's current `status` is checked here: rung 13 does not apply to test-plan creation, so a plan may still be created for a submission whose specification has since been `DEPRECATED`. The new plan copies `specification_id` and `device_type` from the submission, which is the second half of version pinning: neither is ever re-targeted afterwards, so a plan continues to describe the feature graph as it stood at creation even after the specification has been demoted. The plan opens in `state` `DRAFT` with `voided_reason` null.

At most one plan per submission may sit in a state other than `VOIDED`. Creating a plan for a submission that already has a live one is therefore not an error but a deliberate supersede: the prior plan is set to `VOIDED` with `voided_reason` `SUPERSEDED_BY_NEW_PLAN`, every session of that prior plan whose `state` is `SCHEDULED` or `IN_PROGRESS` is set to `CANCELLED`, and each such cancellation decrements the owning laboratory's `reserved_bench_minutes` by exactly that session's `reserved_minutes`. The parent submission's `version` is bumped by the create even though no property of the submission itself changes — an unconditional audit bump that is the one place in the service where §2.4's "a write that changes nothing is not a mutation" rule is deliberately set aside, and it fires whether or not a prior plan was superseded. That bump is precisely why the stale-view guard exists: a client working from an old read would otherwise silently destroy scheduling it never saw.

The plan's scope is resolved once, at creation, by a **closure computation** over the specification's feature graph, and it is never recomputed. The candidate pool is every feature set whose `specification_id` equals the submission's pinned specification and whose `device_type` equals the submission's device class; feature sets of other device classes are never included, even when their `feature_code` happens to appear in `declared_feature_codes`, and a declared code with no matching candidate is simply ignored here because submission creation already refused unknown codes.

From that pool the computation seeds a working set with two groups: every candidate whose `obligation` is `MANDATORY`, and every candidate whose `obligation` is `OPTIONAL` and whose `feature_code` appears in the submission's `declared_feature_codes`. It then propagates to a fixed point, applying two rules on every round and repeating until the working set stops growing, with eight rounds sufficing for any graph this service accepts. The first rule is **dependency closure**: for every feature set already in the working set that carries a non-null `depends_on_feature_set_id`, the feature set it depends on is added, transitively, regardless of that dependency's own obligation. The second rule is **conditional activation**: any candidate whose `obligation` is `CONDITIONAL` and whose `depends_on_feature_set_id` names something already in the working set is added. The two rules interact, and that interaction is the point — one extra declared optional code can pull in a conditional set through the second rule, whose own dependency then pulls in a further optional set through the first rule, a two-round chain that a single-pass implementation silently truncates.

When the working set is final it is written to `included_feature_set_ids`, ordered by `feature_code` ascending. Three case counts are derived from it. `required_case_count` is the sum of `test_case_count` over the whole working set. `mandatory_case_count` is that sum restricted to members whose `obligation` is `MANDATORY` or `CONDITIONAL` — conditional sets, once in scope, are counted as mandatory work. `optional_case_count` is that sum restricted to members whose `obligation` is `OPTIONAL`. By construction `required_case_count` always equals `mandatory_case_count` plus `optional_case_count`.

Issuing a plan releases it to the laboratory network. A `ProgramAdmin` moves it `DRAFT → ISSUED`, which requires that `required_case_count` is at least 1 — an empty closure is refused with `ERR_MANDATORY_COVERAGE_INCOMPLETE` — and that the parent submission is still `IN_REVIEW`. Issuing a plan that is not `DRAFT` draws `ERR_INVALID_TEST_PLAN_STATE`. From there the plan's own progress is entirely a function of its sessions. The system moves it `ISSUED → IN_EXECUTION` the moment the first of its sessions starts. And it moves it `IN_EXECUTION → COMPLETE` when a session completes and, at that instant, all four of the following hold: the plan's own `state` is still `IN_EXECUTION`, so a plan sitting in any other state — including one already `COMPLETE` or `VOIDED` — is left untouched by the completing session; no session of the plan remains in `SCHEDULED` or `IN_PROGRESS`; at least one session of the plan is `COMPLETE`; and every feature set of `included_feature_set_ids` whose `obligation` is `MANDATORY` or `CONDITIONAL` appears as the `feature_set_id` of at least one result line across the plan's completed sessions. A feature-set identifier of `included_feature_set_ids` that no longer resolves to a stored row is skipped rather than treated as uncovered. Completing a session is the only trigger for this bubbling: cancelling the plan's last live session never advances the plan, however complete its coverage already is. A plan may also be voided from `DRAFT`, `ISSUED`, `IN_EXECUTION` or `COMPLETE`, always with the same body: `state` becomes `VOIDED`, `voided_reason` is set to `SUPERSEDED_BY_NEW_PLAN` or `SPECIFICATION_DEPRECATED` according to what triggered the voiding, and the plan's `SCHEDULED` and `IN_PROGRESS` sessions are cancelled with each cancellation decrementing the owning laboratory's `reserved_bench_minutes` by exactly that session's `reserved_minutes`. `VOIDED` is terminal.

### 3.6. Bench Scheduling, Execution and Result Capture

A **test session** is one laboratory occupying one bench for one window against one plan. Either a `ProgramAdmin` or the laboratory itself books it, naming the `test_plan_id` to execute against, the `laboratory_id` that will occupy a bench, a `bench_index` giving the 1-based bench ordinal within that laboratory, a `window_start` and `window_end` bounding the occupation, and a `session_type` of `INTEROP` — exercising interoperability feature sets — or `SECURITY` — exercising the feature sets whose `security_relevant` flag is set. That distinction is descriptive only: `session_type` is stored on the session and offered as a list filter, but it constrains nothing downstream. A session of either type may record a result line naming any feature set of its plan whatever that feature set's `security_relevant` flag says, neither type is required for a plan to reach `COMPLETE`, and no score reads the field. One further input is optional: a `device_type` string may accompany the booking, naming the device class the booking claims to exercise. It is a coherence-check input only and is never stored on the session, whose device class is always the one carried by its plan; omitting it is entirely normal and the booking proceeds on the plan's `device_type`. Being optional and unstored, it is exempt from both the shape and the enumeration rungs: a `device_type` supplied as anything other than a string — a number, a boolean, an array, an object or JSON null — is ignored outright rather than refused at rung 6, and a string value is never tested for membership of the five device classes, so an unrecognised class name is answered at rung 34 with `ERR_DEVICE_TYPE_MISMATCH` and never at rung 7 with `ERR_INVALID_ENUM_VALUE`. `bench_index` must be at least 1 and at most the laboratory's `bench_capacity`. `window_start` is an inclusive lower bound and `window_end` an exclusive upper bound, `window_end` must be strictly after `window_start`, and both must fall exactly on a minute boundary with zero seconds and zero microseconds; a violation of either is rejected with `ERR_INVALID_WINDOW_BOUNDS`.

Booking runs a battery of checks in the ladder order of §2.8. The laboratory must be `AUTHORIZED`, and a laboratory that is `PROVISIONAL`, `SUSPENDED` or `REVOKED` is refused with `ERR_INVALID_LABORATORY_STATE`. The plan must not be `VOIDED`, and a voided plan is refused with `ERR_INVALID_TEST_PLAN_STATE`. The laboratory's `accreditation_expires_at` must be strictly after the logical clock's current instant, or the booking is refused with `ERR_ACCREDITATION_EXPIRED`. The laboratory's `authorized_device_types` must contain the plan's `device_type`, or the booking is refused with `ERR_DEVICE_TYPE_NOT_AUTHORIZED`; and where the session's own device class disagrees with the plan's `device_type` the booking is refused with `ERR_DEVICE_TYPE_MISMATCH`.

Then come the two occupancy rules, in the order that matters. **Bench occupancy** forbids a second session of the same laboratory-and-bench pair, in `state` `SCHEDULED` or `IN_PROGRESS`, from overlapping the requested window — where overlap is judged on the half-open interval running from `window_start` inclusive to `window_end` exclusive, *extended by a mandatory 60-minute changeover buffer on both sides*. The buffer changes the arithmetic in a way worth stating plainly: two sessions that merely touch, where one's `window_end` equals the next one's `window_start`, still conflict, because the buffer forces a full hour of clearance between them; a gap of exactly 60 minutes is accepted. A conflict is rejected with `ERR_BENCH_WINDOW_CONFLICT`. Only if the window is clear does the **capacity ceiling** apply. Each bench is budgeted ten hours — 600 minutes — per cycle, so a laboratory's ceiling is its `bench_capacity` multiplied by 600 minutes. The requested session's `reserved_minutes`, being the whole minutes between `window_start` and `window_end`, are added to the laboratory's current `reserved_bench_minutes`, and if that total *exceeds* the ceiling the booking is rejected with `ERR_LAB_CAPACITY_EXCEEDED`; landing exactly on the ceiling is allowed and one minute over is not. As §2.8 records, a request that fails both rules reports the window conflict.

An accepted booking stores the session in `state` `SCHEDULED` with `started_at` and `completed_at` null, `completed_late` false, `result_lines` an empty array, `disputed_line_count` 0, and `reserved_minutes` computed from the window; the laboratory's `reserved_bench_minutes` rises by that figure immediately.

Starting a session is reserved to the laboratory that owns it — the acting `X-User-ID` must equal the session's `laboratory_id`, and no `ProgramAdmin` may start one — and requires `state` `SCHEDULED`, a laboratory that is currently `AUTHORIZED`, an `accreditation_expires_at` strictly after the logical clock's current instant, and a parent plan whose `state` is `ISSUED` or `IN_EXECUTION`. A suspended laboratory therefore cannot start work even on a session booked while it was in good order. On each of the four ownership-checked session operations — start, results, complete and cancel — the owner is not named in the request but reached through the addressed session, so the path segment is necessarily resolved first: an unknown `test_session_id` is answered with `ERR_TEST_SESSION_NOT_FOUND` and HTTP 404 even when the caller owns nothing at all, and rung 3's precedence over path existence bites only where the owner identifier is itself supplied by the client. Booking, by contrast, carries no ownership check whatever — session creation is not among §2.1's twelve — so a `TestLaboratory` actor may book a bench window at a laboratory other than its own. The start moves `SCHEDULED → IN_PROGRESS` and stamps `started_at`, and where the parent plan was still `ISSUED` it also advances that plan to `IN_EXECUTION`.

Results arrive as appends, never as replacements. The owning laboratory submits a non-empty `result_lines` array in which every entry carries a `feature_set_id` naming a feature set of the plan, an `outcome` of `PASS`, `FAIL`, `BLOCKED` or `WAIVED`, and an `evidence_hash` fixing the evidence package. The `evidence_hash` is any non-empty string and carries no length ceiling or format rule, and the same `feature_set_id` may appear on several lines of one request. Only the owning `TestLaboratory` may append; a `ProgramAdmin` may not. The server appends each entry to the session's stored `result_lines` in the order supplied, stamping each with a `recorded_at` taken from the logical clock — read once for the whole request, so every line of one accepted append shares an identical `recorded_at` — and a `disputed` flag that starts false; lines are addressed thereafter by their zero-based position in that array. A stored line carries exactly five properties — `feature_set_id`, `outcome`, `evidence_hash`, `recorded_at` and `disputed` — and any further property a client attached to an input line is dropped rather than retained. An append never touches `disputed_line_count`, which stays at whatever the disputes so far have made it. A `feature_set_id` that does not appear in the enclosing session's plan's `included_feature_set_ids` is rejected with `ERR_UNKNOWN_RESULT_FEATURE_SET`, and results submitted against a session that is not `IN_PROGRESS` are rejected with `ERR_INVALID_SESSION_STATE`. Every accepted append refreshes the parent submission's provisional readiness score described in §3.8. Because lines are appended rather than overwritten, a feature set may legitimately accumulate several lines with conflicting outcomes; §3.8 explains which of them counts.

Completing a session requires `state` `IN_PROGRESS`, laboratory ownership, and a `result_lines` array that is not empty — completing a session that captured nothing is refused with `ERR_MANDATORY_COVERAGE_INCOMPLETE`. Completion moves `IN_PROGRESS → COMPLETE`, stamps `completed_at`, and recomputes `completed_late`, which is true exactly when `completed_at` is not null and is strictly after `window_end`; a session that finishes precisely at its `window_end` is not late. It also decrements the laboratory's `reserved_bench_minutes` by exactly this session's `reserved_minutes`, and it may bubble the parent plan from `IN_EXECUTION` to `COMPLETE` under the coverage conditions of §3.5.

Cancellation is available to the `ProgramAdmin` or to the owning laboratory, from `SCHEDULED` or from `IN_PROGRESS`, with an identical body from either, and it accepts an optional `reason` of between 1 and 500 characters. That string is shape-checked when supplied — an empty string or one over 500 characters draws `ERR_INVALID_REQUEST` — but it is recorded nowhere: it is neither stored on the session nor echoed in the response, and omitting it or supplying it as JSON null is equally acceptable. When the acting role is `TestLaboratory`, the acting `X-User-ID` must equal the session's `laboratory_id`. Cancellation sets `state` to `CANCELLED`, compensates the laboratory by decrementing `reserved_bench_minutes` by exactly this session's `reserved_minutes` — restoring the figure the laboratory held before this session was ever created — and frees the bench window, so a later booking may occupy the same laboratory-and-bench interval. Both `COMPLETE` and `CANCELLED` are terminal, and an attempt to cancel from either draws `ERR_INVALID_SESSION_STATE`. The system also performs this same cancellation as part of four separate cascades: specification deprecation, laboratory accreditation revocation, submission withdrawal, and any test-plan voiding.

Finally, a recorded line can be challenged. A `ProgramAdmin` or a `ConformanceReviewer` disputes one by supplying its `line_index`, the zero-based position of the line inside `result_lines`, on a session whose `state` is `IN_PROGRESS` or `COMPLETE`. The addressed line's `disputed` flag is set and the session's `disputed_line_count` — the number of `result_lines` entries whose `disputed` flag is true — rises accordingly. `line_index` is a required integer whose declared range has a floor of 0 and no ceiling, so a negative index is a shape failure answered with `ERR_INVALID_REQUEST` at rung 6, while an index at or beyond the current length of `result_lines` reaches rung 37 and is rejected with `ERR_UNKNOWN_RESULT_FEATURE_SET`. Disputing a line that is already disputed is accepted rather than refused, and is a complete no-op: the flag is already true, `disputed_line_count` does not move, the session's `updated_at` and `version` do not advance, and the response is HTTP 200 carrying the unchanged session. Neither disputing role is ownership-checked — the operation is open to any `ProgramAdmin` or `ConformanceReviewer` regardless of which laboratory recorded the line. Disputes do not change any outcome or any readiness score; they feed the dispute-free component of the laboratory competency score, so their effect surfaces at the laboratory's next competency review.

### 3.7. Multi-Vendor Plugfests and Interoperability Credits

Formal certification proves a device against a written specification; a **plugfest** proves it against other people's hardware. A `ProgramAdmin` schedules one by naming the `host_laboratory_id`, which must have `accreditation_status` `AUTHORIZED` at creation, and the `specification_id` exercised at the event, which must have `status` `RATIFIED` at creation. The event's `window_start` and `window_end` bound it — `window_end` strictly after `window_start`, both on a minute boundary, or `ERR_INVALID_WINDOW_BOUNDS` — and a `registration_deadline` fixes the instant after which registration is refused, which must be at or before `window_start` with equality accepted, or `ERR_INVALID_DATE_RANGE`. The minute-boundary rule binds the two window bounds alone: `registration_deadline` may carry any seconds and fractional seconds it likes and is never refused for falling off a minute. A `min_distinct_vendors` between 2 and 8 records the vendor quorum the event needs before it may be locked. A new event opens in `state` `REGISTRATION_OPEN` with `distinct_vendor_count` 0 and `locked_at` null.

A `Member` registers one of its devices into an event by naming the `plugfest_id`, its own `member_id`, the `submission_id` of the device under test, and the `device_model` designation presented at the event, between 1 and 80 characters. The `member_id` must equal the submission's own `member_id` as well as the acting `X-User-ID`, and both comparisons answer a mismatch with `ERR_UNAUTHORIZED` and HTTP 403 — but they sit at different heights on the ladder. The body's `member_id` is compared against `X-User-ID` at rung 3, above reference resolution, so a member naming another member's identifier is refused with `ERR_UNAUTHORIZED` even when that identifier resolves to no stored row; the submission's own `member_id` can only be compared once the submission has been fetched, and that check follows the shape rung, so a request that names somebody else's submission *and* omits `device_model` reports `ERR_INVALID_REQUEST` first. A `member_id` that is present but not a string is likewise left to rung 6 rather than treated as an ownership failure. The submission's pinned `specification_id` must equal the plugfest's `specification_id` — a device certified against one baseline cannot be exercised at an event running another, and the mismatch is rejected with `ERR_DEVICE_TYPE_MISMATCH`. The member must be in good standing. The event must still be `REGISTRATION_OPEN`, and a locked, closed or cancelled event refuses registration with `ERR_INVALID_PLUGFEST_STATE`. The logical clock's current instant must be at or before the event's `registration_deadline`, or the registration is refused with `ERR_REGISTRATION_CLOSED`.

Two further rules stop a vendor double-booking a physical device, and their order is deliberate. First, **calendar-date overlap**: the registration is refused when the same `submission_id` already has a participation, in `state` `REGISTERED`, `PASSED` or `FAILED`, belonging to a *different* plugfest whose UTC calendar-date range shares any date with the requested event's range. Those ranges are closed and inclusive at both ends, running from the calendar date of `window_start` through the calendar date of `window_end`, and clock times are irrelevant: an event that ends at 18:00 UTC on the sixth of October and one that begins at 20:00 UTC on the same sixth of October both occupy that date and therefore conflict, even though their instants do not overlap by a second. The conflict is reported as `ERR_PARTICIPATION_WINDOW_CONFLICT`. Only the *participation's* state is filtered here; the other event's own `state` is never consulted, so a `PASSED` participation at an event that has since been `CLOSED` still occupies its calendar dates and still blocks. Participations of the *requested* event are deliberately excluded from that check, so that a second registration of the same event-and-submission pair — which trivially shares every date with itself — instead falls through to the second rule. That second rule refuses a repeat of the same `plugfest_id` and `submission_id` pair with `ERR_DUPLICATE_PARTICIPATION`, and unlike the first it is blind to `state`: any stored participation of that pair blocks a repeat, a `NO_SHOW` one included.

An accepted registration is stored in `state` `REGISTERED` with `interop_pass_count` 0 and `outcome_recorded_at` null, and the event's vendor count is recomputed. `distinct_vendor_count` is the number of *distinct* `member_id` values across the event's participations whose `state` is `REGISTERED`, `PASSED` or `FAILED`. Two devices entered by the same member therefore count once, because it is a distinct-vendor count and not a participation count. Participations in `state` `NO_SHOW` are excluded, which makes the count non-monotonic: closing an event drops it.

Locking the event freezes its roster. A `ProgramAdmin` moves it `REGISTRATION_OPEN → LOCKED` only when `distinct_vendor_count` is at or above `min_distinct_vendors`; exactly the minimum is sufficient, and a shortfall is refused with `ERR_INSUFFICIENT_DISTINCT_VENDORS`. The lock stamps `locked_at` and refuses all further registrations for the event. It is not gated on the clock in any way: an event may be locked before or after its `registration_deadline` and before or after its `window_start`, and no check compares the current instant against either.

Outcomes are recorded by the hosting laboratory, and only while the event is `LOCKED`. The acting `X-User-ID` must equal the event's `host_laboratory_id`, and because that owner is reached through the addressed participation and its event rather than named in the request, an unknown `participation_id` is answered with `ERR_PARTICIPATION_NOT_FOUND` and HTTP 404 before ownership is weighed at all. The participation must still be `REGISTERED`, with any later state refused as `ERR_INVALID_PARTICIPATION_STATE`. The laboratory supplies an `outcome` of `PASS` or `FAIL` together with an `interop_pass_count` recording how many multi-vendor interoperability pairings the device passed at the event, which must be at least 0 and at most 8, and which must be at least 1 when `outcome` is `PASS`. That conditional minimum is a rung-6 shape rule tested against the literal string `PASS` before rung 7 has judged the enum, so a mis-cased `pass` skips the minimum entirely and is answered with `ERR_INVALID_ENUM_VALUE`. The stored figure is a record of the event and nothing more: it enters no calculation anywhere in the service — the interoperability component of §3.8 reads `plugfest_credit_count` alone, and `interop_pass_count` is never summed, capped or compared against anything. A `PASS` moves the participation `REGISTERED → PASSED`, writes `interop_pass_count`, stamps `outcome_recorded_at`, and increments the named submission's `plugfest_credit_count` by one, that field being the count of the submission's participations in `state` `PASSED`; it also refreshes the submission's provisional readiness score. A `FAIL` moves the participation `REGISTERED → FAILED` and likewise writes `interop_pass_count` and stamps `outcome_recorded_at`, but leaves `plugfest_credit_count` untouched and refreshes no readiness score. Either outcome then recomputes the event's `distinct_vendor_count`, which cannot move — `REGISTERED`, `PASSED` and `FAILED` all count as present vendors — so recording an outcome leaves the plugfest row itself unstamped and unversioned.

Closing the event is the last act. A `ProgramAdmin` moves it `LOCKED → CLOSED` — again with no clock precondition, so an event may be closed while its window is still running — and every participation still in `state` `REGISTERED` is set to `NO_SHOW` — a vendor who registered and never appeared is recorded as such rather than quietly forgotten — leaving `plugfest_credit_count` unchanged. Because no-shows are excluded from the vendor count, `distinct_vendor_count` is recomputed and consequently falls. An event may also be cancelled outright by the system, from `REGISTRATION_OPEN` or from `LOCKED`, as the fan-out of its host laboratory's accreditation revocation described in §3.3; cancellation carries the same no-show treatment of still-registered participations. `CLOSED` and `CANCELLED` are both terminal.

### 3.8. Conformance Review, Security Review and Credential Issuance

A submission that has been tested still has to be judged, and the programme judges it along two axes that move independently. The `state` field carries the submission's primary lifecycle position; `conformance_review_state` records the declaration-of-conformity verdict and `security_review_state` the device-attestation verdict. Neither axis waits on the other, either verdict may be recorded first, and the primary axis moves only when the pair of them permits it.

The member starts the process by submitting the draft. From `DRAFT` the submission requires a pinned specification whose `status` is `RATIFIED`, a member in good standing, and — where that specification's `security_baseline_level` is `SB2` or `SB3` — a `declared_secure_boot` of true together with a `declared_firmware_update_capability` of exactly `OTA_SIGNED`; a self-declaration of `OTA_UNSIGNED` or `NONE` against a hardened baseline is refused with `ERR_SECURITY_BASELINE_NOT_MET`. The member's `credit_balance_cents` must be at least the submission's pinned `certification_fee_cents`, or the request is refused with `ERR_INSUFFICIENT_CREDIT`. Acceptance moves `DRAFT → SUBMITTED`, stamps `submitted_at` from the logical clock, and escrows the fee: the member's `credit_balance_cents` falls by `certification_fee_cents`, its `escrowed_credit_cents` rises by the same figure, and the submission's `fee_escrowed_cents` is set to `certification_fee_cents`. The same call also serves the resubmission path `RETURNED_FOR_INFO → SUBMITTED`, which repeats the ratification, good-standing and security-baseline checks but *not* the balance check, and which escrows nothing a second time — `fee_escrowed_cents` already equals `certification_fee_cents`, so the member's ledger is untouched — while resetting `conformance_review_state` from `RETURNED` back to `PENDING`.

A `ConformanceReviewer` picks the submission up from `SUBMITTED`, moving it `SUBMITTED → IN_REVIEW` and stamping `review_started_at`. From `IN_REVIEW` that reviewer may return it to the vendor for more information, supplying a `reason` of 1 to 500 characters — a required string that is shape-checked at rung 6, ahead of every state condition, and then recorded nowhere: it is neither stored on the submission nor echoed in the response. A return requires `conformance_review_state` to be `PENDING` and `revision_round` to be strictly below 2; a submission that has already been returned twice is refused with `ERR_REVISION_LIMIT_EXCEEDED`. The return moves `IN_REVIEW → RETURNED_FOR_INFO` on the primary axis and `PENDING → RETURNED` on the conformance axis, increments `revision_round` by one, and records `conformance_reviewer_user_id` as the acting `X-User-ID`. The conformance axis is therefore cyclic — `PENDING` to `RETURNED` and back to `PENDING` on resubmission — and it will cycle at most twice before the round limit closes the loop.

The conformance verdict is recorded with a `decision` of `APPROVE` or `REJECT` plus an optional `note` of up to 1000 characters; the `note` carries no minimum length, so an empty string is accepted, and like the return-for-info `reason` it is recorded nowhere. Either decision requires the primary `state` to be `IN_REVIEW`, `conformance_review_state` to be `PENDING`, and the submission's non-`VOIDED` test plan to exist, to be `COMPLETE`, and to carry full mandatory coverage. Rung 18 does not reach this operation at all: a submission with no non-`VOIDED` plan, a plan still in `DRAFT`, `ISSUED` or `IN_EXECUTION`, and a plan whose mandatory coverage is short are one and the same failure here, answered by rung 43 with `ERR_MANDATORY_COVERAGE_INCOMPLETE` and never with `ERR_INVALID_TEST_PLAN_STATE`. That coverage is judged over the result lines of the plan's `COMPLETE` sessions alone — a line recorded in a session still `IN_PROGRESS` does not count toward it — and an entry of `included_feature_set_ids` that no longer resolves to a stored feature set is skipped rather than treated as uncovered. Both decisions then compute the readiness score in its `FINAL` variant. An `APPROVE` additionally demands that the freshly computed final score be at or above the approval threshold of 65.00 — exactly 65.00 is sufficient, and a shortfall is refused with `ERR_READINESS_BELOW_THRESHOLD` — and that `plugfest_credit_count` be at least the pinned specification's `min_plugfest_credits`, with a shortfall refused as `ERR_INSUFFICIENT_PLUGFEST_CREDITS`. The ordering here is deliberate and observable: the score is computed *before* the threshold is evaluated, but it is pinned to `final_readiness_score` only when the request as a whole is accepted, so a rejected `APPROVE` leaves `final_readiness_score` exactly as it was — the write is rolled back with the request along with every other effect of the failed call. An accepted `APPROVE` pins `final_readiness_score`, sets `conformance_review_state` to `APPROVED` and records `conformance_reviewer_user_id`. A `REJECT` pins `final_readiness_score` too, sets `conformance_review_state` to `REJECTED`, records `conformance_reviewer_user_id`, and drives the primary axis to `REJECTED`.

The security verdict is recorded by a `SecurityReviewer`, and it is the segregation-of-duties gate of §2.10: the acting `X-User-ID` must differ from any `conformance_reviewer_user_id` already recorded on the submission, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. The reviewer supplies a `decision` of `APPROVE` or `REJECT`, a `secure_boot_verified` boolean recording whether verified secure boot was actually observed, and a `verified_firmware_update_capability` of `OTA_SIGNED`, `OTA_UNSIGNED` or `NONE` recording what the device actually does — findings that may contradict the vendor's `declared_secure_boot` and `declared_firmware_update_capability` self-declarations, and which are written onto the submission on either decision. An `APPROVE` requires the primary `state` to be `IN_REVIEW`, `security_review_state` to be `PENDING`, the request's `secure_boot_verified` to be true — a `secure_boot_verified` of false on an `APPROVE` is refused with `ERR_SECURE_BOOT_NOT_VERIFIED` — and, where the pinned specification's `security_baseline_level` is `SB2` or `SB3`, the request's `verified_firmware_update_capability` to be exactly `OTA_SIGNED`, a weaker capability being refused with `ERR_SECURITY_BASELINE_NOT_MET`. An accepted `APPROVE` sets `security_review_state` to `APPROVED` and records `security_reviewer_user_id`. A `REJECT` needs neither substantive condition, sets `security_review_state` to `REJECTED`, records `security_reviewer_user_id`, and drives the primary axis to `REJECTED`. Both `APPROVED` and `REJECTED` are terminal on this axis, so a verdict once recorded cannot be revised.

The primary axis then resolves from the pair. At the end of *either* decision the system evaluates a compound bubble-up: when the submission is `IN_REVIEW` and both `conformance_review_state` and `security_review_state` are `APPROVED`, the submission moves `IN_REVIEW → REVIEW_COMPLETE`. Whichever decision lands second is the one that triggers it. Symmetrically, when the submission is `IN_REVIEW` and *either* axis is `REJECTED`, the submission moves `IN_REVIEW → REJECTED` and the escrow is compensated: the member's `escrowed_credit_cents` falls by the submission's `fee_escrowed_cents`, its `credit_balance_cents` rises by the same figure, and `fee_escrowed_cents` is then set to 0. A rejected submission therefore returns the vendor's money.

Issuance is the `ProgramAdmin`'s act and it closes both the primary and the credential axis. It requires `state` to be `REVIEW_COMPLETE`, `dac_state` to be `NOT_ISSUED`, the recorded `secure_boot_verified` to be true, the recorded `verified_firmware_update_capability` to be anything other than `NONE` — a failure of either being refused with `ERR_SECURE_BOOT_NOT_VERIFIED`, and a `verified_firmware_update_capability` that is still null treated exactly like `NONE` — and `fee_escrowed_cents` to equal `certification_fee_cents`. That escrow-equality requirement carries no identifier of its own: it belongs to the submission-state rung, so a mismatch is answered with `ERR_INVALID_SUBMISSION_STATE`, and it is weighed before the two attestation conditions, so a submission whose escrow does not match reports the submission state even when its recorded findings would also have failed. The administrator supplies a `dac_serial` of 1 to 64 characters which must not already be held by any other submission, a collision being refused with `ERR_DUPLICATE_DAC_SERIAL`; a serial is held from the instant it is issued and is never released, so a submission whose `dac_state` has since fallen to `REVOKED` keeps its `dac_serial` and goes on blocking that string. Issuance moves `REVIEW_COMPLETE → CERTIFIED`, stamps `certified_at`, moves `dac_state` `NOT_ISSUED → ISSUED` with the supplied `dac_serial` stored, and *consumes* rather than releases the escrow: the member's `escrowed_credit_cents` falls by `fee_escrowed_cents`, its `credits_consumed_cents` rises by the same figure, and `fee_escrowed_cents` becomes 0. The money leaves the member's available balance permanently, which is exactly the difference between consumption and the release performed on rejection or withdrawal. `CERTIFIED`, `REJECTED` and `WITHDRAWN` are all terminal on the primary axis, and `dac_state` is later revocable — from `ISSUED` to the terminal `REVOKED` — by the intellectual-property withdrawal cascade of §3.2, by a `FULL` firmware classification, and by any listing withdrawal, all described in §3.9.

A member may withdraw a live submission at any point on the review path, from `DRAFT`, `SUBMITTED`, `IN_REVIEW` or `RETURNED_FOR_INFO`, and the body of the withdrawal is identical from all four. It sets `state` to `WITHDRAWN`, releases any escrow back to `credit_balance_cents` and zeroes `fee_escrowed_cents` — a no-op from `DRAFT`, where `fee_escrowed_cents` is already 0, and observable from the other three, where it equals `certification_fee_cents` — voids the submission's non-`VOIDED` test plan with `voided_reason` `SUPERSEDED_BY_NEW_PLAN`, and cancels every `SCHEDULED` or `IN_PROGRESS` session of that plan, each cancellation decrementing the owning laboratory's `reserved_bench_minutes` by exactly that session's `reserved_minutes`.

#### The Readiness Score

The readiness score is a hundred-point weighted assessment of how close a submission is to certification, and it exists in two variants that read the same stored rows and disagree on purpose. The four weights are 50 points for mandatory coverage, 20 for optional coverage, 15 for interoperability and 15 for timeliness.

Everything the score reads comes from the submission's non-`VOIDED` test plan — at most one exists — and from that plan's sessions. A submission with no non-`VOIDED` plan at all is not an error for either variant, and neither is a plan with no counted session: every tally and every count comes out 0, the mandatory ratio takes its zero-denominator value of 0.0000 and the optional ratio its vacuous 1.0000, and the score is whatever the interoperability and timeliness components alone contribute — 35.00 for a `PROVISIONAL` evaluation of a submission holding no plugfest credit. Which sessions count is the first point of divergence: the `PROVISIONAL` variant counts sessions whose `state` is `IN_PROGRESS` or `COMPLETE`, while the `FINAL` variant counts only those whose `state` is `COMPLETE`. Sessions in `SCHEDULED` or `CANCELLED` never participate in either variant, which has a consequence worth naming: cancelling a session that carried failing lines raises both scores, because the failures leave the counted population entirely.

Within the counted sessions, each feature set has one **effective outcome**, being the `outcome` of the latest result line naming it. Latest means ordered by the line's `recorded_at` ascending, and the tie-breakers apply in a fixed precedence: where two lines share a `recorded_at`, the enclosing session's `created_at` ascending decides first, then — for sessions sharing a `created_at` — the store-wide insertion sequence of §2.3, and only among lines of one and the same session does the line's own zero-based position in `result_lines` ascending break the remaining tie. Session order therefore outranks line position: an earlier session's later line beats a later session's earlier line at equal `recorded_at`. The record identifier is never a decision input. Result lines whose `feature_set_id` is absent from the plan's `included_feature_set_ids` are ignored entirely.

An effective outcome is treated as passing when it falls in the variant's pass set — the second point of divergence. The `PROVISIONAL` pass set is optimistic and holds `PASS`, `WAIVED` and `BLOCKED`, on the reasoning that a blocked case is presumed recoverable. The `FINAL` pass set is strict and holds only `PASS` and `WAIVED`, so a case still `BLOCKED` at decision time counts as a failure.

Coverage is then measured in test cases rather than in feature sets. A feature set whose effective outcome is passing contributes its whole `test_case_count`. The mandatory tally sums `test_case_count` over the plan's feature sets whose `obligation` is `MANDATORY` or `CONDITIONAL` and whose effective outcome passes; the optional tally sums it over those whose `obligation` is `OPTIONAL` and whose effective outcome passes. Both tallies and both denominators are recomputed by walking `included_feature_set_ids` at evaluation time rather than read back from the plan's stored counts; the two agree because a feature set is immutable once created, and where an entry of `included_feature_set_ids` no longer resolves to a stored feature set it drops out of the tally and out of the denominator alike. The mandatory ratio is the mandatory tally divided by the plan's `mandatory_case_count`, rounded half-up to four decimal places, and is 0.0000 when that denominator is 0. The optional ratio is the optional tally divided by the plan's `optional_case_count`, likewise at four decimal places, but when that denominator is 0 it is **1.0000**, not 0.0000: a plan with no optional obligations is vacuously satisfied and collects the full 20 points. The asymmetry between the two zero-denominator conventions is intentional.

The interoperability ratio is the submission's `plugfest_credit_count`, capped at the target of 2, divided by 2, rounded half-up to four decimal places — so one credit is worth half the interoperability weight, two credits are worth all of it, and a third credit adds nothing. The timeliness ratio is the third and last point of divergence. Its input is the late ratio, being the number of counted sessions whose `completed_late` flag is true divided by the total number of counted sessions, rounded half-up to four decimal places, and 0.0000 when no session is counted. The `PROVISIONAL` timeliness ratio is pinned at 1.0000 no matter what — nothing can be late before it is complete — while the `FINAL` timeliness ratio is 1.0000 minus the late ratio.

The four ratios are then weighted and summed with **per-component rounding**: each weight is multiplied by its ratio and that product is rounded half-up to two decimal places, and only then are the four rounded components added, the sum being exact. Rounding once at the end instead of four times along the way can differ from the mandated figure by a cent-scale amount, and the per-component rule is what the implementation must follow. Because `FINAL` counts fewer sessions, treats `BLOCKED` as failing, and can lose timeliness points, it is always at or below `PROVISIONAL` on the same data; and only the `FINAL` figure is ever compared against the approval threshold.

The `PROVISIONAL` figure is recomputed and written to `provisional_readiness_score` after every result-line submission and after every plugfest outcome recording; it is null until the first result line exists. The `FINAL` figure is computed inside the conformance decision and pinned to `final_readiness_score` only when that decision is accepted. Both are also readable without writing anything, through a computed read that takes an optional `variant` of `PROVISIONAL` — the default when it is omitted — or `FINAL`, and that exposes the component inputs so the divergence between the two is directly observable: it returns `submission_id`, the `variant` applied, the plan's `mandatory_case_count` and the `mandatory_passed_cases` counted against it, the plan's `optional_case_count` and the `optional_passed_cases` counted against it, the submission's `plugfest_credit_count`, the `counted_session_count` and `late_session_count` under that variant's session filter, and the resulting `score`. No ratio is exposed, and the shapes are mixed: the seven numeric figures other than the score — the two case counts, the two passed-case counts, `plugfest_credit_count`, `counted_session_count` and `late_session_count` — are plain JSON integers, while `score` alone is rendered as a JSON *string* at exactly two decimal places, mirroring the competency read of §3.3. The two figures stored on the submission row behave the other way round: `provisional_readiness_score` and `final_readiness_score` are plain JSON numbers there, so the same score of eighty-five points reads back as `85.0` from the submission and as `"85.00"` from the computed read. This read is not ownership-checked either, so a `Member` may read any submission's readiness.

### 3.9. The Consumer Directory, Recertification and Noncompliance Enforcement

A **certification listing** is the public face of everything the preceding sections produced. A `ProgramAdmin` creates one by naming the `submission_id` it publishes. The submission must have cleared both review axes — its `state` must be `REVIEW_COMPLETE` or `CERTIFIED`, and anything earlier is refused with `ERR_INVALID_SUBMISSION_STATE` — and it must not already have a listing, a second attempt being refused with `ERR_LISTING_ALREADY_EXISTS`. A listing may therefore exist before the device attestation credential is issued; issuance is what publication requires, not what listing requires. Creation copies `member_id` from the submission, assigns `listing_reference` as described in §2.4, resolves `declared_features` as the `feature_code` values of the submission's non-`VOIDED` test plan's `included_feature_set_ids` ordered by `feature_code` ascending — an empty array where the submission has no non-`VOIDED` plan at all, and with any identifier that no longer resolves to a stored feature set silently omitted rather than reported as an error — and opens the listing with `publication_status` `UNPUBLISHED`, `compliance_status` `COMPLIANT`, `recertification_due_at` and `recert_trigger_reason` and `latest_firmware_version` and `recert_classification` and `published_at` all null, and `firmware_revision_count` 0.

The listing carries two independent status axes and they must not be conflated. `publication_status` is the consumer-visibility axis; `compliance_status` is the enforcement axis. Opening an investigation moves the enforcement axis and leaves visibility alone; ordering remediation moves both; confirming remediation restores the enforcement axis to `REMEDIATED` but deliberately leaves visibility at `SUPPRESSED`, so a separate publication act is needed to put the device back in front of consumers.

Publication is the `ProgramAdmin`'s act and it is available from `UNPUBLISHED` or from `SUPPRESSED` — the latter being the re-publication path after a remediation, which makes the visibility axis cyclic. It requires the linked submission's `dac_state` to be `ISSUED`, with a `NOT_ISSUED` or `REVOKED` credential refused as `ERR_INVALID_SUBMISSION_STATE`; it requires `compliance_status` to be `COMPLIANT` or `REMEDIATED`, with an `UNDER_INVESTIGATION` or `NONCOMPLIANT` listing refused as `ERR_INVALID_LISTING_STATE`, as is a listing that is already `PUBLISHED` or `WITHDRAWN`; and it requires the listing's member to be in good standing. Publication sets `publication_status` to `PUBLISHED`, stamps `published_at` from the logical clock, and recomputes `declared_features` from the submission's non-`VOIDED` test plan, so a plan that gained feature sets since the last publication refreshes the consumer-visible declaration.

Withdrawal is the `ComplianceOfficer`'s act, takes a `reason` of 1 to 500 characters — required, shape-checked ahead of the state condition, and then recorded nowhere: neither stored on the listing nor echoed back — and is available from `UNPUBLISHED`, `PUBLISHED` or `SUPPRESSED`, with an already-`WITHDRAWN` listing refused as `ERR_INVALID_LISTING_STATE`; the `compliance_status` axis is not consulted at all here, so a listing that is `UNDER_INVESTIGATION` or already `NONCOMPLIANT` may still be withdrawn. It sets `publication_status` to `WITHDRAWN`, sets `compliance_status` to `NONCOMPLIANT`, and, where the linked submission's `dac_state` is `ISSUED`, sets that `dac_state` to `REVOKED`. `WITHDRAWN` is terminal on the visibility axis; the enforcement axis has no terminal state at all, because a remediated listing can be investigated again without bound.

#### Firmware Revisions and the Recertification Trigger

Certified devices receive firmware, and firmware can quietly change what the device does. Each revision is therefore reported against the listing by a `ProgramAdmin` or by a `Member`, carrying the new `firmware_version` of 1 to 40 characters, a `changed_feature_codes` array — possibly empty, without duplicates — naming the feature codes the revision touches, a `security_change` boolean stating whether the revision alters security-relevant behaviour, and the `expected_listing_version` guard of §2.9. Reporting is not one of §2.1's twelve ownership-checked operations, so the acting `Member` need not be the listing's own member: any `Member` may report a revision against any listing. `expected_listing_version` is a required integer carrying no declared range of its own, so a zero or negative figure is shape-valid at rung 6 and is answered by the stale-view rung with `ERR_STALE_LISTING_VERSION`, never with `ERR_INVALID_REQUEST`. A revision may not be reported against a `WITHDRAWN` listing, which is refused with `ERR_INVALID_LISTING_STATE`, and every entry in `changed_feature_codes` must resolve to a feature set of the listing's pinned specification and device type, an unknown code being refused with `ERR_UNKNOWN_FEATURE_CODE`.

Classification runs after the stale-view check and before any state write. It compares the reported change against what the device actually claims in public: the **overlap** is the set intersection of `changed_feature_codes` with the listing's `declared_features`. A firmware change touching a feature the device never declared is invisible to classification. Among the overlapping codes, the **security-relevant** ones are those whose feature set — read from the rows of the pinned specification and the submission's `device_type`, so the same `feature_code` under another device type is never consulted — has `security_relevant` true.

Five rules are then evaluated in order and the *first* that matches decides, even when several would match. Rule one classifies `FULL` with `recert_trigger_reason` `FIRMWARE_SECURITY_CHANGE` when the request's `security_change` is true and the pinned specification's `security_baseline_level` is `SB2` or `SB3`. Rule two classifies `FULL` with the same reason when at least one overlapping code is security-relevant. Rule three classifies `FULL` with `recert_trigger_reason` `FIRMWARE_FEATURE_DELTA` when the overlap holds strictly more than two codes; the boundary is strict, so an overlap of exactly two codes falls through to rule four while an overlap of three classifies `FULL`. Rule four classifies `DELTA` with reason `FIRMWARE_FEATURE_DELTA` when the overlap holds at least one code. Rule five classifies `NONE` and leaves `recert_trigger_reason` unchanged, and it is where a `security_change` of true lands when the specification's baseline is `SB1` and nothing in the overlap is security-relevant — a security-flagged revision that nevertheless triggers no recertification.

The deadline follows the classification: `FULL` sets `recertification_due_at` to the logical clock's current instant advanced by 30 days, `DELTA` advances it by 90 days, and `NONE` leaves `recertification_due_at` exactly as it was, including null. Whatever the classification, and including `NONE`, two writes always happen: `latest_firmware_version` becomes the request's `firmware_version`, and `firmware_revision_count` rises by one. `recert_classification` records the classification just reached, so each accepted report supersedes the previous one — which is why the operation is version-guarded.

A `FULL` classification carries two further consequences. Where the listing's `publication_status` is `PUBLISHED` it becomes `SUPPRESSED`, pulling the device out of the consumer directory; and where the linked submission's `dac_state` is `ISSUED` it becomes `REVOKED`. A firmware revision that materially changes a certified device therefore de-credentials it until a fresh submission is certified.

#### Noncompliance Investigations

A `ComplianceOfficer` opens an investigation against a listing by naming the `listing_id`, a `category` of `INTEROP_DEFECT`, `SECURITY_DEFECT`, `FALSE_FEATURE_DECLARATION` or `IP_WITHDRAWAL`, an `evidence_summary` of 1 to 500 characters, and a `claimed_impact_units` count of impacted deployed units, at least 0 and at most 10000000. The `IP_WITHDRAWAL` category is reserved to the system: an operator who supplies it is refused with `ERR_DEVICE_TYPE_MISMATCH`, which is the device-and-category coherence rung of the ladder. A listing already `UNDER_INVESTIGATION` cannot take a second case, that being refused with `ERR_INVALID_LISTING_STATE`, so the enforcement axis admits one live case at a time. Acceptance opens the case in `state` `OPEN`, records `opened_by_user_id` as the acting `X-User-ID`, leaves `auto_opened` false, `closed_by_user_id` and `remediation_deadline_at` null, prices the assessment, moves the listing's `compliance_status` to `UNDER_INVESTIGATION` while leaving `publication_status` untouched, and recomputes the member's `open_case_count`.

The same case-opening happens by cascade. The final hop of a member's intellectual-property withdrawal, described in §3.2, auto-opens one case per affected listing with `category` `IP_WITHDRAWAL`, `state` `OPEN`, `auto_opened` true, `opened_by_user_id` the literal `SYSTEM`, `claimed_impact_units` 0, and `evidence_summary` the literal text `Auto-opened: IP commitment withdrawn by member`, its penalty fields priced by the same rule as an operator-filed case.

The **penalty assessment** is priced once at creation, pinned onto the case, and never recomputed — a later disposition, remediation or closure leaves the figures exactly as they were filed. It is a marginally-tiered assessment on `claimed_impact_units`, meaning each band is priced only on the units that actually fall inside it. The first 100 units are priced at 500 cents each. The next 900 units — those from the hundred-and-first through the thousandth — are priced at 300 cents each. Every unit beyond the thousandth is priced at 150 cents each. The three band charges are summed into `assessment_subtotal_cents`. Because the tiering is marginal rather than cliff-edged, 100 units assess 50000 cents and 101 units assess 50300 cents, not 30300.

The `surcharge_cents` is the subtotal multiplied by the category's surcharge rate and rounded half-up to whole cents. The rates are 0.10 for `INTEROP_DEFECT`, 0.35 for `SECURITY_DEFECT`, 0.25 for `FALSE_FEATURE_DECLARATION` and 0.00 for `IP_WITHDRAWAL`, so an auto-opened intellectual-property case always assesses a surcharge of 0. The `penalty_total_cents` is the lesser of the subtotal plus the surcharge and the hard cap of 5000000 cents. The cap applies to the total *only*: `assessment_subtotal_cents` and `surcharge_cents` are both stored uncapped, so a capped case is recognisable by its subtotal plus surcharge exceeding its total. Each case is priced in isolation from its listing's history and from its member's other cases.

Investigations advance under a `disposition`. `ESCALATE` moves the case `OPEN → EVIDENCE_REVIEW` and does nothing else. `ORDER_REMEDIATION` moves it `EVIDENCE_REVIEW → REMEDIATION_ORDERED`, requires `remediation_days` to be present and between 1 and 365 — the two halves of that requirement sitting on different rungs, so an absent, null or non-integer `remediation_days` is a shape failure answered with `ERR_INVALID_REQUEST` at rung 6, while a present integer outside 1 through 365 is answered with `ERR_INVALID_DATE_RANGE` at rung 9 — sets `remediation_deadline_at` to the logical clock's current instant advanced by that many days, and, where the listing's `publication_status` is `PUBLISHED`, suppresses it. `remediation_days` is an input only: it is consumed to derive `remediation_deadline_at` and is never stored on the case, so no case field echoes it back. Its conditional presence rule is tested against the literal string `ORDER_REMEDIATION` before rung 7 has judged the `disposition` enum, so a mis-cased `order_remediation` accompanied by `remediation_days` trips the must-be-absent branch and is answered with `ERR_INVALID_REQUEST`, whereas the same mis-cased value on its own reaches rung 7 and is answered with `ERR_INVALID_ENUM_VALUE`. A `remediation_days` supplied as JSON null counts as absent throughout, so it is accepted under every other disposition and refused under `ORDER_REMEDIATION`. `ORDER_WITHDRAWAL` moves it `EVIDENCE_REVIEW → WITHDRAWAL_ORDERED` and drives the listing to `publication_status` `WITHDRAWN` and `compliance_status` `NONCOMPLIANT`, revoking the linked submission's `dac_state` where it is `ISSUED` — the same enforcement package as an operator-filed listing withdrawal, reached down the case path instead. `CONFIRM_REMEDIATION` moves it `REMEDIATION_ORDERED → REMEDIATED`, requires the logical clock's current instant to be at or before `remediation_deadline_at` — an expired deadline being refused with `ERR_REMEDIATION_DEADLINE_PASSED`, with an instant exactly equal to the deadline accepted — and sets the listing's `compliance_status` to `REMEDIATED` while leaving `publication_status` at `SUPPRESSED`. A `disposition` the current `state` does not admit is refused with `ERR_INVALID_CASE_STATE`.

Closure is available only from `REMEDIATED` or from `WITHDRAWAL_ORDERED`, an attempt from any other state being refused with `ERR_INVALID_CASE_STATE`, and it is the second segregation-of-duties gate: the acting `X-User-ID` must differ from `opened_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. Because a system-opened case records `opened_by_user_id` as the literal `SYSTEM`, any compliance officer may close one. Closure sets `state` to the terminal `CLOSED`, records `closed_by_user_id` as the acting `X-User-ID`, and recomputes the member's `open_case_count` on the listing's member. Closure is the only case operation that recomputes that figure: an advance never does, so a case moved `REMEDIATION_ORDERED → REMEDIATED` leaves the member's stored `open_case_count` still counting it until that member is next recomputed for any reason at all.
