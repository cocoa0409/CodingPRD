# Same-Day Catalog Fulfillment API — Product Requirements Document

## 1. Introduction

Industrial and maintenance buyers judge a distributor by a single question: is the exact part on the shelf, in the right region, and on a truck today? This document specifies the API behind a catalog built for that question — a deep assortment in which every item carries standardized technical attributes, cross-referenced manufacturer part numbers, a dimensional drawing payload and a material specification, backed by inventory deliberately positioned across regional distribution centers so that the widest possible share of orders can still commit to same-day shipment.

The commercial pressure comes from the shape of the order rather than its size. A single maintenance order may carry dozens of cheap, small lines, and the cost of pulling those lines is what decides whether the order is profitable. Around that core sit the operational commitments a buyer is entitled to hold the distributor to: a visible price and live availability at the moment of order entry, a regional cutoff after which the same-day window closes, a freight figure that reflects both the weight and how close the order came to the wire, a restocking path for returned material, and a supplier base willing to hold minimum stock on the long-tail items that no distributor can afford to carry everywhere.

Order fulfillment here is a chain of custody. Data curation gates whether an item may be ordered at all; allocation decides which distribution center commits the units; picking may fall short, and a shortfall has to be dispositioned rather than silently dropped; the cutoff certifies the shipment; returns reopen both the inventory and the supplier ledger. Several sections of this document describe that chain, and each link both consumes and mutates state that other links depend on — which is why the rules below are stated as contracts even where the underlying workflow is operational rather than purely commercial.

The remainder of the document sets out the access model and the system-wide rules that apply to every operation (§2), the business workflows that carry the domain rules (§3), the endpoint surface itself (§4), and the error catalogue (§5).

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two headers, and only two: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the role the caller is acting in. If either header is absent, or if `X-User-Role` does not name one of the five declared roles, the request is rejected before anything else is evaluated with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the named role is not permitted to invoke the operation, the rejection is `ERR_UNAUTHORIZED` (HTTP 403).

Five roles exist, spelled exactly as follows:

- `PlatformAdmin` — the operator that manages distribution centers, suppliers and the logical clock.
- `CatalogCurator` — owns product data curation, standardized attributes, cross-references and supplier records.
- `CustomerAccount` — the purchasing account that searches the catalog, places orders and files returns.
- `WarehousePicker` — picks small-line orders and reopens picks after damage write-offs.
- `DCManager` — owns a distribution center's cutoff, posture, shipments, returns receiving and damage disposition.

The binding between `X-User-ID` and persisted data differs by role, and the difference matters for ownership checks. When `X-User-Role` is `CustomerAccount`, `X-User-ID` is the `id` of the acting `CustomerAccount`; ownership checks on any resource that references a `CustomerAccount` compare the resource's `account_id` (the account recorded on the order, or the account named when an order is opened) to `X-User-ID`, and a mismatch is rejected with `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403). This ownership comparison guards order creation, order release, order allocation, order cancellation and return-authorization creation. For the other four roles — `PlatformAdmin`, `CatalogCurator`, `WarehousePicker` and `DCManager` — `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it where the workflow calls for an actor identity, for example as `curation_last_reviewed_by` on the item a curator approves, but it is never compared against any entity's `id` and it confers no ownership over a resource. A `DCManager` acting on a return is therefore not screened by the ownership rule that screens the account that owns the order, even though both roles may open a return authorization.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list operation accepts `limit` and `offset` as query parameters. `limit` defaults to 10, must be at least 1 and may not exceed 100. `offset` defaults to 0 and counts the number of records to skip. When the caller supplies neither, the first ten records of the collection are returned. Lists are ordered by `created_at` ascending unless the operation's description says otherwise, and the `meta` block of a list response carries `limit`, `offset`, `total_count` and `has_more`; `has_more` is true when further records remain beyond the requested window. Some list operations also accept narrower filters as query parameters — an order, an item, a distribution center, an order line, a pick status, a claim status, a return status, a request, a review status, a delivery region (`home_region` or `region`), a supplier relationship (`long_tail_authorized`, `primary_attribute_name`, `primary_attribute_value`), a catalog filter (`q`, `material_spec`, `long_tail`, `catalog_status`, `supplier_id`) or an allocation filter (`allocated_dc_id`) — which are applied before the window is counted.

### 2.4. Identifiers, Timestamps and Record Versioning

Every persisted resource that carries the common field set exposes four properties. The `id` is a server-minted UUID string; it is never prefixed with a type marker, and clients must not depend on its internal structure. `created_at` is the instant the row was first persisted, expressed as an ISO 8601 UTC timestamp with three fractional digits (for example `2026-09-01T00:00:00.000Z`). `updated_at` is the instant of the row's most recent mutation, in the same format, and is refreshed by every write that touches the row. `version` is an integer that starts at 1 when the row is created and is incremented by exactly 1 by each write that mutates the row; it never decreases, and it is the value that optimistic concurrency compares against, as described in §2.7.

Five resource types do not carry the full common field set. `ClockTick`, `SupplierAvailabilityReport`, `CurationReviewItem`, `ItemAttribute` and `ItemCrossReference` expose only `id` and `created_at`; they have no `updated_at` and no `version`, and no write operation is expected to bump a version on them. This is deliberate: attribute rows and cross-reference rows are immutable after creation, so there is nothing about them for a version to protect, and the two membership-style rows (`SupplierAvailabilityReport` and `CurationReviewItem`) are write-once records of an event rather than mutable aggregates.

Callers should also expect that the parent-child relationships in this domain are not all expressed the same way. Some children are genuine aggregates that move with their parent, others are independent rows that merely name a parent. An order line, a pick task, a shipment, a return authorization and a damage claim all belong to a `CatalogOrder` and are addressed beneath it. A stock row belongs to an item and a distribution center at once, and an availability report belongs to a supplier while covering an item.

### 2.5. The Logical Clock and Regional Wall-Clock Cutoffs

Time in this system is a logical value, not the machine clock. The server holds a single `current_utc` instant, and at startup that instant is exactly `2026-09-01T00:00:00Z`. It is never replaced by wall-clock time, and it advances only when the platform administrator invokes the clock-setting capability with a supplied `current_utc` value. That capability responds with the `ClockTick` record, whose `current_utc` is the instant just set and whose `dc_local_times` map reports, for every distribution center, that center's local wall-clock time after the set.

Each distribution center carries a `utc_offset_minutes` value — the number of minutes its local clock leads UTC, constrained to the range from minus 480 to plus 840 — and a `local_zone`, an IANA zone name that is unique across all distribution centers. Setting the clock recomputes every center's `local_current_time` as `current_utc` plus that center's `utc_offset_minutes`, formatted as an `HH:MM:SS` wall-clock string; the field defaults to `00:00:00` before the first clock set. Two derived facts follow from that local time and only ever change when the clock is set: the `cutoff_passed` flag, and, through it, the same-day eligibility of the center during allocation. A center's `cutoff_passed` is true once its local weekday is a business day and its `local_current_time` is at or after its `local_cutoff_time`, a 24-hour `HH:MM:SS` value each center declares for itself. Note the asymmetry — `cutoff_passed` is recomputed only by the clock-setting capability, whereas the `cutoff_sequence_index` counter moves only when the center's daily cutoff period is rolled, as described in §3.8.

### 2.6. Money, Weight and Rounding Discipline

Money in this system is always an integer count of cents. Prices, subtotals, fees, surcharges, freight and reported damage exposure are all integer cent fields — `unit_price_cents`, `line_subtotal_cents`, `line_total_cents`, `allocated_small_line_fee_cents`, `total_small_line_fee_cents`, `order_total_cents`, `freight_rate_cents`, `freight_surcharge_cents`, `freight_charge_cents` and `damage_value_cents` — and no intermediate value is stored as a decimal. Wherever a fraction arises, the rule is round half up, applied to two decimal places' worth of precision and then carried as an exact integer. Rounding is not a blanket instruction to be applied once at the end of a pipeline; each formula pins its own rounding point, and the formulas in §3 are explicit about whether a figure is rounded per line, per order, or per shipment. The recurring failure mode this guards against is a corrected-looking total that is off by a cent or two because a rounding step was moved.

Weights are decimal kilograms and are the exception to the integer rule. An item's `unit_weight_kg` is a positive number, and the shipment's `billable_weight_kg` is the sum of the picked lines' weights rounded half up to two decimal places. Lengths in the pipe-commitment domain are integers expressed in feet, also rounded half up. Rounding half up means that an exact half-cent, half-kilogram-hundredth or half-foot is rounded away from zero to the next whole unit, not toward the nearest even value; the two-line pricing fixture described in §3.5 turns on precisely that tie.

### 2.7. Stale-Read Protection on Order Commitments

The order row is the object that several roles race to change, so two of its write operations are protected by an explicit version precondition, and the rest are not. The allocation of an order and the certification of its shipment cutoff both require a body field named `expected_order_version`, carrying the `version` of the `CatalogOrder` that the client last observed. If that value does not equal the order's current `version` at the moment the write is attempted, the write is rejected with `ERR_STALE_VERSION` (HTTP 412) and no other effect is applied. A client whose read is stale therefore cannot allocate lines that a concurrent revision has removed, and cannot certify a cutoff against a picture of what was picked that a later pick completion or re-pick has already invalidated. The field is not optional on either operation.

No other operation in this API takes a version precondition. Order release, order cancellation, pick start, pick completion, return approval and return receiving do not carry an `expected_order_version`, even though several of them do mutate the order; only the two operations named above are protected this way. The absence is deliberate rather than an oversight, and an implementation that demands a version field on any other write is out of contract.

### 2.8. Nested Resource Addressing

Resource paths are hierarchical, and their parameters are resolved left to right. Any operation addressed beneath an order resolves the order first and a nested line second: an order identifier that matches no `CatalogOrder` is rejected with `ERR_ORDER_NOT_FOUND` (HTTP 404) before the line identifier is even examined, and a line identifier that matches no line of that order is rejected with `ERR_LINE_NOT_FOUND` (HTTP 404). The same left-to-right discipline governs the other parents, each with its own not-found code — `ERR_ITEM_NOT_FOUND` for an unresolvable `CatalogItem`, `ERR_DC_NOT_FOUND` for an unresolvable `DistributionCenter`, `ERR_RETURN_NOT_FOUND` for an unresolvable `ReturnAuthorization` and `ERR_CLAIM_NOT_FOUND` for an unresolvable `DamageClaim`. This ordering is why a request that names both a bad order and a bad line reports the order failure.

The path parameters themselves are ordinary resource identifiers: `id` names the resource the path hangs from, and `line_id` names a specific line within an order. Body and query identifiers are never accepted as substitutes for a path parameter, and an operation whose path carries a `line_id` expects the line to belong to the order named earlier in the same path.

### 2.9. Rejection Order and Validation Precedence

When more than one rule would reject a request, the rejection that surfaces is the highest-priority one, and priority is fixed by the order below rather than by the order in which an implementation happens to evaluate its checks. The chain is deliberate in a few places: authentication precedes authorization, existence precedes ownership, and state legality precedes the version precondition, so a client receiveing a stale-version rejection can be sure the order really was in a state that permitted the transition.

1. **Authentication.** `X-User-ID` and `X-User-Role` must both be present and `X-User-Role` must name a declared role; otherwise `ERR_UNAUTHENTICATED` (401). This applies to every operation.
2. **Authorization.** The calling role must be permitted to invoke the operation; otherwise `ERR_UNAUTHORIZED` (403). This applies to every operation.
3. **Existence.** Every resource referenced in the path must resolve, validated left to right in path order, as described in §2.8. The code is the not-found code of the unresolvable entity — `ERR_ORDER_NOT_FOUND`, `ERR_LINE_NOT_FOUND`, `ERR_ITEM_NOT_FOUND`, `ERR_DC_NOT_FOUND`, `ERR_RETURN_NOT_FOUND` or `ERR_CLAIM_NOT_FOUND` (all HTTP 404). This check guards order release, order allocation, pick start, pick completion, cutoff certification, order cancellation, return approval, return receiving and claim resumption.
4. **Ownership.** The account behind the action must own the order — the order's `account_id` must equal `X-User-ID` — otherwise `ERR_FORBIDDEN_OWNERSHIP` (403). This guards order release, order allocation, order cancellation and return-authorization creation.
5. **Terminal state.** The target resource must not already sit in one of its declared terminal states; otherwise `ERR_ALREADY_TERMINAL` (409). This guards every state-transition operation whose target entity declares terminal states: `CatalogOrder` (terminal states `CANCELLED` and `RETURNED`), `PickTask` (`PICKED` and `SHORT_CLOSED`), `Shipment` (`DISPATCHED`), `ReturnAuthorization` (`RECEIVED` and `CANCELLED`), `DamageClaim` (`RESOLVED`, `REJECTED` and `VOIDED`) and `SquareFootageRequest` (`FULFILLED` and `RETURNED`).
6. **State legality.** The target resource must be in a state that permits the operation, and the transition must be one the state machine lists for that state; otherwise `ERR_INVALID_STATE` (409). This guards every state-transition operation.
7. **Stale version.** The body's `expected_order_version` must equal the order's current `version`; otherwise `ERR_STALE_VERSION` (412). This guards order allocation and cutoff certification, and only those two.
8. **Distribution-center posture.** The allocated center must not be in posture `LOCKDOWN`; otherwise `ERR_DC_LOCKDOWN` (409). This guards pick start.
9. **Resumed item suspension.** The item whose units are being resumed must not have `catalog_status` `SUSPENDED`; otherwise `ERR_ITEM_SUSPENDED` (409). This guards claim resumption.
10. **Curation gate.** The item's `curation_review_state` must be `APPROVED`; otherwise `ERR_CURATION_NOT_APPROVED` (409). This guards order release and order creation.
11. **Candidate membership.** The order's allocated center must be a member of the candidate set produced by the allocation selector; otherwise `ERR_DC_NOT_CANDIDATE` (409). This guards cutoff certification.
12. **Delivery window.** The order's committed delivery deadline must not fall on or before any candidate center's `local_cutoff_time`, judged on the local weekday first and the local wall-clock time second; otherwise `ERR_CUTOFF_WINDOW_PASSED` (422). This guards order creation and order allocation.
13. **Promise date.** The requested `promised_delivery_by` must not lie in the past relative to the center's local clock; otherwise `ERR_PROMISE_DATE_IN_PAST` (422). This guards cutoff certification.
14. **Return part number.** Every claimed return unit must carry a `removed_manufacturer_part_number`; otherwise `ERR_RETURN_PART_NUMBER_REQUIRED` (422). This guards return receiving.
15. **Inbound capacity.** The allocation must not push the center's `inbound_reserved_units` past its `inbound_capacity_units`; otherwise `ERR_INBOUND_CAPACITY_EXCEEDED` (409). This guards order allocation.
16. **Supplier candidate availability.** At least one supplier must survive the supplier selector's eligibility filter; otherwise `ERR_SUPPLIER_CANDIDATE_EMPTY` (409). This guards availability-report filing.

Separately from this chain, a request whose payload is malformed is rejected with `ERR_INVALID_REQUEST` (400) whenever a required body field is missing or a supplied value fails the type or range constraint declared for it — a `quantity` below 1, a `code` that is not two to eight uppercase characters, a `utc_offset_minutes` outside the range from minus 480 to plus 840, a `unit_price_cents` below 1, a `unit_weight_kg` that is not strictly positive, or a `cut_list_ordinal` below 1, to name the constraints this catalog declares.

### 2.10. Controlled Vocabularies Across the Catalog

Several fields are closed enumerations, and their values are case-sensitive strings. A distribution center's `region`, and a customer account's `home_region`, are one of `NORTHEAST`, `SOUTHEAST`, `MIDWEST`, `SOUTHWEST` or `WEST`. A center's `operations_posture` is one of `OPEN`, `RESTRICTED` or `LOCKDOWN`. An item's `catalog_status` is `ACTIVE` or `SUSPENDED`, and its `curation_review_state` is `UNREVIEWED` or `APPROVED`. A curation review batch's `review_status` is `OPEN` or `REVOKED`. An order's `order_status` is `DRAFT`, `RELEASED` or `CANCELLED`, and its `fulfillment_status` is one of `AWAITING_RELEASE`, `ALLOCATED`, `PICKED`, `SHIPPED` or `RETURNED` — the two dimensions evolve independently, as §3.3 and §3.6 describe. An order line's `line_status` is one of `PENDING`, `ALLOCATED`, `PICKED`, `SHORT`, `RESTOCKED` or `RETURNED`. A pick task's `pick_status` is one of `QUEUED`, `PICKING`, `PICKED` or `SHORT_CLOSED`, and its `shortage_disposition` is `NONE` or `MADE_TO_ORDER`. A shipment's `shipment_status` is one of `STAGED`, `CUTOFF_CONFIRMED`, `DISPATCHED` or `HELD`, and its `service_level` is `GROUND`, `TWO_DAY` or `OVERNIGHT`. A return authorization's `return_status` is one of `DRAFT`, `APPROVED`, `RECEIVED` or `CANCELLED`. A damage claim's `claim_status` is one of `OPEN`, `RESUMED`, `RESOLVED`, `REJECTED` or `VOIDED`, and its `disposition` is one of `PENDING`, `REPLACE_FROM_STOCK` or `ZERO_CHARGE_RESHIP`. A stock row's `positioning_flag` is `OK`, `UNDERSTOCKED` or `LONG_TAIL_DEFICIT`. A square-footage request's `request_status` is `QUOTED`, `CUTTING`, `FULFILLED` or `RETURNED`, its `committed_variant` is `FORWARD_LOOKING` or `ON_HAND_ONLY`, and its cut lines carry a `line_status` of `PLANNED` or `CUT`.

## 3. Business Logic & Workflows

### 3.1. Curation: Turning Raw Catalogue Data into Orderable Items

Nothing in this catalog may be ordered until a curator has certified its data. A `CatalogCurator` opens an item by supplying its `sku` (unique across the catalog), a short `description`, a `material_spec` such as 18-8 stainless steel, a `long_tail` flag that marks the item as sourced from a long-tail supplier on minimum-stock commitment, a `unit_price_cents` of at least 1, a strictly positive `unit_weight_kg`, a `curation_bundle_size` declaring how many dimensional attributes are bundled into one review batch, and a `curated_dimension_json` payload carrying the dimensional drawing. The drawing payload is expected to hold `nominal_length_mm`, `nominal_width_mm`, `nominal_height_mm` and `drawing_revision`. A newly created item starts with `catalog_status` `ACTIVE` and with `curation_review_state` `UNREVIEWED`; its `curation_last_reviewed_by` is empty until a curator first approves it.

Standardized technical attributes are attached one row at a time. Each attribute row names an `attribute_name` and an `attribute_value`, both of which must be unique within their item, and a `unit_of_measure` expressing the value's unit. Attribute rows are immutable once written: neither the name, the value nor the owning `item_id` may be revised later, and an attempt to attach a second row whose name or value collides with an existing row of the same item is rejected. Cross-references work the same way — a curator attaches a `referenced_manufacturer`, a `referenced_part_number` and a `compatibility_note` describing how the alternate part relates to this item, and the row is frozen thereafter under the `item_id` it was written against.

Approval happens at the batch level rather than item by item. Submitting a curation batch takes a set of `item_ids` and opens a `CurationReview` whose `curator_id` records the opaque identifier of the curator who filed it and whose `review_status` starts `OPEN`. Every submitted item must already carry at least one attribute row — an item with no attribute rows blocks the whole submission with `ERR_CURATION_ATTRIBUTES_MISSING` (HTTP 409) — and every item's `curated_dimension_json` must carry a non-null `drawing_revision`; a drawing with no revision cannot be certified. When the batch is accepted, each named item's `curation_review_state` moves `UNREVIEWED → APPROVED`, and each item's `curation_last_reviewed_by` is set to the calling curator's `X-User-ID`. The batch itself records how many items it approved the last time it was submitted in `approved_count`, counts its revision rounds in `bundle_level_revision`, and holds `revision_round_baseline`, the `approved_count` captured at the batch's first revision round, which stays 0 until the batch has been revised at least once. Each membership row in the batch, listing one `item_id` under its `review_id`, tracks `item_level_revision` for how many rounds that particular item has taken part in and `item_attribute_counter`, the count of standardized attributes the item carried at the time of the last review.

Approval is reversible in both directions, and the reversals are ordinary state transitions rather than exceptions. A curator may revoke a batch's approval, which moves `review_status` to `REVOKED` and returns every item in the batch to `curation_review_state` `UNREVIEWED`, so the items stop being order-selectable until they are approved again. An item that is already `APPROVED` may also be submitted for review again after a dimension revision; a re-review of an already-approved item is accepted only while the counter values of every one of its attribute rows are unchanged, and its effect is to refresh `curation_last_reviewed_by` to the curator performing the re-review. An item cannot be approved while its `catalog_status` is `SUSPENDED` for damage reasons without first being reinstated by the workflow in §3.9.

The gate this all serves is stated in a single rule: an order may only be released — and only be created — when every line's item has reached `curation_review_state` `APPROVED`. A line whose item is still `UNREVIEWED` blocks the operation with `ERR_CURATION_NOT_APPROVED` (HTTP 409). This is why curation approval, not item creation, is the true entry point to the sales catalogue: an item can exist, carry attributes and cross-references, and still be invisible to ordering for as long as nobody has approved it.

### 3.2. Suppliers, Long-Tail Commitments and the Availability Report

Long-tail items are the ones a distributor cannot economically stock everywhere, so the supplier itself takes on a stocking obligation. A supplier record carries a `supplier_name`, a `home_dc_id` naming the distribution center the supplier's commitment stocks, and a `primary_attribute_name` paired with a `primary_attribute_value` — the standardized attribute the supplier is contracted to hold. A `min_stock_commitment_units` value (at least 0) states how many units the supplier commits to hold at each stocking center, and a `long_tail_authorized` flag states whether the supplier is permitted to hold minimum-stock commitments for long-tail items at all. A supplier begins life with `commitment_breach_count` 0 and `performance_rating_units` 100.

Suppliers report their own availability, one report at a time, and each report is a write-once record rather than an updatable field. Filing a report supplies the `item_id` of the long-tail item the report covers and a `reported_available_units` count of at least 0; the report is stamped with the `supplier_id` of the filing supplier. Filing a report immediately runs the supplier selector, and the selector ranks surviving candidates by `performance_rating_units` in descending order, breaking ties by `created_at` ascending. The eligibility filter admits only suppliers that are `long_tail_authorized` and whose `min_stock_commitment_units` is at least the `reported_available_units` just filed for the item — that is, only suppliers whose commitment covers the units they are claiming to hold. If no supplier survives the filter, the filing is rejected with `ERR_SUPPLIER_CANDIDATE_EMPTY` (HTTP 409). The winning supplier is the one returned to the caller.

The breach ledger is what keeps the commitment meaningful. The performance rating is not an independent field that a human tunes; it is derived entirely from the breach counter by the fixed expression `performance_rating_units := 100 - 10 * commitment_breach_count`, so every additional breach costs exactly ten rating points and the rating is always recomputed from the counter rather than decremented in place. A breach is recorded against a supplier in either of two circumstances: filing an availability report whose `reported_available_units` falls below that supplier's own `min_stock_commitment_units` increments its `commitment_breach_count` by 1 and recomputes `performance_rating_units` from the new counter; and, separately, when a long-tail item is received back through the return cascade described in §3.9, the supplier behind that item takes a breach and has its rating recomputed the same way. Rating never recovers on its own — only a breach moves it, and it moves only downward.

### 3.3. Order Entry, Line Pricing and the Release Cycle

A `CustomerAccount` builds an order by supplying the `account_id` it is ordering under together with the complete set of `lines`, and optionally a `promised_delivery_by` date if the account needs a delivery commitment. Each line names an `item_id` and a `quantity` of at least 1, and each line's `line_subtotal_cents` is its `allocated_units` multiplied by its item's `unit_price_cents` — so the figure is 0 until the line is allocated, and it falls back to 0 whenever the allocation is unwound. The order is created as a draft: `order_status` begins `DRAFT` and `fulfillment_status` begins `AWAITING_RELEASE`, the two dimensions being independent axes on the same row as §3.6 explains. Creating an order runs the pricing calculations of §3.5 immediately, so a fresh draft already carries a meaningful `order_total_cents`, and it recomputes the line-count guard that keeps `line_count` equal to the number of `CatalogOrderLine` rows on the order. Two gates apply at creation: every line's item must be curated to `APPROVED` (`ERR_CURATION_NOT_APPROVED`, 409), and the committed delivery deadline must not fall on or before any candidate center's `local_cutoff_time` (`ERR_CUTOFF_WINDOW_PASSED`, 422).

A draft is not yet a commitment. Releasing it is what converts the draft into an allocatable order, and the release is gated twice over: the order's `order_status` must currently be `DRAFT`, and every line's item must have `curation_review_state` `APPROVED`. A successful release sets `order_status` to `RELEASED`, leaves `fulfillment_status` at `AWAITING_RELEASE`, and increments the order's `version` by 1 — the first of the version bumps that §2.7's stale-read protection will later compare against.

The cycle between draft and released is not a one-way door. A released order that has not yet been allocated may be sent back to draft — for example when the account revises its arguments or partially cancels lines before anything has been reserved — which returns `order_status` to `DRAFT` and puts every line back to `line_status` `PENDING`, incrementing the order's `version` by 1. Such an order may then be released again, and this may repeat any number of times; the pair of states forms a loop rather than a monotone progression. Clients should not assume that an order they observed in `RELEASED` is still there — the version precondition on allocation exists precisely because a release, a revision cycle or a cancellation can move the row between a client's read and its write.

Cancellation is available from three distinct situations, and each one does a different amount of work. A draft order that has never been released cancels trivially: `order_status` becomes `CANCELLED` and the version bumps, with no inventory to unwind. A released order that is still `AWAITING_RELEASE` cancels just as simply, because nothing has been reserved. A released order that is already `ALLOCATED`, however, must give its reservations back: for every line still in `line_status` `ALLOCATED`, the units reserved at that line's distribution center are released, so the stock row's `reserved_units` is decremented by `allocated_units` and its `available_units` recomputed, and the center's `inbound_reserved_units` is reduced by the total released. Every line then returns to `line_status` `PENDING` with `allocated_units` reset to 0, `fulfillment_status` returns to `AWAITING_RELEASE`, `order_status` becomes `CANCELLED`, and the order's `version` increments by 1. In all three cases the resulting order_status is the terminal value `CANCELLED`, and in all three the order's two pricing passes are re-run over the lines as they now stand — no line holds allocated units at that point, so `total_small_line_fee_cents` and `order_total_cents` both settle at 0.

### 3.4. The Allocation Selector: Choosing a Distribution Center

Allocation is the moment an order stops being a request and starts holding stock. It is available on an order whose `order_status` is `RELEASED`, from the `AWAITING_RELEASE` fulfillment state, and it moves the order to `RELEASED / ALLOCATED`. The request must carry `expected_order_version` matching the order's current `version`; a mismatch is `ERR_STALE_VERSION` (HTTP 412) and nothing else is attempted, because the set of lines to allocate may itself have changed since the client read the order. Before the selector runs, the delivery-window rule is re-checked (`ERR_CUTOFF_WINDOW_PASSED`, 422), and before the order is committed the center's remaining inbound headroom is checked: if the allocation would push the center's `inbound_reserved_units` past its `inbound_capacity_units`, the allocation is refused with `ERR_INBOUND_CAPACITY_EXCEEDED` (HTTP 409).

The account placing the order is itself a record, created by the platform administrator with an `account_name`, a `delivery_zone` giving the IANA zone of the account's shipping address, and a `home_region` naming the region that address sits in. The `delivery_zone` is what decides the zone surcharge on freight, as §3.7 describes, and the `home_region` is what the selector's region filter compares against. Accounts may be listed and read, optionally narrowed by `home_region`.

The selector itself works in three stages — a filter, a ranking and a tie-break — and all three matter. The candidate set is every `DistributionCenter` satisfying both of two conditions at once: the center's `region` must equal the ordering account's `home_region`, and, for every line of the order, the stock row for that line's item at that center must have `on_hand_units` at least the line's `quantity`. A center that cannot cover even one line in full is not a candidate, no matter how strong it looks on the others. The surviving candidates are ranked by estimated total delivery time in seconds, and the smallest total wins. That estimate is built from three terms added together: a full day of 86,400 seconds when the center's `cutoff_passed` flag is true, since a center past its cutoff cannot make today's dispatch; a cross-region penalty of 28,800 seconds whenever the center's `region` is not the account's `home_region`; and the center's own `transit_seconds`. When two candidates tie on that estimate, the tie is broken first by `cutoff_sequence_index` descending and then by `created_at` ascending. If the candidate set is empty, the allocation fails with `ERR_NO_ELIGIBLE_DC` (HTTP 409).

Committing the allocation has a wide footprint, because an order is only as real as the units it holds. The chosen center's identifier is written to the order's `allocated_dc_id`; each line receives that same center as its `allocated_dc_id`, has its `allocated_units` set to the full requested `quantity`, and moves to `line_status` `ALLOCATED`. At the center, each affected stock row has `reserved_units` increased by the units allocated to it and `available_units` recomputed as the difference between `on_hand_units` and `reserved_units`, and the center's `inbound_reserved_units` grows by the total units allocated across the order. The order's own `same_day_committed` flag is then set: it is true when at least one eligible candidate center still had `cutoff_passed` false at the moment of selection — that is, at least one center was still ahead of its local cutoff — and false otherwise, which is the system's way of recording that the order was committed too late to make today's dispatch. The two order-level pricing passes of §3.5 run immediately after the commit — the small-line handling calculation over the newly eligible lines, and the order-total calculation, which before certification takes the own-precision fee term — and the line-count guard is recomputed into `line_count`. The order's `version` increments by 1, which is exactly the bump that will make a client who read the order before allocation stale for the cutoff-certification step later.

A detail that consistently surprises callers: availability is aggregated without regard to cutoff. When the live availability for an item at a center is read, it is that center's stock row's `available_units`, which is its `on_hand_units` minus its `reserved_units`. When availability is aggregated across all centers for an item, the total sums the difference between on-hand and reserved units over those rows whose `available_units` is greater than zero, and rows with no availability contribute nothing. Critically, this aggregate does not exclude rows whose center has `cutoff_passed` true — a center that can no longer ship same day still counts toward displayed availability. Only the selector's delivery-time estimate penalizes a passed cutoff; display availability does not.

A stock row is recorded explicitly by a `DCManager`, supplying the `item_id`, the `dc_id` holding the units, the `account_id` whose order consumes the row, the `on_hand_units` on the shelf, and two figures from the most recently completed cutoff period: `daily_demand_units`, the units the pick engine consumed at that center during the period, and `inbound_daily_units`, the units replenished into the center during the period. Both period figures must be at least 0. The row's `reserved_units` begins at 0 and grows only through allocation, its `available_units` begins equal to `on_hand_units` and is recomputed on every reservation, pick and restock, and its `positioning_flag` is left unset until the center's daily cutoff roll classifies it.

### 3.5. Small-Line Handling Fees and the Order Total

Orders here are typically many cheap lines, and the handling fee is the mechanism that makes such orders economic. It is also the most intricate piece of arithmetic in the system, so it is stated here in full, with every rounding point pinned to where it belongs.

Eligibility comes first, and it is fixed by line status rather than by any flag a caller sets. Only lines in `line_status` `PENDING`, `ALLOCATED` or `PICKED` participate in any pricing calculation. A line in `SHORT`, `RESTOCKED` or `RETURNED` is excluded from every variant, and its `allocated_small_line_fee_cents` is cleared to 0 rather than left standing at a stale figure. A line's `is_small_line` flag records whether its `quantity` is at most the `curation_bundle_size` of its item, but the fee arithmetic below is driven by the live line status and the item's bundle size, not by reading that flag back.

The per-line raw fee is computed at step one of the handling calculation. For each eligible line, if the line's `quantity` is at most its item's `curation_bundle_size`, the line's raw fee is the line's `line_subtotal_cents` multiplied by a base handling rate of 0.10, rounded half up to the cent; otherwise the raw fee is 0. Rounding happens here, once per line, and nowhere else in the per-line step. Step two applies an order-level threshold reduction: if the number of eligible lines is at least 5 — the small-line count threshold — then each eligible line's raw fee is reduced by 250 cents, floored at 0 so a fee never becomes negative. Step three pins a rounding order that an implementation must not reorder: the order-level pool `D` is the sum over eligible lines of the reduced raw fees, an order-level discount is computed by multiplying `D` by 0.37 and rounding half up to the cent, and the order's total handling fee is `D` minus that discount. The pool is rounded once, at this point, and never again. The pool exists only once the count threshold has fired, though: when fewer than five lines are eligible, no reduction applies and the handling total is instead the sum over the eligible lines of the fee at each line's own precision — its `line_subtotal_cents` multiplied by the small-line fee rate of 0.03, rounded half up to the cent — with no order-level discount taken at all. Whichever basis produced it, that handling figure is what the order's `total_small_line_fee_cents` holds.

Step four distributes that total across the eligible lines by largest remainder. The allocation order is by `line_subtotal_cents` descending, ties broken by `created_at` ascending; each line first receives an integer floor-division share of the total, and the leftover cents produced by the flooring are handed out one cent at a time to the lines at the front of that order. Step five writes the outcome: the order's `total_small_line_fee_cents` holds the total fee, and each eligible line's `allocated_small_line_fee_cents` holds its share. Each line's `line_total_cents` is its `line_subtotal_cents` plus its `allocated_small_line_fee_cents`, so a line outside the eligible set — whose fee share has been cleared to 0 — carries its subtotal alone. Step six is a prohibition rather than a computation — this total fee is the fee term used by the order-total calculation that applies once a shipment cutoff is certified, and that calculation must never add a second fee computed on some other basis. The order-level discount rate of 0.37 deliberately does not appear in the order-total formula described below; keying a fee on a tier of the total it is itself part of produces a circular value whose result depends on which side is evaluated first, and the fee is never keyed on the total.

That order-total calculation runs in two variants, and they differ only in how the fee term is produced. Both share step one, which is also shared with the handling calculation above because the material subtotal and the full-curation handling fee live in one pricing domain. Given the eligible lines, `S` is the sum of their `line_subtotal_cents`; the discounted material base is `S` multiplied by a catalog discount factor of 0.97, rounded half up to the cent, once for the order. For a single line, the fee at its own precision is the line's `line_subtotal_cents` multiplied by a small-line fee rate of 0.03, rounded half up to the cent. The first variant, which applies while the order is being quoted, allocated or picked and before its shipment cutoff has been confirmed, sums that per-line own-precision fee across every eligible line and adds the sum to the discounted material base — the fee basis here is a flat 3 per cent of each line's `line_subtotal_cents`. The second variant, which applies once `shipment_status` has become `CUTOFF_CONFIRMED` and the order is re-priced, uses instead the handling figure produced by the calculation above, whose per-line step-one rounding sits on a different fee basis and whose per-line figures are then corrected by the order-level reduction, so the fee term differs from the first variant whenever the order qualifies for the count reduction. Either way the order total is the discounted material base plus the fee term, and the precision rule holds throughout: the material base rounds once for the order, each variant's fee term rounds in its own way, and neither is rounded again when they are added.

A concrete illustration makes the divergence visible. Take five eligible lines with `line_subtotal_cents` of 36000, 18000, 7000, 6000 and 5000 — a material subtotal of 72000 cents. The discounted material base is 72000 multiplied by 0.97, which is 69840 cents, identical under both variants because it is computed before the fee term. Under the own-precision variant the per-line fees are 1080, 540, 210, 180 and 150 cents, summing to a fee term of 2160 cents and an order total of 72000 cents — and it is no accident that the total equals the undiscounted subtotal, since the 3 per cent fee and the 97 per cent discount were designed to offset exactly on faces this large. Under the handling-pool variant on the very same lines the fee term becomes 3748 cents and the order total becomes 73588 cents; the identical order moves from 72000 to 73588 purely because the cutoff has been certified. The reason is the difference in fee basis and the count reduction working together: at the base handling rate of 0.10 the raw per-line fees are 3600, 1800, 700, 600 and 500 cents, the 250-cent count reduction — which applies because there are at least five eligible lines — takes the order-level pool `D` down to 5950 cents, and the 0.37 order-level discount of 2202 cents leaves a fee term of 3748 cents, a basis far different from a flat 3 per cent of each line's `line_subtotal_cents`.

Precision at the tie is equally load-bearing, and a two-line case demonstrates why the evaluation order matters. Take two eligible lines of 1000 cents each. The discounted material base is 2000 multiplied by 0.97, which rounds half up to 1940 cents. Each line's own-precision fee is 1000 multiplied by 0.03 — exactly 30 cents, no rounding needed — for a fee term of 60 cents and an order total of 2000 cents. Had the fee instead been sized off the already-discounted line, the arithmetic would have been 0.97 multiplied by 0.03 and then by 1000, giving 29.1 cents per line, which rounds half up to 29 cents, for a fee term of 58 cents and a total of 1998 cents — a two-cent error introduced purely by evaluating the discount before the fee. The pinning is the point: the fee is computed on the line's own `line_subtotal_cents`, before the discount, and rounding half up is applied once per eligible line and once on the discounted material base, never on the sum.

### 3.6. Picking, Shortages and the Damage Claim

Once an order is allocated, a `WarehousePicker` pulls it line by line. Starting a pick on one allocated line records a `PickTask` for that line: the picker supplies a `requested_units` count of at least 1, and the task is opened against the order, the line and the center the picker works in through the task's `line_id` and `dc_id`. Three conditions must hold before a pick may start: the order's `fulfillment_status` must be `ALLOCATED`, the line's pick task must be in `pick_status` `QUEUED`, and the allocated center's `operations_posture` must not be `LOCKDOWN` — a center under lockdown refuses new picks with `ERR_DC_LOCKDOWN` (HTTP 409), because the material in it is not cleared for release. A successful start moves the task's `pick_status` from `QUEUED` to `PICKING`; the standardized attribute rows of the line's item are immutable throughout and are not touched by picking. Internally, the task's opening is a state move from `QUEUED` to `PICKING` that is only legal while the line's `line_status` is `ALLOCATED`.

Completing a pick is where the reality of the shelf enters the order. The picker reports the units actually pulled as `actual_units`, and the task records `picked_units` as that value and computes `shortage_units` as `requested_units` minus `actual_units` when the pick fell short, and as 0 otherwise. Note that a short pick is not an error: the completion proceeds whether or not there is a shortage, and it is the shortage, if any, that downstream rules react to. On completion the center's stock row for the line's item has its `on_hand_units` reduced by the `picked_units` actually pulled — not by the units requested — and its `available_units` recomputed. The reservation that held those units is consumed along with them, so `reserved_units` falls by the same `picked_units` figure, never below 0, and `available_units` is recomputed as `on_hand_units` minus `reserved_units`; the part of the reservation a shortfall did not fill stays reserved against the line. The line's `line_status` becomes `PICKED` when `shortage_units` is 0, and `SHORT` when it is not; when the line becomes `SHORT`, its `allocated_small_line_fee_cents` is cleared to 0, and both order-level pricing passes — the handling-fee calculation and the order-total calculation — are recomputed so the order's totals and each line's allocation of the fee reflect the new eligibility. Finally, when every line of the order has reached `line_status` `PICKED` or `SHORT`, the order's `fulfillment_status` advances to `PICKED`, and the order's `version` increments by 1.

The task's own `pick_status` follows the size of the shortfall: a task whose picked units equal the requested units lands in `PICKED`, and one that came up short lands in `SHORT_CLOSED`. Both are terminal for the task. The `shortage_disposition` field records how the shortfall is to be handled, and its only non-default value is `MADE_TO_ORDER`. It is set to `MADE_TO_ORDER` when a line's `shortage_units` is greater than 0, the line's item has `long_tail` true, and no other line of the same order carries a shortage on a non-long-tail item — the rule being that a shortfall on long-tail material is something the supplier can make good, and it can only be treated that way when the order has no competing shortfall on ordinary stock.

A shortage on ordinary stock takes a different path and creates a `DamageClaim`. When a line's `shortage_units` is greater than 0 and the line's item has `long_tail` false, a claim is opened against the order and that line, carrying a `claim_units` count that is permitted to be 0 — a claim may legitimately assert that nothing was recoverable — and the owning account's `open_claim_count` is incremented by 1. A claim starts with `claim_status` `OPEN` and `disposition` `PENDING`. Every claim also carries a computed `damage_value_cents` reporting the exposure: the claimed units multiplied by the item's `unit_price_cents` and then by a damage value factor of 0.60, rounded half up to a whole cent. That figure is a reported exposure only — it is never added into the order's `order_total_cents`, as §3.9 reiterates.

A short-closed pick is not necessarily final. While the order's `fulfillment_status` is still `ALLOCATED` and the line's damage claim is still `OPEN`, the picker may start a fresh pick on the same line, which moves the line's `line_status` back to `ALLOCATED`, returns the task from `SHORT_CLOSED` to `PICKING`, and increments the order's `version` by 1. This is the mechanism by which a damaged pick is written off and the line re-attempted, and it cycles: a task may be short-closed and reopened any number of times for as long as the order has not moved past `ALLOCATED`.

The claim's own lifecycle then proceeds under `DCManager` control, with one exception. A picker may resume fulfillment of a claim, which is only permitted while the item's `catalog_status` is `ACTIVE`; a suspended item cannot have fulfillment resumed against it, and the attempt is rejected with `ERR_ITEM_SUSPENDED` (HTTP 409). A successful resumption moves the claim from `OPEN` to `RESUMED` and reverts the order — `fulfillment_status` back to `ALLOCATED` and the line's `line_status` back to `ALLOCATED` — so the units may be picked again. From `RESUMED`, a manager may resolve the claim, which sets `claim_status` `RESOLVED` and `disposition` `ZERO_CHARGE_RESHIP` and decrements the account's `open_claim_count` by 1. From `OPEN` directly, a manager may reject the claim, which sets `claim_status` `REJECTED` and `disposition` `REPLACE_FROM_STOCK` and also decrements the account's `open_claim_count`. From `RESUMED`, a manager may instead void the claim, setting `claim_status` `VOIDED` and decrementing the account's `open_claim_count`. All three terminal outcomes return the account's open-claim counter toward zero, and the counter tracks only claims in non-terminal states.

An order tracks its own damage activity in `damage_claim_count`, the number of `DamageClaim` rows attached to it that are in a non-terminal state. Like the account's counter, it rises when a claim is opened and falls when the claim reaches `RESOLVED`, `REJECTED` or `VOIDED`; it is a live count rather than a lifetime total, and it never enters any monetary calculation.

### 3.7. Cutoff Certification, Freight and Dispatch

An order whose units are picked is ready to be certified against a distribution center's cutoff, and the certification is a `DCManager` responsibility. The request supplies `expected_order_version`, a `service_level` draw from `GROUND`, `TWO_DAY` or `OVERNIGHT`, and optionally a `promised_delivery_by` date if the account wants a delivery commitment recorded. Four conditions gate the operation: the order's `fulfillment_status` must be `PICKED`; its shipment must be in state `STAGED`; the `expected_order_version` supplied must equal the order's current `version`, with a mismatch rejected as `ERR_STALE_VERSION` (HTTP 412); and the order's allocated center must be a member of the candidate set produced by the allocation selector, with a center outside that set rejected as `ERR_DC_NOT_CANDIDATE` (HTTP 409). A `promised_delivery_by` that lies in the past relative to the center's local clock is rejected as `ERR_PROMISE_DATE_IN_PAST` (HTTP 422). A successful certification moves the shipment to `CUTOFF_CONFIRMED`, stamps the shipment's `cutoff_sequence_index` with the center's current `cutoff_sequence_index`, moves the order's `fulfillment_status` from `PICKED` to `SHIPPED` while `order_status` stays `RELEASED`, and increments the order's `version` by 1.

Freight is priced at certification, and it is priced in two layers. The first layer produces the shipment's `freight_rate_cents` from the shipment's `billable_weight_kg`, which is the sum over the order's lines of each line's `allocated_units` multiplied by its item's `unit_weight_kg`, rounded half up to two decimal places. The rate is tiered on that weight. A shipment weighing less than 25.0 kilograms takes a base rate of 450 cents. A shipment weighing at least 25.0 but less than 100.0 kilograms takes 450 cents plus 28 cents for each whole kilogram — rounded up — by which the weight exceeds 25.0. A shipment of 100.0 kilograms or more takes 450 cents, plus 28 cents for each of the 75 whole kilograms between 25.0 and 100.0, plus 19 cents for each whole kilogram — rounded up — by which the weight exceeds 100.0. A zone surcharge is then added: 0 cents when the center's `local_zone` is the account's `delivery_zone`, and 275 cents when it is not. An urgency multiplier is then applied to the sum of base rate and zone surcharge, and this is where the timing of the order matters. If the order's `same_day_committed` flag is false, the multiplier is 1.0 — the order missed today's dispatch and pays no urgency premium. Otherwise, if the order's `commit_minutes_before_cutoff` is at least 120 minutes, the multiplier is 1.1; and if it is less than 120 minutes, the multiplier is 1.6. The resulting product is rounded half up to a whole cent, and that is the shipment's `freight_rate_cents`. The tier selection rounds once on the weight delta, and the urgency step rounds once more on the whole; the two are never collapsed into a single rounding.

Two things drive that multiplier, and both are worth restating. The `commit_minutes_before_cutoff` value on the order is the number of minutes between the allocated center's `local_current_time` at the moment of allocation and that center's `local_cutoff_time`, saturated at 0 — an order committed at or after the cutoff records 0 rather than a negative figure. It is the urgency input to the freight calculation, and it is ignored entirely when `same_day_committed` is false.

The rate calculation admits two variants that differ only in the urgency term. The estimate variant applies before cutoff confirmation, for the order acknowledgement page, and is used when the order was allocated with at least one candidate center still ahead of its local cutoff; in this variant the urgency multiplier is pinned to 1.1 and the order's `commit_minutes_before_cutoff` is ignored entirely. The certified variant applies at certification, is the one recorded on the shipment, and applies the full three-way rule above. On identical weight, zone and account, the estimate gives 798 cents where the certified figure gives 1160 cents, and the difference is exactly the estimate's flat 1.1 versus the certified 1.6 that applies when the order is `same_day_committed` true and its `commit_minutes_before_cutoff` is below the 120-minute threshold.

The second freight layer converts the rate into the charge the account sees. The shipment's `freight_rate_cents` is multiplied by a surcharge rate drawn from the shipment's `service_level`: 0.00 for `GROUND`, 0.30 for `TWO_DAY` and 0.60 for `OVERNIGHT`. That product is rounded half up to a whole cent and becomes the shipment's `freight_surcharge_cents`. The shipment's `freight_charge_cents` is then the rate plus the surcharge, and it is the single authoritative freight figure — it is mirrored onto the order as `freight_charge_cents`, and no separate freight total exists that could drift from it. The surcharge is rounded per shipment, never summed across shipments and then rounded. Once certified, the same assignment that sets `shipment_status` also recomputes the order-level total through the handling-pool variant of §3.5, so re-pricing the order at cutoff is part of certification rather than a separate step.

Certification is followed by dispatch, or by a hold. A `DCManager` dispatches a cutoff-confirmed shipment, moving `shipment_status` from `CUTOFF_CONFIRMED` to `DISPATCHED`, which is the shipment's terminal state. But a shipment that has been certified can be held: when the center's `operations_posture` becomes `LOCKDOWN`, every shipment at that center sitting in `CUTOFF_CONFIRMED` automatically moves to `HELD` — no manager action is required. When the center's last open quality or damage hold is cleared and its posture returns to `OPEN`, every `HELD` shipment at that center automatically returns to `CUTOFF_CONFIRMED`. This pair cycles for as long as the center's posture keeps changing. The order's shipment row comes into existence at the moment the order first reaches `fulfillment_status` `PICKED` — minted in state `STAGED` against the order's allocated center, with a `service_level` of `GROUND`, the order's `promised_delivery_by` carried onto it, and its weight and freight figures left unset until certification — so an order that has not yet been picked carries no shipment at all, and the two preconditions above become satisfiable together.

### 3.8. Distribution-Center Posture and the Daily Cutoff Roll

Each distribution center has an operating posture with three values, and the posture answers two different questions at once. A center is `OPEN` when it has no open quality or damage hold and its `inbound_reserved_units` is below a threshold equal to its `inbound_capacity_units` multiplied by the restricted reserve ratio, rounded up to a whole unit. It is `RESTRICTED` when it has no open hold and its `inbound_reserved_units` is at or above that same threshold. It is `LOCKDOWN` whenever an open quality or damage hold exists on the center, and `LOCKDOWN` outranks `RESTRICTED` — a center with both a hold and a full inbound reserve is reported as `LOCKDOWN`, and a center whose reserve crosses the restricted threshold while a hold is open likewise reads `LOCKDOWN`. The threshold comparison is inclusive at the boundary in a way implementations commonly get wrong: exactly the ceiling of capacity multiplied by the reserve ratio reserved units is already `RESTRICTED`, while one unit fewer is still `OPEN`.

The posture moves with the reserve level in both directions. Crossing from `OPEN` to `RESTRICTED` happens automatically when the reserve first reaches the threshold, and returning from `RESTRICTED` to `OPEN` happens automatically when the reserve falls back below it; neither requires a manager. The hold-driven moves are more consequential because they cascade. Opening an open quality or damage hold on a center drives the posture to `LOCKDOWN`, and the effect runs outward in four hops: first, every shipment at that center in `CUTOFF_CONFIRMED` becomes `HELD`; second, each of those shipments' orders has its `fulfillment_status` reverted back to `ALLOCATED` — from `PICKED`, or from `SHIPPED` where the order had already been certified, since a shipment in `CUTOFF_CONFIRMED` normally belongs to an order that has moved past picking; third, each of those orders' lines has its `line_status` reverted from `PICKED` back to `ALLOCATED`; and fourth, each of those lines reopens its pick task by writing `shortage_disposition` `NONE` and returning `pick_status` to `PICKING`. Clearing the center's last open hold reverses the posture to `OPEN`, and the reversal runs in two hops: every `HELD` shipment at the center becomes `CUTOFF_CONFIRMED` again, and each of those shipments' orders has its `fulfillment_status` restored to `PICKED`. The asymmetry is deliberate — lockdown unwinds pick work, release does not redo it. A `DCManager` raises or clears a hold by supplying a `hold_action` and an optional `reason`; opening it drives the posture to `LOCKDOWN` and clearing the last one returns the posture to `OPEN`.

The daily cutoff roll is the center's period boundary, and it is a `DCManager` operation on the center. It does three things in a fixed sequence: it recomputes the positioning classification of the center's inventory, it increments the center's `cutoff_sequence_index`, and it re-derives the center's `operations_posture`. The classification produces the `positioning_flag` on each of the center's stock rows, and it is pinned to evaluate in a particular order — the center is classified first from the items that are genuinely in stock there, and only afterwards is the long-tail branch consulted; writing the long-tail branch first would make the classification depend on a field it does not read, which is forbidden. The stock rows eligible for the count are those whose `on_hand_units` is at least 1 — no status filter applies, and an item with zero on hand is simply not counted. Those eligible rows are ordered by `sku` ascending and then by the stock row's `created_at` ascending, and their count is the center's in-stock item count. If that count is at least the positioning threshold of 2, the classification is `OK`. If the count is greater than 0 but every one of the ordered rows belongs to an item with `long_tail` true, the classification is `LONG_TAIL_DEFICIT`. In every other case — including the case where the count is 0 — the classification is `UNDERSTOCKED`. Note the shape of the second branch: an item being long-tail is not enough on its own; a single ordinary item among the in-stock rows is enough to route the center to `UNDERSTOCKED` rather than `LONG_TAIL_DEFICIT`.

The `cutoff_sequence_index` that the roll increments is a monotone counter, and it is used twice elsewhere. It is one of the two tie-break keys in the allocation selector of §3.4, and it is copied into a shipment's own `cutoff_sequence_index` at the moment the shipment's cutoff is certified, as §3.7 describes — so the shipment records which roll of the center's counter it was certified under. Because the counter moves only on a roll, two orders allocated at different points between rolls will carry the same value, while the ordering of shipments across successive periods is preserved.

### 3.9. Returns: Restocking Without Friction, and the Supplier Ledger

A return begins as an authorization against a shipped order. A `CustomerAccount` or a `DCManager` creates one by supplying the `order_id` and the `lines` being claimed — each entry naming the line's `line_id` and a `requested_return_units` count, which may be 0 — and the authorization is born in `return_status` `DRAFT`, with `restock_units` and `damaged_units` both 0. The `damaged_units` recorded here are conceptually distinct from the `damaged_units` on an order line: the authorization's figure is the share of this return approved onto the damage path, while the line's figure accumulates the units of that line that have been routed to damage across returns. Approving the authorization is a manager's step and is legal only from `DRAFT`. Each claimed unit quantity must be no greater than the quantity the line actually delivered — an authorization cannot claim more than was shipped. Approval sets `return_status` `APPROVED` and splits the return into a restock share and a damage share; the authorization's own `restock_units` is the sum over its lines of the restock share the ratio waterfall below assigns each of them, and its `damaged_units` is the authorized units minus that restock total. A draft authorization may also be cancelled outright, moving `return_status` to `CANCELLED`, which is a terminal state; no other effect is applied. And an authorization that is already `APPROVED` may be approved again before it is received — a revision round that recomputes `restock_units` and `damaged_units` against the current lines without changing the status, so the restock mix may be re-derived right up to the moment material arrives.

The restock/damage split is a waterfall along the lines, and the cap is what shapes it. The lines are processed in order of the delivered `line_subtotal_cents` descending, ties broken by the line's `created_at` ascending. For each line in that order, the restock units are the authorized return units multiplied by a ratio that starts at 0.80 and is floored to a whole unit, and the damaged units are the remainder. After each line, the ratio drops by 0.30, never going below 0 — so the first line in the order restocks 80 per cent of its units, the second 50 per cent, the third 20 per cent, and every line after the third restocks nothing and is routed entirely to the damage path. The restock cap of 5 units applies as the ceiling on each line's restock share, and the ratio step of 0.30 is what drives the ratio downward between lines. This is the mechanism behind "returns without restocking friction": the fraction of returned material that can go straight back on the shelf declines predictably as the return grows, and beyond the third line the material is all damage.

Receiving the returned material is the heaviest single operation in the system, because it runs a seven-stage cascade and moves the order to its terminal state. Receiving requires `return_status` `APPROVED`, and every claimed unit must carry a `removed_manufacturer_part_number` recorded on the request — supplied as the `removed_manufacturer_part_numbers` collection on the receiving body; a claimed unit with no part number recorded is rejected with `ERR_RETURN_PART_NUMBER_REQUIRED` (HTTP 422). The stages then run in order:

- **Stage A — line return record.** Each line's `returned_units` is increased by the authorized units for that line, and the line moves to `line_status` `RETURNED`.
- **Stage B — restock assessment.** Each line's `restocked_units` is set to the restock share the ratio waterfall of this section assigns it — the same walk the approval performed, over the same ordered lines and against the same cap — and its `damaged_units` is increased by the authorized units minus that restocked figure. The line's `return_friction_units` is the units of this receipt that were not restocked — the damaged units plus any non-restockable units — and it is this figure that expresses the friction of the return against the order's quantity.
- **Stage C — stock restore.** The center's stock row for each line's item has its `on_hand_units` increased by the line's `restocked_units`, and its `available_units` is recomputed. Restocked material returns to the sellable shelf; damaged material does not, and never re-enters `available_units`. If the center had been in `LOCKDOWN`, this stage returns its `operations_posture` to `OPEN`.
- **Stage D — damage path.** A `DamageClaim` is opened for the damaged share of each line's item, and the owning account's `open_claim_count` is incremented by 1.
- **Stage E — supplier breach.** When the line's item has `long_tail` true, the supplier behind that item has its `commitment_breach_count` incremented by 1, and its `performance_rating_units` is recomputed as 100 minus ten times the new breach count — the ledger rule of §3.2 applied at the point where a long-tail item actually failed. The supplier behind an item is the supplier that filed the earliest availability report covering that item; when no report covers it, the item's supplier is the earliest-created `long_tail_authorized` supplier whose `home_dc_id` is the center receiving the return.
- **Stage F — catalogue suspension.** When the item's damage ratio breach condition returns true — evaluated as described below — the item's `catalog_status` is set to `SUSPENDED`.
- **Stage G — fresh authorization.** Every return authorization on this order that is still in `return_status` `APPROVED` is set to `CANCELLED`, so stale authorizations that would otherwise be received twice are invalidated by the first receipt.

After the cascade the authorization itself moves to `return_status` `RECEIVED` — its terminal state — and the order's `fulfillment_status` moves to `RETURNED`, its terminal value, with the order's `version` incremented by 1.

Stage F's suspension condition is an inclusive integer comparison, and its boundary is the part implementations get wrong. The damage ratio breach is true when the line's `damaged_units` is greater than 0 and the line's `damaged_units` multiplied by the item's `unit_price_cents` is at least 10,000 cents. Exactly 10,000 cents suspends the item; 9,999 cents does not. Damage exposure is reported with the same damage value factor of 0.60 used at claim opening: a claim's `damage_value_cents` is its `claim_units` multiplied by the item's `unit_price_cents` and then by that factor, rounded half up to a whole cent. It bears repeating that no damage figure is ever added into the order's `order_total_cents` — the order total is owned solely by the calculation of §3.5 — and a claim resolves at zero charge, so `damage_value_cents` is a reported exposure quantity rather than an order charge.

### 3.10. Square-Footage Consignments and the Pipe-Length Commitment

A separate quotation flow serves accounts buying cut pipe lengths rather than catalog items. A `CustomerAccount` quotes a consignment by supplying its `account_id` and a set of `lines`, each naming a `cut_list_ordinal` and a `requested_feet` count of at least 1. The ordinal is the position of that cut length in the customer's cut list, and no two lines of the same request may share an ordinal. Every line belongs to exactly one request, identified by the `request_id` recorded on the line, and the cut lines of a request can be listed either under the request itself or across all requests narrowed by `request_id` and `line_status`. A new request begins in `request_status` `QUOTED`, and its lines begin in `line_status` `PLANNED`. The quote returns two commitment figures at once — an optimistic one and a conservative one — because the two answer different questions about what the yard can actually deliver today.

Both variants walk the same line order and obey the same stop rule. Lines are taken in order of `cut_list_ordinal` ascending, ties broken by `created_at` ascending. The walk maintains a running "remaining" figure and gives each line as many feet as it can take, up to that line's `requested_feet`, subtracting what it gave from the remaining. The walk stops at the first line it cannot fully satisfy — that is, at the first line whose `requested_feet` exceeds what remains — and no later line is served at all, even if the remaining figure would have covered a shorter one further down the list. The feet allocated before the stop are summed, and the line the walk stopped on records `line_committed_feet` of 0. Only lines in `line_status` `PLANNED` or `CUT` take part.

The two variants differ in the stock pool the running figure is drawn from, and in the allowance added at the end. The forward-looking variant draws its remaining figure from the available stock, converted from millimetres to whole feet using a unit conversion of 304.8 millimetres per foot and rounded, and then adds a cut-in-progress allowance: work-in-progress stock of 182,880.0 millimetres converted to feet in the same way. The available stock is not scoped to a center, an item or an account: it is the total of `on_hand_units` across every stock row in the system, read as a figure in feet. The on-hand-only variant draws the same running figure from available stock, applies the identical stop rule, and adds instead a finished-goods allowance of 121,920.0 millimetres converted to feet. Both variants store integer feet rounded half up. The forward-looking allowance is the larger of the two, because cut-in-progress pipe is counted as though it were already available, which is why the forward-looking figure is the optimistic same-day commitment: both variants walk the identical line order over the identical stock pool, so they allocate exactly the same feet and differ only in the allowance they add, and the forward-looking figure therefore stands exactly 200 feet above the on-hand-only figure — the gap between the 600-foot cut-in-progress allowance and the 400-foot finished-goods allowance. The distinction is not cosmetic — the on-hand-only figure is strictly lower whenever the two allowances differ, because it replaces the cut-in-progress allowance with the smaller finished-goods allowance.

Which variant a request reports is pinned by a field rather than chosen per read. A request's `committed_variant` is `FORWARD_LOOKING` while its `request_status` is `QUOTED`, and flips to `ON_HAND_ONLY` once any one of its lines has reached `line_status` `CUT`. The committed length itself is exposed through `committed_length_feet`, which holds the value of the currently selected variant as of the last recomputation, and the previous variant's figure is preserved in `prior_committed_length_feet`: while the request is still `QUOTED` this field is seeded equal to `committed_length_feet`, and at the first cut it captures the forward-looking figure before the variant flips. Recording a cut is done by a `WarehousePicker` supplying the `cut_list_ordinal` of the line being cut; the ordinal must belong to the request, the request must currently be `QUOTED` or already `CUTTING`, the named line moves to `line_status` `CUT`, the request moves to `request_status` `CUTTING`, and the commitment is recomputed. A consignment may take any number of cuts once it has started, and the request stays in `CUTTING` between them — the variant, however, is pinned to `ON_HAND_ONLY` from the very first cut and does not revert.

### 3.11. Catalogue Availability and Search Visibility

Buyers discover material through catalog search, and the search must show availability at the moment of entry rather than a cached figure. Searching the catalog accepts a free-text `q` term and narrower filters — `material_spec` for the material, `region` for the delivery region, `long_tail` for whether the item is long-tail sourced, `catalog_status` for whether the item is `ACTIVE` or `SUSPENDED`, `dc_id` to scope to one center and `supplier_id` to scope to one supplier — and every result carries its live availability at the relevant center together with its `unit_price_cents`. Reading a single item returns the same live availability alongside the item's full record: its `sku`, `description`, `material_spec`, `long_tail` flag, `catalog_status`, `curation_review_state`, `curation_last_reviewed_by`, `curation_bundle_size`, `unit_price_cents`, `unit_weight_kg`, `curated_dimension_json` and `allocated_dc_id` where one has been set. The live availability at a center is that center's stock row's `available_units`, computed as `on_hand_units` minus `reserved_units`, and it moves as orders allocate and picks consume stock.

Three list-style views tie the catalog back to its activity, and each is scoped differently. Order lines that request a given item can be listed oldest first, and lines can be listed across all orders filtered by the center that allocated them, by the item, or by `line_status`. The lines of a single order can be listed, optionally narrowed to those a particular center allocated. Stock rows can be listed filtered by `item_id`, `dc_id` or `account_id`, and a single row can be read with its `available_units` and its `positioning_flag` — the classification derived by the daily cutoff roll of §3.8. Availability reports against a supplier, and against an item, can each be listed. And the curation membership rows recorded for an item can be listed so a curator can see which review batches an item has passed through.

One warning belongs here for anyone building against the catalog: an item's `catalog_status` and its `curation_review_state` are independent gates. An `ACTIVE` item that is `UNREVIEWED` cannot be ordered at all — order creation and release both reject the attempt with `ERR_CURATION_NOT_APPROVED` — while a `SUSPENDED` item is one that was approved and orderable but has since been withdrawn because of damage, and its units cannot have fulfillment resumed against them (`ERR_ITEM_SUSPENDED`). Search visibility, by contrast, is not gated on either: a suspended or unreviewed item still appears in catalog results, carrying its live availability and price, which is why the response exposes both the curation state and the catalog status as separate fields.
