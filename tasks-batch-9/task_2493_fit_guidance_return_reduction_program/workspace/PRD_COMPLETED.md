# Fit Guidance & Return Reduction Program API — Product Requirements Document

## 1. Introduction

Apparel returns are the single largest controllable cost in online fashion retail, and the majority of them are not quality failures — they are fit failures. A shopper orders two sizes because the brand's own label is untrustworthy, or orders one size and sends it back because the finished-garment measurements behind that label were never checked against the grade rules the vendor claimed to follow. This document specifies the API for the Fit Guidance & Return Reduction Program: a merchandising back-office system that captures vendor measurement specifications, verifies them against declared tolerances and grade increments, standardizes brand sizes onto shared size charts, serves size recommendations built from purchase and review history, and then measures whether any of that actually reduced returns.

The system is deliberately two-sided. On the supply side it holds vendors accountable: every specification that fails verification opens a chargeable correction round against a funded vendor allowance, and repeated failures or quality chargebacks erode a vendor's reliability score until new specification work is refused outright. On the demand side it holds shoppers accountable: return reasons are audited rather than accepted at face value, change-of-mind returns accumulate strikes inside a trailing window, and a shopper whose return rate runs away from the population loses the ability to open new returns at all. Between the two sits the merchandising team, which pays for interventions — chart standardization, model measurements on the product page, detail imagery, recommendation badges, vendor specification corrections — and needs a defensible number for what each lever saved.

Three properties of the system drive most of the engineering difficulty and should be read as first-class requirements rather than implementation detail. First, a catalog item carries **two independent state axes** on the same row: where it stands on the storefront, and how far along it is toward serving fit guidance. They advance on different triggers and must never be collapsed into one status. Second, almost every write in the return pipeline is a **cascade**: resolving a single return case can rewrite item counters, flip an item's chronic-return classification, suspend a listing, reset the guidance axis, reopen a verified specification, debit a vendor, terminate running measurement deployments, and re-derive an intervention's funding posture — all inside one request. Third, the entire time-dependent surface of the system is driven by a **logical clock** that tests may move forward or backward at will; no evaluation may consult real wall-clock time.

## 2. Global Specifications & System-Wide Principles

Every rule in this section applies across the whole API surface, which is mounted under `/fit-program` (the single exception is the logical-clock control endpoint described in §2.5).

### 2.1. Operator Identity and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator or shopper, and `X-User-Role`, declaring the capacity in which they act. If either header is absent or carries an empty value, or if `X-User-Role` is not one of the five recognized role names — the comparison being exact and case-sensitive — the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the declared role is not among the roles authorized for the requested operation, the rejection is `ERR_UNAUTHORIZED` (HTTP 403).

The five roles are spelled exactly `MerchOpsAdmin`, `VendorUser`, `FitAnalyst`, `ReturnsAuditor`, and `Customer`. Their responsibilities divide as follows. A `MerchOpsAdmin` owns merchandising operations: vendor registration, catalog items, size charts, return policies, order ingest, program levers, deployment scheduling, and the periodic ops-run checkpoint. A `VendorUser` is the brand-side operator who authors and corrects measurement specifications for its own items — and, by design, can never verify them. A `FitAnalyst` verifies specifications, maps brand sizes onto standardized charts, and turns fit guidance on — and can never author a specification or resolve a return. A `ReturnsAuditor` codes return reasons and closes cases. A `Customer` is the shopper who opens returns, publishes reviewer fit feedback, and reads fit guidance.

Two of those roles are backed by persisted entities, and three are not. When `X-User-Role` is `VendorUser`, `X-User-ID` is the `id` of the acting `Vendor`; ownership checks on any resource that references a `Vendor` compare the resource's foreign-key field to `X-User-ID` — specifically, a specification write is permitted only when the acting `X-User-ID` equals the `vendor_id` of the `CatalogItem` the specification describes, and a vendor read is permitted only when the acting `X-User-ID` equals the vendor id in the path. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `CustomerProfile`; ownership checks compare the resource's customer foreign key to `X-User-ID` — the `customer_profile_id` of the `OrderLine` behind a return case on return-case writes and reads, the `customer_profile_id` supplied in the body on fit-feedback creation, the `customer_profile_id` of the `FitFeedback` row on retraction, and the `customer_profile_id` query value on the fit-recommendation read. Any of these mismatches is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

When `X-User-Role` is `MerchOpsAdmin`, `FitAnalyst`, or `ReturnsAuditor`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — as `verified_by_user_id` on a `MeasurementSpec` when a `FitAnalyst` decides a verification, and as `classified_by_user_id` and `resolved_by_user_id` on a `ReturnCase` when a `ReturnsAuditor` codes or closes it — but it never compares those values to any entity's `id`. The one place a recorded opaque id is compared is segregation of duties: the `ReturnsAuditor` whose `X-User-ID` was stored as `classified_by_user_id` must not be the operator who resolves the same case, and an attempt to do so is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` — specifically the literal `req_` followed by exactly 20 characters drawn from the uppercase letters A through Z and the digits 0 through 9.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for the paginated collection reads described in §2.3, and for those only: the append-only cost-postings read of a single case returns every posting of that case in one `array` response whose `meta` carries none of the four fields, and that read accepts no `limit` or `offset` at all — such parameters are ignored there rather than validated.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. A request to a path this API does not define, or to a defined path with a method that path does not define, is answered in this same error envelope with `error_id` `ERR_NOT_FOUND` (HTTP 404) or `ERR_METHOD_NOT_ALLOWED` (HTTP 405) respectively; those two identifiers are framework-level fallbacks and are deliberately not part of the catalogue in §5.

### 2.3. Pagination and List Ordering

Collection reads accept two query parameters. `limit` caps the number of rows returned; when omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of rows to skip; when omitted it defaults to 0, and its minimum accepted value is 0. A `limit` outside the inclusive range of 1 through 100, a non-integer value for either parameter, or an `offset` below 0, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400). A supplied value counts as an integer only when it is a base-10 digit string, optionally carrying a single leading `+` or `-`, with surrounding whitespace ignored; an empty value, a fractional value such as `10.5`, and any other text are all non-integer. A parameter that is not supplied at all takes its default and is never range-checked, and `offset` has no upper bound — an `offset` at or beyond `total_count` is accepted and simply yields an empty `data` array.

Unless a specific endpoint states otherwise, every list response is ordered by `created_at` ascending, with ties broken by the order in which the rows were created on the server — a tie-break that matters in practice because the logical clock of §2.5 can stamp any number of rows with the same instant. The `meta` block of a list response carries `limit`, `offset`, `total_count`, and `has_more`, where `total_count` is the number of rows matching the filters before the limit and offset are applied, and `has_more` is true exactly when `offset` plus the number of rows actually returned in `data` is strictly less than `total_count`.

Filters on list endpoints are additive and narrow the result set. Catalog items may be narrowed by `vendor_id`, `listing_status`, `fit_readiness`, or `fit_watch_state`; measurement specifications by `item_id` or `status`; size chart mappings by `item_id`, `chart_id`, or `status`; return policies by `customer_profile_id`, `category_code`, or `scope`; order lines by `customer_profile_id`, `item_id`, or `status`; return cases by `order_line_id`, `effective_policy_id`, `status`, or `reason_family`; fit feedback by `item_id`, `customer_profile_id`, or `status`; and intervention deployments by `intervention_id`, `item_id`, or `status`. Every filter is applied as exact, case-sensitive string equality against the stored field, so a filter value that matches no row yields an empty `data` array rather than an error; query parameters other than the filters declared here and the two pagination parameters are ignored.

### 2.4. Common Resource Properties

Twelve of the thirteen persisted resource types — vendors, catalog items, measurement specifications, size charts, size chart mappings, customer profiles, order lines, return cases, fit feedback rows, return policies, interventions, and intervention deployments — carry the same four system-managed properties:

- `id` (string): a server-minted UUID with no type prefix and no embedded meaning.
- `created_at` (string): the ISO 8601 UTC instant at which the row was created, rendered with three fractional digits (for example `2026-08-01T00:00:00.000Z`), read from the logical clock described in §2.5.
- `updated_at` (string): the ISO 8601 UTC instant of the row's most recent mutation, in the same format.
- `version` (integer): a counter that starts at 1 on creation and increases by exactly 1 on every mutation of that row.

Every other instant-valued field the API returns — a specification's `verified_at`, an order line's `delivered_at`, a policy row's `effective_from` and `effective_to`, a case's `requested_at` and `return_deadline_at`, a deployment's `window_start` and `window_end`, and the `current_utc` echoed by the clock endpoint of §2.5 — is rendered in that same three-fractional-digit UTC format. This holds for instants the client itself supplied: a supplied instant is parsed, normalized to UTC, and re-rendered in the house format rather than echoed back byte-for-byte, so a `window_start` or an `effective_to` given as `2026-08-01T00:00:00Z` reads back as `2026-08-01T00:00:00.000Z`. Normalization accepts either a `Z` suffix or an explicit offset and converts the offset away; an instant supplied with no zone designator at all is read as already being UTC.

A recomputation of a derived field counts as a mutation when it actually changes a stored value. When resolving a return case rewrites a catalog item's counters, or an ops-run walks a customer profile's abuse standing back down, that row's `updated_at` is refreshed and its `version` increases by 1 exactly as if a client had written to it directly. A recomputation that lands on exactly the values already stored has changed nothing, so it is not a mutation: `updated_at` and `version` are left alone, and an ops-run sweep that finds every derived figure already correct bumps no versions at all.

The thirteenth type is the exception. A `ReturnCostPosting` is an immutable ledger line: it carries only `id` and `created_at`. It has no `updated_at` and no `version`, and those keys must be absent from its representation rather than present and null. A posting is never edited; a mistaken posting is answered by writing a second, negating posting, as §2.10 describes.

### 2.5. The Logical Program Clock

Every deadline, every measurement window, and every trailing-window evaluation in this system reads a logical clock rather than the host's wall clock. Before the clock has been set for the first time, it reads exactly `2026-08-01T00:00:00Z`. A `MerchOpsAdmin` may move it to any instant, forward or backward, by supplying a required `to_iso8601` instant to the test-driving clock endpoint — parsed and normalized exactly as any other supplied instant per §2.4, and an absent or unparseable value is an `ERR_INVALID_REQUEST`; the response `data` is an object whose single field is `current_utc`, echoing the new instant in the house three-fractional-digit format. Once set, the clock never falls back to real time — it stays exactly where it was put until it is set again.

Because the clock is authoritative, the same request replayed after the clock moves may legitimately produce a different outcome: a return that was inside its window becomes late, a change-of-mind strike ages out of the trailing window and a shopper's standing improves, a scheduled deployment becomes eligible to activate. Implementations must therefore read the clock at the moment of evaluation and must not cache derived instants across requests.

### 2.6. Millimetres, Cents, and Basis Points: The Arithmetic Discipline

No value in this system is a floating-point quantity exposed to the client. Money is always whole cents. Lengths are always whole millimetres, except fit-model height, which is whole centimetres. Rates, weights, shares, and tolerance percentages are always integer **basis points**, where 10,000 basis points is one whole. Size-step offsets are integers in hundredths of a size step.

Two rounding modes are used, and which one applies is never a matter of taste:

- **Round half up** applies where the scaffold of a calculation names it: the percentage component of a grade tolerance, each of the two restocking-fee steps, each individual return-cost component, the weighted fit offset, and the conversion of that offset into a whole size step. Wherever a negative value can arise — the percentage component of a grade tolerance whose declared increment is negative, the weighted fit offset, and the size-step conversion alike — "half" rounds away from zero rather than toward positive infinity: an offset of −50 hundredths becomes a shift of −1 step, and an offset of +50 hundredths becomes +1 step.
- **Floor** — truncation toward negative infinity — applies at every division that produces a basis-point rate or a whole count: item return rates, the weighted chronic score, mapping coverage, customer return rate, confidence, avoided-return counts, and the median row index of a chart. The stretch step of tolerance resolution also floors.

The pinning rule for the return-cost ledger deserves separate emphasis because it is the most common source of off-by-one-cent divergence: each cost component is rounded to whole cents on its own, and the already-rounded components are then summed. Summing exact fractional component values and rounding once at the end is wrong and produces a different total.

### 2.7. Stale-Version Guards on Mapping and Override Writes

Two write operations in this system act on the strength of a parent row the client read earlier, and both are protected by an explicit optimistic-concurrency check. In each case the version field is a required, non-optional input; omitting it is a malformed request under §2.9's body-validation rule, not a silent skip of the check. Endpoints not named here take no version field at all.

A `POST /fit-program/size-chart-mappings` request must carry `expected_item_version` matching the target `CatalogItem`'s current `version`. Creating a mapping legitimately supersedes the item's prior active mapping and rewrites the item's fit-readiness axis, so a writer holding a stale view of the item would silently discard a mapping decision it never observed. If the item's `version` has advanced past the value the client last read, the create is rejected with `ERR_STALE_ITEM_VERSION` (HTTP 412) and nothing is written.

A `POST /fit-program/customer-profiles/{id}/return-policy-overrides` request must carry `expected_customer_profile_version` matching the target `CustomerProfile`'s current `version`. Overrides are written on the strength of the profile's `abuse_status` and `policy_class`, both of which move whenever a return resolves or is voided, so an override built on a stale profile view is refused rather than applied: the rejection is `ERR_STALE_CUSTOMER_PROFILE_VERSION` (HTTP 412).

### 2.8. Cascade Discipline and the Two Item Axes

A `CatalogItem` carries two independent state axes on the same row, and the system must never conflate them. The `listing_status` axis — `DRAFT`, `LISTED`, `SUSPENDED`, `DELISTED` — describes the item's presence on the storefront. The `fit_readiness` axis — `UNVERIFIED`, `CHART_MAPPED`, `GUIDANCE_READY` — describes how far the item has progressed toward serving fit guidance. Each axis advances on its own triggers. Putting a draft item on the storefront leaves the readiness axis exactly where it was; creating a size chart mapping advances the readiness axis and leaves the storefront axis exactly where it was. Only the chronic-return event described below moves both at once, and it does so by firing two separate transitions.

Cascades in this system are immediate and synchronous. When a single request causes a chain of consequences, every link of the chain is committed before the response is returned, and each link mutates its own row's `updated_at` and `version` in the usual way. The longest chain in the system runs like this: a return resolution advances the item's counters, which re-derives the chronic-return score, which flips `fit_watch_state` to `CHRONIC`, which suspends a `LISTED` item, resets the readiness axis to `UNVERIFIED`, and reopens the item's single verified specification into `CORRECTION_REQUESTED`, which in turn debits the owning vendor's correction allowance, re-derives the vendor's reliability score and standing, and — because the readiness axis fell — terminates the item's running recommendation-badge and chart-standardization deployments, each of which re-derives its owning intervention's spend, savings, and funding posture. A second chain starts at chart retirement and reaches the same deployment and intervention recomputation through mapping supersession.

Cascades run in both directions. Every derived counter, score, rate, and classification in this system is recomputed from its inputs rather than incrementally adjusted, so a reversal walks the derived state back down: voiding a return case can move `fit_watch_state` from `CHRONIC` back to `WATCH` or `NORMAL`, and can move a shopper's `abuse_status` from `BLOCKED` back to `RESTRICTED` or `CLEAR`. What a reversal does **not** undo is the transitions that already fired: a specification reopened into `CORRECTION_REQUESTED` stays there, a suspended listing stays suspended, and the vendor debit stays debited. Only derived aggregates are restored.

### 2.9. Validation Precedence

When several rules could reject the same request, the order in which they are evaluated is fixed, because the error the client sees must be deterministic. The ladder below is evaluated strictly top to bottom and stops at the first failure.

1. **Authentication.** `X-User-ID` and `X-User-Role` are present and the role is one of the five declared names, otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorization.** The acting role appears in the endpoint's authorized list, otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Path existence.** Every identifier in the URL resolves, validated left to right, so the leftmost unresolvable identifier decides the error: `ERR_VENDOR_NOT_FOUND`, `ERR_ITEM_NOT_FOUND`, `ERR_SPEC_NOT_FOUND`, `ERR_CHART_NOT_FOUND`, `ERR_MAPPING_NOT_FOUND`, `ERR_CUSTOMER_PROFILE_NOT_FOUND`, `ERR_POLICY_NOT_FOUND`, `ERR_ORDER_LINE_NOT_FOUND`, `ERR_RETURN_CASE_NOT_FOUND`, `ERR_FEEDBACK_NOT_FOUND`, `ERR_INTERVENTION_NOT_FOUND`, or `ERR_DEPLOYMENT_NOT_FOUND`, each HTTP 404. Applies to every endpoint carrying an identifier in its path.
4. **Ownership.** For the two entity-backed roles, the acting `X-User-ID` owns the target as described in §2.1, otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to exactly the operations enumerated in §2.1 and to no others: for a `VendorUser`, specification creation, submission and resubmission, plus the vendor read; for a `Customer`, return-case creation, the single return-case read, fit-feedback creation, fit-feedback retraction, and the fit-recommendation read. Every other read a `VendorUser` or a `Customer` is merely authorized for is unfiltered and unchecked — a specification row or the specification list, a catalog item, a customer profile, an order line or the order-line list, and a fit-feedback row or the fit-feedback list are all served to any authorized caller regardless of whose rows they are.
5. **Body validity.** Required body fields are present and correctly typed, numbers lie within their declared bounds, enum-valued fields carry declared members, `size_points` has at least 2 entries with unique `size_label` values and unique non-negative `sort_index` values, `grade_rules` entries have distinct `measurement_point` values, and `base_size_label` appears among the `size_points`. Otherwise `ERR_INVALID_REQUEST` (400). Applies to every write endpoint. Four conventions make this rank deterministic. A key present with an explicit `null` is treated as absent: a required field so supplied is rejected, an optional one falls back to its stated default. Keys the endpoint does not declare are ignored rather than rejected. An integer-valued field must be a JSON integer, so a boolean, a numeric string, or a fractional number is rejected, and a string-valued field is taken exactly as supplied without trimming, with enum membership compared case-sensitively. And a request whose body is absent or blank is read as an empty JSON object — its required fields then fail this rank — while a body that is present but is not valid JSON, or is valid JSON that is not an object, is itself an `ERR_INVALID_REQUEST`.
6. **Pagination validity.** `limit` and `offset` obey §2.3, otherwise `ERR_INVALID_PAGINATION` (400). Applies to every list endpoint.
7. **Body foreign keys.** Every foreign key supplied in the body resolves, validated in the order the fields are declared in the request body, yielding `ERR_VENDOR_NOT_FOUND`, `ERR_ITEM_NOT_FOUND`, `ERR_CHART_NOT_FOUND`, `ERR_CUSTOMER_PROFILE_NOT_FOUND`, `ERR_ORDER_LINE_NOT_FOUND`, or `ERR_INTERVENTION_NOT_FOUND` (404). Applies to catalog-item creation, measurement-specification creation, size-chart-mapping creation, order-line creation, return-case creation, fit-feedback creation, and intervention-deployment creation.
8. **Unique keys.** `Vendor.brand_code`, `CatalogItem.sku`, `SizeChart.chart_code`, and `CustomerProfile.email` are still free, otherwise `ERR_DUPLICATE_RESOURCE_KEY` (409). Applies to vendor creation, catalog-item creation, size-chart creation, and customer-profile creation.
9. **Item not delisted.** The `CatalogItem` reached through the path or the body does not have `listing_status` `DELISTED`, otherwise `ERR_ITEM_DELISTED` (409). Applies to ten operations: measurement-specification creation, specification submit, specification verify, specification resubmit, size-chart-mapping creation, guidance publication, product-page enhancement, order-line creation, return-case creation, and intervention-deployment creation.
10. **Transition legality.** The target row is in a state the requested transition declares as its origin, otherwise `ERR_INVALID_ITEM_STATE`, `ERR_INVALID_SPEC_STATE`, `ERR_INVALID_CHART_STATE`, `ERR_INVALID_RETURN_CASE_STATE`, or `ERR_INVALID_DEPLOYMENT_STATE` (409). Applies to every action endpoint: list, delist, product-page enhancement, publish-guidance, submit, verify, resubmit, standardize, retire, classify, resolve, void, terminate, and retract.
11. **Stale parent version.** `expected_item_version` equals the `CatalogItem`'s current `version` on mapping creation, and `expected_customer_profile_version` equals the `CustomerProfile`'s current `version` on override creation, otherwise `ERR_STALE_ITEM_VERSION` or `ERR_STALE_CUSTOMER_PROFILE_VERSION` (412).
12. **Segregation of duties.** The acting `ReturnsAuditor`'s `X-User-ID` differs from the case's `classified_by_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to return-case resolution.
13. **Shopper not blocked.** The purchaser's `abuse_status` is not `BLOCKED`, otherwise `ERR_CUSTOMER_RETURN_BLOCKED` (409). Applies to return-case creation.
14. **Return window open.** The logical clock is at or before the delivery instant plus the effective window in days, otherwise `ERR_RETURN_WINDOW_CLOSED` (422). Applies to return-case creation.
15. **Policy available.** Policy resolution finds at least one candidate row, otherwise `ERR_NO_RETURN_POLICY` (422). Applies to return-case creation. Because the rank-14 deadline cannot be computed without a resolved policy, resolution physically runs first: a shopper with no governing policy row always sees `ERR_NO_RETURN_POLICY`, never `ERR_RETURN_WINDOW_CLOSED`, however long ago the line was delivered.
16. **No duplicate case.** The order line carries no return case in `TRIAGE`, `FIT_REVIEW`, `QUALITY_REVIEW`, `EXPECTATION_REVIEW`, `COOLING_OFF`, `RESOLVED_REFUNDED`, or `RESOLVED_DENIED`, otherwise `ERR_DUPLICATE_RETURN_CASE` (409). Applies to return-case creation.
17. **Vendor not suspended.** The item's vendor does not have `status` `SUSPENDED`, otherwise `ERR_VENDOR_SUSPENDED` (409). Applies to measurement-specification creation, submit, and resubmit.
18. **No revision in flight.** The item has no measurement specification in `DRAFT`, `SUBMITTED`, or `CORRECTION_REQUESTED`, otherwise `ERR_SPEC_REVISION_IN_FLIGHT` (409). Applies to measurement-specification creation.
19. **Verified specification present.** The item has exactly one measurement specification in `VERIFIED`, otherwise `ERR_SPEC_NOT_VERIFIED` (409). Applies to size-chart-mapping creation and guidance publication.
20. **Chart usable.** The referenced size chart has `status` `STANDARDIZED` and its `category_code` equals the item's `category_code`, otherwise `ERR_CHART_NOT_STANDARDIZED` (409). Applies to size-chart-mapping creation and guidance publication.
21. **Label membership.** Every `spec_size_label` in the submitted pairs exists among the verified specification's `size_points`, and every `chart_size_label` exists among the chart's `rows`, otherwise `ERR_SIZE_LABEL_NOT_IN_SPEC` (422) and nothing is written. Applies to size-chart-mapping creation.
22. **Chart row integrity.** Chart rows have `sort_index` values contiguous from 0, strictly increasing and non-overlapping body-chest ranges across consecutive rows, and non-empty values in all four conversion columns, otherwise `ERR_CHART_ROWS_INVALID` (422). Applies to chart standardization.
23. **Override interval free.** For the same combination of `customer_profile_id` and `category_code`, the new override's closed interval from `effective_from` through `effective_to` does not intersect an existing override's closed interval, where a null `effective_to` is treated as unbounded and touching endpoints do intersect. Otherwise `ERR_POLICY_WINDOW_OVERLAP` (409). Applies to customer override creation.
24. **Deployment window free.** For the same combination of `item_id` and the intervention's `lever`, the new half-open window from `window_start` up to but excluding `window_end` does not intersect an existing window whose deployment is neither `TERMINATED` nor `MEASURED`; touching endpoints, where the new `window_start` equals an existing `window_end`, do not intersect; and `window_start` must be strictly earlier than `window_end`. Otherwise `ERR_DEPLOYMENT_WINDOW_OVERLAP` (409). Applies to deployment creation.
25. **Deployment target listed.** The deployment's item has `listing_status` `LISTED`, otherwise `ERR_DEPLOYMENT_ITEM_NOT_LISTED` (409). Applies to deployment creation.
26. **One active review per shopper and item.** The combination of `item_id` and `customer_profile_id` has no fit feedback row with `status` `ACTIVE`, otherwise `ERR_DUPLICATE_FIT_FEEDBACK` (409). Applies to fit-feedback creation.
27. **Feedback still active.** The fit feedback row's `status` is `ACTIVE`, otherwise `ERR_FEEDBACK_ALREADY_RETRACTED` (409). Applies to fit-feedback retraction.
28. **Coverage sufficient.** The item's active mapping has `coverage_bp` of at least 8,000, otherwise `ERR_MAPPING_COVERAGE_INSUFFICIENT` (422). Applies to guidance publication.
29. **Product page complete.** The item has `model_measurements_published` set to true and a `detail_image_count` of at least 3, otherwise `ERR_PDP_ENHANCEMENT_INCOMPLETE` (422). Applies to guidance publication.
30. **Guidance servable.** The item's `fit_readiness` is `GUIDANCE_READY`, otherwise `ERR_GUIDANCE_NOT_READY` (409). Applies to the fit-recommendation read.
31. **Correction allowance intact.** The vendor's `correction_spend_cents` is less than or equal to its `correction_budget_cents`, otherwise `ERR_VENDOR_CORRECTION_BUDGET_EXHAUSTED` (HTTP 402). Applies to specification resubmission.

The practical consequence of this ordering is worth stating explicitly. A resubmission by a suspended vendor whose allowance is also exhausted reports `ERR_VENDOR_SUSPENDED`, not `ERR_VENDOR_CORRECTION_BUDGET_EXHAUSTED`, because vendor standing sits at rank 17 and the allowance check sits at rank 31. A mapping create against a delisted item with a stale version reports `ERR_ITEM_DELISTED`, because rank 9 precedes rank 11. And a return-case create by a blocked shopper past the deadline reports `ERR_CUSTOMER_RETURN_BLOCKED`, because rank 13 precedes rank 14. One consequence reaches back into the body: because rank 4 precedes ranks 5 and 7, the ownership check on return-case creation reads `order_line_id` out of the unvalidated body first (specification creation peeks at its `item_id` the same way). When that key holds a string naming an existing order line that belongs to another shopper, the refusal is `ERR_NOT_RESOURCE_OWNER` even if the rest of the body is malformed or the reason code is missing; when it is absent, not a string, or names no existing line, the ownership check is simply skipped at rank 4 and ranks 5 and 7 decide the error, with the same ownership check then re-applied once the line has been resolved.

### 2.10. The Append-Only Return Cost Ledger

Return cost is tracked as a ledger rather than as a mutable total. Each cost component recognized when a return case is closed is written as its own `ReturnCostPosting` row bearing a `return_case_id`, a `component`, a signed `amount_cents`, and a `posting_kind` of `ORIGINAL`. Reversal is additive, never destructive: voiding a resolved case writes exactly one row per original row, with `posting_kind` `REVERSAL`, `amount_cents` set to the arithmetic negation of the original amount, and `reversed_component` naming the component of the original row it negates. On an `ORIGINAL` row, `reversed_component` is null.

The `component` vocabulary is fixed: `FREIGHT_INBOUND`, `PROCESSING_LABOR`, `REFURB_REPACK`, `MARKDOWN_LOSS`, `PAYMENT_FEE_UNRECOVERED`, and `VENDOR_CHARGEBACK_CREDIT`. All are positive charges against the program except `VENDOR_CHARGEBACK_CREDIT`, which is negative because it credits the program for money recovered from the vendor. Every `REVERSAL` row of a positive component is likewise negative.

Because reversal is additive, the item-level accrual `return_cost_accrued_cents` is simply the sum of `amount_cents` across every posting — original and reversal alike — attached to any return case of that item. A fully voided case therefore contributes exactly zero to the accrual without any row being deleted, while cases still in triage or in a review branch contribute nothing because they have not produced postings yet.

### 2.11. Vendor Standing and the Funded Correction Allowance

A vendor's ability to keep submitting specification work is not granted administratively; it is derived. `reliability_score_bp` starts at 10,000 basis points — a perfect record — and is recomputed as 10,000 less 500 basis points for each non-reversed quality chargeback counted in `quality_chargeback_count`, less 300 basis points for each correction round counted in `correction_round_count`, with the result floored at 0 so the score can never go negative. From that score the vendor's `status` follows: `SUSPENDED` when the score is strictly below 5,000; otherwise `PROBATION` when the score is strictly below 7,000 **or** when `correction_spend_cents` strictly exceeds `correction_budget_cents`; otherwise `ACTIVE`. The recomputation runs on every transition of one of the vendor's specifications into `CORRECTION_REQUESTED`, on every resolution of a quality-family return against one of the vendor's items, and on every void of such a case.

The allowance itself is a simple two-field ledger. `correction_budget_cents` is the annual amount the vendor has funded and is supplied at registration; it must be at least 0. `correction_spend_cents` starts at 0 and accumulates 2,500 cents — twenty-five dollars — for every correction round opened against any of that vendor's specifications, whether the round was opened because verification found a grade violation or because one of the vendor's items became a chronic returner. The debit is applied unconditionally, including when it pushes the running spend past the funded budget; the consequence of overspending is felt at the *next* resubmission attempt, which is refused with `ERR_VENDOR_CORRECTION_BUDGET_EXHAUSTED`, and in the `PROBATION` standing that overspending forces regardless of the reliability score.

## 3. Business Logic & Workflows

### 3.1. Vendors, Catalog Items, and the Two Item Axes

Everything in the program hangs off a supplying vendor. A `MerchOpsAdmin` registers one by supplying its legal `name` — between 1 and 120 characters — and a short `brand_code` of 2 to 8 uppercase characters drawn from A through Z and 0 through 9, which is the token that appears on that brand's size charts and specification paperwork. The `brand_code` must be free across all vendors. Registration also fixes `correction_budget_cents`, the amount the brand has funded for specification correction rounds, which must be at least 0. A freshly registered vendor opens with `status` `ACTIVE`, `reliability_score_bp` at 10,000, `correction_spend_cents` at 0, `correction_round_count` at 0, and `quality_chargeback_count` at 0. Vendor standing is readable by merchandising, by analysts, and by the brand itself.

Catalog items are created by a `MerchOpsAdmin` with a payload naming the `vendor_id` that supplies them, a merchant `sku` unique across the catalog, a `category_code` of `TOPS`, `BOTTOMS`, `DRESSES`, `OUTERWEAR`, or `FOOTWEAR`, the `brand_size_system` the brand labels the item in — one of `US_ALPHA`, `US_NUMERIC`, `EU`, or `UK` — and a `unit_price_cents` list price of at least 1. A new item opens at `DRAFT` on its storefront axis, `UNVERIFIED` on its readiness axis, and `NORMAL` on its chronic-return classification, and every one of its derived return metrics — `units_sold_count`, `fit_return_count`, `expectation_return_count`, `total_return_count`, `fit_return_rate_bp`, `expectation_return_rate_bp`, `chronic_return_score_bp`, `return_cost_accrued_cents`, `fit_signal_weight_total`, and `active_fit_feedback_count` — opens at 0. Its `pdp_review_required` flag opens false, its `model_measurements_published` flag opens false with `detail_image_count` at 0, its `delist_reason_code` is null, and `model_height_cm` and `model_worn_size_label` are null until the product page is enhanced.

Putting an item on the storefront is a `MerchOpsAdmin` action that advances `listing_status` from `DRAFT` to `LISTED` and increments the item's `version` by 1; the readiness axis is deliberately untouched, because listing an item and being ready to give fit advice about it are separate achievements. An item can also be restored from `SUSPENDED` back to `LISTED`, but only as a side effect of republishing guidance — see §3.4.

Removing an item from the storefront permanently is the `delist` decision, again a `MerchOpsAdmin` action, and it is accepted from `DRAFT`, `LISTED`, or `SUSPENDED` — a delist attempt against an item that is already `DELISTED` is refused as an illegal transition with `ERR_INVALID_ITEM_STATE`, not with `ERR_ITEM_DELISTED`, because delist is not one of the ten operations enumerated at rank 9 of §2.9. The request carries a `delist_reason_code` of `CHRONIC_FIT_RETURNS`, `VENDOR_EXIT`, `SEASONAL_END`, or `MANUAL`, which is stored on the item; `listing_status` becomes `DELISTED`, a terminal state, and the item's `version` increments by 1. Delisting also closes out the program's running measurement work on that item: every intervention deployment of the item whose status is `SCHEDULED` or `ACTIVE` moves to `TERMINATED` with `terminated_reason_code` `ITEM_DELISTED`, and where the logical clock is earlier than the deployment's `window_end`, the `window_end` is rewritten to the clock. Each such termination makes its owning intervention recompute `spend_cents`, `gross_savings_cents`, `net_savings_cents`, and `funding_posture`. Once an item is `DELISTED`, the ten operations listed at rank 9 of §2.9 refuse to touch it with `ERR_ITEM_DELISTED`.

### 3.2. Capturing and Verifying Measurement Specifications

A `VendorUser` authors a measurement specification for one of its own items by supplying the `item_id`, the `size_system` the measurements are labelled in (`US_ALPHA`, `US_NUMERIC`, `EU`, or `UK`), a `base_size_label` naming the sample size the grade rules radiate from, a `fabric_stretch_class` of `RIGID`, `STRETCH`, or `HIGH_STRETCH`, the `size_points` themselves, and the `grade_rules` the brand claims to have followed. Each entry of `size_points` is an object carrying a `size_label`, a `sort_index` that orders the size run, and four finished-garment measurements in whole millimetres — `chest_mm`, `waist_mm`, `hip_mm`, and `inseam_mm`. At least 2 size points are required; `size_label` values must be distinct, and `sort_index` values must be distinct and at least 0. Each entry of `grade_rules` is an object carrying a `measurement_point` of `CHEST`, `WAIST`, `HIP`, or `INSEAM`, the `increment_mm` the brand grades that point by between consecutive sizes, and two tolerance declarations — `tolerance_pct_bp` expressed in basis points of the increment and `tolerance_abs_mm` expressed in whole millimetres. At least one grade rule is required and no `measurement_point` may repeat within one specification. Apart from `sort_index`, none of the integers in this payload carries a bound: the four `size_points` millimetre figures and a rule's `increment_mm`, `tolerance_pct_bp`, and `tolerance_abs_mm` may each be zero or negative and are carried into the verification arithmetic exactly as supplied. The `base_size_label` must appear among the `size_points`; if it does not, or if any of the structural conditions above fails, the create is refused with `ERR_INVALID_REQUEST`.

A new specification opens in `DRAFT` with `revision_round` at 0, `violation_count` at 0, `first_violation_point` and `first_violation_from_size_label` null, `tolerance_applied_mm` an empty array, `correction_reason` null, and `verified_by_user_id` and `verified_at` null. Only one revision may be in flight per item at a time: if the item already has a specification in `DRAFT`, `SUBMITTED`, or `CORRECTION_REQUESTED`, authoring another is refused with `ERR_SPEC_REVISION_IN_FLIGHT`. A brand whose `status` has fallen to `SUSPENDED` cannot author, submit, or resubmit at all — those three writes are refused with `ERR_VENDOR_SUSPENDED`.

Submission is the brand's handoff to the analyst: it moves the specification from `DRAFT` to `SUBMITTED`, refreshes `updated_at`, and increments `version` by 1. It is permitted only when the specification is in `DRAFT`, only when the acting `X-User-ID` matches the `vendor_id` of the item the specification describes, only when that item is not `DELISTED`, only when the brand is not `SUSPENDED`, and only when the stored `size_points` still contain at least 2 entries with the `base_size_label` among them.

Verification is a `FitAnalyst` action and its outcome is **computed, not chosen** — the analyst runs the check and the arithmetic decides which of three states the specification lands in. It is permitted only from `SUBMITTED` and only while the item is not `DELISTED`; from any other specification status the request is refused with `ERR_INVALID_SPEC_STATE`.

The verification walk is fully deterministic and no field outside the specification under verification participates: sibling specifications of the same item are never read, and specifications in `DRAFT`, `VERIFIED`, `CORRECTION_REQUESTED`, `REJECTED`, or `SUPERSEDED` are never re-verified. The four measurement points are visited in the fixed order `CHEST`, then `WAIST`, then `HIP`, then `INSEAM`. A point with no matching entry in `grade_rules` is skipped entirely. For each visited point, the tolerance that will actually be enforced is resolved in four steps, in this order:

1. The percentage component is the rule's `tolerance_pct_bp` multiplied by its `increment_mm`, divided by 10,000, rounded half up to a whole millimetre.
2. The raw tolerance is the larger of the rule's `tolerance_abs_mm` and that percentage component.
3. The raw tolerance is then capped downward to a per-point ceiling: 25 millimetres for `CHEST`, `WAIST`, and `HIP`, and 20 millimetres for `INSEAM`. The capped value is the smaller of the raw tolerance and the ceiling.
4. Finally the capped value is scaled by the stretch class and floored to a whole millimetre: `RIGID` scales by 100 percent, `STRETCH` by 150 percent, and `HIGH_STRETCH` by 200 percent, so the enforced tolerance is the capped value multiplied by that percentage, divided by 100, with any fraction discarded.

The resolved value is appended to `tolerance_applied_mm` as an object pairing that `measurement_point` with its `tolerance_mm`, so the stored array records exactly which tolerance was enforced at each point on the last verification run.

Within the point being checked, the `size_points` are walked by `sort_index` ascending — a tie is impossible because `sort_index` values are unique — and every consecutive pair is examined. The observed step is the higher size's measurement at that point minus the lower size's measurement at that point. The check compares the absolute difference between that observed step and the rule's declared `increment_mm` against the enforced tolerance: a violation is recorded only when that absolute difference is **strictly greater** than the tolerance, so a deviation exactly equal to the tolerance passes. Each violation records the point and the `size_label` of the *lower* size of the offending pair.

`violation_count` is the number of violations found across all points. When there are none, `first_violation_point` and `first_violation_from_size_label` are null; otherwise they are taken from the first violation in the walk order above — outermost by measurement point, innermost by ascending `sort_index`.

Three outcomes follow, and they carry different side effects:

- **No violations** advances `SUBMITTED → VERIFIED`. `violation_count` is written as 0, both first-violation fields are cleared to null, and `tolerance_applied_mm` is rewritten from this run. `verified_by_user_id` records the acting `X-User-ID` and `verified_at` records the logical clock instant. Any *other* specification of the same item that was in `VERIFIED` moves to `SUPERSEDED`, refreshing that row's `updated_at` and incrementing its `version` — so an item never holds two verified specifications at once.
- **Violations found while `revision_round` is strictly below 3** advances `SUBMITTED → CORRECTION_REQUESTED`. `violation_count`, `first_violation_point`, `first_violation_from_size_label`, and `tolerance_applied_mm` are all written from the run, and `correction_reason` is set to `GRADE_TOLERANCE_VIOLATION`. The vendor is then charged for the round: `correction_round_count` increases by 1 and `correction_spend_cents` increases by 2,500 cents, and that debit is applied even when it pushes the running spend past `correction_budget_cents`. `reliability_score_bp` is recomputed per §2.11 and the vendor's `status` is re-derived from the new score.
- **Violations found while `revision_round` is at least 3** advances `SUBMITTED → REJECTED`, a terminal state. `violation_count` and both first-violation fields are written from the run, but **no vendor debit is applied** — the correction allowance for this specification is exhausted, not overdrawn further. Rejection also drags the item's readiness axis back: if the item's `fit_readiness` was `CHART_MAPPED` or `GUIDANCE_READY`, it returns to `UNVERIFIED` and the item's `version` increments by 1. That readiness drop stops there — unlike the chart-retirement and chronic cascades it terminates no deployment, so the item's running deployments are left exactly as they were, and the item's `listing_status` and its active mapping are untouched.

Answering a correction request is the brand's move. Resubmission is permitted only from `CORRECTION_REQUESTED`, only by the owning brand, only while the item is not `DELISTED`, and only while `correction_spend_cents` is less than or equal to `correction_budget_cents` — an overdrawn allowance blocks the resubmission with `ERR_VENDOR_CORRECTION_BUDGET_EXHAUSTED` and HTTP 402. The request replaces the stored `size_points` wholesale, and replaces `grade_rules` as well when that array is supplied; when `grade_rules` is omitted the previously declared rules stand. `revision_round` then increases by 1, `correction_reason` is cleared to null, and the specification returns to `SUBMITTED` for another verification pass. The verdict fields of the previous run are deliberately *not* cleared: `violation_count`, `first_violation_point`, `first_violation_from_size_label`, and `tolerance_applied_mm` all keep the values the last verification wrote, and are rewritten only when the next verification runs. Because verification lands on `REJECTED` once `revision_round` has reached 3, the `CORRECTION_REQUESTED → SUBMITTED → CORRECTION_REQUESTED` loop can run at most three times before the specification is permanently refused.

One further path into `CORRECTION_REQUESTED` exists and it is not initiated by anyone: when an item's chronic-return classification flips to `CHRONIC`, the item's single `VERIFIED` specification is reopened by the system into `CORRECTION_REQUESTED` with `correction_reason` set to `CHRONIC_FIT_RETURNS`. This reopening happens only when the specification is in `VERIFIED` and is the item's only verified specification. It carries the same vendor consequences as a tolerance failure: `correction_round_count` increases by 1, `correction_spend_cents` increases by 2,500 cents, `reliability_score_bp` is recomputed, and vendor `status` is re-derived. It is this reopening of an already-verified specification that makes the specification lifecycle a cycle rather than a one-way pipeline.

### 3.3. Standardizing Size Charts and Mapping Brand Sizes Onto Them

Brands disagree about what a size label means, so the program keeps its own standardized charts and maps each brand's labels onto them. A `MerchOpsAdmin` drafts a chart with a `chart_code` of 3 to 16 characters that must be free across all charts, the `size_system` its rows are labelled in, the `category_code` it standardizes, and the `rows` themselves. Each row is an object carrying a `size_label`, a `sort_index`, the body-measurement band the row covers as `body_chest_min_mm`, `body_chest_max_mm`, `body_waist_min_mm`, and `body_waist_max_mm`, and the four conversion columns `conversion_us_alpha`, `conversion_us_numeric`, `conversion_eu`, and `conversion_uk`. At least 2 rows are required, `size_label` values must be distinct, and `sort_index` values must be distinct and contiguous from 0. A new chart opens in `DRAFT` with `row_count` set to the number of rows supplied and `median_row_index` set to the row count less 1, divided by 2, with any fraction discarded — that index is the fallback anchor the recommendation engine reaches for when it has nothing better. Its `retire_reason_code` opens null. Draft-time validation stops at the structural conditions just listed: the body-measurement bands are *not* checked for ordering or overlap and the four conversion columns need only be present as strings of any content, so a chart carrying overlapping bands, a `body_chest_min_mm` above its own `body_chest_max_mm`, or blank conversion values is accepted as a `DRAFT` and refused later, at standardization.

Standardizing a chart is the gate that makes it usable. It is permitted only from `DRAFT`, and it re-runs three structural checks before advancing the chart `DRAFT → STANDARDIZED`: the `sort_index` values must be contiguous from 0, the body-chest bands must be strictly increasing and non-overlapping across consecutive rows in `sort_index` order, and every row must carry non-empty values in all four conversion columns. A failure on any of the three is reported as `ERR_CHART_ROWS_INVALID`. On success, `row_count` and `median_row_index` are refreshed from the stored rows.

Retiring a standardized chart is where the program's longest non-return cascade begins. Retirement is permitted only from `STANDARDIZED`, stores the supplied `retire_reason_code` of `SUPERSEDED_BY_NEW_CHART`, `VENDOR_SYSTEM_CHANGE`, or `DATA_QUALITY`, and moves the chart to `RETIRED`, a terminal state. Every size chart mapping of that chart whose `status` is `ACTIVE` moves to `SUPERSEDED` with `superseded_reason` `CHART_RETIRED`. Each such supersession drags its item's `fit_readiness` back to `UNVERIFIED` — but only where there is something to drop: an item already at `UNVERIFIED` is left alone entirely, its `version` unchanged and none of its deployments touched. Each of those readiness drops in turn terminates that item's `ACTIVE` deployments whose intervention `lever` is `FIT_RECOMMENDATION_BADGE` or `SIZE_CHART_STANDARDIZATION`, with `terminated_reason_code` `MAPPING_SUPERSEDED` and `window_end` rewritten to the logical clock where the clock is earlier. And each of those terminations makes the owning intervention recompute `spend_cents`, `gross_savings_cents`, `net_savings_cents`, and `funding_posture`. Four entities move on one request.

Mapping is a `FitAnalyst` action. The payload names the `item_id` whose brand sizes are being mapped, the `chart_id` of the standardized chart they map onto, the `size_label_pairs` themselves, and the `expected_item_version` demanded by §2.7. Each pair is an object carrying a `spec_size_label` — a label from the item's verified specification — and a `chart_size_label` from the chart's rows. At least one pair is required; `spec_size_label` values must be distinct within the request, and so must `chart_size_label` values. The item must have exactly one specification in `VERIFIED`, otherwise `ERR_SPEC_NOT_VERIFIED`; the chart must be `STANDARDIZED` and its `category_code` must equal the item's `category_code`, otherwise `ERR_CHART_NOT_STANDARDIZED`; and every `spec_size_label` must exist among that verified specification's `size_points` while every `chart_size_label` must exist among the chart's `rows`, otherwise `ERR_SIZE_LABEL_NOT_IN_SPEC` and nothing at all is written.

When the mapping is accepted, its coverage figures are computed from the single verified specification and the submitted pairs, and nothing else. `mapped_row_count` is the number of pairs accepted. `spec_size_point_count` is the number of `size_points` on that verified specification at the moment of mapping. `coverage_bp` is `mapped_row_count` multiplied by 10,000, divided by `spec_size_point_count`, with any fraction discarded — and it is 0 when `spec_size_point_count` is 0. `unmapped_size_labels` lists every `size_label` from the specification that no pair claimed, ordered by that specification's `sort_index` ascending. The new mapping opens with `status` `ACTIVE` and `superseded_reason` null.

Only one mapping per item is `ACTIVE` at a time. Any prior `ACTIVE` mapping of that item moves to `SUPERSEDED` with `superseded_reason` `NEW_MAPPING`. The item's readiness axis then reacts: an item at `UNVERIFIED` advances to `CHART_MAPPED`; an item already at `CHART_MAPPED` stays at `CHART_MAPPED`, the further mapping being accepted and merely superseding the prior one; and an item that had reached `GUIDANCE_READY` falls back to `CHART_MAPPED`, so fit guidance stops being servable until it is published again. In every case the item's `version` increments by 1 and its `listing_status` is untouched, and creating a mapping never terminates a deployment — not even when it pulls the item back from `GUIDANCE_READY` to `CHART_MAPPED`. The readiness axis also falls from `CHART_MAPPED` or `GUIDANCE_READY` all the way to `UNVERIFIED`, with the item's `version` incrementing by 1, in three circumstances that are not mapping creations: when the item's `ACTIVE` mapping is superseded with `superseded_reason` `CHART_RETIRED`, when the item's verified specification is reopened into `CORRECTION_REQUESTED`, and when a verification run lands on `REJECTED` as §3.2 describes.

### 3.4. Enhancing the Product Page and Publishing Fit Guidance

Fit guidance is not served off measurements alone; the program's own research says the product page has to carry the fit model's body data and enough detail imagery for the shopper to judge fabric and seams. A `MerchOpsAdmin` records that work by submitting `model_measurements_published` as a boolean and `detail_image_count` as the number of published fabric and seam detail images, which must be at least 0, optionally accompanied by `model_height_cm` — the fit model's height in whole centimetres, at least 0 — and `model_worn_size_label`, the brand size label the model wears in the imagery, of at least 1 character. The two required fields are always written. The two optional fields make this a partial update rather than a full replacement: each is written only when it is actually supplied, so a request that omits one — or sends it as an explicit `null` — leaves whatever the item already stored for that field exactly as it was rather than clearing it to null. The `pdp_review_required` flag is cleared to false on every such request, and the item's `version` increments by 1 even when the request changed no stored value at all. This enhancement is refused when the item is `DELISTED`.

Publishing guidance is a `FitAnalyst` action and it advances the readiness axis from `CHART_MAPPED` to `GUIDANCE_READY`, after which fit recommendations become servable for the item. Five conditions must all hold. The item's `fit_readiness` must currently be `CHART_MAPPED`. The item must still have exactly one specification in `VERIFIED`, otherwise `ERR_SPEC_NOT_VERIFIED`. The item's `ACTIVE` mapping must exist and its chart must still be `STANDARDIZED` with a matching `category_code`, otherwise `ERR_CHART_NOT_STANDARDIZED`. That mapping's `coverage_bp` must be at least 8,000 — eighty percent of the specification's size run must be mapped — otherwise `ERR_MAPPING_COVERAGE_INSUFFICIENT`. And the product page must be complete: `model_measurements_published` must be true and `detail_image_count` must be at least 3, otherwise `ERR_PDP_ENHANCEMENT_INCOMPLETE`.

The same action doubles as the storefront restoration path. When the item's `listing_status` is `SUSPENDED` and its `fit_watch_state` is no longer `CHRONIC`, and every condition of the readiness advance above holds, `listing_status` moves from `SUSPENDED` back to `LISTED`. An item still classified `CHRONIC` cannot be restored this way. The item's `version` increments by 1.

### 3.5. Reviewer Fit Feedback

Shoppers contribute the other half of the fit signal. A `Customer` publishes feedback on an item by supplying the `item_id`, their own `customer_profile_id`, the `purchased_size_label` they bought, a `fit_verdict` of `TOO_SMALL`, `SLIGHTLY_SMALL`, `TRUE_TO_SIZE`, `SLIGHTLY_LARGE`, or `TOO_LARGE`, and an optional free-text `comment`. The `purchased_size_label` need only be a non-empty string: it is stored as supplied and is never checked against the item's specification, its mapping, its chart, or the shopper's own order lines. The `comment` is likewise stored verbatim under no length bound, and is null when omitted. The submitted `customer_profile_id` must equal the acting `X-User-ID`, and a shopper may hold only one `ACTIVE` feedback row per item — a second attempt is refused with `ERR_DUPLICATE_FIT_FEEDBACK`.

Two values are computed at creation. `verdict_offset_centi` translates the verdict into a size-step offset in hundredths of a step: `TOO_SMALL` becomes positive 100, `SLIGHTLY_SMALL` positive 50, `TRUE_TO_SIZE` zero, `SLIGHTLY_LARGE` negative 50, and `TOO_LARGE` negative 100. The sign convention is that a reviewer reporting the garment ran small pushes the recommendation *up* the size run. `signal_weight` is 200 when the reviewer actually owns the item — that is, when the reviewer has an order line on this item whose `status` is `DELIVERED`, `RETURN_IN_PROGRESS`, `RETURNED`, or `KEPT` — and 100 otherwise, so verified purchasers count double. The row opens with `status` `ACTIVE` and `retract_reason` null, and the item's pool grows accordingly: `fit_signal_weight_total` increases by exactly this row's `signal_weight` and `active_fit_feedback_count` increases by 1.

Retraction is available to the author only. It is permitted only while the row's `status` is `ACTIVE` — a second attempt is refused with `ERR_FEEDBACK_ALREADY_RETRACTED` — and only when the acting `X-User-ID` equals the row's `customer_profile_id`, otherwise `ERR_NOT_RESOURCE_OWNER`. The supplied `retract_reason` of `AUTHOR_WITHDRAWN` or `MODERATION_REMOVED` is stored, the row moves `ACTIVE → RETRACTED`, and the item's pool shrinks by exactly the amounts it grew by: `fit_signal_weight_total` decreases by this row's `signal_weight` and `active_fit_feedback_count` decreases by 1. A retracted row contributes nothing to any recommendation signal pool from that moment on.

### 3.6. Serving the Fit Recommendation

The recommendation read is available to a `Customer` for their own profile, and to a `FitAnalyst` or `MerchOpsAdmin` for inspection. The shopper is named by an optional `customer_profile_id` query parameter, and it is that value the `Customer` ownership check of §2.1 compares against `X-User-ID`; a `Customer` who supplies no value at all passes that check and simply receives the population variant. The parameter is not a foreign key: a value naming no existing profile is not a 404, and an empty value counts as not supplied — either way the personal pool comes up empty and the population variant runs. It is refused with `ERR_GUIDANCE_NOT_READY` unless the item's `fit_readiness` is `GUIDANCE_READY`, and likewise refused with `ERR_GUIDANCE_NOT_READY` when the item carries no `ACTIVE` mapping or that mapping's chart cannot be found. The read never writes anything. Its response carries `recommended_size_label`, `confidence_bp`, `variant_applied`, `sample_count`, `coverage_bp`, `suppressed`, `anchor_index`, and `recommended_index`.

Two variants of the calculation exist and they share one skeleton. The item's `ACTIVE` mapping is located, along with the `STANDARDIZED` chart it points at; the chart's rows are ordered by `sort_index` ascending; and `coverage_bp` is read from the mapping. From the variant's signal pool, a weighted offset in hundredths of a size step is formed: when the total of the weights is 0 the weighted offset is 0, and otherwise it is the sum over the pool of each contribution's offset multiplied by its weight, divided by the sum of the weights, rounded half up. That weighted offset is converted into a whole size step by dividing by 100 and rounding half up, with "half" rounding away from zero for negative values. The recommended row index is the variant's anchor index plus that step shift, clamped to lie between 0 and the chart's `row_count` less 1 inclusive. `confidence_bp` is the variant's confidence cap multiplied by `coverage_bp`, divided by 10,000, with any fraction discarded. The result is `suppressed` when `confidence_bp` is **strictly below** 6,000 — a confidence of exactly 6,000 basis points still emits a recommendation. When suppressed, `recommended_size_label` is null; otherwise it is the `size_label` of the chart row at the recommended index.

Only two kinds of row ever enter a signal pool: fit feedback rows whose `status` is `ACTIVE`, and return cases whose `status` is `RESOLVED_REFUNDED`. Retracted feedback, cases still in `TRIAGE` or in a review branch, `RESOLVED_DENIED` cases, and `VOIDED` cases are all excluded.

The **history_weighted** variant applies when the request supplies a `customer_profile_id` **and** that shopper's own pool has at least 3 contributions. That personal pool is the union of two streams, both restricted to items whose `category_code` equals the target item's `category_code`: the shopper's own `ACTIVE` fit feedback rows, each contributing the offset implied by its `fit_verdict` with weight equal to its `signal_weight`; and the shopper's `RESOLVED_REFUNDED` return cases whose `reason_family` is `FIT` on their own order lines, each contributing positive 100 hundredths for a `reason_code` of `FIT_TOO_SMALL` and negative 100 hundredths for `FIT_TOO_LARGE`, with a fixed weight of 200. `sample_count` is the number of contributions in that union. The anchor index is personal: it is the `sort_index` of the chart row whose `size_label` equals the `chart_size_label` that the mapping pairs with the `size_label` of the shopper's most recent order line on an item of the same `category_code`, ordered by `delivered_at` descending, tie-broken by `created_at` descending and then by reverse order of ingest, so that of two otherwise indistinguishable lines the one ingested later wins; when no such order line exists, or when its `size_label` has no pair in the mapping's `size_label_pairs`, the anchor falls back to the chart's `median_row_index`. The confidence cap is the smaller of 9,500 and the quantity 4,500 plus 1,000 multiplied by `sample_count`.

The **population_fallback** variant applies when the request omits `customer_profile_id`, or when the shopper's personal pool has fewer than 3 contributions. Its signal pool is every `ACTIVE` fit feedback row on *this* item regardless of author, each contributing the offset implied by its `fit_verdict` with weight equal to its `signal_weight`, and `sample_count` is the size of that pool. The anchor index is always the chart's `median_row_index`. The confidence cap is the smaller of 8,000 and the quantity 2,000 plus 500 multiplied by `sample_count`.

For identical stored data the two variants therefore return different `confidence_bp` values and may return different `recommended_size_label` values. The response echoes which one ran in `variant_applied` so that the divergence is observable rather than mysterious.

### 3.7. Shoppers, Return Policy, Purchases, and Opening a Return

Shopper records are created by a `MerchOpsAdmin` with a unique `email` — a string of at least 1 character, stored exactly as supplied and compared for uniqueness by exact, case-sensitive equality, so two addresses differing only in case are two distinct shoppers — and an optional `tier` of `STANDARD` or `PLUS`; when `tier` is omitted it defaults to `STANDARD`. A new profile opens with `abuse_status` `CLEAR`, `abuse_strike_count` at 0, `purchase_line_count` at 0, `return_case_count` at 0, `change_of_mind_count` at 0, `return_rate_bp` at 0, and `refunded_total_cents` at 0. Its `policy_class` opens at `STANDARD_WINDOW`, except that a `PLUS` shopper with `CLEAR` standing opens at `EXTENDED_WINDOW`.

Return policy is expressed as rows, and the same shape serves two purposes. A category default is authored by a `MerchOpsAdmin` against the category as a whole; the row is stamped with `scope` `CATEGORY_DEFAULT` and its `customer_profile_id` is null. A customer override is authored against one shopper's profile; the row is stamped with `scope` `CUSTOMER_OVERRIDE`, its `customer_profile_id` is set to the profile it was authored under, and creating it increments that `CustomerProfile`'s `version` by 1 — which is exactly why the override write demands `expected_customer_profile_version` per §2.7. Either way the row declares the `category_code` it governs, a `window_days` base return window of at least 1 day, a `restocking_applies` boolean deciding whether change-of-mind resolutions withhold a restocking fee, a `non_refundable_shipping` boolean deciding whether the line's allocated shipping is withheld from the refund, an `effective_from` instant that is the first instant the row applies inclusive, and an optional `effective_to` instant that is the last instant it applies inclusive — a null `effective_to` means the row is open-ended. No ordering check binds the two: an `effective_to` earlier than its own `effective_from` is accepted as supplied rather than refused, and simply yields a row that resolution never selects.

Overrides for one shopper and one category may not overlap in time. The interval an override occupies is closed at both ends, a null `effective_to` extends without bound, and endpoints that merely touch **do** count as intersecting, so an override running through the 30th and another starting on the 30th collide and the second is refused with `ERR_POLICY_WINDOW_OVERLAP`. The check looks only at existing `CUSTOMER_OVERRIDE` rows of the same shopper and the same `category_code`; a category default covering the same interval is never a collision. Category defaults themselves are not interval-checked at all — any number of them may be authored for one category over overlapping or identical intervals, and the ranking below decides which one governs.

Purchases enter the program as delivered order lines ingested by a `MerchOpsAdmin` from the commerce platform. Each carries the purchasing `customer_profile_id`, the purchased `item_id`, the brand `size_label` bought (which need only be a non-empty string and is never checked against the item's specification, its mapping or its chart), a `quantity` of at least 1, the `unit_price_cents` actually charged which must be at least 1, the `shipping_allocated_cents` apportioned to this line which must be at least 0, and the `delivered_at` instant. That delivery instant is the anchor for the return window and for every measurement window in the program, so it is authoritative rather than advisory; it is not bounded against the logical clock, so a `delivered_at` in the future is accepted exactly as supplied. The line's `gross_line_cents` is computed as `unit_price_cents` multiplied by `quantity`, and the line opens with `status` `DELIVERED`. Ingest is itself a small cascade: the item's `units_sold_count`, its two return rates, its `chronic_return_score_bp`, and its `fit_watch_state` are all recomputed, and so are the shopper's `purchase_line_count`, `return_rate_bp`, `abuse_status`, and `policy_class` — which means an ingest can by itself lift a shopper out of a rate-driven `BLOCKED` standing, because the extra purchase line dilutes `return_rate_bp` below the rate rule's threshold.

Opening a return is the shopper's own action. The request names the `order_line_id` being returned, the `requested_reason_code` the shopper selected — one of `FIT_TOO_SMALL`, `FIT_TOO_LARGE`, `QUALITY_DEFECT`, `EXPECTATION_MISMATCH`, or `CHANGE_OF_MIND` — and an optional `comment`, which is type-checked as a string when supplied but is not persisted: the case row carries no comment field and none appears in any response. A shopper whose `abuse_status` is `BLOCKED` cannot open one at all: the request is refused with `ERR_CUSTOMER_RETURN_BLOCKED`. Nor may a line carry two live cases: if the line already has a case in `TRIAGE`, `FIT_REVIEW`, `QUALITY_REVIEW`, `EXPECTATION_REVIEW`, `COOLING_OFF`, `RESOLVED_REFUNDED`, or `RESOLVED_DENIED`, the request is refused with `ERR_DUPLICATE_RETURN_CASE` — only a `VOIDED` prior case leaves the line free to be returned again.

The policy that will govern the case is resolved once, at creation, and **frozen** on the case as `effective_policy_id`; it is never re-resolved later, not even at resolution time. Candidate rows are those whose `category_code` equals the item's `category_code`, whose `effective_from` is at or before the logical clock, whose `effective_to` is either null or at or after the logical clock — the interval is closed on both ends — and which are either category defaults or customer overrides belonging to the purchaser of this order line. Rows for other categories, rows belonging to other shoppers, and rows whose interval has elapsed are excluded. The candidates are then ranked: every `CUSTOMER_OVERRIDE` row outranks every `CATEGORY_DEFAULT` row; within one scope the later `effective_from` wins; and a remaining tie is broken by the later `created_at`, and one still remaining by the later order of creation on the server, never by `id`. The single row at the top of that ranking is the winner. When no candidate exists at all, no case is created and the request fails with `ERR_NO_RETURN_POLICY` and HTTP 422.

From the winner, three values are written on the case. `effective_window_days` is the winner's `window_days` adjusted by the purchaser's `policy_class` and then floored at a hard minimum: a `STANDARD_WINDOW` shopper gets the base window unchanged, an `EXTENDED_WINDOW` shopper gets 30 additional days, a `RESTRICTED_WINDOW` shopper loses 15 days, and whatever the arithmetic yields, the stored value is the larger of that result and 7 days. `return_deadline_at` is the order line's `delivered_at` plus `effective_window_days` whole days. `requested_at` records the logical clock at creation. The request is accepted only when the logical clock is at or before `return_deadline_at` — the comparison is inclusive, so a request landing exactly on the deadline is in time — and a later clock is refused with `ERR_RETURN_WINDOW_CLOSED` and HTTP 422.

A newly created case opens with `status` `TRIAGE`, its `reason_code` copied from `requested_reason_code`, and its `reason_family` derived from that code. The shopper's own `requested_reason_code` is itself a stored field of the case and is echoed on every read of it, and it is never rewritten afterwards — an auditor recoding the case moves `reason_code` and `reason_family` and leaves `requested_reason_code` on the shopper's original selection. The derivation is: `FIT_TOO_SMALL` and `FIT_TOO_LARGE` both map to `FIT`, `QUALITY_DEFECT` maps to `QUALITY`, `EXPECTATION_MISMATCH` maps to `EXPECTATION`, and `CHANGE_OF_MIND` maps to `CHANGE_OF_MIND`. Its `item_condition`, `classified_by_user_id`, `resolved_by_user_id`, and `void_reason` are all null, and `restocking_fee_cents`, `refund_amount_cents`, and `total_cost_cents` are all 0. The purchased line moves to `RETURN_IN_PROGRESS`, and the shopper's `return_case_count`, `return_rate_bp`, `abuse_status`, and `policy_class` are recomputed — which means opening a return can, by itself, push a shopper into `BLOCKED` on the rate rule.

### 3.8. Coding, Closing, and Reversing Returns; Shopper Standing

Return reasons are audited, not taken on trust. A `ReturnsAuditor` codes a case in `TRIAGE` by supplying the `reason_code` they believe is correct, optionally with an `evidence_note` recording what they looked at — the note is type-checked as a string when supplied but is not stored on the case and appears in no response. The supplied code overwrites the case's `reason_code`, `reason_family` is re-derived from it, and the acting `X-User-ID` is stamped onto `classified_by_user_id`. Coding is where the case forks: a code of `FIT_TOO_SMALL` or `FIT_TOO_LARGE` moves the case `TRIAGE → FIT_REVIEW`, `QUALITY_DEFECT` moves it `TRIAGE → QUALITY_REVIEW`, `EXPECTATION_MISMATCH` moves it `TRIAGE → EXPECTATION_REVIEW`, and `CHANGE_OF_MIND` moves it `TRIAGE → COOLING_OFF`. Coding a case that is not in `TRIAGE` is refused with `ERR_INVALID_RETURN_CASE_STATE`.

Closing the case is a second `ReturnsAuditor` action and it must be a *different* operator: the acting `X-User-ID` must differ from the stored `classified_by_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`. It is accepted from any of the four review branches — `FIT_REVIEW`, `QUALITY_REVIEW`, `EXPECTATION_REVIEW`, or `COOLING_OFF` — and from nowhere else. The request supplies the warehouse's `item_condition` grading of the returned goods, one of `RESELLABLE_A`, `RESELLABLE_B`, or `SALVAGE`, optionally with a `resolution_note` that, like the `evidence_note` above, is type-checked when supplied and then discarded rather than stored. Where the case lands is decided by the purchaser's standing rather than by the auditor: a purchaser whose `abuse_status` is not `BLOCKED` yields `RESOLVED_REFUNDED`, and a purchaser whose `abuse_status` is `BLOCKED` yields `RESOLVED_DENIED`. The acting `X-User-ID` is stamped onto `resolved_by_user_id` either way.

**The fee and the refund** are computed first, before any cost posting is written. The restocking-fee tier is keyed on the order line's `gross_line_cents` and never on the refund, which is what keeps the pair well defined in a single pass: a gross below 5,000 cents carries a tier of 0 basis points, a gross from 5,000 cents up to but not including 20,000 cents carries 1,000 basis points, and a gross of 20,000 cents or more carries 1,500 basis points. The base fee is that tier multiplied by the gross, divided by 10,000, rounded half up to whole cents. A fee is actually withheld only when three things hold at once: the case's `reason_family` is `CHANGE_OF_MIND`, the policy frozen on the case has `restocking_applies` true, and the case is landing on `RESOLVED_REFUNDED`. In that situation a multiplier is applied — 15,000 basis points when the purchaser's `abuse_status` is `RESTRICTED`, and 10,000 basis points otherwise, which is a multiplier of one — and `restocking_fee_cents` is the base fee multiplied by that multiplier, divided by 10,000, rounded half up. In every other situation `restocking_fee_cents` is 0. Withheld shipping is the line's `shipping_allocated_cents` when the frozen policy has `non_refundable_shipping` true, and 0 otherwise. `refund_amount_cents` is then the gross less the restocking fee less the withheld shipping, floored at 0 so it can never go negative. A case landing on `RESOLVED_DENIED` short-circuits the whole computation: both `restocking_fee_cents` and `refund_amount_cents` are 0.

**The cost postings** are written second, once the refund is known, as `ORIGINAL` ledger rows in a fixed component order. `FREIGHT_INBOUND` is a flat per-category charge: 795 cents for `TOPS`, 895 for `BOTTOMS`, 995 for `DRESSES`, 1,495 for `OUTERWEAR`, and 1,295 for `FOOTWEAR`. `PROCESSING_LABOR` is a labor rate of 62 cents per minute multiplied by the handling minutes the case's `reason_family` consumes — 9 minutes for `FIT`, 17 for `QUALITY`, 11 for `EXPECTATION`, and 7 for `CHANGE_OF_MIND` — rounded half up. `REFURB_REPACK` is a share of the gross keyed on `item_condition`: 150 basis points for `RESELLABLE_A`, 400 for `RESELLABLE_B`, and 0 for `SALVAGE`, multiplied by the gross, divided by 10,000, rounded half up. `MARKDOWN_LOSS` is the same shape with different shares: 0 basis points for `RESELLABLE_A`, 1,200 for `RESELLABLE_B`, and 6,500 for `SALVAGE`. `PAYMENT_FEE_UNRECOVERED` is 290 basis points of the **refund** — not the gross — divided by 10,000 and rounded half up. `VENDOR_CHARGEBACK_CREDIT` is written only for the `QUALITY` family and is the arithmetic negation of 4,000 basis points of the gross, divided by 10,000, rounded half up; it is a credit because the vendor is being charged back. One `ORIGINAL` posting row is written per component in exactly the order just given, including components whose amount works out to 0. A case landing on `RESOLVED_DENIED` writes only two postings — `FREIGHT_INBOUND` and `PROCESSING_LABOR`. Rounding is per component and never deferred, as §2.6 insists. The case's `total_cost_cents` is the integer sum of the `amount_cents` of the `ORIGINAL` rows just written.

**The cascades** differ by branch, and the differences are the point of the fork. All four refunded branches share a common core: the order line moves to `RETURNED`, the shopper's `refunded_total_cents` grows by the refund just paid, the item's `total_return_count` increases by 1, the item's `return_cost_accrued_cents` is re-summed from the ledger, and the item's `chronic_return_score_bp` and `fit_watch_state` are re-derived. Beyond that core:

- A `FIT_REVIEW → RESOLVED_REFUNDED` close carries no restocking fee and no vendor chargeback. It increases the item's `fit_return_count` by 1 alongside `total_return_count`, and it is the branch most likely to move `fit_watch_state`, because fit returns carry the heavier weight in the chronic score.
- A `QUALITY_REVIEW → RESOLVED_REFUNDED` close writes the additional negative `VENDOR_CHARGEBACK_CREDIT` posting. It leaves `fit_return_count` untouched and advances only `total_return_count`. It also charges the brand: the owning vendor's `quality_chargeback_count` increases by 1, after which `reliability_score_bp` and vendor `status` are re-derived per §2.11.
- An `EXPECTATION_REVIEW → RESOLVED_REFUNDED` close carries no restocking fee and no chargeback. It increases the item's `expectation_return_count` by 1 alongside `total_return_count`, sets the item's `pdp_review_required` flag to true so that the product page copy is queued for a rewrite, and recomputes `chronic_return_score_bp` — where the expectation rate contributes its own weighted share — and re-derives `fit_watch_state`.
- A `COOLING_OFF → RESOLVED_REFUNDED` close is the branch where a restocking fee can actually be withheld, including the abuse multiplier when the purchaser is `RESTRICTED`. It advances only `total_return_count` on the item and leaves both the fit and expectation counters untouched. On the shopper it increases `change_of_mind_count` by 1 and then recomputes `abuse_strike_count`, re-deriving `abuse_status` and `policy_class`.

The two denied outcomes are deliberately thinner. Any of the four review branches closing on `RESOLVED_DENIED` writes `refund_amount_cents` 0 and `restocking_fee_cents` 0, writes only the `FREIGHT_INBOUND` and `PROCESSING_LABOR` postings, and moves the order line to `KEPT` rather than `RETURNED` — the shopper keeps the goods and is paid nothing. The item counters for the case's `reason_family` still advance, because a denied case is a closed case: a denied fit case still raises `fit_return_count` and `total_return_count`, and a denied expectation case still raises `expectation_return_count` and `total_return_count` and still sets `pdp_review_required`. A denied change-of-mind case, by contrast, earns **no** abuse strike, because strikes are counted only over refunded change-of-mind cases, and it leaves `change_of_mind_count` untouched as well, since that counter likewise reads only `RESOLVED_REFUNDED` change-of-mind cases. A denied quality case is similarly free for the brand: `quality_chargeback_count` counts only refunded quality cases, so the vendor's `reliability_score_bp` and `status` come back unchanged even though the vendor recomputation does run.

**The chronic-return score** is what turns accumulated returns into an intervention. It is recomputed on every case resolution, on every case void, on every order-line ingest, and on every ops-run, and it is lifetime-to-date with no time window. Units are the sum of `quantity` over the item's order lines whose `status` is `DELIVERED`, `RETURN_IN_PROGRESS`, `RETURNED`, or `KEPT`. `fit_return_rate_bp` is `fit_return_count` multiplied by 10,000, divided by those units, with any fraction discarded, and is 0 when units are 0; `expectation_return_rate_bp` is the same shape over `expectation_return_count`. Both counters read only cases whose `status` is `RESOLVED_REFUNDED` or `RESOLVED_DENIED`, so `VOIDED` cases are excluded entirely. `chronic_return_score_bp` is then 7,500 multiplied by `fit_return_rate_bp`, plus 2,500 multiplied by `expectation_return_rate_bp`, all divided by 10,000, with any fraction discarded — a three-quarters weight on fit and a one-quarter weight on expectation. `fit_watch_state` follows from the score and the raw fit count together: `CHRONIC` when the score is at least 2,500 basis points **and** `fit_return_count` is at least 2; otherwise `WATCH` when the score is at least 1,500 basis points **and** `fit_return_count` is at least 1; otherwise `NORMAL`. Because the classification is re-derived rather than latched, it walks in both directions.

A flip of `fit_watch_state` to `CHRONIC` fires the program's longest cascade, and it fires from a return resolution or from an ops-run sweep alike. An item whose `listing_status` is `LISTED` moves `LISTED → SUSPENDED`, incrementing its `version` by 1. An item whose `fit_readiness` is `GUIDANCE_READY` falls to `UNVERIFIED`, after which the fit-recommendation read for that item fails with `ERR_GUIDANCE_NOT_READY`, and every `ACTIVE` deployment of the item whose intervention `lever` is `FIT_RECOMMENDATION_BADGE` or `SIZE_CHART_STANDARDIZATION` moves to `TERMINATED` with `terminated_reason_code` `MAPPING_SUPERSEDED` and `window_end` rewritten to the logical clock. An item at `CHART_MAPPED` likewise falls to `UNVERIFIED`, but that fall terminates no deployment: on this cascade the deployment closure is tied specifically to a fall *from* `GUIDANCE_READY`, unlike the chart-retirement cascade of §3.3, where a fall from `CHART_MAPPED` closes deployments too. Each of these axis moves is a mutation of the item row in its own right, separate from the mutation that rewrote the counters, so a chronic flip on an item that was `LISTED` and `GUIDANCE_READY` advances that item's `version` by 3 within the one request. And the item's single `VERIFIED` specification is reopened into `CORRECTION_REQUESTED` with `correction_reason` `CHRONIC_FIT_RETURNS`, which debits the vendor 2,500 cents, raises `correction_round_count` by 1, and re-derives `reliability_score_bp` and vendor `status`.

**Reversal** is available to a `ReturnsAuditor` on a case in `RESOLVED_REFUNDED` or `RESOLVED_DENIED`, and it moves the case to `VOIDED`, a terminal state. The request supplies a `void_reason` of `AUDIT_REVERSAL`, `DUPLICATE_CASE`, or `FRAUD_CONFIRMED`, which is stored. Exactly one `REVERSAL` posting is written per `ORIGINAL` posting of the case, each with `amount_cents` negated and `reversed_component` naming the component it negates — so a refunded quality case with six original rows produces six reversal rows, and a denied case with two original rows produces two. The case's `refund_amount_cents` and `restocking_fee_cents` keep their historical values as a record of what was once paid, but `total_cost_cents` becomes 0. The order line returns to `DELIVERED`, leaving it eligible to be returned again. On the shopper, `refunded_total_cents` drops by exactly this case's `refund_amount_cents`, and `return_case_count`, `change_of_mind_count`, `abuse_strike_count`, `abuse_status`, and `policy_class` are all recomputed. On the item, `return_cost_accrued_cents`, `fit_return_count`, `expectation_return_count`, `total_return_count`, both rates, `chronic_return_score_bp`, and `fit_watch_state` are all recomputed, so a void can walk an item out of `CHRONIC`. On the vendor, a quality-family case being voided decrements `quality_chargeback_count`, after which `reliability_score_bp` and vendor `status` are re-derived. What reversal does *not* do is unwind transitions that already fired: a specification reopened into `CORRECTION_REQUESTED` stays there, a suspended listing stays suspended, the readiness axis stays where the cascade left it, a `pdp_review_required` flag an expectation case raised stays raised, a deployment the cascade terminated stays terminated, and the 2,500-cent vendor debit stays spent. Only derived aggregates are restored.

**Shopper standing** is derived from the same recomputations, and it moves in both directions. `return_rate_bp` is `return_case_count` multiplied by 10,000, divided by `purchase_line_count`, with any fraction discarded, and is 0 when `purchase_line_count` is 0; `return_case_count` counts the shopper's cases in `TRIAGE`, `FIT_REVIEW`, `QUALITY_REVIEW`, `EXPECTATION_REVIEW`, `COOLING_OFF`, `RESOLVED_REFUNDED`, or `RESOLVED_DENIED`, and `purchase_line_count` counts order lines whose `status` is `DELIVERED`, `RETURN_IN_PROGRESS`, `RETURNED`, or `KEPT`. `abuse_strike_count` is narrower: it counts only the shopper's cases whose `status` is `RESOLVED_REFUNDED`, whose `reason_family` is `CHANGE_OF_MIND`, whose `refund_amount_cents` is strictly greater than 0, and whose `requested_at` is **strictly later** than the logical clock less the trailing abuse window of 180 days. Because that window is measured from the clock on every recomputation, a shopper's standing improves on its own as old strikes fall out of range.

From those two numbers `abuse_status` follows: `BLOCKED` when `abuse_strike_count` is at least 3, **or** when `return_rate_bp` is at least 7,000 and `purchase_line_count` is at least 4; otherwise `RESTRICTED` when `abuse_strike_count` is at least 2; otherwise `WATCH` when `abuse_strike_count` is at least 1; otherwise `CLEAR`. Note that the rate rule can block a shopper who never earned a single change-of-mind strike, so this axis is not a strict ladder — a `CLEAR` shopper can jump straight to `BLOCKED` after a return-case creation, a resolution, a void, or an ops-run, and can drop straight back to `CLEAR` when a void removes a case or an ops-run ages every strike out, provided their strike count is below 1 and the rate rule no longer holds. Every intermediate rung behaves symmetrically: a shopper escalates `CLEAR → WATCH` when the strike count reaches 1 while still below 2, `WATCH → RESTRICTED` when it reaches 2 while still below 3, and `RESTRICTED → BLOCKED` when it reaches 3 or the rate rule fires; and they de-escalate `BLOCKED → RESTRICTED` when the strike count falls below 3 while remaining at least 2 and the rate rule no longer holds, `RESTRICTED → WATCH` when it falls below 2 while remaining at least 1, and `WATCH → CLEAR` when it falls below 1. Every one of those moves re-derives `policy_class`.

`policy_class` itself is a three-way derivation: `RESTRICTED_WINDOW` when `abuse_status` is `RESTRICTED` or `BLOCKED`, `EXTENDED_WINDOW` when the shopper's `tier` is `PLUS` and `abuse_status` is `CLEAR`, and `STANDARD_WINDOW` in every other case — which includes a `PLUS` shopper who has slipped to `WATCH`. The consequences are concrete: `RESTRICTED_WINDOW` shortens every future `effective_window_days` by 15 days subject to the 7-day floor, and it is `RESTRICTED` standing specifically that arms the 15,000-basis-point multiplier on change-of-mind restocking fees. `BLOCKED` standing is harsher still: new return cases are refused outright with `ERR_CUSTOMER_RETURN_BLOCKED`, and cases already open when the block landed close on `RESOLVED_DENIED` instead of `RESOLVED_REFUNDED`.

### 3.9. Return-Reduction Levers, Measurement Windows, and the Ops-Run Checkpoint

The program's whole justification rests on being able to say what each lever bought. A `MerchOpsAdmin` defines a lever by supplying a program `name` of 1 to 200 characters, the `lever` mechanism itself — one of `SIZE_CHART_STANDARDIZATION`, `PDP_MODEL_MEASUREMENTS`, `DETAIL_IMAGERY`, `FIT_RECOMMENDATION_BADGE`, or `VENDOR_SPEC_CORRECTION` — and a `unit_cost_cents` reference cost per deployment of at least 0, used for program reporting. A new lever opens with `funding_posture` `FUNDED` and every savings counter at 0: `deployment_count`, `measured_deployment_count`, `gross_savings_cents`, `spend_cents`, and `net_savings_cents`.

A lever is exercised by scheduling it on one item over one measurement window. The deployment request names the `intervention_id` of the lever, the `item_id` it is deployed on, a `window_start` that is the inclusive start of the measurement window, a `window_end` that is the **exclusive** end of it, and the `spend_cents` actually spent on this deployment, which must be at least 0. The `window_start` must be strictly earlier than the `window_end`. Windows are unique per item and lever: for the same combination of `item_id` and the lever's `lever` value, the new half-open window must not intersect an existing window whose deployment is neither `TERMINATED` nor `MEASURED`, and because the window is half-open, a new `window_start` that exactly equals an existing `window_end` does **not** intersect and is accepted. A collision is refused with `ERR_DEPLOYMENT_WINDOW_OVERLAP`. The target item must currently be `LISTED` — not `DRAFT`, not `SUSPENDED` — otherwise `ERR_DEPLOYMENT_ITEM_NOT_LISTED`. An accepted deployment opens with `status` `SCHEDULED`, its lever's `deployment_count` grows by 1, and all six measurement fields — `baseline_units_count`, `baseline_return_rate_bp`, `window_units_count`, `measured_return_rate_bp`, `avoided_return_count`, and `attributed_savings_cents` — are null, as is `terminated_reason_code`, because nothing has been observed yet.

A running deployment can be stopped early by a `MerchOpsAdmin`. An early stop is permitted only from `ACTIVE`, otherwise `ERR_INVALID_DEPLOYMENT_STATE`. The request carries a required `terminated_reason_code`, and any of the four declared codes is accepted from the operator and stored exactly as supplied — the endpoint does not insist on `MANUAL_STOP`, it is merely the code an operator-driven stop is expected to record. The three system-driven closures record `WINDOW_ELAPSED` when a window simply elapsed, `ITEM_DELISTED` when the item left the storefront, and `MAPPING_SUPERSEDED` when the item's readiness axis fell away underneath the deployment. In every closure, where the logical clock is earlier than the stored `window_end`, the `window_end` is rewritten to the clock, so the measured window is never longer than the deployment actually ran. Closure is also the moment spend becomes real: the lever's `spend_cents` is the sum of `spend_cents` over its deployments whose `status` is `TERMINATED` or `MEASURED`, so a `SCHEDULED` or `ACTIVE` deployment contributes nothing to recognized spend, and closing one recognizes it and re-derives `net_savings_cents` and `funding_posture`.

The periodic **ops-run checkpoint** is the only mechanism that advances deployments through their lifecycle, and it advances each deployment by **at most one hop per run**. A `SCHEDULED` deployment whose `window_start` is at or before the logical clock, and whose item is still `LISTED`, moves `SCHEDULED → ACTIVE` and snapshots its baseline. An `ACTIVE` deployment whose `window_end` is at or before the logical clock moves `ACTIVE → TERMINATED` with `terminated_reason_code` `WINDOW_ELAPSED`. A `TERMINATED` deployment moves `TERMINATED → MEASURED`, but only on a *later* run than the one that terminated it — which means walking a deployment from `ACTIVE` all the way to `MEASURED` takes two ops-runs, not one. That last hop carries no clock condition of its own: a `TERMINATED` deployment is measured by the first run that sees it, whatever the clock reads and however its window closed, so a deployment stopped early by an operator, by a delist, or by a readiness fall is measured by the very next run. `MEASURED` is terminal. The run's three passes are fixed in order — every deployment first, then the catalog sweep, then the shopper sweep — so a deployment activated at the head of a run stays `ACTIVE` even when the catalog sweep later that same run suspends its item, and a deployment that the catalog sweep's chronic cascade terminates waits for the following run to be measured.

Baseline and window figures come from the deployment's own item and nothing else. The baseline is snapshotted at activation: `baseline_units_count` is the sum of `quantity` over the item's order lines whose `delivered_at` is strictly before `window_start`; the baseline fit-return count is the number of return cases on exactly those lines whose `reason_family` is `FIT`, whose `status` is `RESOLVED_REFUNDED`, and whose `requested_at` is strictly before `window_start`; and `baseline_return_rate_bp` is that count multiplied by 10,000, divided by `baseline_units_count`, with any fraction discarded, and is 0 when `baseline_units_count` is 0. The measurement is computed at `MEASURED`: `window_units_count` is the sum of `quantity` over the item's order lines whose `delivered_at` is at or after `window_start` and strictly before `window_end`; the in-window fit-return count is the number of `FIT`-family, `RESOLVED_REFUNDED` cases on those lines whose `requested_at` is at or after `window_start` and strictly before `window_end`; and `measured_return_rate_bp` is that count multiplied by 10,000, divided by `window_units_count`, floored, and 0 when `window_units_count` is 0. The improvement is the baseline rate less the measured rate, floored at 0 so a deployment that made things worse is credited with nothing rather than penalized. `avoided_return_count` is that improvement multiplied by `window_units_count`, divided by 10,000, with any fraction discarded — whole avoided returns only. `attributed_savings_cents` is `avoided_return_count` multiplied by the avoided-return valuation for the item's `category_code`: 3,200 cents for `TOPS`, 3,600 for `BOTTOMS`, 4,200 for `DRESSES`, 5,200 for `OUTERWEAR`, and 4,400 for `FOOTWEAR`. A window in which nothing was delivered yields a measured rate of 0, an avoided count of 0, and attributed savings of 0 rather than an arithmetic error. A deployment that never activated at all — one terminated straight out of `SCHEDULED` by a delist — is still measured on a later run: its `window_units_count`, `measured_return_rate_bp`, `avoided_return_count`, and `attributed_savings_cents` are computed as above with the missing baseline rate read as 0, which credits it with no avoided returns, while `baseline_units_count` and `baseline_return_rate_bp` stay null because no activation ever snapshotted them.

Each ops-run also sweeps the whole catalog and the whole shopper base. Every catalog item's chronic score and `fit_watch_state` are recomputed, and a flip to `CHRONIC` runs the full chronic cascade described in §3.8 — suspension, readiness reset, specification reopening, vendor debit, deployment termination, intervention recomputation. Every shopper's `abuse_strike_count` is recomputed against the trailing 180-day window as measured from the current logical clock, walking `abuse_status` down as strikes age out and re-deriving `policy_class`. The run's response is not a persisted resource but an object carrying exactly eight integer counters and nothing else, each summarizing what this run actually did. `deployments_activated`, `deployments_terminated`, and `deployments_measured` count the hops the deployment pass itself performed — respectively `SCHEDULED → ACTIVE`, the `ACTIVE → TERMINATED` closures on an elapsed window, and `TERMINATED → MEASURED`; a deployment closed instead by the catalog sweep's chronic cascade is not counted in `deployments_terminated`. `items_swept` counts every catalog item the sweep visited, including `DELISTED` ones and those whose figures did not move. `watch_flips` and `chronic_flips` count only the items whose `fit_watch_state` actually changed during that sweep, to `WATCH` and to `CHRONIC` respectively, so an item that fell back to `NORMAL` is counted in neither. `corrections_opened` counts the verified specifications reopened into `CORRECTION_REQUESTED` by a chronic cascade this run. And `abuse_downgrades` counts the shoppers whose `abuse_status` improved during the shopper sweep — one per shopper that moved to a milder standing on the `CLEAR`, `WATCH`, `RESTRICTED`, `BLOCKED` ladder, whatever the size of the move; escalations are counted nowhere.

Savings roll up to the lever. `deployment_count` on the stored lever row is the number of its deployments in any status and `measured_deployment_count` the number of them in `MEASURED`; `gross_savings_cents` is the sum of `attributed_savings_cents` over its `MEASURED` deployments, `spend_cents` is the recognized spend defined above, and `net_savings_cents` is gross savings less spend. `funding_posture` follows from the net: `FUNDED` when `net_savings_cents` is at least 0; `UNDER_REVIEW` when it is below 0 but not below negative 5,000 cents; and `DEFUNDED` when it is below negative 5,000 cents. A lever whose only deployment is still running therefore reports 0 net savings and stays `FUNDED`, because neither savings nor spend has been recognized.

The savings report is a computed read that recalculates on demand for a requested measurement variant and **never writes** — the persisted fields on the lever row always hold the `deployment_attributed` numbers regardless of what the report was asked for. The variant is selected by a `variant` query value — supplied empty, it counts as not supplied and the default variant runs; supplied as anything other than the two declared variant names, it is refused with `ERR_INVALID_REQUEST`, though only after the path's intervention has been resolved — and echoed back as `variant_applied`, alongside `gross_savings_cents`, `spend_cents`, `net_savings_cents`, `measured_deployment_count`, `avoided_return_count`, and `funding_posture`. Spend is the same under both variants; only gross savings, and therefore net savings and posture, differ.

The **deployment_attributed** variant applies when `variant` is omitted or equals `deployment_attributed`, and it is the variant whose results are persisted. Gross savings is the plain sum of each `MEASURED` deployment's own `attributed_savings_cents`. Every deployment is credited against its own snapshotted `baseline_return_rate_bp`, so two deployments on different items are additive and the order they are processed in is irrelevant.

The **cohort_chronological** variant applies when `variant` equals `cohort_chronological`, and it replays the `MEASURED` deployments against a single running cohort baseline. They are ordered by `window_start` ascending, tie-broken by `window_end` ascending, then by `created_at` ascending, and finally by the order in which the deployments were created on the server, never by `id`. The running baseline begins as the `baseline_return_rate_bp` of the first deployment in that order. For each deployment in order, the improvement is the running baseline less that deployment's `measured_return_rate_bp`, floored at 0; the credit added to gross savings is that improvement multiplied by that deployment's `window_units_count`, divided by 10,000 with any fraction discarded, then multiplied by the avoided-return valuation for that deployment's item `category_code`; and only *after* the credit is taken does the running baseline become that deployment's `measured_return_rate_bp`. The `avoided_return_count` this report returns is the sum of those recomputed per-deployment credits rather than the sum of the deployments' own stored `avoided_return_count` values, so it too shrinks under this variant. Because the running baseline absorbs each earlier deployment's improvement, later deployments are credited only for gains beyond the cohort's already-improved rate. For identical stored data this variant therefore returns a gross savings figure that is never larger than the `deployment_attributed` figure, and is strictly smaller whenever any later deployment's own snapshotted baseline exceeds the previous deployment's measured rate.
