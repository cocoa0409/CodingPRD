# Hospital Nutrition Room Service API — Product Requirements Document

## 1. Introduction

Hospital food and nutrition services sit at an uncomfortable intersection: a hotel-grade room-service operation running inside a clinical safety envelope. A tray that arrives warm, on time, and exactly as ordered is a satisfaction win; the same tray carrying a peanut-containing dessert to a documented peanut-allergic patient, or a regular-texture entrée to a patient who can only manage a puréed diet, is a patient-safety event. Between those two outcomes sit a therapeutic diet order that a physician prescribed and a dietitian cosigned, a menu catalogue with nutrient and allergen profiles, a procedure schedule that periodically forbids the patient from eating at all, and a production line with a finite number of trays and a finite budget.

This document specifies the API for that operation end to end. It covers diet order intake and the layering of therapeutic diet rules; allergen, texture and liquid-thickness validation at order entry and again at tray validation; on-demand meal ordering against a bounded delivery window; tray accuracy and temperature checks performed by two different people; nil-per-os holds that void meals around procedures and the missed-meal escalation that follows; nutrition consults, malnutrition risk scoring and oral supplement regimens; bedside satisfaction capture; and the production forecasting and food-cost rollup that the nutrition manager runs the department on.

Three properties shape almost every rule that follows. First, **the system is auditable before it is convenient** — every clinically meaningful action records who performed it, and several actions may not be performed by the person who performed the paired earlier step. Second, **every deadline is read from a server-controlled logical clock**, never from wall-clock time, so that windows, cutoffs and service-level deadlines are deterministic and testable. Third, **counters and ledgers are exact** — when a tray reserves a production slot it also reserves cents against its period, and every path that releases the tray must release both, returning the period to precisely the value it held beforehand.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API, without exception, carries two headers: `X-User-ID` identifies the acting person and `X-User-Role` declares the capacity in which they are acting. Exactly five roles exist, and their names are matched exactly as written: `Physician`, `Dietitian`, `DietClerk`, `TrayAide`, and `NutritionManager`. A request that omits either header, or that supplies an empty value for either, or that supplies an `X-User-Role` value outside those five spellings, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A well-authenticated request whose role is not among the roles the target endpoint permits is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The five roles divide the department along professional lines. A `Physician` prescribes therapeutic diets and books the nil-per-os holds that coordinate meals with procedures. A `Dietitian` owns the therapeutic rule catalogue, cosigns diet orders, and runs the consult and supplement workflow. A `DietClerk` takes room-service orders at the bedside, validates trays against the diet envelope, and cancels them. A `TrayAide` runs the tray line, records the accuracy and temperature checks, and delivers at the bedside. A `NutritionManager` runs the department: wards, the menu catalogue, meal periods, production forecasting, and cost. Read access is deliberately broad — every listing and single-resource read endpoint is open to all five roles — while write access is narrow and specific, as §4 enumerates.

Identity in this system is **opaque for all five roles**. When `X-User-Role` is `Physician`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server records it (for example as `ordering_physician_user_id` on a diet order, or as `requested_by_user_id` on a procedure hold) but never compares it to any entity's `id`. The same holds for `Dietitian`, whose identifier is recorded as `cosigned_by_user_id`, `signed_by_user_id` or `ordered_by_user_id` where a transition writes it; for `DietClerk`, recorded as `placed_by_user_id` on a tray; for `TrayAide`, recorded as `accuracy_checked_by_user_id` and `temperature_checked_by_user_id`; and for `NutritionManager`, which performs no operation that stamps an identifier at all. Because identity is opaque, there is no ownership check anywhere in this API in the sense of "this resource belongs to this user". What the recorded identifiers exist for is the opposite test — **segregation of duties**, described in §2.10, which asserts that the acting `X-User-ID` differs from a previously recorded one.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint in this API is paginated through two query parameters. `limit` controls page size: it defaults to 10 when omitted, may be no smaller than 1, and may be no larger than 100. `offset` controls the starting position: it defaults to 0 when omitted and may be no smaller than 0. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint states otherwise, list results are sorted by `created_at` in ascending order, so the oldest row appears first and pagination is stable as new rows arrive; because the logical clock only moves when someone moves it, many rows share a `created_at`, and those ties are broken by the order in which the server stored them, earliest insertion first. The `meta` object of a list response carries four pagination fields — `limit` and `offset` echo the effective values in force for the request, `total_count` reports how many rows match the filters before pagination is applied, and `has_more` is true when rows remain beyond the current page. Filter query parameters are documented alongside the endpoints they belong to; they narrow `total_count` as well as the returned page.

### 2.4. Resource Identity, Audit Fields and the Logical Clock

Every persisted resource carries a server-minted `id` in UUID form. Identifiers never carry a type prefix — an entity's `id` is the bare UUID string and nothing more. Clients must never supply an `id`; it is assigned at creation and is immutable thereafter.

Almost every resource additionally carries three audit properties. `created_at` records when the row was first stored and `updated_at` records the most recent mutation, both as ISO 8601 timestamps in UTC with exactly three fractional-second digits. `version` is an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row, including mutations that a cascade performs on the operator's behalf rather than mutations the operator requested directly. Whenever this document says an operation "bumps" or "increments" a row's `version`, it also means the row's `updated_at` is refreshed to the current logical-clock instant.

There is one deliberate exception. A satisfaction survey is an immutable, append-only event: it carries `id` and `created_at` only. It has **no** `updated_at` and **no** `version` field, and neither field appears in its representation. Every other resource in this API — wards, patients, therapeutic diet rules, diet orders, meal periods, menu items, meal orders, meal order lines, procedure holds, nutrition consults and supplement orders — carries the full `id`, `created_at`, `updated_at`, `version` set.

Time itself is a controlled input. The server maintains a **logical UTC clock**, and every deadline, delivery window, ordering cutoff, hold interval, activation timestamp and service-level deadline in this API is evaluated against that clock rather than against real wall-clock time. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real wall-clock time. Any of the five roles may advance the clock by supplying a `to_iso8601` instant to the clock-setting capability; the response reports the new `current_utc`. Advancing the clock has an observable consequence beyond timestamps: a nutrition consult's `is_overdue` flag is re-evaluated against the new instant on the next read of that consult.

### 2.5. The Validation Ladder

Requests are checked in a fixed, globally consistent order, and **the first check that fails determines the response**. Later checks are not evaluated, which means a request with two independent defects always reports the defect that sits higher on the ladder. The ladder is:

1. **Authentication** — both headers present and the role recognised, else `ERR_UNAUTHENTICATED`.
2. **Role authorisation** — the acting role appears in the endpoint's permitted list, else `ERR_FORBIDDEN_ROLE`.
3. **Path existence** — every identifier embedded in the URL resolves to a stored row, checked strictly left to right, else the type-specific not-found error described in §2.8.
4. **Request shape** — required body fields present, types correct, enum members recognised, numeric ranges respected, and the pagination parameters within their bounds, else `ERR_INVALID_REQUEST`.
5. **Body existence** — every identifier supplied in the request body resolves to a stored row, checked in the order the endpoint's input list declares those fields, else the type-specific not-found error.
6. **Interval geometry** — meal period intervals require the ordering cutoff strictly before the window start and the window start strictly before the window end, and a procedure hold requires its start strictly before its end, else `ERR_INVALID_WINDOW`.
7. **Ward operational state** — the governing ward is `ACTIVE`, else `ERR_WARD_SUSPENDED`.
8. **Patient admission state** — the patient the operation touches is `ADMITTED`, else `ERR_PATIENT_DISCHARGED`.
9. **Meal period openness** — the meal period the operation touches is not `CLOSED`, else `ERR_MEAL_PERIOD_CLOSED`.
10. **Transition legality** — the target row currently sits in one of the from-states the requested transition declares, else `ERR_INVALID_STATE`.
11. **Pinned diet order active** — the diet order a tray is pinned to is `ACTIVE`, else `ERR_DIET_ORDER_NOT_ACTIVE`.
12. **Consult signed** — the consult backing a supplement is `SIGNED`, else `ERR_CONSULT_NOT_SIGNED`.
13. **Quality assurance complete** — the tray's quality-assurance dimension reads `TEMP_PASSED` before bedside delivery, else `ERR_QA_NOT_PASSED`.
14. **Diet-order optimistic concurrency** — `expected_diet_order_version` matches, else `ERR_STALE_DIET_ORDER_VERSION`.
15. **Consult optimistic concurrency** — `expected_consult_version` matches, else `ERR_STALE_CONSULT_VERSION`.
16. **Envelope drift** — the tray's `pinned_diet_order_version` still equals the pinned diet order's current `version`, else `ERR_DIET_ORDER_SUPERSEDED`.
17. **Segregation of duties** — the acting `X-User-ID` differs from the recorded actor of the paired earlier step, else `ERR_SEGREGATION_OF_DUTIES`.
18. **Nil-per-os** — the patient's `npo_status` reads `NONE`, else `ERR_NPO_ACTIVE`.
19. **Allergen safety** — else `ERR_ALLERGEN_CONFLICT`.
20. **Texture safety** — else `ERR_TEXTURE_LEVEL_VIOLATION`.
21. **Liquid-thickness safety** — else `ERR_LIQUID_LEVEL_VIOLATION`.
22. **Forbidden dietary tags** — else `ERR_FORBIDDEN_TAG`.
23. **Menu item availability** — every referenced menu item is `ACTIVE`, else `ERR_MENU_ITEM_DISCONTINUED`.
24. **Diet rule availability** — every referenced therapeutic diet rule is `ACTIVE`, else `ERR_DIET_RULE_RETIRED`.
25. **Probe completeness** — else `ERR_TEMPERATURE_PROBE_REQUIRED`.
26. **Albumin completeness** — else `ERR_ALBUMIN_REQUIRED`.
27. **Nutrient ceilings** — else `ERR_NUTRIENT_CAP_EXCEEDED`.
28. **Meal period window collision** — else `ERR_MEAL_PERIOD_WINDOW_OVERLAP`.
29. **Procedure hold collision** — else `ERR_PROCEDURE_HOLD_OVERLAP`.
30. **Ordering cutoff** — else `ERR_ORDER_CUTOFF_PASSED`.
31. **Non-empty tray** — else `ERR_EMPTY_MEAL_ORDER`.
32. **Duplicate tray** — else `ERR_DUPLICATE_MEAL_ORDER`.
33. **Duplicate medical record number** — else `ERR_DUPLICATE_MRN`.
34. **Duplicate diet rule code** — else `ERR_DUPLICATE_DIET_RULE_CODE`.
35. **Duplicate menu item code** — else `ERR_DUPLICATE_MENU_ITEM_CODE`.
36. **Duplicate ward code** — else `ERR_DUPLICATE_WARD_CODE`.
37. **Rated tray delivered** — else `ERR_MEAL_ORDER_NOT_DELIVERED`.
38. **Duplicate survey** — else `ERR_DUPLICATE_SURVEY`.
39. **Revision rounds remaining** — else `ERR_REVISION_LIMIT_EXCEEDED`.
40. **Tray capacity** — else `ERR_TRAY_CAPACITY_EXCEEDED`.
41. **Period cost ceiling** — else `ERR_PERIOD_COST_CEILING_EXCEEDED`.

The conditions that trigger checks 6 through 41 are described in the workflow narratives of §3, next to the business process each one guards; §5 catalogues every error identifier with its HTTP status. Two consequences of the ordering deserve to be called out because they are easy to get wrong. First, authorisation outranks existence: a `TrayAide` addressing a diet-order endpoint receives `ERR_FORBIDDEN_ROLE` even when the identifier in the path names nothing at all. Second, the four safety checks on a tray — allergen, texture, liquid thickness, forbidden tag — are ordered exactly as listed, so a line that is simultaneously an allergen conflict and a texture violation reports `ERR_ALLERGEN_CONFLICT`, and the nutrient-ceiling check that follows them all reports only when no per-line safety defect exists.

### 2.6. Optimistic Concurrency on Cross-Aggregate Writes

Two creation endpoints reach across aggregate boundaries and attach a new child to a parent whose meaning may have shifted since the client last looked at it. Both are guarded by optimistic concurrency control, and in both cases the version field is a **required, non-optional** input — omitting it is a malformed request, not an implicit "no opinion".

A request to create a meal order must carry `expected_diet_order_version`, holding the `version` the client last observed on the diet order named by `diet_order_id`. If it does not equal that diet order's current `version`, the creation is rejected with `ERR_STALE_DIET_ORDER_VERSION` (HTTP 412). This matters because a diet order's `version` moves for several reasons: every accepted meal order increments the order's `linked_meal_order_count` and therefore its `version`, and a cosign, a revision request or a discontinuation advances it too. A client working from an older `version` is therefore reasoning about a therapeutic envelope that may no longer be the one the tray would be validated against.

A request to create a supplement order must carry `expected_consult_version`, holding the `version` the client last observed on the nutrition consult named by `consult_id`. If it does not equal that consult's current `version`, the creation is rejected with `ERR_STALE_CONSULT_VERSION` (HTTP 412). A consult's `version` advances every time a supplement order is attached to it — through `linked_supplement_order_count` — and also on assessment and on signature, so a stale value means the recommendation the client is acting on has since been revised.

No other endpoint in this API accepts a version field. In particular, none of the transition endpoints, none of the `PATCH` update endpoints, and none of the other creation endpoints take one; supplying one there is simply an unrecognised field.

### 2.7. Cascades, Ledger Symmetry and Derived Fields

Many operations in this system mutate more than the row the caller named. When they do, the effects are **immediate and complete within the request** — there is no deferred or eventual settlement. A cascade that reaches a second entity mutates that entity for real: its `updated_at` is refreshed and its `version` increments by 1, exactly as if it had been written directly.

Two of those cascades run several levels deep and are described in full in §3.3 (a diet order superseding its predecessor and reverting that predecessor's trays) and §3.8 (a procedure hold voiding every tray whose service window it covers). The governing discipline is that each level exists *because* of the level above it: a tray that leaves a committed state necessarily changes its meal period's committed counters, which necessarily changes that period's cost rollup, which — when a forecast has been locked — necessarily changes that period's forecast variance.

**Ledger symmetry** is the second discipline. A tray that reaches the validated state reserves exactly one production slot and exactly its own food cost in cents against its meal period. Every route out of a committed state — cancellation, a procedure hold voiding the tray, a period close voiding the tray, a supersede cascade reverting the tray to await revalidation — must return exactly one slot and exactly those cents, leaving the period at precisely the values it held before the reservation. The same symmetry governs the patient's supplement ledger: activating a supplement regimen adds its daily cost to the patient's running total and cancelling an active one subtracts exactly that amount, while cancelling a regimen that never activated leaves the total untouched because it never debited it.

Derived fields are recomputed rather than remembered. A patient's `active_diet_order_id` and `active_procedure_hold_id` are pointers to whichever diet order is currently `ACTIVE` and whichever procedure hold is currently `ACTIVE` for that patient, and read as null when none exists; clients that need the full row navigate by filtering the corresponding list endpoint on `patient_id`. A diet order's `superseded_by_diet_order_id` is the inverse of the supersede pointer and is discovered by filtering the diet order list on `supersedes_diet_order_id`. A ward's `active_patient_census` counts the patients on that ward who are `ADMITTED` and whose `npo_status` is `NONE`, and is recomputed whenever a patient is admitted, discharged, placed under a hold, or released from one.

### 2.8. Nested Addressing and Not-Found Resolution

Path identifiers are resolved strictly left to right, and the first identifier that resolves to nothing determines the error. The tray-line substitution capability is the only two-level path in the API: it names a meal order in the first position through the path variable `id` and a line in the second through the path variable `line_id`, written `{id}` and `{line_id}` in the path template. If the meal order does not exist, the response is `ERR_MEAL_ORDER_NOT_FOUND` even when the line identifier is also nonsense. If the meal order exists but the line identifier resolves to nothing — **or resolves to a line that belongs to some other meal order** — the response is `ERR_MEAL_ORDER_LINE_NOT_FOUND`. A line addressed through the wrong parent is treated as not found, never as a cross-parent operation.

Each entity type has its own not-found error so that a client can tell which reference failed: `ERR_WARD_NOT_FOUND`, `ERR_PATIENT_NOT_FOUND`, `ERR_DIET_RULE_NOT_FOUND`, `ERR_DIET_ORDER_NOT_FOUND`, `ERR_MEAL_PERIOD_NOT_FOUND`, `ERR_MENU_ITEM_NOT_FOUND`, `ERR_MEAL_ORDER_NOT_FOUND`, `ERR_MEAL_ORDER_LINE_NOT_FOUND`, `ERR_PROCEDURE_HOLD_NOT_FOUND`, `ERR_CONSULT_NOT_FOUND`, `ERR_SUPPLEMENT_ORDER_NOT_FOUND` and `ERR_SURVEY_NOT_FOUND`. The same catalogue governs identifiers supplied in a request body, with one difference: body identifiers are resolved in the order the endpoint declares its input fields, so when two body references are both unresolvable the earlier-declared field decides the error.

### 2.9. Precision, Rounding and Money

All money in this API is expressed in **whole cents** as integers; there are no fractional-cent values anywhere in a stored field or a response. Wherever rounding is required, the method is **round half up** — a value exactly halfway between two representable results rounds away from zero to the larger magnitude. Rounded arithmetic is performed with decimal arithmetic rather than binary floating point, so that a weighted sum of, for example, 4.325 rounds up to 4.33 rather than down.

Where a quantity carries a fixed number of decimal places, this document states it at the point the quantity is introduced. In summary: carbohydrate and protein quantities, protein deficits and probe readings carry **1 decimal place**; malnutrition risk scores, satisfaction composites, patient satisfaction averages and forecast variance percentages carry **2 decimal places**; sodium and potassium quantities, all cent amounts, tray counts and the tray service score are whole numbers. Where the *point* at which rounding is applied changes the answer — as it does for tray food cost and for a patient's satisfaction average — §3 pins the evaluation order explicitly, and that pinned order is normative.

### 2.10. Segregation of Duties

Three actions in this system may not be performed by the person who performed the step they check. A diet order may not be cosigned by the same `X-User-ID` recorded as its `ordering_physician_user_id`. A tray's temperature check may not be recorded by the same `X-User-ID` recorded as its `accuracy_checked_by_user_id`. A nutrition consult may not be signed by the same `X-User-ID` recorded as its `requested_by_user_id`. In all three cases the rejection is `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), and in all three cases the comparison is on the raw identifier string, independent of role.

The third case has an edge worth stating plainly: a consult raised by the missed-meal escalation cascade rather than by a person records the literal string `SYSTEM` as its `requested_by_user_id`. Because no human's `X-User-ID` is the string `SYSTEM`, such a consult can be signed by any `Dietitian`.

## 3. Business Logic & Workflows

### 3.1. Wards, Patient Admission and the Bedside Clinical Profile

Everything in this system happens somewhere, and that somewhere is a ward. A `NutritionManager` registers a ward with a human-readable `name` and a short `code` of between 2 and 8 characters that must be unique across all wards — a second ward submitted with a `code` already in use is rejected with `ERR_DUPLICATE_WARD_CODE`. Two operational numbers come with it. `tray_line_capacity_per_window` is how many trays the ward's tray line can plate in a single service window and must be at least 1; it is used in exactly one place, as the fallback tray count when a rolling-average forecast finds no closed history to average, and nowhere else. `delivery_lead_minutes` is the expected gap in minutes between plating and bedside arrival and must be zero or greater. A boolean `temperature_probe_required` completes the profile and defaults to true when omitted; it is recorded and reported back but gates nothing, because the temperature check and the `TEMP_PASSED` precondition on delivery apply to every tray on every ward whatever this flag reads. `delivery_lead_minutes` is likewise descriptive only and is never read by any calculation.

A newly registered ward begins `ACTIVE` with an `active_patient_census` of 0. The manager may later suspend it, moving `status` from `ACTIVE` to `SUSPENDED`, and may reinstate it, moving `SUSPENDED` back to `ACTIVE`; each move requires the ward to be in the corresponding from-state — asking for the status the ward already holds is `ERR_INVALID_STATE` — and bumps the ward's `version` by 1, and the same update capability may re-capacity a ward by revising `tray_line_capacity_per_window`, `delivery_lead_minutes` or `temperature_probe_required`, no other field being revisable and an update that names nothing at all still bumping the version. Wards can be surveyed by `status`. Suspension is not cosmetic: while a ward is `SUSPENDED`, no meal period may be created for it, no meal period of that ward may have its forecast locked, and no meal period of that ward may be opened for service — all three are rejected with `ERR_WARD_SUSPENDED`.

Admitting a patient is a `DietClerk` or `NutritionManager` action. The admission payload names the ward through `ward_id` and carries the patient's `mrn` — a medical record number that must be unique across all patients, with a collision rejected as `ERR_DUPLICATE_MRN` — together with `full_name` and `age_years`, which must fall between 0 and 120 inclusive. Three clinical fields are optional at admission and default when omitted: `allergen_codes` defaults to an empty list and holds upper-snake-case allergen strings such as `PEANUT` or `MILK`; `texture_level` defaults to `REGULAR` and records the coarsest texture the patient can safely manage, drawn from `REGULAR`, `MINCED_MOIST`, `PUREED` and `LIQUIDISED`; and `liquid_level` defaults to `THIN` and records the minimum thickness the patient's fluids require, drawn from `THIN`, `MILDLY_THICK`, `MODERATELY_THICK` and `EXTREMELY_THICK`. An admitted patient starts with `status` of `ADMITTED` and `npo_status` of `NONE`, and the ward's `active_patient_census` is recomputed immediately. Those same three clinical fields may be revised later by a `DietClerk` or a `Dietitian`, whatever the patient's admission status; such a revision bumps the patient's `version` even when it names no field at all, and because the therapeutic envelope reads the patient's texture and liquid floors, the patient's `ACTIVE` diet order reflects the change the next time its envelope is read or a tray is validated against it.

A patient row accumulates a running clinical and financial picture that no client writes directly, and every one of its numeric rollups starts at zero on admission. `missed_meal_count` counts every tray for this patient that ended up missed. `protein_deficit_g` accumulates the protein those missed trays would have delivered, carried to 1 decimal place. `daily_supplement_cost_cents` sums the daily cost of the patient's currently active supplement regimens. `survey_count` counts the satisfaction surveys recorded for the patient and `satisfaction_score_avg` averages them to 2 decimal places, reading null while `survey_count` is 0. Alongside those sit the derived pointers `active_diet_order_id` and `active_procedure_hold_id` described in §2.7.

Discharge is the patient's only state transition, moving `ADMITTED` to the terminal `DISCHARGED`, and it is performed by a `DietClerk` or a `NutritionManager` on a patient who is currently `ADMITTED`. It unwinds the patient's open nutrition work in a strict cascade. At the first level, every meal order for this patient whose fulfillment dimension reads `PENDING_VALIDATION`, `VALIDATED`, `IN_PRODUCTION` or `PLATED` is moved to `CANCELLED`; trays already `DELIVERED`, `CANCELLED` or `MISSED` are untouched. At the second level, because each of those trays left a committed state, its meal period recomputes its committed tray count and committed cents and then re-runs the period cost rollup of §3.5 across its overhead, discount and total components. At the third level, because the committed tray count moved, any meal period already in `FORECAST_LOCKED` or `IN_SERVICE` recomputes its forecast variance. Independently of the tray cascade, every procedure hold for this patient still in `SCHEDULED` moves to `CANCELLED`, and the patient's `ACTIVE` diet order, if one exists, moves to `DISCONTINUED` with `active_diet_order_id` becoming null. The patient's own `version` increments by 1, and the ward census is recomputed. Once `DISCHARGED`, the patient is closed to further clinical or ordering work: drafting or submitting or cosigning a diet order, creating or validating a tray, booking or activating a procedure hold, raising a consult, and activating a supplement regimen all reject with `ERR_PATIENT_DISCHARGED`.

### 3.2. The Therapeutic Rule Catalogue and the Menu

A **therapeutic diet rule** is the reusable clinical template a prescription draws on, published by a `Dietitian` or a `NutritionManager`. Each rule carries a `diet_code` that must be unique across all rules — a duplicate is rejected with `ERR_DUPLICATE_DIET_RULE_CODE` — a human-readable `display_name`, and a `precedence_rank` between 1 and 999 where a lower number means clinically stronger. That rank has exactly one job, and it is a narrow one: it orders the union of forbidden tag codes deterministically when two rules are layered, and it does not otherwise decide which rule wins.

The clinical content of a rule is a set of ceilings and floors, every one of which is optional. `max_sodium_mg_per_meal` and `max_potassium_mg_per_meal` are per-meal ceilings in whole milligrams; `max_carb_g_per_meal` is a per-meal carbohydrate ceiling in grams carried to 1 decimal place. Each must be zero or greater when present, and a null value means **this rule imposes no ceiling on that nutrient** rather than a ceiling of zero. Similarly `min_texture_level` imposes a texture floor drawn from `REGULAR`, `MINCED_MOIST`, `PUREED` and `LIQUIDISED`, and `min_liquid_level` imposes a thickness floor drawn from `THIN`, `MILDLY_THICK`, `MODERATELY_THICK` and `EXTREMELY_THICK`; null in either means the rule imposes no floor there. `forbidden_tag_codes` defaults to an empty list and names menu tag codes the rule prohibits, such as `HIGH_FAT`. Finally, `requires_dietitian_cosign` defaults to **true** and is the flag that decides whether a diet order carrying this rule needs a second signature before it can take effect.

Rules are published `ACTIVE` and may be retired or reinstated by a `Dietitian` or `NutritionManager` through a status revision that moves `status` between `ACTIVE` and `RETIRED` and bumps the rule's `version`; asking for the status the rule already holds is `ERR_INVALID_STATE`, no clinical ceiling or floor is revisable once published, and rules can be surveyed by `status`. A `RETIRED` rule can no longer back a new diet order or a resubmitted one; both attempts are rejected with `ERR_DIET_RULE_RETIRED`. A rule already embedded in an order that activated earlier is not retroactively invalidated.

The **menu item** catalogue is the `NutritionManager`'s domain. Each item carries an `item_code` unique across all items — a duplicate is `ERR_DUPLICATE_MENU_ITEM_CODE` — a `display_name`, and a nutrition profile of `sodium_mg` and `potassium_mg` in whole milligrams together with `carb_g` and `protein_g` in grams to 1 decimal place, each of which must be zero or greater. `unit_cost_cents` is the raw food cost of one unit in whole cents, before the waste factor and the texture surcharge that §3.6 applies. `texture_level` states the texture the item is actually prepared to and `liquid_level` states its thickness when the item is a liquid, reading null for non-liquid items — a distinction that matters, because the thickness check skips items that declare no thickness at all. `service_temp_class` is one of `HOT`, `COLD` or `AMBIENT` and decides which probe reading a tray's temperature check will demand. `allergen_codes` and `tag_codes` both default to empty lists and carry, respectively, the allergens the item contains and the dietary tags it bears.

Menu items are published `ACTIVE` and the manager may later discontinue, reinstate or re-price one, moving `status` between `ACTIVE` and `DISCONTINUED` or revising `unit_cost_cents` — those two being the only revisable fields — with the item's `version` bumping on each change and a request for the status the item already holds rejected as `ERR_INVALID_STATE`. Items can be surveyed by `status`, by `texture_level` and by `service_temp_class`. A `DISCONTINUED` item may not be placed on a new tray, may not be substituted onto an existing line, may not survive a tray validation, and may not back a supplement order; all four reject with `ERR_MENU_ITEM_DISCONTINUED`. Re-pricing an item does not retroactively re-price trays that were already costed.

### 3.3. Prescribing a Diet: Draft, Cosign, Revision and Supersession

A `Physician` opens a prescription by drafting a **diet order** for a patient. The draft payload names the patient through `patient_id` and the mandatory therapeutic template through `primary_diet_rule_id`; an optional `secondary_diet_rule_id` layers a second template on top of the first, and is null when absent. The prescriber may also state the texture and thickness they want, through `texture_level` and `liquid_level`, which default to `REGULAR` and `THIN` respectively — these are the prescriber's *request*, not the final answer, because §3.4 resolves them against the patient's own tolerances and the rules' floors. The new order is stored with `status` of `DRAFT`, a `revision_round` of 0, and `ordering_physician_user_id` stamped from the acting `X-User-ID`. Its `cosigned_by_user_id`, `revision_note`, `effective_from`, `supersedes_diet_order_id` and `superseded_by_diet_order_id` are all null at this point, its five scalar `effective_*` envelope fields read null and `forbidden_tag_codes_effective` reads an empty list until the first submission computes them, and `linked_meal_order_count` is 0. Drafting requires the patient to be `ADMITTED` and every referenced rule to be `ACTIVE`.

Submission is where the workflow forks, and the fork is decided by data rather than by the caller. Submitting a `DRAFT` order requires the patient to be `ADMITTED` and the primary rule — and the secondary rule when one is present — to be `ACTIVE`. If the primary rule's `requires_dietitian_cosign` is true, **or** a secondary rule is present and its `requires_dietitian_cosign` is true, the order moves `DRAFT → PENDING_COSIGN`: the effective envelope of §3.4 is recomputed and the order's `version` increments by 1. If instead the primary rule's `requires_dietitian_cosign` is false **and** either no secondary rule is present or the secondary rule's `requires_dietitian_cosign` is also false, the very same submission moves `DRAFT → ACTIVE` directly: the envelope is recomputed, `effective_from` is set to the current logical-clock instant, `cosigned_by_user_id` is explicitly left null to record that nobody cosigned, the full activation cascade described below runs, and `version` increments by 1.

A `Dietitian` presented with a `PENDING_COSIGN` order has two ways forward. Requesting a revision sends it back to the prescriber, parking the order in `REVISION_REQUESTED` and moving it `PENDING_COSIGN → REVISION_REQUESTED`; the request carries a free-text `revision_note`, which is required rather than optional and is stored on the order, `revision_round` increments by 1, and `version` increments by 1. A prescriber then resubmits, moving `REVISION_REQUESTED → PENDING_COSIGN` — again requiring the patient to be `ADMITTED` and the referenced rules to be `ACTIVE`, again recomputing the effective envelope, and again bumping `version`, but **without** the data-driven fork of the first submission, so a resubmission always lands in `PENDING_COSIGN` however the referenced rules' `requires_dietitian_cosign` flags read — which closes the cycle `PENDING_COSIGN → REVISION_REQUESTED → PENDING_COSIGN`. That cycle is not unbounded: a revision may be requested only while the order's `revision_round` is **strictly less than three**, so the third completed round is the last, and a fourth attempt is rejected with `ERR_REVISION_LIMIT_EXCEEDED`.

Cosigning is the other way forward, and it is the moment a prescription becomes clinical reality. A `Dietitian` cosigns a `PENDING_COSIGN` order whose patient is still `ADMITTED`, and whose `ordering_physician_user_id` differs from the cosigner's own `X-User-ID` — a match is `ERR_SEGREGATION_OF_DUTIES`. The order moves `PENDING_COSIGN → ACTIVE`, recording `cosigned_by_user_id` from the acting `X-User-ID`, setting `effective_from` to the logical-clock instant, and recomputing the effective envelope. The patient's `active_diet_order_id` is repointed at this order.

Activation then runs a four-level cascade, and the same cascade runs on the auto-activating submission fork described above. **Level one:** if the patient already had a diet order in `ACTIVE`, that predecessor moves `ACTIVE → SUPERSEDED`; the predecessor records `superseded_by_diet_order_id` pointing at the new order, and the new order records `supersedes_diet_order_id` pointing back at the predecessor, forming the supersede chain that the diet-order listing exposes through its `supersedes_diet_order_id` filter alongside `patient_id`, `status`, `primary_diet_rule_id` and `secondary_diet_rule_id`. **Level two:** because the predecessor is no longer `ACTIVE`, every meal order pinned to it whose fulfillment dimension reads `PENDING_VALIDATION` or `VALIDATED` is re-pinned onto the new order — its `diet_order_id` and `pinned_diet_order_version` are updated to the new order and the new order's current `version` — its fulfillment dimension is forced back to `PENDING_VALIDATION`, its own `effective_texture_level` and `effective_liquid_level` are refreshed from the new order's envelope while its nutrient totals and its costs are left exactly as they stand until it is validated again, and `revalidation_required` is set true. **Level three:** because each re-pinned tray that had been `VALIDATED` left a committed state, its meal period decrements its committed tray count by one and subtracts that tray's `food_cost_cents` from its committed cents. **Level four:** because the committed cents moved, that meal period re-runs its cost rollup across `period_overhead_cents`, `period_bulk_discount_cents` and `period_total_cost_cents`, and recomputes `forecast_variance_pct` whenever `forecast_tray_count` is neither null nor zero. Both the new order and the superseded order have their `version` incremented by 1.

Discontinuation is the prescriber's exit. A `Physician` may discontinue an order that is `ACTIVE`, moving `ACTIVE → DISCONTINUED`: the patient's `active_diet_order_id` becomes null, every meal order pinned to this order whose fulfillment dimension reads `PENDING_VALIDATION` or `VALIDATED` has `revalidation_required` set true, and the order's `version` increments by 1. A `Physician` may equally discontinue an order still sitting in `PENDING_COSIGN`, moving `PENDING_COSIGN → DISCONTINUED` with no cascade beyond the `version` increment, since such an order never governed a tray. `SUPERSEDED` and `DISCONTINUED` are both terminal; any further transition attempt from either reports `ERR_INVALID_STATE`, as does any transition attempted from a state the transition does not declare — including a second attempt at a transition that already succeeded.

### 3.4. Deriving the Effective Diet Envelope

The **effective envelope** is what a tray is actually judged against, and it is recomputed on every diet order transition into `PENDING_COSIGN` or `ACTIVE` — that is, on submission, on resubmission, and on cosign — and read again on every tray validation. An order whose `status` is `ACTIVE` reports all six fields recomputed live on every read, so a change to the patient's tolerances or `npo_status` is visible immediately without any transition; an order in any other status reports the snapshot its last transition into `PENDING_COSIGN` or `ACTIVE` stored, frozen thereafter. It resolves the prescriber's request, the patient's documented tolerances, one or two therapeutic rules, and any nil-per-os override into six computed fields on the order: `effective_sodium_cap_mg`, `effective_potassium_cap_mg`, `effective_carb_cap_g`, `effective_texture_level`, `effective_liquid_level` and `forbidden_tag_codes_effective`. The rules that participate are the primary rule always, plus the secondary rule when `secondary_diet_rule_id` is not null. Two ordinal scales underpin the comparison: texture ascends `REGULAR`, then `MINCED_MOIST`, then `PUREED`, then `LIQUIDISED`, with `REGULAR` the least restrictive; thickness ascends `THIN`, then `MILDLY_THICK`, then `MODERATELY_THICK`, then `EXTREMELY_THICK`, with `THIN` the least restrictive.

Resolution proceeds in five pinned steps.

**Step one — numeric ceilings.** For each nutrient in turn, gather the ceilings the participating rules declare, ignoring any rule whose ceiling for that nutrient is null. If at least one rule declares a ceiling, the effective ceiling is the **smallest** of them; if every participating rule declares null, the effective ceiling is null, meaning uncapped. `effective_sodium_cap_mg` is resolved this way from each rule's `max_sodium_mg_per_meal`, `effective_potassium_cap_mg` from each rule's `max_potassium_mg_per_meal`, and `effective_carb_cap_g` from each rule's `max_carb_g_per_meal`.

**Step two — texture floor.** Collect the diet order's own `texture_level`, the patient's `texture_level`, and each participating rule's `min_texture_level` where that value is not null. `effective_texture_level` is the candidate with the **highest** position on the texture scale — the most restrictive of them all.

**Step three — thickness floor.** Collect the diet order's own `liquid_level`, the patient's `liquid_level`, and each participating rule's `min_liquid_level` where that value is not null. `effective_liquid_level` is the candidate with the **highest** position on the thickness scale.

**Step four — the nil-per-os override, applied last.** This step is deliberately *not* monotonic with steps two and three; it may tighten a value and it may also loosen one. If the patient's `npo_status` reads `NPO_STRICT`, then `effective_texture_level` is forced to `LIQUIDISED` and all three nutrient ceilings are forced to zero — `effective_sodium_cap_mg` and `effective_potassium_cap_mg` to 0 milligrams and `effective_carb_cap_g` to 0.0 grams — regardless of what steps one and two produced. If instead the patient's `npo_status` reads `NPO_CLEAR_LIQUIDS`, then `effective_texture_level` is forced to `LIQUIDISED`, `effective_liquid_level` is **pinned down to `THIN`** even when step three had raised it above `THIN`, and the carbohydrate ceiling is capped at fifteen grams: if `effective_carb_cap_g` was null it becomes 15.0, and otherwise it becomes the smaller of its current value and 15.0. When `npo_status` reads `NONE`, step four changes nothing.

**Step five — forbidden tags.** `forbidden_tag_codes_effective` is the union of the `forbidden_tag_codes` lists of the participating rules with duplicates removed. The surviving codes are ordered first by the `precedence_rank` of the rule that contributed them, ascending, and then by the tag code itself in ascending alphabetical order — which is the sole reason `precedence_rank` exists.

Carbohydrate ceilings carry 1 decimal place and round half up; sodium and potassium ceilings are whole milligrams. Only rules whose `status` is `ACTIVE` may participate, which the diet-rule availability check on drafting and submission enforces.

### 3.5. Meal Periods: Scheduling, Forecasting and the Cost Rollup

A **meal period** is one ward's service slot for one meal on one day, and it is the unit against which production capacity and food cost are budgeted. A `NutritionManager` schedules it against a ward named by `ward_id`, with a `period_code` of `BREAKFAST`, `LUNCH`, `DINNER` or `LATE_SNACK` and a `service_date` given as an ISO calendar date in `YYYY-MM-DD` form. Three instants define its timing: `order_cutoff_at` is the last logical-clock moment at which a tray may be created for the period, while `window_start_at` and `window_end_at` bound the bedside delivery window. The geometry must be sane — the cutoff strictly before the window start, and the window start strictly before the window end — and a violation is `ERR_INVALID_WINDOW`. `production_capacity_trays` is the hard ceiling on committed trays and must be at least 1. `cost_ceiling_cents` is optional; when supplied it must be zero or greater and caps the period's committed food cost, and when null the period has no cost ceiling at all.

Two meal periods on the same ward may not occupy overlapping delivery windows — every period already stored against that ward is compared whatever its `status`, so even a `CLOSED` period still reserves its window — and the comparison here is **closed on both ends**: the interval running from `window_start_at` through `window_end_at` includes both endpoints, so a new period whose window starts at exactly the instant an existing period's window ends does collide, and is rejected with `ERR_MEAL_PERIOD_WINDOW_OVERLAP`. This closed-interval reading applies only to overlap detection between periods; for scoring a delivery, §3.7 treats the same window as half-open. Creating a period also requires the ward to be `ACTIVE`. A new period is stored `PLANNED`, with `forecast_variant`, `forecast_tray_count`, `forecast_cost_cents`, `forecast_variance_pct` and `locked_at` all null and with `committed_tray_count`, `committed_food_cost_cents`, `delivered_tray_count`, `period_overhead_cents`, `period_bulk_discount_cents` and `period_total_cost_cents` all zero. Periods can be surveyed by `ward_id`, by `period_code`, by `service_date` and by `status`.

**Locking the forecast** moves the period `PLANNED → FORECAST_LOCKED` and requires the ward to be `ACTIVE`. The manager pins a `forecast_variant` on the request — either `ROLLING_AVERAGE` or `CENSUS_BASED` — and that choice is stored on the period and decides how `forecast_tray_count` is produced. The two variants answer the same question from opposite directions and will generally disagree on the same period.

Under **`ROLLING_AVERAGE`**, the system looks backwards. It gathers the meal periods on the same ward with the same `period_code` whose `status` is `CLOSED` and whose `service_date` is earlier than this period's `service_date`, ranks them by `service_date` descending with `created_at` descending as the tie-break, and keeps at most the **three** most recent. If that history is empty, `forecast_tray_count` falls back to the ward's `tray_line_capacity_per_window` — a fallback that typically overshoots a small census. Otherwise the system takes the mean of those periods' `delivered_tray_count` values, multiplies that mean by a no-show adjustment of 0.92, and **rounds the product up to the next whole tray**.

Under **`CENSUS_BASED`**, the system looks forwards. It counts the patients on this period's ward whose `status` is `ADMITTED` and whose `npo_status` is `NONE` at the moment of the lock, multiplies that live census by a participation rate of 0.85, and **rounds the product up to the next whole tray**. Delivered history is ignored entirely.

Whichever variant produced it, `forecast_cost_cents` is `forecast_tray_count` multiplied by the departmental average tray cost of 1,150 cents — eleven dollars and fifty cents per tray — as exact integer arithmetic. `locked_at` is set to the logical-clock instant and the period's `version` increments by 1.

**Forecast variance** is computed at lock time and again on every subsequent change to `committed_tray_count` while the period is `FORECAST_LOCKED`, `IN_SERVICE` or `CLOSED`. When `forecast_tray_count` is null or zero, `forecast_variance_pct` is null — the zero-denominator boundary is a null, never a zero and never an error. Otherwise `forecast_variance_pct` is the committed tray count minus the forecast tray count, divided by the forecast tray count, multiplied by 100, and rounded half up to 2 decimal places. The result is signed: committing fewer trays than forecast yields a negative percentage.

**Opening service** moves the period `FORECAST_LOCKED → IN_SERVICE`, requires the ward to be `ACTIVE`, and bumps the period's `version` by 1; it is the gate that lets validated trays enter production. **Closing** moves `IN_SERVICE → CLOSED`, is terminal, and unwinds whatever the service did not finish. At the first cascade level, every tray in this period whose fulfillment dimension reads `PENDING_VALIDATION`, `VALIDATED`, `IN_PRODUCTION` or `PLATED` moves to `MISSED` with `missed_reason` recorded as `PERIOD_CLOSED`. At the second level, because each of those trays entered `MISSED`, the owning patient's `missed_meal_count` increments by 1 and their `protein_deficit_g` increases by that tray's `total_protein_g`, and the patient's own `version` increments once per tray so treated rather than once for the close as a whole. At the third level, because those counters moved, the missed-meal escalation of §3.8 may raise an automatic consult. The period then recomputes `committed_tray_count` and `committed_food_cost_cents`, re-runs the cost rollup, recomputes `forecast_variance_pct`, and increments its own `version` by 1. Once `CLOSED`, the period admits no tray creation and no tray validation; both report `ERR_MEAL_PERIOD_CLOSED`.

The **period cost rollup** recomputes whenever `committed_food_cost_cents` changes — on a tray validation, on a cancellation out of a committed state, or on a system move to `MISSED` — and it runs in six pinned steps that must be executed in this order.

1. The **line subtotal** is `committed_food_cost_cents`: the sum of `food_cost_cents` across every tray in this period whose fulfillment dimension reads `VALIDATED`, `IN_PRODUCTION`, `PLATED` or `DELIVERED`. Trays that are `PENDING_VALIDATION`, `CANCELLED` or `MISSED` contribute nothing.
2. The **volume tier** is keyed on that step-one subtotal and on nothing else — never on the gross and never on the final total. Tier A applies when the subtotal is **below** 2,000 cents (twenty dollars). Tier B applies when the subtotal is **at least** 2,000 cents and **below** 6,000 cents (sixty dollars). Tier C applies when the subtotal is **at or above** 6,000 cents.
3. `period_overhead_cents` is the subtotal multiplied by the tier's overhead rate — 18.0 percent in tier A, 15.0 percent in tier B, 12.0 percent in tier C — rounded half up to whole cents.
4. The **gross** is the subtotal plus `period_overhead_cents`.
5. `period_bulk_discount_cents` is the **gross** multiplied by the tier's bulk-discount rate — 0.0 percent in tier A, 2.0 percent in tier B, 4.5 percent in tier C — rounded half up to whole cents. Note carefully that this percentage is taken against the gross, which already contains the overhead, and not against the step-one subtotal.
6. `period_total_cost_cents` is the gross minus `period_bulk_discount_cents`, as exact integer arithmetic with no further rounding.

The circular-sounding reading in which the tier is whichever band the *period total* falls into is explicitly rejected: the tier is fixed at step two, before any overhead exists, which is precisely what makes step three well defined.

### 3.6. Placing, Substituting and Validating a Room-Service Tray

Room service begins at the bedside, where a `DietClerk` takes an on-demand order and places a **meal order** — a tray. The creation payload names the patient through `patient_id`, the service slot through `meal_period_id`, and the governing prescription through `diet_order_id`, and it carries `expected_diet_order_version` as described in §2.6. The tray's contents arrive as `lines`, an array in which each entry names a `menu_item_id` and a `quantity` of between 1 and 10 units. The array must contain at least one entry; an empty `lines` array is rejected with `ERR_EMPTY_MEAL_ORDER`. Creation additionally requires the patient to be `ADMITTED`, the meal period not to be `CLOSED`, and every referenced menu item to be `ACTIVE`. Ordering closes when the logical clock reaches the period's `order_cutoff_at`: the clock must be **strictly before** the cutoff, so an attempt at exactly the cutoff instant is already too late and reports `ERR_ORDER_CUTOFF_PASSED`. A patient may hold only one live tray per period — if another meal order already exists for the same `patient_id` and `meal_period_id` whose fulfillment dimension is anything other than `CANCELLED` or `MISSED`, the new one is rejected with `ERR_DUPLICATE_MEAL_ORDER`.

An accepted tray is stored with its fulfillment dimension at `PENDING_VALIDATION` and its quality-assurance dimension at `NOT_CHECKED`, with `placed_by_user_id` stamped from the acting `X-User-ID` and `pinned_diet_order_version` stamped with the diet order's `version` at the instant of pinning — an instant that falls *after* the creation's own `linked_meal_order_count` bump described below, so an accepted tray pins the `version` the diet order carries once that bump has been applied. A fresh tray carries `effective_texture_level` and `effective_liquid_level` copied from the pinned diet order's envelope as read at the instant of creation — which is what the creation-time cost pass below keys its texture surcharge on — `revalidation_required` false, `accuracy_retry_count` and `temperature_retry_count` both zero, `hot_probe_celsius`, `cold_probe_celsius`, `delivered_at`, `delivery_window_compliance`, `service_compliance_score`, `missed_reason`, `accuracy_checked_by_user_id` and `temperature_checked_by_user_id` all null, and `line_cost_cents` on each of its lines starting at zero until the cost pass below writes it — a cost pass run at creation or at validation writes `line_cost_cents` in place and does **not** bump the line's `version` or refresh its `updated_at`, which only a substitution moves. One meal order line is created per `lines` entry, each carrying `meal_order_id` back to the owning tray, a `line_status` of `REQUESTED`, and a null `substituted_from_menu_item_id` and `substitution_reason`. Creation also increments the pinned diet order's `linked_meal_order_count` by 1 and therefore that diet order's `version` by 1 — which is exactly why the next tray placed against the same prescription needs a freshly-read `expected_diet_order_version`.

**Nutrient totals** are computed at creation, again after every line substitution, and again at validation. Every line of the tray participates, whether its `line_status` is `REQUESTED` or `SUBSTITUTED`, processed in ascending `created_at` order; a substituted line contributes its **new** menu item, never the item it originally carried. `total_sodium_mg` is the sum, across lines, of the effective menu item's `sodium_mg` multiplied by that line's `quantity`, in whole milligrams, and `total_potassium_mg` is the same sum over `potassium_mg`. `total_carb_g` is the sum of the effective item's `carb_g` multiplied by `quantity`, with round-half-up to 1 decimal place applied **once to the completed sum**, and `total_protein_g` is the same over `protein_g`. Two booleans fall out of the same pass: `requires_hot_probe` is true when at least one line resolves to a menu item whose `service_temp_class` is `HOT`, and `requires_cold_probe` is true when at least one line resolves to an item whose `service_temp_class` is `COLD`. An `AMBIENT` item demands neither probe.

**Tray cost** is computed at the same three moments and is deliberately rounded at the line rather than at the tray. First the per-unit texture surcharge is read from the tray's `effective_texture_level`: nothing at all for `REGULAR`, 25 cents per unit for `MINCED_MOIST`, 60 cents per unit for `PUREED`, and 90 cents per unit for `LIQUIDISED`. Then, for each line in ascending `created_at` order, the base amount is the effective menu item's `unit_cost_cents` multiplied by the line's `quantity`, the preparation amount is the surcharge per unit multiplied by that same `quantity`, and `line_cost_cents` is the sum of those two amounts multiplied by a waste factor of 1.08, rounded half up to whole cents. Finally `food_cost_cents` is the plain sum of the already-rounded `line_cost_cents` values. **The evaluation order is pinned:** round at the line first, then add the rounded integers. The alternative reading — summing the unrounded line amounts and rounding once at the end — is rejected, and returns a different integer whenever the discarded fractions accumulate past a cent. Because the surcharge is keyed on `effective_texture_level`, which comes from the envelope of §3.4, tightening a prescription changes what the same tray costs.

A tray line may be swapped onto a different item by a `DietClerk` or a `Dietitian`, from whatever fulfillment state the tray currently sits in and whatever its patient's admission status, its meal period's status or its pinned diet order's status — the safety battery below is the only gate. The substitution names the replacement through `substitute_menu_item_id` and may carry a free-text `substitution_reason`, which is stored as supplied and written back to null when the field is omitted. The response body is the updated line, not the tray. On success the line's `menu_item_id` becomes the replacement, `substituted_from_menu_item_id` records the item the line previously carried, `line_status` becomes `SUBSTITUTED`, the reason is stored, and the tray's nutrient totals, the line's own `line_cost_cents` and the tray's `food_cost_cents` are all recomputed; the line's `version` and the tray's `version` each increment by 1. The substitution is not a blind swap — the replacement item is put through the same safety battery a validation would apply, in the same order: the item may not declare an allergen the patient is documented against (`ERR_ALLERGEN_CONFLICT`), it must be prepared at or beyond the tray's own stored `effective_texture_level` (`ERR_TEXTURE_LEVEL_VIOLATION`), it must be thickened at or beyond the tray's own stored `effective_liquid_level` when it declares a thickness at all (`ERR_LIQUID_LEVEL_VIOLATION`), it may not carry a tag listed in the pinned diet order's `forbidden_tag_codes_effective` as read live at that moment (`ERR_FORBIDDEN_TAG`), and it must be `ACTIVE` (`ERR_MENU_ITEM_DISCONTINUED`). Lines can be surveyed independently, filtered by `meal_order_id`, by the current `menu_item_id`, by the pre-substitution `substituted_from_menu_item_id`, or by `line_status`.

**Validation** is the tray's gate into production, performed by a `DietClerk`, and it is where the fullest check ladder in the system runs. The tray must be `PENDING_VALIDATION`; its meal period must be `PLANNED`, `FORECAST_LOCKED` or `IN_SERVICE`; its patient must be `ADMITTED`; the pinned diet order must be `ACTIVE`, else `ERR_DIET_ORDER_NOT_ACTIVE`; and the tray's `pinned_diet_order_version` must still equal that diet order's current `version`, else `ERR_DIET_ORDER_SUPERSEDED` — the tray has drifted away from the envelope it was priced against and must be re-pinned before it can pass. The patient's `npo_status` must read `NONE`, else `ERR_NPO_ACTIVE`. Then the per-line safety battery runs in its fixed order — allergen conflict, then texture, then thickness, then forbidden tag, then menu-item availability — with each of those five checks applied across **every** line of the tray before the next check is applied to any line, so when one line breaches a lower check and a different line breaches a higher one it is still the higher check that decides the response — where the texture test asks whether each line's item sits at or above the tray's `effective_texture_level` on the texture scale, the thickness test asks the same of items that declare a `liquid_level` against `effective_liquid_level`, and the tag test asks whether any line's item carries a code listed in the pinned order's `forbidden_tag_codes_effective`.

Only once every line is individually safe are the totals weighed against the envelope: `total_sodium_mg` must not exceed `effective_sodium_cap_mg`, `total_potassium_mg` must not exceed `effective_potassium_cap_mg`, and `total_carb_g` must not exceed `effective_carb_cap_g`, with any cap that is null skipped entirely rather than treated as zero. A breach of any of the three is `ERR_NUTRIENT_CAP_EXCEEDED`. Capacity comes last: the period's `committed_tray_count` plus this one tray must not exceed `production_capacity_trays`, else `ERR_TRAY_CAPACITY_EXCEEDED`; and when the period's `cost_ceiling_cents` is not null, its `committed_food_cost_cents` plus this tray's `food_cost_cents` must not exceed that ceiling, else `ERR_PERIOD_COST_CEILING_EXCEEDED`.

A tray that survives all of that moves `PENDING_VALIDATION → VALIDATED`. Its `effective_texture_level` and `effective_liquid_level` are refreshed from the pinned order's envelope, its four nutrient totals are recomputed, every `line_cost_cents` and the tray's `food_cost_cents` are recomputed, and `revalidation_required` is cleared to false. The period's `committed_tray_count` increments by 1 and this tray's `food_cost_cents` is added to `committed_food_cost_cents`; the period then re-runs its cost rollup across `period_overhead_cents`, `period_bulk_discount_cents` and `period_total_cost_cents`, and recomputes `forecast_variance_pct` whenever `forecast_tray_count` is neither null nor zero. Both the tray's `version` and the period's `version` increment by 1.

Cancellation is the `DietClerk`'s way out and is available from four fulfillment states. Cancelling from `PENDING_VALIDATION` simply moves the tray to `CANCELLED` and bumps its `version`, because such a tray never reserved anything. Cancelling from `VALIDATED`, from `IN_PRODUCTION` or from `PLATED` moves the tray to `CANCELLED` and, in each of those three cases identically, decrements the period's `committed_tray_count` by 1, subtracts the tray's `food_cost_cents` from `committed_food_cost_cents`, re-runs the period cost rollup and the forecast variance, and increments both the tray's `version` and the period's `version` by 1. This is the exact compensating action for the slot-and-cents reservation that validation took: both the tray count and the cents ledger return to their pre-validation values. `DELIVERED`, `CANCELLED` and `MISSED` are terminal fulfillment states, and a cancellation attempted from any of them reports `ERR_INVALID_STATE`. Trays may be surveyed by `patient_id`, `meal_period_id`, `diet_order_id`, and by either state dimension through `fulfillment_status` and `qa_status`.

### 3.7. The Tray Line: Production, Quality Assurance and Bedside Delivery

A tray carries **two independent state dimensions**, and they advance on separate triggers. `fulfillment_status` tracks where the tray is in production and delivery; `qa_status` tracks what quality assurance has established about it. Neither dimension's transition implies the other's, and both must reach the right value before a tray can reach the bedside.

The `TrayAide` drives the fulfillment dimension forward. Sending a validated tray to the tray line moves it `VALIDATED → IN_PRODUCTION` and requires two things beyond the tray's own state: the owning meal period must be `IN_SERVICE`, and the tray's `revalidation_required` flag must read false; all three failures — a tray that is not `VALIDATED`, a period that is not `IN_SERVICE`, and a tray still awaiting revalidation — report `ERR_INVALID_STATE`, and are checked in that order. That second condition is the teeth behind the supersede and discontinue cascades of §3.3 — a tray whose prescription changed under it cannot slip into production on the strength of a stale validation, and must be validated again first. Plating then moves the tray `IN_PRODUCTION → PLATED`, with no condition beyond the from-state. Both transitions increment the tray's `version` by 1.

Quality assurance begins once the tray is `PLATED`, and every quality-assurance transition requires the tray to be in that fulfillment state. The **accuracy check** is recorded by a `TrayAide` who supplies `observed_line_count` — a mandatory integer of zero or more counting the distinct lines actually seen on the tray — and optionally a `defect_codes` list, which defaults to empty when omitted. The check passes when `observed_line_count` equals the tray's line count **and** no defect codes are supplied; it fails when the observed count differs **or** the defect list is non-empty. From `NOT_CHECKED`, a passing check moves the quality dimension `NOT_CHECKED → ACCURACY_PASSED` and stamps `accuracy_checked_by_user_id` with the acting `X-User-ID`; a failing check moves it `NOT_CHECKED → ACCURACY_FAILED`, increments `accuracy_retry_count` by 1, and stamps `accuracy_checked_by_user_id` just the same. From `ACCURACY_FAILED` the aide re-runs the check after correcting the tray: a passing re-run closes the retry cycle `ACCURACY_FAILED → ACCURACY_PASSED` and re-stamps `accuracy_checked_by_user_id`, while a still-failing re-run leaves the dimension at `ACCURACY_FAILED` and increments `accuracy_retry_count` again. Every one of those four outcomes increments the tray's `version` by 1. `accuracy_retry_count` is never decremented and permanently penalises the tray's final service score.

The **temperature check** is the segregation-of-duties point on the tray line: it requires the tray's quality dimension to be `ACCURACY_PASSED` or `TEMP_FAILED`, and it requires the acting `X-User-ID` to differ from the `accuracy_checked_by_user_id` already recorded on the tray, else `ERR_SEGREGATION_OF_DUTIES`. The check supplies up to two readings in Celsius: `hot_probe_celsius` and `cold_probe_celsius`, each stored rounded half up to 1 decimal place and each stored whenever it is supplied at all — including a reading for a probe this tray does not require — while the satisfactory/unsatisfactory comparison below is made against the value exactly as supplied. Which of them is mandatory is decided by the tray's contents — `hot_probe_celsius` must be supplied whenever `requires_hot_probe` is true and `cold_probe_celsius` must be supplied whenever `requires_cold_probe` is true, and an omission is `ERR_TEMPERATURE_PROBE_REQUIRED`. The hot reading is satisfactory when the tray needs no hot probe at all, or when `hot_probe_celsius` is **at least 60.0 degrees Celsius**; the cold reading is satisfactory when the tray needs no cold probe at all, or when `cold_probe_celsius` is **at most 4.0 degrees Celsius**. Exactly 60.0 passes and exactly 4.0 passes; 59.9 and 4.1 do not.

When both readings are satisfactory the dimension moves `ACCURACY_PASSED → TEMP_PASSED`, storing the supplied readings and stamping `temperature_checked_by_user_id` with the acting `X-User-ID`. When either is not, it moves `ACCURACY_PASSED → TEMP_FAILED`, storing the readings, incrementing `temperature_retry_count` by 1, and stamping `temperature_checked_by_user_id` all the same. From `TEMP_FAILED` the tray is re-thermalised and re-probed: a satisfactory re-run moves `TEMP_FAILED → TEMP_PASSED` storing the new readings, and an unsatisfactory one leaves the dimension at `TEMP_FAILED` and increments `temperature_retry_count` again. Each outcome increments the tray's `version` by 1. `TEMP_PASSED` is the terminal value of the quality dimension.

**Bedside delivery** moves the tray `PLATED → DELIVERED` and demands three things at once: the fulfillment dimension is `PLATED`, the quality dimension has reached `TEMP_PASSED` — anything else is `ERR_QA_NOT_PASSED` — and the patient's `npo_status` reads `NONE`, since a hold that landed between plating and the bedside must stop the tray, reported as `ERR_NPO_ACTIVE`. On success `delivered_at` records the logical-clock instant, the period's `delivered_tray_count` increments by 1, and both the tray's `version` and the period's `version` increment by 1.

Delivery is also where the tray is scored. `delivery_window_compliance` places `delivered_at` against the period's window, and here the window is read as **half-open**: a delivery strictly before `window_start_at` is `EARLY`; a delivery at or after `window_end_at` is `LATE`, so the instant exactly equal to `window_end_at` is already late; anything in between is `ON_TIME`. `service_compliance_score` then starts at 100 and subtracts, in one pass: 25 points when the delivery was `LATE`, 10 points when it was `EARLY`, nothing when it was `ON_TIME`; 15 points for each accumulated `temperature_retry_count`; and 20 points for each accumulated `accuracy_retry_count`. The result is clamped at zero from below, so a tray with a long remedial history scores 0 rather than a negative number, and the score is a whole number in the range 0 through 100. Retry counters are cumulative across the tray's whole quality history and are never reset, which is what makes a single failed check follow the tray all the way to its score. Both `delivery_window_compliance` and `service_compliance_score` read null until the tray is `DELIVERED`.

### 3.8. Procedure Holds, Nil-Per-Os and the Missed-Meal Escalation

Procedures and meals compete for the same patient, and a **procedure hold** is how the two are coordinated. A `Physician` books one against a patient named by `patient_id`, identifying the clinical reason through a `procedure_code` and stating the severity through `npo_kind`, which is either `NPO_STRICT` — nothing by mouth at all — or `NPO_CLEAR_LIQUIDS`. The clinical interval runs from an inclusive `hold_start_at` to an exclusive `hold_end_at`, and the start must be strictly before the end, else `ERR_INVALID_WINDOW`. Around that interval sit two optional protective margins, `buffer_before_minutes` and `buffer_after_minutes`, each defaulting to 0 and each permitted to run from zero up to 720 minutes — a full twelve hours of protected time on either side. From them the system computes the two instants that actually govern everything downstream: `buffered_start_at` is `hold_start_at` moved earlier by `buffer_before_minutes`, and `buffered_end_at` is `hold_end_at` moved later by `buffer_after_minutes`.

Booking requires the patient to be `ADMITTED`, and it requires the buffered interval to be free. Two holds on the same patient whose `status` is `SCHEDULED` or `ACTIVE` may not occupy overlapping buffered intervals, and this comparison is **half-open** — the interval runs from `buffered_start_at` inclusive to `buffered_end_at` exclusive — so a new hold whose buffered start falls exactly on an existing hold's buffered end is accepted, where the closed-interval comparison used for meal period windows in §3.5 would have rejected it. A genuine collision is `ERR_PROCEDURE_HOLD_OVERLAP`. A new hold is stored `SCHEDULED`, with `requested_by_user_id` stamped from the acting `X-User-ID`, `released_at` null and `missed_meal_order_count` zero. Holds can be surveyed by `patient_id` and by `status`.

**Activating** the hold is the disruptive moment. It moves the hold `SCHEDULED → ACTIVE`, requires the patient to be `ADMITTED`, and requires that no other hold for this patient is already `ACTIVE` — a second concurrently active hold reports `ERR_INVALID_STATE`. Five cascade levels follow, each caused by the one above it. **Level one:** the patient's `npo_status` is set to the hold's `npo_kind` and `active_procedure_hold_id` is pointed at this hold. **Level two:** because the patient's `npo_status` has left `NONE`, every meal order for this patient whose meal period window — read from `window_start_at` inclusive to `window_end_at` exclusive — intersects the hold's buffered interval, and whose fulfillment dimension reads `PENDING_VALIDATION`, `VALIDATED`, `IN_PRODUCTION` or `PLATED`, moves to `MISSED` with `missed_reason` recorded as `NPO_HOLD`; the hold's `missed_meal_order_count` is set to the number of trays it moved. **Level three:** because each of those trays that had been `VALIDATED`, `IN_PRODUCTION` or `PLATED` left a committed state, its meal period decrements `committed_tray_count`, subtracts that tray's `food_cost_cents` from `committed_food_cost_cents`, and recomputes `period_overhead_cents`, `period_bulk_discount_cents`, `period_total_cost_cents` and `forecast_variance_pct`. **Level four:** because each tray entered `MISSED`, the patient's `missed_meal_count` and `protein_deficit_g` move, and the escalation described below may fire. **Level five:** because the patient's `npo_status` has left `NONE`, the ward's `active_patient_census` is recomputed. The hold's `version` and the patient's `version` each increment by 1.

**Releasing** the hold moves it `ACTIVE → RELEASED`, sets `released_at` to the logical-clock instant, returns the patient's `npo_status` to `NONE` and their `active_procedure_hold_id` to null, recomputes the ward's `active_patient_census`, and increments both the hold's `version` and the patient's `version` by 1. Release is deliberately **not** a rewind: trays the hold pushed into `MISSED` are not resurrected, and neither `missed_meal_count` nor `protein_deficit_g` is unwound. A hold that never took effect may instead be cancelled, moving `SCHEDULED → CANCELLED`, which increments the hold's `version` by 1 and frees its buffered interval for future overlap checks. `RELEASED` and `CANCELLED` are both terminal.

While a patient's `npo_status` is anything other than `NONE`, two operations are blocked outright with `ERR_NPO_ACTIVE`: a tray for that patient cannot be validated, and a plated tray cannot be delivered. The hold reaches further than that, though, because §3.4's step four rewrites the patient's whole therapeutic envelope for as long as the hold stands.

The **missed-meal escalation** runs on every system transition of a tray into `MISSED`, whether the cause was a hold activation or a period close. Within a single cascade the affected trays are processed in ascending `created_at` order, and for each one: the patient's `missed_meal_count` increases by 1, and their `protein_deficit_g` becomes the previous deficit plus that tray's `total_protein_g`, rounded half up to 1 decimal place after each addition. Then the escalation test runs. If the patient's `missed_meal_count` has reached **two or more**, and no nutrition consult for that patient currently sits in `REQUESTED`, `ASSIGNED` or `ASSESSED`, the system raises a consult on the patient's behalf: `patient_id` set to the patient, `acuity` set to `URGENT`, `reason_code` set to the literal string `MISSED_MEALS`, `requested_by_user_id` set to the literal string `SYSTEM`, `auto_generated` set to true, and `status` at `REQUESTED`. Consults that are already `SIGNED` or `CANCELLED` do not suppress the escalation; only an open one does. At most **one** automatic consult is raised per cascade, because the first creation makes the no-open-consult guard false for every later tray in that same cascade.

### 3.9. Consults, Supplement Regimens and Bedside Satisfaction

A **nutrition consult** is the department's mechanism for putting a dietitian's judgement behind a patient. Either a `Physician` or a `Dietitian` may raise one, naming the patient through `patient_id` and stating a `reason_code`; an optional `acuity` selects the turnaround class and defaults to `ROUTINE` when omitted, the alternative being `URGENT`. The consult is stored `REQUESTED`, with `requested_by_user_id` stamped from the acting `X-User-ID` and `auto_generated` false, and the patient must be `ADMITTED`. Its `due_at` is computed at creation from the consult's `created_at`: four hours later for an `URGENT` consult, twenty-four hours later for a `ROUTINE` one. `is_overdue` is derived rather than stored — it reads true whenever the logical clock stands at or past `due_at` while the consult's `status` is neither `SIGNED` nor `CANCELLED`, and false otherwise, which is why advancing the clock changes it. `assigned_dietitian_user_id`, `assessment_variant`, the four assessment inputs, `malnutrition_risk_score`, `risk_tier`, `recommended_supplement_item_id` and `signed_by_user_id` are all null on a fresh consult, and `linked_supplement_order_count` is zero. Consults raised by the missed-meal escalation of §3.8 are identical in every respect except that they carry `auto_generated` true, `requested_by_user_id` of `SYSTEM`, and an `URGENT` acuity.

The consult then walks a four-step path, every step of which belongs to a `Dietitian`. **Assigning** moves it `REQUESTED → ASSIGNED`, taking `dietitian_user_id` from the request body and storing it as `assigned_dietitian_user_id`. **Assessing** moves it `ASSIGNED → ASSESSED`, and carries the clinical payload: an `assessment_variant` of either `SCREENING` or `COMPREHENSIVE`, together with `weight_loss_pct` (unintentional weight loss as a percentage), `intake_pct` (the percentage of estimated energy needs the patient is meeting), and `bmi`. `albumin_g_dl`, serum albumin in grams per decilitre, is optional in general but **mandatory when `assessment_variant` is `COMPREHENSIVE`** — omitting it there is `ERR_ALBUMIN_REQUIRED` — and is ignored entirely by `SCREENING`. The dietitian may also name a `recommended_supplement_item_id` pointing at the oral supplement they recommend, which is null when none is recommended; when it is supplied it must resolve to a stored menu item, else `ERR_MENU_ITEM_NOT_FOUND`, but that item need not be `ACTIVE`. **Signing** moves it `ASSESSED → SIGNED`, records `signed_by_user_id` from the acting `X-User-ID`, and requires that identifier to differ from `requested_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. Signing is what unlocks activation for the supplement orders hanging off the consult. Every one of these transitions increments the consult's `version` by 1.

**Cancelling** is available from `REQUESTED`, from `ASSIGNED` and from `ASSESSED`, and behaves identically from all three: the consult moves to `CANCELLED`, every supplement order on it that is still `PENDING` moves to `CANCELLED`, and the consult's `version` increments by 1. `SIGNED` and `CANCELLED` are terminal. Consults can be surveyed by `patient_id`, by `status`, by `acuity`, by `auto_generated`, and by `recommended_supplement_item_id`.

Scoring the assessment produces `malnutrition_risk_score`, a value between 0 and 100 carried to 2 decimal places, from four graded sub-scores. **Weight loss** contributes 0 points when `weight_loss_pct` is below 5, 40 points when it is at least 5 but below 10, 70 points when it is at least 10 but below 15, and 100 points at 15 or above. **Intake** contributes 0 points when `intake_pct` is 75 or above, 40 points when it is at least 50 but below 75, 70 points when it is at least 25 but below 50, and 100 points below 25. **Body mass index** contributes 0 points when `bmi` is 22 or above, 40 points when it is at least 18.5 but below 22, 70 points when it is at least 16 but below 18.5, and 100 points below 16. **Albumin** contributes 0 points when `albumin_g_dl` is 3.5 or above, 40 points when it is at least 3.0 but below 3.5, 70 points when it is at least 2.5 but below 3.0, and 100 points below 2.5.

The two variants then weight those sub-scores differently, and they will disagree on identical inputs. The `SCREENING` variant is a three-factor bedside screen: it takes 0.50 of the weight-loss points plus 0.30 of the intake points plus 0.20 of the body-mass-index points, and rounds the sum half up to 2 decimal places; albumin is excluded altogether, so a patient with heavy weight loss but normal labs scores materially **higher** here. The `COMPREHENSIVE` variant is a four-factor assessment: it takes 0.35 of the weight-loss points plus 0.25 of the intake points plus 0.20 of the body-mass-index points plus 0.20 of the albumin points, again rounded half up to 2 decimal places; adding albumin at a weight of 0.20 dilutes the weight-loss term from 0.50 down to 0.35, so identical anthropometrics accompanied by a normal albumin land in a **lower** tier than `SCREENING` would report. `risk_tier` follows directly from the score: `LOW` when `malnutrition_risk_score` is below 30, `MODERATE` when it is at least 30 but below 60, and `HIGH` at 60 or above. Both fields read null before an assessment has been recorded.

A **supplement order** turns a recommendation into a standing regimen. A `Dietitian` creates one against a consult named by `consult_id`, carrying `expected_consult_version` as §2.6 requires, together with the product through `menu_item_id` and a `doses_per_day` of between 1 and 6. The referenced menu item must be `ACTIVE`. On creation, `patient_id` is copied from the consult rather than supplied by the caller, `ordered_by_user_id` is stamped from the acting `X-User-ID`, `status` is `PENDING`, `activated_at` and `cancelled_at` are null, and `daily_cost_cents` is computed as the menu item's `unit_cost_cents` multiplied by `doses_per_day`. Creation also increments the consult's `linked_supplement_order_count` by 1 and therefore its `version` by 1.

Activation requires the supplement order to be `PENDING`, the backing consult to be `SIGNED` — anything else is `ERR_CONSULT_NOT_SIGNED` — the patient to be `ADMITTED`, and the menu item to still be `ACTIVE`. It moves the order `PENDING → ACTIVE`, sets `activated_at` to the logical-clock instant, adds `daily_cost_cents` to the patient's `daily_supplement_cost_cents`, and increments both the order's `version` and the patient's `version` by 1. Cancelling an `ACTIVE` regimen moves it `ACTIVE → CANCELLED`, sets `cancelled_at`, subtracts exactly that `daily_cost_cents` back out of the patient's `daily_supplement_cost_cents` — returning the patient ledger to precisely its pre-activation value — and increments both versions by 1. Cancelling a `PENDING` regimen, whether directly or through the owning consult's cancel cascade, moves it `PENDING → CANCELLED` and sets `cancelled_at`, but leaves `daily_supplement_cost_cents` untouched, because a `PENDING` order never debited it; only the order's own `version` increments. `CANCELLED` is terminal. Supplement orders can be surveyed by `consult_id`, `patient_id`, `menu_item_id` and `status`.

The last word belongs to the patient. A `TrayAide` or a `DietClerk` records a **satisfaction survey** for a delivered tray, naming it through `meal_order_id` and supplying three integer ratings between 1 and 5 — `taste_score`, `temperature_score` and `accuracy_score` — plus an optional free-text `comment`. The rated tray's fulfillment dimension must read `DELIVERED`, else `ERR_MEAL_ORDER_NOT_DELIVERED`, and at most one survey may exist per tray, so a second attempt is `ERR_DUPLICATE_SURVEY`. The survey copies `patient_id` from the tray. Its `composite_score` is 0.40 of the `taste_score` plus 0.35 of the `temperature_score` plus 0.25 of the `accuracy_score`, rounded half up to 2 decimal places.

Recording a survey then refreshes the patient's rollup. `survey_count` becomes the number of surveys held for that patient, and `satisfaction_score_avg` becomes the sum of the **already-rounded** `composite_score` values of those surveys divided by their count, rounded half up to 2 decimal places once more; surveys are taken in ascending `created_at` order and no status filtering applies, because a survey is an immutable append-only event. **The evaluation order is pinned:** average the already-rounded composites and then round the average. The alternative reading — averaging the raw weighted sums and rounding only at the end — is rejected and produces a different answer. The patient's `version` increments by 1. Surveys can be surveyed by `meal_order_id` and `patient_id`, and, as §2.4 states, they carry no `updated_at` and no `version` of their own.

## 5. Error Code Catalogue

Every error response carries one of the identifiers below in its `data.error_id` field, together with a human-readable `message`, inside the standard error envelope of §2.2. The conditions that raise each identifier are not repeated here — they are stated in the §2 and §3 narratives, beside the rule each one guards, and the evaluation order among them is the ladder of §2.5. Two identifiers sit outside the table because they answer requests that never reach an endpoint at all: a path this API does not route answers `ERR_NOT_FOUND` (HTTP 404), and a routed path addressed with a method it does not accept answers `ERR_METHOD_NOT_ALLOWED` (HTTP 405).
